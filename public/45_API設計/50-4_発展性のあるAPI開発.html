    50 互換性と進化

    発展性のあるAPI開発 — 小さく始め、中核を育て、組み合わせで応える

    増田亨『現場で役立つシステム設計の原則』第8章「発展性に富んだ API 開発」の要点です。互換性のルールそのものではなく、API を長く育てるための 進め方と組み立て に絞って、単純なことをかんたんにできる API から始める理由、利用側との共同作業、中核 API のセット、バージョン管理と複合サービスの位置づけを学びます。

    もとにしたノート：50_互換性と進化/04_発展性のあるAPI開発

    ひとことで言うと

    発展する API は、よく使う小さな操作がかんたんに呼べる 状態から始まり、動かしながら 利用側と一緒に育てます。軸になるのはエンドポイントの数ではなく、繰り返し組み合わせる中核操作のセット です。破壊的変更はバージョンで、画面ごとの個別要望は 複合サービス（BFF など） で吸収します。

    1.このページで扱うこと

    • 単純なことをかんたんにできる API から始める理由
    • 動かしながら設計を発展させる
    • 利用側と提供側の共同作業の環境を整える
    • 中核となる API のセットを設計する
    • Web API のバージョン管理（増田本での位置づけ）
    • API を複合したサービスの提供

    前提として、リリース後の運用は APIの進化と運用、バージョンの付け方は バージョニング で扱っています。このページはそれらと重ならないよう、進め方と組み立て に絞ります。

    2.単純なことをかんたんにできる API から始める

    「将来必要になりそうなものを全部入れた」巨大なエンドポイントより、よく使う小さな操作が迷わず呼べる 状態を先に作ります。

    始め方

    • 中核リソースの CRUD／参照が予測どおりに呼べる
    • エラー形式・命名が最初から一貫している

    避けたい始め方

    • 全業務を 1 レスポンスに詰めた万能 API
    • 例外だらけの特別エンドポイントから設計する

    「大は小を兼ねる」万能 API は、かえって使いにくいことが多いです（API設計の原則）。部品として呼べる粒度については 検索と複合操作 も参照してください。

    3.動かしながら設計を発展させる

    1. 最小の契約を公開する
    2. 実際の呼び出し・問い合わせを見る
    3. フィールド追加は後方互換で行う（後方互換性）
    4. 形が歪んできたら、バージョンで整理する

    最初から完璧である必要はありません（APIの進化と運用）。一方で、エラー形式・認証・リソース命名 だけは早めに固めると、後の変更が楽になります。設計を段階的に深めていく進め方そのものは 42章：設計の進め方と段階的な深化 を参照してください。

    4.利用側と提供側の共同作業の環境を整える

    API は利用側との 契約 です。提供側だけで閉じて設計すると、現場の使い方とずれます。利用側が早い段階から関われる仕組みを用意します。

    仕組み目的
    OpenAPI 草案の共有実装前に形を合わせる
    フィードバック窓口「使いにくい」を早期に拾う
    CHANGELOG / Deprecation変更の見通しを共有する

    OpenAPI（API の仕様を決まった形式で書くための標準）の書き方は OpenAPIとドキュメント、チームでの運用は チームでAPI設計を守る で扱います。

    5.中核となる API のセットを設計する

    発展の軸は「エンドポイントの数」ではなく、繰り返し組み合わせて使う中核操作 です。

    中核が安定していると、個別の要望が来るたびに契約全体を壊さずに済みます。ドメイン（業務の領域）側の境界の決め方は APIとドメイン設計、ドメインの組み立て方は 42章：境界づけられたコンテキスト を参照してください。

    6.Web API のバージョン管理

    破壊的変更は避けきれないので、世代を分ける約束が必要です。方式と Sunset は バージョニング、互換のルールは 後方互換性 で扱いました。

    増田本の趣旨

    バージョンを盾に雑な破壊を正当化するのではなく、まず互換で伸ばし、どうしても必要なら世代を分ける。

    7.API を複合したサービスの提供

    クライアントに多数の中核 API を直接呼ばせず、間に「まとめる層」を置くことがあります。

    層役割
    中核 APIドメインの基本操作
    複合サービス／BFF（Backend For Frontend：画面ごとの専用窓口）画面・チャネル向けに組み立てる

    ゲートウェイ／BFF の位置づけは 41章：BFFとAPIゲートウェイ を参照してください。注意点は、複合しすぎて「また万能 API」に戻らないことです。組み立ては チャネル（Web・モバイルなど）固有のものに限定 します。

    8.よくある誤解

    誤解1：「何でもできる万能 API が 1 本あれば、利用者に親切」

    「大は小を兼ねる」万能 API は、パラメータもレスポンスも複雑になり、かえって使いにくくなります。よく使う小さな操作をかんたんに呼べる ことを優先します。

    誤解2：「API が発展する＝エンドポイントの数が増える」

    発展の軸は数ではなく 中核操作のセット です。中核が安定していれば、新しい要望は中核の組み合わせや複合サービスで応えられ、契約全体を壊さずに済みます。

    誤解3：「BFF や複合サービスには何を載せてもよい」

    何でも載せると、複合サービス自体が新たな万能 API になります。画面・チャネル固有の組み立て に限定し、業務の基本操作は中核 API に置きます。

    9.まとめ

    • かんたんに使える小さな API から始め、動かしながら育てる
    • エラー形式・認証・リソース命名だけは早めに固める
    • OpenAPI 草案・フィードバック窓口・CHANGELOG で、利用側と提供側が共同で設計する
    • 中核 API のセットの安定が発展の土台
    • 破壊はバージョンで、個別要望は複合サービス（BFF）で吸収する。ただし複合しすぎない

    次は 認証 です。
