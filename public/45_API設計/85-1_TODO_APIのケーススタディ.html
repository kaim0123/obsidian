    85 ケーススタディ

    TODO API のケーススタディ — 学んだ設計を1つの API にまとめる

    これまでのページで学んだ設計（URL とリソース、HTTP メソッド、ステータスコード、エラー形式、認証・認可、ページネーション、OpenAPI）を、シンプルな TODO API に当てはめる演習です。要件の整理から OpenAPI の草案、振り返りまでを順に追います。

    もとにしたノート：85_ケーススタディ/01_ケーススタディ_TODO_API

    ひとことで言うと

    TODO API は /todos と /todos/{id} の2つの URL に HTTP メソッドを組み合わせる だけで作れます。ポイントは、「自分の TODO だけを操作できる」ことを URL のネストではなく認可（所有者チェック）で守る こと、そして 成功・エラー・一覧の形を最初に統一しておく ことです。

    1.このページで扱うこと

    • 要件の整理：機能要件と非機能要件
    • リソースと URL の設計：/me・/todos・/todos/{id}
    • CRUD エンドポイントの定義：メソッド・パス・成功時のステータス、リクエストとレスポンスの例
    • エラー・認証の設計：401 / 403 / 404 / 422 と統一エラー形式
    • OpenAPI 草案と振り返り

    このページは「演習」なので、個々の考え方は各ページへのリンクで確認してください。たとえば URL の付け方は URLとリソースの設計、メソッドの使い分けは HTTPメソッドと操作の表現 にあります。

    2.要件の整理

    まず 何ができればよいか（機能要件） と、どんな約束ごとで作るか（非機能要件） を書き出します。設計はここから始まります。

    2.1 機能要件

    機能説明
    認証ログインユーザーの TODO のみ操作できる
    CRUD作成・一覧・詳細・更新・削除（Create / Read / Update / Delete の頭文字）
    完了トグル完了 / 未完了の切り替え
    一覧ページネーション、完了フィルタ

    2.2 非機能要件（約束ごと）

    • ベース URL：https://api.example.com/v1（/v1 はバージョン。バージョニング）
    • 形式は JSON、項目名は snake_case（created_at のように単語を _ でつなぐ書き方）、日時は ISO 8601 形式の UTC（2026-06-19T10:00:00Z）。JSONとデータ形式
    • 認証は Bearer Token（Authorization: Bearer <token> ヘッダーでトークンを送る方式）。認証

    3.リソースと URL の設計

    次に、API が扱う「もの」（リソース）を決め、それぞれに URL を割り当てます。

    リソースURL説明
    TODO（コレクション）/todos一覧・作成
    TODO（単一）/todos/{id}詳細・更新・削除
    現在ユーザー/meプロフィール確認用

    コレクション（同じ種類のリソースの集まり）と 単一リソース の2段で表すのが REST の基本形です。

    ネストは浅く

    /users/{id}/todos のように深くネストするより、/todos ＋認可 で十分です。「誰の TODO か」はトークンからわかるので、URL に user の id を入れる必要がありません。ネストの考え方は URLとリソースの設計 を参照してください。

    4.CRUD エンドポイントの定義

    リソースに HTTP メソッドを組み合わせて、操作を定義します。

    メソッドパス説明成功
    GET/v1/todos一覧（?completed=&page=&limit=）200
    POST/v1/todos作成201
    GET/v1/todos/{id}詳細200
    PATCH/v1/todos/{id}部分更新（title, completed）200
    DELETE/v1/todos/{id}削除204

    「完了トグル」は専用の URL を作らず、PATCH で completed を書き換える 形で表しています。作成は 201 Created、削除は本文なしの 204 No Content を返します（ステータスコード）。

    4.1 作成リクエスト

    POST /v1/todos HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json

{"title": "牛乳を買う"}

    4.2 作成レスポンス

    {
  "data": {
    "id": 42,
    "title": "牛乳を買う",
    "completed": false,
    "created_at": "2026-06-19T10:00:00Z",
    "updated_at": "2026-06-19T10:00:00Z"
  }
}

    本体を data で包む形にしておくと、一覧で meta を並べやすくなります（ボディの設計）。

    4.3 一覧レスポンス

    {
  "data": [
    {"id": 42, "title": "牛乳を買う", "completed": false}
  ],
  "meta": {
    "page": 1,
    "limit": 20,
    "total": 1
  }
}

    meta にはページ番号・1ページの件数・全件数を入れます。ページネーションの方式は ページネーション・フィルタ・ソート で詳しく扱います。

    5.エラー・認証の設計

    失敗したときに何を返すかも、最初に決めておきます。

    状況ステータスcode
    トークンなし401UNAUTHORIZED
    他人の todo403FORBIDDEN
    存在しない id404NOT_FOUND
    title 空422VALIDATION_ERROR
     
    {
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容に問題があります",
    "details": [
      {"field": "title", "message": "1 文字以上必要です"}
    ],
    "request_id": "req_xyz789"
  }
}
    • code はプログラムが判定するための固定文字列、message は人が読む説明です
    • details でどの項目が悪いかを返し、request_id（問い合わせ時にログを探すための番号）を付けます

    エラー形式の考え方は エラー設計 にまとめています。

    認可のルールは1つに統一する

    認可は todo の owner_id == トークンの user_id で統一します。詳細・更新・削除のどれでも同じチェックを通すことで、「他人の TODO を消せてしまう」といった認可漏れを防ぎます。認可の考え方は 認可、認可不備の典型は 73章：認可不備と認可の要件定義 を参照してください。

    6.OpenAPI 草案と振り返り

    6.1 OpenAPI 草案

    決めた内容を OpenAPI（API の仕様を YAML / JSON で書くための標準形式）に落とします。書き方は OpenAPIとドキュメント を参照してください。

    openapi: 3.0.3
info:
  title: Todo API
  version: 1.0.0
paths:
  /v1/todos:
    get:
      security: [{ bearerAuth: [] }]
      parameters:
        - name: completed
          in: query
          schema: { type: boolean }
        - name: page
          in: query
          schema: { type: integer, default: 1 }
      responses:
        '200':
          description: TODO 一覧
    post:
      security: [{ bearerAuth: [] }]
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [title]
              properties:
                title: { type: string, minLength: 1 }
      responses:
        '201':
          description: 作成成功
components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
    • security: [{ bearerAuth: [] }] で、その操作に Bearer 認証が必要なことを表します
    • minLength: 1 が「title 空なら 422」のルールに対応します

    6.2 振り返りチェック

    テーマ本ページでの適用
    REST/todos リソース ＋ HTTP メソッド
    エラー統一 JSON ＋ request_id
    認証認可Bearer ＋所有者チェック
    Paginationpage / limit / meta

    7.よくある誤解

    誤解1：「ユーザーごとのデータだから /users/{id}/todos にすべき」

    誰のデータかはトークンでわかるので、/todos ＋所有者チェックで十分です。URL に user の id を入れると、かえって「他人の id に書き換えて送る」攻撃の入口が増えます。ネストは浅く保ちます。

    誤解2：「完了トグルには /todos/{id}/complete のような専用 URL が必要」

    完了は TODO の状態（completed）の一部なので、PATCH /v1/todos/{id} で書き換えれば表せます。動詞の URL を増やさないのが REST らしい設計です。

    誤解3：「ログインしていれば、どの TODO でも操作してよい」

    認証（誰か）と認可（何をしてよいか）は別物です。ログイン済みでも、owner_id がトークンの user_id と一致しない TODO には 403 を返します。違いは 73章：認証と認可の違い を参照してください。

    8.まとめ

    • 要件の整理：機能（認証・CRUD・完了トグル・一覧）と約束ごと（v1・JSON・snake_case・ISO 8601 UTC・Bearer）を先に決める
    • リソースと URL の設計：/me・/todos・/todos/{id}。ネストは浅く
    • CRUD エンドポイントの定義：GET/POST/PATCH/DELETE と 200/201/204
    • エラー・認証の設計：401/403/404/422 と統一エラー JSON、認可は所有者チェックで統一
    • OpenAPI 草案と振り返り：決めたことを仕様書に落とし、学んだテーマと照らし合わせる

    次は、もう少し複雑な EC注文APIのケーススタディ です。
