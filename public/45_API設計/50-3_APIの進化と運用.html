    50 互換性と進化

    APIの進化と運用 — 小さく出して、見ながら育て、丁寧に畳む

    API はリリースして終わりではありません。最初から完璧を目指さず早く出すこと、利用状況の指標を見て改善すること、request_id を手がかりにした障害調査、レガシー API を段階的に置き換える手順、そして廃止と移行支援までを学びます。

    もとにしたノート：50_互換性と進化/03_APIの進化と運用

    ひとことで言うと

    API は 「動く契約」を早く出し、利用状況を見ながら育てる ものです。ただし 命名・エラー形式・認証 だけは最初に固めます。古い API は 並行提供 → Deprecation → 利用ゼロ近くまで待つ → Sunset の順で畳み、廃止は技術だけでなく コミュニケーション だと考えます。

    1.このページで扱うこと

    • 最初から完璧な API は不要
    • 利用状況を見ながら改善する（見るべき指標）
    • モニタリングと request_id による調査
    • レガシー API への段階的改善
    • API の廃止と移行支援
    • 発展性のある進め方への橋渡し（増田本）

    2.最初から完璧な API は不要

    何か月もかけて完璧な設計を目指すより、動く契約 を早く出し、利用者からのフィードバックで改善する方が現実的です。

    1. v1.0 として最小限の CRUD（作成・読み取り・更新・削除）を公開する
    2. 利用データ・問い合わせを集める
    3. 必要なフィールドを後方互換な形で追加する
    4. 形が歪んできたら、必要に応じて v2 で整理する

    完璧主義

    • 6 ヶ月、設計だけ
    • 使われないフィールドが多数

    進化型

    • 2 週間で β 公開
    • 必要なものから追加

    ここだけは最初に固める

    命名・エラー形式・認証 は、あとから変えると全クライアントに影響します。この 3 つだけは最初に固めておくと、後の変更コストが下がります（一貫性、エラー設計、認証）。

    3.利用状況を見ながら改善する

    改善の手がかりは「実際にどう使われているか」です。次のような指標を見ます。

    指標分かること
    エンドポイント別 RPS（1 秒あたりのリクエスト数）よく呼ばれるホットスポット
    4xx / 5xx 率設計・バリデーションの問題
    レイテンシ p99（遅い方から 1% の応答時間）一覧 API のページネーション不足など
    非推奨 API の利用数Sunset（廃止）のタイミング

    たとえばダッシュボードで「非推奨の /v1/users/list がまだ 30% 使われている」と分かれば、廃止を急がずに 移行促進キャンペーン を打つ、という判断ができます。ページネーションは ページネーション・フィルタ・ソート、システム全体の監視の考え方は 41章：観測性 を参照してください。

    4.モニタリングと request_id による調査

    エラー設計 で決めた request_id（リクエストごとに振る一意の番号）を、エラーレスポンスにもサーバーのログにも APM（アプリの性能監視ツール）にも残しておきます。

    {
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "しばらくしてから再試行してください",
    "request_id": "req_abc123"
  }
}
    調査の流れ操作
    ユーザーからの報告request_id を聞く
    ログ検索request_id でトレース（処理の足どりを追う）
    原因特定認可のバグ / DB タイムアウトなど

    request_id はレスポンスとサーバーログの橋 です。これがないと、「昨日の夕方にエラーが出た」という報告から該当ログを探すのはとても大変です。

    5.レガシー API への段階的改善

    古い（レガシー）API は、一度に切り替えずに段階を踏んで置き換えます。

    1. 新 API を並行して提供する（/v2/）
    2. 旧 API のレスポンスに Deprecation ヘッダを付ける
    3. 旧 API の利用数がゼロ近くになるまで待つ
    4. Sunset（廃止）し、503 または 410 Gone を返す
    フェーズ旧 API新 API
    並行期維持推奨
    移行期Deprecationドキュメントで誘導
    廃止停止唯一の正

    Deprecation・Sunset ヘッダの書き方は バージョニング で扱いました。

    6.API の廃止と移行支援

    API の廃止は 技術 だけでなく コミュニケーション の仕事です。利用者が困らずに移れるよう、次のような支援をします。

    支援内容
    移行ガイド旧 → 新の対応表
    SDK 更新クライアントライブラリ（SDK）の v2 対応
    猶予期間Sunset ヘッダ ＋ メール
    410 Gone廃止後も「なぜ使えないか」を JSON で返す

    廃止後に単に 404 を返すと、利用者は「URL を間違えたのか」と迷います。410 Gone（もう存在しない）と、移行先を書いたメッセージを返すと親切です。

    HTTP/1.1 410 Gone
Content-Type: application/json

{
  "error": {
    "code": "API_SUNSET",
    "message": "v1 は 2026-12-01 に廃止されました。/v2/users をご利用ください"
  }
}

    7.発展性のある進め方への橋渡し（増田本）

    「最小から公開し、フィードバックで伸ばす」がこのページの中心です。中核となる API のセット、利用側との共同作業、複合サービスまで含めた進め方は、次の 発展性のあるAPI開発 で扱います。アプリケーション間の連携方式の全体像は 41章：同期API・メッセージ・イベント駆動 を参照してください。

    8.よくある誤解

    誤解1：「公開前に、すべてを完璧に設計しなければならない」

    完璧を目指すほど公開が遅れ、使われないフィールドが増えがちです。最小限で早く出し、利用状況を見て後方互換に足していく方が現実的です。ただし 命名・エラー形式・認証 だけは最初に固めます。

    誤解2：「廃止日が来たら、エンドポイントを消せば終わり」

    廃止はコミュニケーションです。移行ガイド・SDK 更新・メールでの告知を行い、利用数がゼロ近くになるのを確かめてから止めます。止めたあとも 410 Gone と移行先のメッセージ を返します。

    誤解3：「エラーの調査はログを日時で探せば十分」

    リクエストが大量にあると、日時だけで該当ログを見つけるのは困難です。レスポンスとログの両方に request_id を残しておけば、ユーザーから番号を聞くだけで一直線にたどれます。

    9.まとめ

    • 最初から完璧な API は不要。動く契約を早く出し、ただし命名・エラー形式・認証は先に固める
    • RPS・4xx/5xx 率・p99 レイテンシ・非推奨 API の利用数を見て改善する
    • request_id はレスポンスとサーバーログの橋。調査はこの番号から始める
    • レガシー API は並行提供 → Deprecation → 利用ゼロ近くまで待つ → Sunset の順に置き換える
    • 廃止は移行ガイド・SDK・猶予期間・410 Gone で支援する

    次は 発展性のあるAPI開発、その次は 認証 です。
