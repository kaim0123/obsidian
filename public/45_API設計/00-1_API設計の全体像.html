    2.API 設計とは

    2.1 API はプログラム同士の「窓口」

    API（Application Programming Interface） は、プログラム同士がデータをやり取りするための「窓口」です。Web API では、クライアント（ブラウザ・スマホアプリ・他のサーバーなど、サービスを使う側）が HTTP（Web の通信の決まりごと）を使ってサーバーにリクエストを送り、JSON（データを文字で表す形式）などでレスポンスを受け取ります。API そのものの説明は APIとは で詳しく扱います。

    4.1 一貫性 — 同じ種類の操作は同じルールで

    一貫性 とは、同じ種類の操作を同じルールで表現することです。一貫性がない API は、エンドポイント（API の呼び出し先 URL）ごとに「命名が違う」「日付の形式が違う」「成功時の形が違う」などの混乱を生みます。

    なぜ重要か

    • クライアント側の共通処理（エラーハンドリング、ログ、SDK＝API を呼ぶための部品集）が書きやすい
    • 新しいエンドポイントを追加するときの判断基準になる
    • チーム開発で「各自バラバラに作る」を防げる
    項目良い例（統一）悪い例（バラバラ）
    命名snake_case または camelCase を全体で固定/getUser と /orders/list が混在
    日時常に ISO 8601（2026-06-19T10:00:00Z）2026/06/19 と Unix 秒が混在
    ID常に文字列 UUID数値 ID と UUID が混在
    レスポンス常に { "data": ... } でラップ配列を直返しする API とオブジェクト返しが混在
    真偽値true / false1 / 0 や "yes" / "no"

    実践のコツ

    1. API 設計ガイドラインを 1 枚にまとめる（命名、日時、エラー形式など）
    2. OpenAPI（Swagger）（API の仕様を機械が読める形で書く標準形式）などでスキーマを定義し、レビュー時の基準にする
    3. 既存 API があるなら、新規だけ直すのではなく、段階的に揃える計画を立てる
    ◯ 一貫した成功レスポンスの例 
    {
  "data": {
    "id": "usr_01HXYZ",
    "name": "田中太郎",
    "created_at": "2026-06-19T10:00:00Z"
  }
}

    4.2 RESTリソース設計 — URL は名詞、操作は HTTP メソッド

    REST（Representational State Transfer） は Web API でよく使われる設計スタイルです。中心となる考え方は 「URL は名詞（リソース）、操作は HTTP メソッドで表現する」 ことです。リソース とは操作の対象のことで、「ユーザー」「注文」「商品」など、ビジネス上の「もの」を URL で表します。

    /users              … ユーザー一覧（コレクション）
/users/{id}         … 特定のユーザー（単一リソース）
/orders/{id}/items  … 注文に紐づく明細（ネストしたリソース）
    原則良い例悪い例
    名詞を使うGET /usersGET /getUsers
    複数形でコレクション/orders/order
    階層は浅く/users/{id}/orders/api/v1/company/department/team/user/order
    動詞は URL に入れないDELETE /users/{id}POST /deleteUser
    小文字・ハイフン/order-items/OrderItems

    リソース設計の手順（初心者向け）

    1. ドメインの名詞を洗い出す（ユーザー、商品、カート、注文…）
    2. URL パスに落とす（/products, /carts, /orders）
    3. 関連はネストで表現（/orders/{order_id}/items）
    4. 検索・フィルタはクエリパラメータ（GET /products?category=book&sort=price）

    REST 以外も知っておく

    • RPC 風（/users/search のように操作名を URL にする形）は便利な場面もありますが、乱用すると一貫性が崩れやすい
    • GraphQL は「1 つのエンドポイントで必要なデータだけ取得」向き
    • 小規模プロジェクトでも REST の基本（名詞 + HTTP メソッド） は最初の土台として有効

    → 詳しくは RESTの考え方、URLとリソースの設計、REST以外のスタイル。

    4.3 HTTPメソッド — 「何をしたいか」を表す動詞

    HTTP メソッドは 「リソースに対して何をしたいか」 を表す動詞です。REST では、URL（名詞）とメソッド（動詞）の組み合わせで操作を表現します。

    メソッド意味典型用途冪等性安全
    GET取得一覧・詳細の参照○○
    POST作成新規リソース作成、非冪等な処理××
    PUT置換リソース全体の更新（存在しなければ作成も可）○×
    PATCH部分更新一部フィールドだけ変更△×
    DELETE削除リソース削除○×
    • 冪等性（べきとうせい）：同じリクエストを何度送っても結果が同じになること（POST は通常 ×）
    • 安全：サーバー側の状態を変えないこと（GET は ○）
    操作成功時失敗例
    GET 一覧200 OK404（存在しないコレクション）
    GET 詳細200 OK404 Not Found
    POST 作成201 Created + Location ヘッダ400 Bad Request, 409 Conflict
    PUT / PATCH 更新200 OK または 204 No Content404, 409
    DELETE 削除204 No Content404
    ✕ よくある間違い 
    GET /users/123/delete     … 削除を GET で行う（副作用あり・危険）
POST /users/123/update    … 更新を POST + 動詞 URL で行う
    ◯ メソッドで意図を表現する 
    DELETE /users/123         … 削除
PATCH /users/123          … 部分更新

    GET は副作用を持たせない のが鉄則です。キャッシュや prefetch（ブラウザが先回りしてリンク先を読み込むこと）で意図せず実行されるためです。削除・更新・作成は必ず POST / PUT / PATCH / DELETE を使います。

    → 詳しくは HTTPメソッドと操作、ステータスコード。

    4.4 エラー設計 — 失敗も予測可能な形で返す

    API は 成功だけでなく失敗も、予測可能な形で返す 必要があります。クライアントはエラー内容を見て、再試行・ユーザーへの表示・ログ送信を判断します。

    1. HTTP ステータスコード で大分類（4xx = クライアントの問題、5xx = サーバーの問題）
    2. レスポンスボディ で詳細（機械可読なコード + 人間向けメッセージ）
    3. 一貫した JSON 形式 で返す
    コード意味使う場面
    400Bad Requestバリデーションエラー、形式不正
    401Unauthorized認証されていない（ログインが必要）
    403Forbidden認証済みだが権限がない
    404Not Foundリソースが存在しない
    409Conflict重複、楽観ロック競合
    422Unprocessable Entity形式は正しいが業務ルール違反
    429Too Many Requestsレート制限超過
    500Internal Server Errorサーバー内部エラー
    503Service Unavailableメンテナンス、過負荷
    ◯ エラーレスポンスの例 
    {
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容に誤りがあります",
    "details": [
      {
        "field": "email",
        "code": "INVALID_FORMAT",
        "message": "メールアドレスの形式が正しくありません"
      }
    ],
    "request_id": "req_abc123"
  }
}
    • code は固定文字列（VALIDATION_ERROR など）。クライアントが分岐しやすい
    • message は人間向け。多言語化するなら message_key + クライアント側翻訳も可
    • request_id を付けると、サポート・ログ調査が楽になる
    • 5xx の詳細（スタックトレース）は本番レスポンスに含めない
    • バリデーションエラーは フィールド単位 で返すとフォーム UI と相性が良い

    → 詳しくは エラー設計、ステータスコード早見表。

    4.5 バージョニング — 古いクライアントを動かし続ける

    API は公開すると クライアントが依存し始める ため、破壊的変更（既存のクライアントが動かなくなる変更）をいきなり入れられません。バージョニング は、古いクライアントを動かし続けながら新しい仕様を提供する仕組みです。

    なぜ必要か

    • モバイルアプリはユーザーが古いバージョンを長期間使う
    • 外部連携先はすぐに改修できない
    • 「フィールド名を変えただけ」がクライアント側の大量修正につながる
    方式例メリットデメリット
    URL パス/v1/users, /v2/users分かりやすい、キャッシュしやすいURL が長くなる
    ヘッダAccept: application/vnd.myapi.v2+jsonURL を汚さない初心者にはやや難
    クエリ/users?version=2実装が簡単あまり推奨されない

    初心者・チーム開発では URL パス方式（/v1/）が最も理解しやすい ことが多いです。

    https://api.example.com/v1/users
https://api.example.com/v2/users
    • v1 をいつまで維持するか（非推奨 → 廃止日）をドキュメントで明示する
    • 変更は CHANGELOG（変更履歴）に記録する
    • 内部 API（自社フロント専用）なら、バージョンなし + 同時デプロイも選択肢

    → 詳しくは バージョニング。

    4.6 後方互換性 — 変更後も既存のクライアントが壊れない

    後方互換性 とは、既存のクライアントが、変更後も壊れずに動き続けることです。バージョニングとセットで考えるのが基本です。

    安全な変更（後方互換を保てる）

    • 新フィールドの追加：レスポンスに nickname を追加（クライアントは無視できる）
    • 新エンドポイント追加：GET /users/{id}/preferences を新設
    • オプショナルなクエリ追加：?include=orders を追加
    • 新しいエラーコード追加：既存コードはそのまま

    破壊的変更（後方互換が崩れる）

    • フィールド削除・リネーム：user_name → name
    • 型の変更：price: "1000" → price: 1000
    • 必須化：任意だった email を必須に
    • ステータスコード変更：404 → 403
    • URL 変更：/users → /members

    破壊的変更は新バージョン（v2）で行い、v1 は一定期間維持 するのが定石です。

    小さな追加     → 同じ v1 で OK
形を変える変更 → v2 を切る + v1 に非推奨マーク

    レスポンスに deprecated フィールド や Sunset HTTP ヘッダ で「いつ消えるか」を伝えると、クライアント側の移行がスムーズです。

    → 詳しくは 後方互換性、APIの進化と運用。

    4.7 Pagination — 一覧は分割して返す

    一覧 API（GET /users, GET /orders など）は、データが増えると 一度に全部返すと遅く・重く なります。Pagination（ページネーション） は、結果を 分割して返す 仕組みです。レスポンスサイズと DB 負荷を抑え、モバイル回線でも扱いやすくし、タイムアウトを防ぎます。

    オフセット方式（page / limit）

    GET /users?page=2&limit=20
    • リクエスト：page（何ページ目）, limit（1 ページ件数）
    • レスポンス例：{ "data": [...], "meta": { "page": 2, "limit": 20, "total": 150 } }
    • メリット：実装・理解が簡単、「N ページ目へジャンプ」しやすい
    • デメリット：データ追加・削除で 重複や取りこぼし が起きやすい

    カーソル方式（cursor）

    GET /users?limit=20&cursor=eyJpZCI6MTIzfQ
    • リクエスト：limit, cursor（前回レスポンスの続き位置）
    • レスポンス例：{ "data": [...], "meta": { "next_cursor": "...", "has_more": true } }
    • メリット：リアルタイム更新に強い、大量データ向き
    • デメリット：任意ページへのジャンプが難しい
    用途おすすめ
    管理画面の表、件数が少〜中オフセット
    SNS タイムライン、ログ、無限スクロールカーソル
    • limit に上限 を設ける（例：最大 100）
    • total（総件数） は DB コストが高い場合、省略または概算を検討
    • ソート順を固定する（例：created_at desc, id desc）
    • レスポンスに has_more や next_cursor を含め、クライアントの実装を単純にする

    → 詳しくは ページネーション・フィルタ・ソート。

    4.8 認証認可 — 「誰か」と「何ができるか」

    用語意味例
    認証（Authentication）「あなたは誰か」を確認ログイン、API キー、JWT
    認可（Authorization）「何ができるか」を確認管理者のみ削除可、自分の注文のみ閲覧可

    認証 → 認可 の順で確認します。ログインしていない（401）と、ログイン済みだが権限不足（403）を混同しないことが大切です。用語の違いは 73章：認証と認可の違い で詳しく扱っています。

    方式概要向いている場面
    API Key固定文字列をヘッダに付与サーバー間連携、シンプルな内部 API
    Bearer Token（JWT 等）Authorization: Bearer <token>モバイル・SPA、ステートレス
    OAuth 2.0 / OpenID Connect第三者 IdP（ログインを担当する外部サービス）経由の委任Google ログイン、SaaS 連携
    Session Cookieサーバー側セッション + Cookie伝統的な Web アプリ
     
    GET /v1/users/me HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

    認可の設計

    1. リソース所有者チェック — GET /orders/{id} で、注文の user_id が本人か
    2. ロールベース（RBAC） — admin, editor, viewer など役割で権限を決める
    3. スコープ — OAuth の read:orders, write:products など、許可する操作の範囲
    認証 OK + 注文の所有者 → 200
認証 OK + 他人の注文   → 403 Forbidden
認証 NG                → 401 Unauthorized

    セキュリティの基本

    • HTTPS 必須（平文 HTTP でトークンを送らない）
    • トークン・API キーを URL クエリに載せない（ログに残りやすい）
    • レート制限（429）で brute force（総当たり攻撃）を抑える
    • 本番と開発で キーを分ける
    • 最小権限の原則 — 必要なスコープだけ付与

    → 詳しくは 認証、認可、レート制限と冪等性。方式そのものは 73章：OAuth2.0の仕組み、74章：JWTの構造と検証、73章：RBAC・ABAC・ACLの使い分け を見てください。

    7.よくある誤解

    誤解1：「動いていれば API 設計は後回しでよい」

    API は公開した瞬間からクライアントが依存し始めます。命名やレスポンス形式・エラー形式を後から変えると 破壊的変更 になり、全クライアントの修正が必要になります。最初に一貫性のルールを 1 枚決めておくだけで、後の手戻りが大きく減ります。

    誤解2：「401 も 403 も『だめ』という意味だから同じ」

    401 は 認証されていない（ログインが必要）、403 は 認証済みだが権限がない という別の意味です。クライアントは 401 ならログイン画面へ、403 なら「権限がありません」の表示へと、対応を変えます。

    誤解3：「8 テーマを最初から全部完璧にしなければならない」

    最初に決めるべきなのは表の「初心者が最初に決めること」の列だけです。ページネーションの方式やバージョニングの細部は、利用状況を見ながら育てていけます。ただし一貫性・エラー形式・認証と HTTPS は後から直すと影響が大きいので、最初に決めます（優先順位は API設計の原則）。

    8.まとめ

    • API 設計は「誰が使っても迷わない窓口」を、長く使える形で決めること
    • API 設計は設計階層の中で「プログラムの外側に向けた契約」の層
    • 一貫性・REST リソース・HTTP メソッド・エラー・Pagination が 使いやすい窓口の形 を決める
    • バージョニング・後方互換性が 長く使える窓口の寿命 を決める
    • 認証認可（401 と 403 の区別、HTTPS）が 安全な窓口 をつくる
    • 章は 10 → 20 → … → 85 の順に読めば、基礎から実践まで順に学べる
