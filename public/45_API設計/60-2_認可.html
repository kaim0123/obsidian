    60 セキュリティと信頼性

    認可 — 認証のあとで「この操作をしてよいか」を決める

    認証で「誰か」が分かったあとに、「この操作をしてよいか」を判断するのが認可です。401 と 403 の使い分け、自分のリソースだけを操作させる所有者チェック（403 と 404 のどちらを返すか）、ロール（RBAC）とスコープ、最小権限の原則を API 設計の目線で学びます。

    もとにしたノート：60_セキュリティと信頼性/02_認可

    ひとことで言うと

    認可 は 権限チェック（何ができる？）です。認証されていなければ 401、認証済みでも許可がなければ 403（存在を隠したいなら 404）を返します。多くの API では「自分のリソースだけ操作できる」所有者チェックが基本で、ロールやスコープで 必要最小限の権限 だけを与えます。

    2.認可（Authorization）とは何か

    認可 は 権限チェック です。認証 で「誰か」が分かったあと、「何ができるか」を決めます。たとえば、ToDo を削除するリクエストでは次のように判断します。

    所有者なら 204 No Content（成功・本文なし）、そうでなければ 403 Forbidden を返します。

    3.認証と認可の違い（401 と 403）

    ステータス意味クライアントの対応
    401 Unauthorized認証されていない / 無効ログイン・トークン更新
    403 Forbidden認証済みだが許可なし操作を諦める・管理者に連絡

    401

    「身分証を見せてください」

    403

    「身分は分かったが、この部屋には入れません」

    混同すると、クライアントが 無限にリトライ したり（403 なのに再ログインを繰り返すなど）、誤った画面 を表示したりします。401 の返し方は 認証 を参照してください。

    4.リソース所有者チェック

    多くの API には「自分のリソースだけ操作できる」というルールがあります。

    GET /v1/todos/42
  → todo.user_id == ログインユーザー.id ?
      Yes → 200 + todo 本体
      No  → 403（または 404 で存在を隠す）

    他人のリソースを見せてしまうと、ID を書き換えるだけで他人のデータが読めてしまいます。これは API で特に多い脆弱性です（72章：WebAPIの脆弱性）。

    4.1 403 と 404 のどちらを返すか

    方針403404
    メリット権限不足であることが明確存在自体を隠せる（セキュリティ）
    向く場面内部 API公開 API（ID 推測対策）

    403 を返すと「その ID のデータは存在する」ことが相手に伝わります。公開 API では、ID を順番に試して存在を探る攻撃を防ぐため、404 で隠す方針がよく取られます。どちらを使うかは チームで統一 してください。

    5.ロールベース（RBAC）とスコープ

    方式考え方例
    RBAC（ロールベースアクセス制御）ロール（役割）に権限を付与するadmin は全ユーザーを削除できる
    スコープトークンに許可する操作を列挙するread:orders、write:orders

    次は JWT のペイロード（中身の部分）の例です（概念を示すもの）。sub はユーザー ID、roles はロール、scope は許可された操作です。

    {
  "sub": "user-123",
  "roles": ["member"],
  "scope": "read:todos write:todos"
}

    管理画面の API では RBAC、外部サービスとの連携では 細かいスコープ がよく使われます。RBAC・ABAC・ACL の比較は 73章：RBAC・ABAC・ACLの使い分け、実装の進め方は 73章：権限管理・ロール管理の実装、JWT の検証は 74章：JWTの構造と検証 を参照してください。

    6.最小権限の原則

    最小権限（Least Privilege） とは、必要な権限だけを付与する ことです。漏洩や誤操作が起きたときの被害を小さくできます（71章：最小権限とデータ最小化）。

    悪い例

    • 読み取り専用アプリに admin ロール
    • 全 API Key が DELETE 可能

    良い例

    • read:products スコープのみ
    • 用途別の Key（在庫連携用・分析用）

    6.1 権限を設計するときの問い

    • この操作に本当に必要か？
    • 漏洩したときの被害は？
    • ロール / スコープを分離できるか？

    開発者としての方針

    認可は 設計段階 で、エンドポイントごとに「誰が呼べるか」を表にしておくと、実装漏れが減ります。

    7.よくある誤解

    誤解1：「ログインしていれば、どのリソースでも操作してよい」

    認証は「誰か」が分かっただけです。/v1/todos/42 の所有者がそのユーザーかどうかを 毎回チェック しないと、ID を書き換えるだけで他人のデータを操作できてしまいます。

    誤解2：「権限がないときは常に 403 を返すのが正しい」

    403 は権限不足が明確に伝わる反面、「そのリソースが存在する」ことも伝えてしまいます。公開 API では 404 で存在を隠す 選択肢もあります。大事なのは、どちらにするかをチームで統一することです。

    誤解3：「とりあえず admin 権限を渡しておけば、後で困らない」

    強い権限ほど、漏れたときの被害が大きくなります。読み取りだけのアプリには read:* のスコープだけ、用途ごとに Key を分けるなど、最小権限 で設計します。

    8.まとめ

    • 認可は権限チェック。認証で「誰か」が分かったあとに「何ができるか」を決める
    • 未認証・無効は 401、認証済みで許可なしは 403。混同するとクライアントが誤動作する
    • 「自分のリソースだけ操作できる」所有者チェックが基本。403 と 404 のどちらを返すかはチームで統一する
    • 管理画面では RBAC、外部連携では細かいスコープがよく使われる
    • 最小権限の原則で、必要な権限だけを与える。エンドポイントごとに「誰が呼べるか」を表にする
