    RESTとGraphQLの違い — 取得のしかた・エラー・キャッシュ・設計のコツ

    同じ「ユーザーと投稿を表示する」画面を、REST と GraphQL で作るとどう違うのでしょうか。オーバーフェッチ・アンダーフェッチ、エンドポイント、バージョニング、エラー処理、キャッシュの違いを具体例で比べ、GraphQL のスキーマ設計とベストプラクティス、そしてどちらを選ぶべきかを整理します。

    もとにしたノート：82_GraphQL/03_RESTとGraphQLの違い、GraphQL API Basics & Best Practices (Explained Simply)

    ひとことで言うと

    REST は リソースごとのエンドポイントが決まった形のデータを返す のに対し、GraphQL は 1つのエンドポイントにクライアントが欲しい形を伝え、その形だけを返す 方式です。そのぶん GraphQL では エラーでも HTTP 200 が返り、errors フィールドで判断する、HTTP キャッシュが使いにくい といった違いがあります。GraphQL は REST の代替ではなく、適切な場面で選ぶ道具 です。

    • 基本的な違いと、GraphQL が生まれた理由

    • GraphQL のスキーマ設計（契約としてのスキーマ）と ベストプラクティス

    GraphQL の用語（スキーマ・クエリ・ミューテーション）は GraphQLの基本 で説明しています。

    2.基本的な違い

    項目REST APIGraphQL
    エンドポイント複数（リソースごと）単一（通常は /graphql）
    データ取得固定されたデータ構造クライアントが指定
    HTTP メソッドGET, POST, PUT, DELETEPOST（クエリ／ミューテーション）
    バージョニングURL で管理（/v1/users）スキーマで管理
    エラーハンドリングHTTP ステータスコードレスポンス内でエラーを返す

    2.1 GraphQL が生まれた理由

    GraphQL は Facebook が、とても具体的な悩みを解決するために作りました。クライアントが何度も API を呼んでも、なお必要なデータがそろわない という悩みです。

    • Facebook のページには user・posts・comments・likes などの API があり、クライアントはそれぞれを別々に呼ぶ
    • それでも画面に必要なデータがそろわず、同じ API に何度もリクエストすることになる
    • すべての取得が終わるまでページは完成しないので、レイテンシ（待ち時間）が積み上がる

    GraphQL では 単一の GraphQL エンドポイント に対し、クライアントが レスポンスの形（フィールドのツリー）を指定 します。通信は HTTP のままですが、たとえば「ID 123 のユーザーの name だけ」「posts は title だけ（画像は不要）」のように、画面単位で必要なデータだけを取れます。コメントのようにネストしたオブジェクトでも、取るフィールドを細かく指定できます。

    3.具体例で比較：ユーザー情報とその投稿を取得

    3.1 REST API の場合

    リクエスト1：ユーザー情報を取得

    GET /api/users/1

    レスポンス1

    {
  "id": "1",
  "name": "太郎",
  "email": "taro@example.com",
  "address": "東京都...",
  "phone": "090-1234-5678",
  "birthday": "1990-01-01",
  "profileImage": "..."
}

    リクエスト2：ユーザーの投稿を取得

    GET /api/users/1/posts

    レスポンス2

    [
  {
    "id": "1",
    "title": "投稿タイトル",
    "content": "投稿内容...",
    "createdAt": "2024-01-01",
    "updatedAt": "2024-01-02",
    "tags": ["tag1", "tag2"],
    "likes": 10,
    "comments": [...]
  }
]

    問題点

    • 2回のリクエストが必要
    • ユーザー情報に不要なデータ（住所、電話番号など）が含まれる
    • 投稿情報にも不要なデータが含まれる可能性がある

    3.2 GraphQL の場合

    リクエスト

    {
  user(id: "1") {
    name
    email
    posts {
      title
      content
    }
  }
}

    レスポンス：GraphQL のレスポンスは data の中に、クエリと同じ形で入って返ってきます。

    {
  "data": {
    "user": {
      "name": "太郎",
      "email": "taro@example.com",
      "posts": [
        {
          "title": "投稿タイトル",
          "content": "投稿内容..."
        }
      ]
    }
  }
}

    メリット

    • 1回のリクエストで完了
    • 必要なデータだけを取得
    • 関連データも一緒に取得できる

    4.オーバーフェッチとアンダーフェッチ

    4.1 オーバーフェッチ（Over-fetching）— 取りすぎ

    REST API の問題：GET /api/users/1 で、ユーザーの すべての情報 が返ってきます。

    項目この画面で
    名前必要
    メール必要
    住所不要
    電話番号不要
    生年月日不要
    プロフィール画像不要

    結果：ネットワーク帯域の無駄になります。

    GraphQL の解決：必要なデータだけを指定できるので、無駄がありません。

    {
  user(id: "1") {
    name
    email
  }
}

    4.2 アンダーフェッチ（Under-fetching）— 足りなくて何度も呼ぶ

    REST API の問題：ユーザー一覧画面を表示する場合、次のように呼び出しが増えます。

    1. ユーザー一覧を取得：GET /api/users
    2. 各ユーザーの投稿数を取得：GET /api/users/1/posts/count、GET /api/users/2/posts/count、…
    3. 各ユーザーのフォロワー数を取得：GET /api/users/1/followers/count、…

    結果：多数のリクエストが必要になります。

    GraphQL の解決：1回のリクエストで必要なデータをすべて取得できます。

    {
  users {
    id
    name
    postsCount
    followersCount
  }
}

    5.エンドポイントとバージョニングの違い

    5.1 エンドポイント

    REST API

    GET    /api/users    # ユーザー一覧
GET    /api/users/1  # ユーザー詳細
POST   /api/users    # ユーザー作成
PUT    /api/users/1  # ユーザー更新
DELETE /api/users/1  # ユーザー削除
GET    /api/posts    # 投稿一覧
GET    /api/posts/1  # 投稿詳細
...

    エンドポイントが増えると管理が大変になります。

    GraphQL

    POST /graphql

    すべての操作が1つのエンドポイントで完結します。

    5.2 バージョニング

    REST API では、URL でバージョンを管理する必要があります（詳しくは バージョニング）。

    /api/v1/users
/api/v2/users
/api/v3/users

    GraphQL では、スキーマの中でバージョンを管理します。新しいフィールドを追加しても、既存のクライアントは自分が指定したフィールドしか受け取らないので影響を受けません。

    type User {
  id: ID!
  name: String!
  email: String!
  # 新しいフィールドを追加しても既存のクエリは動作する
  phone: String
}

    「足すのは安全、消す・変えるのは危険」という考え方は REST でも同じです（後方互換性）。

    6.エラーハンドリングの違い

    6.1 REST API：HTTP ステータスコードで表す

    200 OK
400 Bad Request
404 Not Found
500 Internal Server Error

    ステータスコードの意味は ステータスコード、REST でのエラー本文の設計は エラー設計 で扱っています。

    6.2 GraphQL：レスポンスの中で errors を返す

    GraphQL は、エラーがあっても多くの場合 HTTP ステータスは 200 OK のまま返します。そのため、成功か失敗かはレスポンス本文の errors 配列 で判断します。

    {
  "data": null,
  "errors": [
    {
      "message": "ユーザーが見つかりません",
      "locations": [{"line": 2, "column": 3}],
      "path": ["user"]
    }
  ]
}
    • 部分的な成功：一部のフィールドは取れて、user だけが null、その理由が errors に載る、という返し方もできます
    • errors には REST で使っていたような情報を載せるのが慣習です
      • message：メッセージ（例：Not found）
      • path：スキーマ上のどのフィールドで失敗したか（例：user）
      • extensions などに HTTP 相当のステータス（例：404）を入れ、何のエラーか分かるようにする

    動画の例のように、user が null で、errors にステータス 404 を明記した形は次のようになります。

    {
  "data": { "user": null },
  "errors": [
    {
      "message": "not found",
      "path": ["user"],
      "extensions": { "status": 404 }
    }
  ]
}

    クライアント実装の注意

    「HTTP 200 だから成功」とは見なさず、errors の有無と内容を必ずチェック します。

    7.キャッシュの違い

    REST API

    HTTP のキャッシュの仕組みを活用できます。

    • ETag
    • Last-Modified
    • Cache-Control

    GraphQL

    単一のエンドポイントに POST で問い合わせるため、URL 単位の HTTP キャッシュは使いにくいです。代わりに、クライアント側でキャッシュを実装 する必要があります（Apollo Client など）。

    8.GraphQL のスキーマ設計

    GraphQL の スキーマ は、クライアントとサーバーの間の 契約（contract） です。REST の「エンドポイントごとの暗黙の形」ではなく、スキーマに型と操作がはっきり書かれます。

    概念役割REST とのざっくりした対応
    型（Type）User などのドメインオブジェクトと、そのフィールド（id, name, posts など）を定義レスポンスの構造
    ネストした型posts がプリミティブ（文字列や数値のような基本の値）でなければ、Post 型を別に定義し [Post] のように参照関連リソースの埋め込み
    Queryデータの 読み取り（例：ID を受け取り User を返す user）GET
    Mutationデータの 変更（例：name を受け取り User を返す createUser）POST / PUT / PATCH / DELETE

    良いスキーマは ドメインモデルを反映 し、直感的で柔軟（拡張しやすい）です。型と Query・Mutation の名前や戻り値が一貫していれば、クライアントもサーバーも同じスキーマを「共通言語」として使えます。ドメインと API の関係は APIとドメイン設計 も参考になります。

    8.1 クエリとミューテーションの使い方

    • Query：スキーマで定義した user を呼び、name・posts の title など欲しい属性だけを並べると、その通りのデータが1回で返る
    • Mutation：たとえば createPost に title と body を渡して投稿を作り、作成後に受け取りたいフィールド（id・title）も同じミューテーションで指定 できる。REST では作成後に別の GET が要ることも多い

    9.GraphQL 設計のベストプラクティス

    プラクティス内容
    スキーマを小さくモジュール化巨大な1つのスキーマより、ドメインごとに分割・合成しやすい形にする
    深いネストを避けるuser → posts → comments → … と無限にネストできてしまう。N+1 問題（1件ごとに追加の取得が発生して問い合わせが爆発する問題）や負荷の温床になりやすい
    クエリ深度制限（depth limiting）サーバー側でネストの深さに上限を設ける（例：6〜7 階層まで）
    型・フィールドに意味のある名前クライアントも同じスキーマを読むので、命名がそのまま API の使いやすさになる
    Mutation には Input 型を使うCreateUserInput のような入力用の型に引数をまとめ、変更操作の引数を構造化する

    Input 型は、たとえば次のように書きます。

    input CreateUserInput {
  name: String!
  email: String!
}

type Mutation {
  createUser(input: CreateUserInput!): User!
}

    10.いつ REST を使い、いつ GraphQL を使うか

    REST API が適している場面

    • シンプルな CRUD 操作
    • HTTP キャッシュが重要な場合
    • 既存の REST API が十分に機能している
    • シンプルなデータ構造
    • ファイルアップロードや、既存の REST 向けインフラとの相性を重視する場合

    GraphQL が適している場面

    • 複数のクライアント（Web、iOS、Android）が異なるデータを必要とする
    • モバイルアプリなど、ネットワーク効率が重要
    • 複雑なデータ構造とリレーション
    • リアルタイム更新が必要
    • フロントエンドとバックエンドのチームが分離している
    • クライアント主導でレスポンスの形を決めたい、往復回数とオーバーフェッチを減らしたい複雑な UI
    特徴REST APIGraphQL
    柔軟性低い（固定されたエンドポイント）高い（クライアントが指定）
    学習コスト低い中程度
    キャッシュ簡単複雑
    複雑なクエリ難しい簡単
    エコシステム成熟している成長中

    結論

    GraphQL は REST API の代替ではなく、適切な場面で選択すべきツール です。「GraphQL の方が常に優れている」わけではありません。プロジェクトの要件に応じて選びましょう。画面ごとに API をまとめる別の方法として 41章：BFFとAPIゲートウェイ もあります。

    11.よくある誤解

    誤解1：「HTTP 200 が返ってきたから成功」

    GraphQL はエラーでも多くの場合 200 OK を返します。errors 配列の有無と内容 を必ず確認します。data の一部だけが取れている「部分的な成功」もあります。

    誤解2：「GraphQL ならバージョン管理は一切いらない」

    フィールドの 追加 は既存クエリに影響しないので URL でバージョンを分けずに済みますが、フィールドの削除や型の変更は既存クライアントを壊します。スキーマの中で互換性を保ちながら進化させる、という考え方です。

    誤解3：「自由にクエリを書けるのだから、制限はかけない方がよい」

    ネストは無限に深くできてしまい、N+1 問題やサーバー負荷の原因になります。クエリ深度制限（例：6〜7 階層）などでサーバー側に上限を設けます。

    12.まとめ

    • REST はリソースごとのエンドポイントが固定の形を返し、GraphQL は単一エンドポイントでクライアントが欲しい形を指定する
    • GraphQL は Facebook が、複数 API の繰り返し呼び出しとレイテンシの積み上がりを解決するために作った
    • オーバーフェッチ（取りすぎ）・アンダーフェッチ（足りずに何度も呼ぶ）を1回のクエリで解決できる
    • バージョンは URL ではなくスキーマで管理。フィールド追加は既存クエリに影響しない
    • エラーは HTTP ステータスではなく errors フィールドで判断する（部分的な成功もある）
    • HTTP キャッシュは使いにくく、クライアント側のキャッシュ（Apollo Client など）が必要
    • スキーマ（型・Query・Mutation）が契約。ドメインモデルを映すように設計し、モジュール化・深度制限・意味のある命名・Input 型を心がける
    • GraphQL は常に正解ではない。要件に応じて REST と使い分ける
