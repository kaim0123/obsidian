    10 APIの基礎

    APIとは — プログラム同士の「窓口」と疎結合

    API の正体は、プログラム同士が機能やデータをやり取りするための「窓口」です。窓口のたとえ、Web API・ライブラリ API・OS API の違い、内部 API と外部公開 API、システム統合と API 連携の違い、そして API の本質である「疎結合」と「情報隠蔽」がなぜイノベーションを加速するのかを、身近な例で学びます。

    もとにしたノート：10_APIの基礎/06_APIとは、02_APIの種類と全体像、機械オンチに「API」を説明する動画

    ひとことで言うと

    API（Application Programming Interface） は、アプリケーション同士が機能やデータをやり取りするための 「窓口」であり「約束事」 です。使う側は 中身を知らなくても、決まった形式で頼めば決まった結果が返ってくる。お互いの内部に踏み込まない 疎結合 のおかげで、組み合わせやすく、変更もしやすくなります。

    2.API の定義と役割

    API（Application Programming Interface） は、「アプリケーション同士が機能やデータをやりとりするための "窓口" や "約束事"」です。プログラム同士が安全かつ効率的に連携するための インターフェース（接点・境界面）を指します。

    キーワード意味
    インターフェース利用者（クライアント）が提供者（サーバーやライブラリ）に「どんな機能が、どんな方法で使えるか」を明示する 契約
    カプセル化内部実装を隠し、外部からは決められた方法でのみ操作できるようにする

    2.1 窓口のたとえ — 中身を知らなくても頼める

    会計ソフトの freee が楽天銀行と「API 連携」して明細を自動で取り込む場面を考えます。楽天銀行は外から使うための 窓口（API） を用意していて、freee は「この口座の明細をちょうだい」と 決まった形式で依頼 するだけです。楽天銀行の内部がどうなっているかを freee は知りません。

    大企業の受付も同じです。営業部が何階にあるかを知らなくても、「営業部の山田部長と 15 時からアポがあります」と伝えれば案内してもらえます。

    API の本質

    利用者側は 内部の仕組みを気にしなくてよく、言われた通りの情報を渡せば望む結果が返ってくる。これが API の強みです。

    2.2 ユーザーインターフェースのプログラム版

    API はよく 「ユーザーインターフェースのプログラム版」 と言われます。人間は銀行のサイトを開き、ログインを押し、明細ボタンを押して明細を見ます。API は これと同じことをプログラム同士が自動で行えるようにするもの です。

    • 相手はプログラムなので、見た目の画面（UI）は要りません。決まったフォーマットのメッセージを送ると、決まったフォーマットで返ってくる だけです
    • イメージは LINE で「定型文を送ると定型文が返ってくる」やり取り（「牛乳買ってきて」「はい」）
    • 私たちは気づかないうちに 1 日平均 1 万回ほど API のお世話になっていると言われます。スマホのホーム画面の天気表示（お天気情報を返す API）、X のタイムラインに埋め込まれた YouTube 動画、タクシーアプリの地図など、外から情報を取ってきて表示しているものの多くは API 経由 です
    • 普段「API」と言うときは、ふつうのインターネット回線を通して情報を取る Web API を指すことが多いです。特別な専用回線で直接つないでいるような仕組みは、一般に言う Web API とは別物の場合もあります
    • URL をブラウザに入力するだけで使える API もたくさんあります（例：アクセスするとランダムな親父ギャグを 1 つ返す API）

    2.3 実装言語が違ってもやり取りできる

    システム A は Python、システム B は C で書かれている、ということはよくあります。API は 「決まったメッセージが来たら、決まったメッセージを返す」 だけなので、それぞれの内部で何の言語が動いているかは関係ありません。極端に言えば「3 と送ったらこの情報、4 と送ったらこの情報」と決めておけば、どの言語からでも 3 を送るだけです。

    電話の ナビダイヤル に似ています。「1 を押せばこうなる」と決まっているので、英語話者がかけても番号を押せば必要な情報にたどり着けます。

    3.API の種類

    3.1 Web API・ライブラリ API・OS API

    種類通信の相手特徴例
    Web APIネットワーク越しHTTP 経由でやり取り。HTTP + JSON が主流天気予報アプリが気象データ API から天気を取得／Web アプリが Google Maps API で地図を表示／EC サイトが決済 API（Stripe、PayPal 等）で支払い処理
    ライブラリ API同じプロセス内プログラム内で関数やクラスを呼び出す。型で契約JavaScript の Array.prototype.map()、Python の os モジュール
    OS APIOS カーネルOS の機能（ファイル操作、ネットワーク、プロセス管理など）を使う。システムコール（OS に処理を頼む呼び出し）Windows API、POSIX API

    Web API は 別のマシン・別のチーム が使うことが多いため、契約の明確さ が特に重要です。この章は Web API を中心に扱います。

    3.2 内部 API と外部公開 API

    種類利用者設計の厳しさ
    内部 API自社フロント・自社サービス同時デプロイ（サーバーとクライアントを同時に更新）なら緩めも可
    外部公開 APIパートナー・一般開発者後方互換・ドキュメント必須

    外部公開 API は 変更の影響が読めない（誰がどう使っているか分からない）ため、バージョニング とドキュメントが必須になります。

    3.3 クライアント（ブラウザ・モバイル・サーバー）の視点

    API は サーバー側の都合 だけで決めると使いにくくなります。設計するときは、次のクライアントを想像してください。

    クライアント気をつけること
    ブラウザ（SPA）CORS（別のドメインの API を呼ぶときのブラウザの制限。72章：CORSの仕組み）、トークン管理（74章：セッション方式とトークン方式）
    モバイルアプリ古いバージョンが長期間残る
    他サーバー安定性、レート制限、冪等性（レート制限と冪等性）

    API 設計は橋渡し

    API 設計は「サーバーを書く人」と「クライアントを書く人」の 橋渡し です。

    4.システム統合と API 連携は別物

    「連携」と聞くと、銀行のシステム統合を思い浮かべる人もいるかもしれません。みずほ銀行は、合併した複数の銀行のシステムを 中身まで 1 つに統合 しようとして、大きな障害を何度も起こしました。業務フローも明細の保存方法も違うシステムを 1 つにまとめるのは、とても難しいのです。

    API 連携はこれとは 質的に違います。楽天銀行と freee は お互いの内部には何も手を出さず、窓口で「明細ちょうだい」「はい」とやり取りするだけです。仮に銀行 A・B・C の間にそれぞれ API があれば、各システムは別々のまま「明細ちょうだい」に答えるだけでよく、共存させるのは比較的楽です。

    5.疎結合と情報隠蔽 — API の本質

    5.1 社内でも API で区切る

    API は外部との連携だけでなく、システムの内部 でも使います。通販サイトを運営していて、「在庫管理システム」を作る人と「通販サイト」を作る人が別の担当者だとします。

    • 通販サイト側が在庫管理システムの中身（データベース）を直接いじれると、思わぬ使い方で壊されそうです
    • そこで在庫管理システムの担当者は 内部を隠して API を立てます。通販サイト側は「商品 A の在庫を教えて」と API に頼み、「10 個だよ」と返してもらいます

    このように、つながってはいるが互いの中身には踏み込まない関係を 疎結合（そけつごう：結合がゆるい、まばらなこと）と呼びます。疎結合は API の本質であり、ソフトウェア工学の重要概念です（詳しくは 42章：凝集度と結合度）。逆に、互いの内部に深く依存し合っている状態を 密結合 と呼びます。

    5.2 疎結合だと内部を気楽に変えられる

    在庫データに「不良品数」を加えることになり、これまでの「在庫数」を「通常品数」と「不良品数」に分けたい（通常品は通販で、不良品はアウトレットで売る）とします。

    疎結合（API で区切っている）

    「在庫を聞かれたら通常品数を返す」ように API の中だけを書き換えれば済みます。項目名をためらいなく変えられます。

    密結合（通販サイトが DB を直接見ている）

    通販サイトのどこで「在庫数」を使っているか分からないため、社内システム全体を見渡して、使っている箇所を全部直す 地獄になります。

    疎結合の良いところは 責任範囲を明確にしてくれる ことです。API で区切られていれば、自分のエリアのことだけを気にし、外向けには約束どおりの返事をしておけばよくなります。「在庫を聞かれたらちゃんと返す」という動作さえ保てば内部はどう変えてもよいので、「こっちの方が効率がいいのでは」と思ったらすぐ改善に挑戦できます。今風に言えば 開発の心理的安全性が上がる のです。密結合では、変えた方がよいと分かっていても、どこで何が起きるか分からず怖くて誰も触れなくなります。

    なお、API は間に立つ「通訳」というより、提供する側が用意した窓口 です。「在庫数」という問い合わせを、提供側の言葉で言う「通常品数」に置き換えて答えるのは、提供側の窓口の仕事です。

    5.3 情報隠蔽のメリット

    内部を隠すことを 情報隠蔽 と呼びます（悪い意味ではなく、「分からなくてよい」状態をつくる好ましい設計のことです。詳しくは 43章：カプセル化と情報隠蔽）。

    メリット内容
    安全外から内部を触れないので、余計な操作をされない
    使いやすい実装の詳細を理解しなくても使える
    イノベーションを加速する組み合わせやすく、変更しやすい（次の節）

    5.4 API がイノベーションを加速する理由

    一時期「API エコノミー」（API を公開し合うことで経済を盛り上げる、という考え方）という言葉が流行しました。API がイノベーションを加速する理由は大きく 2 つあります。

    1. 他のサービスと組み合わせやすく、組み合わせ爆発が起きる：タクシーアプリが Google Maps の API を使えるおかげで、高精度な地図付きのアプリが作れます。タクシー会社が自前で地図を作るのは現実的ではありません
    2. 開発者も気楽に変更・改善できる：システムの内部を API で区切っておけば、各担当が自分の範囲を安心して変えられます（5.2 の在庫の例）

    6.社会学の「弱い紐帯」との共通点

    社会学者マーク・グラノベッターの 「弱い紐帯の強み」 という研究があります。労働者を調べると、親しい人より 「たまに会う程度の人」からの情報で今の仕事に就いた人が多い ことが分かりました。強い紐帯（親しい集団）では情報が共有されすぎていて新しさがなく、新しい情報は弱い紐帯からもたらされるからです。

    観点弱い紐帯（人間関係）疎結合（ソフトウェア）
    つながり方つながってはいるが、深く踏み込まないAPI でつながるが、内部には干渉しない
    もたらすもの新しい情報・イノベーション組み合わせ・変更しやすさ・イノベーション
    心理的安全性村社会的でなく、監視のプレッシャーが少ない変更しやすく、開発の心理的安全性が上がる

    まったく関係のない分野なのに、主張されている利点がそっくりです。「API 的な（要件だけの）会話」をするのはよくありませんが、人間関係でも適度に弱くつながっておく方が新しい動きが生まれやすい と言えます（動画では、ゆる言語ラジオのサポーターコミュニティでも、課外活動や結婚といった「イノベーション」が起きている例が紹介されていました）。次に API 連携のボタンを押すときは、「弱い紐帯でたくさんのサービスがつながっているんだな」と思い出してみてください。

    7.API の設計思想と進化

    設計思想内容
    疎結合API を介してやり取りすることで、システム同士が独立して開発・運用できる
    再利用性一度作った API を他のアプリやサービスでも活用できる
    バージョン管理API の仕様変更時はバージョンを分けて互換性を保つ（バージョニング）
    セキュリティ認証・認可・レートリミットなどで安全性を担保する（APIセキュリティ）

    API の進化

    • Web API の普及で、外部サービス連携や マイクロサービスアーキテクチャ（システムを小さなサービスに分け API でつなぐ構成。41章：モノリスとマイクロサービス）が一般化した
    • REST、GraphQL、gRPC など多様な API 設計手法が登場した（REST以外のスタイル）
    • API ファースト開発（API 仕様を先に決めてから実装する）も主流になった

    API は現代のソフトウェア開発・サービス連携に不可欠な基盤技術です。

    8.API 設計の位置づけと、この章で扱う範囲

    API 設計は設計階層の中で、モジュール設計とクラス設計のあいだにある プログラムの外側に向けた契約 の層です。43章：モジュール設計 で決めたモジュール境界のうち、外部に公開する部分を具体化します（階層の図は API設計の全体像）。

    この章の中心は REST ベースの Web API です。

    • HTTP メソッド + リソース URL
    • JSON ボディ
    • 認証（Bearer Token など）

    80 APIスタイルで GraphQL・RPC・Webhook など 他のスタイル にも触れますが、まず REST の基本を固めることが先です。アプリ同士をつなぐ手段としての Web API の位置（共有 DB・ファイル・メッセージとの比較）は、ノート「06_アプリケーション間連携の価値と4つの方式」にまとめています。サービス間の通信方式は 41章：同期API・メッセージ・イベント駆動 も参考になります。

    9.よくある誤解

    誤解1：「API は 2 つのシステムの間に立つ通訳（翻訳者）」

    API は第三者の通訳ではなく、提供する側が用意した窓口 です。決まったメッセージが来たら決まったメッセージを返すだけなので、相手が何の言語で書かれていても関係ありません。

    誤解2：「API 連携＝システム統合」

    システム統合は中身まで 1 つにまとめる作業で、とても難しく失敗しやすいものです。API 連携は お互いの内部に干渉せず、窓口でやり取りするだけ なので、質的に別物です。

    誤解3：「API は外部サービスと連携するときだけ使う」

    API は社内のシステム同士を区切るのにも使います。在庫管理システムの例のように、内部を API で区切っておくと 責任範囲がはっきりし、内部を安心して変更できる ようになります。

    誤解4：「情報隠蔽は、悪いことを隠す意味」

    ソフトウェアの情報隠蔽は、使う側が内部を知らなくてよい状態をつくる 好ましい設計のことです。外から余計な操作をされず、内部を自由に変えられるようになります。

    10.まとめ

    • API はアプリケーション同士が機能やデータをやり取りするための「窓口」であり「約束事」
    • 使う側は中身を知らなくても、決まった形式で頼めば決まった結果が返ってくる（ユーザーインターフェースのプログラム版）
    • 種類は Web API・ライブラリ API・OS API。Web API は別マシン・別チームが使うので契約の明確さが特に重要
    • 外部公開 API はバージョニングとドキュメントが必須。ブラウザ・モバイル・他サーバーなどクライアントの視点で設計する
    • API 連携はシステム統合と違い、お互いの内部に干渉しない 疎結合
    • 疎結合と情報隠蔽は、安全・使いやすさ・変更しやすさをもたらし、イノベーションを加速する（「弱い紐帯の強み」と同じ構造）
