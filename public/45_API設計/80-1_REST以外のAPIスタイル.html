    REST以外のAPIスタイル — GraphQL・RPC風・Webhook・gRPC・WebSocket の使い分け

    API の作り方は REST だけではありません。必要なデータだけを取る GraphQL、操作を URL に書く RPC 風 API、サーバーから通知する Webhook、高性能な内部通信の gRPC、リアルタイムの WebSocket。それぞれの特徴と向き・不向き、そして「混ぜすぎ」のリスクを見ていきます。

    もとにしたノート：81_スタイルの比較/01_REST以外のAPIスタイル、02_GraphQLと新しいAPI

    ひとことで言うと

    API のスタイルは 要件で選ぶ道具 です。公開の CRUD なら REST、複雑な画面のデータ取得なら GraphQL、イベントの通知なら Webhook、内部の高性能通信なら gRPC、リアルタイム双方向なら WebSocket。ただし混ぜるほど認証・エラー形式・ドキュメントがバラバラになるので、「公開面は REST で統一」などのルールを決めてから 増やします。

    1.このページで扱うこと

    • GraphQL：1つのエンドポイントで必要なデータだけを取得する
    • RPC 風 API：/users/search のような操作指向の URL
    • Webhook：サーバーからクライアントへの通知
    • gRPC：高性能な内部連携
    • WebSocket：双方向・リアルタイムの通信
    • スタイルの選び方と混在のリスク、実務での注意点

    ここまでの章で学んだ REST（RESTの考え方）を基準に、「REST 以外だと何が違うのか」を比べます。サービス同士のつなぎ方（同期・メッセージ・イベント駆動）というアーキテクチャ側の話は 41章：同期API・メッセージ・イベント駆動 にあります。

    2.GraphQL — 必要なデータだけ取得

    GraphQL は Facebook（現 Meta）が開発した、API のためのクエリ言語とランタイム（クエリを解釈して実行する仕組み）です。1つのエンドポイントに対して、クエリ言語 で欲しいフィールドを指定します。

    • クライアントが必要なデータだけを柔軟に取得できる
    • スキーマ駆動・型安全・自己記述的（スキーマを見れば何が取れるか分かる）
    • 1つのエンドポイントで、複数のリソースを横断して取得できる
    query {
  user(id: "42") {
    name
    todos(status: OPEN) { title }
  }
}

    上の例では「ユーザー 42 の名前と、未完了 TODO のタイトルだけ」を1回で取っています。投稿を取る例も同じ形です。

    query {
  user(id: 1) {
    name
    posts {
      title
      createdAt
    }
  }
}
    RESTGraphQL
    リソースごとにエンドポイントが多数基本は 1 URL（/graphql）で柔軟にクエリ
    データの取りすぎ・足りなさ（過不足 fetch）が起きやすい必要なフィールドだけ。オーバーフェッチ／アンダーフェッチ や N+1 的な往復を減らせる
    HTTP のキャッシュが効きやすいキャッシュ設計が別途必要
    形はエンドポイントごとの取り決めスキーマで型・構造・バリデーションを明示

    モバイルアプリのように 通信量の削減 が重要なときに選ばれます。GraphQL の中身は GraphQLの基本、REST との詳しい比較は RESTとGraphQLの違い で扱います。

    3.RPC 風 API — /users/search のような操作指向

    RPC（Remote Procedure Call、遠くのサーバーの関数を呼ぶ考え方）風 の API は、URL に 動詞 が入る形式です。

    POST /v1/users/search
POST /v1/orders/cancel
POST /v1/reports/generate
    REST 風RPC 風
    GET /v1/users?q=taroPOST /v1/users/search
    リソース（名詞）中心操作（動詞）中心

    複雑な検索・バッチ処理では、RPC 風の方が 分かりやすい こともあります。ただし 検索と複合操作 で扱う「REST らしくない操作」は、チーム内で命名ルールを統一 してください。人によって /search だったり /find だったりすると、一貫性（一貫性）が崩れます。

    4.Webhook — サーバーからクライアントへの通知

    Webhook は、イベントが起きたときにサーバーが 相手（クライアント）の URL へ POST する仕組みです。普段とは逆向きに、サーバー側から知らせに行きます。

      注文完了（サーバー）
       │
       └── POST https://partner.example.com/hooks/order-completed
               Body: {"order_id": "ord-99", "status": "paid"}
    ポーリングWebhook
    クライアントが定期的に GET するサーバーが push（送りつける）
    実装が簡単署名検証・再送の設計が必要

    受け取る側は、X-Signature ヘッダーで ペイロード（送られてきた本文）の署名 を検証し、本当にそのサーバーから来たものか確かめます。また再送で同じ通知が2回届くことがあるので、冪等処理（同じ event_id は1回だけ処理する）を実装します。冪等性については レート制限と冪等性 を見てください。

    5.gRPC の概要（高性能な内部連携）

    gRPC は Google が開発した、Protocol Buffers（型付きのバイナリ形式でデータを表す仕組み）と HTTP/2 による 高性能な RPC です。バイナリ通信で高速、多言語に対応しており、マイクロサービス間の通信でよく使われます。

    用途向き
    マイクロサービス間◎ 低レイテンシ（待ち時間が短い）・型安全
    ブラウザ向けの公開 API△ ツールチェーンが REST より重い
    ストリーミング◎ 双方向通信ができる
     
      外部公開 API    →  REST / JSON（汎用性）
  内部サービス間  →  gRPC（性能・契約の厳密さ）

    初心者は REST をマスターしてから gRPC を検討すれば十分です。

    6.WebSocket — 双方向のリアルタイム通信

    WebSocket は、一度つないだ接続を開いたままにして、クライアントとサーバーが双方向に やり取りする仕組みです。チャットやゲームなど、リアルタイム性 が必要な場面で使います。GraphQL の サブスクリプション（変更の監視）も WebSocket を使って通知を受け取ります（GraphQLの基本）。

    7.スタイルの選び方と混在のリスク

    7.1 要件ごとの候補

    要件候補理由
    公開 CRUD API・シンプルな操作RESTシンプルで、幅広い互換性がある
    複雑な画面向けのデータ取得GraphQL柔軟なデータ取得・型安全・複数 API の統合
    イベント連携Webhook起きたときにサーバーから通知できる
    内部の高性能通信gRPC高速・多言語・マイクロサービス向き
    リアルタイム通信WebSocket双方向に即時にやり取りできる

    7.2 混在のリスク

      混在のリスク
       │
       ├─ 認証方式がバラバラ
       ├─ エラー形式がエンドポイントごとに違う
       └─ ドキュメントが分散

    開発者としての方針

    1つのプロダクトの中でも「公開面は REST で統一」 など、ルールを決めてからスタイルを増やします。

    7.3 実務での注意点

    GraphQL

    キャッシュ・認可・N+1 問題への対策が必要です。

    gRPC

    HTTP/2 やバイナリ通信の知識が必要です。

    新しい手法全般

    「要件・運用・エコシステム」に合わせて選びます。

    8.よくある誤解

    誤解1：「GraphQL や gRPC は REST より新しいから、全部置き換えるべき」

    スタイルは新旧ではなく 向き・不向き で選びます。公開 CRUD やキャッシュが効く場面では REST が今も有力です。GraphQL にはキャッシュ・認可・N+1 対策、gRPC には HTTP/2 やバイナリ通信の知識という別のコストがあります。

    誤解2：「URL に動詞を入れる RPC 風は間違い」

    複雑な検索やバッチ処理では、POST /v1/users/search のような RPC 風の方が分かりやすいこともあります。大事なのは チームで命名ルールをそろえる ことです。

    誤解3：「Webhook は相手の URL に POST するだけで済む」

    受け取る側は 署名検証（X-Signature）で送り主を確かめ、再送に備えて 同じ event_id は1回だけ処理 する必要があります。送る側も再送の設計が要ります。

    9.まとめ

    • GraphQL：1つのエンドポイントで必要なデータだけ取得。スキーマ駆動・型安全。キャッシュ設計は別途必要
    • RPC 風 API：/users/search のような操作指向。複雑な操作で分かりやすいが、命名ルールを統一する
    • Webhook：サーバーからクライアントへの通知。署名検証と冪等処理が必須
    • gRPC：Protocol Buffers + HTTP/2 の高性能 RPC。内部連携向き。まず REST をマスターしてから
    • WebSocket：双方向のリアルタイム通信
    • スタイルは要件で選び、混在させるなら「公開面は REST で統一」などのルールを先に決める
