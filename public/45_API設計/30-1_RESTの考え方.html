    30 リソース設計

    RESTの考え方 — URL は名詞、操作は HTTP メソッド

    Web API の基本スタイルである REST を学びます。REST とは何か、リソースと表現、REST の4大設計原則（アドレス可能性・統一インターフェース・ステートレス性・接続性）を身近なたとえで理解し、「URL は名詞、操作は HTTP メソッド」というルール、ステータスコードと冪等性、スケールと進化を支える工夫、REST の利点と限界、REST 以外のスタイルとの関係までを押さえます。

    もとにしたノート：30_リソース設計/01_RESTの考え方、REST APIの仕組み（動画メモ）、REST APIを超分かりやすく図解で説明します ~RESTfulなAPI設計とは~（動画メモ）

    ひとことで言うと

    REST は厳密な規格ではなく、Web API の 設計の考え方（スタイル） です。操作の対象を リソース として名詞の URL で表し、何をするかは GET・POST・PUT・PATCH・DELETE などの HTTP メソッドで表します。サーバーはクライアントの状態を覚えない（ステートレス）ので、どこまでもスケールしやすくなります。この考え方に従った API を RESTful な API と呼びます。

    2.REST とは何か

    REST（Representational State Transfer） は、Roy Fielding（ロイ・フィールディング。HTTP の仕様づくりにも関わった研究者）が提唱した Web API の設計スタイル です。厳密な規格（仕様）というより、よく使われる設計の考え方 として理解するとよいです。仕様ではなく 一連のルール に従う API を RESTful と呼びます。

    REST はシンプルで大半の用途に十分なため、Web やサーバー間の通信で最も普及した API のスタイルになっています。この章でも REST ベースの Web API を中心に扱います。

    2.1 設計思想の一つ — 家の建築にたとえると

    REST をひとことで言うと、Web サービスの設計思想の一つ です。家を建てるとき、「木の温かみが欲しいから木造にする」「地震に強くしたいから鉄筋コンクリートにする」のように、目的によって設計方針を選びます。それと同じように、「大量のアクセスがある SNS を作りたい」という目的があるから REST という考え方を採用する、というイメージです。

    REST 以外には SOAP（XML でメッセージをやり取りする方式）という設計方式もありましたが、現在は REST が主流です。

    2.2 REST の中心思想

    REST の中心思想意味
    リソースURL で表す「もの」（ユーザー、注文など）
    表現（Representation）JSON など、リソースを送受信するときの形式
    ステートレス各リクエストは独立している（HTTPの基本「ステートレス」）
    統一インターフェースHTTP メソッドで操作を統一する

    2.3 名前の意味

    頭文字英語直訳
    RERepresentational代表的な（表現の）
    SState状態
    TTransfer転送する・運ぶ

    直訳だけでは分かりにくいですが、動画では「URL を代表（Representation）として、リソースの状態（＝情報）を転送する」という意味だと考えられる、と説明しています（諸説あり）。たとえば「最新の投稿」を表す URL にアクセスすると、その URL を代表として最新の投稿という情報が送られてくる、というイメージです。

    3.リソースと表現（Representation）

    リソース は操作の 対象 です。表現 は、そのリソースを JSON などで どう表すか です。

    リソース（概念）表現（JSON）
    ユーザー usr_123{ "id": "usr_123", "name": "田中" }
    注文 ord_456{ "id": "ord_456", "total": 3000 }

    同じリソースでも XML や JSON など 複数の表現 があり得ますが、現代の Web API では JSON が主流 です（JSONとデータ形式）。

    4.REST の4大設計原則

    REST の設計ルールは6つほどありますが、大きな4つを押さえればよいとされます。この4つを満たした API が RESTful な API です。

    ① アドレス可能性（Addressability）

    URL を送ると、その URL に対応するデータが 一意に 返ってくる

    ② 統一インターフェース（Uniform Interface）

    HTTP メソッドとデータ形式を 統一 して使う

    ③ ステートレス性（Stateless）

    サーバーがクライアントの 状態（情報）を保持しない

    ④ 接続性（Connectability）

    情報同士が リンクでつながっている

    4.1 アドレス可能性 — レストランの注文

    アドレス は「住所」のことです。URL という住所を指定すると、それに対応するデータ（たとえば Twitter の API なら最新のツイート）が 一意に 返ってくる性質を アドレス可能性 と言います。

    レストランにたとえると、お客様がメニューを見て「ハンバーガーください」とウェイターに頼み、ウェイターが厨房に伝え、厨房が作った料理をウェイターがお客様に運びます。メニューから「ハンバーガー」と指定することが、URL を指定すること にあたります。

    ここで API（Application Programming Interface） の「インターフェース」は、何かと何かをつなぐもの という意味です（マウスやキーボードが人とパソコンをつなぐのと同じ）。API はクライアントとサーバーを中継ぎするもので、たとえではウェイターの役割にあたります。

    4.2 統一インターフェース — ウォーターサーバー

    統一インターフェース は、GET（取得）・POST（投稿）・PUT（更新）・DELETE（削除） などの HTTP メソッドを統一して使うルールです。サーバーが返すデータの形式もそろえます。昔は XML でしたが、今は JSON が一般的です。

    ウォーターサーバーでの操作HTTP メソッド
    蛇口をひねって水を汲むGET（取得）
    水のボトルをセットするPOST（投稿・作成）
    減った水を足すPUT（更新）
    水を取り外すDELETE（削除）

    どの業者のウォーターサーバーと契約しても、水を飲む・足す・外すやり方は同じです。このように 操作方法が統一されている ので、初めての相手でも迷わず使えます。

    4.3 ステートレス性 — 美容室

    ステートレス は「状態（State）が無い（less）」、つまり サーバーがクライアントの情報（キャッシュやセッション）を保持しない 設計です。

    ステートフル（行きつけの美容室）

    美容師さんが「田中さんはいつもショートカット」と覚えていて、言わなくてもショートカットにしてくれる。過去の情報を保持している状態です。

    ステートレス（REST の基本）

    美容師さんは何も覚えていないので、毎回「ショートカットで」と伝える必要がある。リクエストごとに必要な情報をすべて送る状態です。

    毎回伝えるのは面倒に見えますが、過去の情報を保持すると 管理コストが高く なります。ステートレスにすると シンプルな設計 になり、運用コストが下がり、スケーラビリティ（拡張性） が高まります。過去の情報を覚えておけばすぐにログインできるなどの利点もありますが、REST の基本はステートレスです（ログイン状態の扱いは 74章：セッション方式とトークン方式）。

    4.4 接続性 — リンクでつながる

    ブログや技術記事の最後に、関連する記事へのリンクがいくつも貼られていることがあります。このように、一つの点から複数の方向へリンクでつながっている 状態が 接続性 です。Web（＝クモの巣）がここまで広まった理由そのものの考え方です。

    4.5 設計上の原則として整理すると

    4大原則を、URL 設計の視点で言い直すと次のようになります。

    原則意味
    リソース指向エンティティ（もの）を一意な URL で表現する
    ステートレス各リクエストは独立して完結する
    統一インターフェースHTTP の標準メソッド・ステータスコードを活用する
    階層構造URL のパスでリソースの階層を表現する

    5.URL は名詞、操作は HTTP メソッド

    REST の基本ルールです。各リソースに一意の URI（URL とほぼ同じ意味の、リソースの識別子）を割り当て、URI には 動詞ではなく名詞 を使います（get-product ではなく products）。

    要素役割例
    URL（パス）名詞 — 何に対する操作か/users、/orders/{id}
    HTTP メソッド動詞 — 何をするかGET、POST、PATCH、DELETE
    ✕ 悪い例：URL に動詞を入れる・更新を GET で行う 
    POST /deleteUser        … URL に動詞
GET  /users/123/update  … 更新を GET で
    ◯ 良い例：操作はメソッドで表現する 
    DELETE /users/123       … メソッドで操作を表現
PATCH  /users/123       … 部分更新

    5.1 CRUD とメソッド

    データの基本操作である作成・読み取り・更新・削除の頭文字をまとめると CRUD になります。REST では、それぞれを HTTP メソッドに対応させます。

    CRUD意味HTTP メソッド
    Create作成POST
    Read読み取りGET
    Update更新PUT（全置換）／PATCH（部分更新）
    Delete削除DELETE

    URL の設計は URLとリソースの設計、メソッドの使い分けは HTTPメソッドと操作 で詳しく学びます。

    5.2 リクエストの3つの部分

    REST のリクエストは 開始行・ヘッダー・ボディ の3部構成です（リクエストとレスポンス）。

    • 開始行：メソッド、URI、HTTP バージョン
    • ヘッダー：API キーなどの認証情報や、ボディが JSON であることを示す Content-Type
    • ボディ：送るデータを JSON で入れる

    5.3 具体例：ドーナツ店の商品一覧

    ドーナツ店の商品（products）を REST で扱う例です。

    # 商品の一覧を取得する
GET /products

# 売り切れた商品を、ID を指定して置き換える
PUT /products/3
Content-Type: application/json

{ "name": "チョコドーナツ" }

# 新商品を追加する（ボディに名前を入れる）
POST /products
Content-Type: application/json

{ "name": "抹茶ドーナツ" }

# → レスポンス：新しい ID と作成された内容が返る
HTTP/1.1 201 Created

{ "id": 7, "name": "抹茶ドーナツ" }

    （動画の説明をもとに、HTTP の形に書き起こした例です。ID や商品名は例です）

    6.ステータスコード・リトライ・冪等性

    サーバーはリクエストを処理し、先頭にステータスコードを付けて返します（ステータスコード）。

    コード意味
    200 番台成功
    400 番台クライアント側（こちら側）のエラー
    500 番台サーバー側のエラー

    500 番台が返ってきたらリトライ（再送）してよい場面がありますが、POST は二重登録 の危険があります。何度送っても結果が同じになる性質を 冪等性（べきとうせい、idempotency） と言います。GET・PUT・DELETE は冪等に作るのが基本ですが、POST は送るたびに新しいリソースが作られるので冪等ではありません。リトライを設計するときはこの違いを意識します（レート制限と冪等性）。

    7.スケールと進化を支える工夫

    工夫内容詳しく扱うページ
    ステートレス互いの状態を保持しないので、サーバーを際限なく増やしてスケールできるHTTPの基本
    ページネーション巨大なデータは limit（件数）と offset（開始位置）で切り出して返すページネーション・フィルタ・ソート
    バージョニングURI に v1・v2 のようなバージョンを付ければ、破壊的変更をしてもユーザーを徐々に移行できるバージョニング
     
    GET /v1/products?limit=20&offset=40   … 41 件目から 20 件を取得

    8.REST の利点と限界

    利点説明
    学習しやすいHTTP の標準機能をそのまま使う
    キャッシュGET は CDN（配信用のキャッシュサーバー網）やブラウザのキャッシュと相性が良い
    ツールが豊富curl、Postman、OpenAPI のエコシステム
    一貫性名詞 ＋ メソッドで CRUD を統一できる
    限界説明
    複雑な検索1 回のリクエストで多くの条件・多くのリソースを取得しようとすると冗長になりやすい
    CRUD 以外の操作「送信」「承認」などを無理やり CRUD に当てはめると不自然になる
    N+1 問題一覧を取ったあと、関連データを1件ずつ取りに行くため、リクエスト数が増える
    多対多のリレーション多対多の関係を URL で表すのがやや苦手

    限界を知ったうえで、基本は REST、必要なら例外（検索と複合操作）という姿勢が現実的です。REST の原則を過度に厳守するのは現実的でない場合もあります。

    9.REST 以外のスタイル（RPC 風・GraphQL）との関係

    スタイル特徴向いている場面
    RESTリソース ＋ HTTP メソッド一般的な CRUD の API
    RPC 風/users/search など操作を指す URL（RPC＝関数を呼ぶように操作を呼び出す方式）検索・集計・複雑な処理
    GraphQL1 つのエンドポイントで、クライアントが欲しいフィールドを指定する多様なクライアント、柔軟な取得
    1. まず REST の基本（名詞 ＋ メソッド）を固める
    2. 必要に応じて RPC 風・GraphQL を検討する（REST以外のAPIスタイル）

    混ぜすぎに注意

    スタイルを 混在させすぎる と一貫性が崩れやすいので、チームで方針を決めます（一貫性）。

    10.よくある誤解

    誤解1：「REST は厳密な規格で、すべて守らないと REST とは呼べない」

    REST は仕様ではなく 設計の考え方（ルールの集まり） です。原則を過度に厳守するのは現実的でない場合もあり、基本は REST、必要なら例外 という姿勢が現実的です。

    誤解2：「URL に操作の名前を入れたほうが分かりやすい」

    /deleteUser のように URL に動詞を入れると、操作ごとに URL が増えて一貫性が崩れます。URL は 名詞（リソース）、操作は HTTP メソッド で表すのが REST の基本です。

    誤解3：「エラーが返ったら、どのリクエストでも再送すればよい」

    500 番台なら再送してよい場面がありますが、POST は冪等ではない ので、再送すると二重登録になる危険があります。再送しても安全かどうか（冪等性）を意識して設計します。

    誤解4：「ステートレスは不便なだけで、メリットがない」

    毎回必要な情報を送る手間はありますが、サーバーが状態を持たないので 設計がシンプルになり、運用コストが下がり、サーバーを増やしてスケールしやすく なります。

    11.まとめ

    • REST は Roy Fielding が提唱した Web API の設計スタイル。規格ではなくルールの集まりで、従う API を RESTful と呼ぶ
    • リソースは操作の対象、表現は JSON などでの表し方
    • 4大原則：アドレス可能性（URL で一意に指す）・統一インターフェース（メソッドと形式をそろえる）・ステートレス性（状態を持たない）・接続性（リンクでつながる）
    • URL は名詞、操作は HTTP メソッド。POST・GET・PUT/PATCH・DELETE で CRUD を表す
    • ステータスコードと冪等性を意識してリトライを設計する（POST は二重登録に注意）
    • ステートレス性・ページネーション・バージョニングが REST のスケールと進化を支える
    • 複雑な検索や CRUD 以外の操作は苦手。基本は REST、必要なら RPC 風・GraphQL も検討し、混ぜすぎない
