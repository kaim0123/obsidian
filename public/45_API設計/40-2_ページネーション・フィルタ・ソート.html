    40 実践的な設計

    ページネーション・フィルタ・ソート — 一覧 API を分けて・絞って・並べる

    データが増えると、一覧 API で全件を返すことはできなくなります。オフセット方式とカーソル方式のページネーションの違いと選び方、クエリパラメータでのフィルタとソートの表し方、limit の上限や並び順の固定といった共通のベストプラクティスを解説します。

    もとにしたノート：40_実践的な設計/02_ページネーション・フィルタ・ソート

    ひとことで言うと

    一覧 API には 最初からページネーションを設計 します。ページへジャンプしたいなら オフセット方式（page / limit）、順に読み進めるなら カーソル方式（cursor / has_more）。絞り込みと並び替えはクエリパラメータで表します。

    1.このページで扱うこと

    一覧 API の 分割取得（ページネーション）・絞り込み（フィルタ）・並び替え（ソート） を設計します。

    • 一覧 API が必要になる場面
    • オフセット方式（page / limit）
    • カーソル方式（cursor / has_more）
    • フィルタとソートのクエリパラメータ設計
    • 方式の選び方と limit 上限

    2.一覧 API が必要になる場面

    GET /users や GET /orders のように 複数件を返す API は、データが増えるとそのままでは扱えません。

    問題原因
    レスポンスが巨大数万件を一度に JSON にする
    遅いDB・ネットワーク・パース（JSON の読み込み）の負荷
    タイムアウトモバイル回線・サーバーの制限
    ✕ 10 万件を全部返す 
    GET /orders
    ◯ 20 件ずつ返す 
    GET /orders?page=1&limit=20

    一覧 API には最初からページネーションを設計 しておくのが定石です。あとから付けると、全件取得を前提にしたクライアントが壊れます。

    3.オフセット方式（page / limit）

    GET /users?page=2&limit=20
    項目内容
    リクエストpage（何ページ目）、limit（1 ページの件数）
    レスポンス例{ "data": [...], "meta": { "page": 2, "limit": 20, "total": 150 } }
    メリット実装・理解が簡単。「N ページ目へジャンプ」しやすい
    デメリットデータの追加・削除で 重複や取りこぼし が起きやすい

    管理画面の表など、任意のページへジャンプ したい場面に向いています。page の代わりに offset（先頭から何件飛ばすか）を使う API もあります（例：?offset=20&limit=10）。

    4.カーソル方式（cursor / has_more）

    GET /users?limit=20&cursor=eyJpZCI6MTIzfQ

    カーソル とは「前回どこまで読んだか」を表す目印の文字列です。サーバーは「この位置の続きから」データを返します。

    項目内容
    リクエストlimit、cursor（前回の続きの位置）
    レスポンス例{ "data": [...], "meta": { "next_cursor": "...", "has_more": true } }
    メリットリアルタイム更新に強い。大量データ・無限スクロール向き
    デメリット任意のページへのジャンプが難しい

    SNS のタイムライン、ログ、フィードなど 順に読み進める UI に向いています。

    5.フィルタとソートのクエリパラメータ設計

    一覧 API では、クエリパラメータ（URL の ? より後ろの部分）で絞り込み・並び替えを表します。

    GET /products?category=book&status=active&sort=-price,created_at
    パラメータ例意味
    フィルタcategory=bookカテゴリが book
    フィルタstatus=active有効なものだけ
    ソートsort=price価格の昇順
    ソートsort=-price価格の降順（- を前に付ける）
    複合sort=-price,created_at価格の降順 → 同じ価格なら作成日の昇順
    • パラメータ名は 一貫した命名 にする（一貫性）
    • 受け付けるフィルタ・ソート列を ドキュメントにする

    ソート列をそのまま SQL に埋め込むと SQL インジェクションの原因になります。受け付ける列を決めておくことは安全面でも大切です（72章：SQLインジェクション）。キーワード検索や複雑な条件は 検索と複合操作 で扱います。

    6.方式の選び方と limit 上限

    用途おすすめ
    管理画面、件数が少〜中、ページジャンプオフセット
    タイムライン、ログ、無限スクロールカーソル

    6.1 共通のベストプラクティス

    • limit に上限 を設ける（例：最大 100）
    • total（総件数） は数えるのに DB のコストが高い場合、省略や概算を検討する
    • ソート順を 固定 する（例：created_at desc, id desc）。同じ値が並んだときの順番が毎回変わると、ページをまたいで重複や漏れが出る
    • has_more や next_cursor を含め、クライアントの実装を単純にする
    {
  "data": [...],
  "meta": {
    "limit": 20,
    "next_cursor": "eyJpZCI6MTIzfQ",
    "has_more": true
  }
}

    data / meta のラップ形式は ボディの設計 で説明しています。フィルタ・ソート・ページネーションの基本例（category=electronics&inStock=true、page=3&limit=10&sort=price など）は HTTPメソッドと操作の表現 でも紹介しています。

    7.よくある誤解

    誤解1：「最初は件数が少ないから、ページネーションは後で付ければよい」

    あとから付けると、全件が返ってくる前提で作られたクライアントが壊れます。レスポンスの形（data / meta）も変わります。一覧 API には最初からページネーションを設計 しておきます。

    誤解2：「カーソル方式のほうが新しいので、常にカーソルを使うべき」

    カーソル方式は「5ページ目へジャンプ」が苦手です。管理画面の表のようにページを選びたい場面では オフセット方式 が向いています。用途で選びます。

    誤解3：「limit はクライアントが好きに決めればよい」

    上限がないと limit=1000000 のようなリクエストで、結局全件取得と同じ負荷がかかります。サーバー側で上限（例：100）を決めておきます。

    8.まとめ

    • データが増えると全件返却は巨大・遅い・タイムアウトの原因になる
    • オフセット方式は簡単でページジャンプ向きだが、重複・取りこぼしが起きやすい
    • カーソル方式は更新に強く無限スクロール向きだが、ジャンプが難しい
    • フィルタは category=book、ソートは sort=-price,created_at のようにクエリで表し、許可する列を文書化する
    • limit 上限、total の扱い、ソート順の固定、has_more / next_cursor

    次は、CRUD だけでは表せない操作を扱う 検索と複合操作 です。
