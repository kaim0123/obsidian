    70 ドキュメントとテスト

    チームでAPI設計を守る — ガイドライン・レビュー・自動チェック

    1 人で良い API を設計できても、チームで作ると URL の書き方やエラーの形がすぐにばらばらになります。このページでは、チームで API 設計の品質を保つための 設計ガイドライン、設計レビュー の位置づけと見るべきポイント、Lint などの自動チェック、そして クライアントチームとの合意形成 を学びます。

    もとにしたノート：70_ドキュメントとテスト/03_チームでAPI設計を守る

    ひとことで言うと

    チームの「当たり前」を 1 枚のガイドライン に書き、実装前の設計レビュー で OpenAPI 草案を議論し、Spectral などの 機械チェック を CI に組み込みます。人が見るガイドラインと機械チェックの 二段構え にし、クライアントの代表を早くから巻き込むのが、チームで設計を守るコツです。

    1.このページで扱うこと

    • API 設計ガイドライン の策定
    • 設計レビューとコードレビューの違い
    • API レビューで見るべきポイント
    • 設計ルールの 文書化と自動チェック
    • クライアントチームとの合意形成

    レビューの具体的な進め方・チェックリスト・コメントの書き方は、次の API設計レビューの実践 で扱います。

    2.API 設計ガイドラインの策定

    1 枚のガイドライン に、チームの「当たり前」を書きます。

    項目ルールの例
    URL複数形・小文字・/v1/ 必須
    JSONsnake_case に統一
    日時ISO 8601（2026-10-18T09:00:00Z のような国際標準の書き方）、UTC
    エラー{ "error": { "code", "message" } }
    認証Bearer Token、401/403 の使い分け

    一貫性 のチェックリストをベースに、自分たちのチーム版 を作ります。

    3.設計レビューとコードレビューの違い

    種類タイミング見るもの
    設計レビュー実装前URL・契約・後方互換・セキュリティ
    コードレビュー実装後ロジック・テスト・パフォーマンス
     
      新 API 提案
       │
       ├─ 設計レビュー（OpenAPI 草案）→ 合意
       ├─ 実装
       └─ コードレビュー → マージ

    設計を後から直すコストは、実装後だと 10 倍 とも言われます。だから契約が固まる前、OpenAPI 草案の段階でレビューします。

    4.API レビューで見るべきポイント

    #質問NG 例
    1URL は名詞かPOST /createUser
    2メソッドは適切かGET /deleteUser
    3エラー形式は統一されているかHTML のエラーページを返す
    4破壊的変更か既存のフィールドを削除する
    5認可は明確か他人のデータが見える
    6ページネーションは必要か件数無制限の一覧

    それぞれ URLとリソースの設計、HTTPメソッドと操作、エラー設計、後方互換性、認可、ページネーション で詳しく扱っています。

    レビューは対話

    レビューは 批評 ではなく、クライアントの体験を想像する 対話 にします。

    5.設計ルールの文書化と自動チェック

    自動化ツール例
    Lint（ルール違反を機械的に見つけるチェック）Spectral（OpenAPI 向けのルール）
    破壊的変更（Breaking change）の検知openapi-diff
    CIPR のたびにスキーマを検証する
     
    # Spectral ルール例（概念）
paths:
  must-use-plural-nouns: error
  must-have-version-prefix: warn

    上の例は考え方を示すもので、「URL は複数形の名詞（違反ならエラー）」「/v1/ のようなバージョンの接頭辞（違反なら警告）」をルールにしています。

    二段構え

    人が見るガイドライン + 機械チェック の二段構えが効果的です。機械で見られるもの（命名・形式）は機械に任せ、人のレビューは契約やユースケースの議論に集中させます。

    6.クライアントチームとの合意形成

    合意すること文書化する場所
    リリース日CHANGELOG（変更履歴）
    非推奨にする APIDeprecation（非推奨）の告知
    サポート窓口README / Slack チャンネル

    早いうちにクライアントの代表を巻き込む と、リリース後の「使いにくい」が減ります。

    増田本（増田亨『現場で役立つシステム設計の原則』）の第 8 章も、発展性のある API は 提供側と利用側の共同作業の環境 が前提だと述べています。中核となる API セットの設計や、複合サービスとの関係は 発展性のあるAPI開発 で扱います。

    7.よくある誤解

    誤解1：「コードレビューがあれば、設計レビューは要らない」

    コードレビューは実装後に、ロジックやテストを見ます。URL や契約、後方互換は実装前に決めておかないと、直すコストが大きく（実装後は 10 倍とも）なります。設計レビューは実装前 に行います。

    誤解2：「ガイドラインを書けば、みんな守ってくれる」

    人は忘れますし、読み落とします。命名や形式のルールは Spectral や openapi-diff で CI に組み込み、機械にもチェックさせる 二段構えにします。

    誤解3：「API の形はサーバーチームが決めて、完成してから知らせればよい」

    完成してから知らせると、「この形では使いにくい」が後から出てきます。OpenAPI 草案の段階でクライアントの代表に見せ、合意した版を固定します。

    8.まとめ

    • URL・JSON・日時・エラー・認証の「当たり前」を 1 枚のガイドラインにする
    • 設計レビューは実装前に、OpenAPI 草案で URL・契約・後方互換・セキュリティを見る
    • レビューは批評ではなく、クライアント体験を想像する対話にする
    • Spectral・openapi-diff・CI で機械チェックし、ガイドラインと二段構えにする
    • クライアントの代表を早く巻き込み、合意版を CHANGELOG とともに固定する
