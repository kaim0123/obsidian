    85 ケーススタディ

    EC注文 API のケーススタディ — ネスト・ページネーション・互換性を判断する

    EC サイトの「商品・カート・注文」を題材に、リソースの分け方、ネストした URL、冪等性キー、オフセットとカーソルの使い分け、後方互換性の判断、よくある設計ミスの直し方までを1つの API でまとめて考えます。最後に、REST・GraphQL・gRPC それぞれの実践例と運用のコツも整理します。

    もとにしたノート：85_ケーススタディ/02_ケーススタディ_EC注文API、85_ケーススタディ/03_API実践例

    ひとことで言うと

    EC の注文 API では、カート（作業中）と注文（確定した記録）を別のリソースに分ける のが出発点です。そのうえで、お金が動く POST には Idempotency-Key、商品検索はオフセット・注文履歴はカーソル、項目の追加は互換、型の変更は v2 と、場面ごとに判断します。

    • 注文・商品・カートのリソース設計
    • ネストと関連リソース：エンドポイント一覧、カート追加・注文確定の例

    シンプルな例から始めたい場合は、先に TODO APIのケーススタディ を読んでください。

    2.注文・商品・カートのリソース設計

    リソースURL備考
    商品/v1/products公開カタログ
    カート/v1/carts/meログインユーザーのカート
    カート明細/v1/carts/me/items行の追加・更新
    注文/v1/orders確定後の注文
    注文明細/v1/orders/{id}/items読み取り専用

    カートは セッション中の作業領域（何度でも数量を変えたり消したりできる）、注文は 確定後の記録（あとから勝手に変わってはいけない）として分けます。性質がまったく違うので、同じリソース・同じテーブルに混ぜません。

    /carts/me の me は「ログイン中の自分」を表す決まった名前です。カートの id を URL に出さずに済み、他人のカートを指定される心配もありません。

    3.ネストと関連リソース

    3.1 エンドポイント一覧（主要操作）

    メソッドパス説明成功
    GET/v1/products商品一覧200
    GET/v1/products/{id}商品詳細200
    GET/v1/carts/me自分のカート200
    POST/v1/carts/me/itemsカートに追加201
    PATCH/v1/carts/me/items/{item_id}数量変更200
    DELETE/v1/carts/me/items/{item_id}行削除204
    POST/v1/ordersカートから注文確定201
    GET/v1/orders注文履歴一覧200
    GET/v1/orders/{id}注文詳細200
    GET/v1/orders/{id}/items明細一覧200

    明細（items）は親（カート・注文）なしでは意味を持たないので、/carts/me/items・/orders/{id}/items のように 1段だけネスト します。注文明細には GET しかなく、確定後は書き換えられないことが URL の一覧からも読み取れます。

    3.2 カート追加の例

    POST /v1/carts/me/items HTTP/1.1
Authorization: Bearer <token>
Idempotency-Key: cart-add-550e8400-e29b-41d4-a716
Content-Type: application/json

{"product_id": "prod_abc", "quantity": 2}

    3.3 注文確定の例

    POST /v1/orders HTTP/1.1
Authorization: Bearer <token>
Idempotency-Key: order-7c9e6679-7425-40de-944b-e07fc1f90ae7
Content-Type: application/json

{"shipping_address_id": "addr_123", "payment_method_id": "pm_456"}

    Idempotency-Key（冪等性キー：同じリクエストを何度送っても1回分しか処理されないようにするための一意な値）を付けています。通信が切れてクライアントが再送しても、二重に注文・二重に課金されません。仕組みは レート制限と冪等性 を参照してください。

    4.ページネーションと検索

    4.1 商品一覧（オフセット方式）

    GET /v1/products?q=コーヒー&category=drink&sort=price&order=asc&page=1&limit=20

    キーワード（q）、カテゴリでの絞り込み（category）、並び替え（sort・order）、ページ（page・limit）をクエリパラメータで受け取ります。

    {
  "data": [
    {
      "id": "prod_abc",
      "name": "ドリップコーヒー",
      "price": 980,
      "currency": "JPY",
      "in_stock": true
    }
  ],
  "meta": {
    "page": 1,
    "limit": 20,
    "total": 45
  }
}

    4.2 注文履歴（カーソル方式）

    GET /v1/orders?cursor=ord_cursor_xyz&limit=10
    {
  "data": [{"id": "ord_99", "status": "shipped", "total": 1960}],
  "meta": {
    "has_more": true,
    "next_cursor": "ord_cursor_abc"
  }
}

    カーソル は「ここまで読んだ」という目印です。次のページは next_cursor の値を cursor に入れて取りに行き、has_more が false になったら終わりです。

    4.3 使い分け

    API方式理由
    商品検索オフセットページ番号 UI と相性が良い
    注文履歴カーソルリアルタイム追加があり、offset のずれを防ぐ

    オフセット方式は「先頭から何件飛ばすか」で数えるので、読んでいる最中に新しい注文が追加されると、同じ注文が2回出たり飛ばされたりします。カーソル方式ならこのずれが起きません。詳しくは ページネーション・フィルタ・ソート を参照してください。

    5.バージョニングと後方互換性の判断

    シナリオ：注文レスポンスに tracking_number（配送追跡番号） を追加したい。あわせて、ほかの変更も「既存のクライアントを壊すかどうか」で判断します。

    変更判断理由
    tracking_number 追加後方互換 OK任意フィールド
    status を数値 → 文字列に変更破壊的クライアントの switch が壊れる
    /v1/orders/list を廃止Deprecation → Sunset/v1/orders に統一
     
    // v1.1 — 後方互換な追加
{
  "data": {
    "id": "ord_99",
    "status": "shipped",
    "total": 1960,
    "tracking_number": "JP123456789"
  }
}
    • 知らない項目が増えても、既存のクライアントは無視すれば動き続けます。だから 任意項目の追加は互換 です
    • 型を変えると、status == 3 のような分岐が動かなくなります。数値 status から文字列への変更が必要なら /v2/orders を新設し、v1 は 6 ヶ月並行 して提供します
    • URL を廃止するときは、まず Deprecation（非推奨の予告）を出し、期限（Sunset）が来たら止めます

    詳しくは バージョニング と 後方互換性 を参照してください。

    6.よくある設計ミスと修正

    ミス問題修正
    POST /createOrderREST から逸脱（URL に動詞）POST /v1/orders
    カートと注文が同一テーブル状態が混線リソース分離
    注文 POST に Idempotency-Key なし二重課金ヘッダ必須化
    他人の注文が GET できる認可漏れowner チェック ＋ 403/404 方針
    商品一覧が無制限タイムアウトlimit 上限（例：100）

    「403/404 方針」とは、他人の注文にアクセスされたとき 403（権限なし）を返すか、404（存在しない）を返して存在自体を隠すか をあらかじめ決めておくことです。認可漏れの典型は 73章：認可不備と認可の要件定義、API 特有の脆弱性は 72章：WebAPIの脆弱性 にあります。

    1. 設計レビューで指摘する
    2. OpenAPI を更新する
    3. 契約テスト（API が仕様どおりの形で応答するかを確かめるテスト）を追加する

    この流れで直したことを仕様とテストに残します（API設計レビューの実践、APIのテスト）。このページの API は チェックリストとアンチパターン で最終確認してください。

    7.API スタイルごとの実践例と運用のコツ

    ここまでは REST で考えましたが、実際の開発では GraphQL や gRPC を使う場面もあります。スタイルごとに「実践でよくやること」を並べます。各スタイルの違いは REST以外のAPIスタイル を参照してください。

    REST API の実践例

    • ユーザー管理 API（/users, /users/{id}）
    • バージョニング（/v1/users）
    • JWT 認証・RBAC によるアクセス制御
    • OpenAPI でドキュメント自動生成
    • Postman でテスト自動化

    GraphQL API の実践例

    • スキーマ定義（type User, type Post など）
    • クエリ・ミューテーション・サブスクリプションの設計
    • Apollo Server / Client による実装
    • 型安全・バリデーション・認可の実装

    gRPC・API ゲートウェイの実践例

    • gRPC サービス定義（.proto ファイル）
    • サーバー / クライアントの多言語実装
    • API ゲートウェイで REST / GraphQL / gRPC を統合
    • レートリミット・監査ログ・障害時のリトライ設計

    用語の補足：JWT は署名付きのトークン形式（74章：JWTの構造と検証）、RBAC は役割ごとに権限を決める方式（73章：RBAC・ABAC・ACLの使い分け）、API ゲートウェイ は複数の API の前に立つ共通の入口です（41章：BFFとAPIゲートウェイ）。GraphQL は GraphQLの基本 で扱います。

    7.1 運用・障害対応のコツ

    • モニタリング（Prometheus、Grafana、Datadog など）
    • 障害発生時の ロールバック（前の版に戻す）・フェイルオーバー（予備系に切り替える）
    • セキュリティパッチ・脆弱性対応

    8.よくある誤解

    誤解1：「カートは『未確定の注文』だから、注文と同じテーブル・同じリソースでよい」

    カートは何度でも変わる作業領域、注文は確定後に変えてはいけない記録です。同じ場所に置くと状態が混線し、「確定済みの注文の数量が変わる」といった事故につながります。リソースもテーブルも分けます。

    誤解2：「ページネーションはどの一覧でもページ番号方式で統一すればよい」

    ページ番号 UI がある商品検索にはオフセット方式が合いますが、新しいデータが次々に増える注文履歴ではずれが起きます。一覧の性質に合わせて方式を選びます。

    誤解3：「レスポンスを変えるなら、どんな変更でも v2 を作る必要がある」

    任意項目の追加（tracking_number など）は既存クライアントを壊さないので、v1 のままで出せます。v2 が必要になるのは、型の変更や項目の削除のような破壊的変更のときです。

    9.まとめ

    • 注文・商品・カートのリソース設計：カート（作業領域）と注文（確定後の記録）を分ける
    • ネストと関連リソース：明細は1段だけネストし、お金が動く POST には Idempotency-Key
    • ページネーションと検索：商品検索はオフセット、注文履歴はカーソル
    • バージョニングと後方互換性の判断：任意項目の追加は互換、型の変更は v2 を新設して v1 と6ヶ月並行、廃止は Deprecation → Sunset
    • よくある設計ミスと修正：レビュー → OpenAPI 更新 → 契約テスト追加
    • REST・GraphQL・gRPC それぞれの実践例を押さえ、設計・実装・運用・改善のサイクルを回す
