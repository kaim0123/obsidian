    GraphQLの基本 — スキーマ・クエリ・ミューテーション・サブスクリプション

    GraphQL は「クライアントが欲しいデータの形を指定できる」API のクエリ言語です。どんな特徴があり、どんな問題を解決するのか、いつ使うべきかを押さえたうえで、スキーマ・クエリ・ミューテーション・サブスクリプションの4つの基本概念と、変数・エイリアス・フラグメントの書き方を学びます。

    もとにしたノート：82_GraphQL/00_GraphQL入門ガイド、01_GraphQLとは何か、02_GraphQLの基本概念

    ひとことで言うと

    GraphQL は、1つのエンドポイント に「この形でデータをください」とクエリを送ると、その形のとおりに必要なデータだけ が返ってくる API の仕組みです。スキーマ（設計図）に型と操作を定義し、クエリ（取得）・ミューテーション（作成・更新・削除）・サブスクリプション（リアルタイム監視）で使います。

    2.GraphQL とは何か

    GraphQL（Graph Query Language）は、Facebook（現 Meta）が 2015 年に公開した API のためのクエリ言語 です。クエリ言語 とは「問い合わせるための言語」のことで、クライアントとサーバーの間のデータ通信を効率よく行う仕組みを提供します。

    2.1 4つの特徴

    1. 必要なデータだけを取得できる

    REST API ではエンドポイントごとに決められたデータがすべて返ります。GraphQL では クライアントが必要なデータの構造を指定 できるので、不要なデータを取らずに済みます。

    • REST API：ユーザー情報を取ると、名前・メール・住所・電話番号などすべてが返る
    • GraphQL：名前とメールだけ必要なら、それだけを指定して取れる

    2. 単一のエンドポイント

    1つのエンドポイント（通常は /graphql）を通じて、取得・作成・更新・削除のすべての操作を行います。

    3. 強力な型システム

    GraphQL は 型安全（データの型が決まっていて、型の違いを早く見つけられる）です。スキーマでデータ構造をはっきり定義するので、開発中にエラーを見つけやすくなります。

    4. 自己文書化

    スキーマがそのまま API の仕様書 になります。スキーマを見るだけで、どんなデータが取れて、どんな操作ができるかが分かります。

    2.2 GraphQL の歴史

    年できごと
    2012年Facebook が社内で開発を開始
    2015年オープンソースとして公開
    2018年GraphQL Foundation が設立
    現在多くの企業やプロジェクトで採用されている

    3.GraphQL が解決する問題

    オーバーフェッチ（Over-fetching）

    問題：必要なデータ以上の情報を取得してしまう

    例：ユーザー一覧を表示したいだけなのに、各ユーザーの詳細（住所、電話番号など）まで取得してしまう

    解決：GraphQL では必要なフィールドだけを指定できる

    アンダーフェッチ（Under-fetching）

    問題：1つの画面を表示するのに、複数の API リクエストが必要になる

    例：ユーザー情報と、そのユーザーの投稿を表示するために 2 つの API を呼ぶ

    解決：GraphQL では1つのクエリで関連データをまとめて取得できる

    具体的なリクエストとレスポンスでの比較は RESTとGraphQLの違い で詳しく見ます。

    4.GraphQL を使うべき場面

    ◯ 適している場面

    • モバイルアプリなど、ネットワーク帯域が限られている環境
    • 複数のクライアント（Web、iOS、Android）が異なるデータを必要とする
    • リアルタイム更新が必要なアプリケーション
    • 複雑なデータ構造を持つアプリケーション

    ✕ 適していない場面

    • シンプルな CRUD 操作だけの API
    • キャッシュが重要な場面（REST の方が適している場合がある）
    • 既存の REST API が十分に機能している場合

    5.4つの基本概念

    GraphQL を理解するために、重要な4つの概念を学びましょう。スキーマが全体の設計図で、残りの3つはスキーマに定義された「操作の種類」です。

    5.1 スキーマ（Schema）

    スキーマ は、GraphQL API のデータ構造と操作を定義する 設計図 です。スキーマを見るだけで、API で何ができるかが分かります。

    基本的な型

    type User {
  id: ID!
  name: String!
  email: String!
  age: Int
  isActive: Boolean!
}
    書き方意味
    typeオブジェクト型を定義する
    ID!必須の ID 型（! は「必須」の意味）
    String!必須の文字列型
    Intオプショナル（省略可）な整数型（! がない）
    Boolean!必須の真偽値型

    スカラー型（それ以上分解できない基本の値の型）として、次の組み込み型があります。

    型意味
    String文字列
    Int整数
    Float浮動小数点数
    Boolean真偽値
    ID一意の識別子（文字列として扱われる）

    5.2 クエリ（Query）

    クエリ は、データを 取得 するためのリクエストです。REST API の GET に相当します。

    基本的なクエリ：user(id: "1") で ID が "1" のユーザーを取得し、{ name email } で名前とメールアドレスのフィールドだけを取ります。

    {
  user(id: "1") {
    name
    email
  }
}

    複数のデータを取得

    {
  users {
    id
    name
    email
  }
}

    ネストしたデータの取得：ユーザーと、そのユーザーの投稿をまとめて取れます。

    {
  user(id: "1") {
    name
    posts {
      title
      content
    }
  }
}

    5.3 ミューテーション（Mutation）

    ミューテーション は、データを 作成・更新・削除 するためのリクエストです。REST API の POST・PUT・DELETE に相当します。

    データの作成：mutation はミューテーションであることを示すキーワード、createUser(...) で新しいユーザーを作成し、{ id name email } で作成されたユーザーの情報を返してもらいます。

    mutation {
  createUser(name: "太郎", email: "taro@example.com") {
    id
    name
    email
  }
}

    データの更新

    mutation {
  updateUser(id: "1", name: "花子") {
    id
    name
    email
  }
}

    データの削除

    mutation {
  deleteUser(id: "1") {
    id
  }
}

    5.4 サブスクリプション（Subscription）

    サブスクリプション は、リアルタイムでデータの変更を 監視 する仕組みです。WebSocket（接続をつないだままにして双方向にやり取りする通信方式）を使い、データが変わったときに自動で通知を受け取ります。

    subscription {
  newUser {
    id
    name
    email
  }
}
    • subscription：サブスクリプションであることを示すキーワード
    • newUser：新しいユーザーが作成されたときに通知を受け取る
    • 接続が確立されると、新しいユーザーが作成されるたびに自動でデータが送られてくる

    5.5 スキーマ定義の例

    実際のスキーマ定義を見てみましょう。

    type Query {
  user(id: ID!): User
  users: [User!]!
}

type Mutation {
  createUser(name: String!, email: String!): User!
  updateUser(id: ID!, name: String): User!
  deleteUser(id: ID!): User!
}

type Subscription {
  newUser: User!
}

type User {
  id: ID!
  name: String!
  email: String!
  posts: [Post!]!
}

type Post {
  id: ID!
  title: String!
  content: String!
  author: User!
}
    書き方意味
    Queryデータ取得の操作を定義する
    Mutationデータ変更の操作を定義する
    Subscriptionリアルタイム監視の操作を定義する
    [User!]!ユーザーの配列。配列そのものも null にならず、null の要素も含まない
    User!必須のユーザー型

    User の posts と Post の author のように、型どうしが互いを参照してつながっています。このつながりをたどってネストしたクエリが書けます。

    6.便利な書き方：変数・エイリアス・フラグメント

    6.1 変数の使用

    クエリやミューテーションの値を、$ で始まる 変数 にして外から渡せます。クエリの文字列に値を直接埋め込まずに済みます。

    query GetUser($userId: ID!) {
  user(id: $userId) {
    name
    email
  }
}

    変数の値は JSON で別に渡します。

    {
  "userId": "1"
}

    6.2 エイリアス（別名）

    同じクエリの中で、同じフィールドを異なる引数で呼ぶときは エイリアス を付けて区別します。

    {
  firstUser: user(id: "1") {
    name
  }
  secondUser: user(id: "2") {
    name
  }
}

    6.3 フラグメント（Fragment）

    フラグメント は、再利用できるフィールドのまとまりです。...UserInfo のように展開して使います。

    fragment UserInfo on User {
  id
  name
  email
}

{
  user(id: "1") {
    ...UserInfo
  }
}

    ブログアプリを題材にした、レスポンス付きのもっと実践的な例は GraphQLをはじめよう にあります。

    7.よくある誤解

    誤解1：「GraphQL はデータベースのクエリ言語だ」

    GraphQL は API のための クエリ言語です。クライアントがサーバーに「どの形のデータが欲しいか」を伝えるもので、裏側のデータの置き場（データベースなど）は自由です。

    誤解2：「1つのエンドポイントだから、取得しかできない」

    /graphql の1か所で、クエリ（取得）・ミューテーション（作成・更新・削除）・サブスクリプション（監視） のすべてを扱います。操作の種類は URL や HTTP メソッドではなく、クエリの中身で区別します。

    誤解3：「! は否定の意味」

    GraphQL のスキーマでは ! は 必須（null にならない） の意味です。Int は省略可、Int! は必須。[User!]! は「配列も要素も null にならない」です。

    8.まとめ

    • GraphQL は Facebook（現 Meta）が 2015 年に公開した、効率的で柔軟なデータ取得 を可能にする API のクエリ言語
    • 特徴は、必要なデータだけ取得・単一エンドポイント・強力な型システム・自己文書化
    • オーバーフェッチ（取りすぎ）とアンダーフェッチ（足りずに何度も呼ぶ）を解決する
    • 複数のクライアントが異なるデータを必要とする場合や、ネットワーク効率が重要な場面で威力を発揮する。シンプルな CRUD やキャッシュ重視なら REST の方が合うこともある
    • スキーマ：API の設計図 ／ クエリ：取得 ／ ミューテーション：作成・更新・削除 ／ サブスクリプション：リアルタイム監視
    • 変数・エイリアス・フラグメントでクエリを再利用しやすくできる
