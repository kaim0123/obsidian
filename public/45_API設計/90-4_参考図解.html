    90 付録

    参考図解 — API 設計でよく使う図のテンプレート

    API 設計の説明や打ち合わせでよく使う図のテンプレート集です。HTTP のリクエストとレスポンスの流れ、REST のリソースとメソッド、Bearer Token による認証・認可の流れ、URL パス方式のバージョニング、ページネーション、エラー設計のレイヤー、設計の階層での API 設計の位置を、ASCII 図（文字だけで描いた図）で並べました。主な3つは図でも示しています。

    もとにしたノート：90_付録/付録F_参考図解

    ひとことで言うと

    API の図は 「誰が・何を送り・何が返るか」 を矢印で描くのが基本です。リクエストには メソッド・URL・ヘッダー、レスポンスには ステータス・ヘッダー・ボディ を書き添えると、設計の意図が一目で伝わります。ASCII 図はそのまま Obsidian のコードブロックやホワイトボードに転記できます。

    1.このページで扱うこと

    API 設計でよく使う ASCII 図のテンプレート です。Obsidian やホワイトボードに転記して使えます。

    • HTTP リクエスト／レスポンスの流れ（図あり）
    • REST リソースと HTTP メソッド
    • 認証・認可フロー（Bearer Token）（図あり）
    • バージョニング（URL パス方式）（図あり）
    • ページネーション（offset 方式）
    • エラー設計のレイヤー
    • API 設計の階層での位置

    使い方

    各節の図は、詳しく解説しているページの「要点だけ」を描いたものです。意味が分からないときは、節の最後にあるリンク先のページを読んでください。

    2.HTTP リクエスト／レスポンスの流れ

    クライアントがリクエストを送り、サーバーが処理してレスポンスを返す、API 呼び出しのいちばん基本の形です。

    転記用テンプレート

      Client                          Server
    │                                │
    │  GET /users/1                  │
    │  Accept: application/json      │
    │  Authorization: Bearer ***     │
    │ ─────────────────────────────→ │
    │                                │ 認証・認可
    │                                │ ビジネス処理
    │                                │ DB アクセス
    │  200 OK                        │
    │  Content-Type: application/json│
    │  { "id": "1", "name": "..." }  │
    │ ←───────────────────────────── │
    │                                │

    リクエストとレスポンスの各部分の意味は HTTPの基本、リクエストとレスポンス で説明しています。

    3.REST リソースと HTTP メソッド

    REST では、URL で「もの（リソース）」を、HTTP メソッドで「操作」を表します。コレクション（/users）と個々のリソース（/users/{id}）で使えるメソッドが分かれます。

    URLメソッド操作
    /usersGET一覧取得
    POST新規作成
    /users/{id}GET1 件取得
    PUT全体置換
    PATCH部分更新
    DELETE削除

    転記用テンプレート

      /users
    │
    ├─ GET    → 一覧取得
    ├─ POST   → 新規作成
    │
    └─ /{id}
         ├─ GET    → 1 件取得
         ├─ PUT    → 全体置換
         ├─ PATCH  → 部分更新
         └─ DELETE → 削除

  URL = 名詞（リソース）  /  HTTP メソッド = 操作

    詳しくは RESTの考え方、URLとリソースの設計、HTTPメソッドと操作の表現 を見てください。

    4.認証・認可フロー（Bearer Token）

    クライアントはまず認可サーバー（Auth Server）からアクセストークンを受け取り、以後はそれを Authorization: Bearer ヘッダーに載せて API（Resource API）を呼びます。API はトークンを検証し、権限を確かめてから結果を返します。

    転記用テンプレート

      Client                    Auth Server              Resource API
    │                            │                        │
    │  POST /oauth/token         │                        │
    │  (client_id, secret)       │                        │
    │ ─────────────────────────→ │                        │
    │  access_token (JWT)        │                        │
    │ ←───────────────────────── │                        │
    │                            │                        │
    │  GET /orders               │                        │
    │  Authorization: Bearer JWT │                        │
    │ ──────────────────────────────────────────────────→ │
    │                            │      トークン検証      │
    │                            │      権限チェック      │
    │  200 / 401 / 403           │                        │
    │ ←────────────────────────────────────────────────── │

    ④ の結果は、トークンが正しく権限もあれば 200、トークンがない・無効なら 401、トークンは正しいが権限が足りなければ 403 です。詳しくは 認証、認可、OAuth 2.0 の流れ全体は OAuth2.0の仕組み（73章）、JWT の中身は JWTの構造と検証（74章） を見てください。

    5.バージョニング（URL パス方式）

    破壊的変更が必要になったら、URL に新しいバージョン（/v2/）を作り、古いバージョンはしばらく残してから廃止します。

    転記用テンプレート

      /v1/users  ──→ 既存クライアント（保守のみ）
       │
       │ 破壊的変更が必要
       ▼
  /v2/users  ──→ 新クライアント
       │
       ├─ v1 は deprecation 告知
       └─ 一定期間後に v1 廃止

    詳しくは バージョニング、後方互換性、APIの進化と運用 を見てください。

    6.ページネーション（offset 方式）

    一覧を一度に全部返さず、ページに分けて返します。page=2&limit=20 なら 21〜40 件目です。レスポンスには、データ本体の items と、ページ情報の meta（今のページ・件数・総数）を入れます。

    転記用テンプレート

      GET /todos?page=2&limit=20

  ┌──────────────────────────────────────┐
  │ meta: { page: 2, limit: 20, total }  │
  │ items: [ todo_21 .. todo_40 ]        │
  └──────────────────────────────────────┘

    offset 方式と cursor 方式の違いは ページネーション・フィルタ・ソート を見てください。

    7.エラー設計のレイヤー

    エラーの情報は、大まかなものから細かいものへ4段に重ねます。

    段役割例
    HTTP ステータス結果の大分類404、422
    error.code機械可読（プログラムで判定する）USER_NOT_FOUND
    error.message人間向けの短文User not found
    error.detailsフィールド単位の詳細（任意）どの入力項目がなぜ不正か

    転記用テンプレート

      HTTP ステータス  … 結果の大分類（404, 422）
        │
        ▼
  error.code       … 機械可読（USER_NOT_FOUND）
        │
        ▼
  error.message    … 人間向け短文
        │
        ▼
  error.details    … フィールド単位（任意）

    詳しくは エラー設計、ステータスの選び方は ステータスコード早見表 を見てください。

    8.API 設計の階層での位置

    API 設計は、ソフトウェア全体の設計からメソッドの設計までの流れの中で、モジュール設計とクラス設計の間に位置します。モジュール（まとまった部品）同士が外にどんな入口を見せるかを決めるのが API 設計です。

    転記用テンプレート

      ソフトウェア設計 → モジュール設計
                            │
                            ▼
                       API 設計（本教材）
                            │
                            ▼
                      クラス設計 → メソッド設計

    前後の教材は ソフトウェア設計の全体像（42章）、モジュール設計の全体像（43章）、クラス設計の全体像（44章） です。この教材全体の地図は API設計の全体像 にあります。

    9.よくある誤解

    誤解1：「シーケンス図（やり取りの図）は正式な記法で描かないと意味がない」

    このページのテンプレートは、議論のための簡略な図です。「誰が・何を送り・何が返るか」と、メソッド・URL・主なヘッダー・ステータスが伝われば十分役に立ちます。

    誤解2：「Bearer Token を送れば、API はそのまま信じて処理してくれる」

    図の ③ のあと、Resource API は毎回トークンの検証（署名・有効期限など）と権限チェックを行います。トークンが無効なら 401、権限が足りなければ 403 を返します。

    誤解3：「v2 を出したら v1 はすぐ消してよい」

    v1 を使っている既存クライアント（特に更新されない古いモバイルアプリ）が壊れてしまいます。図のように、deprecation の告知と移行期間を置いてから廃止します。

    10.まとめ

    • リクエスト／レスポンスの図には、メソッド・URL・ヘッダー、ステータス・ヘッダー・ボディを書き添える
    • REST は URL＝名詞（リソース）、HTTP メソッド＝操作。/users と /users/{id} で使えるメソッドが分かれる
    • Bearer Token の流れは「トークン取得 → ヘッダーに載せて呼ぶ → 検証・権限チェック → 200 / 401 / 403」
    • バージョニングは v2 を作り、v1 は告知と移行期間のあとに廃止。ページネーションは items + meta
    • エラーは HTTP ステータス → code → message → details の4段。API 設計はモジュール設計とクラス設計の間に位置する
