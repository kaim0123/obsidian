    40 実践的な設計

    エラー設計 — 失敗も予測可能な形で返す

    API は成功するときだけでなく、失敗するときの返し方も設計の対象です。HTTP ステータスで大分類を、機械が読める code で細かい種類を、人間向けの message とフィールドごとの details で原因を、request_id で調査の手がかりを返す — クライアントが「再試行するか・何を表示するか」を判断できるエラーレスポンスの作り方を解説します。

    もとにしたノート：40_実践的な設計/01_エラー設計

    ひとことで言うと

    エラーは HTTP ステータス（大分類）＋ 機械可読な code（細かい種類）＋ 人間向けの message の組み合わせで、全エンドポイント同じ JSON 構造 で返します。request_id を付けるとログ調査が楽になります。

    1.このページで扱うこと

    • エラー設計の目的
    • ステータスコード + 機械可読な code
    • 人間向け message とフィールド単位の details
    • request_id とログ調査
    • エラーレスポンスのチェックリスト

    ステータスコードそのものの意味は ステータスコード で扱っています。

    2.エラー設計の目的

    クライアントはエラーの内容を見て、再試行する・ユーザーに表示する・ログを送る といった次の行動を判断します。

    目的説明
    機械可読プログラムが code で分岐できる
    人間可読開発者・ユーザーに原因が伝わる
    一貫性全エンドポイントで同じ JSON 構造
    調査可能request_id でログと紐づく

    500 だけ返す API

    クライアントは「再試行すべきか」さえ分からない

    設計されたエラー

    UI 表示・リトライ・サポート対応がしやすい

    3.ステータスコード + 機械可読な code

    エラーは 2段階 で表します。

    層役割例
    HTTP ステータス大分類422 Unprocessable Entity
    error.code細かい種類（固定文字列）VALIDATION_ERROR, INSUFFICIENT_STOCK
     
    {
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容に誤りがあります"
  }
}
    • code は 大文字スネークケース（VALIDATION_ERROR のように大文字を _ でつなぐ）の固定文字列にする
    • クライアントは code で switch（分岐）する。message の文字列を比べて分岐するのは避ける（文言は変わることがあるため）

    4.人間向け message とフィールド単位の details

    バリデーションエラー（入力チェックの失敗）は、フィールド単位 で返すとフォームの UI と相性が良くなります。

    {
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容に誤りがあります",
    "details": [
      {
        "field": "email",
        "code": "INVALID_FORMAT",
        "message": "メールアドレスの形式が正しくありません"
      },
      {
        "field": "password",
        "code": "TOO_SHORT",
        "message": "8文字以上で入力してください"
      }
    ]
  }
}
    フィールド向き用途
    message人間画面表示、ログ
    details[].field機械 + 人間フォームの該当欄にエラーを表示
    details[].code機械クライアント側の細かい分岐

    5.request_id とログ調査

    request_id（リクエストごとに振る一意の番号）をエラーレスポンスに含めると、サポートや障害調査が楽になります。

    {
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "サーバーでエラーが発生しました",
    "request_id": "req_abc123xyz"
  }
}
    1. ユーザー「エラーが出ました」
    2. request_id: req_abc123xyz をサポートに伝えてもらう
    3. サーバーログで同じ ID を検索して、原因を特定する
    • 本番のレスポンスに スタックトレース（エラーが起きた場所までの関数呼び出しの履歴）を含めない。内部の情報が漏れる
    • request_id はレスポンスヘッダ X-Request-Id に付ける方式もある

    ログを横断して追いかける仕組みは 41章：観測性 も参考になります。

    6.エラーレスポンスのチェックリスト

    • 4xx / 5xx を原因に応じて使い分けているか
    • すべてのエラーで 同じ JSON 構造（error.code 等）か
    • code は固定文字列で、ドキュメントに一覧があるか
    • バリデーションは フィールド単位 の details があるか
    • request_id を付けてログと紐づけられるか
    • 5xx の詳細（内部情報）を本番レスポンスに漏らしていないか
    • 401 と 403 を正しく区別しているか（認証・認可）

    401（未認証：誰か分からない）と 403（認可されていない：誰かは分かるが権限がない）の違いは 73章：認証と認可の違い で詳しく説明しています。

    増田本の「エラー時の約束事」

    増田亨『現場で役立つシステム設計の原則』では、アプリ間連携の HTTP の約束のひとつとして エラー時の約束事（ステータスと形の一貫）を挙げています。4つの約束の全体は HTTPの基本 を見てください。

    7.よくある誤解

    誤解1：「エラーメッセージを見れば何が起きたか分かるので、code は要らない」

    message は人間向けで、文言の修正や多言語化で変わります。プログラムが文字列比較で分岐していると、文言を直しただけで動かなくなります。分岐には固定文字列の code を使います。

    誤解2：「詳しいエラー（スタックトレース）を返したほうが親切」

    本番でスタックトレースや内部情報を返すと、攻撃者にシステムの中身を教えることになります。利用者には code・message・request_id だけを返し、詳細は サーバーログ に残して request_id で引けるようにします。

    誤解3：「エラーの形はエンドポイントごとに最適なものを選べばよい」

    エンドポイントごとに形が違うと、クライアントはエラー処理を何通りも書くことになります。すべてのエラーで同じ JSON 構造 にそろえるのが基本です（一貫性）。

    8.まとめ

    • エラー設計の目的は、機械可読・人間可読・一貫性・調査可能性
    • HTTP ステータスで大分類、error.code（大文字スネークケースの固定文字列）で細かい種類
    • 人間向けの message、フォーム向けのフィールド単位 details
    • request_id でログと紐づけ、スタックトレースは返さない
    • チェックリストで 4xx/5xx の使い分け、構造の統一、401 と 403 の区別を確認する
