    GraphQLをはじめよう — 実践的な例とハンズオン

    ブログアプリを題材に、GraphQL のクエリ・ミューテーション・変数・エイリアス・フラグメント・エラー処理を、レスポンス付きの実例で確かめます。そのうえで Apollo Server でサーバーを作り、React と Apollo Client から呼び出して画面に表示するまでの流れ、サーバー／クライアントの選択肢、学習リソース、よくある質問をまとめます。

    ひとことで言うと

    GraphQL は「API に問い合わせるための言語」です。サーバー側は typeDefs（型とクエリの定義）＋ resolvers（実際に返す値）、クライアント側は ApolloClient ＋ ApolloProvider ＋ useQuery が基本の流れです。まずは小さなサーバーを作り、GraphiQL などでクエリを試すところから始めましょう。

    2.GraphQL のイメージ —「API のクエリ言語」

    GraphQL を一言でいうと 「API のクエリ言語」 です。「クエリ」と「API」の2つの言葉をほどいてみます（厳密さより、イメージを頭に残すことを優先した説明です）。

    クエリ ＝ 問い合わせ

    Google の検索欄に「YouTube」と打ち込んで Enter を押すと、YouTube の情報が返ってきます。このとき打ち込んだ文字列が、問い合わせるための言語 のイメージです。データベースでも「クエリ」という言葉を使います。

    API ＝ クライアントとサーバーの仲介役

    レストランでいえば、お客さん＝クライアント、厨房＝サーバー、注文を厨房に伝えて料理を運ぶウェイター＝API です。API（Application Programming Interface）の「インターフェース」は「何かと何かをつなぐもの」という意味です。

    つまり GraphQL は、ウェイター（API）に問い合わせ・指示をするための言語 です。API そのものの説明は APIとは にあります。

    2.1 REST API との違いとメリット

    観点REST APIGraphQL
    エンドポイント/students、/courses、/instructors とデータごとに別々にアクセス/graphql の1つ で学生・授業・先生を取得できる
    取得データGET /users/:id で id だけ欲しくても name・住所・誕生日まで返る＝オーバーフェッチクエリで欲しい属性（name、posts の title、followers の name など）を自分で指定し、それだけが返る
    メソッドGET・POST・PUT・DELETE を使い分けるquery を書いて問い合わせる
    1. 1つのエンドポイントで複数のデータ を取得できる
    2. 余計なデータを取得しない（オーバーフェッチが起きない）
    3. 型指定 ができるので扱うデータが明確になり、TypeScript などと同じく型の段階でエラーを捕まえられる（堅牢性）

    3.実践的な例：ブログアプリケーション

    3.1 スキーマ定義

    type Query {
  # すべての投稿を取得
  posts: [Post!]!

  # 特定の投稿を取得
  post(id: ID!): Post

  # ユーザー情報を取得
  user(id: ID!): User

  # すべてのユーザーを取得
  users: [User!]!
}

type Mutation {
  # 新しい投稿を作成
  createPost(title: String!, content: String!, authorId: ID!): Post!

  # 投稿を更新
  updatePost(id: ID!, title: String, content: String): Post!

  # 投稿を削除
  deletePost(id: ID!): Boolean!

  # ユーザーを作成
  createUser(name: String!, email: String!): User!
}

type Post {
  id: ID!
  title: String!
  content: String!
  author: User!
  createdAt: String!
  updatedAt: String!
  comments: [Comment!]!
}

type User {
  id: ID!
  name: String!
  email: String!
  posts: [Post!]!
}

type Comment {
  id: ID!
  content: String!
  author: User!
  post: Post!
  createdAt: String!
}

    authorId: "1"

    id
    title
    content
    author {

    }
    createdAt
  }

    レスポンス 
    {
  "data": {
    "createPost": {
      "id": "3",

    3.5 エイリアスとフラグメント

    エイリアス：同じクエリの中で、異なる引数を使って同じフィールドを呼びます。

    クエリ 
    {
  firstPost: post(id: "1") {
    title
    content
  }
  secondPost: post(id: "2") {
    title
    content
  }
}
    レスポンス 
    {
  "data": {
    "firstPost": {
      "title": "最初の投稿",
      "content": "..."
    },
    "secondPost": {
      "title": "2番目の投稿",
      "content": "..."
    }
  }
}

    フラグメント：再利用できるフィールドのまとまりを定義し、型ごとに使い回します。

    fragment PostInfo on Post {
  id
  title
  content
  createdAt
}

fragment AuthorInfo on User {
  name
  email
}

{
  post(id: "1") {
    ...PostInfo
    author {
      ...AuthorInfo
    }
  }
}

    3.6 エラーハンドリング

    エラーが発生した場合：存在しない投稿を取ろうとすると、post は null になり、理由が errors に入ります。

    クエリ 
    {
  post(id: "999") {
    title
  }
}
    レスポンス 
    {
  "data": {
    "post": null
  },
  "errors": [
    {
      "message": "投稿が見つかりません",
      "locations": [
        {
          "line": 2,
          "column": 3
        }
      ],
      "path": ["post"]
    }
  ]
}

    部分的なエラー：一部のフィールドでエラーが起きても、他のデータは取得できます。path を見ると、どこで失敗したかが分かります。

    クエリ 
    {
  post(id: "1") {
    title
    content
    author {
      name
      invalidField
    }
  }
}
    レスポンス 
    {
  "data": {
    "post": {
      "title": "GraphQL入門",
      "content": "...",
      "author": {
        "name": "太郎",
        "invalidField": null
      }
    }
  },
  "errors": [
    {
      "message": "フィールド 'invalidField' は存在しません",
      "locations": [
        {
          "line": 6,
          "column": 7
        }
      ],
      "path": ["post", "author", "invalidField"]

    エラー処理の考え方（HTTP 200 でも errors を確認する）は RESTとGraphQLの違い「エラーハンドリングの違い」 を見てください。

    3.7 用途に応じたクエリの書き分け

    同じスキーマに対して、画面ごとに必要な分だけを取り分けられるのが GraphQL の強みです。

    モバイルアプリ用の軽量なクエリ

  posts {
    id
    title
    author {
      name
    }
  }
}

    必要な最小限のデータだけを取得します。

    管理画面用の詳細なクエリ 
    {
  posts {
    id
    title
    content
    author {
      id
      name
      email
    }
    createdAt
    updatedAt
    comments {
      id
      content
      author {
        name
      }
      createdAt
    }
  }
}

    詳細な情報を一度に取得します。

    5.GraphQL サーバーの構築方法

    5.1 Node.js + GraphQL.js（最も基本的な方法）

    npm install graphql express express-graphql
    const express = require('express');
const { graphqlHTTP } = require('express-graphql');
const { buildSchema } = require('graphql');

const schema = buildSchema(`
  type Query {
    hello: String
  }
`);

const root = {
  hello: () => 'Hello GraphQL!'
};

const app = express();
app.use('/graphql', graphqlHTTP({
  schema: schema,
  rootValue: root,
  graphiql: true, // ブラウザでGraphQLを試せる
}));

app.listen(4000);

    5.2 Apollo Server（人気の高い GraphQL サーバー）

    npm install apollo-server graphql
    const { ApolloServer, gql } = require('apollo-server');

const typeDefs = gql`
  type Query {
    hello: String
  }
`;

const resolvers = {
  Query: {
    hello: () => 'Hello GraphQL!'
  }
};

const server = new ApolloServer({ typeDefs, resolvers });

server.listen().then(({ url }) => {
  console.log(`Server ready at ${url}`);
});

    typeDefs はスキーマ（型とクエリの定義）、resolvers（リゾルバー）は「そのクエリが実行されたら何を返すか」を決める関数です。

    7.ハンズオン：Apollo Server と React で本の一覧を表示する

    動画のハンズオンでは、本のデータを返す GraphQL サーバーを Node.js + Apollo Server で作り、React（Vite）と Apollo Client から呼び出して画面に表示します。全体の流れは次のとおりです。

    7.1 バックエンド（Node.js + Apollo Server）

    1. backend フォルダで npm init -y を実行して package.json の雛形を作り、graphql と apollo-server をインストールする。package.json に開発サーバーを起動するスクリプト（node server.js）を書いておく
    2. server.js で new ApolloServer({ typeDefs, resolvers }) を作り、server.listen() で起動する。引数がないまま起動すると「typeDefs が必要」というエラーになる
    3. typeDefs（型定義）：gql で Book 型（title・author はどちらも String）と、Book のリストを返すクエリ test を定義する
    4. resolvers（リゾルバー）：クエリ test が実行されたときに返す値を決める。擬似データ（『吾輩は猫である』夏目漱石、『走れメロス』太宰治）の配列 books を返す。本来はデータベースから取ってくる部分
    5. localhost:4000 で Apollo のブラウザ画面を開き、query { test { title author } } を実行すると 2 冊分のデータが返る。画面左のドキュメントからフィールドを選んでクエリを組み立てることもできる

    動画で書いている server.js は、おおよそ次の形です。

    const { ApolloServer, gql } = require('apollo-server');

// 擬似データ（本来はデータベースから取得する）
const books = [
  { title: '吾輩は猫である', author: '夏目漱石' },
  { title: '走れメロス', author: '太宰治' },
];

// 型定義：Book 型と、Book のリストを返すクエリ test
const typeDefs = gql`
  type Book {
    title: String
    author: String
  }
  type Query {
    test: [Book]
  }
`;

// リゾルバー：クエリ test が呼ばれたら books を返す
const resolvers = {
  Query: {
    test: () => books,
  },
};

const server = new ApolloServer({ typeDefs, resolvers });
server.listen().then(({ url }) => {
  console.log(`Server ready at ${url}`);
});

    ブラウザ画面で実行するクエリはこれです。

    query {
  test {
    title
    author
  }
}

    7.2 フロントエンド（React + Apollo Client）

    1. create-react-app より高速な Vite（フロントエンドのビルドツール）で React の雛形を作る（npm create vite）。作ったら npm install を忘れずに実行する（忘れると起動時にエラーになる）
    2. @apollo/client・@apollo/react-hooks・graphql・apollo-boost をインストールする
    3. main.jsx で new ApolloClient({ uri: "http://localhost:4000", cache: new InMemoryCache() }) を作る（cache プロパティがないとエラーになる。InMemoryCache は取得したデータをメモリ上に残しておく仕組み）。ApolloProvider で App を包み、すべてのコンポーネントから使えるようにする
    4. App.jsx で gql を使ってクエリを定義する。結果をそのまま console.log すると構造が深くて分かりにくい
    5. useQuery フック を使うと loading・error・data を取り出せる。ロード中・エラー時の表示を分け、data.test.map() で著者とタイトルを画面に表示する

    main.jsx と App.jsx は、おおよそ次の形です。

    // main.jsx
import React from 'react';
import ReactDOM from 'react-dom/client';
import { ApolloClient, InMemoryCache, ApolloProvider } from '@apollo/client';
import App from './App';

const client = new ApolloClient({
  uri: 'http://localhost:4000',
  cache: new InMemoryCache(),   // ないとエラーになる
});

ReactDOM.createRoot(document.getElementById('root')).render(
  <ApolloProvider client={client}>
    <App />
  </ApolloProvider>
);
    // App.jsx
import { gql, useQuery } from '@apollo/client';

const BOOKS = gql`
  query {
    test {
      title
      author
    }
  }
`;

function Books() {
  const { loading, error, data } = useQuery(BOOKS);
  if (loading) return <p>ロード中...</p>;
  if (error) return <p>エラー</p>;
  return data.test.map(({ title, author }) => (
    <div key={title}>
      <p>{author}: {title}</p>
    </div>
  ));
}

export default function App() {
  return (
    <div>
      <h2>GraphQL Client</h2>
      <Books />
    </div>
  );
}

    バックエンドは npm run dev などで起動したままにしておき、フロントエンドを別のターミナルで起動すると、画面に「夏目漱石: 吾輩は猫である」「太宰治: 走れメロス」が表示されます。動画のソースコードは参考資料の GitHub リポジトリにあります。

    8.よくある質問（FAQ）

    質問答え
    GraphQL は REST API の代替ですか？必ずしも代替ではありません。プロジェクトの要件に応じて選びます。GraphQL は柔軟性が高く、REST API はシンプルでキャッシュが簡単です。
    セキュリティ上の問題はありませんか？GraphQL 自体は安全ですが、適切な 認証・認可 の実装が必要です（認証、認可）。クエリの複雑さを制限する（Depth Limit：ネストの深さの上限、Query Cost Analysis：クエリの重さを見積もって制限）などの対策も重要です。
    パフォーマンスはどうですか？適切に実装すれば、REST API と同等かそれ以上の性能が出ます。N+1 問題 に注意し、DataLoader（同じ種類の取得をまとめて1回にする道具）などを使いましょう。
    どの言語でサーバーを作れますか？JavaScript / TypeScript（Node.js）、Python、Java、Go、Ruby、PHP など、多くの言語で実装できます。

    5. 実践的な機能を追加：認証・認可、リアルタイム更新、ファイルアップロードなど

    重要なポイント

    • スキーマをしっかり設計する
    • セキュリティを考慮する
    • パフォーマンスを最適化する
    • エラーハンドリングを適切に実装する

    10.よくある誤解

    誤解1：「HTTP ステータスが 200 なら成功」

    GraphQL では、存在しない投稿を取ろうとしても data.post が null になり、理由は errors に入ります。一部だけ失敗する「部分的なエラー」もあるので、errors と path を必ず確認します。

    誤解2：「スキーマを書けばデータは自動で返ってくる」

    スキーマ（typeDefs）は「どんな型とクエリがあるか」の定義だけです。実際に何を返すかは resolvers が決めます。ハンズオンでも typeDefs と resolvers の両方を ApolloServer に渡しています（Hasura のように DB から自動生成する道具は別です）。

    誤解3：「GraphQL 自体が安全なので、認可や制限は要らない」

    GraphQL 自体は安全でも、認証・認可 は自分で実装する必要があります。自由なクエリで負荷をかけられないよう、Depth Limit や Query Cost Analysis も入れます。

    11.まとめ

    • GraphQL は「API（ウェイター）に問い合わせるための言語」とまず押さえる。単一エンドポイント・余計なデータを取らない・型で堅牢、がメリット
    • ブログアプリの例で、クエリ・ミューテーション・変数・エイリアス・フラグメント・エラー処理・用途別の書き分けを確認した
    • サーバーは GraphQL.js・Apollo Server・Hasura・Prisma・NestJS など、クライアントは GraphiQL / Playground・Apollo Client・Relay・urql・graphql-request などがある
    • サーバー側は typeDefs（型とクエリ）＋ resolvers（返す値）、クライアント側は ApolloClient ＋ ApolloProvider ＋ useQuery が基本の流れ
    • セキュリティ（認証・認可・クエリの複雑さの制限）とパフォーマンス（N+1・DataLoader）に注意する
    • まずは基本を理解し、小さなプロジェクトから始めて、徐々に複雑な機能を追加していく

    REST で同じような API を設計する練習は TODO APIのケーススタディ でできます。
