    70 ドキュメントとテスト

    API設計レビューの実践 — 進め方・チェックリスト・指摘の書き方

    実際の API 案をレビューする手順を学びます。レビューの進め方と役割分担、レビュー用の短縮チェックリスト、良い API と悪い API の比較、相手に伝わる改善提案の書き方、そして API 設計を学んだ後の次のステップまでを押さえます。

    もとにしたノート：70_ドキュメントとテスト/04_API設計レビューの実践

    ひとことで言うと

    設計レビューは、OpenAPI 草案と背景 を事前に配り、各自で読んでから短い打ち合わせで URL・エラー・認可・互換性 を議論し、決まったことを記録する流れで進めます。チェックリストで漏れを防ぎ、指摘は 問題 + 理由 + 具体案 の 3 点セットで書きます。良い API の本質は、他のエンドポイントと同じルールで予測できる ことです。

    2.設計レビューの進め方

    1. 事前：OpenAPI 草案と背景（なぜこの API が必要か）を用意する
    2. 独読：レビュアーが各自 15 分で読む
    3. 同期 30 分：集まって URL・エラー・認可・互換性を議論する
    4. 記録：決定事項を ADR（設計判断とその理由を残す短い文書）または CHANGELOG に残す
    5. フォロー：実装の PR で OpenAPI の diff を確認する

    ADR については 41章：意思決定とADR にあります。

    役割担当
    提案者草案を作り、ユースケースを示す
    レビュアーサーバー側 + クライアントの代表
    オブザーバー将来の利用者（任意）

    3.レビュー用チェックリスト

    チェックリストとアンチパターン の全体版をもとにした、レビュー時に使う短縮版です。

    カテゴリ確認項目
    URL複数形・名詞・浅いネスト・/v1/
    メソッドGET は安全で副作用なし
    レスポンス成功の形・エラーの形が統一されている
    認証認可401/403 の使い分け・所有者チェック
    寿命破壊的変更か・Deprecation（非推奨）の計画
    ドキュメントOpenAPI・サンプル・CHANGELOG
    信頼性レート制限・Idempotency-Key（必要なとき）

    印刷して ☐ にチェック しながらレビューすると、漏れが減ります。

    4.良い API・悪い API の比較

    ユーザーを検索する API で比べます。

    観点悪い例良い例
    URLGET /getUserByEmail?email=GET /v1/users?email=
    エラー500 だけ422 + VALIDATION_ERROR
    一覧全件を返すpage / limit + meta
    認証クエリに API KeyAuthorization ヘッダ
    ✕ 悪い例：動詞の URL、API キーをクエリに載せる 
    GET /api/getUserByEmail?email=taro@example.com&api_key=SECRET
    ◯ 良い例：名詞のリソース、認証はヘッダで 
    GET /v1/users?email=taro@example.com
Authorization: Bearer <token>

    違いの本質

    良い例は、他のエンドポイントと同じルール で予測できます。1 つ覚えれば残りも推測できるのが、良い API です（一貫性）。

    5.改善提案の書き方

    レビューのコメントは、問題 + 理由 + 具体案 の 3 点セットにします。

    ## 指摘: 注文キャンセル API

**現状案**: POST /v1/cancelOrder

**問題**: 動詞 URL で他 API（/v1/orders）と一貫性がない

**提案**: POST /v1/orders/{id}/cancel
         または PATCH /v1/orders/{id} body: {"status": "cancelled"}

**参考**: 02_URLとリソースの設計 — リソースは名詞

    参考に挙げている考え方は URLとリソースの設計 で扱っています。

    NG コメントOK コメント
    「ダメです」「/v1/orders/{id} に統一すると、一覧と同じ規則になります」
    「セキュリティが心配」「owner（所有者）チェックが無いので、403 を返す処理を追加してください」

    7.よくある誤解

    誤解1：「レビューは集まってその場で読めばよい」

    その場で初めて読むと、議論が浅くなります。草案と背景を事前に配り、各自で読んでから 短い時間で集まると、URL・エラー・認可・互換性といった大事な点に時間を使えます。

    誤解2：「問題点を指摘すればレビューの役目は果たせる」

    「ダメです」「心配です」だけでは、相手は何を直せばよいか分かりません。問題・理由・具体案 をそろえて、そのまま直せるコメントにします。

    誤解3：「決まったことは議事録がなくても覚えている」

    なぜその形にしたのかは、すぐ忘れられます。決定事項は ADR や CHANGELOG に残し、実装の PR では OpenAPI の diff で合意どおりかを確かめます。

    8.まとめ

    • 事前配布 → 独読 15 分 → 同期 30 分 → 記録 → フォローの流れで進める
    • レビュアーにはサーバー側とクライアントの代表を入れる
    • 短縮チェックリスト（URL・メソッド・レスポンス・認証認可・寿命・ドキュメント・信頼性）で漏れを防ぐ
    • 良い API は他のエンドポイントと同じルールで予測できる
    • 指摘は問題 + 理由 + 具体案の 3 点セットで書く
