    HTTPメソッドと操作の表現 — GET・POST・PUT・PATCH・DELETE の使い分け

    REST API では、URL が「何を」、HTTP メソッドが「どうするか」を表します。5つのメソッドの役割、安全性と冪等性、作成・取得・更新・削除の典型パターン、GET に副作用を持たせてはいけない理由、成功・失敗時のステータスコードの組み合わせを、動画で紹介されたベストプラクティスとあわせて解説します。

    もとにしたノート：30_リソース設計/03_HTTPメソッドと操作の表現、REST API Basics & Best Practices Explained（動画まとめ）

    ひとことで言うと

    同じ URL でも、GET は取得、POST は作成、PUT は丸ごと置換、PATCH は部分更新、DELETE は削除 です。GET は状態を変えない（安全）、GET・PUT・DELETE は何度送っても結果が同じ（冪等）、POST は送るたびに新しいものができる（非冪等）と覚えます。

    RESTful とは、リソースを URL で識別し、HTTP メソッドを正しく使い、ステートレス（サーバーが前のやり取りを覚えておかない）に通信するなど、REST の制約に沿った設計のことです。目的は、フロントエンド・他サービス・外部の開発者が迷わず使える 予測可能で一貫した API を作ることです。REST そのものは RESTの考え方、HTTP の基礎は HTTPの基本 を見てください。

    2.GET・POST・PUT・PATCH・DELETE の役割

    REST API は HTTP の上で動くので、HTTP のメソッドを使って CRUD（Create 作成・Read 読み取り・Update 更新・Delete 削除）を表します。

    メソッド意味典型用途例
    GET取得一覧・詳細の参照GET /api/v1/products
    POST作成新規リソース作成、非冪等な処理POST /api/v1/products
    PUT置換リソース全体の更新（存在しなければ作成も可）PUT /api/v1/products/{id}
    PATCH部分更新一部フィールドだけ変更PATCH /api/v1/products/{id}
    DELETE削除リソース削除DELETE /api/v1/products/{id}
     
    GET    /users          … 一覧
POST   /users          … 新規作成
GET    /users/123      … 詳細
PATCH  /users/123      … 名前だけ変更
DELETE /users/123      … 削除

    URL の形は /api/{バージョン}/{リソース} や、その後ろに /{id} を付けたものが典型です。ポイントは、同じパスでもメソッドが操作の意味を担う ことです。

    2.1 PUT と PATCH の違い

    PUT と PATCH は同じ URL（/products/{id}）を使いますが、全体更新か部分更新か で使い分けます。

    PUT（全体置換）

    ID 123 の商品を、フロントエンドから送られてきた新しい内容で 丸ごと置き換え ます。

    PATCH（部分更新）

    たとえばタイトルだけを送ると、タイトルだけが更新 され、ほかの項目はそのまま残ります。

    DELETE は対象の URL に送るだけで、リクエストボディ（本文）は付けません。ボディの中身の設計は ボディの設計 で扱います。

    3.冪等性と安全性

    メソッドには2つの大切な性質があります。安全（Safe） は「サーバーの状態を変えない」こと、冪等（Idempotent、べきとう） は「同じリクエストを何度送っても結果が同じ」ことです。

    性質意味メソッド
    安全（Safe）サーバー状態を変えないGET
    冪等（Idempotent）同じリクエストを何度送っても結果が同じGET、PUT、DELETE（PATCH は △）
    非冪等送るたびに新しいリソースができる等POST
     
    DELETE /users/123  を 2 回  →  2 回目も「削除済み」で同じ結果（冪等）
POST   /users      を 2 回  →  ユーザーが 2 人できる（非冪等）
    • GET /products を2回、3回と送っても、（その間に新しい商品が DB に追加されない限り）毎回同じ結果が返ります
    • POST /products は送るたびに新しい商品が作られ、1回目は1件目の ID、2回目は2件目の ID が返ります

    決済など POST の二重送信対策は レート制限と冪等性（Idempotency-Key）で扱います。

    4.作成・取得・更新・削除の典型パターン

    操作リクエスト成功レスポンス
    一覧取得GET /users200 + 配列（または data でラップ）
    詳細取得GET /users/{id}200 + オブジェクト
    作成POST /users + JSON ボディ201 + Location ヘッダ
    部分更新PATCH /users/{id} + 変更フィールド200 または 204
    削除DELETE /users/{id}204

    作成に成功したら、Location ヘッダ（新しくできたリソースの URL を知らせるヘッダ）を付けて返します。

    POST /v1/users HTTP/1.1
Content-Type: application/json

{"name": "田中太郎", "email": "taro@example.com"}

→ 201 Created
  Location: /v1/users/usr_01HXYZ

    5.GET に副作用を持たせない理由

    GET は安全 でなければなりません。つまりサーバーの状態を 変えてはいけません。副作用（データの削除・更新など、結果を返す以外の変化）を GET に持たせると、次のような事故が起きます。

    理由説明
    キャッシュGET は CDN・ブラウザがキャッシュ（結果を保存して使い回すこと）する
    Prefetchブラウザがリンク先を先読みすることがある
    ブックマーク・共有URL が「操作の実行」になっていると危険
    ✕ 危険な例：GET で状態を変える 
    GET /users/123/delete     … リンクを踏んだだけで削除
GET /orders/456/approve   … 承認が意図せず実行される
    ◯ 安全な例：副作用は POST 等で 
    POST /orders/456/approve

    削除・更新・作成は POST / PUT / PATCH / DELETE を使います。approve のような動詞的な操作の扱い方は 検索と複合操作 で説明します。

    6.メソッドとステータスコードの組み合わせ

    操作成功時よくある失敗
    GET 一覧200 OK—
    GET 詳細200 OK404 Not Found
    POST 作成201 Created400, 409, 422
    PUT / PATCH 更新200 OK または 204404, 409, 422
    DELETE 削除204 No Content404
     
    POST で作成成功 → 201（200 だけ返す API もあるが 201 がより明確）
DELETE 成功     → 204（ボディなし）が一般的

    動画では、ステータスコードを次のように整理しています。

    分類コード使い分けの例
    2xx 成功200 OKGET /products/{id} で商品を取得できたとき
    201 CreatedPOST /products で新しい商品を作ったとき（200 ではなく 201）
    204 No Content削除や更新で、返す本文がないとき
    3xx リダイレクト301 などURL が移動したとき、新しい場所へ誘導する
    4xx クライアントエラー400 Bad Request不正なクエリ、壊れた JSON
    401 Unauthorizedログイン・トークンが必要な操作を未認証で呼んだ
    404 Not Found存在しない productId を指定した（400 ではなく 404）
    5xx サーバーエラー500クライアントは正しいが、サーバー内部で予期しない障害が起きた

    400 と 404 の区別

    パラメータの 形式が間違っている なら 400、形式は正しいが該当 ID が DB に無い なら 404 です。500 のときは原因の詳細をログに残し、レスポンスには内部情報を出しすぎないようにします。

    ステータスコード・エラー設計 と合わせて、成功・失敗の両方 を設計します。

    7.動画で紹介された REST API のベストプラクティス

    動画（Hayk Simonyan「REST API Basics & Best Practices Explained」）は、メソッド以外にもリソース設計や一覧 API の設計を扱っています。それぞれ詳しいページがあるので、ここでは要点だけまとめます。

    7.1 リソースモデリング（名詞で表す）

    商品・注文・レビューといったビジネスドメインを API にするときは、動詞ではなく名詞 でリソースを表します。

    概念悪い例良い例
    商品一覧GET /getProductsGET /products
    特定商品—GET /products/{id}
    注文GET /getOrdersGET /orders（メソッドで取得・作成を区別）
    特定商品のレビュー—GET /products/{productId}/reviews（親子関係が URL から読める）

    /products は複数件の コレクション、/products/{id} は 単一リソース です。詳しくは URLとリソースの設計。

    7.2 フィルタ・ソート・ページネーション

    実際の API では全件を一度に返すことはまれです。クエリパラメータ（URL の ? より後ろの部分）で必要なデータだけを取ります。

    機能例ポイント
    フィルタGET /products?category=electronics&inStock=trueUI に表示する行だけ返し、帯域・レスポンスサイズ・フロントの負荷を抑える
    ソートGET /products?sort=price昇順／降順は API の規約で決める。数千件をクライアントで並べ替えるのは非効率なので サーバー側で並べる
    page + limit?page=2&limit=102 ページ目から最大 10 件。limit がないと「2 ページ目以降すべて」になり得る
    offset + limit?offset=20&limit=10先頭から何件飛ばすか（offset）と件数上限
    cursor?cursor=...ページ位置を表す値（ハッシュなど）で次ページを取る。大量データやリアルタイム更新向き

    これにより、サーバーの帯域の節約、サーバー・クライアント双方の性能向上、フロントが「必要な分だけ」取れる柔軟性が得られます。詳しくは ページネーション・フィルタ・ソート。

    7.3 ベストプラクティス5か条

    1. 複数形の名詞：/product ではなく /products でコレクションを表す
    2. HTTP メソッドを正しく使う：削除は DELETE /users/{id}。POST /users/{id}/delete のような擬似アクション URL は避ける
    3. フィルタ・ソート・ページネーションをそろえる：ページ番号だけでなく limit やソート条件も指定できるようにする（例：page=3&limit=10&sort=price）
    4. API バージョニング：パスに /api/v1、/api/v2 を付ける。互換性を壊す変更をしても、既存のクライアントは旧バージョンを使い続けられる（バージョニング）
    5. 一貫した URL とステータス：リソース名・ネスト・エラーコードのルールをドキュメントにし、チーム全体で守る（一貫性）

    動画の最後では、REST 以外の API スタイル（GraphQL、gRPC など）を別の動画で学ぶよう案内しています。このサイトでは REST以外のAPIスタイル で扱います。

    8.よくある誤解

    誤解1：「PUT と PATCH はどちらも更新だから同じ」

    PUT は リソース全体を置き換える、PATCH は 送った項目だけ変える です。PUT でタイトルだけを送ると、仕様によってはほかの項目が消えたり null になったりします。どちらを使うか、送らなかった項目をどう扱うかを API ごとに明確にします。

    誤解2：「作成も成功だから 200 を返せばよい」

    200 を返す API もありますが、201 Created のほうが「新しく作られた」ことがはっきり伝わります。Location ヘッダで新しいリソースの URL も返すと、クライアントはすぐにそのリソースを取りに行けます。

    誤解3：「GET で削除や承認ができると、リンク1つで済んで便利」

    GET はキャッシュ・先読み・ブックマークの対象になるため、意図しないタイミングで実行される 危険があります。状態を変える操作は必ず POST / PUT / PATCH / DELETE にします。

    誤解4：「存在しない ID を指定されたら 400」

    リクエストの形式は正しく、指定された ID のリソースが見つからないだけなら 404 Not Found です。400 は不正なクエリや壊れた JSON のように、リクエスト自体がおかしい ときに使います。

    9.まとめ

    • GET は取得、POST は作成、PUT は全体置換、PATCH は部分更新、DELETE は削除
    • GET は安全、GET・PUT・DELETE は冪等、POST は非冪等
    • 作成は 201 + Location、削除は 204 が典型
    • GET に副作用を持たせない（キャッシュ・先読み・ブックマークで事故になる）
    • 成功と失敗の両方のステータスコードを設計する（形式不正は 400、存在しないは 404）
    • 複数形の名詞、正しいメソッド、フィルタ・ソート・ページネーション、バージョニング、一貫性がベストプラクティス
