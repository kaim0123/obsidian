    10 APIの基礎

    API設計の原則 — 予測可能性・最小の驚き・契約・ライフサイクル

    一貫性を支える設計の考え方を学びます。予測可能性、最小の驚き、契約としての API、クライアント開発者の体験、設計判断の優先順位、組み立て部品としての API を押さえたうえで、API スタイル（REST・GraphQL・gRPC）とプロトコルの選び方、設計プロセス、設計から廃止までのライフサイクル、分野別のベストプラクティスを見渡します。

    もとにしたノート：10_APIの基礎/05_API設計の原則、07_API設計のベストプラクティス、API Design 101 From Basics to Best Practices

    ひとことで言うと

    API は、サーバーとクライアントのあいだの 契約 です。良い API は 1 つ学べば他も推測でき（予測可能性）、利用者の直感どおりに動き（最小の驚き）、小さな部品として組み合わせられます。そして API 開発はコードを書くことだけではなく、要件の理解から設計・保守・廃止まで を含めて考えるものです。

    2.予測可能性 — ドキュメントなしでも「だいたい当たりがつく」

    予測可能性（Predictability） とは、1 つの API を理解すれば、他も 同じパターン で推測できる状態です。一貫性 は、この予測可能性を生むための手段です。

    予測可能予測不可能
    GET /users, GET /orders で同じレスポンス構造エンドポイントごとに JSON の形が違う
    エラーは常に { "error": { "code": ... } }ある API は文字列、ある API は配列
    作成は常に POST + 201ある API は POST /createUser

    予測可能な API

    学習コストが低く、SDK（API を呼ぶための部品集）にしやすい。

    予測不可能な API

    毎回ドキュメント必読。バグの温床になる。

    3.最小の驚き（Principle of Least Astonishment）

    最小の驚きの原則 とは、利用者が 直感的（intuitive） に期待する動きに合わせる、という考え方です。

    驚きが少ない驚きが大きい
    DELETE /users/123 で削除GET /users/123/delete で削除
    404 = 存在しない404 = 権限不足（403 の方が自然）
    created_at は作成日時created_at が文字列 "不明" を返す

    「一般的な Web API の常識」から大きく外れる設計は、クライアント開発者の混乱・バグ・問い合わせの増加につながります。REST や HTTP の慣習から 意図的に外れる ときは、理由をドキュメントに明記します。

    4.契約（Contract）としての API

    API は 契約（Contract） です。サーバーとクライアントの間で「こう送れば、こう返す」と約束します。どんなリクエストを送れるか（エンドポイント・HTTP メソッドなど）と、エンドポイントごとにどんなレスポンスが返るかを定めます。

    契約の要素内容
    URL・メソッドどこに、何をするか
    リクエスト形式必須フィールド、型
    レスポンス形式成功・失敗時の JSON 構造
    ステータスコード結果の種類
    後方互換性変更してよい範囲（後方互換性）

    契約としての API には、次の 2 つの役割もあります。

    • 抽象化：内部実装を隠して機能だけを公開します。利用者は「ユーザーを保存する」エンドポイントを呼ぶだけで、DB 設計やビジネスロジックを知る必要がありません
    • サービス境界：ユーザー管理用のサーバー、投稿管理用のサーバーのように責務ごとにシステムを分けつつ、クライアント↔サーバー、サーバー↔サーバーの通信を、実装技術が違っても 可能にします

    OpenAPI などで契約を 機械可読（プログラムが読める形）にすると、テスト・レビューに活かせます（OpenAPIとドキュメント）。

    5.クライアント開発者の体験を想像する

    API 設計は サーバー側の都合だけ で決めると使いにくくなります。

    クライアント設計で気をつけること
    ブラウザ（SPA）CORS、トークン管理
    モバイルアプリ古いバージョンが長期間残る、オフライン
    他サーバー安定性、レート制限、冪等性
    管理画面一覧・フィルタ・ページネーション

    「自分がこの API を使う側だったら？」

    そう考えるだけで、命名・エラー・ページネーションの判断が変わります。API設計を学ぶ理由とゴール でも触れたように、API 設計は 橋渡し の仕事です。

    6.設計判断の優先順位のつけ方

    すべてを一度に完璧にしようとせず、優先順位 をつけます。

    優先度項目理由
    高一貫性・REST 基本・エラー形式後から直すと全体に波及
    高認証・HTTPSセキュリティは最初から
    中ページネーション・バージョニングデータが増えてから必要
    中OpenAPI ドキュメントチームが増えたら必須
    低（最初は）HATEOAS など発展的 REST基本が固まってから

    進め方は 小さく公開 → 利用フィードバック → ガイドライン更新 の繰り返しです。APIの進化と運用 でも、最初から完璧は不要 という視点を扱います。

    7.良い Web API — 組み立て部品として提供する

    「大は小を兼ねる」万能エンドポイントは、かえって使いにくいことが多いです（増田亨『現場で役立つシステム設計の原則』の考え方）。

    使いにくい例組み立てやすい例
    全業務を 1 レスポンスに詰めた巨大 API中核リソースの小さな操作を組み合わせる
    サーバー都合の内部構造の丸出しクライアントが予測できるリソースとエラー

    良い Web API は、アプリケーションを組み立てるための部品 です。単純なことをかんたんにできるところから始め、利用を見て育てる進め方は 発展性のあるAPI開発、ドメインとの変換は APIとドメイン設計 で扱います。

    8.API スタイルとプロトコルの選択

    8.1 主要な 3 つの API スタイル

    スタイル特徴向いている用途
    RESTリソース指向、HTTP メソッド（GET/POST/PUT・PATCH/DELETE）、ステートレスWeb・モバイルで最も一般的
    GraphQLクエリ言語、単一エンドポイント、必要なフィールドだけ取得。query / mutation / subscription複雑な UI、ネストしたデータ、往復回数を減らしたいとき
    gRPCProtocol Buffers を使う高性能 RPC、ストリーミング・双方向通信マイクロサービス間・社内システム間の高速通信
    • REST は、各リクエストに処理に必要な情報がすべて含まれ、前のリクエストに頼らずに処理できる ステートレス 設計が特徴です。GET で取得、POST で保存、PUT / PATCH で更新、DELETE で削除と、HTTP の標準メソッドで CRUD（作成・読み取り・更新・削除）を表すため、学習コストが低く普及しています
    • GraphQL は、REST の次によく使われるスタイルです。クライアントが欲しいものを正確に指定できるクエリ言語で、操作を query（取得）、mutation（更新。REST の POST / PUT / PATCH に相当）、subscription（リアルタイム通信）に分けます。REST で 3 回必要な取得を 1 リクエストにまとめられるため、画面ごとに必要なデータが違う 複雑なフロントエンド 向きです
    • gRPC は 3 つの中では相対的にニッチですが、サーバー間通信では HTTP ベースの REST / GraphQL より効率が高いです。proto ファイル（Protocol Buffers の定義ファイル）に RPC（遠隔の関数呼び出し）としてメソッドを定義し、ストリーミングと双方向通信に対応します

    8.2 REST と GraphQL の実務的な違い

    観点RESTGraphQL
    エンドポイントリソース単位（/users、/users/{id}/posts、/followers など）多くは /graphql などの 単一エンドポイント
    関連データの取得ユーザー詳細・投稿・フォロワーで 3 回のリクエスト のように往復が増えやすい1 リクエストで必要なフィールドだけ取得
    レスポンス構造固定（同じエンドポイントなら、値は変わっても形は同じ）クライアントが 構造を指定。取りすぎ（オーバーフェッチ）・不足を抑えられる
    バージョニング/v1/、/v2/ の 明示的バージョニングスキーマは バージョン番号なしで進化 することが多い（followersV2 のようにフィールド単位で版を分ける方法も。旧版を使うクライアントがいないと確かなら、そのまま変更することもある）
    キャッシュリクエストのヘッダーで HTTP キャッシュ を活用しやすいアプリケーションレベルのキャッシュ が中心

    GraphQL のクエリは、たとえば次のように「ID 123 のユーザーの名前、投稿のタイトルと本文、フォロワーの名前だけ」を 1 回で指定します。

    query {
  user(id: 123) {
    name
    posts { title content }
    followers { name }
  }
}

    選び方の目安は、シンプルな CRUD とキャッシュ重視なら REST、1 画面で多様な・ネストしたデータが必要なら GraphQL です。詳しくは REST以外のスタイル、RESTとGraphQLの違い で扱います。

    8.3 プロトコルの選択が設計を左右する

    API スタイルとセットで、通信の土台となる プロトコル（トランスポート層の通信方式）も考えます。

    プロトコル特徴・使いどころ
    HTTPREST・GraphQL の土台。ステータスコードと相性が良く、CRUD の成功・失敗を表現しやすい
    WebSocket双方向・リアルタイム通信（チャット、動画配信など）
    gRPC（HTTP/2 上）マイクロサービス間で低レイテンシ・高スループットを狙う場合。HTTP より高速にできる

    プロトコルは パフォーマンス、リアルタイム性、キャッシュ、運用の複雑さ に直結し、API の構造・性能・機能を根本から左右します。作る API の種類と制約に合わせて、強みと制約で選びます。

    9.API 設計プロセス

    9.1 要件の理解

    • コアユースケース・ユーザーストーリー（利用者が何をしたいか）の洗い出し
    • スコープと境界：大きな API なら一度に全部は作らない。初回リリースに含める機能・含めない機能を決める
    • 性能要件とボトルネック（処理が詰まりそうな箇所）の想定
    • セキュリティ：認証・認可・レート制限を最低限、必要に応じて追加する（APIセキュリティ）

    9.2 設計アプローチ

    アプローチ進め方よく使う場面
    トップダウン高レベルの要件・ワークフローから、エンドポイントと操作を定義する面接や新規設計
    ボトムアップ既存のデータモデル・機能から API を導く企業の既存システムの拡張
    コントラクトファースト実装前にリクエスト／レスポンスの契約を決めて固定する（トップダウンに近い）チーム開発・面接

    10.API ライフサイクル

    API 開発は「コードを書く」だけではありません。設計から廃止までの一生を見据えて考えます。

    1. 設計 — 要件と期待する成果を話し合って合意する
    2. 開発・ローカルテスト
    3. デプロイ・監視 — ステージング（本番前の検証環境）や本番でさらにテストする
    4. メンテナンス — 最初から シンプル に保っておくと、自分にも他の開発者にも保守が楽になる
    5. 非推奨化（deprecation）・廃止（retirement） — 新バージョンが出たとき、v1 → v2 への移行などで旧 API を段階的に止める（バージョニング、APIの進化と運用）

    長期運用を見据え、設計・保守性・廃止計画まで含めて考えることが、スケーラブルで安全な API につながります。

    11.分野別のベストプラクティス

    API 設計は 「一貫性・拡張性・保守性・セキュリティ」 を意識して行います。分野ごとの要点と、詳しく学べるページです。

    エンドポイント・リソース設計

    • リソース指向（/users, /posts, /orders など）
    • 名詞ベースのエンドポイント設計（動詞は使わない）
    • 階層構造でリレーションを表現（/users/1/posts など）
    • 一貫した命名規則（小文字・複数形推奨）

    → URLとリソースの設計

    バージョニング

    • 仕様変更時はバージョンを明示（/v1/users, /api/v2/… など）
    • URL パス・ヘッダー・クエリパラメータでのバージョン管理
    • 旧バージョンの互換性維持と段階的な廃止

    → バージョニング

    エラー設計

    • 一貫したエラーレスポンス形式（例：{ "error": { "code": 400, "message": "Bad Request" } }）
    • 適切な HTTP ステータスコードの選択
    • バリデーションエラーや認証エラーの詳細なメッセージ
    • エラー ID やトレース ID で障害調査を容易に

    → エラー設計

    認証・認可

    • API キー、OAuth2、JWT などの認証方式
    • 権限ごとのアクセス制御（RBAC, ABAC）
    • HTTPS 必須、CORS 設定

    → 認証、認可、73章：RBAC・ABAC・ACL、72章：CORS

    ドキュメント化

    • OpenAPI（Swagger）や API Blueprint で仕様を明文化
    • サンプルリクエスト/レスポンス、エラー例も記載
    • 自動生成ツールの活用（Swagger UI, Redoc など）

    → OpenAPIとドキュメント

    パフォーマンス・スケーラビリティ

    • ページネーション、フィルタリング、ソートの設計
    • レートリミット、キャッシュ制御（ETag, Cache-Control）
    • 非同期処理やバルク API（一括処理）の検討

    → ページネーション、検索と複合操作

    セキュリティ

    • 入力値バリデーション、SQL インジェクション・XSS 対策
    • レートリミット、IP 制限、監査ログ
    • セキュリティヘッダー（CSP, HSTS, X-Frame-Options など）

    → APIセキュリティ、72章：SQLインジェクション、72章：XSS、72章：セキュリティヘッダ

    アンチパターン

    • 動詞ベースのエンドポイント（/getUser, /createOrder など）
    • 一貫性のないレスポンス形式
    • 過度なネストや巨大なレスポンス
    • バージョン管理の欠如

    → チェックリストとアンチパターン

    12.よくある誤解

    誤解1：「何でも 1 回で返す万能 API が一番便利」

    全業務を 1 レスポンスに詰めた巨大 API は、使う側から予測しにくく、変更にも弱くなります。中核リソースの小さな操作を組み合わせられる部品 として提供する方が、結果的に使いやすくなります。

    誤解2：「権限がないことを隠すには 404 を返すのが普通」

    404 は「存在しない」という意味なので、権限不足に使うと利用者は驚きます。最小の驚きの原則 に従い、権限不足は 403 にするのが自然です。慣習から意図的に外れるなら、その理由をドキュメントに書きます。

    誤解3：「GraphQL は REST の上位互換だから、いつも GraphQL を選べばよい」

    GraphQL は複雑な UI や往復回数の削減に強い一方、HTTP キャッシュを活かしにくく、キャッシュはアプリケーション側が中心になります。シンプルな CRUD とキャッシュ重視なら REST、サーバー間の高速通信なら gRPC と、用途で選びます。

    誤解4：「API 開発はリリースしたら終わり」

    API には設計 → 開発 → デプロイ・監視 → 保守 → 非推奨化・廃止という ライフサイクル があります。保守しやすいようにシンプルに作り、いずれ来る廃止まで計画しておくことも設計の一部です。

    13.まとめ

    • 予測可能性 — ドキュメントなしでも「だいたい当たりがつく」
    • 最小の驚き — 利用者の直感どおりに。慣習から外れるなら理由を明記
    • API は契約。抽象化とサービス境界の役割を持ち、破るとクライアントが壊れる
    • クライアント開発者の体験を想像し、優先順位（一貫性・エラー形式・認証を先に）をつけて小さく公開・改善する
    • 万能 API より、組み合わせ可能な部品としての API
    • 一般的な Web は REST、複雑な UI は GraphQL、サーバー間の高速通信は gRPC。プロトコルも強みと制約で選ぶ
    • 要件の理解 → 設計アプローチの選択 → 設計から廃止までのライフサイクル全体を見据えるのが API 設計
