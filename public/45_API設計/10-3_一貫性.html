    10 APIの基礎

    一貫性 — 同じ種類の操作は同じルールで表現する

    API 設計の第一歩である「一貫性」を学びます。一貫性とは何か、ないと何が起きるか、命名・日時・ID・レスポンス形式・真偽値など揃えるべき項目、チームで守るためのガイドライン 1 枚、そして確認用のチェックリストまでを押さえます。

    もとにしたノート：10_APIの基礎/04_一貫性

    ひとことで言うと

    一貫性（Consistency） とは、API 全体で 命名・形式・エラー・レスポンス構造 などのルールが揃っている状態です。1 つの API を覚えれば他も同じように使えるので、クライアントの共通処理が書けて、レビューの基準にもなります。ルールは ガイドライン 1 枚 にまとめて守ります。

    2.一貫性とは何か

    一貫性（Consistency） とは、API 全体で 命名・形式・エラー・レスポンス構造 などのルールが揃っている状態です。言いかえると、同じ種類の操作は同じルールで表現する ことです。

    ◯ 一貫性がある API 
    GET /users     → { "data": [...] }
GET /orders    → { "data": [...] }   ← 同じ形
    ✕ 一貫性がない API 
    GET /users     → { "data": [...] }
GET /orders    → [ {...}, {...} ]    ← 配列を直返し（混乱）

    一貫性は API設計の全体像 で紹介した 8 テーマの第 1 項目です。REST・エラーなど他のテーマも、一貫性の上に成り立ちます。

    3.一貫性がないときに起きる問題

    問題具体例
    共通処理が書けないエンドポイント（API の呼び出し先 URL）ごとにパース（受け取ったデータの読み取り）方法が違う
    ドキュメント依存「この API だけ例外」が増える
    レビュー基準がない各自バラバラに設計する
    SDK・クライアントライブラリが複雑化if 分岐だらけになる（SDK＝API を呼ぶための部品集）

    その結果、次のような悪循環に入ります。

    • クライアントのバグが増える
    • 新メンバーの学習コストが増える
    • レガシー API が固定化する（直すと壊れるので、誰も直せなくなる）

    4.揃えるべき項目

    特に揃えておきたいのは、命名・日時・ID・レスポンス形式・真偽値の 5 つです。

    項目良い例（統一）悪い例（バラバラ）
    命名snake_case（単語を _ でつなぐ）または camelCase（2 語目以降を大文字で始める）を全体で固定/getUser と /orders/list が混在
    日時ISO 8601（日時の国際標準形式。2026-06-19T10:00:00Z）2026/06/19 と Unix 秒が混在
    ID文字列 UUID またはプレフィックス付き ID（usr_01HXYZ のように種類を表す接頭辞を付けた ID）数値 ID と UUID が混在
    レスポンス常に { "data": ... } でラップ配列直返しとオブジェクト返しが混在
    真偽値true / false1 / 0 や "yes" / "no"
    ◯ ルールが揃ったレスポンスの例 
    {
  "data": {
    "id": "usr_01HXYZ",
    "name": "田中太郎",
    "created_at": "2026-06-19T10:00:00Z",
    "is_active": true
  }
}

    この例では、data でラップし、フィールド名は snake_case、ID はプレフィックス付き文字列、日時は ISO 8601（末尾の Z は UTC＝協定世界時の意味）、真偽値は true で表しています。日時や ID の形式は JSONとデータ形式、ボディの設計 でも扱います。

    5.API 設計ガイドラインを 1 枚にまとめる

    チーム開発では、1 枚のガイドライン にルールを書いておくと効果的です。

    カテゴリ決めること（例）
    URL複数形、小文字、ハイフン、ネストの深さ（URLとリソースの設計）
    JSONフィールド命名規則、日時形式、ID 形式
    レスポンス成功時のラップ形式、エラー形式（エラー設計）
    ステータス401/403/404/422 の使い分け（ステータスコード）
    バージョン/v1/ 方式など（バージョニング）

    OpenAPI（API の仕様を機械が読める形で書く標準形式）でスキーマを定義しておくと、ガイドラインとの整合をレビューで確かめやすくなります（OpenAPIとドキュメント）。チームでの運用の視点は チームでAPI設計を守る で扱います。既存の API があるなら、新規だけ直すのではなく、段階的に揃える計画を立てます。

    6.一貫性のチェックリスト

    新しい API を作ったときや、レビューのときに確認します。

    • フィールド命名（snake_case / camelCase）が API 全体で統一されているか
    • 日時は ISO 8601 + UTC（またはタイムゾーン明示）か
    • ID の型・形式がリソース間で揃っているか
    • 成功レスポンスの構造（data / meta）が統一されているか
    • エラーレスポンスの構造（error.code など）が統一されているか
    • 真偽値・列挙値（決まった選択肢から選ぶ値）の表現が統一されているか
    • 新規 API がガイドラインから外れていないか（レビューで確認）

    ほかの観点も含めた全体のチェックリストは チェックリストとアンチパターン にあります。

    7.よくある誤解

    誤解1：「snake_case と camelCase、どちらが正解かを決めることが大事」

    大事なのはどちらを選ぶかより、API 全体で 1 つに固定すること です。混在していると、クライアントはエンドポイントごとに書き分けなければなりません。

    誤解2：「中身が合っていれば、配列を直返ししてもオブジェクトで包んでも同じ」

    エンドポイントごとに形が違うと、クライアントは共通のパース処理を書けず、if 分岐だらけになります。常に { "data": ... } で包むなど、形を揃える ことで共通処理が書けるようになります。

    誤解3：「ルールは各自が頭の中で分かっていれば十分」

    頭の中のルールはレビューの基準になりません。ガイドライン 1 枚 に書き出しておくと、レビュー基準になり、OpenAPI と整合させやすく、新メンバーもすぐ同じ形で追加できます。

    8.まとめ

    • 一貫性とは、API 全体で命名・形式・エラー・レスポンス構造のルールが揃っている状態
    • 一貫性がないと、共通処理が書けず、ドキュメント依存・レビュー基準なし・SDK の複雑化が起き、バグと学習コストが増え、レガシー API が固定化する
    • 命名・日時（ISO 8601）・ID・レスポンス形式（data でラップ）・真偽値（true / false）を揃える
    • ルールは API 設計ガイドライン 1 枚にまとめ、レビューと OpenAPI で守る
    • チェックリストで新規 API がルールから外れていないか確かめる

    次は API設計の原則 です。
