    20 HTTPの土台

    リクエストとレスポンス — HTTP メッセージの中身を読む

    HTTP のリクエストとレスポンスが、それぞれどんな部品でできているかを学びます。リクエストライン・ヘッダー・ボディの役割、レスポンスのステータス・ヘッダー・ボディの読み方、代表的なステータスコードとエラーの返し方、そして curl やブラウザの開発者ツールで実際の HTTP を観察する方法までを押さえます。

    もとにしたノート：20_HTTPの土台/02_リクエストとレスポンスの構造、20_HTTPの土台/05_リクエストとレスポンス

    ひとことで言うと

    リクエスト はクライアントからサーバーへの「お願い」で、リクエストライン（メソッド＋パス）・ヘッダー・ボディ でできています。レスポンス はサーバーからの「答え」で、ステータス行・ヘッダー・ボディ でできています。クライアントは まずステータスコードを見て 成功か失敗かを判断し、詳しい内容はボディから読み取ります。

    HTTP そのものの仕組み（往復・ステートレス・HTTPS）は前の HTTPの基本 で扱いました。

    2.リクエストとレスポンスの全体像

    HTTP のメッセージは、リクエストもレスポンスも 「1行目・ヘッダー・空行・ボディ」 という同じ形をしています。

    リクエストの主な要素

    • URL（エンドポイント＝API の呼び出し先）
    • HTTP メソッド（GET、POST、PUT、DELETE …）
    • ヘッダー（Content-Type、Authorization、Accept など）
    • ボディ（POST・PUT・PATCH 時のデータ本体。JSON やフォームなど）

    レスポンスの主な要素

    • ステータスコード（200、201、400、401、404、500 など）
    • ヘッダー（Content-Type、Set-Cookie …）
    • ボディ（JSON、HTML、バイナリデータなど）

    3.リクエストライン・メソッド・パス

    HTTP リクエストの 1 行目 が リクエストライン です。

    GET /v1/users/123 HTTP/1.1
│   │             │
│   │             └─ プロトコルバージョン
│   └─ パス（リソースの場所）
└─ HTTP メソッド（何をしたいか）
    要素例意味
    メソッドGET取得（HTTPメソッドと操作 で詳述）
    パス/v1/users/123ユーザー ID 123
    バージョンHTTP/1.1プロトコルのバージョン

    メソッドとパスの組み合わせが「どの操作を、どのリソースに対して行うか」を表します。

    4.ヘッダーの役割（Content-Type、Accept など）

    ヘッダー はリクエスト・レスポンスの メタ情報（本文そのものではなく、本文についての付帯情報）です。名前: 値 のペアで送ります。

    GET /v1/users HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
    ヘッダー方向役割
    Hostリクエスト接続先のサーバー
    Content-Type両方ボディの形式（例：application/json）
    Acceptリクエストクライアントが欲しい形式
    Authorizationリクエスト認証情報（認証）
    Locationレスポンス作成したリソースの URL（201 などで返す）
    Set-Cookieレスポンスブラウザに Cookie を保存させる（74章：Cookieの仕組み）

    JSON の API では、POST・PUT・PATCH のリクエストに Content-Type: application/json を付けるのが基本です。

    5.ボディと JSON の基本

    ボディ（Body） は、メッセージの 本文 です。GET には通常ボディがありません。

    POST /v1/users HTTP/1.1
Content-Type: application/json

{
  "name": "田中太郎",
  "email": "taro@example.com"
}
    形式用途API での位置づけ
    JSONデータのやり取りWeb API の主流
    フォームHTML フォーム従来型の Web
    バイナリファイルアップロード（検索と複合操作）

    JSON は人間にも読みやすく、多くの言語で扱えるため、この章でも JSON を前提にします。JSON の書き方や他の形式との比較は JSONとデータ形式 で扱います。

    6.レスポンスの読み方（ステータス・ヘッダー・ボディ）

    レスポンスも ステータス行 ＋ ヘッダー ＋ ボディ の構造です。

    HTTP/1.1 201 Created
Content-Type: application/json
Location: /v1/users/usr_01HXYZ

{
  "data": {
    "id": "usr_01HXYZ",
    "name": "田中太郎",
    "email": "taro@example.com"
  }
}
    部分読み方
    201 Created成功（作成完了）。コードの一覧は ステータスコード
    ヘッダーLocation で新しいリソースの URL を確認する
    ボディ作成されたリソースの内容

    ボディの形はシンプルにリソースをそのまま返すこともあります。

    {
  "id": 1,
  "name": "Taro",
  "email": "taro@example.com"
}

    上の例のように data で包むか、そのまま返すかは API ごとの方針です。どちらにするかは ボディの設計 で扱います。

    読む順番

    クライアントは まずステータスコード を見て、成功か失敗かを判断します。そのあとでヘッダーとボディを読みます。

    7.ステータスコードとエラーハンドリング

    よく使うステータスコードは次のとおりです。意味と選び方は ステータスコード で詳しく扱います。

    コード意味
    200 OK成功
    201 Created新規作成に成功
    204 No Content成功したが返すデータはない
    400 Bad Requestリクエストが不正
    401 Unauthorized認証エラー
    403 Forbidden権限がない
    404 Not Foundリソースがない
    422 Unprocessable Entityバリデーション（入力チェック）エラー
    500 Internal Server Errorサーバーエラー

    エラー時は、エラーの内容を JSON で返す のが一般的です（形の決め方は エラー設計）。

    実践のコツ

    • API を設計するときは「一貫したレスポンス形式」「適切なエラーコード」「詳細なエラーメッセージ」を意識する
    • curl だけでなく、fetch や axios などのクライアントライブラリでのリクエスト例も学んでおくとよい

    8.curl やブラウザ開発者ツールで API を観察する

    設計を学ぶうえで、実際の HTTP を見る 習慣が大切です。

    8.1 curl の例

    curl は、コマンドラインから HTTP リクエストを送れるツールです。

    # GET — 一覧取得
curl -i https://api.example.com/v1/users

# POST — 作成（JSON ボディ付き）
curl -i -X POST https://api.example.com/v1/users \
  -H "Content-Type: application/json" \
  -d '{"name":"田中太郎","email":"taro@example.com"}'
    • -i：レスポンスヘッダー も表示する
    • -X POST：メソッドを指定する
    • -H：ヘッダーを付ける
    • -d：ボディを付ける

    8.2 fetch の例

    ブラウザや Node.js の JavaScript からは fetch で同じリクエストを送れます（参考の最小例です）。

    const res = await fetch('https://api.example.com/v1/users', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: '田中太郎', email: 'taro@example.com' }),
});
console.log(res.status);          // まずステータスを見る
const body = await res.json();    // そのあとボディを読む

    8.3 ブラウザ開発者ツール

    1. F12 キーで開発者ツールを開き、Network（ネットワーク） タブを選ぶ
    2. ページを操作したり、API を呼び出したりする
    3. 一覧からリクエストを選び、Headers / Payload / Response を確認する

    生の HTTP を見る

    ドキュメントだけでなく、生の HTTP を見ると「設計のずれ」に気づきやすくなります。

    9.よくある誤解

    誤解1：「JSON を送るならボディに書くだけでよい」

    サーバーはボディの形式を Content-Type ヘッダーで判断します。POST・PUT・PATCH で JSON を送るときは Content-Type: application/json を付けるのが基本です。

    誤解2：「レスポンスはボディだけ見れば成功か失敗か分かる」

    まず見るべきは ステータスコード です。ボディは詳しい内容を伝える役割で、成功か失敗かの大分類はステータスコードが担います。

    誤解3：「GET でもボディにデータを入れて送ればよい」

    GET には通常ボディがありません。取得の条件は URL のパスやクエリパラメータで表します（ページネーション・フィルタ・ソート）。

    10.まとめ

    • リクエストは「リクエストライン・ヘッダー・ボディ」、レスポンスは「ステータス行・ヘッダー・ボディ」でできている
    • リクエストラインのメソッドとパスで「どの操作を、どのリソースに」を表す
    • ヘッダーはメタ情報。JSON を送るときは Content-Type: application/json
    • ボディは本文。Web API では JSON が主流で、GET には通常ボディがない
    • レスポンスはまずステータスコードを見る。エラーも JSON で返すのが一般的
    • 一貫したレスポンス形式・適切なエラーコード・詳細なエラーメッセージを意識する
    • curl・fetch・開発者ツールで生の HTTP を観察する習慣をつける
