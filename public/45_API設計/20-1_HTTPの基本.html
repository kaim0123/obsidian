    20 HTTPの土台

    HTTPの基本 — Web API が乗っている通信のルール

    Web API の土台になっている HTTP の仕組みを、リクエストとレスポンスの往復から理解します。URL の読み方、ステートレスという性質、HTTPS が必須な理由、アプリ同士が HTTP で連携するための「4つの約束事」、そして HTTP の上に乗る設計スタイルである REST との関係までを押さえます。

    もとにしたノート：20_HTTPの土台/01_HTTPの基本、20_HTTPの土台/04_HTTPとREST

    ひとことで言うと

    HTTP は「クライアントが リクエスト を1回送り、サーバーが レスポンス を1回返す」という単純な往復の通信ルールです。サーバーは前のやり取りを覚えない（ステートレス）ので、必要な情報は毎回送ります。API 設計とは、この HTTP のルールの上で どんな URL・メソッド・ステータスコード・データ形式を使うか を決めることです。

    リクエスト・レスポンスの中身（ヘッダー・ボディ）は次の リクエストとレスポンス で詳しく見ます。

    2.HTTP とは何か

    HTTP（HyperText Transfer Protocol） は、Web 上でデータをやり取りするための 通信ルール（プロトコル） です。ブラウザがページを表示するときも、スマホアプリが API を呼ぶときも、多くの場合 HTTP が使われています。

    用語意味
    プロトコル通信の約束事・手順
    クライアントリクエストを送る側（ブラウザ、スマホアプリ、他のサーバー）
    サーバーリクエストを受け取り、レスポンスを返す側

    API 設計では「HTTP のルールの上に、どんな URL・形式・エラーを使うか」を決めます。

    3.リクエストとレスポンスの流れ

    HTTP 通信は 1 回のリクエストに対して 1 回のレスポンス が返る、シンプルな往復です。

    1. クライアントがリクエストを組み立てる
    2. ネットワーク経由でサーバーへ送る
    3. サーバーが処理し、レスポンスを返す
    4. クライアントがステータス・ボディを解釈する
    段階クライアント側の例
    送信fetch('https://api.example.com/users')
    受信ステータス 200、JSON のユーザー一覧

    3.1 主なメソッド・ヘッダー・ステータスコード

    リクエストには「何をしたいか」を表す メソッド と、補足情報である ヘッダー が付き、レスポンスには結果を表す ステータスコード が付きます。よく出てくるものは次のとおりです。

    主なメソッド

    • GET（取得）
    • POST（作成）
    • PUT（更新・全置換）
    • PATCH（部分更新）
    • DELETE（削除）

    主なヘッダー

    • Content-Type（データ形式）
    • Authorization（認証情報）
    • Accept（受け入れ可能なデータ形式）

    主なステータスコード

    • 200・201（成功）
    • 400・401・404（クライアント側の問題）
    • 500（サーバー側の問題）

    メソッドの使い分けは HTTPメソッドと操作、ヘッダーとボディの中身は リクエストとレスポンス、コードの意味と選び方は ステータスコード で詳しく扱います。

    4.URL・パス・クエリパラメータの読み方

    API の「どこにアクセスするか」は URL で表します。

    https://api.example.com/v1/users?page=2&limit=20

https://api.example.com   … スキーム・ホスト
/v1                       … バージョン
/users                    … パス（リソース）
?page=2&limit=20          … クエリパラメータ
    部分役割例
    スキーム通信方式https://
    ホストサーバーの場所api.example.com
    パスリソースの位置/v1/users
    クエリフィルタ・ページなど?page=2&limit=20
    • パス — 「何のリソースか」を表します（設計方法は URLとリソースの設計）
    • クエリ — 一覧の絞り込み・並び替え・ページ送りなどに使います（ページネーション・フィルタ・ソート）

    5.ステートレスという性質

    HTTP は ステートレス（状態を持たない） プロトコルです。サーバーは、前のリクエストの内容を 自動では覚えません。

    リクエスト1: GET /users/1   → 200 OK
リクエスト2: GET /users/1   → サーバーは「さっきも同じ人？」とは知らない
    ステートレスの意味設計への影響
    各リクエストは独立認証情報は毎回ヘッダーなどで送る
    サーバーがセッションを持たないJWT などの自己完結型トークン（中身だけで誰のものか確かめられる証明書のようなもの）が使われやすい
    スケールしやすいどのサーバー（インスタンス）でも同じリクエストを処理できる

    「ログイン状態」などは、Cookie・トークン・セッション ID など 別の仕組み で表現します（認証）。HTTP とセッション管理の関係は 74章：HTTPとセッション管理、セッションとトークンの違いは 74章：セッション方式とトークン方式、JWT は 74章：JWTの構造と検証 で詳しく扱っています。

    6.HTTPS が必須である理由

    本番の API では HTTPS（HTTP + TLS 暗号化） が必須です。TLS は通信路を暗号化し、改ざんを検知するための仕組みです。

    方式内容API 設計での位置づけ
    HTTP平文通信開発環境のみ（本番では不可）
    HTTPS暗号化通信トークン・個人情報を送る本番 API

    HTTP

    途中で内容が読み取られる可能性があります（パスワード・トークンが漏洩）。

    HTTPS

    暗号化され、改ざん検知も可能です。

    • 認証トークン・API キーを 平文 HTTP で送らない
    • 本番 URL は https:// で始める
    • 認証・認可と合わせた話は 認証・APIセキュリティの全体像 で詳しく扱います

    7.HTTP でアプリ間連携するときの4つの約束事

    Web API は、HTTP 上の次の約束をそろえることで「別のアプリ同士でも同じ言葉で話せる」ようにします（ノートでは「増田本」の整理として紹介しています）。

    約束内容詳しく扱うページ
    要求の対象URL（パス・クエリ）で何を指すかリクエストとレスポンス・URLとリソースの設計
    要求の種類メソッド（GET／POST／…）で何をするかHTTPメソッドと操作
    結果の伝え方ステータスコードで成功・失敗の種類を伝えるステータスコード・エラー設計
    データの形ボディとメディアタイプ（多くは JSON）JSONとデータ形式・ボディの設計

    アプリ同士をつなぐ方式は API だけではありません（共有データベース・ファイル・API・メッセージの4つ）。同期 API とメッセージ・イベント駆動の違いは 41章：同期API・メッセージ・イベント駆動 を見てください。

    8.HTTP と REST

    HTTP は通信のルールそのもので、その上で「API をどう設計するか」の代表的なスタイルが REST（Representational State Transfer） です。REST は「リソース（資源）を URL で表し、HTTP メソッドで操作する」考え方です。詳しくは RESTの考え方 で扱うので、ここでは概要だけ押さえます。

    8.1 REST の設計原則

    原則意味
    リソース指向エンティティ（ユーザー・注文などの「もの」）を一意な URL で表現する
    ステートレス各リクエストは独立して完結する
    統一インターフェースHTTP の標準メソッド・ステータスコードを活用する
    階層構造URL のパスでリソースの階層を表現する

    8.2 RESTful な設計のメリットとデメリット

    メリット

    • シンプルで分かりやすい
    • キャッシュや認証、バージョン管理がしやすい
    • クライアントとサーバーの独立性が高い

    デメリット

    • 複雑な操作や多対多のリレーションの表現がやや苦手
    • REST の原則を過度に厳守するのは現実的でない場合もある

    8.3 REST 以外の API スタイルとの比較

    スタイル特徴
    RESTシンプルな CRUD（作成・読み取り・更新・削除）の API に最適
    GraphQLクライアントが必要なデータだけを柔軟に取得できる。型安全・スキーマ駆動
    gRPCバイナリ通信・高速・多言語対応。マイクロサービス間の通信で利用される

    REST はシンプルな CRUD API に向き、複雑な要件には GraphQL や gRPC も検討します。比較は REST以外のAPIスタイル で扱います。

    9.よくある誤解

    誤解1：「サーバーは前のリクエストを覚えているので、ログイン後は何も送らなくてよい」

    HTTP はステートレスなので、サーバーは前のリクエストを 自動では覚えません。ログイン状態は Cookie・トークン・セッション ID などを 毎回送る ことで表現します。

    誤解2：「社内向けや小さな API なら HTTP（平文）でもかまわない」

    平文の HTTP は途中で内容が読み取られる可能性があり、トークンや API キーが漏れます。HTTP で済ませてよいのは開発環境だけで、本番は必ず HTTPS にします。

    誤解3：「HTTP と REST は同じもの」

    HTTP は 通信のルール、REST はその上で API を設計するための スタイル（考え方） です。HTTP を使っていても REST らしくない API（GraphQL や RPC 風の API など）はいくらでもあります。

    10.まとめ

    • HTTP はクライアントとサーバーがリクエストとレスポンスでやり取りする通信ルール
    • 1 回のリクエストに 1 回のレスポンス。メソッド・ヘッダー・ステータスコードが基本の部品
    • URL はスキーム・ホスト・パス（リソース）・クエリ（絞り込みなど）に分けて読む
    • HTTP はステートレス。認証情報は毎回送り、そのぶんスケールしやすい
    • 本番 API は HTTPS 必須。トークンや API キーを平文で送らない
    • アプリ間連携では 対象・種類・結果・データの形 の4つの約束をそろえる
    • REST は HTTP の上に乗る代表的な設計スタイル。複雑な要件には GraphQL・gRPC も検討する
