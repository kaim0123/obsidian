    認証 — API で「あなたは誰か」を確かめる

    API が「このリクエストは誰から来たか」を確かめる認証の基本を学びます。API Key・Bearer Token（JWT）・Session Cookie・Basic 認証の使い分け、OAuth 2.0 / OpenID Connect の概要、認証情報を URL に載せない理由、401 Unauthorized の返し方、そして API セキュリティ全体の中での認証の位置づけを押さえます。

    もとにしたノート：60_セキュリティと信頼性/01_認証、04_認証とセキュリティ

    ひとことで言うと

    認証 は 本人確認（あなたは誰？）です。API では認証情報を Authorization ヘッダで送り、URL には載せません。認証に失敗したら 401、認証できたが権限がないなら 403（認可）です。認証は API セキュリティの一層にすぎず、HTTPS・認可・レート制限・入力検証などと重ねる 多層防御 で守ります。

    2.認証（Authentication）とは何か

    認証 は 本人確認 です。「このリクエストは誰から来たか」をサーバーが判断します。似た言葉の 認可 と区別しましょう。

    概念英語問い
    認証Authenticationあなたは誰？
    認可Authorization何ができる？

    認証が通っても、その操作をしてよいか（認可）は別にチェック します（認可）。両者の違いは 73章：認証と認可の違い でも詳しく扱っています。

    3.API でよく使う認証方式

    3.1 API Key・Bearer Token（JWT）・Session Cookie

    方式渡し方向いている用途
    API Keyヘッダ X-API-Key: ...サーバー間連携。管理が簡単
    Bearer Tokenヘッダ Authorization: Bearer <token>SPA・モバイル（JWT など）
    Session CookieCookie で自動送信同一ドメインの Web アプリ

    Bearer Token は「持っている人（bearer）を本人とみなす」トークンです。JWT（JSON Web Token） は、トークン自体にユーザー ID や有効期限が入った、署名付きの文字列です。署名で改ざんを見抜けるので、複数のサーバーに分かれた分散システムでも各サーバーが検証でき、認証・認可の両方に使われます。

    GET /v1/me HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

    3.2 方式ごとの注意点

    方式注意点
    API Key漏洩するとなりすまし可能 → ローテーション（定期的な差し替え）・権限最小化
    JWT有効期限・署名の検証が必須。ログアウトにはブラックリスト（無効化リスト）などが必要
    CookieCSRF 対策（SameSite 属性など）が必要

    JWT の中身と検証の手順は 74章：JWTの構造と検証、CSRF は 72章：CSRF で詳しく扱います。

    3.3 Basic 認証

    Basic 認証 は、ユーザー名とパスワードを Base64（文字列を別の文字で表す符号化。暗号ではない）にして毎回送る、最も単純な方式です。Base64 は誰でも元に戻せるので、HTTPS が必須 です。

    4.OAuth 2.0 / OpenID Connect の概要

    OAuth 2.0 は、ユーザーが パスワードをアプリに渡さずに、限定的なアクセス権を与える仕組みです。外部サービスとの連携や、ユーザーの代わりにアプリが API を呼ぶ場面に向いています。

    1. ユーザーは 認可サーバー（ログインとトークン発行を担当するサーバー）でログインする
    2. 認可サーバーがアプリに アクセストークン を発行する
    3. アプリはアクセストークンを付けて API サーバー を呼ぶ
    用語意味
    アクセストークンAPI を呼ぶための鍵
    リフレッシュトークンアクセストークンを更新する鍵
    OpenID ConnectOAuth ＋「ユーザー情報（ID）」の標準

    初心者は Bearer Token をヘッダで渡す 流れを押さえれば十分で、OAuth の詳細は必要になったときに深掘りすれば大丈夫です。詳しくは 73章：OAuth2.0の仕組み、73章：SAML・OAuth・OIDCの違い、トークンの使い分けは 74章：アクセストークンとリフレッシュトークン を参照してください。

    5.認証情報の渡し方（ヘッダに載せる・URL に載せない）

    API Key をクエリで送る実装も見かけますが、認証情報は URL に載せません。理由は次の 3 つです。

    • ブラウザの履歴に残る
    • サーバーのアクセスログに残る
    • Referer ヘッダ（どのページから来たかを伝えるヘッダ）で外部に漏れる
    ✕ 危険な例：URL に秘密を載せる 
    GET /v1/users?api_key=SECRET123
    ◯ 安全な例：ヘッダで送る 
    GET /v1/users
Authorization: Bearer SECRET123
    情報載せてよい場所
    API Key / TokenAuthorization ヘッダ
    セッション IDHttpOnly Cookie（Web のみ。JavaScript から読めない Cookie）
    公開してよいパラメータクエリ（page、limit など）

    6.401 Unauthorized の返し方

    認証に失敗したときは 401 を返します（403 ではありません）。WWW-Authenticate ヘッダで「どの方式で認証してほしいか」を伝えます。

    HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api"
Content-Type: application/json

{
  "error": {
    "code": "UNAUTHORIZED",
    "message": "認証トークンが無効または期限切れです"
  }
}
    状況ステータス
    トークンなし・無効・期限切れ401
    認証済みだが権限不足403（認可）

    クライアントは 401 を受け取ったら、再ログイン や トークン更新 の流れに入ります。エラー本文の形は エラー設計、ステータスコード全般は ステータスコード を参照してください。

    7.API セキュリティの全体の中での認証

    認証は API を守る対策の 一つの層 にすぎません。API のセキュリティでは、複数の対策を重ねる 多層防御 と、必要な権限だけを与える 最小権限の原則 が重要です（71章：深層防御、71章：最小権限とデータ最小化）。

    層主な対策詳しく
    認可（アクセス制御）RBAC（ロール＝役割ごとに権限を設定）、ABAC（ユーザーやリソースの属性で柔軟に制御）認可、73章：RBAC・ABAC・ACLの使い分け
    通信の安全性HTTPS で通信を暗号化（API は必ず HTTPS で公開）／CORS でブラウザからの利用を制御／セキュリティヘッダー（CSP、HSTS、X-Frame-Options、X-Content-Type-Options など）72章：CORSの仕組み、72章：セキュリティヘッダ
    レートリミット・監査一定時間内のリクエスト数を制限（DoS/DDoS 対策）、IP 制限や API キーごとのリミット、監査ログで不正アクセスや障害を調査レート制限と冪等性
    入力値バリデーションと脅威対策サニタイズ・エスケープで SQL インジェクション／XSS／コマンドインジェクションを防ぐ、CSRF 対策（トークン、SameSite Cookie）、バリデーションエラー時は適切なエラーコード・メッセージを返す72章：SQLインジェクション、72章：XSSの基本、72章：CSRF

    これらをまとめて眺めるページとして APIセキュリティの全体像、API 特有の脆弱性は 72章：WebAPIの脆弱性 も参照してください。

    8.よくある誤解

    誤解1：「認証が通れば、その API は何でも呼んでよい」

    認証は「誰か」を確かめるだけです。「その操作をしてよいか」は 認可 で別にチェックします。認証済みでも権限がなければ 403 です。

    誤解2：「HTTPS なら、API Key を URL のクエリに載せても安全」

    HTTPS は通信路を暗号化しますが、URL は ブラウザ履歴・サーバーのアクセスログ・Referer ヘッダ に残ります。認証情報は Authorization ヘッダで送ります。

    誤解3：「認証に失敗したら 403 を返す」

    トークンがない・無効・期限切れは 401 です。403 は「認証済みだが権限がない」ときに使います。混同するとクライアントが再ログインすべきか諦めるべきか判断できません。

    誤解4：「Basic 認証の Base64 は暗号化なので安全」

    Base64 は誰でも元に戻せる符号化で、暗号ではありません。Basic 認証は HTTPS が必須 です。

    9.まとめ

    • 認証は本人確認（あなたは誰？）、認可は権限チェック（何ができる？）
    • API Key はサーバー間、Bearer Token（JWT）は SPA・モバイル、Session Cookie は同一ドメインの Web アプリ向け。Basic 認証は HTTPS 必須
    • OAuth 2.0 はパスワードを渡さずに限定的な権限を与える仕組み。OIDC はそれに ID の標準を足したもの
    • 認証情報は Authorization ヘッダで送り、URL には載せない
    • 認証失敗は 401（WWW-Authenticate 付き）、権限不足は 403
    • 認証は多層防御の一層。認可・HTTPS・レート制限・入力検証と組み合わせ、最小権限を守る

    次は 認可 です。
