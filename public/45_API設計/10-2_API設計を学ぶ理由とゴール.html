    10 APIの基礎

    API設計を学ぶ理由とゴール — 「動く API」から「使われ続ける API」へ

    なぜ API に「設計」が必要なのかを、「動く API」と「使われ続ける API」の違い、設計がないと起きる問題から確かめます。そのうえで、良い API 設計が目指すゴール（迷わない・長く使える・安全な窓口）と 8 つの基本テーマの地図、この章の読み方を示します。

    もとにしたノート：10_APIの基礎/01_API設計を学ぶ理由、03_API設計のゴール

    ひとことで言うと

    リクエストを送れば何か返る「動く API」は作れても、クライアント開発者が迷わず・壊さず・長く使える「使われ続ける API」 にするには設計が必要です。目指すゴールは 「誰が使っても迷わない窓口」を、長く使える形で決めること。そのために使いやすさ・長寿命・安全の 3 つを押さえます。

    2.プログラム同士の「窓口」としての API

    API（Application Programming Interface） は、あるプログラムが別のプログラムの機能を使うための 約束された入口 です。

    レストランに例えると、厨房（サーバー）の中身は見えませんが、メニュー（API） を通じて注文できます。

    種類誰が使うか例
    ライブラリ API同じプログラム内list.sort()
    OS APIアプリケーションファイルの読み書き
    Web API別マシン上のプログラムGET /users

    この章では Web API（HTTP でデータをやり取りする API）を中心に扱います。API そのものの説明は APIとは を見てください。

    3.「動く API」と「使われ続ける API」の違い

    動く API は「リクエストを送れば何か返る」状態です。使われ続ける API は、クライアント開発者が迷わず・壊さず・長く使える 状態です。

    観点動く API使われ続ける API
    命名/getUser と /users/list が混在全体で同じルール
    エラー500 だけ返すステータス + 機械可読な code
    変更フィールド名を突然変更バージョンと後方互換を意識
    権限401 と 403 が曖昧認証・認可が明確

    動く API

    自分だけが使うなら、一時的には足りる。

    使われ続ける API

    チーム・外部・将来の自分 のために設計が必要。

    4.設計がないと起きること

    設計なしで API を増やすと、次の問題が積み上がります。

    • 命名のバラバラ — エンドポイント（API の呼び出し先 URL）ごとにルールが違う
    • 破壊的変更 — フィールド削除でクライアントが一斉に壊れる
    • クライアントの混乱 — ドキュメントを読んでも「この API だけ違う」がある

    5.API 設計のゴール

    5.1 「誰が使っても迷わない窓口」を目指す

    API 設計を一言で

    「誰が使っても迷わない窓口」を、長く使える形で決めること。

    良い API は、名前・形式・エラー・権限 が揃っていて、ドキュメントを読まなくても「だいたい当たりがつく」状態を目指します。

    5.2 使いやすさ・予測可能性・一貫性

    原則意味
    使いやすさクライアント開発者の手間が少ない
    予測可能性1 つ学べば他も同じルール
    一貫性命名・形式・エラーが全体で統一

    一貫性は 一貫性、予測可能性は API設計の原則 で詳しく扱います。

    5.3 長く使える形（バージョニング・後方互換性）

    API は公開すると クライアントが依存 し始めます。

    • バージョニング — /v1/ で変更の世代を分ける
    • 後方互換性（既存のクライアントが変更後も壊れずに動くこと）— 追加は OK、削除・改名は慎重に

    50 互換性と進化の バージョニング、後方互換性 で詳しく学びます。

    5.4 安全な窓口（認証・認可・HTTPS）

    要素役割
    HTTPS通信の暗号化
    認証あなたは誰か（失敗は 401）
    認可何ができるか（失敗は 403）

    60 セキュリティと信頼性の 認証、認可 で詳しく学びます。認証と認可の違いそのものは 73章：認証と認可の違い にもあります。

    8.よくある誤解

    誤解1：「リクエストに正しく応答できれば、良い API だ」

    それは「動く API」です。命名がバラバラだったり、エラーが 500 だけだったり、フィールド名を突然変えたりすると、クライアント開発者は迷い、壊れ、使い続けられません。迷わず・壊さず・長く使える ことまで含めて良い API です。

    誤解2：「自分しか使わないから設計は不要」

    今は自分だけでも、チームのメンバーや外部、そして 将来の自分 が使います。設計がないまま API を増やすと、共通処理が書けずレビュー基準もなく、レガシー API が増えて開発速度が落ちていきます。

    誤解3：「安全のことは、機能ができてから考えればよい」

    HTTPS・認証・認可は「安全な窓口」というゴールの柱の 1 つです。後から足すと全エンドポイントに影響するので、最初から設計に含めます。

    9.まとめ

    • API はプログラム同士の「窓口」（約束された入口）。この章は Web API を中心に扱う
    • 「動く API」と「使われ続ける API」は違う。後者には設計が必要
    • 設計がないと、命名のバラバラ・破壊的変更・クライアントの混乱が積み上がり、開発速度が落ちる
    • ゴールは「誰が使っても迷わない窓口」を長く使える形で決めること：使いやすさ・予測可能性・一貫性、長く使える形、安全な窓口
    • 8 つの基本テーマは、窓口の形・寿命・安全の 3 つに対応する

    次は 一貫性 です。
