    ステータスコード — 結果の種類を3桁の数字で伝える

    HTTP の ステータスコード の意味と、API 設計でどう選ぶかを学びます。2xx・4xx・5xx の大分類、よく使う 11 個のコード、原因ごとの選び方、ステータスコードとエラーボディの役割分担、そして新しいエンドポイントを作るときのチェックリストまでを押さえます。

    もとにしたノート：20_HTTPの土台/03_ステータスコード

    ひとことで言うと

    ステータスコードは「成功（2xx）か、クライアントの問題（4xx）か、サーバーの問題（5xx）か」を伝える3桁の数字です。失敗をすべて 400 や 500 で返さず、401・403・404・409・422 などを原因ごとに使い分ける と、クライアントがエラーの種類に応じて対処できます。詳しい理由はステータスではなく エラーボディ で伝えます。

    1.このページで扱うこと

    • 2xx・4xx・5xx の大分類：「誰の問題か」で分ける
    • よく使うコード一覧（200、201、204、400、401、403、404、409、422、429、500）
    • ステータスコードの選び方：原因の種類ごとに分ける
    • ステータスとエラーボディの役割分担
    • ステータスコードのチェックリスト

    レスポンスのどこにステータスコードが入るかは リクエストとレスポンス で見ました。すべてのコードの一覧は ステータスコード早見表とOpenAPI記述例 にあります。

    2.2xx・4xx・5xx の大分類

    ステータスコードは 3 桁の数字 で、先頭の 1 桁が結果の種類を表します。

    クラス範囲意味誰の問題？
    2xx200〜299成功—
    3xx300〜399リダイレクト（別の場所へ案内）など—
    4xx400〜499クライアントエラーリクエスト側
    5xx500〜599サーバーエラーサーバー側

    API 設計では 2xx / 4xx / 5xx を正しく使い分ける ことが、クライアントのエラー処理を楽にします。

    3.よく使うコード一覧

    コード名称典型的な用途
    200OKGET の成功、PATCH・PUT の成功（ボディあり）
    201CreatedPOST でリソースの作成に成功
    204No ContentDELETE の成功、更新の成功（ボディなし）
    400Bad Request形式が不正、必須項目が足りない
    401Unauthorized未認証（ログイン・トークンが必要）
    403Forbidden認証済みだが権限が足りない
    404Not Foundリソースが存在しない
    409Conflict重複、楽観ロック（同時更新の検出）の競合
    422Unprocessable Entity形式は正しいが業務ルールに違反
    429Too Many Requestsレート制限（一定時間内の回数上限）を超えた
    500Internal Server Errorサーバー内部のエラー

    401 と 403 の違いの背景にある「認証」と「認可」の違いは 73章：認証と認可の違い、429 を返すレート制限は レート制限と冪等性 で扱います。

    4.ステータスコードの選び方

    同じ「失敗」でも、原因の種類 に応じてコードを分けます。

    状況選ぶコード理由
    メールアドレスの形式が不正400リクエストの形式・入力の問題
    在庫不足で注文できない422JSON は正しいが業務ルールに違反
    他人の注文を参照しようとした403存在はするが権限がない
    存在しない注文 ID404リソースそのものがない
    同じメールアドレスで二重登録409競合・重複

    ✕ すべて 400 や 500 で返す

    クライアントが原因別に対処できません。

    ◯ 401 / 403 / 404 / 422 を使い分ける

    画面の表示・再試行・ログの設計がしやすくなります。

    5.ステータスとエラーボディの役割分担

    ステータスコードとボディは 役割が分担 されています。

    担当内容例
    ステータスコード大分類（成功 / クライアントエラー / サーバーエラー）422
    エラーボディ詳細（機械が読むための code、人が読むための message、項目ごとのエラー）エラー設計
     
    HTTP/1.1 422 Unprocessable Entity

{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "在庫が不足しています"
  }
}

    ステータスだけでは足りない情報をボディで補います。ステータスだけ返してボディが空 というのも、設計としては避けた方がよいことが多いです。

    6.ステータスコードのチェックリスト

    新しいエンドポイント（API の呼び出し口）を設計するときの確認項目です。

    • ☐ 成功時に 200 / 201 / 204 を適切に使い分けているか
    • ☐ 認証・認可で 401 と 403 を混同していないか
    • ☐ 存在しないリソースは 404 か（権限不足は 403）
    • ☐ バリデーション（入力チェック）と業務ルール違反で 400 と 422 を分けているか
    • ☐ サーバー障害は 500、一時的な過負荷は 503（Service Unavailable：一時的に利用できない）を検討したか
    • ☐ エラー時も 一貫した JSON 形式 のボディがあるか（エラー設計）

    7.よくある誤解

    誤解1：「401 と 403 はどちらも『入れない』なので同じ」

    401 は「あなたが誰か分からない（未認証）」、403 は「誰かは分かったが、その操作の権限がない」です。401 ならログインやトークンの再取得、403 なら権限の確認と、クライアントの対処が変わります。

    誤解2：「入力エラーは全部 400 でよい」

    形式や必須項目の不足は 400、形式は正しいが在庫不足などの業務ルールに反するものは 422、重複や同時更新の競合は 409 と分けると、クライアントが原因に応じた表示をしやすくなります。

    誤解3：「ステータスコードを正しく返せば、ボディは空でよい」

    ステータスコードは大分類しか伝えません。何が・なぜ 失敗したかは、code と message を持つエラーボディで伝えます。

    8.まとめ

    • 2xx は成功、4xx はクライアント側の問題、5xx はサーバー側の問題
    • 4xx は再送しても同じ失敗になりやすく、5xx は一時的なら再試行の余地がある
    • よく使うのは 200・201・204・400・401・403・404・409・422・429・500
    • 失敗は原因ごとにコードを分ける（形式 400、業務ルール 422、権限 403、不存在 404、競合 409）
    • ステータスは大分類、詳細はエラーボディで伝える
    • 新しいエンドポイントはチェックリストで確認する
