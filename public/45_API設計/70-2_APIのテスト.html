    70 ドキュメントとテスト

    APIのテスト — 契約テストで「窓口の形」を守る

    API 設計の品質をテストで守る方法を学びます。API が約束した形で応答するかを確かめる 契約テスト の考え方、正常系・異常系・境界値のテスト観点、モックサーバーを使った開発の進め方、破壊的変更を見つける回帰テスト、そして「テストを書きにくい API は設計に問題がある」という見方までを押さえます。

    もとにしたノート：70_ドキュメントとテスト/02_APIのテスト

    ひとことで言うと

    ユニットテストが「内部ロジック」を守るのに対し、契約テスト は API の 「窓口の形」 ──OpenAPI で約束したリクエストとレスポンスの形──を守ります。OpenAPI を 唯一の真実 にして、サーバーのテスト・クライアントのモック・CI での破壊的変更の検知をすべてそこから行うと、ズレが減ります。そして テストは設計の鏡 です。

    テストの前提になる契約（OpenAPI）の書き方は OpenAPIとドキュメント にあります。テスト全般の考え方は 42章：テストとリファクタリング も参考になります。

    2.契約テスト（Contract Test）の考え方

    契約テスト は、API が 約束した形 で応答するかを確かめるテストです。約束（契約）の中身は OpenAPI に書いてあります。

    ユニットテストが「内部ロジック」を守るのに対して、契約テストは 「窓口の形」 を守ります。

    3.正常系・異常系・境界値のテスト観点

    観点例
    正常系GET /v1/todos/1 → 200 + 期待どおりの JSON
    異常系無効なトークン → 401、他人の TODO → 403
    境界値limit=0、limit=最大値+1、空文字のタイトル → 422
    冪等性同じ Idempotency-Key で 2 回 POST → 1 件だけ作成される

    境界値 とは、許される範囲のぎりぎり（最小・最大とその 1 つ外側）の値のことです。冪等性の設計は レート制限と冪等性、401 と 403 の使い分けは 認証・認可 を見てください。

    3.1 API のテストピラミッド

      テストピラミッド（API）
       │
       ├─ 契約テスト（エンドポイント単位）
       ├─ 統合テスト（DB 含む）
       └─ E2E（少数）

    エンドポイント単位の契約テストを厚くし、データベースを含めた 統合テスト、システム全体を通す E2E テスト は数を絞ります。

    4.モックサーバーと開発フロー

    クライアント（フロントエンドなど）のチームが サーバーの完成前 に開発を進められるよう、モック（本物の代わりに決まった応答を返すサーバー）を用意します。

    ツール例用途
    PrismOpenAPI からモックサーバーを立てる
    WireMock固定レスポンス・遅延のシミュレート
     
      フロントエンド開発
       │
       └─→ モック API（OpenAPI 準拠）
              │
              後から本番 API に差し替え

    OpenAPI が 唯一の真実（全員が同じものを正とする原本）になると、モックと本番のズレが減ります。

    5.回帰テストと破壊的変更の検知

    既存のクライアントのために、レスポンスの形が変わっていないか を CI で確かめます。これが 回帰テスト（以前動いていたものが壊れていないかを確かめるテスト）です。

    検知したい変更手段
    フィールドの削除スキーマの diff / 契約テスト
    型の変更JSON Schema バリデーション
    ステータスコードの変更固定シナリオのスナップショット（前回の結果との比較）
     
      v1.2 リリース PR
       │
       └─ v1.1 時点の契約テストが全部 Green → 後方互換 OK の目安

    破壊的変更は 意図的に v2 として分け、v1 の契約テストは v1 のブランチで維持します。詳しくは バージョニング と 後方互換性 で扱います。

    6.テストから見えた設計の問題

    テストを書きにくい API は、設計に問題があるサインです。

    テストで苦労する点設計上の問題関連ページ
    同じ操作に URL が 3 通りある一貫性の不足一貫性
    エラーの形式がエンドポイントごとに違うエラー設計が統一されていないエラー設計
    状態が分からず 404/403 がランダムに返る認可ルールが不明確認可
    POST の結果が毎回別の ID になる冪等性が設計されていないレート制限と冪等性

    テストは設計の鏡

    テストを書きやすい API を目指すと、クライアントにとっても使いやすい API になります。

    7.よくある誤解

    誤解1：「ユニットテストが通っていれば API は大丈夫」

    ユニットテストが守るのは内部ロジックです。フィールド名が変わった、型が変わった、といった 窓口の形の変化 は、契約テストやスキーマの diff で見つけます。

    誤解2：「クライアントの開発はサーバーが完成してから」

    OpenAPI からモックサーバー（Prism など）を立てれば、サーバーの完成を待たずに並行して開発できます。OpenAPI を唯一の真実にしておけば、後で本番に差し替えてもズレにくくなります。

    誤解3：「テストが書きにくいのはテストの技術の問題」

    URL がばらばら、エラーの形がばらばら、認可が曖昧──テストのしにくさは、多くの場合 設計の問題 の表れです。テストで苦労した点は、設計を見直すきっかけにします。

    8.まとめ

    • 契約テストは OpenAPI で約束した「窓口の形」を、サーバー側・クライアント側の両方から確かめる
    • 正常系・異常系・境界値・冪等性の観点でテストする。契約テストを厚く、E2E は少数に
    • OpenAPI からモックを立て、クライアントはサーバー完成前に開発できる
    • 回帰テストで破壊的変更を検知し、破壊的変更は意図的に v2 として分ける
    • テストは設計の鏡。書きにくさは設計の問題のサイン
