    60 セキュリティと信頼性

    APIセキュリティの全体像 — API を守る 7 つの定番手法

    API はシステムへの「扉」です。無防備だと、攻撃者がユーザーデータやシステムを好き放題にできてしまいます。このページでは、本番の API でよく使われる 7 つの防御手法（レート制限・CORS・インジェクション対策・ファイアウォール・VPN・CSRF 対策・XSS 対策）を、それぞれ何を防ぐのかに注目して一望します。各攻撃の詳しい仕組みは 71〜72 章のページにつないでいます。

    もとにしたノート：60_セキュリティと信頼性/API Security Explained Rate Limiting, CORS, SQL Injection, CSRF, XSS & More（動画まとめ）

    ひとことで言うと

    API のセキュリティは 1 つの対策では守れません。量の攻撃には レート制限、ブラウザ経由の攻撃には CORS・CSRF トークン・XSS への備え、データベースには パラメータ化クエリ、入口では WAF、社内向け API は VPN で閉じる──ネットワーク境界・アプリケーション・データ層で 重ねて守る（多層防御） のが基本です。

    1.このページで扱うこと

    • API を守る 7 つの手法 と、それぞれが主に防ぐ脅威
    • レート制限 をかける単位（エンドポイント・ユーザー／IP・全体）
    • CORS・SQL／NoSQL インジェクション・WAF・VPN・CSRF・XSS の要点
    • それらを 多層防御 として組み合わせる考え方

    「誰が使っているか」「何をしてよいか」を確かめる 認証 と 認可 は別ページで扱います。このページの手法は、それらと 別のレイヤー で重ねる守りです。

    2.API はシステムへの扉 — 7 つの手法の地図

    API はアプリケーションの入り口です。保護が不十分だと、攻撃者がユーザーデータやシステム全体に自由にアクセスできてしまいます。次の 7 つは、本番の API でよく使われる定番の対策です。

    手法主に防ぐ脅威詳しく
    レート制限過負荷、ブルートフォース、DDoS 的な大量リクエスト3 章・レート制限と冪等性
    CORSブラウザ経由の、許可していないオリジンからのアクセス72章：CORSの仕組み
    パラメータ化クエリ／ORMSQL／NoSQL インジェクション72章：SQLインジェクション

    CSRF トークンなどログイン済みセッションの悪用72章：CSRF
    XSS 対策他のユーザーのブラウザでのスクリプト実行72章：XSSの基本

    3.レート制限（Rate Limiting）

    レート制限 は、一定時間あたりにクライアントが送れる リクエスト数を制限 する仕組みです。たとえば「ユーザー A は一定期間に 100 回まで」と決め、101 回目はブロックして、時間が経ってから再開させます。

    設定しないと、攻撃者に毎分数千のリクエストを送られてシステムを落とされたり、ブルートフォース（パスワードなどを総当たりで試す攻撃）されたりします。

    3.1 どの単位で制限するか

    次の粒度を組み合わせて使うことが多いです。

    粒度説明例
    エンドポイント単位特定のパスだけ厳しく制限する/comments（コメントの作成・取得）を毎分の厳しい上限に
    ユーザー／IP 単位同じ主体からの連続リクエストを抑えるIP「D」から 101 件目が来たら、使いすぎとしてブロック
    全体（グローバル）サーバーに流れ込むトラフィックの合計に上限DDoS 対策

    3.2 IP 単位だけでは足りない理由

    IP ごとに 100 件と決めておけば、攻撃者 1 人では大量に送れません。しかし攻撃者が ボットを多数立ち上げる と、各ボットがそれぞれ上限（100 件）まで使えるので、合計ではシステムが耐えられない負荷になります。

    そこで、もっと大きな数で 全体のレート制限 を設けます。流れ込むトラフィックの合計がその数に達したら、原因がわかるまで一時的にすべてのリクエストを止め、調査の時間を確保します。

    数値は例です

    100 や 1000 といった数はあくまで説明用です。本番ではトラフィックの規模に合わせて調整し、実際はもっと大きな値になります。制限を超えたときの返し方（429・Retry-After・X-RateLimit-*）は レート制限と冪等性 で扱います。

    4.CORS（Cross-Origin Resource Sharing）

    CORS は、ブラウザから どのオリジン（ドメイン）が API を呼び出せるかを制御する仕組みです。正しく設定しないと、悪意のあるサイトがユーザーのブラウザ経由で、ログイン済みセッションなどを悪用したリクエストを送らせる可能性があります。

    • フロントエンドが app.yourdomain.com だけを想定しているなら、そのオリジンからのリクエストだけを許可 する
    • another-domain.com など許可リストにないところからのリクエストはブロックし、認証やデータ取得に使わせない

    CORS はブラウザの中だけの話

    CORS はブラウザの 同一オリジンポリシー に関する仕組みです。サーバー同士の通信や curl などブラウザ以外のクライアントには効かないので、別に認証・認可の守りが必要です。

    仕組みの詳細は 72章：CORSの仕組み、設定の失敗例は 72章：WebAPIの脆弱性（CORS の検証不備）を見てください。

    5.SQL／NoSQL インジェクション

    ユーザーの入力が そのままデータベースのクエリに埋め込まれる と、攻撃者が入力欄に '; DROP TABLE ... のような文字列を送り、認証チェックをすり抜けたり、全ユーザーのデータを読み取り・改ざん・削除したりできてしまいます。

    • 対策は、パラメータ化クエリ（プリペアドステートメント。クエリの形と値を分けて渡す方法）を常に使うこと
    • ORM（データベースをオブジェクトとして扱うライブラリ）の安全な API を使い、文字列の連結でクエリを組み立てない
    • 入力の「エスケープ」だけに頼らず、クエリの構造とデータを分ける のが基本

    攻撃の仕組みと対策の詳細は 72章：SQLインジェクション にあります。

    6.ファイアウォール（WAF）

    ファイアウォール は、API と外部からのトラフィックの間に置き、悪意あるトラフィックを通常のものから ふるい分ける門番 です。Web アプリ向けのものを WAF（Web Application Firewall）と呼びます。

    たとえば AWS WAF は、

    • 疑わしい SQL キーワードを含むリクエスト
    • 不自然な HTTP メソッド

    といった既知の攻撃パターンをブロックし、それ以外は API まで通します。WAF はシグネチャ（攻撃の特徴の一覧）やルールによる守りなので、レート制限やアプリ側の入力検証と 併用 します。ファイアウォール・WAF の種類と比較は 71章：ネットワークと端末の防御 を見てください。

    7.VPN（Virtual Private Network）

    API の中には、特定のネットワークからだけ 使わせたいプライベートな API もあります。そのために VPN を使います。

    公開 API（パブリック向け）

    インターネット上の一般ユーザーから、誰でもリクエストできる。

    VPN 内の API

    会社の VPN など 同じネットワークにいる端末だけ が到達できる。Web 上の一般ユーザーからのリクエストはブロックされる。

    典型例は 社内の管理ダッシュボード です。その API は、会社の VPN に接続した従業員だけが使えるようにします。VPN はネットワーク境界での守りであり、認証・認可 とは 別のレイヤー として設計します（「VPN の内側なら安全」と考えない考え方は 71章：ゼロトラスト）。

    8.CSRF（Cross-Site Request Forgery）

    CSRF は、ログイン中のユーザーのブラウザをだまして、本人が意図しないリクエスト を API へ送らせる攻撃です。

    • 例：銀行サイトが セッション Cookie だけ で認証していると、別タブで開いた悪意あるサイトが、ユーザーの Cookie を使って隠れた「送金」リクエストを自動で送れてしまう
    • 対策：セッション Cookie に加えて CSRF トークン も要求する。サーバーは「Cookie が有効か」と「送られた CSRF トークンがサーバー側の値と一致するか」の 両方 を確かめ、一致しない（知らない送り元からの）リクエストは拒否する
    • SameSite Cookie、Origin／Referer ヘッダの確認なども併用されることが多い

    詳しくは 72章：CSRF、API 特有の攻撃経路は 72章：WebAPIの脆弱性、Cookie の属性は 74章：Cookieの仕組み にあります。

    9.XSS（Cross-Site Scripting）

    XSS は、攻撃者が Web ページに スクリプトを埋め込み、他のユーザーのブラウザで実行させる攻撃です。コメント機能での流れは次のとおりです。

    1. 普通のユーザーは「nice picture」のようなコメントを送り、API が DB に保存する。ここまでは問題ない
    2. 攻撃者がコメント欄に <script>...</script> を投稿する
    3. API が無害化（サニタイズ）せずに、そのまま DB に保存する
    4. 他のユーザーがコメント一覧を開くと、埋め込まれたスクリプトが HTML として返り、ブラウザが実行してしまう
    5. 他のユーザーの Cookie を盗む、さらに改ざんする、といった被害が起こりうる

    対策の方向性：

    • 出力する場所に応じた エスケープ／サニタイズ（表示時の出力エンコーディング）
    • Content-Security-Policy（CSP） でインラインスクリプトを制限する（72章：CSP）
    • Cookie に HttpOnly を付けて、JavaScript から読めないようにする

    「nice picture」のような正常なコメントは問題なく通し、スクリプトを含む危険な入力だけを無害化または拒否します。仕組みの詳細は 72章：XSSの基本 にあります。

    10.多層防御として組み合わせる

    • 量の攻撃 には、レート制限（エンドポイント／IP／全体の組み合わせ）
    • ブラウザ経由の攻撃 には、CORS・CSRF トークン・XSS への備え
    • データベース を守るパラメータ化クエリ、入口 で弾く WAF、内部 API を閉じる VPN

    単一の対策に頼らず、ネットワーク境界・アプリケーション・データ層で 重ねて守る のが実務的な API セキュリティの基本です。考え方の詳細は 71章：深層防御 にあります。

    11.よくある誤解

    誤解1：「CORS を設定すれば、許可していないクライアントは API を呼べない」

    CORS はブラウザが守るルールです。curl やサーバーからのリクエストには効きません。API 側では 認証・認可 で「誰が何をしてよいか」を必ず確かめます。

    誤解2：「IP ごとにレート制限すれば DDoS も防げる」

    攻撃者がボットを多数立ち上げると、1 台ずつは上限内でも合計で耐えられない量になります。全体のレート制限 も組み合わせ、超えたら一時的に止めて原因を調べます。

    誤解3：「WAF や VPN があればアプリ側の対策はいらない」

    WAF は既知のパターンしか止められず、VPN はネットワークの境界を守るだけです。アプリ側のパラメータ化クエリ・出力のエスケープ・認証認可と 重ねて 使います。

    12.まとめ

    • API はシステムへの扉。7 つの定番手法を組み合わせて守る
    • レート制限はエンドポイント・ユーザー／IP・全体の単位を組み合わせる
    • CORS はブラウザからの呼び出し元を制御する。ブラウザ外には効かない
    • インジェクションはパラメータ化クエリ／ORM で、クエリの構造とデータを分けて防ぐ
    • WAF は入口で既知の攻撃を弾き、VPN は社内向け API を閉じる
    • CSRF は Cookie に加えて CSRF トークンを照合、XSS はエスケープ・CSP・HttpOnly で備える
