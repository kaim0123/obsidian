    70 ドキュメントとテスト

    OpenAPIとドキュメント — 契約を書いて共有する

    API ドキュメントを「後から書くおまけ」ではなく 設計の一部 として扱い、OpenAPI で API の契約をチームやクライアントと共有する方法を学びます。OpenAPI の基本、スキーマ定義とレビューへの活用、サンプルの書き方、ドキュメントと実装のズレを防ぐ方法、主なドキュメント作成ツールまでを押さえます。

    もとにしたノート：70_ドキュメントとテスト/01_OpenAPIとドキュメント、05_APIドキュメントとテスト

    ひとことで言うと

    API の 契約（どんなリクエストに、どんなレスポンスを返すかという約束）は、コードだけでは伝わりません。OpenAPI は、その契約を YAML／JSON で書く標準フォーマットです。OpenAPI を レビューのたたき台・ドキュメント・テストやモックの元 にし、CI で実装とのズレを防ぐと、「良い API = 良いドキュメント」をセットで保てます。

    2.なぜドキュメントが設計の一部か

    API の 契約 はコードだけでは伝わりません。ドキュメントは設計の 公開面、つまり利用者から見える API の姿そのものです。

    ドキュメントなしドキュメントあり
    Slack で「この API どう使う？」と聞かれる自己完結で試せる
    実装と説明がズレるレビュー時に契約を議論できる
    新メンバーの onboarding（受け入れ・立ち上がり）が遅いクライアントが並行して開発できる

    ドキュメントは次のような役割を持ちます。

    • 利用者・開発者・運用者の 共通言語 になる
    • 仕様の誤解・バグ・運用トラブルを防ぐ
    • API ファースト開発（仕様 → 実装 → テストの順で進める開発）の基盤になる

    考え方

    良い API = 良いドキュメント とセットで考えます。API の品質は「ドキュメントとテストの充実度」で決まります。

    3.OpenAPI（Swagger）の基本

    OpenAPI は、API を YAML / JSON で記述する標準フォーマットです（以前は Swagger という名前でした）。

    openapi: 3.0.3
info:
  title: Todo API
  version: 1.0.0
paths:
  /v1/todos:
    get:
      summary: TODO 一覧
      responses:
        '200':
          description: 成功
    要素役割
    pathsエンドポイントの定義
    components/schemas共通の JSON スキーマ（データの形の定義）
    securitySchemes認証方式

    Swagger UI や Redoc などを使うと、OpenAPI から ブラウザで読めて、その場で試せる ドキュメントを自動生成できます。

    3.1 その他のドキュメント作成ツール

    ツール特徴
    OpenAPI（Swagger）YAML / JSON で API 仕様を記述。Swagger UI / Redoc で可視化する
    API BlueprintMarkdown に似た記法。Aglio などで HTML にする
    PostmanAPI の設計・テスト・ドキュメントが一体になったツール

    4.スキーマ定義とレビューへの活用

    共通のデータの形は components/schemas にまとめて定義します。

    components:
  schemas:
    Todo:
      type: object
      required: [id, title, completed]
      properties:
        id:
          type: integer
        title:
          type: string
        completed:
          type: boolean

    設計レビューでは、OpenAPI を 議論のたたき台 にします。

    フィールドの 必須 / 任意（required）を OpenAPI 上ではっきり書くと、後方互換の議論がしやすくなります（後方互換性）。

    5.サンプルリクエスト・レスポンスの書き方

    パラメータとレスポンスの example を書いておくと、読み手がすぐに形をつかめます。

    /v1/todos/{id}:
  get:
    parameters:
      - name: id
        in: path
        required: true
        schema:
          type: integer
    responses:
      '200':
        content:
          application/json:
            example:
              data:
                id: 1
                title: "牛乳を買う"
                completed: false
      '404':
        content:
          application/json:
            example:
              error:
                code: NOT_FOUND
                message: "指定された TODO が見つかりません"
    書くべき例理由
    成功 200 / 201正常な形を理解してもらう
    400 / 422バリデーションエラー
    401 / 403認証・認可
    404存在しないリソース

    成功例だけでなく エラー例も充実させる のがポイントです。エラーの形そのものの決め方は エラー設計 を見てください。

    6.ドキュメントと実装のズレを防ぐ

    手法説明
    OpenAPI First先に YAML を書き、実装はそれに従う
    Code First + 生成コードから OpenAPI を自動生成する
    CI で diff チェック実装を変えたときにドキュメントの更新を強制する

    たとえば、プルリクエスト（PR）をマージする条件に次を入れます。

      PR マージ条件
       │
       ├─ OpenAPI 更新あり
       ├─ 破壊的変更は CHANGELOG + バージョン議論
       └─ サンプルが実行可能（Swagger Try it out）

    破壊的変更とバージョンの扱いは バージョニング で扱います。

    6.1 ドキュメントを継続的に更新する

    • 実装や仕様を変えたときは、必ずドキュメントも更新 する
    • サンプルリクエスト／レスポンス、エラー例も充実させる
    • ドキュメントとテストを自動で連携させる（例：OpenAPI からテストコードを生成する）

    6.2 ドキュメントとテストはセット

    ドキュメントで約束したことは、テストで守ります。テストの自動化には次のような層があります。

    • ユニットテスト：個々の API 関数のテスト
    • 統合テスト：API エンドポイント全体のテスト
    • E2E テスト：システム全体の動作確認
    • モックサーバー で外部依存を取り除く
    • CI/CD パイプライン で自動的にテストを流す

    契約テストやモックの使い方は、次の APIのテスト で詳しく扱います。

    7.よくある誤解

    誤解1：「ドキュメントは実装が終わってから書けばよい」

    ドキュメントは設計の公開面です。実装前に OpenAPI 草案を書けば、レビューで契約を議論でき、クライアントも並行して開発できます。後から書くと、実装との ズレ も生まれやすくなります。

    誤解2：「成功時のレスポンス例だけ書けば十分」

    利用者が困るのは失敗したときです。400/422・401/403・404 などの エラー例 も書いておくと、正しく扱えるクライアントが作れます。

    誤解3：「一度きちんと書けば、ドキュメントはそのまま使える」

    実装は変わり続けます。CI での diff チェックや、PR マージ条件に「OpenAPI 更新あり」を入れるなど、ズレを仕組みで防ぐ 必要があります。

    8.まとめ

    • ドキュメントは設計の公開面。利用者・開発者・運用者の共通言語になる
    • OpenAPI は API を YAML / JSON で書く標準。paths・components/schemas・securitySchemes が中心
    • OpenAPI 草案を設計レビューのたたき台にし、必須 / 任意を明示する
    • 成功例だけでなくエラー例も書く
    • OpenAPI First／Code First + 生成／CI の diff チェックで、実装とのズレを防ぐ
    • ドキュメントとテストはセット。API の品質はその充実度で決まる
