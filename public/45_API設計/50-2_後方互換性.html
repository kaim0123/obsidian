    後方互換性 — 安全な変更と破壊的変更を見分ける

    API を変更しても古いクライアントが壊れない「安全な変更」と、バージョンアップが必要な「破壊的変更」を見分けられるようになりましょう。判断の流れと、内部 API・パートナー API・公開 API での方針の違いも整理します。

    もとにしたノート：50_互換性と進化/02_後方互換性

    ひとことで言うと

    後方互換性 とは、サーバーを更新しても 古いクライアントがそのまま動く ことです。任意フィールドや新エンドポイントの「追加」は安全、削除・リネーム・型変更・必須化・ステータスコード変更は破壊的 です。破壊的変更が必要なら、外部 API では v2 を新設し、v1 は Sunset まで守ります。

    1.このページで扱うこと

    • 後方互換性とは何か
    • 安全な変更（フィールド追加・新エンドポイント）
    • 破壊的変更（削除・リネーム・型変更・必須化）
    • 破壊的変更とバージョンアップの判断
    • 内部 API と外部 API での方針の違い

    バージョンの付け方・廃止の告知は前の バージョニング で扱いました。

    2.後方互換性とは何か

    後方互換性（Backward Compatibility） とは、サーバー側を更新しても、古いクライアントがそのまま動く 状態のことです。

    API の契約は 暗黙の約束 です。「この JSON には name がある」とクライアントは信頼して作られています。その約束を破らない変更かどうかが判断の軸になります。

    3.安全な変更（フィールド追加・新エンドポイント）

    一般に 安全 とされる変更です。共通点は「足すだけで、既存のものを変えない」ことです。

    変更なぜ安全か例
    任意フィールドの追加古いクライアントは無視できる"avatar_url" を追加
    新エンドポイント追加既存 URL に影響なしPOST /v1/users/{id}/avatar
    新クエリパラメータ指定しなければ従来どおり?sort=created_at
    レスポンスに null 許容フィールドパース（JSON を読み取ってデータに変換すること）は成功する"bio": null
     
    // v1.0 のレスポンス
{"id": 1, "name": "太郎"}

// v1.1 — フィールド追加（後方互換）
{"id": 1, "name": "太郎", "avatar_url": "https://..."}

    4.破壊的変更（削除・リネーム・型変更・必須化）

    次は 破壊的変更（古いクライアントを壊す変更）です。古いクライアントが壊れる可能性が高くなります。

    変更問題例
    フィールド削除参照すると undefined / 例外name を削除
    リネーム古い名前で読めないuser_id → id
    型変更パース失敗"price": "1000" → 1000
    任意 → 必須送信しないクライアントが 422更新時に email 必須化
    ステータスコード変更クライアントの分岐ロジックが狂う404 → 403
    ✕ 破壊的な例：フィールド名を変える 
    // 旧: {"user_id": 1}
// 新: {"id": 1}   ← 古いクライアントは user_id が取れない

    ステータスコードの意味は ステータスコード を参照してください。コードを変えるだけでも、クライアントの「404 なら○○する」という分岐が壊れます。

    5.破壊的変更とバージョンアップの判断

    変更を検討するときは、次の順に考えます。

    1. その変更は 後方互換か？ → Yes なら、同じ v1 のままリリースし、CHANGELOG に書く
    2. No（破壊的）で、内部 API・全クライアントを同時に更新できる なら → 破壊的変更も可（ただし告知は必要）
    3. No（破壊的）で、外部 API なら → v2 を新設し、v1 は Sunset まで維持する
    判断材料自分に問う質問
    利用者外部開発者がいるか
    更新速度クライアントを強制更新できるか
    影響範囲何件のフィールド・エンドポイントが変わるか
    代替手段v1 との並行期間中に v2 へ誘導できるか

    Sunset や CHANGELOG の書き方は バージョニング を参照してください。

    6.内部 API と外部 API での方針の違い

    種類後方互換の厳しさ典型的な方針
    内部 API中（同時デプロイなら緩め）破壊的変更 OK、Slack などで告知
    パートナー API（取引先など限られた相手に公開）高Deprecation 期間が必須
    公開 API最高v2 新設 ＋ 長期サポート

    内部 API でも、モバイルアプリ のように利用者が古いバージョンを長く使い続ける場合は、外部 API と同じ慎重さが必要です。

    覚え方

    外部に開くほど、「古い約束を守る期間」が長くなります。

    7.よくある誤解

    誤解1：「値の中身が同じなら、型を変えても問題ない」

    "1000"（文字列）を 1000（数値）に変えるだけでも、型を前提にしたクライアントではパースや計算が失敗します。型変更は破壊的変更 です。

    誤解2：「ステータスコードを正しいものに直すのは安全な修正」

    設計として正しくなる場合でも、404 → 403 のような変更はクライアントの分岐ロジックを狂わせます。ステータスコード変更も破壊的変更 として扱い、告知やバージョンで対応します。

    誤解3：「内部 API なら、いつでも自由に壊してよい」

    同時デプロイできるなら緩めでよいですが、それでも告知は必要です。モバイルアプリのように古い版が残る利用者がいるなら、外部 API と同じく慎重に扱います。

    8.まとめ

    • 後方互換性とは、サーバーを更新しても古いクライアントがそのまま動くこと。API の契約は暗黙の約束
    • 任意フィールド・新エンドポイント・新クエリパラメータ・null 許容フィールドの追加は安全
    • 削除・リネーム・型変更・任意→必須・ステータスコード変更は破壊的
    • 破壊的なら、内部で同時更新できれば告知のうえ変更、外部なら v2 を新設して v1 を Sunset まで維持
    • 内部・パートナー・公開の順に互換性の要求が厳しくなる。モバイルアプリがあれば内部でも慎重に
