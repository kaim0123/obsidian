    90 付録

    チェックリストとアンチパターン — API 設計を点検し、悪い形から抜け出す

    新しい API の設計、変更のレビュー、リリース前の確認に使える総合チェックリストと、よく見る悪い設計（アンチパターン）10個の一覧をまとめた付録です。チェックリストで「できているか」を確かめ、アンチパターン一覧で「悪い例」と「良い例」を見比べて直し方を確認します。

    もとにしたノート：90_付録/付録B_チェックリスト / 付録D_アンチパターン一覧

    ひとことで言うと

    チェックリストは 一貫性・URL・メソッドとステータス・ボディ・エラー・ページネーション・互換性・セキュリティ・運用・ドキュメント の10分類と、最後のクイック質問4つです。アンチパターンの多くは 「HTTP の決まりごと（メソッド・ステータス・ヘッダー）を使わずに自己流で済ませる」 か 「形がそろっていない」 のどちらかで、直し方も「HTTP の意味に沿わせる」「ルールを1つに決めてそろえる」が基本です。

    1.このページで扱うこと

    • API 設計チェックリスト（総合版）：11 分類の点検項目（最後はレビュー用のクイック質問）
    • API 設計アンチパターン一覧：よく見る悪い例 10 個と、改善の方向性

    アンチパターン とは、よく見かけるけれど避けるべき悪い設計の型のことです。チェックリストの各分類には、詳しく説明しているページへのリンクを付けました。レビューの進め方そのものは API設計レビューの実践 を、チームでの運用は チームでAPI設計を守る を見てください。

    2.API 設計チェックリスト（総合版）

    新規 API 設計・変更レビュー・リリース前に使えるチェックリストです。上から順に確認し、☐ に当てはまらない項目があれば、リンク先のページで考え方を確認します。

    2.1 全体・一貫性

    → 一貫性、API設計の原則

    • ☐ 命名規則（複数形・ケース・プレフィックス）が プロジェクト全体で統一 されている
    • ☐ 同じ概念に 同じ用語 を使っている（user / member の混在がない）
    • ☐ 日時・金額・ID の 形式が統一 されている（ISO 8601、通貨コードなど）
    • ☐ 成功・エラー・ページネーションの レスポンス構造が揃っている
    • ☐ 内部 API と外部 API で ルールの差 が意図的である

    ケース：snake_case（単語を _ でつなぐ）や camelCase（2語目以降の先頭を大文字にする）などの書き方。ISO 8601：2026-10-18T09:00:00Z のような日時の国際標準の書き方。

    2.2 URL・リソース設計

    → URLとリソースの設計、RESTの考え方

    • ☐ URL に 動詞を載せていない（/getUser ではなく /users/{id}）
    • ☐ リソース名は 名詞・複数形（/users、/orders）
    • ☐ ネストは 浅く、深い階層は別リソースかクエリで表現
    • ☐ ID は パス に、フィルタ・ソートは クエリ に置いている
    • ☐ 同じリソースへの 別名 URL が乱立していない

    2.3 HTTP メソッド・ステータス

    → HTTPメソッドと操作の表現、ステータスコード、ステータスコード早見表

    • ☐ GET は 副作用なし（データを変えない）、POST/PUT/PATCH/DELETE の意味が REST 的に妥当
    • ☐ 201 + Location ヘッダーで 作成したリソース の場所を示している（該当時）
    • ☐ 204 は ボディなし の成功（削除・更新など）に使っている
    • ☐ 400 / 401 / 403 / 404 / 409 / 422 / 429 / 500 を 意味に沿って 使い分けている
    • ☐ 500 以外の 4xx で クライアントが対処可能 な情報を返している

    2.4 リクエスト・レスポンスボディ

    → ボディの設計、JSONとデータ形式

    • ☐ フィールド名は snake_case または camelCase で統一
    • ☐ 不要な内部フィールド（パスワードハッシュなど）を 返していない
    • ☐ 作成・更新で 必要最小限 の入力だけ受け付けている
    • ☐ null と「フィールド省略」の 意味の差 がドキュメント化されている
    • ☐ リスト API は ラッパー（items、data、meta のような包み）の形が統一されている

    2.5 エラー設計

    → エラー設計

    • ☐ エラーボディに 機械可読な code（プログラムで判定できる識別子）がある
    • ☐ 人間向け message と 開発者向け detail を分けている
    • ☐ バリデーションエラーは フィールド単位 で返せる（422 など）
    • ☐ スタックトレース（エラー発生時の内部の呼び出し履歴）などの 内部情報を漏らしていない
    • ☐ エラー形式が 全エンドポイントで同じ

    2.6 ページネーション・検索

    → ページネーション・フィルタ・ソート、検索と複合操作

    • ☐ 一覧 API に ページネーション がある（大量データを想定する場合）
    • ☐ page/limit または cursor 方式が 一貫 している
    • ☐ ソート・フィルタの パラメータ名 が他の API と揃っている
    • ☐ デフォルトの limit と、指定できる limit に 上限 がある
    • ☐ 空の結果は 200 + 空配列（404 ではない）

    2.7 バージョニング・互換性

    → バージョニング、後方互換性、APIの進化と運用

    • ☐ 破壊的変更の 方針 が決まっている（新バージョン / deprecation）
    • ☐ フィールドの 追加 は後方互換として許容されている
    • ☐ 削除・改名・型変更には 移行期間 またはバージョン分離がある
    • ☐ 非推奨 API に Sunset / Deprecation ヘッダー またはドキュメントの記載がある
    • ☐ クライアントへの影響を リリースノート で共有している

    2.8 認証・認可・セキュリティ

    → 認証、認可、レート制限と冪等性、APIセキュリティの全体像、CORSの仕組み（72章）

    • ☐ HTTPS のみ で提供している
    • ☐ 401（未認証）と 403（権限不足）を 区別 している
    • ☐ トークン・API Key を URL クエリに載せていない
    • ☐ レート制限があり、429 と Retry-After を返せる
    • ☐ 入力値の バリデーション・サニタイズ（危険な文字の無害化）がある
    • ☐ CORS 設定で、必要最小限 のオリジンだけを許可している

    2.9 信頼性・運用

    → レート制限と冪等性、APIの進化と運用、APIのテスト

    • ☐ 重要な POST に 冪等性キー または設計上の冪等性がある
    • ☐ タイムアウト・リトライの方針が ドキュメント化 されている
    • ☐ ヘルスチェック（/health など、サービスが動いているかを確かめる入口）がある（該当するサービス）
    • ☐ リクエスト ID（X-Request-Id）で トレース（1つのリクエストの処理を追跡）できる
    • ☐ 変更前に 契約テスト / OpenAPI 検証 がある

    2.10 ドキュメント

    → OpenAPIとドキュメント、OpenAPI記述例

    • ☐ OpenAPI（または同等のもの）で 全公開エンドポイント が記述されている
    • ☐ 認証方法・curl の例・エラーコード一覧がある
    • ☐ サンプルリクエスト／レスポンスが 実際と一致 している
    • ☐ 変更履歴（Changelog）が 更新 されている

    2.11 レビュー用クイック質問

    細かい項目を見る前に、次の4つの質問で全体の感触を確かめます。

    質問OK?

    3.API 設計アンチパターン一覧

    よく見る悪い例と、改善の方向性です。どれもチェックリストのどこかの項目に対応しています。

    3.1 URL に動詞を載せる

    ✕ 悪い例 
    POST /getUserById
POST /createOrder
GET  /deleteTodo?id=5
    ◯ 良い例 
    GET    /users/{id}
POST   /orders
DELETE /todos/{id}

    URL は「もの（名詞）」、操作は HTTP メソッドで表します（URLとリソースの設計）。

    3.2 すべて 200 OK + success フラグ

    ✕ 悪い例 
    HTTP/1.1 200 OK
{ "success": false, "error": "Not found" }
    ◯ 良い例 
    HTTP/1.1 404 Not Found
{ "code": "USER_NOT_FOUND", "message": "User not found" }

    結果は HTTP ステータスで伝えます。200 で失敗を返すと、監視ツールや中継サーバーが成功と誤解します（ステータスコード、エラー設計）。

    3.3 エンドポイントごとに JSON 形式がバラバラ

    ✕ 悪い例 
    GET /users/1     → { "user": { ... } }
GET /orders/1    → { "data": { ... } }
GET /products/1  → { ... }   // ラッパーなし
    ◯ 良い例 
    GET /users/1  → { "id": "...", "name": "..." }
GET /orders/1 → { "id": "...", "total": 1000 }
// 単一リソースは同じ「フラット or ラッパー」規則で統一

    どちらの形を選ぶかより、全エンドポイントで同じ規則にそろえる ことが大切です（一貫性、ボディの設計）。

    3.4 401 と 403 の混同

    ✕ 悪い例

    • トークン期限切れ → 403
    • ログインしていない → 403

    ◯ 良い例

    • 認証情報なし・無効 → 401 + WWW-Authenticate ヘッダーなど
    • 認証済みだが操作不可 → 403

    401 は「あなたが誰か分からない（ログインし直して）」、403 は「誰かは分かったが、その操作は許されていない」です（認証、認可、認証と認可の違い（73章））。

    3.5 破壊的変更を黙ってリリース

    ✕ 悪い例

    • email フィールドを突然 mail_address に改名
    • 必須フィールドを追加し、古いクライアントが 400 を連発

    ◯ 良い例

    • 新フィールドを追加（旧フィールドも当面維持）
    • /v2/ を導入 + deprecation の告知 + 移行期限

    詳しくは 後方互換性、バージョニング を見てください。

    3.6 ページネーションなしの巨大一覧

    ✕ 悪い例 
    GET /users   → 10 万件を一度に返す
    ◯ 良い例 
    GET /users?page=2&limit=20
GET /users?cursor=eyJpZCI6MTIzfQ&limit=20

    上は page（ページ番号）方式、下は cursor（「ここまで読んだ」という目印）方式です（ページネーション・フィルタ・ソート）。

    3.7 内部実装の漏洩

    ✕ 悪い例 
    {
  "error": "SQLException: duplicate key users_pkey",
  "stack_trace": "..."
}
    ◯ 良い例 
    {
  "code": "EMAIL_ALREADY_EXISTS",
  "message": "This email is already registered"
}

    DB のテーブル名やスタックトレースは、攻撃者に内部構造のヒントを与えます。クライアントには対処に必要な情報だけを返します（エラー設計、WebAPIの脆弱性（72章））。

    3.8 GET に副作用

    ✕ 悪い例 
    GET /orders/5/cancel
GET /sendVerificationEmail?user=1
    ◯ 良い例 
    POST /orders/5/cancel
POST /users/1/verification-emails

    GET はキャッシュやリンクの先読みで勝手に呼ばれることがあるため、データを変える操作に使ってはいけません（HTTPメソッドと操作の表現、検索と複合操作）。

    3.9 トークンを URL クエリに載せる

    ✕ 悪い例 
    GET /users/me?access_token=SECRET
    ◯ 良い例 
    GET /users/me
Authorization: Bearer SECRET

    URL はアクセスログや閲覧履歴に残るため、秘密の値は Authorization ヘッダーで送ります（認証）。

    3.10 ドキュメントと実装の不一致

    症状OpenAPI では name が必須なのに、実装は title を期待している
    対策OpenAPI を 単一の真実（正しい仕様はここだけ、という基準）にし、CI（自動テストの仕組み）で契約テストを回す（APIのテスト、OpenAPIとドキュメント）

    4.よくある誤解

    誤解1：「チェックリストの全項目を満たさないとリリースできない」

    「該当時」「該当サービス」と書かれた項目のように、API の種類によっては当てはまらない項目もあります。チェックリストは、抜け漏れに気づくための道具です。レビューでは争点になりそうな項目に絞って話し合い、満たさない項目は「意図的にそうしている」と説明できれば十分です。

    誤解2：「エラーでも 200 を返してボディで判定すれば、クライアントの実装が楽になる」

    一見楽ですが、HTTP クライアントや監視ツール、キャッシュは HTTP ステータスで成否を判断します。200 で失敗を返すと、エラー率が監視に出ず、リトライも働きません。結果は HTTP ステータスで伝え、詳細を共通のエラーボディで返します。

    誤解3：「新しいフィールドを足すのも破壊的変更だから、毎回バージョンを上げる」

    レスポンスへのフィールド 追加 は、後方互換な変更として許容するのが一般的です（クライアントは知らないフィールドを無視する前提）。削除・改名・型変更、必須の入力フィールドの追加が破壊的変更にあたります。

    5.まとめ

    • チェックリストは 一貫性・URL・メソッドとステータス・ボディ・エラー・ページネーション・互換性・セキュリティ・運用・ドキュメント の10分類 + クイック質問4つ
    • アンチパターン：URL に動詞、200 + success フラグ、JSON 形式がバラバラ、401/403 の混同、黙った破壊的変更、ページネーションなし、内部実装の漏洩、GET に副作用、トークンを URL に、ドキュメントと実装の不一致
    • 直し方の基本は「HTTP の意味（メソッド・ステータス・ヘッダー）に沿わせる」「ルールを1つに決めてそろえる」「OpenAPI を単一の真実にして自動で検証する」
