    30 リソース設計

    APIとドメイン設計 — ドメインモデルとリソースを結びつける

    良い API のリソースは、ビジネスで実際に使われている言葉から生まれます。ドメインの名詞をリソースにすること、ユビキタス言語でエンドポイント名をそろえること、集約の境界を API でも守ること、内部モデルをそのまま外に出さないこと — DDD（ドメイン駆動設計）の考え方と API 設計のつなぎ方を解説します。

    もとにしたノート：30_リソース設計/05_APIとドメイン設計

    ひとことで言うと

    API のリソースは ドメインの言葉 で名付け、集約ルート経由 で操作させ、レスポンスは DB の形ではなく API 用に整えた形（DTO） で返します。内部の都合と外部との約束（API 契約）を切り離すのが目的です。

    1.このページで扱うこと

    ドメインモデル（業務の概念をコードで表したもの）と API のリソース設計をどう結びつけるかを学びます。

    • ドメインの名詞がリソースになる
    • ユビキタス言語とエンドポイント名
    • 集約と API 境界の関係
    • 内部モデルをそのまま晒さない（DTO）
    • DDD との接続
    • 変換の不一致と、導出結果か生データか

    DDD そのものは 42章：DDDとは で解説しています。

    2.ドメインの名詞がリソースになる

    ビジネスで使う 名詞 が、そのまま API のリソース候補になります（URL への落とし方は URLとリソースの設計）。

    ドメイン（EC）リソース候補
    商品/products
    カート/carts
    注文/orders
    在庫内部のみ（公開しないこともある）

    ドメインエキスパート（その業務に詳しい人）の会話が、そのまま API になるのが理想です。

    ドメインエキスパートの会話
「注文に商品を追加する」
     │
     ▼
POST /v1/orders/{id}/items

    3.ユビキタス言語とエンドポイント名

    ユビキタス言語 とは、開発者も業務担当者も チーム全体で同じ用語を使う という DDD の考え方です（42章：戦略的設計とユビキタス言語）。

    ドメイン用語API で避けたい命名
    注文（Order）/purchases、/buy_requests が混在
    会員（Member）/users と /members の二重表現

    1枚の用語集で、日本語・URL・ID の形式をまとめておくと迷いません。

    用語集（1 枚）
     │
     ├─ 日本語: 注文
     ├─ 英語 URL: orders
     └─ ID 形式: ord_{uuid}

    エンドポイント名は コード・UI・ドキュメント で同じ単語を使います。

    4.集約と API 境界の関係

    集約（Aggregate） は、一緒に整合性を保つオブジェクトのまとまりです。外から触ってよい入口を 集約ルート と呼びます（42章：集約とリポジトリ）。

    Order 集約
├── Order（ルート）
└── OrderItem × n
    設計例
    集約ルート経由POST /orders/{id}/items（Order 経由で Item を追加）
    Item 単独公開PATCH /order-items/{id} → 整合性が崩れやすい

    原則

    集約の外から子エンティティを直接 PATCH しない。ルートを通すことで、合計金額などのルールをルートがまとめて守れます。

    5.内部モデルをそのまま晒さない

    DB のテーブルや ORM（DB の行をオブジェクトとして扱う仕組み）のエンティティを、そのまま JSON にして返さない ようにします。

    内部モデルAPI レスポンス
    password_hash含めない
    内部ステータス status=7"status": "shipped" など意味のある文字列
    3 テーブルを JOIN した結果クライアントに必要な形に整形
    ✕ 内部丸出し 
    {"id": 1, "password_hash": "...", "internal_flag": true}
    ◯ API 用 DTO 
    {"id": 1, "email": "taro@example.com", "display_name": "太郎"}

    DTO（Data Transfer Object） は、データを受け渡すためだけのオブジェクトです。DTO の層を挟むと、内部の変更と API 契約を分離 できます。DB の列名を変えても、API の形は変えずに済みます。不要な項目を返すことのセキュリティ上の危険は 72章：WebAPIの脆弱性 も参照してください。

    6.DDD との接続

    DDD の概念API 設計での対応
    エンティティリソース（/orders/{id}）
    値オブジェクトJSON のネストしたフィールド
    リポジトリ一覧・検索 API
    ドメインサービスRPC 風エンドポイント、またはサブリソース

    エンティティと値オブジェクトは 42章：エンティティと値オブジェクト で説明しています。設計の段階は次のようにつながります。

    モジュール設計（境界）
     ↓
API 設計（公開するリソース）
     ↓
クラス設計（DTO・ハンドラ）

    43章：モジュール設計 で決めた境界のうち、外部に見せる部分 がこのページの対象です。境界の考え方は 42章：境界づけられたコンテキスト も参考になります。

    7.変換の不一致と、導出結果か生データか（増田本）

    増田亨『現場で役立つシステム設計の原則』（増田本）では、次の点を指摘しています。JSON / DTO とドメインオブジェクトは 目的が違う ため、機械的に 1:1 で対応させると不一致が起きます（必須の値オブジェクト、区分、集約の深さなど）。明示的な変換 で吸収し、ドメインを API の形に合わせて歪めないようにします。

    レスポンスに何を入れるかは、用途で選びます。

    返すもの例向く場合
    導出結果税込価格・可否・表示名クライアントに同じルールを重複実装させたくない
    生データ単価・区分コードクライアントでの再計算や多様な用途を許したい

    詳細とコードのイメージは 42章のノート「ドメインオブジェクトとWeb API」にあります。API を発展させる進め方は 発展性のあるAPI開発 を見てください。

    8.よくある誤解

    誤解1：「DB のテーブルをそのまま API にすれば早くて確実」

    テーブル名や内部ステータスの数字、password_hash のような項目まで外に出てしまいます。しかも DB を変えるたびに API が壊れます。DTO で API 用の形に整え、内部と契約を切り離します。

    誤解2：「子リソースも全部、単独のエンドポイントで更新できたほうが便利」

    PATCH /order-items/{id} で明細を直接変えると、注文の合計などのルールを誰も守れなくなります。集約ルート経由（POST /orders/{id}/items）にすると、整合性を Order がまとめて守れます。

    誤解3：「同じものを指すなら名前は何でもよい」

    /users と /members、/orders と /purchases が混在すると、別物なのか同じなのか分からなくなります。ユビキタス言語 に合わせ、コード・UI・ドキュメントで同じ単語を使います。

    9.まとめ

    • ドメインの名詞がリソースになる（公開しないものもある）
    • ユビキタス言語でエンドポイント名をそろえ、用語集で日本語・URL・ID 形式を決める
    • 集約の子は集約ルート経由で操作させる
    • 内部モデルをそのまま晒さず、DTO で API 契約と分離する
    • エンティティ→リソース、値オブジェクト→ネストしたフィールド、リポジトリ→一覧・検索 API
    • DTO とドメインの不一致は明示的な変換で吸収し、導出結果か生データかを用途で選ぶ

    次は、失敗を予測可能な形で返す エラー設計 です。
