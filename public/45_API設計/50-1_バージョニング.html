    50 互換性と進化

    バージョニング — 古い約束を守りながら新しい約束を始める

    API を長く使い続けるために、変更の「世代」をどう分けるかを学びます。なぜバージョンが必要か、URL パス・ヘッダ・クエリの 3 方式、チームでの選び方、非推奨（Deprecation）と廃止（Sunset）の告知、CHANGELOG の書き方までを押さえます。

    もとにしたノート：50_互換性と進化/01_バージョニング

    ひとことで言うと

    バージョニングは 「古い約束を守りながら、新しい約束を始める」 ための仕組みです。公開 API は /v1/ から始め、破壊的変更は新しいメジャーバージョン（v2）で行い、古い版は Deprecation → Sunset と段階を踏んで告知してから止めます。ただしバージョンは破壊的変更の受け皿であって、雑に壊してよい言い訳ではありません。

    1.このページで扱うこと

    • なぜバージョニングが必要か
    • URL パス方式（/v1/）・ヘッダ方式・クエリ方式
    • 初心者・チーム向けの選び方（チームで合意するルール例つき）
    • 非推奨（Deprecation）と廃止（Sunset）の告知
    • CHANGELOG の書き方
    • 増田本でのバージョンの位置づけ

    「どの変更なら古いクライアントを壊さないか」は次の 後方互換性 で扱います。

    2.なぜバージョニングが必要か

    API を公開すると、クライアント（API を呼ぶ側のアプリ）は 特定の形 に依存し始めます。フィールド名や URL を突然変えると、更新していないアプリが一斉に壊れます。

    状況バージョンなしバージョンあり
    フィールド追加古いクライアントは無視できるv1 はそのまま、v2 で新形式
    URL 変更全クライアントが 404v1 は旧 URL、v2 は新 URL
    破壊的変更緊急対応・問い合わせ増移行期間を設けられる

    3.URL パス方式・ヘッダ方式・クエリ方式

    バージョンをサーバーに伝える代表的な方式は 3 つです。

    方式例メリットデメリット
    URL パスGET /v1/users一目で分かる、キャッシュしやすいURL が長くなる
    ヘッダAccept: application/vnd.myapi.v1+jsonURL を汚さない試しに叩きにくい
    クエリGET /users?version=1実装が簡単キャッシュ・ログが乱れやすい

    初心者・小規模チーム では URL パス方式 が最も分かりやすく、curl（コマンドラインから HTTP リクエストを送る道具）やブラウザでもそのまま試せます。

    GET /v1/users/42 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbG...

    4.初心者・チーム向けの選び方

    条件おすすめ
    外部公開 APIURL パス /v1/ ＋ 明確な CHANGELOG
    内部 API のみ同時デプロイならバージョン省略も可
    モバイルアプリが多い古い v1 を長期サポートする前提で設計

    4.1 チームで合意するルール例

    1. 公開 API は必ず /v1/ から始める
    2. 破壊的変更は 新メジャーバージョン（v2）で行う
    3. v1 の廃止日は 最低 6 ヶ月前 に告知する

    内部 API なら省略してもよい？

    内部 API だけなら「全クライアントを同時に更新できる」ため、厳密なバージョンは不要なこともあります。ただし 将来外部公開する可能性 があるなら、最初から /v1/ を付けておくと楽です。

    5.非推奨（Deprecation）と廃止（Sunset）の告知

    いきなり API を消すのではなく、段階的に移行 してもらいます。

    段階意味クライアントへの伝え方
    Deprecation非推奨（使わないでほしい）レスポンスヘッダ Deprecation: true
    Sunset廃止予定日ヘッダ Sunset: Sat, 01 Jan 2027 00:00:00 GMT

    次の例では、まだ普通に 200 で応答しながら、ヘッダで「非推奨であること」「廃止予定日」「後継の URL（Link ヘッダの rel="successor-version"）」を伝えています。

    HTTP/1.1 200 OK
Deprecation: true
Sunset: Sat, 01 Jan 2027 00:00:00 GMT
Link: </v2/users>; rel="successor-version"
Content-Type: application/json

{"data": {"id": 42, "name": "太郎"}}

    ヘッダだけでは気づかれないこともあります。ドキュメント・メール・ダッシュボードなど 複数のチャネル で告知すると、移行漏れが減ります。廃止までの運用の流れは APIの進化と運用 で扱います。

    6.CHANGELOG の書き方

    CHANGELOG は API の変更履歴です。クライアント開発者が最初に読む資料になります。

    ## v1.3.0 (2026-06-01)
### Added（後方互換）
- `GET /v1/users` に `?role=` フィルタを追加
- レスポンスに `created_at` フィールドを追加（任意）

### Deprecated
- `GET /v1/users/list` → `GET /v1/users` へ移行してください

## v2.0.0 (2026-12-01) ※破壊的変更
### Changed
- 日時形式を ISO 8601 UTC に統一
- `user_id` を `id` にリネーム
    ラベル後方互換例
    Added○新フィールド、新エンドポイント
    Deprecated△旧エンドポイントの非推奨化
    Removed / Changed×フィールド削除、型変更

    ラベルを見るだけで「自分のアプリに対応が要るか」が分かるようにしておくのがコツです。

    7.増田本での位置づけ

    増田亨『現場で役立つシステム設計の原則』では、バージョンは 破壊的変更の受け皿 であり、雑な破壊の免罪符ではありません。まず後方互換で伸ばし、どうしても必要なときだけ世代を分ける、という進め方です。詳しくは 発展性のあるAPI開発 と 後方互換性 を参照してください。

    8.よくある誤解

    誤解1：「バージョンを上げれば、何を変えてもよい」

    v2 を出しても、v1 を使うクライアントは残ります。両方を保守する手間も増えます。まずは 後方互換な変更（フィールド追加など）で伸ばし、どうしても壊す必要があるときだけ世代を分けます。

    誤解2：「Deprecation ヘッダを付けたら、すぐ止めてよい」

    Deprecation は「使わないでほしい」という合図で、まだ動いている状態です。Sunset で廃止日を示し、ドキュメントやメールでも告知し、十分な移行期間（ルール例では最低 6 ヶ月）を取ってから止めます。

    誤解3：「内部 API だからバージョンは一切考えなくてよい」

    全クライアントを同時に更新できるなら省略も可能です。しかしモバイルアプリのように古い版が残る場合や、将来外部公開する可能性がある場合は、最初から /v1/ を付けておく方が後で楽です。

    9.まとめ

    • 公開した API の形にはクライアントが依存するので、変更の世代を分ける仕組みが要る
    • 方式は URL パス・ヘッダ・クエリの 3 つ。初心者・小規模チームには URL パス（/v1/）が分かりやすい
    • 外部公開・モバイルが多いほど、古い版を長く守る前提で設計する
    • 廃止は Deprecation → Sunset の順に、ヘッダと複数チャネルで告知する
    • CHANGELOG は Added / Deprecated / Removed・Changed で、互換性への影響が分かるように書く
    • バージョンは破壊的変更の受け皿。まず互換で伸ばす
