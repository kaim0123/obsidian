    30 リソース設計

    リクエスト・レスポンスボディの設計 — JSON の形・命名・型をそろえる

    API でやり取りするデータの本体（ボディ）は、ほとんどの場合 JSON です。成功レスポンスを data / meta で包むかどうか、フィールド名を snake_case と camelCase のどちらにするか、日時・ID・金額をどんな型で表すか、作成・更新のリクエストに何を入れるか — クライアントが扱いやすい形を API 全体でそろえる方法を解説します。

    もとにしたノート：30_リソース設計/04_リクエスト・レスポンスボディの設計

    ひとことで言うと

    JSON の ラップ形式・命名規則・型の表し方 は、どれを選ぶかより API 全体で1つに固定すること が大切です。日時は ISO 8601 の UTC、ID は文字列、金額は整数（最小単位）が基本です。

    1.このページで扱うこと

    ボディ とは、リクエストやレスポンスで送られるデータの本体です（リクエスト・レスポンス全体の構造は リクエストとレスポンス）。このページでは JSON ボディの 命名・型・ラップ形式 をそろえ、クライアントが扱いやすい形にする方法を扱います。

    • JSON を基本とする理由
    • 成功レスポンスのラップ形式（data / meta）
    • フィールド命名（snake_case と camelCase の統一）
    • 日時・ID・金額などの型と形式
    • 作成・更新リクエストの設計（必須・任意・部分更新）

    2.JSON を基本とする理由

    Web API では JSON（JavaScript Object Notation） が事実上の標準です。

    理由説明
    可読性人間にも読みやすい
    言語非依存Python、Java、Go、JavaScript など広くサポートされている
    ツールOpenAPI、Postman、各種 SDK と相性が良い
    軽量XML よりコンパクト

    JSON でやり取りすることは、ヘッダで伝えます。Content-Type は「送るデータの形式」、Accept は「受け取りたい形式」です。

    Content-Type: application/json
Accept: application/json

    ファイルアップロードなどの特殊なケース以外は、JSON を前提に設計します（ファイルの扱いは 検索と複合操作）。JSON の書き方自体は JSONとデータ形式 を見てください。

    3.成功レスポンスのラップ形式（data / meta）

    一覧 API などでは、本体を data、付加情報を meta で包む（ラップする）と一貫性が保てます。

    {
  "data": [
    { "id": "usr_01", "name": "田中" },
    { "id": "usr_02", "name": "佐藤" }
  ],
  "meta": {
    "page": 1,
    "limit": 20,
    "total": 150
  }
}
    形式用途
    { "data": ... }単一・一覧どちらも同じ構造にできる
    metaページネーション、集計情報
    配列直返しシンプルだが、メタ情報を付けにくい

    チームで ラップするかどうか を決め、全体で統一します（一貫性）。meta に入れるページ情報は ページネーション・フィルタ・ソート で詳しく扱います。

    4.フィールド命名（snake_case と camelCase の統一）

    snake_case は単語を _ でつなぐ書き方、camelCase は2語目以降の頭を大文字にする書き方です。

    規則例向いている場面
    snake_casecreated_at, user_idPython / Ruby の API、DB のカラム名に近い
    camelCasecreatedAt, userIdJavaScript / TypeScript のフロント向け
    snake_case の例 
    {
  "user_id": "usr_01",
  "created_at": "2026-06-19T10:00:00Z"
}

    決め方

    どちらでもよいが、API 全体で1つに固定する ことが重要です。DB は snake_case、JSON は camelCase のように、間に 変換レイヤー（名前を変換する処理の層）を挟むチームもあります。

    5.日時・ID・金額などの型と形式

    種類推奨形式避けたい例
    日時ISO 8601 の UTC 2026-06-19T10:00:00Z"2026/06/19"、Unix 秒との混在
    ID文字列（UUID や usr_01HXYZ）数値と文字列の混在
    金額整数（最小単位）または decimal 文字列浮動小数点 19.99（誤差が出る）
    真偽値true / false1/0、"yes"/"no"
    列挙文字列定数 "pending", "shipped"マジックナンバー（意味が分からない数字）

    用語の補足です。ISO 8601 は日時の国際標準の書き方で、末尾の Z は UTC（協定世界時）を表します。最小単位の整数 とは、円なら1円、ドルなら1セント単位の整数で表すことです。浮動小数点（小数を近似で持つ数の型）は 0.1 + 0.2 がぴったり 0.3 にならないような誤差が出るので、お金には使いません。

    {
  "id": "ord_01HXYZ",
  "total_amount": 3000,
  "currency": "JPY",
  "ordered_at": "2026-06-19T10:00:00Z",
  "status": "pending"
}

    6.作成・更新リクエストの設計（必須・任意・部分更新）

    6.1 作成（POST）

    {
  "name": "田中太郎",
  "email": "taro@example.com",
  "nickname": "taro"
}
    • どのフィールドが 必須 でどれが 任意 かを、ドキュメントで明示する
    • id や created_at のような サーバーが作る項目はリクエストに含めない

    6.2 部分更新（PATCH）と全体置換（PUT）

    {
  "name": "田中花子"
}
    • PATCH は送ったフィールド だけ を更新する
    • PUT は 全体置換。送らなかったフィールドを null 扱いにするかなど、仕様を明確にする
    メソッド意味送る内容
    PUT全体置換リソースの全フィールド
    PATCH部分更新変更したいフィールドのみ

    メソッドそのものの役割は HTTPメソッドと操作の表現 で説明しています。

    7.よくある誤解

    誤解1：「snake_case と camelCase、どちらかが正解」

    どちらでも構いません。問題になるのは、エンドポイントによって user_id と userId が混在することです。API 全体で1つに固定 し、必要なら変換レイヤーで DB 側の命名と切り離します。

    誤解2：「金額は小数で表せばそのまま使える」

    浮動小数点の 19.99 は計算のたびに誤差が出ます。金額は 最小単位の整数（1999 セントなど）か decimal 文字列 で表し、currency で通貨も添えます。

    誤解3：「作成リクエストに id や created_at を入れてもらえば楽」

    ID や作成日時はサーバーが責任を持って決める項目です。クライアントに送らせると、重複や改ざんの原因になります。サーバー生成項目はリクエストに含めない のが基本です。

    8.まとめ

    • JSON は可読性・言語非依存・ツール・軽量さから事実上の標準
    • data / meta でラップするかをチームで決め、全体で統一する
    • フィールド命名は snake_case か camelCase のどちらかに固定する
    • 日時は ISO 8601 UTC、ID は文字列、金額は整数か decimal 文字列、真偽値は true/false、列挙は文字列定数
    • 作成では必須・任意を明示しサーバー生成項目は含めない。PATCH は部分、PUT は全体
