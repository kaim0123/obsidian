    30 リソース設計

    URLとリソースの設計 — ドメインの名詞から読みやすい URL を作る

    REST API の URL は「何を扱うか」を表す住所です。ビジネスで使う名詞からリソースを洗い出し、コレクションと単一リソース、親子関係のネスト、命名規則をそろえると、初めて見る人でも迷わない API になります。よくある間違いと直し方もあわせて見ていきます。

    もとにしたノート：30_リソース設計/02_URLとリソースの設計

    ひとことで言うと

    URL には 名詞（リソース） だけを書き、コレクションは複数形、親子関係は 浅いネスト で表します。「何をするか（動詞）」は URL ではなく HTTP メソッドが担います。

    1.このページで扱うこと

    このページは、ドメインの 名詞 からリソースを洗い出し、読みやすい URL を設計するためのページです。

    • リソースの洗い出し：ドメインの名詞から始める
    • コレクションと単一リソース：/users と /users/{id}
    • ネストしたリソース：/orders/{id}/items
    • 命名規則：複数形・小文字・ハイフン・浅い階層
    • よくある URL 設計の間違い

    リソース（API が扱う「もの」。ユーザー、注文など）という考え方そのものは RESTの考え方 で説明しています。

    2.リソースの洗い出し（ドメインの名詞から）

    URL 設計の第一歩は、ビジネス上の「もの」 を名詞として書き出すことです。EC サイトを例にすると、次のようになります。

    名詞（リソース）URL の候補
    ユーザー/users
    商品/products
    カート/carts
    注文/orders
    注文明細/orders/{id}/items

    手順は次の3段階です。

    DDD（ドメイン駆動設計）の ユビキタス言語（チーム全員が同じ意味で使う共通の用語）とそろえると、チーム内の会話と API が一致しやすくなります。詳しくは 42章：戦略的設計とユビキタス言語 と APIとドメイン設計 を見てください。

    3.コレクションと単一リソース（/users と /users/{id}）

    リソースの URL は大きく2種類です。コレクション（同じ種類のリソースの集まり）と、その中の 単一リソース（1件）です。

    種類URL 例典型メソッド
    コレクションGET /usersGET（一覧）、POST（作成）
    単一リソースGET /users/{id}GET（詳細）、PATCH、DELETE
     
    /users           … ユーザー全体（コレクション）
/users/usr_123   … ID が usr_123 の 1 人（単一）
    • コレクションは 複数形 にします（/user ではなく /users）
    • {id} には UUID や、プレフィックス付き ID（usr_01HXYZ のように種類を表す接頭辞が付いた ID）を使います

    4.ネストしたリソース（/orders/{id}/items）

    親子関係 があるリソースは、パスを入れ子（ネスト）にして表します。

    /orders/{order_id}/items           … 注文に属する明細一覧
/orders/{order_id}/items/{item_id} … 特定の明細
/users/{user_id}/orders            … ユーザーの注文一覧
    ネストの目安例
    強い所属関係注文 → 明細
    スコープが明確ユーザー → その人の注文
    浅く保つ3 階層以上は避ける傾向
    ✕ 深すぎる例 
    /api/v1/company/dept/team/user/order/item
    ◯ 2 階層で十分なことが多い 
    /orders/{id}/items

    5.命名規則（複数形・小文字・ハイフン・浅い階層）

    原則良い例悪い例
    名詞を使う/products/getProducts
    複数形でコレクション/orders/order
    小文字/order-items/OrderItems
    ハイフンで単語区切り/order-items/order_items（URL ではどちらも可。統一 が重要）
    階層は浅く/users/{id}/orders5 階層以上の深いネスト
    動詞は URL に入れないDELETE /users/{id}POST /deleteUser

    バージョンは先頭に /v1/ を付けることが多いです（バージョニング）。こうしたルールを API 全体でそろえる意味は 一貫性 で扱っています。

    6.よくある URL 設計の間違い

    間違い問題改善
    GET /getUser?id=1動詞 URL、ID がクエリGET /users/1
    POST /users/create「作成」が冗長（POST がすでに作成を表す）POST /users
    /user（単数）と /orders（複数）が混在一貫性がないすべて複数形
    すべてを 1 つの URL にREST 的でないリソースごとに分ける
    内部の DB テーブル名をそのまま露出ドメインの言葉とずれるドメインの言葉を使う

    より詳しいアンチパターンは チェックリストとアンチパターン を参照してください。

    7.よくある誤解

    誤解1：「URL に動詞を入れたほうが何をするか分かりやすい」

    /getUser や /deleteUser のように動詞を入れると、操作が増えるたびに URL が増え、命名もばらつきます。REST では URL は名詞、操作は HTTP メソッド と役割を分けるので、GET /users/1・DELETE /users/1 のように同じ URL でメソッドだけを変えます。

    誤解2：「親子関係はすべて URL のネストで表すべき」

    ネストは 強い所属関係 や スコープが明確 なときに使い、深さは2階層程度にとどめます。会社・部署・チーム…と全部つなげると URL が長くなり、使う側が親の ID をすべて知っていないと呼べなくなります。

    誤解3：「ハイフンとアンダースコア、どちらかが絶対に正しい」

    URL ではどちらも使えます。大事なのは API 全体で1つに統一すること です。一般にはハイフン区切りの小文字がよく使われます。

    8.まとめ

    • リソースはドメインの名詞から洗い出す
    • コレクションは複数形（/users）、単一リソースは /users/{id}
    • 親子関係はネストで表すが、2 階層程度に浅く保つ
    • 名詞・複数形・小文字・ハイフン・浅い階層、そして動詞を入れない
    • 動詞 URL、単数と複数の混在、DB テーブル名の露出は典型的な間違い

    次は、URL に対して何をするかを表す HTTPメソッドと操作の表現 です。
