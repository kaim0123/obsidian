    コンテキスト間の関係（抜粋）

    コンテキストマップで描く代表的な関係です。上流はモデルを提供する側、下流はそれを使う側を指します。詳しくは境界づけられたコンテキストを参照してください。

    関係意味
    共有カーネルモデルの一部を共有
    顧客/供給者下流が上流に依存
    腐敗防止層（ACL）外部モデルを変換して取り込む
    別々の道連携しない

    3.参考図解

    この教材で使う概念の参考図解です。ドキュメントや打ち合わせの資料に、考え方ごと写して使えます。

    3.1 設計の階層

    建物にたとえると、アーキテクチャは建物全体、モジュール設計は部屋の役割分担、クラス設計は家具の配置です。この教材（ソフトウェア設計）は、その間で「どんな思想で作るか」を扱います（→ 設計の階層と基本用語）。

    3.2 関心の分離（レイヤー）

    画面・ユースケース・業務ルール・技術的な詳細を層に分けます。依存は上から下（内側）へ向けます（→ 関心の分離、層化・三層・レイヤード（41章））。

    「上 → 下」と「内側へ」の関係

    この図は伝統的なレイヤードの並びです。クリーンアーキテクチャでは、インフラ層もドメイン層に依存させ（依存性逆転）、ドメインを「いちばん内側」にします。図7（依存の方向）と見比べてください。

    3.3 三大パラダイムの組み合わせ

    1つのシステムの中でも、場所によって使う考え方は違います。外側から内側へ、イベント駆動 → DDD → OOP と FP → 手続き と組み合わせます（→ パラダイムの選び方と比較）。

    3.4 境界づけられたコンテキスト

    注文と在庫は、それぞれ自分の用語と集約を持つ別のコンテキストです。互いの内部には踏み込まず、イベント（OrderPlaced）で連携します（→ 境界づけられたコンテキスト）。

    3.5 イベント駆動の連携

    注文サービス（Publisher：イベントを発行する側）は OrderPlaced を発行するだけで、誰が受け取るかを知りません。受け取る側（Subscriber）は自分の都合で処理します（→ イベント駆動設計、同期API・メッセージ・イベント駆動（41章））。

    3.6 集約の構造

    集約（一緒に整合性を保つオブジェクトのまとまり）の中身は、必ず集約ルートを通して操作します。外部から OrderLine を直接書き換えることはしません（→ 集約とリポジトリ）。

    3.7 依存の方向（クリーンアーキテクチャ）

    UI・DB・外部 API といった技術的な詳細は外側に置き、依存はすべて中心のドメインへ向けます。ドメインは外の何にも依存しません（→ 依存性のルールとクリーンアーキテクチャ（41章）、依存性逆転の原則（41章））。

    4.よくある誤解

    誤解1：「早見表の部品（エンティティ・リポジトリ…）を全部使えば DDD になる」

    戦術的設計の部品だけを真似しても、ユビキタス言語や境界づけられたコンテキストといった戦略的設計がなければ「DDD っぽいだけ」になります（→ チェックリストとアンチパターン）。早見表が戦略的設計から始まっているのはそのためです。

    誤解2：「図2（レイヤー）と図7（依存の方向）は同じことを言っている」

    似ていますが、インフラ層の位置が違います。図2 ではインフラ層がいちばん下で、ドメイン層はインフラ層に依存します。図7 ではインフラが外側に回り、ドメインが何にも依存しない中心になります。この違いを生むのが依存性逆転です。

    5.まとめ

    • 戦略的設計：ユビキタス言語・境界づけられたコンテキスト・コンテキストマップ。避けるべきは大泥団、背景には Conway の法則
    • コンテキスト間の関係：共有カーネル・顧客/供給者・腐敗防止層（ACL）・別々の道
    • 戦術的設計：エンティティ・値オブジェクト・集約・リポジトリ・ドメインサービス・アプリケーションサービス・ドメインイベント
    • 層との対応：ドメイン層に業務の部品、アプリケーション層にユースケース、インフラ層にリポジトリ実装と外部 API アダプタ
    • 参考図解 7 枚：設計の階層／レイヤー／パラダイムの組み合わせ／境界づけられたコンテキスト／イベント駆動の連携／集約の構造／依存の方向
