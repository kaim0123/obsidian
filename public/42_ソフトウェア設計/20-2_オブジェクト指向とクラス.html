    オブジェクト指向とクラス — 状態と振る舞いをひとまとめにする

    オブジェクト指向（OOP）は、データ（状態）と処理（振る舞い）をひとまとめにした「オブジェクト」を中心に設計する考え方です。クラスとオブジェクトの関係、カプセル化・継承・多態の設計的な意味、メッセージによる協調、クラスの構成要素、そして向く場面と限界までを解説します。

    もとにしたノート：01_オブジェクト指向設計 / 02_クラスとオブジェクト

    1.このページで扱うこと

    オブジェクト指向（OOP：Object-Oriented Programming）の設計的な意味を学びます。クラス・カプセル化・継承・多態が、なぜ設計に役立つかを押さえます。

    • カプセル化・継承・多態の設計的意味

    継承は継承と合成、多態は多態とインターフェース、設計原則との関係はSOLIDとオブジェクト指向で詳しく扱います。

    2.オブジェクト指向とは何か

    定義

    オブジェクト指向とは、データ（状態）と振る舞い（処理）をひとまとめにしたオブジェクトを中心に設計する考え方です。

    手続き指向の課題 — データと処理の分離による変更の困難 — に対する応答として発展しました。

      手続き指向: データ ←→ 処理（別々）
  OOP:        [オブジェクト] = 状態 + 振る舞い（一体）

    3.クラスとオブジェクト — 状態と振る舞いの一体化

    3.1 設計図と実物

    OOP の基本の道具がクラスとオブジェクトです。この2つの関係をたとえで言うと、

    • クラス = 設計図
    • オブジェクト = その設計図から作った実物

    クッキーの型（クラス）から、同じ形のクッキー（オブジェクト）を何個も作れる、というイメージです。

    概念役割
    クラスオブジェクトの設計図（型）
    オブジェクトクラスから作った実体（インスタンス）

    3.2 オブジェクトとは

    オブジェクトは「状態（データ）」と「振る舞い（処理）」をひとまとめにしたものです。現実世界で考えると分かりやすいです。

    犬というオブジェクト

    • 状態：名前・年齢・色
    • 振る舞い：吠える・走る・食べる

    3.3 クラスとは

    クラスはオブジェクトの設計図です。どんな状態を持つか、どんな振る舞いができるかを定義します。

    class Dog {
  // 状態（フィールド / プロパティ）
  constructor(name, age) {
    this.name = name;
    this.age = age;
  }

  // 振る舞い（メソッド）
  bark() {
    console.log(`${this.name}: わん！`);
  }

  run() {
    console.log(`${this.name}が走っている`);
  }
}

// クラスからオブジェクトを作る（インスタンス化）
const pochi = new Dog('ポチ', 3);
const hachi = new Dog('ハチ', 5);

pochi.bark(); // ポチ: わん！
hachi.bark(); // ハチ: わん！

    pochi と hachi は別々のオブジェクトですが、同じ Dog クラスから作られているため同じ振る舞いができます。

    設計の題材でいえば、注文も同じように書けます。

    class Order {
  constructor(items) {
    this.items = items;  // 状態
  }
  total() {              // 振る舞い
    return this.items.reduce((sum, i) => sum + i.price, 0);
  }
}

    「注文」という現実の概念を、コード上の1つのまとまりとして表現できます。

    4.カプセル化 — 外から勝手にいじらせない

    オブジェクト指向には、一般に「3大要素」と呼ばれるものがあります。

    1. カプセル化（Encapsulation）
    2. 継承（Inheritance） → 継承と合成
    3. 多態性（Polymorphism） → 多態とインターフェース

    ここでは1つ目のカプセル化を中心に解説します（設計の基礎としての考え方はカプセル化と情報隠蔽も参照）。

    4.1 意味となぜ必要か

    カプセル化とは、データと、それを扱う処理をひとまとめにして、外から勝手にいじらせないようにすることです。薬のカプセルのように、中身が見えないけれど、必要な機能は使えるようにするイメージです。

    カプセル化がないと、外部から直接データを書き換えられてしまい、不整合（ルールに合わないおかしな状態）が起きます。

    4.2 コードで比べる

    ✕ 悪い例：カプセル化なし 
    class BankAccount {
  constructor() {
    this.balance = 0; // 誰でも自由に変えられてしまう
  }
}

const acc = new BankAccount();
acc.balance = -99999; // 残高がマイナス！ルールを破られた
    ◯ 良い例：カプセル化あり 
    class BankAccount {
  #balance = 0; // #は「プライベート」を示す（外から見えない）

  deposit(amount) {
    if (amount <= 0) throw new Error('入金額は正の数');
    this.#balance += amount;
  }

  withdraw(amount) {
    if (amount > this.#balance) throw new Error('残高不足');
    this.#balance -= amount;
  }

  getBalance() {
    return this.#balance;
  }
}

const acc = new BankAccount();
acc.deposit(1000);
// acc.#balance = -99999; // ← エラー。直接触れない

    ポイント

    • データは隠す（#balance は外から見えない）
    • 操作はメソッド経由（deposit・withdraw にルールを書ける）
    • ルール違反を入り口で止められる（マイナス入金を拒否）

    4.3 状態と振る舞いを「一緒に」持つ意味

    手続き型プログラミングでは、データと処理がバラバラでした。

    手続き型 
    const balance = 0;
function deposit(balance, amount) { /* ... */ }
function withdraw(balance, amount) { /* ... */ }

    データと処理が離れているので、データを変更するたびに関連する処理を探して歩く必要があります。オブジェクト指向では、データと処理が1つのオブジェクトに結びつくため、変更の影響範囲が狭くなります。

    5.カプセル化・継承・多態の設計的意味

    概念設計的意味
    カプセル化内部を隠し、不正な変更を防ぐ。境界を作る
    継承共通を基底（親）にまとめ、差分だけ派生（子）に書く（ただし乱用注意）
    多態同じインターフェースで実装を差し替える。拡張に強い
     
      カプセル化 → 変更の局所化
  継承       → 再利用（is-a が成立するときだけ）
  多態       → OCP の実現（拡張で対応）

    OCP（開放閉鎖の原則）は「拡張には開き、変更には閉じる」という原則です（→ SOLIDとオブジェクト指向）。また、継承より合成（Composition）を選ぶ場面が多いです（→ 継承と合成）。

    6.メッセージと協調（オブジェクト同士のやりとり）

    OOP では、オブジェクト同士がメッセージ（相手のメソッドを呼ぶこと）で協調します。

    [Order] ──place()──→ [Inventory]
              │
              └── reserve(items)
    • 命令ではなく「〇〇して」というメッセージを送る
    • 送り手は相手の内部を知らなくてよい（疎結合：お互いへの依存が少ない状態）
    • オブジェクトの責務（そのオブジェクトが引き受ける仕事）が協調の単位になる

    7.クラスの構成要素

    要素役割例
    フィールド（プロパティ）オブジェクトの状態name, age
    コンストラクタオブジェクト生成時の初期化constructor(name)
    メソッドオブジェクトの振る舞いbark(), run()
    静的メンバー（static）クラス全体で共有するものMath.PI
    static の例 
    class MathUtil {
  static PI = 3.14159;
  static add(a, b) { return a + b; }
}

MathUtil.add(1, 2); // オブジェクトを作らずに呼べる

    7.1 クラスはモノとは限らない

    初心者向けの説明では「犬」「車」など実在するモノでクラスを例えますが、実際には次のような「役割」を表すクラスのほうが実務では多いです。

    UserRepository

    データアクセスの役割

    PaymentService

    支払い処理の役割

    TaxCalculator

    計算の役割

    クラスは「モノを作る道具」ではなく、「責任の単位を表現する道具」と捉えるほうが本質的です。

    8.オブジェクト指向が向く場面と限界

    向く場面

    • 現実世界の概念をモデル化したい（注文、顧客、商品）
    • 状態とルールがセットのドメイン（業務領域）
    • 振る舞いの差し替えが必要（支払い方法、配送方法）
    • 多くの言語・フレームワークで標準的

    限界

    • 継承の乱用で階層が複雑化
    • 可変状態（あとから書き換わるデータ）が並行処理・テストで問題に
    • 貧血モデル — ロジックがサービスに逃げ、オブジェクトが空（データだけ）になる
    • 単純なデータ変換には関数型の方が自然なことも（→ 関数型と純粋関数）

    クラス設計の詳細は 44_クラス設計・デザインパターン の目次ノート、SOLID はSOLIDとオブジェクト指向を参照してください。

    9.よくある誤解

    誤解1：「何でもクラスにすべき」

    1つの関数で済むものは、クラスにする必要はありません。状態を持つ／振る舞いをまとめる意味がある場合だけクラスにします。

    誤解2：「Getter/Setter を機械的に作ればカプセル化になる」
    class User {
  getName() { return this.name; }
  setName(n) { this.name = n; }
  // 全フィールドに対して…
}

    これはただの公開フィールドと変わらず、カプセル化の意味がありません。「外に何を見せるか」を設計して絞ることが大事です。

    誤解3：「クラス数が多いほど良い」

    関心を分けるのは大事ですが、過剰にクラスを作ると全体像がつかみにくくなります。「関係の深いデータと振る舞いは同じクラスに」が原則です。

    10.まとめ

    • OOP は状態と振る舞いを一体化したオブジェクトを中心に設計する。手続き指向の「データと処理の分離」への応答
    • クラス = 設計図、オブジェクト = 実物。クラスは「責任の単位」を表す道具
    • カプセル化：データは隠し、操作はメソッド経由にして、ルール違反を入り口で止める
    • カプセル化・継承・多態はそれぞれ設計上の意味がある（変更の局所化・is-a での再利用・拡張）
    • メッセージによる協調で疎結合を実現する
    • 向く場面と限界を知り、他の考え方と組み合わせる
