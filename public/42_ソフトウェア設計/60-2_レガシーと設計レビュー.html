    レガシーと設計レビュー — 理解して小さく直し、対話で改善を見つける

    テストがなく変更が怖いレガシーコードに対して、理解してから小さく改善し、ストラングラーと腐敗防止層で段階的に置き換える現実的な進め方を学びます。後半では、設計レビューの進め方・チェックリスト・良い設計と悪い設計の比較・改善提案の書き方と、次の学習ステップをまとめます。

    もとにしたノート：03_レガシーとの向き合い方 / 04_設計レビューの実践

    1.このページで扱うこと

    • レガシーコード に対して、現実的に設計を改善していく考え方（理解してから変える、小さく改善する、境界を守る、優先度をつける）
    • 設計レビュー の進め方・チェックリスト・改善提案の書き方
    • この教材を終えたあとの 次の学習ステップ

    2.レガシーコードとは何か

    レガシーコード

    一般的に、テストがなく・理解が困難で・変更が怖い コードを指します。

    • 悪意あるコードとは限らない
    • 「当時の制約で作られ、今は負債になったもの」が多い
    • 多くの現場では 新規開発より改修 のほうに時間を使う

    見方を変える

    レガシーは 設計の練習場 でもあります。ただし、いきなり全部書き直すのは現実的でないことが多いです。負債としての捉え方は 41章の 技術的負債 を参照してください。

    3.理解してから変える

    変更の前に、まず 理解 します。

    手法内容
    読む・動かす実際に実行し、挙動を確認する
    テストを追加変更の安全網にする（characterization test：仕様の正しさではなく「今どう動いているか」をそのまま記録するテスト）
    図を描く現状の依存関係を可視化する
    小さな変更1箇所だけ直し、影響を観察する

    注意

    「理解なしの大規模リファクタリング」 は新たなバグの温床です。リファクタリングの安全な手順は テストとリファクタリング を参照してください。

    4.絶えず小さく改善する

    ストラングラーパターン（古いシステムを少しずつ新しい設計に置き換えていき、最後に古いものを取り除く方法）が現実的です。巨大な OrderService なら、次の順に進められます。

    1. まず calculateTotal() を純粋関数に抽出する（→ 関数型と純粋関数）
    2. 次に Repository を注入可能にする（→ 集約とリポジトリ）
    3. 最後に Order エンティティに振る舞いを移す（→ エンティティと値オブジェクト）

    一度に全部やらず、毎スプリント1つ でも改善が積み上がります。

    5.境界を守りながらの段階的リファクタリング

    新機能は 新しい設計 で書き、古い部分との境界を明確にします。

    腐敗防止層（ACL：Anti-Corruption Layer）で、古いモデルと新しいモデルを変換します。古いモデルの用語や構造が新しい設計に染み出す（腐敗させる）のを防ぐ層です。コンテキスト間の関係としての ACL は 境界づけられたコンテキスト を参照してください。

    6.設計を諦めない現実的なライン

    すべてを理想的な設計にする必要はありません。

    優先する後回しでもよい
    変更が多い箇所ほぼ触らない箇所
    バグが多い箇所安定している箇所
    新機能の土台廃止予定の機能

    ポイント

    「完璧な設計」より「変更に強い箇所を増やす」。

    7.設計レビューの進め方

    7.1 タイミング

    • 新機能の 実装前（たたき台レビュー）
    • 大きなリファクタリングの 前後
    • 定期的な 設計健全性チェック

    7.2 進行（60 分の例）

    1. 目的とスコープ（5 分）— 何をレビューするか
    2. 現状の説明（15 分）— 図・主要なクラス・依存
    3. 質問と議論（30 分）— チェックリストに沿って
    4. アクション（10 分）— 改善項目と担当

    レビューの姿勢

    批判ではなく「改善のための対話」です。理由を聞き、代替案を一緒に考えます。アーキテクチャのレベルのレビュー観点は 41章の レビュー観点 を参照してください。

    8.レビュー用チェックリスト

    チェックリストとアンチパターン の要約です。

    構造

    • ☐ 関心は分離されているか
    • ☐ 凝集度は高く、結合度は低いか
    • ☐ 依存の方向は適切か（ドメイン → 抽象 → 詳細）

    ドメイン

    • ☐ 用語はユビキタス言語と一致しているか
    • ☐ 業務ルールはドメイン層にあるか
    • ☐ 貧血モデル・神クラスがないか

    変化

    • ☐ 変わりやすい箇所は隔離されているか
    • ☐ 過剰な抽象化がないか（YAGNI）

    テスト・運用

    • ☐ 単体テスト可能か
    • ☐ イベント・非同期の追跡は可能か

    各項目の背景：関心の分離、凝集度と結合度、ユビキタス言語、よくある設計の失敗、変化に強い設計、テストと設計、イベント駆動設計。

    9.良い設計・悪い設計の比較（注文確定の例）

    ✕ 悪い例：Controller に全部 
    app.post('/orders/:id/confirm', async (req, res) => {
  const order = await db.query('SELECT ...');
  if (order.stock < ...) { ... }
  await db.query('UPDATE stock ...');
  await sendMail(...);
  res.json({ ok: true });
});
    ◯ 良い例：薄い Controller ＋ ドメインにルール 
    // 薄い Controller
app.post('/orders/:id/confirm', async (req, res) => {
  await placeOrderUseCase.execute(req.params.id);
  res.json({ ok: true });
});

// ドメインにルール
class Order {
  confirm() { /* ルール + OrderPlaced イベント */ }
}
    観点悪い例良い例
    関心の分離UI・DB・メールが混在層ごとに分離
    テストDB が必須Order 単体でテスト可能
    用語SQL と HTTPconfirm(), OrderPlaced

    ユースケースとドメイン層の分け方は ドメイン層とユースケース を参照してください。

    10.改善提案の書き方

    ◯ 良い例：現状・問題・提案・優先度を書く 
    ## 改善提案: Order への責務移動

**現状**: 確定ロジックが OrderController に 80 行

**問題**: 業務ルールの変更時に Controller を毎回修正。単体テスト困難

**提案**: `Order.confirm()` に移動し、Controller は UseCase 呼び出しのみ

**優先度**: 高（次のスプリントで対応）

**参考**: 戦術的設計 — 貧血モデルの対策

    現状・問題・提案・優先度 を書くと、すぐに行動に移せる（actionable な）提案になります。参考に挙げている貧血モデルの対策は 戦術的設計の全体像 と チームで設計を守る を参照してください。

    43_モジュール設計

    44_クラス設計・デザインパターン

    GRASP・SOLID・パターン

    設計に終わりはない

    設計は学び終わるものではなく、実装とレビューの繰り返し で深まります。

    12.よくある誤解

    誤解1：「レガシーコードは全部書き直すのが一番早い」

    理解なしの全面書き直しは、新たなバグの温床になり、現実的でないことが多いです。理解してから、ストラングラーと腐敗防止層で少しずつ置き換えます。

    誤解2：「レガシーは書いた人の腕が悪かった結果」

    多くは当時の制約の中で作られ、時間がたって負債になったものです。責めるより、変更が多い・バグが多い箇所から優先して改善します。

    誤解3：「設計レビューは問題点を指摘する場」

    批判ではなく改善のための対話です。理由を聞き、代替案を一緒に考え、最後に改善項目と担当を決めます。

    13.まとめ

    • レガシーは 理解してから、小さく改善 する（読む・動かす、characterization test、図、小さな変更）
    • ストラングラーと ACL で段階的に置き換え、新機能は新しい設計で書く
    • 優先度をつけ、全部を一度に直そうとしない。「変更に強い箇所を増やす」
    • 設計レビューは 対話で改善を見つける場。チェックリストで観点を漏らさない
    • 良い・悪いの 比較 で具体イメージを共有し、改善提案は 現状・問題・提案・優先度 を明確に
    • 次はモジュール・クラス・メソッドの下位設計へ。設計は実装とレビューの繰り返しで深まる
