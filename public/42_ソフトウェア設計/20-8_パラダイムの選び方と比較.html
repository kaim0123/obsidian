    20 パラダイム ／ 24 選び方と組み合わせ

    パラダイムの選び方と比較 — 1つに決めず、場面ごとに組み合わせる

    手続き・オブジェクト指向・関数型は、どれか1つを選ぶものではありません。三大パラダイムの比較表（中心・データと処理・制御・状態・再利用、向く場面、限界）で特徴を整理したうえで、レイヤー・場面ごとの使い分け、マルチパラダイム言語での書き方、押し付け合いを避ける考え方、設計レビューでの見方を解説します。

    もとにしたノート：01_パラダイムの選び方と組み合わせ / 付録C_パラダイム比較表

    1.このページで扱うこと

    パラダイム（プログラムをどう組み立てるかについての基本的な考え方）として、ここまで手続き指向・オブジェクト指向（OOP）・関数型を見てきました。これらは排他的ではありません。このページでは、状況に応じた選び方と組み合わせ方を学びます。

    • 三大パラダイムの比較早見表（基本の比較・向く場面・限界・組み合わせの例）
    • 「1つだけ選ぶ」必要がない理由
    • レイヤー・場面ごとの使い分け
    • マルチパラダイム言語での実践
    • パラダイムの押し付け合いを避ける
    • 設計レビューでのパラダイムの見方

    2.三大パラダイムの比較表

    まず、手続き・OOP・関数型の特徴を早見表で並べます。

    2.1 基本の比較

    観点手続き指向オブジェクト指向関数型
    中心処理の流れオブジェクト（状態＋振る舞い）関数・データ変換
    データと処理分離しがち一体化（カプセル化）不変データ＋純粋関数
    制御順次・分岐・反復メッセージ・多態パイプライン・高階関数
    状態グローバル・共有に注意オブジェクト内部の可変状態不変を推奨
    再利用手続きの呼び出し継承・合成・多態関数の合成

    高階関数：関数を引数に受け取ったり、関数を戻り値として返したりする関数（map・filter など）。

    2.2 向く場面

    パラダイム向く場面
    手続きユースケースのオーケストレーション（複数の処理を順番に呼び出して流れをまとめること）、スクリプト、単純な流れ
    OOP現実世界の概念のモデル化、状態とルールのセット、振る舞いの差し替え
    関数型データ変換・検証・集計、並行処理、テスト容易性

    2.3 限界

    パラダイム限界
    手続きデータと処理の散在、大規模化時のグローバル状態
    OOP継承の乱用、可変状態の問題、貧血モデル（データだけ持ち、振る舞いを持たないオブジェクト）
    関数型状態遷移の表現、I/O 境界、学習コスト

    2.4 組み合わせの例

    レイヤーパラダイム
    ユースケース層手続き的
    ドメイン層OOP＋関数型（値オブジェクト・純粋計算）
    インフラ層手続き＋副作用の境界

    3.排他的な選択ではない

    「このプロジェクトは OOP」「あのプロジェクトは関数型」と1つだけ選ぶ必要はありません。現代のシステムは複数の考え方を組み合わせて使うのが普通です。

    考え方は積み重なってきた

    古いものが消えて新しいものに置き換わったわけではありません。課題への応答として、考え方が積み重なってきたのです。

    ソフトウェア設計年表の「現代での使い方」も参照してください。

    4.レイヤー・場面ごとの使い分け

    レイヤー・場面よく使う考え方
    ユースケースの流れ手続き的（オーケストレーション）
    ドメインオブジェクトOOP（エンティティ、値オブジェクト）
    データ変換・検証関数型（純粋関数、immutable）
    サービス間連携イベント駆動（→ イベント駆動設計）
    業務の構造整理DDD（→ DDDとは）

    1つのシステムの中で、これらは次のように重なります。

    5.マルチパラダイム言語での実践

    JavaScript、Python、Java、Kotlin、TypeScript などは複数のスタイルを混在できます。

    // OOP: ドメインオブジェクト
class Order {
  constructor(items) { this.items = items; }
  total() {
    // 関数型: 純粋な集計
    return this.items.reduce((sum, i) => sum + i.price, 0);
  }
}

// 手続き的: ユースケースの流れ
async function placeOrder(order) {
  validate(order);
  await repository.save(order);
  await notify(order);
}

    「言語の機能を使い分ける」のではなく、「問題に合った考え方を選ぶ」ことが重要です。

    6.パラダイムの押し付け合いを避ける

    押し付け問題
    すべてをクラスにする単純な関数で足りる処理までオブジェクト化
    すべてを純粋関数にする状態遷移が不自然、I/O 境界が曖昧
    手続きだけで巨大化責務の分散が進まない

    チームの慣れ・言語・ドメインの性質を考慮し、柔軟に選びます。「正しいパラダイム」は1つではなく、トレードオフの中での選択です。たとえば、種類（クラス）が増えやすいか、操作（関数）が増えやすいかでも向き不向きが変わります（→ 関数型と純粋関数の「データと振る舞いを分ける」）。

    7.設計レビューでのパラダイムの見方

    レビュー時の観点です。

    • ☐ この処理は選んだパラダイムに合っているか
    • ☐ 手続き・OOP・関数型が一貫して混在しすぎていないか（意図的なら OK）
    • ☐ ドメインの性質（状態重視 vs 変換重視）に合っているか
    • ☐ チームが読み・保守できるスタイルか

    判断に迷ったら、2章の比較表に戻って「向く場面」と「限界」を照らし合わせます。

    8.よくある誤解

    誤解1：「プロジェクトごとにパラダイムを1つ決めるべき」

    誤りです。現代のシステムは、ユースケースは手続き的、ドメインは OOP、計算は関数型、サービス間はイベント駆動、というように複数の考え方を組み合わせるのが普通です。

    誤解2：「新しいパラダイムが古いパラダイムを置き換えた」

    誤りです。考え方は課題への応答として積み重なってきたもので、手続き的な書き方も、ユースケースのオーケストレーションなどで今も現役です。

    誤解3：「マルチパラダイム言語なら、言語の機能を全部使い分ければよい」

    大事なのは機能の使い分けではなく、問題に合った考え方を選ぶことです。意図なく混在させると読みにくくなるので、レビューでは一貫性と適合性を確認します。

    9.まとめ

    • 手続きは処理の流れ、OOP は状態＋振る舞いのオブジェクト、関数型は不変データ＋純粋関数が中心。それぞれ向く場面と限界がある
    • パラダイムは排他的ではなく、組み合わせて使う
    • レイヤー・場面ごとに適した考え方がある（ユースケース＝手続き、ドメイン＝OOP＋関数型、インフラ＝手続き＋副作用の境界）
    • 押し付け合いを避け、問題に合わせて選ぶ。正しいパラダイムは1つではなく、トレードオフの中での選択
    • レビューでは一貫性と適合性を確認する
