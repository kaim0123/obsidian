    10 設計の基礎

    関心の分離 — 目的の違う処理を混ぜない

    良い設計の第一歩が「関心の分離」です。表示・計算・保存といった目的の異なる処理を1か所に混ぜると何が困るのか、レイヤー・モジュール・クラス・関数の各レベルでどう分けるのか、そして分けすぎ・分け足りないをどう見分けるのかを、コード例とチェックリストで解説します。

    もとにしたノート：10_設計の基礎/04_関心の分離

    1.このページで扱うこと

    1つの関数に画面の処理もデータベースへの保存もメール送信も全部書いてしまう — 小さなプログラムでは問題になりませんが、規模が大きくなると「どこを直せばいいか分からない」コードの典型的な原因になります。

    このページでは次の内容を扱います。

    • 関心の分離とは何か：定義と由来
    • 1つの場所に全部書く問題：4つの困りごととコード例
    • レイヤー・モジュール・クラス・関数への分離
    • 分けすぎ・分け足りないの見分け方
    • 設計レビューで使えるチェックリスト

    2.関心の分離とは何か

    関心の分離（Separation of Concerns, SoC） とは、目的の異なる処理を別の場所に分ける 設計原則です。Edsger Dijkstra（エドガー・ダイクストラ。構造化プログラミングで知られる計算機科学者）が 1974 年に提唱した考え方で、ソフトウェア設計の根幹のひとつです。

    「関心」とは ソフトウェアが扱う関心事 のことです。表示・計算・保存は、それぞれ別の関心です。

    3.1つの場所に全部書く問題

    すべてを 1 か所に書くと、次の問題が起きます。

    問題具体例
    読みにくい1000 行の関数で何をしているか把握できない
    直しにくいUI を変えると DB 処理まで壊れる
    試しにくい業務ロジックだけテストできない
    再利用できない同じ計算を別画面で使えない
    ✕ 悪い例：すべてが混在 
    function handleSubmit() {
  const name = document.getElementById('name').value;  // UI
  if (!name) { alert('名前を入力'); return; }         // 検証
  const tax = calculateTax(name);                     // 業務
  db.save({ name, tax });                             // 永続化
  sendEmail(name);                                    // 通知
}

    この関数は、画面（UI）・入力チェック（検証）・税計算（業務）・保存（永続化）・メール（通知）という5つの関心を1か所で抱えています。たとえば画面の部品を変えただけで、税計算のテストまでやり直しになります。

    関心ごとに分けると、たとえば次のような形になります（考え方を示すための簡略な例です）。

    ◯ 良い例：関心ごとに分けて、つなぐ役だけを残す 
    // UI の関心：画面から値を取り、結果を表示するだけ
function handleSubmit() {
  const name = document.getElementById('name').value;
  const result = orderService.register(name);
  if (!result.ok) alert(result.message);
}

// 業務の関心：検証と計算、保存・通知の指示
const orderService = {
  register(name) {
    if (!name) return { ok: false, message: '名前を入力' };
    const tax = calculateTax(name);
    orderRepository.save({ name, tax });   // 永続化の関心は別の部品へ
    notifier.send(name);                   // 通知の関心も別の部品へ
    return { ok: true };
  },
};

    こうすると業務ロジック（orderService）だけを画面なしでテストでき、同じ処理を別の画面からも使えます。

    4.レイヤー・モジュール・クラスへの分離

    関心の分離は、設計の階層ごとに適用できます。

    レベル分離の単位例
    レイヤーシステムの層プレゼンテーション / ドメイン / インフラ
    モジュールパッケージ・ディレクトリorder/, billing/, notification/
    クラス型Order, OrderRepository, OrderController
    関数処理の塊validate(), calculateTotal(), save()

    「プレゼンテーション」は画面や API の入口、「ドメイン」は業務ルール、「インフラ」は DB やメール送信などの技術的な詳細を担当する層です。クラスに分けると、たとえば次のような関係になります。

    詳細なモジュール分割は 43_モジュール設計、クラス分割は 44_クラス設計・デザインパターンで扱います。レイヤー単位の分け方は 41章：層化・三層・レイヤード も参照してください。

    5.分けすぎ・分け足りないの見分け方

    分け足りないサイン

    • 1 つのファイル・クラスが 複数の理由で変更 される
    • 「この処理、どこに書けばいい？」が頻繁に起きる
    • テストでモック（本物の代わりに使う偽の部品）が大量に必要になる

    分けすぎのサイン

    • たどるファイル数が多すぎて 全体像が掴めない
    • 1 行の変更に 10 ファイル を触る
    • 抽象化のためだけのクラスが増え、意図が読めない

    目安

    1 つの単位（クラス・モジュール）は 1 つの関心 に集中させます。ただし、小さすぎる分割は避けます（変化に強い設計 の YAGNI も参照）。

    6.関心の分離のチェックリスト

    設計レビュー時に使えるチェックリストです。

    • ☐ この部品は 1 つの関心 に集中しているか
    • ☐ UI のコードに DB や HTTP の詳細 が混ざっていないか
    • ☐ 業務ルールが フレームワークや DB に引っ張られていない か
    • ☐ 横断的関心事（ログ・認証）が 各所にコピペ されていないか
    • ☐ 分離の境界は チームで説明できる か

    横断的関心事 とは、ログ・認証のように多くの機能にまたがって必要になる関心のことです（41章：横断的関心事と認証認可）。

    7.よくある誤解

    誤解1：「関心の分離＝ファイルを細かく分けること」

    目的は「目的の違う処理を混ぜない」ことで、ファイル数を増やすことではありません。1 行の変更に 10 ファイルを触るようなら分けすぎです。

    誤解2：「レイヤーを分ければ関心の分離は完了」

    関心の分離はレイヤーだけでなく、モジュール・クラス・関数の各レベルで適用します。層が分かれていても、1つのクラスに複数の関心が混ざっていれば分け足りていません。

    誤解3：「ログや認証は各所に書くしかない」

    ログ・認証のような横断的関心事こそ、各所へのコピペを避けて1か所にまとめる対象です。チェックリストの項目にもなっています。

    8.まとめ

    • 関心の分離は、目的の異なる処理を別の場所に分ける原則（Dijkstra, 1974）
    • 混在は読みにくさ・変更困難・テスト困難・再利用困難を招く
    • レイヤー・モジュール・クラス・関数の各レベルで適用できる
    • 分けすぎ・分け足りないのバランスが重要。1 つの単位は 1 つの関心に
