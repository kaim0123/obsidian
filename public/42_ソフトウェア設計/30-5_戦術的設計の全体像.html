    戦術的設計の全体像 — コンテキストの内側をコードで組み立てる部品

    DDD の戦術的設計は、1つの境界づけられたコンテキストの「内側」をどうコードにするかを扱います。エンティティ・値オブジェクト・集約・ドメインイベントという4つの基本部品と、リポジトリ・ドメインサービス・アプリケーションサービスの役割、そして避けたい「貧血ドメインモデル」までを、注文（EC）の例で一通り見渡します。

    もとにしたノート：01_戦術的設計 / 02_集約とエンティティと値オブジェクトとドメインイベント

    1.このページで扱うこと

    戦略的設計では、システムを境界づけられたコンテキスト（同じ言葉が同じ意味で通じる範囲）に分けました。このページからは、1つのコンテキストの内部をどうモデル化するか — DDD の戦術的設計（コードの書き方のレベルの設計）を学びます。

    戦術的設計では、ドメイン層（業務のルールを置く層）を次の4つの基本部品で組み立てます。

    エンティティ

    ID で識別される「もの」

    値オブジェクト

    値で意味が決まる「性質」

    集約

    ルールを守るまとまりの単位

    ドメインイベント

    起きた「事実」の記録

    さらに、それらを支えるリポジトリ・ドメインサービス・アプリケーションサービスの役割と、よくある失敗である貧血ドメインモデルも扱います。ここでは導入レベルで全体を見渡し、詳しくは次のページで1つずつ掘り下げます。

    • エンティティと値オブジェクト
    • 集約とリポジトリ
    • ドメインイベント
    • ドメイン層とユースケース

    前提として DDDとは を読んでおくと理解しやすくなります。集約は、41章のアーキテクチャに効く原則でも「不変条件の境界」として触れています。ここでは DDD としての使い方を具体例付きで押さえます。

    2.まず全体の関係

    4つの部品は、次のような関係にあります。

    • 集約は「まとめて一貫性を守る単位」
    • その中にエンティティと値オブジェクトが入る
    • 重要な変化はドメインイベントとして表現する

    3.エンティティと値オブジェクト

    ドメインのオブジェクトは、まず「ID で見分けるもの」と「値で見分けるもの」に分けます。

    種類特徴例
    エンティティ同一性（ID）で識別Order, Customer
    値オブジェクト値で比較。不変が多いMoney, Address, Email
     
    // 値オブジェクト: 500円 + 300円 = 800円（値で比較）
class Money {
  constructor(amount, currency) {
    this.amount = amount;
    this.currency = currency;
  }
  add(other) {
    return new Money(this.amount + other.amount, this.currency);
  }
}

// エンティティ: ID で識別（同じ金額でも別注文）
class Order {
  constructor(id) { this.id = id; }
}

    こうして種類を分けることで、ルールの置き場所を型で明確にします。

    3.1 エンティティ（Entity）

    エンティティは、同一性（ID）で識別されるオブジェクトです。

    • 属性の値が同じでも、ID が違えば別物
    • 時間とともに状態が変わる
    class Order {
  constructor(
    readonly id: OrderId,        // ← これで「どの注文か」が決まる
    private status: OrderStatus,
  ) {}

  ship() {
    if (this.status !== OrderStatus.Paid) {
      throw new Error('支払い前に発送できません');
    }
    this.status = OrderStatus.Shipped;
  }
}
    ポイント説明
    ID があるOrderId, UserId など、型で区別すると安全
    振る舞いを持つcancel(), ship() のようにルールをメソッドに
    ライフサイクルがある作成 → 変更 → （論理）削除

    クリーンアーキテクチャの同心円の中心にある Entities は、DDD では主にここ（ドメイン層のエンティティ・集約ルート）に対応します。

    3.2 値オブジェクト（Value Object）

    値オブジェクトは、属性の値の組み合わせで意味が決まり、交換可能なオブジェクトです。

    • ID がない（または持たない）
    • 不変（immutable：作ったあと中身を変えない）にすることが多い
    • 2つの値オブジェクトは、中身が同じなら等しい
    class Money {
  constructor(
    readonly amount: number,
    readonly currency: string,
  ) {
    if (amount < 0) throw new Error('金額は0以上');
    if (!currency) throw new Error('通貨は必須');
  }

  add(other: Money): Money {
    if (this.currency !== other.currency) {
      throw new Error('通貨が違います');
    }
    return new Money(this.amount + other.amount, this.currency);
  }
}

    値オブジェクトに向いているものは次のとおりです。

    • 金額、住所、メールアドレス、日付範囲
    • 「マイナスの金額はありえない」などの小さな不変条件（いつでも成り立っていなければならないルール）
    • どこにでもコピーして渡してよいデータ

    3.3 エンティティとの見分け方

    質問エンティティ寄り値オブジェクト寄り
    同じ内容でも別物になりうる？はい（別 ID）いいえ（値が同じなら同じ）
    状態を変える？する変えず新しいインスタンスを作る
    例注文、ユーザー金額、郵便番号

    詳しくは エンティティと値オブジェクト で扱います。

    4.集約（Aggregate）— 整合性の単位

    集約は、一貫性（不変条件）を守るためのまとまり、つまり整合性を保つ単位です。41章のアーキテクチャに効く原則にある「不変条件の境界」と同じ発想です。

      Order（集約ルート）
    ├── OrderLine（明細）
    └── OrderLine
    • 外部は集約ルート経由でのみ操作
    • トランザクション境界（まとめて成功・失敗させる範囲）は1 集約が基本
    • 「注文確定」は Order が責任を持つ

    4.1 集約ルート

    集約には1つだけ入り口となる集約ルート（Aggregate Root）があります。

    • 外からは集約ルート経由だけで中身を変更する
    • リポジトリが保存・読み込みするのも集約ルート単位
      外部 ──→ Order（集約ルート）──→ OrderLine
              │
              └── 合計金額・行数などの不変条件をここで守る
    class Order {  // 集約ルート
  private lines: OrderLine[] = [];

  addLine(productId: ProductId, quantity: number, unitPrice: Money) {
    if (quantity <= 0) throw new Error('数量は1以上');
    this.lines.push(new OrderLine(productId, quantity, unitPrice));
    // 合計が上限を超えないか、などもここで検証
  }

  total(): Money {
    return this.lines.reduce(
      (sum, line) => sum.add(line.subtotal()),
      Money.zero('JPY'),
    );
  }
}

    4.2 なぜ集約でまとめるのか

    • 注文全体の合計と各行の小計が矛盾しないようにする
    • 同時更新の単位をはっきりさせる（在庫と注文をいつ一緒にロックするか、など）
    • トランザクションの境界の目安になる

    4.3 集約設計の初心者向けルール

    1. 小さく始める — 最初から巨大な集約にしない
    2. 参照は ID で — 別集約のオブジェクトを直接持たず、ProductId のように ID のみ
    3. 1トランザクションで変更する集約は1つが目安（厳密なルールではないが安全）

    詳しくは 集約とリポジトリ で扱います。

    5.リポジトリ — 永続化の抽象化

    リポジトリは、集約の永続化（DB などへの保存）・取得を抽象化する窓口です。

    • ドメイン層はDB の詳細を知らない
    • テスト時にインメモリ実装（メモリ上の配列などに保存する実装）に差し替え可能
    • 「コレクションのように扱う」イメージ

    インターフェースを内側に置いて実装を外側に置く形は、41章の依存性逆転の原則そのものです。詳しくは 集約とリポジトリ で扱います。

    6.ドメインイベント（Domain Event）

    ドメインイベントは、ドメインの中で起きた、もう戻せない事実を表すオブジェクトです。

    • 過去形（〜した）の名前：OrderPlaced, PaymentCompleted
    • いつ・誰の・何が起きたかの情報を持つ
    • 集約の状態変更と一緒に発生する
    class OrderPlaced {
  constructor(
    readonly orderId: OrderId,
    readonly occurredAt: Date,
    readonly customerId: CustomerId,
    readonly total: Money,
  ) {}
}

class Order {
  private events: DomainEvent[] = [];

  confirm() {
    // ... 状態変更 ...
    this.events.push(
      new OrderPlaced(this.id, new Date(), this.customerId, this.total()),
    );
  }

  pullEvents(): DomainEvent[] {
    const e = [...this.events];
    this.events = [];
    return e;
  }
}

    6.1 ドメインイベントの用途（入門）

    用途例
    同じ BC（境界づけられたコンテキスト）内の別処理を起こす注文確定 → 在庫引当
    監査・履歴「いつ誰が何をしたか」の記録
    後から他システムへ連携メール送信、分析、別 BC への通知

    インフラの「メッセージキュー」と混同しない

    ドメインイベントはまずドメインの言葉での事実であり、Kafka などはその配信の仕組み（インフラ）です。

    詳しくは ドメインイベント で扱います。

    7.ドメインサービスとアプリケーションサービス

    エンティティや値オブジェクトに収まらない処理は、2種類の「サービス」に置きます。

    種類役割例
    ドメインサービス特定のエンティティに属さないドメイン処理複雑な価格計算
    アプリケーションサービスユースケースのオーケストレーション（手順の指揮）PlaceOrderUseCase
     
      アプリケーションサービス（手続き的な流れ）
       │
       ├── ドメインオブジェクトに処理を委譲
       └── リポジトリ・外部サービスを呼ぶ

    基本の分担

    ロジックはドメインに、流れはアプリケーションにが基本です。

    詳しくは ドメイン層とユースケース で扱います。

    8.貧血ドメインモデルの問題と対策

    貧血ドメインモデル（Anemic Domain Model）とは、エンティティが getter/setter だけで、ロジックがサービス層に集中した状態です。

    ✕ 悪い例：Order はデータ入れ物 
    // 貧血: Order はデータ入れ物
class Order { getTotal() { return this.total; } }
// ロジックは OrderService に全部
class OrderService {
  calculateDiscount(order) { ... }
  validate(order) { ... }
}

    8.1 対策

    • 振る舞いをエンティティ・値オブジェクトに置く
    • order.confirm() のように業務の言葉でメソッドを命名（ユビキタス言語をそのままメソッド名にする）
    • アプリケーションサービスは薄く保つ

    9.4つを使い分けるクイックガイド

    やりたいこと使うもの
    「この注文」と「あの注文」を区別したいエンティティ（ID）
    金額や住所にルールを持たせたい値オブジェクト
    注文と明細行を一緒に一貫させたい集約（集約ルート＋内部）
    「注文が確定した」という事実を残したいドメインイベント

    10.ミニ例 — EC の注文

    4つの部品とユースケースを、1つの例にまとめると次のようになります。

    // 値オブジェクト
class OrderId {
  constructor(readonly value: string) {}
}

// 集約ルート（エンティティ）
class Order {
  private lines: OrderLine[] = [];
  private events: DomainEvent[] = [];

  static create(customerId: CustomerId): Order {
    return new Order(OrderId.generate(), customerId, OrderStatus.Draft);
  }

  addItem(productId: ProductId, qty: number, price: Money) {
    this.lines.push(new OrderLine(productId, qty, price));
  }

  place() {
    if (this.lines.length === 0) throw new Error('明細がありません');
    this.status = OrderStatus.Placed;
    this.events.push(new OrderPlaced(this.id, new Date(), this.total()));
  }

  total(): Money { /* ... */ }
}

// ユースケース側
class PlaceOrderUseCase {
  async execute(orderId: OrderId) {
    const order = await this.repo.findById(orderId);
    order.place();
    await this.repo.save(order);
  }
}
    • OrderId は値オブジェクト、Order は集約ルート（エンティティ）
    • 「明細がなければ確定できない」というルールは Order.place() が守る
    • 確定すると OrderPlaced イベントが記録される
    • ユースケースは「取り出す → 操作する → 保存する」の手順だけを書く

    11.よくある誤解

    誤解1：「全部エンティティにする」

    金額・住所は値オブジェクトの方が自然なことが多いです。ID で区別する意味がないものまでエンティティにすると、比較や扱いが不必要に複雑になります。

    誤解2：「集約は大きいほどよい」

    小さく始め、必要性が出たら広げます。

    誤解3：「イベントは非同期のこと」

    まずはドメイン内の「起きた事実」です。同期で配るか非同期で配るかという配信方法は別問題です。

    誤解4：「anemic（貧血）な DTO ＋ 巨大サービスでよい」

    ルールはドメインオブジェクトと集約に寄せます。DTO（データを運ぶだけの入れ物）に何でもサービスで処理を書くと、それは貧血ドメインモデルです。

    12.まとめ

    • 戦術的設計は、1つのコンテキストの内部をどうモデル化するか（コードの書き方）
    • エンティティは ID、値オブジェクトは値で識別する
    • 集約は整合性の単位。外部はルート経由で操作し、参照は ID で、小さく保つ
    • リポジトリで永続化を抽象化する。ドメイン層は DB の詳細を知らない
    • ドメインイベントは起きた事実。配信の仕組み（メッセージキュー）とは別物
    • ロジックはドメインに、流れはアプリケーションに。貧血モデルを避ける
