    2.ソフトウェア設計とは何か

    2.1 SWEBOK の定義

    ソフトウェア工学の知識体系 SWEBOK（IEEE Computer Society がまとめた、ソフトウェア工学で知っておくべき知識の一覧）では、ソフトウェア設計を次のように位置づけています。

    要求を分析して、ソフトウェアの 内部構造の記述 を作り出す活動。その記述は、実装（構築）の土台となる。

    SWEBOK は設計を大きく2つの段階に分けています。

    段階中身このノート群での置き場
    アーキテクチャ設計（高レベル設計）システム全体を構成要素に分け、その関係を決める41_アーキテクチャ（アーキテクチャとは・設計との違い）
    詳細設計各構成要素の中身（モジュール・クラス・関数・データ）を決める42〜46

    42_ソフトウェア設計 は、この2つの 間をつなぐ考え方（原則・パラダイム・ドメインモデリング・設計プロセス）を扱います（→ 設計の階層と基本用語）。

    2.2 設計の階層とフォルダの対応

    設計の階層と、ノート群（章）の対応を図にすると次のようになります。

    そのため、次のテーマは兄弟の章が本拠地です。42 では「設計の考え方としての位置づけ」だけを書き、詳細はそちらに任せます。

    3.「良い設計」の基準 — 複雑さを管理すること

    3.1 設計の目的は「変更しやすさ」

    動くコードを書くだけなら、設計はいりません。設計が必要になるのは、ソフトウェアが 変更され続ける からです（→ ソフトウェア設計を学ぶ理由）。

    • 要求は変わる（新機能・法改正・競合への対応）
    • 技術は変わる（ライブラリの更新・クラウドへの移行）
    • 人は変わる（メンバーの入れ替わり）

    良い設計とは、これらの変更を、少ないコストで、安全に行える設計 です。

    3.2 Ousterhout の「複雑さ」の定義

    スタンフォード大学の John Ousterhout は『A Philosophy of Software Design』（2018、第2版 2021）で、設計の敵を 複雑さ と定義しました。

    複雑さ とは、ソフトウェアの構造のうち、理解しにくく、変更しにくくしているもの すべてである。

    複雑さは、次の3つの症状として現れます。

    症状意味例
    変更の増幅（Change Amplification）一見単純な変更なのに、多くの場所を直す必要がある消費税率を変えるのに、20ファイルを修正する
    認知負荷（Cognitive Load）変更するために、知っておくべきことが多すぎるこの関数を呼ぶ前に、3つのグローバル変数を正しく設定しておく必要がある
    知らないことを知らない（Unknown Unknowns）何を知る必要があるのかすら分からない。最も悪い症状 最悪ある設定値を変えると、まったく関係なさそうな画面が壊れる。変更してバグが出るまで誰も気づかない

    複雑さの原因は、大きく2つに集約されます。

    依存

    あるコードを、他のコードと切り離して理解・変更できない。

    不明瞭さ

    重要な情報が、見て分かる形になっていない。

    3.3 設計原則は「複雑さとの戦い方」

    10_設計の基礎 で学ぶ原則は、すべてこの複雑さと戦うための道具として整理できます。

    原則戦う相手ページ
    関心の分離異なる理由の変更が混ざること（変更の増幅）関心の分離
    高凝集関連するものが散らばること（変更の増幅）凝集度と結合度
    疎結合依存が多く強いこと（変更の増幅・知らないことを知らない）凝集度と結合度
    カプセル化・情報隠蔽知るべきことが多すぎること（認知負荷）カプセル化と情報隠蔽
    変化の隔離変わりやすい部分が広がること変化に強い設計
    明確な命名・ユビキタス言語不明瞭さ戦略的設計とユビキタス言語

    41章との関係

    凝集・結合を「アーキテクチャの単位」で測る話（モジュール性、結合の指標、コナーセンス）は 41章が本拠地です。モジュール性と疎結合高凝集・結合の指標・コナーセンスもあわせて読むと、同じ考え方がズームレベルを変えても通じることが分かります。

    4.設計の基本原則

    4.1 SWEBOK が挙げる設計原則

    SWEBOK は、ソフトウェア設計の基本原則として次のものを挙げています。

    原則意味
    抽象化目的に関係する情報だけに注目し、それ以外を無視する（手続きの抽象・データの抽象・制御の抽象）
    結合度と凝集度モジュール間の依存の強さ／モジュール内の要素の関連の強さ（→ 凝集度と結合度）
    分解とモジュール化大きなソフトウェアを、明確なインターフェースを持つ小さな部品に分ける
    カプセル化・情報隠蔽抽象の内部の詳細をまとめ、外から見えなくする（→ カプセル化と情報隠蔽）
    インターフェースと実装の分離公開する約束（インターフェース）と、中身（実装）を分ける（→ 多態とインターフェース、インターフェースと抽象化）
    十分性・完全性・原始性抽象が必要な性質を過不足なく持ち、基本的な操作だけで構成されていること
    関心の分離関係者ごとの関心事を、別々の部分で扱う（→ 関心の分離）

    4.2 すべての出発点：Parnas の情報隠蔽（1972）

    これらの原則の多くは、David Parnas の 1972 年の論文「On the Criteria To Be Used in Decomposing Systems into Modules（システムをモジュールに分解する基準について）」にさかのぼります。

    Parnas は、同じシステムを2通りに分けて比較しました。

    分け方基準結果
    処理の流れで分ける（入力 → 処理 → 出力）フローチャートの段階ごとにモジュールにするデータ形式を変えると、ほぼすべてのモジュールに影響する
    隠す設計判断で分ける（情報隠蔽）変わりそうな設計判断 を1つずつモジュールに閉じ込めるデータ形式を変えても、影響は1つのモジュールに収まる

    Parnas の結論

    モジュールは、処理の段階ではなく、「何を隠すか」で分けるべきである。隠すべきなのは、変わる可能性の高い設計判断である。

    変わりやすい設計判断の例として、Parnas は データ形式・ユーザーインターフェース・ハードウェア・OS を挙げています。50年以上前の論文ですが、クリーンアーキテクチャの「DB や UI を外側に追い出す」（依存性のルールとクリーンアーキテクチャ）、マイクロサービスの「データを隠す」（データ所有権とSAGA）まで、この考え方の延長線上にあります。

    4.3 深いモジュール（Ousterhout）

    Ousterhout は情報隠蔽を発展させ、深いモジュール（Deep Module）という考え方を示しました。モジュールを「上辺＝インターフェース、面積＝実装」の長方形で描くと、次のようになります。

     浅いモジュール            深いモジュール
 ┌──────────────┐         ┌────┐ ← インターフェース（小さい）
 │インターフェース│         │    │
 ├──────────────┤         │    │
 │   実装       │         │実装│ ← 多くの機能・複雑さを隠している
 └──────────────┘         │    │
                          │    │
                          └────┘

    深いモジュール

    インターフェースは 単純、実装は 多くの機能と複雑さを隠している。

    例：Unix のファイル入出力は open/read/write/close の5つ程度の関数で、ディスク管理・キャッシュ・権限などの膨大な複雑さを隠している。

    浅いモジュール

    インターフェースが実装と同じくらい複雑で、隠しているものが少ない。

    例：何もしないラッパークラス、1行の処理のためのクラス。

    「小さなクラスをたくさん作れば良い設計」とは限らない、という指摘です。これは 41_アーキテクチャ で見た シンクホール（何もしない層） の問題（閉じた層と開いた層）とも重なります。モジュール設計としての詳細は 43_モジュール設計 で扱います。

    5.パラダイム — 設計の「道具箱」

    パラダイム（プログラムをどんな考え方で組み立てるかの流儀）は、複雑さと戦うための道具箱です。

    5.1 3つのパラダイムの関係

    パラダイム複雑さへの対処法得意なことページ
    手続き・構造化処理を手順と関数に分ける単純な処理・スクリプト・性能が重要な部分手続き指向設計
    オブジェクト指向データと振る舞いをまとめ、状態を隠す（カプセル化）種類が増えていく領域、状態を持つ業務の概念オブジェクト指向とクラス
    関数型状態を持たない（不変・純粋関数）、副作用を端に寄せる計算・変換・検証、並行処理、操作が増えていく領域関数型と純粋関数

    オブジェクト指向は「状態を 隠す」ことで、関数型は「状態を 持たない」ことで、それぞれ影響範囲を狭めます。目指しているものは同じで、手段が違う のです。

    オブジェクト指向の中身は 継承と合成・多態とインターフェース・SOLIDとオブジェクト指向 で詳しく扱います。

    5.2 現代は「組み合わせる」時代

    TypeScript・Kotlin・Swift・C# など、現代の主要な言語は複数のパラダイムを取り込んでいます。実務では、次のような組み合わせが一般的です（→ パラダイムの選び方と比較）。

    • 業務の概念（注文・顧客）はオブジェクトや型で表す
    • 計算・検証 は純粋関数で書く
    • 値オブジェクト は不変にする（関数型の考え方。→ エンティティと値オブジェクト）
    • 副作用（画面表示・DB 書き込みなど、関数の外の世界を変えること）はユースケースの最初と最後に集める（Functional Core, Imperative Shell）
    • 状態の種類 は直和型（「A か B か C のどれか」を表す型）で表す（→ 型でドメインを表す）

    6.ドメイン駆動設計 — 「何を」モデル化するか

    6.1 パラダイムと DDD の違い

    パラダイムが「どう 書くか」の道具だとすれば、DDD（ドメイン駆動設計）は「何を 中心に設計するか」の考え方です（→ DDDとは）。

    DDD の核

    ソフトウェアの中心に、業務（ドメイン）の知識を置き、業務の専門家と開発者が同じ言葉でモデルを育てていく。

    6.2 DDD の全体像

    段階問いページ

    戦術的設計コンテキストの中をどう作るか戦術的設計の全体像 / エンティティと値オブジェクト / 集約とリポジトリ / ドメインイベント / ドメイン層とユースケース

    6.3 DDD で最も大切な判断：どこに力を入れるか

    DDD は「重くて難しい」と言われがちですが、その多くは すべての部分に戦術パターンを使おうとする ことから来ています。

    コアサブドメイン

    競争優位を生む部分。ここ だけ、ドメインモデルで丁寧に作る。

    支援サブドメイン

    シンプルに作る（CRUD で十分なことも多い）。

    汎用サブドメイン

    認証・決済など。買う・借りる。

    詳しくは コアドメインとサブドメイン を参照してください。

    6.4 イベント駆動設計

    DDD の ドメインイベント（「注文が確定した」のような、業務で起きた出来事）を軸に、システムの部品やコンテキスト同士をつなぐのが イベント駆動設計 です（→ イベント駆動設計、ドメインイベント）。分散システムとしての実装（メッセージブローカー・SAGA）は 41_アーキテクチャ/40_システム・分散 が本拠地です（→ 同期API・メッセージ・イベント駆動、データ所有権とSAGA）。

    7.設計の進め方・守り方・直し方

    7.1 設計は「一度で決める」ものではない

    考え方内容ページ
    段階的に深める最初は粗く、理解が深まるにつれて詳しくする設計の進め方と段階的な深化
    YAGNI と変化への備えのバランス「いつか必要かも」で作り込まない（YAGNI：You Aren't Gonna Need It）。ただし変わりやすい部分は隔離しておく変化に強い設計
    テストが設計を導くテストしにくいコードは、たいてい結合が強い。TDD（テスト駆動開発）はテストを先に書くことで設計を改善するテストとリファクタリング
    リファクタリングで設計を育てる動作を変えずに構造を改善し続ける。設計は「書いた後」も続くテストとリファクタリング

    Ousterhout は、目の前の機能を動かすことだけを考える 戦術的プログラミング と、設計の質に少しずつ投資し続ける 戦略的プログラミング を対比し、開発時間の 10〜20% 程度 を設計の改善に投資することを勧めています。

    負債と進化の視点

    設計への投資を怠ると、後で払う「利子」が積み上がります。この考え方はアーキテクチャの単位では 技術的負債、進化的アーキテクチャと適応度関数 で扱っています。

    7.2 チームで設計を守る

    設計は、一人が正しく作っても、チームで守られなければ崩れていきます（→ チームで設計を守る）。

    • ユビキタス言語 と用語集で、言葉をそろえる（→ 戦略的設計とユビキタス言語、用語集と推奨図書）
    • 設計レビュー で、判断の理由を共有する（→ レガシーと設計レビュー、レビュー観点）
    • ADR（Architecture Decision Record：決定とその理由を短く記録する文書）で、決定の理由を残す（→ 意思決定とADR）
    • 静的解析・アーキテクチャテスト で、依存のルールを自動で守らせる（→ 進化的アーキテクチャと適応度関数）
    • よくある失敗 を知っておく（→ チームで設計を守る、チェックリストとアンチパターン）

    8.2020年代の論点

    論点内容
    結合を「バランス」で考えるVlad Khononov『Balancing Coupling in Software Design』（2024）は、結合を「ゼロにすべきもの」ではなく、強さ・距離・変動性 の3つでバランスを取るものとして整理した（43_モジュール設計 で扱う。結合の測り方は 結合の指標 も参照）
    型駆動設計の普及TypeScript の普及により、「ありえない状態を表現できなくする」「検証するな、解析せよ」といった関数型由来の型設計が、一般の Web 開発でも使われるようになった（→ 型でドメインを表す）
    協働的モデリングの定着イベントストーミング・ドメインストーリーテリング・DDD Crew のキャンバス群など、業務の専門家と開発者が一緒にモデルを作る手法が体系化された（→ イベントストーミング、ドメインストーリーテリングと例示マッピング）
    AI と設計AI コーディングアシスタントがコードを大量に書く時代には、「どう書くか」より 「何を・どこで分けるか」という設計判断 と、設計のルールを機械が検査できる形で残すこと（型・テスト・アーキテクチャテスト）の価値が高まっている。明確なモジュール境界と型は、人間だけでなく AI にとっての 認知負荷 も下げる

    3. 30_ドメイン駆動設計 — イベントストーミング で業務を発見し、コアドメインとサブドメイン で力の入れどころを決め、戦術的設計 で作る
    4. 40_イベント駆動設計 — ドメインイベントでつなぐ（イベント駆動設計）
    5. 50_設計プロセス / 60_チームと品質 — 進め方・守り方・直し方（設計の進め方と段階的な深化・テストとリファクタリング・チームで設計を守る・レガシーと設計レビュー）

    10.よくある誤解

    誤解1：「設計はコードを書く前に完成させるもの」

    誤りです。設計は段階的に深め、リファクタリングで育て続けるものです（→ 設計の進め方と段階的な深化）。

    誤解2：「クラスや関数を小さく分けるほど良い設計」

    誤りです。インターフェースが単純で多くを隠す 深いモジュール が良い設計です。浅い部品を増やすと、かえって複雑さが増えます（4.3）。

    誤解3：「オブジェクト指向と関数型は対立する」「DDD は全部に戦術パターンを使うこと」

    どちらも誤りです。オブジェクト指向と関数型の目的は同じ（影響範囲を狭める）で、現代は組み合わせて使います。DDD で力を入れるのはコアだけで、DDD の本質は戦略的設計と協働的モデリングです。

    誤解4：「設計原則は守れば守るほど良い」「良い設計は個人のセンス」

    どちらも誤りです。原則同士もトレードオフになるので、YAGNI とのバランスが必要です。また、良い設計は複雑さの症状（変更の増幅・認知負荷・知らないことを知らない）として 言語化・検証 できます。

    11.まとめ

    • ソフトウェア設計は、要求からソフトウェアの 内部構造の記述 を作る活動。42 はアーキテクチャと詳細設計の 間をつなぐ共通の考え方 を扱う
    • 良い設計の物差しは 変更しやすさ。その敵は 複雑さ（変更の増幅・認知負荷・知らないことを知らない）で、原因は依存と不明瞭さ
    • 設計原則はすべて複雑さとの戦い方。出発点は Parnas の 「変わりそうな設計判断を隠す」、発展形が Ousterhout の 深いモジュール
    • パラダイムは「どう書くか」の道具箱（OOP は状態を隠し、関数型は状態を持たない）。DDD は「何を中心に設計するか」の考え方で、力を入れるのはコアだけ
    • 設計は一度で決めず、段階的に深め、テストとリファクタリングで育て、チームの仕組み（言葉・レビュー・ADR・自動検査）で守る
