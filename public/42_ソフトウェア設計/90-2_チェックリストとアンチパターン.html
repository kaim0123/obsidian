    90 付録

    チェックリストとアンチパターン — 設計を点検し、典型的な失敗を避ける

    設計レビューや自己点検に使える総合チェックリストと、設計で避けたい代表的なアンチパターンの一覧です。どの項目も、詳しく説明しているページへリンクしています。「どの場面でどこを見るか」の使い分けも載せています。

    もとにしたノート：付録B_チェックリスト / 付録E_アンチパターン一覧

    1.このページで扱うこと

    • ソフトウェア設計チェックリスト（総合版）：基本原則・構造と境界・ドメインと DDD・変化と拡張・連携とイベント・テストと品質・チームと文書の 7 分野
    • チェックリストの使い方：新機能の前・リファクタリングの前など、場面ごとに重点的に見る分野
    • アンチパターン一覧：アンチパターン（よくある悪い設計のパターン）を 構造系・クラス／オブジェクト系・抽象化系・データ／状態系・プロセス／組織系 に分け、説明と対策を並べたもの

    チェックリストとアンチパターンの関係

    チェックリストは「良い状態になっているか」を確かめる表、アンチパターンは「悪い状態の典型」を並べた表です。たとえばチェック項目「神クラス・神サービスがない」に引っかかったら、アンチパターン一覧の「神クラス」「神サービス」の対策を見る、というように行き来して使います。

    2.ソフトウェア設計チェックリスト（総合版）

    設計レビューや自己点検に使えるチェックリストです。各項目が満たされているかを確認し、分からない項目は右の列のページで考え方を確認してください。

    2.1 基本原則

    ✓チェック項目解説ページ
    ☐異なる関心は分離されている（SoC）関心の分離
    ☐各部品は 1 つの目的にまとまっている（高凝集）凝集度と結合度
    ☐部品間の依存は最小限（低結合）凝集度と結合度
    ☐内部実装は隠蔽されている（カプセル化）カプセル化と情報隠蔽
    ☐依存の方向は内側（ドメイン）向き依存性のルールとクリーンアーキテクチャ（41章）、依存性逆転の原則（41章）

    2.2 構造と境界

    ✓チェック項目解説ページ
    ☐モジュール・レイヤーの境界が明確関心の分離、層化・三層・レイヤード（41章）
    ☐循環依存（A が B に、B が A に依存し合う状態）がない凝集度と結合度、チームで設計を守る
    ☐公開 API の表面積（外から呼べる操作の数・範囲）は最小限カプセル化と情報隠蔽
    ☐命名が意図を表している戦略的設計とユビキタス言語
    ☐ディレクトリ構成が設計意図を反映しているチームで設計を守る、垂直スライスアーキテクチャ（41章）

    2.3 ドメインと DDD

    ✓チェック項目解説ページ
    ☐ユビキタス言語がコードに反映されている戦略的設計とユビキタス言語
    ☐業務ルールはドメイン層にあるドメイン層とユースケース
    ☐神クラス・神サービスがないチームで設計を守る（よくある設計の失敗）
    ☐貧血ドメインモデルになっていない戦術的設計の全体像
    ☐集約の境界が整合性と一致している集約とリポジトリ

    2.4 変化と拡張

    ✓チェック項目解説ページ
    ☐変わりやすい箇所が隔離されている変化に強い設計
    ☐拡張は既存コードの変更なしで可能か（OCP）SOLIDとオブジェクト指向
    ☐過剰な抽象化・パターン乱用がない（YAGNI）変化に強い設計
    ☐技術的負債が可視化されている設計の進め方と段階的な深化、技術的負債（41章）

    2.5 連携とイベント

    ✓チェック項目解説ページ
    ☐同期/非同期の選択に理由があるイベント駆動設計、同期API・メッセージ・イベント駆動（41章）
    ☐イベントは過去形の事実として設計されているドメインイベント
    ☐冪等性が考慮されているイベント駆動設計
    ☐結果整合性が UI・業務と合意されているイベント駆動設計

    2.6 テストと品質

    ✓チェック項目解説ページ
    ☐主要な振る舞いが単体テスト可能テストとリファクタリング
    ☐副作用は境界に押し出されている関数型と純粋関数
    ☐テストが書きにくい箇所に設計改善の候補がないか確認したテストとリファクタリング

    2.7 チームと文書

    ✓チェック項目解説ページ
    ☐重要な設計判断が記録されている（ADR 等）チームで設計を守る、意思決定とADR（41章）
    ☐設計ルールがチームで共有されているチームで設計を守る
    ☐新人が全体像を把握できる説明があるチームで設計を守る、C4モデルとarc42（41章）

    2.8 チェックリストの使い方

    毎回すべてを見る必要はありません。場面に応じて重点を変えます。

    場面重点的に見る分野
    新機能前1〜4 を中心に確認（基本原則・構造と境界・ドメインと DDD・変化と拡張）
    リファクタリング前1〜3 と 6（基本原則・構造と境界・ドメインと DDD・テストと品質）
    分散化検討時5 を重点的に（連携とイベント）
    定期レビュー全体を通しで

    レビューの進め方そのものはレガシーと設計レビューで説明しています。

    3.よくあるアンチパターン一覧

    設計で避けたいアンチパターンの一覧です。「説明」で症状を、「対策」で抜け出し方を確認し、詳しくは解説ページを読んでください。

    3.1 構造系

    アンチパターン説明対策解説ページ
    大泥団（Big Ball of Mud）境界のない巨大モデルコンテキスト・モジュール分割戦略的設計とユビキタス言語、チームで設計を守る
    スパゲッティコード制御フローが絡み合う構造化・関心の分離ソフトウェア設計を学ぶ理由、手続き指向設計
    循環依存A→B→A の依存インターフェース・イベントで解消凝集度と結合度

    3.2 クラス・オブジェクト系

    アンチパターン説明対策解説ページ
    神クラス（God Object）すべてを担当する巨大クラスSRP で分割チームで設計を守る、SOLIDとオブジェクト指向
    神サービスすべてを担当する ApplicationServiceユースケース・ドメインへ分散ドメイン層とユースケース
    貧血ドメインモデルエンティティがデータ入れ物振る舞いをドメインに移動戦術的設計の全体像
    スパゲッティ継承深く複雑な継承階層合成を検討継承と合成
    BaseClass 万能化基底クラスに全部入り継承の見直し継承と合成

    3.3 抽象化系

    アンチパターン説明対策解説ページ
    過剰な抽象化使われない Interface の乱立YAGNI変化に強い設計、チームで設計を守る
    パターン乱用問題なくパターンを適用問題が見えてから適用チームで設計を守る
    Leaky Abstraction内部詳細の漏洩境界の見直しカプセル化と情報隠蔽

    3.4 データ・状態系

    アンチパターン説明対策解説ページ
    共有 mutable 状態どこからでも書き換え可能（mutable＝変更可能）カプセル化・不変性カプセル化と情報隠蔽、関数型と純粋関数
    魔法の数字・文字列意味不明の定数名前付き定数・値オブジェクトエンティティと値オブジェクト
    共有データベースモジュール間で DB を直接共有API・イベントで連携データ所有権とSAGA（41章）

    3.5 プロセス・組織系

    アンチパターン説明対策解説ページ
    設計なき成長境界なしに機能追加定期的な設計レビューレガシーと設計レビュー
    DDD っぽいだけ用語集だけ、ロジックはサービス層戦術的設計の実践戦術的設計の全体像
    早すぎるマイクロサービス化境界が曖昧なまま分散モジュラーモノリス（1つのアプリの中をモジュールできれいに分けた構成）からモノリスとマイクロサービス（41章）

    クラス設計のアンチパターンは、44_クラス設計・デザインパターン の第18章「アンチパターン」でさらに詳しく扱っています。

    4.よくある誤解

    誤解1：「チェックリストを全部満たせば良い設計だ」

    チェックリストは見落としを防ぐための道具で、合格点を付けるものではありません。たとえば「拡張は既存コードの変更なしで可能か（OCP）」と「過剰な抽象化がない（YAGNI）」はぶつかることがあり、どちらを優先するかは状況で判断します。

    誤解2：「アンチパターンを見つけたら、すぐ全部直すべき」

    対策にもコストがかかります。変更が頻繁で困っている箇所から順に、テストで守りながら少しずつ直すのが現実的です（→ テストとリファクタリング）。

    5.まとめ

    • チェックリストは 基本原則・構造と境界・ドメインと DDD・変化と拡張・連携とイベント・テストと品質・チームと文書 の 7 分野
    • 場面で使い分ける：新機能前は 1〜4、リファクタリング前は 1〜3 と 6、分散化検討時は 5、定期レビューは全体
    • アンチパターンは 構造系・クラス／オブジェクト系・抽象化系・データ／状態系・プロセス／組織系 の 5 系統。症状（説明）と抜け出し方（対策）をセットで覚える
    • チェック項目に引っかかったら、対応するアンチパターンと解説ページを行き来して改善策を考える
