    境界づけられたコンテキスト — 意味のまとまりで区切り、関係を地図にする

    大きなシステムでは、同じ「顧客」「商品」「ユーザー」が場所によって違う意味を持ちます。DDD の戦略設計では、そうした意味のまとまりを境界づけられたコンテキストとして切り出し、コンテキスト同士の関係をコンテキストマップで可視化します。なぜ区切るのか、境界の見つけ方、関係のパターン（特に腐敗防止層）、モノリスとマイクロサービスでの使い方、実装のポイントを解説します。

    もとにしたノート：03_境界づけられたコンテキストとコンテキストマップ / 04_境界づけられたコンテキスト

    1.このページで扱うこと

    大きなシステムでは、同じ単語が領域によって違う意味を持つことがよくあります。DDD の戦略設計では、そうした「意味のまとまり」を境界づけられたコンテキスト（Bounded Context）として切り出し、コンテキスト同士の関係をコンテキストマップで可視化します。

    • なぜ区切るのか — 全部入りのモデルの問題
    • 境界づけられたコンテキストとは、ユビキタス言語との関係
    • コンテキストを見つける方法
    • コンテキストマップと、コンテキスト間の関係パターン（特に腐敗防止層）
    • EC サイトの分割例、モノリス・マイクロサービスとの関係
    • 実装のポイントと、小さな練習のしかた

    パターンの細かい暗記より、「なぜ区切るのか」「図の読み方」を重視します。前提：DDDとは、戦略的設計とユビキタス言語。

    2.なぜ区切るのか — 同じ言葉でも意味が違う

    2.1 同じ「顧客」でも意味が違う

    例えば社内システムで「顧客（Customer）」という言葉を考えます。

    コンテキスト「顧客」に含まれる情報・意味
    営業見込み客、商談ステータス、担当者
    会計請求先、与信限度、支払条件
    配送届け先住所、配送希望時間帯

    ほかにも、次のような例はどこにでもあります。

    • 「商品」… 販売時は「値段付きのもの」、倉庫内では「棚にある物体」、配送時は「梱包された荷物」
    • 「ユーザー」… 認証では「ログインできる人」、マーケティングでは「広告を見る人」、サポートでは「問い合わせ主」

    こうしたとき、無理に1つの『ユーザー』『商品』クラスでまとめないのが DDD の考え方です。

    2.2 無理に共通化するとどうなるか

    ✕ 悪い例：全部入りの User クラス 
    class User {
  // 認証情報
  email: string;
  password: string;
  // 購入履歴（ECの関心）
  orders: Order[];
  // 配送先（物流の関心）
  shippingAddresses: Address[];
  // マーケ情報（広告の関心）
  adPreferences: AdPref;
  // サポート履歴
  supportTickets: Ticket[];
  // ...全部1つに
}

    1つの巨大な User クラスや Customer テーブルに全部詰め込むと、次の問題が起きやすくなります。

    モデルの問題

    • クラスが肥大化する（フィールドが増え続け、誰も全体像を把握できない）
    • 変更の影響範囲が広すぎる（営業の変更が会計に副作用を起こす）
    • テストが重い
    • どこで何に使われているか追えない

    チームの問題

    • チーム間で衝突する
    • チーム間で「顧客とは何か」の議論が終わらない

    2.3 境界を引いて分ける

    同じ人物を、コンテキストごとに違うモデルで表現し、それぞれ必要な情報だけを持ちます。

    境界づけられたコンテキストの考え方

    「この言葉・このモデルは、この境界の中ではこの意味」と、意味のまとまりごとに範囲を区切る設計単位です。

    3.境界づけられたコンテキストとは

    3.1 定義

    境界づけられたコンテキスト（Bounded Context, BC）とは、次の3つを満たす独立した意味空間です。

    • 一貫したユビキタス言語（現場と開発で共有する用語）が使われる
    • その言葉に対応したモデル（クラス・テーブル・API）が閉じている
    • 外のコンテキストとは、はっきり境界がある

    営業コンテキスト

    Prospect（見込み客）、Deal（商談）…

    ここでは「顧客」は見込み・商談の文脈

    会計コンテキスト

    BillTo（請求先）、Invoice（請求書）…

    ここでは「顧客」は請求・与信の文脈

    1つの BC の中では、用語とモデルは矛盾なく使えるようにします。BC の外とは、翻訳（変換）を挟んで連携するのが基本です。

    3.2 「コンテキスト」とは何の範囲か

    ここでいうコンテキストとは、次のような範囲のことです。

    • 1つの業務の範囲
    • 用語の意味が一貫している範囲
    • 同じチームが扱う範囲
    • 独立して変更できる範囲

    抽象的ですが、実務では「サブシステム」や「マイクロサービス」に近いものと考えて OK です（ただし同じものではありません。8章）。

    3.3 ユビキタス言語は BC ごとに定義する

    BC を語るうえで欠かせないのがユビキタス言語（開発者とビジネス側が、同じ言葉で同じものを指すこと）です。

    • コードのクラス名・メソッド名に、現場の用語をそのまま使う
    • 「ユーザー」「会員」「顧客」のような曖昧な言い換えを、BC 内では統一する

    ユビキタス言語は BC ごとに定義されます。営業 BC と会計 BC で「顧客」の呼び方や属性が違っても、それぞれの中で一貫していればよいのです。ユビキタス言語そのものは 戦略的設計とユビキタス言語 で詳しく扱っています。

    4.コンテキストを見つける方法

    ヒント1：言葉の意味がズレる境目

    「このチームでは『商品』の意味が違う」と気づいたら、そこが境界。

    ヒント2：チーム・部署の境目

    組織構造がコンテキストを反映することが多い（コンウェイの法則 → 41章）。

    ヒント3：変更の頻度・理由

    同じ理由で変わる部分はまとめ、違う理由で変わる部分は分ける（SRP と同じ発想）。

    ヒント4：ライフサイクル

    別々のタイミングでデプロイ・リリースするなら、別のコンテキストかも。

    5.コンテキストマップとは

    コンテキストマップ（Context Map）は、複数の BC 同士がどう関係しているかを図にしたものです。

    マップを描くと、次のことが議論しやすくなります。

    • どこが「上流」で、どこが「下流」か（上流＝モデルや情報を提供する側、下流＝それに依存する側）
    • データを誰が所有しているか（サービス間のデータ所有権は41章の データ所有権と SAGA を参照）
    • 連携は API か、イベントか、バッチか

    6.コンテキスト間の関係パターン

    全部覚える必要はありません。よく出るものだけ押さえます。

    パターンイメージ例
    共有カーネル（Shared Kernel）一部のモデルを2つ以上の BC で共有する。変更には両チームの合意が必要共通の「金額」「通貨」型
    顧客／供給者（Customer-Supplier）上流が下流のために情報を提供し、下流は上流の API・モデルに依存する会計が営業の顧客 ID を参照
    順応者（Conformist）下流が上流のモデルに合わせきる。合わせるしかない関係（相手が強い）外部 SaaS のデータ形式に完全準拠
    腐敗防止層（Anti-Corruption Layer, ACL）外部のモデルを自 BC の言葉に翻訳する変換層を挟み、外部の都合に汚染されないようにするレガシー API をラップして自社用 DTO に変換
    公開ホストサービス（Open Host Service）標準化した公開 API を広く提供する共通の「注文照会 API」
    別々の道（Separate Ways）相互作用が少なく、連携せずそれぞれ完全に独立に実装する統合コストが利益を上回るとき

    6.1 まず覚えたい：腐敗防止層（ACL）

    初心者がまず覚えるとよいのは ACL（腐敗防止層）です。外の世界の言葉やモデルが、自コンテキストのきれいなモデルを汚さないように、翻訳の層を挟む — これはレガシー連携でもマイクロサービス間でも頻出です。

    外部の古い API（自分では変えられない） 
    interface LegacyUserAPI {
  getUsr(id: string): { uName: string; eAddr: string };
}
    ◯ 自社のコンテキストにとって良い形に変換する 
    class LegacyUserAdapter {
  constructor(private legacy: LegacyUserAPI) {}
  findUser(id: string): User {
    const raw = this.legacy.getUsr(id);
    return new User(raw.uName, raw.eAddr); // 自社の言葉に翻訳
  }
}

    getUsr や uName のような外部の言葉は ACL の中に閉じ込められ、自社のコードは findUser と User だけを使います。

    7.具体例：EC サイトのコンテキスト分割

    各コンテキストは独立した言葉を持ちます。注文の「商品」と配送の「商品」は別モデルです。

    8.モノリスでもマイクロサービスでも使える

    8.1 マイクロサービスとの関係

    境界づけられたコンテキストは、マイクロサービスの分割単位としてしばしば採用されます。

    • 1コンテキスト ＝ 1マイクロサービス
    • コンテキスト間の通信 ＝ REST / gRPC / メッセージング

    モノリスとマイクロサービスの比較や分割の判断は、41章の モノリスとマイクロサービス で扱っています。

    8.2 モノリスの中でも区切れる

    ただし、コンテキスト ≠ マイクロサービスです。1つのデプロイ単位（モノリス）の中でも、フォルダ・パッケージ・モジュールで BC を分けることはよくあります。

    src/
├─ sales/          ← 営業 BC（フォルダ・パッケージで境界）
│   ├─ domain/
│   └─ application/
├─ accounting/     ← 会計 BC
│   ├─ domain/
│   └─ application/
└─ shared-kernel/  ← 共有する最小限の型だけ

    このように区切っておくと、後からサービス分割する際の地図にもなります。

    9.実装のポイント

    9.1 コンテキスト間でモデルを共有しない

    ✕ 全コンテキストで同じ User 
    import { User } from '@shared/User';
    ◯ 各コンテキストで独自モデル 
    import { User } from './auth/User';
import { Customer } from './ordering/Customer';

    9.2 通信は小さな DTO で

    コンテキストをまたいで渡すデータは、最小限の DTO（Data Transfer Object：データを運ぶためだけの入れ物）で渡します。モデルをそのまま渡しません。

    9.3 翻訳層を設ける

    外部コンテキストからのデータは、腐敗防止層で自社の言葉に変換します（6.1）。

    9.4 同じ ID でも別モデル

    同じ「user_id=123」でも、コンテキストごとに違うクラス（User の ID 型 / Customer の ID 型）で扱います。

    10.小さな練習のしかた

    1. 自分のプロジェクトで3つ以上の「言葉がブレやすい用語」を書き出す（例：ユーザー、注文、商品）
    2. それぞれどの業務の文脈かを分ける
    3. 紙に四角（BC）と矢印（関係）を描く
    4. 誰がデータの正（ソース・オブ・トゥルース）を持つかを1行ずつメモする

    これだけで、コンテキストマップの入門は十分です。

    11.よくある誤解

    誤解1：「大きなドメインを1つのモデルで表現できる」

    できません。分割してこそ DDD です。全部入りのモデルは肥大化し、変更の影響範囲が広がり、チームが衝突します。

    誤解2：「BC は必ずマイクロサービス」「BC は DB テーブルの境界と同じ」

    BC はモノリス内のモジュール境界でもかまいません。また、DB のテーブル境界とも必ずしも一致しません。同じテーブルを違うコンテキストから違う意味で読むこともあります。

    誤解3：「最初から完璧なマップを描き、境界はずっと変えない」

    マップは進化させながら更新するもので、初版は「だいたい」でかまいません。境界も時間とともに変わります。業務が進化すれば、境界も引き直します。

    誤解4：「1 BC に必ず1チーム」「全部つなぐべき」

    1 BC に1チームは目安にはなりますが、小さければ1チームが複数 BC を持つこともありえます。また、別々の道（連携しない）も正当な選択です。

    12.まとめ

    • 同じ言葉が場所によって違う意味を持つとき、無理に1つのモデルにまとめない
    • 境界づけられたコンテキストは、一貫したユビキタス言語とモデルが閉じた独立した意味空間。外とは翻訳を挟んで連携する
    • 境界は、言葉のズレ・チームの境目・変更の理由・ライフサイクルから見つける
    • コンテキストマップで上流／下流、データの所有者、連携方法を明らかにする
    • 関係パターンのうち、まず腐敗防止層（ACL）を覚える
    • BC はマイクロサービスの分割単位によく使われるが、モノリスの中のフォルダでも区切れる
    • モデルは共有せず、小さな DTO と翻訳層で連携する。境界は業務とともに引き直す
