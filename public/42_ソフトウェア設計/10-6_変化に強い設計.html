    10 設計の基礎

    変化に強い設計 — 予測より隔離、作りすぎない

    ソフトウェアは必ず変わります。このページでは、変化を前提にした設計の考え方として、変わりやすい箇所を境界で囲む「変化の隔離」、変更理由を1つに絞る「変化の理由」、拡張に開き変更に閉じる「OCP」、作りすぎを戒める「YAGNI」を学び、原則同士がぶつかったときの優先順位の目安を示します。

    もとにしたノート：10_設計の基礎/07_変化に強い設計の考え方

    1.このページで扱うこと

    リリースした瞬間から、割引ルールの追加、画面の作り直し、外部サービスの乗り換えといった変更依頼がやってきます。変化を避けることはできないので、変化が来ても壊れにくい形 にしておくことが設計の大きな目的になります。

    このページでは次の内容を扱います。

    • 変化の予測と変化の隔離
    • 変化の理由（Reason for Change）：単一責任の原則の基礎
    • 拡張に開き、変更に閉じる（OCP の入門）
    • YAGNI と過剰設計のバランス
    • 設計原則の優先順位のつけ方

    2.変化の予測と変化の隔離

    2.1 変化の予測

    すべての変化を当てることはできません。しかし、変わりやすい箇所 は経験的に分かります。

    • 業務ルール（割引条件、承認フロー）
    • UI・画面仕様
    • 外部連携（API、DB、メール送信）
    • 性能要件

    2.2 変化の隔離

    変化の隔離 とは、変わりやすい部分を境界で囲み、変わりにくい部分への波及を防ぐ ことです。

    Strategy は、割引計算のような「やり方」を差し替え可能な部品として切り出すデザインパターンです。Repository は、データの保存・取得を窓口にまとめ、DB の種類を業務ロジックから隠す部品です。

    予測より隔離

    変化を当てる（予測）ことより、変わりやすい箇所を 隔離 しておくことを重視するのが現実的です。

    3.変化の理由（Reason for Change）

    1 つの部品が、複数の理由で変更される と設計が脆くなります。これは単一責任の原則（SRP：1つの部品が変更される理由は1つであるべき、という原則）の基礎でもあります。

    悪い例問題
    Report クラスが PDF 出力と Excel 出力の両方を担当出力形式の変更理由が 2 つ
    UserService が認証とプロフィール更新を担当セキュリティ変更と UI 変更が混在

    「この部品は何のために変更されるか？」 を 1 つに絞る意識が有効です。SRP の詳細は 44_クラス設計・デザインパターンの SRP 章、および SOLIDとオブジェクト指向 を参照してください。

    4.拡張に開き、変更に閉じる（OCP の入門）

    開放閉鎖の原則（Open-Closed Principle, OCP） とは、

    拡張に対しては開いており、変更に対しては閉じているべき

    という原則です。新しい機能は「既存コードを書き換える」のではなく「新しいコードを足す」ことで実現できるようにしておく、という意味です。

    ✕ 悪い例：新しい支払い方法のたびに if 文を追加 
    if (type === 'credit') { ... }
else if (type === 'paypal') { ... }  // 毎回既存コードを変更
    ◯ 良い例：新しい支払い方法は新クラスを追加（既存コードは変更しない） 
    PaymentMethod インターフェース
  ├── CreditCardPayment
  ├── PayPalPayment
  └── NewPayment  ← 追加するだけ

    支払い処理を呼ぶ側は PaymentMethod というインターフェースだけを知っているので、新しい支払い方法を追加しても呼ぶ側のコードは変わりません。OOP での詳細は SOLIDとオブジェクト指向 を参照してください。

    5.YAGNI と過剰設計のバランス

    YAGNI（You Aren't Gonna Need It） = 「今必要ないものは作らない」という考え方です。

    過剰設計適切な設計
    将来の 10 機能分の抽象化を先に作る今必要な分だけ。拡張点は変化が見えたら追加
    使われないインターフェースが大量実際に差し替える箇所だけ抽象化

    実践的な落としどころ

    変化を隔離する意識は持ちつつ、必要になるまで作らない のが実践的です。

    6.設計原則の優先順位のつけ方

    原則同士が衝突することがあります。初心者向けの優先の目安です。

    1. 読める・理解できる — 過度な抽象化より明確さ
    2. 関心の分離・高凝集・低結合 — 基本の物差し（関心の分離、凝集度と結合度）
    3. 変化の隔離 — 変わりやすい箇所を特定して境界を引く
    4. SOLID 等の原則 — 具体化の指針（詳細は 44_クラス設計・デザインパターン、SOLIDとオブジェクト指向）
    5. パターンの適用 — 問題が見えてから

    目的を取り違えない

    「原則に従った」が目的ではありません。「変更しやすく、理解しやすい」 が目的です。

    7.よくある誤解

    誤解1：「変化に強くするには、将来の変更を全部予測して備えておくべき」

    すべての変化を当てることはできません。予測ではなく、変わりやすい箇所を境界で囲む「隔離」を重視するのが現実的です。先回りして作りすぎると、YAGNI に反する過剰設計になります。

    誤解2：「YAGNI だから設計しなくてよい」

    YAGNI は「今必要ないものは作らない」であって、「考えない」ではありません。設計しなければスパゲッティ・変更恐怖に向かいます。変化を隔離する意識は持ちつつ、必要になるまで作らない、が正しいバランスです。

    誤解3：「OCP なら既存コードは一切触ってはいけない」

    OCP は「拡張で対応し、既存コードの変更を減らす」ための指針です。拡張点（インターフェースなど）は変化が見えてから追加すればよく、そのために既存コードを整理するのは自然なことです。

    8.まとめ

    • 変化は避けられない。予測より 隔離 が現実的
    • 変化の理由は 1 つに絞る意識が有効（SRP の基礎）
    • OCP は拡張で対応し、既存コードの変更を減らす
    • YAGNI で過剰設計を避け、バランスを取る
    • 原則の目的は「変更しやすく、理解しやすい」こと
