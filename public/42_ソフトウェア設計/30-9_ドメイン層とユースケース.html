    ドメイン層とユースケース — ルールはドメインに、手順はアプリケーションに

    クリーンアーキテクチャの同心円にある Entities と Use Cases を、DDD では「ドメイン層」と「アプリケーション層（ユースケース／アプリケーションサービス）」という言葉で語ります。それぞれの層に何を置き、何を置かないか、ドメインサービスとの違い、クリーンアーキテクチャとの対応、フォルダ構成の例、そして貧血ドメインモデルと太ったユースケースという落とし穴を解説します。

    もとにしたノート：06_ドメイン層とユースケースとアプリサービス

    1.このページで扱うこと

    41章のクリーンアーキテクチャでは、同心円の中に Entities と Use Cases がありました。DDD では、同じ領域をドメイン層・アプリケーション層（ユースケース／アプリケーションサービス）という言葉で語ります。

    このページでは、層（同心円）の中身を DDD の用語で整理し、どこに何を書くかを説明します。層の構造そのもの（依存性のルールなど）は41章で扱っているので、ここでは「各層に何を置くか」という設計の観点に絞ります。前提として DDDとは と、41章のクリーンアーキテクチャを読んでおくと理解しやすくなります。

    2.全体像 — 3つの役割

    ノートでは上から下へ並べて描かれていますが、依存の向きは変わりません。内側（ドメイン）が外側を知らないのが原則です。インフラ層はドメイン層の下に描かれていても、実際にはドメイン層が定義したインターフェース（リポジトリなど）を実装する「外側」です（依存性逆転の原則）。

    3.ドメイン層 — ビジネスの心臓部

    ドメイン層には、その業務領域のルールとモデルだけを置きます。

    3.1 置くもの

    種類役割例
    エンティティID で識別され、状態が変わるものOrder, Patient
    値オブジェクト値そのもので意味が完結Money, EmailAddress, DateRange
    集約不変条件を守るまとまり（詳細は 戦術的設計の全体像）Order + OrderLine
    ドメインサービス1つのエンティティに収まらないドメインの処理複雑な料金計算、在庫引当ルール
    ドメインイベントドメイン内で起きた「事実」OrderPlaced, PaymentFailed
    リポジトリ（インターフェース）集約の永続化の抽象（実装はインフラ）OrderRepository

    各部品の詳細は エンティティと値オブジェクト、集約とリポジトリ、ドメインイベント を参照してください。

    3.2 置かないもの

    • SQL や HTTP の知識
    • フレームワーク固有のアノテーション（@Entity のような、クラスに付ける目印。可能なら）
    • 「画面に何を表示するか」の都合
    // ドメイン層の例 — ルールはここに
class Order {
  private constructor(
    readonly id: OrderId,
    private status: OrderStatus,
    private lines: OrderLine[],
  ) {}

  cancel() {
    if (this.status !== OrderStatus.Pending) {
      throw new Error('確定済みの注文はキャンセルできません');
    }
    this.status = OrderStatus.Cancelled;
  }
}

    「この注文はキャンセルできるか」はドメインの知識です。DB の更新方法は知りません。

    4.ユースケース — 1つの業務操作

    ユースケース（Use Case）は、クリーンアーキテクチャの Use Cases と同じ考え方です。

    アプリケーションが提供する、1つの具体的な業務操作

    例：「注文を確定する」「ユーザーを登録する」

    4.1 ユースケースの責務

    1. 入力を受け取り、ドメインオブジェクトに変換する
    2. ドメイン層を呼び出し、ルールを実行する
    3. リポジトリや外部サービス（インターフェース経由）で永続化・通知する
    4. 結果を出力用の形にまとめる
    // アプリケーション層（ユースケース）の例
class PlaceOrderUseCase {
  constructor(
    private orderRepo: OrderRepository,
    private paymentGateway: PaymentGateway, // インターフェース
  ) {}

  async execute(input: PlaceOrderInput): Promise<PlaceOrderOutput> {
    const order = Order.create(input.lines);
    await this.paymentGateway.charge(order.total());
    await this.orderRepo.save(order);
    return { orderId: order.id.value };
  }
}

    ユースケースは「手順」を書きますが、ビジネスルールの詳細は Order などドメイン層に任せます。

    5.アプリケーションサービス — 名前の違いと実務

    DDD の文献やフレームワークによって、ユースケースとアプリケーションサービス（Application Service）がほぼ同義で使われることが多いです。

    呼び方よく見る文脈
    ユースケースクリーンアーキテクチャ、Execute メソッド1つ
    アプリケーションサービスDDD 本家、Spring の @Service など

    このページでは、どちらも「アプリケーション層で、1業務操作を orchestrate（指揮）するクラス」と捉えてかまいません。

    アプリケーション層に置いてよいこと

    • トランザクションの開始・コミット（フレームワークに委譲することも多い）
    • 認可チェック（「このユーザーはこの操作をしてよいか」）
    • 複数集約にまたがる手順の組み立て
    • ドメインイベントの発行指示

    アプリケーション層に置きすぎないこと

    • 料金計算の詳細、在庫の引当ルールなどドメインの本質的ルール
    • SQL 文、HTTP クライアントの直接呼び出し

    迷ったときの判断基準

    「そのルールは、専門家がホワイトボードで説明する内容か？」 Yes ならドメイン層、No（手順・連携）ならアプリケーション層、と切るとよいです。

    認可の考え方など、層をまたぐ関心事は41章の 横断的関心事と認証認可 で扱います。

    6.ドメインサービスとの違い

    名前に「サービス」が付くので混同しやすいですが、ドメインサービスとアプリケーションサービスは置き場所も中身も違います。

    ドメインサービスアプリケーションサービス／ユースケース
    層ドメイン層アプリケーション層
    中身純粋なビジネスルール手順・連携・永続化
    状態通常ステートレス（状態を持たない）リポジトリなどを注入
    例2つの集約にまたがる引当ルールの計算「注文確定」フロー全体
     
    // ドメインサービス — ルールそのもの
class ShippingFeeCalculator {
  calculate(order: Order, destination: Address): Money {
    // 距離・重量・会員ランクに基づく料金計算（ビジネスルール）
  }
}

// ユースケース — 手順
class PlaceOrderUseCase {
  async execute(input) {
    const fee = this.feeCalculator.calculate(order, input.address);
    order.applyShippingFee(fee);
    await this.orderRepo.save(order);
  }
}

    送料の計算方法（距離・重量・会員ランク）は専門家が説明するルールなのでドメインサービスに、「計算して、注文に反映して、保存する」という流れはユースケースに置きます。

    7.クリーンアーキテクチャとの対応表

    クリーンアーキテクチャDDD での呼び方主な内容
    Entitiesドメイン層（エンティティ、値オブジェクト、集約）ビジネスルール
    Use Casesアプリケーション層（ユースケース／アプリケーションサービス）業務操作の手順
    Interface Adaptersプレゼンテーション層、インフラの一部HTTP ↔ ユースケースの変換
    Frameworks & Driversインフラ層DB, Web フレームワーク

    図の名前は違っても、依存の向きと責務の分け方は同じ家族です。ポートとアダプタで同じことを表すヘキサゴナルアーキテクチャでも、六角形の中心にあるのはドメインとユースケースです。

    8.フォルダ構成の例

    src/
├─ domain/                    ← ドメイン層
│   ├─ order/
│   │   ├─ Order.ts           （集約ルート）
│   │   ├─ OrderLine.ts
│   │   ├─ OrderRepository.ts （インターフェース）
│   │   └─ OrderPlaced.ts     （ドメインイベント）
│   └─ shared/
│       └─ Money.ts
├─ application/               ← アプリケーション層
│   └─ order/
│       ├─ PlaceOrderUseCase.ts
│       └─ CancelOrderUseCase.ts
├─ infrastructure/            ← インフラ層
│   └─ persistence/
│       └─ SqlOrderRepository.ts
└─ presentation/              ← プレゼンテーション層
    └─ OrderController.ts

    リポジトリのインターフェース（OrderRepository.ts）は domain/ に、実装（SqlOrderRepository.ts）は infrastructure/ に分かれている点がポイントです。層の分け方そのものは41章の 層化・三層・レイヤード も参考になります。

    9.よくある落とし穴

    9.1 貧血ドメインモデル（Anemic Domain Model）

    エンティティがgetter/setter だけで、ルールが全部サービス層に漏れている状態です。

    ✕ 避けたい例：Order はただのデータ入れ物 
    class Order {
  status: string;
}
// ルールは全部 PlaceOrderService の中に…

    振る舞い（メソッド）をドメインオブジェクトに持たせるのが DDD の基本です。

    9.2 ユースケースが太りすぎる

    if 文が何十行も並ぶユースケースは、ルールがドメイン層から逃げ出しているサインです。ドメイン層へ引き戻すか、ドメインサービスに切り出します。

    10.よくある誤解

    誤解1：「ドメインサービスとアプリケーションサービスは同じもの」

    名前は似ていますが別物です。ドメインサービスはドメイン層にある純粋なビジネスルール、アプリケーションサービスはアプリケーション層にある手順・連携・永続化です。

    誤解2：「ユースケースとアプリケーションサービスは別の層」

    文献やフレームワークによる呼び方の違いで、ほぼ同義です。どちらも「アプリケーション層で1業務操作を指揮するクラス」と捉えてかまいません。

    誤解3：「DDD の層とクリーンアーキテクチャは別の考え方」

    図の名前は違っても、依存の向きと責務の分け方は同じ家族です。Entities ≒ ドメイン層、Use Cases ≒ アプリケーション層と対応します。

    11.まとめ

    • DDD では、クリーンアーキテクチャの Entities をドメイン層、Use Cases をアプリケーション層と呼ぶ。内側（ドメイン）は外側を知らない
    • ドメイン層：エンティティ・値オブジェクト・集約・ドメインサービス・ドメインイベント・リポジトリのインターフェース。SQL・HTTP・画面の都合は置かない
    • ユースケース：1つの業務操作の手順（入力 → ドメイン呼び出し → 永続化・通知 → 出力）。ルールの詳細はドメインへ
    • ユースケースとアプリケーションサービスはほぼ同義。トランザクション・認可・手順の組み立てはここ
    • 判断基準：「専門家がホワイトボードで説明する内容か？」Yes ならドメイン層
    • 落とし穴：貧血ドメインモデルと太りすぎたユースケース
