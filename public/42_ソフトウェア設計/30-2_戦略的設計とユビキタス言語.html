    戦略的設計とユビキタス言語 — システムの分け方と、全員で使う言葉

    DDD の戦略的設計は、大きなシステムを「モデルと用語が一貫する範囲」で区切り、その関係を明示する活動です。その土台になるのが、業務の人も開発者もコードもテストも同じ言葉を使う「ユビキタス言語」です。境界づけられたコンテキスト・コンテキストマップ・大泥団・コンウェイの法則の概要と、ユビキタス言語のつくり方・敵・効果を解説します。

    もとにしたノート：01_戦略的設計 / 02_ユビキタス言語

    1.このページで扱うこと

    DDD の戦略的設計 — 大きなシステムをどう区切るか — と、その土台になるユビキタス言語を学びます。

    • 境界づけられたコンテキスト（概要）
    • コンテキストマップ — 境界間の関係（概要）
    • 大泥団（Big Ball of Mud）を避ける
    • 組織と設計の関係（コンウェイの法則）
    • ユビキタス言語 — なぜ同じ言葉が大事か、どこで使うか、どうつくるか、何が敵か
    • 戦略的設計の進め方

    境界づけられたコンテキストとコンテキストマップの詳細は 境界づけられたコンテキスト、分けた部分への力の入れ方は コアドメインとサブドメイン で扱います。

    2.境界づけられたコンテキスト — 1つの巨大モデルに詰め込まない

    境界づけられたコンテキスト（Bounded Context）とは、特定のモデルと用語が有効な範囲です。同じ「商品」でも、コンテキストによって意味が異なります。

    コンテキスト「商品」の意味
    販売顧客に売るもの（価格・在庫）
    物流配送するもの（重量・サイズ）
    会計計上するもの（科目・税区分）

    戦略的設計の要点

    1つの巨大モデルに全部詰め込まない。コンテキストごとに「この言葉はここではこの意味」と決める。

    3.コンテキストマップ — 境界間の関係

    コンテキストマップは、コンテキスト同士の関係を図示したものです。代表的な関係は次のとおりです（全パターンと例は 境界づけられたコンテキスト を参照）。

    関係の種類意味
    共有カーネルモデルの一部を共有
    顧客/供給者下流が上流のモデルに依存
    腐敗防止層（ACL）外部モデルを自コンテキスト用に変換
    別々の道連携しない

    上の図のように、販売から物流へ OrderPlaced（注文された）をイベントまたは API で伝えるなど、境界を越えるときは変換・契約を明示します。

    4.大泥団（Big Ball of Mud）を避ける

    大泥団とは、境界のない単一モデルに全機能が詰め込まれた状態です。

    • 用語が文脈なく混在
    • 変更が全体に波及
    • チームが同じコードベースで衝突

    大泥団を避けるには

    コンテキストで「この言葉はここではこの意味」と決める。

    5.組織と設計の関係（コンウェイの法則）

    コンウェイの法則：システムの構造は、組織のコミュニケーション構造を反映する。

    戦略的設計は技術だけでなく組織設計とも関連します。組織とアーキテクチャの関係は41章の コンウェイの法則と Team Topologies で詳しく扱っています。

    6.ユビキタス言語

    6.1 ユビキタス言語とは

    ユビキタス言語（Ubiquitous Language）は、DDD の中で最も基本的で、最も重要な概念です。「ユビキタス」とは「どこにでも遍在する」という意味です。

    「業務の人も、設計者も、実装者も、ドキュメントも、コードも、テストも、全員が同じ言葉を使う」

    6.2 言葉がズレると何が起きるか

    次のような会話が毎回発生します。

    業務の人：「顧客から受注があったら、出荷指示を出してほしい」
開発者　：「じゃあ、User が Order して、Delivery を create するんですね」
業務の人：「『出荷』じゃなくて、『発送』のはずですけど…」
開発者　：「あ、Delivery じゃなくて Shipment でした」
業務の人：「あと『受注』と『注文』は別物です。『受注』は確定前の状態で…」

    しかも後日、コードを読んでも次のように混乱し続けます。

    • Order は「受注」？「注文」？
    • Delivery と Shipment はどう違う？
    • User は「顧客」なのか「従業員」も含むのか？

    6.3 ユビキタス言語があれば

    最初に用語をそろえて定義しておけば、こうしたズレが起きません。全員がこの定義に従って話し・書きます。

    受注 = Order(status: pending)
注文 = Order(status: confirmed)
発送 = Shipment
顧客 = Customer（User とは別）

    6.4 どこで「同じ言葉」を使うか

    ユビキタスという名のとおり、あらゆる場所で同じ言葉を使います。

    ① 会議・ディスカッション

    「顧客の発送対応で…」と口頭で話すときからそろえます。

    ② 仕様書・ドキュメント

    【発送処理の仕様】
顧客の注文が確定したら、発送指示書が発行される。

    ③ コード

    class Customer { /* ... */ }
class Order { /* ... */ }
class Shipment { /* ... */ }

class ShipmentService {
  createShipment(order: Order) { /* ... */ }
}

    コードのクラス名・メソッド名・変数名が、業務で使う言葉そのものになっています。

    ④ テスト

    test('注文が確定したら発送指示書が発行される', () => {
  const order = Order.confirm();
  const shipment = service.createShipment(order);
  expect(shipment).toBeDefined();
});

    テストコードの日本語も同じ言葉で書きます。

    ⑤ Git コミットメッセージ / PR タイトル

    feat: 発送指示書の発行処理を追加
fix: 顧客IDが空の場合にエラーを返す

    6.5 ユビキタス言語のつくり方

    1. 重要な概念を洗い出す — 業務の人と一緒に、登場する物・出来事・ルールを書き出す
    2. 意味を定義する — 例：顧客 ＝ 商品を購入する個人または法人／注文 ＝ 顧客が商品を指定して購入を申し込む行為
    3. 用語集（Glossary）を作る（下の例）
    4. 英語名も決める（下の例）
    5. コードに反映 — クラス名・変数名・関数名すべてを統一
    6. 育て続ける — 業務の新しい言葉が出てきたら即追加。古くなったら更新
    用語集の例（Markdown） 
    ## 用語集

### 顧客（Customer）
商品を購入する個人または法人。
ゲスト購入者（アカウントなし）も含む。

### 注文（Order）
顧客が商品を指定して購入を申し込む単位。
状態: pending → confirmed → shipped → delivered

### 発送（Shipment）
注文に対して物理的に商品を送り出す行為。
    英語名の決め方の例 
    顧客 = Customer（buyer, user ではない）
注文 = Order（purchase ではない）
発送 = Shipment（delivery は到着を指すので別）

    6.6 実装例

    ✕ Before：言葉がバラバラ 
    class User {
  buy(product) { /* 買う */ }
}

class PurchaseManager {
  processPurchase(user, product) { /* 購入処理 */ }
}

class DeliveryHandler {
  ship(purchase) { /* 発送 */ }
}

    User / Customer、buy / Purchase、Delivery / Ship、どれもバラバラです。

    ◯ After：ユビキタス言語で統一 
    class Customer {
  placeOrder(product: Product): Order { /* 注文する */ }
}

class OrderService {
  confirmOrder(order: Order) { /* 注文確定 */ }
}

class ShipmentService {
  createShipment(order: Order): Shipment { /* 発送指示作成 */ }
}

    業務の言葉がそのままコードになっています。

    6.7 ユビキタス言語の敵

    1. 勝手な意訳

    開発者がカッコいいと思う英語名を勝手につける。業務の人が読めない。

    2. 曖昧な同義語

    user と customer と member が混在する。

    3. 略語・暗号

    custMgr、purProc、dlvSvc のような意味不明な略語。

    4. 業界用語の無視

    業界用語（受注・与信・引当・締日）を勝手な言葉に置き換える。

    5. 更新されない辞書

    用語集が古くなっても放置される。

    6.8 境界づけられたコンテキストとの関係

    ユビキタス言語は1つのコンテキスト内で有効です。

    • 受注システムでの「商品」＝ まだ買われていない在庫
    • 倉庫システムでの「商品」＝ 棚にある物理的な物
    • 配送システムでの「商品」＝ 梱包された荷物

    同じ「商品」でも意味が違うなら、別のコンテキストと捉えて、別々のユビキタス言語を持ちます。詳しくは 境界づけられたコンテキスト へ。

    6.9 実務での効果

    ユビキタス言語を徹底すると、次の効果があります。

    1. 業務の人とのコミュニケーションがスムーズ
    2. 新メンバーが業務を理解しやすい
    3. 仕様書・ドキュメント・コード・テストが一貫する
    4. バグの原因になる解釈違いが激減
    5. 業務の変更をコードに素早く反映できる

    たかが命名、されど命名

    「たかが命名」ですが、最も効果の高い設計活動と言っても過言ではありません。

    7.戦略的設計の進め方

    1. ドメインを洗い出す — 業務領域の一覧
    2. 用語のブレを探す — 同じ言葉で違う意味がないか
    3. コンテキスト候補を決める — モデルと用語が一貫する単位
    4. コンテキストマップを描く — 連携方法を決める
    5. 段階的に分離 — 最初から完璧な分割は不要

    小規模なら1コンテキストで十分なことも多いです。

    8.よくある誤解

    誤解1：「ユビキタス言語は用語集を作れば完成」

    用語集は道具の1つです。会議・仕様書・コード・テスト・コミットメッセージのすべてで同じ言葉を使い、業務の変化に合わせて育て続けてはじめて意味があります。更新されない辞書はむしろ敵です。

    誤解2：「会社全体で1つのユビキタス言語にそろえるべき」

    ユビキタス言語は1つのコンテキスト内で有効です。「商品」の意味が受注・倉庫・配送で違うなら、無理にそろえず、コンテキストを分けてそれぞれの言葉を持ちます。

    誤解3：「最初に完璧なコンテキスト分割を決める」

    最初から完璧な分割は不要です。用語のブレを手がかりに候補を決め、段階的に分離します。小規模なら1コンテキストで十分なことも多いです。

    9.まとめ

    • 境界づけられたコンテキストはモデルと用語の有効範囲。1つの巨大モデルに詰め込まない
    • コンテキストマップで境界間の関係を明示し、境界を越えるときは変換・契約を決める
    • 大泥団を避け、コンウェイの法則を意識して組織と設計の境界をそろえる
    • ユビキタス言語は、業務の人・設計者・実装者・ドキュメント・コード・テストが全員同じ言葉を使うこと
    • つくり方：洗い出す → 定義する → 用語集 → 英語名 → コードに反映 → 育て続ける
    • 敵：勝手な意訳・曖昧な同義語・略語・業界用語の無視・更新されない辞書
    • ユビキタス言語はコンテキストごとに持つ。コンテキストは段階的に分けていく
