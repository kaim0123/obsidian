    30 ドメイン駆動設計 ／ 32 戦術的設計

    ドメインイベント — 「何かが起きた」という業務の事実をオブジェクトにする

    「注文が確定した」「支払いが失敗した」のような業務上の出来事を、過去形の名前を持つ不変のオブジェクトとして表すのがドメインイベントです。使う理由、使わない場合との対比、発火・購読・配信の仕組み、同期と非同期の配信、マイクロサービス間の連携、イベントソーシングとの関係、そして命名のコツまでを解説します。

    もとにしたノート：05_ドメインイベント

    1.このページで扱うこと

    業務の世界では、常に「何かが起きた」という事実が流れています。

    • 注文が確定した
    • ユーザーが登録された
    • 在庫が切れた
    • 支払いが完了した

    こうした業務上の出来事をオブジェクトとして扱うのがドメインイベント（Domain Event）です。戦術的設計の全体像で見た4つの基本部品のうちの1つで、集約の状態が変わったときに発生します。

    このページでは、ドメインイベントの定義と使う理由、仕組み（発火・購読・配信）、同期／非同期の違い、マイクロサービスやイベントソーシングとの関係を扱います。イベントを軸にシステム全体を組み立てる話は イベント駆動設計 で続けます。

    2.ドメインイベントとは

    2.1 定義

    ドメインイベントとは

    過去形で表される、ドメインで起きた重要な出来事を表すオブジェクト。

    • OrderPlaced（注文が確定した）
    • UserRegistered（ユーザーが登録された）
    • PaymentFailed（支払いが失敗した）
    • StockDepleted（在庫が切れた）

    2.2 特徴

    • 過去形で命名する
    • 不変（immutable）：起きた事実は変わらない
    • 日時を持つ（いつ起きたか）
    • 関連するデータを持つ（誰が、何が）

    2.3 実装例

    class OrderPlaced {
  constructor(
    public readonly orderId: OrderId,
    public readonly customerId: CustomerId,
    public readonly total: Money,
    public readonly occurredAt: Date = new Date()
  ) {}
}

    すべてのフィールドが readonly なので、作ったあとで中身を変えられません。性質としては値オブジェクトに近いものです。

    3.なぜドメインイベントを使うのか

    1. 副作用を切り離せる

    注文確定後に起こすべきこと（メール送信、在庫引当、請求、ポイント付与…）を注文処理本体から切り離しできる。

    2. 業務の因果関係が表現できる

    「注文が確定した」→「在庫が引き当てられた」→「配送が指示された」という業務の流れが、コードにも自然に現れる。

    3. 監査・履歴が残しやすい

    すべてのイベントを記録すれば、いつ何が起きたかを後から追える。

    4. システム連携がしやすい

    別のコンテキスト（別マイクロサービスなど）とは、イベントを通じて疎結合（互いの中身を知らずに済む状態）に連携できる。

    ここでいう副作用とは、メインの処理（注文確定）に付随して起こる、外の世界への働きかけ（メール・在庫・ポイントなど）のことです。

    4.使わない場合との対比

    4.1 使わない場合（全部1つの処理に詰め込む）

    ✕ 悪い例：副作用のてんこ盛り 
    class PlaceOrderUseCase {
  async execute(input) {
    const order = new Order(...);
    await this.orderRepo.save(order);

    // ↓ ここから副作用のてんこ盛り
    await this.stockService.reserve(order);     // 在庫引当
    await this.mailer.sendConfirmation(order);  // メール送信
    await this.pointsService.grant(order);      // ポイント付与
    await this.inventoryService.alertLow();     // 在庫アラート
    await this.analyticsService.track(order);  // 分析記録
    // ...10個くらい続く
  }
}

    注文処理が副作用の山になり、メンテナンスが辛くなります。新しい処理を足すたびに注文処理を書き換え、どれか1つが失敗すると注文全体に影響します。

    4.2 ドメインイベントを使うと

    ◯ 良い例：イベントを記録し、ハンドラに任せる 
    class Order {
  confirm() {
    this.status = 'confirmed';
    this.recordEvent(new OrderPlaced(this.id, this.customerId, this.total));
  }
  recordEvent(event) { this._events.push(event); }
  pullEvents() { return this._events.splice(0); }
}

class PlaceOrderUseCase {
  async execute(input) {
    const order = new Order(...);
    order.confirm();
    await this.orderRepo.save(order);

    // イベントを発火するだけ
    const events = order.pullEvents();
    for (const e of events) await this.dispatcher.dispatch(e);
  }
}

// 各ハンドラは別ファイル
class SendConfirmationMail {
  async handle(event: OrderPlaced) { /* メール送信 */ }
}
class ReserveStock {
  async handle(event: OrderPlaced) { /* 在庫引当 */ }
}

    注文処理は「注文確定」だけに集中し、副作用は各ハンドラ（イベントを受け取って処理するクラス）に分散します。集約（Order）はイベントを「記録」するだけで、実際に配るのはアプリケーション層（ユースケース）である点に注目してください。

    5.イベントの発火と購読

    5.1 発火（Publish）

    イベントを発生させます。

    dispatcher.dispatch(new OrderPlaced(...));

    5.2 購読（Subscribe）

    イベントに対応するハンドラを登録します。

    dispatcher.on(OrderPlaced, new SendConfirmationMail());
dispatcher.on(OrderPlaced, new ReserveStock());
dispatcher.on(OrderPlaced, new GrantLoyaltyPoints());

    5.3 配信（Dispatch）

    発火されたイベントを、登録された全ハンドラに配信します。この「発火する側と受け取る側を、登録の仕組みで切り離す」形は、デザインパターンの Observer パターン（44_クラス設計・デザインパターン「振る舞いに関するパターン」）と同じ発想です。

    6.同期 vs 非同期

    同期的な配信（インプロセス）

    • 同じプロセス内で即時実行
    • 成功・失敗をすぐ検知できる
    • 失敗時のハンドリングがしやすい

    非同期的な配信（メッセージキュー）

    • Kafka・RabbitMQ・SQS などに載せる
    • ハンドラの失敗が注文処理に影響しない
    • 別システムに連携しやすい
    • 順序保証・リトライなどは設計が必要

    大規模では非同期が多く、単体アプリでは同期的で十分なこともあります。インプロセスとは「同じプログラムの中で関数呼び出しとして配る」こと、メッセージキューとは「メッセージをいったん外部の仕組みに預け、受け取り側が後から取り出す」ことです。メッセージングの仕組みそのものは41章の 同期 API・メッセージ・イベント駆動 で扱います。

    配信方法はあとで選べる

    ドメインイベントはまず「ドメインの言葉で表した事実」です。同期で配るか、Kafka などで非同期に配るかはインフラの選択で、イベント自体の設計とは別の話です。

    7.Before / After

    7.1 Before：モノリシックな副作用

    ✕ Before：1つの関数に全部 
    async function placeOrder(cart) {
  const order = new Order(cart);
  await saveOrder(order);
  await sendMail(order);
  await reserveStock(order);
  await notifyWarehouse(order);
  // 20行のてんこ盛り
}

    7.2 After：イベント駆動

    ◯ After：ドメインはイベントを記録し、副作用はハンドラへ 
    // ドメイン層
class Order {
  place(cart) {
    // ビジネスロジックのみ
    this.recordEvent(new OrderPlaced(this.id, ...));
  }
}

// 各ハンドラ
class OrderPlacedHandlers {
  async sendMail(e: OrderPlaced) { /* ... */ }
  async reserveStock(e: OrderPlaced) { /* ... */ }
  async notifyWarehouse(e: OrderPlaced) { /* ... */ }
}

    責任が分離され、新しい副作用の追加が安全にできます。

    8.マイクロサービス間のイベント

    マイクロサービスでは、ドメインイベントを別サービスに配信することで疎結合な連携ができます。

    各サービスは注文サービスを知らない、単にイベントを購読するだけです。新しいサービスを追加しても、注文サービスには一切変更が入りません。

    なお、複数サービスにまたがる一連の処理（注文 → 在庫確保 → 決済）を、イベントのやり取りでつなぎ、失敗したら打ち消しの処理で戻す方式を SAGA と呼びます。分散したデータの整合性の話は41章の データ所有権と SAGA、サービスの分け方は モノリスとマイクロサービス を参照してください。

    9.イベントソーシングとの関係

    イベントソーシング（Event Sourcing）は、「状態の代わりに、起きたイベントを全部保存する」パターンです。

    方式保存するもの
    通常の DB「注文の最新状態」を保存
    イベントソーシング「注文にまつわる全イベント」を保存し、状態は再生（イベントを順に当て直すこと）で復元

    DDD と相性が良く、CQRS とセットで使われることが多いです。CQRS については41章の CQRS を参照してください（CQRS 自体はイベントソーシングなしでも使えます）。

    10.命名のポイント

    ポイント良い例避けたい例
    過去形OrderPlaced, PaymentProcessed—
    業務の言葉PaymentFailedUserClickedButton
    具体的OrderConfirmed / OrderCancelledOrderStatusChanged

    イベント名は業務の専門家が使う言葉（ユビキタス言語）で付けます。画面操作の言葉ではなく、業務で何が起きたかを表します。

    11.よくある誤解

    誤解1：「全てのメソッド呼び出しにイベントを発火する」

    重要な業務イベントだけです。何でもイベントにすると、発火でパンクします。

    誤解2：「イベント ＝ ログ」

    違います。業務的に意味のある出来事です。デバッグログではありません。

    誤解3：「イベントは上書き・削除できる」

    できません。起きた事実は消せないからです。取り消したいときは、「注文がキャンセルされた（OrderCancelled）」のような新しいイベントを足します。

    12.まとめ

    • ドメインイベントは、ドメインで起きた重要な出来事を表す過去形・不変のオブジェクト。日時と関連データを持つ
    • 使う理由：副作用の切り離し・因果関係の表現・監査と履歴・疎結合な連携
    • 集約がイベントを記録し、ユースケースが取り出して発火 → 購読しているハンドラへ配信する
    • 配信は同期（インプロセス）か非同期（メッセージキュー）。単体アプリは同期で十分なことも
    • マイクロサービス間では購読するだけの疎結合な連携ができる。イベントソーシングは CQRS とセットで使われることが多い
    • 名前は過去形・業務の言葉・具体的に
