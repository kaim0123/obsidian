    50 設計プロセス

    テストとリファクタリング — テストを設計のフィードバックに使う

    「テストしやすい設計」とは何か、テストが書きにくいときに設計のどこを疑うべきかを学びます。後半では、動作を変えずに構造を改善するリファクタリングの目的・タイミング・代表的なパターン・安全な手順を、Python のコード例でまとめます。

    もとにしたノート：03_テストと設計の関係 / 04_リファクタリングの考え方

    1.このページで扱うこと

    テストとリファクタリングは、設計を 確かめ、育てる ための道具です。

    • テストしやすい設計 の性質と、テストを難しくする典型例
    • テストを 設計のフィードバック装置 として使う考え方（副作用の分離、レビューとの統合）
    • リファクタリング の目的・タイミング・代表的な5つのパターン・手順・注意点

    2.テストしやすい設計とは何か

    テストしやすい設計とは、部品を独立して検証できる 構造です。

    性質説明
    依存の注入外部（DB・API）を差し替えられる
    副作用の分離純粋な計算部分を切り出せる
    小さな単位1つのテストが1つの振る舞いを検証する
    明確な境界何を モック（テスト用の偽物）にするかがはっきりしている

    テストしやすい

    ＝ 設計が分かれているサイン

    テストしにくい

    ＝ 設計の問題のサイン

    依存の注入（DI）のしくみは 41章の DI・IoC・Composition Root を参照してください。

    3.設計がテストを難しくする典型例

    典型例問題
    静的メソッドで DB を直接叩く差し替えできない
    巨大な God クラス何をテストしているのか分からない
    コンストラクタで外部に接続するテストのたびに DB が必要
    グローバル状態テストの実行順序に結果が依存する
    ランダム・現在時刻に依存結果が再現しない

    これらはそのまま 設計の改善ポイント です。

    4.テストから見えた設計の問題

    テストを書こうとして 「無理」 と感じたら、設計を見直すチャンスです。

    「OrderService のテストに DB・メール・決済が全部必要」

    → 依存が多すぎる。インターフェースで分離する。

    「confirm() のテストでモックが 10 個」

    → 責務が多すぎる。分割する。

    テストは設計のフィードバック装置

    テストの書きにくさは、結合度が高すぎる・凝集度が低すぎる ことを教えてくれます。

    5.副作用の分離とテスト容易性

    副作用（DB への保存やメール送信など、計算結果を返す以外に外の世界を変えること）と計算が混ざると、テストのたびに DB やメールの準備が必要になります。

    ✕ 悪い例：計算と I/O が混在していてテストしにくい 
    function processOrder(order) {
  const total = order.items.reduce(...);
  db.save({ ...order, total });
  sendEmail(order.email);
}
    ◯ 良い例：計算を純粋関数に切り出す 
    function calculateTotal(items) {
  return items.reduce((sum, i) => sum + i.price, 0);
}
// I/O は別の層。calculateTotal はモック不要でテスト可能

    関数型の考え方（→ 関数型と純粋関数）がテスト容易性に直結します。

    6.設計レビューとテスト観点の統合

    レビューのときに、次のように問いかけます。

    • ☐ この部品は 単体テスト可能 か
    • ☐ 外部依存は 注入・抽象化 されているか
    • ☐ テストで 何を検証しているか が明確か
    • ☐ テストが書きにくい箇所は 設計改善の候補 か

    設計レビューとテスト戦略を 別々にしない と効果的です。レビューの進め方は レガシーと設計レビュー を参照してください。

    7.リファクタリングとは

    プログラムを書いていると、後から見直して改善できる部分が見つかることがあります。

    リファクタリングの定義

    リファクタリングとは、コードの動作を変えずに、コードの構造を改善することです。

    7.1 リファクタリングの目的

    • 読みやすくする：コードを理解しやすくする
    • 保守しやすくする：将来の変更を容易にする
    • バグを減らす：コードの構造を改善してバグを減らす
    • パフォーマンスを改善する：効率的なコードにする

    7.2 重要な原則

    動作を変えない

    リファクタリングは、コードの動作を変えてはいけません。機能追加やバグ修正とは 別の作業 として行います。

    8.リファクタリングのタイミング

    1. コードを書いた直後

    書いた直後に見直して、改善できる部分をリファクタリングする。

    2. 機能を追加する前

    既存のコードをリファクタリングして、追加しやすくする。

    3. バグを修正した後

    同じようなバグが起きないようにリファクタリングする。

    4. コードレビューの後

    レビューで指摘された点を改善するためにリファクタリングする。

    9.よくあるリファクタリングパターン

    9.1 関数の抽出（Extract Function）

    長い関数を、意味のまとまりごとに小さな関数へ分割します。

    ✕ リファクタリング前：検証・在庫確認・支払いが1つの関数に 
    def process_order(order):
    # 注文の検証
    if not order:
        return False
    if order["total"] <= 0:
        return False

    # 在庫の確認
    for item in order["items"]:
        if item["stock"] < item["quantity"]:
            return False

    # 支払いの処理
    if order["payment_method"] == "credit":
        process_credit_payment(order)
    elif order["payment_method"] == "cash":
        process_cash_payment(order)

    return True
    ◯ リファクタリング後：コメントの単位で関数に分ける 
    def validate_order(order):
    """注文を検証する"""
    if not order:
        return False
    if order["total"] <= 0:
        return False
    return True

def check_inventory(order):
    """在庫を確認する"""
    for item in order["items"]:
        if item["stock"] < item["quantity"]:
            return False
    return True

def process_payment(order):
    """支払いを処理する"""
    if order["payment_method"] == "credit":
        process_credit_payment(order)
    elif order["payment_method"] == "cash":
        process_cash_payment(order)

def process_order(order):
    """注文を処理する"""
    if not validate_order(order):
        return False

    if not check_inventory(order):
        return False

    process_payment(order)
    return True

    process_order を読むだけで「検証 → 在庫確認 → 支払い」という流れが分かるようになりました。

    9.2 変数名の改善（Rename Variable）

    変数名を、より明確な名前に変更します。

    ✕ リファクタリング前 
    def calc(x, y):
    z = x * y * 1.1
    return z
    ◯ リファクタリング後 
    def calculate_total_price(price, tax_rate):
    total = price * (1 + tax_rate)
    return total

    補足：呼び出し側も一緒に変わる

    この例は名前の変更に加えて、税率 1.1 を引数 tax_rate に出しています。引数の意味が変わるため、呼び出し側（calc(price, qty) のような呼び出し）も合わせて直す必要があります。純粋な「名前の変更」だけなら、計算式はそのままにします。

    9.3 マジックナンバーの削除（Replace Magic Number）

    マジックナンバー（意味の説明なしにコードに直接書かれた数値）に名前を付け、意味を持たせます。

    ✕ リファクタリング前 
    def is_adult(age):
    return age >= 18
    ◯ リファクタリング後 
    ADULT_AGE = 18

def is_adult(age):
    return age >= ADULT_AGE

    9.4 重複コードの削除（Remove Duplication）

    同じコードが複数箇所にある場合、関数にまとめます。

    ✕ リファクタリング前：同じ判定が2箇所に 
    def process_user_a(user):
    if user["age"] >= 18:
        user["status"] = "adult"
    else:
        user["status"] = "minor"

def process_user_b(user):
    if user["age"] >= 18:
        user["status"] = "adult"
    else:
        user["status"] = "minor"
    ◯ リファクタリング後：1つの関数にまとめる 
    def set_user_status(user):
    user["status"] = "adult" if user["age"] >= 18 else "minor"

def process_user_a(user):
    set_user_status(user)

def process_user_b(user):
    set_user_status(user)

    9.5 早期リターン（Early Return）

    条件を満たさない場合に先に return して、ネスト（入れ子）を減らします。

    ✕ リファクタリング前：if が3段の入れ子 
    def process_data(data):
    if data:
        if len(data) > 0:
            if all(isinstance(x, int) for x in data):
                return sum(data) / len(data)
            else:
                return None
        else:
            return None
    else:
        return None
    ◯ リファクタリング後：早期リターンで平らにする 
    def process_data(data):
    if not data:
        return None

    if len(data) == 0:
        return None

    if not all(isinstance(x, int) for x in data):
        return None

    return sum(data) / len(data)

    なお Python では空のリストも not data で真になるため、2つめの len(data) == 0 の判定は実は不要です。早期リターンにすると、こうした重複にも気づきやすくなります。

    10.リファクタリングの手順

    1. テストを書く（または確認する）：リファクタリング前の動作を確認するテストを書きます。 
      def test_process_data():
    assert process_data([1, 2, 3]) == 2.0
    assert process_data([]) == None
    assert process_data(None) == None
    2. 小さな変更を繰り返す：一度に大きな変更をせず、小さな変更を積み重ねます。
    3. テストを実行する：変更のたびにテストを実行して、動作が変わっていないことを確認します。
    4. コミットする：動作が確認できたら、変更をコミットします。

    11.実践例：パターンを組み合わせる

    ✕ リファクタリング前：意味の分からない名前と深い入れ子 
    def calc(x, y, z):
    if x > 0:
        if y > 0:
            if z > 0:
                a = x * y
                b = a * z
                c = b / 2
                return c
            else:
                return 0
        else:
            return 0
    else:
        return 0
    ◯ リファクタリング後：名前・早期リターン・ドキュメント 
    def calculate_volume(length, width, height):
    """
    直方体の体積を計算する

    Args:
        length: 長さ
        width: 幅
        height: 高さ

    Returns:
        体積（すべて正の値の場合）、それ以外は0
    """
    if not (length > 0 and width > 0 and height > 0):
        return 0

    volume = length * width * height
    return volume / 2

    改善点：

    • 変数名が明確になった
    • 早期リターンでネストが減った
    • ドキュメントが追加された
    • ロジックが理解しやすくなった

    気づき：名前が実態とズレていないか

    元のコードが / 2 しているので、動作を変えないために後のコードにも / 2 が残っています。しかし直方体の体積なら / 2 は不要で、名前・ドキュメントと計算が食い違っています。リファクタリングで名前を付けると、こうした 「本当にこの計算で正しいのか」 という疑問が表に出てきます。その場合は、仕様を確認してから 別の作業（バグ修正） として直します。

    12.リファクタリングの注意点

    1. 動作を変えない

    リファクタリングは、コードの動作を変えてはいけません。

    2. テストを書く

    リファクタリング前の動作を確認するテストを書きます。

    3. 小さく進める

    一度に大きな変更をせず、小さな変更を繰り返します。

    4. バージョン管理を使う

    Git などのバージョン管理システムを使い、変更を追跡します。

    設計全体をリファクタリングで育てる考え方は 設計の進め方と段階的な深化、レガシーコードでの進め方は レガシーと設計レビュー を参照してください。

    13.よくある誤解

    誤解1：「テストが書きにくいのはテストのやり方が悪いから」

    多くの場合、原因は設計にあります。DB 直叩き・God クラス・グローバル状態・時刻依存など、テストを難しくする典型例は、そのまま設計の改善ポイントです。

    誤解2：「リファクタリングのついでに機能も直してよい」

    リファクタリングは動作を変えない作業です。機能追加やバグ修正と混ぜると、テストが落ちたときに原因が分からなくなります。別のコミットに分けます。

    誤解3：「リファクタリングは時間ができたらまとめてやるもの」

    書いた直後・機能追加の前・バグ修正の後・レビューの後など、日常の中で小さく行うものです。まとめて大きくやるほど危険になります。

    14.まとめ

    • テストしやすさは良い設計の指標。テストが困難なら設計問題のシグナル
    • 副作用を分離 し、依存を注入可能 にする
    • 設計レビューに テスト観点を統合 する
    • リファクタリングは 動作を変えずに構造を改善 すること
    • 関数の抽出・変数名の改善・マジックナンバーの削除・重複コードの削除・早期リターンなど、よくあるパターンがある
    • テストを書いてから、小さな変更を繰り返し、動作が変わっていないことを確認 してコミットする。習慣化するとコードの品質が継続的に向上する
