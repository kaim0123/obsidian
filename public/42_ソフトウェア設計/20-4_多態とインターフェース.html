    多態とインターフェース — 置換可能性で変更に強くする

    同じ呼び出しなのに、受け手によって違う振る舞いをする性質が「多態性（ポリモーフィズム）」で、それを支えるのが「インターフェース」です。if 分岐との比較、インターフェースの役割、前提となるリスコフの置換原則、多態性の3種類、ダックタイピング、実務での使いどころまでを解説します。

    もとにしたノート：04_多態とインターフェース

    1.このページで扱うこと

    プログラムを書いていると、「同じメソッドなのに、呼んだ相手によって結果が違う」という場面があります。たとえば、

    • dog.speak() → 「わん！」
    • cat.speak() → 「にゃー」
    • cow.speak() → 「もー」

    同じ speak() なのに、相手が変わると違う結果になります。これが多態性（Polymorphism）です。多態性を支えるのがインターフェースという仕組みです。

    • 多態性とは何か（多態性なし／ありのコード比較）
    • インターフェースとは何か、なぜ必要か
    • リスコフの置換原則（LSP）

    2.多態性（Polymorphism）とは

    定義

    多態性とは、同じ呼び出しが、受け手の型によって違う振る舞いをする性質です。「ポリモーフィズム」とも呼ばれます。

    2.1 身近な例

    リモコンのボタン

    同じ「電源ON」ボタンでも、TV なら映像、扇風機なら風、照明なら光がつく

    プリンタの印刷ボタン

    インクジェットでもレーザーでも「印刷」の呼び出しは同じ

    使う側はやり方を意識せず、結果だけ受け取れるのが多態性の価値です。

    2.2 コードで比べる

    ✕ 多態性なし：種類ごとに if で分岐 
    function makeSound(animal) {
  if (animal.type === 'dog') {
    console.log('わん！');
  } else if (animal.type === 'cat') {
    console.log('にゃー');
  } else if (animal.type === 'cow') {
    console.log('もー');
  }
  // 動物が増えるたびにif追加…
}

    動物を増やすたびに makeSound を修正しないといけません。しかも、動物に関する処理が何か所にも散らばります。

    ◯ 多態性あり：各クラスが自分の振る舞いを持つ 
    class Animal {
  speak() { throw new Error('子クラスで実装すべき'); }
}

class Dog extends Animal {
  speak() { console.log('わん！'); }
}

class Cat extends Animal {
  speak() { console.log('にゃー'); }
}

class Cow extends Animal {
  speak() { console.log('もー'); }
}

function makeSound(animal) {
  animal.speak(); // どの動物でも同じ書き方
}

makeSound(new Dog()); // わん！
makeSound(new Cat()); // にゃー

    新しい動物を追加したいときは新しいクラスを作るだけで、makeSound は変更不要です。これが OCP（開放閉鎖の原則：拡張には開き、変更には閉じる）です（→ SOLIDとオブジェクト指向）。

    3.インターフェース（Interface）とは

    インターフェースは、「このクラスは最低限これができますよ」という約束の一覧です。TypeScript の例：

    interface Animal {
  speak(): void;
  eat(food: string): void;
}

class Dog implements Animal {
  speak() { console.log('わん！'); }
  eat(food: string) { console.log(`${food}を食べる`); }
}

    インターフェースを実装する（implements）と、そこに書かれたメソッドを必ず持つことが保証されます。

    3.1 なぜインターフェースが必要か

    • 使う側が、具体クラスを知らなくてよい（Animal として扱える）
    • 差し替え可能（Dog でも Cat でも受け取れる）
    • テスト用のモックが作れる（本物の DB の代わりに偽物を渡す）

    インターフェースと抽象化をアーキテクチャの観点で扱う話はインターフェースと抽象化、疎結合・インターフェース・DIP・DI の関係とモジュールでの実現は 43_モジュール設計 のノートで扱います。

    4.リスコフの置換原則（LSP）

    多態性が正しく機能するための大前提がリスコフの置換原則（Liskov Substitution Principle）です。

    「親（または実装元のインターフェース）で期待された振る舞いを、子は必ず守る」

    つまり、子を親のつもりで使っても壊れないことが必要です。

    ✕ 悪い例：飛べないペンギンが Bird を継承する 
    class Bird {
  fly() { /* 飛ぶ */ }
}

class Penguin extends Bird {
  fly() { throw new Error('飛べない'); } // LSP違反！
}

function travel(bird) {
  bird.fly(); // Penguinを渡すと壊れる
}

    ペンギンは鳥だが飛べない。継承は is-a 関係だからといって、機械的に extends すると問題が起きる例です（→ 継承と合成）。

    対処法

    Bird と FlyableBird にインターフェースを分けるなど、「できること」で型を分けるのが解決策です。飛ぶ必要がある travel は FlyableBird だけを受け取るようにすれば、ペンギンを渡す間違いは起きません。

    5.多態性の3種類

    教科書的には、多態性には3つの種類があります。

    種類仕組み説明
    1. 部分型多相（Subtype Polymorphism）親子関係・インターフェース実装オブジェクト指向のメイン。このページで扱っている多態
    2. パラメトリック多相（Parametric Polymorphism）ジェネリクス・テンプレートList<T> のように、型をパラメータ化する
    3. アドホック多相（Ad-hoc Polymorphism）オーバーロード・演算子オーバーロード同じ名前で違う引数を受け取る

    6.ダックタイピング

    「アヒルのように歩き、アヒルのように鳴けば、それはアヒルだ」

    Python や JavaScript など動的型付け言語（実行するまで型をチェックしない言語）では、明示的なインターフェース宣言がなくても、必要なメソッドさえ持っていれば使えます。

    class Duck:
    def quack(self): print('ガー')

class FakeDuck:
    def quack(self): print('（録音）ガー')

def perform(duck):
    duck.quack() # 「quackが呼べれば何でもいい」

perform(Duck())
perform(FakeDuck()) # インターフェース宣言なしで動く

    柔軟ですが、型で守られていないぶんバグを生みやすくもあります。型ヒント（Python の Protocol、TypeScript の interface）で補うのが実務では一般的です。

    7.実務での使いどころ

    7.1 決済方法の切り替え

    interface PaymentMethod {
  pay(amount: number): void;
}

class CreditCard implements PaymentMethod { /* ... */ }
class PayPal implements PaymentMethod { /* ... */ }
class ApplePay implements PaymentMethod { /* ... */ }

function checkout(method: PaymentMethod, amount: number) {
  method.pay(amount); // どの方法でもOK
}

    7.2 通知チャネルの切り替え

    interface Notifier {
  notify(user: User, message: string): void;
}

class EmailNotifier implements Notifier { /* ... */ }
class SlackNotifier implements Notifier { /* ... */ }
class SMSNotifier implements Notifier { /* ... */ }

    7.3 テスト時の差し替え

    interface UserRepository {
  find(id: string): User;
}

class RealDBRepo implements UserRepository { /* ... */ }
class MockRepo implements UserRepository { /* テスト用 */ }

    使う側が UserRepository という抽象にだけ依存するようにすると、本番では DB、テストでは偽物を渡せます。これをアーキテクチャの原則にしたものが依存性逆転の原則（DIP）です。SOLID の LSP / ISP / DIP は多態・インターフェースと深く関連します（原則の詳細は 48_原則 のノート）。

    8.よくある誤解

    誤解1：「is-a が成り立てば継承してよい」

    「ペンギンは鳥」でも、Bird が「飛べる」ことを約束しているなら、Penguin はその約束を守れません。継承やインターフェース実装で大事なのは見た目の分類ではなく、親で期待された振る舞いを守れるか（LSP）です。

    誤解2：「インターフェースがない言語では多態性は使えない」

    動的型付け言語では、ダックタイピングによって明示的な宣言なしで多態性が使えます。ただし型で守られていないため、型ヒント（Protocol など）で補うのが一般的です。

    誤解3：「多態性 = 継承」

    継承による多態（部分型多相）はその一部です。ジェネリクスによるパラメトリック多相、オーバーロードによるアドホック多相もあります。また、部分型多相でも実装を引き継がないインターフェース実装で実現できます。

    9.区分・種別の if を多態で置き換える

    料金種別や顧客区分のように、区分ごとの場合分け が散らばるときは、区分ごとにクラス（または振る舞い付き列挙）を切り、共通インターフェースで扱うと if が消えます。これを増田亨『現場で役立つシステム設計の原則』では 区分オブジェクト と呼びます。手順と状態遷移の書き方は 区分オブジェクトと状態遷移、分岐の読みやすさ（ガード節・複文の分解）は 場合分けのロジックを整理する を参照してください。

    10.まとめ

    • 多態性 = 同じ呼び出しで違う振る舞い。種類ごとの if 分岐を消し、新しいクラスを足すだけで拡張できる（OCP）
    • インターフェース = 「これができます」という約束
    • 使う側が具体クラスを知らなくてよい → 変更・拡張に強くなり、テストでモックに差し替えられる
    • LSP（置換原則）を守るのが前提条件。「できること」で型を分ける
    • 多態性には部分型・パラメトリック・アドホックの3種類がある。動的型付け言語ではダックタイピング
    • 区分の場合分けは 区分オブジェクト（→ 区分オブジェクトと状態遷移）へ
