    手続き指向設計 — 処理の流れで組み立てる設計の源流

    手続き指向は、プログラムを「処理の流れ（手続き）」の集まりとして設計する考え方で、ソフトウェア設計の源流にあたります。構造化プログラミングの3つの制御構造、トップダウンでの手続き分割、データと処理の分離、そして今も使われる場面と限界までを解説します。

    もとにしたノート：01_手続き指向設計

    1.このページで扱うこと

    ソフトウェア設計の源流である手続き指向を理解します。構造化プログラミングと手続き分割は古い話ではなく、今でもユースケースの流れ（ある操作を最初から最後までどう進めるか）などで使われています。

    • 手続き指向とは何か
    • 構造化プログラミング — 順次・分岐・反復
    • トップダウン設計と手続き分割
    • データと処理の分離（初期形）と、そこから生まれた課題
    • 手続き指向が向く場面と限界

    歴史的な背景はソフトウェア設計年表の「手続き指向」の部分を参照してください。

    2.手続き指向とは何か

    定義

    手続き指向とは、プログラムを処理の流れ（手続き）の集合として設計する考え方です。

    • データと処理は別々に定義されることが多い
    • トップダウン（大きいものから小さいものへ）で、大きな処理を小さな手続きに分割する
    • main やコントローラが全体の流れを制御する
    main()
  ├─ input_data()
  ├─ validate()
  ├─ calculate()
  └─ output_result()

    main が「入力 → 検証 → 計算 → 出力」という順番を知っていて、それぞれの手続きを順に呼び出します。全体の流れが1か所に書かれているので、上から読めば何が起きるかが分かります。

    3.構造化プログラミング — 順次・分岐・反復

    Edsger Dijkstra（エドガー・ダイクストラ）らが提唱した構造化プログラミングは、制御フロー（処理がどの順番で進むか）を次の3つだけで組み立てます。

    構造意味
    順次上から順に実行
    分岐if / switch で条件により分岐
    反復for / while で繰り返し

    goto（プログラムの好きな場所へ飛ぶ命令）による飛び飛びの制御は避けます。これにより処理の流れが追いやすくなりました。

    4.トップダウン設計と手続き分割

    トップダウン設計は、大きな問題を段階的に小さな手続きに分解する手法です。

      「注文を処理する」
       │
       ├─ 入力を検証する
       ├─ 在庫を確認する
       ├─ 金額を計算する
       └─ 結果を保存する

    分割の基準は次の3つです。

    1. 1 手続き 1 つの仕事：1つの手続きには1つのことだけをさせる。これは関心の分離の萌芽（芽生え）です
    2. 同じ抽象度のステップを並べる：「在庫を確認する」の隣に「変数 i に 1 を足す」のような細かすぎる処理を混ぜない
    3. 手続き名が意図を表す：名前を読めば何をするかが分かるようにする

    メソッド（手続き）設計の詳細は、46_メソッド設計 の目次ノートを参照してください。

    5.データと処理の分離（初期形）

    手続き指向では、データ構造とそれを操作する手続きが分かれます。

    C 言語の例：データの定義と処理が別々にある 
    // データ
struct Order {
  int id;
  float total;
};

// 処理
void calculate_total(struct Order* order) { ... }
void save_order(struct Order* order) { ... }

    これは整理しやすい反面、同じデータに触る手続きが増えると、変更の影響範囲が読めなくなるという課題を残しました。たとえば Order に項目を足したり意味を変えたりすると、それを使っている手続きをプログラム中から探して歩く必要があります。これがオブジェクト指向への動機のひとつです。

    6.手続き指向が向く場面と限界

    向く場面

    • ユースケースのオーケストレーション（処理の流れの制御）
    • 単純なデータ変換パイプライン
    • スクリプト・バッチ処理
    • 学習初期の小規模プログラム

    限界

    • 同じデータに関する処理があちこちに散らばる
    • 現実世界の「もの」を手続きの集合として表現しにくい
    • 大規模化するとグローバル状態（プログラムのどこからでも読み書きできるデータ）の管理が困難
      手続き指向は「消えた」のではなく、
  オーケストレーション層などで今も使われている

    今も残る手続き指向

    オブジェクト指向のアプリでも、「注文を受け付ける」ユースケースの中身は「検証する → 在庫を確保する → 保存する → 通知する」という手続きの流れで書かれることがよくあります。オーケストレーション（各部品を呼ぶ順番の指揮）は手続き指向、個々のルールはオブジェクトが持つ、という組み合わせが一般的です。

    7.よくある誤解

    誤解1：「手続き指向は古いので、もう使われていない」

    手続き指向は消えたのではなく、ユースケースのオーケストレーション、データ変換パイプライン、スクリプト・バッチ処理などで今も使われています。向く場面と限界を知り、他のパラダイムと組み合わせるのが実務的です。

    誤解2：「手続きに分ければ、それで設計できている」

    分け方が大事です。「1 手続き 1 つの仕事」「同じ抽象度のステップを並べる」「名前が意図を表す」という基準を満たさない分割は、かえって読みにくくなります。また、手続きを分けてもデータと処理が離れている問題は残ります。

    誤解3：「データと処理を分けるのは、いつでも良いこと」

    小さなプログラムでは整理しやすい方法ですが、同じデータに触る手続きが増えると変更の影響範囲が読めなくなります。この課題に応えたのがオブジェクト指向（データと振る舞いを一体にする）です。

    8.まとめ

    • 手続き指向は処理の流れを中心に設計する
    • 構造化プログラミング（順次・分岐・反復）で制御フローを整理し、goto を避ける
    • トップダウンで手続き分割する。データと処理は分離される
    • データと処理の分離は、手続きが増えると影響範囲が読めなくなる課題を残し、OOP への動機になった
    • 向く場面と限界を知り、他パラダイムと組み合わせる（次はオブジェクト指向とクラス）
