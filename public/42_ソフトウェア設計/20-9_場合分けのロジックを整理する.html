    場合分けのロジックを整理する

    区分や種別ごとの if / else / 入れ子 は、プログラムを複雑にする代表的な原因です。まずはメソッド単位で分岐を読みやすくし（早期 return・メソッド抽出・複文の分解）、次のページでクラス／列挙（区分オブジェクト）へ押し出します。

    もとにしたノート：46_メソッド設計/40_本体の書き方/02_Guard_Clause、03_複雑度と分岐、04_Extract_Method／増田亨『現場で役立つシステム設計の原則』第2章前半

    ひとことで言うと

    場合分けは「消す」より「閉じ込める」。条件に名前を付け、else を減らし、入れ子をほどいてから、区分ごとの本体は別クラスへ移します。

    1.区分や種別がコードを複雑にする

    業務アプリでは「顧客区分」「料金種別」「注文ステータス」のような 区分・種別 ごとに処理が分かれます。区分が1つ増えるたびに、同じパターンの if / switch がメソッドのあちこちへコピーされやすくなります。

    症状何が困るか
    同じ switch が複数箇所区分追加のたびに漏れが出る
    if の中に長い計算変更箇所と影響範囲が見えない
    深い入れ子正常系が追えない・テストが爆発する

    整理の段階は次のとおりです。

    1. 判断や計算を メソッドに独立 させる
    2. else をなくし、早期 return（ガード節）にする
    3. 複文（入れ子）を単文の並び に分解する
    4. 区分ごとの本体を 区分オブジェクト へ移す

    2.判断や処理のロジックをメソッドに独立させる

    if の中にごちゃごちゃ書いた式を直すより、名前付きメソッド に抽出した式を直すほうが安全です。変更箇所とその影響を、そのメソッドに閉じ込められます。

    // ✕ if の中に計算がべた書き
function fee(customer) {
  if (customer.age < 12) {
    return 500 * (1 - 0.1);
  }
  // ...
}

// ◯ 意図がメソッド名で読める
function fee(customer) {
  if (isChild(customer)) return childFee();
  if (isSenior(customer)) return seniorFee();
  return adultFee();
}

    抽出の手順の詳細はメソッド設計の Extract Method（docs: 46_メソッド設計/20_責務と分割/04_Extract_Method）を参照してください。

    3.else 句をなくすと条件分岐が単純になる

    結果を変数にためて else でつなぐ書き方より、確定したらすぐ return する書き方のほうが、分岐同士の結びつきが弱くなります。順序の入れ替えや条件の追加がしやすくなります。この書き方を ガード節（Guard Clause） とも呼びます。

    // ✕ else でつなぐ
function fee(customer) {
  let result;
  if (isChild(customer)) {
    result = childFee();
  } else if (isSenior(customer)) {
    result = seniorFee();
  } else {
    result = adultFee();
  }
  return result;
}

// ◯ else をなくし早期 return
function fee(customer) {
  if (isChild(customer)) return childFee();
  if (isSenior(customer)) return seniorFee();
  return adultFee();
}

    「2つの同等な選択肢」のような対称的な分岐は、あえて if-else のままでよい場合もあります。詳細は docs の 02_Guard_Clause を参照してください。

    4.複文は単文に分ける

    複文 は「文の中に文がある」入れ子構造です。ネストした if は、日本語の複文と同じく意図がわかりにくくなります。入れ子をほどき、単文を上から並べる 形にします。

    // ✕ 複文（入れ子）
function discount(order) {
  if (order.isMember()) {
    if (order.total() >= 10000) {
      return order.total() * 0.2;
    } else {
      return order.total() * 0.1;
    }
  }
  return 0;
}

// ◯ 単文の並び + 早期 return
function discount(order) {
  if (!order.isMember()) return 0;
  if (order.total() >= 10000) return largeMemberDiscount(order);
  return smallMemberDiscount(order);
}

    5.ここまでと次の一手

    メソッド単位で読みやすくなっても、同じ区分分岐がクラスやモジュールをまたいで残るなら、区分ごとのクラス／列挙 に押し出します。共通の型で扱うと、使う側の if が消えます。

    多態の考え方は 多態とインターフェース、区分オブジェクトの実装は次のページへ進みます。

    6.まとめ

    • 区分・種別の if は複雑さと重複の温床になる
    • 判断・計算はメソッドに独立させ、意図を名前で表す
    • else を減らし早期 return（ガード節）で分岐を疎にする
    • 入れ子の複文は単文の並びに分解する
    • 散らばる区分ロジックは 区分オブジェクト へ

    7.理解度チェック

    Q1. ガード節（早期 return）の主な利点はどれか

    異常系や確定した区分を先に返し、正常系（または残りの区分）を浅いインデントで読めるようにすること。分岐の入れ替え・追加もしやすい。

    Q2. 「複文は単文に分ける」とは何か

    入れ子の if など「文の中の文」をほどき、早期 return や名前付きメソッドで一段階の判断を並べること。

    Q3. if 内の計算をメソッドに出す利点は

    変更箇所と影響範囲をそのメソッドに閉じ込められ、呼び出し側はメソッド名で意図が読める。

    Q4. メソッド整理のあと、まだ区分 if が散らばるときは

    区分ごとのクラスや振る舞い付き列挙（区分オブジェクト）にロジックを移し、共通インターフェースで扱う。

    Q5. 対称的な二択でも必ず else を消すべきか

    いいえ。同等な二つの選択肢は if-else のままの方が読みやすいこともある。
