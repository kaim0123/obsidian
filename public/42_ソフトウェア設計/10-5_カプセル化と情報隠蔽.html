    10 設計の基礎

    カプセル化と情報隠蔽 — 中身を隠して、決められた入口から使う

    カプセル化と情報隠蔽は、変更に強い設計の核心です。このページでは、カプセル化の3つの目的、公開すべきもの・隠すべきもの、内部を変えても外に波及させない情報隠蔽の考え方、隠したはずの詳細が漏れ出す「漏れ出す抽象化」の危険を解説し、カプセル化が OOP の private だけでなく設計全体の原則であることを確認します。

    もとにしたノート：10_設計の基礎/06_カプセル化と情報隠蔽

    1.このページで扱うこと

    部品の中身を外から自由にいじれる状態だと、どこで何が書き換えられたのか追えなくなり、中身を少し変えるだけで利用者側が次々に壊れます。これを防ぐのが カプセル化 と 情報隠蔽 です。OOP（オブジェクト指向プログラミング）だけでなく、モジュール設計全体に通じる原則として理解します。

    このページでは次の内容を扱います。

    • カプセル化の目的
    • 公開すべきもの・隠すべきもの：コード例つき
    • 変更に強くするための隠蔽（情報隠蔽）
    • 漏れ出す詳細（Leaky Abstraction）の危険性
    • カプセル化は設計全体の原則である

    2.カプセル化の目的

    カプセル化（Encapsulation） とは、データと処理をまとめ、外から勝手にいじれないようにする ことです。目的は次の 3 つです。

    1. 不正な操作を防ぐ — 外部から内部状態を直接壊されない
    2. 変更の影響を閉じ込める — 内部実装を変えても外側に波及しにくい
    3. 意図を明確にする — 公開された操作だけが「できること」

    薬のカプセルのイメージ

    薬のカプセルのように、中身は見えないが、決められた方法で使える イメージです。

    3.公開すべきもの・隠すべきもの

    公開する隠す
    外部が使うべき操作（メソッド）内部のデータ構造
    契約としてのインターフェース実装の詳細
    不変条件を守るための入口中間計算の過程

    不変条件 とは「残高は常に 0 以上」のように、そのデータがいつでも満たしているべきルールのことです。入口を1つに絞れば、そこでルールを必ずチェックできます。

    比較のため、まず何も隠していない例を見てみます。

    ✕ 悪い例：残高を誰でも直接書き換えられる 
    class BankAccount {
  balance = 0;  // 公開されている
}

const account = new BankAccount();
account.balance = -5000;  // ルール違反の値でも入ってしまう
    ◯ 良い例：公開面が明確 
    class BankAccount {
  #balance = 0;  // 隠す

  deposit(amount) {  // 公開する
    if (amount <= 0) throw new Error('正の金額のみ');
    this.#balance += amount;
  }

  getBalance() { return this.#balance; }
}

    JavaScript では # を付けたフィールドはクラスの外から読み書きできません。残高を変える入口は deposit() だけなので、「正の金額のみ」というルールを必ず通ります。

    すべてを public にする必要はない

    本当に外から使うものだけを公開します。

    4.変更に強くするための隠蔽

    内部表現を変えても、公開インターフェースが同じなら 利用者は影響を受けません。

    これが 情報隠蔽（Information Hiding） の力です。David Parnas（デビッド・パーナス）が 1972 年に提唱した考え方で、設計判断ごとに隠す ことを推奨しました。「内部を配列で持つか Map で持つか」のような、あとで変わるかもしれない判断を1つの部品の中に閉じ込めておく、という発想です。

    5.漏れ出す詳細（Leaky Abstraction）の危険性

    漏れ出す抽象化（Leaky Abstraction） とは、隠すはずの詳細が外に漏れる状態です。

    漏れの例問題
    DB のテーブル構造が API に露出DB 変更で API も変更が必要
    同期/非同期の詳細が呼び出し側に漏れる実装変更で全体が壊れる
    エラーコードが DB 固有別 DB に移行できない

    良い抽象化

    利用者は「保存できる」だけ知る。

    漏れる抽象化

    利用者が SQL やテーブル名を知っている。

    抽象化は 「何を隠すか」 を意識して設計します。抽象化とインターフェースの設計については 41章：インターフェースと抽象化 も参照してください。

    6.カプセル化は設計全体の原則である

    カプセル化は OOP の private だけではありません。

    レベルカプセル化の例
    クラスprivate フィールド、公開メソッド
    モジュールパッケージの公開 API、内部実装の非公開
    サービス公開 API のみ、内部 DB スキーマは隠す
    レイヤードメイン層はインフラの詳細を知らない

    カプセル化とは

    カプセル化 = 「内側」と「外側」の境界を意識する設計の姿勢 です。

    OOP での詳細は オブジェクト指向とクラス を参照してください。

    7.よくある誤解

    誤解1：「カプセル化＝フィールドを private にして getter/setter を付けること」

    すべてのフィールドに setter を付ければ、結局は外から自由に書き換えられます。大事なのは、不変条件を守る入口だけを公開し、内部のデータ構造や実装の詳細を隠すことです。

    誤解2：「カプセル化は OOP だけの話」

    モジュールの公開 API、サービスの内部 DB スキーマ、レイヤー間の関係など、カプセル化はすべての設計階層に適用できる「内側と外側の境界を意識する姿勢」です。

    誤解3：「インターフェースを作れば詳細は隠れている」

    インターフェースがあっても、テーブル構造や DB 固有のエラーコード、同期/非同期の詳細が外に見えていれば、詳細は漏れています（漏れ出す抽象化）。「何を隠すか」を意識する必要があります。

    8.まとめ

    • カプセル化は不正操作の防止・変更の局所化・意図の明確化
    • 公開すべきものと隠すべきものを意識する
    • 情報隠蔽（Parnas, 1972）により内部実装の変更が外に波及しにくくなる
    • 漏れ出す抽象化に注意。カプセル化は全設計階層に適用できる
