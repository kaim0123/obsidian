    継承と合成 — 「is-a」より「has-a」を選ぶ理由

    既存のクラスを活かして新しいクラスを作る方法には、「拡張する」継承と「部品として持つ」合成の2つがあります。それぞれの利点・欠点、GoF の「継承より合成」の理由、使い分けの指針、Strategy や委譲といった合成の活用パターンまでを解説します。

    もとにしたノート：03_継承と合成

    1.このページで扱うこと

    オブジェクト指向で「既存のクラスを活用して新しいクラスを作る」方法には、2つの代表的なやり方があります。

    継承（Inheritance）

    既存のクラスを拡張する（「〜の一種である」）

    合成（Composition）

    既存のクラスを部品として持つ（「〜を持っている」）

    初心者のうちは「継承ばかり使う」傾向がありますが、実は合成のほうが使いやすく、壊れにくいことが多いです。このページでは、両者の違いと使い分けを学びます。

    2.継承とは（is-a 関係）

    継承は、親クラスの性質を子クラスが受け継ぐ仕組みです。「子クラスは親クラスの一種である（is-a）」という関係で成り立ちます。

    class Animal {
  constructor(name) { this.name = name; }
  eat() { console.log(`${this.name}が食べる`); }
}

class Dog extends Animal {
  bark() { console.log(`${this.name}: わん！`); }
}

const pochi = new Dog('ポチ');
pochi.eat();  // 親の機能を使える
pochi.bark(); // 自分の機能

    Dog is-a Animal（犬は動物の一種）という関係です。

    継承の利点

    • コードを再利用できる
    • 共通の型として扱える（ポリモーフィズム）

    継承の欠点

    • 親クラスの変更が全子クラスに影響する（脆い）
    • 親子の関係が固く結ばれる（強結合）
    • 多重継承（複数の親を持つこと）をすると依存関係が複雑になる（ダイヤモンド問題：2つの親が同じ祖先を持ち、どちらの実装を使うかがあいまいになる）
    • 実装の継承は「中身の秘密」まで引き継いでしまう

    3.合成とは（has-a 関係）

    合成は、クラスが別のクラスのオブジェクトを部品として持つ方法です。「A は B を持っている（has-a）」という関係です。

    class Engine {
  start() { console.log('エンジン始動'); }
}

class Car {
  constructor() {
    this.engine = new Engine(); // Engineを部品として持つ
  }
  start() {
    this.engine.start();
    console.log('車が発進');
  }
}

const car = new Car();
car.start();

    Car has-a Engine（車はエンジンを持っている）。

    合成の利点

    • 部品を差し替えやすい（ガソリンエンジン → 電気モーターなど）
    • 関係が弱く、変更の影響が狭い
    • 実行時に振る舞いを変えられる
    • テスト時にモック（本物の代わりに使う偽物の部品）を差し込みやすい

    合成の欠点

    • コード量が少し増える
    • 委譲（delegate：受けた仕事を部品に回すこと）のコードを書く必要がある

    4.「継承より合成」— なぜ合成が推奨されるか

    Gang of Four（GoF：4人の著者）の『デザインパターン』では、次のように提唱されています。

    「クラス継承より、オブジェクト合成を使え」（Favor composition over inheritance）

    理由は、継承が強すぎる関係を作るからです。

    4.1 継承が招くトラブル例

    ✕ 悪い例：Stack が ArrayList を継承する 
    class Stack extends ArrayList {
  // ListのaddAll等も継承してしまう → Stackのルール(LIFO)が崩れる
}

    Stack（後に入れたものから取り出す LIFO の入れ物）は「push/pop だけ使える」ことが肝心なのに、ArrayList の機能まで受け継いでしまい、Stack の意図と矛盾するメソッドが外から使えてしまいます。

    ◯ 良い例：合成で書く 
    class Stack {
  constructor() {
    this.items = []; // ArrayListを内部に持つだけ
  }
  push(x) { this.items.push(x); }
  pop() { return this.items.pop(); }
  // 必要な機能だけを提供
}

    Stack は自分の都合に合わせて必要な操作だけ提供できます。これはカプセル化を守ることにもなります。

    5.使い分けの指針

    継承を使ってよい場面

    • 明確な「is-a」関係が成り立つ
    • 親クラスが安定していて変更されない（標準ライブラリの抽象クラスなど）
    • 全ての子クラスで親の振る舞いが適切（リスコフの置換原則を満たす。→ 多態とインターフェース）

    合成を選ぶべき場面

    • 単に「機能を使いたい」だけ（is-a ではなく has-a）
    • 実行時に振る舞いを切り替えたい
    • 親クラスの実装が変わる可能性がある
    • 複数の異なる種類の振る舞いを組み合わせたい

    6.合成の活用パターン

    6.1 戦略（Strategy）パターン

    振る舞いをオブジェクトとして差し込みます。

    class SortStrategy {
  sort(list) { throw new Error('実装が必要'); }
}
class QuickSort extends SortStrategy { sort(list) { /*...*/ } }
class MergeSort extends SortStrategy { sort(list) { /*...*/ } }

class Sorter {
  constructor(strategy) { this.strategy = strategy; }
  run(list) { return this.strategy.sort(list); }
}

new Sorter(new QuickSort()).run(data);
new Sorter(new MergeSort()).run(data); // 差し替え可能

    ここで QuickSort などが SortStrategy を継承しているのは「共通の型として扱う」ため（多態のため）で、Sorter は並べ替えの方法を部品として持つ（合成）だけです。

    6.2 委譲（Delegation）

    自分の仕事の一部を部品に任せます。

    class UserService {
  constructor(userRepo, mailer) {
    this.userRepo = userRepo;
    this.mailer = mailer;
  }
  register(user) {
    this.userRepo.save(user);    // 保存は部品に委譲
    this.mailer.send(user.email); // 送信も部品に委譲
  }
}

    部品をコンストラクタで外から受け取る形にしておくと、テストでは偽物を渡せます。この「外から渡す」考え方はDI（依存性の注入）につながります。デザインパターン全体は 44_クラス設計・デザインパターン のノートで扱います。

    7.よくある誤解

    誤解1：「継承 = コード再利用」

    継承の本当の目的は「多態的に扱うため」であって、単なる再利用ではありません。再利用目的なら合成のほうが適しています。

    誤解2：「深い継承ツリーが『高度』」

    継承を3階層以上重ねると、どこで何が定義されているか分からなくなり、読解コストが跳ね上がります。多くの場合は2階層以下に留めます。

    誤解3：「抽象クラスなら継承しても OK」

    抽象クラスの継承も、親の変更が全子に伝わるという性質は同じです。インターフェースの実装（インターフェース継承）は実装を引き継がないため比較的安全ですが、実装の継承（extends）は慎重に。

    8.まとめ

    • 継承（is-a）… 共通の型で扱うのが目的。親子を固く結ぶので慎重に使う
    • 合成（has-a）… 部品として使う。差し替え・テストがしやすい。デフォルトはこちら
    • GoF：「クラス継承より、オブジェクト合成を使え」
    • 合成の活用例は Strategy パターンと委譲
    • 迷ったら合成を選ぶ
