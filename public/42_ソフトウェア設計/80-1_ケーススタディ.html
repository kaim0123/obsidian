    80 ケーススタディ

    ケーススタディ — TODO アプリと注文管理システムで設計を通しで考える

    小規模な TODO アプリと、業務ルールのある注文管理システムの2つを題材に、これまでのページの考え方を通しで使ってみます。要件整理からパラダイム・モジュール・クラスの選択、コンテキストと集約、ドメインイベント、よくある設計ミスの修正まで、各判断がどのページの考え方に当たるかを示しながら進めます。

    もとにしたノート：01_ケーススタディ_TODOアプリ / 02_ケーススタディ_注文管理システム

    1.このページで扱うこと

    規模と複雑さの違う2つの題材で、設計判断を一通り体験します。

    ケース1：TODO アプリ

    小規模な CRUD。過剰設計をしない 判断と、それでも効く関心の分離・高凝集・低結合を練習します。

    ケース2：注文管理システム

    業務ルールがある。DDD・パラダイム・イベント の考え方を統合します。

    それぞれの設計判断には、もとになる考え方のページへのリンクを付けています。進め方の全体は 設計の進め方と段階的な深化 の流れ（要件 → ユースケース → 名詞・動詞 → モジュール → クラス）に沿っています。

    2.ケース1：TODO アプリの設計

    2.1 要件の整理

    まず 要件・用語を整理 します。

    機能要件

    • タスクを追加・完了・削除できる
    • タスク一覧を表示できる
    • （任意）期限を設定できる

    非機能要件

    • 個人利用・小規模
    • ブラウザで動作する
    用語意味
    タスクやるべきこと1件
    完了タスクを終了状態にする

    2.2 パラダイムと構造の選択

    小規模な CRUD なので、過剰設計は不要 です（→ パラダイムの選び方と比較）。

    選択理由考え方のページ
    手続き的なユースケースの流れ追加・完了・削除の流れが明確手続き指向設計
    シンプルな OOPTask をオブジェクトとして表現オブジェクト指向とクラス
    関数型の要素フィルタ・ソートは純粋関数で関数型と純粋関数

    使わないと決めるのも設計判断

    DDD・イベント駆動は不要 です（コンテキストが1つで、ドメインも単純）。DDD を使うべき場面は DDDとは、イベントにすべきかの判断は イベント駆動設計 を参照してください。

    2.3 モジュール候補の洗い出し

    todo-app/
  ├── ui/          … 表示・入力（関心: プレゼンテーション）
  ├── application/ … ユースケースの流れ（追加・完了・削除）
  ├── domain/      … Task のルール
  └── storage/     … 永続化（localStorage 等）

    関心の分離 を意識した分割です。依存の向きは ui → application → domain とし、storage は domain の Repository インターフェースを実装する形にすると、ドメインが保存方法を知らずに済みます（→ 依存性逆転の原則）。より詳しくは 43_モジュール設計 につながります。

    2.4 クラス・関数の大まかな設計

    要素中身考え方のページ
    Task（エンティティ）id, title, completed, dueDate?
    complete(), isOverdue()    		エンティティと値オブジェクト、カプセル化と情報隠蔽
    TaskRepository（インターフェース）save(task), findAll(), delete(id)多態とインターフェース、集約とリポジトリ
    AddTaskUseCase / CompleteTaskUseCase（アプリケーション）手続き的なオーケストレーション（処理の順番の制御）ドメイン層とユースケース
    ◯ 純粋関数の例 
    function filterActive(tasks) {
  return tasks.filter(t => !t.completed);
}

    2.5 実装と振り返り

    振り返りの問い（→ 設計レビューのチェックリスト）：

    • ☐ UI に永続化の詳細が漏れていないか
    • ☐ Task に完了ルールが閉じているか
    • ☐ テストは Task と filterActive だけで書けるか（→ テストとリファクタリング）
    • ☐ モジュール間の依存方向は一方向か

    改善の余地：

    • 期限機能を足すとき、Task に isOverdue() を置くか
    • 複数ユーザーになったら、コンテキスト分割を検討する（→ 境界づけられたコンテキスト）

    小規模でも効く

    小規模でも「関心の分離」「高凝集・低結合」は良い練習になります。

    3.ケース2：注文管理システム

    3.1 業務ルールの整理とユビキタス言語

    業務ルール（例）

    • 注文は 確定 するとキャンセルできない（配送前まで）
    • 確定時に 在庫を引当 する
    • 合計金額は 明細の合計 − 割引
    • 5,000 円以上で 送料無料

    ユビキタス言語（開発者と業務の専門家が共通で使う言葉。→ 戦略的設計とユビキタス言語）

    用語意味
    注文顧客の購入依頼
    明細注文に含まれる商品1件
    確定注文を受け付け、在庫引当を行う
    引当在庫を一時的に確保する

    3.2 コンテキストと集約の設計

    • コンテキストごとに用語が違う（注文側は「注文・確定」、在庫側は「引当・在庫数」）→ 境界づけられたコンテキスト
    • Order 集約 は Order（集約ルート）と、その下の OrderLine（明細）からなる
    • 外部は order.confirm() 経由でのみ確定する
    • 在庫は Order 集約の外。イベントで連携する → 集約とリポジトリ

    3.3 オブジェクトと関数の使い分け

    置き場所例考え方のページ
    エンティティ（OOP）Order.confirm() — 状態遷移とルールエンティティと値オブジェクト
    値オブジェクトMoney, Discount — 不変の計算エンティティと値オブジェクト、型でドメインを表す
    純粋関数calculateShipping(total) — 送料ルール関数型と純粋関数
    アプリケーションサービスPlaceOrderUseCase — 流れの制御ドメイン層とユースケース
    ◯ 値オブジェクトとエンティティ 
    // 値オブジェクト
class Money {
  constructor(amount) { this.amount = amount; }
  subtract(other) { return new Money(this.amount - other.amount); }
}

// エンティティ
class Order {
  confirm() {
    if (this.status !== 'draft') throw new Error('確定できません');
    this.status = 'confirmed';
    this.addDomainEvent(new OrderPlaced(this.id));
  }
}

    Money.subtract() は自分を書き換えず新しい Money を返す（不変）ので、「明細の合計 − 割引」を安全に計算できます。Order.confirm() は「下書き（draft）のときだけ確定できる」というルールを自分で守ります。オブジェクト指向と関数型の組み合わせ方は パラダイムの選び方と比較 も参照してください。

    3.4 ドメインイベントの設計

    order.confirm()
     │
     └── OrderPlaced { orderId, lines, occurredAt }
              │
              ├──→ 在庫: StockReserved
              ├──→ 通知: 確認メール
              └──→ 分析: 売上記録

    小規模なモノリスなら プロセス内イベント から始め、成長したらメッセージングへ広げます（→ ドメインイベント、イベント駆動設計）。サービスを分けたあとの連携方式は 41章の 同期API・メッセージ・イベント駆動 を参照してください。

    3.5 よくある設計ミスと修正

    ミス修正考え方のページ
    確定ロジックが Controller に全部Order.confirm() に移す関心の分離、良い設計・悪い設計の比較
    在庫を Order が直接更新OrderPlaced イベントで在庫コンテキストが反応集約とリポジトリ、ドメインイベント
    割引が SQL と画面に分散Discount 値オブジェクトに集約エンティティと値オブジェクト
    貧血 Order（getter のみ）確定・キャンセルを Order のメソッドによくある設計の失敗

    設計の流れ

    業務の言葉 → 型とメソッド名 → 境界とイベント

    4.2つのケースの比較

    観点TODO アプリ注文管理システム
    ドメイン単純（CRUD 中心）業務ルールがある
    コンテキスト1つ注文・在庫など複数
    DDD使わない集約・値オブジェクト・ユビキタス言語を使う

    5.よくある誤解

    誤解1：「どんなアプリでも DDD とイベント駆動で作るのが正しい」

    TODO アプリのようにコンテキストが1つで単純なドメインなら不要です。規模と複雑さに合わせて選ぶことが設計です。

    誤解2：「小さなアプリなら設計を考えなくてよい」

    小規模でも関心の分離（ui / application / domain / storage）や依存の一方向化は効きます。テストのしやすさや、機能を足すときの楽さに表れます。

    誤解3：「在庫の引当は Order がまとめてやったほうが分かりやすい」

    在庫は別のコンテキスト・別の集約です。Order が直接更新すると境界が崩れます。OrderPlaced イベントで在庫側が反応する形にします。

    6.まとめ

    • TODO アプリ：小規模 CRUD なので過剰設計しない。手続き・シンプルな OOP・純粋関数を組み合わせ、ui / application / domain / storage に関心を分ける
    • 振り返りでは「UI に永続化が漏れていないか」「ルールが Task に閉じているか」「依存が一方向か」を確かめる
    • 注文管理システム：業務ルールとユビキタス言語から始め、注文・在庫のコンテキストと Order 集約を設計する
    • エンティティ（状態とルール）・値オブジェクト（不変の計算）・純粋関数（送料ルール）・ユースケース（流れ）を使い分ける
    • コンテキスト間は ドメインイベント で連携し、小規模ならプロセス内から始める
    • 業務の言葉 → 型とメソッド名 → 境界とイベント の順に設計を落とし込む
