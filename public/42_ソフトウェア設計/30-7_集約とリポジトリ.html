    集約とリポジトリ — 一貫性を守る塊と、それを出し入れする窓口

    注文と注文明細のように、いくつかのオブジェクトが関連し合って意味をなすものを「1つの塊」として扱う仕組みが集約、その塊を保存・取得する窓口がリポジトリです。集約ルートと3つの重要なルール、集約の境界の引き方、リポジトリの責任と DAO との違い、ユースケースからの使い方、読み取りを分ける CQRS までを解説します。

    もとにしたノート：04_集約とリポジトリ

    1.このページで扱うこと

    ドメインには、複数のオブジェクトが関連し合って意味をなすものがあります。

    • 注文（Order）と、注文明細（OrderItem）
    • 顧客（Customer）と、配送先（Address）
    • ブログ記事（Article）と、タグ（Tag）、コメント（Comment）

    これらを関連する塊として一括で扱うための仕組みが集約（Aggregate）です。そして、集約を保存したり取り出したりする窓口がリポジトリ（Repository）です。

    集約の中身になるエンティティと値オブジェクトについては エンティティと値オブジェクト を、全体の中での位置づけは 戦術的設計の全体像 を参照してください。

    2.集約（Aggregate）

    2.1 定義

    集約とは

    1つの単位として一貫性を保つ、オブジェクトの塊

    • 中心にある代表のエンティティを集約ルート（Aggregate Root）と呼ぶ
    • 外部から触れるのは集約ルートだけ
    • 集約ルートが中身の一貫性を守る

    2.2 例：注文と注文明細

    // 集約ルート
class Order {
  private items: OrderItem[];

  constructor(
    public readonly id: OrderId,
    items: OrderItem[]
  ) {
    if (items.length === 0) throw new Error('注文には最低1つの商品が必要');
    this.items = items;
  }

  addItem(item: OrderItem) {
    if (this.items.length >= 100) throw new Error('注文数上限');
    this.items.push(item);
  }

  removeItem(itemId: OrderItemId) {
    if (this.items.length === 1) throw new Error('最後の商品は削除できない');
    this.items = this.items.filter(i => !i.id.equals(itemId));
  }

  total(): Money {
    return this.items.reduce(
      (sum, i) => sum.add(i.subtotal()),
      new Money(0, 'JPY')
    );
  }
}

// 集約内のエンティティ
class OrderItem {
  constructor(
    public readonly id: OrderItemId,
    private productId: ProductId,
    private price: Money,
    private quantity: number
  ) {}
  subtotal(): Money {
    return new Money(this.price.amount * this.quantity, this.price.currency);
  }
}

    Order が集約ルート、OrderItem が集約の中のエンティティです。「最低1つ」「上限100」「最後の1つは消せない」というルールは、すべて Order のメソッドの中で守られています。

    2.3 集約の重要なルール

    ルール1：集約ルート経由でしか触らない

    ✕ 悪い例：集約の中身に外から直接触る 
    order.items.push(newItem);
    ◯ 良い例：集約ルート経由 
    order.addItem(newItem);

    直接 items に追加されると、「上限100」のチェックがすり抜けてしまいます。

    ルール2：集約ルートが不変条件を守る

    「注文には最低1つの商品」「注文数上限」などの業務ルール（不変条件：いつでも成り立っていなければならない条件）は、集約ルートの責任です。

    ルール3：1トランザクションで1集約を保存

    1つの操作で複数の集約を更新するようなトランザクション（まとめて成功・失敗させる処理の単位）は避けます。集約は整合性の単位です。

    3.集約の境界の引き方

    3.1 小さく保つ

    集約は小さい方が扱いやすいです。大きい集約は読み込み・保存のたびに大量のデータを扱うので性能も悪く、同時に更新しようとする人どうしがロック（更新中の他者を待たせる仕組み）で詰まります。

    3.2 ルールの単位で

    「必ず同時に整合していないといけないものは同じ集約」「別々のタイミングで整合してもよいものは別集約」と考えます。

    3.3 例：顧客と注文の関係

    ✕ 悪い例：顧客集約の中に全注文を持たせる 
    Customer
├── orders: Order[] ← 注文が大量にあると重い
    ◯ 良い例：顧客と注文は別集約。参照は ID だけ 
    Customer (Aggregate)
   id: CustomerId

Order (Aggregate)
   id: OrderId
   customerId: CustomerId  ← 参照はIDのみ

    集約間の参照は他集約のオブジェクトではなく、ID で持つのが原則です。必要になったら、その ID を使ってリポジトリから取り出します。

    4.リポジトリ（Repository）

    4.1 定義

    リポジトリとは

    集約を保存・取得するための抽象的な窓口

    • 集約ルート単位で扱う
    • インターフェースはドメイン層に置く
    • 実装はインフラ層に置く（DB アクセスなど）

    インターフェースを内側に、実装を外側に置くことで、ドメイン層は DB を知らずに済みます。これは41章の依存性逆転の原則と、クリーンアーキテクチャの依存性のルールを DDD の部品に当てはめたものです。

    4.2 例

    // ドメイン層: インターフェース
interface OrderRepository {
  findById(id: OrderId): Promise<Order | null>;
  save(order: Order): Promise<void>;
  delete(id: OrderId): Promise<void>;
}

// インフラ層: 実装
class MySQLOrderRepository implements OrderRepository {
  async findById(id: OrderId): Promise<Order | null> {
    const row = await db.query('SELECT * FROM orders WHERE id = ?', id.value);
    const items = await db.query('SELECT * FROM order_items WHERE order_id = ?', id.value);
    return this.toDomain(row, items); // DB行をドメインオブジェクトに変換
  }

  async save(order: Order): Promise<void> {
    await db.transaction(async t => {
      await t.query('UPSERT INTO orders ...', order);
      await t.query('DELETE FROM order_items WHERE order_id = ?', order.id);
      for (const item of order.items) {
        await t.query('INSERT INTO order_items ...', item);
      }
    });
  }
}

    1つの集約（注文）を保存するために、2つのテーブル（orders と order_items）を1トランザクションでまとめて書いている点に注目してください。

    5.リポジトリの3つの責任

    1. 保存する

    集約を丸ごと保存。集約内の子オブジェクトまで一括。

    2. 取得する

    ID で取り出す。集約全体を復元する。

    3. 削除する

    集約単位で削除。

    5.1 やるべきでないこと

    • 業務ルールを書く（→ ドメインに書く）
    • 集約の中身にアクセスさせるクエリ（→ 集約ルート経由で）
    • 検索・集計のロジック（→ 読み取り専用の Query サービスに分ける場合もある。8章参照）

    6.リポジトリパターンと普通の DAO の違い

    DAO（Data Access Object）は、テーブルへの読み書きを包むクラスです。見た目は似ていますが、考え方が違います。

    観点DAORepository
    扱う単位テーブル1つ集約（複数テーブル束ねる）
    層データアクセス層ドメイン層（インターフェース）
    思想SQL をラップドメインの振る舞い
    例UserDAO → users テーブルOrderRepository → orders + order_items

    DAO はDB 寄り、Repository はドメイン寄り、と捉えると分かりやすいです。

    7.コードでの使い方

    // ユースケース層
class CancelOrderUseCase {
  constructor(private orderRepo: OrderRepository) {}

  async execute(orderId: OrderId): Promise<void> {
    const order = await this.orderRepo.findById(orderId);
    if (!order) throw new Error('注文が見つからない');

    order.cancel(); // 業務ルールはOrder（集約ルート）が知っている

    await this.orderRepo.save(order);
  }
}
    1. 取り出す — リポジトリから集約を丸ごと復元する
    2. 操作する — 集約ルートのメソッドを呼ぶ（ルールは集約が守る）
    3. 保存する — リポジトリに集約を丸ごと渡す

    という単純な流れです。ユースケースについては ドメイン層とユースケース で詳しく扱います。

    8.CQRS：読み取り側は別にすることも

    複雑な読み取り（検索・集計・ダッシュボード）をリポジトリにすべて任せると太りすぎるため、

    • 書き込み：Repository ＋ 集約
    • 読み取り：Query ／ DTO（画面に渡すためのデータの入れ物）で直接返す

    と分ける CQRS（Command Query Responsibility Segregation：コマンドとクエリの責務分離）という考え方もあります。DDD と組み合わせてよく使われます。設計の観点では「集約とリポジトリは書き込みの正しさのための道具であり、画面表示の都合まで背負わせない」ことがポイントです。段階的な導入方法や注意点は41章の CQRS を参照してください。

    9.よくある誤解

    誤解1：「集約は大きいほうがいい」

    逆です。小さい集約の方が性能も良く扱いやすいです。

    誤解2：「Repository はただの DB ラッパー」

    集約単位で扱い、ドメインルールを守る窓口です。単なる ORM（オブジェクトと DB のテーブルを対応づけるライブラリ）のラッパーではありません。

    誤解3：「集約同士を参照で持つ」

    ID で持ち、必要な時に Repository で取得するのが原則です。

    10.まとめ

    • 集約は、1つの単位として一貫性を保つオブジェクトの塊。入り口は集約ルートだけ
    • ルール：ルート経由でしか触らない／ルートが不変条件を守る／1トランザクション1集約
    • 境界は小さく、「必ず同時に整合すべきもの」の単位で引く。集約間の参照は ID
    • リポジトリは集約を保存・取得・削除する窓口。インターフェースはドメイン層、実装はインフラ層
    • DAO はテーブル単位で DB 寄り、Repository は集約単位でドメイン寄り
    • 使い方は「取り出す → 操作 → 保存」。複雑な読み取りは CQRS で分けることもある
