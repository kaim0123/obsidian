    関数型と純粋関数 — 不変データと副作用を端に寄せる設計

    関数型の考え方（第一級関数・純粋関数・副作用・不変性・パイプライン）を、設計の視点で学びます。参照透過性がなぜ嬉しいのか、不変データで状態をどう扱うのか、関数合成・データと振る舞いの分離・「副作用を端に寄せる」置き方までを、TypeScript と JavaScript のコードで解説します。専用の関数型言語がなくても実践できる考え方です。

    もとにしたノート：01_関数型指向の考え方 / 02_不変データと純粋関数_関数型の設計原則

    1.このページで扱うこと

    関数型の考え方 — 純粋関数・副作用・不変性 — を、設計の視点で学びます。専用言語がなくても、JavaScript・Python・Java・TypeScript などで実践できます。歴史的な背景はソフトウェア設計年表の「関数型指向」を参照してください。

    前半で関数型の基本（第一級関数・純粋関数・副作用・不変性・パイプライン）を概観し、後半でそれを設計の原則として一段深く掘り下げます。

    • 参照透過性：なぜ純粋関数は「設計として」嬉しいのか
    • 不変データ：変更しないで、どうやって状態を扱うのか（永続データ構造・構造共有）
    • 関数合成：小さな関数を組み合わせて大きな処理を作る
    • データと振る舞いの分離：オブジェクト指向との対比
    • 副作用を端に寄せる：設計全体としての置き方

    メソッド単位の書き方は別の章で

    純粋関数と副作用のメソッド単位の書き方は、46_メソッド設計の「02_純粋関数と副作用」と「03_Functional_Core_Imperative_Shell」が本拠地です。このページでは設計全体への効き方を中心に扱います。

    2.関数型とは何か — 第一級関数と純粋関数

    関数型とは、関数を第一級オブジェクトとして扱い、副作用を最小化する設計を重視する考え方です。

    概念意味
    第一級関数関数を変数に代入・引数に渡す・戻り値にできる
    純粋関数同じ入力 → 同じ出力。外部状態を変えない
    ◯ 純粋関数 
    function addTax(price, rate) {
  return price * (1 + rate);
}
    ✕ 非純粋（副作用あり） 
    let total = 0;
function addToTotal(price) {
  total += price;  // 外部の total を変更
}

    3.参照透過性 — 「置き換えてよい」ことの価値

    3.1 定義

    式を、その評価結果の値に置き換えても、プログラムの意味が変わらないとき、その式は参照透過（referentially transparent）である。

    // 参照透過：add(2, 3) をどこで 5 に置き換えても意味は変わらない
const add = (a: number, b: number) => a + b;
const x = add(2, 3) * add(2, 3);   // ≡ 5 * 5

// 参照透過でない：呼ぶたびに結果が変わる・外の世界を変える
let counter = 0;
const next = () => ++counter;
const y = next() * next();          // 1 * 2。next() を値に置き換えられない

    純粋関数（同じ入力に同じ出力を返し、副作用がない関数）の呼び出しは、参照透過です。

    3.2 設計として何が嬉しいのか

    効果説明
    局所的に理解できる関数の中だけを読めば、何をするか分かる。外のどこかで変数が書き換えられる心配がない
    テストが単純入力を与えて出力を確かめるだけ。モックも、事前準備（DB の初期化など）も不要
    安全にリファクタリングできる式を変数に括り出す・インライン化するなどの変形が、意味を変えずにできる
    キャッシュ（メモ化）できる同じ入力なら結果も同じなので、結果を保存して再利用できる
    並行処理が安全共有状態を書き換えないので、ロックなしで並列に実行できる

    これはカプセル化と情報隠蔽と同じ方向の効果です。カプセル化が「状態を隠す」ことで影響範囲を狭めるのに対し、参照透過性は「状態を持たない」ことで影響範囲をゼロにします。

    認知負荷の低いコード

    John Ousterhout の言葉を借りれば、純粋関数は「知らなければならないことが少ない（認知負荷が低い）」コードであり、「知らないことを知らない（unknown unknowns）」を生みにくいコードです（→ ソフトウェア設計の全体像）。

    4.副作用（Side Effect）とその管理

    副作用とは、関数が戻り値以外に外部に影響を与えることです。

    • グローバル変数の変更
    • DB への書き込み
    • コンソール出力・メール送信
    • 引数のオブジェクトの変更

    設計のコツは、副作用を「境界」に押し出すことです。純粋な計算・変換をテストしやすい中心に置き、I/O・DB・HTTP は副作用の境界（アダプタ層）に集めます。

      設計のコツ: 副作用を「境界」に押し出す

  [純粋な計算・変換]  … テストしやすい中心
         │
         ▼
  [I/O・DB・HTTP]     … 副作用の境界（アダプタ層）

    すべてを純粋にする必要はありません。副作用の場所を限定するのが現実的です（設計全体での置き方は8章）。

    5.不変データ — 変えずに新しく作る

    5.1 不変データとは

    不変性（Immutability）とは、データを書き換えず、新しい値を作ることです。一度作ったら中身を変えないデータを不変データと呼び、変更が必要なときは変更を反映した新しいデータを作ります。

    ✕ 命令型：元の配列を変更 
    items.push(newItem);
    ◯ 関数型：新しい配列を返す 
    const newItems = [...items, newItem];

    オブジェクトでも同じです。

    ✕ 可変：元のデータを書き換える 
    function addItemMutable(cart: Cart, item: Item) {
  cart.items.push(item);           // 呼び出し元の cart も変わる
  cart.total += item.price;
}
    ◯ 不変：新しいデータを返す 
    function addItem(cart: Cart, item: Item): Cart {
  return {
    ...cart,
    items: [...cart.items, item],
    total: cart.total + item.price,
  };
}

    5.2 なぜ不変にするのか

    まず、不変性のメリットを短くまとめると次のとおりです。

    メリット説明
    共有によるバグ防止誰かが書き換えても元データは安全
    推論しやすい「いつ何が変わったか」が明確
    並行処理に有利ロックが不要になりやすい

    可変データで起きる問題と比べると、より具体的に分かります。

    可変データで起きる問題不変データでは
    どこで変わったか分からない：同じオブジェクトを複数の場所が参照していると、一か所の変更が予期せぬ場所に波及する（エイリアシング問題）誰も変えられないので、渡した先で変わる心配がない
    時間による不整合：処理の途中でデータが変わり、前半と後半で前提が違う処理中に前提が変わらない
    並行処理の競合：複数スレッドが同時に書き換えて壊れる書き換えがないので競合しない
    変更履歴が残らない：元に戻す・比較するのが難しい古い版がそのまま残るので、Undo・差分比較・タイムトラベルデバッグが容易

    React が状態の更新に新しいオブジェクトを渡すことを求めるのも、「参照が変わったかどうか」だけで変更を検出できるからです（→ 47_フロントエンド設計）。

    5.3 「毎回コピーしたら遅いのでは？」— 永続データ構造と構造共有

    不変データへのよくある懸念は「毎回全体をコピーしたら遅くなる」というものです。これを解決するのが永続データ構造（Persistent Data Structure）と構造共有（Structural Sharing）です。

    元のリスト:      A → B → C
先頭に X を追加: X ↗
                （A → B → C はそのまま共有）
    • 変更された部分だけを新しく作り、変わっていない部分は古い版と共有する
    • 木構造なら、根から変更箇所までの経路だけを作り直せばよい
    • Clojure・Scala・Haskell などのコレクションや、JavaScript の Immer・Immutable.js がこの仕組みを使っている

    「永続」の意味

    「永続（persistent）」は DB に保存するという意味ではなく、古い版が消えずに残り続けるという意味です。

    5.4 TypeScript で不変性を表す

    type Money = Readonly<{ amount: number; currency: "JPY" | "USD" }>;
type Cart = Readonly<{ items: ReadonlyArray<Item>; total: Money }>;

const cart: Cart = { items: [], total: { amount: 0, currency: "JPY" } };
// cart.items.push(item);   ← コンパイルエラー
    • readonly・Readonly<T>・ReadonlyArray<T>・as const でコンパイル時に書き換えを防ぐ
    • ただし実行時には防げないので、必要なら Object.freeze や Immer を使う

    5.5 DDD の値オブジェクトとの関係

    DDD の値オブジェクト（金額・住所・期間など）は、不変であることが基本ルールです（→ エンティティと値オブジェクト）。これはオブジェクト指向の中に関数型の考え方を取り入れたもの、と見ることができます。OOP の値オブジェクトと不変性は相性がよいのです。

    6.関数合成とパイプライン — 小さな部品を組み合わせる

    6.1 合成とは

    関数 f: A → B と g: B → C があれば、それをつないで A → C の関数が作れます。これが関数合成です。

    const trim = (s: string) => s.trim();
const toLower = (s: string) => s.toLowerCase();
const removeSpaces = (s: string) => s.replace(/\s+/g, "");

// 合成：小さな関数をつないで新しい関数を作る
const pipe = <T>(...fns: Array<(x: T) => T>) => (x: T) => fns.reduce((v, f) => f(v), x);
const normalizeEmail = pipe(trim, toLower, removeSpaces);

normalizeEmail("  Taro@Example.com ");  // "taro@example.com"

    6.2 データ変換パイプラインの読みやすさ

    関数型では、データを変換の連鎖として表現します。

    const result = orders
  .filter(o => o.isActive)
  .map(o => o.total)
  .reduce((sum, t) => sum + t, 0);
    • 各ステップが小さな純粋関数
    • データの流れが左から右に読める
    • 中間状態が明示的

    関数分割の考え方としては、46_メソッド設計（目次）とも関連します。

    6.3 設計としての意味

    • 部品が小さく、1つのことだけをする：凝集度と結合度でいう機能的凝集
    • 部品同士は「型」でしかつながらない：B を出す関数と B を受け取る関数は、互いの中身を知らない（疎結合）
    • ワークフローをパイプラインとして表せる：「注文を検証する → 価格を計算する → 確認メールを作る」のような業務の流れが、そのままコードの形になる（→ 型でドメインを表す）

    オブジェクト指向が「オブジェクトの組み合わせ（合成）」で大きな構造を作るのに対し、関数型は「関数の合成」で大きな処理を作ります。どちらも「継承より合成」の考え方です（→ 継承と合成）。

    7.データと振る舞いを分ける

    7.1 オブジェクト指向との対比

    オブジェクト指向関数型
    基本の単位データと振る舞いを1つのオブジェクトにまとめるデータ（型）と振る舞い（関数）を分ける
    状態オブジェクトの中に隠して、メソッドで変える不変データとして外に出し、関数で新しい版を作る
    拡張しやすいもの新しい種類（クラス）を足すのが簡単新しい操作（関数）を足すのが簡単
    拡張しにくいもの全クラスに新しい操作を足す全関数に新しい種類を足す

    最後の2行はExpression Problem（式の問題）として知られる、パラダイム間の本質的なトレードオフです。

    操作を足す（例：面積計算）

    図形に「面積計算」という操作を足すのは、関数型なら関数を1つ書くだけ。OOP なら全クラスにメソッドを足す。

    種類を足す（例：三角形）

    図形に「三角形」という種類を足すのは、OOP ならクラスを1つ書くだけ。関数型なら全関数に分岐を足す。

    どちらが優れているかではなく、「種類が増えやすいか、操作が増えやすいか」で選びます（→ パラダイムの選び方と比較）。

    7.2 代数的データ型

    関数型では、データを代数的データ型（「かつ」と「または」の組み合わせでデータの形を表す型）で表すことが多いです。

    種類意味例
    直積型（AND）「A かつ B かつ C」を持つ顧客 ＝ 名前 かつ メール かつ 住所（TypeScript のオブジェクト型）
    直和型（OR）「A または B または C」のどれか1つ支払い方法 ＝ カード または 銀行振込 または 代引き（TypeScript の判別可能ユニオン）
     
    type PaymentMethod =
  | { kind: "card"; cardNumber: string; expiry: string }
  | { kind: "bankTransfer"; accountId: string }
  | { kind: "cashOnDelivery" };

    直和型は、「ありえない組み合わせを表現できないようにする」設計に直結します。詳しくは型でドメインを表すで扱います。

    8.副作用を端に寄せる

    純粋関数だけではプログラムは何もできません（DB に保存も、画面表示もできない）。関数型の設計は副作用をなくすのではなく、副作用を端に寄せ、中心を純粋に保つことを目指します。

    • これは Gary Bernhardt の Functional Core, Imperative Shell（46_メソッド設計「03_Functional_Core_Imperative_Shell」）であり、
    • アーキテクチャのレベルではヘキサゴナル／クリーンアーキテクチャと同じ形です（→ 依存性のルールとクリーンアーキテクチャ、ヘキサゴナルアーキテクチャ）

    つまり、関数型の設計原則は関数の書き方にとどまらず、システム全体の構造の原則としても働きます。

    9.関数型の原則を取り入れる順番（OOP 言語で）

    TypeScript・Java・C# などの OOP 言語でも、関数型の原則は段階的に取り入れられます。

    段階やること効果
    1計算ロジックを純粋関数に切り出す（価格計算・バリデーション・変換）テストが一気に書きやすくなる
    2値オブジェクト・DTO を不変にする（readonly）「どこで変わったか」問題が消える
    3ループを map / filter / reduce に置き換える何をしているかが読みやすくなる
    4状態の種類を直和型で表すありえない状態を型で防げる
    5副作用をユースケースの最初と最後に集める中心のロジックが純粋になり、構造が明確になる

    10.関数型の考え方が向く場面と限界

    向く場面

    • データの検証・変換・集計
    • 並行・並列処理
    • テスト容易性を重視する計算ロジック
    • パイプライン型の処理

    限界

    • 状態を持つドメイン（注文ステータスの遷移など）の表現が不自然になりうる
    • I/O は結局副作用 — 境界の設計が必要
    • モナド（失敗・非同期などの文脈を包んでつなぐための抽象）等の抽象は学習コストが高い
    • チームが命令型に慣れていると読みにくいことも

    関数型は「考え方」として使う

    関数型は「全部関数で書く」ではなく、副作用を減らし、変換を読みやすくする「考え方」として使います。

    11.よくある誤解

    誤解1：「関数型を使うには Haskell などの関数型言語が必要」

    誤りです。参照透過性・不変データ・関数合成・副作用の分離は、TypeScript でも十分に実践できます。

    誤解2：「不変データは遅い」

    多くの場合は誤りです。構造共有によりコピーのコストは小さく抑えられます。また、変更検出が参照比較だけで済むので、全体としては速くなることもあります。ただし、大量データを頻繁に更新する箇所では計測して判断します。

    誤解3：「関数型とオブジェクト指向は対立する」

    誤りです。値オブジェクトの不変性、戦略パターン（関数を渡す）、ヘキサゴナルアーキテクチャ（副作用を外側に）など、両者は多くの場面で混ざり合っています。

    12.まとめ

    • 関数型は第一級関数と純粋関数を重視する
    • 参照透過性：式を値に置き換えても意味が変わらない。局所的に理解でき、テスト・リファクタリング・並行処理が容易になる
    • 不変データ：変えずに新しく作る。エイリアシング・時間による不整合・競合を防ぐ。構造共有で効率も保てる
    • 関数合成：小さな関数を型でつなぐ。パイプラインでデータ変換を表し、機能的凝集と疎結合を自然に実現する
    • データと振る舞いを分ける：操作の追加に強い（OOP は種類の追加に強い）。直和型でありえない状態を防ぐ
    • 副作用を端に寄せる：Functional Core, Imperative Shell。アーキテクチャのレベルではヘキサゴナル／クリーンと同じ形
    • 向く場面（検証・変換・集計）と限界（状態遷移・I/O 境界・学習コスト）を知って使う
