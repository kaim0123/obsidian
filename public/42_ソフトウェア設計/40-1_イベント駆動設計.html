    40 イベント駆動設計

    イベント駆動設計 — 「起きた事実」で部品をつなぐ

    同期呼び出しの限界から出発し、「イベント＝過去形の事実」で部品をつなぐ考え方を学びます。ドメインイベントの設計、結果整合性・冪等性・スキーマ進化、そして「いつイベントにし、いつ同期で済ませるか」の実践判断までをまとめます。

    もとにしたノート：01_イベント駆動を学ぶ理由 / 02_ドメインイベントとシステム連携 / 03_イベント駆動の実践判断

    1.このページで扱うこと

    イベント駆動（「何かが起きた」という知らせをきっかけに、関係する部品がそれぞれ反応する作り方）の設計を、次の順に学びます。

    • 同期呼び出しの限界と、イベントによる 疎結合（部品どうしが互いをあまり知らずに済む状態）のメリット
    • ドメインイベントの設計と、DDD とイベント駆動のつながり
    • 結果整合性・冪等性・スキーマ進化という、イベントを使うなら避けられない論点
    • いつイベントにし、いつ同期にするかという 実践判断

    イベント駆動の歴史的な背景は ソフトウェア設計年表 の「イベント駆動」を参照してください。メッセージブローカーの種類やサービス間の連携方式、分散トランザクション（SAGA）など アーキテクチャとしてのイベント駆動 は41章で扱います（→ 同期API・メッセージ・イベント駆動、データ所有権とSAGA）。このページでは「設計の考え方」に絞ります。

    2.同期呼び出しの限界

    2.1 同期呼び出しの結合と障害伝播

    サービス A がサービス B を 同期的に直接呼ぶ（B の返事が来るまで A が待つ）と、B の調子がそのまま A に響きます。

    問題説明
    結合A は B の存在・API を知る必要がある
    時間的結合両方が同時に稼働している必要がある
    スケール連鎖B の負荷が A に直結する

    結合の種類や強さの測り方は 凝集度と結合度、41章の コナーセンス も参考になります。

    3.イベントと Publisher / Subscriber

    3.1 イベントとは何か（過去形の事実）

    イベントの定義

    イベントは、「何かが起きた」という過去形の事実です。

    • OrderPlaced（注文が確定した）
    • PaymentCompleted（支払いが完了した）
    • StockReserved（在庫が引当された）

    似たものに「命令」がありますが、向きが違います。

    命令：「在庫を引当てろ」

    送り手が 受け手を指定 して、やってほしいことを頼む。

    イベント：「注文が確定した」

    起きた事実を publish（発行） するだけ。誰が反応するかは知らない。

    3.2 Publisher / Subscriber の考え方

    • Publisher：イベントを発行する側
    • Subscriber：イベントを受け取り、反応する側
    • Publisher は 誰が受け取るか知らなくてよい（疎結合）

    4.メリットと、万能ではない理由

    4.1 疎結合と非同期処理のメリット

    非同期処理（相手の処理の完了を待たずに先へ進むやり方）と組み合わせると、次のメリットがあります。

    メリット説明
    障害の局所化在庫サービスが落ちても注文は受け付けられる（キューに溜める）
    独立スケール分析処理だけをスケールアップできる
    機能追加新しい Subscriber を追加するだけ。Publisher は変更不要
    ピーク吸収キューでバッファリング（一時的に溜めておく）できる

    4.2 イベント駆動は万能ではない

    デメリット説明
    結果整合性即時に全体が整合しない。UI 設計が難しくなる
    デバッグ非同期・分散で追跡が困難。トレーシングが必要
    複雑さ単純な CRUD にまでイベントを使うと過剰
    スキーマ進化イベント形式の変更管理が必要

    向いている場面

    イベント駆動が向いているのは、複数の関心が1つの出来事に反応する、分散・非同期が価値ある場面です。

    5.ドメインイベントとシステム連携

    5.1 ドメインイベントの設計

    ドメインイベントは、ドメイン（業務の領域）の中で起きた、意味のある出来事です。詳しくは ドメインイベント を参照してください。

    ◯ 良い例：業務ルールを実行したあと、起きた事実をドメインイベントとして記録する 
    class OrderPlaced {
  constructor(orderId, occurredAt, items) {
    this.orderId = orderId;
    this.occurredAt = occurredAt;
    this.items = items;
  }
}

class Order {
  confirm() {
    // 業務ルールの実行
    this.status = 'confirmed';
    // ドメインイベントを発行
    this.addDomainEvent(new OrderPlaced(this.id, new Date(), this.items));
  }
}

    設計のポイントは3つです。

    • 過去形の名前にする（OrderPlaced。PlaceOrder ではない）
    • 発生時刻・識別子を含める
    • Subscriber が必要な情報だけを持つ

    5.2 DDD とイベント駆動の接続

    DDD（コンテキスト内）イベント駆動（コンテキスト間）
    起きることOrder.confirm() でドメインルールを実行OrderPlaced を publish
    その先→在庫・決済・通知が subscribe（購読して反応）
    • 集約内：ドメインイベントで「起きたこと」を記録する（集約は 集約とリポジトリ）
    • コンテキスト間：イベントをメッセージとして配送する（コンテキストは 境界づけられたコンテキスト）
    • 業務の 出来事 が連携の単位になる

    6.イベントを使うなら避けられない3つの論点

    6.1 結果整合性（Eventual Consistency）の受け入れ

    結果整合性とは、即時には整合しないが、時間とともに収束する状態です。

    注文確定（即時）
     │
     ├── 在庫引当（数秒後）
     ├── 決済（数秒後）
     └── 通知（数秒後）

    強い整合性（同期）

    全部の完了まで待つ。シンプルだが 遅い・脆い。

    結果整合性（非同期）

    すぐ応答し、後から収束する。速いが UI・設計が複雑。

    どちらが正しいということはなく、トレードオフを 意図的に選ぶ ことが重要です。サービスごとにデータを持つ場合の整合性の取り方（SAGA など）は データ所有権とSAGA で扱います。

    6.2 冪等性と再試行

    イベントは 重複配送（同じイベントが2回以上届く）や 失敗時の再試行 があり得ます。そこで必要になるのが冪等性です。

    冪等性（Idempotency）

    同じイベントを 何回処理しても結果が同じ になる性質。

    StockReserved(orderId=123) を 2 回受信
     │
     └── 2 回目は「既に引当済み」として無視（冪等）
    • イベント ID やビジネスキー（注文番号など業務上の識別子）で 重複を検知 する
    • Subscriber は 何度実行しても安全 に設計する

    6.3 イベントスキーマの進化

    イベントの形式（スキーマ）は、受け取る側が複数いるため バージョン管理 が必要です。

    方針内容
    後方互換新しいフィールドは optional（省略可）にする。古い Consumer も動く
    バージョン番号OrderPlacedV2 などと名前で区別する
    変換層古い形式を新しい形式に変換する Adapter を置く

    破壊的変更に注意

    フィールドの削除・意味の変更などの破壊的変更は、Consumer（受け取る側）が次々に壊れる 原因になります。

    7.イベント駆動の実践判断

    7.1 いつイベントにするか・いつ同期にするか

    同期が向くイベントが向く
    即時の応答が必須（残高確認）複数の後続処理がある
    強い整合性が必要障害耐性・スケールが重要
    単純な CRUDコンテキストをまたぐ連携
    小規模・モノリス内独立デプロイのサービス群

    判断の問い

    「呼び出し先が落ちたら、呼び出し元も止まっていいか？」
    「後続処理は即時に完了している必要があるか？」

    7.2 過剰な非同期化を避ける

    すべてをイベントにすると、シンプルな処理まで複雑になります。

    過剰な例

    ユーザー名変更 → 3 イベント → 3 Subscriber → 結果整合性

    適切な例

    ユーザー名変更 → 同期で DB 更新 → 完了

    YAGNI（You Aren't Gonna Need It：必要になるまで作らない）の精神で、必要になるまでは同期で十分なことが多いです（→ 変化に強い設計）。

    7.3 デバッグとトレーシングの必要性

    非同期・分散では、1つの処理がどこを通ったかの 追跡 が難しくなります。

    • 相関 ID（Correlation ID）：一連の処理に共通の ID をイベントに載せる
    • OpenTelemetry などで トレーシング（処理の経路と時間を記録すること）をする
    • イベントの ログ・監査 を設計に含める
    OrderPlaced { orderId, correlationId: "abc-123", ... }
     │
     └── 在庫・決済・通知すべて同じ correlationId で追跡

    観測の仕組み全体は 41章の 観測性 を参照してください。

    7.4 UI とユーザー体験への影響

    結果整合性では、「まだ反映されていない」状態をユーザーにどう見せるか が課題です。

    手法例
    楽観的 UI「処理中です」と表示し、後から更新する
    ポーリング状態を定期的に確認する
    通知完了したらメール・プッシュで知らせる

    「注文完了」と表示するタイミングを、業務側と合意 しておくことが重要です。

    7.5 小規模システムでの適用範囲

    小規模・モノリスでは、次のように考えます。

    • ドメインイベント は、集約内の記録・テストに使う（プロセス内で完結）
    • メッセージブローカー は不要なことが多い
    • コンテキストが1つなら 同期呼び出しで十分

    小規模

    ドメインイベントの「考え方」だけ取り入れる

    中〜大規模

    メッセージング・結果整合性まで検討する

    段階的に導入するのが現実的です。

    8.よくある誤解

    誤解1：「イベントと命令は同じ。名前の付け方が違うだけ」

    違います。命令は送り手が受け手を指定して「やれ」と頼むもの、イベントは「起きた」という事実を流すだけで、誰が反応するかを送り手は知りません。この違いが疎結合を生みます。

    誤解2：「イベント駆動にすれば必ず良い設計になる」

    万能ではありません。結果整合性・デバッグの難しさ・スキーマ進化という代償があります。単純な CRUD や小規模なモノリスでは、同期呼び出しのほうが適切なことが多いです。

    誤解3：「メッセージは1回だけ届く前提でよい」

    重複配送や再試行は起こり得ます。Subscriber は冪等に作り、イベント ID やビジネスキーで重複を検知します。

    誤解4：「ドメインイベントを使うにはメッセージブローカーが必須」

    小規模ならプロセス内のドメインイベントだけで十分です。「起きた事実を記録する」という考え方から始め、必要になったらメッセージングへ広げます。

    9.まとめ

    • 同期呼び出しは 結合・時間的結合・障害伝播 を生む
    • イベントは 過去形の事実。Publisher / Subscriber で疎結合にでき、障害の局所化・独立スケール・機能追加・ピーク吸収が得られる
    • ただし 万能ではない。結果整合性・デバッグ・複雑さ・スキーマ進化とのトレードオフ
    • ドメインイベントは業務の出来事を表す。集約内のイベントがコンテキスト間連携の起点 になる
    • 結果整合性はトレードオフとして意図的に受け入れ、冪等性とスキーマ進化 を設計に含める
    • 同期とイベントは要件で選ぶ。過剰な非同期化を避け、トレーシングと UI を設計に含める。小規模ではドメインイベントの考え方から始める
