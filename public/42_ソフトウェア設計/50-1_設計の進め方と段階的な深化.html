    50 設計プロセス

    設計の進め方と段階的な深化 — たたき台を作り、育てていく

    要件を整理し、ユースケースと名詞・動詞から構造の候補を見つけ、簡単な図で議論できる「たたき台」を作るまでの流れを学びます。さらに、設計は一度で完成しないことを前提に、概要から詳細へ深め、リファクタリング・技術的負債の管理・ADR で育てていく進め方をまとめます。

    もとにしたノート：01_設計の進め方 / 02_設計の段階的な深化

    1.このページで扱うこと

    これまでのページで学んだ原則やパラダイム、DDD を、実際の開発で どの順番で使うか を扱います。

    • 要件から設計案を作る 実践的なプロセス（要件整理 → ユースケース → 名詞・動詞 → 図 → たたき台）
    • 60〜90 分でできる 最初の設計案ワークショップ
    • 設計を 段階的に深める 考え方（概要設計 → 詳細設計、リファクタリング、技術的負債、ADR）

    2.要件から設計へ — 何を作るかを整理する

    設計の出発点は 「何を作るか」 の理解です。次の4つを整理します。

    整理するもの例
    機能要件（システムが何をするか）ユーザーは注文できる、管理者は在庫を更新できる
    非機能要件（速さ・可用性など、どれだけうまく動くか）100 同時接続、99.9% 可用性
    制約Java で書く、既存 DB を使う、3 ヶ月でリリース
    用語注文・明細・出荷の定義

    要件が曖昧なまま設計

    後から大幅な作り直しになる。

    用語を先に揃える

    DDD の ユビキタス言語 の出発点になる。

    非機能要件の詳しい整理は 41章の 品質特性と非機能要件 を参照してください。

    3.ユースケースと名詞・動詞から構造を見つける

    3.1 ユースケースと振る舞いの洗い出し

    ユースケースは、ユーザー（または外部システム）が システムに何をさせるか です。たとえば「注文を確定する」なら、次の手順に分解できます。

    1. カートの内容を検証する
    2. 在庫を確認する
    3. 金額を計算する
    4. 注文を保存する
    5. 確認メールを送る
    • 動詞 が振る舞いの候補になる
    • 誰が 何をするか（アクター：システムを使う人や外部システム）を明確にする
    • 正常系と異常系（在庫が足りない、カードが通らないなど）の両方を考える

    3.2 名詞と動詞から構造を見つける

    オブジェクト指向設計の古典的な手法です。要件やユースケースの文章から名詞と動詞を拾います。

    抽出設計への対応
    名詞クラス・エンティティの候補（Order, Item, Customer）
    動詞メソッド・ユースケースの候補（確定する、計算する）
     
    「顧客が注文を確定する」
  名詞: 顧客、注文  → Customer, Order
  動詞: 確定する     → order.confirm()

    全部をクラスにしない

    名詞をそのまま全部クラスにする必要はありません。責務と関心 で取捨選択します（→ オブジェクト指向とクラス、関心の分離。より詳しくは 44_クラス設計・デザインパターン）。

    4.スケッチと図の使い方（入門）

    完璧な UML（ソフトウェアの図の標準的な書き方）より、手書きスケッチ で十分なことが多いです。

    図用途
    箱と矢印モジュール・サービスの関係
    クラス図（簡易）主要な型と関係
    シーケンス図（簡易）処理の流れ

    図は 議論の道具 です。コードと一緒に更新し続けても、使い捨てでもかまいません。チームで長く使う図の描き方は 41章の C4モデルとarc42 で扱います。

    5.最初の設計案を作るワークショップ

    60〜90 分でできる演習の流れです。

    1. 要件を3行で書く
    2. ユースケースを1つ選ぶ
    3. 名詞・動詞を洗い出す
    4. モジュール候補を3〜5個に分ける
    5. 主要なクラスを5個以内で決める
    6. 依存の方向を矢印で描く
    7. 「ここが変わりそう」を1箇所マークする

    目的はたたき台

    完璧を目指さず、議論できるたたき台 を作ることが目的です。「変わりそうな箇所」の見つけ方は 変化に強い設計 を参照してください。

    6.設計の段階的な深化

    6.1 最初から完璧な設計は不要

    • 要件は開発中に変わる
    • 理解はコードを書いて初めて深まる
    • 過剰な先行設計は 無駄と誤り になりやすい

    進化する設計 を受け入れることが、長期的な成功につながります。アーキテクチャのレベルでの同じ考え方は 41章の 進化的アーキテクチャと適応度関数 にあります。

    6.2 概要設計 → 詳細設計の流れ

    段階内容粒度
    概要設計モジュール・主要な境界・パラダイムの選択大まか
    詳細設計クラス・インターフェース・主要な振る舞い具体

    概要の例

    「注文」「在庫」「通知」に分ける

    詳細の例

    Order 集約に confirm() を置く、Repository インターフェースを定義する

    一度に詳細まで行かず、実装が進むにつれて詳細化 します。設計の階層（アーキテクチャ・モジュール・クラス・メソッド）については 設計の階層と基本用語 を参照してください。

    7.リファクタリングと技術的負債

    7.1 リファクタリングと設計の更新

    リファクタリングは、振る舞いを変えずに 構造を改善 することです。次のようなサインがきっかけになります。

    きっかけ例
    同じ変更で複数箇所を触るExtract Class（クラスの抽出）で責務を分離する
    テストが書きにくい依存を注入可能にする
    名前と実態がズレたRename（名前の変更）、Move Method（メソッドの移動）

    設計は リファクタリングの蓄積 で育ちます。具体的な手順とパターンは テストとリファクタリング、より細かな技法は 46_メソッド設計 を参照してください。

    7.2 技術的負債との向き合い方

    技術的負債とは、短期的な妥協が将来のコストになる状態です。

    意図的な負債

    「リリース優先で境界を後回し。3 ヶ月後に分割」

    無意識の負債

    「気づかないうちに神クラス化」

    • 意図的なら、期限と理由を記録する（ADR）
    • 可視化 して優先度をつける
    • 絶えず小さく返済 する

    負債の分類や返済戦略は 41章の 技術的負債 で詳しく扱います。チームでの可視化は チームで設計を守る も参照してください。

    8.設計判断の記録（ADR 入門）

    ADR（Architecture Decision Record）は、重要な設計判断を短く記録する形式です。

    ◯ 良い例：状況・決定・理由・結果を短く残す 
    # ADR-001: 注文と在庫を別モジュールに分ける

## 状況
注文確定時に在庫を更新する必要がある

## 決定
Order と Inventory を別モジュールにし、OrderPlaced イベントで連携

## 理由
在庫ロジックの変更が注文に波及しないようにする

## 結果
（後から追記）

    「なぜそうしたか」が残ると、後任者や未来の自分が助かります。ADR の書き方・運用は 41章の 意思決定とADR を参照してください。

    9.よくある誤解

    誤解1：「設計はコードを書く前に全部終わらせるもの」

    要件は変わり、理解はコードを書いて深まります。最初は「十分に良い」概要設計にとどめ、実装しながら詳細化・更新していくほうが無駄と誤りが少なくなります。

    誤解2：「名詞はすべてクラスにする」

    名詞・動詞の抽出は 候補 を出すための手法です。責務と関心で取捨選択し、ただの属性で済むものはクラスにしません。

    誤解3：「図は正式な UML でなければ意味がない」

    図は議論の道具です。箱と矢印の手書きスケッチで依存の向きや責務を共有できれば十分なことが多いです。

    誤解4：「技術的負債は悪なので、一切作ってはいけない」

    リリース優先などの理由で意図的に負債を取ることはあります。問題は記録せずに忘れることです。期限と理由を ADR に残し、可視化して小さく返済します。

    10.まとめ

    • 要件・用語を先に整理 する（機能要件・非機能要件・制約・用語）
    • ユースケースと名詞・動詞 から構造の候補を出し、責務と関心で取捨選択する
    • 簡易な図 で関係を可視化する。図は議論の道具
    • ワークショップで たたき台 を素早く作る
    • 完璧な先行設計は不要。進化を前提 に、概要 → 詳細へ段階的に深める
    • リファクタリング で設計を更新し、技術的負債 を可視化して小さく返済し、ADR で判断の理由を残す
