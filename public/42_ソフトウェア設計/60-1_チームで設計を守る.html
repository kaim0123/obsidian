    60 チームと品質

    チームで設計を守る — 合意・ルール・よくある失敗

    設計は一人の頭の中にあるだけでは守られません。合意形成、コードレビューで見る設計観点、短い設計ルール、設計負債の可視化、新人への伝え方を学びます。あわせて、大泥団・神クラス・貧血ドメインモデル・過剰な抽象化という典型的な失敗と、そこから改善する進め方をまとめます。

    もとにしたノート：01_チームで設計を守る / 02_よくある設計の失敗

    1.このページで扱うこと

    • チーム開発で 設計の意図を共有し、守る ための実践（合意形成・コードレビュー・設計ルール・負債の可視化・新人への伝え方）
    • アンチパターン（よくある設計の失敗の型）を知り、回避と改善の考え方を学ぶ

    アンチパターンの一覧は チェックリストとアンチパターン にまとまっています。

    2.設計の合意形成

    設計が 個人の頭の中だけ にあると、チームに共有されません。

    手法内容
    設計レビューたたき台を出して議論する（→ レガシーと設計レビュー）
    ペア設計2人で一緒に構造を決める
    ADR判断の理由を文書化する（→ 意思決定とADR）
    用語集ユビキタス言語 を共有する

    ポイント

    「なぜこう分けたか」を言語化できると、チームの判断が揃います。

    3.コードレビューで見るべき設計ポイント

    機能の正しさだけでなく、設計の観点 も見ます。

    • ☐ 責務は 1箇所 に集まっているか
    • ☐ 依存の方向は 適切 か
    • ☐ 命名は 意図を表している か
    • ☐ 境界（モジュール・レイヤー）を 越えていない か
    • ☐ テストは 適切な単位 で書かれているか

    詳しいチェックリストは チェックリストとアンチパターン、アーキテクチャのレベルの観点は 41章の レビュー観点 を参照してください。

    4.設計ルールの文書化

    チームで守る 設計ルール を短く文書化します。

    ◯ 良い例：短いルールを箇条書きで 
    ## 設計ルール（例）
- ドメイン層はインフラに依存しない
- 1 集約 1 トランザクション
- 新機能は既存モジュールの境界を越えない
- Utils に雑多な処理を追加しない

    長大な設計書より、短いルール ＋ 例 のほうが守られやすいです。ルールの背景は、依存性のルール（ドメイン層はインフラに依存しない）や 集約とリポジトリ（1集約1トランザクション）を参照してください。ルールをツールで自動チェックする方法は 41章の 適応度関数 にあります。

    5.設計負債の可視化

    設計負債（設計上の妥協が将来のコストになっているもの）を隠さず、共有します。

    可視化の方法例
    課題チケット「Order と Inventory の循環依存を解消」
    コード内 TODO// DESIGN-DEBT: 本来はイベントで連携
    定期的な振り返りスプリントごとに負債リストをレビューする

    負債を 悪ではなく、投資の優先順位 として扱います。負債の種類や返済の考え方は 41章の 技術的負債 を参照してください。

    6.新人への設計の伝え方

    全体像から

    設計の階層、モジュール構成の地図を最初に見せる。

    具体例で

    良い例・悪い例のコードを比較する。

    小さなタスクから

    1つのモジュール内の変更から参画してもらう。

    レビューで

    なぜダメかを設計の観点で説明する。

    「ルールを暗記させる」より、「なぜそうするか」を伝える ことが定着につながります。

    7.よくある設計の失敗

    7.1 大泥団（Big Ball of Mud）

    大泥団は、境界のない単一モデルに全機能が詰め込まれた状態です。

    症状対策
    用語が文脈なく混在している境界づけられたコンテキスト で分割する
    変更が全体に波及するモジュール・集約で境界を引く
    誰も全体を理解できない段階的にコンテキストを分離する

    7.2 神クラス・神サービス

    God Object / God Class は、すべてを担当する巨大なクラス・サービスです。

    ApplicationService
  ・注文処理
  ・在庫更新
  ・メール送信
  ・レポート生成
  ・ユーザー管理  … 全部入り

    対策：変化の理由 で分割します。SRP（単一責任の原則：クラスを変更する理由は1つにする）を意識します（→ SOLIDとオブジェクト指向、凝集度と結合度。より詳しくは 44_クラス設計・デザインパターン）。

    7.3 貧血ドメインモデル

    貧血ドメインモデルは、エンティティがただのデータの入れ物で、ロジックがサービス層に集中した状態です。

    対策：振る舞いをエンティティ・値オブジェクトに移します（→ 戦術的設計の全体像、エンティティと値オブジェクト）。

    7.4 過剰な抽象化とパターンの乱用

    症状例
    インターフェースの乱立実装が1つしかないのに Interface を作る
    パターンのためのパターン単純な if で足りるのに Strategy で5クラス
    深い継承階層理解に 30 分かかる

    対策：YAGNI（必要になるまで作らない）。問題が見えてからパターンを適用します（→ 変化に強い設計、継承と合成）。

    8.失敗から学ぶ改善の進め方

    1. 名前を付ける — 「これは神クラス」「これは大泥団」
    2. 影響範囲を限定する — 一度に全部直さない
    3. テストを足す — リファクタリングの安全網（→ テストとリファクタリング）
    4. 小さく分割する — Extract Class / Extract Module
    5. 振り返る — なぜそうなったか。ルールで防げるか

    失敗は学習材料

    責めずに「次はどうするか」を議論します。振り返りで得た学びは、4章の設計ルールに足していきます。

    9.よくある誤解

    誤解1：「詳しい設計書を書けば、設計は守られる」

    長大な設計書は読まれず、更新もされません。短いルール ＋ 例、ADR、用語集、レビューでの対話のほうが守られやすいです。

    誤解2：「コードレビューは動くかどうかを確認する場」

    機能の正しさに加えて、責務・依存の方向・命名・境界・テストの単位といった設計の観点も見ます。設計の意図を共有する一番身近な場です。

    誤解3：「抽象化やパターンは多いほど良い設計」

    実装が1つしかない Interface や、if で足りるところへの Strategy は過剰な抽象化です。問題が見えてから適用します。

    誤解4：「神クラスや大泥団は一気に作り直すべき」

    名前を付け、影響範囲を限定し、テストを足してから小さく分割します。一度に全部直そうとすると新たなバグの温床になります。

    10.まとめ

    • 設計は 合意形成と文書化（設計レビュー・ペア設計・ADR・用語集）で共有する
    • コードレビューに設計観点 を含める
    • 短い設計ルール と 負債の可視化。負債は投資の優先順位として扱う
    • 新人には 全体像と理由 から伝える
    • 大泥団・神クラス・貧血モデル・過剰抽象化 は典型的な失敗
    • 名前を付け、影響を限定し、テストを足し、段階的に改善する。失敗からルールと学びを得る
