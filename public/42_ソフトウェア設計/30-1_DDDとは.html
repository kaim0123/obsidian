    30 ドメイン駆動設計

    DDDとは — 業務（ドメイン）を設計の中心に置く

    ドメイン駆動設計（DDD）は、ソフトウェアの構造と用語をビジネスの現実に合わせて設計する考え方です。技術中心の設計が抱える問題、ユビキタス言語、戦略設計と戦術設計の2つの側面、クリーンアーキテクチャとの関係、そして「どこまでやるか」の判断までを、30章全体の入口としてまとめます。

    もとにしたノート：01_DDDを学ぶ理由 / 02_DDDとは

    1.このページで扱うこと

    ドメイン駆動設計（Domain-Driven Design, DDD）は、Eric Evans（エリック・エヴァンス）が提唱した、ビジネスの複雑さをソフトウェアの構造に反映させるための設計の考え方です。このページの目的は、「技術中心」から「業務中心」へ視点を移すことです。

    • 技術中心の設計が抱える問題
    • DDD を一言で言うと何か、「ドメイン」とは何か
    • ユビキタス言語で開発者と業務担当者の認識をそろえる
    • 戦略設計と戦術設計という2つの側面
    • DDD とクリーンアーキテクチャを一緒に学ぶ理由
    • DDD が向いている場面・やりすぎになる場面
    • 30章の読み方

    30章では DDD 全体を深く追うのではなく、戦略設計と戦術設計の入口として、次の3つを押さえます。

    1. 境界づけられたコンテキストとコンテキストマップ … 大きなシステムをどう区切るか
    2. ドメイン層・ユースケース・アプリサービス … クリーンアーキテクチャの「中身」を DDD の言葉で読む
    3. 集約・エンティティ・値オブジェクト・ドメインイベント … ドメイン層の主要な部品

    前提として、41章のクリーンアーキテクチャやオニオンアーキテクチャとの比較を読んでおくと、「ドメインを中心に置く」という共通の土台がつかみやすくなります。

    2.技術中心の設計が抱える問題

    DB テーブルや画面仕様から設計を始めると、次の問題が起きやすくなります。

    問題具体例
    用語のズレ開発者は「User」、業務は「会員」と呼ぶ
    ロジックの散在割引ルールが SQL・画面・バッチに分散
    変更の波及テーブル1つ変えると全画面が影響
    仕様の誤解コードを読まないと業務が分からない

    3.DDD を一言で — 業務を設計の中心に置く

    DDD を一言で

    ソフトウェアの構造と用語を、ビジネス（ドメイン）の現実に合わせて設計する。

    3.1 ドメインとは

    ドメインとは、そのソフトウェアが扱う事業領域・業務の世界のことです。

    EC

    注文・在庫・配送・決済

    病院

    診療・予約・会計

    社内システム

    承認・経費・勤怠

    DDD は「このソフトウェアは何のためのものか」を先に明確にし、構造と用語を業務に合わせます。

    3.2 先に考える3つのこと

    DDD は「DB のテーブル設計から始める」のではなく、次の3つを先に考え、コードの形に落とし込む姿勢を重視します。

    • 現場の人が使う言葉（ユビキタス言語）
    • 業務の区切り（境界づけられたコンテキスト）
    • ルールを守る単位（集約）

    4.ユビキタス言語で認識をそろえる

    4.1 ユビキタス言語とは

    ユビキタス言語（Ubiquitous Language）とは、開発者・業務担当者・設計者が共有する用語です。

    ✕ 悪い例：同じことを別の言葉で話している 
    開発者「OrderEntity の status を 2 に更新」
業務  「注文を確定する」
    ◯ 良い例：全員が同じ言葉を使い、それがコードになる 
    全員「注文を確定する」→ order.confirm()
    • コードのクラス名・メソッド名に業務の言葉を使う
    • 用語集を作り、ブレを防ぐ
    • 詳しくは 戦略的設計とユビキタス言語 へ

    4.2 開発者と業務担当者の認識をそろえる

    DDD の大きな価値はコミュニケーションにあります。

    • 要件会議で同じ言葉を使う
    • モデル（図・コード）を共通言語として使う
    • 「この仕様、コードのどこ？」がすぐ分かる

    ひとことで

    ユビキタス言語 ＝ 要件とコードの翻訳層をなくすもの。

    5.戦略設計と戦術設計

    DDD は大きく2つの側面に分かれます。

    側面主な問い30章での扱い
    戦略設計システム全体をどう区切るか、チーム間をどう連携するか境界づけられたコンテキスト、コンテキストマップ（30-2〜30-4）
    戦術設計1つのコンテキストの中をどうモデル化するかドメイン層の部品（集約、エンティティなど）（30-5〜30-9）

    戦略 ＝ 地図を描く

    街全体をどう区画分けし、区画どうしをどの道でつなぐかを決める。

    戦術 ＝ 1つの街の建物を設計する

    1つの区画の中で、建物（モデル）をどう組み立てるかを決める。

    小規模な個人開発では戦術だけ意識することも多いですが、チームやシステムが大きくなるほど戦略設計の価値が上がります。

    6.なぜ DDD とアーキテクチャを一緒に学ぶのか

    41章のクリーンアーキテクチャでは、すでに Entities（エンティティ）や Use Cases（ユースケース）という層を見てきました。DDD は、それらの中身をどう設計するかの指針を与えてくれます。

    • クリーンアーキテクチャ … 依存の向き（内側にドメインを置く）
    • DDD … ドメインの中身の作り方（集約、値オブジェクト、ドメインイベントなど）

    7.DDD は「全部やる」ものではない

    向いている場面

    • ビジネスルールが複雑で、仕様変更が頻繁
    • 複数チームが同じシステムの別領域を担当している
    • 長期間保守し、用語のブレがバグの温床になっている

    やりすぎ・不要になりやすい場面

    • 単純な CRUD が中心の小規模アプリ
    • ドメインの知識がほとんどなく、技術的な課題だけを解きたいとき
    • 用語集だけ作ってロジックはサービス層に残る「DDD っぽい設計」

    現実的な使い方

    DDD は銀の弾丸ではありません。「ドメインの複雑さに見合った投資」として使うのが現実的です。どこに力を入れるかは コアドメインとサブドメイン で詳しく扱います。

    8.30章の読み方

    30章は、戦略的設計 → 戦術的設計 → モデリング手法 の順に並んでいます。

    1. DDDとは（このページ）
    2. 戦略的設計 … システムの「地図」：戦略的設計とユビキタス言語 / 境界づけられたコンテキスト / コアドメインとサブドメイン
    3. 戦術的設計 … 部品と層の役割分担：戦術的設計の全体像（集約・エンティティ・値オブジェクト・ドメインイベントの入門）〜 ドメイン層とユースケース
    4. モデリング手法 … 業務の専門家と一緒にモデルを見つける：イベントストーミング / ドメインストーリーテリングと例示マッピング

    順番に読むことをおすすめします。すでにクリーンアーキテクチャに慣れている場合は、ドメイン層・ユースケース（30-9）→ 部品（30-5〜30-8）→ 境界づけられたコンテキスト（30-3）の順でも構いません。

    9.よくある誤解

    誤解1：「DDD は全部のパターンを使わないと意味がない」

    全部やる必要はありません。ドメインの複雑さに見合った分だけ導入します。単純な CRUD 中心の小規模アプリなら、DDD は不要なことも多いです。

    誤解2：「用語集を作れば DDD をやっていることになる」

    用語集だけ作ってロジックはサービス層に残る設計は「DDD っぽい設計」にすぎません。業務の言葉とルールがコードの構造に反映されてはじめて効果が出ます。

    誤解3：「DDD はクリーンアーキテクチャの代わり」

    役割が違います。クリーンアーキテクチャは依存の向き（箱の形）、DDD はドメインの中身の作り方（箱の中身）を扱い、組み合わせて使います。

    10.まとめ

    • 技術中心の設計は、用語のズレ・ロジックの散在・変更の波及・仕様の誤解を招く
    • DDD は、ソフトウェアの構造と用語を業務（ドメイン）の現実に合わせて設計する
    • ユビキタス言語で開発者と業務担当者の認識をそろえ、要件とコードの翻訳層をなくす
    • 戦略設計は地図を描く（全体をどう区切るか）、戦術設計は1つの街の建物を設計する（コンテキストの中をどうモデル化するか）
    • クリーンアーキテクチャは箱の形、DDD は箱の中身の詰め方
    • 全部やる必要はない。ドメインの複雑さに見合って導入する
