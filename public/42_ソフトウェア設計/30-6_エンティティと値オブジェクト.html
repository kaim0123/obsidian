    エンティティと値オブジェクト — 「どれか」で見分けるか、「何か」で見分けるか

    DDD でモデルを作るとき、最初に区別するのが「同じ ID なら同じもの」のエンティティと、「同じ値なら同じもの」の値オブジェクトです。それぞれの特徴と使いどころ、値オブジェクトがもたらす4つの強み、文字列や数値ばかり使う「プリミティブ執着」の罠、ID を専用の型にする方法、そして値オブジェクトを作るときの注意点を解説します。

    もとにしたノート：03_エンティティと値オブジェクト

    1.このページで扱うこと

    DDD でモデル（ドメインオブジェクト：業務の概念を表すオブジェクト）を作るとき、最初に区別するのが次の2種類です。

    エンティティ（Entity）

    「同じ ID を持つなら同じもの」

    値オブジェクト（Value Object）

    「同じ値を持つなら同じもの」

    この区別を明確にするだけで、コードの意図がぐっと伝わるようになります。全体の中での位置づけは 戦術的設計の全体像 を参照してください。このページでは次を扱います。

    • エンティティの特徴と、いつエンティティにするか
    • 値オブジェクトの特徴と、いつ値オブジェクトにするか
    • 値オブジェクトの4つの強みと、プリミティブ型の罠
    • エンティティの ID も値オブジェクトにする方法
    • 値オブジェクトを作るときの注意点

    2.エンティティ（Entity）

    2.1 特徴

    • ID で識別される
    • 時間とともに状態が変わる
    • 同じ ID なら、属性が変わっても同じオブジェクト

    2.2 例：ユーザー

    class User {
  constructor(
    public readonly id: UserId,
    private name: string,
    private email: string
  ) {}

  changeName(newName: string) {
    this.name = newName; // 名前は変わっても、同じUser
  }

  equals(other: User): boolean {
    return this.id.equals(other.id); // IDが同じなら同じ
  }
}

    ユーザーが名前を変えても、それは同じ人物です。だから ID で識別します。

    2.3 いつエンティティにするか

    • 個々に区別する必要がある（A さん と B さん）
    • ライフサイクルがある（作成 → 更新 → 削除）
    • 履歴を追う必要がある

    3.値オブジェクト（Value Object）

    3.1 特徴

    • 値そのもので識別される
    • 不変（immutable：作ったあと中身を変えない）である
    • 同じ値なら、まったく同じと扱える
    • 副作用のない計算（自分や外の状態を書き換えず、結果を返すだけの計算）を持つ

    3.2 例：金額

    class Money {
  constructor(
    public readonly amount: number,
    public readonly currency: string
  ) {
    if (amount < 0) throw new Error('金額は負にできない');
  }

  add(other: Money): Money {
    if (this.currency !== other.currency) throw new Error('通貨が違う');
    return new Money(this.amount + other.amount, this.currency); // 新しいインスタンスを返す
  }

  equals(other: Money): boolean {
    return this.amount === other.amount && this.currency === other.currency;
  }
}

const a = new Money(100, 'JPY');
const b = new Money(100, 'JPY');
console.log(a.equals(b)); // true

    100円と100円は、どこの100円でも同じ100円です。区別する意味がありません。

    3.3 例：住所

    class Address {
  constructor(
    public readonly zipCode: string,
    public readonly prefecture: string,
    public readonly city: string,
    public readonly street: string
  ) {
    if (!zipCode.match(/^\d{3}-\d{4}$/)) throw new Error('郵便番号不正');
  }
}

    同じ住所なら、どの人の「住所」オブジェクトでも同じ値で扱えます。

    3.4 いつ値オブジェクトにするか

    • 「どれ」ではなく「何」が大事
    • ID で区別する意味がない
    • 交換可能（100円 ⇔ 100円）
    • 計算・結合できる（金額＋金額）

    4.比較：エンティティ vs 値オブジェクト

    観点エンティティ値オブジェクト
    識別方法ID値
    可変性可変（状態が変わる）不変（変えない）
    比較id.equals(otherId)全フィールドの値比較
    ライフサイクルあるない
    例User, Order, ProductMoney, Address, Email, Date

    5.値オブジェクトの強み

    5.1 ビジネスルールが凝縮できる

    class Email {
  constructor(public readonly value: string) {
    if (!value.includes('@')) throw new Error('メール形式不正');
    if (value.length > 255) throw new Error('長すぎる');
  }
}

// 使う側
const email = new Email(input); // ← ここでルール違反を検知

    生成時にチェックするので、ルール違反のオブジェクトは存在できません。「メールアドレスとして正しいか」というルールが Email 1か所にまとまります（カプセル化の具体例でもあります）。

    5.2 型安全

    function sendMail(to: Email, body: string) { /* ... */ }

sendMail('hello', 'message'); // ❌ 型エラー
sendMail(new Email(input), 'message'); // ✅

    ただの string だと、何でも渡せてしまいます。値オブジェクトなら型で弾けます。型でドメインを表す考え方は 型でドメインを表す でも扱います。

    5.3 副作用のない計算

    const price = new Money(1000, 'JPY');
const tax = new Money(100, 'JPY');
const total = price.add(tax); // 新しいインスタンス

console.log(price.amount); // 1000（変わらない）
console.log(total.amount); // 1100

    元のオブジェクトが変わらないので、バグの温床になりません。どこかで共有している price が知らないうちに書き換わる、という事故が起きないからです。

    5.4 重複排除

    ✕ 悪い例：ただの数値 
    if (order.price > 0 && order.price < 1_000_000) { ... }
// ↑ 別の場所でも同じチェックを書く羽目になる
    ◯ 良い例：チェックを値オブジェクトに入れる 
    class Price {
  constructor(public readonly value: number) {
    if (value <= 0 || value >= 1_000_000) throw new Error('不正');
  }
}
// チェックロジックが1か所に集約

    6.プリミティブ型の罠（Primitive Obsession）

    string や数値ばかり使うコードは、プリミティブに執着（Primitive Obsession：基本型にこだわりすぎること）と呼ばれるコードの匂い（設計に問題がありそうなサイン）です。

    ✕ 悪い例：string だらけ 
    function createUser(email: string, password: string, phone: string, zipCode: string) { ... }

// どれがどれ？ 順番を間違えてもコンパイル通る
    ◯ 良い例：値オブジェクト化すると 
    function createUser(email: Email, password: Password, phone: PhoneNumber, zipCode: ZipCode) { ... }
    • 型で区別できる
    • それぞれにルールを持てる
    • 順番ミスがコンパイルで弾ける

    7.エンティティの ID も値オブジェクトにする

    エンティティの ID も、専用の値オブジェクトにすると強くなります。

    class UserId {
  constructor(public readonly value: string) {
    if (!value.match(/^user_/)) throw new Error('IDが不正');
  }
  equals(other: UserId): boolean {
    return this.value === other.value;
  }
}

class OrderId { /* 別の型 */ }

class User {
  constructor(public readonly id: UserId) {}
}

// ❌ 型が違うので弾かれる
const user = new User(new OrderId('order_1'));

    userId: string だと、orderId と取り違えてもコンパイルが通ってしまいます。型で区別できると安全性が跳ね上がります。

    エンティティと値オブジェクトは組み合わせて使う

    エンティティ User の中に、値オブジェクト UserId・Email・Address を持たせるのが典型的な形です。エンティティは「同一性とライフサイクル」、値オブジェクトは「個々の値のルール」を受け持ちます。

    8.値オブジェクトの注意点

    8.1 不変にする

    値オブジェクトは変えません。変更したければ新しいインスタンスを返します。

    ✕ 悪い例：可変は値オブジェクトではない 
    class Money {
  add(other) { this.amount += other.amount; } // 自分を変えている
}
    ◯ 良い例：不変 
    class Money {
  add(other) { return new Money(this.amount + other.amount, this.currency); }
}

    8.2 等価性を定義する

    JavaScript のオブジェクトの === は参照比較（同じ実体かどうか）です。値で比較するには equals() メソッドを自前で定義する必要があります。

    8.3 初期化バリデーション

    コンストラクタで必ずルールをチェックします。不正な状態のオブジェクトを作らせません。

    9.よくある誤解

    誤解1：「データベースのテーブルに ID 列があるものは全部エンティティ」

    エンティティかどうかは、DB の都合ではなく業務の上で「どれか」を区別する必要があるかで決めます。住所テーブルに ID 列があっても、業務で住所そのものを追跡しないなら、モデルとしては値オブジェクトで扱うほうが自然です。

    誤解2：「値オブジェクトは中身を変えられないので不便」

    変えたいときは新しいインスタンスを作って差し替えるだけです（price.add(tax) のように）。元が変わらないので、共有していても安全で、バグの温床になりません。

    誤解3：「string や number で十分。クラスを作るのは大げさ」

    それがプリミティブ執着です。引数の順番ミスや ID の取り違えがコンパイルで見つからず、同じチェックがあちこちに重複します。値オブジェクトにすれば、ルールは1か所、間違いは型で弾けます。

    10.まとめ

    • エンティティ：ID で識別し、状態が変わり、ライフサイクルがある（User, Order, Product）
    • 値オブジェクト：値で識別し、不変で、副作用のない計算を持つ（Money, Address, Email, Date）
    • 「どれ」が大事ならエンティティ、「何」が大事なら値オブジェクト
    • 値オブジェクトの強み：ルールの凝縮・型安全・副作用のない計算・重複排除
    • string だらけのプリミティブ執着を避け、ID も専用の型にする
    • 値オブジェクトは不変にし、equals() を定義し、コンストラクタで検証する
