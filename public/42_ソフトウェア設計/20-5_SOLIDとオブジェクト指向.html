    SOLIDとオブジェクト指向 — OOP の道具を良い設計に導く5原則

    OOP の基本（カプセル化・継承・多態性）を理解したら、次は良い OOP コードを書くための設計原則 SOLID です。このページでは、5つの原則それぞれが OOP のどの要素と結びつくのかを、悪い例・良い例のコードで整理します。

    もとにしたノート：05_SOLIDとの関係

    1.このページで扱うこと

    オブジェクト指向プログラミング（OOP）の基本を理解したら、次に学ぶべきは良い OOP コードを書くための設計原則です。それが SOLID 原則です。

    ここでは、OOP の3大要素（カプセル化・継承・多態性）と、SOLID の5原則がどう結びつくのかを整理します。各原則そのものの詳しい解説や成り立ちは 48_原則 のノートで扱います。

    2.SOLID の5原則（おさらい）

    記号名称一言で
    SSingle Responsibility Principle（単一責任）1クラス1責任
    OOpen-Closed Principle（開放閉鎖）拡張には開き、変更には閉じる
    LLiskov Substitution Principle（リスコフ置換）子は親の代わりになれる
    IInterface Segregation Principle（インターフェース分離）使わないメソッドを押しつけない
    DDependency Inversion Principle（依存性逆転）抽象に依存する

    3.OOP の3要素と SOLID の対応

    OOPの3要素          SOLID原則
───────────         ───────────
カプセル化    ──→   S（単一責任）
                    → 状態と責任を1つにまとめる

継承・多態性  ──→   L（リスコフ置換）
                    → 子は親の期待を守る

                    O（開放閉鎖）
                    → 多態性で拡張

抽象化        ──→   I（インターフェース分離）
                    → 必要最小限の約束

                    D（依存性逆転）
                    → 具象でなく抽象に依存

    4.S：単一責任の原則（SRP）

    1つのクラスは、1つの責任だけを持つ。

    4.1 OOP との関係

    カプセル化の目的は「関連するデータと振る舞いをひとまとめにする」ことですが、無関係なものまで詰め込むとクラスが肥大化します。SRP は「まとめる単位を誤らない」ための指針です。

    4.2 コード例

    ✕ 悪い例：1クラスに永続化・通知・表示の責任 
    class User {
  save() { /* DB保存（永続化の責任） */ }
  sendEmail() { /* メール送信（通知の責任） */ }
  render() { /* HTML生成（表示の責任） */ }
}
    ◯ 良い例：責任ごとにクラスを分ける 
    class User { /* ユーザーの状態と振る舞い */ }
class UserRepository { save(user) { } }
class UserMailer { sendWelcome(user) { } }
class UserView { render(user) { } }

    考え方の土台は関心の分離や凝集度と結合度と共通です。

    5.O：開放閉鎖の原則（OCP）

    拡張に対して開いており、変更に対して閉じている。

    5.1 OOP との関係

    多態性のメリットを最大化する原則です。既存のコードを変更せず、新しいクラスを追加するだけで機能を拡張できるようにします。

    5.2 コード例

    ✕ 悪い例：種類が増えるたびに関数を書き換える 
    function calcPrice(item) {
  if (item.type === 'book') return item.price * 0.9;
  if (item.type === 'food') return item.price * 0.95;
  // 種類が増えるたびにここを変更…
}
    ◯ 良い例：種類ごとのクラスに計算を持たせる 
    class Item {
  calcPrice() { throw new Error('サブクラスで実装'); }
}
class Book extends Item { calcPrice() { return this.price * 0.9; } }
class Food extends Item { calcPrice() { return this.price * 0.95; } }
// 新種類を追加 → 新クラスを足すだけ

    6.L：リスコフ置換の原則（LSP）

    親の代わりに子を使っても、プログラムは壊れない。

    6.1 OOP との関係

    継承・多態性が正しく機能するための前提条件です。LSP を破る継承は、見かけ上 is-a 関係でも設計として破綻しています。

    6.2 コード例

    ✕ 悪い例：Square が Rectangle を継承する 
    class Rectangle {
  setWidth(w) { this.w = w; }
  setHeight(h) { this.h = h; }
  area() { return this.w * this.h; }
}

class Square extends Rectangle {
  setWidth(w) { this.w = this.h = w; } // 同時に変わる
  setHeight(h) { this.w = this.h = h; }
}

function test(rect) {
  rect.setWidth(5);
  rect.setHeight(3);
  console.log(rect.area()); // 長方形なら15だが、正方形だと9
}

    「正方形は長方形の一種」と思えても、振る舞いの約束（幅と高さを別々に設定できる）が破れるので LSP 違反です。ペンギンと鳥の例は多態とインターフェースを参照してください。

    7.I：インターフェース分離の原則（ISP）

    使わないメソッドを無理やり実装させない。

    7.1 OOP との関係

    インターフェースを役割ごとに小さく切り分ける指針です。大きな汎用インターフェースではなく、専門的な小さいインターフェースを複数作ります。

    7.2 コード例

    ✕ 悪い例：何でも入った大きなインターフェース 
    interface Worker {
  work(): void;
  eat(): void;
  sleep(): void;
}

class Robot implements Worker {
  work() { /* OK */ }
  eat() { throw new Error('食べない'); } // 困る
  sleep() { throw new Error('眠らない'); } // 困る
}
    ◯ 良い例：役割ごとの小さいインターフェース 
    interface Workable { work(): void; }
interface Eatable { eat(): void; }
interface Sleepable { sleep(): void; }

class Human implements Workable, Eatable, Sleepable { /* 全部実装 */ }
class Robot implements Workable { /* workだけでOK */ }

    インターフェースをどの粒度で切るかはインターフェースと抽象化でも扱っています。

    8.D：依存性逆転の原則（DIP）

    具体に依存せず、抽象に依存する。

    8.1 OOP との関係

    多態性・インターフェースを設計の方向付けに使う原則です。上位モジュール（業務の中心）が下位モジュール（DB などの詳細）に引きずられないように、間に抽象を挟みます。

    8.2 コード例

    ✕ 悪い例：具体クラスを自分で new する 
    class UserService {
  constructor() {
    this.db = new MySQLDatabase(); // 具体クラスに依存
  }
}
    ◯ 良い例：インターフェースを受け取る 
    interface UserRepository {
  save(user: User): void;
}

class UserService {
  constructor(private repo: UserRepository) {} // 抽象に依存
}

class MySQLUserRepo implements UserRepository { /* ... */ }
class MongoUserRepo implements UserRepository { /* ... */ }

    DB を変えても UserService は変更不要。これが依存性逆転の効果です。依存の向きがなぜ「逆転」するのか、アーキテクチャ全体でどう使うのかは依存性逆転の原則で詳しく解説しています。

    9.全体の構図

             ┌──────────────────────────────┐
         │   使いやすく壊れにくいコード   │
         └──────────────────────────────┘
                    ↑
         ┌──────────┼──────────┐
         S           O           L
       単一責任    開放閉鎖    置換可能
         │          │          │
         ↓          ↓          ↓
      クラス       多態         継承
       設計      で拡張     の正しさ
                    │
                 ┌──┴──┐
                 I      D
              小さな   抽象に
              API     依存

    S → クラス設計

    責任の単位でクラスを切る

    O → 多態で拡張

    I（小さな API）と D（抽象に依存）が支える

    L → 継承の正しさ

    置き換えても壊れない

    10.よくある誤解

    誤解1：「OOP で書けば自然と良い設計になる」

    OOP を書くだけでは不十分です。クラスに何でも詰め込めば SRP に、is-a だけで継承すれば LSP に反します。SOLID に沿って責任・拡張・依存を整える必要があります。

    誤解2：「SOLID は特別な上級テクニック」

    1つ1つは特別なテクではなく、当たり前を当たり前にやるための名前です。カプセル化・継承・多態という OOP の道具を正しく使う指針と考えると理解しやすくなります。

    誤解3：「SOLID の5原則はばらばらの規則」

    5つは互いに関係しています。OCP（拡張で対応）は多態性に支えられ、その多態性が正しく働く前提が LSP、約束を小さく保つのが ISP、抽象に依存する向きを決めるのが DIP です。

    11.まとめ

    • OOP の道具を使って良い設計を作るための指針が SOLID
    • カプセル化 → S、継承・多態性 → L・O、抽象化 → I・D と対応する
    • OOP を書くだけでは不十分。SOLID に沿って責任・拡張・依存を整える
    • 1つ1つは特別なテクではなく、当たり前を当たり前にやるための名前
    • 各原則の詳細は 48_原則 のノート、DIP のアーキテクチャでの使い方は依存性逆転の原則
