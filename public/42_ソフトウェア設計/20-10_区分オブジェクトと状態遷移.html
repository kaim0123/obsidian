    区分オブジェクトと状態遷移

    区分ごとの if / switch を、区分専用のクラス（または振る舞い付き列挙） に閉じ込めます。同じ型として扱い、生成はファクトリに寄せ、状態遷移は許可表で一目でわかるようにします。

    もとにしたノート：44_クラス設計/20_責務の割り当て/07_区分オブジェクトと状態遷移、02_継承と多態／42/20/04_多態とインターフェース、03_型でドメインを表す／増田亨『現場で役立つシステム設計の原則』第2章後半

    ひとことで言うと

    区分オブジェクト は、区分の定義とその区分だけの判断・計算をオブジェクトにまとめたものです。使う側は共通の型だけを見ればよく、区分追加は新しいクラス（または列挙定数）を足すだけで済みます。

    1.区分ごとのロジックを別クラスに分ける

    前のページで分岐を読みやすくしても、区分本体が1つの巨大関数に残っていると、区分追加のたびにその関数を開くことになります。区分ごとにクラスを切り、その区分だけのルール を中に置きます。

    // ✕ 区分のたびに switch が増える
function fee(type: string): number {
  switch (type) {
    case "adult": return 1000;
    case "child": return 500;
    case "senior": return 700;
    default: throw new Error("unknown");
  }
}

// ◯ 区分ごとにクラス
class AdultFee { yen() { return 1000; } }
class ChildFee { yen() { return 500; } }
class SeniorFee { yen() { return 700; } }

    2.区分ごとのクラスを同じ「型」として扱う

    使う側が具象クラス名を知らなくてよいよう、共通のインターフェース（型） で扱います。これがポリモーフィズムによる条件分岐の置き換えです（→ 多態とインターフェース）。

    interface Fee {
  yen(): number;
}

class AdultFee implements Fee {
  yen() { return 1000; }
}
class ChildFee implements Fee {
  yen() { return 500; }
}

function charge(fee: Fee): number {
  return fee.yen(); // 区分の if はない
}

    新しい区分は 新クラスを追加するだけ で、charge は変更しません（開放閉鎖の原則）。

    3.区分ごとのクラスのインスタンスを生成する

    どこかで「どの区分か」を決めてインスタンスを作る必要があります。生成の分岐は ファクトリ（またはマップ）1か所 に寄せ、業務ルール本体は各クラスに残します。

    type FeeCode = "adult" | "child" | "senior";

function createFee(code: FeeCode): Fee {
  switch (code) {
    case "adult": return new AdultFee();
    case "child": return new ChildFee();
    case "senior": return new SeniorFee();
  }
}

    4.列挙型を使えばもっとかんたん

    Java の enum は定数だけでなくメソッド（振る舞い）を持てます。TypeScript では、ユニオン＋オブジェクトマップや、static 風の列挙オブジェクトがよく使われます。

    const FeeType = {
  Adult:  { yen() { return 1000; } },
  Child:  { yen() { return 500; } },
  Senior: { yen() { return 700; } },
} as const;

type FeeTypeKey = keyof typeof FeeType;

function charge(key: FeeTypeKey): number {
  return FeeType[key].yen();
}

    言語ごとの列挙の書き方は docs の 44_クラス設計/10_クラスの基礎/05_クラスの種類の整理（列挙型）も参照してください。

    5.区分オブジェクトで分析し整理する

    区分オブジェクト とは、区分の定義と区分ごとの判断・加工・計算をオブジェクトにまとめたものです。

    効果説明
    置き場所が決まる「子供料金はどこ？」→ ChildFee / FeeType.Child
    影響が閉じる1区分の変更が他区分や呼び出し側に波及しにくい
    重複 switch が減る同じ区分分岐のコピーが減る

    金額そのものは値オブジェクト（→ エンティティと値オブジェクト）と組み合わせると、さらに型で安全になります。

    6.状態の遷移ルールをわかりやすく記述する

    ステータス（下書き→確定→出荷など）も区分の一種です。許可される遷移を if の山にせず、遷移表 や状態ごとの型で表します。

    type OrderStatus = "draft" | "confirmed" | "shipped" | "cancelled";

const ALLOWED: Record<OrderStatus, readonly OrderStatus[]> = {
  draft: ["confirmed", "cancelled"],
  confirmed: ["shipped", "cancelled"],
  shipped: [],
  cancelled: [],
};

function canTransit(from: OrderStatus, to: OrderStatus): boolean {
  return ALLOWED[from].includes(to);
}

    状態ごとに型を分け、遷移を関数にする関数型寄りの整理は 型でドメインを表す で詳しく扱っています。

    7.まとめ

    • 区分 if / switch の本体はクラス（または振る舞い付き列挙）へ閉じ込める
    • 共通の型で扱い、生成の分岐はファクトリに寄せる
    • 区分オブジェクト＝区分定義＋区分ごとの業務ロジック
    • 状態遷移は許可表や状態型で一目でわかるようにする

    8.理解度チェック

    Q1. 区分オブジェクトの主な狙いは

    区分ごとの判断・計算をオブジェクトに閉じ込め、呼び出し側と他区分への影響を減らすこと。

    Q2. なぜ共通インターフェースが必要か

    使う側が具象クラスを知らなくてよくなり、区分追加が新クラス追加だけで済む（ポリモーフィズム／OCP）。

    Q3. 生成時の switch は悪いのか

    生成はどこか1か所に必要。分岐をファクトリに寄せ、業務ルール本体を各クラスに残すのがポイント。

    Q4. 状態遷移を表で持つ利点は

    許可される遷移が一覧でき、不正遷移のチェックと仕様の共有がしやすい。

    Q5. メソッド側の整理（ガード節など）との関係は

    先に分岐を読みやすくし、残った区分本体を区分オブジェクトへ移す、という段階的な整理になる（→ 場合分けのロジックを整理する）。
