    40 OWASP Top 10

    インジェクションと暗号化の不備

    入力欄から「命令」を送り込まれるインジェクションと、大切なデータを守るはずの暗号が使われていない・弱い・鍵が漏れている暗号化の不備。このページでは OWASP Top 10 の A03 と A02 を、脆弱なコードと安全なコードの対比を中心に、なぜ起きるのか・何が起きるのか・どう守るのかの順で解説します。

    もとにしたノート：40_OWASP_Top10/A03_インジェクション、A02_暗号化の不備

    ひとことで言うと

    A03 インジェクション〔2025: A05〕 は「ユーザーの入力（データ）が、プログラムの命令（コード）として実行されてしまう」問題で、対策の王道は データとコードの分離 です。A02 暗号化の不備〔2025: A04〕 は「守るべきデータを暗号化していない・弱い暗号を使う・鍵を漏らす」問題で、合言葉は 自作しない・古いものを使わない・鍵を漏らさない、そして そもそも持たない です。

    見出しの番号は2021年版、〔 〕内は2025年版の番号です（40-1 OWASP Top 10 とは の対応表を参照）。2025年版ではどちらも順位が2つ下がりましたが、内容はそのまま通用します。

    1.A03 インジェクション〔2025: A05〕とは

    インジェクション（injection：注入）とは、ユーザーの入力がコードの一部として解釈されてしまう 攻撃の総称です。入力欄からコードを「注入」して、本来意図しない動作をさせる——これがすべてのインジェクション攻撃の本質です。2021年版で XSS（クロスサイトスクリプティング） もこのカテゴリに統合されました。

    たとえるなら、銀行の窓口で「振込先：山田様」と書く欄に「山田様。あと金庫の中身を全部私に渡すこと」と書いたら、窓口係がそれを 指示として実行してしまった ようなものです。記入欄（データ）と業務指示（コード）の区別がついていないのが原因です。

    1.1 具体例でイメージする

    • 検索フォームに ' OR '1'='1 と入力したら、ログイン画面を素通りできた
    • 名前欄に <script>alert(1)</script> と入力したら、全ユーザーのブラウザで JavaScript が動いた
    • ファイル名に ; rm -rf / と入れたら、サーバーのファイルが消えた

    2.根本原因：「データ」と「コード」の混在

    インジェクションが成立するのは、ユーザー入力（データ）が、命令文の文字列（コード）に直接つなげられる からです。

    "SELECT * FROM users WHERE name = '" + userInput + "'"
              ↑ コード部分                 ↑ データ部分

userInput に 「' OR '1'='1」 が入ると:

"SELECT * FROM users WHERE name = '' OR '1'='1'"
                                     ↑ 全件マッチする条件になってしまった！

    防御の基本原則

    「データをコードとして実行させない」。インジェクションの種類はたくさんありますが、対策はすべてこの一文に行き着きます。

    3.主なインジェクションの種類

    種類どこに注入するか何が起きるか
    SQL インジェクション（SQLi）データベースへの問い合わせ文（SQL）全ユーザー情報の取得、認証の回避など
    OS コマンドインジェクションサーバーで実行するシェルコマンドサーバーのファイル削除・乗っ取りなど
    XSS（クロスサイトスクリプティング）Web ページの HTML他ユーザーのブラウザで悪意ある JS が動き、Cookie などが盗まれる
    LDAP インジェクションLDAP（社内のユーザー台帳などを検索する仕組み）への問い合わせ認証の回避などに悪用
    NoSQL インジェクションMongoDB などの NoSQL データベースへの問い合わせ条件をすり替えて全件マッチ・ログイン突破
    テンプレートインジェクション（SSTI）サーバー側のテンプレートエンジンサーバー上でコードが実行される。{{7*7}} が 49 と表示されることで検知される
    XML インジェクション / XXEXML の外部エンティティ（外部ファイルを読み込む機能）サーバー内のファイルを読み出される等

    3.1 種類ごとの「危険な書き方」

    ✕ SQL インジェクション 
    const sql = `SELECT * FROM users WHERE email = '${email}'`;
// email に ' OR '1'='1' -- を入れられると全ユーザー情報が返る
    ✕ コマンドインジェクション 
    exec(`convert ${filename} output.png`);
// filename に image.jpg; rm -rf / を入れられるとサーバーのファイルが消える
    ✕ XSS 
    document.getElementById('name').innerHTML = userInput;
// userInput に <script>fetch('/api/cookie?c='+document.cookie)</script> を入れられると
// 他ユーザーのクッキーが盗まれる
    ✕ NoSQL インジェクション 
    db.users.find({ username: req.body.username, password: req.body.password });
// req.body に { username: {$ne: null}, password: {$ne: null} } を送ると
// 「usernameがnullでない AND passwordがnullでない」= 全件マッチしてログイン可能

    NoSQL の例は、文字列ではなく オブジェクト（条件式） を送り込むのがポイントです。「SQL を使っていないから大丈夫」ではありません。

    4.SQL インジェクション：脆弱なコードと安全なコード

    ✕ 脆弱：文字列結合で SQL を組み立てる 
    const email = req.body.email; // ユーザー入力
const sql = `SELECT * FROM users WHERE email = '${email}'`;
const result = await db.query(sql);

    攻撃：email = "' OR '1'='1' --" を送る → 全ユーザーが返ります（-- は SQL のコメント記号で、後ろに続く部分を無効にします）。

    ○ 安全①：プリペアドステートメント（パラメータ化クエリ） 
    // データとコードを分離
const sql = 'SELECT * FROM users WHERE email = ?';
const result = await db.query(sql, [email]); // emailはデータとして扱われる

    ?（プレースホルダ：値の入る「穴」）にはめ込まれる値は データとしてしか 扱われないので、そこに ' OR '1'='1' が来ても命令としては解釈されません。

    ○ 安全②：ORM を使う 
    // Prisma
const user = await prisma.user.findUnique({ where: { email } });

// Sequelize
const user = await User.findOne({ where: { email } });

    ORM（データベース操作をプログラムのオブジェクトとして書ける仕組み）の多くは内部でプリペアドステートメントを使うため、デフォルトで安全 です。

    よくある誤解：「ORM なら何をしても安全」

    ORM にも、生の SQL 文字列を書ける機能があります。そこで文字列結合をすれば同じように危険です。安全なのは パラメータ化された使い方をしている間だけ です。

    5.XSS：脆弱なコードと安全なコード

    XSS（クロスサイトスクリプティング）は、Web ページに悪意ある JavaScript を埋め込み、そのページを見た他のユーザーのブラウザで実行させる 攻撃です。ログイン状態を表す Cookie を盗まれれば、なりすましにつながります（40-2 のセッションハイジャック）。

    XSS の種類説明
    反射型攻撃用の URL を踏ませて、その場で実行させる
    蓄積型（格納型）掲示板の投稿などとして DB に保存され、他のユーザーが閲覧したときに実行される
    DOM ベースサーバーを経由せず、ブラウザ側の JS がページを書き換える過程で発生する
    ✕ 脆弱：innerHTML に直接代入 
    document.getElementById('profile').innerHTML = `こんにちは ${userName}さん`;
// userName に <img src=x onerror="fetch('/api/steal?c='+document.cookie)"> を入れられると発火
    ○ 安全①：textContent を使う 
    document.getElementById('profile').textContent = `こんにちは ${userName}さん`;

    textContent は中身を HTML として解釈せず、ただの文字として表示するので安全です。

    ○ 安全②：フレームワークの自動エスケープに任せる 
    // React: 自動的にエスケープされる
<div>{userName}</div>
    ✕ 脆弱：自動エスケープを自分で無効化する 
    // dangerouslySetInnerHTML は名前のとおり危険
<div dangerouslySetInnerHTML={{ __html: userInput }} />

    React・Vue・Angular などは デフォルトでエスケープ（< などの特殊文字を無害な表記に置き換えること）してくれます。わざわざ無効化する書き方は避けましょう。

    ○ 安全③：CSP（Content Security Policy）で多重防御 
    Content-Security-Policy: default-src 'self'; script-src 'self'

    CSP はブラウザに「このページで実行してよいスクリプトの出どころ」を伝えるヘッダーです。万一 XSS が混入しても、外部スクリプトの実行や eval を禁止して被害を抑えられます。

    6.コマンドインジェクション：脆弱なコードと安全なコード

    ✕ 脆弱：シェル経由で文字列を実行 
    import { exec } from 'child_process';
exec(`ping ${host}`, callback); // host に ";rm -rf /" が入るとアウト
    ○ 安全：引数を配列で渡す（シェルを通さない） 
    import { execFile } from 'child_process';
execFile('ping', [host], callback); // hostは引数として扱われ、シェル解釈されない

    exec は文字列をシェル（コマンドを解釈するプログラム）に渡すため、; で区切られた2つ目の命令まで実行されます。execFile は引数を「ただの値」として渡すので、; も単なる文字です。

    原則

    シェルを経由しない、引数は配列で渡す、実行してよいコマンド自体をホワイトリスト（許可リスト）にする。

    7.インジェクションの防御の原則

    1. パラメータ化（分離）
      データとコードを必ず分ける。プリペアドステートメント、パラメータ化クエリ、引数配列を使う。これが本命の対策 です。
    2. エスケープ（出力時の無害化）
      HTML / JS / URL / SQL など、出力先の文脈に応じて特殊文字を無害化する。
    3. 入力検証（ホワイトリスト方式）
      「許可するものを列挙する」発想で検証する。ブラックリスト（禁止するものを列挙）は抜けやすい。
    4. 最小権限
      アプリが使う DB ユーザーの権限は必要最小限に。アプリ用ユーザーに DROP TABLE（テーブル削除）権限を与えない。
    5. WAF・CSP・SRI による多重防御
      WAF（Web Application Firewall）で怪しいリクエストをブロック、CSP で XSS の影響を制限、SRI（Subresource Integrity）で外部スクリプトの改ざんを検知。

    7.1 エスケープの基本形

    // HTMLエスケープの基本
function escapeHtml(str) {
  return str
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#39;');
}

    自前エスケープは最後の手段

    エスケープは文脈（HTML の本文・属性・JS・URL）ごとに必要な処理が違い、自作すると漏れが出やすいです。フレームワークやライブラリに任せるのが基本 です。

    7.2 ホワイトリストで入力を検証する

    ○ 許可：英数字とハイフンのみ 
    if (!/^[a-zA-Z0-9-]+$/.test(input)) throw new Error('Invalid input');

    入力検証はあくまで補助です。「検証したから文字列結合しても大丈夫」とはせず、分離（パラメータ化）と組み合わせる のが 深層防御 の考え方です。

    7.3 インジェクションのチェックリスト

    • SQL 実行時、文字列結合していないか？ プリペアドステートメント／ORM を使っているか？
    • innerHTML に外部入力を直接代入していないか？
    • exec、eval、system にユーザー入力を混ぜていないか？
    • 入力検証はホワイトリスト方式か？
    • フレームワークの自動エスケープを無効化していないか？
    • CSP ヘッダーを設定しているか？
    • DB ユーザーは最小権限か？

    XSS や SQL インジェクションの詳しい対策は、72_Web脆弱性対策 で詳しく扱います。

    8.A02 暗号化の不備〔2025: A04〕とは

    暗号化の不備 とは、パスワードやクレジットカード番号などの「大切なデータ」を守るべき場面で、暗号化していない、弱い暗号を使っている、鍵の管理を間違えている 問題です。旧名は「機密データの露出」（Sensitive Data Exposure）で、2021年版で「露出という結果」ではなく「暗号化の失敗という原因」に注目した名前に変わりました。

    暗号化は、手紙を鍵付きの箱に入れて送るようなものです。箱がなければ途中で読まれ（暗号化していない）、おもちゃの南京錠なら簡単に壊され（弱い暗号）、鍵を箱に貼り付けていれば意味がありません（鍵管理のミス）。

    8.1 具体例でイメージする

    • パスワードが 平文（暗号化もハッシュ化もしていない、そのままの文字）で DB に保存されている
    • クレジットカード番号が http（暗号化なし）で送信される
    • 古い方式（MD5、SHA-1、DES）でハッシュ化・暗号化されている
    • 暗号鍵がソースコードに直書きされ、GitHub に公開されてしまった

    8.2 守るべき「機密データ」

    分類具体例
    認証情報パスワード、API キー、秘密鍵、セッショントークン
    個人情報（PII）氏名・住所・電話番号・マイナンバー・生年月日
    金融情報クレジットカード番号、銀行口座
    医療情報病歴、処方箋
    業務データ顧客リスト、契約情報、社内文書

    GDPR（EU の個人データ保護規則）、個人情報保護法、PCI-DSS（クレジットカード業界の基準）、HIPAA（米国の医療情報の法律）など、法規制で 暗号化が求められる データもあります。

    9.データの「3つの状態」と暗号化

    データは、置かれている状態によって守り方が違います。

    1. 転送中（In Transit）

    • http:// ではなく https://
    • TLS 1.2 以上（理想は 1.3）
    • 自己署名ではなく正規の証明書（Let's Encrypt 等で無料取得可）

    2. 使用中（In Use）

    メモリ上のデータは通常守りにくいですが、機密性が極めて高い用途では TEE（Trusted Execution Environment：CPU 内の隔離された安全な実行領域）や Confidential Computing を使います。

    3. 保存中（At Rest）

    • DB の透過的暗号化（TDE）
    • ディスク全体の暗号化（BitLocker、FileVault、LUKS）
    • クラウドの暗号化（AWS KMS、GCP KMS など）

    10.暗号化：脆弱なコードと安全なコード

    10.1 パスワードを平文で保存しない

    ✕ 脆弱：平文で保存 
    // 絶対にやってはいけない
db.users.insert({ email, password: 'mypassword123' });

    DB が漏れたら、全員のパスワードがそのまま読まれます。使い回している人は他のサービスまで乗っ取られます。

    ○ 安全：パスワード用の強いハッシュで保存 
    import bcrypt from 'bcrypt';

const hashed = await bcrypt.hash(password, 12); // コスト12
db.users.insert({ email, password: hashed });

    パスワードには bcrypt・scrypt・Argon2 を使います。MD5、SHA-1、SHA-256 単体は パスワード用途では不適切 です（高速すぎて総当たりされる）。詳しくは 40-2 のパスワード保存 を参照してください。

    よくある誤解：「ハッシュ化＝暗号化」

    暗号化 は鍵があれば元に戻せる（復号できる）変換、ハッシュ化 は元に戻せない一方向の変換です。パスワードは「元に戻す必要がない」ので、暗号化ではなく パスワード用のハッシュ で保存します。

    10.2 弱い暗号を使わない

    ✕ 脆弱：古い暗号（DES・ECB モード） 
    # DES、3DES、RC4、MD5、SHA-1 は非推奨
cipher = DES.new(key, DES.MODE_ECB)
    ○ 安全：標準的な強い暗号（AES-256-GCM） 
    # 対称暗号: AES-256-GCM
# ハッシュ: SHA-256, SHA-3
# 鍵交換・署名: RSA-2048以上, ECDSA P-256以上
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
aesgcm = AESGCM(key)  # keyは256ビット
ciphertext = aesgcm.encrypt(nonce, plaintext, associated_data)

    10.3 鍵をソースコードに書かない

    ✕ 脆弱：暗号鍵の直書き 
    const SECRET_KEY = 'my-super-secret-key-12345'; // GitHubに公開されたら終了
    ○ 安全：秘密情報管理の仕組みから読み込む 
    // 環境変数や Secrets Manager / Vault から取得する
const SECRET_KEY = process.env.SECRET_KEY;
    • 環境変数
    • AWS Secrets Manager / HashiCorp Vault / GCP Secret Manager
    • .env ファイル（ただし .gitignore に必ず入れる）

    10.4 独自の暗号を作らない

    ✕ 独自の暗号アルゴリズムを作る

    「自分で考えた最強の暗号」は、ほぼ確実に破られます。

    ○ 標準ライブラリ・標準アルゴリズムを使う

    自作せず、広くレビューされ枯れている（長く使われて問題が出尽くした）ライブラリ を使いましょう。

    10.5 安全な乱数を使う

    トークンや鍵の生成など、セキュリティ用途では 暗号論的乱数生成器（CSPRNG：予測できないように作られた乱数）を使います。

    ✕ 脆弱：Math.random() は予測可能 
    const token = Math.random().toString(36).slice(2);
    ○ 安全：crypto.randomBytes() を使う 
    import crypto from 'crypto';
const token = crypto.randomBytes(32).toString('hex');

    11.推奨される暗号方式の早見表

    もとのノートの記載時点（2024年時点）の推奨です。暗号の推奨は年々変わるので、定期的に最新情報を確認しましょう。

    用途推奨非推奨
    パスワード保存○ Argon2id、bcrypt、scrypt✕ MD5、SHA-1、SHA-256単体
    対称暗号○ AES-256-GCM、ChaCha20-Poly1305✕ DES、3DES、RC4、AES-ECB
    ハッシュ○ SHA-256、SHA-3、BLAKE2✕ MD5、SHA-1
    公開鍵署名○ Ed25519、ECDSA P-256、RSA-2048以上✕ RSA-1024以下、DSA
    TLS○ TLS 1.3、TLS 1.2✕ SSL 3.0以前、TLS 1.0/1.1
    乱数○ crypto.randomBytes、secrets✕ Math.random()、rand()

    12.暗号化の防御の原則

    1. 不要なデータは持たない
      「そもそも保存しない」が最強の対策です。たとえばクレジットカード番号は自社で保存せず、決済代行サービス（Stripe 等） に任せるのが安全です（データ最小化）。
    2. 必要なデータは必ず暗号化
      保存時・転送時の両方で暗号化します。バックアップも忘れずに。
    3. 暗号鍵の管理を徹底
      鍵をコードに埋め込まない／鍵は定期的にローテーション（交換）する／鍵の保存先と暗号化したデータは別の場所に置く。
    4. 安全な乱数を使う
      セキュリティ用途では CSPRNG（crypto.randomBytes など）。
    5. 通信は常に HTTPS
      HSTS（Strict-Transport-Security）ヘッダーで、ブラウザに「このサイトには必ず HTTPS で接続せよ」と指示します。
    Strict-Transport-Security: max-age=31536000; includeSubDomains; preload

    もとのノートに追記された、2026年の情報漏洩事例を「暗号化・保存」の観点で整理したものです（事例全体は 50-5 サプライチェーン攻撃と2026年の事例 などで扱います）。

    事例暗号化・保存の観点

    米国防総省 DMDC（海外）暗号化していない 個人情報をファイル共有システムに置いていた

    教訓

    • ディスク暗号化（保存時の暗号化）だけでは足りない。アプリや正規アカウント経由で読まれると、復号されたデータがそのまま出ていく。本人確認書類や口座番号は アプリ層で項目ごとに暗号化 し、鍵は KMS で管理して、復号できるサービスを限る（エンベロープ暗号化：データを暗号化した鍵を、さらに別の鍵で暗号化して管理する方式）
    • パスワードは bcrypt / Argon2 で保存していれば、漏れても元のパスワードを割り出されにくい
    • 変更できない情報（免許証画像・生年月日）は、暗号化より先に「持たない」ことを考える

    13.1 暗号化のチェックリスト

    • パスワードは bcrypt / Argon2 でハッシュ化しているか？
    • HTTPS（TLS 1.2 以上）を全ページで使っているか？
    • 古い暗号方式（MD5・SHA-1・DES 等）を使っていないか？
    • 暗号鍵をソースコードに書いていないか？
    • 秘密鍵や API キーは秘密情報管理サービスで管理しているか？
    • 保存しているデータは、本当に必要なものだけか？
    • バックアップも暗号化されているか？

    14.まとめ

    このページの要点

    • インジェクションの本質は データとコードの混在。SQL・コマンド・XSS・NoSQL など種類は多いが原因は同じ
    • 対策の王道は 分離（プリペアドステートメント・ORM・引数配列）。出力時は エスケープ（フレームワーク任せ）、入力時は ホワイトリスト検証、さらに CSP・WAF・最小権限で多重防御
    • 暗号化はデータの 転送中・保存中・使用中 の3状態で考える
    • パスワードは bcrypt / Argon2、それ以外は AES-256-GCM などの標準的な暗号を使う
    • 三原則は 自作しない・古いものを使わない・鍵を漏らさない。そして「そもそも保存しない」が最もリスクを減らす

    15.理解度チェック

    Q1. SQL インジェクションの最も確実な対策は何ですか？ 入力から「'」を取り除くだけでは駄目ですか？

    最も確実なのは プリペアドステートメント（パラメータ化クエリ） や ORM で、データとコードを分離することです。特定の文字を取り除く方式（ブラックリスト）は抜け道が出やすく、それだけに頼るのは危険です。入力検証は補助として組み合わせます。

    Q2. ユーザー名を画面に表示するとき、innerHTML と textContent のどちらを使うべきですか？

    textContent です。innerHTML は文字列を HTML として解釈するため、<img onerror=...> のような入力で JavaScript が実行されます（XSS）。React なら {userName} のように通常の書き方をすれば自動でエスケープされます。

    Q3. 「DB のディスクを暗号化しているから、個人情報の漏洩対策は十分」と言えますか？

    言えません。ディスク暗号化はディスクそのものの盗難などには効きますが、アプリや正規アカウント経由で読まれると復号済みのデータが出ていきます。重要な項目はアプリ層で個別に暗号化して鍵を KMS で管理し、そもそも不要なデータは持たないことが大切です。

    Q4. ログイン用トークンを Math.random() で作ってはいけないのはなぜですか？

    Math.random() は暗号用に作られておらず、出力を予測できる 可能性があるためです。セキュリティ用途では crypto.randomBytes()（Node.js）や secrets（Python）などの暗号論的乱数生成器を使います。
