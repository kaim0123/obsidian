    30 脅威モデリング

    STRIDE ― 脅威を6つに分けて漏れなく探す

    「何が問題になり得るか？」を考えるとき、思いつきに頼ると抜けが出ます。STRIDE は脅威を6つの種類に分けたチェックリストで、データフロー図の部品ひとつひとつに当てはめていくことで、脅威を漏れなく洗い出せます。各カテゴリの意味・具体例・対策と、写真投稿アプリ「フォトボックス」への当てはめ方を解説します。

    もとにしたノート：71_セキュリティ基礎/30_脅威モデリング/02_STRIDE

    ひとことで言うと

    STRIDE ＝ 脅威の6分類チェックリスト。 なりすまし（S）・改ざん（T）・否認（R）・情報漏洩（I）・サービス妨害（D）・権限昇格（E）の頭文字です。それぞれが「守るべき性質」と1対1で対応しているので、「何が守れていないと、何が起きるか」がすっきり整理できます。

    1.STRIDEとは

    STRIDE（ストライド）は、Microsoft が提唱した 脅威を6つのカテゴリに分類する手法 です。脅威モデリングで最も広く使われているフレームワーク（考え方の枠組み）です。

    前のページ の「4つの問い」のうち、②何が問題になり得るか？ に答えるための道具にあたります。

    たとえ：病院の問診票

    医師は「どこか悪いところは？」と漠然と聞くだけでなく、「熱は？ せきは？ 食欲は？」と決まった項目を順に確認します。そうすれば聞き漏らしがありません。STRIDE はセキュリティ版の問診票で、システムの各部品に「なりすましは？ 改ざんは？ …」と6項目を順に聞いていきます。

    頭文字脅威守るべき性質一言で
    SSpoofing（なりすまし）Authenticity（真正性）＝本物であること他人のふりをする
    TTampering（改ざん）Integrity（完全性）＝正しく書き換えられていないことデータを書き換える
    RRepudiation（否認）Non-repudiation（否認防止）＝後から否定できないこと「やってない」と言い逃れる
    IInformation Disclosure（情報漏洩）Confidentiality（機密性）＝許された人だけが見られること見られたくない情報を見る
    DDenial of Service（サービス妨害）Availability（可用性）＝使いたいときに使えることサービスを止める
    EElevation of Privilege（権限昇格）Authorization（認可）＝許された操作だけできること権限を奪う・引き上げる

    CIA三原則とのつながり

    I（情報漏洩）は 機密性、T（改ざん）は 完全性、D（サービス妨害）は 可用性 を壊す脅威です。STRIDE は CIA の3つに、認証（S）・否認防止（R）・認可（E） を加えた6つの性質を守るためのチェックリストだと考えると覚えやすくなります。

    2.6つの脅威を1つずつ見る

    以下、各カテゴリを「どんな脅威？」「具体例」「緩和策（対策）」「フォトボックスでは？」の順に見ていきます。関連する OWASP Top 10 の番号は、ノートに合わせて2021年版の番号です。

    S ― Spoofing（なりすまし）

    攻撃者が他者のふりをする 攻撃です。本人確認（認証）を突破するタイプで、他人の家の合鍵を手に入れて、住人のふりをして入るようなものです。

    具体例

    • パスワードを盗んで他ユーザーとしてログイン
    • セッションID（ログイン状態を示す番号）を盗んでなりすまし
    • 偽の証明書でサーバーを偽装
    • フィッシング（偽サイト）で認証情報を盗む
    • IPアドレスやメール送信元の偽装

    緩和策

    • 強い認証（パスワードは bcrypt / Argon2 でハッシュ化して保存）
    • 多要素認証（MFA）
    • セッションIDの保護（Cookie に HttpOnly・Secure・SameSite 属性）
    • TLS による証明書の正当性検証
    • SPF / DKIM / DMARC（メール送信元の認証）
    • 署名付きトークン（JWT、署名付きCookie）

    関連：OWASP A07（認証と識別の失敗）→ 40-2

    フォトボックスでは：他人のパスワードでログインして、その人として写真を投稿・削除される。→ MFA とログイン試行の回数制限で守ります。

    T ― Tampering（改ざん）

    データを書き換える 攻撃です。完全性（データが正しいまま保たれていること）を壊します。郵便の途中で封筒を開け、中の書類を書き換えるイメージです。

    具体例

    • 通信途中のデータを書き換える（MITM＝通信の間に割り込む中間者攻撃）
    • DBに直接アクセスしてレコードを書き換える
    • フロントから送る価格パラメータを書き換える（商品価格を0円に）
    • アプリ本体（バイナリ）の解析・改造
    • ログを書き換えて攻撃の痕跡を消す
    • JWT の中身（payload）の書き換え

    緩和策

    • HTTPS / TLS で通信を暗号化し、改ざんを検知
    • デジタル署名、HMAC（メッセージが改ざんされていないことを確かめる符号）
    • DBへの直接アクセスを制限
    • サーバー側で最終検証（価格や数量はフロントの値を信じない）
    • ファイル・ログの改ざん検知（ハッシュチェーン、WORM＝一度書いたら消せないストレージ）
    • コード署名

    関連：OWASP A03（インジェクション）、A08（ソフトウェアとデータの整合性の不備）→ 40-3、40-5

    フォトボックスでは：写真をアップロードするとき、「誰の写真か」をブラウザから送らせていると、他人の名前で投稿できてしまいます。

    ✕ フロントの値を信じている 
    // アップロードAPI
const ownerId = req.body.ownerId;   // ブラウザが送ってきた値をそのまま使う
await savePhoto({ ownerId, file });
    ○ サーバー側で決める 
    // アップロードAPI
const ownerId = req.session.userId; // ログイン情報（サーバー側）から決める
await savePhoto({ ownerId, file });

    R ― Repudiation（否認）

    ユーザーが 「そんな操作はしていない」と言い逃れできてしまう 状況です。問題は攻撃そのものより、操作の証拠が残っていない ことにあります。防犯カメラも入館記録もない建物では、誰が何をしたか後から証明できないのと同じです。

    具体例

    • ログを残しておらず、誰が何をしたか分からない
    • ログを消せる権限を使って証拠隠滅
    • 電子契約で「本人が署名した証拠」がない
    • 共有アカウントのせいで個人を特定できない

    緩和策

    • 監査ログ（いつ・誰が・何をしたか）
    • ログの改ざん防止（署名、別の場所への転送、WORM）
    • デジタル署名（本人以外には作れない印）
    • 共有アカウントの禁止、個人アカウントの徹底
    • タイムスタンプサービス（法的に有効な日時証明）

    関連：OWASP A09（セキュリティログとモニタリングの不備）→ 40-6

    フォトボックスでは：不適切な写真が投稿されたとき「自分は投稿していない」と言われても、投稿ログ（日時・ユーザーID・IPなど）がなければ判断できません。管理者が写真を削除した操作も、誰がやったか記録が必要です。

    I ― Information Disclosure（情報漏洩）

    見られてはいけない情報が見られる 状態です。機密性の侵害で、ニュースになる事故の多くがここに当たります。

    具体例

    • 平文（暗号化なし）で保存したパスワードの流出
    • エラー画面にスタックトレース（プログラム内部の状態）やDB接続情報が表示される
    • HTTPS なしの通信でカード番号が漏れる
    • ストレージ（S3バケットなど）が全公開で、個人情報がダウンロードし放題
    • SSRF（サーバーに内部へのリクエストをさせる攻撃）で内部ネットワークの情報が漏れる
    • レスポンスヘッダーから内部IPやサーバーのバージョンが漏れる
    • アクセス制御の不備で他人の請求書が見える

    緩和策

    • データの 暗号化（通信中は TLS、保存時は AES-256 など）
    • 適切な アクセス制御
    • エラーメッセージは汎用的に（詳細はサーバーログだけに）
    • 最小権限の原則
    • クラウドリソースの公開設定の見直し
    • 機密情報のマスキング・最小化（そもそも保存しないのが最強）

    関連：OWASP A01（アクセス制御の不備）、A02（暗号化の失敗）、A05（セキュリティの設定ミス）→ 40-2、40-3、40-4

    フォトボックスでは：ログイン失敗時のメッセージの出し分けが、アカウントの存在を漏らしてしまう典型例です。

    ✕ 登録の有無が分かってしまう 
    このメールアドレスは登録されていません
パスワードが違います
    ○ どちらが違うか言わない 
    メールアドレスまたはパスワードが違います

    D ― Denial of Service（サービス妨害）

    サービスを 使えなくする 攻撃です。可用性の侵害で、お店の入口に大勢で押しかけて本物のお客さんが入れないようにするイメージです。

    具体例

    • DDoS 攻撃（大量の端末から一斉にリクエスト）でサーバーダウン
    • 特定の処理で CPU・メモリを使い切らせる（ReDoS＝正規表現を極端に遅くさせる攻撃、Zip爆弾＝展開すると巨大になる圧縮ファイル）
    • DBの接続（コネクション）を使い切らせる
    • 巨大なファイルをアップロードしてディスクを枯渇させる
    • ログインを無制限に試せる → アカウントロックで正規ユーザーを締め出す

    緩和策

    • レート制限（IPごと・ユーザーごと・エンドポイントごとの回数制限）
    • タイムアウトと入力サイズの上限
    • リソース使用量の上限（スレッド、コネクション、ファイルサイズ）
    • CDN / WAF / DDoS 対策サービス（AWS Shield、Cloudflare など）
    • オートスケーリング（負荷に応じてサーバーを自動で増やす）
    • 危険な正規表現の回避
    • 非同期処理・キュー・バックプレッシャー（受けきれない分を待たせる仕組み）

    フォトボックスでは：数GBのファイルを何度もアップロードされると、画像ストレージや変換処理が詰まります。→ ファイルサイズ上限とアップロード回数のレート制限を設けます。

    E ― Elevation of Privilege（権限昇格）

    本来持っていない 高い権限を不正に手に入れる 攻撃です。一般客用の入館証で、社員専用フロアや金庫室に入れてしまうような状態です。

    具体例

    • 一般ユーザーが管理者機能にアクセスできる
    • バッファオーバーフローなどのメモリ破壊から任意のコードを実行
    • sudo / setuid プログラム（一時的に高い権限で動くもの）の脆弱性で root 権限を奪取
    • SQLインジェクション → DB管理者権限を奪取 → OSに侵入
    • JWT の権限フィールド（role など）の書き換え
    • コンテナエスケープ（コンテナからホストへ抜け出す）

    緩和策

    • 最小権限の原則（→ 20-1）
    • サーバー側での認可チェック（「その写真の持ち主か」などの所有権チェックも）
    • 入力検証とサンドボックス化（隔離された環境で動かす）
    • メモリ安全な言語（Rust、Go など）
    • コンテナの実行環境の強化（seccomp、AppArmor、gVisor）
    • JWT の署名検証を厳密に（alg=none を禁止）
    • 特権プロセスを減らし、分離する

    関連：OWASP A01（アクセス制御の不備）→ 40-2

    フォトボックスでは：管理画面のURL（例：/admin）を知っていれば一般ユーザーでも開けてしまう、写真削除APIで「自分の写真か」を確認していない、などが典型です。

    3.STRIDEの使い方（ミニマム実践）

    1. データフロー図を描く
      部品とデータの流れを図にする（→ 30-1）。
    2. 各要素に STRIDE を当てる
      DFD の 各要素 に6カテゴリをチェックリストのように当てはめる（下の表）。
    3. 「ありうるか？」を議論する
      「このシステムで、この脅威は現実に起き得るか？」「起きたらどう影響するか？」を話し合う。
    4. 対策を決める
      各脅威について、緩和・移転・受容・回避のどれにするかを選ぶ。

    どの要素に、どの脅威を当てるか

    DFD の要素の種類ごとに、検討すべきカテゴリの目安があります。ノートでは次のように整理しています。

    要素STRIDE
    プロセス✓✓✓✓✓✓
    データフロー✓✓✓✓
    データストア✓✓✓✓
    外部エンティティ✓✓

    プロセスには6つ全部が当てはまる ので、重点的にチェックする対象です。なお、Microsoft の「STRIDE-per-element（要素ごとのSTRIDE）」として広く紹介される表では、データフローは T・I・D の3つとされることが多いです。表は「最低限ここは見る」という目安で、厳密さにこだわる必要はありません。

    4.実例：フォトボックスのログインAPIにSTRIDEを当てる

    対象は POST /api/login（ユーザー → ログインAPI → ユーザーDB）です。6項目を順に当てると、次の表ができます。

    STRIDE脅威の例緩和策
    Sパスワードリスト攻撃（他所で漏れたID・パスワードを試す）、セッション固定（攻撃者が用意したセッションIDを使わせる）MFA、レート制限、ログイン成功時にセッションIDを再発行
    Tリクエストボディの改ざんHTTPS、サーバー側でのパスワード検証
    R「ログインしていない」と主張されるログイン成功・失敗のログを記録
    Iエラーメッセージでアカウントの存在が漏れるメッセージを統一（「メールアドレスまたはパスワードが違います」）
    D大量のログイン試行で DB が枯渇レート制限、接続プールの上限
    E権限フィールドの改ざんで admin になるサーバー側で権限を検証、署名付きトークン

    このように6項目を機械的に当てていくと、思いつきでは抜けがちな R（ログ）や I（エラーメッセージ） まで漏れなく拾えるのが STRIDE のメリットです。

    実務でのポイント：表の形で残す

    「要素 × STRIDE × 脅威 × 対策 × 対応方針（緩和／受容など）」の表にして残しておくと、次回の見直しで差分だけ確認できます。「受容」にしたものも、理由と一緒に記録しておきましょう。

    5.STRIDEの限界と、他の手法との組み合わせ

    優先順位はつけられない

    網羅性はあるが、どれが深刻かは分からない。→ DREAD や CVSS と組み合わせる（→ 30-3）。

    業務ロジックの穴は見つけにくい

    「クーポンを何度も使える」のような ビジネスロジックの欠陥 は6分類に当てはめにくい。→ 悪用ケース分析 も併用する。

    慣れないうちは冗長

    全要素×6項目は量が多く感じる。→ 最初は フローの数を絞って 練習する。

    よくある誤解：「STRIDE で全部チェックしたから安全」

    STRIDE は「脅威の種類」の抜けを防ぐ道具であって、「すべての攻撃」を見つけてくれるわけではありません。DFD に描かれていない部品（描き忘れた外部サービスなど）には当てようがありませんし、業務ロジックの穴も残ります。DFD の正確さと、他の手法との併用が前提です。

    6.まとめ

    • STRIDE は脅威を なりすまし・改ざん・否認・情報漏洩・サービス妨害・権限昇格 の6カテゴリに分けるフレームワーク
    • 各カテゴリは 守るべき性質（真正性・完全性・否認防止・機密性・可用性・認可）と1対1で対応する
    • データフロー図の 各要素に当てはめて 使う。プロセスは6つすべてが対象
    • チェックリストとして使うと、ログやエラーメッセージのような 見落としやすい脅威 も拾える
    • 優先度付けは DREAD などの別手法 と組み合わせる

    7.理解度チェック

    Q1. 「共有の管理者アカウントを3人で使っていて、誰が写真を消したか分からない」。STRIDEのどれ？

    R（否認） です。操作した個人を特定できず、「自分はやっていない」と言い逃れできてしまいます。対策は、共有アカウントをやめて個人アカウントにし、監査ログを残すことです。

    Q2. 写真のURLが /photos/1001 のような連番で、番号を変えると他人の非公開写真が見られる。STRIDEのどれ？

    主に I（情報漏洩） です。原因はアクセス制御の不備（その写真を見る権限があるかをサーバーで確認していない）なので、E（権限昇格） の観点の「所有権チェック」も関係します。このように1つの問題が複数のカテゴリにまたがることはよくあり、どちらに分類するかより「見つけられたか」が大事です。

    Q3. DFDのどの種類の要素に、STRIDEの6項目すべてを当てるべき？ それはなぜ？

    プロセス です。プロセスは入力を受け取り、処理し、他の要素に命令を出すので、なりすまされる・改ざんされる・止められる・権限を奪われる…と、あらゆる脅威の舞台になり得るからです。
