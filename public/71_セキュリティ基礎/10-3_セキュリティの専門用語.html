    10 基本概念

    セキュリティの専門用語

    ニュースや脆弱性情報を読んだときに「意味が分かる」状態を目指して、セキュリティの議論に必ず出てくる用語を整理します。情報セキュリティの7要素、攻撃の用語（エクスプロイト・ペイロード・ゼロデイ）、脆弱性の識別子と指標（CVE・CWE・CVSS・EPSS・KEV など）、暗号技術（共通鍵・公開鍵・ハッシュ・電子署名・PKI・TLS）の4つの柱です。

    もとにしたノート：10_基本概念/03_セキュリティの基本概念と専門用語（知識地図3章）

    ひとことで言うと

    用語は4つのグループに分けると迷子になりません。守りたいもの（7要素）、攻撃（脆弱性 → エクスプロイト → ペイロード）、弱点の名前と危険度（CVE が「名前」、CWE が「種類」、CVSS が「深刻度」、EPSS が「悪用されそうか」、KEV が「実際に悪用済みか」）、守る技術（暗号・PKI・TLS）です。

    1.情報セキュリティの7要素

    情報を守るとき、何を「守る」のかを言葉にしたものです。もっとも有名な CIA（機密性・完全性・可用性）に、4つの要素を加えたものが「7要素」です。

    1.1 CIA（基本の3つ）

    要素英語意味守れていないときの例
    機密性Confidentiality許可された者だけが情報にアクセスできる個人情報の漏洩、パスワードの流出
    完全性Integrity情報が改ざん・破壊されていないデータベースの不正な書き換え、ファイルの改ざん
    可用性Availability必要なときに情報・サービスが使えるサーバー停止、DDoS によるアクセス不能

    3つはトレードオフになることも多くあります。たとえば厳しい認証（機密性↑）は手間が増え、使いにくくなる（可用性↓）ことがあります。詳しくは CIA三原則と脅威・脆弱性・リスク を参照してください。

    1.2 追加の4要素

    要素英語意味具体例
    真正性Authenticity送信者・情報源が本物であることなりすましメールの検知、デジタル署名による確認
    信頼性Reliabilityシステムが期待どおり正確に動くこと決済システムの計算ミス、誤ったログ記録（が起きないこと）
    責任追跡性Accountability誰が何をしたか追跡できること監査ログ、操作履歴の記録
    否認防止Non-repudiation行ったことを後から「やっていない」と否定できないこと電子署名付きの契約、改ざんが難しいログ

    1.3 7要素の関係

    7つをバラバラに覚えるより、「何のための要素か」で3つのグループに分けると覚えやすくなります。

    1.4 対策技術との対応

    要素主な対策技術
    機密性暗号化、アクセス制御、認証
    完全性ハッシュ値、デジタル署名、バージョン管理
    可用性冗長化、バックアップ、DDoS 対策
    真正性MFA、デジタル証明書、SPF / DKIM（メールの送信元確認）
    信頼性テスト、監視、エラーハンドリング
    責任追跡性監査ログ、SIEM（ログを集めて分析する仕組み）
    否認防止電子署名、タイムスタンプ、改ざん検知つきのログ

    2.攻撃に関する用語

    2.1 サービス妨害系：DoS と DDoS

    DoS 攻撃（Denial of Service）

    1か所から大量のリクエストを送り、サービスを使えなくする攻撃。

    DDoS 攻撃（Distributed DoS）

    多数の端末（ボットネットなど）から同時に攻撃する DoS。規模が大きく、1か所を遮断しても止まらないため防御が難しい。

    どちらも狙うのは 可用性です。例：EC サイトへのアクセス集中、DNS サーバーの過負荷。

    2.2 脆弱性悪用系：脆弱性 → エクスプロイト → ペイロード

    攻撃の流れを表す言葉は、泥棒の侵入にたとえると覚えやすくなります。

    用語説明たとえ
    脆弱性（Vulnerability）ソフトウェアや設定の弱点鍵のかかっていない窓
    エクスプロイト（Exploit）脆弱性を 実際に悪用する コードや手法その窓から入る道具・手口
    ペイロード（Payload）攻撃が成功した後に実行される 本体の処理（マルウェア本体、データ窃取など）侵入後に運び込む「荷物」
    ゼロデイ攻撃修正パッチがまだない脆弱性（ゼロデイ）を悪用する攻撃鍵屋が来る前に窓から入る
    PoC（Proof of Concept）脆弱性が本当に悪用できるかを示す 実証コード。悪用と同じくらい危険な場合もある「この窓は開く」と実演して見せる

    2.3 マルウェアと標的型攻撃

    用語説明
    マルウェア悪意のあるソフトウェアの総称（ウイルス、ランサムウェア、トロイの木馬など。種類は 10-2 参照）
    標的型攻撃特定の組織・個人を狙って綿密に計画された攻撃。APT（持続的標的型攻撃）と呼ばれる高度なものも含む

    標的型攻撃には、スピアフィッシング（狙い撃ちの偽メール）で入口を作る、長期間潜伏して情報を集める、一般的なマルウェアより検知が難しい、という特徴があります。

    2.4 認証・人を狙う攻撃

    用語説明
    ブルートフォース攻撃パスワードを総当たりで試す
    辞書攻撃よく使われるパスワードのリストで試す
    パスワードスプレーよくある少数のパスワードを、多数のアカウントに試す
    クレデンシャルスタッフィング他のサイトで漏れた ID・パスワードの使い回しを試す
    フィッシング本物の連絡を装い、パスワードや個人情報をだまし取る

    3.脆弱性の識別子と指標

    脆弱性の情報は世界中で毎日公開されています。混乱しないように、同じ弱点に同じ名前を付け、危険度を数値にする仕組みが整っています。アルファベット3〜4文字の略語がたくさん出てきますが、「どの質問に答えるものか」で整理すれば怖くありません。

    3.1 CVE — 脆弱性の「名前」

    CVE（Common Vulnerabilities and Exposures）は、公開された脆弱性に付けられる一意の IDです。

    項目内容
    形式CVE-年-連番（例：CVE-2024-12345）
    管理MITRE が運営し、NVD（米国の国立脆弱性データベース）などで詳細が公開される
    役割「この製品のこのバグ」を、世界中で同じ名前で呼べるようにする

    有名な例が CVE-2021-44228（通称 Log4Shell）で、Java のログライブラリ Log4j の重大な脆弱性です。セキュリティニュースで CVE-XXXX-XXXXX と出てきたら、「公式に登録された脆弱性の名前」と思えば十分です。

    3.2 CWE — 弱点の「種類」

    CWE（Common Weakness Enumeration）は、脆弱性の 原因・パターンの分類です。CVE より抽象的で、「どんな種類のコーディングミスか」を表します。形式は CWE-番号 です。

    CVECWE
    粒度特定の製品の、特定のバグ弱点のパターン・種類
    例CVE-2021-44228（Log4j の具体的な穴）CWE-917（Expression Language Injection）
    病気でいうと「○○さんの今回の症例」「インフルエンザ」という病名
    よく見る CWE名称説明
    CWE-79クロスサイトスクリプティング（XSS）Web ページに悪意のあるスクリプトを埋め込む
    CWE-89SQL インジェクションSQL 文に悪意のある入力を混ぜる
    CWE-787範囲外への書き込み（バッファオーバーフローの一種）想定外のデータでメモリを破壊する
    CWE-798ハードコードされた認証情報ソースコードにパスワードを直書きする

    3.3 CVSS — 脆弱性の「深刻度」

    CVSS（Common Vulnerability Scoring System）は、脆弱性の深刻度を 0.0〜10.0 の数値で表すスコアです。

    スコア帯深刻度目安
    0.0None影響なし
    0.1〜3.9Low低
    4.0〜6.9Medium中
    7.0〜8.9High高
    9.0〜10.0Critical最重要

    評価の観点（CVSS v3.1 の例）は、攻撃ベクトル（ネットワーク経由か、物理的に触る必要があるか）、攻撃の複雑さ、必要な権限、ユーザー操作（被害者の操作が必要か）、そして 機密性・完全性・可用性への影響 です。

    よくある誤解：「CVSS が高い＝自社にとって危ない」

    CVSS は 技術的な深刻度であり、自社環境での実際のリスクとは違います。スコアが高くても、自社でその製品を使っていなければ影響はありません。詳しくは リスク管理のページ でも扱います。

    3.4 CPE — 影響を受ける製品の識別子

    CPE（Common Platform Enumeration）は、影響を受ける製品・バージョンを 機械が読める形式で表す識別子です。形式は cpe:2.3:a:ベンダー:製品:バージョン:... です。

    cpe:2.3:a:apache:log4j:2.14.1:*:*:*:*:*:*:*
→ Apache Log4j バージョン 2.14.1

    脆弱性スキャナーが「自社のどのソフトに当てはまるか」を自動判定するのに使います。日常会話ではあまり出てきませんが、パッチ管理ツールや脆弱性スキャナーの裏側で働いています。

    3.5 SSVC — 「自社にとってどれくらい急ぎか」

    SSVC（Stakeholder-Specific Vulnerability Categorization）は、組織ごとの状況に合わせて、パッチを当てる優先度を判断するためのフレームワークです。CVSS が「脆弱性そのものの深刻度」なのに対し、SSVC は「自社にとっての急ぎ度」を考えます。

    判断軸質問の例
    悪用の可能性攻撃コードはすでに公開されているか
    影響の規模自社でそのソフトを使っているか、重要なシステムか
    環境の安全性インターネットに公開されているか、内部だけか

    判断の結果は Track（監視）／ Track*（優先監視）／ Attend（対応）／ Act（即時対応） のように出力されます。「CVSS 9.8 でも自社で使っていなければ優先度は低い」「CVSS 7.0 でもインターネット公開サーバーなら最優先」といった判断に使います。

    3.6 EPSS — 「悪用されそうか」の確率

    EPSS（Exploit Prediction Scoring System）は、近いうち（今後30日以内）にその脆弱性が悪用される確率を 0〜1（0〜100%）で予測するスコアです。FIRST（インシデント対応チームの国際フォーラム）が提供し、毎日更新されます。

    • CVSS が中程度でも EPSS が高い → 早めにパッチ
    • CVSS が高くても EPSS が低い → 他の対応を優先してよい場合がある

    3.7 KEV カタログ — 「実際に悪用済み」のリスト

    KEV カタログ（Known Exploited Vulnerabilities Catalog）は、米国の CISA（サイバーセキュリティ・インフラストラクチャセキュリティ庁）が管理する、実際の攻撃で悪用が確認された脆弱性のリストです。リストに載っている ＝ 今すぐ対応すべき という強いシグナルです。

    1. 自社の資産をスキャンした結果と KEV リストを照らし合わせる
    2. 一致した CVE は最優先でパッチ、または緩和策を適用する
    3. 政府機関や大企業の調達要件で、KEV への対応が求められることもある

    3.8 使い分けのまとめ

    指標何を教えてくれるかいつ使うか
    CVE脆弱性の名前情報の検索、パッチとの照合
    CWE弱点の種類開発時の予防、コードレビュー
    CVSS技術的な深刻度最初の優先度付け
    CPE影響を受ける製品スキャナーによる自動マッチング
    SSVC組織にとっての優先度パッチ運用の判断
    EPSS悪用される確率CVSS を補った優先度付け
    KEV実際に悪用済みか最優先で対応するかの判断

    実務でのポイント

    優先順位は1つの数字で決めず、深刻度（CVSS）× 悪用されそうか（EPSS・KEV）× 自社での重要度・露出度 を組み合わせます。特に KEV に載った脆弱性が、インターネットに公開している機器（VPN 装置など）にあれば最優先です。

    4.暗号技術の用語

    暗号は、機密性・完全性・真正性・否認防止を支える土台の技術です。ここでは用語の意味と役割を中心に整理します（理論の詳細は 11_コンピューターサイエンス の暗号のノートが本拠地です）。

    4.1 共通鍵暗号と公開鍵暗号

    共通鍵暗号（対称鍵暗号）

    暗号化と復号に同じ鍵を使う。家の鍵と同じで、閉めるのも開けるのも同じ鍵。

    • 長所：処理が速く、大量データ向き
    • 短所：相手に鍵を安全に渡す方法が問題（鍵配送問題）

    公開鍵暗号（非対称鍵暗号）

    公開鍵と秘密鍵のペアを使う。郵便ポストにたとえると、投函口（公開鍵）は誰でも使えるが、中身を取り出す鍵（秘密鍵）は持ち主だけ。

    • 長所：鍵配送問題を解決できる。署名にも使える
    • 短所：共通鍵暗号より処理が重い
    分類アルゴリズム状態・用途
    共通鍵AES現行の標準。ファイル暗号化、VPN、TLS の中身など
    3DES非推奨（古いシステム向け）
    ChaCha20現行。TLS やモバイル向け（AES より速い環境もある）
    公開鍵RSA電子署名、鍵交換（古くからあり、今も広く残っている）
    ECDSA / ECDH現代の TLS や Bitcoin など（楕円曲線暗号。鍵が短く効率的）

    AES（Advanced Encryption Standard）は2001年に米国政府が標準として採用した暗号で、鍵の長さは 128 / 192 / 256 ビット。Wi-Fi（WPA2/WPA3）、ディスク暗号化（BitLocker など）、HTTPS の中で広く使われています。「軍事級の暗号」と表現されることもありますが、正しく実装・運用されていることが前提です。

    公開鍵暗号で秘密のメッセージを送る流れは、「Alice が Bob の公開鍵で暗号化 → Bob だけが自分の秘密鍵で復号できる」です。

    4.2 ハッシュ関数

    任意の長さのデータから、固定長の「指紋」を作る一方向の関数です。元のデータに戻すことはできません。

    • 同じ入力からは常に同じ出力。入力が少しでも変わると出力は大きく変わる
    • 用途：パスワードの保存、ファイルの改ざん検知、デジタル署名の一部
    • 注意：暗号化ではない（元に戻せないが、総当たりで推測されることはある）
    アルゴリズム状態
    SHA-256 / SHA-3現行標準
    MD5 / SHA-1非推奨（別々の入力から同じ出力を作る「衝突攻撃」が現実的）
    ✕ パスワードの悪い保存方法 
    password_plain = "hunter2"              # そのまま保存 → 漏れたら即アウト
password_hash  = sha256("hunter2")      # 速いハッシュだけ → 事前計算表（レインボーテーブル）や総当たりに弱い
    ○ 正しい保存方法 
    password_hash = bcrypt.hash("hunter2")  # bcrypt / scrypt / Argon2 など「わざと遅い」ハッシュ
                                         # ＋ ユーザーごとに異なるソルト（ライブラリが自動で付ける）

    4.3 電子署名

    送信者の身元確認と改ざん検知を同時に実現する技術です。紙の書類に押す実印のデジタル版で、しかも「中身が1文字でも変わったら分かる」実印です。

    署名の作成（送信者）

    1. メッセージのハッシュ値を計算する
    2. 送信者の 秘密鍵 でハッシュ値から署名を作る

    署名の検証（受信者）

    1. 送信者の 公開鍵 で署名を検証し、元のハッシュ値（A）を得る
    2. 受け取ったメッセージのハッシュ値（B）を計算する
    3. A と B が一致 → 改ざんなし ＆ 送信者確認

    守れる要素は 真正性・完全性・否認防止 です。

    4.4 PKI（公開鍵基盤）

    公開鍵暗号には「その公開鍵は本当にその相手のものか？」という問題が残ります。これを解決するのが、公開鍵とデジタル証明書を信頼できる形で配布・管理する仕組みである PKI です。役所が発行する印鑑証明書のような仕組みだと考えてください。

    構成要素役割
    CA（認証局）デジタル証明書を発行する、信頼の起点
    デジタル証明書「この公開鍵はこの組織のものである」と CA が保証する電子文書
    CRL / OCSP失効した（無効になった）証明書のリスト・確認サービス

    身近な例は、ブラウザのアドレスバーの鍵マーク（HTTPS）、社内 VPN のクライアント証明書、コード署名（ソフトウェアの改ざん防止）などです。

    4.5 TLS — HTTPS の「S」の正体

    TLS（Transport Layer Security）は、インターネット上の通信を暗号化するプロトコルです（旧称 SSL）。通信内容の機密性と改ざん検知を守ります。公開鍵暗号で鍵を安全に交換し、その後は共通鍵（AES など）で高速に暗号化する、という 両方のいいとこ取りをしています。

    1. クライアント「接続したい」
    2. サーバー「これが私の証明書です」（公開鍵入り）
    3. クライアントが証明書を検証する（CA の署名を確認）
    4. 双方で共通のセッション鍵を安全に決める
    5. 以降の通信はセッション鍵（AES など）で暗号化する

    よくある誤解：「鍵マークがあれば安全なサイト」

    HTTPS が保証するのは 通信経路の暗号化と、接続先がそのドメインであることまでです。サイト自体が安全とは限りません（フィッシングサイトも HTTPS にできます）。また TLS 1.0 / 1.1 は非推奨で、TLS 1.2 / 1.3 を使います。

    4.6 暗号技術の関係

    目的技術役割
    データの保護共通鍵暗号（AES）大量データの暗号化
    公開鍵暗号（RSA / 楕円曲線）鍵交換、署名
    データの検証ハッシュ関数（SHA-256）改ざん検知、パスワード保存
    電子署名送信者確認 ＋ 改ざん検知
    信頼の仕組みPKI（CA ＋ 証明書）公開鍵の持ち主を保証する
    通信の保護TLS公開鍵で鍵交換 ＋ AES で暗号化 ＋ 証明書で身元確認

    5.用語の総合マップ

    最後に、このページの用語がどうつながっているかを確認しましょう。

    6.まとめ

    • 7要素：CIA が基本。真正性・否認防止などは「誰が・本当に」を守る。
    • 攻撃の用語：脆弱性 → エクスプロイト → ペイロード の順で理解する。
    • CVE と CWE：CVE は「具体的な穴」の名前、CWE は「穴の種類」。
    • CVSS / EPSS / KEV：深刻度・悪用確率・悪用済みか、を組み合わせて優先度を決める。CVSS だけで決めない。
    • 暗号：共通鍵は速い、公開鍵は鍵交換と署名、ハッシュは指紋、TLS は両方を組み合わせた通信保護。

    7.理解度チェック

    Q1. 「CVE-2021-44228」と「CWE-89」の違いは？

    CVE-2021-44228 は Log4j という 特定の製品の特定の脆弱性に付いた名前（ID）です。CWE-89 は SQL インジェクションという 弱点の種類で、多くの製品の多くの脆弱性が同じ CWE に分類されます。

    Q2. CVSS 9.8 の脆弱性と、KEV に載った CVSS 6.5 の脆弱性。自社のインターネット公開 VPN 装置に後者が当てはまるとき、どちらを先に直す？

    状況によりますが、KEV に載っている（実際に悪用されている）脆弱性が、外部から届く機器にあるなら、そちらを最優先にするのが基本です。CVSS は技術的な深刻度であり、自社にとっての緊急度は悪用状況や露出度も合わせて判断します。

    Q3. パスワードを SHA-256 でハッシュ化して保存すれば十分？

    不十分です。SHA-256 は高速なので、事前計算表（レインボーテーブル）や総当たりで推測されやすくなります。bcrypt / scrypt / Argon2 のような「わざと遅い」ハッシュとソルトを使います。

    Q4. 電子署名で守れる要素を3つ挙げると？

    真正性（送信者が本物）、完全性（改ざんされていない）、否認防止（後から「送っていない」と言えない）です。
