    20 設計原則

    ゼロトラスト（Zero Trust）

    「社内ネットワークの内側だから安全」という前提を捨て、すべてのアクセスをその都度確かめるセキュリティの考え方です。従来の「城壁モデル」がなぜ通用しなくなったのか、ゼロトラストは何を・どう確かめるのか、どんな部品で実現し、どの順番で導入するのかを、よくある誤解とあわせて解説します。

    もとにしたノート：20_設計原則/03_ゼロトラスト

    ひとことで言うと

    ゼロトラストのスローガンは "Never trust, always verify"（決して信頼せず、常に検証する）。「どこから来たか（社内か社外か）」ではなく、「誰が・どの端末で・どんな状況で・何にアクセスしようとしているか」 を、アクセスのたびに確かめます。

    1.ゼロトラストとは

    ゼロトラスト（Zero Trust）とは、

    何も信頼しない。すべてのアクセスを都度検証する

    というセキュリティモデルです。2010年に調査会社 Forrester のアナリスト John Kindervag が提唱し、2020年代に入って急速に主流になりました。

    たとえるなら、病院の電子カルテ のようなものです。病院の建物に入れたからといって、誰でも全患者のカルテを見られるわけではありません。カルテを開くたびに「職員証で本人確認」「その患者の担当か」「病院の端末からか」が確かめられ、閲覧の記録も残ります。建物の中にいること自体は、信頼の理由になりません。

    「ゼロ」の意味

    「誰も信用しない冷たい仕組み」という意味ではなく、「場所や過去の1回の確認だけで、無条件に信頼することをゼロにする」 という意味です。確かめたうえで、必要な分だけ信頼します。

    2.従来の「境界防御モデル」とその限界

    2.1 境界防御 ＝ 城壁モデル

    長い間、企業のセキュリティは 境界防御 が標準でした。社内ネットワークと外部（インターネット）の間に ファイアウォール（通信を通すか止めるかを決める関所）を置き、ここだけで厳しくチェックする方式です。

    • 入口（境界）で厳しくチェック する
    • 一度入れば、社内は自由に動ける

    2.2 なぜ破綻したのか

    城壁モデルは、「守るべきものは全部城の中にあり、社員も城の中で働く」という前提で成り立っていました。しかし現代では、その前提が崩れています。

    変化何が起きたか
    リモートワーク社員は自宅・カフェ・海外から接続する。「社内」という境界そのものが消えた
    クラウド利用データは SaaS やクラウドに分散。自社のデータセンターだけに境界を引けない
    モバイル端末スマホや私物PCが業務に使われる
    サプライチェーン攻撃ソフトのアップデートなど 正規の経路 で侵入される（→ サプライチェーン攻撃と2026年の事例）
    内部犯・内部侵害一度侵入した攻撃者が「社内＝信頼」を悪用し、社内の機器を次々と乗っ取って広がる（横展開）

    城壁モデルの弱点

    城壁モデルでは、城門さえ突破すれば城の中は自由 です。盗まれたパスワード1つ、乗っ取られたPC1台から、社内全体に被害が広がります。「境界の内側だから安全」は、もはや幻想になりました。

    3.ゼロトラストの考え方

    3.1 核となる6つの原則

    1. すべての通信を認証・認可する：社内・社外を問わない（認証＝誰かの確認、認可＝それをしてよいかの確認）
    2. 最小権限：必要最小限のアクセスだけを許可する（→ 最小権限）
    3. マイクロセグメンテーション：内部ネットワークも細かく区切る
    4. 常時検証：一度認証したら終わりではなく、継続的に確かめる
    5. 暗号化：すべての通信を暗号化する
    6. 可視化とログ：すべての活動を監視・記録する

    3.2 アクセスは「動的に」判定する

    1回のログインだけで判断せず、アクセスのたびに 次のような情報（コンテキスト＝そのときの状況）を総合して許可・拒否を決めます。

    観点確かめること
    ユーザー誰か、MFA（多要素認証）を通過したか
    端末会社が管理している端末か、OSは最新か、マルウェアに感染していないか
    場所どこからか（普段と違わないか、危険な地域ではないか）
    時間帯通常の業務時間か
    行動普段通りか、異常ではないか
    対象データアクセス先のデータの機密度はどれくらいか

    たとえば「いつもの社員が、会社のPCから、平日昼に、社内Wikiを見る」なら自動で許可。「同じ社員でも、深夜に、初めて見る国から、顧客データを大量に出力しようとしている」なら追加の確認を求めたり拒否したりします。

    4.従来モデルとゼロトラストの比較

    従来（境界防御）ゼロトラスト
    信頼モデル内側を信頼誰も無条件には信頼しない
    認証入口で1回アクセスごとに都度
    ネットワーク内と外で分ける細かくセグメント化
    アクセス権一度与えたら固定動的・状況次第
    確かめる対象主にユーザーユーザー＋デバイス＋ワークロード（サーバーやプログラム）
    VPN社外からの入口として必須必ずしも必要ない

    5.ゼロトラストを支える部品

    ゼロトラストは1つの製品ではなく、複数の部品を組み合わせて実現します。代表的なものは次の6つです。

    ① IDaaS（ID基盤のクラウドサービス）

    組織のID（アカウント）を統合し、認証の中心になる。SSO（一度のログインで複数のサービスを使える仕組み）、MFA、条件付きアクセスを提供。例：Okta、Microsoft Entra ID（旧 Azure AD）、Google Workspace、Auth0。

    ② ZTNA（ゼロトラスト型のネットワークアクセス）

    従来の VPN の代わり。「社内ネットワークに入れる」のではなく 「このアプリだけ使える」 とアプリ単位でアクセスを制御する。例：Cloudflare Access、Zscaler Private Access、Tailscale、Twingate。

    ③ デバイス管理（MDM / EDR）

    端末の健全性を継続的に評価する。MDM は端末の設定を会社が管理する仕組み（例：Jamf、Intune、Kandji）、EDR は端末上の不審な動きを検知・対応する仕組み（例：CrowdStrike、SentinelOne）。

    ④ マイクロセグメンテーション

    ネットワークを細かく区切り、侵害されても横展開させない。サービス同士の通信を mTLS（お互いに証明書を見せ合う相互認証）で確かめる、Kubernetes の NetworkPolicy、Service Mesh（Istio、Linkerd）など。

    ⑤ ポリシー判定点（PDP）

    アクセスを許可するかを判定するエンジン。ユーザー属性＋端末状態＋リクエスト内容を条件に判定する。例：Open Policy Agent（OPA）、クラウド IAM の条件付きポリシー。

    ⑥ 継続的な可視化

    SIEM（ログを集めて分析する基盤）や UEBA（ユーザーや機器の振る舞いを分析して異常を見つける仕組み）で、異常行動を検知し、監査ログを集約する。

    6.例：開発者が本番サーバーに入るとき

    同じ作業でも、従来のやり方とゼロトラストではここまで変わります。

    従来のやり方

    1. VPN に接続（社内ネットワークの一員になる）
    2. SSH で本番サーバーに接続
    3. sudo で root に昇格
    4. 作業

    問題：VPNを越えたら社内全体が見える。SSH鍵が1つ漏れたら全サーバーに被害。権限は固定のまま。

    ゼロトラスト版

    1. IDaaS で SSO + MFA 認証
    2. 端末の健全性チェック（OSが最新、EDRが動作中）
    3. JIT 権限昇格：承認者の許可を得る
    4. ZTNA で、対象サーバーにだけ通路を張る
    5. 操作の録画（Session Recording）
    6. 時間が経つと 自動で権限が失効

    ゼロトラスト版では、攻撃者が認証情報を1つ奪っても、端末・場所・時間などの条件で弾かれます。仮に通っても、届くのはその1台だけで、時間が来れば権限は消えます。

    7.導入のステップ（NIST SP 800-207 を参考に）

    米国の標準化機関 NIST が公表した文書 SP 800-207「Zero Trust Architecture」 などを参考に、段階的に進めます。

    1. 準備：守るべき資産の洗い出し、データの流れとアクセス経路の把握、既存のID基盤の評価
    2. 最小構成のゼロトラスト：全ユーザーに MFA を強制、SSO の統合、デバイス管理の導入、重要なアプリから ZTNA に移行
    3. 拡張：マイクロセグメンテーション、アプリ間通信に mTLS、ポリシーエンジンの導入、継続的な行動分析
    4. 最適化：ポリシーのコード化による自動化、AI による異常検知、定期的なアクセスレビュー

    一般的な導入順

    MFA の全社展開 → SSO → ZTNA → マイクロセグメンテーション の順が一般的です。最初の MFA だけでも大きな効果があります。

    8.ゼロトラストのよくある誤解

    誤解1：「製品を買えば実現できる」

    ゼロトラストは アーキテクチャの考え方 であって、単一の製品ではありません。複数のツールの組み合わせと、日々の運用で実現します。

    誤解2：「VPN を廃止すればゴール」

    VPN はしばしば ZTNA に置き換えられますが、それ自体はゴールではありません。認証・認可のあり方全体が変わることが本質です。

    誤解3：「完全に実装するのは難しいから意味がない」

    段階的な導入が前提 です。MFA を全社に展開するだけでも大きな効果があります。

    誤解4：「内部を信頼しないのは性悪説で、社員に失礼」

    悪意の有無を疑っているのではなく、マルウェア感染や乗っ取り に備えているのです。善良な社員の端末でも侵害されうる、という前提に立っています。

    誤解5：「確認が増えて使いにくくなる」

    うまく実装すれば、SSO と条件付きアクセスで むしろスムーズ になります。いつもの端末・いつもの状況ならパスワード入力すら不要、ということもできます。

    9.他の原則との関係と業界の動き

    9.1 他の原則との関係

    原則ゼロトラストとの関係
    最小権限ゼロトラストの基礎。与える権限が最小だからこそ、常時検証が意味を持つ
    深層防御ゼロトラストは深層防御の進化形。境界頼みをやめ、すべての層で守る
    セキュアバイデザインゼロトラストは設計原則として、初期から組み込む

    9.2 業界の動き

    年出来事
    2010年Forrester の John Kindervag がゼロトラストを提唱
    2020年NIST が SP 800-207「Zero Trust Architecture」を公表
    2021年米国の大統領令で、連邦政府機関にゼロトラストの採用を求める
    2022年日本の NISC もゼロトラストに関する指針を公表
    —主要クラウド（AWS、Azure、GCP）がゼロトラスト関連サービスを拡充

    10.2026年の事例：VPN が最大の入口に

    境界防御モデルの限界は、2026年の国内の統計にもはっきり表れています。

    • 警察庁によると、2026年上半期のランサムウェア被害で侵入経路が分かった36件のうち、VPN 機器が18件、リモートデスクトップが9件
    • 攻撃の中心は 修正されていない脆弱性と、漏えいした認証情報。「社内ネットワークに入れれば信頼される」構造が悪用された
    • VPN 装置そのものがインターネットに公開された攻撃対象になっている（デジタル庁 GSS、両毛システムズなど）

    10.1 認証のあとも検証が必要

    海外では、攻撃者が 電話で従業員を誘導して SSO と MFA を奪い、自分の MFA デバイスを登録させる 手口（ShinyHunters 系）が報告されています。ログインの瞬間だけ確かめても防げません。

    • MFA デバイスの登録やパスワードリセットの直後の高リスクな操作は、追加で確認する
    • ログイン後の挙動（大量のデータエクスポートなど）を継続して監視する（→ ログ不足・SSRF・例外処理）

    10.2 実務での優先順位

    1. VPN をすぐにやめられないなら、MFA 必須・パッチ適用の期限（SLA）・使っていないアカウントの削除（→ 脆弱性管理とランサムウェア対策）
    2. RDP（リモートデスクトップ）をインターネットに公開しない
    3. 段階的に ZTNA へ移し、VPN 装置をインターネットから見えなくする

    11.チェックリスト

    • 全社員に MFA を強制しているか？
    • SSO で認証を集約しているか？
    • 端末の健全性（OS更新、EDRなど）をチェックしているか？
    • 社内・VPN 接続だけで信頼していないか？
    • 重要なアプリは ZTNA で保護しているか？
    • サービス間の通信は相互認証（mTLS）しているか？
    • 異常なアクセスパターンを検知する仕組みがあるか？
    • 特権アクセスは JIT で付与しているか？
    • すべてのアクセスをログに残し、監査できるようにしているか？

    12.まとめ

    このページの要点

    • ゼロトラストは 「決して信頼せず、常に検証する」 モデル
    • 境界防御（城壁モデル）は、リモートワーク・クラウド時代に限界を迎えた。2026年もVPN機器が最大の侵入口
    • ID・デバイス・コンテキスト を、アクセスのたびに検証する。ログイン後も監視を続ける
    • 最小権限 + 継続検証 + 可視化 が柱
    • 製品1つで実現するものではなく、段階的な旅。MFA → SSO → ZTNA → マイクロセグメンテーション の順が一般的

    13.理解度チェック

    Q1. 境界防御モデルの最大の弱点は何ですか？

    一度境界の内側に入られると、中は自由に動けてしまう ことです。盗まれた認証情報1つ、乗っ取られた端末1台から社内全体へ横展開されます。また、リモートワークやクラウドの普及で、そもそも境界が引けなくなりました。

    Q2. ゼロトラストでアクセスを判定するときに見る情報を3つ以上挙げてください。

    ユーザー（誰か・MFA済みか）、端末（管理端末か・OSは最新か・感染していないか）、場所、時間帯、普段の行動との違い、アクセス先データの機密度、などです。

    Q3. 「ZTNA を導入して VPN を廃止したので、ゼロトラストは完成した」。この考えのどこが問題ですか？

    ゼロトラストは製品や VPN 廃止で完成するものではなく、認証・認可のあり方全体を変える考え方 だからです。MFA、端末の健全性チェック、最小権限、ログイン後の継続的な監視などを組み合わせ、運用し続ける必要があります。2026年に報告された「MFA デバイスを攻撃者に登録させる」手口のように、ログインの瞬間だけの確認では防げない攻撃もあります。
