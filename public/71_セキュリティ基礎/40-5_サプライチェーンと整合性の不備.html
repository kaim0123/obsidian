    サプライチェーンと整合性の不備

    ソフトウェアは「作る → ビルドする → 配る → 更新する」という長い流れを通って届きます。その途中のどこかを乗っ取られると、正規の更新や正規のパッケージとして悪意あるコードが届いてしまいます。このページでは、2025年版で新設された「ソフトウェアサプライチェーンの不備」と、それと深く重なる「ソフトウェアとデータの整合性の不備」を、実際の事件と悪い例・良い例のコードで解説します。

    もとにしたノート：40_OWASP_Top10/2025_A03_ソフトウェアサプライチェーンの不備、A08_ソフトウェアとデータの整合性の不備、01_OWASP_Top10_2025の変更点

    ひとことで言うと

    サプライチェーンの不備 は「部品の仕入れ先・工場・配送ルートのどこかが乗っ取られている」問題、整合性の不備 は「届いた荷物が途中ですり替えられていないか確かめずに使ってしまう」問題です。守り方の柱は、部品表（SBOM）で中身を把握し、ビルドと配布の仕組みを固め、署名やハッシュで「本物であること」を確かめてから使う ことです。

    2.まずイメージ：ソフトウェアのサプライチェーンとは

    サプライチェーン はもともと「原材料の調達 → 製造 → 物流 → 販売」という供給の連鎖のことです。食品なら、農家・工場・運送会社・お店のどこか1か所で異物が混入しても、お客さんの口に入ってしまいます。

    ソフトウェアも同じで、開発者の端末で書かれたコードが、リポジトリ（コードの保管場所）→ CI/CD（自動でビルド・テスト・配布する仕組み）→ パッケージレジストリ（npm などの部品の配布所）を経て利用者に届きます。攻撃者はこの流れのどこかに入り込めば、正規の経路でマルウェアを届けられます。

    3.ソフトウェアサプライチェーンの不備（A03:2025 新設 ／ 2021 A06 を拡張）

    3.1 どんな問題か

    2021年版の A06 は「既知の脆弱性を持つライブラリを使っている」問題でした。2025年版の A03 はそこから範囲を広げ、

    ソフトウェアが「作られ・配布され・更新される」仕組みのどこかが壊れている、または乗っ取られている

    ことすべてを扱います。対象は依存ライブラリだけでなく、CI/CD・ビルドサーバー・開発者の端末・IDE 拡張・パッケージレジストリ・コンテナレジストリ・SaaS 連携 まで含みます。

    なぜ CVE が少ないのか

    CVE は「ソフトウェアの欠陥」に付く番号です。ところがサプライチェーン攻撃の多くは、欠陥ではなく 仕組みの悪用（アカウントの乗っ取り、悪意あるパッケージの公開）なので、CVE 番号が付きにくいのです。ツールのテストデータだけでは拾えないため、コミュニティ調査の枠 でも選ばれました。

    4.実際の攻撃シナリオ

    4.1 信頼しているベンダーが侵害される（SolarWinds、2019〜2020年）

    攻撃者が SolarWinds 社のビルド環境に侵入し、監視製品 Orion の 正規アップデートにバックドア（こっそり出入りできる裏口）を混入しました。約18,000の組織（米国政府機関を含む）が、署名された正規の更新としてマルウェアを取り込みました。署名は「この会社が作った」ことは保証しますが、「ビルド環境が汚染されていない」ことまでは保証しない、という教訓を残しました。

    4.2 特定の条件でだけ動く悪意あるコード（Bybit、2025年）

    暗号資産取引所 Bybit から 約15億ドル が盗まれた事件です。ウォレットソフトウェアのサプライチェーンが侵害され、標的のウォレットを使うときだけ 悪意ある動作をするよう仕込まれていました。ふだんは正常に動くため、テストや監視で見つけにくいのが特徴です。

    4.3 自己増殖する npm ワーム（Shai-Hulud、2025年）

    初めて成功した 自己増殖型の npm ワーム（自分で自分をコピーして広がるマルウェア）とされます。

    1. 人気パッケージの悪意あるバージョンが公開される
    2. インストール時に自動で動く postinstall スクリプトが、開発者の端末や CI から認証情報（トークン・クラウドの鍵）を盗み、公開 GitHub リポジトリに書き出す
    3. 盗んだ npm トークン を使い、被害者がメンテナンスしている別のパッケージにも悪意あるバージョンを公開する
    4. 2 に戻って連鎖する

    npm が止めるまでに 500以上のパッケージバージョン が影響を受けました。開発者の端末そのものがサプライチェーン攻撃の主要な標的になった ことを示した事件です。

    4.4 強い権限を持つ部品の欠陥

    部品は通常、アプリと同じ権限で動きます。そのため、どれか1つの欠陥がアプリ全体の乗っ取りにつながります。

    • CVE-2017-5638（Apache Struts 2 のリモートコード実行）：大規模な情報漏洩につながった
    • CVE-2021-44228（Log4Shell）：ランサムウェアや暗号資産の不正採掘などに悪用された（→ Log4Shell から学ぶ教訓）

    4.5 こんな状態なら危ない（OWASP の挙げる条件）

    • 推移的な依存（依存の依存）を含め、クライアント側・サーバー側すべての部品のバージョンを把握していない
    • OS・Web サーバー・DBMS・API・ランタイム・ライブラリに、脆弱・サポート切れ・古いものがある
    • 定期的な脆弱性スキャンや、セキュリティ情報の購読をしていない
    • サプライチェーン全体（IDE・拡張機能・リポジトリ・サンドボックス・成果物の保管場所）の 変更管理・変更履歴 がない
    • サプライチェーンの各要素（特にアクセス制御）を強化していない
    • 職務分離がない：1人がコードを書いて、誰のチェックも受けずに本番へ出せる
    • 信頼できない提供元の部品が本番に影響しうる
    • パッチを月次・四半期ごとにしか当てず、数日〜数か月の無防備な期間がある
    • 更新したライブラリの互換性をテストしていない
    • CI/CD パイプラインのセキュリティが、それがビルド・デプロイするシステムより弱い

    5.サプライチェーンの守り方

    5.1 部品とパッチを管理する

    • SBOM（ソフトウェア部品表）を組織のソフトウェア全体について一元的に生成・管理する（形式は CycloneDX、SPDX）
    • 直接依存だけでなく 推移的な依存 も追跡する
    • 使っていない依存・機能・ファイルを削除し、攻撃対象を減らす
    • OWASP Dependency-Track / Dependency-Check、Retire.js などで継続的に棚卸しする
    • CVE・NVD・OSV（脆弱性情報のデータベース）を監視し、SCA ツールで自動化、アラートを購読する
    • 信頼できる提供元から安全な経路で取得し、署名付きパッケージ を優先する
    • 依存のバージョンは意図して選び、必要なときに上げる（無条件の最新追従はしない）
    • 保守されていない部品に注意。パッチが出ないなら代替へ移行、移行もできないなら 仮想パッチ（WAF などで攻撃を検知・遮断する）
    • CI/CD・IDE・開発ツール自体も定期的に更新する
    • 一斉に更新しない。段階的な展開やカナリア（一部の環境だけ先に更新して様子を見る方法）で、ベンダーが侵害された場合の影響を限定する

    すべてで MFA（多要素認証）を有効にし、IAM（権限）を最小限に します（最小権限）。

    5.4 開発者の端末と npm での実践

    Shai-Hulud 型の攻撃を踏まえた、すぐできる対策です。

    ✕ 危険：インストール時スクリプトを無条件に実行し、ロックファイルも無視しがち 
    # CI でも開発端末でも、毎回これ
npm install
    ○ 安全：スクリプトを既定で止め、ロックファイルどおりに入れる 
    # インストールスクリプトを既定で実行しない（必要なパッケージだけ許可）
npm config set ignore-scripts true

# ロックファイルどおりに入れる（CI では npm install ではなく npm ci）
npm ci

# 公開から一定期間たっていない新しいバージョンを避ける（pnpm の例）
# pnpm-workspace.yaml
# minimumReleaseAge: 1440   # 分。公開から24時間未満のバージョンは入れない
    • npm への公開は Trusted Publishing（OIDC） を使い、長期間有効な公開トークンを持たない（盗まれても使える鍵を置かない）
    • パッケージの公開アカウントには フィッシング耐性のある MFA（パスキー・セキュリティキー）
    • CI の秘密情報は必要なジョブ・環境だけに渡す。外部からの PR で動くワークフローに秘密情報を渡さない
    • GitHub Actions は コミット SHA で固定 する（タグは後から書き換えられる）
    ✕ タグ参照：乗っ取られると中身が差し替わる 
    - uses: some-org/some-action@v3
    ○ コミット SHA で固定（Dependabot / Renovate で更新） 
    - uses: some-org/some-action@3f1c2b7e9a0d4c5b6e7f8a9b0c1d2e3f4a5b6c7d # v3.2.1

    タグ（v3）は「付箋」のようなもので、後から別のコミットに貼り替えられます。SHA はコードの中身から計算される「指紋」なので、中身が変われば必ず変わります。

    6.ソフトウェアとデータの整合性の不備（A08:2021 ／ A08:2025）

    6.1 どんな問題か

    整合性（Integrity：完全性とも訳す）とは、「データやコードが正規のまま、改ざんされていない」ことです（CIA三原則 の I）。この項目は、信頼できないところからコードやデータを取り込み、本物か確かめずに使ってしまう ことで起きる問題を扱います。2021年版で新設され、2025年版でも8位のままです。

    宅配便にたとえると、封がされていない荷物や、差出人が分からない荷物を、中身を確かめずにそのまま使うようなものです。

    • npm のパッケージが乗っ取られ、正規のライブラリを装ったマルウェアが配られる
    • CDN（外部の配信サーバー）から読み込む JavaScript が差し替えられ、全ユーザーのブラウザで悪意あるコードが動く
    • Jenkins のプラグインや CI/CD が改ざんされ、ビルド成果物にバックドアが埋め込まれる
    • 署名を確かめない自動アップデートで、偽のファームウェアを配られる
    • 信頼できないデータをデシリアライズして、リモートコード実行される

    6.2 現実に起きた事件

    事件何が起きたか
    SolarWinds（2020年）Orion のビルドシステムが侵害され、正規の署名付きアップデート にバックドア。18,000の組織（米国政府機関を含む）が影響を受けた、史上最大級のサプライチェーン攻撃
    event-stream（2018年）npm の人気パッケージのメンテナー権限が悪意ある第三者に譲られ、依存パッケージに暗号通貨を盗むコードが埋め込まれた
    Codecov（2021年）CI ツール Codecov の Bash Uploader スクリプトが改ざんされ、CI 環境の環境変数（API キー・トークン）が外部に送られていた

    6.3 3つのリスク

    ① ソフトウェアの整合性

    信頼できない場所からコードを取得して実行してしまう。

    • npm / PyPI / Docker Hub の汚染
    • CDN の JavaScript の改ざん
    • ビルドシステム・CI/CD の侵害

    ② CI/CD パイプラインの整合性

    パイプライン自体が守られていないと、作られた成果物も信頼できない。

    • CI/CD の権限管理が甘い
    • ビルド環境が共有されて汚染される
    • デプロイ時に署名を確かめない

    ③ 安全でないデシリアライゼーション

    外から来たデータをオブジェクトに戻すとき、任意のコードが実行される恐れがある（次の章）。

    7.安全でないデシリアライゼーション

    シリアライズ とは、プログラムの中のデータ（オブジェクト）を、保存や送信ができる形（文字列やバイト列）に変換することです。その逆に、受け取った文字列やバイト列をオブジェクトに戻すことを デシリアライズ といいます。引っ越しにたとえると、家具を分解して箱に詰めるのがシリアライズ、届いた箱から組み立て直すのがデシリアライズです。

    問題は、形式によっては 「組み立て直す」途中で、箱の中の指示書どおりにプログラムを動かしてしまう ものがあることです。攻撃者が細工した箱を送るだけで、サーバー上で好きなコードを動かせてしまいます。

    ✕ 危険：Python の pickle で外部データを復元 
    import pickle
data = pickle.loads(user_input)  # ← 超危険

    pickle は Python のオブジェクトを復元する過程で 任意のコードを実行できます。攻撃者は仕掛けをしたデータを送るだけでサーバーを乗っ取れます。

    ✕ 危険：Java の標準デシリアライズ 
    ObjectInputStream in = new ObjectInputStream(request.getInputStream());
Object obj = in.readObject(); // ← 信頼できないデータを渡すと危険

    Java 標準の ObjectInputStream.readObject() に信頼できないデータを渡すと、ガジェットチェーン（アプリにもともとあるクラスを数珠つなぎに悪用する手法）でリモートコード実行される脆弱性が多数見つかっています。

    ○ 安全：コード実行能力のない形式（JSON など）を使う 
    import json
data = json.loads(user_input)  # JSON はデータしか表せない
# さらにスキーマ（期待する形）で検証してから使う
    • JSON はコードを実行する能力がない、安全な形式
    • Protocol Buffers、MessagePack など、コード実行を含まない形式を選ぶ
    • どうしても言語固有のシリアライズが必要なら、署名検証 と 許可リスト型の復元（決めたクラスしか復元しない）を組み合わせる

    8.整合性を守る4つの対策

    8.1 信頼できる場所からだけ取得し、ハッシュで確かめる

    ○ 取得元を固定し、インストール時スクリプトを止める 
    # npm: 公式レジストリのみ
npm config set registry https://registry.npmjs.org/

# インストール時スクリプトを無効化（サプライチェーン対策）
npm install --ignore-scripts

# 内部プロキシを経由（Artifactory、Nexus など）
npm config set registry https://npm.internal.company/

    package-lock.json や yarn.lock には、各パッケージの ハッシュ値（integrity）が記録されます。ハッシュ値は、ファイルの中身から計算される「指紋」で、1文字でも変われば別の値になります。

    {
  "lodash": {
    "version": "4.17.21",
    "integrity": "sha512-v2kDEe57lecTulaDIuNTPy3Ry4gLGJ6Z1O3vE1krgXZNrsQ+LFTGHVxVjcXPs17LhbZVGedAJv8XZ1tvj5FvSg=="
  }
}

    インストール時にハッシュが一致しなければ失敗するので、途中での改ざんを検知できます。

    ✕ 本番・CI で使わない（依存関係を更新する可能性がある） 
    npm install
    ○ 本番・CI 用（ロックファイルに厳密に従う） 
    npm ci

    8.2 CDN の JavaScript には SRI を付ける

    外部の CDN から JavaScript を読み込む場合、SRI（Subresource Integrity：読み込むファイルのハッシュ値をあらかじめ書いておく仕組み）で改ざんを検知します。

    ✕ SRI なし：CDN 側で差し替えられても気づけない 
    <script src="https://cdn.example.com/lib.js"></script>
    ○ SRI 付き：ハッシュが一致しなければブラウザが実行しない 
    <script
  src="https://cdn.example.com/lib.js"
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYl1kPzQho1wx4JwY8wC"
  crossorigin="anonymous"
></script>

    8.3 コード署名と検証

    署名 は、荷物の封に押す「本人の印鑑」のようなものです。作った人だけが押せる印で、受け取る側はその印が本物か、封が破られていないかを確かめます。

    • アプリ配布：配布時にコード署名（Apple Developer Certificate、Microsoft Authenticode）を行い、アップデート取得時には 必ず署名を検証 する。自動アップデート機構（Sparkle、Squirrel）の署名検証を有効化する
    • コンテナイメージ：Docker Content Trust や Sigstore / Cosign で署名・検証する
    • Git のコミット：コミットに署名すると GitHub で「Verified」バッジが付く
    # Docker Content Trust
export DOCKER_CONTENT_TRUST=1
docker push myimage:v1  # 署名付きでpush
docker pull myimage:v1  # 署名検証してpull

# Gitコミット署名
git config --global commit.gpgsign true
git config --global user.signingkey <key-id>

    8.4 CI/CD パイプラインを守る

    1. 権限を分けて最小にする：ビルド用のロボットアカウントは必要最小限の権限。本番デプロイには人間の承認ステップを必須に。CI の機密情報（API キーなど）は必要なジョブにだけ渡す。
    2. ビルド環境を隔離する：各ビルドを独立したコンテナ・VM で実行し、前のビルドの影響を受けないようにする。プルリクエストのビルドは権限を制限する。
    3. GitHub Actions を固める：サードパーティのアクションはコミット SHA で固定し、ワークフローのデフォルト権限を最小にする（下の例）。
    4. SLSA で段階的に強化する：Google 主導のサプライチェーンセキュリティ成熟度フレームワーク。レベルごとに、来歴・署名・改ざん検知・独立したビルド環境などの要求が定められている。
    ✕ タグ参照＋権限の指定なし 
    - uses: someone/action@v1
    ○ SHA 固定＋デフォルト権限は読み取りのみ 
    permissions:
  contents: read

steps:
  - uses: someone/action@abc1234567890abcdef1234567890abcdef12
    整合性対策のチェックリスト
    • 依存関係は公式／社内プロキシ経由のみから取得しているか？
    • ロックファイル（package-lock.json など）をコミットしているか？
    • 本番ビルドで npm ci などの厳密モードを使っているか？
    • CDN の JavaScript に SRI を設定しているか？
    • 自動アップデート機構で署名検証しているか？
    • Docker イメージ／バイナリに署名しているか？
    • CI/CD の権限は最小化されているか？
    • デシリアライズで pickle / Java Serialization を避け、JSON などを使っているか？
    • インストール時スクリプト（postinstall）を無効化できる構成か？

    9.3つの項目の関係を整理する

    「古いコンポーネント」「サプライチェーン」「整合性」は重なり合っています。違いを表にまとめます。

    観点A06:2021 脆弱で古いコンポーネントA03:2025 サプライチェーンの不備A08 整合性の不備
    主な問題既知の脆弱性を持つ部品を使っている部品の調達・ビルド・配布の仕組みが弱い／侵害されている改ざんされたコード・データを検証せずに信用する
    攻撃者の動き公開された脆弱性を突く上流（ベンダー・メンテナー・CI）を乗っ取り、正規の経路で悪意あるコードを届ける署名なしの更新や、信頼できない入力のデシリアライズを悪用
    代表例Log4Shell、Struts 2SolarWinds、Shai-Hulud、Bybit署名なしの自動更新、CI での未検証プラグイン
    主な対策SCA、パッチ適用SBOM、変更管理、CI/CD と開発端末の強化、段階的展開署名、来歴（provenance）の検証

    A03:2025 は A06:2021 を 包み込み、A08 とは「署名・来歴の検証」で 重なります。委託先や組織どうしのサプライチェーン（ソフトウェア以外）は サプライチェーン攻撃と2026年の事例 で扱います。

    10.よくある誤解

    「署名付きのアップデートなら、中身は安全」

    限りません。 SolarWinds 事件では、ビルド環境そのものが侵害されていたため、バックドア入りの更新に 正規の署名 が付いていました。署名は「この会社から届いた」ことを保証しますが、「作る過程が汚染されていない」ことまでは保証しません。だからこそ、ビルド環境の隔離・職務分離・来歴の記録（SLSA）・段階的な展開を組み合わせます。

    「有名で人気のあるパッケージなら安心」

    誤りです。 event-stream や Shai-Hulud は、人気パッケージが乗っ取られた例です。人気があるほど影響範囲が広いので、むしろ攻撃者に狙われます。

    「開発者のパソコンは本番ではないから、そこまで守らなくていい」

    危険な考えです。 開発者の端末には npm の公開トークンやクラウドの鍵が置かれていることが多く、Shai-Hulud はまさにそこを狙いました。端末にもパッチ・MFA・EDR を適用し、長期トークンを置かない（Trusted Publishing）ようにします。

    「JSON なら何も気にせずに受け取ってよい」

    コード実行の心配は大きく減りますが、検証は必要です。 JSON はコードを実行できないので pickle より安全ですが、想定外の項目や型、巨大なデータが来ることはあります。スキーマで形を検証してから使います。

    11.まとめ

    このページの要点

    • サプライチェーンの不備（A03:2025 新設）は、2021年版 A06 を「部品の脆弱性」から 「作る・配る・更新する仕組み全体」 へ広げたカテゴリ。発生率は全カテゴリで最も高い
    • 攻撃者は 上流（ベンダー・メンテナー・CI・開発者の端末） を乗っ取り、正規の経路で届ける（SolarWinds、Bybit、Shai-Hulud）
    • 対策の柱は SBOM と棚卸し・変更管理・CI/CD と開発端末の強化・署名と来歴・段階的展開。CI/CD はデプロイ先と同じかそれ以上に守る
    • 整合性の不備（A08:2021 ／ A08:2025）は、本物か確かめずにコードやデータを使う問題。ロックファイルのハッシュ・SRI・コード署名・CI/CD の保護 が基本
    • デシリアライズは pickle や Java の ObjectInputStream を避け、JSON など コード実行能力のない形式へ

    12.理解度チェック

    Q1. 2021年版の「脆弱で古いコンポーネント」と、2025年版の「ソフトウェアサプライチェーンの不備」は何が違う？

    2021年版 A06 は 既知の脆弱性を持つ部品を使っている ことが中心でした。2025年版 A03 はそれを含みつつ、部品の調達・ビルド・配布・更新の仕組み全体（CI/CD、開発者の端末、IDE 拡張、レジストリなど）が弱い・乗っ取られている状態まで扱います。攻撃者が上流を乗っ取って正規の経路で届ける、というのが典型的な形です。

    Q2. GitHub Actions を uses: some-org/action@v3 ではなく、コミット SHA で指定するのはなぜ？

    タグ（v3）は後から別のコミットに付け替えられるため、アクションの作者のアカウントが乗っ取られると、同じ @v3 のまま中身を悪意あるコードに差し替えられてしまいます。コミット SHA は中身から計算される値なので、中身が変われば値も変わり、差し替えに巻き込まれません。更新は Dependabot / Renovate の PR として意図して取り込みます。

    Q3. 外部から受け取ったデータを pickle.loads() で復元しているコードを見つけた。何が危険で、どう直す？

    pickle は復元の途中で 任意のコードを実行できる ため、攻撃者が細工したデータを送るだけでサーバーを乗っ取られます（安全でないデシリアライゼーション）。JSON や Protocol Buffers など、コード実行能力のない形式 に置き換え、受け取った後はスキーマで検証します。どうしても言語固有の形式が必要なら、署名検証と許可リスト型の復元を組み合わせます。
