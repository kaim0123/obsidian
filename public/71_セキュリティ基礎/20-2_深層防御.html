    20 設計原則

    深層防御（Defense in Depth）

    「1つの守りが破られても、次の守りで止める」。城の堀と城壁のように、性質の違う対策を何層にも重ねる考え方です。なぜ1つの対策では足りないのか、Webアプリやログイン機能ではどんな層を積むのか、どこから手を付けるべきか、そしてやりがちな失敗までを解説します。

    もとにしたノート：20_設計原則/02_深層防御

    ひとことで言うと

    深層防御は 「卵は一つのカゴに盛るな」 のセキュリティ版です。どんな対策もいつかは破られる前提で、違う場所・違う性質の対策を何層にも重ねて、1層が破られても全体としては守り切れるようにします。

    1.深層防御とは

    深層防御（Defense in Depth）とは、

    1つの防御が破られても、次の防御層で止める

    ために、複数のセキュリティ対策を多層的に重ねる 考え方です。もともとは軍事用語で、お城の 外堀 → 城壁 → 内堀 → 天守閣 のような守りをイメージすると分かりやすいでしょう。外堀を越えられても城壁がある、城壁を越えられても内堀がある――攻める側は何度も壁にぶつかります。

    身近な例では、銀行がそうです。入口には警備員、店内には防犯カメラ、カウンターの奥は関係者以外立入禁止、お金は金庫に入っていて、金庫を開けるには複数人の鍵が必要。どれか1つを突破されても、残りの仕組みが働きます。

    用語メモ

    この分野でいう 層（レイヤー） とは「守りの段」のこと。ネットワークの入口、サーバー、アプリ、データ、そして運用する人間――攻撃者が目的にたどり着くまでに通る場所ごとに、それぞれ守りを置きます。

    2.なぜ1つの対策では足りないのか

    2.1 完璧な防御は存在しない

    どんなに強固な対策も、いつか破られる可能性があります。たとえば次のような理由です。

    • 新しい 脆弱性（ソフトウェアの弱点）が見つかる。修正が出る前に悪用されるものを ゼロデイ と呼ぶ
    • 設定ミス で、対策がいつの間にか無効になっている
    • 人的ミス で、パスワードなどの認証情報が漏れる
    • 誰も予想していなかった 新しい攻撃手法 が登場する

    2.2 攻撃者を遅らせ、コストを上げる

    目的にたどり着くまでに何層も突破が必要なら、攻撃者にとっては次のような不利が生まれます。

    時間がかかる

    作業が長引くほど、防御側に 見つかる可能性 が上がります。

    コストがかさむ

    割に合わなければ、攻撃者は 他の標的に移る ことがあります。

    ミスをする

    手数が増えるほど痕跡が残り、防御側が気付ける チャンスが増えます。

    2.3 検知と対応の時間を稼ぐ

    層を突破されている間に 異常を検知 し、対応する時間 を確保できます。泥棒が玄関の鍵をこじ開けている間に防犯ブザーが鳴れば、家の中に入られる前に警察を呼べる、というわけです。

    3.「多層」の例：Webアプリの顧客情報を守る

    「データベースの顧客情報を盗む」という1つの目標に対して、防御側は次のように層を重ねます。下から順に、攻撃者が通る順番です。

    層内容この層があると…
    1WAF / CDN / DDoS対策。WAF は Web アプリ向けのファイアウォール、DDoS は大量の通信で相手を止める攻撃明らかに悪意ある通信を入口で遮断
    2認証・認可・セッション管理。認証は「あなたは誰か」、認可は「それをしてよいか」の確認他人のふりをさせない、権限外を触らせない
    3入力検証・パラメータ化クエリSQLインジェクションを防ぐ
    4ネットワーク隔離（VPC、プライベートサブネット）DBにインターネットから直接アクセスできない
    5DBユーザーの最小権限侵入されてもテーブル削除や管理操作はできない（→ 最小権限）
    6DB自体の暗号化（保存時の暗号化＝At Rest）ファイルごと盗まれても読めない
    7監査ログと異常検知侵入されても検知してアラートを出せる

    どれか1層だけでは不十分です。すべての層を積んで初めて、実用的な防御になります。

    4.層にはどんな種類があるか

    システム全体で見ると、守りを置く場所は大きく6つに分けられます。

    層主な対策
    物理層データセンターの入退室管理・監視カメラ、サーバー機器の施錠、廃棄時のディスク破壊
    ネットワーク層ファイアウォール（通信の交通整理）、IDS/IPS（侵入の検知・防止）、VPC・セグメンテーション（内部ネットワークの分割）、VPN / ゼロトラストネットワーク
    ホスト層OSパッチ（修正プログラム）の自動適用、アンチウイルス / EDR（端末の不審な動きを検知・対応するツール）、ホストファイアウォール、ディスク暗号化
    アプリケーション層入力検証・出力エスケープ、認証・認可、セッション管理、CSRF対策、CSP、セキュリティヘッダー
    データ層転送中の暗号化（TLS）、保存中の暗号化、機密項目の追加暗号化、アクセスログ
    運用・人間層セキュリティ教育、フィッシング訓練、最小権限の運用、インシデント（事故）対応計画

    ネットワークや端末の対策の詳細は ネットワークと端末の防御、監視の仕組みは セキュリティ監視とツール で扱います。

    5.1つの機能でも層を積む：ログイン機能の例

    深層防御はシステム全体の話だけではありません。ログイン機能1つ にも、次のように何重もの対策を積みます。

    1. HTTPS で通信経路を保護する（盗聴を防ぐ）
    2. CSP（ブラウザに「読み込んでよい場所」を指示する仕組み）で XSS の影響を制限する
    3. 強いパスワードポリシー（漏洩済みパスワードの禁止、12文字以上）
    4. bcrypt / Argon2 でパスワードをハッシュ化して保存する（元に戻せない形に変換）
    5. レート制限（IP・アカウント・デバイスごとに試行回数を制限）
    6. MFA（多要素認証）で、パスワードが漏れても入れないようにする
    7. セッションCookieの属性（HttpOnly、Secure、SameSite）を正しく設定する
    8. 異常検知（普段と違う国・普段と違うデバイスからのログイン）
    9. 不正ログインアラート をユーザーに通知する
    10. 監査ログ で、あとから追跡できるようにする

    ここが深層防御

    1〜3 が甘くても 4〜6 で守れる。4〜6 が破られても 8〜10 で検知できる。「守る」層と「気づく」層の両方 があることがポイントです。

    5.1 アプリの中でも「入力 → 処理 → 出力」で守る

    アプリケーションのコードの中でも、データの流れに沿って各段階で守りを置きます。

    入力時

    • 型チェック・範囲チェック
    • ホワイトリスト検証（許可したものだけ通す）
    • サイズ制限

    処理時

    • パラメータ化クエリ
    • 認可チェック（所有者かどうかも含む）
    • トランザクション

    出力時

    • エスケープ（HTML/JS/URL）
    • 機密情報のフィルタリング
    • ヘッダー設定（X-Content-Type-Options 等）

    入力検証やエスケープの具体的な書き方は、72_Web脆弱性対策 で詳しく扱います。

    6.深層防御と最小権限の関係

    深層防御と最小権限は、別の方向から被害を減らす 補い合う 関係です。

    深層防御

    そもそも 何層も突破させない。侵入される確率を下げる。

    最小権限

    侵入されたときの 1層あたりの被害 を小さくする。

    両方を組み合わせて、「侵入される確率 × 侵入されたあとの被害」 の掛け算を小さくします。リスクを「起こりやすさ × 影響の大きさ」で考える見方は リスク管理とリスクアセスメント と同じです。

    7.よくある失敗（アンチパターン）

    7.1 「多層」ではなく「多重」になっている

    深層防御で最も誤解されやすいのがここです。同じ層・同じ性質の対策 を3つ重ねても、それを破る1つの攻撃には弱いままです。

    7.2 その他の失敗

    アンチパターンなぜダメか
    「WAFを入れれば安全」WAF は1つの層にすぎない。アプリ内部の対策を怠る言い訳にはならない
    「社内ネットだから信頼」外からの攻撃にしか備えないのは古い考え方。内部からの攻撃や、乗っ取られたマシンからの 横移動（社内の別の機器へ次々と侵入を広げること）にも備える（→ ゼロトラスト）
    層を増やしすぎて運用不能層が多すぎて 誰も全体を把握できない のも問題。管理のしやすさとのバランスが必要
    最後の砦「人間」を忘れるどれだけ技術対策を積んでも、フィッシングメール1通で社員が認証情報を渡せば 台無し。教育と訓練も層の1つ

    よくある誤解：「HTTPS にしてあるから安全」

    HTTPS が守るのは 通信の途中 だけです。サーバーに届いたあとの SQLインジェクションや、認可の抜け、保存データの漏洩は防げません。「〇〇さえあれば安全」という言い方が出たら、深層防御の考え方を思い出してください。

    8.どこから手を付けるか：層の優先順位

    すべての層を一度に実装するのは無理です。投資の優先順位の目安は次の通りです。

    1. コストが低く効果が高いもの：HTTPS、セキュリティヘッダー、依存ライブラリの更新
    2. 設計を変えないと入らないもの：認証・認可・ログ（後から入れるのは大変なので早めに。→ セキュアバイデザイン）
    3. 運用で続ける必要があるもの：パッチ適用、権限の棚卸し、監視
    4. 高コストだが重要なもの：WAF、SIEM（ログを集めて分析する基盤）、SOC（セキュリティ監視の専門チーム）

    実務でのポイント

    最も攻撃される層（通常はアプリケーション層）から優先的に固めましょう。

    9.2026年の事例：被害半径で考える

    2026年の国内の漏洩事例を分析した記事では、被害の大きさは「入られたこと」そのものより、侵入後の動きが続いた時間と、届いたデータの量に比例していた と指摘されています。

    事例侵入から発覚まで
    アフラック生命15日（CPUの高負荷で発覚）
    ショップサーブ約72日
    両毛システムズ（委託元への通知）43日
    米国防総省 DMDC（海外）約9か月

    つまり、入口の防御だけでは足りず、入られたあとの層 が被害を決めます。2026年の事例を層ごとに整理すると次のようになります。

    層役割2026年に足りなかった例
    入口脆弱性を塞ぐVPN の脆弱性・ゼロデイ（→ 脆弱性管理とランサムウェア対策）
    権限1つのIDで届く範囲を絞る保守アカウントで大量アクセス（→ 最小権限）
    ネットワーク横に広がらないよう分けるフラットな構成でDBまで到達
    データ持たない・分ける・暗号化する退会者データ・免許証画像の保持（→ データ最小化）
    検知異常な大量取得に気づいて止める大量照会の監視不足（→ ログ不足・SSRF・例外処理）
    復旧バックアップから戻すランサムウェアで長期停止（→ 脆弱性管理とランサムウェア対策）

    10.現代の潮流

    ゼロトラスト

    「境界で守る」だけでは不十分、という考え方。すべてのアクセスを認証・認可・暗号化 する。深層防御の延長線上にある概念です（→ ゼロトラスト）。

    セキュアバイデザイン

    設計段階からセキュリティを織り込む。後付けではなく前提として、深層防御を 設計の一部 にする（→ セキュアバイデザイン）。

    プラットフォームセキュリティ

    層を個別に作るのではなく、クラウドやコンテナ基盤が複数の層をまとめて提供する。例：AWS の VPC + Security Group + WAF + Shield + GuardDuty。

    12.まとめ

    このページの要点

    • 深層防御は 「多層的に、性質の違う防御を重ねる」 考え方
    • 単一の対策に依存しない（WAFさえあれば、HTTPSさえあれば…は誤り）
    • 違う層 で 違う性質 の対策を組み合わせる。同じものを重ねるのは「多重」
    • 「守る」層だけでなく、入られたあとに気づく・戻す 層が被害の大きさを決める
    • 最小権限・ゼロトラストと合わせて、被害を二重三重に限定する。人間（教育・訓練）も防御層の1つ
    • 優先順位は「低コスト・高効果」「設計段階で必要なもの」から

    13.理解度チェック

    Q1. 入口に違うメーカーのWAFを3台並べました。これは深層防御として十分ですか？

    不十分です。 同じ層・同じ性質の対策を重ねる「多重」になっており、WAFをすり抜ける攻撃（例：正規ユーザーの認証情報を使った侵入）には3台とも無力です。認可・最小権限・暗号化・監視など、違う層・違う性質 の対策を組み合わせる必要があります。

    Q2. 深層防御と最小権限は、それぞれ何を小さくしますか？

    深層防御は 侵入される確率（何層も突破させない）を、最小権限は 侵入されたときの被害（1層あたりで失うもの）を小さくします。両方合わせて「確率 × 被害」の積を小さくします。

    Q3. 2026年の事例分析では、被害の大きさは何に比例していたと指摘されていますか？

    侵入後の動きが続いた時間と、届いたデータの量 です。だからこそ、入口だけでなく、権限・ネットワーク分割・データ最小化・検知・復旧といった「入られたあとの層」が重要になります。
