    40 OWASP Top 10

    安全でない設計・設定ミス・古い部品

    コードの書き方そのものではなく、「そもそもの作り方（設計）」「動かし方（設定）」「使っている部品（ライブラリ）」が原因で起きる3つのリスクをまとめて解説します。それぞれ何が起きるのか、実際のコードや設定でどこが危ないのか、どう防ぐのかを、悪い例と良い例の対比で見ていきます。

    もとにしたノート：40_OWASP_Top10/A04_安全でない設計、A05_セキュリティの設定ミス、A06_脆弱で古いコンポーネント、01_OWASP_Top10_2025の変更点

    ひとことで言うと

    家にたとえると、安全でない設計 は「設計図の段階で裏口に鍵を付け忘れた家」、設定ミス は「立派な鍵があるのに掛け忘れた家」、古いコンポーネント は「合鍵の作り方が世間に知られている古い錠前を使い続けている家」です。どれも、コードを1行ずつ丁寧に書くだけでは防げません。設計レビュー・設定の点検・部品の棚卸しと更新 という、コードの外側の仕組みで守ります。

    1.3つの項目と、2021年版・2025年版の番号

    OWASP Top 10 は、Webアプリでよく起きる危険を10個に整理したリストです（詳しくは OWASP Top 10 とは）。もとのノートは 2021年版の番号で書かれていますが、2025年版では順位や名前が変わっています。このページの3項目は次のように対応します。

    このページの項目2021年版2025年版変化
    安全でない設計（Insecure Design）A04A064位 → 6位（内容はそのまま有効）
    セキュリティの設定ミス（Security Misconfiguration）A05A025位 → 2位に上昇。クラウド・コンテナ・IaC の普及で、設定で振る舞いが決まる部分が増えた
    脆弱で古いコンポーネント（Vulnerable and Outdated Components）A06A03 に拡張「ソフトウェアサプライチェーンの不備」として範囲が広がり新設カテゴリに（→ 次のページ）

    2.安全でない設計（A04:2021 ／ A06:2025）

    2.1 どんな問題か

    安全でない設計 は 2021年版で新しく作られたカテゴリです。それまでの Top 10 は「コードのバグ」が中心でしたが、この項目は 設計段階の欠陥、つまり「仕様そのものに穴がある」状態を扱います。

    • パスワード再設定の本人確認が、生年月日だけ
    • 登録フォームに CAPTCHA（人間かどうかを確かめる画像認証など）がなく、bot（自動プログラム）で大量登録できる
    • ECサイトで、在庫数以上の注文を受け付けてしまう
    • 1人が同じクイズに何度でも挑戦できる

    これらは、プログラムが「仕様どおり」に正しく動いていても起きます。どれだけコードを完璧に書いても、設計が甘いと安全ではない というのがこの項目の教えです。

    2.2 「実装の欠陥」と「設計の欠陥」の違い

    同じ「脆弱性」でも、原因がどこにあるかで見つけ方も直し方も変わります。

    実装の欠陥（Bug：バグ）設計の欠陥（Flaw：設計上の穴）
    例SQLインジェクション、バッファオーバーフローCAPTCHA 未実装、本人確認の甘さ
    見つけ方コードレビュー、SAST（ソースコードを自動で検査するツール）脅威モデリング、設計レビュー
    直し方コードを直す仕様・処理の流れから見直す
    直すコスト比較的低い高い（作り直しに近い）

    注意

    設計の欠陥は、コードをいくら直しても消えません。 「生年月日で本人確認する」という仕様のままでは、そのコードにバグが1つもなくても他人がパスワードを変えられます。仕様のレベルで直す必要があり、後になるほど直すコストが上がります。だからこそ設計段階で考えます（セキュアバイデザイン）。

    2.3 よくある「安全でない設計」

    ① 認証・本人確認が弱い

    • パスワードリセットの質問が「母親の旧姓」だけ（SNSで調べられる）
    • 多要素認証がない
    • ログイン試行回数の制限がない → 総当たり攻撃し放題

    ② 業務ロジックの悪用（Business Logic Flaw）

    コード上はバグではないが、仕様の穴を突く 攻撃。

    • クーポンを複数回適用できる
    • 注文確定後に価格を書き換えて送信できる
    • ポイント付与の条件を何度も満たせる

    ③ レート制限の欠如

    レート制限＝「一定時間に受け付ける回数の上限」。

    • 1秒間に1万回 SMS 認証コードを送れる → 通信料金が爆発、サービス停止
    • 1つの IP アドレスから無制限にアカウントを作れる

    ④ 安全な初期設定になっていない

    • 新規登録時、プロフィールが最初から「公開」
    • 権限設定の初期値が「全員書き込み可」

    ⑤ 脅威モデリングをしていない

    そもそも「どんな攻撃があり得るか」を考えていなければ、対策のしようがありません。上の①〜④の多くは、ここが抜けていることから生まれます。

    2.4 例：パスワードリセットの流れ

    同じ「パスワードを忘れた人のための機能」でも、設計しだいで安全性がまったく変わります。

    ✕ 危険な設計 
    1. ユーザーがメールアドレスを入力
2. 生年月日を聞く
3. 正解ならパスワードを変更できる
    • 生年月日は SNS などで調べられる
    • 試行回数に制限がない（365日×数十年分を試せば当たる）
    • 他人のメールアドレスを入れれば、そのアカウントを乗っ取れる
    ○ 安全な設計 
    1. ユーザーがメールアドレスを入力
2. 「もしそのアドレスが登録されていれば、メールを送信しました」と常に同じ応答（列挙攻撃の防止）
3. メールに、15分で失効する使い切りのトークン付きURLを送信
4. URLをクリックしたら新パスワードを設定
5. トークンは1回使ったら失効、同時に全セッションを無効化
6. 変更完了を本人のメールに通知
    改善ポイント何を防ぐか
    応答を常に同じにする列挙攻撃（応答の違いから「このアドレスは登録済み」と1件ずつ調べ上げる攻撃）
    トークンに有効期限・使い切りメールが後から盗み見られたり、URLが漏れたりしても使えない
    全セッションを無効化すでに乗っ取られていた場合でも、攻撃者を追い出せる
    変更を本人に通知本人が気づいて、すぐに対処できる

    2.5 設計段階で考えるべき4つのこと

    1. 脅威モデリング：実装の前に「誰が」「どうやって」「何を狙うか」を洗い出す。代表的な手法は STRIDE（脅威を6種類に分類）、アタックツリー（攻撃経路を木の形で描く）、データフロー図＋信頼境界。
    2. セキュアバイデザイン ／ セキュア・バイ・デフォルト：最初から安全な状態で動く。危険な機能はデフォルトOFF。権限は必要最小限で付与する（最小権限）。
    3. 多層防御（Defense in Depth）：1つの防御が破られても、次の層で止まるようにする（深層防御）。たとえばログイン画面なら、レート制限（1層目）→ CAPTCHA（2層目）→ 多要素認証（3層目）→ 異常検知アラート（4層目）。
    4. 悪用ケース（Misuse Case）の検討：正常な使い方（ユースケース）だけでなく、「悪意のある人がどう悪用するか」のシナリオも書き出す。
      ユースケース：「ユーザーはポイントで買い物ができる」
      悪用ケース：「攻撃者は API を並列で叩き、ポイントを二重に使う」

    2.6 業務ロジックの穴を防ぐ

    ① 同時アクセスに耐える（トランザクションと排他制御）

    上の悪用ケース「ポイントの二重使用」は、レースコンディション（複数の処理が同時に走ったとき、順番しだいで結果がおかしくなる不具合）で起きます。「残高を読む」と「残高を書き換える」の間に、別のリクエストが割り込めてしまうのが原因です。

    ✕ 危険：読んでから書く（間に割り込める） 
    async function usePoints(userId, amount) {
  const user = await db.getUser(userId);
  if (user.points >= amount) {
    await db.updatePoints(userId, user.points - amount);
  }
}
// 並列で叩かれると、両方とも if を通過して残高以上に使えてしまう
    ○ 安全：判定と更新を1つの命令でアトミックに行う 
    async function usePoints(userId, amount) {
  const result = await db.query(
    'UPDATE users SET points = points - ? WHERE id = ? AND points >= ?',
    [amount, userId, amount]
  );
  if (result.affectedRows === 0) throw new Error('Insufficient points');
}

    アトミック とは「途中で割り込まれない、ひとかたまりの操作」という意味です。「残高が足りていれば減らす」を DB の1命令にまとめると、同時に来ても片方しか成功しません。更新件数（affectedRows）が 0 なら残高不足と判断します。

    ② サーバー側で必ず再検証する

    画面（フロントエンド）で「このクーポンは1回のみ」と制御していても、攻撃者はブラウザを使わずに API を直接叩けます。価格計算・在庫チェック・権限チェックは、必ずサーバーで最終確認 します。画面のチェックは「使いやすさのため」、サーバーのチェックは「安全のため」と考えます。

    ③ レート制限をかける

    ✕ 制限なし：何回でもログインを試せる 
    app.post('/api/login', loginHandler);
    ○ 1分間に5回まで（express-rate-limit の例） 
    import rateLimit from 'express-rate-limit';
app.post('/api/login', rateLimit({ windowMs: 60_000, max: 5 }), loginHandler);
    設計フェーズのチェックリスト
    • 脅威モデリングを実施したか？
    • 悪用ケースを洗い出したか？
    • 認証・本人確認は十分に強いか？（多要素、レート制限、試行制限）
    • 業務ロジックが、悪意ある並列リクエストや順序の改ざんに耐えるか？
    • デフォルト設定は最も安全な状態か？
    • セキュリティを破られた場合に、検知・対応できる仕組みはあるか？
    • ユーザー入力は、サーバー側で再検証しているか？

    3.セキュリティの設定ミス（A05:2021 ／ A02:2025）

    3.1 どんな問題か

    設定ミス とは、ソフトウェア・クラウド・サーバーの 設定が不適切なまま 運用されている状態です。コードは完璧でも、設定1つですべてが台無しになります。銀行にたとえれば、金庫は頑丈なのに「扉を開けっ放しにしていた」ようなものです。

    • S3 バケット（AWS のファイル置き場）が「全公開」になっていて、顧客情報が漏洩
    • 管理画面のパスワードが初期値の admin/admin のまま
    • エラー画面にスタックトレース（エラーが起きたプログラムの場所の一覧）と DB 接続情報が表示される
    • 開発用のデバッグ用 URL が本番に残っている
    • テスト用ユーザーなどのサンプルデータが本番 DB に残っている

    どれも コードではなく運用の問題 で、しかも頻度が非常に高いのが特徴です。2025年版では 5位から 2位 に上がり、テストされたアプリの 3.00% で該当する弱点が見つかっています。

    3.2 よくある設定ミスのパターン

    パターン具体例
    ① 初期パスワードの放置DB の root / (空)・admin / admin、管理画面の admin / password、IoT 機器の admin / 1234。bot が世界中をスキャンして、初期パスワードで侵入を試みている
    ② 情報を出しすぎるエラー画面DB サーバーの IP やパスワードがエラー画面に丸見えになる（下の例）
    ③ 不要な機能・ポート・アカウントサンプルアプリがそのまま配置、使っていないポート（21番/FTP、23番/Telnet）が開いている、退職者のアカウントが残っている
    ④ セキュリティヘッダーがないブラウザに「このページをこう扱って」と指示するヘッダー（Content-Security-Policy など）が未設定
    ⑤ クラウドの公開設定ミスS3・GCS・Azure Blob が認証なしで読める、DB がインターネットに直接公開（0.0.0.0/0 を許可＝全世界から接続可）、Elasticsearch / MongoDB が認証なしで公開
    ⑥ CORS の設定ミス他サイトからのアクセスを何でも許可してしまう（下の例）
    ⑦ チュートリアル設定の残存Jenkins のセットアップウィザードを飛ばしたまま公開、Kubernetes ダッシュボードが認証なしで公開
    ✕ 本番で出してはいけないエラー画面の例 
    [ERROR] 500 Internal Server Error
  at users.controller.js:42
  DB connection failed: postgres://admin:mySecretPass@10.0.0.5:5432/prod
  Stack trace: ...

    開発中は便利ですが、本番では DB のユーザー名・パスワード・内部 IP が攻撃者にそのまま渡ります。

    3.3 悪い例と良い例

    例1：本番でデバッグモードが有効

    ✕ 危険（Django の settings.py） 
    DEBUG = True  # ← 本番ではTrueにしない！
ALLOWED_HOSTS = ['*']

    DEBUG=True だと、エラー時にソースコード・設定・環境変数がブラウザに表示されます。

    ○ 安全：環境変数で制御し、既定は False 
    import os
DEBUG = os.environ.get('DEBUG', 'False') == 'True'
ALLOWED_HOSTS = ['example.com', 'www.example.com']

    環境変数が設定されていなければ False になる、つまり 設定を忘れたら安全側 になる書き方です。

    例2：S3 バケットが全公開

    ✕ 危険：誰でも（"*"）読める 
    {
  "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-bucket/*"
}
    ○ 安全：認証必須にする
    • バケットポリシーで、特定の IAM ロール（AWS 上の権限の単位）やオリジンだけを許可
    • Block Public Access（公開を一括で禁止する設定）をアカウント単位で有効化
    • CloudFront + OAI（Origin Access Identity）経由で配信し、バケットを直接公開しない

    例3：生のエラーをクライアントに返す

    ✕ 危険：スタックトレースが丸見え 
    app.use((err, req, res, next) => {
  res.status(500).json({ error: err.stack });
});
    ○ 安全：詳細はサーバーのログだけに、利用者には汎用メッセージ 
    app.use((err, req, res, next) => {
  logger.error(err); // サーバーログにだけ詳細
  res.status(500).json({ error: 'Internal Server Error' }); // クライアントには汎用
});

    この考え方は 2025年版の新項目「例外的状況の不適切な処理」でさらに詳しく扱います（→ ログ不足・SSRF・例外処理）。

    例4：セキュリティヘッダーがない

    ✕ 危険：デフォルトのまま 
    const app = express();
// ヘッダー設定なし → XSS・クリックジャッキングなどに弱い
    ○ 安全：helmet で基本的なヘッダーを自動設定 
    import helmet from 'helmet';
app.use(helmet());

    例5：CORS の設定ミス

    CORS（オリジン間リソース共有）は、「別のサイトから、このサーバーの API を呼んでよいか」をブラウザに伝える仕組みです。

    ✕ 危険：すべてのサイトから、ログイン情報付きで呼べる 
    app.use(cors({ origin: '*', credentials: true }));
    ○ 安全：許可するサイトを明示する 
    app.use(cors({ origin: ['https://app.example.com'], credentials: true }));

    credentials: true（Cookie などの認証情報を送ってよい）と origin: '*'（どのサイトからでも）の組み合わせは最悪です。許可するオリジンは名前で列挙します。

    3.4 最低限設定すべきセキュリティヘッダー

    ヘッダー役割推奨値の例
    Strict-Transport-SecurityHTTPS を強制するmax-age=31536000; includeSubDomains
    Content-Security-Policy読み込めるスクリプトの出どころを制限し、XSS の被害を抑えるdefault-src 'self'
    X-Content-Type-Optionsブラウザがファイルの種類を勝手に推測する（MIME sniffing）のを防ぐnosniff
    X-Frame-Options他サイトに埋め込まれて騙しクリックさせられる（クリックジャッキング）のを防ぐ。frame-ancestors でも可DENY
    Referrer-Policyリンク先に送る「どこから来たか」の情報を制限するstrict-origin-when-cross-origin
    Permissions-Policyカメラ・位置情報などブラウザ機能の利用を制限する用途に応じて設定

    3.5 防御の原則

    1. 安全な基準（ベースライン）を作る：ハードニング（不要な機能を外し、設定を固めること）済みの構成テンプレートを用意する。Terraform・CloudFormation などの IaC（インフラをコードで定義する仕組み）で構成をそろえ、新しい環境はいつも同じ基準から作る。
    2. 本番と開発を分ける：デバッグON・認証の簡略化など開発用の設定を本番に持ち込まない。.env.production と .env.development を分け、開発用エンドポイントを本番に含めない。
    3. 不要なものを削除する（攻撃面の最小化）：使わない機能は無効化・削除、使わないポートは閉じる、退職者・不要アカウントはすぐ削除、サンプルコードやテストデータを本番に残さない。
    4. 自動でスキャンする：構成チェック（CIS Benchmark、AWS Security Hub、GCP Security Command Center）、クラウドの公開チェック（AWS Config、Prowler、Scout Suite）、ヘッダーチェック（securityheaders.com）。
    5. 定期的に見直す：設定は一度決めて終わりではない。退職者、使われなくなった機能、新しく見つかった脆弱性への対応を定期的にレビューする。

    実務でのポイント

    基本姿勢は 「デフォルト設定を信じない」 こと。製品の初期設定は「すぐ動くこと」を優先していて、安全とは限りません。2025年版で設定ミスが2位に上がったことを受け、クラウド設定・IaC のレビューを優先 するのがおすすめです。手作業の設定は忘れや抜けが起きるので、IaC と自動スキャンで人為ミスを減らします。

    設定ミスのチェックリスト

    アプリケーション

    • DEBUG / 詳細表示モードが本番で無効か？
    • エラー画面から内部情報が漏れていないか？
    • セキュリティヘッダー（helmet 相当）を設定しているか？
    • 初期パスワードを変更したか？
    • 不要な管理エンドポイントを削除したか？

    インフラ・クラウド

    • S3 / GCS / Azure の公開設定を確認したか？
    • DB がインターネットに直接公開されていないか？
    • 不要なポートが開いていないか？
    • 退職者・テストアカウントを削除したか？
    • CORS 設定は適切か？（origin: '*' + credentials: true は NG）

    プロセス

    • 構成はコード化（IaC）されているか？
    • 本番デプロイ前にセキュリティスキャンを実施しているか？
    • セキュリティの基準は文書化されているか？

    4.脆弱で古いコンポーネント（A06:2021 ／ A03:2025 に拡張）

    4.1 どんな問題か

    今のアプリは、自分で書いたコードよりも外部ライブラリ（依存関係）のほうが圧倒的に多い のが普通です。npm・pip・Maven などで取り込むオープンソースの部品（コンポーネント）が、アプリの大部分を占めます。

    その部品に 既知の脆弱性（すでに世間に公表されている弱点）があるのに放置していると、攻撃者はそこを狙ってきます。自分のコードが無傷でも、使っていただけで被害に遭う のがこの項目の怖さです。

    事件何が起きたか
    Apache Struts（2017年）Struts の脆弱性を突かれ、Equifax から1.4億人の個人情報が流出
    Log4Shell（2021年）Java のログ部品 Log4j の脆弱性で、世界中の Java アプリが攻撃対象に
    Heartbleed（2014年）OpenSSL の脆弱性で、暗号化した通信の内容を盗まれる
    npm パッケージの乗っ取りライブラリが攻撃者に乗っ取られ、悪意あるコードが正規の経路で配られる（サプライチェーン攻撃 → 次のページ）

    4.2 なぜ起きるのか

    ① 依存関係が何層にもなり、全体を把握しきれない

    Node.js の平均的なプロジェクトでは、依存関係のツリーは数百〜数千パッケージになります。そのどこか1つに脆弱性があれば影響を受けます。

    ② アップデートが怖い

    「動いているものに触りたくない」「互換性が壊れるのが怖い」という心理で、古いバージョンが使われ続けます。

    ③ 公開された脆弱性情報は攻撃者にも見える

    公表された脆弱性は世界中の攻撃者も知ります。公開から数日で PoC（脆弱性を実際に突けることを示す攻撃コードの例）が出回ることも多く、「パッチが出たのに当てていない期間」が狙われます。

    4.3 押さえておきたい用語

    CVE（Common Vulnerabilities and Exposures）

    個々の脆弱性に付けられる 世界共通の ID。例：CVE-2021-44228（Log4Shell）。

    SBOM（Software Bill of Materials）

    アプリに含まれる 全部品の一覧。食品の「原材料表示」のようなもの。米国では大統領令で政府調達に必須化され、業界標準になりつつあります。

    SCA（Software Composition Analysis）

    依存関係をスキャンして、脆弱性のある部品を見つけるツールの種類。

    サプライチェーン攻撃

    ライブラリや配布の仕組みを汚染し、正規の配布経路を通じて マルウェアを広める攻撃。

    CVSS（Common Vulnerability Scoring System）は、脆弱性の 深刻度を 0.0〜10.0 で表すスコア です（セキュリティの専門用語 も参照）。

    スコア深刻度
    0.0なし
    0.1〜3.9低（Low）
    4.0〜6.9中（Medium）
    7.0〜8.9高（High）
    9.0〜10.0緊急（Critical）

    4.4 よくあるリスクパターン

    • 古いメジャーバージョンを使い続けている：Node.js 10 / Python 2 / PHP 5 など サポートが終了 したランタイム（実行環境）。新しい脆弱性が見つかっても修正が出ない。
    • 直接依存は更新しても、間接依存が古い：package.json に書いていない依存の依存にも脆弱性はある。
    • フォーク版や保守されていないパッケージ：メンテナーがいなくなったもの、小規模で使われていないもの、最終更新が何年も前のもの。
    • 使っていないのに入れっぱなし：「試したが使わなかった」パッケージが残っていて、攻撃面（攻撃者が狙える場所）を無駄に広げている。

    4.5 悪い例と良い例

    依存を放置するか、定期的に監査するか

    ✕ 危険：古いバージョンを放置 
    {
  "dependencies": {
    "express": "^4.16.0",
    "lodash": "^4.17.10"  // ← Prototype Pollution の脆弱性がある古いバージョン
  }
}
    ○ 安全：定期的に監査コマンドを実行（CI にも組み込む） 
    # npm
npm audit
npm audit fix

# yarn
yarn audit

# pip
pip-audit

# Go
govulncheck ./...

    手作業の更新か、自動化か

    ○ Dependabot で更新の PR を自動作成（Renovate でも可） 
    # .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"

    新しいバージョンが出るたびに自動でプルリクエストが作られるので、「気づいたら何年も古い」を防げます。

    部品表（SBOM）を作る

    ○ Syft で SBOM を作り、Grype で脆弱性をスキャン 
    # Syft でSBOMを生成
syft packages dir:. -o spdx-json > sbom.json

# Grype で脆弱性スキャン
grype sbom:sbom.json

    コンテナのベースイメージ

    ✕ あいまいなタグ（中身が分からず、古くなりがち） 
    FROM node:latest
    ○ バージョンを明示し、定期的に更新 
    FROM node:20.11-alpine3.19

    4.6 防御の進め方

    1. インベントリ（在庫表）を作る：直接依存＋間接依存をすべてリスト化し、バージョン・ライセンス・出どころ（npm か、フォーク版か）を記録。SBOM ツールで自動化する。
    2. 脆弱性の監視を自動化する：GitHub Dependabot（無料）、Snyk・Mend・Black Duck（商用）、OWASP Dependency-Check・Trivy（OSS）。CI/CD に組み込み、脆弱性のある PR はマージ不可 にする運用が理想。
    3. 使わないものは削除する：npx depcheck で使われていないパッケージを見つけ、npm uninstall <package> で外す。
    4. 信頼できる場所からだけ取得する：公式レジストリ（npm、PyPI、Maven Central）を使い、社内プロキシ（Nexus、Artifactory）経由で監査を一元化。npm install --ignore-scripts でインストール時のスクリプト実行を止める。
    5. バージョンを固定する：ロックファイル（package-lock.json・Pipfile.lock・go.sum）をコミットし、本番ビルドは npm ci（ロックファイルに厳密に従う）で行う。
    6. ランタイムも更新する：OS・Node や Python などのランタイム・コンテナのベースイメージも定期的に更新する。

    4.7 Log4Shell から学ぶ教訓

    2021年12月、Java の非常に有名なログ部品 Log4j に致命的な脆弱性（CVE-2021-44228）が見つかりました。

    • CVSS 10.0（最高）
    • 認証なしで リモートコード実行（外部から好きなプログラムを動かされる）
    • Java 製のほぼすべての業務アプリが影響を受けた
    • 間接依存のさらに奥に潜んでいるケースが多数

    教訓

    • SBOM がないと、自分が影響を受けているかすら分からない
    • 影響の把握と緊急パッチの体制を、日頃から準備しておく必要がある
    • 「有名で枯れている」≠「安全」

    4.8 2026年の事例から

    2026年は 脆弱性の悪用が情報漏洩の最大の入口 になりました。Verizon DBIR 2026 では、侵入の入口の 31% が脆弱性の悪用で、盗まれた認証情報を初めて上回っています。

    事例コンポーネントの問題
    KDDI ISP 向けメール基盤システムの一部に組み込んだ 第三者製ソフトのゼロデイ脆弱性（修正がまだ存在しない脆弱性）。5/16 から被害、6/17 に把握。メールアドレス 1,223万件・パスワード 762万件が漏えい
    タイムズカーサポートが終わった Java フレームワーク Seasar2 を使っていたという指摘がある（因果関係は未確認）
    VPN・ファイル転送製品国内ランサムウェアの入口の約5割が VPN 機器（警察庁、2026年上半期）
    • ライブラリだけでなく、組み込んだ製品・ミドルウェア・境界機器（VPN など社内外の境目にある機器）も インベントリの対象にする
    • EOL（サポート終了）の技術を洗い出す。Seasar2 のように国内で広く使われ、今は保守されていないものは要注意
    • 優先度は CVSS だけでなく、CISA KEV（実際に悪用されたことが確認された脆弱性のリスト）を重視する
    • ゼロデイはパッチでは防げないので、検知（ログとモニタリング）と被害の限定（データ最小化）も組み合わせる

    境界機器のパッチ運用は 脆弱性管理とランサムウェア対策、2026年の事例全体は サプライチェーン攻撃と2026年の事例 で扱います。

    古いコンポーネント対策のチェックリスト
    • 全依存関係（直接・間接）を一覧化しているか？
    • npm audit / pip-audit などを CI で実行しているか？
    • Dependabot / Renovate で自動更新を回しているか？
    • ロックファイルをコミットしているか？
    • OS・ランタイム・ベースイメージも更新しているか？
    • 使っていない依存を削除しているか？
    • サポート終了したランタイム（Node 10、Python 2 など）を使っていないか？
    • SBOM を生成・保管しているか？
    • 脆弱性発見時の対応フロー（誰が検知し、誰がパッチを当てるか）が決まっているか？

    5.よくある誤解

    「テストもコードレビューも通ったから、安全な設計だ」

    不十分です。 テストやコードレビューは「仕様どおりに作れているか」を確かめるもので、「仕様そのものに穴がないか」は確かめません。設計の欠陥は、脅威モデリングや悪用ケースの検討、設計レビューで見つけます。

    「画面でボタンを押せなくしているから、二重送信は起きない」

    誤りです。 攻撃者はブラウザを使わず API を直接、しかも並列で叩けます。回数制限・価格・在庫・権限は必ずサーバー側で、同時アクセスにも耐える形（アトミックな更新）で確認します。

    「クラウドの初期設定なら安全なはず」

    限りません。 初期設定は「すぐ使えること」を優先している場合があり、利用者が公開設定を変えてしまうこともあります。Block Public Access のような一括の安全装置を有効にし、AWS Config・Prowler などで公開状態を自動チェックします。

    「npm audit で何も出なければ、依存関係は安全」

    言い切れません。 監査ツールが見つけられるのは すでに公表された 脆弱性だけです。ゼロデイや、保守が止まった部品、乗っ取られたパッケージは検出できないことがあります。インベントリ（SBOM）・不要な依存の削除・検知の仕組みを組み合わせます。

    「常に最新版に上げておけば安全」

    半分正解です。 古いまま放置するのは危険ですが、公開直後の新バージョンが乗っ取られたものだった、という攻撃もあります。ロックファイルで固定し、更新は Dependabot などの PR として 意図して 取り込みます。詳しくは サプライチェーンと整合性の不備 で扱います。

    6.まとめ

    このページの要点

    • 安全でない設計（2021 A04 ／ 2025 A06）は「コードではなく設計の欠陥」。コードを直しても消えないので、脅威モデリング・悪用ケース・多層防御 を設計段階で組み込む
    • 業務ロジックは 並列・順序の改ざん・二重実行 に耐えるようにし、価格・在庫・権限は サーバー側で最終確認
    • 設定ミス（2021 A05 ／ 2025 A02）は運用の問題で頻度が高い。デフォルトを信じず、本番と開発を分け、不要なものを削除する
    • IaC と自動スキャンで設定の人為ミスを減らし、セキュリティヘッダーやエラー表示も点検する
    • 古いコンポーネント（2021 A06 ／ 2025 A03 に拡張）は、インベントリ（SBOM）→ 監視 → 自動更新 のサイクルで守る
    • Log4Shell のような事件は再発する前提で、すぐに影響を調べてパッチを当てられる体制 を用意しておく

    7.理解度チェック

    Q1. 「パスワードリセットの本人確認が生年月日だけ」。これはバグ（実装の欠陥）と設計の欠陥のどちらで、どう直すべき？

    設計の欠陥 です。コードが仕様どおり正しく動いていても、生年月日は調べられるため他人が通過できます。直すにはコードの修正ではなく 流れそのものを作り直す 必要があります。たとえば「常に同じ応答を返す」「15分で失効する使い切りトークンをメールで送る」「変更後に全セッションを無効化し、本人に通知する」という設計にします。

    Q2. Express で cors({ origin: '*', credentials: true }) と書かれていた。何が問題で、どう直す？

    どのサイトからでも、ログイン情報（Cookie など）付きで API を呼べる 組み合わせになっており、最悪の設定です。origin に許可するサイト（例：['https://app.example.com']）を明示して直します。これは「設定ミス」（2021 A05 ／ 2025 A02）の典型例です。

    Q3. Log4Shell のとき、「自社が影響を受けているか分からない」組織が多かった。日頃から何を用意しておけば良かった？

    SBOM（ソフトウェア部品表） です。直接依存だけでなく間接依存まで含めた部品の一覧があれば、「Log4j のどのバージョンを、どのシステムが使っているか」をすぐに検索できます。あわせて、npm audit などの自動監視と、誰が検知し誰がパッチを当てるかの対応フローも決めておきます。
