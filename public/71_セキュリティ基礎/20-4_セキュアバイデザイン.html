    20 設計原則

    セキュアバイデザイン（Secure by Design）

    セキュリティを「完成してから付け足すもの」ではなく、「最初から仕様に含めるもの」として扱う考え方です。なぜ設計段階でなければならないのか、半世紀前から受け継がれる10の設計原則、初期設定を安全にする「セキュア・バイ・デフォルト」、シフトレフトと DevSecOps による開発プロセスへの組み込み、設計時に自問すべき質問までを解説します。

    もとにしたノート：20_設計原則/04_セキュアバイデザイン

    ひとことで言うと

    「セキュリティは"後付け"ではなく"仕様"」。家を建ててから壁に穴を開けて配線するより、設計図の段階で配線を決めておくほうが安く確実です。セキュリティも同じで、設計の段階で組み込み、さらに 初期設定のままで安全（セキュア・バイ・デフォルト）な状態で提供します。

    1.セキュアバイデザインとは

    セキュアバイデザイン（Secure by Design）とは、

    設計段階からセキュリティを組み込む

    という開発の考え方です。後からセキュリティを追加するのではなく、最初から安全な設計を前提にします。

    似た言葉に セキュア・バイ・デフォルト（Secure by Default：初期設定が安全）があり、両者はセットで使われます。

    セキュアバイデザイン

    作り方 の話。設計の段階で脅威を考え、安全な仕組みを組み込む。家でいえば、設計図の段階で耐震構造や鍵の位置を決めておくこと。

    セキュア・バイ・デフォルト

    届け方 の話。利用者が何も設定しなくても安全な状態で提供する。家でいえば、引き渡しの時点で鍵がかかっていること。

    2.なぜ「設計段階で」必要なのか

    2.1 後から直すほど高くつく

    ソフトウェア開発では、問題は見つかるのが遅いほど、直すコストが大きく膨らむ と言われます。ノートでは、よく引用される IBM System Science Institute のデータとして次の目安を挙げています。

    見つかったタイミング修正コスト（相対値）
    設計段階1
    コーディング段階5〜6倍
    テスト段階10倍
    本番リリース後30〜100倍

    正確な倍率は状況によって変わりますが、「遅く見つかるほど高くつく」という傾向は広く共有されています。セキュリティの欠陥も同じで、設計の欠陥はコードで後から補ってもほとんど直らず、作り直し になりがちです。

    2.2 「設計の穴」はコードでは防げない

    OWASP Top 10 の A04「安全でない設計」 が強調しているように、設計そのものに穴があると、コードをいくらきれいに書いても防げません（→ 安全でない設計・設定ミス・古い部品）。

    • パスワードリセットの本人確認が弱い：コードにバグが1つもなくても、仕組みとして乗っ取られてしまう
    • 業務ロジックでクーポンやポイントを二重に使える：これはコードのバグではなく、仕様の問題

    たとえるなら

    銀行の窓口で「電話で名前と生年月日を言えば、誰でも暗証番号を再設定できる」という ルール になっていたら、窓口の係員がどれだけ正確に仕事をしても、なりすましは防げません。直すべきは係員の手際（コード）ではなく、ルール（設計）です。

    2.3 セキュリティを「機能」として最初から定義する

    「ログイン機能を作る」ではなく、「ログイン + MFA + レート制限 + 監査ログ を作る」 と最初から要件に書きます。こうすれば、後付けでの漏れがなくなります。

    ✕ 後付けになる要件 
    要件：ログイン機能を作る
（セキュリティはリリース前のテストで見る）
    ○ 最初から仕様に含めた要件 
    要件：ログイン機能を作る
  - MFA に対応する
  - 同一アカウント・同一IPへのレート制限
  - ログイン成功・失敗を監査ログに残す（パスワードは記録しない）

    3.CISA が示す3つの原則

    米国の CISA（Cybersecurity and Infrastructure Security Agency：米国のサイバーセキュリティ・社会インフラ防護の政府機関）は、2023年にセキュアバイデザインに関するガイダンスを公表しました。主な原則は次の3つです。

    1. 製造者（開発者）が責任を負う：「利用者が設定を頑張って安全にする」のではなく、開発者側が安全な状態で提供する
    2. 透明性を保つ：脆弱性の情報、パッチの提供状況、サポート終了の予定などを 積極的に公開 する
    3. セキュア・バイ・デフォルトを徹底する：初期状態でセキュリティ機能は ON、危険な機能は OFF（必要な人が明示的に有効にする）。デフォルトパスワードを廃止し、強いパスワードを求める

    4.古典的な10の設計原則（Saltzer と Schroeder）

    1975年に Saltzer と Schroeder が論文で示した設計原則は、半世紀たった今でも有効です。最小権限 もこの中の1つです。

    #原則意味身近なたとえ・例
    1機構の経済性
    Economy of Mechanism    		設計はシンプルに。複雑なセキュリティ機構はバグを生む複雑すぎる鍵は、かけ忘れや故障の元
    2フェイルセーフなデフォルト
    Fail-safe Defaults    		デフォルトは 拒否。許可は明示的に名簿に載っている人だけ入れる（下のコード例）
    3完全な仲介
    Complete Mediation    		すべての アクセスを毎回チェックする。チェック結果を使い回さない（使い回すなら失効を慎重に管理）一度見せた入館証で、その後ずっと素通りにしない
    4オープンデザイン
    Open Design    		仕組みを公開しても安全であるべき。「隠しているから安全」（security through obscurity）は脆い錠前の構造が知られていても、鍵がなければ開かない
    5特権の分離
    Separation of Privilege    		重要な操作には 複数の条件 を求めるMFA、承認フロー、分割した鍵（金庫を2人の鍵でしか開けられない）
    6最小権限
    Least Privilege    		必要最小限の権限だけを与える→ 最小権限とデータ最小化
    7共通機構の最小化
    Least Common Mechanism    		利用者の間で共有する仕組みを最小にする。共有部分は攻撃の通り道になる全住人共用の1本の合鍵は、1人が落とすと全員が困る
    8心理的受容性
    Psychological Acceptability    		使いにくい対策は回避されて無意味になる。使いやすい安全 を目指す面倒すぎるパスワード規則 → 付箋に書いて貼られる
    9作業係数
    Work Factor    		攻撃にかかるコストを、守る資産の価値より大きくする中身より高くつく金庫破りは割に合わない
    10侵害の記録
    Compromise Recording    		侵害されたときに ログで追跡できる ようにする（防げなくても、気づける）防犯カメラの録画

    4.1 フェイルセーフなデフォルトをコードで見る

    2つ目の原則は、コードの書き方に直結します。「ダメなものを列挙して弾く」のではなく、「良いものだけを通す」 書き方にします。

    ✕ 悪い：デフォルトで許可 
    if is_blocked(user): return deny()
return allow()  # 例外的なケースを見落とすと悪用される
    ○ 良い：デフォルトで拒否 
    if is_allowed(user): return allow()
return deny()  # 知らない状態は安全側に倒す

    5.セキュア・バイ・デフォルトの例

    ✕ よくある悪い例

    • データベースの初期パスワードが admin / admin
    • ルーターが admin / 1234 のまま出荷
    • 新しく作った保存場所（バケット）が、最初から誰でも見られる
    • メッセージアプリの通信暗号化が、設定画面でONにしないと有効にならない

    ○ 良い例

    • Bitwarden などのパスワードマネージャー：強いマスターパスワードが必須
    • Signal：すべてのメッセージが最初からエンドツーエンド暗号化（送り手と受け手以外は読めない）
    • AWS S3（現在）：Block Public Access（公開をまとめて禁止する設定）を有効にするのが推奨
    • iOS：最初からディスク全体が暗号化され、アプリはサンドボックス（隔離された区画）で動く

    よくある誤解：「設定項目を用意したから、安全にするのは利用者の責任」

    多くの利用者は初期設定のまま使います。危険な初期設定で出荷すれば、その危険はそのまま世の中に広がります。CISA の原則どおり、安全にする責任は作る側にあります。設定ミスの問題は 安全でない設計・設定ミス・古い部品 でも扱います。

    6.開発プロセスに組み込む

    6.1 シフトレフト

    開発の流れを左から右へ「計画 → 設計 → 実装 → テスト → 運用」と並べたとき、セキュリティの取り組みを より早い段階（左側）へ移す ことを シフトレフト（Shift Left）と呼びます。従来はテスト以降で対応していたものを、計画・設計の段階から始めます。

    6.2 セキュアSDLC：各段階で何をするか

    SDLC（Software Development Life Cycle）はソフトウェア開発の一連の流れのこと。その各段階にセキュリティの活動を組み込んだものを セキュアSDLC と呼びます。

    フェーズセキュリティの活動
    要件定義悪用ケース（攻撃者ならこの機能をどう悪用するか）の洗い出し、セキュリティ要件の定義
    設計脅威モデリング、アーキテクチャレビュー（→ 脅威モデリングとデータフロー図）
    実装セキュアコーディング、コードレビュー
    ビルドSAST（ソースコードを解析して弱点を探す）、SCA（使っているライブラリの既知の脆弱性を調べる）、シークレットスキャン（パスワードや鍵の混入を探す）
    テストDAST（動いているアプリに外から攻撃を試す）、ペネトレーションテスト（専門家による侵入テスト）
    デプロイIaC スキャン（インフラ設定コードの検査）、コンテナスキャン
    運用WAF、監視、インシデント対応
    改善ポストモーテム（事故の振り返り）、教訓の反映

    6.3 DevSecOps：パイプラインで自動チェック

    DevSecOps は、開発（Dev）と運用（Ops）の間にセキュリティ（Sec）を組み込み、CI/CD パイプライン（テストやデプロイを自動で行う流れ）に 自動のセキュリティチェック を入れる考え方です。

    例：GitHub Actions に組み込んだチェック 
    - name: SAST
  uses: github/codeql-action/analyze@v3

- name: Dependency scan
  run: npm audit --audit-level=high

- name: Secret scan
  uses: trufflesecurity/trufflehog@main

- name: Container scan
  run: trivy image myapp:latest

    人が毎回思い出さなくても、コードを変更するたびに機械が確認してくれるのがポイントです。ツールの詳細は セキュリティ監視とツール も参照してください。

    7.設計するときに自問すべきこと

    新しい機能を設計するときは、次の質問に答えられるか確認します。答えられない質問が、そのまま設計の穴の候補です。

    入力について

    • どこから入力が来るか？
    • 信頼できるか？ できないならどう検証するか？
    • サイズ・型・形式の制限は？
    • 許可リスト（ホワイトリスト）型の検証か？

    認証・認可について

    • 誰がアクセスできる機能か？
    • 所有者かどうかのチェックは？
    • 特権操作に追加の認証を求めるか？
    • セッションのタイムアウトは？

    データについて

    • どんな機密度のデータを扱うか？
    • 暗号化は？（転送中・保存中）
    • ログに機密情報が出ないか？
    • 保管期間と削除のルールは？（→ データ最小化）

    エラーと例外

    • エラー時、どこに何を出すか？
    • 内部情報が漏れていないか？
    • 攻撃の痕跡がログに残るか？

    悪用シナリオ

    • どんな悪用があり得るか？
    • 同時実行・二重実行に耐えるか？
    • レート制限は必要か？

    依存関係

    • 外部ライブラリは安全か？ 更新されているか？
    • 外部APIを信頼しすぎていないか？
    • サプライチェーンのリスクは？

    8.OWASP や関連フレームワークとの関係

    8.1 OWASP Top 10 との関係

    Webアプリの代表的なリスクをまとめた OWASP Top 10 の2021年版で、A04「安全でない設計」 が新しく加わりました。これは、設計段階でのセキュリティの重要性が広く認められたことを示しています（→ OWASP Top 10 とは）。

    セキュアバイデザインは、OWASP の全項目に対する 予防策 として働きます。A01〜A10 のどれも、設計時に考慮していれば防げたケースが多くあります。

    8.2 関連フレームワーク

    フレームワーク概要
    OWASP SAMM（Software Assurance Maturity Model）セキュアSDLCの成熟度モデル。組織の現状を評価し、次のステップを示す
    BSIMM（Building Security In Maturity Model）実際の企業の取り組み事例をもとにした成熟度評価
    Microsoft SDL（Security Development Lifecycle）Microsoft が自社製品に適用しているセキュアSDLC。業界の標準的な手本
    NIST SSDF（Secure Software Development Framework）NIST SP 800-218 として2022年に公表。米国政府の調達で求められる

    また、セキュアバイデザインは単独で完結するものではなく、脅威モデリング・最小権限・深層防御・ゼロトラスト と連携して実現します。

    9.チェックリスト

    • 新機能の設計時に脅威モデリングをしているか？
    • セキュリティ要件を明示的に定義しているか？
    • デフォルト設定が安全な状態か？
    • CI/CD パイプラインにセキュリティチェックが組み込まれているか？
    • SAST / DAST / SCA を実施しているか？
    • 開発者はセキュアコーディングの訓練を受けているか？
    • インシデント対応計画は準備されているか？
    • セキュリティに関わる設計判断を記録（ADR＝設計判断の記録文書 など）しているか？

    10.まとめ

    このページの要点

    • セキュアバイデザインは 「設計段階から安全を組み込む」 考え方
    • 後付けは高コスト。設計の欠陥はコードでは防げない
    • セキュア・バイ・デフォルト（初期設定が安全）も合わせて徹底し、安全にする責任は作る側が負う
    • Saltzer と Schroeder の古典原則（デフォルト拒否・完全な仲介・特権の分離など）は今も有効
    • シフトレフト と DevSecOps で開発プロセスに組み込む
    • 脅威モデリング・最小権限・深層防御・ゼロトラストと連携して実現する

    11.理解度チェック

    Q1. セキュアバイデザインとセキュア・バイ・デフォルトの違いは？

    セキュアバイデザインは 作り方（設計段階から安全な仕組みを組み込む）、セキュア・バイ・デフォルトは 届け方（利用者が何も設定しなくても安全な初期状態で提供する）の話です。両者はセットで使われます。

    Q2. 「パスワードリセットで、登録メールアドレスを知っていれば誰でも再設定できる」仕様。コードレビューを丁寧にすれば防げますか？

    防げません。 コードが仕様どおり正しく動いていても、仕様そのものが弱いため乗っ取りが可能です。これは「設計の穴」（OWASP A04 安全でない設計）であり、本人確認の仕組みを設計から見直す必要があります。

    Q3. 次のコードは「フェイルセーフなデフォルト」になっていますか？ if is_blocked(user): return deny() のあとに return allow()

    なっていません。 禁止リストに載っていない相手はすべて許可される「デフォルト許可」です。想定外の利用者や状態を見落とすと、そのまま通ってしまいます。if is_allowed(user): return allow() のあとに return deny() と書き、知らない状態は拒否に倒します。
