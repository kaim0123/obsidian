    50 運用・監視・インシデント

    セキュアな運用とログ出力

    セキュリティは「作って終わり」ではなく、守り続けるプロセスです。このページでは、設計段階から安全を組み込む考え方とセキュアコーディングの基本、そして運用の要となる ログ出力（何を・どの項目で・どう守って・どれだけ残すか）を詳しく解説し、インシデント対応の流れ、脆弱性管理、コンプライアンスまでを整理します。

    もとにしたノート：50_運用・監視・インシデント/05_セキュリティ設計と運用（基礎講座第5回）、06_ログ出力（徳丸本24章）

    ひとことで言うと

    安全なシステムは 「作る（設計・コーディング）→ 守る（ログと監視）→ 対応する（インシデント対応・脆弱性管理）」 を回し続けて保たれます。中でもログは、防げなかったときに事実を残す 「証拠」 であり、異変を知らせる 「センサー」 です。誰が・いつ・どこから・何に・何をして・どうなったか を記録し、パスワードなどの秘密は書かず、改ざんされない場所に、決めた期間だけ残します。

    1.セキュアな設計 — 最初から組み込む

    1.1 多層防御を Web サービスに当てはめる

    多層防御（Defense in Depth） は「1つの対策が破られても、次の壁で止める」考え方です。家にたとえると、門扉・玄関の鍵・部屋の鍵・金庫・防犯意識と、何重にも守るイメージです。Web サービスなら次のように層を分けられます。

    層主な対策
    1. ネットワーク境界ファイアウォール、DDoS 対策、WAF（ネットワークと端末の防御）
    2. サーバー・OS不要なポートを閉じる、OS のアップデート・パッチ適用、不要なサービスの無効化
    3. アプリケーション入力値の検証、プリペアドステートメント、適切な認証・認可
    4. データ暗号化（保存時・転送時）、アクセスログの記録、定期バックアップ
    5. 人・プロセスセキュリティ教育、インシデント対応手順、定期的な脆弱性診断

    考え方の詳細は 深層防御 を参照してください。

    1.2 セキュリティバイデザインとシフトレフト

    セキュリティバイデザイン は「後付けではなく、設計段階からセキュリティを組み込む」考え方です。家を建てた後で耐震補強するより、設計図の段階で耐震構造にしておくほうが、早く・安く・確実です。

    ✕ よくある失敗

    要件定義 → 設計 → 開発 → テスト →「さあセキュリティ対策！」

    最後にまとめて対策しようとすると、手遅れ・高コスト・根本的な問題が残る。

    ○ 各段階で問いを立てる

    • 要件：どのデータが機密か？ 誰がアクセスできるべきか？ 脅威は？
    • 設計：認証・認可をどうする？ 通信は暗号化？ ログは何を記録？
    • 開発：入力検証は？ ガイドラインに沿っている？
    • テスト：脆弱性スキャン・ペネトレーションテスト

    これと密接なのが シフトレフト です。工程表を左から右へ並べたとき、セキュリティ対策を 左側（早い段階）へずらす という意味です。問題は見つかるのが遅いほど直すコストが膨らみます（ノートでは「開発中に見つければ 1、テストで 10、本番後は 100〜」という目安が紹介されています）。

    段階シフトレフトで使う手法・ツール
    設計脅威モデリング（STRIDE など）、セキュリティアーキテクチャレビュー
    開発SAST（コードを実行せずに解析して脆弱性を見つける：SonarQube、Semgrep、CodeQL）
    シークレットスキャン（API キーやパスワードの誤コミットを検出：GitHub Secret Scanning、Gitleaks）
    依存パッケージの脆弱性チェック（Dependabot、npm audit、Snyk）
    CI/CDpush のたびに自動でセキュリティチェックし、問題があればマージを止める

    1.3 脅威モデリング（STRIDE）

    脅威モデリング は「どんな攻撃が来うるか」を設計前に整理する作業です。代表的な枠組み STRIDE は、脅威を6つの頭文字で洗い出します。

    頭文字脅威例主な対策
    SSpoofing（なりすまし）正規ユーザーを装ってログイン強固な認証、MFA
    TTampering（改ざん）データを不正に書き換えるデジタル署名、ハッシュ検証
    RRepudiation（否認）「自分はやっていない」と言い張る監査ログ、デジタル署名
    IInformation Disclosure（情報漏洩）機密情報が外部に漏れる暗号化、アクセス制御
    DDenial of Service（サービス拒否）サービスを使えなくするDDoS 対策、冗長化
    EElevation of Privilege（権限昇格）一般ユーザーが管理者権限を得る最小権限、認可の徹底

    「否認」への対策がログである点に注目してください。ログは後半の主役です。詳しくは STRIDE、セキュアバイデザイン で。

    2.セキュアコーディングの基本

    2.1 入力値の検証 — 「ユーザーの入力は常に信頼しない」

    ○ 許可リスト方式（推奨）

    「許可する値だけ」を定義し、それ以外はすべて拒否。例：郵便番号は「数字7桁」のみ。お店の「会員カードを持つ人だけ入店可」のような考え方。

    ✕ 拒否リスト方式（非推奨）

    「禁止する値」を並べる方式。攻撃者は禁止リストのすき間を探すので、漏れが生じやすい。

    チェックすべき項目は 型（数値のはずが文字列ではないか）・長さ（上限を超えていないか）・形式（メールアドレスや URL）・範囲（年齢 0〜150 など）・文字種（想定外の特殊文字）です。

    2.2 出力時のエスケープ — 出す先に合わせて無害化する

    入力の検証とは別に、データを出力する先 に合わせた処理が必要です。同じ文字でも、HTML・SQL・シェルでは「特別な意味を持つ記号」が違うからです。

    出力先対策
    HTML< → &lt;、> → &gt;、" → &quot;、' → &#x27;、& → &amp; と置き換える
    SQLプリペアドステートメント（値を後から安全に差し込む仕組み）を使う
    シェルコマンドメタ文字（; | & $ ` など）をエスケープ。できれば外部入力をシェルに渡さない
    JavaScriptJSON.stringify などで安全にエンコードする

    詳しくは インジェクションと暗号化の不備、72_Web脆弱性対策 で扱います。

    2.3 エラー処理 — 攻撃者にヒントを与えない

    ✕ 画面に詳細を出す

    • スタックトレース（ファイルパス・行番号が丸見え）
    • SQL のエラー文（テーブル名・カラム名が丸見え）
    • サーバーのバージョン情報

    → 攻撃者に「攻略のヒント」を渡してしまう

    ○ 画面は簡潔に、詳細はログへ

    • 画面：「エラーが発生しました。しばらくしてからお試しください」＋問い合わせ用のエラー ID
    • ログ（外から見えない場所）：詳細なエラー内容とスタックトレース。エンジニアだけが見られる

    2.4 シークレット管理 — 鍵をコードに書かない

    パスワードや API キーなどの シークレット（秘密情報） をソースコードに直書きすると、Git にコミットされた時点で漏洩のリスクが生まれます。公開リポジトリなら世界中から見えてしまいます。

    ✕ ソースコードに直書き 
    DB_PASSWORD = "super_secret_password"
API_KEY = "sk-1234567890abcdef"
    ○ 環境変数やシークレット管理サービスから読む 
    import os
DB_PASSWORD = os.environ.get("DB_PASSWORD")
# .env を使う場合は .gitignore に追加してコミットしない
    • シークレット管理サービスを使う：AWS Secrets Manager、HashiCorp Vault、GitHub Actions Secrets
    • 誤ってコミットしたら：すぐにその認証情報を無効化・再発行（ローテーション） し、Git の履歴からも削除する（git-secrets などで事前に防止）

    よくある誤解：「コミットを消せば大丈夫」

    一度公開された秘密は、すでに誰かにコピーされているかもしれません。履歴の削除だけでは足りず、鍵そのものを無効化して作り直す のが先です。

    2.5 依存パッケージの管理

    リスクは自分が書いたコードだけではありません。使っているライブラリの脆弱性も定期的に確認します。

    pip audit        # Python
npm audit        # Node.js（npm audit fix で自動修正）
bundle audit     # Ruby

    GitHub の Dependabot は、脆弱性のある依存パッケージを検出し、修正のプルリクエストを自動で作ってくれます。また SBOM（使っている部品の一覧表）を整えておくと、Log4Shell のような大事件のときに「うちは影響ある？」をすぐ確認できます（サプライチェーンと整合性の不備）。

    3.ログはなぜ必要か — 証拠とセンサー

    ログ とは、アプリやサーバーが「いつ・誰が・何をしたか」「どんなエラーが起きたか」を時系列で残した記録です。画面には出さず、運用者やセキュリティ担当が後から読むためのメモです。マンションのオートロックが残す 「何時に誰のカードで開いたか」の入退室記録 をイメージしてください。

    用語意味
    ログ出力処理の途中や結果を、ファイルやログ基盤に書き出すこと
    アクセスログリクエストや操作の履歴
    エラーログ失敗や例外の記録
    監査ログセキュリティや運用監査に使う、重要な操作の記録

    3.1 ログがないと何が起きるか

    ログがないと

    • 攻撃されているのに気づけない
    • どこから侵入され、何のデータが盗まれたか分からない
    • パスワードや権限の変更履歴がなく、不正操作を証明できない
    • 障害の原因調査に時間がかかる
    • 監査・インシデント報告・法的対応で説明できない

    ログがあると

    • 攻撃を早期に検知できる
    • 侵入経路を特定できる
    • 被害範囲を把握できる
    • 再発防止策を立てられる

    「ログイン画面を固めた」「認可を入れた」だけでは、起きた事実 は残りません。ログは防御と運用を支える土台です。OWASP Top 10 でも「ログと監視の不備」は独立した項目になっています（ログ不足・SSRF・例外処理）。

    3.2 ログを取る3つの目的

    ① 予兆の把握と早期対策

    攻撃はいきなり成功するとは限らず、失敗や拒否のログとして先に現れる。例：同じ IP から1分に100回ログイン失敗、一般利用者が /admin 配下に連続アクセス、深夜だけ特定アカウントのパスワード変更が繰り返される。アラートを設定すれば、アカウントロックや IP 制限で被害前に止められる。

    ② 事後調査

    いつ始まったか、誰（どのアカウント・IP）が関与したか、どのデータが触られたか、成功と失敗はどれか、影響はまだ残っているか。ログがなければ推測しかできない。

    ③ 運用監査

    規定・法令・契約で「重要な操作を記録・保管」が求められることがある。誰が顧客情報を参照・出力したか、権限を付与したのは誰か。正当な業務でも記録が必要。

    4.何を記録するか — ログの種類・イベント・項目

    4.1 ログの種類（どこが出すか・何に使うか）

    層誰が出すか主な内容向いている調査
    Web サーバーnginx、Apache などURL、ステータスコード、IP、応答時間アクセス全体の把握、404/500 の傾向、攻撃の入口
    アプリケーション自作の Web アプリログイン成否、業務操作、例外、認可拒否「誰が何をしたか」の調査（セキュリティ調査の中心）
    データベースMySQL、PostgreSQL など接続、遅いクエリ、エラー、設定次第で SQLDB 障害、不正な大量取得の手がかり

    Web サーバーのログだけでは「どのユーザーがパスワードを変えたか」までは分からず、DB ログだけでは「画面のどの操作か」が分かりにくいもの。アプリのログを中心に、3つを組み合わせる と正確に再現できます。

    用途で分けると、エラーログ（例外・失敗。必ず残して監視）、アクセスログ（リクエストや重要操作の履歴。セキュリティ・監査用）、デバッグログ（開発時の詳細。本番では原則オフ）の3つです。デバッグログは個人情報やトークンが混ざりやすく、本番で出しっぱなしにするとログ自体が漏洩源になります。

    インフラ全体で見ると、ほかに 認証ログ（ログイン成否・IP・時刻）、システムログ（OS 操作・ユーザー追加・設定変更 → 内部不正の検知）、ネットワークログ（通信の送受信・FW の判断 → 不正通信の検知）、DB アクセスログ（クエリ内容・ユーザー・件数 → データ漏洩の検知）も重要です。

    4.2 必ず記録すべきイベント

    すべてを記録すると量が増えすぎて重要な出来事が埋もれます。少なくとも次は残します。共通するコツは 成功だけでなく失敗も残す ことです。

    イベントなぜ記録するか・何を残すか
    ログイン・ログアウトなりすましの入口・出口を追うため。成功（ユーザー ID・IP・時刻）だけでなく 失敗（入力された ID・IP・時刻・「パスワード不一致」「停止中」程度の理由）も。失敗の急増は総当たりの予兆
    アカウントロックロックの発生と 解除（自動・管理者）。誰が外したかがないと、攻撃者による解除を追えない
    ユーザー登録・削除攻撃者が裏口用アカウントを作る、調査前にアカウントを消す、といった動きを追うため
    パスワード変更本人の変更・管理者リセット・忘れた時の再設定は、いずれも 乗っ取りの定着手段 になり得る。成功・失敗の両方
    重要情報の参照「見るだけ」でも被害になる。個人情報・カード情報・社外秘の帳票など、参照そのものを監査対象にするデータを決める
    重要な操作権限・ロールの変更、管理者機能、データの一括エクスポート、セキュリティ設定の変更、金銭やポイントの移動、削除。認可で拒否された操作 の連続は権限昇格の予兆

    4.3 出力項目 — 5W1H をそろえる

    1件のログから 誰が・いつ・どこから・何に対して・何をして・どうなったか が分かるようにします。

    項目例つまずきやすい点
    日時2026-07-04T15:30:00+09:00タイムゾーン付きで。サーバー間で時刻がずれていると突き合わせられない（5.4）
    リモート IP203.0.113.10プロキシやロードバランサ経由では転送ヘッダの扱いに注意。偽装できるヘッダを鵜呑みにしない
    ユーザー IDuser_12345 / anonymousセッション上の ID を使う。リクエストの「自称ユーザー ID」は信用しない
    アクセス対象/orders/42、画面 ID、API 名URL だけでなく画面 ID や API 名があると業務調査しやすい
    操作内容・操作対象UPDATE、order_id=42「更新しました」だけでは不十分。何の ID をどうしたか
    操作結果success / failure、件数成功だけ残すと、攻撃の失敗パターンが見えない
    ○ 良いログ（1行で状況が分かる） 
    2026-07-04T15:30:00+09:00 ip=203.0.113.10 user=user_12345 action=UPDATE target=order_id=42 result=success
    ✕ 悪いログ 
    エラーが起きました

    4.4 ログに書いてはいけないもの

    秘密の「中身」は書かない

    • パスワード（平文でもハッシュでも、入力値は残さない）
    • クレジットカード番号・セキュリティコード
    • セッション ID・API トークン（漏れるとそのままなりすましに使える）
    • 個人情報の本文を必要以上に長く残すこと

    原則は 「調査に必要な識別子（ID）は残し、秘密の中身は残さない」。ログが漏洩したときの二次被害を防ぐためです。

    5.ログを守る・置く・残す・時刻を合わせる

    ログの「書き方」と同じくらい大事なのが、その後の扱いです。全体像を図で見てみましょう。

    5.1 ログの保護 — ログ自体も攻撃対象

    ログにはユーザー ID、IP、操作内容など、攻撃者にとって有用な情報が詰まっています。また攻撃者は侵入後、自分の足跡を消す ことがよくあります。

    リスク何が起きるか
    漏洩ログから個人情報やシステムの内部構造が漏れる
    改ざん・削除攻撃者が痕跡を消す、他人に罪をなすりつける
    不正な追加偽のログを混ぜて調査を混乱させる
    1. ログの閲覧・変更権限を、必要最小限の担当者・プロセスに限定する
    2. アプリの実行ユーザーが、過去ログを自由に削除・改ざんできないようにする
    3. アプリサーバーとは 別の場所（専用ログサーバー、クラウドのログサービス）へ転送する
    4. 転送後のログは 追記のみ（書き換えにくい）にする
    5. バックアップとアクセス監査を行い、ログ自体への操作も追跡できるようにする

    防犯カメラの録画機を、泥棒が入る部屋に置いておけば持ち去られてしまいます。書いたらすぐ別の場所へ送る 設計が有効です。

    5.2 出力先

    出力先特徴向いている用途
    ローカルファイル実装が簡単。障害時も残ることがある小規模、まずは確実に残す
    標準出力／コンテナログコンテナ環境で収集しやすいクラウド・コンテナ基盤
    専用ログサーバー・SIEM集約・検索・アラートがしやすい本格的な監視とインシデント対応
    クラウドのログサービス保管・権限管理・保持期間の設定がしやすいマネージドな運用

    開発環境と本番環境で出力先を分け、本番にデバッグ用の詳細が流れない ようにします。ログの置き場所自体がインターネットに公開されていないかも確認しましょう。

    現代の開発では、自前でログサーバーを立てるより クラウドのログ管理サービス を使うのが主流です（コスト・運用負荷・拡張性で有利）。

    サービス種別向いている場面
    AWS CloudWatch LogsクラウドAWS を使っているチーム。収集からアラートまで一元管理
    Google Cloud LoggingクラウドGCP 中心。BigQuery と組み合わせて分析
    DatadogSaaSAPM・ログ・メトリクスをまとめて監視したい
    Vercel Logs / SentrySaaSフロントエンド・エッジのログ／エラー・例外の追跡
    Grafana + LokiOSS自分でホストしたい・コスト重視
    Elastic Stack（ELK）OSS / SaaS大量ログの高度な分析

    ツールより設計が大事

    どのサービスを使っても、「何を記録するか」「誰がアクセスできるか」の設計は変わりません。大規模環境では、Splunk、Microsoft Sentinel、Amazon Security Lake、Elastic SIEM などに集約して相関分析します（セキュリティ監視とツール）。SIEM なら「同じ IP から5分間に100回ログイン失敗 → 総当たり攻撃」「深夜に大量の DB レコードをダウンロード → 情報漏洩の可能性」「普段と違う国からのログイン → 乗っ取りの可能性」といった検知ができます。

    5.3 保管期間

    観点考え方
    インシデント調査発覚が遅れることもあるため、数週間〜数か月分はすぐ検索できると安心
    法令・契約・社内規定業種によっては保持期間が決まっている
    容量とコスト古いログは圧縮・アーカイブし、ホット（すぐ見る）と コールド（安く長く置く）を分ける

    運用例：直近90日は検索しやすい場所に → それ以降はアーカイブして長期保管 → 保持期間を過ぎたら手順に従って削除。「なんとなく1週間」ではなく、調査に必要な長さ と 規定上の長さ の両方を満たし、自動削除の設定が早すぎないかも確認します。

    5.4 サーバーの時刻合わせ

    調査では Web・アプリ・DB・認証基盤など 複数のログを時刻で突き合わせ ます。時計がずれていると、因果関係を取り違えます。

    サーバーA: 15:00:10 ログイン成功
サーバーB: 15:00:05 権限変更   ← 実際はログイン後なのに、時刻だけ見ると先に起きたように見える
    • NTP（ネットワーク経由で時計を合わせる仕組み）などで、全サーバーを信頼できる時刻源に同期する
    • タイムゾーンを統一する（UTC で統一するか、+09:00 のようなオフセット付きで記録）
    • 時刻同期が止まったら気づけるよう監視する

    「日時を出す」だけでなく、その日時が信頼できること が調査の前提です。

    6.ログ出力の実装 — ログレベルの使い分け

    実装では言語やフレームワークのロギングライブラリを使い、ログレベル（重要度のラベル）で出し分けます。

    レベル意味例本番での扱い
    fatal致命的。サービス継続が難しい起動不能、必須設定の欠落必ず出す。即対応
    error処理は失敗したが、プロセスは生きている例外、外部 API 失敗、DB エラー必ず出す。監視する
    warnすぐ落ちないが放置すると問題になり得るリトライ発生、非推奨設定、認可拒否の連続出す。しきい値でアラートも検討
    info通常運用の重要な出来事ログイン成功、設定変更、バッチの開始・終了監査・運用に必要な範囲で出す
    debug開発・調査用の詳細変数の値、分岐の途中経過原則オフ
    tracedebug よりさらに細かい追跡ループ内の逐次出力原則オフ
    • セキュリティ上重要なイベント（ログイン、権限変更、重要情報の参照）→ info 以上で、必ず残る設定に
    • 想定外の失敗 → error（状況により fatal）
    • 攻撃の予兆になり得る拒否や異常 → warn または info（監視しやすいレベルで統一）
    • 変数ダンプや詳細トレース → debug / trace（開発時のみ）

    本番を debug のままにすると、量が増えてディスクを圧迫し、秘密情報も混ざりやすくなります。

    6.1 実装時の注意点

    注意点説明
    例外を握りつぶさないエラーを無視すると error ログも残らず、調査不能になる
    ログ出力自体の失敗を想定するディスク満杯などで書けないとき、本処理をどう扱うか決めておく
    フォーマットをそろえる日時・レベル・メッセージの形式を統一すると検索しやすい
    リクエスト ID を付ける1回の操作に ID を振り、複数行のログをひとまとめに追えるようにする
    ユーザー入力をそのまま長く書かない改行などを混ぜて偽のログ行を作る ログインジェクション や、巨大ログを防ぐ
    リクエスト ID でひとまとめにする例 
    request_id=abc-123 user=user_1 action=login result=failure
request_id=abc-123 reason=bad_password

    7.インシデント対応 — 起きたときに慌てないために

    セキュリティインシデント とは、マルウェア感染、不正アクセス・情報漏洩、DDoS によるサービス停止、内部不正、ランサムウェアによるデータ暗号化など、セキュリティ上の問題が発生した事象のことです。対応は消防活動に似ていて、平時の準備 と 延焼を止める初動 が勝負を決めます。

    7.1 対応の6ステップ（PICERL）

    1. Preparation（準備）← 平時にやっておく：対応計画の策定、対応チーム（CSIRT）の組織、連絡先リスト、ツール・環境の準備、定期的な訓練
    2. Identification（検知・識別）：発生を検知し、「本当にインシデントか？」を判断。影響範囲・重大度を初期評価
    3. Containment（封じ込め）← 最優先：被害拡大を止める。感染端末をネットワークから切り離す、不正利用されたアカウントを停止、攻撃経路のシステムを隔離。証拠保全と両立させる
    4. Eradication（根絶）：攻撃者とマルウェアを完全に排除し、脆弱性を修正、侵入経路を塞ぐ
    5. Recovery（回復）：バックアップから復元し、監視しながら段階的にサービスを再開
    6. Lessons Learned（事後検証）← 必ず実施：時系列のまとめ、根本原因の分析、再発防止策の策定・実施、ドキュメント更新

    7.2 初動チェックリスト

    まずやること

    1. 落ち着く（パニックにならない）
    2. 記録を始める：発見日時・状況をメモし、以後の対応もすべて残す
    3. 上長・セキュリティ担当に報告：自分だけで解決しようとしない

    次にやること

    1. 証拠保全：ログをコピー、メモリダンプを取得、不審なファイルは 削除せず隔離
    2. 封じ込め：感染端末を切り離し、関係アカウントのパスワードを変更
    3. 関係者へ連絡：経営陣・法務・広報・必要なら顧客。法的な報告義務があれば当局へ（個人情報漏洩なら個人情報保護委員会）

    よくある失敗：「怪しいファイルを消して、再起動して終わり」

    削除や再起動は、侵入経路や被害範囲を知るための 証拠（ファイル・メモリ上の情報・ログ）を消してしまいます。まず報告し、証拠を保全しながら封じ込めます。調査で使う分析ツールは セキュリティ監視とツール を参照してください。

    8.脆弱性管理・ペネトレーションテスト・バグバウンティ

    8.1 脆弱性管理は回し続けるサイクル

    1. 発見：脆弱性スキャナー、セキュリティ情報（CVE・JVN）の定期確認、ペネトレーションテスト
    2. 評価・優先順位付け：CVSS で深刻度を評価、実際に悪用されているか、ビジネスへの影響度
    3. 対応：パッチ適用・アップデート、設定変更・回避策、またはリスク受容（対応コストが影響を上回る場合）
    4. 検証：正しく適用されたか、再スキャンで確認 → 1 に戻る

    CVSS（Common Vulnerability Scoring System）は、脆弱性の深刻度を 0.0〜10.0 で数値化した指標です。

    スコア深刻度対応方針（ノートの目安）
    9.0〜10.0Critical（緊急）即時対応。業務を止めてでも対処
    7.0〜8.9High（重要）早急に（数日以内）
    4.0〜6.9Medium（警告）計画的に（数週間以内）
    0.1〜3.9Low（注意）リスク評価のうえ対応
    0.0None対応不要

    例として、Log4Shell（CVE-2021-44228） は CVSS 10.0。リモートから任意のコードを実行できる致命的な脆弱性で、公表直後から世界中で攻撃が観測されました。ただし CVSS は参考値の一つ です。スコアが低くても自社環境で悪用されやすいものは優先度を上げます。境界機器のパッチ運用など詳しくは 脆弱性管理とランサムウェア対策 で。

    8.2 ペネトレーションテストの種類と流れ

    種類与える情報視点
    ブラックボックス内部情報なし外部の攻撃者
    ホワイトボックスソースコード・設計書などすべて内部を知る者。最も深く検査できる
    グレーボックス一部の情報一般利用者や内部関係者

    流れは「スコープ定義（どこを何をテストするか）→ 事前調査 → 脆弱性スキャン → 侵入テスト → レポート作成 → 修正・再テスト」。ツールは Nmap、Metasploit、Burp Suite、OWASP ZAP など。必ず許可を得て 行います。

    8.3 バグバウンティ

    バグバウンティ は、脆弱性を見つけて報告した人に報奨金を払う制度です。「うちのシステムを調べて、穴を見つけたら報奨金を払います」と世界中の研究者に呼びかけることで、悪用される前に脆弱性を発見できます。代表的なプラットフォームは HackerOne、Bugcrowd。日本では IPA（情報処理推進機構）の脆弱性の届出制度もあります。

    9.コンプライアンスとセキュリティ基準

    ログの保管期間や重要操作の記録は、法律や業界基準で求められることもあります。

    基準・法律対象概要
    個人情報保護法日本で個人情報を扱う事業者個人情報の適正な取扱い。漏洩時の報告義務など
    GDPREU の個人データを扱う組織EU 域内の人のデータ保護。違反時は巨額の制裁金
    PCI DSSクレジットカード情報を扱う組織カード情報の安全な取扱い
    HIPAA米国の医療情報を扱う組織医療情報の保護
    ISO/IEC 27001認証を受けたい組織情報セキュリティマネジメント（ISMS）の国際規格
    NIST CSF米国発、日本でも参照されるサイバーセキュリティフレームワーク

    10.まとめ

    このページの要点

    • 設計：多層防御・セキュリティバイデザイン・シフトレフト・STRIDE で、最初から安全を組み込む
    • コーディング：入力は許可リストで検証、出力は出す先に合わせてエスケープ、エラー詳細は画面でなくログへ、シークレットは直書きせず、依存パッケージも監査
    • ログの目的は予兆検知・事後調査・運用監査。ログイン・アカウント変更・重要情報の参照・重要操作を、失敗も含めて 記録する
    • 項目は日時・IP・ユーザー・対象・操作・結果。パスワード・カード番号・トークンは書かない
    • ログは すぐ別の場所へ転送して改ざんを防ぎ、保管期間を決め、NTP で時刻を合わせる。本番は info 以上、debug は出さない
    • インシデントは PICERL。封じ込めが最優先だが証拠は消さない。脆弱性管理は発見 → 評価 → 対応 → 検証を回し続ける

    11.理解度チェック

    Q1. ログイン「失敗」もログに残すべきなのはなぜですか？

    攻撃は成功する前に、失敗や拒否として先に現れる からです。同じ IP からの大量のログイン失敗はパスワード総当たりの予兆で、これを監視していればアカウントロックや IP 制限で被害前に止められます。成功だけ残すと、攻撃のパターンが見えません。

    Q2. 「調査に役立つから」と、ログイン時に入力されたパスワードもログに残すのはよいですか？

    いけません。 ログが漏洩したとき、そのままアカウント乗っ取りにつながります。平文でもハッシュでも入力値は残さず、セッション ID・API トークン・カード番号も同様です。原則は「識別子（ユーザー ID など）は残し、秘密の中身は残さない」です。

    Q3. ログをアプリと同じサーバーのディスクだけに保存するのは、なぜ危ういのですか？

    攻撃者は侵入後に 自分の足跡（ログ）を消す ことが多く、同じサーバー上だけだと侵入と同時に消されたり改ざんされたりする可能性があるからです。書いたらすぐ専用ログサーバーやクラウドのログサービスへ転送し、追記のみ・権限限定で保管します。

    Q4. 複数のサーバーのログを突き合わせて調査するとき、前提として必要なことは？

    全サーバーの時刻がそろっていること です。NTP などで同期し、UTC かオフセット付きでタイムゾーンを明示して記録します。時計がずれていると、出来事の順番を取り違えて因果関係を誤ります。

    Q5. インシデント対応で「封じ込め」が最優先なのに、怪しいファイルをすぐ削除してはいけないのはなぜ？

    削除すると、侵入経路や被害範囲を突き止めるための 証拠 が失われるからです。封じ込めは「ネットワークから切り離す」「アカウントを停止する」などで行い、ファイルは削除せず隔離、ログのコピーやメモリダンプを取って証拠を保全します。
