    20 設計原則

    最小権限とデータ最小化

    「使わない権限は持たせない」「持っていないデータは漏れない」。セキュリティ設計のいちばん土台にある2つの原則を、家の合鍵や病院のカルテのたとえから始めて、データベース・クラウド・コンテナ・CI/CD での具体例、実現の手順、よくある失敗まで順に解説します。

    もとにしたノート：20_設計原則/01_最小権限の原則、05_データ最小化

    ひとことで言うと

    最小権限は「人やプログラムが できること を必要最小限に絞る」原則、データ最小化は「持っているデータ そのものを必要最小限に絞る」原則です。どちらも「いつか破られる」前提に立ち、破られたときに失うものを小さくする ための考え方です。

    1.2つの原則のイメージ

    まず身近なたとえで考えてみましょう。あなたが家を留守にする間、植木の水やりを近所の人にお願いするとします。

    ✕ 家じゅうの合鍵を全部渡す

    玄関・寝室・金庫・車の鍵までまとめて渡す。相手が悪い人でなくても、鍵束を落としただけで家の全部が危険 になります。

    ○ 庭の勝手口の鍵だけを、1週間だけ渡す

    水やりに必要なのは庭に入ることだけ。鍵を落としても、入られるのは庭だけ。期間が過ぎれば返してもらいます。

    これが 最小権限の原則 です。さらに、そもそも 家に現金や通帳を置いていなければ、泥棒に入られても盗まれるものはありません。これが データ最小化 の発想です。

    最小権限の原則データ最小化
    絞るもの権限（何ができるか、どこに届くか、いつまで有効か）データ（何を集め、どこに、いつまで持つか）
    合言葉使わない権限は持たせない持っていないデータは漏れない
    家のたとえ必要な部屋の鍵だけを渡す家に貴重品を置いておかない
    効くときアカウントやサーバーが乗っ取られたとき、誤操作したときデータベースやバックアップが盗まれたとき

    2つは別々の原則ですが、「攻撃者が手にできるものを小さくする」という点で同じ方向を向いています。このページでは両方をまとめて扱います。

    2.最小権限の原則とは

    2.1 定義と由来

    最小権限の原則（PoLP：Principle of Least Privilege）とは、

    人・プログラム・プロセスは、必要最小限の権限だけを持つべき

    というセキュリティの基本原則です。ここでいう 権限 とは「そのアカウントやプログラムに許された操作の範囲」のこと。たとえば「このファイルを読める」「このデータベースのテーブルを消せる」といった許可の一つひとつが権限です。

    この原則は1970年代に Saltzer と Schroeder が提唱した情報セキュリティの古典的な原則の1つで、現代でもほぼすべてのセキュリティ設計の土台になっています（彼らの他の原則は セキュアバイデザイン で紹介します）。

    2.2 なぜ重要なのか

    1. 侵害されたときの被害を最小にする：完璧なセキュリティは存在しません。いつか破られる前提で考えるなら、破られたときの影響範囲 を小さくすることが大切です。アカウント1つが乗っ取られても、そのアカウントでできる範囲しか被害は及びません。サーバー1台が侵害（攻撃者に入り込まれること）されても、そのサーバーから届く範囲しか広がりません。
    2. 誤操作・人的ミスの被害も減らす：攻撃だけでなく、うっかりミスにも効きます。開発者が本番データベースを直接触って全レコードを消してしまう、という事故も、そもそも 読み取り権限しかなければ 誤った UPDATE や DELETE は実行できません。
    3. 法律や業界ルール（コンプライアンス）が求めている：GDPR（EUの個人データ保護規則）、PCI-DSS（クレジットカード業界の安全基準）、SOX（米国の企業会計に関する法律）など、多くの規制が最小権限を明示的に求めています。

    「被害半径」という見方

    侵入されたときに被害が広がる範囲を、爆発の届く範囲にたとえて 被害半径（ブラスト・ラジアス） と呼ぶことがあります。最小権限は、この半径を小さくするための一番基本的な手段です（深層防御のページでも登場します → 深層防御）。

    2.3 最小化する3つの次元

    「権限を絞る」と言っても、絞る方向は3つあります。種類・範囲・期間 の3つを意識すると、抜け漏れが減ります。

    次元問い例
    種類何ができるか？操作の種類を表す CRUD（Create 作成 / Read 読取 / Update 更新 / Delete 削除）を必要なものに絞る。レポート閲覧ユーザーなら Read だけで、Write は不要
    範囲どこに対してか？「全テーブル」ではなく「売上テーブルだけ」。「全バケット」ではなく「アップロード用バケットだけ」
    期間いつまで有効か？メンテナンス作業のときだけ一時的に権限を上げる。これを ジャストインタイム（JIT）アクセス と呼ぶ

    3.最小権限の具体例

    ここからは、現場でよく出てくる5つの場面で「悪い例」と「良い例」を比べます。

    3.1 ユーザーアカウント

    ✕ 悪い例

    「管理者に1人1アカウントを作って、全員フル権限」。この状態だと、

    • 誰か1人のアカウントが乗っ取られれば、全権限が奪われる
    • 退職者のアカウントが残りがち
    • 監査（あとから記録を確かめること）で、誰が何をしたか追跡しにくい
    ○ 良い例：役割ごとに権限を分ける（RBAC）
    • 一般ユーザー：閲覧のみ
    • 編集者：自分の担当範囲だけ書き込める
    • 管理者：必要な業務に応じた最小限の管理権限
    • 監査ログ用ユーザー：読み取りのみ・書き込み不可（ログの改ざんを防ぐ）

    3.2 データベースのアカウント

    ✕ 悪い例 
    アプリ用DBユーザー = root（全権限）

    この状態で SQLインジェクション（入力欄に不正な命令文を混ぜてデータベースを操る攻撃）を受けると、テーブルの削除（DROP）や、場合によってはサーバーのOSへの侵入まで許してしまいます。

    ○ 良い例：用途ごとにユーザーを分ける 
    - アプリ用ユーザー        : SELECT, INSERT, UPDATE, DELETE のみ（テーブル定義の変更＝DDL は不可）
- 読み取り専用ユーザー    : SELECT のみ（分析用）
- マイグレーション用ユーザー: DDL を含むフル権限（デプロイ時だけ一時的に使う）

    DDL とは、テーブルを作る・変える・消すといった「データの入れ物そのもの」を操作する命令のことです。普段のアプリは中身を読み書きするだけなので、入れ物を壊す権限は要りません。

    3.3 クラウドの IAM（AWS など）

    IAM（Identity and Access Management）は、クラウドで「誰が・何に・何をしてよいか」を決める仕組みです。権限は JSON で書いた「ポリシー」で表します。

    ✕ 悪い例：すべての操作を、すべての資源に許可 
    {
  "Effect": "Allow",
  "Action": "*",
  "Resource": "*"
}

    このポリシーを付けたアクセスキー（プログラムがクラウドを操作するための合鍵）が漏れたら、クラウド上の資源はすべて攻撃者の思いのままです。

    ○ 良い例：必要な操作と、特定の保管場所だけ 
    {
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject"],
  "Resource": "arn:aws:s3:::my-app-uploads/*"
}
    • 必要なアクションのみ（ファイルの取得と保存だけ）
    • 特定のバケット・場所のみ（S3 のバケットはファイルの保管場所）
    • さらに条件（接続元IPの制限、時間帯、MFA＝多要素認証 必須など）も付けられる

    3.4 コンテナ・プロセス

    アプリを動かすプログラム（プロセス）やコンテナにも、最小権限は当てはまります。

    • root で動かさない：root は Linux の「何でもできる」特権ユーザー。非rootユーザーでコンテナを起動する
    • 不要な Linux capability（root の特権を細かく分けたもの）を外す
    • 読み取り専用のファイルシステム でコンテナを起動する
    • seccomp / AppArmor / SELinux で、プログラムが OS に頼める操作（システムコール）を制限する
    ○ 非rootユーザーで実行する Dockerfile 
    # 非rootユーザーで実行
RUN useradd -r -u 1001 appuser
USER appuser

    3.5 CI/CD のトークン

    CI/CD は、コードのテストやデプロイ（本番への反映）を自動で行う仕組みです。その自動処理が使う トークン（合鍵の役割をする文字列）も絞ります。

    ✕ 悪い例

    GitHub Actions のジョブトークンが、リポジトリへの フルアクセス を持っている。

    ○ 良い例：必要な権限だけを宣言する 
    permissions:
  contents: read      # コード読み取り
  issues: write       # Issue への書き込み（必要な場合のみ）
  # その他はデフォルトで拒否

    4.最小権限を実装するパターン

    権限をどう管理するかには、いくつかの定番のやり方があります。組織の規模や成熟度に合わせて、RBAC → ABAC → JIT の順に取り入れていくのが一般的です。

    RBAC（役割ベース）

    役割（Role） に権限をひも付け、ユーザーを役割に割り当てます。「編集者」「管理者」のような役職ごとに鍵束を用意するイメージ。中小規模なら RBAC で十分なことが多いです。

    ABAC（属性ベース）

    ユーザーの所属部署・時間帯・場所などの 属性 で、その都度判定します。「経理部の人が、営業時間中に、MFA済みなら」のような複雑な条件が必要なときに使います。

    PBAC / Policy-as-Code

    ポリシー（ルール）を コードとして管理 し、専用エンジンで判定します。代表例は Open Policy Agent（OPA）。Kubernetes、マイクロサービス、API Gateway で広く使われます。

    JIT（ジャストインタイム）アクセス

    普段は権限ゼロ、必要なときだけ一時的に付与します。「作業開始」ボタン → 承認 → 30分だけ sudo（管理者として実行）可能、のような流れ。PAM（特権アクセス管理）製品や AWS IAM Identity Center などで実現します。

    RBAC のイメージ 
    Role: editor
  - permissions: ["article.read", "article.write"]

Role: admin
  - permissions: ["article.*", "user.*"]

User "alice" → Role "editor"
User "bob"   → Role "admin"
    ABAC のイメージ 
    Allow if user.department == resource.owner_department
       && time.now() in business_hours
       && user.mfa_verified == true

    4.1 権限の棚卸し（アクセスレビュー）

    どの方式を使っても、権限は放っておくと増えていきます。そこで定期的に「このユーザーに本当にこの権限が必要か？」を見直します。これを 棚卸し（Access Review） と呼びます。

    • 四半期に1回、各マネージャーが部下の権限をレビューする
    • 退職者・異動者の権限はすぐに削除する
    • 使われていない権限を自動で見つける（AWS CloudTrail などの操作ログを分析）

    5.最小権限でよくある失敗

    アンチパターン何が起きるか
    「とりあえず admin」開発中に面倒だからとフル権限で始め、そのまま本番に持ち込んでしまう
    共有アカウント複数人で1つのアカウントを使い回す。誰が何をしたか追跡できず、退職時に無効化しにくい
    権限の足し算しかない追加は気軽にするが削除はしない。権限が増える一方になり、気づけば全員がフル権限
    一時権限が恒久化「一時的に admin にするね」が半年後もそのまま
    サービスアカウントに人並みの権限バッチ処理用のアカウントが「念のため」管理者権限を持っている。実際は少しの読み書きで十分

    よくある誤解：「社員を信用していないみたいで失礼」

    最小権限は人を疑うための仕組みではありません。本人に悪意がなくても、パスワードが盗まれたり、端末がウイルスに感染したり、うっかり操作を誤ったりします。そのとき被害を小さくするための「保険」です。むしろ、強すぎる権限を持たされた本人を事故から守る仕組みでもあります。

    6.最小権限を実現する5ステップ

    いきなり全部を絞ろうとすると業務が止まります。次の順で少しずつ進めます。

    1. 現状把握：誰がどの権限を持っているかを見える化し、どの権限が実際に使われているかを監査ログで確認する
    2. ベースラインを決める：役割ごとの 最低限の権限セット を定義し、それ以上は例外として管理する
    3. 権限を縮小する：使われていない権限、「要件として明確でない権限」を削除する（デフォルト拒否：明示的に許可したもの以外はすべて拒否する考え方）
    4. 仕組みで維持する：IaC（Terraform など、インフラ設定をコードで書く仕組み）でポリシーをコード化し、新規ユーザーの初期権限を最小にする。AWS Access Analyzer や IAM Policy Simulator などで自動チェックする
    5. 定期レビュー：四半期に1回の棚卸し、退職・異動時の即時無効化、インシデント（セキュリティ事故）時の権限の振り返り

    6.1 関連する原則

    原則内容
    Need-to-Know（知る必要性）「知る必要のある情報だけ知らせる」。機密情報の閲覧権限に特化した考え方。病院で、担当でない職員はその患者のカルテを開けない、というイメージ
    職務分掌（Separation of Duties）重要な操作を 1人では完結できない ようにする。開発者が単独で本番にデプロイできない、承認者と実行者を別人にする、など
    深層防御1層目の権限制御が破られても、2層目で止める → 深層防御
    ゼロトラスト「社内だから信頼する」をやめ、すべてのアクセスを検証する。最小権限はゼロトラストの基礎 → ゼロトラスト

    7.データ最小化とは

    7.1 定義

    データ最小化（Data Minimization）とは、

    必要なデータだけを、必要な期間だけ持つ

    という原則です。EU の GDPR の基本原則の1つで、日本の個人情報保護法でも「利用目的の達成に必要な範囲」での取り扱いと、不要になったデータの消去（努力義務）が定められています。

    最小権限が「権限」を絞るのに対し、データ最小化は 攻撃者が手にできるデータそのもの を絞ります。どれだけ鍵を厳重にしても、金庫の中身が少なければ盗まれても困りません。

    7.2 なぜ重要なのか：2026年の事例から

    2026年の国内の情報漏洩では、持ち続けていたデータ が被害を大きくした例が目立ちました。

    事例持ちすぎていたもの
    KDDI ISP向けメール基盤解約済みユーザー の情報も残っていた
    タイムズカー運転免許証などの画像 約160万件。パスワードと違い、本人が変更できない
    米国防総省 DMDC（海外）暗号化していない 個人情報をファイル共有システムに置いていた
    各種会員システム退会者を 論理削除（deleted_at に日時を入れるだけ）のまま残していた例が指摘されている

    変えられない情報ほど、持たない

    パスワードは漏れても変更できます。しかし 氏名・生年月日・免許証の画像・口座番号は変えられません。漏れたときの被害が何年も続くため、こうした情報ほど「そもそも持たない」設計が大切です。

    8.データ最小化の4つの観点

    データ最小化は、データの一生（集める → 保存する → 使う → 消す）に沿って4つの観点で考えると整理しやすくなります。

    8.1 集めない（収集の最小化）

    • 入力フォームの各項目について「何に使うのか」を答えられるか確かめる。答えられない項目は削る
    • 年齢確認なら、生年月日ではなく「18歳以上か」だけで足りることもある

    8.2 持たない（保存の最小化）

    • カード情報：決済代行会社が発行する トークン（カード番号の代わりになる無意味な文字列）だけを持つ。カード業界の安全基準 PCI DSS の対象範囲も小さくなる
    • 本人確認書類：eKYC 事業者（オンラインで本人確認を代行する事業者）に確認を任せ、結果（確認済みフラグと日時）だけを持つ。画像が必要なら、確認が終わったら削除する
    • ログ：個人情報や秘密情報を書かない（詳しくは セキュアな運用とログ出力）

    8.3 期限を決めて消す（保存期間の最小化）

    • データの種類ごとに 保存期間 を決める（例：退会者は法定の保存期間を過ぎたら削除、申込み途中のデータは30日で削除）
    • 論理削除ではなく物理削除。論理削除は「削除済み」の印を付けてアプリから見えなくするだけなので、データベースごと盗まれれば全部読める
    • バックアップ、データウェアハウス（分析用のデータ倉庫）、ログ基盤にあるコピーも対象にする

    論理削除

    deleted_at 列に日時を入れ、画面に出さないだけ。書類に「廃棄済み」の付箋を貼って、キャビネットに入れたままにしている状態です。

    物理削除

    行そのものをデータベースから消す。書類をシュレッダーにかけた状態。盗まれても、もう存在しません。

    8.4 分ける・隠す（アクセスの最小化）

    • 機密度の高いデータ（本人確認書類・口座情報）は 会員DBとは別の保管場所 に置き、アクセスできるサービスを限る
    • 項目単位で暗号化する（暗号化の詳細は インジェクションと暗号化の不備）
    • 分析には 仮名化（名前などを別のIDに置き換える）・マスキング（一部を「***」で隠す）したデータを使う。本番データをテスト環境にコピーしない

    9.データ最小化の実装例

    9.1 保存期間を過ぎたデータを消すバッチ

    ○ 期限切れデータを物理削除する SQL 
    -- 退会から 1 年たったユーザーを物理削除する（関連テーブルは ON DELETE CASCADE）
DELETE FROM users
WHERE withdrawn_at IS NOT NULL
  AND withdrawn_at < NOW() - INTERVAL '1 year';

-- 申込みを途中でやめたデータは 30 日で削除する
DELETE FROM applications
WHERE status = 'draft'
  AND updated_at < NOW() - INTERVAL '30 days';
    • 毎日のジョブとして実行し、削除件数をメトリクス（監視用の数値）として記録する
    • 大きなテーブルは日付で パーティション分割 しておき、古いパーティションごと DROP すると速い
    • S3 などのオブジェクトストレージは ライフサイクルルール で自動削除できる

    9.2 本人確認書類を会員DBに置かない

    ✕ 悪い例 
    users テーブルに license_image_url があり、会員 API と同じ権限で読める
    ○ 良い例 
    確認は eKYC 事業者に任せ、users には kyc_verified_at だけを持つ

画像を残す必要があるなら、別アカウントの暗号化ストレージに置き、
参照できるのは審査サービスだけにする。審査が終わったら削除する

    9.3 データ最小化のアンチパターン

    アンチパターンなぜ危ないか
    「いつか分析に使うかも」で全部残す使われないまま、攻撃者にとって価値のあるデータがたまっていく
    論理削除で消したつもりdeleted_at が立っていても、DBを盗まれれば全部読める
    本番データをテスト環境にコピーテスト環境は本番より守りが弱いことが多い
    バックアップだけ永久保存本番から消しても、バックアップに残っている

    10.2026年の事例：権限の広さが被害を決めた

    2026年の国内の情報漏洩では、侵入されたあとに持っていた権限の広さ が被害の大きさを決めた例が多く報告されました（全体像は サプライチェーン攻撃と2026年の事例 も参照）。

    事例権限の問題
    デジタル庁 GSSVPN の脆弱性から侵入され、保守担当者のアカウント で大量のファイルにアクセスされた
    両毛システムズVPN アカウント が悪用され、ランサムウェア被害が委託元の自治体などに波及
    会員システム各種Webサーバーや業務IDを1つ奪われると DB の奥まで届く「フラットな構成」が指摘された
    AIエージェント（研究者の検証）AWS AgentCore の検証で、既定で有効なシェルツールから 実行ロールのトークン が盗まれ、別の MCP サーバーで使い回せた

    事例からの教訓

    • 保守・委託先アカウントは常時有効にしない。作業のときだけ有効にする JIT アクセスにし、届く範囲も作業対象に限る
    • アプリ用DBアカウントが 全件を SELECT できる と、1回の侵入で全会員分が持ち出される。ビューや 行レベルセキュリティ（行ごとに見える人を制限するDBの機能）で絞り、1回の取得件数の上限と組み合わせる（大量取得の検知は ログ不足・SSRF・例外処理）
    • AIエージェント（自分でツールを呼び出して作業するAI）に渡すツールや実行ロールにも最小権限を適用する（プロンプトインジェクションについては 72_Web脆弱性対策 で詳しく）

    11.チェックリスト

    11.1 最小権限

    • アプリ用DBユーザーに DROP / GRANT 権限を与えていないか？
    • クラウドの IAM で "Action": "*" を使っていないか？
    • コンテナを root で動かしていないか？
    • CI/CD トークンの権限は必要最小限か？
    • 共有アカウントを使っていないか？
    • 退職者・異動者の権限は速やかに削除されているか？
    • 定期的な権限棚卸しの仕組みはあるか？
    • 一時権限の期限管理はされているか？
    • 保守用・委託先用のアカウントを、使うときだけ有効にしているか？
    • アプリ用DBアカウントで、全会員を一度に取得できないようにしているか？
    • AIエージェントの実行ロールが必要以上の権限を持っていないか？

    11.2 データ最小化

    • 集めている項目それぞれについて、利用目的を説明できるか？
    • データの種類ごとに保存期間を決めているか？
    • 退会者のデータを物理削除しているか？
    • カード情報をトークン化しているか？
    • 本人確認書類を会員DBと分けているか（または持っていないか）？
    • テスト環境に本番の個人情報を置いていないか？
    • バックアップやログ基盤にも保存期間を適用しているか？

    12.まとめ

    このページの要点

    • 最小権限の原則は 「使わない権限は持たせない」。最大の目的は侵害されたときの被害の最小化
    • 権限は 種類・範囲・期間 の3次元で絞る
    • RBAC → ABAC → JIT の順に、組織の成熟度に合わせて導入し、棚卸し と コード化 で維持する
    • データ最小化は 「持っていないデータは漏れない」。集めない・持たない・期限を決めて消す・分ける の4観点
    • 論理削除では消したことにならない。バックアップやテスト環境のコピーも忘れない
    • 免許証画像のような 変更できない情報 ほど、持たない設計にする

    13.理解度チェック

    Q1. 権限を最小化するときの「3つの次元」とは何ですか？

    種類・範囲・期間 です。何ができるか（例：読み取りだけ）、どこに対してか（例：売上テーブルだけ）、いつまで有効か（例：作業中の30分だけ＝JIT）の3方向で絞ります。

    Q2. 退会者のレコードに deleted_at を入れて画面に出さないようにしました。データ最小化として十分ですか？

    不十分です。 これは論理削除で、データはDBに残っています。DBが盗まれれば全部読めます。保存期間を過ぎたら 物理削除 し、バックアップやデータウェアハウスにあるコピーにも同じ期間を適用します。

    Q3. アプリ用のDBユーザーを root にしておくと、SQLインジェクションを受けたときに何が問題になりますか？

    攻撃者がアプリと同じ権限で命令を実行できるため、データの読み出しだけでなく テーブルの削除（DROP）や権限の付与、場合によってはOSへの侵入 まで許してしまいます。アプリ用ユーザーを SELECT/INSERT/UPDATE/DELETE に絞っておけば、少なくとも入れ物ごと壊される被害は防げます。

    Q4. 最小権限とデータ最小化の違いを一言で説明すると？

    最小権限は「できること（権限）」を絞り、データ最小化は「持っているもの（データ）」を絞ります。前者は鍵を減らすこと、後者は金庫の中身を減らすことにあたります。
