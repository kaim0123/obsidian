    サプライチェーン攻撃と2026年の事例

    自社の守りが固くても、仕事を頼んでいる委託先や、使っている SaaS・ソフトウェアが破られれば情報は漏れます。このページでは、サプライチェーン攻撃 の3つの型と、委託先・SaaS を管理するための対策を学んだうえで、2026年に国内で相次いだ情報漏洩の事例 から共通する原因と、優先すべき対策をまとめます。シリーズの最終ページとして、これまでのページとのつながりも確認します。

    もとにしたノート：50_運用・監視・インシデント / 09_サプライチェーン攻撃と委託先管理、10_2026年_国内情報漏洩の動向と対策

    ひとことで言うと

    「自社が堅くても、つながっている先が弱ければ漏れる」。しかも1か所破られると、つながっている多数の組織に一斉に波及します。そして2026年の事例が教えてくれたのは、高度な攻撃より 既知の穴の放置・データの持ちすぎ・大量取得の見逃し・委託先からの波及 の4つが被害を大きくしたということです。

    1.サプライチェーン攻撃とは

    サプライチェーン とは、もともと「原材料の調達から製造・配送までのつながり」のことです。IT の世界では、自社の仕事を支えている 取引先・委託先・利用している SaaS やソフトウェア のつながり全体を指します。

    サプライチェーン攻撃 とは、狙った組織を直接攻めるのではなく、このつながりのどこかを足がかりに侵入する攻撃です。IPA「情報セキュリティ10大脅威 2026」組織編では 2位 でした。

    たとえば、マンションの住人がどれだけしっかり鍵をかけていても、管理会社が全戸の合鍵をずさんに保管していた ら、泥棒は管理会社から合鍵を盗むだけで全戸に入れてしまいます。しかも玄関は「正規の合鍵」で開くので、防犯カメラに映っても怪しく見えません。

    2.3つの類型と2026年の例

    類型内容2026年の例
    ① 委託先・取引先経由委託先の PC やネットワークに侵入し、預けたデータや接続経路を悪用する第一興商（委託先 PC のマルウェア感染、約872万件のおそれ）、両毛システムズ（伊勢崎市などへ波及）
    ② SaaS・共通基盤経由複数の企業が使う SaaS やクラウド基盤が侵害され、利用企業すべてに被害が出るi-ask 提供元（大和証券・損保ジャパン・シチズン等）、KDDI のメール基盤（ISP 6社が共有）、ショップサーブ（利用店舗に波及）、IDCF クラウド（495組織）
    ③ ソフトウェア経由ライブラリや製品のアップデートに悪意あるコードが混ざる、または製品の脆弱性が突かれるKDDI（第三者製ソフトのゼロデイ）。npm パッケージの乗っ取りなどもこの類型（→ サプライチェーンと整合性の不備）

    用語メモ：SaaS（Software as a Service）は、インターネット越しに使うソフトウェアのサービスのこと。委託先 は、自社の業務の一部（開発・保守・運用など）を請け負っている会社のことです。

    3.なぜ防ぎにくいのか

    見えない

    委託先の中のセキュリティ状況は、外から確かめにくい。管理会社の金庫の中までは住人には見えません。

    信頼された経路

    委託先の VPN や API キーは 正規の接続 なので、攻撃に使われても目立たない。

    通知が遅れる

    委託先が被害に気づいても、委託元への連絡に時間がかかる（両毛システムズでは 43日）。

    規模の差

    委託先の多くは中小企業で、セキュリティにかけられる予算や人員が限られる（ランサムウェア被害の約6割は中小企業）。

    4.委託先・SaaS を守るための対策

    4.1 契約で決めておく

    委託先の中は見えないので、「何をしてもらうか」を事前に約束しておく ことが出発点です。

    項目例
    インシデントの通知期限「発覚から 24時間以内 に第一報」
    最低限の技術要件MFA 必須、パッチ適用 SLA、EDR 導入、ログを一定期間保管
    再委託の制限再委託（委託先がさらに別の会社に仕事を出すこと）をするときは事前に承認を取る
    監査・報告年1回のチェックシート、必要に応じて立ち入り監査
    契約終了時のデータ削除と、削除したことの証明

    4.2 渡すデータと権限を減らす

    • 委託先に渡すデータは 業務に必要な項目だけ にする（データ最小化）。テストには本番データを使わず、マスキング（氏名などを伏せ字にする加工）したものを渡す。
    • 委託先からの接続は 期間・範囲を限った一時的な権限 にする（最小権限）。保守用 VPN を常時つなぎっぱなしにしない。
    • API 連携は スコープ（できることの範囲）を絞った短命トークン を使い、長期間有効な共有キーを避ける。
    ✕ よくある危ない状態 
    保守会社の VPN アカウント：常時有効・全サーバーに接続可・MFA なし
委託先に渡したデータ：本番の顧客データを丸ごとコピー
API キー：何年も同じ共有キー
    ○ 改善後 
    保守会社の VPN アカウント：作業日だけ有効化・対象サーバーのみ・MFA 必須
委託先に渡したデータ：必要な項目だけ、テストはマスキング済みデータ
API 連携：用途を絞った短命トークン

    4.3 SaaS の選定と運用

    • SSO（シングルサインオン）・MFA・監査ログの出力・IP 制限ができるかを、選ぶときの条件にする。
    • ISMAP（政府のクラウドサービス評価制度）や SOC 2（外部監査人によるセキュリティ評価報告）などの第三者認証を確かめる。
    • SaaS 側が侵害されたときに 自社のどのデータが影響を受けるか を一覧にしておく。

    4.4 経産省「SCS 評価制度」

    経済産業省の サプライチェーン強化に向けたセキュリティ対策評価制度（SCS 評価制度）は、取引先のセキュリティ対策を ★ で表す任意の制度です。ホテルの星のように、取引先の対策レベルを共通の物差しで比べられるようにするものです。

    レベル想定する攻撃評価の方法
    ★3脆弱性を悪用する一般的な攻撃専門家の確認付き自己評価
    ★4供給停止や情報漏洩など、大きな影響を与える攻撃第三者評価

    申請受付は令和8年度末（2027年1〜3月）ごろの予定です（経産省 FAQ、2026年3月時点）。

    4.5 ソフトウェアサプライチェーン

    • SBOM（ソフトウェア部品表）で使っているコンポーネントを把握する（→ 古い部品）。
    • 依存パッケージのバージョンを固定し、署名や来歴（SLSA：ソフトウェアがどこでどう作られたかを確かめる枠組み）を確かめる。

    • アフラック生命：攻撃者のアクセスは「普通の利用と同じ形式」でした。1件ずつ見ると正常なので、量やスピードの異常 を見る仕組みがないと気づけません。

    • KDDI：解約済みユーザーのデータも残っていたと報告されています。要らなくなったデータを消していれば、漏れる量は減らせました。

    7.共通する問題点と、学んできたページとのつながり

    事例を並べてみると、2026年の被害の多くは このシリーズで学んできた基本 の抜けから起きていました。

    #共通する問題点関連するページ・ノート
    1境界機器（VPN/RDP）と第三者製ソフトの脆弱性放置脆弱性管理とランサムウェア対策 ／ 古い部品
    2侵入後は「正規の操作」に見える（盗んだ ID・正規 API の悪用）ログ不足 ／ セキュリティ監視 ／ Web API の脆弱性は 72_Web脆弱性対策 で詳しく
    3SaaS・共通基盤・委託先からの波及このページの1〜4章
    4データの持ちすぎ（退会者データ、免許証画像、平文保存）データ最小化 ／ 暗号化の不備
    5フラットなネットワークと過剰な権限最小権限 ／ 深層防御 ／ ゼロトラスト
    6AI エージェントという新しい攻撃面プロンプトインジェクションのノート（別フォルダ）
    7MFA を突破するソーシャルエンジニアリング（人をだます手口）二要素認証（2FA）のノート（別フォルダ）／ さまざまな脅威

    「フラットなネットワーク」とは、社内が区切られておらず、1台に入られるとどこへでも行ける状態のこと。家にたとえると、玄関を入ったら全部屋の扉に鍵がない家です。

    8.対策マップ（優先度順）

    優先対策詳しくは
    A. 入口を減らすVPN/FW/ファイル転送製品のパッチ SLA（KEV 掲載は48〜72h）、EOL の洗い出し、VPN に MFA、RDP 非公開、ASM脆弱性管理
    B. 被害半径を小さくする最小権限・セグメント分離・本人確認書類の分離・項目暗号化・保持期間を過ぎたら物理削除最小権限とデータ最小化
    C. 正規に見える攻撃を検知1セッションあたりの取得件数・エクスポート量の監視と自動遮断、外向き通信監視、MTTD（平均検知時間）を KPI にログ不足 ／ ログ出力
    D. サプライチェーン委託先の通知期限・MFA・パッチ SLA を契約に、渡すデータの最小化、SCS 評価制度（★3/★4）このページの4章
    E. AI・エージェントツールの許可リスト、実行ロールの最小権限、外部入力は信頼しない、外向き通信の制限プロンプトインジェクションのノート
    F. ランサムウェアイミュータブルで別アカウントのバックアップ、復元テスト、AD 防御、EDR、IR（インシデント対応）訓練ランサムウェア対策
    G. 事後対応証拠保全、個人情報保護委員会への報告（速報・確報）、段階的な公表インシデント対応の基本フローのノート

    2026年の教訓

    「高度な攻撃への備え」より、既知の穴の放置・データの持ちすぎ・大量取得の見逃し・委託先からの波及 の4点。侵入をゼロにする設計から、侵入されても届く範囲を小さくし、早く気づく設計へ。

    よくある誤解：「うちは小さい会社だから狙われない」

    ランサムウェア被害の約6割は中小企業です。しかも委託先として大企業や自治体のデータを預かっていれば、そこが入口として狙われ、取引先にまで被害が広がります。規模に関係なく、入口の穴をふさぐことが基本です。

    11.まとめ

    このページの要点

    • サプライチェーン攻撃は 委託先・SaaS/共通基盤・ソフトウェア を経由する攻撃。1か所破られると多数の組織に波及する
    • 2026年は特に SaaS・共通基盤 から多数の組織に広がる被害が目立った
    • 対策の柱は 契約（通知期限・技術要件）、渡すデータと権限の最小化、接続経路の管理。経産省の SCS 評価制度（★3/★4）が共通の物差しになる見込み
    • 2026年の事例の多くは、高度な攻撃ではなく 既知の穴・データの持ちすぎ・大量取得の見逃し・委託先からの波及 が原因
    • 被害は「時間 × 届くデータ量」で大きくなる。入られても届く範囲を小さく、早く気づく 設計へ

    12.理解度チェック

    Q1. 多くの会社が使っている問い合わせ管理 SaaS が侵害され、利用企業すべてで情報が漏れた。これはどの類型？

    ② SaaS・共通基盤経由 です。2026年の i-ask 提供元の事例がこれにあたります。対策としては、SaaS を選ぶときに SSO・MFA・監査ログ・IP 制限が使えるか、第三者認証（ISMAP・SOC 2 など）があるかを確かめ、侵害時に自社のどのデータが影響を受けるかを一覧にしておきます。

    Q2. 保守会社の VPN アカウントについて、改善すべき点を3つ挙げてください（現状：常時有効・全サーバーに接続可・MFA なし）。

    ①使うときだけ有効にする（期間を限る）、②接続できる範囲を作業対象に絞る（最小権限）、③MFA を必須にする。あわせて、契約にインシデントの通知期限（例：発覚から24時間以内に第一報）を書いておきます。

    Q3. アフラック生命の事例で、攻撃に気づくのが遅れた理由と、必要だった対策は？

    アクセスが 通常の利用と同じ形式 だったため、1件ずつ見ても異常に見えず、短時間の大量照会を監視・制御する機能が不足 していたと報告されています（CPU 高負荷で発覚、侵入から15日後）。1セッションあたりの取得件数やエクスポート量を監視し、しきい値を超えたら自動で遮断する仕組みが有効です（対策マップの C）。

    Q4. 「侵入をゼロにする設計から、〇〇設計へ」。2026年の教訓の〇〇に入るのは？

    「侵入されても届く範囲を小さくし、早く気づく」 設計です。ゼロデイのように防ぎきれない攻撃もあるため、データ最小化・最小権限で被害の「高さ」を、監視と検知で被害の「横幅（時間）」を小さくします。
