    20 責務の割り当て

    ドメインを表すクラス — エンティティ・値オブジェクト・集約

    業務をコードに写す「ドメインモデル」の基本要素である、エンティティ・値オブジェクト・集約を、クラス設計の視点で解説します。業務ルールをどのクラスに置くか、狭い関心事に特化した小さなクラスの作り方も扱います。

    もとにしたノート：20_責務の割り当て/03_ドメインを表すクラス

    ひとことで言うと

    エンティティ は ID で同一性を判断し、値オブジェクト は値で等しさを判断する不変のもの、集約 は整合性を保つクラスのまとまりです。業務ルールはサービスではなく ドメインクラスの中 に置き、クラスは 1つの関心事 に絞ります。

    1.このページで扱うこと

    業務をコードに写す ドメインモデル（業務の概念とルールをクラスで表したもの）の基本要素を学びます。DDD（ドメイン駆動設計）としての詳しい位置づけは 42章：エンティティと値オブジェクト・42章：集約とリポジトリ で扱っており、このページは クラスとしてどう書くか に焦点を当てます。

    2.エンティティ（Entity）— 同一性を持つもの

    エンティティ は ID で区別される オブジェクトです。属性が変わっても「同じもの」として追跡します。

    class Order {
  constructor(id) {
    this.id = id;  // 同一性の鍵
    this.status = 'DRAFT';
  }
  confirm() {
    if (this.status !== 'DRAFT') throw new Error('確定済み');
    this.status = 'CONFIRMED';
  }
}
    特徴例
    同一性（ID）注文番号、ユーザーID
    ライフサイクル作成→確定→配送→完了
    ミュータブル状態が変わる

    ミュータブル（mutable）は「作った後に中身を変えられる」という意味です。

    3.値オブジェクト（Value Object）— 値で比較するもの

    値オブジェクト は 属性の値で等価性 を判断します。ID は持ちません。

    class Money {
  constructor(amount, currency) {
    if (amount < 0) throw new Error('負の金額');
    this.amount = amount;
    this.currency = currency;
  }
  add(other) {
    if (this.currency !== other.currency) throw new Error('通貨不一致');
    return new Money(this.amount + other.amount, this.currency);
  }
}
    特徴例
    不変（immutable）変更時は新インスタンス
    値で比較1000円と1000円は同じ
    ルールを内包通貨・丸め・範囲

    詳細は 42章：エンティティと値オブジェクト を、クラスとしての書き方は 値オブジェクトと完全コンストラクタ を参照してください。

    4.エンティティと値オブジェクトの使い分け

    問いエンティティ値オブジェクト
    同じものの追跡が必要？YesNo
    属性が変わっても同一？ID で Yes値が変われば別物
    例Customer, OrderMoney, Address, DateRange

    住所は「同じ建物でも表記が変われば別値」として値オブジェクトにすることが多いです。

    5.集約（Aggregate）とクラス境界

    集約 は、整合性を保つ クラスのまとまり です。集約ルート（まとまりの代表となるクラス）だけが外部から触られ、内部はルート経由で操作します。

      Order（ルート）
    ├── OrderLine
    └── ShippingAddress（値オブジェクト）

  外部は Order 経由のみ。Line を直接追加させない。
    class Order {
  addLine(product, qty) {
    this._lines.push(new OrderLine(product, qty));
    this._validate();  // 集約全体の不変条件
  }
}

    不変条件 とは、「明細は1件以上」のように、集約が常に満たしていなければならないルールのことです。ルート経由で操作させることで、変更のたびに必ずチェックできます。DDD での詳しい扱いは 42章：集約とリポジトリ も参照してください。

    6.ドメインルールをクラスに置く

    業務ルールは ドメインクラスの中 に置きます。

    ルール置き場所
    注文は空で確定できないOrder.confirm()
    割引は0〜100%Discount 値オブジェクト
    在庫不足で注文不可Order または Inventory
     
    class Order {
  confirm(inventory) {
    if (this.lines.length === 0) throw new Error('明細なし');
    if (!inventory.canFulfill(this)) throw new Error('在庫不足');
    this.status = 'CONFIRMED';
  }
}

    サービス層にロジックを逃がすと 貧血モデル になります（クラス分割の基本プロセス）。

    7.狭い関心事に特化したクラス（ドメインオブジェクト）

    関連する業務データと業務ロジックを、1つの関心事だけ に絞ったクラスにまとめたものを、増田亨『現場で役立つシステム設計の原則』では ドメインオブジェクト と呼びます（業務の用語とクラス名を一致させる）。

    例：送料に関する値と計算だけを持つ ShippingCost。送料と無関係な処理は入れません。

    class ShippingCost {
  private constructor(readonly amount: number) {}

  static forBasePrice(basePrice: number): ShippingCost {
    return new ShippingCost(basePrice < 3000 ? 500 : 0);
  }
}

    （TypeScript で書いています。private constructor は外から new できないようにする書き方で、生成は forBasePrice からだけになります。）

    やること効果
    関心事ごとに小さなクラスを切る変更箇所がクラス名から辿れる
    クラス名を業務用語にする「送料のルールを変えたい」→ ShippingCost を開く
    関係ないロジックを入れないクラスが大きくなりにくい

    値そのものを専用クラスにする話は 値オブジェクトと完全コンストラクタ、一覧のルールを閉じ込める話は オブジェクトの種類の整理 のコレクションオブジェクトを参照してください。

    8.よくある誤解

    誤解1：「住所や金額にも ID を付けてエンティティにしておけば安全」

    同じものを追跡する必要がないなら値オブジェクトにします。値オブジェクトは不変で値で比較できるので、扱いが単純になります。住所も「表記が変われば別値」として値オブジェクトにすることが多いです。

    誤解2：「集約の内部のクラスも、必要なら外から直接操作してよい」

    内部を直接触らせると、集約全体の不変条件をチェックする機会がなくなります。外部は 集約ルート経由のみ にし、OrderLine の追加も Order.addLine() を通します。

    誤解3：「業務ルールはサービス層にまとめるのが整理された設計」

    ドメインルールはクラス内に置き、サービスはオーケストレーション（呼び出しの順序づけ）に徹します。サービスにルールを逃がすと貧血モデルになります。

    9.まとめ

    • エンティティ = ID で同一性、値オブジェクト = 値で等価・不変
    • 集約ルートが整合性の窓口
    • ドメインルールはクラス内に。サービスはオーケストレーション
    • 狭い関心事に特化した小さなクラス（ドメインオブジェクト）にすると、変更の影響を閉じ込めやすい
