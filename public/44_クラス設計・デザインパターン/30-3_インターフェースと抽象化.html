    インターフェースと抽象化 — 具象に依存しないクラスを作る

    インターフェースは「何ができるか」の約束ごとです。抽象クラスとの使い分け、依存性逆転の原則（DIP）、具象クラスに依存しないためのチェックポイント、テストのしやすさとの関係を、注文の保存処理の例で解説します。

    もとにしたノート：30_クラスの関係/03_インターフェースと抽象化

    ひとことで言うと

    インターフェース で「何ができるか」だけを約束し、使う側はその約束（抽象）にだけ依存させます。そうすると、DB・メモリ・モックなどの 実装を差し替えられ、テストもしやすくなります。

    1.このページで扱うこと

    このページでは、インターフェース と 抽象化（細かい中身を隠して、使う側に必要な形だけを見せること）を通じて、具象（実際に動く具体的なクラス）に依存しないクラス設計を学びます。DIP・テスト容易性との関係も押さえます。

    • インターフェースの役割：契約の明示・実装の差し替え・結合度の低減
    • 抽象クラスとインターフェースの使い分け
    • 依存性逆転の原則（DIP）：依存の向きを抽象へ
    • 具象に依存しないクラス設計：チェックポイントと例
    • テスト容易性との関係：テストダブルを差し込む

    このページの範囲

    このページは「クラス設計でどう使うか」を扱います。DIP そのものの説明は 48_原則 のノート『05_DIP (依存性逆転の原則)』と、41章の 依存性逆転の原則 を参照してください。

    2.インターフェースの役割

    インターフェース は「何ができるか」の 契約（使う側と作る側が守る約束ごと）を定義します。実装の詳細は隠します。

    interface OrderRepository {
  save(order: Order): void;
  findById(id: string): Order | null;
}

    OrderRepository（リポジトリ＝注文の保存・取り出しを受け持つ役）は「保存できる」「ID で探せる」という操作だけを約束しています。MySQL に保存するのか、メモリに置くのかは書かれていません。

    役割効果
    契約の明示呼び出し側が知るべき操作がはっきり
    実装の差し替えDB・メモリ・モックを入れ替え可能
    結合度の低減具象クラスに依存しない

    多態（同じ呼び方で、中身の違う処理を動かすこと）とインターフェースの一般論は、42章の 多態とインターフェース を参照してください。

    3.抽象クラスとインターフェースの使い分け

    抽象クラス は、一部のメソッドだけ中身を空けておき、残りは共通の実装を持てるクラスです。それ自体は new できず、継承して使います。

    観点抽象クラスインターフェース
    状態の共有共通フィールドを持てる通常は持たない
    多重継承1つのみ（言語による）複数実装可能
    向く場面共通実装 + 一部抽象能力の契約だけ
     
      共通の骨格がある → 抽象クラス（Template Method）
  能力の差し替えだけ → インターフェース

    Template Method は、処理の流れ（骨格）を親クラスに書き、一部の手順だけを子クラスに任せるデザインパターンです（振る舞いパターン）。

    4.依存性逆転の原則（DIP）

    DIP：上位の方針は下位の詳細に依存すべきでない。両方とも 抽象 に依存する。

    ここでの「上位の方針」は注文を受けるといった業務の処理（OrderService）、「下位の詳細」は MySQL への保存のような技術的な処理（MySqlOrderRepository）です。

      悪い:  OrderService → MySqlOrderRepository（具象）
  良い:  OrderService → OrderRepository（抽象）← MySqlOrderRepository
    class OrderService {
  constructor(repository) {  // 抽象（インターフェース）に依存
    this.repository = repository;
  }
}

    OrderService は、どの実装が渡されるかを知りません。外から渡してもらうこの方法を DI（依存性注入） と呼びます（41章の DI・IoC・Composition Root）。SOLID 全体とのつながりは SOLIDの統合と判断 で扱います。

    5.具象に依存しないクラス設計

    具象依存を避けるチェックポイント：

    • ☐ new をビジネスクラス（業務のルールを書くクラス）の中で直接書いていないか
    • ☐ 外部 API・DB の型がドメイン（業務そのものを表す部分）に漏れていないか
    • ☐ 設定・環境で変わるものは抽象の裏に隠しているか
    ✕ 悪い — ドメインが MySQL を知る 
    class Order {
  save() { new MySqlClient().insert(this); }
}
    ◯ 良い — 永続化は Repository に委譲 
    class OrderService {
  save(order) { this.repository.save(order); }
}

    悪い例では、Order の中で new MySqlClient() しているため、DB を変えるたびに業務のクラスを直すことになります。良い例では、永続化（データを保存して残すこと）を Repository に任せています。

    6.テスト容易性との関係

    抽象化は テストダブル（テストのときに本物の代わりに使う偽物の部品）を差し込む前提です。

    class InMemoryOrderRepository {
  save(order) { this.store.set(order.id, order); }
}

// テスト
const repo = new InMemoryOrderRepository();
const service = new OrderService(repo);
    具象依存抽象依存
    DB がないとテスト不可メモリ実装で単体テスト
    外部 API を叩くスタブ（決まった値を返すだけの偽物）で応答を固定

    詳細は テストしやすいクラス設計 を参照してください。

    7.よくある誤解

    誤解1：「インターフェースは、とにかくたくさん作るほどよい」

    インターフェースは、実装を差し替えたい場所（DB・外部 API・設定や環境で変わるもの）に置くものです。差し替える予定もない場所まで抽象化すると、読むファイルが増えるだけになります。どこまで抽象化するかの判断は SOLIDの統合と判断（DIP vs 直書き）も参照してください。

    誤解2：「抽象クラスとインターフェースはどちらでも同じ」

    抽象クラスは共通のフィールドや実装（骨格）を持てますが、継承できるのは通常1つだけです。インターフェースは能力の契約だけを表し、1つのクラスが複数を実装できます。共通の骨格があるなら抽象クラス、能力の差し替えだけならインターフェース、と使い分けます。

    誤解3：「テストのしやすさのために抽象化する」

    ノートのまとめのとおり、テスト容易性は抽象化の 副産物 です。本来の目的は、使う側を実装の詳細から切り離し、差し替えられるようにすることです。その結果としてテストダブルも差し込めるようになります。

    8.まとめ

    • インターフェースは契約。実装を隠して差し替え可能に
    • 抽象クラスは共通骨格、インターフェースは能力の契約
    • DIP で依存の向きを抽象へ
    • テスト容易性は抽象化の副産物

    次は、SOLID の第一原則 単一責任の原則 に進みます（その前に 継承より合成 もどうぞ）。
