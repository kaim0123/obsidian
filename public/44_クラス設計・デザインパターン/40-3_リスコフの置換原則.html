    40 SOLIDの適用

    リスコフの置換原則（LSP） — 子クラスは親の代わりになれるか

    親クラスの変数に子クラスのオブジェクトを入れても、プログラムが正しく動き続けるか。リスコフの置換原則を、継承階層の契約（事前条件・事後条件・不変条件）、正方形と長方形などの典型的な違反、振る舞いの継承とデータの継承の注意点、LSP を守るための設計判断で解説します。

    もとにしたノート：40_SOLIDの適用/03_リスコフの置換原則

    ひとことで言うと

    リスコフの置換原則（LSP） は「子クラスは、親クラスの 契約を守ったまま 親の代わりに使えなければならない」という原則です。守れないなら継承をやめ、インターフェース + 合成 に切り替えます。

    1.このページで扱うこと

    このページでは リスコフの置換原則（Liskov Substitution Principle, LSP） を学び、継承階層の契約を守る設計判断を身につけます。違反の典型例と、振る舞い継承の注意点を押さえます。名前は、この考え方を示した計算機科学者バーバラ・リスコフに由来します。

    • 子クラスは親の代わりになれる
    • 継承階層の契約：事前条件・事後条件・不変条件
    • LSP 違反の典型例：正方形と長方形、例外の変更
    • 振る舞いの継承とデータの継承
    • LSP を守るための設計判断

    このページの範囲

    このページは「クラス設計でどう使うか」を扱います。原則そのものの説明は 48_原則 のノート『03_LSP (リスコフの置換原則)』を参照してください。

    2.子クラスは親の代わりになれる

    LSP：親型の変数に子型のオブジェクトを代入しても、プログラムの正しさが保たれるべき。

    function printArea(shape) {
  console.log(shape.area());  // Rectangle でも Square でも動くべき
}

    子が親の 期待する振る舞いを壊す と LSP 違反です。

    3.継承階層の契約（Contract）

    契約 とは、メソッドを呼ぶ側と実装する側の間の約束ごとです。契約には次が含まれます。

    要素内容
    事前条件呼び出し前に満たすべき条件（子は緩めてよい）
    事後条件呼び出し後に保証すること（子は強めてよい）
    不変条件常に真であるべき性質

    子が事前条件を厳しくしたり、事後条件を弱めたりすると、親を前提に書いた呼び出し側が困ります。

      親: withdraw(amount) — 残高以上は引き出せない
  子: 無制限に引き出せる → 契約違反（LSP 破壊）

    4.LSP 違反の典型例

    4.1 正方形と長方形

    ✕ 正方形が長方形を継承する 
    class Rectangle {
  setWidth(w) { this.width = w; }
  setHeight(h) { this.height = h; }
}
class Square extends Rectangle {
  setWidth(w) { this.width = this.height = w; }  // 長方形の契約を破る
}

    Rectangle として使うと面積計算がおかしくなります。たとえば「幅を 5、高さを 4 にすれば面積は 20」と期待して書いたコードに Square を渡すと、幅を変えたときに高さも変わってしまい、期待どおりになりません。継承ではなく別の型 + 共通インターフェース が安全です。

    4.2 例外の変更

    親は返す、子は例外を投げる — 呼び出し側の想定を壊します。

    5.振る舞いの継承とデータの継承

    種類リスク
    データ継承フィールドの意図しない共有
    振る舞い継承メソッドのオーバーライドで契約破壊

    継承は実装の共有手段ではなく、契約の特化手段 と捉えます。コード再利用だけなら 合成 を選びます（継承と多態、継承より合成）。

    6.LSP を守るための設計判断

    • 子を親の型として テストで置き換え てみる
    • 「is-a」が言語レベルだけでなく 振る舞いレベル でも成り立つか確認
    • 疑わしい継承は インターフェース + 合成 に変更
    • 深い階層はフラット化を検討
    ◯ 継承しない — 共通インターフェースで別々に実装 
    interface Shape { area(): number; }
class Rectangle implements Shape { /* */ }
class Square implements Shape { /* */ }  // 継承しない

    7.よくある誤解

    誤解1：「現実世界で is-a なら、継承してよい」

    数学では正方形は長方形の一種ですが、プログラムの Square は Rectangle の「幅と高さを別々に変えられる」という契約を守れません。is-a は言語や現実のレベルだけでなく、振る舞いのレベル で成り立つかを確かめます。

    誤解2：「コードを使い回したいから継承する」

    継承は実装の共有手段ではなく、契約の特化手段です。再利用目的の継承は、オーバーライドで契約を壊したり、フィールドを意図せず共有したりする危険があります。コード再利用だけなら合成を検討します。

    誤解3：「子クラスで例外を投げるのは自由」

    親が値を返す約束のメソッドで、子だけが例外を投げると、親を前提に書いた呼び出し側の想定が壊れます。これも典型的な LSP 違反です。

    8.まとめ

    • LSP = 子は親の代わりに使える（契約を守る）
    • 事前・事後条件・不変条件を意識
    • 正方形/長方形、例外の変更が典型違反
    • 再利用目的の継承は危険。合成を検討
