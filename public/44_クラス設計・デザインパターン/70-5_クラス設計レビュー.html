    70 品質と運用

    クラス設計レビュー — 進め方・チェックリスト・改善提案の書き方

    大きな構造の変更は、コードを書き終えてからではなく、設計レビューで先に合意しておくと手戻りが減ります。クラス設計レビューの進め方、重点チェックリスト、注文確定を例にした良い設計と悪い設計の比較、伝わる改善提案の書き方を解説し、この教材全体をまとめて次の学習につなげます。

    もとにしたノート：70_品質と運用/05_クラス設計レビューの実践

    ひとことで言うと

    設計レビューは 文脈 → 全体 → 詳細 → まとめ の順に、約35分で進めます。チェックリストで見落としを防ぎ、良い設計と悪い設計を並べて「なぜ」を共有します。指摘は 現象 → 影響 → 提案 の順に書き、批判ではなく 次の一歩 を示します。

    2.クラス設計レビューの進め方

    段階内容時間目安
    1. 文脈要件・変更の背景5分
    2. 全体クラス図・パッケージ10分
    3. 詳細争点のあるクラス15分
    4. まとめ指摘・合意・フォロー5分

    事前

    クラス図 or 主要クラス名リストを共有

    当日

    「なぜこの分割か」を説明させる

    事後

    改善チケットを1〜3件に絞る

    クラス図の書き方は 参考図解 にテンプレートがあります。

    コードレビュー（PR ごとに差分を見るレビュー）と併用し、大きな構造変更 は設計レビューで先に合意します。コードを書き終えてから構造を否定されると、大きな手戻りになるからです。設計レビュー全般は レガシーと設計レビュー（42章） でも扱っています。

    3.レビュー用チェックリスト

    クラス設計チェックリスト（付録B） をベースに、レビュー時は次を重点確認します。

    • ☐ SRP：変更理由は1つか（単一責任の原則）
    • ☐ 凝集・結合：God Class / 循環依存はないか（凝集度と結合度）
    • ☐ カプセル化：不変条件はクラス内か（カプセル化と情報隠蔽）
    • ☐ 継承：is-a が成立しているか。深すぎないか（継承と多態）
    • ☐ DIP：ドメインが DB・フレームワークを知っていないか（インターフェースと抽象化）
    • ☐ テスト：ドメインを単体テストできるか（テストしやすいクラス設計）
    • ☐ 命名：ユビキタス言語と一致しているか（命名とクラス構成）

    is-a：「子は親の一種である（犬は動物の一種）」という関係。継承はこれが成り立つときだけ使います。

    4.良い設計・悪い設計の比較

    4.1 注文確定の例

    ✕ 悪い設計

    class OrderService {
  confirm(orderId) {
    const order = db.query('SELECT ...');
    if (order.lines.length === 0) return;
    stripe.charge(order.total);
    db.query('UPDATE ...');
    sendMail(order.email);
  }
}
    問題責務混在・DB/Stripe/メール直結・テスト困難

    1つのメソッドが DB の読み書き、業務ルール（明細が空なら確定しない）、決済サービス Stripe への課金、メール送信をすべて直接行っています。テストするには本物の DB と Stripe が必要です。

    ◯ 良い設計

    class Order {
  confirm(inventory) { /* ルール */ }
}
class PlaceOrderUseCase {
  execute(orderId) {
    const order = this.repo.findById(orderId);
    order.confirm(this.inventory);
    this.repo.save(order);
    this.notifier.notify(order);
  }
}
    改善ドメイン分離・依存注入・テスト可能

    業務ルールは Order.confirm() に、保存は repo、通知は notifier に分かれ、PlaceOrderUseCase はそれらを順に呼ぶだけになりました。repo や notifier は外から注入されるので、テストでは偽物に差し替えられます。この形の全体は ケーススタディ で組み立てます。

    5.改善提案の書き方

    レビューコメントは 現象 → 影響 → 提案 の順が伝わりやすいです。

    ## 指摘: OrderService が永続化と決済を直接実行している

**影響**: 単体テストに DB と Stripe が必要。変更が連鎖する。

**提案**:
1. `Order.confirm(inventory)` にルールを移動（貧血モデル解消）
2. `OrderRepository`, `PaymentGateway` インターフェースを注入
3. まず `Order` のテストを1本追加してから Extract

**優先度**: 高（次の支払い方法追加前）

    提案に「まずテストを1本追加してから」と手順まで書き、優先度には「次の支払い方法追加前」という期限の理由を添えています。貧血モデルについては Tell, Don't Ask と貧血モデル、段階的な Extract は 変更に強いクラス設計 を参照してください。

    批判ではなく次の一歩

    「この設計はダメ」で終わらせず、次の一歩 を示します。

    6.次の学習ステップ

    次は ケーススタディ（注文管理システム） で総合演習に進んでください。復習には 用語集と推奨図書（付録A・付録G） を活用してください。

    7.よくある誤解

    誤解1：「コードレビューがあれば、設計レビューは要らない」

    コードレビューは書き終えた差分を見るので、クラスの分け方そのものを否定すると大きな手戻りになります。大きな構造変更は、クラス図や主要クラス名のリストの段階で設計レビューを行い、先に合意しておきます。

    誤解2：「指摘はたくさん出すほど良いレビュー」

    指摘が多すぎると、どれから直せばよいか分からず、結局どれも直りません。事後の改善チケットは1〜3件に絞り、優先度を付けます。

    誤解3：「問題点を指摘すれば、直し方は書いた人が考える」

    現象だけを指摘すると批判に聞こえます。影響（何が困るか）と、具体的な手順の提案までセットで書くと、相手が次の一歩を踏み出せます。

    8.まとめ

    • 設計レビューは文脈→全体→詳細→合意の流れ
    • チェックリストで見落としを防ぐ
    • 良悪比較で「なぜ」を共有
    • 改善提案は影響と具体手順を書く
