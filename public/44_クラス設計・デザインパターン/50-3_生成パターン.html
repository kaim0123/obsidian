    生成パターン — オブジェクトの「作り方」を工夫する5つの型

    new Foo() の書き方を工夫すると、作るクラスを後から変えたり、複雑な組み立てを読みやすくしたりできます。GoF の生成パターン5種（Factory Method・Abstract Factory・Builder・Prototype・Singleton）を、解決する問題・使いどころ・コード例で解説します。

    もとにしたノート：52_生成/01_生成に関するパターン

    ひとことで言うと

    生成パターン は「どう作るか」の問題を解くパターンです。条件で作るクラスを切り替えるなら Factory Method、関連する部品をそろえて作るなら Abstract Factory、引数が多いなら Builder、複製なら Prototype、1つだけなら Singleton（ただし慎重に）を選びます。

    1.このページで扱うこと

    オブジェクト指向では new Foo() でオブジェクトを作りますが、実はこの 作り方 を工夫することで、コードは格段に柔軟になります。

    • 作るクラスを後から変更できる
    • 複雑な組み立てを分かりやすくできる
    • いつ・どのように作るかを制御できる

    こうした「どう作るか」の問題を解くのが 生成に関するパターン です。パターン全体の位置づけは GoFパターンの概要 を参照してください。

    2.GoFの生成パターン5種

    パターン目的
    Factory Methodどのクラスを作るかサブクラスに委ねる
    Abstract Factory関連するオブジェクト群をまとめて作る
    Builder段階的に複雑なオブジェクトを組み立てる
    Prototype既存オブジェクトの複製を作る
    Singletonインスタンスを1つに制限する

    3.Factory Method（ファクトリーメソッド）

    3.1 何を解決するか

    「new を直接書くと、どのクラスを作るかが ハードコード（コードに直接書き込まれて固定）されて、変更しにくい」問題。

    3.2 使いどころ

    • 作るクラスを、条件によって切り替えたい
    • 作り方のロジックをまとめたい
    • テスト時に別のクラスを差し込みたい

    3.3 例：通知方法の切り替え

    ✕ 悪い例 
    // 悪い例
function notify(type, message) {
  if (type === 'email') new EmailNotifier().send(message);
  if (type === 'sms') new SMSNotifier().send(message);
}
    ◯ 良い例：Factory Method 
    // 良い例: Factory Method
class NotifierFactory {
  static create(type) {
    if (type === 'email') return new EmailNotifier();
    if (type === 'sms') return new SMSNotifier();
    if (type === 'slack') return new SlackNotifier();
    throw new Error('unknown');
  }
}

const notifier = NotifierFactory.create('email');
notifier.send('hello');

    new Foo() を呼ぶ場所が 1カ所にまとまる ので、新種追加が容易になります。

    補足：GoF の Factory Method との違い

    上の例のように、1つのメソッドの中で条件分岐して作り分ける形は、厳密には Simple Factory（単純なファクトリー）と呼ばれることがあります。GoF の Factory Method は、表にあるとおり「どのクラスを作るか」を サブクラスがメソッドを上書きして決める 形です。

    class NotificationService {
  createNotifier() { throw new Error('サブクラスで実装'); } // ← Factory Method
  notify(message) { this.createNotifier().send(message); }
}
class EmailNotificationService extends NotificationService {
  createNotifier() { return new EmailNotifier(); }
}

    どちらも「new する場所を呼び出し側から切り離す」という狙いは同じです。

    4.Abstract Factory（抽象ファクトリー）

    4.1 何を解決するか

    「関連する複数のオブジェクト をまとめて、一貫した組み合わせで作りたい」問題。

    4.2 使いどころ

    • UIテーマ（ダーク用・ライト用のボタン・フォームセット）
    • OS別のGUI部品
    • 環境別の依存セット（本番・開発・テスト）

    4.3 例：テーマごとのUIパーツ

    interface UIFactory {
  createButton(): Button;
  createInput(): Input;
}

class DarkThemeFactory implements UIFactory {
  createButton() { return new DarkButton(); }
  createInput() { return new DarkInput(); }
}

class LightThemeFactory implements UIFactory {
  createButton() { return new LightButton(); }
  createInput() { return new LightInput(); }
}

function render(factory: UIFactory) {
  const btn = factory.createButton();
  const input = factory.createInput();
  // どちらも同じテーマで揃う
}

    5.Builder（ビルダー）

    5.1 何を解決するか

    「コンストラクタの引数が多すぎて、何を渡しているか分からない」問題。

    5.2 使いどころ

    • 引数が多いオブジェクト
    • 組み立て方が段階的
    • 選択可能なオプションが多い

    5.3 例：ピザの組み立て

    ✕ 悪い例（引数の地獄） 
    new Pizza('medium', true, false, true, true, false, 'thin', 'tomato', 3);
// 何が何だか分からない
    ◯ Builder パターン 
    class PizzaBuilder {
  constructor() { this.pizza = { toppings: [] }; }
  size(s) { this.pizza.size = s; return this; }
  crust(c) { this.pizza.crust = c; return this; }
  sauce(s) { this.pizza.sauce = s; return this; }
  addTopping(t) { this.pizza.toppings.push(t); return this; }
  build() { return this.pizza; }
}

const pizza = new PizzaBuilder()
  .size('medium')
  .crust('thin')
  .sauce('tomato')
  .addTopping('cheese')
  .addTopping('basil')
  .build();

    メソッドチェーン（各メソッドが自分自身を返し、.a().b().c() とつなげて呼べる書き方）で直感的に書けます。名前付き引数が使える言語（Python, Kotlin）では、Builder を使わず名前付き引数で済むことも多いです。

    6.Prototype（プロトタイプ）

    6.1 何を解決するか

    「既存のオブジェクトを複製 したいが、new して1から設定するのが面倒」問題。

    6.2 使いどころ

    • オブジェクトの生成コストが高い
    • ほとんど同じ設定のオブジェクトを大量に作る
    • 現在の状態を保存・復元したい

    6.3 例

    class Shape {
  constructor(type, color, x, y) {
    this.type = type;
    this.color = color;
    this.x = x;
    this.y = y;
  }
  clone() {
    return new Shape(this.type, this.color, this.x, this.y);
  }
}

const original = new Shape('circle', 'red', 10, 20);
const copy = original.clone();
copy.x = 50; // オリジナルには影響しない

    JavaScript では Object.assign({}, obj) や structuredClone(obj) でも実現できます。

    7.Singleton（シングルトン）

    7.1 何を解決するか

    「アプリ全体で1つだけ 存在するべきオブジェクトを、どこからアクセスしても同じにしたい」問題。

    7.2 使いどころ

    • 設定（Config）
    • ロガー
    • DB接続プール
    • キャッシュ

    7.3 例

    class Logger {
  static #instance;
  constructor() {
    if (Logger.#instance) return Logger.#instance;
    Logger.#instance = this;
    this.logs = [];
  }
  log(msg) { this.logs.push(msg); }
}

const a = new Logger();
const b = new Logger();
console.log(a === b); // true、同じインスタンス

    7.4 Singleton の注意点

    Singleton はアンチパターンと言われることも多い

    • グローバル状態（どこからでも読み書きできる共有の状態）を生むのでテストが難しい
    • 依存関係が見えなくなる（どこから使われるか分からない）
    • 並行処理で事故りやすい

    現代的には、Singleton を直接書かず、DIコンテナ（オブジェクトの生成と受け渡しを引き受ける仕組み）に 「スコープ: シングルトン」として登録 することが多いです。DI の考え方は 41章：DI・IoC・Composition Root を参照してください。

    8.生成パターンの使い分け

    状況選ぶパターン
    クラスを条件で切り替えたいFactory Method
    関連するオブジェクト群をまとめて作るAbstract Factory
    引数が多くて分かりにくいBuilder
    既存オブジェクトを複製したいPrototype
    1つだけ存在させたいSingleton（慎重に）

    9.よくある誤解

    誤解1：「new はすべて Factory に置き換えるべき」

    Factory が役立つのは、作るクラスを条件で切り替えたい・作り方をまとめたい・テストで差し替えたい、といった問題があるときです。1種類しか作らない単純な場面では、そのまま new すれば十分です（デザインパターン入門 の「パターンを使いたい病」も参照）。

    誤解2：「1つしか要らないものは Singleton にすればよい」

    Singleton はグローバル状態を生み、テストを難しくし、依存関係を見えなくします。「1つだけ」にしたいなら、DIコンテナにシングルトンのスコープで登録し、使う側にはコンストラクタで渡す方法が一般的です。

    誤解3：「引数が多いなら必ず Builder」

    Python や Kotlin のように名前付き引数が使える言語では、Builder を使わずに名前付き引数で読みやすく書けることも多いです。

    10.まとめ

    • 生成パターンは「どう作るか」を工夫し、作るクラスの変更・複雑な組み立て・生成のタイミングを扱いやすくする
    • Factory Method：new する場所を1カ所にまとめ、条件で切り替える
    • Abstract Factory：関連する部品一式を一貫した組み合わせで作る
    • Builder：引数の多いオブジェクトをメソッドチェーンで段階的に組み立てる
    • Prototype：既存オブジェクトを複製して作る
    • Singleton：1つだけに制限する。ただし慎重に、現代は DI コンテナのスコープで代替することが多い

    次は、オブジェクトの組み合わせ方を扱う 構造パターン に進みます。
