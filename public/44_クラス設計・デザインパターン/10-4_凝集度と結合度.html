    凝集度と結合度 — クラスの中はまとまりよく、クラスの間はゆるやかに

    クラス設計の物差しになる「凝集度」と「結合度」を、クラス単位に当てはめて学びます。凝集度が低いクラスの典型例、結合度を下げる書き方、「知り合いの知り合いと話さない」デメテルの法則、そして設計レビューで使えるチェックリストまでを押さえます。

    もとにしたノート：10_クラスの基礎/04_クラスの凝集度と結合度

    ひとことで言うと

    凝集度 はクラスの中の要素が1つの目的にまとまっている度合い（高いほどよい）、結合度 はクラス同士の依存の強さ（低いほどよい）です。依存はインターフェース経由にし、デメテルの法則 で「知りすぎ」を防ぎます。

    2.クラスの凝集度とは何か

    凝集度 は、1つのクラスの要素が 1つの目的にどれだけまとまっているか を表します。

    凝集度状態例
    高い関連する状態と振る舞いだけOrder に注文関連のみ
    低い無関係な責務が混在UserManager に認証・メール・レポート

    高凝集の Order

    • 明細管理
    • 合計計算
    • キャンセル

    低凝集の MiscService

    • ユーザー認証
    • PDF 生成
    • 在庫更新

    凝集度は高いほどよい とされます。

    3.凝集度が低いクラスの典型例

    パターン症状対策
    God Class（神クラス）何でもやる巨大クラス責務で分割
    Utils 肥大化無関係な静的メソッドの集積ドメインごとに分離
    Feature Envy（他クラスへの羨望）他クラスのデータを多用メソッドの移動（Move Method）
    ✕ 凝集度が低い — 注文とメールが同居 
    // 凝集度が低い — 注文とメールが同居
class OrderService {
  createOrder() { /* ... */ }
  sendConfirmationEmail() { /* ... */ }
  generateMonthlyReport() { /* ... */ }
}

    メールは EmailNotifier、レポートは ReportGenerator へ分けると凝集度が上がります。こうした「コードの臭い」とリファクタリングの対応は コードの臭いとリファクタリング にまとめています。

    4.クラス間の結合度とは何か

    結合度 は、クラス同士が どれだけ強く依存し合っているか です。

    結合度例問題
    低いインターフェース経由差し替え・テストが容易
    高い具象クラス・内部フィールド直接参照変更が連鎖
    ✕ 結合度が高い — 具象に依存 
    class OrderService {
  constructor() {
    this.db = new MySqlConnection(); // 具象に依存
  }
}
    ◯ 結合度が低い — 抽象に依存 
    class OrderService {
  constructor(repository) { // 抽象に依存
    this.repository = repository;
  }
}

    具象クラス（MySqlConnection のような具体的な実装）を自分で new すると、そのクラスに縛られます。外から渡してもらえば、テストのときに偽物へ差し替えられます。抽象への依存の詳細は インターフェースと抽象化、外から渡す仕組み（依存性注入）は 41章：DI・IoC・Composition Root にあります。

    5.知り合いの知り合いと話さない（デメテルの法則）

    デメテルの法則（Law of Demeter）：オブジェクトは、自分・自分の部品・自分が作ったオブジェクト・引数のオブジェクト 以外に 直接メッセージを送らない。原則そのものは 48_原則 のノート『02_デメテルの法則』が本拠地です。

    ✕ 悪い例 — チェーン呼び出し（結合度が高い） 
    const city = order.getCustomer().getAddress().getCity();
    ◯ 良い例 — Order に委譲 
    const city = order.shippingCity();

    6.クラス設計のチェックリスト

    設計レビューのときに、次の5点を確かめます。

    • ☐ クラスの要素は 1つの責務 に関連しているか
    • ☐ Manager / Util に無関係な処理が溜まっていないか
    • ☐ 依存は インターフェース 経由か
    • ☐ メソッドチェーン（a.b().c().d()）が多すぎないか
    • ☐ 変更時に触るクラス数は妥当か

    モジュールレベルの詳細は 43章の 凝集度・結合度（入口は モジュール設計の全体像）、メソッドレベルは 46_メソッド設計 のノート『目次』を見てください。

    7.よくある誤解

    誤解1：「Manager や Util という名前のクラスにまとめれば整理できている」

    何でも入れられる名前のクラスには、無関係な処理が溜まりがちです（Utils 肥大化・God Class）。責務やドメインごとに分けると、凝集度が上がります。

    誤解2：「結合度はゼロにするのが理想」

    クラスは協調して働くので、依存そのものはなくせません。目指すのは 依存を少なく、ゆるくする こと ── 具象ではなくインターフェースに依存し、必要最小限のことだけを知る状態です。

    誤解3：「ドットが続く書き方はすべてデメテルの法則違反」

    問題になるのは、order.getCustomer().getAddress().getCity() のように 他のオブジェクトの内部構造をたどる 呼び出しです。単純なデータ取得や意図的なビルダーのように、同じオブジェクトを返しながら設定を重ねる書き方は例外として扱われます（クラス設計の変遷「デメテルの法則」）。

    8.まとめ

    • 凝集度 = クラス内のまとまり（高いほどよい）
    • 結合度 = クラス間の依存（低いほどよい）
    • デメテルの法則で「知りすぎ」を防ぐ
    • チェックリストで設計レビューに使う
