    GoFパターンの概要 — 23パターンの分類と、クラス設計でよく使うパターン

    GoF の23パターンを「生成・構造・振る舞い」の3分類で一覧し、普段のコードに隠れているパターン、学び方のコツを紹介します。後半では、クラス設計の実務で特によく使う Strategy・Factory・Observer・Decorator・Repository を、クラス構成の観点でコードとともに見ていきます。

    もとにしたノート：51_入門と概要/02_デザインパターンの概要、51_入門と概要/03_クラス設計でよく使うパターン

    ひとことで言うと

    GoF の23パターンは、作り方（生成 5個）・組み合わせ方（構造 7個）・やり取り（振る舞い 11個） の3つに分かれます。全部を覚える必要はなく、まずは Strategy・Factory・Observer・Adapter・Decorator の5個を「なぜこう書くか」まで説明できるようにするのが近道です。

    1.このページで扱うこと

    プログラムを書いていると、「前にも似たような設計をしたな」と感じることが増えてきます。このような 繰り返し現れる設計問題の、定番の解き方 をまとめたものが デザインパターン です。考え方の入口は デザインパターン入門 で扱いました。このページでは次のことを扱います。

    2.GoF とデザインパターン

    1994年、4人の著者（Gang of Four, GoF）が『デザインパターン ― オブジェクト指向における再利用のための〜』で23個のパターンを体系化しました。現在でも設計の 共通語彙 として使われています。

    3.なぜデザインパターンを学ぶのか

    1. 「車輪の再発明」を防ぐ

    先人が試行錯誤の末にたどり着いた設計を、初めから使えます。車輪の再発明 とは、すでにある解決策を知らずに一から作り直してしまうことです。

    2. チームの共通言語になる

    「ここは Strategy で書こう」「Factory を挟もう」と言うだけで、設計の意図がチームに伝わります。

    3. 設計の引き出しが増える

    「この問題、どう設計しよう？」のとき、知っているパターンから選ぶ だけで出発点ができます。

    4. 既存のフレームワークが理解しやすくなる

    多くのフレームワークはデザインパターンで構成されています（React の Observer、DI コンテナの Factory など）。パターンを知っていると 仕組みが読める ようになります。

    4.GoFの23パターン — 3つの分類

    GoF のパターンは 「何を解決するか」 で3種類に分かれます。

    分類目的代表パターン
    生成（Creational）オブジェクトの作り方を扱うFactory, Builder, Singleton
    構造（Structural）オブジェクトの組み合わせ方を扱うAdapter, Decorator, Facade
    振る舞い（Behavioral）オブジェクト間のやり取りを扱うStrategy, Observer, Command

    詳細は各ページへ：生成パターン、構造パターン、振る舞いパターン。

    5.23パターン一覧（クイックリファレンス）

    5.1 生成に関するパターン（5個）

    パターンひとこと
    Abstract Factory関連するオブジェクト群をまとめて作る
    Builder段階的に複雑なオブジェクトを組み立てる
    Factory Methodどのクラスを作るかサブクラスに任せる
    Prototype既存のオブジェクトを複製して作る
    Singletonインスタンスを1つだけに制限する

    5.2 構造に関するパターン（7個）

    パターンひとこと
    Adapter既存の互換性のないAPIを繋ぐ変換アダプタ
    Bridge抽象と実装を別々に拡張できるよう分離
    Compositeツリー構造を再帰的に扱う
    Decoratorオブジェクトを包んで機能を追加
    Facade複雑なサブシステムに簡単な窓口を用意
    Flyweight共通部分を共有してメモリ節約
    Proxy本物の代理として振る舞う

    5.3 振る舞いに関するパターン（11個）

    パターンひとこと
    Chain of Responsibility処理を次々とバケツリレー
    Command操作をオブジェクト化（Undo可）
    Interpreter小さな言語を解釈する
    Iteratorコレクションを順に辿る
    Mediator仲介者を介してオブジェクト間の通信を整理
    Memento状態を保存・復元（Undo）
    Observer状態変化を他者に通知
    State状態によって振る舞いを変える
    Strategyアルゴリズムを差し替え可能にする
    Template Method処理の骨格だけ親、詳細を子に
    Visitorデータ構造を変えずに処理を追加

    6.身近な例：普段使っているパターン

    意識していないだけで、実はよく使うパターンばかりです。

    Observer（観察者） 
    button.addEventListener('click', handleClick);
// イベント発火 → 登録された関数が通知される
    Iterator（反復子） 
    for (const item of list) { /* ... */ }
// 内部構造を知らずに順番に取り出す
    Strategy（戦略） 
    [1,3,2].sort((a,b) => a-b); // 比較方法を差し込む
    Factory（工場） 
    JSON.parse(str); // stringからオブジェクトを作る
    Decorator（装飾） 
    @autobind
@readonly
class MyClass { /* ... */ }

    ※ TypeScript の @ 記法（言語機能としてのデコレーター）は、クラスやメソッドに機能を付け足すという発想が GoF の Decorator と共通しています。GoF の Decorator そのものの書き方は 構造パターン で扱います。

    7.学び方のコツ

    1. 最初は5個だけ 完全に理解する（Strategy, Factory, Observer, Adapter, Decorator）
    2. 既存のコードの中で見つける（React の hooks、Node.js の EventEmitter など）
    3. 「なぜこう書くか」を説明できる ことを目標にする
    4. 使いどころを間違えないように（小さな問題に大きなパターンは不要）

    8.クラス設計でよく使うパターン

    ここからは、クラス設計の実務に頻出する Strategy・Factory・Observer・Decorator・Repository を、クラス構成の観点で見ていきます。

    8.1 Strategy — 振る舞いの差し替え

    Strategy はアルゴリズムをクラスに切り出し、コンテキスト（そのアルゴリズムを使う側のクラス）から差し替えます。

    class StandardShipping { cost(order) { return 500; } }
class ExpressShipping { cost(order) { return 1500; } }

class Shipment {
  constructor(strategy) { this.strategy = strategy; }
  shippingCost(order) { return this.strategy.cost(order); }
}
    向く場面支払い・配送・税・割引
    SOLIDOCP の定番実装（開放閉鎖の原則）

    8.2 Factory — 生成の責務の分離

    Factory は new の詳細を一か所に集め、呼び出し側を 具象（具体的な実装クラス）から解放します。

    class PaymentFactory {
  create(type, config) {
    switch (type) {
      case 'STRIPE': return new StripePayment(config);
      case 'PAYPAL': return new PayPalPayment(config);
      default: throw new Error(`未対応: ${type}`);
    }
  }
}

    GRASP の Creator（そのオブジェクトを作る責務を誰に持たせるかの指針）と組み合わせ、誰が作るか・どこで作るか を明確にします。

    8.3 Observer — 変更通知の疎結合化

    Observer は状態変化を 購読者に通知 し、直接呼び出しの網を減らします。

    class Order {
  constructor() { this.listeners = []; }
  subscribe(fn) { this.listeners.push(fn); }
  confirm() {
    this.status = 'CONFIRMED';
    this.listeners.forEach(fn => fn(this));
  }
}
    注意通知先が多すぎると追跡困難。ドメインイベントと併用検討
    関連42章：ドメインイベント

    8.4 Decorator — 機能の追加と合成

    Decorator は同じインターフェースを実装し、ラップして機能を足す パターンです。

    class LoggingRepository {
  constructor(inner) { this.inner = inner; }
  save(order) {
    console.log('saving', order.id);
    return this.inner.save(order);
  }
}

    継承階層を深くせず、実行時に層を重ねる のに向きます（継承より合成 も参照）。

    8.5 Repository — 永続化の抽象化

    Repository は 集約（一緒に整合性を保つべきオブジェクトのまとまり）の永続化を抽象化し、ドメインを DB から隔離します。GoF の23パターンには含まれず、DDD やエンタープライズ系のパターンです（GoF以外のパターン）。

    interface OrderRepository {
  save(order: Order): void;
  findById(id: OrderId): Order | null;
}
    役割ドメインは「保存・取得」の契約だけ知る
    実装SqlOrderRepository, InMemoryOrderRepository
    関連42章：集約とリポジトリ

    DIP（依存関係逆転の原則：上位の方針が下位の実装ではなく抽象に依存する。41章：依存性逆転の原則）＋ Pure Fabrication（GRASP：ドメインに無い概念でも、責務をうまく分けるために作る人工的なクラス）の実践です。

    9.よくある誤解

    誤解1：「パターンを使うほど良い設計」

    デザインパターンは 問題に対する解 であって、使うこと自体が目的ではありません。問題がないのに使うと過剰設計 になります。

    誤解2：「とりあえず覚えれば使える」

    パターンは 「どんな問題を解くか」 を理解しないと活きません。コードの形だけ真似ても誤用になりがちです。

    誤解3：「GoF が全て」

    GoF 以外にも、エンタープライズ向けの PoEAA（Martin Fowler『Patterns of Enterprise Application Architecture』。Repository, Unit of Work など）や、並行処理パターン、関数型のパターン など、多くの流派があります。GoF以外のパターン、関数型で置き換わるパターン で扱います。

    10.まとめ

    • GoF の23パターンは 生成（5）・構造（7）・振る舞い（11） の3分類
    • パターンは 車輪の再発明を防ぎ、チームの共通言語 になる
    • イベントリスナー・for...of・sort の比較関数など、普段のコードにもパターンは隠れている
    • 最初は5個（Strategy, Factory, Observer, Adapter, Decorator）を「なぜこう書くか」まで理解する
    • クラス設計でよく使う5つ：
      • Strategy ＝ 振る舞いの差し替え
      • Factory ＝ 生成の集約
      • Observer ＝ 通知の疎結合
      • Decorator ＝ ラップで機能追加
      • Repository ＝ 永続化の抽象化

    次は、生成に関する5つのパターンを 生成パターン で詳しく見ます。
