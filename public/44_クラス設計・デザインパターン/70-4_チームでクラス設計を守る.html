    70 品質と運用

    チームでクラス設計を守る — 合意・レビュー・文書化・負債の可視化

    良いクラス設計も、チームで共有されていなければすぐに崩れます。設計の合意形成、コードレビューで見るべきポイント、クラス設計ルールの文書化、設計負債の可視化、新人への説明の仕方を解説します。

    もとにしたノート：70_品質と運用/04_チームでクラス設計を守る

    ひとことで言うと

    クラス設計は個人の好みではなく チームの合意 です。短い設計スケッチと ADR で合意し、レビューでは スタイルより構造 を見て、ルールは 1ページ に書き残します。設計負債は隠さず可視化し、新人には 悪い例から「なぜ痛いか」 を体験してもらいます。

    2.設計の合意形成

    クラス設計は個人の好みではなく、チームの合意 が必要です。人によって分け方がばらばらだと、同じコードベースの中に複数の流儀が混ざり、読む人が迷います。

    場面手法
    新機能短い設計スケッチ + クラス名リスト
    争点ADR（設計判断の記録）
    定期アーキテクチャ・設計の勉強会

    ADR（Architecture Decision Record）：何を決めたか・なぜそう決めたかを短く残す文書。詳しくは 意思決定とADR（41章）。

    1. 提案
    2. レビュー
    3. 合意
    4. コード
    5. 振り返り

    チームで設計を守る（42章） と同じ考え方を、クラス単位に適用します。

    3.コードレビューで見るべきポイント

    観点質問
    SRPこのクラスの変更理由は1つか
    凝集・結合無関係な処理・過剰な依存はないか
    カプセル化不変条件は守られているか
    命名クラス名で責務が伝わるか
    テスト単体テストしやすい構造か

    SRP：単一責任の原則。凝集・結合：凝集度と結合度。不変条件（オブジェクトが常に満たすべきルール）：カプセル化と情報隠蔽。命名：命名とクラス構成。テスト：テストしやすいクラス設計。

    スタイルより構造

    スタイル（インデント等） より 構造 を優先します。インデントや空白はフォーマッタなどのツールに任せ、人のレビューは責務の置き場所や依存の向きに使います。

    4.クラス設計ルールの文書化

    1ページでよいので、チームの クラス設計ルール を残します。

    ## 例: クラス設計ルール
1. ドメインルールはエンティティに置く（貧血モデル禁止）
2. new は Composition Root / Factory に集約
3. 継承は2階層まで。それ以上は合成
4. Repository はインターフェース + infrastructure 実装
5. 500行超えたら Extract Class を検討

    それぞれの背景は次のページで扱っています。

    • 1. 貧血モデル（エンティティがデータの入れ物になり、ロジックがサービス側に偏る状態）→ Tell, Don't Ask と貧血モデル
    • 2. Composition Root（アプリの起動時に、オブジェクトを組み立てて依存を渡す1か所）・Factory → DI・IoC・Composition Root（41章）、生成パターン
    • 3. 継承と合成 → 継承より合成
    • 4. Repository とインターフェース → インターフェースと抽象化
    • 5. Extract Class → 変更に強いクラス設計

    ルールは、クラス設計チェックリスト（付録B） をベースにチームに合わせてカスタマイズします。

    5.設計負債の可視化

    手法内容
    ラベルtech-debt, refactor チケット
    メトリクスクラス行数、循環依存
    ボーンマルク理想のパッケージ図と現状の差分

    メトリクス：コードから機械的に測れる数値。循環依存：A が B を、B が A を使うような、依存がぐるりと回ってしまう状態。「ボーンマルク」はノートの表記のままで、理想の図を基準（ベンチマーク）にして現状との差を見る手法を指していると考えられます。

      負債リスト → 優先度（影響×頻度）→ スプリントに1〜2件

    隠すと 変更恐怖（どこが壊れるか分からず、コードを触るのが怖くなること）が増えます。可視化して計画的に返済します。技術的負債の考え方は 変更に強いクラス設計 も参照してください。

    6.新人への説明の仕方

    1. 比喩から — 部屋と家具（クラス設計を学ぶ理由）
    2. 悪い例1つ — 神クラスを見せて問題を体感
    3. 直し方1つ — Extract Class をペアで
    4. チェックリスト — クラス設計チェックリスト（付録B）
    5. 既存コードの良い例 — チームのお手本クラスを指す

    神クラス（God Class）：何でもやる巨大なクラス。ペア：2人で1台の画面を見ながら一緒に書くこと（ペアプログラミング）。

    理論の前に 「なぜ痛いか」 を体験させると定着します。

    7.よくある誤解

    誤解1：「クラスの分け方は、書いた人の好みに任せればよい」

    人によって流儀が違うと、同じコードベースが読みにくくなり、レビューのたびに議論が蒸し返されます。スケッチ・ADR・短いルール文書で、チームの合意として残します。

    誤解2：「レビューではインデントや書き方の細部を指摘するのが大事」

    スタイルはツールで揃えられます。人のレビューでは、変更理由が1つか、不変条件が守られているか、テストしやすいかといった 構造 を優先して見ます。

    誤解3：「設計負債は、知られると評価が下がるので黙っておく」

    隠された負債は、触るのが怖い場所を増やすだけです。チケットやメトリクスで見えるようにし、影響×頻度で優先度をつけてスプリントに1〜2件ずつ組み込みます。

    8.まとめ

    • 設計は合意形成が前提。スケッチと ADR を活用
    • レビューは構造・責務・テスト容易性を見る
    • ルールとチェックリストを短く文書化
    • 負債は可視化して計画返済。新人には悪い例から
