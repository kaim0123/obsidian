    60 アンチパターンとコードの臭い

    コードの臭いとリファクタリング — 24の臭いと対処の早見表

    Martin Fowler『リファクタリング 第2版』の24のコードの臭いを、名前・データ・変更・条件分岐・不要なもの・クラス間の関係の6グループに分け、それぞれにどのリファクタリングで対処するかを対応づけた実務用の早見表です。臭いと設計原則の対応、安全に進める手順とタイミングもまとめます。

    もとにしたノート：60_アンチパターンとコードの臭い/03_コードの臭いとリファクタリング対応表

    ひとことで言うと

    コードの臭い（Code Smell） は、より深い設計上の問題があるかもしれないことを示す 表面的な兆候 です。バグではありません が、変更しにくさのサインです。臭いごとに定番の リファクタリング（外から見た振る舞いを変えずに内部の構造を改善すること）があり、テストを用意 → 小さな一歩 → 毎回テスト で、日々の開発の中で少しずつ直します。

    1.このページで扱うこと

    アンチパターンの見分け方 では、代表的なアンチパターンとコードの臭いの考え方を学びました。このページは、Martin Fowler『リファクタリング 第2版』（2018）の 24 のコードの臭い を一覧にし、それぞれに どのリファクタリングで対処するか を対応づけた 実務用の早見表 です。

    • コードの臭いとは何か（臭いはバグではない）
    • 24 の臭い の意味・見分け方・主な対処
    • 臭いの グループ分け（クラス設計の観点で）
    • リファクタリングを安全に進める手順

    メソッド単位のリファクタリング技法（Extract Method など）の早見表は、46_メソッド設計 のノート『付録D_リファクタリング技法早見表』にあります。このページは クラス設計に関わる臭い に重点を置きます。

    2.コードの臭いとは

    コードの臭い（Code Smell）とは、より深い設計上の問題があるかもしれないことを示す、表面的な兆候である。

    • Kent Beck が名付け、Fowler の『リファクタリング』（初版 1999）で広まった
    • 臭いはバグではない。今は正しく動いている
    • しかし、変更しにくい・理解しにくい・バグを生みやすい 構造のサイン
    • 「臭うからといって必ず直す」わけではなく、直すかどうかは判断する（変更の予定がない部分は放っておいてもよい）

    Fowler は「いつリファクタリングすべきか」について、明確な基準を示すことはできないが、臭いに気づく嗅覚を養うことはできる と述べています。

    3.24 の臭いと対処の一覧（第2版）

    日本語訳は『リファクタリング 第2版』（オーム社）の訳語を基本にしています（訳語は資料によって揺れがあります）。

    3.1 名前・重複・長さの臭い

    #臭い（英語）症状主なリファクタリング
    1不可思議な名前（Mysterious Name）名前を見ても、何をするのか分からない関数宣言の変更（名前変更）、変数名の変更、フィールド名の変更
    2重複したコード（Duplicated Code）同じ・似たコードが複数の場所にある関数の抽出、ステートメントのスライド、メソッドの引き上げ
    3長い関数（Long Function）関数が長く、何をしているか一目で分からない関数の抽出、一時変数から問い合わせへの置き換え、条件記述の分解、ループの分離
    4長いパラメータリスト（Long Parameter List）引数が多すぎるパラメータオブジェクトの導入、オブジェクトそのものの受け渡し、フラグパラメータの削除、関数群のクラスへの集約

    3.2 データの臭い

    #臭い症状主なリファクタリング
    5グローバルなデータ（Global Data）どこからでも読み書きできるデータ変数のカプセル化
    6変更可能なデータ（Mutable Data）データが様々な場所で書き換えられ、予期せぬ影響が出る変数のカプセル化、変数の分離、問い合わせと更新の分離、セッターの削除、参照から値への変更
    7基本データ型への執着（Primitive Obsession）金額・電話番号などを number や string のまま扱うオブジェクトによるプリミティブの置き換え（→ 値オブジェクトと完全コンストラクタ）、タイプコードのサブクラスへの置き換え、クラスの抽出
    8データの群れ（Data Clumps）いつも一緒に現れるデータの組（開始日と終了日、緯度と経度）クラスの抽出、パラメータオブジェクトの導入
    9データクラス（Data Class）getter / setter だけで振る舞いを持たないクラスレコードのカプセル化、セッターの削除、関数の移動（振る舞いをデータのそばへ → Tell, Don't Ask と貧血モデル）
    10一時的属性（Temporary Field）特定の場合にしか値が入らないフィールドクラスの抽出、関数の移動、特殊ケースの導入

    3.3 変更の臭い（クラス設計で最重要）

    #臭い症状主なリファクタリング
    11変更の偏り（Divergent Change）1つのクラス が、異なる理由 で何度も変更される（「DB が変わったらここ、商品の種類が増えたらここ」）フェーズの分離、関数の移動、クラスの抽出 → 単一責任の原則（単一責任の原則）
    12変更の分散（Shotgun Surgery）1つの変更 のために、多くのクラス を少しずつ直す必要がある関数の移動、フィールドの移動、関数群のクラスへの集約、関数のインライン化、クラスのインライン化
    13機能の横恋慕（Feature Envy）あるメソッドが、自分のクラスより 他のクラスのデータ をよく使っている関数の移動、関数の抽出 → 情報エキスパート（GRASP）

    変更の偏り と 変更の分散 は対になる臭いです。前者は「1つのクラスに複数の責務が混ざっている」、後者は「1つの責務が複数のクラスに散らばっている」。どちらも、同じ理由で変わるものを1か所に集める（高凝集）ことで解決します。

    3.4 条件分岐・ループの臭い

    #臭い症状主なリファクタリング
    14重複した switch 文（Repeated Switches）同じ条件（種類による分岐）の switch / if-else が、複数の場所 に繰り返し現れるポリモーフィズムによる条件記述の置き換え（→ 継承と多態）
    15ループ（Loops）命令的なループで、何をしているか読みにくいパイプラインによるループの置き換え（map / filter / reduce）

    第2版では、初版の「switch 文」が「重複した switch 文」に変わりました。switch 文そのものが悪いのではなく、同じ分岐があちこちに重複していること が問題、という整理です。

    3.5 不要なものの臭い

    #臭い症状主なリファクタリング
    16怠け者の要素（Lazy Element）ほとんど何もしていない関数・クラス関数のインライン化、クラスのインライン化、階層の平坦化
    17疑わしき一般化（Speculative Generality）「いつか必要になるかも」で作られた、使われていない抽象・フック・引数階層の平坦化、関数・クラスのインライン化、関数宣言の変更、デッドコードの削除 → YAGNI
    18コメント（Comments）コードの分かりにくさを、コメントで補っている（消臭剤としてのコメント）関数の抽出、関数宣言の変更、アサーションの導入

    「コメント」が臭いなのは、コメントが必要なほど分かりにくいコードそのもの が問題だからです。「なぜそうしたか」を説明するコメントは良いコメントです。

    3.6 クラス間の関係の臭い

    #臭い症状主なリファクタリング
    19メッセージの連鎖（Message Chains）a.getB().getC().getD() のような長い連鎖委譲の隠蔽、関数の抽出、関数の移動 → デメテルの法則（48_原則 のノート『02_デメテルの法則』）
    20仲介人（Middle Man）メソッドの大半が、他のクラスへの委譲だけ仲介人の除去、関数のインライン化 → 43章：深いモジュールと浅いモジュール の「パススルーメソッド」
    21インサイダー取引（Insider Trading）クラス同士が、互いの内部のデータを過度にやり取りしている関数の移動、フィールドの移動、委譲の隠蔽、委譲によるサブクラス／スーパークラスの置き換え
    22巨大なクラス（Large Class）フィールドやメソッドが多すぎるクラス（神クラス）クラスの抽出、スーパークラスの抽出、サブクラスによるタイプコードの置き換え
    23クラスのインターフェース不一致（Alternative Classes with Different Interfaces）同じ役割のクラスなのに、メソッド名や引数が違うので差し替えられない関数宣言の変更、関数の移動、スーパークラスの抽出
    24相続拒否（Refused Bequest）サブクラスが、親から継承したメソッドやデータを使わない・使いたくないメソッドの押し下げ、フィールドの押し下げ、委譲によるサブクラス／スーパークラスの置き換え（→ 継承より合成、リスコフの置換原則）

    第2版で「インサイダー取引」は、初版の「不適切な関係（Inappropriate Intimacy）」を置き換えたものです。

    4.臭いから原則への対応

    臭いの多くは、クラス設計の原則が守られていないサインとして読めます。

    原則違反のサインとなる臭い
    単一責任の原則（SRP）変更の偏り、巨大なクラス、長い関数
    高凝集変更の分散、機能の横恋慕、データの群れ
    疎結合・カプセル化グローバルなデータ、変更可能なデータ、インサイダー取引、メッセージの連鎖
    情報エキスパート / Tell, Don't Ask機能の横恋慕、データクラス
    開放閉鎖の原則（OCP）重複した switch 文
    リスコフの置換原則（LSP）相続拒否
    YAGNI疑わしき一般化、怠け者の要素
    値オブジェクト基本データ型への執着、データの群れ

    各原則は 単一責任の原則・凝集度と結合度・カプセル化と情報隠蔽・Tell, Don't Ask と貧血モデル・開放閉鎖の原則・リスコフの置換原則・値オブジェクトと完全コンストラクタ で扱っています。

    5.臭いを見つけたときの進め方

    5.1 安全なリファクタリングの手順

    1. テストがあることを確認する。なければ、まず現状の動作を固定するテスト（特性テスト：今の振る舞いをそのまま記録するテスト）を書く
    2. 小さな一歩 で変更する（1つのリファクタリングごと）
    3. 一歩ごとにテストを実行 する
    4. 振る舞いを変えない。機能追加とリファクタリングを 同じコミットに混ぜない（Kent Beck の「2つの帽子」）
    5. こまめにコミットする

    5.2 いつリファクタリングするか

    Fowler は、リファクタリングのタイミングとして次を挙げています。

    タイミング内容
    準備のためのリファクタリング新機能を追加する 前に、追加しやすい形に整える。「変更を簡単にしてから、簡単な変更をせよ」（Kent Beck）
    理解のためのリファクタリングコードを読んで理解したことを、名前や構造に反映する
    ゴミ拾いのリファクタリング作業中に見つけた小さな臭いを、ついでに直す（ボーイスカウトの規則：来たときよりきれいに）
    コードレビュー時レビューで見つけた臭いを、その場で直す

    日々の開発の中で少しずつ

    「リファクタリングのための期間」を別に取るより、日々の開発の中で少しずつ 行うのが、Fowler の推奨するやり方です。

    5.3 直さなくてよい場合

    • 今後変更する予定がない コード
    • 作り直した方が早い コード
    • 臭いを直すことで、別の臭いが生まれる 場合（例：仲介人を除去したら、メッセージの連鎖が生まれる）

    リファクタリングとテストの関係は 42章：テストとリファクタリング でも扱っています。

    6.よくある誤解

    誤解1：「臭いがあるコードは間違っている」

    誤りです。 臭いはバグではなく、設計上の問題の可能性を示すサイン です。直すかどうかは、変更の予定やコストを見て判断します。

    誤解2：「リファクタリングは、まとまった時間を取ってやるもの」

    推奨されません。 小さく、日々の開発の中で行うのが基本です。大規模なリファクタリングは、テストのない状態で行うと非常に危険です。

    誤解3：「リファクタリング＝コードの書き直し」

    違います。 リファクタリングは 外から見た振る舞いを変えずに、内部の構造を改善する ことです。機能の追加や修正とは区別します。

    7.まとめ

    • コードの臭い：深い設計上の問題を示す表面的な兆候。バグではないが、変更しにくさのサイン
    • 第2版の 24 の臭い を、名前・データ・変更・条件分岐・不要なもの・クラス間の関係に分けて対処を対応づけた
    • クラス設計でとくに重要なのは 変更の偏り（SRP）・変更の分散（高凝集）・機能の横恋慕（情報エキスパート）・データクラス（貧血モデル）・基本データ型への執着（値オブジェクト）・相続拒否（継承より合成）
    • リファクタリングは テストを用意 → 小さな一歩 → 毎回テスト → 振る舞いを変えない
    • タイミングは 準備・理解・ゴミ拾い・レビュー。日々の開発の中で少しずつ

    次は、テストしやすさの観点からクラス設計を見直す テストしやすいクラス設計 に進みます。
