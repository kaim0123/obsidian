    40 SOLIDの適用

    SOLIDの統合と判断 — 5原則をどう組み合わせ、どこで止めるか

    SOLID の5原則は、ばらばらに覚えるより「分割・拡張・契約・接続」のセットとして使うと役立ちます。5原則の関係、原則同士が衝突したときの判断、適用しすぎの兆候、レビューで見るポイント、よくある違反と修正を、SOLID 早見表とあわせてまとめます。

    もとにしたノート：40_SOLIDの適用/05_SOLIDの統合と判断、90_付録/付録D_SOLID早見表

    ひとことで言うと

    SOLID は SRP で分け、OCP・LSP で拡張し、ISP・DIP でつなぐ ための原則のセットです。原則同士はときに衝突するので、完璧な SOLID より、変更の影響が読めること を優先し、適用しすぎないようにします。

    このページでは SOLID 5原則の 関係性・衝突時の優先順位・適用しすぎの回避 を学びます。レビュー観点とよくある違反の修正まで押さえ、最後に付録の SOLID 早見表 を載せます。

    2.5原則の関係性

    原則略称クラス設計での役割
    単一責任SRP責務の分割
    開放閉鎖OCP拡張点の設計
    リスコフ置換LSP継承の契約
    インターフェース分離ISP小さな契約
    依存性逆転DIP抽象への依存

    各原則の詳細は SRP・OCP・LSP・ISP・DIP（インターフェースと抽象化） の各ページを、オブジェクト指向全体との関係は 42章の SOLIDとオブジェクト指向 も参照してください。早見表はこのページの 7章 にあります。

    3.原則同士が衝突するときの優先順位

    衝突判断のヒント
    SRP vs クラス数爆増変化の理由が同じならまとめる
    OCP vs YAGNI実際に来そうな変化だけ拡張点に
    ISP vs 単純さクライアントが2つ以上なら分割検討
    DIP vs 直書きテスト・差し替えが必要なら抽象化

    YAGNI（You Aren't Gonna Need It）は「今必要ないものは作らない」という考え方です。完璧な SOLID より、変更の影響が読めること を優先します。

    4.SOLID を適用しすぎない

    過剰適用の兆候対策
    1メソッド1クラス凝集度 を見直す
    インターフェースだらけ実際のクライアント数を確認
    パターンの乱用問題が起きてから導入

    小規模スクリプトやプロトタイプ（試作品）では、動くものを作ってから 原則を当てはめます。

    5.レビューで見るべき SOLID のポイント

    • ☐ クラスに 複数の変更理由 がないか（SRP）
    • ☐ 新機能で 既存クラスを何度も直している か（OCP）
    • ☐ 継承先で 親の使い方が壊れない か（LSP）
    • ☐ 実装クラスが 空メソッド・未サポート を返していないか（ISP）
    • ☐ ドメインが DB・フレームワークの型 を知っていないか（DIP）

    レビュー全体の進め方は クラス設計レビュー、チェックリストは チェックリストとアンチパターン を参照してください。

    6.よくある SOLID 違反と修正

    違反修正
    5000行の UserServiceSRP で Extract Class
    支払いの巨大 switchOCP + Strategy
    Square extends Rectangleインターフェース + 別実装
    implements で10個の未使用メソッドISP で分割
    new MySqlClient() が散在DIP + コンストラクタ注入

    コンストラクタ注入 は、使う部品をコンストラクタの引数で外から渡してもらう方法です（インターフェースと抽象化）。

    7.SOLID 早見表

    付録D「SOLID 早見表」の内容です。

    7.1 一覧

    原則略称一言ページ
    単一責任の原則SRP変化の理由は1つ単一責任の原則
    開放閉鎖の原則OCP拡張に開き変更に閉じる開放閉鎖の原則
    リスコフの置換原則LSP子は親の代わりに使えるリスコフの置換原則
    インターフェース分離の原則ISP使わないメソッドに依存しないインターフェース分離の原則
    依存性逆転の原則DIP抽象に依存するインターフェースと抽象化

    7.2 違反のサインと対策

    原則違反のサイン対策
    SRP5000行クラス、変更理由が複数Extract Class
    OCP機能追加のたびに同じ switch を修正Strategy / 多態
    LSP子で親の使い方が壊れる継承やめ・合成
    ISP空実装・未サポート例外インターフェース分割
    DIPドメインが MySql を直接 newRepository + 注入

    7.3 適用の順序（目安）

      SRP（分割）→ OCP/LSP（拡張と継承）→ ISP/DIP（接続）

    8.よくある誤解

    誤解1：「SOLID はすべて、いつでも完全に守るべき」

    原則同士は衝突します（SRP とクラス数、OCP と YAGNI など）。目的は原則を守ること自体ではなく、変更の影響が読める ことです。変化の軸とチーム規模を見て判断します。

    誤解2：「最初から SOLID に沿って設計しないといけない」

    小規模スクリプトやプロトタイプでは、動くものを作ってから原則を当てはめます。パターンも「問題が起きてから導入」が対策です。最初からインターフェースだらけにすると、過剰適用になります。

    誤解3：「5つは独立した別々のルール」

    5原則は、分割（SRP）→ 拡張（OCP・LSP）→ 接続（ISP・DIP）という流れでつながったセットです。たとえば OCP の拡張点は、LSP を守る実装と、ISP・DIP に沿った小さな抽象があって初めて機能します。

    9.まとめ

    • SOLID は分割・拡張・契約・接続のセット
    • 原則は衝突する。変化の軸とチーム規模で判断
    • 適用しすぎは複雑化。YAGNI と両立
    • レビューと早見表で定着させる
