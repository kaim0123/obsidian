    90 付録

    チェックリストとアンチパターン — クラス設計を点検し、悪い形から抜け出す

    クラス設計のレビューや自己点検に使える総合チェックリストと、クラス設計で避けるべきアンチパターンの一覧をまとめた付録です。チェックリストで「できているか」を確かめ、アンチパターン一覧で「よくある悪い形」とその対策を引き、最後に脱出の基本フローを確認します。

    もとにしたノート：90_付録/付録B_クラス設計チェックリスト / 付録E_よくあるアンチパターン一覧

    ひとことで言うと

    チェックリストは 責務と凝集・カプセル化・結合と関係・SOLID・テストと変更・命名と配置 の6分類です。アンチパターンは 構造系・ドメイン系・生成系・命名系 の4分類で、どれも テストで固定 → 最も痛い責務を1つ → Extract Class / Move Method → レビュー の順で抜け出します。

    • クラス設計チェックリスト（総合版）：6分類の点検項目と使い方
    • よくあるアンチパターン一覧：構造系・ドメイン系・生成・ライフサイクル系・命名・組織系
    • 脱出の基本フロー

    アンチパターン とは、よく見かけるけれど避けるべき悪い設計の型のことです。見分け方の考え方は アンチパターンの見分け方 を参照してください。

    2.クラス設計チェックリスト（総合版）

    クラス設計のレビュー・自己点検用のチェックリストです。各項目の詳しい説明は、見出しの横のページにあります。

    2.1 責務と凝集

    → 単一責任の原則、凝集度と結合度、ドメインを表すクラス

    • ☐ クラスに 1 つの変更理由 しかない（SRP）
    • ☐ 無関係な処理が Utils / Manager に溜まっていない
    • ☐ ドメインルールがサービスではなく ドメインクラス にある
    • ☐ クラス名だけで責務が説明できる

    2.2 カプセル化

    → カプセル化と情報隠蔽

    • ☐ フィールドは 必要最小限 公開
    • ☐ 不変条件（オブジェクトが常に満たすべきルール）はクラス内のメソッドで守られている
    • ☐ getter/setter だけの「偽カプセル化」になっていない
    • ☐ コレクションは外部から直接書き換えられない

    2.3 結合と関係

    → インターフェースと抽象化、Tell, Don't Ask と貧血モデル、継承と多態

    • ☐ 具象クラスではなく 抽象 に依存している（DIP）
    • ☐ 循環依存 がない
    • ☐ メソッドチェーン（a.b().c()）が過剰でない（デメテル：知り合いの知り合いと直接話さない、という法則）
    • ☐ 継承は is-a のときだけ。深さは 2〜3 階層以内

    2.4 SOLID

    → 開放閉鎖の原則、リスコフの置換原則、インターフェース分離の原則、SOLIDの統合と判断

    • ☐ 新機能追加で 同じクラスを何度も直していない（OCP）
    • ☐ 子クラスは親の 契約を壊していない（LSP）
    • ☐ クライアントが 使わないメソッドを実装させていない（ISP）

    2.5 テストと変更

    → テストしやすいクラス設計、変更に強いクラス設計、チームでクラス設計を守る

    • ☐ ドメインクラスを DB なし で単体テストできる
    • ☐ 副作用（I/O・時刻）は 境界クラス に集約
    • ☐ 500 行を超えたら Extract Class を検討
    • ☐ 設計負債はチケット等で 可視化 されている

    2.6 命名と配置

    → 命名とクラス構成

    • ☐ ユビキタス言語 とクラス名が一致
    • ☐ メソッド名は動詞で 副作用が分かる
    • ☐ パッケージ配置が ドメイン中心（技術詳細は外側）

    2.7 使い方

    1. 新規クラス追加時に上から確認
    2. PR レビューで争点のある項目に絞る
    3. チームで項目の追加・削除を合意

    レビューでの使い方の詳細は クラス設計レビュー を見てください。責務の割り当てと SOLID の早見表は GRASP（付録C）と SOLIDの統合と判断（付録D）にあります。

    3.よくあるアンチパターン一覧

    クラス設計で避けるべきアンチパターンを4つに分けて並べます。詳細は アンチパターンの見分け方 を参照してください。

    3.1 構造系

    アンチパターン症状対策
    God Class / God Object1クラスに全処理SRP + Extract Class
    スパゲッティ継承深い階層・矛盾する override合成 + インターフェース
    循環依存A→B→Aインターフェース・イベントで切断
    巨大インターフェース10個以上のメソッドISP で分割

    override：親クラスのメソッドを子クラスで上書きすること。合成については 継承より合成。

    3.2 ドメイン系

    アンチパターン症状対策
    貧血モデルエンティティはデータのみMove Method でドメインへ
    アナミックドメインモデル同上（英語表記）同上
    プライミティブ偏愛金額を number のみ値オブジェクト（Money）
    魔法の数値・文字列status === 3列挙型・定数

    アナミック（anemic）は「貧血の」という意味の英語。プライミティブ（primitive）は number や string のような言語に最初からある基本の型。関連ページ：Tell, Don't Ask と貧血モデル、値オブジェクトと完全コンストラクタ、区分オブジェクトと状態遷移。

    3.3 生成・ライフサイクル系

    アンチパターン症状対策
    Singleton 乱用テスト困難・グローバル状態DI・スコープ限定
    どこでも new具象に散在依存Factory + Composition Root
    Service Locator依存が隠れるコンストラクタ注入

    Singleton：インスタンスを1つだけに制限するパターン。Service Locator：必要な依存をクラスの中から「置き場」に取りに行く仕組みで、外から見て何に依存しているか分からなくなります。関連ページ：生成パターン、テストしやすいクラス設計、DI・IoC・Composition Root（41章）。

    3.4 命名・組織系

    アンチパターン症状対策
    Utils / Helper 肥大業務ロジックのゴミ箱ドメインクラスへ分配
    Manager 乱立責務不明ユビキタス言語で改名
    Data / Info クラス意味のない名前ドメイン名に

    4.脱出の基本フロー

    どのアンチパターンでも、抜け出す手順は同じです。

    1. テストで現状の振る舞いを固定
    2. 最も痛い責務を1つ選ぶ
    3. Extract Class / Move Method
    4. レビューで命名と境界を確認

    3. の手順は 変更に強いクラス設計、コードの臭いごとのリファクタリングは コードの臭いとリファクタリング にあります。

    5.よくある誤解

    誤解1：「チェックリストは全項目を毎回すべて満たさなければならない」

    使い方にあるとおり、新規クラス追加時には上から確認しますが、PR レビューでは争点のある項目に絞ります。項目そのものも、チームで追加・削除を合意して育てていくものです。

    誤解2：「アンチパターンを見つけたら、すぐに全部直すべき」

    脱出の基本フローは「最も痛い責務を1つ選ぶ」から始まります。まずテストで振る舞いを固定し、1つずつ Extract Class / Move Method で直します。一度に全部直そうとすると、壊れたときに原因が分からなくなります。

    誤解3：「getter/setter を付ければカプセル化できている」

    すべてのフィールドに getter/setter を付けただけでは、外から自由に読み書きできるので「偽カプセル化」です。不変条件をクラス内のメソッドで守り、コレクションを外から直接書き換えられないようにして、初めてカプセル化と言えます。

    6.まとめ

    • チェックリストは 責務と凝集・カプセル化・結合と関係・SOLID・テストと変更・命名と配置 の6分類
    • 新規追加時は上から確認、レビューでは争点に絞り、項目はチームで合意して育てる
    • アンチパターンは 構造系・ドメイン系・生成・ライフサイクル系・命名・組織系 の4分類で、症状と対策をセットで覚える
    • 脱出はテストで固定 → 痛い責務を1つ → Extract Class / Move Method → レビュー
