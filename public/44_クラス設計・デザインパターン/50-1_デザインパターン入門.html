    50 デザインパターン ／ 51 入門と概要

    デザインパターン入門 — 名前の付いた設計の型と、使いどころの判断

    デザインパターンとは何か、生成・構造・振る舞いの3分類の代表例、そして「いつ使い、いつ使わないか」を解説します。あわせて、パターンを暗記した人ほど伸び悩む理由と、パターンとの正しい付き合い方も紹介します。

    もとにしたノート：51_入門と概要/01_デザインパターン入門、51_入門と概要/デザインパターンを覚える人が伸びない理由（動画メモ）

    ひとことで言うと

    デザインパターン は、設計でくり返し出てくる問題に対する 名前の付いた解決策の型 です。パターンは 目的ではなく手段。先に問題があり、パターンは後から当てはめます。「覚えるな、出会え」— 問題で苦労したあとに出会うと、本当に使えるようになります。

    1.このページで扱うこと

    このページでは、デザインパターン の全体像をつかみ、生成・構造・振る舞いの代表例と、使う／使わないタイミングの判断を押さえます。23パターンの一覧や分類の詳しい説明は次の GoFパターンの概要 で扱います。

    • デザインパターンとは何か：名前・問題・解決の3つの要素
    • 3つの分類の代表例：生成（Factory / Builder / Singleton）、構造（Adapter / Decorator / Composite）、振る舞い（Strategy / Observer / Command）
    • パターンを使うタイミングと使わないタイミング
    • デザインパターンを覚える人が伸びない理由：「パターンを使いたい病」と伸びる人の学び方

    2.デザインパターンとは何か

    デザインパターン は、設計上の 繰り返し現れる問題 に対する 検証済みの解決策の型 です。GoF（Gang of Four ＝ 4人の著者）がまとめたものが広く知られています。

    1つのパターンは、次の3つの要素でできています。

    特徴説明
    名前チームで議論する共通語彙
    問題どんな状況か
    解決クラス構成の型

    パターンは目的ではなく手段

    パターンは問題を解くための道具です。問題がなければ不要 です。

    3.3つの分類と代表例

    パターンは「何を整理するか」で、生成・構造・振る舞い の3つに分かれます。ここでは各分類から3つずつ代表例を見ます。

    3.1 生成パターン（Factory / Builder / Singleton）

    オブジェクトの作り方 を整理するパターンです。

    パターン用途
    Factory生成ロジックを隠し、型で作り分け
    Builder複雑なオブジェクトを段階的に構築
    Singletonインスタンスを1つに（乱用注意）
    Factory のイメージ 
    // Factory のイメージ
class PaymentFactory {
  static create(type) {
    if (type === 'CARD') return new CardPayment();
    if (type === 'BANK') return new BankPayment();
    throw new Error('未知のタイプ');
  }
}

    呼び出し側は PaymentFactory.create('CARD') と書くだけで、どのクラスを new するかを知らずに済みます。

    Singleton は グローバル状態（どこからでも読み書きできる共有の状態）を生み、テストが難しくなるため、本当に1つ必要なときだけ 使います。詳しくは 生成パターン で扱います。

    3.2 構造パターン（Adapter / Decorator / Composite）

    クラスの組み合わせ方 を整理するパターンです。

    パターン用途
    Adapter互換性のないインターフェースを橋渡し
    Decorator機能を層で追加（継承より柔軟）
    Composite部分と全体を同じインターフェースで
     
      Adapter:  既存API → 新インターフェース
  Decorator: Coffee → MilkDecorator → SugarDecorator
  Composite: MenuItem / Menu（同じ interface）

    それぞれのコード例は 構造パターン で扱います。

    3.3 振る舞いパターン（Strategy / Observer / Command）

    オブジェクト間の協調・責務分配 を整理するパターンです。

    パターン用途
    Strategyアルゴリズムの差し替え（OCP）
    Observer変更の通知・疎結合
    Command操作をオブジェクト化（Undo 等）

    OCP（開放閉鎖の原則：既存コードを変えずに機能を足せるようにする原則）を実現する定番が Strategy です。開放閉鎖の原則 の Strategy と、GoFパターンの概要 の「クラス設計でよく使うパターン」で実践します。

    4.パターンを使うタイミングと使わないタイミング

    使うとき

    • 同じ構造の問題が 2回以上 現れた
    • 変化の軸がはっきりしている
    • チームがパターン名で 議論できる

    使わないとき

    • 将来かもしれない問題への先回り（YAGNI：You Aren't Gonna Need It ＝ 今必要ないものは作らない）
    • 1回きりの単純な処理
    • パターンのためのパターン（過剰抽象化）

    順番は「まず素朴に書き、痛みが出てからパターンで整理する」です。

      問題 → 素朴な設計 → 痛みが出た → パターンで整理

    5.デザインパターンを覚える人が伸びない理由

    ここからは動画「デザインパターンを覚える人が伸びない理由」（IT技術屋のボヤキ）の内容です。テーマは 「デザインパターンは『覚える』のではなく、問題を経験した後に『出会う』もの」 です。

    GoF の23パターンを暗記しても実務で使えない人が多いのは、パターンが「問題に対する解決策」なのに、その問題を経験していないからです。覚えた人ほど「パターンを使いたい病」にかかって過剰設計になりやすい。伸びる人はまず問題にぶつかって苦労し、その後でパターンを知って理解します。パターンは道具箱として存在を知っておけばよく、使わない判断こそが大事、という話です。

    5.1 デザインパターンを覚えても使えない人

    • 23パターンを全部暗記し、本を何冊も読んだのに、実務で全く使えない人が多い
    • 理由は 使いどころが分からない から。シングルトンやファクトリーを説明できても、目の前のコードにどう適用するか が分からない。知識と実践が結びついていない
    • 試験勉強のように覚えて「自分はデザインパターンを知っている」と 自己満足 しているが、使えなければ意味がない。知識を詰め込むだけではエンジニアとして伸びない

    5.2 パターンは解決策であって問題ではない

    • 多くの人は、問題を知らないまま解決策を覚えようとする。問題を知らないと解決策も理解できない
    • 例：オブザーバーパターンの定義（1つのオブジェクトの状態が変わったら、依存するすべてのオブジェクトに通知する）は覚えられても、なぜ必要か・どんな問題を解決するかを体験していないとピンとこない
    • 薬の名前を覚えても医者にはなれない：薬の名前と効能を暗記しても、どの症状にどの薬を使うかは患者を診ないと分からない。同じように、コードが何に苦しんでいるか、どのパターンを当てれば楽になるかを診断するには、コードと格闘する経験が必要
    • if-else が20個並んだコードを保守した経験があれば、ストラテジーパターンを見て「これだ」となる。問題を経験し、自分なりに解決した後でパターンを知ると「先人も同じことを考えていたのか」と感動する。この 順序 が大事

    5.3 パターンを使いたい病

    • 「このパターンを使いたい」から設計が始まる ＝ 手段の目的化
    • 新しいプロジェクトで、問題を分析する前に「今回はファクトリーを使おう」と決めてしまう。シンプルに new すれば十分な場合もあるのに、必要ないのにストラテジーやデコレーターを導入し、過剰設計 になる
    • 本人は良い設計をしていると思っているが、後から入った人は「なぜこんなに複雑なのか」と困惑する。このギャップが問題
    • 知らなければシンプルに書くのに、知っているから使いたくなる。知っているからこそ陥る罠で、知識が足かせ になることもある

    5.4 伸びる人の学び方

    伸びる人は、パターンを覚える前にまず実際のコードで 問題にぶつかります。

    1. if-else が10個並んだコードを書く。最初は動くのでそれでよい
    2. 条件が増えるたびに if-else を追加し、20個、30個と増えて保守が大変になり、バグが増える
    3. そこで初めて問題に気づき「何とかしたい」と思うが、どうすればいいか分からない
    4. そのタイミングでストラテジーパターンを知り、「まさにこれが欲しかった」と感動する
    5. 苦労した分だけ価値が分かり、次に同じ問題に出会ったとき すぐ適用できる

    順序は 「問題の経験 → パターン」。経験と知識が結びつくことで、暗記では得られない理解になります。

    5.5 デザインパターンとの正しい付き合い方

    • 覚えるな（暗記しようとするな）。実際の問題の中で出会うのがベスト
    • 「こういうパターンがあるらしい」というレベルで 道具箱 として存在を知っておき、詳細は必要になったときに調べればよい。「確かストラテジーパターンというのがあったな」と思い出せれば十分
    • パターンは問題を解決するためにあり、パターンを使うために問題を作るのではない。この順序を間違えると過剰設計になる
    • 使わなくて済むなら使わない。知っていてあえて使わない判断ができるのが上級者。知識をひけらかすのではなく、必要なときだけ使う

    動画のまとめ

    • パターンは問題への解決策。問題を経験していないと本当には理解できない
    • 「パターンを使いたい病」は過剰設計を生む
    • 覚えるな、出会え。苦労してから学ぶ。使わない判断こそ大事

    6.よくある誤解

    誤解1：「パターンを全部覚えれば設計がうまくなる」

    23パターンを暗記しても、どの問題にどのパターンが効くかは、問題を経験しないと分かりません。名前と構造を知っていることと、目の前のコードに適用できることは別です。存在を道具箱として知っておき、詳細は必要になったときに調べれば十分です。

    誤解2：「最初からパターンを入れておけば、将来の変更に強くなる」

    将来起きる「かもしれない」問題への先回りは YAGNI に反し、過剰抽象化になりがちです。まず素朴に書き、同じ構造の問題が2回以上現れて痛みが出たときにパターンで整理します。

    誤解3：「パターンを使わないのは知識が足りないから」

    知っていてあえて使わない判断ができることが、パターンを本当に理解している証拠です。シンプルに書けば済む場面では、パターンを使わない方がチームにとって読みやすいコードになります。

    7.まとめ

    • パターン ＝ 名前付きの設計解。共通語彙 になる
    • 生成・構造・振る舞い の3分類
    • Factory / Strategy / Observer がクラス設計で頻出
    • 問題が先、パターンは後
    • 覚えるな、出会え。使わない判断こそ大事
