    20 責務の割り当て

    オブジェクトの種類の整理 — 「〜オブジェクト」をどの観点で見分けるか

    値オブジェクト、エンティティ、DTO、ドメインオブジェクト、データベースモデル、設定オブジェクト、コレクションオブジェクト、サービスオブジェクト……。設計の話に出てくるこれらの名前は、同じ基準で並べた分類ではありません。「業務の何を表すか」「どの層の都合か」「どんな定石か」という3つの観点で整理し、それぞれの性質・コード例・使いどころ・迷ったときの判断フローをまとめます。

    もとにしたノート：20_責務の割り当て/06_オブジェクトの種類の整理

    ひとことで言うと

    「〜オブジェクト」という名前は、① 業務の何を表すか（エンティティ・値オブジェクト・ドメインサービス）、② どの層の境界の都合か（DTO・DB モデル）、③ どんな定石か（コレクション・設定・サービスオブジェクト）という 別々の観点 でつけられています。観点が違うので重なることもあります。最初から全部そろえず、困りごとが出たところで対応する種類を導入しましょう。

    1.このページで扱うこと

    設計の話をしていると、いろいろな「〜オブジェクト」が出てきます。

    値オブジェクト、エンティティ、DTO、ドメインオブジェクト、データベースモデル、設定オブジェクト、コレクションオブジェクト、サービスオブジェクト

    これらは 同じ基準で並べた分類ではありません。混乱する一番の理由はここにあります。このページでは、それぞれを どの観点で見た名前なのか という軸で整理し、見分け方と使いどころをまとめます。

    個別の詳しい解説は次のページにあります。

    • エンティティと値オブジェクトの基本 → ドメインを表すクラス
    • 値オブジェクトの書き方 → 値オブジェクトと完全コンストラクタ
    • サービスにロジックを寄せすぎる問題 → Tell, Don't Ask と貧血モデル
    • DDD での位置づけ → 42章：エンティティと値オブジェクト / 42章：ドメイン層とユースケース

    2.全体像：3つの観点で分ける

    観点問い該当するもの
    ① 業務の何を表すか（ドメインの中の役割）このオブジェクトは業務上の何か？ドメインオブジェクト（総称）、エンティティ、値オブジェクト、ドメインサービス
    ② どこを運ぶ・どこに置くか（層の境界）どの層の都合で作った形か？DTO、データベースモデル
    ③ どんな定石か（汎用的なクラスの型）どんな困りごとを解くための形か？コレクションオブジェクト、設定オブジェクト、サービスオブジェクト

    ポイントは次の2つです。

    • 分類どうしが重なる ことがあります。たとえば OrderLines（コレクションオブジェクト）は、同時に値オブジェクトであり、ドメインオブジェクトでもあります。
    • 「サービス」は①と③の両方に出てきます。業務ルールを担うドメインサービスと、処理の手順を組み立てるアプリケーションサービスは別物です（→ 7. サービスオブジェクト）。

    3.ドメインオブジェクト（総称）

    業務の概念やルールを表すオブジェクト全般 を指す言葉です。具体的な1つの種類ではありません。

    Eric Evans は『ドメイン駆動設計』（2003）で、ドメインオブジェクトを次の3つに分類しました。Martin Fowler はこれを「Evans Classification」として紹介しています。

    分類Evans の定義（要約）例
    エンティティ時間や表現が変わっても続く 固有の同一性 を持つもの顧客、注文、船、賃貸契約
    値オブジェクト属性の組み合わせだけ に意味があるもの日付、金額
    サービスドメインの中で 単独で成り立つ操作送金、料金計算

    Fowler 自身も、これらの用語は正確に定義するのが難しく、「見れば分かる」種類の分類だと書いています。大事なのは、厳密な定義を覚えることではなく、それぞれの性質を理解して見分けられるようになる ことです。

    4.エンティティ（Entity）

    4.1 性質

    • ID で区別する。属性が全部同じでも ID が違えば別物、属性が変わっても ID が同じなら同じもの
    • ライフサイクルがある。作成 → 変更 → 完了・削除と状態が移り変わる
    • 状態が変わる（ミュータブル）。ただし、変更はメソッドを通して、ルールを守りながら行う

    4.2 例

    class Order {
  private status: 'DRAFT' | 'CONFIRMED' | 'SHIPPED' = 'DRAFT';

  constructor(
    readonly id: OrderId,        // 同一性の鍵
    private lines: OrderLines,
  ) {}

  confirm(): void {
    if (this.status !== 'DRAFT') throw new Error('確定済みの注文です');
    if (this.lines.isEmpty()) throw new Error('明細がありません');
    this.status = 'CONFIRMED';   // 状態の変更はメソッド経由のみ
  }

  equals(other: Order): boolean {
    return this.id.equals(other.id);  // ID だけで比較する
  }
}

    4.3 よくある誤解

    • 「ID カラムがあるもの = エンティティ」ではありません。DB の都合で ID を振っているだけの明細行は、業務上は値オブジェクトであることもあります（→ 9. データベースモデル）。
    • セッター（setter）を並べるだけのエンティティは「貧血モデル」（データの入れ物に、名前だけエンティティと付けた状態）になりがちです（→ Tell, Don't Ask と貧血モデル）。

    5.値オブジェクト（Value Object）

    5.1 性質

    Fowler の bliki「ValueObject」（2016）によると、値オブジェクトとは 同一性ではなく、プロパティの値によって等しさが決まる複合オブジェクト です。例として座標、金額、日付の範囲が挙げられています。

    性質意味
    値で等価1000円と1000円は同じもの
    不変（イミュータブル）作った後で変えない。変えたいときは 新しいオブジェクトに置き換える
    自己検証不正な値ではそもそも作れない（完全コンストラクタ）
    振る舞いを持つ計算・比較・書式化などのロジックを、その値自身が持つ

    5.2 なぜ不変にするのか：エイリアシングのバグ

    Fowler は不変にする理由として エイリアシング（別名参照）のバグ を挙げています。エイリアシングとは、1つのオブジェクトを複数の変数が指している状態のことです。

    ✕ 可変な日付オブジェクトを2か所で共有してしまった例 
    const retirementDate = new MutableDate(2026, 10, 30);
const partyDate = retirementDate;      // 同じオブジェクトを指している

partyDate.setDay(31);                  // パーティーを1日後ろにずらしたつもり
console.log(retirementDate.day);       // 31 ← 退職日まで変わってしまった！

    不変にしておけば「変更 = 新しいオブジェクトを作る」ことになるので、共有していても他方に影響しません。

    5.3 例

    class Money {
  private constructor(readonly amount: number, readonly currency: 'JPY' | 'USD') {}

  static of(amount: number, currency: 'JPY' | 'USD'): Money {
    if (!Number.isInteger(amount) || amount < 0) throw new Error('金額が不正です');
    return new Money(amount, currency);
  }

  add(other: Money): Money {
    if (this.currency !== other.currency) throw new Error('通貨が違います');
    return Money.of(this.amount + other.amount, this.currency);  // 新しい値を返す
  }

  equals(other: Money): boolean {
    return this.amount === other.amount && this.currency === other.currency;
  }
}

    5.4 何を値オブジェクトにするか

    Fowler は、文字列などの プリミティブ型（文字列・数値などの言語に組み込みの基本的な型）の代わりに 電話番号型のような型を作ることも勧めています。そうすると意味が明確になり、検証を1か所にまとめられ、「ID 番号どうしの足し算」のような無意味な操作もできなくなります。

    候補になりやすいもの：金額、数量、メールアドレス、電話番号、郵便番号、住所、期間（開始〜終了）、割合、座標、ID 型（OrderId など）

    5.5 用語の混乱に注意

    昔の J2EE（Java のエンタープライズ向け仕様。現在の Jakarta EE）の文献では、DTO のことを「Value Object」と呼んでいた時期がありました。Fowler はこれを「用語の混乱の元」と書いています。今ではこの使い方はほとんど見なくなりましたが、古い Java の資料を読むときは注意が必要です。

    6.エンティティと値オブジェクトの見分け方

    問いYes なら
    同じ値を持つ2つは 区別する必要がある か？エンティティ
    中身が変わっても 同じものとして追跡したい か？エンティティ
    中身が同じなら 入れ替えても困らない か？値オブジェクト
    他の何かの 属性・説明 として使われるか？値オブジェクト

    同じ概念でも、文脈によって答えが変わります。 Fowler は住所を例に挙げています。

    通販システムの「配送先住所」

    中身が同じなら同じ扱いで構わないので 値オブジェクト

    郵便・地図システムの「住所」

    1件ずつ管理・更新するので エンティティ

    迷ったら まず値オブジェクトとして考え、ID による追跡がどうしても必要になったらエンティティにする、という進め方がおすすめです。値オブジェクトのほうが不変で扱いやすいからです。

    7.サービスオブジェクト（Service）

    「サービス」は意味の広い言葉で、少なくとも次の3種類があります。混ぜて考えないことが大切です。

    種類置き場所役割扱うデータ例
    ドメインサービスドメイン層特定のエンティティに置くと不自然な 業務ルールエンティティ・値オブジェクト口座間の送金ルール、重複チェック
    アプリケーションサービスアプリケーション層ユースケースの 手順を組み立てる（業務ルールは持たない）DTO を受け取り・返す「注文を確定する」処理全体
    インフラサービスインフラ層外部とのやりとりの 技術的な詳細技術的なデータメール送信、決済 API の呼び出し

    7.1 共通する性質

    • 状態を持たない（ステートレス）。何を渡されたかだけで結果が決まる
    • 名前は動詞的 になる（TransferService、ConfirmOrderUseCase）

    7.2 例

    // ドメインサービス：2つの口座にまたがる業務ルール
class TransferService {
  transfer(from: Account, to: Account, amount: Money): void {
    if (from.isFrozen() || to.isFrozen()) throw new Error('凍結口座には送金できません');
    from.withdraw(amount);
    to.deposit(amount);
  }
}

// アプリケーションサービス：手順を組み立てるだけ
class ConfirmOrderUseCase {
  constructor(
    private orders: OrderRepository,
    private mailer: Mailer,            // インフラサービス（インターフェース経由）
  ) {}

  async execute(input: ConfirmOrderInput): Promise<ConfirmOrderOutput> {  // DTO
    const order = await this.orders.findById(new OrderId(input.orderId));
    order.confirm();                   // ルールはエンティティに任せる
    await this.orders.save(order);
    await this.mailer.sendConfirmation(order.id);
    return { orderId: order.id.value, status: 'CONFIRMED' };
  }
}

    7.3 注意点：サービスにロジックを寄せすぎない

    Fowler は「貧血ドメインモデル」（2003）で、ロジックを全部サービスに置き、ドメインオブジェクトを getter と setter の詰め合わせ にしてしまう設計を批判しています。

    If all your logic is in services, you've robbed yourself blind.

    （ロジックが全部サービスにあるなら、自分で自分の得るものを奪っている）

    Evans も、アプリケーション層は 薄く保ち、業務ルールや知識は持たず、作業の調整と委譲だけを行う としています。

    Rails の世界でよく使われる「Service Object」（call メソッドを1つだけ持つクラス）にも、同じ理由で批判があります。call の中に関係ない処理が膨らんでいく、サービスどうしが密に結びつく、モデルの設計の弱さを隠す逃げ道になる、といった点です。使うなら 責務は1つ、公開メソッドは少なく、戻り値の形はそろえる というルールを守ります。

    判断の目安

    「この処理はどのエンティティ／値オブジェクトの仕事か？」と考えて、どこにも自然に置けないときだけ ドメインサービスにする。

    8.DTO（Data Transfer Object）

    8.1 性質

    • データを運ぶためだけの入れ物。ロジックは持たない（持ってもシリアライズ ＝ 送受信できる形式への変換 程度）
    • getter・setter、または public なフィールドだけの単純な構造
    • 不変にしておくと扱いやすい

    8.2 もともとの目的

    Fowler の『エンタープライズアプリケーションアーキテクチャパターン（PoEAA）』（2002）での DTO の定義は、プロセス間でデータを運び、メソッド呼び出しの回数を減らすためのオブジェクト です。リモート呼び出しは1回ごとのコストが大きいので、細かく何度も呼ぶ代わりに、必要なデータを1つの箱にまとめて一度に送る、という発想です。

    8.3 「ローカル DTO」への注意

    Fowler は bliki「LocalDTO」で、同じプロセスの中で DTO を使うことには、たいてい害がある と書いています。

    • ドメインオブジェクトと DTO の間の詰め替えにかかるコストは大きく、O/R マッピングの次につらい（Randy Stafford の言葉）
    • 「将来分散するかもしれないから」という理由で先に DTO を入れるべきではない。まずは ドメインオブジェクトをそのまま扱うサービス層 から始めればよい

    ただし、次のような場合は DTO（に近いもの）を使う価値があると認めています。

    • 画面の形とドメインの形が大きく違う とき（その画面に限って、画面専用の形に変換する）
    • スレッドやキューの境界 を越えてメッセージとして渡すとき

    8.4 現代の Web アプリでの使い方

    今の Web アプリでは、DTO は主に 外部との境界 で使われます。

    使いどころ理由
    API のリクエスト／レスポンス内部構造を外に出さない。パスワードハッシュなど見せたくない項目を隠す
    API のバージョン管理内部の設計を変えても、外向きの形（契約）は保てる
    ユースケースの入力と出力アプリケーション層の外側にドメインオブジェクトを漏らさない（クリーンアーキテクチャ）
     
    // レスポンス DTO：外に見せる形だけ
type OrderResponseDto = {
  readonly id: string;
  readonly total: number;
  readonly status: 'DRAFT' | 'CONFIRMED' | 'SHIPPED';
};

    判断の目安

    境界（外部 API・画面・メッセージ）では DTO、同じ層の中ではドメインオブジェクトをそのまま渡す。全部の層の間に DTO を挟むと、詰め替えのコードばかり増える。

    9.データベースモデル（永続化モデル）

    9.1 性質

    • DB のテーブル構造に合わせたオブジェクト
    • ORM（Prisma、TypeORM、Rails の ActiveRecord、Django の Model、JPA など。テーブルとオブジェクトを対応づけるライブラリ）が扱う形
    • 「保存しやすい形」であり、「業務的に正しい形」と一致するとは限らない

    9.2 2つの代表的なパターン（PoEAA）

    パターン仕組み例向いているもの
    Active Recordオブジェクト自身が保存・読み込みを行う（user.save()）Rails、Laravel Eloquent、DjangoCRUD 中心のシンプルな業務
    Data Mapper別のクラス（マッパー・リポジトリ）が、オブジェクトと DB の間を変換するHibernate/JPA、Doctrine、TypeORM の Data Mapper モード業務ルールが複雑なドメイン、既存の DB 構造に合わせる必要があるとき

    Active Record では DB モデルとドメインオブジェクトが1つのクラス になります。手軽ですが、業務ロジックが DB の都合に引きずられやすくなります。

    9.3 「JPA の @Entity」と「DDD のエンティティ」は別物

    Java の JPA では、DB に保存するクラスに @Entity を付けます。しかし、これは DDD のエンティティとは 別の概念 です。

    • 業務上は値オブジェクトである注文明細も、DB で行を識別するために ID が必要なので @Entity を付けることになる
    • 集約（一緒に整合性を保つオブジェクトのまとまり）の境界を JPA で直接表す方法はない

    そのため、複雑なドメインでは ドメインモデルと永続化モデルを分けて、間に変換処理（マッピング）を置く 方法がよく推奨されます。ただし分けると、変換コードが増え、どこまで読み込むか（オブジェクトのつながりのどこまでを変換するか）の判断も必要になります。

    判断の目安

    最初は1つのモデルで始め、DB の都合でドメインのコードが歪んできたら分ける。

    増田本第6章の「オブジェクトはオブジェクトらしく、テーブルはテーブルらしく」の整理は 42_ソフトウェア設計 のノート『08_オブジェクトとテーブルの設計』、DB 側のコト中心設計は 68_データアーキテクチャ のノート『07_コトに注目するテーブル設計』にあります。

    分けた場合：リポジトリの中で変換する 
    class PrismaOrderRepository implements OrderRepository {
  async findById(id: OrderId): Promise<Order> {
    const row = await prisma.order.findUniqueOrThrow({   // DB モデル
      where: { id: id.value },
      include: { lines: true },
    });
    return OrderMapper.toDomain(row);                     // ドメインオブジェクトへ変換
  }
}

    10.コレクションオブジェクト（ファーストクラスコレクション）

    10.1 性質

    配列やリストを1つのクラスで包み、そのコレクションに関するルールと操作をまとめたもの です。Jeff Bay の「オブジェクト指向エクササイズ（Object Calisthenics）」（『ThoughtWorks アンソロジー』所収）の9つのルールの1つ、「ファーストクラスコレクションを使う」が出どころです。このルールでは、コレクションを持つクラスは 他のインスタンス変数を持たない ことを求めています。増田亨『現場で役立つシステム設計の原則』では コレクションオブジェクト とも呼びます。9規則の一覧は Object Calisthenics。

    10.2 なぜ配列やコレクションはコードを複雑にするか

    素の配列・リストをそのまま扱うと、次の関心事が 使う側のコード各所 に散らばります。

    複雑さの源例
    ループ処理合計・絞り込み・変換がサービス層に並ぶ
    要素数の変化追加・削除のたびに上限チェックが重複する
    個々の要素の状態要素が可変だと、一覧全体の整合性が追い切れない
    件数に関する業務ルール「重要顧客だけ」「売れ筋だけ」が if と filter の山になる

    コレクション型の基本操作（add / remove）以上の 業務上の操作 が必要なときは、ロジックを専用クラスに閉じ込める判断をします。

    10.3 何がうれしいか

    素の配列だとコレクションオブジェクトにすると
    「最大10件」のチェックが、追加する場所ごとに散らばるルールが1か所にまとまる
    合計や絞り込みの処理が、使う場所ごとに書かれるtotal() activeOnly() のように名前付きのメソッドになる
    外から push や splice で自由に書き換えられる変更の入口を制限できる
    Item[] が何の集まりなのか型から分からないOrderLines という名前で意味が伝わる

    オブジェクト指向のコツは、使う側が簡単になるよう、使われる側（コレクションオブジェクト）に処理を寄せる ことです。呼び出し側でまたループを書きたくなったら、「その操作をコレクション側のメソッドに移せないか」を考えます。

    10.4 例

    class OrderLines {
  private static readonly MAX = 10;

  private constructor(private readonly lines: readonly OrderLine[]) {}

  static of(lines: OrderLine[]): OrderLines {
    if (lines.length > OrderLines.MAX) throw new Error(`明細は${OrderLines.MAX}件までです`);
    return new OrderLines([...lines]);   // 防御的コピー
  }

  add(line: OrderLine): OrderLines {     // 不変：新しいコレクションを返す
    return OrderLines.of([...this.lines, line]);
  }

  total(): Money {
    return this.lines.reduce((sum, l) => sum.add(l.subtotal()), Money.of(0, 'JPY'));
  }

  isEmpty(): boolean {
    return this.lines.length === 0;
  }
}

    防御的コピー とは、受け取った配列をそのまま持たずにコピーしておき、外から元の配列を書き換えられても影響を受けないようにすることです。

    10.5 コレクションオブジェクトを安定させる

    内部のリストへの参照を外に渡すと、呼び出し側の push / splice で中身が壊れます。安定させる定石は次のとおりです。

    やり方内容
    操作ロジックを中に移す追加・削除・絞り込みはコレクションオブジェクトのメソッドにする
    同じ型を返すadd の結果も OrderLines（新しいインスタンス）として返す
    不変コレクションを渡すどうしても配列が必要ならコピーや Object.freeze / readonly で渡す
    要素も不変にする要素が可変だと一覧だけ不変でも安心できない → 値オブジェクトと組み合わせる
    ✕ 悪い例：内部参照をそのまま返す 
    getLines(): OrderLine[] {
  return this.lines; // 外から破壊できる
}
    ◯ 良い例：操作は自分で行い、新しいコレクションオブジェクトを返す 
    add(line: OrderLine): OrderLines {
  return OrderLines.of([...this.lines, line]);
}

// 配列が必要なとき: コピーや readonly で渡す
asReadonly(): readonly OrderLine[] {
  return this.lines;
}

    破壊的な配列操作の一般論は 46_メソッド設計 のノート『07_引数の破壊的変更とイミュータブル』を参照してください。

    10.6 コレクションオブジェクトは業務の関心事

    List<Customer> ではなく Customers / ImportantCustomers のように、業務で使う「〜の集まり」 をクラス名にします。関心事とクラスが1対1だと、ルール変更時に開くファイルが直感的に決まります。

    class Customers {
  constructor(private readonly items: readonly Customer[]) {}

  important(): Customers {
    return new Customers(this.items.filter((c) => c.isImportant()));
  }

  count(): number {
    return this.items.length;
  }
}

    中の配列をそのまま返す getter（getLines(): OrderLine[]）を作ると、外から書き換えられて意味がなくなります。返すなら readonly の型にするか、コピーを返します。

    11.設定オブジェクト（Configuration Object）

    11.1 性質

    環境変数や設定ファイルの値を、型の付いた1つのオブジェクトにまとめたもの です。

    • 型が付いている（string のままではなく number や URL などに変換済み）
    • 起動時に検証 する（必須項目の不足や形式の誤りを、最初に見つける）
    • 作った後は不変
    • 必要なクラスに コンストラクタで渡す（どこからでも process.env を読まない）

    ASP.NET Core の Options パターン が代表例です。.NET 6 で追加された ValidateOnStart() を使うと、設定の誤りがあればアプリが起動しません。これを付けないと、その設定を最初に使うリクエストまで誤りに気づけません。

    11.2 例（TypeScript + zod）

    zod は、データの形をスキーマとして書いて検証できる TypeScript のライブラリです。

    import { z } from 'zod';

const ConfigSchema = z.object({
  DATABASE_URL: z.string().url(),
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  MAIL_TIMEOUT_MS: z.coerce.number().int().positive().default(5000),
});

export type AppConfig = Readonly<z.infer<typeof ConfigSchema>>;

// 起動時に1回だけ読み込んで検証する。誤りがあればここで落ちる
export const loadConfig = (): AppConfig => Object.freeze(ConfigSchema.parse(process.env));
    // 使う側は設定オブジェクトを受け取るだけ（テストでは差し替えられる）
class SmtpMailer implements Mailer {
  constructor(private readonly config: Pick<AppConfig, 'MAIL_TIMEOUT_MS'>) {}
}

    11.3 似た言葉：「オプションオブジェクト」

    引数が多い関数で、引数を1つのオブジェクトにまとめるものも「設定オブジェクト」と呼ばれることがあります（fetch(url, { method, headers }) の第2引数など）。リファクタリングの「引数オブジェクトの導入」と同じ考え方です。アプリ全体の設定とは役割が違うので、文脈で区別します。

    12.総まとめ

    12.1 比較表

    種類一言で同一性ロジック可変性主な置き場所
    ドメインオブジェクト業務を表すオブジェクトの総称–あり–ドメイン層
    エンティティID で追跡する業務上の主体IDあり（状態の遷移とルール）可変（メソッド経由）ドメイン層
    値オブジェクト意味とルールを持った値値で比較あり（計算・検証）不変ドメイン層
    ドメインサービスどこにも置けない業務ルールなしあり状態なしドメイン層
    アプリケーションサービスユースケースの手順書なし調整のみ状態なしアプリケーション層
    DTO境界を越えるための箱なしなし不変にするのが望ましい境界（API・ユースケースの入出力）
    DB モデルテーブルの写しDB の主キー少ない可変インフラ層
    コレクションオブジェクトルール付きのリスト値で比較が多いあり（集計・制約）不変が望ましい主にドメイン層
    設定オブジェクト型付き・検証済みの設定なし検証程度不変起動処理 → 各クラスへ注入

    12.2 迷ったときの判断フロー

    12.3 実務の目安

    規模・性質おすすめの構成
    小さな CRUD アプリActive Record の DB モデルを中心にする。値オブジェクトは要所（金額など）だけ。DTO は API の境界だけ
    業務ルールが多いアプリエンティティ・値オブジェクト・コレクションでドメインを厚くする。アプリケーションサービスは薄くする。DTO は境界に置く
    大規模・複雑なドメインドメインモデルと永続化モデルを分ける（Data Mapper／リポジトリ）。必要に応じて読み取り専用のモデルも分ける（CQRS）

    最初から全部の種類をそろえる必要はありません。 困りごと（チェックが散らばる、DB の都合で業務コードが歪む、内部構造が API に漏れる、など）が出てきたところで、対応する種類を導入します。

    13.よくある誤解

    誤解1：「ID カラムがあるものはエンティティ」

    DB の都合で ID を振っているだけの明細行は、業務上は値オブジェクトであることもあります。JPA の @Entity と DDD のエンティティも別の概念です。エンティティかどうかは「業務上、ID で追跡する必要があるか」で決めます。

    誤解2：「サービスはどれも同じもの」

    「サービス」にはドメインサービス・アプリケーションサービス・インフラサービスの少なくとも3種類があり、置き場所も役割も違います。業務ルールを持つのはドメインサービスだけで、アプリケーションサービスは手順の調整だけを行います。

    誤解3：「層の間には必ず DTO を挟むべき」

    DTO はもともとリモート呼び出しの回数を減らすためのものです。Fowler は同じプロセス内での DTO の多用はたいてい有害だとしています。DTO は外部 API・画面・メッセージなどの 境界 に置き、同じ層の中ではドメインオブジェクトをそのまま渡します。

    14.まとめ

    • 「〜オブジェクト」は ① 業務の何を表すか ② どの層の境界の都合か ③ どんな定石か という別々の観点の名前で、重なることもある
    • エンティティ は ID で追跡し、状態の変更はメソッド経由。値オブジェクト は値で等価・不変・自己検証。迷ったらまず値オブジェクトとして考える
    • サービス はドメイン・アプリケーション・インフラの3種類。ドメインサービスは「どこにも自然に置けない」ときだけ
    • DTO は境界で使う。DB モデル は最初は1つで始め、ドメインが歪んだら分ける
    • コレクションオブジェクト で配列のルールと操作を1か所に、設定オブジェクト で設定を型付き・起動時検証・不変に
    • 全部を最初からそろえず、困りごとが出たところで導入する

    次は 区分オブジェクトと状態遷移 → 業務ロジックをデータと一体にする に進みます。
