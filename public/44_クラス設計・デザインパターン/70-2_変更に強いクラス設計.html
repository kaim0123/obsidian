    70 品質と運用

    変更に強いクラス設計 — リファクタリングで小さく頻繁に直す

    クラス設計は一度決めたら終わりではなく、リファクタリングで少しずつ良くしていくものです。直すタイミング、Extract Class と Move Method、異なるクラスの重複コードのなくし方、クラスを段階的に分割する手順、レガシーコードへの適用、技術的負債との向き合い方を解説します。

    もとにしたノート：70_品質と運用/02_変更に強いクラス設計の実践

    ひとことで言うと

    「動いているから触らない」より、テストを足してから、1責務ずつ小さく直す ほうが長期的に安全です。クラス改善の基本の道具は、責務の塊を新クラスへ移す Extract Class と、メソッドをデータのあるクラスへ移す Move Method の2つです。

    1.このページで扱うこと

    リファクタリング（外から見た振る舞いを変えずに、コードの内部構造を改善すること）を通じてクラス設計を改善する実践手順を学びます。

    • リファクタリングのタイミング
    • Extract Class / Move Method の考え方：異なるクラスの重複したコードをなくす手順も
    • クラス分割の段階的な進め方
    • レガシーコードへの適用
    • 技術的負債との向き合い方

    2.リファクタリングのタイミング

    タイミング例
    機能追加の前触る前に構造を整える
    バグ修正のついで原因が構造にあるとき
    テスト追加後安全網がある状態で
    レビュー指摘後小さな PR で直す

    「動いているから触らない」 より、小さく頻繁に直す ほうが長期的に安全です。放っておくと構造の歪みが積み重なり、いざ直すときに大工事になってしまうからです。

    3.Extract Class / Move Method の考え方

    マーティン・ファウラー（Martin Fowler）が『リファクタリング』でまとめた技法のうち、クラス設計で特に重要な2つです。

    3.1 Extract Class

    1つのクラスに溜まった責務の 塊 を新クラスへ移します。

      OrderService
      │
      Extract → TaxCalculator（税計算ブロック）
      Extract → DiscountApplier（割引ブロック）

    3.2 Move Method

    メソッドが 他クラスのデータを多用 しているとき、そのクラスへ移します。自分のデータより他人のデータに興味があるメソッドは Feature Envy（機能の横恋慕）というコードの臭いで、Move Method はその解消法です。

    // Before: OrderService.calculateLineTotal(line)
// After:  line.subtotal()  — Expert へ移動

    明細の小計を計算するのに必要な数量と単価は OrderLine が持っているので、計算も OrderLine に任せます。「情報を持つクラスに処理させる」という GRASP の Information Expert の考え方です（GRASP）。

    3.3 異なるクラスの重複したコードをなくす

    同じ「段落」や計算が複数クラスにコピーされているときは、次の順で寄せます（増田亨『現場で役立つシステム設計の原則』第1章）。

    1. 各クラスで重複部分を メソッドに抽出 する（Extract Method。46_メソッド設計 のノート『04_Extract_Method』）
    2. 参照関係がある 場合 — 参照する側の呼び出しを、参照される側のメソッド呼び出しに置き換える（Move Method）
    3. 参照関係がない 場合 — 共通の置き場として新しい小さなクラスを作り、双方から呼ぶ（Extract Class）
      ClassA.calcTax()  ─┐
                     ├─→ 共通なら Tax クラス（または既存ドメインオブジェクト）へ
  ClassB.calcTax()  ─┘

    寄せ先は業務用語のクラスに

    重複を「共通ユーティリティ」に逃がしすぎると、業務の関心事が見えなくなります。寄せ先はできるだけ 業務用語のクラス（ドメインを表すクラス）にします。原則としての DRY（Don't Repeat Yourself：同じ知識を繰り返し書かない）は、48_原則 のノート『01_DRY_KISS_YAGNI』を参照してください。

    4.クラス分割の段階的な進め方

    1. テストを1本 足す（最低限の安全網）
    2. 変更理由を1つ 選び、関連メソッドを特定
    3. 新クラスを作り フィールドとメソッドを移動
    4. 呼び出し元を更新（旧クラスは委譲で互換維持も可）
    5. テスト実行 → 次の塊へ

    4. の「委譲」は、旧クラスのメソッドを残したまま、中身では新クラスを呼ぶだけにすることです。呼び出し元を一度に全部書き換えなくて済みます。

    ✕ 一気に10クラス

    どこで壊れたか分からなくなり、レビューもできません。

    ◯ 1責務ずつ Extract

    1回ごとにテストで確かめながら進められます。

    「変更理由」で分ける考え方は 単一責任の原則、どのクラスに責務を置くかは GRASP を参照してください。

    5.レガシーコードへの適用

    レガシーコード（テストがなく、変更が怖い既存コード）では、いきなり理想設計 は危険です。

    原則内容
    理解してから変える振る舞いをテストで固定
    境界を守る新コードは新クラス、旧は薄いアダプタ
    絶えず小さく1 PR = 1 Extract
    触らない勇気変化しない領域はそのまま

    アダプタ：古いコードと新しいコードの間に立ち、呼び方の違いを吸収する薄いクラス。

    レガシーとの向き合い方の全体像は レガシーと設計レビュー（42章） も参照してください。

    6.技術的負債との向き合い方

    技術的負債 は、設計を先送りした結果の 将来のコスト です。お金の借金と同じで、返さないと利息（変更のたびの余計な手間）が膨らみます。

      負債の可視化 → 影響・頻度で優先度 → スプリントに小さく組み込む
    やること内容
    記録チケット・ADR・コメントで「なぜこうなったか」を残す
    返済機能開発と 同時に 少しずつリファクタ

    ADR（Architecture Decision Record）：設計判断とその理由を短く記録する文書。スプリント：1〜2週間ほどの開発の区切り。

    完璧を目指さず、変化の多い箇所から 投資します。技術的負債の考え方は 技術的負債（41章） でも扱っています。

    7.よくある誤解

    誤解1：「リファクタリングは、まとまった時間を取ってから一気にやるもの」

    大規模な作り直しは、壊れたときに原因を追えず、レビューもできません。機能追加の前やバグ修正のついでなど、普段の開発の中で 小さく頻繁に 直すのが基本です。

    誤解2：「重複したコードは共通ユーティリティにまとめればよい」

    重複をなくすこと自体は大切ですが、何でも Utils に逃がすと業務の関心事が見えなくなります。寄せ先は、参照関係があれば参照される側のクラス、なければ Tax のような業務用語の小さなクラスにします。

    誤解3：「レガシーコードは理想の設計に作り直すべき」

    テストのないコードをいきなり理想形に書き換えるのは危険です。まず振る舞いをテストで固定し、新しいコードは新しいクラスに書いて旧コードとは薄いアダプタでつなぎます。変化しない領域は、あえて触らないことも選択肢です。

    8.まとめ

    • リファクタは追加・修正のタイミングで小さく
    • Extract Class / Move Method がクラス改善の基本
    • 段階的に1責務ずつ。テストとセット
    • レガシーは境界とアダプタで守りながら改善
