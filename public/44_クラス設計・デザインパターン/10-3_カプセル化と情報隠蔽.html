    カプセル化と情報隠蔽 — 内部を隠し、意味のある操作だけを公開する

    2.カプセル化の目的

    カプセル化 とは、データとそれを扱う処理をまとめ、内部を隠して公開操作だけを提供する ことです。

    目的効果
    整合性の保護不正な状態変更を防ぐ
    変更の局所化内部実装を変えても外部に影響しにくい
    意図の明確化「使ってよい操作」がはっきりする

    42章：オブジェクト指向とクラス の銀行口座の例が典型です。残高は直接触らせず、deposit / withdraw 経由にします。

    3.public / private / protected の考え方

    言語によって記法は異なりますが、考え方は共通です。これらを アクセス修飾子（誰がそのフィールドやメソッドを使えるかを決める指定）と呼びます。

    修飾誰がアクセスできるか設計上の意味
    privateクラス内部のみ実装の詳細。自由に変更してよい
    protectedクラスとサブクラス継承を前提とした拡張点
    public誰でもクラスの 契約（API）
     
    class Order {
  #lines = [];           // private
  addLine(line) { /* */ } // public — 外部が使う入口
}

    基本の方針

    デフォルトは private、必要なものだけ public が基本です。

    4.不変条件（Invariant）をクラス内に閉じ込める

    不変条件 とは、オブジェクトが常に満たすべきルールです。

    • 注文の合計は0未満にならない
    • 口座残高は負にならない
    • 生年月日は未来日にならない
    class OrderLine {
  constructor(product, quantity) {
    if (quantity <= 0) throw new Error('数量は正の数');
    this.quantity = quantity;
    this.product = product;
  }
}

    不変条件は クラスの境界内 で守ります。外からフィールドを直接いじられると、ルールが破られます。生成の時点で検証を済ませる書き方は 値オブジェクトと完全コンストラクタ でさらに詳しく扱います。

    5.情報隠蔽（Parnas）— 設計判断ごとに隠す

    David Parnas の 情報隠蔽 は、「データを隠す」だけでなく 変わりやすい設計判断を隠す 考え方です（歴史的な位置づけは クラス設計の変遷「情報隠蔽」）。

    隠すべきもの例
    データ構造リストか配列か
    アルゴリズム税計算の詳細
    外部システムDB・API の呼び方

    43章（モジュール設計）のカプセル化 と同じ原則が、クラスレベルで適用されます。

    6.getter/setter だけのカプセル化の落とし穴

    全フィールドに getter/setter（フィールドの値を読み出す・書き換えるだけのメソッド）を機械的につけると、ただの公開フィールド と変わりません。

    ✕ 悪い例 — カプセル化のつもりが意味がない 
    // 悪い例 — カプセル化のつもりが意味がない
class User {
  getEmail() { return this.email; }
  setEmail(e) { this.email = e; }  // 検証なし
}
    問題対策
    検証がない setterビジネスルールをメソッドに書く
    内部構造の露出コレクションは 防御的コピー（中身の複製を返して元を守る）・不変ビュー（読み取り専用の見せ方）
    過剰な公開「外に何が必要か」から逆算する

    カプセル化の本質

    「隠す」と「公開する」を意図的に設計する ことがカプセル化の本質です。データを外に渡して判断させるのではなく、オブジェクトに頼む書き方は Tell, Don't Ask と貧血モデル で扱います。

    7.よくある誤解

    誤解1：「フィールドを private にして getter/setter を付ければカプセル化できる」

    検証のない setter があれば、外から何でも書き込めるので公開フィールドと同じです。ビジネスルールを持った意味のある操作（deposit、addLine など）を公開して、初めて整合性が守られます。

    誤解2：「情報隠蔽 = データを隠すこと」

    Parnas の情報隠蔽は、データ構造だけでなく アルゴリズムや外部システムの呼び方など、変わりやすい設計判断 を隠す考え方です。隠しておけば、その判断を変えても外部に影響が出ません。

    誤解3：「あとで使うかもしれないから public にしておく」

    public は クラスの契約（API） で、一度公開すると変えにくくなります。デフォルトは private にし、「外に何が必要か」から逆算して必要なものだけを公開します。

    8.まとめ

    • カプセル化は整合性・変更耐性・意図の明確化のため
    • private を基本に、public は契約として最小限に
    • 不変条件はクラス内で守る
    • 情報隠蔽は変わりやすい設計判断ごと隠す
    • getter/setter だけでは不十分。意味のある操作を公開する
