    20 責務の割り当て

    値オブジェクトと完全コンストラクタ — 不正な値が存在できないクラスを書く

    金額や個数を number のまま使うと、不正な値・チェックの重複・引数の取り違えが起きます。値を専用のクラスにする「値オブジェクト」と、作った時点で正しさを保証する「完全コンストラクタ」を、クラスとしての書き方に絞って解説します。

    もとにしたノート：20_責務の割り当て/04_値オブジェクトと完全コンストラクタ

    ひとことで言うと

    値オブジェクト は、金額・個数・メールアドレスのような「値」を専用のクラスにしたものです。完全コンストラクタ で不正な値をその場で拒否し、不変 にしておけば、「存在すること自体が正しさの保証」になります。

    1.このページで扱うこと

    ドメインを表すクラス では、エンティティと値オブジェクトの違いを学びました。このページでは、値オブジェクトを実際にクラスとして書くときの技法 を掘り下げます。

    • プリミティブ型（number や string のような言語に最初からある基本の型）をそのまま使うと何が困るのか（プリミティブ型への執着）
    • 値オブジェクト の4つの性質
    • 不完全なオブジェクト（生焼けオブジェクト）を防ぐ 完全コンストラクタ
    • 不変性 と、変更したいときの書き方
    • 値オブジェクトに 振る舞い を持たせる
    • どこまで値オブジェクトにするか（実務の判断）

    DDD の文脈での位置づけは 42章：エンティティと値オブジェクト、型による表現（ブランド型など）は 42章：型でドメインを表す を参照してください。このページは クラスとしての書き方 に焦点を当てます。

    2.プリミティブ型への執着

    2.1 よくあるコード

    ✕ 金額も個数もメールアドレスもプリミティブ型のまま 
    class Order {
  constructor(
    public price: number,      // 円？ドル？ 税込？税抜？ マイナスでもいい？
    public quantity: number,   // 0 でもいい？ 小数でもいい？
    public email: string,      // 形式は？
  ) {}
}

function calcTotal(price: number, quantity: number, discountRate: number) {
  return price * quantity * (1 - discountRate);
}

calcTotal(3, 1000, 0.1);       // 引数の順番を間違えても気づかない

    2.2 何が問題か

    問題説明
    不正な値が入り込むprice = -500、quantity = 0.5、email = "abc" がそのまま通る
    チェックが散らばる「金額はマイナス不可」というチェックが、あちこちの関数に重複して書かれる（書き忘れる場所も出る）
    取り違えに気づけないnumber 同士・string 同士なので、引数の順番を間違えてもコンパイラが教えてくれない
    ロジックが散らばる「金額の足し算」「税込計算」「表示用の書式化」が、使う場所ごとに書かれる
    意味が伝わらないnumber を見ても、それが金額なのか個数なのか割合なのか分からない

    Martin Fowler は『リファクタリング』で、これを プリミティブ型への執着（Primitive Obsession） という コードの臭い（設計に問題がありそうなサイン）として挙げています（→ コードの臭いとリファクタリング）。

    3.値オブジェクトとは

    3.1 定義

    金額・日付・個数・メールアドレスのような「値」を、専用のクラスとして表したもの。

    class Money {
  private constructor(
    readonly amount: number,
    readonly currency: Currency,
  ) {}
  ...
}

    3.2 値オブジェクトの4つの性質

    性質意味例
    ① 値で等しさを判断する中身が同じなら同じもの。ID（識別子）を持たない1000円の Money は、どの1000円でも同じ
    ② 不変である一度作ったら変わらない。変えたいときは新しいオブジェクトを作るmoney.add(other) は新しい Money を返す
    ③ 常に正しい状態である不正な値では作れない（完全コンストラクタ）マイナスの金額は存在できない
    ④ 自分に関するロジックを持つその値に関する計算・判断を自分で行う足し算・税込計算・通貨の一致チェック

    エンティティ（ID で区別され、状態が変わるもの）との違いは ドメインを表すクラス を参照してください。

    4.完全コンストラクタ

    4.1 生焼けオブジェクト

    作られた時点で、必要な初期化が終わっていないオブジェクト。

    ✕ 生焼けオブジェクト 
    // ✕ 生焼けオブジェクト
class Money {
  amount?: number;
  currency?: string;
}

const m = new Money();     // この時点では中身が空
m.amount = 1000;           // 後から設定する（忘れるかもしれない）
// m.currency の設定を忘れた → 後の計算で壊れる
    • 使う側が「作った後、何を設定すべきか」を知っていなければならない
    • 設定を忘れても、エラーにならずに不正な状態のまま動いてしまう
    • オブジェクトの状態を、使うたびに疑う必要がある

    4.2 完全コンストラクタとは

    コンストラクタで、すべてのインスタンス変数を初期化し、不正な値はその場で拒否する。

    ◯ 完全コンストラクタ 
    type Currency = "JPY" | "USD";

class Money {
  constructor(
    readonly amount: number,
    readonly currency: Currency,
  ) {
    if (!Number.isInteger(amount)) throw new Error("金額は整数で指定してください");
    if (amount < 0) throw new Error("金額は0以上である必要があります");
  }
}

new Money(1000, "JPY");   // OK
new Money(-500, "JPY");   // その場でエラー → 不正な Money は存在できない
    • オブジェクトが 存在する時点で、正しいことが保証される
    • 使う側は、Money を受け取ったら 中身を疑わなくてよい
    • チェックは コンストラクタの1か所だけ に集まる（ガード節＝関数の先頭で不正な条件を弾いて早めに抜ける書き方で書く → 46_メソッド設計 のノート『02_Guard_Clause』）

    ケント・ベックは『Smalltalk Best Practice Patterns』で、すべての必要な値を一度に受け取って完全なオブジェクトを作る生成方法を Complete Creation Method と呼びました。日本では、ミノ駆動『良いコード／悪いコードで学ぶ設計入門』が 「完全コンストラクタ」 という言葉で紹介し、広く知られるようになりました。同書では 「値オブジェクト＋完全コンストラクタ」をオブジェクト指向設計の最も基本の形 としています。

    4.3 例外を投げるか、Result を返すか

    不正な値への対応は、2通りあります。

    方法使いどころ
    コンストラクタで例外を投げる不正な値が来るのは プログラムのバグ（内部でしか作らない値）
    ファクトリメソッドで Result を返す不正な値が 普通に起こりうる（ユーザー入力・外部 API の値）

    ファクトリメソッド はオブジェクトを作って返す専用のメソッド、Result は「成功（ok）か失敗（err）か」を値として返す型です。

    class EmailAddress {
  private constructor(readonly value: string) {}

  // ユーザー入力から作る：失敗を値として返す
  static parse(input: string): Result<EmailAddress, string> {
    const trimmed = input.trim().toLowerCase();
    return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(trimmed)
      ? ok(new EmailAddress(trimmed))
      : err("メールアドレスの形式が正しくありません");
  }
}
    • private constructor にして、生成の入口をファクトリメソッドだけ に限定する
    • これは関数型設計の 「検証するな、解析せよ」（42章：型でドメインを表す）と同じ考え方です

    5.不変にする

    5.1 なぜ不変にするのか

    ✕ 可変な値オブジェクト 
    // ✕ 可変な値オブジェクト
const price = new Money(1000, "JPY");
order1.price = price;
order2.price = price;      // 同じオブジェクトを共有

price.amount = 2000;       // order1 も order2 も 2000円になってしまう
    • 値オブジェクトは、いろいろな場所で 共有・受け渡し される
    • 可変だと、どこかで書き換えられて、予期せぬ場所に影響する（エイリアシング問題：同じオブジェクトを複数の変数が指しているために起きる問題）

    5.2 変更したいときは新しいオブジェクトを返す

    ◯ 自分を変えず、新しい Money を返す 
    class Money {
  constructor(readonly amount: number, readonly currency: Currency) { /* ガード */ }

  add(other: Money): Money {
    if (this.currency !== other.currency) throw new Error("通貨が異なります");
    return new Money(this.amount + other.amount, this.currency);  // 新しい Money
  }

  multiply(times: number): Money {
    return new Money(Math.round(this.amount * times), this.currency);
  }

  equals(other: Money): boolean {
    return this.amount === other.amount && this.currency === other.currency;
  }
}

const total = new Money(1000, "JPY").add(new Money(500, "JPY"));  // 1500円の新しい Money
    • readonly でフィールドを書き換え不可にする
    • add は 自分を変えず、新しい Money を返す
    • 新しいオブジェクトもコンストラクタを通るので、計算結果も常に正しい状態 になる

    5.3 等しさの判断

    値オブジェクトは 中身で比較 します。JavaScript の === は参照（同じオブジェクトかどうか）の比較なので、equals メソッドを用意します。

    new Money(1000, "JPY") === new Money(1000, "JPY");       // false（別のオブジェクト）
new Money(1000, "JPY").equals(new Money(1000, "JPY"));   // true

    6.振る舞いを持たせる

    値オブジェクトの本当の価値は、その値に関するロジックを1か所に集められる ことです。

    class Quantity {
  static readonly MAX = 99;
  constructor(readonly value: number) {
    if (!Number.isInteger(value)) throw new Error("個数は整数です");
    if (value < 1 || value > Quantity.MAX) throw new Error(`個数は1〜${Quantity.MAX}です`);
  }
  increment(): Quantity { return new Quantity(this.value + 1); }
  canIncrement(): boolean { return this.value < Quantity.MAX; }
}

class TaxRate {
  constructor(readonly percent: number) {
    if (percent < 0 || percent > 100) throw new Error("税率が不正です");
  }
  applyTo(price: Money): Money {
    return price.multiply(1 + this.percent / 100);
  }
}

class DateRange {
  constructor(readonly start: Date, readonly end: Date) {
    if (start > end) throw new Error("開始日は終了日より前である必要があります");
  }
  contains(date: Date): boolean { return this.start <= date && date <= this.end; }
  overlaps(other: DateRange): boolean { return this.start <= other.end && other.start <= this.end; }
}
    • 「個数は1〜99」「税込計算の方法」「期間の重なり判定」が、それぞれ 1つのクラスに集まる（高凝集 → 凝集度と結合度）
    • 使う側は quantity.canIncrement() のように 聞くだけ で済む（→ Tell, Don't Ask と貧血モデル）
    • ルールが変わったら、そのクラスだけ を直せばよい

    7.どこまで値オブジェクトにするか

    すべての number や string を値オブジェクトにすると、コードが重くなります。次の順で優先します。

    優先度対象理由
    高業務ルール（制約）がある値金額（マイナス不可・通貨）、個数（上限）、期間（開始 ≦ 終了）
    高取り違えると事故になる値各種 ID、金額と個数、税込と税抜
    高計算・変換のロジックを持つ値金額の計算、日付の計算、単位の変換
    中形式のある値メールアドレス、電話番号、郵便番号
    低制約もロジックもない単なる文字列メモ欄、自由記述のコメント

    判断基準

    「この値に関するチェックやロジックが、複数の場所に書かれていないか？」 が、値オブジェクトにすべきかの良い判断基準です。

    7.1 DB や JSON との変換

    値オブジェクトは、DB や API との境界で プリミティブ型に変換 します。

    • 保存時：money.amount と money.currency を別々の列に保存する
    • 読み込み時：new Money(row.amount, row.currency) で復元する（不正なデータが入っていれば、ここで検出できる）
    • 変換は Repository（保存・読み込みを担当するクラス）や DTO（データ受け渡し用の入れ物）の変換処理で行い、ドメインの内側では常に値オブジェクトを使う

    8.よくある誤解

    誤解1：「値オブジェクトはデータを入れる箱」

    誤りです。 値オブジェクトの価値は、制約（完全コンストラクタ）と振る舞い（ロジック） にあります。getter しかないなら、プリミティブ型と大差ありません。

    誤解2：「setter を用意しておくと便利」

    危険です。 setter があると、完全コンストラクタで守った正しさが、後から壊されます。値オブジェクトは 不変 にします。

    誤解3：「クラスが増えると複雑になる」

    場合によります。 小さなクラスが増えても、それぞれが 1つの値のルールを完全に引き受けて いるなら、使う側はむしろ単純になります（42・43章で見た 深いモジュール の考え方）。逆に、制約もロジックもない値まで包むと、浅いクラスが増えるだけになります。

    9.まとめ

    • プリミティブ型への執着：金額や個数を number のまま使うと、不正な値・チェックの重複・取り違えが起きる
    • 値オブジェクト：①値で比較 ②不変 ③常に正しい ④自分のロジックを持つ
    • 生焼けオブジェクト：作った時点で初期化が終わっていない → 使う側がバグを生む
    • 完全コンストラクタ：すべての値をコンストラクタで受け取り、ガード節で不正値を拒否する。存在すること自体が正しさの保証 になる
    • 変更は 新しいオブジェクトを返す。等しさは equals で中身を比較
    • 優先して値オブジェクトにするのは 業務ルールがある値・取り違えると危険な値・ロジックを持つ値

    次は、データではなく振る舞いをクラスに持たせる Tell, Don't Ask と貧血モデル に進みます。
