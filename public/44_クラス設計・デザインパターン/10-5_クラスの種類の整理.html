    10 クラスの基礎

    クラスの種類の整理 — 言語の仕組みと設計上の役割で見分ける（TypeScript 中心）

    同じクラスでも、見る観点によって呼び名が変わります。このページでは「言語の仕組み」（抽象クラス・interface・enum・ジェネリック・ミックスインなど）と「設計上の役割」（Wirfs-Brock のロールステレオタイプ、Jacobson の BCE）の2つの観点から、クラスの種類を TypeScript 中心に整理し、どれを使うかの判断フローと他の言語との対応表までをまとめます。

    もとにしたノート：10_クラスの基礎/05_クラスの種類の整理

    ひとことで言うと

    クラスの種類は ①言語の仕組み・②設計上の役割・③業務上の役割 の3つの観点で整理できます。TypeScript では 実行時に残るもの（class）と消えるもの（interface / type） の区別が大事で、final・データクラス・静的クラスがない代わりに private コンストラクタ・type・モジュール を使います。そして「何の係か」に一言で答えられないクラスは、分割を検討します。

    1.このページで扱うこと

    オブジェクトの種類の整理 では、エンティティ・値オブジェクト・DTO などの「オブジェクトの種類」を整理しています。オブジェクトはクラスから作られる実体 なので、あれはそのまま「クラスの種類」と言い換えることもできます（値オブジェクトのクラス、エンティティクラス……）。

    このページでは、それとは 別の観点 からクラスの種類を整理します。TypeScript を中心に 書き、他の言語は「TypeScript にない機能が、他の言語ではどうなっているか」を比べる程度にとどめます。

    同じクラスでも、どの観点から見るかで呼び名が変わります。

    3.TypeScript の「クラスっぽいもの」一覧

    TypeScript は JavaScript に型を付けた言語です。そのため、実行時に残るもの（JavaScript のクラスや値） と、型チェックが終わると消えるもの（型だけ） が混ざっています。この区別が、TypeScript でクラスの種類を考えるときの一番のポイントです。

    種類書き方実行時に残る？new できる？主な用途
    具象クラスclass残るできる状態と振る舞いを持つオブジェクト
    抽象クラスabstract class残るできない共通実装を持つ継承用の土台
    インターフェースinterface消える–「できること」の約束（型）
    型エイリアスtype消える–データの形・ユニオン型
    ジェネリッククラスclass Box<T>残る（T は消える）できる型を引数にとる入れ物・コレクション
    列挙型enum / ユニオン型 / as const書き方による–決まった選択肢
    クラス式（無名クラス）const A = class {}残るできるミックスインの内部など
    ミックスインクラスを返す関数残る–機能を後から混ぜ込む
    カスタムエラークラスclass XxxError extends Error残るできるエラーの種類を区別する

    TypeScript にないもの

    TypeScript には final / sealed クラス、データクラス（record）、静的クラス、内部クラス がありません。代わりの書き方を 4.6〜4.9 で説明します。

    4.それぞれの詳しい説明

    4.1 具象クラス（普通のクラス）

    class Order {
  #status: 'DRAFT' | 'CONFIRMED' = 'DRAFT';   // # は実行時にも本当に隠れる private

  constructor(readonly id: string) {}

  confirm(): void {
    if (this.#status !== 'DRAFT') throw new Error('確定済みです');
    this.#status = 'CONFIRMED';
  }
}
    • private は 型チェックだけ の制限です（実行時には外から見えます）。# を付けたフィールドは、実行時にも 外から触れません。
    • constructor(readonly id: string) は パラメータプロパティ（コンストラクタの引数にそのままフィールドを宣言する書き方）という TypeScript 独自の省略記法です（4.12 の注意も参照）。

    4.2 抽象クラス（abstract class）

    一部のメソッドを未実装のままにして、サブクラスに実装させる土台 です。直接 new はできません。

    abstract class Notifier {
  // 共通の手順（テンプレートメソッド）
  async notify(userId: string, message: string): Promise<void> {
    const text = `[通知] ${message}`;
    await this.send(userId, text);
  }
  protected abstract send(userId: string, text: string): Promise<void>;  // サブクラスが実装
}

class EmailNotifier extends Notifier {
  protected async send(userId: string, text: string) { /* メール送信 */ }
}
    • 共通の実装を持てる のがインターフェースとの違いです。
    • 継承は1つしかできないので、実務では「インターフェース＋合成」で済むことのほうが多いです（→ 継承より合成、24_TypeScript のノート『04-抽象クラスの使いどころ』）。

    4.3 インターフェース（interface）と型エイリアス（type）

    実装を持たず、「この形をしている」「これができる」という約束だけを表す型 です。コンパイル後には消えます。

    interface Mailer {
  send(to: string, body: string): Promise<void>;
}

class SmtpMailer implements Mailer {          // 約束を守っているかコンパイラが確認する
  async send(to: string, body: string) { /* ... */ }
}

class FakeMailer implements Mailer {          // テスト用に差し替えられる
  sent: string[] = [];
  async send(to: string) { this.sent.push(to); }
}

    TypeScript は 構造的型付け（形が合っていれば同じ型とみなす）なので、implements を書かなくても、形が合っていれば Mailer として渡せます。implements は「約束を守れているか、クラスを書いた時点でチェックする」ためのものです。

    比べる点抽象クラスインターフェース
    実装を持てる○×（約束だけ）
    複数を組み合わせられる×（extends は1つだけ）○（implements A, B）
    実行時に残る残る（instanceof が使える）消える
    主な用途共通の手順を持つ土台依存先の差し替え（DIP）

    interface と type の使い分けは 24_TypeScript のノート『01-interfaceとtypeの使い分け』を見てください。依存先の差し替え（DIP：具体ではなく抽象に依存させる原則）のクラス設計での使い方は インターフェースと抽象化 にあります。

    4.4 ジェネリッククラス

    型を引数にとって、いろいろな型に使い回せるクラス です。

    class Result<T, E extends Error = Error> {
  private constructor(readonly value?: T, readonly error?: E) {}
  static ok<T>(value: T) { return new Result<T, never>(value); }
  static fail<E extends Error>(error: E) { return new Result<never, E>(undefined, error); }
}

class TypedEventBus<Events extends Record<string, unknown>> {
  on<K extends keyof Events>(name: K, handler: (payload: Events[K]) => void) { /* ... */ }
}
    • コレクションオブジェクトやリポジトリの共通部分でよく使います。
    • 型引数 T はコンパイル後に消えるので、実行時に T が何の型かは分かりません（Java も同じです。C# は実行時にも残ります）。

    4.5 列挙型（enum と、その代わりの書き方）

    TypeScript には enum がありますが、文字列リテラルのユニオン型（'A' | 'B' のように取りうる値を並べた型）や as const オブジェクト で書くことのほうが多いです。

    // ① ユニオン型（一番シンプル。実行時には何も残らない）
type OrderStatus = 'DRAFT' | 'CONFIRMED' | 'SHIPPED';

// ② as const オブジェクト（一覧を実行時にも使いたいとき）
const OrderStatus = { Draft: 'DRAFT', Confirmed: 'CONFIRMED', Shipped: 'SHIPPED' } as const;
type OrderStatus = (typeof OrderStatus)[keyof typeof OrderStatus];

// ③ enum（TypeScript 独自の構文）
enum Color { Red = 'RED', Blue = 'BLUE' }

    enum が避けられがちな理由：

    • 型を消すだけでは JavaScript に変換できない、TypeScript 独自の構文である
      • TypeScript 5.8 で追加された erasableSyntaxOnly オプションを有効にするとエラーになります
      • Node.js の型除去（type stripping：型の部分だけを取り除いて実行する仕組み）による直接実行でも、そのままでは使えません
    • 数値の enum は、範囲外の数値も代入できてしまうなど、型の安全性が弱い

    他の言語では

    Java の enum は フィールドやメソッドを持てる本物のクラス で、状態ごとの振る舞いまで書けます。TypeScript で同じことをしたい場合は、ユニオン型と switch（網羅性チェック）か、State パターン（振る舞いパターン）で書きます。区分ごとの振る舞いの設計は 区分オブジェクトと状態遷移 で扱います。

    4.6 継承させないクラス（final / sealed の代わり）

    TypeScript には final がありません。継承されたくない 場合、特に値オブジェクトでは、次のように書きます。

    class Money {
  private constructor(readonly amount: number) {}     // private コンストラクタ
  static of(amount: number): Money {                  // 生成はファクトリ経由に限定
    if (amount < 0) throw new Error('負の金額');
    return new Money(amount);
  }
}

// class Bonus extends Money {}   // ❌ コンストラクタが private のクラスは継承できない
// new Money(100)                 // ❌ 外から new もできない

    これで「継承させない」と「必ず検証を通して作る（完全コンストラクタ：生成した時点で正しい状態が保証される作り方）」を同時に実現できます（→ 値オブジェクトと完全コンストラクタ）。

    他の言語では

    Java の final class、C# の sealed class、Kotlin のクラス（デフォルトで継承不可、許可するときに open）。Java 17 と Kotlin の sealed は「継承できるクラスを限定する」もので、TypeScript ではユニオン型がこれに当たります。

    4.7 データだけのクラス（データクラス・レコードの代わり）

    TypeScript には Kotlin の data class や Java の record のような「等価比較などを自動で作ってくれるクラス」はありません。データだけなら、クラスではなく type とオブジェクトリテラルで書く のが TypeScript らしい書き方です。

    type OrderResponseDto = Readonly<{
  id: string;
  total: number;
  status: OrderStatus;
}>;

const dto: OrderResponseDto = { id: 'ORD-1', total: 3000, status: 'CONFIRMED' };
    • DTO（Data Transfer Object：層やシステムの間でデータを運ぶだけのオブジェクト）や API のレスポンスは、ほぼこの書き方で十分です。
    • 振る舞いやルールを持たせたい場合（値オブジェクト）だけクラスにする、と分けると迷いません。
    • クラスにした場合、=== は参照の比較になるので、値で比べたいときは equals() を自分で書きます。

    4.8 静的クラス・ユーティリティクラスの代わり → モジュール

    TypeScript には static class がありません。また、static メソッドだけのクラスは作らない のが一般的です（typescript-eslint の no-extraneous-class ルールでも警告されます）。ファイル（モジュール）そのものが「関数の置き場」になる からです。

    ✕ Java 風 
    class StringUtils {
  static isBlank(s: string) { return s.trim() === ''; }
}
    ◯ TypeScript 風：モジュールから関数を export する 
    // string-utils.ts
export const isBlank = (s: string): boolean => s.trim() === '';

    シングルトン（インスタンスが1つだけであることを保証する作り方）も同じ考え方で、モジュールの中でインスタンスを1つ作って export すれば足ります（モジュールは1回しか読み込まれないため）。

    // logger.ts
export const logger = new Logger();   // どこから import しても同じインスタンス

    ただし、どこからでも直接 import できると差し替えにくくなるので、テストしたいものはコンストラクタで受け取る形（依存性注入）にします（→ 41章：DI・IoC・Composition Root）。

    他の言語では

    C# の static class、Java の「private コンストラクタ＋static メソッド」（Math など）。

    4.9 内部クラス・無名クラスの代わり → クラス式

    TypeScript には Java のような内部クラスはありませんが、クラス式（式としてクラスを書いて、変数に入れたり関数から返したりする書き方）があります。主にミックスインで使います。

    4.10 ミックスイン

    「クラスを受け取って、機能を足したクラスを返す関数」 です。継承は1つしかできないので、横断的な機能を複数のクラスに足したいときに使います。TypeScript の公式ドキュメントでも紹介されている書き方です。

    type Constructor<T = {}> = new (...args: any[]) => T;

function Timestamped<TBase extends Constructor>(Base: TBase) {
  return class extends Base {          // ← クラス式
    createdAt = new Date();
  };
}

class User { constructor(readonly name: string) {} }
const TimestampedUser = Timestamped(User);

new TimestampedUser('kai').createdAt;  // Date

    ただし、型が読みにくくなり、デバッグもしにくくなります。まずは合成（他のオブジェクトをフィールドに持つ）で済まないかを考えます（→ 継承より合成）。

    他の言語では

    Ruby の module + include、Rust・Scala・PHP の trait。

    4.11 カスタムエラークラス

    エラーの種類ごとにクラスを分けて、instanceof で区別する ためのクラスです。TypeScript でもよく使います。

    class DomainError extends Error {
  constructor(message: string) {
    super(message);
    this.name = new.target.name;        // サブクラスの名前を自動で入れる
  }
}
class OrderNotFoundError extends DomainError {}
class OutOfStockError extends DomainError {}

try { /* ... */ }
catch (e) {
  if (e instanceof OrderNotFoundError) { /* 404 を返す */ }
}

    エラーを例外として投げずに、戻り値で返す方法は 24_TypeScript のノート『02-結果型Result_Either』を見てください。

    4.12 TypeScript 独自構文の注意（パラメータプロパティなど）

    constructor(readonly id: string) のパラメータプロパティ、enum、namespace は、型を消すだけでは JavaScript に変換できない TypeScript 独自の構文です。

    • erasableSyntaxOnly を有効にしたプロジェクトや、Node.js の型除去による直接実行では使えません。
    • その場合は、フィールドを明示的に書きます。
    class Order {
  readonly id: string;
  constructor(id: string) { this.id = id; }
}

    プロジェクトの tsconfig（TypeScript のコンパイル設定ファイル）でどちらの書き方にするかを決めておきます（→ 24_TypeScript のノート『12-tsconfig』）。

    5.設計上の役割による種類（ロールステレオタイプ）

    言語の仕組みとは別に、「このクラスは何の係か」で分ける考え方です。Rebecca Wirfs-Brock が『Object Design』（2002）で示した 6つのロールステレオタイプ（クラスが担う典型的な役割の型）が有名です。

    役割担当することTypeScript での例
    情報保持役（Information Holder）情報を持ち、それを提供するMoney、User、DTO の type
    構造化役（Structurer）オブジェクト同士の関係やまとまりを管理するOrderLines（コレクション）、ツリー
    サービス提供役（Service Provider）頼まれた処理を行うTaxCalculator、PasswordHasher
    調整役（Coordinator）自分では判断せず、仕事を他に割り振るイベントの中継役、EventBus
    制御役（Controller）判断を下し、他のオブジェクトを指揮するConfirmOrderUseCase、ワークフロー
    インターフェース役（Interfacer）外部（ユーザー・他システム・DB）とのやりとりを変換するExpress のルートハンドラ、PrismaOrderRepository、API クライアント

    5.1 なぜ役割を意識するのか

    • 1つのクラスには、なるべく1つの役割 を持たせます。2つ以上の役割に当てはまるクラスは、責務を持ちすぎているサインです（→ 単一責任の原則）。
    • 役割が決まると 名前が決まりやすく なります（〜Calculator、〜Repository、〜UseCase、〜Client）。
    • 役割ごとに テストの書き方 も決まってきます。情報保持役はそのまま単体テスト、インターフェース役は差し替え（Fake）を用意する、などです。

    5.2 よくある「役割が混ざった」クラス

    ✕ 制御役 + インターフェース役 + 情報保持役が混ざっている 
    class OrderManager {
  async confirm(req: express.Request, res: express.Response) {
    const row = await prisma.order.findUnique({ where: { id: req.params.id } });  // DB とのやりとり
    if (row!.lines.length === 0) return res.status(400).send('明細なし');         // 業務ルール
    await prisma.order.update({ where: { id: row!.id }, data: { status: 'CONFIRMED' } });
    res.json({ ok: true });                                                       // HTTP とのやりとり
  }
}

    これを役割ごとに分けると、オブジェクトの種類の整理 の構成（ルートハンドラ → ユースケース → エンティティ → リポジトリ）になります。

    5.3 似た分類：BCE

    Ivar Jacobson（UML の作者の一人）は、クラスを次の3つに分けました。MVC やレイヤードアーキテクチャの考え方の元になったものの一つです。

    分類役割ロールステレオタイプでいうと
    Boundary（境界）システムの外とのやりとりインターフェース役
    Control（制御）ユースケースの流れ制御役・調整役
    Entity（エンティティ）業務データとルール情報保持役・構造化役

    MVC やレイヤードアーキテクチャそのものは 41章：MVC、層化・三層・レイヤード を見てください。

    6.TypeScript でどれを使うか：判断フロー

    作りたいものは？
├─ データの形を表したいだけ（振る舞いなし）
│     → type（DTO、API レスポンス、設定の形）
├─ 決まった選択肢
│     → 文字列リテラルのユニオン型（一覧が実行時に必要なら as const）
├─ 差し替え可能な「できること」の約束
│     → interface（Repository、Mailer など依存先）
├─ 状態を持たない関数の集まり
│     → モジュールから関数を export（static だけのクラスは作らない）
├─ ルールや状態と、それを扱う振る舞いをまとめたい
│     → class
│        ├─ 不変・検証済みで作りたい → private コンストラクタ + static ファクトリ
│        └─ 型を引数にとりたい      → ジェネリッククラス
├─ 共通の手順を持ち、一部だけ差し替えたい
│     → まず interface + 合成を検討。それで不自然なら abstract class
├─ 横断的な機能を複数のクラスに足したい
│     → まず合成を検討。それで不自然ならミックスイン
└─ エラーの種類を区別したい
      → class XxxError extends Error

    クラスにしない、という選択肢

    TypeScript は関数型の書き方とも相性がよい言語です。「クラスにしない」という選択肢が常にある ことが、Java や C# との大きな違いです。

    8.よくある誤解

    誤解1：「TypeScript の private を付ければ、実行時にも外から触れない」

    private は 型チェックだけ の制限で、実行時には外から見えます。実行時にも隠したいときは # を付けたフィールドを使います。

    誤解2：「interface を書くと、実行時に instanceof で判定できる」

    interface と type はコンパイル後に 消える ので、実行時には存在しません。instanceof が使えるのは、実行時に残る class（抽象クラスを含む）です。

    誤解3：「ユーティリティ関数は static メソッドだけのクラスにまとめるもの」

    それは Java 風の書き方です。TypeScript では ファイル（モジュール）そのものが関数の置き場 になるので、関数を export すれば足ります。typescript-eslint の no-extraneous-class ルールでも警告されます。

    誤解4：「DTO もクラスで書くべき」

    データだけなら type とオブジェクトリテラルで十分です。振る舞いやルールを持たせたい場合（値オブジェクト）だけクラスにする と分けると迷いません。

    9.まとめ

    • クラスの種類は ①言語の仕組み・②設計上の役割・③業務上の役割 の3つの観点で分けると整理できる
    • TypeScript では 実行時に残るもの（class）と消えるもの（interface / type） の区別が大事
    • TypeScript には final・データクラス・静的クラスがない。代わりに private コンストラクタ、type、モジュール を使う
    • 「何の係か」に一言で答えられないクラスは分割を検討する（ロールステレオタイプ）
