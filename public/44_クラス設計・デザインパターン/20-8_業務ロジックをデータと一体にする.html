    20 責務の割り当て

    業務ロジックをデータと一体にする — 判断・加工・計算をデータのそばへ

    データクラス（貧血モデル）の問題を解く具体的なやり方です。使う側をシンプルにする方針、メソッドをロジックの置き場所にすること、ロジックをデータを持つクラスへ移すこと、短いメソッド・インスタンス変数・クラス分割（Extract Class）・パッケージ整理までを、増田亨『現場で役立つシステム設計の原則』第3章にそってコード例で解説します。

    もとにしたノート：20_責務の割り当て/08_業務ロジックをデータと一体にする

    ひとことで言うと

    使う側のコードがシンプルになるように、データを持つ側に判断・加工・計算を持たせる ことです。getter で値を取り出して呼ぶ側で計算していたら、その処理をデータのクラスへ移します。メソッドは短く分け、インスタンス変数を使い、クラスが太ったら分け、増えたらパッケージで整理します。

    1.このページで扱うこと

    Tell, Don't Ask と貧血モデル では、データクラス／貧血モデルの問題を学びました。このページでは、増田亨『現場で役立つシステム設計の原則』第3章の中核 — データとロジックを一体にして整理する具体的なやり方 — を学びます。

    • 使う側がシンプルになる設計（ロジックの重複を防ぐ）
    • メソッドを ロジックの置き場所 にする
    • 業務ロジックを データを持つクラスへ移動 する
    • 短いメソッド・インスタンス変数・クラス分割・パッケージ整理

    2.業務ロジックを重複させない設計

    方針はシンプルです。

    方針

    使う側のクラスのコードがシンプルになるように、データを持つ側に判断・加工・計算を持たせる。

    呼ぶ側が getter で値を取り出し、あちこちに同じ計算を書くのではなく、データを持っているオブジェクトに依頼する（Tell, Don't Ask / 情報エキスパート。→ GRASP）。

    3.メソッドをロジックの置き場所にする

    メソッドは 判断・加工・計算 を実行するものにします。値を返すだけの getter を並べ、使う側で加工し続けると、ロジックの置き場所がまた散らばります。

    ✕ getter だけ。加工は呼ぶ側の仕事になる 
    class Person {
  constructor(
    private readonly firstName: string,
    private readonly lastName: string,
  ) {}
  getFirstName() { return this.firstName; }
  getLastName() { return this.lastName; }
}
// 使う側のあちこちで `${p.getFirstName()} ${p.getLastName()}`
    ◯ 加工ロジックをメソッドに置く 
    class Person {
  constructor(
    private readonly firstName: string,
    private readonly lastName: string,
  ) {}
  fullName(): string {
    return `${this.firstName} ${this.lastName}`;
  }
}

    表示のためにデータを取り出す getter が必要な場面はあります（Tell, Don't Ask と貧血モデル）。避けるべきは、取り出した値で業務判断・計算を呼ぶ側が行うこと です。

    4.業務ロジックをデータを持つクラスに移動する

    getter を見つけたら、「呼ぶ側でその値を使って判断・計算していないか」を見ます。していれば、その処理を データを持つクラスのメソッドへ移し、呼ぶ側は結果だけ受け取ります（リファクタリングの Move Method / Move Function）。

    ✕ 計算が呼ぶ側にある（重複しやすい） 
    const amount = order.getUnitPrice() * order.getQuantity();
    ◯ データを持つ側が計算する 
    const amount = order.lineAmount();

    移動すると重複が消え、変更箇所がクラス名から辿れます。手順の詳細は Tell, Don't Ask と貧血モデル のリファクタリングの手順 も参照してください。

    5.使う側のクラスに業務ロジックを書き始めたら設計を見直す

    初期は「とりあえず動く」データクラスで進むこともあります。ただし、使う側（サービス・画面）に業務判断を書き始めたら、置き場所とクラス名／メソッド名を見直す合図です。

    設計は一発で完成させず、ロジックをデータのそばへ寄せ続ける活動です。

    6.メソッドを短く書くとロジックの移動がやりやすくなる

    長いメソッドのままでは、「この塊は別クラスの関心事だ」と気づきにくいです。短く分けると、そのクラスにそぐわない段落 が見え、移動の候補になります（46_メソッド設計 のノート『01_サイズと抽象度』『04_Extract_Method』『05_段落と説明用の変数』）。

    7.メソッドは必ずインスタンス変数を使う

    インスタンス変数（オブジェクトごとに持つフィールド）を使わず、引数だけを使うメソッドは、そのクラスのメソッドとして不適切 なことが多いです。引数を渡している側のクラス、または引数の型（値オブジェクト）側への移動を検討します。

    ✕ Order のメソッドなのに order の状態を使っていない 
    class Order {
  static taxIncluded(price: number, rate: number): number {
    return price * (1 + rate);
  }
}
    ◯ 金額を持つ側、または Money / TaxRate に置く 
    class Money {
  taxIncluded(rate: TaxRate): Money { /* ... */ }
}

    データを持つクラスにロジックを寄せると、引数が減り、呼ぶ側が知らなくてよい詳細が減る（結合が弱まる）効果もあります。

    8.クラスが肥大化したら小さく分ける

    インスタンス変数とメソッドが増えすぎたら、関連するデータとロジックを抜き出して新クラスにします（Extract Class）。

    Before：Customer が名前も住所も全部持つ 
    class Customer {
  firstName!: string;
  lastName!: string;
  postalCode!: string;
  city!: string;
  street!: string;
  fullName() { return `${this.firstName} ${this.lastName}`; }
  fullAddress() { return `${this.postalCode} ${this.city} ${this.street}`; }
}
    After：関心事ごとに分割（凝集度が上がる） 
    class Customer {
  constructor(
    readonly name: PersonName,
    readonly address: Address,
  ) {}
}
class PersonName {
  constructor(readonly firstName: string, readonly lastName: string) {}
  fullName() { return `${this.firstName} ${this.lastName}`; }
}
class Address {
  constructor(
    readonly postalCode: string,
    readonly city: string,
    readonly street: string,
  ) {}
  fullAddress() {
    return `${this.postalCode} ${this.city} ${this.street}`;
  }
}

    値オブジェクト・狭い関心事のクラスについては 値オブジェクトと完全コンストラクタ・ドメインを表すクラス も参照してください。

    9.パッケージを使ってクラスを整理する

    クラスが増えたら、関連の強いクラスを同じパッケージ（モジュール／フォルダ）に集めます。

    指針内容
    関連の強いものを近くに注文まわりのクラスは order/ に
    公開範囲を狭く可能ならパッケージ外に出さない
    増えすぎたらサブパッケージさらに関心事で割る
    継続的に見直す初期の浅い理解のまま固定しない

    パッケージ間の参照関係を業務の流れ（注文→出荷→請求など）に沿わせると、全体俯瞰がしやすくなります。三層＋ドメインモデルでの位置づけは 41章：層化・三層・レイヤード・42章：ドメイン層とユースケース へ進みます。

    10.よくある誤解

    誤解1：「getter を作ってはいけない」

    表示のためにデータを取り出す getter が必要な場面はあります。避けるべきは、取り出した値で業務判断・計算を呼ぶ側が行うこと です。getter を見つけたら「呼ぶ側でその値を使って判断・計算していないか」を確かめ、していればデータのクラスへ移します。

    誤解2：「最初から正しい置き場所を決めなければならない」

    初期は「とりあえず動く」データクラスで進むこともあります。使う側に業務判断を書き始めたら見直す合図です。設計は一発で完成させるものではなく、ロジックをデータのそばへ寄せ続ける活動です。

    誤解3：「便利な計算はどのクラスに static で置いてもよい」

    インスタンス変数を使わず引数だけを使うメソッドは、そのクラスのメソッドとして不適切なことが多いです。Order.taxIncluded(price, rate) のような計算は、金額を持つ Money や TaxRate の側に置くと、引数が減り結合も弱まります。

    11.まとめ

    • 重複を防ぐには、使う側を薄くし、データを持つ側にロジックを置く
    • メソッドは判断・加工・計算の置き場所。getter だけにしない
    • 呼ぶ側の計算はデータのクラスへ移動する。書き始めたら設計を見直す
    • 短く分け、インスタンス変数を使う。肥大化したら Extract Class
    • クラスが増えたらパッケージで整理し、参照関係を業務に合わせる
