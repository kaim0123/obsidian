    50 デザインパターン ／ 54 振る舞い

    振る舞いパターン — オブジェクト同士のやり取りを工夫する

    アルゴリズムを差し替えたい、状態の変化を知らせたい、処理を順番に渡したい — こうした「オブジェクト間の動き」の問題を解くのが振る舞いパターンです。GoF の11種を一覧し、よく使う Strategy・Observer・Iterator・Command・State を中心に、コード例で解説します。

    もとにしたノート：54_振る舞い/01_振る舞いに関するパターン

    ひとことで言うと

    振る舞いに関するパターン（Behavioral Patterns） は、オブジェクト同士が どうやってやり取りするか を工夫するパターンです。GoF の23パターンのうち 11個（最多） を占め、とくに Strategy・Observer・Iterator・Command・State はよく使います。

    1.このページで扱うこと

    振る舞いパターンが解くのは、次のような「オブジェクト間の動き」に関わる問題です。

    • アルゴリズムを差し替えたい
    • 状態が変わったら他のオブジェクトに知らせたい
    • 処理を次々と順番に渡したい

    このページでは、GoF（『デザインパターン』の4人の著者、Gang of Four）の振る舞いパターン11種を一覧し、とくによく使うものを中心に順に見ていきます。パターン全体の位置づけは GoFパターンの概要、ほかの分類は 生成パターン・構造パターン を参照してください。

    • GoF の振る舞いパターン11種の一覧
    • Strategy・Observer・Iterator・Command・State（よく使う5つ）
    • Template Method・Chain of Responsibility
    • Mediator・Memento・Visitor・Interpreter（簡単に）
    • 振る舞いパターンの使い分け

    2.GoF の振る舞いパターン11種

    パターン目的
    Chain of Responsibility処理をバケツリレー
    Command操作をオブジェクト化
    Interpreter小さな言語の解釈
    Iteratorコレクションを順に辿る
    Mediator仲介者を介して通信
    Memento状態の保存・復元
    Observer状態変化の通知
    State状態で振る舞いを変える
    Strategyアルゴリズムの差し替え
    Template Method骨格は親、詳細は子
    Visitor構造を変えずに処理追加

    この中でも特に使う Strategy・Observer・Iterator・Command・State を中心に解説します。

    3.Strategy（戦略）

    3.1 何を解決するか

    「アルゴリズムを実行時に切り替えたい」問題です。if / switch の代わりになります。

    3.2 使いどころ

    • ソート方法の切り替え
    • 支払い方法の切り替え
    • 圧縮アルゴリズムの切り替え
    • 配送業者の切り替え

    3.3 例：支払い手数料の計算

    ✕ 悪い例：種類ごとの if が並ぶ 
    function calcFee(type, amount) {
  if (type === 'creditCard') return amount * 0.03;
  if (type === 'paypal') return amount * 0.05;
  if (type === 'bank') return 200;
}

    支払い方法が増えるたびに、この関数を書き換えることになります。Strategy パターンでは、計算方法（アルゴリズム）をそれぞれクラスに分け、共通のインターフェースで差し替えられるようにします。

    ◯ Strategy パターン 
    interface FeeStrategy {
  calc(amount: number): number;
}
class CreditCardFee implements FeeStrategy {
  calc(amount) { return amount * 0.03; }
}
class PayPalFee implements FeeStrategy {
  calc(amount) { return amount * 0.05; }
}
class BankFee implements FeeStrategy {
  calc() { return 200; }
}

class Payment {
  constructor(private fee: FeeStrategy) {}
  total(amount: number) { return amount + this.fee.calc(amount); }
}

new Payment(new CreditCardFee()).total(1000);

    新しい支払い方法は、FeeStrategy を実装したクラスを足すだけで追加でき、Payment は書き換えずに済みます。Strategy は OCP（開放閉鎖の原則）（拡張に開き、修正に閉じる）を実現する代表的なパターンです（→ 開放閉鎖の原則）。

    4.Observer（観察者）

    4.1 何を解決するか

    「状態が変わったら、関連する複数のオブジェクトに自動で通知したい」問題です。

    4.2 使いどころ

    • GUI イベント（クリック・入力）
    • pub/sub（出す側と受け取る側が直接知り合わずにメッセージをやり取りする方式）
    • リアクティブプログラミング（RxJS、Vue、React）

    4.3 例：株価の通知

    class Subject {
  observers = [];
  subscribe(fn) { this.observers.push(fn); }
  unsubscribe(fn) {
    this.observers = this.observers.filter(o => o !== fn);
  }
  notify(data) {
    this.observers.forEach(fn => fn(data));
  }
}

const stock = new Subject();
stock.subscribe(price => console.log(`ログ: ${price}円`));
stock.subscribe(price => { if (price > 1000) console.log('売り時！'); });

stock.notify(950);  // ログ: 950円
stock.notify(1200); // ログ: 1200円 / 売り時！

    通知する側（Subject）は、誰が何をするかを知らずに notify するだけです。JavaScript の addEventListener や Node.js の EventEmitter はこのパターンです。

    5.Iterator（反復子）

    5.1 何を解決するか

    「コレクションの 内部構造を知らずに、要素を順番に取り出したい」問題です。

    5.2 使いどころ

    • 配列・リスト・ツリーを一様にループ
    • 巨大なデータをストリーム処理

    5.3 例：範囲を順に取り出す

    JavaScript では Symbol.iterator（for...of で回せるようにするための特別なメソッド名）で実現されています。

    class Range {
  constructor(start, end) { this.start = start; this.end = end; }
  [Symbol.iterator]() {
    let i = this.start;
    const end = this.end;
    return {
      next() {
        return i <= end ? { value: i++, done: false } : { done: true };
      }
    };
  }
}

for (const n of new Range(1, 5)) console.log(n); // 1 2 3 4 5

    6.Command（コマンド）

    6.1 何を解決するか

    「操作を オブジェクトとして扱いたい」問題です。操作がオブジェクトになると、Undo（取り消し）・キュー・ログが作りやすくなります。

    6.2 使いどころ

    • Undo / Redo
    • マクロ・バッチ実行
    • ジョブキュー

    6.3 例：テキスト追加と取り消し

    class AddCommand {
  constructor(editor, text) { this.editor = editor; this.text = text; }
  execute() { this.prev = this.editor.content; this.editor.content += this.text; }
  undo() { this.editor.content = this.prev; }
}

const editor = { content: '' };
const history = [];
function run(cmd) { cmd.execute(); history.push(cmd); }
function undo() { history.pop()?.undo(); }

run(new AddCommand(editor, 'Hello ')); // content: 'Hello '
run(new AddCommand(editor, 'World')); // content: 'Hello World'
undo();                                 // content: 'Hello '

    実行したコマンドを history に積んでおくので、最後の操作を取り出して undo() を呼ぶだけで取り消せます。

    7.State（状態）

    7.1 何を解決するか

    「状態によって振る舞いが変わる オブジェクトを、if 文の山にせずに 実装したい」問題です。

    7.2 使いどころ

    • ワークフロー（下書き→承認待ち→公開）
    • ゲームのキャラ状態（通常・ダメージ・無敵）
    • ネットワーク接続状態

    7.3 例：文書の公開フロー

    class DraftState {
  publish(doc) { doc.setState(new ReviewState()); }
}
class ReviewState {
  publish(doc) { doc.setState(new PublishedState()); }
}
class PublishedState {
  publish() { console.log('既に公開済み'); }
}

class Document {
  constructor() { this.state = new DraftState(); }
  setState(s) { this.state = s; }
  publish() { this.state.publish(this); }
}

const doc = new Document();
doc.publish(); // Draft → Review
doc.publish(); // Review → Published
doc.publish(); // 既に公開済み

    状態ごとの振る舞いを状態クラスに分けたので、Document 自身は「今の状態に任せる」だけです。区分や状態遷移をクラスで表す考え方は 区分オブジェクトと状態遷移 でも扱います。

    8.Template Method（テンプレートメソッド）

    8.1 何を解決するか

    「処理の大枠は同じ だけど、一部の手順だけ違う 場合に、共通部分と差異を分離したい」問題です。

    8.2 例：料理の手順

    class Recipe {
  cook() {
    this.prepare();
    this.heat();
    this.serve();
  }
  prepare() { throw new Error('実装が必要'); }
  heat() { console.log('加熱'); }
  serve() { console.log('盛り付け'); }
}

class Ramen extends Recipe {
  prepare() { console.log('麺とスープ準備'); }
}
class Curry extends Recipe {
  prepare() { console.log('野菜とルウ準備'); }
}

    手順の並び（cook()）は親クラスが決め、違う部分（prepare()）だけを子クラスが埋めます。継承を使うパターンなので、継承の注意点は 継承より合成 も参照してください。

    9.Chain of Responsibility（責任の連鎖）

    9.1 何を解決するか

    「複数のハンドラ（処理役）を順番に試して、誰かが処理するまで回す」仕組みです。

    9.2 使いどころ

    • Web フレームワークのミドルウェア（Express, Koa）
    • ログフィルタ
    • 認可チェーン

    9.3 例（イメージ）

    app.use(authMiddleware);
app.use(logMiddleware);
app.use(router);
// 順に呼ばれ、next() で次へ

    10.その他のパターン（簡単に）

    Mediator（仲介者）

    オブジェクト同士が直接通信せず、仲介者を介して通信 します。GUI のダイアログ内のコンポーネント制御に使います。

    Memento（記念品）

    オブジェクトの状態を 外部に保存し、後で復元 します。Undo の実装補助になります。

    Visitor（ビジター）

    データ構造を変えずに、新しい処理を追加 します。ツリー・AST（プログラムを木の形で表したもの、抽象構文木）の走査に便利です。

    Interpreter（インタプリタ）

    小さな言語を定義して解釈 します。正規表現エンジンのようなものに近いです。

    11.振る舞いパターンの使い分け

    状況パターン
    アルゴリズムを差し替えたいStrategy
    イベントで通知したいObserver
    コレクションを一様に辿りたいIterator
    操作をオブジェクト化して記録したいCommand
    状態で振る舞いを切り替えたいState
    処理骨格を共通化、細部だけ変えたいTemplate Method
    順番に処理者を試したいChain of Responsibility

    Strategy・Command・Observer・Iterator などは、現代の言語では関数やジェネレータでずっと簡単に書けます。詳しくは 関数型で置き換わるパターン を参照してください。また、パターンは SOLID のうち OCP・DIP（依存性逆転の原則）を実現する手段にもなります（48_原則 のノート『00_設計原則の変遷』）。

    12.よくある誤解

    誤解1：「if / switch は全部 Strategy や State に置き換えるべき」

    Strategy や State が効くのは、アルゴリズムや状態が 本当に増えたり差し替わったりする ときです。種類が1つしかないのに抽象化すると過剰設計になります（→ アンチパターンの見分け方 の「Strategy vs 過剰抽象化」）。

    誤解2：「振る舞いパターンはクラスで書かなければならない」

    このページの Observer の例のように、関数を登録するだけでもパターンの考え方は実現できます。大事なのは「通知したい」「差し替えたい」という問題の形に気づくことで、書き方は言語に合わせて選べます（→ 関数型で置き換わるパターン）。

    13.まとめ

    • 振る舞いパターンは、オブジェクト同士の やり取り を工夫するパターン。GoF の23パターン中 11個 と最多
    • Strategy：アルゴリズムを実行時に差し替える。OCP を実現する代表例
    • Observer：状態変化を複数の相手に通知する。addEventListener・EventEmitter
    • Iterator：内部構造を知らずに順に取り出す。Symbol.iterator
    • Command：操作をオブジェクトにして Undo・キュー・ログを可能にする
    • State：状態ごとの振る舞いをクラスに分け、if の山をなくす
    • Template Method（骨格は親・詳細は子）、Chain of Responsibility（ミドルウェア）も実務でよく見る
