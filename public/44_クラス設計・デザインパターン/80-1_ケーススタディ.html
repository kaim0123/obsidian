    80 ケーススタディ

    ケーススタディ — 注文管理と課金・決済でクラス設計を通しで体験する

    これまで学んだことを、2つの題材で通しで使ってみます。前半の注文管理システムでは、要件整理からクラス候補の洗い出し、GRASP による責務の分配、関係とインターフェースの設計、実装の順序と振り返りまでを体験します。後半の課金・決済ロジックでは、変化の多い領域で Strategy・Factory・値オブジェクトを使う設計と、よくある設計ミスの直し方を見ます。

    もとにしたノート：80_ケーススタディ/01_ケーススタディ_注文管理システム / 02_ケーススタディ_課金・決済ロジック

    ひとことで言うと

    要件の 名詞からクラス、動詞から責務 を拾い、GRASP で置き場所を決め、永続化は Repository の向こうに隠します。変化が多い決済は Strategy + Factory で拡張点を先に切り、金額は Money 値オブジェクトでルールを閉じ込めます。

    1.このページで扱うこと

    ケース1：注文管理システム

    要件の整理からクラス設計・実装・振り返りまで一通り体験します。GRASP・関係・インターフェースの実践を統合します。

    ケース2：課金・決済ロジック

    変化が多い領域で、Strategy・Factory・値オブジェクトを使ったクラス設計を学びます。よくある設計ミスと修正も体験します。

    2.ケース1：注文管理システム

    2.1 要件の整理

    ユースケース（抜粋）

    ユースケース（利用者がシステムを使って達成したいこと）を書き出します。

    1. 顧客が商品をカートに入れる
    2. カートから注文を確定する（在庫確認あり）
    3. 注文をキャンセルする（確定前のみ）
    4. 注文一覧を参照する

    業務ルール

    • 明細が空の注文は確定できない
    • 在庫不足の場合は確定できない
    • 確定後のキャンセルは別フロー（本演習では対象外）

    2.2 クラス候補の洗い出し

    要件に出てくる 名詞 をクラス候補にします（手順は クラス分割の基本プロセス）。

    名詞クラス候補種類
    顧客Customerエンティティ
    商品Productエンティティ
    カートShoppingCart集約候補
    注文Order集約ルート
    明細OrderLineエンティティ/値
    在庫Inventoryドメインサービス候補

    エンティティ：ID で同じものかどうかを見分けるオブジェクト。値（値オブジェクト）：中身の値で比べる不変のオブジェクト。集約：整合性を一緒に保つオブジェクトのまとまりで、窓口になるのが集約ルート。ドメインサービス：どのエンティティにも自然に属さない業務の処理。詳しくは オブジェクトの種類の整理、エンティティと値オブジェクト（42章）、集約とリポジトリ（42章）。

    次に 動詞 を責務としてクラスに配置します：addItem → Cart、confirm → Order、canFulfill → Inventory。

    2.3 GRASP で責務を分配する

    GRASP（責務をどのクラスに割り当てるかの指針集）を当てはめます。

    GRASP適用
    Information ExpertOrderLine.subtotal()
    CreatorOrder が OrderLine を生成
    ControllerPlaceOrderController がユースケース窓口
    Low CouplingOrderRepository インターフェース
    Protected Variations在庫確認を Inventory に隔離
     
    class Order {
  confirm(inventory) {
    if (this.lines.length === 0) throw new Error('明細なし');
    if (!inventory.canFulfill(this)) throw new Error('在庫不足');
    this.status = OrderStatus.CONFIRMED;
  }
}

    2.1 の業務ルール「明細が空なら確定できない」「在庫不足なら確定できない」が、そのまま Order.confirm() の中に書かれています。ルールがサービスではなく Order 自身にあるので、貧血モデル（Tell, Don't Ask と貧血モデル）になっていません。

    2.4 関係とインターフェースの設計

    Customer 1 ──< * Order
Order 1 ◆─── * OrderLine
Order ..> Inventory : canFulfill
PlaceOrderController ..> OrderRepository

    関連・コンポジション（部分が全体と運命をともにする関係）・依存の記号は クラス間の関係 と 参考図解 を参照。

    interface OrderRepository {
  save(order: Order): void;
  findByCustomer(customerId: string): Order[];
}

    永続化は Repository に閉じ、ドメインは DB を知りません（DIP：依存性逆転の原則。インターフェースと抽象化）。

    2.5 実装と振り返り

    実装の順序

    1. OrderLine, Money（値オブジェクト）
    2. Order + 単体テスト
    3. Inventory（スタブでテスト）
    4. OrderRepository インターフェース + メモリ実装
    5. PlaceOrderController

    依存されるほう（小さな値オブジェクト）から作り、外側（コントローラ）を最後にします。スタブ（決まった値を返すだけの偽物）やメモリ実装（DB の代わりに配列などに保存する実装）を使うので、DB がなくてもテストしながら進められます。

    振り返りチェック

    • ☐ 貧血モデルになっていないか
    • ☐ 神クラスができていないか
    • ☐ テストは DB なしでドメインを検証できているか

    改善案

    配送先 Address を値オブジェクト化、確定時に OrderConfirmed イベント発行（ドメインイベント（42章））。

    同じ注文管理を、より上位の視点（DDD・境界づけられたコンテキスト）から扱う姉妹演習が ケーススタディ（42章） にあります。

    3.ケース2：課金・決済ロジック

    3.1 複雑な業務ルールのクラス化

    要件（抜粋）

    • 支払い方法：クレジットカード、銀行振込、請求書払い
    • 手数料・税は支払い方法と地域で異なる
    • 新しい支払い方法が四半期ごとに追加される見込み

    クラス化の方針

    ルール置き場所
    金額・通貨Money 値オブジェクト
    支払い処理PaymentStrategy
    手数料FeePolicy（Strategy）
    生成PaymentFactory

    「新しい支払い方法が四半期ごとに追加される」という要件が、変化する場所（拡張点）を教えてくれています。

    3.2 Strategy / Factory の適用

    Strategy（同じ呼び方で、振る舞いだけを差し替えられるようにするパターン）と Factory（どのクラスを生成するかの判断を1か所に集めるパターン）を組み合わせます（振る舞いパターン、生成パターン）。

    class CardPayment {
  pay(money, context) { /* カード API */ }
}
class InvoicePayment {
  pay(money, context) { /* 請求書発行 */ }
}

class PaymentFactory {
  create(type) {
    const map = {
      CARD: CardPayment,
      INVOICE: InvoicePayment,
    };
    const Cls = map[type];
    if (!Cls) throw new Error(`未対応: ${type}`);
    return new Cls();
  }
}

class CheckoutService {
  constructor(factory) { this.factory = factory; }
  execute(order, paymentType) {
    const payment = this.factory.create(paymentType);
    payment.pay(order.total(), { orderId: order.id });
  }
}

    OCP（開放閉鎖の原則：拡張には開き、修正には閉じる）：新しい支払い方法は 新クラス + Factory 登録 で追加でき、既存コードの変更を最小にできます（開放閉鎖の原則）。

    3.3 値オブジェクトの活用

    class Money {
  constructor(amount, currency) {
    if (!Number.isInteger(amount)) throw new Error('整数円のみ');
    this.amount = amount;
    this.currency = currency;
  }
  add(other) {
    this.#assertSameCurrency(other);
    return new Money(this.amount + other.amount, this.currency);
  }
  #assertSameCurrency(other) {
    if (this.currency !== other.currency) throw new Error('通貨不一致');
  }
}

    コンストラクタで「整数のみ」を確かめ、add() では通貨が違えばエラーにし、自分を書き換えずに新しい Money を返します（# 付きのメソッドは外から呼べない private メソッドです）。

    観点内容
    効果丸め・通貨ミスをクラス境界で防止
    関連ドメインを表すクラス（値オブジェクトそのものは 値オブジェクトと完全コンストラクタ）

    3.4 よくある設計ミスと修正

    ミス1：巨大 switch

    ✕ NG

    // NG
function pay(type, amount) {
  if (type === 'CARD') { /* 100行 */ }
  else if (type === 'INVOICE') { /* 100行 */ }
}

    → Strategy + Factory へ（3.2）。支払い方法が増えるたびにこの関数が100行ずつ伸びていきます。

    ミス2：金額を number のまま

    浮動小数点誤差（0.1 + 0.2 が 0.30000000000000004 になるような小数計算のずれ）・通貨なし → Money 値オブジェクトへ。

    ミス3：決済 API の型がドメインに漏れる

    決済サービス Stripe の型 StripeCharge を Order が知る → PaymentGateway インターフェースで隠す。

    interface PaymentGateway {
  charge(money: Money, token: string): Receipt;
}

    こうしておけば、決済サービスを乗り換えても Order は変わりません。

    4.よくある誤解

    誤解1：「名詞を全部クラスにすればクラス設計は終わり」

    名詞は候補の出発点にすぎません。Inventory がドメインサービス候補、OrderLine がエンティティか値か迷うように、種類を見極め、動詞（責務）をどこに置くかを GRASP で決めて初めて設計になります。

    誤解2：「支払い方法の分岐は if 文で書けば十分」

    四半期ごとに支払い方法が増える要件では、巨大な switch / if は増えるたびに肥大化し、既存の分岐を壊す危険も増えます。変化する場所が分かっているなら、Strategy + Factory で拡張点を先に切っておきます。

    誤解3：「金額はただの数値なので number で十分」

    number のままだと、小数の誤差や通貨の取り違えをどこでも起こせてしまいます。Money にしておけば、整数チェックや通貨の一致チェックがクラスの境界で必ず行われます。

    5.まとめ

    ケース1：注文管理システム

    • 名詞・動詞からクラスと責務を配置
    • GRASP で Expert / Creator / Controller を適用
    • Repository で永続化を抽象化
    • 小さく実装しテストで振り返る

    ケース2：課金・決済ロジック

    • 変化の多い決済は Strategy + Factory が定番
    • Money 等の値オブジェクトでルールを閉じる
    • switch 肥大・プリミティブ偏り・API 漏れが典型ミス
    • 拡張点を先に切り、テストで各 Strategy を独立検証
