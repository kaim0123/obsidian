    50 デザインパターン ／ 53 構造

    構造パターン — 小さな部品を賢く組み合わせる7つの型

    既存のクラスに機能を足す、形の違うAPIをつなぐ、複雑な仕組みに簡単な入口を作る — オブジェクトの「組み合わせ方」を工夫するのが構造パターンです。GoF の構造パターン7種（Adapter・Bridge・Composite・Decorator・Facade・Flyweight・Proxy）を、解決する問題・使いどころ・コード例で解説します。

    もとにしたノート：53_構造/01_構造に関するパターン

    ひとことで言うと

    構造パターン は「小さな部品を 賢く組み合わせて 大きな仕組みを作る」ためのパターン群です。APIが合わなければ Adapter、機能を積み重ねるなら Decorator、ツリーを一様に扱うなら Composite、複雑さを隠すなら Facade、アクセスを制御するなら Proxy を選びます。

    1.このページで扱うこと

    オブジェクトを どう組み合わせるか を工夫するのが 構造に関するパターン です。既存のクラスに機能を追加したり、違う形のAPIを繋いだり、複雑な仕組みに簡単な入口を作ったりするのに使います。

    このページでは、GoF の構造パターン7種それぞれについて「何を解決するか」「使いどころ」「例」を見て、最後に使い分けを整理します。パターン全体の位置づけは GoFパターンの概要 を参照してください。

    2.GoFの構造パターン7種

    パターン目的
    Adapter互換性のないAPIを繋ぐ
    Bridge抽象と実装を別々に拡張
    Compositeツリー構造を一様に扱う
    Decoratorオブジェクトを包んで機能追加
    Facade複雑な仕組みに単純な窓口
    Flyweight共通部分を共有してメモリ節約
    Proxy本物の代理として振る舞う

    3.Adapter（アダプター）

    3.1 何を解決するか

    「使いたいライブラリがあるけど、インターフェース（呼び出し方・メソッドの形）が合わない」問題。

    3.2 使いどころ

    • 古いAPIと新しいAPIを繋ぐ
    • 外部ライブラリを自社の規約に合わせる
    • 型の形が異なるオブジェクト同士を繋ぐ

    3.3 例

    // 自社コードは renderJSON(data) を期待している
// しかし、使いたいライブラリは toXML() しか出せない

class XMLLibrary {
  toXML() { return '<data>...</data>'; }
}

// Adapter で JSON に見せかける
class XMLtoJSONAdapter {
  constructor(xmlLib) { this.xmlLib = xmlLib; }
  renderJSON() {
    const xml = this.xmlLib.toXML();
    return xmlToJson(xml); // 変換
  }
}

    現実世界の 「電源プラグの変換アダプター」 そのままのイメージです。

    4.Bridge（ブリッジ）

    4.1 何を解決するか

    「抽象（使う側）と 実装（使われる側）が強く結びついていて、どちらも拡張しにくい」問題。

    4.2 使いどころ

    • 抽象階層と実装階層を 独立して拡張 したい
    • クロスプラットフォーム実装を共通の抽象で使いたい

    4.3 例：図形 × 描画API

    // 実装側
interface Renderer {
  drawCircle(x: number, y: number, r: number): void;
}
class CanvasRenderer implements Renderer { /* ... */ }
class SVGRenderer implements Renderer { /* ... */ }

// 抽象側
class Shape {
  constructor(protected renderer: Renderer) {}
}
class Circle extends Shape {
  constructor(renderer: Renderer, private x: number, private y: number, private r: number) {
    super(renderer);
  }
  draw() { this.renderer.drawCircle(this.x, this.y, this.r); }
}

// 組み合わせ自由
new Circle(new CanvasRenderer(), 0, 0, 10).draw();
new Circle(new SVGRenderer(), 0, 0, 10).draw();

    図形が増えても、描画方式が増えても、片方だけに影響 します。もし継承だけで作ると「CanvasCircle・SVGCircle・CanvasSquare・SVGSquare…」と、図形の数 × 描画方式の数だけクラスが必要になります。

    5.Composite（コンポジット）

    5.1 何を解決するか

    「ツリー構造 を、葉（単体）も 枝（集合）も 同じインターフェース で扱いたい」問題。

    5.2 使いどころ

    • ファイルシステム（ファイル・フォルダ）
    • GUI（ボタン・コンテナ）
    • 組織階層

    5.3 例

    class File {
  constructor(name, size) { this.name = name; this.size = size; }
  getSize() { return this.size; }
}

class Folder {
  constructor(name) { this.name = name; this.children = []; }
  add(child) { this.children.push(child); }
  getSize() {
    return this.children.reduce((sum, c) => sum + c.getSize(), 0);
  }
}

const root = new Folder('root');
root.add(new File('a.txt', 10));
const sub = new Folder('sub');
sub.add(new File('b.txt', 20));
root.add(sub);

console.log(root.getSize()); // 30 — FileとFolderを意識せず計算

    6.Decorator（デコレーター）

    6.1 何を解決するか

    「既存クラスを変更せずに、機能を追加 したい」問題。継承の代わりになる 合成（オブジェクトを中に持って処理を任せること）ベースの仕組みです（継承より合成）。

    6.2 使いどころ

    • ログを追加する
    • キャッシュを追加する
    • 認証チェックを追加する
    • 入出力を圧縮・暗号化する

    6.3 例

    class BasicCoffee {
  cost() { return 300; }
  describe() { return 'コーヒー'; }
}

class MilkDecorator {
  constructor(coffee) { this.coffee = coffee; }
  cost() { return this.coffee.cost() + 50; }
  describe() { return this.coffee.describe() + ' + ミルク'; }
}

class SugarDecorator {
  constructor(coffee) { this.coffee = coffee; }
  cost() { return this.coffee.cost() + 30; }
  describe() { return this.coffee.describe() + ' + 砂糖'; }
}

let coffee = new BasicCoffee();
coffee = new MilkDecorator(coffee);
coffee = new SugarDecorator(coffee);
console.log(coffee.describe(), coffee.cost()); // コーヒー + ミルク + 砂糖 380

    継承ツリーを増やさずに、必要な機能を積み重ね られます。

    7.Facade（ファサード）

    7.1 何を解決するか

    「複雑なサブシステム（内部で協力し合う多数のクラスのまとまり）を使うとき、関連する多くのクラスを扱うのが大変」問題。Facade は「建物の正面」という意味です。

    7.2 使いどころ

    • ライブラリに対する シンプルなラッパー を作る
    • 複数のAPIを呼ぶ一連の流れを1つにまとめる

    7.3 例

    // 複雑なサブシステム
class VideoDecoder { /* ... */ }
class AudioMixer { /* ... */ }
class Subtitles { /* ... */ }
class Renderer { /* ... */ }

// Facade: 簡単な窓口
class VideoPlayer {
  play(file) {
    const video = new VideoDecoder().decode(file);
    const audio = new AudioMixer().mix(file);
    const subs = new Subtitles().load(file);
    new Renderer().render(video, audio, subs);
  }
}

new VideoPlayer().play('movie.mp4'); // 利用側はこれだけ

    内部の複雑さを隠して、簡単に使える入口 を提供するのがポイントです。

    8.Flyweight（フライウェイト）

    8.1 何を解決するか

    「同じようなオブジェクトを大量に作ると、メモリが爆発 する」問題。

    8.2 使いどころ

    • テキストエディタの文字（フォント情報を共有）
    • ゲームの大量の敵・弾
    • アイコン・画像

    8.3 例

    // 共有する部分（不変）
class CharacterStyle {
  constructor(font, size, color) {
    this.font = font;
    this.size = size;
    this.color = color;
  }
}

const styleCache = {};
function getStyle(font, size, color) {
  const key = `${font}-${size}-${color}`;
  if (!styleCache[key]) styleCache[key] = new CharacterStyle(font, size, color);
  return styleCache[key]; // 同じキーなら同じインスタンスを返す
}

// 固有の部分だけ個別に
class Character {
  constructor(char, style) {
    this.char = char;
    this.style = style;
  }
}

    共有する部分は 不変（作った後に中身を変えない）にしておくのが前提です。共有しているオブジェクトを書き換えると、それを使うすべての文字に影響してしまうからです。

    9.Proxy（プロキシ）

    9.1 何を解決するか

    「本物のオブジェクトへのアクセスを、間に何か挟んで制御したい」問題。

    9.2 使いどころ

    • 遅延読み込み（重い処理を後回し）
    • アクセス制御（権限チェック）
    • キャッシュ
    • ログ

    9.3 例：画像の遅延読み込み

    class RealImage {
  constructor(filename) {
    this.filename = filename;
    this.load();
  }
  load() { console.log(`読み込み: ${this.filename}`); } // 重い
  display() { console.log(`表示: ${this.filename}`); }
}

class ImageProxy {
  constructor(filename) { this.filename = filename; }
  display() {
    if (!this.real) this.real = new RealImage(this.filename); // 本当に必要になってから
    this.real.display();
  }
}

const img = new ImageProxy('big.jpg'); // ここでは読み込まれない
img.display(); // 初回のみ読み込み発生
img.display(); // 2回目は再利用

    10.構造パターンの使い分け

    状況パターン
    既存APIと合わないAdapter
    抽象と実装を独立させたいBridge
    ツリーを一様に扱うComposite
    機能を積み重ねたいDecorator
    複雑な仕組みをシンプルに見せるFacade
    大量オブジェクトのメモリ節約Flyweight
    アクセスに制御・遅延を入れたいProxy

    11.よくある誤解

    誤解1：「Adapter・Decorator・Proxy・Facade は、どれも『包むだけ』だから同じ」

    どれも別のオブジェクトを中に持つ点は似ていますが、目的が違います。Adapter は 形の合わないインターフェースを合わせる、Decorator は 同じインターフェースのまま機能を積み重ねる、Proxy は 同じインターフェースのままアクセスを制御・遅延する、Facade は 多数のクラスに対する簡単な入口を作る ものです。上の使い分けの表で「どんな状況か」から選びます。

    誤解2：「機能を足すなら継承でサブクラスを作るのが基本」

    ミルク入り・砂糖入り・ミルクと砂糖入り…と組み合わせごとにサブクラスを作ると、継承ツリーが増え続けます。Decorator なら既存クラスを変更せず、必要な機能を実行時に積み重ねられます（継承より合成）。

    12.まとめ

    • 構造パターンは、オブジェクトを どう組み合わせるか を工夫するパターン群
    • Adapter：合わないAPIを繋ぐ（電源プラグの変換アダプター）
    • Bridge：抽象と実装を分け、それぞれ独立に拡張する
    • Composite：葉も枝も同じインターフェースでツリーを扱う
    • Decorator：包んで機能を積み重ねる（継承の代わり）
    • Facade：複雑なサブシステムに簡単な窓口を作る
    • Flyweight：共通部分を共有してメモリを節約する
    • Proxy：本物の代理として、アクセスに制御・遅延を挟む

    次は、オブジェクト間のやり取りを扱う 振る舞いパターン に進みます。
