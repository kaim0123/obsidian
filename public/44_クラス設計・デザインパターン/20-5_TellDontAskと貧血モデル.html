    20 責務の割り当て

    Tell, Don't Ask と貧血モデル — 判断はデータを持つクラスに任せる

    「オブジェクトにデータを尋ねて、呼ぶ側で判断する」書き方を続けると、業務ルールがサービスに散らばった「貧血ドメインモデル」になります。Tell, Don't Ask の原則、貧血モデルの問題と生まれる理由、リッチなドメインモデルへのリファクタリング、getter / setter との付き合い方、貧血モデルが許される場面までを、コード例で解説します。

    もとにしたノート：20_責務の割り当て/05_Tell_Dont_Askと貧血モデルの回避

    ひとことで言うと

    Tell, Don't Ask（尋ねるな、命じよ）は、オブジェクトからデータを取り出して呼ぶ側で判断するのではなく、「何をしてほしいか」をオブジェクトに命じる 原則です。これが守られず、クラスがデータ（getter / setter）だけを持ち、業務ロジックがサービスに集まった状態を 貧血ドメインモデル と呼びます。判断や計算は、データを持つクラスの中 に置きましょう。

    1.このページで扱うこと

    GRASP の 情報エキスパート（責務は、その情報を持っているクラスに割り当てる）を学びました。このページでは、その考え方を 日々のコードの書き方 に落とし込む原則と、その原則が守られないときに生まれるアンチパターン（よくある悪い設計の型）を学びます。

    • 貧血ドメインモデル（Anemic Domain Model）とは何か、なぜ問題か

    2.Tell, Don't Ask

    2.1 原則

    原則

    オブジェクトにデータを尋ねて、呼ぶ側で判断・処理するのではなく、オブジェクトに「何をしてほしいか」を命じよ。

    『達人プログラマー』の著者 Andy Hunt と Dave Thomas が広め、Martin Fowler も bliki（Fowler のウェブサイト上の用語解説集）で解説しています。

    ✕ Ask（尋ねて、呼ぶ側で判断する） 
    if (account.getBalance() >= amount) {
  account.setBalance(account.getBalance() - amount);
} else {
  throw new Error("残高不足");
}
    ◯ Tell（命じる。判断はオブジェクト自身が行う） 
    account.withdraw(amount);

    2.2 なぜ Tell なのか

    Ask のコードTell のコード
    「残高が足りるか」の 判断が呼ぶ側にある判断が データを持つクラスの中 にある
    同じ判断が、引き出しを行う あちこちに重複 する判断は 1か所
    setBalance で 誰でも残高を自由に書き換えられる残高は withdraw / deposit を通してしか変わらない
    「残高はマイナスにならない」というルールを 全員が守る必要があるルールは クラスが守る（不変条件のカプセル化）

    ここでいう 不変条件 とは、「残高はマイナスにならない」のように、そのオブジェクトが いつでも満たしているべきルール のことです。

    つまり Tell, Don't Ask は、データとそれを扱うロジックを同じ場所に置く（カプセル化・情報エキスパート）ための、実践的な合言葉です（→ カプセル化と情報隠蔽）。

    2.3 デメテルの法則との関係

    ✕ 友達の友達に話しかけている（デメテルの法則違反） 
    order.getCustomer().getAddress().getPrefecture() === "沖縄県"
    ◯ 直接の相手に命じる・尋ねる 
    order.isRemoteIslandDelivery()
    • デメテルの法則（直接の友達とだけ話せ）は、Tell, Don't Ask と同じ方向の原則です（→ 48_原則 のノート『02_デメテルの法則』）
    • 長いメソッドチェーン（a.getB().getC().getD()）は、Fowler のコードの臭い メッセージの連鎖（Message Chains） にあたります（コードの臭い ＝ 設計の問題を疑うべき兆候。→ コードの臭いとリファクタリング）

    2.4 Tell, Don't Ask の限界

    Fowler 自身は、この原則を 厳格には使っていない と述べています。

    • 画面表示 や レポート のためには、データを取り出す（Ask する）必要がある
    • すべてを Tell にしようとすると、表示用のロジックまでドメインのクラスに入ってしまう
    • 大事なのは「判断や計算のロジックを、データの近くに置く」こと。データを読むこと自体は悪くない
    Ask してよいTell にすべき
    画面に表示する、レポートを作る、ログに出す状態を変える 処理
    データをそのまま外部に渡す（DTO に詰める）業務ルールに基づく判断（キャンセルできるか、割引が適用されるか）

    DTO（Data Transfer Object）は、データを運ぶためだけの入れ物です（→ オブジェクトの種類の整理）。

    3.貧血ドメインモデル

    3.1 定義

    定義

    ドメインのクラスが、データ（getter / setter）だけを持ち、振る舞い（業務ロジック）をほとんど持たない状態。ロジックはすべて「サービス」クラスに書かれる。

    Martin Fowler が 2003 年の bliki 記事「Anemic Domain Model」で名付けました（anemic ＝ 貧血の）。増田亨『現場で役立つシステム設計の原則』第3章では、同じ構造を データクラス（データを格納するクラス）とロジッククラス（機能クラス）の分離 として批判しています。

    ✕ 貧血ドメインモデル 
    class Order {
  id: string;
  status: "draft" | "placed" | "shipped" | "cancelled";
  items: OrderItem[];
  total: number;
  // getter / setter だけ
}

class OrderService {
  cancel(order: Order) {
    if (order.status === "shipped") throw new Error("発送済みはキャンセル不可");
    if (order.status === "cancelled") throw new Error("キャンセル済み");
    order.status = "cancelled";
  }

  addItem(order: Order, item: OrderItem) {
    if (order.status !== "draft") throw new Error("確定後は変更不可");
    order.items.push(item);
    order.total = order.items.reduce((sum, i) => sum + i.price * i.quantity, 0);
  }
}

    3.2 なぜ問題か

    Fowler は、貧血ドメインモデルを 「実質的には手続き型の設計」 だと批判しています。

    問題説明
    オブジェクト指向の利点がないデータと処理を一緒にするというオブジェクト指向の基本が失われている。それでいて、ドメインモデルを作るコスト（DB との対応づけなど）は払っている
    ルールが散らばる「確定後は変更不可」が OrderService にも AdminOrderService にも OrderImportBatch にも書かれる
    不正な状態を作れるorder.status = "shipped" や order.total = 0 を、どこからでも直接書き換えられる
    サービスが肥大化するすべてのロジックがサービスに集まり、神クラス（何でも知っていて何でもする巨大なクラス）になる
    知識がどこにあるか分からない「注文はいつキャンセルできるか」を知るために、複数のサービスを読む必要がある

    3.3 なぜ生まれるのか

    • DB のテーブルをそのままクラスにする（ORM のエンティティ＝テーブルの行。ORM はテーブルとオブジェクトを対応づけるライブラリ）
    • 「エンティティは純粋なデータ、ロジックはサービス層」という 誤ったレイヤードの理解
    • フレームワークが setter を要求する（古い ORM・シリアライザ）
    • Tell, Don't Ask を知らない

    3.4 データクラスを使うと同じロジックがあちこちに重複する

    データをどこからでも読める（getter）と、判断・計算は 使う側（サービス／コントローラ） に書けます。その結果、同じ金額計算や判定が「注文登録」「注文更新」「出荷」など複数の機能クラスにコピーされます。ルール変更のたびに、どのクラスが変更対象か追いきれなくなります。

    3.5 データクラスを使うと業務ロジックの見通しが悪くなる

    三層（プレゼンテーション／アプリケーション／データソース）で分けていても、データクラス方式だと アプリケーション層の構造が画面やテーブルの都合に引きずられます。

    引きずられる側起きやすいこと
    画面寄り「注文画面」用のデータクラス → 登録用・更新用の機能クラスそれぞれに同じ計算が重複
    テーブル寄り注文 CRUD 用・出荷 CRUD 用の機能クラスに、合計金額などのロジックが散在

    「どこに業務ルールがあるか」が見えず、変更の影響調査が難しくなります。（CRUD ＝ 作成・読み取り・更新・削除という、データの基本操作のことです。）

    3.6 共通機能ライブラリが失敗する理由

    重複を Util / Common クラスに寄せても、次の二パターンで使われなくなりがちです。

    1. 汎用化しすぎる — 微妙に違うニーズに合わせ引数が増え、使う側が無関係な引数まで気にする → 「自分で書いた方が早い」
    2. 用途別にメソッドが増えすぎる — 似たメソッドが並び、どれを使うか探すコストが上がる → 同じく自前実装へ

    共通化の置き場は「何でも屋のライブラリ」ではなく、データを持つドメインオブジェクト側（業務ロジックをデータと一体にする）に寄せる方が長続きします。

    3.7 【COLUMN】データクラスが広く使われているのはなぜか

    理由補足
    手続き型の延長で書きやすい「データ構造」と「処理」を分ける発想が馴染みやすい
    ORM・画面バインドと相性がよいテーブルやフォーム項目と 1:1 のプロパティが作りやすい
    フレームワークのサンプルがそうなっているチュートリアルが DTO／Entity（getter/setter）中心になりがち
    単純 CRUD では困りにくいルールが薄い間はコストが見えない（→ 6. 貧血モデルが許される場面）

    コアドメイン（そのシステムの競争力の中心になる業務領域）でルールが増えたあともデータクラスのままにすると、重複と見通しの悪さが一気に表面化します。

    3.8 業務ロジックをわかりやすく整理する基本のアプローチ

    増田本第3章の方針は次の2つです。

    1. データとロジックを一体にして 業務ロジックを整理する（→ 業務ロジックをデータと一体にする）
    2. 三層の関心事と業務ロジックの分離を徹底する（三層＋ドメインモデル → 41章：層化・三層・レイヤード・42章：ドメイン層とユースケース）

    4.リッチなドメインモデルへ

    4.1 リファクタリング後

    ◯ リッチなドメインモデル：ルールをクラス自身が守る 
    class Order {
  private constructor(
    readonly id: OrderId,
    private status: OrderStatus,
    private readonly items: OrderItem[],
  ) {}

  static create(id: OrderId): Order {
    return new Order(id, "draft", []);
  }

  addItem(item: OrderItem): void {
    if (this.status !== "draft") throw new DomainError("確定後は商品を追加できません");
    this.items.push(item);
  }

  cancel(): void {
    if (!this.canCancel()) throw new DomainError("この注文はキャンセルできません");
    this.status = "cancelled";
  }

  canCancel(): boolean {
    return this.status === "draft" || this.status === "placed";
  }

  get total(): Money {
    return this.items.reduce((sum, i) => sum.add(i.subtotal()), Money.zero("JPY"));
  }
}
    ◯ サービス（アプリケーションサービス）は「手順」だけを担う 
    class CancelOrderUseCase {
  async execute(orderId: OrderId) {
    const order = await this.orders.findById(orderId);
    order.cancel();                    // Tell：判断は Order に任せる
    await this.orders.save(order);
    await this.events.publish(new OrderCancelled(orderId));
  }
}

    4.2 変わったこと

    観点貧血モデルリッチなモデル
    status の変更どこからでも直接代入cancel() などのメソッド経由だけ
    キャンセルできるかの判断サービスごとに重複Order.canCancel() の1か所
    total誰かが計算して代入（ずれる可能性）常に明細から計算（ずれない）
    サービスの役割ロジックのすべて取得 → 命令 → 保存 → 通知 の 手順だけ

    これは 42章の ドメイン層とユースケース でいう ドメイン層とアプリケーション層の役割分担 です。

    4.3 リファクタリングの手順

    1. サービスの中で、1つのエンティティのデータだけを使っている処理 を探す（Fowler の臭い 機能の横恋慕（Feature Envy）。自分のクラスより他のクラスのデータに興味を持っているメソッドのこと）
    2. その処理を、エンティティのメソッドとして移動 する（リファクタリング Move Function）
    3. エンティティの setter を削除 し、意味のある名前のメソッド（cancel・addItem）に置き換える
    4. 計算で求められる値（total）は、フィールドに保存せず計算する か、変更時に必ず再計算する
    5. 不正な状態を防ぐチェックを、エンティティの中 に移す

    5.getter / setter との付き合い方

    種類方針
    setter原則として作らない。状態の変更は、業務上の意味を持つ名前のメソッド（changeAddress・approve）にする
    getter表示・保存のために必要なものは作ってよい。ただし、getter で取り出した値で判断している呼び出し側のコード がないかに注意する
    コレクションの getter内部の配列をそのまま返さない（呼ぶ側で push されてしまう）。readonly な配列やコピーを返す
    ✕ 内部の配列をそのまま返す → 外から items.push() できてしまう 
    get items(): OrderItem[] { return this.items; }
    ◯ 読み取り専用にする 
    get items(): ReadonlyArray<OrderItem> { return this.items; }

    6.貧血モデルが許される場面

    貧血モデルは 常に悪い わけではありません。

    場面理由
    単純な CRUD アプリ業務ルールがほとんどないなら、ドメインモデルを作るコストに見合わない（トランザクションスクリプト ＝ 処理の手順を1つの手続きに書く方式 で十分）
    DTO・API のリクエスト／レスポンスデータの受け渡しが目的なので、振る舞いを持たない方が正しい
    支援サブドメイン・汎用サブドメイン42章の コアドメインとサブドメイン でいう、競争優位を生まない単純な部分
    関数型スタイルの設計データ（型）と振る舞い（関数）を意図的に分ける設計。ただしその場合は、不変データ＋状態ごとの型 でルールを守る（42章の 型でドメインを表す）

    問題になるのは

    業務ルールが複雑な部分（コアドメイン） で、ルールがサービスに散らばっている状態です。

    7.よくある誤解

    誤解1：「ドメインのクラスにロジックを入れると、層の分離が崩れる」

    誤りです。 ドメイン層に置くべきなのは 業務ルール です。DB アクセスや HTTP のような 技術的な処理 を入れないことと、業務ロジックを入れないことは別の話です。

    誤解2：「Tell, Don't Ask なら getter は禁止」

    誤りです。 表示や保存のためにデータを読むのは問題ありません。避けるべきは、読んだデータで呼ぶ側が判断・計算・状態変更をすること です。

    誤解3：「サービスクラスがあるのは貧血モデルの証拠」

    誤りです。 アプリケーションサービス（ユースケース）は、手順を組み立てる役として必要です。問題なのは、業務ルールまでサービスに書かれていること です。

    8.まとめ

    • Tell, Don't Ask：データを尋ねて呼ぶ側で判断するのではなく、オブジェクトに命じる。判断はデータを持つクラスに置く
    • デメテルの法則・情報エキスパート と同じ方向の原則。ただし表示・保存のための Ask は問題ない
    • 貧血／データクラス：ロジックが機能クラスに重複し、画面・テーブル都合で見通しが悪くなる。Util 寄せも失敗しやすい
    • 整理の基本は データとロジックの一体化 と 三層と業務ロジックの分離（三層＋ドメインモデル）
    • リファクタリング：機能の横恋慕を探す → メソッドを移動 → setter を意味のあるメソッドに置き換える
    • 貧血モデルが許されるのは、単純な CRUD・DTO・支援サブドメイン。問題はコアドメインでルールが散らばること
