    60 アンチパターンとコードの臭い

    アンチパターンの見分け方 — 一見よさそうな悪い解き方

    神クラス・スパゲッティ継承・貧血モデル・魔法の数字など、クラス設計でよく見るアンチパターンを症状・原因・脱出法で整理します。良いパターンとの見分け方、パターンを使うかどうかの判断基準、そして「パターンを使わない勇気」までを解説します。

    もとにしたノート：60_アンチパターンとコードの臭い/01_アンチパターンとの見分け、02_アンチパターンとコードの臭い

    ひとことで言うと

    アンチパターン（Anti-Pattern） は 「一見よさそうだが、実は悪い結果を生む解き方」 です。良いパターンとアンチパターンは見た目がよく似ていることがあるので、コードの形ではなく、意図と結果 で見分けます。「パターンを使った」こと自体に価値はなく、問題を解いているかどうか がすべてです。

    1.このページで扱うこと

    このページでは、クラス設計でよくある アンチパターン を見分け、脱出の考え方を学びます。良いパターンとの対比で判断眼を養います。

    • アンチパターンとは何か、なぜ学ぶのか
    • クラス設計の典型：神クラス・スパゲッティ継承・貧血モデル・魔法の数字
    • その他の代表的なアンチパターン：スパゲッティコード・コピペ・早すぎる最適化・過剰設計・Singleton の誤用・Yo-Yo 問題・デッドコード
    • 良いパターンとアンチパターンの見分け方と判断基準
    • コードの匂い（アンチパターンの一歩手前のサイン）
    • アンチパターンからの脱出法と、パターンを使わない勇気

    2.アンチパターンとは

    デザインパターン が「繰り返し現れる設計問題の、良い解き方」なのに対し、アンチパターン（Anti-Pattern） は 「一見よさそうだが、実は悪い結果を生む解き方」 です。

    良いパターンもアンチパターンも、見た目はよく似ていることがあります。大事なのは、コードの形ではなく、意図と結果 を見極めることです。

    2.1 なぜアンチパターンを学ぶのか

    1. やらかしを避けるため
    2. 「これパターンっぽいな」と思っても、実はアンチパターンだった ということを防ぐため
    3. 他人のコードレビューで根拠を持って指摘 できるようになるため

    3.クラス設計の典型的なアンチパターン

    クラス設計では、次の 神クラス・スパゲッティ継承・貧血モデル が三大典型です。これに魔法の数字を加えた4つを、症状・原因・脱出法で見ていきます。一覧は チェックリストとアンチパターン（付録E よくあるアンチパターン一覧）を参照してください。

    3.1 神クラス（God Object）

    神クラス（神オブジェクト）は、システムのあらゆる処理を抱えた巨大クラスです。1つのクラスが全てを知っている 状態で、UserManager や AppController のような名前になりがちです。

    症状Application, Manager, Util が数千行
    原因SRP（単一責任の原則）無視、とりあえず1か所に書く
    脱出変更理由で Extract Class（クラスの抽出）、単一責任の原則
    ✕ 神オブジェクト 
    class AppController {
  login() {}
  logout() {}
  register() {}
  sendEmail() {}
  processPayment() {}
  generateReport() {}
  backupDatabase() {}
  // ...さらに50メソッド
}

    SRP 違反 です。責任を分割するのが正解です。変更理由ごとにブロックを見つけ、別のクラスへ抽出します。

    3.2 スパゲッティ継承

    深く絡み合った継承階層 で、オーバーライド（親のメソッドの上書き）と super（親のメソッドの呼び出し）が追えなくなる状態です。

    症状5層以上、兄弟クラスで挙動が矛盾
    脱出合成 + インターフェース、階層のフラット化
    ✕ 危険 — 各層で speak() を上書き 
    class A { speak() { return 'A'; } }
class B extends A { speak() { return super.speak() + 'B'; } }
// … さらに継続

    リスコフの置換原則 と 継承と多態 を復習しましょう。合成への置き換えは 継承より合成 で扱います。

    3.3 貧血モデル（Anemic Domain Model）

    貧血ドメインモデル は、エンティティ（ドメインオブジェクト）が 単なるデータの入れ物 になっていて、ロジック（振る舞い）が外のサービスクラスに偏る 状態です。

    ✕ ルールが全部サービスにある 
    class Order { get lines() { return this._lines; } }
class OrderService {
  confirm(order) { /* ルールは全部ここ */ }
}
    ✕ データだけの User 
    class User {
  constructor(email, password) { this.email = email; this.password = password; }
}

// 処理は全部ここ
class UserService {
  validateEmail(user) { /* ... */ }
  hashPassword(user) { /* ... */ }
  canLogin(user) { /* ... */ }
}

    データと振る舞いが離れるので、カプセル化の意義が失われます。

    脱出ルールを Order.confirm() へ Move Method（メソッドの移動）
    関連クラス分割の基本プロセス、Tell, Don't Ask と貧血モデル

    3.4 魔法の数字・魔法の文字列（Magic Number / Magic String）

    意味の分からない数値・文字列が直書きされ、定数がクラス内に散在している状態です。

    ✕ 3 とは？ 'adm' は typo しやすい 
    if (order.status === 3) { /* 3 とは？ */ }
if (user.role === 'adm') { /*  typo しやすい */ }
if (user.role === 3) { /* 3って何？ */ }
if (status === 'AA23X') { /* 何これ？ */ }
    脱出値オブジェクト・列挙型（enum）・名前付き定数（定数化・enum 化する）
    例OrderStatus.CONFIRMED, Role.ADMIN

    値オブジェクトについては 値オブジェクトと完全コンストラクタ、区分を型で表す方法は 区分オブジェクトと状態遷移 を参照してください。

    4.その他の代表的なアンチパターン

    Spaghetti Code（スパゲッティコード）

    制御の流れが入り組んで 追えないコード。goto・深いネスト・多数のグローバル変数などが原因です。

    Copy & Paste Programming

    同じようなコードをコピペで増やす。DRY（同じ知識を繰り返さない）違反です。

    Premature Optimization（早すぎる最適化）

    計測せずに「速そうだから」という理由で難しいコードを書く。たいていは読みにくくなるだけで、本当のボトルネック（全体を遅くしている箇所）は別の場所にあります。

    「早すぎる最適化は諸悪の根源である」 — ドナルド・クヌース

    Over Engineering（過剰設計）

    将来のための拡張性 や 万能な抽象化 を求めすぎて、今必要なものまで見えなくなる。YAGNI（今必要ないものは作らない）違反です。

    Singleton の誤用

    グローバル変数の置き換え として Singleton を乱用すると、テストが難しくなり、依存関係が見えなくなります。

    Yo-Yo Problem

    継承階層が深すぎて、1つのメソッドの挙動を理解するのに何階層も上下に行き来 する必要がある状態です。

    Dead Code（デッドコード）

    使われていないコード。「念のため残しておく」が溜まると、読むコストばかり増えます。Git に残して削除するのが正解です。

    ✕ 過剰設計：Hello World にファクトリーと戦略を盛り込む 
    class GreetingStrategyFactory { /* ... */ }
class JapaneseGreetingStrategy { /* ... */ }
// 本来は console.log('こんにちは') で済む

    DRY・KISS・YAGNI の原則は 48_原則 のノート『01_DRY_KISS_YAGNI』で扱っています。

    5.良いパターンとアンチパターンの見分け方

    同じパターンでも、使う理由しだいで良いパターンにもアンチパターンにもなります。

    対比良い使い方アンチパターン
    Singleton vs グローバル変数置き場本当に1つしかあってはいけないもの（ハードウェア制御など）単にどこからでもアクセスしたいから使う
    Strategy vs 過剰抽象化本当にアルゴリズムを差し替える必要がある1種類しか実装がないのに抽象化している
    Factory vs 新規関数の濫用作るクラスを条件で切り替える必要があるnew Foo() で済むものに Factory を噛ませる
    Observer vs カプセル化破り疎結合に通知する大量のリスナーが相互に依存し、結局追跡不能になる

    各パターンの本来の使い方は 生成パターン・構造パターン・振る舞いパターン を参照してください。

    6.判断基準

    1. 今、本当にそれが必要か？（YAGNI）
    2. パターンなしで書いたコードより、読みやすくなっているか？
    3. テストしやすくなっているか？
    4. 将来の仕様変更に対して、変更範囲が狭くなるか？

    自信を持って Yes と言えないなら

    これらに 自信を持って Yes と言えないなら、パターンを外すほうが良いことが多いです。

    7.コードの匂い（Code Smell）

    アンチパターンに陥る一歩手前のサインを コードの匂い（Code Smell） と呼びます。Martin Fowler『リファクタリング』に多数紹介されています。

    匂い説明
    Long Method関数が長すぎる
    Large Classクラスが大きすぎる
    Long Parameter List引数が多すぎる
    Duplicate Code重複
    Feature Envy他のクラスのデータばかり触る
    Data Clump同じ引数群が何度も登場
    Shotgun Surgery1つの変更が多くの場所に影響
    Divergent Change1つのクラスが複数の理由で変わる

    匂いを見つけたら、リファクタリング（外から見た振る舞いを変えずに内部の構造を改善すること）で適切なパターンに置き換える のが定石です。24 の臭いと対処の一覧は コードの臭いとリファクタリング、リファクタリングの考え方は 42章：テストとリファクタリング を参照してください。

    8.アンチパターンからの脱出法

    1. 名前で疑う — Manager, Util, Helper の肥大
    2. テストで露呈 — モック地獄、セットアップが長い
    3. 小さく切る — Extract Class / Extract Interface
    4. 振る舞いを移す — Move Method で Expert（そのデータを持つ情報エキスパート、→ GRASP）に
    5. レビューで共有 — クラス設計レビュー

    進め方の流れは次のとおりです。

    気づく → 原因を言語化 → 1つずつリファクタ → テストで守る

    9.パターンを使わない勇気

    • 問題がないのに使わない（YAGNI）
    • 1つしか実装がないのに抽象化しない
    • 読みにくくなるならパターンを外す

    問題を解いているかどうかがすべて

    「パターンを使った」こと自体は価値ではありません。問題を解いているかどうか がすべてです。

    10.よくある誤解

    誤解1：「パターンを使ったコードは良い設計だ」

    パターンを使ったこと自体に価値はありません。1種類しか実装がないのに Strategy を入れる、new Foo() で済むのに Factory を噛ませる、といった使い方はむしろアンチパターンです。判断基準 の4つの問いに自信を持って Yes と言えるかで判断します。

    誤解2：「アンチパターンはコードの形で見分けられる」

    良いパターンとアンチパターンは見た目がよく似ていることがあります。同じ Singleton でも、ハードウェア制御のように本当に1つしかあってはいけないものなら良い使い方、単にどこからでもアクセスしたいだけならアンチパターンです。意図と結果 を見ます。

    誤解3：「念のため残しておいたコードは無害」

    使われていないコードは、読む人にとってのコストです。過去のコードは Git に残っているので、デッドコードは削除して構いません。

    11.まとめ

    • アンチパターン ＝ 一見よさそうだが、実は悪い結果を生む解き方。形ではなく意図と結果 で見分ける
    • 神クラス・スパゲッティ継承・貧血モデル がクラス設計の三大典型
    • 魔法の数値は 値オブジェクト・列挙 で置き換え
    • SRP・合成・ドメインへのロジック移動 が脱出の鍵
    • パターンを使うかは「今必要か・読みやすいか・テストしやすいか・変更範囲が狭くなるか」で判断する
    • コードの匂い はアンチパターンの一歩手前のサイン。リファクタリングで対処する
    • レビューとテストで早期発見。問題がないなら、パターンを使わない勇気も持つ
