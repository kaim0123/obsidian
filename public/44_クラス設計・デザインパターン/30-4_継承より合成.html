    継承より合成 — 継承の代わりに合成をどう使うか

    GoF が「クラスの継承より、オブジェクトの合成を優先せよ」と勧めたのはなぜでしょうか。継承の最大の問題である「脆い基底クラス問題」、継承を合成に置き換える4つの技法（委譲・Strategy・Decorator・インターフェース）、それでも継承を使ってよい場面を、TypeScript の例と画像ライブラリの例で解説します。

    もとにしたノート：30_クラスの関係/04_継承より合成、30_クラスの関係/【入門】継承とコンポジションとは何か（直也テックの動画メモ）

    ひとことで言うと

    継承は親クラスの実装に強く縛られる 最も強い結合 です。型の共有はインターフェースで、実装の共有は合成で 分けて行い、継承は「本当に is-a で、継承用に設計された親・浅い階層」のときだけ使います。

    1.このページで扱うこと

    継承と多態 では継承の仕組みを、42章の 継承と合成 では「is-a と has-a」の考え方を学びました。このページでは、クラス設計の場面で、継承の代わりに合成をどう使うか を具体的に学びます。

    • GoF が「継承より合成」を勧めた理由
    • 継承の最大の問題：脆い基底クラス問題
    • 継承を合成に置き換える 具体的な技法（委譲・Strategy・Decorator・インターフェース）
    • それでも 継承を使ってよい場面
    • TypeScript での書き方
    • 動画メモ：画像ライブラリの例で見る「継承の落とし穴」と「コンポジション＋インターフェース＋DI」

    合成（コンポジション）とは、別のクラスのオブジェクトを 部品としてフィールドに持ち、その部品を使って 機能を実現することです。

    2.GoF の原則

    1994 年の『デザインパターン』（GoF 本。4人の著者 Gang of Four の頭文字）は、序章で2つの原則を掲げました。

    GoF 本の2つの原則

    1. 実装ではなく、インターフェースに対してプログラムせよ。
    2. クラスの継承より、オブジェクトの合成を優先せよ。（Favor object composition over class inheritance.）
    継承（クラスの継承）合成（オブジェクトの合成）
    関係「〜である」（is-a）「〜を持つ」（has-a）
    決まるタイミングコンパイル時（クラス定義で固定）実行時（どのオブジェクトを持たせるか変えられる）
    中身の見え方親の 実装の詳細 が子に見える（ホワイトボックス再利用）相手の インターフェースだけ が見える（ブラックボックス再利用）
    結合の強さ最も強い結合弱い結合

    GoF の23パターンの多くは、継承の代わりに合成を使って柔軟性を得る方法 として読むことができます（GoFパターンの概要）。

    3.脆い基底クラス問題（Fragile Base Class）

    3.1 何が起きるか

    脆い基底クラス問題

    基底クラス（親）の、一見安全な変更が、子クラスを壊してしまう問題。

    class CountingSet<T> extends Set<T> {
  count = 0;

  add(value: T) {
    this.count++;
    return super.add(value);
  }

  addAll(values: T[]) {
    this.count += values.length;
    values.forEach((v) => super.add(v));
  }
}

    もし親クラスの実装が「addAll の中で add を呼ぶ」ように変わったら？

    • addAll で count が二重に増える（addAll で +n、中で呼ばれる add でさらに +n）
    • 親クラスの 公開インターフェースは何も変わっていない のに、子クラスが壊れる
    • 子クラスは、親の 内部実装（どのメソッドがどのメソッドを呼ぶか） に依存していた

    これは Joshua Bloch『Effective Java』の有名な例（InstrumentedHashSet）を TypeScript で書き直したものです。

    3.2 なぜ起きるか

    • 子クラスは親クラスの 実装の詳細 に依存している（カプセル化 が破れている）
    • 親クラスの作者は、どんな子クラスが作られているか知らない
    • 継承の階層が深いほど、祖父母クラスの変更が孫クラスを壊す 可能性が高まる

    43章の 統合強度 の言葉でいえば、継承は相手の内部実装を共有する 侵入的結合 に近い、最も強い結合です。

    3.3 その他の継承の問題

    問題説明
    組み合わせ爆発「音声通知・メール通知」×「即時・まとめて」×「ログあり・なし」を継承で表すと、クラスが掛け算で増える
    不要な機能の継承親のメソッドを子が使わない・使えない（Fowler の臭い 相続拒否（Refused Bequest））。LSP 違反につながる
    ヨーヨー問題処理を追うために、継承階層を上へ下へと何度も行き来する（→ アンチパターンの見分け方）
    単一継承の制約多くの言語は親を1つしか持てない。2つの性質を同時に継承できない
    実行時に変えられない一度作ったオブジェクトの振る舞いを、後から変えられない

    3.4 例：画像ライブラリで見る継承の落とし穴

    動画メモ（直也テック）では、画像ライブラリを例に、継承がどこで破綻するかを説明しています。継承とコンポジションはどちらも「書いたコードを再利用する」ための道具です。

    1. Image クラスに Resize・FlipHorizontal・FlipVertical を持たせ、抽象メソッド Save / Load を追加する。JPEGImage・PNGImage・BMPImage がそれぞれ Save / Load だけを実装すれば、他の処理はタダで再利用できる
    2. ここに「ファイル由来でない、ユーザーが描ける DrawableImage」という要望が来ると破綻する。親の構造がそのまま押し付けられ、意味のない Save / Load を実装して例外を投げるしかない
    3. 回避するには親を組み替える（Image から Save / Load を外し、間に FileImage を挟む）必要があり、Image が保存できる前提のコードがすべて壊れる

    継承は 共通点を親に集める ので、例外が1つ見つかるだけで大規模な再設計になります。話者は「変更が必要になった瞬間に継承は破綻し、変更されないコードは存在しない」と述べ、正規化しすぎた DB スキーマがデータ増加でつまずくのに似ている（NoSQL が重複を許す方向に寄った理由と同じ、と話者は考えている）とたとえています。

    4.継承を合成に置き換える技法

    4.1 委譲（Delegation）

    親クラスを継承する代わりに、そのオブジェクトをフィールドに持ち、処理を任せる 方法です。

    ◯ 委譲：Set を「持つ」。必要なメソッドだけを公開する 
    class CountingSet<T> {
  private readonly inner = new Set<T>();
  count = 0;

  add(value: T): this {
    this.count++;
    this.inner.add(value);
    return this;
  }

  addAll(values: T[]): this {
    values.forEach((v) => this.add(v));
    return this;
  }

  has(value: T): boolean {
    return this.inner.has(value);
  }
}
    • Set の内部実装がどう変わっても、CountingSet は影響を受けない（公開メソッドだけを使っている）
    • 公開するメソッドを 自分で選べる（不要なメソッドを継承しない）
    • Fowler のリファクタリング Replace Superclass with Delegate（スーパークラスを委譲に置き換える）にあたります

    4.2 Strategy で振る舞いを差し替える

    継承で振る舞いのバリエーションを作る代わりに、振る舞いをオブジェクトとして渡す 方法です。

    ✕ 継承：割引の種類ごとにサブクラス 
    class Order { calcTotal() { ... } }
class MemberOrder extends Order { calcTotal() { /* 会員割引 */ } }
class CampaignOrder extends Order { calcTotal() { /* キャンペーン割引 */ } }
// 会員かつキャンペーン中は？ → MemberCampaignOrder…（組み合わせ爆発）
    ◯ 合成：割引を差し替え可能な部品にする 
    interface DiscountPolicy {
  apply(subtotal: Money): Money;
}

class Order {
  constructor(private readonly discounts: DiscountPolicy[]) {}
  calcTotal(): Money {
    return this.discounts.reduce((total, d) => d.apply(total), this.subtotal());
  }
}

new Order([new MemberDiscount(), new CampaignDiscount()]);  // 組み合わせ自由

    詳しくは 振る舞いパターン の Strategy を参照してください。

    4.3 Decorator で機能を重ねる

    継承で機能を追加する代わりに、同じインターフェースを持つオブジェクトで包む 方法です。

    interface Notifier { send(message: string): Promise<void>; }

class EmailNotifier implements Notifier { async send(m: string) { /* メール送信 */ } }

class LoggingNotifier implements Notifier {
  constructor(private readonly inner: Notifier) {}
  async send(m: string) {
    console.log("送信:", m);
    await this.inner.send(m);
  }
}

class RetryingNotifier implements Notifier {
  constructor(private readonly inner: Notifier, private readonly times: number) {}
  async send(m: string) { /* 失敗したら times 回まで this.inner.send を再試行 */ }
}

// 機能を自由に重ねられる
const notifier = new LoggingNotifier(new RetryingNotifier(new EmailNotifier(), 3));
    • 「ログ付き」「リトライ付き」を継承で作ると、LoggingRetryingEmailNotifier のような組み合わせクラスが必要になる
    • Decorator なら、部品を積み重ねるだけ（→ 構造パターン）

    4.4 インターフェースで「型としての共通性」を表す

    継承を使う理由が「同じ型として扱いたい（多態）」だけなら、インターフェース で十分です。

    interface Shape { area(): number; }

class Circle implements Shape { constructor(private r: number) {} area() { return Math.PI * this.r ** 2; } }
class Rect implements Shape { constructor(private w: number, private h: number) {} area() { return this.w * this.h; } }

const shapes: Shape[] = [new Circle(1), new Rect(2, 3)];
    • 実装を共有しないので、脆い基底クラス問題が起きない
    • 1つのクラスが 複数のインターフェース を実装できる

    継承の2つの目的を分ける

    継承には「型の共有（多態のため）」と「実装の共有（コード再利用のため）」の2つの目的が混ざっています。型の共有はインターフェースで、実装の共有は合成で 分けて行うのが、現代的なクラス設計の基本です。

    4.5 例：画像ライブラリをコンポジションで書き直す

    動画メモでは、3.4 の画像ライブラリを次のように書き直しています。「機能を共有したいなら、その機能を 使えばいい」— 継承を使わない再利用で、実は普段からやっていることです。

    • Image はメモリ上の画像を表すだけの単純なクラスにし、JPEG / PNG / BMP クラスは Image を継承しない。this で親をたどる代わりに、対象の画像を 引数で受け取る
    • 描画の要望には、画像を受け取る ImageDraw クラスを追加するだけ。他のクラスに一切触れずに済む
    • 使い方も「目的に合う1クラスを選ぶ」から「複数のクラスを組み合わせる」に変わる（JPEG を読み→描画→保存、BMP を読み→反転→リサイズして書き出し など）

    継承は「コードの再利用」と「抽象化」の2つの能力を1つにまとめています。抽象化とは、相手が具体的に何かを知らずに使える状態で、双方が守る取り決めを 契約（contract） と呼びます。

    • 継承版では、アプリは親クラスの参照で画像を持ち、ファイル形式を気にせず save を呼べた（親のメソッドが契約になっていた）
    • コンポジション版で同じことをするには インターフェース を使う。変数もメソッド本体も持たず、契約だけを定義する。例：save / load を持つ ImageFile インターフェースを各形式が実装
    • 親クラスはすべてを共有するので変えにくいが、インターフェースは必要な契約だけなので、既存クラスにも後から付けやすい
    • どの ImageFile を生成するかの判断をアプリの外に出し、使う側から渡してもらう → これが 依存性注入（Dependency Injection）。「大げさな名前だが、やっていることはそれだけ」
    • 話者は「継承が悪いとまでは言わないが、ほぼ使わなくなった」と述べています

    インターフェースと DI のクラス設計での使い方は インターフェースと抽象化 で扱っています。

    5.それでも継承を使ってよい場面

    「継承は絶対に使うな」ではありません。次の条件がそろうときは、継承が自然な選択です。

    条件説明
    本当に is-a である子クラスは、あらゆる場面で親クラスの代わりに使える（リスコフの置換原則を満たす → リスコフの置換原則）
    親クラスが継承のために設計されている抽象クラスで、オーバーライドしてよいメソッドが明確に決まっている（Template Method パターン）
    同じ作者・同じモジュールで管理されている親の変更が子に与える影響を、作者自身が把握できる
    階層が浅い1〜2段まで。深い階層は避ける
    フレームワークが要求するUI フレームワークの基底クラス、例外クラス（class NotFoundError extends Error）など

    Joshua Bloch は『Effective Java』で、「継承のために設計して文書化せよ。さもなければ継承を禁止せよ」 と述べています。他人が作った具体的なクラスを継承するのは、最も危険なパターンです。

    5.1 動画メモ：コンポジションの弱点と、継承が役立つ場面

    • コンポジションも完璧ではありません。内部部品を初期化する ボイラープレート（毎回同じように書く定型コード）が増え、中身を呼ぶだけのラッパーメソッドが量産されがちです。それでもオブジェクト同士の 接触面 が小さくなり、変更時の痛みが減ります
    • 継承が有効なのは、重複だらけの巨大レガシーで1箇所だけ直したいときです（例：インターフェースに従う100クラスの半分が同じロジックを繰り返している。作り直しにはチームで数か月かかる）
    • 継承を使うなら 継承されることを前提に設計 します。フィールドを protected にしない（public にしないのと同じ理由）、オーバーライド用には明示的な protected API だけを用意し、それ以外は private / final / sealed（それ以上継承・上書きできなくする指定）にする。これで親を変えたときのバグを防げます

    6.判断のフローチャート

    「なぜ継承したいのか」から出発して、使う技法を選びます。

    7.よくある誤解

    誤解1：「継承はコード再利用のための仕組み」

    半分だけ正しいです。 コード再利用だけが目的なら、委譲の方が安全です。継承の本来の価値は 「親の代わりに使える型を作る」（多態）ことにあります。

    誤解2：「合成にするとコードが増える」

    多少は増えます。 委譲では、使いたいメソッドを自分で書く必要があります。しかしその代わりに、親の変更に壊されない安全性 と、公開するものを選べる柔軟性 が得られます。

    誤解3：「抽象クラスを継承するなら安全」

    常にではありません。 抽象クラスでも、子クラスが親の実装の詳細に依存していれば、脆い基底クラス問題は起きます。オーバーライドしてよい場所が明確に決められていることが重要です。

    誤解4：「継承より合成＝継承は使ってはいけない」

    ノートも動画も「継承は絶対に使うな」とは言っていません。本当に is-a で LSP を満たし、継承のために設計された親で、階層が浅いとき（フレームワークの要求や巨大レガシーの手当てを含む）は、継承が自然な選択になります。

    8.まとめ

    • GoF の原則：インターフェースに対してプログラムせよ、継承より合成を優先せよ
    • 継承は 最も強い結合。脆い基底クラス問題（親の安全そうな変更が子を壊す）、組み合わせ爆発、相続拒否などを生む
    • 置き換えの技法：委譲（持って任せる）、Strategy（振る舞いを差し替える）、Decorator（機能を重ねる）、インターフェース（型だけを共有する）
    • 型の共有はインターフェースで、実装の共有は合成で 分ける
    • 継承を使ってよいのは、本当に is-a・LSP を満たす・継承用に設計された親・浅い階層 のとき
    • 動画メモの結論：継承とコンポジションは同じ問題（コード再利用）のための道具。抽象化はインターフェースで、生成の判断は外から注入（DI）すれば、継承なしで同じことができる。変更に強い設計はコンポジションから始め、継承は「継承される前提の設計」で必要なときだけ使う

    次は、SOLID の適用として 単一責任の原則 に進みます。
