    20 責務の割り当て

    クラス分割の基本プロセス — 要件から最初のクラス設計案を作る

    要件の文章から「名詞」を拾ってクラス候補にし、「動詞」を振る舞いとして置き場所を決める。この基本の手順と、データクラス・貧血モデルの問題、分割しすぎ・分割不足の見分け方、1時間でできるワークショップを解説します。

    もとにしたノート：20_責務の割り当て/01_クラス分割の基本プロセス

    ひとことで言うと

    要件の 名詞からクラス候補、動詞から振る舞い（メソッド） を見つけ、振る舞いは その情報を持つクラス に置きます。データと振る舞いを同じクラスにまとめ、分け方の良し悪しは 変化の理由 と 凝集度 で判断します。

    1.このページで扱うこと

    要件から クラス候補を見つけ、振る舞いを配置し、最初の設計案を作る 手順を学びます。あわせて、データクラス・貧血モデルの問題と、分割の過不足の見分け方も押さえます。

    • 名詞の抽出：要件文からクラス候補を拾う
    • 動詞の配置：振る舞いをどのクラスに置くか
    • データクラスと貧血モデル：なぜ問題なのか
    • 分割しすぎ・分割不足：症状と対策
    • ワークショップ：最初のクラス設計案を作る6ステップ

    2.要件から名詞（クラス候補）を抽出する

    ユースケース（利用者がシステムを使って達成したい一連のやり取り）や要件文から 名詞 を拾い、クラス候補にします。

    顧客が 商品 を カート に入れ、注文 を確定する。
    在庫 を確認し、配送先 に届ける。

    名詞クラス候補備考
    顧客Customerエンティティ
    商品Productエンティティ
    カートShoppingCart集約の候補
    注文Order集約の候補
    配送先Address値オブジェクト候補

    備考の エンティティ（ID で区別されるもの）・値オブジェクト（値で比較する不変のもの）・集約（整合性を保つクラスのまとまり）は、ドメインを表すクラス で詳しく扱います。

    すべての名詞がクラスになるわけではありません。振る舞いと状態を持つもの を優先します。

    3.動詞（振る舞い）をどのクラスに置くか

    動詞 はメソッド候補です。情報を持つクラス に置くのが基本です（GRASP の Information Expert）。

    動詞置き場所理由
    カートに入れるShoppingCartカートが明細を持つ
    合計を計算するOrder注文が明細を持つ
    在庫を引くInventory または Product在庫データの所在
     
    class ShoppingCart {
  add(product, quantity) { /* カートが自分の明細を更新 */ }
}

    「サービスに全部書く」のではなく、データと振る舞いの一体化 を意識します（詳しくは 業務ロジックをデータと一体にする）。

    4.データクラスと貧血モデルの問題

    データクラス は、フィールドと getter/setter（値を読み書きするだけのメソッド）だけのクラスです。
    貧血モデル は、ドメインロジック（業務のルール）がサービス層に偏り、エンティティがデータの入れ物になっている状態です。

    ✕ 貧血モデル — Order はデータだけ 
    // 貧血モデル — Order はデータだけ
class Order {
  get lines() { return this._lines; }
}
class OrderService {
  calculateTotal(order) { /* ロジックはここ */ }
}
    問題対策
    ロジックが散在ドメインルールをエンティティへ
    重複振る舞いを1か所に
    テストがサービス依存小さな単位でテスト可能に

    エンティティと値オブジェクトの考え方は 42章：エンティティと値オブジェクト も参照してください。貧血モデルの避け方は Tell, Don't Ask と貧血モデル で掘り下げます。

    5.分割しすぎ・分割不足の見分け方

    症状診断対策
    1 変更で10ファイル分割しすぎ関連クラスをまとめる
    1 クラスが数千行分割不足SRP で分割
    名前が Helper だらけ責務不明ドメイン語で命名
    常に3クラスセットで動く過剰分割集約・1クラスに統合検討

    SRP（単一責任の原則：クラスを変更する理由は1つにする。単一責任の原則）が分割不足の対策になります。

    変化の理由 と 凝集度（クラスの中身がどれだけ1つの目的にまとまっているか。凝集度と結合度）を物差しにします。

    6.最初のクラス設計案を作るワークショップ

    1. 要件を3行で要約 する
    2. 名詞リスト を作り、候補を10個以内に絞る
    3. 主要ユースケース1つ を選び、動詞を配置する
    4. クラス図をスケッチ（完璧不要）
    5. 「ここが変わりそう」 をマークし、境界を確認
    6. ペアで説明 — 説明できなければ責務が曖昧

    時間配分の目安は次のとおりです（合計1時間）。

      15分: 名詞抽出
  15分: 動詞配置
  15分: 図スケッチ
  15分: レビュー

    動詞の置き場所に迷ったときの詳しい判断は GRASP へ進みます。

    7.よくある誤解

    誤解1：「要件に出てきた名詞はすべてクラスにする」

    名詞はあくまで 候補 です。すべての名詞がクラスになるわけではなく、振る舞いと状態を持つもの を優先します。ワークショップでも候補は10個以内に絞ります。

    誤解2：「ロジックはサービスクラスにまとめておけば整理される」

    サービスに全部書くと、エンティティがデータの入れ物になる 貧血モデル になり、ロジックの散在・重複・テストのしにくさにつながります。振る舞いは、その情報を持つクラスに置きます。

    誤解3：「クラスは細かく分けるほどよい」

    1つの変更で10ファイルを触る、常に3クラスがセットで動く、といった状態は分割しすぎです。分けるかどうかは、クラスの大きさではなく 変化の理由 と 凝集度 で判断します。

    8.まとめ

    • 名詞からクラス候補、動詞から振る舞いの配置
    • データと振る舞いは同じクラスに（貧血モデルを避ける）
    • 分割は変化の理由と凝集度で判断
    • 短いワークショップで最初の設計案を作れる

    次は、責務の置き場所を決める指針 GRASP に進みます。
