    00 全体像

    メソッド設計の全体像 — 1つの関数をどう切り出し、どんな形にし、中身をどう書くか

    メソッド設計とは何を扱う分野なのか、46章がどの本を骨格にしているのか、フォルダがどんな問いごとに分かれているのか、どの順に読めばよいのか、そして隣の章（原則・クラス設計・モジュール設計・API設計など）とどう分担しているのかをまとめた、46章の入口ページです。各ページへ進む前に、ここで全体の地図を持っておきましょう。

    もとにしたノート：MOC_メソッド設計体系

    ひとことで言うと

    メソッド設計は、1つの関数・メソッドを「どう切り出し、どんな形にし、中身をどう書くか」 を決める、いちばん小さな単位の設計 です。46章は、メソッドを 責務 → シグネチャ → 本体 → 副作用 → 契約とエラー という構成要素に分け、フォルダごとに1つの問いに答える形で並べています。

    1.このページで扱うこと

    目次が「どこに何があるか」の一覧、メソッド設計の変遷が「どう発展してきたか」の歴史だとすれば、このページは 「46章全体の地図」 です。読み終えたときに、次の問いに答えられることを目標にします。

    1. メソッド設計とは何か、46章はどの本を骨格にしているのか
    2. フォルダ構成。どのフォルダが、どんな問いに答えているのか
    3. 読む順。教材（全25章）を学ぶ順番と、歴史順で読む方法
    4. 他の章との分担。原則の一般論やクラス・モジュールの話はどこにあるのか
    5. 各ページへの入口。フォルダごとのページ一覧

    2.メソッド設計とは何か

    2.1 いちばん小さな単位の設計

    46章は、1つの関数・メソッドを「どう切り出し、どんな形にし、中身をどう書くか」 を扱います。メソッド はクラスに属する関数のことで、設計上の論点は普通の関数とほぼ同じです（詳しくは 関数とメソッドの基本）。

    アーキテクチャ（41章）・モジュール（43章）・クラス（44章）よりもさらに内側、実際に処理が書かれる場所 の設計です。上の階層の設計がどれだけ良くても、中のメソッドが 500 行あれば読めません。

    2.2 骨格になっている本

    46章は、次の本を骨格にし、そこに別の本の視点を加える構成にしています。

    役割本46章で使っている内容
    骨格McConnell『Code Complete』第7章「高品質なルーチン」ルーチン（関数）を作る理由 → 凝集 → 名前 → 長さ → 引数、という流れ
    Martin『Clean Code』第3章「関数」小さく・少ない引数・意図が伝わる名前などの関数ルール
    加える視点Ousterhout『A Philosophy of Software Design』深いメソッド、エラーが起きない設計
    Fowler『Refactoring』第2版Extract Method などのリファクタリング技法
    Normand『Grokking Simplicity』アクション／計算／データの3分類

    リファクタリング とは、外から見た動きを変えずに、コードの中身を読みやすく整えることです。

    3.フォルダ構成 — 構成要素ごとに1つの問い

    3.1 フォルダと問いの一覧

    フォルダは メソッドの構成要素別（責務 → シグネチャ → 本体 → 副作用 → 契約とエラー）に分かれています。シグネチャ とは、メソッドの名前・引数・戻り値の型など「外から見える形」のことです。各フォルダは、メソッドについての1つの問いに答えます。

    フォルダ役割問い
    00 全体像このページ・年表（メソッド設計の変遷）・教材の目次と前書き—
    10 メソッドの基礎なぜ学ぶか ／ 関数とメソッド・入力・出力・副作用の基本メソッドとは何か
    20 責務と分割どこで切るか ／ 1メソッド1責任 ／ KISS・DRY・YAGNI ／ Extract Method何を1つにまとめるか
    30 シグネチャ設計名前 ／ 引数 ／ 戻り値と情報隠蔽外からどう見えるか
    40 本体の書き方サイズと抽象度 ／ Guard Clause ／ 複雑度と分岐中身をどう読ませるか
    50 副作用と状態CQS ／ 純粋関数 ／ FCIS ／ オブジェクトのメソッド何を変えるか
    60 契約とエラー事前・事後条件（DbC）／ Fail Fast ／ エラー処理失敗をどう扱うか
    70 品質と運用テスト ／ リファクタリング ／ レビュー ／ チームで守る品質をどう保つか
    80 ケーススタディ総合演習—
    90 付録用語集・チェックリスト・早見表・アンチパターン・図解・推奨図書—

    表に出てくる略語は、それぞれのページで詳しく説明します。CQS は「読む操作と書く操作を分ける」原則、FCIS（Functional Core, Imperative Shell）は「計算は純粋な関数に、入出力は外側に」という構成、DbC（Design by Contract）は「メソッドの前提と保証を契約として明示する」考え方です。

    3.2 図で見るフォルダの関係

    3.3 ノートの並べ方のルール

    もとになっている Obsidian ノートには、次の運用ルールがあります。解説ページのファイル名（20-1_… など）もこの順番に合わせています。

    • ファイル名は各フォルダ内で 読む順に 01_ から連番。見出しには教材の章番号（第N章）を書かず、節番号は N.M → M. にした
    • 教材の元の章立て（第1〜25章）は、教材の目次ノートと下の 学習順インデックス にだけ残す
    • 各章末の「次の章」リンクは、新しいフォルダ順（10 → 20 → … → 80）でつないである
    • 目次 ／ 00_はじめに ／ 付録X は 42〜45 にも同じ名前のノートがある。リンクするときはフルパスで書く

    3.4 この話はどのフォルダ？（新しいノートの置き場所）

    メソッドについての話題がどのフォルダに入るかは、「何を決める話か」 で判断します。ページを探すときの手がかりにもなります。

    何を決める話か置き場所
    どこで切る・何をまとめる20 責務と分割
    名前・引数・戻り値30 シグネチャ設計
    長さ・ネスト・条件分岐40 本体の書き方
    状態変更・I/O・純粋さ50 副作用と状態
    前提条件・例外・null60 契約とエラー
    テスト・リファクタ・レビュー70 品質と運用
    メソッドの外の話下の 「本拠地」の表 へ

    I/O は入出力（ファイル・データベース・ネットワークなどとのやり取り）、純粋さ は「同じ入力なら必ず同じ出力を返し、外の状態を変えない」性質のことです。

    4.どの順に読むか

    4.1 学習順インデックス（教材 全25章）

    フォルダは構成要素別ですが、もとになった教材（旧 第01〜08部・全25章）は別の順番で書かれています。教材の順に読みたい場合は、次の表の順にページをたどってください。「置き場」はそのページがあるフォルダです。

    部章（ページ）置き場
    前書き教材の前書き（00_はじめに）／ 目次00
    第1部 はじめにメソッド設計を学ぶ理由 → 関数とメソッドの基本10
    第2部 設計の土台メソッドの分割 → 関心の分離と単一責任 → KISS・DRY・YAGNI20
    第3部 メソッドの切り方Extract Method → 情報隠蔽 → 引数の設計20 ／ 30
    第4部 制御の書き方Guard Clause → Design by Contract → 複雑度と分岐40 ／ 60
    第5部 振る舞いの設計CQS → 純粋関数と副作用 → オブジェクトのメソッド → Functional Core, Imperative Shell50
    第6部 読みやすいメソッド命名 → サイズと抽象度 → エラー処理30 ／ 40 ／ 60
    第7部 品質を保つための実践テストしやすいメソッド設計 → リファクタリングの実践 → コードレビューで見るポイント70
    第8部 チーム開発と演習チームでメソッド設計を守る → ケーススタディ（注文処理フロー → 計算・バリデーション）→ 設計レビューの実践70 ／ 80

    4.2 歴史順に読みたい場合

    歴史順で学ぶなら

    メソッド設計の変遷 が、goto の時代 → 構造化 → オブジェクト指向（OOP）→ 関数型 と、考え方が登場した順に並べた年表になっています。「なぜこの技法が生まれたのか」を知りたいときに向いています。

    5.他の章との分担（本拠地の表）

    メソッド設計は、原則・クラス設計・モジュール設計などと話題が重なります。46章では 「メソッド単位でどう使うか」 に絞り、テーマそのものの一般論は次の章（本拠地）に任せています。

    テーマ本拠地
    KISS・DRY・YAGNI・SRP などの原則そのもの48_原則（46 では「メソッド単位での使い方」だけ）
    クラスの責務・カプセル化・GoF44 クラス設計・デザインパターン
    モジュール・パッケージ単位の分割43 モジュール設計
    パラダイム（手続き・OOP・関数型）の一般論42 ソフトウェア設計 の「20 パラダイム」
    Web API のインターフェース設計45 API設計
    命名・フォーマットのチーム規約59_AI開発ツール・コーディング規約 の「コーディング規約」
    テスト戦略・テスト設計技法81_テスト戦略 ／ 87_テスト設計技法

    GoF は『デザインパターン』の著者4人（Gang of Four）のことで、その本にある23のパターンを指します。SRP（単一責任の原則）は「1つのものは1つの理由でだけ変わるべき」という原則です。

    7.よくある誤解

    誤解1：「フォルダの番号順に読まないといけない」

    フォルダは メソッドの構成要素別 に並んでいて、調べたいテーマを探すのに向いています。初めて通して学ぶなら 学習順インデックス（教材の順）、なぜその技法が生まれたかを知りたいなら メソッド設計の変遷（歴史順）と、目的に合わせて読み方を選べます。

    誤解2：「SRP や DRY などの原則は、46章ですべて学べる」

    46章で扱うのは、原則を メソッド単位でどう使うか だけです。原則そのものの一般論は 48_原則、クラスの責務やカプセル化は 44章 が本拠地です（本拠地の表）。

    誤解3：「メソッド設計は細かい話なので、クラスやモジュールの設計が良ければ後回しでよい」

    上の階層がどれだけ整っていても、実際に処理が書かれるのはメソッドの中です。中のメソッドが巨大だったり副作用だらけだったりすると、コードは読めず、テストも変更も難しくなります。理由は メソッド設計を学ぶ理由 で詳しく説明します。

    8.まとめ

    • メソッド設計は、1つの関数・メソッドをどう切り出し、どんな形にし、中身をどう書くか を扱う、いちばん小さな単位の設計
    • 骨格は『Code Complete』第7章と『Clean Code』第3章。Ousterhout・Fowler・Normand の視点を加えている
    • フォルダは構成要素別（責務 → シグネチャ → 本体 → 副作用 → 契約とエラー）で、それぞれ1つの問いに答える
    • 教材の順に読むなら学習順インデックス、歴史順なら メソッド設計の変遷
    • 原則・クラス・モジュール・パラダイム・Web API・規約・テスト戦略の一般論は、それぞれの本拠地の章に任せている
