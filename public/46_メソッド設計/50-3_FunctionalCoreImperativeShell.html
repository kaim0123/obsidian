    50 副作用と状態

    Functional Core, Imperative Shell — 核は純粋に、外縁だけで I/O する

    前のページでは、副作用を境界に押し出すと関数がテストしやすくなることを学びました。このページでは、それをプログラム全体の形にした FCIS（Functional Core, Imperative Shell） を学びます。Core と Shell の境界の決め方、ユースケース層での実践、OOP のメソッドと FP の関数の役割分担、そして小さなアプリで過剰にならないための目安を解説します。

    もとにしたノート：03_Functional_Core_Imperative_Shell

    ひとことで言うと

    核（Core）は純粋関数 で計算・変換・バリデーションを行い、外縁（Shell）だけ が DB・HTTP・ログなどの I/O を行う、という分け方です。Shell が「読む → Core に渡す → 結果を書く」だけになるよう 薄く 保つと、Core をモックなしでテストできます。ただし小さなスクリプトでは不要で、規模に応じて使います。

    1.このページで扱うこと

    このページは、FCIS（Functional Core, Imperative Shell） — 核を純粋関数、外縁を I/O に分けるパターンを学ぶページです。

    • 核は純粋、外縁だけ I/O という基本の形
    • Shell（副作用あり）と Core（純粋関数）の境界の決め方
    • ユースケース層での実践
    • OOP のメソッドと FP の関数の役割分担
    • 小さなアプリでは過剰にならないか（KISS とのバランス）

    純粋関数と副作用の基本は 純粋関数と副作用 を先に読んでください。FP は関数型プログラミング（Functional Programming）、OOP はオブジェクト指向プログラミングの略です。

    2.核は純粋、外縁だけ I/O

    Functional Core, Imperative Shell とは、プログラムを次の2つに分ける考え方です。

    • Core（核）：純粋関数 — 計算・変換・バリデーション
    • Shell（外縁）：副作用 — I/O、DB、HTTP、ログ

    「Imperative（命令型）」は、「これをして、次にあれをする」と手順を順に書くスタイルのことです。外縁は手順どおりに外の世界とやり取りするので、こう呼ばれます。

    核を テストしやすく、Shell を 薄く 保ちます。

    3.Shell（副作用あり）と Core（純粋関数）の境界

    境界の決め方 は、次の3段階です。

    1. 入力 — Shell が DB から取得し、Core に渡す
    2. Core — 純粋関数で計算・判定する
    3. 出力 — Shell が Core の結果を DB / API に書き込む
    ◯ Core：純粋 
    function processOrderData(order, items) {
  const total = calculateTotal(items);
  const discount = applyDiscount(total, order.coupon);
  return { ...order, total, discount, status: 'processed' };
}
    ◯ Shell：I/O 
    async function handleOrderRequest(req) {
  const order = await db.getOrder(req.id);
  const items = await db.getItems(req.id);
  const result = processOrderData(order, items);
  await db.save(result);
  return result;
}

    Core の processOrderData は、DB を一切知りません。受け取った order と items から新しいオブジェクトを作って返すだけです。DB とのやり取りは Shell の handleOrderRequest が最初と最後にまとめて行います。

    4.ユースケース層での実践

    アプリケーションサービス（ユースケース層。「注文する」のような1つの利用場面の手順を組み立てる層）を Shell として設計します。

    class PlaceOrderUseCase {
  async execute(command) {
    const order = await this.repo.find(command.orderId);   // Shell
    const validated = validateOrder(order);                 // Core
    const total = calculateTotal(validated.items);          // Core
    await this.repo.save({ ...validated, total });          // Shell
    await this.notifier.send(validated);                    // Shell
  }
}

    Core 部分（validateOrder・calculateTotal）は モックなし で単体テストできます。モック とは、テストのために DB や外部サービスの代わりをする偽物のオブジェクトのことです。ユースケース層の位置づけは 42章：ドメイン層とユースケース も参考になります。

    5.OOP のメソッドと FP の関数の役割分担

    レイヤー向くパラダイム例
    ドメイン計算純粋関数calculateTax(), applyDiscount()
    エンティティOOP メソッドorder.submit()
    ユースケースShell（手続き）PlaceOrderUseCase.execute()

    エンティティ は、ID で区別され、状態が変わっていく業務上のもの（注文・会員など）です。組み合わせ が現実的です。OOP で状態を表現し、FP で計算を純粋にします。エンティティのメソッドの書き方は オブジェクトのメソッド で扱います。

    6.小さなアプリでは過剰にならないか（KISS とのバランス）

    規模推奨
    スクリプト・100 行FCIS は不要。関数分割だけで十分
    中規模・複数レイヤーCore / Shell の意識を持つ
    大規模・ドメイン複雑FCIS を明示的にレイヤー分け

    過剰設計のサイン

    Shell が1行だけ、Core が1関数だけ — このときは統合を検討します（→ KISS・DRY・YAGNI）。KISS は「シンプルに保て（Keep It Simple, Stupid）」という原則です。

    7.よくある誤解

    誤解1：「FCIS はどんなコードにも必ず適用すべき」

    違います。 100 行程度のスクリプトでは関数分割だけで十分です。Shell が1行・Core が1関数しかないような分け方は、かえって読みにくくします。規模とドメインの複雑さに応じて使います。

    誤解2：「FCIS を使うなら OOP はやめて関数だけで書く」

    違います。 エンティティの状態は OOP のメソッドで表し、計算は純粋関数に、ユースケースは Shell に、という 組み合わせ が現実的です。

    誤解3：「Shell にもロジックをたくさん書いてよい」

    Shell は薄く保ちます。 Shell に判断や計算が増えると、その部分はモックを使わないとテストできなくなります。判断・計算は Core に移し、Shell は「読む → Core を呼ぶ → 書く」だけにします。

    8.まとめ

    • FCIS ＝ 核は純粋、外縁だけ I/O
    • Shell が入出力、Core が計算・判定
    • ユースケース層を Shell として 薄く 保つ。Core はモックなしでテストできる
    • OOP で状態を、FP で計算を — 組み合わせが現実的
    • 小規模では KISS を優先。規模に応じて適用する
