    リファクタリングの実践 — 振る舞いを変えずに、小さく安全に直す

    これまでのページで学んだメソッド設計の考え方を、既存のコードに当てはめていくのがリファクタリングです。このページでは、いつリファクタリングするか、メソッド設計で頻出の3つの技法、200行の巨大関数を段階的に直す手順、そして技術的負債との向き合い方と安全網の張り方を学びます。

    もとにしたノート：02_リファクタリングの実践

    ひとことで言うと

    リファクタリング とは、外から見た振る舞いを変えずに内部構造を改善することです。基本の技法は Extract Method / Introduce Parameter Object / Replace Conditional with Polymorphism の3つ。巨大関数は一度に直さず、まずテストを1つ書き、小さなステップとコミットで少しずつ進めます。

    2.いつリファクタリングするか

    Martin Fowler の 「ルールオブスリー」（同じことを3回やったらリファクタリングする、という目安）などを参考に、次のタイミングが適切です。

    タイミング例
    3 回目の重複同じロジックを 3 回書いた
    機能追加の前触る前に読みやすくする
    バグ修正の後構造が原因なら直す
    レビュー指摘分割・命名の改善

    避けること

    リリース直前の大規模リファクタ、テストなしでの一括変更。

    3.Extract Method / Introduce Parameter Object / Replace Conditional

    メソッド設計で頻出の 3 技法 です。

    技法用途
    Extract Method長い関数・意味の塊を切り出す（Extract Method）
    Introduce Parameter Object引数 3 個以上をオブジェクト化（引数の設計）
    Replace Conditional with Polymorphism分岐をポリモーフィズムに（複雑度と分岐）

    ポリモーフィズム（多態）とは、同じ呼び出し方で、相手の種類に応じて違う処理が動く仕組みです。

    // Replace Conditional の例
// Before: switch (type) { case 'A': ... case 'B': ... }
// After: calculators[type].calculate(data)

    早見表は ルール早見表とリファクタリング技法 を参照してください。

    4.レガシー関数への段階的適用

    200 行の神関数（何でも抱え込んだ巨大な関数）を一度に直さない — 小さく・安全に 進めます。

    1. テストを 1 つ 書く（特性テストでも可）
    2. Guard Clause で異常系を先に抽出
    3. Extract Method で 1 ブロックずつ切り出す
    4. 各ステップで テストが通る ことを確認
    5. 切り出した関数に 名前 を付け、責任を明確化

    特性テスト（Characterization Test）は、「正しい仕様」ではなく「今のコードが実際に返す結果」を記録して固定するテストです。仕様が分からない古いコードでも、変更前後で振る舞いが変わっていないことを確かめられます。

    進め方の例：

    時期作業
    Week 1テスト追加 ＋ Guard Clause
    Week 2検証部分を extract
    Week 3計算部分を extract
    ……

    5.振る舞いを変えずに構造を変える

    リファクタリングの 定義（Fowler）：

    外部から見た振る舞いを変えずに、内部構造を改善すること

    許容不可
    関数の分割・統合仕様変更
    名前の変更バグ修正（別作業）
    引数の整理新機能追加

    小さなコミット ＋ テスト で安全網を張ります。

    6.技術的負債との向き合い方

    技術的負債 とは、今は動くが後で手間（利子）がかかる状態のコードのことです。

    方針説明
    可視化複雑度・行数で負債リストを作る
    優先付け変更頻度の高い関数から
    Boy Scout Rule触ったファイルは少しきれいに
    諦めない全部直す必要はない。重要な所から

    Boy Scout Rule（ボーイスカウト・ルール）は「来たときよりもきれいにして帰る」という、ボーイスカウトの心得から取った習慣です。

    歴史的な整理は メソッド設計の変遷 を参照してください。チームでの運用は チームでメソッド設計を守る で扱います。アーキテクチャ全体での負債の扱いは 41章：技術的負債 にもあります。

    7.安全網 — リファクタ前の最低限

    手段内容
    特性テスト既存出力を記録し、リファクタ後も一致を確認
    スナップショットJSON 出力等を固定
    カバレッジ触る関数の行カバレッジ 80% 以上を目標
    小さな PR1 PR ＝ 1 技法、200 行 diff 以内

    カバレッジ は、テストを実行したときにコードの何割の行が実際に通ったかを示す数字です。

    「テストがないから直せない」→ まず 1 テスト から始めます。

    Boy Scout Rule のメソッド版

    触った関数は、1 つ Extract Method するだけでも負債返済になります。

    8.よくある誤解

    誤解1：「リファクタリングのついでにバグも直す」

    分けます。 バグ修正は振る舞いを変える作業なので、リファクタリングとは別作業です。混ぜると、テストが落ちたときに原因がどちらか分からなくなります。

    誤解2：「テストがないコードはリファクタリングできない」

    まず 1 テストから始めます。 仕様が分からなくても、特性テストやスナップショットで今の出力を固定すれば、安全網になります。

    誤解3：「技術的負債は全部返済しなければならない」

    全部直す必要はありません。 変更頻度の高い関数など重要な所から優先付けし、触ったところを少しずつきれいにします。

    9.まとめ

    • リファクタリング ＝ 振る舞いを変えず構造を改善
    • Extract Method / Parameter Object / Replace Conditional が基本
    • レガシーは段階的に。テストを先に
    • 技術的負債は可視化し、優先付けて改善
