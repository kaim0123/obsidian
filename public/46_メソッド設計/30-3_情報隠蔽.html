    情報隠蔽 — 関数レベルで詳細を閉じ込める

    情報隠蔽はクラスやモジュールだけの話ではありません。1 つの関数にも「呼ぶ側に見せるもの」と「中に隠すもの」があります。このページでは、Parnas の情報隠蔽をメソッドに当てはめ、公開する操作と内部ヘルパーの線引き、戻り値と引数で内部表現を漏らさない方法、クラスのカプセル化との関係を解説します。

    もとにしたノート：03_情報隠蔽

    ひとことで言うと

    呼ぶ側は 「何をするか」だけ を知ればよく、計算の途中式やデータ構造は関数の中に隠します。公開 API と内部ヘルパーを線引き し、戻り値・引数で内部表現を漏らさない ようにします。

    2.情報隠蔽（Parnas）のメソッドへの適用

    David Parnas（1972）が提唱した 情報隠蔽 は、変更しやすい詳細を内部に閉じる 設計原則です。

    メソッドレベルでは、次のように適用します。

    • 呼び出し側 は「何をするか」だけ知ればよい
    • 実装の詳細（計算の途中式、データ構造）は関数の中に隠す
    • 内部表現が変わっても 公開インターフェース（外から呼べる名前・引数・戻り値）が同じなら、呼び出し側は変更不要
    ◯ 内部の詳細を隠す 
    function getOrderTotal(order) {
  return calculateSubtotal(order) + calculateTax(order);
}
// 呼び出し側は税計算の式を知らなくてよい

    3.公開する操作と内部ヘルパーの線引き

    種類役割命名・配置
    公開 API他モジュール・他クラスから呼ばれる明確な名前、ドキュメント
    内部ヘルパー同じファイル・同じクラス内だけで使う_ プレフィックスや private
     
    // 公開
export function processOrder(order) { /* ... */ }

// 内部ヘルパー（モジュール内のみ）
function calculateTax(amount) { /* ... */ }

    Java では private、JavaScript では モジュールスコープ（export しない関数はそのファイルの外から見えない）や # プライベートフィールドを使います。

    4.戻り値 — 内部データ構造をそのまま返さない

    内部表現の漏洩 は、呼び出し側が実装に依存する原因になります。

    ✕ 悪い例：内部の Map をそのまま返す 
    function getItems(order) {
  return order._itemMap;  // 呼び出し側が Map に依存
}
    ◯ 良い例：必要な情報だけ返す 
    function getItems(order) {
  return [...order._itemMap.values()];
}

    悪い例では、内部の持ち方を Map から配列に変えたくなっても、呼び出し側が Map のメソッドを使っているので変えられません。クラス設計でのカプセル化（44章：クラス設計）と同じ考え方を、関数の戻り値にも適用します。戻り値の形については 戻り値の設計 でさらに詳しく扱います。

    5.引数 — 呼び出し側が内部を知りすぎない

    引数に 内部表現 を渡させると、結合度（モジュール同士がどれだけ互いに依存しているか）が上がります。

    ✕ 悪い例：DB の行オブジェクトを直接渡す 
    function calculateDiscount(dbRow) {
  return dbRow.price * dbRow.discount_rate;
}
    ◯ 良い例：ドメインの概念だけ渡す 
    function calculateDiscount(price, discountRate) {
  return price * discountRate;
}

    悪い例では、DB の列名（discount_rate）が変わると割引計算まで直す必要があります。ドメイン（そのソフトウェアが扱う業務の領域）の概念だけを受け取れば、DB の都合から切り離せます。Parameter Object を使う場合も、ドメインの言葉 で組み立てます（→ 引数の設計）。

    6.クラス設計のカプセル化との関係

    クラスは 型の境界、メソッドは 処理の境界 です。両方で情報隠蔽を意識すると、変更に強いコードになります。

    7.演習 — 漏れている詳細を見つける

    次のコードで、情報隠蔽が破れている箇所 を指摘してみましょう。

    function getUserDisplayName(user) {
  return user._internalName.toUpperCase();  // ①
}

function sortOrders(orders) {
  return orders.sort((a, b) => a._priority - b._priority);  // ②
}
    箇所問題改善
    ①_internalName に依存getDisplayName() を User に
    ②_priority と in-place sortgetSortKey() + 非破壊 sort

    _ で始まる名前は「内部用」という慣習なので、外から触っている時点で情報隠蔽が破れています。また in-place sort（元の配列そのものを並べ替える）は、渡された配列を書き換えてしまいます。[...orders].sort(...) のようにコピーしてから並べる 非破壊 の書き方にします（→ 引数の破壊的変更とイミュータブル）。

    8.よくある誤解

    誤解1：「情報隠蔽はクラスやモジュールの話で、関数には関係ない」

    関数にも当てはまります。 関数名・引数・戻り値が関数の公開インターフェースで、計算の途中式やデータ構造が隠すべき詳細です。

    誤解2：「private にしておけば情報隠蔽はできている」

    アクセス修飾子だけでは足りません。戻り値で内部の Map をそのまま返したり、引数に DB の行を受け取ったり すると、private でも内部表現が外に漏れます。

    誤解3：「必要になりそうな情報は全部返しておくほうが親切」

    返したものには呼ぶ側が依存し、あとから変えられなくなります。呼ぶ側に必要な情報だけ を返します。

    9.まとめ

    • 情報隠蔽 = 詳細を内部に閉じ、公開操作だけを提供 する
    • 公開 API と内部ヘルパー を線引きする
    • 戻り値・引数 で内部表現を漏らさない
    • クラスの カプセル化 とメソッドの 情報隠蔽 は連動する
