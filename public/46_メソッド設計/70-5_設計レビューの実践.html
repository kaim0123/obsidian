    設計レビューの実践 — 総合チェックリストと Before/After で伝える

    このページは、これまで学んだメソッド設計の知識を使ってレビューを行う 総合演習 です。レビューの進め方と時間配分、分割・制御・契約・品質をまとめた総合チェックリスト、改善案を Before/After で示す方法、そしてリファクタリング PR の書き方を学びます。

    もとにしたノート：05_設計レビューの実践

    ひとことで言うと

    レビューは エントリポイント（入口の関数）から流れをつかみ → チェックリストで点検し → 優先度を付けて指摘 します。改善案は 具体的な Before/After で示し、直すときのリファクタリング PR は 小さく・振る舞い不変・テスト付き にします。

    2.メソッド設計レビューの進め方

    1. 対象を決める — 新規 PR / 複雑度 Top 10 / 変更頻度の高い関数
    2. オーケストレーションから読む — エントリポイントの流れを把握
    3. チェックリストで点検 — チェックリストとアンチパターン
    4. 優先度付きで指摘 — Critical 3 件以内
    5. フォロー — リファクタ PR または次スプリントで対応

    エントリポイント は、処理が始まる入口の関数（API のハンドラーなど）です。Critical は「必ず直すべき重大な指摘」を表します。

    60 分レビューの例：

    時間やること
    10 min全体像・エントリポイント
    30 min関数ごとにチェックリスト
    15 min指摘の整理・優先度
    5 min次アクション合意

    3.レビュー用チェックリスト（総合版）

    分割と責任

    • ☐ 1 メソッド 1 関心（SoC / SRP）
    • ☐ 50 行超・複雑度 10 超の関数がない
    • ☐ オーケストレーションと詳細が分離

    制御と読みやすさ

    • ☐ Guard Clause で正常系が一直線
    • ☐ ネスト 3 段以内
    • ☐ 動詞 ＋ 目的語の命名

    契約と副作用

    • ☐ CQS — getter に副作用なし
    • ☐ 純粋にできる計算が Core にある
    • ☐ 引数 3 個以下、または Parameter Object

    品質

    • ☐ 主要ロジックに単体テスト
    • ☐ モックが 3 個以上 → 設計見直し

    各項目の詳しい説明は、関心の分離と単一責任、Guard Clause、CQS、Functional Core, Imperative Shell、テストしやすいメソッド設計 を参照してください。

    4.Before / After の提示方法

    レビューコメントでは 具体的な Before/After を示します。

    ✕ Before（L45-80）：検証と計算が混在 
    function process(order) {
  if (!order.items.length) throw new Error('...');
  let total = 0;
  for (...) { total += ...; }
  db.save(order);
}
    ◯ After 提案 
    function process(order) {
  validateOrder(order);
  const total = calculateTotal(order.items);
  saveOrder({ ...order, total });
}

    diff 形式（変更前後の差分を行ごとに示す形式）または 疑似コード で、変更の意図を伝えます。

    5.リファクタリング PR の書き方

    項目内容
    タイトルrefactor: extract validateOrder from handleRequest
    説明何を・なぜ・振る舞いは変えない
    スコープ1 PR ＝ 1 リファクタ主題（Extract Method のみ等）
    テスト既存テスト通過 ＋ 新規テスト（純粋関数）

    PR 説明の例（Markdown）：

    ## Summary
- handleRequest から validateOrder / calculateTotal を Extract Method
- 振る舞い変更なし（既存テスト 42 件通過）

## Why
- 単体テスト可能にするため
- 複雑度 18 → 6 に低減

## Test plan
- [x] npm test
- [x] 手動で注文 API を 1 回確認

    リファクタリングそのものの進め方は リファクタリングの実践 を参照してください。

    6.よくある誤解

    誤解1：「レビューは見つけた問題を全部挙げるほど良い」

    優先度を付けて絞ります。 Critical は 3 件以内にし、残りはリファクタ PR や次スプリントに回します。全部を並べると、本当に直すべきものが埋もれます。

    誤解2：「改善案は言葉で説明すれば伝わる」

    Before/After を見せる方が確実です。 該当行（L45-80 など）を示し、diff 形式や疑似コードで「こう変えたい」を具体的に示します。

    誤解3：「リファクタ PR は、ついでに機能追加もまとめた方が効率的」

    分けます。 1 PR ＝ 1 リファクタ主題にし、振る舞いは変えないことを説明に書きます。機能追加が混ざると、レビューもテストも難しくなります。

    7.まとめ

    • レビューはエントリポイント → チェックリスト → 優先度付き指摘
    • 総合チェックリストで抜け漏れを防ぐ
    • Before/After で改善意図を明確に
    • リファクタ PR は小さく・振る舞い不変・テスト付き
