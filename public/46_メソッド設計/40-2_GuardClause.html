    40 本体の書き方

    Guard Clause — 早期 return で正常系を一直線に

    if の中に if、さらにその中に if……と深くネストしたコードは、読むのもテストするのも大変です。このページでは、異常系や前提条件を関数の入口で先に弾いてすぐ return する Guard Clause（ガード節） を学びます。else をなくして分岐を単純にする方法、if-else のままでよい場面、条件に名前を付ける Extract Method との組み合わせまで扱います。

    もとにしたノート：02_Guard_Clause

    ひとことで言うと

    異常系・前提条件を先に弾いて早期 return し、残りの 正常系を上から下へ一直線に読める ようにする書き方です。else をなくすと分岐同士の結びつきが弱まり、入れ替えや追加もしやすくなります。ただし、対等な二択は if-else のままで構いません。

    1.このページで扱うこと

    Guard Clause（ガード節） は、ネストした if を避け、正常系（エラーや例外的な場合ではない、本来やりたい処理の流れ）を一直線に読ませる技法です。

    • ネストした if の問題（矢印型コード）
    • Guard Clause の書き方と目的
    • else 句をなくすと条件分岐が単純になる理由
    • 対称的な分岐 — if-else のままがよい場面
    • Guard Clause と Extract Method の組み合わせ

    メソッドの長さや抽象度の話は サイズと抽象度、分岐の多さを数値で測る話は 複雑度と分岐 で扱います。

    2.ネストした if の問題

    深くネストした if は、読みにくく・テストしにくい 原因になります。

    ✕ 悪い例：ネストが深い 
    function processOrder(order) {
  if (order) {
    if (order.items.length > 0) {
      if (order.customer.isActive) {
        // 正常系が 3 段インデント
        return calculateTotal(order);
      }
    }
  }
  return null;
}

    インデントが右へ右へと伸びていく形から、このようなコードは 矢印型コード（Arrow Code）と呼ばれます。肝心の正常系が奥に埋もれてしまい、流れを追いにくくなります。

    3.Guard Clause（ガード節）の書き方

    Guard Clause は、異常系・前提条件を先に弾き、早期 return する 書き方です。早期 return とは、関数の最後まで待たずに、結果が決まった時点ですぐ return することです。

    ◯ 良い例：Guard Clause 
    function processOrder(order) {
  if (!order) return null;
  if (order.items.length === 0) return null;
  if (!order.customer.isActive) return null;

  return calculateTotal(order);  // 正常系が一直線
}

    異常系を 関数の入口 に集約し、本流を浅く保ちます。

    4.正常系を一直線に読ませる

    Guard Clause の 目的 は、読み手が 正常系だけ を上から下に読めることです。

      Before（ネスト）          After（Guard Clause）
  ───────────────          ───────────────────
  if (ok) {                if (!ok) return;
    if (valid) {           if (!valid) return;
      正常系                  正常系
    }                      }
  }

    正常系は インデント 1 段 に収めるのが理想です。

    5.else 句をなくすと条件分岐が単純になる

    増田亨『現場で役立つシステム設計の原則』第2章は、区分ごとの料金計算などを例に、else を消して早期 return（ガード節） にすると、分岐同士の結びつきが弱まり、順序の入れ替えや追加がしやすい と説明しています。

    ✕ 悪い例：結果を変数にため、else でつなぐ 
    function fee(customer: Customer): number {
  let result: number;
  if (customer.isChild()) {
    result = childFee();
  } else if (customer.isSenior()) {
    result = seniorFee();
  } else {
    result = adultFee();
  }
  return result;
}
    ◯ 良い例：else をなくし、確定したらすぐ return 
    function fee(customer: Customer): number {
  if (customer.isChild()) return childFee();
  if (customer.isSenior()) return seniorFee();
  return adultFee();
}

    悪い例では、読み手は「result にいつ何が入ったか」を最後まで追う必要があります。良い例では、各行が「この条件ならこの料金」で完結しています。

    条件式そのものをメソッドに独立させると、さらに意図が読めます（同書でいう「判断や処理のロジックをメソッドに独立させる」）。

    function fee(customer: Customer): number {
  if (isChild(customer)) return childFee();
  if (isSenior(customer)) return seniorFee();
  return adultFee();
}

    区分が増えて同じパターンの if があちこちに散らばる段階では、区分ごとの処理をクラスや列挙型へ押し出すことを検討します（→ 44章：区分オブジェクトと状態遷移）。

    6.対称的な分岐 — if-else のままがよい場面

    すべてを Guard Clause にする必要はありません。

    Guard Clause が向くif-else が向く
    前提条件のチェック2 つの同等な選択肢
    異常系の早期脱出状態に応じた対称的処理
    区分の早期振り分け真偽が対等な二択
    ◯ 対称的な分岐 → if-else でよい 
    function getPrice(isMember) {
  if (isMember) {
    return applyMemberDiscount(basePrice);
  } else {
    return basePrice;
  }
}

    会員かどうかはどちらも「普通の」ケースで、どちらかが例外というわけではありません。こうした 対等な二択 は、if-else で並べた方が対称性が伝わります。

    7.Guard Clause + Extract Method の組み合わせ

    ガードの条件が複雑なら、Extract Method（処理の一部を名前の付いたメソッドに取り出すリファクタリング）で名前を付けます。

    function processOrder(order) {
  if (!isValidOrder(order)) return null;
  if (!isActiveCustomer(order.customer)) return null;

  return calculateTotal(order);
}

function isValidOrder(order) {
  return order && order.items.length > 0;
}

function isActiveCustomer(customer) {
  return customer && customer.isActive;
}

    条件に 意図のある名前 を付けると、Guard Clause がさらに読みやすくなります。

    8.よくある誤解

    誤解1：「if-else はすべて Guard Clause に書き換えるべき」

    違います。 Guard Clause が向くのは前提条件のチェックや異常系の早期脱出です。会員／非会員のような 対等な二択 は、if-else のままの方が対称性が伝わります。

    誤解2：「return は関数の最後に1つだけにすべき」

    Guard Clause ではこだわりません。 結果を変数にためて最後に1回だけ return すると、読み手は「いつ値が決まったか」を最後まで追う必要があります。確定したらすぐ return した方が、各分岐が独立し、入れ替えや追加もしやすくなります。

    誤解3：「早期 return にすれば分岐の問題はすべて解決する」

    入口の整理にすぎません。 条件が複雑なら Extract Method で名前を付け、区分ごとの if が散らばってきたら 区分オブジェクト へ寄せることを考えます。

    9.まとめ

    • ネストした if は読みにくい。Guard Clause で浅くする
    • else をなくし早期 return すると、区分分岐の入れ替え・追加がしやすい
    • 異常系を先に弾き、正常系を一直線に
    • 対称的な分岐は if-else のままでよい
    • 複雑な条件は Extract Method で名前を付ける
