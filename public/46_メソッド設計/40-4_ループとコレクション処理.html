    40 本体の書き方

    ループとコレクション処理 — 「どうやって」より「何を」を書く

    メソッドの本体で最もよく書くのが、配列やリストを処理するコードです。このページでは、for ループと map / filter / reduce をつなぐ コレクションパイプライン の違い、Fowler の「ループからパイプラインへの置き換え」、主なコレクション操作の使い分け、ループの方が適している場面、そして reduce の乱用・非同期処理・性能といった落とし穴を学びます。

    もとにしたノート：04_ループとコレクション処理

    ひとことで言うと

    ループは「どうやって」を書き、パイプラインは「何を」を書きます。判定は some、検索は find、グループ化は groupBy のように 専用の操作 を使うと意図が名前になります。ただし、非同期の順次処理や副作用が目的の処理など、ループの方が分かりやすい場面 もあります。

    1.このページで扱うこと

    メソッドの本体で最もよく書くのが、配列やリストを処理するコード です。このページでは次のことを学びます。

    • for ループと コレクションパイプライン（map / filter / reduce）の違い
    • Fowler のリファクタリング ループからパイプラインへの置き換え
    • 主なコレクション操作の 使い分け
    • ループの方が適している場面
    • よくある落とし穴（reduce の乱用・非同期処理・性能）

    コレクション は配列やリストのように値をまとめて持つもの、コレクションパイプライン は、コレクションに対する操作（絞り込む・変換する・並べる…）を鎖のようにつないで書くスタイルです。

    2.ループは「何をしているか」が読みにくい

    2.1 例

    // 有効なユーザーのうち、東京在住の人のメールアドレスを、名前順で最大10件
const result: string[] = [];
const sorted = [...users].sort((a, b) => a.name.localeCompare(b.name));
for (let i = 0; i < sorted.length; i++) {
  const u = sorted[i];
  if (!u.active) continue;
  if (u.prefecture !== "東京都") continue;
  result.push(u.email);
  if (result.length >= 10) break;
}

    このコードを理解するには、ループの中を1行ずつ追って、頭の中で実行する 必要があります。

    • i の範囲は正しいか（< か <= か）
    • continue と break の条件は何か
    • result はどこで増えているか

    2.2 パイプラインで書くと

    const result = users
  .filter((u) => u.active)
  .filter((u) => u.prefecture === "東京都")
  .toSorted((a, b) => a.name.localeCompare(b.name))
  .slice(0, 10)
  .map((u) => u.email);
    • 上から順に読むだけで、何をしているか（絞り込む → 並べる → 先頭10件 → メールを取り出す）が分かる
    • インデックス変数・continue・break・結果を貯める変数がない → バグが入り込む場所が少ない
    • 各段階は 元の配列を変更しない（→ 引数の破壊的変更とイミュータブル）

    ループは「どうやって」を書き、パイプラインは「何を」を書く。

    3.Fowler の「ループからパイプラインへの置き換え」

    Martin Fowler は『リファクタリング 第2版』（2018）で、ループ（Loops） をコードの臭い（設計の問題を示すサイン）の1つに加え、Replace Loop with Pipeline（ループからパイプラインへの置き換え）というリファクタリングを紹介しました。Fowler は「ループは時代遅れの概念になりつつある」とまで述べています。

    3.1 手順

    1. ループが処理している コレクションを変数に取り出す（パイプラインの出発点）
    2. ループの中の処理を、先頭から1つずつ パイプラインの操作に移す。if (...) continue; → filter、値の変換 → map、集計 → reduce などの集計操作
    3. 1つ移すたびに テストを実行 する
    4. ループが空になったら削除する

    3.2 例：ループの中身を順に移す

    ✕ Before 
    function officesIn(csv: string, country: string) {
  const lines = csv.split("\n");
  let firstLine = true;
  const result: { city: string; phone: string }[] = [];
  for (const line of lines) {
    if (firstLine) { firstLine = false; continue; }   // ヘッダーを飛ばす
    if (line.trim() === "") continue;                  // 空行を飛ばす
    const record = line.split(",");
    if (record[1].trim() === country) {
      result.push({ city: record[0].trim(), phone: record[2].trim() });
    }
  }
  return result;
}
    ◯ After 
    function officesIn(csv: string, country: string) {
  return csv.split("\n")
    .slice(1)                                          // ヘッダーを飛ばす
    .filter((line) => line.trim() !== "")              // 空行を飛ばす
    .map((line) => line.split(","))
    .filter((record) => record[1].trim() === country)
    .map((record) => ({ city: record[0].trim(), phone: record[2].trim() }));
}

    4.主なコレクション操作

    4.1 変換・絞り込み

    操作やること例
    map各要素を変換する（要素数は同じ）users.map((u) => u.email)
    filter条件に合う要素だけ残すusers.filter((u) => u.active)
    flatMap各要素を配列に変換し、平らにつなぐorders.flatMap((o) => o.items)
    slice一部を取り出すlist.slice(0, 10)
    toSorted並べ替えた 新しい 配列を返す（ES2023）list.toSorted(byName)

    ES2023 などは JavaScript の仕様の版です。sort は元の配列を並べ替えてしまいますが、toSorted は元を変えずに新しい配列を返します。

    4.2 検索・判定

    操作やること戻り値
    find条件に合う最初の要素要素 または undefined
    findIndex条件に合う最初の位置位置 または -1
    some条件に合う要素が 1つでもあるかboolean
    everyすべての 要素が条件に合うかboolean
    includes値が含まれるかboolean
    ✕ 判定のためにループと変数を使う 
    let hasAdmin = false;
for (const u of users) { if (u.role === "admin") { hasAdmin = true; break; } }
    ◯ 意図がそのまま名前になる 
    const hasAdmin = users.some((u) => u.role === "admin");

    4.3 集計・グループ化

    操作やること例
    reduce要素を1つの値にまとめる合計・最大値
    Object.groupBy / Map.groupByキーごとにグループ化する（ES2024）Object.groupBy(orders, (o) => o.status)
    join文字列として連結するnames.join(", ")
     
    const total = items.reduce((sum, i) => sum + i.price * i.quantity, 0);
const byStatus = Object.groupBy(orders, (o) => o.status);
// { placed: [...], shipped: [...], cancelled: [...] }

    5.reduce の乱用に注意

    reduce は万能ですが、何でも reduce で書くと、ループより読みにくくなる ことがあります。

    ✕ reduce で何でもやる（読むのに時間がかかる） 
    const result = users.reduce<Record<string, string[]>>((acc, u) => {
  if (!u.active) return acc;
  (acc[u.prefecture] ??= []).push(u.email);
  return acc;
}, {});
    ◯ 目的に合った操作に分ける 
    const result = Object.groupBy(users.filter((u) => u.active), (u) => u.prefecture);
// （メールだけ欲しければ、さらに各グループを map する）
    reduce を使ってよい他の操作を使うべき
    合計・積・最大値・最小値のような 単純な集計絞り込み（filter）、変換（map）、グループ化（groupBy）、判定（some / every）

    専用の操作があるなら、専用の操作を使う。名前が意図を語ってくれるからです。

    6.ループの方が適している場面

    パイプラインが常に正解ではありません。次の場面では、素直なループの方が分かりやすいことがあります。

    場面理由
    途中で抜ける複雑な条件 があるbreak で抜ける方が直感的なことがある（単純なものは find / some で書ける）
    非同期処理を順番に 実行したいfor...of ＋ await が最も分かりやすい（7章）
    複数の値を同時に 更新する複雑な状態機械パイプラインに無理に押し込むと、reduce の中が複雑になる
    性能が本当に重要 な、大量データのホットパスパイプラインは中間の配列を作るので、計測して問題があればループにする（8章）
    副作用が目的 の処理（DB 保存・ログ出力）map を副作用のために使うのは誤用。for...of か forEach を使う

    状態機械 は、いまの状態と入力に応じて次の状態が決まる仕組み、ホットパス は、プログラムの中で特に頻繁に実行される部分、副作用 は、値を返す以外に外の世界を変えること（DB への保存やメール送信など）です。

    ✕ map を副作用のために使う（戻り値を捨てている） 
    users.map((u) => sendEmail(u));
    ◯ 副作用が目的なら for...of 
    for (const u of users) sendEmail(u);

    7.非同期処理とコレクション

    ✕ forEach は await を待たない（すべて同時に走り、完了を待たずに次へ進む） 
    users.forEach(async (u) => { await sendEmail(u); });
console.log("送信完了");   // 実際にはまだ終わっていない
    ◯ 順番に1件ずつ（前の完了を待つ） 
    for (const u of users) {
  await sendEmail(u);
}
    ◯ 並列に実行し、すべての完了を待つ 
    await Promise.all(users.map((u) => sendEmail(u)));
    ◯ 一部が失敗しても残りの結果を得たい 
    const results = await Promise.allSettled(users.map((u) => sendEmail(u)));
    方法動き向いている
    for...of ＋ await順番に 1件ずつ順序が重要、相手のサーバーに負荷をかけたくない
    Promise.all ＋ map並列に すべて速さ重視。1件でも失敗したら全体が失敗
    Promise.allSettled ＋ map並列、失敗しても全件の結果 を得る一部の失敗を許容して集計したい
    forEach ＋ async完了を待たない✕ ほぼ常に誤り

    大量の件数を並列に処理するときは、同時実行数を制限 する（p-limit などのライブラリ）ことも検討します。

    8.性能について

    • パイプラインは filter → map のたびに 中間の配列 を作る
    • 多くの場合、この差は 無視できるほど小さい。まず読みやすさを優先する
    • 数十万件以上のデータを何度も処理するような ホットパス で、計測して問題があった場合だけ ループに書き換える（早すぎる最適化を避ける）
    • 大きなデータを 遅延評価（必要になった要素だけを、そのつど計算する方式）で処理したいときは、ジェネレータ や イテレータヘルパー（Iterator.prototype.map など、ES2025）が使える

    9.よくある誤解

    誤解1：「ループは悪い。すべてパイプラインにすべき」

    誤りです。 非同期の順次処理・副作用が目的の処理・複雑な状態更新では、ループの方が分かりやすいことがあります。

    誤解2：「forEach はパイプラインの一種」

    半分だけ正しいです。 forEach は値を返さず、副作用のためだけ にあります。async 関数とも相性が悪いので、for...of で十分なことが多いです。

    誤解3：「パイプラインは遅い」

    多くの場合、問題になりません。 計測してから判断します。

    10.まとめ

    • ループは「どうやって」、パイプラインは「何を」を書く。パイプラインは意図が読みやすく、バグが入る余地が少ない
    • Fowler の Replace Loop with Pipeline：コレクションを取り出し、ループの中身を先頭から1つずつ filter / map などに移す
    • 専用の操作を使う：判定は some / every、検索は find、グループ化は groupBy。reduce は単純な集計に
    • ループが適している場面：非同期の順次処理、副作用が目的、複雑な状態更新、計測済みのホットパス
    • 非同期では forEach ＋ async は使わない。順次なら for...of、並列なら Promise.all / allSettled
