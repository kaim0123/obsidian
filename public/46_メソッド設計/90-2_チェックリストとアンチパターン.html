    90 付録

    チェックリストとアンチパターン — メソッドを点検し、悪い型を見分ける

    メソッド設計のレビューや自己点検に使えるチェックリスト（総合版）と、避けるべき代表的なアンチパターン 8 つをまとめたページです。チェックリストは「分割と責任」「サイズと複雑度」など 6 分類で、場面ごとにどこを重点的に見るかも整理しています。アンチパターンは症状と対策をセットにし、詳しく説明しているページへリンクしています。

    もとにしたノート：付録B_メソッド設計チェックリスト、付録E_よくあるアンチパターン一覧

    ひとことで言うと

    チェックリストは「良いメソッドの条件」、アンチパターンは「その条件を破ったときに出る症状」です。チェックリストで引っかかった項目があれば、対応するアンチパターンの「対策」を見れば、どう直せばよいかが分かります。

    1.このページで扱うこと

    • メソッド設計チェックリスト（総合版）：分割と責任・サイズと複雑度・制御フロー・契約と副作用・命名と読みやすさ・テストと品質の 6 分類
    • チェックリストの使い方：場面ごとの重点セクション
    • よくあるアンチパターン一覧：巨大関数から try-catch だらけまで 8 個と、その対策

    アンチパターンは、よくある悪い設計のパターンのことです。レビューの進め方は 設計レビューの実践、コードレビューで見るポイント を参照してください。クラス単位の「コードの臭い」は コードの臭いとリファクタリング（44章） にまとまっています。

    2.メソッド設計チェックリスト（総合版）

    メソッド設計のレビューや自己点検に使えるチェックリストです。

    2.1 分割と責任

    • ☐ 1 メソッド 1 種類の仕事（SoC＝関心の分離）
    • ☐ 1 メソッド 1 変更理由（SRP＝単一責任の原則）
    • ☐ オーケストレーション関数（手順を並べて他の関数を呼ぶだけの関数）と詳細関数が分離されている
    • ☐ process() handleData() 等の曖昧名がない
    • ☐ 同じ抽象度のステップが並んでいる

    関連：メソッドの分割、関心の分離と単一責任

    2.2 サイズと複雑度

    • ☐ 1 関数 50 行以内（目安 20 行）
    • ☐ 循環的複雑度（分岐の多さを測る指標）10 以下
    • ☐ ネスト 3 段以内
    • ☐ 引数 3 個以下、または Parameter Object

    関連：サイズと抽象度、複雑度と分岐、引数の設計

    2.3 制御フロー

    • ☐ Guard Clause で異常系を先に処理
    • ☐ 正常系が一直線に読める
    • ☐ フラグ引数で複数責任を切り替えていない

    関連：Guard Clause、引数の設計

    2.4 契約と副作用

    • ☐ CQS — getter / is / has に副作用なし
    • ☐ 純粋にできる計算が I/O と分離されている
    • ☐ Fail Fast — 前提条件を入口でチェック
    • ☐ 内部データ構造をそのまま返していない

    関連：CQS、Functional Core, Imperative Shell、Design by Contract、情報隠蔽

    2.5 命名と読みやすさ

    • ☐ 関数名は動詞 + 目的語
    • ☐ boolean は is / has / can / should
    • ☐ コメントが構造を代弁していない（Extract Method 済み）

    関連：命名、Extract Method、段落と説明用の変数

    2.6 テストと品質

    • ☐ 主要ロジックが単体テスト可能
    • ☐ モックが 3 個以上必要な関数がない
    • ☐ エラー処理が境界（Shell）に集約されている

    関連：テストしやすいメソッド設計、エラー処理

    2.7 使い方

    毎回すべてを見る必要はありません。場面に応じて重点セクションを決めます。

    場面重点セクション
    新規関数作成1〜5（2.1〜2.5）
    リファクタリング前1〜4 と 6（2.1〜2.4、2.6）
    コードレビュー全体
    レガシー改善2 と 4 を優先（2.2、2.4）

    3.よくあるアンチパターン一覧

    メソッド設計で避けるべきアンチパターンの一覧です。それぞれ「症状」と「対策」の組で示します。

    3.1 巨大関数（God Function / 神メソッド）

    症状対策
    100 行超、複数の関心Extract Method + SoC
    main / handleRequest に全部段階的詳細化
    ✕ アンチパターン 
    // アンチパターン
function handleEverything(req) { /* 500 行 */ }

    → Extract Method、ケーススタディ（注文処理フロー）

    3.2 曖昧な命名

    症状対策
    process(), handleData()動詞 + 目的語
    検索で数十件ヒット具体的な名前

    → 命名、関心の分離と単一責任

    3.3 副作用付き getter

    症状対策
    getUser() 内でログ・DB 更新CQS — Query は副作用なし
    読むたびに状態が変わるCommand に分離
    ✕ アンチパターン：値を読むだけのはずが状態を書き換える 
    // アンチパターン
function getTotal(order) {
  order.lastAccessed = Date.now();
  return order.cachedTotal;
}

    → CQS

    3.4 フラグ引数

    症状対策
    save(data, true) の意味が不明関数を分割
    1 関数が 2 モードsaveAsHtml() / saveAsText()

    → 引数の設計

    3.5 ネスト地獄

    症状対策
    if の中の if が 4 段Guard Clause
    正常系が右端異常系を先に return

    → Guard Clause（形の比較は 参考図解 にもあります）

    3.6 モック地獄

    症状対策
    テストでモック 10 個純粋関数に Core を切り出す
    モックの順序に依存FCIS、依存注入

    モックは、テストで DB や外部 API などの本物の代わりに使う偽の部品、依存注入は、関数が使う部品を中で作らずに外から渡してもらう書き方です。

    → テストしやすいメソッド設計、Functional Core, Imperative Shell

    3.7 貧血モデル（メソッド版）

    症状対策
    エンティティはデータのみドメインルールをメソッドに
    サービスにロジック集中Tell, Don't Ask

    → オブジェクトのメソッド、Tell Don't Ask と貧血モデル（44章）

    3.8 try-catch だらけ

    症状対策
    各関数に try-catch境界（Shell）に集約
    正常系が読めないFail Fast + 上位で catch

    → エラー処理

    3.9 チェックリストとの対応

    各アンチパターンは、チェックリストのどの項目に引っかかるかで見つけられます。

    アンチパターン引っかかるチェック項目
    巨大関数2.1 分割と責任、2.2 サイズと複雑度
    曖昧な命名2.1 の曖昧名、2.5 命名と読みやすさ
    副作用付き getter2.4 の CQS
    フラグ引数2.3 の「フラグ引数で複数責任を切り替えていない」
    ネスト地獄2.2 のネスト 3 段以内、2.3 の Guard Clause
    モック地獄2.6 の「モックが 3 個以上必要な関数がない」
    貧血モデル2.1 分割と責任（ロジックの置き場所）
    try-catch だらけ2.6 の「エラー処理が境界（Shell）に集約されている」

    4.よくある誤解

    誤解1：「チェック項目を全部満たさないとマージしてはいけない」

    チェックリストは点検の道具で、合否判定表ではありません。「1 関数 50 行以内（目安 20 行）」のように数字は目安です。引っかかった項目は「なぜそうなっているか」を考えるきっかけにし、理由があれば例外として残してかまいません。場面ごとに重点セクションを絞るのもそのためです。

    誤解2：「try-catch は多いほど安全」

    各関数に try-catch を書くと、正常系が読みにくくなるうえ、エラーを握りつぶしやすくなります。前提条件は入口で Fail Fast で弾き、例外は境界（Shell）でまとめて受け止めるほうが、エラーの扱いが一か所にそろいます。

    誤解3：「getter にちょっとしたログや更新を入れるくらいは問題ない」

    呼ぶ側は getter を「何度呼んでも状態が変わらない」と思って使います。中で状態を書き換えると、呼ぶ回数や順番で結果が変わる見つけにくいバグになります。状態を変える処理は Command として別のメソッドに分けます。

    5.まとめ

    • チェックリストは 6 分類：分割と責任／サイズと複雑度／制御フロー／契約と副作用／命名と読みやすさ／テストと品質
    • 場面ごとに重点を絞る：新規作成は 1〜5、リファクタリング前は 1〜4 と 6、レビューは全体、レガシー改善は 2 と 4 を優先
    • 代表的なアンチパターンは、巨大関数・曖昧な命名・副作用付き getter・フラグ引数・ネスト地獄・モック地獄・貧血モデル・try-catch だらけの 8 つ
    • 対策の多くは Extract Method、Guard Clause、CQS、FCIS（純粋な Core と I/O の Shell の分離）の組み合わせで実現できる
