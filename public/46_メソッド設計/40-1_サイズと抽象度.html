    40 本体の書き方

    サイズと抽象度 — 小さく書き、1つの抽象度に揃える

    シグネチャが整っても、本体が長く入り組んでいれば読み手は迷います。このページでは、関数の本体の書き方として、Clean Code の「関数は小さく」というルール、1 関数の中で抽象度を揃えること、20 行という目安とその限界、コメントが構造を代弁しているサイン、読み手の視線で関数を読む練習、そして「メソッドは短く、クラスは小さく」をセットで守る考え方を解説します。

    もとにしたノート：01_サイズと抽象度

    ひとことで言うと

    関数は 小さく・引数少なく・インデント浅く 書き、中のステップは 同じ抽象度 に揃えます。20 行は目安 で、複雑度とセットで判断します。「// --- 認証 ---」のような 構造のコメント は、関数に切り出すべきサインです。

    1.このページで扱うこと

    関数の長さ と 抽象度の統一 を学びます。抽象度 とは、どれだけ細かい手順まで書いているかの度合いです。「注文を保存する」は抽象度が高く、「SQL の INSERT 文を実行する」は抽象度が低い書き方です。

    • Clean Code の関数ルール — 小さく書く
    • 1 関数 = 1 抽象度
    • 20 行の目安 とその限界
    • コメントが構造を代弁している サイン
    • 読み手の視線で関数を読む練習
    • メソッドは短く、クラスは小さく

    2.Clean Code の関数ルール — 小さく書く

    Robert C. Martin（Clean Code, 2008）は 関数は小さく と述べています。

    ルール目安
    短い1 画面に収まる
    少ない行数目安 20 行以下
    少ない引数0〜2 が理想（→ 引数の設計）
    少ないインデント1〜2 段
     
    // 目標: 読み手がスクロールせずに全体を把握できる
function registerUser(user) {
  validateUser(user);
  const hashed = hashPassword(user.password);
  persistUser({ ...user, password: hashed });
  notifyNewUser(user);
}

    詳細は ルール早見表とリファクタリング技法（Clean Code 関数ルール早見表）を参照してください。

    3.1 関数 = 1 抽象度

    1 つの関数の中のステップは、同じ抽象度 に揃えます。

    ✕ 悪い例：抽象度が混在 
    function processOrder(order) {
  validate(order);
  let total = 0;
  for (const i of order.items) {
    total += i.price * i.qty;  // 低レベル
  }
  db.query('INSERT ...');      // インフラ
}
    ◯ 良い例：同じ抽象度 
    function processOrder(order) {
  validate(order);
  const total = calculateTotal(order);
  saveOrder(order, total);
}

    悪い例では、「検証する」という高レベルの一文のすぐ後に、合計を足し上げるループ（低レベル）と DB への SQL（インフラ：データベースなど外部の仕組みを扱う部分）が並んでいます。読み手は頭の中で、細かさの違う話を行き来しなければなりません。

    混在させない

    高レベル = オーケストレーション（手順の段取りだけを書く）、低レベル = 詳細関数（1 つの手順の中身を書く）。この 2 つを 1 つの関数に 混在させない ようにします。詳細を関数に切り出す手順は Extract Method で扱います。

    4.20 行の目安とその限界

    20 行 は 目安 であり、絶対のルールではありません。

    20 行超でも許容20 行以内にすべき
    宣言的な設定・マッピング分岐だらけの処理
    生成されたコード手書きのビジネスロジック
    1 つの式の展開複数の関心が混在

    行数は 複雑度（分岐やループの多さ。→ 複雑度と分岐）と セット で判断します。20 行以内でも、分岐が 10 個あれば分割を検討します。

    5.コメントが構造を代弁しているサイン

    次のようなコメントは、Extract Method の候補 です。

    ✕ コメントで区切って、1 つの関数に 3 つの仕事を詰めている 
    function handleRequest(req) {
  // --- 認証 ---
  if (!req.token) { /* 15 行 */ }

  // --- バリデーション ---
  if (!req.body) { /* 20 行 */ }

  // --- 本処理 ---
  /* ... */
}

    良いコメント

    なぜ（Why）そう書いたのかを説明する

    構造のコメント

    「ここから〇〇」と区切るコメント。関数に切り出すべきサイン。authenticate()・validate() のような関数名がコメントの代わりになる

    6.読み手の視線で関数を読む練習

    書いた関数を、読み手の立場で次の順に読んでみます。

    1. 関数名だけ を上から読む — ストーリーになるか
    2. インデント を数える — 3 段以上あれば Guard Clause（先に例外的な条件を return で抜ける書き方）を検討
    3. 抽象度 を確認する — 同じレベルか
    4. 1 分で説明 する — 口頭で何をする関数か言えるか

    ハッシュ とは、パスワードを元に戻せない形に変換することです。

    7.メソッドは短く、クラスは小さく

    メソッドを短く保つだけでは足りません。関心事がクラスに溜まると、短いメソッドがたくさんある 大きなクラス になります。

    単位方針詳細
    メソッド1 抽象度・少分岐・目安 20 行このページ・段落と説明用の変数・Extract Method
    クラス狭い関心事に特化（ドメインオブジェクト）44章：ドメインを表すクラス・44章：クラス分割の基本プロセス
    値プリミティブのまま広げない44章：値オブジェクトと完全コンストラクタ

    ドメインオブジェクト は業務の概念（注文・顧客など）を表すオブジェクト、プリミティブ は number や string のような言語に最初からある基本の型です。

    「メソッドは短く、クラスは小さく」をセットで守ると、変更する箇所をクラス名から辿りやすくなります。

    8.よくある誤解

    誤解1：「20 行を超えたら必ず分割しなければならない」

    20 行は目安です。 宣言的な設定やマッピング、生成されたコードは長くても問題ありません。行数より、分岐の多さ（複雑度）と関心の混在 を見て判断します。

    誤解2：「短くさえあれば読みやすい関数になる」

    短くても、高レベルの手順と低レベルの詳細が混ざっている と読みにくくなります。行数と同時に、抽象度が揃っているかを確認します。

    誤解3：「コメントで区切って説明すれば、長い関数でも問題ない」

    「ここから認証」のような 構造のコメント は、関数に切り出すべきサインです。関数名がコメントの役割を果たすので、コメントは なぜ（Why） の説明に使います。

    誤解4：「メソッドを短くすれば設計は十分」

    短いメソッドが 1 つのクラスに溜まると、大きなクラス になります。メソッドを短くしたら、次はクラスも小さく保ちます。

    9.まとめ

    • Clean Code = 小さく・少引数・浅いインデント
    • 1 関数 = 1 抽象度。オーケストレーションと詳細を混在させない
    • 20 行は目安。複雑度とセットで判断する
    • 構造のコメント = Extract Method のサイン
    • メソッドを短くしたら、次は クラスも小さく する
