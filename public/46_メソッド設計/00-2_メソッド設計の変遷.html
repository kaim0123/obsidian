    メソッド設計の変遷 — goto の時代から Functional Core, Imperative Shell まで

    メソッド設計の考え方は、ある日まとめて生まれたものではありません。「main に全部書く」「goto で飛び回る」といった時代の困りごとから構造化プログラミングが生まれ、その限界から関心の分離・情報隠蔽・CQS・Guard Clause・Extract Method・純粋関数……と、課題と解決が積み重なってきました。このページでは、17の考え方を登場が早い順（おおよその西暦）に並べ、それぞれ「その前の課題 → 何を提案したか → どう解決したか → 向いている場面・限界」の流れでたどります。

    もとにしたノート：00_メソッド設計の変遷

    ひとことで言うと

    メソッド設計の歴史は 「課題の積み重ね」 です。名前付きの単位に分ける（構造化）→ どこで切るか・何を隠すか（段階的詳細化・関心の分離・情報隠蔽）→ 前提と読み書きを明示する（DbC・CQS）→ 長い関数を直す手順（Guard Clause・Extract Method）→ 計算を純粋にし、I/O を外側へ（純粋関数・FCIS）と、前の時代の限界を次の考え方が補ってきました。

    1.このページで扱うこと

    メソッド設計（関数設計）とは、クラスやモジュールの 中で最も小さい実行単位 — 関数・メソッド・プロシージャ（手続き）— を、読みやすく・テストしやすく・変更しやすい 形に整えることです。

    42章：設計の階層と基本用語 の比喩で言えば、クラス設計が「家具の配置」なら、メソッド設計は 「家具の細部 — 引き出しの開け方、取っ手の位置、1動作の粒度」 に相当します。

    このページでは、メソッド設計の考え方を 登場が早い順（おおよその西暦） に並べ、それぞれを次の流れで整理します。

    1. その前に、どんな課題があったか
    2. 何を提案したか
    3. どう解決したか
    4. 向いている場面・限界

    クラス設計との重なりは 44章：クラス設計の変遷 を参照してください。ここでは 1関数・1メソッド に焦点を当てます。

    3.1940〜1950年代：goto の時代

    3.1 No.0 その前：モノリシック main + goto（1940〜1950年代）

    高級言語（人間に読みやすい形で書けるプログラミング言語）が普及する前、プログラムは main の中にすべてを直書き し、goto（指定した行へ飛ぶ命令）で飛び回るスタイルが一般的でした。モノリシック とは「一枚岩の」、つまり全部が1つの塊になっていることです。

    よく起きていた課題

    • 処理の流れが追えない — ラベルへの goto が乱立し、スパゲッティコード（麺が絡まったように流れがもつれたコード）になる
    • 再利用できない — 同じ処理をコピペし、修正漏れが発生
    • テストできない — 全体を実行しないと1か所の正しさを確認できない
    • 名前で意図を表せない — 「ここからここまでが入力処理」が 行番号とコメント 頼み

    次の時代への問い

    「処理を、名前付きの小さな単位に分け、流れを読みやすくするには？」

    背景は 42章：ソフトウェア設計年表 の「手続き指向（1950年代〜）」を参照してください。

    4.1960〜1970年代：構造化と「どこで切るか」

    この時代には、処理を名前付きの単位に分ける 構造化 が生まれ、続いて「どこで切るか」「何を中に隠すか」「どれだけ複雑か」という物差しが出そろいました。

    No.考え方時期人物

    2KISS1960年頃Kelly Johnson
    3段階的詳細化1970年代（1971）Niklaus Wirth
    4関心の分離（SoC）1974年Edsger W. Dijkstra
    5情報隠蔽（関数レベル）1972年David L. Parnas

    4.1 No.1 手続き（サブルーチン）・構造化プログラミング（1960〜1970年代）

    • 背景：Fortran の SUBROUTINE（1950年代）、ALGOL 60、Dijkstra の構造化プログラミング（1960年代後半〜1970年代）
    • 一言：処理を 名前付きの手続き（関数・サブルーチン） に分割し、順次・分岐・反復 だけで制御する
    • 詳細：42章：ソフトウェア設計年表 の「手続き指向（1950年代〜）」

    その前の課題 — 巨大 main と goto 地獄

    • 数千行の main に入力・検証・計算・出力が 全部入り
    • goto で飛ぶため、どの経路を通ったか が読み取れない
    • 同じ検証ロジックが 3か所にコピペ されている
    • 1行直すと 想定外の場所 が壊れる

    何を提案したか

    原則内容
    3つの基本構造順次・分岐・反復だけで組み立てる（goto を排除）
    手続き（関数）意味のある 名前付き単位 に分割し、呼び出して再利用
    単一入口・単一出口1関数は1か所から入り、出口は整理する（※Guard Clause 登場後は柔軟に解釈）
    ◯ 構造化：意味のある単位に分割 
    // 構造化: 意味のある単位に分割
function processOrder(order) {
  validate(order);
  const total = calculateTotal(order);
  save(order, total);
  return total;
}

    どう解決したか

    • プログラムを 読める塊 に分割し、トップダウン（全体から細部へ）で理解できる
    • 手続き単位で デバッグ・再利用 の入口ができる
    • goto 排除で 制御フローの予測可能性 が上がる

    向いている場面・限界

    • 向く：すべてのメソッド設計の 出発点。どんな言語でも関数に分ける
    • 限界：分けただけでは 関数が巨大・グローバル状態依存 のまま → 段階的詳細化・SoC へ

    今の言葉での解説は 関数とメソッドの基本 にあります。

    4.2 No.2 KISS — Keep It Simple, Stupid（1960年頃）

    • 提唱：Kelly Johnson（Lockheed Skunk Works）
    • 一言：賢さより単純さ — メソッドは必要以上に抽象化・汎化しない
    • 詳細：48_原則 の「設計原則の変遷（KISS）」「DRY・KISS・YAGNI」、このページの章では KISS・DRY・YAGNI

    その前の課題 — 過剰な抽象化

    • 「将来の拡張」を理由に 3層のラッパー関数 だけのメソッド
    • 1行で済む処理を Strategy パターン（処理を差し替え可能な部品にするデザインパターン）で5ファイルに分割
    • 読む人より 書いた人だけ が理解できる関数
    • YAGNI 違反（「今いらないものは作らない」原則に反する）のメソッド引数（使われない options オブジェクト）

    何を提案したか

    最も単純な実装で要件を満たす。 メソッドレベルでは次を意識します。

    • 抽象化は 2回目の重複が見えたとき に検討（DRY とセット）
    • 汎用パラメータより 具体的な名前と引数
    • 「短く書く」より 意図が一目で分かる

    どう解決したか

    • メソッドの 認知負荷（読んで理解するのに必要な頭の負担）を下げ、レビューと変更が速くなる
    • 過剰設計を抑え、読み手の時間 を節約する

    向いている場面・限界

    • 向く：日常の実装判断、リファクタリングで「複雑にしすぎていないか」のチェック
    • 限界：単純さと DRY・拡張性 はトレードオフ → 変更理由で判断

    4.3 No.3 段階的詳細化 — トップダウン設計（1970年代）

    • 背景：Niklaus Wirth（Program Development by Stepwise Refinement, 1971）
    • 一言：大きな処理を 一段ずつ小さな関数 に分解していく

    その前の課題 — 関数の粒度の判断がない

    • 構造化は分かったが 「どこで切るか」 の基準がない
    • 10行の関数と 500行の関数が 同じ「関数」 として混在
    • 抽象度が バラバラ — 高レベルの process() の中にビット演算が直書き
    • 分解しすぎて 1行関数が 50個 並び、全体像が見えない

    何を提案したか

    段階的詳細化（Stepwise Refinement）：

    1. まず 問題を1つの手続き として書く（詳細は仮名でよい）
    2. 各ステップを さらに小さな手続き に置き換える
    3. 同じ抽象度のステップ が並ぶレベルで止める
    printChessboard()
  ├─ printRow(row)          ← 行単位
  │    └─ printSquare(row, col)  ← マス単位
  └─ ...

    どう解決したか

    • トップダウン で関数の階層を設計でき、読み手は 必要な深さだけ 読める
    • 後の Extract Method（意味の塊で切り出す）の思想的背景になる

    向いている場面・限界

    • 限界：粒度の 物差し だけでは不十分 → SoC・SRP へ

    今の言葉での解説は メソッドの分割 にあります。

    4.4 No.4 関心の分離 — SoC（1974年）

    • 提唱：Edsger W. Dijkstra（On the Role of Scientific Thought, 1974）
    • 一言：1つの関数に 1種類の関心 だけを入れる
    • 詳細：48_原則 の「関心の分離」。42章の 関心の分離 も参考になります

    その前の課題 — 1関数に複数の関心が混在

    • saveUser() が バリデーション・DB 保存・メール送信・ログ出力 まで全部やる
    • フォーマット変更のたび DB ロジック付きの関数 を触る
    • テストで DB とメールサーバを両方モック（本物の代わりに使う偽物）する必要がある
    • 「この関数、何をする関数？」と 一言で説明できない

    何を提案したか

    関心の分離（Separation of Concerns）：異なる 変更理由 を持つ処理を、異なる関数（・モジュール）に分ける。

    ◯ 関心ごとに分離 
    // 関心ごとに分離
function validateUser(user) { /* 入力検証だけ */ }
function persistUser(user) { /* 永続化だけ */ }
function notifyUserRegistered(user) { /* 通知だけ */ }

function registerUser(user) {
  validateUser(user);
  persistUser(user);
  notifyUserRegistered(user);
}

    どう解決したか

    • 変更の 影響を関数単位 に閉じ込める
    • テストで 関心ごとにモックを分け られる
    • 後の SRP（単一責任） のメソッド版の基盤になる

    向いている場面・限界

    • 向く：オーケストレーション関数（他の関数を順に呼んで流れをまとめる関数。ここでは registerUser）と詳細関数の 役割分担
    • 限界：分けすぎると 呼び出しチェーン が長くなる → KISS・適切な粒度で調整

    今の言葉での解説は 関心の分離と単一責任 にあります。

    4.5 No.5 情報隠蔽 — 関数レベル（1972年）

    • 提唱：David L. Parnas（On the Criteria To Be Used in Decomposing Systems into Modules, 1972）
    • 一言：変更されうる詳細 を関数内部に閉じ、呼び出し側には 契約だけ 見せる
    • 詳細：43章：モジュール設計年表 の「情報隠蔽 — Parnas モジュール（1972年）」

    その前の課題 — 呼び出し側が内部を知りすぎ

    • 税計算の内部が「10% 固定」から「地域別税率」に変わるたび、呼び出し側 20か所 を修正
    • 関数が 内部表現（配列 vs Map） を返し、利用側が構造に依存
    • 「ヘルパー関数」が モジュール外に漏れ、直接呼ばれて契約化する
    • リファクタリングのたび 利用側の連鎖修正 が起きる

    何を提案したか

    観点悪い例良い例
    公開面内部用 calculateTaxRate() も export必要な操作だけ 公開
    戻り値内部データ構造をそのまま返す必要な情報だけ を返す（DTO・値）
    引数呼び出し側が内部アルゴリズム用の値を渡す意図が分かる引数 だけ

    DTO（Data Transfer Object）は、データを受け渡すためだけの入れ物のオブジェクトです。

    ◯ 税率テーブル・端数処理は関数の中に隠す 
    // 内部: 税率テーブル・端数処理は隠す
function calculateTax(amount, region) {
  const rate = lookupRate(region); // 内部詳細
  return roundTax(amount * rate);  // 内部詳細
}

    どう解決したか

    • 実装変更を 関数の内部 に閉じ込め、呼び出し側の修正を減らす
    • クラス設計の カプセル化 と同じ思想が 関数スコープ にも適用できる

    向いている場面・限界

    • 向く：アルゴリズム・フォーマット・外部 API の差し替えが予想される処理
    • 限界：何を隠すかは SoC・SRP とセットで判断

    今の言葉での解説は 情報隠蔽 にあります。

    4.6 No.6 循環的複雑度 — McCabe（1976年）

    • 提唱：Thomas J. McCabe（A Complexity Measure, 1976）
    • 一言：関数内の 分岐（if / loop / case）の数 で複雑さを測る

    その前の課題 — 複雑な関数の客観評価がない

    • 「この関数、複雑すぎでは？」が 感覚論 だけ
    • 分岐が 15個ある関数が レビューをすり抜ける
    • テストケース数と 分岐数の関係 が設計上意識されない
    • リファクタリングの 優先順位 が付けられない

    何を提案したか

    循環的複雑度（Cyclomatic Complexity）：おおよそ「独立した実行パスの数」。目安として 10以下 が読みやすく、15超 は分割を検討、という運用が広まりました。

    ✕ 複雑度が高い：分岐が多い 
    // 複雑度が高い: 分岐が多い
function process(x) {
  if (x > 0) {
    if (x < 10) { /* ... */ }
    else if (x < 100) { /* ... */ }
    else { /* ... */ }
  } else {
    /* ... */
  }
}
// → Guard Clause + 小関数への Extract で分割

    どう解決したか

    • 関数の 複雑さを数値化 し、Lint（コードを自動で検査するツール）や CI（変更のたびに自動でテスト・検査する仕組み）で検知できる
    • Guard Clause・Extract Method で分割する動機付けになる

    向いている場面・限界

    • 向く：レガシーコードの改修優先度、CI の閾値設定
    • 限界：行数は短くても ネストが深い 問題は別指標 → Guard Clause へ

    今の言葉での解説は 複雑度と分岐 にあります。

    5.1967〜1980年代：オブジェクトと契約

    オブジェクト指向の言語が広まり、メソッドが「データに結びついた操作」になりました。あわせて、メソッドの 前提を契約として明示する（DbC）、読む操作と書く操作を分ける（CQS）という考え方が Bertrand Meyer によってまとめられます。

    No.考え方時期人物・言語
    7オブジェクトのメソッド1967年〜Simula・Smalltalk・C++・Java
    8Design by Contract / Fail Fast1986〜1988年Bertrand Meyer（Eiffel）
    9CQS1988年Bertrand Meyer

    5.1 No.7 オブジェクトのメソッド（1967年〜）

    • 背景：Simula（1967）、Smalltalk（1972）、C++（1983）、Java（1995）
    • 一言：状態（フィールド）に対する操作 としてメソッドを定義する
    • 詳細：44章：クラスとオブジェクトの基本、44章：クラス設計の変遷 の「オブジェクト・クラス（1967年〜）」

    その前の課題 — データと処理の乖離（関数版）

    • updateBalance(accountId, amount) のように ID とデータが別
    • 同じ口座に触るメソッドが クラス外に散在
    • 「誰が残高を変更できるか」の ルール が呼び出し側に分散
    • 手続き名だけでは どのデータに対する操作か が不明瞭

    何を提案したか

    メソッド = オブジェクトに対するメッセージ。 状態を持つ「もの」に、振る舞いを メソッドとして結びつける。

    class BankAccount {
  #balance = 0;

  withdraw(amount) {
    if (amount > this.#balance) throw new Error('残高不足');
    this.#balance -= amount;
  }
}

    #balance の # は、JavaScript でクラスの外から触れない プライベートフィールド を表します。

    どう解決したか

    • データと操作が 同じ型の中 にあり、変更の入口が明確
    • Tell, Don't Ask の土台 — データを取り出して操作するより、オブジェクトに お願いする

    向いている場面・限界

    • 向く：状態を持つドメイン概念、不変条件（常に守られるべきルール。例：残高はマイナスにならない）を守りたい操作
    • 限界：ロジックがサービスクラスに逃げる 貧血モデル（データだけで振る舞いを持たないクラス）→ DDD・ドメインメソッドへ

    今の言葉での解説は オブジェクトのメソッド、クラス側からの説明は 44章：Tell Don't Ask と貧血モデル にあります。

    5.2 No.8 Design by Contract / Fail Fast（1986〜1988年）

    • 提唱：Bertrand Meyer（Eiffel、Object-Oriented Software Construction, 1988）
    • 一言：前提条件をメソッドの先頭で検査 し、違反は 即座に失敗 させる
    • 関連：Fail Fast（Java コミュニティ等で 1990〜2000年代に普及）

    その前の課題 — 不正な状態の先送り

    • 引数が null なのに 深い処理まで進み、原因不明の NPE（NullPointerException。null を使おうとして起きるエラー）
    • エラーを 黙って swallow（握りつぶす）し、後段で奇妙な結果だけが出る
    • バリデーションが 呼び出し側と関数内に二重 に存在
    • 「どこで壊れたか」が スタックトレース（エラーが起きるまでの呼び出し履歴）から遠い

    何を提案したか

    概念内容
    前置条件（Precondition）呼び出し側が満たすべき条件 — メソッド先頭で検査
    後置条件（Postcondition）メソッドが保証する結果
    Fail Fast異常は 早い段階 で検出し、黙って進まない
     
    function withdraw(account, amount) {
  if (!account) throw new TypeError('account is required');
  if (amount <= 0) throw new RangeError('amount must be positive');
  if (amount > account.balance) throw new Error('残高不足');
  // ここから先は前提が満たされている
  account.balance -= amount;
}

    どう解決したか

    • バグの 発見地点と原因 が近づく
    • メソッドの 契約 がコード上で明示される
    • Guard Clause と 相補関係 — 異常系を先に弾く具体技法

    向いている場面・限界

    • 向く：公開 API、ドメインルールの境界、ライブラリの入口
    • 限界：すべてを例外にすると 制御フローが読みにくい 場合も → Result 型等と使い分け

    今の言葉での解説は Design by Contract、Result 型との使い分けは null・undefined・Result型の使い分け にあります。

    5.3 No.9 CQS — Command-Query Separation（1988年）

    • 提唱：Bertrand Meyer（Object-Oriented Software Construction, 1988）
    • 一言：状態を変える（Command） と 値を返す（Query） を 同じメソッドに混ぜない

    その前の課題 — 取得メソッドが副作用を持つ

    • getUser() が DB から読むたびに lastAccessed を更新
    • findAndMarkAsRead() のように 名前は get なのに変更 する
    • 同じ Query を 2回呼ぶと結果や状態が変わる
    • テストで「読むだけ」のつもりが 副作用で DB が汚れる

    何を提案したか

    種類役割戻り値
    Command（コマンド）状態を変えるvoid（または成功／失敗のみ）
    Query（クエリ）状態を 変えず 情報を返すデータ（副作用なし）
     
    // Query: 副作用なし
function getBalance(account) {
  return account.balance;
}

// Command: 状態を変える（残高は Query で取得）
function withdraw(account, amount) {
  if (amount > account.balance) throw new Error('残高不足');
  account.balance -= amount;
}

    例外：同一オブジェクト内の lazy 初期化（初めて使うときに初めて準備する）など、副作用が局所で明白な場合は Meyer 自身も pragmatic（実用的）に許容しています。

    どう解決したか

    • メソッド名と 振る舞いの一致（get / is は Query など）
    • 参照透過性（式をその結果の値に置き換えても意味が変わらない性質）に近い Query を保ち、推論・テスト・並行処理が楽になる
    • 後の CQRS（システム全体の読み書き分離）の メソッド版 として理解できる（41章：CQRS）

    向いている場面・限界

    • 向く：ドメインモデル、リポジトリ、boolean を返す is* / has* / can*
    • 限界：「取得しつつキャッシュ更新」など 現実的な混在 もある → 命名で意図を明示

    命名の具体例は、59_AI開発ツール・コーディング規約 の「リーダブルコード」ノートにあります。今の言葉での解説は CQS にあります。

    6.1990年代：リファクタリングの時代

    既にある長い関数を 安全に直す手順 が整理された時代です。1999年には Fowler の『Refactoring』と Hunt・Thomas の『The Pragmatic Programmer』が出版され、Guard Clause・Extract Method・DRY が広く知られるようになりました。

    No.考え方時期人物・本
    10Guard Clause（早期 return）1990年代〜1999年Kent Beck ら ／ Fowler『Refactoring』
    11Extract Method・リファクタリング1999年Martin Fowler『Refactoring』
    12DRY1999年Andy Hunt, Dave Thomas『The Pragmatic Programmer』

    6.1 No.10 Guard Clause — 早期 return（1990年代〜1999年）

    • 背景：防御的プログラミングの実践、Kent Beck らの Smalltalk / XP（エクストリーム・プログラミング）文化
    • 書籍：Martin Fowler Refactoring（1999）— 「ネストした条件分岐をガード節に置き換える」
    • 一言：異常系・境界条件を先頭で return し、正常系をフラットに書く

    その前の課題 — ネストした if の深さ

    • 正常系が 4段ネスト の奥にあり、読むのにスクロールが必要
    • else 枝が 正常系と異常系 を混在させ、意図が不明
    • 新しい条件追加のたび ネストが深く なり McCabe 複雑度が上がる
    • 「この関数、結局何をしている？」が 最後まで読まないと分からない

    何を提案したか

    Guard Clause（ガード節）：前提を満たさない場合は 即 return / throw し、以降は正常系だけ。

    ✕ Before：ネストが深い 
    // Before: ネストが深い
function process(order) {
  if (order) {
    if (order.isValid()) {
      if (order.hasStock()) {
        return execute(order);
      }
    }
  }
  return null;
}
    ◯ After：Guard Clause 
    // After: Guard Clause
function process(order) {
  if (!order) return null;
  if (!order.isValid()) return null;
  if (!order.hasStock()) return null;
  return execute(order);
}

    どう解決したか

    • 正常系が一直線 に読める（Fail Fast・Design by Contract と相性が良い）
    • 複雑度と 認知負荷 を下げる
    • Extract Method と組み合わせ、ガード後のブロックを 別関数 にできる

    向いている場面・限界

    • 向く：前提チェックが多い関数、API の入口、バリデーション
    • 限界：対称的な分岐（A も B も同等に複雑）では if-else のまま の方が読みやすいことも

    今の言葉での解説は Guard Clause にあります。

    6.2 No.11 Extract Method・リファクタリング（1999年）

    • 提唱：Martin Fowler（Refactoring: Improving the Design of Existing Code, 1999）
    • 一言：長い関数から 意味のある塊 を 新しい関数に抽出 する

    その前の課題 — 100行関数・重複

    • コピペで 同じ 10行 が3関数に存在
    • 1関数が 複数の抽象度 を混在（HTTP パースと税計算）
    • コメント // --- ここから検証 --- が 関数の構造 を代弁している
    • テストしたい部分だけ 切り出せない

    何を提案したか

    Extract Method（メソッド抽出）：選択したコードを、意図が伝わる名前の関数 にする。

    ✕ 抽出前 
    // 抽出前
function printOwing(invoice) {
  printBanner();
  let outstanding = 0;
  for (const o of invoice.orders) outstanding += o.amount;
  printDetails(outstanding);
}
    ◯ 抽出後 
    // 抽出後
function printOwing(invoice) {
  printBanner();
  const outstanding = calculateOutstanding(invoice);
  printDetails(outstanding);
}

    関連するリファクタリング：Replace Temp with Query（一時変数を問い合わせ関数に置き換える）、Introduce Parameter Object（引数の塊をオブジェクト化）

    どう解決したか

    • 関数を 同じ抽象度のステップ の並びにできる（段階的詳細化の実践）
    • 重複除去の 具体手順（DRY の実装手段）
    • テスト対象を 小さく切り出せる

    向いている場面・限界

    • 向く：レガシー改修、コードレビュー後の整理
    • 限界：抽出しすぎると ジャンプだらけ → KISS・読み手の視線で調整

    詳細は 42章：テストとリファクタリング（リファクタリングの考え方）、この章では Extract Method と リファクタリングの実践 にあります。

    6.3 No.12 DRY — Don't Repeat Yourself（1999年）

    • 提唱：Andy Hunt, Dave Thomas（The Pragmatic Programmer, 1999）
    • 一言：同じ知識 を複数のメソッドに書かない
    • 詳細：48_原則 の「DRY・KISS・YAGNI（DRY原則）」、この章では KISS・DRY・YAGNI

    その前の課題 — 関数間のロジック重複

    • 税率計算が 5関数 にコピペされ、税率変更で 5か所修正
    • 「たまたま同じコード」なのに共通化し、変更理由の違う 関数が結合
    • ヘルパーを作らず コピペ する方が早い短期文化

    何を提案したか

    DRY：重複しているのは コードの見た目 ではなく 知識（意図・ルール） かを見る。

    • 同じ知識 → 1つの関数 に集約
    • 知識が違う → 分離を維持（SRP と衝突するときは SRP 優先）

    どう解決したか

    • 変更を 1関数に集約 し、修正漏れを減らす
    • Extract Method とセットで 実践的な重複除去

    向いている場面・限界

    • 向く：ビジネスルール、フォーマット、定数計算
    • 限界：偶然の一致を DRY すると 結合が増える → 48_原則 の「DRY・YAGNI原則の落とし穴と実践的判断」

    7.2000年代：原則の統合と純粋関数の再注目

    それまでの考え方が 原則（SRP）やルール集（Clean Code） としてまとめられ、同時に、関数型プログラミングの 純粋関数 が JavaScript や Java など主流の言語に入ってきた時代です。

    No.考え方時期人物・本
    13SRP（メソッド版）2000年代初頭Robert C. Martin（SOLID）
    14Clean Code の関数ルール2008年Robert C. Martin『Clean Code』
    15純粋関数・副作用の分離1950年代起源、2000年代再注目Lisp・Haskell・各言語の関数型機能

    7.1 No.13 SRP — メソッド版・単一責任（2000年代初頭）

    • 提唱：Robert C. Martin（SOLID、Agile Software Development, 2002 前後）
    • 一言：1メソッドは1つの責任（変更理由） だけ
    • 詳細：48_原則 の「SRP（単一責任の原則）」。クラス単位の説明は 44章：単一責任の原則

    その前の課題 — 巨大メソッド・変更理由の混線

    • handleRequest() が 認証・パース・DB・レスポンス生成 まで 200行
    • ログ形式変更で DB コードに触る 必要がある
    • メソッド名が process() doIt() で 何をするか不明
    • 単体テストが シナリオテスト1本 しか書けない

    何を提案したか

    メソッドレベルの SRP：

    • メソッド名で 1文で説明 できること
    • 1つの抽象度 だけを扱うこと
    • 変更理由が複数なら 分割 する
    ✕ 責任が混在 
    // 責任が混在
function handleRequest(req) {
  /* 認証 + バリデーション + 永続化 + ログ + レスポンス */
}
    ◯ 責任ごとに分割 
    // 責任ごとに分割
function handleRequest(req) {
  const user = authenticate(req);
  const command = parseCommand(req);
  validate(command);
  const result = execute(command, user);
  return formatResponse(result);
}

    どう解決したか

    • SoC を メソッド粒度 で具体化
    • Clean Code の「関数は1つのことだけ」につながる

    向いている場面・限界

    • 向く：サービスクラス、ユースケース関数、HTTP ハンドラ
    • 限界：分けすぎは オーケストレーション関数 が増える → 許容範囲内でバランス

    今の言葉での解説は 関心の分離と単一責任 にあります。

    7.2 No.14 Clean Code の関数ルール（2008年）

    • 提唱：Robert C. Martin（Clean Code, 2008）
    • 一言：小さく・少引数・意図が伝わる命名・副作用を抑える

    その前の課題 — 読めない関数・引数地獄

    • 関数が 50行超、変数宣言だけで画面を占める
    • 引数が 7個 あり、呼び出し時に 順番を間違える
    • getX() が 副作用 でログ出力・キャッシュ更新
    • 関数名が handleData processItem で検索しても特定できない

    何を提案したか

    ルール目安
    サイズ短く。20行以内が目安（長ければ Extract）
    抽象度1関数 = 1抽象度。renderPage() の中に HTML 文字列連結を直書きしない
    引数0〜2 が理想、3以上は Parameter Object を検討
    命名動詞 + 目的語。boolean は is / has / can
    副作用Query 風の関数に 隠れ副作用 を入れない（CQS と一致）
    エラー例外より try-catch だらけ を避け、Guard + Fail Fast
    ✕ 引数が多い 
    // 引数が多い → Parameter Object
function createUser(name, email, age, role, department, managerId) { /* ... */ }
    ◯ Parameter Object にまとめる 
    function createUser(params) {
  validateCreateUserParams(params);
  return buildUser(params);
}

    どう解決したか

    • メソッド設計の 実践チェックリスト として広く使われる
    • CQS・SRP・Guard Clause・Extract Method を 1冊に統合

    向いている場面・限界

    • 向く：コードレビュー、新規コードのスタイル基準
    • 限界：行数だけのルールは 文脈を無視 しうる → 意図と抽象度を優先

    命名については 59_AI開発ツール・コーディング規約 の「命名規則」「リーダブルコード」ノート、この章では 命名・引数の設計・サイズと抽象度、ルールの一覧は ルール早見表とリファクタリング技法 にあります。

    7.3 No.15 純粋関数・副作用の分離（1950年代起源、2000年代再注目）

    • 背景：Lisp（1958）、Haskell（1990）、JavaScript / Java への関数型機能取り込み（2000年代〜）
    • 一言：同じ入力 → 同じ出力、外部状態を変えない 関数を核に
    • 詳細：42章：ソフトウェア設計年表 の「関数型指向（1950年代に起源、2000年代以降に再注目）」

    その前の課題 — テスト困難・状態競合

    • 同じ引数なのに 呼ぶタイミングで結果が変わる（グローバル変数・DB 参照）
    • ログ・DB・API が 1関数に混在 し、モック地獄
    • 並行実行で 同じ関数が状態を壊し合う
    • 「この関数、何に依存している？」が 読みきれない

    何を提案したか

    純粋関数（Pure Function）：

    • 引数以外の 外部状態を読まない
    • 外部状態を書き換えない（副作用なし）
    • 同じ入力に 常に同じ出力
    ✕ 非純粋：外部の taxRate に依存 
    // 非純粋: 外部の taxRate に依存
let taxRate = 0.1;
function calcTax(amount) {
  return amount * taxRate;
}
    ◯ 純粋：依存を引数で明示 
    // 純粋: 依存を引数で明示
function calcTax(amount, rate) {
  return amount * rate;
}

    副作用を減らす 実践：

    • 計算・変換・検証は 純粋関数 に
    • I/O は 境界 に押し出す（次の FCIS）

    どう解決したか

    • ユニットテスト が入力と出力だけで完結
    • 並行処理 でロックが不要になりうる
    • CQS の Query を より厳密 に実践できる

    向いている場面・限界

    • 向く：料金計算、バリデーション、データ変換、ドメインルール
    • 限界：現実の I/O は副作用 → どこで許容するか を設計（FCIS）

    今の言葉での解説は 純粋関数と副作用、パラダイムとしての説明は 42章：関数型と純粋関数 にあります。

    8.2010年代：Functional Core, Imperative Shell

    8.1 No.16 Functional Core, Imperative Shell（2010年代）

    • 背景：Gary Bernhardt（Boundaries, 2012）、関数型コミュニティの実践知
    • 一言：中心は純粋関数（Functional Core）、外側だけ I/O（Imperative Shell）

    その前の課題 — 副作用とロジックの混在

    • 「少しだけ DB 読む」関数が ドメイン計算の真ん中 にある
    • 純粋にしようとして モナド（関数型で副作用などを包んで扱う仕組み）だらけになり、チームが追いつかない
    • テストしたい 計算部分 を切り出す 境界 が設計されていない

    何を提案したか

    // Shell: I/O
async function createOrderHandler(req) {
  const input = parseRequest(req);
  const order = buildOrder(input);       // Core（純粋）
  await repository.save(order);          // Shell
  return formatResponse(order);
}

// Core: 純粋
function buildOrder(input) {
  validateItems(input.items);
  return { items: input.items, total: calculateTotal(input.items) };
}

    どう解決したか

    • 純粋関数のメリット を、現実的な I/O ありシステムで取り込める
    • メソッド設計の 最新の落とし所 — OOP のメソッドと FP（関数型プログラミング）の関数を 役割で使い分け

    向いている場面・限界

    • 向く：ユースケース層、ドメインサービスとリポジトリの境界
    • 限界：小さな CRUD（作成・読み取り・更新・削除だけ）のアプリでは 層が過剰 になりうる → KISS

    今の言葉での解説は Functional Core, Imperative Shell にあります。

    9.3 初心者が覚えておくとよいこと

    1. 分割が最初。 構造化（No.1）と Extract Method（No.11）— 長い関数は必ず疑う。
    2. 正常系を浅く。 Guard Clause（No.10）+ Fail Fast（No.8）— 異常系を先に弾く。
    3. 読むと書くを分ける。 CQS（No.9）— get / is に副作用を入れない。
    4. 計算は純粋に。 副作用（No.15）— テストが一気に楽になる。
    5. 物差しは複数。 KISS vs DRY vs SRP は 矛盾することがある → 変更理由 で判断。

    9.4 学習順 vs 歴史順

    観点おすすめ順理由
    歴史（このページ）構造化 → … → FCIS課題が なぜ生まれたか が分かる
    学習Extract Method → Guard Clause → CQS → SRP → 純粋関数すぐ書ける技法 から入ると効果が見えやすい

    教材の順に学ぶ場合の道順は メソッド設計の全体像 の学習順インデックスにまとめています。

    10.よくある誤解

    誤解1：「新しい考え方が出たら、古い考え方は不要になる」

    歴史は置き換えではなく 積み重ね です。FCIS を使うときも、関数への分割（No.1）、Guard Clause（No.10）、CQS（No.9）はそのまま使います。各項目の「限界」を次の項目が 補っている と考えましょう。

    誤解2：「年表の順番どおりに学ばないと理解できない」

    歴史順は「なぜ生まれたか」を知るのに役立ちますが、学習には すぐ書ける技法から入る 順（Extract Method → Guard Clause → CQS → SRP → 純粋関数）もおすすめです（学習順 vs 歴史順）。

    誤解3：「原則どうしは矛盾しない。全部守ればよい」

    KISS・DRY・SRP は 矛盾することがあります。たとえば DRY で共通化すると、変更理由の違う関数が結合して SRP に反することがあります。そのときは 変更理由 で判断し、知識が違うなら分離を維持します（No.12 DRY の「SRP と衝突するときは SRP 優先」）。

    11.まとめ

    • メソッド設計は、最も小さい実行単位である関数・メソッドを 読みやすく・テストしやすく・変更しやすく 整えること
    • 1940〜1950年代の main + goto の困りごとから、1960〜1970年代に 構造化・段階的詳細化・関心の分離・情報隠蔽・循環的複雑度 が生まれた
    • 1967〜1980年代には オブジェクトのメソッド と、Meyer の Design by Contract・CQS が加わった
    • 1990年代は Guard Clause・Extract Method・DRY による「直し方」の時代、2000年代は SRP・Clean Code による統合と 純粋関数 の再注目
    • 2010年代の Functional Core, Imperative Shell が、OOP のメソッドと FP の関数を役割で使い分ける現在の落とし所
    • 原則どうしが矛盾したら 変更理由 で判断する
