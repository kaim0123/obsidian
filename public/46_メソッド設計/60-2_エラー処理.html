    60 契約とエラー

    エラー処理 — 例外の使い分けと try-catch の置き場所

    エラー処理は、書き方しだいで正常系の流れを埋もれさせてしまいます。このページでは、例外を使う場面と使わない場面、try-catch だらけを避けて境界でまとめる方法、分かりやすいエラーメッセージと Fail Fast、null / undefined の扱い、そして複雑なエラー処理を Extract Method で整理する方法を学びます。

    もとにしたノート：02_エラー処理

    ひとことで言うと

    例外は契約違反、想定内の失敗は Result 型 で表します。try-catch は各所に散らさず 境界（Shell）で1回 にまとめ、Core は例外をそのまま上げます。失敗させるときは 何が・なぜ 失敗したかが分かるメッセージを付けます。

    1.このページで扱うこと

    メソッド設計における エラー処理 の書き方を学びます。

    • 例外を使う場面と使わない場面
    • try-catch だらけを避ける（境界に集約する）
    • エラーメッセージと Fail Fast
    • null / undefined の扱い
    • エラー処理の Extract Method

    Web API として外部にエラーをどう返すか（ステータスコードやエラーレスポンスの形）は 45章：エラー設計 で扱っています。

    2.例外を使う場面と使わない場面

    例外を使う例外を使わない
    契約違反（前提条件の破れ）想定内の失敗（バリデーション）
    回復不能なエラー呼び出し側が分岐したい場合
    プログラムのバグパフォーマンスクリティカルなループ内

    パフォーマンスクリティカル とは、速度がとくに重要な部分のことです。例外を投げる処理は通常の return より重いため、何度も回るループの中では避けます。

    ◯ 想定内 → Result 型 
    function parsePort(input) {
  const n = Number(input);
  if (n < 1 || n > 65535) return { ok: false, error: 'invalid port' };
  return { ok: true, value: n };
}
    ◯ 契約違反 → 例外 
    function divide(a, b) {
  if (b === 0) throw new Error('division by zero');
  return a / b;
}

    詳細は Design by Contract を参照してください。

    3.try-catch だらけを避ける

    try-catch を各所に書く と、正常系が読めなくなります。

    ✕ 悪い例：try-catch だらけ 
    function process(order) {
  try {
    validate(order);
  } catch (e) { log(e); return; }
  try {
    save(order);
  } catch (e) { log(e); return; }
}
    ◯ 良い例：境界でまとめる 
    function process(order) {
  validate(order);
  save(order);
}

// 呼び出し側（Shell）で 1 回 catch
try {
  process(order);
} catch (e) {
  handleError(e);
}

    エラー処理は境界（Shell）に集約 し、Core は例外をそのまま上げます（→ Functional Core, Imperative Shell）。Core は計算や業務ルールを担う内側の部分、Shell は入出力や外部とのやり取りを担う外側の部分です。

    4.エラーメッセージと Fail Fast

    Fail Fast — 不正を早く検出し、分かりやすいメッセージ で失敗させます。

    function withdraw(account, amount) {
  if (amount <= 0) {
    throw new Error(`amount must be positive, got ${amount}`);
  }
  if (amount > account.balance) {
    throw new Error(`insufficient funds: balance=${account.balance}, requested=${amount}`);
  }
  account.balance -= amount;
}

    何が・なぜ 失敗したかが分かるメッセージを付けます。上の例では、実際に渡された値（got ${amount}）や残高と要求額を含めているので、ログを見ただけで原因が分かります。

    5.null / undefined の扱い

    値があるかどうかのチェックがコードのあちこちに広がり、読みにくくなる状態を null 地獄 と呼びます。これを避ける技法です。

    手法例
    Guard Clauseif (!user) return null;
    Optional 型Option<User> で明示
    デフォルト値name ?? 'unknown'
    早期 throw必須なら throw

    Optional 型 は「値があるかもしれないし、ないかもしれない」ことを型で表すものです。??（Null 合体演算子）は、左側が null か undefined のときだけ右側の値を使います。

    ✕ 悪い例：null チェックが各所に 
    function getName(user) {
  if (user && user.profile && user.profile.name) {
    return user.profile.name;
  }
  return 'unknown';
}
    ◯ 良い例：構造を保証するか、Guard で入口に集約 
    function getName(user) {
  if (!user?.profile?.name) return 'unknown';
  return user.profile.name;
}

    TypeScript での体系的な整理は null・undefined・Result型の使い分け で扱います。

    6.エラー処理の Extract Method

    複雑なエラー処理は Extract Method（処理の一部を名前の付いたメソッドに切り出すこと）で名前を付けます。

    function handleRequest(req) {
  try {
    processRequest(req);
  } catch (e) {
    return buildErrorResponse(e);
  }
}

function buildErrorResponse(error) {
  if (error instanceof ValidationError) {
    return { status: 400, message: error.message };
  }
  if (error instanceof NotFoundError) {
    return { status: 404, message: error.message };
  }
  return { status: 500, message: 'Internal error' };
}

    エラー種別ごとの分岐も、1 関数 1 責任 で分割できます。handleRequest は「処理して、失敗したら応答を作る」流れだけを、buildErrorResponse は「エラーの種類を HTTP ステータスに変換する」ことだけを担います。

    7.よくある誤解

    誤解1：「try-catch はこまめに書くほど安全」

    逆効果になりやすいです。 各所で catch してログを出して return すると、正常系が読みにくくなるうえ、呼ぶ側は失敗したことに気づけません。境界（Shell）で1回まとめて処理する方が、読みやすく漏れもありません。

    誤解2：「エラーメッセージは短く『エラー』とだけ出せば十分」

    不十分です。 「何が・なぜ」失敗したか、実際の値は何だったかを含めると、原因の調査がずっと早くなります。

    誤解3：「null チェックは使う場所ごとに書くもの」

    入口に集めます。 Guard Clause・デフォルト値・Optional 型などで、チェックを1か所にまとめるか、そもそも null が来ない構造を保証します。

    8.まとめ

    • 例外 = 契約違反。想定内は Result 型
    • try-catch は境界に集約。Core はシンプルに
    • Fail Fast + 分かりやすいメッセージ
    • null は Guard・Optional・デフォルトで整理
