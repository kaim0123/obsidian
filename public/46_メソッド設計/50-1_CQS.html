    50 副作用と状態

    CQS — コマンドとクエリの分離

    getUser() を呼んだだけなのに、ログが書かれ、キャッシュが更新され、データまで変わっていた――そんなメソッドは、呼ぶ側が安心して使えません。このページでは、状態を変える操作（コマンド）と値を返す操作（クエリ）を分ける原則 CQS（Command-Query Separation） を学びます。getter 系に副作用を入れない理由、副作用を持つ取得メソッドの典型例、実務上の例外、システム版である CQRS との関係まで扱います。

    もとにしたノート：01_CQS

    ひとことで言うと

    メソッドを Command（状態を変える・戻り値なし） と Query（値を返す・副作用なし） に分けます。とくに get / is / has / can で始まるメソッドには副作用を入れません。lazy 初期化のような例外は getOrCreate() のように 名前で明示 します。

    1.このページで扱うこと

    CQS（Command-Query Separation：コマンドとクエリの分離） は、状態を変える操作と値を返す操作を分ける原則です。

    • Command（状態を変える）と Query（値を返す）
    • get / is / has / can に副作用を入れない
    • 取得メソッドが副作用を持つ典型例
    • CQS の pragmatic（実用本位）な例外（lazy 初期化など）
    • CQRS との関係（メソッド版とシステム版）

    副作用 とは、値を返す以外に、外の状態を変えること（変数やオブジェクトの書き換え、DB への書き込み、ログ出力など）です。副作用そのものは次のページ 純粋関数と副作用 で詳しく扱います。

    2.Command（状態を変える）と Query（値を返す）

    Bertrand Meyer（1988）が提唱した CQS は、メソッドを 2 種類に分類します。

    種類役割戻り値
    Command（コマンド）状態を変えるなし（void）
    Query（クエリ）値を返すあり
     
    // Command: 副作用あり、戻り値なし
function activateUser(user) {
  user.isActive = true;
}

// Query: 副作用なし、値を返す
function isActive(user) {
  return user.isActive;
}

    原則

    Query は 副作用を持たない。Command は 戻り値を返さない（厳密な解釈）。

    Meyer はこれを「質問をしても答えが変わってはいけない」とたとえています。Query を何回呼んでも状態が変わらなければ、呼ぶ側は順番や回数を気にせず使えます。

    3.get / is / has / can に副作用を入れない

    getter（値を取り出すためのメソッド）系に 副作用 があると、呼び出し側が予測できません。

    ✕ 悪い例：getter が副作用を持つ 
    function getUser(id) {
  logger.info(`accessed user ${id}`);  // 副作用
  cache.touch(id);                      // 副作用
  return db.findUser(id);
}
    ◯ 良い例：Query は純粋に 
    function getUser(id) {
  return db.findUser(id);
}
// ログは呼び出し側または別レイヤーで

    is / has / can / should も同様に 副作用なし が原則です。名前の付け方は 命名 も参照してください。

    4.取得メソッドが副作用を持つ典型例

    アンチパターン問題
    Lazy 初期化で getter が生成初回アクセスで DB 書き込み
    getter 内でキャッシュ更新読むたびに状態が変わる
    getter 内でログ・メトリクステストで副作用をモックする必要

    Lazy 初期化（遅延初期化）は、最初に必要になったときに初めて値を作る方法です。メトリクス は処理回数や時間などの計測値、モック はテストで本物の代わりに使う偽物のオブジェクトです。

    ✕ 問題：getTotal() が内部状態を更新 
    function getTotal(order) {
  order.lastAccessed = Date.now();  // 副作用
  return order.cachedTotal;
}

    5.CQS の pragmatic な例外（lazy 初期化など）

    実務では 厳密な CQS が難しい場面があります。

    例外理由対処
    Lazy 初期化初回だけ生成getOrCreate() 等、意図を名前で明示
    キャッシュパフォーマンス更新は Command に分離
    Fluent APIbuilder.build()チームで例外として文書化

    Fluent API は、builder.setA(1).setB(2).build() のように、メソッドが自分自身を返して呼び出しを鎖のようにつなげる書き方です。状態を変えつつ値（自分自身）を返すので、厳密な CQS からは外れます。

    ◯ 例外を明示する命名 
    function getOrInitializeConfig() {
  if (!this._config) this._config = loadConfig();
  return this._config;
}

    6.CQRS との関係（メソッド版 vs システム版）

    概念スコープ内容
    CQSメソッド・クラス読むと書くを分ける
    CQRSシステム・アーキテクチャ読み取りモデルと書き込みモデルを分離

    CQS は 1 メソッドの設計原則、CQRS（Command Query Responsibility Segregation）は システム全体のパターン です。メソッドで CQS を守ると、CQRS への移行も容易になります。CQRS の詳細は 41章：CQRS を参照してください。

    7.よくある誤解

    誤解1：「CQS と CQRS は同じもの」

    スコープが違います。 CQS は1つのメソッドを「変える」か「返す」かに分ける設計原則、CQRS はシステム全体で読み取りモデルと書き込みモデルを分けるアーキテクチャのパターンです。

    誤解2：「ログを書くくらいなら getter に入れても問題ない」

    問題になります。 読むだけのつもりで呼んだメソッドが外の世界を変えると、呼び出し側が予測できず、テストでもログやメトリクスをモックする必要が出ます。ログは呼び出し側か別のレイヤーで書きます。

    誤解3：「CQS は例外なく厳密に守らなければならない」

    実務では例外があります。 lazy 初期化・キャッシュ・Fluent API などです。大切なのは、getOrCreate() のように 名前で意図を明示 したり、チームで例外として文書化したりして、呼ぶ側を驚かせないことです。

    8.まとめ

    • CQS ＝ Command（変更）と Query（取得）を分離
    • getter 系に副作用を入れない
    • Lazy 初期化等は pragmatic な例外として名前で明示
    • CQRS はシステム版、CQS はメソッド版
