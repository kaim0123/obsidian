    10 メソッドの基礎

    メソッド設計を学ぶ理由 — いちばん細かい単位が読めないと、全体も読めない

    なぜメソッド設計を学ぶのでしょうか。このページでは、クラス設計・モジュール設計との違い、巨大な main から関数へ分割する理由、メソッド設計が解決する問題、この章の読み方と前提知識、そして今日からできる最初の一歩を説明します。

    もとにしたノート：01_メソッド設計を学ぶ理由

    ひとことで言うと

    メソッド設計は、設計の階層の中で 最も細かい実行単位（関数・メソッドの中身）を扱います。クラスやモジュールの設計が良くても、中のメソッドが 500 行なら読めません。読めない・テストできない・変更が怖い という問題の多くは、メソッドの 構造の問題 で、技法で改善できます。

    2.クラス設計・モジュール設計との違い

    設計には 階層 があります。メソッド設計は、その中で 最も細かい実行単位 を扱います。メソッド は、クラスに属する関数のことです。

    階層比喩扱うもの
    モジュール設計部屋の役割分担パッケージ・レイヤー
    クラス設計家具の配置型・オブジェクト・関係
    メソッド設計家具の細部関数・メソッドの中身

    たとえば注文システムで考えると、それぞれの設計は次のようなことを決めます。

    • モジュール設計：order/ と billing/ を分ける
    • クラス設計：Order クラスと OrderRepository を設計する
    • メソッド設計：calculateTotal() が何行で、何を引数に取るかを決める

    クラスやモジュールの設計が良くても、中のメソッドが 500 行 なら読めません。上の階層については 44章：クラス設計の全体像・43章：モジュール設計 目次 を参照してください。

    3.巨大な main から関数へ — なぜ分割するのか

    初期のプログラムは、main（プログラムの最初に実行される関数）にすべてを直書きするスタイルが一般的でした。

    ✕ 悪い例：すべてが main に入っている 
    // 悪い例: すべてが main に入っている
function main() {
  // 入力 50 行
  // 検証 80 行
  // 計算 100 行
  // DB 保存 60 行
  // メール送信 40 行
}

    分割する理由 は次のとおりです。

    読める

    名前付きの塊で意図が伝わる

    直せる

    変更箇所を見積もれる

    試せる

    部品単位でテストできる

    再利用できる

    同じ処理をコピペしない

    関数への分割は、すべてのメソッド設計の 出発点 です（関数とメソッドの基本）。

    4.メソッド設計が解決する問題

    メソッド設計を意識しないと、次の問題が起きやすくなります。

    問題症状
    読めない100 行関数で何をしているか分からない
    テストできないDB と UI を両方起動しないと検証できない
    変更が怖い1 行直すと想定外の場所が壊れる

    設計を意識しないメソッドは、次のような形に育ち、最後には「変更が怖い」「書いた人しか直せない」状態になります。

    ここで、神メソッド は何でもやってしまう巨大なメソッド、副作用 は戻り値を返す以外に外の状態を変えること（DB 保存・ログ出力など）、属人化 は特定の人しか分からない・直せない状態のことです。

    これらは 構造の問題 です。Extract Method（意味の塊を別の関数に切り出す）・Guard Clause（異常系を先に return する）・CQS（読む操作と書く操作を分ける）などの技法で、かなりの部分は改善できます。

    5.この章の読み方と前提知識

    5.1 前提知識

    • 変数・関数・条件分岐・ループが書ける
    • 小さなプログラム（数十〜数百行）を書いた経験がある

    Guard Clause や CQS の 事前知識は不要 です。

    5.2 読み方

    もとになった教材は8部構成です。次の順に進むと、「なぜ」から始めて実践・定着・統合へと進めます（各部のページは 学習順インデックス にまとめています）。

    1. 第1〜2部 で「なぜ」「何を目指すか」を掴む（このページ・関数とメソッドの基本・メソッドの分割 など）
    2. 第3〜4部 で分割・抽出と制御フローの実践スキル（Extract Method・Guard Clause など）
    3. 第5〜6部 で副作用・命名・読みやすさの定着（CQS・命名 など）
    4. 第7〜8部 でテスト・演習で統合する（テストしやすいメソッド設計・ケーススタディ など）

    歴史順で学びたい場合

    メソッド設計の変遷（西暦順の整理）を併読してください。

    6.最初の一歩 — 今日からできること

    メソッド設計は 明日から 実践できます。

    1. 50 行超の関数を1つ見つける
    2. コメント // --- で区切られた塊を数える
    3. 塊ごとに「動詞 + 目的語」の名前を考える
    4. 次のリファクタリング機会に Extract Method を試す

    リファクタリング とは、外から見た動きを変えずにコードの中身を整えることです。完璧を目指す必要はありません。1関数を 10 行短くする だけでも、読み手への配慮になります。

    7.よくある誤解

    誤解1：「クラスやモジュールをきちんと設計すれば、メソッドの中身は多少雑でもよい」

    上の階層の設計が良くても、中のメソッドが 500 行 なら読めません。実際に処理が書かれ、読まれ、直されるのはメソッドの中です。メソッド設計は「家具の細部」にあたり、ここが雑だと使い勝手が悪くなります。

    誤解2：「メソッド設計は、Guard Clause や CQS などの専門知識がないと始められない」

    前提は、変数・関数・条件分岐・ループが書けることと、小さなプログラムを書いた経験だけです。Guard Clause や CQS の 事前知識は不要 で、最初の一歩 のように、長い関数を見つけて塊に名前を付けるところから始められます。

    誤解3：「読めない・テストできないのは、書いた人の能力の問題だ」

    多くは 構造の問題 です。巨大関数・深いネスト・副作用だらけといった形が原因で、Extract Method・Guard Clause・CQS などの技法でかなりの部分を改善できます。

    8.まとめ

    • メソッド設計は クラスの中身 — 関数・メソッドの粒度と読みやすさを扱う
    • 分割は、読める・直せる・試せる・再利用できるコードのための第一歩
    • 読めない・テストできない・変更が怖い — これらはメソッド設計で改善できる
    • この教材は技法から学べる構成。プログラミングの基礎があれば読める
