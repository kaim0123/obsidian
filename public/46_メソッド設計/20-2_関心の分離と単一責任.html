    20 責務と分割

    関心の分離と単一責任（SoC / SRP）

    「1メソッド1種類の仕事」を実現するための原則を学ぶページです。関心の分離（SoC）と単一責任の原則（SRP）を関数・メソッドのレベルで捉え、流れを組み立てるオーケストレーション関数と1つの仕事をする詳細関数の役割分担、そして名前で責任を表すコツを押さえます。

    もとにしたノート：02_関心の分離と単一責任

    ひとことで言うと

    目的の異なる処理（検証・計算・保存・通知…）は 別の関数 に分け、1つのメソッドが持つ 変更理由は1つ にします。上位の関数は流れを組み立てるだけにし、詳細は下位の関数に任せます。

    1.このページで扱うこと

    1メソッド1種類の仕事 を実現する原則を学びます。

    • 関心の分離（SoC） — 1関数1種類の仕事
    • 単一責任の原則（SRP） のメソッド版 — 1メソッド1責任
    • オーケストレーション関数 と 詳細関数 の役割分担
    • process() handleData() 問題 — 名前で責任を表す

    2.関心の分離（SoC）— 1関数1種類の仕事

    関心の分離（Separation of Concerns, SoC） とは、目的の異なる処理を 別の関数 に分ける原則です（Edsger W. Dijkstra, 1974）。ここでいう 関心 とは、「検証」「保存」「通知」のような処理の目的のことです。

    ✕ 悪い例：関心が混在 
    // 悪い例: 関心が混在
function saveUser(user) {
  if (!user.email) throw new Error('invalid');  // 検証
  db.insert(user);                               // 永続化
  sendWelcomeEmail(user);                        // 通知
  logger.info('saved');                          // ログ
}
    ◯ 良い例：関心ごとに分離 
    // 良い例: 関心ごとに分離
function validateUser(user) { /* 検証だけ */ }
function persistUser(user) { /* 保存だけ */ }
function notifyNewUser(user) { /* 通知だけ */ }

    永続化 とは、データベースなどにデータを保存し、プログラムが終わっても残るようにすることです。ソフトウェア設計全体での SoC は 42章：関心の分離 を参照してください。ここでは 関数レベル に焦点を当てます。

    3.単一責任の原則 — メソッド版（1メソッド1責任）

    単一責任の原則（Single Responsibility Principle, SRP） は、クラス版で広く知られていますが、メソッドにも適用 できます。

    1メソッドは 1つの変更理由 だけを持つべき

    変更理由分離先
    入力形式の変更validate()
    計算ルールの変更calculateTotal()
    保存方式の変更save()

    クラス設計での SRP は 44章：単一責任の原則（44 クラス設計）で詳述しています。

    4.オーケストレーション関数と詳細関数の役割分担

    オーケストレーション関数 は流れを組み立て、詳細関数 は1つの仕事を実行します。オーケストレーション（orchestration）はもともと「管弦楽の編曲」の意味で、ここでは各処理を順に呼び出して全体をまとめる役割を指します。

    // オーケストレーション: 流れの目次
function registerUser(user) {
  validateUser(user);
  const hashed = hashPassword(user.password);
  persistUser({ ...user, password: hashed });
  notifyNewUser(user);
}

// 詳細: 1 つの関心
function hashPassword(plain) { /* ... */ }

    オーケストレーション関数は 短く・同じ抽象度 に保ち、詳細は下位関数に 委譲（仕事を任せること）します。

    5.process() handleData() 問題 — 名前で責任を表す

    曖昧な名前 は、責任が不明確なサインです。

    悪い例良い例
    process()calculateInvoiceTotal()
    handleData()parseCsvRows()
    doStuff()sendOrderConfirmationEmail()

    「この関数、何をする関数？」と 一言で説明できる 名前を付けます（命名）。

    6.メソッド設計のチェックリスト

    • ☐ このメソッドは 1種類の関心 だけを扱っているか
    • ☐ 変更理由 を1つに言えるか
    • ☐ オーケストレーションと詳細が 分かれている か
    • ☐ 名前が 動詞 + 目的語 で意図を表しているか
    • ☐ テストで モック（本物の DB やメール送信の代わりに使う偽物の部品）が最小限で済むか

    総合版は チェックリストとアンチパターン を参照してください。

    7.演習 — 関心のラベル付け

    次の関数の行に 関心ラベル（検証 / 計算 / 保存 / 通知）を付けてください。

    function registerUser(user) {
  if (!user.email) throw new Error('email required');
  const hash = bcrypt.hash(user.password);
  db.insert({ ...user, password: hash });
  mailer.sendWelcome(user.email);
}

    期待する分割：

    function registerUser(user) {
  validateUser(user);
  const hashed = hashPassword(user.password);
  persistUser({ ...user, password: hashed });
  notifyNewUser(user.email);
}

    8.よくある誤解

    誤解1：「SRP はクラスだけの原則」

    メソッドにも適用できます。 「1メソッド1変更理由」と置き換えると、メソッドを分ける判断基準になります。

    誤解2：「分けた関数を呼ぶだけの関数は無駄」

    流れを組み立てる オーケストレーション関数 は、処理の目次として読み手の助けになります。短く・同じ抽象度に保つことが大事です。

    誤解3：「名前は後で直せばよい」

    process() のような曖昧な名前しか付けられないのは、責任が不明確なサイン です。名前を考えることが、そのまま責任を見直すきっかけになります。

    9.まとめ

    • SoC = 目的の異なる処理を別関数に分ける
    • SRP（メソッド版）= 1メソッド1変更理由
    • オーケストレーションは流れ、詳細は下位関数
    • process() 問題は名前で責任を明確にする
