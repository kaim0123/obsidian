    90 付録

    参考図解 — メソッド設計の主要概念を図で見渡す

    メソッド設計の主要な概念を図解で整理した参考ページです。Functional Core, Imperative Shell、抽象度の階層、Guard Clause の Before / After、CQS の Command と Query、設計の階層の中でのメソッド設計の位置づけ、の 5 つを、それぞれ詳しく説明しているページへのリンクと一緒に並べています。復習や、レビューで考え方を説明したいときに使ってください。

    もとにしたノート：付録F_参考図解

    ひとことで言うと

    メソッド設計の図はどれも「分けて、そろえる」を表しています。副作用のある処理と純粋な計算を分け（FCIS）、読む操作と書く操作を分け（CQS）、1 つの関数の中ではステップの抽象度をそろえ、異常系は先に弾いて正常系を浅い位置にそろえます（Guard Clause）。

    1.このページで扱うこと

    • Functional Core, Imperative Shell（FCIS）：純粋関数の核と、副作用を受け持つ外側の殻
    • 抽象度の階層：オーケストレーション関数から詳細関数まで
    • Guard Clause の Before / After：ネストと早期 return の形の違い
    • CQS — Command と Query：書く操作と読む操作の違い
    • 設計の階層での位置づけ：モジュール設計・クラス設計・メソッド設計・コーディング規約

    使い方

    図はどれも考え方を思い出すための手がかりです。意味があいまいなときは、各図の上にあるリンク先のページを読み直してください。

    2.Functional Core, Imperative Shell（FCIS）

    計算・判定などの純粋関数（同じ入力なら同じ出力を返し、副作用がない関数）を内側の Functional Core に集め、DB の読み書きやメール送信などの副作用（戻り値以外に外部へ与える影響）は外側の Imperative Shell に置きます。Shell が外からデータを読み込んで Core に渡し、Core が返した結果を Shell が外へ書き出します（→ Functional Core, Imperative Shell）。

    3.抽象度の階層

    一番上の processOrder() は、手順を並べて他の関数を呼ぶだけのオーケストレーション関数です。下に行くほど「どうやるか」の細かい処理（詳細）になります（→ メソッドの分割、サイズと抽象度）。

    原則

    同じ関数内のステップは同じ抽象度。processOrder() の中に validateOrder() と並んで「価格を 1 件ずつ足すループ」が直接書かれていたら、抽象度がずれています。

    4.Guard Clause Before / After

    条件を満たさない場合（異常系）を先に return で弾くと、正常系がネストの奥から浅い位置に出てきます（→ Guard Clause）。

    ✕ Before（ネスト） 
    if (A) {
  if (B) {
    if (C) {
      → 正常系（深い）
    }
  }
}
    ◯ After（Guard Clause） 
    if (!A) return;
if (!B) return;
if (!C) return;
→ 正常系（浅い）

    5.CQS — Command と Query

    CQS（Command-Query Separation）は、メソッドを「状態を変える Command（書く）」と「値を返す Query（読む）」のどちらか一方にする原則です（→ CQS）。

    Command（書く）

    • submitOrder()
    • saveUser()
    • activateAccount()

    副作用 OK
    戻り値 void が多い

    Query（読む）

    • getOrder()
    • isActive()
    • calculateTotal()

    副作用 NG
    値を返す

    6.設計の階層での位置づけ

    家づくりにたとえると、モジュール設計は「部屋」、クラス設計は「家具」、メソッド設計は「細部」、コーディング規約は「仕上げ」です（→ モジュール設計（43章）、44 クラス設計、コーディング規約は 59_AI開発ツール・コーディング規約 のノート）。

    7.よくある誤解

    誤解1：「FCIS では副作用を一切書いてはいけない」

    副作用をなくすのではなく、置き場所を外側の Shell に寄せる考え方です。DB の読み書きやメール送信は必要な処理なので Shell で行い、判定や計算だけを Core に集めます。こうすると Core はモックなしでテストできます。

    誤解2：「Guard Clause は return を増やすので読みにくくなる」

    関数の先頭に「条件を満たさなければ抜ける」が並ぶだけなので、読む人は先頭を見れば前提条件が分かり、残りは正常系だけに集中できます。読みにくくなるのは、関数の途中のあちこちに return が散らばる場合です。

    誤解3：「calculateTotal() のような計算も、値を返すから Command になることがある」

    値を返して状態を変えない操作は Query です。計算結果を返す関数は典型的な Query で、副作用を入れてはいけません。逆に、状態を変えるのに値も返す関数は CQS に反するので、読む部分と書く部分を分けることを検討します。

    8.まとめ

    • FCIS：純粋関数の Core を、副作用を受け持つ Shell が包む。データは Shell から入り、結果は Shell から出る
    • 抽象度の階層：オーケストレーション（高）→ 中 → 詳細（低）。同じ関数内のステップは同じ抽象度
    • Guard Clause：異常系を先に return して、正常系を浅い位置に
    • CQS：Command は書く（副作用 OK、戻り値 void が多い）、Query は読む（副作用 NG、値を返す）
    • 設計の階層：モジュール設計（部屋）→ クラス設計（家具）→ メソッド設計（細部）→ コーディング規約（仕上げ）
