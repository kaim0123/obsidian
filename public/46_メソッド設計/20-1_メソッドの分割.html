    20 責務と分割

    メソッドの分割 — 最初の一歩

    メソッドをどう切るか、その第一歩を学ぶページです。1つの関数に全部書いてはいけない理由、大きく書いてから小さく割る「段階的詳細化」、同じ抽象度のステップを並べる考え方、そして短すぎ・長すぎを見分ける粒度の判断を押さえます。

    もとにしたノート：01_メソッドの分割

    ひとことで言うと

    1つの関数に全部書くと 読めない・直せない・試せない・再利用できない コードになります。まず流れだけを書き、各ステップを 同じ抽象度 になるまで小さな関数に割っていく（段階的詳細化）のが分割の基本です。

    1.このページで扱うこと

    メソッドをどう切るか の第一歩です。次の点を押さえます。

    • 1つの関数に全部書いてはいけない理由
    • 段階的詳細化（大きく書いて小さく割る）
    • 抽象度（処理をどれくらい細かい言葉で書いているか）をそろえること
    • 粒度（関数1つあたりの大きさ）の判断

    2.なぜ1つの関数に全部書いてはいけないか

    1つの関数にすべてを書くと、次の問題が起きます。

    問題具体例
    読めない300 行で何をしているか把握できない
    直せない表示を変えると DB 処理まで触る必要がある
    試せない計算ロジックだけテストできない
    再利用できない同じ検証をコピペする
    ✕ 悪い例：全部入り 
    // 悪い例: 全部入り
function handleOrder(order) {
  // 検証 50 行
  // 計算 80 行
  // 保存 40 行
  // メール 30 行
}

    分割 は、これらの問題を同時に緩和する最も基本的な技法です。

    3.段階的詳細化（トップダウン）— 大きく書いて小さく割る

    段階的詳細化（Stepwise Refinement） は、プログラミング言語 Pascal の設計者として知られる Niklaus Wirth が提唱した方法です。

    1. まず 問題全体を1つの手続き として書く（詳細は仮名でよい）
    2. 各ステップを さらに小さな手続き に置き換える
    3. 同じ抽象度のステップ が並ぶレベルで止める
    // 第 1 段階: 流れだけ
function processOrder(order) {
  validate(order);
  const total = calculateTotal(order);
  save(order, total);
  notify(order);
}

// 第 2 段階: 各ステップを実装
function calculateTotal(order) {
  const subtotal = sumItems(order.items);
  const tax = calculateTax(subtotal);
  return subtotal + tax;
}

    4.同じ抽象度のステップを並べる

    1関数 = 1抽象度 が目標です。高レベルの流れ（「検証する」「合計を出す」のような業務の言葉）の中に、ビット演算や SQL（データベースへの命令文）が直書きされていると読めません。

    ✕ 悪い例：抽象度が混在 
    // 悪い例: 抽象度が混在
function processOrder(order) {
  if (!order.items) return;
  let total = 0;
  for (const item of order.items) {
    total += item.price * item.qty;  // 低レベルの詳細
  }
  db.query('INSERT INTO ...');       // インフラの詳細
}
    ◯ 良い例：同じ抽象度 
    // 良い例: 同じ抽象度
function processOrder(order) {
  validate(order);
  const total = calculateTotal(order);
  saveOrder(order, total);
}

    詳細は サイズと抽象度 でも扱います。

    5.粒度の判断 — 短すぎ・長すぎの見分け方

    サイン状態対処
    長すぎ50 行超、スクロールが必要Extract Method（Extract Method）
    短すぎ1行関数が大量、全体像が見えない統合または上位関数でまとめる
    名前が説明できない「何をする関数？」と言えない責任を見直す（関心の分離と単一責任）

    目安

    Robert C. Martin の『Clean Code』では 20 行程度を推奨していますが、行数だけ で判断しないようにします（サイズと抽象度）。分けすぎの問題は 深いメソッドと浅いメソッド で扱います。

    6.最初の関数分割ワークショップ

    次の手順で、既存コードを分割してみましょう。

    1. 200 行以上の関数 を1つ選ぶ
    2. コメントで区切られた塊 を見つける（「// 検証」「// 計算」など）
    3. 各塊に 動詞 + 目的語 の名前を付ける
    4. Extract Method で切り出し、元関数は オーケストレーション（各処理を順に呼び出して流れを組み立てるだけの役割）だけにする
    5. テストを1つ書き、分割後も動くことを確認する
      Before: handleRequest() 200 行
  After:  handleRequest() 15 行
          ├─ validateRequest()
          ├─ processOrder()
          └─ sendResponse()

    7.よくある誤解

    誤解1：「20 行を超えたら必ず分ける」

    行数は目安にすぎません。 長すぎ・短すぎ・名前で説明できるかの3つのサインを合わせて判断します。

    誤解2：「細かく分けるほど良い」

    短すぎも問題です。 1行関数が大量にあると全体像が見えなくなります。その場合は統合するか、上位関数でまとめます。

    誤解3：「コメントで区切ってあれば十分読みやすい」

    コメントで区切られた塊は、関数として切り出す候補のサイン です。塊に名前を付けて Extract Method すると、元の関数は流れだけが読める形になります。

    8.まとめ

    • 1関数に全部書くと読めない・直せない・試せない
    • 段階的詳細化 = 大きく書いて、同じ抽象度になるまで小さく割る
    • 粒度は長すぎ・短すぎ・名前で判断する
    • コメント頼みの塊から Extract Method へ
