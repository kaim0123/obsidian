    80 ケーススタディ

    ケーススタディ — 注文処理フローと料金計算・バリデーション

    このページは、これまで学んだメソッド設計の技法を実際のコードに当てはめる演習です。ケース1では 200 行の handleRequest() を題材に、Guard Clause・Extract Method・CQS・SoC・純粋関数の切り出しを順に使って分割します。ケース2では 料金計算 と バリデーション を題材に、Functional Core, Imperative Shell とバリデーション関数の設計を実践します。

    もとにしたノート：01_ケーススタディ_注文処理フロー、02_ケーススタディ_計算・バリデーション

    ひとことで言うと

    巨大関数は Guard Clause → Extract Method の順で分割し、SoC で認証・検証・計算・保存・通知を分けます。計算と判定は 純粋関数（Core） に、DB・メール・時刻は Shell に寄せます。バリデーションは副作用のない Query として Result 型 で返します。

    2つのケースを通して、第1〜7部の技法を統合します。

    ケース1：注文処理フロー

    • CQS と SoC で責任を整理する

    • 実装と振り返り

    ケース2：計算・バリデーション

    • 料金計算ロジックの関数化

    2.ケース1：200 行の handleRequest() を読む

    2.1 Before（抜粋）

    ✕ Before：認証・検証・計算・保存・通知が1つの関数に詰め込まれている 
    function handleRequest(req) {
  if (!req) return { error: 'no request' };
  if (!req.token) return { error: 'unauthorized' };
  // ... 認証 30 行 ...
  if (!req.body?.orderId) return { error: 'invalid' };
  // ... バリデーション 40 行 ...
  const order = db.getOrder(req.body.orderId);
  // ... 計算 50 行 ...
  order.status = 'processed';
  db.save(order);
  email.send(order.customer);
  // ... レスポンス 30 行 ...
}

    2.2 問題点

    問題内容
    行数200 行超
    関心認証・検証・計算・保存・通知が混在
    テストDB・メール必須
    命名handleRequest が曖昧

    3.Guard Clause と Extract Method で分割する

    3.1 Step 1：Guard Clause で異常系を入口に集約

    Guard Clause（ガード節）は、異常な場合を関数の入口で先に return して、正常系をまっすぐ書く書き方です。

    function handleRequest(req) {
  const authError = authenticate(req);
  if (authError) return authError;

  const validationError = validateOrderRequest(req.body);
  if (validationError) return validationError;

  return processOrderRequest(req.body);
}

    3.2 Step 2：Extract Method でブロックを切り出す

    Extract Method は、意味のあるまとまりを名前の付いた関数として切り出すリファクタリングです。

    function authenticate(req) {
  if (!req?.token) return { error: 'unauthorized' };
  // ...
  return null;
}

function validateOrderRequest(body) {
  if (!body?.orderId) return { error: 'invalid orderId' };
  // ...
  return null;
}

    4.CQS と SoC で責任を整理する

    CQS（コマンド・クエリ分離）は、「値を返す問い合わせ（Query）」と「状態を変える命令（Command）」を別のメソッドに分ける原則です。SoC（関心の分離）は、異なる関心ごとを別の場所に置くことです。

    function processOrderRequest(body) {
  const order = loadOrder(body.orderId);           // Query（読み）
  const updated = applyProcessing(order);          // Command 準備
  persistOrder(updated);                           // Command（書き）
  notifyCustomer(updated);                         // Command
  return buildSuccessResponse(updated);            // Query
}
    関数関心CQS
    authenticate認証Query
    validateOrderRequest入力検証Query
    applyProcessing業務ルール純粋に近い
    persistOrder永続化Command
    notifyCustomer通知Command

    5.純粋関数に切り出す部分の特定

    計算・判定 は Core に切り出します。純粋関数 は、同じ入力なら必ず同じ出力を返し、副作用（DB 保存やメール送信など、外の状態を変えること）を持たない関数です（純粋関数と副作用）。

    // Core: 純粋
function calculateOrderTotal(items) {
  return items.reduce((s, i) => s + i.price * i.qty, 0);
}

function applyProcessing(order) {
  const total = calculateOrderTotal(order.items);
  return { ...order, total, status: 'processed' };
}

// Shell: I/O
function processOrderRequest(body) {
  const order = loadOrder(body.orderId);
  const updated = applyProcessing(order);
  persistOrder(updated);
  notifyCustomer(updated);
  return buildSuccessResponse(updated);
}

    calculateOrderTotal と applyProcessing は モックなし でテスト可能です（テストしやすいメソッド設計）。

    7.ケース2：料金計算ロジックの関数化

    7.1 Before — サービスに直書き

    ✕ Before：小計・割引・税の計算が1つの関数に直書きされている 
    function createInvoice(order) {
  let subtotal = 0;
  for (const item of order.items) {
    subtotal += item.price * item.qty;
  }
  let discount = 0;
  if (order.coupon) {
    discount = subtotal * order.coupon.rate;
  }
  const tax = (subtotal - discount) * 0.1;
  return subtotal - discount + tax;
}

    7.2 After — 純粋関数に分解

    ◯ After：1つの計算ごとに1つの純粋関数 
    function calculateSubtotal(items) {
  return items.reduce((s, i) => s + i.price * i.qty, 0);
}

function applyCouponDiscount(subtotal, coupon) {
  if (!coupon) return 0;
  return subtotal * coupon.rate;
}

function calculateTax(taxableAmount, rate = 0.1) {
  return taxableAmount * rate;
}

function calculateInvoiceTotal(order) {
  const subtotal = calculateSubtotal(order.items);
  const discount = applyCouponDiscount(subtotal, order.coupon);
  const taxable = subtotal - discount;
  const tax = calculateTax(taxable);
  return taxable + tax;
}

    各関数が 1 つの計算 に集中し、テストが容易です。

    8.Functional Core, Imperative Shell の適用

    Functional Core, Imperative Shell（FCIS）は、計算を担う純粋な中心部（Core）と、I/O や時刻の取得を担う外側（Shell）に分ける設計です。

    // Core: すべて純粋
function buildInvoice(order) {
  const total = calculateInvoiceTotal(order);
  return {
    orderId: order.id,
    lineItems: order.items,
    total,
    calculatedAt: null,  // Shell で時刻を注入
  };
}

// Shell: I/O と時刻
async function generateAndSaveInvoice(orderId) {
  const order = await repo.find(orderId);
  const invoice = buildInvoice(order);
  invoice.calculatedAt = new Date().toISOString();
  await repo.saveInvoice(invoice);
  return invoice;
}
    • テスト：buildInvoice と calculateInvoiceTotal は固定データで検証
    • Shell のみ統合テスト（DB などの本物を組み合わせて動かすテスト）

    9.バリデーション関数の設計

    バリデーション（入力が正しいかの検査）は Query（副作用なし）として設計します。

    function validateOrder(order) {
  const errors = [];

  if (!order?.items?.length) {
    errors.push({ field: 'items', message: 'items required' });
  }
  if (order.items?.some(i => i.qty <= 0)) {
    errors.push({ field: 'items', message: 'qty must be positive' });
  }
  if (order.coupon && (order.coupon.rate < 0 || order.coupon.rate > 1)) {
    errors.push({ field: 'coupon', message: 'invalid coupon rate' });
  }

  return errors.length === 0
    ? { ok: true }
    : { ok: false, errors };
}
    原則内容
    戻り値Result 型（ok ＋ errors）
    副作用なしログも throw もしない（Shell で）
    1 関数 1 対象validateOrder, validateUser を分ける

    Result 型 は、成功か失敗かと、その中身（値やエラー一覧）を1つの戻り値で表す形です（null・undefined・Result型の使い分け）。

    10.よくある設計ミスと修正

    ミス修正
    バリデーション中に DB 参照必要データは Shell が取得して引数で渡す
    計算関数内で Date.now()時刻を引数で注入
    フラグ引数 validate(order, strict)validateOrderStrict に分割
    エラー時に throw と return 混在Result 型に統一
    ◯ 修正：時刻を注入する 
    function isExpired(deadline, now) {
  return now > deadline;
}

test('isExpired', () => {
  expect(isExpired(future, fixedNow)).toBe(false);
});

    関数の中で現在時刻を取ると、テストのたびに結果が変わってしまいます。now を引数で受け取れば、固定した時刻（fixedNow）で何度でも同じ結果を確かめられます。

    11.よくある誤解

    誤解1：「巨大関数は、一気に書き直したほうが早い」

    段階的に進めます。 まず Guard Clause で異常系を入口に集め、次に Extract Method でブロックを1つずつ切り出します。各ステップでテストが通ることを確かめながら進めるのが安全です（リファクタリングの実践）。

    誤解2：「バリデーションの中でログを出したり throw したりするのは普通」

    バリデーションは副作用のない Query にします。 検査結果は Result 型で返し、ログや例外への変換は Shell 側で行います。こうすると、バリデーション関数は固定データだけでテストできます。

    誤解3：「時刻や DB は関数の中で取得したほうが呼ぶ側が楽」

    テストが難しくなります。 時刻や DB の値は Shell が取得して引数で渡します。計算や判定の関数は、渡された値だけで結果が決まる純粋関数にします。

    12.まとめ

    12.1 ケース1：注文処理フロー

    • 巨大関数は Guard Clause → Extract Method の順で分割
    • SoC で認証・検証・計算・保存・通知を分離
    • 計算は純粋関数（Core）、I/O は Shell
    • 振り返りでチェックリストを確認

    12.2 ケース2：計算・バリデーション

    • 料金計算は小さな純粋関数に分解
    • FCIS — 計算は Core、保存は Shell
    • バリデーションは Result 型・副作用なし
    • 時刻・DB 依存は引数化または Shell に
