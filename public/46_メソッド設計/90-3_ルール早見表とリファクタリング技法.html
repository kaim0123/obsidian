    90 付録

    ルール早見表とリファクタリング技法 — 関数のルールと直し方を一覧で引く

    Robert C. Martin の Clean Code（2008）にある関数ルールと、Martin Fowler の Refactoring にあるリファクタリング技法を、メソッド設計向けに早見表にまとめたページです。「どんな関数が良いか」の目安と、「どう直すか」の技法を、それぞれ詳しく説明しているページへのリンクと一緒に並べています。

    もとにしたノート：付録C_Clean_Code関数ルール早見表、付録D_リファクタリング技法早見表

    ひとことで言うと

    関数は「小さく、1 つのことだけ、抽象度をそろえ、引数は少なく、Query に副作用なし、名前で意図を伝える」が基本ルールです。ルールから外れた関数は、テストで守りながら1 技法ずつリファクタリングして近づけます。レガシー関数なら Guard Clause → Extract Method の順に始めるのが定石です。

    • Clean Code 関数ルール早見表：基本ルール、行数・複雑度の目安、命名ルール、コード例、ルールの限界
    • リファクタリング技法早見表：関数の抽出・整理、制御フロー、データ・副作用の 3 分類

    リファクタリングは、外から見た振る舞いを変えずに内部構造を改善することです。実際の進め方は リファクタリングの実践、クラス単位の技法は コードの臭いとリファクタリング（44章） を参照してください。

    2.Clean Code 関数ルール早見表

    Robert C. Martin（Clean Code, 2008）の関数ルールをメソッド設計向けに整理した早見表です。

    2.1 基本ルール

    ルール内容本教材での章
    小さく1 画面に収まる長さサイズと抽象度
    1 つのこと1 関数 1 責任関心の分離と単一責任
    1 抽象度ステップの抽象度を揃えるメソッドの分割
    少ない引数0〜2 が理想引数の設計
    副作用なしQuery に副作用を入れないCQS
    説明的な名前意図が伝わる命名命名

    抽象度は、処理を「何をするか」の大まかな言葉で書いているか、「どうやるか」の細かい手順で書いているかの度合いです。

    2.2 行数・複雑度の目安

    指標目安超えたら
    行数20 行以下Extract Method
    行数（上限）50 行必ず分割検討
    循環的複雑度10 以下分岐の分割
    インデント2 段以下Guard Clause
    引数3 個以下Parameter Object

    「超えたら」の列が、そのまま次の章の技法につながります（→ Extract Method、複雑度と分岐、Guard Clause、引数の設計）。

    2.3 命名ルール

    種類形式例
    一般動詞 + 目的語calculateTotal()
    真偽値is / has / canisValid()
    取得get + 名詞getOrder()
    禁止（単独）曖昧名process, handle, data

    関連：命名

    2.4 コード例

    各ステップが同じ抽象度の関数呼び出しで並び、関数名だけで「検証 → パスワードのハッシュ化 → 保存 → 通知」の流れが読めます。

    ◯ Clean Code に沿った関数 
    // Clean Code に沿った関数
function registerUser(user) {
  validateUser(user);
  const hashed = hashPassword(user.password);
  persistUser({ ...user, password: hashed });
  notifyNewUser(user);
}

    2.5 限界

    • 20 行は目安 — 宣言的マッピング（対応表をそのまま並べたような、分岐の少ないコード）等は例外あり
    • 複雑度とセットで判断（複雑度と分岐）
    • 小規模プロジェクトでは KISS を優先（KISS・DRY・YAGNI）

    関連：命名、サイズと抽象度、分けすぎの判断は 深いメソッドと浅いメソッド

    3.リファクタリング技法早見表

    メソッド設計で使うリファクタリング技法の早見表です（Martin Fowler, Refactoring）。

    3.1 関数の抽出・整理

    技法用途章
    Extract Method意味の塊を新関数にExtract Method
    Inline Method小さすぎる関数を統合（Extract Method の逆）Extract Method
    Replace Temp with Query一時変数を関数にExtract Method
    Introduce Parameter Object引数をオブジェクト化引数の設計
    Remove Flag Argumentフラグ引数を関数分割に引数の設計

    3.2 制御フロー

    技法用途章
    Replace Nested Conditional with Guard Clausesネストを早期 return にGuard Clause
    Replace Conditional with Polymorphism分岐を多態（同じ呼び出しで型ごとに違う処理が動く仕組み）に複雑度と分岐
    Decompose Conditional条件式を関数に複雑度と分岐
    Consolidate Conditional Expression同じ結果の条件を統合複雑度と分岐

    3.3 データ・副作用

    技法用途章
    Separate Query from ModifierCQS の適用CQS
    Extract Class / Move Method関数を適切なクラスへオブジェクトのメソッド
    Pass Object Instead of Dataプリミティブ（数値・文字列などの基本の型）をオブジェクトに引数の設計

    3.4 適用手順（共通）

    どの技法でも、次の手順を繰り返します。

    1. テストを書く（または既存テストを確認）
    2. 小さく 1 技法ずつ適用
    3. テストが通ることを確認
    4. コミットする
    5. 次の技法へ

    テストが振る舞いを変えていない証拠になり、コミットを細かく刻むことで、失敗してもすぐ一つ前に戻れます（→ リファクタリングの実践、テストしやすいメソッド設計）。

    3.5 レガシー関数への優先順位

    長く複雑な既存の関数（レガシー関数）を直すときは、次の順に手を付けます。

    1. Guard Clause（異常系の抽出）
    2. Extract Method（意味の塊）
    3. Introduce Parameter Object（引数整理）
    4. Replace Conditional（分岐の整理）
    5. Separate Query from Modifier（CQS）

    関連：リファクタリングの実践、技法が生まれた歴史は メソッド設計の変遷

    4.よくある誤解

    誤解1：「20 行を 1 行でも超えたら分割しなければならない」

    20 行は目安です。対応表をそのまま並べたような宣言的なコードは、長くても読みやすいことがあります。行数だけでなく複雑度とセットで判断し、小規模プロジェクトでは KISS（単純さ）を優先します。

    誤解2：「関数は小さければ小さいほど良い」

    細かく分けすぎると、処理を追うために何度もジャンプが必要になります。そのために Inline Method（小さすぎる関数を呼び出し元に戻す技法）があります。分割と統合の判断は 深いメソッドと浅いメソッド を参照してください。

    誤解3：「リファクタリングは一気にまとめてやるほうが効率的」

    複数の技法を同時に適用すると、テストが落ちたときに原因が分からなくなります。テスト → 1 技法 → テスト → コミットの小さなサイクルを回すほうが、結果的に速く安全です。

    5.まとめ

    • Clean Code の基本ルールは「小さく・1 つのこと・1 抽象度・少ない引数・副作用なし・説明的な名前」
    • 目安：20 行以下（上限 50 行）、循環的複雑度 10 以下、インデント 2 段以下、引数 3 個以下。超えたら対応する技法で直す
    • 命名は動詞 + 目的語、真偽値は is / has / can、process などの曖昧名は単独で使わない
    • 技法は「関数の抽出・整理」「制御フロー」「データ・副作用」の 3 分類。テスト → 1 技法 → テスト → コミットで適用する
    • レガシー関数は Guard Clause → Extract Method → Parameter Object → 分岐の整理 → CQS の順に
