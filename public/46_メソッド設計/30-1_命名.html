    30 シグネチャ設計

    命名 — 名前で「何をするか」を伝える

    関数やメソッドは、中身を読まれる回数よりも、名前だけを見て呼ばれる回数のほうがずっと多いものです。このページでは、関数名・メソッド名の付け方として、Clean Code の「動詞 + 目的語」のルール、boolean の命名、意図が伝わる名前と短い名前の使い分け、検索しやすい名前、チームでの命名規約の統一を解説します。

    もとにしたノート：01_命名

    ひとことで言うと

    関数名は 動詞 + 目的語 で「何をするか」を表し、真偽値を返すものは is / has / can / should で始めます。handleData のような曖昧な名前を避け、検索したときに1つの意図に絞れる名前 を付けます。

    1.このページで扱うこと

    関数名・メソッド名 の付け方を学びます。名前は、関数の シグネチャ（関数名・引数・戻り値の型の組み合わせ。呼ぶ側から見える「関数の顔」）の中でも、いちばん最初に目に入る部分です。

    • Clean Code の関数ルール：動詞 + 目的語
    • boolean（真偽値）の命名
    • 意図が伝わる名前 と 短い名前 の使い分け、変数名も業務の用語で書くこと
    • 検索しやすい名前（handleData 問題）
    • チームでの統一（命名規約）
    • 演習：リネーム候補を挙げる

    クラス名やディレクトリ名の付け方は 44章：命名とクラス構成、43章：命名とディレクトリ構成 で扱っています。

    2.関数名は動詞 + 目的語

    関数名は 何をするか が伝わる 動詞 + 目的語 にします。

    悪い例良い例
    data()fetchUserData()
    process()calculateInvoiceTotal()
    handle()sendOrderConfirmation()
     
    function validateOrder(order) { /* ... */ }
function calculateTax(amount) { /* ... */ }
function persistOrder(order) { /* ... */ }

    1 関数 1 動詞

    名前に複数の動詞が入る（validateAndSave など）のは、関数を分割すべきサイン です。1つの関数が2つの仕事をしている可能性があります（→ メソッドの分割）。

    3.boolean は is / has / can / should

    真偽値（true / false）を返す関数・メソッドは、プレフィックス（名前の先頭に付ける決まった語）で統一します。

    プレフィックス用途例
    is状態isActive(), isEmpty()
    has所持・包含hasItems(), hasPermission()
    can能力・可否canSubmit(), canEdit()
    should推奨・条件shouldRetry(), shouldNotify()
     
    function isValidOrder(order) {
  return order && order.items.length > 0;
}

    これらは CQS の Query（値を返すだけで状態を変えない問い合わせ）として、副作用なし で値を返します（→ CQS）。副作用 とは、値を返す以外に外の状態を変えること（変数の書き換え・DB への保存など）です。

    4.意図が伝わる名前と短い名前

    4.1 スコープの広さで長さを決める

    方針向く場面
    意図が伝わる長い名前公開 API、ドメイン用語
    短い名前スコープが狭いループ変数（i, item）

    スコープ とは、その名前が使える範囲のことです。広い範囲から使われる名前ほど、名前だけで意味が伝わる必要があります。

    // スコープが広い → 長く
function calculateOrderTotalWithTaxAndShipping(order) { /* ... */ }

// スコープが 3 行 → 短くてよい
items.forEach(item => sum += item.price);

    略語は避けます。 calc より calculate、usr より user と書きます（チームで例外を決める場合を除く）。

    4.2 変数名も業務の用語で書く

    関数名だけでなく、ローカル変数・フィールド も略語や1文字を避け、業務で通じる語に揃えます（『現場で役立つシステム設計の原則』第1章）。

    ✕ 悪い例：略語と1文字で、何の計算か分からない 
    const up = 100;
const qty = 3;
const a = qty * up;
    ◯ 良い例：業務の用語で書く 
    const unitPrice = 100;
const quantity = 3;
const basePrice = quantity * unitPrice;

    名前が長くなりすぎるときは、形容詞を積み重ねるのではなく、業務用語そのもの がないかを疑うとよいです。計算途中の意図を変数に落とす技法は 段落と説明用の変数 を参照してください。

    5.検索しやすい名前（handleData 問題）

    曖昧な名前 は grep（文字列でファイルを検索するコマンド）でも見つけにくく、その関数が何に責任を持つのかも分かりません。

    ✕ 問題：プロジェクト内に handleData が 50 個 
    function handleData(data) { /* 何をする？ */ }
    ◯ 改善：具体的な名前 
    function parseCsvRows(data) { /* ... */ }
function validateUserInput(data) { /* ... */ }

    検索テスト

    関数名でプロジェクトを検索し、1 つの意図 に絞れるかを確認します。

    6.命名規則とチームでの統一

    チームで 命名規約 を決め、コーディング規約（チームで決めたコードの書き方のルール）と連携させます。

    項目例
    ケースcamelCase（JS）、snake_case（Python）
    プライベート_prefix または #
    テストshould_X_when_Y または test_X
    禁止名data, info, process, handle（単独）

    リファクタリング時（振る舞いを変えずにコードを整えるとき）は、IDE の Rename 機能で一括変更し、テストで確認します。

    7.演習 — リネーム候補を挙げる

    次の関数名を 具体的な名前 に直してみましょう。

    BeforeAfter（例）
    process(data)parseCsvRows(data)
    handle(e)logAndRethrow(e)
    check(x)isValidEmail(x)
    getData()fetchActiveUsers()

    ルール：検索したとき 1 つの意図 に絞れる名前にします。

    8.よくある誤解

    誤解1：「名前は短いほど読みやすい」

    場面によります。 数行のループ変数なら短くてよいですが、公開 API やスコープの広い名前は、意図が伝わる長さ を優先します。略語は避けます。

    誤解2：「中身を読めば分かるから、名前は適当でよい」

    違います。 呼ぶ側は名前だけを見て使います。handleData のような名前は、検索しても意図に絞れず、責任も曖昧になります。

    誤解3：「validateAndSave のように全部書けば正確な名前になる」

    名前としては正直ですが、複数の動詞が必要なこと自体が、関数を分けるべきサイン です。名前で正確に書くより、関数を分けて 1 関数 1 動詞にします。

    9.まとめ

    • 関数名 = 動詞 + 目的語。1 関数 1 動詞
    • boolean = is / has / can / should
    • 意図が伝わる名前 を優先。略語は避け、変数名も業務の用語で書く
    • handleData 問題 — 具体的で検索しやすい名前へ
    • 命名規約をチームで決め、Rename とテストで直す
