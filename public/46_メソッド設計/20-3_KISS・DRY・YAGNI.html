    20 責務と分割

    KISS・DRY・YAGNI — メソッドレベルの原則

    メソッド設計で毎日使う3つの原則を学ぶページです。KISS（単純に保つ）・DRY（同じ知識を二重に書かない）・YAGNI（今必要ないものは作らない）の意味をメソッドの例で確かめ、原則同士が衝突したときに「変更理由」で判断するコツを押さえます。

    もとにしたノート：03_KISS・DRY・YAGNI

    ひとことで言うと

    KISS は賢さより単純さ、DRY は同じ 知識 を1か所に、YAGNI は今使わない汎化や引数を作らない、という原則です。3つがぶつかったら「何が変わったらこのコードを直すか」で決めます。

    1.このページで扱うこと

    メソッド設計で毎日使う 3つの原則 を学びます。

    • KISS・DRY・YAGNI のそれぞれの意味
    • 原則同士が衝突したときの判断
    • 変更理由で判断する実践のコツ

    2.KISS — 賢さより単純さ

    KISS（Keep It Simple, Stupid） = 必要以上に賢く書かない。

    // 過剰: 1 行の処理を Strategy パターンで 5 ファイルに
// 適切: 素直に書く
function calculateTax(amount, rate) {
  return amount * rate;
}

    Strategy パターン は、処理の中身を差し替えられるように別のクラスへ切り出すデザインパターンです（44章：振る舞いパターン）。1行で済む処理に使うのは過剰です。

    メソッドレベルでは次を意識します。

    • 抽象化は 2回目の重複が見えたとき に検討
    • 「短く」より 意図が一目で分かる
    • 将来の拡張を理由に 使われない引数 を増やさない

    3.DRY — 同じ知識を二重に書かない

    DRY（Don't Repeat Yourself） = 同じ知識・同じ変更理由 のコードを重複させない。

    ✕ 悪い例：同じ税計算が3か所 
    // 悪い例: 同じ税計算が 3 か所
function calcA(x) { return x * 0.1; }
function calcB(y) { return y * 0.1; }
    ◯ 良い例：1か所に集約 
    // 良い例: 1 か所に集約
function calculateTax(amount) { return amount * TAX_RATE; }

    注意

    見た目が似ているだけ（偶然の一致）を無理に DRY にしないでください。知識が同じ — 税率が変わったら すべて 直す必要がある — ときに DRY にします。

    4.YAGNI — 使わない引数・汎化を作らない

    YAGNI（You Aren't Gonna Need It） = 今必要ないものは作らない。

    ✕ 悪い例：使われない options 
    // 悪い例: 使われない options
function sendEmail(to, subject, body, options = {}) {
  const { cc, bcc, template, locale, retryPolicy } = options;
  // cc も bcc も未使用
}
    ◯ 良い例：今必要な引数だけ 
    // 良い例: 今必要な引数だけ
function sendEmail(to, subject, body) { /* ... */ }

    汎用パラメータ・多目的関数・「将来用」の フラグ引数（true / false で関数の動きを切り替える引数）は YAGNI 違反になりやすいです。設計全体での YAGNI は 42章：変化に強い設計 でも扱っています。

    5.原則同士が衝突するとき（DRY vs SRP vs KISS）

    SRP（単一責任の原則：1メソッド1変更理由。関心の分離と単一責任）も含めて、原則同士はぶつかることがあります。

    状況判断のヒント
    DRY vs SRP無理に1関数にまとめると責任が混ざる → SRP を優先
    DRY vs KISS抽象化でファイルが増えすぎる → KISS を優先
    SRP vs KISS1行関数が 50 個 → 適度に統合

    原則は「絶対ルール」ではなく「判断の材料」
    → 変更理由・読み手・テスト容易性で決める

    6.変更理由で判断する実践のコツ

    原則が衝突したら 「何が変わったらこのコードを直すか」 で決めます。

    1. 変更理由が同じ → DRY で1関数に
    2. 変更理由が違う → SRP で分離
    3. まだ1回しか出てこない → YAGNI で待つ
    4. 読み手が迷う → KISS で単純に

    歴史的背景は メソッド設計の変遷 の KISS・DRY の節を参照してください。

    7.判断ワークショップ — 3つのシナリオ

    シナリオ判断理由
    同じ3行の税計算が2か所DRY税率変更が1理由
    似たループだが用途が別KISS変更理由が違う。統合しない
    options に未使用フィールドYAGNI削除する
    抽象クラス1回しか継承されないKISS2回目まで待つ

    覚えておくこと

    原則は チェックリスト ではなく 会話の材料 です。「DRY にしよう」より「この2か所、同じ理由で変わる？」と問う方が実践的です。

    8.よくある誤解

    誤解1：「見た目が同じコードは必ず共通化する」

    違います。 DRY が避けるのは 同じ知識 の重複です。見た目が似ていても変更理由が違うなら、無理にまとめると責任が混ざります。

    誤解2：「将来のために引数やオプションを用意しておくのは親切」

    使われない引数は読み手を迷わせ、テストすべき組み合わせも増やします。今必要な引数だけ にし、必要になったときに足します（YAGNI）。

    誤解3：「原則はいつも守るべきルール」

    原則同士は衝突します。判断の材料 として使い、最後は変更理由・読み手・テスト容易性で決めます。

    9.まとめ

    • KISS = 単純さを優先。過剰な抽象化を避ける
    • DRY = 同じ知識の重複を避ける（見た目の一致 ≠ DRY）
    • YAGNI = 今使わない汎化・引数を作らない
    • 衝突時は変更理由で判断する
