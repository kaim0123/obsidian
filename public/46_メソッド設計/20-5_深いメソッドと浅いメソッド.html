    20 責務と分割

    深いメソッドと浅いメソッド — 分割と統合の判断

    メソッドを分割するのは、いつでも良いことでしょうか。このページでは John Ousterhout『A Philosophy of Software Design』第9章「Better Together or Better Apart?」を軸に、メソッドの深さ、一緒にすべきサインと分けるべきサイン、良い分け方・悪い分け方、そして『Clean Code』の「関数は小さく」との付き合い方を学びます。

    もとにしたノート：05_深いメソッドと浅いメソッド_分割と統合の判断

    ひとことで言うと

    メソッドの価値は やってくれる処理（利益）÷ シグネチャの複雑さ（コスト） です。分けた結果、呼ぶ側が知るべきことが増えたなら、その分割は失敗。迷ったら「中身を見なくても分かる名前が付けられるか」を問います。

    1.このページで扱うこと

    メソッドの分割 と Extract Method では、長いメソッドを分割する方法を学びました。しかし、分割は いつでも良いこと でしょうか。

    • 5行ずつに分けたら、処理の流れを追うのに10個のメソッドを行き来するようになった
    • 分けたメソッド同士が、結局お互いの中身を知らないと理解できない
    • 「何もせず次を呼ぶだけ」のメソッドが増えた

    このページでは、John Ousterhout『A Philosophy of Software Design』第9章「一緒にすべきか、分けるべきか（Better Together or Better Apart?）」を軸に、次を学びます。

    • メソッドの 深さ（インターフェースと機能の比率）
    • 一緒にすべき 4つのサイン
    • 分けるべき 2つのサイン
    • メソッド分割の 良い分け方・悪い分け方
    • 『Clean Code』の「関数は小さく」との付き合い方

    モジュール単位の「深いモジュール」の考え方は 43章：深いモジュールと浅いモジュール を参照してください。このページは メソッド単位 に焦点を当てます。

    2.メソッドの深さ

    2.1 コストと利益

    メソッドにも、モジュールと同じ コストと利益 があります。シグネチャ とは、メソッドの名前・引数・戻り値の型の組み合わせのことです。

    部分内容呼ぶ側にとって
    シグネチャと約束ごと名前・引数・戻り値・例外・前提条件・副作用コスト（覚えること）
    本体メソッドが代わりにやってくれる処理利益（自分で書かずに済むこと）

    深いメソッド：シンプルなシグネチャで、多くの処理を引き受ける。
    浅いメソッド：シグネチャの複雑さに比べて、やってくれることが少ない。

    2.2 浅いメソッドの例

    ✕ 浅い：シグネチャを覚えるコストと、中身がほぼ同じ 
    function addNullValueForAttribute(attributes: Map<string, unknown>, key: string) {
  attributes.set(key, null);
}
    ✕ 浅い：呼ぶ側が順番と組み合わせを全部知っている必要がある 
    const conn = openConnection(config);
const tx = beginTransaction(conn);
const result = executeQuery(tx, sql);
commitTransaction(tx);
closeConnection(conn);

    2つ目の例なら、withTransaction(config, (tx) => tx.query(sql)) のように よく使う組み合わせを1つのメソッドにまとめる 方が、呼ぶ側は楽になります。トランザクション とは、複数のデータベース操作を「全部成功するか、全部取り消すか」の1単位として扱う仕組みです。

    2.3 「短い」と「浅い」は違う

    • 3行のメソッドでも、複雑な判断を引き受けて、シンプルな名前で呼べる なら深い
      • 例：isBusinessDay(date)（祝日・振替休日・年末年始の判断を隠している）
    • 50行のメソッドでも、呼ぶ側の手間がほとんど減らない なら浅い

    大事なのは 行数ではなく、呼ぶ側が知るべきことが減るかどうか です。

    3.一緒にすべき4つのサイン

    Ousterhout は、2つの処理を 一緒にした方がよい サインとして次を挙げています。

    3.1 情報を共有している

    2つの処理が、同じ知識（データ形式・プロトコル・業務ルール）に依存しているなら、一緒にする。

    ✕ 分けた結果、CSV の形式という知識が2か所にある（情報漏洩） 
    function parseHeader(line: string) { return line.split(",").map((s) => s.trim()); }
function parseRow(line: string) { return line.split(",").map((s) => s.trim()); }
// 区切り文字やクォートの扱いを変えるとき、両方を直す必要がある
    ◯ 知識を1か所に 
    function parseCsvLine(line: string): string[] { ... }

    情報漏洩 とは、同じ設計判断（知識）が複数の場所に散らばっている状態です（43章：深いモジュールと浅いモジュール）。

    3.2 一緒に使われる

    いつも セットで呼ばれる なら、一緒にすることを検討する。ただし、双方向（A を使うときは必ず B も使い、B を使うときは必ず A も使う）の場合に限る。

    // 毎回この3つがセットで呼ばれているなら…
const normalized = normalize(input);
validate(normalized);
const saved = save(normalized);

// 1つにまとめる
const saved = registerInput(input);

    3.3 概念的に重なっている

    2つの処理が 同じ上位の概念 に属するなら、一緒にする。

    • 例：calcSubtotal・calcTax・calcShipping は、どれも「注文金額の計算」という概念に属する → 同じクラス・モジュールにまとめる

    3.4 片方を読まないと、もう片方を理解できない

    一方のメソッドを理解するのに、もう一方の実装を読む必要がある なら、一緒にする（Ousterhout はこれを 結合したメソッド（Conjoined Methods） と呼び、レッドフラグ（設計の危険信号）としています）。

    ✕ processStep1 が状態を中途半端にして、processStep2 がそれを前提にしている 
    function processStep1(order: Order) { order.tmp = calcSomething(order); }
function processStep2(order: Order) { order.total = order.tmp! * 1.1; delete order.tmp; }
// processStep2 だけを読んでも、tmp が何か分からない

    3.5 一緒にするとインターフェースが単純になる

    一緒にすることで、中間のインターフェースが不要 になったり、呼ぶ側がやるべきことが自動化 されたりするなら、一緒にする。

    4.分けるべき2つのサイン

    4.1 汎用的な処理と特化した処理が混ざっている

    どこでも使える汎用的な処理 と、特定の用途のための処理 が1つのメソッドに混ざっているなら、分ける。

    ✕ 汎用的な「リトライ」と、特定の「ユーザー取得」が混ざっている 
    async function fetchUserWithRetry(id: string) {
  for (let i = 0; i < 3; i++) {
    try { return await api.get(`/users/${id}`); }
    catch (e) { await sleep(2 ** i * 100); }
  }
  throw new Error("取得失敗");
}
    ◯ 汎用的な部分を切り出す 
    async function retry<T>(fn: () => Promise<T>, times = 3): Promise<T> { ... }
const user = await retry(() => api.get(`/users/${id}`));

    リトライ とは、失敗した処理を一定回数やり直すことです。

    4.2 よりきれいな抽象に分けられる

    分けたそれぞれが、単独で意味の通る、シンプルなインターフェース を持つなら、分ける。

    • 分けた後、それぞれのメソッドを、もう一方を見ずに理解できる かどうかが判断基準
    • 理解できないなら、それは「分けた」のではなく「切り刻んだ」だけ

    5.メソッド分割の良い例・悪い例

    Ousterhout は、メソッドを分割するときの良いパターンと悪いパターンを図で示しています。

    分割説明判断
    （b）サブタスクの抽出親メソッドの一部を子メソッドに切り出す。呼ぶ側は親だけを知ればよい。子メソッドは単独で理解できる✅ 良い（Extract Method の基本）
    （c）独立した操作に分ける1つのメソッドが2つの別々のことをしていたので、2つの公開メソッドに分ける。呼ぶ側はどちらか一方だけを使う✅ 良い
    （d）前半と後半に切る処理を途中で切って2つにする。呼ぶ側は両方を順番どおりに呼ぶ必要がある。片方だけでは意味をなさない❌ 悪い（浅いメソッドが2つ増えただけ）

    「分けた結果、呼ぶ側が知るべきことが増えた」なら、その分割は失敗です。

    6.『Clean Code』との付き合い方

    6.1 2つの立場

    Robert C. Martin『Clean Code』John Ousterhout『A Philosophy of Software Design』
    関数の長さ小さく、さらに小さく（数行が理想）長さそのものより 深さ が重要
    分割の基準「1つのことだけをする」まで分ける呼ぶ側の認知負荷（理解するために頭に入れておくべきことの量）が減るか で判断
    懸念長い関数は読みにくい細かく分けすぎると、インターフェースが増えて全体が複雑になる

    Ousterhout と Martin は 2024〜2025 年に、この違いについて公開で議論しています（参考資料参照）。

    6.2 実務での落としどころ

    両者の主張は、次のように組み合わせると実用的です。

    状況判断
    長いメソッドの中に、名前を付けられる意味のまとまり がある✅ 分ける（Extract Method）。抽象度をそろえる（サイズと抽象度）
    分けたメソッドが 単独で理解でき、再利用もできる✅ 分ける
    分けたメソッドを 必ずセットで順番に呼ぶ必要がある❌ 分けない（前半・後半の分割）
    分けたメソッドが 呼び出し元の変数や状態に強く依存 し、引数が大量に必要になる❌ 分けない、またはクラスに抽出（Replace Function with Command）
    メソッドが 引数をそのまま別のメソッドに渡すだけ❌ パススルーメソッド。統合を検討
    分けると 名前が「step1」「doRest」のようにしか付けられない❌ 意味のある単位ではない

    Replace Function with Command は、関数をその処理専用のクラス（コマンドオブジェクト）に置き換え、たくさんの変数をそのクラスのフィールドとして持たせるリファクタリングです。パススルーメソッド は、受け取った引数をそのまま別のメソッドに渡すだけで、自分では何もしないメソッドです。

    迷ったときの問い

    判断に迷ったら、「分けたメソッドに、中身を見なくても分かる良い名前が付けられるか」 を問います。付けられるなら分ける価値があり、付けられないなら分け方が間違っています（→ 命名）。

    7.よくある誤解

    誤解1：「メソッドは短いほど良い」

    常にではありません。 短くても浅いメソッドが増えると、全体の複雑さはむしろ増えます。短さではなく 深さ で判断します。

    誤解2：「重複がなければ分ける必要はない」

    誤りです。 重複がなくても、汎用的な処理と特化した処理が混ざっている なら、分けると理解しやすくなります。

    誤解3：「分けておけば後から再利用できる」

    多くの場合、再利用されません。 「いつか再利用するかも」で分けるのは YAGNI 違反です（→ KISS・DRY・YAGNI）。分ける理由は、今の理解しやすさ であるべきです。

    8.まとめ

    • メソッドの価値は やってくれる処理（利益）÷ シグネチャの複雑さ（コスト）。深いメソッド を目指す
    • 一緒にすべきサイン：情報を共有している、一緒に使われる、概念的に重なる、片方を読まないと理解できない（結合したメソッド）、一緒にするとインターフェースが単純になる
    • 分けるべきサイン：汎用的な処理と特化した処理が混ざっている、よりきれいな抽象に分けられる
    • 良い分割は サブタスクの抽出 と 独立した操作への分割。悪い分割は 前半と後半に切る こと
    • 迷ったら、中身を見なくても分かる名前が付けられるか を問う
