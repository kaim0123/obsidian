    50 副作用と状態

    オブジェクトのメソッド — 状態とルールを同じ場所に置く

    オブジェクト指向（OOP）では、メソッドは「オブジェクトの状態に対する操作」です。このページでは、OOP におけるメソッド設計として、Tell, Don't Ask、貧血モデル の問題、ドメインルールをメソッドに置く方法、そして手続き型の関数との使い分けを学びます。

    もとにしたノート：04_オブジェクトのメソッド

    ひとことで言うと

    メソッドは オブジェクトの状態に対する操作 です。中身を取り出して呼ぶ側で判断せず、オブジェクトにお願いする（Tell, Don't Ask）。業務ルールを外のサービスに逃がす 貧血モデル を避け、ドメインルールはオブジェクトのメソッドに、横断的・無状態な処理は関数に 置きます。

    2.状態に対する操作としてメソッドを定義する

    OOP では、メソッドは オブジェクトの状態に対する操作 として定義します。状態 とは、オブジェクトが持っているデータ（フィールド）の今の値のことです。

    class Order {
  constructor(items) {
    this.items = items;
    this.status = 'draft';
  }

  calculateTotal() {
    return this.items.reduce((s, i) => s + i.price * i.qty, 0);
  }

  submit() {
    if (this.status !== 'draft') throw new Error('already submitted');
    this.status = 'submitted';
  }
}

    データ（items, status）と振る舞い（calculateTotal, submit）が 同じクラス にまとまります。

    3.Tell, Don't Ask — データを取り出さずお願いする

    Tell, Don't Ask（尋ねるな、命じよ）とは、オブジェクトの内部を 取り出して判断せず、お願い（メッセージ） する、という考え方です。

    ✕ 悪い例：Ask（中身を取り出して判断） 
    if (order.status === 'draft' && order.items.length > 0) {
  order.status = 'submitted';
}
    ◯ 良い例：Tell（オブジェクトにお願い） 
    order.submit();

    ロジックが 呼び出し側 に散らばると、変更時に複数箇所を直す必要があります。「下書きのときだけ提出できる」というルールが変わったとき、order.submit() の中だけを直せば済むのが Tell の良さです。

    4.貧血モデル — ロジックがサービスに逃げる問題

    貧血モデル（Anemic Domain Model）とは、エンティティが データの入れ物 になっていて、ロジックが サービスクラス に集中した状態です。エンティティ は注文や会員のように ID で区別される業務上のもの、サービスクラス は処理だけを持つクラスです。

    ✕ 貧血：Order はデータだけ 
    class Order {
  constructor(items, status) {
    this.items = items;
    this.status = status;
  }
}
    ✕ ロジックが OrderService に集中 
    class OrderService {
  submit(order) {
    if (order.status !== 'draft') throw new Error('...');
    order.status = 'submitted';
  }
}
    • 問題：ドメインルールがサービスに散在し、Order の不変条件（いつも守られているべき約束。例：「提出済みの注文は下書きに戻らない」）がクラスの外に漏れる
    • 対策：ルールを Order.submit() などの メソッドに移す

    移動の具体的な手順（短いメソッド・インスタンス変数を使う・肥大化したら分ける）は 44章：業務ロジックをデータと一体にする、貧血モデルの背景は 44章：Tell, Don't Ask と貧血モデル を参照してください。

    5.ドメインルールをメソッドに置く

    変更理由がドメイン（業務の決まりごと）にあるルールは、ドメインオブジェクトのメソッドに置きます。

    ◯ 提出のルールを Order 自身が持つ 
    class Order {
  submit() {
    if (this.status !== 'draft') {
      throw new Error('Order must be draft to submit');
    }
    if (this.items.length === 0) {
      throw new Error('Order must have items');
    }
    this.status = 'submitted';
  }

  isSubmittable() {
    return this.status === 'draft' && this.items.length > 0;
  }
}

    isSubmittable() は Query（状態を変えずに値を返す、副作用なし）、submit() は Command（状態を変える）です（→ CQS）。

    6.手続き型関数 vs OOP メソッドの使い分け

    向く場面手続き型関数OOP メソッド
    状態を持たない変換◎ formatDate()△
    1オブジェクトのルール△◎ order.submit()
    複数オブジェクトの協調◎ オーケストレーション関数△ サービス
    ユーティリティ◎ clamp(value, min, max)△

    オーケストレーション関数 は、複数のオブジェクトを順に呼んで1つの処理を組み立てる関数です（オーケストラの指揮者のような役）。

    方針

    ドメインルールはオブジェクトに、横断的・無状態 の処理は関数に置きます。クラス設計の詳細は 44章：クラス設計 を参照してください。

    7.よくある誤解

    誤解1：「ゲッターで値を取り出して、呼ぶ側で判断すれば十分」

    ルールが呼ぶ側に散らばります。 同じ判断を何か所にも書くことになり、ルールが変わったときに直し漏れが起きます。判断はオブジェクトのメソッド（order.submit()・order.isSubmittable()）に任せます。

    誤解2：「ロジックはすべてサービスクラスに集めるのが整理された設計」

    それが貧血モデルです。 1つのオブジェクトのルールは、そのオブジェクトのメソッドに置きます。サービスや関数に向くのは、複数オブジェクトの協調や、状態を持たない変換です。

    誤解3：「OOP なら、どんな処理もクラスのメソッドにすべき」

    違います。 formatDate() や clamp() のような状態を持たない変換・ユーティリティは、手続き型の関数の方が向いています。

    8.まとめ

    • メソッド ＝ 状態に対する操作。データと振る舞いを同じクラスにまとめる
    • Tell, Don't Ask — 取り出さずお願いする
    • 貧血モデル はロジックをサービスに逃がし、不変条件をクラスの外に漏らす問題
    • ドメインルールはメソッドに。横断的・無状態な処理は関数に。使い分けを意識する
