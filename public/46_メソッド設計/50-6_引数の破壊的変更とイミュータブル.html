    50 副作用と状態

    引数の破壊的変更とイミュータブル — 受け取ったデータを書き換えない

    引数の設計 では「出力引数を避ける」ことを学びました。このページでは、それをさらに一般化して、メソッドが受け取った引数を書き換えてしまう問題（破壊的変更）と、その防ぎ方を学びます。うっかり破壊的になる JavaScript のメソッド、コピーオンライトと防御的コピー、ES2023 の非破壊的な配列メソッド、浅いコピーと深いコピー、TypeScript の readonly を解説します。

    もとにしたノート：07_引数の破壊的変更とイミュータブル

    ひとことで言うと

    受け取った引数の中身を書き換える 破壊的変更 は、呼ぶ側が予想できず、離れた場所に影響し、関数をアクションにしてしまいます。コピーを作り、コピーを変更して、コピーを返す（コピーオンライト）、信頼できないコードとの境界では 防御的コピー、引数の型は readonly にして「書き換えない」をシグネチャで約束します。イミュータブル（一度作ったら変更しない）なデータの扱い方です。

    1.このページで扱うこと

    • 破壊的変更 とは何か、なぜ危険か
    • JavaScript で うっかり破壊的になる 典型的なメソッド（sort・reverse・splice…）
    • 防ぐための技法：コピーオンライト と 防御的コピー（Grokking Simplicity）
    • ES2023 の 非破壊的な配列メソッド（toSorted・toReversed・toSpliced・with）
    • 浅いコピーと深いコピー、structuredClone
    • TypeScript の readonly で コンパイル時に防ぐ 方法

    ES2023 は、2023年版の JavaScript の仕様（ECMAScript 2023）のことです。

    2.破壊的変更とは

    2.1 定義

    メソッドが、引数として受け取ったオブジェクトや配列の中身を書き換えること。

    ✕ 引数を書き換えている 
    function applyDiscount(order: Order, rate: number): Order {
  order.total = order.total * (1 - rate);   // 引数を書き換えている
  return order;
}

const original = { id: 1, total: 1000 };
const discounted = applyDiscount(original, 0.1);

console.log(discounted.total);  // 900
console.log(original.total);    // 900 ← 元のデータも変わってしまった

    JavaScript / TypeScript では、オブジェクトと配列は参照で渡される ため、メソッドの中での変更が呼び出し元にも見えてしまいます。参照で渡す とは、中身のコピーではなく「データの置き場所」を渡すことで、呼ぶ側と呼ばれる側が同じデータを見ている状態になります。

    2.2 なぜ危険か

    問題説明
    呼ぶ側が予想しない関数名から「元のデータが変わる」ことが読み取れない。applyDiscount が引数を変えるとは思わない
    離れた場所に影響する同じオブジェクトを別の場所でも使っていると、そちらも変わる（エイリアシング問題：1つのデータを複数の変数が指していること）
    関数がアクションになる引数の書き換えは 暗黙的な出力。計算のつもりがアクションになる（→ アクション・計算・データ）
    テストしにくいテストで使ったデータが書き換わり、後のテストに影響する
    React などで更新が検出されない参照が同じままなので、「変わった」と判定されず画面が更新されない
    デバッグが難しい「どこで値が変わったのか」を探すために、データを受け取ったすべての関数を調べる必要がある

    2.3 CQS との関係

    CQS の観点では、値を返す関数（クエリ）が引数を書き換える のは、クエリとコマンドが混ざっている状態です。

    3.うっかり破壊的になる JavaScript のメソッド

    JavaScript の配列メソッドには、元の配列を書き換えるもの と 新しい配列を返すもの が混在しています。

    元の配列を 書き換える（破壊的）新しい配列を返す（非破壊的）
    sort()toSorted()（ES2023）、[...arr].sort()
    reverse()toReversed()（ES2023）
    splice()toSpliced()（ES2023）、slice()
    arr[i] = xwith(i, x)（ES2023）
    push() / pop() / shift() / unshift()[...arr, x]、arr.slice(0, -1)、concat()
    fill() / copyWithin()map()
    —map() / filter() / concat() / slice() / flat()

    3.1 典型的なバグ

    ✕ sort が元の配列を並べ替える 
    function getTopScores(scores: number[]): number[] {
  return scores.sort((a, b) => b - a).slice(0, 3);   // sort が元の配列を並べ替える
}

const scores = [50, 80, 30, 90];
const top = getTopScores(scores);
console.log(scores);  // [90, 80, 50, 30] ← 呼び出し元の配列の順番が変わった
    ◯ ES2023 の toSorted を使う 
    function getTopScores(scores: readonly number[]): number[] {
  return scores.toSorted((a, b) => b - a).slice(0, 3);
}

    4.防ぐための技法

    Eric Normand『Grokking Simplicity』は、イミュータブルにするための技法を2つ紹介しています。

    4.1 コピーオンライト（Copy-on-Write）

    データを変更するときは、まずコピーを作り、コピーを変更して、コピーを返す。元のデータには手を触れない。

    ◯ コピーオンライトの書き方 
    // 配列への追加
function addItem(cart: readonly Item[], item: Item): Item[] {
  return [...cart, item];
}

// 配列の要素の更新
function updateQuantity(cart: readonly Item[], name: string, qty: number): Item[] {
  return cart.map((i) => (i.name === name ? { ...i, quantity: qty } : i));
}

// 配列からの削除
function removeItem(cart: readonly Item[], name: string): Item[] {
  return cart.filter((i) => i.name !== name);
}

// オブジェクトのプロパティの更新
function applyDiscount(order: Order, rate: number): Order {
  return { ...order, total: order.total * (1 - rate) };
}

    手順は常に同じです。

    1. コピーを作る（スプレッド構文 ...・slice・map）
    2. コピーを変更する
    3. コピーを返す

    これにより、関数は 計算 のままになります（→ アクション・計算・データ）。スプレッド構文（...）は、配列やオブジェクトの中身を展開して、新しい配列・オブジェクトに詰め直す書き方です。

    4.2 防御的コピー（Defensive Copying）

    自分が管理していないコード（外部ライブラリ・古いコード）とデータをやり取りするとき、渡す前と受け取った後にコピーを作る。

    class ShoppingCart {
  private items: Item[] = [];

  // 受け取るとき：外から渡された配列をコピーしてから保持する
  // （呼ぶ側が後で元の配列を変えても、こちらは影響を受けない）
  replaceAll(items: Item[]) {
    this.items = structuredClone(items);
  }

  // 渡すとき：内部の配列のコピーを返す
  // （呼ぶ側が返された配列を変えても、こちらは影響を受けない）
  getItems(): Item[] {
    return structuredClone(this.items);
  }
}

// 破壊的変更をするかもしれない外部ライブラリを呼ぶとき
const result = legacyLibrary.process(structuredClone(myData));
    技法使う場面コピーの深さ
    コピーオンライト自分のコード の中でデータを変更するとき浅いコピーで十分なことが多い（変更する部分だけ）
    防御的コピー信頼できないコード との境界でデータをやり取りするとき深いコピーが必要なことが多い

    5.浅いコピーと深いコピー

    5.1 浅いコピーの落とし穴

    スプレッド構文 ... や slice() は 浅いコピー です。1段目だけ が新しくなり、中のオブジェクトは元と共有されます。

    ✕ 中のオブジェクトは共有されている 
    const order = { id: 1, customer: { name: "田中", address: "東京" } };
const copy = { ...order };

copy.customer.address = "大阪";
console.log(order.customer.address);  // "大阪" ← 中のオブジェクトは共有されていた

    5.2 ネストしたデータを更新する

    コピーオンライトでネストした（入れ子になった）データを変えるときは、変更する経路のすべての段をコピー します。

    ◯ 経路の各段をコピーする 
    const updated = {
  ...order,
  customer: { ...order.customer, address: "大阪" },
};

    ネストが深くて書きにくい場合は、Immer のようなライブラリを使うと、破壊的な書き方のまま、内部でコピーオンライトをしてくれます。

    import { produce } from "immer";
const updated = produce(order, (draft) => { draft.customer.address = "大阪"; });

    5.3 深いコピー：structuredClone

    const deep = structuredClone(order);   // すべての段を再帰的にコピー
    • ブラウザと Node.js（17以降）で標準で使える
    • JSON.parse(JSON.stringify(x)) と違い、Date・Map・Set・循環参照（オブジェクトが巡り巡って自分自身を指している構造）も扱える
    • 関数・クラスのインスタンスのメソッドはコピーできない点に注意
    • 深いコピーはコストがかかるので、防御的コピーなど本当に必要な場面 で使う

    6.TypeScript でコンパイル時に防ぐ

    function getTopScores(scores: readonly number[]): number[] {
  scores.sort();         // ✕ コンパイルエラー：readonly 配列に sort はない
  return scores.toSorted((a, b) => b - a).slice(0, 3);   // ◯
}

function applyDiscount(order: Readonly<Order>, rate: number): Order {
  order.total = 0;       // ✕ コンパイルエラー：読み取り専用
  return { ...order, total: order.total * (1 - rate) };  // ◯
}
    書き方効果
    readonly T[] / ReadonlyArray<T>配列の書き換えメソッド（push・sort など）を禁止
    Readonly<T>オブジェクトの1段目のプロパティの書き換えを禁止
    readonly 修飾子特定のプロパティの書き換えを禁止
    as constリテラルを深く読み取り専用にする

    引数の型を readonly にしておくと、「この関数は引数を書き換えません」という約束がシグネチャに現れます。呼ぶ側も安心して渡せます。

    注意

    Readonly<T> は 浅い（1段目だけ）です。深く読み取り専用にしたい場合は、自分で DeepReadonly 型を定義するか、ライブラリを使います。また、readonly は コンパイル時のチェックだけ で、実行時には防げません（実行時にも防ぎたいなら Object.freeze）。

    7.破壊的変更が許される場面

    場面理由
    関数の中で作ったローカルな配列・オブジェクト外から見えないので、書き換えても誰にも影響しない（例：関数の中で const result = [] を作って push する）
    性能が本当に重要なホットパス大量データのコピーが計測上のボトルネックになっている場合（ホットパス：何度も実行され、性能を左右する部分）
    名前と型で破壊的であることが明確 なメソッドsortInPlace(arr) のように、名前で書き換えることを宣言している
    オブジェクト自身の状態を変えるコマンドcart.addItem(item) は、引数ではなく 自分自身 の状態を変えるので、カプセル化の範囲内

    問題なのは 他人から受け取った引数 を書き換えることです。自分で作ったデータや、自分自身の状態を変えることとは区別します。

    自分自身の状態を変えるメソッドの設計は オブジェクトのメソッド で扱っています。

    8.よくある誤解

    誤解1：「const で宣言すれば変更されない」

    誤りです。 const は 変数の再代入 を禁止するだけで、中身（配列の要素・オブジェクトのプロパティ）の変更は防げません。readonly や Object.freeze が必要です。

    誤解2：「スプレッド構文でコピーすれば安全」

    浅いコピーです。 ネストしたオブジェクトは共有されたままです。変更する経路のすべての段をコピーする必要があります。

    誤解3：「イミュータブルにすると遅くなる」

    多くの場合、問題になりません。 コピーオンライトは変更する部分だけをコピーし、変わらない部分は共有します（構造共有）。計測して問題があれば、その部分だけ最適化します。

    9.まとめ

    • 破壊的変更：受け取った引数の中身を書き換えること。呼ぶ側が予想できず、離れた場所に影響し、関数をアクションにする
    • JavaScript の sort・reverse・splice は 元の配列を書き換える。ES2023 の toSorted・toReversed・toSpliced・with を使う
    • コピーオンライト：コピーを作り、コピーを変更し、コピーを返す（自分のコードの中で）
    • 防御的コピー：信頼できないコードとの境界で、渡す前・受け取った後にコピーする
    • スプレッド構文は 浅いコピー。ネストは各段をコピーするか、Immer・structuredClone を使う
    • 引数を readonly にして、書き換えないことを シグネチャで約束 する
    • 書き換えてよいのは、自分で作ったローカルなデータ と 自分自身の状態
