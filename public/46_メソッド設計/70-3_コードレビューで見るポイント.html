    70 品質と運用

    コードレビューで見るポイント — メソッド設計の観点で読む

    コードレビューで「なんとなく読みにくい」と感じても、どこをどう直せばよいかを伝えるのは意外と難しいものです。このページでは、メソッド設計 の観点でレビューを進める順番、チェックリスト、良い関数・悪い関数の比較、改善提案の書き方、そして新人へのフィードバックの仕方を学びます。

    もとにしたノート：03_コードレビューで見るポイント

    ひとことで言うと

    レビューは 構造 → 読みやすさ → エラー → スタイル の順に、時間の多くを構造に使います。指摘は「読みにくい」で終わらせず、観察・影響・提案・参考 の型で、具体的な改善案まで書きます。

    1.このページで扱うこと

    このページは、メソッド設計 の観点でコードレビューを進めるためのページです。

    • メソッド設計レビューの進め方

    レビューをまとまった演習として行う方法は 設計レビューの実践 で扱います。クラス単位のレビューは 44章：クラス設計レビュー を参照してください。

    2.メソッド設計レビューの進め方

    1. 全体像 — オーケストレーション関数から読む（流れの目次）
    2. 粒度 — 1 関数 1 責任か、抽象度は揃っているか
    3. 制御 — ネスト・複雑度・Guard Clause
    4. 契約 — 副作用・CQS・エラー処理
    5. テスト — 単体テスト可能か

    オーケストレーション関数 とは、自分では細かい処理をせず、小さな関数を順に呼び出して全体の流れを組み立てる関数です。本の目次のように、読めば処理の流れがつかめます。

    レビュー時間の配分（目安）：

    配分見るところ
    40%構造・分割・責任
    30%読みやすさ・命名
    20%エラー・副作用
    10%スタイル・細部

    3.レビュー用チェックリスト

    • ☐ 1 メソッド 1 種類の仕事（SoC / SRP。関心の分離と単一責任）
    • ☐ 50 行超・複雑度 10 超の関数がないか
    • ☐ ネスト 3 段以上 → Guard Clause を検討
    • ☐ process() handleData() 等の曖昧名がないか（命名）
    • ☐ getter に副作用がないか（CQS）
    • ☐ 引数 3 個以上 → Parameter Object を検討（引数の設計）
    • ☐ 純粋にできる計算が I/O と混在していないか

    複雑度（循環的複雑度）は、関数の中の分岐の多さを数えた指標です（複雑度と分岐）。

    総合版：チェックリストとアンチパターン

    4.良い関数・悪い関数の比較

    4.1 悪い例

    ✕ 悪い例 
    function handle(data, flag) {
  if (data) {
    if (flag) {
      db.save(data);
      return data.total;
    }
  }
}
    問題内容
    名前handle が曖昧
    フラグ引数flag で複数責任
    ネスト正常系が深い
    CQS保存と取得が混在

    フラグ引数 とは、true / false を渡して関数の動きを切り替える引数です。1つの関数が2つの仕事を持っているサインになります。

    4.2 良い例

    ◯ 良い例 
    function persistAndGetTotal(order) {
  if (!order) return null;
  persistOrder(order);
  return order.total;
}

    さらに persistOrder と getTotal に分離すると CQS に沿います。

    5.改善提案の書き方

    建設的なフィードバック の型：

    1. 観察 — 「この関数は 80 行で、検証と保存が混在しています」
    2. 影響 — 「テストで DB モックが必要になります」
    3. 提案 — 「validateOrder と saveOrder に Extract Method しませんか」
    4. 参考 — 「Extract Method の 6.3 節」

    ✕ 「読みにくい」だけ

    どこを、なぜ、どう直せばよいかが伝わりません。

    ◯ 具体的な提案

    「検証部分（L12-45）を validateOrder() に切り出すと、単体テストしやすくなります」

    6.新人へのフィードバックの仕方

    避ける推奨
    人格批判コードへの指摘
    一度に 20 指摘優先度付き 3 点
    正解だけ提示理由と参考リンク

    ペアで読む

    オーケストレーション関数を一緒に上から読み、「ここで何をしている？」と問いかけると、新人自身が分割点を見つけやすくなります。

    7.よくある誤解

    誤解1：「レビューではスタイルの細部を丁寧に見るのが大事」

    優先度は低めです。 時間の配分は構造・分割・責任が 40%、スタイル・細部は 10% が目安です。インデントなどの細部は Formatter や Lint に任せ、人は構造を見ます（チームでメソッド設計を守る）。

    誤解2：「気づいたことは全部指摘したほうが親切」

    特に新人には逆効果です。 一度に 20 個の指摘は受け止めきれません。優先度を付けて 3 点に絞り、理由と参考リンクを添えます。

    誤解3：「『読みにくい』と伝えれば十分」

    伝わりません。 観察（何が起きているか）・影響（何が困るか）・提案（どう直すか）・参考（どこを読めばよいか）までそろえて初めて、相手が動ける指摘になります。

    8.まとめ

    • レビューは構造 → 読みやすさ → エラー → スタイルの順
    • チェックリストで抜け漏れを防ぐ
    • 改善提案は観察・影響・提案・参考
    • 新人には理由付きで、優先度を絞る
