    30 シグネチャ設計

    戻り値の設計 — 型でメソッドの約束を語る

    メソッドが何を返すかは、呼ぶ側が「何に備えればよいか」を決める大事な約束です。このページでは、戻り値の基本方針、boolean を返すとき・返すべきでないとき、「ないかもしれない」値の返し方、失敗するかもしれない処理の返し方、コレクション・複数の値・非同期の戻り値を順に整理し、最後にチェックリストにまとめます。

    もとにしたノート：04_戻り値の設計

    ひとことで言うと

    戻り値の型は メソッドの約束そのもの です。1 つの戻り値に 1 つの意味 を持たせ、「ないかもしれない」は T | undefined、想定内の失敗は Result 型、0 件は 空のコレクション、複数の値は 名前付きのオブジェクト で返します。

    1.このページで扱うこと

    引数の設計 では「何を受け取るか」を、情報隠蔽 では「内部構造を戻り値で漏らさない」ことを学びました。このページでは、メソッドが何を、どんな形で返すべきか を体系的に整理します。

    • 戻り値の 基本方針（1 つの意味・型で語る）
    • boolean を返すとき・返すべきでないとき
    • 「ないかもしれない」値の返し方（null・undefined・Optional）
    • 失敗するかもしれない処理の返し方（例外・Result 型）
    • コレクション を返すとき（空配列・読み取り専用・コピー）
    • 複数の値 を返すとき（オブジェクト・タプル）
    • 非同期 の戻り値（Promise）

    null と Result 型の詳しい使い分けは null・undefined・Result型の使い分け で扱います。

    2.戻り値の基本方針

    2.1 戻り値の型で、メソッドの約束を語る

    戻り値の型は、メソッドの 最も重要なドキュメント です。

    function findUser(id: string): User                       // 必ず見つかる（見つからなければ例外？）
function findUser(id: string): User | undefined           // 見つからないことがある
function findUser(id: string): Result<User, NotFound>     // 見つからないことがあり、理由も返す
function findUser(id: string): Promise<User | undefined>  // 非同期で、見つからないことがある

    型を見るだけで「呼ぶ側が何に備えるべきか」が分かるようにします。

    2.2 1つの戻り値に、1つの意味

    ✕ 戻り値の意味が混ざっている 
    function findIndex(items: Item[], id: string): number {
  // 見つかれば位置、見つからなければ -1
}
// 呼ぶ側が -1 のチェックを忘れると、items[-1] で undefined を扱い続ける
    ◯ 「見つからない」を型で表す 
    function findItem(items: Item[], id: string): Item | undefined
    • 特別な値（番兵値） で別の意味を表すのは、呼ぶ側がその約束を知っていないと危険です。番兵値 とは、-1 のように「普通の値の範囲に、特別な意味を持つ値を紛れ込ませたもの」です
    • -1・0・""・null に特別な意味を持たせない

    2.3 CQS を守る

    CQS（コマンドとクエリの分離）のとおり、状態を変えるメソッド（コマンド）は原則として値を返さない、値を返すメソッド（クエリ）は状態を変えない のが基本です。

    ✕ 状態を変えつつ、成功したかを boolean で返す 
    if (cart.addItem(item)) { ... }
    ◯ 判断はクエリ、変更はコマンド 
    if (cart.canAdd(item)) cart.addItem(item);

    ただし、作成したオブジェクトの ID を返す・スタックの pop（取り出しと同時に値を返す）のように、慣習として値を返すコマンドもあります。

    3.boolean を返すとき

    3.1 boolean が適している場面

    「〜か？」という問いに答えるクエリ は boolean を返します。

    isExpired(): boolean
hasPermission(user: User, action: Action): boolean
canCancel(): boolean
    • 名前は is / has / can / should で始める（→ 命名）
    • 否定形の名前（isNotValid）は避ける。!isNotValid() は読みにくい

    3.2 boolean を返すべきでない場面

    場面問題代わりに
    失敗の理由を知りたいfalse だけでは、なぜ失敗したか分からないResult 型・理由を表す型
    3つ以上の状態があるtrue / false に詰め込むと意味が曖昧になる列挙型・判別可能ユニオン
    成功・失敗を返すコマンド呼ぶ側が戻り値を無視しやすい（失敗に気づかない）例外・Result 型

    列挙型 は決まった選択肢だけをとる型、判別可能ユニオン は「type などの共通の項目で、どの種類かを区別できる複数の型の組み合わせ」です。

    ✕ false の理由が分からない 
    function validatePassword(pw: string): boolean
    ◯ 理由を返す 
    type PasswordError = "tooShort" | "noNumber" | "noUppercase";
function validatePassword(pw: string): PasswordError[]   // 空配列なら OK

    4.「ないかもしれない」値を返すとき

    4.1 選択肢

    返し方例向いている
    T | undefinedfind(id): User | undefinedTypeScript で「見つからない」を表す最も一般的な方法
    T | nullgetAttribute(name): string | null「意図的に値がない」ことを明示したいとき（DOM API・DB の NULL）
    Optional / Maybe 型Java の Optional<User>、Rust の Option<User>言語やライブラリが用意している場合
    例外を投げるgetById(id): User（なければ例外）存在しないことがバグ である場合
    空のオブジェクト（Null Object）GuestUser を返す「ない場合」にも同じインターフェースで振る舞わせたい場合

    Null Object は、「何もしない」「既定の振る舞いをする」オブジェクトを null の代わりに返すパターンです。呼ぶ側は null チェックをせずにそのまま使えます。

    4.2 名前で区別する慣習

    findUser(id: string): User | undefined   // find〜：見つからないことがある（正常）
getUser(id: string): User                // get〜：必ずある。なければ例外（異常）

    find と get のように 名前で約束を区別する 慣習は、多くのコードベースやライブラリで使われています（チームで統一します）。

    TypeScript では、strictNullChecks（null・undefined を厳密に扱うコンパイラ設定）を有効にすると、User | undefined を返すメソッドの戻り値を チェックせずに使うとコンパイルエラー になります。詳しくは null・undefined・Result型の使い分け を参照してください。

    5.失敗するかもしれない処理を返すとき

    返し方向いている注意点
    例外を投げる想定外の失敗（DB 接続断・バグ）、呼ぶ側がその場で対処できない失敗シグネチャに現れないので、呼ぶ側が見落としやすい
    Result 型を返す想定内の失敗（入力エラー・在庫切れ・権限なし）、呼ぶ側が分岐して対処すべき失敗呼ぶ側のコードが少し長くなる

    Result 型 は、「成功してこの値が得られた」か「失敗してこの理由だった」かのどちらかを表す型です。

    type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

function placeOrder(cart: Cart): Result<Order, "emptyCart" | "outOfStock" | "paymentDeclined"> { ... }

const r = placeOrder(cart);
if (!r.ok) {
  switch (r.error) { /* それぞれに応じた表示 */ }
}

    詳しくは エラー処理 と null・undefined・Result型の使い分け を参照してください。

    6.コレクションを返すとき

    6.1 「ない」ときは空のコレクションを返す

    ✕ 0件のときに null を返す → 呼ぶ側は毎回 null チェックが必要 
    function findOrders(userId: string): Order[] | null
    ◯ 0件なら空配列 
    function findOrders(userId: string): Order[]

for (const o of findOrders(id)) { ... }   // 0件でもそのまま動く
    • 空配列なら、for ループ・map・length がすべてそのまま動く
    • これは エラーが起きない設計にする の「特殊なケースをなくす」考え方の一例です

    6.2 内部のコレクションをそのまま返さない

    class Order {
  private items: OrderItem[] = [];

  // ✕ 内部の配列そのもの → 呼ぶ側が push・splice できてしまう
  getItems(): OrderItem[] { return this.items; }

  // ○ 読み取り専用の型で返す（コンパイル時に防ぐ）
  getItems(): ReadonlyArray<OrderItem> { return this.items; }

  // ○ コピーを返す（実行時にも防ぐ）
  getItemsCopy(): OrderItem[] { return [...this.items]; }
}

    これは 情報隠蔽 と、44章の Tell, Don't Ask と貧血モデル の「コレクションの getter」で扱った話と同じです。

    6.3 型は「使う側に必要な最小限」にする

    // 呼ぶ側が反復するだけなら、配列である必要はない
function activeUsers(): Iterable<User>
function activeUsers(): ReadonlyArray<User>
    • 戻り値の型を 具体的すぎるもの（Array・Map）にすると、内部実装を変えにくくなる
    • 一方で、抽象的すぎると呼ぶ側が使いにくい。呼ぶ側が実際に使う操作 に合わせる

    Iterable は「for...of で順に取り出せる」ことだけを約束する型です。

    7.複数の値を返すとき

    ✕ 出力引数（引数を書き換えて結果を返す） 
    function parse(input: string, outErrors: string[]): Data { ... }
    △ タプル：順番の意味を覚える必要がある（位置のコナーセンス） 
    function minMax(xs: number[]): [number, number]
    ◯ 名前付きのオブジェクト 
    function minMax(xs: number[]): { min: number; max: number }
const { min, max } = minMax(values);
    • 出力引数は避ける（→ 引数の設計）
    • タプル（決まった数の値を順番で並べた配列）は、意味が自明な2つ程度（[key, value]、React の [state, setState]）に限る。順番に意味を持たせる依存は 41章：コナーセンス でいう「位置のコナーセンス」です
    • それ以外は 名前付きのオブジェクト にする。複数の値がいつも一緒に返るなら、値オブジェクト にすることも検討する（44章の 値オブジェクトと完全コンストラクタ）

    8.非同期の戻り値

    async function fetchUser(id: string): Promise<User | undefined>

    Promise は「あとで値が届く（または失敗する）」ことを表すオブジェクトで、await で結果を待てます。

    • async 関数は 常に Promise を返す。戻り値の型は Promise<T> と明示する
    • Promise を返すメソッドの戻り値は、必ず await するか、意図的に扱う。await を忘れると、エラーが握りつぶされる（ESLint の @typescript-eslint/no-floating-promises で検出できる）
    • 「値を返すこともあれば Promise を返すこともある」メソッドは作らない。同期か非同期か、どちらかに統一 する

    9.戻り値の設計チェックリスト

    • ☐ 戻り値の型を見るだけで、呼ぶ側が何に備えるべきか 分かるか？
    • ☐ -1 や null のような 番兵値 に特別な意味を持たせていないか？
    • ☐ boolean を返すメソッドは、問いに答えるクエリ になっているか？ 理由が必要な場面で boolean を返していないか？
    • ☐ 「ないかもしれない」ことが 型に現れて いるか？（find / get の使い分け）
    • ☐ 想定内の失敗を 例外だけ で表していないか？
    • ☐ コレクションは、0件のときに 空のコレクション を返しているか？
    • ☐ 内部のコレクションを そのまま 返していないか？
    • ☐ 複数の値を 意味の分かる名前付きのオブジェクト で返しているか？

    10.よくある誤解

    誤解1：「見つからないときは -1 や null を返せば十分」

    番兵値は、呼ぶ側がその約束を 知っていて、毎回チェックする ことを前提にしています。チェックを忘れても型では気づけません。T | undefined のように 型に表す と、コンパイラが確認してくれます。

    誤解2：「失敗はすべて例外で表せばよい」

    例外はシグネチャに現れないため、呼ぶ側が見落としやすくなります。入力エラー・在庫切れのような 想定内の失敗 は Result 型で返し、例外は 想定外の失敗 に使います。

    誤解3：「0件のときは null を返すほうが『ない』ことがはっきりする」

    コレクションの場合は 空のコレクション で「ない」を表せます。null を返すと、呼ぶ側すべてに null チェックを強いることになります。

    11.まとめ

    • 戻り値の型は メソッドの約束そのもの。型を見れば、呼ぶ側が何に備えるべきかが分かるようにする
    • 1つの戻り値に1つの意味。番兵値（-1・null）に特別な意味を持たせない
    • boolean は「〜か？」に答えるクエリに使う。理由が必要なら、理由を表す型を返す
    • 「ないかもしれない」は T | undefined などで型に表す。find（ないこともある）と get（必ずある）を名前で区別する
    • 想定内の失敗は Result 型、想定外の失敗は 例外
    • コレクションは 空のコレクション を返し、内部の配列をそのまま返さない
    • 複数の値は 名前付きのオブジェクト で返す
