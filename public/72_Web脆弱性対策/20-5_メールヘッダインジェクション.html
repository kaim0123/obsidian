    20 インジェクション

    メールヘッダインジェクション

    お問い合わせフォームや会員登録の確認メールなど、Webアプリは メール送信 をよく使います。このページでは徳丸本第12章をもとに、メール送信まわりで起きやすい脆弱性として、メールヘッダインジェクション、Hidden パラメータによる宛先保持、メールサーバーの第三者中継の3つと、その対策を解説します。

    もとにしたノート：20_インジェクション/06_メール送信の問題（徳丸本12章）

    ひとことで言うと

    「メールのヘッダと宛先はアプリが決める。ユーザー入力は本文にだけ使う」 のが、この章の要点です。入力値に改行を混ぜられると、宛先（Bcc など）を勝手に追加され、自社のサーバーがスパムの送信元にされてしまいます。

    1.メール送信の問題の概要

    メール送信機能には、主に次の問題があります。

    問題概要
    メールヘッダ・インジェクション外部入力で件名・送信元・宛先などを改変される
    Hidden パラメータによる宛先保持画面に隠した宛先を改ざんされ、別の人へ送られる
    第三者中継（参考）メールサーバーが誰でも中継でき、スパムの踏み台になる

    外部入力 とは、フォームの入力値や URL のパラメータなど、利用者（攻撃者を含む）が自由に送ってこられる値のことです。踏み台 とは、攻撃者が自分の身元を隠したり送信力を借りたりするために、他人のサーバーを中継点として悪用することをいいます。

    1.1 日常生活での例え

    正常なメール送信

    お問い合わせフォームから、運営宛にだけメールが届きます。

    攻撃された場合

    フォームが悪用され、他人へ迷惑メールやウイルス付きメールが送られます。

    1.2 なぜ危険か

    メール送信機能は、アプリが 「メールを送る権限」 を持っています。攻撃者にその権限を乗っ取られると、次のような被害が出ます。

    • 迷惑メール（スパム）の送信に悪用される
    • ウイルス付きメールの送信に悪用される
    • なりすましメールで フィッシング（偽サイトに誘導してパスワードなどをだまし取る詐欺）に使われる
    • 自社ドメインの信頼が下がる（ブラックリスト 入り。ブラックリストとは、スパム送信元として登録された IP アドレスやドメインの一覧で、載ると受信を拒否されやすくなります）

    2.メールヘッダインジェクション

    メールヘッダインジェクション（Email Header Injection） とは、フォームなどの 外部入力 に改行やヘッダ用の文字列を混ぜ込み、メールのヘッダを勝手に追加・改変する攻撃です。「インジェクション（注入）」という名前のとおり、SQLインジェクション や OSコマンドインジェクション と同じく、データのつもりの入力が「命令・構造」として解釈されてしまう のが原因です（インジェクション全般の考え方は インジェクションと暗号化の不備 を参照してください）。

    2.1 メールの構造（ざっくり）

    メールは大きく ヘッダ と 本文 に分かれます。ヘッダは「誰から・誰へ・件名は何か」を表します。ヘッダと本文の間は空行1つで区切られます。

    To: support@example.com
From: user@example.com
Subject: お問い合わせ
Bcc: attacker@evil.com          ← 攻撃者が勝手に追加したい行

こんにちは、質問があります。   ← 本文

    Bcc（Blind Carbon Copy）は、ほかの受信者には見えない形でメールのコピーを送る宛先です。To・Cc と違って受信者からは見えないため、攻撃者が宛先をこっそり追加するのに好都合です。

    ヘッダの各行は 改行（\r\n や \n） で区切られます。\r は CR（キャリッジリターン）、\n は LF（ラインフィード） という改行用の制御文字です。そのため、入力値に改行を入れると、新しいヘッダ行を追加したように見える ことがあります。

    2.2 攻撃のイメージ

    お問い合わせフォームで「メールアドレス」や「件名」をそのままヘッダに埋め込んでいる場合を考えます。

    【正常な入力】
メールアドレス: user@example.com

【攻撃者の入力】
メールアドレス: user@example.com%0ABcc: victim@example.com
                ↑ %0A は改行（URLエンコード）

    URLエンコード とは、URL やフォーム送信で特殊な文字を % ＋16進数で表す書き方です。%0A は LF、%0D は CR を表します。画面の入力欄には改行を打ち込めなくても、攻撃者はツールなどでリクエストを直接作り、改行入りの値を送ってきます。

    サーバー側でそのままヘッダに連結すると、次のように解釈されます。

    To: support@example.com
From: user@example.com
Bcc: victim@example.com   ← 攻撃者が追加した宛先
Subject: お問い合わせ

    2.3 何を改変されるか

    改変対象攻撃の例
    件名（Subject）迷惑な件名やフィッシング用の件名に差し替え
    送信元（From）信頼できる差出人に見せかける
    宛先（To / Cc / Bcc）第三者へ勝手にメールを送る
    本文ヘッダの後に本文を差し込み、ウイルスや詐欺文を送る

    2.4 悪用の典型例

    悪用説明
    迷惑メールの送信自社サーバーから大量のスパムを送らせる
    ウイルスメールの送信マルウェア（ウイルスなどの悪意あるプログラムの総称）付きメールの踏み台にする
    なりすまし正規サイトからのメールに見せかけて詐欺

    2.5 攻撃の流れ

    1. 攻撃者がお問い合わせフォームを見つける
    2. メールアドレス欄などに「改行 ＋ Bcc: 被害者」を入力
    3. アプリが入力値をそのままメールヘッダに埋め込む
    4. メールサーバーが追加ヘッダを解釈して送信
    5. 被害者に迷惑メール・ウイルスメールが届く
    6. 送信元は正規サイトのサーバーに見える

    3.メールヘッダインジェクションの対策

    対策の基本は 「外部入力をヘッダにそのまま載せない」 と 「改行を許さない」 です。

    3.1 外部からのパラメータをメールヘッダに含ませない

    最も安全なのは、ユーザー入力をヘッダに使わない ことです。

    ヘッダ項目推奨
    To（宛先）アプリ側で固定（例: support@example.com）
    From（送信元）アプリ側で固定（例: noreply@example.com）
    Subject（件名）固定文、または許可した文言のみ
    本文ユーザー入力は本文側にだけ載せ、ヘッダとは分離
    危険な例：ユーザー入力をヘッダに使う 
    From: （ユーザーが入力したメールアドレス）
Subject: （ユーザーが入力した件名）
    安全な例：ヘッダは固定し、入力は本文へ 
    From: noreply@example.com（固定）
Subject: 【お問い合わせ】受付完了（固定）
本文: お名前・内容などユーザー入力を載せる

    返信先が必要な場合は、From ではなく Reply-To（返信ボタンを押したときの宛先を指定するヘッダ）に検証済みのアドレスを入れる、または本文にだけ書く方法が安全です。

    3.2 外部パラメータに改行を含めないようチェックする

    ヘッダに載せる値がどうしても必要な場合は、改行文字を拒否 します。

    安全な例：改行が含まれていたらエラー（PHP） 
    // ✅ 改行が含まれていたらエラー
function hasNewline(string $value): bool
{
    return preg_match('/[\r\n]/', $value) === 1;
}

$email = $_POST['email'] ?? '';
$subject = $_POST['subject'] ?? '';

if (hasNewline($email) || hasNewline($subject)) {
    // 不正な入力として拒否
    exit('不正な入力です');
}

    preg_match は正規表現（文字列のパターン）に一致するかを調べる PHP の関数で、/[\r\n]/ は「CR か LF のどちらかを含む」という意味です。チェック対象の文字は次のとおりです。

    文字名前
    \rキャリッジリターン（CR）
    \nラインフィード（LF）
    \r\nWindows 系の改行

    補足：メールの改行は本来 CR LF です

    ノートでは \r\n を「Windows 系の改行」としていますが、メールの規格（RFC 5322）では、OS に関係なく \r\n（CR LF）がヘッダ行の正式な区切り です。ただし実際のメールソフトやサーバーは \n だけでも改行として扱うことが多いため、\r と \n のどちらか1文字でも含まれていれば拒否 する、という上のチェック方法で問題ありません。

    改行チェックは 最低限の防御 です。可能ならヘッダ自体に外部入力を使わない方が確実です。

    3.3 メール送信には専用の API やライブラリを使う

    昔の実装では、PHP の mail() 関数にヘッダ文字列を自分で組み立てて渡すことが多く、インジェクションが起きやすいです。

    危険な例：ヘッダを文字列連結で組み立てている 
    // ❌ 危険: ヘッダを文字列連結で組み立てている
$to = 'support@example.com';
$subject = $_POST['subject'];
$headers = "From: " . $_POST['email'] . "\r\n";
mail($to, $subject, $_POST['body'], $headers);

    専用ライブラリや API（外部サービスの機能をプログラムから呼び出すための窓口）を使うと、宛先・件名・本文を 別々の引数 で渡し、ライブラリ側がヘッダを安全に組み立てます。

    手段例
    言語のメールライブラリPHPMailer、Swift Mailer / Symfony Mailer、Python の email パッケージ
    外部メール APISendGrid、Amazon SES、Mailgun など

    補足：Swift Mailer は開発終了しています

    Swift Mailer は 2021年にメンテナンスが終了し、後継の Symfony Mailer へ移行するよう案内されています。これから使うなら Symfony Mailer（または PHPMailer）を選んでください。

    安全な例（イメージ）：項目ごとにセットする 
    // ✅ 良い例（イメージ）: 項目ごとにセットする
$mail = new PHPMailer();
$mail->setFrom('noreply@example.com');
$mail->addAddress('support@example.com');
$mail->Subject = '【お問い合わせ】受付完了';
$mail->Body = $safeBody;  // 本文のみユーザー入力を反映
$mail->send();

    ポイントは、ヘッダ文字列を自分で連結しない ことです。

    3.4 メールアドレスのチェック

    宛先や返信先にメールアドレスを使う場合は、形式チェック を行います。

    安全な例：形式チェックの例（PHP） 
    // ✅ 形式チェックの例（PHP）
$email = $_POST['email'] ?? '';

if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
    exit('メールアドレスの形式が正しくありません');
}

// 念のため改行も拒否
if (preg_match('/[\r\n]/', $email)) {
    exit('不正な入力です');
}

    filter_var($email, FILTER_VALIDATE_EMAIL) は、値がメールアドレスとして正しい形かを PHP 標準の機能で判定するものです。

    チェック内容理由
    形式が正しいかuser@example.com のような形か確認
    改行がないかヘッダインジェクション防止
    長さの上限異常に長い入力の拒否
    許可ドメイン（必要なら）社内メールのみ受け付ける等

    形式チェックだけでは不十分な場合もあるため、ヘッダに載せない設計 と組み合わせます。

    3.5 件名のチェック

    件名にユーザー入力を使う場合も、同様に検証します。

    安全な例：件名の改行・長さを検証する（PHP） 
    $subject = $_POST['subject'] ?? '';

// 改行禁止
if (preg_match('/[\r\n]/', $subject)) {
    exit('不正な入力です');
}

// 長さ制限（例: 100文字まで）
if (mb_strlen($subject) > 100) {
    exit('件名が長すぎます');
}

// 可能なら固定件名にする方が安全
// $subject = '【お問い合わせ】受付完了';

    mb_strlen は日本語などのマルチバイト文字も1文字として数える、文字数取得の関数です。

    方針安全性説明
    件名を固定する最も安全ユーザー入力を件名に使わない
    許可リスト安全「質問」「要望」など選択肢のみ
    改行・長さチェック最低限自由入力を許す場合の防御

    4.Hidden パラメータによる宛先保持

    お問い合わせフォームなどで、宛先メールアドレスを <input type="hidden">（画面には表示されないが、フォーム送信時に一緒に送られる入力欄）に入れて送信する実装があります。これは 改ざんしやすい ため危険です。

    4.1 脆弱な実装

    危険な例：宛先が HTML に埋まっている 
    <!-- ❌ 宛先が HTML に埋まっている -->
<form action="/contact" method="POST">
  <input type="hidden" name="to" value="support@example.com">
  <input type="text" name="name">
  <textarea name="body"></textarea>
  <button type="submit">送信</button>
</form>

    攻撃者はブラウザの 開発者ツール（ページの HTML を見たり書き換えたりできる、ブラウザ標準の機能）で to の値を書き換え、任意の宛先 へメールを送らせられます。

    1. ページの HTML を開く
    2. hidden の value を attacker@evil.com に変更
    3. フォームを送信
    4. アプリが改ざんされた宛先へメール送信

    4.2 対策

    対策説明
    宛先はサーバー側で固定HTML やリクエストに宛先を載せない
    どうしても切り替えるならサーバー側の対応表dept=sales のような ID だけ受け取り、サーバーで sales@example.com に変換
    セッションに保持確認画面がある場合、宛先は セッション（サーバー側に利用者ごとの情報を一時保存する仕組み）に置き、hidden に出さない
    安全な例：宛先はサーバー側だけで決める（PHP） 
    // ✅ 良い例: 宛先はサーバー側のみ
$to = 'support@example.com';

// ✅ 部署ごとに送る場合も、許可したキーだけ変換
$deptMap = [
    'sales' => 'sales@example.com',
    'support' => 'support@example.com',
];
$dept = $_POST['dept'] ?? 'support';
$to = $deptMap[$dept] ?? $deptMap['support'];

    対応表にないキーが送られてきても、?? $deptMap['support'] によって既定の宛先になるため、攻撃者が任意のアドレスを指定する余地がありません。

    同じ考え方：クライアント側の値を信じない

    これは 74_セッション管理 の「クッキー出力にまつわる脆弱性（徳丸本第11章）」で扱う 「クライアント側に重要な情報を置かない」 と同じ考え方です。hidden も Cookie も、利用者の手元にある値は自由に書き換えられます。

    5.参考：メールサーバーによる第三者中継

    第三者中継（オープンリレー） とは、メールサーバーが 認証なしで誰のメールでも中継 してしまう設定です。Webアプリ本体の脆弱性というより、メールサーバーの設定不備 です。

    5.1 何が起きるか

    影響説明
    スパムの踏み台自社サーバーから大量の迷惑メールが送られる
    IP・ドメインの評判低下ブラックリストに入り、正規メールも届かなくなる
    帯域・リソースの浪費サーバー負荷が増える

    5.2 対策の要点

    • 外部からの無認証リレーを禁止する
    • 自アプリからの送信は認証付き（SMTP AUTH）や API 経由にする（SMTP はメールを送るための通信の決まり、SMTP AUTH はその送信時にユーザー名とパスワードで認証する仕組みです）
    • 送信元 IP・レート制限（一定時間あたりの送信数の上限）を設ける
    • 可能なら SendGrid / SES 等の外部メールサービスを使う

    Webアプリ側では「ヘッダインジェクション対策」と「宛先のサーバー側固定」を行い、メールサーバー側では「第三者中継を閉じる」ことがセットです。

    なお、他人が自社ドメインを名乗って送る「なりすましメール」を受信側で見抜く仕組み（SPF・DKIM・DMARC）は、ネットワークと端末の防御「メールのなりすまし対策 — SPF・DKIM・DMARC」 で解説しています。

    6.まとめ

    対策内容
    ヘッダに外部入力を載せないTo / From / Subject は固定またはサーバー側で決定
    改行チェック\r \n を含む入力は拒否
    専用ライブラリ・API を使うヘッダ文字列を自分で連結しない
    メールアドレス・件名の検証形式・長さ・改行をチェック
    宛先を Hidden に置かないクライアント側の値を信じない
    第三者中継を禁止メールサーバー設定・外部サービス利用

    6.1 実装のチェックリスト

    • □ 宛先（To）はサーバー側で固定している
    • □ From は自社の固定アドレスを使っている
    • □ 件名は固定、または改行・長さを検証している
    • □ ユーザー入力は本文にのみ反映している
    • □ mail() のヘッダ連結ではなく、ライブラリ / API を使っている
    • □ Hidden パラメータに宛先を入れていない
    • □ メールサーバーがオープンリレーになっていない

    7.理解度チェック

    Q1. お問い合わせフォームのメールアドレス欄に user@example.com%0ABcc: victim@example.com が送られてきました。アプリが "From: " . $email でヘッダを作っていると、何が起きますか？

    %0A（改行）の後ろが新しいヘッダ行として扱われ、Bcc: victim@example.com が追加されます。その結果、攻撃者が指定した第三者にもメールが送られ、スパムやなりすましの踏み台にされます。

    Q2. メールヘッダインジェクションの対策として、最も確実なのは「改行チェック」と「外部入力をヘッダに使わない」のどちらですか？

    外部入力をヘッダに使わない ことです。To・From・Subject をアプリ側で固定し、ユーザー入力は本文にだけ載せます。改行チェックは、どうしてもヘッダに入力値を使う場合の 最低限の防御 です。

    Q3. 利用者の返信先アドレスを受け取りたいとき、From に入れるのがよくないのはなぜですか？ 代わりにどうしますか？

    From に外部入力を入れると、差出人の偽装やヘッダインジェクションの入口になるためです。From は自社の固定アドレス（例: noreply@example.com）にし、返信先は検証済みのアドレスを Reply-To に入れるか、本文にだけ書きます。

    Q4. 宛先を <input type="hidden"> に入れておく実装は、画面に表示されないのになぜ危険なのですか？

    hidden は画面に見えないだけで、HTML としては利用者の手元にあり、開発者ツールなどで自由に書き換えられるからです。宛先はサーバー側で固定するか、dept=sales のようなキーだけ受け取ってサーバー側の対応表で変換します。

    Q5. 第三者中継（オープンリレー）は、Webアプリの脆弱性ですか？ どんな対策が必要ですか？

    Webアプリ本体ではなく、メールサーバーの設定不備 です。外部からの無認証リレーを禁止し、自アプリからの送信は SMTP AUTH や API 経由にします。送信元 IP やレート制限、外部メールサービスの利用も有効です。
