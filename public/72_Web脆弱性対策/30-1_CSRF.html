    30 リクエスト偽造・リダイレクト

    CSRF（クロスサイトリクエストフォージェリ）

    CSRF は、ログイン中の利用者に、本人が意図していないリクエスト（送金・設定変更など）を勝手に送らせる攻撃です。このページでは徳丸本（『体系的に学ぶ 安全なWebアプリケーションの作り方』）第8章をもとに、CSRF の仕組み、XSS との違い、確認画面・hidden・セッション・ファイルアップロードといった場面ごとの落とし穴、そして CSRF トークン・パスワード再入力・Referer チェックによる対策を解説します。

    もとにしたノート：30_リクエスト偽造・リダイレクト/01_CSRF（徳丸本8章）

    ひとことで言うと

    ブラウザは、どのサイトから送られたリクエストでも、宛先サイトの Cookie を 自動で付けて しまいます。そのためサーバーは「ログイン済みの本人から来た」とは分かっても、「本人が自分のサイトの画面で意図して送ったか」 は分かりません。CSRF 対策とは、この「意図」を 攻撃者が知り得ない秘密（CSRF トークン） などで確かめることです。

    第5章 では XSS を、第1章ではセッション管理（74_セッション管理 で扱います）を学びました。第8章では CSRF（クロスサイトリクエストフォージェリ） の仕組みと対策を解説します。

    1.クロスサイトリクエストフォージェリ（CSRF）とは

    CSRF（Cross-Site Request Forgery / クロスサイトリクエストフォージェリ） は、ログイン済みのユーザーに 意図しないリクエストを送らせる 攻撃です。「フォージェリ（forgery）」は「偽造」という意味で、名前のとおり「別のサイトから（クロスサイト）、リクエストを偽造する」攻撃です。読み方は「シーサーフ」と呼ばれることもあります。

    項目内容
    別名クロスサイト・リクエストフォージェリ、One-Click Attack
    前提被害者が対象サイトに ログイン済み（Cookie が有効）
    攻撃方法別サイトから対象サイトへリクエストを送らせる

    Cookie（クッキー） は、サイトがブラウザに保存させる小さなデータです。ログインすると、利用者を見分けるための セッション ID（ログイン状態を表す番号）が Cookie に入り、以後そのサイトへのリクエストには毎回この Cookie が自動で付きます。これが「ログイン状態が続く」仕組みです。

    CSRF は、攻撃者が罠を仕掛け、被害者のブラウザに攻撃を実行させる 受動的攻撃 の一種です（受動的攻撃と同一オリジンポリシー を参照）。

    1.1 日常生活での例え

    正常な操作

    銀行サイトで自分の意志で「送金」ボタンを押す

    CSRF

    別のサイトを見ているだけなのに、裏で銀行サイトへ「送金」リクエストが送られる

    1.2 攻撃の流れ

    1. 被害者が bank.com にログイン（Cookie がブラウザに保存）
    2. 被害者が evil.com を閲覧
    3. evil.com のページが bank.com へリクエストを送る
    4. ブラウザが bank.com の Cookie を自動添付
    5. bank.com は「ログイン済みユーザーの正規リクエスト」と判断
    6. 意図しない操作（送金・設定変更等）が実行される

    1.3 攻撃コードの例

    evil.com のページに、次のような HTML を仕込みます。<img> タグはページを開いただけで src の URL へ GET リクエストを送ります。<form> は <script> の submit() で、利用者がボタンを押さなくても自動で送信されます。type="hidden" は画面に表示されない入力欄です。

    攻撃者が罠サイトに仕込むコード 
    <!-- evil.com のページに仕込む -->

<!-- GET リクエスト（画像タグ） -->
<img src="https://bank.com/transfer?to=attacker&amount=100000" width="0" height="0">

<!-- POST リクエスト（自動送信フォーム） -->
<form action="https://bank.com/transfer" method="POST" id="attack">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="100000">
</form>
<script>document.getElementById('attack').submit();</script>

    画像タグは width="0" height="0" で見えなくしてあり、被害者は何も気づきません。

    1.4 なぜ起きるか

    要因説明
    Cookie の自動送信同一サイトへのリクエストに Cookie が付く（リクエストを作ったのが別サイトのページでも、宛先が bank.com なら bank.com の Cookie が付く）
    リクエスト元の未検証サーバーが「誰が意図して送ったか」を確認しない
    副作用のある GETGET で状態変更処理を行っている（設計上の問題）

    副作用 とは、リクエストによってデータが書き換わること（登録・更新・削除・送金など）です。

    同一オリジンポリシーでは防げない理由

    ブラウザの 同一オリジンポリシー（別のオリジンのデータを勝手に読ませない仕組み）が止めるのは、別サイトの レスポンスを読むこと です。リクエストを送ること自体 は止めません。CSRF の攻撃者はレスポンスを読む必要がなく、送れれば目的を達成できるため、同一オリジンポリシーでは防げません。詳しくは 同一オリジンポリシーが守るもの を参照してください。同じ理由で、CORS の設定も CSRF 対策にはなりません。

    2.CSRF 攻撃と XSS 攻撃の比較

    CSRF と XSS は混同されやすいですが、攻撃の仕組みと対策 が異なります。

    2.1 比較表

    CSRFXSS
    目的意図しない リクエスト を送らせる悪意ある スクリプト を実行させる
    前提ログイン済み（Cookie 有効）入力が HTML に反映される脆弱性
    攻撃者の能力別サイトからリクエストを 送るページ内で JavaScript を実行
    Cookie自動送信を 悪用document.cookie で 窃取
    主な対策CSRF トークン、SameSite CookieHTML エスケープ、CSP

    SameSite Cookie は、別サイトから来たリクエストに Cookie を付けないようにする Cookie の属性です（9.3 で補足します）。CSP は、ページで実行してよいスクリプトをブラウザに指示する仕組みです（CSP を参照）。

    2.2 図解

    CSRF:
  evil.com ──リクエスト──→ bank.com（Cookie 付き）
  「ユーザーが意図した操作か？」をサーバーが確認していない

XSS:
  evil.com ではなく bank.com 上で
  注入された <script> が実行される
  → Cookie 窃取、ページ改ざん等

    CSRF の攻撃コードは evil.com の上 で動き、bank.com のページの中身には手出しできません。XSS の攻撃コードは bank.com のページの中 で動くため、bank.com の画面やデータを自由に読み書きできます。

    2.3 組み合わせ攻撃

    パターン説明
    XSS 単独スクリプトで直接 API を呼び出し、操作可能
    CSRF 単独スクリプト不要。フォームや img タグでリクエスト
    XSS + CSRFXSS で CSRF トークンを読み取り、CSRF 対策を突破

    重要：XSS があると CSRF 対策は無効になる

    CSRF トークンは XSS があると無効化 されます（トークンが JavaScript から読めるため）。XSS 対策も並行して必要です。

    3.確認画面がある場合の CSRF 攻撃

    「確認画面があるから安全」とは 限りません。確認画面は CSRF を防ぐ仕組みではありません。

    3.1 典型的なフロー

    入力画面 → 確認画面 → 完了画面
  POST       POST       （DB更新）

    3.2 なぜ確認画面だけでは防げないか

    攻撃者は 確認画面を経由せず、直接 POST リクエストを送れます。サーバーから見れば、届くのは「確定ボタンを押したときと同じ形のリクエスト」だけなので、確認画面を通ったかどうかは区別できません。

    攻撃者が evil.com に仕込むフォーム 
    <!-- 攻撃者が evil.com に仕込むフォーム -->
<form action="https://shop.com/order/confirm" method="POST">
  <input type="hidden" name="product_id" value="123">
  <input type="hidden" name="quantity" value="1">
  <input type="hidden" name="confirmed" value="1">
  <input type="submit" value="Click me">
</form>
    確認画面の役割:
  ✅ ユーザーが内容を見直す（UX）
  ❌ リクエストの正当性を保証する（セキュリティ）ではない

    UX（ユーザーエクスペリエンス）は、使いやすさや使い心地のことです。

    3.3 確認画面を CSRF 対策に使う場合

    確認画面の POST に CSRF トークン（10章で詳しく説明する、攻撃者が知り得ない秘密の値）を含め、サーバー側で検証する必要があります。

    安全な例：確認画面のフォームにトークンを入れ、サーバーで検証（PHP） 
    // 確認画面のフォーム
<input type="hidden" name="csrf_token" value="<?= $token ?>">

// サーバー側で検証
if (!hash_equals($_SESSION['csrf_token'], $_POST['csrf_token'])) {
    die('不正なリクエストです');
}

    hash_equals は2つの文字列が等しいかを安全に比べる PHP の関数です（理由は 10.4 で説明します）。

    4.Hidden パラメータでパラメータ受け渡ししている場合

    入力画面 → 確認画面 → 完了画面のように画面が続く 多段階フォーム で、hidden パラメータ（<input type="hidden"> に入れて次の画面へ送る値）を使って値を引き継ぐ場合、CSRF のリスクがあります。

    4.1 脆弱なパターン

    危険な例：価格まで hidden で引き継いでいる 
    <!-- 入力画面 → 確認画面へ -->
<form method="POST" action="/order/confirm">
  <input type="hidden" name="product_id" value="123">
  <input type="hidden" name="price" value="1000">
  <input type="text" name="quantity" value="2">
  <button type="submit">確認</button>
</form>

    4.2 攻撃

    攻撃者は 同じパラメータを含むフォーム を evil.com に作成し、自動送信できます。

    攻撃者が evil.com に仕込むフォーム 
    <form action="https://shop.com/order/confirm" method="POST">
  <input type="hidden" name="product_id" value="999">
  <input type="hidden" name="price" value="1">
  <input type="hidden" name="quantity" value="100">
</form>
<script>document.forms[0].submit();</script>

    4.3 なぜ危険か

    問題説明
    Hidden は改ざん可能ブラウザの開発者ツール（ページの HTML を見たり書き換えたりできる機能）で値を変更できる
    CSRF で再現可能攻撃者が任意の hidden 値で POST できる
    価格等の信頼hidden の price を信頼してはいけない

    4.4 対策

    対策説明
    CSRF トークンリクエストの正当性を検証
    サーバー側で値を保持価格等は hidden ではなく セッション（サーバー側に利用者ごとの情報を一時保存する仕組み）や DB から取得
    重要値は hidden に載せないproduct_id のみ受け取り、price はサーバーで再取得

    「クライアント側の値を信じない」という考え方は、メールヘッダインジェクション「Hidden パラメータによる宛先保持」 と同じです。

    5.セッション変数によりパラメータ受け渡ししている場合

    セッション変数（PHP の $_SESSION のように、サーバー側のセッションに保存する値）でパラメータを引き継ぐ方式は、hidden より安全ですが、CSRF 自体は防げません。

    5.1 比較的安全なパターン

    比較的安全な例：値はセッションに置き、価格は DB から取る（PHP） 
    // 入力画面：セッションに保存
$_SESSION['order'] = [
    'product_id' => (int)$_POST['product_id'],
    'quantity'   => (int)$_POST['quantity'],
];
header('Location: /order/confirm');

// 確認画面：セッションから読み取り
$order = $_SESSION['order'];
$product = getProduct($order['product_id']);  // 価格は DB から取得

    (int) は値を整数に変換する書き方、header('Location: ...') は指定した URL へブラウザを移動（リダイレクト）させる命令です。

    5.2 メリット

    メリット説明
    改ざん耐性クライアントから price を送らない
    Hidden より安全攻撃者が price を直接指定しにくい

    5.3 残る CSRF リスク

    攻撃者が「確定」処理の POST だけを送れます。

    攻撃者が仕込むフォーム：パラメータなしで「確定」だけ送る 
    <form action="https://shop.com/order/complete" method="POST">
  <!-- パラメータ不要。セッションに既存データがあれば処理される -->
</form>
<script>document.forms[0].submit();</script>

    被害者のセッションに 正当な注文データ がある場合（例：確認画面まで進んで手を止めている）、攻撃者が「確定」だけ CSRF できる可能性があります。

    5.4 対策

    • 確定処理にも CSRF トークン を必須にする
    • セッション引き継ぎは 値の改ざん防止、CSRF トークンは 意図した操作の確認

    つまり、両者は守っているものが違うので、どちらか一方で済ませることはできません。

    6.ファイルアップロードフォームでの CSRF 攻撃

    ファイルアップロード も CSRF の対象になります。enctype="multipart/form-data"（ファイルを送るときに使うフォームの送信形式）でも同様です。

    6.1 攻撃の例

    攻撃者が evil.com に仕込むアップロードフォーム 
    <!-- evil.com：自動送信するアップロードフォーム -->
<form action="https://docs.example.com/upload" method="POST"
      enctype="multipart/form-data" id="upload">
  <input type="file" name="file" id="file">
</form>
<script>
  // ファイル選択は同一オリジン制限があり、完全自動化は難しい場合も
  // ただし、攻撃者が用意したファイルをユーザー操作で送らせる等の手法あり
  document.getElementById('upload').submit();
</script>

    補足：ファイルアップロードの CSRF も完全に自動化できます

    コード中のコメントにある「ファイル選択の制限」は、正確には同一オリジンポリシーではなく、スクリプトから <input type="file"> に利用者のファイルを勝手にセットできない というブラウザの制限です。ただし攻撃者は利用者のファイルを使う必要がなく、自分で用意した中身 を JavaScript の FormData / Blob で作り、fetch(url, { method: 'POST', body: formData, credentials: 'include' }) のように送れます。レスポンスは読めませんが、送信は成功します（徳丸本でもこの方法による攻撃が紹介されています）。そのため「自動化は難しい」と考えて対策を省略してはいけません。

    6.2 リスク

    リスク説明
    不正ファイルのアップロードログイン済みユーザー権限でファイルを配置
    Web シェルの配置実行可能なスクリプトをアップロード（Web シェル：ブラウザからサーバーを遠隔操作できるようにする不正プログラム）
    設定変更と組み合わせアップロード先や権限の変更と連鎖

    6.3 対策

    対策説明
    CSRF トークンアップロードフォームにも必須
    Content-Type 検証許可するファイル形式を限定
    保存先の制御Web ルート外（URL で直接アクセスできない場所）、実行権限なし
    SameSite Cookieクロスサイトからの Cookie 送信を制限

    アップロード機能そのものの脆弱性（ファイルの種類の偽装など）は、ファイルアップロード のページで扱います。

    7.CSRF 対策の基本方針

    CSRF 対策の基本方針は次の2点です。

    1. CSRF 対策が必要なページを区別する
    2. 正規利用者の意図したリクエストであることを確認する

    1つ目は 8章、2つ目は 9章〜12章で説明します。

    8.CSRF 対策の必要なページを区別する

    すべてのページに CSRF 対策が必要なわけではありません。状態を変更する処理 を対象にします。

    8.1 対策が必要な操作

    操作例CSRF 対策
    作成投稿、注文、ユーザー登録✅ 必要
    更新プロフィール変更、設定変更✅ 必要
    削除記事削除、アカウント削除✅ 必要
    送金・決済振込、購入確定✅ 必要 + 再認証
    参照のみ一覧表示、詳細表示△ 通常不要
    検索（GET）キーワード検索△ GET で副作用がなければ低リスク

    再認証 とは、ログイン済みでも重要な操作の直前にもう一度パスワードなどで本人確認することです（11章）。参照だけのページは、攻撃者がリクエストを送らせても結果（レスポンス）を読めないため、通常は被害になりません。

    8.2 判断基準

    CSRF 対策が必要:
  → リクエストが「副作用」を持つ（データが変わる）
  → 認証済みユーザーの権限で実行される

CSRF 対策が不要（または優先度低）:
  → 参照のみ（GET でデータ変更なし）
  → 公開 API（認証不要）

    8.3 GET で状態変更しない

    危険な例：GET で削除 
    // ❌ 危険：GET で削除
<a href="/delete?id=123">削除</a>
// → CSRF 攻撃が img タグ1つで可能
    安全な例：POST + CSRF トークン 
    // ✅ 安全：POST + CSRF トークン
<form method="POST" action="/delete">
  <input type="hidden" name="id" value="123">
  <input type="hidden" name="csrf_token" value="<?= $token ?>">
  <button type="submit">削除</button>
</form>

    POST にしただけでは 1.3 の自動送信フォームで攻撃できるため、POST と CSRF トークンはセット で使います。

    9.正規利用者の意図したリクエストであることを確認する

    CSRF 対策の本質は、「このリクエストは、ユーザーが自サイト上で意図して送ったものか」 をサーバー側で確認することです。

    9.1 確認方法

    方法信頼性説明
    CSRF トークン高秘密トークンの一致を検証
    SameSite Cookie中〜高クロスサイト Cookie 送信を制限
    Referer チェック低〜中リクエスト元 URL を確認
    パスワード再入力高重要操作で本人確認
    カスタムヘッダ高X-Requested-With 等（API 向け）

    カスタムヘッダ 方式は、「独自のリクエストヘッダが付いたリクエストだけ受け付ける」方法です。フォームや img タグでは独自ヘッダを付けられず、JavaScript で別オリジンから独自ヘッダを付けようとすると プリフライトリクエスト（本番の前にサーバーへ許可を問い合わせる事前確認）が発生し、サーバーが許可しない限り送られません。そのため、CORS で別オリジンを広く許可していないことが前提です。

    9.2 多層防御

    1つの対策に頼らず、複数を重ねます（考え方は 深層防御 を参照）。

    SameSite Cookie（第1の防御線）
    +
CSRF トークン（第2の防御線）
    +
重要操作ではパスワード再入力（第3の防御線）

    9.3 補足：本の出版後に広まった防御

    ブラウザ側の仕組みも CSRF を防ぐ方向に進んでいます

    • SameSite=Lax の既定化：Chrome などでは、SameSite 属性を書かない Cookie を Lax（別サイトからの POST や img などでは Cookie を送らず、リンクをたどる通常の画面遷移では送る）として扱います。ただしすべてのブラウザの既定ではなく、Lax でも GET での画面遷移には Cookie が付く ため、「GET で状態変更しない」は引き続き必須です。SameSite の細かい使い分けは 74_セッション管理 で扱います（概要は Cookie はどう付いていくのか）。
    • Origin ヘッダのチェック：POST などのリクエストには、送信元のオリジン（例：https://evil.com）を表す Origin ヘッダが付きます。これが自サイトでなければ拒否します。Referer より送られる場面が多く、パス（URL の後半）を含まないためプライバシー設定で消されにくいのが利点です。
    • Fetch Metadata（Sec-Fetch-Site）：最近のブラウザは、リクエストが同じサイトから来たか（same-origin / same-site）、別サイトから来たか（cross-site）をこのヘッダで知らせます。JavaScript から偽造できないため、cross-site の状態変更リクエストを拒否する判定に使えます。

    いずれも CSRF トークンを置き換えるものではなく、重ねて使う防御 と考えてください。

    10.秘密情報（トークン）の埋め込み

    CSRF トークン は、CSRF 対策の 最も重要で標準的な手法 です。トークン とは、サーバーが発行する推測できないランダムな文字列のことです。

    10.1 仕組み

    1. サーバーがランダムなトークンを生成
    2. セッションに保存
    3. フォームに hidden フィールドとして埋め込む
    4. 送信時にトークンも POST される
    5. サーバーがセッションのトークンと一致するか検証
    6. 一致しなければ拒否

    10.2 実装例（PHP）

    トークン生成 
    // トークン生成
if (empty($_SESSION['csrf_token'])) {
    $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
}
$token = $_SESSION['csrf_token'];

    random_bytes(32) は暗号論的に安全な（予測できない）乱数を 32 バイト作る関数、bin2hex はそれを 16 進数の文字列（64文字）に変換する関数です。

    フォームに埋め込み 
    <!-- フォームに埋め込み -->
<form method="POST" action="/transfer">
  <input type="hidden" name="csrf_token" value="<?= htmlspecialchars($token) ?>">
  <!-- その他のフィールド -->
  <button type="submit">送金</button>
</form>

    htmlspecialchars は HTML エスケープを行う関数です（htmlspecialchars 関数 を参照）。

    検証 
    // 検証
if (!isset($_POST['csrf_token']) ||
    !hash_equals($_SESSION['csrf_token'], $_POST['csrf_token'])) {
    http_response_code(403);
    die('不正なリクエストです');
}

    http_response_code(403) は「アクセス禁止（403 Forbidden）」のステータスコードを返す命令です。

    10.3 なぜ有効か

    evil.com のページから bank.com へ POST しても:
  → evil.com は bank.com の CSRF トークンを知らない
  → 正しいトークンを送れない
  → サーバーが拒否 ✅

    evil.com が bank.com のフォームページを読み込んでトークンを盗もうとしても、同一オリジンポリシー によってレスポンスは読めません。「送れるが読めない」という性質を、逆に守りに利用しているわけです。

    10.4 トークンの要件

    要件説明
    推測困難random_bytes() 等で生成
    セッションごとユーザー・セッション単位で管理
    重要操作ごとワンタイムトークン（1回使ったら無効になるトークン）も可能
    比較は定数時間hash_equals() でタイミング攻撃を防ぐ

    タイミング攻撃 とは、比較にかかる時間のわずかな差（先頭から何文字目まで一致していたかで処理時間が変わる）を測って、正解を1文字ずつ推測する攻撃です。定数時間の比較 は、一致・不一致にかかわらず同じ時間で比べるため、この手がかりを与えません。

    10.5 Ajax / API での利用

    Ajax は、画面を切り替えずに JavaScript からサーバーと通信する方法です。フォームを使わない場合は、トークンを HTML の <meta> タグなどに置いておき、リクエストヘッダに入れて送ります（meta タグへの埋め込み方は XSS発展編 にも例があります）。

    トークンをヘッダに付けて送る（JavaScript） 
    // メタタグや Cookie からトークンを取得
const token = document.querySelector('meta[name="csrf-token"]').content;

fetch('/api/transfer', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-CSRF-Token': token
  },
  body: JSON.stringify({ to: 'xxx', amount: 1000 })
});

    fetch は JavaScript でリクエストを送る標準の関数です。サーバー側では、X-CSRF-Token ヘッダの値をセッションのトークンと比較します。

    11.パスワード再入力

    送金・パスワード変更・アカウント削除 など、特に重要な操作では パスワードの再入力 を求めます。

    11.1 仕組み

    1. ユーザーが「アカウント削除」をクリック
    2. 確認画面でパスワード入力を要求
    3. サーバーがパスワードを検証
    4. 正しければ処理を実行

    11.2 なぜ有効か

    理由説明
    攻撃者が知らない情報パスワードは evil.com から取得できない
    ユーザー意図の確認能動的な入力が必要
    CSRF トークンと併用より強固な防御

    パスワード再入力は、CSRF だけでなく、席を外した隙に他人に操作される場合や、セッションを乗っ取られた場合の被害も抑えます。

    11.3 実装例

    安全な例：トークン＋パスワード再入力のフォーム 
    <form method="POST" action="/account/delete">
  <input type="hidden" name="csrf_token" value="<?= $token ?>">
  <p>アカウントを削除するにはパスワードを入力してください。</p>
  <input type="password" name="password" required>
  <button type="submit">削除する</button>
</form>
    サーバー側でパスワードを検証（PHP） 
    // パスワード検証
if (!password_verify($_POST['password'], $user['password_hash'])) {
    die('パスワードが正しくありません');
}
// 削除処理...

    password_verify は、入力されたパスワードと、保存してある パスワードハッシュ（パスワードを元に戻せない形に変換した値）が対応しているかを確かめる PHP の関数です。パスワードの保存方法は パスワードの保存：平文・MD5・bcrypt を参照してください。

    11.4 適用場面

    操作再入力
    送金・決済✅ 推奨
    パスワード変更✅ 推奨
    アカウント削除✅ 推奨
    メールアドレス変更✅ 推奨
    プロフィール更新△ 任意
    記事投稿△ CSRF トークンで十分なことが多い

    毎回パスワードを求めると利用者の負担が大きいため、被害が大きい操作に絞って使います。

    12.Referer のチェック

    Referer（Referrer）ヘッダ を検証し、リクエストが 自サイトから 送られたか確認する方法です。Referer は、ブラウザが「どのページからこのリクエストが来たか」を伝えるリクエストヘッダです（HTTP の仕様上、綴りが「Referrer」ではなく「Referer」になっています）。

    12.1 仕組み

    POST /transfer HTTP/1.1
Host: bank.com
Referer: https://bank.com/transfer/form
         ↑ リクエスト元の URL
    Referer チェックの例（PHP） 
    // Referer チェック
$referer = $_SERVER['HTTP_REFERER'] ?? '';
$allowed = 'https://bank.com';
if (strpos($referer, $allowed) !== 0) {
    die('不正なリクエスト元です');
}

    strpos($referer, $allowed) !== 0 は「Referer が https://bank.com で始まっていなければ」という意味です。

    注意：この前方一致チェックはすり抜けられます

    上のコードは「https://bank.com で始まるか」だけを見ているため、攻撃者が https://bank.com.evil.com/ のようなドメインを用意すると、Referer が https://bank.com.evil.com/trap.html となってチェックを通ってしまいます。比較する値は 末尾のスラッシュまで含めて 'https://bank.com/' にするか、URL を分解してオリジン（スキーム＋ホスト＋ポート）が完全に一致するかを確かめてください。

    $allowed = 'https://bank.com/';   // 末尾の / まで含めて前方一致
if (strpos($referer, $allowed) !== 0) {
    http_response_code(403);
    die('不正なリクエスト元です');
}

    12.2 メリット・デメリット

    メリットデメリット
    実装が比較的簡単Referer が 送信されない 場合がある
    補助的防御として有効プライバシー設定で省略される
    偽造の可能性（ブラウザ依存）
    単独では不十分

    なお、現在の一般的なブラウザでは、罠ページの JavaScript から Referer を自由に書き換えることはできません。「偽造の可能性」は、古いブラウザやプラグインの不具合に依存する話です。より実際的な問題は「送られない場合がある」ことで、Referer がないリクエストを拒否すると正規の利用者まで弾いてしまい、許可すると攻撃者に抜け道を与えてしまいます。

    12.3 Referer が送られないケース

    • HTTPS → HTTP への遷移
    • Referrer-Policy: no-referrer の設定（Referrer-Policy は Referer をどこまで送るかを指定するヘッダです。セキュリティヘッダ を参照）
    • ブックマークからの直接アクセス
    • 一部ブラウザ拡張

    12.4 位置づけ

    Referer チェック = 保険的・補助的対策
CSRF トークン    = 根本対策（必須）

    推奨： CSRF トークンを主とし、Referer チェックは 追加防御 として利用します。

    13.まとめ

    トピック要点
    CSRFログイン済みユーザーに意図しないリクエストを送らせる
    XSS との違いCSRF=リクエスト送信、XSS=スクリプト実行
    確認画面UX 用。CSRF 対策にはならない
    Hidden パラメータ改ざん・CSRF で再現可能。信頼してはいけない
    セッション引き継ぎ改ざん防止に有効だが CSRF は別対策が必要
    ファイルアップロードCSRF トークン必須
    対策対象副作用のある操作（POST 等）
    CSRF トークン最も重要な対策
    パスワード再入力重要操作の追加防御
    Referer チェック補助的対策

    13.1 CSRF 対策チェックリスト

    • □ 状態変更処理は POST を使用（GET で変更しない）
    • □ フォームに CSRF トークンを埋め込み、サーバーで検証
    • □ Cookie に SameSite 属性を設定（Strict または Lax）
    • □ 価格・権限等は hidden ではなくサーバー側で管理
    • □ 送金・削除等の重要操作はパスワード再入力
    • □ Referer チェックは補助として（任意）
    • □ XSS 対策も並行（CSRF トークンは XSS で無効化される）

    このページの要点

    Cookie は「誰か」を示しますが、「本人が意図したか」は示しません。副作用のある処理には、攻撃者が知り得ない CSRF トークンを必ず添えさせ、サーバーで検証する のが CSRF 対策の中心です。

    ノートでは「次の章では、セッション管理の脆弱性やその他の Web アプリケーションの問題について学んでいきます」と続きます。このサイトでは、セッション管理は 74_セッション管理 で扱います。30 リクエスト偽造・リダイレクトの続きとしては、次のページの リダイレクトとHTTPヘッダインジェクション へ進んでください。

    14.理解度チェック

    Q1. 利用者は evil.com を見ただけなのに、なぜ bank.com は「本人のリクエスト」と判断してしまうのですか？

    ブラウザは、リクエストを作ったのがどのサイトのページであっても、宛先が bank.com なら bank.com の Cookie（セッション ID）を自動で付けて送るからです。サーバーは Cookie が正しいことしか確認していないため、本人が意図して送ったかどうかを区別できません。

    Q2. 同一オリジンポリシーがあるのに、CSRF が防げないのはなぜですか？

    同一オリジンポリシーが止めるのは別オリジンの レスポンスを読むこと で、リクエストを送ること は止めないからです。CSRF は送れさえすれば成立するため、サーバー側で CSRF トークンなどの対策が必要です。

    Q3. 「入力 → 確認 → 完了」の確認画面があれば CSRF は防げますか？

    防げません。攻撃者は確認画面を経由せず、確定処理への POST を直接送れます。確認画面は利用者が内容を見直すための UX であり、確定処理（とその手前の画面）の POST にも CSRF トークンを入れて検証する必要があります。

    Q4. 注文データを hidden ではなくセッション変数で引き継ぐようにしました。これで CSRF 対策は不要になりますか？

    不要になりません。セッション変数は price などの 値の改ざん を防ぎますが、被害者のセッションに正当な注文データがあれば、攻撃者はパラメータなしで「確定」の POST だけを送らせられます。確定処理にも CSRF トークンが必要です。

    Q5. CSRF トークンが有効なのはなぜですか？ また、XSS があると無効になるのはなぜですか？

    トークンはサーバーが正規の画面にだけ埋め込む推測困難な値で、evil.com は同一オリジンポリシーによりそのページを読めないため、正しいトークンを送れないからです。一方 XSS があると、攻撃スクリプトが bank.com のページ内で動くので、トークンを JavaScript で読み取って一緒に送れてしまいます。

    Q6. Referer チェックだけで CSRF 対策を済ませてはいけないのはなぜですか？

    HTTPS から HTTP への遷移、Referrer-Policy: no-referrer、ブックマーク、ブラウザ拡張などで Referer が送られない場合があり、確実に判定できないからです。また、strpos による前方一致で https://bank.com と比べると https://bank.com.evil.com を通してしまうなど、実装の落とし穴もあります。Referer チェックは CSRF トークンに重ねる補助的対策です。

    Q7. 削除処理を <a href="/delete?id=123"> のような GET で作ると、なぜ危険なのですか？

    罠ページに <img src="https://example.com/delete?id=123"> を1つ置くだけで、ページを開いた被害者のブラウザから削除リクエストが送られてしまうからです。状態を変更する処理は POST にし、CSRF トークンを検証します。SameSite=Lax でも GET の画面遷移には Cookie が付くため、この原則は変わりません。
