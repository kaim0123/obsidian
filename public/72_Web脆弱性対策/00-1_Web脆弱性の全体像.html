    Web脆弱性の全体像

    Webアプリの弱点（脆弱性：攻撃者に悪用されうるセキュリティ上の欠陥）は、どこで生まれ、いつ何を対策すればよいのでしょうか。このページは、徳丸本（『体系的に学ぶ 安全なWebアプリケーションの作り方』）の章立てとこのシリーズの各ページを結ぶ「地図」です。あわせて、すべての脆弱性対策の土台になる 入力→処理→出力 の考え方と入力値検証、代表的な攻撃のあらまし、「全アプリ必須」と「機能実装時」の判断軸、OSI参照モデルに沿った多層防御までを見渡します。

    もとにしたノート：00_全体像/01_安全なWebアプリケーションの作り方_目次・02_Webアプリの機能と脆弱性（徳丸本4章）・03_Webアプリの攻撃と防御（基礎講座第3回）

    ひとことで言うと

    多くの脆弱性は、外から来たデータが、入力・処理・出力のどこかで「意図しない使われ方」をする ことで起きます。対策は段階ごとにあり、入力値の検証だけでは守り切れません。そして対策は「どのアプリでも必ずやること」と「その機能を作るときに考えること」に分けると漏れにくくなります。

    1.このシリーズの地図

    学習の軸は次の3つです。

    ① 基礎

    Webの仕組みと攻撃の前提を押さえる（HTTP・オリジン・CORS など）。

    ② 脆弱性（セキュリティバグ）

    何が起き、どう防ぐか（XSS・SQLインジェクション・CSRF など）。

    ③ セキュリティ機能

    認証・認可・ログなど、守りの仕組みを正しく作る。

    加えて、実装時の判断軸として 「全アプリ必須」と「機能実装時」（14章）、インフラ視点として OSI参照モデルの多層防御（15章）を整理します。

    3.脆弱性はどこで生まれるか：入力→処理→出力

    ここからは徳丸本4章の内容です。Webアプリケーションは、大きく 入力 → 処理 → 出力 の3段階で動作します。利用者から何かを受け取り（入力）、それを使ってDB検索やメール送信などを行い（処理）、結果をHTMLなどで返します（出力）。インジェクション（注入：データのつもりの文字列に命令を紛れ込ませること）系の脆弱性は、この流れのどこかで 外部からのデータが意図しない形で使われる ときに起きます。

    3.1 各段階の例

    段階具体例
    入力フォーム送信、URLパラメータ、Cookie、HTTPヘッダ、ファイルアップロード
    処理入力値の検証、DB検索、計算、メール送信、シェルコマンド実行
    出力HTMLページ表示、JSONレスポンス、HTTPヘッダ、メール本文

    3.2 インジェクションとの関係

    段階起きやすい問題例
    入力不正なデータを受け入れる<script> タグ、SQL断片、改行コード
    処理入力をそのまま命令に混ぜるSQL文への連結、シェルコマンドへの連結
    出力エスケープせずに表示XSS（HTMLへのそのまま出力）

    3.3 防御の基本方針

    入力  → 検証・正規化（ここで不正データを弾く）
処理  → パラメータ化・安全なAPI（命令とデータを分離）
出力  → エスケープ（表示先に合わせて変換）

    重要

    入力値検証だけでは不十分です。処理と出力でも、それぞれ適切な対策が必要です。入力値の検証は「明らかにおかしい値を弾く」ための補助で、本命の対策は、処理や出力の場面で「データがデータのまま扱われる」ようにすることです。

    徳丸本4章では、インジェクション系の脆弱性を「どのインターフェース（データを渡す先の言語や仕組み）で、何が注入されるか」で整理しています。詳しくは各ページで解説します。

    脆弱性名インターフェース悪用手口解説ページ
    クロスサイトスクリプティングHTMLJavaScript の注入20-1・20-2
    HTTPヘッダインジェクションHTTPHTTPレスポンスヘッダの注入30-2
    SQLインジェクションSQLSQL文の注入20-3
    OSコマンドシェルスクリプトコマンドの注入20-4

    どれも「改行・引用符・記号など、注入先の文法で意味を持つ文字」が鍵になります。だから対策は「文法ごと切り離す」（プリペアドステートメント・専用API）か、「意味を消す」（エスケープ）のどちらかが基本です。

    能動的攻撃と受動的攻撃

    攻撃には、攻撃者がサーバーを直接狙う 能動的攻撃（例：SQLインジェクション）と、正規の利用者に罠を踏ませてその人のブラウザ経由で攻撃する 受動的攻撃（例：XSS・CSRF）があります。受動的攻撃では、サーバーから見ると「本物の利用者からのリクエスト」に見えるため、ブラウザ側の防御も重要になります。詳しくは 10-1 受動的攻撃と同一オリジンポリシー で解説します。

    4.入力値に対する3つのステップ

    ユーザーから送られてくるデータ（入力値）は、常に信頼できない 前提で扱います。処理に渡す前に、次の3つのステップを順に行います。

    1. 文字エンコーディングの妥当性検証（5.1）
    2. 文字エンコーディングの変換（5.2）
    3. 入力値の妥当性検証（6章・7章）→ 処理へ渡す

    5.文字エンコーディングの検証と変換

    文字エンコーディング とは、文字をコンピュータが扱えるバイト列に変換する方式のことです。Webでは UTF-8 が標準です。

    5.1 文字エンコーディングの妥当性検証

    なぜ検証が必要か

    問題説明
    文字化け想定外のエンコーディングで解釈すると文字が壊れる
    エンコーディング攻撃同じ文字列でも解釈を変えてフィルタをすり抜ける
    不正バイト列UTF-8として解釈できないデータが混入する

    検証の内容

    • 受け取ったデータが UTF-8として正しいか を確認する
    • 不正なバイト列が含まれていれば 拒否または除去 する
    • 複数のエンコーディング（Shift_JIS、EUC-JP 等）を受け付ける場合は、先に統一形式に変換 する
    Node.js の例：UTF-8 として妥当かチェック 
    function isValidUtf8(buffer) {
  try {
    const decoder = new TextDecoder('utf-8', { fatal: true });
    decoder.decode(buffer);
    return true;
  } catch {
    return false;  // 不正な UTF-8
  }
}

    5.2 文字エンコーディングの変換

    検証のあと、システム内部で使う 統一のエンコーディング（通常は UTF-8） に変換します。

    変換が必要な場面

    場面例
    レガシーシステム連携Shift_JIS のファイルを UTF-8 に変換
    ブラウザからの送信application/x-www-form-urlencoded のデコード
    ファイルアップロードCSV（CP932）を UTF-8 に読み替え

    注意点

    • 変換前後で文字が失われないか 確認する（「髙」など機種依存文字）
    • 変換後に 再度バリデーション を行う（変換で想定外の文字が生じる場合がある）
    • エンコーディングを 推測で決め打ちしない（可能なら明示的に指定）
    iconv-lite 等で Shift_JIS → UTF-8 に変換する例 
    const iconv = require('iconv-lite');
const utf8String = iconv.decode(shiftJisBuffer, 'Shift_JIS');

    6.入力値の妥当性検証

    エンコーディングを整えたうえで、ビジネスルール（業務上の決まり）に沿っているか を検証します。「この値はアプリとして受け入れてよいか？」を判断する段階です。

    6.1 ホワイトリスト vs ブラックリスト

    方式考え方評価
    ホワイトリスト（許可リスト）許可する形式・値だけを定義推奨
    ブラックリスト（拒否リスト）禁止する文字・パターンを定義漏れが生じやすい
     
    ホワイトリスト例：ユーザー名は「英小文字と数字、3〜16文字」のみ許可
ブラックリスト例：「<」「>」「'」を禁止  → 見落としやすい

    6.2 検証すべき項目

    項目例
    型数値フィールドに文字列が来ていないか
    形式メールアドレス、電話番号、日付の形式
    範囲年齢 0〜150、数量 1〜999
    長さコメント 500文字以内
    許可値都道府県は定義済みリストからのみ

    6.3 検証のタイミング

    • サーバー側で必ず検証 する（クライアント側だけでは不十分）
    • 可能な限り 処理の直前 に行う
    • 検証に失敗したら 明確にエラーを返す（曖昧な値で処理を続けない）

    7.入力値検証の具体例：制御文字・文字数・数値

    入力値検証（バリデーション） は、入力値の妥当性検証を具体的なチェック項目に落とし込んだものです。インジェクション攻撃を防ぐ第一の防御線になります。

    7.1 制御文字のチェック

    制御文字 は、画面に表示されない特殊な文字です（改行、タブ、NULL など）。HTTPヘッダインジェクションやログ改ざんの原因になります。

    制御文字コード危険性
    改行（LF）\n (0x0A)HTTPヘッダの注入
    復帰（CR）\r (0x0D)HTTPヘッダの注入
    NULL\0 (0x00)文字列の途中で切れる
    タブ\t (0x09)ログの改ざん
    制御文字を含むかチェック（改行・NULL 等） 
    function containsControlChars(str) {
  return /[\x00-\x08\x0B\x0C\x0E-\x1F\x7F]/.test(str);
}

// メールアドレス入力で改行が混入 → ヘッダインジェクションの恐れ
// 悪意ある入力: "user@example.com\r\nBcc: attacker@evil.com"

    注意：この正規表現は改行を見逃します

    上の文字クラス [\x00-\x08\x0B\x0C\x0E-\x1F\x7F] は、タブ（0x09）・LF（0x0A）・CR（0x0D）を わざと除外 した範囲です。複数行テキスト欄のように改行を許したい場面向けの書き方なので、コメントの「改行」や、すぐ下の \r\n を使ったヘッダインジェクションの例は検出できません。メールアドレスや件名など 1行であるべき値 では、/[\x00-\x1F\x7F]/ のように改行も含めて拒否してください（詳しくは 20-5・30-2）。

    対策： 制御文字を検出したら拒否するか、除去する。

    7.2 文字数のチェック

    入力値の 長さに上限・下限 を設けます。

    目的例
    バッファオーバーフロー防止ユーザー名 最大64文字
    DoS対策コメント 最大5000文字
    業務ルールパスワード 最小8文字

    ※ バッファオーバーフロー：確保したメモリ領域より長いデータを書き込み、隣の領域を壊す不具合。DoS：大量・巨大なリクエストでサービスを止める攻撃です。

    function validateLength(str, min, max) {
  if (str.length < min) return '短すぎます';
  if (str.length > max) return '長すぎます';
  return null;  // OK
}

validateLength(username, 3, 64);

    注意： 文字数は バイト数 と 文字数 が異なる場合がある（日本語1文字 = UTF-8で3バイト）。どちらで制限するかを決めておきます。

    7.3 数値の最小値・最大値のチェック

    数値入力には 型の確認 と 範囲の確認 の両方が必要です。

    function validateAge(value) {
  const num = Number(value);

  // 型チェック
  if (!Number.isInteger(num)) {
    return '整数で入力してください';
  }

  // 範囲チェック
  if (num < 0 || num > 150) {
    return '0〜150の範囲で入力してください';
  }

  return null;  // OK
}
    チェック防げる問題
    整数かどうか"abc" や "1.5" の混入
    最小値マイナスの数量（-1 個注文）
    最大値異常に大きな値によるオーバーフロー

    8.正規表現を使った入力値検証

    形式チェック（メールアドレス、電話番号など）には 正規表現（Regular Expression）：文字列のパターンを記号で表す書き方 がよく使われます。以下は正規表現の基本要素です。

    ※ 原文（徳丸本ノートの元資料）の「u装飾」「i装飾」は 修飾子、「量子指定」は 量詞指定 の意味です。

    8.1 修飾子（フラグ）

    正規表現の末尾に付けるオプションです。

    修飾子意味例
    i大文字・小文字を区別しない/abc/i → ABC にもマッチ
    uUnicode モード（サロゲートペア等を正しく扱う）/^[あ-ん]+$/u
    g全文からすべてのマッチを検索/\d/g
    m複数行モード（^ $ が行単位）/^test$/m
     
    // i 修飾子：大文字小文字を無視
/^[a-z]+$/i.test('Hello');  // true

// u 修飾子：絵文字なども1文字として扱う
/^.{1,10}$/u.test('こんにちは🎉');  // 文字数を正しくカウント

    8.2 文字と文字クラス

    記法意味例
    .任意の1文字a.c → abc, a1c
    \d数字 [0-9]\d\d\d → 123
    \w英数字とアンダースコア\w+ → user_name
    \s空白文字\s → スペース、タブ
    [abc]a, b, c のいずれか1文字[aeiou] → 母音
    [a-z]a〜z の範囲[0-9] → 数字
    [^abc]a, b, c 以外[^0-9] → 数字以外
    |ORcat|dog → cat または dog
     
    // 郵便番号（123-4567 形式）
/^\d{3}-\d{4}$/.test('123-4567');  // true

// 英小文字と数字のみ（ユーザー名）
/^[a-z0-9]{3,16}$/.test('yamada123');  // true

    8.3 量詞指定

    直前のパターンが 何回繰り返されるか を指定します。

    量詞意味例
    *0回以上\d* → 数字が0個以上
    +1回以上\d+ → 数字が1個以上
    ?0回または1回\d? → 数字が0個か1個
    {n}ちょうど n 回\d{3} → 数字3桁
    {n,}n 回以上\d{3,} → 数字3桁以上
    {n,m}n 回以上 m 回以下\d{3,5} → 数字3〜5桁
     
    // パスワード：8文字以上
/^.{8,}$/.test('password123');  // true

// 電話番号：10〜11桁の数字
/^\d{10,11}$/.test('09012345678');  // true

    8.4 アンカー（位置指定）

    記法意味
    ^文字列の先頭
    $文字列の末尾
     
    // ^ と $ で「文字列全体」がパターンに一致することを保証
/^[a-z]+$/.test('abc123');  // false（末尾まで英小文字だけではない）
/^[a-z]+$/.test('abc');     // true

    重要： 検証には ^ と $ を付けて 部分一致ではなく全体一致 にすることが多いです。

    8.5 実践例：メールアドレスの簡易検証

    // 簡易的な形式チェック（厳密なRFC準拠ではない）
const emailPattern = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;

emailPattern.test('yamada@example.com');  // true
emailPattern.test('invalid-email');       // false

    8.6 正規表現を使うときの注意

    注意点理由
    複雑すぎる正規表現は避ける保守が難しく、バグの温床になる
    ReDoS（正規表現DoS）に注意悪意ある入力で処理が極端に遅くなる
    正規表現だけに頼らない型・長さ・範囲チェックと組み合わせる
    ライブラリの活用メール等は validator.js 等の実績あるライブラリを検討

    8.7 入力値検証の流れ（まとめ）

    外部からの入力
    │
    ├─ 1. エンコーディング検証・変換
    ├─ 2. 制御文字・文字数・数値範囲のチェック
    ├─ 3. 正規表現による形式チェック（ホワイトリスト）
    │
    ▼
安全な処理へ

    9.代表的な攻撃：SQLインジェクション・XSS・CSRF

    ここからは基礎講座（第3回）の内容です。Webアプリ開発者が必ず知っておくべき3つの攻撃のあらましを示します。仕組みと対策の詳細はそれぞれのページで解説します。

    9.1 SQLインジェクション

    悪意のあるSQL文を入力として送り込み、データベースを不正操作する攻撃 です。わかりやすく言えば「入力欄を使って、アプリに『別の命令』を紛れ込ませる攻撃」で、Webアプリの脆弱性の中でも最も危険なもののひとつです。たとえばユーザー名に alice' OR '1'='1' -- と入れると、'（文字列の区切り）で文字列を閉じ、OR '1'='1'（常に成り立つ条件）を足し、--（以降をコメント扱い）でパスワード条件を消せてしまいます。

    手口入力例被害
    認証回避alice' OR '1'='1' --全ユーザーが返り、最初の1件（多くの場合は管理者）でログイン成功
    データの全件取得' OR 1=1 --全ユーザーのID・パスワードハッシュ・メールアドレスなどが漏洩
    データの削除'; DROP TABLE users; --ユーザーテーブルが完全に消え、バックアップがなければ復旧不可
    他テーブルのデータ取得（UNION攻撃）' UNION SELECT username, password FROM admin_users --管理者のID・パスワードハッシュが取得され、システム全体を乗っ取られる

    対策の本命は プリペアドステートメント（SQLの骨格を先に確定させ、データは後から別に渡す仕組み）です。データが何であってもSQL命令として解釈されません。

    脆弱なコード（文字列結合でSQL生成） 
    username = request.form['username']
password = request.form['password']
sql = f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'"
cursor.execute(sql)
    安全なコード（プリペアドステートメント） 
    sql = "SELECT * FROM users WHERE username = ? AND password = ?"
cursor.execute(sql, (username, password))
# → ユーザーの入力は「データ」として扱われる
# → SQLの「命令」として解釈されない！

    ORM（Object-Relational Mapper） は、SQLを直接書かずにプログラムのオブジェクト操作でDBを扱える仕組みです（例：User.query.filter_by(id=user_id).first()）。Django・Rails（ActiveRecord）・Laravel（Eloquent）・Spring（JPA/Hibernate）・Prisma など、ほとんどのモダンなフレームワークのORMは内部でプリペアドステートメントを使っているため、正しく使っている限りリスクは大幅に軽減されます。ただし生のSQLを書く機能（rawQuery など）を使うときや、ORMの機能を意図せず回避してしまうときは、必ずプリペアドステートメントを使います。

    対策説明
    プリペアドステートメント最も重要・SQLとデータを分離する
    ORM の使用SQLを直接書かずに済む
    入力値のバリデーション想定外の文字列を弾く
    最小権限のDBユーザー万が一の被害を最小化
    エラーメッセージを隠すDB構造を攻撃者に教えない

    手口の段階的な分解と、動的な検索条件・ソートの扱いは 20-3 SQLインジェクション で解説します。

    補足：DROP TABLE の例について

    ; で区切って2つ目のSQLを実行させる手口（複文実行）は、DBやドライバの設定によっては既定で無効になっています。ただし、だから安全というわけではなく、認証回避やUNION攻撃は複文なしでも成立します。

    9.2 XSS（クロスサイトスクリプティング）

    悪意のあるJavaScriptを被害者のブラウザ上で実行させる攻撃 です。攻撃者の目的は、セッションIDを盗む（Cookieに保存されたセッション情報を窃取してなりすましログイン）、フィッシングサイトへの誘導、マルウェアのダウンロード、キーロガー（キー入力の記録）でのパスワード窃取などです。

    反射型XSS（Reflected XSS）

    攻撃者が https://example.com/search?q=<script>…</script> のような悪意あるURLを作り、メールやSNSで送ります。被害者がクリックすると、サイトがパラメータをそのままページに表示し、スクリプトが実行されてCookieが攻撃者に送られます。

    蓄積型XSS（Stored XSS）

    攻撃者がコメント欄などにスクリプトを投稿し、DBに保存されます。そのページを開いた 全訪問者 のブラウザでスクリプトが実行されるため、被害が広がります。

    脆弱なコード（ユーザー入力をそのまま出力） 
    name = request.args.get('name')
return f"<p>こんにちは、{name}さん！</p>"
    安全なコード（HTMLエスケープ） 
    from html import escape
name = escape(request.args.get('name'))
return f"<p>こんにちは、{name}さん！</p>"

# エスケープの例：
# <script> → &lt;script&gt;
# ブラウザは &lt; を「<」と表示するが
# HTMLタグとして解釈しない！

    保険として CSP（コンテンツセキュリティポリシー） も使えます。「このページでは〇〇からのスクリプトしか実行しない」という宣言をHTTPヘッダで送る仕組みで、たとえば Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted.cdn.com とすると、外部から注入されたスクリプトはブロックされ、XSSの影響を大幅に軽減できます。

    対策説明
    出力時のHTMLエスケープ< > " などを無害化
    CSPの設定信頼できるスクリプトだけ実行を許可
    HttpOnly属性JSからCookieを読み取り不可にする
    テンプレートエンジンの活用自動エスケープ機能を使う

    詳しくは 20-1 XSSの基本・20-2 XSS発展編・10-4 CSP を参照してください。

    9.3 CSRF（クロスサイトリクエストフォージェリ）

    ログイン済みのユーザーに意図しないリクエストを送らせる攻撃 です。XSSが「悪意あるスクリプトをブラウザで実行させる」のに対し、CSRFは「ログイン済みの状態を悪用して意図しない操作を実行させる」点が違います。たとえば bank.com にログイン中の被害者が罠サイト evil.com を開くと、そこに仕込まれた <img src="https://bank.com/transfer?to=attacker&amount=100000"> によってブラウザが bank.com へリクエストを送り、セッションCookieも一緒に送られるため、正規の送金として処理されてしまいます。

    最も重要な対策は CSRFトークン です。サーバーがランダムなトークンを生成してフォームの隠しフィールド（<input type="hidden" name="csrf_token" value="ランダムな文字列">）に埋め込み、送信時に検証します。悪意あるサイトはトークンの値を知る方法がないため、正しいリクエストを作れません。

    Flask での CSRF トークン実装例 
    from flask_wtf.csrf import CSRFProtect

app = Flask(__name__)
csrf = CSRFProtect(app)

# フォームに自動でCSRFトークンが追加される
    対策説明
    CSRFトークンフォームにランダムトークンを埋め込む
    SameSite Cookie他サイトからのリクエストにCookieを送らない
    Refererヘッダーの検証リクエスト元を確認する
    重要操作に再認証送金などはパスワードを再入力させる

    詳しくは 30-1 CSRF を参照してください。

    10.セッション管理の脆弱性

    セッションとCookieの詳しい解説は 74_セッション管理 のフォルダで扱います。ここでは基礎講座の要点をまとめます。

    10.1 セッションとクッキーは別の概念

    セッション（Session）

    サーバー側でユーザーの状態を管理する仕組みです。「誰がログイン中か」「カートに何が入っているか」をサーバーのメモリやDBに保存し、セッションID（例：abc123xyz）で管理します。

    クッキー（Cookie）

    ブラウザ側に情報を保存する仕組みです。サーバーが Set-Cookie ヘッダでブラウザに保存させる小さなデータで、次のリクエストから自動で送信されます。

    【2つの関係】
  サーバー：セッションID「abc123xyz」をセッションに紐づけて保存
      ↓ Set-Cookie: session_id=abc123xyz
  ブラウザ：クッキーにセッションIDを保存
      ↓ Cookie: session_id=abc123xyz（次のリクエストに自動添付）
  サーバー：クッキーのセッションIDで「この人はAliceさん」と識別

→ セッション = サーバー側の状態管理
→ クッキー   = セッションIDをブラウザに保存・送信するための入れ物

    10.2 セッションの仕組み

    HTTPは ステートレス（状態を持たない）プロトコルなので、リクエストのたびに「誰？」がわかりません。そこでセッションを使います。

    1. ログイン成功
    2. サーバーがセッションIDを発行・セッション情報をサーバーに保存
    3. ブラウザのクッキーにセッションIDを保存
    4. 以後のリクエストにクッキー経由でセッションIDを添付
    5. サーバーがセッションIDで「この人はAliceさん」と識別

    セッションIDは「ログイン状態の鍵」です。

    10.3 セッションハイジャック

    攻撃者がセッションIDを入手してリクエストすると、サーバーは本人として処理してしまいます。これが セッションハイジャック（セッションの乗っ取り）です。セッションIDの盗み方には次のものがあります。

    • XSSでCookieを盗む
    • 通信の盗聴（HTTPSを使っていない場合）
    • 推測しやすいセッションIDの総当たり

    10.4 セッション管理の対策

    • 十分にランダムなセッションIDを生成（128bit以上）
    • HTTPS必須（通信経路での盗聴を防ぐ）
    • Secure 属性：HTTPSのみでCookieを送信
    • HttpOnly 属性：JavaScriptからCookieを読み取り不可
    • SameSite 属性：CSRF対策
    • ログイン後にセッションIDを再生成（セッション固定攻撃を防ぐ）
    • 一定時間後にセッションを期限切れにする
    • ログアウト時にサーバー側のセッションを削除
    Set-Cookie: session_id=abc123; Secure; HttpOnly; SameSite=Strict

    11.ディレクトリトラバーサルと安全でないデシリアライゼーション

    11.1 ディレクトリトラバーサル

    Webアプリがファイルパスを外部から受け取る場合に、../（1つ上のフォルダ）を使って本来アクセスできないディレクトリのファイルを読み取る攻撃です。たとえば https://example.com/file?name=report.pdf が正常なリクエストなら、?name=../../../../etc/passwd とすると Linux のユーザー情報が返されてしまいます。AWS の認証情報ファイルを読まれる危険もあります。

    対策は、ユーザー入力をファイルパスに直接使わない、パスを正規化して想定ディレクトリ外をブロックする、ホワイトリストで許可するファイルを限定する、Webサーバーのプロセスに最小権限を付与する、の4つです。詳しくは 40-1 ファイルアクセスとディレクトリトラバーサル を参照してください。

    11.2 安全でないデシリアライゼーション

    デシリアライゼーション とは、保存や送信のためにバイト列にしたオブジェクト（データ構造）を、元のオブジェクトに戻す処理です。攻撃者が悪意あるデータをシリアライズして送り、アプリがそれをデシリアライズすると、悪意あるコードが実行されてしまいます。

    対策として、ノートでは「信頼できないデータのデシリアライズを避ける」「JWTなど安全な形式を使う」「デシリアライズ前にデータを検証する」が挙げられています。詳しくは 40-3 Evalインジェクション・デシリアライズ・XXE を参照してください。

    補足：「JWTなど安全な形式」について

    JWT は署名付きのトークン形式で、オブジェクトを丸ごと復元する仕組みの代わりではありません。一般的な対策は、外部から受け取るデータには JSON のような「データだけを表す形式」 を使い、言語固有のシリアライズ形式（PHP の unserialize、Python の pickle など）を使わないことです。JWT を使う場合も、署名の検証が前提になります。

    12.OWASP Top 10

    OWASP（Open Web Application Security Project） は、Webアプリケーションセキュリティの向上を目的とした非営利組織です。数年ごとに「最も危険なWebアプリの脆弱性 Top 10」を発表しています。各項目の詳しい解説は 71_セキュリティ基礎の OWASP Top 10とは 以降のページにあります。

    12.1 OWASP Top 10（2021年版）

    順位カテゴリ概要
    A01アクセス制御の不備権限のないリソースへのアクセスが可能
    A02暗号化の失敗機密データが暗号化されていない・弱い暗号
    A03インジェクションSQLi・コマンドインジェクションなど
    A04安全でない設計セキュリティを考慮しない設計そのものの問題
    A05セキュリティの設定ミスデフォルト設定・不要な機能の有効化など
    A06脆弱なコンポーネント古いライブラリ・フレームワークの使用
    A07認証・識別の失敗弱いパスワード・MFAなし・セッション管理の不備
    A08ソフトウェアの完全性の失敗安全でないCI/CDパイプライン・デシリアライゼーション
    A09ログ・監視の失敗攻撃を検知・記録できない
    A10SSRFサーバー側からの偽リクエスト

    注意：2025年版が出ています

    ノートの表は2021年版です。2025年版では項目の統合や順位の入れ替えがあります（たとえば SSRF はアクセス制御の不備に統合されました）。2021年版と2025年版の対応は OWASP Top 10とは で確認してください。

    12.2 主な項目のポイント

    A01：アクセス制御の不備（最も多い脆弱性）

    URLを変えるだけで他人のデータが見える（/user/1001/profile → /user/1002/profile。IDOR：Insecure Direct Object Reference と呼ばれる）、管理者ページにログインなしでアクセスできる、など。対策は、すべてのAPIエンドポイントで認可チェック、デフォルトで「拒否」して必要なものだけ許可、ユーザーが自分のデータだけ操作できるかの確認です。→ 71 アクセス制御と認証の失敗

    A05：セキュリティの設定ミス

    デフォルトのパスワードを変更していない、本番環境でデバッグモードが有効、エラーメッセージにスタックトレース（エラー発生箇所の詳細な記録）を表示、不要なポートが開放されている、S3バケットが誰でも読み取り可能、など。対策は、セキュリティのベースライン設定を決める、本番・開発環境の設定を分ける、定期的にセキュリティスキャンを実施する、です。→ 71 安全でない設計・設定ミス・古い部品

    A06：脆弱なコンポーネント

    実例は Log4Shell（2021年）。Java のログライブラリ「Log4j」の脆弱性で世界中のサーバーが影響を受け、修正パッチが出るまでの数日間で大量のシステムが攻撃されました。依存ライブラリの脆弱性は自分のコードを書き換えても直らず、どこで使っているかわからないこともあります。対策は、依存パッケージを定期的に更新する、npm audit・pip-audit 等でスキャンする、SBOM（ソフトウェア部品表）を管理する、GitHub Dependabot などの自動更新ツールを活用する、です。→ 71 安全でない設計・設定ミス・古い部品

    A10：SSRF（サーバーサイドリクエストフォージェリ）

    サーバーに内部ネットワークへのリクエストを代理で送らせる攻撃です。例：URLプレビュー機能に http://169.254.169.254/latest/meta-data/（AWS のメタデータエンドポイント）を指定させ、サーバーが AWS 認証情報を取得して返してしまう。対策は、URLのホワイトリスト、内部IP・プライベートIPへのアクセス拒否、クラウドでは IMDSv2 の使用（AWS の場合）です。→ 30-3 SSRF

    13.安全なWebアプリを作るための5つの原則

    原則具体的には
    ① 入力値は信頼しないすべてのユーザー入力を検証・サニタイズ（無害化）する。「悪意ある入力が来る前提」で設計する
    ② 出力時にエスケープするHTMLに出力するときはHTMLエスケープ、SQLに渡すときはプリペアドステートメント、シェルコマンドに渡すときはエスケープ
    ③ 最小権限を徹底するDBユーザーは必要な操作だけ許可。APIはアクセスできるデータを必要最小限に（→ 71 最小権限とデータ最小化）
    ④ エラーメッセージに情報を入れない「ユーザーが見つかりません」ではなく「IDまたはパスワードが違います」。スタックトレースを本番で表示しない
    ⑤ ライブラリ・フレームワークを最新に保つ依存関係の脆弱性は自分のコードと同じくらい危険

    補足：シェルコマンドは「エスケープ」より「シェルを使わない」

    ②のシェルコマンドについては、エスケープよりも、そもそもシェルを経由しない呼び出し方（引数を配列で渡す関数を使う）や、コマンドを呼ばずにライブラリで済ませる方法が優先です。20-4 OSコマンドインジェクション で解説します。

    14.何をいつ対策するか：全アプリ必須と機能実装時

    脆弱性対策は「毎回全部やる」のではなく、どのアプリでも必ず押さえるものと、その機能を入れるときに考えるものに分けると漏れにくくなります。

    14.1 A. ほぼすべてのWebアプリで対応が必要

    HTMLを返し、状態を持ち、DBやセッションを使う一般的なWebアプリでは、次は前提として対策します。

    領域対応章要点
    出力のエスケープ（XSS）5, 6（20-1・20-2）HTML/属性/JS/URLなど文脈ごとのエスケープ
    SQL呼び出しの安全化7（20-3）プリペアドステートメント、命令とデータの分離
    CSRF対策8（30-1）状態変更リクエストの正当性確認
    セッション管理1, 9（74_セッション管理）安全な発行・固定化対策・タイムアウト・無効化
    Cookieの扱い11（74_セッション管理）HttpOnly / Secure / SameSite など
    HTTPS（通信の保護）（基礎・インフラ）盗聴・改ざん防止。TLSは必須前提
    入力検証の基本4（このページ 6章〜8章）型・長さ・形式の検証（ただしこれだけでは不十分）
    エラー・情報漏洩の抑制4, 18, 24（50-1）詳細エラーを外部に出さない、キャッシュ制御
    ログ出力24（71 ログ出力）認証失敗・重要操作の記録、秘密情報をログに書かない

    ユーザーアカウントがある場合は、次も 全アプリ必須 に近くなります（いずれも 73_認証認可 で扱います）。

    領域対応章要点
    認証21パスワード方針、MFA（多要素認証）、ブルートフォース（総当たり）対策
    認可23サーバー側での権限チェック（UI制御だけでは不可）
    アカウント管理22登録・変更・リセットの安全なフロー

    14.2 B. 機能を実装するときに考えるセキュリティ

    その機能を入れるときだけ、対応する脅威と対策を設計に含めます。

    機能・処理対応章考えること
    外部URLへのリダイレクト10（30-2）オープンリダイレクト、許可リスト
    メール送信12（20-5）ヘッダインジェクション、送信先の制御
    ファイルの読み書き・パス指定13（40-1）パストラバーサル、権限外ファイルへのアクセス
    OSコマンド・外部プロセス呼び出し14（20-4）コマンドインジェクション、呼び出し自体の回避
    ファイルアップロード15（40-2）拡張子・内容検査、保存場所、実行権限
    動的インクルード16（20-6）任意ファイル読み込み・実行
    XML / YAML / シリアライズ等の読み込み17（40-3）XXE、デシリアライズ攻撃

    14.3 判断の流れ（実装チェック）

    機能を追加する
  │
  ├─ 全アプリ必須（A）は満たしているか？
  │     XSS / SQLi / CSRF / セッション / Cookie / HTTPS / ログ …
  │
  └─ この機能固有のリスク（B）は何か？
        メール？ ファイル？ リダイレクト？ API？ コマンド実行？
        → 該当章の対策を設計・実装・テストに含める

    本命の対策＋保険を重ねる

    1つの対策が破られても次で止まるように重ねます。たとえば XSS なら「エスケープ（本命）」＋「CSP」＋「Cookie の HttpOnly」。SQL なら「プリペアドステートメント（本命）」＋「DB ユーザーの権限を最小に」＋「詳細エラーを出さない」。本命を省いて保険だけに頼るのは NG です。

    15.多層防御とOSI参照モデル

    アプリ層だけ守っても、下位層や運用が弱いと突破されます。1つの対策が破られても次の層で止める のが多層防御（Defense in Depth、深層防御とも）です。考え方の詳細は 71 深層防御、ファイアウォール・IDS/IPS・WAF などの仕組みは 71 ネットワークと端末の防御 で解説しています。

    OSI参照モデル は、通信の仕組みを物理層（L1）からアプリケーション層（L7）までの7つの層に分けて考えるモデルです。これに沿って、各層の脅威・対策と、Webサービスでの典型的な配置をまとめます（実務では層がまたがる対策も多くあります。上からインターネット側です）。

    層名称主な脅威の例セキュリティ対策の例Webサービスでの配置例
    L7アプリケーションSQLi, XSS, CSRF, 認可不備, 不正API利用セキュアコーディング、入力検証・出力エスケープ、認証・認可、レート制限、セキュアな設定WAF → Webアプリ（認証・認可・入出力対策）→ API認可
    L6プレゼンテーション平文データの盗聴・改ざん、不正な符号化TLSによる暗号化、証明書管理、適切な文字コード・エンコーディングTLS（HTTPS）の暗号化・証明書
    L5セッションセッションハイジャック、固定化、なりすまし安全なセッションID、再発行、タイムアウト、Cookie属性、再認証セッション・Cookie管理
    L4トランスポートポートスキャン、不正なTCP/UDP通信不要ポート閉鎖、ファイアウォール（ポート制御）、TLS終端の適切な配置境界FW（ポート制御）、TLS終端
    L3ネットワーク不正ルーティング、IPスプーフィング、DDoSファイアウォール（IP/ACL）、VPN、IDS/IPS、DDoS対策、セグメンテーションDDoS対策・境界FW・IDS/IPS
    L2データリンク不正端末の接続、ARPスプーフィングVLAN分割、ポートセキュリティ、MAC制限（環境による）VPC/サブネット分割、内部NWの分離
    L1物理機器への不正アクセス、ケーブル盗聴入退室管理、ラック施錠、媒体管理、冗長化・バックアップ拠点データセンター／クラウド事業者の物理管理
    （データ）L7の先情報漏洩、不正参照・改ざんDBアクセス制御、保存時暗号化、バックアップDB・ストレージの権限と暗号化
    （運用）人・プロセス設定ミス、未パッチ、検知遅れパッチ適用、監視、インシデント対応ログ監視・脆弱性管理・初動手順

    アプリ開発者が主に担うのは L5〜L7（セッション・アプリ・データ） です。L1〜L4 はインフラ・クラウド設定と分担しつつ、前提として把握しておきます。

    注意：層への割り当ては目安です

    Webのセッション管理（Cookie とセッションID）や TLS は、厳密な OSI の定義では L5・L6 にきれいに収まるものではなく、実際の通信（TCP/IP）では HTTP のセッション管理はアプリケーション層の一部として扱われます。この表は「どの層を守る対策か」を整理するための目安として読んでください。

    18.まとめ

    トピック要点
    入力‐処理‐出力モデル各段階で検証・安全な処理・エスケープが必要。入力値検証だけでは不十分
    エンコーディングの妥当性検証・変換UTF-8 として正しいか確認し、内部形式（UTF-8）に統一
    入力値の妥当性検証ホワイトリスト方式で型・形式・範囲・長さをサーバー側でチェック
    制御文字・文字数・数値改行・NULL 等の混入を防ぎ、最小・最大長や最小値・最大値で制限
    正規表現修飾子（i, u）、文字クラス、量詞、^ $ で全体一致の形式検証
    代表的な攻撃SQLi → プリペアドステートメント・ORM、XSS → HTMLエスケープ・CSP、CSRF → CSRFトークン・SameSite Cookie、セッションハイジャック → Secure/HttpOnly・HTTPS、ディレクトリトラバーサル → パスの検証・最小権限、SSRF → URLホワイトリスト・内部IPブロック
    判断軸「全アプリ必須（A）」を満たしたうえで、「機能固有（B）」のリスクを設計に含める
    多層防御OSI の各層と運用で対策を重ねる。開発者が主に担うのは L5〜L7 とデータ

    Webアプリのセキュリティは「攻撃パターンを知ること」が第一歩です。SQLi・XSS・CSRF の3つを理解するだけで、開発時の意識が大きく変わります。

    19.理解度チェック

    Q1. 「入力値をしっかり検証すれば、出力時のエスケープは不要」という考えはなぜ誤りですか？

    インジェクションは入力・処理・出力のそれぞれの段階で起きうるからです。入力値検証は明らかにおかしい値を弾く補助で、処理では命令とデータを分ける（プリペアドステートメント）、出力では出力先の文法に合わせてエスケープする、という本命の対策がそれぞれ必要です。

    Q2. 入力値に対して行う3つのステップを順に答えてください。

    ① 文字エンコーディングの妥当性検証 → ② 文字エンコーディングの変換（内部形式の UTF-8 に統一）→ ③ 入力値の妥当性検証、の順です。変換後に想定外の文字が生じることがあるので、変換後にも検証します。

    Q3. 入力値検証でホワイトリスト方式が推奨されるのはなぜですか？

    ブラックリスト（禁止する文字・パターンを並べる方式）は、危険な文字や表記ゆれを見落としやすいからです。ホワイトリストは「英小文字と数字、3〜16文字」のように許可する形式だけを定義するので、想定外の入力は自然に弾かれます。

    Q4. 次のうち「全アプリ必須」なのはどれですか？　(a) CSRF対策　(b) メールヘッダインジェクション対策　(c) 出力のエスケープ　(d) ファイルアップロードの内容検査

    (a) と (c) です。(b) はメール送信機能、(d) はアップロード機能を作るときに考える「機能実装時」の項目です。

    Q5. XSS対策として CSP と Cookie の HttpOnly だけを設定し、エスケープを省くのはなぜよくないのですか？

    CSP や HttpOnly は被害を小さくする「保険」で、XSS そのものを防ぐ本命の対策は出力時のエスケープだからです。多層防御は本命の対策に保険を重ねる考え方で、本命を省いて保険だけに頼るのは NG です。

    Q6. 「受動的攻撃」とはどのような攻撃ですか？　例も挙げてください。

    攻撃者がサーバーを直接攻撃するのではなく、罠サイトやメールで正規の利用者に罠を踏ませ、その人のブラウザ経由で攻撃する方式です（徳丸本での意味）。XSS や CSRF が代表例で、サーバーからは本物の利用者のリクエストに見えます。
