    30 リクエスト偽造・リダイレクト

    リダイレクトとHTTPヘッダインジェクション

    「ログイン後に元のページへ戻る」のような リダイレクト処理 は、多くの Web アプリにあります。このページでは徳丸本第10章をもとに、リダイレクト処理にまつわる2つの脆弱性 ── 任意の外部サイトへ飛ばされてしまう オープンリダイレクト と、レスポンスヘッダに改行を混ぜられる HTTPヘッダインジェクション ── とその対策を解説します。

    もとにしたノート：30_リクエスト偽造・リダイレクト/02_リダイレクト処理にまつわる脆弱性（徳丸本10章）

    ひとことで言うと

    「リダイレクト先やレスポンスヘッダの値はサーバーが決める。ユーザー入力をそのまま Location などのヘッダに入れない」 のが、この章の要点です。

    URL・ドメインの検証は XSS発展編「リンク先のドメイン名のチェック」（徳丸本第6章）で、HTTP ヘッダインジェクションの概要は第4章のノート（00_全体像/02_Webアプリの機能と脆弱性（徳丸本4章））で触れました。第10章では、リダイレクト処理 にまつわる脆弱性と対策を詳しく見ていきます。

    リダイレクト とは、サーバーがブラウザに「このURLへ移動して」と指示して、別のページへ自動で移らせることです。サーバーはレスポンスのステータスコードを 302 Found などにし、Location ヘッダ（移動先の URL を伝えるレスポンスヘッダ）に行き先を書きます。PHP では header('Location: ...') でこのヘッダを出力します。

    1.オープンリダイレクト

    オープンリダイレクト（Open Redirect） とは、Webアプリケーションが 任意の外部 URL へリダイレクトしてしまう脆弱性です。「オープン（開いている）」は、行き先を誰でも自由に指定できてしまう、という意味です。

    1.1 日常生活での例え

    正常なリダイレクト

    ログイン後、自サイトのマイページへ移動します。

    オープンリダイレクト

    「example.com のリンク」に見せかけて、フィッシングサイトへ飛ばされます。

    1.2 脆弱なコード

    URL の ?url= の部分（URL パラメータ。URL の末尾に付けてサーバーへ値を渡すしくみ）を、確認せずに Location ヘッダへ入れている例です。

    危険な例：ユーザー指定 URL へそのままリダイレクト（PHP） 
    // ❌ ユーザー指定 URL へそのままリダイレクト
$url = $_GET['url'];
header('Location: ' . $url);
exit;
    https://example.com/redirect?url=https://evil.com/phishing
  ↑ 信頼できるドメイン              ↑ 実際の行き先

    リンクの先頭は本物の example.com なので、URL を見ただけでは怪しいと気づきにくいのが問題です。

    1.3 攻撃の流れ

    フィッシング（本物を装って偽サイトへ誘導し、パスワードなどをだまし取る詐欺）の概要は さまざまな脅威と対策の基本「フィッシング」 を参照してください。オープンリダイレクトは、その誘導役に使われます。

    1. 攻撃者が悪意ある URL を作成
      https://bank.com/redirect?url=https://evil-bank.com/login
    2. 被害者にメール・SNS で送る（「銀行からのお知らせ」等）
    3. 被害者が bank.com の URL をクリック（信頼してクリック）
    4. bank.com が evil-bank.com へリダイレクト
    5. 偽のログインページで ID・パスワードを入力させられる

    1.4 被害

    被害説明
    フィッシング信頼ドメイン経由で偽サイトへ誘導
    OAuth 攻撃認可コード等の窃取（リダイレクト URI 悪用）
    マルウェア配布外部サイトへの誘導
    信頼の悪用正規サイトの URL が攻撃に利用される

    OAuth は「Google でログイン」のように、別のサービスに認可を任せるしくみです。認可サーバーは、ログインが済んだ証拠として 認可コード を リダイレクト URI（redirect_uri。認可後に戻ってくる先の URL）へ付けて返します。この戻り先がオープンリダイレクトで外部へ転送されると、認可コードが攻撃者の手に渡るおそれがあります（OAuth の詳細は 73_認証認可 フォルダで扱います）。マルウェア はウイルスなどの悪意あるソフトウェアのことです。

    1.5 よくある実装箇所

    • ログイン後の「元のページへ戻る」
    • ログアウト後のリダイレクト
    • 言語切替・モバイル版切替
    • 広告・提携先リンク
    • 「続きはこちら」ボタン

    2.差し支えがない場合

    外部ドメインへのリダイレクトは すべて禁止 すべきではありません。用途によっては 問題ない場合 があります。

    2.1 差し支えがない（許容しうる）ケース

    ケース説明
    自サイト内のみ同一ドメイン内のパスへリダイレクト
    明示的な外部リンクユーザーが「外部サイトへ移動」と理解できる UI
    検証済みの提携先ホワイトリストに登録されたパートナー URL
    OAuth 等の標準フロー仕様に沿った redirect_uri の検証

    ホワイトリスト（許可リスト）とは、「これだけは許可する」という値をあらかじめ列挙しておき、それ以外をすべて拒否する方式です。

    2.2 判断のポイント

    危険

    ユーザー入力や URL パラメータを 検証なしで Location に設定している。

    許容（対策済み）

    • 遷移先が固定、またはホワイトリストで検証済み
    • ユーザーに外部遷移が明示されている

    3.外部のドメインに遷移する仕様

    アプリケーションの 仕様として 外部ドメインへ遷移する機能があります。

    3.1 例

    機能遷移先
    SNS 連携twitter.com, facebook.com
    決済決済代行会社のドメイン
    SSO / OAuth認可サーバーのドメイン
    提携サービスパートナー企業のサイト
    アプリストアApp Store, Google Play

    SSO（シングルサインオン）は、1回のログインで複数のサービスを使えるようにするしくみです。

    3.2 設計上の注意

    外部遷移が仕様に含まれる場合でも、次を守ります。

    • ✅ 遷移先 URL はサーバー側で管理（固定 or ホワイトリスト）
    • ✅ ユーザー入力をそのまま Location に使わない
    • ❌ ?url= パラメータで任意 URL を受け付けない

    4.外部ドメインに遷移することが自明である

    外部サイトへ移る場合、ユーザーがそれと分かる UI にすることが重要です。「自明」とは、説明されなくても見ればすぐ分かる、という意味です。

    4.1 自明にする方法

    方法例
    確認画面「外部サイト（○○.com）へ移動します。よろしいですか？」
    アイコン表示外部リンクアイコン（↗）を付ける
    文言の明示「外部サイトへ移動します」
    中間ページ自サイトの警告ページを挟んでからリダイレクト
    安全な例：中間ページ（HTML） 
    <!-- 中間ページの例 -->
<p>これより外部サイト（partner.example.net）へ移動します。</p>
<p>example.com とは別のサイトです。個人情報の入力にはご注意ください。</p>
<a href="/go/3">partner.example.net へ移動する</a>
<!-- /go/3 はサーバー側で ID→URL に変換 -->

    リンク先は URL そのものではなく /go/3 という番号になっている点に注目してください。この「番号指定」の考え方は 5.2 で詳しく扱います。

    4.2 なぜ重要か

    オープンリダイレクト ＋ 自明でない UI

    ユーザーは bank.com から来たと思い込む → フィッシング成功

    対策済み ＋ 自明な UI

    ユーザーは外部サイトだと認識 → フィッシングリスク低減

    注意

    UI で自明にするだけでは オープンリダイレクト脆弱性は解消されません。次の章の技術的対策と併用します。

    5.オープンリダイレクトの対策

    オープンリダイレクト対策には、主に3つの方法があります。上から順に安全です。

    1. リダイレクト先の URL を固定にする
    2. リダイレクト先の URL を直接指定せずに番号指定にする
    3. リダイレクト先のドメイン名をチェックする

    5.1 リダイレクト先のURLを固定にする

    最も安全な方法 は、リダイレクト先 URL を サーバー側で固定 することです。

    安全な例：行き先を固定する（PHP） 
    // ✅ ログイン後は常にダッシュボードへ
header('Location: /dashboard');
exit;

// ✅ ログアウト後は常にトップページへ
header('Location: /');
exit;

    戻り先 URL が必要な場合

    「ログイン前に見ていたページへ戻す」など、戻り先を受け取りたい場合は、自サイト内のパスだけ を許可します。

    危険な例：任意 URL を受け付ける 
    // ❌ 任意 URL を受け付ける
$returnUrl = $_GET['return'];
header('Location: ' . $returnUrl);
    安全な例：自サイト内のパスのみ許可 
    // ✅ 自サイト内のパスのみ許可
$returnUrl = $_GET['return'] ?? '/';
if (!str_starts_with($returnUrl, '/') || str_starts_with($returnUrl, '//')) {
    $returnUrl = '/';
}
header('Location: ' . $returnUrl);

    ?? '/' は「値がなければ '/' を使う」という意味です。str_starts_with（PHP 8 以降）は文字列が指定の文字で始まるかを調べる関数です。// で始まる URL は プロトコル相対 URL と呼ばれ、//evil.com は https://evil.com と同じ意味になるため、拒否しています（詳しくは XSS発展編「相対 URL の扱い」）。

    補足：/\ で始まる値にも注意

    多くのブラウザは Location の中のバックスラッシュ \ を / と同じに扱うため、/\evil.com は //evil.com と同じく外部サイトへの移動になります。上のコードはこれを通してしまうので、\ を含む値も拒否するか、/ の次の文字が英数字であることを確認するなど、より厳しく判定してください。

    // ✅ 2文字目に / や \ が来るものを拒否
if (!preg_match('#\A/(?![/\\\\])#', $returnUrl)) {
    $returnUrl = '/';
}

    ポイント

    ポイント説明
    相対 URL の検証/ で始まり、// で始まらない
    絶対 URL 禁止http:// で始まる外部 URL は拒否
    デフォルト値不正な場合は安全な固定 URL へ

    絶対 URL は https://example.com/page のようにスキームとドメインから書いた URL、相対 URL は /page のように今のサイトを基準にした URL です。

    5.2 リダイレクト先のURLを直接指定せずに番号指定にする

    URL を直接パラメータで渡す代わりに、番号（ID） でサーバー側の URL リストから選択します。

    仕組み

    サーバー側のマッピング:
  1 → https://partner-a.example.com
  2 → https://partner-b.example.com
  3 → https://help.example.com

リクエスト: /redirect?id=2
  → サーバーが ID=2 の URL へリダイレクト
  → ユーザーは URL を直接指定できない

    マッピング とは、「番号 → URL」のような対応表のことです。

    安全な例：番号から URL を引く（PHP） 
    $redirectMap = [
    1 => 'https://partner-a.example.com',
    2 => 'https://partner-b.example.com',
    3 => 'https://help.example.com',
];

$id = (int)($_GET['id'] ?? 0);
if (!isset($redirectMap[$id])) {
    header('Location: /');
    exit;
}
header('Location: ' . $redirectMap[$id]);
exit;

    (int) は値を整数に変換する書き方で、数字以外の文字列が来ても 0 などになります。対応表にない番号ならトップページへ戻すので、攻撃者が行き先を自由に選ぶ余地がありません。

    メリット

    メリット説明
    任意 URL 不可攻撃者が evil.com を指定できない
    管理が容易提携先変更はサーバー側リストを更新
    監査可能許可 URL がコードまたは DB で明示

    5.3 リダイレクト先のドメイン名をチェックする

    URL をパラメータで受け取る必要がある場合、ドメイン名をホワイトリスト で検証します。XSS発展編「ドメイン名チェックの方法」（第6章）でも触れた手法です。

    ホワイトリスト検証

    安全な例：スキームとホスト名を検証する（PHP） 
    function isAllowedRedirectUrl(string $url): bool {
    $allowedHosts = ['example.com', 'www.example.com', 'partner.example.net'];

    $parsed = parse_url($url);
    if ($parsed === false || !isset($parsed['host'])) {
        return false;
    }

    // スキーム検証
    if (!in_array($parsed['scheme'] ?? '', ['https', 'http'], true)) {
        return false;
    }

    // ホスト名検証（完全一致）
    return in_array($parsed['host'], $allowedHosts, true);
}

$url = $_GET['url'] ?? '';
if (!isAllowedRedirectUrl($url)) {
    header('Location: /');
    exit;
}
header('Location: ' . $url);
exit;

    parse_url は URL を スキーム（https などの先頭部分）・ホスト（example.com などのドメイン名）・パスなどの部品に分けて配列で返す PHP の関数です。in_array(..., true) の true は、型まで含めて厳密に比べる指定です。

    注意すべき bypass

    bypass（バイパス） とは、チェックをすり抜ける手口のことです。

    手法例対策
    サブドメイン偽装example.com.evil.comホスト名の 完全一致
    プロトコル相対//evil.com// で始まる URL を拒否
    URL エンコード%2f%2fevil.comデコード後に再検証
    @ 記号https://example.com@evil.comparse_url で host を正しく取得
    javascript:javascript:alert(1)スキームを https/http に限定

    example.com.evil.com は「example.com」という文字を含みますが、実際の持ち主は evil.com です。https://example.com@evil.com の @ より前は「ユーザー名」として扱われ、実際の接続先は evil.com になります。URL エンコード は、特殊な文字を % ＋16進数で表す書き方で、%2f は / を表します。

    相対 URL の扱い

    // //evil.com は https://evil.com と同義
if (str_starts_with($url, '//')) {
    return false;  // 拒否
}

    6.HTTPヘッダ・インジェクション

    HTTPヘッダインジェクション（HTTP Header Injection） は、ユーザー入力が HTTP レスポンスヘッダ に混入し、意図しないヘッダを注入する脆弱性です。レスポンスヘッダ とは、サーバーがブラウザへ返す応答のうち、本文の前に付く「付帯情報」の行のことです（Location、Set-Cookie、Content-Type など。代表的なものは セキュリティヘッダ も参照）。

    項目内容
    分類インジェクション系（第4章）
    対象Location、Set-Cookie、Content-Type 等のレスポンスヘッダ

    「データのつもりの入力が、構造（ここではヘッダの区切り）として解釈される」という、インジェクション共通の原因については インジェクションと暗号化の不備「データとコードの混在」 を参照してください。

    6.1 日常生活での例え

    正常

    サーバーが「このページへ移動して」と Location ヘッダを1つ送ります。

    インジェクション

    入力に改行を混ぜ、追加のヘッダ や 別のレスポンス を送らせます。

    6.2 脆弱なコード

    危険な例：ユーザー入力を Location ヘッダに直接出力（PHP） 
    // ❌ ユーザー入力を Location ヘッダに直接出力
$url = $_GET['url'];
header('Location: ' . $url);

    オープンリダイレクトの脆弱なコードと同じ形です。同じ1行が、2つの脆弱性の原因になりえます。

    6.3 攻撃入力

    url=/home%0d%0aSet-Cookie:%20admin=1

%0d%0a = キャリッジリターン + ラインフィード（改行）

    HTTP のヘッダは1行に1つで、行の区切りは CR LF（\r\n）です。CR（キャリッジリターン） と LF（ラインフィード） は改行用の制御文字で、URL エンコードすると %0d と %0a になります。%20 は半角スペースです。CR・LF の考え方は メールヘッダインジェクション「メールの構造」 と同じです。

    6.4 生成されるレスポンス

    HTTP/1.1 302 Found
Location: /home
Set-Cookie: admin=1

→ 攻撃者が任意の Cookie を注入可能

    Set-Cookie は、ブラウザに Cookie（サイトがブラウザに保存させる小さなデータ）を保存させるヘッダです。攻撃者は被害者のブラウザに好きな Cookie を仕込めるため、たとえば攻撃者が用意したセッション ID を使わせる攻撃（セッション固定攻撃。74_セッション管理 で扱います）の足がかりになります。

    補足：今の PHP の header() は改行を拒否します

    PHP は 5.1.2 以降、header() に改行を含む値を渡すと「ヘッダは1行しか送れない」として警告を出し、そのヘッダを送りません。Node.js の標準 HTTP モジュールも、ヘッダ値に CR・LF があるとエラーにします。そのため、上の例は 最近の PHP ではそのままは成立しません。ただし、古い環境・別の言語やフレームワーク・ヘッダを自前で組み立てる実装では今も起こりえますし、同じコードは オープンリダイレクト としては脆弱なままです。「処理系が守ってくれるはず」に頼らず、次の章の対策を行ってください。

    6.5 他の攻撃例

    注入先攻撃
    Locationリダイレクト + 追加ヘッダ
    Set-Cookie任意 Cookie の設定
    本文との混在ヘッダ後に HTML を注入（XSS 的効果）

    改行を2つ続けて送ると「ヘッダの終わり（空行）」と解釈され、その後ろに好きな HTML を本文として入れられます。これにより XSS（ページに攻撃者のスクリプトを埋め込む攻撃）と同じ効果が出ます。このように1つのレスポンスを分割・改変する攻撃は HTTP レスポンス分割 とも呼ばれます。

    6.6 関連：メールヘッダインジェクション

    メール送信機能で To / Subject 等 に改行を混入させ、Bcc 等を追加する攻撃も同系統です（第4章）。詳しくは メールヘッダインジェクション で解説しています。

    7.HTTPヘッダインジェクションの対策

    7.1 外部からのパラメータをHTTPレスポンスヘッダとして出力しない

    根本対策 は、外部入力を ヘッダ値として使わない ことです。外部入力 とは、URL パラメータやフォームの値など、利用者（攻撃者を含む）が自由に送ってこられる値のことです。

    危険な例：ユーザー入力をヘッダに 
    // ❌ ユーザー入力をヘッダに
header('Location: ' . $_GET['url']);
header('Set-Cookie: theme=' . $_GET['theme']);
    安全な例：固定値または検証・変換済みの値のみ 
    // ✅ 固定値または検証・変換済みの値のみ
header('Location: /dashboard');
header('Set-Cookie: theme=light; HttpOnly; Secure');

    HttpOnly（JavaScript から読めなくする）や Secure（HTTPS のときだけ送る）は Cookie の属性です。詳しくは CORSエラーの対処法とCookie「HttpOnly・Secure・SameSite」 を参照してください。

    原則

    HTTP レスポンスヘッダの値 ＝ サーバー側で決定した固定値、または 厳密に検証・サニタイズした値。ユーザー入力をそのままヘッダに載せません。

    サニタイズ とは、危険な文字を取り除いたり無害な形に変えたりすることです。

    7.2 専用APIと改行チェック（両方実施）

    ヘッダ生成が必要な場合は、次の 2つを両方 実施します。

    ① リダイレクトやクッキー生成を専用 API に任せる

    散在させず、専用の関数・クラスに集約 し、検証ロジックを一箇所にまとめます。ここでの API は、決まった使い方で呼び出せる関数や部品のことです。

    安全な例：リダイレクト・Cookie 設定の専用関数（PHP） 
    // リダイレクト専用関数
function safeRedirect(string $url): void {
    if (!isAllowedRedirectUrl($url)) {
        $url = '/';
    }
    header('Location: ' . $url);
    exit;
}

// Cookie 設定専用関数
function setThemeCookie(string $theme): void {
    $allowed = ['light', 'dark'];
    if (!in_array($theme, $allowed, true)) {
        $theme = 'light';
    }
    setcookie('theme', $theme, [
        'httponly' => true,
        'secure'   => true,
        'samesite' => 'Strict',
    ]);
}

    isAllowedRedirectUrl は 5.3 の関数です。setcookie は PHP 標準の Cookie 設定関数で、値をエンコードしてヘッダを組み立ててくれます（配列でオプションを渡す書き方は PHP 7.3 以降）。

    メリット

    メリット説明
    検証の一元化漏れ・バラつきを防ぐ
    レビュー容易セキュリティコードが一箇所
    テスト可能専用関数の単体テスト

    ② ヘッダ生成するパラメータの改行文字をチェック

    どうしても外部入力を使う場合、改行文字（CR/LF）を拒否 します。第4章の制御文字チェックと同様です（メールヘッダでの同じ対策は メールヘッダインジェクション「改行を含めないようチェックする」）。

    安全な例：CR・LF・NULL を含む値を拒否（PHP） 
    function containsHeaderInjectionChars(string $value): bool {
    return preg_match('/[\r\n\x00]/', $value) === 1;
}

function safeRedirect(string $url): void {
    if (containsHeaderInjectionChars($url)) {
        $url = '/';
    }
    if (!isAllowedRedirectUrl($url)) {
        $url = '/';
    }
    header('Location: ' . $url);
    exit;
}

    preg_match は正規表現（文字列のパターン）に一致するかを調べる関数で、/[\r\n\x00]/ は「CR・LF・NULL のどれかを含む」という意味です。

    チェック対象の文字

    文字コード危険性
    CR\r (0x0D)新しいヘッダ行の開始
    LF\n (0x0A)新しいヘッダ行の開始
    NULL\0 (0x00)ヘッダの truncation

    NULL は「文字列の終わり」を意味する特殊な文字で、処理系によってはここで値が切り捨てられます（truncation ＝切り詰め）。

    URL エンコードされた改行も注意

    入力: %0d%0aSet-Cookie: evil=1
→ urldecode 後に改行チェックが必要
    $url = urldecode($_GET['url']);
if (containsHeaderInjectionChars($url)) {
    // 拒否
}

    補足：$_GET はすでにデコード済みです

    PHP の $_GET に入る値は、URL エンコードが すでに1回デコードされた後 のものです（%0d%0a は $_GET の時点で本物の CR LF になっています）。そのため、通常は $_GET['url'] をそのまま改行チェックすれば十分で、さらに urldecode すると 二重デコード になります。大切なのは「実際にヘッダへ出力する値そのもの をチェックする」ことです。デコードした値を検証したなら、出力するのも同じ値にしてください（%250d のように二重にエンコードされた値を、検証後にもう一度デコードして使うと、チェックをすり抜けます）。

    フレームワークの利用

    環境推奨
    PHPheader() 前に検証、または Symfony Response 等
    Express.jsres.redirect() は比較的安全だが URL 検証は必要
    一般ヘッダ出力 API をラップして統一

    ラップする とは、元の関数を自分の関数で包み、必ず検証を通ってから呼ばれるようにすることです。Express の res.redirect() はヘッダインジェクションには比較的強いものの、行き先の検証（オープンリダイレクト対策）はしてくれない 点に注意します。

    8.まとめ

    8.1 オープンリダイレクト

    トピック要点
    オープンリダイレクト任意 URL へ飛ばす脆弱性。フィッシングに悪用
    差し支えない場合検証済み・自サイト内・明示的 UI
    外部ドメイン遷移仕様としてあり得るが URL はサーバー管理
    URL 固定最も安全
    番号指定ID → URL マッピングで任意 URL を防ぐ
    ドメイン名チェックホワイトリスト + bypass 対策

    8.2 HTTPヘッダインジェクション

    トピック要点
    ヘッダインジェクション改行で追加ヘッダを注入
    根本対策外部入力をヘッダ値に使わない
    専用 APIリダイレクト・Cookie 生成を一元化
    改行チェック\r \n \0 を拒否（両方実施）

    8.3 対策の優先順位

    オープンリダイレクト

    1. リダイレクト先 URL を固定（最優先）
    2. 番号指定でサーバー側マッピング
    3. どうしても URL 指定ならドメインホワイトリスト
    4. 外部遷移は UI で明示

    HTTPヘッダインジェクション

    1. 外部入力をヘッダに載せない
    2. 専用 API に集約 + 改行文字チェック（両方）
    3. 制御文字・URL デコード後の再検証

    9.理解度チェック

    Q1. https://bank.com/redirect?url=https://evil-bank.com/login のような URL が、フィッシングに効果的なのはなぜですか？

    URL の先頭が本物の bank.com なので、受け取った人は信頼してクリックしてしまうからです。bank.com が url= の値を検証せずにリダイレクトすると、被害者は気づかないまま偽サイト（evil-bank.com）へ運ばれ、ID・パスワードを入力させられます。

    Q2. オープンリダイレクトの3つの対策を、安全な順に並べてください。

    ① リダイレクト先 URL を固定にする（最も安全）、② URL を直接指定させず番号指定にしてサーバー側の対応表から引く、③ どうしても URL を受け取るならドメイン名をホワイトリストで完全一致チェックする、の順です。UI で外部遷移を明示するのは補助で、それだけでは脆弱性は解消されません。

    Q3. 戻り先として / で始まる値だけを許可しました。//evil.com を拒否しなければいけないのはなぜですか？

    // で始まる URL はプロトコル相対 URL で、https://evil.com と同じ意味になるからです。/ で始まっていても自サイト内とは限りません（同様にブラウザによっては /\evil.com も外部扱いになります）。

    Q4. ホスト名のチェックで「文字列に example.com が含まれるか」と判定するのは、なぜ危険ですか？

    example.com.evil.com のように、攻撃者は自分のドメインに example.com を含めたサブドメインを作れるからです。parse_url でホスト名を取り出し、許可リストと 完全一致 で比べます。

    Q5. url=/home%0d%0aSet-Cookie:%20admin=1 が header('Location: ' . $url) に渡ると、何が起きますか？

    %0d%0a（CR LF）でヘッダの行が分かれ、Location: /home の次の行に Set-Cookie: admin=1 が本物のヘッダとして追加されます。攻撃者は被害者のブラウザに任意の Cookie を設定できます（なお、最近の PHP の header() は改行を含む値を拒否しますが、環境に頼らず対策が必要です）。

    Q6. HTTPヘッダインジェクション対策で「両方実施」とされている2つは何ですか？ そもそもの根本対策は？

    根本対策は 外部入力をヘッダ値に使わない ことです。どうしてもヘッダを生成する場合は、① リダイレクトや Cookie 生成を専用の関数（API）に集約する、② ヘッダに使う値の改行文字（CR・LF、あわせて NULL）をチェックして拒否する、の両方を行います。
