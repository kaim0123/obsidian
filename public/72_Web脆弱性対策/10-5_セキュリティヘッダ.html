    10 ブラウザのセキュリティモデル

    セキュリティヘッダ

    サーバーがレスポンスに数行足すだけで、ブラウザの動きを安全側に切り替えられるのがセキュリティヘッダです。HSTS・クリックジャッキング対策・nosniff・Referrer-Policy・Permissions-Policy・COOP/CORP などを1つずつ取り上げ、何を防ぐのか、推奨値は何か、Express・Next.js・nginx でどう設定するか、そしてやりがちな落とし穴までを解説します。

    もとにしたノート：10_ブラウザのセキュリティモデル/10_セキュリティヘッダ全般

    ひとことで言うと

    セキュリティヘッダは、サーバーがレスポンスに付ける 「ブラウザへの指示書」 です。アプリの脆弱性そのものは直せませんが、XSS・クリックジャッキング・通信の盗聴などが 起きても被害を小さくする 多層防御の層になります（→ 深層防御）。

    1.セキュリティヘッダの全体像

    HTTP ヘッダ とは、HTTP のリクエストやレスポンスの本文の前に付く「付帯情報」の行です（例：Content-Type: text/html）。このうち、ブラウザに安全のための動きを指示するものをまとめて セキュリティヘッダ と呼びます。

    関連する大きなテーマは別ページに分けています。CSP（コンテンツセキュリティポリシー）は CSP、CORS は CORS の仕組み、Cookie の属性はセッション管理（74_セッション管理）で扱います。

    ヘッダ防ぐもの推奨値
    Strict-Transport-Security（HSTS）HTTP への格下げ・盗聴max-age=63072000; includeSubDomains
    Content-Security-PolicyXSS・不正なリソース読み込み・フレーム埋め込みサイトに合わせて作る（→ CSP）
    X-Frame-OptionsクリックジャッキングDENY または SAMEORIGIN
    X-Content-Type-OptionsMIME スニッフィングによる XSSnosniff
    Referrer-PolicyURL に含まれる情報の漏えいstrict-origin-when-cross-origin
    Permissions-Policyカメラ・位置情報などの悪用camera=(), microphone=(), geolocation=()
    Cross-Origin-Opener-Policy（COOP）別ウィンドウからの干渉・XS-Leakssame-origin
    Cross-Origin-Resource-Policy（CORP）他サイトからのリソース読み込みsame-origin / same-site
    Cache-Control共有キャッシュからの個人情報漏えい個人向けページは no-store

    考え方

    どれも「ブラウザに やってはいけないこと を教える」ものです。ヘッダが無いと、ブラウザは古いサイトでも動くように 互換性優先のゆるい動作 をします。ヘッダは「このサイトは新しい安全なルールで動いてよい」という宣言です。

    2.Strict-Transport-Security（HSTS）

    2.1 何が問題か

    利用者が example.com と打つと、最初の 1 回は HTTP（暗号化なし）で接続されます。サーバーはふつう「HTTPS へ移ってください」というリダイレクトを返しますが、この最初の 1 回を公衆 Wi-Fi などで横取りされると、HTTPS へのリダイレクトを消され、平文のまま通信させられます。これを SSL ストリップ攻撃 と呼びます。

    補足：最近のブラウザの動き

    最近の主要ブラウザは、アドレスバーにドメイン名だけを打った場合、先に HTTPS を試すようになっています。それでも http:// で始まるリンクやブックマーク、古いブラウザでは HTTP で接続されるため、HSTS の必要性は変わりません。

    2.2 HSTS の働き

    Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
    指定意味
    max-ageこの秒数のあいだ、ブラウザはこのドメインに HTTPS でしか接続しない（63072000 秒 = 2 年）
    includeSubDomainsサブドメイン（shop.example.com など）にも適用
    preloadブラウザに最初から組み込まれた「HTTPS 専用リスト」（プリロードリスト）への登録を希望する
    • 一度受け取ると、利用者が http:// と打っても ブラウザ内部で https に書き換える。証明書エラーも「無視して続行」できなくなります。
    • HTTPS のレスポンスで返したときだけ有効です（HTTP で返しても無視される）。

    2.3 注意

    • includeSubDomains を付ける前に、HTTP でしか動かないサブドメインがないか 確認する。あるとアクセスできなくなります。
    • preload は外すのに数か月かかります。最初は max-age=300（5 分）などの短い値で試し、問題がないことを確かめてから伸ばします。

    3.X-Frame-Options と frame-ancestors（クリックジャッキング対策）

    3.1 クリックジャッキングとは

    クリックジャッキング とは、攻撃者のページに、対象サイトを 透明な iframe（ページの中に別のページをはめ込む HTML の仕組み）で重ねて表示し、利用者に「ゲームのボタン」を押させているつもりで、実は「退会する」「送金する」ボタンを押させる攻撃です。

    同一オリジンポリシー は iframe の中身を攻撃者のスクリプトから読むことは防ぎますが、表示して重ねること自体 は防ぎません。そこで「そもそも埋め込ませない」ヘッダが必要になります。

    CSRF（利用者に気づかれないよう勝手にリクエストを送らせる攻撃。CSRF のページで扱います）と違い、利用者本人が本物の画面で操作する ので、CSRF トークンでは防げません。

    3.2 対策

    X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none'
    値X-Frame-OptionsCSP frame-ancestors
    どこにも埋め込ませないDENY'none'
    同じオリジンだけ許可SAMEORIGIN'self'
    特定サイトを許可（ALLOW-FROM は廃止済み）https://partner.example
    • 新しい仕様は CSP の frame-ancestors です。両方あるとブラウザは frame-ancestors を優先します。
    • 古いブラウザ向けに 両方付ける のが一般的です。

    4.X-Content-Type-Options

    X-Content-Type-Options: nosniff

    ブラウザには、Content-Type（「このデータは HTML です」「画像です」といった種類＝ MIME タイプ を示すヘッダ）を信用せず、中身を見て種類を推測する 動作があります。これを MIME スニッフィング と呼びます。これがあると、text/plain で返したアップロードファイルの中身に <script> があると、HTML として実行されることがあります。

    • nosniff を付けると、ブラウザは Content-Type のとおりに扱います。
    • <script src> で読む先が JavaScript の MIME タイプでなければ、実行されません。
    • アップロードファイルの配信で特に重要です（ファイルアップロード で扱います）。JSON API での効果は WebAPIの脆弱性 で扱います。

    前提

    Content-Type を正しく付けること。間違った型を返していると、nosniff で逆に動かなくなります（例：JavaScript を text/plain で返していると、スクリプトが読み込まれなくなる）。

    5.Referrer-Policy

    リンクを踏んだとき、ブラウザは遷移元の URL を Referer ヘッダで送ります（綴りは仕様の誤記がそのまま残ったもので、ポリシー側は正しい綴りの Referrer）。URL に セッション ID・パスワードリセット用トークン・検索語 が入っていると、外部サイトに漏れます。

    Referrer-Policy: strict-origin-when-cross-origin
    値同じオリジンへ別オリジンへ
    no-referrer送らない送らない
    same-originフル URL送らない
    strict-origin-when-cross-originフル URLオリジンだけ（HTTPS→HTTP では送らない）
    unsafe-urlフル URLフル URL（使わない）

    ここでの オリジン は「スキーム＋ホスト＋ポート」（例：https://example.com）のことです（→ 受動的攻撃と同一オリジンポリシー）。「オリジンだけ」なら、パスやクエリ文字列に入った秘密は送られません。

    • 現在のブラウザの既定値は strict-origin-when-cross-origin ですが、明示しておくと古いブラウザでも同じ動作になります。
    • 根本対策は URL に秘密を入れない ことです。ヘッダは保険です。

    6.Permissions-Policy

    カメラ・マイク・位置情報・決済などのブラウザ機能を、そのページや埋め込んだ iframe が使えるか を決めます。

    Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()
    • () は「誰にも許可しない」、(self) は「自分のオリジンだけ」。
    • 広告や外部ウィジェットを埋め込むサイトで、XSS や外部スクリプトに機能を悪用させない ために使います。
    • 旧名は Feature-Policy です。

    7.COOP / COEP / CORP（クロスオリジン分離）

    Spectre（CPU の投機実行を悪用して、同じプロセス内の別データを読み取る脆弱性）のような CPU の脆弱性や、別ウィンドウからの探り（XS-Leaks：別サイトのページの状態を、読み込み時間やウィンドウの数などの副次的な情報から推測する攻撃）への対策として追加されたヘッダです。

    ヘッダ役割よく使う値
    COOP（Cross-Origin-Opener-Policy）window.open で開いた別オリジンのウィンドウと、window.opener で互いに触れないようにするsame-origin（OAuth のポップアップを使うなら same-origin-allow-popups）
    CORP（Cross-Origin-Resource-Policy）自分のリソース（画像・JS など）を、他サイトが <img> や <script> で読み込めるかsame-origin / same-site / cross-origin
    COEP（Cross-Origin-Embedder-Policy）自分のページが読み込むリソースに、CORP か CORS での許可を必須にするrequire-corp
    • COOP + COEP がそろうと「クロスオリジン分離」状態になり、SharedArrayBuffer（複数のスレッドでメモリを共有する機能。精密な時間計測に使えるため制限されている）などの強力な機能が使えます。
    • COEP は外部の画像や広告が読めなくなることがあるので、必要なサイトだけ 入れます。COOP と CORP は多くのサイトで入れやすいです。

    COOP

    ウィンドウ同士 の関係を切る。開いた側・開かれた側が互いに触れない。

    CORP

    読み込まれる側 の宣言。「自分のリソースを他サイトに使わせない」。

    COEP

    読み込む側 の宣言。「許可のないリソースは読み込まない」。

    8.キャッシュ・ログアウト関連

    ヘッダ使う場面
    Cache-Control: no-storeマイページ・個人情報・API の個人向け応答。CDN やプロキシ（利用者とサーバーの間で通信を中継・保存する機器）に残さない（競合状態とキャッシュからの情報漏洩 で扱います）
    Clear-Site-Data: "cache", "cookies", "storage"ログアウト時に、ブラウザに残ったキャッシュ・Cookie・Web ストレージを消させる

    9.付けない・消すべきヘッダ

    ヘッダ理由
    X-XSS-Protection古いブラウザの XSS フィルタ用。フィルタ自体が情報漏えいの原因になったため廃止。付けるなら 0（無効化）。XSS 対策は CSP で行う
    Public-Key-Pins（HPKP）設定ミスでサイトに永久に入れなくなる危険があり廃止
    Expect-CT証明書の透明性（CT：発行された証明書をすべて公開ログに記録する仕組み）が必須になったため不要
    X-Powered-By・Server のバージョンExpress・PHP/8.1.2 などを教えると、攻撃者が既知の脆弱性を探しやすくなる（→ セキュリティの設定ミス）
    ✕ 危険：古いヘッダとバージョン情報が残っている 
    HTTP/1.1 200 OK
Server: nginx/1.18.0
X-Powered-By: PHP/8.1.2
X-XSS-Protection: 1; mode=block
    ○ 安全：バージョンを隠し、XSS フィルタは無効化 
    HTTP/1.1 200 OK
Server: nginx
X-XSS-Protection: 0
Content-Security-Policy: default-src 'self'

    10.設定例

    ここでは Express・Next.js・nginx の 3 通りを示します。71 では helmet を既定値のまま使う最小例を紹介しています（→ 安全でない設計・設定ミス・古い部品）。ここでは値を指定する例です。

    10.1 Express（helmet）

    helmet は、Express（Node.js の Web フレームワーク）向けのミドルウェア（リクエスト処理の途中に差し込む部品）で、主要なセキュリティヘッダをまとめて付けます。

    JavaScript 
    import express from 'express';
import helmet from 'helmet';

const app = express();

// helmet は主要なセキュリティヘッダをまとめて付け、X-Powered-By を消す
app.use(
  helmet({
    contentSecurityPolicy: {
      directives: {
        defaultSrc: ["'self'"],
        frameAncestors: ["'none'"],
      },
    },
    strictTransportSecurity: { maxAge: 63072000, includeSubDomains: true },
    referrerPolicy: { policy: 'strict-origin-when-cross-origin' },
  })
);

    10.2 Next.js（next.config.js）

    JavaScript 
    const securityHeaders = [
  { key: 'Strict-Transport-Security', value: 'max-age=63072000; includeSubDomains' },
  { key: 'X-Frame-Options', value: 'DENY' },
  { key: 'X-Content-Type-Options', value: 'nosniff' },
  { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
  { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
];

module.exports = {
  poweredByHeader: false, // X-Powered-By: Next.js を消す
  async headers() {
    return [{ source: '/(.*)', headers: securityHeaders }];
  },
};

    10.3 nginx

    nginx 
    server_tokens off;  # Server ヘッダからバージョンを消す

add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
add_header X-Frame-Options "DENY" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    • always を付けないと、エラー応答（404・500 など）にヘッダが付きません。
    • nginx の add_header は、location ブロックの中に 1 つでも書くと 外側の設定を引き継がなくなる ので注意。
    ✕ 危険：/static/ ではセキュリティヘッダが全部消える 
    server {
    add_header X-Frame-Options "DENY" always;
    add_header X-Content-Type-Options "nosniff" always;

    location /static/ {
        add_header Cache-Control "public, max-age=86400";  # これだけになる
    }
}
    ○ 安全：共通のヘッダをファイルにまとめ、location でも読み込む 
    # security_headers.conf に add_header 行をまとめておく
server {
    include security_headers.conf;

    location /static/ {
        include security_headers.conf;
        add_header Cache-Control "public, max-age=86400";
    }
}

    11.よくある落とし穴

    落とし穴内容
    一部のページにしか付いていないエラーページ・静的ファイル・API にも付ける。リバースプロキシ（サーバーの手前で通信を受ける中継サーバー）や CDN でまとめて付けると漏れにくい
    二重に付いているアプリとプロキシの両方で付け、値が食い違う。どちらで付けるか決める
    HSTS をいきなり長くするHTTP が必要なサブドメインがあると戻せない。短い値から始める
    ヘッダで脆弱性が直ったと思うヘッダは被害を減らす保険。XSS ならエスケープ、CSRF ならトークンが本質的対策

    よくある誤解：「helmet を入れたから XSS は大丈夫」

    ヘッダは、脆弱性があっても 悪用しにくくする ものです。出力のエスケープ漏れがあれば、XSS の穴そのものは残っています。根本対策（エスケープ・トークンなど）とヘッダの両方をそろえて、初めて多層防御になります。

    12.確認方法

    • ブラウザの開発者ツール → Network → レスポンスヘッダを見る
    • curl -I https://example.com でヘッダだけ表示する
    • Mozilla HTTP Observatory や securityheaders.com で採点する
    ターミナル 
    $ curl -I https://example.com
HTTP/2 200
strict-transport-security: max-age=63072000; includeSubDomains
x-frame-options: DENY
x-content-type-options: nosniff
referrer-policy: strict-origin-when-cross-origin

    トップページだけでなく、存在しない URL（404）や静的ファイル にも同じコマンドを打って、ヘッダが付いているかを確かめると、落とし穴の「一部のページにしか付いていない」を見つけられます。

    13.対策の優先順位

    1. HTTPS 化 + HSTS（全サイト必須）
    2. X-Content-Type-Options: nosniff と正しい Content-Type（全サイト必須）
    3. クリックジャッキング対策（X-Frame-Options + frame-ancestors）
    4. CSP（まずは Report-Only で始める → CSP）
    5. Referrer-Policy・Permissions-Policy・COOP/CORP
    6. X-Powered-By などバージョン情報の削除

    14.まとめ

    このページの要点

    • セキュリティヘッダは ブラウザへの指示書。脆弱性は直さないが、起きたときの被害を小さくする多層防御の層
    • HSTS で HTTP への格下げを防ぐ。短い max-age から始め、サブドメインを確認してから伸ばす
    • X-Frame-Options + frame-ancestors でクリックジャッキングを防ぐ。CSRF トークンでは防げない
    • nosniff は正しい Content-Type とセット。Referrer-Policy は保険で、根本は URL に秘密を入れないこと
    • Permissions-Policy・COOP/CORP/COEP でブラウザ機能やウィンドウ・リソースの関係を絞る
    • X-XSS-Protection・HPKP・Expect-CT は使わない。バージョン情報は消す
    • 全ページ（エラー・静的ファイル・API）に付いているかを curl -I や採点サイトで確認する

    15.理解度チェック

    Q1. HSTS を設定していても、守れない「最初の 1 回」を減らすにはどうしますか？

    preload を付けて、ブラウザに組み込まれた HSTS プリロードリスト に登録します。リストに載ったドメインは、一度も訪れたことがなくても最初から HTTPS で接続されます。ただし外すのに数か月かかるため、短い max-age で試してからにします。

    Q2. クリックジャッキングは、なぜ CSRF トークンで防げないのですか？

    利用者本人が、本物のサイトの本物の画面（透明な iframe）でボタンを押しているからです。フォームには正しい CSRF トークンが入ったまま送信されます。防ぐには X-Frame-Options や CSP の frame-ancestors で埋め込みそのものを禁止します。

    Q3. X-Frame-Options と frame-ancestors の両方を付けたとき、ブラウザはどちらを使いますか？ また、なぜ両方付けるのですか？

    CSP の frame-ancestors を 優先 します。frame-ancestors に対応していない古いブラウザでも守れるよう、X-Frame-Options も併せて付けるのが一般的です。

    Q4. nginx で、location ブロックに Cache-Control の add_header だけを書いたら何が起きますか？

    その location では 外側（server）の add_header が引き継がれなくなり、セキュリティヘッダがすべて消えます。共通ヘッダを include ファイルにまとめて location でも読み込むなどして対処します。

    Q5. X-XSS-Protection を「1; mode=block」にすべきですか？

    いいえ。 古いブラウザの XSS フィルタは、それ自体が情報漏えいの原因になったため廃止されました。付けるなら 0（無効化）にし、XSS 対策はエスケープと CSP で行います。

    Q6. nosniff を付けたら、急に JavaScript が動かなくなりました。何が考えられますか？

    JavaScript ファイルを text/plain など 間違った Content-Type で返している可能性があります。nosniff では JavaScript の MIME タイプでないスクリプトは実行されません。サーバー側で正しい Content-Type を付けるのが前提です。
