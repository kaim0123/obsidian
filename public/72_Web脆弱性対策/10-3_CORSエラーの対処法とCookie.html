    10 ブラウザのセキュリティモデル

    CORSエラーの対処法とCookie

    開発中に必ず一度は出会う「blocked by CORS policy」。このページでは、よくあるエラーメッセージの読み方と原因、Express・Next.js・Flask・FastAPI での直し方、開発環境でのプロキシ、そして Cookie などの認証情報を付けて CORS を使うときのルールと落とし穴を解説します。「とりあえず全部許可」で直すと脆弱性になる理由も、危険な例と安全な例で比べます。

    もとにしたノート：10_ブラウザのセキュリティモデル/05_CORSエラーの対処法・08_CORSとCookie（ねる前エンジニアリング）・02_CORS（徳丸本3章）・07_CORS入門（プログラミングチュートリアル）

    ひとことで言うと

    CORSエラーは サーバー側で「許可の札」（レスポンスヘッダ）を正しく返す ことで直します。ただし Cookie を付ける通信では *（全部許可）は使えず、許可するオリジンを具体的に絞る 必要があります。届いた Origin をそのまま返すような「何でも許可」は、それ自体が脆弱性です。

    1.おさらい：CORSエラーとは何か

    CORS（Cross-Origin Resource Sharing／オリジン間リソース共有）の基本の仕組みは CORSの仕組み で解説しました。ここでは対処法に必要な点だけを振り返ります。

    • オリジン とは「スキーム（https など）＋ドメイン＋ポート番号」の組み合わせです。どれか1つでも違えば別オリジンです（→ 受動的攻撃と同一オリジンポリシー）。
    • ブラウザが止めているのは送信そのものではなく、別オリジンのレスポンスを JavaScript が「読むこと」 です。
    • CORS は、サーバーが Access-Control-Allow-Origin などのヘッダで出す 「許可の札」 を見て、ブラウザが例外的に読ませる仕組みです。
    • 条件によっては、本番のリクエストの前に プリフライト（OPTIONS メソッドによる事前の問い合わせ）が送られます。

    エラーを見たら最初に思い出すこと

    CORSエラーのとき、サーバーは正常にレスポンスを返していることが多い です。ブラウザが JavaScript への受け渡しをブロックしているだけなので、curl や Postman で同じ URL を叩くと普通に成功します。だから直す場所は フロントエンドのコードではなく、サーバーが返すヘッダ です。

    2.よくあるCORSエラーと原因

    ブラウザの開発者ツールのコンソールに出るメッセージには、原因がそのまま書かれています。まずは英文のキーワードを読み取りましょう。

    2.1 エラーメッセージ1：No 'Access-Control-Allow-Origin' header

    Access to fetch at 'https://api.example.com/users' from origin 'https://myapp.com'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present
on the requested resource.

    原因：サーバーが Access-Control-Allow-Origin ヘッダを返していない。
    解決策：サーバー側で CORS ヘッダを設定する（→ 3. サーバー側での対処法）。

    2.2 エラーメッセージ2：Credentials flag is true

    Access to fetch at 'https://api.example.com/users' from origin 'https://myapp.com'
has been blocked by CORS policy: The value of the 'Access-Control-Allow-Origin' header
in the response must not be the wildcard '*' when the request's credentials mode is 'include'.

    原因：credentials: 'include'（Cookie などを付けて送る設定）を使っているのに、Access-Control-Allow-Origin が * になっている。
    解決策：具体的なオリジンを指定する（→ 5. 認証情報を含むリクエスト）。

    2.3 エラーメッセージ3：Method not allowed

    Access to fetch at 'https://api.example.com/users' from origin 'https://myapp.com'
has been blocked by CORS policy: Method PUT is not allowed by Access-Control-Allow-Methods.

    原因：使おうとしている HTTP メソッドが許可されていない。
    解決策：Access-Control-Allow-Methods に該当メソッドを追加する。

    同じ仲間に、Request header field Authorization is not allowed by Access-Control-Allow-Headers. というエラーもあります。この場合は Access-Control-Allow-Headers に Authorization を追加します（各ヘッダの意味は CORSの仕組み を参照）。

    2.4 メッセージから直し方を引く

    メッセージのキーワード原因直すところ（サーバー側）
    No 'Access-Control-Allow-Origin' header許可ヘッダを返していないAccess-Control-Allow-Origin を返す
    must not be the wildcard '*'Cookie 付きなのに *具体的なオリジン＋Access-Control-Allow-Credentials: true
    Method PUT is not allowedメソッドが許可されていないAccess-Control-Allow-Methods に追加
    Request header field … is not allowedリクエストヘッダが許可されていないAccess-Control-Allow-Headers に追加

    3.サーバー側での対処法

    CORS の許可を出すのはサーバーです。言語やフレームワークごとに、よく使う書き方を見ていきます。多くのフレームワークには CORS 用の ミドルウェア（すべてのリクエストの前後に共通処理を差し込む部品）があり、それを使うのが基本です。

    3.1 Node.js（Express）：方法1 cors パッケージを使う（推奨）

    npm install cors
    const express = require('express');
const cors = require('cors');
const app = express();

// 全てのオリジンを許可（開発環境のみ）
app.use(cors());

// 特定のオリジンのみ許可
app.use(cors({
  origin: 'https://myapp.com',
  credentials: true
}));

// 複数のオリジンを許可
app.use(cors({
  origin: ['https://myapp.com', 'https://www.myapp.com'],
  credentials: true
}));

    上の3つは「書き方の選択肢」を並べたもので、実際にはどれか1つを使います。origin に配列を渡すと、cors パッケージがリクエストの Origin ヘッダと照らし合わせ、一致したものだけ を Access-Control-Allow-Origin に入れて返してくれます（このヘッダには値を1つしか書けないため）。

    3.2 Node.js（Express）：方法2 手動でヘッダを設定する

    const express = require('express');
const app = express();

// 全てのリクエストに適用
app.use((req, res, next) => {
  res.header('Access-Control-Allow-Origin', '*');
  res.header('Access-Control-Allow-Methods', 'GET, POST, PUT, DELETE');
  res.header('Access-Control-Allow-Headers', 'Content-Type, Authorization');
  next();
});

// プリフライトリクエストの処理
app.options('*', (req, res) => {
  res.header('Access-Control-Allow-Origin', '*');
  res.header('Access-Control-Allow-Methods', 'GET, POST, PUT, DELETE');
  res.header('Access-Control-Allow-Headers', 'Content-Type, Authorization');
  res.sendStatus(204);
});

    手動で書く場合は、プリフライト（OPTIONS）への応答 と 本番リクエストへの応答 の両方にヘッダが必要な点に注意します。204 は「成功したが本文はない」というステータスコードです。

    補足：Express 5 では app.options('*', …) がエラーになる

    上のコードは Express 4 の書き方です。Express 5 ではルートのパス指定のルールが変わり、'*' 単体は使えません（'/{*splat}' のような名前付きワイルドカードを使います）。迷ったら cors パッケージに任せるのが確実です。

    3.3 Next.js（API Routes）

    // pages/api/users.js または app/api/users/route.js
export default function handler(req, res) {
  // CORSヘッダーを設定
  res.setHeader('Access-Control-Allow-Origin', 'https://myapp.com');
  res.setHeader('Access-Control-Allow-Methods', 'GET, POST, PUT, DELETE');
  res.setHeader('Access-Control-Allow-Headers', 'Content-Type, Authorization');

  // プリフライトリクエストの処理
  if (req.method === 'OPTIONS') {
    res.status(200).end();
    return;
  }

  // 実際の処理
  if (req.method === 'GET') {
    res.status(200).json({ message: 'Success' });
  }
}

    注意：この書き方は pages/api（Pages Router）専用です

    handler(req, res) の形は pages/api/ 用です。app/api/…/route.js（App Router）では、メソッド名の関数を export し、Response を返す書き方になります。

    // app/api/users/route.js（App Router の場合）
const corsHeaders = {
  'Access-Control-Allow-Origin': 'https://myapp.com',
  'Access-Control-Allow-Methods': 'GET, POST, PUT, DELETE',
  'Access-Control-Allow-Headers': 'Content-Type, Authorization',
};

export function OPTIONS() {
  return new Response(null, { status: 204, headers: corsHeaders });
}

export function GET() {
  return Response.json({ message: 'Success' }, { headers: corsHeaders });
}

    4.クライアント側での対処法（開発環境）

    本来の解決はサーバー側ですが、開発中に一時的に回避する方法もあります。

    方法1：ブラウザの拡張機能（非推奨）

    開発中のみ使う場合に限り、CORS Unblock などの拡張機能でブラウザのチェックを外す方法があります。

    本番環境では使いません。 利用者のブラウザには入っていないので、根本的な解決にはなりません。

    方法2：プロキシサーバーを使う

    プロキシ（間に立って通信を中継するサーバー）を使い、ブラウザからは同じオリジンにリクエストしているように見せます。

    Next.js の場合、next.config.js の rewrites でプロキシを設定できます。

    // next.config.js
module.exports = {
  async rewrites() {
    return [
      {
        source: '/api/:path*',
        destination: 'https://api.example.com/:path*',
      },
    ];
  },
};

    これにより、ブラウザは /api/…（自分と同じオリジン）にリクエストし、Next.js のサーバーが裏で https://api.example.com に中継します。同じオリジンからのリクエストとして扱われる ため、CORS は発生しません。CORS はブラウザだけのルールで、サーバー同士の通信には関係しないからです。

    5.認証情報（Cookie）を含むリクエスト

    認証情報（Credentials） とは、Cookie、Authorization ヘッダ、TLS クライアント証明書 など、リクエストに付いていく認証用のデータのことです。ログイン状態を Cookie で保っている API を別オリジンから呼ぶときに、この設定が必要になります。

    5.1 デフォルトの動作

    クロスオリジン（別オリジンへ）の fetch() では、セキュリティのため Cookie は自動送信されません。

    // デフォルト: credentials = 'same-origin'
fetch('https://api.example.com/profile');
// → api.example.com の Cookie は送られない

    5.2 認証情報を含める設定：クライアントとサーバーの両方が必要

    クライアント側：fetch に credentials を指定します。

    fetch('https://api.example.com/users', {
  credentials: 'include'  // クッキーを含める
});

// または
fetch('https://api.example.com/users', {
  credentials: 'same-origin'  // 同じオリジンの場合のみ
});

    サーバー側：次の2つのヘッダを返します。

    Access-Control-Allow-Origin: https://myapp.com   ← * は使えない
Access-Control-Allow-Credentials: true
    credentials の値動作
    omit認証情報を送らない
    same-origin同一オリジンのときだけ送る（デフォルト）
    includeクロスオリジンでも送る

    5.3 重要な制約

    制約理由
    Allow-Origin: * と Credentials: true は 併用不可どのサイトからでも Cookie 付きでアクセスできてしまう
    具体的なオリジンを指定する必要がある許可する相手を限定するため
    SameSite Cookie 属性も影響するクロスサイトでの Cookie 送信を制御する（→ 6. Cookie に付ける印）

    ブラウザ側でこの組み合わせを禁止しているのは、もし許してしまうと、利用者が罠サイトを開いただけで ログイン中の情報（プロフィール、メール、残高など）を罠サイトの JavaScript に読まれてしまう からです。

    5.4 設定例（Express.js ＋ cors パッケージ）

    const cors = require('cors');

app.use(cors({
  origin: 'https://myapp.com',   // 具体的なオリジン（* 不可）
  credentials: true               // 認証情報を許可
}));

// クライアント
fetch('https://api.myapp.com/profile', {
  credentials: 'include'
});

    credentials: true を指定すると、レスポンスに Access-Control-Allow-Credentials: true が付きます。開発者ツールの Network タブで、実際に付いているか確認できます。

    6.Cookie はどう付いていくのか：HttpOnly・Secure・SameSite

    Cookie は、ブラウザが「このドメイン宛てのリクエストにはこの Cookie を付ける」と覚えていて、条件が合えば 自動で付けて送る 小さなデータです。ログイン状態を保つセッションID などがよく入っています。サーバーは Cookie を発行するとき、扱い方を決める 印（属性） を付けられます。

    属性意味守れるもの
    HttpOnlyJavaScript（document.cookie）から読めなくするXSS で Cookie を盗まれにくくする
    SecureHTTPS の通信でだけ送る盗聴で Cookie を盗まれない
    SameSite他サイトから始まったリクエストに Cookie を付けるかを決める（Strict / Lax / None）勝手な送信（罠サイトからのリクエストにログイン Cookie が付くこと）を止める

    CORS が止めるのは「読むこと」でした。これに対して SameSite は、そもそも Cookie を付けて送ること を止める仕組みで、守っている場所が違います。属性の細かい使い分けは 74_セッション管理 で、勝手な送信を悪用する攻撃（CSRF）は CSRF のページで扱います。

    6.1 例：画面と API を別のオリジンに分けたとき

    「オリジン」と「サイト」は範囲が違う点に注意が必要です。サイト は、おおまかに「スキーム＋登録可能なドメイン（myapp.com の部分）」の単位で、サブドメインやポートの違いは同じサイトとみなされます。

    構成オリジンサイト必要な設定
    画面 https://myapp.com
    API https://api.myapp.com    		別（CORS が必要）同じCORS の credentials 設定。SameSite=Lax の Cookie も送られる
    画面 https://myapp.com
    API https://api.other.com    		別（CORS が必要）別CORS の credentials 設定に加え、Cookie を SameSite=None; Secure にする必要がある。さらにブラウザの「サードパーティ Cookie 制限」で送られない場合もある

    設計のヒント

    画面と API は、できれば 同じサイト（サブドメイン違い） にそろえるか、プロキシ で同じオリジンに見せると、Cookie まわりのトラブルが減ります。

    7.環境別の設定

    開発環境と本番環境では、許可したいオリジンが違います。設定を環境ごとに切り替えましょう。

    7.1 開発環境

    // 開発環境では全てのオリジンを許可
const corsOptions = {
  origin: process.env.NODE_ENV === 'development' ? '*' : 'https://myapp.com',
  credentials: process.env.NODE_ENV === 'production'
};

    開発環境で credentials を false にしているのは、* と認証情報の併用が禁止されているからです。そのため、この設定では開発環境で Cookie を使ったログインは試せません。Cookie 付きで試したいときは、開発環境でも http://localhost:3000 のように具体的なオリジンを指定します。

    7.2 本番環境

    // 本番環境では特定のオリジンのみ許可
const corsOptions = {
  origin: ['https://myapp.com', 'https://www.myapp.com'],
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization']
};

    8.トラブルシューティング

    8.1 問題1：プリフライトリクエストが失敗する

    1. OPTIONS メソッドのハンドラー（処理する関数）が正しく設定されているか
    2. Access-Control-Allow-Methods に使うメソッドが含まれているか
    3. Access-Control-Allow-Headers に使うヘッダが含まれているか

    8.2 問題2：credentials が送信されない

    1. クライアント側で credentials: 'include' を指定しているか
    2. サーバー側で Access-Control-Allow-Credentials: true を返しているか
    3. Access-Control-Allow-Origin が * ではなく、具体的なオリジンになっているか

    補足：「送られない」のか「読めない」のかを分ける

    2 と 3 は、厳密には「Cookie は送られたが、レスポンスを読ませてもらえない」原因です（プリフライトが必要なリクエストでは、プリフライトの応答にも 2 が必要です）。Network タブで リクエストに Cookie ヘッダが付いていない なら、Cookie 側の SameSite・Secure 属性や、ブラウザのサードパーティ Cookie 制限を疑います（→ 6.1）。

    8.3 問題3：開発環境では動くが本番環境で動かない

    1. 環境変数の設定が正しいか
    2. 本番環境のオリジンが正しく設定されているか
    3. HTTPS / HTTP の違いがないか（スキームが違えば別オリジン）

    8.4 ハマりやすい細かい点

    症状原因と対処
    オリジンを書いたのに通らないオリジンの末尾に / を付けている（http://127.0.0.1:5500/）。オリジンにはパスが含まれないので、http://127.0.0.1:5500 と書く
    localhost で許可したのに通らないブラウザで開いている URL が 127.0.0.1 になっている。localhost と 127.0.0.1 は文字列が違うので 別オリジン
    フロントとバックエンドを同じ PC で動かしているのにエラー例：フロント localhost:5500、API localhost:5000。ポートが違えば別オリジン なので CORS 設定が必要
    プリフライトは成功するのに最後にエラー本番リクエスト（PUT など）のレスポンスに Access-Control-Allow-Origin が付いていない

    調べ方のコツ

    エラーの調査には、開発者ツールの Network タブ（リクエスト・レスポンスのヘッダを1件ずつ確認できる）を使います。Access-Control-Allow-Methods などが実際に何を返しているかが見えます。Cookie が保存されているかは Application タブ で確認するのがおすすめです。

    9.セキュリティのベストプラクティス

    CORS エラーを「とにかく消す」ために許可を広げすぎると、それ自体が 設定ミスの脆弱性 になります（→ 安全でない設計・設定ミス・古い部品）。

    設定リスク
    *（ワイルドカード）どのサイトからでも API を呼んで、レスポンスを読める
    オリジン検証なし悪意あるサイトも許可してしまう
    推奨許可するオリジンを明示的にリストアップする

    9.1 最小限のオリジンを許可する

    危険な例 
    // 悪い例
app.use(cors({
  origin: '*'  // 全て許可（本番環境では非推奨）
}));
    安全な例 
    // 良い例
app.use(cors({
  origin: ['https://myapp.com', 'https://www.myapp.com']
}));

    9.2 届いた Origin をそのまま返さない

    複数のオリジンを許可したいとき、Access-Control-Allow-Origin を 動的に設定 することがあります。このとき Origin ヘッダの検証 を必ず行います。リクエストの Origin を反射的にそのまま返すと、* と同じどころか、* では禁止されている Cookie 付きの読み取りまで あらゆるオリジンに許可 してしまいます（任意オリジン許可の脆弱性）。

    危険な例 
    // ❌ 危険：任意の Origin をそのまま返す
res.setHeader('Access-Control-Allow-Origin', req.headers.origin);
res.setHeader('Access-Control-Allow-Credentials', 'true');
    安全な例 
    // ✅ 許可リストで検証
if (allowedOrigins.includes(req.headers.origin)) {
  res.setHeader('Access-Control-Allow-Origin', req.headers.origin);
  res.setHeader('Access-Control-Allow-Credentials', 'true');
}

    認証情報を含む CORS は、必要最小限のオリジン だけに許可しましょう。また、検証は includes のような 完全一致 で行います。「myapp.com を含むか」のような部分一致だと、myapp.com.evil.example のようなドメインを通してしまいます。

    9.3 必要最小限のメソッドとヘッダを許可する

    危険な例 
    // 悪い例
app.use(cors({
  methods: ['*'],
  allowedHeaders: ['*']
}));
    安全な例 
    // 良い例
app.use(cors({
  methods: ['GET', 'POST'],        // 実際に使うメソッドのみ
  allowedHeaders: ['Content-Type'] // 実際に使うヘッダのみ
}));

    ノートの記述からの修正：オプション名

    もとのノートでは allowMethods / allowHeaders と書かれていましたが、Express の cors パッケージでの正しい名前は methods / allowedHeaders です（allowMethods / allowHeaders は Hono など別のフレームワークの名前）。cors パッケージは知らないオプションを黙って無視するため、名前を間違えると「絞ったつもりで既定値のまま」になります。

    9.4 環境変数で管理する

    許可するオリジンをコードに直接書かず、環境変数（サーバーの起動時に外から渡す設定値）で管理すると、環境ごとの切り替えや追加が安全にできます。

    const allowedOrigins = process.env.ALLOWED_ORIGINS?.split(',') || ['http://localhost:3000'];

app.use(cors({
  origin: allowedOrigins
}));

    たとえば本番サーバーで ALLOWED_ORIGINS=https://myapp.com,https://www.myapp.com と設定します。未設定のときは開発用の http://localhost:3000 だけが許可されるので、設定を忘れても全開放にはなりません。

    9.5 AI にコードを書かせたときに見るところ

    AI が生成したサーバーコードは、エラーを消すために CORS を広く開けていることがあります。次の点を確認しましょう。

    • origin: '*' や cors()（引数なし）が本番用のコードに残っていないか
    • req.headers.origin を検証せずにそのまま返していないか
    • credentials: true が本当に必要か。必要なら許可オリジンが具体的に絞られているか
    • Cookie に HttpOnly・Secure・SameSite が付いているか。SameSite=None にしているなら、それが必要な構成か

    10.まとめ

    このページの要点

    • サーバー側での対処：CORS ミドルウェアを使う（推奨）。必要に応じて手動でヘッダを設定し、プリフライト（OPTIONS）も処理する
    • クライアント側での対処：開発環境ではプロキシを使う。credentials を含む場合は適切に設定する
    • エラーメッセージのキーワード（No Allow-Origin／wildcard '*'／Method／Request header）で直すヘッダが決まる
    • 認証情報付きは credentials: 'include' ＋ Allow-Credentials: true ＋ 具体的なオリジン。* とは併用できない
    • Cookie が送られるかは CORS ではなく Cookie の属性（SameSite・Secure） が決める
    • セキュリティ：本番環境では具体的なオリジンのみを許可し、Origin の反射は許可リストで検証する。メソッドとヘッダも必要最小限にし、設定は環境変数で管理する

    11.理解度チェック

    Q1. CORSエラーが出たのに、curl で同じ API を叩くと成功しました。どこを直すべきですか？

    サーバーが返すレスポンスヘッダ です。CORS はブラウザが行うチェックなので、curl では起きません。サーバーは正常に応答しており、ブラウザが JavaScript への受け渡しを止めているだけなので、Access-Control-Allow-Origin などの許可ヘッダを返すように直します。

    Q2. 「must not be the wildcard '*' when the request's credentials mode is 'include'」と出ました。原因と直し方は？

    Cookie を付ける設定（credentials: 'include'）なのに、サーバーが Access-Control-Allow-Origin: * を返しているのが原因です。https://myapp.com のような 具体的なオリジン を返し、あわせて Access-Control-Allow-Credentials: true を返します。

    Q3. 複数オリジンを許可するために req.headers.origin をそのまま Allow-Origin に入れ、Credentials も true にしました。何が問題ですか？

    どんなオリジンから来ても許可が返るため、罠サイトからも Cookie 付きでリクエストしてレスポンスを読める ようになります（任意オリジン許可の脆弱性）。許可リストを用意し、完全一致で検証したときだけ Origin を返すようにします。

    Q4. 開発中、cors({ origin: 'http://localhost:5500' }) と設定したのに、http://127.0.0.1:5500 で開いた画面からはエラーになります。なぜですか？

    localhost と 127.0.0.1 は同じ PC を指していても、文字列として違うので 別のオリジン として扱われるからです。実際に開いている URL に合わせて許可オリジンを書きます（末尾に / も付けません）。

    Q5. Next.js の rewrites でプロキシを設定すると、なぜ CORS エラーが起きなくなるのですか？

    ブラウザから見ると自分と 同じオリジン（/api/…）にリクエストしているだけになり、別オリジンへの中継は Next.js のサーバーが行うからです。CORS はブラウザのルールで、サーバー同士の通信には関係しません。

    Q6. 画面 https://myapp.com と API https://api.other.com の構成で、CORS の設定は正しいのに Cookie がリクエストに付きません。何を疑いますか？

    2つは 別サイト なので、Cookie の SameSite 属性が Lax（多くのブラウザの既定）や Strict だと送られません。SameSite=None; Secure が必要で、さらにブラウザのサードパーティ Cookie 制限で止められる場合もあります。同じサイトにそろえるか、プロキシで同じオリジンに見せる構成も検討します。
