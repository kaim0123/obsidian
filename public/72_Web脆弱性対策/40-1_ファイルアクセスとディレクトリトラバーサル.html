    40 ファイル・データ処理

    ファイルアクセスとディレクトリトラバーサル

    Webアプリは、画像・PDF・設定ファイルなど サーバー上のファイル を読み書きすることがあります。このページでは徳丸本（『安全なWebアプリケーションの作り方』）第13章をもとに、ファイルアクセスまわりで起きやすい2つの脆弱性 ── ../ でパスを操作される ディレクトリ・トラバーサル と、秘密のファイルを公開場所に置いてしまう 意図しないファイル公開 ── とその対策を解説します。

    もとにしたノート：40_ファイル・データ処理/01_ファイルアクセスにまつわる問題（徳丸本13章）

    ひとことで言うと

    「ユーザーにパスやファイル名を自由に指定させない」「秘密ファイルは公開ディレクトリに置かない」 のが、この章の要点です。どうしてもファイルを渡すときは、「誰の・どのファイルか」をサーバー側で決めて検証します。

    ここでいう パス とは、ファイルの場所を表す文字列（例：/var/www/uploads/photo.jpg）のことです。読み込んだファイルを プログラムとして実行 してしまう似た問題は ファイルインクルード（徳丸本第16章）で扱っています。両者の違いは ファイルインクルード「ディレクトリ・トラバーサルとの違い」 を参照してください。

    1.ファイルアクセスの問題の概要

    ファイルアクセス機能には、主に次の問題があります。

    問題概要
    ディレクトリ・トラバーサル外部入力でパスを操作され、本来見えないファイルを読まれる・改ざんされる
    意図しないファイル公開秘密にすべきファイルが公開ディレクトリに置かれ、URL を知られると誰でも見られる

    外部入力 とは、URL のパラメータやフォームの入力値など、利用者（攻撃者を含む）がアプリに送ってくる値のことです。ディレクトリ はフォルダのことです。

    1.1 日常生活での例え

    正常なファイルアクセス

    自分のプロフィール画像だけが表示される。

    攻撃された場合

    パスワード一覧や設定ファイルなど、サーバー内の秘密ファイルまで見られてしまう。

    1.2 なぜ危険か

    Webアプリは、サーバー上のファイルを 読み書きする権限 を持っています。その権限が悪用されると、次のような被害が出ます。

    ・設定ファイルやパスワード情報の漏洩
・ソースコードの漏洩
・ログや個人情報ファイルの閲覧
・ファイルの改ざん・削除によるサービス妨害

    サービス妨害 とは、サイトを正常に使えない状態にして、利用者がサービスを受けられないようにすることです。

    2.ディレクトリ・トラバーサルとは

    ディレクトリ・トラバーサル（Directory Traversal） とは、外部から渡されたファイル名やパスをそのまま使い、本来アクセスしてはいけないディレクトリやファイル にたどり着いてしまう脆弱性です。パス・トラバーサル（Path Traversal）とも呼ばれます。

    「トラバーサル」は「横断する・渡り歩く」という意味です。ディレクトリの境界を越えて、別の場所のファイルへアクセスされるイメージです。

    2.1 日常生活での例え

    正常

    「自分の部屋の引き出し」だけ開ける。

    攻撃

    「../」で廊下に出て、隣の部屋や金庫まで開けてしまう。

    2.2 何ができるか（被害）

    被害説明
    Webサーバー内のファイルの閲覧設定ファイル、パスワード、ソースコード、ログなどを読まれる
    Webサーバー内のファイルの改ざん・削除書き込み権限がある場合、内容の書き換えや削除ができる

    閲覧だけでも十分危険です。書き込みまでできると、サイトの改ざんやサービス停止につながります。

    2.3 攻撃のイメージ

    たとえば、画像を表示する機能が次のような URL だとします。

    https://example.com/download.php?file=photo.jpg

    アプリが file パラメータ（URL の ?file= の後ろに付く値）をそのままパスに連結している場合は、次のようになります。

    【正常な入力】
file=photo.jpg
→ /var/www/uploads/photo.jpg を読む（想定どおり）

【攻撃者の入力】
file=../../etc/passwd
→ /var/www/uploads/../../etc/passwd
→ /etc/passwd を読む（想定外のファイル）

    ../ は「ひとつ上のディレクトリへ移動する」という意味です。これを繰り返すと、公開用フォルダの外へ出ていけます。

    /var/www/uploads/photo.jpg     ← 本来の場所
/var/www/uploads/../           ← ひとつ上（/var/www/）
/var/www/uploads/../../        ← さらに上（/var/）
/var/www/uploads/../../etc/passwd  ← OS のユーザー一覧など

    /etc/passwd は、Linux などの OS でユーザーアカウントの一覧が書かれているファイルです。攻撃が成功したかを確かめる「定番の標的」としてよく使われます。

    補足：../ の回数について

    ノートの例では ../../etc/passwd で /etc/passwd に届くとしていますが、すぐ上の一覧のとおり /var/www/uploads/ から ../ を2回さかのぼると /var/ なので、正確には /var/etc/passwd になります。/etc/passwd に届くには ../../../etc/passwd（3回）が必要です。実際の攻撃者は ../ を多めに重ねます（ルート / より上には行けないので、多すぎても / で止まります）。「../ の数を調整すれば、想定フォルダの外のどこでも狙える」という点は同じです。

    Windows 環境では ..\..\windows\win.ini のような形でも同様の問題が起きます（Windows ではディレクトリの区切りに \ も使えるためです）。絶対パス（ルートから書いた完全なパス。/etc/passwd や C:\...）を直接指定できる場合もあります。

    2.4 攻撃の流れ

    1. 攻撃者が「ファイル名をパラメータで受け取る」機能を見つける
    2. file=../../etc/passwd のようにパスを操作した値を送る
    3. アプリが入力値をそのままファイルパスに使う
    4. アクセス可否のチェックがないため、秘密ファイルが読まれる
    5. 設定情報・パスワード・ソースコードなどが漏洩する

    2.5 脆弱性が生まれる原因

    次の条件がそろうと、ディレクトリ・トラバーサルが起きやすくなります。

    原因説明
    ファイル名を外部から指定できるURL やフォームのパラメータでファイル名を受け取っている
    絶対パスや相対パスで別ディレクトリを指定できる../ や /etc/passwd のような入力がそのまま通る
    組み立てたファイル名のアクセス可否をチェックしていない「許可されたフォルダ内か」を確認していない

    相対パス とは、今いる場所を基準に書いたパス（../config.php など）のことです。

    特に危険なのは、「ユーザーが指定した名前のファイルを開く」 という仕様そのものです。ダウンロード機能、画像表示、テンプレート読み込みなどでよく見られます。

    2.6 脆弱なコードの例

    ✕ 危険：外部入力をそのままパスに使っている

    // ❌ 危険: 外部入力をそのままパスに使っている
$file = $_GET['file'];
$path = '/var/www/uploads/' . $file;
readfile($path);

    $_GET['file'] は URL の file パラメータの値、readfile() はファイルの中身をそのままレスポンスとして出力する PHP の関数です。

    リクエスト例:
  /download.php?file=../../config/database.php

結果:
  /var/www/uploads/../../config/database.php
  → /var/www/config/database.php が読まれる

    補足：パスの解決結果について

    ここも ../ の回数がずれています。/var/www/uploads/ から2回さかのぼると /var/ なので、正確には /var/config/database.php が読まれます。/var/www/config/database.php を狙うなら file=../config/database.php（1回）です。

    3.ディレクトリ・トラバーサルの対策

    対策の基本は 「外部から自由にパスを指定させない」 ことです。

    3.1 外部からファイル名を指定できる仕様を避ける

    最も安全なのは、ユーザーにファイル名やパスを直接渡させない ことです。

    ✕ 悪い例

    /download.php?file=report.pdf
    → ファイル名そのものを外部から受け取る

    ○ 良い例

    /download.php?id=123
    → ID だけ受け取り、サーバー側で対応するファイルを決める

    方針説明
    ID で管理するDB に「ID ↔ 実ファイルパス」を持ち、外部には ID だけ渡す
    固定パスを使う読み込むファイルをアプリ側で決め打ちする
    選択肢を限定する「avatar」「banner」など許可したキーだけ受け付ける

    ○ 良い例：ID からサーバー側でパスを決める

    // ✅ 良い例: ID からサーバー側でパスを決める
$id = (int)($_GET['id'] ?? 0);

// DB から「このユーザーがアクセスしてよいファイル」を取得
$stmt = $pdo->prepare('SELECT path FROM files WHERE id = ? AND user_id = ?');
$stmt->execute([$id, $currentUserId]);
$row = $stmt->fetch();

if (!$row) {
    exit('ファイルが見つかりません');
}

readfile($row['path']);

    (int) は値を整数に変換する書き方、?? 0 は値がなければ 0 を使うという意味です。SQL の ? は SQLインジェクション 対策のプレースホルダです。AND user_id = ? で「ログイン中のユーザー自身のファイルか」も同時に確かめている点が大切です。ID を書き換えて他人のファイルを取られる問題（IDOR）は 71 セキュリティ基礎「アクセス制御と認証の失敗」 で扱っています。

    3.2 ファイル名にディレクトリが含まれないようにする

    どうしてもファイル名を受け取る場合は、ディレクトリ区切り文字（/ や \）を除去・拒否 します。

    ○ ディレクトリ部分を取り除き、解決後のパスも確認する

    // ✅ ディレクトリ部分を取り除き、ファイル名だけ残す
$file = $_GET['file'] ?? '';
$basename = basename($file);  // "a/b/c.txt" → "c.txt"

// 許可ディレクトリ配下に限定
$baseDir = '/var/www/uploads/';
$path = $baseDir . $basename;

// 念のため、解決後のパスが許可ディレクトリ内か確認
$realBase = realpath($baseDir);
$realPath = realpath($path);

if ($realPath === false || strpos($realPath, $realBase) !== 0) {
    exit('不正なファイル指定です');
}

readfile($realPath);
    チェック目的
    basename()../ や / を含むパスからファイル名だけ取り出す
    realpath()シンボリックリンクや ../ を解決した実パスを得る
    許可ディレクトリ内か確認解決後のパスが想定フォルダの外に出ていないか見る

    シンボリックリンク とは、別の場所にあるファイルを指す「ショートカット」のようなファイルです。realpath() はそれらをたどった最終的な実際のパスを返し、ファイルが存在しなければ false を返します。strpos($a, $b) !== 0 は「$a が $b で始まっていない」ことを調べています。

    basename() だけでは不十分な場合もあるため、最終パスが許可ディレクトリ内か を必ず確認します。

    補足：前方一致チェックは区切り文字まで含める

    realpath('/var/www/uploads/') の結果は末尾の / が取れた /var/www/uploads になります。そのため strpos($realPath, $realBase) !== 0 だけだと、/var/www/uploads_private/secret.txt のような 名前が同じ文字列で始まる別フォルダ も「許可ディレクトリ内」と判定されてしまいます（basename() と組み合わせたこの例では通常起きませんが、チェック単体としては不完全です）。区切り文字まで含めて比べるのが確実です。

    // ✅ 区切り文字まで含めて前方一致を確認（str_starts_with は PHP 8.0 以降）
if ($realPath === false
    || !str_starts_with($realPath, $realBase . DIRECTORY_SEPARATOR)) {
    exit('不正なファイル指定です');
}

    3.3 ファイル名を英数字に限定する

    ファイル名に使える文字を 英数字（と必要なら _ . -）だけ に限定すると、../ や絶対パスを入れにくくなります。

    ○ 英数字・アンダースコア・ハイフン・ドットのみ許可

    // ✅ 英数字・アンダースコア・ハイフン・ドットのみ許可
$file = $_GET['file'] ?? '';

if (!preg_match('/\A[a-zA-Z0-9._-]+\z/', $file)) {
    exit('不正なファイル名です');
}

// 先頭のドット（隠しファイル）や ".." も拒否
if ($file === '.' || $file === '..' || str_starts_with($file, '.')) {
    exit('不正なファイル名です');
}

$path = '/var/www/uploads/' . $file;

    preg_match('/\A[a-zA-Z0-9._-]+\z/', …) は「先頭（\A）から末尾（\z）まで、許可した文字だけか」を 正規表現（文字列のパターンを表す書き方）で確かめています。/ が許可されていないので、../ を使ったディレクトリ移動はできません。隠しファイル とは、.env や .htaccess のように名前が . で始まり、通常は一覧に表示されないファイルで、設定や秘密情報が入っていることが多いです。str_starts_with() は PHP 8.0 以降で使える関数です。

    方針安全性説明
    外部からファイル名を受け取らない最も安全ID 管理など
    英数字に限定 + 許可ディレクトリ確認安全どうしても名前を受け取る場合
    basename() だけ不十分になりやすい他のチェックと組み合わせる

    4.意図しないファイル公開とは

    意図しないファイル公開 とは、本来インターネットに出してはいけないファイルが、公開ディレクトリに置かれ、URL を知られれば誰でもアクセスできる 状態になる問題です。

    ディレクトリ・トラバーサルのように「パスを操作して侵入する」のではなく、最初から公開場所に置いてしまっている 点が違います。

    4.1 日常生活での例え

    正常

    貴重品は鍵付きの金庫（非公開ディレクトリ）に入れる。

    問題

    貴重品を玄関先（公開ディレクトリ）に置きっぱなしにし、住所（URL）を知った人なら誰でも持っていける。

    4.2 脆弱性が生まれる原因

    次の3つがそろうと、意図しない公開が起きます。

    原因説明
    ファイルが公開ディレクトリに置かれているWeb サーバーが直接配信できる場所にある
    ファイルに対する URL を知る手段がある推測・一覧表示・エラー・検索エンジンなど
    ファイルに対するアクセス制限が掛かっていないログイン不要で誰でも取得できる

    公開ディレクトリとは、たとえば次のような場所です。Web サーバーが URL の起点として公開しているフォルダを ドキュメントルート と呼び、その中に置いたファイルは URL で直接取得できます。

    /var/www/html/          ← ここ以下は URL で直接アクセスされやすい
/var/www/html/uploads/
/var/www/html/files/

/var/www/data/          ← ドキュメントルートの外（非公開にしやすい）

    4.3 URL を知られてしまう典型パターン

    「URL を知る手段」には、次のようなものがあります。

    パターン説明
    ディレクトリ・リスティングが有効フォルダにアクセスするとファイル一覧が表示される
    ファイル名が類推可能日付・ユーザー名・連番など、規則から推測できる
    エラーメッセージや他の脆弱性パス名が画面やログに出てしまう
    検索エンジンに登録される外部サイトからリンクされ、Google 等に載る

    ディレクトリ・リスティング

    Web サーバーの設定で、ディレクトリ一覧表示が有効だと次のように見えます。

    Index of /backup/

  backup_20260101.sql
  backup_20260201.sql
  users.csv

    一覧が出るだけで、攻撃者は欲しいファイルの URL をそのまま知ることができます。こうした「サーバー設定の初期値のまま・設定ミス」の問題全般は 71 セキュリティ基礎「安全でない設計・設定ミス・古い部品」 で扱っています。

    類推可能なファイル名

    ✕ 推測されやすい例

    /files/user_1.pdf
/files/user_2.pdf
/reports/2026-07-04.xlsx
/backup/backup.sql

    ○ 推測しにくい例

    /files/a8f3c2e91b0d4f77.pdf

    （それでも公開ディレクトリに置くのは非推奨）

    連番や日付だと、1件見つかれば前後を 総当たり（考えられる値を片っ端から試すこと）できます。

    エラーメッセージ・他の脆弱性

    Warning: fopen(/var/www/html/secret/config.php): failed to open stream

    このようなメッセージから、秘密ファイルのパスが分かることがあります。ディレクトリ・トラバーサルや XSS など、別の脆弱性と組み合わさるとさらに危険です。

    検索エンジンへの登録

    一時的に置いたバックアップやテスト用ファイルが、外部からリンクされたりクロール（検索エンジンのプログラムがリンクをたどってページを自動収集すること）されたりして、検索結果に出ることがあります。

    site:example.com filetype:sql
site:example.com filetype:env

    このような検索（site: は対象サイトの指定、filetype: はファイルの種類の指定）で、意図せず公開されたファイルが見つかるケースがあります。

    4.4 攻撃の流れ

    1. バックアップや設定ファイルが公開ディレクトリに置かれている
    2. ディレクトリ一覧・推測・エラー・検索エンジンなどで URL が分かる
    3. ブラウザやツールでその URL にアクセスする
    4. 認証なしでファイルの中身が取得される
    5. 個人情報・パスワード・ソースコードなどが漏洩する

    5.意図しないファイル公開の対策

    対策の基本は 「秘密ファイルを公開ディレクトリに置かない」 ことです。

    5.1 アプリケーション設計時に、ファイルの安全な格納場所を決める

    設計の段階で、「公開してよいもの」と「公開してはいけないもの」を分けます。

    公開してよい

    • CSS / JavaScript / ロゴ画像など、誰が見てもよい静的ファイル
    • 公開用の商品画像など

    公開してはいけない

    • 設定ファイル（DB パスワードなど）
    • アップロードされた個人の書類
    • バックアップ、ログ、ソースコード
    • .env、秘密鍵、証明書

    静的ファイル とは、アクセスのたびに内容が変わらない、そのまま配るだけのファイルです。.env は、DB のパスワードや API キーなどの環境ごとの設定を書いておくファイルです。

    ○ 推奨構成のイメージ

    /var/www/
  html/                 ← ドキュメントルート（公開）
    index.php
    assets/css/
    assets/js/
  data/                 ← 非公開（ドキュメントルートの外）
    uploads/
    config/
    logs/
  app/                  ← アプリケーション本体（非公開）
    src/

    公開が必要なファイルだけを、アプリ経由で配信します。

    ○ 非公開ディレクトリのファイルを、権限チェック後にだけ返す

    // ✅ 非公開ディレクトリのファイルを、権限チェック後にだけ返す
session_start();
if (empty($_SESSION['user_id'])) {
    http_response_code(403);
    exit('ログインが必要です');
}

$id = (int)($_GET['id'] ?? 0);
// DB で「このユーザーのファイルか」を確認したうえで配信
// readfile('/var/www/data/uploads/...');

    session_start() はセッション（ログイン状態などをサーバー側で覚えておく仕組み）を使い始める関数、http_response_code(403) は「アクセス禁止」を表すステータスコード 403 を返す関数です。

    方針説明
    非公開ディレクトリに置くドキュメントルートの外に保存する
    アプリ経由で配信する認証・認可を通したあとだけ中身を返す
    直接 URL で取れないようにするWeb サーバーがファイルを直接配信しない

    認証 は「あなたは誰か」を確かめること、認可 は「そのファイルを見てよいか」を判断することです。

    5.2 レンタルサーバーでは非公開ディレクトリが使えるか確認する

    レンタルサーバーでは、公開ディレクトリしか使えないプランもあります。契約前・利用開始時に次を確認します。

    確認項目理由
    非公開ディレクトリがあるか秘密ファイルを置ける場所が必要
    ドキュメントルートを変更できるかpublic/ だけを公開する構成にできるか
    .htaccess 等でアクセス拒否できるかやむを得ず公開配下に置く場合の防御

    .htaccess は、Apache という Web サーバーで、フォルダごとに設定を書けるファイルです。非公開ディレクトリが使えない場合の応急策は次のとおりです。

    secret フォルダに置く .htaccess の例（Apache）

    # .htaccess の例: secret フォルダへの直接アクセスを拒否
# （可能なら、そもそも公開配下に置かない方がよい）
<IfModule mod_authz_core.c>
    Require all denied
</IfModule>

    Require all denied は「このフォルダへのアクセスをすべて拒否する」という Apache 2.4 以降の書き方です。この .htaccess を拒否したいフォルダ（この例では secret フォルダ）の中に置きます。

    これは最後の手段です

    設定ミスやサーバー種別の違いで効かないこともあるため、設計としては非公開ディレクトリを使う方が安全です。たとえば Apache の設定で .htaccess が無効（AllowOverride None）になっていたり、nginx のように .htaccess を読まない Web サーバーだったりすると、このファイルは何の効果もありません。

    5.3 あわせてやっておくとよいこと

    対策説明
    ディレクトリ・リスティングを無効化ファイル一覧が出ないようにする
    推測されにくいファイル名ただし「名前を隠すだけ」では不十分
    エラーメッセージを詳細に出さない本番ではパス名を画面に出さない
    バックアップを公開配下に置かない.sql .zip .bak などを特に注意
    検索エンジン対策だけに頼らないrobots.txt は「見ないで」と頼むだけで、取得自体は防げない

    robots.txt は、検索エンジンのクローラーに「このページは収集しないで」と伝えるファイルです。お願いにすぎないうえ、誰でも読めるので、かえって秘密の場所を教えてしまうこともあります。

    ✕ よくある失敗

    /var/www/html/backup.sql
/var/www/html/.env
/var/www/html/config.php.bak
/var/www/html/uploads/../../ のような相対配置の誤解

    ○ 基本方針

    • 秘密のものはドキュメントルートの外へ
    • 必要な人にだけ、アプリが権限チェックして渡す

    6.まとめ

    問題本質対策の要点
    ディレクトリ・トラバーサル外部入力でパスを操作されるファイル名を外部から指定させない。どうしても受け取るなら英数字限定 + 許可ディレクトリ内か確認
    意図しないファイル公開秘密ファイルが公開場所にある設計時に格納場所を分ける。非公開ディレクトリを使う。アプリ経由で権限チェックして配信する

    ファイルアクセス安全の基本

    1. ユーザーにパスやファイル名を自由に指定させない
    2. 秘密ファイルは公開ディレクトリに置かない
    3. どうしても渡すときは「誰の・どのファイルか」をサーバー側で決めて検証する

    次のページ ファイルアップロード では、利用者からファイルを「受け取る」ときの問題を扱います。保存場所を非公開にする考え方は、ここと共通です。

    7.理解度チェック

    Q1. ディレクトリ・トラバーサルと意図しないファイル公開の違いは何ですか？

    ディレクトリ・トラバーサルは、外部入力でパスを操作され、../ などで本来のフォルダの外のファイルにたどり着かれる問題です。意図しないファイル公開は、パス操作をしなくても、秘密ファイルが最初から公開ディレクトリに置かれている ために URL を知られると誰でも取得できてしまう問題です。

    Q2. /var/www/uploads/ を基準に file=../../etc/passwd を連結すると、実際にはどのパスになりますか？

    ../ 1回で /var/www/、2回で /var/ なので、/var/etc/passwd になります。/etc/passwd に届くには ../ が3回必要です。ただし攻撃者は ../ を多めに重ねるだけで済むため、回数は防御になりません。

    Q3. ディレクトリ・トラバーサルの最も安全な対策は何ですか？

    外部からファイル名を指定できる仕様を避ける ことです。たとえば ?id=123 のように ID だけを受け取り、DB で「ID ↔ 実ファイルパス」を引き、「そのユーザーがアクセスしてよいファイルか」もサーバー側で確認します。

    Q4. basename() と realpath() はそれぞれ何のために使いますか？

    basename() は ../ や / を含むパスからファイル名だけを取り出すため、realpath() は ../ やシンボリックリンクを解決した実際のパスを得るために使います。最後に、解決後のパスが許可ディレクトリ（区切り文字まで含めた前方一致）の中にあるかを必ず確認します。

    Q5. 意図しないファイル公開が起きる3つの条件は何ですか？

    ① ファイルが公開ディレクトリに置かれている、② ファイルの URL を知る手段がある（ディレクトリ・リスティング、類推可能な名前、エラーメッセージ、検索エンジンなど）、③ ファイルにアクセス制限が掛かっていない、の3つです。

    Q6. 「ファイル名をランダムにする」「robots.txt で検索エンジンに載らないようにする」だけで十分ですか？

    不十分です。 名前を隠すだけでは、URL が何らかの方法で漏れれば誰でも取得できます。robots.txt は「見ないで」と頼むだけで、取得自体は防げません。秘密ファイルはドキュメントルートの外に置き、アプリが権限チェックしてから渡すのが基本です。

    Q7. 公開ディレクトリしか使えないレンタルサーバーで、.htaccess によるアクセス拒否はどう位置づけるべきですか？

    最後の手段（応急策） です。設定ミスやサーバー種別の違いで効かないことがあるため、可能なら非公開ディレクトリが使えるプランやドキュメントルートを変更できる環境を選ぶ方が安全です。
