    50 API・JavaScript

    競合状態とキャッシュからの情報漏洩

    Webアプリは、複数の利用者からのリクエストを 同時に 処理します。そのとき、メモリ上の変数・ファイル・データベース・キャッシュなど、複数の処理が共有する資源（共有資産） の扱いを誤ると、他人の情報が混ざったり、データが壊れたりします。このページでは徳丸本（『体系的に学ぶ 安全なWebアプリケーションの作り方』）第18章に沿って、競合状態の脆弱性 と キャッシュからの情報漏洩 の仕組みと対策を解説します。

    もとにしたノート：50_API・JavaScript/01_共有資産やキャッシュに関する問題（徳丸本18章）

    ひとことで言うと

    「リクエスト固有の値は共有しない。共有するならロックで守る」「個人向けページはキャッシュさせない（Cache-Control: no-store とキャッシュサーバーの設定の両方で）」 のが、この章の要点です。

    第18章では、次の2つの問題を解説します。

    問題概要
    競合状態の脆弱性共有資源を同時に使う処理がぶつかり、他人の情報表示やデータ破壊が起きる
    キャッシュからの情報漏洩個人向けの応答がキャッシュに残り、別の利用者に見えてしまう

    第13〜17章（ファイルアクセス・ファイルアップロード・構造化データの読み込み など）は「外部入力をどう扱うか」が中心でした。本章は、同時実行 と 一時保存（キャッシュ） という、タイミングや共有の問題がポイントです。入力チェックだけでは防げないことがあります。

    1.共有資産やキャッシュに関する問題の概要

    「共有資産」とは、複数のリクエストやプロセス（実行中のプログラム1つ分）が 同じものを読み書きする資源 です。

    共有資産の例よくある用途
    グローバル変数・静的変数リクエスト間で値を持ち回す（本来は避けるべき）
    ファイル設定・一時ファイル・ログの読み書き
    データベースの行残高・在庫・予約状況などの更新
    キャッシュ応答や計算結果を一時保存して高速化する

    グローバル変数 はプログラムのどこからでも読み書きできる変数、静的変数 はアプリケーション全体で1つだけ存在し、呼び出しをまたいで値が残る変数です。便利な一方で、「誰のデータを扱っているか」「いつ書き換わるか」が曖昧だと、他人のデータが混ざったり、途中状態が保存されたりします。

    1.1 日常生活での例え

    正常

    銀行の窓口で、自分の通帳だけを開いて処理する。

    問題が起きた場合

    窓口の机に「今処理中の名前」を1枚だけ置いていて、隣の窓口の処理と取り違える。

    1.2 なぜ危険か

    Webサーバーは、利用者Aと利用者Bのリクエストを ほぼ同時に 処理します。共有資源の扱いを誤ると、次のような被害が出ます。

    ・別人の個人情報などが画面に表示される
・データベースの不整合（残高や在庫がおかしくなる）
・ファイルの内容の破壊
・キャッシュ経由で、他人のページ内容が漏洩する

    「攻撃者が特別な文字列を送る」タイプの脆弱性（SQLインジェクション など）とは違い、正常な利用が重なっただけでも起きる ことがあります。再現しにくく、気づきにくい点が厄介です。

    2.競合状態の脆弱性とは

    競合状態（Race Condition、レースコンディション） とは、複数の処理が同じ資源を 同時に・順序不定で 使うときに、想定外の結果になる問題です。セキュリティの文脈では、その結果として 他人の情報が見える・データが壊れる・権限チェックをすり抜ける などが起きます。

    項目内容
    分類同時実行・共有資源の扱い不備
    典型的な原因共有変数や共有ファイルに、排他制御なしで読み書きする
    典型的な被害他人の個人情報表示、DB不整合、ファイル破壊

    「競合」は、複数の処理が同じ場所を取り合ってぶつかるイメージです。タイミング次第で結果が変わるため、テストでは見逃されやすいです。

    2.1 日常生活での例え

    正常

    共有のホワイトボードに、自分の名前だけ書いて作業し、終わったら消す。

    問題

    Aさんが「田中」と書いた直後に、Bさんが「鈴木」と上書きする。Aさんの処理は「鈴木」のまま進み、別人の情報が表示される。

    2.2 何ができるか（被害）

    被害説明
    別人の個人情報などが画面に表示される共有変数に入れた「今の利用者名」などが、別リクエストに上書きされる
    データベースの不整合残高や在庫を「読んでから書く」処理が重なり、更新が欠ける・二重になる
    ファイルの内容の破壊同じファイルへの同時書き込みで、内容が混ざる・途中で切れる

    いずれも「攻撃コードを埋め込む」必要はなく、アクセスが重なるだけで起きる 点が特徴です。個人情報の取り違えは、プライバシー侵害として特に深刻です。

    2.3 攻撃・発生のイメージ（共有変数）

    古典的な悪い例として、リクエストごとに使うべき値を、共有変数（グローバル変数など）に置いてしまう パターンがあります。

    危険な例：悪いイメージ（擬似コード） 
    【悪いイメージ（擬似コード）】
共有変数 name を用意する（全リクエストで同じ変数）

リクエストA: name = "田中" をセット
リクエストB: name = "鈴木" をセット   ← ここで上書き
リクエストA: name を画面に表示
→ 「鈴木」が表示される（田中さんの画面なのに別人）

    ここで重要なのは次の2点です。

    ・変数 name は共有変数である
・共有変数 name の排他制御をしていない

    「排他制御」とは、ある処理が資源を使っているあいだ、他の処理が同じ資源を触らないようにする仕組みです。鍵付きの個室のようなもので、鍵を持っている人だけが中に入れます。

    2.4 なぜ共有変数が危険か

    Webアプリでは、リクエストごとに独立した作業スペース を使うのが基本です。グローバル変数や、アプリケーション全体で1つしかない静的変数は、その原則に反します。

    安全なイメージ 
    【安全なイメージ】
リクエストA: 自分専用の箱に「田中」を入れる
リクエストB: 自分専用の箱に「鈴木」を入れる
→ 互いに干渉しない
    危険なイメージ 
    【危険なイメージ】
リクエストA・B: 店に1つしかない箱を共有する
→ 後から書いた方が勝ち、先の処理は別人の値を使う

    言語やフレームワークによっては、ワーカープロセス（リクエストを実際に処理する作業役のプロセス）や スレッド（1つのプロセスの中で並行して動く処理の流れ）の共有範囲が異なります。いずれにせよ、「この変数は誰と共有されているか」を意識しないと、競合状態の温床になります。

    2.5 データベースやファイルでも起きる

    共有変数だけでなく、DBやファイルでも同じ構造の問題が起きます。

    【残高更新の競合イメージ】
1. Aの処理: 残高 1000 を読む
2. Bの処理: 残高 1000 を読む
3. Aの処理: 1000 - 300 = 700 を書く
4. Bの処理: 1000 - 200 = 800 を書く
→ 本来は 500 になるはずが、800 のまま（Aの引き落としが消える）
    【ファイル書き込みの競合イメージ】
処理Aと処理Bが同じ設定ファイルに同時に書き込む
→ 行が混ざる、片方の内容だけ残る、ファイルが壊れる

    「読んでから書く」処理は、そのあいだに別処理が入ると結果が壊れやすいです。これを チェック・ツー・ユース（TOCTOU: Time-of-Check to Time-of-Use） と呼ぶこともあります。確認した瞬間と、実際に使う瞬間のあいだに状態が変わる、という意味です。

    補足：用語の使い分け

    TOCTOU は、正式には「タイム・オブ・チェック・トゥ・タイム・オブ・ユース」と読みます。特に「ファイルが存在するか・権限があるかを確認してから使う」のように、確認と使用の間 の隙を指すことが多い言葉です。上の残高の例のように、2つの更新がぶつかって片方が消える現象は、データベースの分野では 更新の消失（Lost Update） とも呼ばれます。どちらも「間に割り込まれる」ことが原因の競合状態です。

    ポイントの二重使用など、悪意ある同時リクエストで業務ロジックをすり抜ける例と、「判定と更新を1命令にまとめる」書き方は、71 セキュリティ基礎「業務ロジックの穴を防ぐ」 で図とコードつきで説明しています。

    2.6 発生の流れ

    1. アプリが、リクエスト固有の値を共有資源（共有変数・共有ファイルなど）に置く
    2. 利用者Aと利用者Bのリクエストがほぼ同時に届く
    3. Aが共有資源に値を書いた直後に、Bが上書きする（または同時に読む）
    4. Aの続きの処理が、Bの値を使ってしまう
    5. 別人の個人情報表示、DB不整合、ファイル破壊などが起きる

    3.競合状態の脆弱性の対策

    対策の基本は次のとおりです。

    対策安全性説明
    可能であれば共有資源を使用しない最も簡単で安全寄りリクエストごとに独立した変数・領域を使う
    共有資源に対して排他制御を行う共有が必要な場合の必須対策ロックなどで同時アクセスを直列化する

    直列化 とは、同時に来た処理を「1つずつ順番に」実行させることです。

    3.1 可能であれば共有資源を使用しない（最優先）

    個人情報や「今の利用者」に紐づく値は、リクエスト単位・セッション単位のローカルな場所 に置きます。

    避けるべきもの 
    【避けるべきもの】
・グローバル変数に利用者名や個人情報を入れる
・アプリケーション全体で1つだけの静的変数にリクエスト固有の状態を持つ
・一時ファイル名を固定にして、全員が同じファイルを使う
    使うべきもの 
    【使うべきもの】
・関数の引数・ローカル変数
・リクエストオブジェクトやコンテキストに載せる値
・セッション（利用者ごとに分離されている前提で使う）
・DBの行を、利用者IDなどで正しく絞り込んで扱う

    ローカル変数 は関数の中だけで使われ、呼び出しごとに新しく作られる変数です。リクエストオブジェクト／コンテキスト は、フレームワークが1つのリクエストごとに用意する「そのリクエスト専用の入れ物」です。セッション は、ログイン状態などを利用者ごとにサーバー側で覚えておく仕組みです（詳しくは 74_セッション管理 で扱います）。

    「共有しなければ競合しない」ので、まず共有をやめるのが一番わかりやすい対策です。

    3.2 共有資源に対して排他制御を行う

    どうしても共有が必要な場合（在庫の減算、連番の発行、共有設定ファイルの更新など）は、排他制御（ロック） を行います。

    【排他制御の考え方】
1. 資源を使う前にロックを取る（鍵を借りる）
2. 読み取り・更新・書き込みを行う
3. 終わったらロックを解放する（鍵を返す）

ロック中は他の処理が同じ資源を触れないので、途中で割り込まれない

    データベースでは、トランザクション（複数の操作を「全部成功」か「全部取り消し」のひとかたまりとして扱う仕組み）や 行ロック（特定の行だけを他の処理から触れないようにすること）、SELECT ... FOR UPDATE などが使われます。ファイルでは、ファイルロックを使う方法があります。言語の ミューテックス（相互排他。一度に1つの処理だけが入れるようにする鍵）も、メモリ上の共有資源向けの手段です。

    たとえば 2.5 の残高更新は、SQL で次のように書き分けられます。

    危険な例：読んだ値をもとに、ロックなしで書き戻す（SQL） 
    SELECT balance FROM accounts WHERE id = 1;          -- 1000 を読む
-- （この間に別の処理が同じ行を更新できてしまう）
UPDATE accounts SET balance = 700 WHERE id = 1;     -- アプリで計算した値を書く
    安全な例：トランザクションと行ロック（SELECT ... FOR UPDATE） 
    BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;  -- この行をロック
-- 残高が足りるか確認する
UPDATE accounts SET balance = balance - 300 WHERE id = 1;
COMMIT;                                                -- ここでロック解放

    FOR UPDATE を付けると、トランザクションが終わる（COMMIT）まで、他の処理は同じ行を更新したりロックしたりできず、待たされます。そのため 2.5 のような「両方が 1000 を読んで書き戻す」状態になりません。

    【注意点】
・ロックの範囲は必要最小限にする（長く握りすぎると遅くなる）
・ロックを取り忘れた経路がないか確認する
・例外時にもロックが解放されるよう、finally などで必ず解放する
・デッドロック（互いに鍵を待ち合う状態）に注意する

    finally は、処理が成功しても例外（エラー）で中断しても、必ず最後に実行されるブロックです。

    危険な例：例外が起きるとロックが解放されない（擬似コード） 
    lock.acquire()
update_shared_file()   # ここで例外が起きると…
lock.release()         # ← 実行されず、ロックが残ったままになる
    安全な例：finally で必ず解放する（擬似コード） 
    lock.acquire()
try:
    update_shared_file()
finally:
    lock.release()     # 例外が起きても必ず実行される

    3.3 対策の優先順位

    1. リクエスト固有の値を共有変数に置かない
    2. 共有が不要なら、ローカル変数・リクエスト文脈・セッションに分離する
    3. 共有が必要なら、排他制御（ロック・トランザクション）を行う
    4. 「読んでから書く」処理は、途中で割り込まれない設計にする
    5. 負荷試験や同時アクセス試験で、取り違えや不整合が起きないか確認する

    4.キャッシュからの情報漏洩とは

    キャッシュからの情報漏洩 とは、本来その利用者だけが見るべき応答（個人情報を含むページなど）が、キャッシュに保存され、別の利用者に返されてしまう 問題です。

    キャッシュは、同じ内容を何度も生成しないための高速化の仕組みです。ブラウザ、プロキシ、CDN、リバースプロキシ、アプリ内キャッシュなど、経路のあちこちに存在します。

    • プロキシ：利用者とサーバーの間で通信を中継する機器（社内ネットワークの出口などにある）
    • CDN（Content Delivery Network）：世界各地のサーバーにコンテンツのコピーを置き、近い場所から配信する仕組み
    • リバースプロキシ：Webサーバーの手前に置かれ、サーバーの代わりにリクエストを受け付ける中継サーバー

    このうちプロキシ・CDN・リバースプロキシのように、複数の利用者で共用されるキャッシュ を「共有キャッシュ」と呼びます。ブラウザのキャッシュは、その利用者だけの「プライベートキャッシュ」です。

    項目内容
    分類キャッシュ制御の不備による情報漏洩
    典型的な原因アプリのキャッシュ制御ヘッダ不備、キャッシュサーバーの設定不備
    典型的な被害他人のマイページ・注文履歴・個人情報が表示される

    4.1 日常生活での例え

    正常

    自分宛の郵便物は、自分の郵便受けにだけ入る。

    問題

    受付の机に「さっき渡した書類のコピー」が置いてあり、次の来客に同じ書類が渡される。

    4.2 なぜキャッシュが危険になり得るか

    キャッシュは「同じURLなら同じ内容」とみなして使い回すことがあります。個人向けページまで使い回すと、Aさんの応答がBさんに届く ことになります。

    【漏洩のイメージ】
1. 利用者Aが /mypage にアクセス
2. サーバーが「田中さんの個人情報」を返す
3. 途中のキャッシュサーバーが、その応答を /mypage の結果として保存
4. 利用者Bが /mypage にアクセス
5. キャッシュが「保存済みの田中さんのページ」をBに返してしまう

    ログイン後の画面、カート、注文履歴、メッセージ、設定画面など、利用者ごとに内容が違うページ は特に注意が必要です。

    4.3 原因

    原因は大きく次の2つです。

    原因説明
    アプリケーション側のキャッシュ制御不備「キャッシュしてよい／いけない」をレスポンスで正しく伝えていない
    キャッシュサーバーの設定不備CDNやリバースプロキシが、個人向け応答までキャッシュしてしまう

    アプリがヘッダを出していても、キャッシュサーバー側がそれを無視する設定だと防げません。逆に、サーバー設定が厳しくても、アプリが「キャッシュしてよい」と宣言していると危険です。両方の設定が揃って初めて安全 になります。キャッシュサーバーの設定ミスは、OWASP Top 10 の「セキュリティの設定ミス」の一例でもあります（71 セキュリティ基礎「セキュリティの設定ミス」）。

    4.4 発生の流れ

    1. 個人情報を含むページが、キャッシュ可能な応答として扱われる
    2. ブラウザ・プロキシ・CDNなどがその応答を保存する
    3. 別の利用者（または別セッション）が同じURL等でアクセスする
    4. キャッシュ済みの他人の応答が返る
    5. 個人情報の取り違え・漏洩が起きる

    5.キャッシュからの情報漏洩の対策

    対策の基本は次のとおりです。

    対策安全性説明
    アプリ側でキャッシュ制御用の適切なレスポンスヘッダを設定する必須個人向け応答はキャッシュさせない
    キャッシュサーバー側でキャッシュ制御の適切な設定を行う必須認証付き応答などをキャッシュ対象外にする

    5.1 アプリケーション側で適切なレスポンスヘッダを設定する

    個人情報を含むページでは、キャッシュしないよう HTTPレスポンスヘッダ（サーバーが応答の本文と一緒に送る付加情報）で明示します。

    【個人向けページでよく使うヘッダの例】
Cache-Control: no-store
Cache-Control: private, no-cache
Pragma: no-cache
Expires: 0

    意味のイメージは次のとおりです。

    指示意味（イメージ）
    no-store応答を保存しない（いちばん厳しい部類）
    private共有キャッシュ（CDN等）には載せない。ブラウザのみ、という意図
    no-cache使う前に再検証する（「一切保存しない」とは限らない点に注意）
    Expires: 0すでに期限切れ、として扱う古い互換用の指定

    再検証 とは、保存しているコピーをそのまま使わず、「まだ最新ですか？」とサーバーに確認してから使うことです。Pragma: no-cache は、Cache-Control がなかった古い HTTP/1.0 時代の名残りで、互換のために併記されることがあります。

    個人情報や認証後の画面では、no-store を基本 に考えるとわかりやすいです。静的な画像やCSSなど、全員に同じでよいコンテンツだけをキャッシュ対象にします。

    危険な例：マイページに「1時間キャッシュしてよい」と宣言している 
    HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Cache-Control: public, max-age=3600

<h1>田中さんのマイページ</h1> ...
    安全な例：個人向け応答は保存させない 
    HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Cache-Control: no-store

<h1>田中さんのマイページ</h1> ...

    public は「共有キャッシュにも保存してよい」、max-age=3600 は「3600秒（1時間）は保存したものを使ってよい」という意味です。

    【分け方の考え方】
・全員共通（ロゴ、CSS、公開記事）→ キャッシュしてよい
・利用者ごと（マイページ、カート、設定）→ キャッシュさせない

    ほかのセキュリティヘッダとの位置づけや、ログアウト時にブラウザのキャッシュを消させる Clear-Site-Data ヘッダは セキュリティヘッダ「キャッシュ・ログアウト関連」 を、nginx で Cache-Control を追加したときにほかのヘッダが消える落とし穴は セキュリティヘッダ「nginx の設定例」 を参照してください。

    5.2 キャッシュサーバー側で適切な設定を行う

    CDN・リバースプロキシ・社内プロキシなどでも、次を確認します。

    【設定の考え方】
・Cookie や Authorization がある応答はキャッシュしない
・Set-Cookie を含む応答はキャッシュしない
・Cache-Control: private / no-store を尊重する
・個人向けパス（/mypage, /account など）をキャッシュ対象外にする
・キャッシュのキーに、利用者を区別する要素が必要なら正しく含める
    • Cookie：ブラウザがサイトごとに保存し、リクエストのたびに自動で送る小さなデータ。ログイン状態の識別によく使われます（詳しくは 74_セッション管理 で扱います）。
    • Authorization：API のトークンなど、認証情報を送るためのリクエストヘッダ。
    • Set-Cookie：サーバーがブラウザに Cookie を保存させるレスポンスヘッダ。これを含む応答をキャッシュすると、別の利用者に同じ Cookie（セッション ID など）が配られるおそれがあります。
    • キャッシュのキー：キャッシュが「どの保存データを返すか」を決める目印。通常は URL が使われるため、利用者ごとに内容が変わるのにキーに利用者の区別がないと、取り違えが起きます。

    「公開コンテンツだけキャッシュする」方針にすると、事故を起こしにくいです。迷ったらキャッシュしない方が安全です。

    5.3 URLに乱数値を付与する方法について

    キャッシュ回避の小技として、URLに乱数やタイムスタンプを付ける方法が紹介されることがあります。

    例:
/mypage?r=849201
/mypage?r=552118

    URLが毎回違うので、「同じURLのキャッシュを使い回す」問題は起きにくくなります。ただし、次の限界があります。

    ・キャッシュ自体はされてしまう
  （乱数付きURLごとの応答が、キャッシュに残る可能性がある）
・履歴やログ、Referer にURLが残ると、乱数付きでも追跡・再利用のリスクがある
・根本対策（Cache-Control 等）の代わりにはならない

    Referer は、リンクをたどったときに「どのページから来たか」を移動先に伝えるリクエストヘッダです（送る範囲の制御は セキュリティヘッダ「Referrer-Policy」 を参照）。

    乱数付与は補助的な手段

    つまり、乱数付与は 補助的な手段 であり、「キャッシュさせない」制御の代わりにはなりません。本筋は、レスポンスヘッダとキャッシュサーバー設定で、個人向け応答を保存対象から外すことです。

    5.4 対策の優先順位

    1. 個人向け応答に Cache-Control: no-store などを付ける
    2. 認証付き・Cookie付きの応答を、共有キャッシュの対象外にする
    3. CDN / プロキシ側でも、個人向けパスや認証応答をキャッシュしない
    4. 静的な公開コンテンツだけを積極的にキャッシュする
    5. URLへの乱数付与は補助に留め、根本対策の代わりにしない

    Web API の個人向け応答（JSON）も同じ考え方で no-store を付けます。API 特有の問題は次のページ WebAPIの脆弱性 で扱います。

    6.まとめ

    項目競合状態の脆弱性キャッシュからの情報漏洩
    本質共有資源を同時に使い、処理がぶつかる個人向け応答がキャッシュされ、他人に返る
    主な被害別人の個人情報表示、DB不整合、ファイル破壊他人のページ内容・個人情報の漏洩
    原因共有変数などの利用、排他制御の欠如アプリのヘッダ不備、キャッシュサーバー設定不備
    基本対策共有しない / 排他制御する適切なキャッシュ制御ヘッダとサーバー設定

    共有資産・キャッシュの安全の基本

    1. リクエスト固有の値は共有変数に置かない
    2. 共有が必要なら、ロックやトランザクションで排他制御する
    3. 個人向けページはキャッシュさせない（no-store 等）
    4. CDNやプロキシでも、認証付き・個人向け応答をキャッシュしない
    5. URLへの乱数付与だけで安心しない（キャッシュ自体は残り得る）

    本章に共通する考え方は、「今扱っているデータは、本当にこの利用者だけのものか」「そのコピーがどこかに残って、別人に渡らないか」 を疑うことです。同時実行とキャッシュは性能のための仕組みですが、利用者ごとの境界を曖昧にすると、そのまま情報漏洩やデータ破壊につながります。共有しない設計を優先し、共有やキャッシュが必要なところだけを明示的に制御する習慣を付けましょう。

    7.理解度チェック

    Q1. 競合状態の脆弱性が「攻撃者が特別な文字列を送る」タイプの脆弱性と違う点は何ですか？

    攻撃コードを埋め込まなくても、正常な利用が同時に重なっただけで起きる 点です。タイミング次第で結果が変わるため再現しにくく、入力チェックだけでは防げません。

    Q2. 共有変数 name の例で、田中さんの画面に「鈴木」が表示されてしまう原因を2つ挙げてください。

    ① 変数 name が全リクエストで共有される 共有変数 であること、② その共有変数に対して 排他制御をしていない ことです。Aが書いてから読むまでの間に、Bの上書きが割り込みます。

    Q3. 残高 1000 の口座から、Aが 300、Bが 200 をほぼ同時に引き落としたら残高が 800 になりました。何が起きたのですか？

    A・B の両方が残高 1000 を読み、それぞれ 700・800 を計算して書き戻したため、後から書いた B の値でAの更新が消えました。「読んでから書く」間に割り込まれた競合状態です。トランザクションと行ロック（SELECT ... FOR UPDATE）などで、途中で割り込まれないようにします。

    Q4. 競合状態の対策で、最優先とされるのは何ですか？

    可能であれば共有資源を使用しない ことです。リクエスト固有の値はローカル変数・リクエストのコンテキスト・セッションなどに置きます。共有がどうしても必要な場合に限り、ロックなどの排他制御を行います。

    Q5. ロックを使うときの注意点を2つ以上挙げてください。

    ロックの範囲を必要最小限にする、ロックを取り忘れた経路がないか確認する、例外時にも finally などで必ず解放する、デッドロック（互いに鍵を待ち合う状態）に注意する、などです。

    Q6. 個人向けページに Cache-Control: no-cache を付ければ「一切保存されない」と考えてよいですか？

    よくありません。 no-cache は「使う前に再検証する」という意味で、保存そのものを禁止するとは限りません。保存させたくない個人情報や認証後の画面では no-store を基本にします。

    Q7. アプリが正しく Cache-Control: no-store を出していても情報漏洩が起きるのはどんな場合ですか？

    CDN やリバースプロキシなどの キャッシュサーバーが、そのヘッダを無視してキャッシュする設定 になっている場合です。アプリ側のヘッダとキャッシュサーバー側の設定、両方が揃って初めて安全 になります。

    Q8. 「URL に乱数を付ければキャッシュ対策は十分」と言えないのはなぜですか？

    同じURLの使い回しは起きにくくなりますが、乱数付きURLごとの応答は キャッシュ自体には残る 可能性があり、履歴・ログ・Referer にURLが残れば追跡・再利用のリスクもあるからです。乱数付与は補助的な手段で、Cache-Control とキャッシュサーバー設定が根本対策です。
