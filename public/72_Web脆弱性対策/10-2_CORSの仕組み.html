    10 ブラウザのセキュリティモデル

    CORSの仕組み

    「API も URL も正しいのに、ブラウザに止められる」――それが CORS エラーです。同一オリジンポリシーで守られたブラウザが、どんなときに別オリジンのデータを読ませてくれるのか。シンプルリクエストとプリフライト、サーバーが返すヘッダの意味、Express での設定方法、よくある誤解までを順番に解説します。

    もとにしたノート：10_ブラウザのセキュリティモデル/02_CORS（徳丸本3章）・03_CORSとは・04_CORSの仕組み・06_CORSエラーの正体を図解（つるチャンネル）・07_CORS入門（プログラミングチュートリアル）

    ひとことで言うと

    CORS は、ブラウザの「別オリジンのデータは読ませない」という制限（同一オリジンポリシー）を、サーバーが「このオリジンならいいですよ」とレスポンスヘッダで許可したときだけ 安全に緩める仕組みです。チェックするのは ブラウザ、許可を出すのは サーバー です。

    1.CORSとは：なぜ必要なのか

    CORS（Cross-Origin Resource Sharing／クロスオリジンリソース共有、オリジン間リソース共有）は、異なるオリジン間でリソースを共有するための仕組み です。リソース＝データのことなので、「オリジン間でのデータ共有」と読み替えて構いません。たとえば YouTube と Twitter のように、別オリジンどうしでもデータのやり取りを許可するための決まりです。

    1.1 おさらい：オリジン

    オリジン は、スキーム（プロトコル）＋ ドメイン（ホスト）＋ ポート番号 の組み合わせです（例：https ＋ youtube.com ＋ 443）。どれか1つでも違えば別オリジン になります。詳しくは 受動的攻撃と同一オリジンポリシー で扱っているので、ここでは要点だけ確認します。

    スキーム

    通信のルール。鬼ごっこを始める前にルールを決めるのと同じです（https、http など）。

    ドメイン

    ほかと重複できない名前です（example.com など）。

    ポート

    部屋番号のようなもの。省略時は https なら 443、http なら 80 です。

    「オリジン」は「始まり・起源」という意味です。そこを起点に各ページへ移動していくのでオリジンと呼ぶのでは、という説明もあります（これは動画の話者の私見です）。

    すべて異なるオリジン

    https://example.com         ← オリジン1
http://example.com          ← オリジン2（プロトコルが違う）
https://api.example.com     ← オリジン3（ドメインが違う）
https://example.com:8080    ← オリジン4（ポート番号が違う）
https://www.example.com     ← オリジン5（サブドメインが違う）

    すべて同じオリジン

    https://example.com/page1   ← オリジン1
https://example.com/page2   ← オリジン1（パスが違うだけ）
https://example.com/api     ← オリジン1（パスが違うだけ）

    /page1 などの パスはオリジンの一部ではありません。

    1.2 おさらい：同一オリジンポリシー

    ブラウザには 同一オリジンポリシー（Same-Origin Policy、同一生成元ポリシー）というセキュリティ機能があります。Web はデフォルトで 同じオリジンどうしでしかデータのやり取りを許可しない、というルールです。たとえば mywebsite.com のページから mywebsite.com/users.json を読むのは OK ですが、api.mywebsite.com（サブドメイン違い）や randomwebsite.com は別オリジンなので NG です。

    なぜ必要なのかというと、悪意のあるサイトから、別のサイトのデータを勝手に取得されるのを防ぐ ためです。同一オリジンポリシーがなかったら、次のようなことが起こります。

    1. 悪意のあるサイト（evil.com）を開く（誘導される）
    2. そのサイトが、バックグラウンドで bank.com にリクエストを送る
    3. ログイン中の銀行サイトから情報を盗む。勝手に送金されるような被害にもつながる

    同一オリジンポリシーがあるため、このような攻撃を防ぐことができます。

    補足：止めているのは主に「レスポンスの読み取り」

    ノートでは「異なるオリジンからのリクエストは基本的にブロックする」と表現していますが、正確には、ブラウザが止めるのは主に 別オリジンのレスポンスを JavaScript が読むこと です。画像やスクリプトの埋め込み、フォーム送信などはもともと別オリジンにも送れますし、シンプルリクエスト（6章）はサーバーまで届きます。「送れない」のではなく「読めない」と覚えておくと、CORS エラーの正体（13章）が理解しやすくなります。詳しくは 受動的攻撃と同一オリジンポリシー を参照してください。

    1.3 開発者にとっての不便さと、CORSの役割

    現代の Web アプリでは、次のようにフロントエンドとバックエンド API を別のオリジンに置く構成が一般的です。

    フロントエンド: https://myapp.com
バックエンドAPI: https://api.myapp.com   ← ドメインが違う = クロスドメイン

https://myapp.com の JavaScript
  → fetch('https://api.myapp.com/users')
  → 同一オリジンポリシーにより、レスポンスの読み取りがブロックされる

    ドメインが違うので、これらは 異なるオリジン です。開発中も同じで、フロント（例：localhost:5500）とバックエンド（例：localhost:5000）は ポートが違うだけで別オリジン になり、fetch するとエラーになります。

    そこで登場するのが CORS です。CORS は、同一オリジンポリシーの制限を サーバーの許可に基づいて安全に緩和する 仕組みです。同一オリジンポリシーはユーザーを守るためのブラウザの仕組みで、それを 例外的に緩める のが CORS、という関係になります。

    2.たとえで理解する

    学校の教室

    自分のクラスの教室には入れる（同一オリジン）。他のクラス・他校の教室には勝手に入れない（同一オリジンポリシー）。ただし校舎間で 「許可証」 を事前に交換しておけば、指定された相手だけ入れる。この許可証が CORS です。

    銀行の窓口

    自分が口座を開いた銀行の支店に行くのは OK。別の銀行の支店では基本的に NG。ただし 事前に手続き をすれば OK。この「事前の手続き」が CORS です。

    お城の門番

    国王だけが集まる城では、門番が名簿を見て国王だけを通し、市民は通さない。これが同一オリジンポリシーのイメージで、名簿（許可リスト）を書くのはサーバー です。

    3.重要な前提：CORSはブラウザの機能

    ポイント説明
    ブラウザの機能CORS はブラウザが実施する。サーバー間の通信には（基本的に）関係ない
    curl / Postman では起きないツールからのリクエストは CORS チェックされない。curl は HTTP リクエストを送るコマンド、Postman は API を試すアプリ
    サーバー側の設定が必要許可するオリジンをレスポンスヘッダで返す
    異なるオリジンへのリクエストだけ同じオリジンへのリクエストでは CORS は関係ない（常に許可される）

    ここがポイント

    「curl では動くのにブラウザでは動かない」のは、API が壊れているからではありません。ブラウザだけがユーザーを守るためにチェックしているからです。CORS エラーが出たら、API 側でそのオリジンを許可しているか を確認しましょう。

    4.CORSの基本フロー

    ブラウザとサーバーのやり取りは、次の4ステップです。

    1. ブラウザ: https://myapp.com のページから fetch('https://api.example.com/data')
2. ブラウザ: Origin: https://myapp.com ヘッダを付けてリクエスト送信
3. サーバー: Access-Control-Allow-Origin: https://myapp.com をレスポンスに付ける
4. ブラウザ: オリジンが一致 → JavaScript にレスポンスを渡す ✅

    許可がなければ、3・4 が次のようになります。

    3. サーバー: Access-Control-Allow-Origin ヘッダなし
4. ブラウザ: CORSエラー → JavaScript からレスポンスを読めない ❌

    Origin は、ブラウザが「このリクエストはどのオリジンのページから出たか」を伝えるために 自動で付ける リクエストヘッダです。

    4.1 CORSエラーの例

    よくあるのは、次のようにフロントエンド（https://myapp.com）から別オリジンの API を呼ぶ場面です。

    // フロントエンド（https://myapp.com）から
fetch('https://api.example.com/users')
  .then(response => response.json())
  .catch(error => {
    // CORSエラーが発生する可能性がある
    console.error('CORS Error:', error);
  });

    このときブラウザは、リクエスト元 https://myapp.com とリクエスト先 https://api.example.com を比べ、異なるオリジンなので CORS の確認が必要 と判断します。許可がなければ、ブラウザのコンソールに次のようなエラーが表示されます。

    Access to fetch at 'https://api.example.com/users' from origin 'https://myapp.com'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present
on the requested resource.

    注意

    このとき サーバーは正常にレスポンスを返していることが多い のです。ブラウザが JavaScript への受け渡しをブロック しています。

    5.Access-Control-Allow-Origin

    Access-Control-Allow-Origin は、CORS で 最も重要な（必須の）レスポンスヘッダ です。どのオリジンからのアクセスを許可するかを指定します。

    5.1 設定例

    # 特定のオリジンのみ許可（本番環境で推奨）
Access-Control-Allow-Origin: https://myapp.com

# 全オリジンを許可（開発環境のみ。本番では非推奨）
Access-Control-Allow-Origin: *

    * は ワイルドカード（「何でもよい」を表す記号）で、すべてのオリジンを許可します。

    5.2 ブラウザの検証

    リクエストの Origin:     https://myapp.com
レスポンスの Allow-Origin: https://myapp.com
→ 一致 ✅ → レスポンスを JavaScript に渡す

リクエストの Origin:     https://evil.com
レスポンスの Allow-Origin: https://myapp.com
→ 不一致 ❌ → CORSエラー

    5.3 Express.js での設定例

    Express.js は Node.js でよく使われる Web サーバー用のフレームワークです。ヘッダを自分で付ける方法と、cors パッケージを使う方法があります。

    // 特定オリジンのみ許可
app.use((req, res, next) => {
  res.setHeader('Access-Control-Allow-Origin', 'https://myapp.com');
  next();
});

// cors パッケージを使う（推奨）
const cors = require('cors');
app.use(cors({ origin: 'https://myapp.com' }));

    app.use で登録する関数は ミドルウェア（すべてのリクエストの途中に挟まって共通処理をする関数）と呼ばれます。

    5.4 セキュリティ上の注意

    設定リスク
    *（ワイルドカード）どのサイトからでも API を呼べる
    オリジン検証なし悪意あるサイトも許可してしまう
    推奨許可するオリジンを明示的にリストアップ

    CORS の設定ミスが「セキュリティ設定ミス」の典型例として扱われる理由は、安全でない設計・設定ミス・古い部品 にまとめています。

    6.シンプルリクエスト

    CORS リクエストには、シンプルリクエスト と プリフライトリクエストが必要なリクエスト の2種類があります。

    シンプルリクエスト は、条件を満たす場合に 事前確認（プリフライト）なし でそのまま送信できるリクエストです。

    シンプルリクエストの条件（すべて満たす必要がある）

    1. メソッド が GET、HEAD、POST のいずれか
    2. リクエストヘッダ が許可リスト内のみ（カスタムヘッダは不可）
    3. Content-Type（POST の場合）が許可された値のみ（application/json は不可）

    6.1 GET・HEAD・POST

    シンプルリクエストで使える HTTP メソッド（リクエストの種類）は次の3つだけです。

    メソッド用途シンプルリクエスト
    GETデータの取得✅
    HEADヘッダのみ取得（ボディなし）✅
    POSTデータの送信✅
    PUTデータの更新❌ → プリフライト必要
    DELETEデータの削除❌ → プリフライト必要
    PATCH部分更新❌ → プリフライト必要
     
    // シンプルリクエスト（GET、カスタムヘッダーなし）
fetch('https://api.example.com/users');

// シンプルリクエスト（POST + 許可された Content-Type）
fetch('https://api.example.com/users', {
  method: 'POST',
  headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: 'name=yamada&email=yamada@example.com'   // name=山田 でも同じ
});

// プリフライトが必要（PUT）
fetch('https://api.example.com/users/1', { method: 'PUT', ... });

    6.2 リクエストヘッダの制限

    シンプルリクエストでは、ブラウザが自動的に付けるヘッダ以外 に、次の4種類だけを追加できます。

    許可されるヘッダ説明
    Accept受け取れるデータ形式
    Accept-Language希望する言語
    Content-Languageボディの言語
    Content-Typeボディのデータ形式（値は 6.3 の3つのみ）

    許可されないヘッダの例です。

    Authorization: Bearer token123     ← カスタム/認証ヘッダ → プリフライト必要
X-Custom-Header: value             ← カスタムヘッダ → プリフライト必要
X-Requested-With: XMLHttpRequest   ← プリフライト必要

    Authorization は認証用のトークン（ログイン済みであることを示す文字列）を送るヘッダです。

    シンプルリクエストではない例 
    // ❌ シンプルリクエストではない（Authorization ヘッダあり）
fetch('https://api.example.com/users', {
  headers: { 'Authorization': 'Bearer token123' }
});
// → ブラウザが先に OPTIONS リクエスト（プリフライト）を送る

    6.3 Content-Type ヘッダの制限

    POST リクエストで Content-Type を指定する場合、シンプルリクエストとして認められるのは 次の3つの値だけ です。

    Content-Type用途
    application/x-www-form-urlencodedHTML フォームと同じ形式
    multipart/form-dataファイルアップロード
    text/plainプレーンテキスト

    シンプルリクエストにならない Content-Type の例です。

    Content-Type: application/json   ← 最もよく使うが、プリフライト必要
Content-Type: application/xml
Content-Type: text/html
    シンプルリクエストではない例 
    // ❌ シンプルリクエストではない
fetch('https://api.example.com/users', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'yamada' })
});
// → プリフライトリクエストが先に送られる

    現代の API は JSON が主流のため、多くのリクエストで プリフライトが発生する のが普通です。

    なぜこの3つだけ？

    この3つは、CORS ができる前から HTML のフォーム送信で別オリジンに送れた形式です。もともと送れたものは事前確認なしでも危険が増えない、という考え方で「シンプル」扱いになっています。

    6.4 シンプルリクエストの処理フロー

    1. ブラウザがリクエストを送信
   ↓
2. サーバーがレスポンスを返す
   ↓
3. ブラウザがレスポンスヘッダーを確認
   - Access-Control-Allow-Origin があるか？
   ↓
4. あれば成功、なければエラー

    流れは 4章の図1 と同じです。

    7.プリフライトリクエスト

    プリフライトリクエスト（Preflight Request）とは、本番のリクエストの前にブラウザが送る 確認用の OPTIONS リクエスト です。OPTIONS は「このサーバーは何を受け付けるか」を問い合わせる HTTP メソッドです。「飛行機が離陸する前に安全確認をする」イメージで Preflight（事前飛行チェック） と呼ばれます。

    7.1 プリフライトが必要なケース

    シンプルリクエストの条件を満たさない、つまり次の いずれか に該当する場合です。

    メソッド

    PUT、DELETE、PATCH など

    カスタムヘッダ

    X-Custom-Header、Authorization など

    Content-Type

    application/json など

    次の例は3つすべてに該当します。

    // プリフライトリクエストが必要な例
fetch('https://api.example.com/users', {
  method: 'PUT',  // PUTメソッド
  headers: {
    'Content-Type': 'application/json',  // JSON
    'Authorization': 'Bearer token123'   // カスタムヘッダー
  },
  body: JSON.stringify({ name: '山田花子' })
});

    7.2 処理フロー

    ブラウザは本番のリクエストを いったん保留 し、先に OPTIONS で許可を確認します。サーバーが許可をレスポンスヘッダで返し、ブラウザが確認できたら、保留していた本番リクエストが送られます。

    1. ブラウザ → サーバー: OPTIONS（プリフライト）
   Origin: https://myapp.com
   Access-Control-Request-Method: PUT
   Access-Control-Request-Headers: Content-Type, Authorization

2. サーバー → ブラウザ: 204 No Content
   Access-Control-Allow-Origin: https://myapp.com
   Access-Control-Allow-Methods: GET, POST, PUT, DELETE
   Access-Control-Allow-Headers: Content-Type, Authorization

3. ブラウザ: 許可を確認 ✅

4. ブラウザ → サーバー: PUT（本番リクエスト）
   Origin: https://myapp.com
   Content-Type: application/json
   Authorization: Bearer token123

5. サーバー → ブラウザ: 200 OK
   Access-Control-Allow-Origin: https://myapp.com

    Access-Control-Request-Method / Access-Control-Request-Headers は、ブラウザが「これからこのメソッド・このヘッダで送りたいのですが」と伝えるリクエストヘッダです。204 No Content は「成功、ただし本文なし」を表すステータスコードです。

    7.3 プリフライトのリクエスト・レスポンス例

    プリフライトリクエスト

    OPTIONS /api/users/1 HTTP/1.1
Host: api.example.com
Origin: https://myapp.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Content-Type, Authorization

    プリフライトレスポンス

    HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://myapp.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 3600

    最後の Access-Control-Max-Age については 9章 で説明します。

    8.メソッド・ヘッダ・オリジンに対する許可

    プリフライトのレスポンスでは、メソッド・ヘッダ・オリジンの3つについて、サーバーが「どこまで許すか」を答えます。

    8.1 メソッドに対する許可（Access-Control-Allow-Methods）

    プリフライトのレスポンスでは、Access-Control-Allow-Methods ヘッダで許可する HTTP メソッドを指定します。

    Access-Control-Allow-Methods: GET, POST, PUT, DELETE, PATCH

    ブラウザは、プリフライトで要求したメソッドが含まれているかを検証します。

    プリフライトで要求: Access-Control-Request-Method: PUT
サーバーの許可:     Access-Control-Allow-Methods: GET, POST, PUT, DELETE
→ PUT が含まれる ✅ → 本番リクエストを送信
    プリフライトで要求: Access-Control-Request-Method: DELETE
サーバーの許可:     Access-Control-Allow-Methods: GET, POST
→ DELETE が含まれない ❌ → CORSエラー

    Express.js では、OPTIONS リクエストへの応答として次のように設定します。

    app.options('/api/users/:id', (req, res) => {
  res.setHeader('Access-Control-Allow-Origin', 'https://myapp.com');
  res.setHeader('Access-Control-Allow-Methods', 'GET, POST, PUT, DELETE');
  res.setHeader('Access-Control-Allow-Headers', 'Content-Type, Authorization');
  res.sendStatus(204);
});

    8.2 ヘッダに対する許可（Access-Control-Allow-Headers）

    プリフライトのレスポンスでは、Access-Control-Allow-Headers ヘッダで許可するリクエストヘッダを指定します。

    Access-Control-Allow-Headers: Content-Type, Authorization, X-Request-ID
    プリフライトで要求: Access-Control-Request-Headers: Content-Type, Authorization
サーバーの許可:     Access-Control-Allow-Headers: Content-Type, Authorization
→ 両方含まれる ✅

    足りないときは、次のようなエラーになります。エラーメッセージがそのまま直し方を教えてくれます。

    よくあるエラー対処
    Method PUT is not allowed by Access-Control-Allow-Methods.Allow-Methods に PUT を追加
    Request header field Authorization is not allowed by Access-Control-Allow-Headers.Allow-Headers に Authorization を追加

    8.3 オリジンに対する許可（Access-Control-Allow-Origin）

    CORS における オリジンへの許可 は、Access-Control-Allow-Origin ヘッダで行います。プリフライト・本番リクエストの両方 のレスポンスに必要です。

    設定意味用途
    https://myapp.com特定オリジンのみ本番環境（推奨）
    https://myapp.com, https://admin.myapp.com※ヘッダは1つだけ。動的に切り替え（このようにカンマで並べて書くことはできない）複数フロントエンド
    *全オリジン許可開発環境のみ

    複数オリジンを許可する場合

    Access-Control-Allow-Origin ヘッダには 1つの値しか書けません。複数オリジンを許可するには、リクエストの Origin を確認し、許可リストに入っていればその値を動的に返します。

    許可リストで確認してから返す 
    const allowedOrigins = ['https://myapp.com', 'https://admin.myapp.com'];

app.use((req, res, next) => {
  const origin = req.headers.origin;
  if (allowedOrigins.includes(origin)) {
    res.setHeader('Access-Control-Allow-Origin', origin);
  }
  next();
});

    許可リストで確認せずに Origin をそのまま返すのは危険です。この点は認証情報と組み合わせると特に深刻になるため、CORSエラーの対処法とCookie で詳しく扱います。

    プリフライトと本番の両方で必要

    OPTIONS レスポンス → Access-Control-Allow-Origin 必須
PUT レスポンス     → Access-Control-Allow-Origin 必須（ここが漏れやすい）

    漏れやすいポイント

    本番リクエストのレスポンスに Access-Control-Allow-Origin がないと、プリフライトは成功しても最終的に CORS エラー になります。上の app.options だけを書いて満足しないよう注意しましょう。

    9.Access-Control-Max-Age：プリフライトのキャッシュ

    Access-Control-Max-Age は、プリフライトリクエストの結果を キャッシュ（一時的に覚えておくこと）する時間を秒で指定するヘッダです。

    Access-Control-Max-Age: 3600

    この例では、3600秒（1時間）は同じ種類のリクエストに対してプリフライトがスキップされます。JSON の API ではほぼ毎回プリフライトが発生するので、往復を1回減らせるのは性能面で効果があります。

    補足

    ブラウザごとに上限があり、大きな値を指定してもそこで切り詰められます（例：Chromium 系ブラウザは最大2時間）。

    10.CORSレスポンスヘッダ一覧

    サーバーが返す CORS 関連のヘッダを整理します。

    ヘッダいつ必要か意味・例
    Access-Control-Allow-Origin必須（プリフライト・本番の両方）許可するオリジン。* は全オリジン許可（本番では非推奨）、https://myapp.com は特定オリジンのみ
    Access-Control-Allow-Methodsプリフライトのレスポンス許可する HTTP メソッド。例：GET, POST, PUT, DELETE
    Access-Control-Allow-Headersプリフライトのレスポンス許可するリクエストヘッダ。例：Content-Type, Authorization
    Access-Control-Allow-Credentials認証情報を許可する場合Cookie や認証情報を含めることを許可する。例：true
    Access-Control-Max-Age任意（プリフライト）プリフライト結果のキャッシュ時間（秒）。例：3600
    Access-Control-Expose-Headers（補足）任意（本番）JavaScript から読ませてよいレスポンスヘッダを追加で指定する。指定しないと、JS から読めるのは Content-Type など一部の基本的なヘッダだけ

    ブラウザ側が付けるリクエストヘッダは、Origin（全 CORS リクエスト）と、プリフライトの Access-Control-Request-Method・Access-Control-Request-Headers です。

    10.1 認証情報（Cookie）を含む場合はさらに条件がある

    Cookie などの認証情報を含める場合は、次のように Access-Control-Allow-Credentials を付けます。

    Access-Control-Allow-Origin: https://myapp.com
Access-Control-Allow-Credentials: true
    • Access-Control-Allow-Credentials: true を使う場合、Access-Control-Allow-Origin に * は使えません。必ず具体的なオリジンを指定します
    • リクエスト側（fetch）でも credentials: 'include' を指定する必要があります

    クロスオリジンの fetch では Cookie が自動では送られないこと、credentials の値の違い、SameSite 属性との関係、Origin を反射的に返す危険などの詳しい話は、次のページ CORSエラーの対処法とCookie で扱います。

    11.実際のリクエスト・レスポンス例

    11.1 シンプルリクエストの場合

    リクエスト

    GET /api/users HTTP/1.1
Host: api.example.com
Origin: https://myapp.com

    レスポンス

    HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://myapp.com
Content-Type: application/json

[{"id": 1, "name": "田中太郎"}]

    11.2 プリフライトが入る場合

    ① プリフライトリクエスト（OPTIONS）

    OPTIONS /api/users HTTP/1.1
Host: api.example.com
Origin: https://myapp.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: Content-Type, Authorization

    ② プリフライトレスポンス

    HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://myapp.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 3600

    ③ 実際のリクエスト（PUT）

    PUT /api/users/1 HTTP/1.1
Host: api.example.com
Origin: https://myapp.com
Content-Type: application/json
Authorization: Bearer token123

{"name": "山田花子"}

    ④ 実際のレスポンス

    HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://myapp.com
Content-Type: application/json

{"id": 1, "name": "山田花子"}

    ノートの例では、プリフライトのパスが /api/users、本番が /api/users/1 になっています。実際のブラウザは 本番と同じ URL（この場合 /api/users/1）に対してプリフライトを送ります。

    12.ハンズオン：Express + cors でエラーを再現して解決する

    ここでは、実際に CORS エラーを起こしてから cors モジュールで解決する流れを追います。結論は「サーバー側でアクセスを許可するオリジンを指定すれば解決できる」です。

    12.1 手順

    1. server ディレクトリで npm init し、express と nodemon（ファイルを保存するたびにサーバーを自動で再起動するツール）をインストールして、app.listen(5000) でサーバーを起動する
    2. /data エンドポイント（API の受け口となる URL）で、名前と年齢を JSON で返す
    3. client 側に index.html と script.js（defer 付きで読み込み）を作り、VS Code の拡張機能 Live Server（ポート 5500）で開く
    4. fetch("http://localhost:5000/data") → .then(res => res.json()) で取得すると、「No 'Access-Control-Allow-Origin' header」エラーが再現 される
    5. npm i cors し、app.use(cors({ origin: "http://127.0.0.1:5500" })) をミドルウェアとして設定すると、データ取得に成功する

    コードにすると、おおよそ次のようになります（ノートの手順をもとにした最小限の例です）。

    client/script.js（ポート 5500 のページから実行） 
    fetch("http://localhost:5000/data")
  .then((res) => res.json())
  .then((data) => console.log(data));
    server/index.js：CORS 設定なし（エラーになる） 
    const express = require("express");
const app = express();

app.get("/data", (req, res) => {
  res.json({ name: "yamada", age: 25 });
});

app.listen(5000);
    server/index.js：cors で許可オリジンを指定（成功する） 
    const express = require("express");
const cors = require("cors");
const app = express();

app.use(cors({ origin: "http://127.0.0.1:5500" }));  // 末尾に / を付けない

app.get("/data", (req, res) => {
  res.json({ name: "yamada", age: 25 });
});

app.listen(5000);

    つまずきやすい点

    • オリジンの末尾に / を付けるとダメ でした。オリジンにはパスが含まれないので、http://127.0.0.1:5500/ は Origin ヘッダの値 http://127.0.0.1:5500 と文字列として一致しません
    • localhost と 127.0.0.1 は同じコンピューターを指しますが、ホスト名が違うので別オリジン です。origin には、ブラウザのアドレスバーに表示されているページのオリジンをそのまま書きます（Live Server が 127.0.0.1:5500 で開いているなら http://127.0.0.1:5500）

    12.2 cors のオプション

    オプション働き付くヘッダ
    origin許可するオリジンを指定するAccess-Control-Allow-Origin
    methods["GET", "POST"] のように許可する HTTP メソッドを指定する。この状態で PUT を送るとエラーになるAccess-Control-Allow-Methods
    credentials: trueCookie のやり取りを許可する。クライアント側は fetch に credentials: "include" を付けるAccess-Control-Allow-Credentials: true
     
    app.use(cors({
  origin: "http://127.0.0.1:5500",
  methods: ["GET", "POST"],   // PUT は許可しない
  credentials: true,          // Cookie を許可（詳細は 10-3）
}));

// クライアント側
fetch("http://localhost:5000/data", { credentials: "include" });

    credentials の扱いは CORSエラーの対処法とCookie で詳しく説明します。

    12.3 開発者ツールで確認する

    Network タブ

    リクエスト／レスポンスの詳細を確認できます。Access-Control-Allow-Methods などのヘッダが返っているか、プリフライト（OPTIONS）が送られているかもここで見られます。

    Application タブ

    Cookie の中身を確認できます。credentials を使うときに便利です。

    13.よくある誤解

    誤解正しくは
    誤解1：CORS はサーバー側のエラーCORS エラーは ブラウザのセキュリティ機能 によるもの。サーバーは正常にレスポンスを返しているが、ブラウザがそれを JavaScript に渡さずブロックしている
    誤解2：すべてのリクエストにプリフライトが必要シンプルリクエストの条件を満たす場合は、プリフライトは不要
    誤解3：CORS は API の問題CORS は ブラウザのセキュリティ機能。サーバー間通信やツール（curl、Postman）では発生しない。ただし直すのは API（サーバー）側の設定

    補足：「サーバーは正常に返している」とは限らない場合

    誤解1の説明が当てはまるのは、シンプルリクエストや本番リクエストのレスポンスで止められた場合です。プリフライトで拒否された場合は、本番のリクエスト（PUT など）はそもそも送られません。Network タブで OPTIONS だけが出ていて本番が出ていなければ、プリフライトの段階で止まっています。

    もう1つの誤解：CORS は攻撃を防ぐ「盾」ではない

    CORS は守りを 緩める 仕組みです。設定を広げれば広げるほど、同一オリジンポリシーの守りが弱くなります。また、シンプルリクエストはサーバーまで届いてしまうので、「別サイトからの不正な送信」を CORS で止めることはできません。その対策（CSRF 対策）は別に必要です。

    14.まとめ

    このページの要点

    • オリジンは「プロトコル ＋ ドメイン ＋ ポート」の組み合わせ。どれか1つでも違えば別オリジン。パスは含まない
    • 同じオリジンへのリクエストは常に許可され、異なるオリジンへのリクエストには CORS 設定が必要
    • CORS は ブラウザの機能 で、セキュリティのためのもの。CORS エラーはブラウザでのみ発生する
    • 直すには サーバー側で適切な設定（許可オリジン、必要ならメソッド・ヘッダ・credentials）を行う
    • 条件を満たすシンプルリクエストはそのまま、それ以外は OPTIONS のプリフライトで事前確認される
    トピック要点
    CORSサーバーが許可ヘッダを返すことで、ブラウザが同一オリジンポリシーの制限を緩和
    Access-Control-Allow-Origin許可するオリジンを指定（最重要ヘッダ）
    シンプルリクエストGET/HEAD/POST ＋ 限定ヘッダ ＋ 限定 Content-Type。追加の確認なしで実行
    プリフライトリクエスト条件外のリクエストは OPTIONS で事前確認
    メソッドの許可Access-Control-Allow-Methods（プリフライト時に必要）
    ヘッダの許可Access-Control-Allow-Headers（プリフライト時に必要）
    オリジンの許可プリフライト・本番両方のレスポンスで Allow-Origin が必要
    Max-Ageプリフライト結果をキャッシュする秒数
    認証情報credentials: 'include' ＋ Allow-Credentials: true ＋ 具体的なオリジン（→ 10-3）

    全体像を1枚にまとめると次のようになります。

    同一オリジンポリシー（ブラウザのデフォルト防御）
        │
        │  サーバーが CORS ヘッダで許可
        ▼
CORS（安全なクロスオリジン通信）
        │
        ├─ シンプルリクエスト → そのまま送信 → Allow-Origin を確認
        │
        └─ それ以外 → プリフライト（OPTIONS）
                        ├─ Allow-Methods（メソッド許可）
                        ├─ Allow-Headers（ヘッダ許可）
                        └─ Allow-Origin（オリジン許可）
                              ↓
                        本番リクエスト → Allow-Origin を再確認

    次のページでは、実際に CORS エラーを解決する方法と、Cookie（認証情報）を伴う CORS を学びます。

    15.理解度チェック

    Q1. https://myapp.com と https://myapp.com:8080/api は同じオリジンですか？

    違うオリジンです。 パス（/api）はオリジンに含まれませんが、ポート番号が 443（省略時）と 8080 で違うためです。

    Q2. curl では API が正常に動くのに、ブラウザの fetch では CORS エラーになります。API が壊れているのでしょうか？

    壊れていません。 CORS はブラウザが行うチェックで、curl や Postman では行われません。サーバーがレスポンスに Access-Control-Allow-Origin を付けていないか、値がページのオリジンと一致していないのが原因です。直すのはサーバー側の設定です。

    Q3. 次の fetch はシンプルリクエストですか？ fetch(url, { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: ... })

    シンプルリクエストではありません。 メソッドは POST で条件を満たしますが、Content-Type が application/json で、許可された3つ（application/x-www-form-urlencoded・multipart/form-data・text/plain）に含まれないため、プリフライトが送られます。

    Q4. プリフライトは成功しているのに、PUT の結果を JavaScript で読むと CORS エラーになります。何が漏れていると考えられますか？

    本番リクエスト（PUT）のレスポンスに Access-Control-Allow-Origin が付いていない 可能性が高いです。このヘッダはプリフライトと本番の両方のレスポンスに必要です。

    Q5. https://myapp.com と https://admin.myapp.com の両方を許可したいとき、Access-Control-Allow-Origin にカンマ区切りで2つ書けばよいですか？

    いいえ。 このヘッダには1つの値しか書けません。サーバーで許可リストを持ち、リクエストの Origin がリストに含まれる場合だけ、その値を返すように動的に切り替えます。

    Q6. Access-Control-Max-Age: 3600 を付けると何が変わりますか？

    プリフライトの結果が 3600秒（1時間）キャッシュされ、その間は同じリクエストに対するプリフライトが省略されます（ブラウザごとの上限あり）。往復が1回減るので、JSON API の応答が速くなります。
