    10 ブラウザのセキュリティモデル

    CSP（コンテンツセキュリティポリシー）

    CSP は、サーバーがブラウザに「このページでは、ここから来たスクリプトや画像だけを読み込んでよい」と伝える仕組みです。万一 XSS で悪意あるスクリプトが紛れ込んでも、ブラウザが実行を止めてくれます。設定のしかた、主なディレクティブ、'unsafe-inline' を避けるための nonce とハッシュ、違反レポートでのデバッグまでを解説し、最後に同じノートで扱っている PKCE も簡単に紹介します。

    もとにしたノート：10_ブラウザのセキュリティモデル/09_PKCEとCSPとは

    ひとことで言うと

    CSP は ブラウザに渡す「持ち込み許可リスト」 です。リストにない場所のスクリプトや、許可されていないインラインスクリプトは、たとえ HTML に紛れ込んでも ブラウザが実行しません。XSS を「起こさない」対策ではなく、起きたときの 被害を抑える 最後の守りです。

    1.CSP とは

    CSP（Content Security Policy） は、XSS（Cross-Site Scripting） 攻撃を防ぐためのセキュリティポリシーです。XSS とは、攻撃者が Web ページに自分のスクリプトを紛れ込ませ、閲覧者のブラウザで実行させる攻撃のことです（XSSの基本 で詳しく扱います）。

    CSP はサーバーから送る HTTP レスポンスヘッダ（またはHTMLの meta タグ）で、ブラウザに どのリソースを読み込んで良いか を指示します。ここでいう リソース とは、スクリプト・CSS・画像・フォント・通信先など、ページが読み込むもの全般です。

    1.1 日常生活での例え

    CSP は、空港の 「セキュリティチェック」 のようなものです。

    セキュリティチェック

    許可されたものだけ を機内に持ち込める。

    CSP

    許可されたリソースだけ をページに読み込める。

    1.2 なぜ CSP が必要なのか

    XSS 攻撃では、悪意のあるスクリプトが注入される可能性があります。CSP は、許可されていないスクリプトの実行を防ぎます。

    ✕ CSP なし（危険）

    <script>
  // 悪意のあるスクリプトが実行される可能性がある
  eval(userInput); // 危険！
</script>

    ○ CSP あり（安全）

    Content-Security-Policy: script-src 'self'
// 'self'以外のスクリプトは実行されない

    'self' は「このページと 同じオリジン（スキーム＋ホスト＋ポートの組）」という意味です。オリジンの考え方は 受動的攻撃と同一オリジンポリシー を参照してください。script-src 'self' だと、同じオリジンに置いた .js ファイルだけが実行でき、HTML の中に直接書かれた インラインスクリプト や eval() も既定でブロックされます。

    補足：CSP は「XSS対策の本体」ではありません

    ノートでは「XSS 攻撃を防ぐためのポリシー」と説明していますが、XSS の根本対策はあくまで 出力時のエスケープ（HTML として意味を持つ記号を無害な文字に置き換えること）です。CSP は、エスケープ漏れがあっても被害を抑える 多層防御の1層 と考えてください（→ 深層防御、インジェクションの基本は インジェクションと暗号化の不備）。

    2.CSP の設定方法

    CSP を設定する方法は2つあります。ディレクティブ（「スクリプトはここから」などの個々の指示）を ; で区切って並べます。

    2.1 HTTP ヘッダで設定

    Express.js での例

    // Express.jsでの例
app.use((req, res, next) => {
  res.setHeader(
    'Content-Security-Policy',
    "default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline';"
  );
  next();
});

    Express.js は Node.js の Web フレームワーク、app.use はすべてのリクエストで動く処理（ミドルウェア）を登録する書き方です。

    2.2 HTML の meta タグで設定

    <meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self' 'unsafe-inline';">

    どちらを使うか

    基本は HTTP ヘッダ がおすすめです。meta タグでは frame-ancestors（他サイトの iframe に埋め込まれるのを制限する指示）や report-uri / report-to、sandbox が使えません。frame-ancestors などクリックジャッキング対策は セキュリティヘッダ で扱います。

    3.CSP ディレクティブ

    3.1 主なディレクティブ

    ディレクティブ説明例
    default-src他のディレクティブのデフォルト値（個別指定がない種類に使われる）'self'
    script-srcJavaScript の読み込み元'self' 'unsafe-inline'
    style-srcCSS の読み込み元'self' 'unsafe-inline'
    img-src画像の読み込み元'self' data: https:
    font-srcフォントの読み込み元'self' https://fonts.googleapis.com
    connect-srcfetch、XMLHttpRequest などの接続先'self' https://api.example.com
    frame-srciframe の読み込み元'self' https://youtube.com

    補足：Google Fonts のドメイン

    表の font-src の例にある fonts.googleapis.com が配っているのは CSS で、フォントファイル本体は fonts.gstatic.com から届きます。実際には style-src に https://fonts.googleapis.com、font-src に https://fonts.gstatic.com を書きます（4章の実装例はこの形になっています）。

    3.2 CSP の値

    値説明
    'self'同じオリジンのみ許可
    'unsafe-inline'インラインスクリプト／スタイルを許可（非推奨）
    'unsafe-eval'eval() を許可（非推奨）
    'none'すべて禁止
    https:HTTPS のすべてのドメインを許可
    data:data: URL（データそのものを URL に埋め込む形式）を許可

    'self' や 'none' のように シングルクォートで囲む 値はキーワードです。クォートを付け忘れると「self という名前のホスト」と解釈されてしまうので注意してください。

    4.CSP の実装例

    4.1 基本的な設定（Express.js）

    ディレクティブを配列に並べて join('; ') でつなげると、読みやすく管理できます。

    // Express.jsでの例
app.use((req, res, next) => {
  res.setHeader(
    'Content-Security-Policy',
    [
      "default-src 'self'",
      "script-src 'self' 'unsafe-inline' https://cdn.example.com",
      "style-src 'self' 'unsafe-inline' https://fonts.googleapis.com",
      "img-src 'self' data: https:",
      "font-src 'self' https://fonts.gstatic.com",
      "connect-src 'self' https://api.example.com",
      "frame-src 'none'",
    ].join('; ')
  );
  next();
});

    4.2 React アプリでの設定（meta タグ）

    // public/index.html
<!DOCTYPE html>
<html lang="ja">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <meta http-equiv="Content-Security-Policy"
        content="default-src 'self';
                 script-src 'self' 'unsafe-inline' 'unsafe-eval';
                 style-src 'self' 'unsafe-inline';
                 img-src 'self' data: https:;
                 connect-src 'self' https://api.example.com;">
  <title>My App</title>
</head>
<body>
  <div id="root"></div>
</body>
</html>

    4.3 Next.js での設定（next.config.js）

    // next.config.js
module.exports = {
  async headers() {
    return [
      {
        source: '/:path*',
        headers: [
          {
            key: 'Content-Security-Policy',
            value: [
              "default-src 'self'",
              "script-src 'self' 'unsafe-inline' 'unsafe-eval'",
              "style-src 'self' 'unsafe-inline'",
              "img-src 'self' data: https:",
              "connect-src 'self' https://api.example.com",
            ].join('; '),
          },
        ],
      },
    ];
  },
};

    注意：上の例は「まず動かす」ための緩い設定です

    4.1〜4.3 の例はすべて script-src に 'unsafe-inline' を、4.2・4.3 は 'unsafe-eval' まで含んでいます。これでは 注入されたインラインスクリプトも実行できてしまい、XSS に対する CSP の効果はほぼなくなります。'unsafe-eval' は主に開発サーバー（ホットリロード）で必要になるもので、本番ビルドでは通常不要です。本番では次章の nonce かハッシュ に置き換えましょう。

    5.CSP の注意点：'unsafe-inline' を避ける

    5.1 'unsafe-inline' の使用

    ✕ 非推奨（XSS 攻撃のリスクがある）

    script-src 'self' 'unsafe-inline'

    ○ 推奨（nonce やハッシュを使用）

    script-src 'self' 'nonce-random-string'

    インラインスクリプトを丸ごと許可すると、正規のスクリプトと攻撃者が注入したスクリプトの区別がつきません。そこで「自分が書いたインラインスクリプトだけ」に印を付けて許可する方法が nonce とハッシュです。

    5.2 nonce の使用

    nonce（ナンス、number used once）は、リクエストごとに毎回作り直す使い捨てのランダム値 です。サーバーは同じ値を CSP ヘッダと <script nonce="…"> の両方に書きます。攻撃者はその回の値を事前に知り得ないので、注入したスクリプトには正しい nonce を付けられません。

    // サーバー側でnonceを生成
const nonce = crypto.randomBytes(16).toString('base64');

// CSPヘッダーにnonceを含める
res.setHeader(
  'Content-Security-Policy',
  `script-src 'self' 'nonce-${nonce}'`
);

// HTMLでnonceを使用
res.send(`
  <script nonce="${nonce}">
    // このスクリプトは実行される
  </script>
`);

    nonce の注意

    • 毎回のレスポンスで新しい値 を作ること。固定値やキャッシュされた HTML で使い回すと、攻撃者に知られて意味がなくなります
    • 十分な長さの暗号学的に安全な乱数を使います（例の crypto.randomBytes(16) は Node.js の安全な乱数）

    5.3 ハッシュの使用

    ハッシュ は、許可したいインラインスクリプトの中身を SHA-256 などで計算した「指紋」です。中身が1文字でも違えば指紋が変わるので、攻撃者が別のスクリプトを入れても一致しません。中身が毎回変わらない静的なスクリプトに向いています。

    // インラインスクリプトのハッシュを計算
// <script>alert('Hello')</script> のSHA256ハッシュ
const hash = 'sha256-...';

// CSPにハッシュを含める
res.setHeader(
  'Content-Security-Policy',
  `script-src 'self' '${hash}'`
);

    補足：ハッシュを計算する範囲

    ハッシュの対象は <script> タグを 除いた中身（この例では alert('Hello')）です。空白や改行も含めて完全一致が必要です。ブラウザの開発者ツールは CSP 違反時に「このハッシュを許可すれば動く」という値を表示してくれるので、それを参考にできます。

    5.4 nonce とハッシュの使い分け

    方法向いている場面注意
    nonceサーバーが HTML を毎回生成する（SSR）リクエストごとに新しい値が必要。静的配信の HTML では使いにくい
    ハッシュ中身が固定のインラインスクリプト、静的サイトスクリプトを少しでも変えたらハッシュを更新する

    6.CSP のデバッグ

    CSP をいきなり厳しくすると、正規のスクリプトや画像までブロックされてサイトが壊れることがあります。そこで 違反レポート を集めながら調整します。

    6.1 report-uri の使用

    CSP 違反をレポートする エンドポイント（レポートを受け取る URL）を設定できます。違反が起きると、ブラウザがその URL に JSON を POST します。

    res.setHeader(
  'Content-Security-Policy',
  "default-src 'self'; report-uri /api/csp-report"
);

// レポートを受け取るエンドポイント
app.post('/api/csp-report', (req, res) => {
  console.log('CSP違反:', req.body);
  res.status(204).send();
});

    補足：report-uri は非推奨、report-to が後継

    report-uri は仕様上 非推奨 になっており、後継は Reporting-Endpoints ヘッダと組み合わせて使う report-to ディレクティブです。ただし report-to に対応していないブラウザもあるため、当面は 両方を書いておく のが安全です（対応ブラウザは report-to を優先します）。

    Reporting-Endpoints: csp-endpoint="/api/csp-report"
Content-Security-Policy: default-src 'self'; report-uri /api/csp-report; report-to csp-endpoint

    また Express でレポートの本文を読むには、application/csp-report などの Content-Type を受け付ける JSON パーサーの設定が必要です。

    6.2 Content-Security-Policy-Report-Only

    実際にはブロックせず、レポートのみ送信 します。本番に導入する前に「このポリシーにしたら何が壊れるか」を確かめるのに使います。

    res.setHeader(
  'Content-Security-Policy-Report-Only',
  "default-src 'self'; report-uri /api/csp-report"
);
    1. まず Content-Security-Policy-Report-Only で導入し、レポートを集める
    2. 正規のリソースが違反していたら、ポリシーに許可を追加する（またはコード側を直す）
    3. 違反がほぼなくなったら Content-Security-Policy に切り替えて実際にブロックする

    7.実践例：nonce を使った CSP を設定したアプリケーション

    ミドルウェアでリクエストごとに nonce を作り、res.locals（そのリクエストの間だけ使える置き場）に保存して HTML 生成時に使います。base-uri（<base> タグで指定できる URL）と form-action（フォームの送信先）も制限しています。

    // server.js
const express = require('express');
const crypto = require('crypto'); // ノートでは省略されていたため補足
const app = express();

// CSPミドルウェア
app.use((req, res, next) => {
  const nonce = crypto.randomBytes(16).toString('base64');
  res.locals.nonce = nonce;

  res.setHeader(
    'Content-Security-Policy',
    [
      "default-src 'self'",
      `script-src 'self' 'nonce-${nonce}' https://cdn.example.com`,
      "style-src 'self' 'unsafe-inline' https://fonts.googleapis.com",
      "img-src 'self' data: https:",
      "font-src 'self' https://fonts.gstatic.com",
      "connect-src 'self' https://api.example.com",
      "frame-src 'none'",
      "base-uri 'self'",
      "form-action 'self'",
    ].join('; ')
  );

  next();
});

// HTMLを返す
app.get('/', (req, res) => {
  const nonce = res.locals.nonce;
  res.send(`
    <!DOCTYPE html>
    <html>
    <head>
      <title>My App</title>
    </head>
    <body>
      <div id="app"></div>
      <script nonce="${nonce}">
        // このスクリプトは実行される
        console.log('Hello, World!');
      </script>
    </body>
    </html>
  `);
});
    4.1 の基本設定との違い効果
    script-src から 'unsafe-inline' を外し、'nonce-…' に注入されたインラインスクリプトが実行されない
    base-uri 'self' を追加<base> タグの注入で相対パスのスクリプトを外部に向けられるのを防ぐ
    form-action 'self' を追加注入されたフォームで入力内容を外部に送らせるのを防ぐ

    style-src には 'unsafe-inline' が残っています。CSS の注入はスクリプトほど危険ではないため現実的な妥協としてよく見られますが、可能ならスタイルも nonce・ハッシュ化するとより安全です。CSP 以外のセキュリティ関連ヘッダ（X-Content-Type-Options など）は セキュリティヘッダ で扱います。

    8.PKCE について（73 で詳しく）

    元ノートでは CSP と一緒に PKCE も扱っています。PKCE はブラウザのセキュリティモデルではなく OAuth の認可フロー の話なので、73_認証認可（フェデレーション）で詳しく扱います。ここではノートの内容を要点だけ紹介します。

    8.1 PKCE とは

    PKCE（Proof Key for Code Exchange、「ピクシー」と読む） は、OAuth 2.0（他サービスのアカウントで、アプリに権限を委ねる仕組み）の 認可コードフロー をより安全にするための拡張仕様です。特に、モバイルアプリやシングルページアプリケーション（SPA）で使用されます。

    日常の例え：通常の認証

    固定のパスワードを使う（盗まれるリスクがある）。

    日常の例え：PKCE

    毎回新しい ワンタイムパスワード を生成する（盗まれても無効）。

    8.2 なぜ PKCE が必要なのか

    従来の認可コードフローでは、途中で発行される 認可コード（アクセストークンと引き換える一時的な引換券）が盗まれるリスクがありました。

    ✕ PKCE なし（危険）

    1. アプリが認可コードを取得
    2. 認可コードが盗まれる可能性がある
    3. 攻撃者が認可コードを使ってアクセストークンを取得できる

    ○ PKCE あり（安全）

    1. アプリが code_verifier と code_challenge を生成
    2. 認可コードと code_verifier の両方が必要
    3. 認可コードだけではアクセストークンを取得できない

    8.3 基本的な流れ

    1. アプリが code_verifier（ランダムな文字列）を生成
    2. code_verifier から code_challenge を生成（SHA-256 でハッシュ化）
    3. 認可リクエストに code_challenge を含める
    4. 認可サーバーが認可コードを発行
    5. アプリが認可コードと code_verifier を送信
    6. 認可サーバーが code_verifier から code_challenge を再計算し、一致するか確認
    7. 一致すればアクセストークンを発行

    ハッシュは元に戻せないので、途中で code_challenge を見られても code_verifier は分かりません。code_verifier を持っているのは最初にリクエストしたアプリだけ、という点が守りの核心です。

    8.4 実装例（ノートのコード）

    ステップ1〜3 のコードを表示

    ステップ1：code_verifier と code_challenge を生成

    // クライアント側（ブラウザ）
import crypto from 'crypto';

// code_verifierを生成（43-128文字のランダムな文字列）
function generateCodeVerifier() {
  return crypto.randomBytes(32).toString('base64url');
}

// code_challengeを生成（code_verifierをSHA256でハッシュ化）
function generateCodeChallenge(verifier) {
  return crypto
    .createHash('sha256')
    .update(verifier)
    .digest('base64url');
}

// 使用例
const codeVerifier = generateCodeVerifier();
const codeChallenge = generateCodeChallenge(codeVerifier);

// セッションストレージに保存（後で使用するため）
sessionStorage.setItem('code_verifier', codeVerifier);

    ステップ2：認可リクエストに code_challenge を含める

    // 認証リクエスト
const authUrl = `https://accounts.google.com/o/oauth2/v2/auth?
  client_id=YOUR_CLIENT_ID&
  redirect_uri=http://localhost:3000/callback&
  response_type=code&
  scope=email profile&
  code_challenge=${codeChallenge}&
  code_challenge_method=S256`;

window.location.href = authUrl;

    ステップ3：アクセストークンを取得

    // コールバックで認証コードを受け取った後
async function getAccessToken(code) {
  const codeVerifier = sessionStorage.getItem('code_verifier');

  const response = await fetch('https://oauth2.googleapis.com/token', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/x-www-form-urlencoded',
    },
    body: new URLSearchParams({
      code: code,
      client_id: 'YOUR_CLIENT_ID',
      code_verifier: codeVerifier, // code_verifierを含める
      redirect_uri: 'http://localhost:3000/callback',
      grant_type: 'authorization_code',
    }),
  });

  const data = await response.json();
  return data.access_token;
}

    8.5 実践例：PKCE を使った OAuth 2.0 実装

    ノートの「PKCE と CSP の組み合わせ」の PKCE 側です。トークン交換を自前のサーバー（/api/auth/token）経由にしている点がステップ3 と異なります。CSP 側は7章のコードです。

    コードを表示 
    // クライアント側
import crypto from 'crypto';

// code_verifierとcode_challengeを生成
function generatePKCE() {
  const codeVerifier = crypto.randomBytes(32).toString('base64url');
  const codeChallenge = crypto
    .createHash('sha256')
    .update(codeVerifier)
    .digest('base64url');

  return { codeVerifier, codeChallenge };
}

// ログインボタンのクリック
function handleLogin() {
  const { codeVerifier, codeChallenge } = generatePKCE();

  // code_verifierを保存
  sessionStorage.setItem('code_verifier', codeVerifier);

  // 認証リクエスト
  const authUrl = `https://accounts.google.com/o/oauth2/v2/auth?
    client_id=${CLIENT_ID}&
    redirect_uri=${REDIRECT_URI}&
    response_type=code&
    scope=email profile&
    code_challenge=${codeChallenge}&
    code_challenge_method=S256`;

  window.location.href = authUrl;
}

// コールバック処理
async function handleCallback() {
  const urlParams = new URLSearchParams(window.location.search);
  const code = urlParams.get('code');
  const codeVerifier = sessionStorage.getItem('code_verifier');

  // アクセストークンを取得
  const response = await fetch('/api/auth/token', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ code, code_verifier: codeVerifier }),
  });

  const { access_token } = await response.json();
  return access_token;
}

    補足：ノートの PKCE コードの注意点

    • import crypto from 'crypto' と randomBytes / createHash は Node.js のモジュール で、ブラウザではそのまま動きません。ブラウザでは Web Crypto API（crypto.getRandomValues() と crypto.subtle.digest('SHA-256', …)）を使います
    • テンプレート文字列の中で改行・空白を入れて URL を組み立てると、その空白も URL に含まれて壊れます。実際には URLSearchParams で組み立てます
    • CSRF 対策の state パラメータも本来は一緒に付けます
    • 現在の推奨（OAuth 2.0 セキュリティ BCP / OAuth 2.1）では、PKCE はモバイルや SPA に限らず すべてのクライアント で使うことが求められています

    こうした実装の細部は 73_認証認可 で詳しく扱います。

    9.まとめ

    このページの要点

    • CSP は、XSS 攻撃の被害を防ぐセキュリティポリシー。ブラウザに 許可されたリソースのみ 読み込ませる
    • HTTP ヘッダや meta タグ で設定する（frame-ancestors やレポート系はヘッダのみ）
    • default-src を土台に、script-src・style-src・img-src などを種類ごとに指定する
    • 'unsafe-inline' は非推奨（nonce やハッシュ を使用）。'unsafe-eval' も本番では避ける
    • 導入は Content-Security-Policy-Report-Only でレポートを集めてから。レポート先は report-uri と後継の report-to を併記する
    • CSP は根本対策（エスケープ）の代わりではなく、多層防御の1層
    • PKCE は OAuth 2.0 をより安全にする拡張仕様。code_verifier と code_challenge で 認可コードの盗難リスク を軽減する（モバイルアプリや SPA で特に重要。詳しくは 73_認証認可）

    10.理解度チェック

    Q1. script-src 'self' だけを指定したページに、XSS で <script>alert(1)</script> が注入されました。実行されますか？

    実行されません。 'self' は同じオリジンの外部スクリプトファイルを許可するだけで、インラインスクリプトは許可されていないため、ブラウザがブロックします。'unsafe-inline' を付けていると実行されてしまいます。

    Q2. nonce を一度だけ生成して、全リクエストで同じ値を使い回すと何が問題ですか？

    攻撃者がページを一度見れば nonce の値が分かり、注入するスクリプトに同じ nonce を付けて実行できてしまいます。nonce は レスポンスごとに新しく、予測できない乱数で作る必要があります。

    Q3. nonce とハッシュは、それぞれどんな場面に向いていますか？

    nonce はサーバーが毎回 HTML を生成する場面（SSR）に、ハッシュは中身が変わらないインラインスクリプトや静的サイトに向いています。ハッシュはスクリプトを変更するたびに値の更新が必要です。

    Q4. 既存サイトに厳しい CSP をいきなり適用せず、まず何をすべきですか？

    Content-Security-Policy-Report-Only で導入し、違反レポート（report-uri / report-to）を集めます。正規のリソースの違反を解消してから Content-Security-Policy に切り替えると、サイトを壊さずに導入できます。

    Q5. CSP を設定すれば、出力時のエスケープは不要になりますか？

    不要になりません。 CSP は設定の抜けや 'unsafe-inline' などの緩和、許可したドメインの悪用で突破されることがあります。根本対策はエスケープで、CSP は被害を抑える追加の層です。

    Q6. PKCE では、認可コードを盗まれてもなぜアクセストークンを取られないのですか？

    トークンと交換するときに、認可コードに加えて code_verifier が必要だからです。認可サーバーは code_verifier から code_challenge を再計算して、最初のリクエストの値と一致するか確かめます。code_verifier を持っているのは正規のアプリだけで、code_challenge（ハッシュ値）からは逆算できません。
