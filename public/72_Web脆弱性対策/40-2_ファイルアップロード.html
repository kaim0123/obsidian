    40 ファイル・データ処理

    ファイルアップロード

    プロフィール画像・添付資料・帳票など、Webアプリは ファイルのアップロードとダウンロード をよく使います。このページでは、徳丸本（『体系的に学ぶ 安全なWebアプリケーションの作り方』）第15章に沿って、アップロード機能への DoS 攻撃、アップロードしたファイルによるサーバー側スクリプト実行、ダウンロード時の XSS、PDF にまつわる問題と、その対策を解説します。

    もとにしたノート：40_ファイル・データ処理/02_ファイルアップロードにまつわる問題（徳丸本15章）

    ひとことで言うと

    アップロード機能は「外部の人がサーバーにファイルを置ける」機能です。対策の基本は、アップロード時 には「許可リストで拡張子を制限し、公開ディレクトリの外に保存する」こと、ダウンロード時 には「正しい Content-Type・nosniff・Content-Disposition: attachment を付けて返す」ことです。

    1.ファイルアップロードの問題の概要

    アップロード とは利用者のパソコンからサーバーへファイルを送ること、ダウンロード とはサーバーから利用者へファイルを渡すことです。ファイルアップロード機能には、主に次の問題があります。

    問題概要
    アップロード機能に対する DoS 攻撃巨大ファイルや大量アップロードでサーバー資源を枯渇させる
    アップロードファイルのサーバー側スクリプト実行攻撃用スクリプトをアップロードし、サーバー上で実行させる
    仕掛けを含むファイルを利用者にダウンロードさせる攻撃悪意あるファイルを他ユーザーに開かせ、XSS などを起こす
    閲覧権限のないファイルのダウンロード他人のファイルや秘密ファイルを不正に取得する

    1.1 日常生活での例え

    正常なアップロード

    自分のプロフィール写真だけが保存され、自分だけが見られる。

    攻撃された場合

    写真のふりをした「悪いプログラム」がサーバーに置かれ、サーバーごと乗っ取られる。あるいは、他の利用者のブラウザで勝手にスクリプトが動く。

    1.2 なぜ危険か

    アップロード機能は、アプリが 「サーバーにファイルを書き込む権限」 を持っているということです。その権限が悪用されると、次のような被害が出ます。

    ・サーバー上で攻撃用プログラムが動く
・Webサーバー内のファイルの閲覧・改ざん・削除
・他ユーザーへの XSS やマルウェア配布
・他人の非公開ファイルの漏洩
・ディスクや CPU を使い果たす DoS

    マルウェア とは、ウイルスなど悪意を持って作られたソフトウェアの総称です。

    第13章の「ファイルアクセス」（ファイルアクセスとディレクトリトラバーサル）は 既存ファイルの読み書き が中心でした。本章は 外部からファイルを持ち込む 点がポイントです。持ち込まれたファイルが「ただの画像」ではなく「実行可能なプログラム」や「ブラウザを騙す文書」になると、被害が大きくなります。

    補足：閲覧権限のないファイルのダウンロード

    概要表の4つ目（閲覧権限のないファイルのダウンロード）は、ノートでは個別の節がありません。考え方は単純で、ダウンロード用のスクリプトで 「このファイルを、今ログインしている利用者が見てよいか」を毎回サーバー側で確認する ことが対策です。ファイル名や ID を変えるだけで他人のファイルが取れる状態は、アクセス制御の不備です。詳しくは 71 セキュリティ基礎「アクセス制御と認証の失敗」 を参照してください。

    2.アップロード機能に対する DoS 攻撃

    DoS（Denial of Service） は、サービス妨害攻撃です。サーバーに負荷をかけて、正規の利用者がサービスを使えない状態にします（DoS・DDoS の一般的な説明は 71 セキュリティ基礎「さまざまな脅威と対策の基本」 を参照）。アップロード機能では、次のような方法でサーバーを重くしたり止めたりできます。

    手口説明
    巨大ファイルのアップロード数 GB のファイルを送り、ディスクやメモリを圧迫する
    大量の同時アップロード多くのリクエストで帯域・CPU・接続数を使い果たす
    小さなファイルの大量保存ディスクの inode（ファイル数の上限）を使い果たす

    inode とは、Linux などのファイルシステムが「ファイル1個ごと」に使う管理情報のことです。数に上限があるため、ディスクの空き容量が残っていても、ファイルの数が上限に達すると新しいファイルを作れなくなります。

    2.1 日常生活での例え

    正常

    写真を1枚アップロードする。

    攻撃

    倉庫いっぱいに巨大な荷物を送りつけ、他の荷物が置けなくなる。

    2.2 対策の要点

    対策説明
    ファイルサイズの上限アプリ・Webサーバー・PHP 等の設定で上限を設ける
    アップロード回数・頻度の制限同一ユーザー・同一 IP の連続投稿を制限する
    保存先ディスクの監視容量逼迫を検知できるようにする
    ウイルススキャン等の負荷制御重い処理はキュー（後で順番に処理するための待ち行列）に回し、Web 応答を止めない

    サイズ制限は「アプリだけ」では不十分なことがあります。Webサーバー（Nginx / Apache）や言語ランタイム（プログラムを動かす実行環境。PHP など）側の上限もあわせて設定します。

    補足：設定項目の例

    たとえば Nginx では client_max_body_size、Apache では LimitRequestBody、PHP では upload_max_filesize と post_max_size が、受け取れるサイズの上限を決める設定です。アプリでチェックする前に、手前の層で巨大なリクエストを止められます。

    3.アップロードファイルによるサーバー側スクリプト実行

    アップロードファイルによるサーバー側スクリプト実行 とは、攻撃者が サーバーで動くプログラム（PHP・JSP・ASP など）をアップロードし、それを Web 経由で実行させてしまう脆弱性です。

    画像や PDF を受け取るつもりが、実際には shell.php のような攻撃用スクリプトを置かれてしまうイメージです。このような、ブラウザからサーバーを遠隔操作できるようにする不正プログラムを Web シェル と呼びます。

    3.1 日常生活での例え

    正常

    受付に「写真」を預ける。

    攻撃

    「写真」と書いてある封筒の中身が、実は「倉庫の鍵を開ける道具」で、受付が倉庫の中に置いてしまう。

    3.2 何ができるか（被害）

    スクリプトがサーバー上で動くと、Webアプリが持つ権限の範囲で、ほぼ何でもできます。

    被害説明
    Webサーバー内のファイルの閲覧・改ざん・削除設定ファイル、ソースコード、データベース接続情報などを読まれる・書き換えられる
    外部へのメールの送信迷惑メールやフィッシングメールの踏み台にされる
    別のサーバーへの攻撃自サーバーを踏み台に、他サイトへ攻撃する
    サーバー上での暗号通貨の採掘CPU を勝手に使い、電気代や性能を奪う

    踏み台 とは、攻撃者が自分の正体を隠すために、乗っ取ったサーバーを中継点として使い、そこから別の相手を攻撃することです。

    一度スクリプト実行が成功すると、サーバーの乗っ取り に近い状態になります。第14章の OSコマンドインジェクション と同様、影響範囲が非常に広いです。読み込んだファイルがプログラムとして動くという点では、ファイルインクルード とも似ています。

    3.3 攻撃のイメージ

    プロフィール画像のアップロード機能があり、保存先が 公開ディレクトリ（ドキュメントルート配下にあり、URL を指定すればブラウザから直接アクセスできるフォルダ）だとします。ドキュメントルート とは、Webサーバーが URL で公開している一番上のフォルダ（例：/var/www/html/）のことです。

    【正常な利用】
photo.jpg をアップロード
→ https://example.com/uploads/photo.jpg で画像が表示される

【攻撃者の操作】
shell.php をアップロード（中身は攻撃用 PHP）
→ https://example.com/uploads/shell.php にブラウザでアクセス
→ サーバーが PHP として実行してしまう
→ 攻撃者がサーバー上で任意の処理を実行できる

    攻撃用スクリプトの例（概念）です。

    ✕ 攻撃者がアップロードする悪用スクリプトのイメージ

    <?php
// 攻撃者がアップロードした悪用スクリプトのイメージ
// 実際にはもっと巧妙に隠蔽されることが多い
system($_GET['cmd']);  // URL の cmd パラメータを OS コマンドとして実行

    system() は、渡された文字列を OS のコマンドとして実行する PHP の関数です。攻撃者は次のようにアクセスします。

    https://example.com/uploads/shell.php?cmd=ls
→ サーバー上で ls が実行され、ファイル一覧が返る

    3.4 脆弱性が生まれる原因

    この問題が起きる典型的な条件は、次の 2つが同時に成り立つ ことです。

    原因説明
    ① アップロードしたファイルが公開ディレクトリに保存されるURL で直接アクセスでき、Webサーバーがそのファイルを処理する
    ② アップロード後のファイル名として、サーバースクリプトを示す拡張子が指定できる.php .jsp .aspx など、実行対象の拡張子で保存できてしまう

    拡張子 とは、ファイル名の末尾の .php や .jpg など、ファイルの種類を表す部分です。Webサーバーは拡張子を見て「このファイルはプログラムとして実行するか、そのまま返すか」を決めることが多いです。

    【危険な組み合わせ】

公開ディレクトリ（例: /var/www/html/uploads/）
        ＋
実行可能な拡張子（例: .php）
        ↓
URL アクセスだけでスクリプトが動く

    どちらか一方でも防げれば、この攻撃は成立しにくくなります。

    ✅ 公開ディレクトリに置かない
   → URL で直接アクセスできない

✅ .php などの危険な拡張子を拒否する
   → 置かれてもスクリプトとして実行されない（※サーバー設定にも依存）

    3.5 拡張子の偽装にも注意

    単純なチェックだけでは、次のような抜け道があります。

    手口例
    二重拡張子shell.php.jpg（サーバー設定によっては .php として実行される）
    大文字小文字shell.PHP / shell.pHp
    末尾のドットや空白shell.php.（環境によって解釈が変わる）
    ヌルバイト（古い環境）shell.php%00.jpg（昔の言語処理で .php と解釈された例）
    Content-Type だけ信じるブラウザが送る image/jpeg は攻撃者が自由に書き換えられる

    ヌルバイト とは、文字コード 0 の特殊な文字（URL では %00）です。古い処理系では「文字列の終わり」と扱われ、%00 以降が無視されることがありました。Content-Type は「このデータは何の種類か」を表す情報（MIME タイプ。例：image/jpeg）で、アップロード時にはブラウザが申告しますが、攻撃者はリクエストを自由に作れるため信用できません。

    「ブラウザが申告した種類」や「ファイル名の見た目」だけを信じないことが重要です。

    4.ファイルダウンロードによるクロスサイト・スクリプティング（XSS）

    アップロードされたファイルを 他の利用者がダウンロード・表示する 機能でも、XSS が起きることがあります。XSS（クロスサイト・スクリプティング） は、攻撃者の用意したスクリプトを被害者のブラウザで実行させる攻撃です（基本は XSSの基本 を参照）。

    攻撃者は、HTML や JavaScript を含むファイルをアップロードし、被害者がそれをブラウザで開くと、被害者のブラウザ上でスクリプトが実行 されます。

    4.1 日常生活での例え

    正常

    共有フォルダから「資料.pdf」を開く。

    攻撃

    「資料」のふりをしたファイルを開いた瞬間、画面の裏で勝手に操作される（Cookie の盗難、偽画面の表示など）。

    4.2 なぜ起きるか

    ブラウザは、レスポンスの Content-Type（中身の種類） を見て、「画像として表示するか」「HTML として実行するか」を決めます。

    ここが間違っていると、次のようなことが起きます。

    【危険な例】
サーバーが text/html で返す
または Content-Type が曖昧で、ブラウザが HTML だと推測する
        ↓
中身に <script> があると、スクリプトとして実行される

    特に、アップロードファイルを 同一オリジン（同じサイト）上の URL で配信している場合、実行されたスクリプトはそのサイトの Cookie や DOM（ブラウザが画面の中身をプログラムから操作できるように表したもの）にアクセスできます。通常の XSS と同じ被害になります。オリジンの考え方は 受動的攻撃と同一オリジンポリシー を参照してください。

    4.3 対策（ダウンロード時）

    対策説明
    ファイルの Content-Type を正しく設定する画像なら image/jpeg、PDF なら application/pdf など、中身に合った型を返す
    X-Content-Type-Options: nosniff を指定するブラウザに「Content-Type を推測せず、宣言どおり扱え」と指示する
    ダウンロード想定のファイルには Content-Disposition: attachment を指定するブラウザ内で開かず、ダウンロードダイアログを出す（実行・表示を抑える）

    ブラウザが中身を見て種類を推測する動作を コンテンツスニッフィング（MIME スニッフィング）と呼びます。X-Content-Type-Options の詳しい説明は セキュリティヘッダ「X-Content-Type-Options」 を参照してください。

    レスポンスヘッダのイメージです。

    HTTP/1.1 200 OK
Content-Type: image/jpeg
X-Content-Type-Options: nosniff
Content-Disposition: attachment; filename="photo.jpg"
    ヘッダ役割
    Content-Type「これは JPEG 画像です」と正しく宣言する
    X-Content-Type-Options: nosniff中身を見て HTML だと勝手に判断しない
    Content-Disposition: attachment画面に表示せず、ファイルとして保存させる

    メモ

    ヘッダ名は Content-Disposition です（Cotent-Disposition は誤記）。

    5.PDF ダウンロード機能による XSS

    PDF をダウンロード・表示する機能でも、XSS に近い問題が起きます。代表的なのが PDF に偽装した HTML ファイルによる XSS です。

    5.1 PDF に偽装した HTML ファイルによる XSS

    攻撃の流れは次のとおりです。

    1. 攻撃者が、中身は HTML（+ JavaScript）なのに、ファイル名だけ report.pdf にしたファイルをアップロードする
    2. 被害者が「PDF を開く」リンクをクリックする
    3. サーバーが Content-Type を誤って text/html などで返す（またはブラウザが中身を HTML だと推測する）
    4. ブラウザが HTML として解釈し、<script> が実行される

    見た目は「PDF のダウンロード」でも、実際には HTML ページとして動いてしまう のがポイントです。

    5.2 Content-Type の間違いが根本原因

    この攻撃が成立する根本原因は、サーバーが返す Content-Type が正しくない（または曖昧） ことです。

    状況結果
    正しい Content-Type: application/pdf + nosniffブラウザは PDF として扱う（HTML としては実行しない）
    誤り Content-Type: text/htmlHTML として実行される
    曖昧（未設定・application/octet-stream のみ等）ブラウザの推測（コンテンツスニッフィング）に依存し、危険

    application/octet-stream は「中身の種類が分からない、ただのバイナリデータ」を表す汎用の型です。

    ファイル名が .pdf でも、中身の扱いを決めるのは主に Content-Type です。拡張子だけ見て安心してはいけません。

    5.3 Content-Type と IE の挙動の関係

    かつての Internet Explorer（IE）は、Content-Type より 中身の先頭バイトを見て種類を推測する（コンテンツスニッフィング）傾向が強いことで知られていました。

    【IE で起きやすかったこと】

サーバー: Content-Type: application/pdf と返したつもり
実際の中身: <html><script>...</script></html>
        ↓
IE が「これは HTML だ」と推測して実行してしまう

    そのため、次の対策が特に重要でした（現代のブラウザでも防御として有効です）。

    対策効果
    正しい Content-Type種類の宣言を明確にする
    X-Content-Type-Options: nosniff推測をやめさせ、宣言どおりに扱わせる
    Content-Disposition: attachmentブラウザ内表示を避け、ダウンロードさせる

    現代ブラウザでは挙動が改善されていますが、古いブラウザや組み込みブラウザ、設定の違いもあるため、ヘッダ対策は引き続き必須です。

    補足：2026年時点の状況

    IE は 2022年6月にサポートが終了し、現在の Windows では Microsoft Edge に置き換わっています。Chrome・Edge・Firefox・Safari など現代のブラウザは、application/pdf や application/octet-stream と宣言されたものを HTML に「格上げ」して実行することは基本的にありません（application/octet-stream は通常ダウンロード扱いになります）。そのため「IE 特有の危険な推測」は過去の話ですが、Content-Type 未設定や text/html での配信 は今でも XSS の原因になります。ノートのとおり、正しい Content-Type・nosniff・attachment の3点セットは今も基本対策です。

    6.対策（アップロードとダウンロード）

    対策は アップロード時 と ダウンロード時 の両方で行います。どちらか一方だけでは不十分です。

    6.1 アップロード時の対策：拡張子が許可されたものかをチェックする

    許可リスト（ホワイトリスト） 方式で、必要な拡張子だけ を通します。拒否リスト（ブラックリスト。「.php 以外は OK」のように、だめなものだけを列挙する方式）は抜け道が多く、非推奨です。

    ✕ 悪い例（拒否リスト）

    .php だけ禁止

    → .php5 .phtml .cgi .aspx などで回避されることがある

    ○ 良い例（許可リスト）

    画像なら .jpg .jpeg .png .gif .webp のみ許可

    それ以外はすべて拒否

    実装のポイントです。

    ポイント説明
    許可リストを使う業務上必要な拡張子だけ列挙する
    大文字小文字を統一して判定.PHP も .php と同じ扱いにする
    拡張子はサーバー側で付け直すユーザー指定のファイル名をそのまま使わない
    保存名はアプリが決めるUUID（ほぼ重複しないランダムな識別子）など推測しにくい名前にする
    公開ディレクトリに置かないドキュメントルートの外に保存し、アプリ経由で配信する

    ✕ 危険：利用者のファイル名のまま公開ディレクトリに保存する（比較用の例）

    // ❌ 危険: ファイル名も拡張子も利用者まかせで、公開ディレクトリに保存
$name = $_FILES['photo']['name'];          // 例: shell.php
move_uploaded_file($_FILES['photo']['tmp_name'],
                   '/var/www/html/uploads/' . $name);
// → https://example.com/uploads/shell.php で実行できてしまう

    ○ 安全：許可リストで拡張子をチェックし、保存名はサーバーが決める

    // ✅ 許可リストで拡張子をチェックし、保存名はサーバーが決める例（概念）
$allowed = ['jpg', 'jpeg', 'png', 'gif', 'webp'];
$original = $_FILES['photo']['name'];
$ext = strtolower(pathinfo($original, PATHINFO_EXTENSION));

if (!in_array($ext, $allowed, true)) {
    exit('許可されていないファイル形式です');
}

// ユーザーのファイル名は使わず、安全な名前で保存
$newName = bin2hex(random_bytes(16)) . '.' . $ext;
$savePath = '/var/www/data/uploads/' . $newName;  // 非公開ディレクトリ
// move_uploaded_file(..., $savePath);

    使っている関数の意味は次のとおりです。pathinfo(…, PATHINFO_EXTENSION) はファイル名から拡張子だけを取り出し、strtolower() は小文字にそろえます。in_array(…, true) は配列に含まれるかを型まで厳密に調べ、random_bytes(16) と bin2hex() で推測しにくいランダムな名前を作ります。move_uploaded_file() は、一時フォルダに届いたアップロードファイルを保存先へ移動する PHP の関数です。

    6.2 あわせてやっておくとよいこと

    対策説明
    ファイルサイズ上限DoS 対策にもなる
    画像なら画像として再エンコード余計なデータを取り除き、スクリプト混入を減らす
    実行権限を付けない保存先ディレクトリでスクリプト実行を無効化する
    ウイルススキャンマルウェア配布対策（万能ではないが有効）

    再エンコード とは、受け取った画像をいったん画像として読み込み、改めて画像ファイルとして保存し直すことです。画像のふりをしたファイルや、画像の中に紛れ込ませたデータを取り除けます。

    Webサーバー側で、アップロードディレクトリでのスクリプト実行を無効化するのも有効です。

    ○ アップロードディレクトリで PHP を動かさない例（Apache）

    # アップロードディレクトリで PHP を動かさない例（Apache）
<Directory "/var/www/html/uploads">
    php_admin_flag engine off
</Directory>

    可能なら、そもそも公開配下に置かない方が安全です。

    補足：この設定が効く環境

    php_admin_flag engine off は、PHP を Apache のモジュール（mod_php）として動かしている場合の設定です。現在よく使われる PHP-FPM（PHP を Apache とは別のプロセスで動かす方式）の構成では効かないため、そのディレクトリでは PHP へ処理を渡す設定（ハンドラ）を外すなど、構成に合わせた方法が必要です。この点からも「公開配下に置かない」方が確実です。こうした多層の守りの考え方は 71 セキュリティ基礎「深層防御」 を参照してください。

    6.3 ファイルダウンロード時の対策

    対策説明
    Content-Type を正しく設定する拡張子や用途に応じた正しい MIME タイプを返す
    X-Content-Type-Options: nosniff を指定するコンテンツスニッフィングを防ぐ
    必要に応じて Content-Disposition を設定する表示が不要なら attachment でダウンロード強制

    ○ ダウンロード配信のヘッダ例（概念）

    // ✅ ダウンロード配信のヘッダ例（概念）
$file = '/var/www/data/uploads/' . $safeName;
$mime = 'image/jpeg';  // 実際はファイル種別に応じて設定

header('Content-Type: ' . $mime);
header('X-Content-Type-Options: nosniff');
header('Content-Disposition: attachment; filename="download.jpg"');
readfile($file);

    header() はレスポンスヘッダを出力する関数、readfile() はファイルの中身をそのままレスポンスとして送る関数です。readfile() は中身を「送るだけ」なので、ファイルが PHP スクリプトであっても実行されません。なお、$safeName は利用者の入力をそのまま使わず、データベースなどで管理している保存名を使います（そうしないとディレクトリ・トラバーサルの原因になります。ファイルアクセスとディレクトリトラバーサル を参照）。

    【防御の層】

アップロード時: 危険な拡張子を入れない / 非公開に保存する
        ＋
ダウンロード時: 正しい Content-Type / nosniff / attachment
        ↓
スクリプト実行も XSS も起きにくくなる

    関連：アップロードフォームと CSRF

    アップロードフォームそのものも CSRF（ログイン中の利用者に意図しないリクエストを送らせる攻撃）の対象になります。フォームには CSRF トークンが必要です。詳しくは CSRF「ファイルアップロードフォームでの CSRF 攻撃」 を参照してください。

    7.PDF の FormCalc によるコンテンツハイジャック

    PDF には、フォーム計算などに使う FormCalc という仕組み（Adobe の PDF フォームで使える簡易スクリプト言語）があります。これを悪用すると、コンテンツハイジャック（表示内容の乗っ取り）が起きる場合があります。

    7.1 何が起きるか

    悪意のある PDF を、ページ内の object や embed（HTML の中に別のファイルを埋め込んで表示するためのタグ）で埋め込み表示すると、PDF 内のスクリプト的な機能が動き、親ページの表示や操作に影響する ことがあります。

    【攻撃のイメージ】

1. 攻撃者が悪意ある PDF をアップロードする
2. サイトが object / embed でその PDF をページ内表示する
3. PDF 内の FormCalc 等が動き、画面上の情報を書き換えたり奪ったりする

    通常の XSS とは経路が違いますが、「ユーザーが信頼しているページ上で、意図しない表示・操作が起きる」点では近い被害です。

    7.2 対策

    対策説明
    PDF はブラウザ内で開かずダウンロードを強制するContent-Disposition: attachment で保存させる
    PDF を object / embed では開けない仕組みにするページ内埋め込み表示をやめる、または禁止する

    ✕ 危険な表示方法

    <embed src="/files/report.pdf">
<object data="/files/report.pdf"></object>
→ ページ内で PDF が動き、FormCalc 等が実行されうる

    ○ 安全寄りの方法

    Content-Disposition: attachment でダウンロードさせる
または、信頼できる専用ビューアを経由して、スクリプト無効化して表示する

    レスポンス例です。

    Content-Type: application/pdf
X-Content-Type-Options: nosniff
Content-Disposition: attachment; filename="report.pdf"

    「便利だからページ内で PDF を見せたい」という要件があっても、ユーザーがアップロードした PDF をそのまま埋め込む のは避けます。どうしても表示が必要なら、サーバー側で無害化・変換する、スクリプトを無効にしたビューアを使う、別オリジン（ドメインを分けた配信専用のサイト）で隔離する、などの追加対策が必要です。

    補足：2026年時点の状況

    FormCalc によるコンテンツハイジャックは、ブラウザの中で Adobe Reader のプラグイン が PDF を表示していた時代に問題になったものです。現在の主要ブラウザは、プラグイン（NPAPI）の仕組み自体を廃止し、ブラウザ内蔵の PDF ビューア（Chrome・Edge の PDFium、Firefox の PDF.js など）で表示します。これらの内蔵ビューアは FormCalc を実行しないため、この攻撃が主要ブラウザでそのまま成立する可能性は低くなっています。ただし、PDF には JavaScript などの機能もあり、利用者がダウンロードして PDF 専用アプリで開く場合のリスクは残ります。「利用者がアップロードした PDF を、自サイトと同じオリジンで埋め込み表示しない」 という原則は今も有効です。

    8.まとめ

    問題本質対策の要点
    アップロードへの DoS資源を使い果たされるサイズ・回数制限、監視
    サーバー側スクリプト実行実行可能ファイルが公開場所に置かれる許可リストで拡張子制限、非公開保存、実行無効化
    ダウンロードによる XSS誤った Content-Type で HTML として実行される正しい Content-Type、nosniff、attachment
    PDF 偽装 HTMLPDF のつもりが HTML として動く同上。拡張子だけで判断しない
    PDF FormCalc埋め込み PDF がページを乗っ取るダウンロード強制、object/embed で開かない

    ファイルアップロード安全の基本

    1. 許可リストで拡張子を厳しく制限し、保存名はサーバーが決める
    2. アップロード先は公開ディレクトリにしない（アプリ経由で配信する）
    3. ダウンロード時は正しい Content-Type と nosniff を付ける
    4. 表示が不要なファイルは Content-Disposition: attachment でダウンロードさせる
    5. ユーザー投稿の PDF を object / embed で埋め込まない

    9.理解度チェック

    Q1. アップロードファイルによるサーバー側スクリプト実行が起きる、典型的な2つの条件は何ですか？

    ① アップロードしたファイルが 公開ディレクトリに保存される（URL で直接アクセスできる）こと、② 保存後のファイル名に .php などのサーバースクリプトの拡張子を指定できる ことです。どちらか一方でも防げば、攻撃は成立しにくくなります。

    Q2. 「.php だけ禁止する」チェックが不十分なのはなぜですか？

    拒否リスト方式は抜け道が多いからです。.php5 .phtml などの別の拡張子、.PHP のような大文字、shell.php.jpg のような二重拡張子などで回避されることがあります。必要な拡張子だけを通す 許可リスト 方式にし、大文字小文字をそろえて判定します。

    Q3. アップロード時にブラウザが送ってくる Content-Type: image/jpeg を信じて「画像だ」と判断してよいですか？

    よくありません。 アップロード時の Content-Type はブラウザ（利用者側）が申告する値で、攻撃者は自由に書き換えられます。ファイル名の見た目や申告された種類だけを信じず、サーバー側で拡張子を許可リストで確認し、保存名もサーバーが決めます。

    Q4. ダウンロード時に付けるべき3つのレスポンスヘッダと、それぞれの役割を答えてください。

    Content-Type（中身の種類を正しく宣言する）、X-Content-Type-Options: nosniff（ブラウザに中身を推測させず、宣言どおり扱わせる）、Content-Disposition: attachment（画面に表示せず、ファイルとして保存させる）です。

    Q5. ファイル名が report.pdf なのに XSS が起きるのはどんな場合ですか？

    中身が HTML（+ JavaScript）で、サーバーが text/html などの誤った Content-Type で返す場合や、Content-Type が曖昧でブラウザが HTML と推測する場合です。中身の扱いを決めるのは主に Content-Type であり、拡張子だけでは安全になりません。

    Q6. 小さなファイルを大量にアップロードされると、ディスク容量に余裕があっても困るのはなぜですか？

    ファイル1個ごとに使う管理情報 inode の数に上限があり、それを使い果たすと新しいファイルを作れなくなるからです。サイズ上限だけでなく、回数・頻度の制限や監視も必要です。

    Q7. 利用者がアップロードした PDF を embed や object でページ内に表示するのを避けるべきなのはなぜですか？

    PDF 内の FormCalc などの機能が動き、親ページの表示や操作に影響する（コンテンツハイジャック）おそれがあるからです。Content-Disposition: attachment でダウンロードさせるか、どうしても表示するなら無害化・スクリプト無効のビューア・別オリジンでの隔離などを行います。
