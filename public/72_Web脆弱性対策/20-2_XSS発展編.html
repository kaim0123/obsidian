    XSS発展編：属性・JavaScript内のXSS

    XSS の基本では、HTML の本文（要素内容）に出力するときのエスケープを学びました。このページでは、href / src 属性・イベントハンドラ・script 要素など 「どこに出力するか（出力コンテキスト）」 によって必要な対策が変わる点を解説します。JavaScript にデータを安全に渡す方法（data 属性・インライン JSON）と、エラーメッセージの表示の注意点も扱います。

    もとにしたノート：20_インジェクション/02_XSS発展編（徳丸本6章）

    ひとことで言うと

    同じユーザー入力でも、HTML 本文・属性・URL・JavaScript のどこに出すかで「危ない文字」や「危ない値」が変わります。HTML エスケープだけで済むのは本文と（引用符で囲んだ）属性値までです。URL は スキームを検証し、JavaScript には コードとして埋め込まず、データとして渡す のが基本です。

    1.HTMLエスケープの概要とコンテキスト

    HTMLエスケープ は、特殊文字を HTML として解釈されない形式に変換する処理です。仕組みと基本的な使い方は XSSの基本 で学びました。発展編では 「どこに出力するか（コンテキスト）」 によって必要な対策が変わる点が重要です。コンテキスト とは、出力した文字列がブラウザに「何として」読まれる場所か、という意味です（HTML の文章として、URL として、JavaScript のコードとして、など）。

    1.1 エスケープ対象の文字（おさらい）

    文字エスケープ後理由
    <&lt;タグ開始の防止
    >&gt;タグ終了の防止
    "&quot;属性値からの脱出防止
    '&#x27;属性値からの脱出防止
    &&amp;実体参照の防止

    実体参照 とは &lt; のように & で始まる「文字の別名」の書き方です。& 自体もエスケープしておかないと、入力が意図せず別の文字に化けてしまいます。

    1.2 コンテキスト別エスケープの原則

    同じユーザー入力でも、出力場所によって必要なエスケープが異なります。

    出力場所必要な対策詳しくは
    HTML本文HTMLエスケープXSSの基本
    HTML属性HTML属性エスケープ ＋ 引用符で囲む5章
    URL（href等）URLエンコード ＋ スキーム検証2〜4章
    JavaScriptJSエスケープ / JSON による安全な受け渡し6〜9章

    URLエンコード は、URL の中で特別な意味を持つ文字（/ ? & # など）や日本語を %E3%81%82 のような % 付きの形に変換する処理です。スキーム は URL の先頭の https: や javascript: の部分で、「この URL をどう扱うか」を決めます。

    重要

    HTMLエスケープだけでは href 属性や JavaScript 内 の XSS を防げない場合があります。以降の各章でコンテキストごとの対策を学びます。

    2.href属性やsrc属性のXSS

    <a href="..."> や <img src="..."> など、URL を受け取る属性 にユーザー入力を出力すると、HTMLエスケープだけでは不十分なことがあります。

    2.1 典型的な脆弱なコード

    ✕ 脆弱：href にユーザー入力をそのまま出力

    <!-- ❌ 脆弱：href にユーザー入力をそのまま出力 -->
<a href="<?= $url ?>">リンク</a>

<!-- 攻撃入力: javascript:alert(document.cookie) -->
<a href="javascript:alert(document.cookie)">リンク</a>

    <?= ... ?> は PHP で「値をそのまま HTML に書き出す」書き方です。攻撃入力には < や " が1文字も含まれていないため、HTMLエスケープをしても 何も変わらず、リンクをクリックした瞬間にスクリプトが動きます。

    ✕ 脆弱：src にユーザー入力

    <!-- ❌ 脆弱：src にユーザー入力 -->
<img src="<?= $imageUrl ?>">

<!-- 攻撃入力: javascript:alert(1) や onerror イベントを利用したペイロード -->

    ペイロード とは、攻撃のために送り込む中身（攻撃文字列）のことです。

    2.2 なぜ HTMLエスケープだけでは足りないか

    問題説明
    javascript: スキームURL として解釈され、クリックでスクリプトが実行される
    data: スキームBase64 エンコードされた HTML/JS を埋め込める
    属性からの脱出エスケープ漏れで " により属性を閉じ、イベントハンドラを注入

    Base64 は、任意のデータを英数字と記号だけの文字列に変換する方式です。data:text/html;base64,... のように書くと、URL の中に HTML ファイルそのものを入れられます。

    補足：現在のブラウザでの挙動

    <img src="javascript:..."> でスクリプトが動いたのは古い IE などで、現在の主要ブラウザでは実行されません。また data: URL へのリンク（ページ全体の移動）も、現在の主要ブラウザはブロックします。ただし <a href>・<iframe src>・<form action> の javascript: はいまも実行されますし、src でも 属性からの脱出による onerror の注入 は成立します。ブラウザの挙動に頼らず、次の対策をとってください。

    2.3 対策の要点

    1. URL として妥当か検証 する
    2. 許可するスキームを限定 する（http: / https: のみ等）
    3. HTML属性エスケープ も併用する
    4. 可能なら サーバー側で URL を組み立て、ユーザー入力はパスやクエリの一部だけに限定

    3.URLを生成する場合の対策

    ユーザー入力から URL を動的に生成する場合、次の手順で安全に処理します。

    3.1 安全な URL 生成の手順

    1. ユーザー入力を URL の「部品」として扱う（URL 全体を信頼しない）
    2. スキーム（http/https）をサーバー側で固定
    3. パス・クエリ値は URL エンコードする
    4. 完成した URL を属性に出力するときは HTML 属性エスケープ

    パス は URL のうちホスト名の後ろの /search の部分、クエリ は ?q=... の部分です。

    3.2 例：検索結果へのリンク

    ✕ 脆弱：URL 全体をユーザー入力から構成

    // ❌ 脆弱：URL 全体をユーザー入力から構成
$url = $_GET['redirect'];
echo '<a href="' . htmlspecialchars($url) . '">移動</a>';
// javascript: スキームを htmlspecialchars しても href として実行される

    ○ 安全：スキームとホストは固定、パスのみユーザー入力

    // ✅ 安全：スキームとホストは固定、パスのみユーザー入力
$path = $_GET['path'];
$safePath = '/' . ltrim(rawurlencode($path), '/');
echo '<a href="https://example.com' . htmlspecialchars($safePath, ENT_QUOTES, 'UTF-8') . '">移動</a>';

    htmlspecialchars は PHP の HTML エスケープ関数、rawurlencode は URL エンコード関数です。ENT_QUOTES を付けると " と ' の両方がエスケープされます。https://example.com を固定で前に付けているので、入力が javascript:... でも単なるパスの一部になり、スクリプトにはなりません。

    ○ JavaScript でクエリパラメータを安全に付加

    // ✅ JavaScript でクエリパラメータを安全に付加
const keyword = encodeURIComponent(userInput);
const url = `https://example.com/search?q=${keyword}`;

    encodeURIComponent は JavaScript の URL エンコード関数で、& や # もエンコードするため、入力でクエリの区切りを書き換えられることもありません。

    3.3 許可するスキーム

    スキーム用途ユーザー入力への許可
    https:通常のリンク✅（検証後）
    http:非暗号化リンク△（本番では https 推奨）
    javascript:スクリプト実行❌ 禁止
    data:埋め込みデータ❌ 原則禁止
    vbscript:旧IE向け❌ 禁止

    ポイント：「禁止リスト」ではなく「許可リスト」で

    表の ❌ を1つずつ弾く書き方（ブラックリスト）だと、JavaScript:（大文字）や前後の空白・制御文字など、表記ゆれで抜けられることがあります。「https: と http: だけを通す」 という許可リスト（ホワイトリスト）方式で判定してください。

    4.リンク先のドメイン名のチェック

    リダイレクト機能や「外部リンク」機能では、リンク先のドメインを検証 しないとフィッシングや XSS の入口になります。リダイレクト とは、サーバーがブラウザに「このURLへ移動して」と指示して別ページへ飛ばすことです。

    4.1 危険なパターン：オープンリダイレクト

    オープンリダイレクト は、URL パラメータで指定された任意のサイトへ飛ばしてしまう脆弱性です。信頼されたドメインのリンクに見えるため、フィッシング（偽サイトへの誘導）に悪用されます。詳しくは リダイレクトとHTTPヘッダインジェクション で扱います。

    ✕ 脆弱：任意 URL へリダイレクト

    // ❌ 脆弱：任意 URL へリダイレクト
header('Location: ' . $_GET['url']);
// 攻撃者が ?url=https://evil.com/phishing 等を仕込める

    4.2 ドメイン名チェックの方法

    ホワイトリスト方式（推奨）：許可するホスト名（ドメイン名）をあらかじめ列挙し、それ以外を拒否します。

    PHP の例（ノートのコード）

    $allowedHosts = ['example.com', 'www.example.com', 'api.example.com'];
$url = parse_url($_GET['url']);

if (!in_array($url['host'], $allowedHosts, true)) {
    die('許可されていないリンク先です');
}
header('Location: ' . $url);

    補足：上の PHP コードの誤り

    parse_url は URL を部品ごとに分けた 配列 を返すので、最後の header('Location: ' . $url) は URL ではなく Array という文字列を出力してしまいます（PHP 8 では警告も出ます）。また、スキームを確認していないので javascript://example.com/... のような値も通ります。元の文字列を保持し、スキームも確認する形にします。

    $raw = $_GET['url'] ?? '';
$url = parse_url($raw);

if (!is_array($url)
    || !in_array($url['scheme'] ?? '', ['https', 'http'], true)
    || !in_array($url['host'] ?? '', $allowedHosts, true)) {
    die('許可されていないリンク先です');
}
header('Location: ' . $raw);

    ○ JavaScript の例

    function isAllowedUrl(url) {
  try {
    const parsed = new URL(url);
    const allowed = ['example.com', 'www.example.com'];
    return allowed.includes(parsed.hostname)
      && (parsed.protocol === 'https:' || parsed.protocol === 'http:');
  } catch {
    return false;
  }
}

    new URL() はブラウザ標準の URL 解析機能で、URL として読めない文字列なら例外を投げるため、catch で false を返しています。ホスト名とスキーム（protocol）を 両方 確認している点が大切です。

    4.3 チェックのポイント

    項目注意
    ホスト名evil.com と example.com.evil.com を区別
    スキームjavascript: や data: を拒否
    相対 URL//evil.com（プロトコル相対）も検証対象
    IDN（国際化ドメイン）見た目似たドメイン（同形異義字）への注意

    example.com.evil.com は「example.com」という文字を含んでいますが、実際の持ち主は evil.com です。「文字列に example.com が含まれるか」で判定すると突破されるので、ホスト名の 完全一致 で比べます。IDN は日本語などを使えるドメイン名で、キリル文字の「а」とラテン文字の「a」のように見た目がそっくりな文字（同形異義字）で偽ドメインを作られることがあります。

    4.4 相対 URL の扱い

    <!-- 攻撃入力: //evil.com/phishing -->
<a href="//evil.com/phishing">クリック</a>
<!-- 現在のスキーム（https）が付き、https://evil.com へ誘導 -->

    // で始まる URL は プロトコル相対 URL と呼ばれ、「今のページと同じスキームで、別のホストへ」という意味になります。/ で始まっていれば自サイト内だろう、という思い込みは危険です。

    対策

    外部リンクには 絶対 URL のみ許可 し、ドメインをホワイトリストで検証する。

    5.イベントハンドラのXSS

    イベントハンドラ属性（onclick、onerror、onmouseover 等）は、「クリックされたら」「画像の読み込みに失敗したら」などのタイミングで、属性値を JavaScript として実行する属性です。ここにユーザー入力が入ると、HTMLエスケープをすり抜けて XSS が成立することがあります。

    5.1 典型的な攻撃

    ✕ 脆弱：イベントハンドラにユーザー入力

    <!-- ❌ 脆弱 -->
<img src="invalid" onerror="<?= $userInput ?>">

<!-- 攻撃入力: alert(document.cookie)// -->
<img src="invalid" onerror="alert(document.cookie)//">

    属性値がそのまま JavaScript のコードになるので、< や " を使わない攻撃入力なら HTMLエスケープは何の役にも立ちません。

    ✕ 属性値からの脱出

    <!-- ❌ 属性値からの脱出 -->
<div title="<?= $input ?>">テキスト</div>

<!-- 攻撃入力: " onmouseover="alert(1)" x=" -->
<div title="" onmouseover="alert(1)" x="">テキスト</div>

    こちらは普通の title 属性ですが、入力の " で属性値が閉じられ、新しく onmouseover 属性が作られています。" を &quot; にエスケープしていれば防げるパターンです。

    5.2 イベントハンドラを使ったペイロード例

    属性例
    onerror<img src=x onerror=alert(1)>
    onmouseover" onmouseover="alert(1)
    onclick<a href="#" onclick="alert(1)">
    onload<body onload=alert(1)>

    5.3 対策

    対策説明
    イベントハンドラ属性を使わないJavaScript は外部ファイルまたは <script> で addEventListener を使う
    HTML属性エスケープ" ' < > & をエスケープ
    引用符で属性値を囲む囲まないと脱出しやすい
    CSPscript-src でインラインスクリプトを制限

    引用符で囲まない属性値（title=<?= $input ?>）は、空白1つ で次の属性を書き足せてしまうため、" のエスケープだけでは防げません。CSP の設定は CSP を参照してください。

    ○ 安全：イベントハンドラ属性を使わず JS で登録

    <!-- ✅ 安全：イベントハンドラ属性を使わず JS で登録 -->
<img id="avatar" src="<?= htmlspecialchars($url, ENT_QUOTES, 'UTF-8') ?>">
<script>
  document.getElementById('avatar').addEventListener('error', handleError);
</script>

    addEventListener は「この要素でこのイベントが起きたらこの関数を呼ぶ」と JavaScript 側で登録する方法です。ユーザー入力がコードの中に入る余地がありません。なお src は URL のコンテキストなので、2章 のスキーム検証もあわせて行います。

    どうしてもイベントハンドラ属性の中で文字列として値を渡す場合（onclick="init('…')"）は、JavaScript の文字列としてのエスケープ → HTML 属性としてのエスケープ の2段階が必要です。仕組みは 7.3 の図で説明します。

    6.Script要素のXSS

    <script> タグの 中身 や src 属性 にユーザー入力を含めると、最も危険な XSS になります。

    6.1 script 要素内への直接埋め込み

    ✕ 非常に危険

    <!-- ❌ 非常に危険 -->
<script>
  var username = '<?= $name ?>';
</script>

<!-- 攻撃入力: '; alert(document.cookie); // -->
<script>
  var username = ''; alert(document.cookie); //';
</script>

    入力の ' で文字列リテラル（'...' で囲まれた文字列の値）が閉じられ、; の後ろが新しい命令として実行されます。末尾の // は「ここから行末までコメント」という意味で、残った '; を無効にして文法エラーを避けています。

    HTMLエスケープは <script> 内では機能しない 場合があります（ブラウザは script 内容を HTML としてパースしないため）。パース とは、文字列を文法に従って読み解くことです。script 要素の中では &#x27; のような実体参照が元の文字に戻されないので、HTML の道具は役に立ちません。一方で </script> という文字の並びだけは HTML として認識され、そこで script 要素が終わってしまいます。

    6.2 script の src 属性

    ✕ 脆弱：src にユーザー入力

    <!-- ❌ 脆弱：src にユーザー入力 -->
<script src="<?= $scriptUrl ?>"></script>

<!-- 攻撃者が悪意ある JS ファイルの URL を指定 -->

    6.3 対策

    対策説明
    ユーザー入力を script 内に埋め込まない原則として禁止
    外部 JS ファイルを使うロジックは .js ファイルに分離
    src は固定または検証済み URL のみホワイトリスト
    CSP信頼できるソースのみ script 実行を許可

    7.JavaScriptの文字列リテラルの動的生成の対策

    サーバー側で JavaScript の 文字列リテラルを動的生成 するのは XSS の温床です。動的生成 とは、リクエストごとにプログラムで JavaScript のコードを組み立てることです。どうしてもデータを JS に渡す必要がある場合の安全な方法を学びます。

    7.1 危険なパターン

    ✕ サーバーが JS コードを文字列連結で生成

    // ❌ サーバーが JS コードを文字列連結で生成
var msg = '<?= $message ?>';
eval('showMessage("' + userInput + '")');

    eval は、文字列を JavaScript のコードとして実行する関数です。ユーザー入力が混ざった文字列を渡すと、入力がそのままコードになります。

    ✕ エスケープ漏れ1文字で突破される

    // ❌ エスケープ漏れ1文字で突破される
echo "<script>var data = '" . addslashes($input) . "';</script>";
// addslashes だけでは Unicode や改行等で不十分な場合がある

    addslashes は ' " \ の前に \ を付ける PHP の関数です。文字列からは抜け出せなくなりますが、入力に </script> が含まれると script 要素そのものが終わってしまい、その後ろに好きなタグを書けます。

    7.2 なぜ HTMLエスケープや addslashes だけでは不十分か

    手法限界
    HTMLエスケープ<script> 内では期待通り効かない
    addslashesJS の文脈を完全にはカバーしない
    ブラックリスト新しい回避手法が次々と登場

    7.3 2つの文法が重なる場所では、エスケープも2段階

    イベントハンドラ属性の中の文字列は、HTML の属性値 であり、同時に JavaScript の文字列リテラル でもあります。ブラウザは外側（HTML）から順に読み解くので、サーバーでは内側（JavaScript）から順にエスケープします。

    この2段階を毎回正しく行うのは難しく、1つ漏れるだけで突破されます。そこで、そもそも JavaScript のコードの中にデータを書かない 方法が勧められています。

    7.4 安全な代替手段

    1. Script 要素の外部でパラメータを定義（8章）
    2. インライン JSON による方法（9章）
    3. API で JSON を取得（fetch 等）

    fetch は JavaScript からサーバーへリクエストを送る標準の関数です。データを別のリクエストで JSON として受け取れば、HTML や JS のコードに値を埋め込む必要がなくなります。

    8.Script要素の外部でパラメータを定義してJavaScriptから参照する方法

    <script> タグの 外 にデータを置き、JavaScript から読み取る方法です。JS 文字列リテラルへの直接埋め込みを避けられます。HTML 属性に出力するだけなので、必要なのは慣れた HTML属性エスケープだけ になります。

    DOM（Document Object Model）は、ブラウザが HTML を読み込んで作る、JavaScript から操作できる部品の木構造です。

    8.1 方法1：data 属性を使う

    data 属性 は data- で始まる、自由に名前を付けてデータを持たせられる HTML の属性です。

    ○ 安全：data 属性に HTML エスケープして出力

    <!-- ✅ 安全：data 属性に HTML エスケープして出力 -->
<div id="user-data"
     data-username="<?= htmlspecialchars($username, ENT_QUOTES, 'UTF-8') ?>"
     data-email="<?= htmlspecialchars($email, ENT_QUOTES, 'UTF-8') ?>">
</div>

<script>
  const el = document.getElementById('user-data');
  const username = el.dataset.username;  // エスケープ済みの文字列として取得
  const email = el.dataset.email;
</script>

    補足：「エスケープ済みの文字列」ではなく「元の文字列」が返ります

    コード中のコメントは「エスケープ済みの文字列として取得」となっていますが、実際には HTML パーサーが &lt; などを元に戻すので、el.dataset.username は 入力された元の文字列（< を含むならそのまま）です。安全なのは「コードとして解釈されない」からです。取り出した値を innerHTML（文字列を HTML として差し込むプロパティ）に入れると、そこで改めて XSS になります。画面に出すときは textContent を使ってください。

    8.2 方法2：hidden の input 要素

    type="hidden" の input は、画面に表示されない入力欄です。CSRF 対策のトークン（CSRF のページで扱います）などを置くのによく使います。

    <input type="hidden" id="csrf-token"
       value="<?= htmlspecialchars($token, ENT_QUOTES, 'UTF-8') ?>">

<script>
  const token = document.getElementById('csrf-token').value;
</script>

    8.3 方法3：meta 要素

    <meta name="csrf-token" content="<?= htmlspecialchars($token, ENT_QUOTES, 'UTF-8') ?>">

    JavaScript からは document.querySelector('meta[name="csrf-token"]').content のようにして読み取ります。

    8.4 ポイント

    ポイント説明
    HTML属性エスケープENT_QUOTES で " ' をエスケープ
    引用符で囲む属性値は必ず " または ' で囲む
    JS 側では DOM API で取得文字列連結で JS コードを生成しない

    DOM API とは、getElementById や dataset のように、JavaScript から DOM を読み書きするための標準の関数・プロパティのことです。

    9.インラインJSONによる方法

    インライン JSON とは、<script type="application/json"> 等を使い、構造化データを JSON 形式 でページに埋め込む方法です。JavaScript から JSON.parse で安全に読み取れます。JSON は {"username": "taro", "count": 42} のような、データをやり取りするための書式です。data 属性より、複数の値や入れ子のデータをまとめて渡したいときに向いています。

    「インラインJSONP」という表記について

    原文の「インラインJSONP」は インライン JSON の意味で使われることが多いです。JSONP（<script src="...?callback=...">）は別の仕組みで、XSS リスクも異なります（9.4 で比較します）。

    9.1 基本的な書き方

    ○ 安全：JSON として埋め込み（実行されない）

    <!-- ✅ 安全：JSON として埋め込み（実行されない） -->
<script type="application/json" id="app-data">
<?= json_encode($data, JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT) ?>
</script>

<script>
  const jsonText = document.getElementById('app-data').textContent;
  const data = JSON.parse(jsonText);
  console.log(data.username);
</script>

    PHP での json_encode 例

    // PHP での json_encode 例
$data = ['username' => $username, 'count' => 42];
$json = json_encode($data, JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT);
echo '<script type="application/json" id="app-data">' . $json . '</script>';

    json_encode は PHP の配列を JSON の文字列に変換する関数です。| でつないだフラグ（オプション）で、変換のしかたを指定しています。

    9.2 JSON_HEX フラグの意味

    フラグ効果
    JSON_HEX_TAG< > を \u003C 等に変換（</script> 突破防止）
    JSON_HEX_AMP& をエスケープ
    JSON_HEX_APOS' をエスケープ
    JSON_HEX_QUOT" をエスケープ

    \u003C は JSON（と JavaScript）での < の別表記です。HTML パーサーからは </script> に見えないので script 要素が途中で閉じられず、JSON.parse の後には元の < に戻ります。

    9.3 なぜ安全か

    1. type="application/json" → ブラウザは JavaScript として実行しない
    2. json_encode → JS の文法を壊す文字をエスケープ
    3. JSON.parse → 文字列として正しく復元

    9.4 JSONP との違い（注意）

    JSONP は、<script src> なら別オリジンのファイルも読み込めることを利用して、別サイトのデータを関数呼び出しの形（fn({...})）で受け取る古い手法です。オリジンについては 受動的攻撃と同一オリジンポリシー、現在の主流である CORS は CORSの仕組み を参照してください。

    インライン JSONJSONP
    目的同一ページ内でデータを渡すクロスオリジンでデータ取得
    形式<script type="application/json"><script src="api?callback=fn">
    XSS リスクエンコードすれば低いcallback 名の注入等に注意
    現状✅ 推奨△ レガシー（CORS が主流）

    10.エラーメッセージからの情報漏洩

    XSS 対策と並んで、エラーメッセージの出力 も表示処理の重要な問題です。詳細すぎるエラーは 情報漏洩 につながり、攻撃の手がかりを与えます。例外処理の考え方そのものは ログ不足・SSRF・例外処理、ログの残し方は セキュアな運用とログ出力 で扱っています。ここでは表示処理（XSS）とのつながりを中心に見ます。

    10.1 漏洩しやすい情報

    情報攻撃者へのメリット
    スタックトレースファイルパス、行番号、使用ライブラリが分かる
    SQLエラーメッセージテーブル名、カラム名、DB の種類
    OS / ミドルウェアのバージョン既知脆弱性の exploit に利用
    内部 IP アドレスネットワーク構成の推測
    ユーザー入力のそのまま表示反射型 XSS の原因にもなる

    スタックトレース はエラーが起きるまでに呼ばれた関数の一覧、exploit は脆弱性を突くための攻撃コードのことです。SQL エラーの情報が攻撃にどう使われるかは SQLインジェクション で扱います。

    10.2 危険な例

    ✕ 脆弱：DB エラーをそのまま表示

    // ❌ 脆弱：DB エラーをそのまま表示
try {
    $db->query($sql);
} catch (PDOException $e) {
    echo 'エラー: ' . $e->getMessage();
    // → "Table 'users' doesn't exist" 等が漏洩
}

    ✕ 脆弱：ユーザー入力をエラーメッセージに含める

    // ❌ 脆弱：ユーザー入力をエラーメッセージに含める
echo '「' . $_GET['name'] . '」は見つかりませんでした';
// → 反射型 XSS: name=<script>alert(1)</script>

    10.3 安全なエラーハンドリング

    ○ ユーザーには汎用メッセージのみ

    // ✅ ユーザーには汎用メッセージのみ
try {
    $db->query($sql);
} catch (PDOException $e) {
    error_log($e->getMessage());  // サーバーログに詳細を記録
    echo '処理中にエラーが発生しました。しばらくしてからお試しください。';
}

    ○ ユーザー入力をエラーに含める場合もエスケープ

    // ✅ ユーザー入力をエラーに含める場合もエスケープ
$name = htmlspecialchars($_GET['name'], ENT_QUOTES, 'UTF-8');
echo '「' . $name . '」は見つかりませんでした';

    10.4 ベストプラクティス

    項目推奨
    本番環境詳細エラーを画面に表示しない
    ログ詳細はサーバー側ログに記録
    エラー IDユーザーには「エラーID: ABC123」のみ表示し、サポート時に照合
    デバッグモード開発環境のみ詳細表示を有効化
    カスタムエラーページ500 エラー用の汎用ページを用意

    10.5 XSS との関連

    よくある落とし穴

    • エラーメッセージにユーザー入力をそのまま含める → 反射型 XSS の典型パターン
    • 「〇〇が見つかりません」等のメッセージ → 必ず HTML エスケープしてから出力

    反射型 XSS（リクエストに含まれた入力がそのままレスポンスに返ってくるタイプ）の仕組みは XSSの基本 を参照してください。

    12.理解度チェック

    Q1. <a href="..."> にユーザーが入力した URL を出すとき、htmlspecialchars でエスケープしていれば安全ですか？

    安全ではありません。 javascript:alert(1) には HTML の特殊文字が含まれないので、エスケープしても変わらず、クリックで実行されます。スキームを https: / http: に限定する検証 が必要です。できればスキームとホストはサーバー側で固定し、入力はパスやクエリの部品だけにします。

    Q2. リダイレクト先を「URL に example.com が含まれるか」で判定するのはなぜ危険ですか？

    https://example.com.evil.com/ のように、攻撃者のドメインに example.com という文字を含められるからです。URL を解析して取り出したホスト名を、許可リストと 完全一致 で比べます。スキームと、//evil.com のようなプロトコル相対 URL も確認します。

    Q3. <div title="<?= $input ?>"> に " onmouseover="alert(1)" x=" が入力されると何が起きますか？ 防ぐには？

    入力の " で title 属性が閉じられ、onmouseover 属性が新しく作られて、マウスを乗せるとスクリプトが実行されます。ENT_QUOTES 付きの HTML 属性エスケープで " を &quot; にし、属性値を必ず引用符で囲めば防げます。

    Q4. var name = '<?= addslashes($name) ?>'; のように script 内で addslashes を使っても危険なのはなぜですか？

    addslashes は引用符の前に \ を付けるだけなので、入力に </script> が含まれると HTML パーサーがそこで script 要素を終わらせてしまい、その後ろに任意のタグを書けます。改行なども JS の文脈では問題になります。script 内に埋め込まず、data 属性やインライン JSON で渡すのが安全です。

    Q5. インライン JSON が安全に値を渡せる理由を3つ挙げてください。

    ① type="application/json" なのでブラウザが JavaScript として実行しない、② json_encode（JSON_HEX_TAG などのフラグ付き）が </script> や引用符など文法を壊す文字をエスケープする、③ JSON.parse がコードではなくデータとして正しく復元する、の3つです。

    Q6. data 属性から el.dataset.username で取り出した値を innerHTML に入れて表示してもよいですか？

    いけません。 dataset が返すのはエスケープが戻された元の文字列なので、innerHTML に入れると HTML として解釈され、XSS になります。表示には textContent を使います。

    Q7. DB エラーのメッセージを画面に出すことの問題と、代わりにどうすべきかを答えてください。

    テーブル名・カラム名・DB の種類などが漏れ、SQLインジェクションなどの攻撃の手がかりになります。ユーザーには汎用メッセージ（必要ならエラーID）だけを表示し、詳細は error_log などでサーバー側のログに記録します。詳細表示は開発環境のデバッグモードに限ります。
