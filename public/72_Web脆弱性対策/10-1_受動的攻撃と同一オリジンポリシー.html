    10 ブラウザのセキュリティモデル

    受動的攻撃と同一オリジンポリシー

    ブラウザは、怪しいサイトを開いてもパソコンや他のサイトのデータが簡単には盗まれないよう、いくつもの「しきり」を持っています。このページでは、攻撃の分け方（能動的攻撃と受動的攻撃）、プログラムを閉じ込める サンドボックス、ブラウザの最も基本的な防御である 同一オリジンポリシー、そして iframe とクロスドメインアクセスまでを、徳丸本（『体系的に学ぶ 安全なWebアプリケーションの作り方』）第2章に沿って解説します。

    もとにしたノート：10_ブラウザのセキュリティモデル/01_受動的攻撃と同一オリジンポリシー（徳丸本2章）

    ひとことで言うと

    ブラウザは 「別のサイト（別のオリジン）のデータは、JavaScript から勝手に読ませない」 というルールで利用者を守っています。これが同一オリジンポリシーです。ポイントは 「送ること」はできても「レスポンスを読むこと」はできない という点です。

    第1章では HTTP とセッション管理の基礎を学びました。第2章では、ブラウザが備える セキュリティの仕組み と、同一オリジンポリシー について解説します。

    1.能動的攻撃と受動的攻撃

    Webのセキュリティでは、攻撃の種類を 能動的（アクティブ） と 受動的（パッシブ） に分けて考えます。

    注意：「受動的攻撃」には2つの意味があります

    この言葉は分野によって指すものが違うので、混同しないようにしてください。

    • ネットワークセキュリティでの意味（このノートの 1.1〜1.3 の説明）：能動的攻撃＝通信を改ざん・なりすましする攻撃、受動的攻撃＝通信を 盗聴するだけ の攻撃。
    • 徳丸本 第2章での意味：能動的攻撃＝攻撃者が サーバーを直接攻撃する（例：SQLインジェクション）、受動的攻撃＝攻撃者が罠を仕掛け、被害者のブラウザに攻撃を実行させる（例：XSS、CSRF、罠サイト）。

    徳丸本の意味では、XSS や CSRF は 受動的攻撃 に分類されます。また、同一オリジンポリシーは この意味での受動的攻撃（罠サイトの JavaScript が、被害者のブラウザ経由で別サイトの情報を盗む）を防ぐための仕組みです。1.4 で詳しく整理します。

    1.1 能動的攻撃（Active Attack）

    攻撃者が 通信やシステムに直接手を加える 攻撃です。

    例説明
    SQLインジェクション悪意あるSQL（データベースへの命令文）を送り込んでDBを操作
    XSS（クロスサイトスクリプティング）悪意あるスクリプトをページに埋め込む
    CSRF（クロスサイトリクエストフォージェリ）ユーザーに意図しないリクエストを送らせる
    中間者攻撃（MITM）通信の途中に割り込み、改ざん・なりすましをする
     
    ユーザー ──リクエスト──→ 攻撃者（改ざん） ──→ サーバー
         ←──レスポンス── 攻撃者（改ざん） ←──

    特徴： 攻撃者が能動的に介入する。改ざんやなりすましが起きる。

    ※ 上の表のうち XSS と CSRF は、徳丸本の分類では次の「受動的攻撃」側に入ります（1.4 参照）。

    1.2 受動的攻撃（Passive Attack）

    攻撃者が 通信を傍受・監視するだけ で、内容を改ざんしない攻撃です。

    例説明
    盗聴（スニッフィング）ネットワーク上の通信を盗み見る
    トラフィック分析通信の量・パターンから情報を推測
    公開Wi-Fiでの傍受暗号化されていない通信を読む
     
    ユーザー ──リクエスト──→ サーバー
         ↑
      攻撃者（盗み見るだけ、改ざんしない）

    特徴： 攻撃者は「見るだけ」。通信内容が漏洩する。

    1.3 対策の違い

    攻撃の種類主な対策
    能動的攻撃入力値検証、CSRFトークン、WAF（Webアプリ向けのファイアウォール）、認可チェック
    受動的攻撃HTTPS（TLS暗号化）、機密情報をURLに載せない

    HTTPS を強制する仕組み（HSTS など）は セキュリティヘッダ、暗号化の不備そのものは インジェクションと暗号化の不備 で扱います。

    1.4 徳丸本での「能動的／受動的」

    徳丸本 第2章でいう分け方は、「攻撃者が誰を経由して攻撃するか」に注目したものです。

    能動的攻撃

    攻撃者が サーバーに直接 攻撃リクエストを送ります。

    例：SQLインジェクション、OSコマンドインジェクション

    受動的攻撃

    攻撃者は 罠（罠サイト・罠メールなど）を仕掛けて待つ だけ。罠を踏んだ 被害者のブラウザ が、攻撃者の代わりに攻撃を実行します。

    例：XSS、CSRF、罠サイトからの情報窃取

    受動的攻撃では被害者のブラウザが「運び屋」にされるので、ブラウザ側にも防御の仕組みが必要 になります。その代表がこのあと説明するサンドボックスと同一オリジンポリシーです。XSS は XSSの基本、CSRF は CSRF のページで詳しく扱います。

    1.5 本章との関係

    • 同一オリジンポリシー → ノートの分類では「能動的攻撃（他サイトからの不正アクセス）を防ぐ」。徳丸本の分類では、罠サイトによる 受動的攻撃 を防ぐ仕組みにあたります
    • HTTPS → 受動的攻撃（盗聴）を防ぐ
    • CORS → 同一オリジンポリシーの制限を、安全な範囲で緩和する（→ CORSの仕組み）

    2.サンドボックス

    サンドボックス（Sandbox） とは、プログラムを 隔離された安全な環境 で実行する仕組みです。砂場（sandbox）の中で遊ぶと外に影響しないイメージです。

    2.1 日常生活での例え

    サンドボックス

    子ども用の砂場。中で遊んでも、外の道路には影響しない。

    ブラウザのサンドボックス

    Webページの JavaScript。中で動いても、PCのファイルには触れない。

    2.2 ブラウザのサンドボックスが制限すること

    制限説明
    ローカルファイルへのアクセスユーザーのPC上のファイルを読めない
    他サイトのデータ同一オリジンポリシーにより制限
    システムコマンドの実行OSの機能を直接操作できない
    任意のネットワーク接続一部の通信はブラウザが制御

    2.3 iframe の sandbox 属性

    <iframe>（ページの中に別のページを埋め込む要素。4. で説明）に sandbox 属性を付けると、埋め込んだページの権限をさらに制限できます。

    例：sandbox 属性の付け方 
    <!-- スクリプト実行もフォーム送信も禁止 -->
<iframe src="https://untrusted.example.com" sandbox></iframe>

<!-- スクリプトは許可、フォーム送信は禁止 -->
<iframe src="https://example.com/widget" sandbox="allow-scripts"></iframe>

    値を何も書かずに sandbox だけを付けると、ほぼすべてが禁止されます。そこから必要なものだけを allow-* で許可していく「デフォルト拒否」の考え方です。

    sandbox の値許可する操作
    （属性のみ）ほぼ全て禁止
    allow-scriptsJavaScriptの実行
    allow-formsフォーム送信
    allow-same-origin同一オリジンとして扱う（本来のオリジンのまま扱う。付けないと「どのオリジンとも一致しない特殊なオリジン」扱いになる）
    allow-popupsポップアップの表示

    注意：allow-scripts と allow-same-origin の組み合わせ

    allow-scripts と allow-same-origin を 同時に付けると サンドボックスを突破される可能性があるため、信頼できないコンテンツには慎重に使います。特に埋め込むページが親と同じオリジンの場合、中のスクリプトが親から自分の sandbox 属性を取り除けてしまいます。

    危険な例：信頼できないページに両方を許可 
    <iframe src="https://untrusted.example.com" sandbox="allow-scripts allow-same-origin"></iframe>
    安全な例：必要な権限だけを許可 
    <iframe src="https://untrusted.example.com" sandbox="allow-scripts"></iframe>

    3.同一オリジンポリシー

    同一オリジンポリシー（Same-Origin Policy, SOP） は、ブラウザの最も基本的なセキュリティ機能のひとつです。

    3.1 オリジンとは

    オリジン は、Webサイトの「出身地」を表す識別子です。次の3つの組み合わせで決まります。

    オリジン = プロトコル + ドメイン + ポート番号
    https://example.com:443/page1
  │       │          │
  │       │          └─ ポート（HTTPSは443、省略可）
  │       └─ ドメイン
  └─ プロトコル（スキーム）

    用語メモ

    プロトコル（スキーム） は通信の方式（http や https）、ドメイン はサーバーの名前（example.com）、ポート番号 はサーバー内の「受付窓口の番号」です。ポートを省略すると、HTTP なら 80、HTTPS なら 443 とみなされます。

    3.2 同じオリジン vs 異なるオリジン

    URL AURL B同じ？理由
    https://example.com/ahttps://example.com/b○ 同じパスはオリジンに含まれない
    https://example.comhttp://example.com× 違うプロトコルが違う
    https://example.comhttps://api.example.com× 違うドメインが違う
    https://example.comhttps://example.com:8080× 違うポートが違う

    3つのうち 1つでも違えば別オリジン です。サブドメイン（api.example.com）でも、親ドメインとは別オリジンになる点に注意しましょう。

    3.3 同一オリジンポリシーのルール

    あるオリジンのページから、別オリジンのリソースに JavaScript で自由にアクセスすることを禁止する

    https://myapp.com のページ
  → https://myapp.com/api/users  ○ OK（同一オリジン）
  → https://api.example.com/users × NG（異なるオリジン）

    3.4 なぜ必要か

    同一オリジンポリシーがなければ、悪意あるサイトが次のようなことをできます。

    1. ユーザーが evil.com を開く（銀行サイトにはログイン済み）
    2. evil.com の JavaScript が bank.com にリクエストを送る
    3. ブラウザが bank.com の Cookie（ログイン状態を覚えておくための小さなデータ）を自動送信
    4. 口座情報などが evil.com に漏洩

    同一オリジンポリシーにより、evil.com の JavaScript から bank.com のレスポンスを読むこと がブロックされます。

    3.5 同一オリジンポリシーが守るもの

    操作クロスオリジン
    <img src="..."> で画像を 表示○ 可能
    <script src="..."> でJSを 実行○ 可能（ただし中身は読めない）
    <form> で 送信○ 可能（ただしレスポンスは読めない）
    fetch() / XHR で レスポンスを読む× 原則ブロック
    別サイトの DOM に アクセス× 原則ブロック

    XHR は XMLHttpRequest の略で、fetch() より前からある JavaScript の通信機能です。DOM は、ページの中身（HTML）を JavaScript から操作するための木構造のことです。

    ここが重要

    「送ること」と「レスポンスを読むこと」は別、という点が重要です。同一オリジンポリシーは 読み取り を止めますが、送信そのもの は止めません。だからこそ、勝手に送信させる CSRF には、サーバー側で別の対策（CSRFトークンなど）が必要になります。

    4.iframe

    iframe（Inline Frame） は、Webページの中に 別のWebページを埋め込む HTML要素です。

    <iframe src="https://maps.example.com/embed" width="600" height="400"></iframe>

    4.1 用途

    • Google Maps の地図埋め込み
    • YouTube 動画の埋め込み
    • 決済フォーム（Stripe 等）の埋め込み
    • 広告の表示

    4.2 同一オリジンポリシーとの関係

    iframe に読み込まれたページは 独立したオリジン として扱われます。

    親ページ: https://myapp.com
iframe内: https://widget.example.com

→ 親ページの JavaScript から iframe 内の DOM にはアクセスできない
    できない例：クロスオリジンの iframe 
    // クロスオリジンの iframe にはアクセス不可
const iframe = document.querySelector('iframe');
iframe.contentDocument; // エラー（SecurityError）
    できる例：同一オリジンの iframe 
    // 同一オリジンの iframe なら OK
const iframe = document.querySelector('iframe');
iframe.contentDocument.body.innerHTML = '更新';

    親と iframe のオリジンが違っても安全にやり取りしたい場合は、5.2 の表にある postMessage を使います。

    4.3 セキュリティ上の注意

    リスク対策
    クリックジャッキングX-Frame-Options: DENY または Content-Security-Policy: frame-ancestors
    悪意あるコンテンツの埋め込みsandbox 属性で権限を制限
    フィッシング信頼できるソースのみ iframe で読み込む

    クリックジャッキング とは、自分のサイトを透明な iframe で罠サイトに重ねられ、ユーザーが知らないうちにボタンを押させられる攻撃です。フィッシング は、本物そっくりの偽画面でパスワードなどをだまし取る手口です。X-Frame-Options や frame-ancestors の設定方法は セキュリティヘッダ と CSP で解説します。

    5.クロスドメインアクセス

    クロスドメインアクセス とは、異なるドメイン（オリジン）間 でリソースやデータにアクセスすることです。

    5.1 現代のWebで必要になる理由

    フロントエンド（ブラウザで動く画面側）と API（データを返すサーバー側）が分離された構成が一般的になりました。

    フロントエンド: https://myapp.com
バックエンドAPI: https://api.myapp.com   ← ドメインが違う = クロスドメイン
    https://myapp.com の JavaScript
  → fetch('https://api.myapp.com/users')
  → 同一オリジンポリシーにより、レスポンスの読み取りがブロックされる

    自分たちのサービス同士でも、オリジンが違えばブラウザは区別せずにブロックします。そこで「このオリジンからなら読んでよい」と安全に許可する手段が必要になります。

    5.2 クロスドメインアクセスの方法

    方法説明
    CORSサーバーが許可を明示（最も一般的） → CORSの仕組み
    JSONP旧来の手法（<script> タグを利用、非推奨）
    プロキシ同一オリジンのサーバー経由で中継
    postMessageiframe 間の安全なメッセージング

    JSONP は、クロスオリジンでも実行できる <script> タグ（3.5 の表を参照）の性質を利用して、データを JavaScript の関数呼び出しとして受け取る方法です。誰でもそのデータを読めてしまうなどの問題があるため、今は CORS を使います。

    6.まとめ

    トピック要点
    能動的攻撃改ざん・なりすまし。入力検証・CSRF対策等（徳丸本の意味では「サーバーを直接攻撃」）
    受動的攻撃盗聴・監視。HTTPS が主な対策（徳丸本の意味では「罠を仕掛けて被害者のブラウザに攻撃させる」）
    サンドボックスプログラムを隔離実行。iframe の sandbox 属性
    同一オリジンポリシー異なるオリジン間の JS アクセスを制限するブラウザの基本防御
    iframeページ埋め込み。クロスオリジンでは DOM アクセス不可
    クロスドメインアクセス異なるオリジン間の通信。CORS 等で安全に許可

    このページの要点

    • オリジン＝プロトコル＋ドメイン＋ポート。1つでも違えば別オリジン
    • 同一オリジンポリシーは 「送信」ではなく「読み取り」 を止める
    • 「受動的攻撃」は分野によって意味が違う。徳丸本では XSS・CSRF のような 罠型の攻撃 を指す
    • iframe は sandbox 属性で権限を絞り、自サイトが埋め込まれる側ならヘッダでクリックジャッキングを防ぐ

    次の CORSの仕組み（徳丸本 第3章）では、クロスドメインアクセスの代表的な解決策である CORS について詳しく学びます。

    7.理解度チェック

    Q1. https://example.com と https://example.com:8080 は同じオリジンですか？

    違うオリジンです。 プロトコルとドメインは同じですが、ポート番号（443 と 8080）が違います。オリジンはプロトコル・ドメイン・ポートの3つがすべて一致して初めて「同じ」になります。

    Q2. evil.com のページから bank.com へフォームを送信することは、同一オリジンポリシーで止められますか？

    止められません。 同一オリジンポリシーが止めるのは、別オリジンの レスポンスを読むこと です。送信そのものはできてしまうため、勝手に送信させる CSRF にはサーバー側の対策が別途必要です。

    Q3. 徳丸本の分類で、XSS は能動的攻撃と受動的攻撃のどちらですか？理由も答えてください。

    受動的攻撃です。 攻撃者は罠（罠サイトや罠リンク）を用意するだけで、実際に攻撃スクリプトを動かすのは罠を踏んだ 被害者のブラウザ だからです。一方、ネットワークセキュリティでの「受動的攻撃」は盗聴を指すので、文脈に注意しましょう。

    Q4. 信頼できない外部ページを iframe で埋め込むとき、sandbox="allow-scripts allow-same-origin" を避けるべきなのはなぜですか？

    この2つを同時に許可すると、埋め込まれたページのスクリプトがサンドボックスを 突破できる可能性 があるからです。必要な権限だけ（例：allow-scripts のみ）を許可するのが基本です。

    Q5. フロントエンド https://myapp.com から API https://api.myapp.com のレスポンスを読みたいとき、代表的な方法は何ですか？

    CORS です。API サーバーが「https://myapp.com からの読み取りを許可する」とレスポンスヘッダで明示します。ほかにプロキシや、iframe 間なら postMessage がありますが、JSONP は非推奨です。詳しくは CORSの仕組み で学びます。
