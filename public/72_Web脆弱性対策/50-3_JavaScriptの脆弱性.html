    50 API・JavaScript

    JavaScriptの脆弱性

    SPA やリッチな画面では、HTML を組み立てる処理の多くが ブラウザ上の JavaScript に移っています。このページでは徳丸本第20章をもとに、クライアント側の JavaScript で起きやすい4つの問題 ── DOM Based XSS・Webストレージの不適切な使用・postMessage 呼び出しの不備・オープンリダイレクト（JavaScript 版） ── とその対策を解説します。

    もとにしたノート：50_API・JavaScript/03_JavaScriptの問題（徳丸本20章）

    ひとことで言うと

    「ブラウザの中にも外部入力の入り口がある」 のが、この章の要点です。URL の # 以降、Webストレージ、他のウィンドウからのメッセージは、どれも サーバーを通らない外部入力 です。

    SPA（Single Page Application）は、最初に1枚のページを読み込んだあと、画面の切り替えを JavaScript で行う作りのアプリです。React や Vue で作る画面の多くがこれにあたります。

    1.JavaScript で起きる問題の全体像

    第20章では、クライアント側（ブラウザ側）の JavaScript で起きやすい次の問題を解説します。

    問題概要
    DOM Based XSSJavaScript が外部の値をそのまま DOM に書き込み、スクリプトが実行される
    Webストレージの不適切な使用localStorage などに秘密情報を置き、XSS で盗まれる・改ざんされる
    postMessage呼び出しの不備ウィンドウ間のメッセージで、送信先・送信元を確認しない
    オープンリダイレクトJavaScript で、外部から指定された URL へ遷移させる

    DOM（Document Object Model）とは、ブラウザが読み込んだ HTML を、JavaScript から読み書きできる「部品の木」の形にしたものです。JavaScript は DOM を書き換えることで、画面の文字や要素を変えています。

    第5・6章の XSS（XSSの基本・XSS発展編）は、主に サーバーが返す HTML にスクリプトが混ざる問題でした。本章は、サーバーを通らずにブラウザの中だけで完結する 点がポイントです。サーバー側のログやエスケープでは気づけません。

    2.DOM Based XSS

    XSS そのものの仕組み（データが命令に化ける・Cookie を盗まれる など）は XSSの基本「データと命令」 で解説しました。ここでは、JavaScript が DOM に書き込む場面 で起きる XSS を見ていきます。

    2.1 仕組み

    外部から来た値（ソース）が、HTML やスクリプトとして解釈される場所（シンク）に、そのまま渡されると起きます。ソース（source）は「水の出どころ」、シンク（sink）は「流し込む先」というイメージです。

    ソース（外部から来る値）              シンク（解釈される場所）
location.hash / location.search  ─┐
document.referrer                 ├──▶  innerHTML / document.write / eval / location.href
postMessage の data               │
Web ストレージの値                ─┘

    location.hash は URL の # 以降、location.search は ? 以降、document.referrer は「どのページから来たか」を表す値です。どれも攻撃者が URL やリンク元を用意すれば自由に決められます。

    危険な例：URL の # 以降を innerHTML に入れる 
    // ❌ https://example.com/#<img src=x onerror=alert(document.cookie)>
const name = decodeURIComponent(location.hash.slice(1));
document.getElementById('greet').innerHTML = `こんにちは、${name}さん`;
    • # 以降（フラグメント）は サーバーに送られない ので、サーバー側では検知も対策もできません。
    • 反射型 XSS（XSSの基本「反射型XSS」）と同じく、攻撃者は罠の URL を踏ませるだけです。

    2.2 原因になる機能

    原因危険なシンク
    HTML タグが有効になる DOM 操作innerHTML・outerHTML・insertAdjacentHTML・document.write()・document.writeln()・jQuery の $(html) や .html()
    文字列をスクリプトとして実行する機能eval()・setTimeout(文字列)・setInterval(文字列)・new Function(文字列)
    URL が未検証location.href・a 要素の href・iframe の src（javascript: スキームが動く）
    XMLHttpRequest / fetch の URL が未検証取ってきた HTML を画面に入れる処理で、取得先を攻撃者のサーバーに変えられる

    XMLHttpRequest と fetch は、JavaScript からサーバーへ通信してデータを取ってくるための機能です（fetch は新しい書き方）。

    2.3 innerHTML・document.write による XSS

    危険な例：HTML として解釈される 
    // ❌ HTML として解釈される
el.innerHTML = name;
document.write('<p>' + name + '</p>');
    安全な例：テキストとして入れる／要素を作ってから値を入れる 
    // ✅ テキストとして入れる（タグは文字のまま表示される）
el.textContent = name;

// ✅ 要素を作ってから値を入れる
const p = document.createElement('p');
p.textContent = name;
el.appendChild(p);

    textContent は中身を HTML として解釈せず、ただの文字として表示します（インジェクションと暗号化の不備「XSS：脆弱なコードと安全なコード」 でも同じ比較をしています）。

    どうしても HTML を入れる必要がある（リッチテキストなど）場合は、DOMPurify などのサニタイザ を通します。サニタイザ とは、HTML から script 要素や onerror などの危険な部分を取り除き、安全な部分だけを残す道具です。

    安全な例：サニタイザを通してから入れる 
    import DOMPurify from 'dompurify';
el.innerHTML = DOMPurify.sanitize(html);

    2.4 eval・setTimeout・Function による XSS

    危険な例：外部の値がスクリプトとして実行される 
    // ❌ 外部の値がスクリプトとして実行される
setTimeout('showMessage("' + msg + '")', 1000);
eval('var config = ' + location.hash.slice(1));
    安全な例：関数を渡す／JSON.parse を使う 
    // ✅ 関数を渡す / JSON.parse を使う
setTimeout(() => showMessage(msg), 1000);
const config = JSON.parse(decodeURIComponent(location.hash.slice(1)));
    • 文字列形式で外部からの値を渡さない のが原則です。eval は使わずに済む設計にします（Evalインジェクションの対策 と同じ考え方）。
    • JSON.parse はデータとして読むだけで、中のコードを実行しません。

    2.5 javascript スキームによる XSS

    スキーム とは、URL の先頭の https: や mailto: の部分です。javascript: スキームの URL は、開くと後ろに書いたスクリプトが実行されます。属性値の XSS としての説明は XSS発展編「href属性やsrc属性のXSS」 を参照してください。

    危険な例：URL パラメータをそのままリンク先・遷移先にする 
    // ❌ ?url=javascript:alert(document.cookie) で実行される
const url = new URLSearchParams(location.search).get('url');
link.href = url;
location.href = url;
    安全な例：スキームを http / https に限る 
    // ✅ スキームを http / https に限る
function isSafeUrl(value) {
  try {
    const url = new URL(value, location.origin);
    return url.protocol === 'http:' || url.protocol === 'https:';
  } catch {
    return false;
  }
}
if (isSafeUrl(url)) link.href = url;
    • JavaScript:（大文字）や前後の空白・改行で、単純な文字列比較は回避されます。new URL() でパースしてから protocol を見る のが確実です。
    • React などのフレームワークは {name} の埋め込みを自動でエスケープしますが、href={url} の スキームは確認しません。dangerouslySetInnerHTML も同様に危険です。

    補足：React 19 以降の動き

    React 19 では、href などに javascript: で始まる URL を渡すと、React がそれを実行しない値に置き換えてブロックするようになりました。ただし、古い版の React やほかのフレームワーク、data: など別の危険な値、location.href への代入などには効きません。上の isSafeUrl のように自分で検証する方針は変わりません。

    2.6 XMLHttpRequest の URL 未検証

    危険な例：# 以降をそのまま取得先にする 
    // ❌ #/page/news のようなパスを想定しているが、#//attacker.example/evil.html でも取得してしまう
const path = location.hash.slice(1);
fetch(path)
  .then((r) => r.text())
  .then((html) => { main.innerHTML = html; });
    • 攻撃者のサーバーが CORS（別オリジンからの読み取りを許可するしくみ）を許可して悪意ある HTML を返すと、そのまま実行されます。
    • 認証ヘッダやトークンを付けて送る処理なら、トークンを攻撃者に送ってしまう 問題にもなります。

    //attacker.example/… のように // で始まる書き方は、「今のページと同じスキームで、別のホストへ」という意味になります。そのため、パスのつもりで渡した値が外部サーバーへの通信に化けてしまいます。

    安全な例：許可したページ名だけを受け付ける 
    // ✅ 許可したページ名だけを受け付け、URL は自分で組み立てる
const PAGES = ['news', 'about', 'faq'];
const page = location.hash.slice(1);
if (PAGES.includes(page)) {
  fetch(`/pages/${page}.json`).then(/* textContent で描画 */);
}

    2.7 Trusted Types（追加の防御）

    CSP（読み込んでよいスクリプトなどをブラウザに伝えるレスポンスヘッダ）に次の指定を加えると、innerHTML などに ただの文字列を渡すとエラー になります。危険なシンクの使い忘れをブラウザが止めてくれます（対応ブラウザのみ）。

    Content-Security-Policy: require-trusted-types-for 'script'

    Trusted Types は、「安全確認を通った値」だけをシンクに渡せるようにするしくみです。サニタイザなどを通した値だけが「信頼できる型」になり、そのまま書いた文字列ははじかれます。

    CSP 全体は CSP、他のヘッダは セキュリティヘッダ を参照してください。

    3.Webストレージの不適切な使用

    3.1 Webストレージとは

    ブラウザにデータを保存する仕組みで、localStorage（ずっと残る）と sessionStorage（タブを閉じると消える）があります。JavaScript から localStorage.setItem('key', 'value') のように読み書きします。

    3.2 クッキーと Webストレージの特徴

    項目クッキーlocalStoragesessionStorage
    データの区分けドメイン・パス単位オリジン単位オリジン + タブ単位
    有効期間Expires/Max-Age まで（無ければブラウザ終了まで）消すまでずっとタブを閉じるまで
    サーバーへの送信リクエストごとに自動で送られる送られない送られない
    JavaScript からのアクセスできる（HttpOnly なら不可）できるできる
    アクセス制御HttpOnly・Secure・SameSite で制限できる制限する仕組みがない制限する仕組みがない
    利用者から見えるか見える見える見える
    利用者が変更できるかできるできるできる

    オリジン は「スキーム＋ホスト＋ポート」の組み合わせです（受動的攻撃と同一オリジンポリシー「オリジンとは」）。

    ポイント

    Webストレージには HttpOnly にあたる仕組みがありません。同じオリジンで XSS が 1 つでもあれば、全部読まれます。Cookie の属性（クッキー出力にまつわる脆弱性・徳丸本第11章）は 74_セッション管理 フォルダで扱います。HttpOnly の効果は XSSの基本「クッキーに HttpOnly 属性を付与」、属性ごとの動きは CORSエラーの対処法とCookie でも触れています。

    3.3 Webストレージには何を保存してよいか

    保存してよい保存しない
    表示設定（テーマ・言語）、入力途中の下書き、画面の状態セッション ID、アクセストークン・リフレッシュトークン、個人情報、パスワード
    • 判断基準は 「XSS で盗まれても、利用者が改ざんしても困らないか」 です。
    • 利用者が自由に書き換えられるので、権限や価格などの判断に使わない。サーバー側で必ず確かめます。
    • ログイン状態は、HttpOnly・Secure・SameSite を付けた Cookie で持つのが基本です（トークンを localStorage と Cookie のどちらに置くかは 74_セッション管理 で扱います）。

    アクセストークン は API を呼ぶときに「ログイン済みの本人です」と示す通行証、リフレッシュトークン はアクセストークンを取り直すための、より長く使える通行証です。

    3.4 不適切な利用例

    例何が起きるか
    秘密情報を保存していたXSS で localStorage.getItem('token') を読まれ、攻撃者のサーバーに送られる
    XSS や postMessage で漏えい他のウィンドウから受けたメッセージに応じて、保存値を返してしまう
    XSS や postMessage で改ざん保存値を書き換えられ、次回の表示から攻撃が続く（ずっと残る XSS）
    Webストレージを経由した DOM Based XSS保存値を innerHTML で描画している。一度書き込まれると、URL を踏まなくても毎回発火する
    危険な例：保存値を HTML として描画する 
    // ❌ 保存値も「外部から来る値」として扱う
el.innerHTML = localStorage.getItem('nickname');
    安全な例：テキストとして描画する 
    // ✅
el.textContent = localStorage.getItem('nickname');

    サーバーのデータベースに保存されて毎回発火する 持続型XSS と似た状態が、ブラウザの中だけで起きると考えると分かりやすいです。

    4.postMessage 呼び出しの不備

    4.1 postMessage とは

    別のオリジンのウィンドウや iframe と、安全にメッセージをやり取りする ための仕組みです。同一オリジンポリシー（受動的攻撃と同一オリジンポリシー）で直接触れない相手と、決まった窓口だけで会話できます。iframe は、ページの中に別のページをはめ込んで表示する要素です（同ページ「iframe」）。

    // 送信側
otherWindow.postMessage(message, targetOrigin);

// 受信側
window.addEventListener('message', (event) => {
  // event.origin … 送信元のオリジン
  // event.data   … 受け取ったデータ
});
    引数・プロパティ意味
    message送るデータ（オブジェクトも送れる）
    targetOriginこのオリジンのウィンドウにだけ届ける。'*' は誰でも可
    event.origin受け取ったメッセージの送信元

    確認すべきことは、送信側の「誰に届けるか」と受信側の「誰から来たか」の2つです。

    4.2 メッセージ送信先の未確認

    危険な例：送信先を '*' にする 
    // ❌ iframe の中身が攻撃者のページに差し替えられていても、トークンが届く
iframe.contentWindow.postMessage({ token }, '*');
    安全な例：届けたい相手のオリジンを指定する 
    // ✅ 届けたい相手のオリジンを指定する
iframe.contentWindow.postMessage({ token }, 'https://widget.example.com');
    • window.open で開いたウィンドウや iframe は、途中で別のサイトに遷移していることがあります。
    • 秘密の情報を送るときは、必ず targetOrigin を指定 します。

    4.3 メッセージ送信元の未確認

    危険な例：どこから来たメッセージでも処理する 
    // ❌ どのサイトから来たメッセージでも処理してしまう
window.addEventListener('message', (event) => {
  document.getElementById('msg').innerHTML = event.data.html;
  localStorage.setItem('theme', event.data.theme);
});
    安全な例：送信元を完全一致で確かめ、データも検証する 
    // ✅ 送信元を完全一致で確かめ、データも検証する
const ALLOWED = 'https://parent.example.com';
window.addEventListener('message', (event) => {
  if (event.origin !== ALLOWED) return;
  if (typeof event.data?.text !== 'string') return;
  document.getElementById('msg').textContent = event.data.text;
});
    • 攻撃者のページは、あなたのページを iframe や window.open で開き、好きな内容のメッセージを送れます。
    • event.origin.includes('example.com') や startsWith は、https://example.com.attacker.example で回避されます。完全一致 で比べます。
    • 送信元が正しくても、data は外部からの値です。シンクに渡すときの注意は DOM Based XSS と同じです。

    5.オープンリダイレクト（JavaScript 版）

    サーバー側のリダイレクト（リダイレクトとHTTPヘッダインジェクション「オープンリダイレクト」）と同じ問題が、JavaScript の画面遷移でも起きます。被害（フィッシングへの誘導など）は同ページを参照してください。

    危険な例：URL パラメータの値へそのまま遷移する 
    // ❌ ログイン後に ?next=https://phishing.example/ へ飛ばされる
const next = new URLSearchParams(location.search).get('next');
location.href = next;

    さらに JavaScript 版では、?next=javascript:... で XSS にもなる 点に注意します（2.5 の javascript スキームと同じ仕組みです）。

    5.1 対策

    対策例
    リダイレクト先の URL を固定にするログイン後は必ず /mypage
    URL を直接指定せず、番号などで指定する?next=2 → 対応表で /settings に変換
    同じオリジンかを確かめる下のコード

    考え方はサーバー側の オープンリダイレクトの対策 と同じです。

    安全な例：自分のオリジン内のパスだけ許可する 
    // ✅ 自分のオリジン内のパスだけ許可する
function safeRedirect(next) {
  try {
    const url = new URL(next, location.origin);
    if (url.origin === location.origin) {
      location.href = url.pathname + url.search + url.hash;
      return;
    }
  } catch {}
  location.href = '/mypage';
}
    • //attacker.example（スキームなし）や /\attacker.example は、文字列の先頭が / でも外部に飛びます。new URL() で解決してから origin を比べる のが確実です。
    • javascript:... を渡した場合も、new URL() の結果の origin が自分のオリジンと一致しないため、/mypage に落ちます。

    6.共通の対策：ライブラリを最新に保つ

    jQuery・Angular・Vue などの古い版には、DOM Based XSS につながる脆弱性が見つかっているものがあります。

    • 使っているライブラリを把握し、npm audit（npm のパッケージに既知の脆弱性がないか調べるコマンド）や Dependabot（GitHub が依存ライブラリの更新を自動で提案する機能）で更新を追う。
    • CDN（スクリプトなどを配信する外部サーバー）から読むスクリプトには SRI（integrity 属性）を付け、改ざんされたファイルを実行しない。

    詳しくは 安全でない設計・設定ミス・古い部品「脆弱で古いコンポーネント」、SRI の書き方は サプライチェーンと整合性の不備「CDN の JavaScript には SRI を付ける」 を参照してください。

    7.対策の優先順位

    1. 外部の値は textContent / createElement で入れる。innerHTML・document.write・eval に渡さない（本質的対策）
    2. URL はパースしてスキームを http/https に限り、遷移先は同じオリジンか対応表で決める
    3. postMessage は targetOrigin を指定し、受信側で event.origin を完全一致で確かめる
    4. Webストレージに秘密情報を置かない。ログイン状態は HttpOnly Cookie で持つ
    5. HTML が必要なら DOMPurify、追加の防御に CSP・Trusted Types（保険）
    6. ライブラリを最新に保つ

    本章に共通する考え方は、「ブラウザの中にも外部入力の入り口がある」 ことです。URL のフラグメント、Webストレージ、他のウィンドウからのメッセージは、どれもサーバーを通らない外部入力です。サーバー側の対策だけで安心せず、JavaScript で DOM に書き込む・画面を遷移させる・データを保存する 場所を、サーバー側の出力と同じ目で点検します。

    8.まとめ

    トピック要点
    DOM Based XSSソース（location.hash など）→ シンク（innerHTML など）。サーバーを通らない
    危険なシンクHTML として解釈・文字列をスクリプト実行・未検証の URL・未検証の取得先
    安全な書き方textContent・createElement・関数渡し・JSON.parse・new URL() でスキーム確認
    WebストレージHttpOnly にあたる仕組みがない。秘密情報を置かず、保存値も外部入力として扱う
    postMessage送信側は targetOrigin を指定、受信側は event.origin を完全一致で確認
    オープンリダイレクト固定・番号指定・同一オリジン確認。JavaScript 版は XSS にもなる
    ライブラリnpm audit・Dependabot で更新、CDN には SRI

    9.理解度チェック

    Q1. DOM Based XSS が、サーバー側のログやエスケープでは気づけないのはなぜですか？

    ソースからシンクまでの処理が ブラウザの中だけで完結する からです。特に URL の # 以降（フラグメント）はサーバーに送られないので、サーバーは攻撃の文字列を一度も目にしません。

    Q2. 「ソース」と「シンク」とは何ですか？それぞれ例を2つずつ挙げてください。

    ソース は外部から来る値で、location.hash・location.search・document.referrer・postMessage の data・Webストレージの値などです。シンク は HTML やスクリプトとして解釈される場所で、innerHTML・document.write・eval・location.href などです。

    Q3. リンク先 URL のチェックで url.startsWith('javascript:') を拒否するだけでは不十分なのはなぜですか？

    JavaScript:（大文字）や前後の空白・改行などで、単純な文字列比較は回避されるからです。new URL() でパースしてから protocol が http: か https: かを確かめる、許可リスト方式にします。

    Q4. アクセストークンを localStorage に保存するのが危険なのはなぜですか？

    Webストレージには HttpOnly にあたる仕組みがなく、同じオリジンで XSS が1つでもあれば JavaScript からすべて読まれる からです。ログイン状態は HttpOnly・Secure・SameSite を付けた Cookie で持つのが基本です。

    Q5. postMessage の受信側で event.origin.includes('example.com') と確認するのは安全ですか？

    安全ではありません。 https://example.com.attacker.example のような攻撃者のオリジンでも通ってしまいます。event.origin !== 'https://parent.example.com' のように 完全一致 で比べ、さらに data の中身も検証します。

    Q6. iframe.contentWindow.postMessage({ token }, '*') の問題点は何ですか？

    送信先を '*'（誰でも可）にしているため、iframe の中身が攻撃者のページに差し替えられていてもトークンが届いてしまいます。'https://widget.example.com' のように、届けたい相手のオリジンを targetOrigin に指定します。

    Q7. 遷移先 next が / で始まっていれば自サイト内だと判断してよいですか？

    よくありません。 //attacker.example や /\attacker.example は先頭が / でも外部へ飛びます。new URL(next, location.origin) で解決してから origin を自分のオリジンと比べます。
