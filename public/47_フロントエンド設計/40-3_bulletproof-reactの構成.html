    40 ディレクトリ・モジュール構成

    bulletproof-react の構成 — Feature型構成を実務で運用する

    GitHub で公開されている React アプリの設計ガイド bulletproof-react（alan2207/bulletproof-react）のプロジェクト構成を読み、Feature型の構成を実務でどう運用するか を学びます。React 固有の書き方ではなく、構成の考え方 を取り出します。

    もとにしたノート：03_bulletproof-reactの構成

    ひとことで言うと

    bulletproof-react は Feature型構成の実践例 です。機能固有のコードは API も含めて features/<機能>/ に置き、機能どうしは import しない、依存は 共有 → 機能 → アプリ の一方向、という最小限のルールで崩れにくくします。FSD より軽量で、中規模の React アプリに取り入れやすい構成です。

    1.このページで扱うこと

    • bulletproof-react とは
    • トップレベルの構成と feature フォルダの中身
    • 依存の向きのルール（機能どうしを import しない、共有 → 機能 → アプリ）
    • barrel ファイルの扱いの変化
    • FSD との比較
    • 取り入れるときの判断

    React 固有の書き方は 32_React が本拠地です。Feature型の位置づけは ディレクトリ構成の比較 を参照してください。

    2.bulletproof-react とは

    bulletproof-react は、中〜大規模の React アプリを 崩れにくく作るための構成・規約のサンプル です。コードだけでなく、docs/ 以下にプロジェクト構成・状態管理・API 層・テスト・エラー処理などの方針が文章で書かれています。

    特定のライブラリを強制するものではなく、「こういう判断をした」という参考例として読むのが適切です。

    3.トップレベルの構成

    src/
├── app/          # アプリ層: ルート（routes/）、プロバイダ、ルーター
├── assets/       # 静的ファイル
├── components/   # アプリ全体で共有するコンポーネント
├── config/       # グローバル設定・環境変数
├── features/     # 機能ごとのモジュール ← 中心
├── hooks/        # 共有フック
├── lib/          # ライブラリを設定済みで再公開したもの
├── stores/       # グローバルな状態ストア
├── testing/      # テスト用ユーティリティ・モック
├── types/        # 共有の型
└── utils/        # 共有ユーティリティ

    機能に属さないもの だけがトップレベルに残り、機能固有のコードは features/ に入ります。

    4.feature フォルダの中身

    src/features/discussions/
├── api/          # API リクエストの宣言と、それを使うフック
├── assets/
├── components/   # この機能専用のコンポーネント
├── hooks/
├── stores/
├── types/
└── utils/
    • 必要なフォルダだけを作る（全部そろえる必要はない）
    • API 呼び出しを機能ごとに置く のが特徴。「どの機能がどのエンドポイントを使うか」がフォルダで分かる

    API 層の考え方は 37_HTTPクライアント・ユーティリティ のノート『03_APIレイヤーのフォルダ構成』と対応しています。

    5.依存の向きのルール

    bulletproof-react の中心となるルールは 2 つです。

    5.1 機能どうしを import しない

    ✕ NG：features/comments から features/discussions を import 
    import { DiscussionView } from '@/features/discussions/components/discussion-view';

    機能を組み合わせたいときは、上位のアプリ層（app/routes）で組み立て ます。

    5.2 共有 → 機能 → アプリ の一方向

      shared（components, hooks, lib, types, utils）
        ↓ 使われる
  features
        ↓ 使われる
  app

    共有コードは機能を知らず、機能はアプリ層を知りません。このルールは ESLint の import/no-restricted-paths で検査する方法が紹介されています（依存ルールの自動検査）。

    6.barrel ファイルの扱い

    barrel ファイル とは、フォルダの中身をまとめて再 export する index.ts のことです。以前のバージョンでは各 feature に index.ts を置き、そこから export する方針でした。現在のドキュメントでは、Vite 環境で tree shaking やパフォーマンスに悪影響が出ることがある ため、ファイルを直接 import する 方針に変わっています（tree shaking：使われていないコードをビルド時に取り除く最適化）。

    方針利点欠点
    barrel ファイルあり公開 API が明確（FSD はこちら）ビルド・開発サーバーが重くなることがある、循環参照の温床
    直接 importツールに優しい内部ファイルへの依存が生まれやすい（ルールで補う）

    どちらを選ぶ場合も、「外から使ってよいのはどれか」を決めて守る という目的は同じです。

    7.FSD との比較

    観点bulletproof-reactFSD
    分け方共有 / features / app の 3 段6 層 × スライス × セグメント
    機能の粒度業務機能（discussions, users）entity（もの）と feature（操作）を区別
    ルールの数少ない多い（その分明確）
    学習コスト低い高い
    向く場面中規模、React 中心のチーム大規模、長期運用、構成の標準化を重視

    bulletproof-react は Feature型に最小限のルールを足したもの、FSD は それをさらに層で細かく規格化したもの と捉えると整理しやすいです。

    8.取り入れるときの判断

    • そのまま真似る必要はない。features と「機能どうし import しない」ルールだけでも効果が大きい
    • lib/（設定済みライブラリの再公開）は、ライブラリ差し替え時の影響を 1 か所に閉じる良い習慣
    • testing/ を最初から置くと、モック・テストデータの置き場所で迷わない

    9.よくある誤解

    誤解1：「bulletproof-react のフォルダをすべてそのまま真似るべき」

    参考例として読みます。 特定のライブラリを強制するものではなく、「こういう判断をした」という例です。feature フォルダも必要なものだけ作れば十分で、features と「機能どうし import しない」ルールだけでも効果が大きいです。

    誤解2：「各 feature に index.ts（barrel）を置くのが常に正しい」

    現在の bulletproof-react は直接 import 寄りです。 Vite 環境で tree shaking やパフォーマンスに悪影響が出ることがあるためです。barrel の有無より、「外から使ってよいのはどれか」を決めて守ることが本来の目的です。

    誤解3：「機能 A の画面で機能 B の部品を使いたいなら、そのまま import すればよい」

    機能どうしは import しません。 組み合わせはアプリ層（app/routes）で行います。

    10.まとめ

    • bulletproof-react は Feature型構成の実践例。ドキュメントで方針まで読める
    • 機能固有のコードは features/<機能>/ に、API もその中に置く
    • 機能どうしは import しない、依存は 共有 → 機能 → アプリ の一方向
    • barrel ファイルは現在は非推奨寄り（ツールの都合）。目的は公開範囲を守ること
    • FSD より軽量で、中規模の React アプリに取り入れやすい
