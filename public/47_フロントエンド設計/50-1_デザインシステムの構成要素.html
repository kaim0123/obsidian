    50 デザインシステム・スタイリング

    デザインシステムの構成要素 — トークン・コンポーネント・ドキュメント・ガバナンス

    デザインシステム を「UI 部品集」ではなく、トークン・コンポーネント・ドキュメント・運用ルール からなる仕組みとして捉え、どこまで作るかを判断できるようにします。CSS の書き方や React での実装ではなく、何を共通化し、誰がどう守るか を扱います。

    もとにしたノート：01_デザインシステムの構成要素

    ひとことで言うと

    デザインシステムは トークン・コンポーネント・ドキュメント・ガバナンス の 4 層で、見た目と振る舞いの一貫性を 個人の注意力ではなく仕組みで 保つものです。トークンは プリミティブ → セマンティック の階層にし、部品はセマンティックだけを参照します。「いつ使うか」のドキュメントと変更のルールがないと形骸化します。

    CSS の書き方そのものは 22_CSS（ノート『CSS設計（BEM-OOCSS）』）、React でのコンポーネント実装は 32_React（ノート『10-4-Props設計』）が本拠地です。部品の外から見た使い方は Props は公開 API も参照してください。

    2.デザインシステムとは何か

    デザインシステムは、見た目と振る舞いの一貫性を、個人の注意力ではなく仕組みで保つ ためのものです。

      ┌──────────────────────────────────────────┐
  │ 4. ガバナンス（誰が変更し、どう広めるか）   │
  ├──────────────────────────────────────────┤
  │ 3. ドキュメント（使い方・原則・Do/Don't）   │
  ├──────────────────────────────────────────┤
  │ 2. コンポーネント（Button, Dialog, Table…） │
  ├──────────────────────────────────────────┤
  │ 1. デザイントークン（色・余白・文字・影…）   │
  └──────────────────────────────────────────┘
        下の層ほど変更の影響範囲が大きい
    よくある誤解実際
    UI キット（Figma ファイル）を作れば完成実装・ドキュメント・運用が揃って初めて機能する
    コンポーネントライブラリ = デザインシステムライブラリは 4 層のうち 1 層にすぎない
    一度作れば終わりプロダクトと一緒に 進化し続ける製品

    3.デザイントークン — 値に名前を付ける

    デザイントークン は、色や余白などの デザイン上の決定を名前付きの値 にしたものです。W3C の Design Tokens Community Group が共通フォーマット（JSON）の仕様化を進めています。

    トークンは 2〜3 階層に分けるのが定番です。

    階層例役割
    プリミティブ（基本値）blue-600: #2563eb使える値のパレット
    セマンティック（意味）color-action-primary: {blue-600}用途 に名前を付ける
    コンポーネントbutton-primary-bg: {color-action-primary}部品単位の上書き点（必要な場合のみ）
    ◯ セマンティックトークンを CSS 変数として公開する 
    :root {
  --color-action-primary: #2563eb;
  --color-text-default: #111827;
  --space-2: 8px;
}
[data-theme="dark"] {
  --color-action-primary: #60a5fa;
  --color-text-default: #f9fafb;
}

    判断のポイント

    コンポーネントは セマンティックトークンだけ を参照させます。プリミティブを直接使うと、ダークモードやブランド変更のときに全箇所を書き換えることになります。

    4.コンポーネントライブラリ — 何を共通部品にするか

    すべてを共通化すると、使われない汎用部品が増えます。3 回使われたら共通化 くらいの感覚で、次の順に揃えるのが現実的です。

    優先度対象理由
    高Button, Input, Select, Checkbox, Dialog使用頻度が高く、a11y の作り込みが難しい
    中Table, Tabs, Toast, Tooltip振る舞いの一貫性が UX に効く
    低画面固有のカード・レイアウト変更理由がプロダクト側にある

    a11y はアクセシビリティ（障害の有無や環境にかかわらず使えること）の略です。

    実装の選択肢は大きく 3 つです。

    方式例向く場面向かない場面
    既製ライブラリをそのまま使うMUI, Chakra UI早く作りたい・独自ブランド性が低い見た目を大きく変えたい
    Headless + 自前スタイルRadix UI, React Aria独自デザイン + a11y を確保したいスタイリングの工数を割けない
    コードを取り込んで所有shadcn/ui部品を自分たちで改変し続けたい更新の追従を自動化したい

    Headless（ヘッドレス）UI とは、見た目を持たず、キーボード操作やフォーカス管理などの振る舞いだけを提供する部品ライブラリです。振る舞いは Headless に任せ、見た目はトークンで統一する構成が、独自デザインと a11y を両立しやすい組み合わせです（アクセシビリティ）。

    5.ドキュメント — Storybook と使い分けの指針

    部品があっても いつ使うか が伝わらなければ、似た部品が再発明されます。

    • Storybook：部品ごとの状態（通常・hover・disabled・エラー）をカタログ化。ビジュアルリグレッション（画面の見た目が意図せず変わっていないかを画像比較で確かめるテスト）や a11y チェックのアドオンとも連携できる
    • 使い分けの指針：「Dialog と Drawer のどちらを使うか」「Primary ボタンは 1 画面 1 つ」など 判断ルール を書く
    • Do / Don't：良い例と悪い例を並べる
    // Button.stories.tsx — 状態ごとに 1 ストーリー
export const Primary = { args: { variant: "primary", children: "保存" } };
export const Disabled = { args: { variant: "primary", disabled: true, children: "保存" } };

    6.ガバナンス — 誰が変更し、どう広めるか

    ガバナンス とは、デザインシステムを誰がどう変更・管理するかという運用の決まりごとです。

    モデル内容向く規模
    中央集権型専任チームが全部品を管理大規模・複数プロダクト
    連邦型各チームの代表が共同で管理中規模・複数チーム
    兼任型プロダクトチームが片手間で管理小規模・1 プロダクト

    最低限決めておくことは次の 3 つです。

    1. バージョニング：共通パッケージなら SemVer（変更の大きさを「メジャー.マイナー.パッチ」で表すバージョンの付け方）と変更履歴（モノレポ）
    2. 追加の基準：新しい部品をライブラリに入れる条件
    3. 逸脱の扱い：画面側で上書きしてよい範囲（例：余白は可、色は不可）

    7.よくある誤解

    誤解1：「Figma の UI キットを作ればデザインシステムは完成」

    実装・ドキュメント・運用が揃って初めて機能します。 UI キットは見た目の素材にすぎず、コードの部品、使い分けの指針、変更のルールがないと現場で使われません。

    誤解2：「コンポーネントライブラリ = デザインシステム」

    ライブラリは 4 層のうち 1 層にすぎません。 その下にトークン、その上にドキュメントとガバナンスがあります。

    誤解3：「似た部品は全部、最初から共通部品にするべき」

    3 回使われたら共通化くらいで十分です。 何でも共通化すると使われない汎用部品が増えます。画面固有のカード・レイアウトは変更理由がプロダクト側にあるので、無理に共通化しません。

    誤解4：「一度作れば終わり」

    デザインシステムはプロダクトと一緒に進化し続ける製品です。 バージョニング・追加の基準・逸脱の扱いを決めて運用し続けます。

    8.まとめ

    • デザインシステムは トークン・コンポーネント・ドキュメント・ガバナンス の 4 層
    • トークンは プリミティブ → セマンティック の階層にし、部品はセマンティックだけ参照する
    • 共通部品は使用頻度と a11y の難しさで優先度を決め、画面固有の部品は無理に共通化しない
    • 「いつ使うか」のドキュメントと、変更のルールがないと形骸化する
