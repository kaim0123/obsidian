    20 コンポーネント設計

    Props はコンポーネントの公開 API

    コンポーネントを使う側から見えるのは Props だけです。このページでは、Props を 関数の引数 や モジュールの公開 API と同じように設計する考え方を学びます。名前の付け方、矛盾する組み合わせを型で防ぐ方法、制御・非制御の選び方、children とスロットによる拡張、Props が多すぎるときの見直しまでを扱い、使う側が迷わず、変更に強い部品のインターフェースを目指します。

    もとにしたノート：02_Propsはコンポーネントの公開API

    ひとことで言うと

    Props は部品と利用者の 契約 です。少なく・わかりやすく・間違えにくく を目指し、名前は利用者から見た意味で付け、見た目の値ではなく 意図（variant） を渡します。ありえない組み合わせは 判別可能なユニオン で型から消し、表示のバリエーションは children / スロット で吸収します。

    1.このページで扱うこと

    • Props は契約である — 良い API の性質
    • 名前と形 — 利用者の言葉で
    • 矛盾する組み合わせを型で防ぐ
    • 制御・非制御 — 状態を誰が持つか
    • 拡張に強くする — children とスロット
    • Props の数が多いときの見直し

    TypeScript での Props の型の書き方は（32_React のノート『10-4-Props設計』）が本拠地です。

    2.Props は契約である

    コンポーネントを使う側から見えるのは Props だけです。Props は部品と利用者の 契約（「こう渡せば、こう振る舞う」という約束）です。

      利用者 ──(Props)──▶ [ コンポーネント ] ──(イベント)──▶ 利用者
            公開 API       内部実装は隠す
    良い API の性質Props での意味
    少なく、わかりやすい必要な props だけを受け取る
    間違った使い方ができない矛盾する組み合わせを型で防ぐ
    内部を知らなくても使える実装の都合を props に出さない
    後から拡張しやすい既存の呼び出しを壊さずに追加できる

    46_メソッド設計 の「引数の設計」「情報隠蔽」と同じ原則が、そのまま Props に当てはまります。

    3.名前と形 — 利用者の言葉で

    Props の名前は 部品の中身ではなく、利用者から見た意味 で付けます。

    悪い例良い例理由
    datauser何のデータかわかる
    flagisDisabledboolean は is / has / can
    handleClickonSelectイベントは on + 利用者にとっての意味
    bgColor="#f00"variant="danger"見た目の値ではなく意図を渡す

    特に variant のように 意図を渡す 形にすると、デザインが変わっても利用側のコードは変わりません（デザイントークンとの接続は デザインシステムの構成要素 で扱います）。

    4.矛盾する組み合わせを型で防ぐ

    boolean の props が増えると、ありえない組み合わせが生まれます。

    ✕ 悪い例：isLoading と error が同時に true になりうる 
    // 悪い例: isLoading と error が同時に true になりうる
type Props = { isLoading: boolean; error?: string; data?: User[] };
    ◯ 良い例：状態を 1 つの判別可能なユニオンで表す 
    // 良い例: 状態を 1 つの判別可能なユニオンで表す
type Props =
  | { status: 'loading' }
  | { status: 'error'; error: string }
  | { status: 'success'; data: User[] };

    判別可能なユニオン（discriminated union）は、status のような共通の目印の値によって「どの形か」が 1 つに決まる型です。status: 'error' のときだけ error があり、'success' のときだけ data がある、という関係を型が保証します。

    パターン問題対策
    boolean の組み合わせisPrimary && isDanger が可能variant: 'primary' | 'danger'
    状態フラグの乱立loading と error が同時判別可能なユニオン
    片方だけ必要な propshref と onClick の両方を渡せるユニオンで排他にする

    5.制御・非制御 — 状態を誰が持つか

    入力系の部品では、値を部品の中で持つか、利用者が持つか を決める必要があります。

    非制御（uncontrolled）制御（controlled）
    値の持ち主部品の内部利用者（親）
    PropsdefaultValuevalue + onChange
    向く場面値を送信時に読むだけ入力に応じて他の UI が変わる
    向かない場面入力と連動する表示がある単純なフォームで記述が増える

    汎用部品では 両方に対応 し、value が渡されたら制御、なければ非制御として振る舞う設計がよく使われます（ネイティブの <input> と同じ方式）。

    6.拡張に強くする — children とスロット

    表示内容のバリエーションを props で増やし続けると、部品が肥大化します。

    ✕ 悪い例：表示のたびに props が増える 
    // 悪い例: 表示のたびに props が増える
<Card title="..." subtitle="..." icon="..." showFooter footerText="..." />
    ◯ 良い例：中身は children / スロットで利用者が組み立てる 
    // 良い例: 中身は children / スロットで利用者が組み立てる
<Card header={<CardTitle icon={<UserIcon />}>ユーザー</CardTitle>}>
  <UserProfile user={user} />
</Card>

    スロット は、部品の中に「ここに好きな要素を差し込める」口を用意する仕組みです。React では要素を受け取る props（header など）として表現します。

    手法向く場面向かない場面
    設定 props（title, icon）見た目を厳密に統一したいバリエーションが多い
    children中身を自由に差し込ませたい中身の構造を強制したい
    名前付きスロット（header, footer）差し込み口が複数ある差し込み口が 1 つだけ

    7.Props の数が多いときの見直し

    Props が 7〜10 個を超えたら、部品の責務が大きすぎないかを疑います。

    1. 一緒に変わる props をオブジェクトにまとめる（Parameter Object と同じ）
    2. 表示の差し込みは children / スロットに逃がす
    3. 役割が違うなら部品自体を分ける（分割粒度と境界）
    4. 部品を組み合わせる形（Compound）にする（コンポーネントパターンの比較）

    8.よくある誤解

    誤解1：「色やサイズは具体的な値で渡した方が柔軟」

    bgColor="#f00" のように見た目の値を渡すと、デザインが変わるたびに 利用側をすべて直す ことになります。variant="danger" のように 意図 を渡せば、色の変更は部品（とデザイントークン）の中だけで済みます。

    誤解2：「状態ごとに boolean の props を足していけばよい」

    boolean を足すほど、isLoading と error が同時に立つような ありえない組み合わせ が増えます。状態は 判別可能なユニオン 1 つで表し、型の段階で矛盾を消します。

    誤解3：「表示を変えたくなったら props を追加すればよい」

    title・subtitle・icon・footerText……と増やし続けると部品が肥大化します。中身のバリエーションは children / スロット で利用者に組み立ててもらい、Props が 7〜10 個を超えたら部品の責務そのものを見直します。

    9.まとめ

    • Props は部品の公開 API。少なく、わかりやすく、間違えにくく
    • 名前は利用者から見た意味で。見た目の値より意図（variant）を渡す
    • 矛盾する組み合わせは判別可能なユニオンで防ぐ
    • 入力系は制御・非制御を意識して設計する
    • 表示のバリエーションは children / スロットで吸収する
