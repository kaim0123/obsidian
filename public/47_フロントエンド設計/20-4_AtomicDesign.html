    Atomic Design — 使いどころと限界

    Brad Frost が 2013 年に提唱した Atomic Design は、化学のたとえで UI を小さい部品から組み上げる考え方です。このページでは、Atoms → Molecules → Organisms → Templates → Pages の 5 段階を理解したうえで、どこで役立ち、どこで破綻しやすいか、そして多くのチームが採っている現実的な使い方までを扱います。

    もとにしたノート：04_Atomic_Design

    ひとことで言うと

    Atomic Design は デザインシステム・UI カタログ・デザイナーとの共通語 としては今も有効です。一方、アプリ全体のフォルダ構成 にそのまま使うと「見た目の粒度」だけで分類するため、どの機能に属するかという軸が失われて 破綻しやすくなります。現実的には 汎用 UI 部品の中だけ で使い、機能は Feature 単位で切ります。

    2.Atomic Design とは

    化学のたとえで、UI を小さい部品から組み上げる 設計の考え方（メンタルモデル） です。

    段階内容例
    Atomsこれ以上分けられない最小の UIButton, Input, Label, Icon
    MoleculesAtoms を組み合わせた小さな機能単位ラベル付き入力、検索フォーム
    Organisms画面の独立した区画ヘッダー、商品一覧、コメント欄
    Templates部品の配置（レイアウト）。中身はダミー記事ページの骨組み
    PagesTemplates に実データを入れた完成形実際のトップページ

    もともとはデザインと実装の断絶（デザインは「ページ」、実装は「部品」で考える）を埋めるための方法論として提案されました（『Atomic Design』2016 年）。

    3.Atomic Design が役立つ場面

    場面理由
    デザインシステムを作る小さい部品から揃えると、全画面の一貫性が出る
    デザイナーと会話する「これは Molecule」と粒度の共通語ができる
    UI カタログ（Storybook）を整える階層ごとに部品を並べられる
    部品を段階的に作るAtoms → Molecules の順に作ると重複が減る

    特に Atoms と Molecules は、デザインシステム の汎用部品とほぼ一致するため、多くのチームで今も有効です。

    4.よくある破綻

    一方、アプリ全体のフォルダ構成 として Atomic Design をそのまま使うと、次の問題が起きやすいことが知られています。

    問題症状
    分類で迷う「これは Molecule か Organism か」の議論に時間を取られる
    ドメインが見えないorganisms/ に注文・ユーザー・商品の部品が混在する
    ロジックの置き場がないデータ取得や状態を持つ部品をどこに置くか決まっていない
    機能を消しにくい1 つの機能の部品が 5 階層に散らばる
    ✕ 悪い例：アプリ全体を 5 階層のフォルダにする 
      components/
    atoms/        Button, Input ...
    molecules/    SearchForm, PriceTag, UserBadge ...
    organisms/    Header, OrderTable, UserProfile, CartSummary ...  ← 肥大化
    templates/
    pages/

    「見た目の粒度」で分類しているため、「どの機能に属するか」という軸が失われる のが根本的な原因です。

    5.現実的な使い方

    多くのチームは、Atomic Design を 汎用 UI 部品の中だけ に限定して使っています。

    ◯ 良い例：汎用部品の中だけで Atomic Design、機能は縦に切る 
      src/
    shared/ui/          ← 汎用部品。ここで Atoms / Molecules の考え方を使う
      Button/ Input/ Modal/
    features/           ← 機能ごとに縦に切る（ドメインの軸）
      order/ components/ hooks/ api/
      user/  components/ hooks/ api/
    pages/              ← 画面（Templates + Pages に相当）
    使い方向く場面向かない場面
    5 階層をそのままフォルダに小〜中規模、UI 中心のサイトドメインが多い業務アプリ
    汎用部品の中だけで使うほとんどのアプリ—
    考え方（語彙）としてだけ使うデザイナーとの会話—

    Templates と Pages の区別は、フレームワークのルーティング（Next.js の layout と page など）で自然に表現されることも多くなっています。機能ごとに縦に切る構成は Feature-Sliced Design でさらに詳しく扱います。

    6.判断のポイント

    • 分類に迷ったら、その部品はドメインに属している 可能性が高い → features 側へ
    • 汎用部品かどうかは「別のアプリでもそのまま使えるか」で判断する
    • 階層の名前にこだわらず、ui/（汎用）と features/（機能）の 2 分割から始めても十分

    7.よくある誤解

    誤解1：「Atomic Design はフォルダ構成の方法論である」

    もともとは デザインと実装の断絶を埋めるための考え方（メンタルモデル） です。アプリ全体のフォルダ構成にそのまま当てはめると、機能の軸が失われ、organisms/ が肥大化しやすくなります。

    誤解2：「Atomic Design はもう時代遅れで使えない」

    そうとも限りません。Atoms と Molecules はデザインシステムの汎用部品とほぼ一致し、UI カタログの整理やデザイナーとの共通語として今も有効です。使う範囲を汎用 UI 部品に絞るのが現実的です。

    誤解3：「Molecule か Organism かは厳密に決めなければならない」

    分類に迷うこと自体が、その部品が 特定の機能（ドメイン）に属している サインであることが多いです。名前の議論に時間をかけるより、features 側へ置くことを考えます。

    8.まとめ

    • Atomic Design は Atoms → Molecules → Organisms → Templates → Pages の 5 段階
    • デザインシステム・UI カタログ・デザイナーとの共通語として有効
    • アプリ全体のフォルダ構成にすると、ドメインの軸が失われて破綻しやすい
    • 現実的には汎用 UI 部品の中だけで使い、機能は Feature 単位で切る
