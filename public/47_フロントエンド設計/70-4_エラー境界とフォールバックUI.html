    70 品質

    エラー境界とフォールバック UI — 壊れる範囲を小さく、次の行動を残す

    エラーはいつか必ず起きます。大事なのは、起きたときに 画面のどこまでを壊し、何を代わりに見せ、どう回復させるか を設計しておくことです。このページでは、エラーの分類、Error Boundary による境界の置き方、Suspense との組み合わせ、リトライ UI、そして捕まえたエラーを監視に送るところまでを扱います。

    もとにしたノート：04_エラー境界とフォールバックUI

    ひとことで言うと

    入力エラー・業務エラー・一時障害・認証切れ・404 といった 予期できるエラーは状態として扱い、Error Boundary は バグの最後の砦 にします。境界は「アプリ / ページ / 部品」の 3 段階で、「この部分が壊れても、残りの画面は使えるか」で置き場所を決めます。Suspense と並べて読み込み中・失敗・空・成功を区別し、リトライ手段と監視を用意します。

    1.このページで扱うこと

    エラーが起きたときに 画面のどこまでを壊し、何を代わりに見せ、どう回復させるか を設計できるようになるのが目標です。代わりに見せる UI を フォールバック UI と呼びます。

    • 何もしないと何が起きるか
    • エラーの分類 — 誰が・どう対処できるか
    • Error Boundary — 壊れる範囲を区切る（置き場所の 3 段階）
    • Suspense と組み合わせる — 読み込み中・失敗・成功（空状態）
    • リトライ UI — 回復の手段を用意する
    • 監視 — 捕まえたエラーを知る

    React での実装詳細は 32_React/18_エラーハンドリングと品質、HTTP エラーの扱いは 37 章（37_HTTPクライアントのノート『MOC_HTTPクライアント体系』）が本拠地です。サーバー側でエラーをどう返すかは 45章：エラー設計 を参照してください。

    2.何もしないと何が起きるか

    React では、描画中に例外が発生して誰も捕まえないと、アプリ全体がアンマウントされ真っ白な画面 になります。アンマウント とは、コンポーネントが画面から取り除かれることです。

    設計のゴールは、壊れる範囲を小さくし、ユーザーが次の行動をとれる状態を保つ ことです。

    3.エラーの分類 — 誰が・どう対処できるか

    すべてのエラーを同じ画面で扱うと、ユーザーは何をすればよいか分かりません。まず分類します。

    分類例ユーザーができること表示場所
    入力エラー必須項目が空・形式が違う直して再送信フォームの項目のそば
    業務エラー在庫切れ・権限なし別の操作を選ぶ画面内のメッセージ
    一時的な障害ネットワーク切断・タイムアウト・503再試行その部品の位置 + リトライボタン
    認証切れ401再ログインログイン画面へ誘導
    存在しない404別のページへNot Found 画面
    バグ描画中の例外・想定外の値できない（報告）Error Boundary のフォールバック

    （ノートでは「上の 4 つ」と書かれていますが、表の行で数えると入力エラーから存在しない（404）までの 5 つが予期できるエラーにあたります。まとめでも 5 つが挙げられています。）

    予期できるエラー は、Error Boundary に投げずに 状態として扱い ます。Error Boundary は主に 予期しないエラー（バグ）の最後の砦 です。

    4.Error Boundary — 壊れる範囲を区切る

    Error Boundary は、子孫の 描画中・ライフサイクル中 の例外を捕まえて、代わりの UI を表示する React の仕組みです。

    捕まえられない例外

    イベントハンドラ内や非同期処理（setTimeout、Promise）の例外は捕まえない点に注意が必要です。

    import { ErrorBoundary } from "react-error-boundary";

<ErrorBoundary
  FallbackComponent={({ resetErrorBoundary }) => (
    <div role="alert">
      <p>おすすめを表示できませんでした。</p>
      <button onClick={resetErrorBoundary}>再読み込み</button>
    </div>
  )}
  onError={(error) => reportError(error)} // 監視サービスへ送る
>
  <RecommendWidget />
</ErrorBoundary>

    4.1 どこに置くか — 3 段階

    どこに置くか は、3 段階で考えるのが定番です。

    粒度置き場所フォールバック
    アプリ全体ルート「問題が発生しました」+ トップへ戻る
    ページ / ルート各画面ナビゲーションを残したまま本文だけ差し替え
    部品（ウィジェット）独立した領域（おすすめ・グラフなど）その領域だけ差し替え

    判断の基準は「この部分が壊れても、残りの画面は使えるか」です。使えるなら境界を置きます。

    5.Suspense と組み合わせる — 読み込み中・失敗・成功

    データ取得を伴う部品は、読み込み中・失敗・成功 の 3 状態を持ちます。Suspense（子の準備ができるまで代わりの表示を出す React の仕組み。読み込み中を担当）と Error Boundary（失敗を担当）を 同じ単位で並べる と、状態ごとの表示を宣言的に書けます。

    <ErrorBoundary FallbackComponent={OrderListError}>
  <Suspense fallback={<OrderListSkeleton />}>
    <OrderList />  {/* データ取得中は suspend、失敗は throw */}
  </Suspense>
</ErrorBoundary>
    状態表示設計のポイント
    読み込み中スケルトン最終形と同じ大きさ（CLS 対策、パフォーマンスを設計で作り込む）
    失敗エラー表示 + リトライ何が起きたか・何ができるかを書く
    成功（0 件）空状態「まだ注文はありません」+ 次の行動

    空状態を失敗と混同しない ことも重要です。0 件はエラーではありません。

    Next.js App Router の error.tsx / loading.tsx は、ルート単位でこの組み合わせを自動で作る仕組みです。

    6.リトライ UI — 回復の手段を用意する

    一時的な障害は、再試行すれば直る ことが多いエラーです。

    手段内容注意点
    自動リトライ数回まで間隔をあけて再試行（指数バックオフ）4xx（入力エラー・権限）はリトライしない
    手動リトライ「再試行」ボタン押したら境界をリセットし、データを取り直す
    楽観的更新の巻き戻し送信失敗時に画面を元に戻す何が戻ったかを通知する

    指数バックオフ は、再試行の間隔を 1 秒、2 秒、4 秒……と倍々に広げていく方法です。楽観的更新 は、サーバーの応答を待たずに「成功したもの」として先に画面を更新する手法です。

    // TanStack Query と組み合わせる例 — 境界のリセット時にクエリも再実行
const { reset } = useQueryErrorResetBoundary();
<ErrorBoundary onReset={reset} FallbackComponent={OrderListError}>…</ErrorBoundary>

    自動リトライの設定は 37 章のリトライ・タイムアウト設計が本拠地です。

    7.監視 — 捕まえたエラーを知る

    フォールバックを表示しただけでは、開発者はエラーに気づけません。

    • onError で監視サービス（Sentry など）へ送る
    • ユーザー ID・画面・直前の操作を添える（個人情報は送らない）
    • 「同じエラーが何人に起きたか」で優先度を付ける

    観測の考え方全般は 41章：観測性 も参考になります。

    8.よくある誤解

    誤解1：「エラーはすべて Error Boundary で捕まえればよい」

    違います。 入力エラー・業務エラー・一時障害・認証切れ・404 は予期できるエラーなので、状態として扱い、それぞれに合った場所で次の行動を示します。Error Boundary は予期しないエラー（バグ）の最後の砦です。また、イベントハンドラや非同期処理の例外はそもそも Error Boundary では捕まえられません。

    誤解2：「アプリのルートに 1 つ Error Boundary を置けば十分」

    それだけでは壊れる範囲が大きすぎます。 ルートだけだと、おすすめ欄 1 つの不具合で画面全体がフォールバックに置き換わります。「アプリ / ページ / 部品」の 3 段階で考え、壊れても残りが使える部分には境界を置きます。

    誤解3：「データが 0 件ならエラー表示を出す」

    0 件はエラーではありません。 「まだ注文はありません」のような空状態と、次の行動を表示します。失敗と空状態を混同すると、ユーザーは何が起きたのか分からなくなります。

    9.まとめ

    • 予期できるエラー（入力・業務・一時障害・認証・404）は 状態として扱う。Error Boundary はバグの最後の砦
    • 境界は「アプリ / ページ / 部品」の 3 段階で、「壊れても残りが使えるか」で置き場所を決める
    • Suspense と Error Boundary を同じ単位で並べ、読み込み中・失敗・空・成功を区別する
    • 一時障害にはリトライ手段を用意し、捕まえたエラーは監視に送る
