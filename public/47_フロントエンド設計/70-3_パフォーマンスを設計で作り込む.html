    パフォーマンスを設計で作り込む — Core Web Vitals を物差しに

    パフォーマンスは「遅くなってから直すもの」と思われがちですが、実際には 設計段階の判断で大部分が決まります。このページでは Core Web Vitals（LCP / INP / CLS）を物差しに、設計で決まる部分と後で直せる部分を分け、初期表示・応答性・レイアウトの安定性・画像・パフォーマンス予算について、設計で何を決めておくべきかを整理します。

    もとにしたノート：03_パフォーマンスを設計で作り込む

    ひとことで言うと

    物差しは Core Web Vitals（LCP / INP / CLS） で、実ユーザーの 75 パーセンタイルで見ます。レンダリング方式・状態の置き場所・ライブラリ選定 は後から変えにくいので設計段階で決めます。LCP は送る JS を減らす、INP は再レンダリング範囲を絞る、CLS は領域を先に確保する。そして予算を決めて CI で監視します。

    1.このページで扱うこと

    パフォーマンスを「遅くなってから直すもの」ではなく、設計段階の判断で大部分が決まるもの として扱えるようになるのが目標です。Core Web Vitals を物差しに、バンドル分割・レンダリング境界・画像の扱いを整理します。

    • 物差し — Core Web Vitals（LCP / INP / CLS）
    • 設計で決まる部分と、後で直せる部分
    • 初期表示（LCP）— 送る JS を減らす
    • 応答性（INP）— レンダリングの境界を設計する
    • 安定性（CLS）— 領域を先に確保する
    • 画像の扱いと、パフォーマンス予算

    計測と個別の最適化は 67_パフォーマンス（67_パフォーマンスのノート『パフォーマンスとは何か』）と 32_React/11_パフォーマンス（32_React のノート『Part 13 初期ロード最適化：Code SplittingとLazy Loading設計』など）が本拠地です。

    2.物差し — Core Web Vitals

    Google が定める Core Web Vitals は、ユーザー体験を 3 つの指標で測ります。2024 年 3 月に、応答性の指標は FID から INP に置き換わりました。

    指標測るもの「良好」の目安主に効く設計判断
    LCP（Largest Contentful Paint）主要コンテンツが表示されるまで2.5 秒以下レンダリング方式・画像・初期 JS 量
    INP（Interaction to Next Paint）操作してから画面が反応するまで200 ミリ秒以下メインスレッドの負荷・再レンダリング範囲
    CLS（Cumulative Layout Shift）レイアウトのずれ0.1 以下画像・広告・遅延要素の領域確保

    目安は、実ユーザーの 75 パーセンタイル で判定します。75 パーセンタイルとは、利用者を速い順に並べたとき 75% の位置の値のことで、「4 人中 3 人がこの値以内」という意味になります。

    3.設計で決まる部分と、後で直せる部分

    設計段階で決まる（後から変えるのが高い）後から直せる
    レンダリング方式（CSR / SSR / SSG / RSC）個別の memo 化
    状態の置き場所（再レンダリング範囲）画像フォーマット変換
    依存ライブラリの選定（バンドルサイズ）遅延読み込みの追加
    データ取得の設計（ウォーターフォール）キャッシュ設定の調整

    左側を間違えると、右側をいくら頑張っても限界があります。

    4.初期表示（LCP）— 送る JS を減らす

    設計判断内容
    レンダリング方式表示内容が決まっているページは SSG / SSR で HTML を先に返す（41章：レンダリング方式）
    ルート単位の分割画面ごとに JS を分け、最初の画面に不要なコードを送らない
    重い部品の遅延エディタ・グラフ・地図などは lazy で必要になってから読み込む
    ライブラリ選定導入前にサイズを確認（bundlephobia など）。日付・ユーティリティは軽量な代替を検討
    RSCサーバーだけで使う処理のコードはクライアントに送られない
     
    // 重い部品は必要なときだけ読み込む
const Chart = lazy(() => import("./Chart"));
<Suspense fallback={<ChartSkeleton />}><Chart data={data} /></Suspense>

    データ取得のウォーターフォール

    データ取得のウォーターフォール にも注意します。親が取得 → 描画 → 子が取得、という直列の連鎖は、ルートやサーバー側でまとめて並列に取得する設計で避けます。

    5.応答性（INP）— レンダリングの境界を設計する

    INP を悪化させる主な原因は、操作のたびに広い範囲が再レンダリングされる ことと、メインスレッドを長く占有する処理 です。メインスレッドは、ブラウザが JavaScript の実行や描画を行う唯一の流れで、ここが埋まっていると操作に反応できません。

    原因設計での対処
    状態を上に置きすぎる状態は使う部品の近くに置く（状態の分類と置き場所）
    巨大な Context の値が頻繁に変わるContext を分割する / 状態管理ライブラリのセレクタを使う
    長いリストを全部描画仮想化（表示範囲だけ描画）
    重い計算を入力のたびに実行useDeferredValue / useTransition で優先度を下げる、Web Worker に逃がす

    6.安定性（CLS）— 領域を先に確保する

    原因対処
    画像のサイズ未指定width / height か aspect-ratio を必ず指定
    後から出るバナー・広告表示領域を先に確保する
    Web フォントの切り替えfont-display の指定、フォールバックフォントのサイズ調整
    ローディング表示最終形と同じ大きさのスケルトンを使う

    スケルトン は、読み込み中に最終的な内容と同じ形の灰色の枠を表示しておく手法です（エラー境界とフォールバック UI でも使います）。

    7.画像 — 最も効果が大きい資源

    LCP の対象要素は画像であることが多いため、画像の扱いは設計ルールとして決めておきます。

    • 最初に見える画像（LCP 候補）は 遅延読み込みしない、fetchpriority="high" を検討
    • それ以外は loading="lazy"
    • srcset / sizes で画面幅に合ったサイズを配信、AVIF / WebP を使う
    • フレームワークの画像コンポーネント（Next.js の Image など）があれば標準にする

    8.予算で守る

    パフォーマンス予算（JS のサイズや表示時間に上限を決めておくこと）を決めて CI で監視すると、設計判断の劣化を早く検出できます。

    予算の例監視方法
    初期 JS 200KB（圧縮後）以下バンドルサイズの CI チェック
    LCP 2.5 秒以下Lighthouse CI / 実ユーザー計測（RUM）

    9.よくある誤解

    誤解1：「パフォーマンスは遅くなってから memo 化などで直せばよい」

    後から直せる範囲には限界があります。 レンダリング方式・状態の置き場所・ライブラリ選定・データ取得の設計は後から変えるコストが高く、ここを間違えると個別の memo 化や遅延読み込みをいくら頑張っても限界があります。

    誤解2：「画像はすべて loading="lazy" にすれば速くなる」

    最初に見える画像（LCP 候補）は遅延読み込みしません。 LCP の対象であることが多いので、遅らせると LCP が悪化します。最初に見える画像は fetchpriority="high" を検討し、それ以外に loading="lazy" を使います。

    誤解3：「開発者の手元で速ければ問題ない」

    判定は実ユーザーの 75 パーセンタイル で行います。開発者の高性能なマシンと速い回線では見えない遅さがあるため、実ユーザー計測（RUM）や予算の CI 監視で確認します。

    10.まとめ

    • 物差しは Core Web Vitals（LCP / INP / CLS）、実ユーザーの 75 パーセンタイルで見る
    • レンダリング方式・状態の置き場所・ライブラリ選定は後から変えにくい。設計段階で決める
    • LCP は送る JS を減らす、INP は再レンダリング範囲を絞る、CLS は領域を先に確保する
    • 予算を決めて CI で監視し、劣化を早く見つける
