    40 ディレクトリ・モジュール構成

    ディレクトリ構成の方式比較 — Layer型・Feature型・Atomic Design型・FSD

    フロントエンドのディレクトリ構成の代表的な方式 —— Layer型 / Feature型 / Atomic Design型 / Feature-Sliced Design（FSD） —— を比較し、プロジェクトの規模と変化に合わせて選べるようになることを目指します。React でのフォルダ例やモジュール分割の一般論ではなく、どの方式をいつ選ぶか を扱います。

    もとにしたノート：01_ディレクトリ構成の方式比較

    ひとことで言うと

    ディレクトリ構成は 凝集・依存の向き・削除のしやすさ を決める設計です。小規模なら Layer型、中規模の定番は Feature型、大規模・長期運用なら FSD。Atomic Design はアプリ全体ではなく UI 部品の整理に使います。規模に応じて 1 機能ずつ移行 してよく、どの方式でも 依存ルールはツールで検査 します。

    1.このページで扱うこと

    • ディレクトリ構成が決める 3 つのこと
    • Layer型（技術の種類で分ける）
    • Feature型（機能で分ける）
    • Atomic Design型（UI の粒度で分ける）
    • Feature-Sliced Design（層 × 機能で分ける）
    • 比較表と、選び方・移行の進め方

    React でのフォルダ例は 32_React のノート『10-6-ディレクトリ設計』、モジュール分割の一般論は 43章 モジュール設計 が本拠地です（特に 機能別とレイヤー別）。

    2.ディレクトリ構成が決めること

    ディレクトリ構成は、単なる整理整頓ではなく 次の 3 つを決める設計 です。

    決めること問い
    凝集一緒に変わるファイルが近くにあるか
    依存の向きどこからどこへ import してよいか
    削除のしやすさ機能をやめるとき、フォルダごと消せるか

    凝集（関係の深いものが 1 か所にまとまっている度合い）の詳しい話は 43章：凝集度 を参照してください。「1 つの機能を直すのに何フォルダ開くか」が、構成の良し悪しを測る簡単な物差しです。

    3.Layer型（技術の種類で分ける）

    src/
├── components/
├── hooks/
├── services/     (API 呼び出し)
├── stores/
├── types/
└── utils/

    ファイルの技術的な種類 でフォルダを分ける方式です。小さなアプリや、フレームワークのチュートリアルでよく見られます。

    • 利点：最初に迷わない。どこに何を置くかのルールが単純
    • 欠点：「注文機能」を直すと components/ hooks/ services/ types/ を横断する。規模が大きくなると各フォルダが数十ファイルになり、関係のないファイルが隣に並ぶ（低凝集）

    4.Feature型（機能で分ける）

    src/
├── features/
│   ├── auth/
│   │   ├── components/
│   │   ├── hooks/
│   │   └── api/
│   └── orders/
│       ├── components/
│       ├── hooks/
│       └── api/
├── components/   (共有 UI)
└── lib/          (共有ユーティリティ)

    業務上の機能 を第一階層にし、その中を技術で分ける方式です。bulletproof-react がこの形です（bulletproof-react）。

    • 利点：1 機能の変更が 1 フォルダに収まる。機能ごと削除できる
    • 欠点：「どこまでを 1 機能とするか」「機能をまたぐ処理をどこに置くか」の判断が必要。ルールがないと features 同士が import し合う

    5.Atomic Design型（UI の粒度で分ける）

    src/components/
├── atoms/       (Button, Input)
├── molecules/   (SearchField)
├── organisms/   (Header, ProductCard)
├── templates/
└── pages/

    Brad Frost が 2013 年に提唱した UI 部品の粒度 による分類をフォルダにしたものです（Atomic Design）。

    • 利点：デザインシステム・共有 UI ライブラリの整理には向く
    • 欠点：ロジック・API・状態の置き場所を決めない。「この部品は molecule か organism か」の議論が起きやすい。アプリ全体の構成方式としては不十分

    6.Feature-Sliced Design（層 × 機能で分ける）

    src/
├── app/        (初期化・プロバイダ・ルーティング)
├── pages/
├── widgets/
├── features/
├── entities/
└── shared/

    層（layer） と 機能の切れ目（slice） の 2 軸で分け、上の層から下の層へしか import しない ルールを持つ方式です（Feature-Sliced Design）。

    • 利点：依存の向きが明文化され、ツールで検査できる。大規模・複数人開発で崩れにくい
    • 欠点：学習コストが高い。「feature か entity か」の判断に慣れが必要。小さなアプリには過剰

    7.比較表

    方式分ける軸依存ルール向く規模向かない場面
    Layer型技術の種類なし（暗黙）小規模・試作機能が 10 を超える、複数人開発
    Feature型業務機能自分で決める中規模機能間の共有が多く境界が曖昧
    Atomic Design型UI の粒度下の粒度のみ使うデザインシステムアプリ全体の構成（ロジックの置き場がない）
    FSD層 × 機能上→下のみ（明文化）中〜大規模、長期運用数画面の小さなアプリ、短命な試作

    実際には 組み合わせ が多く見られます。たとえば「アプリは Feature型、components/ui/ の中だけ Atomic 的に整理」などです。

    8.選び方と移行

    画面数・機能数が少ない（〜数画面） → Layer型で始めてよい
機能が増え、1 変更で多フォルダを触る → Feature型へ
複数人・長期運用で依存が絡み始めた → FSD、または Feature型 + 依存ルールの自動検査
    • 最初から完璧な構成を選ぶ必要はありません。変更のしづらさを感じた時点で移行 します
    • 移行は 1 機能ずつ 行います（新しい機能から新方式で作り、古い機能は触るときに移す）
    • どの方式でも、依存ルールはツールで守らせる と崩れません（依存ルールの自動検査）

    9.よくある誤解

    誤解1：「最初から大規模向けの構成（FSD など）を選んでおけば安心」

    小さなアプリには過剰です。 FSD は学習コストが高く、数画面のアプリや短命な試作には向きません。小さく始め、変更のしづらさを感じた時点で移行すれば十分です。

    誤解2：「Atomic Design でアプリ全体のフォルダを分ければよい」

    Atomic Design は UI 部品の粒度の分類です。 ロジック・API・状態の置き場所を決めないため、アプリ全体の構成方式としては不十分です。共有 UI ライブラリの中だけ Atomic 的に整理する、という組み合わせが現実的です。

    誤解3：「構成を変えるなら、一度に全部移し替える必要がある」

    移行は 1 機能ずつで構いません。 新しい機能から新方式で作り、古い機能は触るときに移します。

    10.まとめ

    • ディレクトリ構成は 凝集・依存の向き・削除のしやすさ を決める設計
    • Layer型は小規模向け、Feature型は中規模の定番、FSD は大規模・長期運用向け
    • Atomic Design はアプリ全体ではなく UI 部品の整理 に使う
    • 規模に応じて移行してよい。移行は 1 機能ずつ
    • 依存ルールは文書だけでなくツールで検査する
