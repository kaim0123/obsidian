    20 コンポーネント設計

    画面関心事の分割とドメイン連動

    複雑な画面は、たいてい 異なる関心事の寄せ集め です。このページでは、増田亨『現場で役立つシステム設計の原則』第7章のうち 画面／UI 側 の要点を、コンポーネント設計とつなぐ形で整理します。関心事ごとに小さく分け、必要なら画面そのものを分けること、タスクベースのインターフェース が主流になりやすい理由、そして項目の並びやグルーピングをソフトウェアの論理構造と揃える考え方を扱います。

    もとにしたノート：05_画面関心事の分割とドメイン連動

    ひとことで言うと

    複雑な画面＝関心事の混在 です。関心事ごとに部品へ分け、1 画面に載せきれなければ 画面自体を分けます（タスクベース UI）。さらに、項目の並び・グループ・画面の分割を ドメインやシナリオと揃え、両者のずれを改善の手がかりにします。

    1.このページで扱うこと

    • 複雑な画面は異なる関心事の寄せ集めであること
    • 小さく分け・画面そのものを分ける・タスクベース UI が主流になりやすい理由
    • 項目の並び・グルーピングをソフトウェアの論理構造と揃える考え方（増田本）

    前提

    部品の粒度は コンポーネントの分割粒度と境界。ドメイン連動の本論は（42_ソフトウェア設計 のノート『09_画面とドメインオブジェクトの設計』）。アプリ層の分割は（42_ソフトウェア設計 のノート『07_アプリケーション機能を組み立てる』）。

    ここでの ドメイン は、ソフトウェアが扱う業務の領域（顧客・契約・請求など）と、その業務のルールを表すオブジェクトのことです。

    2.複雑な画面は関心事が混ざっている

    1つの画面に次が同居しがちです。

    • 複数ロールの関心（登録・承認・照会）
    • 複数の業務かたまり（顧客・契約・請求）
    • 検索・一覧・詳細編集・副作用つき操作

    混ざったまま巨大コンポーネントや「何でもフォーム」にすると、変更理由が異なる改修が同じファイルに集まります（分割粒度と境界 の分割サインと同型）。

    3.小さな単位に分け、必要なら画面も分ける

    方針内容
    関心事単位に考える「この画面で利用者が一度にやりたいこと」は何か
    部品に分ける変更理由・データのまとまりでコンポーネント境界を切る
    画面を分ける1画面に載せきれない／役割が違うならルートやウィザードのステップに分ける

    アプリ層では参照／更新やシナリオに分けます（42_ソフトウェア設計 のノート『07_アプリケーション機能を組み立てる』）。フロントでは ルート・タブ・ステップ・独立パネル として同じ分割を視覚に出します。

    4.タスクベースのインターフェース

    「1画面に全項目」から、「やりたいこと（タスク）ごとに画面／ダイアログ」へ寄る流れが増えています。これを タスクベースのインターフェース と呼びます。

    4.1 増えている2つの理由（増田本の整理）

    1. 利用者の仕事が多様で、全部入り画面が認知負荷になる
    2. ソフトウェア側も関心事ごとに独立して変更・テストしたい（画面分割＝変更単位の分割）

    モバイルや権限の細分化も、タスク単位の画面と相性がよいです。

    4.2 今後の主流としての位置づけ

    タスクベースに分けると、画面の境界がドメインオブジェクト／ユースケース（利用者がシステムを使って達成したい 1 つの目的）の境界に近づき、画面とドメインの連動（42_ソフトウェア設計 のノート『09_画面とドメインオブジェクトの設計』）がしやすくなります。CRUD（作成・参照・更新・削除）の「1リソース＝1巨大フォーム」は、関心事が単純なとき以外は見直し候補です。

    全部入り画面

    • 1 リソース＝1 巨大フォーム
    • 登録・承認・照会が同じ画面に同居
    • 変更理由の違う改修が 1 ファイルに集まる

    タスクベース

    • やりたいことごとに画面／ダイアログ
    • 画面の境界がユースケースの境界に近づく
    • 関心事ごとに独立して変更・テストできる

    5.視覚表現と論理構造を揃える

    画面（視覚）ソフトウェア（論理）
    項目の並び順フィールド・値オブジェクトの提示順、フォームスキーマの順
    枠・見出しでのグルーピングオブジェクトのまとまり、埋め込み VO（値オブジェクト）、セクション用の型
    画面／ステップの分割関心事・シナリオ・集約の操作単位

    デザインカンプ（完成イメージのデザイン案）とドメインモデルを別々に固めてから無理に合わせるより、ずれを見つけたら両方を少しずつ直す 方が、用語と構造が安定します。デザインシステムの「いつ Dialog / Drawer を使うか」といった判断ルール（デザインシステムの構成要素）も、タスク単位の分割とセットで効きます。

    5.1 表示判断はドメイン寄り、当て方は UI

    状態に応じた強調（警告色・disabled）の 判定 はドメイン／共有の表示モデルへ寄せ、コンポーネントは class や variant を当てるだけ、という分担が安全です（詳細は 42_ソフトウェア設計 のノート『09_画面とドメインオブジェクトの設計』）。API の DTO（Data Transfer Object。通信でやりとりするためだけのデータの形）を画面に直結しない話は API レイヤと型の共有 で扱います。

    5.2 画面以外の利用者向け情報

    帳票・メール・通知・空状態のコピー（データが 0 件のときに表示する文言）も、同じグルーピングと業務用語に揃えると、フロントだけのローカル用語が増えにくくなります（ユビキタス言語）。

    6.よくある誤解

    誤解1：「1 リソースは 1 画面にまとめた方がわかりやすい」

    関心事が単純なときはそれで構いません。しかし登録・承認・照会のように 役割が違う操作 が同居すると、利用者には認知負荷、開発者には変更理由の混在になります。タスクごとに画面やダイアログを分けることを検討します。

    誤解2：「デザインとドメインモデルは別々に完成させてから合わせればよい」

    別々に固めてから無理に合わせると、用語も構造もずれたままになりがちです。ずれを見つけたら両方を少しずつ直す 方が、画面の並び・グループと、ソフトウェアの論理構造が安定します。

    誤解3：「警告色にするかどうかの判定はコンポーネントの中に書けばよい」

    「この状態なら警告」という 判定は業務ルール なので、ドメイン／共有の表示モデルへ寄せます。コンポーネントはその結果を受け取り、class や variant を当てるだけにすると、画面ごとに判定がばらつきません。

    7.まとめ

    • 複雑な画面＝関心事の混在。小さく分け、必要なら画面自体を分ける
    • タスクベース UI は利用者にも開発にも分割の単位を与える
    • 並び・グループ・画面分割をドメイン／シナリオと連動させ、ずれを改善の手がかりにする
