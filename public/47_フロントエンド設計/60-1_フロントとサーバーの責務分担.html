    60 サーバーとの境界

    フロントとサーバーの責務分担 — 隠すのはフロント、守るのはサーバー

    バリデーション（入力チェック）・権限・データ整形を、フロントとサーバーのどちらに置けばよいのでしょうか。このページでは「クライアントは信用しない」という大原則から出発し、バリデーションの二重化、権限の出し分け、データ整形の置き場所、そして BFF や React Server Components（RSC）・Server Actions の登場で 境界の位置そのものが動く 話までを整理します。

    もとにしたノート：01_フロントとサーバーの責務分担

    ひとことで言うと

    ブラウザのコードはユーザーが自由に書き換えられるので、認証・認可・業務ルールの保証はサーバー が担い、フロントは すぐに気づかせる・見せ方を整える という UX のための補助を担います。RSC や Server Actions で境界がコンポーネントの中に入っても、「信用できない入力は、信用できる場所で検証する」という原則は変わりません。

    1.このページで扱うこと

    バリデーション・権限・データ整形などを フロントとサーバーのどちらに置くか を判断できるようになるのが目標です。BFF や React Server Components（RSC）・Server Actions の登場で 境界の位置そのものが動く ことも扱います。

    • 大原則 — クライアントは信用しない
    • バリデーションの二重化とスキーマ共有
    • 権限 — 隠すのはフロント、守るのはサーバー
    • データ整形の置き場所（フロント / BFF / バックエンド API）
    • RSC / Server Actions で境界が動くときの注意点

    HTTP クライアントの実装は 37 章（37_HTTPクライアントのノート『MOC_HTTPクライアント体系』）、レンダリング方式と BFF の構成は 41 章（レンダリング方式・BFF とマイクロフロントエンド）、API の設計は 45 章（API 設計）が本拠地です。

    2.大原則 — クライアントは信用しない

    ブラウザで動くコードは ユーザーが自由に書き換えられます。開発者ツールで JavaScript を書き換えたり、画面を通さずに API へ直接リクエストを送ったりできるからです。そのため、次の原則が出発点になります。

    種類どこで保証するかフロントの役割
    セキュリティ（認証・認可）サーバーのみ見せ方の調整（ボタンを隠すなど）
    データの整合性（業務ルール）サーバーのみ早めのフィードバック
    ユーザー体験（即時の反応）フロント主担当

    認証 は「誰であるか」の確認、認可 は「その人が何をしてよいか」の判定です（詳しくは 認証と認可の違い）。

    3.バリデーションの二重化

    入力チェックは 両方に置く のが基本です。役割が違うからです。

    フロントサーバー
    目的すぐに気づかせる（UX）不正なデータを入れない（正しさ）
    省略したら使いにくいだけデータが壊れる
    例必須・形式・文字数上記 + 重複チェック・在庫・権限

    二重化の手間は、スキーマを共有 して減らします（API レイヤと型の共有）。スキーマ とは「データがどんな形・どんな制約を持つか」の定義です。下の例の Zod は、TypeScript でスキーマを書き、そこから型と実行時チェックの両方を得られるライブラリです。

    // shared/schema/user.ts — フロントとサーバーで同じ定義を使う
import { z } from "zod";
export const UserInput = z.object({
  name: z.string().min(1).max(50),
  email: z.string().email(),
});

    共有できないルールもある

    サーバーでしか判定できないルール（メールアドレスの重複など）は共有できません。サーバーからのエラーをフォームに表示する経路を必ず用意します。

    4.権限 — 隠すのはフロント、守るのはサーバー

    // フロント: 権限がなければボタンを出さない（UX）
{can(user, "order:delete") && <DeleteButton />}
    • ボタンを隠しても、API を直接呼べば実行できてしまう
    • サーバー側の認可チェックが本体、フロントの出し分けは補助
    • 権限の判定ロジックを両方で持つなら、権限一覧（ロール → 操作）をサーバーから受け取り、フロントは表示に使うだけにする

    サーバー側の認可の設計は 45章：認可、認可漏れの典型は 73章：認可不備と認可の要件定義 を参照してください。

    5.データ整形はどこでやるか

    「API のレスポンスを画面の形に変える処理」をどこに置くかは、選択肢が複数あります。

    置き場所向く場面向かない場面
    フロント（API レイヤで変換）API が 1 つ・画面も少ない複数 API を画面ごとに組み合わせる
    BFF（画面専用のサーバー層）複数のバックエンドを束ねる / Web とモバイルで必要な形が違う小規模で BFF の運用コストが見合わない
    バックエンド API を画面に合わせる1 つのフロント専用の API複数のクライアントが同じ API を使う

    BFF（Backend For Frontend）は「フロントエンドチームが持つサーバー」です。フロントの都合（集約・整形・キャッシュ）をバックエンドに押し付けずに済みます。BFF の構成は 41章：BFF と API ゲートウェイ で詳しく扱っています。

    6.RSC / Server Actions で境界が動く

    React Server Components（サーバーだけで実行されるコンポーネント）と Server Actions（フォームなどから直接呼べるサーバー関数）では（Next.js App Router など）、同じコンポーネントツリーの中にサーバー側のコードが入ります。

    // Server Component — サーバーで実行され、DB に直接アクセスできる
export default async function OrdersPage() {
  const orders = await db.order.findMany(); // API を経由しない
  return <OrderList orders={orders} />;
}

// Server Action — フォームから直接サーバー関数を呼ぶ
async function cancelOrder(formData: FormData) {
  "use server";
  const id = String(formData.get("id"));
  await assertCanCancel(id); // ← 認可はここで必ず行う
  await db.order.update({ where: { id }, data: { status: "canceled" } });
}
    変わること注意点
    フロントのコードが DB に触れるServer Action は公開エンドポイントと同じ。認可・入力検証を省略しない
    API レイヤが不要になる場面がある他のクライアント（モバイル等）が同じ処理を使うなら API は別途必要
    データ取得がコンポーネントに近づくサーバー専用コードがクライアントに混ざらないよう server-only などで境界を明示する

    判断の軸は変わらない

    境界の位置が動いても、「信用できない入力は、信用できる場所で検証する」が原則です。

    7.よくある誤解

    誤解1：「フロントで入力チェックしているから、サーバーでは不要」

    違います。 フロントのチェックは書き換えたり、API を直接呼んだりすれば簡単に回避できます。フロントのチェックは すぐに気づかせるための UX、サーバーのチェックは データを壊さないための本番 で、役割が別です。省略したときの結果も「使いにくいだけ」と「データが壊れる」で大きく違います。

    誤解2：「ボタンを隠せば、その操作はできなくなる」

    隠すのは見せ方の調整にすぎません。 ボタンがなくても API を直接呼べば実行できてしまいます。操作を守るのはサーバー側の認可チェックです。

    誤解3：「Server Action は自分のコンポーネントからしか呼ばれないので、認可は要らない」

    Server Action は公開エンドポイントと同じ と考えます。見た目はコンポーネントの中の関数でも、外部から呼び出せる入口です。認可と入力検証を必ず行います。

    8.まとめ

    • 認証・認可・業務ルールの 保証はサーバー、フロントは UX のための補助
    • バリデーションは二重化し、スキーマ共有で手間を減らす。サーバー専用ルールのエラー経路も用意する
    • 画面向けの整形は、規模と API の利用者の数で「フロント / BFF / API 側」を選ぶ
    • RSC・Server Actions では境界がコンポーネント内に入るが、Server Action は公開エンドポイントとして扱う
