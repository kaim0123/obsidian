    80 スケールと組織

    マイクロフロントエンドの判断 — 採るか、やめるか

    1つの画面を、別々のチームが独立して開発・デプロイできる複数のアプリで組み立てる マイクロフロントエンド（Micro-Frontends, MFE）。このページでは、MFE を「採るべきか・やめるべきか」の判断の順番、統合方式ごとのトレードオフ、そして MFE を採っても各アプリの内部設計は別に必要なことを学びます。

    もとにしたノート：02_マイクロフロントエンドの判断

    ひとことで言うと

    MFE は 組織の問題（複数チームが互いを待たずにリリースしたい） を解く手段で、技術の流行で採るものではありません。まずはモノリス内の機能別構成やモノレポで足りないかを確かめ、それでもデプロイまで独立させたいときに検討します。MFE にしても、各 MFE の内部設計は別に必要 です。

    1.このページで扱うこと

    マイクロフロントエンド（MFE） を「採るべきか・やめるべきか」を判断できるようになることが目標です。

    • マイクロフロントエンドとは何か、何のためのものか
    • 採る・やめるの判断と、その順番
    • 統合方式（ビルド時・Module Federation・iframe・Web Components・サーバー合成）の比較
    • MFE の内部にも設計が要ること
    • MFE にするなら決めておく横断の約束ごと

    MFE・BFF・レンダリング方式などの構成そのものの説明は 41章：BFF とマイクロフロントエンド を参照してください。

    2.マイクロフロントエンドとは

    マイクロサービス（サーバー側のシステムを、独立してデプロイできる小さなサービスに分ける考え方）をフロントエンドに持ち込み、1 つの画面を、独立して開発・デプロイできる複数のアプリで構成する 方式です。2016 年ごろ ThoughtWorks Technology Radar で取り上げられて広まり、Cam Jackson の記事「Micro Frontends」（martinfowler.com, 2019）で整理されました。

    シェル（コンテナアプリ） とは、各 MFE を読み込んで1つの画面に組み立てる外枠のアプリです。

    目的は技術ではなく 組織 です。複数チームが互いを待たずにリリースできることが最大の価値です。

    3.採る・やめるの判断

    採る価値がある

    • 3 チーム以上が 1 つのフロントを触り、リリース待ちが常態化
    • 事業領域ごとにチームの責任範囲がはっきりしている
    • レガシー画面を少しずつ新技術に置き換えたい
    • プラットフォームチームが基盤を保守できる

    やめたほうがよい

    • 1〜2 チームで開発している
    • 領域の境界がまだ揺れている
    • 性能（バンドルサイズ）が最優先
    • 共通基盤を持つ人がいない

    判断の順番は次の通りです。

      リリース待ち・衝突が本当に問題か？
        │ いいえ → モノリスのまま（ディレクトリで分ける）
        ▼ はい
  モノレポ + 機能別構成 + 依存ルールで解決できないか？
        │ できる → モノレポ + 機能別構成で十分
        ▼ できない（デプロイまで独立させたい）
  マイクロフロントエンドを検討
    1. リリース待ち・衝突が本当に問題か？ — いいえなら、モノリスのまま（ディレクトリで分ける）
    2. モノレポ + 機能別構成 + 依存ルールで解決できないか？ — できるなら、モノレポ + 機能別構成で十分
    3. できない（デプロイまで独立させたい） — マイクロフロントエンドを検討

    多くの場合、まず 1 つのアプリの中で機能別に分ける（FSD など） ほうが安く、効果も大きいです。

    4.統合方式の比較

    別々に作った MFE を、どのタイミングで1つの画面にまとめるか（統合するか）で、いくつかの方式があります。

    方式統合のタイミング長所短所
    ビルド時統合（npm パッケージとして取り込む）ビルド時単純・型安全1 つ変えるとシェルの再デプロイが必要。独立デプロイにならない
    Module Federation（webpack 5 / Rspack など）実行時（JS）独立デプロイ・依存の共有（React を 1 つだけ読むなど）バージョン不一致の事故、設定が複雑
    iframe実行時（ブラウザ）最強の分離（CSS・JS が混ざらない）画面をまたぐ連携・ルーティング・a11y・レスポンシブが難しい
    Web Components（Custom Elements）実行時（DOM）フレームワーク非依存の境界SSR や React との props 受け渡しに工夫が要る
    サーバー／エッジでの合成（SSI・ESI など）リクエスト時初期表示が速いインタラクションの連携は別途必要

    Module Federation は、別々にビルド・デプロイした JavaScript を実行時に読み込み合う webpack の仕組みです。SSI・ESI は、サーバーや CDN のエッジで HTML の断片を差し込んで1ページに組み立てる仕組みです。

    5.MFE の内部にも設計が要る

    MFE が決めるのは デプロイ単位の分け方 だけです。各 MFE の 内部をどう構成するか は何も決めません。

      MFE の境界（組織・デプロイ）
     └─ 各 MFE の内部（コード構成） ← FSD / bulletproof-react などが別に必要

    そのため、各 MFE の中では Feature-Sliced Design や bulletproof-react の構成 のような構成を採ります。MFE にしたのに中身がスパゲッティなら、小さなスパゲッティが複数できるだけです。

    6.横断の約束ごと

    MFE にするなら、最初に次を決めておきます。

    約束例
    デザインの一貫性共通のデザインシステム（デザインシステムの構成要素）
    MFE 間の通信URL・Custom Event など疎結合な手段に限る。相手の内部 state を直接読まない
    共有依存React などのバージョン方針（Module Federation の shared）
    認証シェルが持ち、MFE はトークンを受け取るだけ
    ◯ 良い例：MFE 間は Custom Event で疎結合に通知する 
    // MFE 間は Custom Event で疎結合に通知する例
window.dispatchEvent(
  new CustomEvent("cart:item-added", { detail: { productId: "p-1" } })
);

    送る側は「カートに商品が追加された」という出来事を知らせるだけで、誰が受け取るかを知りません。受け取る側も、送る側の内部 state を直接読みません。

    7.よくある誤解

    誤解1：「大きなフロントエンドなら MFE にすべき」

    大きさではなく組織で決めます。 1〜2 チームなら、MFE の運用コスト（統合・共有依存・共通基盤）のほうが高くつきます。まずはモノリス内の機能別構成やモノレポで足りないかを確かめます。

    誤解2：「MFE にすればコードもきれいに分かれる」

    MFE が決めるのはデプロイ単位だけです。 各 MFE の中身は FSD などで別に設計しないと、小さなスパゲッティが複数できるだけです。

    誤解3：「npm パッケージで取り込めば MFE になる」

    ビルド時統合では独立デプロイになりません。 1 つ変えるとシェルの再デプロイが必要です。独立してリリースしたいなら、Module Federation など実行時に統合する方式が候補になります。

    8.まとめ

    • MFE は 組織の問題（独立リリース） を解く手段。技術的な流行で採らない
    • まずはモノリス内の機能別構成・モノレポで足りないかを確認する
    • 統合方式はビルド時 / Module Federation / iframe / Web Components / サーバー合成でトレードオフが違う
    • MFE の内部構成は別問題。各 MFE にも FSD などの設計が要る
