    70 品質

    アクセシビリティを部品設計に組み込む — 共通部品で作り込めば全画面に効く

    アクセシビリティ（a11y：障害の有無や利用環境にかかわらず、誰もが使えること）は、リリース前に「最後にチェックするもの」と思われがちです。このページでは a11y を 共通部品の設計に最初から組み込むもの として扱います。ネイティブ要素を優先する原則、WAI-ARIA Authoring Practices Guide（APG）のパターン、フォーカス管理、Headless UI の活用、そして仕組みで守る方法までを整理します。

    もとにしたノート：02_アクセシビリティを部品設計に組み込む

    ひとことで言うと

    a11y の問題の多くは 共通部品 1 つの作りの悪さが全画面に広がる ことで起きます。だから部品の設計で扱います。まずネイティブ要素、ない部品は APG のパターン に従い、フォーカスの移動 を設計に含めます。独自デザインとの両立には Headless ライブラリが有効で、自動チェックと手動確認を組み合わせて守ります。

    1.このページで扱うこと

    アクセシビリティ（a11y）を「最後にチェックするもの」ではなく、共通部品の設計に最初から組み込むもの として扱えるようになるのが目標です。a11y は accessibility の a と y の間に 11 文字あることから来た略記です。

    • なぜ「部品の設計」で扱うのか
    • 原則1 — まずネイティブ要素を使う
    • 原則2 — 複雑な部品は APG のパターンに従う
    • 原則3 — フォーカスを設計する
    • Headless UI を使うという判断
    • 仕組みで守る（lint・axe-core・テスト・手動確認）

    HTML の基礎としての a11y は 21_HTML（21_HTML のノート『12-アクセシビリティ』）、自動チェックの運用は 86_QAプロセス（86_QAプロセスのノート『04_アクセシビリティ（axe-core）』）が本拠地です。

    2.なぜ「部品の設計」で扱うのか

    a11y の問題の多くは、共通部品 1 つの作りの悪さが全画面に広がる ことで起きます。

    逆に言えば、共通部品を正しく作れば、全画面がまとめて改善 します。a11y はデザインシステム（デザインシステムの構成要素）の品質基準に含めるべきものです。

    基準としては WCAG 2.2（W3C の勧告。Web コンテンツのアクセシビリティ指針）が使われ、多くの組織は 適合レベル AA を目標にします。

    3.原則1 — まずネイティブ要素を使う

    WAI-ARIA（HTML に役割や状態の情報を追加するための仕様。role や aria-* 属性）の第一原則は「ネイティブの HTML 要素で済むなら ARIA を使わない」です。

    ✕ 悪い例：div をボタンにする 
    // 悪い例 — div をボタンにすると、キーボード操作・役割・フォーカスを自前で作る必要がある
<div className="btn" onClick={save}>保存</div>
    ◯ 良い例：button を使う 
    // 良い例 — button は Enter/Space・フォーカス・役割がすべて標準で付く
<button type="button" onClick={save}>保存</button>
    やりたいこと使う要素
    操作するbutton
    移動するa href
    入力に名前を付けるlabel + input（htmlFor / id）
    見出し構造h1〜h6 を順番通りに
    領域header nav main footer

    「ボタンかリンクか」は 押すと何が起きるか で決めます。画面遷移ならリンク、処理の実行ならボタンです。

    4.原則2 — 複雑な部品は APG のパターンに従う

    タブ・コンボボックス・メニュー・ダイアログなど、ネイティブ要素がない部品は WAI-ARIA Authoring Practices Guide（APG） のパターンに従います。APG は W3C が公開している実装ガイドで、部品ごとに 必要な role・aria 属性・キーボード操作 を定めています。

    部品主な role期待されるキーボード操作（抜粋）
    Tabstablist / tab / tabpanel←→ でタブ移動
    Dialog（モーダル）dialog + aria-modal="true"Esc で閉じる、Tab がダイアログ内で循環
    Comboboxcombobox / listbox / option↑↓ で候補移動、Enter で確定
    Menumenu / menuitem↑↓ で移動、Esc で閉じる

    自作する場合は、この表を 部品の仕様書 として扱い、テストで確認します。

    5.原則3 — フォーカスを設計する

    キーボード利用者とスクリーンリーダー（画面の内容を音声で読み上げるソフト）利用者にとって、フォーカスの位置 = 今いる場所 です。

    場面フォーカスの正しい動き
    モーダルを開くダイアログ内の最初の要素（または見出し）へ移す
    モーダルを閉じる開いたボタンに戻す
    SPA で画面遷移新しい画面の見出しへ移す、またはページタイトルを通知
    要素を削除次の要素か親へ移す（消えた要素に残さない）
    エラー表示エラー要約か最初のエラー項目へ移す
     
    // フォーカスの見た目は消さない（:focus-visible で必要なときだけ表示）
button:focus-visible { outline: 2px solid var(--color-focus); }

    :focus-visible は、キーボード操作のときなどブラウザが「フォーカス表示が必要」と判断したときだけ当たる CSS の疑似クラスです。

    6.Headless UI を使うという判断

    APG に沿った部品を自作するのは大変です。そこで 振る舞い（a11y・キーボード操作）だけを提供し、見た目は自由 な Headless ライブラリが選択肢になります。

    方式例向く場面向かない場面
    Headless ライブラリRadix UI, React Aria, Headless UI独自デザイン + 高い a11y 品質ライブラリの制約が合わない特殊な部品
    既製の UI ライブラリMUI など見た目もまとめて任せたいブランドに合わせて大きく変えたい
    完全自作—既存にない部品APG を読み込む時間がない
     
    // Radix UI の Dialog — フォーカス管理・Esc・aria 属性は自動で付く
<Dialog.Root>
  <Dialog.Trigger asChild><button>設定</button></Dialog.Trigger>
  <Dialog.Content>
    <Dialog.Title>設定</Dialog.Title>
    …
  </Dialog.Content>
</Dialog.Root>

    Headless の考え方自体は コンポーネントパターンの比較 を参照してください。

    7.仕組みで守る

    手段見つけられるもの限界
    eslint-plugin-jsx-a11yalt 抜け・不正な role実行時の振る舞いは分からない
    axe-core（テスト・CI）コントラスト・ラベル抜けなど自動で分かるのは一部だけ
    Testing Library の getByRole役割と名前で要素を取れるか—
    手動（キーボードのみ・スクリーンリーダー）操作の流れ・読み上げ順時間がかかる

    getByRole("button", { name: "保存" }) でテストを書くと、テストを書くこと自体が a11y の確認 になります（テストしやすいコンポーネントと構成）。

    8.よくある誤解

    誤解1：「a11y はリリース前に最後にチェックすればよい」

    後からでは直すコストが大きくなります。 問題の多くは共通部品の作りから全画面に広がっているため、最後に画面ごとに直すより、部品の設計段階で作り込む方がまとめて効きます。

    誤解2：「ARIA 属性をたくさん付ければアクセシブルになる」

    逆です。 WAI-ARIA の第一原則は「ネイティブ要素で済むなら ARIA を使わない」です。div に role を付けても、キーボード操作やフォーカスは自前で作らなければなりません。まず button や a などのネイティブ要素を使います。

    誤解3：「axe-core などの自動チェックを通れば十分」

    自動で分かるのは一部だけ です。操作の流れや読み上げ順、フォーカスの移動は、キーボードだけで操作したりスクリーンリーダーで聞いたりする手動確認で見つけます。自動チェックと手動確認を組み合わせます。

    9.まとめ

    • a11y は共通部品で作り込むと、全画面にまとめて効く
    • まずネイティブ要素、ない部品は APG のパターンに従う
    • フォーカスの移動（開く・閉じる・遷移・削除）を設計に含める
    • 独自デザインと a11y の両立には Headless ライブラリが有効。自動チェックと手動確認を組み合わせる
