    スタイリング方式の比較 — BEM・CSS Modules・CSS-in-JS・Tailwind CSS

    BEM / CSS Modules / CSS-in-JS / Tailwind CSS などのスタイリング方式を、「どれが優れているか」ではなく スコープの守り方・実行時コスト・チームとの相性 で比べ、プロジェクトに合う方式を選べるようにします。

    もとにしたノート：02_スタイリング方式の比較

    ひとことで言うと

    方式の違いは、CSS のスコープを 規約・ビルド・ランタイム・ユーティリティのどれで守るか です。選定は 「レンダリング方式 → トークンの強制力 → チームのスキル」 の順に考えます。RSC を使う構成ではランタイム型 CSS-in-JS は Client Component に限られます。トークンを CSS 変数にしておけば、方式を移行・混在させても値は一貫します。

    CSS の文法や BEM の書き方そのものは 22_CSS（ノート『CSS設計（BEM-OOCSS）』）が本拠地です。トークンの考え方は デザインシステム を先に読むと分かりやすくなります。

    2.スタイリングで解決したい問題

    CSS はもともと グローバル（書いたスタイルがページ全体に効く）です。規模が大きくなると次の問題が起きます。

    問題例
    名前の衝突別画面の .title が上書きし合う
    消せない CSSどこで使われているか分からず削除できない
    詳細度の戦争!important の連鎖
    状態との連携props に応じた見た目の切り替えが煩雑

    詳細度 とは、複数のスタイルがぶつかったときにどれを優先するかを決める CSS の規則です。上書きのために詳細度を上げ合うと、!important の連鎖に行き着きます。

    各方式は、この問題を 命名規約・ビルド・ランタイム・ユーティリティ のどれで解決するかが違います。

      規約で守る          ビルドで守る         実行時に生成         クラスを組み合わせる
  ───────────        ───────────         ───────────         ─────────────────
  BEM                 CSS Modules          CSS-in-JS           Tailwind CSS
                      ゼロランタイム CSS-in-JS（ビルド時に抽出）

    3.各方式の特徴

    3.1 BEM（命名規約）

    .card__title--large { font-size: 1.5rem; }
    • スコープは 人の規律 で守る。ツール不要で、どのフレームワークでも使える
    • 規約違反を機械的に検出しにくい

    BEM は Block（部品）__Element（部品の中の要素）--Modifier（変化形）の形でクラス名を付ける命名規約です。

    3.2 CSS Modules（ビルド時スコープ）

    import styles from "./Card.module.css";
export const Card = () => <h2 className={styles.title}>…</h2>;
// → class="Card_title__x7a2b" のようにファイル単位で一意化される
    • 普通の CSS を書きつつ、衝突をビルドで防ぐ。実行時コストなし
    • props に応じた動的スタイルはクラスの切り替えか CSS 変数で行う

    3.3 CSS-in-JS（ランタイム型）

    const Title = styled.h2<{ large?: boolean }>`
  font-size: ${(p) => (p.large ? "1.5rem" : "1rem")};
`;
    • styled-components / Emotion など。props と見た目を直接結びつけられる
    • 実行時にスタイルを生成・注入するコスト がある。React Server Components（RSC）ではランタイム型をそのままサーバーコンポーネントで使えず、Client Component にする必要がある

    RSC（React Server Components） は、サーバー側だけで描画され、ブラウザに JavaScript を送らないコンポーネントです。ブラウザで動く通常のコンポーネントは Client Component と呼ばれます。レンダリング方式の全体像は 41章：レンダリング方式 を参照してください。

    3.4 ゼロランタイム CSS-in-JS（ビルド時抽出）

    • vanilla-extract、Panda CSS、Linaria など。TypeScript で書き、ビルド時に静的 CSS に変換 する
    • 型安全とトークン連携の利点を残しつつ、実行時コストを消す

    3.5 Tailwind CSS（ユーティリティファースト）

    <h2 className="text-2xl font-bold text-gray-900 md:text-3xl">…</h2>
    • 小さなユーティリティクラス（1 つの効果だけを持つクラス）を組み合わせる。使われたクラスだけがビルドで出力される
    • CSS ファイルを探しに行かずに済む 反面、マークアップが長くなる。繰り返しは コンポーネント化 で吸収する

    5.選び方 — 向く場面 / 向かない場面

    方式向く場面向かない場面
    BEMビルド環境がない / サーバー生成 HTML 中心大人数で規約を守り切れない
    CSS Modules素の CSS を活かしたい / RSC を使う動的スタイルが大量にある
    CSS-in-JS（ランタイム）既存資産がある SPA / テーマ切り替えが多いRSC 中心の構成 / 初期表示性能を最優先
    ゼロランタイム CSS-in-JS型安全なトークンを徹底したいビルド設定を増やしたくない
    Tailwind素早く UI を作りたい / デザインシステムの値を強制したいマークアップの可読性を最優先 / デザイナーが CSS を直接書く

    判断の順番：

    1. レンダリング方式 — RSC を使うなら、ランタイム CSS-in-JS は外す（41章：レンダリング方式）
    2. トークンの強制力 — 決められた値以外を使わせたいなら Tailwind かゼロランタイム CSS-in-JS
    3. チームのスキル — CSS に強いメンバーが多いなら CSS Modules が素直

    6.混在させるときのルール

    移行期などで方式が混ざるのは珍しくありません。混乱を防ぐには次を決めます。

    • トークンは CSS 変数に一本化 し、どの方式からも同じ値を参照する
    • 新規コードの方式 を決め、既存コードは触るときに移行する
    • 共通部品（デザインシステム）と画面側で方式を分けない

    7.よくある誤解

    誤解1：「どれか 1 つが最も優れたスタイリング方式だ」

    優劣ではなく相性で選びます。 各方式はスコープを規約・ビルド・ランタイム・ユーティリティのどれで守るかが違い、レンダリング方式・トークンの強制力・チームのスキルによって向き不向きが変わります。

    誤解2：「CSS-in-JS はどれも実行時コストがある」

    ゼロランタイム型は実行時コストがありません。 vanilla-extract、Panda CSS、Linaria などはビルド時に静的 CSS に変換します。実行時コストがあり、RSC で Client Component に限られるのはランタイム型（styled-components / Emotion など）です。

    誤解3：「方式を混ぜるとデザインの値がばらばらになる」

    トークンを CSS 変数に一本化すれば一貫します。 どの方式からも同じ CSS 変数を参照させ、新規コードの方式を決めて既存コードは触るときに移行します。

    8.まとめ

    • 方式の違いは スコープを規約・ビルド・ランタイム・ユーティリティのどれで守るか
    • RSC を使う構成では、ランタイム型 CSS-in-JS は Client Component に限られる
    • トークンを CSS 変数にしておけば、方式を移行・混在させても値は一貫する
    • 選定は「レンダリング方式 → トークンの強制力 → チームのスキル」の順に考える
