    40 ディレクトリ・モジュール構成

    依存ルールの自動検査 — ディレクトリ構成のルールを CI で守らせる

    「features どうしは import しない」「上の層から下の層へだけ」といった ディレクトリ構成の依存ルールを、ツールで自動検査する 方法を学びます。ルールは文書に書くだけでは守られません。違反したら CI が落ちる 状態にして初めて、構成は長持ちします。

    もとにしたノート：04_依存ルールの自動検査

    ひとことで言うと

    依存ルールは ツールで検査して CI で止める ことで初めて守られます。手軽なのは import/no-restricted-paths、宣言的に書けるのは eslint-plugin-boundaries、全体解析・循環参照の検出は dependency-cruiser、FSD なら Steiger。既存コードは warning から始めて段階的に error にします。

    • なぜ自動検査が必要か

    • ESLint の import/no-restricted-paths

    CI（継続的インテグレーション：push や PR のたびに自動でテストや検査を走らせる仕組み）に組み込むところまでを扱います。言語やバックエンドも含めた一般論は 43章：依存ルールの自動検査 を参照してください。

    2.なぜ自動検査が必要か

    文書だけのルールツールで検査するルール
    レビューで毎回指摘が必要違反はエディタと CI で即座に分かる
    忙しい時期に崩れる崩れない（通らないとマージできない）
    新しいメンバーが知らない書いた瞬間にエラーで学べる
    「どこまで許すか」が人によって違う設定ファイルが唯一の基準になる

    依存ルールの違反は 1 行の import で起き、気づかないうちに積み重なります。後から直すのは大変なので、構成を決めたら同時に検査を入れます。

    3.主なツール

    ツール種類得意なこと
    import/no-restricted-paths（eslint-plugin-import）ESLint ルール「このフォルダからあのフォルダへの import を禁止」を簡単に書く
    eslint-plugin-boundariesESLint プラグインフォルダを「要素の種類」として定義し、種類どうしの依存を許可・禁止する
    dependency-cruiser依存解析 CLIプロジェクト全体の依存グラフを解析し、ルール検査・循環検出・可視化
    SteigerFSD 公式のリンターFSD の層・スライス・公開 API のルールをそのまま検査
    @nx/enforce-module-boundariesNx の ESLint ルールモノレポでプロジェクト間の依存をタグで制限

    ESLint は JavaScript / TypeScript のコードを規則に沿って検査するツール（リンター）です。エディタ上ですぐ気づきたいなら ESLint 系、プロジェクト全体の構造を見たいなら dependency-cruiser、FSD を採用しているなら Steiger が第一候補です。Nx のようなモノレポでの使い方は モノレポ で扱います。

    4.ESLint：import/no-restricted-paths

    bulletproof-react でも紹介されている、最も手軽な方法です。

    // eslint 設定（抜粋）
'import/no-restricted-paths': ['error', {
  zones: [
    // features どうしの import を禁止（例: comments → discussions）
    { target: './src/features/comments', from: './src/features', except: ['./comments'] },
    // 共有 → 機能 → アプリ の一方向を強制
    { target: './src/features', from: './src/app' },
    {
      target: ['./src/components', './src/hooks', './src/lib', './src/utils'],
      from: ['./src/features', './src/app'],
    },
  ],
}],

    target（import する側）が from（される側）を import するとエラーになります。

    5.eslint-plugin-boundaries

    フォルダを 要素の種類（element type） として宣言し、種類どうしの依存を許可リストで書きます。

    // 設定のイメージ（抜粋）
settings: {
  'boundaries/elements': [
    { type: 'app',      pattern: 'src/app/*' },
    { type: 'features', pattern: 'src/features/*' },
    { type: 'shared',   pattern: 'src/shared/*' },
  ],
},
rules: {
  'boundaries/element-types': ['error', {
    default: 'disallow',
    rules: [
      { from: 'app',      allow: ['features', 'shared'] },
      { from: 'features', allow: ['shared'] },
    ],
  }],
},

    許可したもの以外は禁止（default: 'disallow'）にできるので、層の多い構成でもルールが読みやすくなります。

    6.dependency-cruiser

    ESLint とは別に、CLI でプロジェクト全体の依存を解析します。

    // .dependency-cruiser.js（抜粋）
module.exports = {
  forbidden: [
    {
      name: 'no-cross-feature',
      severity: 'error',
      from: { path: '^src/features/([^/]+)/' },
      to:   { path: '^src/features/', pathNot: '^src/features/$1/' },
    },
    { name: 'no-circular', severity: 'error', from: {}, to: { circular: true } },
  ],
};
    npx depcruise src --validate
    • 循環参照（A が B を、B が A を import するような輪になった依存）の検出 が得意
    • 依存グラフを図として出力でき、構成の現状把握にも使える

    7.Steiger（FSD 用）

    FSD を採用している場合、公式のリンター Steiger で層の向き・スライス間の import・公開 API を経由しない import などをまとめて検査できます。

    npx steiger ./src

    FSD のルールを自分で ESLint 設定に書き起こす手間が省けます（Feature-Sliced Design）。

    8.導入の進め方

    1. ルールを文章で決める（どの層・フォルダからどこへ import してよいか）
    2. ツールを入れ、まず warning で現状の違反数を把握する
    3. 新しいコードから error にする（既存違反は一覧化して段階的に直す）
    4. CI に組み込み、違反があるとマージできないようにする
    判断向く向かない
    ESLint 系で始めるエディタで即座に気づきたい、ルールが少ない複雑な正規表現ルール、全体の可視化
    dependency-cruiser を足す循環参照を潰したい、構成を図で見たいルール 1〜2 個だけの小規模
    SteigerFSD を採用しているFSD 以外の構成

    9.よくある誤解

    誤解1：「ルールは README に書いてレビューで守れば十分」

    文書だけのルールは崩れます。 違反は 1 行の import で起き、忙しい時期や新しいメンバーの参加で気づかないうちに積み重なります。違反したら CI が落ちる状態にして初めて守られます。

    誤解2：「導入したらすぐに全部 error にするべき」

    既存コードがあるなら warning から始めます。 まず違反数を把握し、新しいコードから error にして、既存違反は一覧化して段階的に直します。

    誤解3：「ツールは 1 つ選べば全部できる」

    得意分野が違います。 エディタで即座に気づくなら ESLint 系、循環参照や全体の可視化なら dependency-cruiser、FSD なら Steiger です。必要に応じて組み合わせます。

    10.まとめ

    • 依存ルールは ツールで検査して CI で止める ことで初めて守られる
    • 手軽なのは import/no-restricted-paths、宣言的に書けるのは eslint-plugin-boundaries
    • dependency-cruiser は全体解析・循環参照の検出・可視化に強い
    • FSD なら Steiger でルールをまとめて検査できる
    • 既存コードは warning から始めて段階的に error にする
