    20 コンポーネント設計

    コンポーネントの分割粒度と境界

    画面を どこで部品（コンポーネント）に分けるか は、フロントエンド設計でいちばん頻繁に出てくる判断です。このページでは、分割の目的、分割を考えるサイン、境界を引く 4 つの軸、「大きすぎ」と「細かすぎ」の見分け方、そして分ける順番までを扱います。両方の失敗を避けるための 物差し を持つことが目標です。

    もとにしたノート：01_コンポーネントの分割粒度と境界

    ひとことで言うと

    部品を分ける目的は「ファイルを小さくすること」ではなく、理解しやすくし、変更を局所化する ことです。境界は 見た目の塊・状態の持ち主・データの単位・変更の理由 の 4 つの軸で引きます。props を素通しするだけの中間部品が続くのは細かすぎのサイン。共通化は 同じ UI が繰り返し出てから で十分です。

    1.このページで扱うこと

    • なぜ分割するのか（5 つの目的）
    • 分割を検討するサイン
    • 境界の引き方 — 4 つの軸
    • 粒度の目安 — 大きすぎ・細かすぎ
    • 分ける順番 — 抽出は後からでよい

    React での具体的な分け方は（32_React のノート『10-1-UIコンポーネントとロジックの分離』）が本拠地です。

    2.なぜ分割するのか

    コンポーネントを分ける目的は「ファイルを小さくすること」ではありません。

    目的意味
    理解しやすくする1 つの部品が 1 つの役割を持つ
    変更を局所化する仕様変更の影響が 1 部品に収まる
    再利用する同じ UI を複数画面で使う
    テストしやすくする小さな単位で振る舞いを確かめる
    再レンダリングを絞る変化する範囲を小さくする（再レンダリング＝状態が変わったときに部品を描き直すこと）

    再利用は目的の 1 つにすぎません。1 回しか使わない部品でも、理解と変更のために分ける価値はあります。

    3.分割のサイン

    次のような兆候があれば、分割を検討します。

    サイン例
    JSX にコメントで見出しを付けている{/* ヘッダー部分 */}
    1 つの部品に無関係な状態が並ぶ検索キーワードとモーダルの開閉とタブ
    条件分岐で見た目が大きく切り替わるisEdit ? <巨大な JSX> : <巨大な JSX>
    名前を付けにくいMainContent, Wrapper2
    一部だけ頻繁に再レンダリングされる入力欄のたびに一覧全体が描き直される

    JSX のコメント見出しは、46_メソッド設計 の「コメントが構造を代弁しているサイン」（→ 46章：サイズと抽象度）と同じ考え方です。見出しの単位がそのまま部品の候補になります。

    4.境界の引き方 — 4 つの軸

    部品の境界は、次の軸のどれかで引くと安定します。

      ┌─────────────── ページ ───────────────┐
  │ ┌─ 見た目の塊 ─┐  ┌─ 状態の持ち主 ─┐ │
  │ │ Header       │  │ SearchPanel     │ │
  │ └──────────────┘  │  (keyword)      │ │
  │ ┌─ データの単位 ─────────────────┐   │
  │ │ UserCard（User 1 件）          │   │
  │ └────────────────────────────────┘   │
  └──────────────────────────────────────┘
    軸問い例
    見た目の塊デザイン上ひとまとまりかHeader, Card, Modal
    状態の持ち主この状態を使うのはどこまでか検索条件を持つ SearchPanel
    データの単位ドメインの 1 件に対応するかUserCard, OrderRow
    変更の理由誰の要望で変わるか価格表示（営業）と在庫表示（物流）

    最後の「変更の理由」は 単一責任の原則（SRP） の考え方です。一緒に変わるものを同じ部品に、別々に変わるものを別の部品に置きます。

    5.粒度の目安 — 大きすぎ・細かすぎ

    大きすぎちょうどよい細かすぎ
    症状読むのに全体を追う必要がある名前で中身が想像できる追うのにファイルを何枚も開く
    Props使わない props が多い役割に必要な分だけprops を素通しするだけの部品
    変更小さな変更で全体が影響変更が 1〜2 部品に収まる1 つの変更で多数の部品を触る

    細かすぎ の典型は、props を下へ渡すだけの中間部品が何層も続く状態（props のバケツリレー。prop drilling とも呼ばれます）です。これは部品を増やしすぎたサインであり、children（部品のタグの間に書いた中身を受け取る特別な props）で組み立て直すか、状態の置き場所を見直します。

    ◯ 良い例：中間部品が props を素通しするだけ → children で組み立てる 
    // 中間部品が props を素通しするだけ → children で組み立てる
<Layout sidebar={<UserMenu user={user} />}>
  <Dashboard user={user} />
</Layout>

    Layout は user を知らなくてよくなり、user を使う部品に直接渡せます。

    6.分ける順番 — 抽出は後からでよい

    最初から理想の粒度を狙う必要はありません。

    1. ページ単位で素直に書く
    2. 見出しコメントが付いた塊を部品に切り出す
    3. 状態が一部でしか使われていなければ、その部品に状態を移す
    4. 2 回目・3 回目に同じ UI が出たら共通部品にする（早すぎる共通化は避ける）

    「3 回目で共通化」は DRY（Don't Repeat Yourself。同じことを繰り返し書かない原則）の早すぎる適用を避ける経験則です。似ているだけで変更理由が違う UI を共通化すると、props の分岐が増えて逆に扱いにくくなります。

    7.よくある誤解

    誤解1：「再利用しない部品は分ける意味がない」

    違います。 再利用は分割の目的の 1 つにすぎません。1 回しか使わない部品でも、理解しやすさと変更の局所化のために分ける価値 があります。

    誤解2：「部品は細かく分けるほど良い」

    細かすぎると、追うのにファイルを何枚も開き、1 つの変更で多数の部品を触ることになります。props を素通しするだけの中間部品が続いたら、children で組み立て直すか、状態の置き場所を見直します。

    誤解3：「似た UI を見つけたらすぐ共通化すべき」

    似ているだけで 変更理由が違う UI を共通化すると、props の分岐が増えて扱いにくくなります。2 回目・3 回目に同じ UI が出てから共通部品にするのが目安です。

    8.まとめ

    • 分割の目的は理解・変更の局所化・テスト・再利用・再レンダリングの抑制
    • JSX の見出しコメントや名前の付けにくさは分割のサイン
    • 境界は見た目・状態の持ち主・データの単位・変更の理由で引く
    • 細かすぎる分割（props の素通し）も問題。children で組み立て直す
    • 共通化は同じ UI が繰り返し出てから
