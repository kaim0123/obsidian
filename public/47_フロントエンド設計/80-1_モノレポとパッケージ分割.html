    モノレポとパッケージ分割 — apps と packages の切り方

    アプリが複数になったり、チームが増えたりすると、「コードをどのリポジトリ・どのパッケージに分けるか」を決める必要が出てきます。このページでは、モノレポとポリレポの違い、pnpm workspaces・Turborepo・Nx の役割の違い、apps/ と packages/ の切り方、共有 UI パッケージの作り方、よくある失敗を学びます。

    もとにしたノート：01_モノレポとパッケージ分割

    ひとことで言うと

    モノレポは、複数のアプリと共有コードを 1つのリポジトリ に置き、共有コードの変更を1つの PR で利用側まで直せる ようにする方式です。apps/ は使う側、packages/ は使われる側で、依存は apps → packages の一方向 にします。代わりに、CI で影響範囲だけをビルドする工夫が必要です。

    2.モノレポとは — ポリレポとの比較

    モノレポ（monorepo） は、複数のアプリ・ライブラリを 1 つのリポジトリ で管理する方式です。対になるのが、1 リポジトリ 1 プロジェクトの ポリレポ（polyrepo） です。

    観点モノレポポリレポ
    共有コードの変更1 つの PR で利用側まで直せるパッケージを公開 → 各リポジトリで更新
    バージョン管理内部パッケージは常に最新を参照リポジトリごとにバージョンがずれる
    CI影響範囲だけビルドする仕組みが必要リポジトリ単位で単純
    権限・独立性全員が全コードを見られるリポジトリ単位で分けやすい

    モノレポが向く場面

    • 共通 UI・型・設定を複数アプリで使う
    • 同じチーム（または近いチーム）が複数アプリを持つ
    • フロントとバックエンドで型を共有したい

    モノレポが向かない場面

    • アプリ同士がほとんど何も共有しない
    • 組織・権限を厳密に分ける必要がある
    • ビルド時間の最適化に手をかけられない

    3.ツールの役割分担

    モノレポのツールは レイヤー（担当する層）が違う ので、組み合わせて使います。下の層が「パッケージ同士をつなぐ」、上の層が「どの順に、どこまでビルドするか」を受け持ちます。

    ツール役割特徴
    pnpm workspacesパッケージ管理pnpm-workspace.yaml で対象を列挙。workspace:* で内部パッケージを参照
    Turborepoタスクランナーturbo.json でタスクの依存関係を定義。変更のないタスクはキャッシュから復元
    Nxタスクランナー＋開発基盤依存グラフの可視化、影響範囲（affected）だけの実行、コード生成、モジュール境界の lint ルール

    タスクランナー とは、ビルド・テスト・lint などの作業（タスク）を、依存関係の順に実行してくれる道具です。小〜中規模なら pnpm workspaces + Turborepo、パッケージ数が多く境界の強制まで欲しいなら Nx がよく選ばれます。

    4.apps と packages の切り方

    典型的な構成は次の通りです。

    repo/
├── apps/                 # デプロイする単位（利用する側）
│   ├── web/              # 顧客向け Next.js
│   └── admin/            # 管理画面
└── packages/             # 共有する単位（利用される側）
    ├── ui/               # 共有 UI コンポーネント
    ├── api-client/       # 型付き API クライアント
    ├── config-eslint/    # 共有 ESLint 設定
    └── config-ts/        # 共有 tsconfig

    判断のルールは 3 つです。

    1. apps は packages に依存してよいが、逆は禁止（依存は一方向）
    2. apps 同士は依存しない。共有したくなったら packages に切り出す
    3. 2 つ以上のアプリが使うまで packages に切り出さない（YAGNI ＝「今必要でないものは作らない」という原則）

    パッケージを切る粒度は、43章：モジュール設計 の凝集・結合の考え方（一緒に変わるものは一緒に置く）がそのまま使えます。

    5.共有 UI パッケージの設計

    packages/ui は デザインシステムの実装置き場 になります（デザインシステムの構成要素）。

    // packages/ui/src/Button.tsx
export type ButtonProps = {
  variant?: "primary" | "secondary";
  children: React.ReactNode;
} & React.ButtonHTMLAttributes<HTMLButtonElement>;

export function Button({ variant = "primary", ...rest }: ButtonProps) {
  return <button data-variant={variant} {...rest} />;
}
    // packages/ui/package.json（抜粋）
{
  "name": "@acme/ui",
  "exports": { "./button": "./src/Button.tsx" }
}
    • 業務ロジックを入れない（OrderButton ではなく Button）。業務知識はアプリ側の features に置く
    • exports（package.json で外に公開するファイルを指定する欄）で 公開する入口を絞る。内部ファイルへの直接 import を防げる
    • 破壊的変更は利用側アプリが全部同じリポジトリにあるので、1 PR で直せる — これがモノレポ最大の利点

    6.よくある失敗

    失敗症状対策
    packages/shared に何でも入れる全アプリが巨大パッケージに依存し、変更の影響が読めない目的別に分ける（ui / api-client / utils）
    早すぎる切り出し使うのは 1 アプリだけのパッケージが増える2 つ目の利用者が現れてから
    キャッシュ設定なしCI が毎回全ビルドで遅いTurborepo / Nx のキャッシュ・affected を使う
    依存ルールが口約束apps 同士の import が紛れ込む依存ルールの自動検査 で機械的に止める

    7.よくある誤解

    誤解1：「pnpm workspaces と Turborepo はどちらか一方を選ぶもの」

    担当する層が違います。 pnpm workspaces はパッケージ同士をつなぐ「依存のリンク」、Turborepo / Nx は「タスク実行・キャッシュ」を受け持ちます。ふつうは組み合わせて使います。

    誤解2：「共通にできそうなものは早めに packages へ切り出すべき」

    2 つ以上のアプリが使うまで切り出しません。 早すぎる切り出しは、使うのが 1 アプリだけのパッケージを増やすだけです。また、何でも入る packages/shared を作ると、変更の影響が読めなくなります。

    誤解3：「モノレポにすればビルドや CI も自然に速くなる」

    逆に、何もしないと遅くなります。 1 つのリポジトリにすべてが入るので、変更のたびに全部をビルドしがちです。Turborepo / Nx のキャッシュや affected（影響範囲だけの実行）を設定して初めて実用的になります。

    8.まとめ

    • モノレポは 共有コードを 1 PR で変えられる のが最大の利点。代わりに CI の最適化が必要
    • パッケージ管理（pnpm workspaces）とタスク実行（Turborepo / Nx）は別レイヤー
    • apps/ は使う側、packages/ は使われる側。依存は apps → packages の一方向
    • 共有 UI パッケージには業務ロジックを入れず、exports で入口を絞る
