    70 品質

    テストしやすいコンポーネントと構成 — テストの書きやすさは設計で決まる

    「このコンポーネント、テストが書けない……」という悩みの多くは、テストの技術ではなく 設計 に原因があります。このページでは、フロントエンドのテスト配分の考え方である Testing Trophy、テストしにくいコンポーネントの特徴とその対処、ロジックを層に分ける設計、ネットワーク層でモックする MSW、そして「どこまでテストするか」の判断を扱います。

    もとにしたノート：01_テストしやすいコンポーネントと構成

    ひとことで言うと

    フロントエンドでは 統合テストを最も厚く し、E2E は主要導線だけに絞ります。通信の直書き・計算の埋め込み・現在時刻への依存といった テストしにくさの原因は設計で取り除き、純粋関数・フック・表示に分けて層ごとに合ったテストを書きます。テストは 実装ではなく振る舞い を検証します。

    1.このページで扱うこと

    テストが書きやすいかどうかは設計で決まる ことを理解し、どの層を・どの種類のテストで守るかを判断できるようになるのが目標です。

    • Testing Trophy — フロントエンドのテスト配分
    • テストしにくいコンポーネントの特徴と設計での対処
    • ロジックの分離 — 純粋関数・カスタムフック・表示コンポーネント
    • MSW — ネットワーク層でモックする
    • 構成の判断 — どこまでテストするか

    テストの種類と Testing Library の使い方は 32_React（32_React のノート『13-1-テストの種類』『13-2-Testing-Libraryの基本』）、テスト戦略全体は 81_テスト戦略 が本拠地です。モジュール単位でのテストしやすさは 43章：テストしやすいモジュール設計 も参考になります。

    2.Testing Trophy — フロントエンドのテスト配分

    Kent C. Dodds が提唱した Testing Trophy は、フロントエンドでは 統合テストを厚くする 配分を勧めます。トロフィー（優勝カップ）の形にたとえ、幅が広いほどテストを多く書く層を表します。

    層対象道具の例
    静的解析型の誤り・危険な書き方TypeScript, ESLint
    単体純粋関数・カスタムフックのロジックVitest, Jest
    統合コンポーネント + 状態 + API のモックTesting Library + MSW
    E2Eログイン → 購入など主要導線Playwright, Cypress

    理由は、ユーザーが触るのは部品の組み合わせ だからです。細かい部品を個別にテストしても、組み合わせたときの不具合は見つかりません。

    3.テストしにくいコンポーネントの特徴

    ✕ 悪い例：テストしにくいコンポーネント 
    // テストしにくい例
function OrderPage() {
  const [orders, setOrders] = useState<Order[]>([]);
  useEffect(() => {
    fetch("/api/orders").then(r => r.json()).then(setOrders); // 通信が直書き
  }, []);
  const total = orders.reduce((s, o) => s + o.price * 1.1, 0); // 計算が埋め込み
  return <div>{new Date().toLocaleDateString()} 合計: {total}</div>; // 現在時刻に依存
}
    特徴何が困るか設計での対処
    通信が直書きテストで本物の API を叩くAPI レイヤに分離し、MSW でモック
    計算が JSX に埋め込み計算だけを検証できない純粋関数に切り出す
    現在時刻・乱数に依存結果が毎回変わる引数や props で注入する
    グローバル状態に直接依存テストごとに状態が漏れるProvider で包んで初期値を渡す

    注入する とは、部品の中で値を作るのではなく、外から引数や props として渡してもらうことです。テストでは固定の値を渡せるので、結果が毎回同じになります。

    4.ロジックの分離 — テストの層を分ける設計

    ロジックを 純粋関数 → カスタムフック → 表示コンポーネント に分けると、それぞれに合ったテストを書けます（32_React のノート『10-1-UIコンポーネントとロジックの分離』『10-3-カスタムフック』）。純粋関数 は、同じ入力に対していつも同じ出力を返し、外の状態を変えない関数です。

    ◯ 良い例：1. 純粋関数 
    // 1. 純粋関数 — 単体テストが最も簡単
export const calcTotal = (orders: Order[], taxRate: number) =>
  orders.reduce((s, o) => s + o.price, 0) * (1 + taxRate);
    ◯ 良い例：2. 表示 
    // 2. 表示 — props だけで描画が決まる
export function OrderSummary({ total }: { total: number }) {
  return <p>合計: {total.toLocaleString()}円</p>;
}
    層テスト方法速さ
    純粋関数入力 → 出力を assert非常に速い
    カスタムフックrenderHook または画面の統合テストで速い
    表示コンポーネントprops を渡して描画を確認 / Storybook速い
    画面（組み合わせ）統合テスト + MSW中

    この分け方は「部品をどこで切るか」の話でもあります（コンポーネントの分割粒度と境界）。

    5.MSW — ネットワーク層でモックする

    MSW（Mock Service Worker） は、fetch や axios を差し替えるのではなく、リクエストをネットワークの層で横取り して偽のレスポンスを返します。モック とは、テストのために本物の代わりに使う偽物のことです。

    // mocks/handlers.ts
import { http, HttpResponse } from "msw";
export const handlers = [
  http.get("/api/orders", () => HttpResponse.json([{ id: "o_1", price: 1000 }])),
];
    利点説明
    実装の詳細に依存しないfetch から axios に変えてもテストはそのまま
    開発でも使えるバックエンド未完成でも画面を作れる
    Storybook と共有できる同じハンドラを部品カタログでも使う

    エラー系（500・タイムアウト）もハンドラで再現できるため、エラー境界とフォールバック UI の確認にも使えます。

    6.構成の判断 — どこまでテストするか

    判断目安
    単体テストを書く対象分岐の多い計算・変換・バリデーション
    統合テストの単位1 画面 or 1 機能（Feature）単位
    E2E の対象止まると売上や業務に直結する導線だけ
    見た目の確認Storybook + ビジュアルリグレッション

    ビジュアルリグレッション は、画面のスクリーンショットを前回と比べて、見た目の意図しない変化を検出するテストです。

    振る舞いを検証する

    テストは 実装ではなく振る舞い を検証します。「state が変わったか」ではなく「画面に何が表示されたか」を確認すると、リファクタリングで壊れにくくなります。

    7.よくある誤解

    誤解1：「部品ごとの単体テストをたくさん書けば品質は守れる」

    それだけでは足りません。 ユーザーが触るのは部品の組み合わせなので、個別の部品をテストしても組み合わせたときの不具合は見つかりません。フロントエンドでは画面単位の統合テストを最も厚くします。

    誤解2：「テストしにくいのはテストの書き方が下手だから」

    多くは設計の問題です。 通信の直書き・JSX への計算の埋め込み・現在時刻への依存などがあると、どう工夫してもテストは書きにくくなります。API レイヤへの分離、純粋関数への切り出し、値の注入で原因そのものを取り除きます。

    誤解3：「state の値が正しく変わったかを確認するのがよいテスト」

    実装の詳細に依存したテストは壊れやすい です。内部の state ではなく「画面に何が表示されたか」を確認すると、内部をリファクタリングしてもテストはそのまま通ります。

    8.まとめ

    • Testing Trophy では 統合テストを最も厚く、E2E は主要導線だけに絞る
    • テストしにくさの原因（通信直書き・計算埋め込み・時刻依存）は設計で取り除く
    • 純粋関数・フック・表示に分けると、層ごとに最適なテストが書ける
    • MSW でネットワーク層をモックすれば、実装を変えてもテストが壊れない
