    85 ケーススタディ

    RADIO テンプレート — UI 設計を決まった順番で考える

    「この UI をどう設計するか」と聞かれたとき、思いついた順に話すと抜け漏れや脱線が起きます。このページでは、GreatFrontEnd が提唱する RADIO フレームワーク（要件 → 全体構成 → データ → 境界 → 最適化）を学びます。85 ケーススタディの各ページは、このテンプレートに沿って書かれています。

    もとにしたノート：01_RADIOテンプレート

    ひとことで言うと

    RADIO は Requirements（要件）→ Architecture（全体構成）→ Data model（データ）→ Interface（境界）→ Optimizations（最適化） の順に UI を設計する型です。前の段階が決まらないと次が決まらない ので順番に意味があり、各段階で 47 の 20〜70 の知識を使う総合演習になります。

    1.このページで扱うこと

    「この UI をどう設計するか」を 決まった順番で考えるための型 として、GreatFrontEnd が提唱する RADIO フレームワーク を学びます。

    • RADIO の5段階と、順番に意味がある理由
    • 各段階で問うこと
    • 設計メモの記入テンプレート
    • 使うときのコツと、向く場面・向かない場面

    このテンプレートを実際に使った例は、ニュースフィード、オートコンプリート、管理画面の一覧とフォーム の3つのケーススタディで扱います。

    2.RADIO とは

    フロントエンドのシステム設計を 5 段階で進める手順の頭文字です。もとは面接対策として整理されたものですが、実務の設計メモにもそのまま使えます。

    文字英語日本語決めること
    RRequirements要件何を作るか・どこまで作るか
    AArchitecture全体構成どんな部品があり、どうつながるか
    DData modelデータどんなデータを、どこに持つか
    IInterface (API)境界部品同士・サーバーとの約束
    OOptimizations最適化性能・a11y・エラー・細部の深掘り

    順番に意味があります。要件が決まらないと構成は決まらず、構成が決まらないとデータの置き場所は決まらない からです。

    3.各段階で問うこと

    3.1 R — Requirements（要件）

    問い例
    主要なユースケースは？投稿を見る・いいねする・新しい投稿を読む
    対象デバイス・環境は？モバイル中心、低速回線あり
    規模は？1 画面に何件、どれくらいの頻度で更新
    範囲外は？投稿の作成は今回扱わない

    ユースケース とは、利用者がその画面で何をするかを1つずつ書き出したものです。

    3.2 A — Architecture（全体構成）

    • 画面をどんな コンポーネント に分けるか（コンポーネントの分割粒度と境界）
    • どこが サーバー状態（サーバーから取ってきたデータ）、どこが クライアント状態（ブラウザの中だけにある状態）か
    • レンダリング方式（SSR / CSR）と、API との接続点

    3.3 D — Data model（データ）

    • 主要なエンティティ（画面で扱う「もの」の単位。投稿・ユーザーなど）とフィールド
    • それぞれの 置き場所（状態の分類と置き場所）
    • 正規化するか、真実の源（SSOT） はどこか（SSOT と派生状態）

    3.4 I — Interface（境界）

    • サーバー API：エンドポイント・パラメータ・レスポンス・ページネーション
    • コンポーネント API：主要コンポーネントの Props（Props はコンポーネントの公開 API）

    3.5 O — Optimizations（最適化・深掘り）

    • 性能：初期表示・再レンダリング・大量リスト（パフォーマンスを設計で作り込む）
    • アクセシビリティ：キーボード操作・読み上げ（アクセシビリティを部品設計に組み込む）
    • エラー・オフライン（エラー境界とフォールバック UI）
    • セキュリティ・国際化

    4.記入テンプレート

    新しい設計メモを書くときは、次をコピーして埋めます。

    # 〇〇の設計

## R. 要件
- 機能要件:
- 非機能要件（性能・対応端末・a11y）:
- 範囲外:

## A. 全体構成
（コンポーネント図を ASCII で）
- サーバー状態:
- クライアント状態:
- レンダリング方式:

## D. データモデル
| エンティティ | 主なフィールド | 置き場所 |
|---|---|---|

## I. インターフェース
- サーバー API:
- 主要コンポーネントの Props:

## O. 最適化・深掘り
- 性能:
- a11y:
- エラー・オフライン:
- トレードオフと選ばなかった案:

    5.使うときのコツ

    コツ理由
    R に時間を使う範囲を決めないと O で話が発散する
    A は箱と矢印だけで描く細部はあとで変わる。まず全体の形を合意する
    D と I は表にする抜け漏れが見える
    O は「選ばなかった案」も書く判断の理由が残る（フロントエンドの規約と ADR）

    向く場面

    • 新しい画面・機能の設計を始めるとき
    • 設計レビューの資料
    • フロントエンドのシステム設計面接

    向かない場面

    • 既存画面の小さな修正
    • ライブラリの使い方の調査
    • デザインの見た目だけの議論

    6.よくある誤解

    誤解1：「RADIO は面接対策のためのもの」

    もとは面接対策として整理されたものですが、実務の設計メモにもそのまま使えます。 新しい画面・機能の設計を始めるときや、設計レビューの資料づくりに向いています。

    誤解2：「早く本題に入りたいので、要件（R）はさっと済ませてよい」

    R にこそ時間を使います。 範囲（特に「範囲外」）を決めないと、最後の O で性能・a11y・エラーの話がどこまでも広がり、発散します。

    誤解3：「設計メモには採用した案だけを書けばよい」

    「選ばなかった案」も書きます。 なぜその案を選ばなかったのかが残っていないと、後から同じ検討を繰り返したり、前提が変わったときに見直せなかったりします。

    7.まとめ

    • RADIO = 要件 → 全体構成 → データ → 境界 → 最適化 の順に考える型
    • 順番に意味がある。前の段階が決まらないと次が決まらない
    • 各段階は 47 の各フォルダ（20〜70）の知識を使う総合演習になる
    • 記入テンプレートを使い、「選ばなかった案」も残す
