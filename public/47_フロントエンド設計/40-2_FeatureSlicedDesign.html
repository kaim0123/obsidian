    40 ディレクトリ・モジュール構成

    Feature-Sliced Design — 層・スライス・セグメントで import の向きを制限する

    Feature-Sliced Design（FSD） は、フロントエンドのコードを 層（layer）・スライス（slice）・セグメント（segment） の 3 段階で整理し、import の向きを制限する 設計方法論です。このページでは、6 つの層の役割、entity と feature の区別、import のルール、公開 API の考え方を学びます。

    もとにしたノート：02_Feature-Sliced_Design

    ひとことで言うと

    コードを layer × slice × segment の 3 段階で置き、上の層から下の層へだけ import し、同じ層どうしは import しません。entity は「もの」（名詞）、feature は「操作」（動詞）。スライスは index.ts の 公開 API 経由でだけ 使います。全部の層を最初からそろえず、小さく始めて必要な層を足していきます。

    1.このページで扱うこと

    • FSD とは（2 つの中心的な考え）
    • layer・slice・segment の 3 段階の構造
    • 6 つの層の役割と、features と entities の区別
    • import のルール（上→下のみ、同じ層どうしは禁止、@x 記法）
    • 公開 API（Public API）
    • 向く場面・向かない場面

    方式どうしの比較は ディレクトリ構成の比較、ルールの自動検査は 依存ルールの自動検査 で扱います。

    2.FSD とは

    FSD は、ロシア語圏のフロントエンドコミュニティ発の方法論で、公式ドキュメント（feature-sliced.design）として公開されています。大規模で長く育つ SPA（Single Page Application：1 枚の HTML の中で画面を切り替えるアプリ）・複数チーム開発を想定しています。

    中心となる考えは 2 つです。

    • 標準化された層 にコードを分け、どこに何を置くかを迷わせない
    • 上の層は下の層だけを使う。逆向き・同じ層どうしの import を禁止する

    3.3 段階の構造

    src/
├── app/                 ← 層（layer）
├── pages/
│   └── product-detail/  ← スライス（slice）= 業務上の切れ目
│       ├── ui/          ← セグメント（segment）= 技術的な役割
│       ├── model/
│       └── index.ts     ← 公開 API
├── widgets/
├── features/
│   └── add-to-cart/
├── entities/
│   └── product/
│       ├── ui/
│       ├── model/
│       ├── api/
│       └── index.ts
└── shared/
    ├── ui/
    ├── api/
    ├── lib/
    └── config/
    段階分ける軸例
    Layer（層）責務の広さ（固定の名前）app, pages, widgets, features, entities, shared
    Slice（スライス）業務ドメインproduct, cart, user, add-to-cart
    Segment（セグメント）技術的な役割ui, model, api, lib, config

    4.層（上から順に）

    層役割スライス
    appアプリの起動・プロバイダ・ルーティング・グローバルスタイルなし
    （processes）複数ページにまたがるフロー。非推奨（現在は使わない）—
    pages1 画面（ルート）単位の組み立てあり
    widgetsページを構成する大きな自己完結ブロック（ヘッダー、商品一覧パネル）あり
    featuresユーザーに価値を与える 操作（カートに追加、ログイン、コメント投稿）あり
    entities業務上の もの（商品、ユーザー、注文）の表示とデータあり
    shared業務に依存しない共通部品（UI キット、API クライアント、ユーティリティ）なし

    プロバイダ は、アプリ全体に設定や状態を配る仕組み（React の Context Provider など）です。

    features と entities の区別 が最初の難所です。

    entity = 名詞

    商品、ユーザー。「商品カード」「ユーザーのアバター」

    feature = 動詞

    カートに追加する、ログインする。ボタンとその処理

    すべての層を使う必要はありません。小さめのプロジェクトでは app / pages / shared から始め、必要になってから widgets・features・entities を切り出す進め方も公式に案内されています。

    5.import のルール

      app
   ↓
  pages
   ↓
  widgets
   ↓
  features
   ↓
  entities
   ↓
  shared
    • 上の層は、自分より下の層だけを import できる
    • 同じ層のスライスどうしは import しない（features/add-to-cart から features/login を使わない）
    • 同じ層のものを組み合わせたいときは、1 つ上の層で組み立てる
    ✕ NG：feature どうしの import 
    // features/add-to-cart/ui/AddToCartButton.tsx
import { useAuth } from '@/features/login';
    ◯ OK：下の層（entities）を使う 
    import { useCurrentUser } from '@/entities/user';

    entities どうしがどうしても参照し合う場合（注文が商品を含むなど）のために、公式には @x 記法（明示的な相互参照用の公開 API）が用意されています。乱用せず、例外として扱います。

    6.公開 API（Public API）

    各スライスは index.ts で外に見せるものだけを export します。外からはスライスの内部ファイルを直接 import しません。

    // entities/product/index.ts
export { ProductCard } from './ui/ProductCard';
export { useProduct } from './api/useProduct';
export type { Product } from './model/types';
    ◯ OK：公開 API から import 
    import { ProductCard } from '@/entities/product';
    ✕ NG：内部ファイルに依存 
    import { ProductCard } from '@/entities/product/ui/ProductCard';

    公開 API があると、スライス内部のファイル構成を変えても 使う側を壊さない で済みます（情報隠蔽 のディレクトリ版）。

    7.向く場面・向かない場面

    向く向かない
    画面・機能が多く、長期運用する SPA数画面の小さなアプリ・短命な試作
    複数人・複数チームで開発する一人開発で構成ルールを守る必要が薄い
    依存が絡み合い、変更の影響が読めなくなっているフレームワークが強い構成規約を持ち、衝突する場合（要調整）

    Next.js の App Router のように フレームワーク側がディレクトリに意味を持たせる 場合は、ルーティング用の app/ と FSD の層を分けて置くなどの調整が必要です。

    8.よくある誤解

    誤解1：「FSD を採用するなら、最初から 6 層すべてを作る」

    すべての層を使う必要はありません。 小さめのプロジェクトでは app / pages / shared から始め、必要になってから widgets・features・entities を切り出す進め方が公式に案内されています。

    誤解2：「商品に関するものは全部 features/product に置けばよい」

    「もの」と「操作」を分けます。 商品カードのような「もの」の表示とデータは entities/product、「カートに追加する」のような操作は features/add-to-cart です。

    誤解3：「同じ層の別スライスの機能が必要なら、直接 import してよい」

    同じ層どうしの import は禁止です。 組み合わせたいときは 1 つ上の層（たとえば widgets や pages）で組み立てます。entities どうしの避けられない参照だけは、@x 記法で例外として扱います。

    9.まとめ

    • FSD は layer × slice × segment の 3 段階でコードを置く
    • 層は app / pages / widgets / features / entities / shared（processes は非推奨）
    • 上の層から下の層へだけ import し、同じ層どうしは import しない
    • entity は「もの」、feature は「操作」
    • スライスは index.ts の公開 API 経由でだけ使う
    • 小さく始めて、必要な層だけ足していく
