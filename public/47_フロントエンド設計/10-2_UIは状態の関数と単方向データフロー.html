    10 基礎

    UI = f(state) と単方向データフロー

    現代のフロントエンド設計の土台には、2 つの考え方があります。UI は状態の関数（UI = f(state)） と 単方向データフロー です。このページでは、命令的 UI と宣言的 UI の違いから始めて、「データは props で下へ、変更はイベントで上へ」というルール、双方向バインディングとの比較、そしてこの 2 つから導かれる設計判断までを扱います。コンポーネント設計（20）も状態設計（30）も、この 2 つを前提に組み立てられています。

    もとにしたノート：02_UIは状態の関数と単方向データフロー

    ひとことで言うと

    DOM を命令的に書き換える代わりに、「この状態ならこう見える」と宣言 します（UI = f(state)）。すると設計の問いは「DOM をどう変えるか」から 「どんな状態を持つか」 に移ります。複数の部品では、データは props で親から子へ、変更はイベントで子から親へ 流し、状態を書き換えるのはその 持ち主だけ にします。

    1.このページで扱うこと

    • 命令的 UI と宣言的 UI の違い
    • UI = f(state) という考え方と、その性質
    • 単方向データフロー（props で下へ、イベントで上へ）
    • 双方向バインディングとの比較
    • この 2 つから導かれる設計判断

    2 つの考え方が生まれた歴史は フロントエンド設計の変遷（State Driven UI・Unidirectional Data Flow）で扱っています。

    2.命令的 UI と宣言的 UI

    jQuery 時代の UI は、「何が起きたら DOM をどう書き換えるか」 を 命令的（手順を 1 つずつ指示する書き方）に書いていました。

    ✕ 命令的：変化のたびに DOM を直接操作 
    // 命令的: 変化のたびに DOM を直接操作
$('#add').on('click', () => {
  count++;
  $('#count').text(count);
  if (count > 10) $('#warning').show();
});

    状態が増えると「どの操作がどの DOM を変えたか」を追えなくなり、DOM そのものが真実 になってしまいます。

    宣言的 UI では、「この状態ならこう見える」 だけを書きます。

    ◯ 宣言的：状態から見た目を決める 
    // 宣言的: 状態から見た目を決める
function Counter({ count }: { count: number }) {
  return (
    <>
      <p>{count}</p>
      {count > 10 && <p role="alert">多すぎます</p>}
    </>
  );
}

    3.UI = f(state)

    宣言的 UI を一言で表すと UI = f(state) です。状態（state）を入力に、コンポーネントという関数 f が UI を出力します。

       state ──▶ [ f = コンポーネント ] ──▶ UI
    性質意味設計上のうれしさ
    同じ状態なら同じ見た目f は純粋関数（同じ入力なら必ず同じ出力を返し、外部に影響を与えない関数）に近い再現・テストがしやすい
    状態だけを変えるDOM は触らない変更箇所が 1 か所に集まる
    見た目は結果表示は状態から導かれる表示のズレが起きにくい

    設計の問いは「DOM をどう変えるか」から 「どんな状態を持つか」 に移ります。状態の設計が良ければ UI は自然に正しくなり、状態の設計が悪ければどれだけ UI を工夫してもバグが残ります。

    4.単方向データフロー

    UI = f(state) を複数のコンポーネントに広げたときのルールが 単方向データフロー です。2014 年に Facebook が Flux アーキテクチャとして発表し、Redux などに受け継がれました。

    • データは親から子へ props で流れる
    • 変更は子から親へイベント（コールバック。親が渡しておき、子が呼び出す関数）で伝える
    • 状態を書き換えるのは、その状態の 持ち主だけ
    function Parent() {
  const [name, setName] = useState('');
  // 状態の持ち主は Parent。子は表示と「変えたい」の通知だけ
  return <NameInput value={name} onChange={setName} />;
}

    5.双方向バインディングとの比較

    AngularJS（1.x）などの 双方向バインディング は、View とモデル（データ）が互いに更新し合います。

    観点双方向バインディング単方向データフロー
    記述量少ない（フォームが楽）やや多い（onChange を書く）
    変更の追跡どこから変わったか追いにくい持ち主とイベントを見ればわかる
    規模が大きいとき連鎖更新でデバッグが難しい流れが一方向なので予測しやすい
    向く場面小さなフォーム中心の画面画面間でデータを共有するアプリ

    Vue の v-model のように、書き方は双方向でも中身は単方向（props + イベントの 糖衣構文。同じ処理を短く書けるようにした書き方）という設計も一般的です。

    6.設計判断への効き方

    この 2 つの考え方から、後の章で使う判断基準が導かれます。

    原則導かれる判断詳しく
    UI は状態の結果状態は最小限に、派生値は計算で出すSSOT と派生状態
    状態には持ち主がいる状態は使う部品の最も近い共通の親に置く状態の分類と置き場所
    データは上から下へ部品は props を受け取り、イベントを返すProps は公開 API
    表示と状態を分ける表示専用部品とロジックを分けるコンポーネントパターン

    7.よくある誤解

    誤解1：「UI = f(state) なら、状態はたくさん持つほど便利」

    逆です。 UI が状態の結果である以上、状態の設計が UI の正しさを決めます。状態は最小限 にし、計算で出せる値（派生値）は状態として持たずに毎回計算します（→ SSOT と派生状態）。

    誤解2：「単方向データフローでは、子は親の状態を変えられない」

    変えられます。ただし 直接書き換えるのではなく、イベント（コールバック）で「変えたい」と通知 し、実際に書き換えるのは状態の持ち主（親）です。onChange={setName} がその形です。

    誤解3：「Vue の v-model は双方向バインディングだから単方向ではない」

    v-model は 書き方が双方向に見えるだけ で、中身は props + イベントの糖衣構文です。データの流れそのものは単方向に保たれています。

    8.まとめ

    • 命令的に DOM を操作する代わりに、状態から見た目を宣言する（UI = f(state)）
    • 設計の中心は「どんな状態を持つか」に移る
    • 単方向データフロー: データは props で下へ、変更はイベントで上へ
    • 双方向バインディングは記述が楽だが、規模が大きいと変更の追跡が難しい
