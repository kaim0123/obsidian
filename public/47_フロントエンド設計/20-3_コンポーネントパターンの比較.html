    20 コンポーネント設計

    コンポーネントパターンの比較 — Container-Presentational・Headless・Compound

    1 つの部品に「見た目」と「振る舞い（状態・データ取得・操作）」が混ざると、見た目だけ変えたいときも、振る舞いだけ再利用したいときも困ります。このページでは、その分け方の代表的なパターン — Container-Presentational・Render Props / HOC・カスタムフック・Compound Components・Headless UI — を比較し、場面に応じて選べるようにします。

    もとにしたノート：03_コンポーネントパターンの比較

    ひとことで言うと

    どのパターンも 「見た目」と「振る舞い」を分ける ための手段です。ロジックの共有は今は カスタムフック が主流、構造が柔軟な UI（Tabs・Menu など）は Compound Components、独自デザインでアクセシビリティを担保したいなら Headless UI。パターンは目的で選び、小さな部品に機械的に当てはめません。

    2.パターンが解こうとしている問題

    どのパターンも、根本では同じ問題を解いています。

    共通の問題

    1 つの部品に「見た目」と「振る舞い（状態・データ取得・操作）」が混ざる
    → 見た目だけ変えたい / 振る舞いだけ再利用したい ときに困る

    パターン分けるもの登場
    Container-Presentationalデータ取得・状態 と 表示2015 年、Dan Abramov の記事で広まる
    Render Props / HOC振る舞い を部品間で共有React コミュニティ（2016〜2017 年頃）
    カスタムフック振る舞い を関数として共有React 16.8（2019 年）の Hooks 以降
    Compound Components1 つの UI を協調する複数部品に分けるHTML の <select>/<option> に着想
    Headless UI振る舞い・a11y だけを提供し、見た目を持たないHeadless UI・Radix・TanStack Table など

    Render Props は「何を描くか」を関数として props で受け取る書き方、HOC（Higher-Order Component）は部品を受け取って機能を足した新しい部品を返す関数です。

    3.Container-Presentational

      [ UserListContainer ]  データ取得・状態・イベント処理
          │ props
          ▼
  [ UserList ]           props を受け取って描くだけ
    • Presentational: props → 見た目。状態を持たない（持っても UI 状態のみ）
    • Container: データを用意し、Presentational に渡す

    Hooks 登場後、Dan Abramov 自身が「このパターンを機械的に強制する必要はない」と追記しています。現在は カスタムフックでロジックを切り出し、部品は 1 つのまま にする書き方が主流です。ただし「表示専用の部品を作る」という考え方自体は、Storybook（部品を単独で表示・確認できるカタログツール）での確認やテストのしやすさの点で今も有効です。

    4.カスタムフック（振る舞いの関数化）

    カスタムフック は、useState などの Hooks を組み合わせたロジックを use〜 という名前の関数に切り出したものです。

    function useUserList() {
  const [keyword, setKeyword] = useState('');
  const { data } = useUsers(keyword);
  return { users: data ?? [], keyword, setKeyword };
}

function UserListPage() {
  const { users, keyword, setKeyword } = useUserList();
  return <UserList users={users} keyword={keyword} onKeywordChange={setKeyword} />;
}

    Render Props や HOC が担っていた「振る舞いの共有」は、多くの場合カスタムフックで置き換えられます。部品の入れ子が深くならない点が大きな利点です。

    5.Compound Components

    1 つの UI を、暗黙に状態を共有する複数の部品 として公開します。

    <Tabs defaultValue="profile">
  <Tabs.List>
    <Tabs.Trigger value="profile">プロフィール</Tabs.Trigger>
    <Tabs.Trigger value="settings">設定</Tabs.Trigger>
  </Tabs.List>
  <Tabs.Content value="profile"><Profile /></Tabs.Content>
</Tabs>

    親（Tabs）が状態を持ち、Context（props を経由せずに、離れた子孫の部品へ値を届ける React の仕組み）で子に共有します。利用者は 並び順や中身を自由に組み立てられる 一方、props を大量に渡す必要がありません。

    6.Headless UI

    振る舞いとアクセシビリティ（キーボード操作・ARIA 属性）だけ を提供し、見た目は利用者が付けるパターンです。ARIA 属性 は、スクリーンリーダーなどの支援技術に部品の役割や状態を伝えるための HTML 属性です。

    提供するもの提供しないもの
    開閉状態・フォーカス管理色・余白・フォント
    キーボード操作CSS
    ARIA 属性デザイン

    Radix UI、Headless UI、React Aria、TanStack Table などが代表例です。デザインシステムを自前で持つチーム にとって、難しい a11y を再実装せずに見た目を完全に制御できる点が利点です。shadcn/ui は Radix の上にスタイルを付けたコードを自分のリポジトリにコピーして使う方式で、同じ考え方の延長にあります。

    7.比較と選び方

    パターン向く場面向かない場面
    Container-Presentational表示部品を単独で確認・テストしたい小さな部品（分けるほうが冗長）
    カスタムフック状態・データ取得のロジックを共有したい見た目ごと共有したい
    Render Props描画の一部を利用者に委ねたい（仮想リストの行など）単純なロジック共有（フックで足りる）
    Compound Components構造が柔軟な UI（Tabs, Menu, Accordion）構造が固定の単純な部品
    Headless UI独自デザインで a11y を担保したい既製デザインで早く作りたい

    迷ったときは、次の問いを上から順に確かめます。

    1. 見た目ごと再利用したい？ — はい → 普通の部品（＋ variant）
    2. 構造を利用者に組ませたい？ — はい → Compound Components
    3. ロジックだけ共有したい？ — はい → カスタムフック（a11y が難しい UI なら Headless UI を採用）
    4. 表示を単独で確認したい → 表示専用部品に分ける

    8.よくある誤解

    誤解1：「すべての部品を Container と Presentational に分けるべき」

    提唱者の Dan Abramov 自身が、Hooks 登場後に 機械的に強制する必要はない と追記しています。今はカスタムフックでロジックを切り出し、部品は 1 つのままにする書き方が主流です。ただし「表示専用の部品を作る」考え方は、Storybook での確認やテストのために今も有効です。

    誤解2：「Headless UI は見た目がないので、自分で作るのと変わらない」

    Headless UI が肩代わりするのは、開閉状態・フォーカス管理・キーボード操作・ARIA 属性 といった、正しく作るのが難しい部分です。見た目を完全に自分で決めつつ、a11y を再実装しなくて済むのが価値です。

    誤解3：「新しいパターンほど優れている」

    パターンは 目的で選ぶ ものです。構造が固定の単純な部品に Compound Components を使ったり、小さな部品を Container と Presentational に分けたりすると、かえって冗長になります。

    9.まとめ

    • どのパターンも「見た目」と「振る舞い」を分けるための手段
    • Container-Presentational は考え方として有効だが、今はカスタムフックが主流
    • Compound Components は構造が柔軟な UI の公開 API に向く
    • Headless UI は独自デザイン × アクセシビリティ担保の定番
    • パターンは目的で選ぶ。小さな部品に機械的に当てはめない
