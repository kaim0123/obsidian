    フロントエンド設計の全体像 — 部品・状態・置き場所・見た目をどう決めるか

    フロントエンド設計とは何を扱う分野なのか、47章がどんな「柱」と資料を骨格にしているのか、フォルダがどんな問いごとに分かれているのか、新しい話題がどこに入るのか、そして隣の章（React・状態管理・アーキテクチャ・モジュール設計など）とどう分担しているのかをまとめた、47章の入口ページです。各ページへ進む前に、ここで全体の地図を持っておきましょう。

    もとにしたノート：MOC_フロントエンド設計体系

    ひとことで言うと

    フロントエンド設計は、ブラウザ上の UI を「どう部品に分け、状態とデータをどう流し、コードをどこに置くか」 を決める分野です。47章は コンポーネントの境界 ／ 状態の置き場所 ／ ディレクトリ・モジュール構成 ／ デザインシステム の4本柱を骨格に、フレームワークに依存しない 「判断（どれを選ぶか・なぜか）」 だけを扱います。書き方や実装は、React・状態管理などの本拠地の章に任せています。

    1.このページで扱うこと

    目次が「どこに何があるか」の一覧、フロントエンド設計の変遷が「どう発展してきたか」の年表だとすれば、このページは 「47章全体の地図」 です。読み終えたときに、次の問いに答えられることを目標にします。

    1. フロントエンド設計とは何か、47章はどんな柱と資料を骨格にしているのか
    2. フォルダ構成。どのフォルダが、どんな問いに答えているのか
    3. 新しいノート（話題）の置き場所。ある話題が47章のどこに入るのか、それとも別の章なのか
    4. 他の章との分担。React の書き方や状態管理ライブラリの使い方はどこにあるのか（本拠地の表）
    5. 各ページへの入口。フォルダごとのページ一覧と、関連する他章のノート

    2.フロントエンド設計とは何か

    2.1 フレームワークに依存しない「設計判断」

    47章は、ブラウザ上の UI を「どう部品に分け、状態とデータをどう流し、コードをどこに置くか」 を扱います。ここでいう UI（ユーザーインターフェース）は、利用者が見て操作する画面のことです。

    React・Vue などの フレームワーク（アプリの骨組みと書き方を決めてくれる土台のライブラリ）によって書き方は違いますが、「この状態はどこに持つべきか」「この部品はどこで分けるべきか」といった 判断の考え方 は共通です。47章はこの共通の判断を扱い、フレームワーク固有の書き方は扱いません。

    2.2 骨格になっている4本柱と資料

    47章の骨格は、2025 年時点で論点とされる 4本柱 です（Feature-Sliced Design の解説より）。Feature-Sliced Design（FSD） は、フロントエンドのフォルダを層と機能で分ける構成の方法論です（詳しくは Feature-Sliced Design）。

    柱決めること主なフォルダ
    コンポーネントの境界画面をどんな部品（コンポーネント）に分けるか20 コンポーネント設計
    状態の置き場所画面が覚えておく値（状態）をどこに持ち、どう流すか30 状態とデータフロー
    ディレクトリ・モジュール構成コードをどのフォルダに置き、どこからどこへの import を許すか40 ディレクトリ・モジュール構成
    デザインシステム色・余白・部品の見た目をどう一貫させるか50 デザインシステム・スタイリング

    この4本柱に、次の資料の視点を加えています。

    役割資料47章で使っている内容
    骨格Feature-Sliced Design の解説コンポーネントの境界 ／ 状態の置き場所 ／ ディレクトリ・モジュール構成 ／ デザインシステム の4本柱
    加える視点Micah Godbolt『Frontend Architecture for Design Systems』フロントエンドアーキテクチャを Code ／ Process ／ Testing ／ Documentation の4つで整理する見方
    bulletproof-react機能別構成（features/ フォルダで機能ごとにまとめる）と一方向の依存ルール
    演習GreatFrontEnd の RADIO要件 → 全体構成 → データモデル → インターフェース → 最適化 の順で UI を組み立てる枠組み

    bulletproof-react は、React アプリの構成例を GitHub で公開しているプロジェクトです（詳しくは bulletproof-react）。RADIO は Requirements・Architecture・Data model・Interface・Optimizations の頭文字です（詳しくは RADIO テンプレート）。

    3.フォルダ構成 — 設計の関心事ごとに1つの問い

    3.1 フォルダと問いの一覧

    フォルダは 設計の関心事ごと に分かれています。各フォルダは、フロントエンドについての1つの問いに答えます。

    フォルダ役割問い
    00 全体像このページ・年表（フロントエンド設計の変遷）—
    10 基礎フロントエンドの責務 ／ UI = f(state) ／ 単方向データフローフロントは何を設計するのか
    20 コンポーネント設計分割の粒度 ／ Props＝部品の API ／ Container-Presentational ／ Compound・Headless ／ Atomic Design ／ 画面関心事とドメイン連動画面をどう部品に分けるか
    30 状態とデータフロー状態の分類と置き場所 ／ SSOT ／ 派生状態 ／ サーバー状態との分担状態をどこに持ち、どう流すか
    40 ディレクトリ・モジュール構成Layer型 ／ Feature型 ／ FSD ／ bulletproof-react ／ 依存ルール ／ barrel ファイルコードをどこに置くか
    50 デザインシステム・スタイリングデザイントークン ／ CSS 設計方式の比較 ／ コンポーネントライブラリ見た目をどう一貫させるか
    60 サーバーとの境界API レイヤ ／ BFF ／ 型共有 ／ エラーの受け渡しサーバーとどうつなぐか
    70 品質テスト設計 ／ アクセシビリティ ／ パフォーマンス設計 ／ エラー境界品質をどう作り込むか
    80 スケールと組織モノレポ ／ マイクロフロントエンド ／ 規約・ADR大きくなったらどうするか
    85 ケーススタディRADIO で組み立てる設計演習—
    90 付録用語集・チェックリスト・推奨図書—

    表に出てくる言葉は、それぞれのページで詳しく説明します。ここでは一言だけ紹介します。

    • UI = f(state)：画面は「状態」を入力とする関数の結果だ、という考え方
    • Props：親の部品から子の部品へ渡す入力。部品の「公開 API」にあたる
    • SSOT（Single Source of Truth）：同じデータの「正」を1か所だけに置く原則。派生状態 は、他の状態から計算できる値
    • barrel ファイル：index.ts で公開するものだけを再エクスポートし、フォルダの入口を1つにする手法
    • デザイントークン：色・余白・フォントなどの決定を、名前の付いた値にしたもの
    • BFF（Backend for Frontend）：特定のフロントエンド専用に API を束ね・整形するサーバー層
    • ADR（Architecture Decision Record）：設計判断とその理由を短く残す文書

    4.新しいノートの置き場所 — この話はどこに入る？

    フロントエンドについての話題が47章のどこに入るか（あるいは別の章に入るか）は、次の2つの問いで決めます。ページを探すときの手がかりにもなります。

    1. フレームワーク固有の書き方か？ React の API・Hooks の話なら 32_React、Next.js の機能の話なら 33_Next.js へ。どちらでもない 設計判断 なら次へ
    2. 何を決める話か？ 決める対象に応じて、47章の 20〜80 のフォルダか、41章（レンダリング方式）へ

    同じ内容を表にすると、次のとおりです。

    問い答え置き場所
    フレームワーク固有の書き方？React の API・Hooks32_React
    Next.js の機能33_Next.js
    いいえ・設計判断 → 何を決める話？部品の分け方・Props20 コンポーネント設計
    状態の置き場所30 状態とデータフロー
    フォルダ・依存ルール40 ディレクトリ・モジュール構成
    トークン・CSS 方式50 デザインシステム・スタイリング
    API 層・BFF60 サーバーとの境界
    テスト・a11y・性能70 品質
    モノレポ・MFE80 スケールと組織
    SSR/CSR などレンダリング方式41_アーキテクチャ の「30 フロントエンド構成」（レンダリング方式）

    a11y はアクセシビリティ（accessibility の a と y の間が11文字）の略、MFE はマイクロフロントエンド（フロントエンドを独立してデプロイできる小さなアプリの集まりとして作る構成）の略です。SSR（サーバーサイドレンダリング）と CSR（クライアントサイドレンダリング）は、HTML をサーバーで作るかブラウザで作るかの違いです。

    5.他の章との分担（本拠地の表）

    フロントエンドの話題は、React・状態管理・HTTP クライアント・アーキテクチャなど多くの章と重なります。47章では 判断（どれを選ぶか・なぜか） に絞り、実装や一般論は次の章（本拠地）に任せています。

    テーマ本拠地47 で書くこと
    React でのコンポーネント実装（Hooks・Props の型）32_React の「13 コンポーネント設計」部品の分け方の一般論
    状態管理ライブラリ・状態の種類ごとの実装36_状態管理どの種類の状態をどこに置くかの判断
    HTTP クライアント・API レイヤの実装37_HTTPクライアント・ユーティリティフロントとサーバーの責務分担
    レンダリング方式（CSR/SSR/SSG/ISR/RSC）・BFF・MFE の構成41_アーキテクチャ の「30 フロントエンド構成」（レンダリング方式、BFF とマイクロフロントエンド）コードの構成への影響
    モジュール分割の一般論（凝集・結合・パッケージ原則）43 モジュール設計フロントのディレクトリへの当てはめ
    CSS の基礎・レイアウト22_CSSCSS 設計方式の比較
    HTML・アクセシビリティの基礎21_HTML部品設計に a11y を組み込む方法
    テスト戦略・ツール81_テスト戦略 ／ 83_テストツールテストしやすい部品・構成
    パフォーマンス計測・最適化67_パフォーマンス設計段階で効く判断

    SSG はビルド時に HTML を作る方式、ISR は一定間隔で HTML を作り直す方式、RSC（React Server Components）はサーバーだけで実行されるコンポーネントです。凝集 は「1つのまとまりの中身がどれだけ同じ目的に向いているか」、結合 は「まとまり同士がどれだけ依存し合っているか」を表す言葉です。

    7.よくある誤解

    誤解1：「フロントエンド設計＝React の書き方を覚えること」

    47章が扱うのは、フレームワークに依存しない 判断（部品をどこで分けるか、状態をどこに置くか、コードをどこに置くか、見た目をどう揃えるか）です。Hooks の使い方や Props の型の書き方は 32_React、状態管理ライブラリの使い方は 36_状態管理 が本拠地です（本拠地の表）。

    誤解2：「SSR や CSR の選び方も、47章で全部学べる」

    レンダリング方式・BFF・マイクロフロントエンドの 構成そのもの は 41章の レンダリング方式 と BFF とマイクロフロントエンド が本拠地です。47章では、それが コードの構成にどう影響するか と、採用するかどうかの判断（マイクロフロントエンドの判断 など）を扱います。

    誤解3：「フォルダの番号順に全部読まないと、ケーススタディに進めない」

    章末の「次の章」リンクで 10 → 85 を通読できますが、フォルダは 関心事ごとの問い で分かれているので、今困っている問い（「この状態はどこに置く？」なら 30、「このフォルダ構成でいい？」なら 40）のフォルダから読んでもかまいません。設計演習の手順を先に知りたいなら RADIO テンプレート から入る方法もあります。

    8.まとめ

    • フロントエンド設計は、ブラウザ上の UI をどう部品に分け、状態とデータをどう流し、コードをどこに置くか を決める分野
    • 骨格は コンポーネントの境界 ／ 状態の置き場所 ／ ディレクトリ・モジュール構成 ／ デザインシステム の4本柱。Godbolt の Code / Process / Testing / Documentation と bulletproof-react の機能別構成を加え、演習は RADIO で組み立てる
    • フォルダは設計の関心事ごとに分かれ、それぞれ1つの問いに答える。読む順に連番で、10 → 85 を通読できる
    • 新しい話題は「フレームワーク固有か？」→「何を決める話か？」の2つの問いで置き場所を決める
    • 47章は 判断 を書く場所。実装や一般論は 32・36・37・41・43・22・21・81/83・66 などの本拠地に任せ、リンクでつなぐ
