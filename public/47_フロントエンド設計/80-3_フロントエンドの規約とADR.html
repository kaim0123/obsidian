    80 スケールと組織

    フロントエンドの規約と ADR — 機械に守らせ、判断を残す

    チームが大きくなると、人によって書き方や判断がぶれ始めます。このページでは、規約を自動化する方法（フォーマッタ・リンター・型・CI）と、機械で検査できない規約の書き方、そして設計判断を ADR（Architecture Decision Record） として残す方法を、フロントエンドの例で学びます。

    もとにしたノート：03_フロントエンドの規約とADR

    ひとことで言うと

    規約は 機械で検査できるものから自動化 し、人が決める規約は 理由付きで短く 書きます。変えるのが高くつく設計判断は、1件1ファイルの ADR に「なぜそう決めたか」を残し、判断を変えるときは書き換えずに新しい ADR で置き換えます。

    1.このページで扱うこと

    チームが大きくなっても設計がぶれないように、規約を自動化する方法 と、設計判断を ADR（Architecture Decision Record）として残す方法 を学びます。

    • 規約は「書く」より「機械に守らせる」— レベルごとの手段
    • 人が決める規約の書き方
    • ADR とは何か、置き場所と運用
    • ADR のテンプレートと記入例
    • フロントエンドで ADR にすべき判断・しなくてよい判断

    ADR のステータスやライフサイクル、リスク分析などの一般論は 41章：意思決定と ADR で詳しく扱っています。

    2.規約は「書く」より「機械に守らせる」

    規約をドキュメントに書くだけでは、レビューで毎回指摘することになります。機械で検査できるものは機械に任せ、人は判断が必要なことに集中する のが基本方針です。

    レベル手段例
    フォーマットPrettier / Biomeインデント・引用符・改行
    コードの書き方ESLint / Biomeno-unused-vars、React Hooks のルール
    依存の方向eslint-plugin-boundaries / dependency-cruisershared から features を import しない
    型TypeScript（strict: true）any の禁止、null チェック
    アクセシビリティeslint-plugin-jsx-a11y / axeimg の alt、ラベルの欠落
    コミット時lint-staged + Husky など変更ファイルだけ検査
    CI上記を全部実行違反があればマージ不可

    フォーマッタ（Prettier など）は見た目の整形を自動で直す道具、リンター（ESLint など）は書き方の問題を見つける道具です。CI（継続的インテグレーション）は、PR のたびにこれらの検査を自動で走らせる仕組みです。

    依存の方向の検査は 依存ルールの自動検査 で詳しく扱います。

    3.人が決める規約

    機械で検査できない規約は、短く・理由付きで 文書にします。

    規約例
    命名コンポーネントは名詞（UserCard）、フックは use + 動詞/名詞
    置き場所1 つの feature でしか使わないものは feature 内に置く
    状態サーバー由来のデータはサーバー状態ライブラリに置く（状態の分類と置き場所）
    コンポーネントProps は 5〜7 個を超えたら分割を検討

    ポイント

    「なぜ」を必ず書く ことです。理由のない規約は、例外が必要な場面で判断できません。

    4.ADR とは

    ADR（Architecture Decision Record） は、アーキテクチャ上の重要な判断を 1 件 1 ファイルの短い文書 で残す手法です。Michael Nygard が 2011 年のブログ記事「Documenting Architecture Decisions」で提案しました。

    残す理由は、半年後に「なぜこうなっているのか」を誰も説明できなくなるのを防ぐためです。

    docs/adr/
├── 0001-use-feature-sliced-design.md
├── 0002-server-state-with-tanstack-query.md
└── 0003-styling-with-css-modules.md
    • 連番で管理し、一度決めた ADR は書き換えない
    • 判断を変えるときは新しい ADR を書き、古いほうを「Superseded by 0007」（0007 で置き換えられた）とする

    5.ADR のテンプレート

    Nygard の形式（タイトル / ステータス / コンテキスト / 決定 / 結果）が基本です。コンテキスト はその判断が必要になった背景や問題、結果 は決定によって良くなること・悪くなることです。

    # 0002. サーバー状態の管理に TanStack Query を使う

## ステータス
Accepted（2026-09-25）

## コンテキスト
API から取得したデータを Redux に入れており、
ローディング・キャッシュ・再取得のコードが画面ごとに重複している。

## 決定
サーバー由来のデータは TanStack Query で管理する。
Redux（または Zustand）はクライアント固有の UI 状態だけに使う。

## 結果
- 良い: 取得・キャッシュ・再取得のコードが消える
- 悪い: 既存の Redux スライスの移行作業が必要
- 中立: 新メンバーはサーバー状態とクライアント状態の区別を学ぶ必要がある

    「結果」に 悪い点も書く のが大事です。良い点だけの ADR は、後から読んだ人がトレードオフを判断できません。

    6.フロントエンドで ADR にすべき判断

    判断例
    レンダリング方式SSR / SSG / CSR をどう使い分けるか（41章：レンダリング方式）
    ディレクトリ構成FSD を採るか、どの layer を使うか（Feature-Sliced Design）
    状態管理サーバー状態・グローバル状態に何を使うか
    スタイリングCSS Modules / Tailwind / CSS-in-JS（スタイリング方式の比較）
    API との接続OpenAPI から型生成するか、tRPC か（API レイヤと型の共有）
    テスト方針どの層をどのテストで守るか

    ADR にする

    • 変えるのが高くつく判断
    • 複数の選択肢を比較した判断
    • 後から「なぜ？」と聞かれそうな判断

    ADR にしない

    • ライブラリの小さなバージョン更新
    • 規約で決まっていて迷いがない選択
    • 1 画面だけに閉じた実装の工夫

    7.よくある誤解

    誤解1：「規約はドキュメントにしっかり書けば守られる」

    書くだけでは守られません。 レビューで毎回指摘することになり、見落としも出ます。フォーマット・書き方・依存の方向・型・a11y など、機械で検査できるものはツールと CI に任せ、違反があればマージできないようにします。

    誤解2：「判断が変わったら ADR を書き直せばよい」

    ADR は書き換えません。 新しい ADR を書き、古いほうを「Superseded by 0007」とします。こうすると「いつ・なぜ判断が変わったか」の歴史が残ります。

    誤解3：「どんな小さな決定も ADR にすべき」

    対象は、変えるのが高くつく・複数案を比較した・後から「なぜ？」と聞かれそうな判断です。 小さなバージョン更新や 1 画面だけの工夫まで ADR にすると、本当に大事な判断が埋もれます。

    8.まとめ

    • 規約は 機械で検査できるものから自動化 し、人の規約は理由付きで短く書く
    • ADR は重要な判断を 1 件 1 ファイルで残す手法（Nygard, 2011）
    • ADR は書き換えず、判断を変えるときは新しい ADR で置き換える
    • フロントでは レンダリング・構成・状態・スタイリング・API 接続が ADR の典型
