    90 付録

    フロントエンド設計チェックリスト — 作る前・レビュー・リファクタリング前に確かめること

    47章（フロントエンド設計）の内容を、基礎・コンポーネント・状態・ディレクトリ構成・デザインシステム・サーバーとの境界・品質・スケールと組織の8つの観点に分けて、確認項目の一覧にした総合版のチェックリストです。各項目の理由と例は、観点ごとに示したページで確認できます。

    もとにしたノート：付録B_フロントエンド設計チェックリスト

    ひとことで言うと

    新しい画面・機能を作る前、設計レビュー、リファクタリングの着手前 に上から確認する一覧です。すべてを満たす必要はありません。チェックが付かない項目は 「なぜ満たさないのか」を説明できれば十分 です。

    1.このページで扱うこと

    このチェックリストは、47章の各フォルダの内容を「確かめる問い」の形にまとめたものです。

    1.1 使い方

    • 新しい画面・機能を作る前、設計レビュー、リファクタリングの着手前 に上から確認します。リファクタリング とは、外から見た動きを変えずにコードの中身を整えることです
    • すべてを満たす必要はありません。チェックが付かない項目は「なぜ満たさないのか」を説明できれば十分です
    • 判断に迷った項目は、各観点の「関連」に挙げたページで理由と例を確認してください

    演習の手順とは使い分ける

    このチェックリストは レビュー用 です。1つの UI を最初から設計する手順は RADIO テンプレート（要件 → 全体構成 → データモデル → インターフェース → 最適化）を使います。

    2.基礎 — 何を設計するのか

    関連：フロントエンド設計とは、UI は状態の関数と単方向データフロー

    • ☐ この画面・機能の 状態 と 表示 の関係を説明できる（UI = f(state)）
    • ☐ データは親 → 子、変更要求はイベントで子 → 親、の 一方向 に流れている
    • ☐ DOM を直接書き換えて状態を表していない
    • ☐ 設計判断（何を選び、なぜか）と、フレームワーク固有の実装を分けて考えている

    DOM（Document Object Model）は、ブラウザが HTML を部品の木として扱うための仕組みです。状態を変えれば表示が決まる、という形にしておけば、DOM を直接いじる必要はありません。

    3.コンポーネント設計

    関連：コンポーネントの分割粒度と境界、Props はコンポーネントの公開 API、コンポーネントパターンの比較、Atomic Design

    • ☐ 各コンポーネントの責務を1文で説明できる
    • ☐ 分割の理由が「再利用」「変更理由の分離」「読みやすさ」のどれかで説明できる（行数だけで分けていない）
    • ☐ Props の数が多すぎない（目安 5〜7 個。超えるなら分割か children を検討）
    • ☐ boolean の Props を組み合わせて見た目を切り替えていない（variant などの列挙に寄せる）
    • ☐ 見た目の部品がデータ取得・グローバル状態に直接依存していない
    • ☐ 同じ状態を共有する部品群は Compound や Headless を検討した
    • ☐ Atomic Design の階層分けに迷って時間を使っていない（迷うなら機能別の配置を優先）

    children は、部品のタグの間に書いた中身を受け取る特別な Props です。Compound は複数の部品が状態を共有して1つの UI を作るパターン、Headless は見た目を持たず振る舞いだけを提供する部品です。

    ✕ 悪い例：boolean の Props を組み合わせて見た目を切り替える 
    <Button primary large outline danger />  // primary と danger が同時に true だと？
    ◯ 良い例：列挙（variant）に寄せる 
    <Button variant="danger" size="lg" />  // 取りうる組み合わせが型で決まる

    4.状態とデータフロー

    関連：状態の分類と置き場所、SSOT と派生状態、36_状態管理 のノート『MOC_状態管理体系』

    • ☐ 各状態を ローカル ／ 共有 ／ サーバー ／ URL ／ フォーム のどれかに分類した
    • ☐ 状態は、それを使う部品の 最も近い共通の親 に置いている（必要以上にグローバルにしていない）
    • ☐ サーバーのデータをグローバルストアにコピーしていない（サーバー状態のキャッシュとして扱う）
    • ☐ 他の状態から計算できる値を state として持っていない（派生状態は描画時に計算）
    • ☐ 検索条件・ページ番号・タブなど、共有・再読み込みで残すべき状態は URL にある
    • ☐ 同じデータの「正」が1か所だけ（SSOT）

    グローバルストア は、アプリ全体からアクセスできる状態の置き場所（Redux・Zustand など）です。

    5.ディレクトリ・モジュール構成

    関連：ディレクトリ構成の方式比較、Feature-Sliced Design、bulletproof-react の構成、依存ルールの自動検査、32_React のノート『ディレクトリ設計』

    • ☐ 採用した構成方式（レイヤー型 ／ 機能別 ／ FSD）と、その理由がチームで共有されている
    • ☐ 1つの機能を消すとき、ほぼ1フォルダを消せば済む
    • ☐ 機能どうしが互いを直接 import していない（共通化するなら下の層へ移す）
    • ☐ 各フォルダの公開 API（index.ts など）が決まっていて、内部ファイルを直接 import していない
    • ☐ 依存ルールが Lint ／ CI で自動検査されている
    • ☐ utils/ common/ が何でも入る場所になっていない

    FSD（Feature-Sliced Design）は層と機能でフォルダを分ける構成の方法論、CI（継続的インテグレーション）はコードを push するたびに自動でテストや検査を走らせる仕組みです。

    6.デザインシステム・スタイリング

    関連：デザインシステムの構成要素、スタイリング方式の比較、22_CSS のノート『CSS設計（BEM-OOCSS）』

    • ☐ 色・余白・フォントサイズを直接値で書かず、デザイントークンを使っている
    • ☐ スタイリング方式が1つに決まっている（混在しているなら移行方針がある）
    • ☐ 共通部品はカタログ（Storybook など）で一覧・確認できる
    • ☐ 部品の使い方・使ってはいけない場面がドキュメントにある
    • ☐ デザイナーと同じ名前で部品・トークンを呼んでいる
    ✕ 悪い例：値を直接書く 
    .card { padding: 16px; color: #1a73e8; }
    ◯ 良い例：デザイントークン（名前の付いた値）を使う 
    .card { padding: var(--space-4); color: var(--color-primary); }

    7.サーバーとの境界

    関連：フロントとサーバーの責務分担、API レイヤと型の共有、37_HTTPクライアント・ユーティリティ のノート『MOC_HTTPクライアント体系』、API設計の全体像（45）

    • ☐ API 呼び出しがコンポーネントに直書きされず、API レイヤにまとまっている
    • ☐ レスポンスの型がサーバーと共有・生成されている（OpenAPI・tRPC・Zod など）
    • ☐ 外部から来たデータを境界で検証している
    • ☐ ビジネスルールの最終判断がサーバー側にある（フロントの検証は UX のため）
    • ☐ 読み込み中・空・エラーの3状態を画面ごとに設計している
    • ☐ レンダリング方式（CSR ／ SSR ／ SSG ／ RSC）を画面の性質で選んでいる → 41章の レンダリング方式

    API レイヤ は、サーバーとの通信をまとめて受け持つコードの層です。UX（ユーザー体験）のための検証とは、送信前に入力ミスをすぐ知らせるような検証のことで、ブラウザ側の検証は利用者が書き換えられるため、最終的な判断はサーバーで行います。

    8.品質

    関連：テストしやすいコンポーネントと構成、アクセシビリティを部品設計に組み込む、パフォーマンスを設計で作り込む、エラー境界とフォールバック UI

    • ☐ ロジックが純粋関数・カスタムフックに切り出され、UI なしでテストできる
    • ☐ テストは実装の詳細ではなく、ロール・ラベルなど利用者に見えるものを使っている
    • ☐ ボタン・リンク・フォーム要素に正しい HTML 要素を使っている（div ＋ onClick にしていない）
    • ☐ キーボードだけで操作でき、フォーカスの移動が自然
    • ☐ 画像・アイコンボタンに代替テキスト・ラベルがある
    • ☐ 重い画面・ライブラリを Code Splitting で遅延読み込みしている
    • ☐ Core Web Vitals（LCP・INP・CLS）の目標値と計測方法がある → 66_パフォーマンス のノート『Core_Web_Vitals』
    • ☐ 画面の一部が壊れても全体が真っ白にならない（エラー境界がある）
    • ☐ エラーが監視ツールに送られている

    純粋関数 は同じ入力なら必ず同じ出力を返し外の状態を変えない関数、カスタムフック は React で状態やロジックを部品から切り出して再利用する関数です。

    ✕ 悪い例：div にクリック処理を付けてボタンの代わりにする 
    <div onClick={save}>保存</div>  // キーボードで押せず、支援技術にもボタンと伝わらない
    ◯ 良い例：正しい HTML 要素を使う 
    <button type="button" onClick={save}>保存</button>

    9.スケールと組織

    関連：モノレポとパッケージ分割、マイクロフロントエンドの判断、フロントエンドの規約と ADR

    • ☐ 複数アプリで共有するコードは、パッケージとして境界と所有者が決まっている
    • ☐ マイクロフロントエンドは「チームの独立デプロイが本当に必要か」を確認してから採用した
    • ☐ 命名・フォルダ・状態の置き場所などの規約が文書化されている
    • ☐ 重要な設計判断が ADR に残っている（採用しなかった案と理由も）
    • ☐ 規約の多くが Lint・フォーマッタ・テンプレートで自動化されている

    ADR（Architecture Decision Record）は、設計判断とその理由・却下した案を短く記録する文書です。

    10.よくある誤解

    誤解1：「チェックリストの項目は全部満たさないといけない」

    すべてを満たす必要はありません。小さな画面に FSD や ADR を持ち込むのは過剰なこともあります。チェックが付かない項目は 「なぜ満たさないのか」を説明できれば十分 です。説明できないなら、そこが見直すべき点です。

    誤解2：「チェックリストは完成後のレビューで使うもの」

    使う場面は 新しい画面・機能を作る前、設計レビュー、リファクタリングの着手前 の3つです。状態の置き場所やフォルダ構成は、作ったあとで変えるほどコストが上がるので、作る前に確認するのが最も効果的です。

    誤解3：「チェックを全部付ければ、設計の手順も分かる」

    このチェックリストは確認用で、設計を組み立てる手順ではありません。1つの UI を最初から設計するときは、RADIO テンプレート の順（要件 → 全体構成 → データモデル → インターフェース → 最適化）で進め、できあがったものをこのリストで点検します。

    11.まとめ

    • 作る前・設計レビュー・リファクタリング前に、8つの観点（基礎 ／ コンポーネント ／ 状態 ／ ディレクトリ ／ デザインシステム ／ サーバーとの境界 ／ 品質 ／ スケールと組織）で確認する
    • 全部満たす必要はなく、満たさない理由を説明できればよい
    • 迷った項目は、観点ごとの「関連」のページで理由と例を確かめる
    • 設計の手順は RADIO テンプレート、言葉の意味は 用語集と推奨図書、章の地図は フロントエンド設計の全体像
