    30 状態とデータフロー

    状態の分類と置き場所 — 「真の持ち主」から置き場所を決める

    「とりあえずグローバルストアに入れる」をやめるために、フロントエンドの 状態（state） を 6 種類に分類し、それぞれを どこに置くべきか を判断できるようにします。ライブラリの使い方ではなく、置き場所を決める 判断の基準 を扱います。

    もとにしたノート：01_状態の分類と置き場所

    ひとことで言うと

    状態は ローカル / 共有 / 派生 / サーバー / URL / フォーム の 6 種類に分け、「真の持ち主は誰か」 と 「どこまでの範囲が使うか」 で置き場所を決めます。計算で出せる値は状態にせず、サーバーのデータはキャッシュとして扱い、残りは 使う場所のできるだけ近く に置きます。グローバルストアは最後の選択肢です。

    1.このページで扱うこと

    状態（state） とは、画面の表示を決めるために、時間とともに変わる値のことです。このページでは状態を 種類ごとに分類 し、それぞれを どこに置くべきか を判断できるようになることを目指します。

    • なぜ分類が必要か（混ぜたときの症状）
    • 6 種類の状態と「真の持ち主」
    • 置き場所の判断フロー
    • 「近くに置く」原則（colocation）
    • 種類ごとの置き場所と向き不向き
    • よくある判断ミス

    ライブラリの使い方や実装は 36_状態管理（ノート『MOC_状態管理体系』）が本拠地で、47章では 判断の基準 だけを扱います。状態が UI を決めるという前提は UI = f(state) を先に読むと分かりやすくなります。

    2.なぜ分類が必要か

    状態管理が破綻する典型は、性質の違う状態を 1 か所に混ぜる ことです。

    混ぜたときの症状原因
    API のデータが古いまま表示されるサーバーのデータを「自分の状態」としてコピーした
    リロードすると絞り込み条件が消えるURL に置くべき状態をメモリに置いた
    入力 1 文字ごとに画面全体が再描画されるフォームの状態をグローバルに置いた
    合計金額と明細がずれる計算で出せる値を別の状態として保存した

    置き場所を間違えると、同期のためのコード（2 か所の値をそろえ続けるためだけのコード）が増え続けます。分類はそれを防ぐための道具です。

    3.6 種類の状態

    種類例真の持ち主寿命
    ローカル（UI）状態モーダルの開閉、タブの選択、ホバーそのコンポーネント画面にある間
    共有（クライアント）状態ログイン中のユーザー表示設定、テーマ、カート（未送信）アプリ全体・複数画面セッション中
    派生状態合計金額、絞り込み後の一覧、入力が有効か他の状態（計算で出る）元の状態と同じ
    サーバー状態商品一覧、注文履歴、プロフィールサーバー（フロントはキャッシュ）サーバー側で変わりうる
    URL 状態検索語、ページ番号、並び順、選択中の IDURL（共有・ブックマーク可能）URL が残る限り
    フォーム状態入力中の値、エラー、送信中フラグそのフォーム送信・破棄まで

    ポイントは 「真の持ち主は誰か」 です。サーバー状態の持ち主はサーバーであり、フロントが持っているのは コピー（キャッシュ）（一時的に手元に保存した写し）にすぎません。この区別は 32_React のノート『8-4-サーバー状態vsクライアント状態』でも扱っています。

    4.置き場所の判断フロー

    その値は…
 ├─ 他の状態から計算で出せる？ ─────────── Yes → 状態にしない（派生：描画時に計算）
 ├─ サーバーが持ち主？ ─────────────────── Yes → サーバー状態ライブラリのキャッシュ
 ├─ リロード・共有・戻るボタンで残したい？ ─ Yes → URL（検索パラメータ・パス）
 ├─ 入力中のフォームの値？ ─────────────── Yes → フォームの状態（フォームライブラリ or ローカル）
 ├─ 1 つのコンポーネントだけが使う？ ────── Yes → ローカル状態
 ├─ 近い親子だけが使う？ ─────────────────── Yes → 共通の親に持ち上げる（lifting state up）
 └─ 離れた多数の画面が使う？ ─────────────── Yes → 共有状態（Context / ストア）

    上から順に判定するのがコツです。グローバルストアは最後の選択肢 で、多くの値はそこまで到達しません。

    lifting state up（状態の持ち上げ） とは、複数のコンポーネントが同じ値を使うときに、その値を共通の親コンポーネントへ移し、子には props で渡すことです。

    5.「近くに置く」原則（colocation）

    状態は 使う場所のできるだけ近く に置きます。これを colocation（コロケーション、同じ場所に置くこと） と呼びます。

    ✕ 悪い例：モーダルの開閉をグローバルストアに置く 
    const isOpen = useAppStore((s) => s.isEditModalOpen);
    ◯ 良い例：使うコンポーネントの中に置く 
    function EditButton() {
  const [isOpen, setIsOpen] = useState(false);
  return (
    <>
      <button onClick={() => setIsOpen(true)}>編集</button>
      {isOpen && <EditModal onClose={() => setIsOpen(false)} />}
    </>
  );
}

    近くに置くと、

    • 影響範囲が狭く、どこで変わるか がすぐ分かる
    • コンポーネントを消すと状態も一緒に消える（削除しやすい）
    • 再描画の範囲が小さくなる

    という利点があります。必要になってから 上に持ち上げる のが順序です（逆に、最初から上に置いたものを下げるのは難しい）。

    6.種類ごとの置き場所と向き不向き

    種類向く置き場所向かない置き場所実装の本拠地
    ローカルコンポーネント内の stateグローバルストア36 の 20_ローカル・UI状態
    共有Context / 軽量ストアprops のバケツリレー（深い場合）36 の 30_グローバル状態
    派生描画時の計算・メモ化別の state として保存SSOT と派生状態
    サーバーサーバー状態ライブラリ（キャッシュ）自前のグローバルストアにコピー36 の 40_サーバー状態
    URL検索パラメータ・ルートパラメータメモリ上の state36 の 50_URL状態
    フォームフォームライブラリ・フォーム内の stateグローバルストア36 の 60_フォーム状態

    props のバケツリレー とは、途中のコンポーネントが使わない値を、深い子へ届けるためだけに何段も props で受け渡すことです。メモ化 は、同じ入力に対する計算結果を覚えておき、再計算を省く最適化です。

    7.よくある判断ミス

    • API レスポンスをストアにコピーする — 再取得・無効化・ローディング管理を自前で書くことになる。サーバー状態として扱う
    • 絞り込み条件をメモリに置く — 共有 URL で同じ画面を再現できない。URL に置く
    • 「あとで使うかも」でグローバルに置く — YAGNI（You Aren't Gonna Need It：今必要ないものは作らない）。使う場所に置き、必要になったら持ち上げる
    • フォームの途中入力をストアに流す — 入力のたびに広範囲が再描画される

    8.よくある誤解

    誤解1：「状態はひとまずグローバルストアに入れておけば安心」

    逆です。 グローバルストアは判断フローの 最後の選択肢 です。最初から上に置くと影響範囲が広がり、再描画も増え、後から下げるのも難しくなります。まず使う場所の近くに置き、必要になってから持ち上げます。

    誤解2：「API から取ってきたデータは自分たちの状態だ」

    真の持ち主はサーバーです。 フロントが持っているのはキャッシュ（コピー）にすぎません。自前のストアにコピーすると、古いデータが表示されたり、再取得・無効化を自分で書くことになったりします。サーバー状態ライブラリのキャッシュとして扱います。

    誤解3：「検索条件やページ番号はコンポーネントの state で十分」

    リロード・共有・戻るボタンで残したい値は URL に置きます。 メモリに置くと、リロードで消え、共有した URL で同じ画面を再現できません。

    9.まとめ

    • 状態は ローカル / 共有 / 派生 / サーバー / URL / フォーム の 6 種類に分けて考える
    • 判断の軸は 「真の持ち主は誰か」 と 「どこまでの範囲が使うか」
    • 計算で出せる値は状態にしない。サーバーのデータはキャッシュとして扱う
    • 状態は使う場所の近くに置き、必要になってから持ち上げる
    • 実装（ライブラリの使い方）は 36_状態管理 で扱う
