    60 サーバーとの境界

    API レイヤと型の共有 — 唯一の契約をどこに置くか

    フロントが API の形を手で書き写すと、サーバー側の変更に気づけず、実行時に undefined が出てから慌てることになります。このページでは、フロントとサーバーの間で 型やスキーマをどう共有するか — OpenAPI からのコード生成、tRPC、Zod スキーマの共有、GraphQL Code Generator — を比べ、さらに API のデータを画面に直接流さない「API レイヤ」の責務を整理します。

    もとにしたノート：02_APIレイヤと型の共有

    ひとことで言うと

    型の共有は「唯一の契約（定義）をどこに置くか」で方式が決まります。公開 API・多言語なら OpenAPI、フルスタック TypeScript なら tRPC、既存 REST への後付けなら Zod。そしてどの方式でも、型は実行時のデータを保証しない ので、API レイヤで検証と変換を行い、サーバーの形を画面に直接流さないようにします。

    1.このページで扱うこと

    フロントとサーバーの間で 型やスキーマをどう共有するか を比べ、構成に合った方式を選べるようになるのが目標です。

    • なぜ型の共有が必要か（手書きの型の問題）
    • 4 つの方式：OpenAPI + コード生成、tRPC、Zod スキーマ共有、GraphQL Code Generator
    • 方式の比較 — 向く場面 / 向かない場面
    • API レイヤの責務 — 型の境界をどこに置くか

    API レイヤのフォルダ構成とクライアント実装は 37 章（37_HTTPクライアントのノート『03_APIレイヤーのフォルダ構成』『MOC_HTTPクライアント体系』）が本拠地です。フロントとサーバーの役割分担そのものは フロントとサーバーの責務分担 で扱いました。

    2.なぜ型の共有が必要か

    フロントが API の形を 手で書き写す と、次のことが起きます。

    ✕ 悪い例：手書きの型 
    // 手書きの型 — サーバーが total を totalPrice に変えても気づけない
type Order = { id: string; total: number };
    問題結果
    型のずれ実行時に undefined が出るまで気づかない
    二重管理同じ定義をサーバーとフロントで保守する
    型を信じすぎる型があっても実行時のデータは保証されない

    解決策は 「唯一の定義（契約）」を決めて、そこから両側を導く ことです。契約 とは、フロントとサーバーが「この形でやり取りする」と約束した API の形のことです。どこを唯一の定義にするかで方式が分かれます。

    契約の置き場所方式
    API 仕様書（YAML）OpenAPI + コード生成
    サーバーの TS コードtRPC
    共有スキーマZod などのスキーマ共有
    GraphQL スキーマGraphQL Code Generator

    3.各方式

    3.1 OpenAPI + コード生成（スキーマファースト）

    OpenAPI（REST API の仕様を YAML / JSON で書く標準形式）の仕様書から、型や API クライアントを 生成 します（openapi-typescript、Orval など）。仕様書を先に書く進め方を スキーマファースト と呼びます。

    import type { paths } from "./generated/schema";
type Order = paths["/orders/{id}"]["get"]["responses"]["200"]["content"]["application/json"];
    • サーバーの言語を問わない。仕様書がそのままドキュメントになる
    • 仕様書と実装がずれないよう、サーバー側からの生成 または 契約テスト（実装が仕様書どおりに応答するかを確かめるテスト）が必要

    OpenAPI の書き方は 45章：OpenAPI とドキュメント を参照してください。

    3.2 tRPC（TypeScript のエンドツーエンド型）

    サーバーの関数定義の型を、コード生成なしで フロントが直接参照します。

    // server
export const appRouter = router({
  orderById: publicProcedure.input(z.string()).query(({ input }) => getOrder(input)),
});
// client — 引数も戻り値も型推論される
const order = trpc.orderById.useQuery("o_1");
    • 開発体験が非常に良い。変更すると即座に型エラーになる
    • サーバーもクライアントも TypeScript で、同じリポジトリ（モノレポ） にあることが前提。公開 API には向かない

    3.3 Zod などのスキーマ共有

    スキーマを共有パッケージに置き、型の生成と実行時検証を同じ定義から 行います。

    export const Order = z.object({ id: z.string(), total: z.number() });
export type Order = z.infer<typeof Order>;

// フロントの API レイヤで、受け取ったデータを検証する
const order = Order.parse(await res.json());
    • 実行時の検証 ができるのが最大の利点（型だけでは外部データを保証できない）
    • 既存の REST API に後付けしやすい

    3.4 GraphQL Code Generator

    GraphQL スキーマとクエリから型を生成します（GraphQL 自体は 45章：GraphQL の基本）。

    • 画面が 必要なフィールドだけ を取得でき、その型が得られる
    • GraphQL サーバーの導入・運用が前提

    4.比較 — 向く場面 / 向かない場面

    方式向く場面向かない場面
    OpenAPI + 生成サーバーが別言語 / 公開 API / 複数クライアント仕様書を保守する体制がない
    tRPCフルスタック TS・モノレポ・社内向け外部公開 API / サーバーが別言語
    Zod スキーマ共有既存 REST に型と検証を足したい / フォームと共有したいスキーマが巨大で手書きがつらい
    GraphQL Codegen画面ごとに取得項目が大きく違う単純な CRUD / GraphQL 未導入

    組み合わせも一般的です。例：OpenAPI から Zod スキーマを生成 し、型と実行時検証を両方得る。

    5.API レイヤの責務 — 型の境界をどこに置くか

    どの方式でも、API のデータ形式を画面に直接流さない 層を 1 つ挟むと変更に強くなります。DTO（Data Transfer Object、通信でやり取りするためのデータの形）をそのまま画面で使うと、サーバー側の名前変更が画面全体に波及するからです。

    API レイヤでやることやらないこと
    実行時検証（parse）画面の状態管理
    DTO → 画面用の型への変換画面固有の表示整形（通貨記号など）
    エラーの型付け（業務エラー / 通信エラー）UI の表示

    変換層を省略してもよいのは、サーバーとフロントを同じチームが持ち、API がそのフロント専用 の場合です（tRPC 構成など）。

    エラーの型付けはサーバー側のエラー設計（45章：エラー設計）と対になり、画面での見せ方は エラー境界とフォールバック UI で扱います。

    6.よくある誤解

    誤解1：「TypeScript の型があれば、API のデータは安全」

    違います。 型はコンパイル時の約束で、実行時に届くデータが本当にその形かどうかは保証しません。サーバーの変更や不具合で形が違うデータが来ても、型だけでは気づけません。外部から来るデータは Zod の parse などで検証します。

    誤解2：「tRPC が一番便利だから、どの構成でも tRPC にすべき」

    前提条件があります。 tRPC はサーバーもクライアントも TypeScript で、同じリポジトリにあることが前提です。サーバーが別言語だったり、外部に公開する API だったりするなら、OpenAPI + コード生成の方が向きます。

    誤解3：「型を共有したなら、API レイヤの変換は不要」

    多くの場合は必要です。 サーバーの形（DTO）をそのまま画面に流すと、サーバー側の変更が画面全体に広がります。変換を省略してよいのは、同じチームが持つフロント専用 API（tRPC 構成など）の場合です。

    7.まとめ

    • 型の共有は「唯一の契約をどこに置くか」で方式が決まる
    • 公開・多言語なら OpenAPI、フルスタック TS なら tRPC、既存 REST の後付けなら Zod
    • 型は実行時のデータを保証しない。外部から来るデータは検証する
    • API レイヤで検証と変換を行い、サーバーの形を画面に直接流さない
