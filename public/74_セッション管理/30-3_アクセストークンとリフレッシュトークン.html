    30 トークン

    アクセストークンとリフレッシュトークン

    ログイン後に使うトークンは 1 種類でも動きます。それなのに、なぜ「アクセストークン」と「リフレッシュトークン」の 2 種類に分けるのでしょうか。このページでは、2 つに分ける理由と役割の違い、そしてリフレッシュトークンを盗まれたときに備える設計（ローテーション・期限・無効化・保存方法・送信者制約）を解説します。

    もとにしたノート：30_トークン/05_アクセストークンとリフレッシュトークンの違い（つるチャンネル）、30_トークン/06_リフレッシュトークンの設計

    ひとことで言うと

    アクセストークンは短命にして、漏れたときの被害を抑える。リフレッシュトークンは使う場所を限定しながら、ログイン状態を続ける。この役割分担が 2 種類に分ける理由です。リフレッシュトークンは 長く使える強い鍵 なので、盗まれたときにどうするかまで設計します。

    トークン（ログインした証として渡される文字列）とセッションの基本は セッション方式とトークン方式、トークンの形式としてよく使われる JWT は JWTの構造と検証、これらのトークンを発行する OAuth の全体の流れは OAuth 2.0 の仕組み（73 認証認可） を見てください。

    1.トークンが 1 種類だと何が困るのか

    まず アクセストークン です。ログインするとサーバーから発行され、アプリは API を呼ぶたびにこれを送ります。サーバーはそれを見て、許可されたアクセスかどうかを確認します。

    1.1 期限を長くすると：盗まれたときの危険が長く続く

    「だったら、このトークンをずっと使えるようにすればいいのでは」と思うかもしれません。ところが、トークンが盗まれても、サーバーから見れば正しいトークン です。持ち主が使っているのか、盗んだ人が使っているのかを見分けられません。そのため、期限が切れるまで使われ続ける恐れ があります。

    1.2 期限を短くすると：何度もログインが必要になる

    では期限を短くします。これなら盗まれても使える時間を短くできます。しかし今度は、期限が切れるたびにログインが必要 になります。これでは不便です。

    期限が長い

    便利だが、盗まれたら期限まで使われ続ける。

    期限が短い

    安全だが、切れるたびにログインし直す。

    この「安全」と「便利」を両立させるのが、トークンを 2 種類に分ける仕組みです。

    2.2 種類に分ける仕組み

    ログインのときに、アクセストークン と リフレッシュトークン の 2 つを受け取ります。

    1. ログインすると、サーバーからアクセストークン（例：15 分）とリフレッシュトークン（例：30 日）の 2 つが渡されます。
    2. 普段の API アクセスには、アクセストークンだけ を使います。
    3. アクセストークンの期限が切れたら、リフレッシュトークンを トークン更新の窓口（認証サーバー）へ送ります。
    4. サーバーが検証して問題がなければ、新しいアクセストークンが発行されます。
    5. 利用者は ログインし直さずに 続きを使えます。

    2.1 リフレッシュトークンが盗まれたら、結局危険では？

    その通りです。リフレッシュトークンが盗まれると、新しいアクセストークンを発行される恐れがあります。だからリフレッシュトークン自体も厳重に扱います。

    • 普段の API には送らず、更新するときだけ使う（ネットワークに出る回数を減らす）
    • 一度使ったリフレッシュトークンを無効にして、新しいものへ交換する 仕組みもある（ローテーション。4 章）

    3.2 つのトークンの役割

    アクセストークンリフレッシュトークン
    使う相手API（リソースサーバー＝データを持つサーバー）認証サーバーだけ
    期限短い（5〜15 分程度）長い（数日〜数十日）
    送る頻度API を呼ぶたびアクセストークンが切れたときだけ
    形式JWT が多い（JWTの構造と検証）中身のないランダムな文字列が多い
    盗まれたら期限が切れるまで使われる新しいアクセストークンを作り続けられる

    ポイント

    アクセストークンは何度もネットワークに出るので、漏れやすい。だから短くする。リフレッシュトークンは認証サーバーにしか送らないので、守りやすい場所に置ける、という分担です。

    4.ローテーション（使うたびに作り直す）

    OAuth のセキュリティ指針 RFC 9700（2025 年 1 月。RFC はインターネットの技術仕様の文書）は、ブラウザやスマホアプリのような 公開クライアント（秘密の鍵を安全に隠しておけないアプリ）のリフレッシュトークンに、次のどちらかを 必須 としています。

    1. 送信者制約：そのクライアントしか使えないようにする（DPoP や mTLS。8 章）
    2. ローテーション：更新のたびに新しいリフレッシュトークンを出し、古いものを無効にする

    4.1 ローテーションの仕組み

    以下、アクセストークンを AT、リフレッシュトークンを RT と書きます。

    RT1 で更新 ──▶ 新しい AT ＋ RT2（RT1 は無効）
RT2 で更新 ──▶ 新しい AT ＋ RT3（RT2 は無効）

    4.2 盗まれたことを見つける（再利用の検知）

    攻撃者が RT2 を盗んだとします。本物の利用者と攻撃者のどちらかが先に RT2 を使い、もう一方が 無効になった RT2 を後から使うことになります。

    利用者:  RT2 で更新 ──▶ RT3 を受け取る
攻撃者:  RT2 で更新 ──▶ ❌ 使用済みの RT2 が来た！
                        → 認証サーバーは、どちらが本物か分からない
                        → RT2 から続く一連のトークン（RT3 も）を全部無効にする
                        → 利用者は再ログイン、攻撃者は締め出される
    • 同じログインから続くトークンを 1 つの家系（ファミリー） として記録しておき、使用済みのトークンが来たら家系ごと無効にします。
    • 再利用を見つけたら、セキュリティのログに記録し、必要なら利用者に通知します。

    4.3 同時に更新が走る問題

    タブを複数開いていると、同じ RT で同時に更新が走り、正規の利用者なのに「再利用」と判定されることがあります。

    対策内容
    更新を 1 か所にまとめるクライアント側で更新処理を 1 つにし、他のリクエストはその結果を待つ
    短い猶予期間古い RT を数秒だけ有効にしておく。ただし猶予の間は検知が甘くなる

    5.期限の決め方

    期限内容目安
    使わないと切れる期限（アイドル）最後に更新してから一定期間使われなければ無効数日〜2 週間
    絶対的な期限最初のログインから一定期間で、必ず再ログイン30〜90 日
    アクセストークン短く5〜15 分
    • RFC 9700 も「しばらく使われていないリフレッシュトークンは期限切れにすべき（SHOULD）」としています。
    • 金融や管理画面など重要なサービスほど短くします。

    ローテーションしても絶対的な期限は延ばさない

    新しい RT を出すたびに絶対的な期限まで延ばすと、一度盗まれたトークンが更新され続けて、永遠に使えてしまいます。

    6.無効にするタイミング

    きっかけ処理
    ログアウトその端末のリフレッシュトークンを無効にする（認証サーバーの revocation＝取り消し用の窓口。RFC 7009）
    パスワード変更・リセット全端末 のリフレッシュトークンを無効にする
    MFA の変更・アカウントの停止全端末を無効にする
    再利用の検知その家系を無効にする
    利用者が「他の端末からログアウト」を押した選んだ端末、または全端末を無効にする

    「ログイン中の端末一覧」を画面に出し、利用者が自分で切れるようにすると、乗っ取りに気づきやすくなります。

    7.サーバー側の保存

    リフレッシュトークンは、サーバー側のデータベースに次のような形で記録します。

    refresh_tokens
  id            -- 主キー
  token_hash    -- トークンそのものではなく SHA-256 のハッシュを保存
  user_id
  family_id     -- 同じログインから続くトークンの家系
  client_id
  expires_at    -- 絶対的な期限
  last_used_at  -- アイドル期限の判定
  used_at       -- 使用済みなら日時（再利用の検知に使う）
  revoked_at
  device_info   -- 端末一覧の表示用（ブラウザ・OS・おおよその場所）
    • リフレッシュトークンは ハッシュで保存 します（ハッシュ＝元に戻せない形に変換した値）。DB が漏れても、そのまま使えないようにするためです。ランダムな長い値なので、パスワードのような遅いハッシュは不要で、SHA-256 で十分です（パスワードの場合は パスワードの安全な保存（73））。
    • 推測されないよう、暗号学的に安全な乱数で 32 バイト以上 作ります。

    8.送信者制約（盗んでも使えなくする）

    ローテーションは「盗まれた後に気づく」仕組みです。もう一歩進めると、盗んでも使えない ようにできます。これを送信者制約といいます。

    仕組み内容
    DPoP（RFC 9449）クライアントが鍵ペアを作り、リクエストごとに秘密鍵で署名する。トークンはその鍵と結び付けられるので、トークンだけ盗んでも使えない
    mTLS（RFC 8705）クライアント証明書と結び付ける。サーバー間の通信向け
    DBSC（Device Bound Session Credentials）ブラウザが端末の TPM（鍵を守るための専用チップ）などで鍵を守り、セッションの Cookie をその端末に結び付ける。Chrome 146（2026 年 4 月）から Windows で正式に提供。サイト側の対応が必要

    ブラウザで DPoP を使う場合、秘密鍵は WebCrypto（ブラウザ標準の暗号機能）の 取り出せない鍵（non-extractable）にして IndexedDB（ブラウザ内のデータベース）に置きます。XSS で鍵そのものは盗まれませんが、XSS が動いている間はその鍵で署名させられる点は残ります（XSS は XSSの基本（72））。

    9.クライアント別の考え方

    クライアントリフレッシュトークンの置き場所
    サーバー側の Web アプリ・BFFサーバー側に保存。ブラウザにはセッション Cookie だけ渡す（最も安全）
    SPA（ブラウザだけ）できれば BFF にしてブラウザに置かない。置くならメモリか Web Worker の中。localStorage は避ける
    スマホアプリiOS のキーチェーン、Android の Keystore で守られた領域
    サーバー間（M2M）リフレッシュトークンは使わず、Client Credentials で毎回取り直すのが一般的

    BFF（Backend for Frontend＝画面のために置く自分のサーバー）や SPA（1 枚のページを JavaScript で書き換えて動くアプリ）での置き場所の詳しい比較は、次のページ トークンの保存場所 で扱います。

    10.チェックリスト

    • アクセストークンの期限は短い（15 分程度まで）
    • 公開クライアントでは、ローテーションか送信者制約を入れている
    • 使用済みの RT が来たら、家系ごと無効にしている
    • アイドル期限と絶対的な期限の両方がある
    • ログアウト・パスワード変更で RT を無効にしている
    • RT はハッシュで保存している
    • ブラウザでは RT を localStorage に置いていない

    11.まとめ

    項目要点
    2 種類に分ける理由長い期限は盗まれたとき危険、短い期限は不便。アクセストークンを短命にし、リフレッシュトークンで再ログインなしに更新する
    役割AT は API に毎回送る（漏れやすい→短く）。RT は認証サーバーに更新時だけ送る（守りやすい→長め）
    ローテーション更新のたびに RT を作り直す。使用済み RT が来たら家系ごと無効にして、盗難を検知する
    期限アイドル期限と絶対的な期限の両方。絶対的な期限はローテーションしても延ばさない
    無効化ログアウト・パスワード変更・MFA 変更・再利用検知・利用者の操作で無効にする
    保存サーバーでは SHA-256 のハッシュで保存。32 バイト以上の安全な乱数で作る
    送信者制約DPoP・mTLS・DBSC で、盗んでも別の端末では使えなくする

    12.理解度チェック

    Q1. アクセストークンの期限を長くしても短くしても困るのはなぜですか？

    長くすると、盗まれてもサーバーからは正しいトークンに見えるので、期限が切れるまで使われ続けます。短くすると、期限が切れるたびにログインが必要になり不便です。

    Q2. リフレッシュトークンを普段の API に送らないのはなぜですか？

    リフレッシュトークンは盗まれると新しいアクセストークンを作り続けられる強い鍵だからです。送る相手を認証サーバーだけ、送るタイミングを更新時だけに限ることで、漏れる機会を減らします。

    Q3. ローテーションで、使用済みのリフレッシュトークンが送られてきたら認証サーバーはどうしますか？

    本物の利用者と攻撃者のどちらが本物か分からないので、同じログインから続くトークンの家系を丸ごと無効にします。利用者は再ログインになり、攻撃者は締め出されます。あわせてログに記録し、必要なら利用者に通知します。

    Q4. 複数のタブを開いていると、正規の利用者なのに「再利用」と判定されることがあります。対策は？

    クライアント側で更新処理を 1 か所にまとめて他のリクエストはその結果を待つか、古い RT を数秒だけ有効にする猶予期間を設けます（猶予の間は検知が甘くなります）。

    Q5. ローテーションのたびに絶対的な期限を延ばしてはいけないのはなぜですか？

    延ばすと、一度盗まれたトークンが更新され続けて、永遠に使えてしまうからです。

    Q6. リフレッシュトークンをハッシュで保存するとき、パスワードのような遅いハッシュが不要なのはなぜですか？

    リフレッシュトークンは安全な乱数で作った長いランダムな値なので、総当たりで元の値を当てられないからです。SHA-256 で十分です。

    Q7. ローテーションと送信者制約（DPoP など）の違いは何ですか？

    ローテーションは「盗まれた後に、再利用から気づく」仕組みです。送信者制約はトークンを鍵や端末と結び付けて、「盗んでも使えない」ようにする仕組みです。
