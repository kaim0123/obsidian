    30 トークン

    トークンの保存場所

    「JWT は localStorage と Cookie のどちらに置くべきか」はよく議論になります。2026 年に出版された RFC 10017（OAuth 2.0 for Browser-Based Applications）で、IETF（インターネットの標準を決める団体）の考え方が整理されました。このページでは、置き場所ごとの危険の違いと、おすすめの BFF 方式、BFF が使えない場合の対策を解説します。

    もとにしたノート：30_トークン/07_トークンの保存場所（Cookie_vs_localStorage）

    ひとことで言うと

    結論は 「できればブラウザにトークンを置かない」 です。トークンは自分のサーバー（BFF）に置き、ブラウザには HttpOnly のセッション Cookie だけを渡します。どうしてもブラウザに置くなら、メモリや Web Worker に置き、localStorage は避けます。

    アクセストークンとリフレッシュトークンの役割は アクセストークンとリフレッシュトークン、トークンを発行する OAuth の流れは OAuth 2.0 の仕組み（73 認証認可） を見てください。

    1.結論：3 つの方式と優先順位

    優先方式一言で
    1BFF（Backend for Frontend）トークンはサーバーに置き、ブラウザには HttpOnly のセッション Cookie だけ渡す
    2トークン仲介バックエンドリフレッシュトークンはサーバーに置き、短いアクセストークンだけブラウザのメモリに渡す
    3ブラウザだけで完結（SPA が直接 OAuth）トークンをメモリや Web Worker に置く。localStorage は避ける
    • BFF：画面（フロントエンド）のために用意する、自分の小さなサーバーのことです。
    • SPA（Single Page Application）：1 枚のページを JavaScript で書き換えながら動くアプリのことです。

    重要なアプリでは 3 番を勧めない

    RFC 10017 は、3 番の「ブラウザだけで完結する方式」を 業務アプリ・重要なアプリ・個人情報を扱うアプリには勧めない としています。

    2.なぜ置き場所が問題になるのか

    ブラウザに置いたトークンを狙う攻撃は、主に 2 つです。

    攻撃何が起きるか関係する置き場所
    XSS（XSSの基本）攻撃者のスクリプトが、同じオリジンの JavaScript として動くJavaScript から読める場所（localStorage・sessionStorage・メモリ）
    CSRF（CSRF）別サイトから、利用者のブラウザにリクエストを送らせる自動で送られる場所（Cookie）

    オリジン（スキーム・ホスト・ポートの組み合わせ）については 受動的攻撃と同一オリジンポリシー を見てください。

    大事な前提

    XSS が起きると、どこに置いても そのページの中で API を呼ばれる ことは防げません。違いは、トークンそのものを外に持ち出されるかどうか です。持ち出されると、利用者がブラウザを閉じた後も、攻撃者の手元で使い続けられます。

    3.置き場所ごとの比較

    置き場所XSS で持ち出されるCSRF再読み込みで残るタブ間で共有備考
    localStorageされる関係ない残るされる同じオリジンのどのスクリプトからも読める。ディスクに平文で残る
    sessionStorageされる関係ない残る（タブを閉じると消える）されないlocalStorage よりは少しまし
    メモリ（JavaScript の変数）されやすい関係ない消えるされない再読み込みのたびに取り直しが必要
    Web Worker の中されにくい関係ない消えるされないページから直接読めない。ただし Worker が API を代わりに呼ぶので悪用はされる
    HttpOnly Cookieされない対策が必要残るされるJavaScript から読めない。ブラウザが自動で送る
    JavaScript で書いた Cookieされる対策が必要残るされるRFC 10017 でも勧めない。両方の弱点を持つ

    Web Worker は、ページとは別に裏で動く JavaScript の仕組みです。ページのスクリプトから Worker の中の変数は直接読めません。

    ポイント

    HttpOnly Cookie は XSS で 持ち出されない 唯一の置き場所です。代わりに CSRF の対策が必要ですが、CSRF は SameSite 属性やトークンで確実に防げます。

    4.BFF 方式

    BFF 方式では、OAuth のやり取りとトークンの保管を自分のサーバー（BFF）が受け持ちます。ブラウザが持つのはセッション Cookie だけです。

    ブラウザ（SPA）                    BFF（自分のサーバー）              認証サーバー・API
     │                                 │                                  │
     │── ログイン ───────────────────▶│── OAuth（コード + PKCE）───────▶│
     │                                 │◀─ AT・RT ──────────────────────│
     │◀─ Set-Cookie: session=...       │   （トークンは BFF の中に保存）
     │   HttpOnly; Secure; SameSite    │
     │                                 │
     │── /api/orders（Cookie だけ）──▶│── Authorization: Bearer AT ───▶│ API
     │◀─ 結果 ────────────────────────│◀─────────────────────────────── │

    PKCE（ピクシー）は、OAuth で受け取る認可コードを横取りされても使えないようにする仕組みです。

    4.1 長所と短所

    長所

    • ブラウザにトークンがないので、持ち出されるものがない
    • リフレッシュトークンを安全に扱える（アクセストークンとリフレッシュトークン）
    • OAuth のクライアント認証（client secret）を使える

    短所

    • サーバー（BFF）が必要。完全な静的ホスティングにはできない
    • API への通信が BFF を経由する
    • Cookie なので CSRF 対策が必要

    Next.js・Nuxt などのサーバー機能を持つフレームワークでは、BFF をアプリの一部として作れます。Auth.js（NextAuth）などのライブラリの標準的な形もこれです。

    4.2 BFF の Cookie の設定

    おすすめの設定 
    Set-Cookie: __Host-session=ランダムなID; Path=/; Secure; HttpOnly; SameSite=Lax
    属性理由
    HttpOnlyJavaScript から読めなくする
    SecureHTTPS でだけ送る
    SameSite=Lax（または Strict）別サイトからの POST などで送られなくなる（CSRF 対策の土台）
    __Host- 接頭辞Secure 付き・Domain 属性なし・Path=/ を強制。サブドメインから上書きされない
    • 状態を変える API には、SameSite に加えて CSRF トークン か 独自ヘッダの確認（X-Requested-With などが付いているか）を入れます。
    • Cookie にアクセストークンを入れる場合は、中身を 暗号化 します。
    • Cookie の属性の詳細は Cookieの仕組み と クッキー出力にまつわる脆弱性 を見てください。

    5.BFF が使えない場合（ブラウザだけで完結）

    静的ホスティングの SPA などで、どうしてもブラウザに置く場合です。

    対策内容
    localStorage に置かないメモリに置き、再読み込み時は認証サーバーのセッションを使って取り直す
    リフレッシュトークンは Web Worker の中ページのスクリプトから直接読めないようにする
    短い期限 ＋ ローテーション持ち出されても使える時間を短くし、再利用を検知する
    DPoP取り出せない鍵（non-extractable）でトークンを端末に結び付ける
    XSS 対策を厚くするCSP・Trusted Types・依存ライブラリの管理（CSP、セキュリティヘッダ）

    ローテーションと DPoP の仕組みは アクセストークンとリフレッシュトークン の 4 章・8 章で説明しています。

    保存場所の工夫は XSS 対策の代わりにならない

    RFC 10017 も、「攻撃者のコードが動いている時点で、新しいトークンを取得することは止められない」と書いています。保存場所の工夫は 被害を小さくする ためのものです。

    6.第三者 Cookie の状況（2026 年）

    「Cookie はそのうち使えなくなるから localStorage に」という話を見かけますが、混同されがちです。

    • 制限の対象は、別のサイトに埋め込まれたときに送られる第三者 Cookie（サードパーティ Cookie）です。自分のサイトのログイン Cookie（ファーストパーティ）は関係ありません。
    • Google は 2025 年に、Chrome の第三者 Cookie の廃止計画を取りやめ、Privacy Sandbox もほぼ終了しました。Safari と Firefox は以前から第三者 Cookie を制限しています。
    • 認証サーバーとアプリのドメインを 同じサイト（auth.example.com と app.example.com など）にしておくと、ブラウザの方針に左右されにくくなります。

    7.Cookie そのものが盗まれる場合

    マルウェア（情報窃取型のインフォスティーラー）は、ブラウザの Cookie のファイルを直接盗みます。HttpOnly でも防げません。

    対策内容
    セッションを端末に結び付けるChrome の DBSC（Device Bound Session Credentials）は、端末の TPM（鍵を守る専用チップ）で守った鍵とセッションを結び付け、盗まれた Cookie を別の端末で使えなくする。2026 年 4 月から Windows の Chrome で正式に提供。サイト側の対応が必要
    異常の検知IP・国・端末が急に変わったら再認証を求める
    短いセッション重要な操作の前に再認証（ステップアップ）する（MFAの方式比較）

    8.判断の早見表

    サーバーを持てる？
 ├─ はい → BFF（トークンはサーバー、ブラウザには HttpOnly Cookie）
 └─ いいえ
     ├─ 業務・個人情報を扱う → サーバーを持つ構成を検討し直す
     └─ それ以外 → メモリ / Web Worker に置く + 短い期限 + ローテーション + DPoP
                   localStorage には置かない

    9.まとめ

    項目要点
    結論できればブラウザにトークンを置かない。優先は BFF → トークン仲介バックエンド → ブラウザだけで完結
    攻撃との関係JavaScript から読める場所は XSS、自動で送られる Cookie は CSRF が問題になる
    XSS の前提どこに置いてもページ内で API は呼ばれる。違いはトークンを外に持ち出されるかどうか
    HttpOnly Cookie持ち出されない唯一の置き場所。CSRF は SameSite と CSRF トークン・独自ヘッダで防ぐ
    BFF の Cookie__Host-・Secure・HttpOnly・SameSite=Lax
    BFF なしメモリ／Web Worker、短い期限＋ローテーション、DPoP、XSS 対策。localStorage は避ける
    第三者 Cookie制限されるのは埋め込み先の Cookie で、自分のログイン Cookie は関係ない
    Cookie の窃取マルウェアには HttpOnly も無力。DBSC・異常検知・再認証で備える

    10.理解度チェック

    Q1. RFC 10017 が示す、トークンの置き場所の結論は何ですか？

    「できればブラウザにトークンを置かない」です。最優先は BFF で、トークンはサーバーに置き、ブラウザには HttpOnly のセッション Cookie だけを渡します。

    Q2. XSS が起きたとき、トークンを HttpOnly Cookie に置いていれば被害はゼロですか？

    ゼロではありません。攻撃者のスクリプトはそのページの中で API を呼べます。ただし、トークンそのものは JavaScript から読めないので外に持ち出されず、利用者がブラウザを閉じた後まで使い続けられることは防げます。

    Q3. localStorage にトークンを置くと何が問題ですか？

    同じオリジンのどのスクリプトからも読めるので、XSS で持ち出されます。さらにディスクに平文で残り、再読み込みやブラウザを閉じた後も残ります。

    Q4. HttpOnly Cookie を使うとき、別に必要になる対策は何ですか？

    Cookie はブラウザが自動で送るので、CSRF 対策が必要です。SameSite=Lax（または Strict）を土台に、状態を変える API には CSRF トークンか独自ヘッダの確認を加えます。

    Q5. __Host- 接頭辞を付けると何が保証されますか？

    Secure 付き・Domain 属性なし・Path=/ が強制され、サブドメインから上書きされなくなります。

    Q6. 「第三者 Cookie が廃止されるから、ログインには localStorage を使うべき」という意見は正しいですか？

    正しくありません。制限の対象は別サイトに埋め込まれたときの第三者 Cookie で、自分のサイトのログイン Cookie（ファーストパーティ）は関係ありません。また Chrome は 2025 年に第三者 Cookie の廃止計画を取りやめています。

    Q7. インフォスティーラーに Cookie のファイルを盗まれる場合、どう備えますか？

    HttpOnly では防げないので、DBSC でセッションを端末に結び付ける、IP・国・端末の急な変化で再認証を求める、重要な操作の前に再認証（ステップアップ）する、といった対策を組み合わせます。
