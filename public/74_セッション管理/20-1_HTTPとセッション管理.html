    20 セッション

    HTTPとセッション管理

    Web アプリケーションのセキュリティを理解するには、まず HTTP という通信の仕組みを押さえることが大切です。このページでは『安全なWebアプリケーションの作り方』（徳丸本）第 1 章の内容に沿って、リクエストとレスポンスの形、ステータスコード、GET と POST の使い分け、Hidden パラメータ、Basic 認証、そしてクッキーによるセッション管理とセッション ID の守り方までを順に解説します。

    もとにしたノート：20_セッション/01_HTTPセッション管理（徳丸本1章）

    ひとことで言うと

    HTTP は 「要求して、応答をもらう」を 1 回ずつ繰り返すだけで、前回のやり取りを覚えていません（ステートレス）。そこでログイン状態などは、サーバーが持つデータに番号（セッション ID）を付け、その番号だけをクッキーでブラウザに持たせる ことで保ちます。番号が漏れればなりすましされるので、HTTPS・HttpOnly・ログイン時の ID 再生成 で守ります。

    1.HTTP とは

    HTTP（HyperText Transfer Protocol） は、ブラウザと Web サーバーがデータをやり取りするための「約束事（プロトコル＝通信の決まりごと）」です。

    1.1 日常生活での例え

    HTTP

    レストランでの注文と配膳のルール

    ブラウザ

    お客さん（注文する側）

    Web サーバー

    厨房（料理を作って返す側）

    お客さんが「ハンバーガーをください」と注文（リクエスト）すると、厨房が「はい、どうぞ」と料理を出す（レスポンス）。このやり取りの形式が HTTP です。

    1.2 HTTP の特徴

    特徴説明
    リクエスト・レスポンス型クライアント（ブラウザ）が先に要求し、サーバーが応答する
    ステートレスサーバーは前回の通信を覚えていない（別の仕組みで状態を管理する。→ 11 章）
    テキストベースメッセージの多くは人間が読める形式
    ポート 443（HTTPS）暗号化された安全な通信には HTTPS（HTTP を暗号化したもの）を使う

    1.3 URL の構成

    https://example.com:443/search?q=hello#top
  │       │          │    │      │     │
  │       │          │    │      │     └─ フラグメント（ページ内の位置）
  │       │          │    │      └─ クエリ文字列（パラメータ）
  │       │          │    └─ パス
  │       │          └─ ポート番号（https で省略時は 443）
  │       └─ ホスト名（ドメイン）
  └─ スキーム（http / https）

    2.リクエストメッセージ

    ブラウザがサーバーに送るメッセージを リクエストメッセージ と呼びます。主に リクエストライン・リクエストヘッダ・メッセージボディ の 3 つの部分で構成され、ヘッダとボディの間には空行が入ります。

    GET /search?q=hello HTTP/1.1          ← リクエストライン
Host: example.com                     ← リクエストヘッダ
User-Agent: Mozilla/5.0 ...
Accept: text/html
Cookie: sessionId=abc123
                                      ← 空行
（メッセージボディ ※GETでは通常なし）

    2.1 リクエストライン

    メソッド  リクエストURI  HTTPバージョン
GET       /index.html    HTTP/1.1
    • メソッド：何をしたいか（GET、POST など）
    • リクエスト URI：どのリソース（ページやデータ）にアクセスするか
    • HTTP バージョン：使用する HTTP の版

    2.2 リクエストヘッダ

    リクエストに関する追加情報を伝えます。

    ヘッダ名役割
    Hostアクセス先のホスト名（必須）
    User-Agentブラウザの種類・バージョン
    Accept受け取れるデータ形式
    Content-Typeボディのデータ形式（POST 時）
    Cookie保存済みクッキーの送信
    Refererリンク元の URL（→ 7 章）

    3.レスポンスメッセージとステータスライン

    サーバーがブラウザに返すメッセージを レスポンスメッセージ と呼びます。こちらも ステータスライン・レスポンスヘッダ・メッセージボディ の 3 部構成です。

    HTTP/1.1 200 OK                       ← ステータスライン
Content-Type: text/html; charset=UTF-8 ← レスポンスヘッダ
Content-Length: 1234
Set-Cookie: sessionId=abc123; HttpOnly
                                      ← 空行
<!DOCTYPE html>                       ← メッセージボディ
<html>...</html>

    3.1 ステータスライン

    レスポンスの最初の 1 行で、処理結果を 3 桁の数字（ステータスコード）で表します。

    HTTP/1.1 200 OK
  │       │   └─ 理由フレーズ（人間向けの説明）
  │       └─ ステータスコード（数字）
  └─ HTTPバージョン

    3.2 主なステータスコード

    コード意味例
    2xx 成功
    200OK正常に取得・処理できた
    201Created新しいリソースを作成した
    3xx リダイレクト（別の URL へ移動させること）
    301Moved Permanently恒久的に別 URL へ移動
    302Found一時的に別 URL へ移動
    304Not Modifiedキャッシュが有効（再取得不要）
    4xx クライアントエラー
    400Bad Requestリクエストの形式が不正
    401Unauthorized認証が必要
    403Forbiddenアクセス権限がない
    404Not Foundリソースが存在しない
    5xx サーバーエラー
    500Internal Server Errorサーバー内部のエラー
    502Bad Gateway上流サーバーのエラー
    503Service Unavailable一時的にサービス停止

    401 と 403 の使い分けは、73 の 認証と認可の違い で詳しく解説しています。

    4.レスポンスヘッダと MIME タイプ

    4.1 レスポンスヘッダ

    レスポンスに関する追加情報を伝えます。

    ヘッダ名役割
    Content-Typeボディのデータ形式（MIME タイプ）
    Content-Lengthボディのバイト数
    Set-Cookieクッキーの設定
    Locationリダイレクト先 URL
    Cache-Controlキャッシュの制御
    Strict-Transport-SecurityHTTPS 強制（HSTS）

    Location や Set-Cookie に外から来た値を入れるときの落とし穴は 72 の リダイレクトと HTTP ヘッダインジェクション、HSTS などセキュリティ用のヘッダは セキュリティヘッダ を参照してください。

    4.2 MIME タイプ

    MIME タイプ は、データの種類を表す識別子です。Content-Type ヘッダで指定します。

    Content-Type: text/html; charset=UTF-8
              │         │
              │         └─ 文字コード
              └─ MIMEタイプ
    MIME タイプ内容
    text/htmlHTML 文書
    text/cssCSS スタイルシート
    text/plainプレーンテキスト
    application/jsonJSON データ
    application/javascriptJavaScript
    image/pngPNG 画像
    image/jpegJPEG 画像
    application/pdfPDF ファイル

    ブラウザは MIME タイプを見て、HTML として表示するのか、JSON として処理するのか、画像として描画するのかを判断します。

    5.POST メソッドとメッセージボディ

    POST は、サーバーにデータを 送信（作成・更新） するための HTTP メソッドです。

    5.1 GET との違い（概要）

    GETPOST
    目的データの取得データの送信
    パラメータの位置URL（クエリ文字列）メッセージボディ
    ブックマーク可能不可
    キャッシュされやすいされにくい
    再送信安全注意が必要

    5.2 POST リクエストの例

    POST /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 31

username=yamada&password=secret
    <!-- HTMLフォームからPOSTする例 -->
<form method="POST" action="/login">
  <input type="text" name="username">
  <input type="password" name="password">
  <button type="submit">ログイン</button>
</form>

    5.3 メッセージボディ

    メッセージボディ は、HTTP メッセージの本体部分です。ヘッダとボディの間には 空行 が 1 行入ります。

    リクエストボディ は、POST や PUT など、クライアントからサーバーへデータを送るときに使います。形式は Content-Type で示します。

    Content-Type: application/x-www-form-urlencoded

username=yamada&password=secret
    Content-Type: application/json

{"username": "yamada", "password": "secret"}

    レスポンスボディ は、サーバーから返される実際のコンテンツです。HTML ページ、JSON 形式の API レスポンス、画像・PDF などのバイナリデータ（文字ではないデータ）が入ります。

    ボディのセキュリティ上の注意点

    • パスワードなど 機密情報はボディに入れる（URL に載せない）
    • HTTPS を使わないと、ボディの内容が傍受（盗み見）される可能性がある
    • ボディのサイズには上限を設ける（大量データでサーバーを止める DoS 攻撃への対策）

    6.パーセントエンコード

    URL やフォームデータに 英数字以外の文字（日本語、スペース、&、= など）を含めるときは、特殊な形式に変換します。これを パーセントエンコード（URL エンコード） と呼びます。

    6.1 変換ルール

    1. 英数字と -_.~ 以外の文字を、UTF-8 のバイト列に変換する
    2. 各バイトを % ＋ 16 進数 2 桁で表す
    元の文字    エンコード後
スペース  →  %20
&         →  %26
=         →  %3D
こ        →  %E3%81%93
    /search?q=こんにちは
↓
/search?q=%E3%81%93%E3%82%93%E3%81%AB%E3%81%A1%E3%81%AF

    6.2 なぜ必要か

    • URL には #、?、&、= など 特別な意味を持つ文字 がある
    • そのまま送ると、サーバーがパラメータの区切りと誤解する
    • エンコードすることで、データとして安全に送れる
    // JavaScriptでの例
encodeURIComponent('こんにちは');  // "%E3%81%93%E3%82%93%E3%81%AB%E3%81%A1%E3%81%AF"
decodeURIComponent('%E3%81%93');  // "こ"

    7.リファラー（Referer）

    リファラー（Referer） は、ユーザーが どのページから来たか を示す情報です。HTTP ヘッダ Referer で送信されます（英語の referrer の綴り誤りがそのまま規格に残ったため、歴史的経緯で Referer になっています）。

    Referer: https://example.com/search?q=hello

    7.1 用途

    • アクセス解析：どのサイト・ページから流入したか
    • CSRF 対策：リクエスト元を検証する（CSRF は CSRF を参照）
    • ホットリンク防止：画像の直リンクを制限する

    7.2 セキュリティ上の注意と対策

    リスク説明
    情報漏洩URL にトークンや検索語が含まれると、Referer 経由で外部に漏れる
    プライバシー閲覧履歴が外部サイトに伝わる

    対策は、機密情報を URL に含めない ことと、Referrer-Policy ヘッダで送信を制限することです。

    Referrer-Policy: strict-origin-when-cross-origin

    8.GET・POST の使い分け

    8.1 基本原則

    操作使うメソッド理由
    データの 参照・検索GET安全（副作用なし）、キャッシュ可能
    データの 登録・更新・削除POST（PUT／DELETE）副作用がある操作
    ログインPOSTパスワードを URL に載せない
    検索フォームGET結果 URL をブックマーク・共有可能

    副作用 とは、データが登録・変更されるなど、リクエストによってサーバーの状態が変わることです。

    GET を使うべき場面

    GET /products?category=books&page=2
    • 検索結果の表示
    • ページネーション（ページ送り）
    • フィルタリング
    • 冪等（べきとう：何度実行しても同じ結果）な操作

    POST を使うべき場面

    POST /orders
{"productId": 123, "quantity": 2}
    • ログイン・会員登録
    • フォーム送信（問い合わせ、決済）
    • データの作成・更新
    • 副作用がある 操作

    8.2 よくある間違い

    危険な例：パスワードを GET で送る（URL に残る） 
    <form method="GET" action="/login">
  <input type="password" name="password">
</form>
    安全な例：POST で送る 
    <form method="POST" action="/login">
  <input type="password" name="password">
</form>

    GET で送るとパスワードが URL に入り、ブラウザの履歴・サーバーのログ・Referer などに残ってしまいます。

    9.Hidden パラメータ

    Hidden パラメータ は、HTML フォームで <input type="hidden"> を使い、画面上は見えないがサーバーに送信される値です。

    <form method="POST" action="/transfer">
  <input type="hidden" name="from_account" value="12345">
  <input type="text" name="amount" placeholder="送金額">
  <button type="submit">送金</button>
</form>

    9.1 用途

    • フォームの状態を引き継ぐ（商品 ID、ページ番号）
    • CSRF トークンの埋め込み
    • 処理モードの指定

    9.2 セキュリティ上の重大な注意

    Hidden パラメータは ブラウザの開発者ツールで誰でも見え、値を書き換えられる ため、セキュリティの根拠にはなりません。

    危険な例：権限や価格を hidden に頼る 
    <!-- 危険：権限チェックをhiddenに頼る -->
<input type="hidden" name="is_admin" value="true">

<!-- 危険：価格をhiddenで送る -->
<input type="hidden" name="price" value="100">

    正しい考え方

    • Hidden は 利便性のため に使う（UI の状態引き継ぎなど）
    • 権限・価格・ユーザー ID など 信頼すべき値はサーバー側で管理 する
    • 送られてきた値は必ずサーバーで 再検証 する

    10.Basic 認証

    Basic 認証（ベーシック認証） は、HTTP で定義されている最もシンプルな認証方式です。

    10.1 仕組み

    1. ユーザーが保護されたページにアクセスする
    2. サーバーが 401 Unauthorized と WWW-Authenticate: Basic を返す
    3. ブラウザがログインダイアログを表示する
    4. ユーザーがユーザー名とパスワードを入力する
    5. ブラウザが Authorization: Basic エンコード文字列 ヘッダで送信する
    Authorization: Basic eWFtYWRhOnNlY3JldA==
                              ↑
                    Base64(username:password)

    Base64 は、データを英数字などの文字だけで表すための変換方法です。元に戻すのは誰でもできます。

    GET /admin HTTP/1.1
Host: example.com
Authorization: Basic eWFtYWRhOnBhc3N3b3JkMTIz

    10.2 メリット・デメリット

    メリットデメリット
    実装が簡単HTTPS 必須（平文に近い形式のため）
    ブラウザが対応ログアウト機能が弱い
    小規模な管理画面向けパスワードを毎回送信する
    Base64 は 暗号化ではない（誰でも復号できる）
    セッション管理がない

    セキュリティ上の注意

    • 必ず HTTPS で使う（HTTP では盗聴される）
    • 本番のユーザー認証には セッション＋フォームログイン や OAuth を推奨（OAuth は 73 の OAuth 2.0 の仕組み）
    • 管理画面の簡易保護や、開発環境での利用に限定するのが現実的

    Digest 認証との比較やほかのログイン方式は、73 の HTTP の古典的な方式：Basic 認証と Digest 認証 を参照してください。

    11.クッキーによるセッション管理

    HTTP は ステートレス（状態を保持しない）なので、ログイン状態などを維持するには別の仕組みが必要です。クッキーによるセッション管理 が最も一般的な方法です。クッキー（Cookie） はサーバーの指示でブラウザが保存し、次から自動で送り返す小さなデータ、セッション は複数のリクエストにまたがって状態を管理する仕組みです（クッキー自体の仕組みは Cookie の仕組み）。

    11.1 仕組みの流れ

    1. ログイン成功
   サーバー → ブラウザ: Set-Cookie: sessionId=abc123

2. ブラウザがクッキーを保存

3. 次回以降のリクエスト
   ブラウザ → サーバー: Cookie: sessionId=abc123

4. サーバーが sessionId をキーにセッションデータを取得
   → 「この人はログイン済みの yamada さんだ」と判断

    11.2 セッション ID とセッションデータ

    保存場所内容例
    クッキー（ブラウザ）セッション ID のみsessionId=abc123
    サーバー実際のユーザーデータ{ userId: 1, username: "yamada" }

    セッション ID は「ロッカーの鍵」、サーバー側のデータは「ロッカーの中身」 に例えると分かりやすいです。

    11.3 実装例（Express.js）

    Node.js の Web フレームワーク Express では、express-session というミドルウェア（リクエスト処理の途中に差し込む部品）でセッションを扱えます。

    const session = require('express-session');

app.use(session({
  secret: 'ランダムな秘密鍵',
  resave: false,
  saveUninitialized: false,
  cookie: {
    httpOnly: true,
    secure: true,
    sameSite: 'strict',
    maxAge: 24 * 60 * 60 * 1000
  }
}));

app.post('/login', (req, res) => {
  // 認証成功後
  req.session.userId = 1;
  req.session.username = 'yamada';
  res.json({ message: 'ログイン成功' });
});

    セッションとクッキーを使ったログイン・ログアウトの書き方は、次のページ セッションと Cookie によるログイン で詳しく扱います。

    12.セッション ID 漏洩の原因

    セッション ID が第三者に知られると、その ID を使って なりすまし（セッションハイジャック） が可能になります。ロッカーの鍵を拾われたら、中身を使われてしまうのと同じです。

    12.1 主な漏洩原因

    原因説明対策
    HTTP 通信の盗聴平文通信で Cookie が傍受されるHTTPS を使う、Secure 属性
    XSS 攻撃悪意ある JavaScript が Cookie を読み取るHttpOnly 属性、入力値のエスケープ
    Referer 経由URL にセッション ID を含めると漏洩Cookie 方式を使う（URL に載せない）
    ログやキャッシュサーバーログやプロキシに記録されるURL ではなく Cookie で管理
    セッション固定攻撃攻撃者が用意した ID を被害者に使わせるログイン成功時に ID を再生成
    物理アクセスPC を離席中に Cookie をコピーされるタイムアウト、再認証

    XSS（クロスサイトスクリプティング） は、攻撃者の JavaScript をページに紛れ込ませて被害者のブラウザで動かす攻撃です（XSS の基本）。

    12.2 セッション固定攻撃の例

    1. 攻撃者が sessionId=EVIL123 のセッションを取得する
    2. 被害者にそのURL（?sessionId=EVIL123）を踏ませる
    3. 被害者がログインする → サーバーは同じ sessionId=EVIL123 にユーザー情報を紐付ける
    4. 攻撃者が sessionId=EVIL123 でアクセスする → 被害者として操作できてしまう

    対策：ログイン成功時に必ず 新しいセッション ID を発行 する（session.regenerate() など）。攻撃の詳しい手口と対策は セッション管理の不備 で解説します。

    12.3 セッション ID の要件

    • 推測困難：ランダムで十分な長さ（128 bit 以上推奨）
    • 一意：他のユーザーと重複しない
    • HTTPS で送信：Secure 属性を設定
    • JavaScript から読めない：HttpOnly 属性を設定

    13.クッキーの属性

    クッキーには、送信範囲や有効期限、セキュリティを制御する 属性 があります。安全な Web アプリケーションでは、これらを正しく設定することが重要です。各属性の詳しい動きは Cookie の仕組み で解説しているので、ここでは徳丸本 1 章の要点を整理します。

    Set-Cookie: sessionId=abc123; Domain=example.com; Path=/; Expires=Wed, 01 Jan 2025 00:00:00 GMT; Secure; HttpOnly; SameSite=Strict

    13.1 属性ごとの要点

    属性何を決めるか要点
    Domainどのドメインに送信するかDomain=example.com なら example.com と *.example.com に送る。省略すると設定したホストのみ（www.example.com だけ等）。広げすぎるとサブドメイン間で共有され漏洩リスクが増えるので、必要最小限に
    Pathどの URL パス以下に送信するかPath=/app なら /app、/app/dashboard などに送信。Path=/ はサイト全体（最も一般的）
    Expires／Max-Age有効期限Expires は具体的な日時まで、Max-Age は設定から何秒間（例 Max-Age=86400）。両方省略すると セッション Cookie（ブラウザを閉じると削除）。ログインセッションには適切な期限を設け、長期間有効な Cookie は避ける
    SecureHTTPS 接続でのみ送信HTTP 通信では送信されない。セッション ID など機密性の高い Cookie には 必須
    HttpOnlyJavaScript から読めなくするdocument.cookie で読み取れない。XSS で Cookie が盗まれるリスクを大幅に低減。セッション ID には 必ず設定
    SameSiteクロスサイト（別サイト発）のリクエストで送るかStrict：同一サイトからのみ（最も厳格）／Lax：リンククリックなどのトップレベル移動では送る（デフォルト）／None：クロスサイトでも送る（Secure 必須）。CSRF 対策に有効で、セッション Cookie には Strict か Lax を推奨
     
    // HttpOnly なし → XSSで盗める
document.cookie; // "sessionId=abc123"

// HttpOnly あり → JavaScriptからは見えない
document.cookie; // "" （sessionIdは含まれない）

    13.2 安全なクッキー設定のまとめ

    安全な例：セッション ID のクッキー 
    res.cookie('sessionId', sessionId, {
  httpOnly: true,      // XSS対策
  secure: true,        // HTTPS必須
  sameSite: 'strict',  // CSRF対策
  maxAge: 3600000,     // 1時間で期限切れ
  path: '/'
});
    属性セッション ID一般 Cookie
    HttpOnly必須用途による
    Secure必須推奨
    SameSiteStrict／Lax推奨
    適切な有効期限必須推奨

    Cookie を出力するときの脆弱性（属性の付け忘れやヘッダへの値の混入）は クッキー出力にまつわる脆弱性 で扱います。

    15.理解度チェック

    Q1. HTTP が「ステートレス」であるとは、どういうことですか？ それによって何が必要になりますか？

    サーバーが前回の通信を覚えていない、ということです。そのため、ログイン状態などを複数のリクエストにまたがって保つには、クッキーによるセッション管理のような別の仕組みが必要になります。

    Q2. リクエストメッセージとレスポンスメッセージは、それぞれどんな 3 つの部分でできていますか？

    リクエストは「リクエストライン・リクエストヘッダ・メッセージボディ」、レスポンスは「ステータスライン・レスポンスヘッダ・メッセージボディ」です。どちらもヘッダとボディの間に空行が 1 行入ります。

    Q3. ログインフォームを GET で送ってはいけないのはなぜですか？

    GET ではパラメータが URL（クエリ文字列）に載るため、パスワードが履歴・ログ・Referer などに残って漏れるおそれがあるからです。ログインは POST でボディに入れて送ります。

    Q4. 価格や管理者フラグを Hidden パラメータで送ってはいけないのはなぜですか？

    Hidden パラメータは開発者ツールで誰でも見え、値を書き換えられるからです。権限・価格・ユーザー ID のような信頼すべき値はサーバー側で管理し、送られてきた値は必ずサーバーで再検証します。

    Q5. Basic 認証の Authorization: Basic eWFtYWRh... は暗号化されていますか？

    いいえ。「ユーザー名:パスワード」を Base64 で変換しただけで、誰でも元に戻せます。そのため Basic 認証は必ず HTTPS で使い、本番のユーザー認証にはセッション＋フォームログインや OAuth を使うのが推奨です。

    Q6. クッキーによるセッション管理で、ブラウザ側とサーバー側にはそれぞれ何が置かれますか？

    ブラウザのクッキーにはセッション ID（例 sessionId=abc123）だけが置かれ、ユーザー ID やユーザー名などの実際のデータはサーバー側に置かれます。セッション ID がロッカーの鍵、サーバーのデータがロッカーの中身です。

    Q7. セッション固定攻撃を防ぐために、ログイン成功時に何をしますか？

    新しいセッション ID を発行し直します（session.regenerate() など）。こうすれば、攻撃者があらかじめ被害者に使わせた ID は、ログイン後には使えなくなります。

    Q8. セッション ID のクッキーに付けるべき属性と、それぞれの目的を答えてください。

    HttpOnly（JavaScript から読めなくして XSS での盗難を防ぐ）、Secure（HTTPS のときだけ送って盗聴を防ぐ）、SameSite=Strict または Lax（別サイト発のリクエストで送らず CSRF を防ぐ）、そして適切な有効期限です。
