    00 全体像

    セッション管理の全体像

    一度ログインすれば、ページを移動してもログインしたままでいられます。当たり前に見えますが、HTTP そのものには「さっきの人と同じ人だ」と覚える機能がありません。このページでは、Cookie・セッション・トークンがどう組み合わさって「ログイン状態」を作っているのか、そしてこのフォルダの各ページがどこを扱うのかを、地図として解説します。

    もとにしたノート：00_全体像/MOC_セッション管理（あわせて 74_セッション管理 の各フォルダのノート）

    ひとことで言うと

    HTTP は毎回「はじめまして」です。そこで、ログインした人に 目印（セッション ID やトークン） を渡し、ブラウザが毎回それを見せることで「同じ人」と分かるようにします。セッション管理とは、この目印を安全に発行し、運び、確かめ、捨てる仕組み のことです。目印を盗まれると、パスワードを知らなくてもその人になりすませてしまいます。

    1.このシリーズの地図

    74_セッション管理 は、ステートレス（状態を持たない＝前のやりとりを覚えていない）な HTTP で「ログイン状態」を保つ仕組みと、その攻撃・対策を扱うフォルダです。ノートは次の 4 つのフォルダに分かれています。

    フォルダ役割解説ページ
    10_クッキーCookie のしくみと属性10-1
    20_セッションサーバー側セッションと、Cookie を使ったログイン状態の保持20-1・20-2
    30_トークントークン方式（JWT など）と、セッション方式との比較30-1〜30-4
    40_攻撃と対策セッション固定化・ハイジャック・Cookie 属性の不備40-1・40-2

    ノートのファイル名は「フォルダ内の通し番号_タイトル（出典）」の形です。徳丸浩『体系的に学ぶ 安全なWebアプリケーションの作り方』の章は（徳丸本N章）、動画・記事のクリップは（作者名）を末尾に付けています。

    2.なぜセッション管理が必要なのか

    HTTP は、ブラウザが「リクエスト（お願い）」を送り、サーバーが「レスポンス（返事）」を返す、という 1 往復で完結するやりとりです。1 往復が終わると、サーバーはその相手のことを忘れます。これが ステートレス という性質です。

    そのままだと、ログインした直後に「マイページ」を開いても、サーバーには「さっきログインした人」かどうかが分かりません。ページを移動するたびにパスワードを入れ直すことになってしまいます。

    そこで、次のような仕組みを組み合わせて「状態」を補います。

    Cookie（クッキー）

    サーバーがブラウザに保存させる小さなメモ。ブラウザは次から同じサイトへのリクエストに 自動で 付けて送ります。「運ぶ手段」です。

    セッション

    ログイン情報などを サーバー側 に保存し、ブラウザには番号（セッション ID）だけを渡す方式。番号札で荷物を預けるクロークのイメージです。

    トークン

    「誰か」「いつまで有効か」を書いて 署名 した通行証をブラウザに渡す方式。サーバーは覚えておかなくても、署名を確かめれば判断できます。JWT が代表例です。

    3.ログイン状態が保たれる流れ

    もっとも基本的な「Cookie ＋ セッション」方式の流れを図にします。トークン方式でも、②で渡すものが「番号」から「署名つきの通行証」に変わるだけで、流れの形は同じです。

    1. ログイン：本人確認そのもの（パスワード・MFA・パスキーなど）は 73 の範囲です（ログイン方式と認証の概念）。
    2. 目印の発行：推測できない十分ランダムな ID を作り、Cookie に入れて返します（20-2）。トークン方式なら署名つきの JWT を返します（30-2）。
    3. 目印を運ぶ：Cookie の属性（Secure・HttpOnly・SameSite など）で、どこに・いつ送られるかが決まります（10-1）。
    4. 目印を確かめる：サーバーがセッションを照合するか、トークンの署名と期限を検証します。そのうえで「その操作をしてよいか」（認可）を判断します（認証と認可の違い）。
    5. 目印を捨てる：ログアウトや期限切れで無効にします。トークンは一度発行すると取り消しにくいので工夫が必要です（30-3）。

    4.各フォルダの役割とページ

    4.1 10 クッキー：目印を運ぶ手段

    Cookie は、サーバーがレスポンスの Set-Cookie ヘッダーで保存させ、ブラウザが次のリクエストの Cookie ヘッダーで送り返す小さなデータです。有効期限・送り先・JavaScript から読めるかなどを 属性 で決めます。セッション管理の安全性の多くは、この属性の付け方で決まります。

    • 10-1 Cookieの仕組み — 流れ・中身・属性・種類・localStorage との違い

    4.2 20 セッション：サーバーが覚えておく方式

    情報はサーバーに置き、ブラウザには番号だけを持たせる方式です。番号さえ推測・盗難されなければ、Cookie の中身を見られても個人情報は漏れません。サーバー側で消せば即座にログアウトさせられるのも利点です。

    • 20-1 HTTPとセッション管理 — HTTP の基本から、Cookie によるセッション管理まで（徳丸本1章）
    • 20-2 セッションとCookieによるログイン — ログイン処理の全体像と実装、インフラとの関係

    4.3 30 トークン：サーバーが覚えなくてよい方式

    署名つきの通行証をブラウザ（やアプリ）に持たせる方式です。サーバーが状態を持たないので、複数サーバーやスマホアプリ・API と相性がよい一方、盗まれたときに取り消しにくいという弱点があります。その弱点を、短い期限のアクセストークンと長い期限のリフレッシュトークンの組み合わせで補います。

    • 30-1 セッション方式とトークン方式 — 違いと使い分け、3 種類のトークン
    • 30-2 JWTの構造と検証 — 中身・署名・攻撃・検証手順
    • 30-3 アクセストークンとリフレッシュトークン — 2 つを分ける理由とローテーション
    • 30-4 トークンの保存場所 — Cookie か localStorage か、BFF 方式

    4.4 40 攻撃と対策：目印を狙う攻撃

    目印を手に入れれば、攻撃者はパスワードなしで本人になりすませます（セッションハイジャック）。手に入れ方には「推測する」「盗む」「あらかじめ押し付ける（固定化）」の 3 通りがあります。

    • 40-1 セッション管理の不備 — 推測・盗み出し・固定化と、認証後に ID を変える対策（徳丸本9章）
    • 40-2 クッキー出力にまつわる脆弱性 — Cookie に入れてはいけない情報と Secure 属性（徳丸本11章）

    Cookie が自動で送られる性質を悪用する CSRF と、スクリプトでトークンや Cookie を盗む XSS は 72 で解説しています。

    8.理解度チェック

    Q1. 「HTTP はステートレス」とはどういう意味ですか？それで何が困りますか？

    1 回のリクエストとレスポンスが終わると、サーバーはその相手のことを覚えていない、という意味です。そのままだと、ログインした後に別のページを開いても同じ人だと分からず、毎回ログインし直すことになります。

    Q2. Cookie・セッション・トークンの関係をひとことずつで説明してください。

    Cookie は目印を「運ぶ手段」、セッションは情報をサーバーに置いて番号だけ渡す「方式」、トークンは署名つきの通行証そのものを渡す「方式」です。セッション ID もトークンも、Cookie に入れて運ぶことができます。

    Q3. セッション ID を攻撃者に知られると、何が起きますか？

    攻撃者がその ID を自分のブラウザの Cookie に入れるだけで、パスワードを知らなくても本人としてログインした状態になります（セッションハイジャック）。手口と対策は 40-1 で扱います。

    Q4. 「盗まれたので今すぐログアウトさせたい」とき、セッション方式とトークン方式のどちらが簡単ですか？

    セッション方式です。サーバーに保存したセッションを消せば、その ID はすぐ使えなくなります。トークン方式は、署名が正しく期限内であれば有効と判断されるため、期限を短くする・リフレッシュトークンを無効にするなどの工夫が必要です（30-3）。

    Q5. パスワードの安全な保存方法と、CSRF の対策は、それぞれどのフォルダが本拠地ですか？

    パスワードの保存は 73_認証認可（20-2）、CSRF は 72_Web脆弱性対策（30-1）です。74 はその間にある「ログイン状態の保ち方」を扱います。
