    10 クッキー

    Cookieの仕組み

    Cookie（クッキー）は、サーバーがブラウザに渡し、ブラウザが保存して次から自動で送り返す小さなデータです。HTTP は前の通信を覚えていないのに、一度ログインすると別のページでもログインしたままなのは Cookie のおかげです。このページでは、Cookie の流れ、Domain・Path・Expires／Max-Age・Secure・HttpOnly・SameSite などの属性、サーバーとブラウザでの扱い方、ファーストパーティ／サードパーティ Cookie の違い、「Cookie を許可しますか」との付き合い方、安全に使うための注意点を解説します。

    もとにしたノート：10_クッキー/01_クッキーとは、10_クッキー/02_Cookieとは_図解で理解するWebの仕組み（toamoku）、10_クッキー/03_Cookieとは_なぜログイン状態を覚えていられるのか（つるチャンネル）、10_クッキー/04_機械オンチにCookieを説明する動画（ぴちゃ）

    ひとことで言うと

    値を運ぶのが Cookie、意味を決めて覚えているのはサーバーです。サーバーは Set-Cookie で値を渡し、ブラウザは次から Cookie ヘッダに入れて自動で送ります。ログインに使う Cookie には ランダムなセッション ID だけ を入れ、HttpOnly・Secure・SameSite を付けるのが基本です。

    1.Cookie とは何か

    Cookie（クッキー） は、Web アプリケーションでユーザーの状態を管理するための仕組みです。サーバーがブラウザに送信し、ブラウザが保存する小さなデータで、次回同じサイトにアクセスしたときにブラウザが自動的にサーバーへ送信します。サーバーがブラウザへ渡す 小さなデータの断片（メモ）、つまり「クッキーのかけら」だと考えると覚えやすいです。

    ちなみに Cookie という名前の語源は、はっきりとは分かっていないそうです。

    1.1 前提：HTTP はステートレス

    Web の通信に使う HTTP は、ステートレス（状態を覚えない）な決まりごと（プロトコル）です。リクエスト（ブラウザからの依頼）ごとに独立していて、前の通信を覚えていません。

    たとえばログインして、サーバーが「認証に成功しました」と返したとします。ところが次に「マイページを見せて」と頼むと、サーバーは毎回「あなた誰？」となってしまいます。この問題を解決する仕組みの 1 つが Cookie です。HTTP とセッション管理の関係は HTTPとセッション管理 でくわしく扱います。

    1.2 日常生活での例え

    会員カード・ポイントカード

    店で発行され、次回来店時に提示します。会員カードを見ればあなたが会員だと分かるように、Cookie を見ればサーバーはあなたが誰かを識別できます。

    居酒屋のスタンプカードのように、店（Web サイト）が「この日に来た」「何回来た」と好きに書き込める カードです。ポイントはたまりません。

    Cookie

    サーバーが発行し、次回アクセス時にブラウザが自動的に送信します。

    Amazon でログインしていないのにカートに入れた商品が残っているのは、Cookie の働きです。ブラウザが毎回「かけら」（カギや会員証のようなもの）を渡すので、サーバーはそれに対応する情報を取り出し「このユーザーだ」と判断できます。

    2.Cookie の流れ：Set-Cookie と Cookie ヘッダ

    ログインでセッション ID（サーバーが利用者を見分けるために発行する番号）を保存する例で、流れを見てみます。ヘッダ とは、通信の本文とは別に付ける「付せん」のような情報です。

    1. 初回（Cookie をセット）：ログインに成功すると、サーバーはレスポンス（返事）のヘッダ Set-Cookie でセッション ID（例：ABC123）を返します。
    2. 保存：ブラウザはその値を サイトごとに分けて 保存します。
    3. 次回（自動で送信）：次にそのサイトへリクエストするとき、ブラウザは Cookie ヘッダに入れて 自動で 送ります。
    4. 識別：サーバーは ABC123 を「鶴田さんのログイン済みセッション」として覚えているので、本人だと分かります。

    ヘッダの中身は、次のようになります。

    // サーバーがクッキーを設定（レスポンスヘッダ）
Set-Cookie: sessionId=abc123; Path=/; HttpOnly

// 次回のリクエストで自動的に送信（リクエストヘッダ）
Cookie: sessionId=abc123

    判断しているのは Cookie ではない

    Cookie 自体が「この人は鶴田さん」と判断しているのではありません。値を運ぶのが Cookie、意味を決めるのがサーバー です。HTTP は覚えていない → Cookie を保存して次の通信で送る → サーバーが識別する、という分担です。セッション ID を使ったログインの全体は セッションとCookieによるログイン で扱います。

    3.Cookie の特徴と中身

    3.1 4 つの特徴

    特徴内容
    ブラウザに保存されるChrome・Safari・Firefox など各ブラウザが自動で管理します。サーバー → ブラウザ：Set-Cookie ヘッダで送信 → ブラウザが保存 → 次回アクセス時にブラウザが自動的に送信。
    自動的に送信されるブラウザは、同じドメインへのリクエストに自動的に Cookie を含めます。
    ドメインごとに管理されるCookie は設定されたドメインでのみ送信されます。example.com で設定された Cookie は example.com へのリクエストでのみ送られ、other.com へのリクエストでは送られません。
    サイズ制限がある1 つの Cookie は約 4KB まで、1 つのドメインあたり約 20 個まで保存できます（目安）。

    ドメイン とは、example.com のようなサイトの住所（名前）のことです。

    3.2 Cookie の構造：名前と値＋属性

    Cookie は キー（名前）と値 のペアに、送り方を決める 属性 が付いた形をしています。まるで小さな設定ファイルのようです。

    sessionid=abc123xyz;   ← キーと値
Path=/;                ← 属性：どのパスで送るか
HttpOnly;              ← 属性：JavaScript から読ませない
Secure;                ← 属性：HTTPS だけで送る
SameSite=Lax;          ← 属性：別サイトからの送信条件

    ブラウザがサーバーへ送り返すのは sessionid=abc123xyz の部分だけです。属性は「いつ・どこへ送るか」をブラウザに指示するためのもので、送り返されません。

    4.Cookie の属性

    属性は、Cookie を「いつまで残すか」「どこへ送るか」「誰に読ませるか」を決めるスイッチです。セキュリティに直結するので、1 つずつ見ていきます。

    4.1 属性の一覧

    属性決めること主な目的
    Expires／Max-Age有効期限（いつまで残すか）付けなければブラウザを閉じると消える
    Path送信するパスサイト内の一部だけで使う
    Domain送信するドメインサブドメインにも送るか
    HttpOnlyJavaScript から読めるかXSS で盗まれるのを防ぐ
    SecureHTTPS のときだけ送るか盗聴で抜かれるのを防ぐ
    SameSite別サイトからの依頼で送るかCSRF 対策

    4.2 Expires／Max-Age（有効期限）

    Cookie の有効期限を設定します。Expires は「この日時まで」、Max-Age は「今から何秒間」で指定します。Express.js（Node.js の Web フレームワーク）の res.cookie() では、maxAge をミリ秒、expires を日付で渡します。

    // maxAge（ミリ秒）
res.cookie('username', 'yamada', {
  maxAge: 24 * 60 * 60 * 1000 // 24時間
});

// expires（日付）
res.cookie('username', 'yamada', {
  expires: new Date(Date.now() + 24 * 60 * 60 * 1000) // 24時間後
});

    単位に注意

    Express の maxAge はミリ秒ですが、実際に送られる Set-Cookie ヘッダの Max-Age や、ブラウザの document.cookie で書く max-age は 秒 です（max-age=86400 が 24 時間）。

    有効期限の有無で、Cookie は 2 種類に分かれます。

    セッションクッキー

    ブラウザを閉じると削除される Cookie。maxAge や expires を設定しません。

    res.cookie('sessionId', 'abc123', {
  httpOnly: true
});

    永続クッキー

    有効期限が設定されている Cookie。期限まではブラウザを閉じても残ります。

    res.cookie('username', 'yamada', {
  maxAge: 365 * 24 * 60 * 60 * 1000 // 1年間
});

    期限を過去にする（max-age=0）と、Cookie を削除できます（5 章）。

    4.3 Path（パス）

    Cookie を送信するパス（URL のドメインより後ろの部分）を指定します。

    res.cookie('username', 'yamada', {
  path: '/admin' // /admin以下のパスでのみ送信
});

    Path=/ ならサイト全体で送られます。

    4.4 Domain（ドメイン）

    Cookie を送信するドメインを指定します。

    res.cookie('username', 'yamada', {
  domain: '.example.com' // example.comとそのサブドメインで送信
});

    サブドメイン とは、shop.example.com のように親ドメインの前に名前を足した住所です。Domain を付けなければ、Cookie を発行したホストにだけ送られます。付けると送り先が広がるので、必要なときだけ付けます。Domain 指定の広げすぎが招く問題は クッキー出力にまつわる脆弱性 を参照してください。

    4.5 HttpOnly（JavaScript からのアクセス制限）

    JavaScript から Cookie を読めないようにします。セキュリティのため重要です。

    res.cookie('sessionId', 'abc123', {
  httpOnly: true // JavaScriptからアクセス不可（XSS攻撃対策）
});

    XSS（クロスサイトスクリプティング） とは、攻撃者のスクリプトをページに紛れ込ませる攻撃です。HttpOnly がないと、紛れ込んだスクリプトが document.cookie でセッション ID を読み取り、外へ送れてしまいます。HttpOnly を付けても、Cookie はブラウザが通常どおりサーバーへ送ります（読めなくなるのは JavaScript だけ）。盗み出しの流れは 72 XSSの基本 にあります。

    4.6 Secure（HTTPS のみ）

    HTTPS 接続でのみ送信されるようにします。HTTPS は通信を暗号化した HTTP です。Secure がないと、暗号化されていない HTTP の通信でも Cookie が送られ、途中で盗聴されて抜かれるおそれがあります。

    res.cookie('sessionId', 'abc123', {
  secure: true // HTTPSのみ送信
});

    4.7 SameSite（別サイトからの送信を制御）

    クロスサイトリクエスト（別のサイトのページから、あなたのサイトへ飛んでくる依頼）で Cookie を送る条件を制御します。他サイトから勝手に送信される攻撃、CSRF（クロスサイトリクエストフォージェリ） の対策になります。

    res.cookie('sessionId', 'abc123', {
  sameSite: 'strict' // 同一サイトからのみ送信
  // 'lax': GETリクエストのみクロスサイトで送信
  // 'none': すべてのクロスサイトリクエストで送信（secure必須）
});
    値別サイトからの依頼で送るか補足
    Strict送らない（同一サイトからのみ）いちばん厳しい。別サイトのリンクから来たときも送られないので、ログインしていない状態で開くことになります。
    Lax原則送らない。GET（リンクをたどってページを移動する場合）だけ送るフォームの POST など、状態を変える依頼には付かないので CSRF を防ぎやすい。使い勝手とのバランスがよく、指定しないときの既定値にしているブラウザもあります。
    Noneすべて送るSecure が必須。別サイトに埋め込む用途などに限ります。

    CSRF の攻撃の流れと、SameSite 以外の対策（トークンの埋め込みなど）は 72 CSRF、画面と API を別オリジンに分けたときの Cookie の付き方は 72 CORSエラーの対処法とCookie を参照してください。

    4.8 ログイン用 Cookie の基本形

    ログインに使う Cookie は、4 つの属性をそろえて付けるのが基本です。

    res.cookie('sessionId', sessionId, {
  httpOnly: true,              // JavaScriptから読ませない（XSS対策）
  secure: true,                // HTTPSのみ（盗聴対策）
  sameSite: 'strict',          // 別サイトから送らない（CSRF対策）
  maxAge: 24 * 60 * 60 * 1000  // 24時間
});

    ヘッダにすると Set-Cookie: sessionId=…; Max-Age=86400; Path=/; HttpOnly; Secure; SameSite=Strict のようになります。

    5.Cookie の使い方

    5.1 サーバー側での設定（Express.js）

    cookie-parser は、届いた Cookie ヘッダを読みやすい形（req.cookies）にしてくれる部品です。

    const express = require('express');
const cookieParser = require('cookie-parser');
const app = express();

app.use(cookieParser());

// クッキーを設定
app.get('/set-cookie', (req, res) => {
  res.cookie('username', 'yamada', {
    maxAge: 24 * 60 * 60 * 1000, // 24時間（ミリ秒）
    httpOnly: true, // JavaScriptからアクセス不可
    secure: true, // HTTPSのみ
    sameSite: 'strict' // CSRF攻撃対策
  });
  res.send('クッキーを設定しました');
});

// クッキーを読み取る
app.get('/get-cookie', (req, res) => {
  const username = req.cookies.username;
  res.json({ username: username || 'クッキーがありません' });
});

// クッキーを削除
app.get('/delete-cookie', (req, res) => {
  res.clearCookie('username');
  res.send('クッキーを削除しました');
});

    5.2 クライアント側での操作（JavaScript）

    ブラウザの JavaScript では document.cookie で Cookie を書いたり読んだりできます。読むと a=1; b=2 のように全部がつながった文字列で返るので、名前で取り出す関数を用意します。HttpOnly の Cookie はここには出てきません。

    // クッキーを設定
document.cookie = 'username=yamada; max-age=86400; path=/';

// クッキーを読み取る
function getCookie(name) {
  const value = `; ${document.cookie}`;
  const parts = value.split(`; ${name}=`);
  if (parts.length === 2) {
    return parts.pop().split(';').shift();
  }
  return null;
}

// 使用例
const username = getCookie('username');
console.log(username); // 'yamada'

// クッキーを削除（有効期限を過去に設定）
function deleteCookie(name) {
  document.cookie = `${name}=; max-age=0; path=/`;
}

deleteCookie('username');

    5.3 Cookie の確認方法

    ブラウザの開発者ツールで、保存されている Cookie と属性を一覧できます。

    • Chrome／Edge：F12 → Application → Cookies
    • Firefox：F12 → Storage → Cookies
    • Safari：開発メニュー → Web インスペクタ → Storage → Cookies

    JavaScript で確認するなら、コンソールで次のようにします。

    // すべてのクッキーを表示
console.log(document.cookie);

// 特定のクッキーを取得（5.2 の getCookie を使用）
console.log(getCookie('username'));

    6.Cookie の用途

    Cookie はログイン専用ではありません。ユーザー設定・カート・アクセス解析などにも使われます。

    6.1 ログイン状態の保持

    ログイン成功時に、セッション ID を Cookie に保存します。

    app.post('/api/login', async (req, res) => {
  const { username, password } = req.body;

  // 認証処理
  if (await authenticate(username, password)) {
    const sessionId = generateSessionId();

    // セッションIDをクッキーに保存
    res.cookie('sessionId', sessionId, {
      httpOnly: true,
      secure: true,
      sameSite: 'strict',
      maxAge: 24 * 60 * 60 * 1000 // 24時間
    });

    res.json({ message: 'ログイン成功' });
  } else {
    res.status(401).json({ error: '認証に失敗しました' });
  }
});

    実際には express-session のようなライブラリを使うと、セッション ID の発行と Cookie への保存をまとめて任せられます。セッションに保存するのはユーザー ID などで、Cookie にはセッション ID だけが入ります。

    const express = require('express');
const session = require('express-session');
const app = express();

// セッションの設定（セッションIDはクッキーに保存される）
app.use(session({
  secret: 'your-secret-key',
  resave: false,
  saveUninitialized: false,
  cookie: {
    secure: true, // HTTPSのみ
    httpOnly: true, // JavaScriptからアクセス不可
    maxAge: 24 * 60 * 60 * 1000, // 24時間
    sameSite: 'strict' // CSRF攻撃対策
  }
}));

// ログイン
app.post('/api/login', (req, res) => {
  const { username, password } = req.body;

  if (authenticate(username, password)) {
    // セッションにユーザー情報を保存
    req.session.userId = getUserId(username);
    res.json({ message: 'ログイン成功' });
  } else {
    res.status(401).json({ error: '認証に失敗しました' });
  }
});

// 認証が必要なエンドポイント
app.get('/api/profile', (req, res) => {
  if (!req.session.userId) {
    return res.status(401).json({ error: 'ログインが必要です' });
  }

  const user = getUserById(req.session.userId);
  res.json(user);
});

    この仕組みの詳しい流れは セッションとCookieによるログイン、ログイン方式全体は 73 ログイン方式と認証の概念 を参照してください。

    6.2 ユーザー設定の保存

    言語設定のように画面側でも読みたい値は、httpOnly: false にします（秘密ではない値に限ります）。

    app.post('/api/settings/language', (req, res) => {
  const { language } = req.body;

  res.cookie('language', language, {
    maxAge: 365 * 24 * 60 * 60 * 1000, // 1年間
    httpOnly: false // クライアント側でも読み取り可能
  });

  res.json({ message: '言語設定を保存しました' });
});

    6.3 ショッピングカートの管理

    app.post('/api/cart/add', (req, res) => {
  const { productId, quantity } = req.body;

  // 既存のカートを取得
  const cart = JSON.parse(req.cookies.cart || '[]');

  // 商品を追加
  cart.push({ productId, quantity });

  // クッキーに保存
  res.cookie('cart', JSON.stringify(cart), {
    maxAge: 7 * 24 * 60 * 60 * 1000, // 7日間
    httpOnly: false
  });

  res.json({ message: 'カートに追加しました' });
});

    Cookie の値は利用者が自由に書き換えられるので、価格などをそのまま信じてはいけません。また 1 つ約 4KB までなので、大きなカートには向きません。

    6.4 トラッキング（分析）

    訪問者ごとにランダムな ID を振り、同じ人が何回来たかを数えます。たとえばテスラのサイトで同じ車を 10 回見に来た人がいれば「相当欲しい人だ」と判断でき、その人にだけ特別オファーを出す、といったことができます。Cookie を使わないと「同じ人が何回も来ている」と記録できないので、毎回初めての人として対応するしかありません。

    app.use((req, res, next) => {
  if (!req.cookies.visitorId) {
    const visitorId = generateVisitorId();
    res.cookie('visitorId', visitorId, {
      maxAge: 365 * 24 * 60 * 60 * 1000, // 1年間
      httpOnly: false
    });
  }
  next();
});

    7.ファーストパーティ Cookie とサードパーティ Cookie

    7.1 ファーストパーティ Cookie：その店専用のスタンプカード

    ここまで説明した Cookie は、基本的に 訪問したサイト自身が発行するもの で、ファーストパーティ Cookie と呼ばれます。店が発行して店が書き込むポイントカードで、その店の中で閉じています。居酒屋のスタンプカードを落としても誰も困らないのと同じで、問題視されることはほぼありません。

    7.2 サードパーティ Cookie：共通ポイントカード

    サードパーティ Cookie（Third-Party Cookie） は、「今アクセスしているサイトとは 別のドメインが発行する Cookie」です。たとえば news-site.com を見ているときに、ページに埋め込まれた広告の ad-tracker.com が Cookie を発行するケースです。ユーザーが見ているのは news-site.com なのに、第三者（サードパーティ）である広告サービスが Cookie を付けてくるので、この名前になっています。

    例えるなら T ポイントカード（現在の V ポイント）のような 共通ポイントカード です。いろいろな店で出せるように、サードパーティ Cookie は いろいろなサイトで使い回されます。「この人はこの日に A 店に行き、その後 B 店に行った」が 1 枚のカードに書かれていくわけです。

    7.3 何に使われていたか

    • 複数のサイトにまたがる 行動トラッキング（追跡）
    • 興味に合わせた 広告の最適化（リターゲティング広告）
    • アナリティクス（アクセス解析）の高度な計測

    広告業界の標準技術として長く使われてきました。テスラのサイトを見た後に近所のラーメン屋のサイトやはてなブログを開くと、「テスラが好きなあなたにおすすめ」のように 別サイトで閲覧履歴に基づいた広告 が出るのはこの仕組みです。不動産サイトで北海道の豪邸を見た直後、まったく関係ないサイトで豪邸の広告が並ぶ、といった経験もこれです。

    テスラのサイト内で「よく見てくれるあなたへ」と出る分には気になりませんが、別サイトでテスラの広告が出ると「自分の閲覧行動が抜かれている」と気持ち悪く感じる人が多く、問題視されるようになりました。

    7.4 サードパーティ Cookie は廃止・規制の方向へ

    ノート作成時点で、各ブラウザは次のように廃止方向へ動いています。

    • Safari：既にブロック
    • Firefox：既にデフォルトでブロック
    • Chrome：2024〜2025 に段階的廃止（進行中）
    • Edge：2024 から段階的に廃止

    理由は、トラッキングが過度に行われていたこと、ユーザーのプライバシーを守るため、GDPR（EU の個人データ保護の法律）など各国の法律との整合性のためです。

    法律面では、日本では 2022〜2023 年ごろの法改正で サードパーティ Cookie を許可なしで使うことは禁止 になりました（動画での説明）。ファーストパーティ Cookie は無許可でも OK なことが多いものの、アメリカや EU などで取り決めが違い、EU ではファーストパーティ Cookie でも許可が必要な場合があります。

    開発者としての方針

    サードパーティ Cookie は今後 ほぼ使えなくなる と考えて構いません。Google は「Privacy Sandbox」などの代替技術を提案していますが、基本的には サードパーティ Cookie を前提にした実装はしない、サードパーティ Cookie なしのログイン・分析方法を採用する 方向にシフトしていく必要があります。

    8.「Cookie を許可しますか」との付き合い方

    Web ページを開くと「Cookie を使用します。同意しますか」と大きく表示されることがあります。Cookie が何か分からないと怖く感じますが、結論は そこまで怖がらなくてよい、ただ問題視される面もあるので適切な距離感を知っておく です。

    8.1 Cookie そのものは「店が書き込むカード」

    基本の Cookie は、店（サイト）が勝手に書き込んでいるだけ のスタンプカードです。名前などの個人を特定する情報とは紐づいていません。「許可を押したら自分の名前がサイトに取られるのでは」という類いのものではないのです。個人情報が渡るのは、Google アカウントとの連携のように こちらから個人情報を渡したとき です。

    同意を求められているのがファーストパーティかサードパーティかは、パッと見では分かりません。EU の規制に合わせて国際展開している企業ほどよく聞いてきますし、日本のサイトでも EU 向けに通販していれば同じです。見分けるには「詳細はこちら」から規約を読み、「第三者への送信を含みます」と書かれているかを確認する必要があります。

    8.2 許可・拒否の考え方（動画の講師の場合）

    以下は推奨ではなく「講師はこうしている」という話です。

    • 講師は 全部許可 しています。サードパーティも気にせず、むしろパーソナライズ広告を「育てたい」（興味のない広告ではなく欲しいものを薦めてほしい）と考えているからです。
    • 拒否するメリット：「自分が何を見ているかを統合してまとめられるのが気持ち悪い」人はそれを避けられます。名前とは紐づかないものの、「あるユーザーが北海道の豪邸を見た後にはてなブログを読んでいる」と把握されたくない人は拒否するとよいでしょう。家族共有のパソコンで、閲覧履歴に沿った広告が出ると困る場合も同様です。
    • ログインを含まない閲覧で許可しても、起きるのはせいぜい「いろいろ見ているな」というデータを取られる程度です。
    • 同意ボタンは、押してほしい「許可」がなるべく押しやすい位置に置かれています。

    極端な例として、コンピューターサイエンスの大家ブライアン・カーニハンは、個人情報を取られるのが嫌で JavaScript をすべて切ってブラウジングしている（そのためサイトがまともに表示されない）と著書に書いているそうです。

    8.3 いちばん注意すべきはログイン用の Cookie：診察券

    Cookie を許可して起きうる最大のトラブルは、ログイン情報の代わりに Cookie を使う ケースで、これはここまでの話とは質的に別物です。病院の 診察券 に例えられます。

    1. 初診では、診察券は病院が書き込んでいるだけで、まだあなたの個人情報とは紐づいていません。
    2. 保険証を見せると、病院の中のシステムで診察券とあなたの情報が紐づけられます（＝ログイン）。
    3. 次からは診察券だけで済みます（＝Cookie でログイン状態を再利用）。
    4. 月が変わると保険証を見せてと言われるように、一定期間たつと「もう一度ログインしてください」と言われます。

    この使い方をしている Cookie は、それがあればログインできてしまう 個人情報に近いもの です。友達のパソコンで Twitter などにログインすると、Cookie にログイン情報が残ります。

    他人のパソコンでログインしたら

    • 使い終わったら ログアウトする か、Cookie を消す。ただしログアウトしてもブラウザに余計な情報が残ることがあります。
    • そもそも他人のパソコンでログインしないのがいちばん安全です。
    • どうしても使うなら シークレットモード（Safari では プライベートブラウズ）を使います。ブラウザを閉じれば Cookie などが全部残らない設定になっています。実家や家族共有のパソコンで、見たページの痕跡を残したくないときにも使えます。

    8.4 Cookie を消すと直ることがある

    Amazon で注文画面に進めずループする、いつまでも特定の商品が買えない、といった不具合が再起動でも直らないとき、公式ヘルプには「ブラウザの Cookie を削除すると直ります」と書かれていることがあります。Google Chrome なら右上の 3 つの点のメニュー → 設定 から Cookie を削除できます。ただし消すとログイン情報も消える可能性があるので、各サイトでもう一度ログインが必要になります。

    9.Cookie のセキュリティとよくある間違い

    Cookie は便利な反面、扱いを間違えるとセキュリティの問題になります。特に重要なのは次の 4 つです。

    9.1 機密情報を保存しない

    Cookie はブラウザ側にあり、利用者が中身を見たり書き換えたりできます。パスワード・メールアドレス・クレジットカード番号などの重要情報を直接入れるのは絶対 NG です。入れてよいのは ランダムなセッショントークン（セッション ID） で、機密情報はサーバー側のセッションに保存します。

    危険な例：機密情報をそのまま Cookie に保存 
    res.cookie('password', userPassword); // 危険！
res.cookie('creditCard', cardNumber);
    安全な例：セッションIDのみ保存 
    res.cookie('sessionId', sessionId, {
  httpOnly: true,
  secure: true
});
// 機密情報はサーバー側のセッションに保存
// sessionid=ランダム文字列 ← これはOK

    セッション ID の推測されにくさなどの要件は セッション管理の不備 で扱います。

    9.2 HttpOnly を設定しない

    危険な例：JavaScript からアクセス可能（XSS 攻撃のリスク） 
    res.cookie('sessionId', sessionId);
    安全な例：JavaScript からアクセス不可 
    res.cookie('sessionId', sessionId, {
  httpOnly: true // XSS攻撃から保護
});

    9.3 Secure を設定しない（本番環境）

    危険な例：HTTP でも送信される（盗聴のリスク） 
    res.cookie('sessionId', sessionId, {
  httpOnly: true
});
    安全な例：HTTPS のみ送信 
    res.cookie('sessionId', sessionId, {
  httpOnly: true,
  secure: true // 本番環境では必須
});

    9.4 SameSite を設定しない

    危険な例：CSRF 攻撃のリスク 
    res.cookie('sessionId', sessionId, {
  httpOnly: true,
  secure: true
});
    安全な例：CSRF 攻撃から保護 
    res.cookie('sessionId', sessionId, {
  httpOnly: true,
  secure: true,
  sameSite: 'strict' // CSRF攻撃対策
});

    Cookie を出力するサーバー側のコードに潜む脆弱性（ヘッダインジェクションや属性の付け忘れなど）は クッキー出力にまつわる脆弱性 と 72 リダイレクトとHTTPヘッダインジェクション を参照してください。

    10.セッション・LocalStorage との違い

    10.1 Cookie とセッション

    セッション は、利用者ごとの情報をサーバー側に保存しておく仕組みです。Cookie はその合言葉（セッション ID）を運ぶ役です。

    項目クッキーセッション
    保存場所ブラウザサーバー
    サイズ制限約 4KB制限なし
    セキュリティ低い（利用者が見られる。HttpOnly がなければ JavaScript からもアクセス可能）高い（サーバー側のみ）
    有効期限設定可能設定可能
    用途ユーザー設定、トラッキングログイン状態、機密情報

    使い分けの詳細は HTTPとセッション管理 を参照してください。

    10.2 Cookie と LocalStorage

    LocalStorage は、ブラウザに文字データを保存できる別の仕組みで、JavaScript から読み書きします。

    項目CookieLocalStorage
    サーバーへ自動送信されるされない
    容量4KB5MB
    JS から読める？HttpOnly なら不可いつでも可
    向いている用途認証UI 設定・一時保存

    LocalStorage はいつでも JavaScript から読めるので、XSS があると中身を盗まれやすくなります。元記事では「認証は Cookie（HttpOnly）一択」としています。トークンをどこに保存するかの比較は トークンの保存場所 でくわしく扱います。

    11.まとめ

    テーマ押さえること
    前提HTTP はステートレスで、前の通信を覚えていない
    Cookie とはサーバーが渡し、ブラウザが保存して自動で送り返す小さなメモ。中身はキーと値＋属性
    流れSet-Cookie で渡す → サイトごとに保存 → Cookie ヘッダで自動送信 → サーバーが識別
    役割分担値を運ぶのが Cookie、覚えて意味を決めるのはサーバー
    期限Expires／Max-Age なし＝セッションクッキー、あり＝永続クッキー。Max-Age は秒（Express の maxAge はミリ秒）
    送り先Domain（付けると送り先が広がる）・Path で絞る
    守りの属性HttpOnly（XSS で読ませない）・Secure（HTTPS のみ）・SameSite（CSRF 対策）をログイン用 Cookie に必ず付ける
    中身機密情報は入れず、ランダムなセッション ID だけ。サイズは約 4KB まで
    サードパーティ別ドメインが発行し、サイトをまたいで行動を追う。ブラウザ・法律ともに廃止・規制の方向で、前提にした実装はしない
    利用者として普通の Cookie は過度に怖がらなくてよい。ログイン用 Cookie は診察券なので、他人の PC ではログアウト・Cookie 削除・シークレットモード

    12.理解度チェック

    Q1. HTTP は前の通信を覚えていないのに、なぜログイン状態が続くのですか？

    ログイン成功時にサーバーが Set-Cookie でセッション ID を渡し、ブラウザがそれを保存して、次のリクエストから Cookie ヘッダで自動的に送るからです。サーバーはそのセッション ID が誰のものかを覚えているので、本人だと分かります。

    Q2. 「Cookie がユーザーを判断している」は正しいですか？

    正しくありません。Cookie は値を運ぶだけで、その値が誰を意味するかを決めて覚えているのはサーバーです。

    Q3. HttpOnly・Secure・SameSite は、それぞれ何を防ぎますか？

    HttpOnly は JavaScript から読めなくして、XSS で Cookie を盗まれるのを防ぎます。Secure は HTTPS のときだけ送るようにして、盗聴で抜かれるのを防ぎます。SameSite は別サイトからの依頼で Cookie を送る条件を絞り、CSRF を防ぎます。

    Q4. Express で maxAge: 86400 と書いたら、Cookie は何時間残りますか？

    Express の maxAge はミリ秒なので、86400 ミリ秒＝約 86 秒で消えてしまいます。24 時間にしたいなら 24 * 60 * 60 * 1000 と書きます。一方、document.cookie や Set-Cookie ヘッダの Max-Age は秒なので、そちらでは 86400 が 24 時間です。

    Q5. 有効期限を指定しない Cookie はどうなりますか？

    セッションクッキーになり、ブラウザを閉じると削除されます。期限を付けたものは永続クッキーで、期限までは残ります。

    Q6. SameSite の Strict・Lax・None の違いを説明してください。

    Strict は同一サイトからの依頼でだけ送ります。Lax は別サイトからの依頼では原則送らず、リンクをたどってページを移動する GET のときだけ送ります。None はすべての依頼で送り、Secure が必須です。

    Q7. ユーザー名とパスワードを Cookie に入れておけば、毎回ログインしなくて済みます。この設計の問題は？

    Cookie はブラウザ側にあり、利用者が見たり書き換えたりでき、盗まれれば中身がそのまま漏れます。機密情報はサーバー側のセッションに保存し、Cookie にはランダムなセッション ID だけを入れます。

    Q8. ファーストパーティ Cookie とサードパーティ Cookie の違いと、サードパーティが問題視される理由は？

    ファーストパーティは訪問したサイト自身が発行する Cookie（その店専用のスタンプカード）、サードパーティは別のドメイン（広告会社など）が発行する Cookie（共通ポイントカード）です。サードパーティは複数のサイトで使い回され、サイトをまたいだ行動を追跡できるため、プライバシーの面から問題視され、ブラウザでのブロックや法律での規制が進んでいます。

    Q9. 友達のパソコンで SNS にログインするときの注意点は？

    ログイン用の Cookie は診察券のようなもので、残っていれば他人がログインできてしまいます。使い終わったらログアウトするか Cookie を消すこと、できればシークレットモード（プライベートブラウズ）を使うこと、そもそも他人のパソコンでログインしないのが安全です。

    Q10. 認証情報を LocalStorage ではなく HttpOnly の Cookie に置くことが勧められるのはなぜですか？

    LocalStorage はいつでも JavaScript から読めるので、XSS があると盗まれやすいからです。HttpOnly の Cookie は JavaScript から読めず、しかもサーバーへ自動で送られます。
