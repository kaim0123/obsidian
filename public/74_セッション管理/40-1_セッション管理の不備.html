    40 攻撃と対策

    セッション管理の不備

    セッションID を奪われると、攻撃者はパスワードを知らなくても本人になりすませます。徳丸本 9 章に沿って、セッションID が「推測・盗み出し・強制」で奪われる仕組み（URL 埋め込み・Referer 漏洩・セッション固定化・セッションアダプション）と、ログイン時の ID 再生成を中心とした対策を整理します。

    もとにしたノート：40_攻撃と対策/01_セッション管理の不備（徳丸本9章）

    このページで分かること

    • セッションハイジャックとは何か、セッションID が漏れる 3 つの経路
    • 推測されやすいセッションID の作り方と、安全な作り方・要件
    • URL に セッションID を埋め込むと、なぜ Referer・ログ・履歴から漏れるのか
    • セッション固定化攻撃とセッションアダプションの関係
    • 認証後の ID 再生成、トークンによる代替策、ログイン前の対策

    ひとことで言うと

    セッションID は「本人の代わりになる鍵」です。だから 予測できない乱数で作り、URL に載せず Cookie だけで運び、ログインに成功したら必ず作り直す（session_regenerate_id(true) など）。この 3 つで、推測・盗み出し・強制のほとんどを防げます。

    セッションと Cookie の基礎は HTTPとセッション管理（徳丸本 1 章）と セッションとCookieによるログイン、CSRF は CSRF（徳丸本 8 章、Web脆弱性対策解説）で扱いました。このページは 9 章の「セッション管理の不備」による攻撃と対策です。

    1.セッションハイジャックとは

    セッションハイジャック（Session Hijacking） とは、他人の セッションID（ログイン状態をサーバーが見分けるための番号）を入手し、そのユーザーになりすます攻撃です。サーバーは「正しいセッションID を持っている人＝本人」と判断するので、ID さえ手に入れば本人として振る舞えます。

    1.1 日常生活での例え

    セッションID

    レストランの 整理券。番号が分かれば、誰が持っていても同じサービスを受けられます。

    セッションハイジャック

    他人の整理券を盗んで、本人になりすまして注文することです。

    1.2 攻撃の流れ

    1. 正規ユーザーがログイン（セッションID = abc123）
2. 攻撃者が abc123 を入手
3. 攻撃者が Cookie に sessionId=abc123 を設定
4. サーバーは「正規ユーザー」と判断
5. 攻撃者が本人になりすまして操作

    1.3 セッションIDが漏れる主な経路

    経路説明
    推測規則性のある ID を総当たりする
    盗み出しXSS、盗聴、Referer 漏洩などで ID を取得する
    強制セッション固定化攻撃で、被害者に特定の ID を使わせる

    2.セッションIDの推測・盗み出し・強制

    セッションハイジャックは、セッションID を入手する方法によって 3 つに分けて考えられます。

    2.1 推測

    推測しやすいセッションID を総当たり（ブルートフォース：考えられる値を片っ端から試すこと）で試す方法です。

    攻撃者: sessionId=100001, 100002, 100003 ... と試行
→ 当たればなりすまし成功

    2.2 盗み出し

    正当な手段以外で 第三者が ID を取得 する方法です。

    手法説明
    XSSdocument.cookie で Cookie を読み取る（詳しくは XSS によるクッキー値の盗み出し）
    盗聴HTTP 通信を傍受する（HTTPS 未使用時）
    Referer 漏洩URL に埋め込んだ ID が Referer で外部に送られる（6 章）
    物理アクセス離席中の PC から Cookie をコピーする

    2.3 強制

    攻撃者が 被害者に特定のセッションID を使わせる 方法です（セッション固定化攻撃。7 章）。

    攻撃者が sessionId=EVIL123 を用意
→ 被害者にその ID でアクセスさせる
→ 被害者がログイン
→ 攻撃者も EVIL123 でアクセス可能

    3.ありがちなセッションID生成方法

    安全でないセッションID の作り方は、推測攻撃 を可能にします。

    3.1 危険な生成方法

    方法例問題
    連番100001, 100002次の ID が容易に推測できる
    タイムスタンプ1704067200現在時刻付近を試せば当たる
    ユーザー名のハッシュmd5("yamada")入力の候補が限られれば総当たりできる
    短いランダム6 桁の数字試行回数が現実的な範囲に収まる
    固定値全ユーザー共通1 つ分かれば全員に影響する
    危険な例 
    $sessionId = md5(time());             // タイムスタンプベース
$sessionId = $_SERVER['REMOTE_ADDR']; // IP アドレス
$sessionId = $userId;                 // ユーザーIDそのもの
$sessionId = rand(100000, 999999);    // 範囲が狭い

    3.2 安全な生成方法

    安全な例：暗号学的に安全な乱数を使う 
    $sessionId = bin2hex(random_bytes(32));  // 256bit

// PHP セッション（php.ini / session_regenerate_id 等と併用）
session_start();

    実際には自分で ID を作るより、言語やフレームワークが用意するセッション機能（PHP の session_start() など）に任せるのが基本です。

    3.3 セッションIDの要件

    要件推奨
    エントロピー（予測しにくさの量）128bit 以上（256bit 推奨）
    ランダム性random_bytes() などの CSPRNG（暗号学的に安全な疑似乱数生成器）
    一意性衝突しないよう DB で確認する
    予測不可能時刻・連番・ユーザー情報に依存しない

    4.推測したセッションIDで成りすましを試行する

    セッションID の総当たり攻撃 は、推測可能な ID に対して行われます。

    4.1 攻撃の流れ

    1. 攻撃者がセッションIDの形式を分析
   例: 6桁の数字、タイムスタンプ+連番 等

2. 有効な ID を総当たり
   for id in range(100000, 999999):
       request with Cookie: sessionId=id

3. ログイン済みセッションが見つかればなりすまし

    4.2 防御

    対策効果
    十分なランダム性総当たりを非現実的にする
    ログイン試行制限ブルートフォースの速度を下げる（ログイン機能への攻撃と対策）
    セッション有効期限盗んでも使える時間を短くする
    異常検知IP 変更時などに再認証を求める

    5.URL埋め込みのセッションID

    URL にセッションID を含める 方式（URL リライト：リンクの URL に自動で ID を付け足す仕組み。<a href="?PHPSESSID=abc123"> など）は 非推奨 です。

    5.1 問題のある URL

    https://example.com/page?PHPSESSID=abc123def456
https://example.com/page;jsessionid=abc123

    5.2 なぜ危険か

    問題説明
    Referer 漏洩外部リンクをクリックすると、Referer で ID が送られる
    ブックマークURL が保存され、共有・漏洩のリスクがある
    サーバーログアクセスログにセッションID が記録される
    ブラウザ履歴履歴に ID が残る
    共有URL をコピーして送ると ID も一緒に渡る

    5.3 安全な方式

    安全

    Cookie にセッションID を保存する（HttpOnly, Secure）

    危険

    URL パラメータやパスにセッションID を含める

    安全な例：php.ini で Cookie だけを使う 
    session.use_only_cookies = 1
session.use_trans_sid = 0   // URL への自動付加を無効

    Cookie の属性（HttpOnly・Secure など）の意味は Cookieの仕組み を参照してください。

    6.RefererによりセッションIDが漏洩する条件

    Referer（リンクをたどったとき、ブラウザが「どのページから来たか」を伝えるリクエストヘッダ）により、セッションID が外部サイトに漏れる条件があります。

    6.1 漏洩が起きる条件

    条件説明
    ① URL にセッションID が含まれる?sessionId=abc123 など
    ② ページ内に外部リンクがある<a href="https://evil.com"> など
    ③ ユーザーが外部リンクをクリックReferer に元の URL が送られる
    ④ Referer が送信されるReferrer-Policy で制限されていない

    6.2 攻撃の流れ

    1. ユーザーが https://bank.com/page?sessionId=abc123 を閲覧
2. ページ内の https://evil.com へのリンクをクリック
3. ブラウザが Referer: https://bank.com/page?sessionId=abc123 を送信
4. evil.com がセッションIDを取得
5. 攻撃者が abc123 でなりすまし

    6.3 対策

    対策説明
    Cookie 方式URL にセッションID を載せない（根本対策）
    Referrer-PolicyReferer の送信を制限する
    HTTPS 統一HTTP と HTTPS が混ざった状態（混在コンテンツ）を避ける
     
    Referrer-Policy: strict-origin-when-cross-origin

    Referrer-Policy の値の意味は セキュリティヘッダ：Referrer-Policy（Web脆弱性対策解説）で説明しています。

    7.セッションIDの固定化

    セッション固定化（Session Fixation） は、攻撃者が あらかじめ用意したセッションID を被害者に使わせ、被害者がログインしたあとも同じ ID でアクセスする攻撃です。

    7.1 攻撃の流れ

    1. 攻撃者が example.com にアクセス
   → サーバーが sessionId=EVIL123 を発行

2. 攻撃者が被害者に EVIL123 付き URL を送る
   https://example.com/?PHPSESSID=EVIL123

3. 被害者が URL を開き、ログイン
   → サーバーは EVIL123 にログイン情報を紐付け（ID を変更しない場合）

4. 攻撃者が sessionId=EVIL123 でアクセス
   → 被害者としてログイン状態になる

    7.2 成立条件

    • ログイン 前後でセッションID が同じ
    • 攻撃者が ログイン前の ID を知っている

    8.セッションアダプション

    セッションアダプション（adoption＝受け入れ）とは、ログイン時にサーバーが 新しいセッションID を発行せず、ログイン前から存在するセッション（匿名セッション）を そのまま引き継ぐ 実装パターンです。

    8.1 脆弱な実装

    危険な例：ログイン後も ID が変わらない 
    // ログイン前から session_start() 済み
session_start();  // 匿名セッション ID = abc123

// ログイン成功後も ID を変更しない
$_SESSION['user_id'] = $userId;
// sessionId は abc123 のまま

    8.2 セッション固定化との関係

    セッションアダプション（サーバーの脆弱な実装）
        ↓
ログイン前の ID がログイン後も有効
        ↓
セッション固定化攻撃が成立しやすい
    概念視点
    セッション固定化攻撃者の手法
    セッションアダプションサーバー側の脆弱な挙動

    8.3 安全な実装

    安全な例：ログイン成功時に ID を再生成 
    session_regenerate_id(true);  // 古い ID は無効化
$_SESSION['user_id'] = $userId;

    9.対策の全体像

    セッション管理の不備に対する対策を、優先度順に整理します。続く 10〜12 章で 1 つずつ説明します。

    1. 認証後にセッションID を変更する（最重要。10 章）
    2. ID を変更できない場合は トークンで対策する（11 章）
    3. ログイン前 の段階から固定化を防ぐ（URL に載せない・匿名セッションを作らない。12 章）

    10.認証後にセッションIDを変更する

    ログイン成功時にセッションID を再生成 するのが、セッション固定化対策の 最も重要な手法 です。

    10.1 なぜ必要か

    ログイン前: sessionId = EVIL123（攻撃者も知っている可能性）
ログイン後: sessionId = NEW456（攻撃者は知らない）
→ 固定化攻撃が無効化される

    10.2 実装例

    PHP 
    session_start();

if (authenticate($username, $password)) {
    session_regenerate_id(true);  // true = 古い ID を削除
    $_SESSION['user_id'] = $userId;
    header('Location: /dashboard');
}
    Express.js 
    req.session.regenerate((err) => {
  if (err) return next(err);
  req.session.userId = user.id;
  res.redirect('/dashboard');
});

    10.3 再生成すべきタイミング

    タイミング理由
    ログイン成功時セッション固定化対策（必須）
    権限昇格時一般ユーザー → 管理者など
    パスワード変更後既存セッションの無効化

    11.できない場合はトークンにより対策

    レガシーシステム（古い仕組みのまま動いているシステム）などで セッションID を変更できない 場合は、認証トークン（ログイン成功時にだけ作る別の乱数）を別途管理して対策します。

    11.1 仕組み

    1. ログイン前: セッションID = abc123（変更不可）
2. ログイン成功: サーバーが「認証トークン」をセッションに保存
   $_SESSION['auth_token'] = random_token()
3. 重要操作時: セッションID だけでなく auth_token も検証
4. ログイン前の abc123 には auth_token がない
   → 攻撃者は ID だけでは操作不可

    11.2 実装イメージ

    // ログイン成功時
$_SESSION['authenticated'] = true;
$_SESSION['auth_token'] = bin2hex(random_bytes(32));
$_SESSION['login_time'] = time();

// 重要ページで検証
function requireAuth() {
    if (empty($_SESSION['authenticated']) || empty($_SESSION['auth_token'])) {
        redirect('/login');
    }
}

    同じ「トークンを足して守る」考え方は、HTTP と HTTPS が混在するサイトの Cookie 対策でも使います（クッキー出力にまつわる脆弱性：トークンを用いた対策）。

    11.3 注意点

    注意説明
    第二の防御線理想はセッションID の再生成。トークンは代わりの手段
    トークンも保護HttpOnly Cookie、XSS 対策が必要
    複雑性実装・保守のコストが増える

    12.ログイン前のセッションID固定化攻撃の対策

    ログイン 前 の段階から、セッション固定化を防ぐ対策です。

    12.1 対策一覧

    対策説明
    ログイン後に ID 再生成最も重要（10 章）
    URL にセッションID を載せない攻撃者が ID を仕込みにくくする
    ログイン前セッションの制限匿名セッションでは機密操作をさせない
    saveUninitialized = false不要な匿名セッションを作らない

    12.2 saveUninitialized（Express.js）

    app.use(session({
  secret: 'secret-key',
  saveUninitialized: false,  // セッションにデータがなければ Cookie を発行しない
  resave: false,
  cookie: { httpOnly: true, secure: true, sameSite: 'strict' }
}));

    効果：訪問者ごとに、不用意にセッションID が発行されなくなります。

    12.3 ログインフローの安全な設計

    1. ログインページを表示する（匿名。機密操作は不可）
    2. 認証に成功する
    3. session_regenerate_id() で新しい ID を発行する（必須）
    4. ログイン状態を新しいセッションに保存する
    5. 以降の操作は新しい ID でのみ有効

    12.4 Cookie 属性の設定（再掲）

    Set-Cookie: sessionId=...; HttpOnly; Secure; SameSite=Strict
    属性効果
    HttpOnlyXSS による Cookie 窃取を防ぐ（XSS：クッキーに HttpOnly 属性を付与）
    SecureHTTPS のときだけ送信する
    SameSiteCSRF・クロスサイト送信を制限する（CSRF）

    属性ごとの細かな注意点は クッキー出力にまつわる脆弱性 と Cookieの仕組み で扱います。

    13.まとめ

    トピック要点
    セッションハイジャックセッションID を奪い、なりすます
    推測・盗み出し・強制ID を入手する方法の 3 分類
    危険な ID 生成連番・タイムスタンプ・短い乱数は禁止
    URL 埋め込みReferer・ログ・履歴から漏洩する。Cookie 方式を使う
    Referer 漏洩URL に ID がある ＋ 外部リンクのクリック
    セッション固定化攻撃者が用意した ID をログイン後も使う
    セッションアダプションログイン時に ID を変更しない脆弱な実装
    認証後の ID 変更session_regenerate_id() など（最重要）
    トークン対策ID を変更できないときの第二の防御線
    ログイン前対策URL に載せない、saveUninitialized など

    13.1 セッション管理チェックリスト

    □ セッションIDは random_bytes 等で128bit以上のランダム生成
□ セッションIDを URL に含めない（Cookie のみ）
□ Cookie に HttpOnly, Secure, SameSite を設定
□ ログイン成功時に session_regenerate_id() で ID 再生成
□ セッションに有効期限を設定
□ ログアウト時にサーバー側セッションを削除
□ HTTPS を必須にする
□ XSS 対策（HttpOnly だけでは不十分な操作がある）

    次に読むもの

    徳丸本の次の章では、HTTP ヘッダインジェクションなど、ヘッダや Cookie の出力にまつわる脆弱性を扱います。ヘッダインジェクションは リダイレクトとHTTPヘッダインジェクション、Cookie の出力は クッキー出力にまつわる脆弱性 へ進んでください。

    14.理解度チェック

    Q1. セッションID を入手する 3 つの方法と、それぞれの例を答えてください。

    推測（連番などの規則性ある ID を総当たり）、盗み出し（XSS・盗聴・Referer 漏洩・物理アクセス）、強制（セッション固定化で被害者に特定の ID を使わせる）の 3 つです。

    Q2. md5(time()) でセッションID を作ってはいけないのはなぜですか？

    元になる値が現在時刻なので、攻撃者は現在時刻付近の値を MD5 にして試せば当てられるからです。ハッシュにしても入力の候補が少なければ推測できます。random_bytes() などの CSPRNG で 128bit 以上の乱数を使います。

    Q3. URL にセッションID を埋め込むと、どんな経路で漏れますか？

    外部リンクをクリックしたときの Referer、ブックマーク、サーバーのアクセスログ、ブラウザ履歴、URL の 共有 です。根本対策は Cookie だけで ID を運ぶこと（session.use_only_cookies = 1、session.use_trans_sid = 0）です。

    Q4. セッション固定化攻撃が成立する 2 つの条件は何ですか？

    ログインの 前後でセッションID が同じ であることと、攻撃者が ログイン前の ID を知っている ことです。

    Q5. セッション固定化とセッションアダプションの違いは何ですか？

    セッション固定化は 攻撃者の手法、セッションアダプションはログイン時に ID を作り直さずに匿名セッションを引き継ぐ サーバー側の脆弱な挙動 です。アダプションがあると固定化攻撃が成立しやすくなります。

    Q6. セッションID を再生成すべきタイミングを 3 つ挙げてください。

    ログイン成功時（必須）、権限昇格時、パスワード変更後 です。PHP なら session_regenerate_id(true)、Express なら req.session.regenerate() を使います。

    Q7. セッションID を変更できないシステムでは、どう対策しますか？

    ログイン成功時に 認証トークン（ランダム値）をセッションに保存し、重要な操作ではセッションID に加えてトークンの有無も検証します。ログイン前の ID にはトークンがないので、攻撃者は ID だけでは操作できません。ただし第二の防御線であり、理想は ID の再生成です。
