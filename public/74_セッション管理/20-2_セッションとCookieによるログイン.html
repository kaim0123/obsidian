    20 セッション

    セッションとCookieによるログイン

    Cookie に入っているのは「abc123」のような番号だけ。それなのに、なぜサーバーは「あなた」だと分かるのでしょうか。このページでは、セッションとクッキーの違い、番号でユーザーを特定する仕組み、Express でのログイン・ログアウトの書き方、そしてロードバランサー配下などインフラから見たセッション管理と、安全に使うための設定を解説します。

    もとにしたノート：20_セッション/02_セッションとクッキーとは、20_セッション/03_セッションとは_Cookieの番号であなたが分かる仕組み（つるチャンネル）、20_セッション/04_クッキーとログイン、20_セッション/05_クッキーとセッション管理（旧サーバー教材）

    ひとことで言うと

    状態はサーバー、番号はブラウザ。番号（セッション ID）を運ぶのが Cookie、その番号に対応する状態を管理するのが セッション です。2 つは別物なので、Cookie が残っていることと、ログイン中であることは別 です。

    1.セッションとクッキーとは

    セッションとクッキーは、Web アプリケーションでユーザーの状態（ログインしているか、カートに何が入っているか など）を管理する仕組みです。

    • クッキー（Cookie）：ブラウザに保存される小さなデータです。
    • セッション（Session）：サーバー側で管理される一時的なデータです。

    1.1 日常生活での例え

    クッキー

    会員カード。お客さん（ブラウザ）が持ち歩き、お店に来るたびに見せます。

    セッション

    レストランのテーブル番号。何を注文したかはお店（サーバー）が番号ごとに管理しています。

    2.Cookie の番号であなたが分かる仕組み

    HTTP は リクエストごとに独立 していて、ログインした状態を次のリクエストへ引き継ぎません（ステートレス。HTTP とセッション管理 参照）。そこで サーバー側に状態を保存し、それを識別する番号だけをブラウザに持たせます。複数のリクエストにまたがって状態を管理するこの仕組みが セッション です。

    2.1 ログインからマイページ表示までの流れ

    1. ログイン：サーバーがパスワードを確認し、「ユーザー 42」だと分かります。
    2. セッション表に書き込む：サーバーは セッション表 に「abc123 → ユーザー 42・ログイン済み」と 1 行書き込みます。
    3. 番号だけを返す：この 番号だけ を Set-Cookie ヘッダで返し、ブラウザは Cookie として保存します。ブラウザにあるのは abc123 という番号だけです。
    4. マイページを開く：Cookie が自動で付きます。サーバーは届いた abc123 で表を引き、「ユーザー 42・ログイン済み」を見つけて、ここで初めてログイン済みのユーザー 42 だと判断し、マイページを返せます。

    2.2 Cookie とセッションは別のもの

    • 番号を運ぶのが Cookie、その番号に対応する状態を管理するのがセッション です。
    • これは サーバーサイドセッション（状態をサーバーに置く方式）の一例で、表の置き場所は実装によって異なります（→ 8 章）。
    • ログアウトや期限切れでサーバーがセッションを無効にすると、同じ Cookie が残っていても対応するセッションがない ため、ログイン済みとは判断されません。

    覚え方

    HTTP はステートレスなので、状態はサーバーに保存し、識別番号をブラウザに持たせる。状態はサーバー、番号はブラウザ。この番号がログインの鍵です。鍵なので、漏れるとなりすましに使われます（→ 9 章）。

    3.クッキー（Cookie）の基本

    クッキーは、Web サーバーが HTTP レスポンスで Set-Cookie ヘッダを返すことで、ブラウザに小さなデータ（key-value 形式＝「名前＝値」の組）を保存させる仕組みです。次回以降のリクエスト時、ブラウザは自動で Cookie を送信します。Cookie 自体の仕組みと属性の詳細は Cookie の仕組み で解説しています。

    3.1 クッキーの特徴と用途

    特徴

    • ブラウザに保存される
    • サーバーに自動的に送信される
    • 有効期限を設定できる
    • ドメインごとに管理される

    用途

    1. ログイン状態の保持（セッション管理・認証情報の保持）
    2. ユーザー設定の保存
    3. ショッピングカートの管理
    4. トラッキング（広告など）

    3.2 サーバー側での設定・読み取り・削除（Express）

    const express = require('express');
const app = express();

// クッキーを設定
app.get('/set-cookie', (req, res) => {
  res.cookie('username', 'yamada', {
    maxAge: 24 * 60 * 60 * 1000, // 24時間
    httpOnly: true, // JavaScriptからアクセス不可（セキュリティ）
    secure: true, // HTTPSのみ
    sameSite: 'strict' // CSRF攻撃対策
  });
  res.send('クッキーを設定しました');
});

// クッキーを読み取る
app.get('/get-cookie', (req, res) => {
  const username = req.cookies.username;
  res.json({ username });
});

// クッキーを削除
app.get('/delete-cookie', (req, res) => {
  res.clearCookie('username');
  res.send('クッキーを削除しました');
});

    req.cookies を使うには、届いた Cookie ヘッダを読み解く cookie-parser などのミドルウェアを先に組み込んでおきます。

    3.3 クライアント側での操作（JavaScript）

    // クッキーを設定（JavaScript）
document.cookie = 'username=yamada; max-age=86400; path=/';

// クッキーを読み取る
function getCookie(name) {
  const value = `; ${document.cookie}`;
  const parts = value.split(`; ${name}=`);
  if (parts.length === 2) {
    return parts.pop().split(';').shift();
  }
}

const username = getCookie('username');
console.log(username);

    HttpOnly 属性が付いた Cookie は、この document.cookie からは読み書きできません。セッション ID はこちら側で触れないようにするのが基本です。

    4.セッション（Session）の基本

    セッション は、クライアントとサーバーの間の一時的な状態管理です。サーバーは セッション ID を発行して Cookie に保存させ、ユーザー ID や認証状態などのセッション情報はサーバー側で管理します。クライアントがセッション ID 付きの Cookie を送ると、サーバーはそれを元に状態を復元します。

    4.1 セッションの特徴

    • サーバー側で管理される
    • セッション ID で識別される
    • セキュリティが高い（中身がブラウザに渡らない）
    • サーバーのメモリやデータベースに保存される

    4.2 セッションの使用例（express-session）

    express-session は、Express でセッションを扱うためのミドルウェア（リクエスト処理の途中に差し込む部品）です。セッション ID の発行と Cookie への保存、届いた ID からの req.session の復元を自動で行います。

    const express = require('express');
const session = require('express-session');
const app = express();

// セッションの設定
app.use(session({
  secret: 'your-secret-key',
  resave: false,
  saveUninitialized: false,
  cookie: {
    secure: true, // HTTPSのみ
    httpOnly: true,
    maxAge: 24 * 60 * 60 * 1000 // 24時間
  }
}));

// ログイン処理
app.post('/login', (req, res) => {
  const { username, password } = req.body;

  // 認証処理（簡略化）
  if (username === 'yamada' && password === 'password123') {
    // セッションにユーザー情報を保存
    req.session.user = {
      id: 1,
      username: 'yamada',
      email: 'yamada@example.com'
    };
    res.json({ message: 'ログイン成功' });
  } else {
    res.status(401).json({ error: '認証に失敗しました' });
  }
});

// セッションからユーザー情報を取得
app.get('/profile', (req, res) => {
  if (req.session.user) {
    res.json({ user: req.session.user });
  } else {
    res.status(401).json({ error: 'ログインが必要です' });
  }
});

// ログアウト処理
app.post('/logout', (req, res) => {
  req.session.destroy((err) => {
    if (err) {
      return res.status(500).json({ error: 'ログアウトに失敗しました' });
    }
    res.json({ message: 'ログアウトしました' });
  });
});

    ログアウトで req.session.destroy() を呼ぶと、サーバー側のセッションが消えます。2.2 のとおり、ブラウザに Cookie が残っていてもログイン済みとは扱われなくなります。

    この例は「簡略化」です

    パスワードをコードに直接書いて比べるのは説明用です。実際には保存したハッシュと照合し（パスワードの安全な保存）、secret も推測されにくい値を環境変数などから読み込みます。

    5.クッキーとセッションの違い

    項目クッキーセッション
    保存場所ブラウザサーバー
    サイズ制限約 4KB制限なし
    セキュリティ低い（JavaScript からアクセス可能）高い（サーバー側のみ）
    有効期限設定可能設定可能
    用途ユーザー設定、トラッキングログイン状態、機密情報

    「JavaScript からアクセス可能」は HttpOnly を付ければ防げますが、Cookie の値はそもそもユーザー自身が見たり書き換えたりできる場所にあります。そのため 機密情報や信頼すべき値はセッション（サーバー側）に置き、Cookie には番号だけを入れる のが基本です。

    6.実践例：セッションを使ったログイン機能

    API として作る場合の、最小のログイン・認証が必要なエンドポイント・ログアウトの組み合わせです。セッションにはユーザー ID だけを入れ、必要になったらその ID でユーザー情報を取り出しています。

    const express = require('express');
const session = require('express-session');
const app = express();

app.use(express.json());
app.use(session({
  secret: 'secret-key',
  resave: false,
  saveUninitialized: false,
  cookie: { secure: true, httpOnly: true, maxAge: 24 * 60 * 60 * 1000 }
}));

// ログイン
app.post('/api/login', (req, res) => {
  const { username, password } = req.body;

  // 認証処理
  if (authenticate(username, password)) {
    req.session.userId = getUserId(username);
    res.json({ message: 'ログイン成功' });
  } else {
    res.status(401).json({ error: '認証に失敗しました' });
  }
});

// 認証が必要なエンドポイント
app.get('/api/profile', (req, res) => {
  if (!req.session.userId) {
    return res.status(401).json({ error: 'ログインが必要です' });
  }

  const user = getUserById(req.session.userId);
  res.json(user);
});

// ログアウト
app.post('/api/logout', (req, res) => {
  req.session.destroy();
  res.json({ message: 'ログアウトしました' });
});

    本番では、ログインに成功したときにセッション ID を新しく作り直す処理（req.session.regenerate()）も加えます。理由は セッション管理の不備（セッション固定攻撃）で解説します。

    7.ログイン処理の全体像とクッキー

    7.1 ログイン処理の流れ

    1. ユーザーが ID／パスワードを送信する
    2. サーバー側で認証する（DB 照合、ハッシュ化パスワードの検証）
    3. 認証成功時に「セッション ID」や「JWT」などを発行する
    4. セッション ID やトークンをクッキーやローカルストレージ（ブラウザに用意された保存領域）に保存する
    5. 以降のリクエストでクッキーを使い、認証状態を維持する

    ログイン画面そのものへの攻撃（パスワードの総当たりなど）は 73 の ログイン機能への攻撃と対策 を参照してください。

    7.2 クッキーとログインの関係

    • クッキーは「セッション ID」や「認証トークン」を保存するために使われます。
    • サーバーはクッキーの値でユーザーを識別し、認証済みかどうかを判定します。

    セッション管理の主な方式は次の 2 つです。JWT（JSON Web Token） は、ユーザー情報などを入れて署名した文字列のトークンです。

    サーバーサイドセッション

    セッション ID をクッキーに保存し、状態はサーバーで管理 します。このページで扱っている方式です。

    JWT 認証

    トークンをクッキーやヘッダーに保存します。状態はトークン内に埋め込み、サーバーに表を持たない（サーバーレスな）認証です。

    2 つの比較は セッション方式とトークン方式、JWT の中身は JWT の構造と検証、クッキーとローカルストレージのどちらに置くかは トークンの保存場所 で解説します。

    7.3 実装例

    サーバーサイド（Node.js／Express）：ログイン時に Cookie を発行 
    // ログイン時
res.cookie('session_id', sessionId, { httpOnly: true, secure: true, sameSite: 'lax' });
    クライアントサイド：fetch でクッキーを送信 
    fetch('/api/user', { credentials: 'include' });

    credentials: 'include' は「このリクエストに Cookie を付けて送る」という指定です。フロントエンドと API のオリジンが違う構成では、サーバー側の CORS 設定とあわせて必要になります（CORS エラーの対処法と Cookie）。

    8.サーバー・インフラから見たセッション管理

    8.1 セッションストア

    サーバー側でセッション情報を保存しておく場所を セッションストア と呼びます。2.1 の「セッション表」の置き場所です。

    置き場所特徴
    メモリサーバーのプロセス内に持つ。手軽だが、再起動で消え、複数台では共有できない
    DBデータベースに保存する。複数台で共有できる
    Redis 等高速なキー・バリュー型のデータストアに保存する。複数台で共有でき、期限切れの自動削除もしやすい

    8.2 Web サーバー・インフラとの関係

    • Nginx／Apache などの Web サーバーは リバースプロキシ（利用者とアプリの間に立ってリクエストを中継するサーバー）として Cookie を中継します。
    • HTTPS 終端（暗号化をここでほどく役割）や ロードバランサー（リクエストを複数のサーバーに振り分ける装置）の配下でセッションを維持するには、Sticky Session（同じ利用者を同じサーバーに送り続ける）か、分散セッションストア（全サーバーが共通のストアを見る）を使います。
    • サーバーレス環境やマイクロサービス（機能ごとに小さなサービスに分けた構成）では、セッション管理に工夫が必要です。

    8.3 実装例：express-session ミドルウェア

    // express-sessionミドルウェア利用例
const session = require('express-session');
app.use(session({
  secret: 'your-secret',
  resave: false,
  saveUninitialized: false,
  cookie: { httpOnly: true, secure: true, sameSite: 'lax' }
}));

    express-session は何も指定しないとメモリにセッションを保存します。複数台で動かすときは、store オプションに Redis などのストアを指定して共有します。

    9.セキュリティとベストプラクティス

    セッション ID は「ログインの鍵」なので、盗まれない・使い回されないように設定します。各属性の詳しい動きは Cookie の仕組み、属性の一覧表は HTTP とセッション管理：クッキーの属性 を参照してください。

    設定・対策目的
    HttpOnly 属性JavaScript からアクセス不可にする（XSS 対策。XSS の基本）
    Secure 属性HTTPS 通信時のみ送信する
    SameSite 属性同一サイトからのみ送信するなどして CSRF を防ぐ（Strict／Lax／None。CSRF）
    有効期限（Expires／Max-Age）適切な有効期限を設定する
    ドメイン／パスの制限Cookie が送られる範囲を必要最小限にする
    セッション固定攻撃・ハイジャック対策ログイン時の ID 再生成、推測されにくい ID、タイムアウトなど（セッション管理の不備）
    サーバー側のセッションストアメモリ・DB・Redis 等で状態をサーバーに置き、Cookie には番号だけを入れる
    安全な例：セッション ID の Cookie に付ける設定 
    // 1. HttpOnly：JavaScriptからアクセス不可
// 2. Secure：HTTPSのみ
// 3. SameSite：同一サイトからのみ送信（CSRF対策）
res.cookie('sessionId', sessionId, {
  httpOnly: true,
  secure: true,
  sameSite: 'strict'
});

// 4. セッションの有効期限
app.use(session({
  cookie: {
    maxAge: 24 * 60 * 60 * 1000 // 24時間
  }
}));

    10.まとめ

    • クッキー は、ブラウザに保存される小さなデータ。セッション は、サーバー側で管理される一時的なデータ。
    • HTTP はステートレスなので、状態はサーバーに保存し、識別番号（セッション ID）をブラウザに持たせる。番号を運ぶのが Cookie、その番号に対応する状態を管理するのがセッション。
    • Cookie があることとログイン中であることは別。ログアウトや期限切れでサーバー側のセッションが消えれば、同じ Cookie が残っていてもログイン済みとは判断されない。
    • ログインは「ID／パスワード送信 → 認証 → セッション ID や JWT を発行 → クッキー等に保存 → 以降のリクエストで認証状態を維持」の流れ。方式はサーバーサイドセッションと JWT 認証の 2 つが主。
    • セッションストアはメモリ・DB・Redis 等。ロードバランサー配下では Sticky Session か分散セッションストアでセッションを維持する。
    • HttpOnly・Secure・SameSite、適切な有効期限、ドメイン／パスの制限、セッション固定・ハイジャック対策を設定する。

    11.理解度チェック

    Q1. Cookie には「abc123」という番号しか入っていないのに、サーバーがユーザーを特定できるのはなぜですか？

    ログイン時にサーバーがセッション表へ「abc123 → ユーザー 42・ログイン済み」と書き込んでおき、以後届いた番号でその表を引いているからです。状態はサーバー側にあり、ブラウザは番号だけを持っています。

    Q2. ログアウト後、ブラウザに同じ Cookie が残っていたらログイン中と判断されますか？

    されません。ログアウト（req.session.destroy() など）でサーバー側のセッションが無効になると、Cookie の番号に対応するセッションがないためです。Cookie があることとログイン中であることは別です。

    Q3. クッキーとセッションの違いを、保存場所と向いている用途で説明してください。

    クッキーはブラウザに保存され（約 4KB まで）、ユーザー設定やトラッキングに向きます。セッションはサーバーに保存され、ログイン状態や機密情報の管理に向きます。

    Q4. サーバーサイドセッションと JWT 認証では、状態をどこに持ちますか？

    サーバーサイドセッションは状態をサーバーで管理し、Cookie にはセッション ID だけを入れます。JWT 認証は状態をトークンの中に埋め込み、トークンをクッキーやヘッダーで送ります。

    Q5. アプリサーバーを 2 台に増やしたら、ログインしたのに次のリクエストで未ログイン扱いになることがありました。なぜで、どう直しますか？

    セッションを各サーバーのメモリに保存していると、ロードバランサーが別のサーバーに振り分けたとき、そのサーバーにはセッションがないからです。全サーバーが共通の Redis や DB を見る分散セッションストアにするか、同じ利用者を同じサーバーに送り続ける Sticky Session を使います。

    Q6. フロントエンドから fetch で API を呼ぶとき、Cookie を送るにはどう指定しますか？

    fetch('/api/user', { credentials: 'include' }) のように credentials: 'include' を指定します。オリジンが違う場合はサーバー側の CORS 設定も必要です。

    Q7. セッション ID の Cookie に HttpOnly・Secure・SameSite を付ける目的をそれぞれ答えてください。

    HttpOnly は JavaScript から読めなくして XSS による盗難を防ぎます。Secure は HTTPS のときだけ送って盗聴を防ぎます。SameSite は別サイト発のリクエストで Cookie を送らないようにして CSRF を防ぎます。
