    40 攻撃と対策

    クッキー出力にまつわる脆弱性

    Cookie は「何を入れるか」と「どんな属性で出すか」を間違えると、それだけで盗聴・改ざん・XSS による窃取の入口になります。徳丸本 11 章に沿って、Cookie とセッション変数の使い分け、Secure 属性の付け方、HTTP と HTTPS が混在するときのトークン対策、Domain・Path・Expires・HttpOnly の注意点を整理します。

    もとにしたノート：40_攻撃と対策/02_クッキー出力にまつわる脆弱性（徳丸本11章）

    このページで分かること

    • Cookie とセッション変数の違い（9 つの観点）と、Cookie に入れてはいけない情報
    • セキュア属性の不備で起きること、本番環境の最低ライン
    • Secure 属性の付け方（HTTP ヘッダ・PHP・Express.js）
    • HTTP と HTTPS が混在するときのトークン対策と、それが安全な理由
    • Domain・Path・Expires（Max-Age）・HttpOnly 属性の注意点

    ひとことで言うと

    Cookie にはセッションID だけを入れ、中身はサーバー側のセッション変数に置きます。そのセッションID の Cookie には Secure・HttpOnly・SameSite を必ず付け、Domain は広げず、有効期限は短めにします。どうしても Secure を付けられない混在サイトでは、Secure 付きの トークン Cookie を足して二重に確かめます。

    Cookie の属性そのものの意味は Cookieの仕組み、セッションID の奪われ方（推測・盗み出し・固定化）は セッション管理の不備 で扱いました。Cookie の出力に関わるもう 1 つの脆弱性である、Set-Cookie などのヘッダに改行を混ぜ込まれる攻撃は HTTPヘッダ・インジェクション（Web脆弱性対策解説）を参照してください。

    1.クッキーに保存すべきでない情報

    機密情報や重要な状態は セッション変数（サーバー側に保存する、利用者ごとのデータ）に保存し、Cookie には セッションID など最小限 だけを載せるのが原則です。判断のために、Cookie とセッション変数の違いを比べます。

    1.1 クッキーとセッション変数の比較

    比較項目クッキー（Cookie）セッション変数（Session）
    使いやすさブラウザが自動送信するため、クライアント側の実装は簡単。JavaScript からも読み書きできる（HttpOnly を除く）サーバー側の API だけで完結する。クライアントはセッションID だけ持てばよい
    配列やオブジェクトの格納文字列のみ。配列・オブジェクトは JSON などに シリアライズ（文字列に変換）して保存する必要があるPHP の $_SESSION などに、配列・オブジェクトをそのまま 格納できる
    サイズの制限1 件あたり約 4KB、ドメインあたり約 20 件 程度（ブラウザ依存）サーバーのメモリ・DB 次第で 実質制限なし（ただし過大なデータは非推奨）
    利用者による格納情報の直接参照可能。開発者ツールや document.cookie（HttpOnly なし）で中身を確認できる不可。データはサーバー側にだけあり、利用者は中身を直接見られない
    脆弱性などで漏洩した際の情報漏洩のしやすさ高い。XSS・盗聴・Referer などで Cookie 全体が漏れると、保存していた 値そのもの も漏れる低い（セッションID だけが漏れた場合）。中身はサーバー側に残る（ハイジャックのリスクは別問題）
    利用者によるデータ改変容易。開発者ツールや JS で 値を書き換え られる（HttpOnly でも改変はできる）困難。利用者はサーバー上のセッションデータに 直接触れない
    第三者によるデータ改変可能。通信傍受（HTTP）や XSS により、送受信する Cookie の値を改ざんされるおそれがある困難。第三者は通常、サーバー上のデータを 直接改変できない（セッションID の窃取は別）
    情報の寿命の制御Expires / Max-Age で 細かく設定できる。ブラウザを閉じるまで（セッション Cookie）も選べるサーバー側で タイムアウト・ガベージコレクション（古いデータの自動削除）を設定する。session.gc_maxlifetime など
    異なるサーバーとの情報共有同じ ドメイン（および Path の設定）内のサーバー間で 自動的に共有できるサーバーごとに独立。共有するには DB・Redis などの 共通セッションストア が必要

    1.2 比較の要点

    機密性・改ざん耐性が必要

    → セッション変数（サーバー側）

    クライアントとの利便性

    → クッキー（機密でない設定値など）

    セッション管理

    → クッキーには セッションID だけ、本体はサーバー側

    2.クッキーのセキュア属性不備

    セキュア属性不備 とは、Cookie に Secure・HttpOnly・SameSite などの安全のための属性が付いていない、または不適切な状態です。セッションID など機密性の高い Cookie では 重大な脆弱性 になります。

    2.1 よくある不備

    不備リスク
    Secure なしHTTP 通信でも Cookie が送られ、盗聴 される
    HttpOnly なしXSS で document.cookie から 窃取 される（XSS によるクッキー値の盗み出し）
    SameSite なしクロスサイトのリクエストにも Cookie が送られ、CSRF のリスク（CSRF）
    Expires が長すぎる盗まれた Cookie が 長期間 有効になる
    Domain が広すぎるサブドメイン全体に Cookie が 共有 され、漏洩しやすい

    2.2 攻撃イメージ（Secure 属性なし）

    1. ユーザーが http://example.com（HTTP）にアクセス
2. セッション Cookie が平文で送信される
3. 同一 Wi-Fi 上の攻撃者が通信を傍受
4. セッションID を入手 → なりすまし

    2.3 本番環境の最低ライン

    セッションID 用 Cookie の項目設定
    Secure必須（HTTPS のときだけ送信）
    HttpOnly必須（JS から読めない）
    SameSiteStrict または Lax
    有効期限適切な長さにする

    3.セッションIDのクッキーにSecure属性を付ける方法

    Secure 属性 を付けると、Cookie は HTTPS 接続のときだけ ブラウザから送信されます。

    3.1 HTTP レスポンスヘッダ

    Set-Cookie: sessionId=abc123; Secure; HttpOnly; SameSite=Strict; Path=/

    3.2 PHP

    安全な例：session_start の前に属性を設定する 
    // session_set_cookie_params（session_start 前に設定）
session_set_cookie_params([
    'lifetime' => 0,
    'path'     => '/',
    'secure'   => true,    // Secure 属性
    'httponly' => true,
    'samesite' => 'Strict',
]);
session_start();

// または setcookie
setcookie('sessionId', $sessionId, [
    'secure'   => true,
    'httponly' => true,
    'samesite' => 'Strict',
    'path'     => '/',
]);

    3.3 Express.js（Node.js）

    res.cookie('sessionId', sessionId, {
  secure: true,      // HTTPS のみ（本番では true）
  httpOnly: true,
  sameSite: 'strict',
  maxAge: 3600000,
  path: '/',
});

    3.4 注意点

    注意説明
    HTTPS 必須Secure を付けても、サイト全体が HTTPS でないとログインできない場合がある
    開発環境localhost では secure: false にすることがある（本番では必ず true）
    HTTP と HTTPS の混在HTTP のページには Secure Cookie が送られない → 4 章のトークン対策

    4.トークンを用いた対策

    HTTP と HTTPS が混在するレガシー構成などで、セッション Cookie に Secure 属性を付けられない 場合は、追加のトークン（推測できない乱数）で安全性を補います。

    4.1 なぜ必要か

    問題

    サイトの一部が HTTP のまま。セッション Cookie に Secure を付けると、HTTP のページでセッションが使えない。Secure なしだと、HTTP で Cookie が盗まれる。

    対策

    セッション Cookie（Secure なし）に加え、HTTPS 専用の トークン Cookie（Secure あり）を別に発行し、サーバーで両方の一致を検証する。

    4.2 仕組み

    1. ログイン成功
   サーバー: セッションに auth_token = ランダム値 を保存
   Cookie①: sessionId=abc123（Secure なし・HttpOnly）
   Cookie②: auth_token=xyz789（Secure あり・HttpOnly）← HTTPS のみ

2. HTTP ページへのアクセス
   → sessionId のみ送信（auth_token は Secure のため送られない）
   → サーバー: auth_token が無い → 機密操作は不可

3. HTTPS ページへのアクセス
   → sessionId + auth_token 両方送信
   → サーバー: セッション内の token と Cookie の token が一致 → OK

    4.3 実装例（概念）

    // ログイン成功時
$token = bin2hex(random_bytes(32));
$_SESSION['auth_token'] = $token;

setcookie('sessionId', session_id(), ['httponly' => true, 'path' => '/']);
setcookie('auth_token', $token, [
    'secure'   => true,
    'httponly' => true,
    'samesite' => 'Strict',
    'path'     => '/',
]);

// 機密操作前の検証
function requireSecureAuth(): void {
    $sessionToken = $_SESSION['auth_token'] ?? '';
    $cookieToken  = $_COOKIE['auth_token'] ?? '';
    if ($sessionToken === '' || !hash_equals($sessionToken, $cookieToken)) {
        die('認証が必要です（HTTPS でアクセスしてください）');
    }
}

    hash_equals() は、処理時間の差から値を推測されないように比較する関数です。セッションID を変更できない場合に認証トークンを足す、という同じ発想は セッション管理の不備：できない場合はトークンにより対策 にも出てきます。

    5.トークンにより安全性が確保できる理由

    トークン方式が有効な理由を、攻撃者の視点から整理します。

    5.1 攻撃者の視点

    入手できるもの条件
    sessionId のみHTTP 通信を傍受する
    sessionId ＋ auth_tokenHTTPS 通信を傍受する（はるかに困難）

    5.2 安全性が確保できる理由

    1. auth_token は Secure 属性付き。HTTP 通信には絶対に含まれないので、HTTP の傍受だけではトークンを入手できない
    2. auth_token はサーバー側のセッションにも保存。一致を検証しないと機密操作ができない
    3. 攻撃者が sessionId だけ 盗んでも、機密ページ・操作は auth_token の不一致で拒否される

    5.3 限界と注意

    限界説明
    完全な代替ではないサイト全体を HTTPS 化するのが理想
    実装の複雑さトークンの発行・検証・更新のロジックが必要
    XSSHttpOnly でも、セッション固定など別のリスクは残る → XSS 対策も必要

    結論

    トークンは HTTP と HTTPS が混在する環境での第二の防御線 です。可能なら 全ページ HTTPS ＋ Secure Cookie が最善です。

    6.セキュア属性以外の属性値に関する注意

    Secure 以外の属性も、Cookie の 送信範囲・寿命・アクセス制御 に影響します。

    6.1 Domain 属性

    どのドメインに Cookie を送信するかを指定します。

    Set-Cookie: sessionId=abc123; Domain=example.com
    設定送信先
    Domain=example.comexample.com と *.example.com（すべてのサブドメイン）
    省略Cookie を設定したホストだけ（www.example.com だけ、など）

    注意

    • Domain を 広げすぎない（サブドメイン間で共有されると漏洩リスクが増える）
    • 不要なら Domain 属性は省略 する（ホスト限定のほうが安全）
    • user-content.example.com に XSS があると、広い Domain 設定では Cookie が危険にさらされる

    6.2 Path 属性

    どの URL パス以下に Cookie を送信するかを指定します。

    Set-Cookie: sessionId=abc123; Path=/app
    設定送信先
    Path=/app/app 以下のみ
    Path=/サイト全体（最も一般的）

    注意

    • Path を狭くすると、意図しないパスに Cookie が送られないようにできる
    • セッション Cookie は通常 Path=/
    • Path の 末尾のスラッシュ に注意（/app と /app/ の挙動）

    6.3 Expires 属性（および Max-Age）

    Cookie の 有効期限 を制御します。Expires は日時で、Max-Age は秒数で指定します。

    Set-Cookie: sessionId=abc123; Expires=Wed, 01 Jan 2025 00:00:00 GMT
Set-Cookie: sessionId=abc123; Max-Age=3600
    設定動作
    Expires / Max-Age あり指定した時刻・秒数まで有効
    両方省略セッション Cookie（ブラウザ終了で削除）

    注意

    • ログインセッションには 適切な期限 を設ける（長すぎると、盗まれたあとの被害が広がる）
    • 「ログイン状態を保持」は Max-Age を長くするが、リスクとのトレードオフ になる
    • ログアウト時は 期限切れの Cookie で明示的に上書きして削除する
    ログアウト時に Cookie を削除する 
    setcookie('sessionId', '', [
    'expires'  => time() - 3600,
    'path'     => '/',
    'secure'   => true,
    'httponly' => true,
]);

    6.4 HttpOnly 属性

    JavaScript から Cookie にアクセスできない ようにします。

    Set-Cookie: sessionId=abc123; HttpOnly
    HttpOnly効果
    ありdocument.cookie に表示されない → XSS による窃取を防ぐ
    なしJavaScript から読み書きできる → 危険

    注意

    • セッションID・auth_token には 必ず HttpOnly を付ける
    • HttpOnly でも ブラウザの開発者ツールでは見える（利用者自身による改変はできる）
    • HttpOnly は 改変防止ではない（送信する値の書き換えはできる）→ 重要なデータはサーバー側に置く
    HttpOnly なし 
    document.cookie; // "sessionId=abc123"
// ← XSS で外部に送信できる
    HttpOnly あり 
    document.cookie; // ""
// ← sessionId は含まれない

    HttpOnly が XSS に対してどこまで効くか（保険的対策であること）は XSS：クッキーに HttpOnly 属性を付与 を参照してください。

    7.まとめ

    トピック要点
    保存先の原則Cookie にはセッションID だけ。機密・重要な状態はセッション変数へ
    セキュア属性不備Secure / HttpOnly / SameSite の欠如は盗聴・XSS・CSRF のリスク
    Secure 属性HTTPS のときだけ Cookie を送信。セッションID には必須
    トークン対策HTTP/HTTPS 混在時、Secure 付きのトークン Cookie で二重に検証
    トークンの理由HTTP の傍受ではトークンが取れず、機密操作を拒否できる
    Domain広げすぎない。省略してホスト限定にするのが安全
    Path送信範囲の制限。通常は /
    Expires適切な有効期限。ログアウト時は明示的に削除
    HttpOnlyJS からの読み取りを防ぐ。セッションID には必須

    7.1 セッション Cookie の推奨設定

    Set-Cookie: sessionId=<値>;
  Secure;
  HttpOnly;
  SameSite=Strict;
  Path=/;
  Max-Age=3600

    徳丸本の次の章では、メール送信機能や OS コマンド呼び出しにまつわる脆弱性を扱います。これらは メールヘッダインジェクション と OSコマンドインジェクション（Web脆弱性対策解説）で解説しています。

    8.理解度チェック

    Q1. 「会員ランク」や「カートの合計金額」を Cookie に保存してはいけないのはなぜですか？

    Cookie は 利用者が開発者ツールなどで簡単に書き換えられる からです（HttpOnly でも改変はできます）。漏洩したときに値そのものが漏れる点も問題です。重要な状態は セッション変数（サーバー側）に置き、Cookie にはセッションID だけを入れます。

    Q2. 複数のサーバーでセッション変数を共有するには、何が必要ですか？

    セッション変数はサーバーごとに独立しているので、DB や Redis などの 共通セッションストア が必要です。Cookie は同じドメイン内なら自動的に共有されます。

    Q3. セッションID の Cookie に Secure 属性がないと、どんな攻撃を受けますか？

    HTTP でアクセスしたときに Cookie が平文で送られ、同じ Wi-Fi などにいる攻撃者に 盗聴 されます。攻撃者はそのセッションID で本人になりすませます。

    Q4. HTTP と HTTPS が混在するサイトで、トークン Cookie を使うと安全になるのはなぜですか？

    トークン Cookie には Secure 属性が付いているので、HTTP の通信には決して含まれません。HTTP を盗聴して sessionId を盗まれても、サーバーはセッション内のトークンと Cookie のトークンの一致を確かめるので、機密操作は拒否できます。ただし第二の防御線であり、全ページ HTTPS 化が最善です。

    Q5. Domain 属性を省略した場合と Domain=example.com とした場合の違いは何ですか？

    省略すると、Cookie を設定した ホストだけ に送られます。Domain=example.com とすると example.com と すべてのサブドメイン に送られ、どこか 1 つのサブドメインに XSS があるだけで危険になります。不要なら省略します。

    Q6. Expires も Max-Age も指定しない Cookie はどうなりますか？ また、ログアウト時に Cookie を消すにはどうしますか？

    ブラウザを閉じると消える セッション Cookie になります。ログアウト時は、空の値と 過去の日時（time() - 3600 など）を指定した Cookie で上書きして削除します。

    Q7. HttpOnly を付ければ Cookie の改ざんも防げますか？

    防げません。HttpOnly は JavaScript からの読み取りを防ぐ だけで、利用者は開発者ツールで値を見たり書き換えたりできます。改ざんされて困るデータはサーバー側に置きます。
