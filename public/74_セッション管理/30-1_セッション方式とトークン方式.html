    30 トークン

    セッション方式とトークン方式

    ログインした後の「この人はログイン済み」という状態を覚えておく方法には、大きく 2 つあります。サーバーが覚えておく セッション方式 と、情報を書いた札をユーザーに持たせる トークン方式 です。このページでは、2 つの仕組みと違い、使い分け、アクセストークン・リフレッシュトークン・ID トークンという 3 種類のトークン、そして Node.js（Express）での実装例とセキュリティの注意点を解説します。

    もとにしたノート：30_トークン/01_セッション・トークン基礎、30_トークン/02_セッションとトークンとは

    ひとことで言うと

    セッションは「テーブル番号」、トークンは「会員証」です。セッション方式ではサーバーが情報を持ち、ユーザーには番号だけを渡します。トークン方式では情報そのものを署名付きの札に書いて渡し、サーバーは何も覚えずに札を検証します。セッションは 取り消しやすい、トークンは サーバーを増やしやすい のが長所です。

    1.セッションとトークンとは何か

    セッションとトークンは、Web アプリケーションでユーザーの 認証状態（ログインしているかどうか、誰なのか）を管理するための重要な仕組みです。

    • セッション（Session）：サーバー側で管理される一時的なデータです。ユーザーがログインしてからログアウトするまでの「会話の続き」を管理する仕組みです。
    • トークン（Token）：認証情報を含む文字列で、クライアント側（ブラウザやアプリ）で管理されます。ユーザーの認証情報を表す「証明書」のようなもので、紙のチケットやクーポン券をイメージすると分かりやすいです。

    そもそも HTTP は 1 回ごとのやりとりを覚えていない仕組みなので、こうした工夫が必要になります。その背景は HTTPとセッション管理 を参照してください。

    1.1 日常生活での例え

    セッション＝テーブル番号

    • お店が「テーブル 5 番」と記録する
    • お客様は「テーブル 5 番」という番号だけを受け取る
    • 実際の情報（注文内容など）はお店側に保存される

    トークン＝会員証

    • 会員証には名前や会員番号が書かれている
    • 会員証を見れば、誰であるかが分かる
    • 会員証自体に情報が含まれている

    1.2 レストランと遊園地で流れをたどる

    セッション：レストランでの食事

    1. 入店（ログイン）：店員があなたを認識してテーブルに案内する。これが「セッション開始」
    2. 食事中（ログイン状態）：店員はあなたがどのテーブルにいるか覚えていて、注文を取ったり料理を運んだりする。これが「セッション継続中」
    3. 退店（ログアウト）：会計を済ませて店を出る。これが「セッション終了」

    トークン：遊園地の入場チケット

    1. チケット購入（ログイン）：入場チケットを受け取る。これが「トークン発行」
    2. アトラクション利用（API 呼び出し）：チケットを見せて乗る。係員はチケットを見て入場権を確認する。これが「トークン検証」
    3. 期限切れ：チケットには有効期限があり、切れると使えなくなる。新しいチケットが必要になる

    2.セッション方式

    ユーザーがログインすると、サーバーは セッション ID（ユーザーを見分けるための、推測できない番号）を作り、その ID とユーザー情報をサーバー側に保存します。ブラウザには ID だけを渡し、通常は Cookie（ブラウザが自動で送り返す小さなデータ）に入れておきます。Cookie の詳しい仕組みは Cookieの仕組み、ログインの流れは セッションとCookieによるログイン で扱います。

    2.1 セッションの仕組み

    1. ユーザーがログインする
    2. サーバーがセッション ID を生成する（例："abc123"）
    3. サーバー側に保存する：{ "abc123": { userId: 1, username: "yamada" } }
    4. セッション ID を Cookie でクライアントに送る
    5. 次回のリクエストで、ブラウザがセッション ID を送る
    6. サーバーがセッション ID からユーザー情報を取り出す

    2.2 セッションの特徴

    特徴説明
    長所サーバー側で状態を管理データはサーバーに保存され、クライアントには ID だけが送られる。機密情報がクライアントに渡らないのでセキュリティが高い
    長所サーバー側で無効化できるログアウトや乗っ取りが分かったとき、サーバーの記録を消せばすぐに使えなくなる
    短所サーバーの資源を使うメモリやデータベースなどの保存場所が必要
    短所スケーラビリティに課題サーバーを増やすと、どのサーバーからも同じ記録を見られるようにする必要がある（2.4）

    2.3 セッションの実装例（express-session）

    Node.js の Web フレームワーク Express では、express-session というライブラリでセッションを扱えます。

    const express = require('express');
const session = require('express-session');
const app = express();

// セッションの設定
app.use(session({
  secret: 'your-secret-key', // セッションIDの署名に使用
  resave: false,             // セッションが変更されていなくても再保存しない
  saveUninitialized: false,  // 初期化されていないセッションを保存しない
  cookie: {
    secure: true,                // HTTPSのみ
    httpOnly: true,              // JavaScriptからアクセス不可
    maxAge: 24 * 60 * 60 * 1000, // 24時間
    sameSite: 'strict'           // CSRF攻撃対策
  },
  // セッションストア（デフォルトはメモリ、本番環境ではRedisなどを使う）
  store: new MemoryStore()
}));

// ログイン処理
app.post('/api/login', async (req, res) => {
  const { username, password } = req.body;

  // 認証処理
  const user = await authenticateUser(username, password);

  if (user) {
    // セッションにユーザー情報を保存
    req.session.userId = user.id;
    req.session.username = user.username;
    req.session.email = user.email;

    res.json({ message: 'ログイン成功' });
  } else {
    res.status(401).json({ error: '認証に失敗しました' });
  }
});

// 認証が必要なエンドポイント
app.get('/api/profile', (req, res) => {
  // セッションからユーザー情報を取得
  if (!req.session.userId) {
    return res.status(401).json({ error: 'ログインが必要です' });
  }

  res.json({
    userId: req.session.userId,
    username: req.session.username,
    email: req.session.email
  });
});

// ログアウト処理
app.post('/api/logout', (req, res) => {
  req.session.destroy((err) => {
    if (err) {
      return res.status(500).json({ error: 'ログアウトに失敗しました' });
    }
    res.json({ message: 'ログアウトしました' });
  });
});

    secure・httpOnly・sameSite などの Cookie 属性の意味は Cookieの仕組み を参照してください。

    2.4 セッションストアとサーバーが増えたとき

    セッションストア はセッションを保存する場所です。初期設定のメモリ保存は、サーバーを再起動すると消え、サーバーが複数台あると共有できません。本番環境では、メモリではなくデータベースや Redis（高速に読み書きできるデータの置き場）を使います。

    // Redisを使ったセッションストア
const RedisStore = require('connect-redis')(session);
const redis = require('redis');
const client = redis.createClient();

app.use(session({
  store: new RedisStore({ client }),
  secret: 'your-secret-key',
  resave: false,
  saveUninitialized: false,
  cookie: {
    secure: true,
    httpOnly: true,
    maxAge: 24 * 60 * 60 * 1000
  }
}));

    セッション方式が悪いわけではない

    複数台の問題は Redis などの共有ストアで解決できます。ただし「状態をサーバー側で管理し続ける」点は変わりません。ここがトークン方式（とくに JWT）が生まれた出発点です。詳しくは JWTの構造と検証 で扱います。

    3.トークン方式

    トークンは認証情報を含む文字列で、ユーザー情報や権限情報が入っています。最も一般的な形式が JWT（JSON Web Token、ジョット） です。トークンには 署名（作った本人しか作れない印）が含まれており、改ざんを見つけられます。

    3.1 トークンの仕組み

    1. ユーザーがログインする
    2. サーバーが JWT を生成する（ユーザー情報を含む）
    3. トークンをクライアントに送る
    4. クライアントがトークンを保存する（localStorage、sessionStorage など）
    5. 次回のリクエストで、トークンを送る（多くは Authorization: Bearer トークン ヘッダー）
    6. サーバーがトークンを検証し、ユーザー情報を取り出す

    保存場所によって安全性が変わります。どこに置くべきかは トークンの保存場所 で詳しく扱います。

    3.2 JWT の構造（あらまし）

    JWT は header.payload.signature の 3 つの部分でできています。各部分の意味、クレームの種類、正しい検証の手順は JWTの構造と検証 で解説します。

    1. Header（ヘッダー）

    {
  "alg": "HS256",
  "typ": "JWT"
}

    2. Payload（ペイロード）

    {
  "userId": 1,
  "username": "yamada",
  "email": "yamada@example.com",
  "iat": 1234567890,
  "exp": 1234654290
}

    3. Signature（署名）

    HMACSHA256(
  base64UrlEncode(header)
  + "." +
  base64UrlEncode(payload),
  secret
)

    ペイロードは誰でも読める

    JWT の中身は暗号化されておらず、Base64URL という置き換えをしただけです。上の例のようにメールアドレスを入れると、トークンを手にした人には読めてしまいます。秘密の情報は入れないようにします（JWTの構造と検証）。

    3.3 トークンの特徴

    特徴説明
    長所サーバー側で状態を保持しないステートレス（状態を持たない）なので、サーバーは表を引かずに検証できる
    長所スケーラビリティが高いサーバー間で情報を共有する必要がない
    長所複数のサービス間で共有しやすい同じ鍵（公開鍵）で、別のサービスも検証できる
    短所漏洩すると悪用されるトークンを盗まれると、その人になりすまされる
    短所期限まで無効化しにくい一度発行すると、サーバーが覚えていないので途中で取り消しにくい

    3.4 トークンの実装例（jsonwebtoken）

    サーバー側では jsonwebtoken ライブラリで、ログイン時にトークンを作り（jwt.sign）、リクエストのたびに検証します（jwt.verify）。

    const express = require('express');
const jwt = require('jsonwebtoken');
const app = express();

const JWT_SECRET = process.env.JWT_SECRET || 'your-secret-key';

// ログイン処理
app.post('/api/login', async (req, res) => {
  const { username, password } = req.body;

  // 認証処理
  const user = await authenticateUser(username, password);

  if (user) {
    // JWTトークンを生成
    const token = jwt.sign(
      {
        userId: user.id,
        username: user.username,
        email: user.email
      },
      JWT_SECRET,
      {
        expiresIn: '24h' // 24時間で有効期限切れ
      }
    );

    res.json({ token, user: { id: user.id, username: user.username } });
  } else {
    res.status(401).json({ error: '認証に失敗しました' });
  }
});

// トークンを検証するミドルウェア
function authenticateToken(req, res, next) {
  const authHeader = req.headers['authorization'];
  const token = authHeader && authHeader.split(' ')[1]; // "Bearer TOKEN"

  if (!token) {
    return res.status(401).json({ error: 'トークンが必要です' });
  }

  jwt.verify(token, JWT_SECRET, (err, user) => {
    if (err) {
      return res.status(403).json({ error: '無効なトークンです' });
    }

    req.user = user; // ユーザー情報をリクエストオブジェクトに追加
    next();
  });
}

// 認証が必要なエンドポイント
app.get('/api/profile', authenticateToken, (req, res) => {
  // req.userにユーザー情報が含まれている
  res.json({
    userId: req.user.userId,
    username: req.user.username,
    email: req.user.email
  });
});

    ミドルウェアとは

    ミドルウェア は、本来の処理の手前に差し込む共通処理です。authenticateToken を通ったリクエストだけが /api/profile の本体にたどり着きます。なお、無効なトークンに 403 を返している例ですが、「名乗れていない」ことを表す 401 を返す作りもよく使われます（401 と 403 の違いは 認証と認可の違い）。

    3.5 クライアント側でのトークン使用

    // ログイン
async function login(username, password) {
  const response = await fetch('/api/login', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({ username, password }),
  });

  const { token } = await response.json();

  // トークンを保存
  localStorage.setItem('token', token);

  return token;
}

// トークンを使ってAPIを呼び出す
async function fetchProfile() {
  const token = localStorage.getItem('token');

  const response = await fetch('/api/profile', {
    headers: {
      'Authorization': `Bearer ${token}`,
    },
  });

  if (response.status === 401) {
    // トークンが無効な場合、再ログイン
    localStorage.removeItem('token');
    window.location.href = '/login';
    return;
  }

  const profile = await response.json();
  return profile;
}

    ここでは分かりやすさのために localStorage に保存していますが、localStorage は XSS（悪意のあるスクリプトを埋め込まれる攻撃）で読み取られる危険があります（8.3 と トークンの保存場所）。

    4.セッションとトークンの違い

    項目セッショントークン（JWT）
    保存場所サーバー側クライアント側
    データの場所サーバー側トークン内（エンコードされている）
    状態ステートフル（サーバーに状態を保存）ステートレス（サーバーに状態を保存しない）
    スケーラビリティ低い（サーバー間で共有が必要）高い（サーバー間で共有不要）
    セキュリティ高い（機密情報がクライアントに送られない）中程度（トークンが盗まれるリスク）
    ログアウト簡単（サーバー側で削除）難しい（トークンを無効化する仕組みが必要）
    有効期限の管理サーバー側で管理トークン内に含まれる

    5.セッションとトークンの使い分け

    セッションが適している場合

    1. 従来の Web アプリケーション：サーバーサイドレンダリング（SSR、サーバーで HTML を組み立てて返す作り）。セッション管理が簡単
    2. セキュリティが最優先：機密情報を扱う。トークンの盗難リスクを避けたい
    3. ログアウトの即時反映が必要：サーバー側で消せばすぐ効くので、トークンの無効化の仕組みが不要

    トークンが適している場合

    1. モバイルアプリ：クライアント側で管理しやすい
    2. マイクロサービス（機能ごとに小さなサービスに分ける作り）：複数のサーバー間で認証情報を共有でき、ステートレスに設計できる
    3. SPA（Single Page Application、1 枚のページを JavaScript で書き換えて動く作り）：クライアント側で状態を管理し、API 中心に設計する
    4. スケーラビリティが重要：サーバー間でセッションを共有する必要がない

    6.トークンの 3 つの種類

    トークン方式では、役割の違う 3 種類のトークンがよく登場します。ここでは全体像をつかみ、アクセストークンとリフレッシュトークンの設計の詳細は アクセストークンとリフレッシュトークン で扱います。

    6.1 アクセストークン

    アクセストークン は、API やリソースにアクセスするための「通行証」です。会社の入館証にたとえると、入館証があればオフィスに入れて、会議室や特定のフロアに入る権限も入館証に含まれており、有効期限が切れると使えなくなります。

    • 用途：API リクエストの認証
    • 有効期限：通常は 短い（15 分〜1 時間程度）
    • 含まれる情報：ユーザー ID、権限（スコープ）、有効期限など
    • 保存場所：クライアント側（メモリ、ローカルストレージなど。トークンの保存場所）
    • 長所：短い有効期限でセキュリティが高く、漏洩しても被害を小さく抑えられる。短所：頻繁に更新が必要
    // APIリクエスト時にアクセストークンを使用
fetch('https://api.example.com/user/profile', {
  headers: {
    'Authorization': 'Bearer ' + accessToken
  }
})

// アクセストークンの生成（15分で有効期限切れ）
const accessToken = jwt.sign(
  { userId: user.id },
  JWT_SECRET,
  { expiresIn: '15m' }
);

    6.2 リフレッシュトークン

    リフレッシュトークン は、アクセストークンの期限が切れたときに新しいアクセストークンをもらうための「交換券」です。図書館の貸出カードにたとえられます。

    1. 初回ログイン：貸出カード（リフレッシュトークン）を受け取る。長期間有効
    2. 本を借りる（API アクセス）：カードを見せて、一時的な利用券（アクセストークン）を受け取る
    3. 利用券の期限切れ：カードを見せて、新しい利用券をもらう
    4. カードの期限切れ：もう一度図書館に行き、新しいカードを作る（再ログイン）
    • 有効期限：通常は 長い（数日〜数週間、場合によっては数か月）
    • 含まれる情報：ユーザー ID、トークン ID など
    • 保存場所：クライアント側の安全な場所（HttpOnly Cookie 推奨）
    • 長所：ユーザーは頻繁にログインしなくてよい。漏洩した場合はサーバー側で無効化できる。短所：長期間有効なので漏洩すると危険が大きく、安全に保存する必要がある
    // リフレッシュトークンの生成（7日間で有効期限切れ）
const refreshToken = jwt.sign(
  { userId: user.id, type: 'refresh' },
  JWT_SECRET,
  { expiresIn: '7d' }
);

// アクセストークンの更新
app.post('/api/refresh', (req, res) => {
  const { refreshToken } = req.body;

  jwt.verify(refreshToken, JWT_SECRET, (err, decoded) => {
    if (err || decoded.type !== 'refresh') {
      return res.status(403).json({ error: '無効なリフレッシュトークンです' });
    }

    // 新しいアクセストークンを発行
    const newAccessToken = jwt.sign(
      { userId: decoded.userId },
      JWT_SECRET,
      { expiresIn: '15m' }
    );

    res.json({ accessToken: newAccessToken });
  });
});

    使い回しの検知やローテーション（使うたびに新しいものと取り替える）など、安全な設計は アクセストークンとリフレッシュトークン で解説します。

    6.3 ID トークン

    ID トークン は、ユーザーが「誰であるか」を証明する「身分証明書」です。運転免許証には名前・生年月日・住所が書かれていて、見れば誰か分かります。ただし免許証だけで車の鍵が開くわけではありません。API を使うにはアクセストークンが必要です。

    • 用途：ユーザーの身元確認
    • 有効期限：通常は短い（アクセストークンと同程度）
    • 含まれる情報：ユーザー ID、名前、メールアドレス、認証時刻など
    • 使用場面：OAuth 2.0 や OpenID Connect（OAuth 2.0 にログインの仕組みを足した規格）。詳しくは OAuth2.0の仕組み
    • 長所：身元情報を含み、署名されているので改ざんを検出でき、複数のサービス間でユーザー情報を共有しやすい。短所：アクセストークンとは別物なので混同しやすい
    // IDトークンからユーザー情報を取得
const userInfo = decodeIdToken(idToken);
console.log(userInfo.name);  // ユーザー名
console.log(userInfo.email); // メールアドレス
console.log(userInfo.sub);   // ユーザーID

    6.4 3 つのトークンの関係

    1. ユーザーがログインする
    2. 3 つのトークンが発行される：アクセストークン（短期限）、リフレッシュトークン（長期限）、ID トークン（短期限）
    3. アクセストークンで API にアクセスする（ID トークンでユーザー情報を取得する）
    4. アクセストークンの期限が切れる
    5. リフレッシュトークンで新しいアクセストークンを取得する
    6. リフレッシュトークンの期限が切れる → 再ログインが必要
    項目アクセストークンリフレッシュトークンID トークン
    用途API アクセスアクセストークン更新ユーザー識別
    有効期限短い（15 分〜1 時間）長い（数日〜数週間）短い（15 分〜1 時間）
    含まれる情報ユーザー ID、権限ユーザー ID、トークン IDユーザー情報
    使用頻度高い（毎回の API 呼び出し）低い（期限切れ時のみ）中（ログイン時、ユーザー情報取得時）
    保存場所メモリ、ローカルストレージHttpOnly Cookie 推奨メモリ、ローカルストレージ

    7.実際の使用例（クライアント側の流れ）

    3 種類のトークンを使うクライアント側の処理を、ログイン → API アクセス → 更新 → ユーザー情報の取得の順に見ます。

    7.1 ログインフロー

    // 1. ユーザーがログイン
async function login(username, password) {
  const response = await fetch('/api/auth/login', {
    method: 'POST',
    body: JSON.stringify({ username, password })
  });

  const data = await response.json();

  // 3つのトークンを受け取る
  const accessToken = data.accessToken;   // アクセストークン
  const refreshToken = data.refreshToken; // リフレッシュトークン
  const idToken = data.idToken;           // IDトークン

  // 安全に保存
  localStorage.setItem('accessToken', accessToken);
  // リフレッシュトークンはHttpOnly Cookieに保存（サーバー側で設定）

  return { accessToken, refreshToken, idToken };
}

    7.2 API アクセス（期限切れなら更新して再試行）

    // 2. アクセストークンを使ってAPIにアクセス
async function getUserProfile() {
  const accessToken = localStorage.getItem('accessToken');

  const response = await fetch('/api/user/profile', {
    headers: {
      'Authorization': `Bearer ${accessToken}`
    }
  });

  if (response.status === 401) {
    // アクセストークンが期限切れ
    await refreshTokens();
    // 再試行
    return getUserProfile();
  }

  return await response.json();
}

    7.3 トークンリフレッシュ

    // 3. リフレッシュトークンで新しいアクセストークンを取得
async function refreshTokens() {
  const response = await fetch('/api/auth/refresh', {
    method: 'POST',
    credentials: 'include' // Cookieにリフレッシュトークンが含まれる
  });

  const data = await response.json();

  // 新しいアクセストークンを保存
  localStorage.setItem('accessToken', data.accessToken);

  return data.accessToken;
}

    credentials: 'include' は「Cookie も一緒に送る」という指定です。別オリジン（別のドメインなど）の API に Cookie を送る場合の注意は CORSエラーの対処法とCookie を参照してください。

    7.4 ユーザー情報の取得

    // 4. IDトークンからユーザー情報を取得
function getUserInfo(idToken) {
  // JWTをデコード（実際の実装ではライブラリを使用）
  const payload = JSON.parse(atob(idToken.split('.')[1]));

  return {
    userId: payload.sub,
    name: payload.name,
    email: payload.email
  };
}

    デコードは「読むだけ」

    この関数は署名を確かめずに中身を読んでいるだけです。画面に名前を表示する程度なら構いませんが、サーバー側で「誰か」「何をしてよいか」を決めるときは、必ず署名を検証してから 使います（JWTの構造と検証）。

    8.サーバー側の完全な実装とセキュリティの注意点

    8.1 完全な実装例

    セッション方式とトークン方式それぞれで、ログイン・認証の確認・プロフィール取得・ログアウトをひととおり書いた例です（開くと表示されます）。

    セッションを使った実装（Redis ストア付き） 
    const express = require('express');
const session = require('express-session');
const RedisStore = require('connect-redis')(session);
const redis = require('redis');
const app = express();

const client = redis.createClient();

app.use(express.json());
app.use(session({
  store: new RedisStore({ client }),
  secret: process.env.SESSION_SECRET,
  resave: false,
  saveUninitialized: false,
  cookie: {
    secure: process.env.NODE_ENV === 'production',
    httpOnly: true,
    maxAge: 24 * 60 * 60 * 1000,
    sameSite: 'strict'
  }
}));

// ログイン
app.post('/api/login', async (req, res) => {
  const { username, password } = req.body;
  const user = await authenticateUser(username, password);

  if (user) {
    req.session.userId = user.id;
    req.session.username = user.username;
    res.json({ message: 'ログイン成功' });
  } else {
    res.status(401).json({ error: '認証に失敗しました' });
  }
});

// 認証ミドルウェア
function requireAuth(req, res, next) {
  if (!req.session.userId) {
    return res.status(401).json({ error: 'ログインが必要です' });
  }
  next();
}

// プロフィール取得
app.get('/api/profile', requireAuth, async (req, res) => {
  const user = await getUserById(req.session.userId);
  res.json(user);
});

// ログアウト
app.post('/api/logout', (req, res) => {
  req.session.destroy();
  res.json({ message: 'ログアウトしました' });
});

    ログイン成功時にセッション ID を作り直さないと「セッション固定化」という攻撃を受けることがあります。セッション管理の不備 を参照してください。

    トークンを使った実装（アクセストークン＋リフレッシュトークン） 
    const express = require('express');
const jwt = require('jsonwebtoken');
const app = express();

const JWT_SECRET = process.env.JWT_SECRET;
const JWT_REFRESH_SECRET = process.env.JWT_REFRESH_SECRET;

app.use(express.json());

// ログイン
app.post('/api/login', async (req, res) => {
  const { username, password } = req.body;
  const user = await authenticateUser(username, password);

  if (user) {
    // アクセストークンとリフレッシュトークンを生成
    const accessToken = jwt.sign(
      { userId: user.id, username: user.username },
      JWT_SECRET,
      { expiresIn: '15m' }
    );

    const refreshToken = jwt.sign(
      { userId: user.id, type: 'refresh' },
      JWT_REFRESH_SECRET,
      { expiresIn: '7d' }
    );

    // リフレッシュトークンはデータベースに保存（ログアウト時に無効化するため）
    await saveRefreshToken(user.id, refreshToken);

    res.json({
      accessToken,
      refreshToken,
      user: { id: user.id, username: user.username }
    });
  } else {
    res.status(401).json({ error: '認証に失敗しました' });
  }
});

// トークン検証ミドルウェア
function authenticateToken(req, res, next) {
  const authHeader = req.headers['authorization'];
  const token = authHeader && authHeader.split(' ')[1];

  if (!token) {
    return res.status(401).json({ error: 'トークンが必要です' });
  }

  jwt.verify(token, JWT_SECRET, (err, user) => {
    if (err) {
      return res.status(403).json({ error: '無効なトークンです' });
    }
    req.user = user;
    next();
  });
}

// プロフィール取得
app.get('/api/profile', authenticateToken, async (req, res) => {
  const user = await getUserById(req.user.userId);
  res.json(user);
});

// アクセストークンの更新
app.post('/api/refresh', async (req, res) => {
  const { refreshToken } = req.body;

  if (!refreshToken) {
    return res.status(401).json({ error: 'リフレッシュトークンが必要です' });
  }

  // データベースでリフレッシュトークンを検証
  const isValid = await validateRefreshToken(refreshToken);
  if (!isValid) {
    return res.status(403).json({ error: '無効なリフレッシュトークンです' });
  }

  jwt.verify(refreshToken, JWT_REFRESH_SECRET, (err, decoded) => {
    if (err) {
      return res.status(403).json({ error: '無効なリフレッシュトークンです' });
    }

    // 新しいアクセストークンを発行
    const newAccessToken = jwt.sign(
      { userId: decoded.userId, username: decoded.username },
      JWT_SECRET,
      { expiresIn: '15m' }
    );

    res.json({ accessToken: newAccessToken });
  });
});

// ログアウト
app.post('/api/logout', async (req, res) => {
  const { refreshToken } = req.body;

  // リフレッシュトークンを無効化
  await invalidateRefreshToken(refreshToken);

  res.json({ message: 'ログアウトしました' });
});

    ポイントは、アクセストークンとリフレッシュトークンで 別の秘密（JWT_SECRET と JWT_REFRESH_SECRET）を使うこと、リフレッシュトークンを データベースにも記録 してログアウト時に無効化できるようにしていることです。トークン方式の「取り消しにくい」という弱点を、リフレッシュトークンの側だけサーバーで覚えることで補っています。

    8.2 セッションのセキュリティ

    推奨設定 
    app.use(session({
  secret: process.env.SESSION_SECRET, // 環境変数から取得
  cookie: {
    secure: true,      // HTTPSのみ
    httpOnly: true,    // JavaScriptからアクセス不可
    sameSite: 'strict' // CSRF攻撃対策
  },
  // 本番環境ではRedisなどの外部ストアを使用
  store: new RedisStore({ client })
}));

    秘密の値はコードに直接書かず、環境変数から読みます。sameSite が防ぐ CSRF（ログイン中の利用者に意図しない操作をさせる攻撃）については CSRF を参照してください。

    8.3 トークンのセキュリティ

    推奨設定：強い秘密・短い期限・発行者と受信者の確認 
    const token = jwt.sign(
  payload,
  process.env.JWT_SECRET, // 強力なシークレットキー
  {
    expiresIn: '15m',     // 短い有効期限
    issuer: 'myapp.com',  // 発行者
    audience: 'myapp.com' // 受信者
  }
);

// トークンの検証
jwt.verify(token, process.env.JWT_SECRET, {
  issuer: 'myapp.com',
  audience: 'myapp.com'
}, (err, decoded) => {
  // 検証処理
});

    issuer（発行者）と audience（受け取り手）を検証時にも確かめると、別のサービス向けに発行されたトークンを受け付けずに済みます。検証で確かめる項目の全体は JWTの構造と検証 にまとめています。

    8.4 トークンの保存方法

    間違い：localStorage は XSS 攻撃のリスク 
    localStorage.setItem('token', token);
    推奨：HttpOnly Cookie に保存 
    res.cookie('token', token, {
  httpOnly: true,
  secure: true,
  sameSite: 'strict'
});

// または、メモリに保存
// （ページを閉じると消える）
let token = null; // グローバル変数に保存

    XSS 自体の仕組みは XSSの基本、保存場所ごとの長所と短所の比較は トークンの保存場所 で解説します。

    8.5 セキュリティのベストプラクティス

    • アクセストークンは 短い有効期限 にする
    • リフレッシュトークンは HttpOnly Cookie に保存する
    • トークンは HTTPS で送信する
    • トークンが漏洩した場合は すぐに無効化 する
    • 定期的にログアウト してトークンを無効化する

    9.ハイブリッドアプローチ

    セッションとトークンを組み合わせることもできます。次の例では、ログイン時に作った JWT をサーバー側のセッションに入れておき、リクエストのたびにセッションとトークンの両方を確かめます。

    // セッションにトークンを保存
app.post('/api/login', async (req, res) => {
  const user = await authenticateUser(username, password);

  if (user) {
    // JWTトークンを生成
    const token = jwt.sign(
      { userId: user.id },
      JWT_SECRET,
      { expiresIn: '24h' }
    );

    // セッションにトークンを保存
    req.session.token = token;
    req.session.userId = user.id;

    res.json({ message: 'ログイン成功' });
  }
});

// トークンとセッションの両方を検証
function authenticate(req, res, next) {
  // セッションを確認
  if (!req.session.userId) {
    return res.status(401).json({ error: 'ログインが必要です' });
  }

  // トークンを検証
  const token = req.session.token;
  jwt.verify(token, JWT_SECRET, (err, decoded) => {
    if (err) {
      return res.status(403).json({ error: '無効なトークンです' });
    }
    req.user = decoded;
    next();
  });
}

    10.まとめ

    セッショントークン（JWT）
    たとえテーブル番号会員証
    管理する場所サーバー側クライアント側
    セキュリティ高い（機密情報がクライアントに送られない）盗まれると悪用される。期限を短く
    ログアウト簡単（サーバー側で削除）難しい（無効化の仕組みが必要）
    スケーラビリティ低い（共有ストアが必要）高い（共有不要）
    向いている場面従来の Web アプリ、セキュリティ最優先モバイルアプリ、マイクロサービス、SPA
    • セッション：サーバー側で状態を管理する仕組み
    • アクセストークン：API にアクセスするための通行証（短期限）
    • リフレッシュトークン：アクセストークンを更新するための交換券（長期限）
    • ID トークン：ユーザーが誰であるかを証明する身分証明書

    11.理解度チェック

    Q1. セッション方式とトークン方式で、ユーザーの情報はそれぞれどこにありますか？

    セッション方式ではサーバー側（セッションストア）にあり、ブラウザはセッション ID という番号だけを持ちます。トークン方式では情報そのものがトークンの中に入っていて、クライアント側が持ちます。

    Q2. サーバーを 3 台に増やしたとき、セッション方式では何が問題になり、どう解決しますか？

    どのサーバーに来ても同じセッションの記録を見られる必要があります。Redis などの共有ストアにセッションを保存して解決します。ただし状態をサーバー側で持ち続けることは変わりません。

    Q3. 「ログアウトしたら即座に使えなくしたい」場合、セッションとトークンのどちらが簡単ですか？

    セッションです。サーバー側の記録を消せばすぐに使えなくなります。トークンはサーバーが覚えていないため、期限まで有効なままになりやすく、無効化の仕組み（失効リストやリフレッシュトークンの記録など）が別に必要です。

    Q4. アクセストークンと ID トークンの違いは何ですか？

    アクセストークンは「API にアクセスする権利」を示す通行証、ID トークンは「ユーザーが誰であるか」を示す身分証明書です。免許証（ID トークン）だけでは車（API）は動かせません。

    Q5. リフレッシュトークンはなぜ必要なのですか？

    アクセストークンの有効期限を短くしてセキュリティを高めつつ、ユーザーに頻繁なログインを強いないためです。期限が切れたら、長期間有効なリフレッシュトークンで新しいアクセストークンを受け取ります。

    Q6. トークンを localStorage に保存することの問題点と、代わりの保存先は？

    XSS で悪意のあるスクリプトが動くと、localStorage の中身は読み取られてしまいます。代わりに JavaScript から読めない HttpOnly Cookie に入れるか、ページを閉じると消えるメモリ（変数）に置きます。

    Q7. atob(idToken.split('.')[1]) で読んだ中身を、サーバーでの権限判定に使ってよいですか？

    いけません。これは署名を確かめずに読んでいるだけなので、書き換えられたトークンでもそのまま読めてしまいます。サーバーで判断に使うのは、署名を検証した後の中身だけです。
