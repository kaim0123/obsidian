    JWTの構造と検証

    JWT（JSON Web Token）は、中身を誰でも読めるが、改ざんすると分かる トークンです。サーバーが何も覚えていなくてもログイン状態が分かるのは、署名があるからです。ただし安全かどうかは 受け取った側がどう検証するか で決まります。このページでは、JWT の仕組みと 3 つの部分、署名の方式、よくある攻撃と実際の脆弱性、正しい検証の手順、鍵の入れ替え、そして「取り消しにくい」という弱点への対処を解説します。

    もとにしたノート：30_トークン/03_JWTとは_サーバーが覚えていなくても分かる理由（つるチャンネル）、30_トークン/04_JWTの構造と検証

    ひとことで言うと

    JWT の署名は「読めなくする」ためではなく「改ざんを見つける」ためのもの です。中身は読めても、鍵がないと正しい署名は作れません。事故のほとんどは トークンのヘッダに書かれた内容を信じる ことから起きるので、方式・鍵・宛先は サーバー側で決めて 検証します。

    1.JWT とは：サーバーが覚えていなくても分かる理由

    1.1 出発点：セッション方式

    セッション方式では、ログインするとサーバー側のテーブルに「abc123 はユーザー 42、ログイン済み」と書き込みます。ブラウザに渡るのは番号（session_id）だけです。次のリクエストでこの番号を送ると、サーバーがテーブルを引いてユーザー 42 だと分かります。

    サーバーが 1 台なら単純です。しかし 3 台に増えると、どのサーバーからでも同じテーブルを参照できなければなりません。これは Redis のような共有ストア（複数のサーバーから使える共通の置き場）で解決できます。

    セッション方式が悪いわけではありません。ただ、状態をサーバー側で管理し続ける ことに変わりはありません。ここが出発点です。セッション方式とトークン方式の比較は セッション方式とトークン方式 にまとめています。

    1.2 JWT の仕組み

    そこで、テーブルに書く代わりに 情報そのものをトークンに入れて渡す のが JWT です。

    1. ログインに成功すると、サーバーは「ユーザー 42、ロール（役割）は user、有効期限」を入れたトークンを作る
    2. ブラウザはこれを保存し、次回からは Authorization ヘッダー（認証情報を載せる HTTP ヘッダー）に付けて送る
    3. サーバーはテーブルを引かず、届いたトークンを 検証 してユーザー 42 だと確認する

    毎回テーブルを引かなくてよいのが JWT の特徴です。

    1.3 書き換えたら管理者になれる？

    ここで疑問が浮かびます。トークンはブラウザが持っているのだから、ロールを user から admin に書き換えたら管理者になれるのでは？

    答えは「書き換えること自体はできるが、拒否される」です。JWT の 署名 は、ヘッダとペイロードから サーバーだけが知る鍵 で作られます。ヘッダかペイロードを 1 文字でも変えると、署名と合わなくなります。攻撃者は鍵を持っていないので、書き換えた内容に合う正しい署名を作れません。

    一般的な JWT は暗号化されていない

    ペイロードは Base64URL（データを URL で使える文字だけに置き換えるルール）でエンコードされているだけで、誰でもデコードして読めます。署名は読めなくするためではなく、改ざんを見つけるためのものです。だから パスワードなどの秘密をペイロードに入れてはいけません。

    サーバーが覚えていなくても分かるのは署名があるから。中身は読める、でもこっそり書き換えることはできない。これが JWT です。

    2.JWT の構造

    2.1 3 つの部分

    JWT は、3 つの部分をそれぞれ Base64URL で表し、.（ドット）でつないだ文字列です。

    eyJhbGciOiJSUzI1NiIsInR5cCI6ImF0K2p3dCIsImtpZCI6IjIwMjYtMTAifQ . eyJpc3MiOi... . SflKxwRJSMeKKF2QT4f...
└──────────────── ヘッダ ────────────────┘   └ ペイロード ┘   └── 署名 ──┘
    部分中身例
    ヘッダ署名の方式と鍵の情報{"alg":"RS256","typ":"at+jwt","kid":"2026-10"}
    ペイロードクレーム（主張）の集まり{"iss":"https://auth.example.com","sub":"user_123","aud":"api","exp":1792300000}
    署名ヘッダとペイロードに対する署名秘密鍵がないと作れない

    ポイント： Base64URL は 暗号化ではありません。ペイロードは誰でも読めます。パスワード・個人情報・社内の情報を入れてはいけません。中身を隠したいなら JWE（JSON Web Encryption、暗号化した JWT）を使います。

    2.2 主なクレーム

    クレーム は、ペイロードに書かれる「このトークンについての主張」の 1 つ 1 つです。決まった名前のものがいくつかあり、検証で確かめる対象になります。

    クレーム意味検証で確かめること
    iss（issuer）発行者信頼している発行者か
    sub（subject）誰についてのトークンか利用者 ID として使う
    aud（audience）誰に向けたトークンか自分宛てか。別の API 向けのトークンを受け付けない
    exp（expiration）有効期限過ぎていないか
    nbf（not before）この時刻より前は無効まだ早すぎないか
    iat（issued at）発行時刻古すぎないか
    jti（JWT ID）トークンごとの ID使い捨てにしたい場合や、失効リストに使う

    3.署名の方式

    署名の作り方には、共通鍵（作る側と確かめる側が同じ秘密を持つ）と 公開鍵（秘密鍵で作り、誰でも持てる公開鍵で確かめる）の 2 系統があります。

    方式例鍵向いている場面
    HMAC（共通鍵）HS256発行と検証で 同じ秘密発行と検証が同じサーバーのとき
    RSA（公開鍵）RS256、PS256秘密鍵で署名、公開鍵で検証認証サーバーと API が別のとき
    楕円曲線（公開鍵）ES256、EdDSA同上。鍵と署名が短い同上
    • 認証サーバーと API が分かれているなら 公開鍵方式 にします。HMAC だと、検証するすべてのサーバーが「トークンを作れる秘密」を持つことになります。
    • HMAC の秘密は ランダムな 32 バイト以上 にします。人が覚えられるパスワードを使うと、漏れたトークンを使って手元で総当たりされます。

    4.よくある攻撃

    JWT の事故のほとんどは、トークンのヘッダに書かれた内容を信じてしまう ことが原因です。ヘッダは攻撃者が自由に書き換えられる部分だということを忘れないようにします。

    4.1 攻撃の手口と対策

    攻撃手口対策
    alg: noneヘッダを "alg":"none" にして署名を消す。署名なしのトークンを受け付けるライブラリがあった受け付ける方式を サーバー側で固定 する。noNE のような大文字小文字違いにも注意
    方式の取り違え（アルゴリズム混同）RS256 の 公開鍵 を HMAC の秘密として使わせ、HS256 のトークンを偽造する。公開鍵は誰でも手に入る1 つの鍵は 1 つの方式でしか使わない。HMAC と公開鍵方式を同じ検証処理で混ぜない
    kid の悪用鍵を選ぶ kid（鍵の名札）に ../../dev/null や SQL を入れ、空の鍵や攻撃者の鍵を選ばせるkid は決まった一覧から選ぶだけにする。ファイルパスや SQL に使わない
    jku・x5u の悪用「この URL の鍵で検証して」と指定し、攻撃者の鍵を読ませる。SSRF（サーバーに好きな宛先へ通信させる攻撃）にもなる（SSRF）鍵の取得先は サーバーの設定で固定 する。トークンの指定は無視する
    トークンの使い回し別のサービス向けのトークンや ID トークンを、API のアクセストークンとして送るaud・iss・typ を確かめる
    弱い HMAC の秘密漏れたトークンから、手元で秘密を総当たりする長いランダムな秘密を使い、定期的に入れ替える

    ID トークンとアクセストークンの役割の違いは セッション方式とトークン方式 の 6 章、OpenID Connect での使われ方は SAML・OAuth・OIDCの違い を参照してください。

    4.2 実際の脆弱性の例

    CVE は、公表された脆弱性に付く通し番号です。

    • jsonwebtoken（Node.js）：v8 以前は、検証時に方式を指定しないと none などを受け付ける余地があった（CVE-2022-23540 など。v9 で修正）。
    • Java の ECDSA（CVE-2022-21449、通称 Psychic Signatures）：値が 0 の署名を正しいと判定してしまい、ES256 の JWT を偽造できた。
    • 2026 年にも、JWK（JSON で表した鍵）に alg が書かれていないときに、トークンのヘッダの alg を使って検証してしまう脆弱性が報告されています（Hono の CVE-2026-22817、libjwt の CVE-2026-44699 など）。

    原因はどれも同じ

    どの事例も、方式をトークンから決めている ことが原因です。トークンは攻撃者が作れるものなので、「どう検証するか」をトークンに決めさせてはいけません。

    5.検証の手順

    1. 形式を確かめる（3 つの部分、Base64URL の文字だけ）
    2. ヘッダの alg が「サーバーが許可した方式」と一致するか確かめる
    3. kid で、サーバーが持っている鍵の一覧から鍵を選ぶ
    4. 署名を検証する
    5. iss・aud・exp・nbf を確かめる（時計のずれは 1 分程度まで許す）
    6. typ を確かめる（アクセストークンなら at+jwt）
    7. 必要なら jti で失効済みでないか確かめる
    8. ここまで通って初めて、sub や権限のクレームを使う

    5.1 署名の検証より前にペイロードを使わない

    jwt.decode()（検証しない読み取り）の結果で処理を分けると、偽造されたトークンで通ってしまいます。

    危険な例：検証せずに読んだ中身で判断している 
    const payload = jwt.decode(token); // 署名を確かめていない
if (payload.role === 'admin') {
  // 書き換えたトークンでも、ここに入れてしまう
}
    安全な例：検証を通った中身だけを使う（Node.js・jose） 
    import { jwtVerify, createRemoteJWKSet } from 'jose';

// 鍵の取得先はサーバー側で固定する（トークンの jku は使わない）
const JWKS = createRemoteJWKSet(new URL('https://auth.example.com/.well-known/jwks.json'));

export async function verifyAccessToken(token) {
  const { payload } = await jwtVerify(token, JWKS, {
    algorithms: ['RS256'],               // 許可する方式を固定
    issuer: 'https://auth.example.com',  // 発行者
    audience: 'https://api.example.com', // 自分宛てか
    typ: 'at+jwt',                       // アクセストークンか
    clockTolerance: 60,                  // 時計のずれ（秒）
  });
  return payload; // 検証済みのクレームだけを使う
}
    • createRemoteJWKSet は鍵を取ってきて覚えておき、知らない kid が来たときだけ取り直します。鍵の入れ替え（ローテーション）に自動で追いつけます。
    • 自分で署名の検証を書かないこと。実績のあるライブラリを使い、最新に保つ ことも対策の一部です。

    検証できても「してよいか」は別の話

    署名の検証で分かるのは「このトークンは本物で、誰のものか」までです。その人がその操作をしてよいかは、別に確かめます（認証と認可の違い）。

    6.鍵の入れ替え

    署名用の鍵は、ずっと同じものを使い続けず定期的に入れ替えます。JWKS（JSON Web Key Set、公開鍵の一覧）と kid を使うと、使っている途中のトークンを壊さずに入れ替えられます。

    手順内容
    1新しい鍵ペアを作り、公開鍵を JWKS に 追加 する
    2検証側のキャッシュが更新されるのを待つ
    3新しい鍵で署名を始める（kid で区別される）
    4古い鍵で署名したトークンの期限が全部切れたら、古い公開鍵を JWKS から消す

    秘密鍵が漏れたとき

    すぐに古い鍵を消し、それで署名したトークンをすべて無効にします。

    7.JWT の弱点：取り消しにくい

    JWT は「サーバーが覚えていなくても検証できる」ことが長所ですが、その裏返しで 一度出したトークンを期限前に無効にしにくい という短所があります。

    方法内容
    期限を短くするアクセストークンは 5〜15 分程度にし、リフレッシュトークンで更新する（アクセストークンとリフレッシュトークン）
    失効リストログアウトや乗っ取りが分かったときの jti を、期限まで Redis などに置いて拒否する
    トークンの中身を問い合わせるAPI が毎回、認証サーバーに有効か問い合わせる（Token Introspection）。即時に止められるが、JWT の長所は薄れる

    ログイン状態を保つだけなら、サーバー側のセッション + Cookie のほうが簡単で安全 なことも多いです（セッションとCookieによるログイン）。JWT は、複数のサービスやサーバー間で認可の情報を渡す場面で特に役立ちます。トークンをブラウザのどこに置くかは トークンの保存場所 で扱います。

    8.チェックリスト

    • 許可する alg をサーバー側で固定している（none を受け付けない）
    • HMAC と公開鍵方式を同じ鍵・同じ検証処理で混ぜていない
    • iss・aud・exp を検証している
    • kid・jku・x5u をそのまま使っていない
    • ペイロードに秘密の情報を入れていない
    • アクセストークンの期限が短く、取り消しの手段がある
    • JWT のライブラリを最新に保っている

    9.まとめ

    テーマ要点
    仕組み情報そのものをトークンに入れて渡し、サーバーは表を引かずに署名を検証する
    構造ヘッダ・ペイロード・署名を Base64URL で表し . でつなぐ。暗号化ではないので秘密は入れない
    署名改ざんを見つけるためのもの。認証サーバーと API が別なら公開鍵方式。HMAC の秘密は 32 バイト以上のランダム値
    攻撃alg: none、方式の取り違え、kid・jku の悪用、使い回し、弱い秘密。原因は「ヘッダを信じる」こと
    検証方式と鍵の取得先はサーバーで固定し、iss・aud・exp・typ を確かめ、検証後の中身だけ使う
    鍵JWKS に追加 → 待つ → 切り替え → 古い鍵を消す
    弱点取り消しにくい。短い期限・失効リスト・問い合わせで補う。ログイン状態を保つだけならセッションも有力

    10.理解度チェック

    Q1. JWT のペイロードのロールを user から admin に書き換えて送ると、どうなりますか？

    書き換え自体はできますが、署名はヘッダとペイロードからサーバーだけが知る鍵で作られているため、書き換えた中身と署名が合わなくなり拒否されます。攻撃者は鍵を持たないので、合う署名を作り直せません。

    Q2. 「JWT は署名されているから、ペイロードにパスワードを入れても安全」は正しいですか？

    正しくありません。一般的な JWT は Base64URL でエンコードしただけで暗号化されておらず、誰でも読めます。署名は改ざんを見つけるためのもので、読めなくするものではありません。隠したいなら JWE を使います。

    Q3. 認証サーバーと複数の API が別々にあるとき、HS256 ではなく RS256 などを選ぶのはなぜですか？

    HS256（HMAC）は発行と検証で同じ秘密を使うため、検証するすべての API が「トークンを作れる秘密」を持つことになり、1 か所漏れれば偽造できます。公開鍵方式なら、API は検証用の公開鍵だけを持てばよくなります。

    Q4. ヘッダを "alg":"none" にしたトークンが通ってしまう原因と対策は？

    検証の方式をトークンのヘッダから決めていることが原因です。サーバー側で許可する方式（例：algorithms: ['RS256']）を固定し、それ以外は拒否します。noNE のような大文字小文字違いにも注意します。

    Q5. ヘッダの jku に書かれた URL から鍵を取ってきて検証する作りの問題点は？

    攻撃者が自分の鍵を置いた URL を指定すれば、攻撃者が作ったトークンが正しいと判定されます。さらにサーバーに好きな宛先へ通信させる SSRF にもなります。鍵の取得先はサーバーの設定で固定し、トークンの指定は無視します。

    Q6. 検証の前に jwt.decode() の結果で処理を分けてはいけないのはなぜですか？

    decode は署名を確かめずに中身を読むだけなので、偽造されたトークンの中身でもそのまま使われてしまうからです。sub や権限のクレームは、署名・iss・aud・exp などの検証を通った後にだけ使います。

    Q7. 別のサービス向けに発行されたトークンを自分の API で受け付けないためには、どのクレームを確かめますか？

    aud（誰に向けたトークンか）が自分宛てかを確かめます。あわせて iss（発行者）と typ（アクセストークンなら at+jwt）も確かめると、ID トークンの使い回しも防げます。

    Q8. ログアウトしたユーザーの JWT を、期限前に使えなくするにはどんな方法がありますか？

    アクセストークンの期限を 5〜15 分程度に短くしてリフレッシュトークンで更新する、ログアウトしたトークンの jti を期限まで Redis などの失効リストに置いて拒否する、毎回認証サーバーに問い合わせる（Token Introspection）、のいずれかで補います。
