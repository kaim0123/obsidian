    20 パスワード・MFA・パスキー

    ログイン機能への攻撃と対策

    Webアプリの多くは、「この人は誰か」を確かめてから機能を使わせます。その仕組みが 認証（Authentication） です。このページでは徳丸本（『体系的に学ぶ 安全なWebアプリケーションの作り方』）第21章をもとに、最も一般的な パスワード認証 を中心として、ログイン機能への攻撃と対策、アカウントロックとそれをすり抜ける攻撃、自動ログイン、ログインフォーム・エラーメッセージ・ログアウトの設計を解説します。

    もとにしたノート：20_パスワード・MFA・パスキー/01_認証（徳丸本21章）

    1.認証とログイン機能の概要

    認証 とは、「今アクセスしている人が、主張どおりの本人である」ことを確かめる処理です。Webアプリでは、多くの場合 ユーザーID（またはメールアドレス）とパスワード の組み合わせで行います。

    用語意味
    認証（Authentication）「誰か」を確かめること（本人確認）
    認可（Authorization）「何をしてよいか」を決めること（権限）
    ログイン認証に成功し、以降のリクエストで本人として扱われる状態になること
    ログアウトログイン状態を終わらせること

    認証と認可はセットで語られますが、別物です。「ログインできた」＝認証成功、「管理者メニューを開ける」＝認可の結果、というイメージです。違いの詳細は 認証と認可の違い を参照してください。

    1.1 日常生活での例え

    • 認証：ホテルのフロントで身分証を見せ、「予約した本人です」と確認してもらう
    • 認可：確認後、自分の部屋の鍵だけをもらう（他の部屋には入れない）
    • ログイン状態：リストバンドを付けている間は、館内サービスを本人として使える
    • ログアウト：リストバンドを返却し、本人扱いをやめる

    1.2 本章で扱う主な機能

    • ログイン機能（ID とパスワードの確認）
    • パスワードの安全な保存
    • 自動ログイン（「ログイン状態を保持する」）
    • ログインフォームとエラーメッセージ
    • ログアウト機能

    これらは一見当たり前の機能ですが、実装を誤ると なりすまし（他人のふりをして操作されること）や パスワード漏洩 につながります。

    2.ログイン機能に対する攻撃

    ログイン画面は、攻撃者にとって「他人になりすます入口」です。代表的な攻撃を整理します。

    攻撃概要
    SQLインジェクションによるバイパスログイン判定の SQL を改ざんし、パスワードなしで通る
    SQLインジェクションによるパスワード入手DB からパスワード（やハッシュ）を抜き出す
    ログイン画面でのパスワード試行何度もログインを試し、パスワードを当てる
    ソーシャルエンジニアリング人をだましてパスワードを聞き出す
    フィッシング偽サイトに誘導し、本物だと思わせて入力させる

    2.1 SQLインジェクション攻撃によるログイン機能のバイパス

    ログイン処理が、入力をそのまま SQL に埋め込んでいると、パスワードを知らなくてもログインできてしまう ことがあります。

    ✕ 危険なイメージ

    入力: ID = admin' --
SQL: SELECT * FROM users WHERE id='admin' --' AND password='...'
→ パスワード条件がコメントアウトされ、admin で通る

    -- は SQL で「ここから後ろはコメント（無視される）」という記号です。「パスワードが正しいか」を見る前に、SQL の意味が壊れてしまいます。詳細は SQLインジェクションによる認証回避 を参照してください。

    2.2 SQLインジェクション攻撃によるパスワードの入手

    バイパスだけでなく、SQLインジェクションで ユーザーテーブル全体を読み出す 攻撃もあります（情報を盗む攻撃）。平文や弱いハッシュで保存されていると、そのまま悪用されます。

    2.3 ログイン画面に対するパスワード試行

    攻撃者が、ログイン画面から何度もパスワードを試す方法です。よくあるパスワード（password、123456 など）や、辞書に載っている単語を順に試します。後述の辞書攻撃・パスワードスプレーなどがここに含まれます。

    2.4 ソーシャルエンジニアリングによるパスワード入手

    技術的な脆弱性ではなく、人をだます 手法です。「サポートです。パスワードを教えてください」といった電話やメールで、本人から聞き出すイメージです。代表的な手口と対策は ソーシャルエンジニアリング：「人間の隙」を突く攻撃 を参照してください。

    2.5 フィッシングによるパスワード入手

    本物そっくりの偽ログイン画面を用意し、メールや SNS のリンクから誘導します。利用者が本物だと思って入力すると、攻撃者にパスワードが渡ります。

    1. 攻撃者が偽のログインページを用意する
    2. 「アカウント確認が必要です」などのメールでリンクを送る
    3. 利用者が偽サイトで ID・パスワードを入力する
    4. 攻撃者がその情報で本物のサイトにログインする

    フィッシング全般については 人を狙う攻撃 — フィッシングとソーシャルエンジニアリング も参照してください。

    2.6 なぜ危険か

    ログインを突破されると、攻撃者は その利用者本人として 操作できます。

    • 個人情報の閲覧・変更
    • 金銭やポイントの不正利用
    • 投稿・削除などの操作
    • 管理者アカウントなら、サービス全体の乗っ取り

    3.ログイン機能の基本対策

    攻撃の入口は多様ですが、アプリ側でまず押さえるべき対策は次のとおりです。

    3.1 SQLインジェクションなどセキュリティバグをなくす

    ログイン処理そのものに脆弱性があると、パスワードの強さとは無関係に突破されます。特に次は、ログイン周辺でよく問題になります。

    脆弱性ログインとの関係
    SQLインジェクション認証バイパスやパスワード漏洩
    セッションIDの固定化ログイン後に攻撃者の用意したセッションを使わされる
    クッキーのSecure属性不備HTTPS でない通信でセッションIDが盗まれる
    オープンリダイレクトログイン後の遷移先を偽サイトにし、フィッシングに悪用
    HTTPヘッダ・インジェクション応答ヘッダの改ざん、意図しない Cookie 設定など

    「パスワードを強くする」以前に、認証まわりの実装バグをなくす ことが前提です。セッション固定化は徳丸本第9章（74_セッション管理 で扱います）、オープンリダイレクト（第10章）と Cookie（第11章）は上の表のリンク先を参照してください。

    3.2 パスワードを予測困難なものにする

    パスワード試行や漏洩後の悪用を難しくするため、推測されにくいパスワード を使わせます。

    パスワードの文字種と桁数の要件

    要件の例意図
    十分な桁数（例：8 文字以上、できればそれ以上）総当たりの組み合わせ数を増やす
    文字種の混在（英大文字・小文字・数字・記号など）単純な単語だけのパスワードを減らす

    ただし、「記号を必ず 1 つ」などのルールだけでは、Password1! のような パターン化された弱いパスワード は防げません。桁数を長くする方が、効果が高いことが多いです。最新の推奨については パスワードポリシーの最新推奨 も参照してください。

    積極的なパスワードポリシーのチェック

    登録・変更時に、次のようなチェックを行う考え方です。

    • 短すぎるパスワードを拒否する
    • よくあるパスワード（password、123456 など）を拒否する
    • 漏洩パスワードリストに載っているものを拒否する
    • ユーザーIDと同じ・似すぎるものを拒否する

    「最低 8 文字で英数字混在」だけだと不十分なことがあるため、既知の弱いパスワードを弾く 積極的なチェックが有効です。

    4.基本的なアカウントロック

    パスワードが正しくても、何度も試せる と突破される可能性があります。試行を制限する仕組みが必要です。その基本が アカウントロック で、同じアカウントに対して、短時間にログイン失敗が続いたら、一時的にログインを拒否する方式です。

    1. ユーザーA のパスワードを連続で間違える
    2. 失敗が N 回に達する
    3. 一定時間、ユーザーA へのログインをロックする
    4. 時間経過後、または管理者が解除して再開
    メリット注意点
    特定アカウントへの総当たりを止めやすい攻撃者がわざと失敗させ、正規ユーザーをロックアウトできる（DoS：サービスを使えなくする妨害）
    実装が比較的わかりやすいロック条件・解除方法の設計が必要

    5.パスワード認証に対する攻撃のバリエーション

    アカウントロックだけでは防ぎきれない攻撃パターンがあります。

    攻撃名内容
    辞書攻撃よく使われるパスワードのリストを順に試す
    ジョーアカウント探索admin / admin のように、ID とパスワードが同じ・単純なアカウントを探す
    リバースブルートフォース攻撃1 つのパスワードを、多数の ID に対して試す
    パスワードスプレー攻撃よくある少数のパスワードを、多数のアカウントに少しずつ試す（ロックを避ける）
    パスワードリスト攻撃別サイトから漏洩した「ID とパスワードの組」を、そのまま試す（credential stuffing）

    5.1 辞書攻撃

    password、qwerty、iloveyou など、人間が選びがちなパスワードをまとめた辞書を使い、総当たり（ブルートフォース：あらゆる組み合わせを順に試す方法）より効率よく当てます。

    5.2 ジョーアカウント探索

    ID とパスワードが同じ、または test / test のような雑なアカウントを探す攻撃です。開発用・検証用アカウントが本番に残っていると狙われます。

    5.3 リバースブルートフォース攻撃

    通常のブルートフォースは「1 アカウントに対して多数のパスワード」です。リバースは逆で、1 つのパスワードを多数のアカウントに試す 方式です。アカウントロックが「アカウント単位」だと、ロックされにくいことがあります。

    5.4 パスワードスプレー攻撃

    Welcome1 や Password1 など、よくあるパスワードを少数用意し、多くのアカウントに ゆっくり 試します。失敗回数が分散するため、単純なアカウントロックをすり抜けやすいです。

    5.5 パスワードリスト攻撃

    別サービスから漏洩した「メールアドレスとパスワード」のリストを使い、同じ組み合わせでログインを試みます。利用者が パスワードを使い回している と成功します。近年特に多い攻撃です。

    6.パスワードを狙った攻撃への対策

    対策効果
    二段階認証（多要素認証）パスワードが漏れても、もう一つの要素がないとログインできない
    積極的なパスワードチェック弱い・漏洩済みパスワードの登録を防ぐ
    ログイン失敗率の監視スプレー攻撃やリスト攻撃の兆候を検知し、追加対策やアラートにつなげる
    アカウントロック（適切に設計）単一アカウントへの高速総当たりを抑止
    パスワードの使い回し防止の啓発リスト攻撃の成功率を下げる

    対策は 1 つに頼らず、次のように重ねます。

    1. 実装バグ（SQLi など）をなくす
    2. 強いパスワードを促し、弱いものを拒否する
    3. 試行を制限・監視する
    4. 二段階認証で「パスワードだけ」に依存しない

    二段階認証は、パスワードに加えて スマホアプリのワンタイムコード や SMS、ハードウェアトークン などを求める方式です。「知っているもの（パスワード）」に「持っているもの」を足すイメージです。各方式の違いは MFAの方式比較 で解説します。

    7.パスワードの保存方法

    サーバーは、ログイン時にパスワードを照合するため、何らかの形でパスワード情報を保持します。平文のまま保存してはいけません。 DB が漏洩すると、パスワードリスト攻撃への悪用や、本人の権限での投稿・更新・削除につながるからです。暗号化（復号できてしまう）ではなく、パスワード専用のハッシュ（bcrypt・Argon2 など）にソルトとストレッチングを組み合わせて保存するのが定石です。詳しくは次のページ パスワードの安全な保存 で解説します。

    8.自動ログイン

    「ログイン状態を保持する」にチェックを入れると、ブラウザを閉じてもログインしたままになる機能です。便利な一方、端末を他人に使われたときのリスク や、トークン漏洩時のなりすまし に注意が必要です。

    8.1 自動ログインの安全な実装方法

    代表的な方式は次の 3 つです。

    方式概要
    セッションの寿命を伸ばす通常より長いセッションタイムアウトにする
    トークンを使うログイン状態を示すトークンを Cookie などに持ち、サーバー側で検証する
    チケットを使う認証チケットを発行し、それで自動ログインする

    8.2 セッションの寿命を伸ばす方式

    通常のセッションはブラウザ終了や短時間で切れますが、自動ログインでは寿命を延ばします。PHP の例では、session_set_cookie_params でセッションID クッキーの Expires（Cookie の有効期限）を設定します。

    実装のポイント（イメージ）

    • セッションタイムアウトを 1 週間などに伸ばす
    • セッションID クッキーの Expires 属性を 1 週間後に設定する
    • タイムアウト時間はセッション変数 Timeout に保持する
    • タイムアウト時刻はセッション変数 Expires に保持する
    項目役割
    Timeout「何秒（何日）で切るか」という長さ
    Expires「いつ切れるか」という時刻

    単純でわかりやすい一方、セッションID が長い間有効 になるため、盗まれたときの被害期間が長くなります。また、サーバー側のセッション保存が増えることもあります。

    8.3 トークンによる自動ログイン

    セッションとは別に、自動ログイン用トークン（ログイン済みであることを示すランダムな文字列）を発行する方式です。

    ログイン時

    1. 通常どおり認証する
    2. 十分な長さのランダムなトークンを生成する
    3. トークン（のハッシュ）をサーバー側 DB に保存する
    4. トークンを Cookie などにセットする（Secure、HttpOnly など適切な属性）

    次回アクセス時

    1. セッションが切れていても、トークン Cookie があれば読む
    2. DB 上のトークンと照合する
    3. 正しければ、その利用者としてセッションを開始する（自動ログイン）

    ログアウト時

    1. 通常のセッションを破棄する
    2. 自動ログイン用トークンも DB から削除（または無効化）する
    3. クライアント側のトークン Cookie も削除する

    トークンは 推測困難なランダム値 にし、可能なら DB にはハッシュだけを保存します。漏洩時に備え、トークンの定期的な再発行や、端末ごとの管理も有効です。Cookie の属性（Secure・HttpOnly）は Cookie はどう付いていくのか を参照してください。

    8.4 認証チケットによる自動ログイン

    認証チケットは、トークンと同様に「この人は以前ログイン済み」と示す証明書のようなデータです。署名付きのデータをクライアントに持たせる方式など、実装には幅があります。本書の文脈では、サーバー側で検証可能なチケット／トークンを用いる自動ログイン として理解するとよいです。

    クライアントだけで完結する「改ざん可能な覚え書き」だけに頼ると危険です。サーバー側で正当性を検証できる ことが重要です。

    8.5 トークン方式のメリット

    メリット説明
    自動ログインを選ばない利用者に影響しない通常セッションの寿命を全体で延ばさなくてよい
    複数端末から一斉ログアウトできるサーバー側のトークンをまとめて無効化すればよい
    管理者が特定利用者のログインをキャンセルできるDB 上のトークンを消す・無効にする
    クライアント側に秘密情報が渡らない設計にできるパスワード自体は送らず、トークンだけを持つ。解析されてもパスワードは出ない

    セッション寿命を全体で延ばす方式より、制御しやすく、影響範囲を限定しやすい のがトークン方式の利点です。

    9.ログインフォーム

    ログイン画面の作り方にも、基本的な注意点があります。

    要件理由
    パスワード入力欄はマスク表示肩越しに読まれる（ショルダーハッキング）を防ぐ。HTML では type="password"
    HTTPS を利用通信経路での盗聴・改ざんを防ぐ。パスワードやセッションID の平文送信を避ける

    ◯ 良い例のイメージ（ページ全体を HTTPS で提供する）

    <form method="post" action="/login">
  <input type="text" name="id">
  <input type="password" name="password">
  <button type="submit">ログイン</button>
</form>

    マスク表示は「画面上で見えない」だけなので、端末にキーロガー（キー入力を盗み記録するソフト）がある場合などは防げません。あくまで基本的な保護です。HTTPS は、ログインページだけでなく、ログイン後の全ページ でも使うのが安全です（セッションID の保護）。

    10.エラーメッセージの要件

    ログイン失敗時のメッセージは、攻撃者にヒントを与えすぎない ことが重要です。

    10.1 ID とパスワードのどちらが間違いか分かるとまずい理由

    ✕ 悪い例

    「ユーザーIDが存在しません」
「パスワードが違います」

    ◯ 良い例

    「ユーザーIDまたはパスワードが正しくありません」

    悪い例だと、攻撃者は次のように情報を得られます。

    分かること悪用
    ID が存在するかどうか登録済みメールアドレスの洗い出し、ジョーアカウント探索の効率化
    パスワードだけが違うことその ID に対するパスワード試行に集中できる

    エラーメッセージは、正規利用者には少し不便でも、ID とパスワードのどちらが原因か分からない 表現に統一します。パスワード再設定の有無などで ID の存在が分かる場合もあるため、そちらの設計もあわせて検討します。

    11.ログアウト機能

    ログアウトは、「もう本人として扱わない」ための処理です。実装が中途半端だと、なりすましが続く ことがあります。

    要件理由
    POST メソッドでリクエストするログアウトはサーバー状態を変える副作用のある操作だから。<a href="/logout"> のような GET は、画像埋め込みや prefetch（ブラウザによるリンク先の先読み）で意図せず実行されうる
    セッションを破棄するサーバー側のログイン状態を消す。Cookie を消すだけでは不十分な場合がある
    必要な場合は CSRF 対策の対象とする罠ページからログアウトさせ、利用者を妨害する（または再ログインを誘う）攻撃を防ぐ

    ログアウト処理のイメージ

    1. POST でログアウトを受け付ける（CSRF トークンを検証）
    2. サーバー側セッションを破棄する
    3. 自動ログイン用トークンがあれば無効化する
    4. クライアント側のセッション Cookie・トークン Cookie を削除する
    5. ログイン画面などへ誘導する

    「画面上はログイン前に戻ったように見えるが、セッションID はまだ有効」という状態は危険です。サーバー側でセッションを確実に破棄する ことが本質です。CSRF の詳細は CSRF を参照してください。

    12.まとめ

    テーマ本質対策の要点
    ログインへの攻撃なりすましの入口になるSQLi 等のバグ除去、試行制限、二段階認証
    パスワードポリシー弱いパスワードは当てられる十分な長さ、弱い・漏洩済みパスワードの拒否
    パスワード保存DB 漏洩時に悪用されるパスワード用ハッシュ＋ソルト＋ストレッチング（暗号化は非推奨）
    自動ログイン長期のなりすましリスクトークン方式が制御しやすい。ログアウトで無効化
    フォーム・エラー漏洩と情報収集を助けるマスク、HTTPS、曖昧なエラーメッセージ
    ログアウトログイン状態の終了POST、セッション破棄、必要なら CSRF 対策

    認証安全の基本

    1. ログイン処理の脆弱性（SQLi、セッション固定化など）をなくす
    2. 予測困難なパスワードを促し、弱いものを拒否する
    3. 試行の制限・監視と、可能なら二段階認証を入れる
    4. パスワードは専用ハッシュ（ソルト＋コスト）で保存し、平文や単純な暗号化は使わない
    5. 自動ログインはトークン等で制御し、ログアウトで確実に無効化する
    6. フォームは HTTPS とマスク表示、エラーは ID／パスワードを区別しない
    7. ログアウトは POST で行い、サーバー側セッションを破棄する

    13.理解度チェック

    Q1. ID 欄に admin' -- と入力するとパスワードなしでログインできてしまうのはなぜですか？

    入力がそのまま SQL に埋め込まれ、-- 以降がコメントとして無視されるため、AND password='...' の条件が消えてしまうからです。根本対策はプレースホルダで SQL を組み立てることです。

    Q2. アカウントロックの注意点を 2 つ挙げてください。

    ① 攻撃者がわざと失敗させて正規ユーザーをロックアウトできる（DoS）こと、② ロック条件・解除方法の設計が必要なことです。また、アカウント単位のロックはリバースブルートフォースやパスワードスプレーをすり抜けられます。

    Q3. パスワードスプレー攻撃が単純なアカウントロックをすり抜けやすいのはなぜですか？

    よくある少数のパスワードを多数のアカウントにゆっくり試すため、1 アカウントあたりの失敗回数が少なく、ロックの閾値に達しにくいからです。ログイン失敗率の監視や二段階認証で補います。

    Q4. パスワードリスト攻撃が成功するのはどんなときですか？ 有効な対策は？

    利用者が別サービスと同じ ID・パスワードを 使い回している ときです。二段階認証、漏洩済みパスワードの登録拒否、失敗率の監視、使い回し防止の啓発が有効です。

    Q5. 自動ログインで、セッション寿命を延ばす方式よりトークン方式が優れている点は？

    自動ログインを選ばない利用者に影響しない、複数端末から一斉ログアウトできる、管理者が特定利用者のログインをキャンセルできる、クライアント側にパスワードなどの秘密情報が渡らない、といった点です。制御しやすく影響範囲を限定できます。

    Q6. ログイン失敗時に「パスワードが違います」と表示するのはなぜよくないのですか？

    その ID が存在することが攻撃者に分かり、登録済みアドレスの洗い出しや、その ID へのパスワード試行の集中に使われるからです。「ユーザーIDまたはパスワードが正しくありません」に統一します。

    Q7. ログアウトを <a href="/logout">（GET）で実装すると何が問題ですか？

    ログアウトはサーバーの状態を変える操作なので、GET だと画像埋め込みや prefetch で意図せず実行されうるからです。POST で受け付け、必要に応じて CSRF 対策をし、サーバー側のセッションと自動ログイン用トークンを確実に破棄します。
