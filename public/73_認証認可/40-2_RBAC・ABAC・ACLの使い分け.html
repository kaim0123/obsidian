    40 認可モデル

    RBAC・ABAC・ACLの使い分け

    ログインに成功して「誰か」が分かったあと、そのユーザーがどのリソースにアクセスでき、どの操作をしてよいか を決めるのが 認可 です。このページでは、実務でよく使われる 3 つの認可モデル RBAC・ABAC・ACL の考え方と向き・不向きを整理し、さらにそれを実際に「強制」する仕組みである OAuth 2.0 や JWT との違いまでを、初心者向けにまとめます。

    もとにしたノート：40_認可モデル/02_RBAC・ABAC・ACLの使い分け（Hayk Simonyan）

    このページで分かること

    • 認証と認可の違い（GitHub のリポジトリ権限を例に）
    • RBAC（ロールベース）・ABAC（属性ベース）・ACL（アクセス制御リスト）の考え方
    • それぞれが向いている場面と限界、モデル選びの目安
    • OAuth 2.0・JWT は「モデル」ではなく、認可を運ぶ・強制する「仕組み」であること
    • 実装時のチェックリスト

    1.認可とは：認証の次の段階

    認可（Authorization） は、認証（Authentication） の次に行われる段階です。ログインのリクエストが承認され、システムが「このユーザーは誰か」を把握したら、次は そのユーザーが何をしてよいか を決めます。アクセスしてよいリソースや操作だけでなく、拒否される操作 もあわせて定義することで、システムのセキュリティとプライバシーを守ります。

    段階答える問い例（GitHub）
    認証誰か？ログインしてよいか？ユーザー名・パスワード、SSO で本人確認
    認可ログイン後、何ができるか？リポジトリへの read / write / admin

    認証と認可の違いそのものは 認証と認可の違い で詳しく扱っています。ここでは GitHub のリポジトリを例に、「同じリポジトリでもユーザーごとに権限が違う」様子だけ確認します。

    • ユーザー A：write のみ → コードの push は可能だが、設定変更や削除は不可（動画の例では pull request 作成も不可と説明）
    • ユーザー B：read のみ → 閲覧のみ
    • 管理者：フルコントロール → 設定変更、リポジトリ削除、他ユーザーの権限管理など

    この「ユーザーごとに異なるアクセス制御」を体系的に管理するための考え方が、次に紹介する 認可モデル です。

    2.3 つの主要な認可モデル（概要）

    モデル略称考え方代表例
    ロールベースRBACユーザーに ロール（役割）を付与し、ロールごとに権限セットを定義GitHub、Jira、CMS、チーム管理ツール
    属性ベースABACユーザー・リソース・環境の 属性と条件 で許可／拒否を判定部門・機密区分・時間帯・端末種別などの組み合わせ
    アクセス制御リストACLリソース単位 に「誰が何をできるか」のリストを持つGoogle ドキュメントの共有設定

    3 つの違いは「何を起点に権限を決めるか」です。RBAC は ユーザー → ロール → 権限、ABAC は 属性 → ポリシー → 判定、ACL は リソース → そのリソースに付いた利用者リスト という流れで考えます。

    いずれのモデルにもトレードオフ（一方を取ると他方を失う関係）があり、システムの要件（規模、柔軟性、運用コスト）に応じて選びます。また、本番システムでは単一モデルに限定せず、複数のモデルを組み合わせる のが一般的です。たとえば「RBAC を土台に ABAC で細かい条件を足す」「特定のリソースだけ ACL で共有する」といった ハイブリッド がよく見られます。

    3.RBAC（Role-Based Access Control）

    最も普及している 認可モデルです。ユーザーに ロール を割り当て、各ロールには決められた権限のセットがあります。つまり ユーザー → ロール → 権限 という階層で管理します。

    3.1 典型的なロール例

    ロールできること（概略）できないこと（概略）
    Admin作成・読取・更新・削除、他ユーザー・ロールの管理（ポリシー次第）
    Editorコンテンツの作成・読取・更新削除、他ユーザーの管理
    Viewer読取のみ作成・更新・削除

    Admin は通常すべてのリソースにフルアクセスでき、Editor はそれより少し狭く、Viewer はデータを読むことしかできません。

    3.2 向いている場面

    • 組織内の役割が比較的固定している（管理者／編集者／閲覧者など）
    • ダッシュボード、CMS（コンテンツ管理システム）、社内ツール、開発プラットフォーム。動画では GitHub、Stripe のダッシュボード、チーム管理ツールなど、日常的に使うアプリが例に挙げられています
    • 権限の説明・監査が「ロール名」で分かりやすいことが重要

    3.3 限界

    RBAC が苦手なこと

    • 「同じ Editor でも、部門が HR のときだけこのファイル」といった 細かい条件 には不向きです
    • 条件ごとにロールを作っていくとロールが増えすぎ、ロール爆発（role explosion） になって運用が難しくなります

    4.ABAC（Attribute-Based Access Control）

    ロールを超えて、属性（attributes）とポリシー でアクセスを決めるモデルです。属性とは「部門」「機密区分」「時刻」のような、ユーザーやリソースや状況が持つ性質のことです。データベースにあるユーザーやリソースの情報を確認し、その属性に応じて許可または拒否します。RBAC より柔軟ですが、設計・運用は複雑になります。

    4.1 判定に使う属性の種類

    1. ユーザー属性：部門（例：HR）、年齢、雇用形態、クレーム（トークンに書かれたユーザー情報）上のグループなど
    2. リソース属性：機密区分（internal / public）、所有者、分類ラベルなど
    3. 環境属性：時刻、地理位置、デバイス種別、IP レンジなど

    4.2 ポリシーの例

    動画のイメージ

    ユーザーの department が HR かつ リソースの分類が internal のときだけ、read または write を許可する。

    複数の条件を AND / OR で組み合わせ、read と write を個別に指定できます。RBAC と 併用 することも多く、ロールで大枠を決め、ABAC で例外や細部を決めます。

    4.3 向いている場面

    • 同じロールでも、データの機密度・部門・時間帯で制限が変わる
    • コンプライアンスや ゼロトラスト（社内・社外を問わず毎回確かめる考え方）寄りの「常に条件付き」アクセス

    4.4 注意点

    ABAC の運用で気をつけること

    • ポリシー管理（誰がどのルールを書けるか、テスト、バージョン管理）が必須です
    • ルールが増えると 競合・矛盾（ある条件では許可、別の条件では拒否）の検出が難しくなります
    • デバッグ時に「なぜ拒否されたか」を説明しづらいことがあります

    5.ACL（Access Control List）

    各リソース に対して、「どの主体（ユーザー／グループ）がどの権限を持つか」のリストを持つモデルです。RBAC のように「システム全体のロール表」を持つのではなく、リソース中心 に考えます。

    5.1 動作イメージ（ドキュメント 1 件）

    ユーザーこのドキュメントへの権限
    Aliceread のみ
    Bobread + write
    その他アクセスなし

    ACL で管理するのは次の 2 点です。

    1. 誰が このリソースにアクセスできるか
    2. その主体ごとに どの操作 が許可されるか

    5.2 代表例：Google ドライブ

    1 つの Google ドキュメントを、同僚 A には閲覧のみ、同僚 B には編集・コメント可、と設定する 共有リンク／共有設定 が ACL の典型です。リソース単位の細かい制御に優れています。

    5.3 向いている場面

    • ファイル、フォルダ、レコード単位で「この人だけ編集可」が必要
    • ユーザー数・オブジェクト数が中規模で、リストの運用が現実的

    5.4 限界

    ACL が苦手なこと

    • ACL は非常に個別的でユーザー中心のため、ユーザー・オブジェクトが 数百万規模 になると、リストの更新・同期・クエリのコストが重くなります（Google ドライブのように大規模でも可能ですが、慎重な設計とインフラが必要です）
    • 組織全体で一貫したポリシーを ACL だけで揃えるのは難しいです

    6.モデル選びの目安

    要件第一候補補足
    社内アプリで役割が明確RBACAdmin / Member / Guest など
    部門・機密・時間で細かく変えるABAC（または RBAC + ABAC）ポリシーエンジン（OPA、Cedar 等）の検討
    1 ファイル・1 レコード単位の共有ACLドキュメント、カレンダー、共有フォルダ
    大規模 SaaS多くは RBAC + リソース ACL の併用GitHub もロール＋リポジトリ単位の権限

    ポリシーエンジン は、認可のルール（ポリシー）をアプリのコードから切り離して書き、「このリクエストは許可か拒否か」を評価してくれる仕組みです。OPA（Open Policy Agent）や Cedar がその例です。

    7.認可を「強制」する仕組み（モデルではない）

    動画では、認可の モデル（何を許可するかの設計）と、それを運ぶ メカニズム（トークン・プロトコル）をはっきり分けています。ここを混同しないことが大切です。

    7.1 OAuth 2.0：委任された認可（Delegated Authorization）

    第三者アプリ が、ユーザーの代わりに別サービスのリソースにアクセスするときの プロトコル です。認可モデルそのものではなく、安全に権限を委譲するための枠組み です。

    例：Vercel が GitHub リポジトリにアクセスする

    ✕ 危険なやり方

    GitHub のユーザー名・パスワードを Vercel に渡す → 相手が何をするか分からないまま、第三者にフル権限を渡すことになります。

    ○ OAuth 2.0 のやり方

    ユーザーが GitHub 上で「どのリポジトリに」「どの操作（read / push 等）まで」を承認 → GitHub が アクセストークン を発行 → Vercel はそのトークンの範囲内だけで操作します。

    OAuth 2.0 は、このトークンを 安全に発行・検証するフロー を定義します。スコープ（読取のみ、特定リポジトリのみ、削除不可など、許可する範囲）を、ユーザーが承認した内容に限定できます。フローの詳細は OAuth 2.0の仕組み、スコープについては 通行証の中身：範囲 を参照してください。

    7.2 JWT / Bearer トークン：リクエストごとに認可情報を運ぶ

    認証に成功すると、多くの API は JWT（JSON Web Token：署名付きの JSON 形式トークン）または Bearer トークンをクライアントに返します。以降のリクエストでは Authorization: Bearer <token> ヘッダーで送り、サーバーが検証します。Bearer と JWT の仕組み自体は トークンベース認証：Bearer と JWT で解説しています。

    トークンに含めがちな情報（クレーム）の例は次のとおりです。

    • ユーザー ID
    • ロール（admin / editor など）
    • スコープ（アクセス可能な API や操作の範囲）
    • 有効期限（exp）
    • 発行者（iss）

    サーバーはトークンを検証したうえで、RBAC / ABAC などの ポリシーに照らして 最終的に許可／拒否します。

    7.3 重要な区別

    種類役割
    トークン（JWT 等）身元・ロール・スコープなどの クレームを運ぶメカニズム
    認可モデル（RBAC / ABAC / ACL）「このユーザーは何をしてよいか」を決める ルールの設計

    ここがポイント

    トークンに role: editor が入っていても、そのロールが何を意味するか は RBAC の定義側で決めます。トークンだけでは認可設計は完結しません。

    8.実装時のチェックリスト

    1. 認証のあと に認可を必ず挟む（「ログインできた＝全部できる」にしない）
    2. まず RBAC で大枠を設計し、必要なら ABAC や ACL を足す
    3. 外部連携は OAuth 2.0 でパスワード共有を避け、スコープを最小限にする（考え方は 最小権限とデータ最小化 を参照）
    4. API では 短命アクセストークン ＋ サーバー側でのポリシー評価を組み合わせる
    5. 拒否時は理由が追えるよう、ログ・監査（誰が・何に・なぜ拒否されたか）を残す

    9.まとめ

    認可は「入場許可（認証）」の先で「館内で何ができるか」を制御する仕組みです。

    RBAC

    • ユーザー → ロール → 権限
    • 最も普及、説明・監査しやすい
    • 細かい条件は苦手、ロール爆発に注意

    ABAC

    • ユーザー・リソース・環境の属性 ＋ ポリシー
    • 柔軟だが複雑
    • ポリシー管理・矛盾の検出が課題

    ACL

    • リソースごとに「誰が何をできるか」
    • 1 件単位の共有に強い（Google ドライブ）
    • 大規模化・全体の一貫性は難しい
    • 本番では単一モデルにこだわらず、RBAC を土台に ABAC や ACL を組み合わせる のが一般的です
    • OAuth 2.0 や JWT は権限情報を安全に渡すための メカニズム で、何を許可するかは モデル側 で定義します

    10.理解度チェック

    Q1. 認証と認可は、それぞれどんな問いに答えますか？

    認証は「誰か？ログインしてよいか？」、認可は「ログイン後、何ができるか？」に答えます。認可は認証の次の段階です。

    Q2. RBAC で管理する 3 つの階層は何ですか？ また RBAC の代表的な限界を 2 つ挙げてください。

    ユーザー → ロール → 権限 です。限界は、「同じ Editor でも部門が HR のときだけ」のような 細かい条件に不向き なことと、ロールが増えすぎる ロール爆発 で運用が難しくなることです。

    Q3. ABAC が判定に使う属性の 3 種類と、それぞれの例を答えてください。

    ユーザー属性（部門、年齢、雇用形態など）、リソース属性（機密区分、所有者、分類ラベルなど）、環境属性（時刻、地理位置、デバイス種別、IP レンジなど）です。

    Q4. ACL が RBAC と違うのはどこですか？ 代表例も挙げてください。

    RBAC が「システム全体のロール表」で管理するのに対し、ACL は リソースごと に「誰がどの操作をできるか」のリストを持つ、リソース中心のモデルです。代表例は Google ドキュメントの共有設定（A は閲覧のみ、B は編集・コメント可）です。

    Q5. 「部門・機密区分・時間帯でアクセスを細かく変えたい」場合と「1 ファイル単位で共有したい」場合、第一候補はそれぞれどのモデルですか？

    前者は ABAC（または RBAC + ABAC）、後者は ACL です。大規模 SaaS では RBAC + リソース ACL の併用が多く見られます。

    Q6. 「JWT に role: editor を入れたので認可は完成した」という考えはなぜ不十分ですか？

    JWT はクレームを 運ぶメカニズム にすぎず、editor が何をしてよいかを決めるのは RBAC などの 認可モデル の定義だからです。サーバーはトークンを検証したうえで、ポリシーに照らして許可／拒否を判断する必要があります。

    Q7. Vercel に GitHub リポジトリへのアクセスを許すとき、パスワードを渡す代わりに OAuth 2.0 で何をしますか？

    ユーザーが GitHub 上で「どのリポジトリに」「どの操作まで」を承認し、GitHub が発行した アクセストークン を Vercel に渡します。Vercel はそのトークンのスコープの範囲内だけで操作できます。
