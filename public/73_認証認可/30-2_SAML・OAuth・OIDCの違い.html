    SAML・OAuth・OIDCの違い

    「Google でログイン」や「会社のアカウントで社内システムにまとめてログイン」の裏側では、SAML・OAuth 2.0・OpenID Connect（OIDC） という 3 つのプロトコルが使われています。名前はよく並べて出てきますが、目的もデータ形式も違います。このページでは、それぞれの仕組み・役割・メリットとデメリットを初心者向けに整理し、最後に「どれを選べばよいか」までをまとめます。

    もとにしたノート：30_フェデレーション/03_SAML_OAuth2_OpenIDConnectの基礎

    このページで分かること

    • プロトコルとは何か、なぜ認証にプロトコルが必要なのか
    • SAML：エンタープライズ向けの XML ベースの認証プロトコル
    • OAuth 2.0：認証ではなく認可 のプロトコルであること
    • OpenID Connect：OAuth 2.0 に「身元証明（ID トークン）」を足した認証プロトコル
    • 3 つの比較と、用途別の使い分け

    1.プロトコルとは

    プロトコル は、異なるシステム間で情報をやり取りする際の「約束事」や「ルール」です。

    1.1 簡単な例え

    • プロトコル ＝ 共通の言語とルール
      • 日本語で話す、英語で話す → 言語が違うと通じない
      • 認証プロトコル ＝ 認証の方法を統一したルール

    1.2 なぜプロトコルが必要か

    異なるシステム間で連携するため

    • Google アカウントで Web サイトにログイン
    • 企業の複数システムに 1 回のログインでアクセス

    標準化により実装が簡単になる

    • 各社が独自の方法を開発する必要がない
    • 既存のライブラリやツールが使える

    そもそも「認証」と「認可」の違いがあいまいな場合は、先に 認証と認可の違い を読んでおくと、このページが理解しやすくなります。

    2.SAML（Security Assertion Markup Language）

    2.1 SAML とは

    SAML（Security Assertion Markup Language） は、主にエンタープライズ（企業）向けの認証プロトコルです。XML ベースで、企業の シングルサインオン（SSO）（一度のログインで複数のシステムを使えるようにする仕組み）で広く使われています。

    • SAML ＝ 企業の社員証
      • 社員証を見せれば、複数の部署や施設に入れる
      • 各部署で個別に身分証明をする必要がない

    2.2 SAML の特徴

    特徴内容
    XML ベースデータ形式が XML
    エンタープライズ向け主に企業の内部システムで使用
    セキュリティが高いXML 署名と暗号化をサポート
    Web アプリケーション向け主にブラウザベースのアプリで使用

    2.3 SAML の仕組み

    1. ユーザーがアプリケーションにアクセス
    2. アプリケーションが ID プロバイダにリダイレクト
    3. ユーザーが ID プロバイダでログイン
    4. ID プロバイダが SAML アサーション（XML で書かれた「この人は本人です」という証明書）を発行
    5. アプリケーションが SAML アサーションを検証
    6. 認証成功 → アプリケーションにアクセス可能

    この流れを図にしたものは SSO の仕組み（SAML の場合）（パスワード・MFA・暗号化の基礎）にあります。SSO そのものの考え方は シングルサインオン（SSO）とアイデンティティプロトコル（ログイン方式と認証の概念）も参照してください。

    2.4 SAML の主要な役割

    役割説明例
    ID プロバイダ（IdP）ユーザーを認証する側Okta、Microsoft Azure AD
    サービスプロバイダ（SP）ユーザーがアクセスしたいアプリケーションSalesforce、Slack

    2.5 SAML のメリット・デメリット

    メリット

    • エンタープライズで標準化されている
    • セキュリティが高い（XML 署名と暗号化）
    • 一元管理が可能（企業の ID プロバイダで管理）
    • コンプライアンス対応（企業のセキュリティポリシーに準拠）

    デメリット

    • 実装が複雑（XML ベースで複雑）
    • モバイル対応が弱い（主に Web アプリ向け）
    • 設定が大変（証明書の管理、メタデータの交換など）
    • デバッグが困難（XML の構造が複雑）

    2.6 SAML の使用例

    • 企業の内部システム（複数のアプリケーション）
    • クラウドサービスのエンタープライズ版（Salesforce、Slack など）
    • 教育機関のシステム

    3.OAuth 2.0

    3.1 OAuth 2.0 とは

    OAuth 2.0 は、認可（Authorization） のプロトコルです。ユーザーに代わって、アプリケーションがリソースにアクセスする権限を取得します。

    • OAuth 2.0 ＝ 代理アクセス権
      • 例：写真アプリが Google フォトの写真にアクセスする権限
      • ユーザーは「このアプリに写真を見る権限を与える」と許可
      • アプリはユーザーのパスワードを知らなくてもアクセス可能

    重要なポイント

    OAuth 2.0 は認証（Authentication）のプロトコルではありません。認可（Authorization）のプロトコルです。

    • 認証（Authentication）：「この人は誰か？」を確認
    • 認可（Authorization）：「この人は何をして良いか？」を決定

    ただし、OAuth 2.0 を拡張して認証にも使われることが多いです（その代表が次章の OpenID Connect です）。

    3.2 OAuth 2.0 の特徴

    特徴内容
    認可プロトコルリソースへのアクセス権限を管理
    トークンベースアクセストークン（API を呼ぶための「通行証」）を使用
    広く使用されているGoogle、Facebook、GitHub など多くのサービスで使用
    モバイル対応モバイルアプリでも使用可能

    3.3 OAuth 2.0 の仕組み（認可コードフロー）

    1. ユーザーがアプリケーションにアクセス
    2. アプリケーションが認証サーバーにリダイレクト
    3. ユーザーが認証サーバーでログイン
    4. ユーザーが「このアプリにアクセス権限を与える」と許可
    5. 認証サーバーが 認可コード（一時的な引換券）を発行
    6. アプリケーションが認可コードをアクセストークンと交換
    7. アプリケーションがアクセストークンでリソースにアクセス

    このページでは他の 2 つとの違いに絞ります。各ステップで何が送られるか、PKCE がなぜ必要かといった詳しい流れは OAuth 2.0の仕組み で解説しています。流れの図は OAuth 2.0：認可フレームワーク（ログイン方式と認証の概念）にもあります。

    3.4 OAuth 2.0 の主要な役割

    役割説明例
    リソースオーナー（Resource Owner）ユーザー本人。リソースの所有者—
    クライアント（Client）ユーザーに代わってリソースにアクセスするアプリケーション写真アプリ、SNS アプリ
    認証サーバー（Authorization Server）アクセストークンを発行するサーバーGoogle、Facebook
    リソースサーバー（Resource Server）保護されたリソースを提供するサーバーGoogle フォト、Facebook の API

    ※ Authorization Server は、仕様の訳語としては「認可サーバー」と呼ばれることも多いです。

    3.5 OAuth 2.0 のフロー種類

    OAuth 2.0 には、アプリの種類に合わせて複数の「フロー」（トークンを手に入れるまでの手順）があります。

    フロー用途特徴補足
    認可コードフロー（Authorization Code Flow）Web アプリケーション（サーバーサイド）最も安全なフロー使用例：Next.js、Django、Rails などの Web アプリ
    インプリシットフロー（Implicit Flow）シングルページアプリケーション（SPA）アクセストークンが直接返されるセキュリティ上の理由で非推奨（PKCE 推奨）
    クライアントクレデンシャルフロー（Client Credentials Flow）サーバー間の通信ユーザー認証なしでアクセストークンを取得使用例：API 間の通信
    リソースオーナーパスワードクレデンシャルフロー信頼できるアプリケーションユーザー名とパスワードを直接送信セキュリティ上の理由で非推奨
    PKCE（Proof Key for Code Exchange）モバイルアプリ、SPA認可コードフローをより安全にしたものモバイルアプリや SPA では PKCE を使用

    各フローの詳しい手順とリフレッシュトークンの扱いは OAuth 2.0の仕組み を参照してください。

    3.6 OAuth 2.0 のメリット・デメリット

    メリット

    • 広く使用されている（Google、Facebook、GitHub など）
    • モバイル対応（モバイルアプリでも使用可能）
    • 柔軟性（複数のフローを選択可能）
    • セキュリティ（パスワードを共有しない）

    デメリット

    • 実装が複雑（複数のフロー、トークンの管理など）
    • 認証ではない（認可のプロトコル、認証には拡張が必要）
    • トークンの管理が必要（有効期限、リフレッシュなど）

    3.7 OAuth 2.0 の使用例

    • Google アカウントでログイン
    • Facebook アカウントでログイン
    • GitHub アカウントでログイン
    • 写真アプリが Google フォトにアクセス
    • SNS アプリが Twitter のタイムラインを取得

    「○○アカウントでログイン」は OAuth 2.0 の仕組みの上で動いていますが、「誰がログインしたか」を確かめる部分は、多くの場合 OAuth 2.0 を拡張した OpenID Connect が担っています（4.6 の使用例も参照）。

    4.OpenID Connect（OIDC）

    4.1 OpenID Connect とは

    OpenID Connect（OIDC） は、OAuth 2.0 を拡張した認証プロトコル です。OAuth 2.0 が認可（Authorization）のプロトコルだったのに対し、OpenID Connect は認証（Authentication）のプロトコルです。

    • OpenID Connect ＝ OAuth 2.0 ＋ 身元証明
      • OAuth 2.0：「このアプリにアクセス権限を与える」
      • OpenID Connect：「このアプリにアクセス権限を与える」＋「この人は○○です」という情報も提供

    4.2 OpenID Connect の特徴

    特徴内容
    OAuth 2.0 ベースOAuth 2.0 の上に構築されている
    認証プロトコルユーザーの身元を確認する
    ID トークンユーザー情報を含む JWT（署名付きの JSON をつめた文字列）トークンを発行
    モダンモバイルアプリ、SPA、Web アプリすべてに対応

    JWT そのものの形や Bearer トークンとの関係は トークンベース認証：Bearer と JWT（ログイン方式と認証の概念）で扱っています。

    4.3 OpenID Connect の仕組み

    1. ユーザーがアプリケーションにアクセス
    2. アプリケーションが認証サーバーにリダイレクト
    3. ユーザーが認証サーバーでログイン
    4. ユーザーが「このアプリにアクセス権限を与える」と許可
    5. 認証サーバーが認可コードを発行
    6. アプリケーションが認可コードを ID トークン ＋ アクセストークン と交換
    7. アプリケーションが ID トークンからユーザー情報を取得
    8. 認証成功 → アプリケーションにアクセス可能

    手順の 1〜6 は OAuth 2.0 の認可コードフローとほぼ同じで、違いは ⑥ で ID トークンも返ってくること と、⑦ でアプリがそれを検証して「誰か」を確定すること です。ID トークンに入っていない情報が必要なときは、アクセストークンを使って OP の UserInfo エンドポイント（ユーザー情報を返す API）に問い合わせることもできます。

    4.4 OpenID Connect の主要な役割

    役割説明OAuth 2.0 でいうと例
    エンドユーザー（End User）ユーザー本人リソースオーナー—
    RP（Relying Party）ユーザーを認証したいアプリケーションクライアント—
    OP（OpenID Provider）ユーザーを認証するサーバー認証サーバーGoogle、Auth0、AWS Cognito

    4.5 OpenID Connect のトークン

    トークン形式内容用途
    ID トークン（ID Token）JWT（JSON Web Token）ユーザー情報（名前、メールアドレスなど）ユーザーの認証情報を提供
    アクセストークン（Access Token）JWT または 不透明な文字列（中身に意味を持たないランダムな文字列）リソースへのアクセス権限API へのアクセス
    リフレッシュトークン（Refresh Token）不透明な文字列新しいアクセストークンを取得するためのトークンアクセストークンの更新

    アクセストークンとリフレッシュトークンの関係は アクセストークンとリフレッシュトークン（ログイン方式と認証の概念）でも説明しています。

    4.6 OpenID Connect のメリット・デメリット

    メリット

    • 認証と認可の両方（OAuth 2.0 の認可 ＋ 認証機能）
    • モダンなプロトコル（モバイル、SPA、Web アプリすべてに対応）
    • 標準化されている（広く使用されている）
    • セキュリティ（JWT、PKCE などをサポート）
    • 実装が比較的簡単（OAuth 2.0 よりシンプル）

    デメリット

    • OAuth 2.0 より新しい（一部の古いシステムでは未対応）
    • 実装の複雑さ（トークンの管理、検証など）

    使用例：

    • Google アカウントでログイン（OpenID Connect を使用）
    • Auth0 でログイン
    • AWS Cognito でログイン
    • Microsoft アカウントでログイン
    • モバイルアプリのログイン

    6.使い分けのガイド

    6.1 用途別の選び方

    用途推奨理由例
    1. エンタープライズ SSO（企業の内部システム）SAML企業で標準化されている、セキュリティが高いOkta、Microsoft Azure AD を使用した SSO
    2. API アクセス（アプリが API にアクセス）OAuth 2.0API アクセスに特化している写真アプリが Google フォト API にアクセス
    3. ユーザーログイン（Web アプリ、モバイルアプリ）OpenID Connect認証と認可の両方をサポート、モダンGoogle アカウントでログイン、Auth0 でログイン
    4. Next.js アプリケーションOpenID Connectモダンなプロトコル、実装が比較的簡単NextAuth.js（Next.js の認証ライブラリ）は OpenID Connect をサポート

    社内システムに限った選び方（OIDC を第一候補にする理由、SAML が必要になる場面など）は 社内システム向け認証方式の選び方 でさらに詳しく扱っています。

    6.3 実装の難易度と学習順序

    初心者向けの難易度（やさしい順）

    1. OpenID Connect：モダンで実装が比較的簡単
    2. OAuth 2.0：中程度の難易度
    3. SAML：実装が複雑

    推奨の学習順序

    1. OpenID Connect：まずはこれから始める
    2. OAuth 2.0：OpenID Connect の基礎を理解してから
    3. SAML：エンタープライズ環境で必要になったら

    7.まとめ

    SAML

    • エンタープライズ向けの認証プロトコル
    • XML ベース、企業の SSO で使用
    • 実装が複雑だが、セキュリティが高い

    OAuth 2.0

    • 認可のプロトコル（認証ではない）
    • API アクセスに使用
    • 広く使用されている

    OpenID Connect

    • OAuth 2.0 を拡張した認証プロトコル
    • ユーザーログインに使用
    • モダンで実装が比較的簡単

    Next.js アプリケーションの場合

    OpenID Connect が最も適しています。

    • モダンなプロトコル
    • モバイル、SPA、Web アプリすべてに対応
    • NextAuth.js などのライブラリがサポート
    • 実装が比較的簡単

    8.理解度チェック

    Q1. 認証プロトコルのような「プロトコル」が必要なのはなぜですか？

    異なるシステム同士（例：Web サイトと Google）が連携するには、共通の約束事が必要だからです。標準化されていれば、各社が独自の方法を作らなくてよく、既存のライブラリやツールも使えます。

    Q2. SAML で、ユーザーを認証する側と、ユーザーが使いたいアプリをそれぞれ何と呼びますか？ また、認証結果は何で伝えますか？

    認証する側が ID プロバイダ（IdP）、アプリ側が サービスプロバイダ（SP） です。認証結果は XML で書かれた SAML アサーション で伝え、SP はそれを検証してログインさせます。

    Q3. 「OAuth 2.0 は認証のプロトコルである」は正しいですか？

    正しくありません。OAuth 2.0 は 認可（何をして良いか）のプロトコルです。アクセストークンは「この API にアクセスしてよい」という権限の証明であり、「この人は誰か」を確かめたものではありません。認証に使うには OpenID Connect のような拡張が必要です。

    Q4. OpenID Connect が OAuth 2.0 に加えたいちばん大きなものは何ですか？

    ID トークン です。トークン交換のときにアクセストークンと一緒に JWT 形式の ID トークンが返り、アプリはその署名を検証して「この人は○○です」と確定できます。つまり OIDC ＝ OAuth 2.0 ＋ 身元証明です。

    Q5. OIDC の RP と OP は、OAuth 2.0 のどの役割に相当しますか？

    RP（Relying Party） はクライアント（ユーザーを認証したいアプリ）、OP（OpenID Provider） は認証サーバー（ユーザーを認証してトークンを発行するサーバー）に相当します。

    Q6. インプリシットフローとリソースオーナーパスワードクレデンシャルフローが非推奨なのはなぜで、代わりに何を使いますか？

    インプリシットフローはアクセストークンが直接返されるため、パスワードクレデンシャルフローはユーザー名とパスワードを直接アプリに送るため、どちらもセキュリティ上の理由で非推奨です。モバイルアプリや SPA では、認可コードフローをより安全にした PKCE を使います。

    Q7. 次の 3 つのケースでは、それぞれどのプロトコルが推奨されますか？ ①社内の複数システムに Okta で SSO ②写真アプリが Google フォト API を読む ③Next.js アプリに「Google でログイン」を付ける

    ① SAML（エンタープライズ SSO）、② OAuth 2.0（API アクセス）、③ OpenID Connect（ユーザーログイン。NextAuth.js などがサポート）です。
