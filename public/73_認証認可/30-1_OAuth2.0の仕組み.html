    OAuth 2.0の仕組み

    「○○のアカウントでログイン」「○○と連携」ボタンの裏で動いているのが OAuth 2.0 です。ひとことで言うと、パスワードを渡さずに、権限だけを貸す 仕組みです。前半では、写真印刷アプリを例に「誰が何を持っているか」をたとえ話で追い、引換券（認可コード）・通行証（アクセストークン）・割符（PKCE）の意味をつかみます。後半では、各ステップのリクエスト、React と Express による実装例、フローの種類、主なプロバイダー、セキュリティの注意点を見ていきます。

    もとにしたノート：30_フェデレーション/01_OAuth2.0とは、02_別のアカウントでログインの裏側_OAuth（ねる前エンジニアリング）

    このページで分かること

    • パスワードを預ける昔のやり方の 3 つの問題と、OAuth 2.0 がそれをどう解くか
    • 4 つの登場人物と、認可コードフローの流れ（受付で許可 → 引換券 → 通行証）
    • なぜ引換券をはさむのか（表の道と裏の道）、通行証の範囲・期限・取り消し
    • PKCE（割符）が防ぐ横取り、OAuth 2.0 と OpenID Connect（ログイン）の違い
    • 戻ってきたときの処理・実装例・フローの種類・AI に書かせたときのチェックポイント

    1.OAuth 2.0 とは：パスワードを渡さずに権限だけを貸す

    OAuth 2.0（オーオース 2.0） は「Open Authorization 2.0」の略で、ユーザーが自分のアカウント情報（パスワード）を渡すことなく、第三者のアプリケーションにアクセス権限を与えるためのプロトコル（通信の決まりごと）です。現代の Web アプリケーションで広く使われています。

    アプリでよく見る「○○のアカウントでログイン」ボタンを押すと、別の画面に飛んで、また戻ってきます。このページでは、その「行って戻る」流れを登場人物ごとに追います。鍵になる考え方は パスワードを渡さずに権限だけを貸す ことです。

    1.1 実務でこんな場面に出会います

    1. 新しいアプリに、外部のアカウントでのログインを付けてほしいと言われる
    2. 連携画面に「次の権限を求めています」と出る（よく読まずに許可しがち）
    3. 「トークンという文字がログに出ている」と指摘される
    4. AI が書いた連携コードをレビューすることになる

    どれも、登場人物と、誰が何を持っているか が分かれば判断できます。

    1.2 日常生活での例え：ホテルの鍵カード

    OAuth 2.0 は「ホテルの鍵カード」のようなものです。

    ホテルOAuth 2.0
    あなた（チェックインする人）ユーザー
    フロント（身分を確認して鍵カードを発行）認可サーバー
    鍵カード（部屋に入る権限を持つ）アクセストークン
    部屋（鍵カードがあれば入れる）リソースサーバー

    フロントで身分を証明すれば、鍵カードを使って部屋に入れます。OAuth 2.0 も同じように、認可サーバーで本人確認と許可をすれば、アクセストークンを使ってリソース（データ）にアクセスできます。認証（本人確認）と認可（権限を与えること）の違いは 認証と認可の違い で解説しています。

    2.昔のやり方：パスワードを預ける

    写真を印刷してくれるアプリがあり、あなたの写真は別の写真サービスに置いてあるとします。印刷アプリはその写真を読みたいわけです。OAuth がなかった頃は、写真サービスのパスワードを印刷アプリに教えて いました。印刷アプリはあなたのふりをしてログインします。

    ❌ 従来の方法:
ユーザー → アプリ: 「パスワードは123456です」
アプリ → サービス: 「パスワード123456でログインします」

✅ OAuth2.0:
ユーザー → 認証サーバー: 「このアプリにアクセス権限を付与します」
認証サーバー → アプリ: 「アクセストークンを発行します」
アプリ → サービス: 「アクセストークンでアクセスします」

    パスワードを預けるやり方には、3 つの問題があります。

    ① できることが広すぎる

    頼んだのは写真を読むことだけなのに、写真を消すこともメールを読むこともできてしまいます。

    ② 鍵が残る

    アプリの手元にパスワードが残ります。アプリが情報を漏らせば、アカウントごと取られます。

    ③ 1 つだけ止められない

    やめてほしくなったらパスワードを変えるしかなく、他に連携していたアプリも全部止まります。

    OAuth はこの 3 つを解くために作られました。OAuth 2.0 の主な目的も、これに対応しています。

    OAuth 2.0 の目的内容解く問題
    パスワードを共有しない第三者のアプリにパスワードを渡さずにアクセス権限を与えられる② 鍵が残る
    限定的なアクセス権限アプリに必要な権限だけを与えられる① できることが広すぎる
    アクセス権限の取り消しいつでも（そのアプリの分だけ）権限を取り消せる③ 1 つだけ止められない

    3.合鍵ではなく、期限つきの通行証

    友達に荷物を取ってきてもらうとき、家の合鍵は渡したくありません。何でも開いてしまうからです。ホテルなら、フロントが その部屋だけ・今夜までしか使えないカードキー を作ってくれます。なくしてもフロントで止めてもらえます。

    OAuth の考え方も同じです。合鍵（パスワード）ではなく 通行証 を渡します。

    通行証の性質内容
    範囲決めたことだけできる（写真を読むだけ）
    期限例えば 1 時間で使えなくなる
    取り消しそのアプリの通行証だけを止められる

    範囲の例としては、次のように「アプリごとに必要な権限だけ」を与えます。

    例：
- 写真アプリ: 写真へのアクセスのみ
- カレンダーアプリ: カレンダーへのアクセスのみ
- メールアプリ: メールへのアクセスのみ

    そして パスワードはフロントにだけ見せ、アプリには見せません。このフロントにあたるのが、写真サービスの 受付 です。このページでは、この係をずっと「受付」と呼びます。必要な権限だけを与える考え方は 最小権限の原則（セキュリティ基礎）とつながっています。

    4.登場人物：誰が何を持っているか

    本物の流れには 4 者が登場します。OAuth 2.0 の正式な役割名と、たとえ話の呼び方を対応させておきます。

    正式な役割たとえ話説明例
    リソースオーナー（Resource Owner）あなた（のブラウザ）ユーザーのこと。自分のリソース（データ）の所有者Google アカウントを持っているあなた。Google アカウントのデータがリソース
    クライアント（Client）印刷アプリユーザーのリソースにアクセスしたいアプリケーションあなたが使っている Web アプリ、モバイルアプリ、デスクトップアプリ
    認可サーバー（Authorization Server）写真サービスの受付本人確認とトークン（通行証）の発行を担当するサーバーGoogle・GitHub・Facebook の認可サーバー
    リソースサーバー（Resource Server）写真の置き場実際のデータ（リソース）を提供するサーバーGoogle の API サーバー（ユーザー情報、メールなど）、GitHub の API サーバー（リポジトリ情報など）

    受付と置き場は別の係です。受付は通行証を出す係、置き場は写真を返す係 で、役割が違います。

    用語のゆれ：「認証サーバー」と「認可サーバー」

    もとのノート（01_OAuth2.0とは）では Authorization Server を「認証サーバー」、認可コードを「認証コード」と書いています。仕様上の名前は 認可サーバー・認可コード（authorization code）です。このページでは「認可サーバー」「認可コード」に統一し、ノートのコードやコメントはそのまま載せています。

    5.流れ①：受付でログインして、許可する

    ここからは、最も一般的な 認可コードフロー（Authorization Code Flow）を追います。まず全体図です（PKCE の部分は 9 章 で説明します）。

    あなたが印刷アプリで「写真サービスと連携」を押したところから始めます。

    1. 印刷アプリは 自分ではパスワードを聞きません。代わりにブラウザを受付へ送り出します。これを 転送（リダイレクト） と言います。
    2. そのとき、ブラウザに「手紙」を持たせます。中身は 3 つです。
      • 戻り先：終わったら印刷アプリに戻してください（redirect_uri）
      • 範囲（スコープ）：写真を読むだけを頼みます（scope）
      • 合言葉（state）：あとで本物の戻りか確かめるためのもの。アプリの手元にも控えておきます（state）
    3. ブラウザが受付に着いたら、あなたは 受付の画面で パスワードを入れます。印刷アプリの画面ではありません。パスワードを見るのは受付だけです。
    4. 次に受付が「印刷アプリが写真を読みたいそうです。許可しますか」と聞いてきます。これが 連携画面（同意画面） です。

    連携画面は読んでから押す

    連携画面に書いてある範囲が、そのまま通行証の範囲になります。よく読まずに押しがちな画面ですが、読んでから押しましょう。

    6.流れ②：引換券を、通行証に替える

    1. あなたが許可を押すと、受付はブラウザを戻り先に返します。このとき持たせるのは通行証ではなく 引換券（認可コード） です。引換券は 数分で使えなくなり、1 回しか使えません。
    2. ブラウザは引換券と合言葉を持って印刷アプリに戻ります。印刷アプリはまず 合言葉が手元の控えと同じか を確かめます。同じなら、自分が送り出したブラウザが戻ってきたと分かります。
    3. 次に印刷アプリは 裏の道（ブラウザを通らない、サーバー同士の直接の通信）で受付に話しかけます。持っていくのは引換券と アプリ自身の鍵（クライアントシークレット）です。印刷アプリは前もって受付に登録して、自分の鍵をもらっています。だから受付は、来たのが本物の印刷アプリだと分かります。
    4. 受付は確かめて、引換券を 通行証（アクセストークン） に替えてくれます。
    5. 最後に印刷アプリは通行証を見せて、写真の置き場に頼みます。置き場は通行証の範囲を見て、写真だけ を返します。

    パスワードは一度も印刷アプリに渡っていません。あなたは受付にだけパスワードを見せ、アプリは通行証だけを持っている 状態です。

    ノート（01_OAuth2.0とは）では、同じ流れを「Google でログイン」の例で次の 7 ステップにまとめています。

    1. ユーザーがアプリで「Googleでログイン」をクリック
   ↓
2. アプリがユーザーをGoogleの認証ページにリダイレクト
   ↓
3. ユーザーがGoogleでログインし、アプリへのアクセスを許可
   ↓
4. Googleが認証コードをアプリに返す
   ↓
5. アプリが認証コードを認証サーバーに送信
   ↓
6. 認証サーバーがアクセストークンを発行
   ↓
7. アプリがアクセストークンを使ってリソースにアクセス

    OAuth 2.0 の流れの概要は OAuth 2.0：認可フレームワーク（ログイン方式と認証の概念）でも紹介しています。このページでは、それぞれの段階で「なぜそうするのか」をもう一歩掘り下げます。

    7.なぜ引換券をはさむのか：表の道と裏の道

    「最初から通行証を返せば早いのでは？」と思うかもしれません。ここで、道が 2 本あったことを思い出してください。

    表の道（ブラウザを通る道）

    ここを通ったものは、ブラウザの履歴、URL、入れている拡張機能など、いろいろなところに残り、見られうる 道です。

    裏の道（アプリと受付が直接話す道）

    あなたのブラウザを通りません。だから価値の高い通行証は、裏の道でだけ 受け取ります。

    表の道を通るのは引換券だけです。引換券は 数分で切れ、1 回きりで、アプリの鍵がないと替えられません。拾われても使いにくくしてあるわけです。

    いちばん持ち帰ってほしい考え方

    見られうる道には、見られても困らないものを流す。

    戻り先（redirect_uri）が勝手な URL に書き換えられて引換券が外部へ流れる危険は、オープンリダイレクト（Web脆弱性対策）で扱っています。

    8.通行証の中身：範囲・期限・取り消し

    8.1 範囲

    印刷アプリが写真を消そうとしたらどうなるでしょうか。置き場は通行証の範囲を見て断ります。頼んだ以上のことはできません。

    8.2 期限とリフレッシュトークン

    1 時間たつと、通行証は使えなくなります。毎回あなたに許可を聞き直すのは面倒なので、もう 1 枚 更新券（リフレッシュトークン） をもらっておきます。印刷アプリは裏の道で更新券を受付に見せ、新しい通行証をもらいます。あなたは何もしなくて構いません。

    通行証は短く、更新券で取り直す。 短くしておけば、通行証が漏れても被害は短い時間で済みます。

    ノートのコードでは、アクセストークンの期限が切れたときに次のようにして新しいアクセストークンを取得します（grant_type: 'refresh_token' がポイントです）。

    // アクセストークンの有効期限が切れた場合
async function refreshAccessToken(refreshToken) {
  const response = await fetch('https://oauth2.googleapis.com/token', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/x-www-form-urlencoded',
    },
    body: new URLSearchParams({
      client_id: 'YOUR_CLIENT_ID',
      client_secret: 'YOUR_CLIENT_SECRET',
      refresh_token: refreshToken,
      grant_type: 'refresh_token',
    }),
  });

  const data = await response.json();
  return data.access_token; // 新しいアクセストークン
}

    アクセストークンとリフレッシュトークンの寿命の違いや、リフレッシュトークンの保存場所（localStorage を避ける理由）は アクセストークンとリフレッシュトークン で解説しています。

    8.3 取り消し

    あなたが受付で印刷アプリとの連携を解除すると、更新券が無効になり、次の通行証は出ません。他のアプリはそのまま動き、パスワードも変えなくて構いません。

    これで、2 章 の 3 つの問題（できることが広すぎる・鍵が残る・1 つだけ止められない）が全部解けました。

    9.もう 1 つの例：スマホのアプリと割符（PKCE）

    今度はスマホのアプリを考えます。スマホのアプリには、さっきの アプリの鍵を安全に置けません。アプリは利用者のスマホに配られ、中身を分解して調べられるので、鍵を埋め込んでも取り出されてしまうからです。

    しかもスマホには、戻り先を横取りする手口 があります。本物と同じ戻り先を名乗る なりすましアプリ を入れておくと、受付がブラウザを戻すとき、引換券がなりすましに届いてしまいます。鍵がないので、そのまま通行証に替えられてしまいます。

    そこで 割符（わりふ） のような仕組みを足します。これが PKCE（Proof Key for Code Exchange、「ピクシー」と読む）です。

    1. 本物のアプリは、最初に毎回新しい 秘密の答え（code_verifier）を作ります。
    2. 受付には、答えを決まった計算で崩した 写し（code_challenge）だけを渡します。受付はその写しを控えておきます。写しから元の答えには戻せません（一方向の計算）。
    3. 引換券を替えるとき、アプリは元の答えを出します。受付は答えを同じ計算で崩し、控えの写しと比べます。
    4. なりすましは引換券を拾っても答えを持っていないので、受付は替えてくれません。

    写しは見られても平気で、答えは本物の手元から出ません。これも 「見られうる道には、見られても困らないものを流す」 と同じ考え方です。今は スマホに限らず、どのアプリでも PKCE を使うことが勧められています。

    code_verifier・code_challenge の作り方（SHA-256 によるハッシュ化）や実装コードは PKCE について（Web脆弱性対策の CSP のページ）で詳しく解説しています。一方向の計算（ハッシュ関数）そのものは ハッシュ関数（セキュリティ基礎）を参照してください。

    10.許可の仕組みと、ログインの仕組み（OpenID Connect）

    ところで、最初のボタンは「ログイン」でした。今までの話は写真を読む 許可 の話です。ログインとは違うのでしょうか。

    OAuth は元々 許可を貸す仕組み で、誰なのかは言いません。通行証はホテルのカードキーと同じで、カードキーを持っている人が部屋の持ち主本人とは限りません。拾った人でも開けられます。

    だからログインに使うときは、もう 1 枚 本人の証明書 を受け取ります。OAuth の上に作られた決まりである OpenID Connect（OIDC） で、受付が ID トークン という証明書を出します。

    ID トークンに書いてあること意味
    誰かログインしたユーザー
    どのアプリ宛てかこの証明書を受け取るべきアプリ（宛て先）
    いつまで有効か有効期限
    受付の署名受付が発行した本物であることの証明

    宛て先が大事 です。他のアプリ宛ての証明書を見せられても受け付けません。

    通行証（アクセストークン）

    置き場に見せるもの。何をしてよいかの許可。

    証明書（ID トークン）

    アプリが本人を確かめるもの。あなたは誰か。

    許可は通行証、本人は証明書。 分けて覚えておきましょう。アクセストークンと ID トークンの対比図は OpenID Connect（OIDC）：OAuth 2.0 の上の認証レイヤー、SAML・OAuth・OIDC の比較は次のページ SAML・OAuth・OIDCの違い で扱います。

    11.コードで見る：戻ってきたときの処理とセキュリティの注意点

    受付から戻ってきたときの処理を、順に見ます。戻ってくると、URL に引換券（code）と合言葉（state）が付いています。

    11.1 合言葉（state）を手元の控えと比べる

    まず合言葉を控えと比べ、違えばそこで止めます。これを忘れると、他人が始めた連携をあなたの画面に押し込まれ、あなたのアカウントが知らない人の写真とつながる、といった事故になります。state は CSRF 攻撃（利用者に意図しないリクエストを送らせる攻撃）を防ぐためのランダムな文字列です。

    ノートのコード：state を生成して、コールバックで検証する 
    // stateを生成
const state = Math.random().toString(36).substring(7);
sessionStorage.setItem('oauth_state', state);

// コールバックで検証
const returnedState = urlParams.get('state');
const storedState = sessionStorage.getItem('oauth_state');

if (returnedState !== storedState) {
  throw new Error('State mismatch - possible CSRF attack');
}

    補足：state は推測できない乱数で

    Math.random() は暗号用の乱数ではないため、本番では crypto.randomBytes（Node.js）や crypto.getRandomValues（ブラウザ）などで作るのが安全です。

    CSRF の仕組みと、推測できないトークンを埋め込んで照合する対策の考え方は 秘密情報（トークン）の埋め込み（CSRF のページ）で解説しています。state はこの考え方を OAuth の戻りに当てはめたものです。

    11.2 裏の道で引換券を通行証に替える：アプリの鍵は環境の設定から

    次に、裏の道で引換券を通行証に替えます。割符の答えとアプリの鍵も一緒に 出します。アプリの鍵（クライアントシークレット）は コードに直接書かず、環境の設定から読みます。

    間違い：クライアントシークレットをクライアント側に書く 
    const clientSecret = 'secret-key-12345'; // 危険！
    正しい：サーバー側で管理（環境変数や設定ファイル） 
    const clientSecret = process.env.CLIENT_SECRET;

    鍵をコードに書かない理由は シークレット管理（セキュリティ基礎）も参照してください。

    11.3 通行証をログに出さない

    通行証は 持っている人なら誰でも使えます。ログに出せば、ログを読める人全員が「あなた」になれてしまいます。1.1 の「トークンという文字がログに出ている」と指摘された場面は、まさにこれです。ログに書いてはいけないものの全体は ログに書いてはいけないもの（セキュリティ基礎）にまとまっています。

    11.4 更新券は暗号化して保存する

    更新券は長く使えるので、暗号化して保存 します。そして URL にも、ブラウザの保存場所にも置かない のが基本です。

    11.5 HTTPS を使う

    OAuth 2.0 では、必ず HTTPS を使ってください。

    間違い：HTTP は危険 
    redirect_uri: 'http://localhost:3000/callback'
    正しい：HTTPS を使用 
    redirect_uri: 'https://myapp.com/callback'

    このページのコード例に出てくる http://localhost は、自分の PC だけで動かす開発用の例です。本番の戻り先は HTTPS にします。

    12.AI に連携コードを書かせたときに見るところ

    1. 範囲が必要な分より広くないか：AI は動かすために、とりあえず全部の権限を頼みがちです。連携画面で利用者を怖がらせますし、漏れたときの被害も範囲の広さの分だけ大きくなります。
    2. 合言葉を作って、戻ってきたときに比べているか：作るだけで比べていないコードもあります。比べるくだりを探してください。
    3. 割符（PKCE）を使っているか。
    4. 通行証や更新券をログや URL に出していないか：動作確認のために print で出したまま、という消し忘れがそのまま本番に出ます。
    5. ログインに使うなら、証明書（ID トークン）をきちんと確かめているか：受け取って中身を読むだけで、宛て先が自分のアプリか・まだ有効か・署名が受付のものか を確かめていないことがあります。

    決まった部品に任せる

    証明書の確認などは、自分で書くより 決まった部品（ライブラリ）に任せる のが安全です。AI には、どの部品を使い、何を確かめるか をはっきり頼みましょう。認証を自前で実装しない考え方は 認証を自前実装しない（セキュリティ基礎）でも扱っています。

    ここからは、ノート（01_OAuth2.0とは）のコードで、認可コードフローの各ステップを Google を例に見ていきます。

    13.1 ステップ1：認可リクエスト

    // アプリがユーザーを認証サーバーにリダイレクト
const authUrl = `https://accounts.google.com/o/oauth2/v2/auth?
  client_id=YOUR_CLIENT_ID&
  redirect_uri=http://localhost:3000/callback&
  response_type=code&
  scope=email profile&
  state=random_string`;

window.location.href = authUrl;
    パラメータ説明たとえ話
    client_idアプリの IDどのアプリからの依頼か
    redirect_uri認可後のリダイレクト先戻り先
    response_typecode（認可コードを要求）引換券をください
    scope要求する権限（email、profile など）範囲
    stateCSRF 攻撃を防ぐためのランダムな文字列合言葉

    補足：コード中の URL の改行

    ノートのコードは読みやすさのために URL を途中で改行していますが、実際には改行や空白が URL に入ってしまいます。本番では 1 行で書くか、URLSearchParams で組み立てます。また、PKCE を使う場合はここに code_challenge と code_challenge_method=S256 を加えます（実装例）。

    13.2 ステップ2：ユーザーが認証・許可

    ユーザーが Google でログインし、アプリへのアクセスを許可します（5 章 の受付での操作です）。

    13.3 ステップ3：認可コードを受け取る

    // リダイレクト先（/callback）で認証コードを受け取る
// URL: http://localhost:3000/callback?code=AUTHORIZATION_CODE&state=random_string

const urlParams = new URLSearchParams(window.location.search);
const code = urlParams.get('code');
const state = urlParams.get('state');

    13.4 ステップ4：アクセストークンを取得（サーバー側）

    // サーバー側でアクセストークンを取得
async function getAccessToken(code) {
  const response = await fetch('https://oauth2.googleapis.com/token', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/x-www-form-urlencoded',
    },
    body: new URLSearchParams({
      code: code,
      client_id: 'YOUR_CLIENT_ID',
      client_secret: 'YOUR_CLIENT_SECRET',
      redirect_uri: 'http://localhost:3000/callback',
      grant_type: 'authorization_code',
    }),
  });

  const data = await response.json();
  return data.access_token; // アクセストークン
}

    これが「裏の道」での引換券と通行証の交換です。grant_type: 'authorization_code' で「認可コードを交換したい」と伝え、client_secret（アプリの鍵）を添えます。

    13.5 ステップ5：リソースにアクセス

    // アクセストークンを使ってリソースにアクセス
async function getUserInfo(accessToken) {
  const response = await fetch('https://www.googleapis.com/oauth2/v2/userinfo', {
    headers: {
      'Authorization': `Bearer ${accessToken}`,
    },
  });

  const userInfo = await response.json();
  return userInfo;
}

    Authorization: Bearer ... は「このトークンを持っている者として扱ってください」という送り方です。Bearer の意味は Bearer はパターン、JWT は形式 で解説しています。

    14.1 フロントエンド（React）

    // components/LoginButton.jsx
import { useState } from 'react';

function LoginButton() {
  const [user, setUser] = useState(null);

  const handleLogin = () => {
    // Googleの認証ページにリダイレクト
    const clientId = 'YOUR_CLIENT_ID';
    const redirectUri = encodeURIComponent('http://localhost:3000/callback');
    const scope = encodeURIComponent('email profile');
    const state = Math.random().toString(36).substring(7);

    const authUrl = `https://accounts.google.com/o/oauth2/v2/auth?
      client_id=${clientId}&
      redirect_uri=${redirectUri}&
      response_type=code&
      scope=${scope}&
      state=${state}`;

    window.location.href = authUrl;
  };

  const handleCallback = async () => {
    // URLから認証コードを取得
    const urlParams = new URLSearchParams(window.location.search);
    const code = urlParams.get('code');

    if (code) {
      // サーバーに認証コードを送信してアクセストークンを取得
      const response = await fetch('/api/auth/callback', {
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
        },
        body: JSON.stringify({ code }),
      });

      const { accessToken } = await response.json();

      // ユーザー情報を取得
      const userInfo = await fetch('/api/user', {
        headers: {
          'Authorization': `Bearer ${accessToken}`,
        },
      }).then(res => res.json());

      setUser(userInfo);
    }
  };

  // コールバックページで実行
  useEffect(() => {
    handleCallback();
  }, []);

  if (user) {
    return <div>こんにちは、{user.name}さん</div>;
  }

  return <button onClick={handleLogin}>Googleでログイン</button>;
}

    このコードを使うときの注意

    • useEffect を使っているので、import { useState, useEffect } from 'react'; が必要です。
    • state を作っていますが、保存も照合もしていません。12 章 の「作るだけで比べていない」例にあたるので、11.1 のように控えて比べます。
    • アクセストークンをブラウザに返して使っています。7 章 の「通行証は裏の道でだけ受け取る」に沿うなら、トークンはサーバー側に置き、ブラウザとはセッションでやり取りする形（次の 14.3 の例）が基本です。

    14.2 バックエンド（Express.js）

const express = require('express');
const router = express.Router();
const axios = require('axios');

// 認証コードをアクセストークンに交換
router.post('/callback', async (req, res) => {

});

});

    14.3 Google ログインの完全な実装（サーバー側で完結する例）

    次の例では、state の生成・照合からトークン取得、ユーザー情報の取得、セッションへの保存までをサーバー側で行います。まず環境変数を設定します。

GOOGLE_CLIENT_ID=your-client-id
GOOGLE_CLIENT_SECRET=your-client-secret

    // server.js
const express = require('express');
const session = require('express-session');
const axios = require('axios');
require('dotenv').config();

const app = express();

app.use(session({
  secret: 'your-secret-key',
  resave: false,
  saveUninitialized: false,
}));

// ログインページ
app.get('/login', (req, res) => {
  const state = Math.random().toString(36).substring(7);
  req.session.oauthState = state;

  const authUrl = `https://accounts.google.com/o/oauth2/v2/auth?
    client_id=${process.env.GOOGLE_CLIENT_ID}&
    redirect_uri=${encodeURIComponent(process.env.REDIRECT_URI)}&
    response_type=code&
    scope=email profile&
    access_type=offline&
    prompt=consent&
    state=${state}`;

});

// コールバック
app.get('/callback', async (req, res) => {
  const { code, state } = req.query;

  // stateの検証
  if (state !== req.session.oauthState) {
    return res.status(400).send('Invalid state parameter');
  }

  try {
    // アクセストークンを取得
    const tokenResponse = await axios.post('https://oauth2.googleapis.com/token', {
      code,
      client_id: process.env.GOOGLE_CLIENT_ID,
      client_secret: process.env.GOOGLE_CLIENT_SECRET,
      redirect_uri: process.env.REDIRECT_URI,
      grant_type: 'authorization_code',
    });

    const { access_token, refresh_token } = tokenResponse.data;

    // ユーザー情報を取得
    const userResponse = await axios.get('https://www.googleapis.com/oauth2/v2/userinfo', {
      headers: {
        'Authorization': `Bearer ${access_token}`,
      },
    });

    // セッションに保存
    req.session.user = userResponse.data;
    req.session.accessToken = access_token;
    req.session.refreshToken = refresh_token;

    res.redirect('/dashboard');
  } catch (error) {
    console.error('認証エラー:', error);
    res.status(400).send('認証に失敗しました');
  }
});

// ダッシュボード
app.get('/dashboard', (req, res) => {
  if (!req.session.user) {
    return res.redirect('/login');
  }

  res.send(`
    <h1>ダッシュボード</h1>
    <p>こんにちは、${req.session.user.name}さん</p>
    <p>メール: ${req.session.user.email}</p>

});

});

    15.OAuth 2.0 のフローの種類

    OAuth 2.0 には、場面に応じた複数のフロー（グラントタイプ）があります。

    フロー特徴位置づけ
    認可コードフロー（Authorization Code Flow）最も安全で一般的。サーバー側のアプリケーションで使用。アクセストークンとリフレッシュトークンを取得推奨（PKCE と組み合わせる）
    インプリシットフロー（Implicit Flow）クライアント側（ブラウザだけで動く）アプリケーションで使われていた非推奨
    クライアントクレデンシャルフロー（Client Credentials Flow）アプリケーション同士の認証に使用。ユーザーは関与しないサーバー間通信で使用
    リソースオーナーパスワードクレデンシャルフローパスワードを直接アプリに渡すため、セキュリティリスクが高い非推奨

    補足：現在の推奨

    OAuth 2.0 のセキュリティ上の推奨をまとめた OAuth 2.0 Security BCP（RFC 9700）や策定中の OAuth 2.1 では、インプリシットフローとパスワードクレデンシャルフローは使わないこととされ、ブラウザだけで動くアプリやスマホアプリも 認可コードフロー＋PKCE を使います。

    クライアントクレデンシャルフローでは、ユーザーの許可を挟まず、アプリ自身の ID と鍵だけでトークンを取得します。

    // サーバー間の認証
const response = await fetch('https://oauth2.googleapis.com/token', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/x-www-form-urlencoded',
  },
  body: new URLSearchParams({
    client_id: 'YOUR_CLIENT_ID',
    client_secret: 'YOUR_CLIENT_SECRET',
    grant_type: 'client_credentials',
  }),
});

    知らなくていいこと

    動画（ねる前エンジニアリング）では、フローの種類ごとの細かい差 は知らなくてよいとしています。名前のついた流れはいくつかありますが、このページの流れ と 割符（PKCE） を知っていれば十分です。細かい違いは、必要になったときに決まった部品（ライブラリ）の説明を読めば大丈夫です。

    17.OAuth 2.0 のメリット・デメリット

    メリット

    1. パスワードを共有しない：セキュリティが向上
    2. 限定的な権限：必要な権限だけを付与
    3. アクセス権限の管理：いつでも取り消し可能
    4. 標準化：多くのサービスで対応

    デメリット

    1. 実装が複雑：フローが複雑で実装が難しい
    2. トークンの管理：アクセストークンとリフレッシュトークンの管理が必要
    3. エラーハンドリング：さまざまなエラーケースに対応する必要がある

    実装の複雑さは、12 章 のとおり実績のあるライブラリに任せることで小さくできます。

    18.まとめ

    • OAuth 2.0 は、パスワードを共有せずにアクセス権限を付与する仕組み。パスワードは受付（認可サーバー）にだけ見せ、アプリには通行証を渡す。合鍵ではなく、その部屋だけのカードキー。
    • 4 つの役割：リソースオーナー（あなた）、クライアント（アプリ）、認可サーバー（受付）、リソースサーバー（置き場）。ノートでは認可サーバーを「認証サーバー」と呼んでいる。
    • 認可コードフロー が最も一般的で安全。見られうる 表の道には引換券（認可コード）だけ を流し、裏の道で通行証（アクセストークン）に替える。
    • 通行証には範囲と期限 があり、そのアプリの分だけ取り消せる。リフレッシュトークン で新しいアクセストークンを取得する。
    • PKCE（割符） で引換券の横取りを防ぐ。今はどのアプリでも使うことが勧められている。
    • 許可は通行証、本人かどうかは証明書（ID トークン） で確かめる。ログインには OpenID Connect を使う。
    • セキュリティ：state を作って照合する、クライアントシークレットは環境変数で管理、トークンをログや URL に出さない、更新券は暗号化して保存、HTTPS を使う。
    • フローの種類ごとの細かい差は知らなくてよい。インプリシットフローとパスワードクレデンシャルフローは非推奨。

    19.理解度チェック

    Q1. パスワードをアプリに預ける昔のやり方には、どんな 3 つの問題がありましたか？

    ① できることが広すぎる（写真を読むだけのはずが、消す・メールを読むこともできる）、② 鍵が残る（アプリが漏らせばアカウントごと取られる）、③ 1 つだけ止められない（パスワードを変えると他の連携アプリも全部止まる）です。OAuth は範囲・期限つきで取り消せる通行証を渡すことで、この 3 つを解きます。

    Q2. OAuth 2.0 の 4 つの役割を答え、写真印刷アプリの例で何にあたるか説明してください。

    リソースオーナー＝あなた、クライアント＝印刷アプリ、認可サーバー＝写真サービスの受付（通行証を出す係）、リソースサーバー＝写真の置き場（写真を返す係）です。

    Q3. 受付は、なぜ最初から通行証（アクセストークン）を返さず、引換券（認可コード）を返すのですか？

    ブラウザを通る 表の道 は、履歴・URL・拡張機能などに残り、見られうるからです。表の道には、数分で切れて 1 回きりで、アプリの鍵がないと替えられない引換券だけを流し、価値の高い通行証はブラウザを通らない 裏の道 で受け取ります。「見られうる道には、見られても困らないものを流す」考え方です。

    Q4. state パラメータの照合を忘れると、何が起きますか？

    他人が始めた連携をあなたの画面に押し込まれ、あなたのアカウントが知らない人の写真（アカウント）とつながる、といった事故が起きます。state は CSRF 攻撃を防ぐための合言葉で、作るだけでなく、戻ってきたときに控えと比べる ことが必要です。

    Q5. PKCE は、どんな攻撃をどうやって防ぎますか？

    スマホなどアプリの鍵を安全に置けないアプリで、なりすましアプリが戻り先を横取りして引換券を通行証に替える 攻撃を防ぎます。本物のアプリが毎回秘密の答えを作り、受付には一方向の計算で崩した写しだけを渡しておきます。交換時に元の答えを出させ、受付が同じ計算で崩して写しと比べるので、答えを持たないなりすましは替えられません。

    Q6. 「アクセストークンを受け取れたので、ログインした人が本人だと分かる」は正しいですか？

    正しくありません。OAuth は許可を貸す仕組みで、誰なのかは言いません。通行証はカードキーと同じで、持っている人が本人とは限りません。ログインには OpenID Connect の ID トークン（誰か・どのアプリ宛てか・いつまで有効か・受付の署名）を受け取り、宛て先・有効期限・署名 を確かめます。

    Q7. アクセストークンの有効期限を短くし、リフレッシュトークンを使うのはなぜですか？ また、リフレッシュトークンはどう扱いますか？

    通行証が漏れても被害を短い時間で済ませるためです。期限が切れたら、更新券（リフレッシュトークン）を裏の道で受付に見せて新しい通行証をもらうので、ユーザーは何もしなくて構いません。更新券は長く使えるので、暗号化して保存し、URL やブラウザの保存場所には置きません。連携を解除すると更新券は無効になります。

    Q8. AI が書いた OAuth 連携コードをレビューするとき、確認すべき点を挙げてください。

    ① 範囲（scope）が必要な分より広くないか、② state を作って戻ってきたときに比べているか、③ PKCE を使っているか、④ アクセストークンやリフレッシュトークンをログや URL に出していないか、⑤ ログインに使うなら ID トークンの宛て先・有効期限・署名を確かめているか（ライブラリに任せているか）です。クライアントシークレットがコードに直書きされていないかも見ます。

    Q9. インプリシットフローとリソースオーナーパスワードクレデンシャルフローは、今使うべきですか？

    使うべきではありません。どちらも非推奨で、パスワードクレデンシャルフローはパスワードを直接アプリに渡すためリスクが高いです。ブラウザやスマホのアプリでも 認可コードフロー＋PKCE を使います。ユーザーが関与しないサーバー間の通信では、クライアントクレデンシャルフローを使います。
