    10 基礎概念

    社内システム向け認証方式の選び方

    社内システムで「社員だけがログインできる」ようにするには、どの認証方式を選べばよいのでしょうか。このページでは、モダンな第一候補である OIDC + 社内 IdP への SSO を中心に、OIDC 以外の代替手段と選び方の指針を整理します。後半では、TypeScript の認証ライブラリ Better Auth を使って「社員・部署・入退社・権限を一元管理する認証基盤」を自社で作り、複数の業務アプリに SSO する設計例を、ファイル構成・DB テーブル・環境変数まで含めて解説します。

    もとにしたノート：10_基礎概念/07_社内システム向け認証方式の選び方

    ひとことで言うと

    社員向けログインの第一候補は OIDC で社内 IdP に SSO することです。「社員だけ」を決めるのは認証方式そのものより、どの IdP（社員の ID を管理する仕組み）に繋ぐか です。JWT やセッション Cookie は、ログインした 後 の状態をどう持つかの選択肢です。

    このページに出てくる OIDC・SAML・SSO・JWT・OAuth 2 などの用語の基本は、ログイン方式と認証の概念 で解説しています。パスワードのハッシュや MFA の基礎は パスワード・MFA・暗号化の基礎 を参照してください。ここでは、それらを「社内システムでどう選ぶか」という視点でまとめます。

    1.結論：モダンな第一候補

    OIDC + 社内 IdP への SSO が第一候補です。

    • OIDC（OpenID Connect）：OAuth 2 の上に「ログインした人が誰か」を伝える仕組みを足した認証プロトコルです。
    • IdP（Identity Provider / アイデンティティプロバイダ）：ユーザーの ID とパスワードなどを管理し、ログインを代行するサービスです。
    • SSO（シングルサインオン）：一度ログインすれば、複数のアプリにログインし直さずに入れる仕組みです。
    やりたいこと選ぶもの
    社員の本人確認OIDC（ID トークンで「誰か」を確定）
    一度ログインで複数社内アプリSSO（UX。実装は OIDC / SAML）
    ログイン後の API 呼び出しBearer + JWT（Access / Refresh）または セッション + Cookie

    ID トークン は、IdP が発行する「この人は誰で、いつログインしたか」を記した署名付きのデータです。UX は使い勝手のことです。

    「社員だけ」は認証方式そのものより、どの IdP に繋ぐか で決まります。代表的な IdP は次のとおりです。

    • Microsoft Entra ID（旧 Azure AD）
    • Google Workspace
    • Okta など

    アプリは OIDC で IdP に リダイレクト（ブラウザを別の URL へ移動させること）し、返ってきた ID トークンの email / sub（ユーザーの一意な ID）/ グループクレーム（所属グループの情報）で、在籍社員かどうかを判定します。クレーム とは、トークンの中に書かれた個々の情報のことです。

    1.1 社員以外を弾く典型的な制御

    • 許可ドメインのみ（例：@yourcompany.com）
    • IdP の「全社員」グループ／ロールのみ許可
    • 必要なら VPN や社内ネットワークと併用（認証の代替ではなく補強）

    VPN は「認証の代わり」にはならない

    「社内ネットワークの中なら安全」という考え方の限界は、71 の ゼロトラスト で解説しています。VPN はあくまでネットワーク層での補強であり、アプリ側でも必ず認証します。

    2.概念の整理（一覧）

    認証まわりの用語は「方式」「形式」「フレームワーク」「UX パターン」など、種類の違うものが混ざっています。まず分類を並べて整理します。

    概念分類一言
    Basic / Digest認証方式（レガシー）ヘッダで資格情報／ハッシュを毎回送る
    API キー認証方式DB ルックアップが必要な不透明キー
    セッション + Cookie認証方式ステートフル、古典的 Web
    Bearerパターントークン保持者にアクセス
    JWTトークン形式署名付き・自己完結可能
    Access / Refreshトークン運用短命 API 用 + 長命更新用
    OAuth 2認可フレームワーク第三者アプリのリソースアクセス許可
    OIDC認証（+ OAuth 2）ID トークンで本人確認
    SSOUX パターン一度のログインで複数サービス
    SAML / OIDCアイデンティティプロトコルSSO の下層技術

    不透明キー は、文字列自体に意味がなく、サーバーが DB を引いて初めて持ち主が分かるキーです。ステートフル は、サーバー側にログイン状態を保存しておく方式のことです。各概念の詳しい説明は ログイン方式と認証の概念 を参照してください。

    3.社員ログイン用途ごとの向き不向き

    3.1 向かない・別用途

    方式理由
    Basic / Digestレガシー。社員向け本番ログインの主役にはしない
    API キー人間のブラウザログインではなく、バッチ・連携・マシン間向け
    OAuth 2 単体認可フレームワーク。社員ログインの本体には OIDC が必要（OAuth 2 だけでは「誰か」の保証が弱い）

    3.2 よく使うが「単体の答え」ではない

    方式位置づけ
    JWT / Bearer / Access・Refreshログイン 後 のトークン運用。OIDC ログインのあと、自前 JWT を発行するかセッションに載せ替えるかの話
    セッション + Cookieモダンでも有効（特に社内 Web の BFF 構成）。多くは OIDC で IdP ログイン → サーバーがセッション発行

    BFF（Backend for Frontend） は、画面専用のサーバーを1枚挟み、トークンなどの扱いをそのサーバーに任せる構成です。ブラウザにはセッション Cookie だけを渡すので、トークンを JavaScript から触らせずに済みます。

    3.3 エンタープライズでまだ多い

    方式位置づけ
    SAML既存 IdP・アプリが SAML 固定なら現実的。新規なら OIDC 優先（JSON / JWT エコシステムと相性がよい）

    4.実務でよくある構成

    社員が社内アプリを開いてから使えるようになるまでの流れは、次のようになります。

    • 社内 Web 1 本 … OIDC + セッション + HttpOnly Cookie（CSRF 対策込み）が扱いやすいことが多いです。
    • SPA / モバイル / 複数 API … OIDC のあと 短命 Access + Refresh が一般的です。

    HttpOnly は JavaScript から読めない Cookie にする属性、SPA（Single Page Application）は画面遷移を JavaScript で行う Web アプリです。Cookie を使う場合の CSRF 対策は 72 の CSRF を、セッションそのものの安全な扱い方は 74_セッション管理 を参照してください。

    Microsoft 365 を利用しているなら Entra ID の OIDC、Google Workspace なら Google の OIDC、という形が多いです。

    5.OIDC 以外に使えるもの

    5.1 同じ「SSO・社内 IdP」系（OIDC の兄弟）

    方式向き補足
    SAML 2.0エンタープライズ SSO既存 IdP・アプリが SAML 固定のとき。XML・リダイレクト型。新規は OIDC が多いが社内では十分現役
    WS-FederationMicrosoft 系レガシーEntra / ADFS 周りで残っていることがある

    いずれも「社員だけ」は IdP 側のユーザー／グループ で縛る点は OIDC と同じです。ADFS（Active Directory Federation Services）は、オンプレミスの Active Directory を IdP として使うための Microsoft の製品です。

    5.2 Web アプリ向け（IdP 連携なし〜弱い連携）

    方式向き補足
    セッション + Cookie（自前 ID/パスワード）小規模・社内ツールDB にユーザー、ログイン後セッション。MFA・退職対応は自前。IdP がなくても動く
    LDAP / Active Directory 直接バインドオンプレ AD 中心アプリが AD に認証。OIDC ほど標準化されていないが社内では昔からある
    Windows 統合認証（Kerberos / NTLM）ドメイン参加 PC のイントラネットブラウザがドメイン資格情報を使い画面なし SSO に近い。社外・Mac では弱い

    LDAP はユーザー情報を管理するディレクトリに問い合わせるためのプロトコル、バインド は LDAP サーバーに ID とパスワードで認証することです。Kerberos / NTLM は Windows ドメインで使われる認証方式で、PC にログインした時点の資格情報を使い回せます。

    5.3 トークン・API 寄り（人のログインの「本体」にはしにくい）

    方式向き補足
    Bearer + JWT（自前発行）API・マイクロサービスログイン画面は別途必要。認証の代わりではなくログイン後の形式
    Access / Refresh同上OIDC / SAML / セッションの 後 に自前で発行するパターンが多い
    API キーバッチ・連携・社内スクリプト人間のブラウザログインには不向き

    5.4 レガシー（社内限定なら「使える」がモダン推奨ではない）

    方式補足
    Basic / Digest社内限定ツール・Postman 程度。本番の社員ポータル主役にはしない
    OAuth 2 のみ（OIDC なし）第三者アプリの認可向け。社員ログインの本体には非推奨

    5.5 その他（条件付き）

    • mTLS（クライアント証明書） … 極めて閉じた社内 API 向けです。サーバーだけでなくクライアント側も証明書で身元を示す TLS 通信のことで、ブラウザを使う一般ユーザー向けには運用が重くなります。
    • VPN + 上記のいずれか … 「社員だけ」をネットワーク層でも補強します（認証方式の代替ではありません）。

    6.選び方の指針

    環境・要件おすすめ
    既に Microsoft / Google / Okta があるOIDC が第一候補。ダメなら SAML（ベンダー・既存アプリの都合）
    小さい社内ツール・IdP を立てたくないセッション + 自前アカウント または AD / LDAP 直結
    社内 Windows PC のみ・イントラネットKerberos 統合認証 も選択肢（OIDC リダイレクト不要）
    API・ジョブだけAPI キー や サービス用 JWT（人のログインとは別）

    6.1 ここまでの要点

    • モダンで社員限定 … OIDC で社内 IdP に SSO（必要なら SAML）
    • JWT / セッション / Access・Refresh … その 後 にどうセッションを持たせるかの選択
    • 自前の ID/パスワード DB だけ … MFA・退職者無効化・パスワードポリシーを全部自前で背負うため、社員規模なら IdP 連携が一般的
    • OIDC 以外で社員ログインとしてよくあるもの … SAML、セッション + AD/LDAP、環境によって Kerberos

    7.Better Auth を使った社内 SSO 設計（複数アプリ）

    ここからは設計例です。社員マスタ・部署・入退社・権限を 1 つの認証基盤アプリ で一元管理し、他のアプリは Better Auth + 標準 OIDC で SSO する構成を考えます。プロトコル・暗号・セッションを一から自前実装する案は採用しません（理由は 7.2 で説明します）。

    7.1 用語の整理：IAM / Better Auth / AWS

    用語何か本設計での役割
    AWS IAMAWS リソースへの権限管理サービス使わない（高コスト・本件と無関係）
    認証基盤（旧メモの「IAM 基盤」）社員・部署・入退社・権限を持つ 自社アプリ の通称1 台の Next.js（等）アプリ として実装
    Better AuthTypeScript 向け 認証ライブラリ（旧 Auth.js / NextAuth 系の後継）認証基盤と各業務アプリに 組み込む実装部品

    IAM（認証基盤）と Better Auth は別物ですが、セットで使います。

    認証基盤アプリ

    社員マスタ・管理画面・SSO の 中心（IdP） という 役割・データの正（正しい元データを持つ場所）

    Better Auth

    ログイン・セッション・MFA・OIDC 発行・管理 API を 安全に実装するためのライブラリ

    AWS に課金するサービスではなく、自社サーバー上のアプリ + OSS ライブラリ で構成します。

    7.2 「自前は危ない」とは何を避けるか

    危ないのは 「認証基盤という名前のアプリを自社で作る」こと自体ではなく、次をゼロから書くことです。

    • パスワードハッシュ・タイミング攻撃対策
    • セッション固定・CSRF・オープンリダイレクト
    • Authorization Code / PKCE / トークン署名・失効
    • MFA・レート制限・監査ログ

    タイミング攻撃 は処理時間の差から秘密の値を推測する攻撃、セッション固定 は攻撃者が用意したセッション ID を被害者に使わせる攻撃、PKCE は認可コードを横取りされても使えないようにする OAuth の追加の仕組みです。オープンリダイレクトについては 72 の リダイレクトとHTTPヘッダインジェクション を参照してください。

    Better Auth を使う ＝ 自社運用の認証基盤

    Better Auth を使うことは、上記をライブラリと標準プロトコルに委ねる 「自社運用の認証基盤」 を作ることであり、Entra ID のような マネージド SaaS IdP（運用まで事業者が担うクラウドの IdP）とは別物です。自社で書くのは、自社固有の部分（部署マスタ・業務権限・入退社 UI）だけです。

    7.3 ゴールと責務分担

    責務認証基盤アプリ業務アプリ（複数）
    社員・部署マスタ正（Better Auth user + 拡張 + Organization）API 参照・キャッシュ
    入退社Admin banUser 等で即時無効化Webhook / 同期で追随
    ログインログイン画面・MFA・OIDC 発行Better Auth が IdP へリダイレクト
    権限Organization RBAC + カスタム permissionアプリ固有データは各アプリ
    SSOOIDC Provider（Authorization Code + PKCE）OIDC クライアントとして接続

    RBAC（Role-Based Access Control）はロール（役割）ごとに権限を割り当てる方式、Webhook は出来事が起きたときに相手のサーバーへ HTTP で通知する仕組みです。認可モデルの詳細は、今後追加予定の 40 系（認可モデル）のページで扱います。

    7.4 全体構成

    7.5 SSO フロー（Better Auth OIDC Provider）

    認証基盤に OIDC Provider プラグイン を載せ、業務アプリを OAuth クライアント（IdP にログインを頼む側のアプリ）として登録します。外部の Okta や Entra ではなく、自社の Better Auth が IdP になります。

    1. 社員 → 業務アプリ：保護ページへアクセス
    2. 業務アプリ → 認証基盤：OIDC 認可リダイレクト
    3. 社員 → 認証基盤：ログイン（セッションがあればスキップ）
    4. 認証基盤 → 社員：同意画面（trustedClient なら省略可）
    5. 認証基盤 → 業務アプリ：redirect_uri?code=...（認可コードを付けて戻す）
    6. 業務アプリ → 認証基盤：トークン交換（サーバー間）
    7. 認証基盤 → 業務アプリ：access_token / id_token
    8. 業務アプリ：ローカルセッション Cookie 発行
    9. 業務アプリ → 社員：ログイン完了

    手順 6 のトークン交換はブラウザを通らず、サーバー同士で行われます。そのためトークンがブラウザの履歴や URL に残りません。

    注意：プラグインの成熟度を確認する

    OIDC Provider プラグインは開発が活発です。本番前に 公式ドキュメント と後継の OAuth Provider プラグイン の安定性を確認してください。

    7.6 認証基盤アプリの Better Auth 設定（例）

    プラグイン用途
    コア（email + password）社員ログイン。招待制は sign-up 無効 + Admin でユーザー作成
    twoFactorTOTP / バックアップコード（MFA 一元化）
    adminユーザー作成・ロール・ban（退職時は全セッション失効）
    organization部署・チーム相当、メンバー・招待
    oidcProvider + jwt他アプリ向け SSO（IdP）
    databaseHooks社員ドメイン検証、active チェック

    TOTP は認証アプリに表示される、30 秒ごとに変わるワンタイムパスワードです（MFA の基礎は パスワード・MFA・暗号化の基礎 を参照）。ban はアカウントを利用停止にすることです。

    認証基盤 auth.ts（概念例・抜粋） 
    // 認証基盤 auth.ts（概念例・抜粋）
import { betterAuth } from "better-auth";
import { admin, organization, twoFactor, oidcProvider, jwt } from "better-auth/plugins";

export const auth = betterAuth({
  emailAndPassword: { enabled: true },
  disabledPaths: ["/token"],
  plugins: [
    twoFactor(),
    admin(),
    organization({ /* カスタム role / permission */ }),
    jwt(),
    oidcProvider({
      loginPage: "/sign-in",
      consentPage: "/consent",
      useJWTPlugin: true,
      trustedClients: [
        {
          clientId: "app-a",
          clientSecret: process.env.APP_A_SECRET!,
          name: "業務アプリ A",
          type: "web",
          redirectUrls: ["https://app-a.corp.example.com/api/auth/callback/oauth2"],
          skipConsent: true,
        },
      ],
      getAdditionalUserInfoClaim: async (user) => ({
        department_id: user.departmentId,
        permissions: user.appPermissions,
      }),
    }),
  ],
});
    • trustedClients は、あらかじめ信頼する業務アプリ（OAuth クライアント）の一覧です。redirectUrls に登録した URL 以外には認可コードを返しません。
    • getAdditionalUserInfoClaim で、部署 ID や権限を UserInfo（ログイン中ユーザーの情報を返す OIDC 標準の窓口）に追加しています。
    目的やり方
    社員だけ招待制・社用ドメイン・banUser・カスタム active フラグ
    退職auth.api.banUser({ userId, banReason: "退職" }) → サインイン不可 + 既存セッション全失効

    7.7 業務アプリの Better Auth 設定（例）

    業務アプリ auth.ts（概念例・抜粋） 
    // 業務アプリ auth.ts（概念例・抜粋）
import { betterAuth } from "better-auth";
import { genericOAuth } from "better-auth/plugins";

export const auth = betterAuth({
  baseURL: "https://app-a.corp.example.com",
  plugins: [
    genericOAuth({
      config: [
        {
          providerId: "corp-auth",
          clientId: process.env.OAUTH_CLIENT_ID!,
          clientSecret: process.env.OAUTH_CLIENT_SECRET!,
          discoveryUrl: "https://auth.corp.example.com/.well-known/openid-configuration",
          scopes: ["openid", "profile", "email"],
        },
      ],
    }),
  ],
});

    discoveryUrl は、IdP の各エンドポイント（ログイン画面やトークン交換の URL など）をまとめて教えてくれる OIDC 標準の URL です。ブラウザ向けは BFF + HttpOnly セッション Cookie を推奨します。パスワードは認証基盤だけが保持し、業務アプリは持ちません。

    レイヤ担当

    権限は必要最小限にとどめるのが原則です（71 の 最小権限とデータ最小化 を参照）。

    7.10 SAML が必要な場合

    SSO プラグイン（@better-auth/sso） は、アプリを SAML SP（SAML でログインを頼む側＝サービスプロバイダ）として外部 IdP に繋ぐ用途です。自社認証基盤が IdP となって複数アプリに SSO する本構成では、まず OIDC Provider で足ります。将来 Entra 連携が必要になったら SSO プラグインを追加します。

    7.11 入退社・権限変更の伝播

    手段実装
    即時banUser / setRole / organization メンバー更新
    Webhook認証基盤から業務アプリへ POST（自前実装）
    定期同期Admin listUsers + updatedAt

    7.12 セキュリティ（Better Auth が担う例）

    • パスワードハッシュ・セッション管理・CSRF（フレームワーク連携）
    • OIDC 標準フロー（PKCE、redirect URI 検証、trustedOrigins）
    • MFA（twoFactor）、レート制限（設定可能）

    運用で足すもの

    HTTPS、監査ログ、秘密情報のローテーション（定期的な入れ替え）は、ライブラリではなく運用側で用意します。

    7.13 新規業務アプリの追加手順

    1. oidcProvider.trustedClients に client 登録
    2. 業務アプリに Better Auth + OIDC クライアント設定
    3. organization / カスタム permission でアプリ用ロール定義
    4. 結合テスト（ログイン → UserInfo → ban 後 401）

    401 は「認証されていない」ことを表す HTTP ステータスコードです。退職者を ban したあと、確かにアクセスできなくなることまで確認します。

    7.14 方式の比較（本要件）

    方式採用
    プロトコル完全自前（独自 code 交換のみ）不採用
    AWS IAM / Cognito不採用
    Better Auth + 自社 OIDC Provider採用
    Better Auth + Organization / Admin採用
    外部 Entra / Google任意（SSO プラグインで追加可）
    SAML外部 IdP 連携が必要になったら検討

    8.実装ファイル一覧（Next.js App Router 想定）

    「Auth フォルダ」「セッション用ファイル」を自分で書いていた場合、Better Auth では 役割が公式の置き場所に分かれます。セッションの生成・検証ロジック自体は auth.ts と /api/auth/* に集約 し、自前で session.ts に crypto（暗号処理）を書きません。

    8.1 認証基盤アプリ（1 台）— 最低限ほしいファイル

    auth-hub/                          # 例: auth.corp.example.com
├── .env.local
├── src/
│   ├── lib/
│   │   ├── auth.ts                # ① サーバー側の認証の「本体」
│   │   └── auth-client.ts         # ② ブラウザから auth API を呼ぶ窓口
│   ├── app/
│   │   ├── api/auth/[...all]/
│   │   │   └── route.ts           # ③ /api/auth/* を Better Auth に渡す
│   │   ├── (auth)/sign-in/page.tsx    # ④ ログイン画面（UI）
│   │   ├── (auth)/consent/page.tsx    # ⑤ OIDC 同意画面（任意）
│   │   └── (admin)/employees/page.tsx # ⑥ 入退社・権限 UI（自前）
│   ├── middleware.ts              # ⑦ 未ログイン → /sign-in へ

    app-a/

    8.3 各ファイルの役割

    ファイル担うこと自分で書く量
    lib/auth.tsDB 接続、プラグイン（admin / organization / oidcProvider 等）、パスワード・MFA・SSO のルール設定が中心（ロジックはライブラリ）
    lib/auth-client.tsログイン・ログアウト・useSession() などフロント用 API数行〜十数行
    api/auth/[...all]/route.tsPOST/GET /api/auth/sign-in 等 すべての認証 HTTP を処理ほぼ定型（コピペ可）
    sign-in/page.tsxメール・パスワード入力、authClient.signIn.email() 呼び出しUI は自前
    middleware.tsCookie のセッションを見て保護ページをガード十数行
    db/schema.tsテーブル定義npx auth generate で生成推奨
    (admin)/employees/page.tsx社員招待・ban・ロール変更完全自前（auth.api.banUser 等を呼ぶ）
    api/internal/employees/route.ts他アプリ向け社員一覧 API自前（サービス間トークン検証）

    ③ route.ts ＝ 昔の「Auth ルート一式」

    ここに sign-in / sign-out / callback がまとまるので、auth/login.ts をバラバラに書く必要はありません。

    ① auth.ts ＝ 昔の「セッション管理 + パスワード検証」

    ただし中身の実装は Better Auth が持ち、ここは設定ファイルに近いものです。

    8.4 ③ route.ts の中身（定型）

    // src/app/api/auth/[...all]/route.ts
import { auth } from "@/lib/auth";
import { toNextJsHandler } from "better-auth/next-js";

export const { GET, POST } = toNextJsHandler(auth);

    [...all] は Next.js の「それ以降のすべてのパスを受け取る」ルートの書き方です。/api/auth/ 以下へのリクエストをすべて Better Auth に渡します。

    8.5 ⑦ middleware.ts のイメージ

    // src/middleware.ts（概念例）
import { NextResponse } from "next/server";
import type { NextRequest } from "next/server";
import { getSessionCookie } from "better-auth/cookies";

export function middleware(request: NextRequest) {
  const session = getSessionCookie(request);
  if (!session && request.nextUrl.pathname.startsWith("/dashboard")) {
    return NextResponse.redirect(new URL("/sign-in", request.url));
  }
  return NextResponse.next();
}

    業務アプリでは、未ログイン時に authClient.signIn.oauth2({ providerId: "corp-auth" }) で認証基盤へ飛ばします。

    middleware は「入口の振り分け」

    getSessionCookie は Cookie が あるかどうか を見るだけです。Cookie の中身が本当に有効なセッションかは、サーバーが DB の session と照合して初めて分かります（9 章）。重要なデータを返す処理では、サーバー側でもセッションを検証します。

    9.DB：何を保存するか

    9.1 原則

    保存してよい絶対に平文で保存しない
    パスワードの ハッシュパスワード本体
    セッション用の ランダム tokenセッション token を推測可能な値（連番など）
    ユーザー ID・メール・部署 ID—
    OAuth の client_secret（環境変数推奨）ソースコードへの直書き

    ハッシュ は、元に戻せない形に変換した値です（詳しくは パスワード・MFA・暗号化の基礎）。

    • ブラウザの Cookie に入るもの … 多くの場合 セッション token（またはそれを指す署名付き Cookie）です。Cookie だけでは「誰か」は確定せず、サーバーが DB の session と照合 します。
    • .env の BETTER_AUTH_SECRET … DB には入れません。トークン署名・暗号化用の鍵（32 文字以上のランダム文字列）です。

    9.2 最低限の DB テーブル（コア 4 つ）

    Better Auth 本体が使うテーブルです。npx auth migrate または npx auth generate で作ります。

    user — 「社員」その人

    カラム意味例
    id社員の一意 ID（UUID 等）clx7abc...
    name表示名山田 太郎
    emailログイン ID 兼連絡先taro@corp.example.com
    emailVerifiedメール確認済みかtrue / false
    imageアイコン URL（任意）null
    createdAt / updatedAt作成・更新日時

    社員だけにしたいとき は、additionalFields で employeeNumber / departmentId を足すか、別テーブル employee_profile を userId で紐づけます。

    account — ログイン手段（パスワードはここ）

    1 人の user に、Google 連携・メール/パスワードなど 手段ごとに 1 行 作られます。

    カラム意味初心者メモ
    userIdどの社員かuser.id への外部キー
    providerId手段の種類メール/パスワードなら "credential"
    accountIdプロバイダ側 IDcredential なら多くの場合 userId と同じ
    passwordハッシュされたパスワード平文ではない。Better Auth が bcrypt 等で保存
    accessToken 等外部 SSO 用メール/パスワードだけなら空でよい

    users テーブルの password カラムはどこへ？

    昔「users テーブルに password カラム」としていた構成は、Better Auth では account.password（ハッシュ） に分かれるイメージです。

    session — 「今ログイン中」の印

    カラム意味初心者メモ
    idセッション行の IDDB 上の主キー
    userId誰のセッションか
    tokenランダムなセッション IDCookie と照合する値。推測困難な長い文字列
    expiresAtいつまで有効か過ぎたら未ログイン扱い
    ipAddress / userAgent端末の手がかり（任意）不正ログイン調査用

    退職・ban 時 は、該当 userId の session 行を削除します（Admin の banUser がやってくれます）。

    verification — 一時的な確認用

    メール確認リンク・パスワードリセット・MFA セットアップなど 短命のコード 用です。恒常的な社員データではありません。

    カラム意味
    identifier何の確認か（例：メールアドレス）
    value確認コード or トークン
    expiresAt有効期限

    プラグイン主な追加テーブル用途
    adminuser に role, banned, banReason 等管理者・退職 ban

    12.理解度チェック

    Q1. 社内システムで「社員だけ」がログインできるようにするとき、最も重要な判断は何ですか？

    どの IdP（Entra ID・Google Workspace・Okta など）に繋ぐかです。アプリは OIDC で IdP にログインを任せ、返ってきた ID トークンの email / sub / グループクレームで在籍社員かを判定します。許可ドメインや「全社員」グループでの制限を組み合わせます。

    Q2. 社員ログインに OAuth 2 だけ（OIDC なし）を使うのが勧められないのはなぜですか？

    OAuth 2 は第三者アプリにリソースへのアクセスを許可する 認可 のフレームワークで、「ログインした人が誰か」の保証が弱いからです。本人確認には、ID トークンを発行する OIDC を使います。

    Q3. 「JWT を使えば社員ログインは完成」という考えはなぜ誤りですか？

    JWT はトークンの 形式 で、ログイン 後 の状態をどう持つかの選択肢だからです。ログイン画面と本人確認（OIDC / SAML / パスワードなど）は別に必要です。

    Q4. 「認証基盤を自社で作るのは危ない」と言われるとき、本当に避けるべきなのは何ですか？

    認証基盤アプリを作ること自体ではなく、パスワードハッシュ・セッション固定や CSRF 対策・PKCE やトークン署名・MFA やレート制限などを ゼロから自前で書く ことです。Better Auth などのライブラリと標準プロトコルに任せ、部署マスタや入退社 UI など自社固有の部分だけを書きます。

    Q5. 社員が退職したとき、この設計ではどうやってアクセスを止めますか？

    認証基盤で auth.api.banUser({ userId, banReason: "退職" }) を呼びます。サインインできなくなり、その社員の session 行が削除されて既存セッションもすべて失効します。業務アプリへは Webhook や定期同期で伝え、結合テストで ban 後に 401 になることを確認します。

    Q6. Better Auth では、パスワードとログイン状態はそれぞれどのテーブルに保存されますか？

    パスワードは account テーブルの password カラムに ハッシュ として保存されます。ログイン状態は session テーブルに推測困難なランダム token と有効期限 expiresAt として保存され、ブラウザの Cookie の token と照合されます。

    Q7. BETTER_AUTH_SECRET はどこに置き、どのような値にしますか？

    DB やソースコードではなく、.env などの環境変数に置きます。トークン署名・暗号化用の鍵なので、openssl rand -base64 32 などで作った 32 文字以上のランダムな文字列にします。
