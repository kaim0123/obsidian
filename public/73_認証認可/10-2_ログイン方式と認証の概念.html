    10 基礎概念

    ログイン方式と認証の概念

    パスワード、Basic 認証、API キー、セッション、JWT、OAuth 2.0、OpenID Connect、SSO、SAML、LDAP、MFA、パスキーにつながる生体認証……。ログインまわりには似た言葉がたくさん出てきます。このページでは、それぞれの仕組み・メリット・デメリット・使いどころを整理し、さらに「どれが認証方式で、どれがトークンの形式やUXのパターンなのか」という、開発者が混同しやすい点をほどいていきます。

    もとにしたノート：10_基礎概念/03_ログインの種類と認証方式、10_基礎概念/04_開発者が知るべき認証の7つの概念（Hayk Simonyan）

    ひとことで言うと

    認証が答える問いは 「リクエストしてきたのは誰か？」 の1つだけです。その答え方には、パスワードやセッションのような 認証方式 のほかに、JWT のような トークンの形式、Bearer のような 運用パターン、OAuth 2.0 のような 認可フレームワーク、SSO のような UX パターン が組み合わさっています。「それは何の種類の言葉か」を意識すると、ログインの仕組みがぐっと見通しやすくなります。

    認証と認可そのものの違いは、前のページ 認証と認可の違い で説明しました。このページはその続きとして、「認証（本人確認）をどうやって行うか」の具体的な方式を見ていきます。

    1.まず整理：開発者が混同しやすい5つの点

    Hayk Simonyan 氏の動画「7 Authentication Concepts Every Developer Should Know」では、最初に次のような混同をよくある間違いとして挙げています。

    よくある誤解実際は
    認証方式と認可フレームワークは同じもの別物です。認証方式 は「誰か」を確かめる方法、認可フレームワーク は「何にアクセスしてよいか」を決める枠組みです
    JWT は認証方式であるJWT は トークンの形式（フォーマット） です
    Bearer ＝ JWTBearer は「トークンを持っている者にアクセスを与える」という パターン で、JWT そのものではありません
    OAuth 2 は認証方式であるOAuth 2 は 認可フレームワーク です
    SSO は認証方式であるSSO（シングルサインオン）は「一度ログインすれば複数サービスにアクセスできる」という UX パターン です

    UX（ユーザーエクスペリエンス）は、使いやすさや使い心地のことです。

    ツールの画面も混同のもと

    API を試すツールの Postman では、Basic / Digest / API Key / Bearer などが「認証タイプ（Auth Type）」として同じリストに並んでいます。画面をシンプルにするための見せ方ですが、そのせいで「方式」「フレームワーク」「UX」が余計に混ざりやすい、と動画では指摘されています。

    各用語がどの種類に入るかの一覧は、このページの最後（15. 全体の整理）にまとめています。

    2.認証とは何か：「リクエストしてきたのは誰か？」

    システムが何かを許可したり制限したりする前に、まず リクエストしてきた相手が誰なのか を知る必要があります。相手はブラウザやモバイルアプリから使う人間のユーザーのこともあれば、外部のサービス（プログラム）のこともあります。相手が名乗った通りの本人かを確かめるのが認証です。

    典型的な流れは次のとおりです。

    1. ユーザーまたは別サービスが、API ゲートウェイ（API の入口になるサーバー）などにアクセスする
    2. ログイン（資格情報＝パスワードなど本人であることを示す情報の提示）で身元を確認する
    3. 有効なら、システム内の API・サービス・データへのアクセスを許可する
    4. 無効なら 401 Unauthorized（「認証されていない」を表す HTTP ステータスコード）を返す

    認可（アクセスできるリソースや操作の範囲を決めること）は、この後の別ステップとして扱います。認可モデルの詳しい話は、後の「40 認可モデル」のページで扱う予定です。

    3.ユーザー名／パスワード認証

    最も基本的な認証方式です。ユーザー名（またはメールアドレス）とパスワードの組み合わせで認証を行います。

    メリット

    • 実装が簡単：基本的な認証方式で、多くのシステムで標準的に使われている
    • ユーザーに馴染みがある：ユーザーが最も慣れ親しんでいる認証方式
    • 追加の外部サービスが不要：自社で完全に管理できる
    • コストが低い：特別なインフラやサービスが不要

    デメリット

    • セキュリティリスク：パスワードの漏洩、推測、再利用のリスクがある
    • ユーザーの負担：強力なパスワードの管理がユーザーに委ねられる
    • パスワードリセット機能が必要：忘れた場合の対応が必要
    • ブルートフォース攻撃に脆弱：総当たりでパスワードを試す攻撃のこと。レート制限（一定時間内の試行回数の制限）などの対策が必要

    適用例：一般的な Web アプリケーション、企業内システム、会員制サイト。

    パスワードの安全な保存方法（ハッシュ化）やパスワードポリシーは、次のページ パスワード・MFA・暗号化の基礎 と、71 の パスワードの保存：平文・MD5・bcrypt で扱います。

    4.HTTP の古典的な方式：Basic 認証と Digest 認証

    ここからは、HTTP リクエストで「誰か」を伝える具体的な方式を見ていきます。まずは昔からある2つです。

    4.1 Basic 認証

    最も単純な方式です。

    1. 資格情報なしでリソース（例：GET /api/users）にアクセスすると、サーバーは 401 を返して資格情報を求める
    2. 次のリクエストで、Authorization ヘッダに Base64 エンコードした username:password を付ける
    3. サーバーで検証し、成功なら 200 OK とデータを返す。失敗なら再び 401

    Base64 は、データを英数字と記号だけの文字列に置き換える 変換方式 です。鍵を使わないので、暗号化ではありません。

    Basic 認証のヘッダ：Base64 は誰でも元に戻せる 
    # 送られるヘッダ（"user:pass" を Base64 にしたもの）
Authorization: Basic dXNlcjpwYXNz

# 盗み見た人はすぐに元に戻せる
$ echo dXNlcjpwYXNz | base64 -d
user:pass

    Basic 認証の弱点

    • Base64 は暗号化ではなく、容易に復号できます。
    • 通信を暗号化する HTTPS が必須 です。それでも 毎リクエストで資格情報そのものを送る ため、本番の外部向け API ではほとんど使われません（社内ツール程度）。

    4.2 Digest 認証

    Basic 認証と似た流れ（まず 401 → 資格情報を付けて再リクエスト → 成功なら 200、失敗なら 401）ですが、パスワードを平文で送らず、MD5 ハッシュ にした値を送る点でやや改善されています。ハッシュ とは、データから元に戻せない固定長の値を計算することです（詳しくは 71 の 暗号技術の用語 を参照）。

    ただし MD5 は古いハッシュ関数で、後で紹介するセッションや JWT などの現代的な選択肢と比べると レガシー（時代遅れ） とみなされることが多く、今はほとんど使われません。

    5.API キー認証

    クライアント（API を使う側）ごとに 一意のキー を発行し、リクエストのたびに Authorization ヘッダまたは X-API-Key ヘッダで送ってもらう方式です。SaaS のダッシュボードで「API キーを生成」して、そのキーを付けて API を呼び出す体験は、多くがこの方式です。

    API キーを付けたリクエストの例 
    GET /api/users HTTP/1.1
Host: api.example.com
X-API-Key: 8f3a9c1e7b2d4f60a5e1c9d7b3f2a8e4
    • サーバー側では、キーそのものではなくキーの ハッシュ と、そのキーの スコープ（権限範囲） を DB などに保存しておきます。
    • リクエストが来たら、権限やユーザーのテーブルを ルックアップ（検索） してキーを検証します。
    状況レスポンス
    キーが有効成功レスポンス（データを返す）
    キーが無効401 Unauthorized
    ヘッダ自体がない400 Bad Request（キー必須の設計の場合。リクエストの形が不正という扱い）

    API キーの弱点

    • キーが漏洩すると、誰でもなりすまし可能 です。有効期限は組み込まれていないので、自前で設けない限りずっと使えてしまいます。
    • キーは ランダムな文字列 で、JWT のように中に情報は入っていません。そのため 所有者や権限を知るには毎回 DB を参照する 必要があります。

    「毎回ヘッダに秘密の値を載せる」という点で JWT と似て見えますが、API キーは 自己完結しない（キーだけでは誰のものか分からない）のが大きな違いです。

    6.セッション認証（従来の Web）

    従来の Web アプリで使われてきた方式です。ユーザーがログインすると、サーバー側の セッションストレージ（ログイン状態を保存しておく場所）にセッションを作り、クライアントには セッション ID（ログイン状態を表す番号）を Cookie で返します。以降のリクエストでは、ブラウザが Cookie のセッション ID を自動で送り、サーバーはそれでストレージを参照します。有効ならユーザーデータを取得して応答し、見つからなければ認証されていないとして 401 を返します。

    セッションストアには次のような選択肢があります。

    方式特徴
    メモリ単純（変数に置くだけ）だが、サーバーの再起動やクラッシュで消える
    Redis高速で、TTL（有効期限）を標準で持つ。本番でよく使われる定番
    SQL DB永続化できる
    ファイルシステムスケールしにくく、使われることは稀

    セッション認証の特徴：ステートフル

    セッション認証は ステートフル、つまりサーバーがセッションを「覚えている」必要があります。従来の Web アプリには向いていますが、サーバーを何台にも分けた API や マイクロサービス（機能ごとに小さなサービスへ分けた構成）では、ストアを共有する必要があるためスケールが難しくなりがちです。

    セッション ID の発行・Cookie の属性・セッション固定攻撃などの詳しい話は 74_セッション管理 で扱います。Cookie の HttpOnly・Secure・SameSite 属性は 72 の Cookie はどう付いていくのか、Cookie が自動送信されることを悪用する攻撃は CSRF を参照してください。

    7.トークンベース認証：Bearer と JWT

    セッションの代わりに、現代のアプリでは トークン（ログイン済みであることを示す文字列）を使うことが多くなっています。認証後に発行されたトークンを、クライアントがリクエストのたびに送る方式です。

    7.1 Bearer はパターン、JWT は形式

    Bearer（ベアラー＝持参人）は、「このトークンを持っている主体にアクセスを与える」という運用パターンです。特定の方式ではありません。トークンは Authorization: Bearer <token> の形でヘッダに載せます。

    Bearer トークンの実体として最も一般的なのが JWT（JSON Web Token、ジョット） です。JWT は 署名付きの JSON で、次のような情報（クレームと呼びます）を中に含められます。

    • ユーザー ID、メールアドレス
    • 有効期限（exp）
    • ロール・権限など
    Bearer トークンとして送る JWT と、その中身（ペイロード）の例 
    Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ1MTIzIn0.xxxxx

// ペイロード部分を読むと、たとえばこんな JSON が入っている
{
  "sub": "u123",                 // ユーザー ID
  "email": "taro@example.com",
  "role": "editor",              // ロール
  "exp": 1767225600              // 有効期限（UNIX 時刻）
}

    JWT の中身は Base64URL で変換されているだけで、誰でも読めます。改ざんされていないことは 署名 で確かめますが、秘密にしたい情報は入れてはいけません。

    7.2 ログイン後の流れ

    1. 初回だけ資格情報（ユーザー名とパスワードなど）を検証する
    2. 有効なら JWT を発行してクライアントに返す
    3. 以降は Authorization: Bearer <token> で送ってもらい、サーバーは 署名をローカルで検証 する（多くの場合 DB 不要）
    4. 有効ならデータを返し、無効なら 401

    7.3 セッションとの比較

    セッションJWT（典型的な使い方）
    状態サーバーがセッションを保持（ステートフル）ステートレス（トークンが自己完結）
    検証ストアを参照署名を検証
    スケールストアの共有が課題分散しやすい

    JWT 以前のトークンは、中に情報を持たない 不透明トークン（ただの文字列）で、使うたびに DB やキャッシュを参照する必要がありました。つまりステートフルでした。JWT はクレームをトークン内に載せられるため、DB 負荷の軽減 と 検証の簡素化 に役立ちます。

    7.4 トークンベース認証のメリット・デメリット

    メリット

    • ステートレス：サーバー側でセッションを管理する必要がない
    • スケーラビリティ：複数のサーバー間で共有できる
    • モバイル対応：モバイルアプリとの連携が容易
    • マイクロサービス対応：分散システムに適している

    デメリット

    • トークンの有効期限管理：適切な有効期限の設定が必要
    • トークンの無効化が困難：一度発行したトークンは、通常、有効期限まで無効化できない
    • セキュリティリスク：トークンが漏洩すると、有効期限まで使われる可能性がある
    • 実装の複雑さ：トークンの生成・検証・更新のロジックが必要

    適用例：RESTful API、マイクロサービスアーキテクチャ、モバイルアプリのバックエンド、SPA（Single Page Application：1枚のページを JavaScript で書き換えながら動く Web アプリ）。

    8.アクセストークンとリフレッシュトークン

    「漏れたら有効期限まで使われる」という弱点を小さくするため、現代のシステムでは多くの場合、寿命の違う2種類のトークンを組み合わせます。

    種類寿命用途
    アクセストークン短い（15分〜1時間程度）API 呼び出し
    リフレッシュトークン長い（数日〜数週間）新しいアクセストークンの取得
    1. ログイン時に、アクセストークンとリフレッシュトークンの両方を発行する
    2. クライアントはアクセストークンで API を呼び出し、リフレッシュトークンは保管しておく
    3. アクセストークンの期限が切れて 401 になったら、リフレッシュトークンで認証サーバーに再発行を依頼する
    4. 新しいアクセストークンで API の呼び出しを再開する。ユーザーは資格情報を入れ直さずにログイン状態が続く

    リフレッシュトークンは長く使えるぶん、盗まれたときの被害が大きくなります。保存場所に注意が必要です。

    危険な例：リフレッシュトークンを localStorage に置く 
    // JavaScript から自由に読めるので、XSS があると盗まれる
localStorage.setItem('refresh_token', data.refreshToken);
    安全な例：サーバーが HttpOnly Cookie で渡す 
    Set-Cookie: refresh_token=...; HttpOnly; Secure; SameSite=Strict; Path=/auth/refresh

    localStorage はブラウザにデータを保存する仕組みで、ページ上の JavaScript から読み書きできます。そのため XSS（攻撃者のスクリプトをページで実行させる攻撃）があると盗まれやすくなります。HttpOnly を付けた Cookie は JavaScript から読めないので、こうした保存方法が推奨されます。

    9.OAuth 2.0 と OpenID Connect（ソーシャルログイン）

    「Google でログイン」「GitHub でログイン」のように、Google・Facebook・Twitter・GitHub などの外部サービス（アイデンティティプロバイダー（IdP）＝本人確認を引き受けるサービス）のアカウントを使ってログインする方式を ソーシャルログイン と呼びます。その裏側で使われているのが OAuth 2.0 と OpenID Connect です。ノートの言葉でまとめると、OAuth 2.0 は認可のための仕組み、OpenID Connect は認証のための仕組み です。

    9.1 OAuth 2.0：認可フレームワーク

    OAuth 2.0 は 認可フレームワーク です。答える問いは「このアプリは、ユーザーに代わって何にアクセスできるか」で、単体では「ユーザーが誰か」をアプリに伝えません。

    例として、外部アプリにあなたの Google Drive のファイルを読ませる場合を考えます。

    1. アプリがユーザーを Google の 同意画面（「このアプリに Drive の読み取りを許可しますか？」という画面）へリダイレクトする
    2. ユーザーが許可すると、認可コード（一時的な引換券）がアプリに返る
    3. アプリが認可コードを アクセストークン と交換する
    4. アプリはそのアクセストークンで Drive API を呼び出し、ファイルを取得する

    ここが混同ポイント

    このとき得るアクセストークンは「Drive にアクセスしてよいという 権限の証明」です。アクセストークンを受け取れたからといって、アプリは「あなたが誰か」を確かめたわけではありません。OAuth 2.0 のアクセストークンは本人確認（認証）そのものではない、という区別が重要です。

    9.2 OpenID Connect（OIDC）：OAuth 2.0 の上の認証レイヤー

    OpenID Connect（OIDC） は、OAuth 2.0 の上に 認証のレイヤー（層） を載せたものです。「Google でサインイン」などで使われます。

    1. 認可エンドポイント（IdP のログイン受付窓口）へリダイレクトし、ユーザーがログイン・同意する
    2. アプリが認可コードを受け取る
    3. コードをトークンと交換すると、アクセストークン（OAuth 2.0 の認可用）に加えて ID トークン（JWT 形式で、メールアドレスやユーザー ID などの 本人情報 が入っている）が返る
    4. アプリは ID トークンの署名を検証して身元を確定し、そのうえで自前のセッションやアクセストークンを発行できる

    現代の「Sign in with Google / GitHub / Microsoft」の多くは、この OIDC 系統です。安全でスケールしやすい現代的な方法とされています。OAuth 2.0 や OIDC のフロー（認可コードフローや PKCE など）の詳細は、後の「30 フェデレーション」のページで扱う予定です。

    9.3 ソーシャルログインのメリット・デメリット

    メリット

    • ユーザー体験が良い：新規登録の手間が減り、ログインが簡単
    • パスワード管理の負担がない：ユーザーがパスワードを覚える必要がない
    • セキュリティが高い：大手プロバイダーのセキュリティ対策を利用できる
    • 登録率の向上：登録のハードルが下がり、ユーザー獲得に有利

    デメリット

    • 外部依存：プロバイダーのサービス停止やポリシー変更の影響を受ける
    • プライバシーへの懸念：ユーザー情報が外部サービスと共有される
    • 実装の複雑さ：OAuth 2.0 の実装には専門知識が必要
    • プロバイダーごとの対応が必要：複数のプロバイダーに対応すると実装が複雑になる

    適用例：消費者向け Web アプリケーション、モバイルアプリ、スタートアップのサービス。

    10.シングルサインオン（SSO）とアイデンティティプロトコル（SAML・OIDC）

    10.1 SSO は「UX パターン」

    シングルサインオン（SSO） は、一度ログインすれば、関連する複数のアプリケーションやサービスに自動的にログインできる仕組みです。たとえば Google（や Okta）に一度ログインすれば、Gmail・Drive・YouTube・カレンダーに再ログインなしでアクセスできます。SSO そのものは認証方式ではなく UX パターン で、下層では次に説明する SAML や OIDC などの アイデンティティプロトコル（身元を伝えるための通信の取り決め）を使います。

    1. Google などの IdP に一度ログインすると、IdP 側のセッションストアに グローバルセッション が保存される
    2. クライアントに SSO 用の Cookie が付与される
    3. 別のサービス（例：Drive）に初めてアクセスしたときも、IdP でセッションを検証するだけで通過できる
    4. 以降のサービス（YouTube、カレンダーなど）も同様に、セッション検証だけで済む

    SSO のメリット

    • ユーザー体験が良い：複数のパスワードを覚える必要がない
    • 管理が容易：管理者が一元的にユーザーを管理できる
    • セキュリティ向上：パスワードの再利用が減り、一元管理でセキュリティポリシーを統一できる
    • 生産性向上：ログインの手間が減り、業務効率が上がる

    SSO のデメリット

    • 実装が複雑：SAML、OAuth 2.0、OpenID Connect などのプロトコル理解が必要
    • 初期コストが高い：専用のソリューションやインフラが必要
    • 単一障害点：SSO サービスが止まると、すべてのサービスにアクセスできなくなる
    • セキュリティリスク：SSO アカウントが侵害されると、すべてのサービスが危険にさらされる

    適用例：企業内システム（複数のアプリケーション）、クラウドサービスの統合、教育機関のシステム。

    10.2 アイデンティティプロトコル：SAML と OIDC

    プロトコル形式・用途備考
    SAMLXML ベース。エンタープライズやレガシー（Salesforce、社内ダッシュボードなど）で今も広く普及ログイン画面へリダイレクトされ、ログイン後に SAML アサーション（XML で書かれた「この人は本人です」という証明書）で身元を確認
    OIDCJWT 形式の ID トークン。Google などモダンなサービスで主流SAML より新しく、JSON / JWT の仕組みと相性が良い

    どちらも SSO と組み合わせて使われ、いずれも安全で現役の選択肢です。

    10.3 SAML 認証のメリット・デメリット

    SAML（Security Assertion Markup Language）は、企業向けの SSO で使われるプロトコルです。

    メリット

    • 企業向けに標準化：多くの企業システムでサポートされている
    • 一元管理：企業の ID プロバイダーで一元的に管理できる
    • セキュリティ：XML 署名と暗号化による高いセキュリティ
    • コンプライアンス：企業のセキュリティポリシーに準拠しやすい

    デメリット

    • 実装が複雑：XML ベースで、実装が複雑
    • モバイル対応が弱い：主に Web アプリケーション向け
    • 初期設定が大変：証明書の管理、メタデータ（設定情報）の交換などが必要
    • デバッグが困難：XML の構造が複雑で、問題の特定が難しい

    適用例：企業の内部システム、クラウドサービスのエンタープライズ版、教育機関のシステム。

    11.LDAP／Active Directory 認証

    LDAP（Lightweight Directory Access Protocol：ユーザーや組織の情報を保存した「ディレクトリ」にアクセスするためのプロトコル）や、Microsoft の Active Directory（社内のユーザー・PC をまとめて管理する仕組み）を使い、既存のディレクトリサービスと連携して認証する方式です。

    メリット

    • 既存インフラの活用：企業の既存のディレクトリサービスを利用できる
    • 一元管理：ユーザー情報を一元的に管理できる
    • コスト削減：新たなユーザー管理システムを構築する必要がない
    • 統合性：企業の既存システムと統合しやすい

    デメリット

    • オンプレミス依存：多くの場合、オンプレミス（自社で設置・運用する）のインフラが必要
    • 設定が複雑：LDAP の設定や Active Directory との連携が複雑
    • スケーラビリティ：大規模なシステムではパフォーマンスの問題が起こる可能性
    • クラウド対応：クラウドネイティブなアプリケーションとの統合が難しい場合がある

    適用例：企業の内部システム、オンプレミスのアプリケーション、大学や研究機関のシステム。社内システムでどれを選ぶかは 社内システム向け認証方式の選び方 で詳しく扱います。

    12.認証を強くする・パスワードをなくす：MFA・パスワードレス・生体認証

    ここまでの方式とは別の軸として、「パスワードだけに頼らない」ための方式があります。それぞれの仕組みの詳細は次のページ パスワード・MFA・暗号化の基礎 や、後の「20 パスワード・MFA・パスキー」のページで扱う予定です。ここでは特徴だけを押さえます。

    12.1 多要素認証（MFA）

    2つ以上の異なる 認証要素（知識＝知っているもの、所有物＝持っているもの、生体情報＝本人の体の特徴）を組み合わせて認証する方式です。例：パスワード ＋ SMS コード、パスワード ＋ 認証アプリのコード。

    メリット

    • セキュリティが非常に高い：単一要素の認証よりはるかに安全
    • 不正アクセスの防止：パスワードが漏洩しても、第二要素がなければアクセスできない
    • コンプライアンス対応：多くの規制要件（PCI DSS、GDPR など）で推奨・必須
    • 柔軟な実装：ハードウェアトークン、SMS、アプリ、生体認証などさまざまな方式がある

    デメリット

    • ユーザー体験の低下：ログインに追加の手順が必要
    • 実装コスト：追加のインフラやサービスが必要
    • 運用コスト：SMS 送信などに継続的なコストがかかる場合がある
    • デバイス依存：スマートフォンやトークンが必要な場合がある

    適用例：金融機関のシステム、企業の機密情報システム、クラウドサービス（AWS、Azure など）、医療情報システム。MFA とパスキーの位置づけは 71 の MFA・パスキー、そして「自前実装しない」 も参考になります。

    12.2 パスワードレス認証

    パスワードを使わず、メールや SMS に送られた ワンタイムコード（一度だけ使える使い捨てのコード）や、マジックリンク（クリックするだけでログインできる URL）で認証する方式です。

    メリット

    • パスワード管理の負担がない：ユーザーがパスワードを覚える必要がない
    • セキュリティ向上：パスワード漏洩のリスクがない
    • ユーザー体験：メールや SMS のリンクをクリックするだけ
    • パスワードリセット機能が不要：パスワードがないため、リセット機能もいらない

    デメリット

    • メール／SMS アカウントのセキュリティに依存：メールや SMS が侵害されると危険
    • デバイス依存：メールや SMS を受信できるデバイスが必要
    • 実装の複雑さ：ワンタイムコードの生成、有効期限管理などが必要
    • コスト：SMS 送信にコストがかかる場合がある

    適用例：モバイルアプリ、一時的なアクセスが必要なサービス、パスワード管理を簡素化したいサービス。

    12.3 生体認証

    指紋、顔、虹彩、声紋などの生体情報を使って認証する方式です。

    メリット

    • ユーザー体験が非常に良い：簡単で速い認証
    • セキュリティが高い：生体情報は他人に渡すことができない
    • パスワード不要：パスワードを覚える必要がない
    • 偽造が困難：生体情報の偽造は技術的に難しい

    デメリット

    • デバイス依存：生体認証に対応したデバイスが必要
    • プライバシーへの懸念：生体情報の収集・保存に対する懸念
    • 誤認率：環境や体の状態によって誤認証が起こる可能性
    • 変更不可：生体情報が漏洩した場合、パスワードのように変更できない
    • コスト：専用のハードウェアやソフトウェアが必要

    適用例：スマートフォンのロック解除、企業の入退室管理、金融機関の ATM、空港の入国審査。

    13.AWS Cognito：複数の方式をまとめて提供するサービス

    AWS Cognito は、AWS が提供する マネージド認証サービス（サーバーの運用を AWS に任せられる認証サービス）です。ここまでに紹介した認証方式の多くを、1つのサービスでまとめてサポートしています。

    13.1 Cognito がサポートする認証方式

    認証方式Cognito での実現方法
    ユーザー名／パスワード認証Cognito User Pools で標準的にサポート。カスタム属性の追加も可能
    ソーシャルログイン（OAuth 2.0 / OIDC）Google、Facebook、Amazon、Apple、その他の OIDC プロバイダーに対応。簡単な設定で統合できる
    多要素認証（MFA）SMS ベースの MFA、TOTP（Time-based One-Time Password：時刻をもとに30秒ごとなどに変わるコード）アプリベースの MFA、ソフトウェアトークン MFA
    シングルサインオン（SSO）Cognito Identity Pools と User Pools を組み合わせて実現。SAML 2.0 ID プロバイダーとの統合も可能
    パスワードレス認証メールベースのワンタイムパスワード、SMS ベースの認証コード
    トークンベース認証（JWT）認証後に JWT を発行。ID トークン、アクセストークン、リフレッシュトークンを提供
    SAML 認証SAML 2.0 ID プロバイダーとの統合をサポート（エンタープライズ向け機能）
    LDAP／Active Directory 認証AWS Directory Service（AD Connector）と連携して実現可能。既存の Active Directory と統合

    13.2 Cognito の構成要素

    Cognito User Pools

    • ユーザー認証とユーザー管理
    • ユーザー登録、ログイン、パスワードリセット
    • ソーシャルログイン、MFA、カスタム認証フロー

    Cognito Identity Pools

    • AWS リソースへの一時的な認証情報の提供
    • フェデレーテッドアイデンティティ（外部の IdP で確認した身元を受け入れること）の管理
    • 未認証ユーザーへのアクセス許可

    13.3 Cognito のメリット・デメリット

    メリット

    • マネージドサービス：インフラの管理が不要
    • スケーラビリティ：自動的にスケールする
    • 複数の認証方式を統合：1つのサービスで複数の認証方式をサポート
    • AWS サービスとの統合：Lambda、API Gateway、AppSync などと簡単に統合
    • コスト効率：使用量ベースの料金で、初期費用なし
    • セキュリティ：AWS のセキュリティベストプラクティスを適用

    デメリット

    • AWS 依存：AWS エコシステムに依存する
    • 学習曲線：設定やカスタマイズには知識が必要
    • カスタマイズの制限：完全なカスタマイズには限界がある
    • コスト：大規模なユーザーベースではコストがかかる可能性

    Cognito は「組み合わせ」が強み

    AWS Cognito は、上記の認証方式のほとんどをサポートする包括的な認証サービスです。単一の方式に限定されず、複数の認証方式を組み合わせて使える のが大きな特徴です。特に次の組み合わせが強力です。

    • ユーザー名／パスワード ＋ ソーシャルログイン ＋ MFA
    • SAML SSO ＋ トークンベース認証
    • パスワードレス認証 ＋ JWT

    14.認証方式の選び方

    14.1 用途別の推奨

    用途推奨認証方式

    企業向けシステムSSO（SAML）、LDAP／Active Directory
    金融・医療システムMFA、生体認証
    モバイルアプリソーシャルログイン、トークンベース認証

    14.2 セキュリティレベル別

    セキュリティレベル推奨認証方式

    中（個人情報）ソーシャルログイン、パスワードレス認証

    16.まとめ

    • 認証が答える問いは「リクエストしてきたのは誰か？」。認証に失敗したら 401 を返し、「何ができるか」は認可で別に決めます。
    • Basic 認証 は Base64 で資格情報を毎回送るだけ、Digest 認証 は MD5 を使うがレガシー。どちらも現代の外部向け API ではほぼ使われません。
    • API キー は中身のない不透明な文字列で、所有者や権限は DB 参照が必要。漏れると有効期限なしでなりすましされます。
    • セッション認証 はステートフル（サーバーが覚える）、JWT はステートレス（署名をローカル検証）。JWT は「形式」、Bearer は「パターン」です。
    • トークンは 短命のアクセストークン ＋ 長命のリフレッシュトークン で運用し、リフレッシュトークンは localStorage ではなく HttpOnly Cookie に置きます。
    • OAuth 2.0 は認可（アクセストークン＝権限の証明）、OIDC は認証（ID トークン＝本人の証明）。ソーシャルログインの多くは OIDC です。
    • SSO は UX パターン で、下層では SAML（XML・企業向け）や OIDC（JWT・モダン）が使われます。
    • LDAP／AD、MFA、パスワードレス、生体認証、Cognito など、方式にはそれぞれメリット・デメリットがあり、用途とセキュリティレベルに応じて組み合わせて選ぶ のが基本です。

    17.理解度チェック

    Q1. 「JWT 認証を使っています」という言い方は、何が不正確なのでしょうか？

    JWT は認証方式ではなく、トークンの形式（フォーマット） だからです。正確には「ログイン時に資格情報を検証し、その結果を JWT 形式の Bearer トークンとして発行している」といった構成です。Bearer は「持っている者にアクセスを与える」パターン、JWT はそのトークンの中身の形式です。

    Q2. Basic 認証のヘッダは文字列が読めないので、盗み見られても安全ですか？

    安全ではありません。Base64 は暗号化ではなく単なる変換なので、誰でもすぐに username:password に戻せます。HTTPS が必須で、しかも毎リクエストで資格情報を送るため、本番の外部向け API ではほとんど使われません。

    Q3. API キーと JWT は、どちらも毎回ヘッダに載せて送ります。大きな違いは何ですか？

    API キーは情報を持たない ランダムな文字列 で、誰のキーか・どんな権限かを知るには毎回 DB を参照する必要があります（自己完結しない）。JWT は署名付きの JSON で、ユーザー ID・有効期限・ロールなどのクレームを中に含められるため、多くの場合 DB を見ずに署名検証だけで済みます。

    Q4. セッション認証が分散システムやマイクロサービスでスケールしにくいのはなぜですか？

    セッション認証は ステートフル で、サーバーがセッションを覚えておく必要があるからです。サーバーが複数あると、どのサーバーでも同じセッションを参照できるようにストア（Redis など）を共有しなければならず、それが課題になります。

    Q5. アクセストークンとリフレッシュトークンを分けるのはなぜですか？ また、リフレッシュトークンはどこに保存すべきですか？

    API 呼び出しに使うアクセストークンを短命（15分〜1時間程度）にして、漏れたときの被害期間を短くするためです。長命のリフレッシュトークンで新しいアクセストークンを取り直すので、ユーザーは何度もログインし直さずに済みます。リフレッシュトークンは XSS で盗まれやすい localStorage ではなく、JavaScript から読めない HttpOnly Cookie に保存します。

    Q6. OAuth 2.0 で Google Drive のアクセストークンを受け取ったアプリは、「ユーザーが誰か」を確認できたことになりますか？

    なりません。OAuth 2.0 のアクセストークンは「Drive にアクセスしてよい」という 権限の証明 で、本人確認ではありません。ユーザーが誰かを知るには、OAuth 2.0 の上に認証レイヤーを載せた OpenID Connect を使い、ID トークン（JWT）の署名を検証して本人情報を取り出します。

    Q7. SSO と SAML・OIDC の関係を説明してください。また、SSO の弱点を1つ挙げてください。

    SSO は「一度ログインすれば複数サービスを使える」という UX パターン で、それを実現する下層の アイデンティティプロトコル が SAML（XML、企業・レガシー向け）や OIDC（JWT、モダンなサービス向け）です。弱点としては、SSO サービスが止まるとすべてのサービスが使えなくなる 単一障害点 になることや、SSO アカウントが侵害されるとすべてのサービスが危険にさらされることがあります。

    Q8. 企業向けの社内システムと、金融・医療システムでは、それぞれどんな認証方式が推奨されていましたか？

    企業向けシステムでは SSO（SAML）や LDAP／Active Directory、金融・医療システムでは MFA や生体認証（最高レベルでは MFA ＋ 生体認証、ハードウェアトークン）が推奨されています。
