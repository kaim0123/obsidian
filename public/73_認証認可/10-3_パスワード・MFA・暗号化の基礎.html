    1.認証と認可：似ているようで全然違う

    まず土台となる 2 つの言葉をおさらいします。詳しくは 認証と認可の違い で解説しているので、ここでは要点だけを確認します。

    認証（Authentication）

    「あなたは誰ですか？」 を確認すること。

    • 会社の入口で ID カードをかざす →「田中さんですね」
    • ログイン画面で ID・パスワードを入力 →「このアカウントの持ち主ですね」
    • スマホの顔認証 →「あなた本人ですね」

    認可（Authorization）

    「あなたは何ができますか？」 を確認すること。

    • 入館できても「社長室には入れない」
    • ログインできても「管理者ページは見られない」
    • ファイルにアクセスできても「削除はできない（読み取りのみ）」

    処理の順番は「アクセス要求 →【認証】ID とパスワードで本人確認 →【認可】権限・ロール（役割）を確認（管理者なら全操作 OK、一般ユーザーなら読み取りのみ）→ 許可または拒否」です。ホテルにたとえると、認証＝チェックイン時の身分証確認、認可＝カードキーの権限設定（305 号室には入れるが 501 号室には入れない、レストランは使えるが VIP ラウンジは NG）です。

    2.パスワードの仕組みと安全な保存

    2.1 やってはいけない保存方法

    保存方法何が起きるか
    平文保存（password123 をそのまま保存）データベース（DB）が漏洩したら、全員のパスワードが即座にバレる
    暗号化して保存（元に戻せる＝可逆）暗号化の鍵が漏れたら、全パスワードが解読される

    2.2 正しい保存方法：ハッシュ化

    ハッシュ関数 は、入力データから決まった長さの値（ハッシュ値）を作る関数です。パスワードそのものではなく、ハッシュ値だけを保存します。

    「password123」→ SHA-256 → 「ef92b778bafe771...」（これを保存）

    ハッシュ値には次の特徴があります。

    1. 元のパスワードに戻せない（一方向性）
    2. 同じ入力なら必ず同じ出力 になる
    3. 少しでも違う入力なら全く違う出力 になる

    ログイン時は、入力されたパスワードを同じ方法でハッシュ化し、保存済みのハッシュ値と比較します。一致すれば認証 OK です。サーバーはパスワードそのものを知らなくても、本人確認ができます。

    2.3 ハッシュだけでは不十分：レインボーテーブル攻撃

    レインボーテーブル攻撃 とは、「よく使われるパスワードのハッシュ値」をあらかじめ大量に計算して表（テーブル）にしておき、漏洩したハッシュ値と突き合わせるだけでパスワードを割り出す攻撃です。

    password → ef92b778...
123456   → 8d969eef...
qwerty   → 65e84be3...
（数十億件のテーブル）

    2.4 ソルトでレインボーテーブル攻撃を防ぐ

    ソルト（Salt） は、パスワードに付け加えるランダムな文字列です。ユーザーごとに異なるソルトを使うので、同じパスワードでも違うハッシュ値になり、事前に作った表が使えなくなります。

    ソルトなし：「password123」            → ハッシュ → 「ef92b778...」
ソルトあり：「password123」+「x7kP9m」 → ハッシュ → 「3a8f2c1b...」（全く違う値）
    危険な例：平文・速いハッシュだけ 
    保存値 = "password123"            # 平文 → 漏れたら即アウト
保存値 = sha256("password123")    # ソルトなし → レインボーテーブルで割り出される
    安全な例：ソルト付きの専用パスワードハッシュ関数 
    保存値 = bcrypt.hash("password123")  # bcrypt / scrypt / Argon2
                                     # ユーザーごとのソルトはライブラリが自動で付ける

    現在の推奨

    bcrypt・scrypt・Argon2 などの、ソルト付きの 専用パスワードハッシュ関数 を使います。これらは「わざと遅く」作られており、総当たりにも強くなっています。コード例を含む詳しい比較は パスワードの保存：平文・MD5・bcrypt（セキュリティ基礎）を参照してください。実装の詳細は、このサイトの 20 系（パスワード・MFA・パスキー）で扱う予定です。

    2.5 安全なパスワードの条件

    条件理由
    12 文字以上短いと総当たり攻撃（全組み合わせを試す攻撃）で解読される
    大文字・小文字・数字・記号を混在文字の種類が多いほど総当たりに時間がかかる
    辞書に載っている単語を避ける辞書攻撃（よく使われる単語を順に試す攻撃）を防ぐ
    サービスごとに異なるパスワード1 つ漏洩しても他に影響しない
    パスワードマネージャーを使う複雑なパスワードを安全に管理できる

    補足：運営側のパスワードポリシー

    利用者が自分で選ぶときは上の表が目安になります。一方、サービス側が「記号を必ず混ぜる」「定期的に変更させる」と 強制する ことは、米国 NIST のガイドラインでは推奨されなくなっています（長さと漏洩済みパスワードの禁止を重視）。詳しくは パスワードポリシーの最新推奨 を参照してください。

    3.多要素認証（MFA）の仕組み

    3.1 認証の 3 要素

    多要素認証（MFA：Multi-Factor Authentication） は、性質の違う認証要素を 2 つ以上組み合わせて本人確認をする方式です。認証要素は次の 3 種類に分けられます（考え方は ログイン方式と認証の概念 も参照）。

    知識情報

    Something You Know

    • パスワード
    • PIN
    • 秘密の質問

    所持情報

    Something You Have

    • スマートフォン（認証アプリ）
    • SMS で届くワンタイムパスワード
    • セキュリティキー（YubiKey など）

    生体情報

    Something You Are

    • 指紋
    • 顔認証
    • 虹彩認証

    3.2 TOTP の仕組み（Google Authenticator など）

    TOTP（Time-based One-Time Password） は、時刻をもとに作る使い捨てのパスワードです。

    1. サービスとスマホが「シークレットキー」（秘密の値）を共有する
    2. 現在時刻 ＋ シークレットキー から 6 桁の数字を生成する
    3. 30 秒ごとに新しい数字に変わる

    サービス側も同じ計算をして照合します。毎回違う数字なので、盗まれてもすぐ使えなくなり、インターネット接続なしでも生成できます。

    3.3 SMS・TOTP・セキュリティキーなどの比較

    方式安全性利便性備考
    SMS 認証★★★★★★★★SIM スワップ攻撃（電話番号を乗っ取る攻撃）のリスクあり
    TOTP アプリ★★★★★★★★Google Authenticator 等
    プッシュ通知★★★★★★★★★MFA 疲労攻撃のリスクあり（次の章）
    セキュリティキー★★★★★★★★YubiKey 等・最も安全
    生体認証★★★★★★★★★デバイス依存

    4.プッシュ通知 MFA と MFA 疲労攻撃

    4.1 プッシュ通知 MFA の仕組み

    プッシュ通知 MFA は、ログイン時にスマホへ「承認しますか？」という通知が届き、タップするだけで認証できる方式です。Microsoft や Duo などで広く使われています。

    1. ユーザーが ID とパスワードを入力する
    2. サーバーがスマホに「承認リクエスト」を送信する
    3. スマホに「example.com へのログインを承認しますか？［承認］［拒否］」という通知が届く
    4. ［承認］をタップすると認証完了・ログイン成功

    メリットは、6 桁のコードを入力する手間がないこと、直感的でわかりやすいことです。多くのビジネス向けサービスで採用されています。

    4.2 MFA 疲労攻撃（MFA Fatigue Attack）

    プッシュ通知 MFA には MFA 疲労攻撃 という弱点があります。大量の通知で利用者を疲れさせ、うっかり承認させる手口です。

    1. 攻撃者がパスワードを入手する（フィッシング等）
    2. ログインを何度も試み、スマホに「承認しますか？」通知が大量に届く
    3. ユーザーが「なんの通知だろう？」とうっかりタップ、または「通知がうるさい！」と止めようとタップしてしまう
    4. 攻撃者がログインに成功する

    実際の事例：2022 年 Uber 社

    攻撃者が WhatsApp で「IT 部門です」と連絡し、承認を押すよう説得して社内システムに侵入しました。技術（MFA）と人の心理（ソーシャルエンジニアリング、9 章）を組み合わせた攻撃です。

    4.3 MFA 疲労攻撃への対策

    • 通知に「ログイン場所・デバイス情報」を表示する
    • 数字照合（ナンバーマッチング） を有効にする：ログイン画面に表示された数字と、通知の数字が一致するかを確認してから承認する方式です。うっかりタップを防げます
    • 身に覚えのない承認リクエストは必ず拒否する
    • 大量のリクエストが来たらすぐパスワードを変更する
    • セキュリティキー（FIDO2）に移行する（最も安全）

    パスキー・FIDO2 など、より強い認証方式の詳細は、このサイトの 20 系（パスワード・MFA・パスキー）で扱う予定です。

    5.SSO（シングルサインオン）

    5.1 SSO とは

    SSO（Single Sign-On） は、1 回のログインで複数のサービスを使えるようにする仕組み です。

    SSO なし

    Google・Slack・GitHub・Salesforce……サービスごとに毎回 ID とパスワードを入力する必要があります。

    SSO あり

    IdP に 1 回ログインするだけで、Google・Slack・GitHub・Salesforce をすべて使えます。

    5.2 用語の整理：IdP・SAML・SP

    用語意味例
    IdP（Identity Provider：アイデンティティプロバイダー）「認証を一手に引き受ける管理者」。ユーザーの ID・パスワードを管理し、「この人は本物です」という証明を発行するOkta・Microsoft Entra ID（旧 Azure AD）・OneLogin
    SAML（Security Assertion Markup Language：サムル）IdP とサービスの間で認証情報を安全にやり取りする規格。「この人は認証済みです」という情報を XML 形式で送受信する。企業向け SSO で広く使われている標準プロトコルほかに OAuth 2.0・OpenID Connect（OIDC）という規格もある
    SP（Service Provider：サービスプロバイダー）実際に使うサービス側。IdP を信頼して認証を委ねるSlack・GitHub・Salesforce

    まとめると「ユーザー → IdP（認証）→ SAML（やり取り）→ SP（利用）」という関係です。

    5.3 SSO の仕組み（SAML の場合）

    1. ユーザーが Slack にアクセスする
    2. Slack が IdP（例：Okta）にリダイレクトする
    3. ユーザーが IdP でログインする（1 回だけ）
    4. IdP が「このユーザーは認証済み」という証明書を発行する
    5. Slack が証明書を検証し、アクセスを許可する
    6. 次に GitHub にアクセスしても、IdP はすでに認証済みなので再ログイン不要

    SAML・OIDC など SSO を実現するプロトコル（フェデレーション）の詳細は、このサイトの 30 系（フェデレーション）で扱う予定です。

    5.4 SSO のメリット・デメリット

    メリット

    • ユーザーの利便性向上（覚えるパスワードの数が減る）
    • パスワードの使い回しを防ぐ
    • 退職者のアクセス管理を一元化できる
    • セキュリティポリシーを一箇所で管理できる

    デメリット

    • IdP が攻撃されると全サービスに影響する
    • IdP が落ちると全サービスにログインできない
    • 導入・運用コストがかかる

    6.暗号化の仕組み：共通鍵暗号と公開鍵暗号

    暗号の用語は 共通鍵暗号と公開鍵暗号（セキュリティ基礎）で詳しく解説しています。ここではノートの要点を表で整理します。

    共通鍵暗号（対称暗号）公開鍵暗号（非対称暗号）
    鍵同じ鍵 で暗号化・復号する秘密鍵（自分だけが持つ）と 公開鍵（誰にでも配る）のペアを使う
    使い方送信者が共通鍵で暗号化 → 受信者が同じ共通鍵で復号暗号化通信：送信者が公開鍵で暗号化 → 受信者が秘密鍵で復号（秘密鍵を持つ人だけが読める）
    デジタル署名：送信者が秘密鍵で署名 → 受信者が公開鍵で検証
    メリット処理が高速鍵の配布が安全
    デメリット鍵を安全に共有する方法が問題処理が重い（共通鍵の 10〜1000 倍）
    代表的なアルゴリズムAES-128・AES-256（現在の標準・非常に安全）
    3DES（古い・非推奨）
    DES（非常に古い・危険）    		RSA（広く普及・鍵長 2048bit 以上推奨）
    ECDSA（楕円曲線・より短い鍵で同等の安全性）
    Ed25519（最新・高速・SSH で普及中）

    6.1 実際の通信では両方を組み合わせる（ハイブリッド暗号）

    HTTPS では、① 公開鍵暗号で「共通鍵」を安全に交換し、② あとは高速な共通鍵暗号で通信 します。公開鍵暗号は安全だが遅く、共通鍵暗号は速いが鍵の共有が問題なので、「安全な鍵配送」だけ公開鍵暗号を使い、「実際のデータ通信」は共通鍵暗号で処理する、いいとこどりの方式です。TLS の流れは TLS — HTTPS の「S」の正体 を参照してください。

    7.ハッシュ関数とデジタル署名

    どちらも ハッシュ関数・電子署名（セキュリティ基礎）で解説しています。ここでは要点をまとめます。

    7.1 ハッシュ関数

    任意の長さのデータを、固定長のハッシュ値に変換します。

    「Hello」                → SHA-256 → 「185f8db32...」（64 文字）
「Hello!」               → SHA-256 → 「334d016f7...」（64 文字・全然違う）
「War and Peace（全文）」→ SHA-256 → 「a1b2c3d4...」（同じく 64 文字）
    重要な特性意味
    ① 一方向性ハッシュ値から元データを復元できない
    ② 衝突耐性異なるデータが同じハッシュ値にならない
    ③ 雪崩効果1 ビット変わるだけでハッシュ値が大きく変わる

    用途：① パスワードの保存（2 章）、② ファイルの改ざん検知（ダウンロードしたファイルのハッシュ値を計算し、公式が公開している値と一致すれば改ざんなし）、③ ブロックチェーン（前のブロックのハッシュ値を次のブロックに含めるので、1 つでも改ざんすると以降のハッシュがすべて変わる）。

    代表的なアルゴリズム：SHA-256（現在の標準・Bitcoin 等でも使用）、SHA-3（次世代標準）。MD5・SHA-1 は衝突が発見済みで非推奨です。

    7.2 デジタル署名

    「このデータは確かに私が作り、改ざんされていない」ことを証明する仕組み です。

    署名する（送信者）

    1. 元データをハッシュ関数に通してハッシュ値を作る
    2. ハッシュ値を 秘密鍵 で暗号化 → デジタル署名
    3. 元データ ＋ デジタル署名を送る

    検証する（受信者）

    1. 受け取ったデータをハッシュ化 → ハッシュ値 A
    2. デジタル署名を 公開鍵 で復号 → ハッシュ値 B
    3. A ＝ B なら正当・改ざんなし、A ≠ B なら改ざんありか偽物
    証明すること内容理由
    ① 真正性（Authenticity）確かにその人が作成した秘密鍵を持っている人しか署名できないから
    ② 完全性（Integrity）署名後に改ざんされていない1 ビットでも変わるとハッシュ値が変わるから
    ③ 否認防止（Non-repudiation）「自分は署名していない」と言い張れない秘密鍵を持っている本人しか署名できないから

    デジタル署名は、SAML の証明や、トークン（JWT など）の改ざん検知にも使われています。

    8.PKI（公開鍵基盤）と証明書

    信頼の連鎖の図を含む詳しい説明は PKI（公開鍵基盤）（セキュリティ基礎）を参照してください。ここではノートの要点を整理します。

    8.1 なぜ証明書が必要か

    公開鍵だけでは「この公開鍵は本当に google.com のものか？」が分かりません。攻撃者が偽の google.com を作り、偽の公開鍵を配ることができてしまいます（中間者攻撃：通信の間に割り込んでなりすます攻撃）。そこで「この公開鍵は確かに本物」と証明する仕組みが必要になります。

    8.2 PKI の仕組み

    PKI（Public Key Infrastructure） は、公開鍵の正当性を証明する仕組みです。中心になるのが 認証局（CA：Certificate Authority） で、公開鍵の正当性を証明する信頼できる機関です（DigiCert・Let's Encrypt・VeriSign など）。

    デジタル証明書の中身

    • 誰の証明書か（example.com）
    • 公開鍵
    • 有効期限
    • 発行した CA
    • CA のデジタル署名

    信頼の連鎖（Chain of Trust）

    ルート CA（最上位・ブラウザに組み込み済み）→ 署名 → 中間 CA → 署名 → サーバー証明書（example.com）→ ユーザーが接続。

    ルート CA を信頼することで、中間 CA、サーバー証明書まで信頼がつながります。

    8.3 HTTPS の証明書確認

    ブラウザの鍵マークをクリックすると、発行先（example.com）、発行者（Let's Encrypt）、有効期限（2026/09/01 まで）、公開鍵（RSA 2048bit）などが見られます。ブラウザは接続のたびに、次の確認を自動で行っています。

    1. 証明書の有効期限を確認する
    2. CA の署名を検証する（信頼できる CA か？）
    3. ドメイン名が一致するか確認する
    4. 証明書が失効していないか確認する（OCSP / CRL：失効した証明書を確認する仕組み）

    9.ソーシャルエンジニアリング：「人間の隙」を突く攻撃

    どんなに強固な認証・暗号化も、人間の心理的な弱点 を突かれると一瞬で突破されます。「システムを攻撃するより人間を騙す方がずっと簡単だ」という有名なハッカーの言葉のとおり、人を騙せば鍵を開けてもらえるからです。

    ソーシャルエンジニアリング とは、人間の心理・行動・信頼を悪用して情報を盗み出したり、不正操作をさせたりする攻撃手法です。手口の種類と対策は 人を狙う攻撃 — フィッシングとソーシャルエンジニアリング（セキュリティ基礎）でも解説しています。ここではノートの例を中心に整理します。

    9.1 代表的な手口

    手口内容と例対策・見分け方
    フィッシング（Phishing）偽のメール・サイトで認証情報を騙し取る。例：「【緊急】Amazon アカウントが不正アクセスされました。こちらから確認してください」→ 偽サイトで ID・パスワードを入力させる
    種類：スピアフィッシング（特定の人・組織を狙い撃ち）、ホエーリング（経営幹部を標的）、スミッシング（SMS）、ビッシング（電話）    		送信元アドレスが微妙に違う（amazon.co.jp → amaz0n.co.jp など）、URL が本物と少し違う、「今すぐ」「緊急」など焦らせる言葉、日本語が不自然
    プリテキスティング（Pretexting）架空のシナリオ（口実）で信頼させて情報を引き出す。例：「IT 部門の XX ですが、メンテナンスでパスワードを確認させてください」「人事部です。口座変更の確認で社員番号を教えてください」「警察です。捜査でアカウント情報が必要です」本物の組織はパスワードや秘密情報を電話やメールで聞くことは絶対にない
    テールゲーティング（Tailgating）物理的なセキュリティを突破する。例：「荷物を持っているので、ドアを押さえてください」「今日から来た新入社員ですが、カードをまだもらっていなくて…」と同情を誘って侵入どんな理由があっても第三者を連れ込まない。不審な人物は必ず確認・受付に連絡
    ベイティング（Baiting）好奇心・欲求を利用する。例：「当選おめでとうございます！USB ドライブをお送りします」→ 刺すとマルウェア（悪意あるプログラム）が起動。駐車場に USB を落としておき、拾った人が会社の PC に刺して社内ネットワークに感染出所不明の USB は絶対に刺さない。拾った USB は IT 部門に届ける

    9.2 人間を守る 3 つの対策

    ① 教育・訓練

    • 定期的なフィッシングメール訓練
    • 「怪しいと思ったら確認する」文化を作る
    • 事例を共有して組織全体の意識を高める

    ② プロセス・ルール

    • 「電話でパスワードを教えない」ルールを明文化
    • 本人確認の手順を決めておく
    • 不審なアクセスの報告フローを整備

    ③ 技術的な補完

    • フィッシングサイトをブロックする DNS フィルタリング
    • 怪しいメールを自動検知するメールフィルタ
    • MFA で「パスワードが盗まれても突破されない」設計

    最大の防御

    最終的には 「おかしいと思ったら確認する」。この一言を習慣にすることが最大の防御です。

    9.3 ソーシャルエンジニアリングまとめ

    手口狙うもの対策
    フィッシング認証情報・クレジットカードURL を確認・公式サイトから直接アクセス
    プリテキスティング機密情報・アカウント電話・メールで機密情報を教えない
    テールゲーティング物理的な侵入不審者を連れ込まない
    ベイティングマルウェア感染不審な USB を刺さない
    MFA 疲労攻撃MFA の突破身に覚えのない承認を拒否

    10.まとめ

    概念一言で言うと
    認証「あなたは誰？」本人確認
    認可「あなたは何ができる？」権限確認
    ハッシュ元に戻せない一方向の変換・改ざん検知に使う
    ソルトハッシュにランダム文字列を追加してレインボーテーブルを防ぐ
    MFA複数の認証要素を組み合わせて安全性を高める
    プッシュ通知 MFA便利だが MFA 疲労攻撃に注意・ナンバーマッチングで対策
    SSO1 回のログインで複数サービスを使える仕組み
    共通鍵暗号同じ鍵で暗号化・復号。高速だが鍵配送が課題
    公開鍵暗号公開鍵で暗号化・秘密鍵で復号。安全だが遅い
    デジタル署名秘密鍵で署名・公開鍵で検証。真正性・完全性を証明
    PKI公開鍵の正当性を証明する仕組み（CA と証明書）
    ソーシャルエンジニアリング技術ではなく「人間の隙」を突く攻撃

    認証・認可・暗号化はセキュリティの核心技術です。普段なんとなく使っている HTTPS・パスワード・MFA の裏側には、ここで見た仕組みが動いています。ログイン後の状態をどう保つか（セッション）は 74_セッション管理 で、社内システムでどの方式を選ぶかは次のページで扱います。

    11.理解度チェック

    Q1. パスワードを「暗号化して保存」するのがよくないのはなぜですか？

    暗号化は元に戻せる（可逆）ため、暗号化の鍵が漏れると全パスワードが解読されてしまうからです。パスワードは元に戻せない ハッシュ化 で保存し、ログイン時は入力をハッシュ化して比較します。

    Q2. ソルトはどんな攻撃を防ぐために使いますか？

    レインボーテーブル攻撃 です。ユーザーごとに異なるランダムな文字列を混ぜてからハッシュ化するので、同じパスワードでも違うハッシュ値になり、事前に計算した表が使えなくなります。実際には bcrypt・scrypt・Argon2 などソルト付きの専用関数を使います。

    Q3. MFA 疲労攻撃とは何で、どう防ぎますか？

    盗んだパスワードで何度もログインを試み、プッシュ通知を大量に送って利用者にうっかり（または止めたくて）承認させる攻撃です。対策は、数字照合（ナンバーマッチング）、通知への場所・デバイス情報の表示、身に覚えのない承認の拒否、パスワード変更、セキュリティキー（FIDO2）への移行などです。

    Q4. SSO における IdP・SAML・SP の役割をそれぞれ答えてください。

    IdP は認証を一手に引き受け「この人は本物」という証明を発行する側（Okta、Entra ID など）。SAML はその認証情報を XML 形式で安全にやり取りする規格。SP は IdP を信頼して認証を委ねる、実際に使うサービス側（Slack、GitHub など）です。

    Q5. HTTPS で公開鍵暗号と共通鍵暗号を組み合わせるのはなぜですか？

    公開鍵暗号は鍵配送が安全だが処理が重く、共通鍵暗号は高速だが鍵の共有が難しいからです。そこで、共通鍵の受け渡しだけを公開鍵暗号で行い、実際のデータ通信は共通鍵暗号で高速に処理します（ハイブリッド暗号）。

    Q6. デジタル署名が証明する 3 つのことは何ですか？

    ① 真正性（確かにその人が作成した）、② 完全性（署名後に改ざんされていない）、③ 否認防止（「署名していない」と言い張れない）です。

    Q7. 「IT 部門です。メンテナンスのためパスワードを教えてください」と電話が来ました。これは何という手口で、どう対応すべきですか？

    架空の口実で信頼させる プリテキスティング です。本物の組織はパスワードを電話やメールで聞くことはないので、教えずに、決められた本人確認・報告の手順に従って確認します。
