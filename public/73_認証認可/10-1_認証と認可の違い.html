    10 基礎概念

    認証と認可の違い

    認証は「あなたは誰か」を確かめること、認可は「それをしてよいか」を決めることです。名前が似ていて混ざりやすいのですが、混ぜると「URL の番号を 1 つ変えたら他人の注文が見えた」ような事故が起きます。このページでは、2 つの違いと 401／403 の使い分け、認可を「どこで」確かめるべきか、そして認証・認可それぞれの代表的な実装方法と API 認証の 4 方式を解説します。

    もとにしたノート：10_基礎概念/01_認証と認可とは、10_基礎概念/02_認証と認可の違い（ねる前エンジニアリング）、10_基礎概念/05_API認証の仕組み（直也テック）

    ひとことで言うと

    認証が通っても、認可は済んでいません。「誰か分かった」と「それをしてよい」は別の質問です。認可は 画面ではなくサーバーで、入口ごとではなくデータを取る手前の 1 か所で、決まっていなければ断る を基本に行います。

    1.認証と認可とは何か

    認証と認可は、Web アプリケーションのセキュリティにおいて重要な概念です。

    • 認証（Authentication／オーセンティケーション）：「あなたは誰ですか？」を確認すること。ユーザーが本人であることを確認するプロセスです。ログインが認証にあたります。
    • 認可（Authorization／オーソリゼーション）：「あなたはその操作をしても良いですか？」を確認すること。認証されたユーザーが、特定の操作を実行する権限があるかを確認するプロセスです。例：管理者だけが編集できる。

    英語ではどちらも「Auth」で始まるため、短く AuthN（認証）／AuthZ（認可）と書き分けることもあります。

    1.1 日常生活での例え

    認証

    身分証明書を見せて「私は山田太郎です」と証明する。会社の受付で身分証を見せ、「この人は A さんだ」と分かる段階です。

    認可

    「この部屋に入る権限がありますか？」を確認する。受付を通った社員でも、入れる部屋は入館証で決まっています（社員でも社長室には入れない）。

    1.2 比較表と 401／403

    認証（Authentication）認可（Authorization）
    問いあなたは誰かそれをしてよいか（何ができるか）
    たとえ受付で身分証を見せる入館証で入れる部屋が決まる
    手段パスワード、ログイン時にもらう札（トークン）持ち主かどうか、役割（ロール）は何か
    失敗時401（名乗ってください＝誰か分からない）403（誰かは分かったがダメ）

    トークン は、ログインに成功したときにサーバーから受け取る「札」のような文字列です。以後のリクエストにこれを付けて送ることで、毎回パスワードを入力しなくても「誰か」を伝えられます。401・403 は HTTP のステータスコード（サーバーが返す結果の番号）です。

    「ログインしているのに 403」はなぜ？

    401 は「誰か分からない」、403 は「誰かは分かったけれどダメ」です。ちゃんとログインしているのに 403 と言われたなら、認証は通っていて、認可で断られた ということです。

    認証・認可の用語全体の整理は、71 の セキュリティの専門用語 と アクセス制御と認証の失敗：認証と認可の違い も参照してください。

    2.2 つの関門

    依頼（リクエスト）は、「誰ですか」の関門 → 「してよいか」の関門 の順に通ります。受付と入館の確認が順番に並んでいるイメージです。

    例として、注文の表に「注文 101 は A さんのもの」「注文 102・103 は B さんのもの」と記録されているとします。

    • A さんが「注文 101 を見せて」と頼む → 札は本物で A さんだと分かる（関門 1 通過）→ 101 の持ち主は A さんなので見てよい（関門 2 通過）→ 101 が届く。
    • 札を持たずに頼む → 1 つ目の関門で止まり、返事は 401。認証で止まったら、認可の関門までは行きません。

    「誰かを確かめる関門」と「してよいかを決める関門」の 2 つで 1 組です。この 2 つが別々の仕事をしている、という点を覚えておいてください。

    3.実務でよくある 3 つの場面

    名前が似ているせいで中身まで混ざりやすく、混ぜると他人のデータが見える事故が起きます。実務では次のような場面で出会います。

    1. URL の注文番号を 101 → 102 に変えたら、他人の注文が見えた。
    2. ボタンを消したのに、操作できてしまった。
    3. ちゃんとログインしているのに 403 と言われた（認証は通っていて、認可で断られた）。

    3 つとも、認証と認可を分けて考えるとすっきり分かります。3 つ目は 1.2 で説明しました。1 つ目・2 つ目を次の章から見ていきます。

    4.番号を 1 つ変えると：2 つ目の関門がない作り

    「番号を 1 つ変えたら他人の注文が見えた」は本当によく起きる事故です。よくある作りでは、2 つ目の関門（認可）がそもそもありません。作った人が「ログインしていれば十分」と考えたためです。

    1. A さんが自分の注文 101 を頼む。1 つ目の関門を通り、2 つ目は素通りで 101 が届く。ここまでは普通に動いていて、テストも通ります。
    2. A さんが URL の番号を 102 に書き換える。札は本物なので 1 つ目の関門は通る（A さんだと分かる）。
    3. 2 つ目の関門がないので素通りし、B さんの注文（住所・電話番号・購入品）が全部返ってくる。

    A さんは何も悪い道具を使っていません。番号を 1 つ変えただけなので、見つかりやすく起きやすい 事故です。このように、URL などに含まれる ID を書き換えるだけで他人のデータに届いてしまう脆弱性は IDOR（Insecure Direct Object Reference／安全でない直接オブジェクト参照）とも呼ばれます。OWASP Top 10 の「アクセス制御の不備」の代表例です（A01 のよくある攻撃パターン を参照）。

    この事故の本質

    認証が通ったことで安心してしまう ことです。「A さんだと分かった」で止まっていて、「A さんが 102 を見てよいか」は誰も聞いていません。認証が通っても認可は済んでいない——ここがこのページで一番大事なところです。

    4.1 2 つ目の関門を置く

    2 つ目の関門で、表を見て注文の持ち主を確かめるようにします。

    • A さんが 102 を頼む → 1 つ目は通る → 2 つ目で持ち主（B さん）と違うので止まり、403（誰かは分かったけど見せられません）。
    • B さんが同じ 102 を頼む → 2 つとも通り、102 が届く。

    同じ 102 でも、頼む人によって答えが変わります。これが認可で、誰が・どれに・何をするか の組み合わせで答えが決まります。番号だけ見て答えると、誰が頼んでも同じ答えになってしまいます。

    403 か 404 か

    403 ではなく 404（見つかりません） を返し、他人の注文が存在することすら教えない作りもあります。「あるけど見せない」より「ないことにする」ほうが用心深いやり方です。どちらにするかはチームで決めればよく、大事なのは 中身を渡さないこと です。

    4.2 コードで見る

    危ないのは、ログイン中の人を取り出す（1 つ目の関門）だけで、番号で注文を探してそのまま返す 形です。誰の注文かを見ていません。

    危険な例：番号だけで探して返す（2 つ目の関門がない） 
    app.get('/api/orders/:id', authenticateToken, async (req, res) => {
  // 1つ目の関門（authenticateToken）は通っている：誰か分からなければ 401
  const order = await db.orders.findOne({ id: req.params.id }); // 番号だけで探す
  res.json(order); // 他人の注文でもそのまま返してしまう
});

    直した形では、探すときに「番号＋持ち主は私」という条件 を付けます。この持ち主の条件が 2 つ目の関門です。見つからなければ 404 を返すので、他人の注文はそもそも探せません。

    安全な例：取り方そのものに持ち主を組み込む 
    app.get('/api/orders/:id', authenticateToken, async (req, res) => {
  const order = await db.orders.findOne({
    id: req.params.id,
    userId: req.user.userId   // 持ち主は私、という条件（2つ目の関門）
  });
  if (!order) {
    return res.status(404).json({ error: '見つかりません' });
  }
  res.json(order);
});

    データを取ってくる その場所で条件を付ける のがコツです。取ってきた後で確かめる書き方だと、確かめを忘れる道ができます。取り方そのものに持ち主を組み込むほうが漏れにくい のです。1 行の差で他人の住所が守られます。

    5.画面で隠しても守れない

    冒頭の 2 つ目の場面「ボタンを消したのに操作できた」です。

    • 「お知らせを消す」ボタンを管理者の画面にだけ出し、A さん（一般ユーザー）の画面には出さない。それで安心と考え、サーバー側に 2 つ目の関門を作らなかった。
    • しかし、ブラウザが送る依頼はただの文字 です。画面にボタンがなくても、同じ文字を自分で作って送れます。ブラウザの開発者ツール（開発者向けの調査用機能）でも、プログラムからでも送れます。
    • A さんがボタンを通さずに「お知らせを消して」と送ると、1 つ目は通り、2 つ目は素通りで、お知らせが消えてしまう。

    サーバーに 2 つ目の関門を置けば、同じ依頼は「役割が一般だからダメ」と止まり、管理者が頼んだときだけ通ります。

    画面で隠すのは鍵ではなく目隠し

    ボタンを隠すのは 使いやすさのため、守るのは サーバーの関門 です。画面は親切のため、守りはサーバー、と分けて覚えてください。

    6.入口が増えると

    もう 1 つの具体例として、お店の売上を見る業務用画面を考えます。店長は 自分の店の売上だけ を見られる決まりです。

    • ブラウザ用の入口には 2 つ目の関門があり、1 号店の店長が 2 号店の売上を頼むと「違う店だからダメ」と止まる。ここまではよい。
    • ある日、スマホアプリ用の入口を新しく足した。ブラウザ用の入口に書いた確かめを 写し忘れた ため、新しい入口から頼むと 2 号店の売上が届いてしまった。

    入口ごとに確かめを書くと、入口が増えるたびに抜け道が増えます。入口が 10 個になったら 10 回書かなければなりません。そこで確かめは 入口ではなく、データを取る手前の 1 か所 に集め、どの入口から来ても必ずそこを通る形にします。そうすれば、入口が増えても関門は 1 つで済みます。

    夜間の集計や裏で動く処理も、同じように入口の 1 つです。入口は思ったより多いものです。

    7.札に書いた役割

    もう 1 つ混ざりやすいところが、ログインの札（トークン）に何を書くかです。札に「この人は管理者」と書いておく作りがあります。毎回表を調べなくてよいので速い、という利点があります。

    • しかし、C さんが今日管理者を外れたとします。C さんの手元には、朝もらった「管理者」と書かれた札が残っています。
    • その札で「お知らせを消して」と頼むと、通ってしまいます。札は本物なので、認証としては正しい のです。ただ、役割の中身が古くなっています。

    札は「誰か」を伝えるのが得意

    「してよいか」は 今の表（現在の役割） で決めます。2 つ目の関門が今の役割を見れば、C さんの依頼は止まります。札に役割を書くなら、札の期限を短くする 工夫が要ります。ここも認証と認可を分けて考えると、何を確かめるべきかが見えてきます。

    トークンを使った「ログイン状態の保ち方」の詳細は 74_セッション管理 で扱います。

    8.どこで確かめるか：4 つの原則

    ここまでの内容を「どこで確かめるか」としてまとめます。

    原則内容対応する例
    1. 画面ではなくサーバーで画面は目隠し、守りはサーバーボタンを消したのに操作できた（5 章）
    2. 入口ごとではなくデータを取る手前の 1 か所で入口が増えても関門は 1 つスマホ用の入口で他店の売上が見えた（6 章）
    3. 決まっていなければ断るを基本に確かめをかけ忘れても漏れない新しい画面を足したとき
    4. 誰が・どれに・何をするかの 3 つで決める番号だけでも、人だけでも決められないA さんが注文 102 を見る（4 章）

    3 つ目の「決まっていなければ断る」について補足します。新しい画面を足したとき、確かめをかけ忘れることがあります。そのとき「何もしなければ通る」作りだとデータが漏れます。「何もしなければ断る」作りなら、困るのは作った人が試したときだけです。お客さんのデータが漏れるよりずっとよい、という考え方です（デフォルト拒否。71 の A01 の防御の原則 も参照）。必要な権限だけを与える考え方は 最小権限とデータ最小化 で解説しています。

    9.認証の方法

    ここからは、認証と認可を実際にコードでどう書くかを見ていきます（Node.js の Express というフレームワークの例です）。まず認証の代表的な方法を 3 つ紹介します。それぞれの詳細は、パスワードは 73 の 20 系（パスワード・MFA・パスキー）、OAuth は 30 系（フェデレーション）で扱う予定です。

    9.1 ユーザー名とパスワード

    最も一般的な認証方法です。bcrypt.compare は、入力されたパスワードと保存されたハッシュ値（元に戻せない形に変換した値）が一致するかを確かめる関数です。

    // ログイン処理
app.post('/api/login', async (req, res) => {
  const { username, password } = req.body;

  // データベースからユーザーを検索
  const user = await db.users.findOne({ username });

  if (!user) {
    return res.status(401).json({ error: 'ユーザー名またはパスワードが正しくありません' });
  }

  // パスワードを検証
  const isValid = await bcrypt.compare(password, user.password);

  if (!isValid) {
    return res.status(401).json({ error: 'ユーザー名またはパスワードが正しくありません' });
  }

  // 認証成功：セッションまたはトークンを発行
  req.session.userId = user.id;
  res.json({ message: 'ログイン成功', user: { id: user.id, username: user.username } });
});

    ユーザーが存在しない場合もパスワードが違う場合も、同じエラーメッセージを返している点に注目してください。どちらが間違っているかを教えると、攻撃者に「このユーザー名は存在する」というヒントを与えてしまうためです。

    9.2 トークンベース認証（JWT）

    JWT（JSON Web Token／ジョット） を使った認証方法です。ログイン時にサーバーが署名付きのトークンを発行し、以後のリクエストでは Authorization: Bearer トークン というヘッダーで送ってもらいます。

    const jwt = require('jsonwebtoken');

// ログイン処理
app.post('/api/login', async (req, res) => {
  const { username, password } = req.body;

  // 認証処理
  const user = await authenticateUser(username, password);

  if (!user) {
    return res.status(401).json({ error: '認証に失敗しました' });
  }

  // JWTトークンを発行
  const token = jwt.sign(
    { userId: user.id, username: user.username },
    process.env.JWT_SECRET,
    { expiresIn: '24h' }
  );

  res.json({ token, user: { id: user.id, username: user.username } });
});

// トークンを検証するミドルウェア
function authenticateToken(req, res, next) {
  const authHeader = req.headers['authorization'];
  const token = authHeader && authHeader.split(' ')[1]; // "Bearer TOKEN"

  if (!token) {
    return res.status(401).json({ error: 'トークンが必要です' });
  }

  jwt.verify(token, process.env.JWT_SECRET, (err, user) => {
    if (err) {
      return res.status(403).json({ error: '無効なトークンです' });
    }
    req.user = user;
    next();
  });
}

// 保護されたエンドポイント
app.get('/api/profile', authenticateToken, (req, res) => {
  res.json({ user: req.user });
});

    ミドルウェア は、リクエストが本来の処理に届く前に挟まる共通処理のことです。authenticateToken が「1 つ目の関門」の役割を果たします。

    補足：無効なトークンは 401 が本来の意味に近い

    このコードでは、トークンが無効なとき 403 を返しています。ただ 1.2 の整理に従うと、トークンが偽物・期限切れのときは「誰か分からない」状態なので、401 を返すほうが意味としては正確です。403 は「誰かは分かったが権限がない」ときに使います。

    9.3 OAuth（サードパーティ認証）

    Google、GitHub などの外部サービスを使った認証です。OAuth（オーオース） は本来「権限を委譲する」ための仕組みで、ログイン用途では OpenID Connect と組み合わせて使われます（30 系のフェデレーションで詳しく扱います）。

    // Google OAuthの例（簡略化）
app.get('/auth/google', (req, res) => {
  // Googleの認証ページにリダイレクト
  res.redirect('https://accounts.google.com/oauth/authorize?...');
});

app.get('/auth/google/callback', async (req, res) => {
  const { code } = req.query;

  // トークンを取得
  const token = await getGoogleToken(code);

  // ユーザー情報を取得
  const userInfo = await getGoogleUserInfo(token);

  // ユーザーを登録またはログイン
  const user = await findOrCreateUser(userInfo);

  // セッションに保存
  req.session.userId = user.id;
  res.redirect('/dashboard');
});

    10.API 認証の代表的な 4 方式

    API は URL を知っていれば誰でも呼べてしまいます。そのため、入口で「誰か」を確かめる認証が必要になります。代表的な方式は次の 4 つです。

    方式仕組みポイント
    Basic 認証ユーザー名とパスワードを Base64 にしてヘッダーに入れて送るBase64 は 64 文字でデータを表す 置き換えのルールにすぎず、暗号化ではない。鍵がないので誰でも元に戻せる
    API キー発行された固有のキーをリクエストに付ける誰がどれだけ使ったかを測れるので、レート制限や従量課金 がしやすい。漏れたらパスワード同様に無効化が必要
    JWTログイン時にサーバーが署名付きトークンを発行ヘッダー（アルゴリズム）・ペイロード（ID や権限）・署名（2 つと秘密鍵から作る改ざん検知値）の 3 部構成。改ざんはすぐ分かり、サーバーは ステートレス なのでスケールしやすい
    OAuthGoogle などに認証を任せ、アクセストークンを受け取る今もっとも使われる方式。自分でパスワードを扱わない。トークンには 有効期限 があり、いつでも取り消せる

    レート制限 は一定時間あたりの呼び出し回数を制限すること、ステートレス はサーバーがログイン状態を記憶しておかなくてよい（トークン自体に情報が入っている）ことです。記憶がいらないので、サーバーの台数を増やしやすくなります（スケールしやすい）。

    Base64 は暗号ではない

    Basic 認証は、中身が丸見えになる前提で考えます。必ず HTTPS（通信を暗号化する仕組み）の上で使います。

    4 方式の特徴をひとことで言うと、API キーは 利用量の計測 に強く、JWT は 署名による改ざん検知とステートレス性、OAuth は パスワードを預からない委譲 が特徴です。ただし JWT は 7 章で見たとおり、札に書いた権限が古くなる問題があるので、有効期限は短めにします。

    11.認可の実装例

    認可（2 つ目の関門）の代表的な書き方は 2 つです。認可モデル（RBAC・ABAC など）の詳細は 73 の 40 系（認可モデル）で扱う予定です。

    11.1 ロールベース認可

    ユーザーの役割（ロール）に基づいて権限を管理します。「管理者だけが削除できる」のように、役割単位で決めます。

    // ユーザーのロールを定義
const ROLES = {
  ADMIN: 'admin',
  USER: 'user',
  GUEST: 'guest'
};

// ロールをチェックするミドルウェア
function requireRole(...allowedRoles) {
  return (req, res, next) => {
    if (!req.user) {
      return res.status(401).json({ error: '認証が必要です' });
    }

    if (!allowedRoles.includes(req.user.role)) {
      return res.status(403).json({ error: 'この操作を実行する権限がありません' });
    }

    next();
  };
}

// 管理者のみアクセス可能
app.delete('/api/users/:id', authenticateToken, requireRole(ROLES.ADMIN), (req, res) => {
  // ユーザーを削除
  deleteUser(req.params.id);
  res.status(204).send();
});

// ユーザーと管理者がアクセス可能
app.get('/api/users/:id', authenticateToken, requireRole(ROLES.USER, ROLES.ADMIN), (req, res) => {
  const user = getUser(req.params.id);
  res.json(user);
});

    401（誰か分からない）と 403（権限がない）がきちんと使い分けられています。ただし最後の例は「ユーザーなら誰でも、どのユーザーの情報でも見られる」状態で、4 章と同じ問題が残ります。役割だけでなく どれに（どのリソースに） まで見るのが次のリソースベース認可です。

    11.2 リソースベース認可

    特定のリソース（データ）に対する権限を確認します。「自分のデータだけ」「自分の投稿だけ」のように、持ち主で決めます。

    // 自分のデータのみアクセス可能
app.get('/api/users/:id', authenticateToken, async (req, res) => {
  const userId = parseInt(req.params.id);

  // 自分のデータか、管理者か確認
  if (req.user.userId !== userId && req.user.role !== 'admin') {
    return res.status(403).json({ error: 'このリソースにアクセスする権限がありません' });
  }

  const user = await getUser(userId);
  res.json(user);
});

// 自分の投稿のみ削除可能
app.delete('/api/posts/:id', authenticateToken, async (req, res) => {
  const postId = parseInt(req.params.id);
  const post = await getPost(postId);

  // 投稿の所有者か、管理者か確認
  if (post.userId !== req.user.userId && req.user.role !== 'admin') {
    return res.status(403).json({ error: 'この投稿を削除する権限がありません' });
  }

  await deletePost(postId);
  res.status(204).send();
});

    これらは「取ってきた後で確かめる」書き方です。4.2 で見たように、可能なら 取り方そのものに持ち主の条件を組み込む ほうが確かめ忘れが起きにくくなります。

    12.認証と認可の流れと実践例

    12.1 処理の流れ

    1. ユーザーがログイン
    2. 認証（ユーザー名とパスワードを確認）
    3. 認証成功 → トークンまたはセッションを発行
    4. ユーザーがリクエストを送信（トークンを含む）
    5. 認証を確認（トークンが有効か）
    6. 認可を確認（権限があるか）
    7. リクエストを処理

    5 が 1 つ目の関門、6 が 2 つ目の関門にあたります。

    12.2 実践例：認証・認可システム一式

    登録・ログイン・プロフィール取得（認証が必要）・ユーザー削除（管理者のみ）をまとめた例です。

    const express = require('express');
const jwt = require('jsonwebtoken');
const bcrypt = require('bcrypt');
const app = express();

app.use(express.json());

// 認証ミドルウェア
function authenticateToken(req, res, next) {
  const authHeader = req.headers['authorization'];
  const token = authHeader && authHeader.split(' ')[1];

  if (!token) {
    return res.status(401).json({ error: '認証が必要です' });
  }

  jwt.verify(token, process.env.JWT_SECRET, (err, user) => {
    if (err) {
      return res.status(403).json({ error: '無効なトークンです' });
    }
    req.user = user;
    next();
  });
}

// 認可ミドルウェア
function requireRole(...roles) {
  return (req, res, next) => {
    if (!roles.includes(req.user.role)) {
      return res.status(403).json({ error: '権限がありません' });
    }
    next();
  };
}

// 登録
app.post('/api/register', async (req, res) => {
  const { username, password, email } = req.body;

  // パスワードをハッシュ化
  const hashedPassword = await bcrypt.hash(password, 10);

  // ユーザーを作成
  const user = await db.users.create({
    username,
    password: hashedPassword,
    email,
    role: 'user'
  });

  res.status(201).json({ message: 'ユーザーが作成されました' });
});

// ログイン
app.post('/api/login', async (req, res) => {
  const { username, password } = req.body;

  const user = await db.users.findOne({ username });
  if (!user) {
    return res.status(401).json({ error: '認証に失敗しました' });
  }

  const isValid = await bcrypt.compare(password, user.password);
  if (!isValid) {
    return res.status(401).json({ error: '認証に失敗しました' });
  }

  const token = jwt.sign(
    { userId: user.id, username: user.username, role: user.role },
    process.env.JWT_SECRET,
    { expiresIn: '24h' }
  );

  res.json({ token });
});

// プロフィール取得（認証必要）
app.get('/api/profile', authenticateToken, async (req, res) => {
  const user = await db.users.findById(req.user.userId);
  res.json({ user: { id: user.id, username: user.username, email: user.email } });
});

// ユーザー削除（管理者のみ）
app.delete('/api/users/:id', authenticateToken, requireRole('admin'), async (req, res) => {
  await db.users.delete(req.params.id);
  res.status(204).send();
});

    この例で気をつけたい点

    ログイン時に role をトークン（札）に書き込み、requireRole はその札の役割を見ています。これは 7 章の「札に書いた役割」の作りです。管理者を外れても札の期限（ここでは 24 時間）までは管理者として操作できてしまうため、期限を短くするか、重要な操作では今の役割をデータベースで確かめるようにします。

    13.セキュリティの注意点

    13.1 パスワードのハッシュ化

    間違い：平文で保存 
    const user = { username: 'yamada', password: 'password123' };
    正しい：ハッシュ化して保存 
    const hashedPassword = await bcrypt.hash('password123', 10);
const user = { username: 'yamada', password: hashedPassword };

    なぜ MD5 ではなく bcrypt なのかなどの詳細は、71 の パスワードの保存：平文・MD5・bcrypt を参照してください。

    13.2 トークンの有効期限

    適切な有効期限を設定します。

    const token = jwt.sign(payload, secret, { expiresIn: '24h' });

    13.3 HTTPS の使用

    認証情報は必ず HTTPS で送信します。

    13.4 レート制限

    ブルートフォース攻撃（パスワードを総当たりで試す攻撃）を防ぎます。次の例は、15 分間にログインを 5 回までに制限します。

    const rateLimit = require('express-rate-limit');

const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15分
  max: 5 // 5回まで
});

app.post('/api/login', loginLimiter, loginHandler);

    ログイン試行の制限やセッション管理の考え方は、71 の セッション管理とログイン試行の制限 も参照してください。

    14.AI にコードを書かせたときに見るところ

    AI はログインの確認（1 つ目の関門）はほぼ必ず書いてくれます。よく知られているからです。しかし 2 つ目の関門は、仕様に書いていないと抜けやすい です。次の 4 点を確認します。

    1. 番号で取ってきて、そのまま返していないか（4.2 の危険な形）
    2. ログインの確認だけで安心していないか（401 を返す行があると、守っている気になってしまう）
    3. 新しい入口を足したとき、2 つ目の関門を通っているか（スマホ用の入口を AI に足してもらったときが危ない）
    4. テストに「他人の番号で頼んで断られる」が入っているか（自分の注文が見えるだけのテストは、関門がなくても通る。4 章の図でも A さんの 101 は関門なしで届いていた）

    断られることを確かめるテスト

    AI に頼むときも「他人の番号で断られるテストを書いて」と言えば済みます。他人の 102 を頼んで 断られることまで 確かめましょう。

    15.まとめ

    • 認証 は「あなたは誰ですか？」を確認する。認可 は「その操作をしても良いですか？」を確認する。失敗時は 401 と 403。
    • 認証が通っても認可は済んでいない。番号を変えたら他人の注文が見える事故は、これを混ぜた結果。
    • 認可は 画面ではなくサーバーで、データを取る手前の 1 か所で、決まっていなければ断る。誰が・どれに・何をするか の 3 つで決める。
    • 札（トークン）は「誰か」を伝えるのが得意。「してよいか」は今の表で決め、札に役割を書くなら期限を短くする。
    • パスワード は必ずハッシュ化する。トークン や セッション を使って認証状態を管理する。
    • ロール や リソース に基づいて認可を実装する。
    • API 認証の 4 方式：Base64 は暗号ではないので Basic 認証は中身が丸見えの前提。API キーは利用量の計測、JWT は署名による改ざん検知とステートレス性、OAuth はパスワードを預からない委譲が特徴。
    • 札が本物かどうか（暗号の数学）は道具に任せ、その人がそれをしてよいかは自分で決める。セキュリティを最優先に考える。

    16.理解度チェック

    Q1. 認証と認可の違いを、それぞれの「問い」と失敗時のステータスコードで説明してください。

    認証は「あなたは誰か」を確かめることで、失敗すると 401（名乗ってください）。認可は「それをしてよいか」を決めることで、失敗すると 403（誰かは分かったがダメ）です。

    Q2. ちゃんとログインしているのに 403 が返ってきました。何が起きていますか？

    認証（1 つ目の関門）は通っていて、認可（2 つ目の関門）で「その操作をする権限がない」と断られています。

    Q3. URL の注文番号を 101 から 102 に変えたら他人の注文が見えました。原因と直し方は？

    ログインしているか（認証）だけを確かめ、その注文の持ち主か（認可）を確かめていないことが原因です。注文を探すときに「番号＋持ち主は私」という条件を付け、見つからなければ 404（または 403）を返すように直します。取ってきた後で確かめるより、取り方そのものに持ち主を組み込むほうが漏れにくくなります。

    Q4. 管理者の画面にだけ削除ボタンを出しています。これで一般ユーザーの削除を防げますか？

    防げません。ブラウザが送る依頼はただの文字なので、開発者ツールやプログラムで同じ依頼を作って送れます。画面で隠すのは目隠しであって鍵ではありません。サーバー側で役割を確かめる認可が必要です。

    Q5. 認可の確かめを「入口ごと」に書くと、どんな問題が起きますか？

    スマホ用の入口や夜間集計など、入口が増えるたびに確かめを写し忘れる抜け道が増えます。確かめはデータを取る手前の 1 か所に集め、どの入口から来ても必ず通る形にします。

    Q6. トークンに「管理者」と書いておく作りの注意点は何ですか？

    管理者を外れた後も、手元の札には「管理者」と残っていて操作できてしまいます。札は本物なので認証としては正しいのが厄介な点です。「してよいか」は今の役割で決め、札に役割を書くなら有効期限を短くします。

    Q7. Basic 認証のパスワードは Base64 にしてあるので安全、と言えますか？

    言えません。Base64 は 64 文字でデータを表す置き換えのルールにすぎず、鍵もないので誰でも元に戻せます。暗号化ではないため、必ず HTTPS 上で使います。

    Q8. 「決まっていなければ断る」を基本にする理由は何ですか？

    新しい画面や入口に確かめをかけ忘れたとき、「何もしなければ通る」作りだとデータが漏れますが、「何もしなければ断る」作りなら困るのは作った人が試したときだけで済むからです。
