    権限管理・ロール管理の実装

    権限管理・ロール管理機能は、ユーザーがシステム内で どの操作を実行できるか を制御する重要なセキュリティ機能です。適切な権限設計により、最小権限の原則に基づいた安全なシステムを構築できます。このページでは、RBAC（ロールベースのアクセス制御）を例に、データベースの設計・サーバー側の権限チェック・ロール管理 API・管理画面までを、実際のコードで順に見ていきます。

    もとにしたノート：40_認可モデル/03_権限管理・ロール管理機能

    このページで分かること

    • ユーザー・ロール・権限をデータベースでどうつなぐか
    • サーバー側で「この操作をしてよいか」を確かめるミドルウェアの書き方
    • ロールの作成・更新・削除、ユーザーへの割り当てを行う API と管理画面
    • リソースベース権限・動的権限・最小権限・監査ログ
    • システム規模ごとの権限モデルの選び方

    コード例は Node.js の Web フレームワーク Express と、MongoDB（文書型のデータベース）を扱うライブラリ Mongoose で書かれています。画面側は React です。

    1.権限管理の基本概念

    1.1 認証（Authentication）と認可（Authorization）

    • 認証：ユーザーが 誰であるか を確認
    • 認可：ユーザーが 何を実行できるか を決定

    このページで作るのは「認可」の仕組みです。2 つの違いと 401／403 の使い分けは 認証と認可の違い で詳しく説明しています。

    1.2 権限モデル

    モデル正式名何で決めるか
    RBACRole-Based Access Controlロール（役割）ベース
    ABACAttribute-Based Access Control属性ベース
    ACLAccess Control Listアクセス制御リスト
    PBACPolicy-Based Access Controlポリシー（規則の集まり）ベース

    それぞれの考え方と使い分けは、前のページ RBAC・ABAC・ACLの使い分け を参照してください。このページでは、いちばん広く使われる RBAC を実装します。

    2.データベーススキーマ設計（RBAC）

    スキーマ は、データベースに保存するデータの形（項目名と型）の定義です。RBAC では「ロール」「ユーザーとロールの割り当て」「権限」の 3 つを用意し、ユーザーにロール情報を追加します。

    // ロールスキーマ
const RoleSchema = new mongoose.Schema({
  name: { type: String, required: true, unique: true },
  description: String,
  permissions: [{ type: String, required: true }],
  isActive: { type: Boolean, default: true },
  createdAt: { type: Date, default: Date.now },
  updatedAt: { type: Date, default: Date.now }
});

// ユーザーロールスキーマ
const UserRoleSchema = new mongoose.Schema({
  userId: { type: mongoose.Schema.Types.ObjectId, ref: 'User', required: true },
  roleId: { type: mongoose.Schema.Types.ObjectId, ref: 'Role', required: true },
  assignedBy: { type: mongoose.Schema.Types.ObjectId, ref: 'User' },
  assignedAt: { type: Date, default: Date.now },
  expiresAt: Date, // ロールの有効期限
  isActive: { type: Boolean, default: true }
});

// 権限スキーマ
const PermissionSchema = new mongoose.Schema({
  name: { type: String, required: true, unique: true },
  resource: { type: String, required: true }, // リソース（例：users, posts, orders）
  action: { type: String, required: true },   // アクション（例：create, read, update, delete）
  description: String,
  isActive: { type: Boolean, default: true }
});

// ユーザースキーマにロール情報を追加
UserSchema.add({
  roles: [{ type: mongoose.Schema.Types.ObjectId, ref: 'UserRole' }],
  permissions: [{ type: String }] // 直接権限（オーバーライド用）
});

    ObjectId は MongoDB が各データに振る ID、ref は「この ID はどのデータを指すか」の指定です。

    スキーマ役割ポイント
    Roleロール（役割）の定義permissions に権限名（例：posts:read）の配列を持つ。isActive で無効化できる
    UserRoleユーザーとロールの割り当て誰が割り当てたか（assignedBy）、いつ割り当てたか、ロールの有効期限（expiresAt）を記録できる
    Permission権限の一覧（マスタ）リソース（例：users, posts, orders）と アクション（例：create, read, update, delete）の組み合わせ
    User（追加分）ロール情報roles で割り当てを参照。permissions はロールを通さない 直接権限（オーバーライド用）

    ユーザーとロールを直接つながず、間に UserRole を置くことで、「期限付きで一時的に権限を渡す」「誰がいつ権限を与えたかを残す」といった管理ができるようになります。

    3.バックエンド：権限チェックの仕組み

    3.1 権限チェックミドルウェア

    ミドルウェア は、リクエストが本来の処理に届く前に挟み込む関数です。checkPermission('roles:read') のように、必要な権限を引数に渡して使います。

    // 権限チェックミドルウェア
const checkPermission = (requiredPermission) => {
  return async (req, res, next) => {
    try {
      const user = req.user;
      
      if (!user) {
        return res.status(401).json({ error: 'Authentication required' });
      }
      
      // ユーザーの権限を取得
      const userPermissions = await getUserPermissions(user.id);
      
      // 権限チェック
      if (!userPermissions.includes(requiredPermission)) {
        return res.status(403).json({ 
          error: 'Insufficient permissions',
          required: requiredPermission,
          userPermissions: userPermissions
        });
      }
      
      next();
    } catch (error) {
      console.error('Permission check error:', error);
      res.status(500).json({ error: 'Permission check failed' });
    }
  };
};

    ログインしていなければ 401（誰か分からない）、ログインしていても権限がなければ 403（権限がない）を返します。req.user は、その前に動く認証の仕組み（セッションや JWT の検証）が入れておく前提です。

    エラー応答に渡す情報は最小限に

    このコードは 403 の応答に userPermissions（そのユーザーが持つ権限の一覧）まで含めています。開発中の確認には便利ですが、本番では攻撃者に手がかりを与えるため、エラー内容だけを返すのが安全です（71 の エラー処理 — 攻撃者にヒントを与えない を参照）。

    3.2 ユーザーの権限取得

    // ユーザーの権限取得
const getUserPermissions = async (userId) => {
  try {
    const user = await User.findById(userId)
      .populate({
        path: 'roles',
        populate: {
          path: 'roleId',
          model: 'Role'
        }
      });
    
    if (!user) {
      return [];
    }
    
    const permissions = new Set();
    
    // ロールから権限を取得
    user.roles.forEach(userRole => {
      if (userRole.isActive && (!userRole.expiresAt || userRole.expiresAt > new Date())) {
        const role = userRole.roleId;
        if (role && role.isActive) {
          role.permissions.forEach(permission => {
            permissions.add(permission);
          });
        }
      }
    });
    
    // 直接権限を追加（オーバーライド）
    user.permissions.forEach(permission => {
      permissions.add(permission);
    });
    
    return Array.from(permissions);
  } catch (error) {
    console.error('Get user permissions error:', error);
    return [];
  }
};

    populate は、ID で参照している先のデータを取り込んで一緒に取得する Mongoose の機能です。ここでは User → UserRole → Role と 2 段階でたどっています。権限を集めるときの条件は次のとおりです。

    • 割り当て（UserRole）が 有効（isActive）で、期限切れでない（expiresAt がないか、未来の日時）
    • ロール（Role）自体も 有効
    • 最後に、ユーザーの 直接権限 を追加（オーバーライド）

    Set は重複を持たない集合で、複数のロールに同じ権限があっても 1 つにまとまります。エラー時に空の配列を返すので、何かあれば「権限なし」として扱われます（安全側に倒れる）。

    4.ロール管理 API

    ロールの一覧・作成・更新・削除を行う API です。どの API にも checkPermission を付け、ロールを管理する操作そのものにも権限が必要 にしています。

    操作メソッドとパス必要な権限
    ロール一覧取得GET /api/rolesroles:read
    ロール作成POST /api/rolesroles:create
    ロール更新PUT /api/roles/:roleIdroles:update
    ロール削除DELETE /api/roles/:roleIdroles:delete
     
    // ロール管理API
// ロール一覧取得
app.get('/api/roles', checkPermission('roles:read'), async (req, res) => {
  try {
    const roles = await Role.find({ isActive: true })
      .select('name description permissions createdAt')
      .sort({ name: 1 });
    
    res.json({ roles });
  } catch (error) {
    res.status(500).json({ error: 'Failed to fetch roles' });
  }
});

// ロール作成
app.post('/api/roles', checkPermission('roles:create'), async (req, res) => {
  try {
    const { name, description, permissions } = req.body;
    
    // 入力値検証
    if (!name || !permissions || !Array.isArray(permissions)) {
      return res.status(400).json({ error: 'Name and permissions are required' });
    }
    
    // 重複チェック
    const existingRole = await Role.findOne({ name });
    if (existingRole) {
      return res.status(409).json({ error: 'Role already exists' });
    }
    
    // 権限の有効性チェック
    const validPermissions = await Permission.find({ 
      name: { $in: permissions },
      isActive: true 
    });
    
    if (validPermissions.length !== permissions.length) {
      return res.status(400).json({ error: 'Invalid permissions provided' });
    }
    
    const role = await Role.create({
      name,
      description,
      permissions
    });
    
    res.status(201).json({ 
      success: true, 
      role: {
        id: role.id,
        name: role.name,
        description: role.description,
        permissions: role.permissions
      }
    });
    
  } catch (error) {
    console.error('Role creation error:', error);
    res.status(500).json({ error: 'Role creation failed' });
  }
});

// ロール更新
app.put('/api/roles/:roleId', checkPermission('roles:update'), async (req, res) => {
  try {
    const { roleId } = req.params;
    const { name, description, permissions } = req.body;
    
    const role = await Role.findById(roleId);
    if (!role) {
      return res.status(404).json({ error: 'Role not found' });
    }
    
    // 権限の有効性チェック
    if (permissions) {
      const validPermissions = await Permission.find({ 
        name: { $in: permissions },
        isActive: true 
      });
      
      if (validPermissions.length !== permissions.length) {
        return res.status(400).json({ error: 'Invalid permissions provided' });
      }
    }
    
    // ロール更新
    role.name = name || role.name;
    role.description = description !== undefined ? description : role.description;
    role.permissions = permissions || role.permissions;
    role.updatedAt = new Date();
    
    await role.save();
    
    res.json({ 
      success: true, 
      role: {
        id: role.id,
        name: role.name,
        description: role.description,
        permissions: role.permissions
      }
    });
    
  } catch (error) {
    console.error('Role update error:', error);
    res.status(500).json({ error: 'Role update failed' });
  }
});

// ロール削除
app.delete('/api/roles/:roleId', checkPermission('roles:delete'), async (req, res) => {
  try {
    const { roleId } = req.params;
    
    const role = await Role.findById(roleId);
    if (!role) {
      return res.status(404).json({ error: 'Role not found' });
    }
    
    // ロールを使用しているユーザーをチェック
    const usersWithRole = await UserRole.countDocuments({ 
      roleId, 
      isActive: true 
    });
    
    if (usersWithRole > 0) {
      return res.status(400).json({ 
        error: 'Cannot delete role. Users are still assigned to this role.' 
      });
    }
    
    // ソフトデリート
    role.isActive = false;
    role.updatedAt = new Date();
    await role.save();
    
    res.json({ success: true, message: 'Role deleted successfully' });
    
  } catch (error) {
    console.error('Role deletion error:', error);
    res.status(500).json({ error: 'Role deletion failed' });
  }
});

    コードの中で確かめていることを整理します。

    • 入力値検証：名前と権限の配列がなければ 400（リクエストの誤り）
    • 重複チェック：同じ名前のロールがあれば 409（競合）
    • 権限の有効性チェック：指定された権限名がすべて Permission マスタに有効な形で存在するかを照合し、存在しない権限名が混ざっていれば 400
    • 削除前のチェック：そのロールを割り当てられたユーザーが残っていれば削除しない
    • ソフトデリート：データを実際には消さず、isActive = false にして「無効」の印を付ける方法。履歴を残せ、誤操作からも戻せます

    ユーザーにロールを割り当てたり、外したりする API です。

    ユーザーロール一覧取得GET /api/users/:userId/rolesusers:read
    ユーザーロール割り当てPOST /api/users/:userId/rolesusers:update
    ユーザーロール削除DELETE /api/users/:userId/roles/:roleIdusers:update
     
    // ユーザーロール管理API
// ユーザーロール一覧取得
app.get('/api/users/:userId/roles', checkPermission('users:read'), async (req, res) => {
  try {
    const { userId } = req.params;
    
    const userRoles = await UserRole.find({ 
      userId, 
      isActive: true 
    }).populate('roleId', 'name description permissions');
    
    res.json({ userRoles });
  } catch (error) {
    res.status(500).json({ error: 'Failed to fetch user roles' });
  }
});

// ユーザーロール割り当て
app.post('/api/users/:userId/roles', checkPermission('users:update'), async (req, res) => {
  try {
    const { userId } = req.params;
    const { roleId, expiresAt } = req.body;
    const assignedBy = req.user.userId;
    
    // ユーザー存在チェック
    const user = await User.findById(userId);
    if (!user) {
      return res.status(404).json({ error: 'User not found' });
    }
    
    // ロール存在チェック
    const role = await Role.findById(roleId);
    if (!role || !role.isActive) {
      return res.status(404).json({ error: 'Role not found' });
    }
    
    // 既存の割り当てチェック
    const existingAssignment = await UserRole.findOne({
      userId,
      roleId,
      isActive: true
    });
    
    if (existingAssignment) {
      return res.status(409).json({ error: 'User already has this role' });
    }
    
    // ロール割り当て
    const userRole = await UserRole.create({
      userId,
      roleId,
      assignedBy,
      expiresAt: expiresAt ? new Date(expiresAt) : undefined
    });
    
    res.status(201).json({ 
      success: true, 
      userRole: {
        id: userRole.id,
        role: {
          id: role.id,
          name: role.name,
          description: role.description
        },
        assignedAt: userRole.assignedAt,
        expiresAt: userRole.expiresAt
      }
    });
    
  } catch (error) {
    console.error('User role assignment error:', error);
    res.status(500).json({ error: 'User role assignment failed' });
  }
});

// ユーザーロール削除
app.delete('/api/users/:userId/roles/:roleId', checkPermission('users:update'), async (req, res) => {
  try {
    const { userId, roleId } = req.params;
    
    const userRole = await UserRole.findOne({
      userId,
      roleId,
      isActive: true
    });
    
    if (!userRole) {
      return res.status(404).json({ error: 'User role assignment not found' });
    }
    
    // ソフトデリート
    userRole.isActive = false;
    await userRole.save();
    
    res.json({ success: true, message: 'User role removed successfully' });
    
  } catch (error) {
    console.error('User role removal error:', error);
    res.status(500).json({ error: 'User role removal failed' });
  }
});
    • 割り当て時に、ユーザーとロールが存在するか、すでに同じロールを持っていないかを確かめます。
    • assignedBy に操作した人を記録し、expiresAt で有効期限を付けられます。
    • ロールを外すときもソフトデリートです。外した時点で isActive が false になるため、次の権限チェックからそのロールの権限は使われなくなります。

    6.フロントエンド実装（React）

    管理者がロールを作ったり、ユーザーにロールを割り当てたりする画面です。authenticatedRequest は、ログイン情報を付けて API を呼ぶ自作の関数を想定しています。

    6.1 ロール管理コンポーネント

    ロール一覧と権限一覧を読み込み、作成フォームの表示切り替え・作成・削除を行います。

    // フロントエンド（React）
import { useState, useEffect } from 'react';

// ロール管理コンポーネント
const RoleManagement = () => {
  const [roles, setRoles] = useState([]);
  const [permissions, setPermissions] = useState([]);
  const [isLoading, setIsLoading] = useState(false);
  const [showCreateForm, setShowCreateForm] = useState(false);

  useEffect(() => {
    fetchRoles();
    fetchPermissions();
  }, []);

  const fetchRoles = async () => {
    try {
      const response = await authenticatedRequest('/api/roles');
      const data = await response.json();
      setRoles(data.roles);
    } catch (error) {
      console.error('Failed to fetch roles:', error);
    }
  };

  const fetchPermissions = async () => {
    try {
      const response = await authenticatedRequest('/api/permissions');
      const data = await response.json();
      setPermissions(data.permissions);
    } catch (error) {
      console.error('Failed to fetch permissions:', error);
    }
  };

  const handleCreateRole = async (roleData) => {
    setIsLoading(true);
    try {
      const response = await authenticatedRequest('/api/roles', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(roleData)
      });

      if (response.ok) {
        await fetchRoles();
        setShowCreateForm(false);
        alert('Role created successfully');
      } else {
        const error = await response.json();
        alert(error.error);
      }
    } catch (error) {
      alert('Failed to create role');
    } finally {
      setIsLoading(false);
    }
  };

  const handleDeleteRole = async (roleId) => {
    if (!confirm('Are you sure you want to delete this role?')) {
      return;
    }

    try {
      const response = await authenticatedRequest(`/api/roles/${roleId}`, {
        method: 'DELETE'
      });

      if (response.ok) {
        await fetchRoles();
        alert('Role deleted successfully');
      } else {
        const error = await response.json();
        alert(error.error);
      }
    } catch (error) {
      alert('Failed to delete role');
    }
  };

  return (
    <div className="role-management">
      <div className="page-header">
        <h2>Role Management</h2>
        <button 
          onClick={() => setShowCreateForm(true)}
          className="create-btn"
        >
          Create New Role
        </button>
      </div>

      {showCreateForm && (
        <CreateRoleForm
          permissions={permissions}
          onSubmit={handleCreateRole}
          onCancel={() => setShowCreateForm(false)}
          isLoading={isLoading}
        />
      )}

      <div className="roles-list">
        {roles.map(role => (
          <RoleCard
            key={role.id}
            role={role}
            onDelete={handleDeleteRole}
          />
        ))}
      </div>
    </div>
  );
};

    6.2 ロール作成フォーム

    権限を リソース別にグループ化 し、チェックボックスで選べるようにしています（例：posts の下に create / read / update / delete が並ぶ）。

    // ロール作成フォーム
const CreateRoleForm = ({ permissions, onSubmit, onCancel, isLoading }) => {
  const [formData, setFormData] = useState({
    name: '',
    description: '',
    permissions: []
  });

  const handleInputChange = (e) => {
    const { name, value } = e.target;
    setFormData(prev => ({
      ...prev,
      [name]: value
    }));
  };

  const handlePermissionChange = (permission, checked) => {
    setFormData(prev => ({
      ...prev,
      permissions: checked
        ? [...prev.permissions, permission]
        : prev.permissions.filter(p => p !== permission)
    }));
  };

  const handleSubmit = (e) => {
    e.preventDefault();
    onSubmit(formData);
  };

  // 権限をリソース別にグループ化
  const groupedPermissions = permissions.reduce((groups, permission) => {
    const resource = permission.resource;
    if (!groups[resource]) {
      groups[resource] = [];
    }
    groups[resource].push(permission);
    return groups;
  }, {});

  return (
    <form onSubmit={handleSubmit} className="create-role-form">
      <h3>Create New Role</h3>
      
      <div className="form-group">
        <label htmlFor="name">Role Name</label>
        <input
          type="text"
          id="name"
          name="name"
          value={formData.name}
          onChange={handleInputChange}
          required
        />
      </div>
      
      <div className="form-group">
        <label htmlFor="description">Description</label>
        <textarea
          id="description"
          name="description"
          value={formData.description}
          onChange={handleInputChange}
          rows="3"
        />
      </div>
      
      <div className="form-group">
        <label>Permissions</label>
        <div className="permissions-grid">
          {Object.entries(groupedPermissions).map(([resource, resourcePermissions]) => (
            <div key={resource} className="permission-group">
              <h4>{resource}</h4>
              {resourcePermissions.map(permission => (
                <label key={permission.id} className="permission-item">
                  <input
                    type="checkbox"
                    checked={formData.permissions.includes(permission.name)}
                    onChange={(e) => handlePermissionChange(permission.name, e.target.checked)}
                  />
                  {permission.action}
                </label>
              ))}
            </div>
          ))}
        </div>
      </div>

  );

    画面は入口、守りはサーバー

    管理画面を見せない・ボタンを隠すのは使いやすさのためで、守りにはなりません。API を直接呼ばれても止まるよう、必ずサーバー側の checkPermission で確かめます（画面で隠しても守れない）。

    7.リソースベース権限

    ロールの権限だけでは「投稿を編集できる人」までしか決まりません。リソースベース権限 は、さらに「この 投稿を編集してよいか」を、データの持ち主などで確かめる方法です。

    // リソースベース権限チェック
const checkResourcePermission = (resource, action, resourceId = null) => {
  return async (req, res, next) => {
    try {
      const user = req.user;
      const permission = `${resource}:${action}`;
      
      // 基本権限チェック
      const userPermissions = await getUserPermissions(user.id);
      if (!userPermissions.includes(permission)) {
        return res.status(403).json({ error: 'Insufficient permissions' });
      }
      
      // リソース固有の権限チェック
      if (resourceId) {
        const hasResourceAccess = await checkResourceAccess(user.id, resource, resourceId);
        if (!hasResourceAccess) {
          return res.status(403).json({ error: 'Access denied to this resource' });
        }
      }
      
      next();
    } catch (error) {
      console.error('Resource permission check error:', error);
      res.status(500).json({ error: 'Permission check failed' });
    }
  };
};

// リソースアクセスチェック
const checkResourceAccess = async (userId, resource, resourceId) => {
  switch (resource) {
    case 'posts':
      const post = await Post.findById(resourceId);
      return post && (post.authorId.toString() === userId || await hasAdminRole(userId));
    
    case 'users':
      return resourceId === userId || await hasAdminRole(userId);
    
    default:
      return true;
  }
};
    • まず posts:update のような 基本権限 を確認します。
    • 次に checkResourceAccess で リソース固有の権限 を確認します。投稿なら作成者本人か管理者、ユーザー情報なら本人か管理者だけが通ります。

    同じ考え方の短い例は リソースベース認可（認証と認可の違い）にもあります。この確認が抜けると、ID を書き換えるだけで他人のデータに触れられる「認可不備」になります（認可不備と認可の要件定義 を参照）。

    8.動的権限

    動的権限 は、ロールの権限に加えて、時刻やリクエストの内容など その場の状況 で判定する方法です。判定用の関数を渡せるようにしておくと、さまざまな条件を同じ形で書けます。

    // 動的権限チェック
const checkDynamicPermission = (permissionFunction) => {
  return async (req, res, next) => {
    try {
      const user = req.user;
      const hasPermission = await permissionFunction(user, req);
      
      if (!hasPermission) {
        return res.status(403).json({ error: 'Insufficient permissions' });
      }
      
      next();
    } catch (error) {
      console.error('Dynamic permission check error:', error);
      res.status(500).json({ error: 'Permission check failed' });
    }
  };
};

// 使用例：時間制限付き権限
const timeBasedPermission = async (user, req) => {
  const userPermissions = await getUserPermissions(user.id);
  
  if (!userPermissions.includes('posts:create')) {
    return false;
  }
  
  // 営業時間内のみ投稿可能
  const currentHour = new Date().getHours();
  return currentHour >= 9 && currentHour <= 17;
};

app.post('/api/posts', checkDynamicPermission(timeBasedPermission), createPostHandler);

    この例では、posts:create 権限を持っていても、営業時間内（9〜17 時台）のみ投稿可能 になります。属性（時刻など）で判定する点は ABAC の考え方に近いものです。

    9.セキュリティベストプラクティス

    9.1 権限の最小化

    デフォルトロール（最初から用意しておくロール）を、それぞれの仕事に必要な権限だけで作ります。

    // デフォルトロールの設定
const createDefaultRoles = async () => {
  const defaultRoles = [
    {
      name: 'admin',
      description: 'Full system access',
      permissions: ['*'] // 全権限
    },
    {
      name: 'user',
      description: 'Basic user access',
      permissions: [
        'profile:read',
        'profile:update',
        'posts:create',
        'posts:read'
      ]
    },
    {
      name: 'moderator',
      description: 'Content moderation access',
      permissions: [
        'posts:read',
        'posts:update',
        'posts:delete',
        'users:read'
      ]
    }
  ];
  
  for (const roleData of defaultRoles) {
    const existingRole = await Role.findOne({ name: roleData.name });
    if (!existingRole) {
      await Role.create(roleData);
    }
  }
};
    ロール説明権限
    adminシステム全体へのアクセス*（全権限）
    user基本的なユーザーアクセスプロフィールの閲覧・更新、投稿の作成・閲覧
    moderatorコンテンツの管理（モデレーション）投稿の閲覧・更新・削除、ユーザーの閲覧

    一般ユーザーには投稿の削除権限を、モデレーターにはロール管理の権限を渡していない点が「最小化」です。最小権限の原則そのものは 71 の 最小権限とデータ最小化 を参照してください。

    * は自動では効かない

    3 章の checkPermission は includes(requiredPermission) で完全一致を見るだけなので、'*' を「全権限」として扱うには、チェック側に '*' を特別扱いする処理を足す必要があります。

    9.2 監査ログ

    監査ログ は、「誰が・いつ・何をしたか」を後から確かめるための記録です。権限の変更は不正や事故の調査で特に重要なので、ロール作成などのたびに記録します。

    // 権限変更の監査ログ
const auditLog = async (action, details) => {
  await AuditLog.create({
    action,
    details,
    timestamp: new Date(),
    ipAddress: req.ip,
    userAgent: req.get('User-Agent')
  });
};

// ロール変更時の監査ログ
app.post('/api/roles', checkPermission('roles:create'), async (req, res) => {
  // ... ロール作成処理 ...
  
  await auditLog('role_created', {
    roleId: role.id,
    roleName: role.name,
    permissions: role.permissions,
    createdBy: req.user.userId
  });
  
  res.json({ success: true, role });
});

    操作の種類・内容・時刻・IP アドレス・ブラウザ情報（User-Agent）と、誰が作成したか（createdBy）を残しています。なお、この例の auditLog は中で req を使っていますが引数で受け取っていないため、実際には req も渡す形にします。何を記録しどう守るかは 71 の 何を記録するか — ログの種類・イベント・項目 を参照してください。

    11.まとめ

    トピック要点
    データ設計User → UserRole（割り当て・期限・付与者）→ Role（権限名の配列）。Permission はマスタ
    権限チェックミドルウェアで未ログインは 401、権限不足は 403
    権限の集め方有効で期限内の割り当て → 有効なロールの権限 ＋ 直接権限
    管理 APIロール管理自体にも権限が必要。入力・重複・権限名を検証し、削除はソフトデリート
    画面使いやすさのため。守りはサーバー側のチェック
    リソースベース「この」データの持ち主か・管理者かまで確かめる
    動的権限時刻などその場の条件で判定する
    運用ロールは必要最小限の権限で作り、権限の変更は監査ログに残す
    選び方小規模は RBAC、中規模は RBAC ＋ リソースベース、大規模は ABAC ＋ ポリシーエンジン

    12.理解度チェック

    Q1. ユーザーとロールを直接つながず、間に UserRole を置くのはなぜですか？

    割り当てごとに「誰が割り当てたか（assignedBy）」「いつ割り当てたか」「いつまで有効か（expiresAt）」「今も有効か（isActive）」を記録するためです。期限付きの権限付与や、権限変更の追跡ができるようになります。

    Q2. checkPermission は、どんなときに 401 を返し、どんなときに 403 を返しますか？

    req.user がない（ログインしていない）ときは 401、ログインしているが必要な権限を持っていないときは 403 を返します。

    Q3. getUserPermissions が、あるロールの権限を集めないのはどんな場合ですか？

    割り当て（UserRole）が無効のとき、割り当ての有効期限が過ぎているとき、またはロール（Role）自体が無効のときです。

    Q4. 管理画面で「削除」ボタンを権限のない人に見せなければ、サーバー側のチェックは省けますか？

    省けません。画面を通さずに API を直接呼べるため、ボタンを隠すのは使いやすさのためでしかありません。守りは必ずサーバー側の checkPermission などで行います。

    Q5. posts:update 権限を持つ一般ユーザーが、他人の投稿を編集できないようにするには何を加えますか？

    リソースベース権限です。基本権限の確認に加えて、checkResourceAccess のように「その投稿の作成者本人か、管理者か」を確かめます。

    Q6. ロール削除で、データを実際に消さずに isActive = false にするのはなぜですか？

    ソフトデリートにすると、履歴が残って後から調べられ、誤って削除しても元に戻せるからです。さらにこの例では、割り当てられたユーザーが残っているロールは削除できないようにしています。

    Q7. 中規模のシステムでは、どの権限モデルが勧められていますか？

    RBAC ＋ リソースベースです。ロールによる分かりやすい管理と、データ単位の確認を組み合わせ、柔軟性とセキュリティのバランスを取ります。
