    20 パスワード・MFA・パスキー

    パスワードの安全な保存

    「なぜ暗号化ではなくハッシュなのか」「ソルトとストレッチングは何を防ぐのか」を徳丸本 21 章で押さえたうえで、実際に何を選び、どう設定し、古い方式からどう移るか（Argon2id・ペッパー・移行・NIST の指針）までを整理します。

    もとにしたノート：20_パスワード・MFA・パスキー/01_認証（徳丸本21章）のパスワード保存の部分、20_パスワード・MFA・パスキー/02_パスワードの安全な保存

    このページで分かること

    • パスワードを守る必要性と、暗号化による保存が向かない理由
    • ハッシュ（メッセージダイジェスト）に対する攻撃と、ソルト・ストレッチングの考え方
    • いま使うべきアルゴリズム（Argon2id・scrypt・bcrypt・PBKDF2）と推奨設定
    • ソルト・ペッパー・ストレッチングの役割分担と、保存される文字列の読み方
    • Node.js での実装例、コストの決め方、古いハッシュからの移行方法
    • NIST SP 800-63B によるパスワードの受け付け方と、よくある落とし穴

    ハッシュ・レインボーテーブル・ソルトの基本は パスワードの仕組みと安全な保存 で図を使って説明しました。このページはその続きとして、もう一段深く掘り下げます。ログイン画面そのものへの攻撃（パスワード試行・パスワードリスト攻撃など）は ログイン機能への攻撃と対策 で扱います。

    1.なぜパスワードを守る必要があるのか

    サーバーは、ログイン時にパスワードを照合するため、何らかの形でパスワード情報を保持します。平文（そのままの文字）で保存してはいけません。

    目的は、データベース（DB）が漏洩した場合でも、攻撃者がそのままログインできないようにすることです。保護が不十分だと、次のような悪用が起きます。

    悪用説明
    パスワードリスト攻撃への悪用漏洩した ID・パスワードを、他サービスでも試される
    該当利用者の権限で使える機能の悪用なりすまして、その人だけができる操作を実行される
    データの投稿・更新・削除本人の権限で、内容を書き換え・消される

    日常生活での例え

    • 平文保存：金庫の暗証番号を、メモにそのまま書いて机に置く
    • 適切な保護：メモには「本人だけが再現できる形」だけを残し、元の番号は書かない

    2.暗号化によるパスワード保護と課題

    パスワードを暗号アルゴリズムで暗号化して保存する考え方です。一見よさそうですが、パスワード保存には向かない ことが多いです。

    論点内容
    安全な暗号アルゴリズムの選定古い・弱いアルゴリズムは使えない
    暗号化・復号処理の安全な実装実装ミスで平文が漏れたり、改ざんされたりする
    鍵の生成推測しやすい鍵では意味がない
    鍵の保管鍵が DB と同じ場所にあると、DB 漏洩時にまとめて復号される

    最大の課題は 復号できる（元に戻せる）ことです。サーバーが復号できるなら、鍵を手に入れた攻撃者も復号できます。パスワード照合に必要なのは「入力が同じかどうか」であり、元のパスワードを取り出せる必要はありません。

    【暗号化のイメージ】
保存: パスワード →（鍵で暗号化）→ 暗号文をDBへ
照合: 入力 →（同じ鍵で暗号化）→ DBの暗号文と比較
     または、暗号文を復号して入力と比較

→ どちらも「鍵」が弱点になる

    そのため、パスワード保存の定石は暗号化ではなく、次に説明する メッセージダイジェスト（ハッシュ） です。

    3.メッセージダイジェスト（ハッシュ）による保護

    3.1 メッセージダイジェストとは

    メッセージダイジェスト（ハッシュ値） とは、入力データから計算した、固定長の要約値です。代表的な性質は次のとおりです。

    性質意味
    一方向性ハッシュから元のパスワードを簡単には戻せない
    決定性同じ入力なら、いつも同じハッシュになる
    入力が少し違うと大きく変わる1 文字違うだけで、見た目が全く違う値になる

    パスワード保存では、MD5 や SHA-1 のような高速な汎用ハッシュをそのまま使うのは推奨されません。パスワード向けには bcrypt、scrypt、Argon2 などの専用アルゴリズムが使われます。

    3.2 ハッシュでパスワードを保護する流れ

    【登録時】
1. 利用者がパスワードを入力
2. サーバーがハッシュを計算
3. ハッシュだけをDBに保存（元パスワードは捨てる）

【ログイン時】
1. 利用者がパスワードを入力
2. 同じ方法でハッシュを計算
3. DB上のハッシュと比較し、一致すれば認証成功

    元パスワードが DB に無いので、DB が漏れても すぐにはパスワードが分からない のが利点です。ただし、ハッシュだけでは不十分な攻撃もあります。

    4.ハッシュに対する攻撃

    攻撃内容
    オンラインブルートフォース攻撃ログイン画面経由で、実際にログインを試し続ける
    レインボーテーブルよくあるパスワードのハッシュを事前計算した巨大な表で、ハッシュからパスワードを逆引きする
    ユーザー DB 内にパスワード辞書を作られる漏洩したハッシュを、攻撃者の手元で辞書や総当たりで解析する（オフライン攻撃）

    オンライン攻撃はアカウントロックや監視で抑えられます（詳しくは ログイン機能への攻撃と対策）。一方、DB が漏洩したあとの オフライン攻撃 は、攻撃者の計算機リソース次第で高速に試行できるため、ハッシュの作り方が重要です。

    5.ハッシュ解読対策の考え方：ソルトとストレッチング

    対策内容効果
    ソルト（salt）ユーザーごとに異なるランダム値をパスワードに足してからハッシュする同じパスワードでもハッシュが異なり、レインボーテーブルが使いにくい
    ストレッチングハッシュ計算を何千・何万回と繰り返す（または意図的に遅いアルゴリズムを使う）オフライン総当たりの速度を落とす

    ソルトを使った登録・照合の流れは ソルトでレインボーテーブル攻撃を防ぐ の図を参照してください。要点は次のとおりです。

    【ソルト付きハッシュのイメージ】
保存するもの:
  ・ソルト（平文でよい。秘密ではない）
  ・ハッシュ(ソルト + パスワード)

照合:
  入力パスワードと、保存してあるソルトで同じ計算をし、ハッシュを比較
    【ストレッチングのイメージ】
hash = H(password)
hash = H(hash)
hash = H(hash)
... を多数回繰り返す

→ 1回の照合が重くなるので、攻撃者の試行回数も減る

    現代的なパスワードハッシュ（bcrypt、Argon2 など）は、ソルトとコスト（遅さ）の考え方を組み込んでいます。自前で SHA-256 を何度も回すより、実績のあるパスワード用ライブラリを使う 方が安全です。ここからは、その「実際に何を選び、どう設定するか」を見ていきます。

    6.結論：何を使うか

    優先アルゴリズム推奨設定（OWASP の目安）使う場面
    1Argon2idメモリ 19 MiB・反復 2・並列 1新しく作るなら第一候補
    2scryptN=2^17・r=8・p=1Argon2 が使えない環境
    3bcryptコスト 10 以上古くからある実績重視の環境。72 バイトまでしか使われない 点に注意
    4PBKDF2（HMAC-SHA-256）反復 600,000 回FIPS（米国政府の暗号モジュール基準）準拠が必要なとき
    使ってはいけない理由
    平文・可逆な暗号化DB と鍵が漏れれば全員分が分かる
    MD5・SHA-1・SHA-256 を 1 回速すぎる。GPU なら 1 秒に数十億回試せる
    自作の「SHA-256 を 1000 回」回数が足りず、実装ミスも起きやすい。専用のアルゴリズムを使う

    ポイント

    パスワード用ハッシュは わざと遅く、メモリを多く使う ように作られています。正規の利用者は 1 回計算するだけですが、攻撃者は何十億回も計算する必要があるので、その差で守ります。

    平文・MD5・bcrypt のコード比較は パスワードの保存：平文・MD5・bcrypt（セキュリティ基礎）にもあります。

    7.ソルト・ペッパー・ストレッチングの役割

    要素中身どこに置くか防ぐもの
    ソルト利用者ごとのランダム値（16 バイト以上）ハッシュと一緒に DB に置く（秘密ではない）レインボーテーブル、同じパスワードの利用者が一目で分かること
    ストレッチング計算を重くする設定（コスト・反復・メモリ）ハッシュ文字列の中に記録されるオフラインでの総当たり
    ペッパー（任意）全員共通の秘密の値DB とは 別の場所（環境変数・KMS・HSM）DB だけが漏れた場合の解析

    KMS（Key Management Service）はクラウドの鍵管理サービス、HSM（Hardware Security Module）は鍵を安全に保管する専用機器です。

    • Argon2・bcrypt・scrypt のライブラリは ソルトを自動で作り、結果の文字列に含めます。自分で管理する必要はありません。
    • ペッパーは、HMAC（鍵付きハッシュ）で混ぜるか、ハッシュ結果を鍵で暗号化します。鍵を入れ替える手順も決めておく必要があるので、ここまでは任意 です。

    7.1 保存される文字列の例

    $argon2id$v=19$m=19456,t=2,p=1$c29tZXNhbHQ$RdescudvJCsgt3ub+b+dWRWJTmaaJObG
 └ 方式 ─┘ └版┘ └─ コスト設定 ──┘ └ ソルト ┘ └──── ハッシュ値 ────┘

    方式・設定・ソルトが文字列に含まれるので、照合に必要な情報は 1 つの列にまとまります。後で設定を強くしても、古い行は古い設定のまま照合できます。

    8.実装例（Node.js）

    安全な例：Argon2id で保存し、ログイン時に必要なら作り直す 
    import argon2 from 'argon2';

const OPTIONS = {
  type: argon2.argon2id,
  memoryCost: 19456, // KiB（= 19 MiB）
  timeCost: 2,
  parallelism: 1,
};

// 登録・パスワード変更時
export async function hashPassword(password) {
  return argon2.hash(password, OPTIONS);
}

// ログイン時
export async function verifyPassword(user, password) {
  const ok = await argon2.verify(user.passwordHash, password);
  if (!ok) return false;

  // 設定を強くした後なら、ログイン成功のタイミングで新しい設定に作り直す
  if (argon2.needsRehash(user.passwordHash, OPTIONS)) {
    user.passwordHash = await hashPassword(password);
    await user.save();
  }
  return true;
}
    • 比較は必ずライブラリの verify を使います。=== で文字列比較すると、処理時間の差から情報が漏れる（タイミング攻撃）ことがあります。
    • 存在しないユーザーでもダミーのハッシュで verify を実行し、応答時間でアカウントの有無が分からない ようにします。

    8.1 コストの決め方

    • 本番と同じ性能のサーバーで測り、1 回の計算がおよそ 0.1〜0.5 秒 になる設定にします。
    • 重くしすぎると、ログイン画面への大量アクセスでサーバーが止まります（DoS：サービス妨害）。レート制限（一定時間あたりの回数制限）と一緒に考えます。

    9.古い方式からの移行

    MD5 や SHA-1 で保存してしまっている場合、元のパスワードが分からないので、すぐには作り直せません。2 つの方法を組み合わせます。

    方法内容長所・短所
    ログイン時に作り直すログイン成功時に、入力された平文で Argon2id のハッシュを作り直す簡単。ただし、ログインしない利用者は古いまま残る
    包んで作り直す今ある MD5 の値を入力にして Argon2id(MD5(password)) を全件すぐに作る。照合時も同じ順で計算する全件をすぐ強くできる。どの方式で包んだかの印を持たせる
     
    1. 全件を Argon2id(旧ハッシュ) に置き換え、方式の列に "wrapped" と記録
2. ログイン成功時に Argon2id(平文) へ作り直し、"argon2id" に更新
3. 一定期間ログインのない利用者は、パスワードを無効にしてリセットしてもらう

    10.パスワードの受け付け方（NIST SP 800-63B）

    保存方法とあわせて、どんなパスワードを受け付けるか も決めます。NIST（米国国立標準技術研究所）の最新の指針（SP 800-63B Rev.4）の要点です。「定期変更や複雑さの強制がなぜ逆効果か」という背景は パスワードポリシーの最新推奨（セキュリティ基礎）を参照してください。

    項目指針
    最小の長さパスワードだけで認証するなら 15 文字以上、MFA と組み合わせるなら 8 文字以上
    最大の長さ64 文字以上は受け付ける。空白・絵文字などすべての文字を許す
    文字種の組み合わせルール「大文字・数字・記号を必ず入れる」のような強制はしない
    定期的な変更強制しない。漏えいが分かったときだけ変更させる
    ブロックリストよく使われるパスワード・漏えい済みのパスワード・サービス名を含むものを拒否する
    貼り付けパスワードマネージャーのために、貼り付けを許可する
    • 漏えい済みかどうかは、Have I Been Pwned の Pwned Passwords API で確かめられます。ハッシュの先頭 5 文字だけを送る方式なので、パスワードそのものは外に出ません。
    • bcrypt を使う場合、72 バイトを超えた部分は無視されます。最大の長さを決めるか、Argon2id を選びます。

    11.よくある落とし穴

    落とし穴内容
    ログに平文が残るリクエストボディをそのままログに出し、パスワードが残る。マスクする項目を決める（ノート「06_ログ出力（徳丸本24章）」）
    パスワードをメールで送る登録完了やリセットのメールに平文を書く。リセットは 1 回だけ使えるリンクで行う（ノート「03_パスワードリセット機能」）
    「パスワードを表示」機能のためにとっておく復号できる形で保存する理由にならない。利用者にはリセットしてもらう
    ハッシュ化をクライアント側だけで行う送られてきたハッシュがそのままパスワードの代わりになる。サーバー側で必ずハッシュ化する

    12.対策の優先順位

    1. 平文・可逆暗号・高速ハッシュをやめ、Argon2id（または scrypt / bcrypt）で保存する
    2. コストを本番環境で測って決め、needsRehash で順次強くする
    3. 古いハッシュは「包んで作り直す」で全件すぐ強くする
    4. 漏えい済みパスワードのブロックリスト・長さの指針を入れる
    5. ペッパー（DB と別の場所に置く秘密）は余裕があれば追加

    保存を正しくしても足りないこと

    パスワードは「保存を正しくしても、使い回しやフィッシングには勝てない」仕組みです。根本的な対策は MFAの方式比較 と パスキーとWebAuthn に続きます。

    13.まとめ

    テーマ要点
    保護の必要性DB が漏れても、パスワードリスト攻撃やなりすましに使わせない
    暗号化復号できるので、鍵が弱点になる。パスワード保存には向かない
    ハッシュ一方向・決定的。ただし速い汎用ハッシュはオフライン攻撃に弱い
    ソルト利用者ごとのランダム値。レインボーテーブルと同一パスワードの判別を防ぐ（秘密ではない）
    ストレッチング1 回の計算を重くし、オフライン総当たりを遅くする
    ペッパーDB と別の場所に置く共通の秘密。任意
    選ぶものArgon2id → scrypt → bcrypt → PBKDF2 の順。自作しない
    運用コストは 0.1〜0.5 秒を目安に測って決め、needsRehash と「包んで作り直す」で移行する
    受け付け方長さ重視・ブロックリスト・定期変更なし・貼り付け許可（NIST SP 800-63B）

    14.理解度チェック

    Q1. パスワードを暗号化して保存するのが向かない最大の理由は何ですか？

    復号できる ことです。サーバーが復号できるなら、鍵を手に入れた攻撃者も復号できます。照合に必要なのは「入力が同じかどうか」だけなので、元に戻せないハッシュで十分です。

    Q2. オンライン攻撃とオフライン攻撃の違いと、それぞれの主な対策を答えてください。

    オンライン攻撃はログイン画面経由で試すので、アカウントロックや監視で抑えられます。オフライン攻撃は漏洩したハッシュを攻撃者の手元で解析するのでサーバー側の対策が届かず、ソルトとストレッチング（遅いパスワード用ハッシュ） が防御になります。

    Q3. ソルトとペッパーの違いは何ですか？

    ソルトは利用者ごとのランダム値で、ハッシュと一緒に DB に置きます（秘密ではない）。ペッパーは全員共通の秘密の値で、DB とは別の場所（環境変数・KMS・HSM）に置き、DB だけが漏れた場合の解析を防ぎます。ペッパーは任意です。

    Q4. bcrypt を使うときに注意すべき制限は何ですか？

    入力の 72 バイトまでしか使われない ことです。超えた部分は無視されるので、最大の長さを決めるか、Argon2id を選びます。

    Q5. ハッシュの比較に === を使わず、ライブラリの verify を使うのはなぜですか？

    === の文字列比較は処理時間に差が出て、そこから情報が漏れる（タイミング攻撃）ことがあるからです。あわせて、存在しないユーザーでもダミーのハッシュで verify を実行し、応答時間でアカウントの有無が分からないようにします。

    Q6. MD5 で保存された既存のパスワードを、全件すぐに強くするにはどうしますか？

    今ある MD5 の値を入力にして Argon2id(MD5(password)) を全件作り、「wrapped」と印を付けます（包んで作り直す）。ログイン成功時に Argon2id(平文) へ作り直して「argon2id」に更新し、一定期間ログインのない利用者はパスワードを無効にしてリセットしてもらいます。

    Q7. NIST SP 800-63B Rev.4 では、パスワードだけで認証する場合の最小の長さは何文字ですか？ また定期的な変更はどう扱いますか？

    15 文字以上です（MFA と組み合わせるなら 8 文字以上）。定期的な変更は強制せず、漏えいが分かったときだけ変更させます。
