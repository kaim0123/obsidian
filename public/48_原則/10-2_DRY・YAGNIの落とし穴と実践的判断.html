    10 汎用原則

    DRY・YAGNI の落とし穴と実践的判断 — いつ適用し、いつ適用しないか

    設計原則は「知っている」だけでは不十分で、いつ適用し、いつ適用しないか の判断が本質です。このページでは、DRY の本来の意味（コードの見た目ではなく知識の重複）、DRY と SRP（単一責任の原則）が衝突する場面、「間違った抽象化より重複のほうが安い」という考え方、YAGNI が初心者には難しい理由、そしてベテランの「勘」の正体を整理し、重複を見つけたときの判断フローにまとめます。

    もとにしたノート：03_DRY・YAGNI原則の落とし穴と実践的判断

    ひとことで言うと

    DRY が避けたいのは コードの見た目の重複ではなく、ビジネス上の知識や意図の重複 です。見た目が同じでも変わる理由が違えば分けておき、迷ったら3回目まで待ちます。YAGNI は テスト・リファクタリング・CI/CD がそろって初めて成り立つ 原則です。設計判断の本質は「正解を選ぶ」ことではなく 「どちらの壊れ方がマシか」を比較する ことです。

    1.このページで扱うこと

    DRY・KISS・YAGNI の基本的な定義は DRY・KISS・YAGNI を見てください。このページでは、DRY・YAGNI・SRP が衝突する場面での考え方を整理します。

    • DRY 原則の致命的な誤解（偶然の重複と本質的な重複、判断のチェックリスト）
    • DRY と SRP の衝突と、「壊れ方」で比べる考え方
    • 「間違った抽象化」より「重複」のほうが安い（Rule of Three と AHA）
    • YAGNI 原則が初心者に遵守できない理由と、成立する前提条件
    • ベテランの「勘」の正体
    • 重複を見つけたときの実践的な判断フロー

    SRP そのものは 単一責任の原則、クラス単位で SOLID 同士や他の原則とのバランスをどう取るかは 44 の SOLID の統合と判断 で扱います。

    2.DRY 原則の致命的な誤解

    2.1 原著者による訂正

    『The Pragmatic Programmer』（邦題『達人プログラマー』）20周年記念版で、著者の Dave Thomas と Andy Hunt は DRY の誤解を明確に訂正しました。

    「DRY とは『知識』や『意図』の重複に関するものです」

    本来の定義 は次のとおりです。

    すべての知識はシステム内で単一で、あいまいでなく、権威ある表現を持たなければならない

    つまり 避けるべきは「コードの外観の重複」ではなく「ビジネス上の知識や意図の重複」 です。ここでいう ビジネス上の知識 は、「年齢は0以上」「送料は500円」のような、そのシステムが扱う業務のルールのことです。

    2.2 偶然の重複 vs 本質的な重複

    コードが同じでも、表している 知識 が異なれば、それは「偶然の一致」であり DRY 違反ではありません。

    // 年齢の検証
function validateAge(value: number) {
  validateType(value, 'integer');
  validateMinInteger(value, 0);
}

// 数量の検証
function validateQuantity(value: number) {
  validateType(value, 'integer');
  validateMinInteger(value, 0);
}

    一見同じコードですが、年齢と数量は異なる知識 を表しています。

    • 年齢 → 将来「20歳以上」という制約が追加される可能性
    • 数量 → 将来「在庫数以下」という制約が追加される可能性

    これらを無理に共通化すると、変更理由が異なるものが結合 してしまい、一方の変更がもう一方に波及します。

    2.3 判断のチェックリスト

    共通化すべきか迷ったら、次を確認します。

    質問Yes → 共通化No → 分けておく
    同じビジネスルールを表しているか？○×
    一方が変わったら必ず他方も変わるか？○×
    変更理由（＝責務）は同一か？○×

    3つとも Yes なら共通化し、1つでも No なら分けておく、と読みます。

    3.DRY vs SRP（単一責務原則）の衝突

    3.1 なぜ衝突するのか

    SRP（単一責任の原則、単一責務原則とも）は「1つのモジュールが変わる理由は1つだけにする」という SOLID の1つ目の原則です。

    DRY

    「共通知識の重複」を警告する

    SRP

    「変更理由の混線」を警告する

    この2つは、同じコードに対して 正反対の指示 を出すことがあります。

    3.2 具体例：部門ごとの税計算

    // 営業部の売上税計算
function calcSalesTax(amount) {
  return amount * 0.1;
}

// 経理部の仕入税計算
function calcPurchaseTax(amount) {
  return amount * 0.1;
}
    • DRY の観点：「同じ amount * 0.1 が重複している → 共通化すべき」
    • SRP の観点：「営業部と経理部は異なる変更理由を持つ → 分離すべき」

    正解は SRP を優先する場合が多い です。なぜなら：

    • 税率改正で売上税と仕入税が異なる率になる可能性がある
    • 共通化していると、片方だけ変更したいときに条件分岐が増殖する

    3.3 壊れ方のトレードオフで考える

    良い設計とは「正解を選ぶ」ことではなく、壊れ方の比較 です。トレードオフ（何かを得ると別の何かを失う関係）として、どちらを選んでも何かしらの壊れ方が残ります。

    選択壊れ方
    DRY を優先して共通化変更理由が分岐したとき、条件分岐が増殖してスパゲティ化
    SRP を優先して分離共通のビジネスルールが変わったとき、複数箇所の修正が必要

    どちらの壊れ方がより危険か を判断します。将来の変更が予測しにくい場合は、分離しておくほうが安全です。

    4.「間違った抽象化」より「重複」のほうが安い

    Sandi Metz の名言があります。

    "Duplication is far cheaper than the wrong abstraction"
    （重複は、間違った抽象化よりはるかに安上がりである）

    不適切な共通化がもたらすスパゲティコードの修正コストは、2箇所に同じコードがある状態の修正コストより はるかに高い のです。間違った共通部品には、呼び出し元ごとの事情を吸収するための引数やフラグ、条件分岐が少しずつ足されていき、誰も全体を把握できなくなります。

    4.1 Rule of Three（3回の法則）と AHA

    AHA（Avoid Hasty Abstractions）：性急な抽象化を避ける、という考え方です。Rule of Three と組み合わせて、次の順で進めます。

    1. 1回目：普通にコードを書く
    2. 2回目：同じ処理でもコピペして重複させる（まだ共通化しない）
    3. 3回目：3回目で初めて共通化を検討する

    2つのサンプルだけでは、共通化のパターンが本当に正しいか判断できません。3回目に初めて「これは本質的に同じ知識だ」と確信を持てます。

    5.YAGNI 原則が初心者に遵守できない理由

    5.1 「何が不要か」を見抜く難しさ

    YAGNI の文言「まだ必要ないものは作らない」は一見簡単に見えます。しかし実際には 「何が不要か」を正しく判断する能力 が前提となります。

    初心者が識別できる「不要な機能」

    • 明らかに使わない画面やボタン
    • 誰も要求していない機能

    ベテランが識別できる「不要なもの」

    • 過剰な抽象化レイヤー
    • 先回りしたデザインパターンの適用
    • 将来の拡張を見越した不要なインターフェース
    • 必要以上の設定可能性（configurability）

    初心者は「不要なもの」の認識範囲が狭い ため、YAGNI を知っていても実践できません。目に見える機能は削れても、「設計の作りすぎ」は不要だと気づけないのです。

    5.2 YAGNI が成立する前提条件

    YAGNI が機能するには、次が 必須 です。

    1. テスト環境が整っていること — 後から安全に変更できる保証
    2. リファクタリング能力があること — 「後で追加する」が実行できる技術力（リファクタリングは、外から見た動きを変えずにコードの中身を整理すること）
    3. CI/CD が整備されていること — 変更を素早くデプロイできる体制（CI/CDは、変更のたびに自動でテスト・ビルド・リリースする仕組み）

    これらがなければ「今は作らない → 必要になったら追加する」の後半が成立せず、YAGNI は ただの手抜きの言い訳 になります。

    5.3 教育上の課題

    標語の暗記では YAGNI は身につきません。身につけるには：

    • 具体的なコードレビューを通じて「これは不要」「これは必要」の境界線を体験する
    • ベテランの判断過程を言語化してもらう
    • 自分で「作りすぎた」「作らなさすぎた」の両方を経験する

    6.ベテランの「勘」の正体

    ベテランの設計判断が素早く見えるのは、才能やセンスではなく 危険察知のパターンマッチング です。

    過去に「共通化して壊れた」「分離しておいて助かった」という経験の蓄積が、コードを見た瞬間に「これは危ない」というシグナルを発します。

    原則の扱い方
    初心者原則を「ルール」として機械的に適用する
    ベテラン原則を「ヒューリスティクス（経験則）」として、状況に応じて使い分ける

    7.実践的な判断フロー

    コードの重複を見つけたら、次の2つの観点で確かめます。左は「知識として同じか」、右は「何回出てきたか」の観点です。

    同じ内容を文章にすると、次のとおりです。

    • 同じビジネスルール／知識を表しているか？
      • Yes → 一方が変わったら他方も必ず変わるか？ Yes なら 共通化する（DRY 適用）、No なら 分離しておく（SRP 優先）
      • No → 偶然の一致。共通化しない
    • 3回以上出現したか？（Rule of Three）
      • Yes → 共通化を検討する
      • No → まだ様子を見る

    8.よくある誤解

    ノートのまとめの表を、誤解と正しい理解の形で並べます。

    誤解1：「同じコードは共通化すべき（DRY）」

    DRY が避けるのは同じ 知識 の重複です。コードの見た目が同じでも、年齢と数量のように知識が違えば共通化しません。迷ったら 判断のチェックリスト の3つの質問で確かめます。

    誤解2：「YAGNI は簡単に実践できる」

    「何が不要か」の判断には、過剰な抽象化や先回りのパターン適用まで見抜く目が必要です。さらに、後から追加するための テスト・リファクタリング能力・CI/CD が前提です。これがないと、YAGNI はただの手抜きの言い訳になります。

    誤解3：「SRP は DRY と矛盾しない」

    DRY と SRP は、同じコードに対して正反対の指示を出す場面があります。変更理由が異なるなら分離を優先 し、どちらの壊れ方がより危険かで判断します。

    9.まとめ

    原則よくある誤解正しい理解
    DRY同じコードは共通化すべき同じ 知識 の重複を避ける。コードの見た目が同じでも知識が違えば共通化しない
    YAGNI簡単に実践できる「何が不要か」の判断にはテスト・リファクタリング能力が前提
    SRPDRY と矛盾しないDRY と衝突する場面がある。変更理由が異なるなら分離を優先

    設計判断の本質は「正解を選ぶ」ことではなく「どちらの壊れ方がマシか」を比較すること。
