    30 オブジェクト指向の原則

    開放閉鎖の原則（OCP）— 拡張には開き、修正には閉じる

    SOLID の 2 番目の原則 Open/Closed Principle（OCP、開放閉鎖の原則） を学びます。新しい機能を足すたびに既存コードを書き換えると何が困るのか、if-else の分岐を 抽象化とポリモーフィズム で置き換える方法を図形・割引・通知の 3 つの例で確かめ、継承・インターフェース・戦略パターンという実装の型、過度な抽象化を避ける判断基準までを扱います。

    もとにしたノート：02_OCP (開放閉鎖の原則)

    ひとことで言うと

    新しい機能は「新しいコードを足す」だけで追加でき、既存のコードは書き換えずに済む ようにする原則です。種類ごとの if-else / switch を、共通のインターフェースを持つクラス（ポリモーフィズム）に置き換えるのが典型です。ただし、変更の見込みが低い部分まで抽象化するのはやりすぎです。

    1.このページで扱うこと

    Open/Closed Principle（OCP） は、SOLID 原則 の 2 番目の原則です。

    定義

    「ソフトウェアのエンティティ（クラス、モジュール、関数など）は、拡張に対して開いており、修正に対して閉じているべき」

    つまり：

    拡張に対して開いている（Open）

    新しい機能を追加しやすい

    修正に対して閉じている（Closed）

    既存のコードを変更せずに済む

    • なぜ重要なのか（問題点とメリット）
    • 悪い例と良い例 — 図形の面積計算
    • 実践的な例 — 割引システム、通知システム
    • 実装パターン（継承・インターフェース・戦略パターン）
    • よくある間違い、判断基準、適用のヒント、チェックリスト

    クラス設計での適用は 44 の「開放閉鎖の原則」でも扱っています。

    2.なぜ重要なのか

    問題点：既存のコードを修正して新機能を追加すると

    • 既存機能への影響 — 動作していたコードが壊れる可能性
    • テストの再実行 — 既存のテストをすべて再実行する必要がある
    • リスクの増加 — 変更箇所が多いほど、バグが入り込む可能性が高い
    • 保守性の低下 — コードが複雑になり、理解が困難になる

    メリット

    • 既存コードの保護 — 動作しているコードを変更しない
    • 拡張性の向上 — 新しい機能を追加しやすい
    • テストの簡素化 — 既存のテストを変更する必要がない
    • リスクの低減 — 新機能の追加が既存機能に影響しない

    3.悪い例：if-else 文による分岐

    ✕ 悪い例：新しい図形を追加するたびに既存コードを修正 
    // ❌ 悪い例: 新しい図形を追加するたびに既存コードを修正
class AreaCalculator {
  calculateArea(shape) {
    if (shape.type === 'circle') {
      return Math.PI * shape.radius * shape.radius;
    } else if (shape.type === 'rectangle') {
      return shape.width * shape.height;
    } else if (shape.type === 'triangle') {
      return (shape.base * shape.height) / 2;
    }
    // 新しい図形を追加するたびに、このメソッドを修正する必要がある
  }
}

const calculator = new AreaCalculator();
const circle = { type: 'circle', radius: 5 };
const rectangle = { type: 'rectangle', width: 4, height: 6 };

console.log(calculator.calculateArea(circle));     // 78.54
console.log(calculator.calculateArea(rectangle));  // 24

    問題点：

    • 新しい図形（例：楕円）を追加するたびに、calculateArea メソッドを修正する必要がある
    • 既存のコードを変更するため、既存機能に影響が出る可能性がある

    4.良い例：抽象化とポリモーフィズムを活用

    抽象化 は、具体的な違いを隠して共通の約束（ここでは「calculateArea() を持つ」）だけを取り出すことです。ポリモーフィズム（多態性） は、同じメソッド呼び出しでも、相手のクラスに応じて違う処理が動く仕組みです。

    ◯ 良い例：抽象化により拡張に対して開いている 
    // ✅ 良い例: 抽象化により拡張に対して開いている

// 抽象クラス（インターフェース）
class Shape {
  calculateArea() {
    throw new Error('calculateArea must be implemented');
  }
}

// 各図形クラスがShapeを継承
class Circle extends Shape {
  constructor(radius) {
    super();
    this.radius = radius;
  }

  calculateArea() {
    return Math.PI * this.radius * this.radius;
  }
}

class Rectangle extends Shape {
  constructor(width, height) {
    super();
    this.width = width;
    this.height = height;
  }

  calculateArea() {
    return this.width * this.height;
  }
}

class Triangle extends Shape {
  constructor(base, height) {
    super();
    this.base = base;
    this.height = height;
  }

  calculateArea() {
    return (this.base * this.height) / 2;
  }
}

// AreaCalculatorは既存コードを変更せずに済む
class AreaCalculator {
  calculateArea(shape) {
    return shape.calculateArea();
  }
}

// 使用例
const calculator = new AreaCalculator();
const circle = new Circle(5);
const rectangle = new Rectangle(4, 6);
const triangle = new Triangle(3, 4);

console.log(calculator.calculateArea(circle));     // 78.54
console.log(calculator.calculateArea(rectangle));   // 24
console.log(calculator.calculateArea(triangle));    // 6

    メリット：

    • 新しい図形（例：楕円）を追加する場合、新しいクラスを作るだけで良い
    • AreaCalculator クラスは変更不要
    • 既存のコードに影響を与えない

    4.1 新しい図形を追加する例

    ◯ 新しい図形を追加（既存コードを変更せずに） 
    // 新しい図形を追加（既存コードを変更せずに）
class Ellipse extends Shape {
  constructor(radiusX, radiusY) {
    super();
    this.radiusX = radiusX;
    this.radiusY = radiusY;
  }

  calculateArea() {
    return Math.PI * this.radiusX * this.radiusY;
  }
}

// 既存のコードは一切変更不要
const ellipse = new Ellipse(5, 3);
console.log(calculator.calculateArea(ellipse));  // 47.12

    5.実践的な例

    5.1 例2：割引システム

    ✕ 悪い例：新しい割引タイプを追加するたびに修正が必要 
    // ❌ 悪い例: 新しい割引タイプを追加するたびに修正が必要
class PriceCalculator {
  calculatePrice(price, discountType) {
    if (discountType === 'student') {
      return price * 0.9;  // 10%割引
    } else if (discountType === 'senior') {
      return price * 0.85;  // 15%割引
    } else if (discountType === 'member') {
      return price * 0.95;  // 5%割引
    }
    return price;
  }
}

    戦略パターン（Strategy Pattern） は、処理のやり方（ここでは割引の計算方法）をクラスとして切り出し、差し替えられるようにするデザインパターンです。

    ◯ 良い例：戦略パターンを使用 
    // ✅ 良い例: 戦略パターンを使用
class Discount {
  apply(price) {
    throw new Error('apply must be implemented');
  }
}

class StudentDiscount extends Discount {
  apply(price) {
    return price * 0.9;  // 10%割引
  }
}

class SeniorDiscount extends Discount {
  apply(price) {
    return price * 0.85;  // 15%割引
  }
}

class MemberDiscount extends Discount {
  apply(price) {
    return price * 0.95;  // 5%割引
  }
}

class NoDiscount extends Discount {
  apply(price) {
    return price;
  }
}

class PriceCalculator {
  calculatePrice(price, discount) {
    return discount.apply(price);
  }
}

// 使用例
const calculator = new PriceCalculator();
const studentDiscount = new StudentDiscount();
const seniorDiscount = new SeniorDiscount();

console.log(calculator.calculatePrice(1000, studentDiscount));  // 900
console.log(calculator.calculatePrice(1000, seniorDiscount));    // 850

// 新しい割引タイプを追加（既存コードを変更せずに）
class VIPDiscount extends Discount {
  apply(price) {
    return price * 0.8;  // 20%割引
  }
}

const vipDiscount = new VIPDiscount();
console.log(calculator.calculatePrice(1000, vipDiscount));  // 800

    5.2 例3：通知システム

    ✕ 悪い例：通知の種類ごとに分岐 
    // ❌ 悪い例
class NotificationService {
  send(message, type) {
    if (type === 'email') {
      console.log(`Sending email: ${message}`);
    } else if (type === 'sms') {
      console.log(`Sending SMS: ${message}`);
    } else if (type === 'push') {
      console.log(`Sending push notification: ${message}`);
    }
  }
}
    ◯ 良い例：通知チャネルをクラスに分ける 
    // ✅ 良い例
class NotificationChannel {
  send(message) {
    throw new Error('send must be implemented');
  }
}

class EmailChannel extends NotificationChannel {
  send(message) {
    console.log(`Sending email: ${message}`);
    // メール送信のロジック
  }
}

class SMSChannel extends NotificationChannel {
  send(message) {
    console.log(`Sending SMS: ${message}`);
    // SMS送信のロジック
  }
}

class PushChannel extends NotificationChannel {
  send(message) {
    console.log(`Sending push notification: ${message}`);
    // プッシュ通知のロジック
  }
}

class NotificationService {
  send(message, channel) {
    channel.send(message);
  }
}

// 使用例
const service = new NotificationService();
const emailChannel = new EmailChannel();
const smsChannel = new SMSChannel();

service.send('Hello', emailChannel);
service.send('Hello', smsChannel);

// 新しい通知チャネルを追加（既存コードを変更せずに）
class SlackChannel extends NotificationChannel {
  send(message) {
    console.log(`Sending Slack message: ${message}`);
    // Slack送信のロジック
  }
}

const slackChannel = new SlackChannel();
service.send('Hello', slackChannel);

    6.実装パターン

    6.1 継承（Inheritance）

    // 基底クラスを継承して拡張
class Animal {
  makeSound() {
    throw new Error('makeSound must be implemented');
  }
}

class Dog extends Animal {
  makeSound() {
    return 'Woof!';
  }
}

class Cat extends Animal {
  makeSound() {
    return 'Meow!';
  }
}

    6.2 インターフェース（Interface）

    // TypeScriptの例
interface PaymentMethod {
  pay(amount: number): void;
}

class CreditCard implements PaymentMethod {
  pay(amount: number) {
    console.log(`Paying ${amount} with credit card`);
  }
}

class PayPal implements PaymentMethod {
  pay(amount: number) {
    console.log(`Paying ${amount} with PayPal`);
  }
}

    6.3 戦略パターン（Strategy Pattern）

    // アルゴリズムを交換可能にする
class SortStrategy {
  sort(data) {
    throw new Error('sort must be implemented');
  }
}

class QuickSort extends SortStrategy {
  sort(data) {
    // クイックソートの実装
    return data.sort((a, b) => a - b);
  }
}

class MergeSort extends SortStrategy {
  sort(data) {
    // マージソートの実装
    return this.mergeSort(data);
  }

  mergeSort(arr) {
    // マージソートのロジック
    return arr;
  }
}

    （QuickSort・MergeSort の中身は形だけの例です。ポイントは、使う側が SortStrategy の sort() だけを知っていれば、並べ替えの方法を差し替えられることです。）

    継承とインターフェースの違い、継承より合成を選ぶ考え方は 44 の「インターフェースと抽象化」「継承より合成」、戦略パターンは「振る舞いパターン」で扱っています。

    7.よくある間違い

    7.1 過度な抽象化

    ✕ やりすぎ：まだ必要のない抽象化 
    // ❌ やりすぎ: まだ必要のない抽象化
class Shape {
  calculateArea() { }
  calculatePerimeter() { }
  draw() { }
  // ... まだ使わないメソッド
}

    適切なタイミング：

    • 実際に拡張が必要になったときに抽象化する
    • YAGNI 原則（You Aren't Gonna Need It＝必要になるまで作らない）を考慮（→ DRY・KISS・YAGNI）

    7.2 すべてを拡張可能にする

    ✕ すべてを拡張可能にする必要はない 
    // ❌ すべてを拡張可能にする必要はない
class User {
  // このクラスは拡張する必要がないかもしれない
}

    判断基準：

    • 将来変更される可能性が高い部分だけを拡張可能にする
    • 安定している部分はシンプルに保つ

    8.判断基準

    OCP を適用すべきか判断する質問です。

    質問OCP を適用シンプルに保つ
    1. 将来変更される可能性は高いか？高い低い
    2. 変更の頻度は？頻繁に変更されるほとんど変更されない
    3. 複数のバリエーションが必要か？必要不要

    9.適用のヒント

    9.1 if-else 文や switch 文に注意

    // if-else文が多い場合、OCP違反の可能性
if (type === 'A') { }
else if (type === 'B') { }
else if (type === 'C') { }

    → ポリモーフィズムで置き換えることを検討します。分岐の整理全般は 42 の「場合分けのロジックを整理する」も参照してください。

    9.2 変更される部分を特定

    • 変更されやすい部分 → 抽象化して拡張可能にする
    • 変更されにくい部分 → シンプルに保つ

    9.3 段階的な抽象化

    最初はシンプルに始め、必要になったときに抽象化します。

    // 最初: シンプル
class Calculator {
  add(a, b) { return a + b; }
}

// 必要になったら抽象化
class Operation {
  execute(a, b) { }
}

class AddOperation extends Operation {
  execute(a, b) { return a + b; }
}

    10.関連原則

    原則・パターン関係
    Single Responsibility Principle（単一責任の原則）責任が明確でないと、OCP も守りにくい
    Liskov Substitution Principle（リスコフの置換原則）OCP を実現するための前提条件
    Strategy Pattern（戦略パターン）OCP を実現するためのデザインパターン

    11.よくある誤解

    誤解1：「最初からすべてを拡張可能に作っておくべき」

    まだ使わないメソッドを並べた抽象クラスや、拡張の予定がないクラスの抽象化は 過度な抽象化 です。最初はシンプルに始め、実際に拡張が必要になったとき に抽象化します（YAGNI）。

    誤解2：「OCP を守れば既存コードは一切変更しなくてよい」

    OCP が守るのは、変更されやすい部分 を抽象化して差し替え可能にした箇所です。どこを抽象化するかは「将来変更される可能性」「変更の頻度」「バリエーションの必要性」で判断するもので、安定している部分はシンプルに保ちます。

    誤解3：「if-else があること自体が OCP 違反」

    種類ごとの if-else が 多い 場合は OCP 違反の 可能性 があり、ポリモーフィズムへの置き換えを 検討 する合図です。種類が増える見込みのない分岐まで、すべてクラスに置き換える必要はありません。

    12.まとめ

    12.1 重要なポイント

    1. 拡張に対して開いている — 新しい機能を追加しやすい
    2. 修正に対して閉じている — 既存コードを変更しない
    3. 抽象化を活用 — 継承、インターフェース、ポリモーフィズム
    4. 適切なタイミングで適用 — 過度な抽象化は避ける

    12.2 チェックリスト

    • ☐ 新しい機能を追加するときに既存コードを変更しているか？
    • ☐ if-else 文や switch 文が多すぎないか？
    • ☐ 抽象化により拡張可能になっているか？
    • ☐ 過度な抽象化になっていないか？
