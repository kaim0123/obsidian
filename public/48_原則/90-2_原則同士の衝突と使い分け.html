    90 付録

    原則同士の衝突と使い分け — ぶつかったときの判断基準

    原則を覚えると、今度は 「DRY に従うと SRP に反する」「YAGNI に従うと OCP に反する」 といった場面に出会います。原則はどれも「ある問題を防ぐための指針」なので、防ぎたい問題が違えばぶつかる のは自然なことです。このページでは、よくある衝突を一覧にし、どちらを優先するかの判断基準 をまとめます。

    もとにしたノート：02_原則同士の衝突と使い分け

    ひとことで言うと

    「原則は目的のための道具。迷ったら "今いちばん困っている変更はどれか" で選ぶ」。

    1.このページで扱うこと

    • よくある衝突 10 組の一覧と判断基準
    • 詳しい判断 — DRY vs SRP、YAGNI vs OCP、デメテル vs 凝集、DRY vs 疎結合
    • 判断に迷ったときの順番
    • よくある誤解

    各原則の意味は「原則の用語集」から引けます。

    2.衝突の一覧

    衝突片方に従うと…もう片方に従うと…判断の基準
    DRY vs SRP共通化した関数が複数の目的に使われ、変更理由が増える似たコードが 2 か所に残る変更理由が同じか。同じなら DRY、違うなら重複を許す
    YAGNI vs OCP拡張ポイントがなく、後で修正が入る使われない抽象やインターフェースが増える実際に 2 つ目の変化が来たか。来てから OCP にする
    KISS vs 拡張性単純だが、要件追加で書き直しになる柔軟だが、読むのが大変変化の予定が確定しているか。不確かなら KISS
    デメテル vs 凝集委譲メソッドが増え、クラスが太る呼び出し側が内部構造を知る相手が振る舞いを持つオブジェクトか、データの入れ物か
    DRY vs 疎結合共通モジュールに多くのサービスが依存する各サービスに同じ処理がコピーされる境界をまたぐか。同じモジュール内は DRY、サービス間は重複を許す
    SRP vs KISSクラスが細かく分かれ、追いかけるファイルが増える1 つのクラスが大きくなる分けたクラスを単独で説明できるか。説明できない分割はしない
    情報隠蔽 vs テストしやすさ内部が見えず、テストで確認しにくいテストのために内部を公開してしまう公開された振る舞いでテストする。内部を見たくなったら分割のサイン
    継承より合成 vs KISS部品が増え、組み立てが見えにくい継承で素直に書けるが、後で階層が崩れる組み合わせのバリエーションがあるか。1 通りなら継承でもよい
    ポステルの法則 vs 驚き最小何でも受け付けるので、壊れた入力が通る厳しくはじくので、相手に不便境界の外か中か。外部入力は寛容に受けて正規化、内部は厳密に
    IoC/DI vs 読みやすさ処理の流れがコードから追えない依存が直書きで差し替えられない差し替える必要（テスト・環境）があるか

    3.各衝突の詳しい判断

    3.1 DRY vs SRP —「同じに見えるだけ」の重複

    ✕ 一見同じだから共通化したくなる 
    function validateUserName(name)    { return name.length > 0 && name.length <= 20; }
function validateProductName(name) { return name.length > 0 && name.length <= 20; }

    ユーザー名と商品名の上限は たまたま同じ だけで、変わる理由は別々です。1 つにまとめると、商品名だけ 50 文字にしたいときに if (type === 'product') が入り込みます。

    • 知識が同じ（税率・会員ランクの定義など）→ DRY でまとめる
    • 見た目が同じだけ（変わる理由が別）→ 重複を許す
    • 迷ったら 3 回目が出るまで待つ（Rule of Three）

    詳しくは「DRY・YAGNI の落とし穴と実践的判断」。

    3.2 YAGNI vs OCP — 拡張ポイントはいつ作るか

    支払い方法がクレカしかない段階 
    function pay(amount) { return creditCard.charge(amount); }

    この段階で PaymentStrategy インターフェースを作るのは YAGNI 違反になりがちです。銀行振込が実際に来た時点 でインターフェースを切り出せば、OCP に必要な「変化の軸」が正しく分かります。

    • 変化の軸が 未確定 → YAGNI を優先し、単純に書く
    • 変化の軸が 1 度でも現れた → OCP で拡張ポイントを作る
    • ただし 外部公開 API・ライブラリ は後から変えにくいので、OCP を早めに考える

    3.3 デメテル vs 凝集 — 委譲メソッドが増えすぎる

    デメテルの法則 を厳密に守ると、order.getShippingZipCode()、order.getShippingCity()、… と 中継ぎのメソッドが Order に大量に生える ことがあります。これは Order の凝集を下げます。

    • 相手が 振る舞いを持つオブジェクト → デメテルを守り「頼む」形に
    • 相手が DTO・設定値などデータの入れ物 → たどってよい
    • 中継ぎが増えすぎたら、本当に頼みたい処理（例：order.shipTo(courier)） をまとめて 1 つにする

    3.4 DRY vs 疎結合 — マイクロサービス間の共通ライブラリ

    複数サービスで「共通ドメインライブラリ」を共有すると、そのライブラリを変えるたびに 全サービスを同時にリリース する必要が生まれます。これは DRY のために疎結合を失った状態です。

    • 同じデプロイ単位の中 → DRY
    • 独立してリリースしたい境界をまたぐ → 重複を許す（ログ出力などの技術的な共通部品は例外的に共有してもよい）

    4.判断に迷ったときの順番

    1. 今、実際に困っている変更は何か を書き出す（想像上の変更は数えない）
    2. その変更を いちばん小さくする 原則を選ぶ
    3. 決めきれなければ KISS（単純なほうは後から変えやすい）
    4. 判断した理由をコメントや ADR（Architecture Decision Record：設計判断の記録）に残す（次に読む人のため）

    5.よくある誤解

    誤解1：「原則に例外はない」

    原則は経験則の圧縮です。前提（変更の頻度・チームの規模）が違えば結論も変わります。

    誤解2：「たくさんの原則を満たすほど良い設計」

    原則を満たすための抽象が、それ自体で複雑さになることがあります。

    誤解3：「衝突したら上位の原則が勝つ」

    原則に固定の優先順位はありません。毎回「何を防ぎたいか」で決めます。

    6.まとめ

    • 原則の衝突は、防ぎたい問題が違う から起きる
    • DRY は「知識」の重複に、YAGNI/OCP は「変化が来たか」に、デメテルは「相手が振る舞いを持つか」に注目する
    • 境界（モジュール・サービス・公開 API）をまたぐかどうかで判断が変わることが多い
    • 迷ったら KISS、そして判断理由を残す
