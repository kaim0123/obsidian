    20 構造の原則

    デメテルの法則 — 知り合いの知り合いと話さない

    user.company.address.city.name のようにオブジェクトをたどってたどって値を取り出すコードは、一見自然でも、後々バグや変更コストを生む原因になります。このページでは、それを防ぐ デメテルの法則（Law of Demeter, LoD） の正式なルール、悪い例と「頼む」形への書き換え、「ドットの数」という目安とその例外、守る理由、実務でよくある違反パターンまでを学びます。

    もとにしたノート：02_デメテルの法則

    ひとことで言うと

    「知り合いの知り合いと話してはいけない」。あるオブジェクトは、自分がすぐ知っている相手（自分・引数・フィールド・自分で作ったもの）とだけ話し、その相手の内部構造までたどって触らない という原則です。深いメソッドチェーンは、相手に 「してほしいこと」を頼む 形に書き直します。

    1.このページで扱うこと

    プログラムを書いていると、user.company.address.city.name のように オブジェクトをたどってたどってたどって 値を取り出すコードを見ることがあります。一見自然に見えますが、実は 後々バグや変更コストを生む原因 になります。これを防ぐのが デメテルの法則（Law of Demeter, LoD） です。別名 「最小知識の原則（Principle of Least Knowledge）」 とも呼ばれます。

    • 一言でいうと — 知り合いの知り合いと話さない
    • 正式なルール（呼んでよい 4 種類の相手）
    • 悪い例（メソッドチェーンでたどる）と良い例（「頼む」形）
    • 見分け方 — 「ドットの数」ルールとその限界
    • なぜ守るのか
    • 実務でよくある違反パターンと、守らなくてよい例外

    クラス設計での「頼む」形（Tell, Don't Ask）は 44 の「Tell, Don't Ask と貧血モデル」でも扱っています。

    2.一言でいうと

    知り合いの知り合いと話してはいけない

    あるオブジェクトは、自分がすぐ知っている相手（直接のフィールドや引数）だけと話すべきで、その相手の内部構造までたどって触ってはいけない という原則です。

    3.正式なルール

    あるメソッドの中から呼んでよいのは、次のものだけです。

    1. 自分自身 のメソッド
    2. 引数として渡された オブジェクトのメソッド
    3. 自分のフィールド（プロパティ） のメソッド
    4. 自分の中で作った オブジェクトのメソッド

    これ以外、つまり 「呼び出した結果、返ってきたオブジェクト」のメソッドをさらに呼ぶのは NG というルールです。

    4.悪い例：メソッドチェーンでたどる

    ✕ 悪い例：新聞配達員がお客さんの財布に直接手を突っ込む 
    class Wallet {
  constructor(money) { this.money = money; }
  getMoney() { return this.money; }
  setMoney(m) { this.money = m; }
}

class Customer {
  constructor(name, wallet) {
    this.name = name;
    this.wallet = wallet;
  }
  getWallet() { return this.wallet; }
}

class PaperBoy {
  // 新聞配達員が、お客さんの財布に直接手を突っ込んでお金を取る
  charge(customer, price) {
    const wallet = customer.getWallet();
    const money = wallet.getMoney();
    if (money >= price) {
      wallet.setMoney(money - price);
    }
  }
}

    customer.getWallet().setMoney(...) のように、Customer の内部にある Wallet の内部構造 まで PaperBoy が知ってしまっています（上のコードでは変数に分けていますが、やっていることは同じです）。

    4.1 何が問題か

    • Customer の中身が変わると PaperBoy まで壊れる（例：Wallet を廃止してクレカに変更）
    • カプセル化が崩れる（Wallet を外から自由にいじれてしまう）。カプセル化 とは、データとそれを扱う処理をまとめ、内部を外から直接触らせないことです
    • 現実世界でも変（配達員が勝手に財布から金を抜いてよいわけがない）

    5.良い例：「頼む」形に変える

    ◯ 良い例：PaperBoy は Customer に「支払って」と頼むだけ 
    class Customer {
  constructor(name, wallet) {
    this.name = name;
    this.wallet = wallet;
  }
  // 支払いは Customer に「頼む」
  pay(price) {
    return this.wallet.withdraw(price);
  }
}

class Wallet {
  constructor(money) { this.money = money; }
  withdraw(amount) {
    if (this.money < amount) throw new Error('残高不足');
    this.money -= amount;
    return amount;
  }
}

class PaperBoy {
  charge(customer, price) {
    customer.pay(price); // Customer に支払いを頼むだけ
  }
}

    PaperBoy は Customer に「支払って」と頼む だけ。Wallet の存在も構造も知りません。Customer がクレカに変わっても PaperBoy は影響を受けません。

    6.見分け方：「ドットの数」ルール

    6.1 よく言われる目安

    目安

    「メソッド呼び出しのドット（.）は 1 つまで」

    a.b()       // OK
a.b().c()   // 怪しい（デメテル違反の可能性）
a.b().c().d() // ほぼアウト

    ただし、厳密に 1 つまで守れ という意味ではありません。以下は違反ではない例です。

    ◯ 違反ではない例 
    // メソッドチェーンでも、同じオブジェクトを返し続けているだけならOK
builder.setName('a').setAge(20).setEmail('x@x').build();

// 自分自身のメソッドや、引数のメソッドを呼ぶのもOK
this.repository.save(user);

    「他人のオブジェクトの内部をたどっているか」 が判断の基準です。

    7.なぜ守るのか

    1. 変更に強くなる

    user.company.address.city.name のようなチェーンは、途中のどこが変わっても壊れます。法則を守っておけば、内部構造の変更が外に漏れません。

    2. カプセル化が守られる

    「持っているデータ」ではなく「してほしいこと」を頼む設計になるので、オブジェクト指向本来の強さが出ます。

    3. テストが書きやすくなる

    モック（テスト用の偽物のオブジェクト）が減ります。user.company.address.city.name をテストするには company, address, city すべてを用意する必要がありますが、user.getCityName() なら user 1 つで済みます。

    8.実務でよくある違反パターン

    8.1 パターン1：Getter の連鎖

    ✕ Getter をたどって値を取り出す 
    order.getCustomer().getAddress().getZipCode()

    → order.getShippingZipCode() のように、Order に代わりに聞く。

    8.2 パターン2：DTO（データ転送オブジェクト）へのアクセス

    config.database.connection.pool.max

    DTO（Data Transfer Object）は、処理を持たずにデータを運ぶだけの入れ物です。

    → 深いアクセスは 設定オブジェクトに getMaxPoolSize() のような薄いメソッドを持たせる か、ここは DTO なので例外扱いとして許容する、など判断が必要です。

    8.3 パターン3：フレームワーク／ライブラリ

    $('.btn').on('click', fn) // jQuery

    これは Fluent API（メソッドをつなげて文章のように書けるように設計された API）と呼ばれる意図的な設計で、同じオブジェクトを返し続けているだけなので違反ではありません。

    9.例外：いつ守らなくてよいか

    例外例
    DTO や設定オブジェクト など、単なる「データの入れ物」へのアクセスconfig.database.connection.pool.max
    ビルダーパターン のような、自身を返すメソッドチェーンbuilder.setName('a').setAge(20).build()
    標準ライブラリlist.stream().filter(...).map(...).collect(...)

    デメテルの法則は 「振る舞いを持つオブジェクトの内部をたどってはいけない」 という趣旨なので、振る舞いを持たないデータだけの構造には厳しく適用しなくて OK です。

    10.よくある誤解

    誤解1：「ドットが 2 つ以上あれば必ず違反」

    「ドットは 1 つまで」は 目安 にすぎません。ビルダーや jQuery のように 同じオブジェクトを返し続ける チェーンや、this.repository.save(user) のように自分のフィールドを呼ぶのは違反ではありません。基準は 他人のオブジェクトの内部をたどっているかどうか です。

    誤解2：「チェーンを変数に分ければ違反ではなくなる」

    悪い例の PaperBoy は const wallet = customer.getWallet(); と変数に分けていますが、返ってきたオブジェクトのメソッドをさらに呼んでいる ことに変わりはありません。書き方ではなく、誰の内部構造を知っているか が問題です。

    誤解3：「どんなデータ構造にも厳密に適用すべき」

    DTO や設定オブジェクトのような 振る舞いを持たないデータの入れ物 には、厳しく適用しなくて構いません。すべてに薄いメソッドを足すと、かえってコードが増えるだけになることもあります。

    11.まとめ

    • 知り合いの知り合いとは話さない
    • 自分が 直接触れる相手 にだけ話しかける
    • 深いメソッドチェーンは 「頼む」形 に書き直す
    • データの入れ物（DTO）や Fluent API では例外的に許容される
