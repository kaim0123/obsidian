    設計原則の変遷 — KISS から SOLID まで、何を解決してきたか

    ソフトウェア設計の原則は、過去の現場で繰り返し起きた失敗 を教訓に、時代とともに積み重ねられてきました。このページでは代表的な6つ（KISS・高凝集/低結合・関心の分離・YAGNI・DRY・SOLID）を 提唱・体系化された西暦順 に並べ、それぞれ 何が課題だったのか と どう解決しようとしたのか を整理します。

    もとにしたノート：00_設計原則の変遷

    ひとことで言うと

    原則は「その時代の困りごと」への答えとして生まれました。KISS（1960年頃） は複雑さそのものを疑い、高凝集・低結合 と 関心の分離（1974年） は分け方の物差しと考え方を与え、YAGNI（1996年頃） は先回り実装を止め、DRY（1999年） は知識の重複をなくし、SOLID（2000年） はそれらをクラス設計の言葉にしました。原則同士は置き換え関係ではなく、効くレイヤーが違う ものです。

    1.このページで扱うこと

    このページは48章の 年表 です。各原則の詳しい定義や誤解は、それぞれのページで扱います。ここでは「なぜその原則が必要になったのか」に注目します。

    • 6つの原則の年表（提唱・体系化の時期と主な提唱者）
    • 各原則の 背景となった課題・何を解決しようとしたか・解決の考え方
    • 原則同士の関係（時代の流れ、効くレイヤー、向いている方向）

    48章全体の地図は 原則の全体像 を見てください。

    3.KISS（1960年頃）

    Keep It Simple, Stupid — 「シンプルに保て」。米国の航空機メーカー Lockheed の開発部門（Skunk Works）の技術者 Kelly Johnson の言葉とされます。

    3.1 背景となった課題

    • 高度な技術ほど複雑になりがちで、現場で修理・運用できない 設計が増えていた
    • 複雑さはバグ・故障・コスト増の温床になる
    • ソフトウェアでも、1960〜70年代に 複雑さがプロジェクト失敗の主因 だと認識され始めた

    3.2 何を解決しようとしたか

    「動くが複雑すぎて使えない・直せない」 という問題に対し、設計段階から 不要な複雑さを排除する ことを目標にしました。

    • 平均的な技術者が、限られた道具で 現場で修理できる レベルまで単純化する（航空機設計の文脈）
    • ソフトウェアでは、読みやすさ・保守性・信頼性 を優先し、賢さより分かりやすさを選ぶ

    3.3 解決の考え方

    • 必要以上の抽象化・最適化・機能追加を避ける
    • 1つの関数・モジュールは 1つのこと だけを行う
    • 将来の拡張を理由にした 今の複雑化 を疑う

    → 詳細：DRY・KISS・YAGNI の「KISS 原則」

    4.高凝集・低結合（1960年代中盤〜1974年）

    High Cohesion / Low Coupling — モジュール内はまとまりよく、モジュール間はゆるやかにつなぐ。モジュール は、プログラムを分けたときの1つのまとまり（関数・クラス・ファイル・パッケージなど）のことです。

    4.1 背景となった課題

    • ソフトウェア規模が拡大し、スパゲッティコード（goto 多用・全体が絡み合った構造）が保守不能に
    • 1か所を直すと どこまで影響するか分からない 変更が日常化
    • 「良いプログラム」と「壊れやすいプログラム」の違いを 客観的に語る尺度 がなかった

    4.2 何を解決しようとしたか

    「変更しやすいモジュール分割の基準は何か」 という問題に対し、2つの尺度を提示しました。

    尺度悪い状態良い状態
    凝集度関係のない処理が1モジュールに混在（低凝集）同じ目的の処理だけが集まる（高凝集）
    結合度モジュール同士が内部まで知り合い（密結合）必要最小限のインターフェースだけで接続（疎結合）

    4.3 解決の考え方

    • 高凝集：変更の理由が同じものは1モジュールにまとめ、影響を局所化する
    • 低結合：モジュール間は抽象（インターフェース）越しに接続し、差し替え・テスト・再利用を容易にする
    • 1968年に初出、1974年の Structured Design（Stevens, Myers, Constantine）で広く知られるようになった

    → 詳細：41 の モジュール性と疎結合・高凝集。分類の詳細は 43 の 凝集度・結合度、設計の基本としては 42 の 凝集度と結合度

    5.関心の分離 SoC（1974年）

    Separation of Concerns — 異なる関心（目的・責任）は別の場所に分ける。

    5.1 背景となった課題

    • プログラムの 正しさ・効率・望ましさ など、評価軸が異なる性質を 同時に扱おうとすると思考が混乱 する
    • 1つの関数・モジュールに 表示・検証・永続化・通知 など目的の異なる処理が混在する（永続化は、データベースなどにデータを保存すること）
    • 構造化プログラミング（goto を使わず、順次・分岐・繰り返しの組み合わせで書く方法）以降、複雑さをどう整理して考えるか の方法論が求められていた

    5.2 何を解決しようとしたか

    「複数の観点を一度に扱うと、どれも中途半端になる」 という認知的な問題に対し、1つの観点に集中して考える 技法を提唱しました。

    • 正しさだけを見る日、効率だけを見る日、と 関心ごとに分けて検討 する
    • 設計では、異なる目的・責任を別モジュール・別レイヤーに分離 する（後世のソフトウェア設計への展開）

    5.3 解決の考え方

    • 「ユーザー登録」という流れの中でも、表示・検証・保存・通知 は別の関心として切り出す
    • 1か所の変更が他の関心に波及しないよう、境界 を設ける
    • 高凝集・低結合と組み合わさり、レイヤードアーキテクチャや MVC の根底にある（レイヤードアーキテクチャは表示・業務ロジック・データアクセスなどを層に分ける構成、MVC は Model・View・Controller に分ける構成）

    → 詳細：関心の分離（設計の基礎としては 42 の 関心の分離）

    6.YAGNI（1996年頃）

    You Aren't Gonna Need It — 今いらない機能は作らない。

    6.1 背景となった課題

    • 1990年代、綿密な事前設計 が主流で、「将来の拡張性」の名のもと 使われない機能を先回り実装 する傾向が強かった
    • 作った機能の多くは 実際には使われず、テスト・保守コストだけが残る
    • 要件は開発中に変わるため、先回りした設計が すぐ陳腐化 する

    6.2 何を解決しようとしたか

    「将来必要になるかもしれない」という理由での過剰実装 を止め、今の問題だけを今解く ことを促しました。

    • Chrysler C3 給与プロジェクト（1996年〜）で Kent Beck が Chet Hendrickson の先回り提案に繰り返し使ったフレーズが起源
    • エクストリーム・プログラミング（XP）（短い周期で動くものを作り、テストとリファクタリングを重ねるアジャイル開発の手法）の Simple Design（単純な設計） の中核

    6.3 解決の考え方

    • 今のテストを通す最小の実装に集中する
    • 「いつか必要になる」機能は、本当に必要になったとき に追加する
    • ただし 変更しやすい構造 を作ることと、未使用機能を作ること は別（構造の柔軟性は残す）

    → 詳細：DRY・KISS・YAGNI の「YAGNI 原則」、DRY・YAGNI の落とし穴と実践的判断

    7.DRY（1999年）

    Don't Repeat Yourself — 同じ知識を二重に持たない。

    7.1 背景となった課題

    • 同じロジック・仕様・知識が コード・コメント・DB スキーマ・テスト・ドキュメント など複数箇所に散在する（DB スキーマは、データベースの表や列の定義）
    • 1か所だけ直して 他を直し忘れる と、システム内で矛盾が生じる（「いつ忘れるか」の問題）
    • 「コピペを避ける」だけでは、見た目は違うが意味は同じ 重複を見逃す

    7.2 何を解決しようとしたか

    「知識の重複」 そのものを排除し、変更は1か所で済む 状態を目指しました。

    • Andy Hunt と Dave Thomas が『達人プログラマー』（1999年）で体系化
    • コピペ防止にとどまらず、意図・仕様・データ定義 の単一の正（Single Source of Truth）を保つ

    7.3 解決の考え方

    • 「この仕様が変わったら、何か所直す必要があるか？」が acid test（それで本物かどうかが分かる決め手の試験）
    • 定数化・関数化・コード生成・自動テスト生成など、表現形式が違っても知識は1つ にまとめる
    • ただし たまたま似ているだけ のコードを無理に統合すると、かえって複雑になる（DRY の誤用に注意）

    → 詳細：DRY・KISS・YAGNI の「DRY 原則」、コードの重複と DRY 原則違反

    8.SOLID（2000年）

    Single Responsibility ／ Open-Closed ／ Liskov Substitution ／ Interface Segregation ／ Dependency Inversion の頭文字です。

    8.1 背景となった課題

    • オブジェクト指向（OO）普及後、継承の乱用・巨大クラス・具体クラスへの直接依存 により、ソフトウェアが 変更に弱く腐敗（software rot） していく
    • モジュール分割の原則（SoC、高凝集・低結合）はあるが、クラス設計レベルでどう実践するか の指針が不足していた
    • 小さな変更が 連鎖的に広がる 依存関係の設計が問題だった

    8.2 何を解決しようとしたか

    「変更に強い OO 設計」 のための5原則を1つの枠組みにまとめました。

    原則解決する課題解決の方向
    SRP1クラスに複数の変更理由が混在1クラス1責任に分割
    OCP機能追加のたびに既存コードを書き換える拡張で対応し、修正は閉じる
    LSPサブタイプが親の契約を破る置換可能な継承関係を保つ
    ISP使わないメソッドへの依存を強いられる小さく分割したインターフェース
    DIP上位が下位の具体実装に依存抽象に依存し、具体は注入する
    • Robert C. Martin が 2000年の論文 Design Principles and Design Patterns で整理
    • 略語 SOLID は Michael Feathers が 2004年頃に提案（個々の原則はそれ以前から存在）

    8.3 解決の考え方

    • クラス単位で 関心の分離（SRP） と 依存の向きの制御（DIP） を実践する
    • 高凝集・低結合を OO の文法（クラス・インターフェース・継承） で具体化したもの
    • デザインパターンやクリーンアーキテクチャの土台になる

    → 詳細：SRP（単一責任の原則）、OCP（開放閉鎖の原則）、LSP（リスコフの置換原則）、ISP（インターフェース分離の原則）、DIP（依存性逆転の原則）（入口は SOLID の全体像）

    9.原則の関係 — 時代の流れとレイヤー

    年表の図のとおり、原則は「複雑さを疑う → 分け方の物差し → 考え方の整理 → 作りすぎの抑制 → 知識の重複の排除 → OO 設計への具体化」と積み重なってきました。ただし、原則同士は 置き換え関係ではなく、効くレイヤーが違う ことが多いです。

    レベル主な原則
    思想・全般KISS
    アーキテクチャ・モジュールSoC、高凝集・低結合
    クラス設計（OO）SOLID
    実装・日々の判断DRY、KISS、YAGNI

    向いている方向でも分けられます。

    作らない・複雑にしない

    KISS と YAGNI

    整理して変更しやすくする

    DRY と SoC と SOLID

    良し悪しを測る物差し

    高凝集・低結合（「整理して変更しやすくする」方向の評価に使う）

    10.よくある誤解

    誤解1：「新しい原則は古い原則を置き換えたもの」

    SOLID は KISS や高凝集・低結合を時代遅れにしたわけではありません。SOLID は 高凝集・低結合をオブジェクト指向の文法で具体化 したもので、KISS は今も思想・全般のレベルで、DRY・YAGNI は日々の実装判断のレベルで効いています。原則同士は 効くレイヤーが違う と考えます。

    誤解2：「YAGNI は変更しやすい構造も作らなくてよい、という意味」

    YAGNI が止めるのは 未使用の機能を先回りで作ること です。変更しやすい構造 を作ることとは別で、構造の柔軟性は残します。詳しくは DRY・YAGNI の落とし穴と実践的判断。

    誤解3：「DRY はコピペを禁止する原則」

    DRY が排除したいのは 知識の重複 です。コピペ防止にとどまらず、コード・コメント・DB スキーマ・ドキュメントなど 表現形式が違っても同じ知識 なら1つにまとめます。逆に、たまたま似ているだけ のコードを無理に統合するのは誤用です。

    11.まとめ

    • KISS（1960年頃）：「動くが複雑すぎて直せない」に対し、不要な複雑さを設計段階から排除する
    • 高凝集・低結合（1960年代中盤〜1974年）：変更しやすいモジュール分割を語る 客観的な尺度 を与えた
    • SoC（1974年）：複数の観点を一度に扱わず、1つの関心に集中 して考え、設計でも分ける
    • YAGNI（1996年頃）：「将来必要かも」の過剰実装を止め、今の問題だけを今解く
    • DRY（1999年）：知識の重複 を排除し、変更を1か所で済ませる
    • SOLID（2000年）：変更に強い OO 設計の5原則。高凝集・低結合をクラス設計の言葉にしたもの
    • KISS・YAGNI は「作らない・複雑にしない」方向、DRY・SoC・SOLID は「整理して変更しやすくする」方向、高凝集・低結合はその 物差し

    関連：アーキテクチャに効く原則は 41 の トレードオフと原則、オブジェクト指向と SOLID の関係は 42 の SOLID とオブジェクト指向 で扱っています。
