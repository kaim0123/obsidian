    30 オブジェクト指向の原則

    継承より合成 — 親子関係より「部品として持つ」

    オブジェクト指向を学ぶと、最初に「継承」で共通部分をまとめる方法を教わります。便利なので、つい なんでも継承でつなげたくなります が、階層が深くなるほど、親クラスを 1 か所直しただけで子クラスがあちこちで壊れる…ということが起きます。このページでは、それに対する定番の指針 継承より合成（Composition over Inheritance） の出典、継承の何が困るのか、部品を持たせる書き方、そして継承を使ってよい場面までを学びます。

    もとにしたノート：01_継承より合成

    ひとことで言うと

    「機能を借りたいなら、親子関係ではなく "部品として持つ" ほうを先に考える」。継承（is-a：〜の一種である）ではなく、合成（has-a：〜を持っている）で機能を組み立てるほうが、たいていの場合は変更に強くなる、という原則です。

    1.このページで扱うこと

    • 一言でいうと — is-a より has-a
    • 定義・背景 — GoF（1994）の言葉と「ホワイトボックス再利用／ブラックボックス再利用」
    • 継承の何が困るのか（4 つの問題）
    • 悪い例（継承で組み合わせを表現する）と良い例（振る舞いを部品として持たせる）
    • よくある誤解 — 継承を使ってよい場面

    クラス設計での使い方は 44 の「継承より合成」、パラダイムとしての整理は 42 の「継承と合成」で扱っています。このページは 原則そのもの（出典・理由・誤解）に絞ります。

    2.一言でいうと

    機能を借りたいなら、まず「部品として持つ」

    継承（is-a：〜の一種である）ではなく、合成（has-a：〜を持っている）で機能を組み立てるほうが、たいていの場合は変更に強くなります。

    3.定義・背景

    • 出典は 1994 年の GoF 本（Gamma, Helm, Johnson, Vlissides『オブジェクト指向における再利用のためのデザインパターン』。4 人の著者を Gang of Four＝GoF と呼びます）
    • 原文は "Favor object composition over class inheritance."（クラス継承よりオブジェクト合成を好め）
    • 同じ本の "Program to an interface, not an implementation."（実装ではなくインターフェースに対してプログラムせよ）と対になる考え方

    継承 ＝ ホワイトボックス再利用

    親の中身が子から見える。子は親の 実装の詳細 に依存するため、GoF は 「継承はカプセル化を破る」 とも述べています。

    合成 ＝ ブラックボックス再利用

    部品の中身は見えず、インターフェース越しに使う。部品の内部が変わっても、約束（インターフェース）が同じなら使う側は影響を受けません。

    3.1 継承の何が困るのか

    問題内容
    壊れやすい基底クラス親クラスの変更が、知らないうちに子クラスの動きを変えてしまう
    組み合わせ爆発「飛ぶ」「泳ぐ」「鳴く」の組み合わせごとにサブクラスが必要になる
    実行時に変えられない継承関係はコードを書いた時点で固定される
    不要な機能まで受け継ぐ使わないメソッドまで子に付いてくる

    4.悪い例：継承で組み合わせを表現する

    ✕ 悪い例：飛べないペンギンが fly() を持ってしまう 
    class Bird {
  fly() { console.log('空を飛ぶ'); }
  sing() { console.log('鳴く'); }
}

class Penguin extends Bird {
  // ペンギンは飛べない…けれど Bird を継承したので fly() を持ってしまう
  fly() { throw new Error('ペンギンは飛べません'); }
}

class RobotBird extends Bird {
  // ロボットの鳥は鳴かないが飛ぶ。さらに「充電する」も欲しい…
  sing() { throw new Error('鳴けません'); }
  charge() { console.log('充電する'); }
}
    • Penguin は 親の約束（fly できる）を破っている（リスコフの置換原則（LSP） 違反）
    • 「泳げる鳥」「鳴くロボット」などが増えるたびに、クラス階層がどんどん複雑になる

    5.良い例：振る舞いを部品として持たせる

    ◯ 良い例：動き方・鳴き方を部品にして組み合わせる 
    // 振る舞いを小さな部品にする
const canFly  = { move: () => console.log('空を飛ぶ') };
const canSwim = { move: () => console.log('水中を泳ぐ') };
const chirp   = { sound: () => console.log('チュンチュン') };
const silent  = { sound: () => {} };

class Bird {
  constructor(name, movement, voice) {
    this.name = name;
    this.movement = movement; // 部品を持つ（has-a）
    this.voice = voice;
  }
  move()  { this.movement.move(); }
  sound() { this.voice.sound(); }
}

const sparrow = new Bird('スズメ', canFly, chirp);
const penguin = new Bird('ペンギン', canSwim, chirp);
const robot   = new Bird('ロボット', canFly, silent);

// 実行時に部品を差し替えることもできる
robot.movement = canSwim;
    • 新しい組み合わせは クラスを増やさず部品の組み合わせ で作れる
    • 部品を差し替えるだけで振る舞いが変わる（これは Strategy パターン（アルゴリズムを部品として差し替えられるようにする設計パターン）そのもの）
    • Bird は部品の 中身を知らず、move() を呼ぶだけ

    6.よくある誤解

    誤解1：「継承は使ってはいけない」

    原則は "Favor"（好め） であって禁止ではありません。次の場合は継承が素直です。

    • 本当に is-a 関係 で、親の約束を子が必ず守れる（LSP を満たす）
    • フレームワークが継承を前提にしている（例：例外クラス class NotFoundError extends Error）
    • 階層が浅く、親クラスが安定している
    誤解2：「合成にすれば必ずシンプルになる」

    部品を細かく分けすぎると、どこで何が組み立てられているか追いにくく なります。組み合わせのバリエーションがない段階で無理に部品化するのは YAGNI 違反です。

    誤解3：「コードの共通化 ＝ 継承」

    コードを共有したいだけなら、継承ではなく 関数やヘルパーに切り出す ほうが軽い場合も多いです。継承は「型としての関係」を表すときに使うのが本来の役割です。

    7.まとめ

    • GoF（1994）の 「クラス継承よりオブジェクト合成を好め」
    • 継承は親の中身に依存する（ホワイトボックス）。合成はインターフェース越しに使う（ブラックボックス）
    • 振る舞いを 部品として持たせる と、組み合わせ爆発と壊れやすい基底クラスを避けられる
    • 継承が向くのは 本物の is-a 関係で、LSP を守れるとき
