    50 法則・経験則

    ポステルの法則 — 送るものは厳密に、受け取るものは寛容に

    インターネットは、世界中のバラバラな人たちが書いたバラバラな実装同士がつながって動いています。仕様の解釈が少しずつ違う相手とも、なんとか通信できなければなりません。その初期のインターネットを支えた心構えが ポステルの法則（別名 堅牢性原則／Robustness Principle）です。ただし近年は、この原則の 副作用 も指摘されています。両方を見ていきます。

    もとにしたノート：04_ポステルの法則

    ひとことで言うと

    「送るものには厳密に、受け取るものには寛容に」。ただし寛容すぎると間違いが広まって固定化するので、今は 「寛容さは境界で吸収し、内側には持ち込まない」、機械同士の通信では仕様違反をはっきり伝える、という使い方が勧められています。

    2.法則の中身と出典

    原文は次のとおりです。

    ポステルの法則（堅牢性原則）

    Be conservative in what you do, be liberal in what you accept from others.
    （自分のすることには保守的に、他人から受け取るものには寛大に）

    • インターネットの基礎を作った研究者 Jon Postel の言葉
    • RFC 760（1980 年、IP の仕様）に登場し、RFC 793（1981 年、TCP の仕様）にも「堅牢性原則」として書かれた。RFC はインターネットの技術仕様をまとめた公開文書のこと
    • まだ実装が少なく、仕様も粗かった時代に、相互接続を最優先する ための知恵だった

    3.現場で起きる例

    3.1 寛容に受け取る例

    ◯ 入力はゆるく受け、出力は 1 つの形式に揃える

    // 日付の入力を受け取る
function parseDate(input) {
  // "2026-10-18" "2026/10/18" " 2026-10-18 " のどれでも受け付ける
  const normalized = input.trim().replace(/\//g, '-');
  return new Date(normalized);
}

// 自分が出力するときは、必ず ISO 8601 の決まった形式で出す
function formatDate(date) {
  return date.toISOString().slice(0, 10); // "2026-10-18"
}

    入力は多少ゆるくても受け止め、出力は 1 つの形式に揃える——これがポステルの法則のお手本的な使い方です。

    3.2 寛容すぎた例：HTML

    ブラウザは閉じタグ忘れや入れ子の間違いがある HTML でも、なんとか表示してきました。その結果、

    • 壊れた HTML が世の中に大量に出回った（壊れていても表示されるので、誰も直さない）
    • 後発のブラウザは 他のブラウザの「壊れ方の解釈」まで真似する 必要が生じた
    • 最終的に HTML5 では、壊れた HTML をどう解釈するか まで仕様に書くことになった

    4.近年の批判：RFC 9413

    2023 年の RFC 9413（「Maintaining Robust Protocols」）は、ポステルの法則を長期的に適用し続けることの問題点を整理しています。

    寛容さが仕様を書き換える

    受け手が間違いを許すと、送り手は間違いに気づかない。いつの間にか「間違った形式」が事実上の標準になる（→ ハイラムの法則）

    実装がどんどん複雑になる

    新しい実装は、既存実装が許してきた「あらゆる間違い」を受け入れなければ相互接続できない

    セキュリティの穴になる

    実装ごとに「寛容さの解釈」が違うと、同じ入力が A では安全・B では危険、というすき間が生まれる

    RFC 9413 の提案は、寛容に受け取るのではなく、プロトコルを積極的にメンテナンスする（仕様違反を見つけたら相手に知らせて直してもらう、仕様を明確に保つ）ことです。

    5.どう付き合うか

    場面方針
    人間からの入力（フォーム・検索ボックス）寛容に受けて、内部で 正規化（決まった形に揃えること）する。空白・全角半角・ハイフン有無などは吸収してよい
    機械同士の通信（API・プロトコル）仕様違反は はっきりエラーにする。エラーメッセージで何が悪いかを伝える
    自分の出力常に厳密に。1 つの正しい形式だけを出す
    外部からの入力をシステム内に入れるとき境界で 1 回だけ検証・正規化し、内側には正しい形のデータだけを流す

    ポイントは 「寛容さは境界で吸収し、内側には持ち込まない」 ことです。API の互換性の守り方は 後方互換性（45章）も参照してください。

    6.よくある誤解

    誤解1：「何でも受け入れるのが堅牢」

    寛容すぎると、間違いが広まり、互換性の負債が積み上がります。

    誤解2：「入力は全部厳しく弾けばいい」

    人間が相手なら、ある程度の寛容さはユーザー体験として必要です。

    誤解3：「もう古い原則」

    「送るものは厳密に」の半分は今も完全に有効です。議論されているのは 受け取り側の寛容さの度合い です。

    7.まとめ

    • 送るものは厳密に、受け取るものは寛容に（Postel, RFC 760 / 793）
    • 初期インターネットの相互接続を支えた知恵
    • ただし寛容さは 間違いを固定化し、複雑さとセキュリティリスクを生む（RFC 9413）
    • 人間の入力には寛容に、機械同士の通信では仕様違反をはっきり伝える
    • 寛容さは 境界で吸収し、内側には持ち込まない
