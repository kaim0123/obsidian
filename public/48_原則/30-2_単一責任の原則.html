    30 オブジェクト指向の原則

    単一責任の原則（SRP）— 変更される理由は 1 つだけ

    SOLID の最初の原則 Single Responsibility Principle（SRP、単一責任の原則） を学びます。1 つのクラスに複数の責任があると何が困るのか、ユーザー管理と注文処理の例で責任をどう分けるのか、「1 クラス 1 メソッド」といった誤解や分けすぎをどう避けるのか、そして分けるかどうかの判断基準と見つけ方のヒントまでを扱います。

    もとにしたノート：01_SRP（単一責任の原則）

    ひとことで言うと

    「1 つのクラスは、変更される理由が 1 つだけであるべき」 という原則です。ユーザー情報・レポート形式・メール送信方法のように 変わる理由が違うもの は別のクラスに分けます。ただし「1 クラス 1 メソッド」ではありません。同じ理由で変わるメソッドは同じクラスにまとめて 構いません。

    1.このページで扱うこと

    Single Responsibility Principle（SRP） は、SOLID 原則 の最初の原則です。

    定義

    「1 つのクラスは、変更される理由が 1 つだけであるべき」

    つまり、1 つのクラスは 1 つの責任（役割）だけを持つべき という原則です。

    • なぜ重要なのか（問題点とメリット）
    • 悪い例と良い例 — ユーザー管理とレポート生成の分離
    • 実践的な例 — 注文処理システム
    • よくある間違い（過度な分割、責任の誤解）
    • 判断基準と適用のヒント、チェックリスト

    SRP は「関心の分離」をクラスに当てはめた具体形です。クラス設計での適用は 44 の「単一責任の原則」、メソッド単位では 46 の「関心の分離と単一責任」でも扱っています。

    2.なぜ重要なのか

    問題点：1 つのクラスに複数の責任があると

    • 変更の影響範囲が広がる — 1 つの機能を変更するだけで、他の機能にも影響が出る
    • テストが困難 — 複数の責任が絡み合い、単体テストが書きにくい
    • 再利用性が低い — 必要な機能だけを取り出せない
    • 理解が困難 — クラスの役割が不明確で、コードの理解が難しくなる

    メリット

    • 変更の影響を局所化 — 1 つの責任だけを変更すれば良い
    • テストしやすい — 各責任を独立してテストできる
    • 再利用性が高い — 必要な機能だけを再利用できる
    • 理解しやすい — クラスの役割が明確

    3.悪い例：ユーザー管理とレポート生成が混在

    ✕ 悪い例：複数の責任を持つクラス 
    // ❌ 悪い例: 複数の責任を持つクラス
class User {
  constructor(name, email) {
    this.name = name;
    this.email = email;
  }

  // 責任1: ユーザー情報の管理
  getName() {
    return this.name;
  }

  getEmail() {
    return this.email;
  }

  save() {
    // データベースに保存
    console.log(`Saving user ${this.name} to database...`);
  }

  // 責任2: レポート生成（本来は別の責任）
  generateReport() {
    console.log(`Report for ${this.name}:`);
    console.log(`Email: ${this.email}`);
    // レポート生成のロジック...
  }

  // 責任3: メール送信（これも別の責任）
  sendEmail(subject, body) {
    console.log(`Sending email to ${this.email}: ${subject}`);
    // メール送信のロジック...
  }
}

    問題点：

    • ユーザー情報の変更 → User クラスを変更
    • レポート形式の変更 → User クラスを変更
    • メール送信方法の変更 → User クラスを変更

    変更理由が 3 つある ＝ SRP 違反 です。

    4.良い例：責任を分離する

    ◯ 良い例：各クラスが 1 つの責任だけを持つ 
    // ✅ 良い例: 各クラスが1つの責任だけを持つ

// 責任1: ユーザー情報の管理
class User {
  constructor(name, email) {
    this.name = name;
    this.email = email;
  }

  getName() {
    return this.name;
  }

  getEmail() {
    return this.email;
  }
}

// 責任2: データベース操作
class UserRepository {
  save(user) {
    console.log(`Saving user ${user.getName()} to database...`);
    // データベース保存のロジック
  }

  findById(id) {
    // ユーザー検索のロジック
  }
}

// 責任3: レポート生成
class UserReportGenerator {
  generateReport(user) {
    console.log(`Report for ${user.getName()}:`);
    console.log(`Email: ${user.getEmail()}`);
    // レポート生成のロジック
  }
}

// 責任4: メール送信
class EmailService {
  sendEmail(to, subject, body) {
    console.log(`Sending email to ${to}: ${subject}`);
    // メール送信のロジック
  }
}

// 使用例
const user = new User('田中太郎', 'tanaka@example.com');
const userRepo = new UserRepository();
const reportGenerator = new UserReportGenerator();
const emailService = new EmailService();

userRepo.save(user);
reportGenerator.generateReport(user);
emailService.sendEmail(user.getEmail(), 'Welcome', 'Welcome to our service!');

    メリット：

    • ユーザー情報の変更 → User クラスのみ変更
    • レポート形式の変更 → UserReportGenerator クラスのみ変更
    • メール送信方法の変更 → EmailService クラスのみ変更

    各クラスの変更理由が 1 つ ＝ SRP 準拠 です。

    なお、悪い例では save() は「責任 1：ユーザー情報の管理」の中に置かれていましたが、良い例ではデータベース操作を独立した責任として UserRepository（データの保存・取り出しを受け持つクラス）に分けています。

    5.実践的な例：注文処理システム

    ✕ 悪い例：計算・保存・メール・印刷が Order に同居 
    // ❌ 悪い例
class Order {
  constructor(items, customer) {
    this.items = items;
    this.customer = customer;
    this.total = 0;
  }

  calculateTotal() {
    // 合計計算
    this.total = this.items.reduce((sum, item) => sum + item.price, 0);
  }

  save() {
    // データベース保存
    console.log('Saving order to database...');
  }

  sendConfirmationEmail() {
    // メール送信
    console.log('Sending confirmation email...');
  }

  printInvoice() {
    // 請求書印刷
    console.log('Printing invoice...');
  }
}
    ◯ 良い例：責任を分離 
    // ✅ 良い例: 責任を分離
class Order {
  constructor(items, customer) {
    this.items = items;
    this.customer = customer;
  }

  getItems() {
    return this.items;
  }

  getCustomer() {
    return this.customer;
  }
}

// 合計計算の責任
class OrderCalculator {
  calculateTotal(order) {
    return order.getItems().reduce((sum, item) => sum + item.price, 0);
  }
}

// データベース操作の責任
class OrderRepository {
  save(order) {
    console.log('Saving order to database...');
    // データベース保存のロジック
  }
}

// メール送信の責任
class EmailService {
  sendConfirmation(order) {
    console.log('Sending confirmation email...');
    // メール送信のロジック
  }
}

// 請求書生成の責任
class InvoicePrinter {
  print(order) {
    console.log('Printing invoice...');
    // 請求書印刷のロジック
  }
}

    分けた後の Order は「データだけ」になっていないか

    この例では合計計算まで外に出したため、Order はデータを返すだけのクラスになっています。合計の計算は注文そのもののルールなので Order に残す、という判断もありえます。データと振る舞いを切り離しすぎる問題は 44 の「Tell, Don't Ask と貧血モデル」で扱っています。何を同じ責任とみなすかは、次の「判断基準」で考えます。

    6.よくある間違い

    6.1 過度な分割

    ✕ やりすぎ：1 つのメソッドごとにクラスを作る 
    // ❌ やりすぎ: 1つのメソッドごとにクラスを作る
class UserNameGetter {
  getName(user) {
    return user.name;
  }
}

class UserEmailGetter {
  getEmail(user) {
    return user.email;
  }
}

    適切な粒度：

    • 関連する責任は 1 つのクラスにまとめる
    • 変更理由が異なる責任は分離する

    6.2 責任の誤解

    「1 つのクラスは 1 つのメソッドだけを持つべき」という誤解があります。

    正しい理解：

    • 1 つのクラスは 1 つの変更理由 だけを持つべき
    • 関連する複数のメソッドは同じクラスに属して良い
    ◯ これは OK：すべて「ユーザー情報の管理」という 1 つの責任 
    // ✅ これはOK: すべて「ユーザー情報の管理」という1つの責任
class User {
  getName() { }
  getEmail() { }
  setName(name) { }
  setEmail(email) { }
  validate() { }
}

    7.判断基準

    責任を分離すべきか判断する質問です。

    質問例判断
    1. 変更理由が異なるか？ユーザー情報の変更とレポート形式の変更は別の理由分離すべき
    2. 再利用性が異なるか？ユーザー情報は他の場所でも使うが、レポート生成は特定の場所だけ分離すべき
    3. テストの難易度は？1 つの責任をテストするために、他の責任のモック（テスト用の偽物）が必要分離すべき

    8.適用のヒント

    8.1 クラス名から判断

    クラス名に「and」や「or」が含まれる場合、複数の責任がある可能性が高いです。

    ✕ 複数の責任の可能性 
    // ❌ 複数の責任の可能性
class UserAndReportManager { }
class OrderAndEmailService { }

    8.2 メソッドのグループ化

    関連するメソッドをグループ化し、グループ間の関連性が低ければ分離を検討します。

    class Order {
  // グループ1: 注文情報の取得
  getItems() { }
  getCustomer() { }

  // グループ2: 計算（別の責任かも？）
  calculateTotal() { }
  calculateTax() { }

  // グループ3: 永続化（別の責任かも？）
  save() { }
  load() { }
}

    8.3 変更の影響範囲

    変更したときに、他の機能に影響が出るか確認します。

    • 影響が出る → 責任が混在している可能性
    • 影響が出ない → 適切に分離されている

    9.関連原則

    原則関係
    Open/Closed Principle（開放閉鎖の原則）SRP を守ることで、変更が局所化され、OCP も守りやすくなる
    Separation of Concerns（関心の分離）関心の分離は SRP の基盤となる考え方

    10.よくある誤解

    誤解1：「1 つのクラスは 1 つのメソッドだけを持つべき」

    SRP の「1 つ」は 変更理由 の数です。getName・getEmail・setName・setEmail・validate がすべて「ユーザー情報の管理」という 1 つの責任なら、同じクラスにあって構いません。

    誤解2：「細かく分けるほど SRP に忠実」

    UserNameGetter・UserEmailGetter のように 1 メソッドごとにクラスを作るのは 過度な分割 です。関連する責任は 1 つのクラスにまとめ、変更理由が異なるものだけを分けます。

    誤解3：「責任＝そのクラスが持つ機能の数」

    責任は機能の数ではなく、何が変わったときにそのクラスを直すことになるか で数えます。判断に迷ったら「変更理由が異なるか」「再利用性が異なるか」「テストに他の責任のモックが要るか」の 3 つを問います。

    11.まとめ

    11.1 重要なポイント

    1. 1 つのクラス ＝ 1 つの変更理由
    2. 責任を明確に定義する
    3. 過度な分割は避ける
    4. 関連する責任はまとめる

    11.2 チェックリスト

    • ☐ クラス名に「and」や「or」が含まれていないか？
    • ☐ 変更理由が 1 つだけか？
    • ☐ テストが独立して書けるか？
    • ☐ 再利用性が高いか？
