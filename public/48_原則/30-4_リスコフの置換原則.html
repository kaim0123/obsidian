    30 オブジェクト指向の原則

    リスコフの置換原則（LSP） — 子クラスは親の代わりになれるか

    SOLID 原則の 3 番目、リスコフの置換原則（Liskov Substitution Principle, LSP） を学びます。「親クラスを使っている場所に子クラスを入れても、プログラムが壊れてはいけない」という原則です。有名な「正方形と長方形」の例、鳥とペンギン、読み取り専用コレクションの例を通して、契約（事前条件・事後条件・不変条件） を守るとはどういうことかを見ていきます。

    もとにしたノート：03_LSP (リスコフの置換原則)

    ひとことで言うと

    子クラス（派生クラス）は、親クラス（基底クラス）と 同じ約束を守る ときだけ継承してよい、という原則です。「概念として is-a（〜は〜の一種）か」ではなく、「親の代わりに渡しても同じように動くか」 で判断します。子クラスが例外を投げたり、受け付ける値を狭めたり、返す結果を弱めたりしたら違反のサインです。

    2.LSP とは

    Liskov Substitution Principle（LSP） は、SOLID 原則 の 3 番目の原則です。

    「派生クラス（サブクラス）のオブジェクトは、その基底クラス（スーパークラス）のオブジェクトと置き換え可能でなければならない」

    つまり、基底クラスのオブジェクトを使っている場所で、派生クラスのオブジェクトに置き換えても、プログラムの動作が壊れてはいけない という原則です。

    • 基底クラス（スーパークラス、親クラス）：継承の元になるクラス
    • 派生クラス（サブクラス、子クラス）：基底クラスを継承して作ったクラス

    この原則は、1987 年に バーバラ・リスコフ（Barbara Liskov） によって提唱されました。

    3.なぜ重要なのか

    問題点（LSP に違反すると）

    • 予期しない動作 — 基底クラスを期待しているコードで、派生クラスを使うとエラーが発生
    • テストの失敗 — 基底クラスで動作していたテストが、派生クラスで失敗する
    • ポリモーフィズムの破綻 — オブジェクト指向の多態性が正しく機能しない
    • 保守性の低下 — どの派生クラスが安全に使えるか判断が困難

    メリット（LSP を守ると）

    • 安全な置き換え — 基底クラスと派生クラスを安全に交換できる
    • ポリモーフィズムの保証 — 多態性が正しく機能する
    • テストの一貫性 — 基底クラスのテストが派生クラスでも有効
    • 拡張性の向上 — 新しい派生クラスを追加しやすい

    ポリモーフィズム（多態性） とは、同じ呼び出し方（例：shape.getArea()）で、渡されたオブジェクトの種類に応じた処理が動く仕組みのことです。LSP は、このしくみを安心して使うための前提条件だといえます。

    4.基本的な考え方 — 契約（Contract）

    基底クラスと派生クラスの間には 契約 があります。契約とは「このメソッドはこう呼べば、こうなる」という約束のことです。

    契約の種類意味
    1. 事前条件（Preconditions）メソッドを呼び出す前に満たすべき条件
    2. 事後条件（Postconditions）メソッド実行後に保証される条件
    3. 不変条件（Invariants）常に保たれるべき条件

    ルール

    派生クラスは、基底クラスの契約を弱めてはいけない。 具体的には、事前条件を強めない（受け付ける値を狭めない）、事後条件を弱めない（保証する結果を減らさない）、不変条件を壊さない、の 3 つです（8. LSP 違反のパターン で例を見ます）。

    この「契約」の考え方は 契約による設計（Design by Contract） から来ています。メソッド単位での書き方は 46 章の「Design by Contract」で扱っています。

    5.悪い例 — 正方形と長方形の問題

    5.1 例1：正方形と長方形の問題（クラシックな例）

    「正方形は長方形の一種」なので、Square が Rectangle を継承するのは自然に見えます。ところが、これが LSP 違反の代表例です。

    ✕ 悪い例：Square が Rectangle を継承している 
    // ❌ 悪い例: LSP違反
class Rectangle {
  constructor(width, height) {
    this.width = width;
    this.height = height;
  }

  setWidth(width) {
    this.width = width;
  }

  setHeight(height) {
    this.height = height;
  }

  getArea() {
    return this.width * this.height;
  }
}

// SquareはRectangleを継承しているが、置き換え不可能
class Square extends Rectangle {
  constructor(side) {
    super(side, side);
  }

  setWidth(width) {
    this.width = width;
    this.height = width;  // 正方形なので、高さも同じにする
  }

  setHeight(height) {
    this.width = height;
    this.height = height;  // 正方形なので、幅も同じにする
  }
}

// 問題: Rectangleを期待している関数で、Squareを使うと予期しない動作
function testRectangle(rectangle) {
  rectangle.setWidth(5);
  rectangle.setHeight(4);

  // Rectangleなら 5 * 4 = 20 を期待
  // しかしSquareなら 4 * 4 = 16 になってしまう！
  console.log(`Expected: 20, Got: ${rectangle.getArea()}`);
}

const rect = new Rectangle(10, 10);
testRectangle(rect);  // Expected: 20, Got: 20 ✅

const square = new Square(10);
testRectangle(square);  // Expected: 20, Got: 16 ❌ LSP違反！

    問題点:

    • Square は Rectangle の代わりに使えない
    • setWidth と setHeight の動作が異なる
    • 基底クラスを期待しているコードで、派生クラスを使うと予期しない動作

    6.良い例 — 継承関係を見直す

    6.1 解決策1：継承関係を変更（共通の基底クラスを作る）

    Square を Rectangle の子にするのをやめ、両方を共通の親 Shape の子にします。Shape が約束するのは「getArea() で面積を返す」ことだけなので、どちらも約束を守れます。

    ◯ 良い例：共通の基底クラス Shape を作る 
    // ✅ 良い例: 共通の基底クラスを作る
class Shape {
  getArea() {
    throw new Error('getArea must be implemented');
  }
}

class Rectangle extends Shape {
  constructor(width, height) {
    super();
    this.width = width;
    this.height = height;
  }

  setWidth(width) {
    this.width = width;
  }

  setHeight(height) {
    this.height = height;
  }

  getArea() {
    return this.width * this.height;
  }
}

class Square extends Shape {
  constructor(side) {
    super();
    this.side = side;
  }

  setSide(side) {
    this.side = side;
  }

  getArea() {
    return this.side * this.side;
  }
}

// これで、Shapeを期待している関数で、RectangleもSquareも使える
function calculateTotalArea(shapes) {
  return shapes.reduce((total, shape) => total + shape.getArea(), 0);
}

const shapes = [
  new Rectangle(5, 4),
  new Square(3)
];

console.log(calculateTotalArea(shapes));  // 20 + 9 = 29 ✅

    ※ Shape の getArea() が例外を投げているのは「子クラスで必ず実装する」という目印です。JavaScript には抽象メソッドの仕組みがないため、このように書いて代用しています。

    6.2 解決策2：不変オブジェクトとして扱う

    不変オブジェクト（作った後で中身を変えられないオブジェクト）にすると、「幅だけ変える」という操作そのものがなくなるので、問題が起きません。

    ◯ 良い例：setter をなくし、不変オブジェクトとして扱う 
    // ✅ 良い例: 不変オブジェクトとして扱う
class Rectangle {
  constructor(width, height) {
    this.width = width;
    this.height = height;
  }

  getArea() {
    return this.width * this.height;
  }
}

class Square {
  constructor(side) {
    this.side = side;
  }

  getArea() {
    return this.side * this.side;
  }
}

// 共通のインターフェース（JavaScriptでは型がないので、暗黙的）
// 両方ともgetArea()メソッドを持つ

    7.実践的な例

    7.1 例2：鳥クラスの問題

    「鳥は飛ぶ」と決めて Bird に fly() を置くと、飛べないペンギンを子クラスにしたときに困ります。

    ✕ 悪い例：Penguin が fly() で例外を投げる 
    // ❌ 悪い例: LSP違反
class Bird {
  fly() {
    console.log('Flying...');
  }

  eat() {
    console.log('Eating...');
  }
}

class Sparrow extends Bird {
  fly() {
    console.log('Sparrow is flying...');
  }
}

class Penguin extends Bird {
  // ペンギンは飛べない！
  fly() {
    throw new Error('Penguins cannot fly!');  // ❌ LSP違反
  }
}

// 問題: Birdを期待している関数で、Penguinを使うとエラー
function makeBirdFly(bird) {
  bird.fly();  // Penguinの場合、エラーが発生
}

const sparrow = new Sparrow();
makeBirdFly(sparrow);  // ✅ OK

const penguin = new Penguin();
makeBirdFly(penguin);  // ❌ エラー！LSP違反
    ◯ 良い例：飛べる鳥と飛べない鳥でインターフェースを分ける 
    // ✅ 良い例: インターフェースを分離
class Bird {
  eat() {
    console.log('Eating...');
  }
}

// 飛べる鳥のインターフェース
class FlyingBird extends Bird {
  fly() {
    throw new Error('fly must be implemented');
  }
}

// 飛べない鳥のインターフェース
class NonFlyingBird extends Bird {
  swim() {
    throw new Error('swim must be implemented');
  }
}

class Sparrow extends FlyingBird {
  fly() {
    console.log('Sparrow is flying...');
  }
}

class Penguin extends NonFlyingBird {
  swim() {
    console.log('Penguin is swimming...');
  }
}

// これで、FlyingBirdを期待している関数で、Sparrowは使える
function makeBirdFly(bird) {
  bird.fly();  // FlyingBirdを期待
}

const sparrow = new Sparrow();
makeBirdFly(sparrow);  // ✅ OK

// PenguinはFlyingBirdではないので、この関数には渡せない（正しい）

    「必要なメソッドだけを持つ小さなインターフェースに分ける」という考え方は、次の インターフェース分離の原則（ISP） そのものです。

    7.2 例3：コレクションクラス

    読み取り専用のコレクションを、書き込みできるコレクションの子にしてしまう例です。

    ✕ 悪い例：ReadOnlyCollection が add / remove で例外を投げる 
    // ❌ 悪い例: LSP違反
class Collection {
  add(item) {
    // コレクションに追加
    this.items.push(item);
  }

  remove(item) {
    // コレクションから削除
    const index = this.items.indexOf(item);
    if (index > -1) {
      this.items.splice(index, 1);
    }
  }
}

class ReadOnlyCollection extends Collection {
  add(item) {
    throw new Error('Cannot add to read-only collection');  // ❌ LSP違反
  }

  remove(item) {
    throw new Error('Cannot remove from read-only collection');  // ❌ LSP違反
  }
}

// 問題: Collectionを期待している関数で、ReadOnlyCollectionを使うとエラー
function addItems(collection, items) {
  items.forEach(item => collection.add(item));  // ReadOnlyCollectionの場合、エラー
}
    ◯ 良い例：継承関係を変更する（または共通のインターフェースを作る） 
    // ✅ 良い例: 継承関係を変更
class Collection {
  add(item) {
    this.items.push(item);
  }

  remove(item) {
    const index = this.items.indexOf(item);
    if (index > -1) {
      this.items.splice(index, 1);
    }
  }
}

// ReadOnlyCollectionはCollectionを継承しない
class ReadOnlyCollection {
  constructor(items) {
    this.items = [...items];  // コピーを作成
  }

  getItems() {
    return [...this.items];  // コピーを返す
  }

  // addやremoveメソッドは提供しない
}

// または、共通のインターフェースを作る
class ReadableCollection {
  getItems() {
    throw new Error('getItems must be implemented');
  }
}

class MutableCollection extends ReadableCollection {
  add(item) { }
  remove(item) { }
  getItems() { }
}

class ReadOnlyCollection extends ReadableCollection {
  getItems() { }
  // addやremoveは提供しない
}

    ※ コードは要点だけを示しています（Collection の this.items の初期化などは省略）。また、2 つの案を続けて書いているため ReadOnlyCollection が 2 回出てきます。実際にはどちらか一方を選びます。

    8.LSP 違反のパターン

    パターン何が起きるか
    1. 派生クラスが例外を投げる親では動いた呼び出しが、子ではエラーになる
    2. 派生クラスが事前条件を強める親なら受け付けた値を、子が拒否する
    3. 派生クラスが事後条件を弱める親なら保証した結果を、子が返さない

    8.1 派生クラスが例外を投げる

    ✕ 悪い例：親の処理を「対応していない」で潰す 
    // ❌ 悪い例
class Base {
  method() {
    // 何か処理
  }
}

class Derived extends Base {
  method() {
    throw new Error('Not supported');  // ❌ LSP違反
  }
}

    8.2 派生クラスが事前条件を強める

    ✕ 悪い例：親は任意の数値を受け付けるのに、子は負の数を拒否する 
    // ❌ 悪い例
class Base {
  method(value) {
    // valueは任意の数値を受け入れる
  }
}

class Derived extends Base {
  method(value) {
    if (value < 0) {
      throw new Error('Value must be positive');  // ❌ 事前条件を強めている
    }
    super.method(value);
  }
}

    8.3 派生クラスが事後条件を弱める

    ✕ 悪い例：親は必ず結果オブジェクトを返すのに、子は null を返す 
    // ❌ 悪い例
class Base {
  method() {
    return { result: 'success', data: 'some data' };
  }
}

class Derived extends Base {
  method() {
    return null;  // ❌ 事後条件を弱めている（nullを返す可能性）
  }
}

    9.良い例のパターン

    9.1 契約を守る

    ◯ 良い例：事前条件を強めず、事後条件を弱めない 
    // ✅ 良い例
class Base {
  method(value) {
    if (value < 0) {
      throw new Error('Value must be non-negative');
    }
    return value * 2;
  }
}

class Derived extends Base {
  method(value) {
    // 事前条件を弱めない（同じか、より緩い条件）
    // 事後条件を弱めない（同じか、より強い保証）
    return super.method(value) + 1;
  }
}

    ※ この例が「良い例」になるのは、親の契約が「0 以上の数を受け取り、数値を返す」程度のときです。親の契約が「ちょうど value * 2 を返す」と決まっているなら、+ 1 は事後条件を破ることになります。何を約束しているかを明確にしておく ことが大切です（11.3 契約を明確にする）。

    9.2 不変条件を保つ

    ◯ 良い例：「残高は 0 以上」を子クラスでも保つ 
    // ✅ 良い例
class Account {
  constructor(balance) {
    if (balance < 0) {
      throw new Error('Balance cannot be negative');
    }
    this.balance = balance;
  }

  withdraw(amount) {
    if (amount < 0) {
      throw new Error('Amount must be positive');
    }
    if (this.balance < amount) {
      throw new Error('Insufficient funds');
    }
    this.balance -= amount;
    // 不変条件: balance >= 0 が常に保たれる
  }
}

class SavingsAccount extends Account {
  withdraw(amount) {
    // 不変条件を保つ（balance >= 0）
    super.withdraw(amount);
  }
}

    10.判断基準

    LSP を守っているか判断する質問です。

    質問LSP 準拠LSP 違反
    1. 基底クラスのオブジェクトを派生クラスに置き換えても動作するか？動作する動作しない
    2. 派生クラスが例外を投げていないか？投げていない投げている → 違反の可能性
    3. 事前条件・事後条件・不変条件を守っているか？守っている守っていない

    11.適用のヒント

    11.1 "is-a" 関係を確認

    // "Square is a Rectangle" は数学的には正しいが、
// プログラム的には置き換え不可能な場合がある

    判断:

    • 数学的・概念的な "is-a" 関係だけでなく、動作的な "is-a" 関係 を確認
    • 基底クラスの代わりに使えるか？

    無理に継承せず、部品として持たせる（合成）ほうが安全な場面も多くあります。詳しくは 44 章の「継承より合成」を参照してください。

    11.2 テストで確認

    // 基底クラスのテストが、派生クラスでも通るか確認
function testBase(base) {
  // 基底クラスのテスト
}

// これが派生クラスでも通るべき
testBase(new Derived());  // エラーが出たらLSP違反

    11.3 契約を明確にする

    • 事前条件、事後条件、不変条件を明確に定義
    • コメントやドキュメントで契約を記述

    原則LSP との関係
    Open/Closed Principle（OCP）LSP を守ることで、OCP も守りやすくなる
    Interface Segregation Principle（ISP）適切なインターフェース設計が LSP を守る助けになる

    13.よくある誤解

    誤解1：「概念として is-a なら継承してよい」

    「正方形は長方形の一種」は数学的には正しくても、setWidth と setHeight を別々に呼べる長方形の 振る舞い を、正方形は再現できません。継承してよいかは 「親の代わりに渡しても同じように動くか」（動作的な is-a）で判断します。

    誤解2：「例外さえ投げなければ LSP は守れている」

    例外を投げるのは分かりやすい違反のサインにすぎません。受け付ける値を狭める（事前条件を強める）、null を返すなど結果を弱める（事後条件を弱める）、「残高は 0 以上」のような性質を壊す（不変条件を壊す）のも違反です。正方形の例も、例外は出ないのに結果が食い違っています。

    誤解3：「違反したら使う側で条件分岐して対処すればよい」

    使う側で「Penguin なら fly を呼ばない」と分岐し始めると、子クラスを追加するたびに使う側を直すことになり、ポリモーフィズムの意味がなくなります。鳥やコレクションの例のように、継承関係そのものを見直す（共通の親を作る・インターフェースを分ける・継承をやめる）のが基本です。

    14.まとめ

    14.1 重要なポイント

    1. 派生クラスは基底クラスと置き換え可能 — 同じように動作する
    2. 契約を守る — 事前条件、事後条件、不変条件
    3. 例外を投げない — 基底クラスが例外を投げないなら、派生クラスも投げない
    4. 動作の一貫性 — 基底クラスを期待しているコードで、派生クラスも動作する
