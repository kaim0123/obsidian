    10 汎用原則

    DRY・KISS・YAGNI — 重複させない・シンプルに・作りすぎない

    プログラムを書くとき、「どう書けばよいコードになるのか」と迷うことがあります。そんなときに道しるべになるのが、先人たちが残した 開発原則 です。このページでは、どの単位のコードにも効く特に有名な3つ — DRY（同じことを繰り返し書かない）・KISS（シンプルに保つ）・YAGNI（今いらない機能は作らない）— の定義・理由・悪い例と良い例・適用例・注意点・よくある誤解を、まとめて学びます。

    もとにしたノート：01_DRY_KISS_YAGNI、02_DRY原則・KISS原則

    ひとことで言うと

    DRY は「同じ 知識 を二重に書かない」、KISS は「賢さより分かりやすさ」、YAGNI は「今いらないものは作らない」。どれも 読みやすく、壊れにくいコード を書くための原則です。ただし、見た目が似ているだけのコードを無理にまとめたり、要件を削ったり、変更しやすい構造まで捨てたりするのは誤用です。

    1.このページで扱うこと

    • DRY・KISS・YAGNI それぞれの定義と、なぜ必要なのか
    • 悪い例と良い例（JavaScript）、よくある適用例
    • 各原則で気をつけること（過度な抽象化・偶然の重複など）
    • 3つの原則の関係と、組み合わせた実践例
    • よくある誤解

    DRY と他の原則（SRP）がぶつかる場面や、YAGNI が初心者に難しい理由は DRY・YAGNI の落とし穴と実践的判断、実際のコードに出がちな重複のパターンは コードの重複と DRY 原則違反 で扱います。それぞれの原則が生まれた背景は 設計原則の変遷 を見てください。メソッド単位での使い方は 46 の KISS・DRY・YAGNI が本拠地です。

    2.3つの原則の概要

    この3つは、それぞれ頭文字を取った略語です。どれも「読みやすく、壊れにくいコードを書くため」のものです。

    DRY（ドライ）

    Don't Repeat Yourself
    同じことを繰り返し書かない

    KISS（キス）

    Keep It Simple, Stupid
    シンプルに保つ

    YAGNI（ヤグニ）

    You Aren't Gonna Need It
    今いらない機能は作らない

    3.DRY 原則（Don't Repeat Yourself）

    「同じことを繰り返し書かない」 という原則です。Andy Hunt と Dave Thomas が『達人プログラマー』で提唱しました。基本的な考え方は次の一文に表されています。

    すべての知識はシステム内で単一、明確、信頼できる表現を持つべきである

    3.1 なぜ必要なのか

    同じ処理をあちこちにコピーして書いてしまうと、次のような問題が起きます。

    • 修正漏れが発生する … 仕様変更のとき、1つだけ直し忘れてバグになる
    • 読むのに時間がかかる … 同じようなコードが散らばっていると、どれが本物か分からなくなる
    • テストが難しい … 同じロジックを何度もテストしなくてはならない

    3.2 例1：税率の計算

    ✕ 悪い例：同じ計算が複数の関数に 
    function calcTaxForFood(price) {
  return price + price * 0.08; // 軽減税率8%
}

function calcTaxForBook(price) {
  return price + price * 0.08; // 同じ計算！
}

function calcTaxForToy(price) {
  return price + price * 0.10; // 標準税率10%
}

    軽減税率が将来8%から9%に変わったら、2か所を直さなくてはなりません。直し忘れると、食べ物と本で税額がズレてバグになります。

    ◯ 良い例：税率を定数に、計算を1つの関数に 
    const TAX_REDUCED = 0.08;
const TAX_STANDARD = 0.10;

function calcTax(price, rate) {
  return price + price * rate;
}

calcTax(1000, TAX_REDUCED); // 食べ物
calcTax(1500, TAX_REDUCED); // 本
calcTax(3000, TAX_STANDARD); // おもちゃ

    税率の変更は定数1か所の修正で済みます。

    3.3 例2：価格の計算（税と送料）

    ✕ 悪い例：重複コード 
    function calculatePrice1() {
  const price = 1000;
  const tax = price * 0.1;
  const shippingFee = 500;
  return price + tax + shippingFee;
}

function calculatePrice2() {
  const price = 2000;
  const tax = price * 0.1;  // 重複！
  const shippingFee = 500;  // 重複！
  return price + tax + shippingFee;
}

function calculatePrice3() {
  const price = 3000;
  const tax = price * 0.1;  // 重複！
  const shippingFee = 500;  // 重複！
  return price + tax + shippingFee;
}

    問題点：

    • 税率や送料が変わったら、全箇所を修正する必要がある
    • 修正漏れが発生しやすい
    • バグが混入しやすい
    ◯ 良い例：DRY を適用 
    const TAX_RATE = 0.1;
const SHIPPING_FEE = 500;

function calculateTax(price) {
  return price * TAX_RATE;
}

function calculateTotalPrice(price) {
  const tax = calculateTax(price);
  return price + tax + SHIPPING_FEE;
}

// 使用
console.log(calculateTotalPrice(1000));  // 1600
console.log(calculateTotalPrice(2000));  // 2700
console.log(calculateTotalPrice(3000));  // 3800

    メリット：

    • 税率や送料の変更が1箇所で済む
    • バグが入りにくい
    • コードが短くなる

    3.4 DRY の適用例

    データ・ロジック・設定 の3つの重複を、それぞれ1か所にまとめる例です。

    ✕ NG：データの重複 
    const users = [
  { id: 1, name: "太郎", email: "taro@example.com" },
  { id: 2, name: "花子", email: "hanako@example.com" }
];

const userEmails = [
  "taro@example.com",  // 重複！
  "hanako@example.com"  // 重複！
];
    ◯ OK：データソースを1つに 
    const users = [
  { id: 1, name: "太郎", email: "taro@example.com" },
  { id: 2, name: "花子", email: "hanako@example.com" }
];

const userEmails = users.map(user => user.email);

    メールアドレスの一覧は users から 計算で作る ので、ユーザーを追加・変更しても食い違いが起きません。

    ✕ NG：同じバリデーションロジックが複数箇所に 
    function registerUser(email) {
  if (!email.includes('@')) {
    throw new Error('Invalid email');
  }
  // ユーザー登録処理
}

function updateEmail(email) {
  if (!email.includes('@')) {  // 重複！
    throw new Error('Invalid email');
  }
  // メール更新処理
}
    ◯ OK：バリデーションを共通化 
    function validateEmail(email) {
  if (!email.includes('@')) {
    throw new Error('Invalid email');
  }
}

function registerUser(email) {
  validateEmail(email);
  // ユーザー登録処理
}

function updateEmail(email) {
  validateEmail(email);
  // メール更新処理
}

    バリデーション（入力値が正しい形かどうかの検査）のルールは「メールアドレスの正しさ」という1つの知識なので、1つの関数にまとめます。

    ✕ NG：設定が散らばっている 
    const API_URL = 'https://api.example.com';
const TIMEOUT = 5000;

function fetchUsers() {
  fetch('https://api.example.com/users', { timeout: 5000 });  // 重複！
}

function fetchPosts() {
  fetch('https://api.example.com/posts', { timeout: 5000 });  // 重複！
}
    ◯ OK：設定を一元化 
    const config = {
  API_URL: 'https://api.example.com',
  TIMEOUT: 5000
};

function fetchUsers() {
  fetch(`${config.API_URL}/users`, { timeout: config.TIMEOUT });
}

function fetchPosts() {
  fetch(`${config.API_URL}/posts`, { timeout: config.TIMEOUT });
}

    補足：fetch のタイムアウト

    この例は「設定を1か所にまとめる」ことを示すためのものです。ブラウザ標準の fetch には timeout というオプションはなく、渡しても無視されます。実際にタイムアウトさせたいときは { signal: AbortSignal.timeout(config.TIMEOUT) } のように AbortSignal を使います（MDN「AbortSignal.timeout()」）。

    3.5 DRY で気をつけること

    いちばん大事なのは 「見た目が同じ」なだけで無理にまとめない ことです。たまたま同じコードになっているだけなら、別物として置いておくほうが安全な場合もあります。DRY は「同じ知識 を二重に書かない」ことが本質です。

    過度な抽象化を避ける

    抽象化（共通部分を取り出して、汎用的な関数やクラスにすること）はやりすぎると、かえって読みにくくなります。

    ✕ やりすぎ 
    function processData(data, operation) {
  return data.map(operation);
}

const doubled = processData([1, 2, 3], x => x * 2);
const squared = processData([1, 2, 3], x => x * x);
    ◯ 適度 
    const doubled = [1, 2, 3].map(x => x * 2);
const squared = [1, 2, 3].map(x => x * x);

    processData は map を包んだだけで、新しい知識を何も表していません。名前が1つ増えて読み手が調べる手間が増えるだけです。

    偶然の重複に注意

    同じコードでも、意味が違う 場合は無理に共通化しません。

    // これらは偶然同じコードだが、意味が違う
function calculateShippingFee(weight) {
  return weight * 100;  // 重量ベース
}

function calculateStorageFee(weight) {
  return weight * 100;  // 重量ベース（でも別の意味）
}

// 共通化すべきではない（将来、計算式が変わる可能性がある）

    送料と保管料は、たまたま今は同じ計算式なだけで、変わる理由が別々です。この判断の詳しい基準は DRY・YAGNI の落とし穴と実践的判断 で扱います。

    4.KISS 原則（Keep It Simple, Stupid）

    「シンプルに保て」 という原則です。「難しいことをしようとせず、単純に作れ」という意味です。基本的な考え方は次のとおりです。

    複雑さは敵である。シンプルなシステムの方が理解しやすく、保守しやすい。

    4.1 なぜ必要なのか

    複雑なコードは、書いた本人でさえ1週間後には読めなくなります。コードは書く時間より読む時間のほうが圧倒的に長い ため、シンプルさは大きな武器です。

    4.2 例1：偶数の判定

    ✕ 悪い例：複雑すぎる 
    // 偶数か判定する関数
function isEven(n) {
  return ((n & 1) === 0) ? true : (((n % 2) === 0) ? true : false);
}

    ビット演算や 三項演算子（条件 ? A : B の形で書く短い if）を使って格好良く見えますが、読みにくくバグの温床になります。

    ◯ 良い例：シンプル 
    function isEven(n) {
  return n % 2 === 0;
}

    4.3 例2：ネストした三項演算子

    ✕ 悪い例：複雑すぎる 
    function processUser(user) {
  return user && user.name && user.name.length > 0
    ? user.age && user.age >= 20
      ? user.isActive !== false
        ? { ...user, status: 'valid' }
        : { ...user, status: 'inactive' }
      : { ...user, status: 'underage' }
    : null;
}

    問題点：

    • ネストが深い
    • 読みにくい
    • デバッグが難しい
    ◯ 良い例：シンプルに 
    function processUser(user) {
  if (!user || !user.name || user.name.length === 0) {
    return null;
  }

  if (user.age < 20) {
    return { ...user, status: 'underage' };
  }

  if (user.isActive === false) {
    return { ...user, status: 'inactive' };
  }

  return { ...user, status: 'valid' };
}

    メリット：

    • フラットな構造
    • 読みやすい
    • デバッグしやすい

    4.4 KISS の適用例

    早期リターン

    早期リターン は、結果が決まった時点ですぐ return して、if のネストを浅くする書き方です（メソッド設計での詳しい扱いは 46 の Guard Clause）。

    ✕ NG：ネストが深い 
    function getDiscount(user) {
  if (user) {
    if (user.isPremium) {
      if (user.purchases > 10) {
        return 0.2;
      } else {
        return 0.1;
      }
    } else {
      return 0.05;
    }
  } else {
    return 0;
  }
}
    ◯ OK：早期リターン 
    function getDiscount(user) {
  if (!user) return 0;
  if (!user.isPremium) return 0.05;
  if (user.purchases > 10) return 0.2;
  return 0.1;
}

    シンプルなロジック

    ✕ NG：複雑 
    function isWeekend(date) {
  const day = date.getDay();
  if (day === 0) {
    return true;
  } else if (day === 6) {
    return true;
  } else {
    return false;
  }
}
    ◯ OK：シンプル 
    function isWeekend(date) {
  const day = date.getDay();
  return day === 0 || day === 6;
}

    過度な抽象化を避ける

    ✕ NG：汎用的すぎて複雑 
    class DataProcessor {
  process(data, config) {
    const strategy = this.getStrategy(config.type);
    const validator = this.getValidator(config.validation);
    const transformer = this.getTransformer(config.transformation);

    // 複雑な処理...
  }
}
    ◯ OK：シンプルに 
    function doubleNumbers(numbers) {
  return numbers.map(n => n * 2);
}

function filterEvenNumbers(numbers) {
  return numbers.filter(n => n % 2 === 0);
}

    「どんな処理にも使える」汎用の仕組みは、設定の組み合わせを読み解かないと何をするのか分かりません。やりたいことが「2倍にする」「偶数だけ残す」なら、それを名前にした小さな関数のほうが読みやすくなります。

    4.5 KISS で気をつけること

    • 賢いコードより、わかりやすいコードを書く
    • 早すぎる最適化は避ける（パフォーマンスより読みやすさ優先）
    • 1つの関数は1つのことだけを行う

    5.YAGNI 原則（You Aren't Gonna Need It）

    「たぶん必要にならない」 という原則です。エクストリーム・プログラミング（XP）（短い周期で動くものを作り、テストとリファクタリングを重ねる開発手法）で提唱されました。

    「将来役に立ちそうだから」という理由で、今不要な機能を先回りして作ってはいけない という意味です。言い換えると、今必要ないものは作らない という原則です。

    5.1 なぜ必要なのか

    「将来のために」と思って作った機能は、80%以上は使われない と言われています。にもかかわらず、次のコストは確実にかかります。

    • コードが肥大化して読みにくくなる
    • テストしなければならないコードが増える
    • 仕様変更のとき、使わないコードも直さなくてはならない
    • 本当に使うときには要件が変わっていて、作り直しになる

    5.2 例1：使わないエクスポート機能

    ✕ 悪い例：「将来使うかも」で作った 
    // ユーザー登録機能だけ作ればいい場面で…
class UserManager {
  register(user) { /* ... */ }

  // 「将来使うかも」でつくった
  exportToPDF() { /* 未使用 */ }
  exportToCSV() { /* 未使用 */ }
  exportToXML() { /* 未使用 */ }
  sendSMS() { /* 未使用 */ }
  integrateWithSlack() { /* 未使用 */ }
}
    ◯ 良い例：今必要な機能だけ 
    class UserManager {
  register(user) { /* 今必要な機能だけ */ }
}
// エクスポート機能は、本当に必要になってから実装する

    5.3 例2：将来のために作りすぎたクラス

    ✕ 悪い例：将来のために作りすぎ 
    class User {
  constructor(name, email) {
    this.name = name;
    this.email = email;
    this.preferences = {};  // まだ使わない
    this.history = [];      // まだ使わない
    this.metadata = {};     // まだ使わない
    this.settings = {};     // まだ使わない
    this.cache = {};        // まだ使わない
  }

  // まだ使わないメソッド
  exportData() { /* ... */ }
  importData() { /* ... */ }
  migrate() { /* ... */ }
}
    ◯ 良い例：必要なものだけ 
    class User {
  constructor(name, email) {
    this.name = name;
    this.email = email;
  }
}

// 必要になったら追加する

    5.4 YAGNI で気をつけること

    「いつか必要になる」の 「いつか」は来ない と思っておくくらいでちょうど良いです。本当に必要になったときに追加すれば、その時点の要件に合った形で作れます。将来の予測に時間をかけすぎないことも大切です。

    ただし、「後から追加する」を安全に行うには、テストやリファクタリングの力が前提になります。この点は YAGNI 原則が初心者に遵守できない理由 で扱います。

    6.3つの原則の関係

    3つはそれぞれ独立した原則ですが、互いに補い合います。

    原則意味一言で
    DRY重複を避ける書くのは1回だけ
    KISSシンプルを保つ賢さより分かりやすさ
    YAGNI先回りしない今いらないものは作らない

    6.1 3つをまとめて見た例

    ✕ 悪い例：DRY 違反・KISS 違反・YAGNI 違反すべて 
    function processUser(user, type, format, notify, future1, future2) {
  if (type === 'admin') { /* 独自処理A */ }
  if (type === 'user') { /* 独自処理A（コピペ）*/ }
  if (format === 'json') { /* 変換 */ }
  if (format === 'xml') { /* 未使用 */ }
  if (notify) { /* まだ使わない通知 */ }
  // ...
}
    ◯ 良い例：3つの原則すべてを満たす 
    function processUser(user) {
  validate(user);
  save(user);
}

    悪い例では、type ごとのコピペ（DRY 違反）、引数と分岐の多さ（KISS 違反）、未使用の xml・notify・future1・future2（YAGNI 違反）が1つの関数に同居しています。

    6.2 実践例：ユーザー登録機能

    3つの原則を組み合わせると、次のようになります。コメントの括弧に、その部分で効いている原則を書いています。

    // 設定（DRY）
const config = {
  MIN_PASSWORD_LENGTH: 8,
  EMAIL_REGEX: /^[^\s@]+@[^\s@]+\.[^\s@]+$/
};

// バリデーション（DRY + KISS）
function validateEmail(email) {
  if (!config.EMAIL_REGEX.test(email)) {
    throw new Error('Invalid email format');
  }
}

function validatePassword(password) {
  if (password.length < config.MIN_PASSWORD_LENGTH) {
    throw new Error(`Password must be at least ${config.MIN_PASSWORD_LENGTH} characters`);
  }
}

// ユーザー登録（KISS + YAGNI）
function registerUser(email, password) {
  validateEmail(email);
  validatePassword(password);

  // シンプルな実装（必要なものだけ）
  const user = {
    email,
    password: hashPassword(password),
    createdAt: new Date()
  };

  return saveUser(user);
}
    • DRY：パスワードの最小文字数やメールの形式は config の1か所だけに書き、エラーメッセージでも同じ値を使う
    • KISS：検証は1つの関数に1つのことだけ。登録処理は上から順に読める
    • YAGNI：ユーザーには今必要な email・password・createdAt だけを持たせる

    7.よくある誤解

    誤解1：「DRY だからといって何でもまとめる」

    たまたま見た目が似ているだけの2つの関数を無理にまとめると、逆にコードが複雑になります。同じ「意味」「目的」「責任」を持つコードだけをまとめる のが正しい DRY です。判断の基準は DRY・YAGNI の落とし穴と実践的判断 を見てください。

    誤解2：「KISS だから機能を削ってもよい」

    KISS は「実装 をシンプルに」という原則で、「要件 を削る」ことではありません。必要な機能は必要な分だけ作ります。

    誤解3：「YAGNI だから拡張性を考えなくてよい」

    後から変更しやすい 構造 を作ることと、今いらない 機能 を先回りで作ることは別物です。構造の柔軟性は大切ですが、未使用の機能は作らない。これが YAGNI です。

    8.まとめ

    DRY（Don't Repeat Yourself）

    • 重複を避ける
    • 変更は1箇所で済むようにする
    • ただし、過度な抽象化は避ける

    KISS（Keep It Simple, Stupid）

    • シンプルに保つ
    • 複雑さは敵
    • 早期リターンでネストを減らす

    YAGNI（You Aren't Gonna Need It）

    • 今必要ないものは作らない
    • 将来の予測に時間をかけない
    • 必要になったら追加する

    これらの原則を意識することで、保守しやすいコードが書けるようになります。次の一歩として、よくある問題の解決策の型である デザインパターン入門（44章）や、より体系的な設計原則である SOLID に進むとよいでしょう。

    関連：関心の分離、デメテルの法則、42 の テストとリファクタリング（リファクタリングの考え方）
