    10 汎用原則

    コードの重複と DRY 原則違反 — AI 生成コードに出がちな5つのパターン

    AI が生成するコードには、同じロジックが複数箇所に重複している場合があります。このページでは、Node.js（Express）の API を例に、バリデーション・データベースクエリ・エラーハンドリング・フォーマット処理・設定値 の5つの重複パターンを、問題のあるコードと正しい実装の対比で見ていきます。最後に、コードを書くときに使える DRY 原則チェックリストをまとめます。

    もとにしたノート：04_コードの重複とDRY原則違反

    ひとことで言うと

    同じコードが複数箇所にあると、修正のたびに全部を直す必要があり、直し忘れがバグになります。検証は validator に、DB 操作はモデルに、エラー処理はミドルウェアに、整形は utils に、設定値は config に と、役割ごとに1か所へ 共通化・集約 しましょう。ただし、意味の違うものまでまとめる過度な共通化は避けます。

    1.このページで扱うこと

    DRY（Don't Repeat Yourself） は、「同じことを繰り返すな」という原則です（定義と基本は DRY・KISS・YAGNI）。同じコードが複数箇所に存在すると、次のような問題が発生します。

    • 同じコードが複数箇所に存在
    • 関数やクラスの再利用がされていない
    • 修正時に複数箇所を変更する必要がある
    • バグが複数箇所に存在する可能性がある
    • コードの保守性が低下する

    このページでは、よく見かける重複を5つのパターンに分けて、それぞれの直し方を見ます。

    パターン重複しているもの集約先
    1. バリデーション入力値チェックvalidators/user_validator.js
    2. データベースクエリ同じ SELECT と「見つからない」処理models/User.js
    3. エラーハンドリングtry-catch の中身middleware/error_handler.js
    4. フォーマット処理価格の表示形式utils/formatter.js
    5. 設定値リトライ回数・タイムアウトconfig/constants.js

    例は Node.js の Web フレームワーク Express で書かれています。req はリクエスト（受け取った内容）、res はレスポンス（返す内容）、db.query はデータベースへの問い合わせです。

    2.バリデーションロジックの重複

    バリデーション は、受け取った入力値が正しい形かどうかを確かめる処理です。

    ✕ 問題のあるコード例：コードの重複 
    // controllers/user_controller.js
async function createUser(req, res) {
  const { name, email } = req.body;

  // ❌ バリデーションロジックが重複
  if (!name || name.trim() === '') {
    return res.status(400).json({ error: '名前が必要です' });
  }
  if (!email || !email.includes('@')) {
    return res.status(400).json({ error: '有効なメールアドレスが必要です' });
  }

  // ユーザー作成処理
  const result = await db.query(
    'INSERT INTO users (name, email) VALUES (?, ?)',
    [name, email]
  );

  res.status(201).json({ userId: result.insertId });
}

async function updateUser(req, res) {
  const { name, email } = req.body;

  // ❌ 同じバリデーションロジックが重複
  if (!name || name.trim() === '') {
    return res.status(400).json({ error: '名前が必要です' });
  }
  if (!email || !email.includes('@')) {
    return res.status(400).json({ error: '有効なメールアドレスが必要です' });
  }

  // ユーザー更新処理
  await db.query(
    'UPDATE users SET name = ?, email = ? WHERE id = ?',
    [name, email, req.params.id]
  );

  res.json({ success: true });
}

    問題点：

    • バリデーションロジックが2箇所に存在
    • バリデーションルールを変更する際、2箇所を修正する必要がある
    • バグが発生した場合、2箇所で修正が必要
    ◯ 正しい実装例：バリデーションロジックを共通化 
    // validators/user_validator.js
function validateUser(name, email) {
  const errors = [];

  if (!name || name.trim() === '') {
    errors.push('名前が必要です');
  }
  if (!email || !email.includes('@')) {
    errors.push('有効なメールアドレスが必要です');
  }

  return errors;
}

module.exports = { validateUser };
    ◯ 正しい実装例：共通のバリデーションを使用 
    // controllers/user_controller.js
const { validateUser } = require('../validators/user_validator');

async function createUser(req, res) {
  const { name, email } = req.body;

  // ✅ 共通のバリデーションを使用
  const errors = validateUser(name, email);
  if (errors.length > 0) {
    return res.status(400).json({ errors });
  }

  // ユーザー作成処理
  const result = await db.query(
    'INSERT INTO users (name, email) VALUES (?, ?)',
    [name, email]
  );

  res.status(201).json({ userId: result.insertId });
}

async function updateUser(req, res) {
  const { name, email } = req.body;

  // ✅ 共通のバリデーションを使用
  const errors = validateUser(name, email);
  if (errors.length > 0) {
    return res.status(400).json({ errors });
  }

  // ユーザー更新処理
  await db.query(
    'UPDATE users SET name = ?, email = ? WHERE id = ?',
    [name, email, req.params.id]
  );

  res.json({ success: true });
}

    エラーを最初の1つで返すのではなく配列に集めて返すので、利用者は名前とメールの両方の問題を一度に知ることができます。

    3.データベースクエリの重複

    ✕ 問題のあるコード例：データベースクエリが重複 
    // controllers/user_controller.js
async function getUserById(req, res) {
  const userId = req.params.id;
  const [users] = await db.query('SELECT * FROM users WHERE id = ?', [userId]);

  if (!users || users.length === 0) {
    return res.status(404).json({ error: 'ユーザーが見つかりません' });
  }

  res.json(users[0]);
}

async function updateUser(req, res) {
  const userId = req.params.id;
  // ❌ 同じクエリが重複
  const [users] = await db.query('SELECT * FROM users WHERE id = ?', [userId]);

  if (!users || users.length === 0) {
    return res.status(404).json({ error: 'ユーザーが見つかりません' });
  }

  // 更新処理
  // ...
}

async function deleteUser(req, res) {
  const userId = req.params.id;
  // ❌ 同じクエリが重複
  const [users] = await db.query('SELECT * FROM users WHERE id = ?', [userId]);

  if (!users || users.length === 0) {
    return res.status(404).json({ error: 'ユーザーが見つかりません' });
  }

  // 削除処理
  // ...
}

    テーブル名や「見つからないときの扱い」が変わると、3つの関数すべてを直す必要があります。

    ◯ 正しい実装例：データベース操作をモデルに集約 
    // models/User.js
class User {
  static async findById(id) {
    const [users] = await db.query('SELECT * FROM users WHERE id = ?', [id]);
    if (!users || users.length === 0) {
      return null;
    }
    return new User(users[0]);
  }

  static async findByIdOrFail(id) {
    const user = await User.findById(id);
    if (!user) {
      throw new Error('ユーザーが見つかりません');
    }
    return user;
  }
}

module.exports = User;
    ◯ 正しい実装例：モデルを使用 
    // controllers/user_controller.js
const User = require('../models/User');

async function getUserById(req, res) {
  try {
    const user = await User.findByIdOrFail(req.params.id);
    res.json(user);
  } catch (error) {
    res.status(404).json({ error: error.message });
  }
}

async function updateUser(req, res) {
  try {
    const user = await User.findByIdOrFail(req.params.id);
    // 更新処理
    // ...
  } catch (error) {
    res.status(404).json({ error: error.message });
  }
}

async function deleteUser(req, res) {
  try {
    const user = await User.findByIdOrFail(req.params.id);
    // 削除処理
    // ...
  } catch (error) {
    res.status(404).json({ error: error.message });
  }
}

    モデル（データとその読み書きをまとめたクラス）に「ID で1件探す」「見つからなければエラーにする」を集めたので、コントローラーは呼び出すだけになりました。名前の OrFail は「見つからなければ失敗（例外）にする」版であることを表しています。

    補足：catch で何でも 404 にしない

    この例の catch は、どんなエラーでも 404（見つからない）を返します。データベースに接続できないなど別の原因のエラーまで 404 になってしまうので、実際には「見つからない」専用のエラー（次の節の NotFoundError のようなもの）を投げ、その種類のときだけ 404 にするのが安全です。

    4.エラーハンドリングの重複

    ✕ 問題のあるコード例：エラーハンドリングが重複 
    async function createUser(req, res) {
  try {
    // 処理
  } catch (error) {
    console.error('エラー:', error);
    res.status(500).json({ error: 'エラーが発生しました' });
  }
}

async function updateUser(req, res) {
  try {
    // 処理
  } catch (error) {
    // ❌ 同じエラーハンドリングが重複
    console.error('エラー:', error);
    res.status(500).json({ error: 'エラーが発生しました' });
  }
}

    Express では、エラーを1か所で受け取る エラーハンドリングミドルウェア（リクエストの処理の途中に差し込む共通処理のうち、エラーを受け取る専用のもの。引数が4つ）を使えます。

    ◯ 正しい実装例：エラーハンドリングミドルウェアを定義 
    // middleware/error_handler.js
function errorHandler(error, req, res, next) {
  console.error('エラー:', error);

  if (error.name === 'ValidationError') {
    return res.status(400).json({ error: error.message });
  }

  if (error.name === 'NotFoundError') {
    return res.status(404).json({ error: error.message });
  }

  res.status(500).json({ error: 'エラーが発生しました' });
}

module.exports = errorHandler;
    ◯ 正しい実装例：エラーハンドリングミドルウェアを使用 
    // app.js
const errorHandler = require('./middleware/error_handler');

// ルート定義
app.use('/api/users', userRoutes);

// エラーハンドリングミドルウェア（最後に配置）
app.use(errorHandler);
    ◯ 正しい実装例：コントローラーはシンプルに 
    // controllers/user_controller.js
async function createUser(req, res, next) {
  try {
    // 処理
    res.status(201).json({ userId: result.insertId });
  } catch (error) {
    next(error); // エラーハンドリングミドルウェアに渡す
  }
}

    ログの出し方や、エラーの種類ごとのステータスコード（400・404・500）の決め方が1か所にまとまります。コントローラーは next(error) でエラーを渡すだけです。

    5.フォーマット処理の重複

    ✕ 問題のあるコード例：フォーマット処理が重複 
    // controllers/product_controller.js
async function getProduct(req, res) {
  const product = await db.query('SELECT * FROM products WHERE id = ?', [req.params.id]);

  // ❌ 価格のフォーマット処理が重複
  const formattedPrice = `¥${product.price.toLocaleString()}`;

  res.json({
    ...product,
    formattedPrice
  });
}

async function getProducts(req, res) {
  const products = await db.query('SELECT * FROM products');

  // ❌ 同じフォーマット処理が重複
  const formattedProducts = products.map(product => ({
    ...product,
    formattedPrice: `¥${product.price.toLocaleString()}`
  }));

  res.json(formattedProducts);
}

    「価格をどう表示するか」は1つの知識です。円記号の位置や桁区切りの形式を変えたくなったら、すべての箇所を探して直すことになります。

    ◯ 正しい実装例：フォーマット処理を共通化 
    // utils/formatter.js
function formatPrice(price) {
  return `¥${price.toLocaleString()}`;
}

function formatDate(date) {
  return new Date(date).toLocaleDateString('ja-JP');
}

module.exports = { formatPrice, formatDate };
    ◯ 正しい実装例：共通のフォーマット処理を使用 
    // controllers/product_controller.js
const { formatPrice } = require('../utils/formatter');

async function getProduct(req, res) {
  const product = await db.query('SELECT * FROM products WHERE id = ?', [req.params.id]);

  res.json({
    ...product,
    formattedPrice: formatPrice(product.price)
  });
}

async function getProducts(req, res) {
  const products = await db.query('SELECT * FROM products');

  const formattedProducts = products.map(product => ({
    ...product,
    formattedPrice: formatPrice(product.price)
  }));

  res.json(formattedProducts);
}

    6.設定値の重複

    ✕ 問題のあるコード例：設定値が重複 
    // services/email_service.js
const MAX_RETRY = 3;
const TIMEOUT = 5000;

async function sendEmail(email) {
  for (let i = 0; i < MAX_RETRY; i++) {
    try {
      await fetch(email.url, { timeout: TIMEOUT });
      return;
    } catch (error) {
      if (i === MAX_RETRY - 1) throw error;
    }
  }
}

// services/sms_service.js
// ❌ 同じ設定値が重複
const MAX_RETRY = 3;
const TIMEOUT = 5000;

async function sendSMS(phone) {
  for (let i = 0; i < MAX_RETRY; i++) {
    try {
      await fetch(phone.url, { timeout: TIMEOUT });
      return;
    } catch (error) {
      if (i === MAX_RETRY - 1) throw error;
    }
  }
}

    どちらのファイルにも定数はありますが、同じ値が別々のファイルに書かれている ので、片方だけ変えると食い違います。

    ◯ 正しい実装例：設定値を共通化 
    // config/constants.js
module.exports = {
  MAX_RETRY: 3,
  TIMEOUT: 5000,
  PAGE_SIZE: 20
};
    ◯ 正しい実装例：共通の設定値を使用 
    // services/email_service.js
const { MAX_RETRY, TIMEOUT } = require('../config/constants');

async function sendEmail(email) {
  for (let i = 0; i < MAX_RETRY; i++) {
    try {
      await fetch(email.url, { timeout: TIMEOUT });
      return;
    } catch (error) {
      if (i === MAX_RETRY - 1) throw error;
    }
  }
}

// services/sms_service.js
const { MAX_RETRY, TIMEOUT } = require('../config/constants');

async function sendSMS(phone) {
  for (let i = 0; i < MAX_RETRY; i++) {
    try {
      await fetch(phone.url, { timeout: TIMEOUT });
      return;
    } catch (error) {
      if (i === MAX_RETRY - 1) throw error;
    }
  }
}

    設定値は1か所になりました。さらに見ると、sendEmail と sendSMS の リトライ（失敗したらやり直す）のループ 自体も同じ形です。これも「失敗したら決まった回数までやり直す」という同じ知識なら、retry のような関数に共通化できます。ただし、メールと SMS でやり直し方が変わる見込みがあるなら分けておく、という判断もあります（DRY・YAGNI の落とし穴と実践的判断）。

    補足：fetch のタイムアウト

    標準の fetch には timeout オプションはありません。実際にタイムアウトさせるには { signal: AbortSignal.timeout(TIMEOUT) } のように AbortSignal を使います（MDN「AbortSignal.timeout()」）。この例の要点は「設定値を1か所にまとめる」ことです。

    7.DRY 原則チェックリスト

    コードを書く際（AI が生成したコードをレビューする際も）、次の点を確認しましょう。

    • □ 同じコードが複数箇所に存在していないか
    • □ 共通のロジックを関数やクラスに抽出できているか
    • □ 設定値が一箇所に集約されているか
    • □ エラーハンドリングが共通化されているか
    • □ バリデーションロジックが共通化されているか
    • □ データベース操作がモデルに集約されているか

    8.よくある誤解

    誤解1：「似ているコードは全部共通化すればよい」

    このページの例はどれも「同じ知識」（同じ検証ルール、同じ表示形式、同じ設定値）の重複です。見た目が似ていても 意味や変わる理由が違う コードは、無理に共通化すると片方の変更がもう片方に波及します。迷ったら 判断のチェックリスト で確かめます。

    誤解2：「定数にしてあれば DRY を守れている」

    設定値の例では、どちらのファイルも定数を使っていましたが、同じ値の定数が2つのファイルにある ことが重複でした。大事なのは名前を付けることではなく、その知識の置き場所が1か所であること です。

    誤解3：「共通化は関数を1つ作れば終わり」

    共通化した部品をどこに置くかも重要です。このページでは、検証は validators/、DB 操作は models/、エラー処理は middleware/、整形は utils/、設定は config/ と、役割ごとの置き場所 に集約しています。置き場所が決まっていないと、別の人が同じ関数をもう一度作ってしまいます。

    9.まとめ

    DRY 原則に従うことで、コードの保守性と品質を向上させることができます。次の点が重要です。

    1. 共通化：同じロジックを関数やクラスに抽出
    2. 集約：関連する処理を一箇所に集約
    3. 再利用：既存のコードを再利用
    4. 設定の一元化：設定値を一箇所で管理

    ただし、過度な共通化は避けることも重要です。適度な共通化を心がけましょう（判断の基準は DRY・YAGNI の落とし穴と実践的判断）。
