    60 思想・美徳

    UNIX 哲学 — 1つのことをうまくやる小さな道具を組み合わせる

    ターミナルで cat access.log | grep 404 | sort | uniq -c のようなコマンドを書いたことはあるでしょうか。小さなコマンドを |（パイプ：前のコマンドの出力を次のコマンドの入力に渡す仕組み）でつなぐだけで、ログ集計のような仕事がこなせてしまいます。この「小さな道具を組み合わせて大きな仕事をする」という作り方の背後にあるのが UNIX 哲学 です。UNIX を作った人たちが共有していた設計の姿勢で、OS に限らず、今のソフトウェア開発全般で参照され続けています。

    もとにしたノート：04_UNIX哲学

    ひとことで言うと

    「1つのことをうまくやる小さな道具を作り、それを組み合わせる」。道具同士は共通のインターフェース（UNIX ではテキスト）でつなぎ、早く試作して、ダメなら捨てて作り直します。

    1.このページで扱うこと

    1. 出典・背景：McIlroy（1978年）、Salus の3行要約（1994年）、Gancarz の9つの定理（1995年）、Raymond の17のルール（2003年）
    2. 中身の解説：共通する3本の柱と、コードへの置き換え
    3. 他の原則との関係：KISS・関心の分離・高凝集低結合・SRP・Worse is Better
    4. 現代の開発での活かし方 と よくある誤解

    2.出典・背景

    UNIX 哲学には「公式の条文」はありません。何人もの人が、それぞれの言葉でまとめています。代表的なものを挙げます。

    2.1 Doug McIlroy（1978年）

    パイプの発案者である Doug McIlroy が、Bell System Technical Journal の UNIX 特集号（1978年）の序文で書いたものが最も有名です。

    1. 1つのプログラムには1つのことをうまくやらせる。 新しい仕事をするときは、古いプログラムに機能を足して複雑にするのではなく、新しく作る
    2. すべてのプログラムの出力が、まだ知らない別のプログラムの入力になることを想定する。 余計な出力で汚さない
    3. 早く試せるように設計・構築する（OS でさえ数週間で）。出来の悪い部分はためらわず捨てて作り直す
    4. 人手の作業より道具を使う。 道具を作るために回り道をしてでも

    後に Peter Salus が『A Quarter Century of UNIX』（1994年）で次の3行に要約し、こちらもよく引用されます。

    Salus の3行要約

    • 1つのことを行い、それをうまくやるプログラムを書け
    • 協調して動くプログラムを書け
    • テキストストリームを扱うプログラムを書け。それが普遍的なインターフェースだからだ

    2.2 Mike Gancarz『UNIXという考え方』（The UNIX Philosophy, 1995年）

    UNIX 哲学を9つの定理として整理した本です。

    #定理
    1スモール・イズ・ビューティフル
    21つのプログラムには1つのことをうまくやらせる
    3できるだけ早く試作する
    4効率より移植性を優先する
    5数値データは ASCII フラットファイルに保存する
    6ソフトウェアの梃子（てこ）を有効に活用する（再利用・既存の道具を使う）
    7シェルスクリプトを使って梃子の効果と移植性を高める
    8過度の対話的インターフェースを避ける
    9すべてのプログラムをフィルタとして設計する

    2.3 Eric S. Raymond『The Art of UNIX Programming』（2003年）

    「モジュール性のルール」「明確性のルール」「沈黙のルール（言うべきことがなければ何も言うな）」など、17のルールにまとめています。

    3.中身の解説：共通する3本の柱

    いろいろなまとめ方がありますが、共通する柱は次の3つです。

    1. 小さく、1つのことをうまくやる

    grep は「行を探す」だけ、sort は「並べる」だけ、wc は「数える」だけ。1つの道具が1つの仕事に集中しているので、使い方が覚えやすく、バグも入りにくくなります。

    2. 組み合わせられるようにする

    どの道具も 標準入力から読み、標準出力に書く という共通のルールを守っています。だから、作った人が想定していなかった組み合わせでも動きます。

    3. テキストを共通のインターフェースにする

    道具同士が「ただのテキスト（行の並び）」でやりとりするので、特別な変換なしにつなげられます。人間が目で読んで確認できるのも利点です。

    3.1 パイプで組み合わせる例

    # アクセスログから、404 を返した URL の上位 5 件を出す
grep ' 404 ' access.log | awk '{print $7}' | sort | uniq -c | sort -rn | head -5

    6つの道具はどれも「404 の集計」のために作られたわけではありません。それでも組み合わせるだけで目的が達成できます。

    3.2 コードに置き換えると

    プログラムの関数でも同じ考え方が使えます。

    ✕ 悪い例：1つの関数が「読む・絞る・数える・整形する」を全部やる 
    function report404(lines) { /* 全部入り */ }
    ◯ 良い例：小さな関数を組み合わせる 
    const is404 = (line) => line.includes(' 404 ');
const toUrl = (line) => line.split(' ')[6];
const countBy = (items) =>
  items.reduce((m, x) => m.set(x, (m.get(x) ?? 0) + 1), new Map());

const result = countBy(lines.filter(is404).map(toUrl));

    is404 や countBy は、別の集計でもそのまま再利用できます。

    4.他の原則との関係

    原則UNIX 哲学との関係
    KISS「スモール・イズ・ビューティフル」はほぼ同じ主張。複雑な万能ツールより単純な道具を選ぶ
    関心の分離「1つのことをうまくやる」は、道具ごとに関心を分けることそのもの
    高凝集・低結合道具の中身は1つの仕事に集中（高凝集）、道具同士はテキストだけでつながる（低結合）
    SRP（単一責任の原則）1つのプログラム＝1つの責任、という発想がクラス単位に降りてきたものと見ることができる
    Worse is BetterUNIX と C の「単純な実装を優先する」文化を説明した論考

    5.現代の開発での活かし方

    • CLI ツールを作るとき：標準入力・標準出力を使い、成功時は余計なメッセージを出さない（沈黙のルール）。他のツールとパイプでつなげるようにする
    • 関数・モジュールの設計：「全部入りの関数」より、小さな関数を合成する。関数型プログラミングの map / filter / reduce は、パイプとよく似た考え方（関数型の基本は 関数型と純粋関数（42章））
    • マイクロサービス：「1つのサービスは1つの仕事」「共通のインターフェース（HTTP / JSON）でつなぐ」は、UNIX 哲学をサービス単位に当てはめたものとよく言われる（モノリスとマイクロサービス（41章））
    • データ形式：JSON Lines や CSV のように、行単位で扱えるテキスト形式を選ぶと、既存の道具（jq, grep など）がそのまま使える

    6.よくある誤解

    誤解1：「小さければ小さいほど良い」

    細かく分けすぎると、つなぎ合わせる手間やつなぎ目のバグが増えます。「1つのこと」の大きさは、それ単体で意味がある仕事 かどうかで決めます。関心の分離 の「分けすぎ」と同じ注意が必要です。

    誤解2：「テキストでないといけない」

    テキストは UNIX の時代に最も普遍的だった形式、というのが本来の意味です。大事なのは みんなが合意した共通のインターフェース でつなぐことで、今なら JSON や HTTP がその役割を担うこともあります。

    誤解3：「古い OS の話で、今は関係ない」

    Linux・macOS のコマンドはもちろん、Git やコンテナのツール群、関数型の書き方、マイクロサービスなど、今の道具や設計の多くにこの考え方が生きています。

    7.まとめ

    • 1つのことをうまくやる 小さな道具を作る
    • 道具は 組み合わせられる ように作る（共通のインターフェースでつなぐ）
    • 早く試作し、ダメなら捨てて作り直す
    • KISS・関心の分離・高凝集低結合と根っこは同じ
