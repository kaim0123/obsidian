    20 構造の原則

    関心の分離 — 違うことは違う場所に書く

    「いろんなことが 1 か所にまとまっていて、何が本題か分からない…」というコードを解きほぐすのが 関心の分離（Separation of Concerns, SoC） です。このページでは「関心」とは何か、なぜ分けるのか、どんな軸で分けるのか、SOLID の単一責任の原則との関係、そして分けすぎの落とし穴までを、ユーザー登録の例で学びます。

    もとにしたノート：01_関心の分離

    ひとことで言うと

    「違うことは違う場所に書く」 という原則です。表示・検証・保存・通知のように 目的の違う処理を混ぜずに分ける と、読みやすく、差し替えやテストもしやすくなります。目安は 「別々の理由で変更される部分は分け、同じ理由で変更される部分はまとめる」 です。

    1.このページで扱うこと

    プログラムを読み書きしていると、「いろんなことが 1 つの場所にまとまっていて、何が本題か分からない…」と感じることがあります。これを解決するのが 関心の分離（Separation of Concerns, SoC） という考え方です。一言でいうと 「違うことは違う場所に書く」 という原則です。

    • 「関心」とは何か
    • なぜ分けるのか — 詰め込んだ関数と分けた関数の比較
    • 関心を分ける主な軸（レイヤー・機能・横断的関心事）
    • SOLID（単一責任の原則）との関係
    • 分けすぎ（過剰分離）への注意
    • 実例：Web アプリでの関心の置き場所

    アーキテクチャ全体での考え方は 42 の「関心の分離」、メソッド単位での適用は 46 の「関心の分離と単一責任」でも扱っています。このページは原則そのものの定義と考え方をまとめます。

    2.「関心」とは何か

    ここでいう 「関心（Concern）」 とは、ソフトウェアが担っている 1 つの役割・目的・責任 のことです。

    たとえば、ユーザー登録の画面を作るとき、内部で行っていることは次のように複数あります。

    やっていること関心
    画面の見た目を描画する表示の関心
    ユーザーが入力した値をチェックする検証の関心
    データベースに保存する永続化の関心（永続化＝データを消えない場所に残すこと）
    確認メールを送る通知の関心

    これらは「ユーザー登録」という 1 つの流れの中にありますが、それぞれ 目的がまったく違います。こうした異なる目的を混ぜずに分けて書く、というのが「関心の分離」です。

    3.なぜ分けるのか

    3.1 悪い例：何もかも詰め込んだ関数

    ✕ 悪い例：1 つの関数に 6 つの関心が詰まっている 
    function registerUser(name, email, password) {
  // HTMLを生成（表示の関心）
  const html = `<div>登録中: ${name}</div>`;
  document.body.innerHTML = html;

  // 入力チェック（検証の関心）
  if (!email.includes('@')) {
    alert('メール形式が不正');
    return;
  }

  // パスワード暗号化（セキュリティの関心）
  const hashed = btoa(password);

  // DBに保存（永続化の関心）
  const db = new Database();
  db.query(`INSERT INTO users VALUES ('${name}', '${email}', '${hashed}')`);

  // メール送信（通知の関心）
  sendMail(email, '登録完了しました');

  // アクセスログ記録（監査の関心）
  console.log(`${new Date()} ${name} 登録`);
}

    1 つの関数に 6 つの関心が詰まっています。問題は次のとおりです。

    • メール送信だけ直したい のに、関数全体を読む必要がある
    • DB を別の種類に変更したい のに、画面コードまで影響してしまう
    • テストが書きにくい（DB もメールも同時に動かす必要がある）
    • 誰かが似た処理を別のところでコピペして コード重複が生まれる

    この悪い例はセキュリティ面でも危険です

    関心の話とは別に、btoa は Base64 という ただの符号化 で、暗号化でもハッシュ化でもありません（誰でも元に戻せます）。また、入力値を文字列のまま SQL に埋め込むと SQL インジェクション の原因になります。詳しくは 72 の「SQL インジェクション」や 71 の「インジェクションと暗号化の不備」を参照してください。

    3.2 良い例：分けて書く

    ◯ 良い例：関心ごとに関数を分け、流れの関数で組み合わせる 
    // 検証の関心
function validate(email) {
  if (!email.includes('@')) throw new Error('メール形式が不正');
}

// セキュリティの関心
function hashPassword(password) {
  return bcrypt.hash(password);
}

// 永続化の関心
function saveUser(user) {
  return db.users.insert(user);
}

// 通知の関心
function sendWelcomeMail(email) {
  return mailer.send(email, '登録完了しました');
}

// これらを組み合わせる「流れ」の関心
async function registerUser({ name, email, password }) {
  validate(email);
  const hashed = await hashPassword(password);
  await saveUser({ name, email, password: hashed });
  await sendWelcomeMail(email);
}

    それぞれの関数は 1 つのことだけ をするので、理解しやすく、差し替えやテストもしやすくなります。「組み合わせる流れ」そのものも 1 つの関心として独立した関数になっている点に注目してください。

    4.関心を分ける主な軸

    4.1 レイヤー（階層）で分ける

    よく使われる分け方です。

    層担う関心
    プレゼンテーション層画面・UI の関心
    アプリケーション層業務の流れ（ユースケース＝利用者がシステムで行う一連の操作）
    ドメイン層ビジネスルール
    インフラ層DB・外部 API などの関心

    → 詳しくは 41 の「層化・三層・レイヤード」

    4.2 機能（モジュール）で分ける

    「ユーザー機能」「注文機能」「商品機能」のように、業務の単位で分けます。モジュール単位での分け方は 43 の「機能別とレイヤー別」も参照してください。

    4.3 横断的関心事（Cross-Cutting Concern）で分ける

    ログ出力・例外処理・トランザクション・認証などは、どの機能でも必要 なので、専用の仕組み（ミドルウェア、アスペクト指向など）にまとめます。横断的関心事 とは、このように多くの機能にまたがって必要になる関心のことです。ミドルウェア は本処理の前後に共通処理を差し込む仕組み、アスペクト指向（AOP） は共通処理を本処理のコードに書かずに外から織り込む考え方です。

    → 41 の「横断的関心事と認証認可」

    5.SOLID との関係

    関心の分離は、SOLID 原則の SRP（単一責任の原則） と深く関係しています。

    関心の分離

    全体を設計する際の 大方針

    SRP

    個々のクラスに対する 具体的なガイドライン

    どちらも根は同じで、「1 つのものに複数の役割を持たせない」という思想です。SRP については「単一責任の原則」で詳しく扱います。

    6.分けすぎにも注意

    関心の分離は大切ですが、何でも細かく分ければよい、というわけではありません。

    • 関数が 1 行だけのファイルが 100 個ある
    • 読むために 10 個のファイルを行き来しないといけない

    これは 過剰分離 で、かえって読みにくくなります。

    分けるかどうかの目安

    「別々の理由で変更される部分は分ける」「同じ理由で変更される部分はまとめる」

    7.実例：Web アプリでの関心の分離

    関心置き場所（例）
    画面の見た目HTML/CSS, React コンポーネント
    画面の操作JavaScript, イベントハンドラ
    業務ルールService / UseCase / ドメイン層
    データ保存Repository / DAO / Model
    外部 API 連携Adapter / Gateway
    認証・認可ミドルウェア
    ログロガー / AOP

    この表のように 「どこに何を書くか」が揃っている だけで、チーム全体のコードが劇的に読みやすくなります。

    8.よくある誤解

    誤解1：「細かく分ければ分けるほど良い設計になる」

    1 行だけの関数ファイルが 100 個ある、読むために 10 個のファイルを行き来する、という状態は 過剰分離 で、かえって読みにくくなります。分ける基準は「細かさ」ではなく 変更される理由が別かどうか です。

    誤解2：「1 つの流れ（ユーザー登録など）は 1 つの関数にまとめるべき」

    「ユーザー登録」という 1 つの流れの中にも、表示・検証・永続化・通知といった 目的の違う関心 が含まれています。流れをまとめる関数は残しつつ、中身の各関心は別の場所に書くのが関心の分離です。

    誤解3：「関心の分離と SRP は別物なので、片方だけ知っていればよい」

    関心の分離は全体設計の大方針、SRP は個々のクラスへの具体的なガイドラインで、根は同じ「1 つのものに複数の役割を持たせない」という思想です。設計の粒度に応じて両方を使い分けます。

    9.まとめ

    • 関心とは、ソフトウェアが担う 1 つの役割・目的・責任のこと
    • 目的の違う処理を 1 か所に詰め込むと、修正・差し替え・テストが難しくなり、重複も生まれる
    • 分ける軸は、レイヤー・機能（モジュール）・横断的関心事の 3 つが代表的
    • SRP は関心の分離をクラスに当てはめた具体形
    • 分けすぎは逆効果。「別々の理由で変わるものは分け、同じ理由で変わるものはまとめる」
