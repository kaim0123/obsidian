    30 オブジェクト指向の原則

    依存性逆転の原則（DIP） — 詳細ではなく抽象に依存する

    SOLID 原則の最後、依存性逆転の原則（Dependency Inversion Principle, DIP） を学びます。ビジネスロジックがデータベースなどの「実装の詳細」に直接ぶら下がるのをやめ、間に 抽象（インターフェース） を挟んで依存の向きをひっくり返す考え方です。DIP を実現する技術である 依存性注入（DI） の 3 つのやり方、DI コンテナとファクトリー、テストでの活用までを扱います。

    もとにしたノート：05_DIP (依存性逆転の原則)

    ひとことで言うと

    大事なロジック（高レベル）が、交換されうる技術（低レベル）を 直接 new しない ようにする原則です。両者の間に抽象（インターフェース）を置き、高レベル → 抽象 ← 低レベル の形にします。具体的な実装は外から渡す（依存性注入）ので、データベースを替えても、テストでモックに差し替えても、ロジック側は変わりません。

    • 実装パターン — DI コンテナ、ファクトリー

    アーキテクチャ全体での DIP（なぜ「逆転」と呼ぶのか、インターフェースをどこに置くか、クリーンアーキテクチャとの関係）は 41 章の「依存性逆転の原則」で詳しく扱っています。このページは原則の定義とコードレベルの基本形が中心です。

    2.DIP とは

    Dependency Inversion Principle（DIP） は、SOLID 原則 の最後の原則です。

    「高レベルのモジュールは低レベルのモジュールに依存すべきではない。両方とも抽象（インターフェース）に依存すべきである」

    つまり：

    用語意味
    高レベルのモジュールビジネスロジックなど、アプリケーションの核心部分
    低レベルのモジュールデータベース、ファイルシステム、外部 API など、実装の詳細
    抽象（インターフェース）両者をつなぐ契約

    依存の方向を逆転させる ことで、高レベルのモジュールが低レベルのモジュールの実装詳細に依存しないようにします。ここでいう「A が B に 依存する」とは、「A のコードが B の名前を知っていて、B が変わると A も直す必要が出る」関係のことです。

    3.なぜ重要なのか

    問題点（高レベルが低レベルに直接依存すると）

    • 結合度が高い — 実装の詳細に強く結びついている
    • テストが困難 — 実際のデータベースや外部サービスが必要
    • 変更に弱い — 低レベルの実装を変更すると、高レベルのコードも変更が必要
    • 再利用性が低い — 高レベルのロジックを他の環境で使えない

    メリット（抽象に依存すると）

    • 疎結合 — 実装の詳細から独立している
    • テストしやすい — モックやスタブを使いやすい
    • 変更に強い — 低レベルの実装を変更しても、高レベルのコードは変更不要
    • 再利用性が高い — 高レベルのロジックを他の環境でも使える

    結合度 は部品どうしの結びつきの強さ、疎結合 はその結びつきが弱い状態です（43 章「結合度」）。モック・スタブ は、テストのときに本物の代わりに使う偽物の部品です。

    4.悪い例 — 低レベルへの直接依存

    4.1 例1：高レベルのモジュールが低レベルのモジュールに直接依存

    ✕ 悪い例：UserService が MySQLDatabase を直接 new している 
    // ❌ 悪い例: 高レベルのモジュールが低レベルのモジュールに直接依存

// 低レベルのモジュール（実装の詳細）
class MySQLDatabase {
  connect() {
    console.log('Connecting to MySQL database...');
  }

  query(sql) {
    console.log(`Executing query: ${sql}`);
    return [{ id: 1, name: 'John' }];
  }

  disconnect() {
    console.log('Disconnecting from MySQL database...');
  }
}

// 高レベルのモジュール（ビジネスロジック）
class UserService {
  constructor() {
    // 直接MySQLDatabaseに依存している ❌
    this.database = new MySQLDatabase();
  }

  getUser(id) {
    this.database.connect();
    const result = this.database.query(`SELECT * FROM users WHERE id = ${id}`);
    this.database.disconnect();
    return result[0];
  }
}

// 問題点:
// 1. UserServiceがMySQLDatabaseに直接依存している
// 2. データベースをPostgreSQLに変更する場合、UserServiceも変更が必要
// 3. テストするために実際のMySQLデータベースが必要
// 4. UserServiceを他の環境で使えない

    問題点:

    • UserService が MySQLDatabase に直接依存している
    • データベースを変更する場合、UserService も変更が必要
    • テストが困難（実際のデータベースが必要）

    注意：SQL の組み立て方

    このページのコードは DIP の説明に集中するため、`SELECT * FROM users WHERE id = ${id}` のように値を SQL 文字列へ直接埋め込んでいます。実際のコードでこう書くと SQL インジェクション（入力値で SQL を書き換えられる攻撃）の原因になります。実務ではプレースホルダ（? などの穴に値を別途渡す仕組み）を使ってください（72 章「SQL インジェクション」）。

    5.良い例 — 抽象（インターフェース）に依存する

    ◯ 良い例：UserService は Database（抽象）だけを知り、実装は外から受け取る 
    // ✅ 良い例: 抽象（インターフェース）に依存

// 抽象（インターフェース）を定義
class Database {
  connect() {
    throw new Error('connect must be implemented');
  }

  query(sql) {
    throw new Error('query must be implemented');
  }

  disconnect() {
    throw new Error('disconnect must be implemented');
  }
}

// 低レベルのモジュール（実装の詳細）
class MySQLDatabase extends Database {
  connect() {
    console.log('Connecting to MySQL database...');
  }

  query(sql) {
    console.log(`Executing query: ${sql}`);
    return [{ id: 1, name: 'John' }];
  }

  disconnect() {
    console.log('Disconnecting from MySQL database...');
  }
}

class PostgreSQLDatabase extends Database {
  connect() {
    console.log('Connecting to PostgreSQL database...');
  }

  query(sql) {
    console.log(`Executing query: ${sql}`);
    return [{ id: 1, name: 'John' }];
  }

  disconnect() {
    console.log('Disconnecting from PostgreSQL database...');
  }
}

// 高レベルのモジュール（ビジネスロジック）
class UserService {
  constructor(database) {
    // 抽象（Databaseインターフェース）に依存している ✅
    this.database = database;
  }

  getUser(id) {
    this.database.connect();
    const result = this.database.query(`SELECT * FROM users WHERE id = ${id}`);
    this.database.disconnect();
    return result[0];
  }
}

// 使用例
const mysqlDb = new MySQLDatabase();
const userService1 = new UserService(mysqlDb);
userService1.getUser(1);

// データベースを変更しても、UserServiceは変更不要 ✅
const postgresDb = new PostgreSQLDatabase();
const userService2 = new UserService(postgresDb);
userService2.getUser(1);

    メリット:

    • UserService が抽象（Database インターフェース）に依存している
    • データベースを変更しても、UserService は変更不要
    • テスト時にモックデータベースを使える

    なぜ「逆転」と呼ぶのか、抽象を高レベル側（使う側）に置く理由は 41 章の「依存性逆転の原則」で図とともに説明しています。

    6.実践的な例

    6.1 例2：依存性注入（Dependency Injection）

    依存性注入（DI） とは、クラスが使う部品を自分で new せず、外から渡してもらう ことです。DIP を実現するための代表的なテクニックです。

    ✕ 悪い例：内部でインスタンスを作成 
    // ❌ 悪い例: 内部でインスタンスを作成
class EmailService {
  constructor() {
    // 直接SMTPSenderに依存している ❌
    this.sender = new SMTPSender();
  }

  sendEmail(to, subject, body) {
    this.sender.send(to, subject, body);
  }
}

class SMTPSender {
  send(to, subject, body) {
    console.log(`Sending email via SMTP to ${to}: ${subject}`);
  }
}
    ◯ 良い例：依存性を注入する 
    // ✅ 良い例: 依存性を注入する
class EmailSender {
  send(to, subject, body) {
    throw new Error('send must be implemented');
  }
}

class SMTPSender extends EmailSender {
  send(to, subject, body) {
    console.log(`Sending email via SMTP to ${to}: ${subject}`);
  }
}

class SendGridSender extends EmailSender {
  send(to, subject, body) {
    console.log(`Sending email via SendGrid to ${to}: ${subject}`);
  }
}

class EmailService {
  constructor(sender) {
    // 抽象（EmailSenderインターフェース）に依存している ✅
    // 依存性を外部から注入（Dependency Injection）
    this.sender = sender;
  }

  sendEmail(to, subject, body) {
    this.sender.send(to, subject, body);
  }
}

// 使用例
const smtpSender = new SMTPSender();
const emailService1 = new EmailService(smtpSender);
emailService1.sendEmail('user@example.com', 'Hello', 'Hello World');

// 送信方法を変更しても、EmailServiceは変更不要 ✅
const sendGridSender = new SendGridSender();
const emailService2 = new EmailService(sendGridSender);
emailService2.sendEmail('user@example.com', 'Hello', 'Hello World');

    6.2 例3：テストでの活用

    抽象に依存していれば、テストのときだけ本物のデータベースの代わりに モック を渡せます。

    ◯ 良い例：テストでモックを使える 
    // ✅ 良い例: テストでモックを使える

// 抽象（インターフェース）
class UserRepository {
  findById(id) {
    throw new Error('findById must be implemented');
  }

  save(user) {
    throw new Error('save must be implemented');
  }
}

// 実装（低レベルのモジュール）
class DatabaseUserRepository extends UserRepository {
  constructor(database) {
    super();
    this.database = database;
  }

  findById(id) {
    // データベースから取得
    return this.database.query(`SELECT * FROM users WHERE id = ${id}`);
  }

  save(user) {
    // データベースに保存
    this.database.query(`INSERT INTO users ...`);
  }
}

// 高レベルのモジュール
class UserService {
  constructor(userRepository) {
    // 抽象（UserRepositoryインターフェース）に依存している ✅
    this.userRepository = userRepository;
  }

  getUser(id) {
    return this.userRepository.findById(id);
  }

  createUser(userData) {
    const user = { ...userData, id: Date.now() };
    this.userRepository.save(user);
    return user;
  }
}

// テスト用のモック（低レベルのモジュール）
class MockUserRepository extends UserRepository {
  constructor() {
    super();
    this.users = [];
  }

  findById(id) {
    return this.users.find(u => u.id === id);
  }

  save(user) {
    this.users.push(user);
  }
}

// テスト
describe('UserService', () => {
  it('should get user by id', () => {
    // 実際のデータベースは不要 ✅
    const mockRepo = new MockUserRepository();
    mockRepo.save({ id: 1, name: 'John' });

    const userService = new UserService(mockRepo);
    const user = userService.getUser(1);

    expect(user.name).toBe('John');
  });
});

    UserRepository のように「ユーザーを探す・保存する」という 業務の言葉 で書かれた抽象は、SQL や接続の手順を知りません。高レベル側が必要とする形で抽象を作ると、DIP の効果が大きくなります（11. よくある誤解 の誤解1も参照）。

    7.依存性注入のパターン

    パターン渡し方
    1. コンストラクタインジェクション生成時にコンストラクタの引数で渡す
    2. セッターインジェクション生成後にセッターメソッドで渡す
    3. インターフェースインジェクションメソッドの引数で渡す

    7.1 コンストラクタインジェクション

    // コンストラクタで依存性を注入
class Service {
  constructor(dependency) {
    this.dependency = dependency;
  }
}

const dependency = new Dependency();
const service = new Service(dependency);

    7.2 セッターインジェクション

    // セッターメソッドで依存性を注入
class Service {
  setDependency(dependency) {
    this.dependency = dependency;
  }
}

const service = new Service();
service.setDependency(new Dependency());

    7.3 インターフェースインジェクション

    // メソッドの引数で依存性を注入
class Service {
  doSomething(dependency) {
    dependency.method();
  }
}

const service = new Service();
service.doSomething(new Dependency());

    ※ メソッドの引数で渡すこの形は、一般には メソッドインジェクション とも呼ばれます。Martin Fowler の記事（参考資料）でいう「インターフェースインジェクション」は、注入を受けるための専用インターフェース（例：injectFinder() を持つ）をクラスに実装させる別の方式を指すので、資料を読むときは注意してください。

    8.実装パターン

    8.1 依存性注入コンテナ（DI Container）

    DI コンテナ は、「どのクラスにどの部品を渡すか」を登録しておき、必要なときに組み立てて渡してくれる仕組みです。

    // シンプルなDIコンテナの例
class DIContainer {
  constructor() {
    this.services = {};
  }

  register(name, factory) {
    this.services[name] = factory;
  }

  resolve(name) {
    const factory = this.services[name];
    if (!factory) {
      throw new Error(`Service ${name} not found`);
    }
    return factory(this);
  }
}

// 使用例
const container = new DIContainer();

container.register('database', () => new MySQLDatabase());
container.register('userRepository', (container) => {
  return new DatabaseUserRepository(container.resolve('database'));
});
container.register('userService', (container) => {
  return new UserService(container.resolve('userRepository'));
});

const userService = container.resolve('userService');

    8.2 ファクトリーパターン

    ファクトリー は、オブジェクトの組み立て方を 1 か所にまとめた「工場」役のクラスや関数です。

    // ファクトリーで依存性を管理
class UserServiceFactory {
  static create(databaseType = 'mysql') {
    let database;
    if (databaseType === 'mysql') {
      database = new MySQLDatabase();
    } else if (databaseType === 'postgresql') {
      database = new PostgreSQLDatabase();
    }

    const userRepository = new DatabaseUserRepository(database);
    return new UserService(userRepository);
  }
}

// 使用例
const userService = UserServiceFactory.create('mysql');

    DI コンテナやファクトリーのように「組み立てを 1 か所に集める」考え方（Composition Root）は、41 章の「DI・IoC・Composition Root」で詳しく扱っています。

    11.よくある誤解

    ノートの「よくある間違い」をもとにしています。

    誤解1：「インターフェースを 1 枚挟めば、中身は MySQL 専用でもよい」
    ✕ 悪い例：抽象が具体的すぎる 
    // ❌ 悪い例: 抽象が具体的すぎる
class MySQLDatabaseInterface {
  connectToMySQL() { }  // MySQL固有のメソッド
  queryMySQL(sql) { }   // MySQL固有のメソッド
}
    ◯ 良い例：抽象は一般的に 
    // ✅ 良い例: 抽象は一般的に
class Database {
  connect() { }
  query(sql) { }
}

    抽象に特定の技術の名前や手順が出てくると、技術を替えたときに抽象ごと作り直すことになり、DIP の意味がなくなります。

    誤解2：「引数で受け取れるようにしたが、中で new してもかまわない」
    ✕ 悪い例：内部でインスタンスを作成 
    // ❌ 悪い例: 内部でインスタンスを作成
class Service {
  constructor() {
    this.dependency = new ConcreteDependency();  // ❌
  }
}
    ◯ 良い例：外部から注入 
    // ✅ 良い例: 外部から注入
class Service {
  constructor(dependency) {
    this.dependency = dependency;  // ✅
  }
}

    クラスの中で具体クラスを new した時点で、そのクラスは具体クラスに依存します。インスタンスを作るのは外側（DI コンテナやファクトリー、アプリの起動処理）の仕事です。

    誤解3：「DIP のために、すべてのクラスに最初からインターフェースを用意する」

    ノートの「抽象化のタイミング」にあるとおり、最初から抽象化する必要はありません。データベースや外部 API のように「替わりうる・テストで差し替えたい」低レベルの部品に対して、必要になったときに抽象化します。使わない抽象は、読む人の負担を増やすだけです。

    12.まとめ

    12.1 重要なポイント

    1. 高レベルのモジュールは抽象に依存 — 実装の詳細に依存しない
    2. 低レベルのモジュールも抽象に依存 — インターフェースを実装する
    3. 依存性を注入する — 外部から依存性を提供する
    4. テストしやすくする — モックやスタブを使いやすくする

    12.2 チェックリスト

    • ☐ 高レベルのモジュールが低レベルのモジュールに直接依存していないか？
    • ☐ 抽象（インターフェース）を定義しているか？
    • ☐ 依存性を外部から注入しているか？
    • ☐ テストでモックを使えるか？
