    60 思想・美徳

    Worse is Better — 完璧さより単純さが先に広まる

    「完璧に正しく作られたソフトウェア」と「ところどころ雑だけれど、シンプルですぐ使えるソフトウェア」。広く使われるようになるのはどちらでしょうか。直感的には前者に思えますが、歴史を振り返ると、勝ち残ったのは後者であることが少なくありません。この逆説を言い表したのが Worse is Better（悪いほうが良い） という考え方です。

    もとにしたノート：05_Worse_is_Better

    ひとことで言うと

    「完璧さより単純さ。単純で 50% の出来のものが先に広まり、そのあと育っていく」。ただし手抜きの言い訳ではなく、何を優先するかのトレードオフ の話です。

    1.このページで扱うこと

    1. 出典・背景：Richard P. Gabriel の論考と、本人による揺れ
    2. 2つの設計スタイル：The Right Thing（MIT / Stanford 流）と Worse is Better（New Jersey 流）
    3. 有名な例：PC 失敗（PC loser-ing）問題と EINTR
    4. なぜ「悪いほう」が勝つのか
    5. 現代の開発での活かし方 と よくある誤解

    2.出典・背景

    2.1 Richard P. Gabriel の論考

    提唱者は Lisp の研究者・実装者だった Richard P. Gabriel です。1989年に書いた講演原稿「Lisp: Good News, Bad News, How to Win Big」の中の一節で、「Worse is Better」という言葉を使いました。この節が1991年ごろに Jamie Zawinski によって抜き出されて広まり、独立した論考として知られるようになりました。

    Gabriel が問題にしていたのは、「なぜ設計として優れた Lisp ではなく、UNIX と C が広まったのか」 という疑問です。

    2.2 その後の揺れ

    Gabriel 自身は、その後「Worse is Better は本当に良いのか」を何度も考え直しています。ペンネーム（Nickieben Bourbaki）で反論「Worse is Better is Worse」を書いたこともあり、本人の中でも結論が出ていない 問いかけ として読むのがよいでしょう。

    3.2つの設計スタイル

    Gabriel は、設計の価値観を次の2つに分けて比べました。

    観点The Right Thing（MIT / Stanford 流）Worse is Better（New Jersey 流）
    単純さインターフェース（使う側）の単純さを最優先。実装は複雑でもよい実装の単純さ を最優先。インターフェースが多少複雑になってもよい
    正しさあらゆる面で正しくなければならない正しいほうがよいが、単純さのためなら少し譲る
    一貫性一貫性を崩してはならない単純さのためなら一貫性を少し譲る
    完全性想定される状況をすべてカバーするカバーしたいが、単純さのためなら削る
    代表例Lisp マシン、Common LispUNIX、C

    「New Jersey 流」という呼び名は、UNIX と C を生んだ Bell 研究所がニュージャージー州にあったことに由来します。

    3.1 有名な例：PC 失敗（PC loser-ing）問題

    論考では、システムコール（プログラムが OS に仕事を頼む呼び出し）の途中で割り込みが入ったときの扱いが例に挙がっています。

    MIT 流（ITS という OS）

    OS 側がきちんと状態を戻して、ユーザーのプログラムからは何も起きなかったように見せる。使う側は楽だが、OS の実装は複雑。

    New Jersey 流（UNIX）

    OS は「失敗した」というエラーを返すだけ。やり直しは呼び出す側のプログラムの責任 にする。使う側は面倒だが、OS の実装は単純。

    今でも UNIX 系 OS のシステムコールが EINTR（割り込みで中断された）を返し、呼び出し側がリトライするのは、この設計の名残です。

    // 呼び出し側が「中断されたらやり直す」を書く必要がある
ssize_t n;
do {
    n = read(fd, buf, size);
} while (n == -1 && errno == EINTR);

    4.なぜ「悪いほう」が勝つのか

    Gabriel の説明はこうです。

    1. 実装が単純なので、すぐ作れて、いろいろな環境に移植しやすい
    2. 完璧ではないが「だいたい動く」ので、先に広まる
    3. 使う人が増えると、ユーザー自身が改良していく（ウイルスのように広がる、と Gabriel は表現しました）
    4. 気づいたときには、それが標準になっている

    一方「正しいもの」は、完成までに時間がかかり、実装が重く、移植しにくいため、広まる前に機会を逃しがちです。

    5.現代の開発での活かし方

    • MVP（Minimum Viable Product、実用最小限の製品）：最小限の機能で早く出し、使われながら改善する。Worse is Better の考え方とよく重なる
    • プロトタイプを先に出す：設計会議で完璧を目指すより、単純な実装を動かして反応を見るほうが早く正解に近づくことが多い
    • 普及するものの見極め：技術選定で「設計が美しいもの」と「広く使われているもの」がずれることがある。その理由を説明する手がかりになる
    • YAGNI・KISS との関係：「今いらない完全性は捨てる」という点で YAGNI と、「単純さを最優先する」という点で KISS とつながっている（DRY・KISS・YAGNI）

    6.よくある誤解

    誤解1：「品質が低くてもいい」という意味だ

    違います。Worse is Better でも 正しさは大事 で、譲るのは「単純さとぶつかったとき、少しだけ」です。手抜きを正当化する言葉ではありません。

    誤解2：「The Right Thing は間違っている」

    Gabriel は2つのスタイルの 良し悪しではなく、広まりやすさ を論じています。安全性が最優先の領域（医療・航空・金融の勘定系など）では、The Right Thing 寄りの設計が求められます。

    誤解3：「単純」＝「使う人にとって簡単」

    ここでいう単純さは 実装の単純さ です。そのぶん、使う側に負担（例：EINTR のリトライ）が回ることがあります。KISS の「単純」とどちらの単純さを指しているのか、区別して考える必要があります。

    7.まとめ

    • Richard P. Gabriel が 1989年の講演原稿で提唱、1991年ごろから広まった
    • The Right Thing（MIT 流）：正しさ・完全性・使う側の単純さを優先
    • Worse is Better（New Jersey 流）：実装の単純さを最優先し、他は少しずつ譲る
    • 単純なものは早く作れて移植しやすく、先に広まって育つ。UNIX と C が例
    • 手抜きの言い訳ではなく、何を優先するかのトレードオフ の話
