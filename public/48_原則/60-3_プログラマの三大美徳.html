    60 思想・美徳

    プログラマの三大美徳 — 怠惰・短気・傲慢と、リファクタリング・命名

    Perl の作者ラリー・ウォールが挙げた プログラマの三大美徳 は、怠惰・短気・傲慢 という、ふつうは悪徳とされる言葉です。ゆるコンピューター科学ラジオの「プリンシプルオブライフ」第3回は、リファクタリング・コードの臭い・命名 の話から入り、三大美徳、とくに「傲慢」を ものづくりをする人全般の矜持 として読み替えます。

    もとにしたノート：03プログラマの三大美徳に痺れる。「傲慢」が特に最高【プリンシプルオブライフ3】28

    ひとことで言うと

    良いコードを生むのは、同じ面倒を繰り返したくない「怠惰」、遅さに我慢できない「短気」、そして 「自分が書いたものがこんなに汚いはずがない」と書き直す「傲慢」 です。リファクタリング・臭いへの嗅覚・命名へのこだわりは、編集者の推敲・見出しづくりと同じ構造で、「これでいいはずがない」という傲慢さがコードも作品も磨き続けさせます。

    1.このページで扱うこと

    もとのノートは YouTube 動画のクリップです。このページでは「詳しい要約」を中心に、次の順で解説します。

    1. リファクタリング：外から見た振る舞いを変えずにコードを書き直すこと
    2. 引き継ぎの難しさ と、直す手がかりとしての コードの臭い
    3. その場しのぎ（Quick and Dirty）と TypeScript の any
    4. 命名は最重要課題：編集者との共通点
    5. プログラマの三大美徳（怠惰・短気・傲慢）と、傲慢のクリエイターへの読み替え

    コードの臭いとリファクタリングをクラス単位で詳しく見るなら コードの臭いとリファクタリング（44章）、メソッド単位では リファクタリングの実践、命名は 命名（46章）と 命名とクラス構成（44章）を参照してください。

    2.シリーズの位置づけ

    「プリンシプルオブライフ」第3回です（第1回 銀の弾丸はない、第2回 情報隠蔽は正義）。今回の柱は リファクタリング、コードの臭い（code smell）、命名の重要性、そしてラリー・ウォールの プログラマの三大美徳（怠惰・短気・傲慢）です。

    冒頭から「編集者とプログラマはほぼ同じ仕事（相手は才能ある人で、見出し・命名にこだわる）」という抽象化で始まります。

    3.リファクタリングとは

    • リファクタリング：外から見た振る舞いは変えずに、ソースコードを きれいに書き直す 作業（rewrite に近い）。コンピューター界隈でしか使わない専門語だ、という自虐的な比喩（官能小説の「海」レベル）付きで紹介されます。
    • 具体例：重複した処理の統合、インデント（字下げ）の整理。編集でいう 推敲・リライト や、自分の数か月前の原稿を見て恥ずかしくなる感覚と同じ構造です。
    • 共有コードの羞恥：サポーターサイトをフロントエンド担当と分担するようになり、自分のバックエンドのコードが丸見えになる「苦行」。本来フロントでやるべき処理を、サーバー側でごまかしている部分などがある、という告白です。
    • Excel の比喩：#NAME? エラー、とりあえず全部 SUM、「本来オフィスでやる仕事を家に持ち帰る」——非エンジニアにも伝わるレベルで説明されます。

    賛否

    動いているものに手を入れると壊れるリスクもあり、「あまりやらない方がいい」という派閥もあります。それでも本は 少しずつ書き直せ（きれいにしておかないと、次の担当者の負荷が爆増するから）と繰り返し述べています。「少しずつ」は第1回の インクリメンタル にも通じます。

    4.引き継ぎ・コードを直す難しさ

    • 前任者のコードは、「深い理由がある」のか「その場しのぎ」なのか判別できません。
    • 不要に見える分岐を消したら動かなくなった、というのはよくある話です（数学の因数分解・場合分けのたとえ）。
    • 直すときの手がかりは、フィーリングではなく、経験則としての 「臭い（くさい）ところ」 です。

    5.コードの臭い（Code Smell）

    調香師 の比喩で説明されます。物理的な臭いがするわけではなく、「このままだと失敗しがち」という経験則を「臭い」と呼んでいます。

    用語（おしゃれな例）ざっくり意味
    重複コード同じことを繰り返している
    長すぎるメソッドクリック4回分を1行にまとめるべきではない
    消費税8%と10%で別関数まとめられる処理の重複
    昨日の横恋慕他クラスのメソッドを過度に呼ぶ
    不適切な親密さ他クラスの実装詳細に依存
    相続拒否（用語として紹介）

    補足：用語の一般的な呼び名

    • 「昨日の横恋慕」は、一般には 「機能の横恋慕」（Feature Envy） と訳される臭いです（自動文字起こしで「機能」が「昨日」になったものと思われます）。あるメソッドが、自分のクラスよりも他のクラスのデータやメソッドばかり使っている状態を指します。
    • 「相続拒否」は Refused Bequest の訳で、文字起こしでは「基底クラスの規約が尊重されない形で」継承している状態として説明されています（子クラスが親から受け継いだものを使わない・守らない）。

    現場では「臭い」と言うよりも、「関数が長いので分割しましょう」 と具体的に言うことが多い、というメタな話もあります。重複コードと DRY 原則の関係は コードの重複とDRY原則違反 を参照してください。

    6.その場しのぎ（Quick and Dirty）と TypeScript

    • その場しのぎ：Excel でとりあえず全部足す、any で型エラーを黙らせる（TypeScript の any の乱用）など。動くけれど後から読めない ＝ 腐臭のするコード です。
    • TypeScript は 型（値の種類をあらかじめ決めておく仕組み）で安全にする言語ですが、エラーを消すために any（どんな値でも通す型）を書くのは、愚かさの自覚 ネタとして自己開示されます。
    ✕ 悪い例：any でエラーを黙らせる（その場しのぎ） 
    function total(items: any) {
  return items.reduce((sum: any, x: any) => sum + x.price, 0);
}
    ◯ 良い例：型を書いて、間違いをコンパイラに見つけてもらう 
    type Item = { price: number };

function total(items: Item[]): number {
  return items.reduce((sum, x) => sum + x.price, 0);
}

    ※ 上のコードはこのページで補った説明用の例です。

    7.命名は最重要課題

    本の中で何度も繰り返される原則です。

    • 関数名やファイル名は、半導体回の ゲートの記号（AND・OR などの論理回路の記号。形を見れば働きが分かる）のように、見ただけで役割が分かる べきです。ノートでは「穴埋めパン（半導体のゲート記号）」と書かれています。
    • 悪い例：registerCustomerInformation と名付けたが、中身の大半が入力の検証 → 実態は validateCustomerInformation。名前と中身がずれたまま残ると、リファクタリングが必要になります。
    • 編集者との共通点：雑誌の特集タイトルや、大トリの見出しが軸になる。「〇〇の未来」「〇〇入門」は角度が弱い——命名と同じ構造の失敗です。
    ✕ 悪い例：名前（登録）と中身（大半が検証）がずれている 
    function registerCustomerInformation(input) {
  // ほとんどが入力チェック
  if (!input.name) throw new Error("name is required");
  if (!input.email.includes("@")) throw new Error("invalid email");
  // ...
}
    ◯ 良い例：中身に合わせて名前を変える（または処理を分ける） 
    function validateCustomerInformation(input) {
  if (!input.name) throw new Error("name is required");
  if (!input.email.includes("@")) throw new Error("invalid email");
}

    ※ コードはノートの例（関数名）をもとに、このページで補ったものです。

    8.プログラマの三大美徳（Three Virtues）

    Perl（プログラミング言語の一つ）の作者 ラリー・ウォール に由来します。怠惰・短気・傲慢（Laziness, Impatience, Hubris）の3つです。

    美徳意味（番組での解釈）
    怠惰（Laziness）同じ面倒を繰り返さない。自動化・再利用
    短気（Impatience）遅い・待たされる部分を早くしたがる原動力
    傲慢（Hubris）「俺が書いたコードがこんなに汚いはずがない」——許せずに書き直す。作品への矜持

    怠惰 → 自動化・再利用

    手作業の繰り返しを嫌うから、仕組みにする。重複を嫌う DRY の発想とも重なります。

    短気 → 速くする

    待たされるのが我慢できないから、遅い部分を改善する原動力になります。

    傲慢 → 書き直す

    自分の作品が汚いことを許せないから、リファクタリングや命名の見直しに向かいます。

    動画の主張は、傲慢はプログラマに限らず、ものづくりをする人全般に広げられる ということです。

    9.傲慢の具体例（クリエイター）

    • 東村アキコ（NHK『まんべん』）：アシスタントが仕上げた完成原稿を見て「違う」と書き直す。多くの連載と育児の合間でも、品質の一線を譲らない。
    • 浦沢直樹：漫画家の仕事は100人いれば100通り——それを比べ、解説する面白さ。
    • ラジオ制作への応用：ボツ素材だらけで更新が遅いのは、むしろ 傲慢が足りない のでは（「公開順を推測し間違えてはいけない」という気持ち）。悪用はせず、プロ意識 として持つ。

    10.よくある誤解

    誤解1：「怠惰・短気・傲慢は、文字どおり悪い性格のことだ」

    三大美徳はあえて悪徳の言葉を使った言い回しです。怠惰 は「同じ面倒を繰り返さないために自動化・再利用する」、短気 は「遅さを改善する原動力」、傲慢 は「自分の作品の汚さを許さず書き直す矜持」を指します。いずれも良いコードを生むエネルギーとして語られています。

    誤解2：「動いているコードは、触らないのがいちばん安全だ」

    確かに、手を入れると壊れるリスクはあり、不要に見える分岐を消して動かなくなることもあります。それでも本は 少しずつ書き直せ と述べます。汚いまま残すと、次の担当者の負荷が爆増するからです。直すときはフィーリングではなく、コードの臭い を手がかりにします。

    誤解3：「名前は動けば何でもいい。中身が正しければ問題ない」

    命名は本の中で何度も繰り返される 最重要課題 です。registerCustomerInformation の中身が実は検証ばかり、のように名前と中身がずれていると、読む人を誤らせ、リファクタリングが必要になります。雑誌の見出しと同じで、名前が軸になります。

    11.まとめ

    • リファクタリング・臭い・命名は、編集の 推敲・タイトル・リライト と 同じ構造。
    • リファクタリング：振る舞いを変えずにきれいに書き直す。少しずつ行う。
    • コードの臭い：「このままだと失敗しがち」という経験則。重複コード、長すぎるメソッド、機能の横恋慕、不適切な親密さ、相続拒否など。
    • その場しのぎ（any で黙らせるなど）は、動くが後から読めない腐臭のするコード。
    • 命名は最重要課題：見ただけで役割が分かる名前に。中身とずれたら直す。
    • プログラマの三大美徳（ラリー・ウォール）：怠惰・短気・傲慢。とくに 傲慢——「これでいいはずがない」という感覚を持って、コードも番組も磨き続ける、という締め。
    • おまけ：水野さんのダメコードを酒を飲みながら実況レビューする企画案（コードレビュー文化のエンタメ化）もネタとして出ています。
