    30 オブジェクト指向の原則

    インターフェース分離の原則（ISP） — 使わないメソッドに依存させない

    SOLID 原則の 4 番目、インターフェース分離の原則（Interface Segregation Principle, ISP） を学びます。何でも詰め込んだ「太ったインターフェース」を、使う側（クライアント）に合わせた小さなインターフェースに分ける考え方です。労働者・プリンター・データベースの例で分け方を見たあと、分けすぎの失敗や、分けるべきかの判断基準まで扱います。

    もとにしたノート：04_ISP (インターフェース分離の原則)

    ひとことで言うと

    大きなインターフェースを、使う側が一緒に使うメソッドのまとまり ごとに小さく分け、それぞれが必要なものだけに依存するようにする原則です。「実装クラスが throw new Error('Not supported') を書いている」のが分けどきのサインです。ただし、1 メソッドずつ分けるような 分けすぎ は逆効果です。

    1.このページで扱うこと

    • ISP とは何か — 原則の文言
    • なぜ重要なのか — 太ったインターフェースの問題と、分離のメリット
    • 悪い例と良い例 — 労働者、プリンター、データベース
    • 実装パターン — 分離、ロールインターフェース、アダプター
    • 判断基準と適用のヒント、よくある間違い（分けすぎ）

    クラス設計の中での使い方（役割インターフェースと YAGNI のバランスなど）は 44 章の「インターフェース分離の原則」でも扱っています。

    2.ISP とは

    Interface Segregation Principle（ISP） は、SOLID 原則 の 4 番目の原則です。

    「クライアントは、自分が使用しないメソッドに依存することを強制されるべきではない」

    つまり、大きなインターフェースを複数の小さなインターフェースに分割し、クライアントが必要なものだけに依存させる という原則です。

    • インターフェース：クラスが「どんなメソッドを持つか」だけを決めた約束（型）。中身の処理は書かない
    • クライアント：そのインターフェースを使う側のコード

    JavaScript には interface 構文がないため、このページのコードでは「メソッドを呼ぶと must be implemented 例外を投げるクラス」をインターフェースの代わりに使っています。

    3.なぜ重要なのか

    問題点（大きなインターフェース＝太ったインターフェースがあると）

    • 不要な依存関係 — 使わないメソッドにも依存してしまう
    • 実装の負担 — 使わないメソッドも実装しなければならない
    • 変更の影響 — 使わないメソッドの変更が、使っているクラスにも影響する
    • インターフェースの汚染 — インターフェースが肥大化し、理解が困難

    メリット（分離すると）

    • 必要なものだけに依存 — クライアントは必要なメソッドだけに依存
    • 実装の簡素化 — 使わないメソッドを実装する必要がない
    • 変更の局所化 — 変更の影響範囲が限定的
    • インターフェースの明確化 — 各インターフェースの役割が明確

    4.悪い例 — 太ったインターフェース

    4.1 例1：太ったインターフェース

    ✕ 悪い例：すべての機能を 1 つのインターフェースに詰め込む 
    // ❌ 悪い例: すべての機能を1つのインターフェースに詰め込む
class Worker {
  work() {
    throw new Error('work must be implemented');
  }

  eat() {
    throw new Error('eat must be implemented');
  }

  sleep() {
    throw new Error('sleep must be implemented');
  }
}

// 人間の労働者: すべてのメソッドを実装する必要がある
class HumanWorker extends Worker {
  work() {
    console.log('Human is working...');
  }

  eat() {
    console.log('Human is eating...');
  }

  sleep() {
    console.log('Human is sleeping...');
  }
}

// ロボットの労働者: eat()とsleep()は不要だが、実装しなければならない
class RobotWorker extends Worker {
  work() {
    console.log('Robot is working...');
  }

  eat() {
    // ロボットは食べない！でも実装しなければならない ❌
    throw new Error('Robots do not eat');
  }

  sleep() {
    // ロボットは眠らない！でも実装しなければならない ❌
    throw new Error('Robots do not sleep');
  }
}

    問題点:

    • RobotWorker は eat() と sleep() を使わないのに、実装しなければならない
    • 使わないメソッドに依存してしまう
    • インターフェースが肥大化している

    使えないメソッドで例外を投げている点は、前のページの リスコフの置換原則（LSP） の違反パターンとも同じ形です。

    5.良い例 — インターフェースを分離する

    5.1 インターフェースを分離する

    ◯ 良い例：Workable・Eatable・Sleepable に分ける 
    // ✅ 良い例: インターフェースを分離

// 労働者のインターフェース
class Workable {
  work() {
    throw new Error('work must be implemented');
  }
}

// 食事可能なインターフェース
class Eatable {
  eat() {
    throw new Error('eat must be implemented');
  }
}

// 睡眠可能なインターフェース
class Sleepable {
  sleep() {
    throw new Error('sleep must be implemented');
  }
}

// 人間の労働者: すべてのインターフェースを実装
class HumanWorker extends Workable {
  work() {
    console.log('Human is working...');
  }
}

class HumanEater extends Eatable {
  eat() {
    console.log('Human is eating...');
  }
}

class HumanSleeper extends Sleepable {
  sleep() {
    console.log('Human is sleeping...');
  }
}

// または、多重継承が可能な言語では
class Human implements Workable, Eatable, Sleepable {
  work() { console.log('Human is working...'); }
  eat() { console.log('Human is eating...'); }
  sleep() { console.log('Human is sleeping...'); }
}

// ロボットの労働者: Workableだけを実装
class RobotWorker extends Workable {
  work() {
    console.log('Robot is working...');
  }
  // eat()やsleep()を実装する必要がない ✅
}

// 使用例
function manageWork(worker) {
  worker.work();  // Workableインターフェースだけが必要
}

const human = new HumanWorker();
const robot = new RobotWorker();

manageWork(human);   // ✅ OK
manageWork(robot);   // ✅ OK - eat()やsleep()は不要

    ※ JavaScript の class は 1 つのクラスしか継承できないため、前半では人間を HumanWorker・HumanEater・HumanSleeper に分けて書いています。class Human implements Workable, Eatable, Sleepable の部分は、TypeScript や Java のように 1 つのクラスが複数のインターフェースを実装できる言語での書き方です（JavaScript ではこのままでは動きません）。

    5.2 JavaScript での実装例

    JavaScript では、型ではなく「そのメソッドを持っているか」で判断する ダックタイピング（アヒルのように鳴けばアヒルとみなす考え方）がよく使われます。

    ◯ 良い例：必要なメソッドを持っているかだけを確認する 
    // ✅ 良い例: JavaScriptでの実装
class Workable {
  work() {
    throw new Error('work must be implemented');
  }
}

class Eatable {
  eat() {
    throw new Error('eat must be implemented');
  }
}

class Sleepable {
  sleep() {
    throw new Error('sleep must be implemented');
  }
}

// ミックスイン（Mixin）パターンを使用
class Human {
  work() {
    console.log('Human is working...');
  }

  eat() {
    console.log('Human is eating...');
  }

  sleep() {
    console.log('Human is sleeping...');
  }
}

class Robot {
  work() {
    console.log('Robot is working...');
  }
  // eat()やsleep()は実装しない ✅
}

// 使用例
function manageWork(worker) {
  if (typeof worker.work !== 'function') {
    throw new Error('Worker must implement work()');
  }
  worker.work();
}

const human = new Human();
const robot = new Robot();

manageWork(human);   // ✅ OK
manageWork(robot);   // ✅ OK

    ミックスイン は、複数の部品からメソッドを取り込んでクラスを組み立てる手法です。

    6.実践的な例

    6.1 例2：プリンターインターフェース

    ✕ 悪い例：印刷・スキャン・ファックスを 1 つのインターフェースに 
    // ❌ 悪い例: すべての機能を1つのインターフェースに
class Printer {
  print() {
    throw new Error('print must be implemented');
  }

  scan() {
    throw new Error('scan must be implemented');
  }

  fax() {
    throw new Error('fax must be implemented');
  }
}

// シンプルなプリンター: scan()とfax()は不要
class SimplePrinter extends Printer {
  print() {
    console.log('Printing...');
  }

  scan() {
    // スキャン機能がない！でも実装しなければならない ❌
    throw new Error('Scan not supported');
  }

  fax() {
    // ファックス機能がない！でも実装しなければならない ❌
    throw new Error('Fax not supported');
  }
}
    ◯ 良い例：機能ごとにインターフェースを分ける（またはコンポジション） 
    // ✅ 良い例: インターフェースを分離
class Printable {
  print() {
    throw new Error('print must be implemented');
  }
}

class Scannable {
  scan() {
    throw new Error('scan must be implemented');
  }
}

class Faxable {
  fax() {
    throw new Error('fax must be implemented');
  }
}

// シンプルなプリンター: Printableだけを実装
class SimplePrinter extends Printable {
  print() {
    console.log('Printing...');
  }
  // scan()やfax()を実装する必要がない ✅
}

// 多機能プリンター: すべてのインターフェースを実装
class MultiFunctionPrinter extends Printable {
  print() {
    console.log('Printing...');
  }
}

class MultiFunctionPrinterScanner extends Scannable {
  scan() {
    console.log('Scanning...');
  }
}

// または、コンポジションを使用
class MultiFunctionPrinter {
  constructor() {
    this.printer = new SimplePrinter();
    this.scanner = new Scanner();
    this.fax = new Fax();
  }

  print() {
    this.printer.print();
  }

  scan() {
    this.scanner.scan();
  }

  fax() {
    this.fax.fax();
  }
}

    コンポジション（合成） は、継承の代わりに、機能を持つ部品オブジェクトをフィールドとして持ち、処理を任せる方法です（44 章「継承より合成」）。

    ※ コンポジション版で this.fax = new Fax() と書くと、インスタンスの fax プロパティが fax() メソッドを覆い隠してしまい、printer.fax() が動きません。実際に書くときは this.faxMachine のように別の名前にします。また、2 つの案を続けて書いているため MultiFunctionPrinter が 2 回出てきます。

    6.2 例3：データベース操作インターフェース

    ✕ 悪い例：接続・読み・書き・削除を 1 つのインターフェースに 
    // ❌ 悪い例: すべての操作を1つのインターフェースに
class Database {
  connect() {
    throw new Error('connect must be implemented');
  }

  disconnect() {
    throw new Error('disconnect must be implemented');
  }

  read() {
    throw new Error('read must be implemented');
  }

  write() {
    throw new Error('write must be implemented');
  }

  delete() {
    throw new Error('delete must be implemented');
  }
}

// 読み取り専用データベース: write()とdelete()は不要
class ReadOnlyDatabase extends Database {
  connect() { }
  disconnect() { }
  read() { }

  write() {
    // 書き込み不可！でも実装しなければならない ❌
    throw new Error('Write not allowed');
  }

  delete() {
    // 削除不可！でも実装しなければならない ❌
    throw new Error('Delete not allowed');
  }
}
    ◯ 良い例：Connectable・Readable・Writable・Deletable に分ける 
    // ✅ 良い例: インターフェースを分離
class Connectable {
  connect() {
    throw new Error('connect must be implemented');
  }

  disconnect() {
    throw new Error('disconnect must be implemented');
  }
}

class Readable {
  read() {
    throw new Error('read must be implemented');
  }
}

class Writable {
  write() {
    throw new Error('write must be implemented');
  }
}

class Deletable {
  delete() {
    throw new Error('delete must be implemented');
  }
}

// 読み取り専用データベース: ConnectableとReadableだけを実装
class ReadOnlyDatabase extends Connectable {
  connect() {
    console.log('Connecting to read-only database...');
  }

  disconnect() {
    console.log('Disconnecting from read-only database...');
  }
}

class ReadOnlyDatabaseReader extends Readable {
  read() {
    console.log('Reading from database...');
  }
  // write()やdelete()を実装する必要がない ✅
}

// 読み書き可能なデータベース: すべてのインターフェースを実装
class ReadWriteDatabase extends Connectable {
  connect() { }
  disconnect() { }
}

class ReadWriteDatabaseReader extends Readable {
  read() { }
}

class ReadWriteDatabaseWriter extends Writable {
  write() { }
}

class ReadWriteDatabaseDeleter extends Deletable {
  delete() { }
}

    connect() と disconnect() は必ず一緒に使うので、1 つの Connectable にまとめている点に注目してください。「一緒に使うものはまとめる」が分け方の基本です（11. よくある誤解）。

    7.実装パターン

    7.1 インターフェースの分離

    // 大きなインターフェースを小さなインターフェースに分割
class LargeInterface {
  method1() { }
  method2() { }
  method3() { }
  method4() { }
}

// 分離後
class Interface1 {
  method1() { }
  method2() { }
}

class Interface2 {
  method3() { }
  method4() { }
}

    7.2 ロールインターフェース

    ロールインターフェース（役割インターフェース）は、「読む人」「書く人」のように、使う側の 役割 ごとに定義するインターフェースです。

    // 各ロール（役割）ごとにインターフェースを定義
class UserReader {
  read() { }
}

class UserWriter {
  write() { }
}

class UserDeleter {
  delete() { }
}

// 必要に応じて組み合わせる
class UserRepository extends UserReader {
  read() { }
}

class FullUserRepository extends UserReader {
  read() { }
}

// UserWriterとUserDeleterも実装

    7.3 アダプターパターンとの組み合わせ

    アダプターパターン は、既存のオブジェクトを別の形のインターフェースに合わせる「変換アダプター」を挟む設計パターンです（44 章「構造パターン」）。

    // 既存の大きなインターフェースを、小さなインターフェースに適応
class LargeInterface {
  method1() { }
  method2() { }
  method3() { }
}

class SmallInterface {
  method1() { }
}

class Adapter extends SmallInterface {
  constructor(large) {
    super();
    this.large = large;
  }

  method1() {
    return this.large.method1();
  }
}

    8.判断基準

    ISP を適用すべきか判断する質問です。

    質問ISP を適用現状のままで良い
    1. クライアントが使わないメソッドがあるか？あるない
    2. 実装クラスが使わないメソッドを実装しているか？実装している実装していない
    3. インターフェースが肥大化しているか？肥大化している適切なサイズ

    9.適用のヒント

    9.1 使わないメソッドを探す

    // 実装クラスで、例外を投げているメソッドを探す
class SomeClass extends LargeInterface {
  method1() { }
  method2() {
    throw new Error('Not supported');  // ← これがヒント
  }
}

    9.2 クライアントの使用パターンを確認

    // クライアントが使うメソッドの組み合わせを確認
client1.method1();  // method1だけを使う
client2.method2();  // method2だけを使う
client3.method1(); client3.method2();  // method1とmethod2を一緒に使う

    9.3 インターフェースのサイズを確認

    • 5 つ以上のメソッドがある → 分割を検討
    • メソッドが異なる責任を持っている → 分割を検討

    10.関連原則

    原則ISP との関係
    Single Responsibility Principle（SRP）ISP は SRP をインターフェースに適用したもの
    Dependency Inversion Principle（DIP）ISP を守ることで、DIP も守りやすくなる

    11.よくある誤解

    ノートの「よくある間違い」をもとにしています。ISP は「小さいほど良い」という原則ではありません。

    誤解1：「インターフェースは細かいほど良い（1 メソッドごとに分ける）」
    ✕ やりすぎ：1 つのメソッドごとにインターフェースを作る 
    // ❌ やりすぎ: 1つのメソッドごとにインターフェースを作る
class Method1Interface {
  method1() { }
}

class Method2Interface {
  method2() { }
}

class Method3Interface {
  method3() { }
}

    適切な粒度:

    • 関連するメソッドは 1 つのインターフェースにまとめる
    • クライアントが一緒に使うメソッドは同じインターフェースに
    誤解2：「メソッドが別なら分けてよい（getter と setter も分ける）」
    ✕ 意味のない分離：関連性の高いメソッドを分離 
    // ❌ 意味のない分離: 関連性の高いメソッドを分離
class GetNameInterface {
  getName() { }
}

class SetNameInterface {
  setName() { }
}

    適切な分離:

    • 意味的に異なる責任を持つメソッドを分離
    • クライアントが別々に使うメソッドを分離
    誤解3：「ISP は実装クラスの都合で分けるもの」

    原則の主語は クライアント（使う側） です。「実装クラスが例外を投げている」は分けどきの ヒント ですが、どう分けるかは「どのクライアントが、どのメソッドを一緒に使うか」（9.2）で決めます。

    12.まとめ

    12.1 重要なポイント

    1. クライアントは必要なものだけに依存 — 使わないメソッドに依存しない
    2. インターフェースを小さく保つ — 1 つの責任だけを持つ
    3. 関連するメソッドをまとめる — 一緒に使うメソッドは同じインターフェースに
    4. 過度な分割は避ける — 適切な粒度を保つ

    12.2 チェックリスト

    • ☐ 実装クラスが使わないメソッドを実装しているか？
    • ☐ インターフェースが肥大化していないか？
    • ☐ クライアントが使わないメソッドに依存していないか？
    • ☐ インターフェースの責任が明確か？
