    20 構造の原則

    高凝集・低結合 — 集めるべきものを集め、つなぎを細くする

    「この機能を直したら、関係なさそうな別の画面が壊れた」「1 つの変更のために 10 個のファイルを触る羽目になった」。こうした経験の多くは、コードの分け方・つなぎ方に原因があります。このページでは、その良し悪しを測る物差し 凝集度 と 結合度、目指す方向をまとめた 高凝集・低結合（High Cohesion, Low Coupling） の原則を、背景・コード例・よくある誤解とともに学びます。

    もとにしたノート：03_高凝集・低結合

    ひとことで言うと

    「関係の深いものは 1 か所に集め、関係の浅いものどうしはつなぎを細くする」。凝集度（中身のまとまり）は高く、結合度（モジュールどうしの依存の強さ）は低くします。2 つは セット で考え、結合をゼロにしたり細かく分けすぎたりはしません。

    1.このページで扱うこと

    「この機能を直したら、関係なさそうな別の画面が壊れた」「1 つの変更のために 10 個のファイルを触る羽目になった」。こうした経験の多くは、コードの分け方・つなぎ方 に原因があります。その分け方・つなぎ方の良し悪しを測る物差しが 凝集度（Cohesion） と 結合度（Coupling） で、目指す方向をまとめたのが 高凝集・低結合 という原則です。

    • 一言でいうと — 集めるべきものを集め、つなぎを細くする
    • 定義・背景（Constantine と構造化設計）
    • 悪い例（低凝集・高結合）と良い例（高凝集・低結合）
    • 2 つをセットで考える理由
    • よくある誤解と使いどころ

    このページでは原則としての考え方を扱います。凝集度・結合度の 7 段階の詳しい分類 は 43 の「凝集度」「結合度」にまとめてあります。

    2.一言でいうと

    関係の深いものは 1 か所に集め、関係の浅いものどうしはつなぎを細くする

    • 凝集度 … 1 つのモジュールの 中身がどれだけ同じ目的でまとまっているか。高いほど良い
    • 結合度 … モジュール どうしがどれだけ強く依存しているか。低いほど良い

    3.定義・背景

    • Larry L. Constantine が 1960 年代に考え始め、1974 年 に Stevens・Myers・Constantine の論文「Structured Design」で体系化されました。その後、Yourdon と Constantine の書籍『Structured Design』（1979 年）で広く知られるようになります
    • もともとは 構造化設計（関数・サブルーチン単位で処理を分けて組み立てる設計手法）の考え方ですが、のちにクラス・パッケージ・マイクロサービスなど、どの大きさの単位にも当てはまる物差し として使われるようになりました
    • SOLID の SRP（単一責任の原則）は、凝集度の考え方をクラス向けに言い直したものと見ることもできます

    年代順の位置づけは「設計原則の変遷」も参照してください。

    4.悪い例：低凝集・高結合

    ✕ 悪い例：何でも屋のユーティリティと、他クラスの内部をいじるサービス 
    // 何でも屋のユーティリティ（低凝集）
const Utils = {
  formatDate(date) { /* ... */ },
  calcTax(price) { /* ... */ },
  sendSlack(message) { /* ... */ },
  validateEmail(email) { /* ... */ },
};

// 他のクラスの内部データを直接いじる（高結合）
class OrderService {
  checkout(cart) {
    let total = 0;
    for (const item of cart.items) {
      total += item.price * item.quantity;
    }
    cart.items = [];          // Cart の中身を外から直接書き換え
    cart.discountRate = 0;    // Cart の内部の都合まで知っている
    Utils.sendSlack(`注文: ${total}円`);
    return total;
  }
}

    4.1 何が問題か

    • Utils は 目的がバラバラ なので、どこに何があるか分からず、無関係な変更でも同じファイルを触ることになる
    • OrderService は Cart の内部構造を知りすぎている。Cart の持ち方を変えると OrderService も壊れる

    5.良い例：高凝集・低結合

    ◯ 良い例：カートのことは Cart に集め、OrderService は窓口だけを知る 
    // カートに関することは Cart に集める（高凝集）
class Cart {
  #items = [];
  add(item) { this.#items.push(item); }
  total() {
    return this.#items.reduce((sum, i) => sum + i.price * i.quantity, 0);
  }
  clear() { this.#items = []; }
}

// OrderService は Cart の公開メソッドと通知の「窓口」だけを知る（低結合）
class OrderService {
  constructor(notifier) {
    this.notifier = notifier; // Slack かメールかは知らない
  }
  checkout(cart) {
    const total = cart.total();
    cart.clear();
    this.notifier.notify(`注文: ${total}円`);
    return total;
  }
}
    • 合計の計算・中身の消去は Cart の中で完結（#items の # は、クラスの外から触れない private フィールドを表します）
    • OrderService は Cart の 中身の持ち方を知らない。通知先も 差し替えられる

    6.2 つはセットで考える

    凝集度と結合度は、片方だけを良くしようとするとうまくいきません。

    状態どうなるか
    高凝集・低結合目指す形。変更が 1 か所で済み、影響も広がらない
    低凝集・低結合何でも屋のモジュールが孤立している。どこに書けばいいか迷う
    高凝集・高結合それぞれはまとまっているが、つながりが太すぎて一緒にしか動かせない
    低凝集・高結合いわゆるスパゲッティ。どこを触っても他が壊れる

    関係の深いものを同じ場所に集めると、自然と外とのつなぎは細くなる。逆に、関係の深いものをバラバラに置くと、それらをつなぐための結合が増えます。

    7.使いどころ

    • 「この変更で何ファイル触る？」が多いとき → 凝集度 を疑う
    • 「ここを直したら、あっちが壊れた」が起きるとき → 結合度 を疑う
    • クラス・モジュール・サービスの 境界を決めるとき の判断基準として使う

    8.よくある誤解

    誤解1：「結合度はゼロにすべき」

    モジュールどうしが協力しない限りソフトウェアは動きません。目標は 結合をなくすこと ではなく、結合を「細く・明確に・安定したものに」すること です。

    誤解2：「細かく分ければ凝集度が上がる」

    1 メソッドだけのクラスを大量に作ると、今度はそれらをつなぐ結合が増えます。「一緒に変わるもの」が同じ場所にあるか が基準で、小ささ自体は目的ではありません。

    誤解3：「インターフェースを挟めば低結合」

    インターフェースを挟んでも、相手の内部事情を前提にしたメソッド（呼ぶ順番が決まっている、特定の値を前提にしている など）なら、結合度は高いままです。

    9.まとめ

    • 凝集度は高く：関係の深いものを 1 か所に集める
    • 結合度は低く：モジュールどうしのつなぎを細く・明確にする
    • Constantine らが 1974 年 に体系化。どの大きさの単位にも当てはまる
    • 2 つは セット。結合をゼロにする・細かく分けすぎるのは逆効果
