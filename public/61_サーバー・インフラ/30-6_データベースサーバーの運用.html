    データベースサーバーの運用

    データベース（DB）は、失ったら二度と戻らないデータそのものを預かるサーバーです。このページでは、DB サーバーをアプリサーバーと分ける理由、Ubuntu 24.04 に PostgreSQL を入れて 外部接続・認証・最小権限のロール を設定する手順、メモリ設定の基本（shared_buffers など）と接続数の問題を解く PgBouncer、バックアップ・レプリカ・監視の要点、RDS / Aurora / Cloud SQL などマネージド DB の選び方、MySQL との運用面の違いを解説します。最後に「MySQL はセキュリティが弱いのか」という疑問を、動画メモをもとに整理します。

    もとにしたノート：docs/61_サーバー・インフラ/30_アプリ実行環境/06_データベースサーバーの運用、docs/61_サーバー・インフラ/60_サーバー・ネットワークセキュリティ/MySQLはセキュリティが弱いのか（IT技術屋のボヤキ、動画 https://www.youtube.com/watch?v=atj_i_u0YaU）

    ひとことで言うと

    データベースサーバーは、お店の 「金庫と帳簿を預かる倉庫」 です。売り場（アプリサーバー）は壊れても建て直せますが、倉庫の中身（注文・顧客データ）は失ったら二度と戻りません。だから倉庫は売り場と別の建物にし、鍵を厳重にし（認証・最小権限）、出入りの人数を制限し（接続数）、毎日コピーを取って（バックアップ）、本当にそのコピーで復元できるかを確かめます。

    このページでは、Shop の PostgreSQL を 「アプリと同居」から「専用 DB サーバー」へ移し、安全に運用する までを扱います。10-4 Linuxサーバーの基本 と 30-5 設定と環境変数・シークレット を読んでいると理解しやすいです。DB そのものの理論（トランザクション、インデックス、WAL など）は、データアーキテクチャ体系のノートで扱います。

    1.DB サーバーを分ける理由

    最初の Shop は 1 台に Nginx・Shop API・PostgreSQL が同居していました。成長に伴い、DB を別サーバー（またはマネージド DB）に分けます。

    理由説明
    性格の違いアプリはステートレス（いつでも作り直せる）、DB は ステートフル（データそのもの）。扱い方を分けたい
    リソースの奪い合いDB はメモリ（キャッシュ）とディスク I/O を大量に使う。アプリの負荷が上がると DB も遅くなり、逆もしかり
    スケールの方向が違うアプリは台数を増やす（水平）、DB は基本的に 1 台を強くする（垂直）＋読み取りレプリカ
    セキュリティDB はインターネットから一切見えないプライベートサブネットに置ける
    運用の独立アプリの再起動・デプロイで DB を巻き込まない。DB のメンテナンス時間を別に計画できる

    2.PostgreSQL のインストールと初期設定

    2.1 インストール

    Ubuntu 24.04 の標準リポジトリには PostgreSQL 16 が入っています（2026 年時点）。より新しいメジャーバージョンが必要なら、PostgreSQL 公式の apt リポジトリ（PGDG）を追加します。

    sudo apt update
sudo apt install -y postgresql          # Ubuntu 24.04 では 16 系が入る
sudo systemctl status postgresql        # 自動で起動・enable される
pg_lsclusters                           # クラスタ（16/main）の状態とポート

    Ubuntu（Debian 系）のパッケージでは、ファイルは次のように分かれています。

    用途パス
    設定ファイル/etc/postgresql/16/main/postgresql.conf
    認証設定/etc/postgresql/16/main/pg_hba.conf
    データ（クラスタ本体）/var/lib/postgresql/16/main/
    ログ/var/log/postgresql/postgresql-16-main.log

    インストール直後、DB 管理者の postgres ロールにはパスワードがなく、同名の OS ユーザーからのローカル接続だけ（peer 認証：OS のユーザー名で本人確認する方式）が許可されています。管理作業は次のように行います。

    sudo -u postgres psql

    2.2 listen_addresses：どこで待ち受けるか

    既定値は localhost で、同じサーバー内からしか接続できません。DB を別サーバーに分けたら、アプリから届くインターフェースで待ち受けるようにします。

    # /etc/postgresql/16/main/postgresql.conf
listen_addresses = 'localhost,10.0.2.10'   # プライベート IP だけ。'*' は避ける
port = 5432

    listen_addresses の変更は 再起動が必要 です（sudo systemctl restart postgresql）。

    DB ポートをインターネットに公開しない

    listen_addresses = '*' に加えてファイアウォールやクラウドのセキュリティグループで 5432 を 0.0.0.0/0 に開けてしまうのは、情報漏えい事故の典型パターンです。DB は 待ち受けアドレス・pg_hba.conf・ファイアウォールの 3 重 で守ります（60-3 ファイアウォールとネットワーク制御）。

    2.3 pg_hba.conf：誰がどこから入れるか

    pg_hba.conf（host-based authentication）は、接続の種類・DB・ユーザー・接続元アドレス・認証方式 の組み合わせを上から順に照合し、最初にマッチした行を使います。

    # TYPE    DATABASE  USER       ADDRESS          METHOD
local     all       postgres                    peer
local     all       all                         peer
host      all       all        127.0.0.1/32     scram-sha-256
# Shop API サブネットから、shop DB へ、shop_app だけ、TLS 必須
hostssl   shop      shop_app   10.0.1.0/24      scram-sha-256
# マイグレーション用ユーザーは踏み台サーバーからだけ
hostssl   shop      shop_owner 10.0.0.5/32      scram-sha-256
    • hostssl は TLS で暗号化された接続だけにマッチします。Ubuntu のパッケージは自己署名証明書で ssl = on になっていますが、正式な証明書に差し替えるのが望ましいです。
    • 認証方式は scram-sha-256 を使います。PostgreSQL 14 以降は password_encryption の既定値が scram-sha-256 で、md5 は非推奨です。trust（パスワードなし）は本番では使いません。
    • 変更は リロードで反映 されます（sudo systemctl reload postgresql または SELECT pg_reload_conf();）。SELECT * FROM pg_hba_file_rules; で書式エラーを確認できます。

    2.4 ロール作成と最小権限

    アプリが スーパーユーザー（postgres）で接続するのは厳禁 です。SQL インジェクションが 1 つあるだけで、全 DB の削除やサーバー上でのコマンド実行まで可能になります（72 SQLインジェクション）。役割ごとに ロール（PostgreSQL ではユーザーとグループを合わせて「ロール」と呼ぶ）を分けます。

    ロール用途権限
    shop_ownerテーブルの所有者。マイグレーション（スキーマ変更）で使うapp スキーマの所有者
    shop_appShop API が普段使うデータの読み書き（SELECT/INSERT/UPDATE/DELETE）だけ。DROP や ALTER は不可
    shop_readonly分析・調査用SELECT だけ
     
    -- sudo -u postgres psql で実行
CREATE ROLE shop_owner LOGIN PASSWORD '...';
CREATE ROLE shop_app   LOGIN PASSWORD '...' CONNECTION LIMIT 50;
CREATE ROLE shop_readonly LOGIN PASSWORD '...';

CREATE DATABASE shop OWNER shop_owner ENCODING 'UTF8' TEMPLATE template0;

\c shop
-- 誰でも接続できる既定の権限を外す
REVOKE ALL ON DATABASE shop FROM PUBLIC;
GRANT CONNECT ON DATABASE shop TO shop_app, shop_readonly;

-- アプリ用スキーマを shop_owner 所有で作る
CREATE SCHEMA app AUTHORIZATION shop_owner;
GRANT USAGE ON SCHEMA app TO shop_app, shop_readonly;

-- 「今後 shop_owner が作るテーブル」にも自動で権限が付くようにする
ALTER DEFAULT PRIVILEGES FOR ROLE shop_owner IN SCHEMA app
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO shop_app;
ALTER DEFAULT PRIVILEGES FOR ROLE shop_owner IN SCHEMA app
  GRANT USAGE, SELECT ON SEQUENCES TO shop_app;
ALTER DEFAULT PRIVILEGES FOR ROLE shop_owner IN SCHEMA app
  GRANT SELECT ON TABLES TO shop_readonly;

-- アプリが使うスキーマの検索順
ALTER ROLE shop_app SET search_path = app;
    • PostgreSQL 15 以降は、新規 DB の public スキーマに一般ユーザーがテーブルを作れなくなりました（以前は誰でも作れた）。古いバージョンから移行した DB では REVOKE CREATE ON SCHEMA public FROM PUBLIC; を実行しておきます。
    • パスワードは 30-5 設定と環境変数・シークレット の方法で保管し、DATABASE_URL としてアプリに渡します。

    3.メモリ設定と接続数

    3.1 メモリ設定の基本

    既定値は「どんな小さなマシンでも起動できる」控えめな値なので、専用 DB サーバーでは調整します。

    パラメータ既定値意味目安（公式ドキュメント等）
    shared_buffers128MBPostgreSQL 自身が持つ共有キャッシュRAM 1GB 以上の専用サーバーなら RAM の 25% から。40% を超えて効果が出ることはまれ（OS のページキャッシュにも頼るため）
    effective_cache_size4GB「OS キャッシュも含めて使えそうなキャッシュ量」のヒント。実際には確保しないRAM の 50〜75% 程度がよく使われる
    work_mem4MBソートやハッシュ 1 回あたりの作業メモリ接続数 × クエリ内の操作数 倍まで膨らみうるので、上げすぎに注意
    maintenance_work_mem64MBVACUUM・インデックス作成用work_mem より大きくしてよい。autovacuum ワーカー数倍になる点に注意

    RAM 8GB の専用 DB サーバーの出発点の例です。

    # /etc/postgresql/16/main/conf.d/tuning.conf （conf.d に分けると管理しやすい）
shared_buffers = 2GB              # 25%（変更は再起動が必要）
effective_cache_size = 6GB
work_mem = 16MB
maintenance_work_mem = 512MB
max_connections = 100

    これらは 出発点 にすぎません。PGTune のような計算ツールで初期値を出し、監視（キャッシュヒット率、一時ファイルの発生、メモリ使用量）を見ながら調整します。

    3.2 接続数の問題とコネクションプーリング

    PostgreSQL は 1 接続ごとに 1 つの OS プロセス を起動します。接続は「作るのが重く、維持するのにもメモリを使う」ため、max_connections（既定 100）を安易に 1000 などに増やすと、メモリ不足や性能低下を招きます。

    一方アプリ側は、Shop API が 4 台 × ワーカー 4 プロセス × プール 10 接続 = 160 接続、のように台数を増やすだけで簡単に上限を超えます（30-1 のコネクションプール参照）。そこで コネクションプーラー（多数のアプリ接続を少数の実接続にまとめる中継役）を間に入れます。

    PgBouncer は軽量なプーラーで、プールモードは 3 種類あります。

    モード実接続を占有する期間注意
    sessionクライアントが切断するまで全機能が使えるが、節約効果は小さい
    transactionトランザクションの間だけ最もよく使われる。SET / LISTEN / セッション単位の advisory lock などセッション状態に依存する機能は使えない。プロトコルレベルのプリペアドステートメントは max_prepared_statements を設定すれば利用可
    statement1 文ごと複数文のトランザクション不可。特殊用途
     
    # /etc/pgbouncer/pgbouncer.ini（sudo apt install pgbouncer）
[databases]
shop = host=10.0.2.10 port=5432 dbname=shop

[pgbouncer]
listen_addr = 127.0.0.1
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction
max_client_conn = 500       # アプリから受け付ける接続数
default_pool_size = 20      # DB への実接続数（ユーザー×DB ごと）

    Shop API の DATABASE_URL を postgres://shop_app:...@127.0.0.1:6432/shop に向けるだけで使えます。PgBouncer を各アプリサーバーに置く方式（1 章の図）と、DB の手前に 1 か所置く方式があります。AWS では RDS Proxy が同じ役割のマネージドサービスです。

    4.バックアップ・レプリカ・監視

    4.1 バックアップ

    方式ツール特徴用途
    論理バックアップpg_dump / pg_dumpallSQL レベルのダンプ。バージョン間の移行にも使える。大きな DB では時間がかかり、取得時点にしか戻せない小〜中規模の日次バックアップ、移行
    物理バックアップ＋WAL アーカイブpg_basebackup、pgBackRest、WAL-Gデータファイルのコピー＋変更履歴（WAL）。任意の時点に戻せる（PITR：Point-In-Time Recovery）本番の本命
     
    # 論理バックアップ（カスタム形式 -Fc は圧縮され、pg_restore で部分復元も可能）
sudo -u postgres pg_dump -Fc -d shop -f /var/backups/shop_$(date +%Y%m%d).dump

# 別名の DB に復元して中身を確認する（本番 DB に直接上書きしない）
sudo -u postgres createdb shop_restore_test
sudo -u postgres pg_restore -d shop_restore_test /var/backups/shop_20261012.dump

    実務のポイントは次のとおりです。

    • バックアップは DB サーバーの外（S3 などのオブジェクトストレージ、別リージョン）に置く。同じディスクにあるとディスク故障で一緒に消えます。
    • 復元テストを定期的に行う。「バックアップは取れていたが復元できなかった」は非常によくある失敗です。
    • どこまで戻せればよいか（RPO：失ってよいデータの時間幅）、何時間で戻せばよいか（RTO：復旧までの目標時間）を先に決め、方式を選びます（DR 訓練と RTO・RPO のノート）。
    • PITR の仕組み（WAL とは何か、なぜ任意時点に戻せるのか）は、WAL とクラッシュリカバリのノートを参照してください。

    4.2 レプリカの概要

    PostgreSQL の ストリーミングレプリケーション は、プライマリの WAL をスタンバイ（レプリカ）に送り続けて、ほぼ同じ状態のコピーを保つ仕組みです。

    • 読み取りの分散：レポートや検索などの重い SELECT をレプリカに逃がせる（ホットスタンバイ）。
    • 障害時の切り替え：プライマリが壊れたらレプリカを昇格（promote）させる。自動化には Patroni などを使う。
    • 注意：既定の非同期レプリケーションでは、レプリカは少し遅れる（レプリケーション遅延）。「書いた直後に読むとレプリカにはまだない」ことを考慮する。レプリカは バックアップの代わりにならない（誤って DELETE すればレプリカでも消える）。

    冗長化の全体像は 50-5 高可用性と冗長化 で扱います。

    5.マネージド DB との比較と選び方

    ここまでの作業（インストール、パッチ適用、バックアップ、レプリカ、フェイルオーバー、監視）の多くを、クラウド事業者に任せられるのが マネージド DB です。

    観点自前（EC2 / VPS に PostgreSQL）Amazon RDS for PostgreSQLAmazon Aurora PostgreSQLGoogle Cloud SQL
    OS・DB のパッチ自分メンテナンスウィンドウで自動同左同左
    バックアップ・PITR自分で構築自動バックアップ＋PITR が標準同左（ストレージ層で継続的）自動バックアップ＋PITR
    高可用性Patroni 等を自分でMulti-AZ（スタンバイへ自動フェイルオーバー）ストレージが 3 AZ に 6 コピー、高速フェイルオーバーHA 構成（リージョン内の別ゾーン）
    読み取りレプリカ自分で構築数クリックで追加最大 15 台、遅延が小さい追加可能
    自由度最大（拡張機能・OS 設定すべて）一部制限（スーパーユーザー不可、パラメータグループ経由）RDS とほぼ同じ制限同様の制限
    コストインスタンス代のみ（＋運用の人件費）同スペックの EC2 より割高RDS よりさらに高めになりやすいRDS と同程度

    選び方の目安（2026 年時点） は次のとおりです。

    • 基本はマネージド DB。DB の運用（特にバックアップ・フェイルオーバー）は失敗したときの被害が大きく、少人数のチームが自前で同等の品質を出すのは大変です。Shop も本番構成では RDS を想定します。
    • 自前が向くのは、マネージドで使えない拡張機能や OS レベルの調整が必要な場合、オンプレミス、コストを極限まで抑えたい小規模・検証環境など。
    • Aurora を選ぶのは、高い可用性・多数のリードレプリカ・ストレージの自動拡張が必要な場合。小規模ならまず RDS で十分なことが多いです。
    • マネージドでも 責任共有モデル（クラウド事業者と利用者で守る範囲を分担する考え方）です。ロール設計・最小権限・セキュリティグループ・スロークエリ対策・メジャーバージョンアップの計画は利用者の仕事として残ります。

    6.MySQL との違い（運用面）

    基本的な考え方（DB を分ける・最小権限・プーリング・バックアップ・監視）は MySQL でも同じです。名前と道具が違う点を押さえておけば、どちらの現場にも入れます。

    観点PostgreSQLMySQL（InnoDB）
    既定ポート54323306
    主な設定ファイル（Ubuntu）/etc/postgresql/16/main/postgresql.conf/etc/mysql/mysql.conf.d/mysqld.cnf
    待ち受けアドレスlisten_addressesbind-address
    接続元の制御pg_hba.confユーザー定義の 'user'@'host' 部分
    初期の安全化ロール設計、public スキーマの権限mysql_secure_installation
    接続の処理単位1 接続 = 1 プロセス1 接続 = 1 スレッド
    主なメモリ設定shared_buffers（RAM の 25% 目安）innodb_buffer_pool_size（専用サーバーなら RAM の大部分、公式は最大 80% 程度を例示）
    変更履歴ログWALbinlog（レプリケーション用）＋ redo log
    論理バックアップpg_dumpmysqldump、MySQL Shell の dump ユーティリティ
    物理バックアップpg_basebackup、pgBackRestPercona XtraBackup、MySQL Enterprise Backup
    コネクションプーラーPgBouncerProxySQL

    バージョンのサポート期限に注意

    MySQL 5.7 は 2023 年 10 月、MySQL 8.0 も 2026 年 4 月にサポートが終了しています（2026 年時点の移行先は 8.4 LTS）。PostgreSQL もメジャーバージョンごとに約 5 年でサポートが終わります。サポート切れの DB を使い続けるのは、どの製品でもセキュリティリスクです。「MySQL だから危ない／PostgreSQL だから安全」ではなく、設定と運用で決まる という話を、次の章でくわしく整理します。

    7.発展：MySQL はセキュリティが弱いのか

    「MySQL はセキュリティが弱い」とよく言われます。動画「MySQLはセキュリティが弱いのか」（IT技術屋のボヤキ）の結論は、弱いのは MySQL ではなく設定と運用 だというものです。デフォルト設定のまま使う、権限を緩くする、サポート切れのバージョンを使い続ける——これらが事故の原因であり、PostgreSQL に乗り換えても使い方が同じなら同じ事故が起きます。

    7.1 弱いと言われる理由

    • 情報漏洩事故で「MySQL を使っていた」と報道されますが、直接の原因は 設定ミスやアプリケーションの脆弱性 であることが多いです。
    • MySQL は世界で最も使われる DB の 1 つなので、利用者が多いぶん事故が目立ちます。PostgreSQL や Oracle でも事故は起きていますが、話題になりにくいのです。
    • 事故が起きるとツールのせいにしたくなります（責任転嫁しやすい）。

    7.2 弱いのは設定と運用

    MySQL のデフォルト設定には、セキュリティより利便性を優先している部分があります。

    • 古いバージョンでは root パスワードなし でインストールでき、直後はパスワードなしで root ログインできました（最近のバージョンでは改善）。
    • bind-address の設定ミスで外部接続を許可してしまう（本来は localhost に限定すべき）。
    • クラウドで セキュリティグループ を誤り、MySQL のポートがインターネットに公開される。

    中でも 権限設定 が最も致命的です。「面倒だから」「動けばいいから」と全ユーザーに全権限を与えると、それがセキュリティホールになります。

    7.3 MySQL 5.7 を使い続ける危険性

    • MySQL 5.7 は 2023 年 10 月にサポート終了。以後はセキュリティパッチが出ず、新しい脆弱性が修正されません。
    • それでも本番で 5.7 を動かしている現場は多いです。理由は 5.7 と 8.0 の互換性 の問題（一部挙動が変わりアプリが動かなくなる可能性）と、大規模テスト・本番停止のリスクで、結果として「動いているから触らない」になります。
    • サポート切れソフトを使い続けるのは 時限爆弾を抱えている状態 です。これも MySQL ではなく運用の問題です。

    7.4 安全に使うための対策

    対策内容
    初期設定インストール直後に mysql_secure_installation を実行（root パスワード設定、不要ユーザー・匿名ユーザーの削除など）
    最小権限の原則アプリには SELECT・INSERT・UPDATE・DELETE など必要な権限だけ。DROP は与えない → SQL インジェクションが起きても被害を最小化
    暗号化通信は SSL/TLS、データは透過的データ暗号化（TDE）。個人情報を扱うなら必須
    監査誰がいつ何をしたかを記録し、問題発生時に追跡できるようにする
    バージョンアップ最も大事。最新のセキュリティパッチを適用し、サポート切れは使わない。これができないと他の設定は意味がない

    これらは 2 章で PostgreSQL に対して行った「待ち受けアドレス・pg_hba.conf・ファイアウォールの 3 重防御」「最小権限のロール」「TLS 必須」と同じ考え方です。

    7.5 PostgreSQL なら安全なのか

    • 答えは No です。デフォルト設定の甘さ、権限の設定ミス、古いバージョンの放置は PostgreSQL でも起きます。
    • 「エンタープライズ向けだから」「設計思想が堅牢だから」という主張は、根拠が曖昧なことが多いです。
    • Oracle・SQL Server・PostgreSQL・MySQL のどれでも、設定を間違えれば危険、正しく設定すれば安全です。脆弱性の発見頻度や対応速度に差はありますが、設定と運用の影響の方が大きい のです。

    DB を乗り換える前に

    MySQL が弱いと言われるのは、利用者が多く事故が目立つからです。事故の多くは設定・権限・古いバージョン放置という運用ミスが原因で、対策は初期設定、最小権限、暗号化、監査、そして何よりバージョンアップです。ツールのせいにする前に、自分の設定と運用を見直しましょう。

    8.よくある誤解・つまずき

    ✕ 誤解◯ 実際
    アプリから postgres ユーザーで接続すれば権限エラーで悩まないSQL インジェクション 1 つで全データ削除まで可能になります。アプリ用ロールには DML（SELECT/INSERT/UPDATE/DELETE）だけを与え、スキーマ変更は別ロールで行います。
    接続数が足りないなら max_connections を増やせばよいPostgreSQL は接続ごとにプロセスを作るため、増やしすぎるとメモリ不足や性能低下を招きます。まず PgBouncer / RDS Proxy でプーリングします。
    レプリカがあるからバックアップは不要誤操作の DELETE や DROP はレプリカにも即座に反映されます。過去の時点に戻せるのはバックアップ（PITR）だけです。
    バックアップのジョブが成功していれば安心実際に復元してみるまで、使えるかどうかは分かりません。定期的に別環境へ復元するテストを行います。
    マネージド DB なら運用は何もしなくてよいパッチやバックアップは任せられますが、権限設計・ネットワーク制御・クエリ性能・メジャーバージョンアップは利用者の責任です。
    MySQL は弱いから PostgreSQL にすれば安全どの DB でも、デフォルト設定のまま・権限が緩い・サポート切れのまま使えば危険です。安全さは製品より設定と運用で決まります。

    9.まとめ

    • DB はステートフルで性格がアプリと違うため、別サーバー（またはマネージド DB）に分け、プライベートネットワークに置く
    • PostgreSQL は listen_addresses・pg_hba.conf（hostssl ＋ scram-sha-256）・ファイアウォールの 3 重で守り、アプリには最小権限のロールを使わせる
    • メモリは shared_buffers を RAM の 25% 程度から始め、work_mem は接続数倍に膨らむことに注意して監視しながら調整する
    • 接続はプロセス単位で重いので、PgBouncer（transaction モード）や RDS Proxy でプーリングする
    • バックアップは外部保管と定期的な復元テストが必須。任意時点への復元は物理バックアップ＋WAL（PITR）。レプリカはバックアップの代わりにならない
    • 少人数のチームでは基本的にマネージド DB（RDS / Aurora / Cloud SQL）を選び、権限設計や性能監視に集中する
    • 「MySQL だから危ない」のではなく、どの DB でも初期設定・最小権限・暗号化・監査・バージョンアップという設定と運用で安全さが決まる

    10.理解度チェック

    Q1. pg_hba.conf に hostssl shop shop_app 10.0.1.0/24 scram-sha-256 を追加したのに、アプリサーバー（10.0.1.20）から接続できません。listen_addresses は localhost のままです。何が原因で、どう直しますか？

    PostgreSQL が localhost でしか待ち受けていないため、そもそも外部からの TCP 接続が届いていません。listen_addresses = 'localhost,10.0.2.10' のようにプライベート IP を追加し、再起動 します（pg_hba.conf はリロードで反映されますが、listen_addresses は再起動が必要）。ファイアウォールやセキュリティグループで 10.0.1.0/24 からの 5432/tcp が許可されているかも確認します。

    Q2. Shop API を 10 台に増やしたら FATAL: sorry, too many clients already が出るようになりました。max_connections を 1000 にする以外の対策は何ですか？

    PgBouncer（transaction モード）や RDS Proxy などのコネクションプーラーを導入し、多数のアプリ接続を少数の実接続に集約します。あわせて各アプリのプールサイズを見直し、idle in transaction のまま接続を握り続けるコードがないかも確認します。

    Q3. 開発者が誤って本番の orders テーブルを DELETE しました。プライマリとレプリカの構成で、毎日深夜に pg_dump を取っています。この場合の問題点と、より望ましい構成は何ですか？

    レプリカにも削除が反映されているため役に立たず、pg_dump からの復元では前日深夜以降のデータが失われます。物理バックアップ＋WAL アーカイブ（pgBackRest など、またはマネージド DB の自動バックアップ）で PITR を可能にし、削除直前の時点に戻せるようにするのが望ましいです。

    Q4. アプリ用に shop_app、マイグレーション用に shop_owner とロールを分けるのはなぜですか？

    最小権限のためです。アプリが普段使うロールにはデータの読み書き（SELECT/INSERT/UPDATE/DELETE）だけを与え、DROP や ALTER はできないようにします。SQL インジェクションが起きても、テーブル削除やスキーマ変更まではされずに済みます。

    Q5. 少人数のチームが本番の DB を用意するとき、基本的にマネージド DB を選ぶのはなぜですか？ 選んでも利用者に残る仕事は何ですか？

    バックアップ・PITR・フェイルオーバー・パッチ適用といった、失敗したときの被害が大きい作業を任せられるからです。ただし責任共有モデルなので、ロール設計・最小権限・セキュリティグループ・スロークエリ対策・メジャーバージョンアップの計画は利用者の仕事として残ります。

    Q6. 「MySQL はセキュリティが弱いから PostgreSQL に乗り換えよう」という提案に、どう答えますか？

    乗り換えだけでは解決しません。事故の多くは、デフォルト設定のまま使う、権限を緩くする、サポート切れのバージョン（MySQL 5.7 など）を使い続けるといった設定・運用の問題で、PostgreSQL でも同じことが起きます。まず mysql_secure_installation、最小権限、TLS などの暗号化、監査、そして何よりバージョンアップを見直すべきです。
