    40 構築・IaC

    Terraform入門

    Terraform は、インフラの「あるべき姿」を HCL という言語で書き、plan で差分を確かめてから apply で作る・変えるプロビジョニングツールです。このページでは、インストールと HCL の基本要素、init → plan → apply → destroy のワークフローと plan の読み方、state ファイル の役割と危険性、S3 リモート state とロック、Shop の EC2 + セキュリティグループを作る完全な例、モジュール、import とドリフト検出を解説します。さらに動画「Terraform 恐怖症克服マニュアル」をもとに、plan と apply の内部の仕組み、state と実体の変化を追う実験、本番で怖がらずに Terraform を扱うための練習法も紹介します。

    もとにしたノート：40_構築・IaC/03_Terraform入門、40_構築・IaC/【効果抜群】Terraform 恐怖症克服マニュアル（りょうま@インフラ攻略、YouTube https://www.youtube.com/watch?v=viGoSsrW-oE）

    ひとことで言うと

    Terraform は 「インフラの設計図を渡すと、現場との差を見積もって（plan）、その通りに工事してくれる（apply）建築会社」 です。工事記録台帳（state ファイル）で「どの設計図の部品が、現実のどの建物に当たるか」を覚えています。plan を読まずに apply しない こと、そして コード・state・実体の 3 つの関係 を理解することが、本番で怖がらずに扱うための鍵です。

    1.Terraform とは

    • HashiCorp 製の プロビジョニングツール（クラウドの API を呼んでリソースを作るツール）。AWS / GCP / Azure / Cloudflare / GitHub など数千の プロバイダー（各サービスの API につなぐプラグイン）に対応
    • 設定は HCL（HashiCorp Configuration Language） という宣言型の言語で書く
    • 「書く → plan で差分確認 → apply で適用」の繰り返し。plan を読まずに apply しない のが鉄則

    宣言型と冪等性の考え方は 40-2 IaCとは、クラウドの基本は 10-3 仮想化とクラウド で扱っています。

    2.インストールと HCL の基本

    2.1 インストール（Ubuntu 24.04）

    HashiCorp 公式の apt リポジトリから入れます。

    wget -O - https://apt.releases.hashicorp.com/gpg | \
  sudo gpg --dearmor -o /usr/share/keyrings/hashicorp-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] \
https://apt.releases.hashicorp.com $(lsb_release -cs) main" | \
  sudo tee /etc/apt/sources.list.d/hashicorp.list
sudo apt update && sudo apt install -y terraform
terraform version

    macOS なら brew tap hashicorp/tap && brew install hashicorp/tap/terraform。複数バージョンを使い分けるなら tfenv などのバージョンマネージャーも便利です。AWS の認証情報は aws configure や SSO（aws sso login）で設定しておきます。

    アクセスキーをコードに書いてはいけない

    AWS のアクセスキーを .tf ファイルに書くと、Git の履歴に残って漏れます。認証情報は aws configure や SSO で手元に設定し、コードには書きません。

    2.2 HCL の 6 つの要素

    # provider: どのクラウドの API を使うか
provider "aws" {
  region = var.region
}

# variable: 外から渡せる入力値（関数の引数）
variable "region" {
  type    = string
  default = "ap-northeast-1"
}

# locals: ファイル内で使う計算済みの値（ローカル変数）
locals {
  name = "shop-${var.env}"
  tags = { Project = "shop", Env = var.env }
}

# data: 既存の情報を読み取る（作らない）
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"] # Canonical
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"]
  }
}

# resource: 作る・管理するもの（本体）
resource "aws_instance" "api" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.small"
  tags          = merge(local.tags, { Name = "${local.name}-api" })
}

# output: 適用後に表示・他から参照する値（関数の戻り値）
output "api_public_ip" {
  value = aws_instance.api.public_ip
}
    要素役割参照の書き方
    providerAPI の接続先と認証—
    resource "型" "名前"作成・管理するリソースaws_instance.api.id
    data "型" "名前"既存情報の読み取りdata.aws_ami.ubuntu.id
    variable入力値var.region
    locals内部の計算値local.name
    output出力値terraform output api_public_ip

    参照（aws_instance.api.id など）を書くと、Terraform は 依存関係を自動で判断 し、作る順番を決めます。セキュリティグループを参照する EC2 は、セキュリティグループの後に作られます。

    3.基本ワークフロー

    コマンド何をするかいつ
    terraform initプロバイダーのダウンロード、backend（state の置き場）の初期化最初、プロバイダーや backend を変えたとき
    terraform fmt / validate整形・文法チェックコミット前（CI でも）
    terraform plan現実と state とコードを比べ、何が起きるかを表示apply の前に毎回
    terraform applyplan の内容を適用（確認プロンプトあり）レビュー後
    terraform destroy管理している全リソースを削除検証環境の後片付け

    init で作られる .terraform.lock.hcl（プロバイダーのバージョン固定）は Git にコミット します。.terraform/ ディレクトリはコミットしません。

    3.1 plan をレビューする習慣

    plan は、手元のコードを実際の環境に適用する前に「これからどんな変更をかけようとしているか」を教えてくれる、いわば ドライラン（予行演習） です。出力は記号で読みます。

      # aws_security_group.web will be updated in-place
  ~ resource "aws_security_group" "web" { ... }

  # aws_instance.api must be replaced
-/+ resource "aws_instance" "api" {
      ~ ami = "ami-0aaa" -> "ami-0bbb" # forces replacement
    }

Plan: 1 to add, 1 to change, 1 to destroy.
    記号意味危険度
    +作成低
    ~その場で変更（in-place）中
    -/+削除して作り直し（replace）高：IP やディスクの中身が変わる
    -削除高

    特に forces replacement と destroy の数 を必ず確認します。「AMI を新しくしたつもりが、本番の API サーバーが作り直される」は典型的な事故です。実務では次のように plan を保存して、その plan だけを apply します。

    terraform plan -out=tfplan      # 計画をファイルに保存
terraform show tfplan           # レビュー（PR に貼る・CI で表示）
terraform apply tfplan          # 保存した計画だけを適用（確認プロンプトなし）

    消されては困るリソースには lifecycle { prevent_destroy = true } を付けておくと、削除を含む plan がエラーになります。

    4.state ファイル

    4.1 役割

    terraform.tfstate は JSON ファイルで、コード上の名前（aws_instance.api）と現実のリソース ID（i-0abc...）の対応表 です。Terraform は plan のたびに state を見て「このコードの部品はどれか」を知り、実機の現在値を読み直して差分を出します。

    コード (.tf)            state (.tfstate)              AWS 上の実体
aws_instance.api  ←→  "aws_instance.api": i-0abc  ←→  EC2 i-0abc

    state がないと、Terraform は既存のサーバーを「知らないもの」とみなし、もう 1 台作ろうとします。

    4.2 plan と apply の内部の仕組み

    動画「Terraform 恐怖症克服マニュアル」では、plan の差分は次の 3 つの関係で決まると説明しています。ソースコードと AWS の実体は普段から目にしますが、state ファイルは S3 などに置かれていて中身を見たことがある人は少なく、影が薄い のがやっかいな点です。

    要素置き場所呼び方
    ステートファイル（.tfstate）S3 や HCP Terraform（旧 Terraform Cloud）などCurrent（現在の状態）
    ソースコード（.tf）手元Desire（こうしたいという意思）
    AWS リソースAWSReal（実体）
    • plan：S3 から state をダウンロードしてメモリに保持 → state 内の ID をもとに AWS API で実体を参照し、メモリ上の state を最新に リフレッシュ → .tf と比較して差分を出力します。
      • state を鵜呑みにせず 実体を見に行く 点が重要です。
      • もう 1 つ重要なのは、state にないリソースは API で問い合わせすらされず、存在しないものとして扱われる 点です。
    • apply：plan 結果を反映（例：ECR を作成）し、最新の状態をメモリ上の state に展開して S3 にアップロードします。Current・Real・Desire の 3 つがそろうので、再度 plan すると No changes になります。

    4.3 実験：state と実体の変化を追う

    動画では、ECR リポジトリ（AWS のコンテナイメージ置き場）を 1 つ作るだけの簡単なコードで、実体や state をわざと変えて plan の結果を確かめています。結果を予想してから試すのがポイントです。

    操作予想と結果
    初回 plan → applycreate 差分 → ECR と state（JSON）ができる
    コンソールで実体を削除して planstate にはまだあるが、実体を見に行くので「ない」とリフレッシュされ、create 差分が出る
    コンソールで MUTABLE → IMMUTABLE に変更して planコードは MUTABLE なので、IMMUTABLE → MUTABLE に戻す差分が出る（「一時的にコンソールから手で変えた」は実務でもよくあるパターン）
    実体を削除し、コードもコメントアウトして planどちらもないので No changes
    state ファイルだけ削除して planstate にないので実体を認知できず create 差分 → apply すると同じ名前で作ろうとして AlreadyExists エラー
    terraform import既存の実体を state に取り込み、Terraform で管理できるようになる（plan の出力からリソースアドレスをコピーすると楽）
    terraform state rmstate からは消えるが実体は残る（本番のインフラには何も変更をかけない）。例：Route 53 のレコードが事故で消えたので Terraform 管理外にしたいとき。terraform state list で管理対象を確認できる
     
    terraform state list                     # state が管理しているリソースの一覧
terraform import <リソースアドレス> <実体の ID>   # 既存の実体を state に取り込む
terraform state rm <リソースアドレス>           # state から外す（実体は消えない）

    仮説を立てて plan の結果が当たるようになると、Terraform の解像度が上がります。

    4.4 state の危険

    • 機密情報が平文で入る：RDS のパスワードなど、リソースの属性はそのまま state に保存されます。state を Git にコミットしてはいけません（.gitignore に *.tfstate* を入れる）。
    • 同時実行で壊れる：2 人が同時に apply すると、後から書いた方が state を上書きし、対応表が壊れます。
    • ローカルに置くと失われる：PC が壊れたら対応表も消えます。チームで共有もできません。

    4.5 リモート state（S3 + ロック）

    そこで state は リモート backend に置き、ロック で同時実行を防ぎます。AWS では S3 が定番です。

    terraform {
  backend "s3" {
    bucket       = "shop-terraform-state-123456789012"
    key          = "prod/web/terraform.tfstate"
    region       = "ap-northeast-1"
    encrypt      = true
    use_lockfile = true   # S3 ネイティブのロック
  }
}

    2026 年時点の状況：

    • 以前は S3 にロック機能がなく、DynamoDB テーブル（dynamodb_table）をロックに使っていました。
    • Terraform 1.10 で S3 の条件付き書き込みを使った use_lockfile が実験的に導入され、1.11 で正式機能（GA） になりました。state と同じ場所に .tflock ファイルを作ってロックします。
    • これに伴い DynamoDB によるロックは非推奨（deprecated） となり、将来のマイナーバージョンで削除予定です。移行期間中は両方を同時に指定することもできます。新規構築では use_lockfile = true だけで十分です。

    state 用バケットには バージョニング（壊れたときに戻せる）、暗号化、パブリックアクセスのブロック を必ず設定し、アクセスできる IAM を絞ります。バケット自体は「鶏と卵」問題（state を置くバケットを Terraform で作るには state の置き場が要る）があるため、手作業か別の小さな Terraform 構成で先に作っておきます。

    5.Shop の EC2 + セキュリティグループを作る完全な例

    Shop の Web/API サーバー 1 台を作る構成です。ファイルを役割ごとに分けます。

    infra/
├── versions.tf      # Terraform とプロバイダーのバージョン、backend
├── variables.tf
├── main.tf
├── outputs.tf
└── prod.tfvars      # 環境ごとの値

    5.1 versions.tf

    # versions.tf
terraform {
  required_version = ">= 1.11"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
  backend "s3" {
    bucket       = "shop-terraform-state-123456789012"
    key          = "prod/web/terraform.tfstate"
    region       = "ap-northeast-1"
    encrypt      = true
    use_lockfile = true
  }
}

provider "aws" {
  region = var.region
  default_tags {
    tags = { Project = "shop", Env = var.env, ManagedBy = "terraform" }
  }
}

    5.2 variables.tf

    # variables.tf
variable "region" {
  type    = string
  default = "ap-northeast-1"
}
variable "env" {
  type = string
}
variable "instance_type" {
  type    = string
  default = "t3.small"
}
variable "admin_cidr" {
  description = "SSH を許可する管理者の IP（/32）"
  type        = string
}
variable "ssh_public_key" {
  type = string
}

    5.3 main.tf

    # main.tf
data "aws_vpc" "default" {
  default = true
}

data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"] # Canonical
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd-gp3/ubuntu-noble-24.04-amd64-server-*"]
  }
}

resource "aws_key_pair" "deploy" {
  key_name   = "shop-${var.env}-deploy"
  public_key = var.ssh_public_key
}

resource "aws_security_group" "web" {
  name        = "shop-${var.env}-web"
  description = "Shop web/api server"
  vpc_id      = data.aws_vpc.default.id
}

# ルールは 1 つずつ別リソースにする（AWS プロバイダー推奨の書き方）
resource "aws_vpc_security_group_ingress_rule" "http" {
  security_group_id = aws_security_group.web.id
  cidr_ipv4         = "0.0.0.0/0"
  ip_protocol       = "tcp"
  from_port         = 80
  to_port           = 80
}

resource "aws_vpc_security_group_ingress_rule" "https" {
  security_group_id = aws_security_group.web.id
  cidr_ipv4         = "0.0.0.0/0"
  ip_protocol       = "tcp"
  from_port         = 443
  to_port           = 443
}

resource "aws_vpc_security_group_ingress_rule" "ssh_admin" {
  security_group_id = aws_security_group.web.id
  cidr_ipv4         = var.admin_cidr   # SSH は管理者の IP だけ
  ip_protocol       = "tcp"
  from_port         = 22
  to_port           = 22
}

resource "aws_vpc_security_group_egress_rule" "all" {
  security_group_id = aws_security_group.web.id
  cidr_ipv4         = "0.0.0.0/0"
  ip_protocol       = "-1"
}

resource "aws_instance" "web" {
  ami                    = data.aws_ami.ubuntu.id
  instance_type          = var.instance_type
  key_name               = aws_key_pair.deploy.key_name
  vpc_security_group_ids = [aws_security_group.web.id]

  root_block_device {
    volume_size = 20
    volume_type = "gp3"
    encrypted   = true
  }

  metadata_options {
    http_tokens = "required"   # IMDSv2 を強制
  }

  tags = { Name = "shop-${var.env}-web-01" }

  lifecycle {
    ignore_changes = [ami]     # 新 AMI が出ても勝手に作り直さない
  }
}

resource "aws_eip" "web" {
  instance = aws_instance.web.id
  domain   = "vpc"
}

    http_tokens = "required" は、EC2 の中からインスタンス情報を取る仕組み（IMDS）を、より安全な v2 だけに限る設定です。aws_eip は固定のパブリック IP（Elastic IP）です。

    5.4 outputs.tf・prod.tfvars と実行

    # outputs.tf
output "public_ip" {
  value = aws_eip.web.public_ip
}
    # prod.tfvars
env            = "prod"
admin_cidr     = "203.0.113.10/32"
ssh_public_key = "ssh-ed25519 AAAA... deploy@shop"
    terraform init
terraform plan -var-file=prod.tfvars -out=tfplan
terraform apply tfplan
terraform output public_ip     # → Ansible のインベントリや DNS に使う

    出力した IP を使って中身を整える方法は 40-4 構成管理とAnsible で扱います。セキュリティグループの設計は 60-3 ファイアウォールとネットワーク制御 も見てください。

    学習用の簡略化

    ここでは分かりやすさのためデフォルト VPC を使っています。本番では VPC・パブリック/プライベートサブネットも Terraform で作り、DB は RDS としてプライベートサブネットに置きます。また 5432 番（PostgreSQL）や 3000 番（Node.js）を インターネットに開けていない ことを確認してください。

    6.モジュール

    同じ構成を本番・ステージングで使い回すには モジュール（Module） にします。モジュールは「variable を受け取り、resource を作り、output を返す 関数」のようなもので、ディレクトリ 1 つがモジュール 1 つです。

    # environments/prod/main.tf
module "web" {
  source        = "../../modules/web-server"
  env           = "prod"
  instance_type = "t3.medium"
  admin_cidr    = "203.0.113.10/32"
}

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"   # 公開 Registry のモジュール
  version = "~> 6.0"
  name    = "shop-prod"
  cidr    = "10.0.0.0/16"
  # ...
}

output "web_ip" {
  value = module.web.public_ip
}
    • 自作モジュール：modules/ に置き、環境ごとのディレクトリから呼ぶ
    • 公開モジュール：Terraform Registry の terraform-aws-modules などは品質が高い。version を必ず固定 する
    • 環境（prod/stg）ごとに state を分ける（backend の key を変える）。1 つの state に全環境を入れると、ステージングの作業で本番を壊すリスクがあります

    7.import と drift

    7.1 既存リソースの import

    手作業で作った既存の EC2 を Terraform 管理下に入れるには import を使います。Terraform 1.5 以降は import ブロックで宣言的に書けます。

    import {
  to = aws_instance.web
  id = "i-0abc1234def567890"
}
    # 対応する resource ブロックの雛形を自動生成
terraform plan -generate-config-out=generated.tf

    生成されたコードを整えて、plan が "No changes" になるまで調整してから apply します。これで「ペット」だったサーバー（40-1 サーバー構築の流れ）を段階的にコード化できます。

    7.2 ドリフトの検出

    誰かがコンソールからセキュリティグループに手でルールを足した場合、次の plan で「コードに戻すための変更」として表示されます。

    terraform plan                  # ドリフトがあれば差分として出る
terraform plan -refresh-only    # 実機の変化だけを確認（state を実機に合わせる用途）

    対処は 2 通りです。

    1. 手動変更が間違い → terraform apply でコードの状態に戻す
    2. 手動変更が正しい（緊急対応など） → コードを同じ内容に直し、plan が "No changes" になることを確認

    CI で毎日 terraform plan -detailed-exitcode（差分ありで終了コード 2）を実行し、ドリフトを通知する運用もよく使われます。

    8.Terraform 恐怖症を克服する

    ここからは動画「Terraform 恐怖症克服マニュアル」の内容です。テーマは 「state ファイルの理解と terraform import の反復で、本番で Terraform を触る怖さを克服する」 ことです。

    8.1 なぜ Terraform が怖いのか

    本番で Terraform を触るのが怖い根本原因は、コマンドを実行した後に「世界」、つまり ソースコード・AWS リソースの実体・state ファイル の 3 つがどう変わるかをイメージできていないことです。既存コードをコピーして似たリソースを増やしたり、新規に作ったりはできても、本番で意図しない差分が出ると手も足も出なくなります。

    • 実務では plan と apply 以外のコマンド（state rm、state mv、import など）はチームの state を書き換え、他の人が実行したときに大量の destroy & create（作り直し）差分を生むため、基本的に禁止されています。
    • そのため plan と apply だけを繰り返すことになり、state ファイルを理解する機会がなく、恐怖心が消えません。

    state を理解すべき理由は 2 つです。

    理由①：plan の差分の元になる

    差分は「ソースコード・実体・state ファイル」の 3 つの関係で決まります。コードと実体は普段から見ているので、あとは state を理解すれば差分の原因が分かります。

    理由②：予期せぬ差分に落ち着いて対応できる

    チームで長く運用していると、大量の destroy & create や replace が出ることがあります。そのとき apply してよいかの判断と、ダメな場合の回避方法が分かります。

    8.2 実体験：深夜の本番リリース

    動画の投稿者は、AWS WAF（Web アプリケーションファイアウォール）を適用する深夜リリースで、plan に予期しない大量の destroy & create が出た経験を紹介しています。このまま apply すると既存リソースが削除される状態でした。朝 6 時までに終える必要があり、依存関係が複雑で中止もできず、Terraform に詳しいのは実質本人だけでした。

    1. state rm・import・state mv で、state と実体のつじつまを合わせた
    2. どうしても消えない差分は lifecycle の ignore_changes で一時的に無視した
    3. 最後に本当に必要な create だけが残り、安全に apply できた

    この経験から、本質的な Terraform 力とは 「どんな予期しない差分が出ても、手触り感をもって元の状態に戻せる力」 だと述べています。映画の時限爆弾で、絶対に切ってはいけない線を見極めながら他の線を切っていくようなイメージです。

    8.3 実力がつかないアンチパターン

    新規作成を繰り返すだけでは伸びない

    入門書によくある「コードをコピー → plan → apply で新規リソースを作成」をひたすら繰り返す学び方は、楽しいものの state ファイルを意識しないので、本番への恐怖心は消えません。新規作成の工程には難しい要素がほとんど入っていないからです。実務ではゼロから作ることはほぼなく、既存の大量のコードとリソースに変更をかけたときに出る予期せぬ差分を、地道に解きほぐして本番を壊さないように直す力 が求められます。

    8.4 正しい学習法：terraform import をやりまくる

    import は既存の AWS リソースを Terraform の管理下に置くコマンドです。「これから Terraform を導入する会社でしか使わない」と思われがちですが、実務でもよく使います。初めての構成はまずコンソールで手動構築して一通りつなぎ込み、動作確認し、構成が固まってから import でコード化する流れが多いのです。慣れていないリソースをいきなり Terraform で作ると手触り感がなく、かえって効率が悪くなります。

    投稿者自身、5 年ほど前は既存環境の Terraform 化プロジェクトで先輩 SRE のコードを見て学んでいましたが、差分が出ると周りに泣きつく状態でした。副業で Google Cloud 環境を一人で Terraform 化したとき、import ではきれいな差分が出ず、あらゆるケースを踏み抜きました。その中で次のような判断ができるようになったそうです。

    • モジュールに切り出してリファクタリングしたら state mv が必要
    • Terraform と相性の悪いリソースは state rm で管理から外す
    • ひどい差分は一度 state rm して import し直した方が早い

    同じ年に別案件で 2 つ、既存リソースの全面 Terraform 化を担当し、力が大きく伸びたといいます。誰かが作ったきれいな基盤の上で plan と apply を繰り返すだけでは得られない視点です。

    8.5 Terraform はインフラ版の Git

    Git に慣れた人は、reset・rebase・cherry-pick・revert などで、どの状態からどの状態になるかを体で分かっています（動画では、新人がぐちゃぐちゃにした履歴を CTO があらゆるコマンドで元に戻した例が紹介されています）。Terraform も同じで、state mv・state rm・import・refresh を駆使して、本番を絶対に壊さないという確信をもって操作できる 状態が「自由自在に扱える」状態です。

    9.よくある誤解・つまずき

    よくある誤解

    • ✕ terraform.tfstate は生成物だから Git に入れておけば安全
      ◯ state には秘密情報が平文で入り、同時実行の制御もできません。S3 などのリモート backend に暗号化して置き、ロックを有効にします。
    • ✕ plan で ~（変更）と出ていれば作り直しはされない
      ◯ -/+ や forces replacement が付いていれば削除→再作成です。EC2 なら IP やローカルディスクの中身が失われます。plan の最終行の to destroy の数を必ず見ます。
    • ✕ コンソールで少し直すくらいなら問題ない
      ◯ 次の apply で手動変更が消されるか、逆に手動変更を前提にした plan が誰かを混乱させます。直したら必ずコードに反映します。
    • ✕ リモート state のロックには DynamoDB が必須
      ◯ Terraform 1.11 以降は S3 の use_lockfile = true だけでロックでき、DynamoDB 方式は非推奨になっています。
    • ✕ terraform destroy は検証環境でしか動かないから安心
      ◯ どの backend・どの AWS アカウントに向いているかで決まります。本番の認証情報を持ったまま実行すれば本番が消えます。重要リソースには prevent_destroy を。
    • ✕ plan は state ファイルの中身だけを見て差分を出す
      ◯ state 内の ID をもとに実体を見に行き、最新の状態にリフレッシュしてからコードと比べます。ただし state に無いリソースは問い合わせすらされません。
    • ✕ terraform state rm を実行すると実体も消える
      ◯ state から外れるだけで、実体（本番のリソース）には何も影響しません。

    10.まとめ

    • Terraform は HCL で「あるべき姿」を書き、init → plan → apply で適用する
    • HCL の要素は provider / resource / data / variable / locals / output
    • plan は必ずレビューし、-/+（作り直し）と destroy に注意。plan -out → apply tfplan で計画通りに適用
    • state はコードと実体の対応表。機密を含むので S3 などに暗号化して置き、use_lockfile でロックする（1.11 で GA、DynamoDB ロックは非推奨）
    • plan は「state を読み込み → 実体でリフレッシュ → コードと比較」、apply は「反映して state を更新」。state にないものは認知されない
    • モジュールで再利用し、環境ごとに state を分ける
    • 既存リソースは import で取り込み、ドリフトは plan で検出する
    • 恐怖心の原因は、コード・state・実体の 3 者の関係をイメージできていないこと。新規作成の繰り返しではなく、import で既存リソースを取り込む練習 を重ねるのが克服の近道

    11.理解度チェック

    Q1. state ファイルを失うと、次の terraform apply で何が起きる可能性がありますか。

    Terraform はコード上のリソースと既存の実体の対応を失うため、既存リソースを「存在しない」とみなして同じリソースをもう一式作ろうとします（名前の重複でエラーになるか、重複したリソースができる）。動画の ECR の実験では AlreadyExists エラーになりました。import で対応付けを復元する必要があります。

    Q2. plan に -/+ resource "aws_instance" "web" と出ました。何を確認すべきですか。

    EC2 が削除→再作成されることを意味するので、どの属性が forces replacement の原因か、再作成で IP・ディスクの中身・稼働中のサービスにどんな影響が出るかを確認します。意図しないなら原因の変更を取り消すか、lifecycle の ignore_changes などで抑止します。

    Q3. 本番とステージングで同じ構成を使いたいとき、どう構成するのがよいですか。

    共通部分をモジュールにまとめ、環境ごとのディレクトリからモジュールを呼び出して、入力値（インスタンスタイプなど）を変えます。state は環境ごとに別の key（別ファイル）に分けます。

    Q4. Terraform で作った ECR をコンソールから手で削除し、コードはそのままで plan すると、どうなりますか。

    create 差分が出ます。plan は state 内の ID をもとに実体を見に行き、「もう無い」と分かるのでメモリ上の state をリフレッシュし、コード（あるべき姿）と比べて「作る必要がある」と判断するからです。

    Q5. terraform state rm と terraform import は、それぞれ state と実体に何をしますか。

    state rm は state からリソースを外すだけで、実体は残します（Terraform の管理外になる）。import は既存の実体を state に取り込み、Terraform で管理できるようにします。どちらも実体そのものは変更しません。

    Q6. 複数人で同じ state に対して同時に apply すると何が起きますか。どう防ぎますか。

    後から書いた方が state を上書きし、コードと実体の対応表が壊れます。state を S3 などのリモート backend に置き、use_lockfile = true でロックして同時実行を防ぎます。

    Q7. 動画で「Terraform の実力がつかないアンチパターン」とされた学び方と、代わりに勧められた練習は何ですか。

    コードをコピーして plan → apply で新規リソースを作るのを繰り返すことがアンチパターンです。state を意識しないため、本番の予期せぬ差分に対応する力がつきません。代わりに、既存リソースを terraform import で取り込む練習を繰り返すことが勧められています。
