    20 Webサーバー・リバースプロキシ

    リバースプロキシ

    リバースプロキシ は、アプリの前に立ってリクエストを受け取り、裏のアプリへ中継するサーバーです。このページでは、フォワードプロキシとの違いとアプリの前に Nginx を置く理由、proxy_pass の 末尾スラッシュの罠、X-Forwarded-For などの転送ヘッダーとアプリ側の trust proxy 設定、タイムアウト・バッファリング・WebSocket・upstream の基本を説明し、最後に Shop API を api.shop.example.com で公開する完全な設定例を示します。

    もとにしたノート：20_Webサーバー・リバースプロキシ/03_リバースプロキシ

    ひとことで言うと

    リバースプロキシは 「会社の代表電話の受付係」 です。お客さんは代表番号（api.shop.example.com）にしか電話をかけず、受付係が担当者（裏のアプリ）の内線（127.0.0.1:3000）につなぎます。アプリは外にさらさず、Nginx が付け足すヘッダーを アプリが正しく信頼する設定 が必要です。

    1.受付係としてのリバースプロキシ

    お客さんは担当者の内線番号を知る必要がなく、担当者が休んでいても受付が「少々お待ちください」と応対でき、担当者が増えれば受付が振り分けます。

    • クライアントから見ると、Nginx が「サーバーそのもの」に見えます
    • アプリは外部に直接さらさず、127.0.0.1（そのマシンの中からだけ届くアドレス）だけで待ち受けます
    • Nginx が付け足すヘッダーを、アプリが正しく信頼する設定が必要です

    前提として 20-2 Nginx入門 を読んでいると理解しやすくなります。

    2.フォワードプロキシとリバースプロキシ

    フォワードプロキシリバースプロキシ
    誰の代理かクライアント（利用者）サーバー（提供者）
    置く場所利用者の組織のネットワーク出口サービス提供側の入口
    主な目的社外アクセスの制限・監視、キャッシュTLS 終端、振り分け、保護、静的配信
    相手が知っていることサイト側はプロキシしか見えない利用者はプロキシしか見えない
    例Squid、企業の Web フィルタNginx、HAProxy、AWS ALB、Cloudflare

    2.1 なぜアプリの前に Nginx を置くのか

    1. TLS 終端：証明書の管理と暗号化処理を Nginx に集約できます（20-4 HTTPSとTLS証明書）
    2. 遅いクライアントの吸収：Nginx がリクエスト全体を受け取ってからアプリに渡し、レスポンスも Nginx がバッファして返します。アプリの貴重な処理能力が遅い回線に縛られません
    3. アプリを外にさらさない：アプリは 127.0.0.1 で待ち受け、80/443 番を開けるのは Nginx だけです。アプリに root 権限も不要です
    4. 1 つの入口で複数アプリ：ドメインやパスで Shop API / 管理画面 / 静的ファイルに振り分けます
    5. 無停止の切り替え・負荷分散：裏のアプリを複数台にしても、クライアントから見た入口は変わりません（50-2 ロードバランサーの仕組み）
    6. 共通処理：アクセスログ、圧縮、リクエストサイズ制限、レート制限、IP 制限

    3.proxy_pass と末尾スラッシュ

    3.1 最小の設定

    server {
    listen 80;
    server_name api.shop.example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
    }
}

    これで http://api.shop.example.com/products へのリクエストが http://127.0.0.1:3000/products に中継されます。

    localhost より 127.0.0.1 を書く

    localhost と書くと IPv6 の ::1 に解決されて、IPv4 だけで待ち受けているアプリに接続できず 502 になることがあります。アプリの待ち受けアドレスと揃えて明示しましょう。

    3.2 末尾スラッシュの挙動（最重要の罠）

    proxy_pass の URL に パス部分（/ 1 文字でも）があるかどうか で、転送先のパスが変わります。

    設定リクエストアプリに届くパス
    location /api/ { proxy_pass http://127.0.0.1:3000; }/api/products/api/products（そのまま）
    location /api/ { proxy_pass http://127.0.0.1:3000/; }/api/products/products（/api/ が / に 置き換わる）
    location /api/ { proxy_pass http://127.0.0.1:3000/v1/; }/api/products/v1/products
    location /api { proxy_pass http://127.0.0.1:3000/; }/api/products//products（✕ スラッシュが二重に）

    ルールは 1 つだけです。

    • proxy_pass に パスがない → 元の URI をそのまま渡す
    • proxy_pass に パスがある → location に一致した部分をそのパスに 置き換える

    20-2 Nginx入門 の root（連結）と alias（置き換え）の関係とそっくりです。location と proxy_pass の末尾スラッシュは揃えておくのが安全です。

    正規表現 location では URI 付き proxy_pass は書けない

    location ~ ^/api/ の中で proxy_pass http://127.0.0.1:3000/; と書くと、nginx -t でエラーになります。パスを書き換えたいときは前方一致 location を使うか、rewrite を併用します。

    4.転送ヘッダーとアプリ側の trust proxy

    4.1 何も設定しないとどうなるか

    リバースプロキシを挟むと、アプリから見た「接続相手」は常に Nginx（127.0.0.1）になります。何もしないと、アプリは次のように誤解します。

    アプリが知りたいこと何も設定しないと起きる問題
    利用者の IPすべて 127.0.0.1IP ごとのレート制限が全員共通になる、監査ログが無意味
    元のプロトコルすべて httpHTTPS なのに http:// のリダイレクト URL を生成、Secure Cookie が付かない
    元のホスト名127.0.0.1:3000（Nginx 既定は $proxy_host）絶対 URL・OAuth のコールバック URL が壊れる

    Secure 属性（HTTPS のときだけ Cookie を送る指定）については 74 Cookieの仕組み を参照してください。

    4.2 ヘッダーで伝える

    proxy_set_header Host              $host;                       # 元のホスト名
proxy_set_header X-Real-IP         $remote_addr;                # 直前の接続元 IP
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;  # 経由したIPの履歴に追記
proxy_set_header X-Forwarded-Proto $scheme;                     # http か https か
proxy_set_header X-Forwarded-Host  $host;

    X-Forwarded-For は、プロキシを通るたびに右側へ IP が追記されていくリストです。

    利用者 198.51.100.7 ─▶ CDN 203.0.113.20 ─▶ Nginx ─▶ Shop API
X-Forwarded-For: 198.51.100.7, 203.0.113.20
                 ↑本当の利用者    ↑Nginx の直前（$remote_addr）

    X-Forwarded-For は偽装できる

    クライアントは最初から X-Forwarded-For: 1.2.3.4 を付けて送れます。だから「左端の値を信じる」のは危険です。信頼してよいのは 自分が管理するプロキシが追記した部分だけ で、「右から数えて、信頼するプロキシの数だけさかのぼった値」が本当のクライアント IP です。これをアプリやフレームワークに教えるのが trust proxy 設定です。

    4.3 アプリ側：trust proxy の設定

    Shop API（Express）

    import express from "express";
const app = express();

// Nginx が同じマシン（127.0.0.1）にいる場合: ループバックからのプロキシだけを信頼
app.set("trust proxy", "loopback");
// 手前に ALB など 1 段のプロキシがあるだけなら: app.set("trust proxy", 1);

app.get("/whoami", (req, res) => {
  res.json({ ip: req.ip, protocol: req.protocol, secure: req.secure, host: req.hostname });
});

    trust proxy を設定すると、req.ip が X-Forwarded-For から、req.protocol / req.secure が X-Forwarded-Proto から計算されます。express-session の cookie.secure: true が HTTPS 下で動かない、という定番トラブルの多くはこの設定漏れが原因です。

    ✕ 危険な例：すべてのプロキシを信頼する 
    app.set("trust proxy", true);
    ◯ 安全な例：信頼するプロキシを具体的に指定する 
    app.set("trust proxy", "loopback");   // または段数 1 や IP 範囲

    trust proxy を true にしない

    true は「すべてのプロキシを信頼する」＝利用者が送った偽の X-Forwarded-For 左端を req.ip として採用します。IP 制限やレート制限を簡単にすり抜けられるので、プロキシの段数か IP 範囲で具体的に指定します。

    管理画面（FastAPI + Uvicorn）

    # Uvicorn は --proxy-headers が既定で有効。信頼するプロキシの IP を指定する（既定は 127.0.0.1）
uvicorn admin.main:app --host 127.0.0.1 --port 8000 --forwarded-allow-ips 127.0.0.1

    アプリを本番で動かす詳細は 30-2 Node.jsアプリを本番で動かす、30-3 Pythonアプリを本番で動かす で扱います。

    5.タイムアウト・バッファリング・WebSocket

    5.1 タイムアウト

    ディレクティブ意味既定値
    proxy_connect_timeoutアプリへの TCP 接続が確立するまで60s（通常 75 秒を超えられない）
    proxy_send_timeoutアプリへ送信する際、2 回の書き込みの間隔60s
    proxy_read_timeoutアプリから受信する際、2 回の読み込みの間隔60s

    proxy_read_timeout は「レスポンス全体にかかる時間」ではなく「アプリが何も送ってこない時間」の上限です。CSV エクスポートのように 2 分かかる処理が途中で 504 になるなら、その location だけ延ばします。

    location /admin/export {
    proxy_pass http://127.0.0.1:3000;
    proxy_read_timeout 300s;   # 全体を長くするのではなく、必要な場所だけ
}

    本当は長い処理はジョブキューに回して非同期にするのが筋です。タイムアウトを全体で長くすると、アプリが固まったときに接続がたまり続けて障害が広がります。

    5.2 バッファリング

    proxy_buffering on;（既定）では、Nginx がアプリのレスポンスをメモリ（足りなければ一時ファイル）に受け取りきってからクライアントへ送ります。アプリはすぐ次のリクエストに移れるので、通常はオンのままにします。

    例外は 少しずつ送り続けるレスポンス（Server-Sent Events、ストリーミング応答、LLM のトークン逐次表示など）です。バッファされると利用者に何も届かなくなるので、その location だけオフにします。

    location /events {
    proxy_pass http://127.0.0.1:3000;
    proxy_buffering off;
    proxy_read_timeout 1h;
}

    アプリ側からレスポンスヘッダー X-Accel-Buffering: no を返して、そのレスポンスだけバッファを止めることもできます。リクエスト側の proxy_request_buffering（既定 on）は、アップロードを Nginx が受け取りきってからアプリに渡すかどうかで、client_max_body_size（既定 1m）と合わせて設定します。

    5.3 WebSocket

    WebSocket（ブラウザとサーバーが接続を開いたまま双方向に送り合う仕組み）は、HTTP の Upgrade ヘッダーで別プロトコルに切り替えます。Upgrade と Connection は 隣の相手との間だけで有効なヘッダー（hop-by-hop） なので、Nginx は既定では転送しません。明示的に引き継ぎます。

    # http ブロック（conf.d/ などに置く）
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

# server ブロック内
location /ws/ {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;                       # Upgrade は HTTP/1.1 の機能
    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_read_timeout 1h;                        # 無通信 60 秒で切られないように
}

    proxy_http_version の既定値（2026 年時点）

    nginx 1.29.7 以降は proxy_http_version の既定が 1.1 になりましたが、それより前（Ubuntu 24.04 標準の 1.24 系を含む）は 1.0 です。どちらの環境でも動くよう、明示的に proxy_http_version 1.1; を書いておきます。

    6.upstream で複数台に振り分ける

    upstream ブロックで転送先のグループを定義すると、Nginx がロードバランサーとして振り分けます。

    upstream shop_api {
    server 10.0.1.11:3000 max_fails=3 fail_timeout=30s;
    server 10.0.1.12:3000 max_fails=3 fail_timeout=30s;
    keepalive 32;      # アプリとの接続を使い回す（毎回 TCP 接続しない）
}

server {
    location / {
        proxy_pass http://shop_api;
        proxy_http_version 1.1;
        proxy_set_header Connection "";   # keepalive のため "close" を送らない
        proxy_next_upstream error timeout http_502 http_503;  # 失敗時に別サーバーで再試行
    }
}

    既定はラウンドロビン（順番に配る方式）で、least_conn（接続数が最少のサーバーへ）、ip_hash（同じ IP は同じサーバーへ）なども選べます。max_fails / fail_timeout による 受動的ヘルスチェック で、失敗が続いたサーバーを一時的に外します。アルゴリズムの選び方、能動的ヘルスチェック、AWS ALB との使い分けは 50-2 ロードバランサーの仕組み で詳しく扱います。

    POST の再試行に注意

    proxy_next_upstream は既定で、POST のような 非冪等（2 回実行すると結果が変わる）リクエストを別サーバーで再試行しません。non_idempotent を付けると注文が二重に作られる恐れがあるので、付けないのが基本です。

    7.完全な設定例：Shop API を api.shop.example.com で公開

    前提：Shop API が同じサーバーの 127.0.0.1:3000 で待ち受けており、証明書は 20-4 HTTPSとTLS証明書 の手順で取得済みとします（まだなら 443 の server ブロックを外し、80 番の location / に proxy 設定を書けば HTTP で動作確認できます）。

    # /etc/nginx/conf.d/00-proxy-common.conf  （http ブロックに読み込まれる共通設定）
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      "";          # Upgrade でないときは Connection を空に → upstream の keepalive が効く
}

log_format proxy '$remote_addr - [$time_local] "$request" $status $body_bytes_sent '
                 '"$http_user_agent" rt=$request_time urt=$upstream_response_time '
                 'ua=$upstream_addr us=$upstream_status';
    # /etc/nginx/sites-available/api.shop.example.com
upstream shop_api {
    server 127.0.0.1:3000;
    keepalive 16;
}

# HTTP → HTTPS（Let's Encrypt の HTTP-01 認証用パスは certbot が処理）
server {
    listen 80;
    listen [::]:80;
    server_name api.shop.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;                       # Ubuntu 24.04 標準の nginx 1.24 の書き方
    listen [::]:443 ssl http2;
    server_name api.shop.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.shop.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.shop.example.com/privkey.pem;
    include /etc/nginx/snippets/tls-intermediate.conf;   # 次回作成する TLS 共通設定

    access_log /var/log/nginx/api.access.log proxy;
    error_log  /var/log/nginx/api.error.log;

    client_max_body_size 10m;                   # 商品画像アップロードを想定

    # 共通のプロキシ設定
    proxy_http_version 1.1;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Upgrade           $http_upgrade;
    proxy_set_header Connection        $connection_upgrade;
    proxy_connect_timeout 5s;                   # 同一マシンなので短くてよい
    proxy_read_timeout    60s;

    location / {
        proxy_pass http://shop_api;
    }

    # 注文状況のリアルタイム通知（WebSocket）
    location /ws/ {
        proxy_pass http://shop_api;
        proxy_read_timeout 1h;
    }

    # ヘルスチェックはログを汚さない
    location = /health {
        proxy_pass http://shop_api;
        access_log off;
    }
}

    nginx.org 公式リポジトリの新しい版（1.25.1 以降）を使う場合

    listen の http2 パラメータは非推奨になり、listen 443 ssl; ＋ 別行の http2 on; と書きます（古い書き方は警告が出ますが動きます）。

    sudo ln -s /etc/nginx/sites-available/api.shop.example.com /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx

# 確認：アプリ側に正しい IP とプロトコルが届いているか
curl -s https://api.shop.example.com/whoami
# {"ip":"198.51.100.7","protocol":"https","secure":true,"host":"api.shop.example.com"}

    ここで proxy_set_header を server レベルに書いたのは、各 location に繰り返さないためです。ただし 20-2 Nginx入門 で説明したとおり、ある location で proxy_set_header を 1 つでも書くと server レベルの分はすべて継承されなくなる ので、location ごとに足したいヘッダーがある場合は全部書き直すか snippet を include します。プロキシの後ろでアプリを無停止で入れ替える話は、ゼロダウンタイムデプロイのノート（別章）で扱っています。

    8.よくある誤解・つまずき

    よくある誤解

    • ✕「proxy_pass の末尾スラッシュは好みの問題」
      ◯ パスの有無で「そのまま渡す」か「置き換える」かが変わります。アプリで 404 が出たら、まずアクセスログでアプリに届いたパスを確認します。
    • ✕「X-Forwarded-For の左端が利用者の本当の IP」
      ◯ 左端は利用者が自由に書き換えられます。信頼するプロキシの段数をアプリに教え、右から数えて特定します。
    • ✕「502 / 504 はタイムアウトを延ばせば直る」
      ◯ 502 は「アプリにつながらない・不正な応答」、504 は「時間内に返事がない」です。まずアプリが動いているか、なぜ遅いかを調べ、延長は特定 location に限ります。
    • ✕「アプリも 0.0.0.0 で待ち受けておけば便利」
      ◯ Nginx をすり抜けてポート 3000 に直接アクセスでき、TLS もログも制限も効きません。同一マシンなら 127.0.0.1 で待ち受けます。

    9.まとめ

    • リバースプロキシはサーバー側の代理人。TLS 終端・遅いクライアントの吸収・振り分け・保護を担う
    • proxy_pass にパスがなければそのまま、あれば location 一致部分を置き換える
    • Host / X-Forwarded-For / X-Forwarded-Proto を付け、アプリ側で trust proxy を 具体的に 設定する
    • proxy_read_timeout は無通信時間の上限。延ばすのは必要な location だけ
    • SSE やストリーミングはバッファリングをオフ、WebSocket は Upgrade / Connection を引き継ぐ
    • 複数台は upstream で振り分け。詳細は 50-2 ロードバランサーの仕組み

    10.理解度チェック

    Q1. location /api/ { proxy_pass http://127.0.0.1:3000/; } のとき、/api/orders/5 はアプリにどのパスで届きますか。

    /orders/5 です。proxy_pass にパス（/）があるので、location に一致した /api/ が / に置き換えられます。

    Q2. HTTPS で公開しているのに、Express アプリのログイン後リダイレクトが http:// になってしまいます。原因と対策は？

    Nginx から X-Forwarded-Proto が渡されていないか、Express で trust proxy が設定されていないため、アプリが自分を HTTP だと思っています。Nginx に proxy_set_header X-Forwarded-Proto $scheme; を書き、Express で app.set("trust proxy", "loopback") のように信頼するプロキシを指定します。

    Q3. 管理画面の「売上 CSV 出力」だけが 60 秒ちょうどで 504 になります。どう対処しますか。

    proxy_read_timeout の既定 60 秒に達しています。その location だけ proxy_read_timeout 300s; などに延ばすのが応急処置です。根本的には処理をジョブキューで非同期にし、完了後にダウンロードさせる設計にします。

    Q4. Express で app.set("trust proxy", true) にしてはいけないのはなぜですか。

    すべてのプロキシを信頼するため、利用者が自分で付けた偽の X-Forwarded-For の左端が req.ip になります。IP 制限やレート制限を簡単にすり抜けられるので、"loopback" や段数・IP 範囲で具体的に指定します。

    Q5. LLM の回答を少しずつ表示する API を Nginx 経由にしたら、最後まで何も表示されなくなりました。なぜですか。

    既定の proxy_buffering on で、Nginx がレスポンスを受け取りきるまでクライアントに送らないためです。その location だけ proxy_buffering off; にするか、アプリから X-Accel-Buffering: no を返します。

    Q6. WebSocket を中継するのに Upgrade と Connection を明示的に設定する必要があるのはなぜですか。

    この 2 つは隣の相手との間だけで有効な hop-by-hop ヘッダーで、Nginx は既定では転送しないからです。proxy_http_version 1.1; とあわせて proxy_set_header で引き継ぎます。
