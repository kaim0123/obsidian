    10 サーバーの基礎

    非機能要件を支えるサーバー

    Web サイトやアプリの機能そのものではなく、運用・管理・セキュリティを裏から支えるサーバー を一通り見渡します。DHCP・DNS・NTP サーバーの役割と設定ファイルの例（dhcpd.conf／named.conf／ntp.conf）、ログ・監視・バックアップ・セキュリティ（認証）サーバー、プロキシ・メール・ファイルサーバーの役割と代表的な製品、そしてこれらを運用するときの監視・セキュリティ・災害対策の観点を解説します。

    もとにしたノート：docs/61_サーバー・インフラ/10_サーバーの基礎/07_非機能要件を支えるサーバー（DHCP・DNS・NTP・ログ・監視ほか）.md

    ひとことで言うと

    システムには、ユーザーに見える機能を出すサーバー（Web・AP・DB）のほかに、住所を配る（DHCP）・名前を引く（DNS）・時刻をそろえる（NTP）・記録する（ログ）・見張る（監視）・守る（バックアップ・認証） サーバーがいます。これらが連携して、安定したシステム運用を実現しています。

    このページは 10-6 DHCPとNTP と 10-2 サーバーの種類と役割 を読んでいると理解しやすいです。

    1.非機能要件のサーバーとは

    非機能要件 とは、「商品を買える」「ログインできる」のような 機能 そのものではなく、「止まらない」「速い」「安全」「障害時に原因を追える」といった、品質や運用に関する要求 のことです。

    非機能要件のサーバーは、システムの基本機能を直接提供するのではなく、システムの運用・管理・セキュリティを支える重要なインフラサーバー です。DHCP サーバーをはじめ、DNS サーバー、NTP サーバー、ログサーバー、監視サーバーなど、さまざまな非機能要件のサーバーが連携して、安定したシステム運用を実現しています。

    サーバーひとことで代表的な製品・設定ファイル
    DHCPIP アドレスなどを自動で配るISC DHCP（dhcpd.conf）
    DNS名前と IP を変換するBIND（named.conf）
    NTP時刻をそろえるntpd（ntp.conf）
    ログログを集めて保存・分析するrsyslog、SIEM、ELK Stack、Splunk
    監視稼働状況を見張って知らせるNagios、Zabbix、Prometheus、Grafana
    バックアップデータを複製して復旧に備えるrsync などのスクリプト、クラウドストレージ
    セキュリティ（認証）誰かを確かめ、権限を管理するActive Directory、OpenLDAP、RADIUS、SIEM
    プロキシ通信を中継するNginx（nginx.conf）
    メールメールを送受信するPostfix、Sendmail、Dovecot、SpamAssassin
    ファイルファイルを共有するSamba、NFS、FTP／SFTP

    2.DHCP サーバー

    2.1 DHCP とは

    • 定義：Dynamic Host Configuration Protocol
    • 役割：ネットワークに接続するデバイスに IP アドレスを自動で割り当てる
    • 機能：IP アドレス、サブネットマスク、デフォルトゲートウェイ、DNS サーバーの設定を配る
    • メリット：手動設定が不要になり、IP アドレスを効率よく管理できる

    2.2 DHCP サーバーの動作

    クライアントとサーバーは、次の 4 つのメッセージ（頭文字をとって DORA）でアドレスを決めます。

    1. DHCP Discover：クライアントが IP アドレスを要求する（DHCP サーバーを探す）
    2. DHCP Offer：サーバーが利用可能な IP アドレスを提示する
    3. DHCP Request：クライアントが、提示された IP アドレスを要求する
    4. DHCP Ack：サーバーが IP アドレスの割り当てを確認（承認）する

    送信元・宛先アドレス、UDP 67/68、DHCP リレー、リース更新（T1／T2）、APIPA などの詳細は 10-6 DHCPとNTP で扱っています。

    2.3 DHCP サーバーの設定例

    Linux で広く使われてきた ISC DHCP サーバーの設定ファイル dhcpd.conf の例です（10-6 で扱った Cisco ルータの ip dhcp pool と同じことを、Linux サーバーで書いたものです）。

    # DHCPサーバー設定ファイル（dhcpd.conf）
subnet 192.168.1.0 netmask 255.255.255.0 {
    range 192.168.1.100 192.168.1.200;
    option routers 192.168.1.1;
    option domain-name-servers 8.8.8.8, 8.8.4.4;
    option domain-name "example.com";
    default-lease-time 600;
    max-lease-time 7200;
}
    行意味
    subnet … netmask …このネットワーク（192.168.1.0/24）向けの設定のまとまり（スコープ）
    range貸し出すアドレスの範囲（.100〜.200）
    option routersデフォルトゲートウェイ
    option domain-name-serversDNS サーバー
    option domain-nameドメイン名
    default-lease-time / max-lease-timeリース期間の既定値と最大値（秒）。600 秒＝10 分、7200 秒＝2 時間

    2.4 DHCP サーバーの管理

    リース管理

    IP アドレスの有効期限を管理します。

    予約設定

    特定のデバイス（プリンターやサーバーなど）に、いつも同じ固定 IP を割り当てます。

    スコープ管理

    ネットワークセグメント（区切られたネットワークの単位）ごとに設定を分けます。

    監視

    リース状況（どれだけ貸し出し済みか、枯渇していないか）を監視します。

    3.DNS サーバー

    DNS レコード（A・AAAA・CNAME・TTL など）と名前解決の流れは 10-5 ネットワークの基本 で扱いました。ここでは DNS サーバーを運用する側から見ます。

    3.1 DNS サーバーの役割

    • 名前解決：ドメイン名と IP アドレスを相互に変換する（名前 → IP の正引き、IP → 名前の逆引き）
    • キャッシュ：問い合わせ結果を一時保存する
    • 冗長化：複数の DNS サーバーを置いて信頼性を高める
    • セキュリティ：DNS over HTTPS（DNS の問い合わせを HTTPS で暗号化する）、DNSSEC（DNS の回答に電子署名を付け、改ざんを見抜けるようにする）

    3.2 DNS サーバーの種類

    種類役割
    権威 DNS サーバー特定ドメインの情報（正解）を管理する
    キャッシュ DNS サーバー問い合わせ結果をキャッシュする
    フォワーダー受けた問い合わせを、ほかの DNS サーバーへ転送する
    リゾルバークライアントからの問い合わせを処理する（10-5 の「フルリゾルバー」は、キャッシュ DNS サーバーとしてこの役を担います）

    3.3 DNS サーバーの設定例

    代表的な DNS サーバーソフト BIND の設定ファイル named.conf の例です。ゾーン（そのサーバーが責任を持つドメインの範囲）ごとに、レコードを書いたファイルを指定します。

    # BIND設定ファイル（named.conf）
zone "example.com" {
    type master;
    file "/var/named/example.com.zone";
};

zone "1.168.192.in-addr.arpa" {
    type master;
    file "/var/named/192.168.1.rev";
};
    • zone "example.com"：example.com の正引き（名前 → IP）のゾーンです。
    • zone "1.168.192.in-addr.arpa"：192.168.1.0/24 の 逆引き（IP → 名前）のゾーンです。逆引きでは IP アドレスを逆順に並べ、in-addr.arpa を付けた名前で表します。
    • type master：このサーバーがゾーンの原本を持つ（権威 DNS のプライマリ）という意味です。

    4.NTP サーバー

    4.1 NTP とは

    • 定義：Network Time Protocol
    • 役割：ネットワーク上のデバイスの時刻を同期する
    • 重要性：ログの整合性、セキュリティ、認証
    • 精度：ミリ秒レベルの時刻同期

    4.2 NTP サーバーの階層

    階層内容
    Stratum 0原子時計、GPS
    Stratum 1Stratum 0 に直接接続
    Stratum 2Stratum 1 に接続
    Stratum 3Stratum 2 に接続

    値が小さいほど正確で、16 は「同期していない」を表すことなど、ストラタムの詳細と Cisco での設定・確認は 10-6 DHCPとNTP で扱っています。

    4.3 NTP サーバーの設定例

    # NTP設定ファイル（ntp.conf）
server 0.pool.ntp.org
server 1.pool.ntp.org
server 2.pool.ntp.org
server 3.pool.ntp.org

restrict default nomodify notrap nopeer noquery
restrict 127.0.0.1
restrict 192.168.1.0 mask 255.255.255.0
    • server *.pool.ntp.org：時刻をもらう上位のサーバーです。pool.ntp.org は世界中のボランティアの NTP サーバーをまとめたもので、4 つ書いて 1 台が落ちても大丈夫なようにしています。
    • restrict default nomodify notrap nopeer noquery：既定では、設定の変更・トラップ（通知）・ピア（対等な同期相手）・状態の問い合わせを許さない、という制限です。
    • restrict 127.0.0.1：自分自身からは制限なし。
    • restrict 192.168.1.0 mask 255.255.255.0：社内の 192.168.1.0/24 からの時刻の問い合わせを許可します（このサーバーが社内の NTP サーバーになります）。

    補足：最近の Linux では chrony が標準

    RHEL 系や Ubuntu の新しい版では、時刻同期に ntpd ではなく chrony（設定ファイル chrony.conf）や systemd-timesyncd が標準で使われています。server／pool で上位サーバーを指定する考え方は同じです。

    5.ログサーバー

    5.1 ログサーバーの役割

    • ログ収集：複数のシステムからログを集める
    • ログ保存：長期保存とアーカイブ（古いデータを保管用にまとめること）
    • ログ分析：ログを検索・分析する
    • アラート：異常なログを検出して通知する

    ログを 1 か所に集めておけば、サーバーが壊れたり攻撃者にログを消されたりしても記録が残り、複数サーバーの出来事を時系列で並べられます（そのためにも NTP で時刻をそろえておくことが前提です）。

    5.2 ログサーバーの種類

    種類内容
    Syslog サーバーシステムログを収集する（Syslog はログを転送するための標準的な仕組み）
    SIEMセキュリティ情報とイベント管理（Security Information and Event Management）。多数のログを突き合わせて攻撃の兆候を見つける
    ログ分析ツールELK Stack（Elasticsearch・Logstash・Kibana の組み合わせ）、Splunk
    監査ログコンプライアンス（法令や社内規則の順守）対応のための記録

    5.3 ログサーバーの設定例

    Linux 標準の rsyslog で、ほかの機器からログを受け取るサーバーにする例です。

    # rsyslog設定ファイル（rsyslog.conf）
# リモートログの受信
$ModLoad imudp
$UDPServerRun 514

# ログの保存先
local0.*    /var/log/application.log
local1.*    /var/log/security.log
local2.*    /var/log/network.log
    • $ModLoad imudp と $UDPServerRun 514：UDP 受信モジュールを読み込み、Syslog の標準ポート UDP 514 でログを受け付けます。
    • local0.* /var/log/application.log：「ファシリティ（ログの分類）が local0 のログは、重大度にかかわらず（*）application.log に書く」という振り分けです。local0〜local7 は利用者が自由に使える分類です。

    この $ModLoad 形式は古くからの書き方で、新しい rsyslog では module(load="imudp") と input(type="imudp" port="514") という書き方も使えます。

    ログを使ったセキュリティ監視は 60-5 ログ監査と侵入の検知 で扱います。Syslog の重大度や転送、ログ集約基盤は 66_可観測性のノート（「Syslog（ログ転送の標準プロトコル）」「ログ集約基盤」）にまとまっています。

    6.監視サーバー

    6.1 監視サーバーの役割

    • システム監視：CPU、メモリ、ディスクを監視する
    • サービス監視：アプリケーションの稼働状況を監視する
    • ネットワーク監視：ネットワークの状態を監視する
    • アラート：異常時に通知する

    6.2 監視サーバーの種類

    製品特徴
    Nagiosオープンソースの監視システム
    Zabbix統合監視システム
    Prometheusメトリクス（CPU 使用率などの数値データ）の収集・保存
    Grafana可視化・ダッシュボード

    6.3 監視サーバーの設定例

    # Prometheus設定ファイル（prometheus.yml）
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: "node-exporter"
    static_configs:
      - targets: ["localhost:9100"]

  - job_name: "web-server"
    static_configs:
      - targets: ["192.168.1.10:80"]
    • scrape_interval: 15s：15 秒ごとに監視対象から数値を取りに行きます（Prometheus は自分から取りに行く「プル型」です）。
    • node-exporter（localhost:9100）：サーバーの CPU・メモリ・ディスクなどの数値を公開する小さなプログラムです。
    • web-server（192.168.1.10:80）：Web サーバーの数値を取りに行く対象です。

    ネットワーク機器の監視（SNMP）は 66_可観測性の「SNMP（ネットワーク機器のメトリクス収集）」のノートにまとまっています。

    7.バックアップサーバー

    7.1 バックアップサーバーの役割

    • データバックアップ：システムのデータを定期的にバックアップする
    • 復旧：障害時にデータを復旧する
    • アーカイブ：長期保存データを管理する
    • 災害対策：災害時の事業継続を支える

    7.2 バックアップサーバーの種類

    ファイルバックアップ

    ファイルシステムのバックアップ

    データベースバックアップ

    データベースのバックアップ

    システムバックアップ

    システム全体のバックアップ

    クラウドバックアップ

    クラウドストレージへのバックアップ

    7.3 バックアップサーバーの設定例

    rsync（ファイルを差分だけ効率よくコピーするコマンド）を使ったバックアップスクリプトの例です。

    # rsyncを使用したバックアップスクリプト
#!/bin/bash
SOURCE_DIR="/var/www/html"
BACKUP_DIR="/backup/web"
DATE=$(date +%Y%m%d_%H%M%S)

rsync -av --delete $SOURCE_DIR/ $BACKUP_DIR/$DATE/
    • DATE=$(date +%Y%m%d_%H%M%S)：実行した日時（例：20261018_093000）を名前にしたフォルダへコピーするので、世代ごとに残ります。
    • -a：権限や更新日時を保ったままコピー（アーカイブモード）。-v：経過を表示。
    • --delete：コピー元で消えたファイルは、コピー先からも消します。

    データベースのバックアップは 30-6 データベースサーバーの運用、冗長化と災害対策は 50-5 高可用性と冗長化 で扱います。

    8.セキュリティサーバー

    8.1 セキュリティサーバーの役割

    • 認証：ユーザーの身元を確認する
    • 認可：アクセス権限を管理する
    • 監査：アクセスログを記録する
    • 脅威検知：不正アクセスを検出する

    認証と認可の違いは 73 認証と認可の違い で詳しく扱っています。

    8.2 セキュリティサーバーの種類

    種類内容
    Active DirectoryWindows 環境の認証（社内のユーザー・PC をまとめて管理する Microsoft の仕組み）
    LDAP サーバーディレクトリサービス（ユーザーや組織の情報を木構造で管理し、問い合わせに答える）
    RADIUS サーバーネットワーク認証（Wi-Fi や VPN、ネットワーク機器へのログインなど）
    SIEMセキュリティ情報管理（5 章のログサーバーと同じもの）

    RADIUS などを使ったネットワーク機器の認証は 60-7 AAA で扱います。

    8.3 セキュリティサーバーの設定例

    LDAP サーバーソフト OpenLDAP の設定ファイル slapd.conf の例です。

    # OpenLDAP設定ファイル（slapd.conf）
database bdb
suffix "dc=example,dc=com"
rootdn "cn=admin,dc=example,dc=com"
rootpw {SSHA}password_hash
    • database bdb：データの保存方式（バックエンド）。
    • suffix "dc=example,dc=com"：このサーバーが管理する木の根（example.com に対応）。
    • rootdn：管理者アカウントの名前。
    • rootpw {SSHA}…：管理者のパスワード。平文ではなく、{SSHA}（ソルト付き SHA-1）でハッシュ化した値を書きます。

    補足：新しい OpenLDAP では書き方が変わっている

    OpenLDAP 2.5 以降では bdb バックエンドは廃止され、mdb を使います。また設定は slapd.conf ではなく、設定自体を LDAP の中に持つ cn=config 方式が推奨されています。上の例は考え方をつかむためのものと考えてください。

    9.プロキシサーバー

    9.1 プロキシサーバーの役割

    • 中継：クライアントとサーバーの間で通信を中継する
    • キャッシュ：よくアクセスされるコンテンツをキャッシュする
    • フィルタリング：不正なコンテンツをブロックする
    • 負荷分散：複数のサーバーに負荷を分散する

    9.2 プロキシサーバーの種類

    種類内容
    Web プロキシHTTP/HTTPS 通信を中継する
    リバースプロキシサーバー側に置くプロキシ（外からの通信を受けて、裏のサーバーへ渡す）
    フォワードプロキシクライアント側に置くプロキシ（社内からの外向き通信をまとめて中継する）
    透明プロキシクライアントが設定しなくても、気づかないうちに通る（透過的な）プロキシ

    9.3 プロキシサーバーの設定例

    Nginx をリバースプロキシとして使い、2 台のバックエンドへ振り分ける例です。

    # Nginx設定ファイル（nginx.conf）
upstream backend {
    server 192.168.1.10:8080;
    server 192.168.1.11:8080;
}

server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
    • upstream backend：転送先のサーバーのグループ。2 台に順番に振り分けます（負荷分散）。
    • proxy_pass http://backend：受けたリクエストをそのグループへ転送します。
    • proxy_set_header：元のホスト名（Host）と、本当の接続元 IP（X-Real-IP）を裏のサーバーへ伝えます。

    詳しい設定は 20-3 リバースプロキシ、負荷分散の仕組みは 50-2 ロードバランサーの仕組み で扱います。

    10.メールサーバー

    10.1 メールサーバーの役割

    • メール送信：SMTP サーバー
    • メール受信：POP3／IMAP サーバー（POP3 はメールを手元にダウンロードする方式、IMAP はサーバー上に置いたまま読む方式）
    • スパムフィルタリング：不正メールをブロックする
    • ウイルススキャン：メールの添付ファイルをスキャンする

    10.2 メールサーバーの種類

    製品内容
    Postfix高機能な SMTP サーバー
    Sendmail伝統的な SMTP サーバー
    DovecotIMAP/POP3 サーバー
    SpamAssassinスパムフィルタリング

    10.3 メールサーバーの設定例

    # Postfix設定ファイル（main.cf）
myhostname = mail.example.com
mydomain = example.com
myorigin = $mydomain
mydestination = $myhostname, localhost.$mydomain, localhost, $mydomain
relayhost = [smtp.gmail.com]:587
    • myhostname / mydomain：このメールサーバーのホスト名とドメイン名。
    • myorigin = $mydomain：送信するメールの差出人ドメインを example.com にします。
    • mydestination：「自分宛て」として受け取るドメインの一覧。
    • relayhost = [smtp.gmail.com]:587：外へ送るメールを、直接ではなく指定した SMTP サーバー（587 番＝メール送信用ポート）経由で送ります。

    11.ファイルサーバー

    11.1 ファイルサーバーの役割

    • ファイル共有：ネットワーク経由でファイルを共有する
    • アクセス制御：ファイルへのアクセス権限を管理する
    • バックアップ：ファイルを自動でバックアップする
    • 同期：複数のデバイス間でファイルを同期する

    11.2 ファイルサーバーの種類

    種類内容
    SambaWindows 互換のファイル共有
    NFSUnix/Linux 環境のファイル共有
    FTP サーバーファイル転送プロトコル
    SFTP サーバーセキュアな（SSH で暗号化した）ファイル転送

    11.3 ファイルサーバーの設定例

    # Samba設定ファイル（smb.conf）
[global]
workgroup = WORKGROUP
server string = File Server
security = user

[shared]
path = /srv/shared
browseable = yes
writable = yes
valid users = @users
    • [global]：サーバー全体の設定。security = user はユーザー名とパスワードで認証する方式です。
    • [shared]：shared という名前の共有フォルダ。実体は /srv/shared です。
    • browseable = yes：一覧に表示する。writable = yes：書き込みを許可する。
    • valid users = @users：users グループのユーザーだけがアクセスできます（アクセス制御）。

    12.非機能要件サーバーの運用

    これらのサーバー自体も止まったり攻撃されたりします。運用では次の 3 つの観点で守ります。

    運用管理

    • 監視：各サーバーの稼働状況を監視
    • バックアップ：設定ファイルとデータをバックアップ
    • 更新：セキュリティパッチを適用
    • ログ管理：ログの収集・分析・保存

    セキュリティ対策

    • アクセス制御：適切な権限管理
    • 暗号化：通信とデータの暗号化
    • 監査：アクセスログの記録・分析
    • 脆弱性管理：セキュリティホールの対策

    災害対策

    • 冗長化：複数サーバーで冗長化
    • バックアップ：定期的なバックアップ
    • 復旧計画：災害時の復旧手順
    • テスト：災害対策を定期的にテスト

    パッチ適用は 60-4 OSのハードニングとパッチ管理、冗長化は 50-5 高可用性と冗長化 で扱います。

    13.まとめ

    • 非機能要件のサーバーは、システムの基本機能を直接提供するのではなく、運用・管理・セキュリティを支える重要なインフラ です。
    • DHCP（アドレス配布）、DNS（名前解決）、NTP（時刻同期）は、ネットワークの土台になるサービスです。
    • ログサーバーと監視サーバーで「何が起きたか」「今どうなっているか」を把握し、バックアップとセキュリティ（認証）サーバーでデータと利用者を守ります。
    • プロキシ・メール・ファイルサーバーも、通信の中継・連絡・共有を支えます。
    • これらのサーバー自体も、監視・セキュリティ対策・災害対策の対象です。適切な設計と運用により、効率的で安全なシステムインフラを構築できます。

    次の章 20-1 Webサーバーとは からは、サービス本体を届ける Web サーバーを扱います。

    14.理解度チェック

    Q1. 「非機能要件のサーバー」とはどんなサーバーですか？ 例を 3 つ挙げてください。

    システムの基本機能（商品を買える、など）を直接提供するのではなく、運用・管理・セキュリティを支えるサーバーです。例：DHCP サーバー、DNS サーバー、NTP サーバー、ログサーバー、監視サーバー、バックアップサーバー、認証サーバーなど。

    Q2. dhcpd.conf の range 192.168.1.100 192.168.1.200; と default-lease-time 600; は何を表しますか？

    range は貸し出すアドレスの範囲（192.168.1.100〜200）、default-lease-time 600 はリース期間の既定値が 600 秒（10 分）であることを表します。

    Q3. 権威 DNS サーバーとキャッシュ DNS サーバーの違いは？

    権威 DNS サーバーは、特定ドメインの情報（正解）を管理するサーバーです。キャッシュ DNS サーバーは、利用者からの問い合わせに答えるために、ほかのサーバーに聞いた結果を TTL の間キャッシュするサーバーです。

    Q4. named.conf の zone "1.168.192.in-addr.arpa" は何のゾーンですか？

    192.168.1.0/24 の逆引き（IP アドレス → 名前）のゾーンです。逆引きでは IP アドレスを逆順に並べ、in-addr.arpa を付けた名前で表します。

    Q5. ログを 1 台のログサーバーに集める利点と、そのときに欠かせない前提は？

    複数システムのログを 1 か所で検索・分析・長期保存でき、異常を検出して通知できます。元のサーバーが壊れてもログが残ります。前提として、NTP で全サーバーの時刻をそろえておかないと、ログを時系列で突き合わせられません。

    Q6. Prometheus と Grafana は、それぞれ何を担当しますか？

    Prometheus はメトリクス（CPU 使用率などの数値）を収集・保存し、Grafana はそれを可視化してダッシュボードに表示します。

    Q7. リバースプロキシとフォワードプロキシの違いは？

    リバースプロキシはサーバー側に置き、外からの通信を受けて裏のサーバーへ渡します（負荷分散や HTTPS の終端など）。フォワードプロキシはクライアント側に置き、社内などからの外向きの通信を中継します（キャッシュやフィルタリングなど）。

    Q8. 非機能要件サーバーの災害対策として挙げられている 4 つの観点は？

    冗長化（複数サーバー）、定期的なバックアップ、災害時の復旧計画（手順）、そして災害対策の定期的なテストです。
