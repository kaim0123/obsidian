    10 サーバーの基礎

    ネットワークの基本（IP・ポート・DNS）

    サーバーを公開するときに最低限必要なネットワークの知識を、IP アドレス・ポート・DNS の 3 つに絞って解説します。IPv4／IPv6、グローバル／プライベート IP、CIDR、NAT、ポート番号と TCP／UDP、0.0.0.0 と 127.0.0.1 で listen する違い、DNS レコードと名前解決の流れ、shop.example.com を自分のサーバーに向ける手順、そして「繋がらない」ときの疎通確認コマンドまでを扱います。

    もとにしたノート：docs/61_サーバー・インフラ/10_サーバーの基礎/05_ネットワークの基本（IP・ポート・DNS）.md

    ひとことで言うと

    ネットワークは 郵便 です。IP アドレス＝建物の住所（どのサーバーか）、ポート番号＝部屋番号（そのサーバーのどのプログラムか）、DNS＝住所録（名前から住所を調べる）。サーバー運用の「繋がらない」トラブルの大半は、この 3 つのどれかの設定ミスです。

    このページは 10-1 サーバーとは何か と 10-4 Linuxサーバーの基本 を読んでいると理解しやすいです。

    1.ネットワークは「郵便」

    IP アドレス＝住所

    どの建物（サーバー）宛てかを表します。例：203.0.113.10

    ポート番号＝部屋番号

    その建物の、どの部屋（プログラム）宛てかを表します。例：443 番＝HTTPS の Nginx

    DNS＝住所録

    shop.example.com という名前から、住所（IP）を調べます。

    https://shop.example.com を開くと、ブラウザは DNS で住所（IP）を調べ、その建物の 443 号室（HTTPS の Nginx）に手紙（リクエスト）を届けます。

    OSI 参照モデル（通信の仕組みを 7 つの層に分けた考え方）やルーティング（経路の選び方）のような理論の深掘りは、11_コンピューターサイエンスのノート（コンピューターサイエンス体系の MOC）に譲ります。ここでは サーバーを公開するのに必要な最低限 に絞ります。

    2.IP アドレス

    2.1 IPv4 と IPv6

    IPv4IPv6
    書き方203.0.113.10（0〜255 の数を 4 つ）2001:db8::10（16 進数を : で区切る。連続する 0 は :: で省略）
    数約 43 億個（枯渇している）事実上無限
    現状まだ主流。クラウドのパブリック IPv4 は有料化が進んでいる普及中。モバイル回線では多数派

    例に出てくるアドレス

    203.0.113.0/24 や 2001:db8::/32 は ドキュメント用に予約された アドレスで、実在のサーバーには割り当てられません。このシリーズでは、例として使う Shop サービスのサーバーの IP を 203.0.113.10 とします。

    2.2 グローバル IP とプライベート IP

    • グローバル IP（パブリック IP）：インターネット上で一意（ほかと重ならない）な住所。外から直接届きます。
    • プライベート IP：家庭や社内、クラウドの VPC（クラウド上に作る自分専用のネットワーク）の中だけで使う住所。インターネットからは直接届きません。

    プライベート IP として使える範囲は、RFC 1918（インターネットの標準を定めた文書の 1 つ）で決まっています。

    範囲CIDRよく見る場所
    10.0.0.0 〜 10.255.255.25510.0.0.0/8AWS の VPC、社内ネットワーク
    172.16.0.0 〜 172.31.255.255172.16.0.0/12Docker の既定ネットワーク（172.17.0.0/16）、AWS のデフォルト VPC（172.31.0.0/16）
    192.168.0.0 〜 192.168.255.255192.168.0.0/16家庭のルーター

    特別なアドレスとして、127.0.0.1（ループバック、localhost） は「自分自身」を指し、外には一切出ていきません。

    2.3 CIDR 表記

    CIDR（Classless Inter-Domain Routing、サイダー） は、IP アドレスの範囲を アドレス/数字 で表す書き方です。/ の後ろの数字は「先頭から何ビットが固定か（ネットワーク部）」を表し、残りのビットで個々のホスト（機器）を表します。

    CIDR固定ビットアドレス数意味
    203.0.113.10/32321その 1 つだけ（ファイアウォールで「自宅 IP だけ許可」など）
    10.0.1.0/242425610.0.1.0〜10.0.1.255（サブネットの典型）
    10.0.0.0/161665,53610.0.0.0〜10.0.255.255（VPC 全体の典型）
    0.0.0.0/00すべて「どこからでも」

    計算のコツ：アドレス数は 2^(32 - 数字) です。/24 なら 2^8 = 256 個です（AWS のサブネットでは、そのうち 5 個が予約されていて使えません）。

    0.0.0.0/0 に SSH を開けない

    セキュリティグループ（AWS のファイアウォール機能）で 0.0.0.0/0 を SSH（22 番）に許可するのは「全世界から SSH を受け付ける」という意味なので避けます。詳しくは 60-3 ファイアウォールとネットワーク制御 で扱います。

    2.4 NAT

    NAT（Network Address Translation） は、プライベート IP とグローバル IP を変換する仕組みです。

    • 中から外へ出る通信は、送信元を NAT のグローバル IP に書き換えて出ていきます。返事は、NAT が覚えている対応表を使って元の端末に戻します。
    • 逆に、外から中の端末へ、いきなり通信を始めることはできません。これが「プライベート IP のサーバーには外から直接届かない」理由です。
    • AWS では、パブリック IP を持つ EC2（AWS の仮想サーバー）も、OS 上ではプライベート IP（例：10.0.1.23）しか見えません。インターネットゲートウェイが 1 対 1 で変換しているからです。ip addr にグローバル IP が出てこなくても正常です。

    Shop をステージ 2 以降でサーバーごとに分離するとき、DB サーバーには プライベート IP だけ を持たせ、インターネットから直接届かないようにするのが定石です。

    3.ポートと TCP / UDP

    3.1 ポート番号

    1 台のサーバーでは、複数のプログラムが同時に通信します。どのプログラム宛てかを区別するのが ポート番号（0〜65535） です。

    範囲名前説明
    0〜1023well-known ポート定番サービス用。Linux では使うのに root 権限（または特別な権限）が必要
    1024〜49151registered ポートアプリ用（3000、5432、8080 など）
    49152〜65535dynamic / ephemeral ポートクライアント側の送信元ポートとして OS が自動で割り当てる
    ポートプロトコル用途
    22TCPSSH
    25 / 587TCPSMTP（メール送信）
    53UDP/TCPDNS
    80TCPHTTP
    443TCP（HTTP/3 は UDP）HTTPS
    3000TCPNode.js アプリの慣習（Shop API）
    3306TCPMySQL
    5432TCPPostgreSQL
    6379TCPRedis

    Shop API が 80 番ではなく 3000 番で待つのは、1024 未満のポートを使うには特権が必要で、アプリを root で動かしたくない からです。80/443 は Nginx が受け、内側の 3000 番へ転送します（20-3 リバースプロキシ）。

    3.2 TCP と UDP

    TCP（Transmission Control Protocol）UDP（User Datagram Protocol）
    例え書留郵便（届いたか確認、順番保証）普通のハガキ（送りっぱなし）
    接続最初に 3-way ハンドシェイク（3 回のやり取り）で接続を確立接続なしでいきなり送る
    信頼性再送・順序保証ありなし（アプリ側で対処）
    速さオーバーヘッド（余分な手間）がある軽くて速い
    用途HTTP/1.1・HTTP/2、SSH、DB 接続DNS 問い合わせ、動画通話、ゲーム、HTTP/3（QUIC）

    ファイアウォールでポートを開けるときは、「443/tcp」のように TCP か UDP かも指定します。

    3.3 0.0.0.0 と 127.0.0.1 で listen する違い

    サーバープログラムは「どのアドレスの、どのポートで待つか」を指定して listen（待ち受け） します。ここは本番で頻出のつまずきポイントです。

    listen アドレス意味誰が接続できるか
    127.0.0.1:3000ループバックだけで待つ同じサーバー内のプログラムだけ（Nginx からは OK、外からは不可）
    0.0.0.0:3000すべての IPv4 アドレスで待つ外部からも（ファイアウォールが許せば）接続できる
    [::]:3000すべての IPv6（設定により IPv4 も）同上
    10.0.1.23:5432特定のプライベート IP で待つ同じネットワーク内から
     
    // Shop API（Node.js）: Nginx の内側にいるので localhost だけで待つ
app.listen(3000, "127.0.0.1");
    • Shop API は 127.0.0.1:3000 で待ちます。外から 3000 番に直接来られると、Nginx の HTTPS や制限をすり抜けてしまうからです。
    • PostgreSQL も、同じサーバーに同居している間は localhost のみ で待ちます（listen_addresses = 'localhost' が既定値）。DB を別サーバーに分離したら、プライベート IP で待つよう変更し、pg_hba.conf（PostgreSQL の接続許可の設定ファイル）とファイアウォールで API サーバーからだけ許可します。
    • 逆に、Docker コンテナの中では 0.0.0.0 で listen しないと、外（ホスト）から届きません。「手元では動くのにコンテナだと繋がらない」原因の定番です（53_コンテナの「Dockerとは」のノートも参照）。

    4.DNS

    4.1 DNS レコード

    DNS（Domain Name System） は、ドメイン名と IP アドレスなどを対応付ける、世界規模の分散データベースです。登録する 1 行 1 行を レコード（record） と呼びます。

    レコード意味例
    A名前 → IPv4 アドレスshop.example.com. A 203.0.113.10
    AAAA名前 → IPv6 アドレスshop.example.com. AAAA 2001:db8::10
    CNAME名前 → 別の名前（別名）www.shop.example.com. CNAME shop.example.com.
    MXメールの配送先example.com. MX 10 mail.example.com.
    TXT任意の文字列（ドメイン所有確認、SPF など）example.com. TXT "v=spf1 include:amazonses.com ~all"
    NSこのドメインを管理する DNS サーバーexample.com. NS ns1.example-dns.net.
    • CNAME はゾーンの頂点（example.com そのもの）には置けず、同じ名前でほかのレコードと共存することもできません。ロードバランサーのように IP が変わる相手を頂点で指したいときは、Route 53（AWS の DNS サービス）の エイリアスレコード や、Cloudflare の CNAME フラットニングを使います。
    • TTL（Time To Live）：その回答を何秒キャッシュ（一時保存）してよいか。300 なら 5 分です。TTL が長いと、IP を変えても古い IP を見続ける人が TTL の間残ります。

    引っ越し前に TTL を下げる

    サーバーの IP を変える予定があるなら、数日前に TTL を 300 秒程度に下げておき、切り替え後に元に戻します。これで切り替えが数分で全体に行き渡ります。

    4.2 名前解決の流れ

    • フルリゾルバー（キャッシュ DNS）：利用者の代わりに走り回って答えを探し、TTL の間キャッシュします。
    • 権威 DNS サーバー（authoritative）：そのドメインの「正解」を持っているサーバーです。Route 53 や Cloudflare、お名前.com の DNS など、あなたがレコードを登録する場所 がこれです。
    • ブラウザ・OS・リゾルバーの各段にキャッシュがあるので、変更がすぐ反映されないのは TTL のせいです。

    DNS サーバー自体を運用する側の話（BIND の設定など）は 10-7 非機能要件を支えるサーバー で触れます。

    5.shop.example.com をサーバーに向ける手順

    1. ドメインを取得する：レジストラ（ドメインを販売・登録する事業者。お名前.com、Route 53、Cloudflare Registrar など）で example.com を購入します。
    2. 権威 DNS を決める：レジストラ付属の DNS をそのまま使うか、Route 53 などにホストゾーン（ドメインのレコードをまとめる入れ物）を作り、レジストラ側で NS レコード（ネームサーバー） をそちらに向けます。
    3. サーバーの固定 IP を確認する：EC2 なら Elastic IP（固定のパブリック IP）を割り当てます。停止・起動でパブリック IP が変わるためです。VPS は通常、最初から固定です。
    4. レコードを登録する（下のコード）。
    5. 反映を確認する（下のコード）。
    6. ファイアウォールで 80/443 を開け、Nginx で server_name shop.example.com を設定 します（20-2 Nginx入門）。
    7. HTTPS 証明書を取得 します。Let's Encrypt は、DNS が正しく向いていないと証明書を発行できません（20-4 HTTPSとTLS証明書）。
    手順 4：レコードを登録する

    6.疎通確認コマンド

    「繋がらない」ときは、外側から順に 切り分けます。DNS → 経路 → ポートとアプリ → サーバー内、の順です。

    # ① 名前は正しく引けるか（DNS）
dig shop.example.com +short
dig shop.example.com            # ANSWER SECTION と TTL を確認

# ② その IP に届くか（ネットワーク）
ping -c 4 203.0.113.10          # ※ICMP を遮断しているサーバーも多いので、失敗＝停止とは限らない
traceroute 203.0.113.10         # 途中のどこで止まるか（sudo apt install traceroute）

# ③ ポートが開いていて HTTP が返るか（アプリ）
curl -v https://shop.example.com/
#   * Connected to shop.example.com (203.0.113.10) port 443   ← TCP 接続成功
#   * SSL connection using TLSv1.3 ...                       ← TLS 成功
#   < HTTP/2 200                                             ← HTTP 応答
curl -I http://127.0.0.1:3000/health   # サーバー内から API に直接（Nginx を介さず）

# ④ サーバー側で、誰がどのアドレス:ポートで待っているか
sudo ss -tlnp
#   State  Local Address:Port  Process
#   LISTEN 0.0.0.0:443         users:(("nginx",pid=812,...))
#   LISTEN 127.0.0.1:3000      users:(("node",pid=1033,...))
#   LISTEN 127.0.0.1:5432      users:(("postgres",pid=640,...))

    ss のオプションは、-t（TCP）、-l（listen 中のみ）、-n（名前解決せず数字で表示）、-p（プロセスを表示）です。ping が使う ICMP は、通信の到達確認やエラー通知に使うプロトコルです。

    6.1 症状別の原因と確認

    症状よくある原因確認
    dig で IP が返らない / 古い IPレコード未登録、NS の向き先違い、TTL キャッシュdig @権威DNS、dig NS example.com
    curl がタイムアウトファイアウォール / セキュリティグループで閉じているsudo ufw status、クラウドのコンソール
    curl が Connection refusedそのポートで誰も listen していないsudo ss -tlnp、systemctl status nginx
    502 Bad GatewayNginx は動いているが、裏の API が落ちているcurl 127.0.0.1:3000、journalctl -u shop-api
    サーバー内からは繋がるが、外から繋がらないアプリが 127.0.0.1 で listen している（意図どおりか確認）ss -tlnp の Local Address

    タイムアウトと Connection refused の違い

    タイムアウトは途中で捨てられている（ファイアウォール）、refused はサーバーまで届いたが待ち受けがいない（プロセス未起動・ポート違い） というヒントになります。この違いは重要です。

    7.よくある誤解・つまずき

    ✕ 誤解◯ 実際
    DNS を変更したら、すぐ全員に反映されるTTL の間は各地のキャッシュが古い値を返す。変更前に TTL を短くしておく
    ping が通らない＝サーバーが落ちているICMP を遮断しているだけのことも多い（AWS のセキュリティグループは既定で ICMP を許可しない）。curl で実際のポートを確認する
    アプリは 0.0.0.0 で listen しておけば安心外部に公開されてしまう。Nginx の裏にいる API や同居の DB は 127.0.0.1 で待つ。逆にコンテナ内では 0.0.0.0 が必要
    EC2 の ip addr にグローバル IP が出ないのは設定ミスAWS は NAT で 1 対 1 変換しているので、OS にはプライベート IP しか見えないのが正常
    CNAME で example.com（頂点）をロードバランサーに向ければいい頂点には CNAME を置けない。エイリアスレコードなどを使う

    8.まとめ

    • IP アドレスは住所、ポートは部屋番号、DNS は住所録。
    • プライベート IP（10/8・172.16/12・192.168/16）は外から直接届かない。NAT で外に出る。CIDR の / の後の数字が大きいほど範囲は狭い。
    • 1024 未満のポートは特権が必要。だから Nginx が 80/443 を受け、API は 127.0.0.1:3000 で内側に隠す。
    • DNS は A / AAAA / CNAME / TTL を押さえる。ドメインを向けるのは「権威 DNS に A レコードを登録」すること。
    • 疎通確認は DNS（dig）→ 経路（ping traceroute）→ ポートとアプリ（curl -v）→ サーバー内（ss -tlnp）の順に切り分ける。

    次の 10-6 DHCPとNTP では、IP アドレスの自動割り当てと時刻同期を扱います。80/443 で待ち受ける Web サーバーは 20-1 Webサーバーとは から始まります。

    9.理解度チェック

    Q1. 10.0.1.0/24 には何個のアドレスが含まれますか？ また 0.0.0.0/0 は何を意味しますか？

    2^(32-24) = 256 個（10.0.1.0〜10.0.1.255）です。0.0.0.0/0 は固定ビットが 0 なので「すべての IPv4 アドレス」、つまり「どこからでも」を意味します。

    Q2. 新しく立てたサーバーで curl https://shop.example.com が Connection refused になりました。タイムアウトの場合と比べて、まず何を疑いますか？

    パケットはサーバーまで届いているが、443 番で待ち受けているプロセスがいない可能性が高いです。sudo ss -tlnp で 443 の listen を確認し、systemctl status nginx で Nginx が起動しているか、HTTPS の設定が読み込まれているかを確認します。タイムアウトなら、まずファイアウォールやセキュリティグループを疑います。

    Q3. Shop API を 0.0.0.0:3000 で listen させ、ファイアウォールでも 3000 番を開けていました。何が問題ですか？

    インターネットから Nginx を経由せずに API へ直接アクセスできてしまいます。HTTPS（暗号化）や Nginx 側のアクセス制限・レート制限をすり抜けられるため危険です。API は 127.0.0.1:3000 で listen させ、3000 番は外に開けないようにします。

    Q4. サーバーの IP を変更する予定があります。DNS について事前にしておくとよいことは？

    数日前に A レコードの TTL を 300 秒程度に下げておきます。TTL の間は各地のキャッシュが古い IP を返し続けるため、短くしておくと切り替えが数分で行き渡ります。切り替え後は TTL を元に戻します。

    Q5. EC2 で ip addr を実行したら、グローバル IP が表示されず 10.0.1.23 だけが出ました。設定ミスですか？

    設定ミスではありません。AWS ではインターネットゲートウェイがプライベート IP とパブリック IP を 1 対 1 で NAT 変換しているので、OS からはプライベート IP しか見えないのが正常です。

    Q6. Node.js アプリをコンテナに入れたら、ホストから繋がらなくなりました。listen アドレスの観点で考えられる原因は？

    コンテナ内で 127.0.0.1 で listen していると、コンテナの外（ホスト）からは届きません。コンテナ内では 0.0.0.0 で listen する必要があります。

    Q7. example.com（ゾーンの頂点）を、IP が変わるロードバランサーに向けたいとき、CNAME を使えますか？

    使えません。CNAME はゾーンの頂点には置けず、同じ名前でほかのレコードと共存もできません。Route 53 のエイリアスレコードや Cloudflare の CNAME フラットニングを使います。
