    30 アプリ実行環境

    設定と環境変数・シークレット

    DB の接続先やパスワードのように、環境ごとに変わる値は コードから分けて 渡します。このページでは、The Twelve-Factor App の「設定は環境変数に」という原則とその理由、環境変数をアプリに渡す方法（systemd、.env、コンテナ）、パスワードや API キーなどの シークレット を安全に保管・配布する方法（Secrets Manager / Parameter Store / Vault / sops）、起動時に設定を検証して「設定ミスのまま動き出す」事故を防ぐ方法、ローテーションと「ログにシークレットを出さない」ための実務の注意を解説します。

    もとにしたノート：docs/61_サーバー・インフラ/30_アプリ実行環境/05_設定と環境変数・シークレット

    ひとことで言うと

    アプリのコードは 「レシピ」、設定は 「その日の仕入れ先や店舗の鍵」 です。レシピは全店舗で同じものを使い回しますが、仕入れ先や鍵は店舗ごとに違います。鍵をレシピ本に書き込んで配ってしまったら、レシピ本を見た人は誰でも店に入れてしまいます。だから コードと設定を分け（同じビルド成果物を開発・ステージング・本番で使い回す）、設定のうち シークレット（secret：パスワード、API キー、秘密鍵など、漏れると被害が出る値）はさらに厳重に保管するのが基本方針です。

    この記事は 30-4 プロセス管理とsystemd を読んでいると理解しやすいです。設計の観点からの整理は 41 設定・シークレット・フィーチャーフラグ も参照してください。

    1.The Twelve-Factor App の Config 原則

    The Twelve-Factor App は、Heroku の開発者がまとめた「クラウドで動かしやすいアプリの 12 の原則」です。その 3 番目 Config では次のように述べています。

    • 設定（config）とは デプロイごとに変わりうる値 のこと。DB の接続先、外部サービスの認証情報、ホスト名など
    • 設定はコードから 厳密に分離 する。ルーティングのように環境で変わらないものは設定ではなく、コードに置いてよい
    • 設定は 環境変数 に格納する。言語や OS に依存せず、うっかりリポジトリにコミットされにくいから
    • 判定基準：「今すぐこのリポジトリをオープンソースにしても、認証情報が漏れないか？」

    Shop API の例で、何が設定で何がコードかを整理します。

    項目分類理由
    DATABASE_URL（DB 接続先とパスワード）設定（シークレット）環境ごとに違い、漏れると致命的
    STRIPE_SECRET_KEY設定（シークレット）決済の API キー
    PORT=3000、LOG_LEVEL=info設定環境で変えたいことがある
    PUBLIC_BASE_URL=https://shop.example.com設定ステージングは別ドメイン
    /api/orders のルーティング、税率計算ロジックコードどの環境でも同じ

    1.1 環境ごとの設定

    「config/production.json と config/development.json をリポジトリに置いて NODE_ENV で切り替える」方式もよく見かけますが、次の問題があります。

    • シークレットまでファイルに書くとリポジトリに入ってしまう
    • 環境が増える（ステージング、検証用、顧客別…）たびにファイルが増える
    • 本番の値を変えるのにコードのデプロイが必要になる

    環境で変わらない既定値はコード、環境で変わる値は環境変数、シークレットは専用ストアから環境変数へ と分けると整理しやすくなります。

    2.環境変数の渡し方

    2.1 systemd の EnvironmentFile

    VM 上で systemd から起動する場合（30-4 プロセス管理とsystemd）は、EnvironmentFile= で 1 行 1 変数のファイルを読ませます。/etc/shop-api/env（root 所有、shop グループだけ読める 640）の例です。

    PORT=3000
LOG_LEVEL=info
PUBLIC_BASE_URL=https://shop.example.com
DATABASE_URL=postgres://shop_app:xxxxxxxx@10.0.2.10:5432/shop
STRIPE_SECRET_KEY=sk_live_xxxxxxxx
    [Service]
EnvironmentFile=/etc/shop-api/env
# 先頭に - を付けると「ファイルが無くてもエラーにしない」
# EnvironmentFile=-/etc/shop-api/env.local

    注意点は次のとおりです。

    • これはシェルスクリプトではありません。$(...) や export は使えません。
    • パーミッション（ファイルの読み書き権限）を必ず絞ります。/etc/systemd/system/*.service は誰でも読めるので、unit ファイルの Environment= にシークレットを直接書かない でください。
    • systemctl show shop-api -p Environment や /proc/<PID>/environ（root か同じユーザーなら読める）で値が見えることは理解しておきます。より厳密にしたい場合は systemd の LoadCredential=（ファイルとして渡し、環境変数に残さない仕組み）もあります。

    2.2 .env と dotenv（主に開発環境）

    開発機では、プロジェクト直下の .env ファイルを読み込むのが一般的です。Node.js では長く dotenv パッケージが使われてきましたが、Node.js 20.6 以降は標準で --env-file オプションがあります。

    # Node.js 20.6+ の標準機能
node --env-file=.env dist/server.js

# dotenv パッケージを使う場合（コードの先頭で）
# import "dotenv/config";

    .env は Git に入れない のが鉄則です。代わりに、キーの一覧だけを書いた .env.example をコミットして「何を設定すればよいか」を共有します。

    # .gitignore
.env
.env.*
!.env.example
    # .env.example（値はダミー。これはコミットする）
PORT=3000
DATABASE_URL=postgres://shop_app:password@localhost:5432/shop_dev
STRIPE_SECRET_KEY=sk_test_xxx

    一度コミットしたシークレットは「漏れた」と考える

    後のコミットで削除しても Git の履歴に残ります。公開リポジトリなら数分以内に自動収集ボットに拾われることもあります。まず該当キーを無効化・再発行（ローテーション） し、その後で履歴の書き換え（git filter-repo など）を検討します。順序が逆だと、書き換え作業の間も漏れたキーが有効なままです。GitHub の secret scanning / push protection や gitleaks などで事前に止める仕組みも入れておきましょう。

    2.3 コンテナ

    docker run --env-file ./env.prod -e LOG_LEVEL=info shop-api:1.4.0
    # Kubernetes：Secret を環境変数として注入
env:
  - name: DATABASE_URL
    valueFrom:
      secretKeyRef:
        name: shop-api-secrets
        key: database-url

    Dockerfile の ENV や ARG にシークレットを書かない でください。イメージのレイヤーや docker history から読めてしまいます。Kubernetes の Secret も既定では base64 で符号化されているだけ（暗号化ではない）なので、etcd（Kubernetes の設定データの保存先）の暗号化や外部シークレットストア連携（External Secrets Operator など）と組み合わせます。くわしくはコンテナの本番向けベストプラクティスのノートを参照してください。

    3.シークレットの管理

    /etc/shop-api/env を手でサーバーに置く方法は 1 台なら成り立ちますが、台数が増えたり、担当者が入れ替わったりすると「誰がどの値を持っているか」が分からなくなります。そこで シークレット専用の保管庫 を使います。

    サービス / ツール概要向いている場面
    AWS Systems Manager Parameter Store階層的なキー（/shop/prod/DATABASE_URL）で値を保存。SecureString 型は KMS（AWS の鍵管理サービス）で暗号化。標準パラメータは追加料金なし（2026 年時点）AWS 上の設定値全般。まずはここから
    AWS Secrets Managerシークレット専用。自動ローテーション（RDS のパスワード等）、他アカウントとの共有に強い。1 シークレットごとに月額課金DB パスワードなど定期的に変えたいもの
    HashiCorp Vaultクラウド非依存のシークレット管理。動的シークレット（要求のたびに期限付き DB ユーザーを発行）が特徴マルチクラウド・オンプレ、高度な要件
    sops（＋ age / KMS）YAML / JSON / .env の 値だけを暗号化 して Git に置けるGitOps、IaC と一緒にバージョン管理したい場合
    GCP Secret Manager / Azure Key Vault各クラウドの同等サービス各クラウド上で

    3.1 Shop API で Parameter Store を使う例

    # 運用者が値を登録（一度だけ）
aws ssm put-parameter --name /shop/prod/DATABASE_URL \
  --type SecureString --value 'postgres://shop_app:xxxx@db.internal:5432/shop'

    サーバー側は、EC2 にアタッチした IAM ロール（サーバーに与える AWS の権限セット）で読み取ります。サーバー上に AWS のアクセスキーを置く必要がないのがポイントです（「シークレットを取り出すためのシークレット」問題を IAM ロールで解決）。IAM ポリシーは ssm:GetParametersByPath を arn:aws:ssm:*:*:parameter/shop/prod/* だけに絞り、kms:Decrypt も該当キーに限定します。

    起動前にパラメータを取得してファイル（例：/run/shop-api/env）に書き出すスクリプトを ExecStartPre= で実行する方法や、アプリ自身が AWS SDK で起動時に読む方法があります。後者はファイルに平文が残らない利点があります。

    3.2 sops で暗号化したファイルを Git に置く

    # age で鍵を作り、.env の値だけを暗号化
sops --encrypt --age age1xxxx... env.prod > env.prod.enc
# 復号（デプロイ時に、鍵を持つ CI やサーバーだけが実行）
sops --decrypt env.prod.enc > /etc/shop-api/env

    キー名は平文のまま残るので差分レビューができ、値は暗号化されているのでリポジトリに置けます。復号鍵の管理は KMS などに任せるのが一般的です。

    4.起動時バリデーション

    環境変数は「文字列」で、しかも 設定し忘れても undefined になるだけ です。DATABASE_URL を書き忘れた本番サーバーが起動し、最初の注文が来た瞬間にエラーになる——という事故を防ぐため、起動時にまとめて検証し、不備があれば即座に終了する（fail fast）ようにします。

    // src/config.ts
import { z } from "zod";

const EnvSchema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
  PORT: z.coerce.number().int().min(1).max(65535).default(3000),
  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
  PUBLIC_BASE_URL: z.string().url(),
  DATABASE_URL: z.string().startsWith("postgres://"),
  STRIPE_SECRET_KEY: z.string().min(1),
});

const parsed = EnvSchema.safeParse(process.env);

if (!parsed.success) {
  // 値そのものは出さず、どのキーが不正かだけを出す
  console.error("Invalid environment variables:",
    parsed.error.issues.map((i) => `${i.path.join(".")}: ${i.message}`));
  process.exit(1);
}

export const config = parsed.data; // 型付きで安全に使える
    • アプリ内では process.env.XXX を直接参照せず、この config だけを使うようにすると、必要な設定の一覧がこのファイルに集約されます。
    • systemd 配下で process.exit(1) すると Restart=on-failure で再起動を繰り返し、起動回数制限で failed になります。journalctl -u shop-api に原因が残るので、すぐに気づけます。
    • Python（FastAPI の管理画面）なら pydantic-settings の BaseSettings が同じ役割を担います。

    5.ローテーションとログへの漏えい防止

    5.1 ローテーション

    ローテーション（rotation）とは、シークレットを定期的、または漏えいの疑いがあるときに新しい値に入れ替えることです。漏れていても気づいていないケースに備え、被害を受ける期間を短くします。DB パスワードを止めずに入れ替える基本手順は次のとおりです。

    1. 新しいパスワード（または新しい DB ユーザー）を作る — この時点で新旧どちらでも接続できる
    2. シークレットストアの値を新しいものに更新
    3. アプリを順番に再起動（ローリング）して新しい値を読ませる
    4. すべてのインスタンスが新しい値で動いていることを確認
    5. 古いパスワードを無効化

    AWS Secrets Manager の自動ローテーションは、この手順を Lambda 関数で自動化したものです。「アプリが起動時にしか値を読まない」作りだと、ローテーション後に再起動が必要な点に注意します。

    5.2 ログにシークレットを出さない

    よくある漏えい経路は次のとおりです。

    経路例対策
    起動時の設定ダンプconsole.log(process.env) / console.log(config)出力するならキー名だけ、または値をマスク
    エラーメッセージ接続失敗時に DATABASE_URL 全体がスタックトレースに入るロガーの redact 機能を使う
    リクエストログAuthorization ヘッダーや Cookie をそのまま記録ロガーで該当パスを除外
    URL のクエリ文字列?api_key=... がアクセスログに残るキーはヘッダーで送る
     
    // pino の redact 機能で、該当フィールドを自動マスク
import pino from "pino";
export const logger = pino({
  redact: ["req.headers.authorization", "req.headers.cookie", "*.password", "*.token"],
});

    ログはログ集約基盤に送られ、アプリより多くの人が見られることが多いため、「ログに出た時点で漏えい」と考えるのが安全です。ログ出力の注意点は 71 セキュアな運用とログ出力 でも扱います。

    6.よくある誤解・つまずき

    ✕ 誤解◯ 実際
    .env は .gitignore に入れたから安全追加する前に一度でもコミットしていれば履歴に残っています。git log --all -- .env で確認し、残っていればキーを再発行します。
    環境変数にすれば暗号化される環境変数は平文です。/proc/<PID>/environ や docker inspect で見えます。守っているのは「リポジトリに入らない」ことと、ファイル・ストアのアクセス権です。
    Kubernetes の Secret は暗号化されている既定では base64 符号化だけです。etcd の暗号化や RBAC での読み取り制限が別途必要です。
    本番とステージングで同じ DB パスワードでもよいステージングは権限が緩くなりがちです。環境ごとに別のシークレットにし、ステージングから本番の値を読めないよう IAM で分けます。
    設定が足りなくても動くところまで動けばよい起動時に検証して即終了する方が、障害の発見が早く原因も明確です。

    7.まとめ

    • 設定（デプロイごとに変わる値）はコードから分離し、環境変数で渡す。判定基準は「今すぐ公開しても認証情報が漏れないか」
    • VM では systemd の EnvironmentFile=（権限 640）、開発では .env（Git に入れない、.env.example を共有）、コンテナでは --env-file や Kubernetes Secret
    • 本番のシークレットは Parameter Store / Secrets Manager / Vault / sops で一元管理し、サーバーは IAM ロールなどで取り出す
    • 起動時に zod などで必須の環境変数を検証し、不備があれば即終了（fail fast）
    • シークレットは定期的にローテーションし、ログ・エラーメッセージ・URL に出さない

    8.理解度チェック

    Q1. 新人が誤って本番の STRIPE_SECRET_KEY を含む .env を公開リポジトリに push してしまいました。最初にやるべきことは何ですか？

    Stripe の管理画面でそのキーを無効化し、新しいキーを発行して本番に反映することです。Git の履歴から削除するのはその後です。公開リポジトリでは短時間で収集される可能性があるため、「漏れた前提」で動きます。

    Q2. config/production.json に DB パスワードを書いてリポジトリに置く方式の問題点を 2 つ挙げてください。

    ①リポジトリを読める人全員（や漏えい時の第三者）に本番の認証情報が見える。②パスワードの変更（ローテーション）にコードの変更とデプロイが必要になる。ほかに、環境が増えるたびにファイルが増える点もあります。

    Q3. EC2 上の Shop API が Parameter Store から値を読むとき、AWS のアクセスキーをサーバーに置かずに済むのはなぜですか？

    EC2 にアタッチした IAM ロールの一時的な認証情報を、SDK や CLI がインスタンスメタデータから自動で取得するためです。権限はロールのポリシーで /shop/prod/* の読み取りだけに絞ります。

    Q4. 環境変数にしたシークレットは暗号化されていますか？

    いいえ、平文です。/proc/<PID>/environ や docker inspect で見えます。環境変数で守れるのは「リポジトリに入らない」ことで、あとはファイルやストアのアクセス権で守ります。

    Q5. 起動時に環境変数を検証して、不備があれば即終了させる（fail fast）利点は何ですか？

    設定漏れのまま動き出し、最初の注文が来た瞬間にエラーになるような事故を防げます。起動直後に止まり、journalctl などに「どのキーが不正か」が残るので、障害の発見が早く原因も明確です。

    Q6. DB パスワードを止めずにローテーションするとき、古いパスワードを無効化するのはどの段階ですか？

    新しいパスワードを作ってストアを更新し、アプリを順番に再起動して、すべてのインスタンスが新しい値で動いていると確認した後です。先に無効化すると、まだ古い値を使っているインスタンスが接続できなくなります。
