    50 スケーリング・負荷分散

    ロードバランサーの仕組み

    ロードバランサー は、入口を 1 つにまとめて後ろの複数サーバーにリクエストを振り分ける仕組みです。このページでは、L4 と L7 の違い、振り分けアルゴリズム（ラウンドロビン・最小接続・重み付き・IP ハッシュ・最小応答時間）の特徴と弱点、ヘルスチェック で壊れたサーバーを切り離して戻す流れ、スティッキーセッション・TLS 終端・コネクションドレイニング、Nginx upstream と AWS ALB の設定例、DNS ラウンドロビンとの違いを解説します。

    もとにしたノート：61_サーバー・インフラ/50_スケーリング・負荷分散/02_ロードバランサーの仕組み、61_サーバー・インフラ/50_スケーリング・負荷分散/ロードバランサの裏側 — 振り分けと切り離し｜ねる前エンジニアリング（動画 https://www.youtube.com/watch?v=NG4JOHdCmUY）

    ひとことで言うと

    ロードバランサーは 入口を 1 つにして、渡す先を決める受付係 です。重さがバラバラなら「空いている所へ（最小接続）」、壊れた先は ヘルスチェックが続けて失敗したら外し、続けて成功したら戻す。止めるときは まず新しい依頼を止め、手元を片付けてから 止めます。

    1.ロードバランサーとは

    1.1 よくある場面

    • セール開始の瞬間にアクセスが一気に来て、1 台では受け切れない
    • 台数を増やしたのに、1 台だけがやけに重い（振り分け方の問題）
    • 新しい版を出すたびに数秒だけエラーが出る（「少しだけならいい」と放っておかないのが、品質に責任を持つということです）

    このページの前半は「振り分け方」、後半は「壊れた先・止める先の外し方」の話です。

    1.2 1 台に全部が集まると

    1 台のサーバーが同時にさばける数（例：6 つ）を超えると、溢れた分は待たされるか、間に合わずエラーになります。しかもその 1 台が止まれば全員が使えません。1 台に頼ると 「遅い」と「止まる」 の 2 つが困るので、サーバーを複数台並べます（スケーリングの基本 のスケールアウト）。

    ところが、利用者に 3 つの住所を教えるのは大変です。そこで真ん中に振り分け役を置き、入口を 1 つにします。これがロードバランサーです。

    1.3 銀行の受付係の例え

    ロードバランサー（Load Balancer、LB：負荷分散装置） は、銀行の「番号札の受付係」です。お客さんは入口で受付に並ぶだけで、どの窓口に行くかは受付係が「空いている窓口」を見て案内してくれます。窓口の係員が倒れたら、受付係はそこに案内するのをやめます。受付係は自分では処理せず、窓口へ案内するだけです。

    • 入口（IP アドレス・ドメイン）を 1 つ にまとめ、後ろの複数サーバーに振り分ける
    • 振り分け方（アルゴリズム）を選べる
    • ヘルスチェック で壊れたサーバーを自動で切り離し、直れば戻す
    • 利用者からは後ろに何台いても 1 台に見える

    ロードバランサーは リバースプロキシ（利用者の代わりに後ろのサーバーへ取り次ぐ中継役）の一種と考えると分かりやすいです。リバースプロキシの転送先が複数になったものがロードバランサーです。

    2.L4 と L7 の違い

    「L4」「L7」は OSI 参照モデル（通信の仕組みを 7 つの層に分けた考え方）の層（レイヤー）を指します。どの層の情報を見て振り分けるか の違いです。

    L4 ロードバランサーL7 ロードバランサー
    見る情報IP アドレスとポート（TCP/UDP）HTTP の中身（パス、ホスト名、ヘッダー、Cookie）
    例え封筒の宛名だけ見て仕分ける手紙を開けて内容を読んで仕分ける
    できること高速な転送、TCP 以外（UDP、DB 接続、ゲームなど）も扱える/api/* は API へ、/admin/* は管理画面へ、などの経路ルール。ヘッダー追加、リダイレクト
    TLSそのまま通すことが多い（終端も可能）終端して中身を見るのが普通
    速さ速い、遅延が小さい中身を解析するぶん少し重い
    製品例AWS NLB、HAProxy（mode tcp）、Nginx streamAWS ALB、Nginx（http）、HAProxy（mode http）、Envoy、GCP 外部アプリケーション LB

    Web アプリ（Shop）ではたいてい L7 を使います。L4 は「固定 IP が欲しい」「HTTP 以外のプロトコル」「とにかく低遅延・大量接続」などの場合に選びます。

    3.振り分けアルゴリズム

    アルゴリズム仕組み得意弱点
    ラウンドロビン（Round Robin）順番に 1 台ずつ配るリクエストの重さが揃っているとき。既定値であることが多い重さを見ない。重い処理が 1 台に続くとそこだけ詰まる
    重み付き（Weighted）性能に応じて配る比率を変える（例 3:1）性能の違うサーバーが混在、新バージョンに少しだけ流す重みの管理が必要
    最小接続（Least Connections）処理中の接続・リクエストが最も少ない所へ処理時間がバラバラな API「すぐエラーを返す壊れたサーバー」は処理中が少なく見え、そこに集まる
    IP ハッシュ（IP Hash）送信元 IP から計算して毎回同じサーバーへ簡易的なスティッキー会社や携帯キャリアの NAT で同じ IP の利用者が大量だと偏る。台数が変わると振り先がずれる
    最小応答時間（Least Time／Least Response Time）応答が速いサーバーを優先性能差や一時的な遅延に追従実装が製品依存。計測のための仕組みが必要

    NAT は、多くの端末が 1 つのグローバル IP アドレスを共有して外へ出る仕組みです。そのため、会社や携帯回線の利用者は外から見ると同じ IP に見えることがあります。

    3.1 順番に配る（ラウンドロビン）

    1 つ目はサーバー 1、2 つ目は 2、3 つ目は 3、4 つ目でまた 1 に戻る、という配り方です。数は公平で、依頼の重さがどれも同じならうまくいきます。しかし一覧を出すだけの軽い依頼もあれば、大きな集計をする重い依頼もあります。重い依頼がたまたまサーバー 1 に続けて当たると、数は公平でもサーバー 1 だけ処理が積み上がります。「増やしたのに 1 台だけ重い」の正体の 1 つがこれです。順番は数を揃えるだけで、重さは見ていません。

    性能の違うサーバーが混ざるときは、強いサーバーに多めに配る 重み を付けます（重み付き）。

    3.2 空いている所へ（最小接続）

    振り分け役は各サーバーの処理中の数を覚えておき、渡したら +1、返事が来たら −1 して、一番少ない所へ次の依頼を渡します。重い依頼で詰まった所は処理中の数が多いのでしばらく選ばれず、重さの違いに後から追いつく 配り方です。

    多くの場面で良い選択ですが、数える手間がかかります。さらに、処理中の数が少ないのが「壊れてすぐエラーを返すから」という場合もあり、早く失敗するサーバーに依頼が集まる 危険があります。だからこそ次のヘルスチェックがセットで必要です。

    3.3 同じ人は同じ所へ

    ログイン中の情報などをサーバーの記憶（メモリ）に置いている場合、A さんの情報はサーバー 1 にしかないので、A さんの依頼はいつもサーバー 1 へ渡す、という決め方です（IP ハッシュや、5 章のスティッキーセッション）。弱点は 2 つあります。1 つは 偏りやすい こと。もう 1 つは、そのサーバーが止まると別のサーバーは A さんを知らないので、ログインし直しになったりカートの中身が消えたり することです。今は記憶を 共有の置き場 に出し、どのサーバーでも同じ記憶を読めるようにする作りが多いです（ステートレス化）。

    3.4 AWS ALB で選べるもの

    AWS ALB では「ラウンドロビン（既定）」「最小未処理リクエスト（Least outstanding requests）」「重み付きランダム（Weighted random）」から選べます（2026 年時点）。

    4.ヘルスチェックと切り離し

    何もしなければ、LB は落ちたサーバーにも律儀に振り分け続けます。3 台中 1 台が落ちれば、3 回に 1 回エラー です。しかも利用者にはどのサーバーかは見えず、「たまにエラーが出る」としか分かりません。だから振り分け役の側で、倒れた先に気づく必要があります。

    ヘルスチェック（Health Check：健康診断） には 2 種類あります。

    • アクティブ：LB が数秒ごとに /healthz などへリクエストを送り、決まった時間内に 200 が返るか確かめる（ALB、HAProxy、NGINX Plus）
    • パッシブ：実際のリクエストの失敗を数えて判断する（オープンソース版 Nginx の max_fails）

    4.1 外す・戻すの流れ

    1 回失敗しただけでは外しません（たまたま遅れただけかもしれないからです）。決めた回数 続けて失敗 したら切り離し、以降は残りのサーバーにだけ配ります。切り離した後も様子見の依頼は送り続けるので、直ったことにも気づけます。決めた回数続けて成功したら戻します。外すのも戻すのも振り分け役が自動で 行います。

    4.2 設計のポイント

    1. 気づくまでの時間 ≒ 間隔 × 失敗回数。気づくまでの間はエラーが出ています。間隔 5 秒 × 3 回ならおよそ 15 秒、ALB の既定（間隔 30 秒・Unhealthy 閾値 2 回）だと最大 1 分ほど気づきません。かといって間隔を短く・回数を少なくしすぎると、一瞬遅れただけで外してしまい、外しすぎると残りの台に依頼が集まってそこも倒れます。早すぎても遅すぎても困ります。
    2. 浅いチェックと深いチェック。/healthz が「プロセスが動いているか」だけなら軽いが DB 障害を見落とします。DB まで確認すると、DB 全体が落ちたときに全台が不合格になり全部外れる という事故が起きます。
    3. 全台不合格のときの挙動を知っておく。ALB は全ターゲットが Unhealthy になると、あえて全台に流す フェイルオープン の動作をします。

    4.3 浅い確認と深い確認

    サーバー側には様子見のための窓口を用意します。最短の形は、呼ばれたら 200（成功）で OK を返すだけです。

    浅い確認深い確認
    見るもの返事ができるか（プログラムが動いているか）DB なども使えるか（DB に一言聞き、答えがあれば 200、なければ 503＝使えない）
    重さ軽い確かめる分重い
    弱点つながる先の不調を見落とす（DB につながらなくても OK を返す）共通の先が止まると全部外れる（全サーバーが揃って「使えない」と答え、誰も使えなくなる）

    どちらが正解ということはなく、現場では使い分けたり組み合わせたりします。外したら何が起きるか を先に考えて、何を確かめるかを決めます。

    // Shop API のヘルスチェック窓口（浅い／深いを分ける）
app.get("/healthz", (_req, res) => res.status(200).send("ok")); // LB 用：生きているか

app.get("/readyz", async (_req, res) => {                        // 監視用：依存先も見る
  try {
    await pool.query("SELECT 1");
    res.status(200).send("ready");
  } catch {
    res.status(503).send("db unavailable");
  }
});

    Kubernetes の liveness／readiness の考え方やデプロイ時の自動ロールバックは、65_リリース・デプロイの「03_ヘルスチェックと自動ロールバック」のノートを参照してください。

    5.スティッキーセッション・TLS 終端・コネクションドレイニング

    5.1 スティッキーセッション（Sticky Session／Session Affinity）

    同じ利用者を同じサーバーへ送り続ける機能です。ALB では LB が AWSALB という Cookie を発行して実現します。サーバーのメモリにセッションがあるアプリを、とりあえず複数台で動かすための 応急処置 です。偏りやすく、そのサーバーが落ちるとセッションは消えるので、根本対策はステートレス化（スケーリングの基本）です。

    5.2 TLS 終端（TLS Termination）

    HTTPS の暗号を LB で解いて、後ろには HTTP（または再暗号化した HTTPS）で渡すことです。

    • 証明書を LB 1 か所で管理できる（ALB なら ACM の証明書を無料で自動更新）
    • 暗号処理の CPU 負荷をアプリサーバーから外せる
    • L7 の振り分け（パス・Cookie を見る）には TLS 終端が必須
    • アプリには X-Forwarded-Proto: https や X-Forwarded-For（元の利用者 IP）が渡るので、アプリ側で信頼するプロキシを設定する（Express なら app.set("trust proxy", 1)）

    証明書そのものの話は HTTPSとTLS証明書 を参照してください。

    5.3 コネクションドレイニング（Connection Draining）

    新しい版を出すときは 1 台ずつ止めて入れ替えますが、いきなり止めると処理中だった依頼が途中で切れます。これが 「出すたびに数秒だけ出るエラー」の正体 です。正しい順番は次のとおりです。

    1. まず、そのサーバーに 新しい依頼を送るのをやめる
    2. 手元の処理中の分だけ片付ける（処理中の数が 3、2、1 と減っていく）
    3. 処理中が 0 になってから止めて入れ替える
    4. これを 1 台ずつ繰り返せば、止めずに入れ替えられる

    このように「新しいリクエストを送るのをやめる → 処理中のものが終わるのを待つ → 止める」の順にする機能がコネクションドレイニングです。外すのは壊れたときだけではありません。

    ALB では「登録解除の遅延（Deregistration delay）」と呼び、既定 300 秒です。API が数秒で応答するなら 30〜60 秒程度に短くするとデプロイやスケールインが速くなります。アプリ側も SIGTERM（プロセスに「終了して」と伝える合図）を受けたら新規受付を止めて処理中を片付けるようにします（65_リリース・デプロイの「08_ゼロダウンタイムデプロイの条件」「03_ローリングアップデート」のノート）。

    6.設定例：Nginx upstream と AWS ALB

    6.1 Nginx upstream（Shop：API 2 台 + 予備）

    # /etc/nginx/conf.d/shop-api.conf
upstream shop_api {
    least_conn;                      # 最小接続（既定はラウンドロビン）

    # 10 秒（fail_timeout）の間に 3 回（max_fails）失敗したら、
    # 10 秒間そのサーバーを使わない（パッシブヘルスチェック）
    server 10.0.1.11:3000 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:3000 max_fails=3 fail_timeout=10s;
    server 10.0.1.13:3000 backup;    # 上 2 台が使えないときだけ使う

    keepalive 32;                    # 後ろとの接続を再利用
}

server {
    listen 443 ssl;
    http2 on;
    server_name api.shop.example.com;
    # ssl_certificate などは「HTTPSとTLS証明書」の回を参照

    location / {
        proxy_pass http://shop_api;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 失敗時に次のサーバーへ再送する条件（POST など非冪等は既定で再送しない）
        proxy_next_upstream error timeout http_502 http_503;
        proxy_connect_timeout 3s;
    }
}
    • max_fails の既定は 1、fail_timeout の既定は 10 秒です。fail_timeout は「失敗を数える時間幅」と「使わない期間」の 2 つの意味を持ちます。
    • オープンソース版 Nginx には アクティブヘルスチェック（health_check）がありません（NGINX Plus の機能）。実リクエストが失敗して初めて気づくので、その 1 回は利用者にエラーが見えることがあります（proxy_next_upstream で別サーバーへ再送して隠せる場合もあります）。
    • least_time（最小応答時間）や drain パラメータは長く商用版のみでしたが、最近のバージョンでオープンソース版にも入りつつあります。使う前に手元のバージョンのドキュメントで確認してください（2026 年時点）。
    • 設定変更後は sudo nginx -t && sudo systemctl reload nginx。

    非冪等（ひべきとう）とは、同じ依頼を 2 回送ると結果が変わる処理のことです（例：注文の POST を再送すると注文が 2 件できる）。Nginx の基本は Nginx入門 を参照してください。

    6.2 AWS ALB の構成要素

    ALB（shop-alb）  ← DNS 名を Route 53 で api.shop.example.com に紐付け
 ├─ リスナー :80   → ルール：すべて HTTPS へリダイレクト
 └─ リスナー :443（ACM 証明書・TLS 終端）
     ├─ ルール 1：Host = api.shop.example.com      → ターゲットグループ shop-api-tg
     ├─ ルール 2：Path = /admin/*                  → ターゲットグループ shop-admin-tg
     └─ デフォルト：固定レスポンス 404
ターゲットグループ shop-api-tg（HTTP:3000）
 ├─ ヘルスチェック：GET /healthz、間隔・閾値
 ├─ 属性：アルゴリズム、登録解除の遅延、スティッキー
 └─ ターゲット：EC2 ×N（Auto Scaling Group が自動登録）
    要素役割
    リスナー（Listener）どのポート・プロトコルで待ち受けるか。443 では証明書を持つ
    ルール（Rule）条件（ホスト名・パス・ヘッダー等）と行き先（転送・リダイレクト・固定応答）。優先度順に評価
    ターゲットグループ（Target Group）振り分け先の集まり。ヘルスチェックとアルゴリズムはここで設定

    ターゲットグループのヘルスチェック既定値（instance／ip ターゲット、2026 年時点）は、間隔 30 秒、タイムアウト 5 秒、Healthy 閾値 5 回、Unhealthy 閾値 2 回、成功コード 200 です。Terraform で書くと次のようになります（Terraform の基本は Terraform入門）。

    resource "aws_lb_target_group" "shop_api" {
  name     = "shop-api-tg"
  port     = 3000
  protocol = "HTTP"
  vpc_id   = aws_vpc.main.id

  load_balancing_algorithm_type = "least_outstanding_requests"
  deregistration_delay          = 60   # 既定 300 秒を短縮

  health_check {
    path                = "/healthz"
    interval            = 10
    timeout             = 5
    healthy_threshold   = 3
    unhealthy_threshold = 2
    matcher             = "200"
  }
}

resource "aws_lb_listener_rule" "api" {
  listener_arn = aws_lb_listener.https.arn
  priority     = 10
  condition {
    host_header { values = ["api.shop.example.com"] }
  }
  action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.shop_api.arn
  }
}

    6.3 その他の製品

    HAProxy

    オープンソースの高性能 LB。L4/L7 両方、アクティブヘルスチェック標準搭載。オンプレや自前構築の定番。

    AWS NLB

    L4。AZ ごとに固定 IP（Elastic IP）を持てる、超大量接続向け。

    GCP Cloud Load Balancing

    グローバルな単一 Anycast IP で複数リージョンに振り分けられる外部アプリケーション LB などがある。

    Envoy

    サービスメッシュ（Istio など）やモダンなプロキシの中核。動的設定、リトライ、サーキットブレーカーが得意。Kubernetes の Ingress／Gateway の実体として使われることも多い（53_コンテナの「10-Kubernetes」のノート）。

    製品ごとの設定画面は覚えなくてかまいません。名前や画面は製品で違っても、振り分け方と外し方の考え方は同じです。

    7.DNS ラウンドロビンとの違い

    DNS に同じ名前で複数の A レコードを登録し、問い合わせごとに順番を変えて返す方法を DNS ラウンドロビン と呼びます（DNS の基本は ネットワークの基本）。

    api.shop.example.com.  60  IN  A  203.0.113.11
api.shop.example.com.  60  IN  A  203.0.113.12
    DNS ラウンドロビンロードバランサー
    費用・手軽さほぼ無料、すぐできるLB の費用がかかる
    壊れたサーバー基本は気づかない。TTL の間、キャッシュした利用者は落ちたサーバーに行き続けるヘルスチェックで数十秒以内に外す
    振り分けの細かさクライアントやリゾルバのキャッシュ次第で偏るリクエスト単位で制御
    サーバー入れ替えDNS 変更が全世界に行き渡るまで時間がかかるターゲット登録・解除で即時

    TTL は、DNS の答えをキャッシュしてよい秒数です（上の例では 60 秒）。実務では「DNS で複数リージョンや複数 LB に大まかに分け、その先は LB で細かく振り分ける」という 組み合わせ が一般的です。Route 53 のヘルスチェック付きフェイルオーバールーティングは 高可用性と冗長化 で扱います。

    8.AI に設定を書かせたときに見るところ

    振り分けの設定も、今は AI に書かせることが多くなりました。AI は動く設定は書けますが、壊れたときの動きはこちらが聞かないと考えてくれない ことが多いです。「1 台倒れたらどうなる？」と聞くのが大事です。見るところは次の 4 つです。

    1. 様子見の窓口が何を確かめているか（OK を返すだけか、DB まで見るか）
    2. 続けて何回で外すか、間隔は何秒か
    3. 止めるときに手元の依頼を待っているか（待つ時間がゼロだと、出すたびにエラーが出る）
    4. ログインなどの記憶をサーバーの中に置いていないか（止まったときに消える）

    9.よくある誤解・つまずき

    誤解実際
    LB を置けば壊れたサーバーは自動で外れるヘルスチェックの設定と、アプリ側の /healthz 窓口が正しくないと外れません。OSS 版 Nginx はパッシブのみです。
    ヘルスチェックは深いほど安全DB まで見ると、DB 障害時に全台が外れて全面停止します。外したら何が起きるかを考えて決めます。
    スティッキーセッションでセッション問題は解決そのサーバーが落ちればセッションは消えます。偏りも出ます。根本はステートレス化です。
    LB 自体は壊れない自前の Nginx/HAProxy 1 台の LB は新たな SPOF です。ALB などのマネージド LB は複数 AZ に分散されていますが、サブネットを 2 つ以上の AZ に置く必要があります。
    デプロイ時の数秒のエラーは仕方ないコネクションドレイニングとアプリの graceful shutdown（処理中を片付けてから終わる、行儀の良い終了）で防げます。

    10.まとめ

    • LB は入口を 1 つにまとめ、後ろの複数台に振り分けるリバースプロキシ。L4 は IP/ポート、L7 は HTTP の中身を見る
    • アルゴリズムは重さが揃えばラウンドロビン、バラバラなら最小接続。ただし壊れた台に集まらないようヘルスチェックとセット
    • ヘルスチェックは続けて失敗したら外し、続けて成功したら戻す。「間隔 × 回数」で気づく速さが決まる。浅い／深いの使い分けが大事
    • TLS 終端は LB で行い、X-Forwarded-* で元の情報をアプリへ渡す
    • 止めるときはコネクションドレイニングで、まず新しい依頼を止めて処理中のリクエストを待つ
    • DNS ラウンドロビンは手軽だが壊れたサーバーを外せない。LB と組み合わせて使う
    • 製品ごとの設定画面は知らなくてよい。名前や画面は違っても考え方は同じ

    11.理解度チェック

    Q1. ALB のヘルスチェックを「間隔 30 秒・Unhealthy 閾値 2」のまま使っています。API が 1 台落ちてから切り離されるまで、最大でどれくらいかかりますか。また短くしすぎると何が起きますか。

    およそ 30 秒 × 2 回 = 最大 1 分ほどです（タイムアウト時間も加わります）。短くしすぎると、GC（ガベージコレクション：使わなくなったメモリの片付け）や一時的な高負荷で少し遅れただけのサーバーまで外してしまい、残りのサーバーに負荷が集中して連鎖的に落ちる危険があります。

    Q2. オープンソース版 Nginx の server 10.0.1.11:3000 max_fails=3 fail_timeout=10s; は何を意味しますか。

    10 秒の間にこのサーバーへの通信が 3 回失敗したら、その後 10 秒間はこのサーバーを使わない、という意味です。実リクエストの失敗で判断するパッシブヘルスチェックです。

    Q3. 最小接続アルゴリズムで「1 台だけエラー率が高いのに、そこにリクエストが集まる」現象が起きました。なぜでしょうか。

    壊れたサーバーはリクエストを受けるとすぐエラーを返すため、処理中の接続数が常に少なく見えます。最小接続は「処理中が少ない所」を選ぶので、そこに集まります。ヘルスチェックで切り離す、あるいはエラー率を見て外す仕組み（ALB の自動ターゲット重みなど）と組み合わせます。

    Q4. ラウンドロビンで 3 台に均等に配っているのに、1 台だけやけに重くなりました。考えられる原因と対策は？

    ラウンドロビンは数を揃えるだけで重さを見ないため、重い依頼（大きな集計など）がたまたま 1 台に続けて当たると、そこだけ処理が積み上がります。重さがバラバラなら最小接続（空いている所へ）に変えると、詰まった所を自然に避けられます。性能の違うサーバーが混ざっている場合は重み付けも検討します。

    Q5. ヘルスチェックの窓口で DB まで確認する「深い確認」にした場合、どんな事故が起きえますか。

    DB が全体で止まると、全サーバーが揃って 503（使えない）を返し、振り分け役が全台を切り離してしまいます。浅い確認は軽いが DB の不調を見落とし、深い確認は気づけるが共通の先が止まると全部外れる、というトレードオフです。外したら何が起きるかを先に考えて決めます（ALB は全台 Unhealthy 時にフェイルオープンで全台に流します）。

    Q6. 新しい版をデプロイするたびに数秒だけエラーが出ます。原因と正しい手順は？

    サーバーをいきなり止めて、処理中の依頼を途中で切っているのが原因です。まず新しい依頼を送るのをやめ、手元の処理中の分を片付け、0 になってから止めて入れ替える（コネクションドレイニング）を 1 台ずつ繰り返します。アプリ側も SIGTERM で新規受付を止めて処理中を片付けるようにします。

    Q7. DNS ラウンドロビンだけで 2 台に振り分けているとき、1 台が落ちたらどうなりますか。

    DNS は基本的にサーバーの故障に気づかないので、TTL の間（キャッシュした利用者はそれ以上）落ちたサーバーに行き続けます。LB ならヘルスチェックで数十秒以内に外せます。実務では DNS で大まかに分け、その先を LB で細かく振り分ける組み合わせが一般的です。
