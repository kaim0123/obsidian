    高可用性と冗長化

    冗長化 は予備を用意して 1 つ壊れても全体が止まらないようにすること、高可用性 はその結果としてサービスが使える時間の割合が高い状態です。このページでは、可用性 99.9%／99.99% が「年間どれだけ止まってよいか」を意味するのか、単一障害点（SPOF） の洗い出し方、アクティブ-アクティブ／アクティブ-スタンバイ／N+1 の冗長化パターン、マルチ AZ・マルチリージョンと DB のフェイルオーバー、RTO／RPO と「バックアップは冗長化ではない」理由、Shop の最終構成を解説します。発展として、デフォルトゲートウェイの冗長化（FHRP：HSRP／VRRP／GLBP）も扱います。

    もとにしたノート：61_サーバー・インフラ/50_スケーリング・負荷分散/05_高可用性と冗長化

    ひとことで言うと

    可用性は 年間何分まで止まってよいか に直して考え、まず SPOF を見つけて潰します。予備への切り替え（フェイルオーバー）にも時間はかかり、ゼロにはなりません。冗長化は「壊れても動き続ける」、バックアップは「壊れた後に戻す」ためのもので、別物なので両方必要 です。

    1.冗長化と高可用性：飛行機の例え

    飛行機にはエンジンが 2 つ以上あり、1 つ止まっても飛び続けられます。パイロットも 2 人乗っています。冗長化（Redundancy） とは、このように 予備を用意して、1 つ壊れても全体が止まらないようにすること です。そして 高可用性（High Availability、HA） は、その結果として「サービスが使える時間の割合が高い」状態のことです。

    • 可用性は %（稼働率） で表し、「年間何分まで止まってよいか」に直して考える
    • まず 単一障害点（SPOF：Single Point of Failure） を見つけて潰す
    • 予備への 切り替え（フェイルオーバー） には時間がかかる。ゼロにはならない
    • 冗長化は「壊れても動き続ける」、バックアップは「壊れた後に戻す」。別物 で両方必要

    可用性は、性能やセキュリティと並ぶ 非機能要件（機能そのもの以外の品質の要求）の代表です（非機能要件を支えるサーバー、41 品質特性と非機能要件）。

    可用性年間停止時間月間停止時間（30 日）イメージ

    覚えておきたいポイントは 3 つです。

    1. 9 を 1 つ増やすごとに、許される停止時間は 1/10、費用と手間は数倍 になる
    2. 直列につながる部品の可用性は掛け算 で下がる。99.9% の部品が 3 つ直列なら 0.999³ ≈ 99.7%
    3. 並列（冗長化）にすると上がる。99% の部品 2 台が独立に壊れるなら、両方同時に壊れる確率は 1% × 1% = 0.01% → 99.99%（ただし「独立に壊れる」が前提。同じ AZ・同じバグなら同時に壊れる）

    計画停止も停止

    利用者から見れば、メンテナンスでもデプロイでも止まっていれば同じです。99.99% を目指すなら、OS パッチ・DB のバージョンアップ・デプロイも無停止で行える必要があります（65_リリース・デプロイの「08_ゼロダウンタイムデプロイの条件」のノート）。目標値の決め方（SLO・エラーバジェット）は 69_SRE・インシデント対応のノート（MOC）を参照してください。

    5.マルチ AZ・マルチリージョンと DB の冗長化

    5.1 マルチ AZ とマルチリージョン

    • AZ（Availability Zone）：同じリージョン内の、電源・ネットワーク・建物が独立したデータセンター群。AZ 間は低遅延の専用回線（仮想化とクラウド）
    • マルチ AZ：ALB・ASG・RDS を 2〜3 AZ に分散。AZ 間の遅延は小さいので、DB の 同期レプリケーション（書き込みが複製先にも届いてから完了とする複製）が使える。多くのサービスはまずここまでで十分
    • マルチリージョン：東京と大阪など、地理的に離れたリージョンで動かす。大地震やリージョン全体の障害に耐えるが、距離があるので DB は 非同期レプリケーション（複製を後から追いかけて送る）になり、切り替え時に直近のデータが失われ得る。費用・複雑さが大幅に増える
    マルチ AZマルチリージョン
    守れるもの1 データセンターの障害リージョン全体の障害・広域災害
    DB 複製同期（データ損失ほぼなし）非同期（数秒分の損失があり得る）
    切り替え自動（数十秒〜数分）Route 53 フェイルオーバーなど。手順と訓練が必要
    コスト・複雑さ中大

    5.2 DB の冗長化（RDS Multi-AZ）

    • Multi-AZ DB インスタンス：別 AZ に同期スタンバイを 1 台持つ。スタンバイは読み取りには使えない（読み取り分散は スケーリングの基本 のリードレプリカで）。フェイルオーバーは 通常 60〜120 秒（AWS の記載、2026 年時点）
    • Multi-AZ DB クラスター：読み取り可能なスタンバイを 2 台持つ構成。フェイルオーバーがより短い
    • 切り替えは DNS の向き先変更 で行われるので、アプリは 既存の接続が切れたら再接続する 必要があります。接続プールの再接続設定、DNS を長時間キャッシュしない設定（JVM は TTL 60 秒以下が推奨）を確認します
    • 同期レプリケーションのため、Single-AZ より書き込みレイテンシがやや増えます

    自前の PostgreSQL で冗長化する場合はストリーミングレプリケーションと Patroni などの自動フェイルオーバーツールが必要で、難易度が高いです（データベースサーバーの運用、62_データアーキテクチャの「05_WALとクラッシュリカバリ」のノート）。

    5.3 フェイルオーバーと切り替え時間

    「冗長化しているから止まらない」は誤りで、正確には 「切り替え時間だけ止まる・遅くなる」 です。

    部品検知 + 切り替えの目安利用者への影響
    API サーバー 1 台（ALB 配下）ヘルスチェック間隔 × 閾値（数十秒）その間、一部のリクエストがエラー
    RDS Multi-AZ60〜120 秒書き込み・読み込みとも失敗。アプリは再接続
    Redis（ElastiCache レプリカ付き）数十秒程度セッション読み書き失敗。キャッシュなら DB にフォールバック
    リージョン（Route 53 フェイルオーバー）ヘルスチェック + DNS TTL（数分）＋手順次第数分〜数十分

    切り替え中に利用者に起きることを想定し、リトライ（冪等な処理だけ）、タイムアウト、エラー画面の文言 まで設計しておきます。冪等（べきとう）とは、同じ処理を何度やっても結果が同じになる性質です。ヘルスチェックの仕組みは ロードバランサーの仕組み を参照してください。

    6.RTO／RPO と「バックアップは冗長化ではない」

    • RTO（Recovery Time Objective：目標復旧時間）：障害発生から何分以内に復旧させるか
    • RPO（Recovery Point Objective：目標復旧時点）：最大で何分前までのデータなら失ってよいか
    手段主に縮めるもの例
    冗長化（Multi-AZ、ASG）RTO（自動で数分以内に戻る）RDS Multi-AZ で RTO 2 分・RPO ほぼ 0
    バックアップ（スナップショット、PITR）RPO（どの時点に戻せるか）RDS の自動バックアップで 5 分前の時点に復元
    マルチリージョン広域災害時の RTO／RPO非同期レプリカで RPO 数秒、RTO 数十分

    PITR（Point-In-Time Recovery） は、バックアップと変更履歴を使って、指定した時点の状態に戻す機能です。

    バックアップは冗長化ではない、冗長化はバックアップではない

    • バックアップからの復元は 数十分〜数時間 かかります。止まらないための仕組みではありません。
    • 逆に、冗長化は 間違った操作もそのまま複製 します。DELETE FROM orders; を誤って実行すれば、スタンバイからも一瞬で消えます。ランサムウェアや誤削除から守るのはバックアップ（できれば別アカウント・別リージョン、削除できない設定）です。
    • そして 復元を試したことのないバックアップは、無いのと同じ です。定期的に復元訓練をします。

    RTO／RPO の決め方と復旧訓練の進め方は 69_SRE・インシデント対応の「04_DR訓練とRTO・RPO」、手順書の作り方は「02_ランブックの書き方」のノートを参照してください。ランサムウェア対策は 71 脆弱性管理とランサムウェア対策 でも扱っています。

    8.よくある誤解・つまずき

    誤解実際
    冗長化すれば止まらないフェイルオーバーの切り替え時間（RDS なら 1〜2 分）は止まります。アプリ側の再接続とリトライの設計が必要です。
    バックアップを取っているから冗長化は不要（またはその逆）冗長化は止まらないため（RTO）、バックアップは戻すため（RPO・誤操作対策）。両方必要です。
    2 台にすれば可用性は 2 倍同じ AZ・同じ電源・同じバグなら同時に落ちます。「独立して壊れる」ように分けることが重要です。
    RDS Multi-AZ のスタンバイで読み取りを分散できるMulti-AZ DB インスタンスのスタンバイは読めません。読み取り分散はリードレプリカか Multi-AZ DB クラスターです。
    99.99% を目標にすれば安心年 52 分しか止められず、デプロイやパッチも無停止が前提になります。費用と手間に見合う目標を選びます。

    9.発展：デフォルトゲートウェイの冗長化（FHRP：HSRP／VRRP／GLBP）

    ここまではサーバー・DB・AZ の冗長化を見てきましたが、ネットワークの入口である デフォルトゲートウェイ（ルーター） も SPOF になり得ます。この節では、複数のルーターで仮想 IP アドレスを共有してゲートウェイを冗長化する FHRP（HSRP／VRRP／GLBP）を扱います。ネットワークの基本は ネットワークの基本、ルーティングの基本は 11_コンピューターサイエンスの「28ルーティングの基本とスタティックルート」、デフォルトゲートウェイそのものは「05IPアドレスとサブネットとゲートウェイ」のノートを参照してください。

    9.1 FHRP の目的

    PC に設定できるデフォルトゲートウェイ（サブネットの外へ出るときの出口ルーター）は通常 1 つだけ です。そのため、デフォルトゲートウェイのルーターが故障すると、PC はサブネットの外と通信できなくなります。

    FHRP（First Hop Redundancy Protocol、ファーストホップ冗長化プロトコル） は、デフォルトゲートウェイを冗長化 するための仕組みです。複数のルーターで 1 つの仮想ルーター を作り、仮想 IP アドレス（と仮想 MAC アドレス）を共有します。担当ルーターが故障すると、別のルーターが自動で引き継ぎます。

    目的が似ていて混同しやすい技術との違いを整理します。

    目的技術
    デフォルトゲートウェイの冗長化FHRP（HSRP／VRRP／GLBP）
    L2 ネットワークのループ防止STP
    端末への IP アドレス自動割り当てDHCP（DHCPとNTP）
    宛先までの最短経路の計算OSPF などのルーティングプロトコル

    9.2 HSRP の動作

    HSRP（Hot Standby Router Protocol） は Cisco 独自 の FHRP です。

    • グループ内で アクティブルーター が仮想 IP アドレスと仮想 MAC アドレスで応答し、実際の転送 を行う
    • スタンバイルーター は普段は転送を担当しない。アクティブの故障時に引き継ぐ予備
    • アクティブルーターが故障すると、スタンバイルーターが 仮想 IP／仮想 MAC を引き継ぐ
    • PC から見ると、ゲートウェイの IP アドレスも MAC アドレスも変わらないので、設定を変えずに通信を続けられる（ARP キャッシュの更新も不要）

    ARP は、IP アドレスから MAC アドレス（機器固有の番号）を調べる仕組みです。PC のデフォルトゲートウェイには HSRP の仮想 IP アドレスを設定 します。ほかの値を設定してはいけない理由は次のとおりです。

    設定しがちな値なぜダメか
    アクティブルーターの実際の IP アドレスアクティブが故障するとそのアドレスに届かなくなり、冗長化の意味がない
    スタンバイルーターの実際の IP アドレススタンバイは普段は転送を担当しない
    HSRP の仮想 MAC アドレスデフォルトゲートウェイには IP アドレスを設定する。仮想 MAC は、PC が ARP で仮想 IP を問い合わせたときに返される

    HSRP の仮想 MAC アドレス：

    • HSRPv1：0000.0c07.acXX（XX はグループ番号の 16 進数。グループ 1 なら 0000.0c07.ac01）
    • HSRPv2：0000.0c9f.fXXX

    2. 同じなので IP アドレスを比較 → 192.168.1.2 > 192.168.1.1 → R2 がアクティブ、次点の R1 がスタンバイ
    3. ただし、すでに動作しているグループに後から加わった場合は、プリエンプトの有無で結果が変わる（次節）

    9.5 プリエンプト

    プリエンプト（preempt） は、優先度の高いルーターがアクティブの役割を奪い返す機能です。HSRP のプリエンプトはデフォルトで無効 です。そのため、一度アクティブが入れ替わると、プライオリティの高いルーターが故障から復旧して戻ってきても、アクティブの役割は交代しません。

    意図したルーターを常にアクティブにしたい場合は、プライオリティを高くしたうえで standby <グループ> preempt も設定 します。

     時刻   R1（Pri 110, preempt なし）     R2（Pri 100）
 ──────────────────────────────────────────────────────
  t0    Active                          Standby
  t1    故障                            Active に昇格
  t2    復旧 → Standby のまま           Active のまま   ← プリエンプトがないので戻らない
 ──────────────────────────────────────────────────────
        R1 に standby 1 preempt を設定していれば、t2 で R1 が Active を取り戻す

    「復旧したルーターをアクティブに戻したい」ときに、次のコマンドでは目的を果たせません。

    コマンドなぜダメか

    standby 1 ip 192.168.1.254仮想 IP アドレスを設定するコマンド

    GLBP（Gateway Load Balancing Protocol） は、1 つの仮想 IP アドレスに対して、ルーターごとに異なる仮想 MAC アドレス を ARP 応答で答えて、PC ごとに通信を振り分けます。

    • AVG（Active Virtual Gateway）：ARP に応答し、どの仮想 MAC を返すかを割り振る役（1 台）
    • AVF（Active Virtual Forwarder）：実際に転送する役（最大 4 台）
     PC1 ─ARP「192.168.1.254 のMACは？」→ AVG ─応答→ 「0007.b400.0101（R1の仮想MAC）」 → PC1 は R1 経由
 PC2 ─ARP「192.168.1.254 のMACは？」→ AVG ─応答→ 「0007.b400.0102（R2の仮想MAC）」 → PC2 は R2 経由

    HSRP や VRRP でも、VLAN ごとにアクティブ（マスター）のルーターを分ける ことで、ネットワーク全体として負荷を分散する設計はできます（例：VLAN10 は R1 がアクティブ、VLAN20 は R2 がアクティブ）。ただし 1 つのグループ内で同時に転送するのは 1 台だけです。

    OSPF はルーティングプロトコルであり、デフォルトゲートウェイの冗長化（FHRP）ではありません（11_コンピューターサイエンスの「29OSPF（リンクステート型ルーティング）」のノート）。

    9.7 ひっかけポイント・よくある誤解

    • FHRP の目的はデフォルトゲートウェイの冗長化。STP（ループ防止）、DHCP（アドレス割当）、OSPF（経路計算）と混同しない
    • PC のゲートウェイは 仮想 IP。実 IP でも仮想 MAC でもない
    • HSRP のアクティブは プライオリティが大きい方（同じなら IP アドレスが大きい方）。ルーター ID や MAC は使わない
    • HSRP のプリエンプトは デフォルト無効。復旧後に戻すには standby <グループ> preempt。VRRP はデフォルト有効
    • グループ内で負荷分散できるのは GLBP だけ
    • HSRP＝アクティブ／スタンバイ、VRRP＝マスター／バックアップ（用語を取り違えない）

    9.8 押さえておくポイントと数値・コマンドの整理

    • FHRP＝仮想 IP／仮想 MAC を共有してデフォルトゲートウェイを冗長化
    • HSRP：Cisco 独自、アクティブ／スタンバイ、プライオリティ 100、大きい方が優先、preempt はデフォルト無効
    • VRRP：標準、マスター／バックアップ、preempt はデフォルト有効
    • GLBP：Cisco 独自、ルーターごとに異なる仮想 MAC で負荷分散
    • 設定：standby <grp> ip <VIP>、standby <grp> priority <値>、standby <grp> preempt。確認：show standby brief

    10.まとめ

    • 可用性は年間停止時間に直して考える。99.9% は約 8.8 時間、99.99% は約 53 分
    • 構成図をたどり、機械だけでなく人・手順・証明書も含めて SPOF を洗い出す
    • ステートレスな層はアクティブ-アクティブ＋N+1、DB はアクティブ-スタンバイ（Multi-AZ）が基本
    • まずはマルチ AZ。マルチリージョンは非同期複製と運用負担を理解したうえでビジネス判断で
    • 冗長化は RTO を、バックアップは RPO と誤操作対策を担う。バックアップは冗長化ではない
    • Shop は CloudFront → ALB（2 AZ）→ API（ASG）→ RDS Multi-AZ ＋ Redis ＋ S3 の構成になった
    • （発展）デフォルトゲートウェイは FHRP で冗長化する。PC には仮想 IP を設定し、HSRP は preempt がデフォルト無効、負荷分散できるのは GLBP

    11.理解度チェック

    Q1. ALB（99.99%）→ API 群（99.95%）→ RDS（99.95%）が直列につながっているとき、全体の可用性はおよそいくつですか。

    0.9999 × 0.9995 × 0.9995 ≈ 0.9989、つまり 約 99.89% です。直列の部品が増えるほど全体の可用性は下がります。各部品を冗長化して個々の可用性を上げることが大切です。

    Q2. 開発者が誤って本番 DB の orders テーブルを DROP しました。RDS は Multi-AZ 構成です。スタンバイから復旧できますか。

    できません。Multi-AZ は同期レプリケーションなので、DROP もスタンバイに即座に反映されます。自動バックアップのポイントインタイムリカバリ（PITR）で、DROP 直前の時点に復元する必要があります。これが「冗長化はバックアップではない」理由です。

    Q3. Shop の API は通常 4 台でピークをさばけます。2 AZ に分けて、1 AZ 全体が落ちてもピーク性能を保ちたい場合、何台必要ですか。3 AZ ならどうですか。

    2 AZ では、残る 1 AZ だけで 4 台必要なので各 AZ 4 台・合計 8 台 です。3 AZ なら、1 AZ が落ちても残り 2 AZ で 4 台あればよいので各 AZ 2 台・合計 6 台 で済みます。AZ を増やすほど予備の割合が小さくなります。

    Q4. 可用性 99.99% は年間・月間でどれくらいの停止まで許されますか。目標にするときの注意点は？

    年間約 52.6 分、月間約 4.3 分です。計画停止も停止に数えるので、OS パッチ・DB のバージョンアップ・デプロイも無停止で行える必要があります。9 を 1 つ増やすごとに費用と手間は数倍になるので、見合う目標を選びます。

    Q5. RDS Multi-AZ のフェイルオーバーで、アプリ側が確認しておくべきことは何ですか。

    切り替えは DNS の向き先変更で行われ、通常 60〜120 秒かかります。アプリは既存の接続が切れたら再接続する必要があるので、接続プールの再接続設定と、DNS を長時間キャッシュしない設定（JVM なら TTL 60 秒以下）を確認します。さらに冪等な処理だけのリトライ、タイムアウト、エラー画面の文言まで設計しておきます。

    Q6. HSRP で、PC のデフォルトゲートウェイに設定すべき値は何ですか。アクティブルーターの実 IP ではいけない理由は？

    HSRP の仮想 IP アドレス（例：192.168.1.254）です。アクティブルーターの実 IP にすると、そのルーターが故障したときに届かなくなり、冗長化の意味がありません。仮想 IP ならスタンバイが引き継ぐので、PC は設定を変えずに通信を続けられます。

    Q7. HSRP で R1（プライオリティ 110）が故障し、R2 がアクティブになりました。R1 が復旧してもアクティブに戻りません。なぜで、どうすればよいですか。

    HSRP のプリエンプトはデフォルトで無効なので、復旧してもアクティブの役割は交代しません。R1 に standby 1 preempt を設定すれば、プライオリティの高い R1 がアクティブを取り戻します（VRRP はプリエンプトがデフォルト有効）。

    Q8. HSRP・VRRP・GLBP のうち、1 つのグループ内で複数のルーターが同時に転送して負荷分散できるのはどれですか。その仕組みは？

    GLBP です。AVG が ARP に応答するとき、PC ごとにルーターごとの異なる仮想 MAC アドレスを返し、PC1 は R1、PC2 は R2 というように振り分けます。実際に転送する AVF は最大 4 台です。HSRP／VRRP はグループ内で 1 台しか転送しませんが、VLAN ごとにアクティブを分けて全体として負荷を分散する設計はできます。
