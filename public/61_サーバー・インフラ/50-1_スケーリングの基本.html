    50 スケーリング・負荷分散

    スケーリングの基本

    アクセスが増えてサーバーが苦しくなったとき、取れる手は 1 台を大きくする（スケールアップ） か 台数を増やす（スケールアウト） の 2 つです。このページでは、両者の違いとどちらを先に選ぶか、増やす前に「どこが詰まっているか（ボトルネック）」を調べる方法、スケールアウトの前提となる ステートレス化、DB のスケールの考え方、Shop が 1 台から複数台へ育っていく段階、キャパシティ計画の入口までを解説します。

    もとにしたノート：61_サーバー・インフラ/50_スケーリング・負荷分散/01_スケーリングの基本

    ひとことで言うと

    スケールアップは 1 台を大きく、スケールアウトは台数を増やすことです。増やす前にまず計測してボトルネックを特定 し、スケールアウトするなら サーバーに状態を持たせない（ステートレス化） のが前提です。DB は最後に詰まりやすいので別の手順で手を打ちます。

    1.スケーリングとは：ラーメン屋の例え

    ラーメン屋が繁盛して行列ができたとき、取れる手は 2 つあります。1 つは 店主の腕を上げて大きな寸胴鍋に替える（1 人を強くする）。もう 1 つは 店員を雇い、厨房を増やす（人数を増やす）。前者は簡単ですが限界があり、店主が倒れたら店は閉まります。後者は限界が遠く、1 人休んでも営業できますが、「誰がどのお客さんの注文を受けたか」をメモで共有する仕組みが必要になります。

    サーバーの スケーリング（Scaling：処理能力を増やすこと） もまったく同じです。

    • スケールアップ（Scale Up／垂直スケーリング）：1 台のサーバーを大きくする（CPU・メモリを増やす）
    • スケールアウト（Scale Out／水平スケーリング）：同じ役割のサーバーを並べて台数を増やす
    • 逆方向はそれぞれ スケールダウン（小さくする）、スケールイン（台数を減らす）
    • スケールアウトの前提は ステートレス（Stateless：サーバー自身が利用者ごとの状態を持たない） にすること

    2.スケールアップとスケールアウトの比較

    観点スケールアップ（垂直）スケールアウト（水平）
    やることインスタンスタイプを大きくする同じサーバーを増やし、ロードバランサーで振り分ける
    アプリの改修ほぼ不要ステートレス化が必要
    上限1 台の最大サイズで頭打ち理論上はかなり遠い（ただし DB など共有部分が先に詰まる）
    停止クラウドでもタイプ変更には再起動が必要なことが多い1 台ずつ入れ替えれば無停止
    障害への強さ1 台なので 単一障害点（SPOF） のまま1 台落ちても残りで動く
    コスト大きいサイズほど割高になりやすい小さい台を必要な数だけ。自動増減（オートスケーリング）と相性が良い
    向いているものDB（特に書き込み）、初期のとりあえずの対処Web／API サーバー、ワーカー

    単一障害点（SPOF：Single Point of Failure） とは、そこが 1 つ壊れたら全体が止まる部品のことです（高可用性と冗長化 でくわしく扱います）。

    2.1 実務での順番

    1. まずは 計測してボトルネックを特定 する
    2. コード・クエリを改善する（インデックス追加など）
    3. 足りなければ スケールアップ
    4. それでも足りない、または可用性が必要なら スケールアウト

    これが定番の順番です。スケールアップは「時間を買う」手段としてとても有効で、恥ずかしいことではありません。

    スケールアップの再起動

    AWS EC2 でインスタンスタイプを変えるには、インスタンスを一度 停止 する必要があります（2026 年時点）。1 台構成ならその間 Shop は止まります。メンテナンス時間を告知するか、先に 2 台構成にしておくのが安全です。

    3.ボトルネックの見つけ方

    ボトルネック（Bottleneck：瓶の首のように一番細くて流れを制限している所） を直さずに台数を増やしても、効果はありません。例えば DB が詰まっているのに API サーバーを 10 台にすると、DB への接続数が 10 倍になって むしろ悪化 します。

    調べる順番の目安と、Ubuntu 24.04 で使える基本コマンドです。

    資源詰まったときの症状確認コマンド見る値
    CPU応答が全体的に遅い、ロードアベレージが高いtop、mpstat -P ALL 1%us（アプリ）が高い／%wa が高いならディスク待ち
    メモリ突然プロセスが死ぬ（OOM Killer）、スワップ多発free -h、vmstat 1available が少ない、si/so（スワップ入出力）が 0 でない
    ディスク I/O書き込みやログ出力で固まるiostat -xz 1%util が 100% 近い、await（待ち時間）が大きい
    ネットワーク大きなファイル配信で遅い、帯域上限sar -n DEV 1、ss -s送受信量がインスタンスの帯域上限付近、接続数が異常
    DBAPI は暇なのに遅いpg_stat_activity、スロークエリログ長時間実行のクエリ、ロック待ち、接続数上限

    OOM Killer は、メモリが足りなくなったときに Linux がプロセスを強制終了する仕組みです。

    # sysstat（mpstat / iostat / sar）は Ubuntu では別パッケージ
sudo apt install -y sysstat

# 1 秒ごとに全 CPU コアの使用率
mpstat -P ALL 1

# ディスクごとの使用率と待ち時間
iostat -xz 1

# PostgreSQL：いま実行中で長いクエリ
sudo -u postgres psql -c "
  SELECT pid, now() - query_start AS duration, state, left(query, 80)
  FROM pg_stat_activity
  WHERE state <> 'idle'
  ORDER BY duration DESC;"

    コマンドで一時的に見るだけでなく、監視（メトリクスの継続記録） があれば「いつから」「何と一緒に」上がったのかが分かります。監視の仕組みは 66_可観測性の「04_サーバー監視とログ管理の基本」のノートと、可観測性体系の MOC を参照してください（観測性の考え方は 41 観測性 にもあります）。

    「アプリは暇なのに遅い」は外部待ち

    API サーバーの CPU が 10% なのにレスポンスが 2 秒かかるなら、時間は DB や外部 API の 待ち に使われています。このとき API サーバーを増やしても速くなりません。

    4.スケールアウトの前提：ステートレス化

    1 台のときは何も考えずに済んでいたことが、2 台になると問題になります。

    利用者 A ─ ログイン ─▶ API #1（メモリにセッション保存）
利用者 A ─ カートを見る ─▶ API #2（「誰？」→ ログイン画面へ）  ← 事故

    これを防ぐには、サーバーのメモリやローカルディスクに「状態」を置かない ことです。どの API サーバーに当たっても同じ結果になれば、自由に台数を増減できます。

    4.1 何をどこへ出すか

    状態1 台時代の置き場所スケールアウト後の置き場所
    ログインセッションプロセスのメモリ（express-session の MemoryStore など）Redis（ElastiCache 等）や DB。または署名付きトークン（JWT）で状態をクライアント側に持たせる
    アップロードファイル（商品画像）/var/www/shop/uploadsオブジェクトストレージ（S3 など）。配信は CDN から
    アプリ内キャッシュプロセス内の Map共有キャッシュ（Redis）。プロセス内キャッシュは「消えても困らない短命なもの」だけ
    定期実行（cron）各サーバーの crontab1 か所だけで動く仕組み（専用ワーカー、EventBridge Scheduler 等）。全台で動くと二重実行になる
    ログローカルファイルログ集約基盤へ送る（66_可観測性の「04_ログ集約基盤」のノート）
    設定・シークレットサーバー上で手編集環境変数・シークレットストア（設定と環境変数・シークレット）

    Redis は、メモリ上で動く高速なデータの置き場（キー・バリュー型のデータストア）で、複数のサーバーから共通に使えます。JWT は署名付きのトークンで、改ざんされていないことをサーバーが確かめられます（74 JWTの構造と検証）。

    4.2 セッションを Redis に置く例

    // Shop API（Express）：セッションを Redis に置く例
import session from "express-session";
import { RedisStore } from "connect-redis";
import { createClient } from "redis";

const redisClient = createClient({ url: process.env.REDIS_URL });
await redisClient.connect();

app.use(
  session({
    store: new RedisStore({ client: redisClient, prefix: "shop:sess:" }),
    secret: process.env.SESSION_SECRET!,
    resave: false,
    saveUninitialized: false,
    cookie: { secure: true, httpOnly: true, sameSite: "lax" },
  }),
);

    セッション管理の詳細は 74 セッション管理（特に セッションとCookieによるログイン）を参照してください。「同じ利用者を同じサーバーへ送る」スティッキーセッション で回避する方法もありますが、サーバーが落ちたら状態が消えるので、根本対策はあくまでステートレス化です（ロードバランサーの仕組み）。

    5.DB のスケール

    Web／API サーバーはステートレスにすれば簡単に増やせますが、DB は状態そのもの なので単純には増やせません。多くのシステムで、最後に詰まるのは DB です。手を打つ順番の目安は次のとおりです。

    1. クエリとインデックスの改善：遅いクエリを EXPLAIN ANALYZE で調べる。最も安く効果が大きい
    2. コネクションプーリング：API を増やすと DB 接続が増える。PgBouncer や RDS Proxy で束ねる（データベースサーバーの運用）
    3. スケールアップ：DB は垂直スケールが基本。メモリを増やしてキャッシュに載せる
    4. キャッシュ：よく読まれる商品一覧などを Redis に置き、DB に届く読み取りを減らす
    5. リードレプリカ（Read Replica：読み取り専用の複製）：読み取りを複製に分散。ただし複製には少し遅れ（レプリケーションラグ）がある
    6. シャーディング（Sharding：データを分割して複数 DB に分ける）：最終手段。アプリの設計が大きく変わる

    5 と 6、および整合性の問題は分散システムの領域なので、詳しくは 68_分散システムと 62_データアーキテクチャのノート（それぞれの MOC）を参照してください。

    6.Shop が 1 台から複数台へ育つ段階

    このサイトでは、架空の EC サイト「Shop」（Node.js の API、PostgreSQL、Nginx）を例に、構成がどう育つかを追っています。

    1. 段階 1：1 台　Nginx ＋ Shop API ＋ PostgreSQL（EC2 1 台）
      → DB と API が CPU・メモリを奪い合うようになったら次へ
    2. 段階 2：DB 分離　EC2（Nginx ＋ API）＋ RDS PostgreSQL
      → API 1 台が限界・SPOF になったら次へ
    3. 段階 3：スケールアウト　ALB ＋ API ×2 以上 ＋ RDS。セッションは Redis／画像は S3
      → 波のあるアクセス・静的ファイルが重くなったら次へ
    4. 段階 4：自動化と負荷軽減　Auto Scaling ＋ CloudFront（CDN）＋ リードレプリカ／キャッシュ
      → 止まると売上が消える段階になったら次へ
    5. 段階 5：高可用性　マルチ AZ・RDS Multi-AZ、SPOF の排除
    段階きっかけ主な作業該当ページ
    1サービス開始1 台に全部入りサーバー構築の流れ
    2DB と API がリソースを奪い合う、バックアップが不安DB を RDS に移すデータベースサーバーの運用
    3API の CPU が常に高い、1 台落ちると全停止ステートレス化 → LB の後ろに 2 台ロードバランサーの仕組み
    4セール時だけ急増、画像配信が重いオートスケーリング、CDNオートスケーリング、CDNによる負荷軽減
    5停止時間の目標ができたマルチ AZ、冗長化高可用性と冗長化

    大事なのは 全部を最初からやらない ことです。段階 1 で月間数万 PV は十分さばけます。早すぎる分散は、運用の手間と障害点を増やすだけです。

    7.キャパシティ計画の入口

    キャパシティ計画（Capacity Planning） は「いつ・どれだけ増やすか」を事前に決めることです。最低限次の 3 つを押さえます。

    1. 現状の上限を測る：負荷試験ツール（k6、wrk など）で、API 1 台が何 RPS（1 秒あたりリクエスト数）までレイテンシ（応答までの待ち時間）を保てるかを測る
    2. ピークを見積もる：普段の何倍のアクセスが来るか（セール、テレビ放映、月末）
    3. 余裕を持つ：CPU 使用率 100% を上限と考えない。目安として平常時 40〜60% 程度に収めると、急増や 1 台故障に耐えられる
    # k6 での簡単な負荷試験（別マシンから実行する）
# 50 仮想ユーザーで 2 分間、商品一覧 API を叩く
k6 run --vus 50 --duration 2m - <<'EOF'
import http from "k6/http";
export default function () {
  http.get("https://api.shop.example.com/products");
}
EOF

    例えば「API 1 台で 200 RPS、ピーク予測 900 RPS、1 台壊れても耐えたい」なら、900 ÷ 200 = 4.5 → 5 台、さらに 1 台故障分で 6 台 が目安です（N+1 の考え方は 高可用性と冗長化）。詳しい性能計測・計画は 67_パフォーマンスのノート（MOC）を参照してください。

    本番に負荷試験をかけない

    本番環境に予告なしで負荷試験をすると、それ自体が障害になります。クラウドによっては事前申請や規約上の制限もあります。本番と同じ構成のステージング環境で行いましょう。

    8.よくある誤解・つまずき

    誤解実際
    遅くなったら台数を増やせばいいボトルネックが DB なら API を増やすと悪化します。まず計測です。
    スケールアウトのほうが常に優れているアプリ改修と運用の複雑さが増えます。小さいうちはスケールアップで十分なことが多いです。
    ロードバランサーを置けばそのまま複数台にできるセッションやアップロードファイルをサーバー内に持っていると、ログインが切れたり画像が見つからなくなったりします。
    DB もリードレプリカを足せばどんどんスケールするレプリカで増やせるのは読み取りだけです。書き込みは 1 台（プライマリ）に集まります。
    cron は全台に同じ設定を入れておけばいい全台で同時に実行され、メールの二重送信などが起きます。

    9.まとめ

    • スケールアップは 1 台を大きく、スケールアウトは台数を増やす。前者は簡単だが限界と SPOF がある
    • 増やす前に CPU・メモリ・ディスク・ネットワーク・DB のどこが詰まっているかを計測する
    • スケールアウトの前提はステートレス化。セッションは Redis、ファイルは S3、ログは集約基盤へ出す
    • DB は最後に詰まりやすい。クエリ改善 → プーリング → スケールアップ → キャッシュ・レプリカ → シャーディングの順
    • Shop は 1 台 → DB 分離 → LB＋複数台 → 自動化と CDN → 高可用性と段階的に育てる
    • キャパシティ計画は「1 台の上限 × ピーク予測 × 余裕」で台数を見積もる

    10.理解度チェック

    Q1. API サーバーの CPU 使用率は 15% なのに、レスポンスが遅いです。API サーバーを 2 倍に増やすのは良い対策でしょうか。

    良い対策ではない可能性が高いです。CPU が暇なのに遅いのは、DB や外部 API の待ちに時間を使っているからです。まず pg_stat_activity やスロークエリログで DB を調べます。API を増やすと DB 接続が増え、かえって悪化することもあります。

    Q2. Shop API を 2 台にしたところ、「ログインしたのに次の画面でログアウトされる」と報告がありました。原因と根本対策は何でしょうか。

    セッションを各 API サーバーのメモリに保存しているため、2 回目のリクエストが別のサーバーに届くと「知らない人」になります。根本対策はセッションを Redis などの共有ストアに出す（ステートレス化する）ことです。スティッキーセッションは応急処置にすぎません。

    Q3. API 1 台で 150 RPS さばけ、ピークは 600 RPS の見込みです。1 台故障しても耐えるには何台必要でしょうか。

    600 ÷ 150 = 4 台がピークに必要な台数です。1 台故障に備えて +1 で 5 台 です（N+1）。実際には CPU の余裕も考えて、さらに少し多めにすることがあります。

    Q4. 各 API サーバーの crontab に「毎朝 9 時にお知らせメールを送る」処理を入れて 3 台に増やしました。何が起きますか。

    3 台すべてで同時に実行され、メールが 3 通ずつ届く二重（三重）送信が起きます。定期実行は専用ワーカーや EventBridge Scheduler など、1 か所だけで動く仕組みに移します。

    Q5. 読み取りが多く DB が苦しいので、リードレプリカを追加しました。書き込みもこれで分散できますか。

    できません。リードレプリカで分散できるのは読み取りだけで、書き込みはプライマリ 1 台に集まります。また複製には少し遅れ（レプリケーションラグ）があります。書き込みまで分けるにはシャーディングが必要ですが、アプリの設計が大きく変わる最終手段です。

    Q6. スケールアップを選ぶのはどんなときで、注意点は何ですか。

    DB（特に書き込み）や、サービス初期にとりあえず時間を買いたいときに向きます。アプリの改修はほぼ不要ですが、1 台の最大サイズで頭打ちになり、1 台なので SPOF のままです。EC2 ではタイプ変更に停止が必要なので、1 台構成なら止まる時間を告知するか、先に 2 台構成にしておきます。
