    アプリケーションサーバーとは

    Nginx のような Web サーバー と、あなたが書いたコードを動かす アプリケーションサーバー は、得意なことが違うので役割を分けます。このページでは、両者の境界線、リクエストが Nginx → アプリサーバー → アプリのコード → DB と流れる全体像、Node.js / Python / Ruby / Java / PHP それぞれのアプリサーバーの正体、プロセス・スレッド・イベントループという 3 つの同時処理モデル、そして本番で必須になる ステートレス設計 と コネクションプール を解説します。最後に補足として、プログラミング言語とデータベースの分類・選び方・連携（ORM・トランザクション）も整理します。

    もとにしたノート：docs/61_サーバー・インフラ/30_アプリ実行環境/01_アプリケーションサーバーとは

    ひとことで言うと

    レストランに例えると、Web サーバーは「ホール係」、アプリケーションサーバーは「厨房」 です。ホール係（Nginx）は入口でお客さんを迎え、水やメニュー（静的ファイル）ならその場で出し、料理の注文（動的なリクエスト）だけを厨房に通します。厨房（アプリケーションサーバー）はレシピ（あなたが書いたアプリのコード）に従って料理を作り、必要なら冷蔵庫（データベース）から食材を取り出します。

    この記事は 20-1 Webサーバーとは と 20-3 リバースプロキシ を読んでいると理解しやすいです。

    1.Web サーバーとアプリサーバーの違い

    Web サーバー

    HTTP の受付・TLS 終端（HTTPS の暗号をここで解くこと）・静的ファイル配信・振り分けが得意です。中身の「業務ロジック」は知りません。

    アプリケーションサーバー（Application Server）

    あなたのコードを実行して、リクエストごとに違う結果（動的コンテンツ）を作ります。

    両者を分けるのは「得意なことが違う」からです。Nginx は数万の接続をさばくのが得意ですが、商品の在庫計算はできません。アプリは計算できますが、遅いクライアントや大量の静的ファイルの相手は苦手です。

    2.Web サーバーとアプリサーバーの境界

    2.1 それぞれの担当

    仕事Web サーバー（Nginx）アプリケーションサーバー
    HTTPS（TLS）の暗号化・復号◎ ここでやる✕ 通常やらない
    画像・CSS・JS などの静的ファイル◎ ディスクから直接返す△ できるが非効率
    遅いクライアントの相手（バッファリング）◎✕ 苦手
    ログイン判定・注文処理・DB 読み書き✕◎ ここでやる
    複数のアプリへの振り分け・負荷分散◎✕

    バッファリング とは、通信の遅い相手とのやり取りを Web サーバーがいったん受け止めて、アプリを待たせないようにすることです。

    「アプリケーションサーバー」という言葉は少し曖昧で、次の 2 つの意味で使われます。

    1. ソフトウェアとしてのアプリサーバー：Gunicorn、Puma、Tomcat など、「アプリのコードを読み込んで HTTP リクエストを渡してくれるプログラム」
    2. マシン（役割）としてのアプリサーバー：「アプリが動いているサーバー機」。構成図で「AP サーバー」と書かれるもの

    このページでは主に 1 の意味で使い、「アプリのコードを動かす実行環境」として説明します。

    2.2 Shop でのリクエストの流れ

    この章で例に使う通販サイト「Shop」の 1 台構成（Nginx ＋ Shop API ＋ PostgreSQL）で、「商品一覧を見る」リクエストを追ってみます。

    Nginx からアプリへの転送は proxy_pass http://127.0.0.1:3000/products のように書きます。ポイントは、ポート 3000 は外に公開せず、127.0.0.1（自分自身だけを指すアドレス）で待ち受ける ことです。外から届くのは Nginx の 443 番だけで、アプリサーバーは「Nginx からしか話しかけられない厨房」にしておきます（20-3 リバースプロキシ 参照）。

    2.3 「アプリサーバー」と「アプリのコード」の境界

    言語によっては、アプリサーバーとアプリのコードの間に 決まったインターフェース（約束事） があります。

                  ┌───────────── アプリサーバー ─────────────┐   ┌── アプリのコード ──┐
Nginx ─HTTP─▶ │ ソケット受付 → HTTP解析 → ワーカーへ割当 │ ─▶│ Flask / FastAPI    │
              └──────────────────────────────────────────┘   │ Rails / Spring ... │
                         ▲ 約束事: WSGI / ASGI / Rack / Servlet / FastCGI        │
                                                              └────────────────────┘

    この約束事があるおかげで、「Flask アプリを Gunicorn で動かす」「Rails アプリを Puma で動かす」のように、アプリサーバーとフレームワークを自由に組み合わせられる のです。

    3.言語ごとのアプリサーバー

    言語代表的なアプリサーバーアプリとの約束事同時処理モデル（既定）
    Node.jsなし（Node.js 自身がサーバー）http モジュールイベントループ（1 プロセス）
    Python（同期）Gunicorn、uWSGIWSGIマルチプロセス（＋スレッド）
    Python（非同期）Uvicorn、Hypercorn、Gunicorn＋ASGI ワーカーASGIイベントループ × プロセス
    RubyPumaRackマルチプロセス × マルチスレッド
    JavaTomcat、Jetty（Spring Boot に組み込み）Servletスレッドプール
    PHPPHP-FPMFastCGIマルチプロセス（リクエストごとに使い捨ての状態）

    3.1 Node.js：自分自身がサーバー

    Node.js では、Express などのアプリが app.listen(3000) を呼んだ瞬間に アプリ自体が HTTP サーバー になります。Python の Gunicorn のような「間に入るアプリサーバー」はありません。その代わり、プロセスの監視や再起動、マルチコア活用は PM2 や systemd、コンテナ基盤に任せます。詳しくは 30-2 Node.jsアプリを本番で動かす で扱います。

    3.2 Python：WSGI / ASGI サーバーが必要

    Flask・Django（同期）は WSGI、FastAPI（非同期）は ASGI という約束事でアプリサーバーとつながります。flask run のような開発用サーバーは本番向けではないため、Gunicorn や Uvicorn を使います。詳しくは 30-3 Pythonアプリを本番で動かす で扱います。

    3.3 Ruby：Puma

    Rails の既定アプリサーバーです。workers（プロセス数）と threads（各プロセスのスレッド数）の 2 軸で同時処理数を決めます。

    # config/puma.rb（抜粋）
workers ENV.fetch("WEB_CONCURRENCY", 2)
threads 5, 5
bind "tcp://127.0.0.1:3000"

    3.4 Java：Tomcat / Jetty

    Java では Servlet という仕様に沿ったコンテナ（Tomcat、Jetty）がアプリサーバーです。昔は Tomcat を別にインストールして WAR ファイルを配置していましたが、現在の Spring Boot は Tomcat を内蔵した実行可能 JAR を java -jar app.jar で起動するのが主流です。リクエストごとにスレッドプールのスレッドが 1 本割り当てられます。

    3.5 PHP：PHP-FPM

    PHP は Nginx から FastCGI で PHP-FPM（FastCGI Process Manager）にリクエストを渡します。PHP-FPM はワーカープロセスを何本か用意し、1 リクエストずつ処理します。リクエストが終わると変数はすべて捨てられるので、PHP は言語の仕組みとして自然にステートレス になっています。

    ; /etc/php/8.3/fpm/pool.d/www.conf（Ubuntu 24.04 の PHP 8.3 の例・抜粋）
[www]
user = www-data
group = www-data
listen = /run/php/php8.3-fpm.sock
pm = dynamic
pm.max_children = 20      ; 同時に処理できるリクエスト数の上限
pm.start_servers = 4
pm.min_spare_servers = 2
pm.max_spare_servers = 6
pm.max_requests = 500     ; 500 リクエストごとにワーカーを作り直す（メモリリーク対策）

    Nginx 側では、.php へのリクエストを PHP-FPM のソケットへ渡します。

    location ~ \.php$ {
    include snippets/fastcgi-php.conf;
    fastcgi_pass unix:/run/php/php8.3-fpm.sock;
}

    4.同時処理モデル：プロセス・スレッド・イベントループ

    アプリサーバー選びで一番大事なのは「同時に来たリクエストをどうさばくか」です。厨房の例えで比べます。

    マルチプロセス

    料理人 A・B・C が、それぞれ 専用の台所 を持って料理します。

    マルチスレッド

    料理人 A・B・C が、1 つの共有の台所 で一緒に料理します。

    イベントループ

    料理人は 1 人。鍋を火にかけたら、煮えるのを待たずに次の注文へ取りかかります。

    モデル仕組み長所短所代表例
    マルチプロセスOS のプロセスを複数起動し、それぞれが 1 リクエストを担当1 つが落ちても他は無事。メモリが独立していて安全プロセスごとにメモリを消費。同時数＝プロセス数Gunicorn sync、PHP-FPM
    マルチスレッド1 プロセス内に複数スレッド。メモリを共有プロセスより軽い。同時数を増やしやすい共有データの競合（スレッドセーフ）に注意Tomcat、Puma、Gunicorn gthread
    イベントループ1 スレッドが「待ち時間」の間に別の処理を進めるDB や外部 API 待ちが多い処理で非常に効率的CPU を長く使う処理が 1 つあると全体が止まるNode.js、Uvicorn

    スレッドセーフ とは、複数のスレッドが同時に同じデータを触っても壊れないように作られていることです。

    実際には組み合わせて使います。たとえば「Puma = プロセス × スレッド」「Gunicorn＋Uvicorn ワーカー = プロセス × イベントループ」「Node.js を PM2 cluster で 4 プロセス = プロセス × イベントループ」です。プロセスを増やすのはマルチコア CPU を使い切るため、スレッドやイベントループは 1 コアの中で待ち時間を有効活用するため、と覚えると整理しやすいです。

    Web アプリは「待ち時間」が大半

    一般的な API の処理時間の多くは、DB や外部 API の応答待ち（I/O 待ち）です。この待ち時間に CPU を遊ばせないために、スレッドやイベントループが使われます。逆に画像変換や暗号計算のような CPU を使う処理（CPU バウンド）は、プロセスを増やすかバックグラウンドジョブに逃がすのが基本です。

    5.ステートレスにする理由

    ステートレス（stateless） とは、「アプリサーバーのメモリやローカルディスクに、次のリクエストで必要な情報を残さない」設計です。

    5.1 なぜ必要か

    Shop が成長して API を 2 台にし、ロードバランサー（LB）（リクエストを複数のサーバーに振り分ける装置）の後ろに置いたとします。

    ログイン状態やカートをサーバー1のメモリに持っていると、次のリクエストがサーバー2に振られた瞬間に「ログアウトされた」「カートが空になった」という事故が起きます。また、デプロイや再起動でプロセスが入れ替わるたびに状態が消えます。同じことは 1 台の中でも起こります。PM2 cluster や Gunicorn のように 複数プロセスで動かすと、プロセス同士はメモリを共有しない からです。

    5.2 どこに状態を置くか

    状態置き場所
    セッション・ログイン状態Redis などの 共有ストア（複数のサーバーから使える共通の置き場）、または署名付きトークン（JWT など）
    カート・注文などの業務データPostgreSQL
    アップロード画像S3 などのオブジェクトストレージ
    キャッシュRedis（ローカルメモリのキャッシュは「消えてもよい」ものだけ）

    ステートレスにしておけば、サーバーを増やす・減らす・入れ替えるのが自由になります。これは 50-1 スケーリングの基本 や、ローリングアップデート（サーバーを 1 台ずつ順に入れ替えるデプロイ方法）の前提条件です。セッションの詳細は 74 セッション管理 を参照してください。

    6.コネクションプール

    6.1 例え

    DB への接続は「電話をかけて相手が出るまで待つ」ようなもので、TCP 接続・認証・セッション準備に毎回時間がかかります。コネクションプール（connection pool） は、あらかじめ何本か電話をつないだままにしておき、使いたい処理が「借りて、使ったら返す」仕組みです。

    6.2 仕組みと設定例（Shop API / Node.js + pg）

    // src/db.ts
import { Pool } from "pg";

export const pool = new Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,                      // このプロセスが持つ最大接続数
  idleTimeoutMillis: 30_000,    // 使われない接続は 30 秒で閉じる
  connectionTimeoutMillis: 5_000, // 借りられないまま 5 秒経ったらエラー
});

// 使う側：pool.query は「借りる → 実行 → 返す」を自動で行う
const { rows } = await pool.query("SELECT id, name, price FROM products LIMIT 50");

    6.3 実務での注意：接続数は「掛け算」で増える

    プールはプロセスごとに作られます。DB から見た接続数は次の掛け算です。

    DB への総接続数 = サーバー台数 × 1台あたりのプロセス数 × プールの max
例）API 2台 × PM2 4プロセス × max 10 = 80 接続

    PostgreSQL の max_connections の既定値は 100 です。台数やプロセスを増やしたとたんに too many connections で落ちる、という事故がよくあります。対策は次のとおりです。

    • プールの max を「DB の上限 ÷ 全プロセス数」から逆算する（管理用・マイグレーション用の余裕も残す）
    • 接続数が多くなる構成では PgBouncer や RDS Proxy のような 外部のコネクションプーラー を間に置く
    • 詳しくは 30-6 データベースサーバーの運用 を参照

    7.アプリサーバー選びの観点

    多くの場合「言語とフレームワークが決まれば、アプリサーバーもほぼ決まる」ので、迷ったら各フレームワークの公式ドキュメントが推奨するものを選ぶのが正解です。そのうえで次の観点を確認します。

    観点確認すること
    処理の性質I/O 待ちが多い → イベントループ／スレッド。CPU を使う → プロセスを増やす・ジョブに分離
    同時処理数プロセス数 × スレッド数（または非同期の同時実行数）が想定アクセスに足りるか
    メモリ1 プロセスあたりのメモリ × プロセス数がサーバーのメモリに収まるか
    再起動とシャットダウンSIGTERM で処理中のリクエストを終えてから止まれるか（グレースフルシャットダウン）
    運用のしやすさsystemd・コンテナとの相性、ログの出し方、ヘルスチェックのしやすさ
    実行基盤VM なら 1 台でプロセスを複数、コンテナなら「1 コンテナ 1 プロセス」でコンテナ数を増やす方が素直

    コンテナ時代の考え方

    Kubernetes や ECS では、プロセス監視・再起動・台数の増減を基盤が担当します。そのため、アプリサーバー側のマルチプロセス機能（PM2 cluster、Gunicorn の複数ワーカー）を使わず、1 コンテナ 1 プロセスにしてコンテナ数で調整する 構成がよく選ばれます（コンテナの本番向けベストプラクティス）。

    8.よくある誤解・つまずき

    ✕ 誤解◯ 実際
    Nginx があればアプリも動くNginx はアプリのコードを実行しません。アプリを実行するのはアプリサーバー（Node.js、Gunicorn など）で、Nginx は手前で受け付けて転送するだけです。
    Node.js はアプリサーバーがないから本番では Nginx が不要Node.js 自身が HTTP サーバーになれても、TLS 終端・静的ファイル・遅いクライアント対策のために Nginx を前に置くのが定番です。
    プロセスを増やせば増やすほど速くなるCPU コア数やメモリ、DB の接続上限を超えると逆に遅くなったり落ちたりします。
    メモリ上の変数にセッションを持っても 1 台なら問題ない1 台でも複数プロセスで動かせばプロセス間で共有されず、再起動でも消えます。最初から外部ストアに置きましょう。
    コネクションプールの max は大きいほど安心総接続数は「台数 × プロセス数 × max」。DB の上限を超えないよう逆算します。

    9.補足：プログラミング言語とデータベースの役割

    アプリサーバーの上で動くプログラミング言語と、その先にあるデータベースについて、種類・選び方・連携方法（ORM・トランザクション）を整理します。

    プログラミング言語とデータベースは、Web アプリケーションやシステム開発において重要な役割を果たします。プログラミング言語は、コンピュータに指示を与えるための言語であり、データベースは、データを効率的に保存・管理・検索するためのシステムです。両者は密接に関連し、現代の IT システムを支える基盤技術です。

    データモデルによる分類

    • NoSQL：非リレーショナル、柔軟なスキーマ
    • グラフ：ノードとエッジの関係
    • 時系列：時間順のデータ

    用途による分類

    • OLTP：オンライントランザクション処理（注文などの日々の細かい読み書き）
    • OLAP：オンライン分析処理（大量データの集計）
    • キャッシュ：高速アクセス用
    • 検索：全文検索、ファセット検索

    9.6 データベース設計の原則

    正規化

    • 第 1 正規形：原子値のみ
    • 第 2 正規形：部分関数従属の除去
    • 第 3 正規形：推移関数従属の除去
    • 目的：データの重複排除、整合性確保

    ACID 特性

    • Atomicity：原子性、全成功または全失敗
    • Consistency：一貫性、データの整合性
    • Isolation：独立性、並行実行の制御
    • Durability：永続性、データの永続化

    インデックス設計

    • 主キー：一意性の保証
    • 外部キー：参照整合性
    • 複合インデックス：複数カラムの組み合わせ
    • 部分インデックス：条件付きインデックス

    10.まとめ

    • Web サーバーは「受付・TLS・静的ファイル・振り分け」、アプリサーバーは「アプリのコードの実行」を担当する
    • Python は WSGI/ASGI、Ruby は Rack、Java は Servlet、PHP は FastCGI という約束事でアプリサーバーとアプリがつながる。Node.js はアプリ自身がサーバー
    • 同時処理モデルはプロセス・スレッド・イベントループの 3 つ。マルチコア活用はプロセス、待ち時間の活用はスレッド／イベントループ
    • 状態はアプリサーバーに持たず、DB・Redis・オブジェクトストレージに置く（ステートレス）
    • DB 接続はコネクションプールで再利用し、総接続数を DB の上限から逆算する

    11.理解度チェック

    Q1. Shop API を 2 台に増やしたら「ときどきログインが外れる」と苦情が来ました。考えられる原因と対策は？

    セッションを各サーバーのメモリに保存していることが原因と考えられます。ロードバランサーが別のサーバーに振ると、そのサーバーはセッションを知りません。Redis などの共有ストアにセッションを置くか、署名付きトークンを使ってアプリをステートレスにします。

    Q2. API 3 台 × 各 4 プロセス × プール max 10 の構成で、PostgreSQL の max_connections が既定値の 100 だと何が起きますか？

    最大 3 × 4 × 10 = 120 接続になり、上限 100 を超えて too many connections エラーが起こり得ます。max を 6〜7 程度に下げるか、PgBouncer / RDS Proxy などのプーラーを入れます。

    Q3. 画像のサムネイル生成（CPU を長く使う処理）を Node.js の API の中で同期的に実行すると、何が問題になりますか？

    Node.js はイベントループ（1 スレッド）で動くため、CPU を占有する処理の間はそのプロセスの他のリクエストがすべて待たされます。ワーカースレッドやバックグラウンドジョブに分離するのが基本です。

    Q4. Nginx を入れれば、アプリのコードも Nginx が実行してくれますか？

    いいえ。Nginx は受付・TLS 終端・静的ファイル配信・振り分けを担当し、アプリのコードは実行しません。コードを動かすのは Node.js、Gunicorn、Puma、PHP-FPM などのアプリサーバーです。

    Q5. 「Flask アプリを Gunicorn で動かす」のように、フレームワークとアプリサーバーを自由に組み合わせられるのはなぜですか？

    両者の間に WSGI / ASGI / Rack / Servlet / FastCGI といった決まった約束事（インターフェース）があるからです。約束事を守っていれば、どのアプリサーバーでも同じアプリを動かせます。

    Q6. プロセスを増やす目的と、スレッドやイベントループを使う目的の違いは何ですか？

    プロセスを増やすのはマルチコア CPU を使い切るためです。スレッドやイベントループは、1 コアの中で DB や外部 API の待ち時間を有効活用するためです。
