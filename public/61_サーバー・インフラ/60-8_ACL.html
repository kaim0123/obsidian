    60 サーバー・ネットワークセキュリティ

    ACL（アクセスコントロールリスト）

    ACL は、ルータを通るパケットを条件に応じて許可・拒否するための、上から順に並んだルールのリストです。このページでは、標準 ACL と拡張 ACL の違い、評価順序（上から順・最初に一致・暗黙の deny any）、ワイルドカードマスクの計算、拡張 ACL の書き方と置き場所、インターフェースと vty への適用、名前付き ACL の編集、確認とトラブルシューティングまでを例題つきで解説します。

    もとにしたノート：60_サーバー・ネットワークセキュリティ/08_ACL（アクセスコントロールリスト）

    ひとことで言うと

    ACL は書いた順に上から調べ、最初に一致した行だけを適用し、どれにも一致しなければ暗黙の deny any で捨てます。標準 ACL（送信元だけ）は宛先の近く、拡張 ACL（宛先・ポートも見る）は送信元の近くに置き、インターフェースには ip access-group、vty には access-class で適用します。

    このページは、IP アドレスとサブネットマスクの考え方（11_コンピューターサイエンスの「05IPアドレスとサブネットとゲートウェイ」のノート）と 60-3 ファイアウォールとネットワーク制御 を読んでいると理解しやすいです。サーバー側のファイアウォール（ufw）やクラウドのセキュリティグループ・ネットワーク ACL は 60-3 を参照してください。このページでは、ルータで通信を許可・拒否する ACL を扱います。

    ACL（Access Control List）の 1 行 1 行を ACE（Access Control Entry） と呼びます。ネットワークのセキュリティで特によく出てくるテーマなので、仕組み・書式・計算・適用・確認まで一通り身につけましょう。

    「ACL」という言葉について

    アプリの認可モデルとしての ACL（リソースごとに「誰が何をできるか」を並べたリスト）もあります。考え方は似ていますが、ここで扱うのはパケットを通すかどうかを決めるネットワーク機器の ACL です。認可モデルの ACL は 73 RBAC・ABAC・ACLの使い分け を参照してください。

    1.ACL の種類

    種類番号条件にできるもの推奨される適用場所
    標準 ACL1〜99、1300〜1999送信元 IP アドレスだけ宛先に近い場所
    拡張 ACL100〜199、2000〜2699プロトコル、送信元 IP、宛先 IP、送信元/宛先ポート番号など送信元に近い場所
    名前付き ACL番号の代わりに名前標準（standard）または拡張（extended）を指定標準/拡張それぞれの推奨に従う

    標準 ACL（1〜99）で条件にできるのは送信元 IP アドレスだけです。宛先 IP アドレス、宛先ポート番号、プロトコル（TCP/UDP）を条件にするには拡張 ACL を使います。

    標準ACL:  access-list 10  permit 192.168.1.0 0.0.0.255
                          │      └──── 送信元（＋ワイルドカード）だけ
拡張ACL:  access-list 100 permit tcp 192.168.1.0 0.0.0.255 host 10.1.1.10 eq 80
                          │      │   └──── 送信元 ────┘  └── 宛先 ──┘  └ 宛先ポート
                          │      └ プロトコル
                          └ 動作

    2.ACL の評価順序（上から順・最初に一致・暗黙の deny）

    ACL の動作は、次の 3 つのルールですべて説明できます。

    1. 上の行から順に確認する。
    2. 最初に一致した行の動作（permit/deny）だけを適用し、そこで確認を終了する（下の行は見ない）。
    3. どの行にも一致しなければ、最後にある暗黙の deny any（設定にも表示されない）で破棄する。
    パケット到着
   │
   v
[1行目に一致？] ──Yes──> 1行目の動作（permit/deny）を実行して終了
   │No
   v
[2行目に一致？] ──Yes──> 2行目の動作を実行して終了
   │No
   v
  ...
   │No
   v
[暗黙の deny any] ─────> 破棄

    一言でいうと「上の行から順に確認し、最初に一致した行の動作だけを適用する」です。次のような理解は誤りです。

    • 「すべての行を確認し、最後に一致した行を使う」→ 最初に一致した行です。
    • 「deny を先に確認し、そのあと permit」→ 種類に関係なく書かれた順です。
    • 「条件が最も具体的な行を優先」→ ルーティングのロンゲストマッチ（最も長く一致する経路を選ぶ規則）と混同しています。ACL は書いた順番がすべてです。

    このため、ACL は具体的な条件の行を上に、広い条件の行を下に書くのが基本です。

    ✕ 悪い例：permit any が先頭にあるので、2 行目の deny は一度も使われない 
    access-list 10 permit any
access-list 10 deny   host 192.168.1.5
    ◯ 良い例：具体的な deny を先に、広い permit を後に 
    access-list 10 deny   host 192.168.1.5
access-list 10 permit any

    2.1 暗黙の deny any

    ACL の最後には、設定に表示されない「すべての通信を拒否する（deny any）」が必ずあります。「permit any」ではありません。「直前のルールを繰り返す」ような動作もなく、「暗黙のルールは存在しない」わけでもありません。

    access-list 10 deny host 192.168.1.5
(access-list 10 deny any)       ← 表示されないが必ず存在する

    2.2 例題：deny だけの ACL

    問題：192.168.1.5 の PC だけを止めるつもりで access-list 10 deny host 192.168.1.5 だけを作り、インターフェースに適用しました。結果はどうなるでしょうか。

    ステップ1: 実際に評価される行を書き出す（暗黙の行も含める）
    1行目  deny host 192.168.1.5
    暗黙   deny any

ステップ2: 送信元 192.168.1.5 のパケットを当てはめる
    1行目に一致 → deny（破棄）

ステップ3: 送信元 192.168.1.20 のパケットを当てはめる
    1行目に不一致 → 暗黙の deny any に一致 → 破棄

ステップ4: 結論
    permit の行が1つもないので、すべての送信元からの通信が拒否される

    よくある勘違いも確認しておきます。

    • 「192.168.1.5 だけ拒否され、他は許可される」→ permit の行がないので、他も拒否されます。
    • 「192.168.1.5 だけが許可される」→ deny を指定しているので逆です。
    • 「permit がないので ACL は無視される」→ permit がなくても ACL は有効で、すべてを拒否します。

    意図どおりにするには 2 行目を追加します。

    R1(config)# access-list 10 permit any

    実務の注意

    「deny だけの ACL はすべてを止める」は実務でもよくある事故です。リモート（SSH）から ACL を変更・適用すると、自分の管理用の接続まで切ってしまうことがあります。

    3.ワイルドカードマスク

    ACL でアドレスの範囲を指定するには、サブネットマスクではなくワイルドカードマスクを使います。

    ビット意味
    0そのビットは一致が必要（チェックする）
    1そのビットはどの値でもよい（無視する）

    サブネットマスクとは 0 と 1 の意味が逆です。

    指定意味キーワードでの書き方
    192.168.1.5 0.0.0.0全ビット一致が必要 → 1 台だけhost 192.168.1.5
    0.0.0.0 255.255.255.255全ビットどの値でもよい → すべてのアドレスany
    192.168.1.0 0.0.0.255先頭 3 オクテットが一致すればよい → 192.168.1.0/24—

    3.1 計算方法：255.255.255.255 からサブネットマスクを引く

      255.255.255.255
− 255.255.255.0     （/24 のサブネットマスク）
─────────────────
    0.  0.  0.255   ← ワイルドカードマスク

    例題：標準 ACL で 192.168.1.0/24 全体を許可します。access-list 10 permit 192.168.1.0 の後に指定するワイルドカードマスクは何でしょうか。

    ステップ1: /24 のサブネットマスクは 255.255.255.0
ステップ2: 255.255.255.255 − 255.255.255.0 = 0.0.0.255
ステップ3: 意味の確認
           0.0.0.255 → 前の3オクテット（192.168.1）は一致が必要、最後のオクテットはどの値でもよい
           → 192.168.1.0 〜 192.168.1.255
答え: access-list 10 permit 192.168.1.0 0.0.0.255

    ほかの値を書いた場合の意味は次のとおりです。

    値意味
    255.255.255.0サブネットマスクそのもの。ワイルドカードでは意味が逆になる
    0.0.0.0192.168.1.0 の 1 つのアドレスだけ（host と同じ）
    255.255.255.255すべてのアドレス（any と同じ）

    3.2 速算法：最後のオクテット＝ブロックサイズ − 1

    ブロックサイズは、そのサブネットに含まれるアドレスの数（256 − サブネットマスクの第 4 オクテット）です。

    プレフィックスサブネットマスク（第4オクテット）ブロックサイズワイルドカード（第4オクテット）
    /240256255
    /25128128127
    /261926463
    /272243231
    /282401615
    /2924887
    /3025243
    /3225510（host）

    例題：192.168.1.64/26（192.168.1.64〜192.168.1.127）を指定するワイルドカードマスクは何でしょうか。

    ステップ1: /26 のサブネットマスク → 255.255.255.192
ステップ2: 反転する → 255 − 192 = 63 → 0.0.0.63
          （速算：/26 のブロックサイズは 256 − 192 = 64 → 64 − 1 = 63）
ステップ3: 範囲の検算
          192.168.1.64  = ...0100 0000
          ワイルドカード63 = ...0011 1111   ← 下位6ビットはどの値でもよい
          → 192.168.1.64（01 000000）〜 192.168.1.127（01 111111）  ✔
答え: access-list 10 permit 192.168.1.64 0.0.0.63

    間違えやすい値は次のとおりです。

    値なぜ合わないか
    0.0.0.64ブロックサイズ 64 をそのまま書いている。ワイルドカードはブロックサイズ − 1
    255.255.255.192/26 のサブネットマスク。ワイルドカードではない
    0.0.0.127/25 のワイルドカード。192.168.1.0〜127 になり広すぎる

    補足

    ACL では、指定したアドレスとワイルドカードマスクの組み合わせで「0 のビットだけを比較」します。アドレス部分はネットワークアドレス（ブロックの先頭）で書くのが原則です。

    4.拡張 ACL の書式

    access-list 番号 {permit|deny} プロトコル 送信元 ワイルドカード [ポート条件] 宛先 ワイルドカード [ポート条件]
    • 番号：100〜199（および 2000〜2699）
    • プロトコル：ip（すべての IP）、tcp、udp、icmp など
    • アドレス：any、host X.X.X.X、X.X.X.X ワイルドカード
    • ポート条件：eq 80（等しい）、neq、lt、gt、range 20 21 など。送信元の後に書けば送信元ポート、宛先の後に書けば宛先ポート

    よく使うポート番号は次のとおりです（ポート番号の基礎は 11_コンピューターサイエンスの「06ポート番号とファイアウォール基礎」のノートも参考になります）。

    サービスプロトコル/ポート
    FTPTCP 20/21
    SSHTCP 22
    TelnetTCP 23
    SMTPTCP 25
    DNSUDP 53（TCP 53 も）
    DHCPUDP 67/68
    TFTPUDP 69
    HTTPTCP 80
    HTTPSTCP 443
    SNMPUDP 161/162
    TACACS+TCP 49
    RADIUSUDP 1812/1813

    4.1 例題：拡張 ACL を書く

    問題：192.168.1.0/24 の PC から、Web サーバ 10.1.1.10 への HTTP 通信だけを許可する拡張 ACL の行を書きます。

    ステップ1: 必要な要素を書き出す
          プロトコル … HTTP は TCP
          送信元     … 192.168.1.0/24 → 192.168.1.0 0.0.0.255
          宛先       … 10.1.1.10 の1台 → host 10.1.1.10（= 10.1.1.10 0.0.0.0）
          宛先ポート … HTTP = 80 → eq 80
          番号       … 拡張なので 100〜199
ステップ2: 「プロトコル 送信元 宛先 eq ポート」の順に並べる
答え: access-list 100 permit tcp 192.168.1.0 0.0.0.255 host 10.1.1.10 eq 80

    次のように書くと意図どおりになりません。

    書き方なぜ合わないか
    ... permit udp ... eq 80HTTP は TCP。UDP を指定すると HTTP 通信に一致しない
    ... permit tcp host 10.1.1.10 192.168.1.0 0.0.0.255 eq 80送信元と宛先が逆。拡張 ACL では送信元を先に書く
    access-list 10 permit tcp ...番号 10 は標準 ACL（1〜99）なので、宛先やポートを指定できない

    4.2 例題：ACL を読み取る

    access-list 101 deny tcp any host 10.1.1.1 eq 23
access-list 101 permit ip any any
    ステップ1: 1行目を「プロトコル 送信元 宛先 ポート」に分解
          deny | tcp | any（送信元：すべて）| host 10.1.1.1（宛先：1台）| eq 23（宛先ポート：Telnet）
          → 「どこからでも、10.1.1.1 宛ての Telnet を拒否」
ステップ2: 2行目
          permit | ip（すべてのIP通信）| any | any → 「残りはすべて許可」
ステップ3: 暗黙の deny any は、2行目ですべて一致するため実質的に使われない
結論: 10.1.1.1 へのTelnetだけを拒否し、それ以外の通信はすべて許可する

    読み間違えやすい点です。

    • 「10.1.1.1 からのすべての通信を拒否」ではありません。10.1.1.1 は宛先で、拒否しているのは Telnet だけです。
    • 「すべての通信を拒否」ではありません。2 行目の permit ip any any で Telnet 以外は許可されます。
    • 「10.1.1.1 への SSH を拒否」ではありません。SSH は TCP 22 で、拒否しているのは 23 番（Telnet）です。

    最後の permit ip any any がないと、暗黙の deny any によってすべての通信が止まってしまう点も合わせて押さえましょう。

    5.ACL の適用場所（標準は宛先の近く、拡張は送信元の近く）

    目的：PC-A から Server-X への通信だけを止め、PC-A から Server-Y への通信は通したいとします。

    • 標準 ACL は送信元しか見ないので、deny host 192.168.1.10 を送信元に近い R1 に置くと、PC-A から Server-Y への必要な通信まで止めてしまいます。→ 宛先に近い R3（Server-X 側のインターフェース）に置くのが基本です。
    • 拡張 ACL は宛先・ポートまで指定できるので、deny ip host 192.168.1.10 host 10.3.3.3 を送信元に近い R1 に置けば、Server-Y への通信は通しつつ、不要な通信を早い段階で止められます。宛先の近くに置くと、最終的に破棄される通信がネットワーク内（R1→R2→R3）を長く流れて帯域を無駄にします。

    拡張 ACL を置く場所として正しいのは「止めたい通信の送信元にできるだけ近い場所」です。

    考え方判定
    送信元にできるだけ近い場所◯（拡張 ACL の推奨）
    宛先にできるだけ近い場所✕（これは標準 ACL の推奨）
    どこに置いても効果は同じ✕（止められる範囲や無駄に流れる通信量が変わる）
    必ずコア層のスイッチ✕（コア層は高速転送に専念させ、細かいフィルタは置かないことが多い）

    覚え方は「拡張は送信元の近く、標準は宛先の近く」です。

    6.インターフェースへの適用：ip access-group

    ACL は作成しただけでは効果がありません。インターフェースに方向を指定して適用する必要があります。

    R1(config)# access-list 100 permit tcp 192.168.1.0 0.0.0.255 host 10.1.1.10 eq 80
R1(config)# interface g0/0
R1(config-if)# ip access-group 100 in       ← 受信方向（インターフェースに入ってくるパケット）

    方向の考え方は「ルータから見て」です。

                 in（ルータに入る）           out（ルータから出る）
  LAN ─────────────────> [g0/0  R1  g0/1] ─────────────────> WAN

    ACL 100 をインターフェースの受信方向に適用するコマンドは ip access-group 100 in（インターフェース設定モード）です。似たコマンドとの違いは次のとおりです。

    コマンド実際の意味
    ip access-group 100 in◯ インターフェースに受信方向で適用
    access-class 100 invty（Telnet/SSH のライン）に ACL を適用して、機器へのリモートログインを制限するコマンド
    ip access-list 100 in存在しないコマンド。ip access-list は名前付き ACL を作成するとき（例：ip access-list extended WEB）
    service-policy input 100QoS（通信の優先制御）のポリシーをインターフェースに適用するコマンド

    ルール：1 つのインターフェースに適用できる ACL は、1 方向・1 プロトコル（IPv4/IPv6）ごとに 1 つまでです（例：g0/0 に IPv4 の in 1 つ、IPv4 の out 1 つ、IPv6 の in 1 つ…）。

    適用状況は show ip interface で確認します。

    R1# show ip interface g0/0
GigabitEthernet0/0 is up, line protocol is up
  Internet address is 192.168.1.1/24
  ...
  Outgoing access list is not set
  Inbound  access list is 100
  ...

    7.名前付き ACL とシーケンス番号

    名前付き ACL は、用途がわかる名前を付けられ、シーケンス番号（各行に付く並び順の番号）で行単位の編集ができます。

    R1(config)# ip access-list extended WEB
R1(config-ext-nacl)# 10 permit tcp any host 10.1.1.10 eq 80
R1(config-ext-nacl)# 20 deny   ip any host 10.1.1.10
R1(config-ext-nacl)# permit ip any any            ← 番号なし → 最後に追加（30）
R1(config-ext-nacl)# exit
R1(config)# interface g0/0
R1(config-if)# ip access-group WEB in

    例題：10 と 20 の間に行を追加します。

    R1(config)# ip access-list extended WEB
R1(config-ext-nacl)# 15 permit tcp any host 10.1.1.10 eq 443
    R1# show access-lists WEB
Extended IP access list WEB
    10 permit tcp any host 10.1.1.10 eq www
    15 permit tcp any host 10.1.1.10 eq 443      ← 番号で指定した位置に挿入された
    20 deny ip any host 10.1.1.10
    30 permit ip any any
    • 各行にはデフォルトで 10、20、30… と 10 ずつ間隔を空けたシーケンス番号が付きます。
    • 間に行を挿入できます（例：15）。
    • no 20 のように番号を指定して1 行だけ削除できます。
    • 番号を付けずに入力した行は ACL の最後に追加されます（自動で 10 と 20 の間には入りません）。
    • 「作り直すしかない」のは、番号付き ACL を昔の方法（グローバル設定の access-list コマンド）で編集する場合の話です。
    • 「順番は関係ない」は誤りです。ACL は上から順に確認されるので順番はとても重要です。
    R1(config)# ip access-list extended WEB
R1(config-ext-nacl)# no 20                        ← 20番の行だけ削除
R1(config-ext-nacl)# exit
R1(config)# ip access-list resequence WEB 10 10    ← 番号を10から10刻みに振り直す

    名前付きの標準 ACL は ip access-list standard 名前 で作ります。

    8.確認とトラブルシューティング

    R1# show access-lists
Standard IP access list 10
    10 deny   192.168.1.5 (3 matches)
    20 permit any (152 matches)
Extended IP access list 101
    10 deny tcp any host 10.1.1.1 eq telnet (15 matches)
    20 permit ip any any (2048 matches)

    各行（ACE）に何個のパケットが一致したかは show access-lists で確認します（各行末の (15 matches)）。

    コマンドわかること
    show access-lists（show ip access-lists）ACL の内容と、各行の一致数
    show ip interfaceどのインターフェースに、どの ACL が、どの方向で適用されているか（一致数は出ない）
    show running-config設定全体（適用コマンドも含む）
    show ip routeルーティングテーブル（ACL とは無関係）
    show ip nat translationsNAT の変換テーブル（ACL とは無関係）

    トラブルシューティングの手順は次のとおりです。

    1. show ip interface で「どこに・どの向きで」適用されているかを見る。
    2. show access-lists で「どの行に一致しているか」（カウンタ）を見る。
    3. 期待した行のカウンタが増えていない場合は、次を疑う：上の行に先に一致している（順番の問題）／適用したインターフェースや方向（in/out）が間違っている／暗黙の deny any で落ちている（どの行のカウンタも増えない）。
    4. clear access-list counters でカウンタをリセットして再テストすると分かりやすい。

    9.vty への ACL 適用：access-class

    機器への SSH/Telnet の接続元を制限するには、ACL を vty ラインに access-class で適用します（vty については 60-6 ネットワーク機器への管理アクセス）。

    R1(config)# access-list 10 permit 192.168.100.0 0.0.0.255    ! 管理用PCのネットワーク
R1(config)# line vty 0 4
R1(config-line)# access-class 10 in
R1(config-line)# transport input ssh
R1(config-line)# login local
                         ┌──────────── R1 ────────────┐
管理用PC 192.168.100.5 ─SSH─> │ vty: access-class 10 in → 許可 → ログイン画面 │
一般PC   192.168.1.20  ─SSH─> │ vty: access-class 10 in → 拒否（接続拒否）     │
                     └─────────────────────────────┘
       ※ R1を「通過」するパケットには影響しない（それは ip access-group の役目）

    vty への接続元を制限するコマンドは access-class 10 in（line vty 0 4 の設定モード）です。

    コマンド適用先・役割
    access-class 10 invty への接続を、ACL で許可した送信元だけに制限
    ip access-group 10 inインターフェースを通過するパケットを制御。line vty モードでは使えない
    transport input sshvty で使える接続方式を SSH だけにする（Telnet 禁止）。接続元の制限はしない
    login localローカルユーザーで認証する。接続元の制限はしない

    覚え方は「インターフェースには ip access-group、vty には access-class」です。3 つ（access-class・transport input ssh・login local）を組み合わせると、機器への管理アクセスを安全に制限できます。

    10.よくある誤解

    • 標準 ACL は送信元だけ。宛先・ポート・プロトコルは拡張 ACL です。
    • ACL の最後は暗黙の deny any（permit any ではない）。deny だけの ACL はすべてを止めます。permit がなくても ACL は無視されません。
    • ACL は最初に一致した行で終了します。最後の一致でも、deny 優先でも、最長一致（ロンゲストマッチ）でもありません。
    • ワイルドカードはサブネットマスクと 0/1 が逆。ブロックサイズ − 1（64 ではなく 63）。0.0.0.0＝host、255.255.255.255＝any。/25 の 0.0.0.127 は /26 には広すぎます。
    • 拡張 ACL は送信元→宛先の順。HTTP は TCP。番号 10 は標準 ACL なのでポート指定はできません。
    • 「host 10.1.1.1」が宛先の位置にあれば「10.1.1.1 への」通信です。23 は Telnet、22 は SSH。
    • 拡張は送信元の近く、標準は宛先の近く。コア層に必ず置くわけではありません。
    • インターフェースは ip access-group、vty は access-class。ip access-list 100 in は存在しません。service-policy は QoS です。
    • 1 インターフェースに、1 方向・1 プロトコルごとに 1 つの ACL。
    • 名前付き ACL で番号なしの行は末尾に追加されます。順番は重要です。
    • 一致数は show access-lists、適用場所と方向は show ip interface で見ます。

    11.まとめ

    • 標準（1〜99）＝送信元のみ・宛先の近く／拡張（100〜199）＝詳細条件・送信元の近く。
    • 評価順序：上から順・最初の一致で終了・最後は暗黙の deny any。具体的な行を上に。
    • ワイルドカード＝255.255.255.255 − サブネットマスク（最後のオクテットはブロックサイズ − 1）。
    • 拡張 ACL 書式：access-list 番号 動作 プロトコル 送信元 WC 宛先 WC eq ポート。
    • 適用：ip access-group 番号 in|out（インターフェース）、access-class 番号 in（vty）。
    • 名前付き ACL はシーケンス番号で挿入（15 ...）・削除（no 20）が可能。
    • 確認：show access-lists（matches）と show ip interface（適用状況）。

    12.理解度チェック

    Q1. 標準 ACL で条件にできるのは何ですか？

    送信元 IP アドレスだけです。宛先 IP・ポート番号・プロトコルを条件にするには拡張 ACL（100〜199）を使います。

    Q2. access-list 10 deny host 192.168.1.5 だけを適用すると、192.168.1.20 からの通信はどうなりますか？

    拒否されます。1 行目には一致しませんが、最後の暗黙の deny any に一致するためです。他を通したいなら access-list 10 permit any を追加します。

    Q3. 1 行目が permit any、2 行目が deny host 192.168.1.5 の ACL では、192.168.1.5 は止まりますか？

    止まりません。ACL は上から順に調べて最初に一致した行で終わるので、すべてが 1 行目の permit any に一致し、2 行目は一度も使われません。具体的な行を上に書きます。

    Q4. 192.168.1.64/26 を指定するワイルドカードマスクは何ですか？

    0.0.0.63 です。/26 のマスクは 255.255.255.192 なので 255 − 192 = 63（ブロックサイズ 64 − 1）になります。

    Q5. 拡張 ACL を送信元の近くに置くのはなぜですか？

    宛先やポートまで指定できるので、必要な通信を巻き込まずに不要な通信だけを早い段階で止められ、捨てられる通信がネットワーク内を流れて帯域を無駄にしないためです。標準 ACL は送信元しか見ないので、巻き込みを避けるため宛先の近くに置きます。

    Q6. 機器への SSH 接続を管理用ネットワークからだけに制限するには、どのコマンドを使いますか？

    line vty で access-class 10 in を使います（ACL 10 で管理用ネットワークを permit）。ip access-group はインターフェースを通過するパケット用です。

    Q7. 名前付き ACL で、10 と 20 の間に行を入れるにはどうしますか？

    ip access-list extended 名前 に入り、15 permit ... のようにシーケンス番号を付けて入力します。番号を付けないと末尾に追加されます。

    Q8. ACL のどの行に何回一致したかを見るコマンドは何ですか？

    show access-lists です。どのインターフェースにどの方向で適用されているかは show ip interface で確認します。
