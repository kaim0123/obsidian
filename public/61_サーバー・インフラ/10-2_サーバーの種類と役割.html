    10 サーバーの基礎

    サーバーの種類と役割

    Web / AP / DB / キャッシュ / メール / DNS / ファイル / プロキシ / ジョブ（ワーカー）サーバーが、それぞれどんな 係 なのかを整理します。定番の 3 層アーキテクチャ（Web - AP - DB） となぜ層に分けるのか、1 台に同居させる構成と役割ごとに分ける構成の比較、そして Shop の構成が「1 台 → 分離 → 冗長化」と育っていく道筋まで解説します。前提として 10-1 サーバーとは何か を読んでいると理解しやすいです。

    もとにしたノート：10_サーバーの基礎/02_サーバーの種類と役割

    ひとことで言うと

    「〇〇サーバー」は そのソフトウェアが担う役割 の名前で、お店の「係」のようなものです。最初は 1 台に全部の係を同居させ、負荷や信頼性の要求が上がったら 係ごとに別マシンへ分けます。分ける「切れ目」は役割の境界なので、最初から役割を意識しておくことが大事です。

    1.サーバーの種類は「お店の係」

    小さな個人店では店主が 1 人で受付も調理も在庫管理もこなしますが、繁盛してくると受付係・料理人・倉庫番と分業します。サーバーも同じです。

    • 「〇〇サーバー」は そのソフトウェアが担う役割 の名前です（Web サーバー＝Nginx が担う係、など）
    • 最初は 1 台に全部の係を同居させ、負荷や信頼性の要求が上がったら 係ごとに別マシンへ分けます
    • 分ける「切れ目」は役割の境界です。だから最初から役割を意識しておくことが大事です

    2.主なサーバーの種類

    2.1 一覧

    種類役割代表的なソフト / サービス主なポート
    Web サーバーHTTP(S) を受ける玄関。静的ファイル配信、HTTPS 終端、AP への転送Nginx、Apache、Caddy80, 443
    AP サーバー（アプリケーションサーバー）ビジネスロジックを実行し動的な結果を作るNode.js、Gunicorn/Uvicorn（Python）、Tomcat（Java）、PHP-FPM3000, 8000, 8080 など
    DB サーバー（データベースサーバー）データを永続化し、検索・更新・トランザクションを担うPostgreSQL、MySQL、Amazon RDS5432, 3306
    キャッシュサーバーよく使うデータをメモリに置いて高速に返す。セッション保存にも使うRedis、Memcached、Valkey6379, 11211
    メールサーバーメールの送信（SMTP）・受信（IMAP/POP3）Postfix、Amazon SES、SendGrid25, 587, 993
    DNS サーバードメイン名を IP アドレスに変換するBIND、Route 53、Cloudflare DNS53
    ファイルサーバー / ストレージファイルの保存・共有NFS、Samba(SMB)、Amazon S32049, 445
    プロキシサーバー通信を仲介する。外向き（フォワード）と内向き（リバース）があるNginx、HAProxy、Squid80, 443, 3128
    ジョブ（ワーカー）サーバー時間のかかる処理を裏で非同期に実行BullMQ、Celery、Sidekiq、cron（待ち受けない）

    2.2 Web サーバー・AP サーバー・DB サーバー

    Web サーバー は「何でも受け付ける玄関」です。重い処理は自分でせず、画像や CSS のような ファイルをそのまま返す仕事 と、残りを AP サーバーへ 取り次ぐ仕事 に徹します。Nginx が軽量で大量の同時接続に強いのはこのためです。詳しくは 20-1 Webサーバーとは・20-2 Nginx入門。

    AP サーバー は「注文を受けて料理を作る」係です。在庫を確認し、価格を計算し、注文を DB に書き込みます。Shop API（Node.js、ポート 3000）がこれにあたります。詳しくは 30-1 アプリケーションサーバーとは。

    DB サーバー は「倉庫番」です。データを失わないこと（永続化）と、同時に注文が来ても在庫数が狂わないこと（トランザクション：複数の処理をひとまとまりで確実に行う仕組み）が使命です。一番「壊れたら困る」サーバーなので、バックアップや冗長化の優先度が最も高くなります。詳しくは 30-6 データベースサーバーの運用。

    2.3 キャッシュ・メール・DNS・ファイルサーバー

    キャッシュサーバー は「よく出る料理を作り置きしておくカウンター」です。DB に毎回聞くと遅い商品一覧やランキングをメモリに置いておき、ミリ秒以下で返します。データは消えても良い（DB から作り直せる）前提で使うのが基本です。

    メールサーバー は自前運用がとても難しい部類です。迷惑メール判定を避けるための SPF/DKIM/DMARC（送信元が正しいことを証明する仕組み）の設定、IP の評判管理などが必要なため、Shop のような EC サイトでは注文確認メールの送信に Amazon SES や SendGrid などの送信サービスを使う のが一般的です（クラウドでは 25 番ポートの外向き通信が既定で制限されていることも多いです）。

    DNS サーバー は「電話帳」です。自分で BIND を立てることは減り、Route 53 や Cloudflare、レジストラ（ドメインの登録業者）付属の DNS を使うのが一般的です（→ 10-5 ネットワークの基本）。

    ファイルサーバー は社内のファイル共有（SMB/NFS）が古典的な用途ですが、Web サービスでは 商品画像やユーザーのアップロードファイルを S3 のようなオブジェクトストレージに置く のが定番です。サーバーのローカルディスクに置くと、サーバーを 2 台にしたとき片方にしかファイルがない、という問題が起きるからです。

    2.4 プロキシサーバー：フォワードとリバース

    プロキシサーバー（代理で通信するサーバー）には 2 種類あります。

    Web サービスで主に使うのは リバースプロキシ です。Shop では Nginx が Web サーバー兼リバースプロキシとして働きます（→ 20-3 リバースプロキシ）。

    2.5 ジョブ（ワーカー）サーバー

    ジョブ（ワーカー）サーバー は「裏方」です。注文確定メールの送信、画像のサムネイル生成、売上集計など、ユーザーを待たせたくない処理を キュー（queue）（処理待ちの行列）に積み、別プロセスが順番に処理します。HTTP を待ち受けないのでポートは開けません。

    1. ユーザーが注文し、Shop API が注文を DB に保存する
    2. Shop API は「メール送って」をキュー（Redis）に積み、すぐに 201 を返す
    3. ワーカーがキューから取り出し、SES でメールを送信する（数秒かかっても OK）

    3.3 層アーキテクチャ（Web - AP - DB）

    Web システムの最も基本的な形が 3 層アーキテクチャ（3-tier architecture） です。

    層別名担当特徴
    Web 層プレゼンテーション層受付・HTTPS・静的ファイル状態を持たないので増やしやすい
    AP 層アプリケーション層、ビジネスロジック層処理・計算状態を DB に預ければ増やしやすい
    DB 層データ層保存・整合性状態を持つので増やしにくい

    3.1 なぜ層に分けるのか

    1. 役割ごとに得意なソフトを使える：大量接続は Nginx、計算は Node.js、整合性は PostgreSQL
    2. セキュリティの壁を作れる：インターネットから直接触れるのは Web 層だけ。DB は内側に隠す
    3. 層ごとに増やせる：アクセスが増えたら AP 層だけ台数を増やす、といった調整ができる（→ 50-1 スケーリングの基本）
    4. 障害の影響範囲を絞れる：どの層の問題かを切り分けやすい

    3 層はマイクロサービスの「前段階」

    サービスごとに API と DB を分ける マイクロサービス も、1 つ 1 つのサービスの中身はたいてい 3 層です。まずは 3 層を確実に理解するのが近道です。設計論は 41 層化・三層・レイヤード、41 モノリスとマイクロサービス や、34_Backend・68_分散システムの体系ノートを参照してください。

    4.同居構成と分離構成の比較

    3 層は「論理的な」分け方です。物理的に 1 台に全部載せる（同居） か 層ごとに別マシンにする（分離） かは別の判断です。

    観点1 台に同居層ごとに分離
    コスト安い（月数千円から）台数分かかる。マネージド DB はさらに割高
    構築・運用の手間少ない。1 台に SSH すれば全部見られる台数分の更新・監視・ネットワーク設定が必要
    通信localhost で速い・安全ネットワーク越しになり、遅延と通信制御（ファイアウォール）が必要
    リソースの奪い合いDB の重いクエリで API も遅くなる互いに影響しない
    障害の影響1 台死ぬと全部止まる（単一障害点）層ごとに冗長化できる
    スケール1 台を大きくする（スケールアップ）しかない必要な層だけ台数を増やせる
    向いている段階開発初期・検証・小規模サイト本番でユーザーが増えてきた段階

    結論

    最初は同居で始めてよいです。ただし「API が DB に localhost 決め打ちで接続している」「アップロード画像をローカルディスクに保存している」のような 同居を前提にした作り にしないことが重要です。接続先は環境変数で切り替えられるようにしておけば（→ 30-5 設定と環境変数・シークレット）、分離は設定変更だけで済みます。

    5.Shop の構成の成長

    Shop がどう育っていくかを先に見ておきましょう。このシリーズ全体の地図です。

    1. ステージ 1：1 台に同居：Ubuntu 1 台に Nginx ＋ Shop API ＋ PostgreSQL
    2. ステージ 2：DB を分離：Nginx ＋ Shop API のサーバーから、別サーバーまたは RDS の PostgreSQL へ接続する。きっかけは「DB が重くなった」「バックアップを楽にしたい」
    3. ステージ 3：冗長化：ロードバランサーの後ろに Nginx ＋ API #1 と #2 を並べ、両方が DB プライマリと Redis につながる。DB プライマリはスタンバイへレプリケーション（複製）する。きっかけは「1 台止まると全停止が怖い」「アクセスが増えた」
    ステージきっかけやること詳しい章
    1. 1 台まず公開したいUbuntu に Nginx・Node.js・PostgreSQL を入れる10-4 Linuxサーバーの基本、20-2 Nginx入門、30-2 Node.jsアプリを本番で動かす
    2. DB 分離DB と API がリソースを奪い合う、バックアップを確実にしたいDB を別サーバーまたはマネージド RDS へ。API からの接続先を変える30-6 データベースサーバーの運用
    3. 冗長化1 台止まると売上ゼロ、セール時のアクセス増API を 2 台以上にしてロードバランサーの後ろへ。セッションは Redis、画像は S3 へ50-2 ロードバランサーの仕組み、50-5 高可用性と冗長化
    4. 自動化台数が増えて手作業がつらい構築を Terraform / Ansible でコード化40-2 IaCとは

    ステージ 3 で API を 2 台にしたとき、「ログイン状態が API #1 のメモリにしかない」「画像が API #1 のディスクにしかない」と困ります。だから 状態（セッション・ファイル）は AP サーバーの外に置く のが鉄則です。これを守った AP サーバーを ステートレス と呼び、台数を自由に増減できるようになります。

    6.よくある誤解・つまずき

    ✕ よくある誤解◯ 実際は
    Web サーバーと AP サーバーは別の機械でなければならない「〇〇サーバー」は役割の名前。1 台に同居しても、それぞれ Web サーバー・AP サーバーと呼ぶ
    Node.js は自分で HTTP を受けられるから Nginx は不要受けることはできるが、HTTPS 終端・静的ファイル配信・遅いクライアントの吸収・複数台への振り分けは Nginx の方が得意で安全。本番では前に置くのが定番（→ 20-3 リバースプロキシ）
    最初から分離構成・マイクロサービスにした方がプロっぽい小さいうちは同居の方が安く、障害点も少ない。分けるのは「分けないと困る」理由が出てから
    キャッシュサーバーにデータを入れておけば安心キャッシュは消えても困らないデータ用。正しいデータの置き場所（正本）は DB
    注文確認メールのために自前でメールサーバーを立てる迷惑メール判定対策が難しいため、送信サービス（SES など）を使うのが現実的

    7.補足：三層アーキテクチャの基本構造

    3 章の 3 層アーキテクチャを、各層の技術スタック・実装例・メリット/デメリット・実装パターンの観点から掘り下げます。

    三層アーキテクチャ（Three-Tier Architecture） とは、Web アプリケーションを 3 つの論理的な層に分けて構築する設計パターンです。プレゼンテーション層、アプリケーション層、データ層の 3 層で構成され、それぞれが独立した役割を持ち、システムの保守性、拡張性、再利用性を向上させます。

    ┌─────────────────────┐
│  プレゼンテーション層  │ ← ユーザーインターフェース
├─────────────────────┤
│   アプリケーション層   │ ← ビジネスロジック
├─────────────────────┤
│      データ層        │ ← データベース
└─────────────────────┘
    層役割機能技術例
    1. プレゼンテーション層（Presentation Layer）ユーザーとのインターフェース画面表示、ユーザー入力の受付HTML、CSS、JavaScript、フロントエンドフレームワークWeb ブラウザ、モバイルアプリ、デスクトップアプリ
    2. アプリケーション層（Application Layer）ビジネスロジックの実装データ処理、業務ルールの実装サーバーサイド言語、フレームワークWeb サーバー、アプリケーションサーバー
    3. データ層（Data Layer）データの保存・管理データの永続化、検索、更新データベース、ファイルシステムMySQL、PostgreSQL、MongoDB

    「層」の切り方の違いに注意

    この補足の 3 層は「画面（ブラウザ側）・処理・データ」というソフトウェアの分け方で、ブラウザで動く画面をプレゼンテーション層に数えています。3 章の表は「サーバーの層」の分け方で、Nginx をプレゼンテーション層（Web 層）と呼んでいます。どちらも「表示・処理・データを分ける」考え方は同じです。

    8.補足：各層の詳細と実装例

    8.1 プレゼンテーション層

    役割と責任

    • ユーザーインターフェース：画面の表示と操作
    • 入力検証：クライアントサイドでの入力チェック
    • 表示制御：データの表示形式の制御
    • ユーザー体験：操作性の向上

    技術スタック

    • HTML：ページの構造
    • CSS：デザインとレイアウト
    • JavaScript：動的な動作
    • フレームワーク：React、Vue.js、Angular
    • UI ライブラリ：Bootstrap、Material-UI

    実装例（API からユーザー一覧を取ってきて表示する）：

    <!-- HTML -->
<div id="user-list">
  <h2>ユーザー一覧</h2>
  <ul id="users"></ul>
</div>

<script>
  // JavaScript
  fetch("/api/users")
    .then((response) => response.json())
    .then((users) => {
      const userList = document.getElementById("users");
      users.forEach((user) => {
        const li = document.createElement("li");
        li.textContent = user.name;
        userList.appendChild(li);
      });
    });
</script>

    8.2 アプリケーション層

    役割と責任

    • ビジネスロジック：業務ルールの実装
    • データ処理：データの変換・加工
    • 認証・認可：ユーザーの権限管理
    • API 提供：プレゼンテーション層へのデータ提供

    技術スタック

    • サーバーサイド言語：Java、Python、PHP、Node.js
    • フレームワーク：Spring、Django、Laravel、Express
    • Web サーバー：Apache、Nginx
    • アプリケーションサーバー：Tomcat、IIS

    実装例（Python の Flask でユーザーの一覧取得・作成 API を作る）：

    # Python (Flask)
from flask import Flask, jsonify, request
from flask_sqlalchemy import SQLAlchemy

app = Flask(__name__)
app.config['SQLALCHEMY_DATABASE_URI'] = 'mysql://user:pass@localhost/db'
db = SQLAlchemy(app)

class User(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(80), nullable=False)
    email = db.Column(db.String(120), unique=True, nullable=False)

@app.route('/api/users', methods=['GET'])
def get_users():
    users = User.query.all()
    return jsonify([{'id': u.id, 'name': u.name, 'email': u.email} for u in users])

@app.route('/api/users', methods=['POST'])
def create_user():
    data = request.get_json()
    user = User(name=data['name'], email=data['email'])
    db.session.add(user)
    db.session.commit()
    return jsonify({'id': user.id, 'name': user.name, 'email': user.email})

    接続先の書き方に注意

    この例は説明のため DB の接続先（localhost）とパスワードをコードに直接書いています。実際には 4 章の結論のとおり、接続先や認証情報は環境変数から読み込むようにします（→ 30-5 設定と環境変数・シークレット）。

    8.3 データ層

    役割と責任

    • データ永続化：データの保存
    • データ整合性：データの一貫性保証
    • 高速検索：インデックスによる高速化
    • バックアップ：データの保護

    技術スタック

    • リレーショナルデータベース：MySQL、PostgreSQL、Oracle
    • NoSQL データベース：MongoDB、Redis、Cassandra
    • ファイルシステム：ローカルストレージ、クラウドストレージ
    • データベース管理：正規化、インデックス設計

    実装例（テーブル作成・インデックス・登録・検索）：

    -- SQL
CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(80) NOT NULL,
    email VARCHAR(120) UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_users_email ON users(email);

INSERT INTO users (name, email) VALUES ('John Doe', 'john@example.com');
SELECT * FROM users WHERE email = 'john@example.com';

    9.補足：三層アーキテクチャのメリット・デメリット

    9.1 メリット

    1. 保守性

    • 責任分離：各層の役割が明確
    • 独立した変更：一層の変更が他層に影響しない
    • デバッグ：問題の特定が容易
    • テスト：各層の独立したテスト

    2. 拡張性

    • 水平スケーリング：各層の独立したスケーリング
    • 負荷分散：層ごとの負荷分散
    • 新機能追加：既存層への影響を最小化
    • 技術選択：各層で最適な技術を選択

    3. 再利用性

    • コンポーネント化：各層の独立した再利用
    • API 化：アプリケーション層の API 化
    • ライブラリ化：共通機能のライブラリ化
    • テンプレート化：設計パターンの再利用

    4. セキュリティ

    • 層間の分離：セキュリティ境界の明確化
    • アクセス制御：層ごとのアクセス制御
    • データ保護：データ層の保護
    • 監査：各層の独立した監査

    9.2 デメリット

    1. 複雑性

    • 設計の複雑さ：層間の依存関係の管理
    • 実装の複雑さ：各層の実装と連携
    • デバッグの複雑さ：層間の問題の特定
    • テストの複雑さ：統合テストの必要性

    2. パフォーマンス

    • 層間通信：ネットワーク通信のオーバーヘッド
    • データ変換：層間でのデータ変換コスト
    • レイテンシ：複数層を経由する遅延
    • リソース使用：各層のリソース使用量

    3. 運用コスト

    • インフラ：各層のインフラ管理
    • 監視：各層の独立した監視
    • デプロイ：各層の独立したデプロイ
    • バックアップ：各層の独立したバックアップ

    三層アーキテクチャは、Web アプリケーションの設計において重要なパターンです。プレゼンテーション層、アプリケーション層、データ層の 3 層に分けることで、システムの保守性、拡張性、再利用性を向上させることができます。適切な設計と実装により、効率的で安全な Web アプリケーションを構築することができます。また、現代の技術発展により、三層アーキテクチャも進化し続けており、クラウドネイティブやマイクロサービスなどの新しいアプローチと組み合わせて活用されています。

    11.まとめ

    • 「〇〇サーバー」はソフトウェアが担う 役割 の名前。Web / AP / DB を中心に、キャッシュ・メール・DNS・ファイル・プロキシ・ワーカーがある
    • 基本形は 3 層アーキテクチャ（Web - AP - DB）。外に出すのは Web 層だけで、DB は内側に隠す
    • 最初は 1 台に同居で始めてよいが、接続先やファイル保存先を差し替え可能にしておく
    • Shop は 1 台 → DB 分離 → 冗長化 → コード化 と育っていく
    • 台数を増やすには、セッションやファイルなどの 状態を AP サーバーの外に出す

    12.理解度チェック

    Q1. 3 層アーキテクチャで、台数を増やすのが最も難しいのはどの層ですか？理由も答えてください。

    DB 層 です。データという「状態」を持っており、複数台に分けると「どれが正しいデータか」の整合性を保つ必要があるからです。Web 層・AP 層は状態を持たないように作れば、同じものを並べるだけで増やせます。

    Q2. Shop で「注文後の確認メール送信が遅く、注文ボタンを押してから画面が返るまで 5 秒かかる」という問題が出ました。どの種類のサーバーを使って解決しますか？

    ジョブ（ワーカー）サーバー です。API は注文を DB に保存したら「メール送信」をキューに積んですぐ応答し、ワーカーが裏でメールを送ります。ユーザーはメール送信を待たなくて済みます。

    Q3. Shop の API を 2 台に増やしたら、「ログインしたのに次の画面でログアウト状態になる」ことがありました。原因と対策は？

    セッション情報を各 API サーバーのメモリに保存しているため、リクエストが別の台に振り分けられるとセッションが見つからないのが原因です。セッションを Redis などの共有キャッシュサーバー（または DB）に置き、API サーバーをステートレスにします。

    Q4. フォワードプロキシとリバースプロキシの違いは？Shop の Nginx はどちらですか？

    フォワードプロキシは社内の利用者の代わりに外のサイトへアクセスする「利用者側の代理」、リバースプロキシは外のユーザーからの通信をサーバーの代わりに受けて内側の AP サーバーへ振り分ける「サーバー側の代理」です。Shop の Nginx は リバースプロキシ です。

    Q5. 商品画像を AP サーバーのローカルディスクに保存する設計は、何が問題になりますか？

    AP サーバーを 2 台にしたとき、画像がアップロードを受けた片方にしかなく、もう片方に振り分けられると表示できません。S3 のようなオブジェクトストレージに置き、AP サーバーをステートレスに保ちます。

    Q6. キャッシュサーバー（Redis など）に入れるデータは、どんな前提で扱うべきですか？

    消えても困らない（DB から作り直せる）データとして扱います。正しいデータの置き場所（正本）は DB で、キャッシュは高速化のための「作り置き」です。

    Q7. 小規模な段階で 1 台に同居させるとき、後で分離しやすくするために気を付けることは？

    DB の接続先を localhost 決め打ちにせず環境変数で切り替えられるようにすること、アップロードファイルをローカルディスクに置かないことなど、同居を前提にした作りにしないことです。そうすれば分離は設定変更だけで済みます。
