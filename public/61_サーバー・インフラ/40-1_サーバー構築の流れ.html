    40 構築・IaC

    サーバー構築の流れ

    これまでに学んだ部品（SSH・ファイアウォール・Nginx・Node.js・systemd・DNS・HTTPS など）を、ネットショップ「Shop」のサーバー 1 台に 手作業で組み立てる順番 にまとめます。各ステップの作業と 確かめるコマンド を対にして示したうえで、手順書を書いても残る手作業の限界（スノーフレークサーバー・構成ドリフト）、ペットと家畜、イミュータブルインフラ を説明し、なぜ IaC（Infrastructure as Code）が必要になるのかを見ていきます。

    もとにしたノート：40_構築・IaC/01_サーバー構築の流れ

    ひとことで言うと

    サーバー構築は 「安全を固める → 動かす → 公開する → 見守る」 の順で進め、各ステップに 確認方法 をセットにします。1 台なら手作業でも作れますが、2 台目・作り直し・半年後の変更 で手作業は破綻します。これが IaC へ進む理由です。

    1.サーバー構築を例えると

    サーバー構築は 「引っ越し先の部屋を、住める状態にする作業」 に似ています。

    引っ越しサーバー構築
    部屋を借りるサーバー調達
    鍵を替えるユーザー／SSH の設定
    戸締まりファイアウォール
    家具を入れるNginx・ランタイム・アプリ
    表札を出すDNS
    防犯カメラと保険監視・バックアップ

    順番を間違えると、たとえば「鍵を替える前に荷物を運び込んで、その間に空き巣に入られる」ようなことが起きます。

    • 構築は 「安全を固める → 動かす → 公開する → 見守る」 の順で進める
    • 各ステップには 「できたことを確かめる方法」 がセットで必要
    • 1 台なら手作業でも作れるが、2 台目・作り直し・半年後の変更 で手作業は破綻する。これが IaC へ進む理由

    このページは 10-4 Linuxサーバーの基本、20-2 Nginx入門、30-4 プロセス管理とsystemd を読んでいると理解しやすくなります。

    2.Shop を 1 台構築する全体地図

    これまでの章で学んだ部品を、実際に組み立てる順番に並べると次のようになります。

    DNS と HTTPS の順番

    Let's Encrypt の HTTP-01 チャレンジ（証明書を出す前の本人確認）は「そのドメインが本当にこのサーバーを指しているか」を確認するため、DNS を先に向けておく必要があります。図では DNS → HTTPS の順にしています。

    #ステップ主な作業詳しくは
    1サーバー調達Ubuntu Server 24.04 LTS のインスタンス作成、固定 IP 割当10-3 仮想化とクラウド
    2OS 初期設定apt upgrade、タイムゾーン、ホスト名、自動更新10-4 Linuxサーバーの基本
    3ユーザー/SSH作業ユーザー作成、公開鍵認証、パスワード・root ログイン禁止60-2 SSHの安全な運用
    4ファイアウォールufw で 22/80/443 だけ許可60-3 ファイアウォールとネットワーク制御
    5Nginxインストール、proxy_pass で 3000 番へ20-3 リバースプロキシ
    6ランタイムNode.js LTS、PostgreSQL30-2 Node.jsアプリを本番で動かす、30-6 データベースサーバーの運用
    7アプリ配置専用ユーザー shop、ビルド、.env30-5 設定と環境変数・シークレット
    8systemdunit ファイル、enable --now30-4 プロセス管理とsystemd
    9DNSshop.example.com → サーバーの IP10-5 ネットワークの基本
    10HTTPScertbot で証明書取得・自動更新20-4 HTTPSとTLS証明書
    11監視・バックアップ死活監視、ログ、DB の定期バックアップ66_可観測性の「サーバー監視とログ管理の基本」、69_SRE・インシデント対応の「DR訓練とRTO・RPO」のノート

    3.各ステップの作業と確認方法

    ここでは「何を打つか」と「どう確かめるか」を対にして示します。細かい設定の意味は各ページに任せ、流れをつかむ ことを優先します。

    3.1 OS 初期設定（ステップ 2）

    sudo apt update && sudo apt upgrade -y
sudo timedatectl set-timezone Asia/Tokyo
sudo hostnamectl set-hostname shop-web-01
sudo apt install -y unattended-upgrades   # セキュリティ更新の自動適用

    確認：

    timedatectl            # Time zone: Asia/Tokyo になっているか
hostnamectl            # Static hostname を確認
cat /etc/os-release    # Ubuntu 24.04 であること

    ロケールは英語のままが無難

    サーバーの ロケール（表示言語や書式の設定）を ja_JP.UTF-8 にすると、エラーメッセージが日本語になって検索しにくくなります。ログやエラーは C.UTF-8 / en_US.UTF-8 のまま、タイムゾーンだけ合わせるのが実務では一般的です。

    3.2 ユーザーと SSH（ステップ 3）

    # 作業用ユーザーを作り sudo を与える
sudo adduser deploy
sudo usermod -aG sudo deploy

# 手元 PC から公開鍵を登録（手元で実行）
ssh-copy-id deploy@<サーバーIP>

# 鍵でログインできるのを確かめてから、パスワードと root ログインを禁止
sudo tee /etc/ssh/sshd_config.d/10-hardening.conf <<'EOF'
PermitRootLogin no
PasswordAuthentication no
EOF
sudo sshd -t && sudo systemctl reload ssh

    確認：今の SSH セッションを閉じずに、別ターミナルで ssh deploy@<IP> が通ることを確認します。設定ミスで締め出されても、開いているセッションから戻せます。

    Ubuntu 24.04 のサービス名

    Ubuntu では SSH サーバーの unit 名は ssh（sshd ではない）です。また 24.04 は ssh.socket による ソケット起動（接続が来たときに起動する方式）が既定なので、ポート番号を変える場合は socket 側の設定も関係します。詳しくは 60-2 SSHの安全な運用 を見てください。

    3.3 ファイアウォール（ステップ 4）

    sudo ufw allow OpenSSH        # 先に SSH を許可しないと締め出される
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable

    確認：sudo ufw status verbose で 22/80/443 だけが ALLOW になっていること。クラウドでは セキュリティグループ（クラウド側のファイアウォール）も同じ方針 にそろえます。3000 番（Node.js）や 5432 番（PostgreSQL）は 外に開けません。

    3.4 Nginx・ランタイム・アプリ・systemd（ステップ 5〜8）

    sudo apt install -y nginx postgresql
# Node.js LTS は NodeSource などのリポジトリから（2026 年時点の LTS は 24 系）
curl -fsSL https://deb.nodesource.com/setup_24.x | sudo -E bash -
sudo apt install -y nodejs

# アプリ専用ユーザー（ログイン不可）と配置先
sudo useradd --system --home /opt/shop --shell /usr/sbin/nologin shop
sudo mkdir -p /opt/shop && sudo chown shop:shop /opt/shop
# ここで git clone / ビルド成果物の転送、npm ci --omit=dev、.env の配置
sudo systemctl enable --now shop.service   # unit ファイルは前章参照

    確認は 内側から外側へ 順に行うのがコツです。どこで止まっているかがすぐ分かります。

    systemctl status shop          # active (running) か
curl -i http://127.0.0.1:3000/health   # アプリ単体が応答するか
sudo nginx -t                  # Nginx 設定の文法
curl -i http://127.0.0.1/health        # Nginx 経由で届くか
ss -tlnp                       # 3000 番が 127.0.0.1 だけで待ち受けているか

    unit ファイルの書き方は 30-4 プロセス管理とsystemd で扱っています。

    3.5 DNS・HTTPS（ステップ 9〜10）

    dig +short shop.example.com        # サーバーの IP が返るか（手元で確認）
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d shop.example.com -d api.shop.example.com
sudo certbot renew --dry-run       # 自動更新が通るか

    確認：curl -I https://shop.example.com で 200 系、ブラウザで鍵マーク、systemctl list-timers | grep certbot で更新タイマーがあること。

    3.6 監視・バックアップ（ステップ 11）

    最低限、次の 3 つがないサーバーは「本番」と呼べません。

    外形監視

    外部から https://shop.example.com/health を定期的に叩き、落ちたら通知します（UptimeRobot、CloudWatch Synthetics など）。

    ログ

    journalctl -u shop、Nginx のアクセスログを見られる・保管される状態にします（66_可観測性の「ログ集約基盤」のノート）。

    バックアップ

    pg_dump を毎日取り、別の場所（S3 など）に保存します。そして リストアを実際に試します（30-6 データベースサーバーの運用）。

    4.手順書（ランブック）にする

    ここまでの作業を、次の人（＝半年後の自分）が再現できるように書き残したものが 手順書（Runbook、ランブック） です。良い手順書は次の形をしています。

    ## 手順 3: SSH のハードニング
目的: パスワード総当たり攻撃を防ぐ
前提: deploy ユーザーで鍵ログインできること
作業:
  1. /etc/ssh/sshd_config.d/10-hardening.conf を作成（内容は下記）
  2. sudo sshd -t で文法チェック
  3. sudo systemctl reload ssh
確認: 別端末から ssh deploy@<IP> が通る / ssh root@<IP> が拒否される
戻し方: 上記ファイルを削除して reload

    目的・前提・作業・確認・戻し方 の 5 点がそろっていると、他人が実行しても事故になりにくくなります（書き方の詳細は 69_SRE・インシデント対応の「ランブックの書き方」のノート）。

    …ところが、手順書をどれだけ丁寧に書いても、次の問題は残ります。

    5.手作業構築の限界

    5.1 スノーフレークサーバー

    スノーフレーク（Snowflake、雪の結晶）サーバー とは、「同じものが二つとない」サーバーのことです。手作業で作ると、

    • 手順書の 12 行目を飛ばした、apt upgrade のタイミングが違ってパッケージのバージョンがずれた
    • 障害対応で nginx.conf を直接直したが、手順書に反映し忘れた

    といった小さな違いが積み重なり、「本番 1 号機だけで再現するバグ」「誰も作り直し方を知らないサーバー」が生まれます。

    5.2 構成ドリフト

    構成ドリフト（Configuration Drift） は、「あるべき姿（手順書・設計書）」と「実際のサーバーの状態」が時間とともにずれていく現象です。

    構築直後            3 か月後                  1 年後
手順書 = 実機   →  手順書 ≒ 実機          →  手順書 ≠ 実機
                   (緊急パッチ・手動修正)     (誰も全体を知らない)

    ドリフトが進むと、2 台目を作ろうとしても 1 号機と同じものが作れません。ロードバランサーの後ろに API を 2 台並べる（50-1 スケーリングの基本）段階で、これは致命的になります。

    5.3 再現できない・速くない・レビューできない

    問題具体例
    再現性がない障害でサーバーが壊れた。作り直すのに手順書を見ながら 1 日かかり、しかも前と同じか分からない
    遅いAPI を 2 台 → 10 台にしたい。10 回手で打つ？
    レビューできない「ufw のルールを変えた」が口頭とチャットでしか残らず、誰がいつなぜ変えたか追えない
    人に依存する構築できるのは A さんだけ。A さんが休むと誰も触れない

    6.ペットと家畜、イミュータブルインフラ

    6.1 Pets vs Cattle

    クラウド時代のサーバー観を表す有名な例えが ペットと家畜（Pets vs Cattle） です。

    ペット（Pets）家畜（Cattle）
    名前shop-main のように愛称を付けるweb-0a1b2c のように番号
    病気になったら手当てして治す（SSH して直す）群れから外して新しい個体に入れ替える
    作り方一台ずつ手作業同じ型から自動で量産
    例手作業の 1 号機オートスケーリングの EC2、コンテナ

    手作業構築のサーバーは必然的にペットになります。「壊れても同じものをすぐ作れる」家畜にするには、作り方そのものをコード化 する必要があります。

    全部を家畜にする必要はない

    DB サーバーのように状態（データ）を持つものは、簡単には「捨てて作り直す」ことができません。データはマネージド DB やバックアップで守り、状態を持たない Web/API サーバーから家畜化する のが現実的な順番です。

    6.2 イミュータブルインフラ

    イミュータブルインフラ（Immutable Infrastructure、不変のインフラ） は家畜の考え方を徹底したもので、一度作ったサーバーには変更を加えない というルールです。

    変更したいときは、新しいイメージ（AMI＝AWS のサーバーの雛形、やコンテナイメージ）を作り、新しいサーバーを立てて 古いものと入れ替え ます。ドリフトは原理的に起きず、問題があれば古いイメージに戻すだけです。入れ替え方は 65_リリース・デプロイの「Blue-Greenデプロイ」「ローリングアップデート」のノートで扱います。コンテナ（53_コンテナの「Dockerとは」のノート）はこの考え方を最も手軽に実現する手段です。

    7.そこで IaC へ

    ここまでの問題はすべて「サーバーの作り方が 人の手と頭の中 にある」ことが原因です。これを コード（テキストファイル） にしてしまうのが IaC（Infrastructure as Code） です。

    手作業の問題IaC での解決
    スノーフレーク同じコードからは同じサーバーができる
    ドリフトコードと実機の差分を検出し、コードの状態に戻せる
    再現できないapply 一発で作り直せる
    レビューできないGit でプルリクエスト・履歴・差分が残る

    この章の残りでは、次の順で学びます。

    1. 40-2 IaCとは — 考え方とツールの全体像
    2. 40-3 Terraform入門 — EC2 やセキュリティグループなど「箱」を作る
    3. 40-4 構成管理とAnsible — 箱の中（Nginx・Node・systemd）を整える
    4. 40-5 CloudFormationとCDK — AWS 純正の IaC

    このページの手順 1（調達）と 4（クラウド側 FW）・9（DNS）は Terraform、手順 2〜8 と 10 は Ansible、という対応を覚えておくと後のページが読みやすくなります。

    8.よくある誤解・つまずき

    よくある誤解

    • ✕ 手順書を丁寧に書けば手作業でも再現できる
      ◯ 手順書は「実行されなかった変更」や「手順書に書かれなかった修正」を検出できません。ドリフトを防ぐには、手順そのものを実行可能なコードにする必要があります。
    • ✕ ファイアウォールを有効にしてから SSH を許可すればよい
      ◯ ufw enable の時点で SSH が許可されていないと、その場で締め出されます。必ず ufw allow OpenSSH が先です。クラウドならコンソールから復旧できることもありますが、VPS では詰むこともあります。
    • ✕ 動作確認はブラウザで https を開けば十分
      ◯ 失敗したときに原因が分かりません。systemctl status → curl 127.0.0.1:3000 → curl 127.0.0.1 → curl https://... と内側から順に確かめるのが近道です。
    • ✕ イミュータブルインフラなら SSH は一切不要
      ◯ 調査のためにログインすることはあります。「ログインして 変更しない」がルールです。最近は SSH 自体を閉じ、AWS Systems Manager Session Manager などで調査する構成も増えています。

    9.まとめ

    • 構築は「調達 → OS → SSH → FW → Nginx → ランタイム → アプリ → systemd → DNS → HTTPS → 監視・バックアップ」の順
    • 各ステップに確認コマンドを対にし、確認は内側から外側へ
    • 手順書は「目的・前提・作業・確認・戻し方」で書く
    • 手作業はスノーフレークと構成ドリフトを生み、2 台目・作り直しで破綻する
    • サーバーはペットではなく家畜として扱い、変更は「入れ替え」で行うのがイミュータブルインフラ
    • その実現手段が IaC

    10.理解度チェック

    Q1. Let's Encrypt で証明書を取得する前に、DNS の設定を済ませておく必要があるのはなぜですか。

    HTTP-01 チャレンジでは、Let's Encrypt がそのドメイン名で HTTP アクセスしてきて、サーバーが所定の応答を返せるかを確認します。ドメインがまだこのサーバーの IP を指していないと検証に失敗するためです。

    Q2. 「構成ドリフト」とは何で、なぜスケールアウトのときに問題になりますか。

    あるべき構成（手順書・コード）と実機の状態が、手動修正などによって時間とともにずれていく現象です。ずれた 1 号機と同じものを 2 台目として作れないため、台数を増やしたときに「特定のサーバーだけ挙動が違う」問題が起きます。

    Q3. イミュータブルインフラで、Nginx の設定を変えたいときはどうしますか。

    稼働中のサーバーを直接編集せず、設定を変更した新しいイメージ（またはコンテナイメージ）を作り、新しいサーバーを立てて古いサーバーと入れ替えます。

    Q4. ufw を有効にするとき、ufw enable より先に必ず実行すべきコマンドは何ですか。

    sudo ufw allow OpenSSH です。SSH を許可しないまま有効にすると、その場で SSH が切れて締め出されます。

    Q5. 動作確認を「内側から外側へ」行うとは、具体的にどんな順番ですか。

    systemctl status shop（プロセス）→ curl 127.0.0.1:3000（アプリ単体）→ nginx -t と curl 127.0.0.1（Nginx 経由）→ curl https://...（外から）の順です。どこで止まっているかがすぐ分かります。

    Q6. 良い手順書（ランブック）にそろえるべき 5 つの項目は何ですか。

    目的・前提・作業・確認・戻し方です。これがそろうと他人が実行しても事故になりにくくなります。ただし手順書では、書かれなかった修正（ドリフト）を検出できません。

    Q7. DB サーバーを最初から「家畜」として扱いにくいのはなぜですか。

    データという状態を持っていて、捨てて作り直すとデータが失われるからです。データはマネージド DB やバックアップで守り、状態を持たない Web/API サーバーから家畜化するのが現実的です。
