    10 サーバーの基礎

    サーバーとは何か

    「サーバー」は特別な機械の名前ではなく、サービスを提供する役割 の名前です。このページでは、クライアント/サーバーモデルとリクエスト・レスポンスの流れ、サーバー用ハードウェアと普通の PC の違い、物理サーバー / VPS / クラウド VM / コンテナ / サーバーレス という「サーバーの形」、Lambda・ECS・Cloud Run の得意・不得意、そしてブラウザで URL を開いてから画面が出るまでの全体の流れを解説します。前提は、Web アプリを手元（localhost）で動かしたことがあれば十分です。

    もとにしたノート：10_サーバーの基礎/01_サーバーとは何か、30_アプリ実行環境/Cloud Runが強すぎる理由【LambdaとECSの良いとこどり】（りょうま@インフラ攻略）

    ひとことで言うと

    サーバーは 「頼まれたら応える係」 です。機械の種類ではなく役割の名前なので、ノート PC でも npm run dev すればその瞬間サーバーになります。ただし本番のサーバーには 「24 時間止まらない」「大勢を同時にさばく」「壊れてもデータを失わない」 ことが求められ、そのために専用のハードウェアや運用の工夫があります。

    1.サーバーは「頼まれたら応える係」

    レストランで例えると、お客さん（クライアント）が注文（リクエスト）を出し、厨房（サーバー）が料理（レスポンス）を返します。厨房は「料理を作る専用の建物」である必要はなく、注文を受けて応える役割を担っていればサーバー です。

    • サーバー（server）＝「serve（仕える・提供する）するもの」。役割の名前 であって機械の種類ではありません
    • あなたのノート PC でも npm run dev すれば、その瞬間それは「サーバー」です
    • ただし本番のサーバーには「24 時間止まらない」「大勢を同時にさばく」「壊れてもデータを失わない」ことが求められます。だから専用のハードウェアや運用の工夫が必要になります

    2.クライアント/サーバーモデル

    2.1 役割の分担

    クライアント/サーバーモデル（client-server model） は、「お願いする側」と「応える側」を分ける考え方です。

    クライアント（client）サーバー（server）
    例ブラウザ、スマホアプリ、curlNginx、Shop API（Node.js）、PostgreSQL
    動き方必要なときに 自分から 接続する常に起動して 接続を待ち受ける（listen）
    数多数（数千〜数百万）少数（1 台〜数十台）
    寿命ユーザーが閉じたら終わり基本的に止まらない

    ポイントは「サーバーは待つ側」だということです。サーバーは ポート（port）（通信の窓口番号）を開けて待ち続け、そこにクライアントが接続してきます。ポートは 10-5 ネットワークの基本 で詳しく扱います。

    2.2 リクエストとレスポンス

    Web の世界では、クライアントとサーバーは HTTP（HyperText Transfer Protocol） という決まりごとで会話します。

    クライアント → サーバー（リクエスト）
  GET /api/products/42 HTTP/1.1
  Host: shop.example.com
  Accept: application/json

サーバー → クライアント（レスポンス）
  HTTP/1.1 200 OK
  Content-Type: application/json

  {"id":42,"name":"マグカップ","price":1200}
    • リクエスト（request）：「何を（パス）」「どうしたいか（メソッド：GET/POST など）」を伝えます
    • レスポンス（response）：「結果どうだったか（ステータスコード：200/404/500 など）」と中身を返します
    • 1 往復で完結するのが基本です。サーバーは前回の会話を覚えていない（ステートレス）ので、ログイン状態などは Cookie やトークンで毎回伝えます（→ 74 HTTPとセッション管理、74 Cookieの仕組み）

    サーバー同士もクライアント/サーバー

    Shop API が PostgreSQL にクエリを投げるとき、Shop API は「DB のクライアント」です。1 つのプログラムが、ブラウザに対してはサーバー、DB に対してはクライアント、という二役を担うのはごく普通のことです。

    3.サーバーの中身と、PC との違い

    3.1 中身は PC と同じ 4 つの部品

    サーバーも中身はコンピューターです。主な部品は PC と同じです。

    部品役割例え足りないと起きること
    CPU計算・処理をする料理人リクエスト処理が遅くなる、応答待ちの行列ができる
    メモリ（RAM）作業中のデータを置く短期記憶調理台スワップ（ディスクで代用）が起きて激遅になる、OOM（Out Of Memory：メモリ切れ）でプロセスが強制終了
    ストレージ（SSD/HDD）電源を切っても消えない長期記憶冷蔵庫・倉庫ディスクフルでログや DB が書けなくなり停止
    NIC（Network Interface Card）ネットワークにつなぐ口店の出入口帯域不足で通信が詰まる

    実務でサーバーの性能を語るときは「vCPU 2 / メモリ 4GB / SSD 80GB / 帯域 〇Gbps」のようにこの 4 つで表します。それぞれの詳しい仕様は 10 章の補足 で扱います。

    3.2 サーバー用ハードウェアならではの工夫

    本番用の物理サーバーは「止まらない・壊れてもすぐ直せる」ために、PC にはない工夫がされています。

    工夫内容なぜ必要か
    常時稼働前提の設計24 時間 365 日動かす前提の部品・冷却PC は「使うときだけ」動かす前提
    冗長電源（redundant PSU）電源ユニットを 2 つ載せ、片方が壊れても動き続ける電源は壊れやすい部品の代表
    ECC メモリ（Error-Correcting Code）メモリのビット化けを検出・訂正する長時間・大量データでは宇宙線などによるビット反転が無視できない。DB の値が化けたら大事故
    RAID複数ディスクに分散・複製して 1 本壊れても大丈夫にするディスクも消耗品
    ホットスワップ電源を入れたままディスク・電源を交換できる交換のために止めなくて済む
    ラックマウント19 インチラックに薄い板状（1U ≒ 4.45cm）で積むデータセンターに高密度に並べ、配線・冷却を効率化
    リモート管理（BMC/IPMI）OS が固まっていても別回線で電源操作・画面確認データセンターまで行かずに復旧できる

    クラウドを使うならハードは意識しなくていい？

    クラウドや VPS では、こうしたハードウェアの面倒は事業者が見てくれます。ただし「物理サーバーは壊れる」という事実は変わりません。クラウドの VM も、裏の物理マシンが壊れれば止まります。だから後の章で 冗長化（50-5 高可用性と冗長化）を学びます。

    4.サーバーの「形」：物理・VPS・クラウド VM・コンテナ・サーバーレス

    「サーバーを用意する」といっても、今は色々な形があります。下に行くほど 自分で管理する範囲が狭く、手軽になりますが、自由度は下がります。

    形ざっくり言うと自分で管理するもの例
    物理サーバー（ベアメタル）本物の機械を 1 台まるごとハード・OS・アプリ全部自社データセンター、さくらの専用サーバ
    VPS（Virtual Private Server）物理サーバーを仮想的に分けた 1 区画を月額で借りるOS・アプリさくらの VPS、ConoHa VPS、DigitalOcean、Amazon Lightsail
    クラウド VMVPS に近いが、API で秒単位に作成・削除・増減できるOS・アプリAmazon EC2、Compute Engine、Azure Virtual Machines
    コンテナOS の上で、アプリと依存物を箱詰めして動かすアプリ＋コンテナイメージDocker、Kubernetes、Amazon ECS
    サーバーレス（FaaS）関数を置くだけ。呼ばれたときだけ動くコード（関数）だけAWS Lambda、Cloud Run functions、Azure Functions

    自分で管理する範囲を層ごとに並べると、次のようになります（■＝自分で管理、□＝事業者が管理、△＝サービス次第）。

    形ハード仮想化OSランタイムアプリ
    物理■■■■■
    VPS/VM□□■■■
    コンテナ□□△（ホスト OS はサービス次第）■■
    サーバーレス□□□□■

    「サーバーレス」でもサーバーが無いわけではなく、サーバーの存在を意識しなくていい という意味です。仕組みと選び方は 10-3 仮想化とクラウド で、コンテナは 53_コンテナの「Dockerとは」のノートで詳しく扱います。設計の観点からのサーバーレスは 41 サーバーレス も参考になります。

    このシリーズでは、仕組みを理解しやすい Ubuntu の VPS / EC2 1 台 からスタートします。一番「サーバーらしい」形で基礎を押さえておくと、コンテナやサーバーレスに進んだときも「裏で何が起きているか」が分かるからです。

    5.発展：Lambda・ECS・Cloud Run の得意・不得意

    サーバーレスやコンテナの具体的なサービスとして、AWS の Lambda（サーバーレス関数）と ECS（コンテナ実行サービス）、Google Cloud の Cloud Run（コンテナをサーバーレスのように動かすサービス）を比べてみます。技術選定では、サービスの得意・不得意をざっくり頭に入れておくと「こういうときは Cloud Run」「こういうときは ECS」とすぐ判断できます。ここはりょうま@インフラ攻略さんの動画「Cloud Runが強すぎる理由【LambdaとECSの良いとこどり】」の内容です。

    動画の結論

    AWS で安く API を動かそうとすると、実質 Lambda（安いが制限が多い）か ECS（安定しているが高い） の二択になり、そのトレードオフに悩み続けることになります。Google Cloud の Cloud Run は「ゼロスケールできるのに ECS 並みのパワーがある」ため、両方の良いところを取れます。新規サービスを立ち上げるなら真っ先に検討したいほどおすすめ、という話です。

    5.1 Lambda の強み

    • ゼロスケール：イベント（リクエスト）があったときだけ起動し、終われば停止します。0 台から 1 台へ増やせることを「ゼロスケール」と呼びます。イベント駆動アーキテクチャ（何かが起きたときだけ処理が動く作り）を実現でき、ワークロード（処理量）の少ないサービスなら非常に安く運用できます。
      • 事例：Lambda ＋ API Gateway ＋ EFS（Lambda にマウントできるファイルシステム。その上で SQLite を動かして DB 代わりにする）で、月額約 200 円の社内システムを作ったそうです。RDS（AWS のマネージド DB）だと月 5〜6 千円かかります。リクエストがあったときしかお金がかからないので、ほぼ無料で運用できます
    • スケーラビリティが優秀：リージョンあたりアカウント全体で同時実行数 1000 まで（申請で引き上げ可）。1 回の処理が 200ms なら 1 つの実行枠を 1 秒に約 5 回使えるので、1000 × 5 で秒間約 5000 リクエスト、100ms なら秒間約 1 万リクエストをさばけます
    • スケールアウト（台数を増やすこと）も速く、リクエスト量に応じて 10 秒ごとに最大 1000 個の実行環境 を階段状に自動で追加します。よほどのスパイク（急な負荷増）でない限り対応でき、テレビ局の数万同時接続規模の配信システム（API Gateway ＋ Lambda）にも使われています。社内システムに閉じず、大規模サービスにも耐えるスケーラビリティです

    5.2 Lambda の弱み

    ハードクォータ（申請しても緩和できない上限）が多いのが辛いところです。

    上限値実務での影響
    タイムアウト15 分前段に API Gateway を置くのが一般的で、そちらの上限（REST API か HTTP API かで多少違う）により実質 約 29〜30 秒 以内に返す必要がある
    リクエスト／レスポンスボディ6MB特にきつい。大きめの JSON や CSV アップロードですぐ超える。CSV ファイルがだんだん大きくなって ECS へ移行した実体験が語られている
    ファイルディスクリプタ（同時に開けるファイルなどの数）1024 個—
    デプロイパッケージ（解凍後）250MB—
    • Durable Functions で「最大 1 年実行」と発表されましたが、Step Functions のようにマルチステップで実行して合計 1 年という意味で、1 回の実行のタイムアウト 15 分は変わらないそうです
    • コールドスタート：久しぶりにリクエストが来ると、コンテナの初期化から始めるため 3〜5 秒の遅延が出ます（昔は 10 秒ほどあった）。SSR（サーバーサイドレンダリング）を Lambda で行ったら、最初にブラウザを開いたユーザーは体感 10 秒待たされたこともあったそうです
    • Provisioned Concurrency で常に温めておけばコールドスタートは解消できますが、常時課金になりゼロスケールのメリットが消えます（それなら ECS でよい、となる）。社内システムなど多少の待ちを許容できるなら Lambda で問題ありません

    5.3 ECS の強みと弱み

    • ECS は基本的に Lambda の逆です。パワーがあり安定 していますが、ゼロスケールできず常時起動なので コストは高め（最小スペックでも月 5000〜7000 円程度）
    • タイムアウト・ファイル数・コールドスタートといった制約がなく、「迷ったら多少コストを払っても ECS にしておけ」と言えるほど安定しています
    • 他の選択肢として、App Runner はゼロスケールできず ECS より少し安い程度で、新規受付も停止しています。EKS（AWS の Kubernetes）はさらに高くなります。結局「Lambda か ECS か」のトレードオフを考え続けるのが今の AWS の実態だ、と動画は述べています

    5.4 Cloud Run が強すぎる理由

    項目LambdaCloud Run
    ゼロスケール可可（最小インスタンス数を 0 にすれば、普段は落としておいて 1 円も払わない）
    パワー弱め最大 8 vCPU / 32GB メモリ
    リクエスト／レスポンス上限6MB32MB（ストリーミングならそれ以上）。Lambda の約 5 倍
    タイムアウト15 分（API Gateway 経由で約 30 秒）最大 60 分

    例えるなら「Fargate（ECS のサーバー管理不要な実行環境）のコンテナを Lambda っぽく使える」のが Cloud Run です。

    5.5 実務で Cloud Run に救われた事例

    • 要件：リモートデスクトップを立て、その中で Playwright（ブラウザ自動操作ツール）を使ってスクレイピング的な操作をし、WebSocket（つなぎっぱなしで双方向に通信する仕組み）でユーザーの画面からインタラクティブに操作できるようにする。ユーザーに一時的に認証・ログインしてもらい、認証情報を一時保存する機能
    • Lambda が厳しかった理由：15 分タイムアウト。さらにリクエストが終わると停止する性質で、常駐する WebSocket サーバーと相性が悪い（API Gateway の WebSocket はあるが、リモートデスクトップのような常駐接続の維持には不向き）
    • ECS が厳しかった理由：たまにしか使わない機能のためにタスクを常駐させるとコストが高い。リクエストのときだけ単発でタスクを起動すると約 1 分かかり、ユーザーを 30 秒〜1 分待たせるのは許容できない
    • Cloud Run なら：使うときだけ起動するので安く、起動は 10〜20 秒程度。起動時の CPU ブースト（コールドスタートのときだけ一時的に CPU を増やす）でさらに改善でき、タイムアウト 60 分、WebSocket も使えたため要件を満たせました

    5.6 この比較から分かること

    • サービスの得意・不得意をざっくり頭に入れておくと、技術選定ですぐ判断できます
    • Lambda＝安くてスケールに強いが、ハードクォータとコールドスタートがある。ECS＝安定・高パワーだが常時コストがかかる
    • Cloud Run はゼロスケールとパワーを両立し、社内ツールやコミュニティ内だけで使うようなワークロードの少ないサービス、初期フェーズの選択肢として非常に有力です。EC2・ECS・Lambda・Kubernetes に加えて Cloud Run という手札を持っておくと、Cloud Run でしかできない要件に出会ったときに強い、と動画はまとめています

    数値は動画時点のもの

    上限値・料金・提供状況（App Runner の新規受付停止など）は動画（2026 年 10 月公開）時点の内容です。クラウドの制限は改定されるので、選定するときは各サービスの公式ドキュメントで最新値を確かめてください。

    6.Shop が 1 台で動く全体図

    このシリーズの題材である EC サイト「Shop」は、最初は 1 台のサーバーで動かします。

    • Nginx：玄関係。HTTPS の暗号を解き、画像などの静的ファイルは自分で返し、API へのリクエストは Shop API に渡します（→ 20-3 リバースプロキシ）
    • Shop API：店員。注文や商品検索などの処理（ビジネスロジック）を行います（→ 30-1 アプリケーションサーバーとは）
    • PostgreSQL：倉庫番。商品・注文・会員データを保存します（→ 30-6 データベースサーバーの運用）

    1 台に全部載っていても、役割は 3 つに分かれている ことが大事です。この役割分担が、後で台数を増やすときの「切れ目」になります（→ 10-2 サーバーの種類と役割）。

    7.URL を開いてから表示されるまで

    ブラウザで https://shop.example.com/products/42 を開いたとき、裏では次のことが起きています。

    1. 名前解決（DNS）：shop.example.com という名前を 203.0.113.10 のような IP アドレスに変換します（→ 10-5 ネットワークの基本）
    2. TCP 接続：その IP の 443 番ポートに接続します
    3. TLS ハンドシェイク：証明書でサーバーが本物か確認し、暗号化の鍵を決めます（→ 20-4 HTTPSとTLS証明書）
    4. HTTP リクエスト：GET /products/42 を送ります
    5. サーバー内の処理：Nginx → Shop API → PostgreSQL と順に処理が流れ、結果が戻ってきます
    6. HTTP レスポンス：HTML や JSON が返ります
    7. 追加のリクエスト：HTML に書かれた CSS・JS・画像を、ブラウザがさらに取りに行きます
    8. 描画：ブラウザが画面を組み立てて表示します

    「サイトが遅い」「繋がらない」というトラブルは、この どの段階で詰まっているか を切り分けるのが基本です。DNS が引けないのか、ポートが開いていないのか、API が遅いのか、DB が遅いのか。この流れを頭に入れておくと、後の章の内容がすべてこの地図のどこかに収まります。

    8.よくある誤解・つまずき

    ✕ よくある誤解◯ 実際は
    サーバーは特別な高い機械のことサーバーは「役割」。ノート PC でも Raspberry Pi でもサーバーになれる。本番用は「止まらない工夫」がされているだけ
    サーバーレスならサーバーは存在しないサーバーはある。管理を事業者に任せられるので「意識しなくていい」という意味
    1 台のサーバーにはアプリが 1 つだけ動いているShop の例のように、1 台の中で Nginx・API・DB など複数の「サーバーソフト」が同時に動くのが普通
    localhost で動いたら本番でも同じように動く本番では DNS・ファイアウォール・HTTPS・プロセスの常駐化など、手元にはなかった層が加わる。このシリーズはその層を一つずつ学ぶためのもの
    クラウドなら壊れない裏は物理サーバーなので壊れる。壊れても困らない構成（冗長化・バックアップ）は利用者側の仕事

    9.補足：サーバーの基本概念・種類・設置場所

    サーバーの役割、代表的なサーバーの種類、通信プロトコル、設置場所（オンプレミス / クラウド）を一覧できる形で整理します。

    9.1 概要と基本概念

    サーバー（Server）とは、ネットワーク上で他のコンピュータ（クライアント）からの要求に応じて、サービスやリソースを提供するコンピュータのことです。

    クライアント・サーバーシステム

    • クライアント：サービスを要求する側のコンピュータ
    • サーバー：サービスを提供する側のコンピュータ
    • 例：Web ブラウザ（クライアント）が Web サーバーに Web ページを要求

    サーバーの役割

    1. リソースの共有：ファイル、プリンター、データベースなどを複数のクライアントで共有
    2. サービスの提供：Web ページ、メール、ファイル転送などのサービスを提供
    3. 集中管理：ユーザー認証、セキュリティ、バックアップなどを一元管理

    9.2 サーバーの種類

    種類役割代表例用途
    1. Web サーバーWeb ページや Web アプリケーションを提供Apache、Nginx、IIS企業サイト、EC サイト、ブログなど
    2. データベースサーバーデータの保存・管理・検索を提供MySQL、PostgreSQL、Oracle Database顧客情報管理、在庫管理、ログ管理など
    3. メールサーバー電子メールの送受信を管理Postfix、Sendmail、Exchange Server企業内メール、顧客対応メールなど
    4. ファイルサーバーファイルの保存・共有を提供Samba、NFS、Windows File Server社内文書共有、バックアップ保存など
    5. DNS サーバードメイン名と IP アドレスの変換を提供BIND、PowerDNSインターネット上の名前解決

    それぞれの役割と構成の育て方は 10-2 サーバーの種類と役割 で詳しく扱います。

    9.3 サーバーの特徴

    ハードウェア面

    • 高性能：大量の処理を安定して実行
    • 高信頼性：24 時間 365 日の稼働を前提
    • 拡張性：必要に応じてリソースを追加可能

    ソフトウェア面

    • マルチユーザー対応：複数のユーザーが同時に利用可能
    • セキュリティ：不正アクセスやデータ漏洩を防ぐ機能
    • ログ管理：アクセス履歴やエラー情報を記録

    9.4 サーバーとクライアントの通信

    通信プロトコル（通信の決まりごと）

    • HTTP/HTTPS：Web ページの送受信
    • SMTP/POP3/IMAP：メールの送受信
    • FTP/SFTP：ファイルの転送
    • SSH：セキュアなリモート接続

    通信の流れ

    1. クライアントがサーバーに要求を送信
    2. サーバーが要求を処理
    3. サーバーが結果をクライアントに返送
    4. クライアントが結果を表示・利用

    9.5 サーバーの設置場所

    オンプレミス（自社設置）

    • メリット：完全な制御、カスタマイズ性
    • デメリット：初期費用、保守コスト、専門知識が必要

    クラウド（外部サービス）

    • メリット：初期費用削減、スケーラビリティ、保守不要
    • デメリット：月額費用、インターネット接続必須

    詳しい比較は 10-3 仮想化とクラウド で扱います。

    サーバーは現代の IT システムの中核となる重要なコンポーネントです。Web サイトの表示、メールの送受信、データの保存など、私たちが日常的に利用している多くのサービスがサーバーによって提供されています。サーバーの理解は、IT システム全体を理解するための基礎となります。

    10.補足：ハードウェアリソース（CPU・メモリ・ストレージ・NIC）

    3 章の「4 つの部品」それぞれについて、仕様・種類・性能指標・最適化・仮想化環境での割り当てまで掘り下げます。サーバーのハードウェアリソースは、システムの性能と機能を決定する重要な要素です。主要なリソースには、CPU（中央処理装置）、メモリ（主記憶装置）、ストレージ（補助記憶装置）、NIC（ネットワークインターフェースカード）があります。

    10.1 CPU（Central Processing Unit：中央処理装置）

    CPU の役割

    • 命令の実行：プログラムの命令を順次実行
    • 計算処理：数値計算、論理演算の実行
    • 制御：他のハードウェアの制御・管理

    CPU の主要仕様

    • コア数：同時に処理できる命令の数（シングルコア：1 つの処理／マルチコア：複数の処理を並列実行）
    • クロック周波数：処理速度（GHz）
    • キャッシュメモリ：高速アクセス用の一時記憶領域
    • アーキテクチャ：x86、ARM、RISC-V など

    サーバー向け CPU の特徴

    • 高信頼性：24 時間 365 日の稼働に対応
    • 高性能：大量の処理を安定して実行
    • 拡張性：複数 CPU の搭載が可能
    • 仮想化対応：仮想マシンの効率的な実行

    CPU 性能指標

    • IPC（Instructions Per Cycle）：1 クロックあたりの命令実行数
    • スループット：単位時間あたりの処理量
    • レイテンシ：処理開始から完了までの時間

    10.2 メモリ（Memory：主記憶装置）

    メモリの役割

    • プログラムの実行：実行中のプログラムを格納
    • データの一時保存：処理中のデータを高速アクセス
    • OS の動作：オペレーティングシステムの動作領域

    メモリの種類

    • DRAM（Dynamic RAM）：主記憶として使用。DDR4、DDR5 が最新の規格。ECC（Error Correcting Code）はエラー訂正機能
    • SRAM（Static RAM）：キャッシュメモリとして使用
    • NVRAM（Non-Volatile RAM）：電源断でもデータ保持

    メモリの仕様

    • 容量：GB、TB 単位で表現
    • 転送速度：メモリバスの速度
    • レイテンシ：アクセス時間
    • ECC 機能：エラー検出・訂正機能

    メモリ管理

    • 仮想メモリ：物理メモリより大きな論理メモリ空間
    • ページング：メモリの効率的な利用
    • スワッピング：ストレージとのデータ交換

    10.3 ストレージ（Storage：補助記憶装置）

    ストレージの役割は、データの永続保存（電源断でもデータを保持）、プログラムの保存（アプリケーションの格納）、バックアップ（データの複製保存）です。

    種類特徴メリットデメリット用途
    HDD（Hard Disk Drive）磁気ディスクによる記録大容量、低コストアクセス速度が遅い、物理的衝撃に弱い大容量データ保存、バックアップ
    SSD（Solid State Drive）フラッシュメモリによる記録高速アクセス、低消費電力、衝撃に強い高コスト、書き込み回数制限OS、アプリケーション、データベース
    NVMe SSDPCIe 接続による高速 SSD極めて高速なアクセス—高性能サーバー、データベース

    ストレージの接続方式

    • SATA：シリアル ATA 接続
    • SAS：シリアル SCSI 接続
    • PCIe：PCI Express 接続
    • NVMe：高速 SSD 用プロトコル

    ストレージ管理

    • RAID：複数ディスクによる冗長化
    • LVM：論理ボリューム管理
    • ファイルシステム：データの整理・管理

    10.4 NIC（Network Interface Card：ネットワークインターフェースカード）

    NIC の役割

    • ネットワーク接続：サーバーとネットワークの接続
    • データの送受信：ネットワーク経由でのデータ転送
    • プロトコル処理：ネットワークプロトコルの実装

    NIC の種類

    • 有線 NIC：イーサネット接続（10/100/1000BASE-T：ギガビットイーサネット、10GBASE-T：10 ギガビットイーサネット）
    • 無線 NIC：Wi-Fi 接続
    • 光ファイバー NIC：高速・長距離通信

    NIC の仕様

    • 転送速度：Mbps、Gbps 単位
    • ポート数：複数ポートによる冗長化
    • オフロード機能：CPU 負荷軽減機能
    • 仮想化対応：SR-IOV、VMDq

    ネットワーク性能

    • スループット：単位時間あたりの転送量
    • レイテンシ：データ送信から受信までの時間
    • パケット損失率：転送エラーの発生率

    10.5 ハードウェアリソースの最適化

    性能チューニング

    • CPU：コア数、クロック周波数の最適化
    • メモリ：容量、速度のバランス調整
    • ストレージ：SSD 化、RAID 構成の最適化
    • ネットワーク：帯域幅、レイテンシの改善

    監視・管理

    • リソース使用率：CPU、メモリ、ストレージ、ネットワークの使用状況
    • 性能指標：レスポンス時間、スループット
    • アラート：閾値超過時の通知
    • ログ分析：パフォーマンスの傾向分析

    スケーリング

    • 垂直スケーリング：既存サーバーの性能向上
    • 水平スケーリング：サーバー台数の増加
    • オートスケーリング：負荷に応じた自動調整

    詳しくは 50-1 スケーリングの基本。

    10.6 仮想化環境でのリソース管理

    リソース割り当て

    • CPU：vCPU（仮想 CPU）の割り当て
    • メモリ：仮想メモリの割り当て
    • ストレージ：仮想ディスクの割り当て
    • ネットワーク：仮想 NIC の割り当て

    リソース共有

    • オーバーコミット：物理リソースより多くの仮想リソースを割り当て
    • 動的割り当て：負荷に応じたリソースの再配分
    • リソースプール：複数仮想マシンでのリソース共有

    ハードウェアリソースは、サーバーの性能と機能を決定する重要な要素です。CPU、メモリ、ストレージ、NIC それぞれが異なる役割を持ち、相互に連携してシステム全体の性能を実現しています。適切なリソースの選択と最適化により、効率的で信頼性の高いサーバーシステムを構築することができます。また、仮想化技術の普及により、リソースの柔軟な管理と効率的な利用が可能になっています（→ 10-3 仮想化とクラウド）。

    11.まとめ

    • サーバーは「リクエストを待ち受けてレスポンスを返す」役割 の名前
    • 中身は CPU・メモリ・ストレージ・NIC。本番用ハードは冗長電源・ECC・RAID・ラックなどで「止まらない」ようにできている
    • サーバーの形は物理 → VPS → クラウド VM → コンテナ → サーバーレスと、管理範囲がだんだん狭くなる
    • Lambda は安くてスケールに強いがハードクォータとコールドスタートがあり、ECS は安定・高パワーだが常時コストがかかる。Cloud Run はゼロスケールとパワーを両立する
    • Shop は最初、1 台の Ubuntu サーバーに Nginx・Shop API・PostgreSQL を載せて動かす
    • URL を開くと DNS → TCP → TLS → HTTP → サーバー内処理 → 描画の順に進む。トラブル時はどこで詰まったかを切り分ける

    12.理解度チェック

    Q1. Shop API が PostgreSQL にデータを問い合わせるとき、Shop API はクライアントとサーバーのどちらですか？

    クライアント です。ブラウザに対してはサーバーですが、DB に対しては「お願いする側」なのでクライアントになります。クライアント/サーバーは機械ではなく役割で決まります。

    Q2. 本番用サーバーで ECC メモリが使われる理由を説明してください。

    長時間・大量のデータを扱うと、メモリ上のビットが偶発的に反転する確率が無視できなくなるからです。ECC はそれを検出・訂正し、DB の値が気づかないうちに化けるといった事故を防ぎます。

    Q3. 「サイトが表示されない」と言われました。URL を開いてから表示までの流れのうち、最初に確認すべき段階は何ですか？

    最初は DNS（名前解決） です。名前が正しい IP に解決されていなければ、その後の段階には一切進めません。次に TCP 接続（ポートが開いているか）、TLS、HTTP 応答…と順に切り分けます。

    Q4. 「サーバーレスなのでサーバーは存在しない」という説明はどこが誤りですか？

    サーバーレスでも裏にはサーバーがあります。OS やハードの管理を事業者に任せられるので、利用者がサーバーの存在を「意識しなくていい」という意味です。

    Q5. 物理サーバー・VPS・コンテナ・サーバーレスのうち、OS の管理が自分の仕事にならないのはどれですか？

    サーバーレス です。物理サーバーは全部、VPS／クラウド VM は OS から上が自分の管理です。コンテナはホスト OS の扱いがサービス次第で、サーバーレスでは自分が管理するのはコード（関数）だけになります。

    Q6. Lambda ＋ API Gateway で作った API で、ユーザーの CSV アップロードが大きくなって失敗するようになりました。何が原因と考えられ、どんな選択肢がありますか？

    Lambda のリクエスト／レスポンスボディの上限 6MB（緩和できないハードクォータ）に当たっていると考えられます。動画の事例では ECS へ移行しました。上限 32MB で、ゼロスケールもできる Cloud Run も候補になります。

    Q7. Lambda の Provisioned Concurrency でコールドスタートを消すと、どんなデメリットがありますか？

    常に温めておくため常時課金になり、「リクエストがあったときだけお金がかかる」というゼロスケールのメリットが消えます。それなら最初から ECS でよい、ということになりがちです。

    Q8. Shop を 1 台のサーバーで動かすとき、インターネットに開けるポートと内側専用のポートはそれぞれ何番ですか？

    外に開けるのは 22（SSH）・80・443 だけです。Shop API の 3000 と PostgreSQL の 5432 は localhost からだけ使う内側専用です。Nginx が玄関になり、内側に取り次ぎます。
