    20 Webサーバー・リバースプロキシ

    Webサーバーとは

    ブラウザでページを開くと、裏では Webサーバー が HTTP リクエストを受け取り、レスポンスを返しています。このページでは、1 回のやり取りの流れ、静的ファイル配信と動的処理 の分担、本番の Web サーバーが担う 6 つの役割、プロセス／スレッド／イベント駆動という処理モデルと C10K 問題、Nginx・Apache・Caddy などの製品の違い、curl -v での観察方法を解説します。最後に、静的コンテンツと動的コンテンツの種類・技術・使い分けを補足として掘り下げます。

    もとにしたノート：20_Webサーバー・リバースプロキシ/01_Webサーバーとは

    ひとことで言うと

    Web サーバーは 「お店の受付カウンター」 です。棚にある商品（HTML・画像などのファイル）はその場で手渡し、料理が必要な注文（ログインや注文処理）は厨房（アプリケーション）に回して、できあがったものを返します。暗号の解読・振り分け・来客記録といった雑務も受付が引き受けるので、厨房は料理に集中できます。

    1.Web サーバーの正体

    お客さん（ブラウザ）が「このページください」と注文（HTTP リクエスト）すると、受付（Web サーバー）は次のように動きます。

    • Web サーバー ＝ HTTP（HyperText Transfer Protocol）を話すソフトウェア です。物理マシンのことではありません
    • ファイルを返すだけなら Web サーバー単体で完結します（静的配信）
    • 本番では「アプリの前に立つ受付」として使うのが主流です（リバースプロキシ。20-3 リバースプロキシ）

    このページは 10-5 ネットワークの基本（IP・ポート・DNS）を読んでいると理解しやすくなります。

    2.HTTP リクエストとレスポンスの仕組み

    2.1 1 回のやり取りの流れ

    ブラウザで https://shop.example.com/index.html を開いたとき、裏では次のことが起きています。

    1. DNS で名前を IP アドレスに変換します（10-5 ネットワークの基本）
    2. その IP の 80 番（HTTP）か 443 番（HTTPS）ポートに TCP 接続します
    3. HTTPS なら TLS で暗号化の準備をします（20-4 HTTPSとTLS証明書）
    4. リクエスト（メソッド・パス・ヘッダー）を送ります
    5. Web サーバーが中身を用意して レスポンス（ステータスコード・ヘッダー・本文）を返します

    2.2 リクエストとレスポンスの中身

    HTTP/1.1 はテキストのプロトコル（通信の決まりごと）なので、中身はそのまま読めます。まずリクエストです。

    GET /index.html HTTP/1.1
Host: shop.example.com
User-Agent: Mozilla/5.0
Accept: text/html

    次にレスポンスです。空行のあとが本文です。

    HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1234
Last-Modified: Mon, 12 Oct 2026 01:00:00 GMT

<!DOCTYPE html>
<html>...
    要素意味例
    メソッド何をしたいかGET（取得）、POST（送信・作成）、PUT/PATCH（更新）、DELETE（削除）
    パスどのリソースか/index.html、/api/products/42
    Host ヘッダーどのサイト宛てか（1 台で複数サイトを持てる理由）shop.example.com
    ステータスコード結果2xx 成功 / 3xx リダイレクト / 4xx クライアント側の誤り / 5xx サーバー側の失敗

    Host ヘッダーが大事な理由

    1 つの IP アドレスで shop.example.com と api.shop.example.com の両方を受けられるのは、Web サーバーが Host ヘッダーを見て「どのサイトの設定を使うか」を決めているからです。これを バーチャルホスト（Virtual Host） と呼び、Nginx では server_name、Apache では <VirtualHost> で設定します。

    運用でよく見るステータスコードも押さえておきましょう。

    コード意味インフラ視点でよくある原因
    301 / 308恒久的なリダイレクトHTTP→HTTPS 転送
    304変更なし（キャッシュを使って）20-6 HTTPキャッシュと圧縮
    403禁止ファイルのパーミッション、deny 設定
    404見つからないroot のパス間違い
    502 Bad Gateway上流（アプリ）から正常な応答がないアプリが落ちている・ポート違い
    504 Gateway Timeout上流が時間内に応答しないアプリが遅い・タイムアウト短すぎ

    3.静的ファイル配信と動的処理

    3.1 2 種類のコンテンツ

    静的コンテンツ（Static）動的コンテンツ（Dynamic）
    中身誰に対しても同じファイルリクエストごとに計算して作る
    例HTML、CSS、JS、画像、フォント商品検索結果、カート、ログイン後のマイページ、API の JSON
    担当Web サーバーがディスクから読んで返すアプリケーション（Node.js、Python、PHP など）が DB を見て生成
    速さ非常に速い（OS の sendfile で直接送れる）DB 問い合わせなどで遅くなりがち

    3.2 Shop での分担

    このシリーズで例に使う EC サイト「Shop」では、次のように役割を分けます。

    Node.js の Express にも express.static() があり、アプリ自身で静的ファイルを返すこともできます。開発中はそれで十分ですが、本番では Web サーバーに任せるのが定石です。理由は次のとおりです。

    • アプリのプロセス（特に Node.js のシングルスレッド）を、画像の転送のような「頭を使わない仕事」で塞がないため
    • Web サーバーはファイル配信に特化した最適化（sendfile、キャッシュヘッダー、圧縮）を持っているため
    • アプリを再起動している間も静的ファイルは配信し続けられるため

    4.Web サーバーの 6 つの役割

    本番環境の Web サーバーは「ファイルを返す」以外にも多くの仕事をしています。

    役割何をするか詳しくは
    ① 静的配信HTML・画像などをディスクから返す20-2 Nginx入門
    ② リバースプロキシ受けたリクエストを裏のアプリに中継する20-3 リバースプロキシ
    ③ TLS 終端HTTPS の暗号を解いて、裏には平文 HTTP で渡す20-4 HTTPSとTLS証明書
    ④ 負荷分散複数のアプリサーバーへ振り分ける50-2 ロードバランサーの仕組み
    ⑤ 圧縮・キャッシュgzip / brotli で転送量を減らし、キャッシュ用ヘッダーを付ける20-6 HTTPキャッシュと圧縮
    ⑥ アクセスログ誰がいつ何にアクセスし、何秒かかったかを記録20-2 Nginx入門、60-5 ログ監査と侵入の検知

    その他にも、リクエストサイズ制限（巨大アップロードの拒否）、レート制限（一定時間あたりの回数制限）、IP 制限、Basic 認証、セキュリティヘッダーの付与なども Web サーバー層でよく行います。アプリに届く前に門前払いできるものは門前払いする、というのが基本的な考え方です。セキュリティヘッダーの中身は 72 セキュリティヘッダ を参照してください。

    5.処理モデル：プロセス・スレッド・イベント駆動

    5.1 同時にたくさんのお客さんをどうさばくか

    Web サーバーは同時に数百〜数万の接続を相手にします。その「さばき方」が製品ごとに違います。

    5.2 C10K 問題

    C10K 問題（Client 10,000 problem） とは、1999 年ごろに提起された「1 台のサーバーで 1 万の同時接続をさばけるか」という課題です。プロセス/スレッド型では接続 1 つにつき数 MB のメモリと コンテキストスイッチ（CPU が担当を切り替えるコスト）がかかるため、1 万接続でメモリも CPU も足りなくなりました。

    この問題への答えが、OS の epoll（Linux）/ kqueue（BSD） といった「多数のソケット（通信の出入り口）のうち準備ができたものだけを通知してもらう」仕組みと、それを使った イベント駆動型サーバー です。Nginx（2004 年公開）はまさにこの問題を解くために作られ、少ないメモリで大量の接続を保持できます。

    実務での意味

    遅いクライアント（スマホの弱い回線など）は接続を長時間つかみっぱなしにします。イベント駆動型の Nginx を前に置くと、遅いクライアントの相手は Nginx が引き受け、アプリには「完成したリクエスト」だけが速く渡ります。これがアプリの前に Nginx を置く大きな理由の 1 つです（20-3 リバースプロキシ）。

    プロセス・スレッド・I/O 多重化の理論は、11_コンピューターサイエンスのノートで扱っています。

    6.主要な Web サーバー製品

    製品処理モデル強み弱み・注意よく使われる場面
    Nginx（エンジンエックス）イベント駆動軽量・高速、リバースプロキシとして定番、情報が豊富設定のリロードが必要、.htaccess 相当はない迷ったらこれ。本シリーズの基準
    Apache HTTP ServerMPM で選択（prefork / worker / event）歴史が長くモジュール豊富、.htaccess でディレクトリ単位の設定設定次第で重くなるレンタルサーバー、PHP / WordPress の既存環境（20-5 Apache入門）
    Caddyイベント駆動（Go 製）HTTPS 証明書の取得・更新が自動、設定が短い日本語情報は Nginx より少ない小規模サービス、個人開発
    LiteSpeedイベント駆動Apache 設定（.htaccess）と互換で高速、WordPress 向けキャッシュ商用版が中心（OSS 版は OpenLiteSpeed）WordPress ホスティング
    IISスレッド型（Windows）Windows Server / ASP.NET と統合Windows 専用.NET Framework の社内システム
    Envoyイベント駆動（C++）動的設定 API、gRPC・可観測性が強い設定が冗長で、単体の Web サーバー用途には過剰Kubernetes のサービスメッシュ（Istio）、API ゲートウェイ

    選び方の目安（2026 年時点）

    • 普通の Web アプリをサーバーに載せる → Nginx
    • 証明書管理を極力したくない小規模サイト → Caddy
    • 既存の PHP / WordPress 資産、.htaccess 前提の環境 → Apache（または LiteSpeed）
    • コンテナ基盤でサービス間通信を制御したい → Envoy（多くはサービスメッシュ経由で間接的に使う）

    AWS の ALB や CloudFront のようなマネージドサービス（クラウド事業者が運用を引き受けるサービス）が Web サーバーの役割の一部（TLS 終端・負荷分散・キャッシュ）を肩代わりする構成も一般的です。

    7.curl -v で HTTP のやり取りを見る

    curl はコマンドラインから HTTP リクエストを送るツールで、-v（verbose）を付けると送受信したヘッダーがすべて表示されます。Web サーバーのトラブルシュートで最初に使う道具です。

    curl -v http://example.com/
    *   Trying 93.184.215.14:80...
* Connected to example.com (93.184.215.14) port 80        ← TCP 接続できた
> GET / HTTP/1.1                                          ← ここから自分が送ったリクエスト
> Host: example.com
> User-Agent: curl/8.5.0
> Accept: */*
>
< HTTP/1.1 200 OK                                         ← ここからサーバーの応答
< Content-Type: text/html; charset=UTF-8
< Content-Length: 1256
< Cache-Control: max-age=604800
< Server: ...
<
<!doctype html>                                           ← 本文
...
    • * で始まる行：curl 自身の動き（DNS 解決、接続、TLS）
    • > で始まる行：送ったリクエスト
    • < で始まる行：受け取ったレスポンス

    よく使うオプションをまとめます。

    # ヘッダーだけ見る（HEAD リクエスト）
curl -I https://shop.example.com/

# リダイレクトを追いかける（HTTP→HTTPS 転送の確認）
curl -IL http://shop.example.com/

# DNS を変えずに、特定の IP のサーバーへ Host を指定して送る（切り替え前の新サーバー確認に便利）
curl -v --resolve api.shop.example.com:443:203.0.113.10 https://api.shop.example.com/health

# サーバー上でアプリに直接（Nginx を通さずに）話しかける
curl -v http://127.0.0.1:3000/health

# 圧縮されるか確認
curl -sI -H 'Accept-Encoding: gzip' https://shop.example.com/assets/app.js | grep -i content-encoding

    切り分けの基本

    「サイトが見られない」ときは、外側から内側へ順に curl していきます。

    1. 手元から curl -v https://shop.example.com/ → DNS・ファイアウォール・TLS の問題か？
    2. サーバー上で curl -v http://127.0.0.1/ → Nginx の設定の問題か？
    3. サーバー上で curl -v http://127.0.0.1:3000/ → アプリ自体の問題か？

    どこで失敗するかで、原因の層がほぼ特定できます。

    8.よくある誤解・つまずき

    よくある誤解

    • ✕「Web サーバー＝サーバーマシンのこと」
      ◯ ここでいう Web サーバーは Nginx や Apache などの ソフトウェア です。1 台のマシンで Web サーバー・アプリ・DB が同居していることもよくあります。
    • ✕「Node.js（Express）で HTTP を返せるなら Nginx は不要」
      ◯ 動きはしますが、TLS 終端・静的配信・遅いクライアントの吸収・ログ・複数アプリの振り分けを Nginx に任せたほうが、安全で速く、アプリはビジネスロジックに集中できます。
    • ✕「502 が出たら Nginx が壊れている」
      ◯ 502 / 504 は「Nginx は動いているが、裏のアプリから正常な返事がない」という意味です。まずアプリのプロセスとポートを確認します。
    • ✕「イベント駆動ならどんな処理も速い」
      ◯ イベント駆動が得意なのは「待ち時間の多い I/O」をたくさんさばくことです。重い計算をイベントループの中でやると、全接続が止まります（Node.js でも同じ）。

    9.補足：静的コンテンツと動的コンテンツ

    3 章の 2 種類のコンテンツについて、それぞれの種類・技術・ハイブリッドな手法・使い分けの指針を掘り下げます。Web コンテンツは、その生成方法と更新頻度によって「静的コンテンツ」と「動的コンテンツ」に分類されます。それぞれ異なる特徴と用途を持ち、Web サイトの目的や要件に応じて適切に使い分けることが重要です。

    9.1 静的コンテンツ（Static Content）

    • 定義：事前に作成され、変更されないコンテンツ
    • 特徴：サーバー側で処理を行わず、そのまま配信
    • 更新：手動でファイルを更新する必要がある
    • 例：HTML、CSS、JavaScript、画像、動画

    メリット

    • 高速配信：サーバー処理が不要で高速
    • 低コスト：サーバーリソースをほとんど使用しない
    • 高信頼性：シンプルな構造で障害が少ない
    • キャッシュ効率：CDN での効率的なキャッシュ
    • セキュリティ：サーバーサイドの脆弱性が少ない

    デメリット

    • 更新の手間：手動での更新が必要
    • 個人化困難：ユーザーごとのカスタマイズが困難
    • リアルタイム性：リアルタイムな情報更新が困難
    • 機能制限：複雑な機能の実装が困難

    静的コンテンツの種類は次のとおりです。

    種類役割特徴例用途
    HTML ファイルWeb ページの構造と内容マークアップ言語による文書構造index.html、about.html、contact.html企業サイト、ポートフォリオ、ブログ
    CSS ファイルWeb ページのデザインとスタイル見た目の制御とレイアウトstyle.css、bootstrap.cssデザイン統一、レスポンシブ対応
    JavaScript ファイルクライアントサイドの動作制御ブラウザ上での動的な動作script.js、jquery.jsインタラクション、アニメーション
    メディアファイル画像・動画・音声形式ごとにファイルが分かれる画像：JPEG、PNG、GIF、SVG／動画：MP4、WebM、AVI／音声：MP3、WAV、OGG視覚的コンテンツ、マルチメディア

    静的サイトジェネレーター（原稿から HTML をまとめて生成するツール）には、Jekyll（Ruby 製、GitHub Pages 対応）、Hugo（Go 製、高速ビルド）、Gatsby（React 製、モダンな開発）、Next.js（React 製、SSG 対応）などがあり、ブログ・ポートフォリオ・企業サイトに使われます。

    9.2 動的コンテンツ（Dynamic Content）

    • 定義：リクエスト時にサーバー側で生成されるコンテンツ
    • 特徴：データベースや外部 API から情報を取得
    • 更新：リアルタイムで内容が変化
    • 例：SNS、EC サイト、ニュースサイト、検索結果

    メリット

    • リアルタイム性：最新情報の即座な反映
    • 個人化：ユーザーごとのカスタマイズ
    • インタラクティブ：双方向のコミュニケーション
    • 機能豊富：複雑な機能の実装が可能
    • データ活用：データベースとの連携

    デメリット

    • 処理負荷：サーバーリソースを多く使用
    • コスト：サーバー費用が高くなる
    • 複雑性：システム構成が複雑
    • セキュリティ：脆弱性のリスクが高い
    • スケーラビリティ：負荷分散が困難

    動的コンテンツの種類は次のとおりです。

    ユーザー生成コンテンツ（UGC）

    ユーザーが作成・投稿するコンテンツ。SNS（Twitter、Facebook、Instagram）、ブログ（WordPress、Medium）、動画（YouTube、TikTok）、レビュー（Amazon、楽天）。

    データベース連携コンテンツ

    データベースから動的に生成。EC サイト（商品情報、在庫状況）、ニュースサイト（記事、コメント）、検索エンジン（検索結果、ランキング）、地図サービス（位置情報、ルート検索）。

    パーソナライズドコンテンツ

    ユーザーごとに異なる内容。レコメンデーション（おすすめ商品、記事）、ダッシュボード（個人の情報表示）、カスタマイズ（ユーザー設定に基づく表示）、ターゲティング（ユーザー属性に応じた内容）。

    動的コンテンツを支える技術は次のとおりです。

    分類代表例
    サーバーサイド技術PHP（WordPress、Laravel）、Python（Django、Flask）、Java（Spring、Struts）、Node.js（Express、Koa）、Ruby（Ruby on Rails）、.NET（ASP.NET、Blazor）
    データベースMySQL（リレーショナルデータベース）、PostgreSQL（高機能な RDBMS）、MongoDB（NoSQL データベース）、Redis（インメモリデータベース）、Elasticsearch（検索エンジン）
    フロントエンド技術（動的な UI の実装）React（ユーザーインターフェース）、Vue.js（プログレッシブフレームワーク）、Angular（フルスタックフレームワーク）、Svelte（軽量フレームワーク）

    9.3 ハイブリッドアプローチ

    静的生成 ＋ 動的機能

    JAMstack（JavaScript、API、Markup）、SSG + API（静的生成と API の組み合わせ）、ISR（Incremental Static Regeneration：静的ページを一定間隔で作り直す方式）。高速性と動的機能の両立に使います。

    エッジサイドレンダリング

    Edge Functions（利用者に近い CDN の拠点＝エッジでの動的処理）、CDN + 動的処理（配信と処理の最適化）。グローバルな高速配信に使います。

    プログレッシブエンハンスメント

    基本的な機能は静的に作り、JavaScript で動的機能を追加します。アクセシビリティと機能性の両立に使います。

    9.4 パフォーマンスの比較

    観点静的コンテンツ動的コンテンツ
    配信速度非常に高速処理時間に依存
    サーバー負荷最小限高い
    キャッシュ効率高い低い
    スケーラビリティ優れている複雑
    CDN 効果高い限定的

    最適化手法としては、キャッシュ戦略（適切なキャッシュ設定）、CDN 活用（静的リソースの配信最適化）、データベース最適化（クエリの最適化）、負荷分散（複数サーバーでの処理分散）があります。

    9.5 選択の指針

    静的が適している

    • 企業サイト：情報発信が中心
    • ポートフォリオ：個人の作品紹介
    • ブログ：記事中心のサイト
    • ランディングページ：単一目的のページ
    • ドキュメント：技術文書、マニュアル

    動的が適している

    • EC サイト：商品管理、在庫管理
    • SNS：ユーザー投稿、コミュニケーション
    • ニュースサイト：リアルタイム情報
    • 検索エンジン：動的検索結果
    • ダッシュボード：個人化された情報

    ハイブリッドが適している

    • 企業サイト + ブログ：静的 + 動的
    • EC サイト + 静的ページ：商品 + 企業情報
    • ニュースサイト + 静的コンテンツ：記事 + 固定ページ
    • SNS + 静的プロフィール：動的投稿 + 固定情報

    9.6 実装のベストプラクティス

    対象やること
    静的コンテンツの最適化ファイル圧縮（Gzip、Brotli）、画像最適化（WebP、AVIF 形式）、CSS/JS 最適化（ミニファイ、バンドル）、キャッシュ設定（適切な Cache-Control）、CDN 活用（グローバル配信）
    動的コンテンツの最適化データベース最適化（インデックス、クエリ最適化）、キャッシュ戦略（Redis、Memcached）、非同期処理（バックグラウンド処理）、負荷分散（ロードバランサー）、監視（パフォーマンス監視）
    セキュリティ対策静的：ファイルアクセス制御／動的：入力検証、SQL インジェクション対策／共通：HTTPS、セキュリティヘッダー／監視：ログ監視、侵入検知

    静的コンテンツと動的コンテンツは、それぞれ異なる特徴と用途を持つ重要な概念です。静的コンテンツは高速で低コストですが、更新に手間がかかります。動的コンテンツは機能豊富でリアルタイム性がありますが、複雑でコストが高くなります。適切な選択と最適化により、目的に応じた効率的な Web サイトを構築できます。また、ハイブリッドアプローチにより、両方の利点を活用したシステム構築も可能です。動的処理を担う側の話は 30-1 アプリケーションサーバーとは で扱います。

    10.まとめ

    • Web サーバーは HTTP リクエストを受けてレスポンスを返すソフトウェアで、Host ヘッダーで複数サイトを使い分ける
    • 静的ファイルは Web サーバー、動的処理はアプリケーションが担当するのが本番の定石
    • 本番の Web サーバーは静的配信・リバースプロキシ・TLS 終端・負荷分散・圧縮・ログを引き受ける「受付」
    • C10K 問題をきっかけに、少数のプロセスで大量接続をさばくイベント駆動型（Nginx など）が主流になった
    • 迷ったら Nginx。自動 HTTPS なら Caddy、既存 PHP 資産なら Apache
    • トラブル時は curl -v で外側から内側へ順に確認する

    11.理解度チェック

    Q1. Shop の画像ファイル（/assets/logo.png）とカート内容の API（/api/cart）は、それぞれ誰が返すのが望ましいでしょうか。

    画像は誰に対しても同じ静的コンテンツなので Nginx がディスクから直接返します。カートはユーザーごとに DB を見て作る動的コンテンツなので Shop API（Node.js）が返し、Nginx はそれを中継（リバースプロキシ）します。アプリのプロセスを静的ファイル転送で塞がず、Nginx の配信最適化を活かせるためです。

    Q2. ブラウザで 502 Bad Gateway が表示されました。最初にサーバー上で実行すべき確認コマンドの例は？

    curl -v http://127.0.0.1:3000/health のように、Nginx を通さずアプリへ直接リクエストします。応答がなければアプリが落ちているかポートが違う、応答があれば Nginx の proxy_pass 設定を疑います。

    Q3. C10K 問題とは何で、Nginx はどうやってそれを解決したのでしょうか。

    1 台で 1 万の同時接続をさばけるかという問題です。接続ごとにプロセス/スレッドを割り当てるとメモリとコンテキストスイッチのコストが膨らみます。Nginx は epoll などの OS 機能を使い、少数の worker プロセスが「準備ができた接続だけ」を順に処理するイベント駆動型でこれを解決しました。

    Q4. 1 つの IP アドレスで shop.example.com と api.shop.example.com を別々に扱えるのはなぜですか。

    Web サーバーがリクエストの Host ヘッダーを見て、どのサイトの設定を使うかを決めているからです（バーチャルホスト）。Nginx では server_name、Apache では <VirtualHost> で設定します。

    Q5. curl -v の出力で、> と < で始まる行はそれぞれ何を表しますか。

    > は自分が送ったリクエスト、< はサーバーから受け取ったレスポンスです。* で始まる行は DNS 解決・接続・TLS など curl 自身の動きです。

    Q6. イベント駆動型サーバーで、重い計算をイベントループの中で行うと何が起きますか。

    イベントループが計算で塞がり、その間すべての接続の処理が止まります。イベント駆動が得意なのは待ち時間の多い I/O をたくさんさばくことで、重い計算は別プロセスなどに逃がします（Node.js でも同じです）。
