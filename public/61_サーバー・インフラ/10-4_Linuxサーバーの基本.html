    10 サーバーの基礎

    Linuxサーバーの基本

    なぜサーバーの OS は Linux が主流なのか、どのディストリビューションを選ぶかから始めて、ディレクトリ構成（/etc /var/log /home /opt /srv）、ユーザー・グループ・パーミッション・sudo、apt によるパッケージ管理、プロセスとサービス（systemctl）、ログ（journalctl）とリソース確認、そして 新しいサーバーを借りた初日にやること までを解説します。前提は 10-3 仮想化とクラウド を読んでいること、ターミナルで cd や ls を使ったことがあれば十分です。

    もとにしたノート：10_サーバーの基礎/04_Linuxサーバーの基本

    ひとことで言うと

    Linux サーバーは 「画面のない、ひたすら働き続けるパソコン」 です。マウスもデスクトップもなく、SSH で遠隔からコマンドを打って操作します。覚えることは 「どこに何があるか（ディレクトリ）」「誰が何をできるか（権限）」「何が動いているか（プロセス・サービス）」「何が起きたか（ログ）」 の 4 つに集約されます。

    1.Linux サーバーは「画面のないパソコン」

    最初は不安ですが、覚えることは上の 4 つです。このページの基準は次のとおりです。

    • サーバー OS は Linux が圧倒的多数派です。このシリーズでは Ubuntu Server 24.04 LTS を基準にします
    • 設定は /etc、ログは /var/log と journald、サービスは systemctl で管理します
    • root で直接作業せず、一般ユーザー＋sudo で必要なときだけ管理者権限を使います

    コマンド操作そのもの（ファイル操作・リダイレクト・vi など）を基礎から学びたい場合は、52_シェルCLI の「Linux基礎」のノート群（Linuxとは何か、権限管理、プロセス監視、パッケージ管理、サービス管理など）も参照してください。

    2.なぜ Linux か、どれを選ぶか

    2.1 Linux が選ばれる理由

    • 無料・オープンソース：台数を増やしてもライセンス費用がかかりません
    • GUI が不要で軽い：メモリや CPU をアプリに回せます
    • 自動化しやすい：すべてがコマンドとテキストの設定ファイルなので、スクリプトや Ansible で再現できます（→ 40-4 構成管理とAnsible）
    • エコシステム：Nginx・PostgreSQL・Docker など、サーバーソフトの多くは Linux を第一の動作環境としています
    • コンテナの土台：Docker のコンテナは Linux カーネルの機能で動きます（→ 10-3 VM とコンテナの違い）

    Windows Server も .NET Framework や Active Directory を使う社内システムでは現役ですが、Web サービスでは Linux が標準です。

    2.2 ディストリビューション

    Linux は「カーネル＋ソフト一式」を組み合わせた ディストリビューション（distribution、略してディストロ） として配布されます。

    系統代表パッケージ管理特徴
    Debian 系Ubuntu Server LTS、Debianapt（.deb）情報が多く初心者向き。クラウドのイメージも豊富
    RHEL 系Red Hat Enterprise Linux、Rocky Linux、AlmaLinuxdnf（.rpm）企業システムで定番。RHEL は有償サポート付き
    Amazon LinuxAmazon Linux 2023dnfAWS 向けに最適化。Fedora ベース

    LTS（Long Term Support） は長期サポート版のことです。Ubuntu の LTS は 2 年ごとに出て、標準で 5 年間のセキュリティ更新、Ubuntu Pro（個人は 5 台まで無料）でさらに延長されます。Ubuntu 24.04 LTS の標準サポートは 2029 年 5 月までです（2026 年時点）。本番サーバーには必ず LTS を選びます。

    他ディストリでの読み替え

    以降のコマンドは Ubuntu 基準です。RHEL 系・Amazon Linux では apt → dnf、ufw → firewalld、管理者グループ sudo → wheel、/var/log/syslog → /var/log/messages と読み替えてください。systemctl と journalctl は共通です。

    3.ディレクトリ構成（FHS）

    Linux のディレクトリ配置は FHS（Filesystem Hierarchy Standard） という規約でおおむね決まっています。「設定ファイルどこ？」で迷わないために、主要な場所を覚えましょう。

    パス中身Shop での例
    /etc設定ファイル/etc/nginx/nginx.conf、/etc/systemd/system/shop-api.service
    /var/logログファイル/var/log/nginx/access.log、/var/log/nginx/error.log
    /var/libアプリが管理するデータ/var/lib/postgresql/16/main（DB の実データ）
    /var/wwwWeb コンテンツ（慣習）静的ファイルを置く場所の候補
    /home一般ユーザーのホーム/home/deploy
    /rootroot ユーザーのホーム普段は使わない
    /optパッケージ外の追加ソフト/opt/shop-api（自作アプリの配置先の候補）
    /srvそのサーバーが提供するデータ/srv/shop（配置先の別候補）
    /usr/bin, /usr/sbinコマンド本体node、nginx
    /tmp一時ファイル。再起動で消える大事なものは置かない

    自作アプリを /opt と /srv のどちらに置くかは流派がありますが、チーム内で 1 つに決めて揃える ことが大切です。本シリーズでは /opt/shop-api に置きます。

    4.ユーザー・グループ・パーミッション・sudo

    4.1 ユーザーとグループ

    Linux は複数人・複数プログラムで使う前提の OS で、誰がやったか を常に管理しています。

    root

    何でもできる管理者。うっかり rm -rf / も実行できてしまいます。

    一般ユーザー

    人間の作業用（例：deploy）。

    システムユーザー

    サービス専用でログインできないユーザー（例：Nginx の www-data、DB の postgres、Shop API 用の shop）。

    サービスごとに専用ユーザーを作るのは、乗っ取られても被害をそのユーザーの権限内に閉じ込める ためです（最小権限の考え方。→ 71 最小権限とデータ最小化）。

    4.2 パーミッション

    パーミッション（アクセス権）は、ls -l で見られます。

    $ ls -l /opt/shop-api/.env
-rw-r----- 1 shop shop 512 Oct 12 10:00 /opt/shop-api/.env
 │└┬┘└┬┘└┬┘   │    │
 │ │  │  │    │    └ 所有グループ
 │ │  │  │    └ 所有ユーザー
 │ │  │  └ その他(other): ---  何もできない
 │ │  └ グループ(group): r--  読むだけ
 │ └ 所有者(user):  rw-  読み書き
 └ 種類（- はファイル、d はディレクトリ）
    記号数字ファイルではディレクトリでは
    r4読める中身の一覧を見られる
    w2書ける中にファイルを作成・削除できる
    x1実行できる中に入れる（cd）
     
    sudo chown shop:shop /opt/shop-api/.env   # 所有者を shop に
sudo chmod 640 /opt/shop-api/.env         # rw-r----- （6=4+2, 4, 0）

    やってはいけない

    DB のパスワードを含む .env を 644（誰でも読める）にしない、chmod 777 で「とりあえず動かす」をしない、が鉄則です。

    4.3 sudo

    sudo（superuser do）は、許可された一般ユーザーが そのコマンドだけ root 権限で実行する 仕組みです。Ubuntu では sudo グループのメンバーが使えます。

    sudo adduser deploy              # ユーザー作成（対話式）
sudo usermod -aG sudo deploy     # sudo グループに追加（-a を忘れると他のグループから外れる）
sudo -u shop whoami              # shop ユーザーとして実行 → shop

    root で直接ログインせずに sudo を使う理由は、誰がいつ何をしたかがログに残る（/var/log/auth.log）ことと、うっかり事故を減らす ことです。

    5.パッケージ管理（apt）

    ソフトのインストール・更新は パッケージマネージャー（ソフトの導入・更新・削除をまとめて管理する道具）で行います。Ubuntu では apt です。

    sudo apt update                  # パッケージ一覧（カタログ）を最新化する。インストールはしない
sudo apt upgrade                 # インストール済みのソフトを更新する
sudo apt install nginx           # インストール
apt list --installed | grep nginx  # インストール済みか確認
sudo apt remove nginx            # 削除（設定ファイルは残る）
sudo apt purge nginx             # 設定ファイルごと削除
sudo apt autoremove              # 不要になった依存パッケージを削除
    • update と upgrade の違いはよく混同されます。update はカタログ更新、upgrade は実際の更新 です
    • Ubuntu Server では unattended-upgrades が既定で有効になっており、セキュリティ更新は自動で適用されます。カーネル更新後は再起動が必要なことがあり、/var/run/reboot-required ファイルの有無で分かります
    • Ubuntu 標準リポジトリの Node.js や PostgreSQL は版が古いことがあるため、公式リポジトリ（NodeSource、PostgreSQL の apt リポジトリ）を追加して入れることが多いです（→ 30-2 Node.jsアプリを本番で動かす）

    6.プロセスとサービス

    6.1 プロセスを見る

    プロセス（process） は「実行中のプログラム」です。

    ps aux | grep node          # 全プロセスから node を探す
ps aux --sort=-%mem | head  # メモリ使用量の多い順
top                         # リアルタイム表示（q で終了）
htop                        # top の見やすい版（sudo apt install htop）

    top の見どころは、上部の load average（直近 1・5・15 分の平均的な実行待ちの数。vCPU 数を大きく超えると混雑）と、各プロセスの %CPU・%MEM です。

    6.2 サービスを管理する（systemd）

    サーバーで常駐するプログラム（Nginx、PostgreSQL、Shop API）は サービス（service） として systemd に管理させます。systemd は起動時の自動起動、落ちたときの自動再起動、ログの収集を引き受けてくれます。

    systemctl status nginx         # 状態確認（active (running) なら稼働中）
sudo systemctl start nginx     # 起動
sudo systemctl stop nginx      # 停止
sudo systemctl restart nginx   # 再起動
sudo systemctl reload nginx    # 設定だけ読み直す（接続を切らない）
sudo systemctl enable nginx    # OS 起動時に自動起動する
systemctl is-enabled nginx     # 自動起動が有効か
systemctl --failed             # 失敗しているサービス一覧

    start は「今起動」、enable は「次回起動時から自動起動」で、別物 です（enable --now で両方）。Shop API 用のサービスファイルの書き方は 30-4 プロセス管理とsystemd で扱います。

    7.ログとリソース確認

    7.1 ログを見る

    journalctl -u nginx                 # nginx サービスのログ
journalctl -u shop-api -f           # Shop API のログを追いかけ表示（tail -f 相当）
journalctl -u shop-api --since "1 hour ago"
journalctl -p err -b                # 今回の起動以降のエラー以上のログ
sudo tail -f /var/log/nginx/error.log   # ファイルに書くタイプのログ
sudo less /var/log/auth.log         # ログイン・sudo の記録

    ログには 2 系統あります。systemd 管理下のサービスの標準出力は journald（journalctl で読む）に、Nginx などが独自に書くログは /var/log 配下のファイル に残ります。

    1. systemctl status でサービスが動いているか見る
    2. journalctl -u でサービスのログを見る
    3. アプリ固有のログ（/var/log/nginx/error.log など）を見る

    「動かない」ときは、この順に見ましょう。ログの集約や監視は 66_可観測性の「サーバー監視とログ管理の基本」「ログ集約基盤」のノートや、60-5 ログ監査と侵入の検知 へ。

    7.2 リソースを確認する

    df -h          # ディスク使用量（Use% が 90% 超えは要注意）
du -sh /var/log/*  # どのディレクトリが容量を食っているか
free -h        # メモリ。見るべきは used ではなく available
uptime         # 稼働時間と load average
nproc          # CPU コア数
ss -tlnp       # 待ち受け中の TCP ポートと、どのプロセスか（要 sudo で全表示）

    free で free 列が小さくても慌てないでください。Linux は空きメモリをディスクキャッシュに使うので、実際に使える量は available 列 です。ss の読み方は 10-5 ネットワークの基本 で詳しく扱います。

    8.初日にやるサーバー初期設定の流れ

    新しい Ubuntu サーバー（VPS / EC2）を借りたら、アプリを入れる前に次の流れで整えます。各項目のセキュリティ的な詳細は 60 章で扱います。

    1. SSH でログイン：EC2 なら ubuntu ユーザー＋鍵
    2. パッケージを最新化：apt update && apt upgrade
    3. 作業用ユーザー作成：sudo グループに追加し、SSH 鍵を配置
    4. SSH を堅くする：パスワード認証・root ログインを禁止
    5. ファイアウォール：22・80・443 のみ許可
    6. タイムゾーン・ホスト名・自動更新の確認
    7. アプリ用のシステムユーザー作成：その後 Nginx / Node.js / PostgreSQL を導入
    # 2. 最新化
sudo apt update && sudo apt upgrade -y

# 3. 作業用ユーザー
sudo adduser deploy
sudo usermod -aG sudo deploy
sudo mkdir -p /home/deploy/.ssh
sudo cp ~/.ssh/authorized_keys /home/deploy/.ssh/
sudo chown -R deploy:deploy /home/deploy/.ssh
sudo chmod 700 /home/deploy/.ssh && sudo chmod 600 /home/deploy/.ssh/authorized_keys
# → 別ターミナルで deploy として SSH ログインできることを必ず確認してから次へ

# 4. SSH（詳細は 60 章）
#   /etc/ssh/sshd_config.d/ に PasswordAuthentication no / PermitRootLogin no を設定し
sudo systemctl reload ssh

# 5. ファイアウォール（クラウドではセキュリティグループも設定）
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose

# 6. 基本設定
sudo timedatectl set-timezone Asia/Tokyo
sudo hostnamectl set-hostname shop-web-01
systemctl status unattended-upgrades

# 7. アプリ用のシステムユーザー（ログイン不可）
sudo useradd --system --create-home --home-dir /opt/shop-api --shell /usr/sbin/nologin shop

    締め出しに注意

    SSH の設定変更やファイアウォール有効化の前に、今の SSH セッションを閉じずに、別ターミナルで新しくログインできることを確認 してください。ufw enable の前に ufw allow OpenSSH を忘れると、自分自身が締め出されます。VPS ならコンソール機能、EC2 ならシリアルコンソールや EC2 Instance Connect が最後の救済手段です。

    SSH・ファイアウォール・ハードニングの詳細は 60-2 SSHの安全な運用・60-3 ファイアウォールとネットワーク制御・60-4 OSのハードニングとパッチ管理 を、構築全体の流れは 40-1 サーバー構築の流れ を参照してください。

    9.よくある誤解・つまずき

    ✕ よくある誤解◯ 実際は
    権限エラーが出たら chmod 777 で解決誰でも書き換え可能になり、侵入の足がかりになる。所有者（chown）と必要最小限の権限を設定する
    apt update でソフトが更新されるupdate はカタログの更新だけ。実際の更新は apt upgrade
    systemctl start したから再起動後も動く自動起動には systemctl enable が必要
    free の free 列が少ない＝メモリ不足Linux は空きをキャッシュに使う。見るべきは available 列
    作業は root でやった方が楽一度のタイプミスでシステムを壊せるうえ、誰が何をしたか追えない。一般ユーザー＋sudo が基本

    10.補足：Linux の特徴とアーキテクチャ

    Linux そのものの特徴、カーネルからアプリケーションまでの構造、主要ディストリビューション、用途とセキュリティ機能を一覧で整理します。

    Linux（リナックス） とは、1991 年にリーナス・トーバルズ（Linus Torvalds）によって開発されたオープンソースの Unix 系オペレーティングシステムです。現在、サーバー、デスクトップ、組み込みシステム、スーパーコンピュータなど、様々な環境で広く使用されています。

    10.1 Linux の特徴

    1. オープンソース

    • ソースコード公開：誰でもソースコードを閲覧・改変可能
    • 無料：基本的に無料で使用可能
    • コミュニティ開発：世界中の開発者が協力して開発
    • 透明性：開発プロセスが公開されている

    2. 高い安定性

    • 長時間稼働：サーバーとして 24 時間 365 日の稼働
    • クラッシュ耐性：システムの異常終了が少ない
    • メモリ管理：効率的なメモリ使用と管理
    • プロセス管理：堅牢なプロセス制御

    3. 高いセキュリティ

    • 権限管理：細かいアクセス権限の設定
    • ユーザー分離：ユーザー間の適切な分離
    • セキュリティパッチ：迅速な脆弱性修正
    • 監査機能：詳細なログ記録

    4. 高いカスタマイズ性

    • 設定の柔軟性：詳細な設定変更が可能
    • モジュール設計：必要な機能のみを組み込み
    • ディストリビューション：多様な Linux 版の選択
    • ソースコード改変：必要に応じた機能追加・修正

    10.2 Linux のアーキテクチャ

    構成要素役割機能・種類例・特徴
    1. カーネルLinux の中核部分ハードウェア管理、プロセス管理、メモリ管理モノリシックカーネル、モジュール化。定期的な更新・改良
    2. シェルユーザーとカーネルのインターフェースBash、Zsh、Fish、PowerShell。コマンド実行、スクリプト処理、環境設定強力なコマンドライン環境
    3. システムライブラリアプリケーションとカーネルの仲介システムコールの提供、共通機能の実装glibc、musl、uClibc。標準化された API
    4. アプリケーション具体的な機能の実現デスクトップアプリ、サーバーアプリ、開発ツールFirefox、LibreOffice、Apache、MySQL。豊富なソフトウェア選択肢

    12.補足：Linux の基本操作と用途

    12.1 Linux の基本操作

    1. ファイルシステム

    • 階層構造：ルート（/）を起点とした階層
    • 主要ディレクトリ：/bin、/etc、/home、/var、/tmp
    • 権限：読み取り（r）、書き込み（w）、実行（x）
    • 所有者：ユーザー、グループ、その他

    2. 基本コマンド

    • ファイル操作：ls、cd、cp、mv、rm、mkdir
    • テキスト処理：cat、grep、sed、awk、sort
    • プロセス管理：ps、top、kill、jobs
    • ネットワーク：ping、ssh、scp、wget、curl

    3. パッケージ管理

    15.理解度チェック

    Q1. Shop API の設定ファイル .env に DB パスワードが入っています。所有者 shop、パーミッション 600 と 644 のどちらにすべきですか？

    600（rw-------） です（グループで読む必要があれば 640）。644 は「その他」のユーザーも読めるため、サーバー上の別のプロセスが乗っ取られた場合にパスワードが漏れます。

    Q2. sudo systemctl start shop-api で起動できたのに、サーバー再起動後に Shop API が動いていませんでした。何が足りなかったでしょう？

    sudo systemctl enable shop-api です。start は今起動するだけで、OS 起動時の自動起動は enable で設定します。sudo systemctl enable --now shop-api で両方を一度に行えます。

    Q3. 「サイトが急に 500 エラーを返すようになった」とき、Linux サーバー上で最初に確認するコマンドを 3 つ挙げてください。

    例：systemctl status shop-api（サービスが落ちていないか）、journalctl -u shop-api --since "10 min ago"（エラーログ）、df -h（ディスクフルでログや DB が書けなくなっていないか）。他に free -h（メモリ不足）、sudo tail /var/log/nginx/error.log も有効です。

    Q4. apt update と apt upgrade の違いは？

    apt update はパッケージ一覧（カタログ）を最新化するだけで、ソフトは更新しません。apt upgrade がインストール済みのソフトを実際に更新します。

    Q5. free -h で free 列がほとんど 0 でした。メモリ不足と判断してよいですか？

    まだ判断できません。Linux は空きメモリをディスクキャッシュに使うので free 列は小さくなりがちです。実際に使える量は available 列で見ます。

    Q6. Nginx の設定ファイル、Nginx のアクセスログ、PostgreSQL の実データは、それぞれ FHS ではどのディレクトリにありますか？

    設定は /etc（/etc/nginx/nginx.conf）、ログは /var/log（/var/log/nginx/access.log）、アプリが管理するデータは /var/lib（/var/lib/postgresql/16/main）です。

    Q7. 初期設定で ufw enable を実行する前に、必ずやっておくことは何ですか？

    sudo ufw allow OpenSSH で SSH を許可しておくことです。忘れると自分が締め出されます。加えて、今の SSH セッションを閉じずに、別ターミナルで新しくログインできることを確認してから進めます。

    Q8. root で直接作業せず、一般ユーザー＋sudo を使うのはなぜですか？

    誰がいつ何をしたかが /var/log/auth.log に残ること、そして一度のタイプミスでシステムを壊すようなうっかり事故を減らせることです。
