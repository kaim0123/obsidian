    構成管理とAnsible

    Ansible は、サーバーの中身（パッケージ・設定ファイル・ユーザー・サービス）を「あるべき状態」にそろえる 構成管理ツール です。このページでは、エージェントレス（SSH だけ） で動く仕組み、インベントリ・プレイブック・モジュールの書き方、冪等性と changed 表示の読み方、--check --diff による事前確認、ロール・変数・Jinja2 テンプレート・ansible-vault、Shop サーバー（Nginx + Node.js + systemd）を構成するプレイブックの完全な例、Terraform との分担を解説します。最後にネットワーク自動化の観点から Ansible・Terraform・Puppet・Chef を比較します。

    もとにしたノート：40_構築・IaC/04_構成管理とAnsible

    ひとことで言うと

    Ansible は 「チェックリストを持って各部屋を回る、几帳面な管理人」 です。リスト（プレイブック）の各項目について「もうできていればそのまま、できていなければ直す」を繰り返します。各部屋に常駐スタッフ（エージェント）は要らず、合鍵（SSH）さえあれば回れます。「箱」は Terraform、「中身」は Ansible という分担が定番です。

    1.Ansible とは

    • 構成管理（Configuration Management） ツール：OS の中身（パッケージ、設定ファイル、ユーザー、サービス）を「あるべき状態」にそろえる
    • 対象サーバーに SSH と Python があればよい（エージェントレス＝管理対象に専用プログラムを常駐させない）
    • YAML で書き、何度実行しても同じ結果になる（冪等）

    手作業の構築手順は 40-1 サーバー構築の流れ、「箱」を作る側は 40-3 Terraform入門 で扱っています。

    2.仕組み：エージェントレスと SSH

    • Ansible を入れるのは コントロールノード（操作する側）だけ。管理対象には何も常駐しません
    • Chef / Puppet はエージェントが定期的にサーバーから設定を取りに行く pull 型、Ansible は手元から押し込む push 型 です

    インストール（コントロールノード側）：

    sudo apt install -y pipx
pipx install --include-deps ansible
ansible --version

    Ubuntu の apt にも ansible パッケージがありますが、新しいバージョンを使うなら pipx（Python の CLI ツールを隔離して入れる仕組み）が便利です。

    3.インベントリ・プレイブック・モジュール

    3.1 インベントリ

    インベントリ（Inventory） は「管理対象サーバーの一覧とグループ分け」です。

    # inventory/prod.yml
all:
  vars:
    ansible_user: deploy
    ansible_ssh_private_key_file: ~/.ssh/shop_deploy
  children:
    web:
      hosts:
        shop-web-01:
          ansible_host: 203.0.113.21   # Terraform の output の IP
        shop-web-02:
          ansible_host: 203.0.113.22
    db:
      hosts:
        shop-db-01:
          ansible_host: 10.0.2.10

    接続確認：

    ansible -i inventory/prod.yml web -m ansible.builtin.ping
# shop-web-01 | SUCCESS => {"ping": "pong"}

    クラウドではサーバーが増減するので、AWS のタグからインベントリを自動生成する 動的インベントリ（amazon.aws.aws_ec2 プラグイン）もよく使われます。

    3.2 プレイブックとモジュール

    プレイブック（Playbook） は「どのホストに、どのタスクを、どの順で」を書いた YAML です。各タスクは モジュール（Module） を 1 つ呼び出します。

    # site.yml（最小例）
- name: Shop web サーバーの基本設定
  hosts: web
  become: true            # sudo で実行
  tasks:
    - name: Nginx をインストール
      ansible.builtin.apt:
        name: nginx
        state: present
        update_cache: true
        cache_valid_time: 3600

    - name: Nginx を起動し、自動起動を有効にする
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

    よく使うモジュール（ansible.builtin に含まれるもの）：

    モジュール役割例
    aptパッケージ管理name: nginx, state: present
    userユーザー作成name: shop, system: true, shell: /usr/sbin/nologin
    fileディレクトリ・権限path: /opt/shop, state: directory, owner: shop
    copyファイルをそのまま配置静的な設定ファイル
    templateJinja2 で値を埋めて配置nginx.conf.j2 → /etc/nginx/sites-available/shop
    service / systemd_serviceサービスの起動・有効化state: restarted
    command / shell任意のコマンド最後の手段。冪等にならないので注意

    FQCN で書く

    apt: ではなく ansible.builtin.apt: のように FQCN（完全修飾コレクション名） で書くのが現在の推奨です。同名モジュールの取り違えを防げます。

    4.冪等性と changed 表示

    プレイブックを 2 回実行すると、結果の表示が変わります。

    # 1 回目
TASK [Nginx をインストール] ************
changed: [shop-web-01]
PLAY RECAP *****************************
shop-web-01 : ok=3  changed=2  unreachable=0  failed=0

# 2 回目（何も変わっていない）
TASK [Nginx をインストール] ************
ok: [shop-web-01]
PLAY RECAP *****************************
shop-web-01 : ok=3  changed=0  unreachable=0  failed=0
    表示意味
    okすでにあるべき状態だった。何もしていない
    changed状態を変更した
    failed失敗（そのホストの以降のタスクは止まる）
    skippedwhen: の条件で実行しなかった

    2 回目に changed=0 になること が、プレイブックが冪等である証拠です。毎回 changed が出るタスクは、たいてい command / shell を素のまま使っています。どうしても使う場合は creates: や changed_when: で冪等にします。

    - name: 依存パッケージをインストール（package-lock.json が変わったときだけ）
  ansible.builtin.command: npm ci --omit=dev
  args:
    chdir: /opt/shop/app
  become_user: shop
  when: lockfile.changed      # 直前の copy/git タスクの結果を register しておく

    本番に流す前は ドライラン（実際には変更しない試し実行）で確認します。Terraform の plan に相当します。

    ansible-playbook -i inventory/prod.yml site.yml --check --diff

    --check は変更せずに「変更されるはず」を表示し、--diff は設定ファイルの差分を表示します（command などチェックモード非対応のタスクは正確に予測できない点に注意）。

    5.変数・テンプレート・ロール・vault

    5.1 変数と Jinja2 テンプレート

    環境ごとに違う値は 変数 にし、設定ファイルは Jinja2 テンプレート（{{ }} に値を差し込む雛形の書式）で生成します。変数はグループ単位のファイルに置けます。

    # inventory/group_vars/web.yml
shop_domain: shop.example.com
shop_api_port: 3000
node_major: 24
    # roles/nginx/templates/shop.conf.j2
server {
    listen 80;
    server_name {{ shop_domain }} api.{{ shop_domain }};

    location / {
        proxy_pass http://127.0.0.1:{{ shop_api_port }};
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

    {{ 変数 }} が値に置き換わります。$host などは Nginx の変数なのでそのまま残ります。proxy 設定の意味は 20-3 リバースプロキシ を見てください。

    5.2 ロール

    タスクが増えたら ロール（Role） に分けます。ロールは「Nginx 担当」「Node.js 担当」のような再利用単位で、決まったディレクトリ構成を持ちます。

    ansible/
├── ansible.cfg
├── inventory/
│   ├── prod.yml
│   └── group_vars/
│       ├── web.yml
│       └── web_vault.yml    # 暗号化された秘密情報
├── site.yml
└── roles/
    ├── common/      tasks/main.yml
    ├── nginx/       tasks/main.yml  templates/shop.conf.j2  handlers/main.yml
    ├── nodejs/      tasks/main.yml
    └── shop_app/    tasks/main.yml  templates/shop.service.j2  templates/env.j2  handlers/main.yml

    ハンドラー（Handler） は「設定ファイルが changed のときだけ Nginx を reload する」ための仕組みです。タスクに notify: を書いておくと、プレイの最後にまとめて 1 回だけ実行されます。

    5.3 ansible-vault

    DB のパスワードなどの秘密情報は ansible-vault で暗号化してから Git に入れます。

    ansible-vault create inventory/group_vars/web_vault.yml   # 作成（エディタが開く）
ansible-vault edit   inventory/group_vars/web_vault.yml   # 編集
ansible-playbook -i inventory/prod.yml site.yml --ask-vault-pass
    # web_vault.yml の中身（保存時は暗号化される）
vault_database_url: "postgres://shop:S3cr3t@10.0.2.10:5432/shop"

    group_vars/web.yml 側で database_url: "{{ vault_database_url }}" と参照すると、どの変数が秘密か一目で分かります。秘密情報を使うタスクには no_log: true を付けてログに出さないようにします。vault パスワード自体は CI のシークレットや --vault-password-file で渡します（秘密情報全般は 30-5 設定と環境変数・シークレット）。

    6.Shop サーバーを構成するプレイブック例

    40-1 サーバー構築の流れ の手順 2〜8 をコード化したものです。group_vars に shop_repo、shop_version（Git のタグ）も定義しておきます。

    6.1 site.yml と common ロール

    # site.yml
- name: Shop web サーバーを構成する
  hosts: web
  become: true
  roles:
    - common
    - nginx
    - nodejs
    - shop_app
    # roles/common/tasks/main.yml
- name: パッケージを最新化
  ansible.builtin.apt:
    update_cache: true
    upgrade: safe
    cache_valid_time: 3600

- name: タイムゾーンを設定
  community.general.timezone:
    name: Asia/Tokyo

- name: 基本パッケージ（acl は become_user で一般ユーザーになるために必要）
  ansible.builtin.apt:
    name: [unattended-upgrades, acl, git]
    state: present

    common ロールに入れたいハードニング項目は 60-4 OSのハードニングとパッチ管理 を参考にしてください。

    6.2 nginx ロール

    # roles/nginx/tasks/main.yml
- name: Nginx をインストール
  ansible.builtin.apt:
    name: nginx
    state: present

- name: Shop 用のサイト設定を配置
  ansible.builtin.template:
    src: shop.conf.j2
    dest: /etc/nginx/sites-available/shop
    mode: "0644"
  notify: Reload nginx

- name: サイトを有効化
  ansible.builtin.file:
    src: /etc/nginx/sites-available/shop
    dest: /etc/nginx/sites-enabled/shop
    state: link
  notify: Reload nginx

- name: default サイトを無効化
  ansible.builtin.file:
    path: /etc/nginx/sites-enabled/default
    state: absent
  notify: Reload nginx

- name: Nginx を起動・自動起動
  ansible.builtin.service:
    name: nginx
    state: started
    enabled: true

    ハンドラーは 同じ名前を listen する 2 つ にして、「文法チェックが通ったときだけ reload」にします。

    # roles/nginx/handlers/main.yml
- name: Check nginx config
  ansible.builtin.command: nginx -t
  changed_when: false
  listen: Reload nginx

- name: Reload nginx service
  ansible.builtin.service:
    name: nginx
    state: reloaded
  listen: Reload nginx

    nginx -t が失敗すればそこで止まり、壊れた設定で reload されることはありません。

    6.3 nodejs ロール

    # roles/nodejs/tasks/main.yml
- name: NodeSource リポジトリを追加
  ansible.builtin.deb822_repository:
    name: nodesource
    types: deb
    uris: "https://deb.nodesource.com/node_{{ node_major }}.x"
    suites: nodistro
    components: main
    signed_by: https://deb.nodesource.com/gpgkey/nodesource-repo.gpg.key

- name: Node.js をインストール
  ansible.builtin.apt:
    name: nodejs
    state: present
    update_cache: true

    6.4 shop_app ロール

    # roles/shop_app/tasks/main.yml
- name: アプリ用ユーザー（ログイン不可）
  ansible.builtin.user:
    name: shop
    system: true
    home: /opt/shop
    shell: /usr/sbin/nologin

- name: ソースを取得（指定バージョン）
  ansible.builtin.git:
    repo: "{{ shop_repo }}"
    dest: /opt/shop/app
    version: "{{ shop_version }}"
  become_user: shop
  register: shop_src

- name: 依存関係のインストールとビルド
  ansible.builtin.shell: npm ci && npm run build && npm prune --omit=dev
  args:
    chdir: /opt/shop/app
  become_user: shop
  when: shop_src.changed
  notify: Restart shop

- name: 環境変数ファイル（秘密情報を含む）
  ansible.builtin.template:
    src: env.j2
    dest: /etc/shop.env
    owner: root
    group: shop
    mode: "0640"
  no_log: true
  notify: Restart shop

- name: systemd unit を配置
  ansible.builtin.template:
    src: shop.service.j2
    dest: /etc/systemd/system/shop.service
    mode: "0644"
  notify: Restart shop

- name: Shop API を起動・自動起動
  ansible.builtin.systemd_service:
    name: shop
    state: started
    enabled: true
    daemon_reload: true
    # roles/shop_app/templates/shop.service.j2
[Unit]
Description=Shop API
After=network-online.target
Wants=network-online.target

[Service]
User=shop
WorkingDirectory=/opt/shop/app
EnvironmentFile=/etc/shop.env
ExecStart=/usr/bin/node dist/server.js
Restart=on-failure
NoNewPrivileges=true

[Install]
WantedBy=multi-user.target
    # roles/shop_app/handlers/main.yml
- name: Restart shop
  ansible.builtin.systemd_service:
    name: shop
    state: restarted
    daemon_reload: true

    unit ファイルの各項目の意味は 30-4 プロセス管理とsystemd で扱っています。

    6.5 実行

    ansible-playbook -i inventory/prod.yml site.yml --check --diff --ask-vault-pass  # 確認
ansible-playbook -i inventory/prod.yml site.yml --ask-vault-pass                 # 適用
ansible-playbook -i inventory/prod.yml site.yml --limit shop-web-01 ...          # 1 台だけ

    community.general.timezone は community.general コレクションのモジュールです（pipx で入れた ansible パッケージには同梱。ansible-core だけの場合は ansible-galaxy collection install community.general）。HTTPS（certbot）もロールにできますが、最初の 1 回は DNS が向いてからの手動実行にして、更新は certbot のタイマーに任せる運用も現実的です（20-4 HTTPSとTLS証明書）。

    7.Terraform との分担

    TerraformAnsible
    得意クラウドリソースの作成・削除サーバー内部の設定
    状態state ファイルで管理持たない（毎回実機を確認）
    削除コードから消せば実体も消える「消す」には state: absent を明示的に書く
    実行タイミングインフラ変更時構築時・設定変更時・定期的なドリフト修正
    • Terraform の user_data（cloud-init＝起動時に初期設定スクリプトを流す仕組み）でも初期設定はできますが、起動時 1 回だけ です。継続的な設定変更は Ansible が向いています
    • Ansible でも EC2 を作れますが（amazon.aws コレクション）、状態管理がないので削除や差分把握が苦手です
    • イミュータブル にしたい場合は、Ansible を Packer から実行して AMI に焼き込み、Terraform はその AMI を使うだけにします（40-2 IaCとは）

    8.発展：構成管理ツールの比較（ネットワーク自動化の観点）

    ネットワーク機器の自動化の観点から、Ansible・Terraform・Puppet・Chef の方式と使い分けを比較します。ネットワーク自動化全体は 40-6 ネットワーク自動化とSDN で扱います。

    8.1 構成管理ツールとは

    構成管理ツール は、機器やサーバーの「あるべき設定」をコード（ファイル）として記述し、そのとおりに自動で設定・維持するツールです。代表は Ansible・Terraform、比較対象として Puppet・Chef です。

    8.2 プッシュ型とプル型

     プッシュ型（Ansible）                     プル型（Puppet / Chef）

  管理サーバ ──SSHで接続して設定を送る──>   管理サーバ <──定期的に設定を取りに行く── エージェント
       │                    機器             (Puppet Master /          (各機器に
       ├──────────────────> 機器              Chef Server)              インストール)
       └──────────────────> 機器
  ・管理サーバが主体                        ・機器側のエージェントが主体
  ・エージェント不要                        ・エージェントが必要
    方式動作代表例
    プッシュ型管理サーバが主体 となって機器に接続し、設定を送り込むAnsible
    プル型機器に入れた エージェント が、定期的に管理サーバへ設定を 取りに行くPuppet、Chef

    ネットワーク機器には追加のソフト（エージェント）を入れられないことが多いため、エージェント不要のプッシュ型（Ansible）はネットワークの自動化と相性がよい のです。（「ブロードキャスト型」「ピアツーピア型」は構成管理ツールの方式を表す用語ではありません。）

    8.3 ツール比較

    項目AnsibleTerraformPuppetChef
    方式プッシュ型プッシュ型（API 経由）プル型プル型
    エージェント不要（SSH / API で接続）不要（プロバイダが API を呼ぶ）必要必要
    記述言語YAML（プレイブック）HCLPuppet 独自 DSL（マニフェスト）Ruby（レシピ／クックブック）
    記述スタイル主に 手順的（タスクを順に実行）宣言的（あるべき状態を書く）宣言的手順的
    状態の記録なしステートファイル――
    よく使う用途機器の設定変更リソースの構築（クラウド、ネットワーク）サーバ構成管理サーバ構成管理

    補足：Ansible は手順的？宣言的？

    Ansible のモジュール自体は冪等に作られており「あるべき状態」を書く側面もありますが、プレイブックはタスクを上から順に実行する手順的な記述です。学習上は「Ansible＝YAML のプレイブックで処理の手順を記述」「Terraform＝HCL で宣言的」と区別します。

    8.4 Ansible の構成要素（ネットワーク機器の例）

    要素内容
    インベントリ管理対象の機器の ホスト名・IP アドレス・グループ（routers、switches 等）を書く一覧。「どの機器に」
    プレイブック実行する処理の内容と手順を YAML で書くファイル。「何をするか」
    モジュール個々の処理の部品（例：cisco.ios.ios_vlans、ios_config）
    変数・テンプレート機器ごとに違う値（ホスト名、IP など）の扱い。テンプレートは Jinja2

    インベントリの例（INI 形式）：

    [routers]
R1 ansible_host=10.1.1.1
R2 ansible_host=10.1.1.2

[switches]
SW1 ansible_host=10.1.1.11
SW2 ansible_host=10.1.1.12

[all:vars]
ansible_network_os=cisco.ios.ios
ansible_connection=ansible.netcommon.network_cli

    プレイブックの例（YAML）：

    ---
- name: VLANを作成
  hosts: switches            # インベントリのグループ名 → SW1, SW2 の全台に実行
  gather_facts: false
  tasks:
    - name: VLAN 10 Sales を作る
      cisco.ios.ios_vlans:
        config:
          - vlan_id: 10
            name: Sales
        state: merged

    実行：

    $ ansible-playbook -i inventory.ini vlan.yml

    プレイブックで グループ名を指定すると、そのグループのすべての機器に同じ処理を実行 できます。

    Ansible の特徴まとめ：

    • エージェント不要、SSH で接続（API 接続も可）
    • YAML のプレイブック
    • プッシュ型
    • 監視ツールではなく、主に 設定の自動化 ツール（SNMP 監視専用ツールではない）

    8.5 Terraform（おさらい）

    • インフラの「あるべき状態」を HCL（HashiCorp Configuration Language） で 宣言的 に記述し、その状態になるようにリソースを作成・変更する。
    • 宣言的 ＝「どういう手順で作るか」ではなく「最終的にどうなっていてほしいか」を書く。
    • 現在の状態を ステートファイル（terraform.tfstate）に記録し、書かれた状態との 差分だけを適用 する。
    • クラウドやネットワークのリソースをコードで構築・管理する IaC（Infrastructure as Code） の代表的ツール。

    HCL の例：

    resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "web" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
}

    Terraform の基本ワークフロー：

     terraform init  ──>  terraform plan  ──>  terraform apply   (… terraform destroy)
   準備                変更内容の確認          適用                 全削除
 (プロバイダ取得)     (差分の一覧を表示)
    コマンド役割
    terraform init作業ディレクトリを初期化し、必要な プロバイダ（プラグイン） を準備

    8.6 Ansible と Terraform の使い分け

    AnsibleTerraform
    得意既存機器の 設定変更リソース（VM、VPC、ネットワーク）の 構築
    ファイルインベントリ ＋ プレイブック（YAML）設定ファイル（HCL）＋ ステートファイル
    スタイル手順を記述あるべき状態を宣言

    8.7 ひっかけポイントと押さえておくポイント

    ひっかけポイント・よくある誤解

    • 「機器ごとにエージェントが必要」は Puppet / Chef の特徴。Ansible は エージェント不要。
    • 「Ruby で記述」は Chef。Ansible は YAML。
    • Ansible は監視ツールではない。
    • 「HCL で宣言的」＝ Terraform。Ansible は YAML のプレイブックで手順を記述。Syslog / NTP はプロトコル。
    • Ansible ＝ プッシュ型。プル型は Puppet / Chef。ブロードキャスト型・ピアツーピア型という方式名はない。
    • 機器の一覧＝インベントリ、処理内容＝プレイブック、Terraform の状態記録＝ステートファイル、running-config は Cisco 機器の動作中の設定。
    • 変更前の確認＝ terraform plan。apply は適用、init は準備、destroy は全削除。

    押さえておくポイント

    • Ansible：エージェントレス・SSH・YAML プレイブック・プッシュ型・インベントリ。
    • Puppet / Chef：エージェント型・プル型。Chef は Ruby。
    • Terraform：HCL・宣言的・ステートファイル・init → plan → apply。

    9.よくある誤解・つまずき

    よくある誤解

    • ✕ shell / command で手順書のコマンドを並べれば Ansible 化できる
      ◯ それは「SSH で流すシェルスクリプト」で、冪等になりません。可能な限り専用モジュール（apt、user、template など）を使い、shell には when / creates / changed_when を付けます。
    • ✕ プレイブックから行を消せば、サーバーからも消える
      ◯ Ansible は state を持たないので、書かれていないものには何もしません。削除したいときは state: absent のタスクを書きます。
    • ✕ 設定ファイルを変えたら、毎回 state: restarted のタスクで再起動する
      ◯ 毎回再起動すると冪等でなくなり、無駄な瞬断も起きます。ハンドラーで「変更があったときだけ」reload / restart します。
    • ✕ vault で暗号化すれば、パスワードはどこにも漏れない
      ◯ 実行時のログ（-v）やエラー表示に出ることがあります。no_log: true を付け、配置先ファイルの権限（0640 など）も絞ります。

    10.まとめ

    • Ansible はエージェントレスで、SSH 経由でモジュールを送り込んで実行する push 型の構成管理ツール
    • インベントリ（対象）＋プレイブック（何を）＋モジュール（どうやって）で構成する
    • 2 回目の実行で changed=0 が冪等の証拠。本番前は --check --diff
    • ロール・group_vars・Jinja2 テンプレート・ハンドラーで整理し、秘密情報は ansible-vault で暗号化
    • 「箱」は Terraform、「中身」は Ansible。イミュータブルにするなら Packer で焼き込む
    • Puppet / Chef はエージェント型・プル型。エージェント不要のプッシュ型の Ansible はネットワーク機器の自動化と相性がよい

    11.理解度チェック

    Q1. 同じプレイブックを 2 回続けて実行したら、2 回目も changed=3 と表示されました。何が疑われますか。

    冪等でないタスクがあることが疑われます。command / shell を条件なしで使っている、毎回 state: restarted にしている、テンプレートに実行時刻など毎回変わる値を埋め込んでいる、などが典型例です。

    Q2. Nginx の設定テンプレートを変更したときだけ Nginx を reload したい。どう書きますか。

    template タスクに notify: Reload nginx を付け、handlers/main.yml に state: reloaded のハンドラーを定義します。テンプレートの内容が変わって changed になったときだけ、プレイの最後に 1 回 reload されます。さらに nginx -t のハンドラーを同じ名前で listen させれば、文法チェックが通ったときだけ reload できます。

    Q3. Terraform と Ansible の両方で EC2 を作れるのに、作成を Terraform に任せることが多いのはなぜですか。

    Terraform は state で「作ったもの」を把握しているため、差分の確認（plan）や、コードから消したリソースの削除ができます。Ansible は state を持たないので、リソースのライフサイクル全体を管理するのが苦手だからです。

    Q4. Ansible の管理対象サーバーに、事前に必要なものは何ですか。

    SSH で接続できることと Python です。エージェントを常駐させる必要はありません。Ansible 本体はコントロールノード（手元 PC や CI）にだけ入れます。

    Q5. プレイブックからパッケージのインストールタスクを消しました。次の実行で、サーバーからそのパッケージは消えますか。

    消えません。Ansible は state を持たず、書かれていないものには何もしないからです。削除したいときは state: absent のタスクを明示的に書きます。

    Q6. プッシュ型とプル型の違いと、それぞれの代表的なツールを答えてください。

    プッシュ型は管理サーバーが主体となって機器に接続し、設定を送り込みます（Ansible）。プル型は機器に入れたエージェントが定期的に管理サーバーへ設定を取りに行きます（Puppet、Chef）。エージェントを入れにくいネットワーク機器にはプッシュ型が向いています。

    Q7. 本番に適用する前に、何が変わるかを確かめるには Ansible でどうしますか。

    ansible-playbook ... --check --diff でドライランします。--check は変更せず「変更されるはず」を表示し、--diff は設定ファイルの差分を表示します。ただし command などチェックモード非対応のタスクは正確に予測できません。
