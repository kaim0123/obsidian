    ひとことで言うと

    サーバー・インフラは、アプリを動かす器（サーバー・Web サーバー・実行環境）と、それを用意し（構築・IaC）、増やし（スケーリング）、守る（セキュリティ）方法 です。このシリーズは EC サイト「Shop」を 1 台構成から冗長構成まで育てながら、10 → 20 → 30 → 40 → 50 → 60 の順に学びます。61 は運用領域（61〜69）の最初の土台で、ここを学んでから 62 データアーキテクチャ、63 AWS へ進みます。

    1.インフラとは何か

    インフラ（インフラストラクチャー、基盤）とは、書いたアプリを 安定して動かすための土台 のことです。家にたとえると、アプリが「家具や部屋の使い方」なら、インフラは「土地・建物・電気・水道・玄関の鍵」にあたります。どんなに良いアプリを書いても、それを置く場所・外から入れる玄関・止まらない仕組み・泥棒よけがなければ、利用者には届きません。

    61_サーバー・インフラでは、インフラのうち次の部分を扱います。

    • 動かす器：サーバー（サービスを提供するコンピューター）、Web サーバー（リクエストの玄関）、アプリの実行環境と DB サーバー
    • 器を用意・拡張・防御する方法：手作業とコード（IaC：Infrastructure as Code、インフラの構成をコードで書いて自動で作る方法）での構築、アクセス増や故障に耐えるスケーリング・負荷分散、攻撃から守るセキュリティ

    動画「インフラ完全攻略」では、インフラを「AWS・Google Cloud などクラウド上の、アプリを安定稼働させる土台」と説明しています。今日ではその多くがクラウドの上にありますが、クラウドの製品（EC2・ELB・VPC など）を使いこなすには、その下にあるサーバーとネットワークの知識が前提になります。だから AWS（63）の前に、このフォルダで製品に依存しない基礎を学びます。

    このシリーズで軸にしている資料は、roadmap.sh DevOps（OS → ネットワーク → Web サーバー → IaC → スケーリング → セキュリティの流れ）、The Twelve-Factor App（クラウドで動くアプリの 12 の原則）、各製品の公式ドキュメント（nginx.org、Ubuntu Server docs、systemd、Terraform、Ansible、AWS）です。

    2.3 なぜこの順番なのか

    順番は roadmap.sh DevOps の「OS → ネットワーク → Web サーバー → IaC → スケーリング → セキュリティ」の流れを軸にしています。Shop を育てる順番に沿っているので、前のフォルダが次のフォルダの前提になります。

    1. 10 サーバーの基礎：まず「器」そのもの（サーバー・仮想化・Linux・ネットワーク）を知らないと、何を設定しているのか分かりません。
    2. 20 Webサーバー・リバースプロキシ：器ができたら、外からのリクエストを受け止める玄関（Nginx と HTTPS）を作ります。利用者から最初に見える部分です。
    3. 30 アプリ実行環境：玄関の奥でアプリと DB を動かし、落ちても自動で立ち上がるようにします。ここまでで「1 台に公開」が完成します。
    4. 40 構築・IaC：10〜30 の作業を一度手で経験したあとで、それをコードにします。手順を知らないままツールから入ると、何を自動化しているのか分からなくなるためです。
    5. 50 スケーリング・負荷分散：コードで同じサーバーを何台でも作れるようになって初めて、台数を増やす・壊れても止まらない構成が現実的になります。
    6. 60 サーバー・ネットワークセキュリティ：最後に、ここまで作った構成全体を守ります。60-5 にはシリーズ全体のまとめとして Shop のセキュリティチェックリストがあります。

    セキュリティは「最後にやればよい」わけではない

    60 が最後にあるのは、守る対象（10〜50 で作るもの）を知ってから学ぶほうが分かりやすいからです。実際の作業では、SSH の鍵認証やファイアウォールは公開する前に設定します。そのため、下の「1 台に公開する近道」には 60-2・60-3 が入っています。

    3.Shop の最終構成

    シリーズの最後に Shop は次の構成になります。図中の数字は、その部分を扱うフォルダです。

    入口から順に見ると、利用者は DNS（ドメイン名を IP アドレスに変換する仕組み、10）で行き先を知り、CDN（世界中に置かれたキャッシュサーバー、50）を経由して、HTTPS（暗号化した HTTP、20）で ロードバランサー（複数のサーバーに振り分ける装置、50）に届きます。その先には複数の AZ（アベイラビリティゾーン、クラウドの独立したデータセンター群）に分けて置いた Web サーバーがあり、Nginx（20）が Node.js API（30）にリクエストを渡します。アプリは systemd（Linux のプロセス管理の仕組み、30）が見張っていて、落ちても自動で再起動します。データは Multi-AZ 構成の PostgreSQL（30・50）に置きます。この全体を Terraform / Ansible（40）でコードから作り、ファイアウォール・SSH・パッチ・監査・ACL・VPN（60）で守ります。

    5.61〜69 の中での位置

    61〜69 は、書いたコードを動かす土台を理解し、本番に届け、動かし続け、観察して直す ための「運用領域」です。学ぶ順に 9 つの分野が並んでいて、61_サーバー・インフラはその最初にあります。並びは roadmap.sh DevOps の学習順（OS・ネットワーク・サーバー → クラウド → CI/CD → 監視）、Google SRE 本の「原則 → 実践」の流れ、DDIA（Designing Data-Intensive Applications 第 2 版）の構成を参考にしています。

    7.動画で学ぶ：なぜインフラを身につけるのか

    ここからは、りょうま@インフラ攻略 さんの動画「【永久保存版】インフラ完全攻略 - 現役エンジニア向け」（2026-07-04 公開）の内容をまとめます。テーマは バックエンドエンジニアがインフラ力を身につけるべき理由・難しさ・学び方・5 段階ロードマップ です。

    7 年のエンジニア経験を持つ SRE（サイト信頼性エンジニア、サービスを止めないことを専門にするエンジニア）の投稿者が、インフラの重要性、バックエンドとインフラを掛け合わせる価値、インフラの実務経験が積みにくい構造的な理由、学習の 5 つのポイント、そして EC2 → ECS → Lambda → Google Cloud → EKS（Kubernetes）の習得ロードマップを語ります。投稿者自身、7 年の中でインフラの技術を身につけることに一番苦労し、1 年目は会社のインフラ構成がまったく分からなかったそうです。結論は、インフラは「運ガチャ」に頼らず、正しいやり方で再現性高く伸ばせる ということです。

    7.1 なぜ今インフラが重要か

    • 生成 AI でアプリの母数が膨大になりました。ローカル（自分の PC）で動くものは誰でも作れますが、デプロイして公開する部分は難しく、インフラの知識が要ります。
    • リリース後も、セキュリティ、クラウドコストの管理、リクエスト増に応じた増強、障害時の復旧など、やることは膨大に増えます。
    • AI でバックエンドの処理がリッチになり、非機能要件（機能そのものではなく、速さ・止まらなさ・安全さなどの品質の要求）の水準も上がっています。それを AI だけで丸ごと解決する未来は、SRE として働く投稿者にはまだ見えないといいます。

    7.2 バックエンドエンジニアこそインフラをやるべき理由

    • テックリードや CTO は、ほぼ例外なくバックエンドもインフラも強いです。テックリードまで上がるには、インフラを避けて通れません。
    • 「技術の難易度（横軸）× 領域（縦軸：インフラ／バックエンド／フロント）」の図で見ると、メンバークラスとテックリードの差は 非機能要件への設計力 と インシデント対応力（障害が起きたときに原因を突き止めて直す力）です。どちらもバックエンドとインフラにまたがらないと発揮できません。

    7.3 掛け算①：非機能要件への設計力

    • 非機能要件の例：レスポンス 50ms 以下（99%）の API、エンタープライズ向けの論理ネットワーク分離、100 万件のメールを 1 時間以内に一斉配信、1 万人同時接続のストリーミング、10GB の 3D データを 30 分以内に低コストで変換、など。
    • API の性能を改善する手札は、バックエンド側（クエリのチューニング、N+1 問題の解消、Redis などのアプリケーションキャッシュ）と、インフラ側（DB のリードレプリカ、Web サーバーのオートスケール）の両方にあります。
    • 設計ドキュメントにも両方の観点が必要です。API 仕様書・DB スキーマ・シーケンス図・負荷試験に加え、インフラ構成図・監視（例：SQS のメッセージ数やデッドレターキューを監視して Slack に通知）まで書きます。非同期処理（SQS・Kafka・Pub/Sub）や、RDBMS 以外の DB を選ぶ力も要ります。
    • 生成 AI の時代はこれが加速します。LLM のストリーミングには長時間の接続を維持する設計、ベクトル検索の本番運用には大規模データを低レイテンシで検索する基盤、AI エージェントの並列実行には非同期処理とキューイングの基盤が必要です。
    • 非機能要件は大口顧客が導入するかどうかを左右し、満たせるかどうかは 0 か 100 の世界です。高い水準で満たせるエンジニアは市場価値が高く、AI に置き換えられにくいといえます。

    7.4 掛け算②：インシデント対応

    • 500 エラーを調べるとき、バックエンド側では アプリケーションログ → ソースコード、DB のコネクション数、スロークエリを見ます。インフラ側では ネットワークの異常、CPU・メモリ・ディスクを見ます。
    • 両方分かれば多角的に仮説を立てられ、「そこはインフラ側なので分かりません」といった押し付け合いになりません。

    7.5 インフラができるメリット 4 つ

    1. 技術のポータビリティ（持ち運びやすさ）が高い：A 社で苦労して EC2 → ECS 移行をした経験で、B 社の ECS 新規構築は一瞬で終わったそうです。インフラはドメイン知識（業界や業務の知識）から遠く、OSI 参照モデルの L1〜L6 など標準化された技術を扱う割合が高いためです（バックエンドは主に L7 で、ドメイン知識と密結合）。業界が変わっても、構成は EC2・ECS・Kubernetes・Cloud Run など似たり寄ったりです。
    2. 技術が陳腐化しにくい：根底にあるのはネットワーク・DB・SQL・Linux・CS など息の長い技術です。フロントエンド（Next.js・React）や生成 AI のように半年で常識が変わる領域と違い、後から来た人に逆転されにくいです。
    3. 実績を語りやすい：「AWS コストを月 25 万円削減」「デプロイを 25 分 → 5 分」「API を 2 秒 → 20ms」のように数字で語れ、他社の人にも大変さがすぐ伝わります。バックエンドの実績は社外秘も多く、「〇〇 API を開発」と抽象化するしかないことが多いです。
    4. 単価が高い：ミスの影響範囲が大きく誰もやりたがらない、学習コストが高く参入障壁が高い、という理由でできる人が少ないためです。ハードスキル次第で月単価 100 万円超（高い人で 165 万円）もあるそうです。

    8.動画で学ぶ：経験の積みにくさと学び方

    8.1 なぜインフラの経験は積みにくいのか（4 つの理由）

    1. プロダクトの心臓だから

    DB や DNS の対応を間違えると大障害になります。1 分の障害で数十万〜数百万円が飛ぶこともあります。フロントの文言修正のような「肩慣らしタスク」がなく、最初の打席に立ちにくいです。

    2. レバレッジが効くから

    Terraform などの IaC や CI/CD を作れば半永久的に効き、お手本の構成は若手に真似されて広がります。逆に、未熟な人が作った初期構成は負債が雪だるま式に増えます（本番では「動いているものが正義」なので、緩い設定もそのままコピーされます）。だから経験者に任せたい力学が働きます。

    3. 不可逆だから

    たとえば DB をパブリックサブネット（インターネットから届く区画）に作ると、後からプライベートに移すには作り直しが必要です。リソース名も ID として使われるため、変更には作り直しが要ります。アプリ層のように git revert で戻せません。

    4. タスクが少ないから

    フロント：バックエンド：インフラのタスク量は、体感で 5：4：1 です。詳しい人が 1 人いれば回ってしまい、できる人がタスクを独占します（本人は任せたいのに、納期や顧客影響を考えてつい自分でやってしまう）。

    8.2 インフラ力が上がらないジレンマ

    • 経験豊富な人がいる会社：収益が安定していてサービスを落とせないので、SRE チームやプラットフォームチームによる分業体制になっています。実績がないと任せてもらえず、打席が回ってきません。
    • 未経験でも触り放題の会社（小規模スタートアップ）：お手本もフィードバックもなく我流になり、頭打ちになります。変な癖がついて、むしろ悪化することもあります。

    我流構成のあるある

    • 1 つの AWS アカウントにステージング環境と本番環境が混在（S3 バケットの中をパスで dev / stg / prod に分けるケースも）
    • DB や ECS がパブリックサブネットにむき出し
    • 命名規則（prd・prod・production、接頭辞・接尾辞）が揺れまくり
    • 全員に AdministratorAccess（何でもできる権限）
    • セキュリティグループを使い回して 0.0.0.0/0 でフルオープン
    • 毎月の AWS コストを誰も知らない
    • インシデントに、ユーザーからの問い合わせで初めて気づく

    これらはこのシリーズでも繰り返し扱う問題です。パブリックに置かない・ポートを開けすぎない話は 60-3 ファイアウォールとネットワーク制御、権限を絞る話は 60-1 サーバーセキュリティの基本 で取り上げます。

    8.3 インフラ学習で押さえるべき 5 つのポイント

    1. クラウド代をケチらない：ALB で月 2,000 円、NAT Gateway で 7,000 円といった請求が怖くて手を動かせないことが、最大の心理的な壁です。ただし闇雲に作ると高額請求も起こるので、詳しい人に頼るのが確実です（学習時間外の自動停止や、NAT Gateway の代わりに NAT インスタンスを使って月数百円に抑える工夫など）。
    2. ベストプラクティスに沿った綺麗な構成を真似する：これが最も大事です。投稿者はスタートアップで EC2・ECS・API Gateway・Lambda・Step Functions・CloudFront などを触り倒しても一定以上伸びませんでしたが、メガベンチャーで高レベルな構成を見て霧が晴れたそうです。特に、既存の dev・stg・prod に加えて sandbox 環境を Terraform（Google Cloud）と Kubernetes マニフェストで複製したタスクで力が大きく伸びました。眺めるだけでなく、複製するために既存の設定を理解する、というインプットとアウトプットの往復が効きます。
    3. 最初はコンソールから手動で構築する：いきなり Terraform・CloudFormation・CDK から入ると、GUI でしか得られない手触り感を捨てることになります。おすすめは「コンソールで構築 → terraform import でコード化 → 別環境を apply で複製」です。たとえば CloudFront のオリジン設定画面では、重要な項目が上にあり追加設定はトグルで隠れている、関数（CloudFront Functions）はディストリビューションと同じ階層なので独立して作って紐付ける、オリジンやビヘイビアはディストリビューションの中に 1 対 N で作る、といった重要度やリソース同士の関係が直感的に分かります。この感覚があったので、初見の Cloudflare もすぐ使えたそうです。このシリーズでも、40-1 サーバー構築の流れ で手作業を経験してから IaC に進みます。
    4. 点ではなく線（ストーリー）で構築する：ハンズオンの「いきなり NAT Gateway を作りましょう」は点の学習です。線の例は次のとおりです：API を動かす → 外部パッケージや外部 API に通信できない → ECS をパブリックサブネットに置いてグローバル IP を持たせる → 外からアクセスできてしまうのは危険 → NAT Gateway が必要 → 学習用には月 7,000 円は高い → EC2 で iptables を設定して NAT の代わりにする → 停止忘れを防ぐため EventBridge Scheduler で自動停止。小さな理由付けと意思決定の積み重ねが設計力になり、実務と同じ筋肉を使います（資格教材は点になりがちです）。
    5. アプリケーションコードにこだわる：チュートリアルが「Welcome to nginx」で完結するから実務に効かない、という指摘です。実務では DB マイグレーション、バッチ・非同期処理、外部 API や AWS サービスとの連携、認証情報、環境変数の管理、デプロイパイプラインなどが必要です。教材が nginx だらけなのは、教える側がインフラエンジニアでアプリ側は専門外かつ工数を割きたくないからでは、というのが投稿者の仮説です。理想は実務で本格的な構成を丸ごと作ること、次点はバックエンドエンジニアと組んだ個人開発です。このシリーズが Node.js API と PostgreSQL を持つ「Shop」を題材にしているのも、この考え方に沿っています。

    9.動画で学ぶ：インフラスキル習得ロードマップ

    多くの会社のインフラ構成は、おおむね次の 5 パターンに集約されます。「うちは ECS」「うちは Kubernetes」と聞くだけで、技術力・プロダクトの特性・組織文化がある程度透けて見えるそうです。下に行くほど学習コストが上がります（業界のレベルマップのようなもの）。

    STEPサービス抽象化した概念
    1EC2仮想マシン
    2ECSコンテナ
    3Lambdaイベント駆動
    4Google Cloudマルチクラウド
    5EKSKubernetes

    仮想マシン・コンテナ・サーバーレスの違いの基礎は 10-1 サーバーとは何か と 10-3 仮想化とクラウド で扱います。

    9.1 STEP1：EC2（仮想マシン）

    • 選ぶ動機：① 自由度が圧倒的に高い（責任共有モデルで OS から上が利用者の管理）② 既存資産との互換性（オンプレの API をそのまま移す。後に Kubernetes へ移る流れも多い）③ 特殊要件（GPU インスタンス、大容量メモリの X 系インスタンスなど）
    • 採用企業は「AWS に詳しい人がいない」か「非常に詳しい人がいる（金融・製造・公共・医療・物流などの基幹システム、大手日系企業）」の両極端です。
    • キャリア上の利点：インフラの手触り感。SSH で入ってプロセスを起動・停止する、wget でインストールする、nslookup・dig で疎通確認する、など。コンテナ時代でもビルド時に Linux コマンドで中身を構築するので、すべての原点になります。
    • つらい点
      • サーバー管理の負担：OS のセキュリティパッチ、Apache・nginx などのミドルウェアのバージョン管理、カーネル更新、脆弱性対応を全台分行います。台数が増えると指数関数的に大変になり、メンテナンスのたびにダウンタイムの調整も要ります。
      • リソース割り当てが柔軟でない：同居するプロセス A（ピーク時に 3GB へスパイク）・B・C のために、平常時も 3GB のインスタンスを払い続けます。プロセスごとに分けると、コストと運用工数が増えます。
      • 属人性が高くなる：EC2 の再起動後にアプリが起動しないインシデントの原因は、最近別の人が入れた Datadog エージェントと、サーバー内で動かしていた別のプロセスが悪さをしていたことでした。中で何でもできるので、誰が何をしたか把握できなくなります（Ansible・Chef で多少改善しますが、緊急時の手作業は残ります）。

    9.2 STEP2：ECS（コンテナ）

    • 選ぶ動機：EC2 のつらさを解決します。
      • Fargate（サーバーを意識せずにコンテナを動かす ECS の実行方式）なら、ホスト OS のハードニング（不要ポートの閉鎖、SSH・SELinux の設定）、OS の監視、パッチ適用を AWS が管理します。
      • 属人性を構造的に排除：インフラは JSON の タスク定義（イメージ、CPU・メモリ、環境変数、ログ出力先、ヘルスチェック）と Dockerfile の 2 つで静的に管理します。タスクはデプロイのたびに使い捨てなので、手作業の変更が残りません（ECS Exec でログインはできますが例外的な使い方です）。
      • リソース割り当てが柔軟：タスク・コンテナ単位で CPU・メモリを割り当てられます。
    • 多くの Web 系企業でメジャーです。キャリア上の利点は コンテナ時代のお作法（プロセスをコンテナで包む、Dockerfile の書き方、SSH せず構成を静的に定義する、サーバーを使い捨てる）が身につくことです。Kubernetes や Azure Container Apps などにも横展開でき、Lambda もコンテナで動かせます。
    • 弱点：常駐課金でコストが高くつきやすい（社内ツールや初期プロダクトには割高）、オートスケールは自動だが即時ではない（タスクの起動・安定まで 30〜60 秒かかり、急なスパイクに間に合わないことも）、CPU・メモリ・ネットワークセキュリティ・スケーリングなどの管理負担は残る。オートスケールの遅れは 50-3 オートスケーリング でくわしく扱います。

    9.3 STEP3：Lambda（イベント駆動）

    • イベントが起きたときに一時的に起動し、処理が終わると停止します。
    • 選ぶ動機：① 従量課金で圧倒的に安い ② スケーラビリティ（設定不要で 1,000 並列まで自動スケール、数十ミリ秒単位で立ち上がる）③ デプロイが速い（ECS は 5〜20 分かかることもあるが、Lambda はものの 5 分ほど）
    • デメリット：コールドスタート（しばらく使われていない関数の初回起動）で数秒かかる、リクエスト・レスポンスのサイズ上限 6MB、タイムアウト 15 分などの制約があります。ECS の完全な上位互換ではありません。
    • キャリア上の利点：イベント駆動アーキテクチャ という設計の手札が増えます。例：DynamoDB へのレコードの put を検知して別の場所へ同期する、S3 へのアップロードを検知して圧縮や動画変換をする。EC2・ECS は AWS のイベントから直接起動できず、EventBridge・SQS・Lambda を挟む必要があるので、Lambda はイベント駆動の入口として活躍します。あわせて EventBridge、Step Functions、SQS、SNS、Kinesis Data Streams、Firehose にも詳しくなると世界が広がります。
    • EC2・ECS・Lambda の 3 つで、1 つのクラウドにおける仮想マシン・コンテナ・イベント駆動を一通りカバーできます。

    9.4 STEP4：Google Cloud（マルチクラウド）

    • 前提：AWS の次は、自分の業界でシェアが高いクラウドを選びます（Web 系やスタートアップなら Google Cloud、大手 SIer や金融系の顧客なら Azure）。
    • 理由① AWS の理解が深まる（海外に行くと日本が分かるのと同じ）：Cloud Run を触って、ECS は VPC・サブネット・セキュリティグループ・タスク定義・タスク実行ロール／タスクロールなど設定項目が多いと気づいたそうです。裏返せば、細かいセキュリティ要件に柔軟に対応できる良さでもあります。Cloud Run はゼロスケール（使われていないときは 0 台まで減らす）できるが ECS はできない、似たことは Lambda でできるがサイズやタイムアウトの制約がある、などを俯瞰して見られるようになります。
    • 理由② いいとこ取りの設計：API はゼロスケールできる Cloud Run、データ基盤は BigQuery、メール配信は Amazon SES、ビデオ通話は Amazon Chime、他社とのファイル連携は権限設計が柔軟な S3、フロントのホスティングは Amplify、Kubernetes のマイクロサービス基盤は GKE、などです。
    • 生成 AI で「SaaS のソフトそのものより保有データに価値がある」という風潮が強まり、データ基盤を整える流れから「データ基盤は BigQuery、API は AWS の ECS」というマルチクラウド構成の会社が増えています。
    • 2 倍の労力にはならない：仮想マシン・コンテナ・イベント駆動の概念があればすぐキャッチアップでき、サービスはほぼ 1 対 1 で対応します（EC2 ↔ GCE、ECS ↔ Cloud Run、S3 ↔ GCS、RDS ↔ Cloud SQL、Lambda ↔ Cloud Functions）。考え方が大きく違う IAM・ネットワーク・Cloud Load Balancing を重点的に押さえればよいです。

    9.5 STEP5：EKS / Kubernetes

    • Kubernetes は、Google が社内で培ったコンテナ運用のノウハウを OSS 化した コンテナオーケストレーションツール（たくさんのコンテナの配置・起動・増減をまとめて管理する道具）です。
    • 導入の動機：ECS でマイクロサービスが増えると、機能ごとに AWS サービスを継ぎはぎする意思決定・キャッチアップのコストが積み上がります（サービス間通信は Cloud Map・Service Connect、デプロイは CodePipeline・CodeBuild・CodeDeploy、監視は CloudWatch、オートスケールは ECS Service Auto Scaling、バッチは EventBridge Scheduler・AWS Batch など）。Kubernetes ならマニフェスト（YAML）で統一的に表現でき（Service・Istio、Argo CD、Prometheus・Grafana、HPA、CronJob・Argo Workflows、マイグレーションは Job）、規模が大きいほど差が効きます。
    • キャリア上の利点① 技術力がブーストする：Kubernetes が必要なプロダクトは限られ、ほとんどは ECS で十分です。それでも習得すると、コンテナ・ネットワーク・クラウドの理解が大きく上がります。投稿者は EC2 → ECS で挫折 → Cloud Run → GKE → ECS と経験し、GKE の後は ECS が非常に簡単に感じ、コンテナ本を 1 冊読むだけでベストプラクティスに沿った設計・構築ができたそうです。
    • キャリア上の利点② Kubernetes を扱う会社は技術レベルが高い：金銭・学習・運用のコストが高いので、売上があり組織に投資できる会社でないと導入しません。採用力が強く、勉強熱心なエンジニアが集まります。投稿者も GKE の案件で優秀なメンバーから刺激を受け、技術力が爆発的に伸びたそうです。

    9.6 ロードマップのまとめ

    • 5 段階を一通り経験すれば、Web 系の会社のどれかの技術でキャッチアップに困りません。
    • 「EC2 なら ECS に変えたら？」「ECS なら Lambda や Kubernetes を入れたら？」「AWS なら Google Cloud を取り入れたら？」と多角的に考えられ、奥深い設計力がつきます。
    • インフラは広く深く、一朝一夕では身につきませんが、だからこそ逆転されにくいです。最初から全部やろうと気負わず、実務をこなしながら少しずつ守備範囲を広げればよい、と締めくくっています。

    9.7 動画全体のまとめ

    • バックエンド × インフラの掛け算が、テックリード級の非機能要件の設計とインシデント対応を可能にし、市場価値を高めます。
    • インフラは「心臓・レバレッジ・不可逆・タスクが少ない」ために経験を積みにくく、強い人がいる会社でも我流の会社でも伸び悩むジレンマがあります。
    • 学び方の鍵は、クラウド代をケチらない、綺麗な構成を真似して複製する、まずコンソールで手動構築する、ストーリーで線として学ぶ、本格的なアプリコードで構築する、の 5 点です。
    • 習得順は EC2（仮想マシン）→ ECS（コンテナ）→ Lambda（イベント駆動）→ Google Cloud（マルチクラウド）→ EKS（Kubernetes）です。

    10.まとめ

    • サーバー・インフラは、アプリを動かす器と、それを用意・拡張・防御する方法 です。
    • 10 サーバーの基礎 → 20 Web サーバー → 30 アプリ実行環境 → 40 構築・IaC → 50 スケーリング → 60 セキュリティ の順に、Shop を 1 台構成から冗長構成まで育てながら学びます。手作業を知ってからコード化し、コード化できてから台数を増やし、最後に全体を守る、という流れです。
    • 61 は運用領域 61〜69 の最初の土台です。61 → 62 データアーキテクチャ → 63 AWS → 64 CI-CD → 65 リリース・デプロイ → 66 可観測性 → 67 パフォーマンス → 68 分散システム → 69 SRE・インシデント対応 と進みます。
    • OS・ネットワークの理論は 11_コンピューターサイエンス、セキュリティの考え方とアプリ側の対策は 71〜74 にあり、61 はそれをサーバーの運用に当てはめます。
    • 動画「インフラ完全攻略」によれば、インフラは経験を積みにくい領域ですが、綺麗な構成を真似る・手で作ってからコード化する・ストーリーで学ぶ・本物のアプリで作る、といった正しいやり方で再現性高く伸ばせます。

    11.理解度チェック

    Q1. 61_サーバー・インフラで扱う「インフラ」とは何ですか。

    アプリを安定して動かすための土台です。具体的には、アプリを動かす器（サーバー・Web サーバー・実行環境・DB サーバー）と、それを用意する（構築・IaC）、増やす（スケーリング・負荷分散）、守る（サーバー・ネットワークセキュリティ）方法を扱います。

    Q2. 40 構築・IaC が 10〜30 の後にあるのはなぜですか。

    手作業でサーバーを構築する手順を一度経験してからでないと、IaC ツールが何を自動化しているのか分からないからです。動画でも「最初はコンソールから手動で構築し、その後 terraform import でコード化する」学び方が勧められています。また、コードで同じサーバーを何台でも作れるようになって初めて、50 のスケーリングが現実的になります。

    Q3. 60 セキュリティが最後にあるなら、公開前にセキュリティ設定をしなくてよいのですか。

    いいえ。60 が最後にあるのは、守る対象を知ってから学ぶほうが分かりやすいからです。実際には SSH の鍵認証やファイアウォールは公開前に設定します。そのため「1 台に公開する近道」にも 60-2・60-3 が含まれています。

    Q4. 61〜69 の中で、なぜ 61 は 63 AWS より先なのですか。

    EC2・VPC・ELB といった AWS の製品は、サーバーとネットワークの知識が前提だからです。61 で製品に依存しない概念を学び、62 で DB の基礎を学んでから、63 でそれらをクラウドの製品に当てはめます。

    Q5. TCP/IP や DNS の仕組みそのものを詳しく知りたいときは、どこを見ますか。

    11_コンピューターサイエンスの「60 ネットワーク・Web」（OS なら「50 OS・並行処理」）のノートです。61 はそれらの理論をサーバーの運用に使う実践側を扱います。

    Q6. 「502 Bad Gateway」が出たとき、まず読むページはどれですか。

    20-3 リバースプロキシ、続いて 30-4 プロセス管理とsystemd です。502 は Nginx（リバースプロキシ）が後ろのアプリから正しい応答を受け取れないときに出るので、転送設定とアプリのプロセスが動いているかを確認します。

    Q7. 動画で挙げられた「インフラの経験が積みにくい 4 つの理由」は何ですか。

    ① プロダクトの心臓で、間違えると大障害になる ② レバレッジが効くので、経験者に任せたい力学が働く ③ 不可逆で、git revert のように戻せない ④ タスクが少なく、できる人が独占しがち、の 4 つです。

    Q8. 動画のロードマップで、EC2 → ECS と進む理由を説明してください。

    EC2（仮想マシン）でインフラの手触り感を得たあと、そのつらさ（全台分のサーバー管理、リソース割り当ての硬さ、属人性）を ECS（コンテナ）が解決するからです。ECS ではタスク定義と Dockerfile で構成を静的に管理し、タスクを使い捨てにするので属人性が構造的に排除され、コンテナ時代のお作法が身につきます。
