    50 スケーリング・負荷分散

    CDNによる負荷軽減

    CDN は、世界中のサーバー（エッジ）にコンテンツのコピーを置き、本来のサーバー（オリジン）に届くリクエストそのものを減らす仕組みです。このページでは、エッジ・オリジン・キャッシュヒット率 の考え方、何をキャッシュしてよいか、キャッシュキー とパージ、オリジン保護と DDoS 対策としての側面、Shop の画像と JS を CloudFront に載せる構成を解説します。

    もとにしたノート：61_サーバー・インフラ/50_スケーリング・負荷分散/04_CDNによる負荷軽減

    ひとことで言うと

    CDN は「サーバーを増やす」のではなく 「サーバーに届くリクエストを減らす」、最も安くて効果の大きい手段です。ハッシュ付きの静的ファイルは長期、公開 API は短い TTL でキャッシュし、個人データは絶対にキャッシュしない。オリジンは CDN 経由でしか入れないように守ります。

    1.CDN とは：コンビニの例え

    CDN（Content Delivery Network：コンテンツ配信網） は、本店の商品を全国の コンビニに置いておく 仕組みです。お客さんは遠くの本店まで行かず近所のコンビニで買えるので速く、本店の行列もなくなります。コンビニに在庫がないときだけ本店から取り寄せます。

    用語意味例え
    オリジン（Origin）本来のサーバー（Shop の ALB や S3）本店
    エッジ（Edge／PoP）世界中にある CDN のサーバーコンビニ
    キャッシュヒットエッジに在庫があり、オリジンに行かずに返せたコンビニに在庫があった
    キャッシュヒット率全リクエストのうちヒットした割合。これが高いほどオリジンの負荷が減る取り寄せずに済んだ割合

    スケーリングの観点では、CDN は「サーバーを増やす」（スケーリングの基本、オートスケーリング）のではなく 「サーバーに届くリクエストを減らす」 最も安くて効果の大きい手段です。

    2.CDN の仕組み

    なぜ速く・軽くなるのか：

    1. 距離が近い：利用者の近くのエッジが返すので往復時間（RTT）が短い。TLS ハンドシェイク（暗号通信を始めるためのやり取り）もエッジで完結
    2. オリジンに届かない：ヒット率 95% なら、オリジンに来るのは 20 回に 1 回だけ
    3. 帯域を肩代わり：画像や動画など大きなデータの転送を CDN が担う。オリジンのネットワーク帯域とデータ転送料が減る

    エッジが「どれくらいの間キャッシュしてよいか」は、オリジンが返す Cache-Control ヘッダーで決まります。max-age、s-maxage、private、no-store などヘッダーの意味は HTTPキャッシュと圧縮 で詳しく扱っているので、ここでは CDN 側の設計に絞ります。

    3.何をキャッシュするか

    種類例キャッシュ方針
    ファイル名にハッシュ付きの静的アセットapp.3f9a1c.js、style.8b2e.css1 年など 長期キャッシュ。中身が変わればファイル名が変わるので、古いものが残っても困らない
    画像商品画像 /images/products/123.webp長め（数日〜）。差し替えるときはファイル名を変えるかパージ
    HTMLトップページ短め（数十秒〜数分）か、キャッシュしない。ログイン状態で内容が変わるなら キャッシュしない
    公開 API の一部GET /products（商品一覧）、GET /categories数秒〜数十秒の 短い TTL でも、セール時のアクセス集中を劇的に減らせる
    個人データ・更新系GET /me、/cart、POST /orders絶対にキャッシュしない。Cache-Control: private, no-store

    ハッシュ とは、ファイルの中身から計算した短い文字列です。中身が 1 文字でも変わると別の値になるので、ファイル名に入れておけば「中身が変わった＝名前が変わった」になります。TTL はキャッシュしてよい時間です。

    個人情報のキャッシュ事故

    ログイン中の利用者向けページを誤って CDN にキャッシュすると、他人のマイページや住所が別の人に表示される 事故が起きます。CDN 側の設定で「Cookie や Authorization ヘッダーがあるリクエストはキャッシュしない」「API は既定でキャッシュ無効、許可したパスだけキャッシュ」という 安全側の既定 にしてください。キャッシュからの情報漏洩は 72 競合状態とキャッシュ でも扱っています。

    4.キャッシュキーとパージ

    4.1 キャッシュキー（Cache Key）

    エッジが「同じものか」を判定する鍵です。既定は ホスト名 + パス が中心で、クエリ文字列・ヘッダー・Cookie をどこまで含めるかを設定します。

    含めすぎる

    ?utm_source=... や Cookie の違いで別物扱いになり、ヒット率が激減 する。

    含めなさすぎる

    ?page=2 と ?page=1 が同じ扱いになり、違う内容が返る。

    良い例（商品一覧 API）
  キャッシュキー = Host + Path + クエリ(page, category, sort のみ)
  → utm_* などの計測用パラメータは無視
  → Cookie・Authorization はキーに含めず、そもそも転送しない

    CloudFront では「キャッシュポリシー」でキャッシュキーと TTL を、「オリジンリクエストポリシー」でオリジンに転送する値を分けて管理します。キーに含めたものはオリジンにも転送されますが、転送するだけでキーに含めないことも可能です。

    4.2 パージ（Purge／Invalidation）

    エッジのキャッシュを期限前に消すことです。

    # CloudFront：商品画像を差し替えたのでキャッシュを無効化
aws cloudfront create-invalidation \
  --distribution-id E1234567890ABC \
  --paths "/images/products/123.webp"
    • 全消し（/*）は簡単ですが、直後にオリジンへリクエストが殺到する（キャッシュスタンピード）ので注意
    • CloudFront の無効化は月 1,000 パスまで無料、それ以上は有料です（2026 年時点）
    • 理想は パージに頼らない設計：ファイル名にハッシュやバージョンを付ける（app.3f9a.js、123.webp?v=2 ではなく 123-v2.webp）
    • Fastly や Cloudflare（Enterprise）には、関連するキャッシュをまとめて消せる サロゲートキー／キャッシュタグ があります（例：商品 123 に関するページ・API を一括パージ）

    5.オリジン保護と DDoS 対策

    5.1 オリジンを CDN 経由に限定する

    CDN を置いても、オリジンに直接アクセスできてしまっては意味がありません。

    仕組み内容
    OAC（Origin Access Control）CloudFront から S3 へのアクセスを署名付きにし、S3 バケットは CloudFront 経由のみ 許可する。S3 を公開しなくて済む（旧方式 OAI の後継）
    オリジンシールド（Origin Shield）エッジとオリジンの間にもう 1 段の集約キャッシュ層を置く。世界中のエッジのミスが 1 か所にまとまり、オリジンへのリクエストがさらに減る
    ALB を CDN 経由のみにALB のセキュリティグループで CloudFront のマネージドプレフィックスリストだけ許可し、さらにカスタムヘッダー（秘密の値）を CloudFront から付けて ALB のルールで検査する。CloudFront の VPC オリジンを使えば ALB をプライベートサブネットに置ける
    Cloudflare Tunnel などオリジンから CDN へ外向きに接続し、オリジンの受信ポートを開けない方式

    セキュリティグループ は AWS のサーバー単位のファイアウォール（通信の許可・拒否の設定）です。通信制御の考え方は ファイアウォールとネットワーク制御 を参照してください。

    5.2 DDoS の防波堤

    DDoS（Distributed Denial of Service：大量のアクセスでサービスを止める攻撃） に対して、CDN は巨大な防波堤になります。

    • 世界中のエッジに分散した大容量のネットワークで攻撃トラフィックを吸収する
    • L3/L4 の攻撃（SYN フラッドなど）は CDN 側で落とされ、オリジンに届かない（CloudFront には AWS Shield Standard が追加料金なしで付く）
    • L7 の攻撃（大量の HTTP リクエスト）には WAF（Web Application Firewall） のレート制限ルールを CDN に付ける
    • キャッシュヒットするリクエストは、攻撃であってもオリジンに届かない

    ただし、キャッシュされない API（検索・ログイン）を狙われるとオリジンに届くので、WAF のレート制限とオートスケーリングの最大台数（オートスケーリング）で守ります。セキュリティ全般は 71 セキュリティ基礎（特に ネットワークと端末の防御）を参照してください。

    6.主要 CDN と Shop の構成

    6.1 主要な CDN

    CDN特徴（2026 年時点）
    Amazon CloudFrontAWS（S3・ALB・ACM・WAF）との統合が強い。OAC、Origin Shield、CloudFront Functions／Lambda@Edge
    CloudflareDNS と一体で手軽、無料プランあり。DDoS 対策が強く、Workers でエッジ処理
    Fastly設定変更とパージが非常に速い（秒単位）。サロゲートキーによる細かいパージ。大手メディアで実績
    Akamai最古参で最大級のネットワーク。大企業・金融・動画配信

    6.2 Shop の CloudFront 構成

    Shop では AWS を使っているので CloudFront を選び、1 つのディストリビューション（CloudFront の配信設定の単位）でパスごとにオリジンを分けます。

    ビヘイビア（パスパターン）オリジンキャッシュ
    /assets/*S3（OAC）1 年。ビルド時にハッシュ付きファイル名で出力
    /images/*S3（OAC）7 日。差し替えは別ファイル名で
    /api/products*ALB30 秒。クエリ page・category・sort だけキーに含める
    /api/*ALBキャッシュ無効（AWS 管理の CachingDisabled ポリシー）。Cookie・Authorization を転送
    既定 *ALBHTML は短い TTL、またはキャッシュ無効

    デプロイ時に JS を S3 に置く例です。

    # ハッシュ付きアセットは長期キャッシュ
aws s3 sync ./dist/assets s3://shop-static/assets \
  --cache-control "public, max-age=31536000, immutable"

# index.html はキャッシュさせず、毎回新しいアセット名を参照させる
aws s3 cp ./dist/index.html s3://shop-static/index.html \
  --cache-control "no-cache"

    効果を確かめる

    レスポンスヘッダーの X-Cache: Hit from cloudfront／Miss from cloudfront や Age でヒットを確認できます。CloudFront のレポートでキャッシュヒット率を定期的に見て、低いパスはキャッシュキーの設計を見直しましょう。

    なお、CloudFront で使う証明書は us-east-1（バージニア北部）リージョンの ACM 証明書です（証明書の話は HTTPSとTLS証明書）。CDN 自体もエッジ側で冗長化された仕組みです（高可用性と冗長化）。

    7.よくある誤解・つまずき

    誤解実際
    CDN は画像や動画のためだけのもの公開 API の短い TTL キャッシュでも、セール時のオリジン負荷を大きく減らせます。
    キャッシュキーに全部のクエリと Cookie を含めれば安全ヒット率がほぼ 0 になり、CDN の意味がなくなります。必要な値だけを含めます。
    更新したらパージすればいい全パージはオリジンへの殺到を招きます。ファイル名にハッシュを付けてパージ不要にするのが基本です。
    CDN を置いたからオリジンは安全オリジンの IP や ALB の DNS 名に直接アクセスされると素通りです。OAC・セキュリティグループ・カスタムヘッダーで CDN 経由に限定します。
    ログイン後のページも CDN に載せれば速くなる他人の個人情報を返す事故の原因になります。個人向けは private, no-store です。

    8.まとめ

    • CDN はエッジにコピーを置き、オリジンに届くリクエストそのものを減らす。ヒット率が鍵
    • ハッシュ付き静的アセットは長期、画像は長め、公開 API は短い TTL、個人データはキャッシュしない
    • キャッシュキーは必要最小限の値だけ。パージに頼らずファイル名で世代管理する
    • OAC やセキュリティグループでオリジンを CDN 経由に限定し、オリジンシールドでさらに保護する
    • CDN は DDoS の防波堤。L7 攻撃には WAF のレート制限を組み合わせる
    • Shop は CloudFront でパスごとに S3 と ALB を振り分ける

    9.理解度チェック

    Q1. 商品一覧 API に CDN を設定したところ、キャッシュヒット率が 2% しかありません。考えられる原因は何でしょうか。

    キャッシュキーにすべてのクエリ文字列（utm_source など計測用パラメータ）や Cookie を含めているため、利用者ごとに別物扱いになっている可能性があります。キーに含めるのを page・category・sort など内容に影響する値だけにします。

    Q2. JS ファイルを app.js という固定名で 1 年キャッシュしたところ、デプロイしても古い JS が使われ続けます。どう直すべきですか。

    ビルド時にファイル名へ内容のハッシュを付け（app.3f9a.js）、HTML 側はキャッシュさせない（no-cache）ようにします。新しいデプロイでは HTML が新しいファイル名を参照するので、パージせずに切り替わります。

    Q3. S3 に置いた商品画像を CloudFront で配信しています。S3 バケットを公開設定にしないためには何を使いますか。

    OAC（Origin Access Control）を使い、S3 のバケットポリシーで「この CloudFront ディストリビューションからのアクセスだけ許可」とします。S3 のブロックパブリックアクセスは有効のままにできます。

    Q4. ヒット率 95% のとき、オリジンに届くリクエストは何回に 1 回ですか。CDN でオリジンの負荷が下がる理由を 3 つ挙げてください。

    20 回に 1 回です。理由は、① 利用者の近くのエッジが返すので往復時間が短く TLS もエッジで完結する、② ヒットしたリクエストはオリジンに届かない、③ 画像や動画など大きなデータの転送を CDN が肩代わりし、オリジンの帯域とデータ転送料が減る、の 3 つです。

    Q5. GET /me や /cart を CDN でキャッシュするとどんな事故が起きますか。どう設定すべきですか。

    ある利用者のマイページやカートの内容がキャッシュされ、別の人に表示される個人情報漏洩が起きます。Cache-Control: private, no-store を返し、CDN 側でも「Cookie や Authorization があるリクエストはキャッシュしない」「API は既定でキャッシュ無効、許可したパスだけキャッシュ」という安全側の既定にします。

    Q6. 画像を差し替えたので /* を全部パージしました。何が起きる恐れがありますか。

    エッジのキャッシュが一斉に消え、直後にオリジンへリクエストが殺到するキャッシュスタンピードが起きる恐れがあります。差し替えたパスだけを無効化するか、そもそも 123-v2.webp のように別ファイル名にしてパージに頼らない設計にします。

    Q7. CDN を置いたのに、攻撃者が ALB の DNS 名に直接アクセスしてきました。どう防ぎますか。

    ALB のセキュリティグループで CloudFront のマネージドプレフィックスリストだけを許可し、さらに CloudFront から秘密のカスタムヘッダーを付けて ALB のルールで検査します。CloudFront の VPC オリジンを使えば ALB をプライベートサブネットに置くこともできます。
