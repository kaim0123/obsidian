    10 サーバーの基礎

    仮想化とクラウド

    1 台の物理サーバーを複数の「仮想的なコンピューター」に区切る 仮想化 と、それを巨大な規模でインターネット越しに貸す クラウド の仕組みを解説します。ハイパーバイザ（Type 1 / Type 2）、VM とコンテナの違い、IaaS / PaaS / SaaS / FaaS と責任共有モデル、オンプレミスとクラウドの比較と「クラウドの裏側」、主要クラウドの対応サービス、リージョンと AZ、VPS という選択肢までを扱い、発展として仮想スイッチと VRF、補足としてデータセンターの構成も整理します。

    もとにしたノート：10_サーバーの基礎/03_仮想化とクラウド、10_サーバーの基礎/仮想化の仕組み（直也テック）、10_サーバーの基礎/クラウド vs オンプレ。何で動いている？AWS・GCP・Azureの裏側の技術を徹底解説（IT技術屋のボヤキ）

    ひとことで言うと

    仮想化は 「1 軒の大きな家をシェアハウスに区切る」 技術です。物理サーバー 1 台は性能が高すぎて、アプリ 1 つでは 10% くらいしか使い切れないことがよくあります。そこで 1 台を複数の仮想マシンに区切って貸し出すのが仮想化で、その大家さんを API で操作でき、使った分だけ払えるようにしたのが クラウド です。クラウドは「抽象化」、オンプレは「制御」。どちらが新しい・古いではなく、目的に応じて選びます。

    1.仮想化は「シェアハウス」

    • 仮想マシン（VM: Virtual Machine）：ソフトウェアで作られた「部屋」。中で別々の OS が動き、互いに干渉しません
    • ハイパーバイザ（hypervisor）：物理の CPU・メモリ・ディスクを切り分けて各 VM に配る「大家さん」
    • クラウド：その大家さんを API で操作でき、使った分だけ払える仕組み

    2.仮想化とハイパーバイザ

    2.1 なぜ仮想化するのか

    かつては「メールは Windows、Web は Linux、DB は UNIX」と 1 アプリ 1 台（計 3 台）で、サーバーの性能が高いため 3 台とも 10% 程度しか使われず、どの機械もほとんど遊んでいました。そこで 3 台分を 1 台にまとめる。これが 仮想化、つまりハードウェアをソフトウェアで模倣する技術です。

    中に作られる各マシンが 仮想マシン（VM） で、VM はソフトウェア上のコンピューターです。VM ごとに別の OS を動かせ、互いに干渉せず、利用者からは実サーバーと区別がつきません。VM を動かすソフトウェアが ハイパーバイザ で、たとえば「メール用 VM に CPU 2 個とメモリを割り当て」、そこに OS とアプリを入れれば完成です。仮想化すると次の利点があります。

    • 集約：3 台分を 1 台にまとめ、電気代・設置スペース・購入費を削減（1 台分で済む）
    • 可搬性：VM の実体は ファイル（ディスクイメージ） なので、コピー・バックアップ・別マシンへの移動ができます。丸ごと持ち運べ、壊れても別マシンで再起動できます
    • 速さ：機械を買って届くのを待たずに、数分で新しいサーバーを作れます
    • 隔離：ある VM がクラッシュしても他の VM には影響しません

    2.2 Type 1 と Type 2

    Type 1（ベアメタル型）Type 2（ホスト型）
    置き場所ハードウェアの上に 直接（OS なし）Windows / macOS などの OS の上にアプリとして
    速さ間に OS がないので速いホスト OS を経由する分、オーバーヘッドがある
    用途データセンター・クラウド（データセンターの標準）手元の PC で別 OS を試す
    例VMware ESXi、Microsoft Hyper-V、Xen、AWS Nitro HypervisorVirtualBox、VMware Workstation、Parallels

    KVM はどっち？

    Linux カーネルに組み込まれた KVM（Kernel-based Virtual Machine） は、「Linux 自体がハイパーバイザになる」ので Type 1 とも Type 2 とも説明されます。境界は曖昧になってきており、実務では「クラウドの VM は Type 1 系のハイパーバイザで動いている」と押さえれば十分です。AWS の Nitro も KVM をベースにした軽量ハイパーバイザです。

    CPU コア数より VM の vCPU 合計が多くても動くのは、ハイパーバイザが 時間を細かく区切って順番に少しずつ実行 し、同時に動いているように見せているからです。逆に言えば、混み合った物理マシン上の VM は 他人の VM の負荷の影響を受けることがある（noisy neighbor 問題：うるさい隣人問題）、というのが VPS や安いクラウドインスタンスの性能がブレる理由です。

    3.VM とコンテナの違い

    コンテナ（container） も「区切って動かす」技術ですが、区切り方が違います。

    観点VMコンテナ
    区切る単位ハードウェアを仮想化。OS ごと丸ごとOS の中でプロセスを隔離
    カーネルVM ごとに別々ホストのカーネルを共有
    起動時間数十秒〜数分（OS が起動する）数秒以下（プロセスが起動するだけ）
    サイズGB 単位MB〜数百 MB
    隔離の強さ強い（別カーネル）VM より弱い（カーネルの脆弱性は全コンテナに影響）
    別 OSLinux の上で Windows も動くLinux カーネル上では Linux コンテナのみ

    コンテナは Linux カーネルの namespace（見える範囲を分ける） と cgroups（使えるリソース量を制限する） という機能で実現されています。実務では「VM の上でコンテナを動かす」組み合わせが普通で、クラウドの Kubernetes もノード（コンテナを載せるマシン）は VM です。詳しくは 53_コンテナの「Dockerとは」「09-Docker」「10-Kubernetes」のノートを参照してください。

    4.IaaS / PaaS / SaaS / FaaS と責任共有モデル

    クラウドのサービスは「どこまで事業者が面倒を見てくれるか」で分類されます。ピザで例えると、IaaS は「キッチンを借りて自分で作る」、PaaS は「生地と窯は用意されていて具を載せるだけ」、SaaS は「出来上がったピザを食べるだけ」です。

    分類正式名借りるもの自分がやること例
    IaaSInfrastructure as a Service仮想マシン・ネットワーク・ディスクOS の更新、ミドルウェア、アプリ、データEC2、Compute Engine、Azure VM
    PaaSPlatform as a Serviceアプリ実行環境アプリのコードと設定、データElastic Beanstalk、App Engine、Azure App Service、Heroku
    FaaSFunction as a Service関数の実行環境関数のコードLambda、Cloud Run functions、Azure Functions
    SaaSSoftware as a Service完成したソフト使い方・アカウント・データの管理Gmail、Slack、Salesforce

    4.1 責任共有モデル

    クラウドでは「セキュリティの責任」を事業者と利用者で分担します。AWS はこれを「クラウドの セキュリティ（事業者）」と「クラウドにおける セキュリティ（利用者）」と表現しています。

    担当範囲IaaS（EC2）マネージド DB（RDS）FaaS（Lambda）SaaS
    データ・アクセス権利用者利用者利用者利用者
    アプリケーション利用者―利用者事業者
    ミドルウェア・DB利用者事業者事業者事業者
    OS のパッチ利用者 ★事業者事業者事業者
    仮想化・物理・施設事業者事業者事業者事業者

    ★ が重要

    EC2 や VPS を選んだら、OS のセキュリティ更新は自分の仕事 です。「クラウドだから安全」ではありません。一方で、どの形態でも データとアクセス権（誰が何を触れるか）は常に利用者の責任 です。S3 を公開設定にして情報漏えい、という事故はこの部分です。

    5.オンプレミス vs クラウド

    オンプレミス（on-premises、略してオンプレ） は、自社でサーバーを買ってデータセンターや社内に置く方式です。

    観点オンプレミスクラウド
    初期費用大きい（機器購入、設置）ほぼゼロ
    継続費用減価償却・保守・電気・人件費。長く使うほど割安になりやすい従量課金。大規模・長期だと高くつくことも
    調達速度数週間〜数か月数分
    増減難しい（ピークに合わせて買う必要）API で即座に増減
    コントロールハード・ネットワークまで自由抽象化されており裏側には触れない
    運用負担ハード故障対応・電源・冷却まで自前物理層は事業者任せ
    向いている例低遅延必須（工場・金融の一部）、規制で外に出せないデータ、負荷が一定で大規模スタートアップ、負荷の変動が大きいサービス、まず試したいとき

    動画「クラウド vs オンプレ。何で動いている？AWS・GCP・Azureの裏側の技術を徹底解説」では、この違いを 「クラウド＝抽象化、オンプレ＝制御」 とまとめています。どちらが新しい・古いではなく、目的に応じた選択です。両方を組み合わせる ハイブリッドクラウド も一般的です。以下、この動画の内容を紹介します。

    5.1 クラウドは何の言語で動いているか

    • クラウドも結局はプログラム、しかも異常なほど巨大なプログラムです。内部で使われる言語は大きく 3 系統：C++、Java もしくは C#、Rust や Go などのモダン言語
    • Python はインタプリタ言語（実行しながら翻訳する言語）で速度・メモリ効率が弱く、クラウドの根幹にはほぼ使われません。基盤はネットワーク制御・仮想化・巨大データのストリーミング処理・超高速のスケジューリングなど性能がシビアな領域ばかりなので、高速・安全・低レベルに強い言語が選ばれます
    • AWS の内部では C と Java が長く使われ、最近は Rust が強くなっています。Google のインフラは C++、Microsoft Azure は C と C++ が中心です
    • クラウドは「低レイヤーの塊」です。「Lambda 便利」の裏では C++ や Rust が徹底した速度最適化をしています

    5.2 クラウドの裏側で働く AI

    • サーバー故障の予兆検知、ディスクの健康状態のスコアリング、エラーログの自動解析、負荷予測によるサーバー自動増減、ネットワークの異常判定などを AI が常時チェックしています
    • 普通のデータセンターとは規模が桁違いで人間には見きれないため、クラウドは AI なしでは回らない 世界です。壊れる前に兆候を見つけて予備サーバーへ流すことで、全体の安定性を保っています
    • ただし AI がすべてを解決するわけではなく、クラウドにも弱点があります。その弱点がオンプレを選ぶ理由につながります

    5.3 オンプレの 3 つの強み

    1. 物理的なコントロール権

    ハード・電源・ネットワークを自分で選び、自分の判断で触れます。クラウドは抽象化されていて裏側に触れず、触れないことは時に大きな制約になります。

    2. コスト構造が明確

    クラウドは便利ですが、長期・大規模になるほど高くつきます。オンプレは最初に投資する分、使い続けるほど安くなります。

    3. 低遅延が必要なシステムに強い

    工場システム、研究施設、金融の一部など、遅延が少しでも許されない世界では、物理的に近いオンプレに勝てません。

    • オンプレは古い技術ではなく 適所 の問題です。クラウドとオンプレは優劣ではなく用途の違いです
    • オンプレにはネットワーク設定・仮想化・サーバー構築・ストレージ管理・電源冷却の理解・セキュリティポリシー運用など幅広いスキルが必要です。クラウドはクリックで済む部分を肩代わりしてくれますが、オンプレはすべての責任を自分で持ちます。大変ですが、その分コントロールは最大です
    • オンプレでもログ監視・故障予兆検知・トラフィック分析で AI が使われ始めています（クラウドの考え方がオンプレに降りてきている）。ただし AI を活用するにも人手が必要で、クラウドほど自動化は進んでいません

    動画のまとめ

    クラウドは AI と巨大資本によるインフラ、オンプレは 人間の技術と判断によるインフラ で、どちらにも価値があります。本質的な違いは「クラウド＝抽象化、オンプレ＝制御」。新しいから良い、古いから悪いではなく、目的に合った選択をするのが最も賢い判断です。

    6.2 リージョンとアベイラビリティゾーン（AZ）

    • リージョン（Region）：地理的に離れた拠点。例：東京 ap-northeast-1、大阪 ap-northeast-3。リージョン同士は独立しており、リソースは自動ではコピーされません
    • アベイラビリティゾーン（AZ: Availability Zone）：1 つのリージョンの中にある、互いに隔離された複数の拠点（1 つ以上のデータセンター群）。例：ap-northeast-1a。電源・ネットワークが独立しているので、1 つの AZ が停電しても他は動き続けます

    選び方の基本：

    • リージョンは ユーザーに近い場所（日本向けなら東京）、加えて法規制（データの国外持ち出し）や料金で選びます
    • 本番で止められないなら、サーバーを 複数 AZ に分散 します（マルチ AZ）。1 AZ に全部置くと、その AZ の障害で全停止します（→ 50-5 高可用性と冗長化）
    • 地震などの広域災害まで考えるなら、別リージョンにバックアップを置きます（69_SRE・インシデント対応の「DR訓練とRTO・RPO」のノートを参照）

    7.VPS という選択肢

    VPS（Virtual Private Server） は、仮想化された 1 台を 月額固定料金 で借りるサービスです。

    VPSクラウド VM（EC2 等）
    料金月額固定（数百円〜）、通信量込みが多い従量課金。通信量（特に外向き）にも課金
    機能サーバー 1 台＋簡単なファイアウォールロードバランサー・マネージド DB・IAM など周辺サービスが豊富
    増減プラン変更（再起動が必要なことも）API で数分、オートスケールも可能
    向いている個人開発、学習、小規模サイト本番サービスで成長が見込まれるもの
    例さくらの VPS、ConoHa VPS、Xserver VPS、DigitalOcean、Linode(Akamai)、Amazon LightsailEC2、Compute Engine、Azure VM

    Shop をどこで動かすか：学習や最初の公開なら、VPS または EC2 の小さなインスタンス 1 台で十分です。料金が読みやすい VPS は「請求額が怖い」初心者に向いています。DB 分離やロードバランサー、オートスケールまで進むなら、周辺サービスが揃ったクラウドに乗っておくと後が楽です。どちらを選んでも 中身は Ubuntu の Linux サーバー なので、次の 10-4 Linuxサーバーの基本 の内容はそのまま使えます。

    クラウドの課金事故に注意

    クラウドは「作ったまま忘れた」リソースにも課金されます。学習用アカウントでは 予算アラート（AWS Budgets など）を最初に設定 し、使い終わったインスタンス・ディスク・Elastic IP は削除しましょう。

    8.よくある誤解・つまずき

    ✕ よくある誤解◯ 実際は
    コンテナは軽量な VMコンテナは「隔離されたプロセス」で、ホストのカーネルを共有する。VM とは隔離の仕組みも強さも違う
    クラウドに載せればセキュリティは事業者が守ってくれるIaaS では OS のパッチ・ファイアウォール設定・アクセス権は利用者の責任（責任共有モデル）
    クラウドは常にオンプレより安い負荷が一定で大規模・長期なら、オンプレや VPS の方が安いことも多い。クラウドの価値は「速さ」と「増減の柔軟さ」
    1 つのリージョンに置けば冗長化されている1 つの AZ に全部置くと、その AZ の障害で止まる。冗長化はマルチ AZ にして初めて意味がある
    サーバーレスにすれば運用はゼロOS 管理は不要になるが、権限設定・タイムアウト・コールドスタート・コスト監視などの運用は残る

    9.発展：仮想化（ハイパーバイザー・仮想スイッチ・コンテナ・VRF）

    ここまでの内容を、ハイパーバイザーの 2 つのタイプ、仮想スイッチ、VM とコンテナの比較、ネットワーク機器の仮想化である VRF まで広げて整理します。

    9.1 サーバの仮想化とハイパーバイザー

    9.2 VM 同士の通信と仮想スイッチ

    VM 同士や VM と外部の通信には、ハイパーバイザーの中の 仮想スイッチ（vSwitch） が使われます。各 VM の仮想 NIC（vNIC）が仮想スイッチのポートにつながり、仮想スイッチが物理 NIC（アップリンク）を通じて物理スイッチにつながります。仮想スイッチでも VLAN（1 台のスイッチを論理的に複数のネットワークに分ける技術）を設定でき、物理スイッチとの間は トランク（1 本の線で複数の VLAN を運ぶ接続）にするのが一般的です。VLAN の詳細は 11_コンピューターサイエンスの「24スイッチングとVLAN」のノートを参照してください。

 │          物理NIC                    │
 └──────────────┼─────────────────────┘
                │ トランク（複数VLAN）
           [物理スイッチ]

    9.3 コンテナ

    コンテナ は、ホスト OS のカーネルを共有 し、アプリケーションとその実行に必要なもの（ライブラリ・設定など）だけをまとめて、互いに分離して動かす仕組みです（構造は 3 章の図 と同じです）。

    項目仮想マシン（VM）コンテナ
    仮想化するものハードウェアOS（アプリケーションの実行環境）
    OSVM ごとに完全なゲスト OS を持つゲスト OS を持たず、ホスト OS のカーネルを共有
    サイズ大きい（GB 単位）小さい（MB 単位）
    起動時間数十秒〜数分数秒
    分離の強さ強いVM より弱い
    動作基盤ハイパーバイザーDocker などのコンテナエンジン（ハイパーバイザーは必須ではない）
    管理ツールvCenter などKubernetes（オーケストレーション：多数のコンテナの配置・管理）

    まとめ：VM＝重いが分離が強い、コンテナ＝軽くて速い。

    9.4 VRF

    VRF（Virtual Routing and Forwarding） は、1 台のルータの中でルーティングテーブル（宛先ごとの道順表）を複数に分け、仮想的に複数のルータとして動かす技術です。「L3 版の VLAN」のようなものです。

    • インターフェースを どの VRF に所属させるか を設定します
    • VRF ごとにルーティングテーブルが独立 しているので、VRF が違えば 同じ IP アドレス範囲（例：10.0.0.0/24）を使っていても互いに干渉しません
    • 用途：通信事業者が複数の顧客を 1 台のルータで収容する（MPLS VPN）、管理用の通信を業務用の通信から分離する（管理 VRF）
                ┌───────────── Router ─────────────┐
 顧客A ─── Gi0/1 ┤ VRF CUST-A のルーティングテーブル │
 10.0.0.0/24     │   10.0.0.0/24 → Gi0/1           │
                 ├────────────────────────────────┤
 顧客B ─── Gi0/2 ┤ VRF CUST-B のルーティングテーブル │
 10.0.0.0/24     │   10.0.0.0/24 → Gi0/2           │   ← 同じアドレスでも衝突しない
            └──────────────────────────────────┘

    設定と確認の例（Cisco ルータ）：

    Router(config)# vrf definition CUST-A
Router(config-vrf)# address-family ipv4
Router(config-vrf-af)# exit-address-family
Router(config)# vrf definition CUST-B
Router(config-vrf)# address-family ipv4
Router(config-vrf-af)# exit-address-family

Router(config)# interface gigabitethernet0/1
Router(config-if)# vrf forwarding CUST-A          ! IPアドレスより先にVRFを指定
Router(config-if)# ip address 10.0.0.1 255.255.255.0
Router(config)# interface gigabitethernet0/2
Router(config-if)# vrf forwarding CUST-B
Router(config-if)# ip address 10.0.0.1 255.255.255.0   ! 同じアドレスでもエラーにならない

Router# show ip route vrf CUST-A
Routing Table: CUST-A
...
C        10.0.0.0/24 is directly connected, GigabitEthernet0/1
L        10.0.0.1/32 is directly connected, GigabitEthernet0/1

Router# ping vrf CUST-A 10.0.0.10

    紛らわしい技術：

    技術何を分ける・何をするか分野
    VRFL3：ルーティングテーブルを分けるネットワーク基礎
    VLANL2：ブロードキャストドメインを分ける（ルーティングテーブルは分けない）ネットワークアクセス
    NATアドレスを変換するIP サービス
    HSRPデフォルトゲートウェイを冗長化する（FHRP）IP 接続
    ロードバランサ複数のサーバに通信を振り分けて負荷分散するネットワーク基礎

    9.5 ひっかけポイント・よくある誤解

    • コンテナを「VM を動かすソフト」と考える誤り。 VM を動かすのはハイパーバイザー。コンテナは OS のカーネルを共有してアプリを分離する仕組みです
    • 「コンテナごとに完全なゲスト OS を持つ」は誤り。 それは VM の特徴です
    • 「コンテナはハイパーバイザーがなければ動作しない」は誤り。 コンテナエンジン（Docker など）の上で動き、ハイパーバイザーは必須ではありません
    • タイプ1とタイプ2の取り違え。 ハードウェア上で直接動く＝タイプ1（ベアメタル型）。OS の上でアプリとして動く＝タイプ2
    • VRF と VLAN の混同。 VLAN は L2 の分割でルーティングテーブルは分けません。ルーティングテーブルを分けるのは VRF です
    • VRF を NAT・HSRP・ロードバランサと混同しない。

    9.6 押さえておくポイント

    • ハイパーバイザー タイプ1＝ベアメタル型（例：VMware ESXi）、タイプ2＝ホスト型
    • VM 同士の通信は仮想スイッチ（vSwitch）
    • コンテナ＝ホスト OS のカーネルを共有、軽量・高速起動、Docker などで動く、Kubernetes で管理
    • VM＝ゲスト OS を持つ、重いが分離が強い
    • VRF＝1 台のルータでルーティングテーブルを分ける（L3 版 VLAN）、アドレスが重複してもよい

    10.補足：データセンター

    サーバーが実際に置かれる施設であるデータセンターの構成・種類・設備・評価指標と、クラウドとの関係を扱います。データセンター（Data Center） とは、サーバーやネットワーク機器などの IT 機器を安全かつ効率的に運用するための専用施設のことです。企業の重要なデータやシステムを 24 時間 365 日安定して稼働させるための物理的な基盤となります。

    10.1 データセンターの基本構成

    物理的構造

    • 建物：耐震性、耐火性を備えた専用建物
    • フロア：サーバーラックを配置する広いフロア
    • ラック：サーバー機器を収納する金属製の棚
    • ケージ：複数のラックをまとめた区画

    主要設備

    1. サーバーラック：IT 機器を収納・管理
    2. ネットワーク機器：スイッチ、ルーター、ファイアウォール
    3. 電源設備：UPS（無停電電源装置）、発電機
    4. 空調設備：精密空調、冷却システム
    5. 監視設備：セキュリティカメラ、センサー

    10.2 データセンターの種類

    種類特徴メリットデメリット
    1. 企業内データセンター自社専用のデータセンター完全な制御、カスタマイズ性高コスト、専門知識が必要
    2. コロケーション（Colo）他社のデータセンター内に自社機器を設置インフラ管理不要、コスト削減物理的アクセス制限
    3. クラウドデータセンタークラウドプロバイダーが運営初期費用不要、スケーラビリティ月額費用、カスタマイズ制限

    10.3 データセンターの重要な機能

    1. 電源管理

    • UPS（無停電電源装置）：停電時の電源供給
    • 発電機：長時間停電時の電源確保
    • 冗長化：複数の電源系統による信頼性向上

    2. 冷却・空調

    • 精密空調：サーバーの適切な温度・湿度管理
    • ホットアイル・コールドアイル：効率的な空気循環（ラックの吸気側と排気側の通路を分ける）
    • 冷却効率：PUE（Power Usage Effectiveness）の最適化

    3. セキュリティ

    • 物理的セキュリティ：入退室管理、監視カメラ
    • 論理的セキュリティ：ファイアウォール、暗号化
    • アクセス制御：生体認証、IC カード認証

    4. ネットワーク

    • 高速回線：複数の通信事業者との接続
    • 冗長化：複数の回線による信頼性向上
    • CDN：コンテンツ配信の最適化

    10.4 データセンターの評価指標

    1. 可用性（Availability）

    • 稼働率：99.9%（8.76 時間/年の停止）
    • Tier 分類：Tier I〜IV による信頼性レベル
    • SLA：サービスレベル合意による保証

    2. 効率性（Efficiency）

    • PUE：電力使用効率（1.0 に近いほど効率的）
    • 冷却効率：空調システムの最適化
    • スペース効率：ラック密度の最適化

    3. スケーラビリティ

    • 拡張性：必要に応じた容量増加
    • 柔軟性：多様なニーズへの対応
    • 将来性：新技術への対応能力

    10.5 データセンターの運用

    日常運用

    • 監視：24 時間 365 日のシステム監視
    • メンテナンス：定期点検・更新作業
    • バックアップ：データの定期的なバックアップ
    • ログ管理：アクセス・エラーログの記録・分析

    災害対策

    • BCP（事業継続計画）：災害時の事業継続
    • DR（災害復旧）：バックアップサイトでの復旧
    • 冗長化：地理的に分散したデータセンター

    10.6 クラウド時代のデータセンター

    パブリッククラウド

    • AWS：Amazon Web Services
    • Azure：Microsoft Azure
    • GCP：Google Cloud Platform
    • 特徴：共有リソース、従量課金

    プライベートクラウド

    • 特徴：専用リソース、高いセキュリティ
    • 用途：金融機関、政府機関
    • メリット：完全な制御、カスタマイズ性

    ハイブリッドクラウド

    • 特徴：パブリックとプライベートの組み合わせ
    • メリット：柔軟性、コスト最適化
    • 用途：段階的なクラウド移行

    10.7 データセンターの将来

    新技術の導入

    • エッジコンピューティング：データセンターの分散化
    • AI/ML：運用の自動化・最適化
    • 5G：高速通信の実現
    • 量子コンピューティング：次世代計算技術

    環境への配慮

    • グリーンデータセンター：環境負荷の削減
    • 再生可能エネルギー：太陽光・風力発電の活用
    • カーボンニュートラル：CO2 排出量の削減

    データセンターは現代のデジタル社会を支える重要なインフラです。サーバーやネットワーク機器を安全かつ効率的に運用するための物理的な基盤として、電源、冷却、セキュリティ、ネットワークなどの様々な機能を統合的に提供しています。クラウドサービスの普及により、データセンターの重要性はさらに高まっており、今後の技術発展とともに進化し続けています。

    11.まとめ

    • 仮想化は 1 台の物理マシンをハイパーバイザで区切り、複数の VM を動かす技術。VM の実体はファイルで、集約・可搬性・復旧のしやすさが利点。クラウドの土台
    • ハイパーバイザには Type 1（ハード直上、データセンター向け）と Type 2（OS 上、手元 PC 向け）がある
    • コンテナはホストのカーネルを共有するので軽くて速いが、隔離は VM より弱い
    • IaaS → PaaS → FaaS → SaaS の順に事業者の担当が広がる。IaaS では OS パッチは自分の責任
    • クラウド＝抽象化、オンプレ＝制御。優劣ではなく用途で選ぶ
    • リージョンは場所、AZ はリージョン内の独立した拠点。本番はマルチ AZ が基本
    • 学習・小規模なら VPS、成長と周辺サービスを見込むならクラウド VM

    12.理解度チェック

    Q1. VM とコンテナの最も本質的な違いは何ですか？

    カーネルを共有するかどうか です。VM はそれぞれが自分の OS（カーネル）を持ちますが、コンテナはホスト OS のカーネルを共有し、namespace と cgroups でプロセスを隔離しているだけです。そのため起動が速く軽量な反面、隔離の強さは VM に劣ります。

    Q2. Shop を EC2 で動かしていたところ、OS の脆弱性を突かれて侵入されました。責任共有モデルでは、これは誰の責任ですか？

    利用者（自分）の責任 です。EC2（IaaS）ではゲスト OS の更新・パッチ適用は利用者の担当です。AWS が責任を持つのはハイパーバイザ・物理サーバー・データセンターなど「クラウドそのもの」のセキュリティです。

    Q3. Shop の API サーバー 2 台を同じ AZ に置いています。何が問題で、どう直すべきですか？

    その AZ で停電やネットワーク障害が起きると 2 台とも同時に止まり、冗長化の意味がありません。API サーバーを 別々の AZ（例：1a と 1c）に配置 し、ロードバランサーで振り分けます。

    Q4. ハードウェア上で直接動くハイパーバイザーはタイプ1・タイプ2のどちらですか？VirtualBox はどちらですか？

    ハードウェア上で直接動くのは タイプ1（ベアメタル型） で、VMware ESXi などがあり、データセンターの標準です。VirtualBox は Windows や Mac などのホスト OS の上でアプリとして動く タイプ2（ホスト型） です。

    Q5. 物理コアが 4 つしかないマシンで、vCPU 合計 8 個分の VM が動くのはなぜですか？そのとき起こりうる問題は？

    ハイパーバイザが時間を細かく区切り、順番に少しずつ実行して同時に動いているように見せているからです。そのぶん、混み合ったマシンでは他の VM の負荷の影響を受けて性能がブレることがあります（noisy neighbor 問題）。

    Q6. オンプレミスがクラウドより向いているのはどんな場合ですか？

    ハード・電源・ネットワークまで自分で制御したい場合、負荷が一定で大規模・長期に使う（使い続けるほど安くなる）場合、工場・研究施設・金融の一部のように低遅延が必須の場合、規制でデータを外に出せない場合などです。

    Q7. VRF と VLAN の違いを説明してください。

    VLAN は L2 でブロードキャストドメインを分ける技術で、ルーティングテーブルは分けません。VRF は L3 で 1 台のルータの中のルーティングテーブルを分ける技術で、VRF が違えば同じ IP アドレス範囲を使っても干渉しません。

    Q8. 「サーバーレスにすれば運用はゼロ」は正しいですか？

    正しくありません。OS 管理は不要になりますが、権限設定・タイムアウト・コールドスタート・コスト監視などの運用は残ります。また、どの形態でもデータとアクセス権は利用者の責任です。
