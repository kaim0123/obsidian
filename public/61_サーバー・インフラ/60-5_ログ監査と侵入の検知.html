    60 サーバー・ネットワークセキュリティ

    ログ監査と侵入の検知

    ここまでのページは「鍵を掛ける」話でした。このページは 防犯カメラと警報装置 の話です。セキュリティの観点で見るべきログ（auth.log / journal、sudo、Nginx アクセスログ）と読み方、ログを別サーバーへ送る理由、auditd・AIDE による操作記録と改ざん検知、侵入の兆候と初動（隔離・証拠保全）、クラウドの監査ログ（CloudTrail・GuardDuty）、そして Shop セキュリティチェックリストをまとめます。

    もとにしたノート：61_サーバー・インフラ/60_サーバー・ネットワークセキュリティ/05_ログ監査と侵入の検知

    ひとことで言うと

    どれだけ鍵を固くしても、100% 侵入を防ぐことはできません。大切なのは 記録が残っている（誰が・いつ・何をしたか）、異常にすぐ気づける（警報が鳴る）、気づいたときに慌てず動ける（初動の手順がある）ことです。侵入から発覚までの期間が長いほど被害は大きくなるので、防御と同じくらい「検知」に投資します。

    このページは 60-1 サーバーセキュリティの基本 〜 60-4 OSのハードニングとパッチ管理 を読んでいると理解しやすいです。何をログに出すか・ログの守り方の一般論は 71 セキュアな運用とログ出力、SIEM などの監視の考え方は 71 セキュリティ監視とツール で扱っています。

    1.見るべきログ

    1.1 認証ログ：auth.log と journal

    SSH のログイン、sudo の実行、ユーザーの追加などは 認証ログ に残ります。Ubuntu 24.04 では rsyslog（ログを書き出す仕組み）により /var/log/auth.log に書かれ、同じ内容を journalctl（systemd のログ置き場 journal を見るコマンド）でも見られます。

    # SSH ログインの成功（誰が、どこから、どの鍵で）
sudo grep "Accepted" /var/log/auth.log
# Accepted publickey for taro from 198.51.100.24 port 50122 ssh2: ED25519 SHA256:abc...

# 失敗（ボットの総当たりはここに大量に出る）
sudo grep -E "Failed|Invalid user" /var/log/auth.log | tail

# journal で SSH サービスのログを見る
sudo journalctl -u ssh --since today

# ログイン履歴（成功）と失敗の履歴
last -n 20
sudo lastb -n 20

    注目すべきは「失敗」ではなく「成功」

    失敗はボットの日常ですが、見覚えのない IP・時間帯・鍵での成功 は侵入そのものかもしれません。鍵の フィンガープリント（SHA256:...、鍵ごとの指紋のような短い値）を見れば、どの鍵が使われたかが分かります（60-2 SSHの安全な運用 で鍵にコメントを付けたのはこのためです）。

    1.2 sudo のログ

    sudo の実行は、誰がどのコマンドを root 権限で実行したかの記録です。

    sudo journalctl _COMM=sudo --since "2026-10-01"
# taro : TTY=pts/0 ; PWD=/home/taro ; USER=root ; COMMAND=/usr/bin/systemctl restart nginx

    root で直接ログインさせず、個人ユーザー + sudo にしたのは、この記録を残すためでもあります（60-4 OSのハードニングとパッチ管理）。

    1.3 Nginx のアクセスログ

    Web 経由の攻撃は Nginx のアクセスログ（/var/log/nginx/access.log）に表れます。

    # 秘密ファイルや管理画面を探すリクエスト
sudo grep -E '\.env|\.git/|wp-login|phpmyadmin' /var/log/nginx/access.log | tail

# リクエスト数の多い IP 上位 10
sudo awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head

# 4xx/5xx の急増
sudo awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c

    /.env へのリクエストに 200 を返していたら大問題です（秘密情報が漏れている）。404 なら探られただけです。アプリへの攻撃の見分け方は 72 Web脆弱性対策 も参照してください。

    1.4 ログの一覧

    ログ場所主に分かること
    認証/var/log/auth.log、journalctl -u sshSSH ログイン成否、ユーザー追加、sudo
    システム全般journalctl、/var/log/syslogサービスの起動・停止・異常終了
    Web/var/log/nginx/access.log, error.log攻撃的なリクエスト、不審な IP
    パッケージ/var/log/apt/history.log、/var/log/dpkg.log誰がいつ何をインストールしたか
    自動更新/var/log/unattended-upgrades/パッチ適用の状況
    ファイアウォールjournalctl -k | grep UFWブロックされた通信

    2.ログを別サーバーへ送る理由

    侵入した攻撃者が最初にやることの 1 つは、自分の痕跡をログから消すこと です。root を取られれば、同じサーバー上のログは自由に書き換えられます。だからログは リアルタイムでサーバーの外へ送り、攻撃者の手が届かない場所に保管します。

    別サーバーへ送る利点は次のとおりです。

    • 改ざん対策：サーバー側のログが消されても、送信済みの記録は残る
    • 横断的な検索：API 2 台・DB・LB のログをまとめて時系列で追える
    • アラート：「root でのログイン成功」「authorized_keys の変更」などをルール化して通知できる
    • サーバーが消えても残る：オートスケーリングで削除されたインスタンスのログも残る

    送信には rsyslog の転送機能、CloudWatch Agent、Fluent Bit、Grafana Alloy などを使います。集約基盤の設計は 66_可観測性の「ログ集約基盤」、監視全般は同じく「サーバー監視とログ管理の基本」のノートを参照してください。保管先には S3 の オブジェクトロック のような「一定期間削除できない」設定を使うと、さらに改ざんに強くなります。

    3.auditd と AIDE：操作の記録と改ざんの検知

    3.1 auditd：カーネルレベルの操作記録

    auditd（Linux Audit）は、カーネルが「どのファイルに誰がアクセスしたか」「どの システムコール（プログラムが OS に仕事を頼む窓口）が呼ばれたか」を記録する仕組みです。auth.log では分からない、重要ファイルの変更 を記録できます。

    sudo apt install auditd
    # /etc/audit/rules.d/shop.rules
# アカウント情報の変更を監視（w=書き込み, a=属性変更）
-w /etc/passwd -p wa -k identity
-w /etc/shadow -p wa -k identity
-w /etc/group -p wa -k identity
# sudo 設定と SSH 設定の変更
-w /etc/sudoers -p wa -k privilege
-w /etc/sudoers.d/ -p wa -k privilege
-w /etc/ssh/sshd_config -p wa -k sshd
-w /etc/ssh/sshd_config.d/ -p wa -k sshd
# 管理者の authorized_keys
-w /home/taro/.ssh/authorized_keys -p wa -k ssh_keys
    sudo augenrules --load            # ルールを読み込む
sudo auditctl -l                  # 有効なルールを確認
sudo ausearch -k identity -i      # キーで検索（-i で UID を名前に変換）
sudo aureport --summary           # 集計レポート

    最初から大量のルールを入れるとログが膨れるので、上のような「変更されたら重大なファイル」から始めます。CIS Benchmarks にも推奨ルールの一覧があります（60-4 OSのハードニングとパッチ管理）。

    3.2 AIDE：ファイル改ざん検知

    AIDE（Advanced Intrusion Detection Environment）は、正常な状態のファイルのハッシュ値を記録しておき、定期的に比較して変化を検出する ツールです。ハッシュ値 はファイルの中身から計算する指紋のような値で、1 バイトでも変わると別の値になります。攻撃者が /usr/bin/ls や /usr/sbin/sshd を バックドア（こっそり出入りするための裏口）入りのものに差し替えても、ハッシュが変わるので気づけます。

    sudo apt install aide
sudo aideinit                    # 初期データベースを作成（時間がかかる）
# 作成された /var/lib/aide/aide.db が「正しい状態」の基準になる

sudo aide --check --config /etc/aide/aide.conf    # 現在の状態と比較
    AIDE found differences between database and filesystem!!
Changed entries:
f   ...    .C... : /usr/sbin/sshd

    Ubuntu のパッケージでは日次チェックの仕組みも用意されています。注意点は、パッケージ更新でも当然ファイルは変わる ことです。正当な更新の後はデータベースを更新し（aideinit で作り直す）、「説明できない変化」だけを調べる運用にします。また基準のデータベースが同じサーバー上にあると攻撃者に書き換えられうるため、コピーを外部に保管しておくと確実です。

    4.侵入の兆候と初動

    4.1 こんなときは疑う

    兆候確認方法
    CPU が理由なく 100% に張り付く（マイニング）top、ps aux --sort=-%cpu
    見知らぬプロセス・/tmp や /dev/shm から動く実行ファイルps aux、ls -la /tmp /dev/shm
    知らない外部 IP への大量の通信ss -tnp、クラウドの VPC フローログ
    authorized_keys に知らない鍵、知らないユーザーcat ~/.ssh/authorized_keys、/etc/passwd
    見覚えのない cron・systemd ユニットcrontab -l、ls /etc/cron.*、systemctl list-timers
    知らない IP・時間帯の SSH ログイン成功auth.log の Accepted
    AIDE / auditd の想定外の変更検知前章のコマンド

    4.2 初動の流れ

    慌ててサーバーを消したり再起動したりしてはいけない

    侵入を疑ったときに 最もやってはいけないのは、慌ててサーバーを消したり再起動したりすること です。メモリ上の証拠（動いているプロセス、通信先）が失われ、何が起きたか分からなくなります。

    1. エスカレーション：侵入の疑いを検知したら、責任者・チームに連絡し、記録を開始します。
    2. 隔離：インバウンド・アウトバウンドともに全拒否の「隔離用 SG」に付け替え、ロードバランサーから外します。攻撃者の操作と外部への通信（データ流出・他への攻撃）を止めつつ、サーバーは動かしたまま（電源は切らない） にします。冗長構成なら Shop のサービスは残りの台で継続できます（50-5 高可用性と冗長化）。
    3. 証拠保全：EBS スナップショット（ディスクの丸ごとコピー）を取り、ps・ss の結果、ログを外部へ退避します。集約基盤にログを送っていれば、ここで大いに役立ちます。
    4. 認証情報の無効化：そのサーバーにあった秘密情報は すべて漏れた前提 で、SSH 鍵・DB パスワード・API キー・IAM アクセスキーを失効・作り直し（ローテーション）します（30-5 設定と環境変数・シークレット）。
    5. 復旧：侵入されたサーバーを「掃除して使い続ける」のではなく、クリーンなイメージから作り直す のが原則です。どこにバックドアが残っているか完全には分からないからです。侵入経路を塞いでから公開します。IaC でサーバーを作れるようにしておくことが、ここで効いてきます（40-2 IaCとは）。
    6. 振り返り：原因・経路・再発防止策をまとめます。

    個人情報が漏えいした可能性がある場合は、法令に基づく報告や利用者への通知が必要になることがあるため、早い段階で責任者に判断を仰ぎます。インシデント対応の体制・コミュニケーション・ポストモーテム（事後の振り返り）は 69_SRE・インシデント対応、手順書の作り方は同じく「ランブックの書き方」のノートを参照してください。この初動手順を事前にランブック（手順書）として書いておく ことが、本番で慌てないための最大の準備です。インシデント対応の一般論は 71 セキュアな運用とログ出力 にもあります。

    5.クラウドの監査ログ：CloudTrail と GuardDuty

    クラウドでは、サーバーの中だけでなく クラウドの操作そのもの も攻撃対象です。漏れたアクセスキーで EC2 を大量に起動される、SG を書き換えて DB を公開される、といった攻撃はサーバーのログには一切残りません。

    サービス役割ポイント
    AWS CloudTrail「誰が・いつ・どの API を呼んだか」の記録管理イベントは既定で 90 日分をイベント履歴で閲覧可能。長期保管にはトレイルを作成して S3 へ保存し、ログファイルの整合性検証を有効にする
    Amazon GuardDutyCloudTrail・VPC フローログ・DNS ログなどを分析する脅威検知サービス有効化するだけで動く。「EC2 が SSH 総当たりを受けている／している」「暗号資産マイニングのドメインと通信」などを検出
    VPC フローログVPC 内の通信の記録（誰と誰が通信したか）侵入後の外部通信の調査に使う
    AWS Configリソース設定の変更履歴「いつ SG が開けられたか」を追える
     
    # 例：最近 SG を変更した操作を CloudTrail で探す
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=EventName,AttributeValue=AuthorizeSecurityGroupIngress \
  --max-results 10

    GuardDuty の検出結果（finding）は EventBridge 経由で Slack やメールに通知できます。小規模な Shop でも、CloudTrail のトレイル作成・GuardDuty の有効化・ルートアカウントの MFA は最初の日にやっておく価値があります。

    6.Shop セキュリティチェックリスト

    サーバーセキュリティのまとめとして、Shop を公開・運用する際のチェックリストをまとめます。

    6.1 公開前（構築時）

    • ☐ SSH は公開鍵認証のみ（PasswordAuthentication no）、PermitRootLogin no、AllowUsers 設定済み（60-2）
    • ☐ SSH は管理者の IP だけに許可、または SSM Session Manager でポート 22 を閉じている
    • ☐ ufw / SG で外に開いているのは 80・443（と制限付きの 22）だけ（60-3）
    • ☐ Shop API（3000）と PostgreSQL（5432）は 127.0.0.1 かプライベートサブネットでのみ待ち受け
    • ☐ Docker の公開ポートに 127.0.0.1: を付けている
    • ☐ 外部から nmap して、80/443 以外が open でないことを確認した
    • ☐ HTTPS 化と HTTP→HTTPS リダイレクト（20-4）
    • ☐ アプリは専用ユーザー（nologin）で動作、.env は 600（60-4、30-5）
    • ☐ DB のアプリ用ユーザーは必要最小限の権限（30-6）
    • ☐ 不要なサービス・パッケージを削除、sudo はコマンドを限定
    • ☐ 構成は Ansible / Terraform でコード化されている（40-4、40-3）

    6.2 継続運用

    • ☐ unattended-upgrades が有効、/var/run/reboot-required を監視し計画的に再起動
    • ☐ OS・Node.js・PostgreSQL・Nginx の EOL を把握している
    • ☐ fail2ban が動作している
    • ☐ ログ（auth・sudo・Nginx）を集約基盤へ転送し、重要イベントにアラートを設定（66_可観測性「ログ集約基盤」）
    • ☐ auditd で重要ファイルの変更を記録、AIDE で改ざんを定期チェック
    • ☐ CloudTrail トレイル・GuardDuty 有効、ルートアカウントに MFA
    • ☐ 四半期ごとに authorized_keys・ユーザー・sudo・SG の棚卸し、Lynis で再診断
    • ☐ バックアップを取り、リストアを試している（69_SRE・インシデント対応「DR訓練とRTO・RPO」）
    • ☐ 侵入時の初動手順がランブックになっている（69_SRE・インシデント対応「ランブックの書き方」）

    アプリケーション自体の脆弱性（SQL インジェクション、XSS など）は 72 Web脆弱性対策、ログインやセッションの設計は 73 認証認可 と 74 セッション管理 で確認してください。

    6.3 よくある誤解・つまずき

    ✕ 誤解◯ 実際
    ログはサーバーに残っているから大丈夫root を取られればローカルのログは消されます。リアルタイムで外部に送って初めて証拠になります。
    侵入されたらすぐ電源を切るメモリ上の証拠が失われます。まずネットワークで隔離し、スナップショットなどで証拠を保全してから対処します。
    怪しいファイルを消せば元通りバックドアがどこに残っているか分かりません。認証情報を全部替え、クリーンなイメージから作り直すのが原則です。
    ログイン失敗が多いのが一番危ない失敗はボットの日常です。本当に注目すべきは見覚えのないログイン「成功」です。
    クラウドの操作はサーバーのログで追えるSG の変更や EC2 の起動は CloudTrail にしか残りません。クラウドの監査ログは別途有効化が必要です。

    7.まとめ

    • 見るべきは auth.log / journal（特に見覚えのないログイン成功）、sudo の記録、Nginx アクセスログ
    • ログは改ざん対策のためリアルタイムで別サーバーへ送り、アラートを設定する
    • auditd で重要ファイルへの操作を記録し、AIDE でシステムファイルの改ざんを検知する
    • 侵入を疑ったら「隔離 → 証拠保全 → 認証情報の無効化 → クリーンな再構築 → 振り返り」。電源を切らない、掃除して使い続けない
    • クラウドでは CloudTrail と GuardDuty でクラウド操作そのものを監査する
    • セキュリティは構築時のチェックと継続運用の両輪。チェックリストとランブックで仕組み化する

    8.理解度チェック

    Q1. Shop の API サーバーの auth.log に、深夜 3 時に海外の IP から Accepted publickey for deploy という行がありました。まず何を確認しますか？

    ログの鍵フィンガープリント（SHA256:...）から、どの鍵が使われたかを確認し、その鍵の持ち主や CI など正当な利用か確かめます。説明がつかなければ侵入の可能性が高いので、責任者に連絡し、サーバーの隔離・証拠保全の初動に移ります。集約基盤のログで、その後に実行された sudo や他サーバーへのログインも追います。

    Q2. 侵入されたサーバーで、攻撃者が /var/log/auth.log を消していました。どうすれば侵入の経緯を調べられたでしょうか？

    ログをリアルタイムでログ集約基盤（CloudWatch Logs など別の場所）に転送していれば、消される前の記録が残っています。さらに、保管先を削除不可の設定にしておく、auditd の記録も転送する、CloudTrail や VPC フローログといったサーバー外の記録を組み合わせることで経緯を再構成できます。

    Q3. GuardDuty から「EC2 インスタンスが暗号資産マイニングに関連するドメインと通信している」という検出結果が届きました。インスタンスをすぐ終了（削除）するのはなぜ良くないのですか？

    終了するとメモリ上のプロセスや通信状況、ディスクの状態といった証拠が失われ、侵入経路や被害範囲が分からなくなります。まず隔離用 SG に付け替えて外部通信を止め、EBS スナップショットやログを保全してから、認証情報の無効化とクリーンなイメージからの再構築を行います。

    Q4. AIDE が /usr/sbin/sshd の変更を報告しました。ただし直前に unattended-upgrades で openssh-server が更新されています。どう判断しますか？

    パッケージ更新でもファイルは当然変わるので、apt のログ（/var/log/apt/history.log）で正当な更新か確認します。説明がつけば AIDE のデータベースを作り直し、説明できない変化だけを調べる運用にします。

    Q5. SG が書き換えられて DB が公開されていました。誰がいつ変更したかは、サーバーのどのログを見れば分かりますか？

    サーバーのログには残りません。SG の変更はクラウドの API 操作なので、CloudTrail（AuthorizeSecurityGroupIngress などのイベント）や AWS Config の変更履歴で追います。

    Q6. Nginx のアクセスログで /.env へのリクエストが見つかりました。ステータスコードが 404 と 200 では何が違いますか？

    404 なら探られただけで、ファイルは返していません。200 なら秘密情報が漏れている大問題なので、中の認証情報をすべて無効化・作り直し、公開ディレクトリから .env を外します。
