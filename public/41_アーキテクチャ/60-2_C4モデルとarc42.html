    60 意思決定・文書化

    図と文書化（C4 モデル・arc42）

    アーキテクチャをチーム全員が同じ地図で見るための、図の描き方（C4 モデル）と文書の構成（arc42）を詳しく解説します。C4 の4つのズームレベルと補助図、表記のルールとツール、arc42 の12章に何を書くか、そして ADR と組み合わせる実務の型が分かります。

    もとにしたノート：60_意思決定・文書化/00_解説_意思決定・文書化.md（§4 図解）、00_全体像/00_解説_アーキテクチャ体系.md（§1-1・§3・§6）。個別ノートがないため C4 モデル・arc42 の公式サイトなどで補足

    1.このページで扱うこと

    アーキテクチャは、決めただけではチームに伝わりません。「どこに何があり、どうつながっているか」を全員が同じ地図で見られるようにするのが、図と文書の役割です。このページでは、図の描き方の型である C4 モデルと、文書全体の目次の型である arc42 を詳しく見ていきます。

    テーマこのページで分かること
    図と文書の目的なぜ図だけでは足りないのか、「誰の・どんな関心に答える図か」という考え方
    C4 モデル4つのズームレベル（コンテキスト・コンテナ・コンポーネント・コード）と、補助図（システムランドスケープ・動的図・デプロイ図）
    表記のルールタイトル・凡例・要素の種類・矢印のラベルなど、C4 が推奨するチェックリスト
    ツール作図ツールとモデリングツールの違い、Structurizr・C4-PlantUML などの書き方
    arc4212章それぞれに何を書くか、小さく始めるならどの章か
    組み合わせ方「C4 で描き、arc42 の枠に入れ、決定は ADR で残す」という実務の型

    このテーマにはまだ個別ノートがないため、フォルダの解説ノートと全体解説の該当部分をもとに、C4 モデル・arc42 の公式サイトの内容で詳しく補っています。決定の記録（ADR）そのものは 意思決定の進め方と ADR、図を使ったレビューは アーキテクチャのレビュー観点 で扱います。

    境界の目安

    「どう書くか（Markdown の記法・ドキュメントツール・README 一般）」は 41 外のノート（56_ドキュメント）の担当です。このページは「アーキテクチャの何を、なぜ、どの粒度で残すか」を扱います。

    2.なぜ図と文書が必要か

    図と文書は「チームが同じ地図を見る」ための道具です。口頭やチャットで伝えた構造は人によって解釈がずれ、時間がたつと誰も正確に覚えていない状態になります。アーキテクチャ上の決定は後から変えにくいものなので、その形を目に見える形で残しておく価値は大きいのです。

    「誰の、どんな関心に答えるか」— ISO/IEC/IEEE 42010 の考え方

    アーキテクチャ記述の国際規格 ISO/IEC/IEEE 42010 は、アーキテクチャを「システムの根本的な概念または性質であり、要素・関係・設計と進化の原則に表れるもの」と定義しています。そのうえで、記述のための言葉として次の4つを定めています。

    用語意味具体例
    ステークホルダーシステムに利害を持つ人・組織利用者、経営者、開発者、運用者、監査担当
    関心事（Concern）ステークホルダーが気にしていること「外部のどのシステムとつながるのか」「どこにデプロイされるのか」
    ビューある関心事に答えるための、アーキテクチャの見せ方（図や文書）コンテナ図、デプロイ図
    ビューポイントビューを作るための約束事（何を・どの表記で描くか）「コンテナ図にはコンテナと技術とプロトコルを描く」

    つまり「1枚の図ですべてを説明する」のではなく、読み手と関心事ごとに図を描き分けるのが基本です。C4 モデルのズームレベルも、arc42 の章立ても、この考え方の上に成り立っています。

    図だけではアーキテクチャを説明できない

    『ソフトウェアアーキテクチャの基礎』（Richards & Ford）は、アーキテクチャを 構造・アーキテクチャ特性・アーキテクチャ決定・設計原則 の4つの次元の組み合わせとして捉えます。構造の図は、このうち「構造」しか表しません。

    図で伝えるもの

    構造（どんな部品があり、どうつながるか）。C4 モデルが担当します。

    文書で伝えるもの

    なぜその構造なのか（品質目標・制約）、どう守らせるのか（決定・原則）。arc42 と ADR が担当します。

    この2つを組み合わせて初めて、後から来た人が「この構造を盲目的に受け入れるか、盲目的に変えるか」の二択に陥らずに済みます。

    3.C4 モデルの考え方 — 地図のようにズームする

    C4 モデルは Simon Brown が考案した、ソフトウェアアーキテクチャの図を描くための手法です。名前は4つの階層（Context・Containers・Components・Code）の頭文字から来ています。地図アプリで縮尺を変えるように、全体像から細部へ段階的に拡大して描き分けるのが特徴です。

    C4 は特定の記法（UML など）にも特定のツールにも縛られない、「表記非依存・ツール非依存」の手法とされています。決まっているのは記号の形ではなく、何を抽象化の単位とするかです。

    C4 の5つの抽象

    C4 では、ソフトウェアを次の階層的な「抽象」で捉えます。「ソフトウェアシステムは1つ以上のコンテナでできており、コンテナは1つ以上のコンポーネントを含み、コンポーネントは1つ以上のコード要素で実装される」という入れ子の関係です。

    抽象意味例
    人（Person）システムを使う人。役割・ペルソナ・特定の個人など顧客、店舗スタッフ、管理者
    ソフトウェアシステム利用者に価値を届ける最上位の単位。1チームが責任を持てる程度の範囲EC サイト、決済サービス、メール配信サービス
    コンテナアプリケーションまたはデータストア。システム全体が動くために、動いていなければならない実行の境界Web アプリ、API サーバー、DB、キュー、サーバーレス関数
    コンポーネント1つのコンテナの中にある、インターフェースの裏にまとまった機能のかたまり注文コントローラ、注文サービス、注文リポジトリ
    コードクラス・インターフェース・関数・テーブルなど、実装そのものOrderService クラス、orders テーブル

    「コンテナ」は Docker のコンテナではない

    C4 の「コンテナ」は、コードが実行される、またはデータが保存される実行時の境界のことです。C4 の公式サイトでも、コンテナ技術の普及で「コンテナ＝Docker」と連想されるようになったのは残念だ、と断っています。公式に挙げられている例は次のようなものです。

    • サーバー側の Web アプリケーション（Java EE、ASP.NET、Node.js など）
    • クライアント側の Web アプリケーション（ブラウザで動く JavaScript アプリ）
    • デスクトップアプリ、モバイルアプリ
    • コンソールアプリ・バッチ
    • サーバーレス関数（AWS Lambda、Azure Functions など）
    • データベース、Blob・コンテンツストア（Amazon S3、CDN など）、ファイルシステム
    • シェルスクリプト

    4.C4 の4つのレベルを詳しく

    レベル見せるもの主な読み手公式の推奨
    1. System Context（コンテキスト）対象システムと、利用者・外部システムの関係非技術者も含む全員ほとんどのチームに推奨
    2. Container（コンテナ）Web アプリ、API、DB、キューなど実行・デプロイの単位と、その間の通信開発者・運用者（技術者以外の関係者にも）ほとんどのチームに推奨
    3. Component（コンポーネント）1つのコンテナの中の主要な部品そのコンテナの開発者・アーキテクト価値があるときだけ
    4. Code（コード）クラス図・ER 図など開発者価値があるときだけ

    4つ全部を描く必要はない

    C4 の公式サイトは「4つのレベルすべてを使う必要はなく、価値のあるものだけでよい」と明言しています。実務ではレベル1・2だけで十分なことが多いとされます。レベル3・4はコードの変更のたびに古くなりやすく、描くなら自動生成やモデリングツールの助けを借りるのが現実的です。

    レベル1：システムコンテキスト図

    対象のソフトウェアシステムを中央に1つの箱として置き、その周りに使う人とつながる外部システムを描きます。中身の技術（言語・DB・プロトコル）は描きません。「このシステムは誰のためのもので、何に依存しているのか」を、エンジニア以外も含めた全員が理解できるようにする図です。

    • 範囲：1つのソフトウェアシステム
    • 主な要素：対象システム
    • 補助の要素：人、直接つながる外部システム
    • 使いどころ：プロジェクトの最初の説明、新メンバーのオンボーディング、外部連携の洗い出し

    レベル2：コンテナ図

    システムの箱を「拡大」して、中にあるアプリケーションとデータストアを描きます。各コンテナに使っている技術を書き、コンテナ間の矢印には通信のプロトコル（HTTPS、SQL、AMQP など）を書きます。アーキテクチャの大まかな形と、主要な技術選択が一目で分かる図です。

    このページの全体マップでいえば、40 システム・分散 や 30 フロントエンド構成 が扱う範囲がこのレベルにあたります。

    レベル3：コンポーネント図

    1つのコンテナを「拡大」し、その中の主要なコンポーネント（インターフェースの裏にまとまった機能のかたまり）と、それらの関係を描きます。例えば API サーバーの中にある「注文コントローラ」「注文サービス」「注文リポジトリ」などです。レイヤー や クリーンアーキテクチャ のような 20 アプリ内部構造の話は、このレベルで表現されます。

    コンポーネントの数が多いコンテナでは図がすぐに大きくなり、更新も追いつかなくなりがちです。公式サイトでも「価値があるときだけ」とされており、描く場合はコードから自動で作ることが勧められています。

    レベル4：コード図

    コンポーネントの実装を、UML のクラス図や ER 図などで描くレベルです。通常は手で描かず、IDE やツールで必要なときに自動生成します。特に複雑で重要な部分だけを説明したいときに限って使う、という位置づけです。クラス単位の設計の話は 41 外のノート（42〜44 の設計・パターン系フォルダ）の範囲になります。

    5.補助の図 — ランドスケープ・動的図・デプロイ図

    4つのレベルは「静的な構造」を描くための図です。C4 にはこれを補う3種類の図があります。

    システムランドスケープ図

    組織・部門など、ある範囲に存在する複数のソフトウェアシステムと人の全体像。

    動的図

    ユーザーストーリーやユースケースを実現するために、要素が実行時にどう協調するか。

    デプロイ図

    コンテナがどのインフラに、どう配置されるか。環境（本番・ステージングなど）ごとに描く。

    システムランドスケープ図

    公式サイトによれば、システムランドスケープ図は「特定のソフトウェアシステムに焦点を当てないシステムコンテキスト図」です。企業・組織・部門など、選んだ範囲の中にある人とソフトウェアシステムをすべて並べ、それらがどうつながっているかを示します。

    • 読み手：技術者・非技術者の両方。開発チームの外の人も含む
    • 向いている場面：多数のシステムを抱える大きな組織。エンタープライズアーキテクチャの世界への「橋渡し」になる図とされています
    • コンテキスト図との違い：コンテキスト図は「1つのシステムから見た周辺」、ランドスケープ図は「全システムの地図」

    動的図

    静的な図に描いた要素（ソフトウェアシステム・コンテナ・コンポーネントのどれでもよい）が、ある機能を実現するためにどの順番でやり取りするかを描きます。描き方は2通りあります。

    スタイル描き方向いている場面
    コラボレーション形式要素を自由に配置し、矢印に「1. 2. 3.」と番号を振って順序を示す構造図と同じ配置で、流れを重ねて見せたいとき
    シーケンス形式UML のシーケンス図のように、時間を縦軸にして並べるやり取りの数が多く、順序が重要なとき

    公式には「控えめに使う」ことが推奨されています。すべての機能について描くのではなく、興味深い・繰り返し現れる・やり取りが複雑なパターンに絞ります。たとえば「注文確定時のイベント連携」や「認証のリダイレクトの流れ」などです。arc42 の第6章（ランタイムビュー）に入れる図として最適です。

    デプロイ図

    1つのデプロイ環境（本番、ステージング、開発など）の中で、ソフトウェアシステムやコンテナのインスタンスがどこで動くかを示します。

    要素内容
    デプロイノードソフトウェアが動く場所。物理サーバー・端末、仮想化された基盤（IaaS・PaaS・仮想マシン）、コンテナ化された基盤（Docker コンテナ）、実行環境（DB サーバーなど）。入れ子にできる
    コンテナインスタンスコンテナ図のコンテナが、どのノードにいくつ配置されるか
    インフラノードDNS、ロードバランサー、ファイアウォールなどの補助的な要素

    読み手はアーキテクト・開発者・インフラ担当・運用担当です。AWS や Azure のアイコンを使ってもかまいませんが、その場合も凡例で意味を説明します。ここで初めて「Docker のコンテナ」がデプロイノードとして登場する点に注意してください。C4 のコンテナ（アプリ）は、Docker コンテナ（ノード）の上で動くものという関係です。

    6.表記の推奨 — 図だけで読めるようにする

    C4 は記号の形を決めていない代わりに、「図は説明なしで単独で（おおむね）理解できるべき」という方針と、そのためのチェックリストを示しています。

    対象推奨理由・補足
    図全体タイトルを付け、図の種類と範囲を書く例：「［コンテナ図］EC サイト」。何の図か迷わせない
    凡例（キー）を付ける形・色・枠線のスタイル・線の種類・矢じりの意味を説明する
    要素要素の種類を明記する人／ソフトウェアシステム／コンテナ／コンポーネントのどれか
    短い説明を書く主な責務がひと言で分かるように
    コンテナとコンポーネントには技術を書く例：［コンテナ：Spring Boot］
    関係（線）線は一方向の関係として描く双方向の矢印で曖昧にしない
    線にはラベルを付ける「使う」ではなく「注文 API を呼ぶ」のように、意図と向きが分かる具体的な言葉で
    コンテナ間の通信には技術・プロトコルを書く例：［JSON/HTTPS］、［AMQP］。同期か非同期かもここで分かる
    その他略語は全員が分かるものにするか、凡例で説明するチーム外の人も読む前提で
    色の使い方は図の間で一貫させる色覚の多様性や白黒印刷でも読めるよう、色だけに意味を持たせない

    このフォルダの約束：凡例と日付

    図には必ず凡例（矢印が同期か非同期かなど）と日付を付けます。日付があれば、図が古くなっているかどうかを読み手が判断できます。

    7.ツール — 作図とモデリング

    C4 の公式サイトは、ツールを大きく2種類に分けています。

    作図（Diagramming）

    「箱と線」を描くツール。要素の意味をツールが理解しないので検証がほとんどできず、同じ要素を複数の図で使うにはコピーが必要です。データ形式も差分を見にくいことが多いです。

    例：汎用の作図ツール、ホワイトボード

    モデリング（Modelling）推奨

    図とは別に、要素と関係のモデルを1か所で定義し、そこから複数の図（ビュー）を生成します。要素の名前を変えれば全部の図に反映され、問い合わせや検証もできます。

    例：Structurizr

    Structurizr（モデリング）

    Structurizr は C4 の考案者 Simon Brown による、C4 のためのモデリングツール群です。テキストの DSL でモデルを書き、そこからコンテキスト図・コンテナ図などのビューを生成します。テキストなので、コードと同じリポジトリでバージョン管理し、レビューできます。

    workspace.dsl（イメージ） 
    workspace {
  model {
    customer = person "顧客"
    shop = softwareSystem "EC サイト" {
      web = container "Web アプリ" "画面を表示する" "React"
      api = container "API サーバー" "注文を受け付ける" "Spring Boot"
      db  = container "データベース" "注文と商品を保存する" "PostgreSQL"
    }
    payment = softwareSystem "決済サービス" "外部の決済代行"

    customer -> web "商品を探して購入する" "HTTPS"
    web -> api "注文 API を呼ぶ" "JSON/HTTPS"
    api -> db "注文を読み書きする" "SQL/TCP"
    api -> payment "決済を依頼する" "HTTPS"
  }
  views {
    systemContext shop { include * autolayout lr }
    container shop { include * autolayout lr }
  }
}

    1つのモデルから「コンテキスト図」と「コンテナ図」の2つのビューを作っている点がポイントです。コンテキスト図では shop の中身が隠れ、コンテナ図では中身が展開されます。

    C4-PlantUML（作図をテキストで）

    PlantUML に C4 用のマクロを追加するライブラリです。Person・Container・Rel などのマクロで要素と関係を書きます。モデルは図ごとに書くので厳密には「作図」側ですが、テキストで差分が取れる点は大きな利点です。

    container.puml（イメージ） 
    @startuml
!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Container.puml

title ［コンテナ図］EC サイト

System_Boundary(shop, "EC サイト") {
  Container(web, "Web アプリ", "React", "画面を表示する")
  Container(api, "API サーバー", "Spring Boot", "注文を受け付ける")
  ContainerDb(db, "データベース", "PostgreSQL", "注文と商品")
}
System_Ext(payment, "決済サービス", "外部の決済代行")

Rel(customer, web, "商品を探して購入する", "HTTPS")
Rel(web, api, "注文 API を呼ぶ", "JSON/HTTPS")
Rel(api, db, "注文を読み書きする", "SQL/TCP")
Rel(api, payment, "決済を依頼する", "HTTPS")

SHOW_LEGEND()
@enduml

    そのほかの選択肢

    • Mermaid の C4 図：Markdown の中に書ける Mermaid にも C4 図の構文があります（公式ドキュメントでは実験的な機能とされています）。Obsidian や GitHub で手軽に表示できるのが利点です。
    • 汎用作図ツール：C4 用の図形セットを使えば普通の作図ツールでも描けます。少数の図を手早く描くには十分ですが、図が増えると整合性を保つのが難しくなります。

    選び方の目安

    図が1〜2枚なら、使い慣れたツールで十分です。図が増えてきたら、同じ要素を何度も描かずに済むモデリング（Structurizr など）や、コードと一緒にレビューできるテキスト形式（diagrams as code）に移ると、図が古くなりにくくなります。

    8.このノート群のフォルダと C4 の対応

    41_アーキテクチャのフォルダは、範囲の大きさ（ズームレベル）で分けてあり、C4 の考え方と対応しています。

    ズームC4 のレベル対応するフォルダ
    広い：システムの外と中L1 コンテキストシステムと外部の関係（60 で図にして残す）
    中：プロセス・サービス間L2 コンテナ40 システム・分散、30 フロントエンド構成
    狭い：1つのアプリの中L3 コンポーネント20 アプリ内部構造
    さらに狭い：コードL4 コード41 外のノート（42〜44 の設計・パターン）

    ズームの軸とは別に、横に効くものと時間・人の軸があります。

    • どのレベルでも使う物差し：10 基礎（品質特性・トレードオフ・結合）
    • 全レベルを貫く仕組み：50 横断的関心事（認証・観測性・設定）
    • 決めて残す：60 意思決定・文書化（ADR・C4・arc42。このページ）
    • 時間と人：70 進化と組織（負債・適応度関数・コンウェイ）

    9.arc42 とは — アーキテクチャ文書の目次の型

    arc42 は、2005年から公開されている、技術に依存しない 12章構成のアーキテクチャ文書テンプレートです。Gernot Starke と Peter Hruschka によって作られ、無料で使えます。C4 が「図の描き方」なら、arc42 は「文書全体の構成」です。

    arc42 の考え方は「どこに何を書くかを決めておく」ことにあります。章の置き場所が決まっていれば、書く人は迷わず、読む人は必要な情報をすぐに見つけられます。公式ドキュメントでは、軽量に使う（lean）・しっかり書く（thorough）・最低限これだけは（essential）という観点で、章ごとの書き方のヒントが示されています。

    10.arc42 の12章 — それぞれに何を書くか

    #章中身関連
    1導入と目標要求の要点、品質目標トップ3、ステークホルダー品質特性
    2制約守らなければならない技術・組織・法律上の制約、規約
    3コンテキストとスコープ外部システム・利用者との境界≒ C4 L1
    4解決戦略（ソリューション戦略）中心となるアイデアと方針の要約
    5ビルディングブロックビュー静的な構造を階層的に分解≒ C4 L2・L3
    6ランタイムビュー重要なシナリオでの動きC4 動的図
    7デプロイメントビューインフラと配置C4 デプロイ図
    8横断的コンセプト認証・ログ・エラー処理など、全体に効く仕組み横断的関心事
    9アーキテクチャ決定重要な決定（ADR の一覧）ADR
    10品質要求品質ツリーと品質シナリオ品質特性シナリオ
    11リスクと技術的負債リスク分析の結果、負債の一覧技術的負債
    12用語集ドメイン用語・技術用語

    以下、章ごとに書く内容を詳しく見ていきます（開くと詳細が表示されます）。

    第1章 導入と目標（Introduction and Goals）

    文書を読む人が最初に知るべき「このシステムは何のためにあり、何を大事にするのか」を書きます。

    • 要求の概要：主な機能要求を短く。詳しい要求仕様があるならそこへのリンクでよい
    • 品質目標：アーキテクチャにとって最も重要な品質特性を、優先順位を付けて3つ程度（多くても5つ）挙げる。「性能」「保守性」のような言葉に、具体的な意味を一文添える
    • ステークホルダー：誰がこの文書・システムに関心を持ち、何を期待しているかを表にする（役割・連絡先・期待）

    品質目標は、第10章の品質要求と第4章の解決戦略につながる「アーキテクチャの出発点」です。

    第2章 制約（Architecture Constraints）

    設計者が自由に選べない条件を書きます。ここに書かれたものは、トレードオフの議論の対象外になります。

    • 技術的な制約：使える言語・クラウド・既存システムとの互換性など
    • 組織的な制約：チーム構成、予算、期限、開発プロセス
    • 法律・規制上の制約：個人情報保護、業界の規制、データの保存場所
    • 規約：コーディング規約、命名規則、文書化のルール
    第3章 コンテキストとスコープ（Context and Scope）

    システムの境界を明らかにします。どこまでが自分たちの責任で、どこからが外部かを決める章です。

    • ビジネスコンテキスト：やり取りする相手（利用者・外部システム）と、交換するデータや業務上の意味
    • 技術コンテキスト：外部との接続に使うチャネル・プロトコル・ハードウェア

    ビジネスコンテキストの図は、C4 のシステムコンテキスト図（L1）がほぼそのまま使えます。

    第4章 解決戦略（Solution Strategy）

    アーキテクチャを形作る根本的な判断の要約を短く書きます。詳細は後の章や ADR に任せ、ここでは全体の方針が一望できるようにします。

    • 技術の選択（言語・フレームワーク・DB など）
    • トップレベルの分割方針（どのアーキテクチャスタイル・パターンを使うか）
    • 重要な品質目標をどう達成するか（「品質目標 → 採用した方法」の対応表にすると分かりやすい）
    • 組織上の判断（開発プロセス、外部への委託など）
    第5章 ビルディングブロックビュー（Building Block View）

    システムの静的な構造を、階層的に分解して示します。公式ドキュメントでは、アーキテクチャ文書の中で最も詳しくなることが多い章とされています。

    • レベル1：システム全体を「ホワイトボックス」として開き、中の主要な部品を示す
    • レベル2以降：レベル1の部品のうち重要なものをさらに開く
    • ブラックボックスの説明：各部品の責務とインターフェース（中身は見せない）
    • ホワイトボックスの説明：部品の中の構成と、分割の理由

    レベル1は C4 のコンテナ図、レベル2は C4 のコンポーネント図に対応させると描きやすくなります。

    第6章 ランタイムビュー（Runtime View）

    部品が実行時にどう協調するかを、具体的なシナリオで示します。すべての機能ではなく、アーキテクチャ上重要なものに絞ります。

    • 重要なユースケース・機能の流れ
    • 外部インターフェースとの重要なやり取り
    • 起動・停止などの運用・管理の流れ
    • エラーや例外が起きたときの流れ

    表現にはシーケンス図・アクティビティ図、または番号付きの手順を使います。C4 の動的図がそのまま使えます。

    第7章 デプロイメントビュー（Deployment View）

    システムを動かす技術的なインフラと、そこへのソフトウェアの配置を示します。

    • インフラの構成（サーバー・ネットワーク・クラウドのサービス）。必要なら階層的に詳しくする
    • 第5章のビルディングブロックが、どのインフラ要素に配置されるかの対応
    • 環境ごとの違い（本番・ステージング・開発）

    C4 のデプロイ図がこの章の図になります。

    第8章 横断的コンセプト（Crosscutting Concepts）

    特定の部品に属さず、システム全体に繰り返し現れる仕組みや決まりを書きます。

    • ドメインモデル（業務の主要な概念とその関係）
    • アーキテクチャ・設計のパターン（例：全サービスでヘキサゴナルにする）
    • 技術の使い方のルール
    • 永続化、ユーザーインターフェース、セキュリティ（認証・認可）、エラー処理、ログ・観測性、テストのしやすさ、設定など

    41 の 50 横断的関心事（認証・観測性・設定）がほぼそのままこの章の中身になります。

    第9章 アーキテクチャ決定（Architecture Decisions）

    重要・高コスト・大規模・リスクが高い・意見が分かれた決定を、その理由とともに記録します。他の章に書いた内容と重複させないようにします。

    形式として ADR が適しており、この章には ADR の一覧（タイトル・ステータス・リンク）を並べるのが実務的です。第4章の解決戦略には「要約」を、第9章には「個々の決定の記録」を、という役割分担になります。

    第10章 品質要求（Quality Requirements）

    第1章の品質目標を具体的で測れる形にします。

    • 品質ツリー：「性能 → 応答時間 → 検索は1秒以内」のように、品質特性を木構造で具体化したもの（ATAM の品質特性ユーティリティツリーと同じ考え方）
    • 品質シナリオ：「ピーク時に〜したら、〜以内に〜する」のように、刺激と応答で書く。通常の利用シナリオと、変更シナリオ（「新しい決済手段を追加したら」など）がある

    書き方は 品質特性シナリオと計測 を参照してください。ここで測れる形にした品質は、適応度関数 による自動チェックの対象にもなります。

    第11章 リスクと技術的負債（Risks and Technical Debt）

    既知のリスクと技術的負債を、優先順位を付けて一覧にします。それぞれに、起きたときの影響と、軽減・返済の方針を添えます。

    リスクマトリクスやリスクストーミングの結果（意思決定の進め方と ADR）や、意図的な暫定案の「意図・範囲・期限・直し方」（技術的負債と意図的な暫定案）を置く場所として使えます。

    第12章 用語集（Glossary）

    重要なドメイン用語と技術用語の定義を表にします。関係者が同じ言葉を同じ意味で使えるようにするための章です。複数の言語で開発する場合は訳語も載せます。DDD のユビキタス言語を置く場所としても使えます。

    全部を埋めなくてよい

    arc42 の12章は「置き場所の一覧」であって、すべてを埋めるべきノルマではありません。小さなプロジェクトなら、第1章（目標）・第3章（コンテキスト）・第4章（解決戦略）・第5章（構造）・第9章（決定）だけでも十分に役立ちます。空の章は「まだ書いていない」ことが分かるよう見出しだけ残しておくと、後から足しやすくなります。

    11.C4・arc42・ADR の組み合わせ方

    実務でよく使われるのが、C4 で描き、arc42 の枠に入れ、決定は ADR で残すという組み合わせです。それぞれの得意分野が重ならないので、組み合わせても無駄がありません。

    道具役割答える問いarc42 での置き場
    C4 モデル図の描き方何があり、どうつながっているか第3章（L1）、第5章（L2・L3）、第6章（動的図）、第7章（デプロイ図）
    arc42文書全体の構成どこに何が書いてあるか文書そのもの
    ADR個々の決定の記録なぜそうしたか第9章（一覧）。第4章は要約

    このノート群との対応

    41_アーキテクチャのフォルダ構成も、arc42 の章立てとほぼ対応しています。

    arc42 の章対応するフォルダ・ページ

    小さく始める手順

    1. コンテキスト図を1枚描く（C4 L1）。利用者と外部システムを洗い出すだけで、境界の認識のずれが見つかります。
    2. コンテナ図を1枚描く（C4 L2）。技術とプロトコルを書き、凡例と日付を付けます。
    3. arc42 の見出しだけのファイルを作る。第1・3・4・5・9章から埋め、図はそれぞれの章に貼ります。
    4. 大きな決定が出るたびに ADR を書き、第9章に一覧として足していきます。
    5. レビューのたびに図の日付を確認する。古くなった図は直すか、消します（レビュー観点）。

    図と文書をコードと同じリポジトリ（例：docs/architecture/）に置き、テキスト形式で書いておくと、コードの変更と一緒にレビューでき、古くなりにくくなります。

    12.よくある誤解

    誤解実際
    C4 の「コンテナ」は Docker コンテナのことアプリケーションやデータストアなど「実行時の境界」のこと。Docker コンテナはデプロイ図の「デプロイノード」として現れる
    C4 なら4つのレベルを全部描かなければならない価値があるレベルだけでよい。多くの場合はレベル1・2で十分
    C4 は独自の記号（表記法）を覚える必要があるC4 は表記非依存。記号の形より、タイトル・凡例・種類・技術・ラベルを書くことが大切
    図があればアーキテクチャは説明できる図は「構造」だけ。特性・決定・原則まで含めて初めてアーキテクチャ（Richards & Ford の4次元）
    arc42 は12章すべてを埋めるもの置き場所の一覧であり、小さく始めてよい。第1・3・4・5・9章だけでも役立つ
    arc42 と C4 と ADR はどれか1つを選ぶもの役割が違うので組み合わせて使う。C4 で描き、arc42 に入れ、ADR で決定を残す
    一度描いた図はずっと使える図はすぐに古くなる。日付を付け、コードと一緒に管理し、レビューで確認する

    13.まとめ

    覚えること内容
    図と文書の目的チームが同じ地図を見るため。読み手と関心事ごとに描き分ける（42010 のビューの考え方）
    C4 の4レベルコンテキスト → コンテナ → コンポーネント → コード。地図のようにズームする。まずは L1・L2
    C4 の補助図システムランドスケープ（全システムの地図）、動的図（実行時の流れ）、デプロイ図（インフラへの配置）
    表記タイトル・凡例・要素の種類・説明・技術・一方向の矢印とラベル・プロトコル。日付も付ける
    ツール図が増えるならモデリング（Structurizr）やテキスト形式（C4-PlantUML など）で、コードと一緒に管理する
    arc4212章の文書テンプレート。全部埋めなくてよい。小さくは第1・3・4・5・9章から
    組み合わせC4 で描き、arc42 の枠に入れ、決定は ADR で残す
