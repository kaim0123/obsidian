    50 横断的関心事

    設定・シークレット・フィーチャーフラグ

    3つとも「コードの外から振る舞いを変える」ものですが、変わるタイミングと扱いの厳しさが違います。それぞれの置き場所と管理方法、ドメイン層に漏らさないための層の境界、12-Factor App との対応を、アーキテクチャの観点から整理します。

    もとにしたノート：50_横断的関心事/04設定とシークレットとフィーチャーフラグ.md（＋ 00_解説_横断的関心事.md の該当節）

    1.このページで扱うこと

    アプリケーションは、環境（開発・ステージング・本番）や運用中の判断（機能の ON/OFF）によって振る舞いを変える必要があります。これらも、どの機能にも関わる横断的関心事です。このページでは次の3つを、アーキテクチャの観点から概要レベルで整理します。

    設定（Configuration）

    接続先 URL、タイムアウト、機能パラメータなど

    シークレット（Secrets）

    パスワード、API キー、証明書など

    フィーチャーフラグ（Feature Flags）

    デプロイと機能公開を切り離す仕組み

    CI/CD でデプロイ時に環境変数をどう注入するかといった具体的な手順は（41 外のノート：64_CI-CD／65_リリース・デプロイ）の担当です。ここでは「コードから分離する」という原則と、置き場所の判断までを扱います。

    前提：横断的関心事と認証・認可の境界、BFF・API ゲートウェイ・グレースフルデグレーデーション、依存性のルールとクリーンアーキテクチャ

    2.なぜ横断的関心事なのか

    例影響範囲
    DB 接続文字列ほぼすべての永続化処理
    外部決済 API の URL注文・返金など複数の機能
    「新チェックアウト UI を有効化」フロント・BFF・複数の API

    設定をコードに直書きしたり、リポジトリに秘密情報をコミットしたりすると、環境の追加、鍵のローテーション、インシデント対応が一気に難しくなります。

    3つの違いの早見表

    3つは変わるタイミングと扱いの厳しさが違うため、分けて管理します。

    項目例変わるタイミング典型的な管理
    設定DB の接続先、外部 API の URL、タイムアウトデプロイ時環境変数、設定ファイル
    シークレットパスワード、API キー、署名鍵ローテーション時シークレットマネージャー
    フィーチャーフラグ新機能の ON/OFF、段階リリースの対象割合実行中にもフラグサービス、管理画面

    3.設定（Configuration）

    設定とは、環境やデプロイごとに変わる値のことです。ビジネスロジックそのものではなく、「どこに接続するか」「どれくらい待つか」といったパラメータです。

    3.1 設定の例

    種類例
    インフラDB ホスト、Redis の URL、メッセージキュー名
    外部連携決済・メール・地図 API のエンドポイント
    動作パラメータHTTP タイムアウト、リトライ回数、ページサイズの上限
    環境識別ENV=production、ログレベル

    3.2 設定の置き場所（よくあるパターン）

    設定は複数の場所から読み込まれ、後から読む層ほど前の値を上書きするのが一般的なイメージです。

    方式メリット注意
    環境変数12-Factor App の定番。コンテナと相性がよい数が増えると管理が煩雑
    設定ファイル構造化しやすい。ローカル開発向き環境ごとにファイルを分ける
    専用ストア（AWS SSM Parameter Store、HashiCorp Vault など）集中管理、監査できるインフラに依存する

    3.3 アーキテクチャ上のポイント

    • ドメイン層に環境変数を直接読ませない — クリーンアーキテクチャ の「詳細は外側」に合わせ、インフラ層または Composition Root（起動時の組み立て部分）で読み込み、業務ロジックには値として注入します（DI・IoC・Composition Root）。こうするとテストで値を差し替えやすくなります。
    • 設定スキーマを決める — 起動時に必須項目が欠けていたらすぐに失敗させる（fail fast）。本番で初めて「URL が空だった」と気づくのを防ぎます。
    ✕ ドメインの奥で環境変数を読む 
    class Order {
  canCancel(now: Date) {
    const hours = Number(process.env.CANCEL_LIMIT_HOURS); // ドメインが環境に依存
    ...
  }
}
    ○ 入口で読み、検証し、値として渡す 
    // config.ts（起動時に1回だけ読む・足りなければ起動失敗）
const raw = process.env.CANCEL_LIMIT_HOURS;
if (!raw) throw new Error("CANCEL_LIMIT_HOURS is required");
export const config = { cancelLimitHours: Number(raw) };

// main.ts（Composition Root）
const policy = new CancelPolicy(config.cancelLimitHours);
const useCase = new CancelOrderUseCase(orderRepo, policy);

    3.4 環境の分離

    環境目的
    開発（dev）個人・チームの日常開発
    ステージング（staging）本番に近い構成で結合テスト
    本番（production）実ユーザー向け

    環境の境界を図に書く

    本番の設定を開発に流用しない、本番 DB を開発環境から触らない。こうした境界をアーキテクチャ図に明示すると、事故が減ります。同じビルド成果物を、設定を変えるだけで開発・検証・本番で動かせるのが理想です。

    4.シークレット（Secrets）

    シークレットは、漏洩すると被害が大きい設定です。設定と同じ仕組みで扱うこともありますが、より厳格な管理が求められます。

    4.1 シークレットの例

    • DB のパスワード
    • JWT の署名鍵
    • 外部 API のクライアントシークレット
    • TLS 証明書の秘密鍵

    4.2 やってはいけないこと

    NG 集

    • ✕ ソースコードに API キーを直書きする
    • ✕ .env を Git にコミットする（.gitignore だけに頼りすぎない。一度コミットした秘密は履歴に残るので、消すだけでなく差し替えが必要）
    • ✕ ログにシークレットを出力する
    • ✕ フロントエンド（ブラウザ）に、本来サーバーだけが持つべき秘密を置く（ブラウザに届いた値は誰でも読める）

    4.3 推奨される置き方（概要）

    プラクティス理由
    最小権限必要なサービスだけが読めるようにし、漏洩時の被害範囲を絞る
    ローテーション漏洩時や定期的に、鍵を差し替えられるようにしておく
    コードと分離デプロイパイプラインまたはランタイムで注入する

    認証・認可の境界 と合わせて、JWT の署名鍵などは特に厳重に扱います。署名鍵が漏れると、誰でも正規のトークンを偽造できてしまうからです。

    5.フィーチャーフラグ（Feature Flags）

    フィーチャーフラグ（機能フラグ）は、コードはデプロイ済みだが、機能の ON/OFF を実行時に切り替える仕組みです。「デプロイ（コードを置く）」と「リリース（機能を見せる）」を切り離す道具といえます。BFF・API ゲートウェイ・グレースフルデグレーデーション でも、障害時に機能をリモートで OFF にする例が出てきました。

    5.1 なぜ使うか

    用途説明
    段階的リリース一部のユーザーだけに新 UI を見せる（カナリア、A/B テスト）
    デプロイと公開の分離main にマージしても、フラグが OFF ならユーザーには見えない
    キルスイッチ本番障害時に、問題のある機能だけを即座に OFF にする
    長期ブランチの回避大きな機能を、小さく main にマージし続けられる（トランクベース開発）

    5.2 ざっくりした仕組み

    5.3 アーキテクチャ上の注意

    良い習慣悪い習慣
    フラグは境界（BFF、ユースケースの入口）で評価するドメインのあちこちに if (flag) を書く
    短命にする — 全員 ON になったらフラグを削除するフラグが永久に残り、分岐が増殖する
    フラグ OFF 時のテストも書くON のパスだけテストする
    監視 — フラグの切り替えをログに残す誰がいつ OFF にしたか分からない

    フラグでルールを破らない

    ドメインの不変条件（「締め後は変更不可」など）をフラグで無効化するのは危険です。フラグは振る舞いの選択であり、ルールの破り方ではありません。

    ○ ユースケースの入口で1回だけ評価する 
    // BFF / ユースケース入口
const checkout = flags.isOn("newCheckout", { userId })
  ? newCheckoutFlow
  : legacyCheckoutFlow;
return checkout.execute(cart);

    6.設定・シークレット・フラグの関係

    項目変更頻度典型的な管理
    設定デプロイ時環境変数、設定ファイル
    シークレットローテーション時シークレットマネージャー
    フィーチャーフラグ実行中もフラグサービス、管理 UI

    7.12-Factor App との対応（入口）

    クラウドネイティブな設計では、The Twelve-Factor App の次の原則がよく参照されます。

    • III. 設定（Config） — 設定をコードから厳密に分離し、環境変数に格納する。同じビルド成果物を、設定を変えるだけで開発・検証・本番で動かせるようにする。
    • X. 開発／本番一致（Dev/prod parity） — 開発・ステージング・本番の差をできるだけ小さく保ち、環境差は設定で吸収する。

    ここでは詳細まで扱いませんが、「設定はコードに埋め込まない」はアーキテクチャの基本です。

    8.よくある誤解

    誤解実際
    .env があれば十分本番ではシークレットストアと権限管理が必要なことが多い
    フラグ＝設定ファイルフラグは運用中に切り替える用途が主
    フロントにフラグを置けば安全サーバー側でも検証・制御が必要な機能がある（フロントの判定は利用者が書き換えられる）
    設定はインフラだけの問題層の境界（ドメインに漏らさない）も設計の課題

    9.小さな練習

    1. 自分のプロジェクトで、環境ごとに変わる値を3つ書き出す。
    2. そのうちシークレットに当たるものを分け、今どこに置いているか確認する。
    3. 新機能をフラグで段階公開するなら、どの層で ON/OFF を判定するか決める。

    10.まとめ

    覚えること内容
    設定環境ごとに変わるパラメータ。コードから分離し、入口で読み込んで検証（fail fast）、値として注入する
    シークレット漏れると被害が大きい設定。リポジトリ・ログ・ブラウザに置かず、専用ストア＋最小権限＋ローテーション
    フィーチャーフラグデプロイとリリースを分ける。境界で評価し、短命にし、不変条件は破らない
    層の境界ドメイン層に環境変数やフラグ判定を漏らさない
    12-FactorIII. 設定、X. 開発／本番一致
