    DI・IoC・Composition Root

    「必要な相手を自分で作らず、外から渡してもらう」依存性注入（DI）の基本から、IoC・DIP・DI の違い、最終的に誰が new するのかという Composition Root、アンチパターンのサービスロケーター、ライフタイムと「捕らわれた依存」までを解説します。手動 DI と DI コンテナの使い分けも分かります。

    もとにしたノート：01_依存性注入.md、03_制御の反転とComposition Root.md

    1.このページで扱うこと

    依存性注入（Dependency Injection, DI） は、設計の基本技のひとつです。考え方はとても単純です。

    クラスが必要とする相手（依存先）を、自分で作らず、外から渡してもらう。

    たったこれだけですが、守るだけで テストが書きやすく、差し替えやすい コードになります。ところが、実際にアプリを組み立てようとすると次の疑問が出てきます。

    • 「IoC（制御の反転）」「DIP（依存性逆転）」「DI（依存性注入）」は、どう違うのか
    • コンストラクタで依存を受け取るのはよいが、最終的に誰が new するのか
    • DI コンテナは、アプリの どこで 使えばよいのか
    • 「サービスロケーター」は DI と何が違うのか

    このページでは、前半で DI そのもの（3 つの形・効果・DI コンテナ・コツ）を、後半で次の内容を扱います。

    • IoC・DIP・DI の 3 つの言葉の関係
    • 依存を組み立てる唯一の場所 Composition Root
    • アンチパターンとしての サービスロケーター
    • 依存の ライフタイム（シングルトン・スコープ・トランジェント）と 捕らわれた依存
    • 手動 DI か DI コンテナか の判断

    DIP（依存性逆転の原則）そのものは、前のページ 依存性逆転の原則（DIP） で扱っています。

    2.「依存」とは何か

    クラス A がクラス B のメソッドを呼んでいるとき、A は B に依存している といいます。

    class UserService {
  save(user) {
    const db = new MySQLDatabase(); // ここで B を作っている
    db.insert(user);
  }
}

    この例では、UserService が MySQLDatabase に依存しています。しかも 自分で作っている（new している）ので、両者を切り離せません。テストで偽物の DB を使いたくても、save() の中で本物が作られてしまいます。

    DI は、この「new している場所」を クラスの外へ追い出す 技術です。

    3.DI の 3 つの形

    3.1 コンストラクタ注入（Constructor Injection）— 最も推奨

    コンストラクタで依存を受け取ります。

    class UserService {
  constructor(private db: Database) {} // 外から渡してもらう

  save(user) {
    this.db.insert(user);
  }
}

// 使う側
const service = new UserService(new MySQLDatabase());

    メリット：必須の依存を強制できます（渡さないとオブジェクトが作れない）。作った後に依存が変わらないので、不変に保てます。

    3.2 セッター注入（Setter Injection）

    setter メソッドで依存を渡します。

    class UserService {
  private db: Database;
  setDatabase(db: Database) { this.db = db; }
}

const service = new UserService();
service.setDatabase(new MySQLDatabase());

    デメリット：依存がセットされる前に使われる可能性があります（セットし忘れると、実行時に初めてエラーになる）。

    3.3 メソッド注入（Method Injection）

    個別のメソッドで依存を渡します。

    class UserService {
  save(user, db: Database) {
    db.insert(user);
  }
}

    用途：たまにしか使わない依存を、使うときだけ渡したい場合。

    形渡すタイミング長所短所・注意
    コンストラクタ注入生成時必須の依存を強制、不変、依存が一目で分かる依存が多いと引数が長くなる（＝責務過多のサイン）
    セッター注入生成後いつでも任意の依存や後からの差し替えに対応セット前に使われる危険
    メソッド注入呼び出しごと一時的な依存を、使う場面だけで渡せる呼び出し側が毎回用意する必要がある

    4.DI の効果

    4.1 テストが書きやすい

    class UserService {
  constructor(private db: Database) {}
  save(user) { this.db.insert(user); }
}

// テスト
test('save は DB の insert を呼ぶ', () => {
  const mockDb = { insert: jest.fn() };
  const service = new UserService(mockDb);
  service.save({ id: 1 });
  expect(mockDb.insert).toHaveBeenCalled();
});

    本物の DB を動かさずに テストできます。

    4.2 差し替えが簡単

    // 本番
new UserService(new MySQLDatabase());

// 開発
new UserService(new InMemoryDatabase());

// テスト
new UserService(new MockDatabase());

    4.3 依存関係が明示的

    「このクラスは何を必要としているか」が、コンストラクタを見れば分かります。

    4.4 SOLID 原則との相性

    • DIP（依存性逆転） を実現する手段になる
    • SRP（単一責任）：「部品を作る責務」と「部品を使う責務」を分離できる
    • OCP（開放閉鎖）：既存クラスを変えずに、新しい実装を渡すだけで振る舞いを拡張できる

    5.DI を使わない書き方との比較

    ✕ DI なし 
    class OrderService {
  async placeOrder(input) {
    const orderRepo = new MySQLOrderRepository(); // 直接生成
    const payment = new StripePayment();          // 直接生成
    const mailer = new SendGridMailer();          // 直接生成
    const order = new Order(input);
    await payment.charge(order.total);
    await orderRepo.save(order);
    await mailer.send(input.email);
  }
}
    • テストできない（本物の決済 API やメール API を叩いてしまう）
    • 差し替えられない（Stripe を変えたければ全部書き直し）
    • 依存が隠れている（コードを読まないと何に依存しているか分からない）
    ○ DI あり 
    class OrderService {
  constructor(
    private orderRepo: OrderRepository,
    private payment: PaymentGateway,
    private mailer: Mailer
  ) {}

  async placeOrder(input) {
    const order = new Order(input);
    await this.payment.charge(order.total);
    await this.orderRepo.save(order);
    await this.mailer.send(input.email);
  }
}
    • テスト時はすべてモックに差し替えられる
    • 本番では Stripe や任意の実装を渡せる
    • 何に依存しているかがコンストラクタで一目瞭然

    なお new Order(input) は残っていますが、これは問題ありません。Order は外部とやり取りしないドメインのオブジェクト（エンティティ）なので、差し替える必要がないからです。DI の対象は、外部とつながる部品や差し替えたい部品です。

    6.DI を活かすコツ

    6.1 抽象に依存させる

    // ✕ 具体クラスに依存（差し替え不可）
constructor(private repo: MySQLUserRepository) {}

// ○ インターフェースに依存
constructor(private repo: UserRepository) {}

    外から渡していても、型が具体クラスでは差し替えが困難です。抽象に依存させる理由は 依存性逆転の原則（DIP） を参照してください。

    6.2 依存は少なく保つ

    コンストラクタの引数が 5 個以上 になったら、責任が大きすぎるサイン です（SRP 違反）。クラスを分割できないか検討します。

    6.3 コンストラクタでは依存を受け取るだけ

    重い処理・DB 接続・副作用は、コンストラクタでは やりません。コンストラクタは「部品を受け取って保持する」だけにしておくと、組み立てが速く、予測しやすくなります。

    7.IoC・DIP・DI の違い

    この 3 つは名前が似ていて混同されやすいのですが、レベルの違う概念 です。

    用語種類ひとことで問い
    IoC（Inversion of Control：制御の反転）設計の 考え方（最も広い）「誰が呼び出すか」を逆にする自分のコードがフレームワークを呼ぶのか、フレームワークが自分のコードを呼ぶのか
    DIP（Dependency Inversion Principle：依存性逆転の原則）設計の 原則「依存の矢印の向き」を逆にする上位モジュールが下位モジュールに依存するのか、両方が抽象に依存するのか
    DI（Dependency Injection：依存性注入）実装の テクニック「依存を誰が用意するか」を外に出す自分で new するのか、外から渡してもらうのか

    7.1 IoC —「ハリウッドの原則」

    IoC は 「Don't call us, we'll call you.（こちらから連絡するので、電話してこないでください）」 という ハリウッドの原則 で説明されます。オーディションの後、役者が何度も電話してくるのを断る決まり文句です。

    // 普通の制御：自分のコードが流れを決め、ライブラリを呼ぶ
const input = readline();
const result = calculate(input);
print(result);

// 制御の反転：フレームワークが流れを決め、自分のコードを呼ぶ
app.get("/users/:id", (req, res) => {   // いつ呼ばれるかは Express が決める
  res.json(findUser(req.params.id));
});
    • フレームワークとライブラリの違いは、まさにこの IoC です。ライブラリは自分が呼ぶもの、フレームワークは自分を呼ぶもの です。
    • React のコンポーネント、テストフレームワークの test()、イベントハンドラ、テンプレートメソッドパターンも IoC の例です。

    7.2 DI は IoC の一種

    Martin Fowler は 2004 年の論文「Inversion of Control Containers and the Dependency Injection pattern」で、当時 Java で広まっていた「IoC コンテナ」について、次のように整理しました。

    IoC という言葉は広すぎる。ここで逆転しているのは「依存の用意（組み立て）」の制御なので、Dependency Injection（依存性注入） と呼ぶことにする。

    DI という言葉は、ここから広まりました。

    • 普通は、オブジェクトが 自分で 依存を new する（制御は自分にある）
    • DI では、外の誰か が依存を作って渡す（制御が外に反転している）

    7.3 DIP と DI の関係

    DIP なしDIP あり
    DI なし内部で new MySqlRepo() を直接作るインターフェースに依存しているが、内部で new MySqlRepo() している（逆転が中途半端）
    DI あり具体クラス MySqlRepo を外から受け取る（テストで差し替えにくい）インターフェースを外から受け取る（目指す形）

    DIP が「どちらに依存するか」を決め、DI が「どうやって渡すか」を実現します。クリーンアーキテクチャでは両方が必要です（依存性のルールとクリーンアーキテクチャ 参照）。

    8.Composition Root — 依存を組み立てる唯一の場所

    8.1 「最終的に誰が new するのか」問題

    DI を徹底すると、どのクラスも依存を 受け取るだけ になります。では、最初に new するのは誰でしょうか。

    答えは、Mark Seemann（『Dependency Injection Principles, Practices, and Patterns』の著者）が名付けた Composition Root です。

    Composition Root とは

    アプリケーションの エントリーポイントにできるだけ近い場所 に置く、オブジェクトの組み立て（依存の配線）を 一手に引き受ける唯一の場所。

    8.2 例（手動 DI）

    // src/main.ts ← Composition Root（アプリの入口）
import express from "express";
import { PrismaClient } from "@prisma/client";

// ① 最も外側の技術的な部品を作る
const prisma = new PrismaClient();
const mailer = new SendGridMailer(process.env.SENDGRID_API_KEY!);

// ② アダプタ（インターフェースの実装）を作る
const userRepository = new PrismaUserRepository(prisma);
const notifier = new EmailNotifier(mailer);

// ③ ユースケースに注入する
const registerUser = new RegisterUserUseCase(userRepository, notifier);

// ④ 入口（Controller）に注入する
const userController = new UserController(registerUser);

// ⑤ フレームワークにつなぐ
const app = express();
app.post("/users", (req, res) => userController.register(req, res));
app.listen(3000);
    • new はここに集まります。 ユースケースやドメインのコードには new PrismaUserRepository() が一切出てきません。
    • どの実装を使うか（テスト用・本番用・別の DB）を変えたいときは、ここだけを変えればよい のです。
    • クリーンアーキテクチャの図でいえば、最も外側の「Frameworks & Drivers」 に属する場所です。Robert C. Martin はこれを「Main コンポーネント」と呼んでいます。

    8.3 Composition Root のルール

    ルール理由
    アプリに 1 つだけ（エントリーポイントごとに 1 つ）組み立ての知識が散らばらない
    エントリーポイントのできるだけ近く に置くアプリの他の部分が組み立てを知らずに済む
    DI コンテナを使うなら、ここでだけ使うここ以外で使うと、次章のサービスロケーターになる
    組み立てた後は、ルートのオブジェクトを 1 つ取り出して動かすだけ残りは、注入された依存が連鎖的に動く

    入口が複数あるアプリ

    Web API・バッチ・CLI のように入口が複数あるアプリでは、入口ごとに Composition Root を持ちます。共通部分は関数にまとめて構いません。

    9.アンチパターン：サービスロケーター

    9.1 サービスロケーターとは

    グローバルな「部品置き場」から、必要なときに依存を取り出す 方式です。

    ✕ サービスロケーター 
    class RegisterUserUseCase {
  async execute(input: RegisterInput) {
    const repo = ServiceLocator.get<UserRepository>("UserRepository");  // 中で取り出す
    const notifier = ServiceLocator.get<Notifier>("Notifier");
    ...
  }
}
    ○ DI（コンストラクタ注入） 
    class RegisterUserUseCase {
  constructor(
    private readonly repo: UserRepository,
    private readonly notifier: Notifier,
  ) {}
}

    一見すると、どちらも「具体クラスを new していない」ので同じに見えます。実際、Fowler の 2004 年の論文でも、サービスロケーターは DI の 代替案 として紹介されていました。

    9.2 なぜアンチパターンなのか

    Mark Seemann は 2010 年の記事「Service Locator is an Anti-Pattern」で、次の問題を指摘しました。

    問題説明
    依存が隠れるコンストラクタを見ても、このクラスが何に依存しているか分からない。コードを全部読まないと分からない
    コンパイル時ではなく実行時に失敗する必要な部品を登録し忘れても、コンパイルは通る。実行して get() した瞬間に初めてエラーになる
    テストしにくいテストのたびに、グローバルな部品置き場へ偽物を登録・解除する必要がある。テスト同士が干渉しやすい
    どこからでも何でも取り出せる依存のルール（内側は外側を知らない）を簡単に破れてしまう

    補足：Jimmy Bogard の「Service Locator is not an Anti-Pattern」のように、フレームワークの都合などで使わざるを得ない場面もあるとする反対意見もあります。ただし、アプリのコード（ユースケースやドメイン）の中で使うべきでない、という点はおおむね共通しています。

    9.3 DI コンテナを「サービスロケーターとして」使ってしまう

    注意したいのは、DI コンテナを使っていても、サービスロケーターになりうる ことです。

    ✕ DI コンテナをサービスロケーターとして使っている 
    import { container } from "tsyringe";

class RegisterUserUseCase {
  async execute() {
    const repo = container.resolve<UserRepository>("UserRepository");  // ← 中で呼んでいる
  }
}

    DI コンテナの resolve() を呼んでよいのは Composition Root だけ です。それ以外の場所で呼ぶと、DI コンテナを使っているのにサービスロケーターと同じ問題が起きます。これは 依存性逆転の原則（DIP） の「DI コンテナを使えば自動的に DIP」が誤解である、という話とも同じです。

    フレームワークが生成を管理している場合

    一部の Web フレームワークなど、フレームワークがオブジェクトの生成を管理している場合は、フレームワークの拡張点でコンテナを呼ぶ必要が出ることがあります。これは「Composition Root をフレームワークの入口に置いている」と考え、使う場所を最小限に保つ ことが大切です。

    10.依存のライフタイムと捕らわれた依存

    Composition Root（や DI コンテナ）では、オブジェクトをいつ作り、いつまで使い回すか（ライフタイム）も決めます。

    ライフタイム意味向いているもの
    シングルトン（Singleton）アプリ全体で 1 つだけ 作り、ずっと使い回す状態を持たないもの、作るのが高価なもの（DB 接続プール、HTTP クライアント、設定）
    スコープ（Scoped）1 リクエストごとに 1 つ 作るリクエストごとの状態を持つもの（トランザクション、ログインユーザー情報、Unit of Work）
    トランジェント（Transient）使うたびに新しく 作る軽量で状態を持つもの

    ここでの「シングルトン」は DI コンテナが 1 つだけ作って使い回すというライフタイムの意味で、GoF のシングルトンパターン（クラス自身が static なインスタンスを持つ）とは別物です。

    10.1 捕らわれた依存（Captive Dependency）

    ライフタイムでよくある失敗が 捕らわれた依存 です（Mark Seemann らの命名）。

    長生きするオブジェクトが、短命であるべきオブジェクトを抱え込んでしまう こと。

    UserService（シングルトン：アプリ全体で 1 つ）
   └── RequestContext（本来はスコープ：リクエストごとに 1 つ）
    • UserService は最初のリクエストのときに 1 回だけ作られ、そのときの RequestContext を抱え込みます。
    • 2 回目以降のリクエストでも、最初のリクエストのユーザー情報 が使われてしまいます。
    • 結果として、別のユーザーのデータが見えてしまう、トランザクションが混ざる、などの深刻なバグになります。

    ルール

    オブジェクトは、自分より短命な依存を持ってはいけません。 シングルトン → スコープ → トランジェント の順に、長い方から短い方へは依存しないようにします。

    一部の DI コンテナは、この違反を検出して警告してくれます（例：.NET の組み込みコンテナは、開発環境でスコープの検証を行い、シングルトンからスコープのサービスを解決しようとすると例外を出します）。

    11.DI コンテナ

    11.1 DI コンテナとは

    アプリに必要な すべての依存の組み立て を自動でやってくれるツールです。Composition Root で「この抽象にはこの実装を使う」と登録しておくと、コンテナが依存関係をたどってオブジェクトを組み立てます。

    11.2 有名な DI コンテナ

    言語DI コンテナ
    JavaScript / TypeScriptInversifyJS、tsyringe、NestJS のモジュール
    JavaSpring
    C#.NET 組み込み DI コンテナ、Autofac
    Pythondependency-injector

    11.3 簡単な例：tsyringe

    import { injectable, inject, container } from 'tsyringe';

@injectable()
class UserService {
  constructor(@inject('Database') private db: Database) {}
}

container.register('Database', { useClass: MySQLDatabase });

const service = container.resolve(UserService); // 自動で組み立て

    補足：tsyringe はデコレーターと型メタデータを使うため、reflect-metadata の読み込みと、tsconfig の experimentalDecorators・emitDecoratorMetadata の有効化が必要です。この container.resolve() も、Composition Root でだけ呼びます。

    11.4 メリットとデメリット

    メリット

    • 配線コードを自動化 できる
    • ライフサイクル管理（シングルトン、リクエストごと、一時など）
    • 環境別の差し替え が楽

    デメリット

    • 学習コスト がかかる
    • デバッグが難しくなる（マジックが増える）
    • 小規模なら手動 DI で十分

    12.手動 DI か、DI コンテナか

    12.1 手動 DI で十分な場合

    • 小〜中規模のアプリ
    • Express のルーター単位など、局所的な配線
    // main.ts
const db = new MySQLDatabase();
const userRepo = new UserRepository(db);
const userService = new UserService(userRepo);

    12.2 DI コンテナが有効な場合

    • 大規模アプリ
    • 依存グラフが複雑
    • 環境別（本番／テスト／開発）の切り替えが多い

    12.3 Composition Root の観点での比較

    手動 DI（Pure DI）DI コンテナ
    組み立て方Composition Root で new を並べるComposition Root で登録し、コンテナに組み立てさせる
    間違いに気づくタイミングコンパイル時（型チェックが効く）多くは 実行時
    コードの見通し組み立てが目で見える規約や設定に隠れる
    向いている小〜中規模、依存の数がそれほど多くない大規模、依存が多い、ライフタイム管理が複雑

    Mark Seemann も、まずは手動 DI（Pure DI）で始め、組み立てのコードがつらくなってから DI コンテナを検討する ことを勧めています。TypeScript は型チェックが強力なので、手動 DI で十分なケースが多いです。

    13.よくある誤解

    誤解1：DI は難しい高度なテクニック

    「コンストラクタで渡す」だけのこと です。難しくありません。

    誤解2：DI コンテナを使わないと DI ではない

    手動で渡すだけでも立派な DI です。むしろ小規模なら手動の方がシンプルです。

    誤解3：DI はすべてのクラスに必要

    純粋な計算や値オブジェクトなど、依存がないクラスには DI は不要です。

    誤解4：IoC と DI は同じ意味

    誤りです。 IoC は「制御を外に任せる」という広い考え方で、DI はその一種（依存の用意を外に任せる）です。

    誤解5：DI コンテナを使っていれば正しい DI

    誤りです。 Composition Root 以外でコンテナの resolve() を呼ぶと、サービスロケーターになります。

    誤解6：全部シングルトンにすれば効率がよい

    危険です。 リクエストごとの状態を持つものをシングルトンにすると、捕らわれた依存 によってユーザー間でデータが混ざります。

    14.まとめ

    • DI（依存性注入）：必要な相手を自分で作らず、外から渡してもらうテクニック。形は コンストラクタ注入（最も推奨）・セッター注入・メソッド注入の 3 つ。
    • DI の効果は、テストのしやすさ・差し替えの容易さ・依存の明示。抽象に依存させ、依存は少なく、コンストラクタでは受け取るだけにする。
    • IoC（制御の反転）：誰が呼び出すかを逆にする広い考え方。「ハリウッドの原則」。
    • DIP（依存性逆転の原則）：依存の矢印を抽象に向ける原則。
    • DI は Fowler が 2004 年に IoC の一種として名付けた。DIP がゴール、DI が手段。
    • Composition Root：エントリーポイントの近くに置く、依存を組み立てる 唯一の場所。new と DI コンテナはここに集める。
    • サービスロケーター は依存を隠し、実行時エラーを招くアンチパターン。DI コンテナも Composition Root の外で使うとこれになる。
    • ライフタイムは シングルトン・スコープ・トランジェント。長生きするものが短命なものを抱え込まない（捕らわれた依存）。
    • まずは 手動 DI で始め、必要になってから DI コンテナを検討する。
