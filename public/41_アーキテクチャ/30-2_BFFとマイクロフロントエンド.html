    BFF・マイクロフロントエンド

    BFF（Backend for Frontend）は特定の画面のためだけに置く薄いバックエンド、マイクロフロントエンドは大きなフロントエンドをチームごとの独立したアプリに分ける考え方です。このページでは、それぞれが生まれた背景（SoundCloud の BFF、ThoughtWorks のマイクロフロントエンド）、役割と配置、統合方式（ビルド時・サーバー側・ランタイム、Module Federation）、設計上の注意点と「使うべきでない場面」までを整理します。

    2.BFF とは何か・なぜ必要か

    定義

    BFF（Backend for Frontend） とは、特定のフロントエンド（Web、iOS、Android、管理画面など）専用に用意する、薄いバックエンド です。汎用の API を全クライアントで共有するのではなく、「この画面（このユーザー体験）のための API」をサーバー側に1枚はさみます。

    BFF がないと何が困るか

    マイクロサービス化が進むと、1つの画面を表示するために、フロントエンドが複数のサービスを呼んでデータを組み合わせる必要が出てきます。たとえば商品詳細ページを表示するのに、スマホアプリが次のように5つの API を呼ぶ状況です。

      スマホアプリ ──→ 商品 API
              ├──→ 在庫 API
              ├──→ 会員 API
              ├──→ おすすめ API
              └──→ レビュー API

  × 呼び先が多すぎる（通信回数が増え、遅いモバイル回線では特に遅い）
  × 認証を各所で繰り返す
  × 画面1枚分のデータを集める・組み合わせるロジックがクライアントに散らばる
  × 内部のサービス構成を変えると、全クライアントの改修が必要になる

    これをブラウザやアプリでやると通信回数が増え、フロントのコードも複雑になります。また、Web とモバイルでは必要なデータの量や形が違うのに、汎用 API は「全員に合わせた最大公約数」になりがちです。

    BFF がやること

    役割内容
    集約（アグリゲーション）複数の API を呼んで 1画面分のデータにまとめ、1リクエストで返す
    変換・整形フロントが使いやすい形にデータを変換し、不要なフィールドを落とす。Web には多めの情報、モバイルには軽量な JSON と小さい画像 URL、のように出し分ける
    ブラウザに置きたくない処理の肩代わり認証トークンの扱い、API キーの保持など
    画面特化のロジック表示順、ページネーション、キャッシュ戦略など、画面の都合
    バックエンドの変更を隠す内部サービスの分割・統合をフロントから切り離す。サービス構成が変わっても BFF の中だけで吸収できる

    3.BFF の由来 ── SoundCloud と Sam Newman

    BFF という名前と考え方は、音楽配信サービス SoundCloud の実践から広まりました。

    1. モノリスから公開 API へ：SoundCloud は 2011 年ごろまで、すべてのロジックを1つのモノリスに持っていました。その後 UI 層を切り出し、Web やモバイルのアプリが 外部向けの汎用公開 API を直接呼ぶ構成にしました。
    2. 汎用 API の問題：プロフィール画面1つを表示するのに /tracks、/related、/users など多数の HTTP 呼び出しが必要で、不安定なモバイル回線では特に問題になりました。また、API を変えるには全クライアントやサードパーティとの調整が必要で、A/B テストや機能の段階的な公開もしにくくなっていました。
    3. クライアントごとのバックエンド：そこで Web・iOS・Android などのクライアントごとに専用のバックエンドを用意し、クライアントを担当するチームが他チームと調整せずに速く動けるようにしました。やがて画面の表示ロジックも BFF に寄せ、クライアントは GET /user-profile/123.json のような1回のリクエストで画面分のデータを受け取るようになりました。
    4. 名前の誕生：「BFF」という呼び名は、当時の Web のテックリード Nick Fisher が付けたものです。この経緯は元 SoundCloud の Phil Calçado が 2015 年の記事「The Back-end for Front-end Pattern (BFF)」で紹介しています。
    5. パターンとしての整理：同じ 2015 年、Sam Newman（『マイクロサービスアーキテクチャ』の著者）が記事「Pattern: Backends For Frontends」で、Phil Calçado の紹介を出発点に、SoundCloud や REA での実践をパターンとして整理しました。BFF が一般に知られるようになったのはこの記事からです。

    SoundCloud のその後

    Phil Calçado の記事によると、SoundCloud では BFF が5つほどに増えた段階で、複数の BFF に同じコードが重複していることに気づきました。そこで、ユーザープロフィールのような中核の業務データを扱う専用のマイクロサービス（例：UserProfileService）を作り、BFF からはそれを呼ぶ形に整理していきました。「BFF に業務ロジックを入れすぎると重複する」という、後述の注意点の実例です。

    Sam Newman の整理で特に大事なのは次の2点です。

    • BFF は1つの UI（1つのユーザー体験）に密着する：その UI のためだけに存在するので、小さく焦点の絞れたサービスになる。
    • その UI を担当するチームが BFF も持つ：画面の変更と API の変更を同じチームが同時に行えるので、他チームを待たずにリリースできる。

    4.BFF の配置と API ゲートウェイとの違い

    配置図

    BFF はクライアントと内部サービスの間に置きます。実務では、全クライアント共通の API ゲートウェイの内側に、クライアントごとの BFF を置く構成もよく見られます。

    同じ「商品詳細ページ」でも、Web は SEO 用の HTML と多めの情報、モバイルは軽量な JSON と画像サイズ違い、というように画面の要望が違います。図のモバイル BFF はレビューを呼ばない（モバイル画面では別タブで遅延読み込みする）といった、クライアントごとの出し分けを BFF の中で行えます。

    API ゲートウェイとの違い

    観点API ゲートウェイBFF
    位置づけ全クライアント共通の入口クライアントごとの専用窓口
    主な目的横断的関心事（認証の一次チェック・レート制限・ルーティング・ログ）画面都合の集約・変換、画面・クライアント向けの API 設計
    誰が書くかインフラ／プラットフォーム寄りのチームフロントエンドチーム、またはその近くのチーム
    ロジック薄いのが理想集約・整形のロジックを持つ
    個数しばしば1つ（環境ごと）クライアント種別（ユーザー体験）ごとに複数ありうる

    両者は対立するものではなく、組み合わせて使う こともよくあります（図1の構成）。API ゲートウェイの詳細と、一部のサービスが落ちても機能を縮小して動き続けるグレースフルデグレーデーションは、40-5 のページ で扱います。

    5.BFF を設計するときの判断ポイント

    いくつ作るか：プラットフォームごとか、体験ごとか

    BFF の分け方には「iOS 用と Android 用を別々に作る」か、「モバイル体験として1つにまとめる」かの選択があります。Sam Newman は、iOS と Android の画面がほぼ同じなら1つにまとめてもよいが、担当チームが別々なら BFF も分けた方が自然 だとしています。チームの分け方がシステムの分け方に表れる、というコンウェイの法則の典型例です。逆に、1つの BFF に性質の違う複数の UI をぶら下げると、BFF が肥大化して「汎用 API」に逆戻りします。

    重複をどう扱うか

    BFF を複数作ると、似た集約処理が BFF ごとに重複しがちです。ある程度の重複は「チームが独立して動ける」代償として受け入れ、重複が業務ロジックに及んできたら、SoundCloud のように 共通部分を下流のサービスに移す のが基本方針です。共有ライブラリにまとめる方法もありますが、ライブラリの更新が BFF 同士を結合させてしまう点に注意します。

    下流呼び出しと部分障害

    BFF は1リクエストで複数のサービスを呼ぶ（ファンアウトする）ので、次の点を設計します。

    • 並列か順番か：依存関係のない呼び出しは並列にして待ち時間を短くする。前の結果が必要な呼び出しだけ順番にする。
    • 部分的な失敗：おすすめ欄のサービスだけが落ちた場合に、ページ全体をエラーにするのか、その欄だけ空にして返すのかを決めておく。タイムアウトとフォールバックを BFF に置くと、グレースフルデグレーデーションを実現しやすくなります。

    BFF に入れてよいもの・入れないもの

    入れてよい（画面の都合）

    • 複数 API の集約、レスポンスの整形
    • 表示順・ページネーション・画面向けキャッシュ
    • トークンの保持などセキュリティ上ブラウザに置きたくない処理

    入れない（業務の都合）

    • 価格計算・在庫引当などの業務ルール
    • 複数クライアントで同じ結果になるべき判定
    • データの所有（BFF は自前のデータを持たないのが基本）

    注意：BFF は「画面の都合を吸収する層」にとどめる

    BFF に業務ロジックを入れすぎると、クライアントごとにロジックが重複し、Web とモバイルで計算結果が食い違うといった不具合の原因になります。業務ルールは下流のサービス（ドメイン）に置き、BFF は集約・変換に徹します。

    BFF と認証：トークンをブラウザに置かない

    SPA がアクセストークンをブラウザ内（JavaScript から読める場所）に保持すると、XSS で盗まれる危険があります。そこで、OAuth のトークンは BFF が保持し、ブラウザとは HttpOnly の Cookie によるセッションでやり取りする構成が使われます。IETF の「OAuth 2.0 for Browser-Based Applications」でも、ブラウザアプリの構成パターンの1つとして BFF が挙げられています。詳しくは 41 外のノート（73_認証認可）が本拠地です。

    GraphQL という選択肢

    クライアントごとに BFF を作る代わりに、GraphQL の API を1つ用意し、各クライアントが必要なフィールドだけを問い合わせる方法もあります。「画面ごとに欲しいデータの形が違う」という問題を、BFF の数ではなくクエリの柔軟さで解く考え方です。実際には、GraphQL サーバー自体を BFF として各サービスの前に置く構成もよく見られます。

    6.レンダリング方式と BFF の関係

    前のページで扱った SSR や React Server Components は、BFF と深く結びついています。

    • Next.js の Route Handler（app/api/.../route.js）や Server Components でサーバー側のデータ取得を書くと、それ自体が BFF の役割 を果たします。
    • SSR / RSC を選ぶことは、実質的に「フロントエンドチームがサーバー層を持つ」＝「BFF を持つ」ことでもあります。
    • 一方、CSR だけの SPA では、BFF を別に立てるか、ブラウザから直接 API（または API ゲートウェイ）を呼ぶことになります。
    Server Component が BFF として複数サービスを集約する例（イメージ） 
    // app/products/[id]/page.js（サーバーでだけ実行される）
export default async function ProductPage({ params }) {
  // 依存関係のない呼び出しは並列にする
  const [product, stock, reviews] = await Promise.all([
    fetch(`${PRODUCT_API}/products/${params.id}`).then((r) => r.json()),
    fetch(`${STOCK_API}/stock/${params.id}`).then((r) => r.json()),
    fetch(`${REVIEW_API}/reviews?product=${params.id}`)
      .then((r) => r.json())
      .catch(() => []),            // レビューが落ちても空で表示を続ける
  ]);
  return <ProductView product={product} stock={stock} reviews={reviews} />;
}

    この例では、内部 API の URL やキーはサーバーの中だけにあり、ブラウザには完成した画面だけが届きます。「集約」「部分障害の吸収」「ブラウザに置きたくない情報の隠蔽」という BFF の役割を、フロントエンドのフレームワークの中で果たしているわけです。

    気をつけたいこと

    フレームワークの中に BFF が溶け込むぶん、「どこまでが画面の都合で、どこからが業務ロジックか」の境界があいまいになりがちです。Server Component の中に価格計算を書き始めたら、それは BFF に業務ロジックが漏れているサインです。

    7.マイクロフロントエンドとは

    定義

    マイクロフロントエンド とは、大きなフロントエンドを、機能（ドメイン）ごとに独立したアプリに分け、別々のチームが開発・デプロイできるようにする 考え方です。バックエンドのマイクロサービスの考え方をフロントエンドに持ち込んだものといえます。Cam Jackson（martinfowler.com, 2019）は、これを「独立して提供できるフロントエンドのアプリを、より大きな全体へと組み立てるアーキテクチャスタイル」と表現しています。

    由来

    • 「Micro Frontends」という言葉は、2016 年 11 月の ThoughtWorks Technology Radar で取り上げられたのが始まりとされています。バックエンドはマイクロサービスに分かれたのに、フロントエンドだけが巨大な一枚岩（フロントエンドモノリス）として残る問題への対策として紹介されました。
    • その後、Michael Geers のサイト「micro-frontends.org」や、Cam Jackson の記事「Micro Frontends」（martinfowler.com, 2019）によって考え方と実装方法が広く知られるようになりました。

    全体像

    観点内容
    分け方「商品検索」「カート」「マイページ」など、ドメイン単位 でチームとアプリを分ける（技術の層で分けるのではない）
    組み立て方ビルド時に統合（npm パッケージ）／サーバーやエッジで統合／実行時に統合（Module Federation、iframe、Web Components）
    長所チームごとに独立してリリースできる。技術スタックを段階的に移行できる
    短所共通 UI・デザインの一貫性を保つのが難しい。重複したライブラリで JS が重くなる。構成が複雑
    向く場面複数チームが1つの大規模画面を開発していて、リリースの調整がボトルネックになっているとき

    得られるもの

    Cam Jackson は利点として次の4つを挙げています。

    段階的なアップグレード

    古いフレームワークで書かれた画面を、全面書き換えせずに一部ずつ新しい技術へ移行できる。

    小さく分離されたコードベース

    1つのアプリが小さくなり、境界がはっきりするので、意図しない結合が生まれにくい。

    独立したデプロイ

    それぞれが自分のパイプラインでデプロイできるので、1回のリリースの影響範囲が小さい。

    自律したチーム

    画面からバックエンドまで、1つのドメインを1つのチームが縦に持てる。

    8.マイクロフロントエンドの統合方式

    マイクロフロントエンドで最も重要な設計判断は、分けたアプリを「いつ・どこで」1つの画面に組み立てるか です。前のページのレンダリング方式と同じく、ビルド時・サーバー側（リクエスト時）・ブラウザ（ランタイム）の3つのタイミングがあります。

    方式しくみ長所短所
    ビルド時統合各マイクロフロントエンドを npm パッケージとして公開し、コンテナアプリが依存として取り込んでまとめてビルドする単純。1つのバンドルなので依存の重複を除きやすく、型チェックも効くどれか1つを変えるたびにコンテナを再ビルド・再リリースする必要があり、リリースが足並みをそろえる（ロックステップ） ことになる。マイクロフロントエンドの最大の利点である独立デプロイを失うため、Cam Jackson は推奨していない
    サーバー側統合サーバーやエッジ（CDN）が、各チームの HTML 断片を組み合わせて1枚の HTML を作る。古典的には SSI（Server Side Includes）や ESI（Edge Side Includes）を使う最も昔からある素朴な方法。完成した HTML を返せるので初回表示・SEO に強いページ内で動的にやり取りする UI には向きにくい。断片をまたいだ状態共有が難しい
    ランタイム統合：iframe各アプリを iframe で埋め込むスタイルも JS も完全に隔離される。最も単純な隔離手段ルーティング・ディープリンク・履歴の扱い、レスポンシブな高さ調整、アプリ間の連携がやりにくい。アクセシビリティや SEO の面でも不利
    ランタイム統合：JavaScriptコンテナ（シェル）が各アプリの JS バンドルを実行時に読み込み、各アプリが公開した描画関数（例：window.renderCart(el)）を呼ぶ。Module Federation や single-spa もこの系統最も柔軟。各アプリを独立してデプロイでき、シェルは実行時に最新版を読み込める依存ライブラリの重複、グローバルな名前・CSS の衝突、エラーの波及に注意が必要
    ランタイム統合：Web Components各アプリをカスタム要素（例：<cart-widget>）として定義し、コンテナは HTML タグとして配置するブラウザ標準の仕組みでフレームワークに依存しない。Shadow DOM でスタイルを隔離できるReact などとの属性・イベントの受け渡しにひと手間かかる。SSR との組み合わせが難しい
    サーバー側統合の例（SSI と ESI） 
    <!-- Nginx などの SSI：サーバーが断片を埋め込んでから返す -->
<body>
  <!--# include virtual="/search/fragment" -->
  <!--# include virtual="/cart/fragment" -->
</body>

<!-- CDN の ESI：エッジで断片を組み立てる -->
<esi:include src="https://cart.example.com/fragment" />
    ランタイム統合の例（Web Components） 
    // カートチームが公開するスクリプト（https://cart.example.com/cart.js）
class CartWidget extends HTMLElement {
  connectedCallback() {
    const userId = this.getAttribute("user-id");
    this.attachShadow({ mode: "open" }).innerHTML = `<p>カート（${userId}）</p>`;
  }
}
customElements.define("cart-widget", CartWidget);

<!-- コンテナ側：タグを置くだけ -->
<script src="https://cart.example.com/cart.js" defer></script>
<cart-widget user-id="123"></cart-widget>

    9.Module Federation と主な道具

    Module Federation とは

    Module Federation は、2020 年に webpack 5 で導入された機能で、Zack Jackson が中心になって考案しました。別々にビルド・デプロイされたアプリ同士が、実行時にお互いのモジュールを読み込み合える 仕組みです。ランタイム統合の「JavaScript」方式を、バンドラーの機能として扱いやすくしたものといえます。

    用語意味
    Host（ホスト）他のアプリのモジュールを読み込んで使う側。シェル／コンテナアプリ
    Remote（リモート）自分のモジュールを公開する側。remoteEntry.js という入口ファイルを出力する
    exposesリモートが外部に公開するモジュールの一覧
    sharedReact などを複数アプリで共有する設定。singleton: true で1つのインスタンスにそろえ、重複読み込みを防ぐ
    リモート側（カートチーム）の webpack 設定 
    const { ModuleFederationPlugin } = require("webpack").container;

new ModuleFederationPlugin({
  name: "cart",
  filename: "remoteEntry.js",                 // 公開用の入口
  exposes: { "./Cart": "./src/Cart" },        // 外に見せるモジュール
  shared: { react: { singleton: true }, "react-dom": { singleton: true } },
});
    ホスト側（シェル）の設定と使い方 
    new ModuleFederationPlugin({
  name: "shell",
  remotes: { cart: "cart@https://cart.example.com/remoteEntry.js" },
  shared: { react: { singleton: true }, "react-dom": { singleton: true } },
});

// アプリのコード：実行時にカートチームの最新版を読み込む
const Cart = React.lazy(() => import("cart/Cart"));

    カートチームが新しい版をデプロイすると、シェルを再ビルドしなくても、次にページを開いたときから新しいカートが読み込まれます。これが「独立デプロイ」の実体です。その後、型定義の共有やマニフェストによる公開モジュールの発見、プリロードなどを加えた Module Federation 2.0 が登場し、webpack 以外に Rspack や Vite などのバンドラーでも使えるようになっています。

    その他の主な道具

    • single-spa：複数のフレームワークで作ったアプリを、URL に応じて1つのページ上で起動・停止させる「ルーター兼ライフサイクル管理」のフレームワーク。
    • Import Maps：ブラウザ標準の仕組みで、import "cart" のようなモジュール名を実際の URL に対応づける。バンドラーに頼らないランタイム統合に使われる。
    • iframe・Web Components：8章のとおり、ブラウザ標準だけで統合する手段。

    10.マイクロフロントエンドの設計課題

    スタイルの衝突

    CSS はページ全体に効くため、あるチームの h2 { … } が別チームの画面を崩すことがあります。BEM のような命名規約、CSS Modules、CSS-in-JS、Shadow DOM による隔離などで、チームが互いを気にせず作業できる 状態を作ります。

    共有コンポーネントライブラリとデザインの一貫性

    ボタンやアイコンなどの見た目の部品は、共有のコンポーネントライブラリ（デザインシステム）にまとめるとデザインの一貫性を保ちやすくなります。ただし、業務ロジックやドメインの概念を共有ライブラリに入れると、チーム同士が強く結合 してしまいます。Cam Jackson は、最初から共有ライブラリを作り込むのではなく、重複が見えてから抽出すること、ライブラリの品質に責任を持つ担当者を決めることを勧めています。

    アプリ間の通信

    マイクロフロントエンド同士の直接のやり取りは最小限にします。必要な場合は、カスタムイベント（疎結合な通知）、コンテナからのコールバック・属性の受け渡し、URL（ルーティング）を介した状態の共有などを使い、グローバルな状態を共有しない ようにします。

    カスタムイベントで疎結合に知らせる例 
    // 商品チーム：カートに追加されたことを知らせるだけ（誰が受け取るかは知らない）
window.dispatchEvent(new CustomEvent("cart:item-added", { detail: { sku: "A-100" } }));

// カートチーム：関心があれば受け取る
window.addEventListener("cart:item-added", (e) => refreshCart(e.detail.sku));

    バックエンドとの関係：マイクロフロントエンドごとの BFF

    マイクロフロントエンドとBFF は相性がよく、各マイクロフロントエンドに対応する BFF をそのチームが持つ 構成がよく紹介されます。チームが画面から BFF までを縦に持てば、他チームの API 変更を待たずに動けます。認証はコンテナ側で一度だけ行い、トークンなどを各マイクロフロントエンドに渡します。

    テスト

    テストの考え方は通常のアプリと同じで、各マイクロフロントエンドの中ではユニットテストを中心にします。全体を組み合わせた E2E テストは「正しく組み立てられているか」の確認に絞り、チーム間の約束（イベントの形・属性など）は契約テストで検証すると、壊れやすい統合環境に頼らずにすみます。

    デメリット

    JS が重くなる

    各チームが同じライブラリを別々に同梱すると、ダウンロード量が増える。共有すると今度はチームの独立性が下がる、という綱引きになる。

    環境の差

    開発中は自分のアプリ単体で動かすため、本番で組み合わせたときに初めて問題が出ることがある。本番に近い環境での確認が欠かせない。

    運用の複雑さ

    リポジトリ・パイプライン・配信先が増える。自動化とガバナンス（決まりごと）を整えられる組織の成熟度が必要。

    11.使うべき場面・使うべきでない場面

    BFF が向いている

    • Web とモバイルなど、画面の要望が大きく違うクライアントがある
    • 1画面のために多数のサービスを呼ぶ必要があり、サーバー側での集約が効く
    • フロントエンドチームとバックエンドチームが分かれていて、API 変更の調整が遅い
    • トークンなど、ブラウザに置きたくない情報がある

    BFF が過剰になりやすい

    • クライアントが1種類しかなく、バックエンドもモノリスで API が1つ
    • バックエンドの API がすでに画面に合った形で、集約・変換がほぼ不要
    • BFF を担当できるチーム・運用体制がない（サーバーが1つ増えるだけになる）

    マイクロフロントエンドが向いている

    • 複数チームが1つの大規模画面を開発していて、リリースの調整がボトルネックになっている
    • 古いフロントエンドを、全面書き換えせずに段階的に移行したい
    • ドメインごとにチームが分かれ、画面からバックエンドまで縦に持つ体制がある

    マイクロフロントエンドが過剰になりやすい

    • 小〜中規模のチーム（1〜数チーム）
    • リリースの調整がまだ問題になっていない
    • CI/CD・監視・デザインシステムなどの基盤が整っていない

    まずは1つのアプリの中で機能別に分ける

    マイクロフロントエンドは 小〜中規模のチームには過剰 になりやすい構成です。まずは1つのアプリの中で、ディレクトリ・モジュールを機能別に分ける（41 外のノート：47_フロントエンド設計、43_モジュール設計）ところから始め、チームの独立性が本当に必要になってから検討します。バックエンドで「いきなりマイクロサービスにせず、まずモジュラーモノリス」とするのと同じ考え方です。チーム構成がシステム構成に表れる点は、コンウェイの法則 と同じ話です。

    12.よくある誤解

    「BFF と API ゲートウェイは同じもの」

    API ゲートウェイは全クライアント共通の入口で、認証の一次チェックやレート制限など横断的な処理を薄く担います。BFF はクライアントごとの専用窓口で、画面の都合に合わせた集約・変換を担います。目的も持ち主も違い、組み合わせて使うこともあります。

    「BFF に業務ロジックを書けば、フロントもバックエンドも楽になる」

    BFF はクライアントごとにあるので、業務ロジックを入れると BFF の数だけ重複し、結果の食い違いを生みます。SoundCloud でも BFF が増えたときに重複が問題になり、共通部分を下流のサービスに移しました。BFF は画面の都合を吸収する層にとどめます。

    「BFF は 1 つのバックエンドで全クライアントに対応するもの」

    それは汎用 API の考え方です。BFF の本質は「1 つのユーザー体験に密着した、その UI のチームが持つバックエンド」です。1つの BFF に性質の違う UI を詰め込むと、肥大化して汎用 API に逆戻りします。

    「マイクロフロントエンドにすれば、技術を自由に混ぜられるのが一番の利点」

    技術の混在は「できる」だけで、積極的にやるべきことではありません。フレームワークが増えるほど JS が重くなり、知識も分散します。主な利点は チームごとの独立したリリース と 段階的な移行 です。

    「npm パッケージに分ければマイクロフロントエンドになる」

    ビルド時統合では、どれか1つを変えるたびにコンテナ全体を再ビルド・再リリースする必要があり、独立デプロイという最大の利点が得られません。コードの整理としては有効ですが、マイクロフロントエンドの目的を果たすにはサーバー側かランタイムでの統合が必要です。

    「マイクロフロントエンドは画面のパーツ（コンポーネント）を細かく分けること」

    分ける単位は UI 部品ではなく ドメイン（業務の領域）とチーム です。ボタンやヘッダーの共有はデザインシステムの役割で、マイクロフロントエンドの境界とは別の話です。

    13.まとめ

    • BFF は、特定のフロントエンド専用の薄いバックエンド。複数 API の集約、画面向けの変換、ブラウザに置きたくない処理の肩代わりを担う。
    • BFF は SoundCloud の実践から生まれ（命名は Nick Fisher、紹介は Phil Calçado）、Sam Newman が 2015 年にパターンとして整理した。要点は「1 つの UI に密着」「その UI のチームが持つ」。
    • API ゲートウェイ は全クライアント共通の入口、BFF はクライアントごとの窓口。組み合わせて使える。
    • BFF に業務ロジックを入れすぎると重複する。画面の都合を吸収する層 にとどめる。
    • Next.js の Server Components や Route Handler は、それ自体が BFF の役割を果たす。SSR / RSC を選ぶことは BFF を持つことでもある。
    • マイクロフロントエンド は、フロントエンドをドメインごとの独立したアプリに分け、チームごとに開発・デプロイする考え方（2016 年の ThoughtWorks Technology Radar が発端）。
    • 統合方式は ビルド時・サーバー側・ランタイム（iframe / JavaScript / Web Components）。独立デプロイを得るならサーバー側かランタイム。Module Federation はランタイム統合の代表的な道具。
    • スタイルの衝突、共有ライブラリ、JS の重複、運用の複雑さが課題。小〜中規模には過剰 になりやすく、まずは1つのアプリの中で機能別に分けることから始める。
