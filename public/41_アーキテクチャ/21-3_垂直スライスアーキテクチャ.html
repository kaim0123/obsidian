    垂直スライスアーキテクチャ

    レイヤードやクリーンアーキテクチャはアプリを「横に」切りますが、実際の変更はたいてい「1つの機能」単位でやってきます。このページでは、機能ごとに縦に切る垂直スライスアーキテクチャ（Vertical Slice Architecture）の原則・構造・コード例と、クリーンアーキテクチャとの組み合わせ方、向き不向きを解説します。

    もとにしたノート：03_垂直スライスアーキテクチャ（＋ 00_解説_アプリ内部構造）

    1.このページで扱うこと

    レイヤードやクリーンアーキテクチャは、アプリを横に切ります（画面・業務・DB のように技術の役割で分ける）。しかし実際の変更は、たいてい1つの機能単位でやってきます。「注文に割引を追加する」と言われたら、画面・API・業務ロジック・DB アクセスを縦に全部触ることになります。

    このページでは、機能ごとに縦に切るという発想の垂直スライスアーキテクチャについて、次のことを扱います。

    • 横に切る（Package by Layer）と縦に切る（Package by Feature）の違い
    • 垂直スライスアーキテクチャの原則と構造
    • コードのイメージ（コマンドとクエリで作り方が違う）
    • クリーンアーキテクチャとの関係（対立か、組み合わせか）
    • メリット・デメリット、向いている場面・向いていない場面

    2.横に切るか、縦に切るか

    2.1 横に切る（Package by Layer）

    src/
  controllers/
    OrderController.ts
    ProductController.ts
    UserController.ts
  services/
    OrderService.ts
    ProductService.ts
    UserService.ts
  repositories/
    OrderRepository.ts
    ProductRepository.ts
    UserRepository.ts
    • フォルダを開くと「何の技術で作られているか」が分かる
    • 「注文」の機能を直すには、3つのフォルダを行き来する

    2.2 縦に切る（Package by Feature）

    src/
  features/
    orders/
      place-order/
        PlaceOrderEndpoint.ts
        PlaceOrderHandler.ts
        PlaceOrderValidator.ts
        PlaceOrder.test.ts
      cancel-order/
        CancelOrderEndpoint.ts
        CancelOrderHandler.ts
      get-order-history/
        GetOrderHistoryEndpoint.ts
        GetOrderHistoryQuery.ts
    products/
      search-products/
      ...
    • フォルダを開くと「このアプリが何をするか」が分かる
    • 「注文をキャンセルする」機能を直すには、cancel-order/ だけを見ればよい

    叫ぶアーキテクチャ（Screaming Architecture）

    Robert C. Martin は、フォルダ構成を見たときに「Rails のアプリだ」ではなく「これは EC サイトだ」と叫んでいるべきだ、と述べました（『Clean Architecture』第21章）。機能でまとめた構成は、まさにアプリの目的を叫ぶ構成です。

    3.垂直スライスアーキテクチャとは

    3.1 提唱と原則

    Jimmy Bogard（.NET のライブラリ MediatR・AutoMapper の作者）が 2018 年のブログ記事で提唱しました。原則はひとことで表されます。

    スライス間の結合は最小に、スライス内の結合は最大に。
    （Minimize coupling between slices, and maximize coupling in a slice.）

    • スライス＝1つのリクエスト（1つのユースケース）を処理するのに必要な、画面〜DB までのすべてのコード
    • スライスの中は強く結びついていてよい（高凝集）
    • スライス同士はできるだけ独立させる（疎結合）

    これは モジュール性・疎結合と高凝集 の「凝集の単位＝変更の単位」を、機能（ユースケース）を単位にして徹底した形です。

    3.2 スライスごとに作り方を変えてよい

    垂直スライスの大きな特徴は、スライスごとに最適な実装方法を選べることです。

    スライス複雑さ実装方法の例
    注文履歴を表示する単純な参照SQL を直接書いて DTO で返す。ドメインモデルは使わない
    商品を検索する性能が重要検索エンジンや最適化したクエリを直接使う
    注文する業務ルールが複雑ドメインモデル（集約）を使い、在庫・割引・与信のルールを表現する

    レイヤードでは「すべての機能が Controller → Service → Repository を通る」のが普通ですが、垂直スライスでは単純な機能は単純に、複雑な機能だけ丁寧に作れます。閉じた層と開いた層・シンクホール で見たシンクホール（何もしない層）が生まれにくい構造です。

    3.3 共通の抽象を減らす

    Bogard は、垂直スライスにすると層ごとの共通の抽象（汎用 Repository、汎用 Service、基底 Controller など）の多くが不要になると述べています。

    • 各スライスは、他のスライスとサービス・リポジトリ・基底クラスを共有しないのが基本
    • 共有するのは「本当に共有すべき理由があるもの」だけ（ドメインモデル、認証、ログなど）

    4.コードのイメージ

    TypeScript で「注文をキャンセルする」（書き込み）と「注文履歴を見る」（読み取り）のスライスを書くと、次のようになります。

    書き込みのスライス：features/orders/cancel-order/CancelOrderHandler.ts 
    export type CancelOrderCommand = { orderId: string; userId: string };

export class CancelOrderHandler {
  constructor(private readonly db: Database) {}

  async handle(cmd: CancelOrderCommand): Promise<void> {
    const order = await this.db.orders.findById(cmd.orderId);
    if (!order) throw new NotFoundError("注文が見つかりません");
    if (order.userId !== cmd.userId) throw new ForbiddenError();

    order.cancel(); // 業務ルール（発送済みならキャンセル不可など）はドメインモデルに
    await this.db.orders.save(order);
  }
}
    読み取りのスライス：features/orders/get-order-history/GetOrderHistoryQuery.ts 
    // 参照だけのスライスは、ドメインモデルを通さず直接 SQL で DTO を返してよい
export async function getOrderHistory(db: Database, userId: string) {
  return db.sql<OrderHistoryDto>`
    SELECT id, ordered_at, total_amount, status
    FROM orders WHERE user_id = ${userId}
    ORDER BY ordered_at DESC LIMIT 50`;
}
    • 書き込み（コマンド）と読み取り（クエリ）で、作り方がまったく違います
    • これは自然と CQRS — コマンドとクエリの責務分離 の考え方に近づきます。実際、垂直スライスは CQRS と組み合わせて紹介されることが多いです（Bogard の MediatR も、リクエストごとにハンドラーを1つ持つ形でこのスタイルを支えています）

    5.クリーンアーキテクチャとの関係

    5.1 対立するものではない

    「垂直スライスか、クリーンアーキテクチャか」と対立的に語られることがありますが、実際には切る方向が違うだけで、組み合わせられます。

    クリーン / ヘキサゴナル / オニオン垂直スライス
    主な関心依存の向き（内側＝ドメインを守る）変更の単位（機能ごとにまとめる）
    切る方向同心円（技術 vs ドメイン）縦（機能ごと）
    共通の抽象Port（インターフェース）を多く定義する必要なものだけ

    5.2 よくある組み合わせ方

    src/
  features/                 ← 縦に切る（垂直スライス）
    orders/
      place-order/
      cancel-order/
  domain/                   ← 複数のスライスで共有するドメインモデル（内側）
    order/Order.ts
    order/OrderStatus.ts
  infrastructure/           ← DB・外部 API のアダプタ（外側）
    db/
    payment-gateway/
    • 最上位は機能で縦に切り、
    • 業務ルールが複雑な部分はドメインモデルとして内側に置き、インフラへの依存を逆転させる（→ 依存性のルールとクリーンアーキテクチャ）
    • 単純なスライスはドメイン層を通さない

    これは アーキテクチャ量子と粒度・論理コンポーネント の「最上位をドメインで分割し、その中を技術で分ける」とも同じ発想です。

    6.メリットとデメリット

    6.1 メリット

    メリット説明
    変更が局所化する1つの機能の変更が、1つのフォルダに閉じる
    理解しやすい新しく入った人も「この機能のコードはここ」とすぐ分かる
    過剰な抽象が減る何もしない Service や汎用 Repository が不要になる
    スライスごとに最適化できる単純な機能は単純に、複雑な機能だけ丁寧に
    並行開発しやすい別の機能を担当する人同士の衝突が減る
    削除しやすい不要になった機能はフォルダごと消せる

    6.2 デメリット・注意点

    デメリット説明対策
    コードの重複スライス間で似た処理が繰り返される3回以上重複したら共通化を検討する（早すぎる共通化を避ける）
    業務ルールが散らばる「注文はキャンセルできるか」のルールが複数スライスに書かれる業務ルールはドメインモデルに集約する。スライスはそれを呼ぶだけ
    スライスごとにバラバラな作り自由度が高いぶん、統一感がなくなるチームでパターン（単純な参照ならこう、複雑な更新ならこう）を決めておく
    リファクタリングの力が必要「どこまで共通化するか」を継続的に判断する必要があるコードの匂い（重複・肥大化）に気づいたら直す習慣をつける

    業務ルールの散らばりに注意

    垂直スライスはドメインモデルが不要になるという意味ではありません。複雑な業務ルールは、引き続きドメインモデルに集めるべきです（→ 41 外のノート：42_ソフトウェア設計『DDD』）。

    7.向いている場面・向いていない場面

    向いている

    • 機能ごとに複雑さが大きく違う
    • 機能の追加・変更が頻繁
    • シンクホール（何もしない層）が多いレイヤードに悩んでいる
    • 将来、機能のまとまりをモジュール・サービスとして切り出す可能性がある

    向いていない

    • すべての機能が同じような単純 CRUD（素直なレイヤードで十分）
    • 業務ルールが複雑に絡み合い、ほぼすべての機能が同じドメインモデルを使う
    • チームがリファクタリングや重複の判断に慣れていない

    とくに最後の「切り出し」の点は重要です。垂直スライスで機能ごとにまとまっていると、モジュラーモノリスやサービスに切り出すときの境界がすでに見えています（→ モノリス・分散モノリス・マイクロサービス）。

    8.よくある誤解

    「垂直スライスはレイヤーを使わない」

    誤りです。スライスの中には、必要に応じて層（エンドポイント・処理・データアクセス）があります。違うのは、層を最上位の分け方にしないことと、スライスごとに層の数を変えてよいことです。

    「クリーンアーキテクチャの代わりになる」

    半分だけ正しいです。切る方向が違うので、組み合わせられます。依存の向きの考え方（ドメインを技術から守る）は、垂直スライスでも有効です。

    「重複は絶対に悪い」

    誤りです。スライス間で似たコードがあっても、変わる理由が違うなら別々にしておく方が安全です。早すぎる共通化は、スライス同士を結合させてしまいます。

    9.まとめ

    • 横に切る（Package by Layer）は技術で、縦に切る（Package by Feature）は機能で分ける
    • 垂直スライスアーキテクチャ：Jimmy Bogard が 2018 年に提唱。「スライス間の結合は最小に、スライス内の結合は最大に」
    • スライスごとに最適な作り方を選べる。単純な参照は単純に、複雑な更新だけドメインモデルで
    • 層ごとの共通の抽象が減り、シンクホールが生まれにくい
    • クリーンアーキテクチャとは切る方向が違うだけで、組み合わせられる
    • 注意点は業務ルールの散らばり。複雑なルールはドメインモデルに集める
