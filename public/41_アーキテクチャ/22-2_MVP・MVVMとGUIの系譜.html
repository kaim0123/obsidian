    2.なぜ UI とドメインを分離するのか

    UI のコードとドメインロジックを同じ場所に書くと、典型的に次の問題が起きます。

    ロジックを再利用できない

    別の画面で同じ計算を再実装することになります。

    テストが書きにくい

    UI を起動しないとロジックを試せません。

    画面の変更でロジックも壊れる

    軽い見た目の変更が業務バグを誘発します。

    読みにくい

    1つのファイルに「描画」「計算」「DB 呼び出し」が混在します。

    これを防ぐために、ドメイン（業務ロジック）を UI から切り離すのが大原則です。代表的な失敗例（モデルに HTML を含めるパターンなど）は MVC（MVC 違反） を参照してください。

    2.1 すべてのパターンに共通する問い：3種類のロジックをどこに置くか

    GUI のパターンはどれも、次の3種類のロジックをどこに置くかの違いとして整理できます。

    ロジックの種類例
    ドメインロジック「在庫が0なら注文できない」「会員ランクで割引率が変わる」
    プレゼンテーションロジック（画面の振る舞い）「在庫が0なら注文ボタンを無効にする」「割引中は価格を赤字で表示する」
    描画ボタンを置く、文字を描く、色を塗る

    どのパターンでも、ドメインロジックは画面から切り離すことは共通しています。違いは、プレゼンテーションロジックを View に置くか、別のオブジェクトに置くかです。この軸を頭に置いておくと、以降のパターンの違いがすっきり理解できます。

    3.MVC（おさらい）

    3.1 構成要素

    • Model（モデル）：業務ロジックとデータ。UI に依存しない
    • View（ビュー）：画面表示。Model の状態を見て描画する
    • Controller（コントローラー）：ユーザー入力を受け取り、Model を操作する。Model を操作し、View へ結果を渡す仲介役

    3.2 動きの典型例

    1. ユーザーがボタンを押す
    2. Controller がイベントを受け取る
    3. Controller が Model を更新する
    4. Model の変化を View が描画する（古典的 MVC では Model から View へ通知）

    Web の MVC では、典型的にはリクエスト → Controller → Model → View（テンプレート）という一方向の流れになります（フレームワークによって View と Model の参照関係は変わります）。

    3.3 メリットと落とし穴

    メリット

    • Model が UI から独立していてテストしやすい
    • Controller・View・Model で役割が明確

    落とし穴

    • View と Controller の境界が曖昧になりやすい
    • View が Model を直接読む実装と、Controller 経由で読む実装が混在しがち
    • Controller が重くなりがち（Fat Controller）

    4.MVP（Model-View-Presenter）

    4.1 構成要素

    • Model：MVC と同じく業務ロジック・データ
    • View：画面表示。自分では何も決めず、Presenter の指示どおりに動く（受け身のビュー、ダムビュー）
    • Presenter（プレゼンター）：View からのイベントを受け取り、Model を操作し、結果を View への指示として返す。View を「直接操作」する

    4.2 MVC との違い

    MVP では、View は Model を直接見ないのが特徴です（ただし流派によって異なります。10 節参照）。すべての描画指示は Presenter から View へ渡ります。

    4.3 メリットと落とし穴

    メリット

    • View が完全に受け身になり、Presenter だけを単体テストできる
    • ロジックが Presenter に集まり、追跡しやすい

    落とし穴

    • View ⇔ Presenter のインターフェース定義が手作業で煩雑になる
    • Presenter が肥大化しがち（「神 Presenter」問題）

    5.MVVM（Model-View-ViewModel）

    5.1 構成要素

    • Model：データ・業務ルール（MVC・MVP と同じ）
    • View：画面の見た目。ViewModel を観察して自動で更新される
    • ViewModel（ビューモデル）：View のための状態と、View が呼ぶ操作を提供する。ユーザー操作に応じて Model を更新する

    5.2 最大の特徴：データバインディング

    MVVM の最大の特徴は、View が ViewModel を「観察」することです。View と ViewModel が双方向にバインディングされています。

    • ViewModel の値が変わる → View が自動で更新される
    • View で入力される → ViewModel の値が自動で更新される

    これにより、Controller に相当する「橋渡しのコード」をほとんど書かずに済みます。

    5.3 得意な場面

    • GUI・デスクトップアプリ（WPF、.NET MAUI）
    • モバイル（SwiftUI、Jetpack Compose）
    • SPA（Vue、Angular、現代的な React ＋ 状態管理）

    5.4 メリットと落とし穴

    メリット

    • View に描画ロジックをほぼ書かないで済む
    • ViewModel を画面なしで単体テストできる
    • 同じ ViewModel に対して複数の View（PC／モバイル）を作りやすい

    落とし穴

    • データバインディングの仕組みにフレームワーク依存する
    • 双方向バインディングがバグの追跡を難しくすることがある

    6.3つのパターンの比較

    観点MVCMVPMVVM
    間を取り持つ役ControllerPresenterViewModel
    View が見る（知る）ものModel と Controller（古典的）Presenter のみViewModel だけ
    ロジックの主体ControllerPresenterViewModel
    View の役割描画＋一部の入力処理完全に受け身バインディングで自動更新
    データの流れ・更新方向主に一方向。Model から通知（push）Presenter からの指示双方向データバインディング
    テスト容易性Controller が重くなりがちPresenter を単体テストできるViewModel を UI 抜きでテストできる
    主な舞台・向く場面古典的・サーバーサイドの Web FW（Rails など）デスクトップ・AndroidGUI・リッチクライアント・SPA

    正解はひとつではない

    どれが「正解」ということはなく、フレームワークと文化に応じて選ぶものです。共通点は「View をできるだけ薄くし、ドメイン（業務ロジック）を独立させる」という方針です。

    6.1 その他の派生パターン

    Flux / Redux

    React と一緒に使われる一方向データフロー。「Action → Reducer → Store → View」の流れ。MVC／MVVM とは違う発想ですが、関心の分離は同じです。

    MVP の2流派

    Supervising Controller と Passive View。10 節で詳しく扱います。

    Clean Architecture

    MVC／MVVM より広い範囲（アプリ全体の依存の向き）を扱います（→ 依存性のルールとクリーンアーキテクチャ）。

    7.コード例：同じ要件を3通りで書く

    要件：「カウンターの数を +1 するボタン」

    7.1 MVC 風（Web サーバー）

    // Model
class Counter { constructor() { this.count = 0; } }
const model = new Counter();

// View（HTML テンプレート）
// <form method="post" action="/increment"><button>+</button></form><span>{{count}}</span>

// Controller
app.post('/increment', (req, res) => {
  model.count += 1;
  res.render('view', model);
});

    ボタンを押すたびに HTTP リクエストが飛び、Controller が Model を更新して、ページ全体の HTML を作り直して返します。

    7.2 MVVM 風（Vue）

    // ViewModel
const vm = reactive({
  count: 0,
  increment() { vm.count += 1; }
});

// View（Vue テンプレート）
// <button @click="increment">+</button><span>{{ count }}</span>
// → count の変更が自動で画面に反映される

    ViewModel の count を書き換えるだけで、バインディングによって画面が更新されます。「画面を更新する」コードはどこにもありません。

    7.3 Redux 風（単方向データフロー）

    // Reducer
function reducer(state = { count: 0 }, action) {
  if (action.type === 'INCREMENT') return { count: state.count + 1 };
  return state;
}

// View（JSX）
<button onClick={() => dispatch({ type: 'INCREMENT' })}>+</button>
<span>{state.count}</span>

    View は「INCREMENT が起きた」というアクションを送るだけで、状態の変え方は Reducer に集まっています。データは「アクション → 新しい状態 → 描画」と一方向にだけ流れます。

    8.フロントエンドの状態管理との対応

    モダンなフロントエンド（React、Vue など）では、状態管理ライブラリを使うのが一般的です。

    • Redux、Zustand（React 系）
    • Vuex、Pinia（Vue 系）
    • NgRx（Angular）

    これらは、MVVM の考え方をより明示的にフロントエンドに持ち込んだものと理解できます（Redux や NgRx は、厳密には Flux 系の単方向データフローです。13 節参照）。

    8.1 対応関係（おおまかに）

    クラシック MVVMモダンフロント
    ModelAPI クライアント／ビジネスロジック関数
    Viewコンポーネント（JSX、テンプレート）
    ViewModelストア（Store）＋セレクター＋アクション
    データバインディングリアクティブ更新（state → 再描画）

    8.2 状態管理を使うときの落とし穴

    • ストアにビジネスロジックを書きすぎる：本来 Model に置くべき計算がストアの中に紛れ込む
    • 状態を全部グローバルストアに入れる：本来コンポーネントのローカル状態でよいものまで入れて肥大化する
    • UI の都合の状態とドメインの状態を混ぜる：「モーダルが開いている」「フォームの入力値」とドメインデータが同じストアに混在する

    「ストアに何を入れて、何を入れないか」も、結局はUI とドメインを分離する設計判断の延長です。フロントエンドの状態管理ライブラリの詳細は（41 外のノート：36_状態管理）を参照してください。

    9.GUI アーキテクチャの系譜

    ここまでは MVC・MVP・MVVM の3つを比較しました。しかし実際の歴史はもっと枝分かれしていて、「MVP」と呼ばれるものにも複数の流派があり、MVVM にも前身があります。これを知らないと、資料によって説明が食い違う理由が分かりません。ここからは Martin Fowler の論考「GUI Architectures」（2006）を軸に、「画面のロジックをどこに置くか」という1本の軸で系譜を整理します。

    9.1 Forms and Controls（フォームとコントロール）

    1990 年代の Visual Basic や Delphi でおなじみの、最も素朴な形です。

    • フォーム（画面）に、コントロール（テキストボックス・ボタンなどの部品）を並べる
    • 単純なデータの表示はデータバインディングで行い、複雑な処理はイベントハンドラに書く
    Button1_Click() {
  if (txtQuantity.Text > stock) {     ← ドメインロジック
    lblError.Visible = true           ← プレゼンテーションロジック
    lblError.Text = "在庫が足りません"
  }
}

    良い点

    作るのが簡単で速い。

    悪い点

    画面とロジックが同じ場所にあるため、ロジックだけをテストできない。画面が増えると同じロジックが重複する。

    後のすべてのパターンは、この「全部フォームに書く」状態から、何を外に出すかの工夫です。

    10.MVP の2つの流派

    MVP（Model-View-Presenter）は 1990 年代半ばに Taligent 社（Apple と IBM の合弁）で生まれ、Dolphin Smalltalk で広まりました。Fowler は 2006 年に、MVP を2つのパターンに分けて整理しました。

    10.1 Supervising Controller（監督するコントローラー）

    単純な表示の同期は View に任せ（データバインディング）、複雑なロジックだけを Presenter が担当する。

    • ユーザーの操作は View が受けて Presenter に渡す
    • 「名前を表示する」程度の単純な同期は、View がデータバインディングで行う（そのため View は Model を知っている）
    • 「在庫が足りなければボタンを無効化してエラーを出す」のような複雑な処理は Presenter が行う

    10.2 Passive View（受け身のビュー）

    View は完全に受け身で、ロジックを一切持たない。表示の更新はすべて Presenter が行う。

    • View は Model を知らない。Presenter から「このテキストを表示せよ」「このボタンを無効にせよ」と言われたとおりにするだけ
    • データバインディングも使わない
    Passive View：View はインターフェースだけ 
    interface OrderView {
  setPrice(text: string): void;
  setOrderButtonEnabled(enabled: boolean): void;
  showError(message: string): void;
}

class OrderPresenter {
  constructor(private view: OrderView, private model: OrderModel) {}

  onQuantityChanged(quantity: number) {
    const result = this.model.canOrder(quantity);      // ドメインロジックは Model
    this.view.setOrderButtonEnabled(result.ok);         // 表示の判断は Presenter
    this.view.setPrice(`${this.model.priceFor(quantity).toLocaleString()} 円`);
    if (!result.ok) this.view.showError(result.reason);
  }
}

// テストでは偽物の View を渡すだけで、画面なしに振る舞いを検証できる
    補足：偽物の View を使ったテストのイメージ
    class FakeOrderView implements OrderView {
  price = ""; enabled = true; error: string | null = null;
  setPrice(text: string) { this.price = text; }
  setOrderButtonEnabled(enabled: boolean) { this.enabled = enabled; }
  showError(message: string) { this.error = message; }
}

test("在庫を超える数量では注文ボタンが無効になる", () => {
  const view = new FakeOrderView();
  const presenter = new OrderPresenter(view, new OrderModel({ stock: 3, unitPrice: 1000 }));
  presenter.onQuantityChanged(5);
  expect(view.enabled).toBe(false);
  expect(view.error).not.toBeNull();
});

    画面フレームワークを一切起動せずに、「ボタンが無効になるか」「エラーが出るか」というプレゼンテーションロジックまで検証できるのが Passive View の強みです（OrderModel のコンストラクタ引数は説明用の仮のものです）。

    10.3 2つの比較

    観点Supervising ControllerPassive View
    View のロジック単純な同期（データバインディング）を持つ一切持たない
    Presenter の仕事複雑な処理だけ表示の更新すべて
    テスト容易性高い（ただし View の同期部分はテストしにくい）最も高い（View 以外すべてテストできる）
    コード量少なめ多め（すべての表示更新を書く）
    向いているデータバインディングが強力な環境テストを最優先したいとき

    説明が食い違う理由

    資料によって「MVP では View は Model を知らない」「いや知ってよい」と説明が食い違うのは、Passive View と Supervising Controller のどちらを MVP と呼んでいるかの違いです。

    11.Presentation Model から MVVM へ

    11.1 Presentation Model とは

    Fowler が 2004 年ごろに整理したパターンです。

    画面の状態と振る舞いをすべて持つ「画面専用のモデル」を作り、View はそれと同期するだけにする。

    • Presentation Model は「注文ボタンが有効か」「エラーメッセージは何か」「表示用の価格文字列」といった画面の状態をプロパティとして持つ
    • View はそのプロパティを読んで描画し、操作があれば Presentation Model のメソッドを呼ぶ
    • Presentation Model はView を知らない（Passive View の Presenter が View を知っているのとは逆）
    Presentation Model：画面の状態と振る舞いを持つが、View は知らない 
    class OrderPresentationModel {
  quantity = 1;
  get price(): string { return `${this.model.priceFor(this.quantity).toLocaleString()} 円`; }
  get canOrder(): boolean { return this.model.canOrder(this.quantity).ok; }
  get errorMessage(): string | null {
    const r = this.model.canOrder(this.quantity);
    return r.ok ? null : r.reason;
  }
  constructor(private model: OrderModel) {}
}

    11.2 MVVM は Presentation Model の一種

    2005 年、Microsoft の John Gossman が WPF（Windows の UI フレームワーク）向けに MVVM を発表しました。MVVM の ViewModel は、Presentation Model を強力なデータバインディングと組み合わせたものです。

    • Presentation Model では、View と同期するコードを自分で書く必要があった
    • WPF のデータバインディングがそれを自動化したので、ViewModel のプロパティを書き換えるだけで画面が更新されるようになった

    つまり、「ViewModel ＝ 画面のための Model」です。「View のためのロジック置き場」というより、「画面の状態そのもの」と捉えると理解しやすくなります。ただし、ビジネスルールは ViewModel ではなく Model 側に持たせます。

    12.Humble Object（謙虚なオブジェクト）

    ここまでのパターンに共通する、テストのための考え方です。

    テストしにくい部分（画面・DB・外部 API）は、ロジックを持たない「謙虚な（humble）」薄い層にし、ロジックはテストしやすいオブジェクトに移す。

    • Michael Feathers が「The Humble Dialog Box」（2002）として提唱し、Gerard Meszaros『xUnit Test Patterns』で Humble Object パターンとして一般化されました
    • Passive View は、Humble Object を GUI に当てはめた典型例です
    • Robert C. Martin も『Clean Architecture』で、Presenter と View の境界を Humble Object で説明しています

    この考え方は GUI に限りません。クリーンアーキテクチャの Interface Adapters、ヘキサゴナルの Adapter も「外部との境界を薄くし、ロジックを内側へ」という同じ発想です（→ 依存性のルールとクリーンアーキテクチャ、ヘキサゴナルアーキテクチャ）。

    13.Web の MVC と、その後の単方向データフロー

    13.1 Web MVC（Model 2）

    1999 年ごろ、Java の JSP の設計で Model 2 と呼ばれる形が登場し、Struts・Ruby on Rails・Spring MVC・Express に受け継がれました（→ MVC（定義・Web の MVC・MVC 違反））。

    Smalltalk の MVCWeb の MVC（Model 2）
    Controller の役割キーボード・マウスの入力を処理HTTP リクエストを受けて処理を振り分ける
    View の更新Model の変更通知（Observer）で自動更新リクエストごとにHTML を生成して返す
    寿命画面が開いている間ずっと生きている1リクエストで終わる

    名前は同じでも、中身はかなり違うパターンです。「Web の MVC は本来の MVC ではない」と言われるのはこのためです。

    13.2 単方向データフローへ

    2014 年ごろから、フロントエンドでは Flux（Facebook）・Redux・Elm Architecture のような単方向データフローが主流になりました。

    • 双方向データバインディング（MVVM）は、画面が複雑になると「どこで状態が変わったか」が追いにくくなる
    • そこで「状態 → 描画 → 操作（アクション）→ 新しい状態」と、データを一方向にだけ流す

    詳しくは（41 外のノート：47_フロントエンド設計『02_UIは状態の関数と単方向データフロー』）を参照してください。

    14.系譜のまとめ表

    パターン年（目安）プレゼンテーションロジックの置き場所View が知っているものテスト容易性
    Forms and Controls1990年代フォーム（View）のイベントハンドラすべて低い
    MVC（Smalltalk）1979View と Controller に分散Model中

    Passive View2006（整理）すべて PresenterPresenter だけ最も高い

    単方向データフロー2014〜ストア（Reducer）・セレクター状態（読み取り専用）高い

    Fowler 自身も、Presentation Model・Supervising Controller・Passive View のどれを選ぶかは、使っている GUI 環境での作りやすさと好みの問題だと述べています。大事なのはパターン名ではなく、次の共通の原則です。

    共通の原則

    ドメインロジックを画面から外す。プレゼンテーションロジックも、テストしたいなら描画から外す。

    15.共通する大原則

    3つのパターンと状態管理ライブラリに共通する大原則は、次の3つです。

    1. View（描画）をできるだけ薄くする
    2. ドメイン（業務ロジック）は UI から独立させる
    3. View ⇔ ドメインの橋渡し役（Controller / Presenter / ViewModel / Store）を明示的に置く

    つまり、「MVC の C が MVP の P になり、MVVM の VM になり、状態管理の Store になった」と捉えると、

    • 名前は変わっても、やっていることの本質は同じ
    • それぞれはフレームワークや時代の流行に合わせた表現

    だと分かります。これは次に扱うクリーン／ヘキサゴナル／オニオンの依存ルールにもつながる発想です。

    16.よくある誤解

    「フレームワークが MVC と書いてあるから、これは MVC」

    必ずしも誤りではありませんが、要注意です。たとえば Rails の「MVC」は、Model にビジネスロジックと DB 操作の両方が入りがちで、古典的な MVC とは中身が違います。名前より、実際にどこに何の責任があるかを見ることが大切です。

    「MVC は Web アプリ全体の構造である」

    誤りです。MVC は画面まわりのパターンです。DB アクセスやドメインロジックは Model の中か、別のレイヤーに置きます。「M」を単なる DB モデルと混同すると責務が崩れます。

    「Model と DB テーブルは同じ」

    誤りです。Model はドメイン（業務ロジック）を表すもので、DB の構造とは別物です。DB テーブルそのものを Model にしてしまうと、業務ルールがSQL の中や画面コードの中に分散してしまいます。

    「MVVM の ViewModel は View のロジック置き場」

    誤りです。ViewModel はView に必要な状態・操作を提供する場所（画面のための Model）です。ビジネスルールは Model 側に持たせます。

    「MVVM が一番新しいから一番良い」「どれかが常に優れている」

    誤りです。ベストはコンテキスト次第で、用途で選ぶのが正解です。

    • サーバーサイドで HTML を返す → MVC が自然
    • リアクティブな単一ページアプリ・動的 GUI → MVVM／状態管理が自然
    • イベント駆動のデスクトップアプリ → MVP が向くことも
    「MVP は1種類」

    誤りです。Supervising Controller と Passive View の2つの流派があり、View が Model を知っているかどうかが違います。

    「MVVM はまったく新しい発明」

    誤りです。MVVM は Presentation Model を、強力なデータバインディングのある環境に合わせたものです。

    「Web の MVC と Smalltalk の MVC は同じ」

    誤りです。名前は同じでも、Controller の役割と View の更新方法がまったく違います。

    17.まとめ

    • UI とドメインを分離する目的は、ロジックの再利用・テスト容易性・変更の局所化です。
    • 代表的なパターンは MVC・MVP・MVVM の3つで、いずれも「View を薄く、ドメインを独立させる」が共通の方針です。違いはプレゼンテーションロジックをどこに置くかです。
    • MVC：View が Model を見る（Model から通知）／MVP：View は Presenter の指示で動く／MVVM：View は ViewModel を観察して自動更新。
    • Forms and Controls は全部フォームに書く、すべての出発点です。
    • MVP には Supervising Controller（単純な同期は View）と Passive View（View は完全に受け身）の2流派があります。
    • Presentation Model は画面専用のモデルで、MVVM はそれをデータバインディングと組み合わせたものです。
    • Humble Object：テストしにくい境界を薄くし、ロジックをテストしやすい場所へ移す。クリーンアーキテクチャのアダプタにも通じます。
    • Web MVC（Model 2）は Smalltalk の MVC とは別物。フロントエンドはその後単方向データフローへ進みました。モダンフロントの状態管理ライブラリは MVVM の発展形として理解できます。
    • 「フレームワークの名前」ではなく「実際の責任配置」を見ることが、設計判断の本質です。
