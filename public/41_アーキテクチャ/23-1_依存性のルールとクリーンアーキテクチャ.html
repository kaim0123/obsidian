    依存性のルールとクリーンアーキテクチャ

    クリーンアーキテクチャの同心円4層（Entities / Use Cases / Interface Adapters / Frameworks & Drivers）に何を書き、何を書かないかを、コード例つきで整理します。そのうえで、本体である「ソースコードの依存は外側から内側へのみ」という依存性のルールと、それを依存性逆転（DIP）で実現する仕組み、導入してかえってコードが汚くなる原因まで扱います。

    もとにしたノート：依存性のルール / クリーンアーキテクチャの概要 / レイヤー構成（21_レイヤー） / クリーンアーキテクチャを入れたら、コードが汚くなった（動画要約） / 00_解説_アプリ内部構造

    1.このページで扱うこと

    クリーンアーキテクチャ（Clean Architecture）は、Robert C. Martin（通称 Uncle Bob、アンクル・ボブ）が提唱した、長持ちするソフトウェアを作るための設計方針です。「クリーン」という名前のとおり、フレームワークや DB に依存しない、純粋で変更に強い構造を目指します。

    クリーンアーキテクチャといえば4重の同心円の図が有名ですが、その中で最も大事なのはたった1つのルール、依存性のルール（The Dependency Rule）です。

    ソースコードの依存関係は、外側から内側へのみ向かわなければならない。

    このルールが守られていれば、システムは変更に強くなります。逆に守られていなければ、どんなにきれいな同心円の図を描いても意味がありません。このページでは次の内容を順に扱います。

    • クリーンアーキテクチャの成り立ちと「約束したもの」
    • 同心円の4つの層と、各層に 書くべきこと／書くべきでないこと（コード例つき）
    • 依存性のルールの意味、OK 例と NG 例
    • 内側から外側を使うための仕掛け：依存性逆転（DIP）
    • 層をまたぐデータの渡し方（DTO）、層ごとの import ルール、フォルダ構成、テスト
    • メリット・デメリット、よくある NG パターン、そして「導入したらコードが汚くなった」と言われる理由

    このページの一言要約

    クリーンアーキテクチャの本体は4つの円ではなく「依存は内向きのみ」の1行です。円の数やディレクトリ構成は手段にすぎません。

    2.クリーンアーキテクチャの成り立ち

    生みの親：ロバート・C・マーティン

    クリーンアーキテクチャを提唱したロバート・C・マーティンは、2001 年の「アジャイルソフトウェア開発宣言」に名を連ねた 17 人の1人で、2008 年の著書『Clean Code』で広く知られるようになりました。SOLID 原則を構成する各原則も彼が提唱したものです（ただし「SOLID」という頭文字の並びを考えたのはマイケル・フェザーズです）。

    2012 年 8 月、マーティンはブログ記事「The Clean Architecture」で、4つの同心円の図を発表しました。円は内側から エンティティ、ユースケース、インターフェースアダプター、フレームワークとドライバー の順に並びます。そして、そこに課されたルールは1つだけ、依存性のルールでした。2017 年には書籍『Clean Architecture』として体系化されています。

    ゼロからの発明ではなく「統合」

    クリーンアーキテクチャは、まったく新しい発明というより、先行するアーキテクチャを統合したブランドに近いものです。マーティン本人も「細部は違うが狙いは同じだ」と認めています。

    年提唱者アーキテクチャ
    1992イヴァー・ヤコブソンBCE（Boundary-Control-Entity）
    2005アリスター・コーバーンヘキサゴナルアーキテクチャ（ポート&アダプタ）
    2008ジェフリー・パレルモオニオンアーキテクチャ
    2012ロバート・C・マーティンクリーンアーキテクチャ（上記を統合）

    クリーンアーキテクチャが約束したもの

    • 交換可能な部品：ビジネスルールを円の中心に隔離すれば、DB・Web フレームワーク・UI は後から取り換えられる部品になります。
    • 決定を遅らせられる：「良いアーキテクトは、まだ決めていない決定の数を最大化する」。DB やフレームワークの決定をぎりぎりまで遅らせられる構造が良い構造だ、という考え方です。
    • テストが回る：中心が DB にも Web にも依存しなければ、サーバーを立てずにテストを実行できます。
    • 叫ぶアーキテクチャ（Screaming Architecture）：2011 年のブログ記事で、マーティンは「ディレクトリ構成は『Rails です』ではなく『会計システムだ』と叫ぶべきだ」と主張しました。構造を見ればフレームワークではなく業務が分かるべき、という意味です。

    約束の中身

    クリーンアーキテクチャが約束したのは交換可能性とテスト性であって、ファイルやディレクトリを増やすことではありませんでした。この点は第 12 章の「コードが汚くなる理由」で効いてきます。

    なぜこうするのか：4つの独立

    1. フレームワークから独立

    Rails や Next.js が廃れても、ビジネスの中核（Entities・Use Cases）はそのまま動きます。

    2. DB から独立

    MySQL から MongoDB に変えても、中心のロジックは変更不要です。

    3. UI から独立

    Web → モバイル → CLI と入れ替えても、業務ルールを再利用できます。

    4. テストが独立して書ける

    外部依存（DB・API・UI）をモックにして、純粋な Use Case・Entity だけをテストできます。

    3.象徴的な「同心円」と4つの層

    クリーンアーキテクチャは、よく次のような同心円の図で表現されます。外側ほど詳細で変わりやすく、内側ほど中核で変わりにくいものを置きます。

    層役割例
    Entities企業全体のビジネスルール。どのアプリでも共通する「物事のあり方」User, Order, Money, Product
    Use Casesアプリ固有の業務フロー。「ユーザーを登録する」「注文を確定する」など、アプリがやることを1つずつ表現するRegisterUserUseCase, PlaceOrderUseCase
    Interface AdaptersUse Case と外界の間の翻訳役Controller, Presenter, Gateway, Repository 実装
    Frameworks & Drivers一番外側。フレームワーク・DB・UI など差し替え可能な道具Express, React, PostgreSQL, Redis

    以下、各層に「何を書くべきか」「何を書くべきでないか」を、注文処理を題材にしたコードで見ていきます。

    層1：Entities（エンティティ層）

    書くべきこと

    • 業務上の概念（User、Order、Product、Email、Price…）
    • 業務ルール（canCancel()、applyDiscount() など）
    • 不変条件の保証（メール形式の検証、金額が負にならない、など）

    書くべきでないこと

    • DB アクセス
    • HTTP / REST
    • フレームワーク固有のもの
    • UI / ビュー
    entities/Order.ts 
    class Order {
  constructor(
    public readonly id: string,
    public readonly items: OrderItem[],
    private _status: OrderStatus
  ) {
    if (items.length === 0) throw new Error('注文には最低1つの商品が必要');
  }

  get status(): OrderStatus {
    return this._status;
  }

  canCancel(): boolean {
    return this._status === 'pending';
  }

  cancel(): void {
    if (!this.canCancel()) throw new Error('キャンセル不可');
    this._status = 'cancelled';
  }

  total(): number {
    return this.items.reduce((sum, i) => sum + i.price, 0);
  }
}

    外部依存がまったくない、純粋な業務モデルです。どこに持ち出しても動きます。コンストラクタで「商品が0件の注文は作れない」という不変条件を守り、「保留中（pending）のときだけキャンセルできる」という業務ルールをメソッドとして持っています。

    ※ もとのノートでは割引ルール applyDiscount(rate)（合計に 1 - rate を掛ける）も Entity の例として挙げています。こうした「業務の決まり事」が Entity の中身です。

    層2：Use Cases（ユースケース層）

    書くべきこと

    • アプリ固有の業務の流れ
    • Entity を組み立て、Repository で保存し、外部サービスを呼ぶ、といった流れ
    • トランザクション境界

    書くべきでないこと

    • HTTP や UI の詳細
    • フレームワーク固有の型
    • ビジネスルールそのもの（Entity に書くべき）
    usecases/PlaceOrderUseCase.ts 
    interface OrderRepository {
  save(order: Order): Promise<void>;
}
interface PaymentGateway {
  charge(amount: number): Promise<void>;
}

class PlaceOrderUseCase {
  constructor(
    private orderRepo: OrderRepository,
    private payment: PaymentGateway
  ) {}

  async execute(input: PlaceOrderInput): Promise<Order> {
    const order = new Order(
      generateId(),
      input.items.map(i => new OrderItem(i.id, i.price)),
      'pending'
    );
    await this.payment.charge(order.total());
    await this.orderRepo.save(order);
    return order;
  }
}

    ここが依存性逆転のポイント

    インターフェース（OrderRepository、PaymentGateway）は Use Case 層に定義します。Use Case は「保存できるもの」「課金できるもの」という抽象だけを知っており、MySQL や Stripe の名前は一切出てきません。

    層3：Interface Adapters（アダプタ層）

    この層に書くのは次のようなものです。

    • 翻訳役：HTTP リクエスト → Use Case の入力、Use Case の出力 → HTTP レスポンス、といった変換
    • Controller / Presenter / ViewModel
    • Repository の実装（Use Case が定義したインターフェースを実装し、DB につなぐ）
    adapters/controllers/OrderController.ts 
    class OrderController {
  constructor(private placeOrder: PlaceOrderUseCase) {}

  async handle(req: Request, res: Response) {
    const input = {
      items: req.body.items.map((i: any) => ({ id: i.id, price: i.price }))
    };
    const order = await this.placeOrder.execute(input);
    res.json({ id: order.id, total: order.total() });
  }
}
    adapters/repositories/MySQLOrderRepository.ts 
    class MySQLOrderRepository implements OrderRepository {
  async save(order: Order): Promise<void> {
    await db.query('INSERT INTO orders (id, status) VALUES (?, ?)', [
      order.id, order.status
    ]);
    // ...明細の保存など
  }
}

    Use Case が定義したインターフェースを、この層で実装します。HTTP の req/res や SQL といった「外の世界の言葉」は、ここで内側の言葉に翻訳されます。

    ※ もとのノートの例では Repository が order._status（private フィールド）を直接読んでいましたが、TypeScript ではコンパイルエラーになるため、Entity に読み取り専用の status ゲッターを追加した形に直しています。

    層4：Frameworks & Drivers（フレームワーク層）

    一番外側の層には、次のものを書きます。

    • Express / Fastify などの Web サーバー起動
    • MySQL / PostgreSQL などの DB 接続
    • 外部サービスのクライアント
    • main 関数・エントリポイント
    • 依存関係の組み立て（DI コンテナや手書きの配線）
    frameworks/main.ts 
    import express from 'express';
import { MySQLOrderRepository } from '../adapters/repositories/MySQLOrderRepository';
import { StripeGateway } from '../adapters/gateways/StripeGateway';
import { PlaceOrderUseCase } from '../usecases/PlaceOrderUseCase';
import { OrderController } from '../adapters/controllers/OrderController';

const app = express();

// 依存を組み立て
const orderRepo = new MySQLOrderRepository();
const payment = new StripeGateway();
const placeOrder = new PlaceOrderUseCase(orderRepo, payment);
const controller = new OrderController(placeOrder);

app.post('/orders', (req, res) => controller.handle(req, res));
app.listen(3000);

    ここが唯一、すべての層を知っている場所です。全部を組み立てる「配線板」の役割を持ちます。この組み立て場所は一般に Composition Root と呼ばれます（詳しくは DI・IoC・Composition Root）。

    4.依存性のルール — The Dependency Rule

    ルールの本質

    • 外側のものが、内側のものに依存してもよい
    • 内側のものが、外側のものに依存してはいけない

    つまり、Entities は何も知らない。Use Cases は Entities だけを知る。Adapter や Framework は外側から中を呼ぶだけ、ということです。矢印（依存）は必ず内側に向き、逆向きに依存してはいけません。

    「依存している」とはどういうことか

    あるモジュール A が、モジュール B を import したり、B のクラス名をコードに書いたりしているとき、「A は B に依存している」といいます。依存の矢印はデータの流れではなく「知っている」の向きです。

    // UserService が UserRepository に依存している
import { UserRepository } from './UserRepository';

class UserService {
  constructor(private repo: UserRepository) {}
}

    この「知っている」の矢印を、常に内側に向けるのがルールです。

    OK な例

    ○ 依存がすべて内側を向いている 
    // 内側（Entities）
class User {
  constructor(public email: string) {}
}

// 一つ外側（UseCase）
import { User } from '../entities/User'; // ✅ 内側への依存 OK

class RegisterUserUseCase {
  execute(input) { return new User(input.email); }
}

// さらに外側（Controller）
import { RegisterUserUseCase } from '../usecases/RegisterUserUseCase'; // ✅ 内側への依存 OK

class UserController {
  constructor(private useCase: RegisterUserUseCase) {}
}

    NG な例

    ✕ Entity が外側の Express に依存している 
    import { Request } from 'express';

class User {
  constructor(req: Request) { /* ... */ }
}

    User（Entity）はドメインの中心にある存在です。Express（フレームワーク）を知ってはいけません。Express の仕様が変わるだけで User が壊れてしまいます。

    ✕ UseCase が具体的な DB（MySQL）を知っている 
    import mysql from 'mysql2';

class PlaceOrderUseCase {
  async execute() {
    const conn = await mysql.createConnection(...);
    await conn.query('INSERT INTO orders ...');
  }
}

    Use Case はどの DB を使うかまで知るべきではありません。この書き方では、MySQL から PostgreSQL に変えるだけで Use Case が壊れます。

    5.依存性逆転（DIP）で内側から外側を使う

    ここで、「でも Use Case は DB に保存したい。依存を内側にしか向けられないなら、どうやって内側から外側を使うの？」という疑問が出てきます。本来なら「UseCase → DB」の向きに依存しそうなところです。

    この疑問に答えるのが 依存性逆転の原則（DIP）です。解決策は、インターフェースを内側に置くことです。

    // 内側：UseCase がインターフェースを定義
interface OrderRepository {
  save(order: Order): Promise<void>;
}

class PlaceOrderUseCase {
  constructor(private repo: OrderRepository) {} // 抽象に依存
}

// 外側：具体実装
class MySQLOrderRepository implements OrderRepository {
  async save(order: Order) { /* SQL */ }
}

    インターフェース（抽象）は内側にあり、実装（具象）は外側にあります。外側が内側のインターフェースを実装するので、ソースコードの依存の方向は外 → 内のままです。実行時の呼び出しは「Use Case → MySQL」の向きに流れますが、ソースコード上で相手の名前を知っているのは MySQL 側だけ、という状態になります。こうすると、Use Case は MySQL も PostgreSQL も知らないまま動きます。

    この仕掛けを 依存性逆転（Dependency Inversion）と呼びます。そして、実装をどこで選んで渡すかは第 3 章の main.ts（Composition Root）が担当します。これが依存性注入（DI）です。

    詳しくは 依存性逆転の原則（DIP）、インターフェースの切り方は インターフェースと抽象化 を参照してください。

    6.境界をまたぐデータ — DTO で持ち運ぶ

    層をまたぐ（Cross the Boundary）ときは、単純なデータ構造（DTO：Data Transfer Object）で持ち運ぶのが原則です。

    // Controller から UseCase へは、専用の入力 DTO で
class RegisterUserInput {
  constructor(public email: string, public age: number) {}
}

class RegisterUserUseCase {
  execute(input: RegisterUserInput) { /* ... */ }
}

    こうすることで、Use Case は HTTP リクエストの形状を知らずに済みます。HTTP の req.body を Use Case に直接渡してしまうと、Use Case が「外側の都合（HTTP）」に依存することになります。出力側も同様で、Use Case の結果は Presenter が ViewModel / レスポンス用の形に変換して View に渡します。

    ただし「詰め替えの沼」に注意

    リクエストモデル → DTO → エンティティ → レスポンスモデル、と境界ごとに型を作りすぎると、項目を1つ追加するだけで多数のファイルを触ることになります（第 12 章参照）。DTO は本当に守りたい境界に使うものです。

    7.層ごとの import ルールと依存の見分け方

    層ごとの import ルール

    層import してよいもの
    Entities他の Entities のみ（または何も import しない）
    Use CasesEntities・自分が定義したインターフェース
    Interface AdaptersUse Cases・Entities・インターフェース・フレームワーク
    Frameworks & Drivers何でも（Adapter・Use Case・Entity すべて）

    外側の層ほど多くを知り、内側ほど何も知らないのが理想形です。

    判定チェックリスト

    コードを開いたら、まずファイル先頭の import 文を見ます。

    1. Entity は何を import しているか？ → 何も（または他の Entity のみ）
    2. Use Case は何を import しているか？ → Entity とインターフェース
    3. Adapter は何を import しているか？ → Use Case とインターフェース（＋フレームワーク）
    4. Framework 層は何を import しているか？ → すべて（Adapter, Use Case, Entity）

    ルールを人の規律ではなく機械の検査に

    import の向きは機械的にチェックできます。Java なら ArchUnit で「domain パッケージは infrastructure パッケージに依存しない」といったルールをテストとして書き、違反したら CI を落とせます。TypeScript でも dependency-cruiser や ESLint の import 制限ルールなどで同じことができます。

    8.フォルダ構成例

    「ボブおじさんの同心円」をそのままコードに落とすと、次のようなフォルダ構成になります。

    src/
├─ entities/               ← 中央：企業全体のルール
│   ├─ Order.ts
│   ├─ OrderItem.ts
│   └─ User.ts
├─ usecases/               ← ユースケース（＋インターフェース定義）
│   ├─ PlaceOrderUseCase.ts
│   ├─ CancelOrderUseCase.ts
│   └─ RegisterUserUseCase.ts
├─ adapters/               ← 変換役
│   ├─ controllers/
│   │   └─ OrderController.ts
│   ├─ presenters/
│   │   └─ OrderPresenter.ts
│   ├─ repositories/
│   │   └─ MySQLOrderRepository.ts
│   └─ gateways/
│       └─ StripeGateway.ts
└─ frameworks/             ← 外側：道具と配線
    ├─ main.ts
    ├─ db.ts
    └─ config.ts

    ディレクトリを4つ作っても、クリーンにはならない

    大事なのはフォルダ名ではなく依存の向きです。usecases/ の中のファイルが ORM の型を import していれば、フォルダがどれだけ整っていてもルール違反です。また「叫ぶアーキテクチャ」の考え方に立てば、orders/ users/ のように業務で切ってから中を層に分ける構成も有力です（垂直スライスアーキテクチャ 参照）。

    9.テストしやすさ — 層に分けた最大の恩恵

    Entity のテスト

    test('canCancel は pending なら true', () => {
  const order = new Order('1', [new OrderItem('a', 100)], 'pending');
  expect(order.canCancel()).toBe(true);
});

    依存がないので、すぐにテストできます。

    Use Case のテスト（モック注入）

    test('注文処理の流れ', async () => {
  const mockRepo = { save: jest.fn() };
  const mockPayment = { charge: jest.fn() };
  const useCase = new PlaceOrderUseCase(mockRepo, mockPayment);

  await useCase.execute({ items: [{ id: 'a', price: 100 }] });

  expect(mockPayment.charge).toHaveBeenCalledWith(100);
  expect(mockRepo.save).toHaveBeenCalled();
});

    DB も HTTP も使わずにテストできます。Use Case がインターフェースにしか依存していないので、テストではモックを渡すだけで済みます。これがクリーンアーキテクチャの本領です。

    10.メリット・デメリットと向いている場面

    メリット

    1. 変更に強い：外側（UI・DB・フレームワーク）が変わっても内側は無傷
    2. テスト容易：Use Case を外部依存なしで単体テストできる
    3. ドメインが主役・守られる：業務ルールがフレームワークの都合に振り回されず、読み取りやすい
    4. 長寿命：フレームワークが変わっても資産が残る

    デメリット

    1. 小規模だとオーバースペック：CRUD が中心ならやりすぎ
    2. 書く量が増える：変換・インターフェースが多い
    3. 学習コスト：新メンバーが迷う

    クリーンアーキテクチャは「ビジネスルールが豊かで、長く使う予定のシステム」に向きます。

    スタイル手軽さ・コストシンプルさデプロイ容易性テスト容易性拡張性耐障害性進化しやすさ
    レイヤード★★★★★★★★★★★★★★★★
    クリーン・ヘキサ・オニオン★★★★★★★★★★★★★★★

    レイヤードは『ソフトウェアアーキテクチャの基礎』（Richards & Ford）の評価、クリーン・ヘキサ・オニオンは書籍に評価がないためノート独自の目安です。1つのデプロイ単位である点はレイヤードと同じなので、デプロイ・スケール・耐障害性は変わりません。一方、ドメインを DB なしでテストでき外側を差し替えやすいぶんテスト容易性・進化しやすさが上がり、層とインターフェースが増えるぶんシンプルさ・コストが下がります。

    11.よくある NG パターンと「完璧主義にならない」

    NG 1：Entity に ORM のアノテーションを付ける

    ✕ Entity が ORM を知っている 
    @Entity() // ← ORM のアノテーション
@Table('users')
class User { /* ... */ }

    ORM に縛られると、Entity が外側（ORM）に依存してしまいます。厳格に守るなら、永続化用のモデルは Entity と別に用意し、Repository 実装で相互に変換します。

    NG 2：Use Case で HTTP 例外を throw する

    ✕ Use Case が HTTP を知ってしまう 
    throw new BadRequestException('invalid');

    Use Case はビジネス例外（例：OrderCannotBeCancelledError）を throw し、HTTP ステータスへの変換は外側の Controller で行うのが正しい形です。

    NG 3：View が Entity を直接使う

    Entity の内部構造が変わると View が壊れます。View には ViewModel / DTO で渡します。

    3つの NG に共通すること

    いずれも 内側が外側の事情を知ってしまっている状態です。

    完璧主義にならない

    依存性のルールを 100% 守ろうとすると、小さなアプリでは書く量が爆発します。重要な部分だけ厳密に守り、周辺は柔軟にというのが現実解です。特に、

    • Entities・Use Cases はフレームワーク非依存を死守する
    • Controllers・Adapters はフレームワーク依存でも OK

    と割り切ると、コストと効果のバランスがとりやすくなります。

    12.補足：「クリーンアーキテクチャを入れたら、コードが汚くなった」の正体

    ここでは動画「クリーンアーキテクチャを入れたら、コードが汚くなった」（IT技術屋のボヤキ）の要約から、導入の失敗パターンを整理します。動画の主張は、クリーンアーキテクチャの本体は「依存は内向きのみ」の1行であり、コードが汚くなるのはその誤読と過剰のせいだ、というものです。

    コードが汚くなる4つのメカニズム

    1. 図のカーゴカルト：4つの円をそのまま4つのディレクトリにするが、依存の向きは誰も検査しない。結果として、Use Case が ORM の型を参照していたりする。
    2. 実装が1つしかないインターフェースの量産：差し替える日は来ないのに、すべてにインターフェースを切る。エディタの「定義へ移動」で宣言に飛ばされ、読む人は毎回迷子になる。
    3. 詰め替えの沼：リクエストモデル → DTO → エンティティ → レスポンスモデル。項目を1つ追加するだけで 7 ファイル前後を触ることになる。
    4. 円の数の誤読：マーティンは「4つと決まっているわけではない、概念図だ」と明記しているのに、画面3枚の社内システムにまでフル装備の4層を敷いてしまう。

    原因はルールの誤読と過剰であって、依存性のルールそのものではありません。

    なぜ世界中で同じ誤読が起きたのか

    • 伝わり方の非対称：図は一目で覚えられるが、「依存は内向きのみ」は痛い目を見ないと腹落ちしない。そのため図だけが広がり、ルールは置き去りにされた。
    • コストとリターンの時間差：抽象化のコスト（ファイル増・詰め替え・学習時間）は今日払うが、リターンは DB を差し替える日にしか発生しない。そして多くのシステムはその日を迎えない（Rails から Django に乗り換えた、という話はほとんど聞かない）。
    • 批判者の存在：ダン・ノースは 2017 年に SOLID の全要素に疑義を示し、2022 年に対案として CUPID を発表した。「単純さは性質であって、層を増やして得るものではない」という主張である。
    • チームの理解度：1人だけが理解している4層は、その人が抜けた瞬間にただの迷路になる。

    誤読は個人の資質の問題ではなく、図の伝わりやすさとコストの時間差という構造から量産された、というのが動画の分析です。

    AI 時代のクリーンアーキテクチャ

    • 定型コードやインターフェースは AI が一瞬で書けるため、「7 ファイルの詰め替えが面倒」という反対理由は弱まった。
    • 一方で、間接参照だらけのコードは人間にも AI にも追いにくい。ホップ数が多いほど、AI が問題箇所を特定したり修正を提案したりする精度が落ちる。書くコストは下がったが、読むコストは残る。
    • ルールは人間の規律ではなく機械の検査にする（ArchUnit などで依存の向きをテストとして書き、違反したら CI を落とす）。
    • 価値が移る先は「どこに境界を引けば元が取れるか」の判断。変更が頻繁な場所の境界は元が取れるが、5 年触っていない DB への抽象は掛け捨てになる。

    動画のまとめ

    コードを汚したのは道具ではなく、1行のルールを様式として輸入した使い方です。綺麗なコードとは層が多いコードではなく、変更したい場所にまっすぐたどり着けるコードです。円は2つでも6つでもかまいません。

    13.他のアーキテクチャとの関係

    アーキテクチャクリーンとの関係
    レイヤードアーキテクチャ4層を上下に並べた古典的な表現。ただし伝統的なレイヤードではドメイン層がインフラ層（DB）に依存しており、依存の向きが違う
    ヘキサゴナルアーキテクチャポート&アダプタとして同じ思想を表現。層の内訳はクリーンより粗い（コア＋アダプタ）
    オニオンアーキテクチャ層をタマネギ状に描く。Domain Service と Application Service を分ける
    CQRSクリーンで「一覧画面のために Entity を大量に組み立てる」のがつらいときに、読み取り側だけ別モデルにする

    これら3つ（クリーン・ヘキサゴナル・オニオン）は 本質的にほぼ同じ思想（依存を内側へ、ドメインを中心に）で、図の描き方と用語が違うだけと捉えて差し支えありません。また、副作用（DB・HTTP）を外側の薄い殻に、純粋な計算を内側に置く「Functional Core, Imperative Shell」は、同心円型アーキテクチャを関数レベルで表したものです（41 外のノート：46_メソッド設計『03_Functional_Core_Imperative_Shell』）。SOLID 原則そのものは 41 外のノート：48_原則『SOLID』が本拠地です。

    14.よくある誤解

    誤解1：クリーンアーキテクチャ＝4つの同心円（4つのディレクトリ）

    本体は図ではなく「ソースコードの依存は外側から内側へのみ」というルールです。4つのディレクトリを作っても、内側が外側を import していればクリーンではありません。逆に、ディレクトリが2つでもルールが守られていれば、その精神に沿っています。

    誤解2：円は必ず4つでなければならない

    マーティン自身が「4つと決まっているわけではない、概念図だ」と明記しています。小さなシステムなら「ドメイン」と「それ以外」の2つでも十分なことがあります。

    誤解3：すべての依存にインターフェースを切るべき

    インターフェースが必要なのは、内側から外側を使う境界（DB・外部 API・メールなど）と、テストで差し替えたい場所です。実装が1つしかなく差し替える予定もない場所にまで切ると、読みにくさだけが増えます。

    誤解4：依存の向き＝処理（データ）の流れる向き

    依存の矢印は「ソースコード上で相手の名前を知っている」向きです。実行時には Use Case が Repository を呼び出しますが、DIP を使えばソースコード上は Repository 実装が Use Case 側のインターフェースを知っている（外 → 内）状態になります。

    誤解5：100% 厳密に守らないと意味がない

    小さなアプリで完全に守ると書く量が爆発します。Entities・Use Cases のフレームワーク非依存だけは死守し、Controller・Adapter は柔軟に、という割り切りが現実的です。

    15.まとめ

    • クリーンアーキテクチャは Robert C. Martin が 2012 年に提唱した、BCE・ヘキサゴナル・オニオンを統合した設計方針。約束したのは交換可能性とテスト性
    • 同心円は内側から Entities（企業全体のルール）→ Use Cases（アプリ固有の流れ）→ Interface Adapters（翻訳役）→ Frameworks & Drivers（道具と配線）
    • 唯一のルールは 依存性のルール：ソースコードの依存（import・クラス名の参照）は外側から内側へのみ。外側ほど多くを知り、内側ほど何も知らない
    • 内側から外側を使うときは、インターフェースを内側に置き、実装を外側に置く（DIP）。実装は main.ts などの Composition Root で組み立てて渡す（DI）
    • 層をまたぐときは DTO で運び、Use Case に HTTP の形を知らせない。ただし詰め替えすぎに注意
    • NG：Entity に ORM アノテーション／Use Case で HTTP 例外／View が Entity を直接使う。完璧主義にならず、中心だけは死守
    • コードが汚くなるのは、図のカーゴカルト・実装1つのインターフェース・詰め替えの沼・円の数の誤読という誤読と過剰のせい。大事なのは「どこに境界を引けば元が取れるか」
