    アーキテクチャとは・設計との違い

    ソフトウェアアーキテクチャとは「システムをどんな部品に分け、どうつなぎ、どんなルールで縛るか」という全体の骨組みのことです。このページでは、その定義と構成要素、『ソフトウェアアーキテクチャの基礎』の4つの側面、そして混同されやすい「設計（詳細設計）」との違いを、建築の比喩を使いながら順に整理します。

    もとにしたノート：01_ソフトウェアアーキテクチャとは／02_アーキテクチャと設計の違い／00ソフトウェアアーキテクチャ（＋ 10_基礎/00_解説_アーキテクチャの基礎）

    1.このページで扱うこと

    「アーキテクチャ」という言葉は開発の現場で頻繁に使われますが、初めて学ぶ人にとっては抽象的でとらえにくい概念です。さらに「設計」という言葉とどう違うのかも曖昧になりがちです。このページでは次のことを、省略せずに順を追って説明します。

    • ソフトウェアアーキテクチャを一言でいうと何か、建築の比喩でどうイメージするか
    • アーキテクチャを構成する要素（コンポーネント・関係性・原則と制約）と、『ソフトウェアアーキテクチャの基礎』の4つの側面
    • アーキテクチャを考えると何がうれしいのか
    • アーキテクチャと設計（詳細設計）の違い、両者の境界がグラデーションであること、それでも区別する理由
    • 実務で考える順番、代表的なアーキテクチャの「形」と、それらが生まれた歴史

    このページの結論

    アーキテクチャは「家の間取りと骨組み」、設計は「各部屋の家具配置と内装」です。両者とも構造を決める行為ですが、スコープ（広さ）と抽象度（高さ）、そして後から変えるコストが違います。

    2.ソフトウェアアーキテクチャを一言でいうと

    ソフトウェアアーキテクチャとは、ひとつのソフトウェアシステムを、どのような「部品（コンポーネント）」に分け、それらをどのように「つなぎ、役割分担させるか」という、システム全体の骨組み・構造のことです。

    言い換えると、「このシステムは何でできていて、どれとどれがどう連携するのか」という大きな絵のことです。コードの一行一行や、個々の関数・クラスの書き方（いわゆる「設計」や「コーディング」）よりも一段上にある、システム全体の形を決めるものがアーキテクチャです。

    業界でよく使われる定義

    業界では、ソフトウェアアーキテクチャを次の3つを意図的に決め、文書化・共有したものとして説明することが多くあります。

    1. ソフトウェアシステムを構成する主要なコンポーネント（部品） ― 何を「部品」とするか
    2. コンポーネント同士の関係（依存・通信・データの流れ） ― 部品同士がどう関係するか
    3. それらを支える原則や制約（ルール・技術選定・非機能要件への対応方針） ― どんなルールや制約で縛るか

    国際規格 ISO/IEC/IEEE 42010 も、アーキテクチャを「環境の中に置かれたシステムの基本的な概念や性質であり、その要素、関係、そして設計と進化の原則に具体化されたもの」と定義しています。表現は違っても、「部品・関係・ルール」の3つを扱うという点は共通しています。

    もう一つの有名な見方

    Martin Fowler は論考「Who Needs an Architect?」で、Ralph Johnson の言葉を引きながら、アーキテクチャを「重要なもの（それが何であれ）」「後から変えるのが難しい決定」ととらえる見方を紹介しています。この「変えにくさ」という視点は、後半の「設計との違い」を考えるうえで大きなヒントになります。

    3.建築のアーキテクチャにたとえて理解する

    「アーキテクチャ」という言葉は、もともと建築の世界の言葉です。ソフトウェアのアーキテクチャをイメージするために、まず家を建てる場面で考えてみます。

    建物における「アーキテクチャ」

    一軒の家を建てるとき、建築家は次のようなことを決めます。

    部屋の割り方

    リビング・寝室・キッチン・浴室など、どのような「部屋（＝部品）」に分けるか。

    部屋同士のつながり

    どこに廊下やドアを置き、どの部屋からどの部屋へ行けるようにするか。

    骨組みと強度

    土台・柱・梁をどう配置するか。何階建てにするか。

    設備の配置

    水道・電気・ガスをどこで分岐させ、どの部屋に引き込むか。

    これらは内装の色や家具の選び方（細部のデザイン）よりも前の段階で決まる、建物全体の形と構造です。この「全体の形と構造を決めること」が、建築の世界でのアーキテクチャです。

    ソフトウェアに置き換えると

    建築での例ソフトウェアでの例
    部屋の割り方機能をどの「サービス」や「モジュール」に分けるか
    部屋同士のつながりコンポーネント同士がどう連携・通信するか
    骨組み・階数サーバー構成、何層構造にするか（例：3層構造）
    設備の配置データベースやキャッシュをどこに置くか
    内装・家具（細部）クラス設計、関数の書き方（＝コードレベルの設計）

    つまり、アーキテクチャ＝システム全体の「部品の分け方」と「つなぎ方」の骨組み、設計（詳細設計・コーディング）＝その骨組みの上で、各部品をどう実装するかという細部、という関係になります。クラスや関数の分け方・依存のさせ方（41 外のノート：42_ソフトウェア設計『設計とは何か』で扱う内容）は、この細部の設計にあたります。

    4.アーキテクチャを構成する3つの要素

    ここからは、定義に出てきた「コンポーネント」「関係性」「原則・制約」を具体的に見ていきます。

    4.1 コンポーネント（部品・構成要素）

    コンポーネントとは、システムを構成する、ひとまとまりの機能や役割を持つ単位です。規模や見方によって、次のようなものがあります。

    種類説明例
    モジュール・パッケージコードのまとまりユーザー管理モジュール、注文処理モジュール
    サービスネットワーク越しに API で呼び出される独立したアプリケーション認証サービス、決済サービス
    レイヤー（層）役割で分けた「層」プレゼンテーション層、ビジネスロジック層、データアクセス層

    アーキテクチャを考えるときは、システムをどの粒度で分けるか（大きな1つの塊にするか、細かくサービスに分けるか）と、それぞれにどんな責任（役割）を持たせるかを決めます。これが「コンポーネントの設計」です。

    4.2 関係性（つながり・依存・データの流れ）

    コンポーネントが決まっても、お互いにどう連携するかが決まっていなければシステムは動きません。そこで考えるのが関係性です。

    • 依存の向き：「A は B を使うが、B は A を知らない」のように、どちらがどちらに依存するかを決めます。依存の向きをそろえることで、変更の影響範囲を限定できます。
    • 通信の方法：同じプロセス内の関数呼び出しなのか、HTTP API なのか、メッセージキューなのか。
    • データの流れ：どこでデータが作られ、どこに渡され、どこに保存されるか（データフロー）。

    「どのコンポーネントが、どのコンポーネントと、どのような方法でつながるか」を決めることが、アーキテクチャの関係性の部分です。

    4.3 原則・制約（ルールと技術選定）

    アーキテクチャには、守るべきルールや制約も含まれます。これは、チーム全員が同じ方針で開発・変更できるようにするために重要です。

    • 設計原則：例「ビジネスロジックは DB や UI に直接依存しない」「新機能は既存コードを壊さずに追加する」
    • 技術選定：使用する言語、フレームワーク、データベース、インフラ（オンプレミスかクラウドか）など
    • 非機能要件への対応方針：パフォーマンス・可用性・セキュリティ・スケーラビリティを、アーキテクチャのどの部分でどう実現するか（→ 品質特性と非機能要件・特性の見つけ方）

    「何をしてよいか・してはいけないか」「何を使って実現するか」をアーキテクチャの一部として明文化しておくのが、原則・制約です。

    5.『ソフトウェアアーキテクチャの基礎』の4つの側面

    Mark Richards と Neal Ford の『ソフトウェアアーキテクチャの基礎』では、ソフトウェアアーキテクチャを次の4つの側面から成り立つものとして説明しています。

    側面役割
    ① アーキテクチャスタイルシステム全体の型。レイヤード、マイクロサービスなど（詳しくは下の§12）
    ② アーキテクチャ特性システムが備える性質と成功基準を定め、システムが「どうあるべきか」を示す（性能・可用性・保守性など）
    ③ 論理コンポーネントシステムの振る舞い（機能のまとまり）を定義する
    ④ アーキテクチャ決定システムをどのように構築すべきかのルールを定める（例：「UI 層から DB を直接呼ばない」）

    2つの見方の比較

    前の節の「3要素」と、この「4つの側面」は、見方が違うだけで矛盾するものではありません。

    見方構成要素
    構造としての見方① コンポーネント　② 関係性（依存・データの流れ）　③ 原則・制約
    『ソフトウェアアーキテクチャの基礎』の見方① アーキテクチャスタイル　② アーキテクチャ特性　③ 論理コンポーネント　④ アーキテクチャ決定

    どちらも「部品と、その関係と、それを縛るルール」を扱っている点は共通しています。後者はそこに「何を良しとするか（特性）」を明示的に加えているのが特徴です。特性については 品質特性と非機能要件・特性の見つけ方、論理コンポーネントについては アーキテクチャ量子と粒度・論理コンポーネント で詳しく扱います。

    6.なぜソフトウェアアーキテクチャが重要か

    アーキテクチャをきちんと考えると、次のようなメリットが得られます。

    変更しやすさ（保守性・拡張性）

    役割が分かれていれば、変更したい部分だけに手を入れやすくなります。依存の向きが整理されていれば、ある部分の変更が他の部分に及ぼす影響を小さくできます。

    複数人での開発（分業と責任の明確化）

    コンポーネントごとに担当を分けやすくなり、「この部分は誰が責任を持つか」が明確になって、重複や抜け漏れを減らせます。

    品質と信頼性（テスト・障害の局所化）

    部品ごとに単体テスト・結合テストをしやすくなります。障害が起きたときも「どのコンポーネントの問題か」を切り分けやすくなります。

    パフォーマンス・スケーラビリティ

    負荷が高い部分だけをスケールさせたり、キャッシュや DB の配置を決めたりするのはアーキテクチャの判断です。性能や拡張性を計画的に改善できます。

    共通の理解（意思決定の根拠）

    アーキテクチャを図や文書で残しておくと、「このシステムはこういう形になっている」という共通の認識が生まれます。新メンバーのオンボーディングや、技術的な意思決定の根拠になります（→ 意思決定の進め方と ADR）。

    意識しないまま開発を進めると

    • 変更のたびに全体に影響が及ぶ
    • どこに何があるか分からず、修正が怖い
    • チームで役割分担がしづらい

    といった状態になりやすく、技術的負債がたまっていきます（→ なぜ早く意識するか・アーキテクトの役割と思考、技術的負債と意図的な暫定案）。

    7.アーキテクチャと設計（詳細設計）の違い

    「アーキテクチャ」と「設計」は、現場でしばしば混同されます。どちらも「構造を決める」行為ですが、扱うスコープと抽象度が違います。

    7.1 一言での違い

    観点アーキテクチャ設計（詳細設計）
    何を決めるかシステム全体の骨組み個々の部品の中身
    粒度粗い（サービス、レイヤー、コンポーネント）細かい（クラス、メソッド、変数）
    抽象度高い低い
    主な関心部品の分け方、つなぎ方、原則アルゴリズム、データ構造、命名
    主な成果物アーキテクチャ図、ADR、原則ガイドクラス図、シーケンス図、コード

    短くまとめると、アーキテクチャ＝家の「間取りと骨組み」を決める、設計＝「各部屋の家具配置と内装」を決めるです。このイメージを最初に固めておくと、以降の議論がぶれません。

    7.2 建築でのスコープの違い

    家を建てるとき、関わる人はそれぞれ違う粒度の決定をします。

    建築家（アーキテクト）＝全体構造

    • 何階建てにするか
    • 部屋数と配置（間取り）
    • 玄関・廊下・階段の位置
    • 構造（木造・RC 造）と耐震性能
    • 水道・電気の幹線をどう通すか

    インテリアデザイナー／施主＝各部屋の中身

    • リビングのソファをどこに置くか
    • 壁紙・床材の色や素材
    • 照明器具の選定
    • 収納の細かい仕切り

    どちらも「家を作る」仕事ですが、前者は後戻りしにくい大枠を、後者は調整しやすい細部を扱っています。ソフトウェアに置き換えると次のようになります。

    建築での例ソフトウェアでの例区分
    何階建てか・間取りサーバー構成、層構造（3層など）、サービス分割アーキテクチャ
    玄関・廊下の位置API の境界、認証の置き場所アーキテクチャ
    構造・耐震性能性能・可用性・スケーラビリティの方針アーキテクチャ
    水道・電気の幹線DB・キャッシュ・メッセージキューの配置アーキテクチャ
    ソファの位置クラスやメソッドの分け方設計
    壁紙の色命名規則、コードの書き方設計
    収納の仕切りデータクラスの構造、DTO の設計設計

    ソファをずらすのは簡単、間取りを変えるのは大工事

    これはソフトウェアでも同じです。アーキテクチャの判断はあとから直しにくいため、先に決めておく価値があります。

    8.それぞれが決めること

    8.1 アーキテクチャが決めること

    アーキテクチャは、§4 で見た3つ（コンポーネント・関係性・原則と制約）を扱います。具体的には次のような判断です。

    • この機能はマイクロサービスに分けるか、モノリスのままにするか（→ モノリス・分散モノリス・マイクロサービス）
    • 「ビジネスロジックは DB に直接依存しない」というルールを置くか（→ 依存性のルールとクリーンアーキテクチャ）
    • 認証は API ゲートウェイで一括するか、各サービスで個別に行うか（→ 横断的関心事と認証・認可の境界）
    • 性能のために CQRS（読み書き分離）を採用するか（→ CQRS — コマンドとクエリの責務分離）

    これらはシステム全体の形に関わる判断で、後から覆すと多くのコードを書き直す必要が出てきます。

    8.2 設計（詳細設計）が決めること

    一方、設計（特に詳細設計）は、アーキテクチャで決めた骨組みの中で、各部品をどう作るかを決めます。

    • ユーザー登録のユースケースを、どんなクラスとメソッドに分けるか
    • User クラスにどんなフィールドを持たせるか
    • メールアドレスのバリデーションをどこで行うか
    • この処理を for ループと map のどちらで書くか
    • この変数の名前は userList か users か

    詳細設計では、設計原則（SOLID・DRY・KISS など）、オブジェクト指向の概念（カプセル化・継承・多態）、命名規則・コーディング規約を駆使して、アーキテクチャが定めた境界の内側で部品を磨き上げます。これらの本拠地は 41 の外にあります（41 外のノート：48_原則、42_ソフトウェア設計、44_クラス設計・デザインパターン）。

    8.3 観点ごとの比較表

    観点アーキテクチャ設計（詳細設計）
    対象システム全体の構造モジュール・クラス・関数などの内部構造
    粒度粗い（サービス・レイヤー・コンポーネント）細かい（クラス・メソッド・変数）
    主な決定何を部品にするか、どうつなぐか、ルール部品の中身をどう実装するか
    関心非機能要件（性能・可用性・保守性）可読性、再利用性、テスト容易性
    例モノリス vs マイクロサービス、3層 vs クリーンクラス分割、インターフェース、命名規則
    担当者アーキテクト／テックリード開発者全員
    後戻りしにくい（大規模改修になりがち）しやすい（リファクタリングで対応可）
    ドキュメント図、ADR、原則ガイドコメント、コード自体、クラス図
    検証手段プロトタイプ、性能試験、レビュー単体テスト、リファクタリング

    両方とも「構造を決める」ことですが、スコープ（広さ）と抽象度（高さ）が違うと理解するとよいでしょう。この2軸で見ると、両者は地続きのスペクトラムになっています。

    9.境界はグラデーション

    注意したいのは、アーキテクチャと設計の境界はきっちり線が引けるものではないという点です。

    同じテーマでも、視点の高さによってアーキテクチャにも設計にもなります。

    テーマアーキテクチャの話詳細設計の話
    ユーザー認証をどこで行うかサービス全体の境界のどこで認証するかその認証ミドルウェアのクラス構成
    注文と決済を別サービスにするか分けるかどうか分けたあと、それぞれの内部をどう作るか

    つまり、ある決定がアーキテクチャか設計かは、視点の高さで決まるということです。だからこそ現場では、両方を同時に行ったり来たりしながら進めるのが普通です。

    実務での目安

    迷ったら「後から変えるのが高くつく判断ほどアーキテクチャ寄り」と考えると整理しやすくなります。§2 で紹介した「変えるのが難しい決定」という見方と同じ発想です。

    10.それでも区別する理由

    「グラデーションなら区別する意味はあるの？」と思うかもしれません。区別するメリットは次の3つです。

    10.1 議論の粒度がそろう

    「設計レビュー」と言ったとき、全体の話をしたいのか、特定のクラスの話をしたいのかで、求める意見も判断基準も違います。区別することで、いま何の話をしているのかが明確になります。

    10.2 検証手段が変わる

    • アーキテクチャの妥当性はプロトタイプ・性能試験・経験で確かめる
    • 詳細設計の妥当性は単体テスト・コードレビューで確かめる

    両者を混ぜると、「テストは通るのに本番で性能が出ない」「テストは書きにくいが実は問題なく動く」といった不一致が起きます。

    10.3 後戻りコストの見積もりが変わる

    「これを直したい」と言われたとき、原因によってコスト感が大きく違います。

    アーキテクチャ起因

    大改修（数週間〜数か月）

    詳細設計起因

    リファクタリング（数時間〜数日）

    区別できていると、見積もりがぶれにくくなります。

    11.実務で考える順番

    実務では、おおむね次の順番で考えます。

    1. アーキテクチャ ― 何を部品にするか、どうつなぐか、どんなルールにするか
    2. 概要設計 ― 各部品の責任とインターフェース（クラス／API の境界）
    3. 詳細設計 ― 各部品の内部構造、データ構造、アルゴリズム
    4. コーディング ― 実装

    ただし、これは完全なウォーターフォール（滝）ではありません。小さく作って試しながら、1〜4 を行き来するのが現代的な進め方です。

    • アーキテクチャの選択が良いかどうかは、動かしてみないと分からない
    • 詳細設計でつまずくと、アーキテクチャの前提を疑うこともある

    逆に、いきなり 4 から始めて 1 を後回しにすると、全体の整合性が取れずに技術的負債が膨らみがちです。だからこそ、早い段階でアーキテクチャに目を向ける価値があります。この点は次のページ なぜ早く意識するか・アーキテクトの役割と思考 で深掘りします。

    12.アーキテクチャを決める人と、代表的な「形」

    12.1 アーキテクチャを決め、描く人（アーキテクト）

    アーキテクチャを検討し、方針を決め、図やドキュメントに落とす役割は、ソフトウェアアーキテクト（またはアーキテクト役）が担うことが多くあります。ただし、

    • 小さいチームでは、開発者が兼務することもよくあります。
    • 「アーキテクト」という肩書きがなくても、全体の形を決める、コンポーネントの切り方やつなぎ方を提案するという行為そのものが、アーキテクチャを考えることです。

    つまり、誰かが「システムの骨組み」を意識して決め、伝えることが重要で、その役割をアーキテクトと呼びます。アーキテクトに期待されることは 次のページ で詳しく見ます。

    12.2 代表的なアーキテクチャの「形」

    「どのような部品に分け、どうつなぐか」には、よく使われるパターンがあります。ここでは名前とイメージだけを挙げます。

    モノリシックアーキテクチャ

    機能を1つの大きなアプリケーションにまとめる形。シンプルだが、規模が大きくなると変更やスケールが難しくなることがある。

    マイクロサービスアーキテクチャ

    機能ごとに小さなサービスに分け、API やメッセージで連携する形。スケールや担当分けに有利だが、運用・連携の複雑さは増す。

    レイヤードアーキテクチャ（多層）

    UI 層・ビジネスロジック層・データ層のように「層」で分ける形。多くの Web アプリの基礎になっている。

    イベント駆動アーキテクチャ

    コンポーネント間の連携を「イベントの発生と購読」で行う形。非同期処理や疎結合に向く。

    どの形を選ぶかは、チームの規模、変更の頻度、非機能要件（性能・可用性など）によって変わります。「正解は一つではない」ので、文脈に合わせて選ぶことがアーキテクチャの考え方です。スタイルの比較は スタイル比較ツール で試せます。

    12.3 『基礎』が扱うアーキテクチャスタイルと主な論点

    『ソフトウェアアーキテクチャの基礎』では、次のスタイルを取り上げ、それぞれ次のような論点を解説しています。

    スタイル主な論点（キーワード）
    レイヤードアーキテクチャレイヤー分離、レイヤーの追加。
    リスク モノリシックなデプロイとモジュール性の欠如により、耐障害性をサポートしない。たとえばメモリ不足を起こすと、アプリケーション全体がクラッシュする
    モジュラーモノリスモノリシック構造、モジュラー構造、モジュール間通信
    パイプラインアーキテクチャフィルター、パイプ
    マイクロカーネルアーキテクチャコアシステム、プラグインコンポーネント、レジストリ、コントラクト
    サービスベースアーキテクチャサービスの設計と粒度、ユーザーインターフェースの選択肢、API ゲートウェイの選択肢
    イベント駆動アーキテクチャイベントとメッセージの違い、派生イベント、拡張可能なイベントの送信、非同期処理、ブロードキャスト、イベントペイロード、ブヨの群れアンチパターン、データ損失の防止、リクエスト・リプライ処理、メディエーター型イベント駆動

    オーケストレーション駆動サービス指向アーキテクチャサービスの分類、再利用と結合
    マイクロサービスアーキテクチャ境界づけられたコンテキスト、粒度、データ分離、API レイヤー、運用面での再利用、フロントエンド、通信、コレオグラフィとオーケストレーション、トランザクション

    12.4 スタイルが生まれた順番と、解決したかった問題

    各スタイルは、それ以前の構造が抱えていた問題を解決するために登場しました。時期はおおよその目安です（詳しい年表は アーキテクチャ年表）。

    登場時期（目安）アーキテクチャ解決したかった問題
    1970年代レイヤードアーキテクチャプログラムが一枚岩で、UI・業務処理・DB 処理が混在し保守しづらかった。責務を階層ごとに分離したかった
    1970年代パイプラインアーキテクチャデータ変換処理を何段階にも分けて、再利用・組み合わせしたかった（コンパイラ、ETL など）
    1980年代マイクロカーネルアーキテクチャ機能追加のたびに本体を変更する必要があり、拡張性が低かった。プラグイン方式にしたかった
    1990年代後半オーケストレーション駆動サービス指向アーキテクチャ（SOA）社内システムごとに機能が重複し、再利用できなかった。サービスとして共通化したかった
    2000年代前半イベント駆動アーキテクチャシステム同士が同期通信で密結合になり、変更や負荷に弱かった。イベントによる疎結合・非同期化を実現したかった
    2000年代前半スペースベースアーキテクチャアクセス集中で DB がボトルネックになり、スケールできなかった。メモリグリッドで大量アクセスに耐えたかった
    2000年代後半サービスベースアーキテクチャSOA はサービスの粒度が細かすぎて複雑になった。より粗い粒度で、シンプルにサービス分割したかった
    2011年頃（用語の登場）マイクロサービスアーキテクチャモノリスや SOA では独立開発・独立デプロイが難しく、チーム開発の速度が上がらなかった。小さなサービス単位で独立運用したかった
    2018年頃モジュラーモノリスマイクロサービスは運用コストが高すぎるケースが多かった。単一アプリのまま内部だけを疎結合にしたかった
    アプリケーション内部のアーキテクチャパターンの年表（参考）

    13.学習の進め方

    ソフトウェアアーキテクチャを学ぶときの流れの一例です。

    1. 用語とイメージを固める：このページで「アーキテクチャ＝システム全体の骨組み（部品の分け方・つなぎ方・ルール）」であることを理解する。
    2. 具体例に触れる：動画や資料（41 内の参考資料ノート：90_参考資料『ソフトウェアアーキテクチャ研修【MIXI 25新卒技術研修】』など）で、モノリス・マイクロサービス・疎結合・DDD などの具体例に触れる。
    3. 設計の基礎とつなげる：コードレベルの設計（41 外のノート：42_ソフトウェア設計『設計とは何か』、48_原則『単一責任の原則』）が、アーキテクチャで決めた方針をどう支えるかを見る。
    4. 実務や個人プロジェクトで意識する：小さなシステムでも「コンポーネントの分け方」「依存の向き」「守るルール」を少しずつ意識して設計してみる。

    このサイトでは、アーキテクトの役割と思考 → 品質特性 → モジュール性 と読み進めると、20 以降の個別スタイルを「特性」と「結合」の観点で比べられるようになります。

    14.よくある誤解

    14.1 「アーキテクチャは大規模システムでだけ必要」

    誤りです

    小さな個人開発でも、ファイルをどんなフォルダに分けるか、ロジックを UI と分けるか混ぜるか、DB アクセスをどこに置くか、はアーキテクチャ判断です。「意識しないアーキテクチャ」は単に自然発生したアーキテクチャであり、良い形になっているとは限りません。

    14.2 「アーキテクチャは資格者だけが触れる聖域」

    誤りです

    アーキテクトという肩書きはありますが、実態は全員が日常的にアーキテクチャ判断をしています。「controllers/ と services/ を分ける」のような小さな判断も、れっきとしたアーキテクチャです。

    14.3 「アーキテクチャを完璧に決めてからコードを書くべき」

    誤りです

    完璧を目指すと、動くコードがないまま机上の空論で終わりがちです。重要な部分だけ先に決めて、細部は走りながら学んで調整するのが現実的です。

    14.4 「アーキテクチャと設計は、はっきり線を引ける」

    実際はグラデーションです

    同じテーマでも視点の高さでどちらにもなります（§9）。区別は「線を引くため」ではなく、議論の粒度・検証手段・後戻りコストを正しく扱うために行います。

    15.まとめ

    • ソフトウェアアーキテクチャとは、システムをどのような部品（コンポーネント）に分け、どうつなぎ、どのような原則・制約で縛るかという、システム全体の骨組み・構造のことです。
    • コンポーネント（部品）、関係性（依存・通信・データの流れ）、原則・制約（ルール・技術選定・非機能要件への方針）の3つが主な要素です。『基礎』ではこれをスタイル・特性・論理コンポーネント・決定の4側面で整理し、「何を良しとするか（特性）」を明示します。
    • 建築にたとえると、アーキテクチャは「間取りと骨組み」、詳細設計・コーディングは「各部屋の家具配置と内装」です。
    • アーキテクチャを意識すると、変更しやすさ・分業のしやすさ・品質・性能を高めやすくなり、共通の理解にもつながります。
    • アーキテクチャと設計はグラデーションで、現場では行き来しながら進めます。それでも区別するのは、議論の粒度・検証手段・後戻りコストを正しく見積もるためです。迷ったら「後から変えるのが高くつく判断ほどアーキテクチャ寄り」と考えます。
    • 代表的な形にはモノリス・マイクロサービス・レイヤード・イベント駆動などがあり、それぞれ前の時代の問題を解決するために生まれました。文脈に応じて選ぶものです。
    • 「大規模だけ」「資格者だけ」「完璧に決めてから書く」はいずれも誤解で、全員が日常的にアーキテクチャ判断に関わっています。

    次のページでは、なぜアーキテクチャを早い段階で意識する価値があるのかを、変更コスト・チーム・長期保守の3つの観点から見たうえで、アーキテクトの役割と思考法を整理します。
