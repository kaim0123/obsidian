    オニオンアーキテクチャと3つの比較

    レイヤードとオニオンの違いは、つまるところ「依存の矢印（＝import）の向き」だけです。このページでは、その違いを入り口にオニオンアーキテクチャの4つの層と Domain Service の位置づけを解説し、最後にクリーン・ヘキサゴナル・オニオンの3つを比べて、共通点・違い・選び方を整理します。

    もとにしたノート：オニオンアーキテクチャとの比較 / レイヤードとオニオン、何が違うのか｜ねる前エンジニアリング（動画要約） / 00_解説_アプリ内部構造

    1.このページで扱うこと

    オニオンアーキテクチャ（Onion Architecture）は、Jeffrey Palermo（ジェフリー・パレルモ）が 2008 年に提唱したアーキテクチャで、ドメインを中心に据え、その外側に層を重ねていくスタイルです。名前のとおり、タマネギのように層が重なる図で表現されます。

    オニオンはクリーンアーキテクチャ・ヘキサゴナルアーキテクチャとよく似ていますが、微妙な違いがあります。また、昔ながらのレイヤードアーキテクチャとは「層に分ける」点は同じなのに、決定的に違うところがあります。このページでは次の順に整理します。

    • レイヤードとオニオンの違い ＝ 依存の矢印（import）の向き
    • オニオンアーキテクチャの4つの層と、独自のポイントである Domain Service の位置
    • コードで見るオニオン、AI にコードを書かせたときのチェックポイント
    • クリーン・ヘキサゴナル・オニオンの比較（似ている点・違うところ・選び方）

    覚えるべき1行

    「ドメインを中心に置き、依存は必ず外から内へ流す」。この一行さえ覚えておけば、3つのアーキテクチャのどれを採用していても同じゴールに向かえます。

    2.出発点：レイヤードの何が困るのか

    ここからしばらくは、動画「レイヤードとオニオン、何が違うのか」（ねる前エンジニアリング）の要約をもとに、レイヤードとオニオンの違いを見ていきます。

    実務でよくある場面（3つとも原因は同じ）

    • コストの都合などで、保存先のデータベースを別製品に変えることになった。AI に直させたら、DB と関係ないはずの業務ルールのファイルまで書き変わっていた。差分が大きく、レビューがつらい。
    • 業務ルールを試したいだけなのに、テストを動かすと DB が必要になる。

    レイヤードとは

    • 上から 画面 → アプリ（手順）→ 業務ルール → データベース の4層に並べます。業務ルールとは「在庫が足りなければ注文できない」のような決まり事のことです。
    • 決まりは1つ：上の層は、すぐ下の層だけを使ってよい。
    • 図の矢印はデータの流れではなく「知っている」の向きです。コードの中で相手の名前を書いて呼び出す、つまり import していることを指します。
    • 上は下を知りますが、下は上を知りません。だから画面を作り替えても、業務ルールは影響を受けません。

    下の変更が上に響く — レイヤードの弱点

    • 実際によく変わるのは、一番下の DB です。それを知っている上の業務ルールが引きずられます。
    • 業務ルールが DB を知っているので、ルールだけ試したくても DB ごと用意することになります。

    レイヤードの弱点を一言で

    大事なもの（業務ルール）が、変わりやすいもの（DB）に依存している。冒頭の「業務ルールまで書き変わる」「テストに DB が要る」は、どちらもこれが原因です。

    矢印をひっくり返す（依存性逆転）

    • 業務ルールの側に「注文を保存できるもの」という中身のない約束（インターフェース）を書きます。業務ルールはこの約束だけを知り、DB のことは知りません。
    • DB の側が、その約束を守るように作られます。すると矢印は DB から業務ルールへ 向きます。これが依存の向きの逆転です（詳しくは 依存性逆転の原則（DIP））。

    3.レイヤードとオニオンを並べて比べる

    矢印をひっくり返した結果、DB は「一番下」から「一番外」へ移り、図は上下の積み木から同心円（タマネギ）に変わります。

    オニオンの形

    • 一番大事な業務ルールを真ん中に置き、その外側にアプリ（手順）、さらに外側に画面・DB・外部サービスを置きます（玉ねぎの形）。
    • 決まりは1つ：矢印はすべて内側に向ける。外側は内側を知ってよいが、内側は外側を知らない。
    • 外側は細部（よく変わるもの）、内側は方針（めったに変わらないもの）。DB を変えても変わるのは外側の輪だけで、真ん中は無傷です。
    レイヤードオニオン
    DB の置き場所一番下一番外
    みんなが知っているもの下（DB 側）中心（業務ルール）
    DB 変更の影響上（業務ルール）に響く外側の輪だけ
    業務ルールのテストDB が必要になりがちDB なしで書ける
    手間少ない約束（インターフェース）を1つ挟む分増える

    オニオンが常に正解とは限らない

    画面から保存まで一直線の小さなアプリなら、レイヤードで十分です。業務ルールが複雑で、外のもの（DB・外部サービス・画面）がよく変わるなら、オニオンの手間が報われます。

    4.オニオンアーキテクチャの4つの層

    パレルモのオニオンアーキテクチャは、次の4つの輪で構成されます。

    層中身ポイント
    1. Domain Model（最内層）Entity、値オブジェクト、集約ビジネスの中核となる概念。外部依存なし
    2. Domain Service複数の Entity にまたがる業務ロジックどこか1つの Entity に閉じない処理（例：送金 ＝ 2つの口座を操作する）
    3. Application Serviceユースケースを1つずつ表現トランザクション境界。外部（UI など）にインターフェースを提供する
    4. Infrastructure（最外層）DB、メール、外部 API、UIすべての外部との接続。テストもここに置かれる

    Repository などのインターフェースは内側（コア）に置き、その実装を Infrastructure に置きます。これにより、Infrastructure が内側を知り、内側は Infrastructure を知らない、という依存の向きが保たれます。

    5.オニオン独自のポイント：Domain Service の位置

    オニオンでは、Domain Service が Application Service より内側に置かれます。両者の違いは次のとおりです。

    Domain Service（内側）

    ビジネス概念そのもの。送金・認証のような業務ロジックで、どの Entity にも自然に属さないもの。

    Application Service（外側）

    「ユースケースを実現する流れ」。Repository から取り出し、Domain Service を呼び、保存する、といった段取りとトランザクション管理。

    送金を例にすると、次のように分かれます（説明用の例です）。

    Domain Service：業務ロジックそのもの 
    class TransferService {
  transfer(from: Account, to: Account, amount: Money): void {
    from.withdraw(amount);   // 残高不足なら Account が例外を投げる
    to.deposit(amount);
  }
}
    Application Service：ユースケースの流れ 
    class TransferMoneyUseCase {
  constructor(
    private accounts: AccountRepository,   // インターフェース（内側に定義）
    private transferService: TransferService
  ) {}

  async execute(input: { fromId: string; toId: string; amount: number }) {
    const from = await this.accounts.findById(input.fromId);
    const to = await this.accounts.findById(input.toId);
    this.transferService.transfer(from, to, new Money(input.amount));
    await this.accounts.save(from);
    await this.accounts.save(to);
  }
}

    この分離は DDD（ドメイン駆動設計）の考え方と親和性が高く、DDD と一緒に学ぶと理解が深まります（41 外のノート：42_ソフトウェア設計『02_DDDとは』）。

    6.コードで見るオニオンと、AI に書かせたときのチェック

    コードで見る

    動画では、オニオンのコードを次のように説明しています。

    • 中心の業務ルールには「注文の保存先」という約束があり、「保存する」ができるものとだけ書いてある。注文を受ける処理はこの約束を受け取って「保存する」を呼ぶだけで、DB の名前はどこにも出てこない。
    • 外側のファイルは、一番上で業務ルールの約束を読み込んでいる。つまり import の向きが外から中へなっている。約束を守る形で、中身を SQL で書く。
    • どの保存先を使うかは、アプリの起動時に渡す。これが 依存性の注入（DI）。

    TypeScript で書くと、たとえば次のようになります。

    ✕ レイヤード：業務ルールが DB を import している 
    // domain/PlaceOrder.ts
import { MySqlOrderDao } from '../data/MySqlOrderDao';   // ← 中心が外を知っている

export class PlaceOrder {
  private dao = new MySqlOrderDao();
  async execute(order: Order) { await this.dao.insert(order); }
}
    ○ オニオン：import は外から中へ 
    // domain/OrderRepository.ts（中心：約束だけ）
export interface OrderRepository {
  save(order: Order): Promise<void>;
}

// application/PlaceOrder.ts（DB の名前は出てこない）
import { OrderRepository } from '../domain/OrderRepository';
export class PlaceOrder {
  constructor(private repo: OrderRepository) {}
  async execute(order: Order) { await this.repo.save(order); }
}

// infrastructure/SqlOrderRepository.ts（外側：約束を守って SQL を書く）
import { OrderRepository } from '../domain/OrderRepository';
export class SqlOrderRepository implements OrderRepository {
  async save(order: Order) { await db.query('INSERT INTO orders ...'); }
}

// main.ts（起動時に保存先を渡す ＝ DI）
const placeOrder = new PlaceOrder(new SqlOrderRepository());

    AI に書かせたときに見る3点

    1. 業務ルールのファイルの import を見る。DB や外部サービスの名前が出てきたら、矢印が外を向いています。ファイルの一番上を見るだけで判定できます。
    2. 約束（インターフェース）が中心の側に置かれているか。外側に置かれていると、結局、中心が外を知ることになります。
    3. 変更を頼んだときの差分が外側の輪だけで済んでいるか。中まで変わっていたら、どこかで矢印が逆を向いていると疑います。

    7.クリーン・ヘキサゴナル・オニオンの比較

    項目クリーンヘキサゴナルオニオン
    提唱者Robert C. MartinAlistair CockburnJeffrey Palermo
    発表年201220052008
    図同心円六角形タマネギ（同心円）
    層の数4層（Entities / Use Cases / Interface Adapters / Frameworks & Drivers）2層（コア＋アダプタ）4層（Domain Model / Domain Service / Application Service / Infrastructure）
    キー用語Entities, Use Cases, BoundaryPort, AdapterDomain, Application, Infrastructure
    ドメイン中心○○○
    依存は内側へ○○○

    要点：3つとも本質的に同じ思想

    • ドメインを中心に置く
    • 依存の向きは外から内へ
    • 外部は差し替え可能

    違うのは、図の描き方・用語・層の切り方の細かさだけです。

    似ている点（共通する原則）

    1. ドメインが主役：ビジネスルールは中心に置く
    2. フレームワーク非依存：外側を差し替えても中心は壊れない
    3. テスト容易：中心部分は外部依存なしでテストできる
    4. 依存性逆転（DIP）を使う：インターフェースを内側に置き、内側から外側を使えるようにする

    違うところ

    観点クリーンヘキサゴナルオニオン
    1. 層の切り方Use Cases を独立した層として明示そもそも2層（コア＋アダプタ）とシンプルDomain Service と Application Service を分ける
    2. 言葉の重点「Boundary（境界）」を強調「Port / Adapter」を強調「Domain」を強調
    3. 最外層の扱いFrameworks & Drivers としてまとめるAdapter として統一的に扱うInfrastructure として明示

    なお、クリーンアーキテクチャは、ヤコブソンの BCE（1992）、ヘキサゴナル（2005）、オニオン（2008）などを統合したものです。年代順に「ヘキサゴナル → オニオン → クリーン」と、層の内訳が細かく定義されていったと見ることができます。

    8.どれを選ぶべきか

    状況おすすめ理由
    小〜中規模、またははじめて触るヘキサゴナルシンプルで覚えやすい（コア＋アダプタ）
    DDD と組み合わせたいオニオンDomain Model / Domain Service の切り方が DDD と相性が良い
    層を明確に分けて大規模開発したいクリーン層の内訳が最も詳細に定義されている
    現場で迷ったときどれでも大丈夫チームで選び、大事な原則（依存の向き）だけは揺らさないことが一番大切
    画面から保存まで一直線の小さなアプリレイヤード約束（インターフェース）を挟む手間が報われにくい

    読み取り（一覧画面・集計）が重くなってきたら、どのスタイルでも CQRS を組み合わせられます。

    9.よくある誤解

    誤解1：3つはまったく別のアーキテクチャで、どれか1つを厳密に選ばなければならない

    3つは本質的に同じ思想で、図・用語・層の細かさが違うだけです。動画でも「流派の細かい違いは覚えなくてよい」としています。実務では「ヘキサゴナルのポート&アダプタの用語で、オニオンの Domain Service を使う」といった混ぜ方もよく見られます。

    誤解2：レイヤードとオニオンは層の数や名前が違う

    どちらも層に分ける点は同じで、違いは依存の矢印の向きだけです。レイヤードは下（DB）をみんなが知り、オニオンは中心（業務ルール）をみんなが知ります。

    誤解3：オニオンにすれば常に良くなる

    約束（インターフェース）を挟むぶん手間が増えます。小さなアプリならレイヤードで十分です。業務ルールが複雑で外のものがよく変わるときに、手間が報われます。

    誤解4：インターフェースを作れば、どこに置いてもよい

    インターフェースを外側（infrastructure）に置くと、中心がそれを import することになり、結局中心が外を知ってしまいます。約束は中心の側に置くのが要です。

    誤解5：矢印はデータが流れる向きを表している

    矢印は「知っている」の向き＝ import の向きです。実行時にデータは中心から DB へ流れますが、ソースコード上で相手の名前を書いているのは DB 側（外側）です。

    10.まとめ

    • 矢印は「知っている」の向き、コードでは import の向き
    • レイヤードは下を知るので、下の DB が変わると上（業務ルール）に響く。オニオンは中心を知るので、外を変えても業務ルールは無傷。ただし約束の分だけ手間が増えるので、小さなアプリならレイヤードで十分
    • オニオン（Palermo, 2008）は Domain Model → Domain Service → Application Service → Infrastructure の4層。Domain Service を Application Service より内側に置くのが独自のポイントで、DDD と相性が良い
    • AI に書かせたら、①業務ルールの import、②インターフェースの置き場所、③差分が外側の輪だけか、の3点を見る
    • クリーン・ヘキサゴナル・オニオンは本質的に同じ（ドメイン中心・依存は外から内・外部は差し替え可能）。違うのは図・用語・層の細かさだけ
    • 覚えるべき1行：「ドメインを中心に置き、依存は必ず外から内へ流す」
