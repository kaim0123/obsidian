    2.MVC とは何か

    MVC（Model-View-Controller）は、アプリケーションを3つのコンポーネントに分けて設計するアーキテクチャパターンです。Web アプリケーションの設計でも代表的なパターンで、Rails・Django・Laravel・Spring MVC など多くのフレームワークが採用しています。

    View（ビュー）

    ユーザーが見る部分。表示を担当します。

    Controller（コントローラー）

    処理の制御。入力を受けて Model と View を橋渡しします。

    Model（モデル）

    データとビジネスロジックを担当します。

    2.1 日常生活での例え：レストラン

    • View（ビュー）：メニューやテーブル（お客様が見る部分）
    • Controller（コントローラー）：ウェイター（注文を受け取り、キッチンに伝える）
    • Model（モデル）：キッチンとシェフ（実際に料理を作り、食材を管理する）

    お客様（ユーザー）はメニュー（View）を見て、ウェイター（Controller）に注文します。ウェイターはキッチン（Model）に伝え、料理ができたらお客様に提供します。

    2.2 生まれと「2つの MVC」

    MVC は 1979 年、Xerox PARC に客員研究員として来ていたノルウェーの研究者 トリグヴ・リーンスカウグ（Trygve Reenskaug）が、Smalltalk のために考案した設計です。もともとはデスクトップ GUIの設計で、画面部品の一つひとつが Model・View・Controller を持ち、Model が変わると View に通知されて自動で再描画される、という仕組みでした。

    一方、今日 Rails や Express で使われている Web の MVC は、「HTTP リクエストを Controller が受け、Model を呼び、View（テンプレート）で HTML や JSON を返す」という流れの整理術です。Java の世界で Model 2 と呼ばれていた設計に MVC の名前がついたもので、元の MVC とは中身がかなり違います（詳しくは 14 節）。このページのコード例は主に Web の MVC です。

    3.MVC の各コンポーネント

    3.1 Model（モデル）

    役割：データとビジネスロジックを担当します。

    責任

    • データベースとのやり取り
    • データの検証
    • ビジネスルールの実装
    • データの取得・保存・更新・削除

    特徴

    • View や Controller に依存しない
    • 再利用できる
    • テストしやすい

    Model のコード例は、5 節の Express 実装で示します（findById・findAll・save・validate・delete・toJSON を持つ User クラス）。

    Model に DB 操作まで入れるか

    このページの例では、Model が自分で SQL を発行しています（Rails の ActiveRecord と同じ Active Record 型）。小さなアプリではこれで十分ですが、規模が大きくなると「業務ルール（ドメイン）」と「DB アクセス（Repository）」を分けたくなります。それがレイヤードアーキテクチャのドメイン層とインフラ層の分離です（→ 層化・三層・レイヤード（4層））。

    3.2 View（ビュー）

    役割：ユーザーインターフェースを担当します。

    責任

    • データを表示する
    • ユーザーからの入力を受け取る
    • ユーザーに情報を提示する

    特徴

    • Model や Controller の詳細を知らない
    • 表示のみを担当する
    • 再利用できる

    同じユーザー情報を、コンソール・サーバーサイドの HTML・React コンポーネントという3通りに表示する View の例です。表示方法が変わっても、Model は何も変わらないことがポイントです。

    views/userView.js 
    class UserView {
  // ユーザー情報を表示（コンソール）
  displayUser(user) {
    console.log(`
      ユーザー情報:
      ID: ${user.id}
      名前: ${user.name}
      メール: ${user.email}
    `);
  }

  // HTML で表示（サーバーサイドレンダリング）
  renderUserHTML(user) {
    return `
      <div class="user-profile">
        <h1>${user.name}</h1>
        <p>メールアドレス: ${user.email}</p>
      </div>
    `;
  }

  // React コンポーネント（クライアントサイド）※JSX
  renderUserComponent(user) {
    return (
      <div className="user-profile">
        <h1>{user.name}</h1>
        <p>メールアドレス: {user.email}</p>
      </div>
    );
  }

  // エラーメッセージを表示
  displayError(error) {
    console.error('エラー:', error.message);
  }
}

module.exports = UserView;

    3.3 Controller（コントローラー）

    役割：Model と View の間の仲介を担当します。

    責任

    • ユーザーの入力を受け取る
    • Model に処理を依頼する
    • View に表示を依頼する
    • フローの制御

    特徴

    • Model と View の両方に依存する
    • ビジネスロジックは含まない（Model に委譲する）
    • リクエストのルーティングを担当する

    上の UserView と組み合わせた、フレームワークを使わない Controller の例です（Express 版は 5 節）。

    コード：フレームワークなしの UserController（取得・作成・更新・削除）
    // controllers/userController.js
const User = require('../models/User');
const UserView = require('../views/userView');

class UserController {
  constructor() {
    this.view = new UserView();
  }

  // ユーザーを取得して表示
  async showUser(userId) {
    try {
      const user = await User.findById(userId);   // Model からデータを取得
      if (!user) {
        this.view.displayError(new Error('ユーザーが見つかりません'));
        return;
      }
      this.view.displayUser(user);                 // View に表示を依頼
    } catch (error) {
      this.view.displayError(error);
    }
  }

  // ユーザーを作成
  async createUser(name, email) {
    try {
      const user = new User(null, name, email);    // Model を作成
      user.validate();                             // バリデーション
      await user.save();                           // 保存
      this.view.displayUser(user);                 // View に表示
    } catch (error) {
      this.view.displayError(error);
    }
  }

  // ユーザーを更新
  async updateUser(userId, name, email) {
    try {
      const user = await User.findById(userId);
      if (!user) throw new Error('ユーザーが見つかりません');
      user.name = name;
      user.email = email;
      user.validate();
      await user.save();
      this.view.displayUser(user);
    } catch (error) {
      this.view.displayError(error);
    }
  }

  // ユーザーを削除
  async deleteUser(userId) {
    try {
      const user = await User.findById(userId);
      if (!user) throw new Error('ユーザーが見つかりません');
      await user.delete();
      console.log('ユーザーを削除しました');
    } catch (error) {
      this.view.displayError(error);
    }
  }
}

module.exports = UserController;

    どのメソッドも「Model に頼む → 結果を View に渡す」だけで、検証ルールや SQL は Model 側にあることを確認してください。

    4.MVC のデータの流れ

    4.1 基本的な流れ

    1. ユーザーが View で操作する（ボタンをクリックするなど）
    2. View が Controller に通知する
    3. Controller が Model に処理を依頼する
    4. Model がデータベースとやり取りする
    5. Model が結果を Controller に返す
    6. Controller が View に表示を依頼する
    7. View がユーザーに結果を表示する

    4.2 詳細な例：ユーザー作成

    手順やり取り各コンポーネントがすること
    1ユーザー → Viewユーザーがフォームに入力して送信。View がフォームのデータを取得する
    2View → Controllerデータを渡す。Controller が createUser(name, email) を呼び出す
    3Controller → Model新しい User オブジェクトを作成。Model がバリデーションを実行する
    4Model → データベースINSERT 文を実行し、データベースがユーザーを保存する
    5データベース → Model → Controller保存されたデータ（採番された ID など）が返り、Model が User オブジェクトを Controller に返す
    6Controller → Viewユーザー情報を渡し、View がそれを表示する

    5.2 Model（モデル）

    // models/User.js
const db = require('../config/database');

class User {
  constructor(id, name, email) {
    this.id = id;
    this.name = name;
    this.email = email;
  }

  static async findById(id) {
    const [rows] = await db.query('SELECT * FROM users WHERE id = ?', [id]);
    if (rows.length === 0) {
      return null;
    }
    const row = rows[0];
    return new User(row.id, row.name, row.email);
  }

  static async findAll() {
    const [rows] = await db.query('SELECT * FROM users');
    return rows.map(row => new User(row.id, row.name, row.email));
  }

  async save() {
    if (this.id) {
      // 更新
      await db.query(
        'UPDATE users SET name = ?, email = ? WHERE id = ?',
        [this.name, this.email, this.id]
      );
    } else {
      // 新規作成
      const [result] = await db.query(
        'INSERT INTO users (name, email) VALUES (?, ?)',
        [this.name, this.email]
      );
      this.id = result.insertId;
    }
  }

  // バリデーション（ビジネスルール）
  validate() {
    if (!this.name || this.name.trim() === '') {
      throw new Error('名前が必要です');
    }
    if (!this.email || !this.email.includes('@')) {
      throw new Error('有効なメールアドレスが必要です');
    }
  }

  async delete() {
    await db.query('DELETE FROM users WHERE id = ?', [this.id]);
  }

  toJSON() {
    return {
      id: this.id,
      name: this.name,
      email: this.email
    };
  }
}

module.exports = User;

    5.3 Controller（コントローラー）

    // controllers/userController.js
const User = require('../models/User');

class UserController {
  // ユーザー一覧を取得
  async index(req, res) {
    try {
      const users = await User.findAll();
      res.json(users.map(user => user.toJSON()));
    } catch (error) {
      res.status(500).json({ error: error.message });
    }
  }

  // 特定のユーザーを取得
  async show(req, res) {
    try {
      const user = await User.findById(req.params.id);
      if (!user) {
        return res.status(404).json({ error: 'ユーザーが見つかりません' });
      }
      res.json(user.toJSON());
    } catch (error) {
      res.status(500).json({ error: error.message });
    }
  }

  // ユーザーを作成
  async create(req, res) {
    try {
      const { name, email } = req.body;
      const user = new User(null, name, email);
      user.validate();
      await user.save();
      res.status(201).json(user.toJSON());
    } catch (error) {
      res.status(400).json({ error: error.message });
    }
  }

  // ユーザーを更新
  async update(req, res) {
    try {
      const user = await User.findById(req.params.id);
      if (!user) {
        return res.status(404).json({ error: 'ユーザーが見つかりません' });
      }
      const { name, email } = req.body;
      user.name = name;
      user.email = email;
      user.validate();
      await user.save();
      res.json(user.toJSON());
    } catch (error) {
      res.status(400).json({ error: error.message });
    }
  }

  // ユーザーを削除
  async delete(req, res) {
    try {
      const user = await User.findById(req.params.id);
      if (!user) {
        return res.status(404).json({ error: 'ユーザーが見つかりません' });
      }
      await user.delete();
      res.status(204).send();
    } catch (error) {
      res.status(500).json({ error: error.message });
    }
  }
}

module.exports = new UserController();

    実装上の注意：this の束縛

    このようにインスタンスのメソッドをそのまま router.get('/', userController.index) に渡すと、メソッド内で this を使った場合に undefined になります。上の例は this を使っていないので動きますが、使う場合は userController.index.bind(userController) とするか、アロー関数のプロパティで定義します。

    this.title = title;

  // 投稿者を取得（Model 同士の連携）
  async getAuthor() {

    return { id: this.id, title: this.title, content: this.content, userId: this.userId };

    6.フロントエンドでの MVC

    React では、コンポーネントが View、API 呼び出しをまとめたサービスが「Controller 的な役割」を担う、という分け方がよく見られます。

    // components/UserList.jsx（View）
import { useState, useEffect } from 'react';
import UserService from '../services/UserService';

function UserList() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    // Controller 的な役割（サービス層）に任せる
    UserService.getAllUsers()
      .then(data => {
        setUsers(data);
        setLoading(false);
      });
  }, []);

  // View：表示のみ
  if (loading) {
    return <div>読み込み中...</div>;
  }

  return (
    <ul>
      {users.map(user => (
        <li key={user.id}>
          {user.name} - {user.email}
        </li>
      ))}
    </ul>
  );
}
    // services/UserService.js（Controller 的な役割）
class UserService {
  static async getAllUsers() {
    const response = await fetch('/api/users');
    return response.json();
  }

  static async getUser(id) {
    const response = await fetch(`/api/users/${id}`);
    return response.json();
  }

  static async createUser(userData) {
    const response = await fetch('/api/users', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(userData)
    });
    return response.json();
  }
}

export default UserService;

    フロントエンドでは MVC は主流ではない

    実際には、React のような宣言的 UI では「状態（state）が変わると画面が再描画される」仕組みが中心で、古典的な MVC よりも MVVM や単方向データフロー（Flux / Redux）に近い考え方で設計されます。上の例の「サービス＝Controller 的」という対応は、あくまで役割分担のイメージです（→ MVP・MVVM と GUI アーキテクチャの系譜）。

    7.MVC と三層・レイヤードアーキテクチャの関係

    もとのノートでは「MVC は三層アーキテクチャのビジネスロジック層をさらに細分化したもの」と説明し、次のように対応づけています。

    • View ＝ プレゼンテーション層
    • Controller ＝ 制御
    • Model ＝ ビジネスロジック ＋ データアクセス

    ただし、この対応は資料によって説明が分かれるところで、より一般的な整理は次のとおりです。

    より正確な位置づけ：MVC は「プレゼンテーション層まわり」のパターン

    レイヤードアーキテクチャの観点では、Controller と View はプレゼンテーション層の中にあります。Model は「業務ルールとデータ」の総称で、規模が大きくなるとビジネスロジック層（アプリケーション層＋ドメイン層）とデータアクセス層に分かれていきます。つまり MVC はアプリ全体の構造ではなく、UI まわりの責務の分け方です。「MVC を使っているから層の設計は要らない」とはなりません。

    8.MVC のメリット・デメリット

    8.1 メリット

    1. 責任の分離

    各コンポーネントが明確な責任を持ちます。Model はデータとビジネスロジック、View は表示、Controller は制御です。

    2. 再利用性

    各コンポーネントを独立して再利用できます。たとえば同じ Model を複数の View で使えます。

    // 同じ Model を複数の View で使用
const user = await User.findById(1);
userView.displayUser(user);
adminView.displayUser(user);

    3. テストしやすい

    各コンポーネントを独立してテストできます。とくに Model のバリデーションは、画面も DB もなしで検証できます。

    // Model のテスト（DB 不要）
describe('User Model', () => {
  it('should validate user data', () => {
    const user = new User(null, 'Test', 'test@example.com');
    expect(() => user.validate()).not.toThrow();
  });
});

// Controller のテスト（Model の保存処理はモックにするのが一般的）
describe('UserController', () => {
  it('should create a user', async () => {
    const res = { status: jest.fn().mockReturnThis(), json: jest.fn() };
    jest.spyOn(User.prototype, 'save').mockResolvedValue();
    await userController.create({ body: { name: 'Test', email: 'test@example.com' } }, res);

    ※もとのノートの Controller テストは戻り値を検証する形でしたが、5 節の Express 版 Controller は res に書き込む形なので、それに合わせて書き換えています。

    4. 保守性

    変更の影響範囲が限定されます。

    • View を変更しても Model や Controller に影響しない
    • Model を変更しても View や Controller に影響しない（インターフェースが同じなら）

    8.2 デメリット

    複雑性

    小規模なアプリケーションには過剰な場合があります。

    学習コスト

    MVC の概念を理解する必要があります。

    ファイル数の増加

    コンポーネントごとにファイルが必要です。

    加えて、Web の MVC ではController が太りやすい（Fat Controller）、逆に Model に何でも入れるとFat Modelになる、という問題が実務でよく起きます。その具体例が次の「MVC 違反」です。

    9.MVC 違反とは

    MVC 違反とは、MVC の原則に従わず、各層の責務が混在している状態を指します。とくに AI でコードを生成すると、MVC の原則を無視したコードが出てくることがよくあります。

    9.1 各層の正しい責務

    層担当すること担当しないこと
    Modelデータの管理、ビジネスロジック、データベース操作HTML・CSS・イベント処理などの表示
    Viewユーザーインターフェースの表示のみ（ロジックなし）計算・判定などのビジネスロジック
    Controllerユーザー入力の処理、Model と View の橋渡し・調整価格計算・送料計算などのビジネスロジック、SQL

    典型的な違反は次の4つです。

    1. View にビジネスロジックを含める
    2. Controller に過度なロジックを実装する（Fat Controller）
    3. Model が View に直接依存する
    4. Model に HTML・CSS・イベントを含める（3 の拡張パターン）

    10.違反パターン1：View にビジネスロジックを含める

    ✕ 悪い例：View に年齢計算と会員ランク判定がある 
    <!-- views/user_profile.html -->

    • このロジックを他の View で再利用できない
    • テストが難しい
    • ロジックを変更するとき、複数の View を修正する必要がある
    ○ 良い例：Model にビジネスロジックを置く

    ※もとのノートの良い例では Controller が直接 db.query('SELECT …') を実行していましたが、これ自体が違反パターン2（Controller に DB 処理）に当たるため、User.findById を使う形に直しています。

    ○ 良い例：View は表示のみ

    11.違反パターン2：Controller に過度なロジックを実装する

    ✕ 悪い例：Controller に価格・送料・ポイント計算と SQL が混在（Fat Controller） 
    // controllers/order_controller.js
async function createOrder(req, res) {
  const { userId, items } = req.body;

  // ✕ コントローラーにビジネスロジックが含まれている
  let total = 0;
  for (const item of items) {
    const product = await db.query('SELECT * FROM products WHERE id = ?', [item.productId]);
    const price = product.price;
    const discount = product.discount || 0;
    const itemTotal = price * item.quantity * (1 - discount / 100);
    total += itemTotal;
  }

  // ✕ ビジネスルール（送料）がコントローラーに含まれている
  let shippingFee = 0;
  if (total < 5000) {
    shippingFee = 500;
  } else if (total < 10000) {
    shippingFee = 300;
  }

  // ✕ ポイント計算ロジックがコントローラーに含まれている
  const pointsEarned = Math.floor(total * 0.01);
  const user = await db.query('SELECT * FROM users WHERE id = ?', [userId]);
  const newPoints = user.points + pointsEarned;
  await db.query('UPDATE users SET points = ? WHERE id = ?', [newPoints, userId]);

  const order = await db.query(
    'INSERT INTO orders (user_id, total, shipping_fee, points_earned) VALUES (?, ?, ?, ?)',
    [userId, total, shippingFee, pointsEarned]
  );

  res.json({ orderId: order.insertId });
}

    問題点

    • Controller にビジネスロジックが含まれている
    • 価格計算、送料計算、ポイント計算などのロジックが混在している
    • テストが難しい（Controller のテストが複雑になる）
    • ロジックを再利用できない（管理画面やバッチから注文を作るときに再実装が必要）
    ○ 良い例：Model にビジネスロジックを置く 
    // models/Order.js
class Order {
  constructor(userId, items) {
    this.id = null;
    this.userId = userId;
    this.items = items;
    this.total = 0;
    this.shippingFee = 0;
    this.pointsEarned = 0;
  }

  // 注文合計を計算（ビジネスロジック）
  async calculateTotal() {
    let total = 0;
    for (const item of this.items) {
      const product = await Product.findById(item.productId);
      const price = product.price;
      const discount = product.discount || 0;
      const itemTotal = price * item.quantity * (1 - discount / 100);
      total += itemTotal;
    }
    this.total = total;
    return total;
  }

  // 送料を計算（ビジネスロジック）
  calculateShippingFee() {
    if (this.total < 5000) {
      this.shippingFee = 500;
    } else if (this.total < 10000) {
      this.shippingFee = 300;
    } else {
      this.shippingFee = 0;
    }
    return this.shippingFee;
  }

  // 獲得ポイントを計算（ビジネスロジック）
  calculatePointsEarned() {
    this.pointsEarned = Math.floor(this.total * 0.01);
    return this.pointsEarned;
  }

  // 注文を保存
  async save() {
    const [result] = await db.query(
      'INSERT INTO orders (user_id, total, shipping_fee, points_earned) VALUES (?, ?, ?, ?)',
      [this.userId, this.total, this.shippingFee, this.pointsEarned]
    );
    this.id = result.insertId;
  }
}

module.exports = Order;
    ○ 良い例：Controller は制御のみ 
    // controllers/order_controller.js
const Order = require('../models/Order');
const User = require('../models/User');

async function createOrder(req, res) {
  try {
    const { userId, items } = req.body;

    // モデルを作成
    const order = new Order(userId, items);

    // モデルのメソッドを使用して計算
    await order.calculateTotal();
    order.calculateShippingFee();
    order.calculatePointsEarned();

    // 注文を保存
    await order.save();

    // ユーザーのポイントを更新（ポイント加算のルールも User モデルのメソッドに）
    const user = await User.findById(userId);
    await user.addPoints(order.pointsEarned);

    res.json({ orderId: order.id });
  } catch (error) {
    res.status(500).json({ error: error.message });
  }
}

module.exports = { createOrder };

    さらに進めるなら

    この良い例でも、Controller が「計算する順番」を知っています。注文の作成手順（計算 → 保存 → ポイント加算）をひとまとめにしたいなら、PlaceOrderService のようなアプリケーション層（ユースケース）に移し、Controller はそれを1回呼ぶだけにします。注文保存とポイント更新を同じトランザクションにまとめる責任も、そこに置くのが自然です（→ 層化・三層・レイヤード（4層））。

    12.違反パターン3・4：Model が View に依存する

    12.1 パターン3：Model が HTML を生成する

    ✕ 悪い例：Model がビュー層の責務（HTML・CSS）を持つ 
    // models/User.js
class User {
  constructor(id, name, email) {
    this.id = id;
    this.name = name;
    this.email = email;
  }

  // ✕ モデルが HTML を生成している（ビュー層の責務）
  toHTML() {
    return `
      <div class="user-card">
        <h2>${this.name}</h2>
        <p>${this.email}</p>
      </div>
    `;
  }

  // ✕ モデルが HTML と CSS をデータとして返している
  toJSONHTML() {
    return {
      html: `<div>${this.name}</div>`,
      css: '.user-card { color: blue; }'
    };
  }
}

    問題点

    • Model がプレゼンテーション層（HTML）に依存している
    • Model を他の View（モバイルアプリ、API など）で再利用できない
    • 関心の分離が崩れている
    ○ Model はデータのみ 
    // models/User.js
class User {
  constructor(id, name, email) {
    this.id = id;
    this.name = name;
    this.email = email;
  }

  // データのみを返す
  toJSON() {
    return {
      id: this.id,
      name: this.name,
      email: this.email
    };
  }
}

module.exports = User;
    ○ HTML は View で生成 
    // views/user_view.js
function renderUserCard(user) {
  return `
    <div class="user-card">
      <h2>${user.name}</h2>
      <p>${user.email}</p>
    </div>
  `;
}

module.exports = { renderUserCard };

    12.2 パターン4：Model に HTML・CSS・イベントを含める（拡張パターン）

    「Model が View に直接依存する」違反の、AI 生成で特に多いバリエーションです。

    4.1 Model が toHTML() やテーブル行を返す

    ✕ 悪い例：Model がボタンとクリック処理まで生成している 
    // models/Product.js
class Product {
  constructor(id, name, price, description) {
    this.id = id;
    this.name = name;
    this.price = price;
    this.description = description;
  }

  toHTML() {
    return `
      <div class="product-card">
        <h3>${this.name}</h3>
        <p class="price">¥${this.price.toLocaleString()}</p>
        <button onclick="addToCart(${this.id})">カートに追加</button>
      </div>
    `;
  }
}

    問題点：同じデータを API・モバイル・PDF で出し分けにくくなります。HTML を変えるたびに Model を直すことになり、Model のテストで HTML 生成まで検証する必要が出てきます。

    バリエーション何が起きるか
    4.2 Model が CSS やインラインスタイルを持つModel が getStyles() のように見た目の都合を返すと、デザイン変更がドメイン層に波及する
    4.3 Model が <form> と <script> を文字列で返すModel に onsubmit や fetch を埋め込むと、フロントの振る舞いがドメインに混ざり、テストと再利用が難しくなる
    4.4 Model が JSON で html / css / js をまとめて返すプレゼンテーション層の要素をデータとして束ねると、関心の分離が一か所で崩れる

    正しい分離

    • Model はtoJSON() やドメイン操作にとどめる（表示用の軽い整形は、チームの規約で許容する場合もある）
    • HTML の組み立てはテンプレート／View／コンポーネントへ
    • スタイルはCSS やデザインシステムへ
    • イベントと通信はView 層または Controllerへ
    ○ Model はデータとルール 
    // models/Product.js
class Product {
  toJSON() {
    return {
      id: this.id,
      name: this.name,
      price: this.price,
      description: this.description,
      formattedPrice:
        `¥${this.price.toLocaleString()}`,
    };
  }
  isOnSale() {
    return this.price < 1000;
  }
}
    ○ View 側で HTML を組み立てる 
    // views/product_view.js
function renderProductCard(product) {
  const saleBadge = product.isOnSale()
    ? '<span class="badge">セール中</span>'
    : '';
  return `
    <div class="product-card">
      ${saleBadge}
      <h3>${product.name}</h3>
      <p class="price">${product.formattedPrice}</p>
    </div>
  `;
}

    なぜ分離するのか：同じ Model を Web・API・別のクライアントで使い回せます。Model の単体テストが HTML に引きずられません。見た目の変更がドメインに波及しにくくなります。

    補足：テンプレート文字列と XSS

    上の View の例のように、ユーザー入力（名前など）をテンプレート文字列でそのまま HTML に埋め込むと、クロスサイトスクリプティング（XSS）の原因になります。実務では、自動でエスケープしてくれるテンプレートエンジンや React などを使うか、埋め込む前にエスケープしてください。

    14.補足：MVC が 47 年間生き残った理由

    YouTube 動画「フロントエンドで敗れた MVC が、サーバーでは無敵な理由」（IT技術屋のボヤキ）の要約から、MVC の歴史と、なぜ今も使われ続けているのかを整理します。動画の結論は、MVC は MVP・MVVM・Flux の挑戦を受けてフロントエンドでは敗れたが、Rails・Django・Laravel・Spring などのサーバーサイドでは今も背骨であり続けている、その理由は技術的な優秀さよりも、Web の構造・教育・会話という人間側の事情とかみ合い、「言葉」として生き残ったことにある、というものです。

    14.1 誕生：造船業界出身の研究者と Xerox PARC

    • MVC の誕生は Rails が流行した 2000 年代ではなく 1979 年。Windows も Mac もまだない時代です。
    • 舞台は GUI・イーサネット・パーソナルコンピューターの原型を生んだ Xerox PARC（Smalltalk もここで誕生）。
    • 1978 年、ノルウェーから客員研究員のトリグヴ・リーンスカウグ（当時 48 歳）が来訪します。もとは造船業界で、船の設計や生産計画を支えるシステムを作っていた人物です。
    • 関心は理論よりも、「ユーザーの頭の中のイメージ」と「コンピューターの中のデータ」の溝をどう埋めるか（今でいう UX に近い問題意識）でした。
    • 1979 年 5 月のメモ「Thing-Model-View-Editor」では、現実の物事を Model に写し、View で画面に映し、Editor で操作する、と書かれています。Editor は数か月後の議論で Controller に改められました。
    • Smalltalk チームが実装に落とし込み、Smalltalk-80 で MVC が初めて動くコードになりました（思想が先、実装が後）。

    14.2 名前だけが世界に広がった

    1. 1988 年：Krasner と Pope が Smalltalk-80 の MVC を解説した論文を発表し、設計パターンとして広く知られるようになる
    2. NeXTSTEP：ジョブズの NeXT が MVC を採用。のちに Mac の中核、iPhone アプリの標準設計（Cocoa の MVC）に受け継がれる
    3. 2004 年 Rails：決定打。DHH が「Web アプリの正しい作り方」として MVC を前面に押し出し、Model＝ActiveRecord、View＝ERB、Controller＝ルーティングと直結させた。ディレクトリ構成まで決まっていて迷う余地がなかった
    4. その後：Django・CakePHP（2005）、ASP.NET MVC（2009）、Laravel（2011）が続き、業界標準になる

    Web の MVC は元の MVC とは別物

    元の MVC は、画面部品の一つひとつが M・V・C を持つデスクトップ GUIの設計でした。Web の MVC は「リクエストを受けて DB を読み、HTML を返す」流れの整理術で、Java で Model 2 と呼ばれていた設計に MVC の名前がついたものです。

    Smalltalk の MVCWeb の MVC（Model 2）
    Controller の役割キーボード・マウスの入力を処理するHTTP リクエストを受けて処理を振り分ける
    View の更新Model の変更通知（Observer）で自動更新リクエストごとにHTML を生成して返す
    寿命画面が開いている間ずっと生きている1リクエストで終わる

    14.3 曖昧さが武器になった4つの理由

    1. 人間の分業と一致

    デザイナー＝View、DB 担当＝Model、つなぐ人＝Controller。チームの形とコードの形がそろいます。

    2. Web の仕組みと相性が良い

    HTTP のリクエスト→処理→レスポンスを、入口＝Controller、処理＝Model、出口＝View と一本道で説明できます。

    3. 教えやすい

    3つの箱と矢印だけで、新人に5分で説明できます。学習コストの低さも武器です。

    4. 共通言語になった（最重要）

    「そのロジックを Controller に書くと太りすぎでは」という会話が、Rails でも Laravel でも Spring でも通じます。

    14.4 挑戦者たちとの攻防

    • MVP（1996 年、Taligent）：View と Model を完全に切り離し、Presenter がすべてを仲介する
    • MVVM（2005 年、Microsoft の John Gossman が WPF 向けに設計）：ViewModel と View をデータバインディングで同期する
    • 挑戦者の多くは名前が MVC の変形で、むしろ MVC という土台の存在感を強めました
    • 最大の強敵は 2014 年の Facebook の Flux。「双方向のデータの流れが複雑さの元凶」と主張し、React と Redux がフロントエンドを塗り替えました
    • ブラウザの中では MVC は敗れましたが、サーバー側では何も変わらず、動画の時点（2026 年）でも Rails 8・Laravel 12・Django は MVC のままです

    14.5 MVC が本当に残したもの

    • サーバーサイドの Web アプリなら、今でもMVC から始めるのは合理的です。枯れた構造・豊富なドキュメント・誰でも読める配置は、新しい設計では得られません。
    • MVC を窮屈に感じたら、アプリが育ったサインです。Controller が肥大化したらサービス層やドメイン層を足せばよい。MVC は出発点であって終着点ではありません。
    • MVC が残った本当の理由は、アーキテクチャとしてではなく言葉として生き残ったからです。厳密な定義は崩れても、「どこに何を書くか」を議論する単位として毎日使われています。
    • リーンスカウグ本人も、MVC の本質は「ユーザーの心の中のモデルとコンピューターの中のデータの橋渡し」であり、実装は時代ごとに変わってよいと振り返っています。

    15.よくある誤解

    「MVC は Web アプリ全体の構造である」

    誤りです。MVC は画面まわりのパターンです。DB アクセスやドメインロジックは Model の中か、別のレイヤーに置きます。「M」を単なる DB モデルと混同すると責務が崩れます。

    「Model ＝ DB のテーブル」

    誤りです。Model は業務ルールを持つものです。テーブルの写しにすぎない Model しかないと、業務ルールが Controller や View、SQL の中に散らばります（違反パターン1・2の原因）。

    「フレームワークが MVC と名乗っていれば、MVC になっている」

    要注意です。Rails の「MVC」は Model にビジネスロジックと DB 操作の両方が入りがちで、Smalltalk の MVC とは中身が違います。名前より、実際にどこに何の責任があるかを見ることが大切です。

    「MVC は古いので使うべきではない」

    誤りです。フロントエンドでは単方向データフローなどが主流になりましたが、サーバーサイドの Web アプリでは今も合理的な出発点です。育ってきたらサービス層・ドメイン層を足していきます。

    16.まとめ

    • MVC は、アプリケーションを Model・View・Controller の3つに分ける設計パターン
    • Model：データとビジネスロジック／View：ユーザーインターフェース（表示のみ）／Controller：Model と View の仲介（入力処理と調整のみ）
    • 責任の分離により、保守性・再利用性・テスト容易性が向上する
    • 1979 年の Smalltalk の MVC（GUI）と、Rails などの Web の MVC（Model 2）は別物
    • MVC はUI まわりの分け方。アプリが育ったら Model をアプリケーション層・ドメイン層・インフラ層に分けていく
    • MVC 違反の典型は「View にビジネスロジック」「Fat Controller」「Model が HTML/CSS/イベントを持つ」。チェックリストで防ぐ
    • MVC が長生きしたのは、関心を分けて名前をつけ、会話できるようにしたから
