    10 基礎 ／ 13 モジュール性・結合

    コナーセンス

    コナーセンスは、結合の「数」ではなく「種類と強さ」を表すための語彙です。3つの性質（強さ・局所性・程度）、静的5種類・動的4種類の合計9種類とそれぞれの弱め方、そしてサービス間の結合を評価するための使い方を解説します。

    もとにしたノート：10_基礎/13_モジュール性・結合/04_コナーセンス

    1.このページで扱うこと

    結合の指標 では、結合を 数 で測る方法を学びました。しかし「依存が3つある」と分かっても、次のことは分かりません。

    • その依存は どのくらい壊れやすいのか
    • どう直せば弱くなるのか

    コナーセンス（Connascence） は、結合の 種類と強さ を表すための語彙です。コナーセンスを知っていると、コードレビューで「ここ、結合が強いですね」とあいまいに言う代わりに、「ここは 位置のコナーセンス なので、名前のコナーセンス に弱めましょう」と、問題と直し方を具体的に伝えられるようになります。

    このページでは次の内容を扱います。

    1. コナーセンスの 定義と由来
    2. 3つの性質（強さ・局所性・程度）
    3. 9つの種類（静的5つ・動的4つ）と、それぞれの弱め方
    4. コナーセンスを改善する 3つの指針
    5. アーキテクチャ（サービス間）での使い方

    2.コナーセンスとは

    2.1 定義

    2つの部品があり、一方を変更したときに、システム全体の正しさを保つためにもう一方も変更しなければならない とき、その2つは コナーセント（connascent）である。

    • 「connascence」は「共に生まれる」という意味の英語です。一緒に変わる運命にある関係、というニュアンスがあります
    • Meilir Page-Jones が 1990 年代に提唱し（『What Every Programmer Should Know about Object-Oriented Design』1996 など）、その後 Jim Weirich の講演で広く知られるようになりました
    • 『ソフトウェアアーキテクチャの基礎』第3章でも、結合を正確に説明するための言語として紹介されています

    2.2 なぜ「数」だけでは足りないのか

    次の2つの関数呼び出しは、どちらも「依存が1つ」です。

    // A: 名前で依存している
createUser({ name: "Taro", email: "taro@example.com", isAdmin: false });

// B: 位置で依存している
createUser("Taro", "taro@example.com", false);

    A：名前で依存

    引数の 名前 にだけ依存しています。定義側で引数の順番を入れ替えても壊れません。

    B：位置で依存

    引数の 順番 に依存しています。定義が createUser(email, name, ...) に変わると、エラーにならずに 名前とメールアドレスが入れ替わって保存されます。

    数は同じでも、B の方が壊れやすい。この違いを表すのがコナーセンスです。

    3.コナーセンスの3つの性質

    性質意味望ましい状態
    強さ（Strength）見つけにくさ・直しにくさ。種類によって決まる弱い ほど良い
    局所性（Locality）結合している部品同士がどれだけ 近い か（同じ関数・同じクラス・同じモジュール・別サービス）強い結合ほど 近く に置く
    程度（Degree）その結合に巻き込まれている部品の 数少ない ほど良い

    この3つを 組み合わせて 考えるのがポイントです。

    • 同じ関数の中の強い結合（局所性が高い）は、ほとんど問題になりません
    • 別サービスとの強い結合（局所性が低い）は、深刻な問題になります
    • 2か所だけの結合（程度が小さい）より、200か所に散らばった結合（程度が大きい）の方が直すのが大変です

    4.9つの種類

    コナーセンスには、現在広く合意されている 9つの種類 があります。コードを読めば分かる 静的コナーセンス が5つ、実行しないと分からない 動的コナーセンス が4つです。後ろにあるものほど 強い（見つけにくく、直しにくい）結合です。

    静的と動的の境目

    動的コナーセンスは、もっとも弱いものでも、もっとも強い静的コナーセンスより強い とされます。実行時にしか分からない結合は、コンパイラやテストで見つけにくいためです。

    4.1 静的① 名前のコナーセンス（Connascence of Name）

    複数の部品が、ある要素の 名前 について合意している必要がある状態です。

    function calculateTax(price: number) { ... }
calculateTax(1000);   // 関数名を変えたら、呼び出し側も変える必要がある
    • もっとも弱い コナーセンスで、どんなコードにも必ずあります
    • IDE のリネーム機能で、安全に一括変更できます
    • 他のコナーセンスを、できるだけこの形に変えていく のが基本方針です

    4.2 静的② 型のコナーセンス（Connascence of Type）

    複数の部品が、ある要素の 型 について合意している必要がある状態です。

    function sendMail(to: EmailAddress) { ... }
sendMail(user.email);  // user.email も EmailAddress 型である必要がある
    • 静的型付け言語ではコンパイラが不一致を検出してくれるので、比較的安全です

    4.3 静的③ 意味のコナーセンス（Connascence of Meaning / Convention）

    複数の部品が、ある 値の意味 について合意している必要がある状態です。「慣習（Convention）のコナーセンス」とも呼ばれます。

    ✕ 「1 は有効、0 は無効」という約束を、送る側と受け取る側の両方が知っている 
    if (user.status === 1) { ... }
    ○ 名前付きの定数・列挙型にする → 名前のコナーセンスに弱まる 
    enum UserStatus { Active = "active", Inactive = "inactive" }
if (user.status === UserStatus.Active) { ... }
    • 「マジックナンバー」「マジックストリング」がこれにあたります
    • 定数や列挙型で名前を付ける と、名前のコナーセンスに弱められます

    4.4 静的④ 位置のコナーセンス（Connascence of Position）

    複数の部品が、値の 順番 について合意している必要がある状態です。

    ✕ 引数の順番に依存 
    createUser("Taro", "taro@example.com", false, true);
    ✕ 配列の位置に意味がある 
    const row = ["Taro", 30, "Tokyo"];  // row[1] が年齢、という約束
    ○ オブジェクトにして名前で渡す → 名前のコナーセンスに弱まる 
    createUser({ name: "Taro", email: "taro@example.com", isAdmin: false, notify: true });
    • 静的コナーセンスの中で強い部類 です。同じ型の引数が並ぶと、順番を間違えてもコンパイラが気づきません（上の例の false, true はどちらがどちらか読み取れません）
    • 引数が3つを超えたら、オブジェクト（引数オブジェクト）にまとめることを検討します

    4.5 静的⑤ アルゴリズムのコナーセンス（Connascence of Algorithm）

    複数の部品が、同じ アルゴリズム を使うことに合意している必要がある状態です。

    // 送信側
const signature = hmacSha256(payload, secret);
// 受信側（別のサービス）も、まったく同じ方式で検証する必要がある
const expected = hmacSha256(payload, secret);
    • 例：パスワードのハッシュ方式、署名の検証方式、チェックディジットの計算方法、データの暗号化方式
    • 片方だけ変えると、エラーにならずに検証が失敗し続けます
    • 対策：アルゴリズムを 1か所（共通モジュール・ライブラリ）に集約 し、両方がそれを呼ぶ形にします。こうすると、両者の結合は「その関数の名前」に対するコナーセンスに弱まります

    4.6 動的⑥ 実行順序のコナーセンス（Connascence of Execution）

    部品の 実行順序 が重要である状態です。

    ✕ open → write → close の順番を、呼び出し側が守る必要がある 
    const file = new File(path);
file.open();
file.write(data);
file.close();
    ○ 順番を内部に閉じ込める 
    writeFile(path, data);  // 内部で open → write → close
    • 例：「初期化メソッドを呼んでから使う」「メール送信前に宛先を設定する」
    • 対策：正しい順番でしか呼べない API にする（コンストラクタで初期化を済ませる、まとめて実行する関数を用意する）

    4.7 動的⑦ タイミングのコナーセンス（Connascence of Timing）

    部品の 実行タイミング が重要である状態です。

    • 例：2つのスレッドが同時に同じ変数を更新すると壊れる（競合状態）、タイムアウト値が呼び出し側と呼ばれる側で整合している必要がある
    • 発見が非常に難しく、テストでも再現しにくい種類です
    • 対策：ロック・トランザクション・不変データ・メッセージキューによる直列化

    4.8 動的⑧ 値のコナーセンス（Connascence of Values）

    複数の値が、互いに整合した状態で一緒に変わる 必要がある状態です。

    • 例：「注文の合計金額」と「明細の金額の合計」が常に一致している必要がある
    • 例：分散システムで、2つのサービスにまたがるデータを同時に更新する必要がある（分散トランザクション）
    • これは 不変条件（常に成り立つべきルール）そのものです（→ トレードオフとアーキテクチャに効く原則 の「不変条件の境界」）
    • 対策：整合性が必要な値を 1つの境界（集約・1つのサービス・1つのトランザクション）の中に閉じ込める

    4.9 動的⑨ 同一性のコナーセンス（Connascence of Identity）

    複数の部品が、同じインスタンス（実体） を参照している必要がある状態です。

    • 例：2つのコンポーネントが同じキュー・同じキャッシュオブジェクト・同じ DB 接続を共有していないと正しく動かない
    • もっとも強い コナーセンスです
    • 対策：共有を減らし、必要なら所有者を1つに決めて、他はその所有者経由でアクセスする

    4.10 9種類の一覧

    #種類分類合意している内容主な弱め方
    ①名前静的要素の名前（目標とする形）IDE のリネームで管理
    ②型静的要素の型静的型付けでコンパイラに検査させる
    ③意味静的値の意味（マジックナンバー）定数・列挙型で名前を付ける
    ④位置静的値の順番引数オブジェクトにして名前で渡す
    ⑤アルゴリズム静的同じ計算方式1か所に集約して共有する
    ⑥実行順序動的呼び出しの順番正しい順番でしか呼べない API にする
    ⑦タイミング動的実行のタイミングロック・トランザクション・不変データ・キュー
    ⑧値動的複数の値の整合1つの境界に閉じ込める
    ⑨同一性動的同じ実体を参照所有者を1つに決め、他は経由させる

    5.コナーセンスを改善する3つの指針

    Page-Jones と Weirich の考え方をまとめると、次の3つになります。

    指針内容例
    ① 強さを弱める強い種類のコナーセンスを、弱い種類に置き換える位置 → 名前（引数オブジェクト）、意味 → 名前（列挙型）、実行順序 → 内部に隠す
    ② 局所性を高める強いコナーセンスほど、近く（同じ関数・クラス・モジュール）に置く値のコナーセンスがある2つのデータを、別サービスから同じサービスへ移す
    ③ 程度を減らす結合に巻き込まれる部品の数を減らす50か所で同じ計算をしている → 1つの関数に集約して1か所にする

    『基礎』ではこれを 「カプセル化によって、強いコナーセンスをモジュールの内側に閉じ込める」 と表現しています。これは 高凝集 の言い換えでもあります。

    モジュールの中は強く結びつき（高凝集）、モジュールの間は弱く結びつく（疎結合）

    これは、モジュール性・疎結合と高凝集 の原則を、コナーセンスの言葉で具体化したものです。

    6.アーキテクチャでの使い方 — サービス間のコナーセンス

    コナーセンスはクラスや関数の話だけではありません。サービス間・システム間の結合 を考えるときにも非常に役立ちます。サービス間は局所性がもっとも低い（＝遠い）場所なので、サービス間には弱いコナーセンスしか置くべきではありません。

    コナーセンスサービス間での例弱め方判定
    名前API のエンドポイント名・JSON のフィールド名許容範囲。API のバージョニングで変更を管理許容
    型JSON スキーマ・gRPC の型定義スキーマを契約として公開し、互換性を保つ許容
    意味status: 3 が「発送済み」を意味する意味の分かる文字列にする、契約に明記する要注意
    位置CSV 連携で列の順番に意味がある項目名付きの形式（JSON など）にする要注意
    アルゴリズム両サービスが同じ方式で署名・ハッシュを計算共通ライブラリ化、または一方に処理を寄せる要注意
    実行順序「先に在庫サービスを呼んでから決済サービスを呼ぶ」必要があるオーケストレーション（SAGA）で順序を1か所に集約要注意
    タイミング呼び出し側のタイムアウトが、呼ばれる側の処理時間より短い非同期化、タイムアウトとリトライの設計要注意
    値注文サービスと在庫サービスのデータを同時に整合させる必要があるサービス境界を見直す、または結果整合性と SAGA を採用境界を疑う
    同一性複数のサービスが同じ DB テーブルを直接読み書きするデータ所有権 を1サービスに決め、他は API 経由にする境界を疑う

    値・同一性のコナーセンスがサービス間にあったら

    表の下の2行（値・同一性）がサービス間に現れたら、サービスの分け方そのものが間違っている サインであることが多いです。これは 分散モノリス（分けたのに一緒にしか動かせない状態）の典型的な原因です（→ モノリス・分散モノリス・マイクロサービス、データ所有権・分散トランザクション・SAGA）。

    ※「判定」列は、本文の指針（遠い場所には弱いコナーセンスだけを置く）に沿って、このページで整理した目安です。

    7.よくある誤解

    「コナーセンスはゼロにすべき」

    誤りです。 部品が協力して動く以上、コナーセンスは必ずあります。目標は ゼロにすること ではなく、弱い種類にし、近くに置き、数を減らす ことです。

    「強いコナーセンスは常に悪い」

    誤りです。 同じ関数の中で、2つの変数が値のコナーセンスを持つのは普通のことです。問題になるのは、強いコナーセンスが遠い場所（別モジュール・別サービス）にまたがるとき です。

    「静的型付け言語なら結合の問題は起きない」

    誤りです。 型のコナーセンスまではコンパイラが守ってくれますが、意味・位置（同じ型が並ぶ場合）・アルゴリズム・すべての動的コナーセンスは検出できません。

    8.まとめ

    このページの要点

    • コナーセンス：一方を変えたら、もう一方も変えなければ正しく動かない関係。結合の 種類と強さ を表す語彙
    • 3つの性質：強さ（種類で決まる）・局所性（近さ）・程度（巻き込まれる数）
    • 9つの種類（弱い → 強い）
      • 静的：名前 → 型 → 意味 → 位置 → アルゴリズム
      • 動的：実行順序 → タイミング → 値 → 同一性
    • 改善の指針：強さを弱める・局所性を高める・程度を減らす。強いコナーセンスはモジュールの内側に閉じ込める（＝高凝集）
    • サービス間に 値・同一性 のコナーセンスがあれば、境界を見直すべきサイン
