    品質特性シナリオと計測

    「可用性が大事」と決めただけでは、何をもって合格とし、どう確かめ、どう劣化に気づくのかが分かりません。このページでは、特性を具体的で検証できる形に書き下す「品質特性シナリオ（6要素）」、シナリオに優先順位をつける「ユーティリティツリー」、運用・構造・プロセスの3種類の計測、そして計測を自動で守り続ける「適応度関数」までを一続きで解説します。

    もとにしたノート：05_品質特性シナリオと計測

    1.このページで扱うこと

    前のページでは「品質属性は測れるべき」ことと、重要な特性を見つけて上位3つに絞る方法を学びました。しかし「可用性が大事」と決めただけでは、まだ次のことが分かりません。

    • どのくらいの可用性なら合格なのか
    • 設計がそれを満たしているか、どう確かめるのか
    • 運用中に劣化していないか、どう気づくのか

    このページでは、特性を具体的で、検証できる形に書き下す方法として、次の4つを順に解説します。

    1. SEI（カーネギーメロン大学ソフトウェア工学研究所）の品質特性シナリオ（6要素）
    2. シナリオを優先順位づけするユーティリティツリー（ATAM）
    3. 『ソフトウェアアーキテクチャの基礎』の3種類の計測（運用・構造・プロセス）
    4. 計測を自動で守り続ける適応度関数への橋渡し

    2.なぜ「シナリオ」で書くのか

    「システムは高い可用性を持つこと」という要件には、次の問題があります。

    問題例
    何が起きたときの話か分からないサーバーが1台落ちたとき？ データセンター全体が落ちたとき？
    どこの話か分からない注文 API？ 管理画面？ バッチ処理？
    合格ラインが分からない99%？ 99.99%？ 30秒で復旧？ 1時間で復旧？

    そこで、「いつ・何が起きて・どこに・どう反応し・どの程度なら合格か」を1文で書きます。これが品質特性シナリオです。

    3.品質特性シナリオの6要素

    SEI が提唱した形式（Bass・Clements・Kazman『実践ソフトウェアアーキテクチャ』で広まったもの）では、シナリオを次の6つの要素で書きます。

    要素意味可用性の例
    ① 刺激の発生源（Source）刺激を引き起こすもの（人・システム・環境）クラウド基盤
    ② 刺激（Stimulus）システムに届く出来事アプリサーバー1台が突然停止する
    ③ 環境（Environment）そのときのシステムの状態平常運用中（ピーク時間帯）
    ④ 成果物（Artifact）刺激を受ける部分注文 API
    ⑤ 応答（Response）システムがどう反応するかロードバランサーが故障を検知し、残りのサーバーに振り分ける
    ⑥ 応答の測定値（Response Measure）応答が合格かどうかを判定する数値30秒以内に切り替わり、失敗する注文は 0.1% 以下

    6要素を1文にまとめると、次のようになります。

    ピーク時間帯の平常運用中に、クラウド基盤の障害でアプリサーバー1台が停止したとき、注文 API は残りのサーバーで処理を継続し、30秒以内に切り替わり、失敗する注文は 0.1% 以下である。

    書くときのコツ

    ⑥ の測定値が書けないシナリオは、まだ検証できません。逆に ⑥ があれば、設計レビュー・負荷試験・障害試験・本番監視のどれで確かめるかを決められます。

    3.1 特性ごとのシナリオ例

    特性シナリオ（6要素を含む1文）
    性能年末セールのピーク時に、利用者が毎秒 1,000 件の商品検索を送ったとき、検索 API は 95パーセンタイルで 300ms 以内に結果を返す
    スケーラビリティ／弾力性チケット発売開始の瞬間に、アクセスが平常時の 50 倍に急増したとき、受付システムは 5分以内に自動でスケールアウトし、エラー率 1% 以下を保つ
    修正容易性（保守性）開発者が新しい決済手段を追加するとき、通常の開発期間中に、決済モジュールだけを変更し、他モジュールの変更なしで 3人日以内に本番リリースできる
    セキュリティ外部の攻撃者が、平常運用中に、ログイン API に総当たり攻撃を仕掛けたとき、システムは同一アカウントへの試行を5回で一時ロックし、管理者に 1分以内に通知する
    テスト容易性開発者が、開発中に、注文ドメインのロジックを変更したとき、DB や外部 API なしで単体テストを1分以内に実行できる
    デプロイ容易性開発チームが、平日の業務時間中に、在庫サービスの新バージョンをデプロイするとき、利用者に停止を見せずに 15分以内に完了し、問題があれば 5分以内にロールバックできる
    例：修正容易性のシナリオを6要素に分解すると
    要素内容
    ① 発生源開発者
    ② 刺激新しい決済手段を追加したい
    ③ 環境通常の開発期間中
    ④ 成果物決済モジュール（とそれ以外のモジュール）
    ⑤ 応答決済モジュールだけを変更して本番リリースする
    ⑥ 応答の測定値他モジュールの変更なし、3人日以内

    運用特性だけでなく、変更という「刺激」を考えれば構造特性も同じ型で書けることが分かります。

    ポイントは、保守性やテスト容易性のような「構造特性」もシナリオで書けることです。「保守しやすいこと」は検証できませんが、「新しい決済手段を他モジュールの変更なしで追加できる」は設計レビューで検証できます。

    4.ユーティリティツリーで優先順位をつける

    シナリオを書き出すと、数十個になることもあります。全部を同じ重みで扱うことはできません（→ トレードオフとアーキテクチャに効く原則）。SEI の評価手法 ATAM（Architecture Tradeoff Analysis Method）では、ユーティリティツリーでシナリオを整理し、優先順位をつけます。

    各シナリオに2つの評価（H＝高・M＝中・L＝低）を付けます。

    評価軸問い
    ビジネス上の重要度満たせないと事業にどれだけ影響するか
    アーキテクチャ上の難しさ実現するのがどれだけ難しいか・リスクが高いか

    （H, H）のシナリオが、アーキテクチャで最も注意して扱うべきものです。上の例なら「サーバー1台停止で30秒以内に切替」がそれにあたり、ここに設計の工数とレビューを集中させます。

    （H, H）

    重要で難しい。設計の中心課題。プロトタイプや障害試験で早めに確かめる。

    （H, M）・（M, H）

    次に注意すべきもの。重要度か難しさのどちらかが高い。

    （H, L）

    重要だが実現は容易。通常の設計で満たせることが多い。

    （M, L）・（L, *）

    優先度は低め。後回しや設計レベルでの対応でよい。

    小さなチームでの使い方

    ATAM 自体は、ステークホルダーを集めて数日かけて行う本格的な評価手法で、シナリオに対する設計上のリスク・感度点（ある特性を大きく左右する設計判断）・トレードオフ点を洗い出します。小さなチームでは、ユーティリティツリーの考え方だけを借りて、30分のワークショップで上位シナリオを決めるだけでも十分効果があります。

    5.『ソフトウェアアーキテクチャの基礎』の3種類の計測

    『基礎』では、アーキテクチャ特性の計測を3種類に分けています。

    運用の計測

    本番での振る舞い。性能・可用性・スケーラビリティなど。

    構造の計測

    コードの構造。保守性・テスト容易性など。

    プロセスの計測

    開発プロセス。アジリティ・デプロイ容易性など。

    5.1 運用の計測（Operational measures）

    本番環境での振る舞いを測ります。性能・可用性・スケーラビリティなどの運用特性が対象です。

    指標注意点
    応答時間平均だけを見ない。平均は少数の極端に遅いリクエストを隠す。パーセンタイル（p95・p99）で見る
    スループット単位時間あたりの処理件数
    エラー率失敗したリクエストの割合
    稼働率99.9% なら月に約 43 分、99.99% なら月に約 4 分の停止が許される
    平均とパーセンタイルの違い（仮の数値で考える）

    100件のリクエストのうち、90件が 100ms、10件が 2,000ms で返ったとします。

    • 平均：(90 × 100 + 10 × 2,000) ÷ 100 ＝ 290ms。数字だけ見ると「300ms 以内」で問題なさそうに見えます。
    • p95（遅い方から5%の位置の値）：2,000ms。10人に1人が2秒待たされていることが分かります。

    p95 は「95% のリクエストはこの時間以内に返る」という意味なので、利用者の体感の悪いケースを捉えられます。

    運用の計測は、SRE（サイト信頼性エンジニアリング）の SLI／SLO とほぼ同じ考え方です。

    用語意味例
    SLI（サービスレベル指標）何を測るか300ms 以内に返ったリクエストの割合
    SLO（サービスレベル目標）どこを目標にするか30日間で 99% のリクエストが 300ms 以内
    SLA（サービスレベル合意）顧客との約束と、破ったときの補償稼働率 99.9% を下回ったら返金
    エラーバジェット100% − SLO。許容される失敗の量SLO 99.99%（30日）なら約4分の停止まで許容

    品質特性シナリオの「⑥ 応答の測定値」は、運用中は SLO として監視されます。一般に SLA は SLO より緩く設定し、SLO を守っていれば SLA 違反にならないようにします。SLI・SLO の設計の詳細は、41 外のノート：66_可観測性『01_SLI・SLOの設計』を参照してください（観測性の全体は 観測性（ログ・メトリクス・トレース））。

    5.2 構造の計測（Structural measures）

    コードの構造を測ります。保守性・テスト容易性などの構造特性が対象です。

    指標何を測るか目安
    循環的複雑度（Cyclomatic Complexity）関数の中の分岐（if・for・case）の多さ。McCabe が提唱1関数あたり 10 以下が一般的な目安。5 以下が望ましいとする意見も多い
    凝集度の欠如（LCOM）クラス内のメソッドが同じフィールドを共有していない度合い高いほど、クラスを分割すべきサイン
    結合度（求心性・遠心性）モジュール間の依存の数→ 結合の指標（求心性・遠心性・主系列からの距離）
    循環依存の有無モジュール間の依存がループしていないか0 であるべき

    循環的複雑度は、おおまかには「分岐の数 ＋ 1」で、その関数を網羅するのに必要なテストケースの数の目安にもなります。

    function shippingFee(order) {        // 基本の経路：1
  if (order.total >= 5000) return 0;  // if：+1
  if (order.isRemote) {               // if：+1
    return order.express ? 1500 : 1000; // 三項演算子：+1
  }
  return 500;
}
// 循環的複雑度 ＝ 4

    数値は「問題がありそうな場所」を見つける道具

    構造の計測は、それだけで「良い設計」を保証しません。数値は問題の候補を見つけるためのもので、最終的な判断は人が行います。

    5.3 プロセスの計測（Process measures）

    開発プロセスを通して測ります。アジリティ・テスト容易性・デプロイ容易性などが対象です。

    指標例
    テストカバレッジ自動テストがコードのどれだけを通っているか
    デプロイ頻度1日に何回本番デプロイできるかFour Keys
    変更のリードタイムコミットから本番反映までの時間Four Keys
    変更失敗率デプロイが障害につながった割合Four Keys
    復旧時間障害から復旧するまでの時間Four Keys

    下の4つは、DevOps の研究（DORA：DevOps Research and Assessment）で使われる Four Keys と同じものです。「アジリティ」のような複合特性は、このプロセスの計測で間接的に測ります。

    6.計測から適応度関数へ

    シナリオを書き、計測方法を決めたら、最後はそれを自動で守り続ける仕組みにします。これがアーキテクチャ適応度関数（Fitness Function）です（Neal Ford ほか『進化的アーキテクチャ』。→ 進化的アーキテクチャと適応度関数）。

    シナリオ（品質目標）適応度関数（自動チェック）種類
    検索 API は p95 で 300ms 以内本番監視で SLO を常時計測し、違反したらアラート継続型
    注文ドメインは DB に依存しないアーキテクチャテスト（ArchUnit など）を CI で実行トリガー型
    モジュール間の循環依存ゼロ静的解析を CI で実行し、検出したらビルド失敗トリガー型
    関数の循環的複雑度 10 以下Lint ルールで検査トリガー型
    サーバー1台停止で30秒以内に切替カオスエンジニアリング（意図的に障害を起こすテスト）を定期実行継続型

    トリガー型

    コミットやビルドなど、特定のきっかけで実行されるチェック。CI のテストや静的解析が代表例。

    継続型

    本番環境などで常に動き続けるチェック。監視・アラートや定期的な障害注入が代表例。

    流れをまとめると、次のようになります。

    7.よくある誤解

    7.1 「数値目標は高いほど良い」

    誤りです

    99.9% と 99.99% では、許される停止時間が月 43 分と月 4 分で約10倍違い、必要な構成とコストも大きく変わります。ビジネス上必要な水準に合わせます（前のページの「過剰品質」）。

    7.2 「平均応答時間を見れば性能が分かる」

    誤りです

    平均は少数の非常に遅いリクエストを隠します。利用者の体感に近いのは p95・p99 です。

    7.3 「保守性やテスト容易性は測れない」

    誤りです

    「新機能の追加が他モジュールの変更なしでできる」のようなシナリオで書けば、設計レビューや変更履歴で検証できます。構造の計測（循環的複雑度・結合度）やプロセスの計測（リードタイム）も補助になります。

    7.4 「メトリクスの数値が良ければ設計も良い」

    数値は目安です

    循環的複雑度やカバレッジは、問題の候補を見つける道具です。数値を満たすためだけのテストや分割は、かえって設計を悪くすることがあります。最終判断は人が行います。

    8.まとめ

    • 品質特性はシナリオで書くと、具体的で検証できる要求になります。
    • シナリオの6要素は ① 発生源　② 刺激　③ 環境　④ 成果物　⑤ 応答　⑥ 応答の測定値。構造特性も「変更」を刺激として同じ型で書けます。
    • ユーティリティツリーで「ビジネス上の重要度 × アーキテクチャ上の難しさ」を評価し、（H, H）に集中します。
    • 計測には運用（p95・稼働率・SLO）／構造（循環的複雑度・結合度）／プロセス（デプロイ頻度・リードタイム）の3種類があります。
    • 計測を CI や監視で自動化したものが適応度関数。特性を「決める」から「守り続ける」へ進めます。

    次のページでは、特性同士が衝突したときにどう判断するか ― トレードオフと、判断の軸になる原則 ― を学びます。構造の計測をさらに詳しく知りたい場合は、モジュール性・疎結合と高凝集 と 結合の指標 へ進んでください。
