    CQRS — コマンドとクエリの責務分離

    CQRS は、データを更新するためのモデル（コマンド側）と読み取るためのモデル（クエリ側）を分ける考え方です。源流の CQS との関係、「コードの分離 → モデルの分離 → データストアの分離」という3つの段階、クリーン／ヘキサゴナルとの組み合わせ方、そして Fowler が警告する「使うべきでない場面」までを解説します。

    もとにしたノート：CQRS_コマンドとクエリの責務分離 / 00_解説_アプリ内部構造

    1.このページで扱うこと

    クリーンアーキテクチャやヘキサゴナルアーキテクチャでドメインモデルを中心に据えると、しばらくして次のような悩みが出てきます。

    • 一覧画面のために、集約を何十件も読み込んでから DTO に詰め替えている。遅いうえにコードが冗長
    • 画面ごとに欲しいデータの形が違い、Repository に findForListScreen() findForDashboard() … とメソッドが増え続ける
    • 書き込みのための「正しいモデル」と、読み取りのための「便利なモデル」が、1つのクラスの中でせめぎ合っている

    このページでは、この悩みに対する考え方 CQRS（Command Query Responsibility Segregation：コマンドとクエリの責務分離）を解説します。

    • 源流である CQS（コマンド・クエリ分離）との関係
    • CQRS の 段階（コードの分離 → モデルの分離 → データストアの分離）
    • イベントソーシングとの関係
    • クリーン／ヘキサゴナル／垂直スライスとの組み合わせ
    • 使うべきでない場面（Fowler の警告）と、ありがちな誤解

    2.源流：CQS（コマンド・クエリ分離）

    CQS とは

    CQS（Command Query Separation）は、Bertrand Meyer（バートランド・メイヤー）が『オブジェクト指向入門』（1988）で提唱した、メソッドレベルの原則です。

    メソッドは、状態を変える「コマンド」か、値を返す「クエリ」のどちらか一方であるべきで、両方を兼ねてはならない。

    「質問をしても答えが変わってはいけない」

    ✕ 値を返しながら状態も変える 
    function popAndCount(): number { ... }
    ○ コマンドとクエリに分ける 
    function pop(): void { ... }        // コマンド：状態を変える、何も返さない
function count(): number { ... }    // クエリ：値を返す、状態を変えない

    クエリを何回呼んでも状態が変わらないので、安心して呼べ、テストもしやすくなります。CQS の詳細は 41 外のノート：46_メソッド設計『01_CQS』を参照してください。

    CQS から CQRS へ

    Greg Young（グレッグ・ヤング）が 2010 年ごろ、この考え方をアーキテクチャのレベルに広げたのが CQRS です。

    CQSCQRS
    単位メソッドモデル・コンポーネント・データストア
    分けるもの1つのメソッドの責務書き込み側のモデルと読み取り側のモデル
    提唱Bertrand Meyer（1988）Greg Young（2010 年ごろ）

    3.CQRS とは

    基本の考え方

    CQRS の定義

    データを更新するためのモデル（コマンド側）と、データを読み取るためのモデル（クエリ側）を、別々に作る。

    なぜ分けるのか — 書き込みと読み取りは性質が違う

    観点書き込み（コマンド）読み取り（クエリ）
    目的業務ルールを守って状態を変える画面に必要な形でデータを見せる
    重視すること整合性・不変条件・トランザクション速さ・画面への合わせやすさ
    データの形集約（業務のまとまり）単位画面単位（複数の集約をまたいで結合・集計）
    量少ない（1件ずつ）多い（一覧・検索・集計）
    頻度一般的に少ない一般的に多い（読み取りが大半を占めるシステムも多い）

    1つのモデルで両方を満たそうとすると、どちらにとっても中途半端になります。

    • 業務ルールのためのドメインモデルに、画面表示用のプロパティが増えていく
    • 一覧表示のために、重いドメインモデルを大量に組み立てて、すぐ捨てる

    4.CQRS の3つの段階

    CQRS は「全部やるか、やらないか」ではなく、段階的に適用できます。

    段階1：コードの分離（同じ DB）

    書き込みはドメインモデル、読み取りは直接クエリに分けます。DB は1つのままです。

    コマンド側：ドメインモデルで業務ルールを守る 
    class CancelOrderUseCase {
  constructor(private orders: OrderRepository) {}
  async execute(orderId: string) {
    const order = await this.orders.findById(orderId);
    order.cancel();                 // 「発送済みならキャンセル不可」などのルールは Order が守る
    await this.orders.save(order);
  }
}
    クエリ側：ドメインモデルを通さず、画面に必要な形を直接取る 
    class OrderListQuery {
  constructor(private db: Database) {}
  async forUser(userId: string): Promise<OrderListItemDto[]> {
    return this.db.sql`
      SELECT o.id, o.ordered_at, o.status, SUM(i.price * i.qty) AS total
      FROM orders o JOIN order_items i ON i.order_id = o.id
      WHERE o.user_id = ${userId}
      GROUP BY o.id ORDER BY o.ordered_at DESC`;
  }
}
    • 最も手軽で、効果が大きい段階です。多くのアプリはここで十分です。
    • Repository は集約の保存と取得だけに専念でき、画面ごとの検索メソッドが増え続ける問題が消えます。
    • 垂直スライスアーキテクチャの「スライスごとに作り方を変える」（単純な参照は SQL 直書き、複雑な更新だけドメインモデル）も、この段階の CQRS とほぼ同じ発想です。

    段階2：モデルの分離（読み取り専用のビュー・テーブル）

    読み取り用に、画面に最適化したビューやテーブル（リードモデル・投影〔プロジェクション〕）を用意します。

    • 例：注文一覧のために、注文・顧客・商品を結合済みの order_list_view を用意する
    • 書き込み時に、同じトランザクション内で更新するか、イベント経由で（後から）更新する

    同じトランザクション内で更新すれば読み取り側はすぐに最新になりますが、イベント経由で非同期に更新する場合は、反映までの遅れ（結果整合性）が生じます。そのため、表では結果整合性を「更新方法次第」としています。

    段階3：データストアの分離

    書き込み用と読み取り用で、別のデータベースを使います。

    • 例：書き込みは RDB（整合性重視）、読み取りは検索エンジン（Elasticsearch など）やキャッシュ（速さ重視）
    • 両者は非同期に同期されるため、結果整合性（書き込み直後は読み取り側に反映されていないことがある）を受け入れる必要があります
    • ここまで来ると、40_システム・分散の領域（イベント駆動・結果整合性）と重なります（→ データ所有権・分散トランザクション・SAGA、同期 API・メッセージ・イベント駆動）

    3つの段階の比較

    段階分けるもの複雑さ結果整合性
    1. コードの分離クラス・処理低いなし
    2. モデルの分離読み取り用ビュー・テーブル中更新方法次第
    3. データストアの分離データベース高いあり

    5.補足：イベントソーシングとの関係

    CQRS は イベントソーシング（状態ではなく「起きた出来事の列」を保存する方式）とセットで語られることが多いですが、別の概念です。

    CQRS だけを使う

    イベントソーシングなしでも使えます。段階1・2の多くはそうです。普通のテーブルに「現在の状態」を保存し、読み取りだけ別の経路にします。

    イベントソーシングを使う

    出来事の列（「注文された」「キャンセルされた」…）から画面用の読み取りモデルを作る必要があるため、ほぼ必ず CQRS になります。

    イベントソーシングはデータの持ち方の話なので、41 外のノート：68_データアーキテクチャ、および 40_システム・分散の領域で扱います。

    6.クリーン／ヘキサゴナルとの組み合わせ

    CQRS は、クリーンアーキテクチャやヘキサゴナルと相性が良いです。フォルダ構成の例を示します。

    src/
  application/
    commands/                    ← コマンド側：ドメインモデルを使う
      PlaceOrderUseCase.ts
      CancelOrderUseCase.ts
    queries/                     ← クエリ側：読み取り専用のインターフェース
      OrderListQuery.ts          （interface：内側に置く）
  domain/
    order/Order.ts               ← 業務ルールはコマンド側だけが使う
    order/OrderRepository.ts     ← 集約の保存・取得だけ
  infrastructure/
    db/PrismaOrderRepository.ts
    db/SqlOrderListQuery.ts      ← クエリの実装：SQL を直接書いてよい
    • コマンド側は、これまでどおり依存性のルールを守り、ドメインモデルで業務ルールを表現します。
    • クエリ側は読み取り専用なので、業務ルールを守る必要がありません。インターフェースだけ内側に置き、実装は SQL を直接書いてかまいません。
    • 結果として、ドメインモデルは書き込みの正しさだけに集中でき、画面の都合から解放されます。

    クエリ側も「インターフェースは内側、実装は外側」という形にしておけば、依存の向き（外 → 内）は崩れません。ヘキサゴナルの用語でいえば、OrderListQuery は読み取り用の Driven Port、SqlOrderListQuery はその Driven Adapter です。

    CQRS を入れるサイン

    クリーンアーキテクチャで「一覧画面のためだけに Entity を大量に組み立てる」のがつらいと感じたら、それは段階1の CQRS を入れるサインです。

    7.使うべきでない場面 — Fowler の警告

    Martin Fowler は CQRS の解説で、はっきりと次のように警告しています。

    ほとんどのシステムにとって、CQRS はリスクの高い複雑さを加える。

    CQRS を使うときは、非常に慎重であるべきだ。

    とくに段階3（データストアの分離）は、

    • 同期の仕組み・結果整合性への対応・障害時のリカバリが必要になる
    • 「保存したのに一覧に出てこない」という問い合わせに対応する必要がある
    • チームの学習コストが高い

    という大きなコストを伴います。

    CQRS が向いているCQRS が向いていない
    読み取りと書き込みの負荷が大きく違う（読み取りが圧倒的に多い）単純な CRUD アプリ
    読み取りの形が画面ごとに大きく違う（ダッシュボード・検索・レポート）読み書きのモデルがほぼ同じ
    書き込み側の業務ルールが複雑（DDD を使っている）業務ルールが単純
    システムの一部分（境界づけられたコンテキストの1つ）に限定して使うシステム全体に一律に適用しようとしている

    Fowler も、CQRS はシステム全体ではなく、特定の境界づけられたコンテキストにだけ適用すべきだと述べています。

    実務的な指針

    まず段階1（コードの分離）から始める。これは低コストで、ほとんどのアプリで効果があります。段階2・3は、性能やスケールの問題が実際に起きてから検討します。

    8.ありがちな誤解

    誤解1：「CQRS には DB を2つ用意する必要がある」

    誤りです。同じ DB のまま、コードとモデルを分けるだけでも CQRS です（段階1）。

    誤解2：「CQRS とイベントソーシングはセット」

    誤りです。よく一緒に使われますが、別の概念です。CQRS はイベントソーシングなしで使えます（逆に、イベントソーシングを使うならほぼ必ず CQRS になります）。

    誤解3：「CQRS を入れればスケールする」

    半分だけ正しいです。段階3まで進めれば読み取り側を独立してスケールできますが、そのぶん複雑さと結果整合性のコストを払います。多くのシステムでは段階1で十分です。

    誤解4：「CQRS は CQS と同じもの」

    CQS はメソッド単位の原則（1つのメソッドはコマンドかクエリのどちらか）、CQRS はそれをモデル・コンポーネント・データストアの単位に広げたアーキテクチャパターンです。源流は同じですが、扱うレベルが違います。

    9.まとめ

    • CQS（Meyer, 1988）：メソッドはコマンドかクエリのどちらか。CQRS（Greg Young, 2010 年ごろ）：それをモデル・アーキテクチャのレベルに広げたもの
    • 書き込み（業務ルール・整合性）と読み取り（速さ・画面への合わせやすさ）は性質が違うので、モデルを分ける
    • 段階は ① コードの分離 → ② モデルの分離 → ③ データストアの分離。③ では結果整合性を受け入れる必要がある
    • イベントソーシングとは別の概念
    • クリーン／ヘキサゴナルでは、コマンド側だけドメインモデル、クエリ側は SQL 直書き（インターフェースは内側）という組み合わせが実用的
    • Fowler の警告：ほとんどのシステムにとって CQRS はリスクの高い複雑さ。まず段階1から、必要な部分（境界づけられたコンテキスト）にだけ
