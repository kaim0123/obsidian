    モジュール性・疎結合と高凝集

    良い設計かどうかを判断する最も基本的な物差しが「凝集度」と「結合度」です。このページでは、モジュールとは何かから始めて、凝集度・結合度のレベル、結合を語る言葉としてのコナーセンスの概要、そして「疎結合 × 高凝集」をどう実現するかを、コード例とリファクタリング例で解説します。

    もとにしたノート：10_基礎/13_モジュール性・結合/01モジュール性、03_疎結合と高凝集、10_基礎/00_解説_アーキテクチャの基礎（§3 モジュール性）

    1.このページで扱うこと

    「良い設計とは何か」と聞かれたとき、もっとも基本的で、もっとも広く使われている答えが 「疎結合（Loose Coupling）かつ高凝集（High Cohesion）」 です。クラス設計からマイクロサービスの境界決めまで、規模を問わず同じ物差しが使えます。

    凝集度（Cohesion）

    1つのモジュール の中 のまとまりの強さ。強い（高い）ほうが良い。

    結合度（Coupling）

    モジュール 同士 のつながりの強さ。弱い（疎な）ほうが良い。

    このページでは次の内容を扱います。

    • モジュールとモジュール性：そもそも「モジュール」とは何を指すのか
    • 凝集度：高凝集・低凝集の例と、凝集度の7つのレベル
    • 結合度：疎結合・密結合の例と、結合度の6つのレベル、結合を数える指標（求心性・遠心性）の入口
    • コナーセンスの概要：結合の「種類と強さ」を表す言葉
    • 疎結合 × 高凝集：4つの組み合わせ、なぜ良いのか、どう達成するか、失敗パターン
    • 判断の目安とリファクタリング例：実際のコードでどう見分け、どう直すか

    結合の指標の詳細は 結合の指標（求心性・遠心性・主系列からの距離）、コナーセンスの詳細は コナーセンス で扱います。このページはその入口にあたります。

    2.モジュールとモジュール性

    2.1 モジュールの定義

    モジュール とは、より複雑な構造を組み立てるために使う、標準化された部品（独立した単位） のことです。言語のパラダイムによって、具体的に指すものは変わります。

    パラダイムモジュールにあたるもの
    オブジェクト指向関連する クラスの集まり
    構造化言語・関数型言語関連する 関数の集まり
    アーキテクチャの議論（広い意味）パッケージ・名前空間・ライブラリ・コンポーネント・サービスなど、あらゆる「まとまりの単位」

    アーキテクチャの文脈では、モジュールを特定の言語機能に限定せず、「中身をまとめて、外とは境界で区切った単位」 として広くとらえます。このページで「モジュール」と言うときも、クラス・パッケージ・サービスのどれにも当てはまる話だと考えてください。

    2.2 モジュール性とは

    モジュール性（Modularity） とは、システムがこうした部品にうまく分けられている度合いのことです。『ソフトウェアアーキテクチャの基礎』では、モジュール性をアーキテクチャの 組織化の原則 として扱い、その良し悪しを測る手段として次の3つを挙げています。

    1. 凝集度：モジュールの中の要素が、どれだけ同じ目的のためにまとまっているか（→ 3章）
    2. 結合度：モジュール同士がどれだけ依存し合っているか。求心性結合・遠心性結合などの指標で数える（→ 4章）
    3. コナーセンス：結合の「数」ではなく「種類と強さ」を正確に表す言葉（→ 5章）

    ポイント

    モジュール性は「分けること」そのものではなく、うまく分けること です。分け方が悪ければ、モジュールの数を増やしても変更は楽になりません。うまく分けられているかを判断する物差しが、凝集度・結合度・コナーセンスです。

    3.凝集度（Cohesion）— モジュールの中のまとまり

    3.1 凝集度とは

    凝集度 とは、あるモジュールが機能するのに必要な要素が、どの程度そのモジュールの中にまとまっているか を表す指標です。言い換えると、モジュール内の要素同士の関連性の強さを測るものです。

    高凝集 とは、1つのモジュール（クラス・ファイル・パッケージ）の中にあるコードの関連性が強く、同じ目的のために動いている 状態を指します。「このモジュールは何をするものか」を一文で言えるなら、凝集度は高いといえます。

    3.2 例：高凝集なクラス

    ○ 高凝集 
    class Order {
  private items: OrderItem[];
  private status: OrderStatus;

  addItem(item) { /* ... */ }
  removeItem(id) { /* ... */ }
  confirm() { /* ... */ }
  cancel() { /* ... */ }
  total() { /* ... */ }
}

    このクラスは 「注文」に関する操作だけ を持っています。すべてのメソッドが同じ目的（注文の管理）に貢献しており、どのメソッドも items や status という同じデータを扱っています。

    3.3 例：低凝集なクラス

    ✕ 低凝集 
    class Utility {
  sendEmail() { /* ... */ }
  parseJSON() { /* ... */ }
  encryptPassword() { /* ... */ }
  formatDate() { /* ... */ }
  calculateTax() { /* ... */ }
}

    メール送信・JSON の解析・パスワードの暗号化・日付の整形・税計算と、互いに関係のない機能が詰め込まれています。これは凝集度が 低い 状態です。どれか1つを変更するときにも、このクラス全体を開いて読む必要があり、「このクラスは何のためにあるのか」を説明できません。

    3.4 凝集度の7つのレベル

    凝集度は、構造化設計（Larry Constantine らによる）以来、次の7段階で整理されるのが一般的です。上ほど望ましく（強い凝集）、下ほど望ましくない（弱い凝集） 並びにしています。

    順位レベルまとめている理由例
    1（最高）機能的凝集1つの機能に必要なものだけがそろっている。単一の目的に集中注文の管理だけを行う Order クラス
    2逐次的凝集ある処理の出力が次の処理の入力になる、手順の連続「読み込む → 整形する → 検証する」と結果を受け渡す処理群
    3通信的凝集同じデータを扱う処理をまとめた同じ顧客レコードを読み、表示用と集計用の値を作る処理
    4手続き的（手順的）凝集決まった実行順序でまとめた（データの受け渡しはない）「権限チェックをして、ログを書いて、画面を開く」を1関数に
    5時間的凝集「同じタイミングで動く」というだけでまとめた起動時の初期化処理を1か所に集めた init()
    6論理的凝集「種類が似ている」というだけでまとめたあらゆる入出力処理を集めた IOHelper
    7（最低）偶発的凝集関係のないものが、たまたま同じ場所にあるだけ前述の Utility クラス、何でも入った utils

    前述の Utility クラスは 偶発的凝集 に近く、分割すべき対象です。たとえば Mailer・JsonParser・PasswordHasher・DateFormatter・TaxCalculator のように、目的ごとに分けると機能的凝集に近づきます。

    覚え方

    下の3つ（時間的・論理的・偶発的）は「たまたま」でまとめた凝集、上の2つ（機能的・逐次的）は「目的や流れ」でまとめた凝集です。名前に「Utils」「Helper」「Common」「Misc」が付くモジュールは、下の3つになっていないか疑ってみましょう。

    4.結合度（Coupling）— モジュール同士のつながり

    4.1 結合度とは

    結合度 とは、モジュール同士がどれだけ依存し合っているか を表す指標です。疎結合 とは、モジュール同士が ゆるやかに つながっていて、一方を変えても他方にあまり影響しない状態を指します。

    4.2 例：疎結合

    ○ 疎結合 
    interface Mailer {
  send(to: string, body: string): Promise<void>;
}

class OrderService {
  constructor(private mailer: Mailer) {} // インターフェースに依存
}

    OrderService は Mailer の中身を知りません。知っているのは「send(to, body) を呼べばメールが送られる」という約束だけです。そのため、実装が SendGrid でも AWS（Amazon SES など）でも、テスト用の偽物でも差し替えられます。

    4.3 例：密結合

    ✕ 密結合 
    class OrderService {
  async sendMail() {
    const sendgrid = require('@sendgrid/mail');
    sendgrid.setApiKey('xxx');
    await sendgrid.send(...);
  }
}

    OrderService が SendGrid の詳細（ライブラリ名・API キーの設定方法・送信メソッド）まで知っています。メールの送信サービスを変えるには OrderService 自体を書き換える必要があり、テスト時に本物のメールを送らないようにするのも困難です。変更・差し替えが不可能に近い状態です。

    4.4 結合度の6つのレベル

    結合度も、構造化設計の時代から次の6段階で整理されています。上ほど弱い結合（良い）、下ほど強い結合（悪い） です。

    順位レベル状態例
    1（最弱）データ結合必要な値だけを引数で渡すcalcTax(price)
    2スタンプ結合オブジェクト（データ構造）全体を渡し、受け取り側はその一部しか使わないcalcTax(order) で order.price だけ使う
    3制御結合フラグを渡して、相手の振る舞い（処理の分岐）を制御するsave(data, isDraft) の中で分岐
    4外部結合外部で決められたデータ形式・通信手順・デバイスなどに、複数のモジュールが直接依存する複数のモジュールが外部 API の形式を直接扱う
    5共通結合グローバル変数（共有データ）を複数のモジュールが読み書きするグローバルな config を各所で書き換える
    6（最強）内容結合他のモジュールの内部（非公開のデータや処理）を直接参照・書き換えるリフレクションで他クラスの private フィールドを変更する

    判断の軸は「相手のことをどれだけ知っているか」です。データ結合では値の意味しか知りませんが、制御結合では相手の内部の分岐を、共通結合では共有データの存在を、内容結合では相手の非公開の中身まで知っています。知っていることが多いほど、相手の変更に巻き込まれます。

    4.5 結合を「数える」指標の入口

    レベル分けは結合の「質」を見る方法ですが、結合を 数で測る 方法もあります。『ソフトウェアアーキテクチャの基礎』では、次の2つを基本の指標として紹介しています。

    求心性結合（Ca：Afferent Coupling）

    外部から自分に 入ってくる 接続（依存）の数。どれだけ 頼られているか。

    遠心性結合（Ce：Efferent Coupling）

    自分から他のモジュールへ 出ていく 接続（依存）の数。どれだけ 他に頼っているか。

    この2つから、さらに次の指標を計算できます。

    指標意味
    不安定度 I = Ce / (Ca + Ce)1 に近いほど、他の変更の影響を受けやすい（変わりやすい）
    抽象度 Aモジュール内の抽象要素（インターフェース・抽象クラス）の割合
    主系列からの距離 D = |A + I − 1|0 に近いほど、抽象度と安定度のバランスが良い

    根底にあるのは「よく頼られる（安定した）モジュールほど抽象的であるべき」という考え方で、依存性逆転の原則（DIP） の裏付けにもなっています。詳しい計算方法や苦痛ゾーン・無駄ゾーンの読み方は 結合の指標 で解説します。

    5.コナーセンス（Connascence）の概要

    5.1 結合の「種類と強さ」を表す言葉

    求心性結合・遠心性結合は結合の 数 を測りますが、「その結合がどれくらい壊れやすいか」は分かりません。そこで使われるのが コナーセンス です。コナーセンスは、結合度のメトリクスではなく、異なる種類の結合をより正確に説明するための言語 であり、結合の種類ごとの一般的な影響を理解するためのものです。

    2つの部品のうち一方を変えたとき、もう一方も変えなければシステムが正しく動かない なら、その2つはコナーセント（connascent）である。

    5.2 静的コナーセンスと動的コナーセンス

    静的コナーセンス

    ソースコードのレベル の結合。コードを読めば分かる。

    動的コナーセンス

    実行時の呼び出し を分析して分かる結合。実行しないと分からない。

    分類種類例
    静的
    （ソースコードで分かる）    		名前関数名を変えると、呼び出し側も直す必要がある
    型引数の型が一致している必要がある
    意味1 が「有効」を意味する、と双方が知っている
    位置引数の順番に依存している
    アルゴリズム送信側と受信側が同じハッシュ方式を使う必要がある
    動的
    （実行時に分かる）    		実行順序open() の後に write() を呼ぶ必要がある
    タイミング同時に実行されると壊れる（競合状態）
    値複数の値が同時に整合している必要がある
    同一性同じインスタンスを参照している必要がある

    表の 上ほど弱く、下ほど強い 結合です。動的コナーセンスは、もっとも弱いものでも静的コナーセンスより強いとされます。

    5.3 コナーセンスの3つの指針

    1. 強いコナーセンスは弱いものに置き換える：例として、位置 → 名前（引数をオブジェクトにまとめる）
    2. 距離が遠いほど弱くする：同じクラスの中なら強い結合も許容できるが、サービス間では弱い結合だけにする
    3. 強いコナーセンスはモジュールの内側に閉じ込める：これは高凝集の言い換えでもある

    9種類それぞれの詳しい例と弱め方、サービス間での使い方は コナーセンス で解説します。

    6.疎結合 × 高凝集 — 4つの組み合わせ

    凝集度と結合度は、別々に評価するのではなく セットで 考えます。2つの軸を組み合わせると、次の4つの状態ができます。

    疎結合密結合
    高凝集理想 変更が局所化し、テストしやすい中身はまとまっているが、変更が波及する
    低凝集つながりは少ないが、何のモジュールか分からない最悪 大きな泥団子（Big Ball of Mud）への道

    6.1 なぜ「疎結合 × 高凝集」が良いのか

    両方がそろうと、次の4つのメリットが生まれます。高凝集と疎結合がそれぞれ別の角度から効いている点に注目してください。

    メリット高凝集の効き目疎結合の効き目
    1. 変更の影響が狭い変更が1か所に閉じる他のモジュールに波及しない
    2. 理解しやすい「このクラスは何をするもの？」が明確1つのモジュールを読むのに、他を読まずに済む
    3. 再利用しやすい機能の塊として取り出せる他に引きずられずに使える
    4. テストしやすい1つの責任をテストすればよいモック（偽物）が少なく済む

    実践的な目安：凝集の単位 = 変更の単位

    同じ理由で変わるものは一緒に、違う理由で変わるものは別々に 置きます。一緒に変わるものを一緒に置けば、変更が1つのモジュールに閉じ（高凝集）、他のモジュールを触らずに済む（疎結合）ので、自然と両方が達成されます。

    7.「疎結合 × 高凝集」を達成する手段

    1. 関心の分離

    異なる責任は別のモジュールに分けます。（41 外のノート：48_原則『01_関心の分離』）

    2. SOLID 原則

    単一責任（SRP）・開放閉鎖（OCP）・リスコフの置換（LSP）・インターフェース分離（ISP）・依存性逆転（DIP）。どれも結合度・凝集度の改善に寄与します。（41 外のノート：48_原則『SOLID』）

    3. 依存性注入・抽象化

    具体的な実装ではなく抽象（インターフェース）に依存させます。→ DI・IoC・Composition Root、依存性逆転の原則（DIP）、インターフェースと抽象化

    4. レイヤー分け

    レイヤー間のつながりは厳密に（細く）、層内のつながりは濃く。→ 層化・三層・レイヤード（4層）

    5. 凝集の単位 = 変更の単位

    同じ理由で変わるものは一緒に、違う理由で変わるものは別々に。上の4つの手段はすべて、最終的にはこの目標のための道具です。

    8.対となる失敗パターン

    4象限の「理想」以外の3つを、コードで見てみます。

    8.1 低凝集 × 密結合 = 最悪

    ✕ 低凝集 × 密結合 
    class App {
  // 認証も、支払いも、メールも、DB接続も、全部ここに
  login() { /* SendGridに直書き */ }
  payment() { /* Stripeに直書き */ }
  mail() { /* MySQLに直書き */ }
}
    • 関係のない機能が同じクラスに同居している（低凝集）
    • 具体的な外部サービスや DB の実装に直接依存している（密結合）

    メソッドの中身もちぐはぐで、どこに何が書かれているか予測できません。変更が怖くて、テストできない 典型です。

    8.2 高凝集だが密結合

    △ 高凝集 × 密結合 
    // 注文に関することだけ扱う（高凝集）
class OrderService {
  // でも StripeとSendGridに直接依存（密結合）
  async place(input) {
    await Stripe.charge(...);
    await SendGrid.send(...);
  }
}

    凝集は良いのですが、結合が強いので、決済サービスやメール送信サービスの差し替えや、テスト（本物の決済を走らせずに試すこと）が困難です。

    8.3 疎結合だが低凝集

    △ 疎結合 × 低凝集 
    // インターフェースは使っている（疎結合）
class Utility {
  constructor(
    private mailer: Mailer,
    private db: Database,
    private encryptor: Encryptor,
    // ...10個の依存
  ) {}
  // 何でもやる（低凝集）
}

    依存先はすべてインターフェースなので結合は良いのですが、1つのクラスに関係のない機能が同居しているため読みにくくなります。コンストラクタの引数が極端に多い のは、低凝集のサインであることがよくあります。

    9.判断の目安 — チェックリスト

    凝集度のチェック

    • クラス名を一言で言えるか？「UserService」「OrderRepository」のような明確な名前で表せるか
    • クラスの全メソッドが同じ目的か？
    • クラス名を見ただけで、メソッドの内容が想像できるか？

    結合度のチェック

    • このクラスを変更したら、どれだけ多くの他クラスが影響を受けるか？
    • このクラスを単体でテストできるか？
    • 依存先を差し替えられるか？

    どちらも「はい」と答えにくい項目があれば、そこが改善の候補です。結合の数を客観的に見たい場合は 結合の指標、結合の壊れやすさを言葉にしたい場合は コナーセンス が役立ちます。

    10.実例：リファクタリング

    10.1 Before：低凝集 × 密結合

    ✕ Before 
    class OrderController {
  async handle(req, res) {
    // バリデーション
    if (!req.body.items) return res.status(400).send();
    // 料金計算
    const total = req.body.items.reduce((s, i) => s + i.price, 0);
    // 支払い（Stripeに直接）
    await stripe.charges.create({ amount: total });
    // DBに直接SQL
    await db.query('INSERT INTO orders ...');
    // メール（SendGridに直接）
    await sendgrid.send(req.body.email, '完了');
    res.json({ total });
  }
}

    1つのメソッドに、バリデーション・料金計算・支払い・永続化・メール送信という5つの責任が詰め込まれ（低凝集）、Stripe・生の SQL・SendGrid に直接依存しています（密結合）。料金計算のルールを1つ変えるだけでも、HTTP や決済の知識が混ざったこのメソッドを触ることになります。

    10.2 After：高凝集 × 疎結合

    ○ After 
    // それぞれが1つの責任に集中 = 高凝集
class OrderValidator { validate(input) { /* ... */ } }
class OrderPriceCalculator { calc(items) { /* ... */ } }

interface PaymentGateway { charge(amount): Promise<void>; }
interface OrderRepository { save(order): Promise<void>; }
interface Mailer { send(to, body): Promise<void>; }

// UseCase は抽象に依存 = 疎結合
class PlaceOrderUseCase {
  constructor(
    private validator: OrderValidator,
    private calc: OrderPriceCalculator,
    private payment: PaymentGateway,
    private repo: OrderRepository,
    private mailer: Mailer
  ) {}
  async execute(input) {
    this.validator.validate(input);
    const total = this.calc.calc(input.items);
    await this.payment.charge(total);
    await this.repo.save(input);
    await this.mailer.send(input.email, '完了');
  }
}

class OrderController {
  constructor(private useCase: PlaceOrderUseCase) {}
  async handle(req, res) {
    const result = await this.useCase.execute(req.body);
    res.json(result);
  }
}

    各クラスは 1つのことに集中 し（高凝集）、抽象に依存 しています（疎結合）。この結果、次のような変化が起きます。

    • 料金計算のルールを変えるときは OrderPriceCalculator だけを触ればよい
    • Stripe を別の決済サービスに変えるときは、PaymentGateway の新しい実装を作って差し替えるだけで、PlaceOrderUseCase は変わらない
    • PlaceOrderUseCase は、偽物の PaymentGateway・OrderRepository・Mailer を渡せば、外部サービスなしでテストできる
    • OrderController は HTTP の受け渡しだけに集中する

    11.よくある誤解

    「疎結合とは、依存をゼロにすることだ」

    誤りです。 モジュールが協力して動く以上、依存は必ずあります。目指すのは依存をなくすことではなく、弱い種類の結合（データ結合や名前のコナーセンス）にし、変わりにくいもの（抽象）に向ける ことです。

    「インターフェースを挟めば、それで良い設計になる」

    不十分です。 8.3 の「疎結合だが低凝集」の例のように、インターフェースで結合を弱めても、1つのクラスに無関係な責任が集まっていれば読みにくいままです。凝集度と結合度は 両方 見る必要があります。また、誰からも差し替えられない抽象を大量に作ると、かえって複雑になります（→ 結合の指標 の「無駄ゾーン」）。

    「共通処理は1か所にまとめれば凝集度が上がる」

    まとめ方によります。 「再利用できそうなもの」を何でも utils や common に集めると、偶発的凝集や論理的凝集になります。さらに、多くのモジュールがそこに依存するので、変更の影響が広がる場所にもなります。まとめる基準は「似ているか」ではなく「同じ理由で変わるか」です。

    「クラスを細かく分けるほど高凝集になる」

    誤りです。 一緒に変わるものまでバラバラにすると、1つの変更のために多くのクラスを同時に直す必要が生じ、モジュール間の結合が増えます。分ける単位は「変更の単位」に合わせます。

    12.まとめ

    このページの要点

    • モジュール：より大きな構造を組み立てるための独立した部品。クラスや関数の集まりから、パッケージ・サービスまで含む
    • 凝集度：モジュール内のまとまり。高いほど良い。機能的凝集（最高）〜偶発的凝集（最低）の7段階
    • 結合度：モジュール間のつながり。弱いほど良い。データ結合（最弱）〜内容結合（最強）の6段階
    • 結合は 求心性結合（Ca）・遠心性結合（Ce） で数えられ、不安定度・抽象度・主系列からの距離に発展する
    • コナーセンス：結合の種類と強さを表す言葉。静的5種類・動的4種類。強いものは弱く、遠いものほど弱く、強いものは内側へ
    • 疎結合 × 高凝集 が理想。変更の影響が狭く、理解・再利用・テストがしやすい
    • 達成する手段は関心の分離・SOLID・依存性注入と抽象化・レイヤー分け。根本は 「凝集の単位 = 変更の単位」
