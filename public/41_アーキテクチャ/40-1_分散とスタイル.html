    40 システム・分散

    分散とスタイル（7スタイルの概観）

    1つのアプリの「中」をどう分けるかから一歩引いて、システム全体をいくつのデプロイ単位に分け、それらをどうつなぐかを考えるための入口のページです。「分散」とは何か、分散すると何が難しくなるのかを押さえたうえで、モノリスからマイクロサービスまでの7つのアーキテクチャスタイルを、特徴・向き不向き・★評価で比べます。

    もとにしたノート：40_システム・分散/01_分散とスタイル.md、00_解説_システム・分散.md

    1.このページで扱うこと

    20 アプリ内部構造（層化・三層・レイヤード や クリーンアーキテクチャ など）では、1つのアプリケーション（モノリス）の中で、層の分け方やドメインの置き方を学びました。40 システム・分散では視点を広げ、複数の部品・複数のサーバーにまたがるシステムをどう設計するかを扱います。

    問いは大きく2つです。

    • システム全体を、いくつのデプロイ単位・プロセス・サービスに分けるか
    • 分けた部品同士を、どうつなぐか

    このフォルダ（40 システム・分散）で扱うこと

    • システム全体のアーキテクチャスタイル（モノリス／モジュラーモノリス／マイクロカーネル／サービスベース／イベント駆動／スペースベース／マイクロサービス）
    • サービス間のつなぎ方（同期 API・メッセージ・イベント）→ 同期 API・メッセージ・イベント駆動
    • データの持ち方と整合性（データ所有権・分散トランザクション・SAGA・結果整合性）→ データ所有権・分散トランザクション・SAGA
    • システムの入口（API ゲートウェイ・BFF）と、部分障害への備え（グレースフルデグレーデーション）→ BFF・API ゲートウェイ・グレースフルデグレーデーション

    このフォルダの内容は概要レベルです。各トピックを深掘りする前に、「全体の地図」と「初心者がつまずきやすいポイント」を押さえることを目的にしています。

    2.「分散」とは何か

    分散とは、システムの部品が複数のプロセス・複数のマシン・複数のチームに分かれている状態のことです。たとえば、ユーザーからのリクエストを Web API が受け、注文サービスを呼び、さらに注文サービスが在庫サービスを呼ぶ、という構成は分散システムです。それぞれのサービスが別々の DB を持つこともあります。

    反対に、1台のサーバー・1つのプロセスで全部が動くモノリスは「分散していない」と言います。部品を別プロセス・別リポジトリ・別デプロイ単位に分け始めた瞬間から、設計の論点が一気に増えます。関数呼び出しだったものがネットワーク通信になり、1つだった DB が複数になり、1つのチームで済んでいた調整が複数チームにまたがるからです。

    3.なぜ分散を学ぶのか — 分けると生まれる新しい課題

    分散にすると、モノリスでは考えなくてよかった次のような課題が出てきます。

    課題ざっくりした問い詳しいページ
    通信同期で呼ぶか、メッセージで渡すか40-3
    データ誰が正（ソース・オブ・トゥルース）を持つか40-4
    整合性複数サービスをまたぐ処理を、どう「まとめて成功」させるか40-4
    障害一部が落ちたとき、全体を道連れにしないか40-5
    境界フロント向けの API（入口）をどこに置くか40-5

    分散は「楽になる魔法」ではない

    「マイクロサービスにすれば楽になる」わけではありません。分散は独立性やスケールを得る代わりに、通信・データ・障害の難しさを抱え込む選択です。トレードオフを理解したうえで、意図的に選ぶのがアーキテクチャの仕事です（トレードオフとアーキテクチャに効く原則）。

    4.スタイルの全体地図

    システム全体のアーキテクチャスタイルは、まずデプロイ単位が1つか、複数かで大きく2つに分かれます。さらに、どのスタイルを選んでも共通して考える「横に効く論点」（つなぎ方・データ・入口）があります。

    左（1つのデプロイ単位）から右（分散）へ進むほど、独立性・スケール・耐障害性が上がる代わりに、シンプルさ・コスト・一貫性の取りやすさを失っていきます。

    大切なのは、どれが一番よいかではなく、今のチーム・規模・品質特性に合うかで選ぶことです（トレードオフ）。

    5.1つのデプロイ単位のスタイル

    まずは、アプリ全体を1つの単位としてデプロイする3つのスタイルです。どれも「分散していない」ので、安くてシンプルですが、スケールと耐障害性には限界があります。

    5-1. モノリス（Monolith）

    アプリ全体を1つのデプロイ単位として作り、1つのプロセス・1つの DB で動かす形です。中身はたいてい レイヤードアーキテクチャ のように「技術の層」（プレゼンテーション・ビジネス・永続化など）で分かれています。

    良い点

    • 開発・テスト・デプロイが単純
    • 1つのトランザクションで整合性を保てる
    • 呼び出しはプロセス内（ローカル）なので速い

    悪い点

    • 規模が大きくなると、1か所の変更でも全体を再デプロイする必要がある
    • 一部だけをスケールできない
    • 1つのバグ（メモリリークなど）で全体が落ちることがある

    モノリスは「悪い形」ではなく、多くのプロダクトの正しい出発点です。詳しくは モノリス・分散モノリス・マイクロサービス で扱います。

    5-2. モジュラーモノリス（Modular Monolith）

    デプロイ単位は1つのまま、中身を「技術の層」ではなく「ドメイン（注文・在庫・会計…）」で区切ったモノリスです。Mark Richards と Neal Ford の『ソフトウェアアーキテクチャの基礎』第2版で、独立した章として追加されました。

    • モジュール間は公開インターフェース経由でしか呼ばない、他モジュールのテーブルを直接触らない、というルールを守ります。
    • 将来サービスに切り出すとき、境界がすでに引かれているので分割しやすくなります。
    • ルールを破ってもコンパイルは通り、動いてしまいます。そのため、依存関係のチェック（アーキテクチャテスト）で境界を自動的に守るのが実務的です。

    「いきなりマイクロサービス」を避けたいときの有力な選択肢です。モジュール分割の実務は（41 外のノート：43_モジュール設計）で扱います。

    5-3. マイクロカーネル（Microkernel／Plug-in）

    最小限のコアシステムに、機能をプラグインとして差し込む形です。Eclipse・VS Code・Jenkins・ブラウザ拡張などが代表例です。

    要素・観点内容
    コア基本の流れと、プラグインを登録・呼び出す仕組みだけを持つ
    プラグイン互いに独立した追加機能。コアが決めた契約（インターフェース）に従う
    向いている顧客ごとに機能を足し引きする製品、ルールが頻繁に変わる業務（保険の査定ルールなど）
    弱い点通常は1つのデプロイ単位なので、スケール・耐障害性はモノリスと同程度

    6.分散（複数のデプロイ単位）のスタイル

    ここからは、システムを複数のデプロイ単位に分けるスタイルです。スケールや耐障害性が上がる一方で、ネットワーク・データ・運用の難しさが加わります。

    6-1. サービスベース（Service-Based）

    4〜12個程度の粗い「ドメインサービス」に分けて別々にデプロイし、DB は共有することが多い、分散の中では最も実務的な形です。

    • マイクロサービスほど細かく切らないので、サービス間通信やデータ同期の苦労が少なくて済みます。
    • DB を共有しているため、1サービス内の処理なら通常の ACID トランザクションが使えます。
    • 「モノリスから分けたいが、マイクロサービスは重すぎる」ときの落とし所になります。

    注意：分散モノリスへの入り口

    DB を共有したまま、サービス同士が同期で呼び合い始めると分散モノリスになりやすくなります（モノリス・分散モノリス・マイクロサービス）。

    6-2. イベント駆動（Event-Driven Architecture, EDA）

    「〜が起きた」というイベントを発行し、関心のある部品が非同期に反応する形です。発行側は誰が受け取るかを知らず、応答も待ちません（ファイア＆フォーゲット）。詳しくは 同期 API・メッセージ・イベント駆動 で扱います。

    イベントの流し方には2つの型（トポロジー）があります。

    型仕組み向いている弱い点
    ブローカー型中央の指揮役がいない。各プロセッサーがイベントを受けて処理し、結果を派生イベントとして発行する（連鎖反応）拡張性・応答性を重視、処理の追加が多い全体の流れが見えにくい。エラー処理・再実行が難しい
    メディエーター型メディエーター（指揮役）がワークフローを持ち、各プロセッサーに順番に指示する手順が決まった業務フロー、エラー時の制御が必要メディエーターが結合点・ボトルネックになりやすい

    これは SAGA のコレオグラフィ（ブローカー型に近い）とオーケストレーション（メディエーター型に近い）の関係と同じ構図です（40-4）。

    良い点

    • 高いスケール・性能・耐障害性
    • 新しい処理を、既存コードを変えずに「購読者を足す」だけで追加できる

    悪い点

    • 流れが追いにくく、テストしにくい
    • イベントの取りこぼし・重複・順序への対策（永続化キュー、確認応答、冪等性）が必要

    6-3. スペースベース（Space-Based）

    DB をリクエスト処理の経路から外し、処理ユニットごとにメモリ内のレプリケートされたデータ（データグリッド）で処理する形です。DB への書き込みは後から非同期で行います。名前は「タプルスペース」という分散共有メモリの考え方に由来します。

    • 向いている：チケット販売・オークション・セールなど、アクセスが一瞬で数十倍に跳ねるシステム
    • 良い点：DB がボトルネックにならないため、弾力性・スケール・性能が非常に高い
    • 悪い点：データの衝突・同期の設計が難しく、テストも困難。構築・運用コストが高い

    まだ個別のノートはありません。まずは「極端な負荷に耐えるための特殊なスタイル」と覚えておけば十分です。

    6-4. マイクロサービス（Microservices）

    1つの業務の境界（境界づけられたコンテキスト）ごとに小さなサービスを作り、サービスごとに DB を持ち、独立してデプロイする形です。

    良い点

    チームごとに独立して開発・デプロイ・スケールできる。障害が1サービスに閉じやすい。技術選択も独立。

    悪い点

    ネットワーク越しの呼び出しで遅くなる。分散トランザクション・観測性・運用の難易度が上がる。コストが最も高い。

    前提条件

    自動デプロイ（CI/CD）・監視・トレースが整っていること。チームが複数あること。

    本質は「数」ではなく「独立」

    マイクロサービスの本質は、サービスの数よりもデータと境界の独立にあります。DB を共有したまま細かく分けても、マイクロサービスの利点は得られません（40-2）。

    読み方のポイント

    • 1つのデプロイ単位のスタイル（レイヤード・モジュラーモノリス・マイクロカーネル）は、安くてシンプルですが、スケールと耐障害性が★1です。
    • 分散のスタイルは、スケール・耐障害性が上がる代わりに、シンプルさとコストを失います。
    • サービスベースは分散の中で最もバランスがよく、最初の分割先として選ばれやすいスタイルです。
    • ★の合計が多いスタイルが「最良」ではありません。自分のシステムで重要な特性（上位3つ程度）に★が付いているかで選びます（品質特性と非機能要件）。

    8.横に効く論点の早見

    スタイルを決めたあとは、どのスタイルでも共通して出てくる論点を順に決めていきます。ここでは概要だけを示し、詳しくは各ページに譲ります。

    8-1. 同期と非同期（つなぎ方）

    部品を分けたら、次はどうつなぐかを決めます（40-3）。

    つなぎ方呼んだ側は例注意点
    同期 API（REST・gRPC）返事を待つ在庫の問い合わせ、ログイン相手が遅い・落ちると自分も止まる（連鎖障害）
    メッセージ（キュー）送ったら待たない。宛先は決まっているメール送信、画像変換到達保証・再送・重複処理（冪等性）が必要
    イベント（Pub/Sub）「起きたこと」を知らせるだけ。宛先を知らない注文確定 → 在庫・通知・分析がそれぞれ反応全体の流れが見えにくい
    • コマンドは「〜してほしい」（宛先は1つ、断られることもある）、イベントは「〜が起きた」（過去形、受け手は複数・任意）です。
    • 実務では「ユーザーが結果をすぐ必要とする部分は同期、後でよい部分は非同期」というハイブリッドが一般的です。

    8-2. データ所有権・SAGA・結果整合性

    分散で一番難しいのがデータです（40-4）。

    • データ所有権：各データには「持ち主」のサービスを1つだけ決め、他のサービスは API やイベント経由でしか触らないようにします。他サービスの DB を直接読むのは典型的なアンチパターンです。
    • 分散トランザクション：複数の DB をまたいで「全部成功か全部失敗か」を保証する方法（2PC など）は、遅く壊れやすいため、一般には避けます。
    • 結果整合性（Eventual Consistency）：「一瞬ずれることはあるが、最終的には揃う」ことを受け入れる考え方です。在庫表示が数秒遅れても業務上問題ないか、を業務側と決めます。
    • SAGA：長い処理を各サービスのローカルトランザクションの連鎖に分け、途中で失敗したら補償トランザクション（取り消し処理）で戻す方法です。指揮役が順番に指示するオーケストレーション（追いやすい）と、各サービスがイベントを見て次を起こすコレオグラフィ（疎結合だが追いにくい）があります。

    8-3. API ゲートウェイ・BFF・グレースフルデグレーデーション

    サービスが増えると、クライアントから見た入口を整える必要が出てきます（40-5）。

    • API ゲートウェイ：全クライアント共通の単一の入口。ルーティング・認証の一次チェック・レート制限・ログなど、横断的な処理をまとめます（→ 横断的関心事と認証・認可の境界）。
    • BFF（Backend for Frontend）：Web 用・モバイル用など、画面の種類ごとの専用バックエンド。複数サービスの結果を画面に合わせて集約・整形します。フロントエンド側の構成は BFF・マイクロフロントエンド とつながります。
    • グレースフルデグレーデーション：一部のサービスが落ちても、機能を縮小して動き続ける設計です。例：おすすめ欄が出なくても、商品ページと購入は動く。タイムアウト・サーキットブレーカー・フォールバックで実現します。

    2. モノリス・分散モノリス・マイクロサービス — スタイルの選び方。3つの形の比較と、分けるべきサイン
    3. 同期 API・メッセージ・イベント駆動 — サービス間のつなぎ方の3分類と選び方。イベント駆動アーキテクチャの読書メモ（イベントブローカー・データロス防止・エラー処理）も含む
    4. データ所有権・分散トランザクション・SAGA — データを分けたときの現実。データの持ち主、2PC が難しい理由、SAGA
    5. BFF・API ゲートウェイ・グレースフルデグレーデーション — 入口の整理と部分障害への備え
    6. サーバーレス — サーバー管理をクラウドに任せる実行モデルと、その向き不向き

    2 → 3 → 4 → 5 の順がおすすめです。すでにマイクロサービスを触っている場合は、4（データと整合性）から入っても構いません。

    まだ個別ノートのないスタイル

    モジュラーモノリス・マイクロカーネル・サービスベース・スペースベースは、まだ個別のノートがありません。書くときは MOC のスタイルノート共通テンプレートを使う予定です。このページの §5・§6 が現時点での説明です。

    10.初心者が覚えておきたい3つのこと

    1. 最初はモノリスでよいことが多い — 分ける理由がはっきりするまで、無理に分割しない（40-2）。
    2. 分散トランザクションは難しい — 「全部同時に成功」を厳密に保つのはコストが高い。現実的な落とし所（SAGA・結果整合性）を知る（40-4）。
    3. 障害は前提 — 一部が死んでも、可能な範囲でサービスを続ける設計を考える（40-5）。

    11.よくある誤解

    誤解実際
    マイクロサービスにすれば楽になる独立性と引き換えに、通信・データ・障害・運用の難しさが増える。トレードオフを理解して意図的に選ぶもの
    モノリスは悪い形・レガシー多くのプロダクトにとって正しい出発点。モジュラーモノリスとして中を整理しておけば、後で分けやすい
    ★の合計が多いスタイルが最良自分のシステムで重要な特性（上位3つ程度）に★が付いているかで選ぶ
    サービスを細かく分ければマイクロサービス本質はデータと境界の独立。DB を共有したまま分けると分散モノリスになりやすい
    スタイルは1つだけ選ぶものマイクロサービス＋イベント駆動のように組み合わせることも多い。図の点線（組み合わせ）を参照

    12.まとめ

    このページのポイント

    • 分散とは、部品が複数のプロセス・マシン・チームに分かれた状態。分け始めると、通信・データ・整合性・障害・境界という新しい課題が生まれる。
    • スタイルは1つのデプロイ単位（モノリス・モジュラーモノリス・マイクロカーネル）と分散（サービスベース・イベント駆動・スペースベース・マイクロサービス）に分かれる。
    • 分散側へ進むほど独立性・スケール・耐障害性が上がり、シンプルさ・コスト・一貫性の取りやすさを失う。
    • 迷ったら、モジュラーモノリスで境界を引き、必要になったらサービスベースへ、という段階的な進め方が現実的。
    • 選ぶ基準は「流行」ではなく、チーム・規模・重要な品質特性。
