    70 進化と組織

    進化的アーキテクチャと適応度関数

    アーキテクチャを「一度きりの設計」ではなく、守るべき性質を確かめながら少しずつ変えていくための考え方と道具を解説します。適応度関数の定義と分類、ArchUnit・dependency-cruiser・負荷テスト・監視・カオスエンジニアリングによる実装例、導入の手順、移行パターンが分かります。

    もとにしたノート：70_進化と組織/04進化型アーキテクチャとリバースコンウェイの法則.md（§1）、70_進化と組織/00_解説_進化と組織.md（§2・§4）、00_全体像/00_解説_アーキテクチャ体系.md（§7-2・§9-4）。適応度関数は個別ノートがないため公開資料で補足

    1.このページで扱うこと

    「アーキテクチャはリリース前に完成させるもの」というイメージは、現実とずれています。システムは動き続けながら形を変えていくのが普通です。問題は、変わっていく中で、守りたかった性質（依存の向き・性能・セキュリティなど）が少しずつ崩れていくことです。

    このページでは、変化を前提にしながら崩れないようにするための考え方と道具を扱います。

    • 進化的アーキテクチャ：変化を前提に、ガイドしながら形を変える考え方
    • 適応度関数（フィットネス関数）：守りたい性質を客観的に、できれば自動でチェックする仕組み。その分類と実装例（ArchUnit・dependency-cruiser・負荷テスト・監視・カオスエンジニアリング）
    • 導入の手順：どこから始め、どう CI や監視に組み込むか
    • 移行パターン：ストラングラーフィグ・抽象化によるブランチ・並行稼働・フィーチャーフラグ
    • AI 時代のアーキテクチャの逸脱（ドリフト）と、機械が検査できるルールの価値

    適応度関数にはまだ個別ノートがないため、フォルダの解説ノートと全体解説をもとに、書籍『進化的アーキテクチャ』に関する公開資料などで詳しく補っています。組織の話（コンウェイの法則）は コンウェイの法則と Team Topologies で扱います。

    2.進化的アーキテクチャとは

    進化的アーキテクチャ（Evolutionary Architecture）は、Neal Ford・Rebecca Parsons・Patrick Kua の書籍『進化的アーキテクチャ』（Building Evolutionary Architectures）で提唱された考え方です。書籍では次のように定義されています。

    複数の観点にわたって、ガイドされた漸進的な変更を支えるアーキテクチャ

    ひとことで言えば、アーキテクチャを「一度きりの設計」ではなく、継続的に変えていけるようにする考え方です。なお同書の第2版には「Automated Software Governance（自動化されたソフトウェアガバナンス）」という副題が付いており、「ルールを自動で守らせる」ことが中心テーマになっています。

    2つのキーワード

    キーワード意味
    漸進的（incremental）一気に作り直さず、小さな変更を積み重ねる。そのために、デプロイやテストが自動化されている
    ガイドされた（guided）好き勝手に変わるのではなく、守るべき性質を適応度関数でチェックしながら変わる

    「複数の観点にわたって」とは、コードの構造だけでなく、データ・セキュリティ・性能・運用など、アーキテクチャに関わる複数の側面すべてで変化を支える、という意味です。

    従来型のイメージと進化型のイメージ

    「最初から完璧なマイクロサービス」を目指すより、今必要な形から始め、データと経験に基づいて分けていく方が現実的だ、という立場です。これは「アーキテクチャ上の決定は二択ではなくスペクトラム上にある」という第3法則（トレードオフと原則）とも通じます。

    変化を支える前提条件

    漸進的に変えるためには、変更を安全に小さく出せる仕組みが必要です。

    • デプロイの自動化：小さな変更を何度もリリースできる（CI/CD）
    • テストの自動化：変更で既存の振る舞いが壊れていないことをすぐ確かめられる
    • 適切な結合の低さ：変更が一部に閉じる（モジュール性・疎結合と高凝集、アーキテクチャ量子）
    • 守るべき性質の明文化：何が崩れたら困るのかが測れる形で決まっている → 適応度関数

    3.適応度関数とは

    適応度関数（Fitness Function）は、アーキテクチャが守るべき性質を、客観的にチェックする仕組みです。『進化的アーキテクチャ』では次のように定義されています。

    アーキテクチャ適応度関数とは、あるアーキテクチャ特性（1つまたは複数）の完全性を、客観的に評価する仕組みである

    名前は進化生物学や遺伝的アルゴリズムの「適応度関数」から借りています。遺伝的アルゴリズムでは、候補となる解が目的にどれだけ近いかを適応度関数で評価し、良いものを残していきます。同じように、アーキテクチャが変化していく中で「目的とする性質にどれだけ近いか」を測るのが、アーキテクチャの適応度関数です。

    ノートによって「適応度関数」「フィットネス関数」と表記が分かれていますが、同じものです。

    「客観的」であることが大切

    適応度関数は、人によって判断が変わらないものでなければなりません。「コードが読みやすいこと」のような主観的な基準ではなく、「循環依存が0件」「p95 レイテンシが 300ms 以内」「許容範囲20件のうち違反は17件」のように、数値や合否で判定できる形にします。

    適応度関数にならない

    • 速いこと
    • 保守しやすいこと
    • レイヤーをきれいに保つこと

    適応度関数になる

    • ピーク時の p95 レイテンシが 300ms 以内
    • ドメイン層からインフラ層への依存が0件
    • モジュール間の循環依存が0件

    この「測れる形にする」作業は、品質特性を品質特性シナリオに落とす作業（品質特性シナリオと計測）そのものです。シナリオで測れる形にした品質特性が、適応度関数でそのまま自動チェックの対象になります。

    適応度関数の例

    例何を守るか
    ビルド時に層の依存方向を検査するドメイン層が UI やインフラに依存しない
    レスポンスタイムの閾値でアラートを出す性能要件
    循環依存を検出するモジュール境界の健全性
    セキュリティスキャンを実行する既知の脆弱性がない
    サービス間の循環依存を静的解析で検出するサービス境界の健全性

    ADR は「決定を残す」、適応度関数は「決定を守らせる」

    ADR（意思決定の進め方と ADR）に「ドメイン層はインフラ層に依存しない」と書いても、それを守るかどうかは人の記憶と注意力次第です。適応度関数にすれば、違反したコードはビルドが失敗するので、ルールが人の記憶ではなく仕組みで守られます。

    初心者向けの理解

    適応度関数とは「設計ルールを、人の記憶だけに頼らない」ための仕組みです。CI に組み込むほど強力ですが、いきなりツールを入れなくても、レビューのチェックリストから始めるだけでも近い効果があります（アーキテクチャのレビュー観点）。

    4.適応度関数の分類

    『進化的アーキテクチャ』では、適応度関数をいくつかの観点で分類しています。分類は排他的ではなく、1つの適応度関数を複数の観点で特徴づけます（例：「原子的で、トリガー型で、静的で、自動」）。

    原子的と全体的（Atomic / Holistic）

    分類意味例
    原子的（アトミック）単一の文脈で、1つの性質だけを見るこのモジュールに循環依存がないか。単体テストのように実行できる
    全体的（ホリスティック）共有された文脈で、複数の性質の組み合わせを見る暗号化を入れても性能要件を満たすか。キャッシュがセキュリティと拡張性に与える影響

    品質特性は互いに影響し合う（セキュリティを上げると性能が落ちる、など）ので、個別にはすべて合格でも、組み合わせると問題が起きることがあります。全体的な適応度関数はこの「組み合わせたときの問題」を見つけるためのものです。

    トリガー型と継続型（Triggered / Continual）

    分類意味例
    トリガー型特定のきっかけ（コミット、ビルド、デプロイ、手動実行）で実行されるCI での依存ルール検査、デプロイ前の負荷テスト
    継続型本番などで常に評価し続けるレスポンスタイムの監視とアラート、本番での障害注入

    トリガー型は「入ってくる変更」を止めるのに向き、継続型は「本番の実際の負荷や環境」でしか分からない問題を見つけるのに向いています。

    静的と動的（Static / Dynamic）

    分類意味例
    静的結果が固定の基準で決まる（合格か不合格か、決まった閾値を超えたか）循環依存が0件、テストカバレッジが一定以上
    動的基準が状況（文脈）によって変わる利用者数が多いときは応答時間の許容範囲を少し緩める、など規模に応じて閾値が変わるもの

    なお、ノートによっては「静的＝コードを解析するもの、動的＝実行して測るもの」という意味で使われることもあります。書籍での区別は「判定基準が固定か、状況で変わるか」です。

    自動と手動（Automated / Manual）

    適応度関数はできる限り自動化するのが原則です。ただし、法務の確認やセキュリティ専門家によるレビューなど、どうしても人が判断しなければならないものもあります。その場合も、「いつ・誰が・何を基準に確認するか」を決めておけば、手動の適応度関数として扱えます。

    そのほかの観点

    分類意味例
    時間的（Temporal）一定の時間や条件で発火する依存ライブラリのバージョンが古くなったら警告する、ライセンスの監視、ある期限を過ぎたらビルドを失敗させて「見直し」を強制する（break-on-upgrade）
    意図的と創発的（Intentional / Emergent）最初から計画して作るものと、運用しているうちに必要だと分かって追加するもの創発的なものが多いのは、事前に守るべき性質を考えきれていなかったサインでもある
    ドメイン固有（Domain-specific）業界や業務に特有の要件を守る金融での監査ログの必須化、個人情報（PII）がログに出ていないかの検査、高セキュリティ領域専用の負荷・耐性試験

    5.実装例とツール

    守りたい性質ツールの例分類の目安
    レイヤーの依存方向（Java）ArchUnit：「domain パッケージは infrastructure に依存しない」をテストとして書ける原子的・トリガー型・静的
    モジュール間の依存方向（JavaScript / TypeScript）dependency-cruiser、eslint-plugin-boundaries原子的・トリガー型・静的
    依存方向（.NET）NetArchTest原子的・トリガー型・静的
    性能負荷テストの閾値（k6 など）、本番の SLO アラートトリガー型（負荷テスト）／継続型（監視）
    セキュリティ依存ライブラリの脆弱性スキャン（CI に組み込む）、シークレットの混入検査トリガー型
    可用性・回復性カオスエンジニアリング（障害を意図的に注入する）全体的・継続型

    ArchUnit（Java）：依存ルールを単体テストとして書く

    ArchUnit は、Java のコードのパッケージやクラスの依存関係を解析し、アーキテクチャのルールを JUnit のテストとして書けるライブラリです。ルールに違反するとテストが失敗し、CI のビルドが止まります。

    ArchitectureTest.java（イメージ） 
    @AnalyzeClasses(packages = "com.example.shop")
class ArchitectureTest {

  // ドメイン層はインフラ層に依存しない（依存性のルール）
  @ArchTest
  static final ArchRule domain_must_not_depend_on_infra =
      noClasses().that().resideInAPackage("..domain..")
          .should().dependOnClassesThat().resideInAPackage("..infrastructure..");

  // レイヤーの呼び出し方向を決める
  @ArchTest
  static final ArchRule layers = layeredArchitecture().consideringAllDependencies()
      .layer("Controller").definedBy("..controller..")
      .layer("Service").definedBy("..service..")
      .layer("Persistence").definedBy("..persistence..")
      .whereLayer("Controller").mayNotBeAccessedByAnyLayer()
      .whereLayer("Service").mayOnlyBeAccessedByLayers("Controller")
      .whereLayer("Persistence").mayOnlyBeAccessedByLayers("Service");

  // 機能ごとのパッケージの間に循環依存がない
  @ArchTest
  static final ArchRule no_cycles =
      slices().matching("com.example.shop.(*)..").should().beFreeOfCycles();
}

    1つ目のルールは クリーンアーキテクチャの依存性のルール、2つ目は 閉じた層 の考え方をそのままコードにしたものです。ヘキサゴナル・オニオンのような構造にも、同じようにルールを書けます。

    dependency-cruiser（JavaScript / TypeScript）

    dependency-cruiser は、JavaScript / TypeScript の import の関係を解析し、禁止したい依存をルールとして書けるツールです。たとえば次のようなルールを CI で検査できます。

    .dependency-cruiser.js（イメージ） 
    module.exports = {
  forbidden: [
    {
      name: "domain-must-not-depend-on-infra",
      severity: "error",
      from: { path: "^src/domain" },
      to: { path: "^src/infrastructure" },
    },
    { name: "no-circular", severity: "error", from: {}, to: { circular: true } },
  ],
};

    これで「ドメイン層はインフラ層に依存しない」という クリーンアーキテクチャ のルールが、人の記憶ではなく CI で守られるようになります。ESLint を使っているなら、eslint-plugin-boundaries で「どの要素がどの要素を import してよいか」を宣言する方法もあります。

    負荷テストの閾値（k6）：性能を合否で判定する

    k6 では thresholds に性能の基準を書くと、基準を満たさなかったときにコマンドが失敗として終了します。これを CI やデプロイ前の段階に入れれば、性能要件がトリガー型の適応度関数になります。

    load-test.js（イメージ） 
    import http from "k6/http";

export const options = {
  vus: 50,
  duration: "1m",
  thresholds: {
    http_req_duration: ["p(95)<300"], // 95% のリクエストが 300ms 未満
    http_req_failed: ["rate<0.01"],   // 失敗率 1% 未満
  },
};

export default function () {
  http.get("https://staging.example.com/api/products");
}

    認証や暗号化を有効にした本番に近い構成で実行すれば、「セキュリティと性能の組み合わせ」を見る全体的な適応度関数にもなります。

    本番の監視：継続型の適応度関数

    本番で常に「p95 レイテンシ」「エラー率」「可用性」を測り、SLO（サービスレベル目標）を下回りそうになったらアラートを出す仕組みは、継続型の適応度関数です。テスト環境では再現できない、実際の負荷やデータの偏りによる劣化を見つけられます。観測の仕組みそのものは 観測性（ログ・メトリクス・トレース） を参照してください。

    カオスエンジニアリング：全体的・継続型の代表例

    Netflix の Chaos Monkey に代表されるカオスエンジニアリングは、本番環境で意図的にサーバーを止めるなどの障害を起こし、システム全体として可用性と回復性が保たれるかを確かめる手法です。Netflix はこれを拡張したツール群を「Simian Army」と呼び、セキュリティ設定の不備や、規約に沿っていないインスタンスを見つけるものなども含めていました。『進化的アーキテクチャ』では、これらが全体的で継続型の適応度関数の例として紹介されています。

    カオスは最後に

    本番での障害注入は、監視・自動復旧・切り戻しの仕組みが整っていることが前提です。最初に取り組むべきものではなく、構造の適応度関数や監視が整ったあとの段階で検討します。

    6.導入の手順

    適応度関数は、一度に全部そろえる必要はありません。公開されている解説でも、まずは構造の適応度関数（依存ルールの検査）から始め、実行時やデータに関するものは後から足すことが勧められています。

    1. 守りたい性質を選ぶ。関係者（事業・運用・セキュリティ・開発）の意見を集め、アーキテクチャにとって重要な特性を3つ程度に絞ります（品質特性と非機能要件）。ADR や arc42 の品質目標に書かれているものが候補です。
    2. 測れる形にする。「速い」ではなく「ピーク時 p95 300ms 以内」のように、合否や数値で判定できる形に落とします（品質特性シナリオ）。
    3. 分類と道具を選ぶ。コードの構造なら原子的・トリガー型（ArchUnit など）、性能なら負荷テストと監視、というように、性質に合った実行タイミングとツールを決めます。
    4. 現状を測ってから厳しくする。既存のコードに違反が大量にあると、いきなりビルドを止めることはできません。まず現状の違反を記録し、新しい違反だけを止めるところから始めます。ArchUnit には既存の違反を記録して新しい違反だけを検出する仕組み（FreezingArchRule）があります。
    5. パイプラインと監視に組み込む。トリガー型は CI に、継続型は監視とアラートに組み込み、違反したら誰かが気づく状態にします。
    6. 定期的に見直す。事業や品質目標が変われば、守るべき性質も変わります。適応度関数を ADR と結び付け、決定を変えたら適応度関数も更新します。

    ツールの前にチェックリスト

    CI に組み込む余裕がないうちは、レビューのチェックリスト に「ドメイン層からインフラ層への import がないか」などを入れるだけでも始められます。これは「手動の適応度関数」です。慣れてきたら、頻繁に指摘される項目から順に自動化していきます。

    7.移行パターン — 少しずつ形を変える

    古い構造から新しい構造へ移るとき、一気に作り直す（ビッグバン書き換え）のはほとんどの場合失敗しやすいとされます。代わりに、動かしながら少しずつ置き換える移行パターンを使います（このテーマの専用ノートはまだありません）。

    パターンやり方向いている場面
    ストラングラーフィグ古いシステムの前に入口（ルーターやプロキシ）を置き、機能ごとに新システムへ振り分けていく。最後に古い方を止めるモノリスからサービスへの段階的な移行
    抽象化によるブランチ（Branch by Abstraction）置き換えたい部品の前にインターフェースを作り、裏で新旧の実装を切り替える1つのコードベース内での大きな部品の入れ替え（インターフェースと抽象化）
    並行稼働（Parallel Run）新旧両方で同じ処理をし、結果を比べる。ユーザーには旧の結果を返す計算ロジックなど、正しさの確認が重要な部分
    フィーチャーフラグ新機能をフラグで一部の利用者にだけ公開する段階的な公開と、問題時の即時切り戻し（設定・シークレット・フィーチャーフラグ）

    ストラングラーフィグ（絞め殺しのイチジク）

    名前は、宿主の木に絡みついて育ち、最後には宿主に取って代わるイチジクの木から来ています。新しい部分を少しずつ増やし、古い部分への依存を減らしていきます。

    技術的負債の「計画的な返済」（技術的負債と意図的な暫定案）とも直接つながる手法です。

    移行と適応度関数を組み合わせる

    どのパターンでも、「何を・どの順で・どうなったら完了か」を ADR に残し、適応度関数で後戻りを防ぐのが基本です。たとえばストラングラーフィグで注文機能を移したら、「新しいコードから旧システムのモジュールを呼んではいけない」というルールを適応度関数にしておきます。こうすると、移行が進むほど旧システムへの依存は減る一方になり、逆戻りしません。

    レガシーシステムを置き換える場面では、ストラングラーフィグ＋適応度関数の組み合わせを優先して検討するとよいでしょう。

    8.AI 時代のアーキテクチャの逸脱（ドリフト）

    コーディングエージェントが大量にコードを書く時代には、アーキテクチャの逸脱（ドリフト）が起きやすくなります。エージェントは目の前の課題を解くことに集中するため、レイヤーをまたいだ近道の import や、既存の共通部品を使わない重複実装を、悪気なく持ち込むことがあるからです。

    対策として、次のような取り組みが出てきています。

    • 適応度関数・アーキテクチャテストを CI に入れて、逸脱を自動で検出する
    • ADR をエージェントにも読ませる（なぜその構造なのかを伝える）
    • 参照実装を MCP サーバー経由でエージェントに見せ、お手本に沿ったコードを書かせる

    「人が読んで守るルール」から「機械が検査できるルール」へ移す価値は、AI によって一段と高まっています。適応度関数は、人にもエージェントにも同じように効くガードレールです。

    9.よくある誤解

    誤解実際
    進化的アーキテクチャ＝最初は何も設計しなくてよい変えにくい部分は早めに決める。そのうえで、変化を「ガイド」するための適応度関数と自動化を用意する
    適応度関数は特別なツールのこと「守りたい性質を客観的に評価する仕組み」全般を指す。単体テスト・負荷テスト・監視・レビューのチェックリストも適応度関数になり得る
    適応度関数は CI でしか動かないトリガー型（CI）だけでなく、本番の監視やカオスエンジニアリングのような継続型もある
    品質特性を全部チェックすべき重要な特性を3つ程度に絞り、構造の検査から小さく始める
    既存の違反がある間は導入できない現状を記録し、新しい違反だけを止める形で始められる
    負債がたまったら一気に作り直すのが早いビッグバン書き換えは失敗しやすい。移行パターンで少しずつ置き換え、適応度関数で後戻りを防ぐ

    10.まとめ

    覚えること内容
    進化的アーキテクチャ変化を前提に、測定とガイドで形を変えていく。キーワードは「漸進的」と「ガイドされた」
    適応度関数守りたい性質を客観的に評価する仕組み。ADR が決定を残し、適応度関数が決定を守らせる
    分類原子的／全体的、トリガー型／継続型、静的／動的、自動／手動、時間的、意図的／創発的、ドメイン固有
    実装例ArchUnit・dependency-cruiser（依存ルール）、k6（性能）、監視と SLO（継続型）、カオスエンジニアリング（全体的・継続型）
    導入重要な特性を選び、測れる形にし、構造の検査から始め、新しい違反だけを止め、定期的に見直す
    移行パターンストラングラーフィグ・抽象化によるブランチ・並行稼働・フィーチャーフラグ。ADR に残し、適応度関数で後戻りを防ぐ
