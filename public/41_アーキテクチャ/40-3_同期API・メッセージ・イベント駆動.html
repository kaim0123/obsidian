    40 システム・分散

    同期 API・メッセージ・イベント駆動

    サービスやモジュールを分けると、「どうやって連携するか」が設計の中心になります。このページでは、同期 API・メッセージ（キュー）・イベント駆動の3つのつなぎ方の特徴と選び方を整理し、後半ではイベント駆動アーキテクチャの仕組み（ブローカー型とメディエーター型、データロス防止、エラー処理、データトポロジー）を詳しく見ます。

    もとにしたノート：40_システム・分散/03同期APIとメッセージとイベント駆動の概観.md、イベント駆動アーキテクチャ.md（＋ 00_解説_システム・分散.md）

    2.なぜ「つなぎ方」が重要か

    同じ「在庫を減らす」処理でも、

    • 呼び出し側が結果を待つのか
    • 後で別のプロセスが処理するのか

    によって、性能・障害時の振る舞い・データの整合性が大きく変わります。3つのつなぎ方を並べると、次のようになります。

    3.同期 API（リクエスト／レスポンス）

    3-1. どんなものか

    クライアントが HTTP や gRPC などで相手を直接呼び出し、応答が返ってくるのを待ってから次に進む方式です。たとえば注文サービスが在庫 API に GET /stock/123（在庫ある？）と問い合わせ、在庫 API が在庫 DB を見て 200 OK, quantity: 5 を返し、呼び出し元はこの結果を使って処理を続けます。

    ブラウザ / 注文サービス
   │  GET /stock/123   （在庫ある？）
   ▼
在庫 API ──→ 在庫 DB
   │  200 OK, quantity: 5
   ▼
呼び出し元はこの結果を使って続行

    REST API、GraphQL、内部の gRPC 呼び出しは、多くがこの同期モデルです。

    3-2. メリット・デメリット

    メリット

    • わかりやすい — 「呼んだら結果が返る」が直感的
    • すぐ結果が必要な処理に向く（在庫をチェックしてから注文確定、など）
    • エラー処理がその場でできる（在庫なしなら 409 を返す）

    デメリット

    • 結合が強くなりやすい — 在庫 API が遅い・落ちていると、注文も止まる（連鎖障害）
    • チェーンが長いと遅い — A→B→C→D と直列に呼ぶと遅延が足し算される
    • 呼び出し先の負荷がピークと連動する

    3-3. 向いている例

    • ユーザーが画面で結果を待っている操作（ログイン、在庫の問い合わせ）
    • 読み取りが中心で、少しの遅延は許容できる
    • サービス数が少なく、運用を単純に保ちたいとき

    4.メッセージ（非同期）

    4-1. どんなものか

    送信側はメッセージキュー／メッセージブローカーにメッセージを投げるだけで、すぐに戻ります。受信側（コンシューマー）が後から取り出して処理します。たとえば注文サービスが「注文確定」メッセージをキューに入れ、在庫サービスがそれを非同期に取り出して在庫を減らします。

    代表的な製品：RabbitMQ、Amazon SQS、Apache Kafka、Google Cloud Pub/Sub など。

    4-2. メリット・デメリット

    メリット

    • 時間的な切り離し — 受信側がオンラインでなくても（一定期間なら）投げられる
    • 負荷の平準化 — ピーク時はキューに溜め、後で処理できる
    • 障害の緩和 — 一時的な障害時にリトライしやすい（設計次第）

    デメリット

    • 結果がすぐわからない — 「在庫が減ったか」は後で確認が必要
    • 運用が増える — キューの監視、デッドレターキュー、順序・重複の扱い
    • デバッグが難しい — 処理がいつ・どこで行われたか追いにくい（観測性）

    4-3. 向いている例

    • メール送信、画像変換、レポート生成、検索インデックス更新
    • ユーザーが待たなくてよい後処理
    • ピークが激しく、吸収バッファが欲しいとき

    5.イベント駆動（Event-Driven）

    5-1. どんなものか

    ある処理が起きたときに、「何が起きたか」という事実（イベント）を発行し、興味のある複数の購読者がそれぞれ反応するスタイルです。注文サービスが OrderPlaced（注文された）を発行すると、在庫サービスは在庫を減らし、会計サービスは売上を計上し、通知サービスはメールを送ります。

    メッセージキューを使うことも多いですが、イベント駆動は特に次の点を強調します。

    • 過去形の事実を伝える（OrderPlaced）
    • 発行者は購読者を知らない（疎結合）。応答も待たない（ファイア＆フォーゲット）
    • 購読者が複数に増えやすい

    5-2. コマンドとイベントの違い

    種類意味例宛先
    コマンド「〇〇してほしい」という依頼。断られることもあるReserveStock（在庫を確保して）1つの宛先を想定しがち
    イベント「〇〇が起きた」という事実。過去形StockReserved（在庫が確保された）0人以上の購読者を想定

    コマンドとイベントを混同すると設計がぶれやすいので、名前（命令形か過去形か）で区別するのがおすすめです。

    5-3. メリット・デメリット

    メリット

    • 拡張しやすい — 新機能は「イベントを購読するサービスを足す」だけで済むこともある
    • ドメインの事実をそのまま伝えられる（（41 外のノート：42_ソフトウェア設計『02_集約とエンティティと値オブジェクトとドメインイベント』）と相性がよい）
    • 高いスケール・性能・耐障害性を得やすい

    デメリット

    • 全体の流れが見えにくい — 誰が何に反応するか、図やドキュメントがないと迷子になる
    • 結果整合性（最終的整合性）になりやすい — すぐには全部そろわない（40-4）
    • 順序・重複 — 同じイベントが2回来たらどうするか、を決める必要がある

    6.3つの比較

    観点同期 APIメッセージ（非同期）イベント駆動
    応答すぐ返る後で処理後で複数が反応
    呼んだ側は返事を待つ送ったら待たない（宛先は決まっている）「起きたこと」を知らせるだけ（宛先を知らない）
    結合度やや強い弱め弱め
    ユーザー待ち向く不向き（本体処理）本体は別途
    障害時相手次第で失敗キューに残せる同上＋購読者が増える
    運用比較的単純キュー監視が必要同上＋可視化が重要
    例在庫の問い合わせ、ログインメール送信、画像変換注文確定 → 在庫・通知・分析がそれぞれ反応

    7.どう選ぶか — 初心者向けの目安

    同期 API を基本にする

    • チーム・サービスがまだ少ない
    • ユーザーがその場で結果を必要とする
    • 強い整合性が必要（在庫を見てから確定、など）

    メッセージ／イベントを足す

    • 後でよい処理が明確にある
    • ピーク吸収や、呼び出し先のダウンに耐えたい
    • 1つの出来事に複数の反応がある（注文 → 在庫・会計・通知）

    ハイブリッドが現実的

    多くのシステムは同期 API ＋ イベントの併用です。ユーザーの操作に対しては同期 API で注文を確定してすぐに OK/NG を返し、その裏でイベントを発行して、在庫更新・分析用ログ・メール送信をバックグラウンドで進めます。

    「全部イベント」も「全部同期」も極端になりやすいので、ユーザー体験が必要とする部分で線を引くとよいでしょう。

    8.よくあるつまずきと対策

    つまずき対策のヒント
    同期チェーンが長すぎる読み取りは集約 API（BFF・API ゲートウェイ）でまとめ、更新はイベント化を検討する
    イベントの順序が狂う同じ集約 ID で同じパーティションに流す、またはバージョン番号で順序を制御する
    同じメッセージが2回来る冪等性（何度処理しても同じ結果になる性質）を設計する。処理済み ID を記録するなど
    失敗したメッセージの行き場がないデッドレターキュー、リトライ上限、アラートを用意する

    9.イベント駆動アーキテクチャを詳しく見る

    ここからは、アーキテクチャスタイルとしてのイベント駆動アーキテクチャ（EDA）を、Richards & Ford『ソフトウェアアーキテクチャの基礎』の内容に沿って掘り下げます。もとのノートは見出しだけの読書メモが多いため、書籍の考え方に沿って説明を補っています。

    EDA の基本は、コンシューマーからの応答を待たない「ファイア＆フォーゲット」型の非同期通信を活用することです。

    9-1. ブローカー型：開始イベントと派生イベント

    1. 開始イベント：イベントフロー全体を開始するイベントです。イベントブローカーのイベントチャネルに送信されます。
    2. イベントプロセッサーが開始イベントを受け取り、そのイベントに関連する特定のタスクを実行します。
    3. 処理を終えたプロセッサーは、派生イベントを非同期に発行し、「自分が何をしたか」をイベントブローカーを通じてシステム全体に知らせます。
    4. 他のイベントプロセッサーは派生イベントに反応して自分の処理を行い、さらに新しい派生イベントで自分が行ったことを知らせます。これが連鎖していきます。

    イベントブローカーは通常フェデレーションされています。つまり、1つの巨大なブローカーではなく、ドメインごとにクラスタ化された複数のブローカーのインスタンスに分かれています。ここでの「クラスタ」は、同じ役割の複数のサーバーをまとめて1つのように動かし、冗長性や処理能力を高めた構成のことです。「インスタンス」は、実際に動いている1つのブローカーのことです。フェデレーションされた各ブローカーには、その特定ドメインのイベントフローで使うすべてのイベントチャネルが含まれます。イベントは複数の購読者に配られる性質があるため、チャネルにはトピック、（AMQP の）トピックエクスチェンジ、またはストリームを使います。

    9-2. イベントとメッセージの違い

    観点イベントメッセージ
    意味「何かが起きた」という状態変化の通知特定の相手への指示（コマンド）や問い合わせ（リクエスト）
    送り手と受け手送り手は誰が受け取るかを知らないし、気にしない送り手は宛先を知っている
    受け手の数0〜複数（ブロードキャスト）通常1つ（ポイントツーポイント）
    典型的なチャネルトピック・ストリームキュー

    9-3. 応答性とパフォーマンス

    非同期通信で改善されるのは、主に応答性（responsiveness）です。たとえばユーザーがコメントを投稿したとき、同期処理なら投稿の検証・保存・通知まで全部終わってから「投稿しました」と返しますが、非同期なら「受け付けました」とすぐに返し、残りは裏で処理します。ユーザーが感じる待ち時間は大きく短くなります。

    ただし、処理全体にかかる時間（パフォーマンス）が短くなるわけではありません。また、裏の処理が失敗したときにユーザーへどう知らせるか、というエラー処理の難しさが代わりに生まれます。「非同期にすると速くなる」ではなく「待たせなくなる」と理解するのが正確です。

    9-4. ブロードキャスト機構

    イベント駆動の特徴の1つは、プロデューサーが誰が受け取るのか、受け取って何をするのかを知らずにイベントを配信（ブロードキャスト）できることです。新しい購読者を追加しても発行側は変更不要なので、システムを最も疎結合に保てる仕組みです。一方で、「このイベントを誰が使っているのか」を把握しにくくなるため、イベントの一覧や購読関係を文書化しておくことが重要になります。

    9-5. イベントペイロード：データ型とキー型

    イベントに何を載せるか（ペイロード）には2つの考え方があります。

    データイベントペイロード

    処理に必要なデータをすべてイベントに含める方式。

    • 良い点：受け手は DB に問い合わせ直さなくてよい。性能・スケールに有利
    • 注意点：イベントのスキーマ（契約）の管理が大変。ペイロードが大きくなる。使わないデータまで受け取る（スタンプ結合）。受け取った時点でデータが古い可能性

    キーイベントペイロード

    キー（注文 ID など）だけをイベントに含め、詳しいデータは受け手が取りに行く方式。

    • 良い点：契約がシンプルで変更に強い。常に最新のデータを読める
    • 注意点：受け手が DB や API に問い合わせるため、負荷と結合が増える。データの持ち主が落ちていると処理できない

    9-6. 「ブヨの群れ」アンチパターン

    派生イベントを、誰も必要としていない細かい単位で大量に発行してしまう状態を、小さな虫が群がる様子にたとえて「ブヨの群れ（Swarm of Gnats）」と呼びます。ブロードキャストは便利なので「念のため」何でもイベントにしたくなりますが、イベントが増えすぎると、ブローカーの負荷が増え、流れの把握もできなくなります。派生イベントは、意味のある状態変化を表すものに絞って発行するのが基本です。

    9-7. エラー処理：ワークフローイベントパターン

    非同期の世界では、コンシューマーがエラーに遭遇しても、プロデューサーはすでに次の仕事に移っています。そこで使われるのがワークフローイベントパターンです。

    1. イベントプロデューサーが、メッセージキュー（イベントチャネル）を介してイベントコンシューマーに非同期にデータを渡します。
    2. コンシューマーはデータ処理中にエラーに遭遇すると、そのエラーをワークフロープロセッサーに委譲し、自分はすぐにキュー内の次のメッセージの処理に移ります（全体の応答性を落とさないため）。
    3. ワークフロープロセッサーはエラーを受け取ると、メッセージの何が問題なのかを調べます。プログラムで修正できればデータを直して元のキューに戻し、再処理させます。
    4. 自動で直せない場合は、ダッシュボードなどに送り、人が確認・修正して再送します。

    副作用：順序が崩れる

    エラーになったメッセージは修正後に再投入されるため、後から来たメッセージより遅れて処理されることがあります。同じ注文に対する更新の順序が重要な場合は、別途対策（同じキーのメッセージを保留するなど）が必要です。

    9-8. データロスの防止

    AMQP（RabbitMQ などが使うメッセージングのプロトコル）を使う構成では、イベントはエクスチェンジに発行されます。エクスチェンジは、コンシューマー側のイベントプロセッサーが設定したバインディングルールを使って、そのイベントを購読している各プロセッサーのキューへ転送します（Amazon SNS ＋ SQS の組み合わせも、トピックからキューへ配るという点で同じ構図です）。

    プロセッサー A がイベントを発行し、プロセッサー B が受け取って DB に保存する流れを考えると、データが失われる可能性は3か所にあります。

    #データロスが起きる場面対策
    1A が発行したメッセージがキューに届かない。または届いても、B が取得する前にブローカーが落ちてしまう永続化されたキュー＋同期送信：イベントは高速化のためにメモリに置くだけでなく、物理的なデータストアにも永続化する（保証付き配信）。ブローカーが復旧した後でも処理できる。さらに A はブローカーが永続化を終えたという応答を待ってから次を送る
    2B がキューからメッセージを取り出した後、処理する前にクラッシュしてしまうクライアント確認応答（client acknowledge）モード：取り出した時点ではメッセージをキューから消さず、クライアント ID を付けてロックし、他のコンシューマーが読めないようにする。B が処理完了を応答して初めて削除される。B がクラッシュしてもメッセージはキューに残る
    3何らかのデータエラーで、B がメッセージを DB に永続化できないDB コミットによる ACID トランザクション：コミットが成功すればデータは確実に永続化される。さらに LPS（Last Participant Support）を使うと、処理が完了して DB に永続化されたことを確認してから、キューからイベントを削除できる

    9-9. リクエスト・リプライ処理（疑似同期通信）

    イベント駆動の中でも、注文 ID を受け取るなど応答が必要な場面があります。そのときはメッセージングで疑似的に同期通信を実現します。

    相関 ID（Correlation ID）を使う方法

    1. プロデューサーはリクエストキューにメッセージを送り、そのメッセージ ID を覚えておく
    2. コンシューマーは処理後、リプライキューに応答を送る。このとき応答の相関 ID に元のメッセージ ID を入れる
    3. プロデューサーはリプライキューで、相関 ID が自分のメッセージ ID と一致する応答を待って受け取る

    テンポラリーキューを使う方法

    1. プロデューサーはリクエストごとに一時的な応答用キューを作り、その名前をメッセージに付けて送る
    2. コンシューマーはその一時キューに応答を送る
    3. 応答を受け取ったら一時キューを削除する

    仕組みは単純ですが、リクエストのたびにキューを作るため、量が多いとブローカーの負荷が高くなります。

    9-10. メディエーター型トポロジー

    ブローカー型と対になるのがメディエーター型です。イベントメディエーター（指揮役）が開始イベントを受け取り、ワークフローの手順を知っていて、各プロセッサーに順番に処理を指示します。

    • メディエーターと各プロセッサーの間のチャネルには、宛先が決まったキュー（ポイントツーポイント）がよく使われます。プロセッサーは処理結果をシステム全体に宣伝せず、メディエーターに返します。
    • メディエーターは、扱うワークフローの複雑さに応じて使い分けます。単純なルーティングなら Apache Camel や Spring Integration のような統合フレームワーク、複雑な条件分岐があるならワークフロー・エンジン（BPEL など）、人の承認が入る長いフローなら BPM エンジン（jBPM など）といった具合です。
    型良い点弱い点
    ブローカー型疎結合。拡張性・応答性・性能・耐障害性が高い。処理の追加が容易ワークフロー全体の制御ができない。エラー処理・再実行・再開が難しい。全体の状態が分からない
    メディエーター型ワークフローを制御できる。エラー処理・回復・途中からの再開がしやすい。状態を管理できるメディエーターとの結合が強い。メディエーターがボトルネック・単一障害点になりやすく、スケールと性能で劣る

    この関係は、SAGA のコレオグラフィ（ブローカー型に近い）とオーケストレーション（メディエーター型に近い）と同じ構図です（40-4）。

    9-11. データトポロジー

    イベントプロセッサーがどのように DB を持つかにも、いくつかの選択肢があります。

    トポロジー形良い点弱い点
    モノリシックデータベースすべてのプロセッサーが1つの DB を共有するシンプル。データの取得が簡単で、整合性を取りやすいDB がスケール・耐障害性のボトルネックになる。スキーマ変更が全プロセッサーに波及する
    ドメインデータベースドメインごとに DB を分け、同じドメインのプロセッサーで共有する変更の影響がドメイン内に閉じる。バランスがよいドメインをまたぐデータはイベントや API 経由で取る必要がある
    専用データベースプロセッサーごとに専用の DB を持つ最も疎結合。個別にスケール・変更できるデータ共有はイベント経由になり、結果整合性・重複データの管理が必要

    9-12. リクエストベースモデルとイベントベースモデル

    リクエストベースモデル

    「この注文履歴を見せて」のようなデータ駆動の要求を、決まった手順で処理するモデル（オーケストレーターが順に処理を呼ぶ）。

    • 良い点：流れが決定的で分かりやすい。強い整合性を保ちやすい。結果がすぐ分かる
    • 弱い点：スケールや応答性に限界がある。変更に対して柔軟性が低い

    イベントベースモデル

    「入札が入った」のような状況（出来事）に反応して処理を進めるモデル。

    • 良い点：動的な状況に強い。スケール・応答性・耐障害性が高い
    • 弱い点：結果整合性になる。処理の流れを制御しにくく、結果が不確定になりやすい

    1つのシステムの中でも、要求の性質によって両方を使い分けるのが一般的です。

    10.小さな練習

    EC サイトの「注文確定」について、次の3つに分類してみてください。

    1. 同期でやるべきこと（ユーザーが待つ）
    2. 非同期でよいこと（後でよい）
    3. イベントとして発行するとよさそうな事実（過去形で名前をつける）
    答えの一例
    • 同期：支払い可否、在庫の最終チェック、注文番号の返却
    • 非同期：配送手配、レコメンド更新、社内レポート
    • イベント：OrderPlaced、PaymentCaptured

    11.よくある誤解

    誤解実際
    非同期にすれば処理が速くなる速くなるのはユーザーへの応答。処理全体の時間は変わらないか、むしろ増えることもある
    キューを使えばイベント駆動宛先が決まった「〜して」はコマンド（メッセージ）。イベントは過去形の事実を、宛先を知らずに知らせるもの
    全部イベントにすれば疎結合で理想的流れが見えなくなり、ブヨの群れや結果整合性の問題を招く。ユーザーが待つ部分は同期がよい
    メッセージは必ず1回だけ届く重複・順序の入れ替わり・取りこぼしは起こりうる前提で、冪等性・永続化・確認応答を設計する

    12.まとめ

    このページのポイント

    • 同期 API は待つ。分かりやすく強い整合性を取りやすいが、連鎖障害と遅延の足し算に注意。
    • メッセージは宛先に投げて待たない。負荷の平準化と障害の緩和に効くが、運用と冪等性が必要。
    • イベントは起きた事実を知らせるだけ。拡張しやすいが、流れが見えにくく結果整合性になる。
    • コマンド（〜して）とイベント（〜した）を名前で区別する。
    • 現実的なのは 同期 API ＋ イベントのハイブリッド。ユーザー体験が必要とする部分で線を引く。
    • EDA にはブローカー型とメディエーター型があり、データロス防止（永続化・確認応答・LPS）とエラー処理（ワークフローイベント）の設計が欠かせない。
