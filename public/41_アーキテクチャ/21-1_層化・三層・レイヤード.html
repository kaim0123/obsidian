    層化・三層・レイヤード（4層）

    ソフトウェアの内部を整理する最も基本的な方法が「層化（Layering）」です。このページでは、層化の考え方と依存ルール、古典的な三層アーキテクチャ、ドメイン層を独立させたレイヤードアーキテクチャ（4層）、そして N 層への拡張までを、コード例・Next.js での対応・落とし穴とあわせて詳しく解説します。

    もとにしたノート：01層化 ／ 三層アーキテクチャ ／ レイヤードアーキテクチャ（＋ 00_解説_アプリ内部構造）

    1.このページで扱うこと

    アプリを作っていると、必ず「どこにどのコードを書けばいいのか」という問題にぶつかります。画面・業務ロジック・データ保存といった役割の違いでコードを水平に切り分け、上から下へ依存させる——これが層化です。このページでは次のことを扱います。

    • 層化とは何か、なぜ採用されるのか（メリット）
    • 三層・レイヤード（4層）・N 層の違いと関係
    • 各層の役割と、層ごとの具体的なコード例
    • 「Layer（層）」と「Tier（ティア）」の違い
    • Next.js（App Router）で三層を当てはめるときの置き場所
    • 層化の典型的な落とし穴と、何層構成にするかの判断軸

    前提として アーキテクチャとは・設計との違い と トレードオフとアーキテクチャに効く原則（関心の分離）を読んでおくと、理解が深まります。

    このフォルダ（20 アプリ内部構造）の位置づけ

    20 アプリ内部構造は「1つのアプリケーション（1つのプロセス・1つのデプロイ単位）の中を、どう部品に分け、どの向きにつなぐか」を扱います。C4 モデルでいえば「コンテナの中身（コンポーネント）」のズームレベルです。アプリ内部構造のアーキテクチャは、大きく「上下に積む（層）」から「中心と周辺に分ける（同心円）」へと発展してきました。このページの「層」はその出発点です。

    2.層化とは

    層化（Layering）とは、ソフトウェアを役割の異なる水平の層に分け、次の一方向の依存ルールで構造化する手法です。

    してよいこと

    上の層は下の層を呼び出してよい。

    してはいけないこと

    下の層は上の層を呼び出してはならない（存在すら知らない）。

    たとえばピザ屋のシステムなら、次のように分けます。

    • 注文画面（プレゼンテーション層）
    • 注文受付ロジック（ビジネスロジック層）
    • 注文 DB（データ層）

    画面はビジネスロジックを呼び、ビジネスロジックは DB を触ります。しかしDB が画面を呼び出すことはない、というルールにします。

    日常生活での例え：レストラン

    ウェイター

    ＝表示層（プレゼンテーション）。お客様との接点です。

    シェフ

    ＝業務層（ビジネスロジック）。料理のルールを知っています。

    冷蔵庫・食材庫

    ＝データ層。材料を保存しています。

    ウェイターはシェフに注文を伝え、シェフは食材庫から材料を出します。食材庫がお客様に話しかけることはありません。

    3.なぜ層化するのか（メリット）

    3.1 関心の分離が自然になる

    関心の分離（トレードオフとアーキテクチャに効く原則）が、層という形で物理的に表現されます。「画面の話はこの層」「DB の話はこの層」と、どこに何を書くかが一意に決まります。画面の都合・業務の都合・DB の都合が混ざりません。

    3.2 変更の影響が局所化する

    • 画面を改修する → プレゼンテーション層だけを直す
    • DB を切り替える → データ層だけを直す

    このようにできれば、変更コストが大きく下がります（なぜ早く意識するか・アーキテクトの役割と思考 の変更コストの話）。画面のデザイン変更が DB 処理を壊すこともありません。

    3.3 チームの分業が成立しやすい

    • フロントエンド担当 → プレゼンテーション層
    • バックエンド担当 → ビジネスロジック層・データ層

    このように担当範囲を層で切れるので、UI チームとバックエンドチームが並行して作業できます。

    3.4 テストしやすい

    • ビジネスロジック層を画面なしで単体テストできる
    • データ層を偽物の DBで動かしてテストできる

    3.5 三層ノートでのメリットの内訳

    1. 保守性 — UI だけ変えたいときに、業務層・データ層を触らなくてよいことが多い
    2. 再利用 — 同じ業務 API を Web・モバイル・管理画面から使える
    3. テスト — 業務層を UI 抜きで検証しやすい
    4. スケール — 層ごとにサーバーや DB を伸ばしやすい（物理的に分けた Tier の場合）
    5. 役割分担 — フロント／バックエンド／データ担当で境界を描きやすい

    そして何より、フォルダ構成を見るだけで分担がわかるので「どこに書くべきか迷わない」ことが、日々の開発では大きな効果になります。

    4.三層・レイヤード・N 層の関係

    三つの言葉は対立するものではなく、同じ層化という考え方の、粒度の違いです。

    構成層特徴
    三層表示層 / 業務層 / データアクセス層最も古典的。業務層にユースケースも業務ルールも入る。小〜中規模の CRUD 向き
    レイヤード（4層）プレゼンテーション / アプリケーション / ドメイン / インフラ業務層を「アプリケーション層（手順）」と「ドメイン層（業務ルール）」に分ける。中〜大規模向き
    N 層必要に応じて増やす層を増やすほど分離は進むが、素通りする層も増える

    レイヤードアーキテクチャ（Layered Architecture）は層化を設計手法として一般化したもので、層の数や名前は固定ではありません。一般には、ドメイン層を独立させた4層の形を指して「レイヤード」と呼ぶことが多く、このページでもその意味で使います。三層はその最も基本的な形、N 層は必要に応じた拡張です。

    5.三層アーキテクチャ

    三層アーキテクチャ（Three-Tier / 3-Layer Architecture）は、最もシンプルで広く使われているアーキテクチャのひとつで、レイヤードの最も基本的な形です。アプリを「表示」「業務」「データ」の3つに分けることで、誰でも迷わずどこに書くかを判断できるようにします。この3つに分けるだけでも、関心の分離は十分に機能します。

    • 上の層 → 下の層 を呼び出す
    • 下の層は上の層を知らない

    5.1 表示層（Presentation Layer）

    • 役割：ユーザーが見る・触る部分
    • 技術例：HTML、CSS、React、Vue、HTTP エンドポイント
    • やること：入力を受け取る／業務層に処理を依頼する／結果を整形して表示する
    例：HTTP コントローラ（表示層） 
    app.post('/orders', async (req, res) => {
  const result = await orderService.placeOrder(req.body); // 業務層に依頼
  res.json(result);
});

    5.2 業務層（Business Logic Layer, BLL）

    • 役割：アプリケーションの中核。業務ルールを扱う
    • 技術例：Service クラス、UseCase クラス
    • やること：業務ルールを計算する／データアクセス層に読み書きを依頼する／複数の処理をまとめる
    例：OrderService（業務層） 
    class OrderService {
  async placeOrder(input) {
    if (input.items.length === 0) throw new Error('商品がない');
    const total = input.items.reduce((sum, i) => sum + i.price, 0);
    const order = { id: uuid(), total, items: input.items };
    await orderRepo.save(order); // データ層に依頼
    return order;
  }
}

    5.3 データアクセス層（Data Access Layer, DAL）

    • 役割：DB やファイルとの読み書き
    • 技術例：Repository、DAO、ORM（Prisma、Sequelize、TypeORM）
    • やること：SQL・クエリを発行する／オブジェクトとレコードを変換する
    例：OrderRepository（データアクセス層） 
    class OrderRepository {
  async save(order) {
    await db.query('INSERT INTO orders ...', order);
  }
  async find(id) {
    return db.query('SELECT * FROM orders WHERE id = ?', id);
  }
}

    5.4 データの流れの例

    商品検索

    1. ユーザーが「ラーメン」と検索する
    2. [表示層] SearchController が searchService.search('ラーメン') を呼ぶ
    3. [業務層] SearchService が検索ルールを適用し、productRepo.findByName('ラーメン') を呼ぶ
    4. [データ層] ProductRepository が SELECT * FROM products WHERE name LIKE '%ラーメン%' を DB に発行する

    ログイン

    1. ユーザーがフォームを送信する
    2. 表示層：HTTP リクエストを受け取る
    3. 業務層：入力を検証し、認証の流れを進める
    4. データ層：ユーザーを検索する
    5. 業務層：パスワードを検証し、セッションを作成する
    6. 表示層：レスポンスを画面に反映する

    5.5 フォルダ分けの例

    my-app/
├── frontend/     # 表示層（React など）
├── backend/      # 業務層（ルート・サービス）
└── database/     # スキーマ・マイグレーション（データ層の都合を集約）

    5.6 Next.js（App Router）での対応の目安

    Next.js は「どのフォルダが層を決める」と公式に定めているわけではないので、ルールはチームで決め、業務・データの処理は lib/ などに置くことが多いです。三層の考え方でよく当てはまる配置は次のとおりです。

    層Next.js 上の置き場所の例役割のイメージ
    表示層app/**/page.tsx、layout.tsx、loading.tsx、error.tsx、not-found.tsx などルート配下の UI画面の描画・入力の受け取り。業務はサービスや Server Action へ委譲する
    表示層（HTTP 境界）app/api/**/route.ts（Route Handlers）REST 的な入出力。中身は薄くし、業務層の関数を呼ぶだけにすると三層に近い
    表示層（部品）components/（クライアント／サーバーを問わず、見た目とイベントが主なもの）ボタン・フォーム・レイアウトなど。DB 直叩きや複雑なルールは避ける
    業務層lib/services/、lib/use-cases/、server/actions/ 内の薄いラッパー以外の処理など（命名はプロジェクト次第）バリデーション（ドメインルール）、計算、複数リポジトリの組み合わせ
    データアクセス層lib/repositories/、lib/dao/、Prisma／Drizzle のクエリをまとめたモジュール、prisma/schema.prismaDB・外部ストレージへの読み書き。ORM の利用自体はここに寄せる

    迷いやすい場所

    • middleware.ts（ルート直下） — 認可・リダイレクトなど横断的な HTTP 前処理で、厳密には三層のどれか一つに閉じません。薄く保つのが無難です。
    • Server Actions（app/.../actions.ts や lib/actions/ など） — HTTP 的な入口に近いので表示層寄りとも言えますが、中に業務処理や SQL をべた書きすると層が混ざります。入口は薄く、本体はサービス／リポジトリと分けると整理しやすくなります。
    • Server Component 内での fetch / ORM 直呼び — ファイルの場所が app/ でも、呼んでいる処理の種類で層が決まります。ページにロジックを詰め込まず、業務・データは lib/ 側に出すと三層の意図に沿います。
    • public/ — 静的アセットのみです。業務層・データ層ではありません。

    Pages Router の場合も考え方は同じで、pages/**/* のページコンポーネントが表示層、pages/api/* が HTTP 境界、業務・データは App Router と同様に lib/ などへ置く、という対応になります。

    5.7 三層のメリットとデメリット

    メリット

    • 覚えることが少ない
    • 多くのフレームワークが前提とする構造（Spring、Rails、Laravel…）
    • 小規模チームでも運用できる
    • 教科書どおりで伝わりやすい

    デメリット

    • 業務ロジックが肥大化すると業務層が太る（Fat Service 問題）
    • ドメインが育たない（ビジネスルールが Service 層に散らばる）
    • データ層の都合がロジックに漏れやすい（JOIN 前提の設計など）
    • 小規模では層分割が過剰に感じることがある（ファイル数だけ増える）
    • 層をまたぐたびにわずかなオーバーヘッドがある
    • 層の境界を誤ると、かえって変更が難しくなる

    小さいアプリには十分ですが、複雑な業務を扱うようになったら、レイヤードアーキテクチャやクリーンアーキテクチャへの移行を検討します。

    5.8 よくある変種

    三層＋プレゼンターパターン

    表示層を Controller / View / Presenter の3つに分け、MVP パターンと組み合わせます（→ MVP・MVVM と GUI アーキテクチャの系譜）。

    三層＋リポジトリパターン

    データ層を Repository インターフェース＋実装に分け、業務層はインターフェースだけに依存させます（DIP。→ 依存性逆転の原則（DIP））。

    6.「Layer（層）」と「Tier（ティア）」の違い

    英語の Tier と Layer はほぼ同じ意味で使われますが、ニュアンスに違いがあります。

    用語意味典型例
    Layer（層）論理的な分け方（同じプロセス内で分けてもよい）コード上のパッケージ／モジュール分割
    Tier（ティア）物理的な分け方（別サーバー／プロセスに分ける）Web サーバー・AP サーバー・DB サーバー

    文脈で読み分ける

    「3層構造」と言うとき、3つのモジュールに論理的に分かれている場合と、Web・AP・DB の3台に物理的に分かれている場合の両方を指します。どちらの意味かは文脈で読み分けるのが現実的です。三層ノートのメリット「層ごとにサーバーや DB を伸ばしやすい」は、物理的に分けた Tier の話です。

    7.レイヤードアーキテクチャ（4層）

    レイヤードでは、上の層は下の層の機能を使えますが、下の層は上の層を知りません。三層との最大の違いは、ドメイン層（業務ルール）を独立した層にすることです。

    7.1 プレゼンテーション層

    • 役割：ユーザーとの接点（画面、HTTP エンドポイント、CLI）。API のリクエスト／レスポンス処理
    • 具体例：React コンポーネント、Express のルートハンドラ、REST API のコントローラ
    • 書くべきこと：入力の受け付け、出力の整形
    • 書くべきでないこと：ビジネスルール、DB アクセス
    良い例：コントローラは受けて渡して返すだけ 
    app.post('/users', async (req, res) => {
  const user = await userService.register(req.body);
  res.json(user);
});

    7.2 アプリケーション層

    • 役割：「ユースケース」を1つずつ表現し、処理の流れをまとめる。複数ドメインをコーディネートする
    • 具体例：RegisterUserUseCase、PlaceOrderService
    • 書くべきこと：処理の流れ、トランザクション境界
    • 書くべきでないこと：ビジネスルールの中身、UI 処理
    class RegisterUserUseCase {
  async execute(input) {
    const user = User.create(input);          // ドメインに依頼
    await this.userRepo.save(user);           // インフラに保存を依頼
    await this.mailer.sendWelcome(user.email);
  }
}

    7.3 ドメイン層（業務ロジック層）

    • 役割：業務ルール・計算・状態遷移を持つ中核
    • 具体例：User、Order、Product などのエンティティ、Price、Email などの値オブジェクト
    • 書くべきこと：業務のルール（「未成年はお酒を買えない」など）
    • 書くべきでないこと：DB の都合、UI の都合
    class User {
  constructor(email, age) {
    if (!email.includes('@')) throw new Error('メール不正');
    this.email = email;
    this.age = age;
  }
  canBuyAlcohol() {
    return this.age >= 20;
  }
}

    7.4 インフラ層（インフラストラクチャ層）

    • 役割：外の世界との接続（DB、外部 API、ファイルシステム、メール送信）
    • 具体例：MySQLUserRepository、SendGridMailer
    • 書くべきこと：永続化・外部通信・フレームワーク固有のコード
    • 書くべきでないこと：業務ルール

    7.5 具体例：ユーザー登録の流れ

    1. HTTP POST /users を受ける ← プレゼンテーション層
    2. RegisterUserUseCase.execute が流れを進める ← アプリケーション層
    3. User.create(input) がルールを検証する ← ドメイン層
    4. userRepository.save(user) が DB に書き込む ← インフラ層

    7.6 三層との違い

    項目三層アーキテクチャレイヤードアーキテクチャ
    層の数3層4層以上（ドメイン層を分離）
    ドメイン層業務層に含まれる独立した層
    主な使い道小〜中規模の CRUD アプリ中〜大規模・複雑な業務
    学習コスト低いやや高い

    簡単に言えば、三層は「業務層」の中にビジネスルールもユースケースも全部入っているのに対し、レイヤードでは「アプリケーション層（ユースケース）」と「ドメイン層（業務ルール）」に分けるのが違いです。

    8.層の間のルール

    8.1 原則：上から下への依存のみ

    古典的なレイヤードでは、次の順に依存します。

    プレゼンテーション層 → アプリケーション層 → ドメイン層 → インフラストラクチャ層

    逆向きの依存（インフラがドメインを呼ぶ、ドメインが UI を知る）が起きると、層化のメリットが崩れます。

    8.2 禁止されていること

    • 下位層が上位層を直接呼ぶ（ドメインが UI を知る）
    • 層をスキップする（UI から直接 DB を叩く）。ただし、意図して「飛ばしてよい層」を設計する考え方もあります（→ 閉じた層と開いた層・シンクホール）
    • 業務ルールを UI に書く
    • DB の都合をドメインに漏らす

    8.3 古典的レイヤードの弱点と、その先

    ドメイン層が DB に依存している

    伝統的なレイヤードではドメイン層がインフラ層（DB）に依存します。これが「DB を変えると業務ロジックまで影響する」問題の原因になり、23 の同心円型アーキテクチャ（クリーン／ヘキサゴナル／オニオン）が生まれるきっかけになりました。現代的なレイヤードでは、インフラ層の側がドメインに定義されたインターフェースに依存するように逆転させる考え方（DIP）がよく使われます（→ 依存性のルールとクリーンアーキテクチャ）。クリーンアーキテクチャ／オニオンは、この依存の向きをドメインを中心に整理し直したもの、と理解できます。

    9.N 層アーキテクチャ

    9.1 必要に応じて層を増やす

    N 層アーキテクチャ（N-Tier Architecture）は、三層を必要に応じて拡張したものです。

    • 4層：プレゼン／アプリケーション／ドメイン／インフラ
    • 5層：プレゼン／API ゲートウェイ／アプリケーション／ドメイン／インフラ
    • 6層：さらに上に BFF（Backends For Frontends）を足す、など

    「何層が正解」というものはなく、システムの複雑さとチームの規模に応じて選びます。

    9.2 層を増やすメリットとコスト

    観点増やすメリット増やすコスト
    関心の分離より細かく整理できる1つの変更で多くの層を通過する
    テスト容易性各層を個別にテストできるテストする層が増える
    チーム分業細かく担当を切れる層をまたぐ仕様調整が増える
    性能層単位でキャッシュできる層間の通信オーバーヘッド

    「多ければ良い」わけではありません。何の関心を分けるための層かを明確に説明できるなら追加する、というのが原則です。

    10.層化の落とし穴・よくある罠

    10.1 層を「素通り」する

    層を増やしても、各層が何もせずに次の層に渡すだけだと、コードが膨らむだけで意味がありません。それぞれの層が固有の責任を持っていることが大前提です。この「素通り」はアーキテクチャ・シンクホールと呼ばれ、閉じた層と開いた層・シンクホール で詳しく扱います。

    10.2 ビジネスロジックがプレゼンテーション層に染み出す

    「画面の都合で、ここで税計算しちゃおう」のような実装をすると、

    • 別の画面で同じロジックを再実装する羽目になる
    • ビジネスルールの変更時に画面を漏れなく直す必要が出る

    関連する典型的なアンチパターン（モデルに HTML/CSS を含める例など）は MVC（定義・Web の MVC・MVC 違反） を、MVC 系全体の整理は MVP・MVVM と GUI アーキテクチャの系譜 を参照してください。

    10.3 データ層への直接アクセス

    プレゼンテーション層からデータ層を直接呼ぶと、層化の意味が崩れます。「ちょっと早く実装したい」誘惑に負けると、後からビジネスロジックを差し込む場所がなくなることに気づきます。

    10.4 層が固定的になりすぎて変えにくい

    層を厳密に守りすぎると、ちょっとした処理を書くために毎回4層を貫通する必要が出て、開発速度が落ちます。「何を厳密に守り、何を緩めるか」はチームのコンテキストで判断します。

    10.5 「ただの MVC」と混同する

    MVC は「画面まわりの分担」なので、レイヤードアーキテクチャとは抽象度が違うものです。Controller はプレゼンテーション層の中にあります。

    10.6 ドメイン層が空っぽ

    初心者がよくやる失敗です。ビジネスロジックを全部サービス層やコントローラに書いてしまい、ドメイン層がただのデータ置き場（貧血ドメインモデル）になります。結果として、構造はただの「Controller → Service → DB」になってしまいます。

    10.7 層を横断する関心

    ログ・認証・トランザクションはすべての層に関係します。これらはミドルウェアや AOP（アスペクト指向プログラミング）として別扱いにします（→ 横断的関心事と認証・認可の境界）。

    10.8 分けすぎ

    必ずしも4層である必要はありません。小さいアプリならプレゼンテーション＋ドメイン＋インフラの3層で十分です。

    11.層構成の選び方

    プロジェクトの規模・複雑さおすすめの層数例
    学習・プロトタイプ2〜3層UI ＋ ロジック（DB なしも可）
    個人開発・小規模3層プレゼン／業務／データ
    中規模 Web アプリ4層プレゼン／アプリ／ドメイン／インフラ
    大規模・複雑な業務4〜5層＋クリーン系の同心円DDD と組み合わせる

    迷ったら少なめから

    迷ったら少なめから始めるのが鉄則です。後から層を足すのは比較的楽ですが、最初から多すぎる層を整理するのは大変です（YAGNI 原則）。三層で始め、業務ルールが育ってきたら「業務層」を「アプリケーション層」と「ドメイン層」に分ける、という段階的な進め方が安全です。

    11.1 スタイルとしての評価（★1〜5）

    MOC のスタイル比較表では、レイヤードは次のように評価されています（『ソフトウェアアーキテクチャの基礎』に基づく。★が多いほど優れ、「手軽さ・コスト」は★が多いほど安く済む）。

    12.よくある誤解

    「層化＝古い設計」

    誤りです。クリーンアーキテクチャ・ヘキサゴナル・オニオンも、すべて層化の発展形です。層化は過去の設計ではなく、現代の設計の基礎です。

    「層が多いほど良い」

    誤りです。層は必要な分だけです。意味のない層は負担にしかなりません。

    「層化すれば自動的にクリーンになる」

    誤りです。層を切っても、依存の向きを意識しないと、画面と DB が直接つながったまま、ということが起きます。重要なのは依存ルールであって、層の本数ではありません（23 で深掘りします）。

    「MVC を使っているからレイヤードは要らない」

    誤りです。MVC はアプリ全体の構造ではなく、UI まわりの構造です。MVC の Controller と View はプレゼンテーション層の中の話で、業務ルールをどこに置くかは別に決める必要があります。

    13.まとめ

    • 層化は、ソフトウェアを役割の異なる水平の層に分け、上から下への一方向で依存させる、最も基本的な構造化手法です。
    • 三層は古典的な形（表示 → 業務 → データ）で、小〜中規模ならこれで十分です。
    • レイヤード（4層）は、業務層をアプリケーション層（ユースケース）とドメイン層（業務ルール）に分けたもの、N 層は必要に応じた拡張です。
    • メリットは関心の分離・変更の局所化・分業・テスト容易性。落とし穴は素通り層・ロジックの染み出し・直接アクセス・過剰な厳密さ・空っぽのドメイン層です。
    • 「Layer（論理）」と「Tier（物理）」はニュアンスが違うので、文脈で読み分けます。
    • 層数は少なめから始め、必要に応じて増やすのが安全です。
    • 古典的レイヤードはドメインが DB に依存する弱点を持ち、それを解決したのがクリーン／ヘキサ／オニオンです。

    次は 閉じた層と開いた層・シンクホール で、「層を飛ばしてよいか」という実務の疑問を扱います。その後、MVC や MVP・MVVM で、層化の中でも特にプレゼンテーション層を整えるパターン群を見ていきます。
