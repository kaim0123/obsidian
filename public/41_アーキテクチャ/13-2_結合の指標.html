    10 基礎 ／ 13 モジュール性・結合

    結合の指標（求心性・遠心性・主系列からの距離）

    「このモジュールは結合が強すぎるか？」を感覚ではなく数値で判断するための指標を解説します。凝集度を測る LCOM、結合度を測る求心性結合（Ca）・遠心性結合（Ce）、そこから計算する不安定度・抽象度・主系列からの距離と、苦痛ゾーン・無駄ゾーンの読み方、アーキテクチャでの使い方までを扱います。

    もとにしたノート：10_基礎/13_モジュール性・結合/02_結合の指標_求心性遠心性と主系列からの距離

    1.このページで扱うこと

    モジュール性・疎結合と高凝集 では、「疎結合・高凝集が良い」ことを学びました。しかし「このモジュールは結合が強すぎるか？」を 感覚ではなく数値で 判断できると、コードレビューや改善の優先順位づけがずっとしやすくなります。

    このページでは、『ソフトウェアアーキテクチャの基礎』第3章で紹介されている モジュール性の計測指標 を解説します。

    • 凝集度を測る LCOM
    • 結合度を測る 求心性結合（Ca）・遠心性結合（Ce）
    • そこから計算する 不安定度（I）・抽象度（A）・主系列からの距離（D）
    • 苦痛ゾーン・無駄ゾーン の読み方
    • アーキテクチャの評価・CI での使い方と、指標の限界

    結合度の指標（Ca・Ce・I・A・D）は、Robert C. Martin（『Clean Architecture』の著者）が 1990 年代に提唱したものです。パッケージ設計の原則（安定依存の原則 SDP・安定抽象の原則 SAP）としての詳しい解説は（41 外のノート：43_モジュール設計『01_パッケージ設計の原則』）にあり、このページでは アーキテクチャを評価する物差しとしての使い方 に焦点を当てます。

    2.凝集度を測る — LCOM

    2.1 LCOM とは

    LCOM（Lack of Cohesion in Methods：メソッドの凝集の欠如）は、Chidamber と Kemerer が 1994 年に発表したオブジェクト指向メトリクス群（CK メトリクス）の1つです。名前のとおり 凝集の「欠如」 を測るので、値が大きいほど凝集度が低い（＝分割を検討すべき）という意味になります。数値の向きが直感と逆なので注意してください。

    2.2 考え方

    LCOM の基本的な発想は「同じフィールドを使うメソッド同士は関係が深い」というものです。

    class OrderService {
    orders      // フィールドA
    mailer      // フィールドB

    placeOrder()     → orders を使う
    cancelOrder()    → orders を使う
    sendNewsletter() → mailer を使う    ← 他のメソッドと共有するフィールドがない
}
    • placeOrder と cancelOrder は orders を共有している → 関係が深い
    • sendNewsletter は他と何も共有していない → このクラスにいる理由がない

    LCOM は、こうした「フィールドを共有していないメソッドの組」がどれだけ多いかを数えます。上の例では、sendNewsletter を別のクラス（たとえば NewsletterService）に移すべき、というサインになります。

    2.3 注意点

    LCOM を使うときの注意

    • LCOM には定義のバリエーションが多く（LCOM1〜LCOM4 など）、ツールによって値の意味が違う
    • 『基礎』でも、LCOM は 構造的な凝集しか測れない（メソッドが論理的に一緒にあるべきかどうかは分からない）と注意しています
    • 「分割を検討すべき場所」を見つける道具 として使い、最終判断は人が行う

    3.結合度を測る — 求心性と遠心性

    3.1 2つの向きの結合

    モジュール（パッケージ・コンポーネント）の依存には 2つの向き があります。

    指標英語数えるもの直感的な意味
    求心性結合（Ca）Afferent Coupling外から自分へ 入ってくる依存の数どれだけ 頼られているか（責任の重さ）
    遠心性結合（Ce）Efferent Coupling自分から外へ 出ていく依存の数どれだけ 他に頼っているか（変更の受けやすさ）

    覚え方

    「求心」＝中心に向かう＝自分に 入ってくる。「遠心」＝中心から離れる＝自分から 出ていく。英語では Afferent を Arriving（到着）、Efferent を Exiting（出発）と結びつけると覚えやすいです。

    3.2 例で数える

    次のような依存関係を持つ6つのモジュールで考えます（矢印は「依存している」向き）。

    モジュールCa（入ってくる）Ce（出ていく）
    ui / api / batch01
    application3（ui・api・batch）2（domain・infrastructure）
    infrastructure1（application）1（domain）
    domain2（application・infrastructure）0

    domain

    頼られる一方で、何にも頼っていません。他の変更の影響は受けにくいのですが、自分を変更すると影響が大きい モジュールです。

    ui

    何にも頼られず、他に頼っています。自由に変えられる 一方で、他の変更の影響を受けやすいモジュールです。

    4.不安定度（I）— 変更の影響の受けやすさ

    4.1 定義

    不安定度（Instability）

    I = Ce ÷ (Ca + Ce)

    I = 0：安定

    外への依存がない。他の変更の影響を受けません。ただし、自分を変えると頼っている側への影響が大きいので、変えにくい。

    I = 1：不安定

    外からの依存がない。他の変更の影響を受けやすいのですが、自分を変えても誰も困らない。

    先ほどの例で計算すると、次のようになります。

    モジュールCaCeI
    ui011 ÷ (0 + 1) = 1.0（不安定）
    application322 ÷ (3 + 2) = 0.4
    infrastructure111 ÷ (1 + 1) = 0.5
    domain200 ÷ (2 + 0) = 0.0（安定）

    4.2 「不安定」は悪い意味ではない

    ここでの「不安定」は「壊れやすい」という意味ではなく、「変わりやすい・変えやすい」 という意味です。UI のように頻繁に変わる部分は、むしろ不安定（I が 1 に近い）であるべきです。

    大事なのは依存の 向き です。

    依存は、不安定なものから安定したものへ向かうべき（安定依存の原則：SDP / Stable Dependencies Principle）

    安定した domain が不安定な ui に依存していると、UI を変えるたびにドメインが壊れることになります。

    5.抽象度（A）— インターフェースの割合

    5.1 定義

    抽象度（Abstractness）

    A = 抽象要素の数（インターフェース・抽象クラス） ÷ 要素の総数

    • A = 0：すべて具体クラス
    • A = 1：すべてインターフェース・抽象クラス

    5.2 安定したものほど抽象的であるべき

    安定したモジュール（I が 0 に近い）は、多くのモジュールに頼られています。これが 具体的な実装 だと、変更したときに影響が広がるうえ、拡張もしにくくなります。そこで、次のように考えます。

    安定したモジュールほど抽象的であるべき（安定抽象の原則：SAP / Stable Abstractions Principle）

    抽象（インターフェース）に依存させておけば、実装を差し替えても依存元は影響を受けません。これは 依存性逆転の原則（DIP） をモジュール単位に広げた考え方です。

    6.主系列からの距離（D）

    6.1 主系列とは

    横軸に不安定度 I、縦軸に抽象度 A をとると、理想的なモジュールは A + I = 1 の直線の近くに並びます。この線を 主系列（Main Sequence）と呼びます。

    • 安定（I = 0）なら抽象的（A = 1）
    • 不安定（I = 1）なら具体的（A = 0）
    • その中間なら、中間の抽象度

    6.2 定義

    主系列からの距離（Distance from the Main Sequence）

    D = | A + I − 1 |

    • D = 0：主系列の上にある。抽象度と安定度のバランスが良い
    • D = 1：主系列から最も遠い。バランスが悪い

    たとえば先ほどの例で、domain が I = 0.0 のまま具体クラスだけ（A = 0）なら D = |0 + 0 − 1| = 1 となり、主系列から最も遠くなります。domain の公開部分をインターフェース中心にして A を上げるほど、D は 0 に近づきます。

    6.3 2つの危険ゾーン

    ゾーン位置状態例対策
    苦痛ゾーン
    Zone of Pain    		左下
    （A≈0, I≈0）    		具体的なのに、多くのモジュールが依存している。変更すると影響が広がり、拡張もしにくい何でも入った common / utils パッケージ、全サービスが直接参照する DB スキーマインターフェースを抽出する、責務ごとに分割する
    無駄ゾーン
    Zone of Uselessness    		右上
    （A≈1, I≈1）    		抽象的なのに、誰も依存していない。拡張のために作ったが使われていない実装が1つしかないのに作られたインターフェース群、使われなくなった基底クラス不要な抽象を削除する（YAGNI：必要になるまで作らない）

    例外：ほとんど変わらないモジュール

    文字列ユーティリティや標準ライブラリのように ほとんど変更されない 具体的なモジュールは、苦痛ゾーンにあっても実害は小さいです。苦痛は「変更するとき」に生じるからです。D の値は 変更頻度とあわせて 見ます。

    7.アーキテクチャでの使い方

    7.1 どこで役立つか

    場面使い方
    レイヤードやクリーンアーキテクチャの検証domain が I≈0・A が高め、外側の層が I≈1 になっているか。逆転していたら依存の向きが壊れている（→ 層化・三層・レイヤード、依存性のルールとクリーンアーキテクチャ）
    モジュラーモノリスの境界チェックあるモジュールの Ca が急に増えたら、「他モジュールから内部を直接呼ばれている」サイン
    分割候補の発見Ca も Ce も高いモジュール（頼られていて、頼ってもいる）は、変更の影響の中継点になりやすい
    共通ライブラリの見直しcommon が苦痛ゾーンにあれば、分割や抽象化を検討する
    適応度関数として CI に組み込む「domain の Ce は 0」「D が 0.7 を超えるパッケージを作らない」などのルールを自動チェックする（→ 進化的アーキテクチャと適応度関数）

    言語・環境ツール
    JavaJDepend、ArchUnit、SonarQube
    PHPPDepend（Abstraction Instability Chart を出力）
    .NETNDepend
    TypeScript / JavaScriptdependency-cruiser、ArchUnitTS

    7.3 限界

    指標で分からないこと

    • これらの指標は 「構造の結合」の数 しか測れません。結合の 種類や強さ（名前に依存しているのか、実行順序に依存しているのか）は分かりません → それを表すのが コナーセンス
    • サービス間の 実行時の結合（同期呼び出し・共有 DB）も測れません → アーキテクチャ量子と粒度
    • 数値を目標にすると、数値をよく見せるための不自然な設計（不要なインターフェースの追加など）が生まれます。数値は議論のきっかけ として使います

    8.よくある誤解

    「不安定度が高いモジュールは悪い」

    誤りです。 UI やアダプターのように、頻繁に変わる部分は不安定（I≈1）であるべきです。問題なのは 安定したものが不安定なものに依存している ことです。

    「抽象度は高いほど良い」

    誤りです。 誰も依存していないのにインターフェースばかり作ると 無駄ゾーン に入ります。抽象化は、多くのモジュールから頼られる安定した部分 にこそ必要です。

    「指標が良ければ良い設計」

    誤りです。 指標は構造的な結合の数しか見ていません。ドメインとして正しい分け方か、変更の単位と合っているかは、人が判断します。

    9.まとめ

    このページの要点

    • LCOM：クラス内のメソッドがフィールドを共有していない度合い。大きいほど分割を検討する
    • 求心性結合 Ca：自分に入ってくる依存（頼られている）／遠心性結合 Ce：自分から出ていく依存（頼っている）
    • 不安定度 I = Ce / (Ca + Ce)：0 が安定、1 が不安定。依存は 不安定 → 安定 に向けるべき（SDP）
    • 抽象度 A：抽象要素の割合。安定したものほど抽象的に（SAP）
    • 主系列からの距離 D = |A + I − 1|：0 に近いほどバランスが良い
    • 左下の 苦痛ゾーン（具体的なのに頼られすぎ）と右上の 無駄ゾーン（抽象的なのに使われない）に注意する
    • 指標は CI に組み込んで 適応度関数 にできる。ただし数値は議論のきっかけであり、結合の「種類」は コナーセンス で補う
