    00 全体像

    アーキテクチャ年表

    MVC からマイクロサービスまで、代表的なアーキテクチャを登場の早い順にたどります。それぞれについて「その前にどんな課題があったか」「何を提案したか」「どう解決したか」「向いている場面と限界」を整理し、最後にコンポーネント・関係性・原則という3要素で歴史を横断的に見直します。

    もとにしたノート：00_全体像/アーキテクチャ.md（有名なアーキテクチャ — 西暦順でたどる）

    1.このページで扱うこと

    ソフトウェアのアーキテクチャには、MVC やクリーンアーキテクチャなど、よく名前を聞くスタイルがいくつもあります。しかし 「なぜ生まれたのか」「何の問題を解決したのか」 が分からないと、名前だけ覚えても使いどころが分かりません。

    このページでは、代表的なアーキテクチャを 登場が早い順（おおよその西暦） に並べ、それぞれを次の4つの観点で解説します。

    1. その前に、どんな課題があったか
    2. そのアーキテクチャは何を提案したか
    3. どう解決したか（ざっくりした仕組み）
    4. 向いている場面と限界

    さらに、各時代で コンポーネント（部品）・関係性（依存）・原則と制約 がどう変わったかを、アーキテクチャとは・設計との違いで扱う3要素に沿って、14章で横断的に整理します。各アーキテクチャの詳しい中身は、章ごとに示す個別ページを参照してください。

    2.全体の流れ（年表）

    まず全体を一覧します。下の図は、出発点のスパゲッティコードから順に、色で「どの軸の進化か」を分けたものです。

    順番アーキテクチャ登場時期一言で言うと主に解決した課題
    1MVC1979年画面・操作・データを3つに分ける全部1か所に書く乱れ
    23層アーキテクチャ1990年代表示・業務・DB を層で分けるサーバー側の責務の混在
    3MVP1990年代後半画面制御を Presenter に任せるMVC の Controller 肥大化
    4ドメイン駆動設計（DDD）2003年ビジネスルールをドメインモデルに集約ビジネスロジックの肥大化・用語のズレ
    5MVVM2005年View と Model の間に ViewModel を置くイベントだらけの画面連携
    6ヘキサゴナルアーキテクチャ2005年Port ／ Adapter で外側を差し替え可能に業務ロジックが DB に依存
    7オニオンアーキテクチャ2008年依存の向きを内側（ドメイン）へ依存関係の整理不足
    8クリーンアーキテクチャ2012年これまでの考え方を1つに統合層・依存・責務の全体整理
    9イベント駆動アーキテクチャ（EDA）1990年代〜2010年代「起きたこと」をイベントで通知し、非同期に反応するシステム間の直接依存・同期連鎖
    10マイクロサービス2014年頃機能ごとに小さなサービスに分割して独立デプロイ巨大モノリスのデプロイ・スケール・チームの瓶頸

    年の読み方

    ここでの年は「名前が広まった時期」の目安です。考え方の源流はもっと前から存在するものもあります。また、3層 はレイヤードアーキテクチャ（4層・N層）の源流で、レイヤードはアプリケーション層・ドメイン層をさらに細分化した発展形です。

    3.その前：スパゲッティコード

    アーキテクチャという言葉が普及する前から、ソフトウェアは作られていました。当時（1970年代以前〜）よく起きていたのが、スパゲッティコード と呼ばれる状態です。処理の流れや依存が麺のように絡み合い、どこを引っ張るとどこが動くのか分からないことから、こう呼ばれます。

    • 画面の表示、計算、DB アクセスが 1つのファイルに全部書かれている
    • UI を変えると DB 処理まで壊れる
    • すべてが密結合しているため、テストが書けない

    この状態への反省から生まれた 「役割ごとに分けて、つなぎ方のルールを決めよう」 という発想が、アーキテクチャの出発点になりました。

    4.MVC（1979年）

    提唱 Trygve Reenskaug（Xerox PARC、Smalltalk 向け） 一言 画面・操作・データを3つに分ける
    詳しく MVC（定義・Web の MVC・MVC 違反）、MVP・MVVM と GUI アーキテクチャの系譜

    その前の課題 — 全部1か所に書く乱れ

    • 画面（View）の中に、データ処理や計算まで書いてしまう
    • 画面デザインを変えるだけなのに、ロジックまで触る必要がある

    何を提案したか

    部品役割
    Modelデータとビジネスルール
    Viewユーザーに見せる部分
    Controller入力を受け取り、Model と View をつなぐ

    ノートでは関係を次のように単純化して表しています。

      ユーザー → View ⇄ Controller ⇄ Model

    補足：MVC の図は1種類ではない

    1979年の元祖 Smalltalk MVC では、View は Model を 監視（Observer） していて、Model が変わると通知を受けて自分で描き直します。一方、Rails などの Web フレームワークの MVC や Apple の Cocoa MVC では、Controller が View と Model の間に立って仲介し、View と Model は直接やり取りしません。上のテキスト図は後者に近い形です。どちらも「関心の分離」という核は同じなので、名前が同じでも図が違う点を知っておくと混乱しません。

    どう解決したか

    • 関心の分離：見た目と中身の処理を別の場所に書く
    • 画面を差し替えても Model はそのまま使える

    向いている場面・限界

    向いている

    Web アプリ、デスクトップ GUI など、UI があるアプリ全般。

    限界

    Controller や Model が肥大化しやすい。→ MVP・3層・DDD へ。

    5.3層アーキテクチャ（1990年代）

    背景 クライアント・サーバー型のエンタープライズシステムの普及 一言 表示・業務・DB を層で分ける
    詳しく 層化・三層・レイヤード（4層）

    その前の課題 — サーバー側の責務の混在

    • MVC だけでは、Model の中に DB アクセス・ビジネスルール・画面用の整形が混ざる
    • 大規模システムで「この機能、どのファイルに書く？」が人によってバラバラになる

    何を提案したか

    サーバー側を 3つの水平な層 に分け、上の層から下の層へ一方向に呼び出します。

    どう解決したか

    • 役割の固定：DB はデータ層、ルールはビジネス層、と置き場所を決められる
    • UI を変えてもビジネス層に手を入れなくて済む（理想形）

    向いている場面・限界

    向いている

    中〜大規模の業務システム、モノリスのアプリ。

    限界

    ビジネス層が DB や UI に依存してしまうと、層を分けた意味が薄れる。→ ヘキサゴナル・クリーンへ。

    6.MVP（1990年代後半）

    背景 MVC の Controller 肥大化への対処（Taligent、のちに Windows Forms などで普及） 一言 画面制御を Presenter に任せる
    詳しく MVP・MVVM と GUI アーキテクチャの系譜

    その前の課題 — MVC の Controller 肥大化

    • Controller に UI ロジック・バリデーション・Model 操作が全部集まる
    • View が Model を直接読む実装と、Controller 経由の実装が混在し、処理を追いにくい
    • View の単体テストが難しい

    何を提案したか

    Controller の代わりに Presenter を置き、View は完全に受け身 にします。

    ユーザー入力 → View → Presenter → Model
                  ←       ←      (結果)
    部品MVC との違い
    ViewModel を直接見ない。Presenter の指示どおりに描画するだけ
    Presenter画面制御のロジックをすべて担当する

    どう解決したか

    • View が薄くなり、Presenter だけを単体テスト しやすくなる（View をモックに差し替えられる）
    • 画面とロジックの境界が MVC より明確になる

    向いている場面・限界

    向いている

    デスクトップアプリ、Android（初期の UI パターン）など。

    限界

    Presenter 自体が肥大化しやすい（神 Presenter）。双方向の画面更新が多いと MVVM の方が向く。

    7.ドメイン駆動設計 — DDD（2003年）

    提唱 Eric Evans（書籍 Domain-Driven Design の出版） 一言 ビジネスルールをドメインモデルに集約
    詳しく （41 外のノート：42_ソフトウェア設計『02_DDDとは』）

    その前の課題 — ビジネスロジックの肥大化・用語のズレ

    • ビジネスルールが Service クラスや Controller に散らばる
    • 開発者の用語と現場の用語がズレて、要件のすり合わせに時間がかかる
    • DB のテーブル設計から始めると、業務の本質がコードに反映されない

    何を提案したか

    ソフトウェアの構造と用語を、ビジネス（ドメイン）の現実に合わせる ことを提案しました。

    概念意味
    ユビキタス言語開発者と現場が同じ用語を使う
    境界づけられたコンテキスト大きなシステムを業務の区切りで分割する
    集約・エンティティ・値オブジェクトルールを守る単位としてモデル化する
     
      現場の言葉 → ドメインモデル → コードの構造
                    ↑
            クリーンアーキテクチャの
            Entities / Use Cases と相性が良い

    どう解決したか

    • ビジネスルールを ドメイン層 に集約し、UI や DB から独立させる
    • チーム間・コンテキスト間の境界（戦略設計）と、1つのコンテキスト内のモデル（戦術設計）を分けて考える

    向いている場面・限界

    向いている

    業務ルールが複雑で、長期保守するシステム。

    限界

    単純な CRUD では過剰。DDD は アーキテクチャそのもの というより 設計の考え方 で、クリーン・オニオンと組み合わせて使う。

    8.MVVM（2005年）

    背景 Microsoft の WPF ／ Silverlight 向け（John Gossman が発表） 一言 View と Model の間に ViewModel を置く
    詳しく MVP・MVVM と GUI アーキテクチャの系譜

    その前の課題 — イベントだらけの画面連携

    • 入力のたびに Controller ／ Presenter が View を手動で更新するコードが増える
    • 双方向の画面更新（フォーム ↔ 計算結果）がイベント地獄になる
    • 同じデータを PC 版・モバイル版で別々に実装しがち

    何を提案したか

    ViewModel が画面用の状態を保持し、データバインディング によって View と自動で同期させます。

    どう解決したか

    • View に描画ロジックをほぼ書かず、ViewModel の変更が 自動で画面に反映 される
    • ViewModel を画面なしでテストできる
    • 1つの ViewModel に複数の View（PC ／ モバイル）を接続しやすい

    向いている場面・限界

    向いている

    WPF、Vue、Angular、React＋状態管理など リッチな UI。

    限界

    双方向バインディングのバグは追いにくい。フレームワークへの依存が強い。

    MVC 系3パターンの比較

    観点MVCMVPMVVM
    ロジックの主体ControllerPresenterViewModel
    View の役割描画＋一部の入力完全に受け身バインディングで自動更新
    主な舞台Rails などの Webデスクトップ・Androidモダンなフロントエンド

    9.ヘキサゴナルアーキテクチャ（2005年）

    提唱 Alistair Cockburn（別名 ポート&アダプタ） 一言 Port ／ Adapter で外側を差し替え可能に
    詳しく ヘキサゴナルアーキテクチャ

    その前の課題 — 業務ロジックが DB に依存

    • 3層でも、ビジネス層が MySQL や REST API に 直接依存 してしまう
    • DB を変えたいのに、SQL がビジネスロジックの中に散らばっている
    • テストのたびに DB を起動しないといけない

    何を提案したか

    Application Core（ビジネスロジック） を中心に置き、外の世界とは Port（コア側が定める差し込み口のインターフェース） と Adapter（その差し込み口に合わせて外部技術をつなぐ実装） を経由して接続します。

      Web UI ──→ [Adapter] ──→ Port
                              │
                     Application Core
                              │
  MySQL  ←── [Adapter] ←── Port

    上のテキスト図の矢印は「呼び出し（制御）の流れ」です。DB 側では Core → Port → Adapter → MySQL と呼び出しが流れますが、ソースコードの依存は Adapter → Port の向き（Adapter が Port を実装する）になります。この「制御の流れと依存の向きが逆になる」点が依存性逆転です（依存性逆転の原則（DIP））。

    どう解決したか

    • 外側（DB・UI）が内側（ルール）に合わせる形で、依存の向きを逆転 する
    • DB や UI を差し替えても、コアはほぼ変更しなくて済む

    向いている場面・限界

    向いている

    ドメインルールが複雑で、インフラを差し替えたいモノリス。

    限界

    小さな CRUD アプリでは抽象化が過剰になる。

    10.オニオンアーキテクチャ（2008年）

    提唱 Jeffrey Palermo 一言 依存の向きを内側（ドメイン）へ
    詳しく オニオンアーキテクチャと3つの比較

    その前の課題 — 依存関係の整理不足

    • ヘキサゴナルと同様に、フレームワークや DB が主役 になりがち
    • 「ドメイン層」「アプリケーションサービス」といった 層の役割 がチーム内で曖昧
    • 依存性逆転（DIP）を フォルダ構成 として表現したい

    何を提案したか

    タマネギ状 に層を重ね、Domain Model を最も中心 に置きます。

    どう解決したか

    • ドメインモデルを 最も安定した中心 として明示する
    • ヘキサゴナルと同じ思想だが、層の名前と同心円の図 によってチームで共有しやすい

    向いている場面・限界

    向いている

    DDD と組み合わせた長期保守システム。

    限界

    クリーン・ヘキサゴナルと 思想はほぼ同じ で、違いは主に用語。小規模では過剰。

    11.クリーンアーキテクチャ（2012年）

    提唱 Robert C. Martin（Uncle Bob。2012年のブログ記事、2017年に書籍化） 一言 これまでの考え方を1つに統合
    詳しく 依存性のルールとクリーンアーキテクチャ、依存性逆転の原則（DIP）

    その前の課題 — 層・依存・責務の全体整理

    • ヘキサゴナル・オニオン・DDD がそれぞれ別の言葉で語られ、初学者が混乱 する
    • UseCase と Entity の境界、Adapter の置き場所がプロジェクトごとにバラバラ

    何を提案したか

    同心円の層 と 依存は常に内側へ というルール（依存性のルール）を、1つの図に統合しました。

            ┌─────────────────────────────┐
        │  Frameworks & Drivers（外）   │
        ├─────────────────────────────┤
        │  Interface Adapters          │
        ├─────────────────────────────┤
        │  Use Cases                   │
        ├─────────────────────────────┤
        │  Entities                    │  ← 最も安定
        └─────────────────────────────┘

    どう解決したか

    • MVC・3層・ヘキサゴナル・オニオン・DDD の 共通思想に1つの名前 を付けた
    • エンティティとユースケースを中心に置き、UI・DB の変更の影響を最小化する

    向いている場面・限界

    向いている

    長期保守する業務システム（DDD と相性が良い）。

    限界

    学習コストとボイラープレート（定型コード）の多さ。短命・小規模のプロジェクトでは過剰設計になる。

    12.イベント駆動アーキテクチャ — EDA（1990年代〜2010年代）

    背景 メッセージキュー（IBM MQ など）、書籍 Enterprise Integration Patterns（2003年）、Kafka（2011年にオープンソース化） 一言 「起きたこと」をイベントで通知し、非同期に反応する
    詳しく 同期 API・メッセージ・イベント駆動

    その前の課題 — システム間の直接依存・同期連鎖

    • システム A が B を 直接 HTTP で呼ぶ と、B の障害の影響をそのまま受ける
    • 注文・在庫・配送・メールを 1本の同期フロー に詰め込むと、1か所の失敗で全体が止まる

    何を提案したか

    「何が起きたか（イベント）」 を発行し、必要な側が後から反応する形にします。

    どう解決したか

    • 疎結合：注文サービスは在庫サービスの URL を知らなくてよい
    • 非同期：API はすぐに応答し、重い処理は後回しにできる
    • 拡張：新しい購読者を、既存のコードを触らずに追加できる

    向いている場面・限界

    向いている

    複数サービス・複数チームの連携、ピーク時の負荷分散。

    限界

    結果がすぐにはそろわない（結果整合性：eventual consistency）。運用コストが高い。

    13.マイクロサービス（2014年頃）

    背景 Netflix などの実践、James Lewis と Martin Fowler による整理（2014年の記事） 一言 機能ごとに小さなサービスに分割して独立デプロイ
    詳しく モノリス・分散モノリス・マイクロサービス

    その前の課題 — 巨大モノリスのデプロイ・スケール・チームの瓶頸

    • 小さな修正でも 全体を再デプロイ する必要がある
    • 100人規模のチームが1つのコードベースでコンフリクトする
    • 在庫機能だけスケールしたいのに、全部が同じサーバーで動いている

    何を提案したか

    システムを 小さな独立サービス に分割し、各サービスが 自分のデータを所有 します。

    どう解決したか

    • 独立したデプロイ・スケール：在庫サービスだけを修正・リリース・増強できる
    • チームの自律：サービス単位でチームを分けやすい
    • サービスの内部は クリーンアーキテクチャ、サービス間の連携は EDA と組み合わせることが多い

    向いている場面・限界

    向いている

    大規模なプロダクト、複数チーム、部分ごとにリリース頻度が違う場合。

    限界

    分散システム特有の難しさ（データ所有権・分散トランザクション・SAGA）。小さなチームでは モノリスから始める 方が合理的なことが多い。

    14.3要素の進化 — コンポーネント・関係性・原則

    アーキテクチャとは・設計との違いで扱う 3つの要素（コンポーネント・関係性・原則と制約）は、アーキテクチャの「名前」が増えるたびに、何を部品とみなすか・どうつなぐか・何を守るか が段階的に洗練されてきました。ここでは、上の年表と対応させてその変化を整理します。

    14-1. コンポーネント（部品）— 「何を1単位とみなすか」

    段階主なコンポーネント変化のポイント
    スパゲッティなし（1ファイルが全部）部品という概念自体がない
    MVCModel ／ View ／ ControllerUI・操作・データ を3つに分けた最初の型
    3層プレゼンテーション ／ ビジネス ／ データ層MVC の Model を サーバー側の水平層 に再分割
    MVPView ／ Presenter ／ ModelController を Presenter に特化（画面制御専用の部品）
    DDDエンティティ・値オブジェクト・集約・境界づけられたコンテキスト技術の層ではなく ビジネス概念 を部品にする
    MVVMView ／ ViewModel ／ Model画面用の状態を担う ViewModel が新しい部品として登場
    ヘキサゴナルApplication Core ／ Port ／ Adapter中心の コア と、外側を差し替える アダプタ を明示
    オニオンDomain Model ／ Application Service ／ Infrastructureコアを 同心円の層 として名前付け
    クリーンEntities ／ Use Cases ／ Interface Adapters ／ Frameworksヘキサゴナル・オニオン・DDD の部品名を 1セットに統合
    EDAイベント発行者 ／ ブローカー ／ 購読者部品の境界が プロセス・サービスをまたぐ 単位へ
    マイクロサービス注文・在庫・ユーザー…などの 独立サービス1つのアプリ内のモジュールから、デプロイ単位 そのものが部品になる

    流れの要約：「1塊のコード」→「UI 用の3分割」→「サーバー側の層」→「ビジネス概念（ドメイン）」→「差し替え可能な外側」→「サービス単位の分割」。

    14-2. 関係性（依存・通信・データの流れ）— 「どうつなぐか」

    段階主な関係性変化のポイント
    スパゲッティどこからでもどこへでも参照依存の向きが 無秩序
    MVCView ⇄ Controller ⇄ Model関心ごと に経路を分ける
    3層上の層 → 下の層（一方向の呼び出し）層をまたぐ依存 をルール化
    MVPView → Presenter → Model（View は受け身）View と Model の 直接結合を禁止
    DDDドメインモデルが中心、コンテキスト間は明示的に連携部品間の関係を 業務の境界 で定義
    MVVMView ⇄ ViewModel（データバインディング）→ Model双方向の自動同期 で手動更新を減らす
    ヘキサゴナル外側 → Port → Core（依存の向きを逆転）DB・UI がコアに 直接触れない
    オニオン ／ クリーンすべての依存が 内側（ドメイン）へ依存性逆転（DIP）を アーキテクチャの前提 にする
    EDA発行者 → イベント → 購読者（非同期・疎結合）呼び出し元は 相手の存在を知らなくてよい
    マイクロサービスAPI（同期）＋イベント（非同期）でサービス間を連携関係性の単位が プロセス境界 に拡大

    流れの要約：密結合 → 役割ごとの経路 → 層の一方向 → 内側への依存集中 → イベントによる疎結合 → 分散システム間の連携。

    14-3. 原則・制約（ルール）— 「何を守るか」

    段階主な原則・制約変化のポイント
    スパゲッティ（暗黙のルールもない）変更の影響範囲が 予測不能
    MVC関心の分離 — 見た目とデータ処理を分けるアーキテクチャの 最初の明示的なルール
    3層層の責務の固定 — DB はデータ層だけ、など「どこに何を書くか」を チームで共有
    MVPView は 描画だけ、ロジックは PresenterUI をテスト可能にする 役割の縛り
    DDDユビキタス言語、境界づけられたコンテキスト技術のルールに加えて ビジネス用語を統一
    MVVMView にロジックを書かない、バインディング経由フレームワーク前提の UI 更新ルール
    ヘキサゴナル外側は内側に合わせる、Port 経由のみインフラの差し替えを 設計段階で保証
    オニオン ／ クリーン依存は常に内側へ、フレームワークは詳細変更に強い中心（Entities）を 最優先
    EDA結果整合性、イベントは過去形で表現する同期処理の 即時一貫性 を手放す代わりに拡張性を得る
    マイクロサービスデータ所有権、独立デプロイ、サービスの自律チーム・リリース単位という 組織的な制約 も含む

    流れの要約：ルールなし → 分離・層の責務 → ドメイン中心・依存逆転 → 分散環境での整合性と自律性。

    14-4. 3要素を横断で見る — 各アーキテクチャは何を変えたか

    各アーキテクチャは、3要素のうち どこを主に変えたか が異なります（◎＝主に変えた、○＝変えた）。

    アーキテクチャコンポーネント関係性原則・制約主な焦点
    MVC ／ MVP ／ MVVM◎○○UI まわりの部品分割
    3層○◎○サーバー側の層と呼び出し方向
    DDD◎○◎部品の意味をビジネスに合わせる
    ヘキサゴナル ／ オニオン ／ クリーン○◎◎依存の向きと差し替え可能性
    EDA○◎○システム間のつなぎ方
    マイクロサービス◎◎◎3要素すべてをサービスの粒度で再定義

    覚え方

    歴史上の「新しいアーキテクチャ」は、毎回3要素すべてを発明したわけではありません。多くは 前の時代の弱点（Controller の肥大化、DB への依存、同期の連鎖…）を、3要素のどこか1〜2か所で補正した結果 です。だから「最新＝全部が新しい」ではなく、「今の課題が3要素のどこにあるか」で選ぶ のが実務的です。

    15.よくある誤解

    誤解実際
    新しいアーキテクチャほど優れている多くは前の時代の弱点を3要素の1〜2か所で補正したもの。小さなアプリにマイクロサービスやクリーンは不要なことが多い
    年表の年は「発明された年」名前が広まった時期の目安。考え方の源流はもっと前からあることが多い（EDA は特に期間が長い）
    DDD はアーキテクチャスタイルの1つアーキテクチャそのものというより設計の考え方。クリーン・オニオンなどと組み合わせて使う
    ヘキサゴナル・オニオン・クリーンはまったく別物「ドメインを中心に置き、依存を内側へ向ける」という思想はほぼ同じで、違いは主に用語と図の描き方
    MVC やクリーンとマイクロサービスは、どれか1つを選ぶもの扱うズームが違う。マイクロサービスの中身をクリーン＋DDD で書き、API 層は MVC、サービス間は EDA、のように組み合わせる
    MVC の図は1種類元祖 Smalltalk MVC（View が Model を監視）と、Web フレームワークの MVC（Controller が仲介）では矢印が違う

    16.まとめ — 歴史は「課題の積み重ね」

    ここまでの流れを1本にまとめると、次のようになります。各アーキテクチャは、前の段階で残った課題に答える形で登場してきました。

    3つの軸で整理すると分かりやすい

    軸該当するアーキテクチャ主な問い
    UI の分離MVC、MVP、MVVM画面とロジックをどう分けるか
    モノリス内の構造3層、DDD、ヘキサゴナル、オニオン、クリーンビジネスルールをどこに置き、何に依存させるか
    システム間の連携EDA、マイクロサービスサービスをどう分け、どうつなぐか

    この3つの軸は、14章の コンポーネント・関係性・原則 のどこを主に変えたか、という見方とも対応します。UI の分離は「部品と関係性」、モノリス内の構造は「関係性と原則」、システム間の連携は「関係性と部品の粒度」を主に変えてきました。

    初心者が覚えておくとよいこと

    1. 新しいほど良いわけではない

    小さなアプリに、マイクロサービスやクリーンアーキテクチャは不要なことが多いです。

    2. 組み合わせて使う

    例：マイクロサービスの中身はクリーン＋DDD、API 層は MVC、サービス間は EDA。

    3. すべてはトレードオフ

    修正しやすさ、性能、運用コスト、チーム構成で選び方が変わります（トレードオフとアーキテクチャに効く原則）。
