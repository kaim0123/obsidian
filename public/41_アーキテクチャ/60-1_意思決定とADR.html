    60 意思決定・文書化

    意思決定の進め方と ADR

    アーキテクチャを「どう決め、どう残し、どう確かめるか」の入口です。何をアーキテクチャ決定とみなすか、決め方のアンチパターン、リスクの洗い出しを押さえたうえで、決定を短く残す ADR（Architecture Decision Record）の書き方・ステータス・置き場所を、テンプレート例つきで詳しく解説します。

    もとにしたノート：60_意思決定・文書化/01_意思決定と進化.md、02ADRとArchitecture Decision Record.md、00_解説_意思決定・文書化.md

    1.このページで扱うこと

    10〜50 番台のページでは、どんな構造にするか（層、ドメイン、分散、横断的関心事）を学んできました。60 番台では視点を変えて、その構造をどう決め、どう記録し、どう確かめ、どう変えていくかというプロセスと記録を扱います。

    アーキテクチャは「一度描いたら終わり」ではありません。チームが変わり、要件が変わり、技術が変わるなかで、なぜそうしたかを残し、いつ直すかを意識することが長期保守の鍵です。この 60 番台も概要レベルで、アーキテクト専門職の代わりではなく、「設計会議で何を話し、何を残すか」の地図を押さえることが目的です。

    境界の目安：「どう書くか（道具・書式）」は 56、「アーキテクチャの何を、なぜ残すか」は 60 です。ADR を Markdown で書くときの記法は 56、ADR に何を書くべきかは 60 に置きます。

    前提：アーキテクチャとは・設計との違い、品質特性と非機能要件、トレードオフとアーキテクチャに効く原則

    2.意思決定と進化とは

    意思決定 — トレードオフのなかで選んだ道

    意思決定とは、トレードオフのなかで選んだ道のことです。

    • モノリスにするか、サービスを分けるか
    • 同期 API か、イベント駆動か
    • 認証をゲートウェイに集約するか、各サービスで行うか

    これらは「正解が1つ」ではなく、状況・制約・優先順位によって変わります。だからこそ、なぜその選択をしたかを残す（ADR）ことが重要になります。

    進化 — アーキテクチャは時間とともに変わる

    「最初から完璧な設計」は現実にはほとんどありません。測定できる指標とレビューの習慣を持ち、必要なときに形を変えられるようにするのが進化的アーキテクチャの考え方です（詳しくは 進化的アーキテクチャと適応度関数）。

    なぜプロセスと記録を学ぶのか

    構造パターンだけを学ぶと、次のような落とし穴に入りやすくなります。

    問題典型例
    理由が消える「昔そう決めた」が誰も覚えておらず、同じ議論を繰り返す
    暫定案が永久化「とりあえず」の実装が、リファクタ予定のないまま残る
    組織と設計のズレマイクロサービスを目指したが、チーム構成がモノリス向きのまま
    レビューが表面的図はきれいだが、障害時の運用や非機能要件が抜けている

    目標

    ジュニアでも「この決定、ADR に書きませんか？」「この暫定案、いつ直すか決めましょう」と言えるようになることです。

    決める → 残す → 見せる → 確かめる のループ

    初心者が覚えておきたい3つのこと

    1. 決定には理由を残す — 結論だけでなく、検討した選択肢とトレードオフを短く書く（このページの ADR）。
    2. 暫定案は「暫定」と決める — 借金をゼロにする必要はないが、意図・期限・直し方をセットにする（技術的負債と意図的な暫定案）。
    3. レビューは4つの観点で — きれいな図だけでなく、境界・非機能・運用まで見る（アーキテクチャのレビュー観点）。

    おすすめの読み順は、このページ（記録）→ 技術的負債（負債の扱い）→ レビュー観点（実践）です。チーム編成や組織設計に関心がある場合は、技術的負債のあとに コンウェイの法則と Team Topologies を読むとつながります。

    3.アーキテクチャ決定とは何か

    アーキテクチャ決定とは、あとから変えるのが高くつく、システム全体の形に効く選択のことです。『ソフトウェアアーキテクチャの基礎』（Mark Richards ＆ Neal Ford）では、次のいずれかに当てはまる決定を「アーキテクチャ上重要（architecturally significant）」とみなします。

    観点例
    構造レイヤードにするか、マイクロサービスにするか
    非機能特性可用性 99.9% を満たすために冗長化する
    依存関係サービス間を同期 API でつなぐか、イベントでつなぐか
    インターフェース外部公開 API を REST にするか GraphQL にするか
    構築手法特定のフレームワークやクラウドサービスを全社標準にする

    逆に、「関数名をどうするか」「どのループ構文を使うか」はアーキテクチャ決定ではありません（アーキテクチャとは・設計との違い）。

    決め方のアンチパターン

    同書では、決定をめぐる3つの典型的な失敗が紹介されています。

    Covering Your Assets（保身）

    症状：間違えるのが怖くて、決定を先延ばしにする。

    対策：「最後に責任を持てる時点（last responsible moment）」まで待ち、そこで決める。開発者と協働して決定を検証する。

    Groundhog Day（毎日が同じ日）

    症状：同じ議論が何度も繰り返される。

    対策：決定の理由（技術的理由とビジネス上の理由の両方）を必ず残す。

    Email-Driven Architecture（メール駆動）

    症状：決定がメールやチャットに埋もれ、誰も見つけられない。

    対策：決定は1か所（ADR など）にまとめ、通知ではリンクだけを送る。

    2番目と3番目の対策が、そのまま次の ADR につながります。

    4.リスク分析 — 決める前に「何が困るか」を洗い出す

    アーキテクチャの仕事の多くは、「何がうまくいかない可能性があるか」を先に見つけることです。『ソフトウェアアーキテクチャの基礎』では、2つの道具が紹介されています。

    リスクマトリクス

    リスクを影響度 × 発生可能性の2軸で、それぞれ 1（低）〜3（高）で評価し、掛け算で点数にします。

    影響度 ＼ 可能性低 (1)中 (2)高 (3)
    高 (3)369
    中 (2)246
    低 (1)123
    • 1〜2 低リスク（緑）
    • 3〜4 中リスク（黄）
    • 6〜9 高リスク（赤）

    評価するときは、まず影響度を考え、次に可能性を考えるのがコツです。これを「サービス × 品質特性（可用性・拡張性・性能…）」の表にすると、どこが危ないかが一目で分かるリスク評価表になります。

    リスクストーミング

    一人で評価すると見落としが出るため、チームで行う共同作業がリスクストーミングです。Simon Brown（C4 モデルの考案者）が広めた手法で、次の3段階で進めます。

    1. 識別（個人作業） — アーキテクチャ図を見ながら、各自が付箋にリスクと点数を書く。
    2. 合意（全員） — 付箋を図に貼り、点数が食い違うところを話し合う。食い違いこそ、メンバー間の知識の差を表している。
    3. 軽減（全員） — 高リスクの箇所について、対策とそのコストを検討する。

    観点を1つに絞る

    一度に全部を対象にせず、「今日は可用性だけ」のように観点を1つに絞ると議論が深まります。

    5.ADR とは

    設計会議で「REST にしよう」「DB は PostgreSQL にしよう」と決まっても、半年後には誰も理由を覚えていないことがよくあります。ADR（Architecture Decision Record）は、そうしたアーキテクチャ上の重要な決定を、1つの決定につき1枚の短い文書として残す形式です。2011年に Michael Nygard がブログ記事「Documenting Architecture Decisions」で提案し、現在では多くのチームが使っています。

    要素英語でよく使う語書く内容
    状況Context何が問題で、どんな制約があるか
    決定Decision何を選んだか（はっきりと）
    結果Consequences得られるメリット・受け入れるデメリット
    1. 状況：チームは3人、リリースは2週間後
    2. 検討：モノリス／マイクロサービス／モジュラーモノリス
    3. 決定：まずモノリス＋モジュール境界を明確に
    4. 結果：デプロイは単純。将来分離するときの境界は意識済み

    ADR は設計書全体ではない

    「この論点について、こう決めた」という1枚（または数段落）の記録です。

    なぜ ADR を書くのか

    メリット説明
    同じ議論の繰り返しを減らす過去の前提が読める（Groundhog Day 対策）
    新人・異動者のオンボーディング「なぜこうなっているか」が追える
    決定の見直しがしやすい状況が変わったとき、「当時の前提はまだ有効か」と比較できる
    トレードオフが可視化される「安易に変えない理由」が残る

    アーキテクチャの仕事は、コードを書くことだけではなく、チームの記憶を外部化することでもあります。ADR はそのための軽量な道具です。

    6.ADR のテンプレートと記入例

    基本構成

    節書く内容
    タイトル通し番号＋決定を一言で（例：ADR-007: 注文通知を非同期イベントで送る）
    ステータス今この決定がどの段階にあるか
    状況（Context）なぜこの論点が生まれたか、制約は何か
    決定（Decision）何を選んだか。「〜する」と言い切る
    結果（Consequences）良くなること、受け入れる悪いこと

    余裕があれば「検討した選択肢」「見直し条件」を加えると、後から読む人が判断を追いやすくなります。形式はチームごとに多少違いますが、初心者には次の2例のような構成が扱いやすいです。

    記入例1：注文と在庫を同一モノリスに置く

    docs/adr/0001-use-monolith-for-order-inventory.md 
    # ADR-001: 注文と在庫を同一モノリスに置く

## 状況
- 初期メンバー3名、MVP を3ヶ月でリリースしたい
- 注文と在庫は密に連携する（在庫引当は注文確定と同一トランザクション）
- 運用チームはまだ専任なし

## 検討した選択肢
1. モノリス（モジュール分割あり）
2. 注文・在庫を別サービス + 同期 API
3. イベント駆動で非同期連携

## 決定
選択肢1を採用する。パッケージ（またはモジュール）で注文・在庫の境界は分ける。

## 結果
### 良いこと
- ローカル開発・デプロイが単純
- トランザクション境界が明確

### 受け入れること
- 将来サービス分割するとき、データ移行と API 切り出しが必要
- スケールはアプリ全体単位になる

## ステータス
Accepted（2025-06-01）

## 関連
- 見直し条件: DAU 10万超、または在庫チームが独立したとき

    記入例2：注文完了の通知を非同期イベントで送る

    docs/adr/0007-publish-order-completed-event.md 
    # ADR-007: 注文完了の通知を非同期イベントで送る

## ステータス
Accepted（2026-09-25）

## 状況
- 注文完了時にメール・在庫・ポイントの3処理を同期で呼んでいる
- メール送信の遅延で注文 API のレスポンスが 3 秒を超えることがある
- チームにはメッセージキューの運用経験が少ない

## 検討した選択肢
1. 現状維持（同期呼び出し）
2. 非同期イベント（マネージドなキューを使う）
3. メール送信だけバックグラウンドジョブに移す

## 決定
選択肢2を採用する。注文サービスは「注文完了」イベントを発行するだけにする。

## 結果
- 良い: 注文 API の応答が通知処理に左右されなくなる
- 受け入れる: 通知は数秒遅れることがある（結果整合性）
- 受け入れる: キューの監視・デッドレターの運用が新たに必要

## 見直し条件
- イベントの種類が 20 を超えたら、スキーマ管理の方式を再検討する

    どちらの例も、状況に制約（人数・期限・運用経験）が書かれていること、採らなかった選択肢が残っていること、結果に「受け入れる悪いこと」が正直に書かれていることがポイントです。これがあるから、後で読んだ人が「前提が変わったので見直そう」と判断できます。

    7.ステータスとライフサイクル

    ステータス意味
    Proposed提案中・議論中
    Accepted採用された
    Rejected検討の結果、却下された（却下した理由も記録として価値がある）
    Deprecated原則として使わない（新規は別方針）
    Superseded別の ADR に置き換えられた

    古い ADR は書き換えない・消さない

    決定を変えるときは、古い ADR を書き換えたり消したりしません。新しい ADR を作り、古い方のステータスを「Superseded by ADR-012」とし、相互にリンクします。こうすると「なぜ変えたか」の歴史が残ります。

    8.何を ADR にするか

    すべての細かい判断を書く必要はありません。目安は次のとおりです。

    ADR に向くこと

    • 変更コストが高い（DB 選定、認証方式、モノリス／分散の方針）
    • チーム全体に影響する（API スタイル、エラーハンドリング方針）
    • 反対意見や代替案があった（トレードオフがはっきりしている）

    ADR にしなくてよいこと

    • 1ファイル内の実装詳細（通常はコードレビューやコメントで足りる）
    • フレームワークの公式推奨どおりの使い方だけの話
    • すぐ戻せる一時的な実験（ただし本番に残るなら ADR または暫定案メモを検討）

    迷ったときの問い

    「6ヶ月後に、この決定を説明できるか？」と自問します。説明できる自信がなければ書きます。「迷ったら書く」くらいでよく、書かずに後悔する方がずっと高くつきます。

    認証方式やログ基盤の選定（横断的関心事と認証・認可）、モノリスかマイクロサービスか（モノリス・分散モノリス・マイクロサービス）は、ADR の典型的な題材です。

    9.どこに置き、どう運用するか

    置き場所向き
    リポジトリ内 docs/adr/コードと一緒にバージョン管理・レビューできる（よく使われる）
    Wiki／Notion非エンジニアも読みやすい
    設計専用リポジトリ複数サービスにまたがる決定を集約する
     
    docs/
└── adr/
    ├── 0001-use-monolith-for-order-inventory.md
    ├── 0002-use-postgresql.md
    ├── ...
    └── 0007-publish-order-completed-event.md

    運用のコツ

    • ファイル名に番号を振ると時系列が追いやすくなる（例：0001-use-monolith-for-order-inventory.md）
    • 1ファイル1決定、短く（1〜2ページ）
    • PR の説明から ADR へリンクする。チャットやメールで通知するときもリンクだけを送る（Email-Driven Architecture 対策）
    • ADR の Proposed 段階を、そのままアーキテクチャレビューの場にする
    • 文書全体の構成に組み込むなら、arc42 の「9. アーキテクチャ決定」節に ADR の一覧を置く（図と文書化（C4 モデル・arc42））

    10.初心者がつまずきやすい点

    長く書きすぎる

    ADR は短くが原則です。1〜2ページ以内を目安に、決定とトレードオフに集中します。詳細設計は別のドキュメントへ回します。

    決定だけ書いて状況がない

    「PostgreSQL を使う」だけでは、将来「なぜ MySQL ではなかったのか」が分かりません。当時の制約（チームのスキル、既存の契約、性能要件）を1段落でよいので残します。

    書いたあと放置する

    ADR は生きた文書です。前提が変わったら、新しい ADR で更新・置き換えます。技術的負債と意図的な暫定案 と組み合わせ、「暫定で受け入れた決定」の見直し日や見直し条件を ADR に書いておくことも有効です。

    11.よくある誤解

    誤解実際
    ADR は詳細な設計書のこと1つの決定を状況・決定・結果で残す短い記録。詳細設計は別文書
    決定が変わったら ADR を書き直せばよい古い ADR は残し、新しい ADR で Superseded にしてリンクする
    結論さえ書けば十分状況（制約）と検討した選択肢がないと、見直しの判断ができない
    間違えないように、決定はできるだけ先延ばしにするそれは Covering Your Assets。最後に責任を持てる時点で決め、記録して見直せるようにする
    決まったことはチャットで共有すれば伝わる流れて見つからなくなる（Email-Driven Architecture）。1か所に残してリンクを送る

    12.まとめ

    覚えること内容
    アーキテクチャ決定あとから変えるのが高くつく選択（構造・非機能特性・依存関係・インターフェース・構築手法）
    アンチパターン保身（先延ばし）、毎日が同じ日（理由が残らない）、メール駆動（埋もれる）
    リスク分析影響度 × 可能性のマトリクス。チームで行うならリスクストーミング
    ADR とはアーキテクチャの1つの決定を、状況・決定・結果で残す短い記録
    目的記憶の共有、議論の短縮、見直しのしやすさ
    書き方短く、代替案とトレードオフ、見直し条件を含める
    更新変えたら新しい ADR で Superseded。消さない
