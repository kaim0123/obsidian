    閉じた層と開いた層・シンクホール

    「何もしない層まで全部通す必要があるのか」「共通処理はどこに置くのか」——レイヤードアーキテクチャを実務で使うと必ず出てくる疑問に答えます。閉じた層・開いた層、隔離層、アーキテクチャ・シンクホールと 80/20 ルール、そしてレイヤードの★評価がなぜ低いのかを、Mark Richards の整理に沿って解説します。

    もとにしたノート：02_閉じた層と開いた層_隔離層とシンクホール（＋ 00_解説_アプリ内部構造）

    1.このページで扱うこと

    層化・三層・レイヤード（4層） では、「上の層は下の層だけを使う」という基本ルールを学びました。しかし実務では、すぐに次のような疑問にぶつかります。

    • 画面に一覧を出すだけなのに、Controller → Service → Repository と何もしない層を全部通す必要があるのか
    • 「共通処理」はどの層に置けばよいのか
    • 「素通りの層」はどのくらいまで許されるのか

    このページでは、『ソフトウェアアーキテクチャの基礎』と『Software Architecture Patterns』（Mark Richards）で整理されている次の考え方を解説します。

    • 閉じた層と開いた層
    • 隔離層（Layers of Isolation）という考え方
    • アーキテクチャ・シンクホールアンチパターンと80/20 ルール
    • レイヤードアーキテクチャの★評価の理由と、向いている場面・向いていない場面

    2.閉じた層と開いた層

    2.1 閉じた層（Closed Layer）

    リクエストは、閉じた層を飛ばして下に進めない、というルールです。

    • プレゼンテーション層が DB のデータを欲しくても、必ずビジネス層・永続化層を順に通る
    • これがレイヤードアーキテクチャの標準です

    2.2 開いた層（Open Layer）

    その層を飛ばして、さらに下の層に直接アクセスしてよい、というルールです。典型例は共通サービス層です。

    • 共通サービス層（ログ・監査・暗号化・日付処理など）を、ビジネス層の下に置く
    • この層を開いた層にすると、ビジネス層は共通サービスを使いたいときだけ使い、使わないときは飛ばして永続化層に行ける
    • 共通サービスをビジネス層からしか使えないようにする（プレゼンテーション層から直接使わせない）という制約も表現できる

    2.3 どちらを選ぶか

    閉じた層開いた層
    依存の範囲1つ下の層だけ2つ以上下の層にも依存できる
    変更の影響1つ上の層にしか広がらない飛ばして使っている層すべてに広がる
    素通りの手間多い少ない
    向いている層主要な層（プレゼンテーション・ビジネス・永続化）補助的な層（共通サービス・ユーティリティ）

    いちばん大切なのは「明文化」

    どの層が開いていて、どの層が閉じているかを、チームで明文化しておくことが最も大切です。曖昧なままだと開発者ごとに判断がばらつき、層の意味がなくなります。決めたことは ADR に残し（→ 意思決定の進め方と ADR）、アーキテクチャテストで検査します。

    3.隔離層（Layers of Isolation）

    3.1 考え方

    ある層の変更が、他の層に影響しない状態を隔離層と呼びます。

    • 永続化層で SQL を ORM に書き換えても、ビジネス層・プレゼンテーション層は影響を受けない
    • プレゼンテーション層で画面フレームワークを変えても、ビジネス層は影響を受けない

    3.2 閉じた層が隔離を生む

    隔離層が成り立つのは、層が閉じているからです。

    • プレゼンテーション層が永続化層に直接アクセスしていたら、SQL の変更がプレゼンテーション層にまで及ぶ
    • 層が閉じていれば、永続化層の変更の影響はすぐ上のビジネス層で止まる

    トレードオフ

    閉じた層を増やすほど隔離は強まるが、素通りの手間も増える。これが次のシンクホールの問題につながります。

    4.アーキテクチャ・シンクホール アンチパターン

    4.1 シンクホールとは

    リクエストが、どの層でも何の処理もされずに、ただ素通りしていく状態です。「シンクホール（陥没穴）」のように、リクエストがそのまま下に落ちていくイメージです。

    ✕ シンクホールの例 
    // Controller：受け取って渡すだけ
class UserController {
  getUser(id: string) {
    return this.userService.getUser(id);
  }
}

// Service：受け取って渡すだけ
class UserService {
  getUser(id: string) {
    return this.userRepository.findById(id);
  }
}

// Repository：ここで初めて仕事をする
class UserRepository {
  findById(id: string) {
    return db.query("SELECT * FROM users WHERE id = ?", [id]);
  }
}
    • Controller と Service は何もしていない
    • それでもファイルが3つ必要で、テストも3つ、変更時の修正箇所も3つになる

    4.2 80/20 ルール

    Richards は、シンクホールがある程度あるのは自然だとしています。判断の目安が80/20 ルールです。

    状態判断
    リクエストの約 20% がシンクホール許容範囲 単純な参照系があるのは普通
    リクエストの約 80% がシンクホール要見直し レイヤードアーキテクチャがこのアプリに合っていないサイン

    4.3 80% がシンクホールだったら

    1. 一部の層を開く：参照系だけビジネス層を飛ばしてよい、と明文化する
    2. 層を減らす：業務ロジックがほぼない CRUD アプリなら、2層（Controller ＋ Repository）で十分なこともある
    3. 別のスタイルを検討する：機能ごとに必要な層が違うなら、垂直スライスアーキテクチャ のように「機能ごとに必要なだけ層を持つ」構成も選択肢になる。読み取りだけ別の作り方にしたいなら CQRS も候補

    層は手段

    「何もしない Service」が大量にあるのは、層の数を目的にしてしまった典型的な状態です。層は手段であり、仕事をしない層は削ってよい、という判断も立派な設計です。

    5.層が抱えやすいその他の問題

    問題症状対策
    層の飛び越し（明文化されていない）プレゼンテーション層から Repository を直接呼ぶコードが少しずつ増える開いた層・閉じた層を明文化し、アーキテクチャテスト（ArchUnit、dependency-cruiser など）で検査する
    ロジックの染み出し業務ルールが Controller や画面に書かれる業務ルールはビジネス（ドメイン）層、と明確にする（→ MVC（MVC 違反））
    巨大な層ビジネス層に全機能のサービスが集まり、数千行のファイルになる層の中をドメイン（機能）ごとに分ける
    技術で分けたことによる変更の分散「注文に割引を追加」で全層を修正する層の中を機能で分ける、または垂直スライスを検討する
    補足：アーキテクチャテストの例（dependency-cruiser）

    JavaScript／TypeScript なら dependency-cruiser、Java なら ArchUnit で「この層からあの層への import を禁止する」ルールをテストとして書けます。次は dependency-cruiser の設定のイメージです（ディレクトリ名はプロジェクトに合わせて読み替えてください）。

    // .dependency-cruiser.js（イメージ）
module.exports = {
  forbidden: [
    {
      name: "presentation-must-not-use-persistence",
      comment: "プレゼンテーション層から永続化層を直接使わない（閉じた層）",
      severity: "error",
      from: { path: "^src/presentation" },
      to:   { path: "^src/persistence" }
    }
  ]
};

    CI でこのチェックを回せば、「明文化したルール」が少しずつ崩れていくのを機械的に防げます。

    6.レイヤードアーキテクチャの★評価の理由

    MOC のスタイル比較表で、レイヤードは次のように評価されています（『ソフトウェアアーキテクチャの基礎』）。

    特性★理由
    手軽さ・コスト★★★★★最もよく知られた形で、多くの FW がこの形を前提にしている
    シンプルさ★★★★★構造が直感的で、学習コストが低い
    デプロイ容易性★1つのデプロイ単位。小さな変更でも全体を再デプロイする
    テスト容易性★★層ごとのテストはできるが、変更のたびに全体の回帰テストが必要になりがち
    拡張性（スケール）★全体をまとめてしかスケールできない
    耐障害性★1か所のメモリ不足やバグで全体が落ちる
    進化しやすさ★技術で分割しているため、業務の変更が全層に散らばる

    テスト容易性は資料によって★1〜2と揺れがあります。書籍の評価はデプロイ単位全体に対するもので、「3行の変更でも全体を再デプロイする」ためにデプロイ容易性・テスト容易性が低く評価されています。

    ポイントは、低い★の多くが「1つのデプロイ単位であること」と「技術で分割していること」から来ていることです。

    「1つのデプロイ単位」から来るもの

    デプロイ容易性・拡張性・耐障害性。アプリ内部の構造をどう工夫しても改善しません。→ 分散とスタイル など 40 システム・分散 のスタイルの領域です。

    「技術で分割」から来るもの

    進化しやすさ。層の中を機能で分ける、クリーンアーキテクチャで依存を整理する、垂直スライスにする、などで改善できます。

    参考までに、MOC ではクリーン・ヘキサ・オニオンを次のように評価しています（書籍に評価がないため独自の目安）。1つのデプロイ単位である点はレイヤードと同じなので、デプロイ・スケール・耐障害性は変わりません。一方、ドメインを DB なしでテストでき、外側の技術を差し替えやすいぶん、テスト容易性・進化しやすさが上がり、層とインターフェースが増えるぶんシンプルさ・コストが下がっています。

    スタイル手軽さ・コストシンプルさデプロイテスト拡張性耐障害性進化
    レイヤード★★★★★★★★★★★★★★★★
    クリーン・ヘキサ・オニオン★★★★★★★★★★★★★★★

    6.1 レイヤードが向いている場面

    • 小規模なアプリ、予算や期間が限られたプロジェクト
    • 最初の一歩として、アーキテクチャがまだはっきりしないとき（後から別のスタイルに移る前提で）
    • チームのメンバーがレイヤードに慣れている

    6.2 向いていない場面

    • 大規模で、多くのチームが同時に開発する
    • 部分ごとに必要なスケール・可用性が大きく違う
    • 業務の変更が頻繁で、変更のたびに全層を触っている

    7.よくある誤解

    「層は必ず全部通らなければならない」

    誤りです。補助的な層を開いた層にするのは正当な設計です。大事なのは、どの層が開いているかを明文化することです。

    「何もしない層があるのは悪い設計」

    半分だけ正しいです。2割程度のシンクホールは自然です。8割を超えたら、構成を見直すサインです。

    「層を守れば保守性は自動的に上がる」

    誤りです。層は技術で分けているので、業務の変更は複数の層にまたがります。レイヤードの「進化しやすさ」が★1なのはそのためです。

    8.まとめ

    • 閉じた層：飛ばせない層。隔離を生む。主要な層は閉じるのが基本
    • 開いた層：飛ばしてよい層。共通サービス層などの補助的な層に使う
    • 隔離層：ある層の変更が他の層に影響しない状態。閉じた層によって成り立つ
    • シンクホール：何もしない層を素通りするリクエスト。20% なら許容、80% なら構成を見直す（80/20 ルール）
    • どの層が開いていて閉じているかを明文化し、ツールで検査する
    • レイヤードの低い★は「1つのデプロイ単位」と「技術での分割」から来ている
