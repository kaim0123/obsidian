    40 システム・分散

    サーバーレス

    サーバーレスは「サーバーをなくす」技術ではなく、構築・監視・パッチ適用・スケーリングといったサーバー管理をクラウドに任せ、必要なときだけ処理を動かす実行モデルです。このページでは、仕組み（イベントで起動し、終われば消える関数）、注目される理由、4つのメリットと5つの落とし穴、向いている場面と向かない場面、そして小さく始める方法を整理します。

    テーマ

    サーバーレスは「サーバー管理をクラウドに任せる」仕組みであり、万能ではありません。向き不向きを理解して、合う部分から小さく選ぶものです。

    2.サーバーレスとは何か

    2-1. 従来のサーバー運用で起きていたこと

    従来、アプリを動かすには、サーバーを構築し、OS をインストールし、ミドルウェアを設定し、アプリをデプロイする必要がありました。さらに、落ちないように監視し、セキュリティパッチを当て、負荷が増えたらスケーリングもしなければなりません。アプリを動かすために、アプリとは関係ない作業が大量に発生していたわけです。

    サーバーレスは、これらの作業をクラウドに任せる仕組みです。名前は「サーバーレス（サーバーなし）」ですが、サーバーがなくなるわけではありません。サーバーは存在しますが、自分で管理する必要がなくなるのです。

    作業自前のサーバー（オンプレミス・仮想マシン）サーバーレス
    サーバーの構築・OS インストール自分クラウド
    ミドルウェア・ランタイムの設定自分クラウド（言語・バージョンを選ぶだけ）
    セキュリティパッチの適用自分クラウド
    監視・障害対応（サーバー自体）自分クラウド
    スケーリング自分（事前に台数を増やす）クラウドが自動で行う
    アプリのコード自分自分
    課金起動している時間に対して（使っていなくても）実行した分だけ

    代表的なサービスは AWS Lambda、Google Cloud Functions（現在は Cloud Run functions として提供）、Azure Functions です。

    2-2. FaaS と BaaS

    サーバーレスという言葉は、広い意味では次の2種類をまとめて指します（Mike Roberts による martinfowler.com の記事「Serverless Architectures」の整理）。

    FaaS（Function as a Service）

    自分で書いた関数（処理）を、イベントに応じてクラウドが実行してくれるサービス。AWS Lambda、Azure Functions など。動画で主に扱っているのはこちらです。

    BaaS（Backend as a Service）

    DB・ストレージ・認証などのバックエンド機能を、サーバー管理なしで使えるサービス。DynamoDB、Firestore、S3、Firebase Authentication など。

    実際のサーバーレス構成は、FaaS で処理を書き、データやファイルは BaaS（マネージドサービス）に置く、という組み合わせになります。

    3.サーバーレスの仕組み（実行モデル）

    3-1. 必要なときだけ起動し、終わったら消える

    EC サイトで「注文が入ったら在庫を減らす」処理を考えます。従来なら、この処理を動かすサーバーを 24 時間起動しておく必要がありました。注文がなくてもサーバーは動き続けます。サーバーレスでは、リクエスト（イベント）が来た瞬間だけ処理が起動し、処理が終わったら消えます。注文がなければ何も動いていません。

    1. イベントが届く：HTTP リクエスト、ファイルのアップロード、決まった時刻、キューへのメッセージなどが、関数を起動するきっかけ（トリガー）になります。
    2. 起動：実行用の環境がなければ、クラウドが新しく用意してコードを読み込みます。この初回の準備にかかる時間がコールドスタートです。
    3. 実行：関数のコードが処理を行い、結果を返したり、DB に書き込んだりします。
    4. 待機と破棄：実行後の環境はしばらく保持され、続けて来たリクエストはすぐに処理されます（ウォームスタート）。使われない状態が続くと破棄されます。

    同時に多くのリクエストが来れば、クラウドは実行環境を並列に増やします。これが「何もしなくても勝手にスケールする」仕組みです。

    3-2. 処理が終わったら消えるなら、データはどこへ？

    サーバーレス（FaaS）は、あくまで処理を実行する部分の話です。データの保存先は別に用意します。ただし、その DB もサーバーを自分で管理しないマネージドサービスを使うことが多く、AWS なら DynamoDB、Google なら Firestore が代表例です。「サーバーを自分で管理しない」という考え方が、DB にも広がっているのです。

    ユーザーが注文ボタンを押すと Lambda が起動して注文処理を実行し、DynamoDB に注文データを保存して在庫を減らし、S3 に領収書の PDF を保存します。処理が終われば Lambda は消えます。Lambda が処理のロジック、DynamoDB がデータの保存、S3 がファイルの保存というように、役割に合ったクラウドサービスを組み合わせて使うのがサーバーレスの基本形です。

    4.なぜサーバーレスが注目されているのか

    従来のサーバー運用では、構築・監視・パッチ適用・障害対応・スケーリングを全部自分たちでやる必要があり、インフラエンジニアがいないと回りませんでした。特に小さなチームやスタートアップにとって、この負担は大きなものです。エンジニアが3人しかいないのに1人がインフラの面倒を見ていて、本当はプロダクト開発に集中したいのにサーバーの障害対応に時間を取られる——という状況です。

    サーバーレスなら、サーバーの構築も監視もクラウドが担うので、エンジニアはアプリケーションのコードだけに集中できます。これがスタートアップや少人数チームに支持される最大の理由です。動画では、Netflix、コカ・コーラ、iRobot など大企業でも採用が進んでいる例が挙げられており、規模に関係なくメリットがある技術だとされています。

    アーキテクチャの観点で言えば、サーバーレスは「運用という非機能の仕事を、お金を払ってクラウドに外注する」選択です。分散システムの運用コスト（マイクロサービス・プレミアム）を下げる手段の1つとも言えます。

    5.4つのメリット

    1. インフラ管理が不要

    サーバーの構築・OS・パッチ・監視をクラウドに任せられる。チームの時間をプロダクト開発に回せる。

    2. 自動スケーリング

    アクセスが急増しても自動で対応する。従来は事前にサーバーを増やしておく必要があったが、テレビで紹介されてアクセスが殺到しても、クラウドが負荷に応じてリソースを調整する。

    3. 従量課金

    使った分だけ課金される。リクエストがなければコストはほぼ 0。平日の日中しか使わない社内システムなら、夜間・休日に 24 時間サーバーを動かしていた分が丸ごと節約できる。

    4. 開発スピードの向上

    インフラ設定に時間を取られず、すぐにコードを書き始められる。プロトタイプを素早く作りたいとき、アイデアを形にするまでが格段に速くなる。

    補足：「落ちる心配がほぼない」の注意点

    動画では「サーバーが落ちる心配がほぼない」と説明されていますが、正確には「サーバー自体の面倒を見なくてよい」ということです。同時実行数には上限（クォータ）があり、上限を超えるとリクエストが制限（スロットリング）されます。また、関数は自動でスケールしても、その先の DB や外部 API がついてこられずに詰まることがあります。スケールの上限と下流への影響は設計で確認しておきましょう。

    6.5つの落とし穴

    ここまで聞くと「全部サーバーレスにすればいい」と思えてきますが、そうではありません。

    6-1. コールドスタート

    サーバーレスでは、リクエストがないときは処理が停止しています。久しぶりにリクエストが来ると、起動に数百ミリ秒から、場合によっては数秒かかることがあります。普段は気にならなくても、リアルタイム性が求められるシステムでは問題になります。

    補足：AWS Lambda には、あらかじめ実行環境を温めておく Provisioned Concurrency（プロビジョニングされた同時実行）や、起動を速くする SnapStart といった緩和策があります。ただし、温めておく分は常時課金されるため、従量課金のメリットとのトレードオフになります。

    6-2. 実行時間の制限

    AWS Lambda の場合、1回の処理は最大 15 分までです。15 分を超える処理は動かせないため、動画のエンコード、大量データの一括処理、機械学習のトレーニングといった長時間の処理には向いていません。

    補足：長い処理は、小さなステップに分けてワークフローサービス（AWS Step Functions など）でつなぐか、コンテナ（AWS Fargate など）やバッチ用サービスで動かすのが一般的です。

    6-3. デバッグの難しさ

    クラウド上で動くため、ローカル環境で完全に再現するのが大変です。ローカルとクラウドで挙動が違うこともあり、ログを追いかけるのも従来のアプリより手間がかかります。関数が細かく分かれるほど、1つのリクエストが複数の関数とサービスを渡り歩くので、分散トレーシングなどの観測性の仕組みが重要になります。

    6-4. ベンダーロックイン

    AWS Lambda で作ったシステムを Google Cloud Functions に移すのは簡単ではありません。クラウドサービスごとにイベントの形式や設定・周辺サービスの仕様が違うため、書き直しが必要になります。一度選んだら乗り換えにくいと考えておくべきです。

    補足：業務ロジックをクラウド固有の API から切り離しておくと（ハンドラーは薄くし、中身は普通の関数やクラスにする）、移行や単体テストが楽になります。これは ヘキサゴナルアーキテクチャ の「アダプター」の考え方そのものです。

    6-5. コストの罠

    少量のリクエストなら安く済みますが、リクエスト数が膨大になると、従来のサーバーより高くつくことがあります。常に大量のリクエストが来るシステムなら、サーバーを立てたほうが安い場合もあります。サーバーレスが安いとは限りません。

    関連する事例

    2023 年には、Amazon Prime Video の映像品質監視サービスが、サーバーレス／分散構成を1プロセスにまとめてインフラコストを約90%削減した事例が話題になりました。コンポーネント間で大量のデータを受け渡す処理を、ネットワーク越しに細かく分けていたことが問題でした。「サーバーレスはダメ」という話ではなく、処理の性質に合った粒度を選ぶことの大切さを示す例です（40-2）。

    落とし穴のまとめ

    落とし穴何が起きるか主な対策・回避策
    コールドスタート久しぶりのリクエストで数百ミリ秒〜数秒の遅延事前に温める仕組み、軽いランタイム・小さなパッケージ、リアルタイム性が必要な処理には使わない
    実行時間の制限Lambda は1回最大 15 分処理を分割してワークフローでつなぐ、長時間処理はコンテナ・バッチへ
    デバッグの難しさローカル再現が難しく、ログ追跡が手間ロジックをクラウド API から分離して単体テスト、ログ・トレースの整備
    ベンダーロックイン他のクラウドへの移行に書き直しが必要ハンドラーを薄くし、業務ロジックを分離しておく
    コストの罠大量・常時のリクエストでは割高になりうる想定リクエスト数で試算し、常時高負荷ならサーバー・コンテナと比較する

    7.アーキテクチャから見たサーバーレス

    動画の内容を、41 アーキテクチャのほかのページとつなげて整理しておきます。

    7-1. 関数は「状態を持たない」前提で設計する

    実行環境はいつ破棄されるか分からず、同じ関数が並列に何個も動くため、関数の中に状態（セッションや一時ファイルなど）を残してはいけません。状態は DB やストレージに置きます。これが「処理とデータを分ける」構成になる理由です。

    7-2. イベント駆動との相性がよい

    「画像がアップロードされたらリサイズする」「ファイルが保存されたらメールを送る」というように、サーバーレスは「何かが起きたら処理を実行する」パターンと非常に相性がよい実行モデルです。そのため、イベント駆動・メッセージで学んだ注意点——同じイベントが2回届いても壊れない冪等性、失敗したイベントのリトライやデッドレターキュー——がそのまま当てはまります。

    7-3. スタイルではなく「実行モデル」

    サーバーレスは、モノリスやマイクロサービスのような「システムをどう分けるか」のスタイルというより、「処理をどこで、どう動かすか」という実行モデル・運用モデルの選択です。サーバーレスで細かい関数をたくさん作れば、マイクロサービスやイベント駆動と同じ分散の難しさ（データ所有権・整合性・観測性）を抱えることになります（40-4）。

    8.向いている場面・向かない場面

    向いている向かない
    API のバックエンド：リクエストが来たら処理して結果を返す。サーバーレスの得意分野長時間の処理：動画処理、大規模なデータ変換（15 分の制限）
    イベント駆動の処理：画像のアップロード時にリサイズ、ファイル保存時にメール通知リアルタイム通信：チャットやオンラインゲームのような常時接続が必要なシステム（コールドスタートの問題もある）
    定期バッチ：毎朝 6 時のレポート生成、毎時のデータ集計など、15 分以内に終わる処理24 時間常に高負荷のシステム：大量のリクエストが来続けるなら、従来のサーバーのほうがコスパがよい場合がある
    MVP 開発：最小限の機能でサービスを立ち上げたいとき、インフラ設定に時間をかけずコードに集中できる

    サーバーレスには、はっきりした向き不向きがあります。特性を理解したうえで選ぶことが大切です。

    9.どう始めるか

    1. 小さな処理から試す：いきなり本番システムをサーバーレスにする必要はありません。問い合わせフォームの送信処理、画像のリサイズ、定期的なデータ取得といった小さな処理を Lambda で動かしてみます。
    2. 既存システムは一部から段階的に：全部を置き換える必要はありません。たとえば通知機能だけを Lambda に切り出し、メインのシステムはそのまま残します。いきなり全部をサーバーレスにしようとすると、落とし穴にはまる可能性があります。小さく始めて感覚をつかんでから広げるのが安全です。
    3. 手を動かして学ぶ：学習には AWS の公式ドキュメントとハンズオンがおすすめです。Lambda のチュートリアルが充実しており、無料で試せる範囲も広くあります。ドキュメントを読むだけでなく、実際に動かしてコールドスタートを体感し、ログを見て、コストを確認すると、向き不向きが肌感覚で分かるようになります。

    既存システムの一部を切り出していく進め方は、40-2 で紹介したストラングラーフィグ（少しずつ置き換える）の考え方と同じです。

    10.よくある誤解

    誤解実際
    サーバーレスはサーバーがないサーバーは存在する。自分で管理する必要がなくなるだけ
    サーバーレスは必ず安い少量なら安いが、大量・常時のリクエストではサーバーより高くつくことがある
    サーバーレスなら何でも動かせる実行時間の制限（Lambda は最大 15 分）、常時接続の苦手さ、コールドスタートがある
    サーバーレスにすれば運用がゼロになるサーバー管理は不要になるが、ログ・監視・権限設定・コスト管理・冪等性の設計は残る
    全部をサーバーレスにすべき合う部分から小さく始め、向かない処理は従来のサーバーやコンテナと組み合わせる

    11.まとめ

    このページのポイント

    • サーバーレスは「サーバー管理をクラウドに任せる」仕組み。サーバーがなくなるわけではない。
    • 関数はイベントで起動し、終われば消える。データ保存はマネージド DB・ストレージと組み合わせる。
    • メリットはインフラ管理不要・自動スケーリング・従量課金・開発スピードの4つ。
    • 落とし穴はコールドスタート・実行時間制限・デバッグの難しさ・ベンダーロックイン・コストの罠の5つ。万能ではない。
    • API・イベント処理・短いバッチ・MVP に向き、長時間処理・常時接続・常時高負荷には向かない。
    • 全部をサーバーレスにせず、合う部分から小さく始める。
