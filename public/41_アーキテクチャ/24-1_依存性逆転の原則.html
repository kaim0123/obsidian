    依存性逆転の原則（DIP）

    業務ロジックを DB やフレームワークに縛りつけないための原則「DIP」を、原則の本文・コード・図の三方向から解説します。「自然な依存」と「逆転した依存」の違い、インターフェースを上位側に置く理由、DI との違い、クリーン／ヘキサゴナル／オニオンとのつながり、そしてありがちな誤解までを一通り押さえられます。

    もとにしたノート：01依存性逆転.md（依存性逆転（DIP）の実務的イメージ）、02_依存関係逆転の原則.md

    1.このページで扱うこと

    ソフトウェアを構造化する基本は 層化 です。しかし「層を上から下へ積む」だけでは、次のような問題が残ります。

    • ドメイン層（業務ロジック）が インフラ層（DB・外部 API）に依存 してしまう
    • DB を変えると 業務ロジックまで書き換える 必要がある
    • 業務ロジックの テストに DB の起動が必要 になる

    これを解決するのが 依存性逆転の原則（Dependency Inversion Principle, DIP） です。日本語では「依存関係逆転の原則」とも訳されます。直感的には分かりにくい原則ですが、クリーンアーキテクチャ・ヘキサゴナルアーキテクチャ・テストしやすいコード を支える要（かなめ）の考え方です。

    このページでは次の内容を、初心者でも実際にコードが書けるレベルまでかみ砕いて説明します。

    • DIP とは何か（原則の本文と、一言での言い換え）
    • 「自然な依存」と「逆転した依存」の違い、そしてなぜ「逆転」と呼ぶのか
    • 逆転すると何がうれしいのか
    • 抽象（インターフェース） を間に挟む具体的な実装イメージと、実装のポイント
    • DIP と DI（依存性注入）の違い
    • クリーン／ヘキサゴナル／オニオンとの関係
    • ありがちな誤解・よくある疑問・アンチパターン

    前提として読んでおくと理解が深まるページ

    層化・三層・レイヤード（4層） と トレードオフとアーキテクチャに効く原則。また、疎結合の考え方は モジュール性・疎結合と高凝集 で扱っています。

    2.DIP とは — 原則の本文

    DIP は SOLID 原則の 5 番目、D にあたる原則です。Robert C. Martin（通称 Uncle Bob）が 1990 年代に提唱し、著書『アジャイルソフトウェア開発の奥義』（原題 Agile Software Development, Principles, Patterns, and Practices）などで広めました。原則は次の 2 文で述べられています。

    A. 上位モジュールは、下位モジュールに依存してはならない。両者は、抽象に依存するべきである。

    B. 抽象は、具体的な実装（詳細）に依存してはならない。具体的な実装が、抽象に依存するべきである。

    難しく見えますが、言い換えると次のようになります。

    一言でいうと

    重要な上位モジュール（業務ロジック）を、下位モジュール（DB やフレームワーク）に依存させてはいけない。両方とも「抽象（インターフェース）」に依存させなさい。

    さらに短くすれば、「具体的なものに頼らず、抽象に頼れ」 ということです。

    用語の整理

    用語意味例
    上位（高水準）モジュールアプリの目的そのもの。業務のルールや手順を表すOrderService、RegisterUserUseCase
    下位（低水準）モジュール上位の目的を実現するための技術的な詳細MySQL 接続、SendGrid のメール送信、HTTP クライアント
    抽象「何ができるか」という契約だけを決め、実装を持たないものOrderRepository インターフェース
    具体（詳細）契約を実際に実現するコードMySQLOrderRepository クラス

    「依存の向きを 逆転 させる」というのは、

    • 普通：業務ロジック → DB（業務ロジックが DB に依存する）
    • 逆転後：業務ロジック → 抽象 ← DB（DB の方が抽象に従う）

    のように、業務ロジックがインフラに依存しない形 に組み替えることを指します。

    3.「自然な依存」と「逆転した依存」

    3.1 自然な依存（多くの初学者が書く形）

    まずは、何も意識せずに書くとこうなる、という例です。

    ✕ 自然な依存：業務ロジックが MySQL を直接 new している 
    class OrderService {
    submit(order) {
        // MySQL の具体クラスを直接 new する
        const conn = new MySQLConnection("localhost", "root", ...);
        conn.execute("INSERT INTO orders ...");
    }
}

    このコードでは、OrderService（業務ロジック）が MySQLConnection（インフラ）を 直接知っています。依存の向きは次のとおりで、業務ロジックが MySQL という具体的な技術に縛られた 状態です。

    [業務ロジック] ───依存───▶ [MySQL（具体）]

    TypeScript で、リポジトリクラスを分けた場合も同じことが起きます。

    ✕ 逆転していない（通常の依存） 
    // 下位（インフラ層）
class MySQLUserRepository {
  async save(user: User) {
    await mysql.query('INSERT INTO users ...');
  }
}

// 上位（業務層）
class RegisterUserUseCase {
  private repo = new MySQLUserRepository(); // 具体クラスに依存

  async execute(input) {
    const user = new User(input);
    await this.repo.save(user);
  }
}

    この形の問題点

    • ユースケースが MySQL を知ってしまう
    • DB を変えるだけで、ユースケースも変更が必要になる
    • テスト時にモック（偽物）へ差し替えられない

    3.2 逆転した依存

    同じ処理を、抽象（インターフェース）を挟んで書き直します。

    ○ 逆転した依存（擬似コード） 
    // 抽象（インターフェース）を定義する
interface OrderRepository {
    save(order): void;
}

// 業務ロジックは抽象にだけ依存する
class OrderService {
    constructor(repo: OrderRepository) { this.repo = repo; }
    submit(order) { this.repo.save(order); }
}

// MySQL 実装は抽象を「実装する」側
class MySQLOrderRepository implements OrderRepository {
    save(order) { /* MySQL 固有の処理 */ }
}
    [業務ロジック] ──▶ [OrderRepository（抽象）] ◀── [MySQL 実装]

    業務ロジックも MySQL 実装も、両方が抽象（インターフェース）の方を向いている 状態です。これが「依存性が逆転した」状態です。

    ○ 逆転している（DIP 適用・TypeScript） 
    // 抽象（UseCase 側に定義）
interface UserRepository {
  save(user: User): Promise<void>;
}

// 上位（業務層）
class RegisterUserUseCase {
  constructor(private repo: UserRepository) {} // 抽象に依存
  async execute(input) {
    const user = new User(input);
    await this.repo.save(user);
  }
}

// 下位（インフラ層）
class MySQLUserRepository implements UserRepository {
  async save(user: User) {
    await mysql.query('INSERT INTO users ...');
  }
}

// 配線
const useCase = new RegisterUserUseCase(new MySQLUserRepository());

    改善点

    • ユースケースは UserRepository（抽象）しか知らない
    • DB を PostgreSQL に変えても、ユースケースは変更不要
    • テストではモックを注入できる

    4.なぜ「逆転」と呼ぶのか

    4.1 矢印の向きを比べる

    DIP 適用前と適用後で、依存の矢印を並べてみます。

    DIP 適用前（普通の依存）

    [UseCase] ──依存──→ [MySQLUserRepository]
  上位                  下位

    矢印は「上位 → 下位」。下位の変更が上位に波及します。

    DIP 適用後

    [UseCase] ──依存──→ [UserRepository (interface)]
                            ↑
                          実装
                            │
                [MySQLUserRepository]
                        下位

    下位から出る矢印が、上位側の抽象へ向かいます。

    適用前は「上位 → 下位」だった矢印が、適用後は下位（MySQLUserRepository）から上位側（UserRepository）へ向かう「下位 → 上位」の矢印に変わっています。矢印が逆転したように見えるので、「依存関係逆転」 と呼びます。

    4.2 「下位が上位に合わせる」という逆転

    もう一つの見方は、誰が誰に合わせるのか の逆転です。

    • 普通の依存：上位（業務ロジック）が、下位（MySQL の API）の都合に合わせてコードを書く
    • 逆転した依存：上位が「こういう操作がほしい」とインターフェースで宣言し、下位がそれに合わせて実装する

    ユースケースは抽象（インターフェース）に依存し、MySQL はその抽象を実装するだけになります。下位が上位に「合わせる」形に変わった ことこそが、「逆転」の本当の意味です。この意味での逆転が成り立つには、抽象が上位側に置かれている必要があります（7 章 で詳しく説明します）。

    制御の流れは逆転しない

    逆転するのは「ソースコード上の依存（import や型の参照）」の向きです。実行時の呼び出しは、相変わらず「ユースケース → MySQL 実装」の順に流れます。実行時の流れと、コード上の依存の向きが逆になる のが DIP のポイントです。

    5.なぜ逆転するとうれしいのか

    5.1 業務ロジックが技術選択に左右されない（外部システムの変更に強い）

    「DB を PostgreSQL に変えよう」「メール送信を SendGrid から AWS SES に変えよう」となったとき、

    自然な依存

    業務ロジックを書き換える 必要がある。

    逆転した依存

    新しい実装クラスを足す だけで済む。業務ロジックは無傷。

    5.2 テストが書きやすい（外部依存をテストできる）

    テスト時には、DB・外部 API・メール送信を 偽物（モック）の実装 に差し替えて、純粋なロジックだけ をテストできます。

    const fakeRepo = { save: (o) => { /* メモリ内に保存 */ } };
const service = new OrderService(fakeRepo);
service.submit({ id: 1, total: 100 });
// DB を起動せずにテストできる

    5.3 業務ロジックが「読んで分かる」コードになる

    業務ロジック側に MySQL のクエリや HTTP クライアントの初期化が出てこなくなり、「業務として何をしているか」だけが残る ため、コードが読みやすくなります。

    5.4 並行開発できる

    「OrderRepository というインターフェースだけ先に決める」という合意があれば、

    • A さん：業務ロジック（OrderService）を書く
    • B さん：MySQL 実装（MySQLOrderRepository）を書く

    という作業を 並行して 進められます。

    5.5 レイヤー間の契約が明確になる

    インターフェースが レイヤー間の約束事 として機能します。「業務層はこの操作だけを求める」「インフラ層はこの操作を必ず提供する」ということが、型としてコードに書かれます。

    5.6 クリーンアーキテクチャが成立する

    内側（ビジネス）を外側（技術）から守るためには DIP が不可欠です。業務ロジックが DB を「使う」のに、依存は「内側へ」向けたい——この矛盾を解くのが DIP です（10 章）。

    6.抽象（インターフェース）を介す

    DIP の心臓部は「抽象を間に挟む」ことです。抽象の表現方法は言語によって違います。

    表現主な言語
    インターフェースJava、TypeScript、C#、Go など
    抽象クラス多くのオブジェクト指向言語（Java、C#、C++、Python の ABC など）
    プロトコルSwift（Python の typing.Protocol も同様の発想）
    トレイトRust
    型クラスHaskell
    関数の型シグネチャだけを使う動的言語、関数型スタイル（「この形の関数を渡して」と決めるだけ）

    表現は違っても、「実装ではなく契約だけを決める」 という点は共通しています。業務ロジックは、

    • 「保存できる何か」（インターフェース）にだけ依存する
    • どんな技術で保存するのかは 知らない

    これによって技術と業務の結合度が下がります。これは アーキテクチャに効く原則 や 疎結合と高凝集 で扱う「疎結合」の話そのものです。インターフェースの設計の仕方そのものは インターフェースと抽象化 で詳しく扱います。

    7.実装のポイント

    7.1 インターフェース（抽象）は上位側に置く

    DIP で最も見落とされやすいのが、インターフェースをどこに置くか です。

    src/
├─ usecases/
│   ├─ RegisterUserUseCase.ts
│   └─ UserRepository.ts       ← インターフェース（抽象）
└─ infrastructure/
    └─ MySQLUserRepository.ts  ← 実装

    抽象は上位（使う側）の持ち物 です。下位（実装する側）が、上位のインターフェースに合わせに行きます。こうすると、infrastructure が usecases を import する形になり、パッケージ（フォルダ）単位でも依存が「下位 → 上位」に逆転します。

    7.2 上位が「ほしいもの」を宣言する

    インターフェースは、上位（ユースケース）が「自分の仕事にはこういう機能が必要だ」と宣言するものです。下位はその宣言に合わせて実装します。

    // UseCase が自分に必要なものをインターフェースで宣言
interface EmailSender {
  send(to: string, body: string): Promise<void>;
}

// 下位はそれに合わせて実装
class SendGridEmailSender implements EmailSender { /* ... */ }
class AWSEmailSender implements EmailSender { /* ... */ }

    7.3 コンストラクタで DI する

    上位は、抽象をコンストラクタで受け取ります（依存性注入、DI）。

    class UseCase {
  constructor(private sender: EmailSender) {} // DI
}

    DI の詳細は DI・IoC・Composition Root で扱います。

    8.実務での実装パターン

    8.1 DI（Dependency Injection）

    業務ロジックに、依存先を外から注入する 手法です。注入の仕方には 3 種類あります。

    注入の方法コード特徴
    コンストラクタ注入（最も一般的）new OrderService(new MySQLOrderRepository());必須の依存を強制でき、作った後は変わらない
    セッター注入service.setRepository(new MySQLOrderRepository());後から差し替えられるが、セット前に使われる危険がある
    メソッド引数による注入service.submit(order, repo);そのメソッドでだけ使う依存を、使うときに渡す

    コツは、依存先を new するのは業務ロジックの「外側」（main 関数や DI コンテナ）に寄せる ことです。この「外側」を一か所にまとめたものが Composition Root です。

    8.2 リポジトリパターンの典型

    DDD（ドメイン駆動設計）でも頻出する リポジトリパターン は、DIP の代表的な応用例です。

    [業務ロジック] ──▶ [Repository インターフェース] ◀── [MySQL / Redis / Memory 実装]

    業務ロジックは UserRepository.findById(id) と書くだけです。具体的な保存先は、起動時に 外側で組み立てます（DI コンテナや main で）。

    8.3 テスト時の差し替え

    // 本番
const service = new OrderService(new MySQLOrderRepository());

// テスト
const service = new OrderService(new InMemoryOrderRepository());

    「インターフェースさえ満たせば差し替えられる」——これが DIP の実用的なご利益です。

    9.DIP と DI（依存性注入）の違い

    この 2 つは名前も似ていて混同しやすいのですが、別物です。

    DIP（依存性逆転の原則）DI（依存性注入）
    何か原則・思想テクニック
    目的抽象に依存させる（依存の矢印の向きを決める）依存を外から渡す（誰が用意するかを外に出す）
    ない場合設計の方向性が決まらない依存先がハードコードされる
    関係ゴール手段

    DIP はゴール、DI はその手段 と捉えると整理しやすくなります。インターフェースに依存していても、クラスの中で new MySQLUserRepository() していれば逆転は中途半端です。逆に、外から渡していても型が具体クラスなら差し替えは困難です。「抽象を、外から受け取る」 で両方がそろいます。

    さらに広い概念である IoC（制御の反転）を含めた 3 つの関係は、DI・IoC・Composition Root で整理しています。

    10.クリーン／ヘキサゴナル／オニオンとの関係

    10.1 共通の発想

    クリーンアーキテクチャ・ヘキサゴナルアーキテクチャ・オニオンアーキテクチャは、いずれも DIP を アーキテクチャ全体に拡大して適用 したものです。

    • 中心にドメイン（業務ロジック）を置く
    • 周辺にインフラ（DB、UI、外部 API）を置く
    • すべての矢印が中心に向かう ように、抽象を間に挟む

    「ドメインがインフラを知らない」という鉄則は、結局 DIP の言い換えです。

    10.2 名前は違えど本質は同じ

    アーキテクチャ中心周辺間に挟む抽象
    クリーンエンティティ／ユースケースフレームワーク／DB／UIBoundary／Gateway
    ヘキサゴナルドメインアダプタ（DB／UI／外部 API）ポート（Port）
    オニオンドメインモデルインフラ・UIドメインサービス／リポジトリの抽象

    詳しくは 依存性のルールとクリーンアーキテクチャ、ヘキサゴナルアーキテクチャ、オニオンアーキテクチャと3つの比較 を参照してください。

    11.よくある誤解・疑問とアンチパターン

    11.1 誤解：「とにかく全部にインターフェースを切ればよい」

    誤りです。 インターフェースは増やすほどコードが複雑になります。置き換える可能性がなく、テストで偽物も要らない 部品にインターフェースを切るのは過剰設計（YAGNI 違反）です。

    ガイドライン：どこにインターフェースを置くか

    外部に依存する境界（DB、外部 API、UI、ファイル、メール、時計、乱数など）にインターフェースを置くのが定石です。中の純粋な計算ロジック同士には、たいてい不要です。

    11.2 誤解：「DI コンテナを使えば自動的に DIP になる」

    誤りです。 DI コンテナは便利な道具ですが、依存の 向き を正しく設計するのは人の仕事です。コンテナを使っていても、業務ロジックが具体クラスに直接依存していれば DIP は守れていません。また、コンテナを業務ロジックの中から呼び出すと「サービスロケーター」というアンチパターンになります（DI・IoC・Composition Root 参照）。

    11.3 誤解：「インターフェースは多機能なほどよい」

    誤りです。 インターフェースは「最低限の契約」です。利用者（業務ロジック）が必要としない機能は書きません。実装側の都合で機能を増やすと、抽象の意味が薄まります（インターフェース分離の原則、ISP と関連）。

    11.4 疑問：実装が 1 つしかないのに、インターフェースを作る意味はある？

    二つのノートで扱いが分かれていた論点なので、整理しておきます。

    アンチパターン：実装を写しただけのインターフェース

    • 実装クラス MySQLOrderRepository のために、そのコピーのような IMySQLOrderRepository を切る
    • 結局その実装 1 つしか存在しない

    これは「インターフェースのための DIP」であり、本来の目的（業務ロジック側の都合 で抽象を切る）と逆です。

    意味がある場合：使う側の言葉で切ったインターフェース

    実装が 1 つでも、テスト容易性（モックを渡したい）と 将来の差し替え可能性 のために作る価値はあります。名前は「業務ロジックにとって必要な操作」を表すもの（例：OrderRepository）にします。

    ただし、本当に 1 つしかないと分かっていて テストにも困らない なら、省略して構いません。

    つまり問題は「実装の数」ではなく、インターフェースが誰の都合で、誰の言葉で作られているか です。

    11.5 疑問：インターフェースを全クラスに作るべき？

    不要です。 外部依存（DB、API、ファイル、メール）を またぐ境界 だけに作れば十分です。中の純粋な計算クラスには不要です（11.1 と同じ結論です）。

    11.6 疑問：抽象クラスとインターフェース、どちらを使う？

    抽象クラスインターフェース
    実装の共有できる（共通処理を書ける）基本的にできない（契約だけ）
    複数採用Java・C# などでは 1 つしか継承できない1 つのクラスが複数実装できる

    迷ったら インターフェース を選びます。

    補足：言語によって事情は異なります。C++ や Python は多重継承ができますし、Java 8 以降のデフォルトメソッドや C# 8 以降のデフォルトインターフェースメソッドのように、インターフェースが一部の実装を持てる言語もあります。それでも「契約だけを表すならインターフェース」という使い分けは共通です。

    11.7 アンチパターン集

    ✕ 上位が下位を new する 
    class UseCase {
  private db = new MySQLDatabase(); // 具体クラスに直接依存
}
    ✕ インターフェースを下位側に置く 
    infrastructure/
├─ MySQLUserRepository.ts
└─ UserRepository.ts  ← 下位側にインターフェースがある

    これでは、依存は「上位 → 下位」のままです（図2 の右側）。抽象は 上位側 に置きます。

    ✕ インターフェースが実装に引きずられている 
    interface UserRepository {
  executeQuery(sql: string): any; // ← MySQL の都合が漏れている
}

    インターフェースは ビジネスの言葉 で定義します。SQL を受け取るインターフェースでは、DB を差し替えたときに業務ロジックも書き直しになり、抽象の意味がありません。

    12.まとめ

    • 依存性逆転の原則（DIP） は、業務ロジック（上位）を 抽象（インターフェース）にだけ依存 させ、具体的な技術（下位）も同じ抽象を 実装する 形に組み替える原則です。一言でいえば「具体ではなく、抽象に依存せよ」。
    • 自然な依存では「業務ロジック → MySQL」と直接結びつきますが、DIP 適用後は「業務ロジック → 抽象 ← MySQL」と 両方が抽象を向きます。下位が上位に合わせる形になることが「逆転」の意味です。
    • 抽象は上位側の持ち物 です。下位がそれに合わせに行きます。下位側にインターフェースを置くと逆転は起きません。
    • メリットは、技術選択からの独立・テストの容易化・読みやすさ・並行開発・レイヤー間の契約の明確化 です。
    • 実装は インターフェース＋DI（コンストラクタ注入が王道） で行い、new するのは業務ロジックの 外側 に寄せます。DIP はゴール、DI は手段です。
    • クリーン／ヘキサゴナル／オニオンは、いずれも DIP を アーキテクチャ全体に適用 したもので、「ドメインがインフラを知らない」が共通の鉄則です。
    • 「全部にインターフェース」「DI コンテナ＝DIP」「実装を写しただけのインターフェース」「実装の都合でインターフェースを増やす・SQL を漏らす」は典型的な誤りです。

    次は DI・IoC・Composition Root で「抽象を外から渡す」手段と、最終的に誰が組み立てるのかを見ていきます。DIP を全体構造として実装するパターンは、クリーンアーキテクチャ・ヘキサゴナル・オニオン の各ページで扱っています。
