    ヘキサゴナルアーキテクチャ

    ヘキサゴナルアーキテクチャ（ポート&アダプタ）は、業務ロジックのコアを中心に置き、外の世界とはすべて「ポート（インターフェース）」と「アダプタ（実装）」でつなぐスタイルです。このページでは、Driving（入力側）と Driven（出力側）の2種類のポートの違い、フォルダ構成、テストのしやすさ、クリーンアーキテクチャとの対応関係を詳しく見ていきます。

    もとにしたノート：ヘキサゴナルアーキテクチャ / 00_解説_アプリ内部構造

    1.このページで扱うこと

    ヘキサゴナル（六角形）アーキテクチャは、Alistair Cockburn（アリスター・コーバーン）が 2005 年に提唱したアーキテクチャスタイルで、別名 「ポート&アダプタ（Ports and Adapters）」と呼ばれます。

    クリーンアーキテクチャとほぼ同じ思想ですが、図と用語が違います。特に「ビジネスロジックを中心に置き、外の世界はすべてアダプタでつなぐ」という考え方が明快で、同心円型アーキテクチャの入門として最も覚えやすいスタイルです。このページでは次の内容を扱います。

    • ヘキサゴナルアーキテクチャが生まれた狙い
    • 中心概念：Application Core・Port・Adapter
    • 2種類のポート：Driving Port（入力側）と Driven Port（出力側）、それぞれのコード例
    • 依存の向きとフォルダ構成、実装のコツ
    • テストのしやすさ、メリット
    • クリーンアーキテクチャとの対応関係、よくある誤解

    2.ヘキサゴナルアーキテクチャの狙い

    Cockburn がこのスタイルで目指したのは、アプリケーションを、人間のユーザーからでも、別のプログラムからでも、自動テストやバッチスクリプトからでも同じように動かせるようにし、最終的に使う実行環境のデバイスや DB から切り離して開発・テストできるようにすることでした。

    当時よくあった問題は、業務ロジックが UI のコードや DB アクセスのコードに混ざり込み、

    • 画面を操作しないと業務ロジックをテストできない
    • DB がないと何も動かない
    • 入口（Web 画面、バッチ、他システム連携）が増えるたびに、同じロジックを書き写すことになる

    というものです。そこで、アプリケーションの「内側」と「外側」をはっきり分け、内側と外側の接点をポート（差し込み口）として定義し、外側の技術ごとにアダプタ（変換器）を差し込む、という構造を考えました。電気製品のコンセントとプラグ、あるいは USB ポートと各種機器をイメージすると分かりやすいでしょう。

    一言でいうと

    コアは「どんな形の差し込み口があるか」だけを決める。外の世界は、その差し込み口に合うアダプタを作って差し込む。アダプタを替えても、コアは一切変わらない。

    3.六角形の図と3つの中心概念

    真ん中に アプリケーションコアを置き、その周りを ポート → アダプタ → 外部 の順で囲みます。図を六角形で描くことが多いので「ヘキサゴナル」と呼ばれます。慣習として、左側にコアを呼び出す側（入力）、右側にコアから呼び出される側（出力）を描きます。

    1. Application Core（中心）

    • 業務ロジックの塊
    • 外部のことは何も知らない
    • クリーンアーキテクチャの Entities ＋ Use Cases に相当

    2. Port（ポート）

    • コアが外と会話するための「窓口」
    • 実体は単なるインターフェース
    • Driving Port と Driven Port の2種類がある

    3. Adapter（アダプタ）

    • ポートと外部をつなぐ具体的な実装
    • 同じポートに対して複数のアダプタを取り替え可能
    • 例：PostgresUserRepository, MongoUserRepository

    4.2種類のポート — Driving と Driven

    ポートには、誰が会話を始めるかによって2種類あります。

    観点Driving Port（駆動ポート）Driven Port（被駆動ポート）
    図の位置左側・入力側（Primary）右側・出力側（Secondary）
    会話を始めるのは外部がコアを呼ぶコアが外部を呼ぶ
    ポートの中身Use Case のインターフェースRepository・外部サービスのインターフェース
    ポートを実装するのはコア（Use Case のサービス）アダプタ（DB・メッセージングなどの具体実装）
    ポートを使うのはアダプタ（Controller・CLI・テスト）コア
    アダプタの例HTTP Controller、CLI、Slack Bot、バッチ、テストMySQL Repository、インメモリ Repository、Kafka Producer、メール送信

    ポイント：どちらのポートもコア側に置かれる

    Driving Port はコアが「こう呼んでください」と公開する入口、Driven Port はコアが「こういう機能をください」と要求する出口です。どちらもコアが定義するので、アダプタはどちら側でもコアに依存し、コアはアダプタを知りません。

    Driving Port（左側・入力側）

    外部がコアを呼び出すときに使う窓口です。

    // Driving Port
interface PlaceOrderPort {
  execute(input: PlaceOrderInput): Promise<Order>;
}

// コア（実装）
class PlaceOrderService implements PlaceOrderPort { /* ... */ }

// Driving Adapter（外から呼ぶ側）
class HTTPOrderController {
  constructor(private port: PlaceOrderPort) {}
  async handle(req) {
    return this.port.execute({ items: req.body.items });
  }
}

// 別の Driving Adapter：CLI
class CLIOrderCommand {
  constructor(private port: PlaceOrderPort) {}
  run(args) { return this.port.execute({ items: args.items }); }
}

    → HTTP から呼んでも CLI から呼んでも、コアは同じです。アダプタの仕事は、HTTP リクエストやコマンドライン引数を PlaceOrderInput に変換することだけです。

    Driven Port（右側・出力側）

    コアが外を呼び出すときに使う窓口です。

    // Driven Port
interface OrderRepository {
  save(order: Order): Promise<void>;
}

// コアはこのインターフェースだけを知る
class PlaceOrderService {
  constructor(private repo: OrderRepository) {}
}

// Driven Adapter（外の具体実装）
class MySQLOrderRepository implements OrderRepository { /* ... */ }
class InMemoryOrderRepository implements OrderRepository { /* テスト用 */ }

    → DB を MySQL からインメモリに差し替えても、コアは変更なしです。Driven Port の仕組みは、依存性逆転の原則（DIP）そのものです。

    5.フォルダ構成例

    ポートの In / Out、アダプタの In / Out をフォルダで分けると、依存の向きがひと目で分かります。

    src/
├─ core/                  ← 中心
│   ├─ domain/            ← Entity
│   │   └─ Order.ts
│   └─ application/       ← UseCase
│       ├─ ports/         ← ポート（インターフェース）
│       │   ├─ in/        ← Driving Port
│       │   │   └─ PlaceOrderPort.ts
│       │   └─ out/       ← Driven Port
│       │       └─ OrderRepository.ts
│       └─ services/
│           └─ PlaceOrderService.ts
├─ adapters/
│   ├─ in/                ← Driving Adapter（入力）
│   │   ├─ web/           ← HTTP Controller
│   │   └─ cli/           ← CLI コマンド
│   └─ out/               ← Driven Adapter（出力）
│       ├─ persistence/   ← MySQL Repository
│       └─ messaging/     ← Kafka Producer
└─ main.ts                ← 配線（どのアダプタを差し込むかを決める）

    main.ts は、クリーンアーキテクチャの Frameworks & Drivers 層にある配線板と同じ役割です。ここで「本番では MySQL アダプタ、ローカル開発ではインメモリアダプタ」のように、どのアダプタを差し込むかを決めます（DI・IoC・Composition Root 参照）。

    6.実装のコツ

    1. Port は必ず core 側に置く
      ポートが core の外にあると、core が外部に依存してしまいます。インターフェースは core に、実装は adapters に置きます。
    2. Adapter は薄く
      アダプタに業務ロジックを書きません。変換だけの薄い層に保ちます。アダプタに「在庫が足りなければ…」のような判断が入り始めたら、それはコアに移すべきサインです。
    3. In と Out を分ける
      Driving Port と Driven Port はフォルダで明確に分けると、依存の向きがひと目で分かります。

    7.テスト例 — インメモリのアダプタを差し込む

    // インメモリのアダプタでテスト
test('注文が保存される', async () => {
  const inMemoryRepo = {
    orders: [] as Order[],
    async save(o: Order) { this.orders.push(o); }
  };
  const service = new PlaceOrderService(inMemoryRepo);

  await service.execute({ items: [{ id: 'a', price: 100 }] });

  expect(inMemoryRepo.orders.length).toBe(1);
});

    DB を起動せず、モックフレームワークも不要です。インメモリのアダプタは「本物と同じポートを実装した、もう1つのアダプタ」にすぎません。これがヘキサゴナルの一番の恩恵です。

    ※ もとのノートの例では変数に OrderRepository 型を注釈していましたが、その型には orders プロパティがないためアサーションで型エラーになります。ここでは型注釈を外し、構造的型付けでポートに適合させる形にしています。

    テストの分担が自然に決まる

    コアはインメモリアダプタでユニットテスト、Driving Adapter（Controller など）は変換が正しいかをユニットテスト、Driven Adapter（MySQL Repository など）は本物の DB を使った統合テスト、という分担が自然に生まれます。

    8.メリット

    1. テストが非常にしやすい

    • インメモリのアダプタを差し込めば、DB なしでコアのすべてをテストできる
    • Driving Adapter はユニットテスト、Driven Adapter は統合テストという分担が自然

    2. 外部依存の差し替えが簡単

    • DB の変更、メッセージブローカーの変更、UI の変更が、すべてアダプタの差し替えで済む
    • レガシーシステムからの移行でも、中核を先に作ってアダプタを後からつなぎ替えられる

    3. 新しい入口を増やしやすい

    • 既存の HTTP API に加えて、CLI・Slack Bot・バッチ処理を増やしたい場合、新しい Driving Adapter を書くだけで済む

    デメリット・注意点

    インターフェースとアダプタのぶん、ファイル数と間接参照が増えます。画面から保存まで一直線の小さな CRUD アプリでは、手間に見合わないことがあります。ポートは外部との境界にだけ置くのが原則です（第 10 章「誤解3」）。

    9.クリーンアーキテクチャとの関係

    項目ヘキサゴナルクリーン
    発案者Alistair Cockburn（2005）Robert C. Martin（2012）
    図六角形同心円
    用語Port, AdapterBoundary, Interface Adapter
    層の数コア＋アダプタ（2層）4層
    本質同じ同じ

    両者はほとんど同じことを言っています。クリーンアーキテクチャのほうが、コアの中身（Entities と Use Cases）を分けるなど、層の内訳が細かく定義されています。用語はおおよそ次のように対応します。

    ヘキサゴナルクリーンアーキテクチャでの近いもの
    Application CoreEntities ＋ Use Cases
    Driving PortUse Case の入力境界（Input Port / Input Boundary）
    Driven PortUse Case 層に置く Repository・Gateway のインターフェース（Output Port を含む）
    Driving AdapterController（Interface Adapters 層）
    Driven AdapterRepository 実装・Gateway 実装（Interface Adapters 層）＋ DB ドライバ等（Frameworks & Drivers 層）
    main.ts（配線）Frameworks & Drivers 層の main（Composition Root）

    3つのスタイル（クリーン・ヘキサゴナル・オニオン）の比較は オニオンアーキテクチャと3つの比較 で詳しく扱います。

    10.よくある誤解

    誤解1：ポートとアダプタは同じもの

    違います。ポート＝インターフェース（設計上の約束）、アダプタ＝その実装（具体物）です。1つのポートに対して、本番用・テスト用など複数のアダプタがありえます。

    誤解2：六角形は6層を意味する

    六角形の面の数に特別な意味はありません。Cockburn は、四角形以外の形にして「上下（層）」の印象を避け、ポートとアダプタを描き込む余白を確保するために六角形を選んだだけです。3面でも8面でも本質は変わりません。

    誤解3：すべての機能にポートを作る

    過剰設計になります。外部との境界にだけポートを置けば十分です。コア内部のクラス同士の呼び出しにまでポートは要りません。

    誤解4：Driven Port はアダプタ側（infrastructure 側）に置く

    Repository のインターフェースを infrastructure フォルダに置いてしまうと、コアが infrastructure を import することになり、依存が外を向きます。Driven Port もコアが定義し、コア側に置きます。

    11.まとめ

    • ヘキサゴナルアーキテクチャ（ポート&アダプタ）は Alistair Cockburn が 2005 年に提唱。アプリを UI・テスト・バッチのどこからでも同じように動かし、DB などから切り離して開発・テストできるようにするのが狙い
    • 構成要素は Application Core（外を知らない業務ロジック）・Port（窓口＝インターフェース）・Adapter（ポートと外部をつなぐ実装）
    • Driving Port：外がコアを呼ぶ入口（Controller・CLI・テストが使う）。Driven Port：コアが外を呼ぶ出口（MySQL・インメモリ・Kafka が実装する）
    • ポートはどちらも core 側に置く。アダプタは薄く、変換だけ。In と Out をフォルダで分ける
    • インメモリアダプタを差し込めば、DB もモックフレームワークもなしにコアをテストできる
    • クリーンアーキテクチャとは本質的に同じ。クリーンのほうが層の内訳が細かい。六角形の「6」に意味はない
