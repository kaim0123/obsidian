    40 システム・分散

    モノリス・分散モノリス・マイクロサービス

    「モノリスは悪」「マイクロサービスが正義」という単純な話ではなく、状況に応じて選ぶものだということを整理します。3つの形がそれぞれ何を指し、どんな長所と短所があるのか、そして「いつ分けるべきか」「分けすぎないための目安」を、図と比較表で確認します。

    もとにしたノート：40_システム・分散/02モノリスと分散モノリスとマイクロサービスといつ分けるか.md（＋ 00_解説_システム・分散.md、00_全体像/00_解説_アーキテクチャ体系.md の関連部分）

    1.このページで扱うこと

    このページでは、次の3点を初心者向けに整理します。

    • モノリス、分散モノリス、マイクロサービスがそれぞれ何を指すか
    • それぞれのメリット・デメリット
    • いつ分けるべきか、分けすぎないための目安

    前提として、分散とスタイル と（41 外のノート：42_ソフトウェア設計『03_境界づけられたコンテキストとコンテキストマップ』）を読んでおくと理解しやすくなります。

    3つのスタイルを一言で

    スタイル一言でのイメージ
    モノリス1つのアプリ・1つのデプロイ単位に、ほぼ全部が入っている
    分散モノリス見た目は複数サービスに分かれているが、密結合で一緒にデプロイされる
    マイクロサービス独立してデプロイ・運用できる小さなサービスの集まり

    見るべきは「境界」

    重要なのは「コードが何ファイル・何リポジトリに分かれているか」ではなく、デプロイ・データ・チームの境界がどう切れているかです。この3つの軸で見ると、3つのスタイルの違いがはっきりします。

    2.モノリス（Monolith）

    2-1. どんな形か

    層（プレゼンテーション・ドメイン・インフラ）は分かれていても、実行時は1プロセス・1リポジトリ・1デプロイであれば、多くの文脈ではモノリスと呼びます。中身は レイヤードアーキテクチャ のように技術の層で分かれていることが多いです。

    2-2. メリット

    • 開発が単純 — ローカルで全部動かしやすく、デバッグしやすい
    • トランザクションが楽 — 1つの DB なら ACID トランザクションがそのまま使える
    • 性能 — プロセス内の関数呼び出しは、ネットワーク通信より速いことが多い
    • 小〜中規模チームに向きやすい

    2-3. デメリット

    • コードベースが大きくなると、変更の影響範囲が読みにくくなる
    • スケールの単位がアプリ全体になる（「在庫だけ増やしたい」が難しい）
    • チームが増えると、同じリポジトリで衝突しやすい
    • 1か所の小さな変更でも全体の再デプロイが必要で、1つのバグで全体が落ちることもある

    モノリスは「悪い形」ではなく、多くのプロダクトにとって正しい出発点です。

    3.分散モノリス（Distributed Monolith）

    3-1. どんな形か

    見た目はマイクロサービス（API が分かれ、サーバーも分かれている）なのに、

    • サービス同士が強く依存している
    • 一緒にデプロイしないと動かない
    • データが共有 DB だったり、境界が曖昧だったりする

    といった状態を分散モノリスと呼びます。いわば「分けたつもりのモノリス」で、モノリスの短所（一緒にしか変えられない）は残ったまま、ネットワークの複雑さ（遅延・部分障害・運用負荷）だけが増えた、という皮肉なパターンです。

    なぜ「最悪の組み合わせ」と言われるか

    モノリスなら関数呼び出しで済んだものがネットワーク越しになり、遅く・壊れやすくなります。それでいて独立デプロイもできないので、マイクロサービスの利点（チームの自律・部分的なスケール）は得られません。両方の悪いところ取りになりやすいのです。

    3-2. なぜ起きるか

    • 「モダンだから」という理由での早すぎる分割
    • 境界づけられたコンテキストを決めずに、技術単位（レイヤーだけ）で分割した
    • 共有 DB を残したまま、API だけを分けた

    3-3. 避けるために

    • 分割前に、（41 外のノート：42_ソフトウェア設計『03_境界づけられたコンテキストとコンテキストマップ』）で境界を描く
    • 1サービスだけを独立してリリースできるかを実際に試す
    • データの正を1サービスに閉じる（データ所有権・分散トランザクション・SAGA）
    • サービス間の同期呼び出しの連鎖を減らし、必要に応じてイベントでつなぐ（40-3）

    4.マイクロサービス（Microservices）

    4-1. どんな形か

    マイクロサービスに厳密な定義は1つではありませんが、一般に次の点が重視されます。

    • 独立デプロイ — 1サービスの変更が、他のサービスに同時リリースを強制しない
    • データ所有権 — 各サービスが自分のデータを所有する（40-4）
    • 組織との対応 — チーム構造とアーキテクチャが似るというコンウェイの法則を逆手に取る「逆コンウェイ戦略」を意識することが多い（コンウェイの法則と Team Topologies）

    4-2. メリット

    • チームの自律性 — 領域ごとに開発・リリースのペースを分けられる
    • 部分的なスケール — 負荷の高いサービスだけを増やせる
    • 障害の局所化 — 障害が1サービスに閉じやすい（設計次第）
    • 技術の多様性 — サービスごとに言語・DB を選べる（やりすぎ注意）

    4-3. デメリット

    • 運用が重い — 監視・デプロイ・障害対応の対象が複数に増える
    • 分散システムの難しさ — ネットワーク遅延、部分障害、整合性（40-4）
    • テスト・デバッグ — エンドツーエンドで問題を再現するのが大変

    マイクロサービスの前提条件

    Martin Fowler は「MicroservicePrerequisites」で、マイクロサービスを始める前に素早いインフラ準備（プロビジョニング）、基本的な監視、素早いアプリケーションのデプロイが整っている必要があると述べています。CI/CD・監視・分散トレースが整っていない状態で分けると、運用負荷に押しつぶされやすくなります。

    5.3つの比較

    観点モノリス分散モノリスマイクロサービス
    デプロイ単位1つ見かけは複数、実質1つサービスごと
    データ共有しやすい共有しがち（問題）サービスごとに所有
    開発のしやすさ（初期）◎△△〜×
    スケールの柔軟性△△◎
    チーム拡大時の分離△×◎（設計が合えば）
    運用コスト低め高め（それでいて得をしないことも）高め

    分散モノリスは、運用コストはマイクロサービス並みに高いのに、スケールやチーム分離の利点はモノリス以下になりがちです。表の中で唯一「×」が付いているのはそのためです。

    6.段階的に分ける流れ

    実務では、いきなりマイクロサービスを作るのではなく、痛みが出たところから少しずつ外に出す進化がよく使われます。

    1. モノリス：まず1つのアプリとして作り、ドメインの理解を深める。
    2. モジュラーモノリス：デプロイ単位は1つのまま、中身をドメインで区切る。モジュール間は公開インターフェース経由のみ、他モジュールのテーブルは直接触らない。境界をアーキテクチャテストで守る。
    3. サービスベース：独立させたい領域を、粗いサービスとして切り出す。DB は共有でも始められる。
    4. マイクロサービス：独立デプロイ・個別スケールが本当に必要な領域だけを、データごと分離する。

    Monolith First とマイクロサービス・プレミアム

    Martin Fowler は 2015 年の時点で、MonolithFirst（まずモノリスで作り、中をモジュールに分け、問題になってから切り出す）と、マイクロサービス・プレミアム（分散そのものが追加のコストとリスクを生むため、その「割増料金」に見合う複雑さがあるときだけ選ぶ）を指摘していました。

    2023 年には、Amazon Prime Video の映像品質監視サービスが、サーバーレス／分散構成を1プロセスにまとめてインフラコストを約90%削減した事例が話題になりました。ただしこれは1つのサービス内の構成変更であり、「マイクロサービスはダメ」という話ではありません。コンポーネント間で大量のデータを受け渡す処理を、ネットワーク越しに分けていたことが問題でした。

    『ソフトウェアアーキテクチャの基礎』第2版（2025）でモジュラーモノリスが独立した章として追加されたのも、この揺り戻しの流れを反映しています。教訓は「モノリスに戻れ」ではなく、分割の粒度はデータの流れ・チーム・品質特性に合わせて調整するものだということです。

    ストラングラーフィグ（絞め殺しのイチジク）パターン

    既存のモノリスから少しずつ切り出すときによく使われるのが、Fowler が名付けたストラングラーフィグパターンです。モノリスの前にルーティング層（API ゲートウェイなど）を置き、切り出した機能へのリクエストだけを新しいサービスに振り向けます。これを1機能ずつ繰り返し、最後に古い部分を取り除きます。一度に全部を書き換える「ビッグバン移行」を避けられるのが利点です（入口の置き方は 40-5）。

    7.いつ分けるか — 実務的な目安

    まだモノリスでよいサイン

    • チームが1〜2つで、コードベースを把握できている
    • ドメイン境界がまだ固まっていない（試行錯誤の初期）
    • 可用性・スケールの要求が、1アプリで足りている
    • 分割の理由が「流行っているから」だけ

    分割を検討するサイン

    • 別チームが同じリポジトリで頻繁に衝突する
    • リリース周期や可用性要求が領域ごとに大きく違う
    • 特定の部分だけスケールや技術変更が必要
    • 境界づけられたコンテキストがコード上でもはっきりしている
    • モノリス内の変更が、関係ない領域に波及し続けている

    Rule of thumb（経験則）：最初はモジュラーモノリス（モノリスの中でモジュール境界をはっきりさせる）から始め、痛みが出たら外に出す、という進化がよく使われます。

    どの単位で独立させるべきかを考えるときは、「独立してデプロイでき、高い機能的凝集を持つ単位」であるアーキテクチャ量子の考え方が役に立ちます。量子ごとに必要な品質特性が違うなら、分ける理由になります。

    分けるときの進め方（概要）

    1. コンテキストマップで境界と関係を描く
    2. 最も独立しやすい1つ（依存の少ないところ）から切り出す
    3. データの正を決め、共有 DB から徐々に離す
    4. 切り出したサービスが単独でデプロイできることを確認する

    一気に10サービスにしない

    1つ成功させてから次へ進むのが安全です。最初の1つで、デプロイ・監視・データ同期の仕組みを整え、それを次のサービスに使い回します。

    8.よくある誤解

    誤解実際
    モノリスはレガシー多くの成功プロダクトは、長くモノリスで運用されている
    小さいほどよいので、サービス数を増やす小さすぎるサービスは運用負荷だけを増やす
    API を分ければマイクロサービスデプロイとデータの独立性がなければ、分散モノリスになりやすい
    分ければ必ず速くなるネットワーク往復が増え、かえって遅くなることもある

    9.小さな練習

    自分の（または想像の）システムで、次を試してみてください。

    1. システムを3〜5個の業務領域に分けて書き出す
    2. 今は1リポジトリか、複数かをメモする
    3. 各領域について「単独でリリースできるか」「DB を共有しているか」を Yes/No で答える
    4. 単独リリースが No で DB 共有が Yes の領域が多いのに、複数の API に分かれているなら、分散モノリスの可能性を疑う

    10.まとめ

    このページのポイント

    • 3つの違いは、コードの分かれ方ではなくデプロイ・データ・チームの境界で見る。
    • モノリスは単純・速い・トランザクションが楽。多くのプロダクトの正しい出発点。
    • 分散モノリスは「分けたつもりのモノリス」。早すぎる分割・技術単位での分割・共有 DB が原因になりやすい。
    • マイクロサービスは独立デプロイとデータ所有権が本質。チームの自律と部分スケールを得る代わりに、運用と分散の難しさを払う。
    • モジュラーモノリスで境界を引き、痛みが出たところから1つずつ切り出すのが安全。
