    レンダリング方式（CSR・SSR・SSG・ISR）

    画面の HTML を「いつ・どこで」完成させるかによって、Web のレンダリング方式は CSR・SSR・SSG・ISR の4つに分かれます。このページでは、それぞれの仕組み・長所と短所・向いている場面を図とコード例で比べ、ハイドレーションやストリーミング SSR・React Server Components・アイランドといった発展形、そして「どう選ぶか」までを整理します。

    もとにしたノート：30_フロントエンド構成／Webレンダリング方式_SSG_SSR_CSR_ISR、あなたはどのレンダリングパターンを採用しますか？【CSR/SSR/SSG/ISRを図解で解説】（詳しい要約）、00_解説_フロントエンド構成（レンダリング部分）

    2.判断の軸は2つだけ

    レンダリング方式は名前が多くて混乱しがちですが、判断の軸は次の2つに集約できます。

    1. HTML はいつ・どこで完成するか ── ビルド時（開発者の手元や CI）なのか、リクエストが来た時（サーバー上）なのか、ブラウザが JavaScript を実行したあとなのか。
    2. データはどれくらいの頻度で変わるか ── ほぼ変わらないのか、ときどき変わるのか、常に最新が必要なのか。さらに「ユーザーごとに中身が違うか」も、この軸の一部として考えます。

    4つの方式を「HTML が完成するタイミング」で並べると、次の図のようになります。濃い色の箱が「中身の入った HTML ができる場所」です。

    左に行くほど「事前に作っておく」ので配信は速くなりますが、データの鮮度は落ちます。右に行くほど「その場で作る」のでデータは新しく、ユーザーごとの内容にも対応できますが、そのぶん誰かが処理時間を負担します（SSR ならサーバー、CSR ならユーザーの端末）。

    HTML が完成するタイミング対応する方式
    ビルド時SSG / ISR
    リクエスト時SSR / ストリーミング SSR / React Server Components
    ブラウザ実行後CSR

    実際のアプリは1つの方式に統一する必要はなく、ページ単位（さらには部品単位）で混ぜる のが現在の主流です（10 章）。

    3.4つの基本レンダリング方式の概要

    略称正式名（英語）日本語HTML ができるタイミング一言
    CSRClient-Side Renderingクライアントサイドレンダリングブラウザが JS を実行したあと空の HTML ＋ JS で、ブラウザが画面を組み立てる
    SSRServer-Side Renderingサーバーサイドレンダリングリクエストのたび（サーバー上）毎回サーバーで完成した HTML を返す
    SSGStatic Site Generation静的サイト生成ビルド時事前に HTML を作り、CDN から配る
    ISRIncremental Static Regeneration増分（インクリメンタル）静的再生成ビルド時＋後から再生成SSG のページを一定時間ごと・トリガーで作り直す（主に Next.js）

    このうち SSR と SSG は、どちらも「ブラウザに届く前に HTML を作っておく」方式で、まとめて プリレンダリング と呼ばれます。違いは作るタイミングがリクエスト時かビルド時か、という点だけです。ISR は SSG の発展形、CSR はプリレンダリングをしない方式、と位置づけると全体が見えやすくなります。

    4.CSR（クライアントサイドレンダリング）

    仕組み

    サーバーは最初に、<div id="app"> のような入れ物しかない ほぼ空の HTML と、大きな JavaScript バンドルを返します。ブラウザが CSS と JS をダウンロードして実行し、必要なら API を呼んでデータを取得し、App コンポーネントを空の div に描画します。HTML が「中身つき」になるのは、ブラウザが JavaScript を実行したあと です。いわゆる SPA（シングルページアプリケーション） の形です。

    サーバーが返す HTML（ほぼ空） 
    <!doctype html>
<html>
  <head><link rel="stylesheet" href="/app.css"></head>
  <body>
    <div id="app"></div>   <!-- 中身は空。JS が後から埋める -->
    <script src="/bundle.js"></script>
  </body>
</html>
    ブラウザで実行される JS（React 18 以降の書き方） 
    import { createRoot } from "react-dom/client";
import App from "./App";

// 空の div に App コンポーネントを描画する
createRoot(document.getElementById("app")).render(<App />);

// React 17 以前は ReactDOM.render(<App />, document.getElementById("app")) と書いた

    長所と短所

    長所

    • 2回目以降の画面遷移は、サーバーに HTML を取りに行かず DOM を差し替えるだけなので 最も高速でなめらか
    • インタラクションの多い UI を作りやすい。従来の SPA と相性がよい
    • サーバーは静的ファイルの配信と API だけでよい（HTML を作るサーバー処理が要らない）

    短所

    • 最初に必要な JS をすべて読み込むため 初回表示が遅い。JS を読み込むまで何も表示されない
    • コンポーネントが増えるほど JS バンドルも大きくなる
    • 空の HTML なので、検索エンジンのクローラーが中身を読みにくく SEO に不利 になりやすい
    • 描画をユーザーの端末に任せるため、低速な端末では不利

    向いている場面

    Google マップのような地図アプリ、座席予約、チャット、ダッシュボード、管理画面など、動的でインタラクションが多い「アプリ」に近い UI に向いています。ログイン後の画面 は検索エンジンに読ませる必要がないので、SEO の弱点も問題になりにくい領域です。

    補足：「React は CSR のみ」ではない

    もとの動画では「React は CSR のみ、Next.js ならページごとに使い分けられる」と説明されています。これは「Vite などで作る素の React アプリは CSR になる」という意味では正しいのですが、React 自体にはサーバーで HTML を作る API（renderToString、ストリーミング用の renderToPipeableStream など）があり、SSR もできます。ただしサーバーの用意やデータ取得・ルーティングとの統合を自分で組む必要があるため、React の公式ドキュメントも SSR などをするなら Next.js などのフレームワークを使うことを勧めています。

    5.SSR（サーバーサイドレンダリング）

    仕組み

    ユーザーのリクエストが来るたびに、サーバー（または Edge）がデータを取得し、完成した HTML を組み立てて返します（プリレンダリング）。キャッシュ戦略を組み合わせて、毎回ではなく一定時間ごとに作り直す運用もあります。

    Next.js（Pages Router、Next.js 12 以前からの書き方） 
    // pages/products/[id].js
export async function getServerSideProps({ params }) {
  const res = await fetch(`https://api.example.com/products/${params.id}`);
  const product = await res.json();
  return { props: { product } };   // リクエストのたびに実行される
}

export default function ProductPage({ product }) {
  return <h1>{product.name}：{product.price}円</h1>;
}
    Next.js（App Router、Next.js 13 以降） 
    // app/products/[id]/page.js（Server Component）
export default async function ProductPage({ params }) {
  // キャッシュしない ＝ リクエストごとに最新データを取る（SSR 相当）
  const res = await fetch(`https://api.example.com/products/${params.id}`, {
    cache: "no-store",
  });
  const product = await res.json();
  return <h1>{product.name}：{product.price}円</h1>;
}

    長所と短所

    長所

    • リクエスト時点の最新データ を反映できる
    • 構築済みの HTML を返すので 初回表示が速い
    • 描画をサーバーが行うので、ユーザーの端末スペックに依存しにくい
    • クローラーが HTML をそのまま読めるので SEO に強い。初回表示の制御もしやすい

    短所

    • 毎回サーバー処理が走るので サーバー負荷・レイテンシが増えやすい
    • 常時動くサーバー（または Edge）という 実行環境が必要
    • ページ遷移のたびにサーバーでレンダリングするため、2回目以降の遷移は CSR より遅くなりやすい
    • HTML は届いても、ハイドレーションが終わるまでは操作できない（8 章）

    向いている場面

    • 在庫・価格が頻繁に変わる EC の商品ページ
    • 個人別のダッシュボード、ログイン後の画面（ユーザーごとに中身が違い、かつ初回表示を速くしたい場合）
    • ブログ・ニュース・コーポレートサイトなど、コンテンツ重視で SEO が必要 なサイト（ただし更新頻度が低いなら SSG・ISR も候補）

    動画では、デジタル庁のサイトが当初 Next.js を採用していた（その後 PHP ベースの構成に置き換えられた）という話にも触れています。行政サイトのようにコンテンツと SEO が重要なサイトで、プリレンダリングできるフレームワークが選ばれた例として紹介されています。

    6.SSG（静的サイト生成）

    仕組み

    npm run build などの ビルド時 に全ページの HTML を作っておき、できあがったファイルを CDN や静的ホスティングで配ります。リクエスト時にはサーバー処理が一切なく、ファイルをそのまま返すだけです。

    Next.js（Pages Router） 
    // pages/docs/[slug].js
export async function getStaticPaths() {
  const slugs = await getAllDocSlugs();          // ビルド時に作るページの一覧
  return { paths: slugs.map((slug) => ({ params: { slug } })), fallback: false };
}

export async function getStaticProps({ params }) {
  const doc = await getDoc(params.slug);         // ビルド時に1回だけ実行される
  return { props: { doc } };
}
    Next.js（App Router） 
    // キャッシュを使う ＝ ビルド時に取得した結果を使い回す（SSG 相当）
const res = await fetch("https://api.example.com/docs", { cache: "force-cache" });

    Next.js のバージョンによる既定値の違い

    Next.js 13〜14 の App Router では fetch は既定でキャッシュされ（SSG 寄り）、Next.js 15 で「既定ではキャッシュしない」側に変更されました。どちらの方式になるかはバージョンと設定で変わるため、意図をはっきりさせたい場所では cache オプションを明示するのが安全です。具体的な書き方は 33_Next.js が本拠地です。

    長所と短所

    長所

    • 最速。完成済みのファイルを CDN から返すだけ
    • サーバー負荷がほぼゼロで、キャッシュしやすい。端末スペックにも依存しない
    • HTML が最初から完成しているので SEO にも強い
    • 常時動くサーバーが不要（静的ホスティングで配信できる）

    短所

    • 内容を更新するたびに 再ビルドが必要
    • データが頻繁に変わるページには不向き
    • ページ数が多いと ビルド時間が長くなる
    • ユーザーごとに違う内容は作れない（全員に同じ HTML を配る）

    向いている場面

    ブログ、ドキュメント、ヘルプページ、LP（ランディングページ）、コーポレートサイト、ポートフォリオの固定ページなど、更新頻度が低いページ に向いています。動画では目安として「更新が月1回程度以下」を挙げ、1日1投稿のブログなら SSR か ISR の方がよい としています。

    7.ISR（インクリメンタル静的再生成）

    仕組み

    ISR は SSG と SSR のいいとこ取り を狙った方式です。まず SSG と同じようにビルド時に HTML を作って配り、返した HTML をキャッシュして2回目以降はそれを表示します。そのうえで、一定時間が経ったら（またはトリガーで）、バックグラウンドで静的ファイルを作り直す というモデルです。

    代表的には Next.js の機能 として知られており、HTTP や Web 標準として「ISR」という共通仕様があるわけではありません。考え方としては、HTTP キャッシュの stale-while-revalidate（期限切れのキャッシュを返しつつ裏で更新する）をページ生成に当てはめたものです。

    Next.js 12（Pages Router） 
    export async function getStaticProps() {
  const posts = await getPosts();
  return {
    props: { posts },
    revalidate: 3600,   // 3600 秒（1時間）経ったら、次のリクエストをきっかけに再生成
  };
}
    Next.js 13 以降（App Router） 
    // fetch ごとに再検証の間隔を指定する
const res = await fetch("https://api.example.com/posts", {
  next: { revalidate: 3600 },
});

// ページ全体に指定することもできる
export const revalidate = 3600;

    時系列で見る：期限切れ直後は一度だけ古いページが返る

    revalidate: 3600（1時間）を設定したときの動きを時系列で追うと、ISR の性質がよく分かります。

    1. 1800 秒時点のアクセス：まだ期限内なので、キャッシュされた HTML（ビルド時のデータ）をそのまま返します。
    2. 3800 秒時点のアクセス：期限切れです。ただしこのリクエストには 一度は古いデータの HTML を返し、その裏で再生成（再ビルド）を始めます。
    3. 次のアクセス：再生成が終わっていれば、最新の HTML を返し、それを新しいキャッシュとして保持します。

    ここから分かるのは、期限が切れても誰もアクセスしなければ再生成されない（時間で自動的に作り直すのではなく、リクエストがきっかけ）こと、そして 期限切れ直後のアクセスには古いページが返る ことです。

    オンデマンド再生成（トリガーによる更新）

    時間で待つのではなく、「記事を公開した」「商品を更新した」というタイミングで再生成させることもできます。Next.js では CMS の Webhook などから revalidatePath("/blog") や revalidateTag("posts") を呼び、該当ページのキャッシュを無効化します。これで「時間ベースの遅れ」を小さくできます。

    長所と短所・向いている場面

    長所

    • SSG の速さを保ちつつ、ある程度の更新頻度に追従できる
    • 全ページを毎回ビルドし直さなくてよい（ページ単位で作り直す）
    • サーバー処理は再生成のときだけなので負荷が小さい

    短所

    • 期限切れ直後も一度は古いデータが返るため、常に最新とは限らない
    • フレームワーク・ホスティングの対応に依存 する。共通の標準仕様はない
    • 動画では「簡単に使えるのは Vercel でホスティングした場合で、他のサービスでは仕組みづくりが必要かもしれない」と補足されている

    ホスティングについて補足すると、Next.js の ISR は Vercel 以外でも、next start で Node.js サーバーとして動かせば利用できます。一方、完全な静的ファイルとして書き出す構成（static export）では、再生成するサーバーがないため ISR は使えません。「再生成の基盤が必要」という点を押さえておけば十分です。

    向いている例：1〜2日に1回投稿するブログや記事サイト、ニュース一覧、商品一覧、SNS のプロフィール欄のように、「SSR ほど頻繁ではないが、ときどき更新される」「毎リクエスト DB まで見に行く必要はない」 ページです。

    8.ハイドレーション ── SSR・SSG の「見た目だけ」問題

    SSR や SSG で届いた HTML は、表示はされていても、そのままでは ボタンを押しても動かない「見た目だけ」 の状態です。ブラウザで JS を読み込み、すでにある HTML にイベント処理（クリックなど）や状態を結びつけて操作可能にする工程を ハイドレーション（hydration、水分補給） と呼びます。乾いた HTML に JS という水を与えて「生き返らせる」というイメージです。

    1. サーバー（またはビルド）で HTML を作って送る → すぐに表示される
    2. ブラウザが同じコンポーネントの JS をダウンロードする
    3. React などが HTML と仮想 DOM を突き合わせ、イベントハンドラを付ける → 操作できるようになる

    このため SSR 系の方式には 「表示は速いが、操作できるまでに時間がかかる」 という弱点があります。結局はページ全体のコンポーネントの JS をブラウザに送る必要があるので、JS の量は CSR とあまり変わりません。この重さを減らそうとして生まれたのが、次の章の発展形です。

    ハイドレーションエラー

    サーバーで作った HTML と、ブラウザで同じコンポーネントを描画した結果が食い違うと、ハイドレーションに失敗します（日時や乱数をそのまま描画した場合など）。SSR を使うときに出会いやすいエラーです。

    9.発展形：ストリーミング SSR・RSC・アイランド

    基本の4方式の弱点（SSR の待ち時間、ハイドレーションの重さ）を減らすために、新しい方式が登場しています。ここでは概要だけ押さえます。

    方式何を改善するかしくみ代表例
    ストリーミング SSRSSR で「全データが揃うまで何も返せない」問題準備できた部分から HTML を少しずつ送る。遅い部分は後から差し込むReact 18 の Suspense、Next.js App Router
    React Server Components（RSC）JS バンドルとハイドレーションの重さサーバーだけで動くコンポーネントを作り、その部分の JS をブラウザに送らない。操作が必要な部品だけ Client Component にするNext.js App Router
    アイランドアーキテクチャページ全体をハイドレーションする無駄ページは基本的に静的 HTML とし、操作が必要な「島」だけを個別にハイドレーションするAstro の client:*

    ストリーミング SSR

    通常の SSR は、ページに必要なデータがすべて揃うまで HTML を1バイトも返せません。おすすめ欄の API だけが遅くても、ページ全体が待たされます。ストリーミング SSR では、ヘッダーや本文など準備できた部分を先に送り、遅い部分は「読み込み中」の代わりを表示しておいて、データが揃いしだい同じレスポンスの中で HTML を追加で流し込みます。

    React Server Components（RSC）

    RSC では、コンポーネントを「サーバーだけで動くもの（Server Component）」と「ブラウザでも動くもの（Client Component）」に分けます。Server Component は DB や API に直接アクセスでき、描画結果だけをブラウザに送るので、その部分の JS はブラウザに届きません。ボタンやフォームなど操作が必要な部品だけを Client Component にすれば、ハイドレーションの対象も小さくなります。

    アイランドアーキテクチャ

    ページの大部分を JS なしの静的 HTML とし、検索ボックスやカルーセルなど操作が必要な部分だけを「島（island）」として個別にハイドレーションする考え方です。Astro では client:load（すぐ読み込む）や client:visible（画面に入ったら読み込む）のように、島ごとに読み込みのタイミングを指定します。

    共通する流れ

    3つに共通するのは、「JS をブラウザに送る量を減らし、サーバーでできることはサーバーでやる」 という方向です。CSR 中心だった SPA 時代から、サーバー側に振り戻す方向に進んでいます。

    10.どう選ぶか

    判断フロー

    2章の2つの軸を、質問の順番に並べると次のようになります。

    プロジェクト別の目安

    パターン生成タイミング強み向いている例
    CSRブラウザで実行時2回目以降の操作が最速マップ、座席予約、ダッシュボード、管理画面、チャット
    SSRリクエストごとにサーバーで初回が速い・SEO に強い・常に最新EC の商品詳細、個人別ダッシュボード、コンテンツサイト
    SSGビルド時非常に高速・サーバー不要ドキュメント、ヘルプ、LP、ポートフォリオ
    ISRビルド時＋定期再生成高速かつ定期的に更新適度に更新するブログ、ニュース一覧、商品一覧

    1つに決めなくてよい：ページ単位で混ぜる

    Next.js のようなフレームワークでは、ページ単位でレンダリングパターンを使い分けられる のが大きな強みです。たとえば EC サイトなら次のような組み合わせが自然です。

    ページ方式理由
    トップ・会社概要・利用規約SSGほとんど変わらない
    商品一覧・特集ページISRときどき変わるが、毎回 DB を見るほどではない
    商品詳細（在庫・価格）SSR最新の在庫・価格を表示したい、SEO も必要
    マイページ・カート・管理画面CSR（または SSR）ユーザーごとに違い、検索エンジンに読ませる必要がない

    さらに RSC やアイランドを使えば、1ページの中でも「静的な部分」「サーバーで作る部分」「ブラウザで動く部分」を部品単位で混ぜられます。仕組みを理解しておけば、プロジェクトの更新頻度やインタラクションの量 に応じて選べるようになります。

    12.Astro との対応

    ここまでの用語は Next.js を中心に語られることが多いので、Astro を使う場合の対応関係も整理しておきます。

    • Astro の デフォルト寄りは SSG です（静的に HTML を出力する）。
    • SSR やサーバー API は、アダプターを設定するオプションとして利用できます。
    • CSR に近い挙動は、client:* ディレクティブを付けて React / Vue などのコンポーネントを「島」として動かす部分で起きます（9章のアイランドアーキテクチャ）。
    • ISR は Next.js の名前として有名で、Astro 単体に「ISR」という同名の機能があるわけではありません。似た運用は「CMS 更新時に Webhook で再ビルド・再デプロイする」などで代替することが多く、別物として理解すると混乱が減ります。

    13.よくある誤解

    「SSR にすれば速くなる」

    速くなるのは主に 初回の表示 です。毎リクエストでサーバー処理が走るため、サーバーが遅ければ最初の1バイトが届くまでの時間はむしろ延びますし、ハイドレーションが終わるまでは操作もできません。2回目以降の遷移は CSR の方が速いこともあります。何を速くしたいのかを分けて考えます。

    「CSR は SEO に絶対使えない」

    Google のクローラーは JavaScript を実行してから内容を読むこともできるため、「まったく読まれない」わけではありません。ただし実行が後回しになったり、JS を実行しないクローラーや SNS のリンクプレビューでは中身が見えなかったりと 不利になりやすい のは事実です。SEO が重要なページはプリレンダリング（SSR / SSG / ISR）を選ぶのが確実です。

    「ISR は時間が来たら自動で作り直される」

    時間ベースの ISR は、期限切れ後の最初のリクエストがきっかけ で再生成されます。そのリクエスト自体には古いページが返ります（7章の図2）。すぐに反映したいなら、オンデマンド再生成（revalidatePath / revalidateTag）を使います。

    「ISR は Web の標準的な方式」

    ISR は主に Next.js の機能の名前で、共通の標準仕様はありません。他のフレームワークやホスティングでは、名前も仕組みも違う代替手段（再ビルド、CDN のキャッシュ設定など）で同じような運用をします。

    「アプリ全体で1つの方式を選ばなければならない」

    現在の主流は ページ単位、さらには部品単位で混ぜる ことです（10章）。「このサイトは SSR」と1つに決めるより、「このページは何を重視するか」で選びます。

    「SSR / SSG ならブラウザに送る JS が減る」

    従来の SSR / SSG は、ハイドレーションのためにページ全体のコンポーネントの JS を結局ブラウザに送ります。JS の量そのものを減らしたいなら、RSC やアイランドのような発展形が必要です（9章）。

    14.まとめ

    • よく並べられるのは CSR・SSR・SSG・ISR の4つ。違いは「HTML がいつ・どこで完成するか」です。
    • CSR：ブラウザで描画。2回目以降の操作は最速だが、初回表示と SEO に弱い。インタラクションの多いアプリ向き。
    • SSR：リクエストごとにサーバーで生成。最新データ・SEO・初回表示に強いが、サーバー負荷と実行環境が必要。
    • SSG：ビルド時に生成して CDN から配る。最速だが、更新のたびに再ビルドが必要。
    • ISR：SSG ＋ 後から再生成。速さと更新への追従を両立するが、期限切れ直後は古いページが返り、FW・ホスティングに依存する。
    • SSR / SSG の HTML は ハイドレーション で操作可能になる。その重さを減らすのがストリーミング SSR・RSC・アイランド。
    • 迷ったら「HTML はいつ・どこで完成するか」と「データはどのくらいの頻度で変わるか」の2軸で選び、ページ単位で混ぜます。
