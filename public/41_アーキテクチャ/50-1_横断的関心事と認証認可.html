    50 横断的関心事

    横断的関心事と認証・認可の境界

    認証・ログ・設定のように「どの機能にも必要なのに、どの業務にも属さない」関心事を、アーキテクチャ図のどこに置き、どう各機能へ行き渡らせるかを整理します。後半では代表例である認証・認可を取り上げ、ゲートウェイ・ミドルウェア・ユースケース・ドメインのどこで何を判定するかを詳しく見ます。

    もとにしたノート：50_横断的関心事/01_横断的関心事.md、02認可と認証の置き方と境界とアイデンティティ.md、00_解説_横断的関心事.md

    1.このページで扱うこと

    ここまでのページでは、主に機能をどう分けるか（層、ドメイン、サービス境界）を見てきました。50 番台では視点を変えて、どの機能にも関わるが、1つのビジネス機能だけには属さない設計上のテーマ、つまり横断的関心事（Cross-Cutting Concerns）を扱います。

    「横断的」とは、注文・在庫・会計のどの機能にもまたがる、という意味です。置き方を間違えると、各所に同じロジックが増えたり、障害時に原因が追えなくなったりします。

    この 50 番台は概要レベルです。セキュリティや SRE の専門書の代わりではなく、「アーキテクチャ図を描くとき、どこに書くか」という置き場所の判断を押さえることが目的です。

    2.横断的関心事とは

    横断的関心事とは、システムの複数の部分に共通して必要な関心事のことです。アーキテクチャは機能を縦に分けます（層・ドメイン・サービス）。ところが認証やログは、どの縦の区切りにも横から関わってきます。

    例なぜ「横断的」か
    認証Web API、バッチ、管理画面のすべてで「誰が操作しているか」が必要
    ログどの層・どのサービスでも、障害調査のために記録が必要
    設定DB 接続先、外部 API の URL など、多くの部品が参照する

    放置すると起きる3つの問題

    コピペの増殖

    全ハンドラーに同じ認証チェック・ログ出力を書き、1か所の修正漏れが障害やセキュリティホールになる。

    業務ロジックの汚染

    本来の処理の間にログ・権限チェック・設定読み込みが混ざり、読みにくく、テストしにくくなる。

    障害時に追えない

    ログの形式や ID がバラバラで、どのリクエストがどこで失敗したかがつながらない。

    対策の基本は2つ

    1. 共通基盤に寄せる：ミドルウェアやフックなど、機能から独立した場所で一括して処理します。
    2. 業務の意味を持つ部分だけは業務側に残す：「この注文をキャンセルしてよいか」「なぜ失敗したか」は業務ルールなので、ユースケースやドメインで扱います。

    これは トレードオフとアーキテクチャに効く原則 で学んだ関心の分離を、機能をまたぐ方向に適用したものです。「各機能にベタ書き」ではなく、境界を決めて1か所（または少数の箇所）に集約するのが基本です。

    3.なぜ設計段階で扱うのか

    横断的関心事は、機能要件の一覧では目立たないことが多いものです。しかし設計を後回しにすると、次のような問題が起きやすくなります。

    問題典型例
    重複各 API が独自に JWT を検証し、ルールがバラバラ
    漏れ新しいエンドポイントだけ認可チェックを忘れる
    追跡不能ログ形式がサービスごとに違い、障害時にリクエストをたどれない
    設定の散乱本番 URL がコードに直書きされ、環境ごとにビルドし直している

    アーキテクチャの仕事

    横断処理を「どこで」「誰が」「どのルールで」行うかを決めることです。

    全体像 — 1つの関心事を層ごとに分担する

    大事なのは、1つの関心事を1か所にまとめ切るのではなく、層ごとに役割を分担させることです。たとえば認可なら、「ゲートウェイでログイン済みか」「ユースケースでこの注文の持ち主か」「ドメインで締め後は変更不可か」というように、層によって判定の中身が違います。

    50 番台の読み方

    このページ（横断的関心事と認証・認可）→ 観測性 → 設定・シークレット・フィーチャーフラグ の順がおすすめです。すでに本番運用をしている場合は、観測性から入っても構いません。

    初心者が覚えておきたい3つのこと

    1. 認証と認可は別物 — 「誰か」を確かめることと、「その人が何をしてよいか」は分けて設計します（このページの第6章以降）。
    2. 観測性は後付けより最初から — ログ形式・トレース ID・メトリクスの置き場所を、図の段階で決めておきます（観測性）。
    3. シークレットはコードに入れない — 設定と秘密情報は環境や専用ストアで管理し、機能の ON/OFF はフィーチャーフラグで切り替えます（設定・シークレット・フィーチャーフラグ）。

    4.3つの代表的な横断的関心事の早見表

    詳細は各ページに譲り、ここでは「置き場所の判断」の要点だけを並べます。

    認証・認可

    • 認証は外側（入口）で早めに、細かい認可は内側（業務に近い場所）で、が基本の型です。
    • 「ここから内側は検証済みとして信用する」線＝信頼境界を明示します。
    • マイクロサービスでは「誰の操作か」を下流に伝搬させる設計が必要です。

    観測性（ログ・メトリクス・トレース）

    • 境界ごとに計測点を置く：入口（HTTP）、外部呼び出し、DB、メッセージの送受信は必ず計測します。
    • 相関 ID（requestId／traceId）を入口で発行し、ログ・メッセージ・下流の呼び出しすべてに引き継ぎます。
    • HTTP ステータスや DB エラーはインフラ・ミドルウェアで、業務上の理由はユースケースで記録します。

    設定・シークレット・フィーチャーフラグ

    項目例変わるタイミング典型的な管理
    設定DB の接続先、外部 API の URL、タイムアウトデプロイ時環境変数、設定ファイル
    シークレットパスワード、API キー、署名鍵ローテーション時シークレットマネージャー
    フィーチャーフラグ新機能の ON/OFF、段階リリースの対象割合実行中にもフラグサービス、管理画面

    5.実現手段 — ミドルウェア・AOP・サイドカー・サービスメッシュ

    横断的関心事を「各機能に書かずに行き渡らせる」ための代表的な仕組みを、効く範囲が小さいものから大きいものの順に並べます。

    手段どこで効くか仕組み例
    ミドルウェア1つのアプリの HTTP の入口リクエストが業務処理に届く前後に、共通処理をチェーン状に挟むExpress のミドルウェア、Next.js の middleware、認証チェック、アクセスログ
    AOP（アスペクト指向プログラミング）1つのアプリのメソッド単位「どのメソッドの前後に何をするか」を別に定義し、実行時に織り込むSpring の @Transactional、デコレーターでのログ・計測
    サイドカー1つのサービスの隣サービスと同じ単位で別プロセスを横に置き、通信・ログ転送などを肩代わりさせるログ収集エージェント、Envoy プロキシ
    サービスメッシュサービス間通信の全体全サービスのサイドカーをまとめて管理し、mTLS・リトライ・トレースをインフラ側で一括適用Istio、Linkerd

    選び方の目安

    • モノリスや小規模なら、ミドルウェアと共通ラッパー（DB クライアントのフック、メッセージ consumer の共通処理）で十分です。
    • AOP は便利ですが、コードを読んだだけでは何が実行されるかが見えにくくなります。トランザクション・ログ・計測など用途を絞って使います。
    • マイクロサービスで言語やチームがバラバラなときに、サイドカー・サービスメッシュが効いてきます。ただし運用の複雑さが大きく増えるので、サービス数が少ないうちは導入しないのが一般的です。

    どの手段でも共通の注意

    業務の判断（細かい認可・業務ログ）までインフラ側に押し込まないことが大切です。インフラ側に寄せてよいのは、業務の意味を持たない部分だけです。

    関連：層化・三層・レイヤード（ミドルウェア・AOP で横断処理を扱う説明）、BFF・API ゲートウェイ（ゲートウェイに集める共通処理）

    6.認証と認可を分ける

    ここからは、横断的関心事の代表である認証・認可を詳しく見ます。「ログイン機能を作る」というと、1つの画面や API に閉じた話に見えがちです。しかしアーキテクチャの観点では、システム全体のどこで「誰か」を確かめ、どこで「何ができるか」を決めるかが重要です。

    用語英語問い例
    認証Authentication（AuthN）誰かパスワードや OAuth で「この人はユーザーA」と確かめる
    認可Authorization（AuthZ）何ができるかユーザーAは「自分の注文だけ閲覧可、他人の注文は不可」
    • 401 Unauthorized — 本人確認ができていない（未ログイン、トークンが無効・期限切れ）。名前は「Unauthorized」ですが、意味は実質「未認証」です。
    • 403 Forbidden — 本人は分かったが、その操作は許可されていない。

    切り分けのコツ

    初心者が混同しやすいのは「ログインできたのに 403 が出る」ケースです。これは認証は通ったが認可で弾かれている状態、と切り分けます。

    7.アイデンティティとは

    アイデンティティ（Identity）とは、システムがリクエストを「誰（または何）」として扱うかを表す情報です。

    概念説明例
    主体（Subject）操作を行う者ユーザー、サービスアカウント、API キー
    クレーム（Claim）主体についての属性ユーザー ID、メール、所属組織
    ロール（Role）まとまった権限のラベルadmin、member、guest
    権限（Permission）具体的な操作の許可order:read、order:cancel

    人間とサービス

    分散システムでは、主体は人間だけではありません。

    • エンドユーザー — ブラウザやモバイルアプリから操作する人
    • サービス間 — 注文サービスが在庫サービスを呼ぶときの、サービス自身のアイデンティティ（サービスアカウント、mTLS など）

    アーキテクチャ図には「誰が誰を呼んでいるか」を書く習慣をつけると、認可の置き場所が見えやすくなります。

    トークンとセッション（概要）

    方式ざっくりしたイメージ向きやすい場面
    セッションサーバー側にログイン状態を保持し、クライアントは Cookie でセッション ID を送る従来型 Web、サーバー主導の画面
    JWT などのトークン署名付きの情報をクライアントが持ち、各 API が署名を検証するSPA、マイクロサービス、モバイル

    どちらも「正解」ではなく、チームの運用、失効（即時ログアウト）の要否、サービス数で選びます。ここでは詳細なプロトコルより、検証をどこで行うかに焦点を当てます。仕組みそのもの（OAuth・JWT・セッション）は（41 外のノート：73_認証認可／74_セッション管理）で学びます。

    8.どこに置くか — 境界の選択肢

    認証・認可は横断的関心事なので、1か所に集約するか、層ごとに分担するかを決めます。代表的な選択肢を4つ見ていきます。

    8.1 入口で一括（ゲートウェイ・リバースプロキシ）

    クライアント → API ゲートウェイ（認証・レート制限）→ 各マイクロサービス

    メリット

    • 各サービスが認証ロジックを持たなくてよい
    • ポリシー変更が1か所で済む

    デメリット

    • ゲートウェイをすり抜ける経路（内部通信、バッチ）の扱いを別途決める必要がある
    • 細かい業務ルールの認可（「この注文の所有者か」）はゲートウェイだけでは足りないことが多い

    BFF・API ゲートウェイ でも触れたとおり、ゲートウェイは横断的関心事の集約点としてよく使われます。

    8.2 各サービス／各 API で検証

    クライアント → 注文 API（JWT 検証）→ 注文ドメイン
            → 在庫 API（JWT 検証）→ 在庫ドメイン

    メリット

    • ゲートウェイなしの構成でも成立する
    • サービスごとに独立してデプロイしやすい

    デメリット

    • 検証ロジックや鍵の配布が各所に散らばりやすい
    • 共通ライブラリやポリシーエンジンで重複を抑える設計が必要

    8.3 ミドルウェア（フレームワークの入口）

    Web フレームワークでは、HTTP リクエストの入口にミドルウェアを置くパターンが一般的です。

    • Next.js の middleware.ts — 三層アーキテクチャ で触れた、横断的な HTTP 前処理の置き場所
    • Express／FastAPI の middleware — 認証が済んだら request.user に主体をセットする

    ここで行うのは、多くの場合認証と粗い認可（ログイン済みか、管理者か）です。

    8.4 ユースケース層・ドメイン層での認可

    「このユーザーはこの注文をキャンセルしてよいか」のようなルールはビジネスに近いため、ドメインまたはユースケース層に置くことが多いです（41 外のノート：42_ソフトウェア設計『06_ドメイン層とユースケースとアプリサービス』）。

    1. 入口：トークンが有効か（認証）
    2. ユースケース：操作者はこの注文の所有者か（認可）
    3. ドメイン：注文はキャンセル可能な状態か（ビジネスルール）

    データと結びつく認可は内側まで落とす

    認可のうち「データと結びつく部分」は、UI やゲートウェイだけに任せず、ユースケースまたはドメインまで落とすのが安全です。「API ではチェックしたが、別経路（バッチ、管理画面、別の API）からは素通りできる」という穴を防ぎやすくなります。

    9.置き方のパターン（まとめ表）

    レイヤー向いている処理向いていない処理
    API ゲートウェイ共通認証、レート制限、TLS 終端注文ごとの所有者チェック
    ミドルウェアセッション／JWT の検証、ルート単位のロール判定複雑なドメインルール
    ユースケース「この操作をしてよいか」の判定と組み立て（持ち主か、状態は正しいか）トークン署名の検証（インフラ寄り）
    ドメイン不変条件と一体の権限（例：締め後は変更不可）HTTP ヘッダーの解釈

    基本の型

    認証は外側（入口）で早めに、細かい認可は内側（業務に近い場所）で。

    10.分散システムでの注意点

    10.1 信頼境界（Trust Boundary）

    信頼境界とは、「ここから内側は検証済みとして信用する」という線のことです。インターネット向け API と内部サービス間通信では、求める認証の強さが違います。

    • 外向き：ユーザー認証が必須
    • 内部：ネットワーク分離＋サービス認証、またはゼロトラストの考え方で呼び出しごとに再認証

    「内部だから認証不要」は、侵入や漏洩が起きたときに被害を広げます。近年は、ゲートウェイを通ったからといって内部サービス同士の呼び出しを無条件に信用しないゼロトラストの設計が増えています。境界を図に書く習慣が重要です。

    10.2 アイデンティティ（認可情報）の伝搬

    BFF や API ゲートウェイを通過したあと、下流のサービスに誰が操作しているかをどう渡すかを決めます。

    • ヘッダー（X-User-Id など）— 改ざん防止が前提です。ゲートウェイだけが付与し（外から来た同名ヘッダーは捨てる）、内部ネットワークに限定します。
    • トークンそのものを転送 — 下流でも同じトークンを検証します。
    • サービス間は別のサービス用トークン — 呼び出し元サービス自身のアイデンティティで認証します（mTLS なども同じ発想）。

    11.よくある誤解

    誤解実際
    ログイン画面＝認証設計の全部サービス間・バッチ・管理 API も含めて境界を決める
    認可はフロントでボタンを非表示にすれば足りるサーバー側で必ず検証する（MVC の「UI だけで制御する MVC 違反」と同じ根っこの問題）
    ゲートウェイですべて解決する業務データに依存する認可は下流にも必要
    ロールだけで十分細かい操作単位の権限（order:cancel など）が必要になることが多い
    横断的関心事はすべて1か所に集めればよい入口で済む部分は共通基盤に寄せ、業務の意味を持つ部分は業務側に残す。層ごとの分担が基本

    12.小さな練習

    自分の（または想像の）EC システムについて考えてみましょう。

    1. 認証をどこで行うか（ゲートウェイ／各 API／ミドルウェア）を1つ選ぶ。
    2. 「他人の注文を見られない」をどの層で保証するか書く。
    3. 注文サービス → 在庫サービスの内部呼び出しは、誰として認可するか考える。

    13.まとめ

    覚えること内容
    横断的関心事とはどの機能にも必要だが、どれか1つの業務には属さない関心事（認証・ログ・設定など）
    対策の基本共通基盤に寄せる＋業務の意味を持つ部分だけ業務側に残す
    実現手段小さい順にミドルウェア・AOP、サイドカー、サービスメッシュ。規模に応じて選ぶ
    認証と認可「誰か」（401）と「何ができるか」（403）を分けて設計する
    置き場所認証は外側で早めに、データと結びつく細かい認可はユースケース・ドメインで
    分散時信頼境界を図に書き、アイデンティティの伝搬方法とサービス自身の認証を決める
