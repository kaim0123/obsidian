    40 システム・分散

    データ所有権・分散トランザクション・SAGA

    サービスを分けると、データも分かれるのが原則です。そのとき、モノリス時代のように「1つのトランザクションですべて成功させる」ことは簡単ではありません。このページでは、データの持ち主を決める「データ所有権」、分散トランザクションが難しい理由、現実的な代替である SAGA、そして強い整合性と結果整合性の使い分けを整理します。

    もとにしたノート：40_システム・分散/04データ所有権と分散トランザクションとSAGAと整合性.md（＋ 00_解説_システム・分散.md）

    1.このページで扱うこと

    • データ所有権（誰が正を持つか）とは何か
    • 分散トランザクションが難しい理由（概要）
    • SAGA という現実的な代替のイメージ
    • 整合性を「強い／最終的（結果整合性）」で考える入門

    2PC（二相コミット）の実装の詳細は扱いません。DB のテーブル設計は（41 外のノート：68_データアーキテクチャ）が本拠地で、このページは「どのサービスがどのデータを所有するか」までを扱います。前提として 分散とスタイル、同期 API・メッセージ・イベント駆動 を読んでおくと理解しやすくなります。

    分散で一番難しいのはデータ

    コードを分けるのは比較的簡単ですが、データを分けると「どこが正しい値を持つのか」「複数の更新をどうそろえるのか」という問題が一気に表に出ます。マイクロサービスの成否は、データの扱いで決まると言っても過言ではありません。

    2.データ所有権（Data Ownership）

    2-1. データ所有権とは

    データ所有権とは、ある種類のデータについて、次のように決めるルールです。

    「このデータの正（ソース・オブ・トゥルース）は、このサービス／コンテキストだけが持つ」

    2-2. なぜ重要か

    • 変更の責任がはっきりする（このデータが壊れたら、どのチームが直すのか）
    • サービス同士が同じテーブルを直接更新しなくて済む
    • DDD の境界づけられたコンテキストの「誰が正を持つか」と直結する（41 外のノート：42_ソフトウェア設計『03_境界づけられたコンテキストとコンテキストマップ』）

    2-3. よくあるアンチパターン

    アンチパターン問題
    共有 DBスキーマ変更が全サービスに波及し、分散モノリス化する（40-2）
    他サービスの DB を直接読む相手の内部構造（テーブル設計）に依存し、相手の変更に弱くなる
    同じエンティティを各所にコピーして双方向更新どちらが正なのか分からなくなる

    2-4. 他サービスのデータが必要なとき

    API で問い合わせる

    同期。常に最新を読めるが、相手が落ちていると読めない。

    イベントでコピーを持つ

    非同期。相手の更新イベントを受けて、自分の手元に読み取り用のレプリカを作る。結果整合性になる。

    読み取り専用ビュー

    表示用に複数サービスのデータを合成したビューを別途用意する（CQRS の入門イメージ）。

    やりがちな違反

    「在庫サービスのテーブルに、注文サービスが SQL で JOIN する」は、所有権の原則に反しやすい典型例です。便利ですが、在庫サービスがテーブルを変えた瞬間に注文サービスが壊れます。

    3.モノリス時代のトランザクション

    1つの DB なら、よく知られた ACID トランザクションが使えます。

    BEGIN;
  INSERT INTO orders ...;
  UPDATE stock SET quantity = quantity - 1 ...;
COMMIT;   -- 両方成功、または両方取り消し
    性質意味
    原子性（Atomicity）全部成功か、全部失敗か。途中までだけ反映されることはない
    一貫性（Consistency）制約（在庫はマイナスにならない等）を満たした状態から、満たした状態へ移る
    独立性（Isolation）同時に走るトランザクションが互いの途中状態を見ない
    永続性（Durability）コミットした結果は障害があっても失われない

    サービスが分かれると、この「1つの COMMIT」がそのままでは使えなくなります。

    4.分散トランザクションが難しい理由

    4-1. 複数の DB をまたぐ

    注文サービス（注文 DB）と在庫サービス（在庫 DB）は別のデータベースです。1つの SQL トランザクションでは括れません。

    4-2. 2PC（二相コミット）のイメージ

    理論上は 2PC（Two-Phase Commit、二相コミット）で「全部コミット」を調整できます。コーディネーターが、まず全参加者に「コミットできる状態か」を問い合わせ（準備フェーズ）、全員が OK なら「コミットせよ」と指示します（コミットフェーズ）。1人でも NG なら全員にロールバックを指示します。

    しかし、2PC には次の問題があります。

    • 遅い — 複数ノードの合意が必要で、その間ロックを持ち続ける
    • 可用性に弱い — コーディネーターが途中で落ちると、参加者がロックを持ったまま待たされることがある
    • クラウドのマネージド DB や、メッセージブローカーとの組み合わせでは使えないことも多い

    そのため、マイクロサービスでは 2PC に頼らない設計が一般的です。

    初心者向けの結論

    「分散トランザクションで全部を厳密に同時成功させる」は、最初の選択肢にしない。代わりに、ビジネスプロセスとして段階的に進め、失敗したら戻す設計（SAGA）や、少しのズレを許す設計（結果整合性）を検討します。

    5.整合性の2つのレベル

    種類意味例
    強い整合性（Strong / Immediate）読んだ瞬間、常に最新で矛盾がない1つの DB 内のトランザクション
    結果整合性（最終的整合性、Eventual Consistency）一時的にズレても、時間が経てばそろうイベントで在庫のコピーを更新する

    分散システムでは CAP 定理（一貫性 Consistency・可用性 Availability・ネットワーク分断耐性 Partition tolerance のうち、ネットワーク分断が起きたときには一貫性と可用性のどちらかを選ばなければならない、という定理）の話もよく出てきます。ただし入門としては、次の2点を押さえれば十分です。

    • ユーザーが困るズレは減らす（在庫のオーバー売れなど）
    • 許容できるズレは設計で明示する（ダッシュボードの数字が数秒遅れる、など）。在庫表示が数秒遅れても業務上問題ないかを、業務側と決めておきます

    トレードオフで学んだ「一貫性と遅延」の関係が、ここで具体的な形になります。

    6.SAGA とは

    6-1. 一言で

    SAGA は、複数ステップからなるビジネス処理を、

    • 各ステップを独立したローカルトランザクション（各サービスが自分の DB だけを更新するトランザクション）で実行し、
    • 途中で失敗したら、すでに完了したステップを打ち消す処理（補償トランザクション）を逆順に実行する

    ことで、全体として一貫した結果に近づけるパターンです。もともとは 1987 年に Hector Garcia-Molina と Kenneth Salem が、長時間かかるデータベーストランザクションのために提案した考え方です。

    6-2. 例：注文 → 在庫確保 → 決済

    正常系

    1. 注文作成（注文サービス）  ✓
2. 在庫確保（在庫サービス）  ✓
3. 決済（決済サービス）      ✓
→ 完了

    3 で失敗した場合（補償）

    1. 注文作成   ✓
2. 在庫確保   ✓
3. 決済       ✗ 失敗
── 補償 ──
2'. 在庫解放（在庫サービス）
1'. 注文キャンセル（注文サービス）

    各ステップは自分の DB だけをトランザクションで更新します。全体の「原子性」は、補償トランザクションのチェーンによって近似的に実現します。ACID のうち「独立性（Isolation）」は失われる点に注意が必要です。SAGA の途中では、他の処理から「在庫は確保済みだが決済前」という中間状態が見えます。

    6-3. オーケストレーションとコレオグラフィ

    SAGA の進め方（誰が次のステップを起こすか）には2つの方式があります。

    方式誰が進行を管理するかイメージ良い点弱い点
    オーケストレーション専用のオーケストレーターが順番に指示する指揮者がいるオーケストラ流れが1か所に書かれていて追いやすい。失敗時の補償も制御しやすいオーケストレーターに結合が集まる。ロジックが太りやすい
    コレオグラフィ各サービスがイベントを見て次を起こすダンサーが互いに合わせて踊る疎結合。中央のボトルネックがない全体の流れが見えにくい。循環依存やイベントの連鎖が追いにくい

    初心者は、まずオーケストレーションのほうが流れを追いやすいことが多いでしょう。成熟すると、イベント中心のコレオグラフィに寄せることもあります。これは、イベント駆動アーキテクチャのメディエーター型（≒オーケストレーション）とブローカー型（≒コレオグラフィ）と同じ構図です（40-3）。

    6-4. SAGA の現実的な注意点

    • 補償は必ずしも「元に戻る」わけではない — 送ってしまったメールは取り消せません。決済済みなら返金という別の業務処理が必要で、手数料などのビジネスルールも決めなければなりません。
    • 途中状態が見える — 「在庫は確保したが決済待ち」などの状態を、UI でどう見せるか（「処理中」表示など）を決める必要があります。
    • 冪等性 — 同じステップや同じ補償が2回走っても壊れないようにします（メッセージは重複して届くことがあるため）。
    • 監視 — どの SAGA がどの段階で止まっているかを追えるようにします（観測性）。

    6-5. 補足：DB 更新とイベント発行をそろえる（Outbox パターン）

    SAGA やイベントでの連携では、「自分の DB を更新する」ことと「イベントを発行する」ことを両方確実に行う必要があります。しかし DB とメッセージブローカーは別物なので、DB は更新できたのにイベント発行の直前に落ちる、ということが起こりえます（二重書き込み問題）。

    よく使われる対策が Transactional Outbox パターンです。業務データの更新と同じローカルトランザクションで、発行したいイベントを DB 内の「outbox テーブル」に書き込み、別のプロセスがそれを読み出してブローカーに送ります。こうすると「DB 更新とイベントの記録」は ACID で一緒に成功・失敗し、送信は後から確実に（ただし重複の可能性はあるので受け手は冪等に）行えます。

    7.在庫オーバー売れを防ぐ例

    結果整合性だけでは困る典型例が、在庫のオーバー売れです。

    悪い例

    注文サービスが手元の在庫のコピーを見て注文を受け付け、後からイベントで在庫を減らす。同時に注文が来ると、コピーが更新される前に両方が「在庫あり」と判断し、オーバー売れが起きる。

    現実的な対策の方向性

    • 注文確定の直前に、在庫サービスへ同期で確保を依頼する（ReserveStock）
    • 在庫サービス側で楽観ロック／悲観ロックや在庫引当テーブルを使う
    • 1商品の在庫は在庫サービスだけが更新する（所有権）

    よくある落とし所

    「全部非同期」にはしない。お金と在庫に関わるところは強めの整合性、それ以外（通知・分析・検索）は結果整合性、という切り分けがよく使われます。

    8.何をいつ使うか

    やり方向く場面避けたい場面
    1 DB トランザクションモノリス、強い整合性が必要サービス境界をまたぐとき
    2PC 系レガシー統合、特定製品の内部一般的なマイクロサービスの新規設計
    SAGA複数サービスにまたがる長いビジネスフロー補償が定義できない処理
    結果整合性分析、通知、検索インデックス在庫・残高などクリティカルな読み取り

    9.小さな練習

    「旅行予約：フライト予約 → ホテル予約 → 決済」を SAGA で考えてみてください。

    1. 各ステップの正を持つサービスはどれか
    2. ホテル予約が失敗したときの補償は何か
    3. ユーザーに見える途中状態は何か（「フライトだけ取れた」など）
    考え方の一例
    • 正を持つサービス：フライト予約はフライトサービス、ホテル予約はホテルサービス、支払いは決済サービス。
    • 補償：ホテル予約が失敗したら、フライト予約をキャンセルする（キャンセル料の扱いなど、業務ルールが必要）。
    • 途中状態：「フライト確保済み・ホテル手配中」「予約処理中」など。完了するまで「確定」と表示しない工夫が必要。

    10.よくある誤解

    誤解実際
    サービスを分けても DB は共有のままでよいスキーマ変更が全体に波及し、分散モノリスになる。データの正は1サービスに閉じる
    分散でも 2PC を使えばモノリスと同じに扱える遅く、可用性に弱く、そもそも使えない環境も多い。最初の選択肢にしない
    SAGA は分散トランザクションの完全な代替原子性を補償で近似するだけ。独立性はなく、途中状態が見える。補償も「元通り」とは限らない
    結果整合性はいつでも許される在庫・残高などお金に関わる部分では強めの整合性が必要。許容できるズレを業務側と決める

    11.まとめ

    このページのポイント

    • データ所有権：各データの正は1つのサービスだけが持ち、他は API・イベント・読み取り用ビューで扱う。共有 DB や他サービス DB の直接参照は避ける。
    • サービスが分かれると、1つの COMMIT で全部をそろえることはできない。2PC は最初の選択肢にしない。
    • 整合性には強い整合性と結果整合性があり、ユーザーが困るズレは減らし、許容できるズレは明示する。
    • SAGA はローカルトランザクションの連鎖＋補償で全体の一貫性に近づける。オーケストレーション（追いやすい）とコレオグラフィ（疎結合）がある。
    • 補償・途中状態・冪等性・監視を設計に含める。お金と在庫は強めの整合性で。
