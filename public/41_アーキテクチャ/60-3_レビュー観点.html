    60 意思決定・文書化

    アーキテクチャのレビュー観点

    アーキテクチャのレビューでは図のきれいさに目が行きがちですが、本番で困るのは境界の曖昧さ、非機能要件の抜け、運用の想定不足です。設計レビュー・PR レビュー・振り返りで使える「図・境界・非機能・運用」の4観点をチェックリストとして整理し、本格的な評価手法 ATAM の考え方にも触れます。

    もとにしたノート：60_意思決定・文書化/05レビュー観点と図と境界と非機能と運用.md（＋ 00_解説_意思決定・文書化.md のレビュー・ATAM の節）

    1.このページで扱うこと

    アーキテクチャのレビューでは、図がきれいかだけを見がちです。しかし本番で困るのは、境界の曖昧さ、非機能要件の抜け、運用の想定不足であることが多いものです。このページでは、設計レビュー・PR レビュー・振り返りで使える4つの観点を、初心者向けのチェックリストとして整理します。

    図

    誰に何を伝えるか。抽象度のレベルは適切か。

    境界

    モジュール・サービス・データのオーナーは明確か。

    非機能

    品質属性（性能・可用性・セキュリティなど）に触れているか。

    運用

    デプロイ、障害、観測は設計に含まれているか。

    前提：意思決定の進め方と ADR、品質特性と非機能要件、観測性（ログ・メトリクス・トレース）。図の描き方そのもの（C4 モデル・arc42）は 図と文書化（C4 モデル・arc42） で詳しく扱います。コードレビューの作法は（41 外のノート：81_テスト戦略／86_QAプロセス）の担当です。

    2.レビューとは何をするか

    アーキテクチャレビューの目的は、実装の細部を全部見ることではありません。後から直すと高くつく問題を、安いうちに見つけることです。

    目的説明
    リスクの早期発見後から直すと高い問題を、安い段階で見つける
    前提の共有チームが同じ地図を見ているか確認する
    トレードオフの合意何を優先し、何を犠牲にするかを言語化する

    レビューのタイミング

    • 新機能の設計提案時
    • モノリス分割・大規模リファクタリングの前
    • 本番障害の振り返りの後（学びを設計に戻す）
    • ADR が Proposed の段階（意思決定の進め方と ADR）

    4観点の全体像

    3.観点1 — 図

    図のレベルは読み手に合っているか

    図には抽象度のレベルがあります。Simon Brown が考案した C4 モデルはその代表例で、地図の縮尺のように図を段階的に拡大していきます（詳しくは 図と文書化（C4 モデル・arc42））。

    レベル見せるもの読み手の例
    1. コンテキスト（System Context）システムと外部（ユーザー、他システム）ステークホルダー、新メンバー（非技術者を含む全員）
    2. コンテナ（Container）Web アプリ、API、DB、キューなどの実行・デプロイ単位開発チーム全体、運用者
    3. コンポーネント（Component）1つのアプリ内の主要モジュール実装担当者
    4. コード（Code）クラス図など（レビューではあまり使わない）詳細設計時

    ※ C4 の「コンテナ」は Docker のコンテナではなく、「独立して動く実行単位」という意味です。

    よくある問題

    いきなりクラス図だけを出して、システム全体の位置づけが伝わらない。レビューはコンテキスト図から始めます。

    図のチェックリスト

    • □ 矢印の意味が凡例または説明にあるか（同期呼び出し？ イベント？）
    • □ 外部システムが書かれているか
    • □ データの流れ（誰が書き、誰が読むか）が分かるか
    • □ 同期・非同期が区別されているか
    • □ 図の版または日付があるか（古い図は害になる）

    4.観点2 — 境界

    何の境界を見るか

    境界の種類問い
    ドメイン境界用語・ルールがコンテキストごとに一貫しているか（41 外のノート：42_ソフトウェア設計『03_境界づけられたコンテキストとコンテキストマップ』）
    モジュール／サービス境界責務は1つに絞れているか、循環依存はないか（モジュール性・疎結合と高凝集）
    データ境界誰がそのデータの正（Source of Truth）を持つか（データ所有権・分散トランザクション・SAGA）
    チーム境界オーナーは誰か、横断的な変更はどう調整するか（コンウェイの法則と Team Topologies）

    悪い例

    注文サービスが在庫テーブルを直接 UPDATE する。在庫の正が誰なのか曖昧になり、在庫側の変更で注文が壊れる。

    良い例

    在庫サービスの API 経由で更新する。在庫データの正は在庫サービスが持つ。

    境界のチェックリスト

    • □ 単一責任 — 1つの部品の変更理由は1種類に近いか
    • □ 依存の方向 — 内側（ドメイン）が外側（UI・DB）に依存していないか（依存性逆転の原則）
    • □ 公開面 — 外部に見せる API と内部実装が分かれているか
    • □ 横断的関心事 — 認証・ログが各所にコピーされていないか（横断的関心事と認証・認可の境界）
    • □ 暫定境界 — 「とりあえず同じ DB」の場合、見直し条件が書いてあるか（技術的負債と意図的な暫定案）

    5.観点3 — 非機能（品質属性）

    品質特性と非機能要件 で学んだ非機能要件は、図の脚注に消えがちです。レビューでは、少なくとも次を明示的に聞きます。

    よく問う品質属性

    品質属性レビューでの問い設計への影響例
    性能想定 QPS・レイテンシは？ ピークは？キャッシュ、非同期化、読み取りモデル（CQRS）
    可用性止まったらどうなる？ 許容ダウンタイムは？冗長化、フェイルオーバー、デグレード
    セキュリティ誰が何にアクセスする？ 機密データは？認証・認可の置き場所、暗号化
    修正容易性どこがよく変わる？モジュール分割、インターフェース
    スケーラビリティ何を水平スケールする？ステートレス化、キュー

    非機能のチェックリスト

    • □ 数値または目安があるか（「速く」だけで終わっていないか。品質特性シナリオと計測）
    • □ トレードオフが言語化されているか（トレードオフと原則）
    • □ セキュリティ — 認証・認可・秘密情報の扱いが図または ADR にあるか
    • □ 一貫性 — 強い一貫性が必要な箇所と、緩めてよい（結果整合性でよい）箇所が分かれているか
    • □ テスト可能性 — 重要な振る舞いをどう検証するか

    6.観点4 — 運用

    「動けばよい」という設計は、本番で初めて問題になります。

    運用で見ること

    項目問い
    デプロイ無停止で出せるか、ロールバックはどうするか
    設定環境ごとの差分はどこで管理するか（設定・シークレット・フィーチャーフラグ）
    観測性障害時に何をログ・メトリクス・トレースで見るか（観測性）
    障害依存先が落ちたときの振る舞いは（BFF・API ゲートウェイ・グレースフルデグレーデーション）
    データバックアップ、移行、リストアの想定はあるか

    運用のチェックリスト

    • □ 障害シナリオを1つ以上想定しているか（依存先のダウン、DB の遅延など）
    • □ ログに載せる情報（相関 ID、ユーザー ID のマスキング）が決まっているか
    • □ アラートの条件が、ざっくりとでもあるか
    • □ 手動運用が必要な作業と、その頻度が分かっているか
    • □ オンコールが必要なら、Runbook（対応手順書）またはそのリンクがあるか

    7.レビューの進め方（初心者向け）

    30分の軽いレビュー例

    1. 5分 — コンテキスト図で「何のシステムか」を確認する。
    2. 10分 — 境界（データのオーナー、API の公開面）を確認する。
    3. 10分 — 非機能（性能・可用性・セキュリティのうち1〜2つ）を確認する。
    4. 5分 — 運用（デプロイ、障害時、観測）を確認する。
    5. メモ — 決定事項は ADR またはチケットへ残す（意思決定の進め方と ADR）。

    レビュアーでなくても使える — PR 説明の4行

    プルリクエストの説明に、次の4行を足すだけでも効果があります。

    ## 境界: 変更は注文モジュール内。在庫APIは呼び出しのみ。
## 非機能: ピーク100req/s、P95 200ms 目標。
## 運用: 既存メトリクス dashboard-X にエラー率追加。
## リスク: 在庫API障害時は注文確定をリトライキューに退避（暫定）。

    4行目の「（暫定）」のように、暫定案であることを明記しておくと、後で技術的負債として追いかけやすくなります。

    8.本格的な評価手法 — ATAM（軽く知っておく）

    ATAM（Architecture Tradeoff Analysis Method）は、カーネギーメロン大学ソフトウェア工学研究所（SEI）が体系化した、本格的なアーキテクチャ評価手法です。

    用語意味
    品質特性ユーティリティツリー品質目標を「性能 → 応答時間 → 検索は1秒以内」のように木構造で具体化したもの
    シナリオ「ピーク時に1万人が同時に検索したら」のような具体的な状況
    感度ポイントある品質特性に大きく効く設計上の選択
    トレードオフポイント複数の品質特性に逆向きに効く選択（例：暗号化はセキュリティ↑・性能↓）
    リスク／非リスク問題になりそうな決定／問題なさそうな決定

    ATAM は数日がかりの正式な手法なので、日常のレビューでそのまま使うことはまれです。ただ、「シナリオで具体化し、トレードオフポイントを見つける」という考え方は、普段のレビューでも役立ちます（トレードオフと原則、品質特性シナリオと計測）。日常の観点としては、このページの4観点（図・境界・非機能・運用）で十分です。

    リスクストーミングとの組み合わせ

    レビューの前に、意思決定の進め方と ADR で紹介したリスクマトリクスやリスクストーミングで高リスク箇所を洗い出しておくと、限られた時間をそこに集中できます。

    9.よくある誤解

    誤解実際
    図がきれいならレビューは合格本番で困るのは境界の曖昧さ・非機能の抜け・運用の想定不足。4観点で見る
    アーキテクチャレビュー＝実装の細部チェック目的は後から直すと高い問題を安いうちに見つけること。細部はコードレビューで
    非機能は「後で考える」でよい性能・セキュリティは構造に効くので、数値か目安を設計段階で出す
    レビューはレビュアーの仕事PR 説明に境界・非機能・運用・リスクの4行を書くだけで、誰でも参加できる
    本格的にやるなら必ず ATAMATAM は数日がかり。日常は4観点＋シナリオの考え方で十分

    10.まとめ — 4観点の一覧

    観点中心の問い見落としがちな例
    図誰に何を伝えるかレベルが合わない、矢印の意味が不明
    境界誰が何を持つかデータの二重管理、循環依存
    非機能どの品質を優先するか「後で考える」性能・セキュリティ
    運用本番でどう動かすかログなし、ロールバック未考慮

    成熟度の目安

    アーキテクチャの成熟度は、きれいな図を描けるかよりも、この4つを習慣的に話せるかに近いものです。
