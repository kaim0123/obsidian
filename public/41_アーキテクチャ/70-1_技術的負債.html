    技術的負債と意図的な暫定案

    技術的負債を「汚いコードの言い訳」でも「リファクタリングの口実」でもなく、管理できるものとして扱うための考え方を整理します。負債の種類と四象限、暫定案を安全に使う4点セット、利息が高いサイン、アーキテクチャ上の負債、チームでの返済の進め方が分かります。

    もとにしたノート：70_進化と組織/03技術的負債と意図的な暫定案.md、70_進化と組織/00_解説_進化と組織.md（§1 技術的負債）、00_全体像/00_解説_アーキテクチャ体系.md（§7-1）

    1.このページで扱うこと

    「技術的負債」という言葉は、汚いコードの言い訳のように聞こえることもあれば、リファクタリングの正当化に使われることもあります。実際には、負債には意図的に借りたものといつの間にかたまったものがあり、扱い方がまったく違います。

    このページでは、70 進化と組織の入口として、次のことを整理します。

    • 技術的負債とは何か（借金の比喩が意味すること）
    • 負債の種類：意図的な暫定案・無意識の負債・陳腐化した設計、そして Martin Fowler の四象限
    • 暫定案を安全に使うための「意図・範囲・期限・直し方」の4点セット
    • 「利息」が高くなっているサインと、アーキテクチャ上の負債
    • チームで負債を扱うときの実務の目安（優先順位・返済のバランス・言葉選び）

    70 進化と組織の位置づけ

    60 意思決定・文書化が「今の決定をどう決めて残すか」なら、70 はその決定が古くなったあとの話です。「放っておくと劣化する」→「測って気づく」→「少しずつ直す」→「組織もそれに合わせる」という流れで、このページは最初の「劣化」を扱います。測る・直すは 進化的アーキテクチャと適応度関数、組織は コンウェイの法則と Team Topologies で扱います。

    前提として 意思決定の進め方と ADR と なぜ早く意識するか・アーキテクトの役割と思考（変更コスト・チーム・長期保守）を読んでおくと理解しやすくなります。

    2.技術的負債とは — 借金の比喩

    技術的負債（Technical Debt）は、Ward Cunningham が 1992 年に使い始めた比喩です。

    今は楽で早い選択をした結果、将来の変更や保守に余分なコストがかかるようになった状態

    金融の「借金」にたとえると、それぞれ次のものにあたります。

    借りたとき

    早くリリースできた。機能を先に出せた。市場の機会をつかめた。

    利息

    同じ変更にかかる時間が増える。バグが出やすくなる。新しく来た人が理解しにくい。

    返済

    リファクタリング、設計の見直し、テストの追加。

    負債は必ずしも悪ではない

    重要なのは、負債は必ず悪というわけではないという点です。お金の借金と同じで、期限のある市場機会のために意図的に借りることは、戦略的な判断になり得ます。問題になるのは、借りたことを忘れること、そして利息を払い続けていることに気づかないことです。

    3.負債の種類

    意図的な暫定案・無意識の負債・陳腐化した設計

    種類特徴例
    意図的な暫定案「今はこうする。理由と直し方を知っている」MVP では在庫同期を手動バッチで行い、3か月後に API 化する
    無意識の負債「気づいたらこうなっていた」コピー＆ペーストが増え、どれが正しい実装か分からない
    陳腐化した設計当時は正しかったが、前提が変わったトラフィックが10倍になり、当時の DB 設計が限界に来た

    アーキテクチャの会話では、意図的な暫定案を負債として認め、管理することが大切です。「暫定」であることを隠すと、それはやがて無意識の負債に変わります。

    Martin Fowler の負債の四象限

    Martin Fowler は、負債を「意図的（Deliberate）か / うっかり（Inadvertent）か」と「無謀（Reckless）か / 慎重（Prudent）か」の2軸で4つに分けました。

    無謀（Reckless）慎重（Prudent）
    意図的（Deliberate）「設計する時間はない」
    → 分かっていて雑に作る    		「今は出荷を優先し、結果は受け入れる」
    → 意図的な暫定案
    うっかり（Inadvertent）「レイヤー分けって何？」
    → 知識不足で生まれる    		「今なら、どう作るべきだったか分かる」
    → 学習の結果として気づく
    • 右上（意図的・慎重）の負債は、戦略として正当になり得ます。そのためには、次の節の「意図・範囲・期限・直し方」の4点セットを決め、ADR に残します（ADR）。
    • 右下（うっかり・慎重）は、どれだけ優秀なチームでも必ず生まれます。システムを作りながらドメインへの理解が深まっていくからです。これは失敗ではなく学習の証拠であり、気づいた時点で記録して扱えばよいものです。
    • 左側（無謀）の2つは避けたい負債です。左上は「借りている自覚はあるが返す計画がない」状態、左下は「借りていることにすら気づいていない」状態です。左下は教育やレビュー、左上は次の4点セットを習慣にすることで減らせます。

    4.意図的な暫定案を使うときの4点セット

    暫定案を採用するときは、次の4つをセットで決めます。どれか1つでも欠けると、暫定案はいつの間にか「恒久的な雑な実装」になります。

    #項目問い例
    1意図なぜ今は完璧にしないのかデモの期限が2週間後
    2範囲どこまでが暫定なのか管理画面のエクスポートだけ CSV を直接書き出す
    3期限・条件いつ、何が起きたら直すのか正式リリース前、またはユーザーが100人を超えたら
    4直し方どう直すのか（ざっくりでよい）ジョブキュー＋オブジェクトストアに移行する

    これを ADR やチケット、README の「Known limitations（既知の制約）」に書いておくと、後から「そんなことは知らなかった」となりにくくなります（意思決定の進め方と ADR）。

    ADR に書く場合の例

    4点セットは、ADR の「決定」「結果」「見直し条件」にそのまま収まります。

    docs/adr/0012-export-csv-temporary.md（例） 
    # ADR-012: 管理画面のエクスポートは暫定的に CSV を直接書き出す

## ステータス
Accepted

## 状況
- 投資家向けデモが2週間後にある（意図）
- 大量データのエクスポートを非同期にする仕組みはまだない

## 決定
管理画面のエクスポート機能に限り、リクエストの中で CSV を直接生成して返す（範囲）。

## 結果
- 良い: デモに間に合う
- 受け入れる: 件数が多いとタイムアウトする可能性がある

## 見直し条件
- 正式リリース前、またはユーザーが100人を超えたら（期限・条件）
- ジョブキュー＋オブジェクトストアによる非同期エクスポートに移行する（直し方）

    コードに残す軽い方法

    ADR を書くほどではない小さな暫定案は、コードのコメントに追跡用の ID を付けて残す方法もあります。

    # TEMP(debt-42): 在庫は夜間バッチで同期。注文API化は Q3 で対応予定。
def sync_inventory():
    ...

    debt-42 のように ID を振っておくと、grep で一覧にしたり、チケットと結び付けたりしやすくなります。ID のない「TODO」は誰も追跡しないまま残りがちです。

    5.負債の「利息」が高いサイン

    次のような状態は、返済（リファクタリングや設計の見直し）を検討するタイミングです。

    サイン意味
    小さな変更に何日もかかる結合が強く、影響範囲が読めない
    同じバグが何度も出る根本の構造に問題がある
    新しいメンバーが何か月も理解できない複雑さが知識の属人化を生んでいる
    テストを書くのが怖い設計が変更に耐えられなくなっている
    「そこは触らないで」が口癖になっている運用上のリスクが積み上がっている

    これらは、品質特性でいう修正容易性（Modifiability）が落ちている状態と考えてよいでしょう（品質特性と非機能要件）。結合の強さを測る見方は 結合の指標 や コナーセンス も参考になります。

    6.アーキテクチャ上の負債

    コードの汚さより高くつくのが、構造そのものの負債です。技術的負債は、しばしば境界の曖昧さから生まれます。

    負債の例アーキテクチャ上の原因関連ページ
    ドメインのルールがコントローラに散らばっている層の分離が崩れている層化・レイヤード
    レイヤーの依存方向が崩れ、ドメインが DB に依存している依存性のルールが守られていない依存性のルール
    サービス間の循環依存境界づけられたコンテキストが不明確41 外のノート：42_ソフトウェア設計『03_境界づけられたコンテキストとコンテキストマップ』
    サービスを分けたのに DB を共有しており、分散モノリスになっているデータの所有権が決まっていないモノリス・分散モノリス・マイクロサービス
    認証やログの処理が各所にコピーされている横断的関心事の置き場所が決まっていない横断的関心事
    設定がコードに直接書かれている設定の置き場所が決まっていない設定・シークレット

    だから負債の話は「コードが汚い」だけで終わらず、設計の見直しにつながります。アーキテクチャのレビュー観点（図・境界・非機能・運用）で定期的に点検するとよいでしょう。

    構造の負債は一度に返せない

    アーキテクチャ上の負債は影響範囲が広く、一度に返すことはできません。そこで、適応度関数で悪化を止め（新しい違反を CI で検出する）、移行パターンで少しずつ返す（ストラングラーフィグなど）という二段構えをとります。詳しくは 進化的アーキテクチャと適応度関数 で扱います。

    7.チームで負債を扱う実務の目安

    全部直そうとしない

    負債はゼロにはなりません。ビジネス価値と「利息」の大きさで優先順位をつけます。

    状況対応
    影響が大きい × 利息が高い早めに返済
    影響が小さい × 利息が低い様子見 触るときに直す
    影響が大きい × 触る機会がない境界だけ整える 大規模な変更は計画を立てて行う

    「利息が高い」とは、そのコードを頻繁に変更しているということでもあります。ほとんど変更しない部分の負債は、汚くても利息はほとんど発生しません。どこから返すかを決めるときは、汚さよりも変更の頻度に注目すると判断しやすくなります。

    新機能と返済のバランス

    よく使われる考え方は次の3つです。

    継続的に少しずつ

    機能開発の時間の一部（例えば2割程度）を、継続的にリファクタリングに充てる。割合はチームによって異なります。

    ボーイスカウトルール

    「来たときよりもきれいにして帰る」。触ったファイルは少しきれいにしてから出す。

    ストラングラーフィグ

    古い部分を少しずつ新しい実装に置き換える（移行パターン）。

    「負債」と言うときの言葉をそろえる

    「技術的負債」は感情的になりやすい言葉です。「誰が汚くしたのか」という責任追及に聞こえることもあります。会議では、次のように言い換えると建設的になりやすくなります。

    • 「この暫定案の見直し条件はまだ有効ですか？」
    • 「ここを直すと、次の3つの機能がどれだけ楽になるか」
    • 「返済しない場合のリスク（障害・セキュリティ・採用）」

    ビジネス側の人と話すときは、「リファクタリングしたい」ではなく「この変更にかかる日数を減らせる」「この種類の障害を防げる」のように、利息の大きさを相手の言葉で伝えるのがコツです。

    8.負債を記録して見えるようにする

    負債を管理するには、まずどこにどんな負債があるかが見えることが必要です。意図的な暫定案は正当な判断ですが、記録と返済計画がないと「ただの劣化」になります。

    記録する場所向いているもの
    ADR の「結果」「見直し条件」アーキテクチャ上の決定として借りた負債（ADR）
    arc42 の第11章「リスクと技術的負債」既知の負債の一覧。優先順位と返済方針を添える（C4 モデルと arc42）
    チケット（課題管理）返済作業そのもの。追跡用 ID と紐付ける
    コードのコメント（TEMP(debt-42) など）小さな暫定案。どこが暫定かをコードの場所で示す
    README の Known limitations利用者や新メンバーに知らせるべき制約

    記録した負債は、レビューのたびに「見直し条件はまだ有効か」「期限が過ぎていないか」を確認します。こうして「決める → 残す → 確かめる」のループに乗せることで、負債は管理された状態に保たれます。

    9.よくある誤解

    誤解実際
    技術的負債はすべて悪いもの意図的・慎重な負債は戦略として正当になり得る。問題は記録と返済計画がないこと
    技術的負債＝汚いコードより高くつくのは構造（境界・依存の向き・データの所有権）の負債。陳腐化した設計のように、当時は正しかったものも負債になる
    負債はゼロにするべきゼロにはならない。利息（変更頻度×影響）が高いところから優先して返す
    優秀なチームなら負債は生まれない作りながらドメインを理解するので、「今ならこう作る」という負債は必ず生まれる
    負債がたまったら一気に作り直せばよいビッグバンの書き直しは失敗しやすい。適応度関数で悪化を止め、移行パターンで少しずつ返す
    暫定案は「後で直す」と言っておけば十分意図・範囲・期限・直し方の4点セットを記録しないと、暫定案は無意識の負債に変わる

    10.まとめ

    覚えること内容
    負債とは今の楽さの代わりに、将来の変更コスト（利息）が増える状態
    四象限意図的／うっかり × 無謀／慎重。意図的・慎重な負債は戦略になり得る
    意図的な暫定案悪ではない。意図・範囲・期限・直し方をセットにして記録する
    無意識の負債記録とレビューなしでたまる。避けるべきはこちら
    アーキテクチャ上の負債境界の曖昧さから生まれる。適応度関数で悪化を止め、移行パターンで返す
    返済全部ではなく、利息が高いところから優先する
