    観測性（ログ・メトリクス・トレース）

    本番で「今何が起きているか」「障害の原因はどこか」を知るための仕組みが観測性です。ログ・メトリクス・トレースの違いを押さえたうえで、それらをサービス境界・層・通信方式とどう結びつけ、設計段階で何を決めておくべきかを整理します。

    もとにしたノート：50_横断的関心事/03観測性とログとメトリクスとトレースとアーキテクチャ上の接点.md（＋ 00_解説_横断的関心事.md の観測性の節）

    1.このページで扱うこと

    システムが本番で動き始めると、「今何が起きているか」「障害の原因はどこか」を知る必要が必ず出てきます。そのための仕組みをまとめて観測性（Observability）と呼びます。

    このページでは次の3つを整理します。

    • ログ（Logs）、メトリクス（Metrics）、トレース（Traces）の違い
    • なぜ観測性を、アーキテクチャ（境界・層・サービス分割）と設計段階で結びつけるのか
    • 初心者が最初に決めておくとよい最低限の約束事

    ここで扱うのは「計測点と相関 ID の設計」までです。OpenTelemetry や分散トレーシング基盤などのツールと運用は（41 外のノート：65_可観測性）、構造化ログの実装は（41 外のノート：34_Backend『70_エラー処理・ロギング』）で扱います。

    前提：横断的関心事と認証・認可の境界、分散とスタイル、品質特性と非機能要件（運用性・可用性）

    2.観測性とは

    観測性とは、システムの内部状態を、外部に出てくる出力（ログ・メトリクス・トレース）から推測できる度合いのことです。

    監視（Monitoring）

    あらかじめ決めた指標が閾値を超えたらアラートを出す。「想定していた問題」を見張るイメージ。

    観測性（Observability）

    想定外の事象にも、データから原因をたどれる度合い。「想定していなかった障害も調べられる」ことを目指す。

    実務では、監視と観測性はセットで語られることが多いです。監視が「何かがおかしい」と知らせ、観測性が「なぜおかしいのか」を調べさせてくれる、という関係です。

    アーキテクチャとの接点

    設計上の選択起きること必要になるもの
    サービスを分けた1リクエストが複数プロセスをまたぐトレース ID
    非同期（メッセージ）にした処理のつながりが見えにくい相関 IDと構造化ログ
    レイヤーを分けたどの層で失敗したか分かりにくい層ごとに何をログに残すかの設計

    観測性は設計の一部

    同期 API・メッセージ・イベント駆動 でも、イベント駆動は「デバッグが難しい」と触れました。観測性はその対症療法ではなく、設計の一部です。

    3.三本柱：ログ・メトリクス・トレース

    種類何を記録するか何がわかるか・向いている問い例
    ログ離散的なイベント・メッセージ個別の出来事の詳細。「この注文 ID で何が起きた？」orderId=123 cancel failed: out of stock／「注文 123 のキャンセルが、締め後のため拒否された」
    メトリクス数値の時系列（集計）数値の傾向。「今エラー率は上がっている？」リクエスト数、5xx の割合、P95／P99 レイテンシ
    トレース1リクエストの経路と所要時間1リクエストの旅路。「どのサービスが遅い？」ゲートウェイ → BFF → 注文 → 在庫 → DB の各所要時間

    典型的な調査の流れは、メトリクスで異常に気づく（エラー率が上がった）→ トレースで遅い・失敗した区間を特定する（在庫サービスで時間がかかっている）→ ログでその区間の詳細を読む（タイムアウトの原因）、という順番です。3つは役割が違うので、どれか1つでは足りません。

    3.1 ログ（Logs）

    テキストや JSON で「何が起きたか」を残すものです。良いログの目安は次のとおりです。

    • 構造化 — JSON など、機械がパースしやすい形式にする
    • 相関 ID — 同じリクエストを requestId／traceId でつなぐ
    • コンテキスト — ユーザー ID、注文 ID など、調査に必要な ID を載せる
    • レベル — DEBUG／INFO／WARN／ERROR を使い分ける
    ✕ 避けたい例 
    Error occurred
login ok user=alice password=hunter2 token=eyJhbGciOi...
    ○ 良い例（構造化・相関 ID・コンテキストあり） 
    {"level":"WARN","time":"2026-10-05T09:12:03Z","service.name":"order",
 "traceId":"abc-123","requestId":"req-789","userId":"u-42","orderId":"123",
 "event":"CancelOrder.rejected","reason":"already_closed"}

    避けたいこと

    • パスワード・トークン・個人情報の平文出力
    • 「エラーが発生しました」だけで原因が分からないメッセージ

    3.2 メトリクス（Metrics）

    数値を定期的に集計し、ダッシュボードやアラートに使います。

    種類性質例
    カウンタ増える一方の累計値リクエスト総数、エラー件数
    ゲージ上下する現在値現在の接続数、キュー長
    ヒストグラム値の分布レイテンシの分布（P50、P95、P99）

    アーキテクチャ上は、各サービスの境界（HTTP ハンドラー、メッセージ consumer の入口）でメトリクスを取ると、「どの境界がボトルネックか」が分かりやすくなります。なお P95 とは「95% のリクエストがこの時間以内に収まる」値で、平均では見えない一部の遅いリクエストを捉えるために使います。

    3.3 トレース（Traces）

    1つの操作がシステム内をどう流れたかを、スパン（Span）の木構造で記録します。スパンは「ある区間の処理」1つ分で、開始時刻・所要時間・親スパンを持ちます。

    分散システムでは、同じ traceId を HTTP ヘッダーで下流へ伝搬するのが定番です（W3C Trace Context の traceparent ヘッダーが標準）。モノリスでも、リクエスト開始時に ID を発行してログに載せるだけで、調査がぐっと楽になります。

    4.アーキテクチャ上の「接点」

    観測性はインフラチームだけの仕事ではなく、サービス境界・層・通信方式を決める段階から関わる横断的関心事です。

    4.1 境界（Boundary）ごとに計測点を置く

    入口（HTTP）、外部呼び出し、DB、メッセージの送受信は必ず計測します。

    図にメモしておく

    C4 図やシーケンス図を描くとき、「ここでログ／メトリクスを取る」とメモしておくと、実装時の漏れが減ります（C4 については 図と文書化（C4 モデル・arc42））。

    4.2 横断的関心事としての実装 — 共通基盤に寄せる

    レイヤードアーキテクチャ では、ログ・認証・トランザクションをミドルウェアや AOP で扱うと説明しました。観測性も同じで、各ハンドラーにコピペするより、次のように共通基盤へ寄せます。

    • HTTP ミドルウェアで requestId を発行し、アクセスログとレイテンシを記録する
    • ORM／DB クライアントのフックでスロークエリをログに出す
    • メッセージ consumer の共通ラッパーで処理時間を記録する
    // Express の例：入口で requestId を発行し、全ログと下流呼び出しに引き継ぐ
app.use((req, res, next) => {
  req.requestId = req.get("x-request-id") ?? crypto.randomUUID();
  res.set("x-request-id", req.requestId);
  const start = Date.now();
  res.on("finish", () => {
    logger.info({ requestId: req.requestId, path: req.path,
                  status: res.statusCode, ms: Date.now() - start });
  });
  next();
});

    4.3 ドメイン層と観測性の線引き

    置き場所記録するもの（例）
    インフラ・ミドルウェアHTTP ステータス、レイテンシ、DB 接続エラー
    ユースケースCancelOrder の開始・失敗・成功、ビジネス上の拒否理由
    ドメイン通常はログを厚くしない（ドメインの純度を保つ）。重要な出来事はドメインイベントとして発行し、別途記録してもよい

    ビジネス理由

    「なぜキャンセルできなかったか」は業務の理由なので、ユースケースまたはドメインの近くで意味のあるログを残す。

    インフラ理由

    「DB 接続がタイムアウトした」はインフラ寄りなので、ミドルウェアや DB クライアントのフックで記録する。

    5.サービス分割と観測性

    5.1 モノリス

    • 1つの traceId（requestId）で十分なことが多い
    • ログの集約先（ファイル、stdout → ログ基盤）を1プロジェクトで統一する

    5.2 マイクロサービス

    • 分散トレーシング（OpenTelemetry など）の導入を検討する
    • ログのフィールド名（traceId、spanId、service.name）をチームで統一する
    • ダッシュボードはサービス横断で「ユーザー体験」が見えるように設計する

    5.3 非同期（メッセージ・イベント）

    メッセージにもトレース情報を載せないと、イベントの先で流れが途切れます。

    同期 API・メッセージ・イベント駆動 の非同期処理では、メッセージ ID と元リクエスト ID を対応づける設計が重要です。

    6.SLI / SLO の入口（アーキテクチャとの関係）

    本番運用では、何をもって「正常」とするかを数値で決めることがあります。

    用語意味例
    SLI（Service Level Indicator）測る指標。「何を測れば利用者の満足度がわかるか」可用性（成功したリクエストの割合）、レイテンシ
    SLO（Service Level Objective）目標値。「どこまでを目標とするか」99.9% のリクエストが 500ms 以内
    • 品質特性と非機能要件 や 品質特性シナリオと計測 で書いた「測れる目標値」が、運用では SLI／SLO になります。
    • SLI／SLO を決めると、計測点が自然に決まります（その指標を測れる場所に計測を置く）。
    • アーキテクチャの選定（同期か非同期か、キャッシュの有無）が、SLO を達成できるかに直結します。

    7.最初に決めておく約束事（チェックリスト）

    ノートの内容から、設計の初期に決めておきたい最低限の項目をまとめます。

    1. 相関 ID：入口で発行し、ログ・メッセージ・下流の呼び出しすべてに引き継ぐ。
    2. ログ形式：構造化（JSON）、共通フィールド名（traceId、service.name など）、レベルの使い分け。
    3. 計測点：入口（HTTP）、外部呼び出し、DB、メッセージ送受信。
    4. 層ごとの分担：インフラ理由はミドルウェア、業務理由はユースケース。ドメインは薄く。
    5. 出してはいけない情報：パスワード・トークン・個人情報のマスキング。
    6. SLI／SLO：利用者の満足度を表す指標と目標値。

    8.よくある誤解

    誤解実際
    ログを大量に出せば観測性が高い意味のあるフィールドと相関 ID がないと探せない
    メトリクスだけあれば十分個別事象の調査にはログ・トレースも必要
    本番リリース後に考えればよい形式・ID・計測点は最初から決めた方が安い
    観測性＝監視ツールの導入ツールは手段。何を記録するかが設計

    9.小さな練習

    1. 自分のプロジェクトに、1リクエストを追う ID があるか確認する。
    2. アーキテクチャ図に、メトリクス／ログの計測点を3か所書き込む。
    3. 「注文キャンセル失敗」をログに残すなら、どの層でどんなフィールドを付けるか決める。

    10.まとめ

    覚えること内容
    観測性とは外部への出力から内部状態を推測できる度合い。想定外の障害も調べられることを目指す
    三本柱ログ＝個別の出来事、メトリクス＝数値の傾向、トレース＝1リクエストの旅路
    計測点境界ごと（入口・外部呼び出し・DB・メッセージ）に置き、共通基盤で実装する
    相関 ID入口で発行し、同期・非同期を問わず全部に引き継ぐ
    層の分担インフラ理由はミドルウェア、業務理由はユースケース、ドメインは薄く
    SLI／SLO測る指標と目標値。決めると計測点が決まり、アーキテクチャ選定にも効く
