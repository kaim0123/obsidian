    40 システム・分散

    BFF・API ゲートウェイ・グレースフルデグレーデーション

    サービスが増えると、ブラウザやアプリから見た「入口」と、一部が壊れたときの振る舞いが重要になります。このページでは、全クライアント共通の入口である API ゲートウェイ、画面ごとの専用バックエンドである BFF の違いと配置、そして一部が故障しても主要機能を続けるグレースフルデグレーデーションの考え方と実装手段を整理します。

    もとにしたノート：40_システム・分散/05BFFとAPIゲートウェイとグレースフルデグレーデーション.md（＋ 00_解説_システム・分散.md）

    1.このページで扱うこと

    • API ゲートウェイとは何か
    • BFF（Backend for Frontend）とは何か、API ゲートウェイとの違い
    • グレースフルデグレーデーション — 一部が壊れても、可能な範囲でサービスを続ける考え方

    前提として 分散とスタイル、同期 API・メッセージ・イベント駆動 を読んでおくと理解しやすくなります。フロントエンド側から見た BFF は BFF・マイクロフロントエンド、ゲートウェイに置く認証の考え方は 横断的関心事と認証・認可の境界 もあわせて読むと全体像がつかめます。

    2.なぜ「入口」が必要になるのか

    マイクロサービスを、フロントエンドからそのまま直接呼ぶと、次のような問題が出ます。

    直接呼び出しの問題

    • 呼び先が多すぎる — 画面1枚のために何往復も通信する（モバイル回線では特に遅い）
    • 認証を各所で繰り返す — 全サービスがインターネットに晒され、それぞれが認証・レート制限を実装する
    • 画面1枚分のデータを集めるのにクライアントが頑張る — 集約・整形のロジックがアプリ側に散らばる
    • 内部のサービス分割を変えると、クライアントも修正・再配布が必要になる

    そこで、入口を1か所（またはクライアントの種類ごと）にまとめるパターンが、API ゲートウェイや BFF です。

    3.API ゲートウェイ

    3-1. API ゲートウェイとは

    API ゲートウェイは、クライアントとバックエンドの前に立つ単一の入口です。すべてのリクエストがまずゲートウェイを通り、そこから各マイクロサービスに振り分けられます。ゲートウェイでは、ルーティング、認証・レート制限、SSL/TLS 終端、ログ・メトリクスの収集などを行います。

    代表的な製品：Kong、AWS API Gateway、Azure API Management、Envoy など。

    3-2. 主な役割

    役割説明
    ルーティング/orders → 注文サービス、/stock → 在庫サービス のように振り分ける
    横断的関心事認証の一次チェック、レート制限、CORS、HTTPS（SSL 終端）、ログ・メトリクス（横断的関心事）
    集約（限定的）複数サービスの結果をまとめて返すこともある
    保護内部サービスを直接インターネットに晒さない

    ゲートウェイは、インフラ寄りの横断レイヤーとして使われることが多いです。

    3-3. 注意点

    • ゲートウェイにビジネスロジックを詰め込みすぎない — 太るとボトルネックになり、どのチームの変更もゲートウェイを触る「変更の塊」になる
    • 単一障害点になりうる — 全リクエストが通るため、冗長化・ヘルスチェックが必要

    4.BFF（Backend for Frontend）

    4-1. BFF とは

    BFF は、特定のフロントエンド（Web、モバイル、管理画面など）向けに最適化したバックエンドです。Web ブラウザには Web BFF、モバイルアプリには Mobile BFF を用意し、それぞれが背後の注文・在庫・会員などのサービスを呼び出します。このパターンは Sam Newman が 2015 年に記事で紹介して広まりました（SoundCloud での実践がもとになっています）。

    同じ「商品詳細ページ」でも、

    • Web は SEO 用の HTML と多めの情報が欲しい
    • モバイルは軽量な JSON と、画面サイズに合った画像が欲しい

    というように、画面の要望が違うときに BFF が効きます。1つの汎用 API ですべてのクライアントに対応しようとすると、どのクライアントにとっても中途半端な API になりがちだからです。

    4-2. 主な役割

    役割説明
    API の集約画面に必要なデータを1リクエストで返す
    レスポンスの整形フロントに不要なフィールドを落とし、画面に合った形にする
    フロント特化のロジック表示順、ページネーション、キャッシュ戦略
    バックエンドの変更を隠す内部サービスの分割・統合を、フロントから切り離す

    4-3. API ゲートウェイとの違い

    観点API ゲートウェイBFF
    主な目的横断的関心事、ルーティング画面・クライアント向けの API 設計
    誰が書くかインフラ／プラットフォーム寄りのチームフロントチームやその近くのチーム
    ロジック薄いのが理想集約・整形のロジックを持つ
    個数しばしば1つ（環境ごと）クライアントの種類ごとに複数ありうる

    4-4. 配置：ゲートウェイの内側に BFF

    実務では、ゲートウェイの内側に BFF を置く構成がよく使われます。クライアント → API ゲートウェイ（認証・レート制限）→ BFF → マイクロサービス という流れです。

    5.グレースフルデグレーデーション

    5-1. グレースフルデグレーデーションとは

    グレースフルデグレーデーション（Graceful Degradation）とは、システムの一部が故障・遅延していても、可能な範囲で主要機能を続け、壊れた部分だけ機能や品質を段階的に落とす設計・運用の考え方です。

    「全部動くか、全部落ちるか」の二択を避けるための考え方で、可用性（品質特性）に直結します。分散システムでは、どこかが常に壊れている可能性があるという「障害は前提」の発想が出発点です。

    5-2. 例

    障害デグレードの例
    おすすめ API が落ちた商品一覧は表示するが、おすすめ欄だけ非表示にする
    レビュー API が遅いタイムアウト後はレビューなしでページを表示する
    在庫 API が落ちた購入ボタンを無効化する（在庫不明のまま売らない）
    決済が落ちた注文は受け付けず、はっきりエラーにする（ここはデグレードしない）

    何を落としてよいかはビジネス判断

    「おすすめがなくても買える」は OK、「在庫不明のまま売る」は NG、というように、機能ごとに優先度を決めます。技術者だけで決めず、業務側と合意しておくことが大切です。

    5-3. 実装の手段

    手法説明
    タイムアウト遅い依存先を待ち続けない。待ち時間の上限を決める
    サーキットブレーカー連続して失敗したら、一時的に呼び出し自体を止める（下で詳しく）
    フォールバックキャッシュ、デフォルト値、簡略版のレスポンスを返す
    機能フラグ障害時に該当機能をリモートで OFF にする（設定・シークレット・フィーチャーフラグ）
    バルクヘッド（隔壁）スレッドプールや接続プールを依存先ごとに分け、1つの遅延が全体を塞がないようにする（船の隔壁と同じ発想）

    BFF やゲートウェイは、複数のサービスを集約する場所なので、集約時にタイムアウトとフォールバックを入れやすい場所です。

    5-4. サーキットブレーカーの状態

    サーキットブレーカーは、Michael Nygard『Release It!』で広まったパターンで、家庭のブレーカーと同じく「異常が続いたら回路を切る」仕組みです。3つの状態を行き来します。

    Open の間は相手を呼ばずにすぐ失敗（またはフォールバック）を返すので、弱っている相手にさらに負荷をかけず、呼び出し側のスレッドも待ちで詰まりません。これが連鎖障害を防ぐ鍵です。

    5-5. ユーザー体験

    • 何が使えないかを、可能なら伝える（「おすすめを読み込めませんでした」）
    • サイレントに壊れるより、制御された劣化のほうが信頼されやすい
    • クリティカルパス（ログイン、決済、在庫）は、デグレードではなく明確な失敗を選ぶのも選択肢

    6.3つをまとめて見る

    Web 画面からのリクエストは、まず API ゲートウェイで認証・レート制限を受け、Web BFF が画面用に注文・在庫サービスの結果を集約します。おすすめサービスへの呼び出しにはタイムアウトを設定し、障害時はおすすめ欄だけを省略してページを返します。

    7.よくある誤解

    誤解実際
    BFF ＝ ゲートウェイ役割が違う。併用することが多い
    ゲートウェイですべてを集約すればよい集約しすぎると BFF 相当の太さになり、変更が重くなる
    デグレード ＝ エラーを隠すこと意図した劣化であり、監視とログは必要（観測性）
    全部フォールバックすれば安全在庫・決済などは失敗を明示したほうが安全なこともある

    8.小さな練習

    自分の（または想像の）EC サイトのトップページについて考えてみてください。

    1. 必須のデータ（なければページ自体を出せない）は何か
    2. あればよいデータ（おすすめ、バナー、レビュー件数など）は何か
    3. BFF を置くとしたら、1つの API で何をまとめて返すか

    必須と任意を分けるだけで、グレースフルデグレーデーションの設計がぐっとしやすくなります。任意のデータにはタイムアウトとフォールバックを、必須のデータには明確なエラー表示を用意します。

    9.まとめ

    このページのポイント

    • サービスを直接呼ぶと、呼び先・認証・集約の負担がクライアントに乗る。入口をまとめるのが API ゲートウェイと BFF。
    • API ゲートウェイ：全クライアント共通の単一の入口。ルーティングと横断的関心事を担い、ロジックは薄く。単一障害点にならないよう冗長化する。
    • BFF：クライアントの種類ごとの専用バックエンド。集約・整形を担い、フロントチームの近くで作る。
    • 実務では クライアント → ゲートウェイ → BFF → サービス の配置が多い。
    • グレースフルデグレーデーション：一部が壊れても主要機能を続ける。何を落としてよいかはビジネス判断。タイムアウト・サーキットブレーカー・フォールバック・機能フラグ・バルクヘッドで実現する。
