    インターフェースと抽象化

    DIP や DI の土台になっている「抽象化」と「インターフェース」を、身近な例から言語別の書き方まで解説します。抽象度を上げすぎ・下げすぎたときに何が起きるのか、良いインターフェースを設計するコツ、そして「抽象化しすぎ」を避ける判断基準が分かります。

    もとにしたノート：04_インターフェースと抽象化.md

    1.このページで扱うこと

    設計を学び始めると、「抽象」という言葉に何度も出会います。

    • 「具体ではなく抽象に依存せよ」（DIP：依存性逆転の原則）
    • 「実装ではなく、インターフェースに対してプログラミングせよ」（GoF『デザインパターン』）
    • 「詳細を隠せ」（情報隠蔽）

    これらすべての核心にあるのが 抽象化（Abstraction） と インターフェース（Interface） です。このページでは次の内容を扱います。

    • 抽象化とは何か、インターフェースとは何か
    • なぜ抽象化が大事なのか（5 つの理由）
    • 抽象化の 粒度：上げすぎ・下げすぎ・ちょうどよい
    • 抽象化の 種類：手続き・データ・制御・ポリモーフィック
    • インターフェース設計のコツと、抽象化のやりすぎへの注意
    • TypeScript／Java・Python・Go・JavaScript での書き方

    2.抽象化とは

    2.1 定義

    抽象化（Abstraction）

    本質的な特徴だけを取り出し、余計な詳細を切り捨てる こと。

    2.2 身近な例

    車のハンドル

    内部の油圧やリンク機構を意識しなくても、「回す」だけで曲がれます。

    電源スイッチ

    中の電気回路を知らなくても、「押す」だけで電気がつきます。

    関数 sort()

    中のアルゴリズム（クイックソート？ マージソート？）を知らなくても、並び替えられます。

    使う側が 知るべきことだけを知れば動く ようにするのが抽象化です。逆にいえば、抽象化とは「使う側に何を見せ、何を隠すか」を決める作業です。

    2.3 情報隠蔽とのつながり

    「詳細を隠せ」という考え方は、David Parnas が 1972 年の論文「On the Criteria To Be Used in Decomposing Systems into Modules」で示した 情報隠蔽（Information Hiding） にさかのぼります。Parnas は、モジュールの分け方の基準を「処理の手順」ではなく「変わりやすい設計判断を 1 つずつ隠すこと」に置くべきだと主張しました。抽象化とインターフェースは、この「隠す」を実現するための道具です。モジュールの分け方そのものは モジュール性・疎結合と高凝集 で扱っています。

    3.インターフェースとは

    インターフェース（Interface）

    「できることの約束」を定義したもの。中身（どうやるか）は書かず、何ができるかだけを決めます。

    interface Mailer {
  send(to: string, body: string): Promise<void>;
}

    これは「Mailer と呼ばれるものは、send メソッドを持っていることが約束されている」という宣言です。

    3.1 インターフェースを使う側

    function notify(mailer: Mailer, user: User) {
  mailer.send(user.email, 'こんにちは');
}

    使う側は、それが何の Mailer なのかを知りません。send が呼べればよいのです。

    3.2 インターフェースを実装する側

    class SendGridMailer implements Mailer {
  async send(to, body) { /* SendGrid API 呼び出し */ }
}

class AWSMailer implements Mailer {
  async send(to, body) { /* AWS SES API 呼び出し */ }
}

class MockMailer implements Mailer {
  async send(to, body) { /* テスト用 */ }
}

    約束（send）さえ守れば、中身は自由 です。

    4.なぜ抽象化が大事か

    理由内容
    1. 複雑さを閉じ込められるインターフェースの 外側 からは、複雑な中身が見えない。中身をいじっても、外に影響しない
    2. 差し替え可能になる同じインターフェースなら どんな実装でも使える。本番は SendGrid、テストはモック、開発はログ出力のみ、と自由に選べる
    3. テストが書ける外部 API につながず、モックでテスト できる
    4. 依存方向を制御できる具体クラスに依存しないので、依存関係逆転（DIP） が可能になる（依存性逆転の原則（DIP））
    5. 設計の言語が豊かになる「Mailer」「PaymentGateway」「Logger」など、意図を名前で表現 できる

    2 と 3 の「差し替え」を実際に行う仕組みが DI です（DI・IoC・Composition Root）。インターフェースで「何を受け取るか」を決め、DI で「何を渡すか」を外から決める、という分担になります。

    5.抽象化の粒度

    抽象化には「ちょうどよい高さ」があります。上げすぎても下げすぎても役に立ちません。

    5.1 抽象度を上げすぎると

    ✕ 抽象的すぎる 
    interface DoSomething {
  execute(input: any): any; // 何をするか分からない
}

    何でもできるように見えて、何もできない 抽象です。使う側は何を渡せばよいのか、何が返ってくるのか分からず、結局実装を読みに行くことになります。型の助けも得られません。

    5.2 抽象度を下げすぎると

    ✕ 具体的すぎる 
    interface SendGridMailer {
  sendViaSendGridApiV3(...): ...; // 特定の実装に引きずられている
}

    抽象が具体の都合に汚染されています。AWS SES に変えたくても、インターフェース自体が SendGrid 前提なので差し替えられません。インターフェースとして役に立ちません。

    5.3 適切な抽象化

    ○ ちょうどよい 
    interface Mailer {
  send(to: string, subject: string, body: string): Promise<void>;
}
    • 十分に汎用的：どんなメール配信サービスでも実装できる
    • 十分に具体的：使う側は何をすればよいか分かる

    漏れのある抽象化（Leaky Abstraction）

    Joel Spolsky は「重要な抽象化は、程度の差こそあれ、すべて漏れる」と述べました（The Law of Leaky Abstractions, 2002）。たとえば Mailer.send() でも、配信サービスごとの送信レート制限やエラーの種類の違いは、完全には隠しきれません。抽象化は「詳細を一切気にしなくてよくする魔法」ではなく、「普段は気にしなくてよくする 道具」だと理解しておくと、エラーの扱いなどを設計するときに役立ちます。

    6.抽象化の種類

    抽象化はインターフェースだけではありません。プログラミングでは、次の 4 種類の抽象化を日常的に使っています。

    6.1 手続きの抽象（関数）

    // 詳細を隠して、やってくれることだけ見せる
function sendMail(to: string, body: string) { /* ... */ }

    6.2 データの抽象（クラス・型）

    class Email {
  // 中身がどう実装されているか気にせず使える
}

    6.3 制御の抽象（イテレータ・コールバック）

    // 内部のループを意識せず処理を渡せる
list.forEach(item => doSomething(item));

    6.4 ポリモーフィックな抽象（インターフェース）

    interface Animal {
  speak(): void;
}
// Dog も Cat も同じ型として扱える
    種類隠すもの見せるもの例
    手続きの抽象処理の手順名前と引数・戻り値sendMail()、sort()
    データの抽象内部の表現（フィールドの持ち方）操作（メソッド）Email クラス、値オブジェクト
    制御の抽象ループや実行タイミング「各要素にこれをして」という指示forEach、map、コールバック
    ポリモーフィックな抽象どの実装が動くか共通の約束（型）Animal、Mailer

    DIP で使うのは主に 4 番目のポリモーフィックな抽象ですが、関数型スタイルでは「関数の型」を渡すことで同じ効果を得ることもできます。

    7.インターフェース設計のコツ

    7.1 小さく保つ（ISP：インターフェース分離の原則）

    多機能なインターフェースは使いにくくなります。目的別に分けます。

    ✕ 全部入り 
    interface UserStore {
  save(user); find(id); delete(id);
  sendMail(user); generateReport(); backupAll();
}
    ○ 分ける 
    interface UserRepository { save(user); find(id); delete(id); }
interface UserMailer { send(user); }

    全部入りのインターフェースでは、メールを送りたいだけのクラスも、レポートやバックアップの機能に依存してしまいます。テスト用のモックを作るときも、使わないメソッドまで実装しなければなりません。

    7.2 利用者目線で定義する

    使う側がほしい形 で定義します。実装の都合に合わせません。

    ✕ 実装側目線 
    interface UserRepository {
  executeQuery(sql: string): any;
}
    ○ 使う側目線 
    interface UserRepository {
  findById(id: UserId): Promise<User | null>;
  save(user: User): Promise<void>;
}

    これは DIP の「抽象は上位（使う側）の持ち物」という考え方と同じです。インターフェースを使う側のモジュールに置き、使う側の都合で形を決めると、実装の詳細が漏れにくくなります（依存性逆転の原則（DIP） の「インターフェースは上位側に置く」）。

    7.3 ビジネスの言葉で名付ける

    ✕ 技術の言葉 
    interface DAO { select(); insert(); update(); delete(); }
    ○ ビジネスの言葉 
    interface OrderRepository { findActive(); registerNew(); cancel(); }

    ビジネスの言葉で書かれたインターフェースは、それ自体が「この業務で何ができるか」の説明書になります。設計の言語が豊かになる（4 章の理由 5）というのは、こういうことです。

    8.抽象化のやりすぎに注意

    8.1 「すべてに抽象を」はアンチパターン

    ✕ クラス数が 2 倍に増える 
    interface IUser { ... }
class UserImpl implements IUser { ... }
interface IOrder { ... }
class OrderImpl implements IOrder { ... }

    必要がないなら抽象化しません。YAGNI（You Aren't Gonna Need It：必要になるまで作るな）を守ります。IUser と UserImpl のように「I ＋名前」「名前＋Impl」という組を機械的に作っている場合、そのインターフェースは使う側の都合ではなく実装を写しただけになっていることが多く、読む量と移動の手間が増えるだけです。

    8.2 抽象化すべきタイミング

    複数の実装が存在する／する予定

    配信サービスの切り替え、決済手段の追加など。

    外部システムへの境界

    DB、API、ファイルなど。技術の変更から業務ロジックを守ります。

    テストでモック／スタブを差し込みたい

    遅い・不安定・お金がかかる外部依存を、テストで偽物に替えたい場所。

    モジュール境界

    Bounded Context（境界づけられたコンテキスト）の間など、チームやモジュールをまたぐ契約。

    8.3 判断の手順

    1. まず具体クラスで書く。 純粋な計算や値オブジェクトなど、外部とやり取りしないものはそのままで構いません。
    2. 外部システムとの境界か？ DB・外部 API・ファイル・メール・時計・乱数なら、使う側の言葉でインターフェースを切ります。
    3. テストで差し替えたいか？ 遅い・不安定な依存なら、インターフェースを置く価値があります。
    4. 2 つ目の実装が実際に現れたか？ 現れた時点で抽象化しても遅くありません（インターフェースの抽出はリファクタリングで後からできます）。
    5. どれにも当てはまらなければ、抽象化しない。

    9.言語別の実装

    9.1 TypeScript ／ Java

    interface Mailer { send(to, body): Promise<void>; }
class SendGridMailer implements Mailer { /* ... */ }

    補足：TypeScript は 構造的型付け なので、implements Mailer と書かなくても、同じ形（send メソッド）を持つオブジェクトなら Mailer として渡せます。implements は「約束を守れているか」をコンパイラにチェックさせるための宣言です。Java は名前で型を区別する（公称型）ため、implements の宣言が必須です。

    9.2 Python

    from abc import ABC, abstractmethod

class Mailer(ABC):
    @abstractmethod
    def send(self, to: str, body: str) -> None: ...

# もしくは Protocol（ダックタイピング）
from typing import Protocol

class Mailer(Protocol):
    def send(self, to: str, body: str) -> None: ...

    抽象基底クラス（ABC）は継承を明示する方式、Protocol（PEP 544）は「同じ形のメソッドを持っていれば OK」という構造的な方式で、型チェッカー（mypy など）が検査します。

    9.3 Go

    type Mailer interface {
    Send(to, body string) error
}

    Go のインターフェースは 暗黙的に満たされます。implements のような宣言はなく、Send メソッドを持つ型は自動的に Mailer として扱えます。そのため Go では、インターフェースを 使う側のパッケージで定義する のが慣習とされています。これは DIP の「抽象は使う側の持ち物」と自然に一致します。

    9.4 JavaScript（interface なし）

    // 型はないが、ダックタイピングで同じことができる
function sendNotification(mailer, user) {
  mailer.send(user.email, 'hello'); // send があれば何でも OK
}

    言語に interface がなくても、「send を持っているものを渡す」という約束は成り立ちます。ただし約束はコメントやドキュメントでしか表せず、違反は実行時まで分かりません。TypeScript や JSDoc の型注釈で補うのが一般的です。

    10.よくある誤解

    誤解1：すべてのクラスにインターフェースを用意するのが「良い設計」

    誤りです。 抽象化が必要なのは、複数の実装・外部システムとの境界・テストでの差し替え・モジュール境界といった場所です。それ以外にまで用意すると、クラス数が倍になり読みにくさだけが増えます（8 章）。

    誤解2：抽象度が高いほど汎用的で優れている

    誤りです。 execute(input: any): any のような抽象は、何でもできそうに見えて何も伝えません。「十分に汎用的」かつ「十分に具体的」な粒度を狙います（5 章）。

    誤解3：インターフェースは実装クラスに合わせて作るもの

    逆です。 インターフェースは 使う側の都合と言葉 で作ります。実装に合わせると executeQuery(sql) のように詳細が漏れ、差し替えられなくなります（7 章）。

    誤解4：interface 構文がない言語では抽象化できない

    誤りです。 Python の ABC や Protocol、Go の暗黙的なインターフェース、JavaScript のダックタイピングなど、表現方法が違うだけで「約束に対してプログラミングする」ことはどの言語でもできます（9 章）。

    11.まとめ

    • 抽象化 は、本質的な特徴だけを取り出し、余計な詳細を切り捨てること。使う側が知るべきことだけを知れば動くようにする。
    • インターフェース は「できることの約束」。使う側は約束だけを知り、実装する側は約束を守る限り中身は自由。
    • 抽象化の効果は、複雑さの閉じ込め・差し替え・テスト・依存方向の制御（DIP）・設計の言語の豊かさ。
    • 粒度は「十分に汎用的で、十分に具体的」が目標。上げすぎると何もできず、下げすぎると具体の都合に汚染される。抽象は多少漏れるものと心得る。
    • 抽象化には 手続き・データ・制御・ポリモーフィック の 4 種類がある。
    • インターフェースは 小さく（ISP）、利用者目線 で、ビジネスの言葉 で定義する。
    • 「すべてに抽象を」はアンチパターン。複数実装・外部境界・テストでの差し替え・モジュール境界 のときに抽象化する（YAGNI）。
    • 表現は言語ごとに違う（TypeScript／Java の interface、Python の ABC・Protocol、Go の暗黙的インターフェース、JavaScript のダックタイピング）が、考え方は共通。
