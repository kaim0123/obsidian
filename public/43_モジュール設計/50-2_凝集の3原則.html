    50 パッケージ原則

    凝集の3原則 — REP・CCP・CRP とテンションダイアグラム

    「何を1つのパッケージにまとめるか」を決めるのが凝集の3原則です。REP・CCP・CRP の意味と具体例、3つが互いに引っ張り合う関係（テンションダイアグラム）、そしてプロジェクトの成長段階によって重視すべき原則が変わることを、実務の症状と対策の表とあわせて解説します。

    もとにしたノート：50_パッケージ原則/02_凝集の3原則とテンションダイアグラム

    ひとことで言うと

    REP と CCP は「まとめろ」、CRP は「分けろ」 と言うので、3つを同時に完全に満たすことはできません。初期は CCP（変更しやすさ）寄り にし、実際に再利用されるようになってから REP 寄りに移るのが現実的です。

    1.このページで扱うこと

    パッケージ設計の原則 では、6つのパッケージ原則を1ページで概観しました。このページでは、そのうち 「何を1つのパッケージ（コンポーネント）にまとめるか」 を決める 凝集の3原則 を掘り下げます。

    • 3原則それぞれの意味 と、実務での具体例
    • 3原則が 互いに引っ張り合う 関係（テンションダイアグラム）
    • プロジェクトの 成長段階 によって、重視すべき原則が変わること
    • アプリ内部のディレクトリ・モジュールへの当てはめ方と、よくある症状

    Robert C. Martin『Clean Architecture』第13章「コンポーネントの凝集性」を骨格にしています。ここでいう コンポーネント は、npm パッケージ・Java の jar・.NET のアセンブリのような リリースの単位（バージョンを付けて配る単位）を指しますが、リポジトリ内のモジュール（ディレクトリ）にも同じ考え方が使えます。

    クラスやモジュールの「凝集度」という一般論は 42章：凝集度と結合度 と 凝集度 で扱っています。このページは、それを パッケージの単位 に広げた話です。

    2.3つの原則

    2.1 REP：再利用・リリース等価の原則（Reuse/Release Equivalence Principle）

    原則

    再利用の単位は、リリースの単位と等しい。

    • 他の人に再利用してもらうなら、バージョン番号を付けてリリースし、変更履歴を管理する 必要があります
    • だから、1つのパッケージにまとめるクラスやモジュールは、一緒にリリースして意味のあるもの でなければなりません
    • 「たまたま同じリポジトリにある、無関係な機能の寄せ集め」は REP 違反です
    ✕ REP 違反：無関係な機能の寄せ集め 
    @company/utils
   ├─ date/        ← 日付処理
   ├─ payment/     ← 決済 SDK のラッパー
   └─ image/       ← 画像変換
   → 日付処理だけ使いたい人も、決済の変更のたびにバージョンが上がる
    ◯ REP を満たす：意味のある単位ごとにリリース 
    @company/date-utils
@company/payment-client
@company/image-tools

    2.2 CCP：閉鎖性共通の原則（Common Closure Principle）

    原則

    同じ理由・同じタイミングで変更されるものは、同じコンポーネントにまとめる。異なる理由・異なるタイミングで変更されるものは、別のコンポーネントに分ける。

    • 単一責任の原則（SRP。1つの部品が変わる理由は1つにする原則）をコンポーネント単位にした ものです
    • 「1つの変更要求が来たとき、直すコンポーネントが1つで済む」ようにします
    • 保守性を重視する原則です。多くのアプリでは 再利用性より保守性の方が重要 なので、CCP が最も重要な原則になることが多いです
    「消費税の計算方法が変わった」という変更要求に対して
✕ tax-calc は utils に、税率は config に、表示は ui に散らばっている → 3つ直す
○ tax/ コンポーネントに計算・税率・表示用フォーマッタがまとまっている → 1つ直す

    2.3 CRP：全体再利用の原則（Common Reuse Principle）

    原則

    コンポーネントの利用者に、不要なものへの依存を強制してはならない。

    • 一緒に使われるものは一緒にまとめ、一緒に使われないものは分けます
    • インターフェース分離の原則（ISP。使わないメソッドへの依存を強制しない原則）をコンポーネント単位にした ものです
    • あるコンポーネントに依存すると、その 中の一部しか使っていなくても、残りの部分の変更のたびに再ビルド・再テスト・再デプロイが必要になります
    ✕ CRP 違反：使わない重い部品まで抱き合わせ 
    @company/ui
   ├─ Button, Input       ← 全員が使う
   └─ RichTextEditor      ← 1画面しか使わない。巨大な依存ライブラリを含む
   → Button だけ使いたいアプリも、エディタの依存ライブラリまでインストールする
    ◯ CRP を満たす：一緒に使われるものだけをまとめる 
    @company/ui-basic          （Button, Input）
@company/ui-rich-editor    （RichTextEditor）

    2.4 3原則の性格

    原則性格コンポーネントの大きさ守るもの
    REPまとめる方向（包含的）大きく する再利用する人の便利さ
    CCPまとめる方向（包含的）大きく する保守する人の便利さ
    CRP分ける方向（排他的）小さく する利用者を不要な変更から守る

    REP と CCP は「まとめろ」、CRP は「分けろ」と言っています。3つを同時に完全に満たすことはできません。

    3.テンションダイアグラム

    3.1 図

    Martin は、3原則の引っ張り合いを 三角形の図（テンションダイアグラム。テンション＝張力、引っ張り合う力）で表しました。頂点が3つの原則、辺は、反対側の頂点の原則を捨てたときに払う代償 を表します。

    重視する原則捨てる原則払う代償
    REP ＋ CCPCRP不要なリリースが多すぎる：大きなコンポーネントになり、使っていない部分の変更でもバージョンが上がり、利用者は追従を強いられる
    CCP ＋ CRPREP再利用しにくい：変更しやすく不要な依存もないが、リリースの単位として整理されていないので、外部の人が再利用しにくい
    REP ＋ CRPCCP変更の影響を受けるコンポーネントが多すぎる：細かく分かれていて再利用しやすいが、1つの変更要求で多くのコンポーネントを直す必要がある

    3.2 どこに位置するかは、プロジェクトの段階で変わる

    Martin は、三角形のどこに位置すべきかは、プロジェクトの成熟度によって変わる と述べています。

    段階重視する原則理由
    初期CCP（＋CRP）何が再利用されるかまだ分からない。まずは 変更しやすさ が最優先。再利用性（REP）は後回しでよい
    成長期CCP ＋ CRP利用者が増え、不要な依存による再ビルド・再デプロイが問題になってくる
    成熟期REP の比重が増える他のチームや外部から再利用されるようになり、リリースの単位としての整理が重要になる

    再利用は、再利用されてから

    最初から「再利用できるように」と細かく分けたパッケージを作ると、変更のたびに多くのパッケージを直すことになります（REP ＋ CRP で CCP を捨てた状態）。再利用は、実際に再利用されるようになってから 考えるのが現実的です。

    4.実務での判断

    4.1 ディレクトリ・モジュールに当てはめる

    npm パッケージとして公開しない、アプリ内部のモジュール（ディレクトリ）でも、3原則は役立ちます。

    原則アプリ内部での問い
    REPこのモジュールの公開 API（index.ts）は、まとまった意味のある単位 になっているか？
    CCP1つの業務の変更要求で、直すモジュールは1つで済む か？
    CRPこのモジュールを使う側は、中身の大部分を使っている か？ 一部しか使わないなら分けるべきでは？

    4.2 よくある症状と、どの原則の問題か

    症状原則対策
    小さな機能追加で、いつも5つのモジュールを直しているCCP 違反一緒に変わるものを1つのモジュールに集める
    common/ を import すると、関係ない巨大ライブラリまで読み込まれるCRP 違反用途ごとにモジュールを分ける
    社内ライブラリのバージョンが毎週上がり、追従が大変CRP 違反（REP＋CCP 寄りすぎ）変更頻度の違う部分を別パッケージに分ける
    共通化したパッケージが細かすぎて、どれを使えばいいか分からないREP 違反意味のあるリリース単位にまとめ直す

    4.3 バランス結合との関係

    CCP（同じ理由で変わるものをまとめる）と CRP（一緒に使われないものを分ける）は、バランス結合 でいう 「強く結びつくものは近くに、弱く結びつくものは遠くに」 を、リリースの単位で表したものと見ることができます。

    5.よくある誤解

    誤解1：「3原則をすべて満たすのが理想」

    不可能です。 REP・CCP はまとめる方向、CRP は分ける方向に働くので、必ずどこかで妥協します。

    誤解2：「最初から再利用しやすく作るべき」

    多くの場合、逆効果です。 初期は CCP（変更しやすさ）を優先し、実際に再利用されるようになってから REP を考えます。

    誤解3：「凝集の原則は npm パッケージだけの話」

    誤りです。 アプリ内のディレクトリ・モジュールの切り方にもそのまま使えます。

    6.まとめ

    • REP（再利用・リリース等価）：再利用の単位＝リリースの単位。意味のあるまとまりでリリースする
    • CCP（閉鎖性共通）：同じ理由で変わるものをまとめる。SRP のコンポーネント版。多くのアプリで最重要
    • CRP（全体再利用）：利用者に不要な依存を強制しない。ISP のコンポーネント版
    • REP・CCP は 大きくする、CRP は 小さくする 方向に働き、テンションダイアグラム で引っ張り合う
    • 辺は「捨てた原則の代償」：不要なリリースが多すぎる／再利用しにくい／変更の影響が広すぎる
    • 初期は CCP 寄り、成熟するにつれて REP 寄り に移る

    次は、コンポーネント同士の「つながり方」の原則である 結合の3原則と循環依存 に進みます。
