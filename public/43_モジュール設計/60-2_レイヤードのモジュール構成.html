    レイヤードのモジュール構成 — 層をディレクトリにどう落とし込むか

    最も広く使われている「レイヤー（層）」による構成を、モジュールとディレクトリのレベルで見ていきます。4つの層それぞれの責務、依存の向きを破る「レイヤー違反」の典型例、そしてメリット・デメリットと向く場面を、コード例と図で解説します。

    もとにしたノート：60_構成と実装/02_レイヤードアーキテクチャのモジュール構成

    ひとことで言うと

    レイヤードは「関心ごとに 水平な層 に分け、上から下へだけ 依存させる」構成です。層を飛ばしたり逆向きに依存したりする レイヤー違反 を避け、規模に応じて簡略化したり、ドメインごとに層を繰り返したりして使います。

    1.このページで扱うこと

    このページは「レイヤードアーキテクチャを モジュール・ディレクトリにどう落とし込むか」を扱います。スタイルそのものの説明（歴史や三層構造との関係など）は 41章：層化・三層・レイヤード と 41章：閉じた層と開いた層 を参照してください。

    技術的関心事による分割 で触れた 3 層を、実践レベルで理解することが目的です。

    • レイヤー構造の基本：水平な層と依存の向き
    • 各レイヤーの責務：Presentation / Application / Domain / Infrastructure
    • レイヤー違反の典型例
    • メリット・デメリットと向く場面

    2.レイヤー構造の基本

    レイヤードアーキテクチャ とは、関心ごとに 水平な層 に分け、上から下へ 依存させる構造です。「依存する」とは、あるコードが別のコードを呼び出したり import したりして、それが無いと動かない関係のことです。

    ノートでは「Domain は下に依存しない」と補足しています。業務ルール（Domain）が DB などの技術詳細に引きずられないようにするためです。実際には Domain が Repository の インターフェース（約束ごとだけを書いた型）を定義し、Infrastructure がそれを実装する形にします（次の節のコード例と、3 節の「正しい」形を参照）。この「依存の向きを逆転させる」考え方は 41章：依存性逆転の原則 で詳しく扱っています。

    3.各レイヤーの責務

    レイヤー責務含むもの例
    Presentation入出力、HTTP ステータスController, View, DTO 変換
    Applicationユースケースの orchestration（複数の部品を呼ぶ順番の取りまとめ）ApplicationService, CommandHandler
    Domain業務ルール・不変条件（常に守られるべき決まり）Entity, ValueObject, DomainService
    Infrastructure技術詳細Repository 実装, ORM, HTTP Client

    DTO（Data Transfer Object）は層の間でデータを運ぶための入れ物、ORM はデータベースの表とプログラムのオブジェクトを対応づけるライブラリです。Entity・ValueObject などの用語は 42章：エンティティと値オブジェクト を参照してください。

    Application 層の例 
    // Application 層の例
class PlaceOrderUseCase {
  constructor(
    private orderRepo: OrderRepository,  // interface（Domain）
    private payment: PaymentPort
  ) {}

  async execute(cmd: PlaceOrderCommand): Promise<OrderId> {
    const order = Order.create(cmd.items);  // Domain
    await this.payment.charge(order.total);
    await this.orderRepo.save(order);       // Infra 実装が注入
    return order.id;
  }
}

    ユースケースは「注文を作る → 支払う → 保存する」という 手順の取りまとめ だけをしています。注文の中身のルールは Order（Domain）に、保存の方法は Infrastructure の実装に任せています。実装をコンストラクタで外から渡す（注入する）しくみは 41章：DI・IoC・Composition Root で扱っています。

    4.レイヤー違反の典型例

    レイヤー違反 ＝ 依存の向きを破ることです。

    違反例
    Presentation → Infrastructure 直行Controller が SQL を直接実行
    Domain → InfrastructureEntity が ORM アノテーションだらけ
    Infrastructure → PresentationRepository が HTTP レスポンスを返す

    アノテーション とは、@Column のようにクラスや項目に付ける注釈で、ここでは ORM の設定が業務ルールのクラスに入り込んでいる状態を指します。

      違反
  Controller ──→ SQL（Infra をスキップ）

  正しい
  Controller → UseCase → Repository(IF) ← RepositoryImpl

    5.レイヤード構造のメリット・デメリット

    メリットデメリット
    関心が分かれて理解しやすい1 機能が複数層に散らばる
    インフラの差し替えがしやすい小規模では過剰に感じる
    チームで層分担しやすい「どの層？」の議論が増える

    向く場面：中規模以上の Web/API アプリ、CRUD（作成・読み取り・更新・削除）＋ 業務ルールがあるシステム。

    注意：ドメインごとに層を繰り返す

    レイヤーを ドメインモジュールごと に繰り返すと、機能単位の見通しが良くなります（技術的関心事による分割）。たとえば order/ の中に presentation・application・domain・infrastructure を置き、payment/ の中にも同じ 4 つを置く形です。機能別とレイヤー別の比較は 機能別とレイヤー別 も参照してください。

    6.よくある誤解

    誤解1：「上の層から下の層なら、どこを呼んでもよい」

    Controller が UseCase を飛ばして SQL を直接実行するのは、表の最初にある典型的なレイヤー違反です。間の層を飛ばすと、業務ルールを通らない抜け道ができてしまいます（層を飛ばしてよいかどうかの考え方は 閉じた層と開いた層 を参照）。

    誤解2：「Domain は一番下の Infrastructure を使ってよい」

    図では Domain が Infrastructure の上にありますが、Domain は下に依存させません。Entity に ORM アノテーションを詰め込むのは違反の例です。Domain がインターフェースを定義し、Infrastructure がそれを実装します。

    誤解3：「どんな規模でも 4 層をきっちり作るべき」

    小規模では 4 層が過剰に感じることがデメリットとして挙がっています。規模に応じて簡略化し、必要ならドメインごとに層を繰り返す形を選びます。

    7.まとめ

    • レイヤード ＝ 水平分割 ＋ 上から下への依存
    • Presentation / Application / Domain / Infrastructure の 4 層 が一般的
    • レイヤー違反（直行・逆依存）を避ける
    • 規模に応じて簡略化し、ドメインごとに層を繰り返す
