    10 モジュールの基礎

    深いモジュールと浅いモジュール — 小さな入口で多くを隠す

    良いモジュールとはどんなモジュールでしょうか。スタンフォード大学の John Ousterhout は『A Philosophy of Software Design』で、「使う人が払うコスト（インターフェース）に対して、得られる利益（機能）が大きいか」という物差しを示しました。このページでは、深いモジュールと浅いモジュール、情報漏洩とその原因である時間的分解、パススルーメソッドとクラス病、汎用的な設計、エラーを定義からなくす考え方、そして設計の危険信号（レッドフラグ）を解説します。

    もとにしたノート：10_モジュールの基礎/04_深いモジュールと浅いモジュール_情報漏洩

    ひとことで言うと

    モジュールの価値は 機能（利益）÷ インターフェース（コスト） です。深いモジュール は単純なインターフェースで多くの複雑さを隠します。逆に、同じ設計判断が複数のモジュールに散らばる 情報漏洩 は最も重要な危険信号の1つで、実行順にモジュールを分ける 時間的分解 がその典型的な原因です。

    1.このページで扱うこと

    カプセル化と情報隠蔽 では「公開すべきもの・隠すべきもの」を学びました。このページでは、John Ousterhout が『A Philosophy of Software Design』（2018／第2版 2021）で示した視点から、モジュールの良し悪しを測る具体的な物差し を学びます。

    • 深いモジュール と 浅いモジュール
    • 情報漏洩（Information Leakage）と、その原因となる 時間的分解
    • パススルーメソッド と クラス病（Classitis）
    • 「汎用的に作るとかえって深くなる」という考え方
    • エラーを定義からなくす
    • Ousterhout の レッドフラグ（設計の危険信号）一覧

    一般論としての「複雑さ」の定義は 42章：ソフトウェア設計の全体像 にまとめています。

    2.モジュールの「コスト」と「利益」

    Ousterhout は、モジュールを インターフェース と 実装 に分けて考えます。

    部分意味使う人にとって
    インターフェース使う人が知らなければならないこと（関数名・引数・戻り値・前提条件・副作用・例外…）コスト（覚えること・気をつけること）
    実装モジュールが内部でやってくれること利益（自分で書かなくて済むこと）

    良いモジュールとは、小さなコスト（インターフェース）で、大きな利益（機能）が得られるモジュールである。

    ここで「インターフェース」には、型シグネチャだけでなく、呼ぶ順番・前提条件・副作用・性能特性 といった 非形式的な部分 も含まれる点に注意します。副作用 とは、戻り値を返す以外に外の状態を変えること（ファイルへの書き込みなど）です。ドキュメントに書かないと分からない約束ごとも、使う人が覚えるべきコストです。

    3.3 浅いモジュールの例

    ✕ 浅い：インターフェースが実装とほぼ同じ大きさ。隠しているものがない 
    class UserNameSetter {
  setUserName(user: User, name: string) {
    user.name = name;
  }
}
    ✕ 浅い：呼ぶ側が「どのクラスをどの順番で組み合わせるか」を全部知る必要がある 
    const stream = new FileInputStream(path);
const buffered = new BufferedInputStream(stream);
const reader = new ObjectInputStream(buffered);

    最後の例は、Java の古いファイル読み込み API です。Ousterhout は「ほとんどの人はバッファリング（まとめて読み込んで速くする仕組み）を必要とするのに、それを使う人に毎回組み立てさせている」として、浅い設計の典型に挙げています。よく使うケースを、いちばん簡単に できるのが深いモジュールです。

    3.4 「小さく分けるほど良い」とは限らない

    「関数は短く、クラスは小さく」という教えは広く知られていますが、Ousterhout はこれに注意を促しています。

    • 小さな部品を増やすと、部品ごとのインターフェース（コスト） が積み重なる
    • 部品同士の つなぎ方 を理解する必要が生まれる
    • 結果として、システム全体の複雑さはむしろ増える

    分割すること自体が目的ではない。分割によって、使う人が知るべきことが減るか で判断する。

    ただし「深い」は「長い」という意味ではありません。インターフェースに対して、隠している機能が大きいか という比率の話です。

    4.情報漏洩（Information Leakage）

    4.1 定義

    ある設計判断（知識）が、複数のモジュールに反映されている状態。

    Ousterhout は、情報漏洩を 最も重要なレッドフラグの1つ としています。

    ✕ 情報漏洩：CSV の列の並び（設計判断）を、2つのモジュールが知っている 
    // importer.ts
const [name, email, birthday] = line.split(",");

// exporter.ts
const line = [user.name, user.email, user.birthday].join(",");
    • どちらもインターフェースには CSV の形式を出していない
    • しかし 両方が同じ形式に依存している ので、列を1つ増やすと両方を直す必要がある
    • しかも、片方だけ直しても コンパイルエラーにならない（→ 41章：コナーセンス でいう「位置のコナーセンス」）

    前のページの Leaky Abstraction は公開 API や型を通じて詳細が漏れる状態でしたが、情報漏洩はインターフェースに現れなくても起きる点に注意します。

    4.2 対策

    その知識を1つのモジュールに閉じ込める ことです。

    ◯ CSV の形式という知識を UserCsv モジュールだけが持つ 
    // user-csv.ts
export function parseUserCsv(line: string): User { ... }
export function formatUserCsv(user: User): string { ... }

    情報漏洩は、凝集度 の言葉でいえば「同じ理由で変わるものが散らばっている」状態です。

    5.時間的分解（Temporal Decomposition）

    5.1 情報漏洩の典型的な原因

    処理が実行される順番に沿って、モジュールを分けてしまうこと。

    例：ファイルを読んで、変更して、書き出すアプリ

    • 「読む → 変更する → 書く」と実行順に分けると、ファイル形式の知識が読み込みと書き出しの両方に漏れる
    • 実行順ではなく、どの知識を隠すか で分ける

    これは 42章：カプセル化と情報隠蔽 で見た Parnas の 1972 年の論文（処理の流れではなく、隠す設計判断でモジュールを分けよ）と同じ主張です。

    6.パススルーメソッドとクラス病

    6.1 パススルーメソッド

    引数をそのまま別のメソッドに渡すだけで、何もしないメソッド。

    class UserService {
  findById(id: string) {
    return this.userRepository.findById(id);  // 渡すだけ
  }
}
    • 同じシグネチャのメソッドが2つの層にある → どちらかの層は不要 かもしれない
    • 41章：閉じた層と開いた層 の シンクホール アンチパターン（何もせず下の層に流すだけの層）と同じ現象を、メソッド単位で見たもの
    • 対策：層を減らす、責務を寄せる、または呼び出し側から直接下の層を使えるようにする（開いた層）

    6.2 クラス病（Classitis）

    「クラスは良いものだから、多いほど良い」という誤った信念。

    • 結果として、小さくて浅いクラス が大量に生まれる
    • 1つの機能を理解するのに、何十ものファイルを行き来する必要が出る
    • 41章：依存性のルールとクリーンアーキテクチャ で紹介している「クリーンアーキテクチャを入れたら、コードが汚くなった」で語られている問題の多くは、これにあたります

    7.汎用的なモジュールは深くなりやすい

    Ousterhout は、意外な主張をしています。

    モジュールは「やや汎用的に」作るほうが、深くなりやすい。

    例：テキストエディタのテキスト管理クラス

    設計インターフェースの例問題
    特化しすぎbackspace(), deleteSelection(), pasteAtCursor()UI の操作ごとにメソッドが増える。UI の知識がテキストクラスに漏れる
    やや汎用的insert(position, text), delete(start, end)メソッドが少なく、UI の操作はすべてこの2つの組み合わせで実現できる
    • 「今の使い方」に特化させると、使い方の知識がモジュールに漏れて、メソッドが増え、浅くなる
    • ただし、将来の仮定の要求のために作り込む こと（YAGNI 違反。YAGNI は「今必要ないものは作らない」という原則で、42章：変化に強い設計 で扱っています）とは違う。今の要求を、より少ない汎用的な操作で満たせないか を考える

    判断のための問いとして、Ousterhout は次を挙げています。

    • ☐ 今の要求をすべて満たす、最もシンプルなインターフェース は何か？
    • ☐ このメソッドは、何か所から使われる か？（1か所だけなら、特化しすぎかもしれない）
    • ☐ このインターフェースは、今の要求に対して使いやすい か？

    8.例外を「定義からなくす」

    例外やエラーケースも、インターフェースのコストです。Ousterhout は 「エラーを定義からなくす（Define Errors Out of Existence）」 ことを勧めています。

    ✕ 存在しないキーを消そうとすると例外を投げる → 呼ぶ側は毎回 try/catch か事前チェックが必要 
    cache.delete(key);  // throws KeyNotFoundError
    ◯ 「消した後、そのキーは存在しない」という意味にする → 存在しなくても正常終了 
    cache.delete(key);  // 何もなければ何もしない
    • JavaScript の Map.prototype.delete や Array.prototype.slice（範囲外でも例外にならない）はこの考え方
    • 使う人が扱うべき 特殊なケースが減る ので、モジュールが深くなる

    9.レッドフラグ一覧

    Ousterhout は、設計の危険信号（レッドフラグ）を一覧にしています。モジュール設計に関係する主なものを挙げます。

    レッドフラグ症状
    浅いモジュールインターフェースが、提供する機能に比べて複雑
    情報漏洩同じ設計判断が、複数のモジュールに反映されている
    時間的分解実行順に沿ってモジュールが分かれ、知識が重複している
    過剰な公開よく使う機能を使うために、めったに使わない機能まで知る必要がある
    パススルーメソッド引数を渡すだけで何もしないメソッド
    重複同じコードが何度も現れる
    汎用と特化の混在汎用的な仕組みに、特定の用途のコードが混ざっている
    結合したメソッド1つのメソッドを理解するのに、別のメソッドの実装を読む必要がある
    曖昧な名前名前が何をするのかを正確に表していない
    説明しにくいシンプルなコメントやドキュメントで説明できない（設計が複雑なサイン）

    実践で便利な判断基準

    最後の「説明しにくい」は、実践的に便利な判断基準です。モジュールの役割を短い文で説明できないなら、そのモジュールは何かがおかしい 可能性が高いです。

    10.よくある誤解

    誤解1：「深いモジュール＝大きなファイル」

    誤りです。 深さは インターフェースと機能の比率 です。小さなファイルでも、単純なインターフェースで多くを隠していれば深いモジュールです。

    誤解2：「クラスや関数は小さいほど良い」

    常にではありません。 分割で使う人が知るべきことが増えるなら、まとめた方が良いこともあります。

    誤解3：「汎用的に作る＝将来のために作り込む」

    違います。 汎用的な設計は「今の要求を、より少ない操作で満たす」こと。将来の仮定の要求のために機能を足すことではありません。

    11.まとめ

    • モジュールの価値は 機能（利益）÷ インターフェース（コスト）。深いモジュール は単純なインターフェースで多くを隠す
    • 浅いモジュール はインターフェースが機能に比べて大きく、複雑さを隠さない。クラス病 で量産されやすい
    • 情報漏洩：同じ設計判断が複数のモジュールに散らばること。最も重要なレッドフラグの1つ
    • 時間的分解（実行順で分ける）が情報漏洩の典型的な原因。隠す知識 で分ける
    • パススルーメソッド は不要な層のサイン
    • やや汎用的に 作り、エラーを定義からなくす と、モジュールは深くなる
