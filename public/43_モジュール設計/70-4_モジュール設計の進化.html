    70 品質と運用

    モジュール設計の進化 — 小さく始めて境界を育てる

    モジュール設計は、最初から完璧である必要はありません。このページでは、動くモノリスから仮説を立てて境界を調整していく進め方、段階的な分割の手順、リファクタリングのタイミング、新機能を追加するときの境界の見直し方、そしてレガシーコードに良い境界を広げていく方法を解説します。

    もとにしたノート：70_品質と運用/04_モジュール設計の進化

    ひとことで言うと

    境界は仮説です。小さく分けて実装で確かめ、機能追加やバグ修正のたびに見直して育てます。一度に全部を作り直す（Big Bang リライト）のではなく、新しいコードから良い境界を広げていくのが基本です。

    1.このページで扱うこと

    設計は 最初から完璧でなくてよい — 段階的にモジュール境界を改善する進め方を学びます。

    • 最初から完璧な設計は不要な理由
    • 小さく始めて段階的に分割する手順と Strangler Fig パターン
    • リファクタリングのタイミング
    • 機能追加時の境界の見直し
    • レガシーコードへの適用

    2.最初から完璧な設計は不要

    現実対応
    要件は変わる境界も見直す
    学習しながら進む小さく試して修正
    時間は有限重要な境界から

    これは 42章：設計の進め方と段階的な深化 と同じ精神です。進化的に設計を守る考え方は 41章：進化的アーキテクチャと適応度関数 も参照してください。

    3.小さく始めて段階的に分割する

    3.1 段階的アプローチ

    1. 第 1 段階：レイヤーだけ分ける（web / app / domain / infra）
    2. 第 2 段階：ドメインモジュールを 2〜3 個に分割
    3. 第 3 段階：依存ルールと CI を導入（→ 依存ルールの自動検査）
    4. 第 4 段階：細分化・イベント連携

    時間軸で見ると、たとえば次のような進み方になります。

      Week 1:  order と catalog を分離
  Week 4:  payment を切り出し
  Month 3: 依存チェックを CI に

    3.2 Big Bang リライトを避ける

    全体を一度に書き直す Big Bang リライト は避け、Strangler Fig（絞め殺しのイチジク）パターンで置き換えます。Strangler Fig は、古い木に巻きついて育ち、やがて置き換わるイチジクにたとえた手法で、新しい部分を少しずつ作って古い部分の役目を移していきます。

    4.リファクタリングのタイミング

    タイミング例
    機能追加前触るモジュールの整理
    バグ修正後根本原因が境界なら分割
    テスト追加時依存を注入可能に
    定期四半期の依存グラフレビュー

    ルール

    リファクタ専用 PR と機能 PR を 分ける とレビューしやすくなります。動きを変えない変更と動きを変える変更が混ざらないからです。

    5.機能追加時の境界の見直し

    新機能が 既存モジュールの責務外 なら、境界を見直します。

    質問アクション
    どのモジュールの「変化の理由」に合うかそこに置く
    どのモジュールにも合わない新モジュール を検討
    2 モジュールにまたがるどちらが主担当か、イベント連携か
     
      新機能「クーポン」
  order に置く？ promotion 新設？
  → 変化の理由が「販促ルール」なら promotion モジュール

    「変化の理由」で分ける考え方は モジュール分割の基本プロセス を参照してください。

    6.レガシーコードへの適用

    42章：レガシーと設計レビュー のモジュール版です。レガシーコード は、テストが無く変更が怖い既存コードのことです。

    原則説明
    理解してから依存グラフ・ホットスポットを把握
    新コードは良い境界旧コードを触らなくてよい形で拡張
    絶えず小さく触ったファイルの周辺だけ整理
    諦めないライン100% きれいは不要。改善トレンドが重要

    ホットスポット は、変更が頻繁で問題が集中している場所です。

    アンチコラプション層（ACL） とは、外側（ここでは旧コード）のモデルや用語が新しいモジュールに入り込まないよう、間で変換する層です。

    7.よくある誤解

    誤解1：「最初に正しい境界を決めきらないと後で困る」

    要件は変わり、チームも学びながら進みます。境界は仮説として立て、実装で検証して調整するものです。重要な境界から始めれば十分です。

    誤解2：「レガシーは一度全部作り直すのが一番早い」

    Big Bang リライトは危険が大きいため避けます。Strangler Fig パターンで新しいコードから少しずつ置き換えます。

    誤解3：「リファクタリングは機能追加と同じ PR でついでにやればよい」

    混ざるとレビューが難しくなります。リファクタ専用 PR と機能 PR を分けるのがルールです。

    8.まとめ

    • 完璧な初期設計は不要 — 仮説と検証を繰り返す
    • 段階的分割 でリスクを抑える
    • 機能追加・バグ修正を 境界見直しの機会 に
    • レガシーは 新コードから良い境界 を広げる
