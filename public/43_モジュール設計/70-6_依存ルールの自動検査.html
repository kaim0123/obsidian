    70 品質と運用

    依存ルールの自動検査 — ツールと CI でモジュール境界を守り続ける

    設計ルールを文書に書き、コードレビューで確かめても、人の目だけでは境界はいつか崩れます。このページでは、依存のルールをツールで自動的に検査し、CI で違反を止める方法を解説します。何を検査すべきか、JavaScript / TypeScript の主なツール（dependency-cruiser・eslint-plugin-boundaries・Nx・ArchUnitTS）と他言語のツール、既存のコードベースへの段階的な導入、AI 時代にこの仕組みが持つ意味までを扱います。

    もとにしたノート：70_品質と運用/06_依存ルールの自動検査

    ひとことで言うと

    依存のルールは機械に検査させ、CI で違反を止めます。まずは「循環依存の禁止」と「層の依存の向き」の 2 つから。既存のコードには、今ある違反を記録して新しい違反だけを止め、そのあと計画的に減らします。ルールには意図を書いておくと、人にも AI にも伝わります。

    1.このページで扱うこと

    チームでモジュール設計を守る では、設計ルールの文書化やコードレビューで境界を守る方法を学びました。しかし、人の目だけでは限界があります。

    • レビュアーが見落とす
    • 「急いでいたので一時的に」が積み重なる
    • 新しいメンバーはルールを知らない
    • AI コーディングアシスタントが、境界を無視したコードを書く

    このページでは、依存のルールをツールで自動的に検査し、CI で違反を止める 方法を学びます。

    • 何を検査すべきか（ルールの種類）
    • JavaScript / TypeScript の主なツール：dependency-cruiser・eslint-plugin-boundaries・Nx・ArchUnitTS
    • 他の言語のツール：ArchUnit（Java）・Deptrac（PHP）・import-linter（Python） など
    • 導入の進め方（既存のコードベースへの段階的な導入）

    これは、41章で学んだ アーキテクチャ適応度関数（設計の特性を自動で守り続ける仕組み。41章：進化的アーキテクチャと適応度関数）の、最も身近な実践例です。

    2.何を検査するか

    ルールの種類例関連する原則
    循環依存の禁止どのモジュール間にも循環がないADP（結合の3原則と循環依存）
    層の依存の向きdomain は infrastructure を import しない依存性のルール・SDP
    機能間の境界features/orders は features/customers の内部を import しない（公開 API だけ）情報隠蔽・カプセル化
    公開 API 経由の強制他のモジュールの index.ts 以外への import を禁止モジュール間インターフェース
    特定ライブラリの使用制限domain では prisma や express を import しない依存性のルール
    孤立したモジュールの検出どこからも使われていないファイル不要なコードの削除
    外部パッケージの制限package.json にない依存の import、開発用依存を本番コードで使う依存の明示

    ADP（非循環依存の原則）はパッケージの依存に循環を作らない原則、SDP（安定依存の原則）は変わりにくいものに向かって依存する原則です。依存性のルール は、クリーンアーキテクチャで「依存は内側（業務ルール）に向ける」という決まりです（41章：依存性のルールとクリーンアーキテクチャ）。

    最初の 2 つ

    最初は 循環依存の禁止 と 層の依存の向き の 2 つから始めるのがおすすめです。効果が大きく、ルールも分かりやすいからです。

    3.dependency-cruiser

    3.1 概要

    dependency-cruiser は、JavaScript / TypeScript のプロジェクトの 依存関係を解析・検査・可視化 するツールです。ESLint（コードの書き方を検査するツール）のプラグインではなく、独立したツールとして動きます。

    • 依存グラフ全体を見るので、循環依存の検出 が得意
    • ルールを forbidden（禁止する依存） として書く
    • 依存グラフを 図として出力 できる（Graphviz・Mermaid など）

    3.2 ルールの例

    循環依存の禁止、domain から infrastructure への依存の禁止、他機能の内部への import の禁止、孤立ファイルの警告、の 4 つのルールを書いた例です。

    // .dependency-cruiser.cjs
module.exports = {
  forbidden: [
    {
      name: "no-circular",
      severity: "error",
      comment: "循環依存は禁止（ADP）",
      from: {},
      to: { circular: true },
    },
    {
      name: "domain-not-to-infrastructure",
      severity: "error",
      comment: "domain は infrastructure に依存しない（依存性のルール）",
      from: { path: "^src/[^/]+/domain" },
      to: { path: "^src/[^/]+/infrastructure" },
    },
    {
      name: "no-cross-feature-internals",
      severity: "error",
      comment: "他の機能は公開 API（index.ts）経由でのみ使う",
      from: { path: "^src/features/([^/]+)/" },
      to: {
        path: "^src/features/([^/]+)/.+",
        pathNot: ["^src/features/$1/", "^src/features/[^/]+/index\\.ts$"],
      },
    },
    {
      name: "no-orphans",
      severity: "warn",
      comment: "どこからも使われていないファイル",
      from: { orphan: true, pathNot: ["\\.d\\.ts$", "(^|/)main\\.ts$"] },
      to: {},
    },
  ],
  options: {
    tsConfig: { fileName: "tsconfig.json" },
  },
};

    path は正規表現（文字列のパターン）で書きます。3 つ目のルールの $1 は、from 側で ([^/]+) が捕まえた機能名を指し、「自分の機能の中」と「他機能の index.ts」以外への import を禁止しています。

    # 検査
npx depcruise src --config .dependency-cruiser.cjs

# 依存グラフを図にする
npx depcruise src --include-only "^src" --output-type mermaid > deps.mmd

    4.eslint-plugin-boundaries

    4.1 概要

    eslint-plugin-boundaries は、アーキテクチャの要素（element）と、その間の依存ルール を ESLint で検査するプラグインです。

    • ESLint の一部として動くので、エディタ上で保存するたびに違反が表示される
    • 「この種類のファイルは、この種類のファイルにしか依存できない」という 要素の種類ベース のルールが書きやすい

    4.2 設定の例

    // eslint.config.mjs
import boundaries from "eslint-plugin-boundaries";

export default [
  {
    plugins: { boundaries },
    settings: {
      "boundaries/elements": [
        { type: "app",      pattern: "src/app/*" },
        { type: "feature",  pattern: "src/features/*", capture: ["featureName"] },
        { type: "shared",   pattern: "src/shared/*" },
      ],
    },
    rules: {
      "boundaries/element-types": ["error", {
        default: "disallow",
        rules: [
          { from: "app",     allow: ["feature", "shared"] },
          { from: "feature", allow: ["shared"] },   // feature 同士の直接依存は禁止
          { from: "shared",  allow: ["shared"] },
        ],
      }],
    },
  },
];

    default: "disallow" で「書いていない依存はすべて禁止」にし、許す方向だけを allow で並べています。

    4.3 dependency-cruiser との使い分け

    dependency-cruisereslint-plugin-boundaries
    動き方独立したツール（CI で実行）ESLint のプラグイン（エディタでも即座に表示）
    得意なこと依存グラフ全体 の解析（循環・孤立）、可視化ファイル単位 の import ルール、エディタでのフィードバック
    使い分けCI での全体検査・定期的なグラフの確認日々の開発中のフィードバック

    両方を併用するチームも多いです。

    5.Nx の enforce-module-boundaries

    モノレポ（複数のパッケージを 1 つのリポジトリで管理する方式）で Nx を使っているなら、@nx/enforce-module-boundaries ルールで、プロジェクト（パッケージ）間の依存を タグ で制御できます。

    "@nx/enforce-module-boundaries": ["error", {
  depConstraints: [
    { sourceTag: "type:app",     onlyDependOnLibsWithTags: ["type:feature", "type:ui", "type:util"] },
    { sourceTag: "type:feature", onlyDependOnLibsWithTags: ["type:domain", "type:ui", "type:util"] },
    { sourceTag: "type:domain",  onlyDependOnLibsWithTags: ["type:util"] },
    { sourceTag: "scope:orders", onlyDependOnLibsWithTags: ["scope:orders", "scope:shared"] },
  ],
}]
    • 種類のタグ（type:*）で層のルール
    • スコープのタグ（scope:*）で業務の境界のルール
    • 循環依存も検出する

    詳しくは npmパッケージとモノレポ を参照してください。

    6.ArchUnit 系 — テストとして書く

    6.1 ArchUnit（Java）

    Java の ArchUnit は、アーキテクチャのルールを 単体テストとして 書けるライブラリです。

    @AnalyzeClasses(packages = "com.example")
class ArchitectureTest {
  @ArchTest
  static final ArchRule domain_should_not_depend_on_infrastructure =
      noClasses().that().resideInAPackage("..domain..")
          .should().dependOnClassesThat().resideInAPackage("..infrastructure..");

  @ArchTest
  static final ArchRule layered = layeredArchitecture().consideringAllDependencies()
      .layer("Controller").definedBy("..controller..")
      .layer("Service").definedBy("..service..")
      .layer("Repository").definedBy("..repository..")
      .whereLayer("Controller").mayNotBeAccessedByAnyLayer()
      .whereLayer("Service").mayOnlyBeAccessedByLayers("Controller")
      .whereLayer("Repository").mayOnlyBeAccessedByLayers("Service");
}
    • 普通のテストとして実行されるので、CI に組み込むのが簡単
    • 「ルールの意図」をテストの名前として残せる（→ ドキュメントにもなる）

    6.2 TypeScript 向け：ArchUnitTS

    TypeScript にも、同じ発想の ArchUnitTS があります。Jest・Vitest（JavaScript のテストツール）のテストとして、依存ルールや循環の禁止、さらに 41章：結合の指標 で学んだ 主系列からの距離などのメトリクス（抽象度と安定度のバランスを表す数値）を検査できます。

    6.3 他の言語のツール

    言語ツール特徴
    Java / KotlinArchUnit、Konsist（Kotlin）テストとしてルールを書く
    C# / .NETNetArchTest、ArchUnitNETArchUnit の .NET 版
    PHPDeptrac層（レイヤー）を定義し、層間の依存を YAML で制御
    Pythonimport-linter「層」「独立」「禁止」の契約（contract）を設定ファイルで書く
    Gogo-arch-lint、言語標準の internal/internal/ ディレクトリは親パッケージからしか import できない
    Rust言語標準の可視性（pub(crate) など）言語レベルで強く制御できる

    言語ごとのモジュール機構については 言語のモジュール機構 も参照してください。

    7.導入の進め方

    7.1 新しいプロジェクト

    最初から、循環依存の禁止 と 層の依存の向き のルールを入れておきます。ルールが少ないうちに入れる方が、後から入れるよりずっと楽です。

    7.2 既存のプロジェクト — 段階的に導入する

    既存のコードベースにいきなり厳しいルールを入れると、数百件の違反 が出て、導入が頓挫します。次の順番で進めます。

    ステップやること
    1. 可視化するまず依存グラフを図にして、チームで現状を眺める。問題の大きさを共有する
    2. ルールを決める守りたいルールを 2〜3 個に絞る
    3. 今ある違反を記録する既存の違反を「既知の違反」として記録し、新しい違反だけをエラーにする（dependency-cruiser の --ignore-known、ESLint の抑制コメント、ベースラインファイルなど）
    4. CI で止める新しい違反が入ったら PR をマージできないようにする
    5. 既知の違反を減らす計画的にリファクタリングし、既知の違反を少しずつ減らす。違反の件数を指標として追う
    6. ルールを増やす最初のルールが定着したら、次のルールを追加する

    ベースラインファイル は、導入時点の違反の一覧を保存しておき、それと比べて増えた分だけを検出するためのファイルです。

    既存コードへの導入のコツ

    「違反を増やさない」ことから始め、「違反を減らす」のは後から、というのが既存コードへの導入のコツです。

    7.3 ルールの意図を残す

    ツールの設定ファイルには、なぜそのルールがあるのか をコメントで書いておきます。

    {
  name: "domain-not-to-infrastructure",
  comment: "ドメインを DB やフレームワークから独立させ、単体テスト可能にするため（ADR-012 参照）",
  ...
}

    違反したときのエラーメッセージに意図が表示されれば、ルールが「押し付け」ではなく「理由のある約束」として伝わります。関連する ADR（41章：意思決定とADR）へのリンクも有効です。

    8.AI 時代の依存ルール

    AI コーディングアシスタントは、既存のコードの書き方を真似て、大量のコードを素早く書きます。

    • 人間のレビューだけでは、境界違反のコードが入るスピードに追いつけない
    • 一方で、ツールのルールは AI が書いたコードにも同じように適用される
    • エラーメッセージにルールの意図が書いてあれば、AI もそれを読んで自分で修正できる

    「人が読んで守るルール」から「機械が検査するルール」へ移すことの価値は、AI 時代にさらに高まっています（→ 41章：アーキテクチャ全体像）。

    9.よくある誤解

    誤解1：「ルールはドキュメントに書いてあれば十分」

    不十分です。 ドキュメントは読まれず、忘れられます。ツールで検査して初めて、ルールは守られ続けます。

    誤解2：「最初から全部のルールを入れるべき」

    逆効果です。 違反が多すぎると導入が頓挫します。少ないルールから始め、新しい違反だけを止め、段階的に増やします。

    誤解3：「ツールを入れれば設計が良くなる」

    誤りです。 ツールは 決めたルールを守らせる だけです。どんなルールにすべきか（どこに境界を引くか）は、設計として考える必要があります。

    10.まとめ

    • 人の目だけでは境界は守れない。依存ルールをツールで検査し、CI で違反を止める
    • まず検査すべきは 循環依存の禁止 と 層の依存の向き
    • JavaScript / TypeScript のツール
      • dependency-cruiser：依存グラフ全体の解析・循環検出・可視化
      • eslint-plugin-boundaries：要素の種類ベースのルール、エディタで即時フィードバック
      • Nx enforce-module-boundaries：モノレポのタグベースのルール
      • ArchUnitTS：テストとしてルールとメトリクスを検査
    • 他の言語：ArchUnit（Java）・Deptrac（PHP）・import-linter（Python）・Go の internal/
    • 既存のコードには 可視化 → 既知の違反を記録 → 新しい違反だけ止める → 計画的に減らす の順で導入する
    • ルールには 意図 を書く。AI が書いたコードにも同じルールが効く

    ルールを守りながらモジュール構成を進化させる方法は モジュール設計の進化 を参照してください。
