    00 全体像

    モジュール設計の全体像 — どこで区切り、どうつなぎ、どこに置くか

    モジュール設計とは何か、43章がどこからどこまでを扱い、どの本を骨格にしているのか、フォルダをどの順に読めばよいのか、そして41章（アーキテクチャ）・42章（ソフトウェア設計）など隣の章とどう分担しているのかをまとめた、43章の入口ページです。各ページへ進む前に、ここで全体の地図を持っておきましょう。

    もとにしたノート：MOC_モジュール設計体系（＋各フォルダのノート）

    ひとことで言うと

    モジュール設計は、コードを 「どこで区切り、どうつなぎ、どこに置くか」 を決める、モジュール・パッケージ単位の設計 です。43章は『Clean Architecture』のコンポーネントの原則を骨格に、Ousterhout の「深いモジュール・情報隠蔽」と Khononov の「結合の強度・距離・変動性」を加えた構成になっています。

    1.このページで扱うこと

    目次が「どこに何があるか」の一覧、モジュール設計年表が「どう発展してきたか」の歴史だとすれば、このページは 「43章全体の地図」 です。読み終えたときに、次の問いに答えられることを目標にします。

    1. モジュール設計とは何か。アーキテクチャやクラス設計とどう違うのか
    2. この章が扱う範囲 と、骨格になっている 3冊の本
    3. フォルダ構成と読む順。どのフォルダに何があり、どう進めばよいか
    4. 他の章との分担。一般論はどこで学び、43章では何を書いているのか

    2.モジュール設計とは何か

    2.1 「区切り・つなぎ・置き場所」を決める設計

    モジュール（ソフトウェアを「ひとまとまりの部品」として扱う単位）は、言語やプロジェクトによって、パッケージ（Java の com.example.order）、ディレクトリ（src/order/）、名前空間（C# の namespace Order）、論理的なサービス（「注文サービス」）などの形で現れます。モジュールは 外から見える単位 で、中身の詳細は隠し、決めた入口だけを公開します（詳しくは モジュールの基本概念）。

    モジュール設計 とは、コードをこうした まとまりのある単位（モジュール・パッケージ・コンポーネント） に分け、中身のまとまり（凝集） と つながり方（結合） を整えることです。43章では、これを次の3つの問いとして扱います。

    どこで区切るか

    責務・変更理由・業務の区切りで、モジュールの境界を決める。
    → 10・20・30 フォルダ

    どうつなぐか

    公開インターフェース、依存の向き、データの受け渡しを決める。
    → 40・50 フォルダ

    どこに置くか

    ディレクトリ・パッケージ構成として形にし、チームで守り続ける。
    → 60・70 フォルダ

    2.2 設計の階層の中での位置

    アーキテクチャが「家全体の間取り」なら、モジュール設計は 「部屋の役割分担と、部屋同士のドアの付け方」 に相当します。アーキテクチャが 全体の骨組み を決め、モジュール設計が その中の切り方の具体 を担います。

    なぜこの単位の設計が必要になるのか ── 機能が増えると「どこに何があるか分からない」「触ると壊れそう」が増え、開発速度が落ちていきます。モジュール設計は、この複雑さを 意味のある塊 に分けて管理するための設計です。理由の詳細は モジュール設計を学ぶ理由 で扱います。

    3.この章が扱う範囲と、骨格になる3冊

    3.1 骨格になる3冊

    43章は、次の3冊を組み合わせた構成にしています。骨格は1冊目、そこに2冊目と3冊目の考え方を加えています。

    『Clean Architecture』第4部

    Robert C. Martin

    コンポーネントの原則。パッケージの中身のまとまりを決める REP・CCP・CRP（凝集の3原則）と、パッケージ同士のつながりを決める ADP・SDP・SAP（結合の3原則）。章の 骨格 です。

    → パッケージ設計の原則、凝集の3原則、結合の3原則と循環依存

    『A Philosophy of Software Design』

    John Ousterhout

    深いモジュール（小さなインターフェースの奥に多くの機能を隠すモジュール）と 情報隠蔽。モジュールの良し悪しを測る具体的な物差しとして加えています。

    → カプセル化と情報隠蔽、深いモジュールと浅いモジュール

    『Balancing Coupling in Software Design』（2024）

    Vlad Khononov（邦題『ソフトウェア設計の結合バランス』）

    結合を「なくすもの」ではなく「バランスを取るもの」と捉え直し、統合強度・距離・変動性 の3つの次元で見る考え方（バランス結合）を加えています。

    → バランス結合 ほか 20-4〜20-7

    3.2 扱う範囲

    43章が書くのは、「モジュール・ディレクトリでどう実現するか」 です。凝集・結合の一般論、DDD、アーキテクチャスタイル、SOLID などの個別原則は、それぞれ兄弟の章が 本拠地 になっていて、43章ではモジュール設計に関わる部分だけを書き、詳細はリンクで渡します（5章の分担表）。

    扱うこと扱わないこと（本拠地へリンク）
    モジュールの境界・カプセル化・深さ凝集・結合・カプセル化の一般論
    モジュール単位の凝集度・結合度、バランス結合コナーセンス・結合の指標の詳しい定義
    ドメイン・技術・機能・レイヤーによる分割の仕方DDD そのもの（境界づけられたコンテキスト等）
    インターフェース・依存の向き・データの受け渡しSOLID・DIP などの個別原則の詳細
    パッケージ原則（REP/CCP/CRP・ADP/SDP/SAP）クラス単位の設計・GoF デザインパターン、メソッド設計
    スタイルをディレクトリ構成に落とし込む方法アーキテクチャスタイル自体、分散としてのモノリス／マイクロサービス判断

    読み分けのコツ

    「凝集度とは何か」「DDD とは何か」のような 考え方そのもの を知りたいときは本拠地へ、「それをパッケージやフォルダにどう落とすか」を知りたいときは43章へ、と使い分けると迷いません。

    6.よくある誤解

    誤解1：「モジュール設計はフォルダの並べ方の話」

    フォルダ構成は最後に現れる 形 にすぎません。中心にあるのは「どこで区切るか（凝集）」「どうつなぐか（結合・依存の向き）」の判断で、ディレクトリはその判断を表現し、守るための手段です。だから43章は 10〜50 で考え方を積み上げてから、60 で構成に落とし込む順になっています。

    誤解2：「アーキテクチャを決めればモジュール設計も決まる」

    アーキテクチャは全体の骨組み（家の間取り）を決めますが、その中で どの部屋に何を置き、ドアをどう付けるか は別に決める必要があります。同じクリーンアーキテクチャでも、モジュールの切り方次第で変更のしやすさは大きく変わります。

    誤解3：「結合はなくせばなくすほど良い」

    43章で加えている Khononov のバランス結合は、結合を なくすもの ではなく バランスを取るもの として扱います。強く結びついていてよい場所もあり、結合を消そうと層やインターフェースを増やしすぎると、かえって複雑になります。詳しくは バランス結合 で扱います。

    7.まとめ

    • モジュール設計は、コードを どこで区切り、どうつなぎ、どこに置くか を決める、モジュール・パッケージ単位の設計である。
    • アーキテクチャ（家全体の間取り）とクラス・メソッド設計の間にあり、部屋の役割分担と部屋同士のドア を受け持つ。
    • 骨格は『Clean Architecture』第4部のコンポーネントの原則。そこに Ousterhout の 深いモジュール・情報隠蔽 と、Khononov の 結合の強度・距離・変動性 を加えている。
    • フォルダはテーマ別で、10 基礎 → 20 凝集と結合 → 30 分割 → 40 つなぎ方 → 50 パッケージ原則 → 60 構成 → 70 品質と運用 → 80 演習 の順に読む。90 付録は辞書として使う。
    • 一般論（凝集・結合・カプセル化、DDD、アーキテクチャスタイル、SOLID など）は兄弟の章が本拠地。43章は「モジュール・ディレクトリでどう実現するか」に絞っている。
