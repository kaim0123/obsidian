    60 構成と実装

    ヘキサゴナルのモジュール構成 — ポートとアダプタでコアを守る

    ドメインを中心に置き、HTTP や DB などの外部を差し替え可能にするのがヘキサゴナルアーキテクチャ（ポートとアダプタ）です。コアと外部の分け方、Driving / Driven の2種類のポート、アダプタの役割、そしてテストしやすさとの関係を、モジュール構成の視点で解説します。

    もとにしたノート：60_構成と実装/03_ヘキサゴナルアーキテクチャのモジュール構成

    ひとことで言うと

    ヘキサゴナルは「コア（ドメイン）が必要な約束（ポート）を自分で定義し、外部の技術はその約束を実装するアダプタとして外側に置く」構成です。アダプタを付け替えるだけで UI や DB を変えられ、テストでは偽物のアダプタで DB なしに動かせます。

    1.このページで扱うこと

    このページは「ポートとアダプタを モジュール・ディレクトリにどう落とし込むか」を扱います。スタイルそのものの説明は 41章：ヘキサゴナルアーキテクチャ・41章：依存性のルールとクリーンアーキテクチャ を参照してください。

    ヘキサゴナルアーキテクチャ（ポートとアダプタ）で、ドメインを 中心 に置き、外部を 差し替え可能 にする構造を学びます。

    • コアと外部の分離
    • ポートの設計：Driving（Primary）と Driven（Secondary）
    • アダプタの役割
    • テストしやすさとの関係

    前のページの レイヤード が「上から下へ」の積み重ねだったのに対し、ヘキサゴナルは「中心と外側」で考えます。

    2.コアと外部の分離

    ヘキサゴナルでは、アプリケーションを コア（ドメイン ＋ アプリケーション） と 外部（UI, DB, 外部サービス） に分けます。

    部分内容
    コア業務ルール。外部技術に依存しない
    外部入出力の詳細。コアの ポート を 実装

    3.ポートの設計

    ポート ＝ コアが外部に要求する インターフェース（約束ごとだけを書いた型）です。依存関係の管理 で扱った DIP（依存性逆転の原則：詳細が抽象に依存するように向きをそろえる）をそのまま使っています。DIP の一般論は 41章：依存性逆転の原則 を参照してください。

    種類方向例
    Driving（Primary）外 → コアPlaceOrderUseCase の入口
    Driven（Secondary）コア → 外OrderRepository, PaymentGateway

    Driving は「コアを 動かす側（画面や API）が使う入口」、Driven は「コアに 動かされる側（DB や決済サービス）に対してコアが求める出口」と覚えると分かりやすいです。

    // Driven Port（コアが定義）
interface PaymentGateway {
  charge(amount: Money, customerId: CustomerId): Promise<PaymentId>;
}

// Driving Port（ユースケースそのもの）
interface PlaceOrderPort {
  placeOrder(cmd: PlaceOrderCommand): Promise<OrderId>;
}

    4.アダプタの役割

    アダプタ ＝ ポートの 具体実装 です。外部技術をコアの言語に 翻訳 します。

    アダプタ例
    Web AdapterREST Controller → UseCase 呼び出し
    DB AdapterPostgresOrderRepository
    External API AdapterStripePaymentGateway

    図の UseCase → StripeGateway の矢印は「呼び出しの流れ」です。ソースコード上の依存は、StripeGateway がコアの PaymentGateway ポートを実装する（外側からコアへ向かう）形になります。

    差し替えのしやすさ

    新しい UI（CLI, gRPC） を足すとき、コアはそのまま、アダプタだけ追加します。

    5.テストしやすさとの関係

    ヘキサゴナルは テスト容易性 と相性が良いです。

    テスト方法
    ドメイン単体ポートなし、純粋な Entity / DomainService
    ユースケースポートを Fake / Mock で差し替え
    アダプタ統合テストで DB / API と接続

    Fake はメモリ上で動く簡易版の実装、Mock は呼ばれ方を確かめるための偽物の部品です。

      UseCase テスト
  ┌─────────────────────────┐
  │ PlaceOrderUseCase       │
  │   + FakePaymentGateway  │
  │   + InMemoryOrderRepo   │
  └─────────────────────────┘
  → DB なしで実行可能

    テストしやすいモジュール設計 と合わせて読むと理解が深まります。

    6.よくある誤解

    誤解1：「ポートは外部（DB 側）が用意するもの」

    ポートは コアが定義する契約 です。DB や決済サービスの都合でポートの形を決めるのではなく、コアが「こういう操作が欲しい」と決め、アダプタがそれに合わせて翻訳します。

    誤解2：「ポートは出口（Repository など）だけ」

    ポートには、外からコアを動かすための Driving（Primary）と、コアが外を使うための Driven（Secondary）の2種類があります。ユースケースの入口も Driving ポートです。

    誤解3：「新しい UI を足すとコアも書き換えが必要」

    CLI や gRPC を足すときは、コアはそのままでアダプタだけを追加します。これがヘキサゴナルの「差し替え可能」の意味です。

    7.まとめ

    • ヘキサゴナル ＝ コア（ドメイン）中心 ＋ ポート/アダプタ
    • ポート はコアが定義する契約（Driving / Driven）
    • アダプタ が HTTP, DB, 外部 API を接続
    • ポートの差し替えで テスト・技術変更 がしやすい
