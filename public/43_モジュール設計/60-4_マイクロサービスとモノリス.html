    60 構成と実装

    マイクロサービスとモノリス — モジュール境界とサービス境界の関係

    アプリ全体を1つにまとめるモノリスと、小さなサービスに分けるマイクロサービス。どちらが優れているかではなく、それぞれのトレードオフを知ることが大切です。このページでは、両者の構造・メリット・デメリットの比較、モジュラーモノリス、いつサービスに分けるかの判断、過剰分割のリスク、代表的な課題とよくある失敗を、モジュール設計の視点からまとめます。

    もとにしたノート：60_構成と実装/04_マイクロサービスとモノリスのモジュール設計、60_構成と実装/05_マイクロサービスとモノリス

    ひとことで言うと

    モノリス内のモジュールもマイクロサービスも「責務・境界・インターフェースで区切る」点は同じです。まず モノリスで作り、モジュール境界を固めた「モジュール化されたモノリス」 を目指し、独立デプロイ・チーム・障害分離などの強い理由があるときだけサービスに切り出します。

    1.このページで扱うこと

    システムの アプリケーション全体をどう分けるか という、最も大きな粒度での分割の話です。

    • モノリス（Monolith） … 1つの大きなアプリ として作る
    • マイクロサービス（Microservices） … 複数の小さなサービス に分けて作る

    どちらが優れているというものではなく、それぞれにトレードオフ（一方を良くすると他方が悪くなる関係）があります。このページではモノリス内のモジュール境界とサービス境界の関係に重点を置きます。分散システムとしての判断（分散モノリスやいつ分けるかの詳しい議論）は 41章：モノリスとマイクロサービス を参照してください。

    • モノリスとマイクロサービスの 構造・メリット・デメリット・比較表
    • モノリス内モジュールとサービス境界の 共通点
    • モジュラーモノリス と、モジュール設計が分割の土台になる理由
    • いつサービスに分けるか と 過剰分割のリスク
    • マイクロサービスの 代表的な課題、始め方、よくある失敗

    2.モノリスとは

    2.1 構造

    全機能が 1つのコードベース・1つのプロセス（実行中のプログラム1つ）で動きます。

    ┌────────────────────────────────────┐
│         1つのアプリケーション        │
│  ┌──────┐ ┌──────┐ ┌──────┐       │
│  │ユーザー│ │ 注文  │ │在庫   │       │
│  └──────┘ └──────┘ └──────┘       │
│         ↓         ↓         ↓         │
│         ┌───────────────┐             │
│         │    1つのDB     │             │
│         └───────────────┘             │
└────────────────────────────────────┘
1プロセス、1デプロイ、1データベース

    2.2 メリットとデメリット

    メリット

    • 開発が簡単
    • デバッグしやすい
    • トランザクションが扱いやすい（同じDB内で整合を取れる）
    • デプロイが単純（1つのサービスを動かすだけ）
    • パフォーマンスが良い（ネットワーク越しの通信がない）

    デメリット

    • コードが巨大化
    • チーム同士の衝突（同じコードを触る）
    • 一部の変更で全体を再デプロイ
    • 技術スタックを統一しないといけない
    • スケールが難しい（一部だけ増やせない）

    トランザクション とは、複数の更新を「全部成功か、全部取り消しか」のひとまとまりで扱うしくみです。スケール は、負荷に合わせて処理能力を増やすことです。

    3.マイクロサービスとは

    3.1 構造

    機能ごとに 独立したサービス を動かし、HTTP/gRPC/メッセージングで連携します。

    ┌─────────┐  ┌─────────┐  ┌─────────┐
│ユーザー  │  │ 注文    │  │ 在庫    │
│サービス  │  │サービス  │  │サービス  │
└────┬────┘  └────┬────┘  └────┬────┘
     ↓            ↓            ↓
 ┌──────┐   ┌──────┐   ┌──────┐
 │ DB-A │   │ DB-B │   │ DB-C │
 └──────┘   └──────┘   └──────┘

    3.2 メリットとデメリット

    メリット

    • 独立したデプロイ（影響範囲が狭い）
    • チーム独立（他チームに邪魔されない）
    • 技術選択の自由度（Node.js + Go + Python など）
    • 障害の隔離（1サービス落ちても他は動く）
    • 個別にスケール可能
    • 境界づけられたコンテキスト に合わせて切りやすい

    デメリット

    • 複雑さが爆増（デプロイ・監視・ログ・トレース）
    • 分散トランザクションが難しい
    • ネットワーク起因の問題（遅延・失敗・タイムアウト）
    • 開発環境の構築が大変
    • チームに経験が必要（初心者には厳しい）
    • 初期コストが高い

    境界づけられたコンテキスト は、DDD（ドメイン駆動設計）で「同じ言葉が同じ意味で通じる範囲」を指す用語です（42章：境界づけられたコンテキスト）。

    4.比較表

    観点モノリスマイクロサービス
    開発のしやすさ簡単難しい
    デプロイ1つサービスごと
    一貫性強い（ACID）弱い（結果整合性）
    チーム数1〜少数多数
    スケール難しい個別に可
    技術スタック統一自由
    障害の局所化低い高い
    ネットワーク遅延なしあり
    運用コスト低い高い
    初期開発コスト低い高い

    ACID はトランザクションが常に正しく完了することを保証する性質の総称、結果整合性 は「一時的にデータがずれても、時間がたてば正しくそろう」という考え方です。

    5.モノリス内モジュールとサービス境界の共通点

    どちらも 責務・境界・インターフェース で区切る点は同じです。

    観点モノリス内モジュールマイクロサービス
    境界パッケージ / ディレクトリ独立デプロイ単位
    通信関数呼び出しHTTP / メッセージ
    データ同一 DB（分離推奨）サービスごと DB

    良いモノリス内モジュール は、将来サービス分割するときの 候補境界 になります。

    6.モジュラーモノリス — 分割の土台

    6.1 モジュラーモノリスとは

    最近注目されているのが、モジュラーモノリス（Modular Monolith） です。

    • 1つのアプリ として動かす（デプロイ単位はモノリス）
    • 内部では明確にモジュールで分ける（境界づけられたコンテキストを意識）
    • 将来必要になったら マイクロサービスに切り出せる
    ┌──────────────────────────────────────┐
│  モジュラーモノリス（1アプリ）          │
│  ┌─────────┐ ┌─────────┐ ┌────────┐ │
│  │ user    │ │ order   │ │ stock  │ │
│  │ module  │ │ module  │ │ module │ │
│  └─────────┘ └─────────┘ └────────┘ │
│      ↕（内部API）    ↕          ↕     │
└──────────────────────────────────────┘

    マイクロサービスの設計思想 と、モノリスのシンプルさ のハイブリッドです。多くのプロジェクトでは、これが現実的な選択肢になります。

    6.2 モジュール設計がマイクロサービス分割の土台になる理由

    サービス分割前に モノリス内でモジュール境界を確立 しておくと、次の状態になっています。

    • 依存関係が すでに一方向
    • 公開 API が すでに定義 されている
    • 分割時は 通信方式を HTTP/イベントに置き換える 程度で済む
    段階状態
    1スパゲッティモノリス
    2モジュール化されたモノリス ← ここを目指す
    3サービス分割（必要なら）

    分散モノリスを避ける

    Distributed Monolith（分散モノリス：サービスに分散しただけで、中身は密結合のまま）を避けるには、段階 2 が不可欠です。

    7.どちらを選ぶか・いつ分けるか

    7.1 「モノリスが悪」ではない

    一時期「マイクロサービスが正義」という風潮がありましたが、モノリスは現在も現役 です。

    モノリスが向く場面

    • 小〜中規模 のプロジェクト
    • スタートアップ初期（仕様が不確定）
    • チームが小さい（10人以下）
    • 運用体制が整っていない
    • 業務ロジックがそれほど複雑でない

    マイクロサービスが向く場面

    • 大規模 な組織・システム
    • チームが多数（コンウェイの法則）
    • 異なる技術が必要
    • 個別のスケールが必要
    • 障害の隔離が重要
    • 既に運用体制が整っている

    コンウェイの法則 は「システムの構造は、それを作る組織のコミュニケーション構造に似る」という経験則です（41章：コンウェイの法則と Team Topologies）。

    7.2 いつモジュールをサービスに分けるか

    分ける理由が強い分けない方がよい
    独立したデプロイ・スケールが必要小チーム・小規模
    チームが完全に独立頻繁な横断変更
    技術スタックを分けたいトランザクション整合性が厳しい
    障害の分離が重要ネットワーク遅延が許容できない

    簡易的な判断フローは次のとおりです。

    1. 独立デプロイが必要？ → No なら、モジュール分割で十分
    2. Yes なら モジュール境界は明確？ → No なら、先にモノリス内で整理
    3. Yes なら、サービス分割を検討

    7.3 「マイクロ」の粒度

    「マイクロ」と名がついていても、コードが少ない必要はありません。

    • 1サービス = 1業務境界
    • 独立してデプロイ・運用できる
    • 内部は1つのアプリとして十分な機能を持つ

    粒度が細かすぎる（例：1 関数 = 1 サービス）のは ナノサービス と揶揄されることもあり、逆効果です。

    8.過剰分割のリスク

    リスク説明
    運用コストデプロイ・監視・ログが N 倍
    分散トランザクション整合性が複雑
    レイテンシネットワーク往復
    デバッグ困難リクエストが複数サービスを横断
     
      過剰分割
  UserService → ProfileService → AvatarService → ImageService
       （1 画面表示に 4 回 HTTP）

    YAGNI

    YAGNI（You Aren't Gonna Need It：必要になるまで作らない）の考え方で、必要になるまでサービス分割しません。まず モジュール で境界を学びます。

    9.マイクロサービスの代表的な課題

    9.1 分散トランザクション

    複数サービスをまたいだデータ整合性をどう取るか、という課題です。

    • Saga パターン：各サービスが自分の処理 ＋ 補償トランザクション（失敗時に取り消すための処理）を持つ
    • 結果整合性：一時的なズレを許容

    詳しくは 41章：データ所有権と SAGA を参照してください。

    9.2 サービス間通信

    • 同期通信（HTTP/gRPC）：シンプルだが依存が強くなる
    • 非同期通信（メッセージキュー）：疎結合だが複雑

    通信方式の比較は 41章：同期API・メッセージ・イベント駆動 で扱っています。

    9.3 観測性（Observability）

    • 分散トレーシング（OpenTelemetry, Jaeger）
    • 集約ログ（ELK, Loki）
    • メトリクス（Prometheus）

    何か問題が起きたとき、どのサービスの、どの処理で失敗したか を追える仕組みが必須です（41章：観測性）。

    9.4 サービスディスカバリ

    どのサービスがどこにあるかを動的に解決する仕組みです（Kubernetes, Consul）。

    10.どう始めるか — モノリスファースト

    1. まず モノリス で作る
    2. 業務を理解し、境界づけられたコンテキスト を見つける
    3. 成長とともに、モジュラーモノリス に整理
    4. どうしても必要なら、一部をマイクロサービスに切り出す

    最初からマイクロサービスは危険

    業務を理解する前に分けると、間違った境界で分けてしまい、やり直しが巨大コスト になります。

    11.よくある失敗

    1. 早すぎるマイクロサービス化

    業務理解が浅いまま分けて、後で 境界の引き直し に大きな手戻り。

    2. サービス間の強結合

    「マイクロサービス」と言いつつ、サービス間の呼び出しが多すぎて、実質モノリス ＋ ネットワーク遅延 状態。

    3. 運用コストを過小評価

    マイクロサービスは、インフラ・監視・CI/CD の整備コスト が大きい。これを甘く見積もると破綻する。

    4. データ共有

    複数サービスが同じ DB テーブルを触る → 密結合。DB も分ける。

    12.よくある誤解

    誤解1：「マイクロサービスの方が新しくて優れている」

    どちらが優れているというものではなく、トレードオフです。小〜中規模・小さなチーム・運用体制が整っていない場合は、モノリスの方が向いています。

    誤解2：「サービスに分ければ疎結合になる」

    モジュール境界が整理されないまま分散すると、呼び出しが多すぎる「分散モノリス」になり、密結合にネットワーク遅延が加わるだけです。先にモノリス内でモジュール境界を確立します。

    誤解3：「マイクロサービスはコードを小さくするほど良い」

    「マイクロ」はコード量ではなく「1サービス＝1業務境界」で考えます。1関数＝1サービスのような細かすぎる分割はナノサービスと呼ばれ、逆効果です。

    13.まとめ

    • モノリスとマイクロサービスは優劣ではなく トレードオフ。モノリスは現在も現役
    • モノリス内モジュールとサービスは 境界設計の考え方が共通
    • サービス分割は 独立デプロイ・チーム・障害分離 が理由のとき
    • モジュール化されたモノリス（モジュラーモノリス） が分割の土台。基本方針は モノリスファースト
    • 過剰分割 は運用・整合性・性能のコストを増やす
