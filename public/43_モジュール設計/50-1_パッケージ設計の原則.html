    50 パッケージ原則

    パッケージ設計の原則 — REP・CCP・CRP と ADP・SDP・SAP

    クラスの設計に SOLID 原則があるように、パッケージ（モジュール・コンポーネント）の設計にも原則があります。Robert C. Martin が提唱した6つのパッケージ設計原則を、「中身のまとまり（凝集）」の3原則と「パッケージ同士のつながり（結合）」の3原則に分けて、全体像をつかみます。原則どうしのトレードオフ、安定性と抽象度の関係、規模に応じた使い分け、npm パッケージでの例まで扱います。

    もとにしたノート：50_パッケージ原則/01_パッケージ設計の原則

    ひとことで言うと

    パッケージの 中身 は「同じ理由で変わるものをまとめ（CCP）、一緒に使われないものは分け（CRP）、リリースの単位で配る（REP）」。パッケージ同士の つながり は「循環させず（ADP）、安定したものに依存し（SDP）、安定したものほど抽象的にする（SAP）」。小規模なら CCP と ADP の2つを守るだけで十分です。

    1.このページで扱うこと

    クラスの設計に SOLID 原則（単一責任・開放閉鎖など、クラス設計の5原則。42章：SOLID とオブジェクト指向）があるように、パッケージ（モジュール・コンポーネント） の設計にも原則があります。Robert C. Martin（ロバート・C・マーティン。「ボブおじさん」の愛称で知られ、SOLID 原則やクリーンアーキテクチャを広めた技術者）が提唱した、6つのパッケージ設計原則 です。

    • REP / CCP / CRP — パッケージの 凝集（中身のまとまり） に関する3原則
    • ADP / SDP / SAP — パッケージ間の 結合（つながり） に関する3原則

    クラスレベルでは見えない、大きな粒度での設計指針 として役立ちます。このページは6原則の全体像をまとめたものです。各原則の詳しい説明は次のページで扱います。

    • 凝集の3原則とテンションダイアグラム → 凝集の3原則
    • 結合の3原則と循環依存の断ち切り方 → 結合の3原則と循環依存
    • npm パッケージやモノレポでの使い方 → npm パッケージとモノレポ

    2.凝集の3原則（中身のまとまり）

    「どのクラスを同じパッケージに入れるか」を決める3原則です。

    2.1 REP（Reuse-Release Equivalence Principle）— 再利用・リリース等価の原則

    原則

    「再利用の単位は、リリースの単位に等しい」

    パッケージとして 再利用してもらう なら、リリース（バージョン管理された配布物） の単位で提供すべき、という原則です。具体的には次のようになっていることです。

    • バージョン番号がついている
    • 変更履歴がある
    • 壊す変更は新バージョンで示す

    npm、PyPI、Cargo（それぞれ JavaScript・Python・Rust のパッケージ配布の仕組み）などのパッケージは、REP に従ってバージョン管理されています。

    2.2 CCP（Common Closure Principle）— 共通閉鎖の原則

    原則

    「同じ理由で変更されるクラスは、同じパッケージにまとめよ」

    SRP（単一責任の原則）のパッケージ版 です。仕様変更時に、1つのパッケージだけ変更すれば済む ようにします。

    例：「税率が変わる」という変更なら、税計算に関わるクラスは 同じパッケージ に集めておきます。

    2.3 CRP（Common Reuse Principle）— 共通再利用の原則

    原則

    「一緒に使われるものは、同じパッケージに。使われないものは、別パッケージに」

    使う側は 不要なものを含んだパッケージ を引き込みたくありません。使うクラスだけを含む 小さなパッケージ が望ましい、という原則です。ISP（インターフェース分離の原則：使わないメソッドへの依存を強制しない）のパッケージ版 とも言えます。

    3.凝集3原則のトレードオフ

    この3つは 同時に完全に満たすのは不可能 な関係です。CCP は「まとめよ」、CRP は「分けよ」と、逆方向に引っ張り合うからです。

         REP (リリース単位)
        /            \
    CCP                CRP
  (まとめよ)          (分けよ)
    • REP と CRP を取ると、パッケージが 小さくなりすぎ、リリースが煩雑に
    • REP と CCP を取ると、パッケージが 大きくなり、不要なものも含まれる
    • CCP と CRP を取ると、再利用しにくい

    プロジェクトの段階 によって、どの原則を重視するかが変わります。

    段階重視する原則
    開発初期CCP（共通閉鎖）
    成熟期CRP（共通再利用）

    この三角形（テンションダイアグラム）の読み方は 凝集の3原則 で詳しく扱います。

    4.結合の3原則（つながり）

    「パッケージ同士をどうつなぐか」を決める3原則です。

    4.1 ADP（Acyclic Dependencies Principle）— 非循環依存の原則

    原則

    「パッケージの依存関係に循環があってはならない」

    パッケージ A → B → C → A のような 依存の輪 を作らない、という原則です。

    循環依存の何が悪いか

    • ビルド順序が決まらない
    • 1つ変更すると全体を再テスト
    • モジュールが事実上1つの大きな塊になってしまう

    対策

    1. 依存方向を統一（上から下へ）
    2. 共通部分を別パッケージに抽出
    3. 依存性逆転でインターフェースを挟む

    循環の見つけ方・断ち切り方は 結合の3原則と循環依存、依存の方向の管理は 依存関係の管理 を参照してください。

    4.2 SDP（Stable Dependencies Principle）— 安定依存の原則

    原則

    「安定しているパッケージに依存せよ」

    変更されやすいパッケージに、変更されにくいパッケージが依存すると、常に巻き込まれます。ここでいう「安定」とは、変わりにくさのことです。

    • 安定している = 他から多く依存される、自分からは少ししか依存しない
    • 不安定 = 他への依存が多く、自分は他から少ししか依存されない

    多くのパッケージに使われているものは、変えると影響が大きいので簡単には変えられません（＝安定）。逆に、誰にも使われていないものは気軽に変えられます（＝不安定）。依存は常に 不安定 → 安定 の向きにします。

    4.3 SAP（Stable Abstractions Principle）— 安定抽象の原則

    原則

    「安定なパッケージは抽象的であれ」

    安定なパッケージ（他から多く依存される）は、具体ではなく抽象であるべき です。

    • 具体的だと、変更があったときに 多くの依存元が壊れる
    • 抽象なら、具体実装を差し替えても影響が最小化

    → DIP（依存性逆転の原則） のパッケージ版です（41章：依存性逆転の原則、疎結合・DIP・DI の整理）。

    5.SDP と SAP の関係：安定性と抽象度は相関する

    SDP で「依存は安定な方へ」、SAP で「安定なものは抽象的に」と言っているので、2つを合わせると 安定度と抽象度はそろっているのが良い ことになります。

           抽象的
          ↑
          │    理想（安定＋抽象）
          │         ●
          │
          │
          │   ●
          │  危険（安定＋具体）
          └───────────→ 安定
                 苦痛ゾーン
    組み合わせ評価理由
    安定かつ抽象良いインターフェースが定まっている基盤
    不安定かつ具体良い詳細は自由に変更できる
    安定かつ具体苦痛変更しにくいのに、変更の要求が多い
    不安定かつ抽象無益抽象なのに、誰も使っていない

    安定度や抽象度を数値で測る指標は 結合の3原則と循環依存、アーキテクチャ全体での結合の指標は 41章：結合の指標 を参照してください。

    6.実務での活かし方

    1. 共通ユーティリティ置き場を小さく保つ

    shared/ や utils/ が巨大化しやすいので、本当に共通なものだけ を置きます。

    2. ライブラリは抽象的に

    自分で作る共有ライブラリは、具体的な業務ロジックを持たない ようにします（安定＋抽象）。

    3. 依存の向きを可視化する

    パッケージ間の依存関係図を描き、循環がないか確認します。

    4. 内部ルールを強制する

    ESLint の import ルール、モノレポのパッケージ境界、Nx の boundaries など、ツールで依存方向を強制 します（依存ルールの自動検査）。

    モノレポ は複数のパッケージを1つのリポジトリで管理する方式、Nx はモノレポ用のビルドツールで、パッケージ間の依存ルール（boundaries）を検査できます。

    7.初心者向けの実践ガイド

    小規模プロジェクト

    • CCP（同じ理由で変わるものはまとめる）を意識
    • ADP（循環依存を避ける）を守る

    この2つだけで十分です。

    中〜大規模プロジェクト

    • CRP（使われないものは別パッケージに）
    • SDP（安定したものに依存）
    • REP（バージョン管理する）

    ライブラリ化・モノレポ化するときに意識します。

    8.npm パッケージでの例

    8.1 REP を満たす

    {
  "name": "@company/user-lib",
  "version": "1.2.3",   // バージョン管理あり
  "main": "dist/index.js",
  "files": ["dist"]
}

    package.json（npm パッケージの設定ファイル）に version があり、配布するファイル（files）と入口（main）が決まっています。リリースの単位で再利用してもらえる形です。

    8.2 CRP を満たす

    // user-lib（ユーザー機能だけを含む）
export { User, UserRepository };

// order-lib（注文機能だけを含む）
export { Order, OrderRepository };

    ユーザー機能だけ使いたい人が、order-lib を引き込まずに済みます。モノレポでの詳しい適用は npm パッケージとモノレポ で扱います。

    9.よくある誤解

    誤解1：「6つの原則は全部いつも守るべき」

    凝集の3原則は同時に完全には満たせない関係です。小規模なら CCP と ADP の2つで十分で、CRP・SDP・REP はライブラリ化・モノレポ化するときに意識すれば間に合います。プロジェクトの段階に合わせて重みを変えます。

    誤解2：「安定したパッケージ＝よくできていて、バグが少ないパッケージ」

    ここでいう「安定」は品質の高さではなく、変わりにくさ のことです。多くのパッケージから依存されていると、変えたときの影響が大きいので変えにくくなります。だからこそ、安定なパッケージは抽象的にしておく（SAP）必要があります。

    誤解3：「共通で使うものは、とりあえず shared/ や utils/ に入れておけばよい」

    何でも入れると、共通置き場は多くのパッケージから依存される「安定かつ具体」の塊になり、苦痛ゾーンに入ります。また、使わないものまで引き込むことになり CRP にも反します。本当に共通なものだけを置き、小さく保ちます。

    10.まとめ

    原則意味一言で
    REP再利用単位=リリース単位バージョン管理を
    CCP同じ理由で変わるものは一緒に変更の単位でまとめる
    CRP一緒に使われるものは一緒に使われないものは除外
    ADP循環依存するな矢印は一方向に
    SDP安定なものに依存不安定→安定
    SAP安定なら抽象DIPの拡大版
