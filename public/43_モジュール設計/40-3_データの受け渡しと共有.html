    40 つなぎ方

    データの受け渡しと共有 — 何を渡し、何を共有しないか

    モジュール同士は、データをやり取りしないと協力できません。しかし渡し方を間違えると、せっかく分けたモジュールがまた絡み合ってしまいます。このページでは、モジュール間で何をどう渡すか、DTO・値オブジェクト・エンティティの使い分け、密結合の典型である共有データベースの問題、イベントによる連携、そしてトランザクション境界の考え方を解説します。

    もとにしたノート：40_つなぎ方/03_データの受け渡しと共有

    ひとことで言うと

    モジュール間では ID・DTO・コマンド を渡し、相手の 内部の状態（エンティティ）やデータベースのテーブルは直接触らない ようにします。即時の結果が要らない連携は イベント でゆるくつなぎ、1つのトランザクションで守る範囲は 1つの集約・1つのモジュール にとどめるのが基本です。

    1.このページで扱うこと

    モジュールに分けたあとも、注文モジュールが決済モジュールに「この注文の代金を請求して」と頼むように、モジュール同士はデータを受け渡します。このとき 何を渡すか、そして 何を共有してはいけないか が、モジュールの独立性を大きく左右します。

    このページでは次の内容を扱います。

    • モジュール間で何を渡すべきか：ID・DTO・コマンド・ドメインオブジェクト
    • DTO・値オブジェクト・エンティティの使い分け
    • 共有データベースの落とし穴：密結合の典型
    • イベントとメッセージによる連携
    • 整合性とトランザクション境界

    インターフェース（公開 API）の形そのものは モジュール間インターフェース、依存の向きは 依存関係の管理 で扱います。

    2.モジュール間で何を渡すべきか

    モジュール間で渡すものには、主に次の4種類があります。

    渡すもの向いている場面
    プリミティブ + ID参照だけ必要（orderId: string）
    DTO（データ転送オブジェクト）読み取り専用のスナップショット
    コマンド / クエリオブジェクト意図が明確な操作
    ドメインオブジェクト同一境界内、または慎重に設計した共有

    用語を補足します。

    • プリミティブ：文字列や数値のような、言語に最初からある単純な値です
    • DTO（Data Transfer Object）：データを運ぶためだけの入れ物です。振る舞い（メソッド）は持たず、値を並べただけの形をしています
    • スナップショット：ある時点の状態を写し取ったコピーです。受け取った側が書き換えても、元のデータには影響しません
    • コマンド / クエリオブジェクト：「注文を確定する」（コマンド＝変更の依頼）、「注文一覧を探す」（クエリ＝問い合わせ）のように、操作の意図を1つの型で表したものです
    • ドメインオブジェクト：業務のルールや振る舞いを持つオブジェクト（下で説明するエンティティや値オブジェクト）です
    ✕ 避けたい：相手モジュールの Entity をそのまま書き換える（mutate） 
    // 決済モジュールが、注文モジュールの Order を直接書き換えてしまう
order.status = 'PAID';
    ◯ 推奨：ID または読み取り専用 DTO を渡す 
    // 注文モジュールの公開 API に、ID を渡して頼む
orderApi.markAsPaid(orderId);

    原則

    相手の 内部状態 を直接触らないこと。状態を変えたいときは、その状態を持っているモジュールに「頼む」形にします。

    3.DTO・値オブジェクト・エンティティの使い分け

    データを表す型には性質の違う3種類があり、モジュールの境界をまたいでよいかどうかが変わります。

    種類特徴モジュール間
    DTO平坦、シリアライズ向きAPI 境界でよく使う
    値オブジェクト不変、値で等価共有可能（小さく安定）
    エンティティID で同一性、ライフサイクル原則モジュール内
    • シリアライズ：オブジェクトを JSON などの文字列やバイト列に変換して、通信や保存ができる形にすることです。DTO は入れ子が少なく平坦なので変換しやすい形です
    • 値オブジェクト：金額や住所のように、作ったあと変わらず（不変）、中身の値が同じなら同じものとみなすオブジェクトです。小さく安定しているので、モジュール間で共有しても困りにくいものです
    • エンティティ：注文や会員のように、ID で「同じもの」かどうかを見分け、作成→変更→削除という一生（ライフサイクル）を持つオブジェクトです。業務ルールを内側に抱えているので、原則としてモジュールの外には出しません
    // モジュール境界での DTO
interface OrderSummaryDto {
  orderId: string;
  status: string;
  totalAmount: number;
}

// モジュール内部の Entity（export しない）
class Order {
  cancel(): void { /* 業務ルール */ }
}

    外には OrderSummaryDto だけを公開し、cancel() のような業務ルールを持つ Order はモジュールの中に閉じ込めます。エンティティと値オブジェクトそのものの詳しい説明は 42章：エンティティと値オブジェクト を参照してください。クラス単位での詳しい設計は 44_クラス設計・デザインパターン で深掘りします。

    4.共有データベースの落とし穴

    複数モジュールが同じ DB テーブルを直接読み書き するのは、アンチパターン（よく見かけるが避けるべき設計）です。

    問題説明
    スキーマ変更の連鎖1 テーブル変更が全モジュールに波及
    整合性の責任が不明誰がトランザクションを張るか
    境界の消失モジュール分割の意味が薄れる

    スキーマ はテーブルの列や型などの構造のこと、トランザクション は「全部成功するか、全部なかったことにするか」をまとめて保証する処理の単位のことです。テーブルを共有すると、テーブルの構造がそのまま全モジュールの「隠れた公開 API」になってしまいます。

    ノートの図をテキストで書くと次のとおりです。

      アンチパターン
  [Order Module] ──→ orders テーブル ←── [Report Module]
                           ↑
                    直接 SQL で共有

  改善
  [Order Module] ──→ OrderRepository（唯一の書き込み）
  [Report Module] ──→ OrderQuery API または 読み取りレプリカ

    改善後は、orders テーブルに書き込めるのは注文モジュールの OrderRepository だけです。集計をしたいレポートモジュールは、注文モジュールが公開する問い合わせ用の API（OrderQuery API）か、読み取りレプリカ（読み取り専用に複製したデータベース）から読みます。テーブル構造を変えても、影響は注文モジュールの中で止まります。

    サービス単位でのデータの持ち主の考え方は 41章：データ所有権と SAGA も参照してください。

    5.イベントとメッセージによる連携

    相手を直接呼び出して結果を待つ 同期呼び出し の代わりに、イベント（「注文が確定した」のような、起きた出来事の知らせ）で疎結合にできます。発行する側は、誰が受け取るかを知りません。

      Order Module                    Payment Module
       │                                │
       │  OrderPlacedEvent              │
       └──────── publish ──────────────→│ subscribe
                                        │ charge()

    連携の方式は、場面に応じて使い分けます。

    方式向く場面
    同期 API即座の結果が必要（在庫確認など）
    イベント副作用・通知・他コンテキスト連携
    メッセージキュー非同期・耐障害性が必要

    副作用 は本来の処理に付随して起きる別の処理（メール送信など）、コンテキスト は業務上の意味が通じる範囲（DDD の「境界づけられたコンテキスト」）、メッセージキュー はメッセージを一時的にためておき、受け手が後から順に取り出す仕組みです。受け手が止まっていてもメッセージは失われないため、障害に強くなります。

    イベント駆動の考え方は 42章：イベント駆動設計、通信方式の比較は 41章：同期 API・メッセージ・イベント駆動 も参照してください。

    6.整合性とトランザクション境界

    1 トランザクション で整合性を保てる範囲は、通常 1 集約・1 モジュール内 です。集約 とは、注文と注文明細のように「一緒に整合性を保つべきオブジェクトのまとまり」のことです（詳しくは 42章：集約とリポジトリ）。

    パターン説明
    単一モジュール内 TX注文作成 + 明細保存
    分散 TX（2PC）複雑・避けがち
    結果整合性イベント + eventual consistency
    • TX：トランザクションの略です
    • 2PC（2相コミット）：複数のデータベースにまたがる処理を、「全員準備できたか確認 → 全員で確定」の2段階でまとめて確定させる方式です。仕組みが複雑で、参加者の1つが止まると全体が待たされるため、避けられがちです
    • 結果整合性（eventual consistency）：一瞬はデータが食い違っていても、イベントが届いて処理されれば 最終的には つじつまが合う、という考え方です
      Order モジュール内（強整合）
  ┌─────────────────────┐
  │ TX: Order + Lines   │
  └─────────────────────┘

  Order → Payment（結果整合）
  OrderPlaced → 非同期で決済 → PaymentCompleted

    注文と明細の保存は同じモジュールの中なので、1つのトランザクションで「両方保存するか、どちらも保存しないか」を保証できます（強整合）。一方、注文から決済への流れはモジュールをまたぐので、OrderPlaced イベントを受けて非同期に決済し、終わったら PaymentCompleted を知らせる、という結果整合で扱います。

    7.よくある誤解

    誤解1：「同じ会社の同じシステムなら、テーブルを直接読むくらい問題ない」

    読むだけでも、テーブルの構造に依存したことになります。列名を変えた・テーブルを分けたというだけで、別モジュールの SQL が壊れます。読み取りでも、持ち主のモジュールが公開する API か読み取りレプリカを通すのが基本です。

    誤解2：「エンティティをそのまま返せば、DTO を作る手間が省ける」

    エンティティを外に出すと、受け取った側が業務ルールを通さずに状態を書き換えられてしまいます。また、エンティティの中身を変えるたびに外のモジュールも影響を受けます。境界では DTO や ID を渡し、エンティティはモジュール内に閉じ込めます。

    誤解3：「イベントにすれば、どんな連携も疎結合になって良くなる」

    イベントは結果整合になるので、データが一時的に食い違う状態を受け入れる必要があります。在庫確認のように即座の結果が必要な場面では、同期 API の方が向いています。イベントは「結果整合性を理解した上で」使う道具です。

    8.まとめ

    • モジュール間は ID・DTO・コマンド を渡し、内部 Entity を共有しない
    • 共有 DB 直接アクセス は密結合の温床
    • イベント で疎結合連携（結果整合性を理解した上で）
    • トランザクション境界 = 集約・モジュール単位が基本

    次は、モジュールをさらに大きな単位（パッケージ）としてまとめるときの原則を パッケージ設計の原則 で見ていきます。
