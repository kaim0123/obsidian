    10 モジュールの基礎

    モジュールの基本概念 — 責務・境界・インターフェースと3つの性質

    「モジュール」とは何でしょうか。関数・クラス・パッケージ・サービスとどう関係するのでしょうか。このページでは、以降のページで繰り返し使う 責務・境界・インターフェース の意味を固め、Vlad Khononov が示した 機能・ロジック・コンテキスト という3つの性質と、モジュールが 入れ子（多層） になっているという見方を解説します。

    もとにしたノート：10_モジュールの基礎/02_モジュールの基本概念

    ひとことで言うと

    モジュール は、責務を持ち、境界で囲まれた部品の塊です。境界の外には インターフェース（何をするか＝機能） を見せ、内側には 実装（どうやるか＝ロジック） を隠します。さらに、使われる前提である コンテキスト も意識します。この形は、サービスからメソッドまで、どの層にも同じように現れます。

    1.このページで扱うこと

    以降のページで繰り返し使う言葉の定義を、ここで固めます。

    • モジュールとは何か、どんな形で現れるか
    • 関数・クラス・パッケージ・サービスとの関係
    • 責務・境界・インターフェースと実装の分離
    • モジュールの3つの性質：機能・ロジック・コンテキスト（Khononov）
    • モジュール化は多層的：サービス・パッケージ・サブパッケージ・オブジェクト・メソッド

    2.モジュールとは何か

    モジュール とは、ソフトウェアを ひとまとまりの部品 として扱う単位です。言語やプロジェクトによって、次のような形で現れます。

    形例
    パッケージJava の com.example.order
    ディレクトリsrc/order/
    名前空間C# の namespace Order
    サービス（論理）「注文サービス」モジュール

    モジュールは 「外から見える単位」 です。中身の詳細は隠し、決めた入口だけを公開します。

    3.関数・クラス・パッケージ・サービスとの関係

    単位粒度モジュールとの関係
    関数最小モジュール 内部 の処理
    クラス小モジュールを構成する部品
    パッケージ / ディレクトリ中モジュールの 物理的な表現 が多い
    サービス（マイクロサービス）大独立デプロイされる モジュールの極端な形
     
    モジュール Order
├── OrderService.java      （クラス）
├── OrderRepository.java   （クラス）
└── calculateTotal()       （関数・メソッド）

    1 モジュール = 関連するクラス・関数の集まり + 公開インターフェース と考えるとよいです。「独立デプロイ」とは、他の部分と切り離して単独で本番環境に出せることです（マイクロサービスとモノリスの比較は マイクロサービスとモノリス で扱います）。

    4.責務（Responsibility）という考え方

    責務 とは、そのモジュールが 担当すべき仕事 です。

    良い例

    Payment モジュール → 「支払い処理と決済連携」

    悪い例

    Common モジュール → 「なんでも」

    問い意図
    このモジュールは 何のため に存在するか1 文で説明できるか
    変化の理由は 1 つ にまとまるか分割・統合の判断材料

    責務が曖昧なモジュールは、時間とともに ゴミ箱（何でも放り込まれる場所）になりやすいです。

    5.境界（Boundary）と内部・外部

    境界 は、モジュールの 内側と外側 を分ける線です。

    • 内部：自由に変更してよい（外に影響しない限り）
    • 外部：公開インターフェース。変更は慎重に

    境界がないと、他モジュールが内部実装に直接依存し、結合度（モジュール同士の依存の強さ）が上がります。結合度については 結合度 で詳しく扱います（一般論は 42章：凝集度と結合度）。

    6.インターフェースと実装の分離

    モジュールは インターフェース（契約） と 実装（中身） を分けて設計します。インターフェースは「こう呼べばこう動く」という外向けの約束です。

    // インターフェース（境界の外側に見える契約）
interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order): Promise<void>;
}

// 実装（境界の内側・差し替え可能）
class PostgresOrderRepository implements OrderRepository {
  // ...
}
    分離する理由効果
    実装を隠す内部変更が他モジュールに波及しにくい
    契約を固定する呼び出し側のコードが安定する
    差し替えテスト用の偽実装（モック）を入れやすい

    詳細は モジュール間インターフェース で深掘りします。

    7.モジュールが持つ3つの基本的な性質：機能・ロジック・コンテキスト

    Vlad Khononov『ソフトウェア設計の結合バランス』（原著 Balancing Coupling in Software Design、2024）の第4章「結合とモジュール性」では、モジュールを 機能（Function）・ロジック（Logic）・コンテキスト（Context） の3つの性質で捉えます。

    モジュールとは、明確に定義された機能を囲む境界であり、その機能をシステムの他の部分に公開するもの である。

    性質何か外から見えるかひとことで
    機能（Function）モジュールの目的。提供する機能公開（公開インターフェースで表現）何をするか
    ロジック（Logic）機能を実現するための実装と設計判断のすべて隠す（境界で守る）どうやってするか
    コンテキスト（Context）モジュールが使われる環境についての、明示的な要件と暗黙の前提公開だが、インターフェースには現れにくいどんな状況で使う前提か

    7.1 身近な例で理解する

    本で使われている例です。

    レゴブロック交換レンズ（カメラ）
    機能他のブロックとつながる（上のポッチと下の穴＝接続インターフェース）特定の焦点距離・絞りで画像をとらえる
    ロジック丈夫な構造を支え、確実にくっつくプラスチック素材カメラとつながり、光学効果を生む内部の機構
    コンテキスト子ども向けの安全なおもちゃ。本物の家を建てるためのものではない対応するカメラの機種。オートフォーカスが使えるかどうかは機種による

    ソフトウェアで言うと、たとえば次のようになります。

    // 機能：公開メソッドが「何ができるか」を表す
interface CustomerRepository {
  load(id: string): Promise<Customer>;
  save(customer: Customer): Promise<void>;
  findByName(name: string): Promise<Customer[]>;
  findByPhone(phone: string): Promise<Customer[]>;
}
// ロジック：RDB でも、ドキュメント DB でも、複数の DB の組み合わせでもよい。利用者は知らなくてよい
// コンテキスト：例えば「呼び出しは認証済みである前提」「同時アクセスは少ない前提」など。シグネチャには書かれない

    シグネチャ とは、メソッドの名前・引数・戻り値の型の組み合わせのことです。

    7.2 3つの性質と結合の関係

    • 機能だけを知って使える なら、結合は弱い（契約結合・データ結合）
    • ロジックを知らないと使えない（DB を直接読む、内部クラスを使う）なら、結合は強い（侵入的結合・内容結合）
    • コンテキストは見落とされやすい。インターフェースに現れないため、「いつの間にか前提が崩れて壊れる」原因になる

    契約結合・侵入的結合は 統合強度、データ結合・内容結合は 結合度 で扱います。

    7.3 設計・レビューでの問い

    • ☐ そのモジュールの 機能（目的）を、ロジック（実装の詳細）に触れずに説明できる か？
    • ☐ そのモジュールの 使われ方の前提（コンテキスト）は明示されている か？ それとも、いずれ忘れられる暗黙の前提になっていないか？

    5節とのつながり

    5節の「境界の外 ＝ インターフェース、内 ＝ 実装」は、機能（外）とロジック（内） の区別にあたります。コンテキストは、そのどちらにも書かれにくい 第3の要素 として意識しておくと、設計の抜け漏れに気づきやすくなります。

    8.モジュール化は多層的に行われる

    3節では「関数・クラスはモジュールの 内部」と整理しました。これは「業務単位のモジュール」を中心に見た場合の言い方です。Khononov はもっと広く、

    独立した単位として切り出せる可能性があるなら、それはモジュールである。

    と考えます。つまり、サービスもパッケージもクラスもメソッドも、それぞれがモジュール です。そして、モジュールは平らに並ぶのではなく、入れ子（階層） になっています。

    8.1 どの層にも「機能・ロジック・コンテキスト」がある

    層機能（公開するもの）ロジック（隠すもの）コンテキスト（前提）の例
    サービスREST API・メッセージなどの公開契約ソースコード、内部の DB・メッセージバス実行環境、計算資源、ネットワーク帯域、「呼び出しは認証済み」
    パッケージ公開されたクラス・関数（index.ts で export するもの）非公開のクラスと、その協調の仕方パッケージ全体が前提とする設定・ランタイム
    サブパッケージ親パッケージ内の他の部分に見せるものサブパッケージ内部の実装親パッケージの中だけで使われる前提
    オブジェクト（クラス）public なメソッド・プロパティprivate なフィールド・メソッド、データの保存方法呼び出し順序、スレッド安全性の前提など
    メソッド（関数）名前とシグネチャメソッドの本体、private なヘルパー引数の前提（null でない等）、必要な状態

    ※ サービスとオブジェクトの機能・ロジックの例は本の記述に基づきます。コンテキスト列の多くと、パッケージ・サブパッケージの行は、同じ考え方を当てはめた補足です。

    8.2 フラクタル（自己相似）な構造

    どの層も「境界・公開インターフェース・隠された実装」という 同じ形 をしています。拡大しても縮小しても同じ模様が現れる図形（フラクタル）に似ているので、Khononov はこれを ソフトウェア設計のフラクタル的な性質 と呼びます（本の第III部にも「ソフトウェア設計のフラクタル幾何学的性質」という章があります）。

    ここから分かる大事なことは2つです。

    1. 同じ原則がどの層にも使える
      情報隠蔽・高凝集・疎結合・バランス結合は、メソッドの設計にもサービスの設計にも使えます。「設計」と「アーキテクチャ」に本質的な境目はなく、見ている縮尺が違うだけ です。
    2. ある層の「外の複雑さ」は、1つ上の層では「中の複雑さ」になる
      クラス同士のつながり（クラスの外の複雑さ）は、パッケージから見れば内部の問題です。だから、モジュールを分けるだけでは複雑さは消えず、上の層に押し上げられるだけのこともあります（→ バランス結合 の「分散した複雑さ」）。

    8.3 実務でのヒント

    • 「モジュール」という言葉を見たら、いまどの層の話をしているか を確認する
    • 各層で「機能を、ロジックに触れずに説明できるか」を確かめる。メソッド名で中身が説明できない、パッケージの公開 API が内部クラスだらけ、などは境界がうまく引けていないサイン
    • 下の層ほど変更コストが小さい（同じファイル内）。上の層ほど大きい（別チーム・別デプロイ）。強く結びつくものほど、下の層（近い場所）にまとめる

    9.よくある誤解

    誤解1：「モジュール＝フォルダ（パッケージ）のことだけ」

    パッケージやディレクトリはモジュールの物理的な表現として多いだけです。Khononov の見方では、独立した単位として切り出せる可能性があれば、サービスもクラスもメソッドもモジュールです。

    誤解2：「インターフェースに書いてあることが、使う側の知るべきことのすべて」

    コンテキスト（「呼び出しは認証済み」「同時アクセスは少ない」などの前提）はシグネチャに現れにくく、見落とされやすい要素です。明示しておかないと、いつの間にか前提が崩れて壊れます。

    誤解3：「モジュールに分ければ複雑さは消える」

    ある層の外の複雑さは、1つ上の層の中の複雑さになるだけです。分けるだけでは複雑さは上に押し上げられることがあり、強く結びつくものは近い場所にまとめる必要があります。

    10.まとめ

    • モジュール = 責務を持つ、境界で囲まれた部品の塊
    • 関数・クラスはモジュール 内部、パッケージ・ディレクトリはモジュールの 表現
    • 責務 が明確だと分割・命名・レビューがしやすい
    • 境界 の外はインターフェース、内は実装 — この分離がモジュール設計の基本
    • モジュールの3つの性質：機能（何をするか・公開）、ロジック（どうやるか・隠す）、コンテキスト（どんな前提で使うか・暗黙になりがち）
    • モジュール化は サービス → パッケージ → サブパッケージ → オブジェクト → メソッド と多層的（フラクタル）に行われ、どの層にも同じ原則が使える
