    バランス結合 — 強度・距離・変動性で結合を判断する

    「結合度は低いほどよい」だけでは判断できない場面がたくさんあります。Vlad Khononov の『Balancing Coupling in Software Design』は、結合を「なくすもの」ではなく「バランスを取るもの」と捉え直しました。統合強度・距離・変動性という3つの次元、バランスの式、そして実務での優先順位の付け方を解説します。

    もとにしたノート：20_凝集と結合/03_バランス結合_強度・距離・変動性

    ひとことで言うと

    結合は なくすものではなく、バランスを取るもの です。強く結びつくもの（統合強度が高いもの）は近くに、弱く結びつくものは遠くに 置きます。ただし、変わらない部分ならアンバランスでも実害は小さい。式にすると BALANCE ＝（STRENGTH XOR DISTANCE）OR NOT VOLATILITY です。

    1.このページで扱うこと

    結合度 では「結合度は低いほどよい」と学びました。しかし実際には、

    • 同じクラスの中のメソッド同士は、強く結びついていて当然
    • 結合をなくそうとして層やインターフェースを増やしすぎると、かえって複雑になる
    • 二度と変わらない部分なら、多少強く結びついていても問題は起きない

    という場面がたくさんあります。

    Vlad Khononov は『Balancing Coupling in Software Design』（2024）で、結合を 「なくすもの」ではなく「バランスを取るもの」 として捉え直しました。このページは、そのモデル（バランス結合）の 入口 です。

    2.結合はなくせない

    結合の定義

    結合とは、システムの部品同士が相互作用するために、知識を共有している状態である。

    部品が協力して動く以上、何らかの知識（関数名・データの形・業務ルール…）は必ず共有されます。結合がゼロのシステムは、何もしないシステム です。

    だから問うべきは「結合をどう減らすか」ではなく、

    「どの部品とどの部品が、どのくらいの知識を、どのくらいの距離で共有してよいか」

    です。これを判断するために、Khononov は結合を 3つの次元 で考えます。

    2.1 知識は依存と逆向きに流れる（第1章「知識の流れ」）

    モジュール A が B を呼び出す（A → B に依存する）とき、知識は B から A へ流れます。B が自分の機能やデータ形式という知識を A に提供し、A はそれを前提にコードを書くからです。

    • 上流（upstream）＝ 知識を 提供する 側、下流（downstream）＝ 知識を 受け取って依存する 側
    • 上流が変わると、受け取った知識が古くなるので 下流が壊れる。だから「どれだけの知識が流れているか」が結合の強さになる
    • 第1章では、結合の 大きさ（Magnitude） も扱います。「結合している・していない」の二択ではなく、どのくらいの知識を共有しているか という程度の問題として捉える、という第II部への導入です

    3.結合の3つの次元（概要）

    次元問い要点詳細
    統合強度どれだけの知識を共有しているか強い順に 侵入的 → 機能的 → モデル → 契約統合強度
    距離一緒に変更するのにどれだけ手間がかかるかコードの位置（メソッド → クラス → モジュール → サービス → システム）＋ 組織の距離距離と変動性
    変動性どれくらい頻繁に変わるかコアサブドメイン（事業の競争力の源になる、よく変わる業務領域）ほど高い。変わらないなら強く結合しても実害は小さい距離と変動性

    4.バランスの式

    4.1 強度と距離は逆にする

    Khononov のモデルの核心は、次の関係です。

    距離が近い距離が遠い
    強度が高い✅ 高凝集（一緒に変わるものが近くにある）❌ 分散した複雑さ（一緒に変わるものが遠くに散らばる。最悪の状態）
    強度が低い⚠️ 局所的な複雑さ（関係の薄いものが同じ場所に詰め込まれている）✅ 疎結合（関係の薄いものが離れている）
    • 強く結びつくものは近くに置く（高凝集）
    • 弱く結びつくものは離して置く（疎結合）
    • つまり、高凝集と疎結合は、同じ原則の表と裏 です

    分散モノリス

    「分散モノリス」（41章：モノリスとマイクロサービス）は、右上の 強度が高いのに距離が遠い 状態の典型例です。サービスに分けた（距離を遠くした）のに、互いの内部データや業務ルールを共有している（強度が高い）ために、毎回一緒に変更・デプロイする必要が生まれます。

    4.2 変動性で緩和する

    ただし、変わらないなら、アンバランスでも実害はない という例外があります。これを式で表すと次のようになります。

    BALANCE = (STRENGTH ⊕ DISTANCE) ∨ ¬VOLATILITY

    バランスが取れている ＝（強度 XOR 距離）または（変動性が低い）

    • XOR（排他的論理和）：強度と距離の どちらか一方だけが高い とき真。両方高い・両方低いときは偽
    • OR NOT 変動性：変動性が低ければ、強度と距離がアンバランスでも許容できる

    4.3 具体例で判断する

    ケース強度距離変動性判断
    注文モジュール内の Order と OrderLine高（モデル・機能）近（同じモジュール）高✅ 高凝集
    注文サービスが配送サービスの DB を直接読む最強（侵入的）遠（別サービス）高❌ 最優先で直す
    注文サービスが配送サービスの公開 API を呼ぶ低（契約）遠高✅ 疎結合
    utils/ に日付処理と決済処理と画像変換が同居低近中⚠️ 局所的な複雑さ。分けた方が理解しやすい
    全サービスが古い社内の住所マスタ DB を直接読む最強（侵入的）遠低（10年変わっていない）✅ 変動性が低いので当面は許容。変わる予定が出たら見直す

    4.4 式を分解して読む

    この式は、次のような段階を踏んで組み立てられています（第3章・第10章）。

    大域的な複雑さ  = STRENGTH AND DISTANCE          … 強く結びつくものが遠くに散らばる
局所的な複雑さ  = NOT STRENGTH AND NOT DISTANCE  … 関係の薄いものが近くに詰め込まれる
複雑さ          = 局所的な複雑さ OR 大域的な複雑さ
モジュール性    = NOT 複雑さ = STRENGTH XOR DISTANCE
バランス        = モジュール性 OR NOT VOLATILITY

    バランス ＝ モジュール的である、または変わらない と読めます。

    4.5 数値スケールで考える（第10章「数値スケールでの結合の均衡化」）

    真偽（高い／低い）だけでは粗すぎる場合、各次元を 1〜10 の数値 で表して比べます。以下は二次資料（Software Architecture Guild）による目安で、値の付け方そのものより、同じ物差しで一貫して比べること が大事です。

    値統合強度距離変動性
    1〜2契約結合同じクラス・オブジェクト安定したレガシー
    3〜5モデル結合同じモジュール・サービス支援・汎用サブドメイン
    7〜9機能結合共有ライブラリ・複数サービスコア（よく変わる）
    10侵入結合別製品・別ベンダー・別組織—
     
    MODULARITY  = |STRENGTH − DISTANCE| + 1
BALANCE     = max(|STRENGTH − DISTANCE|, 10 − VOLATILITY) + 1
    • 強度と距離の 差が大きいほど モジュール的
    • バランスが低い（＝モジュール的でなく、しかも変動性が高い）結合ほど、繰り返し痛みを生む場所

    たとえば、注文サービスが配送サービスの DB を直接読む（強度 10・距離 8・変動性 8）なら、max(|10 − 8|, 10 − 8) + 1 = 3 と低く、直すべき場所だと分かります。同じ連携を公開 API 経由（強度 2）にすると max(6, 2) + 1 = 7 に上がります。

    4.6 痛み（保守コスト）の目安

    保守コスト（痛み） ≈ STRENGTH × DISTANCE × VOLATILITY
    • 掛け算なので、どれか1つが 1 に近ければ全体が小さくなる。3つすべてが高い所が最優先（→ 5.1）
    • 裏返すと、痛みを減らすには つまみを1つ回せばよい こともある（強度・距離・変動性のどれか）
    • ※ 精密な計測式ではなく、考えるための メンタルモデル です

    5.実務での使い方

    5.1 改善の優先順位を決める

    すべての結合を一度に直すことはできません。「強度が高い × 距離が遠い × 変動性が高い」 の組み合わせから順に直します。

    優先度状態対策の方向
    1強度高 × 距離遠 × 変動性高強度を下げる（契約を導入・腐敗防止層）か、距離を縮める（同じモジュール・サービスに統合）
    2強度高 × 距離遠 × 変動性低監視する。変動性が上がりそうなら優先度を上げる
    3強度低 × 距離近分けると理解しやすくなる。余裕があれば分割

    5.2 「強度を下げる」か「距離を縮める」か

    アンバランスを直す方法は2つあります。

    強度を下げる

    相手の内部を直接使うのをやめ、公開 API・DTO・イベントを経由する（侵入的・モデル結合 → 契約結合）。

    距離を縮める

    そもそも一緒に変わるものなら、同じモジュール・同じサービスにまとめる。

    マイクロサービスの議論では「強度を下げる」ばかりが語られがちですが、サービスを統合して距離を縮める のも正当な選択です。41章：アーキテクチャ量子と論理コンポーネント でいう「統合要因」がこれにあたります。

    5.3 レビューでの問い

    • この依存は、相手の 公開された契約 に対するものか、内部の詳細 に対するものか？
    • 同じ業務ルールが、別の場所にも書かれていない か？
    • この2つが一緒に変わる頻度は？ それに対して、距離は適切 か？
    • この部分は コアサブドメイン（よく変わる）か？

    6.よくある誤解

    誤解1：「結合はゼロにすべき」

    誤りです。 結合は部品が協力するために必要です。目標はゼロではなく バランス です。

    誤解2：「疎結合にするには、とにかく分ければよい」

    誤りです。 強く結びつくものを分けると（距離を遠くすると）、分散した複雑さ という最悪の状態になります。分ける前に、強度を下げられるかを考えます。

    誤解3：「インターフェースを挟めば結合は弱くなる」

    半分だけ正しいです。 インターフェースを挟んでも、そこに 相手のドメインモデルがそのまま現れている ならモデル結合のままです。また、同じ業務ルールを両側で知っている なら機能的結合のままです（統合強度）。

    7.まとめ

    • 結合は なくすものではなく、バランスを取るもの
    • 3つの次元
      • 統合強度：共有する知識の量。強い順に 侵入的 → 機能的 → モデル → 契約
        • 機能結合の度合いは弱い順に 順序 → トランザクション → 対称。対称結合（同じルールの重複）が最も見えにくく強い
        • 契約結合は、ファサード・OHS/PL・ACL・DTO で作る
      • 距離：一緒に変更するコスト（コードの位置＋組織の距離）
      • 変動性：変更の頻度。コアサブドメインほど高い
    • 強度と距離は逆にする：強いものは近くに（高凝集）、弱いものは遠くに（疎結合）
    • BALANCE ＝（STRENGTH XOR DISTANCE）OR NOT VOLATILITY
    • 「強度高 × 距離遠 × 変動性高」から優先的に直す。直し方は 強度を下げる か 距離を縮める か
    • クネビンの視点：複雑さは 部品同士のつながり方（制約） から生まれる。縛りすぎるともろく、縛りゼロでは成り立たない（結合と複雑性）
    • 相互作用の視点：設計のまずい結合は 見えない経路の相互作用 を生む。分割は複雑さを 別の階層に移す だけのこともある（結合と複雑性）
    • 再均衡化：戦略的な変更は強度・距離・変動性を変える。痛む所で つまみを1つ回して 再評価する（結合の再均衡化と実践）
    • フラクタル：複雑さは超線形に増え、認知容量は一定。抽象化の階層を足し、どの階層でも同じルールを当てはめる ことで成長を続けられる（結合の再均衡化と実践）

    次は、3つの次元の詳細として 統合強度 と 距離と変動性 に進みます。結合の考え方を使って実際にモジュールを切る手順は モジュール分割の基本プロセス、結合の種類を細かく見るなら 41章：コナーセンス を参照してください。
