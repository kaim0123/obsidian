    80 ケーススタディ

    ケーススタディ — 小規模 Web アプリと業務システムをモジュールに分ける

    これまで学んだことを、2 つの題材で通して使ってみます。前半は「ブログ + コメント」の小規模 Web アプリで、要件の整理からモジュール候補の洗い出し、依存関係、インターフェース定義、実装と振り返りまでを手順どおりに体験します。後半は「受注・在庫・請求」を含む業務システムで、複雑な業務ルール・複数チームでの分担・外部システム連携と、よくある設計ミスの直し方を扱います。

    もとにしたノート：80_ケーススタディ/01_ケーススタディ_小規模Webアプリ / 02_ケーススタディ_業務システム

    ひとことで言うと

    小規模でも article / comment / auth / web のように分け、依存は一方向・ID で参照・公開 API を先に決めます。規模が大きくなったら、業務ルールはドメインモジュールごとの domain 層へ、チーム境界とモジュール境界をそろえ、外部連携はポート/アダプタ + ACL で閉じ込めます。

    1.このページで扱うこと

    • ケース 1：小規模 Web アプリ（ブログ + コメント）：要件の整理 → モジュール候補 → 依存関係 → インターフェース → 実装と振り返り
    • ケース 2：業務システム（受注・在庫・請求）：複雑な業務ルールの分割、複数チームでの分担、外部システム連携の境界、よくある設計ミスと修正

    分割の手順そのものは モジュール分割の基本プロセス、DDD を使ったより大きな題材は 42章：ケーススタディ も参照してください。

    2.ケース 1：小規模 Web アプリ

    ブログ + コメント の小規模 Web アプリを題材に、モジュール分割から実装までを 手順どおり 体験します。

    2.1 要件の整理

    機能説明
    記事一覧・詳細公開済み記事の表示
    記事作成・編集認証ユーザーのみ
    コメント投稿記事に対するコメント
    認証ログイン / ログアウト

    アクター（システムを使う人の役割）は次の 2 つです。

    • 訪問者（閲覧・コメント）
    • 著者（記事 CRUD ＝ 作成・参照・更新・削除）

    非機能要件：小規模（同時ユーザー数百）、単一 DB、モノリスデプロイ（1 つのアプリとしてまとめて配置）。

    2.2 モジュール候補の洗い出し

    名詞・責務から候補を出します。

    モジュール責務（1 文）
    article記事の作成・公開・表示
    comment記事へのコメント管理
    authユーザー認証・セッション
    webHTTP ルーティング・レスポンス

    想定する依存は次のとおりです。

      依存（想定）
  web → article, comment, auth
  comment → article（記事 ID 参照）
  article → auth（著者 ID 参照、インターフェース経由）

    2.3 依存関係の設計

    ルール適用
    domain は infra 非依存article/domain に ORM なし
    循環禁止comment → article のみ（逆なし）
    auth の詳細を漏らさないCurrentUser インターフェース

    ORM は、DB のテーブルとプログラムのオブジェクトを対応づけるライブラリです。domain 層に ORM を持ち込まないことで、記事のルールを DB なしでテストできます（→ テストしやすいモジュール設計）。

    2.4 インターフェース定義

    実装より先に、各モジュールの公開 API を決めます。

    // article モジュール公開 API
interface ArticleService {
  listPublished(): Promise<ArticleSummary[]>;
  getById(id: ArticleId): Promise<Article | null>;
  create(cmd: CreateArticleCommand, author: UserId): Promise<ArticleId>;
}

// comment モジュール公開 API
interface CommentService {
  listByArticle(articleId: ArticleId): Promise<Comment[]>;
  post(articleId: ArticleId, body: string, author: UserId): Promise<CommentId>;
}

    comment は記事そのものではなく ArticleId だけを受け取ります。公開 API の設計の考え方は モジュール間インターフェース を参照してください。

    2.5 実装と振り返り

    ディレクトリ構成の例です。モジュールごとに domain / application / infra の層を持ち、index.ts で公開 API をまとめます。

    src/
  article/  domain/ application/ infra/ index.ts
  comment/  domain/ application/ infra/ index.ts
  auth/     domain/ application/ infra/ index.ts
  web/      controllers/ middleware/

    振り返りチェック：

    • ☐ 各モジュールを 1 文で説明できるか
    • ☐ 記事公開ルール変更は article だけか
    • ☐ テスト：article domain は DB なしで実行できるか
    • ☐ common に逃げていないか

    振り返りには チェックリストとアンチパターン の総合チェックリストも使えます。

    3.ケース 2：業務システム

    受注・在庫・請求 を含む業務システムを題材に、複雑なルール・チーム分担・外部連携のモジュール設計を学びます。

    3.1 複雑な業務ルールの分割

    ドメイン主なルール
    受注注文確定、キャンセル、ステータス遷移
    在庫引当、解放、在庫不足
    請求請求書発行、税計算、入金消込

    引当 は注文のために在庫を確保すること、入金消込 は届いた入金をどの請求の支払いか突き合わせることです。業務ルールは「そのドメインのモジュール内」に置きます。

      order/domain/     … キャンセル条件
  inventory/domain/ … 引当ルール
  billing/domain/   … 税・請求タイミング

    共通の計算をどこに置くか

    税のような 共通の計算 が必要なら、shared-kernel（複数のモジュールで共有する小さな核）または billing が提供する 値オブジェクト（金額や税率のような、値そのものを表す小さな型）を検討します。巨大な common は避けます。

    3.2 複数チームでのモジュール分担

    チーム担当モジュール
    受注チームorder, catalog
    物流チームinventory, shipping
    経理チームbilling, payment

    Conway の法則：組織の構造 ≒ システムのモジュール構造。チームの分かれ方とモジュールの分かれ方は似てくるので、最初からそろえておくと並行開発しやすくなります（41章：コンウェイの法則とTeam Topologies）。

    運用内容
    CODEOWNERSモジュールごと
    公開 API レビュー他チーム影響のある変更
    コンテキストマップチーム間の統合方式を文書化

    コンテキストマップ は、DDD で境界づけられたコンテキスト同士の関係を描いた図です。モジュールの境界は 42章：戦略的設計 のコンテキスト境界と対応させます。

    3.3 外部システム連携の境界

    外部モジュール側
    決済 GWpayment/infra/StripeAdapter
    倉庫 WMSshipping/infra/WmsClient
    会計 ERPbilling/infra/ErpExporter

    決済 GW（決済ゲートウェイ）はカード決済などを代行する外部サービス、WMS は倉庫管理システム、ERP は会計などを扱う基幹システムです。

    • アンチコラプション層（ACL） で外部のモデルを内部モデルに変換
    • 外部 DTO（外部 API がやり取りするデータの形）を domain に持ち込まない

    ポートとアダプタの構成は ヘキサゴナルのモジュール構成 を参照してください。

    3.4 よくある設計ミスと修正

    ミス修正
    全モジュールが orders テーブルに直接 SQLOrderRepository のみ書き込み、他は Query API
    在庫引当を Order 内で直接 SQLinventory モジュールの reserve() を呼ぶ
    請求ロジックが order に散在billing に集約、OrderPlaced イベントで連携
    integration 巨大モジュール外部ごとに該当ドメインの infra へ
    ✕ Before：order が在庫 SQL を直接実行 
      Before: order が在庫 SQL を直接実行
    ◯ After：在庫モジュールの API を経由する 
      After:  inventory.reserve(orderId, lines) を API 経由

    データの共有とイベントでの連携は データの受け渡しと共有 で詳しく扱っています。

    4.よくある誤解

    誤解1：「小規模アプリならモジュールに分ける必要はない」

    小規模でも article / comment / auth / web と分けると見通しが良くなります。分け方の手間は小さく、記事公開ルールの変更が article だけで済むといった効果がすぐに得られます。

    誤解2：「税計算のような共通処理は common にまとめればよい」

    巨大な common は凝集度が低くなる典型です。shared-kernel や billing が提供する値オブジェクトとして、責任を持つ場所をはっきりさせます。

    誤解3：「外部連携は integration モジュール 1 つに集めると管理しやすい」

    すべての外部連携が 1 か所に集まると巨大なモジュールになります。外部ごとに、それを使うドメインの infra にアダプタを置きます。

    5.まとめ

    • 小規模でも article / comment / auth / web と分けると見通しが良い
    • 依存は一方向、ID 参照でモジュール間をつなぐ
    • 公開 API を先に定義 してから実装
    • 振り返りで チェックリスト を使う
    • 複雑な業務ルールは ドメインモジュールごと に domain 層へ
    • チーム境界 ≒ モジュール境界 で並行開発
    • 外部連携は ポート/アダプタ + ACL
    • 共有 DB・巨大 integration は アンチパターン一覧 の典型

    本教材を終えたら、44_クラス設計・デザインパターン でクラス単位の設計へ進んでください。
