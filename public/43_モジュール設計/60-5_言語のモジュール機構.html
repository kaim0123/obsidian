    言語のモジュール機構 — ESM・TypeScript・barrel ファイル

    設計で決めたモジュールの境界は、最終的に言語のモジュール機構で実現します。JavaScript / TypeScript を例に、ESM と CommonJS の違い、moduleResolution の選び方、パスエイリアスとサブパスインポート、barrel ファイルの利点と性能上の問題、そして言語機能で公開範囲をどう表すかを解説します。

    もとにしたノート：60_構成と実装/06_言語のモジュール機構_ESM・TypeScript・barrel

    ひとことで言うと

    新しいプロジェクトは ESM を使い、TypeScript は フロントエンドなら bundler、Node.js なら nodenext。barrel ファイル（index.ts）は モジュールの境界にだけ 置いて「公開 API の宣言」として使います。TypeScript には言語レベルの「モジュール内だけ公開」が無いので、exports・Lint・慣習を組み合わせて境界を守ります。

    1.このページで扱うこと

    ここまでのページでは、モジュールを 設計の単位 として考えてきました。しかし最終的には、その設計を 言語のモジュール機構（ファイル同士を読み込み合うための言語の仕組み）で実現する必要があります。

    このページでは、JavaScript / TypeScript を例に、次の内容を解説します。

    • ESM と CommonJS の違いと、今どちらを使うべきか
    • TypeScript の moduleResolution の選び方
    • パスエイリアス（paths）と サブパスインポート（#imports）
    • barrel ファイル（index.ts での再エクスポート）の利点と、性能上の問題
    • 言語機能で 公開範囲（カプセル化） をどう表すか

    2.モジュール機構が設計に関係する理由

    設計の考え方言語のモジュール機構での実現
    公開 API を絞る（モジュール間インターフェース）export するものを選ぶ、package.json の exports
    依存を明示する（依存関係の管理）import 文、package.json の dependencies
    循環を作らない（結合の3原則と循環依存）ESM の循環 import の挙動を理解する
    モジュールの境界ファイル・ディレクトリ・パッケージ

    言語の仕組みを理解していないと、設計上は分けたつもりでも、実際には境界が守られていない ことがよく起きます。

    3.ESM と CommonJS

    3.1 2つの方式

    ESM（ECMAScript Modules）CommonJS（CJS）
    構文import / exportrequire() / module.exports
    標準JavaScript の言語標準（ES2015〜）Node.js 独自の方式（2009〜）
    読み込み静的（実行前に依存関係が決まる）動的（実行時に require が呼ばれる）
    tree shakingできる（使われていない export を削除できる）難しい
    トップレベル await使える使えない
    ブラウザネイティブで動く動かない（バンドラーが必要）

    tree shaking は、木を揺すって枯れ葉を落とすように、使われていないコードを最終的な成果物から取り除く処理です。バンドラー は、たくさんのファイルを配布用にまとめるツール（Vite・webpack など）です。

    3.2 今どちらを使うべきか

    • 新しいプロジェクトは ESM が基本（package.json に "type": "module"）
    • Node.js も ESM を標準としてサポートし、主要なライブラリも ESM へ移行が進んでいる
    • CommonJS は既存資産との互換性のために残っている、と考えてよい

    3.3 ESM の「静的」であることの意味

    ESM の import は ファイルの先頭で、文字列リテラルで書く 必要があります。そのため、

    • 実行前に依存グラフ全体が分かる → ツールで依存を解析・検査できる（依存ルールの自動検査）
    • 使われていない export を削除できる（tree shaking）→ バンドルサイズが小さくなる

    設計の観点では、「依存が静的に分かる」ことが、モジュール境界をツールで守るための前提になっています。

    3.4 循環 import の挙動

    ESM では循環 import は エラーにならず動いてしまう ことがありますが、評価順によって値が undefined になる（TDZ エラーになる）ことがあります。TDZ（Temporal Dead Zone）とは、const や let の変数が宣言・初期化される前に触ると ReferenceError になる期間のことです。

    ✕ 循環 import の例 
    // a.ts
import { b } from "./b";
export const a = "A" + b;

// b.ts
import { a } from "./a";
export const b = "B" + a;   // a.ts の評価が終わっていないので ReferenceError になる場合がある

    「動くこともあるが、順序次第で壊れる」という厄介なバグになるので、循環は設計の段階でなくし、ツールで検出する のが鉄則です。

    4.TypeScript のモジュール解決

    4.1 moduleResolution の選び方

    TypeScript は、import に書いたパスから どのファイルを読むか を moduleResolution の設定で決めます。

    設定使う場面特徴
    bundlerVite・webpack・Next.js など、バンドラーを使うフロントエンド拡張子なしの import を許す。package.json の exports を解釈する
    nodenext（node16）Node.js で直接動かすバックエンド・ライブラリESM では .js 拡張子が必須（.ts ファイルでも import "./foo.js" と書く）。exports を解釈する
    node（node10）古い設定exports を解釈しない。新規プロジェクトでは使わない
     
    // フロントエンド（Vite / Next.js）
{ "compilerOptions": { "module": "esnext", "moduleResolution": "bundler" } }

// Node.js バックエンド
{ "compilerOptions": { "module": "nodenext", "moduleResolution": "nodenext" } }

    重要

    node（node10）では package.json の exports が無視されるため、npmパッケージとモノレポ で見た exports によるカプセル化が効きません。bundler か nodenext を使いましょう。

    4.2 verbatimModuleSyntax

    型だけを import するときは import type と書くことを強制する設定です。

    import type { User } from "./user";   // 型だけ。実行時には消える
import { createUser } from "./user";  // 値。実行時にも残る
    • 「型だけの依存」と「実行時の依存」が明確に区別される
    • 型だけの import は実行時の循環を生まないので、依存関係の分析にも役立つ

    5.パスエイリアスとサブパスインポート

    5.1 相対パス地獄

    import { Money } from "../../../../shared/kernel/money";
    • 読みにくい
    • ファイルを移動すると、import をすべて直す必要がある

    5.2 TypeScript の paths

    パスエイリアス とは、長いパスに短い別名を付ける仕組みです。

    // tsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/shared/*": ["src/shared/*"],
      "@/features/*": ["src/features/*"]
    }
  }
}
    import { Money } from "@/shared/kernel/money";

    注意点

    paths は TypeScript の型チェックのための設定 で、実行時のパス解決はしてくれません。

    • バンドラー（Vite・Next.js）を使うなら、バンドラー側にも同じエイリアスを設定する（多くは自動で読み込んでくれる）
    • Node.js で直接動かすなら、tsc-alias などで変換するか、次のサブパスインポートを使う

    5.3 Node.js のサブパスインポート（#imports）

    package.json の imports フィールドを使うと、Node.js 自体がエイリアスを解決 してくれます。

    // package.json
{
  "imports": {
    "#shared/*": "./src/shared/*.js",
    "#features/*": "./src/features/*.js"
  }
}
    import { Money } from "#shared/kernel/money";
    • # で始まるのがルール
    • Node.js・TypeScript（nodenext/bundler）・主要なバンドラーが対応している
    • パッケージの内部からしか使えない（外部からは見えない）ので、内部用のエイリアスとして安全

    5.4 エイリアスと境界

    エイリアスは便利ですが、どこからでも何でも import できる ようにしてしまう危険もあります。

    ✕ 他の機能の内部に手が届いてしまう 
    // エイリアスがあると、他の機能の内部にも簡単に手が届いてしまう
import { calculateDiscountInternal } from "@/features/orders/pricing/internal";

    エイリアスを使うなら、機能の公開 API（index.ts）以外への import を禁止するルール をあわせて設定します（→ 依存ルールの自動検査）。

    6.barrel ファイル

    6.1 barrel ファイルとは

    定義

    他のモジュールを再エクスポートするだけの index.ts。 barrel は「樽」のことで、中身をまとめて1つの入れ物に詰めるイメージです。

    // features/orders/index.ts（barrel ファイル）
export { placeOrder } from "./application/placeOrder";
export { cancelOrder } from "./application/cancelOrder";
export type { Order } from "./domain/order";
    // 使う側
import { placeOrder, cancelOrder } from "@/features/orders";

    6.2 利点：モジュールの公開 API になる

    • 使う側は 1つの入口 から import できる
    • 公開するものを選べる（index.ts に書かないものは「内部」とみなせる）
    • モジュールの中の構成を変えても、index.ts を直せば使う側に影響しない

    設計の観点では、barrel ファイルは「モジュールの公開 API」を表す という重要な役割を持ちます。

    6.3 問題：性能への悪影響

    一方で、barrel ファイルには 性能上の問題 があることが広く知られるようになりました。

    問題説明
    余計なモジュールの読み込みimport { placeOrder } from "./orders" と書いても、barrel が再エクスポートしている すべてのモジュールが読み込まれ、評価される ことがある
    tree shaking の失敗再エクスポート先のモジュールに副作用（トップレベルのコード）があると、バンドラーは削除できず、使っていないコードがバンドルに残る
    テストが遅くなるJest などは tree shaking をしないので、barrel 経由の import がテストごとに巨大な依存グラフを読み込む
    開発サーバー・型チェックが遅くなる依存グラフが膨らみ、HMR（保存した変更を画面に即反映する仕組み）や IDE の型チェックが遅くなる
    循環 import を生みやすいモジュール内部のファイルが自分の barrel を import すると、簡単に循環ができる

    Atlassian は、Jira のフロントエンドで barrel ファイルをなくしたことで、ビルドが 75% 速くなった と報告しています（TypeScript のハイライト速度も 30% 以上改善）。

    6.4 どう付き合うか

    方針内容
    モジュールの境界にだけ置くfeatures/orders/index.ts のように、機能の公開 API としてだけ使う。モジュール内部の各ディレクトリには置かない
    深い barrel を作らないbarrel が barrel を再エクスポートする、何階層もの構成は避ける
    export * を避ける何が公開されているか分からなくなる。明示的に名前を書く
    モジュール内部では直接 import同じモジュール内のファイル同士は、自分の barrel を経由せず直接 import する（循環防止）
    大きな共通ライブラリは分割@acme/ui 全体の barrel より、@acme/ui/button のようなサブパスエクスポートを使う（→ npmパッケージとモノレポ）
    フレームワークの最適化を使うNext.js の optimizePackageImports など、barrel を自動で展開する機能を活用する

    使い分け

    まとめると、barrel は「公開 API の宣言」としては有用、「import を短くするための便利機能」としては有害になりやすい、という使い分けです。

    7.言語機能で公開範囲を表す

    TypeScript / JavaScript には、Java の package-private のような 「同じモジュールの中だけ公開」 という仕組みがありません。そのため、次のような方法を組み合わせます。カプセル化の一般論は カプセル化と情報隠蔽 を参照してください。

    方法強さ内容
    package.json の exports強い（言語・ツールが強制）パッケージ単位で公開する入口を限定（→ npmパッケージとモノレポ）
    barrel ファイル（index.ts）弱い（慣習）公開するものを index.ts に書く。書かないものは内部扱い
    Lint ルール中（CI で強制）「他の機能の index.ts 以外への import を禁止」などをルール化（→ 依存ルールの自動検査）
    命名の慣習弱いinternal/ ディレクトリ、_ で始まるファイル名
    @internal JSDoc ＋ stripInternal中型定義ファイル（.d.ts）から内部 API を除外

    Lint はコードの書き方をルールで自動チェックするツール、CI は変更のたびに自動でテストや検査を走らせる仕組みです。

    他の言語では、より強い仕組みがあります。

    言語仕組み
    Javapackage-private、Java 9 以降の モジュールシステム（JPMS） の exports
    Kotlininternal（同じモジュール内だけ公開）
    C#internal（同じアセンブリ内だけ公開）
    Go小文字で始まる名前は非公開、internal/ ディレクトリは親パッケージからしか import できない
    Rustpub / pub(crate) / pub(super) で細かく制御

    8.よくある誤解

    誤解1：「paths を設定すれば実行時も動く」

    誤りです。 paths は型チェック用です。実行時の解決は、バンドラーの設定・tsc-alias・Node.js のサブパスインポートで別途行います。

    誤解2：「barrel ファイルは常に良い／常に悪い」

    どちらも誤りです。 モジュールの境界での公開 API としては有用、深い階層や export * での多用は性能と循環の問題を生みます。

    誤解3：「import がエラーにならなければ、境界は守られている」

    誤りです。 TypeScript / JavaScript は、ほとんどのファイルを自由に import できます。境界は exports・Lint ルール・ツール で意図的に守る必要があります。

    9.まとめ

    • 新しいプロジェクトは ESM。静的な import により、依存グラフをツールで解析・検査 できる
    • TypeScript の moduleResolution は、フロントエンドは bundler、Node.js は nodenext。古い node では exports が効かない
    • paths は型チェック用。実行時は別の解決が必要。Node.js の サブパスインポート（#imports） はランタイムも解決してくれる
    • barrel ファイル は公開 API の宣言として有用だが、性能（Atlassian でビルド 75% 高速化の例）と循環 の問題がある。モジュールの境界にだけ 置く
    • TypeScript には言語レベルの「モジュール内公開」がないので、exports・Lint・慣習 を組み合わせて境界を守る
