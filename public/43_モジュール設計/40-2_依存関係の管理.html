    40 つなぎ方

    依存関係の管理 — 向きを決め、輪を断ち、組み立てを1か所に

    モジュール間の依存の向きをどう決めるか、循環依存をどう解消するか、依存性逆転の原則（DIP）で何が「逆転」するのか。依存グラフの読み方、DIP のよくある失敗、DI と Composition Root による組み立て、そして DIP・DI をどこに適用するかまでを、TypeScript のコード例で解説します。

    もとにしたノート：40_つなぎ方/02_依存関係の管理

    ひとことで言うと

    依存は 内側（ドメイン）に向かう一方向 にします。DIP は 処理の流れはそのまま、import の向きだけを逆にする 技で、鍵はインターフェースを 使う側が持つ こと。new は Composition Root に集めます。

    1.このページで扱うこと

    モジュール間の 依存の向き を決め、循環依存 を避け、依存逆転 を実践します。結合度 の具体的な運用方法にあたるページです。

    • 依存とは何か、依存の方向の決め方
    • 循環依存の問題と解消法
    • 依存逆転の原則（DIP）と、何が「逆転」するのか
    • 依存グラフの読み方と改善
    • DI と Composition Root：誰が組み立てるか
    • どこに DIP・DI を適用するか

    2.依存とは何か

    依存 とは、モジュール A がモジュール B の 型・関数・データ を使うことです。

      order  ──depends on──→  payment
    │
    import { charge } from '../payment'
    依存の形例
    import / requireコード上の参照
    実行時注入DI コンテナ経由
    設定・環境同じ DB への接続

    考え方

    依存がある ＝ 変更が伝播する可能性がある、と考えます。

    3.依存の方向を決める

    依存は 一方向 に流れるように設計します。一般的なルールは次のとおりです。

    ルール意図
    内側（ドメイン）ほど安定変更の少ない核
    外側ほど詳細（DB, UI）差し替えやすい
    依存は内側に向かうドメインがフレームワークに依存しない

    このルールをアーキテクチャとして体系化したものが「依存性のルール」です（41章：依存性のルールとクリーンアーキテクチャ）。

    4.循環依存の問題と解消法

    循環依存 とは、A → B → A のように依存が輪になる状態です。

      order ──→ payment
    ↑          │
    └──────────┘   ← 循環！
    問題説明
    変更が相互に波及どちらを先に直すか決められない
    テスト・ビルド困難単体で切り離せない
    理解困難責務の境界が曖昧

    4.1 解消法

    1. 共通部分を第3モジュールに抽出
    2. インターフェースを Domain に置き、依存逆転（次節）
    3. イベント で非同期・一方向に（データの受け渡しと共有）

    パッケージ単位での断ち切り方（ADP・SDP・SAP）は 結合の3原則と循環依存 で扱います。

    5.依存逆転の原則（DIP）

    依存逆転の原則（DIP） とは、詳細（実装）が抽象（インターフェース）に依存するようにすることです。

      Before（ドメインが DB に依存）
  order/domain ──→ postgres/driver

  After（DIP）
  order/domain ──→ OrderRepository (interface)
                        ↑
              postgres/OrderRepositoryImpl
    要素役割
    抽象（ポート）ドメイン側が定義
    実装（アダプタ）インフラ側が実装
    注入アプリケーション層で組み立て

    DIP の一般論は 41章：依存性逆転の原則、SOLID の中での位置づけは 42章：SOLIDとオブジェクト指向 を参照してください。

    6.依存グラフの読み方と改善

    6.1 読み方

    依存グラフ は、モジュールを点、依存を矢印にした図です。

    • 矢印の多いモジュール ＝ 変更のハブ（注意）
    • 双方向の矢印 ＝ 循環の候補
    • ドメインから外への矢印 ＝ DIP 違反の候補
            web
         │
         ▼
    application ──→ domain
         │              ↑
         ▼              │
       infra ────────────┘  （infra が domain の IF を implement）

    6.2 改善

    • ツール：dependency-cruiser、madge、IDE の依存図
    • ルールを CI でチェック（例：domain は infra を import 禁止）。CI は変更のたびに自動で検査・テストを走らせる仕組みです
    • 改善は 循環と DIP 違反 から優先

    ルールの書き方と導入手順は 依存ルールの自動検査 を参照してください。

    7.DIP をもう一段深く

    7.1 何が「逆転」するのか

    「逆転」とは、処理の流れ と ソースコードの依存 の向きが逆になることです。

    • 業務ロジックが DB を呼ぶ、という 処理の流れは変わらない
    • しかし import の矢印は DB 側から業務側へ 向く

    依存の矢印は「矢印の先が変わると、矢印の元が壊れる」と読みます。DIP 後は DB を替えても業務ロジックは壊れません。

    7.2 DIP の核心は「インターフェースの所有者」

    インターフェースを作っただけでは DIP になりません。どのモジュールに置くか がすべてです。

    インターフェースの置き場所import の向きDIP か
    infra/OrderRepository.tsorder → infra✕（矢印はそのまま）
    order/domain/OrderRepository.tsinfra → order◯
    shared/interfaces/OrderRepository.tsorder → shared ← infra△（共通置き場が肥大しやすい）

    インターフェースの形は「DB が提供できるもの」ではなく、「業務ロジックが必要とするもの」で決めます（モジュール間インターフェース の所有権とポートの節）。

    7.3 よくある失敗

    失敗何が問題か直し方
    インターフェースを infra 側に置く矢印が逆転しない使う側（domain）に移す
    実装の機能をそのまま写したインターフェース技術の都合が業務に漏れる業務の言葉で、必要な操作だけにする
    インターフェースを作ったのに中で new結局、具体クラスに依存したままDI で外から渡す（8節）
    全クラスに IXxx / XxxImpl抽象が多すぎて追えない境界だけに絞る（9節）
    domain が ORM のエンティティ型を使う型経由で infra に依存しているdomain 独自の型を定義し、アダプタで変換する

    ORM は、DB のテーブルとプログラムのオブジェクトを対応づけるライブラリ（Prisma、TypeORM など）です。

    8.DI と Composition Root：誰が組み立てるか

    DIP で依存の向きを整えても、どこかで new PostgresOrderRepository() は必要です。それを 使う側の外 で行い、完成品を渡す技法が 依存性注入（DI） です。DI・IoC の一般論は 41章：DI・IoC・Composition Root を参照してください。

    8.1 コンストラクタ注入

    // order/application/PlaceOrderUseCase.ts
import type { OrderRepository } from '../domain/OrderRepository';
import type { PaymentPort } from '../domain/PaymentPort';

export class PlaceOrderUseCase {
  constructor(
    private readonly orders: OrderRepository,
    private readonly payment: PaymentPort,
  ) {}
}
    注入の方法内容評価
    コンストラクタ注入生成時に渡す◎ 必須の依存が明確、不変にできる
    メソッド注入呼び出しごとに引数で渡す○ 呼び出しごとに変わるもの向け
    セッター注入後から set で渡す△ 未設定のまま使われるリスク

    8.2 Composition Root はどこに置くか

    Composition Root とは、依存を組み立てる 唯一の場所 です。アプリの入口（main.ts など）の近くに置きます。

    src/
  order/          ← new しない。受け取るだけ
  payment/        ← new しない。受け取るだけ
  infra/          ← new しない。受け取るだけ
  main.ts         ← ここだけが全モジュールを知り、組み立てる
    // main.ts（Composition Root）
const pool = new Pool(config.db);
const orders = new PostgresOrderRepository(pool);
const payment = new StripePaymentAdapter(config.stripeKey);
const placeOrder = new PlaceOrderUseCase(orders, payment);

startServer({ placeOrder });

    main.ts は特別

    main.ts だけは 全モジュールに依存してよい 特別な場所です。逆に、他のモジュールが main.ts を import してはいけません。

    8.3 モジュールごとに組み立て関数を公開する

    モジュールが増えると main.ts が肥大します。各モジュールが 組み立て関数 を公開し、main.ts はそれをつなぐだけにすると見通しがよくなります。

    // order/index.ts（order モジュールの公開面）
export type { OrderRepository } from './domain/OrderRepository';
export type { PaymentPort } from './domain/PaymentPort';

export function createOrderModule(deps: {
  orders: OrderRepository;
  payment: PaymentPort;
}) {
  return {
    placeOrder: new PlaceOrderUseCase(deps.orders, deps.payment),
    cancelOrder: new CancelOrderUseCase(deps.orders, deps.payment),
  };
}
    // main.ts
const order = createOrderModule({
  orders: new PostgresOrderRepository(pool),
  payment: new StripePaymentAdapter(config.stripeKey),
});
    • モジュールが外に求めるもの（deps の型）が 関数の引数として明示 される
    • モジュール内部の配線（どのユースケースに何を渡すか）は内部に隠れる

    8.4 DI コンテナとサービスロケーター

    方式内容評価
    手動 DI上のように自分で new して渡す小〜中規模ならこれで十分
    DI コンテナ型やトークンから自動で組み立てる（NestJS, InversifyJS など）大規模・ライフタイム管理が必要なとき
    サービスロケーター使う側が container.get(X) で取りに行く✕ 依存が隠れる。アンチパターン

    DI コンテナも Composition Root の外で get するとサービスロケーターになります。詳しくは 41章：DI・IoC・Composition Root を参照してください。

    9.どこに DIP・DI を適用するか

    適用する

    • DB・外部 API・メール・ファイルなど I/O
    • 時刻・乱数など、テストで固定したいもの
    • 別チームのモジュールとの境界
    • 循環依存を断ち切りたい箇所

    適用しなくてよい

    • 純粋な計算、値オブジェクト
    • 同じモジュール内の密接なクラス同士
    • 実装が1つで、替わる見込みもテストの不便もないもの
    • 標準ライブラリ・安定した言語機能

    最初から全部に差し込み口を作る必要はありません。素直に書いて、辛くなった境界から引き出す のが現実的です。DI の入門と、疎結合・インターフェース・DIP・DI の関係は 疎結合・DIP・DIの整理 にまとめています。

    10.よくある誤解

    誤解1：「インターフェースを作れば DIP になる」

    DIP の核心はインターフェースの 置き場所 です。infra 側に置いたままなら import の矢印は逆転しません。使う側（domain）に置いて初めて逆転します。

    誤解2：「DIP で処理の流れも逆になる」

    業務ロジックが DB を呼ぶという処理の流れは変わりません。逆になるのはソースコードの依存（import）の向きだけです。

    誤解3：「DI コンテナを使えば DI ができている」

    使う側があちこちで container.get(X) を呼んでいれば、それはサービスロケーターで、依存が隠れるアンチパターンです。組み立ては Composition Root だけで行い、使う側はコンストラクタで受け取るだけにします。

    誤解4：「すべてのクラスにインターフェースを用意すべき」

    全クラスに IXxx / XxxImpl を作ると抽象が多すぎて追えなくなります。I/O や別チームとの境界など、必要な場所に絞って適用します。

    11.まとめ

    • 依存 ＝ 変更が伝播するつながり
    • 依存は 内側（ドメイン）に向かう一方向 が基本
    • 循環依存 は抽出・DIP・イベントで解消
    • 依存グラフ を可視化し、CI でルールを守る
    • DIP は 処理の流れはそのまま、import の向きだけを逆にする。鍵は インターフェースを使う側が所有 すること
    • DI は 生成を外に出す 技法。new は Composition Root に集める
    • 各モジュールは 組み立て関数 で必要な依存を明示すると見通しがよい
    • DIP・DI は I/O や境界 に絞って適用する
