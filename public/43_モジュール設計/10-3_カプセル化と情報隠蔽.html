    10 モジュールの基礎

    カプセル化と情報隠蔽 — モジュールの中身を隠し、入口だけを見せる

    モジュールの内部を隠し、必要な操作だけを公開する — これがカプセル化と情報隠蔽です。このページでは、クラス単位で語られることの多いこの考え方を、パッケージ・ディレクトリ単位のモジュールに当てはめます。何を公開し何を隠すか、隠すと何がうれしいか、詳細が漏れ出すとどうなるか、そしてディレクトリや言語機能でどう表現するかを解説します。

    もとにしたノート：10_モジュールの基礎/03_モジュールのカプセル化と情報隠蔽

    ひとことで言うと

    モジュールは 「外のモジュールが知る必要があるもの」だけを公開 API として見せ、DB の構造や内部ヘルパーなどは隠します。そうすれば、内部を作り替えても公開 API が同じである限り、他のモジュールは無傷で済みます。

    2.カプセル化の目的

    カプセル化 とは、モジュールの 内部実装を隠し、決めた 公開面（API） だけを外に見せることです。API（Application Programming Interface）は、外から呼び出してよい関数や型の一覧のことです。

    目的効果
    変更の自由内部を書き換えても、公開 API が同じなら外は無傷
    理解のしやすさ外から見る情報量が減る
    誤用の防止触ってはいけない内部にアクセスできない

    3.公開すべきもの・隠すべきもの

    公開する

    • ユースケース（利用者がしたいこと）を表す関数・クラス
    • ドメイン（業務領域）の型（必要な範囲）
    • エラー型・結果型
    • 設定の インターフェース

    隠す

    • DB スキーマ（テーブル構造）の詳細
    • 内部ヘルパー・ユーティリティ
    • フレームワーク固有の実装
    • 接続文字列・認証情報の具体

    ルール

    「外のモジュールが知る必要があるか？」で判断する。

    4.内部表現の変更を安全にする

    内部表現が変わっても、公開 API が安定していれば 他モジュールへの影響はない はずです。

    4.1 例：注文の永続化

    永続化 とは、データをファイルや DB に保存して、プログラムを止めても残るようにすることです。

    これが情報隠蔽の力です。内部表現の変更理由 をモジュール内に閉じ込めます。

    5.漏れ出す詳細（Leaky Abstraction）の危険性

    Leaky Abstraction（漏れ出す抽象化） とは、隠すはずの詳細が公開 API や型を通じて外に漏れる状態です。

    漏れの例問題
    ORM の Entity をそのまま公開DB 構造変更が全体に波及
    SQLException をそのまま throwDB 依存が呼び出し側に伝播
    内部用 DTO を export意図しない依存が生まれる

    ORM は DB のテーブルとプログラムのオブジェクトを対応づけるライブラリ、Entity はそのテーブル1行に対応するクラス、DTO（Data Transfer Object）はデータを運ぶためだけの入れ物のクラスです。

    ✕ 漏れている（悪い例） 
    export class OrderEntity {  // DB カラムと 1:1
  dbRow: RawDbRow;
}
    ◯ 隠蔽できている（良い例） 
    export class Order {  // ドメインの概念だけ
  readonly id: OrderId;
  cancel(): void;
}

    どんな知識が漏れると困るのか、漏れの典型的な原因は何かは、次のページ 深いモジュールと浅いモジュール の「情報漏洩」でさらに掘り下げます。

    6.カプセル化の実践例

    6.1 ディレクトリで表現

    order/
  index.ts          ← 公開 API のみ re-export
  domain/           ← 内部（export しない）
  infra/            ← 内部
  application/      ← ユースケース（公開する場合あり）

    re-export は、他のファイルで定義したものを、この入口ファイルからまとめて公開し直すことです。外のモジュールは order/index.ts だけを import すればよく、domain/ や infra/ の中は知らずに済みます。

    6.2 言語機能

    言語手段
    Javapublic / package-private
    TypeScriptexport の有無、barrel file
    Python_ プレフィックス、__all__
    Go小文字 = パッケージ外非公開

    barrel file は、上の index.ts のように公開するものをまとめて re-export するファイルのことです（詳しくは 言語のモジュール機構）。

    package.json の "exports"（パッケージの外から import できるパスを限定する設定）や、モジュール境界 linter（依存方向チェック）も有効です。後者は 依存ルールの自動検査 で扱います。

    7.よくある誤解

    誤解1：「カプセル化はクラスの private の話だけ」

    カプセル化はクラスだけでなく、パッケージ・ディレクトリ単位のモジュールにも当てはまります。index.ts で公開するものを絞る、"exports" で外から触れるパスを限定する、といった形で表現します。

    誤解2：「便利そうな型や関数は全部 export しておけばよい」

    公開したものには外から依存されます。内部用 DTO や ORM の Entity を export すると、意図しない依存が生まれ、内部を変えにくくなります。「外のモジュールが知る必要があるか？」で絞ります。

    誤解3：「型で隠していれば漏れていない」

    SQLException のような例外をそのまま投げると、型としては見えなくても DB への依存が呼び出し側に伝わります。例外も公開面の一部として扱います。

    8.まとめ

    • カプセル化 = 内部を隠し、公開 API だけを見せる
    • 公開は「外が知る必要があるもの」だけに絞る
    • 内部表現の変更をモジュール内に閉じ込められる
    • Leaky Abstraction — 内部詳細の漏れ — に注意する
