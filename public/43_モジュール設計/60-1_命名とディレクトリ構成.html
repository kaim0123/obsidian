    命名とディレクトリ構成 — 構造そのものを地図にする

    名前とフォルダ構造は、コードを開く前に設計意図を伝える手段です。責務と境界を表す名前の付け方、ディレクトリとモジュール境界の対応、barrel や package.json の exports による公開範囲の制限、チームでの命名規則の統一、そして構成が伝える設計意図の良いサイン・悪いサインを解説します。

    もとにしたノート：60_構成と実装/01_命名・ディレクトリ・パッケージ構成

    ひとことで言うと

    名前は責務の説明、ディレクトリはモジュール境界の物理的な表現 です。名前をユビキタス言語にそろえ、公開範囲をツールで制限し、命名規約をチームで統一すると、ディレクトリ一覧だけで地図になる 状態に近づきます。

    1.このページで扱うこと

    このページでは、名前とフォルダ構造 が設計意図を伝える方法を学びます。目指すのは、コードを開く前に ディレクトリ一覧だけで地図 になる状態です。

    • 名前が設計を表す：良い名前・悪い名前
    • ディレクトリ構造とモジュール境界
    • パッケージの公開範囲 を制限する手段
    • 命名規則とチームでの統一
    • 構成が伝える設計意図 と、良いサイン・悪いサイン

    2.名前が設計を表す

    良い名前は 責務と境界 を説明します。

    良い名前悪い名前
    order, paymentcore, base
    PlaceOrderUseCaseOrderManager
    OrderRepositoryOrderDAO（層が混在）

    core や base は「何でも入れられる」名前なので、責務が読み取れません。OrderManager の「Manager」も何を管理するのかが曖昧で、何でも抱え込みがちです。PlaceOrderUseCase（注文を確定するユースケース）なら、名前だけで役割が分かります。

    名前のチェック

    「このモジュールは何をする？」→ 名前だけで答えられるか。

    名前は ドメインに基づく設計 のユビキタス言語（業務の専門家と開発者が共通で使う言葉）と一致させます。

    3.ディレクトリ構造とモジュール境界

    1 ディレクトリ ＝ 1 モジュール（または明確なサブモジュール） が基本です。

    src/
  order/
    domain/
    application/
    infra/
    index.ts          ← 公開 API
  payment/
    domain/
    application/
    infra/
  shared-kernel/      ← 最小限の共有（注意して使う）

    トップレベルに業務の名前（order・payment）が並び、その中に層（domain・application・infra）が入る形です。トップに業務名を並べる考え方は Screaming Architecture、機能別とレイヤー別の比較は 機能別とレイヤー別 を参照してください。

    原則説明
    深すぎない3〜4 階層が目安
    技術名だけのトップcontrollers/ 単体は避け、ドメイン配下に
    対称性各ドメインモジュールが同じ構造

    4.パッケージの公開範囲

    言語・ツールで export 可能な範囲（外から使ってよい範囲）を制限します。

    手段例
    barrel fileorder/index.ts だけ export
    package.json exports"exports": { ".": "./dist/index.js" }
    Java module systemmodule-info.java
    アーキテクチャテストdomain が infra を import 禁止

    barrel file は、モジュールの公開するものだけを再 export してまとめる入口ファイル（多くは index.ts）です。

    ◯ 公開面だけを export する barrel 
    // order/index.ts — 公開面
export { PlaceOrderUseCase } from './application/place-order';
export type { OrderId } from './domain/order-id';
// domain/infra の内部は export しない

    exports の詳しい使い方は npmパッケージとモノレポ、barrel の注意点は 言語のモジュール機構、アーキテクチャテストは 依存ルールの自動検査 で扱います。公開面の設計そのものは モジュール間インターフェース を参照してください。

    5.命名規則とチームでの統一

    対象例（TypeScript）
    モジュール / ディレクトリkebab-case：order-management
    クラス / インターフェースPascalCase：OrderRepository
    関数 / メソッドcamelCase：placeOrder
    定数UPPER_SNAKE または camelCase（チームで統一）

    kebab-case は小文字をハイフンでつなぐ書き方、PascalCase は単語の頭をすべて大文字にする書き方、camelCase は先頭だけ小文字で始める書き方、UPPER_SNAKE は大文字をアンダースコアでつなぐ書き方です。

    • README または ADR（設計上の決定とその理由を残す短い文書。41章：意思決定とADR）に規約を 1 ページで文書化します
    • レビューで 命名と配置 も見ます（チームで設計を守る）

    6.構成が伝える設計意図

    新メンバーが 5 分で構造を把握 できるか、を基準にします。

    構成が伝えること
order/domain/order.ts     → 注文の核はここ
order/infra/postgres-*    → DB はインフラ
order/application/*       → ユースケースの入口

    良いサイン

    • ドメイン名で並ぶ
    • 各モジュールが対称
    • import パスが読める

    悪いサイン

    • util, helper, misc が巨大
    • 1 フォルダだけ構造が違う（理由なし）
    • ../../../ の連続

    7.よくある誤解

    誤解1：「名前は後からいくらでも直せるので気にしなくてよい」

    名前は責務と境界の説明そのものです。core や OrderManager のような曖昧な名前は「何でも入れてよい場所」になり、責務が膨らむ原因になります。最初からユビキタス言語に合わせた名前を付けます。

    誤解2：「ディレクトリ構成は見た目の整理にすぎない」

    ディレクトリはモジュール境界の物理的な表現です。1 ディレクトリ ＝ 1 モジュールにそろえ、公開範囲を barrel や exports、アーキテクチャテストで制限して初めて、境界として機能します。

    誤解3：「トップは controllers/・services/ のような技術名で分けるのが標準」

    技術名だけのトップは避け、ドメイン配下に置くのが基本です。トップにドメイン名が並ぶと、構成そのものが「何のシステムか」を伝える地図になります。

    8.まとめ

    • 名前 は責務の説明。ユビキタス言語に合わせる
    • ディレクトリ ＝ モジュール境界の物理表現
    • 公開範囲 を barrel / ツールで制限
    • 命名規約 をチームで統一し、構成自体が地図になる

    次は、レイヤードアーキテクチャをモジュール構成に落とし込む レイヤードのモジュール構成 に進みます。
