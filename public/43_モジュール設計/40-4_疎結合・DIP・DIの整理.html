    40 つなぎ方

    疎結合・インターフェース・DIP・DI の整理 — 4つの関係を1枚で

    「疎結合」「インターフェース」「依存性逆転の原則（DIP）」「依存性注入（DI）」は、いつもセットで語られるので混ざりやすい言葉です。このページでは4つの役割分担を1枚に整理し、同じコードを密結合から4段階で直しながら違いを確かめます。さらに、モジュール（ディレクトリ・パッケージ）単位での実現方法と、添付ファイルサービスを題材にした DI の具体例、そして「どこまでやるか」の目安までをまとめます。

    もとにしたノート：40_つなぎ方/04_疎結合・インターフェース・DIP・DIの整理、40_つなぎ方/【入門】依存性注入とは何か（動画メモ）

    ひとことで言うと

    疎結合 が目的、インターフェース が道具、DIP が依存の向きの原則、DI が実物の渡し方です。インターフェースを作るだけ、DI するだけでは依存の矢印は逆転せず、使う側（上位）がインターフェースを所有 して初めて DIP になります。そして DI は万能薬ではなく、変わりうる境界にだけ差し込み口を作る道具 です。

    1.このページで扱うこと

    4つの言葉は、それぞれ別の本や記事で別々に説明されることが多く、「結局どれがどれ？」となりがちです。このページでは4つの関係を整理し、モジュール単位でどう実現するかまでをまとめます。各概念の詳しい説明は、41章のページにリンクします。

    • 4つの概念の役割分担：目的・道具・原則・技法
    • 段階を追って見る：密結合のコードを4段階で直す
    • 「処理の流れ」と「依存の方向」は別物
    • モジュール単位での実現：インターフェースの置き場所、import ルール、モジュール間の DI
    • DI を具体例で見る：添付ファイルサービスを if 文地獄から組み直す（動画の要点）
    • どこまでやるか：やりすぎ注意と、差し込み口を作る3つのシグナル
    • 混同しやすいポイント

    2.4つの概念の役割分担

    概念役割一言でいうと詳細の本拠地
    疎結合目的部品同士が互いの中身をなるべく知らない状態結合度 / 41章：モジュール性と疎結合高凝集
    インターフェース手段（道具）「何ができるか」だけを決め、「どうやるか」を隠すモジュール間インターフェース / 41章：インターフェースと抽象化
    DIP（依存性逆転の原則）設計原則依存の矢印を、変わりにくい側（ビジネスロジック）に向ける依存関係の管理 / 41章：依存性逆転の原則
    DI（依存性注入）実装の技法使う部品を自分で new せず、外から渡してもらう41章：DI・IoC・Composition Root

    つながりで覚える

    疎結合 にしたい → インターフェース で中身を隠す → その置き場所と矢印の向きを決めるのが DIP → 実物を外から渡す仕組みが DI

    Composition Root（コンポジションルート） とは、アプリの部品を new して組み立てる場所を1か所（たいていは起動処理の main.ts）に集めたものです。

    3.段階を追って見る

    同じコードを、密結合から順に4段階で直していきます。注文を受け付ける OrderService が、注文を Postgres（データベース製品の1つ）に保存する例です。

    3.1 段階0：密結合（具体クラスを直接 new）

    // order/OrderService.ts
import { PostgresOrderRepository } from '../infra/PostgresOrderRepository';

export class OrderService {
  private repo = new PostgresOrderRepository(); // 具体クラスを直接生成

  async place(cmd: PlaceOrderCommand) {
    const order = Order.create(cmd);
    await this.repo.save(order);
  }
}
    • DB を替えると OrderService も直す必要がある
    • テストに本物の Postgres が必要
    • order モジュールが infra モジュールの 内部クラス名 まで知っている（結合度 の内容結合に近い）

    3.2 段階1：インターフェースを導入しただけ

    // infra/OrderRepository.ts   ← インターフェースを infra 側に置いてしまった
export interface OrderRepository { save(order: Order): Promise<void>; }
export class PostgresOrderRepository implements OrderRepository { /* ... */ }

// order/OrderService.ts
import { OrderRepository, PostgresOrderRepository } from '../infra/OrderRepository';

export class OrderService {
  private repo: OrderRepository = new PostgresOrderRepository(); // まだ new している
}

    型はインターフェースになりましたが、疎結合にはなっていません。

    • new が残っているので、結局 Postgres 実装に依存している
    • インターフェースが infra にあるので、order → infra の矢印は消えていない

    3.3 段階2：DI を導入（外から渡す）

    // order/OrderService.ts
export class OrderService {
  constructor(private readonly repo: OrderRepository) {} // 受け取るだけ
}

    new は消えました。テストではメモリ実装（データベースの代わりに、メモリ上の配列などに保存する簡易版）を渡せます。ただし インターフェースがまだ infra 側 にあるなら、order は infra を import し続けます。

    3.4 段階3：DIP を適用（インターフェースを上位側が所有）

    // order/domain/OrderRepository.ts   ← 上位（使う側）が定義
export interface OrderRepository {
  save(order: Order): Promise<void>;
  findById(id: OrderId): Promise<Order | null>;
}

// order/application/OrderService.ts
import type { OrderRepository } from '../domain/OrderRepository';
export class OrderService {
  constructor(private readonly repo: OrderRepository) {}
}

// infra/PostgresOrderRepository.ts  ← 下位が上位の契約を実装しに行く
import type { OrderRepository } from '../order/domain/OrderRepository';
export class PostgresOrderRepository implements OrderRepository { /* ... */ }

// main.ts（Composition Root）  ← new はここに集める
const repo = new PostgresOrderRepository(pool);
const service = new OrderService(repo);
      段階0〜2                         段階3（DIP 適用後）
  ────────                         ─────────────────
  order ──→ infra                  order ←── infra
                                     ▲
                                    main（組み立て）
    段階インターフェースDIDIP疎結合か
    0なしなしなし✕
    1あり（infra 所有）なしなし✕
    2あり（infra 所有）ありなし△（テストは楽になるが矢印はそのまま）
    3あり（order 所有）ありあり◯

    ポイント

    インターフェース・DI・DIP は 3つそろって初めて モジュール間の矢印が逆転します。

    4.「処理の流れ」と「依存の方向」は別物

    DIP の「逆転」がわかりにくいのは、2つの矢印を混同しやすいからです。

      処理の流れ（実行時の呼び出し）
    OrderService ───呼ぶ───▶ PostgresOrderRepository

  ソースコードの依存（import の向き）
    OrderService ──▶ «OrderRepository» ◀── PostgresOrderRepository
    • 処理の流れ は変わらない（業務ロジックが DB を呼ぶ）
    • ソースコードの依存 だけが、下位から上位へ逆向きになる

    依存の矢印は「どちらが変わったら、どちらが壊れるか」を表します。DIP 後は DB 側を変えても業務ロジックは壊れず、業務ロジック側の契約が変わったときだけ DB 側が追従します。変わりにくく重要な方 が主導権を持つ構造です。

    5.モジュール単位での実現

    モジュール設計の視点で、ディレクトリ・パッケージにどう落とすかをまとめます。

    5.1 インターフェースの置き場所

    src/
  order/                      ← 上位（業務）
    domain/
      Order.ts
      OrderRepository.ts      ← ポート（インターフェース）はここ
    application/
      PlaceOrderUseCase.ts
    index.ts                  ← 外部に公開する面
  infra/                      ← 下位（技術的詳細）
    postgres/
      PostgresOrderRepository.ts   ← order/domain を import して実装
  main.ts                     ← Composition Root

    ポート は「業務側が外の世界に求める機能」を表すインターフェース、アダプタ はそのポートを特定の技術（Postgres など）で実装したものです。

    ルール理由
    ポートは 使う側のモジュール に置く契約の形を業務の都合で決めるため
    アダプタは infra 側 に置く技術の詳細を外側に閉じ込めるため
    order/** は infra/** を import しない依存の矢印を内向きに保つため
    new は main.ts（または各モジュールの composition.ts）だけ組み立てを1か所に集めるため

    詳しい構成例は ヘキサゴナルのモジュール構成 を参照してください。

    5.2 import ルールで矢印を守る

    DIP は「気をつける」だけでは崩れます。import 制約を CI で検査 して守ります（依存ルールの自動検査）。CI（継続的インテグレーション）は、コードを共有リポジトリに入れるたびに自動でテストや検査を走らせる仕組みです。

    // .dependency-cruiser.js（イメージ）
{
  name: 'domain-must-not-depend-on-infra',
  from: { path: '^src/order/domain' },
  to:   { path: '^src/infra' },
  severity: 'error',
}

    5.3 モジュール間の DI

    モジュール A がモジュール B の機能を使う場合も、考え方は同じです。

    // order モジュールが「在庫を引き当てたい」
// order/domain/InventoryPort.ts   ← order が必要な形で定義
export interface InventoryPort {
  reserve(items: OrderItem[]): Promise<ReservationResult>;
}

// inventory モジュールの公開 API を、order のポートに合わせるアダプタ
// composition/InventoryAdapter.ts
import { inventoryApi } from '../inventory';          // inventory の index.ts だけを使う
import type { InventoryPort } from '../order/domain/InventoryPort';

export const inventoryAdapter: InventoryPort = {
  reserve: (items) => inventoryApi.reserve(items.map(toSku)),
};
    • order は inventory を一切 import しない
    • inventory 側の API が変わっても、直すのはアダプタだけ
    • テストでは InventoryPort の偽物を渡せる

    6.DI を具体例で見る — 添付ファイルサービス

    ここからは、動画「【入門】依存性注入とは何か」（直也テック）の要点を整理して紹介します。

    依存性注入（Dependency Injection）は名前ほど難しくありません。あるコードが別のコードを使いたいとき、内部で直接作らず外から渡してもらう——この「渡すこと」を「注入」と呼びます。仕組みはこれだけです。「要するに関数に引数を渡しているだけ」と言う人もいるほどで、形としては古くからある Strategy パターン（処理のやり方を部品として差し替えられるようにするデザインパターン）とほぼ同じです。「プログラミングの大半は Builder と Strategy の2つのパターンでできている」と言うシニアエンジニアもいるほど、身近な考え方です。

    6.1 題材：保存先が顧客ごとに違う

    舞台は同僚とやり取りするビジネスチャットアプリです。メッセージ本文はリアルタイム性が大事なチャットサービスへ送られ、画像やファイルなどの添付は専用の アタッチメントサービス にアップロードされます。受け取ったファイルは一時保存され、処理を経て最終的な保存先に送られます。

    デフォルトの保存先は Amazon の S3（クラウドのファイル保存サービス）です。大半の顧客は S3 で問題ありませんが、一部の企業はデータの永続保存を嫌がるため、顧客の会社によって保存先を切り替える必要があります。多くは SFTP サーバーの指定ですが、1社だけ WebDAV を要求してきました（どちらもファイルを転送・保存するための通信方式です）。

    6.2 if 文で拡張すると何が壊れるか

    まず思いつくのは、アップロード処理を if 文で拡張し、保存先の指定と接続情報を呼び出し側から引数で渡してもらう方法です。保存先ごとに必要な項目をユニオン型（「A または B または C」を表す型）で結びつけておけば、間違った組み合わせはコンパイラーが弾いてくれる、という意見もあり、それも有効な手です。ただ、分岐を足していくと次の問題が出てきます。

    1. 責任が肥大する：性質の違う AWS・SFTP・WebDAV のコードが1か所で絡み合い、分岐だらけで流れが追いにくくなる
    2. 呼び出し側に不親切：保存先ごとに必要な情報が違うので引数は任意（省略可能）だらけになり、どれを埋めるべきかはコメント頼み。ミスに気づくのは実行時
    3. 設定のバケツリレー：どの会社のファイルかを一番よく知っているのはリクエストの入口なのに、そこからゴールまで接続情報を引き回すことになる

    6.3 DI の導入

    1. ストレージを表す インターフェース を作る。持つのは upload と download だけ＝呼ぶ側がやりたいことだけを表す
    2. この差し込み口に合う実装クラスを3つ（S3・SFTP・WebDAV）作る。それぞれの接続設定はコンストラクタで受け取るので、任意引数だらけが消え、各クラスは必要な値だけを要求する。渡し忘れればその場でエラーになる
    3. 認証が終わって所属する会社が分かった瞬間に、使うべきストレージを作る。そしてリクエスト処理には 完成したストレージだけ を渡す。これが注入

    設定情報をバケツリレーする必要はもうありません。リクエスト処理はファイルの行き先を知らず、「upload を呼べば保存される」ことだけを知っています。この組み立てコードは、入力＝会社の設定、出力＝ストレージなので、丸ごと ファクトリー（オブジェクトの作り方を引き受ける部品）に切り出せます。イメージをコードで書くと、たとえば次のようになります（考え方を示すための簡略な例です）。

    // 呼ぶ側がやりたいことだけを表す差し込み口
interface Storage {
  upload(file: File): Promise<void>;
  download(id: string): Promise<File>;
}

class S3Storage implements Storage     { constructor(cfg: S3Config) {} /* ... */ }
class SftpStorage implements Storage   { constructor(cfg: SftpConfig) {} /* ... */ }
class WebDavStorage implements Storage { constructor(cfg: WebDavConfig) {} /* ... */ }

// 入力＝会社の設定、出力＝ストレージ
function createStorage(company: CompanySettings): Storage { /* 保存先に応じて new */ }

// リクエスト処理は行き先を知らない
async function handleUpload(file: File, storage: Storage) {
  await storage.upload(file);
}

    6.4 パイプライン：最終保存は最後の1歩

    実際のアップロードは、保存の前に次の4工程を通ります。どの工程も同じ考え方で注入できます。

    1. ウイルススキャン：既知のウイルスを弾く。本番では ThreatProtect、乗り換え先の Synergy は性能が高いが契約の都合で開発環境でしか使えない → 2つに共通のインターフェースを被せ、起動時 にどちらかを選んで注入する。処理側はスキャンするだけで、どちらが動いているかは知らない
    2. 画像縮小：最大幅 2500 ピクセルに縮めて帯域を節約。ライブラリ Sharp を ImageScaler というインターフェースで包み、縮小に対応したファイルかどうかを返すメソッドも一緒に持たせる
    3. プレビュー：チャットに表示する小さなサムネイルを作る。文書用・動画用・画像用の3実装を用意し、画像用はさっきの ImageScaler を使い回す（同じ部品を別の場所にもう一度注入するだけ）。どれを使うかは MIME タイプ（ファイルの種類を表す文字列）次第だが、それは処理側の悩みではないので、選ぶ責任ごとファクトリーにして注入 する
    4. 暗号化：S3 に置くファイルを事前に暗号化して漏えいに備える。実装は AES の1つだけだが、鍵はユーザーごとに KeyService から取る → KeyService を暗号化クラスに注入し、その暗号化を StorageFactory に注入。S3 宛てのリクエストが来ると、ファクトリーが暗号化入りのストレージを組み立てる

    リクエスト処理は相変わらず upload を呼ぶだけで、裏にこれだけの連携が隠れていることを知りません。注目したいのは、構成のすべてが1か所で決まっている ことです。そのおかげで変更が局所化されます。

    • Synergy との契約が通ったら、変更はたった2行
    • 新しいファイル形式のプレビュー対応は、実装を1つ足すだけ
    • ローカル環境にキーサーバーがなければ、固定キーを差し込むだけ

    注入のタイミングは2種類あります。どちらも原理は同じで、コードは必要な依存を宣言し、外側がそれを満たす だけです。

    • 多くの依存は 起動時 に決まる（ウイルススキャナーなど）
    • 一部は リクエストが来た瞬間 に選ばれる（会社ごとのストレージなど）

    6.5 実装が1つでもインターフェースを使う理由：テスト

    暗号化のように実装が1つしかないものにまで、わざわざインターフェースを使う意味はあるのでしょうか。大きな利点が テスト です。

    部品同士がすべてインターフェース越しにつながっていれば、接続点はすべて中身を差し替えられます。本物の代わりに 偽物（フェイク）やスタブ（決まった値を返すだけの代役）を注入すれば、一部分だけを隔離してテストできます。

    • 例：S3 ストレージクラスのテストでは、本物のクラウドの代わりにローカルで動く偽の S3 を使い、upload を呼ぶとファイルが1件アップロードされたことを検証する
    • ただし暗号化のせいで中身が壊れていないかまでは検証できない → 何もしない暗号化 を注入すれば、アップロード機能だけを完全に隔離して検証できる

    これには「本物の通信も暗号化も走らず、エラーも起きない。それはテストと呼べるのか」という批判もあります。反論の一例は「テストしているのはあくまで自分のコード。S3 がちゃんと動くことを確かめるのは Amazon の仕事」というものです。

    良いモック（偽物）の見分け方

    • 本番でもそのまま使えそうな偽物 なら価値がある（例：Postgres の代わりに SQLite）
    • 本番では絶対にありえない偽物なら、そのテストは捨ててよい、という考え方もある

    モックが本領を発揮する場面

    • うまくいく場合ではなく わざと失敗させたいとき。通信の切断もサービス停止も、好きなタイミングで再現できる（本物相手ではこれが一番難しい）
    • どこで切るかを自由に選べる：暗号化をテストしたければキーストアだけを偽物に、暗号化と AWS のコードをまとめて試したければ本物をつないで統合テスト

    テストのしやすさは、構造をこじつけた結果ではなく、良い設計の自然な作用です。もし プライベートメソッドのテストに悩み始めたら、それはその部分を分離して注入すべきだというコードからのシグナル、という話もあります。テストの観点は テストしやすいモジュール設計 も参照してください。

    7.どこまでやるか（やりすぎ注意）

    効果が大きい場所

    • DB・外部 API・ファイル・メール・時刻・乱数など、外部・変わりやすい・テストしにくい もの
    • 業務ロジックと技術的詳細の 境界
    • 別チームが持つモジュールとの 境界

    やりすぎになりやすい場所

    • 実装が1つしかなく、替わる見込みもテスト上の不便もないもの
    • 同じモジュール内のクラス同士（モジュール内部は密でもよい＝高凝集）
    • すべてのクラスに IFoo / FooImpl を作る

    7.1 現場の声：DI は万能ではない

    動画では、やりすぎたときの困りごととして次のような声が紹介されています。

    • 便利だからとあらゆるものを注入した結果、引数が6〜7個もある関数 だらけになり、手に負えなくなった（そして書いていて楽しくない）
    • 「定義へジャンプ」がいつもインターフェースで止まり、実装クラスを探すのに苦労する。これがつらくなり始めたらやりすぎのサイン、という人もいる（実装へ飛べるショートカットを持つエディタならそこまで困らない、という声もある）
    • より深刻なのは、初めてそのコードベースに入った人が、どの関数も少し処理しては依存に投げる連鎖を前に、読めば分かるコードが、動かさないと分からないコード に変わってしまうこと
    • デバッグでは、注入されたものにバグがあるのではなく 注入するものを間違えていた ケースが厄介。まず依存が間違っていると気づくのに時間がかかり、どこから来たのかを探すと、ファクトリーの奥にまた別の注入が隠れている

    現場の工夫

    インターフェース・その実装・どれを選ぶかのルール、この3つをなるべく同じ場所にまとめておきます。遠くからじわじわ引いてくる魔法ではなく、その場で読める設定にしておくだけで、追いかける負担はかなり軽くなります。

    そして一番多く聞かれる批判が「早すぎる抽象化は、早すぎる最適化よりたちが悪い」です。「変わるかもしれない」という理由だけで作られた差し込み口は、たいてい使われないまま複雑さだけを残します。間違った抽象化を選ぶくらいなら、コードが重複していた方がまだましで、重複は3回目に気づいてからまとめれば十分、という意見もあります。

    7.2 差し込み口を作る3つのシグナル

    1. 分岐が 3つ以上 に増えてきた
    2. テストのためにその依存を用意するのが明らかに面倒
    3. たまにしか使わないのに起動を重くしている部品がある

    どれにも当てはまらなければ、まだ作らなくてかまいません。そして一番大事な注意点は、最初の1行目から完璧に注入しようとしない ことです。動画の題材も、複雑になりすぎたコードを後から直す作業でした。まず素直に書いてみて、どこがつらいのかを理解してから、必要な場所だけを引き出します。どこまで疎結合にするかの判断軸は バランス結合 も参照してください。

    8.混同しやすいポイント

    よくある誤解実際
    DI と DIP は同じもの別物。DIP は 依存の向き の原則、DI は 渡し方 の技法。具体クラスを DI することもできる（その場合 DIP は満たさない）
    インターフェースを作れば DIPインターフェースを 下位側に置いたら逆転しない。置き場所と所有者が重要
    DI には DI コンテナが必要不要。コンストラクタ引数で渡すだけで DI
    IoC = DIIoC（制御の反転）はより広い概念。DI はその一種（41章：DI・IoC・Composition Root）
    疎結合なら結合はゼロにすべき結合は なくせない。強さ・距離・変動性のバランスで決める（バランス結合）

    DI コンテナ は、どのインターフェースにどの実装を渡すかを登録しておくと自動で組み立ててくれるライブラリです。便利ですが、DI そのものに必須ではありません。

    9.よくある誤解

    誤解1：「実装が1つしかないなら、インターフェースは無駄」

    替わる見込みがなく、テストでも困らないなら、確かに作らなくてかまいません。ただし DB や暗号化・外部サービスのように、テストで偽物に差し替えたい・わざと失敗させたい部品なら、実装が1つでもインターフェース越しにしておく価値があります。判断は「替わるかも」ではなく、7.2 の3つのシグナルで行います。

    誤解2：「最初から何でも注入しておくのが良い設計」

    何でも注入すると、引数だらけの関数や「動かさないと分からないコード」が生まれます。DI は変わりうる境界にだけ差し込み口を作る道具です。まず素直に書き、つらくなってから必要な場所だけ引き出します。

    誤解3：「偽物を注入したテストは、本物を試していないので意味がない」

    テストの対象は自分のコードです。偽物を使えば、通信の切断のように本物では再現しにくい失敗も好きなタイミングで起こせます。本物との組み合わせは、どこで切るかを選んで統合テストで確かめれば十分です。

    10.まとめ

    • 疎結合 が目的、インターフェース が道具、DIP が向きの原則、DI が渡し方
    • インターフェースを作るだけ、DI するだけでは矢印は逆転しない。上位側がインターフェースを所有 して初めて DIP になる
    • 処理の流れは変わらず、ソースコードの依存の向き だけが逆になる
    • モジュール単位では「ポートは使う側に置く」「new は Composition Root に集める」「import ルールを CI で検査する」
    • DI の正体は「依存は中で作らず外から渡す」「つながりはインターフェースに任せる」だけ。それで変更もテストもパズルのように自由になる
    • 抽象化は 境界とテストのため に絞り、早すぎる抽象化は避ける。差し込み口は3つのシグナルが出てから作る
