    90 付録

    参考図解 — モジュール設計でよく使う図を1ページで見渡す

    モジュール設計でよく使う 9 つの図のテンプレートを集めたページです。設計の階層、高凝集・低結合、レイヤード、ヘキサゴナル、良い依存グラフと悪い依存グラフ、モジュール間のデータの渡し方、イベント連携、ドメイン主軸のディレクトリを、それぞれ詳しく説明しているページへのリンクと一緒に並べています。復習や、設計の打ち合わせで図を見せたいときに使ってください。

    もとにしたノート：90_付録/付録D_参考図解

    ひとことで言うと

    モジュール設計の図は、ほぼ「箱（モジュール）」と「矢印（依存）」だけで描けます。良い図では矢印が一方向に流れ、循環や共有 DB への矢印がありません。図を描くこと自体が、境界と依存の向きを点検する作業になります。

    1.このページで扱うこと

    モジュール設計でよく使う図のテンプレートです。ホワイトボードやノートに転記して使えます。

    • 構造の図：設計の階層／高凝集・低結合／レイヤードアーキテクチャ／ヘキサゴナル（ポートとアダプタ）
    • 依存の図：依存グラフ（良い例）／依存グラフ（悪い例）
    • つなぎ方と置き場所：モジュール間データの渡し方／イベント連携／ドメイン主軸のディレクトリ

    使い方

    図はどれも考え方を思い出すための手がかりです。意味があいまいなときは、各図の上にあるリンク先のページを読み直してください。図の中の矢印は「依存する（使う）」向き、点線の矢印は「実装する」または「良くない依存」を表します。

    2.構造の図

    2.1 設計の階層

    大きな単位から細かい単位へ、設計の階層が並びます。この教材（モジュール設計）は、ソフトウェア設計とクラス設計の間で「パッケージ・レイヤーをどう分けるか」を扱います（→ モジュール設計の全体像、設計の階層と基本用語（42章））。

    クラス設計（44_クラス設計・デザインパターン）とメソッド設計（46_メソッド設計）は別の章で扱います。

    2.2 高凝集・低結合

    モジュールの中身は 1 つの目的にまとめ（高凝集）、モジュール同士はインターフェース（IF）という最小限の約束だけでつなぎます（低結合）（→ 凝集度、結合度）。

    2.3 レイヤードアーキテクチャ

    関心ごとに水平に層を分け、依存は上から下へ向けます（→ レイヤードのモジュール構成、層化・三層・レイヤード（41章））。

    伝統的なレイヤードとクリーンアーキテクチャの違い

    この図は伝統的なレイヤードの並びで、Domain が Infrastructure に依存します。DIP（依存逆転の原則）を使うと、Infrastructure が Domain の定めたインターフェースを実装する形にでき、Domain を「いちばん内側」にできます。次の図4（ヘキサゴナル）と見比べてください（→ 疎結合・DIP・DIの整理）。

    2.4 ヘキサゴナル（ポートとアダプタ）

    中心のコア（業務ロジック）は、外と話す口（ポート）だけを持ちます。HTTP などの入口のアダプタは Driving Port を通してコアを呼び、コアは Driven Port を通して外部を使います。DB のアダプタは Driven Port を実装します（→ ヘキサゴナルのモジュール構成、ヘキサゴナルアーキテクチャ（41章））。

    ノートの図は縦向き（上に HTTP Adapter、下に DB Adapter）ですが、ここでは横向きに並べています。

    3.依存の図

    3.1 依存グラフ（良い例）

    web が各モジュールを使い、各モジュールは自分の domain と infra を持ちます。domain は infra に依存せず、循環もありません（→ 依存関係の管理）。

    3.2 依存グラフ（悪い例）

    order と payment が互いに import し合い（循環）、さらに同じ orders テーブルに直接 SQL を書いています（共有 DB）。どちらかを変えると、もう一方も壊れます（→ 結合の3原則と循環依存、データの受け渡しと共有）。

    4.つなぎ方と置き場所

    4.1 モジュール間データの渡し方

    モジュールの間では、ID や必要最小限の DTO（モジュール間で渡すためのデータの入れ物）を渡します。内部の Entity や DB の行そのものを渡すと、内部の変更が相手に波及します（→ データの受け渡しと共有）。

    良い

    • OrderId
    • OrderSummaryDto

    悪い

    • OrderEntity（内部）
    • RawDbRow

    4.2 イベント連携

    order は「注文が確定した」というイベント（OrderPlacedEvent）を発行（publish）するだけで、誰が受け取るかを知りません。在庫や通知のモジュールがそれを受け取って、それぞれの処理を行います（→ データの受け渡しと共有、イベント駆動設計（42章））。

    4.3 ドメイン主軸のディレクトリ

    トップレベルをドメイン名（order・payment・catalog）で分け、それぞれの中に層を持たせます。フォルダを見るだけで、何のシステムかが分かります（→ 命名とディレクトリ構成、Screaming Architecture）。

    src/
  order/     domain/ application/ infra/
  payment/   domain/ application/ infra/
  catalog/   domain/ application/ infra/

    5.よくある誤解

    誤解1：「図3（レイヤード）と図4（ヘキサゴナル）は同じことを言っている」

    どちらも関心ごとに分ける点は同じですが、依存の向きが違います。伝統的なレイヤードでは Domain が Infrastructure に依存しますが、ヘキサゴナルでは DB のアダプタがコアの定めたポートを実装し、依存がすべてコアに向きます。

    誤解2：「依存グラフは一度描けば十分」

    依存はコードが変わるたびに変わります。図6のような循環や共有 DB は少しずつ入り込むので、定期的に描き直す（またはツールで自動生成する）ことが大切です（→ 依存ルールの自動検査）。

    6.まとめ

    • 設計の階層の中で、モジュール設計は「パッケージ・レイヤー」を扱う
    • 高凝集・低結合：中はまとめ、間はインターフェースで細くつなぐ
    • レイヤードは上から下へ、ヘキサゴナルはポートを通して依存をコアに向ける
    • 良い依存グラフは一方向で循環なし。悪い依存グラフには循環と共有 DB がある
    • モジュール間は ID・DTO・イベントでつなぎ、ディレクトリはドメインを主軸にする
