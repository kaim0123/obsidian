    70 品質と運用

    変更に強いモジュール設計 — 拡張点・後方互換・技術的負債

    仕様は変わり、技術も入れ替わります。このページでは、変更に耐えるモジュールを作るための考え方 — 開放閉鎖の原則（OCP）をモジュール単位で使うこと、拡張点の置き方、公開 API の後方互換、リファクタリングしやすい構造、技術的負債との付き合い方 — を解説します。

    もとにしたノート：70_品質と運用/02_変更に強いモジュール設計

    ひとことで言うと

    新しい機能は既存コードを書き換えずに「足す」形で入れられるようにし（OCP・拡張点）、公開 API を変えるときは呼び出し元を壊さない手順を踏みます。拡張点は変化が実際に起きた軸にだけ置き、テストと高凝集・低結合を土台に少しずつ改善します。

    1.このページで扱うこと

    仕様変更・技術変更 に耐えるモジュール設計を学びます。

    • 開放閉鎖の原則（OCP）をモジュールに当てはめる
    • 拡張点の設計：どこに・どれだけ置くか
    • 後方互換性：公開 API を変えるときの手法
    • リファクタリングしやすい構造と進める順序
    • 技術的負債との向き合い方

    変化に強い設計の一般論（YAGNI など）は 42章：変化に強い設計 も参照してください。

    2.開放閉鎖の原則（OCP）

    OCP（Open-Closed Principle、開放閉鎖の原則） = 拡張に対して開き、変更に対して閉じる。新しい機能は「足す」ことで実現し、すでに動いている部分は書き換えなくて済むようにする、という原則です。

    閉じる（変更不要）開く（拡張可能）
    既存モジュールのコアロジック新しい支払い方法の追加
    安定した公開 API新しいアダプタの追加
     
      悪い例: payment モジュールに if (stripe) ... else if (paypal) ...
  良い例: PaymentGateway IF + StripeAdapter, PayPalAdapter

    これは SOLID 原則の OCP（42章：SOLIDとオブジェクト指向）を、モジュール単位に適用したものです。

    3.拡張点の設計

    拡張点 = 新機能を 既存コードを書き換えず 足せる場所。

    拡張点例
    インターフェースNotificationSender
    プラグイン / レジストリ税率計算の Strategy
    イベント購読新リスナーを追加
    設定機能フラグ

    Strategy は「計算方法などを部品として差し替えられるようにする」デザインパターン、レジストリ は部品を登録しておく台帳、機能フラグ は設定で機能のオン・オフを切り替える仕組みです。

    interface TaxCalculator {
  calculate(amount: Money, region: Region): Money;
}
// 新地域 = 新クラスを追加するだけ

    拡張点の増やしすぎに注意

    拡張点を増やしすぎ るのも YAGNI（今必要ないものは作らない）違反です。変化が 実際に起きた 軸に置きます。

    4.後方互換性の考え方

    公開 API を変えるとき、既存の呼び出し元を壊さない 配慮が必要です。これを 後方互換性 といいます。

    手法説明
    追加のみ新関数・新フィールド（オプション）
    非推奨期間@deprecated → 次メジャーで削除
    バージョン分離/api/v1, /api/v2
    アダプタ旧 API を新実装でラップ

    @deprecated は「この API はいずれ削除する予定」と知らせる印です。メジャー はバージョン番号の最初の数字（互換性が壊れる変更を表す）のことです。公開 API の変更の詳しい進め方は モジュール間インターフェース（ノートの 9.5 節）と連動します。

    5.リファクタリングしやすい構造

    リファクタリング は、外から見た動きを変えずに内部の構造を改善することです。

    条件理由
    高凝集・低結合変更が局所化
    テストがある安全網
    依存が一方向切り離しやすい
    小さなコミット単位モジュールごとに漸進改善

    リファクタリングは次の順序で進めます。

    1. テストを足す（または characterization test）
    2. 内部を整理（外部 API は維持）
    3. 必要なら API を段階的に変更

    characterization test（仕様化テスト）とは、仕様が分からない既存コードについて「今こう動いている」ことをそのまま記録するテストです。これがあれば、整理の途中で動きが変わったことにすぐ気づけます。

    6.技術的負債との向き合い方

    技術的負債 = 設計を妥協した結果の将来コスト（一般論は 41章：技術的負債）。

    戦略説明
    可視化負債リスト、依存グラフ
    優先付け変更頻度 × 痛み
    絶えず小さくBoy Scout Rule — 触ったモジュールを少し良く
    境界を守る新コードは良い設計、旧コードは段階的に

    Boy Scout Rule（ボーイスカウトの規則）は「来たときよりも美しく」— 触ったところを少しだけきれいにして去る、という習慣です。完璧を待たず、新規・変更箇所から 適用します（→ モジュール設計の進化）。

    7.よくある誤解

    誤解1：「将来に備えて、あらゆる所に拡張点を用意しておくべき」

    使われない拡張点は複雑さを増やすだけで、YAGNI 違反です。変化が実際に起きた軸（例：支払い方法が 2 つ目に増えた）に置きます。

    誤解2：「公開 API はいつでも自由に変えてよい」

    呼び出し元が壊れます。追加のみ・非推奨期間・バージョン分離・アダプタといった手法で、段階的に移行します。

    誤解3：「技術的負債は、まとめて返済する時間を取ってから直す」

    まとまった時間はなかなか取れません。可視化して優先順位をつけ、Boy Scout Rule で触ったところから少しずつ良くします。

    8.まとめ

    • OCP — 拡張で足し、既存を書き換えない
    • 拡張点 は変化の実績がある軸に置く
    • 後方互換 で公開 API 変更の影響を抑える
    • テスト + 高凝集低結合 がリファクタリングの前提

    次は チームでモジュール設計を守る に進みます。
