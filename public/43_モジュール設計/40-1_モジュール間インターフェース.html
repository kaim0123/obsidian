    40 つなぎ方

    モジュール間インターフェース — 公開API・契約・ポートの設計

    モジュール同士はどうやって通信すればよいのでしょうか。内部を隠したうえで外に見せる「境界」を、契約（入出力と副作用）、最小限の公開面、命名、変更の影響範囲の観点から設計します。さらに「インターフェース」の2つの意味を区別し、ポートを誰が持つか、どう小さく保つか、TypeScript での実現のコツまでを解説します。

    もとにしたノート：40_つなぎ方/01_モジュール間インターフェースの設計

    ひとことで言うと

    インターフェースは 契約・境界・安定点 です。入出力と副作用を明確にし、公開面は最小限に。差し替え用のポートは 使う側が持ち、使う側の言葉で 小さく 定義します。

    1.このページで扱うこと

    モジュール同士が どうやって通信するか — 公開 API・契約・命名 — を設計します。カプセル化と情報隠蔽 で隠した内部に対して、外に見せる 境界 を具体化するページです。

    • インターフェースの役割（契約・境界・安定点）
    • 入力・出力・契約、最小限の公開面、命名
    • インターフェース変更の影響範囲と後方互換
    • 「インターフェース」の2つの意味（①公開 API と ②抽象型＝ポート）
    • ポートの所有権、小さなポート、TypeScript での実現のコツ

    2.インターフェースの役割

    モジュール間の インターフェース（モジュール同士の接合面）は、次の役割を持ちます。

    役割説明
    契約何を渡し、何が返るかを約束する
    境界内部実装と外部利用者を分離する
    安定点変更しにくい「接合面」になる

    3.入力・出力・契約（Contract）

    良いインターフェースは 入出力が明確 です。

    // 契約の例
interface PlaceOrderCommand {
  customerId: string;
  items: { productId: string; quantity: number }[];
}

interface PlaceOrderResult {
  orderId: string;
  totalAmount: number;
}

function placeOrder(cmd: PlaceOrderCommand): Promise<PlaceOrderResult>;
    要素設計ポイント
    入力必要最小限。バリデーション（入力値の検査）の責務をどちらが持つか決める
    出力成功・失敗の型を明示（例外 or Result 型。Result 型は成功と失敗のどちらかを値として返す型）
    副作用DB 更新・メール送信など、何が起きるか文書化

    4.最小限の公開面（Surface Area）

    公開面 とは、外に export する API の総量です。小さいほどよい です。

    原則理由
    必要な関数・型だけ export変更の影響範囲を限定
    内部型は export しないLeaky Abstraction（抽象化の漏れ：隠したはずの内部事情が外に見えてしまうこと）を防ぐ
    Facade で入口を1つにindex.ts からだけ公開（Facade は窓口役の部品）

    公開面が大きい

    • export 50 クラス
    • 変更が広く波及

    公開面が小さい

    • export 3 関数
    • 内部を自由にリファクタ可能

    公開面を小さく保ち、その裏に多くの機能を隠すモジュールを「深いモジュール」と呼びます（深いモジュールと浅いモジュール）。

    5.命名と可読性

    インターフェースの 名前 は、利用者の 意図 が読めるようにします。

    良い例悪い例
    OrderService.placeOrderOrderService.doProcess
    OrderRepository.findByIdOrderRepo.get
    OrderCancelledEventEventType3
    • ユビキタス言語（開発者と業務の専門家が共通して使う言葉）に合わせる（ドメインに基づく設計）
    • モジュール名をプレフィックスに含めると衝突を防げる

    6.インターフェース変更の影響範囲

    公開 API を変えると、依存するすべてのモジュール に影響します。

    変更の種類影響
    新関数の追加通常は安全（後方互換：既存の呼び出し側を壊さないこと）
    引数の追加デフォルト値やオーバーロードで互換維持
    引数・戻り値の変更破壊的変更 — 全呼び出し元を更新
    関数の削除破壊的 — 非推奨期間を設ける
     
      変更前: placeOrder(userId, items)
  変更後: placeOrder(userId, items, couponCode?)
              ↑
  オプション引数で後方互換を保つ

    バージョニング（API v1 / v2）や 非推奨（deprecated） マーキングも検討します。

    7.「インターフェース」の2つの意味

    設計の文脈では「インターフェース」が2つの意味で使われます。混ざりやすいので区別しておきます。

    意味何を指すか例目的
    ① 公開 APIモジュールが外に見せる入口の総体index.ts から export される関数・型内部を隠し、変更の影響を限定する
    ② 抽象型（ポート）実装を差し替えるための型interface OrderRepository実装を隠し、差し替え・テストを可能にする

    ① 公開 API

    [order モジュール]
 ├─ index.ts  ← ここだけ見せる
 ├─ domain/   （隠す）
 └─ infra/    （隠す）

    ② 抽象型（ポート）

    [order]  ──→ «OrderRepository»
                     ▲
                     │ implements
       [PostgresOrderRepository]

    ①は モジュールの外側 をどう見せるか、②は モジュールが外部に何を求めるか の話です。2〜6節は主に①を、以下の8〜9節は主に②を扱います。抽象化の一般論は 41章：インターフェースと抽象化、多態性との関係は 42章：多態とインターフェース を参照してください。

    8.インターフェースは誰が持つか（所有権）

    ②の抽象型は、どちらのモジュールに置くか で依存の向きが変わります。

    8.1 提供側が所有する（Provided Interface）

      payment/
    PaymentGateway.ts      ← interface をここに置く
    StripeGateway.ts
  order/
    OrderService.ts        ← payment を import する

  依存: order ──→ payment
    • 汎用ライブラリや、多数の利用者がいる共通基盤に向く
    • 契約の形は 提供側の都合 で決まる

    8.2 利用側が所有する（Required Interface / ポート）

      order/
    domain/PaymentPort.ts  ← order が必要とする形で定義
    OrderService.ts
  payment/
    StripePaymentAdapter.ts ← order の PaymentPort を実装する

  依存: order ←── payment
    • 業務ロジック（上位）と技術的詳細（下位）の境界に向く
    • 契約の形は 業務の都合 で決まる。これが 依存性逆転の原則（DIP） です（41章：依存性逆転の原則）
    判断基準提供側に置く利用側に置く
    守りたいのはどちらか提供側（共通基盤）利用側（業務ロジック）
    利用者の数多い少ない（主に1つ）
    変わりやすいのは利用側提供側（DB・外部サービス）
    代表例ロガー、HTTP クライアントのラッパリポジトリ、決済・通知のポート

    依存の向きの詳細は 依存関係の管理、ディレクトリでの表現は ヘキサゴナルのモジュール構成 を参照してください。

    9.ポートは小さく、利用者の言葉で

    利用側が所有するインターフェースは、利用者が本当に使う操作だけ に絞ります。これは ISP（インターフェース分離の原則：使わないメソッドへの依存を強いない。42章：SOLIDとオブジェクト指向）の考え方です。

    ✕ 悪い例：実装（S3）の機能をそのまま写した大きなインターフェース 
    interface StorageService {
  putObject(bucket: string, key: string, body: Buffer, acl: string): Promise<void>;
  getObject(bucket: string, key: string): Promise<Buffer>;
  listObjects(bucket: string, prefix: string): Promise<string[]>;
  setLifecycle(bucket: string, rule: LifecycleRule): Promise<void>;
  // ...
}
    ◯ 良い例：使う側がやりたいことだけ。技術用語（bucket, acl）が漏れていない 
    interface AttachmentStore {
  save(attachment: Attachment): Promise<AttachmentId>;
  load(id: AttachmentId): Promise<Attachment>;
}
    観点悪い例良い例
    名前技術の名前（Storage, S3）業務の名前（AttachmentStore）
    引数技術の概念（bucket, acl）業務の概念（Attachment）
    操作数実装ができること全部利用者が必要なものだけ
    差し替えS3 以外に替えにくいSFTP・メモリ実装に替えやすい

    注意

    技術の都合がインターフェースに漏れると、抽象化しても結合は弱まりません（深いモジュールと浅いモジュール の情報漏洩）。

    10.TypeScript での実現のコツ

    テクニック効果
    import type { X } を使う型だけの依存であることを明示し、実行時の依存を生まない
    構造的型付けを活かすimplements を書かなくても、形が合えば渡せる（アダプタを薄くできる）
    公開面は index.ts / package.json の exports で制御①の公開 API を物理的に制限できる（言語のモジュール機構）
    インターフェースの隣に偽物実装を置くInMemoryOrderRepository をテストで使い回せる

    構造的型付け とは、型の名前ではなく「形（持っているプロパティやメソッド）」が合っていれば同じ型として扱う TypeScript の仕組みです。

    // order/domain/Clock.ts
export interface Clock { now(): Date; }

// テストでは implements なしでも渡せる（構造的型付け）
const fixedClock = { now: () => new Date('2026-01-01T00:00:00Z') };
const service = new OrderService(repo, fixedClock);

    疎結合・インターフェース・DIP・DI の関係は 疎結合・DIP・DIの整理 にまとめています。

    11.よくある誤解

    誤解1：「interface を書けばモジュールの境界ができる」

    「インターフェース」には①公開 API と②抽象型（ポート）の2つの意味があります。境界を作るのは①（何を export するか）で、②の型を作っても内部を全部 export していれば境界は守られません。

    誤解2：「インターフェースは実装側に置くもの」

    共通基盤なら提供側でよいですが、業務ロジックと DB・外部サービスの境界では 利用側 に置きます。置き場所で依存の向きが変わり、利用側に置くことが DIP です。

    誤解3：「実装の機能を全部インターフェースに写せば差し替えやすい」

    逆です。S3 の bucket や acl のような技術の概念が漏れたインターフェースは、S3 以外に替えにくくなります。利用者が必要な操作だけを、業務の言葉で定義します。

    12.まとめ

    • インターフェース ＝ 契約・境界・安定点
    • 入出力・副作用を明確にし、最小限の公開面 にする
    • 命名 はユビキタス言語と利用者の意図を反映
    • 公開 API の変更は 影響範囲が広い — 後方互換を意識する
    • 「インターフェース」には ①公開 API と ②抽象型（ポート） の2つの意味がある
    • ポートを 利用側が所有 すると依存の向きが逆転する（DIP）
    • ポートは小さく、業務の言葉 で。技術の都合を漏らさない
