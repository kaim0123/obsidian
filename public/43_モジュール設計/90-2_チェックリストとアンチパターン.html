    90 付録

    チェックリストとアンチパターン — モジュール設計を点検し、典型的な失敗を避ける

    設計レビューやリファクタリングの前に使える、モジュール設計の総合チェックリストと、避けるべき典型的な失敗（アンチパターン）10 個の一覧です。チェックリストで「できているか」を確かめ、アンチパターン一覧で「やってしまっていないか」を確かめます。各項目から、詳しく説明しているページへ移動できます。

    もとにしたノート：90_付録/付録B_チェックリスト / 付録C_アンチパターン一覧

    ひとことで言うと

    チェックリストは良い設計の条件、アンチパターンは悪い設計の典型です。同じことを表と裏から見ています。見つけた問題は全部を一度に直さず、循環依存・共有 DB（結合度）→ common の肥大化（凝集度）→ レイヤー違反・抽象化の漏れ → 命名・ディレクトリの順に手を付けます。

    1.このページで扱うこと

    • モジュール設計チェックリスト（総合版）：分割・凝集度と結合度・境界とカプセル化・依存関係・インターフェース・テストと品質・チームと運用・変更シナリオの 8 分類
    • よくあるアンチパターン一覧：大泥団から巨大 integration モジュールまで 10 個と、その対策
    • 対策の優先順位

    アンチパターン は、よくある悪い設計のパターンのことです。設計レビューの進め方は モジュール設計レビュー を参照してください。

    2.モジュール設計チェックリスト（総合版）

    設計レビュー・リファクタ前に使えるチェックリストです。

    2.1 モジュール分割

    • ☐ 各モジュールを 1 文 で説明できる
    • ☐ モジュール名が ユビキタス言語（チームで共有する業務の用語）と一致している
    • ☐ util / common / misc に無関係な処理が溜まっていない
    • ☐ 分割しすぎ（1 変更で 5 モジュール以上）でない
    • ☐ 分割不足（1 モジュール 50 ファイル超）でない

    関連：モジュール分割の基本プロセス

    2.2 凝集度・結合度

    • ☐ モジュール内のファイルは 同じ変化の理由 を持つ
    • ☐ モジュール間は インターフェース 経由で通信
    • ☐ 循環依存 がない
    • ☐ 共有 DB テーブル への直接アクセスがない
    • ☐ 巨大 DTO の受け渡しを避け、必要最小限のデータ

    関連：凝集度、結合度

    2.3 境界・カプセル化

    • ☐ 公開 API は 最小限（barrel / exports で制限）
    • ☐ 内部型・ORM Entity を export していない
    • ☐ domain が infra / フレームワークに依存していない
    • ☐ Leaky Abstraction（内部詳細の漏れ）がない

    barrel は公開 API をまとめる index.ts のようなファイル、exports は package.json で外から読めるファイルを制限する設定です（→ 言語のモジュール機構、カプセル化と情報隠蔽）。

    2.4 依存関係

    • ☐ 依存の向きが 一方向（内側に向かう）
    • ☐ DIP — ドメインがポートを定義、infra が実装
    • ☐ 依存グラフを 定期的に確認 している
    • ☐ CI で依存ルールを 自動チェック している（可能なら）

    関連：依存関係の管理、依存ルールの自動検査

    2.5 インターフェース

    • ☐ 入出力・エラー・副作用が 明確
    • ☐ 公開 API 変更時に 後方互換 を考慮
    • ☐ 命名が 意図を伝える

    関連：モジュール間インターフェース、変更に強いモジュール設計

    2.6 テスト・品質

    • ☐ domain が DB なし で単体テスト可能
    • ☐ application が Fake ポート でテスト可能
    • ☐ 副作用が infra に局所化 されている
    • ☐ テストが書きにくい箇所に 設計問題 がないか確認

    関連：テストしやすいモジュール設計

    2.7 チーム・運用

    • ☐ モジュール設計ルールが 文書化 されている
    • ☐ コードレビューで 境界・依存 を見ている
    • ☐ 設計負債が 可視化 されている
    • ☐ 大きな境界変更前に 設計レビュー がある

    関連：チームでモジュール設計を守る

    2.8 変更シナリオ（What-If）

    「もしこれが変わったら、どのモジュールを触るか」を想像して、境界が妥当かを確かめます。

    シナリオ触るモジュールは妥当か
    決済 API の差し替えpayment のみ（+ 設定）
    注文キャンセルルール変更order のみ
    UI を REST から gRPC にweb/adapter のみ
    新ドメイン「クーポン」追加新モジュール or 既存のどちらか明確

    gRPC は、REST とは別の方式でサーバー同士が通信するための仕組みです。通信方式が変わっても業務のモジュールは触らずに済むのが理想です。

    3.よくあるアンチパターン一覧

    モジュール設計で避けるべき典型パターンです。

    アンチパターン症状対策
    1. 大泥団（Big Ball of Mud）境界がなく、すべてが相互依存ドメイン単位で段階的分割（モジュール設計の進化）
    2. 巨大 common / util モジュール無関係な処理が common に集まる機能的凝集で本来のモジュールへ移す（凝集度）
    3. 共有データベース複数モジュールが同一テーブルに直接 SQLRepository 経由、Query API、スキーマ分離（データの受け渡しと共有）
    4. 循環依存order ↔ payment の相互 import第 3 モジュール抽出、DIP、イベント（依存関係の管理）
    5. レイヤー違反Controller が SQL 直実行、Domain が ORM 依存レイヤー依存ルール + CI（レイヤードのモジュール構成）
    6. 漏れ出す抽象化（Leaky Abstraction）ORM Entity、SQLException がモジュール境界を越えるDTO / ドメイン型で変換、infra に閉じ込め（カプセル化と情報隠蔽）
    7. 神サービス / 神モジュール1 モジュールが全ユースケースを担当責務分割、変化の理由で分ける（モジュール分割の基本プロセス）
    8. 過剰分割（Premature Microservices）小規模なのにサービスが乱立、Distributed Monolithまずモノリス内モジュール化（マイクロサービスとモノリス）
    9. 技術名だけのトップ構造controllers/, services/, models/ だけでドメインが見えないドメイン主軸 + モジュール内レイヤー（技術的関心事による分割）
    10. 巨大 integration モジュールすべての外部連携が 1 モジュールに集中各ドメインの infra にアダプタを配置（ケーススタディ）

    いくつか補足します。大泥団 は、構造がなく何もかもが絡み合った泥の塊のようなシステムのことです。機能的凝集 は、1 つの目的のためだけの処理が集まった、最も望ましい凝集の種類です。Distributed Monolith（分散モノリス）は、サービスに分けたのに互いに強く依存していて、結局まとめてしか変更・デプロイできない状態を指します。

    4.対策の優先順位

    複数のアンチパターンが見つかったら、次の順に手を付けます。

    1. 循環依存・共有 DB の解消（結合度）
    2. common 肥大化の分解（凝集度）
    3. レイヤー違反・Leaky Abstraction
    4. 命名・ディレクトリの整理

    5.よくある誤解

    誤解1：「チェックリストを全部満たせば良い設計だ」

    チェックリストは見落としを防ぐ道具で、設計の判断そのものではありません。たとえば「分割しすぎでない」「分割不足でない」は互いに引っ張り合う項目で、どこでバランスを取るかはシステムごとに考える必要があります。

    誤解2：「アンチパターンを見つけたら、すぐ全部直すべき」

    一度に全部を直すと危険が大きくなります。対策の優先順位に沿って、影響の大きい結合度の問題から、触ったところを少しずつ直していきます（モジュール設計の進化）。

    6.まとめ

    • チェックリストは 分割・凝集と結合・境界・依存・インターフェース・テスト・チーム・変更シナリオ の 8 分類
    • 変更シナリオ（What-If）で、変更が 1 つのモジュールに収まるかを確かめる
    • アンチパターンは 大泥団・巨大 common・共有 DB・循環依存・レイヤー違反・Leaky Abstraction・神モジュール・過剰分割・技術名だけの構造・巨大 integration の 10 個
    • 対策は 結合度 → 凝集度 → レイヤー違反・抽象化の漏れ → 命名・ディレクトリ の順
