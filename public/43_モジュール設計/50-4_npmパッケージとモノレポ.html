    npmパッケージとモノレポ — パッケージ原則を実践する

    凝集・結合のパッケージ原則は、JavaScript / TypeScript のモノレポで最も直接的に実践できます。モノレポとポリレポの違い、pnpm workspaces による内部パッケージの作り方、package.json の exports による公開範囲の制御、パッケージの切り方、Turborepo・Nx によるビルドと境界の管理、バージョン管理の考え方までを解説します。

    もとにしたノート：50_パッケージ原則/04_npmパッケージとモノレポでの適用

    ひとことで言うと

    モノレポは 1つのリポジトリに入れただけではモジュール化されません。workspace:* による 依存の明示、exports による 公開範囲の限定、Nx などによる 境界ルールの強制 がそろって初めて、パッケージ原則どおりの構成になります。

    2.モノレポとは

    2.1 定義

    定義

    モノレポ：複数のプロジェクト・パッケージを、1つのリポジトリで管理する方式。反対に、パッケージごとに別々のリポジトリで管理する方式を ポリレポ といいます。

    モノレポポリレポ
    リポジトリ1つパッケージごとに別々
    パッケージ間の変更1つのコミット・PR で複数パッケージを同時に変更できる各リポジトリで順番にリリース・更新が必要
    依存のバージョン内部パッケージは常に最新を参照できる各リポジトリが別々のバージョンを参照する
    ツール・設定共通化しやすいリポジトリごとに重複しがち
    注意点規模が大きくなるとビルド時間・権限管理が課題。境界を守る仕組みが必要横断的な変更が大変

    2.2 モノレポの典型的な構成

    my-monorepo/
  pnpm-workspace.yaml
  package.json
  turbo.json                 （または nx.json）
  apps/                      ← デプロイされるアプリ
    web/                     （Next.js）
    api/                     （Node.js / NestJS）
    admin/
  packages/                  ← 内部パッケージ（ライブラリ）
    domain-orders/           ← 業務のパッケージ
    domain-customers/
    ui/                      ← 共通 UI 部品
    api-client/              ← API の型とクライアント
    config-eslint/           ← 共通設定
    config-typescript/
    • apps/ は 不安定（頻繁に変わる・誰からも依存されない）
    • packages/ は 安定（apps から依存される）
    • 依存は apps → packages の一方向（SDP：安定した方へ依存する原則。結合の3原則）

    3.pnpm workspaces で内部パッケージを作る

    pnpm は npm と同じ役割のパッケージマネージャーで、workspaces は1つのリポジトリの中に複数のパッケージを置いて互いに参照できるようにする機能です。

    3.1 ワークスペースの宣言

    # pnpm-workspace.yaml
packages:
  - "apps/*"
  - "packages/*"

    3.2 内部パッケージに依存する

    // apps/web/package.json
{
  "name": "@acme/web",
  "dependencies": {
    "@acme/domain-orders": "workspace:*",
    "@acme/ui": "workspace:*"
  }
}
    • workspace:* は「このリポジトリ内のパッケージを使う」という指定です
    • import は通常の npm パッケージと同じ書き方になります：import { placeOrder } from "@acme/domain-orders"
    • 相対パスで他のパッケージの中身を直接 import しません（../../packages/domain-orders/src/internal/... は禁止）

    3.3 依存を明示することの意味

    ワークスペースでは、package.json の dependencies に書いていないパッケージは import できません（pnpm は厳格）。これにより、

    • パッケージ間の依存関係が package.json を見るだけで分かる
    • 「いつの間にか依存していた」が起きにくい
    • 依存グラフが ツールで可視化・検査 できる

    4.exports でカプセル化する

    4.1 問題：何でも import できてしまう

    exports を指定しないパッケージは、中のどのファイルでも import できてしまいます。

    ✕ 本来は公開していない内部実装を直接使えてしまう 
    import { calculateDiscountInternal } from "@acme/domain-orders/src/pricing/internal";

    これは 統合強度 でいう 侵入的結合（相手の内部実装に直接触れる、最も強い結合）です。

    4.2 exports で公開する入口を限定する

    ◯ 公開する入口を2つだけに限定する 
    // packages/domain-orders/package.json
{
  "name": "@acme/domain-orders",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    },
    "./testing": {
      "types": "./dist/testing.d.ts",
      "import": "./dist/testing.js"
    }
  }
}
    • @acme/domain-orders と @acme/domain-orders/testing だけ が import できます
    • それ以外のパス（@acme/domain-orders/src/...）は Node.js・TypeScript・バンドラーがエラーにします
    • つまり exports は、パッケージの公開 API を言語レベルで強制する仕組み です（→ モジュール間インターフェース）

    4.3 サブパスエクスポートで CRP を満たす

    凝集の3原則 の CRP（不要な依存を強制しない）は、サブパスエクスポート（パッケージ名/○○ の形で部分ごとに入口を作ること）でも実現できます。

    // packages/ui/package.json
"exports": {
  "./button": "./dist/button/index.js",
  "./dialog": "./dist/dialog/index.js",
  "./rich-editor": "./dist/rich-editor/index.js"
}
    • import { Button } from "@acme/ui/button" と書けば、リッチエディタの依存は読み込まれません
    • パッケージを分けるほどではないが、部分ごとに独立して使えるようにしたい ときに便利です

    5.パッケージの切り方 — 原則の当てはめ方

    5.1 切り方の軸

    軸パッケージの例当てはまる原則
    業務（ドメイン）domain-orders, domain-customersCCP（同じ業務の変更は1つのパッケージで）
    技術的な共通部品ui, api-client, loggerREP（再利用の単位としてまとめる）、CRP（使わないものを強制しない）
    設定config-eslint, config-typescriptREP
    アプリapps/web, apps/api最も不安定。誰からも依存されない

    5.2 内部パッケージの依存ルールの例

    • 依存は 上から下へ だけ（ADP・SDP）
    • domain-* 同士は 直接依存しない（必要なら公開 API かイベント経由）
    • shared-kernel は 小さく、抽象的に 保つ（SAP）

    5.3 よくある失敗

    失敗結果対策
    packages/common に何でも入れる苦痛ゾーン（安定しているのに具体的で、変えにくく拡張もできない状態）。全アプリが依存し、変えられなくなる用途ごとに分割（CRP）
    最初から細かく分けすぎる1つの機能追加で5パッケージを直す（CCP 違反）初期は粗く。必要になってから分割
    exports を書かない内部実装に直接依存される（侵入的結合）すべての内部パッケージに exports を書く
    アプリ同士が依存するapps/admin が apps/web の中身を import共通部分を packages/ に切り出す

    6.Turborepo と Nx

    モノレポの規模が大きくなると、ビルド時間 と 境界の管理 が課題になります。それを支援するのが Turborepo と Nx です。

    機能TurborepoNx
    タスクの依存関係に沿った実行✅ turbo.json でパイプラインを定義✅
    キャッシュ（変更のないパッケージはビルドを省略）✅ ローカル＋リモート✅ ローカル＋リモート
    影響範囲の実行（変更されたパッケージと、それに依存するものだけテスト）✅ --filter✅ nx affected
    依存グラフの可視化✅✅ nx graph
    モジュール境界の強制❌（ESLint などを別途使う）✅ @nx/enforce-module-boundaries（タグで依存ルールを定義）
    思想軽量。既存の pnpm workspaces に後から足しやすい多機能。コード生成・プラグインも含む

    6.1 Nx のモジュール境界ルール（例）

    // 各プロジェクトの project.json でタグを付ける
{ "tags": ["type:domain", "scope:orders"] }
    // eslint.config.mjs
"@nx/enforce-module-boundaries": ["error", {
  depConstraints: [
    { sourceTag: "type:app",     onlyDependOnLibsWithTags: ["type:feature", "type:ui", "type:domain"] },
    { sourceTag: "type:feature", onlyDependOnLibsWithTags: ["type:domain", "type:ui"] },
    { sourceTag: "type:domain",  onlyDependOnLibsWithTags: ["type:domain-kernel"] },
    { sourceTag: "scope:orders", onlyDependOnLibsWithTags: ["scope:orders", "scope:shared"] }
  ]
}]
    • 種類のタグ（app・feature・domain）で層のルール、スコープのタグ（orders・customers）で業務の境界のルールを表せます
    • ルール違反の import は ESLint のエラー になります

    詳しくは 依存ルールの自動検査 を参照してください。

    7.バージョン管理の考え方

    内部パッケージのバージョンには、大きく2つの方針があります。

    方針内容向いている
    バージョンを付けない（内部専用）常に workspace:* で最新を参照。リポジトリ全体で1つの状態アプリ内部だけで使うパッケージ。ほとんどのプロダクト開発
    バージョンを付けて公開するChangesets などで変更履歴とバージョンを管理し、npm に公開外部・他チームに配布するライブラリ（REP が重要になる段階）
    • 社内のモノレポでは、バージョンを付けない内部パッケージ から始めるのが一般的です
    • 外部に公開する段階になったら、REP（再利用の単位＝リリースの単位）に沿って整理し、セマンティックバージョニング（互換性を壊す変更・機能追加・修正で番号の上げ方を決める規則。例：2.4.1）と 変更履歴 を管理します

    8.よくある誤解

    誤解1：「モノレポにすれば自然とモジュール化される」

    誤りです。 1つのリポジトリに入れただけでは、相対パスでどこでも import できてしまいます。exports・依存の明示・境界ルール がそろって初めてモジュール化されます。

    誤解2：「パッケージは細かいほど再利用しやすい」

    初期には逆効果です。 CCP（同じ理由で変わるものはまとめる）を優先し、実際に再利用されるようになってから分けます。

    誤解3：「モノレポはマイクロサービスと相性が悪い」

    誤りです。 複数のサービスを1つのリポジトリで管理し、共通の型やクライアントをパッケージとして共有する構成はよく使われます。ただし、共有パッケージがサービス間の強い結合（分散モノリス）を生まないように 注意します。分散モノリス とは、サービスを分けたのに互いに強く結合していて、結局まとめて変更・デプロイしなければならない状態です（41章：モノリスとマイクロサービス）。

    9.まとめ

    • モノレポ：複数パッケージを1リポジトリで管理。横断的な変更がしやすいが、境界を守る仕組みが必要
    • pnpm workspaces：workspace:* で内部パッケージに依存。依存を package.json に明示する
    • exports：公開する入口を限定し、内部実装への 侵入的結合を言語レベルで防ぐ。サブパスで CRP も満たせる
    • 切り方：業務パッケージは CCP、共通部品は REP・CRP。依存は apps → feature → domain → shared-kernel の一方向
    • Turborepo はビルドとキャッシュ、Nx はそれに加えて タグによるモジュール境界の強制 が得意
    • 内部パッケージは バージョンなし から始め、外部公開の段階で REP に沿って整理する

    言語レベルでのモジュールの仕組み（ESM・TypeScript・barrel）は 言語のモジュール機構 で扱います。
