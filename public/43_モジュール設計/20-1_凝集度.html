    20 凝集と結合

    凝集度 — モジュールの中身は1つの目的にまとまっているか

    モジュールを分けるときの物差しの1つが「凝集度」です。凝集度が低いと何が困るのか、目指すべき「機能的凝集」とは何か、凝集度を高めるための分割の手順を、例とチェックリストで解説します。

    もとにしたノート：20_凝集と結合/01_凝集度

    ひとことで言うと

    凝集度 は、モジュールの中身が どれだけ1つの目的のために集まっているか を表す指標です。高いほどよく、モジュール設計では「1つの明確な責務を完結させる」機能的凝集 を目指します。

    このページでは、モジュールの 中身がどれだけ一つの目的にまとまっているか — すなわち 凝集度 — を学びます。クラスや関数も含めた一般論は 42章：凝集度と結合度 で扱っており、このページはその モジュール版 です。モジュールをどう分けるかを判断する物差しになります。

    • 機能的凝集を目指す：凝集度の7つのレベル

    2.凝集度とは何か

    凝集度（Cohesion） とは、1つのモジュール内の要素が どれだけ関連した目的のために集まっているか を表す指標です。ここでいう モジュール は、ディレクトリやパッケージのような「関連するコードをまとめた単位」のことです（詳しくは モジュールの基本概念）。

    凝集度状態モジュール例
    高い1つの関心・責務に集中billing — 請求関連だけ
    低い無関係な処理が混在misc — 日付・メール・CSV が同居

    凝集度は高いほどよい とされます。モジュール同士のつながりの強さを表す 結合度 とセットで覚えましょう。

    3.凝集度が低いときに起きる問題

    問題具体例
    変更範囲が読めないメール仕様変更のつもりが、無関係な CSV 処理まで触る
    名前が意味を失うcommon / util / helper が肥大化
    テストが難しい1モジュールのテストに無関係な依存が必要
    再利用しにくい必要な機能だけ取り出せない

    しかも低凝集は、放っておくと悪化していきます。

    1. 低凝集のモジュールでは、変更のたびに「どこまで触る？」が分からなくなる
    2. 新機能が「とりあえず common に」で追加される
    3. モジュールが肥大化し、さらに低凝集になる（1. に戻る）

    4.機能的凝集を目指す

    凝集度にはいくつかのレベルがありますが、モジュール設計では 機能的凝集（Functional Cohesion） を目指します。

    機能的凝集 とは、モジュール内のすべてが 1つの明確な機能・責務を実現するために存在する 状態です。

    レベル（低→高）説明
    偶発的関連性なしでたまたま同じ場所
    論理的カテゴリだけ共通（すべて「ユーティリティ」）
    時間的同じタイミングで実行されるだけ
    手続き的処理順序だけ共通
    通信的同じデータを扱う
    順次的出力が次の入力になる
    機能的1つの機能を完結

    先ほどの misc や Utils は、「ユーティリティ」というカテゴリだけが共通の 論理的凝集（またはたまたま同じ場所にある偶発的凝集）にあたります。

    5.凝集度を高めるための分割の考え方

    5.1 手順

    1. モジュールの 1文説明 を書く（「このモジュールは ○○ を担当する」）
    2. 説明に 含まれない処理 をリストアップする
    3. 含まれない処理を 別モジュールへ移す か、新モジュールを作る

    5.2 例：order モジュール

    「注文を担当する」はずの order モジュールに、メール送信や決済 API の呼び出しまで入っていたとします。1文説明に含まれない処理を外へ出すと、次のようになります。

    5.3 注意

    分ければよいわけではない

    • 分割しすぎ も問題です（モジュール分割の基本プロセス 参照）
    • 2〜3回の変更で一緒に触る処理は、同じモジュールに残す こともあります

    6.凝集度のチェックリスト

    • ☐ このモジュールを 1文 で説明できるか
    • ☐ モジュール内のファイルは 同じ変化の理由 を持つか
    • ☐ util / common / misc に 無関係な機能 が溜まっていないか
    • ☐ 新機能追加時、「ここに置く理由」を 言語化 できるか
    • ☐ モジュール単体で テストの意味 があるか

    より詳しいチェックは チェックリストとアンチパターン も参照してください。

    7.よくある誤解

    誤解1：「細かく分けるほど凝集度は高くなる」

    凝集度は「中身が1つの目的にまとまっているか」であって、モジュールの小ささではありません。一緒に変わる処理まで別々のモジュールに分けると、変更のたびに複数のモジュールを触ることになります。2〜3回の変更で一緒に触る処理は同じモジュールに残す、という判断もあります。

    誤解2：「共通処理は common や util にまとめておけばよい」

    「共通で使う」というカテゴリだけでまとめると、論理的凝集（低い凝集）になります。common は「とりあえずここに」の置き場になって肥大化しやすいので、置く理由を言語化できない処理は、関係するモジュールの側に置くことを考えます。

    8.まとめ

    • 凝集度 ＝ モジュール内のまとまりの強さ（高いほどよい）
    • 低凝集は変更範囲の不明瞭・肥大化・テスト困難を招く
    • 機能的凝集 — 1つの明確な責務 — を目指す
    • 1文説明と「含まれない処理」の洗い出しで分割を判断する

    次は、モジュール同士のつながりの強さを表す 結合度 に進みます。
