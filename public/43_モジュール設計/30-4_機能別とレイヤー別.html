    30 分割の仕方

    機能別とレイヤー別 — フォルダをどう切るか

    プロジェクトが大きくなると必ずぶつかる「フォルダをどう切るか」。業務ごとに分ける機能別（垂直分割）と、役割ごとに分けるレイヤー別（水平分割）を比べ、規模による使い分け、分割の原則、境界の見つけ方、循環依存の避け方、公開APIの絞り方までを解説します。

    もとにしたノート：30_分割の仕方/04_モジュール分割の考え方

    ひとことで言うと

    小規模ならレイヤー別で十分、中規模は「機能別＋中でレイヤー別」のハイブリッド、大規模は機能別が主です。どちらが正解かではなく 規模と目的に応じて使い分け、最初から最終形を目指さず段階的に進化させます。

    1.このページで扱うこと

    プロジェクトが大きくなると、「フォルダをどう切るか」「ファイルをどう分けるか」 という問題に必ずぶつかります。これを モジュール分割（module decomposition） と呼び、大きく2つの軸で考えます。

    • 機能別（垂直分割）：「ユーザー機能」「注文機能」のように、業務ごと に分ける
    • レイヤー別（水平分割）：「controller」「service」「model」のように、役割ごと に分ける

    どちらが正解というわけではなく、規模と目的に応じて使い分け ます。このページでは両者の比較、規模による使い分け、分割の原則、機能の境界の見つけ方、循環依存の回避、公開APIの設計、ディレクトリ構成の進化パターンを扱います。

    2.レイヤー別（水平分割）

    2.1 例：典型的なMVCフォルダ

    MVC（Model・View・Controller に分ける構成。41章：MVC）のフレームワークでよく見る形です。

    src/
├─ controllers/
│   ├─ UserController.ts
│   ├─ OrderController.ts
│   └─ ProductController.ts
├─ services/
│   ├─ UserService.ts
│   ├─ OrderService.ts
│   └─ ProductService.ts
├─ repositories/
│   ├─ UserRepository.ts
│   ├─ OrderRepository.ts
│   └─ ProductRepository.ts
└─ models/
    ├─ User.ts
    ├─ Order.ts
    └─ Product.ts

    メリット

    • 役割が揃っている（「controllerを探す」で全て見つかる）
    • 初心者に理解しやすい
    • 小規模なら十分に整理されている

    デメリット

    • 1つの機能追加でフォルダをまたぐ（user機能を足すのに、controllers/services/repositories/models すべてを触る）
    • 大規模になると同じ層のフォルダが肥大化
    • 機能の境界が見えなくなる

    3.機能別（垂直分割）

    3.1 例：機能ごとのフォルダ

    src/
├─ features/
│   ├─ user/
│   │   ├─ UserController.ts
│   │   ├─ UserService.ts
│   │   ├─ UserRepository.ts
│   │   └─ User.ts
│   ├─ order/
│   │   ├─ OrderController.ts
│   │   ├─ OrderService.ts
│   │   ├─ OrderRepository.ts
│   │   └─ Order.ts
│   └─ product/
│       └─ ...
└─ shared/
    └─ ...

    メリット

    • 1つの機能が1つのフォルダに集まる（凝集度が高い）
    • 機能単位で開発・削除できる
    • チーム分担しやすい
    • 機能が増えても他のフォルダに影響しない

    デメリット

    • 共通部分（shared）の扱いに悩む
    • 小規模すぎると冗長
    • 機能間の共通化が難しくなる

    機能ごとに縦に切る考え方をアーキテクチャとしてまとめたものに 41章：垂直スライスアーキテクチャ があります。

    4.規模による使い分け

    規模おすすめ理由・発展
    小規模（〜数十ファイル）レイヤー別 で十分全体を把握しやすい
    中規模（数十〜数百ファイル）機能別 ＋ レイヤー別のハイブリッド下の構成例
    大規模（数百〜数千ファイル）機能別（＝境界づけられたコンテキスト） が主モノレポ、マイクロサービスへ発展する

    中規模のハイブリッド構成の例です。

    src/
├─ user/
│   ├─ controller/
│   ├─ service/
│   └─ model/
├─ order/
│   ├─ controller/
│   ├─ service/
│   └─ model/
└─ shared/

    境界づけられたコンテキスト は、DDD（ドメイン駆動設計）で「同じ言葉が同じ意味で通じる範囲」を1つの単位として区切ったものです（42章：境界づけられたコンテキスト）。大規模での発展先は マイクロサービスとモノリス、npmパッケージとモノレポ で扱います。

    5.モジュール分割の原則

    5.1 同じ理由で変わるものは一緒に

    SRP（単一責任の原則：1つの部品が変わる理由は1つにする。42章：SOLIDとオブジェクト指向）をモジュール単位に拡張した原則です。機能追加・仕様変更のとき、1つのフォルダだけ触れば済む のが理想です。

    5.2 依存方向を明確に

    • 機能 A → 機能 B への依存はあるか
    • 共通部分は両方から依存されていいか
    • 循環依存を作らない

    5.3 公開APIを絞る

    各モジュールに 外から使ってよい入口（公開API） を1つ決め、内部実装は隠します。

    // user/index.ts — 公開する
export { UserController } from './UserController';
export { User } from './User';

// user/UserRepository.ts — 非公開

    5.4 共通部分は慎重に

    shared/, common/, utils/ は 全機能から依存される ため、変更しにくくなる リスクがあります。必要なものだけ置きます。

    6.機能の境界をどう見つけるか

    ヒント1：業務の言葉で分かれる単位

    「ユーザー管理」「注文」「請求」「配送」など、業務の人が 別々の話題 として扱う単位。

    ヒント2：変更理由が違う単位

    「セール機能を変えたい」のときに、ユーザー管理まで触る必要がある → 境界が正しくない。

    ヒント3：ライフサイクル・チーム

    別々のタイミングでリリース する、別々のチームが担当 するなら、別のモジュールに。

    ヒント4：データの所有権

    あるデータを 誰が書き込めるか で分ける。User機能だけが User を書き込める、など。

    業務の単位で分ける考え方は ドメインに基づく設計 でも詳しく扱っています。

    7.循環依存の回避

    A → B
B → A

    これが 循環依存（依存が輪になっている状態）です。次の問題を引き起こします。

    • ビルド順序が決まらない
    • 変更の影響が連鎖する
    • テストが書けない
    • 理解できない構造になる

    7.1 対策

    1. 共通部分を抽出（A・B から依存される C を作る）
    2. 依存方向を統一（どちらかを上位、どちらかを下位に）
    3. イベント駆動にする（A→B から、A→Event→B へ）

    依存の向きの決め方は 依存関係の管理、パッケージ単位の断ち切り方は 結合の3原則と循環依存 を参照してください。

    8.モジュールの公開APIを考える

    ✕ 悪い例：全部 export 
    // user/index.ts
export * from './UserController';
export * from './UserService';
export * from './UserRepository';
export * from './UserValidator';
export * from './UserMailer';
// 内部実装まで全部漏れている
    ◯ 良い例：必要なものだけ 
    // user/index.ts
export { UserController } from './UserController';
export type { User } from './User';
// UserService、UserRepository は内部用

    「外から触ってよいもの」と「内部用」を分ける ことで、モジュールを変更しても外への影響を抑えられます。公開APIの設計は モジュール間インターフェース で詳しく扱います。

    9.Screaming Architecture

    Robert C. Martin の言葉です。

    「コードを開いたとき、それが『注文システム』だと叫んでいるべき」

    ✕ 「MVC」だと叫んでいる

    src/
  controllers/
  services/
  models/

    ◯ 「注文管理システム」だと叫んでいる

    src/
  order/
  shipping/
  customer/

    技術ではなく、業務が見えるフォルダ構成 が理想とされます。詳しくは次のページ Screaming Architecture で掘り下げます。

    10.ディレクトリ構成の進化パターン

    1. スタート：単一ファイルやフラット構成
    2. レイヤー別：controller / service / model に分ける
    3. ハイブリッド：機能フォルダ ＋ 内部でレイヤー
    4. 機能別：完全に業務単位のモジュール
    5. モノレポ / マイクロサービス：独立したパッケージ・サービスへ

    方針

    最初から最終形を目指さない。規模に応じて段階的に進化させます（モジュール設計の進化）。

    11.よくある誤解

    誤解1：「機能別が正解で、レイヤー別は時代遅れ」

    小規模（〜数十ファイル）ならレイヤー別で十分に整理でき、初心者にも分かりやすい構成です。規模と目的で使い分けます。

    誤解2：「機能別にすれば shared は不要になる」

    共通部分は必ず出てきます。ただし shared/ は全機能から依存されて変えにくくなるので、必要なものだけを置き、肥大化させないことが大切です。

    誤解3：「フォルダを分ければモジュールになる」

    フォルダを分けても、中身を全部 export * していれば内部実装が漏れ、境界は守られません。公開APIを絞り、循環依存を作らないことまでがモジュール分割です。

    12.まとめ

    • モジュール分割は 機能別（垂直） と レイヤー別（水平） の2つの軸で考える
    • 小規模はレイヤー別、中規模はハイブリッド、大規模は機能別（境界づけられたコンテキスト）が主
    • 原則は「同じ理由で変わるものは一緒に」「依存方向を明確に」「公開APIを絞る」「共通部分は慎重に」
    • 境界は業務の言葉・変更理由・ライフサイクルとチーム・データの所有権で見つける
    • 循環依存は共通部分の抽出・依存方向の統一・イベント駆動で避ける
    • フォルダ構成は業務を叫ぶのが理想。最初から最終形を目指さず段階的に進化させる
