    20 凝集と結合

    結合度 — モジュール同士はどれだけ強く依存しているか

    高凝集と並ぶもう1つの物差しが「結合度」です。密結合で何が困るのか、内容結合からデータ結合までの6種類の結合の見分け方と弱め方、「疎結合」とは相手の何を知らないことなのか、そして疎結合にしすぎるコストまでを、TypeScript のコード例で解説します。

    もとにしたノート：20_凝集と結合/02_結合度

    ひとことで言うと

    結合度 は、モジュール同士が どれだけ強く依存し合っているか を表す指標です。結合の強さは「相手と何を共有しているか」で決まり、強い順に 内容 → 共通 → 外部 → 制御 → スタンプ → データ。ただし結合はゼロにはせず、モジュールの境界だけを疎に します。

    1.このページで扱うこと

    このページでは、モジュール同士の 依存の強さ — 結合度 — を学びます。凝集度 が高く、結合度が 低い 組み合わせが、変更に強いモジュール構造の基本です。凝集・結合の一般論は 42章：凝集度と結合度 にまとめてあり、ここではモジュール単位で詳しく見ます。

    • 結合度とは何かと、結合度が高いときに起きる問題
    • 結合の6種類：内容・共通・外部・制御・スタンプ・データ結合（コード例つき）
    • 疎結合を保つための原則とチェックリスト
    • 「疎結合」とは何を知らないことか
    • 見落としやすい「生成による結合」と DI
    • 結合の種類ごとの弱め方
    • 疎結合にしすぎるコスト

    2.結合度とは何か

    結合度（Coupling） とは、モジュール同士が どれだけ強く依存し合っているか を表す指標です。

    結合度状態例
    低い（疎結合）最小限の契約だけ共有インターフェース経由の呼び出し
    高い（密結合）内部の詳細まで知っている相手モジュールの内部クラスを直接 import

    結合度は低いほどよい とされます（ただし「ゼロ」を目指すわけではありません。11節で扱います）。

    3.結合度が高いときに起きる問題

    問題説明
    変更の連鎖A を直すと B・C も直す必要が出る
    テスト困難1モジュールのテストに全体が必要
    差し替え不可DB や外部 API の実装を変えにくい
    並行開発の衝突同じモジュールに多数が依存し、変更がぶつかる

    たとえば A ⇄ B ⇄ C が互いに密に結合していると、1か所の変更が全体に波及 します。

    4.結合の種類

    モジュール間の結合には、強さの異なる種類があります（弱い順のイメージ）。

    種類説明モジュール例
    データ結合必要なデータだけ渡すDTO で注文 ID を渡す
    スタンプ結合構造体の一部だけ使うが全体を渡す巨大な User オブジェクトを丸ごと
    制御結合相手の処理フローを制御するフラグで相手の分岐を指定
    外部結合外部で決められた形式・規約を共有する2つのモジュールが同じ CSV 形式・通信プロトコルに依存
    共通結合グローバルな共有状態全モジュールが同じ DB テーブルを直接更新
    内容結合内部実装に直接依存相手の private 関数を呼ぶ

    目標：データ結合に近づける。共通結合・内容結合は避ける。

    DTO（Data Transfer Object）は、モジュール間でデータを受け渡すためだけに作る型のことです。

    5.6種類の結合を詳しく見る

    この分類は、Stevens・Myers・Constantine の論文「Structured Design」（1974）で示され、Yourdon & Constantine の同名書籍（1979）や Myers『高信頼性ソフトウェア』で広まったものです。応用情報技術者試験などでもよく出ます。強い（悪い）順 に並べると次のとおりです。

    見分け方のコツ

    「相手と何を共有しているか」 を見ます。内部実装 → グローバルデータ → 外部の形式 → 制御情報 → データ構造 → 必要なデータだけ、の順に共有するものが小さくなり、結合が弱くなります。

    5.1 内容結合（Content Coupling）— 最も強い

    相手モジュールの内部（private なデータ・関数・コード）を直接参照・変更する 結合です。

    ✕ payment モジュールの内部状態を、order モジュールが直接書き換える 
    import { _internalCache } from '../payment/internal/cache';
_internalCache.balance = 0;
    • 相手は「使われている」ことを知らないので、相手の リファクタリング（外から見た振る舞いを変えずに中身を整理すること）だけで壊れる
    • 情報隠蔽（カプセル化）を完全に破っている（カプセル化と情報隠蔽）
    • 昔のアセンブラでの「他モジュールのコード途中へのジャンプ」もこれにあたる

    5.2 共通結合（Common Coupling）

    複数のモジュールが、同じグローバルなデータ（共通領域）を読み書きする 結合です。

    ✕ order と invoice の両方が appState を直接読み書きする 
    // global-state.ts
export const appState = { currentUser: null as User | null, taxRate: 0.1 };

// order と invoice の両方が appState を直接読み書きする
appState.taxRate = 0.08;   // ← どこで変わったか追えない
    • 誰がいつ値を変えたか 追跡できない。1か所の誤りが予期しない場所に波及する
    • グローバル変数、書き換え可能なシングルトン（アプリ全体で1つだけ作られるオブジェクト）、複数モジュールが直接更新する共有 DB テーブルが典型

    5.3 外部結合（External Coupling）

    外部で決められたデータ形式・通信プロトコル・デバイスのインターフェースなどを、複数のモジュールが共有する 結合です。共通結合と似ていますが、共有しているのが データそのものではなく「外から押しつけられた形式・規約」 である点が違います。

    ✕ import と export の両モジュールが、取引先指定の固定長フォーマットをそれぞれ独自に解釈している 
    const amount = Number(line.slice(20, 32));   // 20〜31桁目が金額、という外部仕様
    • 外部の仕様が変わると、それに依存する すべてのモジュールを同時に直す 必要がある
    • 対策は、外部形式を解釈する場所を 1か所（アダプタ・腐敗防止層）に閉じ込め、他のモジュールには内部の型で渡すこと。アダプタは外部の形式を内部の形に変換する部品、腐敗防止層は外部のモデルが内部に染み込まないよう翻訳する層です

    5.4 制御結合（Control Coupling）

    フラグなどの「何をすべきか」という制御情報を渡して、相手の処理の流れを操る 結合です。

    ✕ 呼び出し側が相手の内部の分岐を知っている 
    function printReport(data: Report, mode: 'summary' | 'detail' | 'csv') { /* mode で分岐 */ }
printReport(report, 'csv');   // 呼び出し側が相手の内部の分岐を知っている
    • 呼び出し側が 相手の内部ロジック（どんな分岐があるか）を知っている
    • 相手に分岐が増えると、呼び出し側も影響を受ける
    • 弱め方は 10節（インターフェース＋多態）を参照

    5.5 スタンプ結合（Stamp Coupling）

    構造体・オブジェクトを丸ごと渡すが、受け取る側はその一部しか使わない 結合です。

    ✕ メール送信に必要なのはアドレスと名前だけなのに、User 全体を受け取る 
    function sendWelcome(user: User) {
  mail.send(user.email, `${user.name}さん、ようこそ`);
}
    • 使っていない項目（User の住所・権限など）の 変更でも影響を受ける可能性がある
    • テストのたびに巨大な User を組み立てる必要がある
    • 「データ構造という型（スタンプ）を共有している」ことが名前の由来

    5.6 データ結合（Data Coupling）— 最も弱い

    必要なデータだけを、引数として渡す 結合です。

    ◯ 必要なデータだけを引数で受け取る 
    function sendWelcome(email: string, name: string) {
  mail.send(email, `${name}さん、ようこそ`);
}
    • やりとりが引数と戻り値だけで完結し、相手の内部も、余計なデータも知らない
    • 理想の状態。ただし引数が増えすぎる場合は、必要な項目だけの小さな型 を作って渡すのが現実的（それは「スタンプ結合」ではなく、目的に合わせて設計されたデータ結合と考えてよい）

    5.7 6種類の比較

    結合共有しているもの問題になる場面対策
    内容結合相手の内部実装相手のリファクタリング公開 API だけを使う
    共通結合グローバルデータどこで変わったか分からないデータの所有者を1つに決める
    外部結合外部の形式・規約外部仕様の変更アダプタに閉じ込める
    制御結合制御フラグ相手の分岐の追加・変更多態で振る舞いを分ける
    スタンプ結合データ構造全体使わない項目の変更必要な項目だけの型にする
    データ結合必要なデータのみほぼなし—

    5.8 補足：紛らわしいポイント

    • 共通結合と外部結合の違い：共通結合は「同じ データ を共有」、外部結合は「同じ 形式・規約（外部から決められたもの）を共有」。資料によって境界の書き方に揺れがあります。
    • スタンプ結合は必ずしも悪ではない：オブジェクト全体を渡す方が自然な場面（エンティティをそのまま保存する等）もあります。問題なのは「使わない項目まで知ってしまう」ことです。
    • 現代的な見方：この分類は手続き型プログラミング時代のものです。現代のモジュール・サービス単位では、統合強度（侵入的・機能的・モデル・契約）や、41章：コナーセンス で捉え直されています。おおまかには、内容結合 ≒ 侵入的結合、データ結合 ≒ 契約結合に近い位置づけです。

    6.疎結合を保つための原則

    1. インターフェース経由 でだけ通信する
    2. 必要最小限のデータ だけ渡す（巨大 DTO を避ける）
    3. グローバル状態・共有 DB テーブル に頼らない
    4. 依存の方向 を決める（依存関係の管理）
    5. イベント で非同期・疎結合にする（必要な場合）
    ✕ 密結合：他モジュールの内部を import 
    import { postgresPool } from '../infra/db';  // 他モジュールの内部
    ◯ 疎結合：インターフェースを import 
    import { OrderRepository } from './order-repository.interface';

    7.結合度のチェックリスト

    • ☐ モジュールは 公開 API 以外 に依存していないか
    • ☐ 循環依存（A→B→A）がないか
    • ☐ 共有の グローバル変数・シングルトン に頼っていないか
    • ☐ 変更時に触るモジュール数は 妥当 か
    • ☐ テストで 本物の DB や外部 API が必須になっていないか

    依存グラフの読み方は 参考図解 を参照してください。

    8.「疎結合」とは何を知らないことか

    疎結合は「依存がない」ことではありません。依存はあるが、相手の事情を最小限しか知らない 状態です。モジュール A が B について知りうることを並べると、知っている範囲が狭いほど結合は弱くなります。

    A が B について知っていること結合B のどんな変更で A が壊れるか
    B の内部クラス名・private な関数非常に強いB のリファクタリングすべて
    B が使っている技術（Postgres、S3 など）強い技術の差し替え
    B の具体クラス名（new するため）中クラス名・コンストラクタ引数の変更
    B の公開 API（関数シグネチャ）弱い公開 API の破壊的変更だけ
    自分が定義した インターフェースだけ最も弱い自分が契約を変えたときだけ

    最後の行が 依存性逆転の原則（DIP） を適用した状態です。A は B を知らず、自分で決めた契約だけを知っています（依存関係の管理、41章：依存性逆転の原則）。

    9.見落としやすい結合：生成による結合

    import している型だけでなく、new していること 自体も結合です。

    ✕ 型はインターフェースでも、生成で具体クラスに縛られている 
    class OrderService {
  private repo: OrderRepository = new PostgresOrderRepository(pool);
}
    new で生まれる結合問題
    具体クラス名を知る実装の差し替えにコード修正が必要
    コンストラクタ引数を知る相手の依存（pool など）まで知ってしまう
    生成タイミングを決めるテストで偽物に差し替えられない

    これを断つ技法が 依存性注入（DI） です。生成は外側（Composition Root：アプリの起動時に部品を組み立てる1か所）に任せ、自分は受け取るだけにします。

    ◯ 生成は外に任せ、コンストラクタで受け取る 
    class OrderService {
  constructor(private readonly repo: OrderRepository) {}
}

    詳しくは 41章：DI・IoC・Composition Root を参照してください。

    10.結合の種類ごとの弱め方

    5節の結合の種類それぞれに、典型的な弱め方があります。

    結合の種類弱め方使う道具
    内容結合公開 API だけを使い、内部は export しないindex.ts による公開面の制限（モジュール間インターフェース）
    共通結合共有データの所有者を1モジュールに決め、他は API 経由で使うデータの所有権（データの受け渡しと共有）
    外部結合外部形式の解釈を1か所に閉じ込め、内部の型に変換して渡すアダプタ・腐敗防止層
    制御結合フラグで分岐させず、振る舞いごとに実装を分けて渡すインターフェース + 多態（42章：多態とインターフェース）
    スタンプ結合必要な項目だけの型を定義して渡す専用 DTO、小さなインターフェース（ISP）
    具体クラスへの依存使う側が定義した抽象に依存させるDIP + DI

    ISP（インターフェース分離の原則）は、「使う側が必要としないメソッドへの依存を強制しない」という原則です。

    制御結合をインターフェースで解消する例です。多態（同じ呼び出し方で、実装ごとに違う振る舞いをさせること）を使います。

    ✕ 制御結合：呼び出し側がフラグで相手の分岐を指定 
    function notify(user: User, channel: 'email' | 'slack' | 'sms') {
  if (channel === 'email') { /* ... */ }
  else if (channel === 'slack') { /* ... */ }
  else { /* ... */ }
}
    ◯ 疎結合：振る舞いを実装ごとに分け、使う側はインターフェースだけ知る 
    interface Notifier { send(user: User, message: string): Promise<void>; }

class SignupService {
  constructor(private readonly notifier: Notifier) {}
  async signup(user: User) {
    // ...
    await this.notifier.send(user, 'ようこそ');
  }
}

    11.疎結合にしすぎるコスト

    結合度は低いほどよい、と言っても ゼロにはできず、ゼロを目指すべきでもありません。

    やりすぎ起きること
    すべてのクラスにインターフェース「定義へジャンプ」がインターフェースで止まり、読むのがつらくなる
    モジュール内部まで DI引数が6〜7個のコンストラクタだらけになる
    何でもイベントで通知処理の流れが追えず、動かさないと分からないコードになる

    判断の目安

    • モジュールの内部 は密でよい（高凝集。凝集度）
    • モジュールの境界、特に変わりやすい外部（DB・外部 API）との境界を疎にする
    • どこを疎にするかは、強度・距離・変動性で判断する（バランス結合）

    疎結合・インターフェース・DIP・DI の関係は 疎結合・DIP・DIの整理 にまとめています。

    12.よくある誤解

    誤解1：「疎結合とは、依存がないことだ」

    依存がなければ部品は協力できません。疎結合とは 依存はあるが、相手の事情を最小限しか知らない 状態です。最も弱いのは「自分が定義した契約だけを知る」状態（DIP）です。

    誤解2：「型をインターフェースにすれば、もう結合していない」

    型がインターフェースでも、クラスの中で new PostgresOrderRepository(pool) のように具体クラスを生成していれば、生成による結合が残ります。生成は DI で外に出します。

    誤解3：「スタンプ結合は常に悪い」

    エンティティをそのまま保存する場面など、オブジェクト全体を渡す方が自然なこともあります。問題なのは「使わない項目まで知ってしまう」ことです。

    13.まとめ

    • 結合度 ＝ モジュール間の依存の強さ（低いほどよい）
    • 密結合は変更連鎖・テスト困難・差し替え困難を招く
    • データ結合に近づけ、共通結合・内容結合を避ける
    • 結合は強い順に 内容 → 共通 → 外部 → 制御 → スタンプ → データ。見分けるには「相手と何を共有しているか」を見る
    • インターフェース・最小データ・依存方向で疎結合を保つ
    • 疎結合とは 相手の事情を最小限しか知らない こと。最も弱いのは「自分が定義した契約だけを知る」状態（DIP）
    • new も結合。生成は DI で外に出す
    • 結合はゼロにしない。境界だけを疎に、内部は高凝集に

    次は、結合を「なくすもの」ではなく「バランスを取るもの」として捉え直す バランス結合 に進みます。結合の考え方を使って実際にモジュールを切る手順は モジュール分割の基本プロセス で扱います。
