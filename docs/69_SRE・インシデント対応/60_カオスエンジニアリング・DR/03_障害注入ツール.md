# 障害注入ツール

カオスエンジニアリングやゲームデイで、障害を **安全に・再現可能に・止められる形で** 入れるためのツールです。手作業でサーバーを落とすこともできますが、ツールを使うと、影響範囲の指定・時間制限・自動停止・記録ができます。このノートでは代表的なツールと選び方を整理します。

---

## 1. 注入できる障害の種類

| 分類 | 例 |
|------|----|
| インスタンス・プロセス | サーバー・Pod・コンテナの停止、プロセスの kill |
| リソース | CPU・メモリ・ディスク I/O の負荷、ディスクフル |
| ネットワーク | 遅延の追加、パケットロス、通信の遮断（特定の依存先だけ）、DNS 失敗 |
| 依存サービス | DB・キャッシュ・外部 API のエラーや遅延 |
| 時間 | 時計のずれ |
| クラウド | AZ 障害の模擬、API のスロットリング |
| アプリケーション | 特定の関数で例外・遅延を起こす（コード内の障害注入ポイント） |

---

## 2. 代表的なツール

| ツール | 種類 | 対象 | 特徴 |
|--------|------|------|------|
| **Chaos Monkey** | OSS（Netflix） | インスタンス | ランダムにインスタンスを停止する元祖。Simian Army の一部として始まった |
| **AWS Fault Injection Service（FIS）** | マネージド | AWS（EC2・ECS・EKS・RDS・ネットワーク） | 実験テンプレートと、CloudWatch アラームによる自動停止条件を持てる |
| **Azure Chaos Studio** | マネージド | Azure | Azure 版のマネージド障害注入 |
| **Gremlin** | 商用 SaaS | ホスト・コンテナ・K8s | GUI、豊富な攻撃の種類、ワンクリックで停止（Halt） |
| **LitmusChaos** | OSS（CNCF） | Kubernetes | ChaosExperiment を K8s のカスタムリソースとして定義。実験のハブがある |
| **Chaos Mesh** | OSS（CNCF） | Kubernetes | Pod・ネットワーク・I/O・時間の障害をカスタムリソースで定義。ダッシュボード付き |
| **Toxiproxy** | OSS（Shopify） | TCP 接続 | アプリと依存先の間にプロキシを挟み、遅延・切断を入れる。テストやローカルでも使いやすい |
| **tc / stress-ng** | Linux コマンド | 単一ホスト | `tc netem` でネットワーク遅延、`stress-ng` で CPU・メモリ負荷。手軽だが管理機能はない |

---

## 3. 例

```yaml
# Chaos Mesh：api の Pod 1 つに 200ms の遅延を 5 分間入れる
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: api-delay
  namespace: staging
spec:
  action: delay
  mode: one
  selector:
    labelSelectors:
      app: api
  delay:
    latency: "200ms"
  duration: "5m"
```

```bash
# Linux：eth0 に 100ms の遅延を入れる → 元に戻す
sudo tc qdisc add dev eth0 root netem delay 100ms
sudo tc qdisc del dev eth0 root netem
```

- AWS FIS では、実験テンプレートに **停止条件（stop condition）** として CloudWatch アラームを指定できます。エラー率が上がったら自動で実験を止める、という安全装置です。

## 4. 選び方

| 状況 | 向いている選択 |
|------|----------------|
| まず手軽に試したい・ローカルやテストで依存先の障害を再現したい | Toxiproxy、tc / stress-ng |
| Kubernetes 中心 | LitmusChaos、Chaos Mesh |
| AWS 中心でマネージドがよい | AWS FIS |
| 複数環境をまとめて GUI で扱いたい・サポートが欲しい | Gremlin |

選ぶときの観点：
- **止める仕組み**：すぐに・確実に止められるか、停止条件を自動化できるか（最重要）
- **範囲の指定**：1 台・1% などに絞れるか
- **記録**：いつ何を入れたかが残るか、監視ツールに注釈を入れられるか
- **権限**：誰が実行できるかを制限できるか

---

## 5. 注意点

- ツールで障害を入れる前に、**観察できる状態** を作る（ダッシュボード・アラート。66_可観測性）。
- 実験は必ず **時間制限付き** にし、終了後に元の状態に戻ったことを確認する。
- 本番で使うときは、関係者への周知と承認のルールを決めておく（[[02_ゲームデイ]]）。
- ツールそのものの障害（止まらない・範囲が広がる）もあり得ます。最初はステージングで挙動を確かめます。
