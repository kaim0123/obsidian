# カオスエンジニアリング入門

**カオスエンジニアリング**は、本番に近い環境で意図的に障害を起こし、システムがそれに耐えられるかを **実験で確かめる** 取り組みです。「壊すこと」が目的ではなく、「本番で障害が起きる前に弱点を見つけること」が目的です。Netflix が 2010 年頃に始めた Chaos Monkey をきっかけに広まり、原則は Principles of Chaos Engineering（principlesofchaos.org）にまとめられています。

---

## 1. なぜ必要か

- 分散システムは、部品が多く、組み合わせが複雑で、**設計図を見ただけではどう壊れるか分からない**。
- タイムアウト・リトライ・フェイルオーバー・オートスケールといった仕組みは、**実際に障害が起きたときにしか動かない**。動かない仕組みは、壊れていても気づけません。
- テストは「既知の入力に対して正しい出力が出るか」を確かめます。カオスエンジニアリングは「**未知の条件でシステム全体がどう振る舞うか**」を確かめます。

| | テスト | カオスエンジニアリング |
|---|---|---|
| 目的 | 仕様どおりか確認する | 知らなかった弱点を見つける |
| 対象 | 部品・機能 | システム全体（人と手順も含む） |
| 環境 | テスト環境 | 本番、または本番に近い環境 |
| 結果 | 成功 / 失敗 | 新しい知識（仮説が正しかったか） |

---

## 2. 5 つの原則（Principles of Chaos Engineering）

1. **定常状態の仮説を立てる**：システムが正常なときの測れる指標（注文数/分、エラー率、p99 レイテンシ）を決め、「障害を入れてもこの指標は変わらない」と仮説を立てる。内部の CPU ではなく、**ユーザーから見た出力** を指標にします。
2. **現実の出来事を模す**：サーバー停止、ネットワーク遅延、依存サービスの失敗、ディスクフル、時計のずれ、トラフィック急増など、実際に起きうることを入れる。
3. **本番で実験する**：本番のトラフィックと構成でしか分からないことがある。ただし最初はステージングから始めてよい。
4. **自動化して継続的に回す**：一度確かめても、システムは変わり続ける。定期的に自動で実行する。
5. **爆発半径（blast radius）を最小にする**：影響範囲を小さく始め、すぐ止められるようにする。

---

## 3. 実験の進め方

1. **定常状態を定義する**：例「注文成功率 99.9% 以上、p99 < 500ms」。
2. **仮説を立てる**：例「Redis のプライマリが落ちても、フェイルオーバーで 30 秒以内に回復し、注文成功率は下がらない」。
3. **実験を設計する**：何を・どこに・どれくらいの規模で・どれくらいの時間入れるか。**中止条件**（指標がここを超えたら即停止）を決める。
4. **実行して観察する**：ダッシュボードを見ながら、中止条件を監視する。
5. **結果を分析する**：仮説は正しかったか。違ったなら、それが見つかった弱点。
6. **直して、また試す**：修正後に同じ実験を回し、改善を確認する。自動化の対象にする。

---

## 4. 始め方の段階

| 段階 | やること |
|------|----------|
| 1. 机上 | 障害シナリオを紙の上で追う（「このサーバーが落ちたらどうなる？」） |
| 2. ステージング | テスト環境で小さな障害を入れる |
| 3. ゲームデイ | 日時を決め、チームで集まって計画的に障害を入れる（[[02_ゲームデイ]]） |
| 4. 本番の小規模実験 | 本番の一部（1 台・1% のトラフィック）で実行 |
| 5. 継続的な自動実行 | Chaos Monkey のように常時・自動で実行 |

- **前提条件**：可観測性（指標が見えること）と、すぐに止める手段がなければ始めてはいけません（66_可観測性）。
- 弱点が分かっている状態で実験しても意味がありません。**既知の問題は先に直します**。

---

## 5. よくある誤解

- 「本番を壊すのは危険だ」：実験は小さく、止められる形で行います。本当に危険なのは、**本番障害で初めて弱点を知ること** です。
- 「ツールを入れれば終わり」：大事なのは仮説と観察と学び。ツールは手段です（[[03_障害注入ツール]]）。
- 「大企業だけのもの」：1 台の再起動、依存 API のタイムアウトを試すだけでも立派な実験です。
