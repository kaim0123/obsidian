# ゲームデイ

**ゲームデイ**は、日時を決めてチームで集まり、計画的に障害を起こして **システムと人の両方の対応力を試す演習** です。Amazon や Google で昔から行われてきた習慣で、Google SRE の DiRT（Disaster Recovery Testing）や、SRE Workbook の「インシデント対応の訓練」もこの考え方です。自動のカオス実験（[[01_カオスエンジニアリング入門]]）が「システム」を試すのに対し、ゲームデイは **アラート・ランブック・連絡体制・判断** まで含めて試します。

---

## 1. 何を確かめるか

| 観点 | 確かめること |
|------|--------------|
| システム | フェイルオーバー・リトライ・オートスケールが期待どおり動くか |
| 検知 | アラートは鳴るか、誰に届くか、何分で気づけるか |
| ランブック | 手順どおりにやって直るか、古くなっていないか（[[02_ランブックの書き方]]） |
| 人と役割 | インシデントコマンダー・連絡係が機能するか（[[03_インシデントコマンダーと役割分担]]） |
| 権限とツール | 必要な権限があるか、ダッシュボード・管理画面にアクセスできるか |
| 連絡 | ステータスページ・関係者への告知が回るか |

- 実際の障害で「権限がなくて操作できない」「ランブックのコマンドが古い」と分かるのは最悪です。ゲームデイで先に見つけます。

---

## 2. 準備

1. **目的とシナリオを決める**：例「プライマリ DB のフェイルオーバー」「外部決済 API の全面停止」「オンコール担当が 1 人欠けた状態での対応」。
2. **仮説を書く**：「5 分以内にアラートが鳴り、ランブックに従って 15 分以内に復旧できる」。
3. **範囲と環境を決める**：ステージングか本番か。本番なら影響範囲と時間帯（利用の少ない時間）を決める。
4. **中止条件と戻し方を決める**：どの指標がどこまで悪化したら中止するか、どうやって元に戻すか。
5. **役割を決める**：
   - **ファシリテーター**：シナリオを進め、障害を注入する（参加者には詳細を伏せることもある）
   - **対応者**：本番と同じように対応する
   - **観察者・記録係**：時刻と行動を記録する（[[06_インシデントタイムラインの記録]]）
6. **関係者に周知する**：サポート・他チームに、演習であることと時間帯を伝える。

---

## 3. 当日の進め方

1. 開始の宣言。定常状態のダッシュボードを全員で確認する。
2. 障害を注入する（[[03_障害注入ツール]]）。
3. 対応者は **本番と同じ手順** で対応する。記録係は「いつアラートが鳴り、いつ誰が何をしたか」を書き留める。
4. 中止条件に触れたら、ためらわずに止めて元に戻す。
5. 終了を宣言し、定常状態に戻ったことを確認する。

所要時間の目安は 1〜2 時間。最初は 1 シナリオに絞ります。

---

## 4. ふりかえり

ゲームデイの直後に、ポストモーテムと同じ形式でふりかえります（[[02_ポストモーテム雛形]]）。

- 仮説は正しかったか。どこで想定と違ったか。
- 検知・判断・対応のそれぞれに何分かかったか。
- ランブック・アラート・権限・ツールで直すべき点。
- 見つかった問題はアクションとして担当と期限を付ける（[[04_再発防止アクションの管理]]）。

**問題が見つかったゲームデイは成功** です。何も見つからなかったなら、シナリオが簡単すぎた可能性があります。

- 新人のオンコール研修としても有効です。本番障害の前に、安全な場で一連の流れを経験できます。
