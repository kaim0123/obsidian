# DR訓練とRTO・RPO

**DR（Disaster Recovery：災害復旧）** は、リージョン全体の障害・大規模なデータ消失・ランサムウェアなど、通常の冗長化では防げない事態から **どう立ち直るか** の計画です。計画の目標は **RTO** と **RPO** という 2 つの数字で表し、それを満たせるかを **訓練で確かめます**。バックアップは取っているだけでは意味がなく、「戻せること」を確かめて初めて価値が出ます。

---

## 1. RTO と RPO

| 指標 | 意味 | 問い |
|------|------|------|
| **RTO**（Recovery Time Objective：目標復旧時間） | 障害発生から、サービスを再開するまでに許される時間 | 「何時間止まってよいか」 |
| **RPO**（Recovery Point Objective：目標復旧時点） | 失ってよいデータの時間幅（最後の復旧点からどれだけ遡るか） | 「何分前までのデータが戻ればよいか」 |

```
  最後のバックアップ         障害発生                サービス再開
  ────●────────────────────────✕──────────────────────●────→ 時間
      |←──── RPO（失うデータ）────→|←──── RTO（止まる時間）────→|
```

- RTO・RPO を小さくするほど、コストと複雑さが大きくなります。**業務ごとに** 決めます（決済・注文は厳しく、分析用データは緩く）。
- 決めるのはエンジニアだけではありません。「何時間止まると、どれだけの損失か」をビジネス側と合意します（[[02_リスクの受け入れと信頼性目標]]）。

---

## 2. DR 戦略の 4 段階（AWS のホワイトペーパーより）

| 戦略 | 仕組み | RTO / RPO の目安 | コスト |
|------|--------|------------------|--------|
| **バックアップ & リストア** | 別リージョンにバックアップだけ置き、災害時に環境ごと作り直して復元する | 数時間〜1 日 / 数時間 | 低 |
| **パイロットライト** | データは別リージョンに複製し続け、アプリは最小構成（止めた状態）で用意しておく | 数十分〜数時間 / 数分 | 中 |
| **ウォームスタンバイ** | 縮小版の本番環境を別リージョンで常に動かし、災害時に拡大して切り替える | 数分〜数十分 / 数秒〜数分 | 中〜高 |
| **マルチサイト アクティブ/アクティブ** | 複数リージョンで同時に本番を動かし、どちらも常にトラフィックを受ける | ほぼゼロ / ほぼゼロ | 高 |

- 多くのサービスはバックアップ & リストアかパイロットライトで十分です。**RTO/RPO の要件から逆算して** 選びます。
- どの戦略でも、IaC（Terraform・CloudFormation）で環境を再現できることが前提です（61_サーバー・インフラ/40_構築・IaC）。

## 3. バックアップの原則

- **3-2-1 ルール**：データのコピーを 3 つ、2 種類の媒体に、1 つは別の場所（別リージョン・別アカウント）に置く。
- **不変（イミュータブル）なバックアップ**：ランサムウェアや誤操作で消されないよう、削除できない設定（S3 Object Lock、AWS Backup Vault Lock など）にする。
- **別アカウントに置く**：本番アカウントの権限が乗っ取られても、バックアップは守られるようにする。
- **暗号化キーも復元できるか**：バックアップが暗号化されているなら、キーも別に守る。
- **PITR（ポイントインタイムリカバリ）**：RDS などの機能で、保持期間内の任意の時点に戻せる。誤操作によるデータ破損に有効（[[08_データ破損・不整合]]）。

## 4. DR 訓練

**訓練していない DR 計画は、動かないものと考えます**。

| 訓練の種類 | 内容 | 頻度の目安 |
|------------|------|------------|
| 机上訓練 | 手順書を読み合わせ、抜け漏れを探す | 半年ごと |
| バックアップ復元テスト | バックアップを別環境に実際に復元し、データを検証する | 月次〜四半期 |
| 部分的なフェイルオーバー | 1 つの DB・1 つのサービスを DR 先に切り替える | 四半期 |
| 全面的なフェイルオーバー | リージョン全体を切り替え、本番トラフィックを流す | 年次 |

訓練で測ること：
- **実際にかかった RTO**（手順の開始から再開まで）と、**実際に失ったデータ（RPO）**。目標を満たしたか。
- 手順書どおりに進んだか、途中で詰まった箇所。
- 必要な権限・認証情報・連絡先が揃っていたか。
- 切り戻し（元のリージョンに戻す）までできたか。

- Google の DiRT のように、計画的な大規模訓練を年に一度行う企業もあります。ゲームデイの形式で実施できます（[[02_ゲームデイ]]）。

## 5. ランサムウェアを想定した復旧（追記 2026-10-17）

2026年の国内のランサムウェア被害では、復旧に長い時間とお金がかかっています（警察庁、2026年上半期。全体は [[10_2026年_国内情報漏洩の動向と対策]]）。

- 復旧費用は約 6 割が 1,000万円以上、4件は 1億円以上
- 1か月以内に復旧できたのは 48件中 23件。13件は公表時点でも復旧中

自然災害と違い、ランサムウェアは **攻撃者がバックアップを先に壊しに来る** 点が違います。

| 想定 | 対策 |
|---|---|
| 本番の管理者権限でバックアップを消される | バックアップは **別アカウント・別の認証基盤** で管理し、Object Lock などで削除できないようにする |
| バックアップにもマルウェアが入っている | どの時点までさかのぼれば安全かを判断できるよう、**保持世代を長めに** とる。復元後にスキャンする |
| クラウド事業者の基盤が被害に遭う | 2026年は IDCF クラウドの基盤が被害を受け 495 組織に影響。**事業者とは別の場所** にもバックアップを持つ |
| 全台を一度に戻す必要がある | 1 台の復元だけでなく、**全体を戻すのにかかる時間** を訓練で測る |

詳しくは [[08_ランサムウェア対策]]。

## 6. よくある失敗

- バックアップは取っていたが、**復元したことがなく、実際には壊れていた**。
- 復元に必要な手順・権限を知っている人が 1 人しかいない。
- DR 先の環境が本番の変更に追いついておらず、切り替えても動かない（構成のずれ）。
- DNS の TTL が長く、切り替えがユーザーに反映されるまで時間がかかる。
- 依存する外部サービスや認証基盤が、DR 先から使えない。
