# 信頼性とスピードの両立

「速くリリースすると壊れる、壊さないためには遅くするしかない」と考えがちですが、DORA（DevOps Research and Assessment）の調査は**速いチームほど安定している**ことを繰り返し示しています。この章では、信頼性と開発速度を両立させる仕組みを、SRE と継続的デリバリーの観点から整理します。

---

## 1. 速さと安定はトレードオフではない

DORA の 4 つの指標（『LeanとDevOpsの科学』/ State of DevOps Report）は、速さと安定を同時に測ります。

| 指標 | 分類 | 意味 |
|------|------|------|
| デプロイ頻度 | 速さ | どれくらいの頻度で本番に出しているか |
| 変更のリードタイム | 速さ | コミットから本番までの時間 |
| 変更失敗率 | 安定 | デプロイが障害を起こした割合 |
| 復旧時間（Failed deployment recovery time） | 安定 | 失敗したデプロイから回復するまでの時間 |

高パフォーマンスのチームは、**デプロイ頻度が高く、変更失敗率が低く、復旧も速い**という結果が出ています。理由は次の通りです。

- 1 回の変更が**小さい**ので、壊れても影響が小さく、原因も特定しやすい
- **頻繁に出している**ので、リリース手順が自動化・習熟されている
- **すぐ戻せる**ので、失敗を恐れずに出せる

---

## 2. 両立のための 4 つの仕組み

### 2.1 エラーバジェットで「どこまで攻めてよいか」を決める

[[03_エラーバジェット方針]] で、残り予算に応じてリリースの慎重さを変えます。予算が余っているときは速く、減ってきたら慎重に。**判断基準が数値なので議論が短くなる**のが利点です。

### 2.2 変更を小さく、段階的に出す

| 手法 | 効果 |
|------|------|
| 小さな PR・トランクベース開発 | 1 回の変更のリスクを下げる |
| カナリアリリース | 1% のユーザーにだけ出して様子を見る |
| フィーチャーフラグ | デプロイ（コードを置く）とリリース（機能を見せる）を分ける |
| 段階的ロールアウト | 1% → 10% → 50% → 100% と広げる |

詳しくは 65_リリース・デプロイ/10_デプロイ戦略 で扱います。

### 2.3 すぐ戻せるようにする

- **ロールバックを 1 コマンド・数分で**できるようにする（65_リリース・デプロイ/40_ロールバック）
- フィーチャーフラグで**機能だけ即座に切る**
- DB の変更は**後方互換**にして、アプリだけ戻せるようにする（expand-migrate-contract）

「壊さない」より「**すぐ直せる**」ほうが、コストが低く現実的です。これを **MTTR（復旧時間）重視**の考え方と言います。

### 2.4 本番で早く気づく

- SLO ベースのアラートで、ユーザー影響が出たらすぐ分かる（[[03_ページングとアラートの受け方]]）
- デプロイと同時に**自動でメトリクスを比較**し、悪化したら自動ロールバック（カナリア分析）
- デプロイ直後の重点監視（[[01_デプロイ直後の異常]]）

## 3. 信頼性を「機能」として計画する

信頼性の改善は、放っておくと新機能の開発に押し出されます。次のようにして**計画に組み込み**ます。

| やり方 | 内容 |
|--------|------|
| 信頼性の作業枠を確保 | スプリントの 20% を信頼性・技術的負債に充てる |
| ポストモーテムのアクションを必ず入れる | [[04_再発防止アクションの管理]] で追跡 |
| PRR（Production Readiness Review） | 新サービスを本番に出す前に、監視・ランブック・キャパシティを確認する |
| SLO を四半期目標（OKR）に入れる | 信頼性が評価の対象になる |

### PRR のチェック例

- [ ] SLO が定義され、ダッシュボードがある
- [ ] SLO ベースのアラートがあり、オンコール体制が決まっている
- [ ] 主要な障害シナリオのランブックがある
- [ ] ロールバック手順が確認済み
- [ ] 負荷試験で想定ピークの 2 倍を捌ける
- [ ] 依存先が落ちたときの挙動（タイムアウト・縮退）が決まっている

## 4. よくある失敗パターン

| パターン | 何が起きるか | 対策 |
|----------|--------------|------|
| 障害のたびに承認フローを増やす | リリースが遅く・大きくなり、かえって事故が増える | 承認より自動テストと段階リリース |
| 金曜デプロイ禁止を拡大解釈 | デプロイがまとめて月曜に集中し、大きな変更になる | ロールバックとオンコールを整えた上で、曜日ではなくリスクで判断 |
| 信頼性はSREチームの仕事 | 開発チームが運用を意識しない | 開発チームもオンコールに入る、SLO を共有する |
| 速さだけを目標にする | 変更失敗率が上がっても気づかない | 速さと安定の指標を必ずセットで見る |
