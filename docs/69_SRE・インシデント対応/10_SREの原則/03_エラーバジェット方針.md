# エラーバジェット方針

**エラーバジェット**は「SLO で許される失敗の量」を、**使ってよい予算**として扱う考え方です。SLO が 99.9% なら、残りの 0.1% はリリースや実験で失敗してよい枠になります。この章では、エラーバジェットの計算方法と、予算を使い切ったときに何をするかを決める**エラーバジェット方針（Error Budget Policy）**を説明します（Google SRE Workbook 付録「Example Error Budget Policy」が下敷き）。

---

## 1. エラーバジェットの計算

```
エラーバジェット = 1 − SLO
```

| SLO（30 日） | バジェット | 月 1,000 万リクエストの場合 | 時間に換算 |
|--------------|------------|-----------------------------|------------|
| 99% | 1% | 10 万件の失敗まで OK | 約 7.2 時間 |
| 99.9% | 0.1% | 1 万件の失敗まで OK | 約 43 分 |
| 99.99% | 0.01% | 1,000 件の失敗まで OK | 約 4.3 分 |

例：30 日の SLO が 99.9% のサービスで、先週のデプロイ失敗により 5,000 件のエラーが出た → **バジェットの 50% を消費**。残り 5,000 件分を今月の変更に使えます。

---

## 2. なぜ「予算」として扱うのか

エラーバジェットは、開発と運用の対立（[[01_SREとは]]）を**データで解決**します。

| 状況 | 判断 |
|------|------|
| バジェットが十分残っている | どんどんリリースしてよい。実験的な変更も OK |
| バジェットが減ってきた | リリースを慎重にする（カナリア比率を下げる、レビューを厚くする） |
| バジェットを使い切った | 新機能のリリースを止め、信頼性の改善を優先する |

- 「リリースしてよいか」を**人の声の大きさではなく残り予算で決める**
- 逆に、予算が余りすぎているなら「**慎重すぎる**」サイン。もっと速く出してよい、あるいは SLO が緩すぎる

---

## 3. エラーバジェット方針の中身

方針は**事前に文書化し、プロダクト責任者・開発・SRE が合意しておく**のが肝心です。障害が起きてから決めようとすると必ず揉めます。

### 方針の雛形

| 項目 | 記載例 |
|------|--------|
| 対象サービスと SLO | 決済 API：30 日ローリングで成功率 99.95% |
| 測定方法 | ロードバランサーのログから算出、ダッシュボード URL |
| 予算超過時の対応 | P0 以外の機能リリースを凍結。信頼性改善のチケットを最優先にする |
| 凍結の解除条件 | 30 日ローリングで SLO を回復するまで |
| 1 回の障害で予算の 20% 超を消費した場合 | ポストモーテム必須、再発防止策を次スプリントに入れる |
| 例外 | セキュリティ修正・法令対応は凍結中でもリリース可 |
| 判断者・エスカレーション | 意見が割れたら CTO が判断 |
| 見直し頻度 | 四半期ごと |

### 誰のせいで減ったかで扱いを変える

| 原因 | 扱い |
|------|------|
| 自チームの変更・バグ | 自チームのバジェットから消費 |
| 依存先（社内の別サービス）の障害 | 消費はするが、依存先チームに改善を依頼 |
| クラウド事業者の大規模障害 | 方針で「除外する」かを事前に決めておく |
| 想定外の負荷（テレビで紹介された等） | 消費する。キャパシティ計画の改善材料にする |

---

## 4. バーンレート（消費速度）で気づく

月末に「使い切っていた」と気づいても遅いので、**消費の速さ（バーンレート）**を見ます。

```
バーンレート = 実際のエラー率 ÷ 許容エラー率
```

- バーンレート 1 = ちょうど 30 日で使い切るペース
- バーンレート 14.4 = 約 2 日で使い切るペース → 1 時間続いたら即ページ
- バーンレート 6 = 約 5 日で使い切るペース → 6 時間続いたらページ

SRE Workbook 5 章「Alerting on SLOs」では、このように**複数の時間窓とバーンレートを組み合わせたアラート**を推奨しています。詳細は 66_可観測性/60_SLO・アラート で扱います。

---

## 5. 運用でつまずきやすい点

- **SLO が現実離れしている**：常に予算切れなら、凍結ばかりで方針が形骸化する。SLO 自体を見直す
- **凍結が守られない**：経営判断で例外が乱発されると意味がなくなる。例外の条件を文書に書き、例外を使った記録を残す
- **予算が余っているのに慎重なまま**：「余りは使ってよい」ことを明示し、カナリアの段階を減らすなどスピードに還元する
- **計測が信用されない**：SLI の定義があいまいだと「このエラーはカウントしない」論争になる。定義を 1 か所に書いておく
