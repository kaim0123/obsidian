# インシデント中のコミュニケーションと告知

インシデント対応では、技術的な復旧と同じくらい**情報を伝えること**が重要です。何も知らされない利用者は問い合わせを増やし、何も知らされない社内の関係者は対応チームに直接質問してきて、作業の邪魔になります。この章では、**対応チーム内**・**社内の関係者**・**利用者**の 3 つの相手ごとに、何を・いつ・どう伝えるかを整理します。

---

## 1. 伝える相手と手段

| 相手 | 知りたいこと | 手段 | 担当 |
|------|--------------|------|------|
| **対応チーム** | 今の仮説、誰が何をしているか、次の行動 | インシデント専用チャンネル、通話 | IC・全員 |
| **社内関係者**（CS・営業・経営） | 影響範囲、顧客への案内文、復旧見込み | 社内向け告知チャンネル、メール | Comms |
| **利用者** | 使えるか、いつ直るか、何をすればよいか | ステータスページ、アプリ内バナー、SNS | Comms |

**対応チャンネルと報告チャンネルを分ける**のが基本です。対応チャンネルに質問が殺到すると作業が止まるため、関係者には報告チャンネルを見てもらいます。

---

## 2. 対応チーム内のコミュニケーション

- **チャンネルで実況する**：口頭や通話で決めたことも、必ずテキストに残す（[[06_インシデントタイムラインの記録]]）。
- **定型のプレフィックス**を使うと読みやすくなります。

| プレフィックス | 意味 | 例 |
|----------------|------|----|
| `[決定]` | IC の判断 | `[決定] v2.13.3 にロールバックする` |
| `[実行]` | システムへの変更 | `[実行] 14:12 ロールバック開始` |
| `[観測]` | 見えた事実 | `[観測] 5xx 率 8% → 0.5%` |
| `[仮説]` | 推測 | `[仮説] 新しい決済 SDK のタイムアウト設定` |
| `[要約]` | IC の定期まとめ | 現状・影響・次の行動 |

- **事実と推測を分ける**：「DB が落ちている」ではなく「DB への接続でタイムアウトが出ている（観測）。DB 自体の障害かは未確認」。

---

## 3. 社内への定期報告

Comms は**決まった間隔で**報告します。新しい情報がなくても「変化なし、次回は 15:00」と送ることで、個別の問い合わせを減らせます。

| 重大度 | 報告間隔の目安 |
|--------|----------------|
| SEV1 | 15〜30 分ごと |
| SEV2 | 30〜60 分ごと |
| SEV3 以下 | 大きな変化があったとき |

報告テンプレート：

```text
【インシデント報告 #3】決済エラー（SEV2）14:30 時点
■ 現状: ロールバック完了。エラー率は平常値に戻りつつある
■ 影響: 13:55〜14:15 にクレジットカード決済の約 8% が失敗
■ 顧客対応: 失敗した注文は再度お試しいただくよう案内してください
■ 次の行動: 15 分間監視し、問題なければ収束宣言
■ 次回報告: 14:45
```

## 4. 利用者への告知

### 4.1 ステータスページ

Statuspage や Instatus などのステータスページで、状態を段階的に更新します。

| 状態 | 意味 |
|------|------|
| **Investigating**（調査中） | 問題を認識し調査している |
| **Identified**（特定） | 原因を特定し対応中 |
| **Monitoring**（監視中） | 修正を適用し様子を見ている |
| **Resolved**（解決） | 収束した |

### 4.2 文面のポイント

- **早く出す**：原因がわからなくても「〇〇で問題が発生しており調査中です」と出す。沈黙が最も不信を招く。
- **利用者の言葉で書く**：「payment-service の 5xx」ではなく「一部のクレジットカード決済が完了しない」。
- **何をすればよいか書く**：「時間をおいて再度お試しください」「他の決済方法はご利用いただけます」。
- **復旧見込みは約束しない**：確実でない時刻は書かず、「次回 15:00 に更新します」と更新時刻を約束する。
- **責任を他社に押しつけない**：外部サービスが原因でも、利用者にとってはこちらのサービスの障害。

---

## 5. 経営層・顧客担当へのエスカレーション

- SEV1 は発生時点で経営層に一報を入れる（詳細は後で）。
- 大口顧客や SLA 契約のある顧客には、顧客担当から個別連絡する。そのための**事実だけをまとめた短い文**を Comms が用意する。
- 個人情報の漏えいのおそれがある場合は、法務・セキュリティ担当と相談してから外部に出す（71_セキュリティ基礎/50）。

---

## 6. 収束後の告知

- 収束宣言は社内・利用者の両方に出す。
- 利用者向けには、必要に応じて**事後報告（公開ポストモーテム）**を出す。影響・原因の概要・再発防止策を利用者向けに書く（[[01_ポストモーテムとは]]）。
