# キュー詰まり

メッセージキュー（SQS・Kafka・RabbitMQ・Redis ベースのジョブキューなど）にメッセージが溜まり続け、処理が追いつかなくなる障害です。**ユーザーからは「メールが届かない」「反映が遅い」と遅れて見える** ため、気づくのが遅れがちです。このノートは汎用の型なので、自分の構成に合わせて書き換えて使います（[[02_ランブックの書き方]]）。

---

## 1. 症状とよくある原因

| 症状 | よくある原因 |
|------|--------------|
| キューの長さ（深さ）が増え続ける | 流入の急増、コンシューマーの停止・処理速度の低下 |
| Kafka のコンシューマーラグが増える | コンシューマーの処理が遅い、パーティション数に対してコンシューマーが少ない、リバランスの繰り返し |
| 同じメッセージが何度も処理される | 処理時間が可視性タイムアウトより長い、処理後の削除（ack）漏れ |
| 特定のメッセージで止まる | 処理できない「毒メッセージ」が先頭で再試行され続けている |
| DLQ が急に増える | 下流（DB・外部 API）の障害、メッセージ形式の変更 |

- コンシューマーの遅さの原因は、多くの場合 **下流の DB・外部 API** にあります（[[02_DBダウン・DB遅延]]、[[03_外部APIダウン]]）。

---

## 2. 影響の確認

- キューの深さ、最古のメッセージの経過時間（age of oldest message）、コンシューマーラグ（66_可観測性）。
- どの業務が遅れているか（メール・通知・決済後処理・集計）。遅れの許容範囲は業務ごとに違います。
- **今のペースで何分後に解消するか** を見積もる：溜まった量 ÷（処理速度 − 流入速度）。

```bash
# SQS：おおよそのメッセージ数
aws sqs get-queue-attributes --queue-url <url> \
  --attribute-names ApproximateNumberOfMessages ApproximateAgeOfOldestMessage

# Kafka：コンシューマーグループのラグ
kafka-consumer-groups.sh --bootstrap-server <broker> --describe --group <group>
```

---

## 3. 初動（止血）

- **コンシューマーが止まっているなら**：プロセス・Pod の状態とログを確認し、再起動する。
- **処理が遅いなら**：コンシューマーを増やす。ただし Kafka ではパーティション数より増やしても効かない。下流が原因なら、増やすと下流をさらに苦しめるので注意。
- **毒メッセージなら**：そのメッセージを DLQ に移す・スキップする。最大受信回数（maxReceiveCount）を設定して自動で DLQ に送る。
- **流入が異常なら**：発生元（バッチ・ループしているプロデューサー）を止める。
- **優先度をつける**：重要な処理（決済後処理）を別キューに分けて先に流す。

---

## 4. 切り分け

1. **流入が増えたのか、処理が減ったのか**：送信数と処理数のグラフを並べる。
2. **コンシューマーのエラー**：ログに同じエラーが繰り返し出ていないか。
3. **1 件あたりの処理時間**：普段と比べて伸びていれば、下流（DB・外部 API）を調べる。
4. **重複処理**：処理時間と可視性タイムアウトの関係、ack のタイミング。
5. **デプロイ**：メッセージの形式を変えていないか（プロデューサーとコンシューマーのバージョンのずれ）。

---

## 5. 復旧

- 溜まった分を流すときは、**下流が耐えられる速度に絞る**。一気に流すと DB や外部 API を倒します（二次災害）。
- DLQ のメッセージは、原因を直してから再投入（redrive）する。再投入の前に、二重処理になっても問題ないか確認する（冪等性）。
- 古すぎて意味がなくなったメッセージ（期限切れの通知など）は、流さずに捨てる判断もあります。

---

## 6. 事後にやること

- 再発防止の候補：
  - キューの深さではなく **最古メッセージの経過時間** でアラートを出す（業務の遅れに直結する）
  - すべてのキューに DLQ と最大受信回数を設定する
  - コンシューマーを冪等にする（68_分散システム/40_メッセージング・キュー）
  - キュー深さに応じたオートスケールを入れる
  - メッセージ形式にバージョンを持たせる
