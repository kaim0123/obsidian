# 外部APIダウン

決済・メール送信・地図・認証基盤など、自分たちが管理していない外部サービスが落ちたり遅くなったりする障害です。**相手は直せない** ので、やることは「自分のサービスへの影響を最小にする」ことに集中します。このノートは汎用の型なので、依存している外部サービスごとに書き換えて使います（[[02_ランブックの書き方]]）。

---

## 1. 症状とよくある原因

| 症状 | よくある原因 |
|------|--------------|
| 特定機能だけエラー（決済できない、メールが届かない） | 外部サービスの障害・メンテナンス |
| 全体が遅くなる・タイムアウトが連鎖する | 外部 API の応答遅延で、呼び出し側のスレッド・接続・イベントループが占有される |
| `401` / `403` の急増 | API キー・証明書の期限切れ、権限の変更 |
| `429 Too Many Requests` | レート制限の超過（自分たちの呼び出し過多） |
| レスポンスの形が変わった | 相手側の仕様変更・バージョン廃止 |

- 一番怖いのは **外部の遅延が自分のサービス全体を巻き込む** ことです（カスケード障害）。タイムアウトが長すぎると、待っているリクエストが積み上がって全体が止まります。

---

## 2. 影響の確認

- 外部 API ごとのエラー率・レイテンシ（呼び出し側で計測しておく。66_可観測性）。
- **相手のステータスページ** を確認する。公表済みなら原因探しの時間を省けます。
- どの機能が使えなくなっているか、代替手段があるかを整理する。
- 自社全体に波及しているか（無関係な API まで遅くなっていないか）。

---

## 3. 初動（止血）

- **巻き込まれを止める**：
  - サーキットブレーカーを開く（自動で開いていなければ手動で）。
  - タイムアウトを短くする、同時呼び出し数を制限する（バルクヘッド）。
  - リトライを止める・減らす。障害中のリトライは相手と自分の両方を苦しめます。
- **機能を縮退させる**：
  - Feature Flag でその機能を OFF にし、「現在ご利用いただけません」と表示する。
  - 非同期にできるもの（メール送信・通知・外部連携）はキューに溜めて後で送る。
  - キャッシュ済みの古いデータで表示を続ける（地図・為替レートなど）。
- 自分たちの問題（キー期限切れ・レート超過）なら、キーの更新・呼び出し量の削減を行う。

---

## 4. 切り分け

1. **自分側か相手側か**：同じ API を別環境（ステージング・ローカル）から `curl` で叩き、同じ結果になるか確かめる。

```bash
curl -sS -o /dev/null -w "%{http_code} %{time_total}s\n" https://api.example.com/health
```

2. **ネットワークか**：DNS 解決、TLS 証明書、NAT ゲートウェイ・プロキシ、送信元 IP の許可リスト。
3. **認証か**：キーの有効期限、ローテーションの反映漏れ。
4. **量か**：自分たちの呼び出し回数が急増していないか（ループ・リトライの暴走）。
5. **仕様変更か**：相手のチェンジログ・廃止予定の通知。

---

## 5. 復旧

- 相手が復旧したら、サーキットブレーカーが半開→閉に戻るのを確認する。
- キューに溜めた処理を流す。一気に流すと相手のレート制限に当たるので、流量を絞る。
- 縮退させた機能を戻し、ユーザー向けの告知を更新する（[[05_インシデント中のコミュニケーションと告知]]）。
- 処理が二重に走っていないか（決済の二重請求など）を確認する。外部呼び出しには冪等キーを付けておくのが前提です。

---

## 6. 事後にやること

- 相手の障害でも、**自社のポストモーテムは書く**。問うのは「相手が落ちたとき、なぜ自分たちの被害がこの大きさになったか」。
- 再発防止の候補：
  - すべての外部呼び出しにタイムアウト・リトライ上限・サーキットブレーカーを付ける（68_分散システム/60_障害耐性パターン）
  - 外部依存の一覧と、それぞれの縮退方法を決めておく
  - 重要な依存は代替プロバイダーを持つ（決済・メール）
  - API キー・証明書の期限をアラートにする
  - 相手のステータスページを購読する
