# デプロイ直後の異常

デプロイの直後にエラー率やレイテンシが跳ね上がる障害です。本番障害の原因として最も多い「変更」が引き金なので、**原因を深追いする前にまず戻す**のが鉄則です。このノートは汎用の型なので、自分のサービスの構成に合わせて書き換えて使います（書き方は [[02_ランブックの書き方]]）。

> 想定スタック：Node.js のアプリを Kubernetes または ECS で動かし、PostgreSQL/MySQL・Redis を使う一般的な Web サービス。

---

## 1. 症状とよくある原因

| 症状 | よくある原因 |
|------|--------------|
| 5xx エラー率の急上昇 | コードのバグ、環境変数・シークレットの設定漏れ、依存パッケージの不整合 |
| 起動しない・再起動を繰り返す（CrashLoopBackOff） | 起動時の設定読み込み失敗、ヘルスチェックの失敗、ポート違い |
| レイテンシの悪化 | 新しい N+1 クエリ、インデックスのないクエリ、キャッシュキーの変更でヒット率が低下 |
| 一部のユーザーだけ失敗 | Feature Flag の設定ミス、古いクライアントとの互換性の破壊（API の破壊的変更） |
| DB エラーの急増 | マイグレーションとコードの順序の不一致（カラムがない・まだ使われている） |

- **「デプロイから何分後に始まったか」** が一番の手がかりです。デプロイ時刻とメトリクスの変化が重なるなら、まず変更を疑います。

---

## 2. 影響の確認

- エラー率・レイテンシ（p95/p99）・リクエスト数を、デプロイ時刻の前後で比べる（66_可観測性 のダッシュボード）。
- **影響範囲**：全エンドポイントか、特定の API だけか。全ユーザーか、特定の地域・クライアントだけか。
- Canary や段階リリースの途中なら、**新バージョンの Pod/タスクだけ** の指標を見る。旧バージョンが正常なら原因はほぼ確定です。
- 重大度を決める（[[02_重大度レベル（Severity）]]）。

---

## 3. 初動（止血）

**迷ったらロールバック**。原因調査は元に戻してからで間に合います。

```bash
# Kubernetes：直前のリビジョンに戻す
kubectl rollout undo deployment/api -n production
kubectl rollout status deployment/api -n production

# 段階リリース中なら、まず新バージョンへのトラフィックを止める
# （Argo Rollouts の例）
kubectl argo rollouts abort api -n production
```

- ECS なら直前のタスク定義リビジョンでサービスを更新する。
- Feature Flag で出した機能なら、**Flag を OFF にする** のが最速で最も安全。
- 戻せない変更（破壊的なマイグレーション）が含まれる場合は、前方修正（修正版をすぐ出す）を選ぶ。どちらにするかの判断基準は 65_リリース・デプロイ/40_ロールバック を参照。
- ロールバックしたら、インシデントチャンネルに「何時何分にロールバックした」と記録する（[[06_インシデントタイムラインの記録]]）。

---

## 4. 切り分け

ロールバックで直ったら、原因は今回の差分の中にあります。

1. **差分を確認**：`git log <前回のタグ>..<今回のタグ>` で含まれた変更を並べる。
2. **設定の差分**：環境変数・シークレット・ConfigMap・インフラ（IaC）の変更も差分に含める。コードだけ見て見落とすことが多い。
3. **ログ**：新バージョンの起動ログ、最初に出たエラーのスタックトレース（84_デバッグ/40_サーバー・Node）。
4. **依存**：lockfile の変更、ベースイメージの更新、ランタイムのバージョン。
5. **データ**：マイグレーションが適用済みか、コードとスキーマの順序が合っているか。

ロールバックで直らない場合は、デプロイ以外（DB・外部 API・トラフィック増）を疑い、該当するランブックへ移ります。

---

## 5. 復旧

- 原因を直した版を、**通常より慎重に** 出す（Canary の比率を小さく、観察時間を長く）。
- マイグレーションを含む場合は、expand → migrate → contract の順で互換性を保つ。
- 復旧後 30 分〜1 時間は重点監視を続け、エラー率が平常に戻ったことを確かめてからインシデントをクローズする。

---

## 6. 事後にやること

- ポストモーテムを書く（[[01_ポストモーテムとは]]）。問うのは「誰が壊したか」ではなく「**なぜ本番に届くまで気づけなかったか**」。
- 再発防止の候補：
  - CI にテスト・型チェック・マイグレーションの検証を追加する
  - Canary と自動ロールバック（エラー率のしきい値）を入れる
  - 設定値の検証を起動時に行い、不正なら起動を失敗させる
  - デプロイを小さく・頻繁にする
- アクションは担当と期限を付けて管理する（[[04_再発防止アクションの管理]]）。
