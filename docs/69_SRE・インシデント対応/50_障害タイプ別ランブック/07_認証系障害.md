# 認証系障害

ログインできない、ログイン済みのユーザーが突然ログアウトされる、API が一斉に `401` を返す、といった障害です。認証はほぼ全機能の入口なので、**1 か所の障害が全機能の障害に見えます**。このノートは汎用の型なので、自分の構成に合わせて書き換えて使います（[[02_ランブックの書き方]]）。

> 想定スタック：自前のセッション（Redis）または JWT、外部 IdP（Auth0・Cognito・Google など）との OIDC 連携。

---

## 1. 症状とよくある原因

| 症状 | よくある原因 |
|------|--------------|
| 全員が突然ログアウトされた | セッションストア（Redis）の再起動・データ消失、署名キー・Cookie 名の変更 |
| 全リクエストが `401` | JWT 署名キーのローテーション失敗、JWKS の取得失敗、サーバー間の時計のずれ |
| ソーシャルログイン・SSO だけ失敗 | 外部 IdP の障害、クライアントシークレットの期限切れ、リダイレクト URI の設定変更 |
| 一部のブラウザだけログインできない | Cookie 属性（SameSite・Secure・Domain）の変更、サードパーティ Cookie の制限 |
| ログイン画面が遅い・タイムアウト | パスワードハッシュの計算負荷、認証 DB の遅延、ブルートフォース攻撃 |

- 攻撃（クレデンシャルスタッフィング）でも同じ症状が出ます。**セキュリティインシデントの可能性** を常に頭に置き、疑わしければセキュリティ担当を呼びます（71_セキュリティ基礎/50）。

---

## 2. 影響の確認

- ログイン成功率・失敗率、`401`/`403` の発生率を時系列で見る。
- **新規ログインだけか、既存セッションも切れているか**。
- ログイン方式ごと（パスワード・SSO・パスキー）に分けて見る。
- 失敗ログインの送信元に偏りがないか（特定 IP・国・User-Agent からの大量試行）。

---

## 3. 初動（止血）

- **デプロイ・設定変更の直後なら**：ロールバックする（[[01_デプロイ直後の異常]]）。署名キー・Cookie 設定の変更は影響が大きいので最優先で疑う。
- **外部 IdP の障害なら**：相手のステータスページを確認し、ユーザーに告知する。パスワードログインなど別の手段が使えるなら案内する（[[03_外部APIダウン]]）。
- **セッションストアの障害なら**：Redis を復旧させる。データが消えた場合は再ログインが必要になる旨を告知する。
- **攻撃なら**：WAF・レート制限で送信元を遮断し、CAPTCHA を有効にする。
- **署名キーの問題なら**：旧キーを検証用に戻す（新旧両方で検証できる状態にする）。

---

## 4. 切り分け

1. **どこで失敗しているか**：ログイン画面 → IdP へのリダイレクト → コールバック → トークン検証 → セッション作成、のどの段階か。ブラウザの DevTools の Network タブで追う。
2. **トークンの中身**：JWT をデコードして `exp`・`iat`・`kid`・`iss`・`aud` を確認する（本番トークンを外部サイトに貼らない）。
3. **時計**：サーバーの時刻がずれていないか。`exp`/`nbf` の検証が失敗します。
4. **キー**：JWKS エンドポイントに到達できるか、`kid` に一致するキーがあるか。
5. **Cookie**：`Set-Cookie` が返っているか、属性が正しいか、ブラウザが保存・送信しているか。

---

## 5. 復旧

- キーのローテーションは「新キーを追加 → 新キーで署名開始 → 旧キーの有効期限切れを待って削除」の順で行う。
- シークレット・証明書を更新したら、全インスタンスに反映されたか確認する。
- 攻撃だった場合は、影響を受けたアカウントのパスワードリセット・セッションの無効化を検討する。
- 仕組みの詳細は 73_認証認可・74_セッション管理。

---

## 6. 事後にやること

- 再発防止の候補：
  - ログイン成功率の低下をアラートにする
  - シークレット・証明書・キーの期限を一覧化し、期限前にアラートを出す
  - キーのローテーション手順をランブック化し、訓練する（[[02_ゲームデイ]]）
  - 認証まわりの設定変更は、段階的に出す・レビューを必須にする
  - セッションストアの冗長化
