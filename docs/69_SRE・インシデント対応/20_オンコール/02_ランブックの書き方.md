# ランブックの書き方

**ランブック（Runbook）** は、特定のアラートや作業に対して「**何を確認し、何をすればよいか**」を書いた手順書です。夜中に起こされた寝ぼけた頭でも、その分野に詳しくない当番でも、同じ品質で初動できるようにするのが目的です。この章では、ランブックの構成と書き方のコツを説明します。

---

## 1. ランブックとプレイブック

| 用語 | 意味 | 例 |
|------|------|----|
| **ランブック** | 特定のアラート・作業の具体的な手順 | 「API 5xx 率上昇」アラートの初動手順 |
| **プレイブック** | より広い状況での対応方針・役割分担 | 「大規模障害時の対応方針」 |

呼び方は組織によって混ざりますが、このフォルダでは**アラート単位の手順 = ランブック**、**障害の型ごとの手順 = 50_障害タイプ別ランブック**として扱います。

---

## 2. 手順と判断を分ける

旧 Operations 目次の運用ルールにある通り、ランブックでは次の 2 つを**分けて書き**ます。

| 種類 | 性質 | 書き方 |
|------|------|--------|
| **手順（Runbook）** | 誰がやっても同じ結果になる機械的な操作 | コマンドをそのままコピーできる形で、番号付きで書く |
| **判断（Decision）** | 状況次第で答えが変わる | 判断の基準と、迷ったときの連絡先を書く |

混ぜると、初動で「これはやってよいのか」と迷います。例えば「ロールバックする」は手順、「ロールバックすべきか」は判断です。

---

## 3. ランブックの構成

```markdown
# [アラート名] API 5xx エラー率上昇

## 概要
- 何が起きているか：API の 5xx 率が 5 分間 2% を超えた
- ユーザー影響：一部のリクエストが失敗している
- 重大度の目安：SEV2（決済 API なら SEV1）

## まず確認すること（5 分以内）
1. ダッシュボード：<URL>
2. 直近のデプロイ：`deploy-history --service api --since 1h`
3. 依存先のステータス：DB / 決済 API / 認証

## 判断
- 直近 1 時間にデプロイあり → 「ロールバック手順」へ
- 特定のエンドポイントだけ → 該当機能のフィーチャーフラグを OFF
- 全体かつデプロイなし → DB・依存先を疑う（50_障害タイプ別ランブック）
- 15 分で見当がつかない → インシデント宣言、セカンダリを呼ぶ

## 手順
### ロールバック
1. `deploy rollback --service api --to previous`
2. 5 分待って 5xx 率を確認
3. 下がらなければ「判断」に戻る

## エスカレーション
- API チーム：@api-oncall
- DB：@db-oncall

## 関連
- 過去の事例：<ポストモーテムへのリンク>
- 最終更新：2026-09-26 / 更新者
```

### 各項目のポイント

| 項目 | ポイント |
|------|----------|
| 概要 | アラートの意味とユーザー影響を 3 行で |
| まず確認すること | 見るべき場所の**リンクとコマンドをそのまま**書く |
| 判断 | 「もし〜なら〜」の分岐で書く。フローチャートでもよい |
| 手順 | コピー＆ペーストで実行できる形。破壊的な操作には⚠️を付ける |
| エスカレーション | 名前ではなくロール・チャンネル名で書く（人は異動する） |
| 関連 | 過去のポストモーテム、設計ドキュメント |

---

## 4. 良いランブックの条件

- **アラートから 1 クリックで開ける**：アラートの本文にランブックの URL を入れる
- **前提知識を要求しない**：「いつものやつを再起動」ではなく、コマンドを書く
- **冪等な操作から先に書く**：何度やっても安全な確認・再起動を先に、データを変える操作は後に
- **止まる場所がある**：「ここで改善しなければエスカレーション」と明記する
- **最終更新日がある**：古いランブックは誤った操作を招く

### よくある悪い例

| 悪い例 | 問題 | 改善 |
|--------|------|------|
| 「適宜対応する」 | 何もしていないのと同じ | 具体的な確認項目を書く |
| スクリーンショットだけ | UI が変わると使えない、検索できない | コマンドや URL をテキストで |
| 作った人しか分からない略語 | 他の当番が読めない | 初出で説明する |
| 全障害を 1 ページに | 探せない | アラート単位で分ける |

---

## 5. ランブックを保守する

ランブックは**陳腐化しやすい**文書です。

1. **使うたびに直す**：対応後、手順と違った点をその場で修正する
2. **ポストモーテムのアクションに入れる**：障害のたびに「ランブックの更新」を確認する（[[04_再発防止アクションの管理]]）
3. **定期レビュー**：四半期に 1 回、使われていないランブック・存在しないアラートを整理
4. **演習で使う**：ゲームデイでランブック通りに動けるか試す（[[02_ゲームデイ]]）
5. **自動化の候補にする**：毎回同じ手順なら、スクリプト化・自動化する（[[04_トイルの削減と自動化]]）
