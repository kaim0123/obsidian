# ページングとアラートの受け方

**ページング**は、アラートを受けて人を呼び出すことです。人を呼ぶアラートが多すぎるとオンコールは疲弊し、少なすぎると障害に気づけません。この章では、Google SRE 本 6 章「Monitoring Distributed Systems」・10 章「Practical Alerting」、PagerDuty の Incident Response ドキュメントをもとに、**どのアラートで人を呼ぶか**と、**呼ばれたときにどう受けるか**を説明します。

---

## 1. アラートの 3 つの行き先

すべての異常で人を起こす必要はありません。緊急度で行き先を分けます。

| 行き先 | 条件 | 例 |
|--------|------|----|
| **ページ**（電話・プッシュ通知） | 今すぐ人が対応しないとユーザー影響が広がる | 決済のエラー率が SLO を急速に消費している |
| **チケット** | 数日以内に対応すればよい | ディスク使用率が 3 日後に 90% に達する見込み |
| **ログ・ダッシュボード** | 調査時に見られればよい | 個別サーバーの CPU 使用率 |

SRE 本の原則は「**ページは、人間の知性が必要な、緊急で、実際にユーザーに影響している問題にだけ使う**」です。

---

## 2. 良いページの条件

アラートを作るときに、次の質問に答えます（SRE 本 6 章より）。

- このアラートは、**放っておくとユーザーに影響する**状態を検知しているか？
- 鳴ったとき、**何か行動できる**か？ それとも「見て終わり」か？
- その行動は**自動化できない**か？ 機械でできるなら人を呼ばない
- **誤報（鳴ったが問題なし）**はどれくらいあるか？

### 症状ベースと原因ベース

| 種類 | 例 | ページに向くか |
|------|----|----------------|
| **症状**（ユーザーが感じること） | エラー率の上昇、レイテンシの悪化、SLO バーンレート | 向く |
| **原因**（内部の状態） | CPU 90%、メモリ 80%、1 台のサーバーダウン | 原則として向かない（チケットやダッシュボードへ） |

CPU が 90% でもユーザーが困っていなければ問題ありません。逆に、CPU は正常でも外部 API の障害でエラーが出ていることもあります。**症状で呼び、原因はダッシュボードで調べる**のが基本です。

### SLO ベースのアラート

最も推奨されるのは、エラーバジェットの消費速度（バーンレート）で呼ぶ方法です（[[03_エラーバジェット方針]]、66_可観測性/60_SLO・アラート）。

- 1 時間で予算の 2% を消費 → ページ
- 6 時間で予算の 5% を消費 → ページ
- 3 日で予算の 10% を消費 → チケット

## 3. アラート疲れ（Alert Fatigue）

鳴りすぎるアラートは、**本当に重要なアラートを見逃す**原因になります。

| 症状 | 対策 |
|------|------|
| 同じアラートが毎日鳴り、毎回「様子見」 | 削除するか、チケットに格下げする |
| 1 つの障害で 50 件のアラートが鳴る | 依存関係でまとめる（グルーピング・抑制） |
| 自然に回復するアラート（フラッピング） | 継続時間の条件を付ける（「5 分間続いたら」） |
| 夜間に鳴るが朝まで待っても問題ない | 営業時間のみ通知にする |
| 誰も意味を説明できないアラート | 作成者に確認、不明なら削除 |

**定期的なアラート棚卸し**（月 1 回、鳴ったアラートを一覧にして「対応が必要だったか」を振り返る）が有効です。

---

## 4. ページを受けたときの動き

PagerDuty の Incident Response ドキュメントでは、ページを受けたらまず**Acknowledge（確認）**することを求めています。

| ステップ | やること | 目安時間 |
|----------|----------|----------|
| 1. 確認（Ack） | ページングツールで「対応中」にする。セカンダリへのエスカレーションが止まる | 5 分以内 |
| 2. 状況把握 | アラートに付いたランブックとダッシュボードを開く | 5〜10 分 |
| 3. 影響判断 | ユーザー影響があるか、どれくらい広いか | 〜15 分 |
| 4. 分岐 | 自分で直せる → 対応 / 大きい → インシデント宣言（[[01_インシデント対応の基本フロー]]） | — |
| 5. 記録 | 何を見て何をしたかを、チャンネルやチケットに残す | 随時 |
| 6. 解決（Resolve） | 回復を確認してからツールで解決にする | — |

### やってはいけないこと

- Ack だけして放置する（セカンダリにも届かなくなる）
- 1 人で 30 分以上抱え込む。**迷ったら早めに人を呼ぶ**。呼んで何もなかったのは失敗ではない
- 記録を残さずに操作する（後から何が効いたか分からなくなる）

---

## 5. エスカレーションポリシー

ページングツールでは、応答がないときの自動エスカレーションを設定します。

```
0 分   プライマリにプッシュ通知
5 分   応答なし → プライマリに電話
10 分  応答なし → セカンダリに通知
20 分  応答なし → チームリードに通知
```

- 夜間は**電話**を使う（プッシュ通知は気づかないことがある）
- エスカレーションが発生したら、その理由（寝ていた、電波がなかった）を責めずに記録し、体制を見直す
