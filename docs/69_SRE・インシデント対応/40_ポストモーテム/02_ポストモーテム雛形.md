# ポストモーテム雛形

ポストモーテムは、毎回同じ形で書くと**書く人の負担が減り、読む人も比較しやすく**なります。この章では、Google SRE 本の付録「Example Postmortem」や SRE Workbook、Atlassian の Incident Handbook のテンプレートを参考にした雛形と、各欄の書き方のコツをまとめます。

---

## 1. 雛形の構成

| セクション | 書くこと | 読む人が知りたいこと |
|------------|----------|----------------------|
| 概要 | 3〜5 行の要約 | 何が起きたか、一目で |
| 影響 | 利用者・事業への影響を数字で | どれくらい大きかったか |
| タイムライン | 時系列の出来事 | どう展開したか |
| 原因と寄与要因 | 引き金と、それを許した条件 | なぜ起きたか |
| 対応の評価 | うまくいったこと・いかなかったこと・幸運だったこと | 対応から学べること |
| アクション | 再発防止策、担当、期限 | 何が変わるか |

---

## 1. 概要
<何が・いつ・どれくらいの時間・誰に影響し、どう復旧したかを 3〜5 行で>

## 2. 影響

## 3. 各欄の書き方のコツ

### 3.1 概要

- 忙しい人は概要しか読みません。**これだけ読めば全体がわかる**ように書く。
- 例：「9 月 26 日 13:55〜14:35 の 40 分間、クレジットカード決済の約 8% が失敗した。原因は決済 SDK の更新でタイムアウトが短くなったこと。デプロイのロールバックで復旧した。」

### 3.2 影響

- **数字で書く**：「多くのユーザー」ではなく「約 1,200 件の注文が失敗」。
- SLO があれば、エラーバジェットを何%消費したかを書く（[[03_エラーバジェット方針]]）。

### 3.3 タイムライン

- [[06_インシデントタイムラインの記録]]で整えたものを貼る。長すぎれば主要な出来事に絞り、詳細は付録へ。

### 3.4 原因と寄与要因

- **引き金**と**寄与要因**を分けて書く。引き金は 1 つでも、それが障害になった条件は複数ある（[[03_根本原因分析と寄与要因]]）。
- 人名を主語にしない（[[01_ポストモーテムとは]]）。

### 3.5 対応の評価

- 「**幸運だったこと**」の欄は重要です。「たまたま詳しい人が起きていた」「平日昼間だった」などは、次回は期待できない条件です。SRE 本の例でもこの欄が設けられています。

### 3.6 アクション

- 種類を分けると抜けが見えます。

| 種類 | 狙い | 例 |
|------|------|----|
| **予防** | 起きないようにする | 設定値のバリデーションを CI に追加 |
| **検知** | 早く気づく | 決済ブランド別のエラー率アラートを追加 |
| **緩和** | 起きても影響を小さく | 決済 SDK の更新を Feature Flag で段階公開 |
| **プロセス** | 手順・体制を直す | ランブックにロールバック手順を追記 |

- 担当者と期限のないアクションは書かない（[[04_再発防止アクションの管理]]）。

## 4. 書き終えたらのチェックリスト

- [ ] 概要だけ読んで何が起きたかわかる
- [ ] 影響が数字で書かれている
- [ ] 個人を責める表現がない
- [ ] 寄与要因が 2 つ以上ある（「ヒューマンエラー」だけで終わっていない）
- [ ] すべてのアクションに担当・期限・チケットがある
- [ ] 検知についてのアクションがある（監視の抜けはなかったか）
- [ ] 社内の誰でも読める場所に置いた
