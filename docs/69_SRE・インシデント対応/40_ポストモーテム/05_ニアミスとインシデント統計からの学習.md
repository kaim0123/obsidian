# ニアミスとインシデント統計からの学習

1 件ずつのポストモーテムに加えて、**大事に至らなかった事象（ニアミス）**や、**複数のインシデントを横に並べた傾向**からも多くを学べます。一方で、MTTR などの指標は使い方を誤ると、数字を良く見せるための行動を招きます。この章では、ニアミスの扱い方、インシデント統計の取り方と注意点、組織として学び続ける仕組みを整理します。

---

## 1. ニアミスとは

**ニアミス（Near miss）**は、障害になりかけたが、偶然や誰かの機転で利用者への影響が出なかった事象です。

| 例 | 何が防いだか |
|----|--------------|
| 本番 DB への誤った DELETE を、実行直前に気づいて止めた | 担当者の気づき |
| ディスク使用率が 98% に達したが、夜間バッチの終了で下がった | 偶然 |
| 証明書の期限切れ 2 日前に、別件の作業中に気づいて更新した | 偶然 |
| カナリアでエラーが出て、自動ロールバックされた | 仕組み（うまく働いた例） |

航空業界の安全研究で知られる**ハインリッヒの法則**（1 件の重大事故の背後に 29 件の軽微な事故と 300 件のヒヤリ・ハットがある）が示すように、ニアミスは大きな事故の**予兆**です。

### ニアミスを報告してもらうには

- **報告を歓迎する**：ニアミスの報告を褒める。非難すれば誰も報告しなくなる（[[01_ポストモーテムとは]]）。
- **書く負担を小さくする**：フル雛形ではなく、「何が起きかけたか・何が防いだか・何を変えるか」の 3 行でよい。
- **偶然に頼っていたものを探す**：「偶然助かった」は、次は助からない。

## 2. インシデント統計の指標

| 指標 | 意味 | 何がわかるか |
|------|------|--------------|
| **件数（SEV 別）** | 期間中のインシデント数 | 増減の傾向 |
| **MTTD** | Mean Time To Detect：発生から検知まで | 監視の良さ |
| **MTTA** | Mean Time To Acknowledge：アラートから応答まで | オンコールの応答性 |
| **MTTR** | Mean Time To Recover / Restore：検知または発生から復旧まで | 復旧の速さ |
| **MTBF** | Mean Time Between Failures：障害と障害の間隔 | 安定性 |
| **変更失敗率** | デプロイのうち障害を起こした割合（DORA メトリクス） | リリースの品質 |
| **アクション完了率** | 再発防止策が期限内に完了した割合 | 学習が行動になっているか |
| **検知経路** | アラート／問い合わせ／社内報告の比率 | 監視の抜け |

---

## 3. 指標の落とし穴

### 3.1 平均値はあてにならない

インシデントの長さは**ばらつきが非常に大きく**、少数の長時間の障害が平均を大きく動かします。Štěpán Davidovič の論文「Incident Metrics in SRE」（Google, 2021）は、MTTR のような平均値は件数が少ないと統計的にほとんど意味を持たず、改善したかどうかの判断に使えないことを示しています。

- 平均より**中央値やパーセンタイル**、**個別の事例**を見る。
- 四半期ごとの数字の上下で一喜一憂しない。

### 3.2 数字が目標になると歪む

グッドハートの法則（「指標が目標になると、良い指標でなくなる」）がそのまま当てはまります。

| 目標にした指標 | 起きがちな歪み |
|----------------|----------------|
| インシデント件数を減らす | 宣言しない、SEV を低く付ける |
| MTTR を短くする | 早すぎる収束宣言、再発を別件扱い |
| 変更失敗率を下げる | デプロイ頻度を下げる |

指標は**傾向を知るための材料**として使い、個人やチームの評価に直結させないのが原則です。

## 4. 横断的に見る：傾向分析

1 件ずつでは見えないパターンを、複数のポストモーテムを並べて探します。

| 観点 | 問い |
|------|------|
| **寄与要因の分類** | 「検証環境と本番の差」が何度も出ていないか |
| **発生源** | 特定のサービス・チーム・依存先に偏っていないか |
| **きっかけ** | デプロイ起因、設定変更起因、外部起因の比率は |
| **時間帯** | 深夜・週末・リリース日に集中していないか |
| **検知経路** | 問い合わせで気づくケースが多くないか |

四半期に 1 回、ポストモーテムの寄与要因にタグを付けて集計すると、**組織として投資すべき弱点**が見えてきます。

---

## 5. 学び続ける仕組み

- **ポストモーテム読書会**：月 1 回、社内外の良いポストモーテムを読む。Google SRE 本 16章でも、ポストモーテムの読み合わせや「今月のポストモーテム」の共有が紹介されています。
- **過去事例ライブラリ**：検索できる場所に集め、タグを付ける（91_トラブルシューティング事例集）。
- **新人のオンボーディング**：代表的なポストモーテムを読んでもらう。システムの弱点を知る近道。
- **ゲームデイで再現**：過去のインシデントを訓練シナリオにする（[[02_ゲームデイ]]）。
- **ランブックへの反映**：対応で得た手順を 50_障害タイプ別ランブックに書き戻す。
