# キューの種類 — FIFO / 優先度 / 遅延 / DLQ

## はじめに

「キュー」と一口に言っても、**用途に応じていくつかの種類** があります。一般的な「先入れ先出し」だけでなく、優先度や遅延、退避専用などのバリエーションがあり、それぞれ解決する問題が違います。

---

## 1. 標準キュー（Standard Queue）

### 特徴

- 最もシンプルな形式
- 入れた順にほぼ取り出されるが、**順序は厳密ではない**
- **スループット最大化** を優先

### いつ使う

- 順序が重要でないタスク（メール送信、サムネ生成等）
- 大量のメッセージを高速に処理したい

### 例

- Amazon SQS Standard Queue
- RabbitMQ の基本的なキュー

### 注意

- 稀にメッセージが重複することがある（at-least-once）
- 順序がズレる可能性を前提に設計する

---

## 2. FIFO キュー（First-In-First-Out）

### 特徴

- **厳密に入れた順** に取り出される
- **重複排除**（特定時間内の同一メッセージは1回のみ）
- スループットは標準キューより低い

### いつ使う

- 注文処理（順序が崩れると在庫計算が狂う）
- イベントソーシング
- 金融取引

### 例

- Amazon SQS FIFO Queue
- Kafka（パーティション単位で順序保証）

### 注意

- **グループ単位（MessageGroupId）で順序保証** されるのが一般的
- 全メッセージに同じグループIDを付けると、並列処理できず遅くなる
- ユーザーIDや注文IDでグループ化するのが定石

---

## 3. 優先度キュー（Priority Queue）

### 特徴

- メッセージに **優先度** を付けられる
- 高優先度のメッセージが先に取り出される

### いつ使う

- VIPユーザーのリクエストを先に処理
- 緊急のアラート通知
- 有料プランのジョブを無料プランより先に

### 例

- RabbitMQ の priority queue
- Redis Sorted Set を使った自作

### 注意

- **優先度インフレ**: みんな「高優先度」にすると意味がなくなる
- 低優先度メッセージが **永遠に処理されない**（starvation）リスク
- 優先度は 3〜5段階程度に絞るのが実用的

---

## 4. 遅延キュー（Delay Queue）

### 特徴

- 指定時間が **経過するまでメッセージが見えない**
- 例: 「30分後に処理」「明日9時に実行」

### いつ使う

- スケジュール通知（リマインダー）
- 課金処理の一定時間後
- 「カート放置24時間後のメール」
- リトライのバックオフ

### 例

- Amazon SQS の `DelaySeconds`
- RabbitMQ の dead-letter-exchange + TTL トリック

### 注意

- 遅延時間の精度は製品依存（秒単位〜分単位）
- 長期（1日以上）の遅延は別方式（スケジューラ）を検討

---

## 5. デッドレターキュー（DLQ / Dead Letter Queue）

### 特徴

- **処理に失敗したメッセージ** が送られる退避先
- 通常のキューと並行して必ず設置する

### いつ使う

- 一定回数（例: 5回）リトライしても成功しないメッセージを退避
- 後で手動で調査・再投入する

### 典型的なフロー

```
[メインキュー]
    ↓ 取り出し
[ワーカー] 処理失敗
    ↓ 失敗がN回続く
[DLQ] に移動 ← 開発者が後で調査
```

### なぜ必要か

- 不正なメッセージが **永遠にリトライされる** のを防ぐ
- 問題のあるメッセージを **隔離** して他の処理を止めない
- **何が失敗したか** を可視化する

→ 詳細は `DLQ_デッドレターキュー設計.md` 参照。

---

## 6. Pub/Sub（トピック / ファンアウト）

### 特徴

- **1つのメッセージを複数の Consumer に配る**
- キュー（1対1）とは対照的

### いつ使う

- 「注文が入った」イベントを、在庫・配送・メールなど複数サブシステムに通知
- ブロードキャストのイベント駆動

### 例

- Amazon SNS + SQS
- Google Pub/Sub
- Kafka の consumer group
- Redis Pub/Sub

→ 詳細は `Pub_Sub_vs_Queue.md`

---

## 7. ストリーム型（ログ型）

### 特徴

- メッセージが **時系列のログ** として保存される
- 取り出しても消えない（永続 / 指定期間保持）
- 複数 Consumer が **独立したオフセット** で読める

### いつ使う

- 大量イベントの蓄積・再処理
- 解析・データレイク
- マイクロサービス間のイベント駆動

### 例

- Apache Kafka
- Amazon Kinesis
- Redis Streams
- Apache Pulsar

### 従来キューとの違い

| 項目 | 通常キュー | ストリーム |
|------|-----------|-----------|
| メッセージの消費 | 取り出したら消える | ずっと残る |
| Consumer数 | 通常1人 | 何人でもOK |
| 再処理 | 原則不可 | 過去に戻って読める |
| 保存期間 | 短い（処理後削除） | 長い（日〜月） |

---

## 8. 一時キュー（Transient / Exclusive）

### 特徴

- 特定のクライアントが接続している間だけ存在
- 切断されたら消える

### いつ使う

- リクエストごとの一時的な応答受信
- RPC 的なパターン

### 例

- RabbitMQ の exclusive queue

---

## 使い分けの目安

| やりたいこと | 選ぶべきキュー |
|------------|---------------|
| メール送信・サムネ生成など並列処理 | **標準キュー** |
| 処理順を厳密に守る | **FIFO キュー** |
| VIPリクエストを先に | **優先度キュー** |
| 「30分後に実行」 | **遅延キュー** |
| 失敗メッセージの退避 | **DLQ** |
| 複数サブシステムに配る | **Pub/Sub** |
| 大量イベントの蓄積・解析 | **ストリーム型** |

---

## よくある組み合わせ

### 標準 + DLQ（最も基本）

```
[Standard Queue] → [Worker] → 成功
                     ↓ 失敗が3回
                   [DLQ]
```

ほぼすべてのキュー運用の基本形。

### Pub/Sub + 複数の標準キュー

```
      [SNS Topic]
      ↓      ↓       ↓
   [SQS-A] [SQS-B] [SQS-C]
    ↓        ↓       ↓
  [メール] [在庫]  [分析]
```

1つのイベントを別々のサブシステムに流す。

### 遅延 + 標準（リトライ用途）

```
[Worker] 失敗
  ↓
[Delay Queue (30秒)] → [Standard Queue] → [Worker] 再試行
```

失敗したら30秒後にリトライ、を実現。

### FIFO + グループ化

```
[FIFO Queue]
  │ MessageGroupId="user-1" → Consumer-A
  │ MessageGroupId="user-2" → Consumer-B
  │ MessageGroupId="user-1" → Consumer-A
```

ユーザー単位で順序保証、ユーザー間は並列。

## よくある勘違い

### 「FIFOキュー使えば順序は100%安全」

部分的に正しい。**同じ MessageGroupId 内では順序保証** だが、Producer 側で順番に投入しないと意味がない。並列 Producer では入れる時点で順序が崩れる可能性。

### 「優先度キュー使えば VIP 対応は完璧」

緊急用に予約されるはずだった「高優先度」が濫用され、すべて高優先度になっていく現象が起きやすい。**レートリミットとセット** で考える必要。

### 「DLQ に入ったらとりあえず再送」

原因を調べずに再送しても、また同じ場所で失敗する。**DLQ に入った理由を必ず調査**。

### 「Pub/Sub とキューは同じ」

違う。**キュー = 1対1（1つの Consumer が取る）**、**Pub/Sub = 1対多（全員に配る）**。

## まとめ

- **標準キュー**: 並列処理、順序ゆるい（多くの用途の基本）
- **FIFO キュー**: 厳密順序、グループ化でスケールも可
- **優先度キュー**: 優先処理、starvation 注意
- **遅延キュー**: 時間を指定して実行
- **DLQ**: 失敗メッセージの退避、**必ず設置**
- **Pub/Sub**: 1対多配信、複数サブシステム連携
- **ストリーム**: イベントログ、再処理可能、複数 Consumer
- 組み合わせて使うのが実務の常識（標準+DLQ、Pub/Sub+SQSなど）
