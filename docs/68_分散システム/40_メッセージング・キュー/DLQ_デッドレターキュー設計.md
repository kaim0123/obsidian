# DLQ（デッドレターキュー）設計

## はじめに

**DLQ（Dead Letter Queue / デッドレターキュー）** とは、

> **処理に失敗したメッセージを退避しておく専用のキュー**

のことです。**死んだ手紙の置き場所** ── つまり、「配達できなかった手紙」を一箇所に集めて、後で調査・再送できるようにする仕組みです。

メッセージキューを運用する以上、**DLQ は必須** と考えたほうが良い設計要素です。

---

## なぜ DLQ が必要か

### DLQ がない世界の悲惨な例

```
[Queue] → [Worker]
              ↓ 処理失敗
           リトライ
              ↓ また失敗
           リトライ
              ↓ また失敗
           リトライ（永遠に）
```

1つの「壊れたメッセージ」が **永遠にリトライされ続ける** と:

- 処理リソースを食い続ける
- 他のメッセージの処理を遅らせる
- ログが汚染される
- 外部API を叩くケースでは **攻撃的なトラフィック** になる

### DLQ がある世界

```
[Queue] → [Worker]
              ↓ 処理失敗（3回）
           [DLQ] に退避 → 後で人間が調査
              ↓
           Queue は次のメッセージへ
```

- 問題のメッセージを **隔離**
- 他の処理は継続
- **後で調査・再投入** できる

---

## DLQ に入る典型的なシナリオ

### 1. 不正なデータ

```json
{"user_id": "abc", "amount": "invalid"}
```

- 期待: `amount` は数値、`user_id` は数値
- どう頑張っても処理できない → DLQ へ

### 2. 依存先の永続的な問題

- 指定されたユーザーが DB に存在しない
- 外部API が認証エラーを返し続ける

### 3. バグの温床

- Consumer のコードにバグがあり、特定パターンで例外
- 一時的でなく、何度試しても同じ例外

### 4. Poison Message（毒メッセージ）

- 正しく見えるが、何らかの理由で処理が失敗し続ける
- キュー全体を止める危険がある

---

## 標準的な DLQ の仕組み

### 配信回数制限

キューは「このメッセージは何回配信されたか」を記録します。

```
[Queue] → 1回目配信 → 失敗
       → 2回目配信 → 失敗
       → 3回目配信 → 失敗
       → maxReceiveCount 到達
       → [DLQ] へ移動
```

製品ごとの設定:
- SQS: `maxReceiveCount`（デフォルトなし、明示必要）
- RabbitMQ: `x-dead-letter-exchange` + `max-delivery-count`
- Kafka: 自前実装 or Confluent Dead Letter Queue

### Visibility Timeout（可視性タイムアウト）

Consumer が「処理中」と宣言している間、メッセージは他の Consumer から見えない。
タイムアウト内に ACK できないと、**「失敗扱い」で再配信**。

```
Consumer が取り出し → Visibility Timeout 30秒
    ↓ 処理が30秒超えた
    ↓
他の Consumer から再び見える → 再配信
    ↓ 何度も失敗
    ↓
maxReceiveCount 超 → DLQ
```

## DLQ の設計ポイント

### 1. maxReceiveCount をちゃんと設定

**最重要**。設定がないと DLQ は機能しない。

- 多すぎ（10+）: 壊れたメッセージが長く残って負荷を生む
- 少なすぎ（1〜2）: 一時的なエラー（DB切断等）で即 DLQ 入り → 正常データが DLQ に流れ込む

**目安**: 3〜5回

### 2. 必ず DLQ を **監視** する

DLQ は「作って終わり」ではない。**メッセージが溜まったら検知** する仕組みが必要:

- CloudWatch / Datadog 等でメトリクス監視
- 「DLQ のメッセージ数 > 0 が N 分続いたら Slack 通知」

**監視のない DLQ はゴミ箱**。溜まったメッセージに誰も気づかず、ビジネス影響が出てから判明する。

### 3. DLQ メッセージの保持期間

- SQS: デフォルト4日、最大14日
- RabbitMQ: 設定次第
- 短すぎ: 休暇中に失われる
- 長すぎ: 古いメッセージを再投入すると他のデータと整合性が崩れる

**目安**: 最低14日（調査時間を確保）。

### 4. 情報を残す

DLQ に送られるメッセージは、**失敗理由が分からない** と調査できません。
できれば:
- 最後のエラーメッセージ
- リトライ回数
- タイムスタンプ
- スタックトレース

を **メッセージ属性** or **別テーブル** に記録。

## DLQ の運用フロー

### 日常

```
1. DLQ のメッセージ数を監視
2. 0 件なら OK
3. 増えたらアラート → 即調査
```

### 調査手順

```
1. DLQ の中身を確認（1〜数件サンプリング）
2. なぜ失敗したか特定
   - データの問題? → データ修正 or ルール修正
   - コードの問題? → バグ修正
   - 外部依存の問題? → 依存先を調査
3. 問題修正後、メッセージを再投入（可能なら）
4. 再発防止策を検討（バリデーション強化、モニタリング改善など）
```

### 再投入

**自動再投入はしない** のが鉄則（失敗の原因が残っていれば即 DLQ に戻る）。

手動で:
- コンソール GUI から操作
- CLI スクリプト（`aws sqs start-message-move-task` 等）
- 自前の再投入ツール

## よくあるアンチパターン

### 1. DLQ を設定していない

「うちは安定してるから」は甘え。**どんなシステムも壊れる**。

### 2. maxReceiveCount が大きすぎ

```
maxReceiveCount = 100
```

→ 壊れたメッセージが 100 回処理試行 → 100 回エラーログ → 100 回外部API叩く。
**3〜5が目安**。

### 3. DLQ を監視していない

「溜まってから気づく」では遅い。**アラートは必須**。

### 4. DLQ を自動再投入している

```
DLQ にメッセージが入ったら、10分後に元キューに戻す（自動）
```

→ 無限ループ。DLQ が意味をなさなくなる。

### 5. DLQ 自体の DLQ を設定していない

`DLQ` でも設定ミスがあれば、**メッセージがロスト** することが。
→ DLQ にも十分な保持期間を設定。

### 6. Poison Message がキュー全体を止める

DLQ がないと、**同じメッセージで全 Consumer が繰り返し失敗** して、スループットが壊滅する。

## 製品別の具体例

### Amazon SQS

```
[メインキュー] (maxReceiveCount=3)
       ↓ 3回失敗
[DLQ] (保持期間14日)
       ↓ 監視
CloudWatch Alarm → SNS → Slack
```

### RabbitMQ

- `x-dead-letter-exchange`: エラー時の exchange を指定
- `x-dead-letter-routing-key`: どのキューに送るか

### Kafka

Kafka 自体に DLQ の概念はない。**アプリ側で DLQ トピックを作って、失敗時に publish する** 実装。

### Redis

同様にアプリレベルで DLQ を実装する必要あり。

## DLQ の先にある考え方

### リカバリテーブル

DLQ のメッセージを、**DB のテーブルに移して管理** するパターン。

```sql
CREATE TABLE failed_events (
    id UUID PRIMARY KEY,
    message JSONB,
    error_text TEXT,
    created_at TIMESTAMP,
    status TEXT  -- 'pending', 'analyzed', 'reprocessed', 'discarded'
);
```

メリット:
- 検索・分析しやすい
- 管理画面で一覧できる
- 大量の失敗を整理しやすい

## まとめ

- DLQ は **失敗メッセージの退避先**
- **キュー運用に DLQ は必須** と考える
- `maxReceiveCount` は **3〜5** が目安
- DLQ は **監視とアラート** とセットで機能する
- **自動再投入はしない**（調査→修正→手動再投入）
- 失敗理由が追跡できる情報を残す
- 保持期間は十分長く（最低14日）
- Poison Message からシステム全体を守る防波堤
