# 再試行とバックオフ

## はじめに

分散システムでは **一時的な失敗** が日常的に発生します:

- ネットワークの瞬断
- DB の一時的な高負荷
- 外部 API のタイムアウト
- デプロイ中のごく短い接続失敗

これらは **少し待ってから再実行すれば成功する** ことが多いため、**自動リトライ（再試行）** を設計することが重要です。ただし、何も考えずにリトライすると、**障害を悪化させる** ことがあります。

---

## リトライすべき理由

### 一時的エラー（Transient Error）の吸収

```
ネットワーク瞬断（100ms）
    ↓ 失敗を人間に返す?
    ↓ もう一度試せば成功するのに?
```

→ **自動リトライで吸収** する方が、ユーザー体験も成功率も改善。

### 分散システムの現実

「99.9% 稼働」の依存先が3つあると、全体の成功率は `0.999^3 = 99.7%`。
リトライなしでは **1000回に3回失敗** する計算。

---

## リトライのリスク

### 1. 「リトライの嵐」（Retry Storm）

```
大量のクライアントが同時にリトライ
    ↓
依存先サーバーに一斉に再リクエスト
    ↓
さらに過負荷で全滅
    ↓
復旧が遅れる
```

### 2. 重複処理

```
API 呼び出し → タイムアウト
    ↓ 本当は成功してた（応答だけ届かなかった）
    ↓ リトライ
    ↓ 2回処理された → 2回課金
```

→ 冪等性の設計と組み合わせる必要。

### 3. 永遠にリトライ

本質的に成功しないエラー（400 Bad Request など）をリトライしても意味がない。

---

## リトライ戦略

### 1. Fixed Interval（固定間隔）

毎回同じ間隔で再試行:

```
1秒 → 1秒 → 1秒 → 1秒 → ...
```

**長所**: シンプル
**短所**: 障害を悪化させる（みんな同時に叩く）
**用途**: あまり推奨されない

### 2. Linear Backoff（線形バックオフ）

間隔を段々長くする:

```
1秒 → 2秒 → 3秒 → 4秒 → ...
```

**長所**: 少しマシ
**短所**: 依存先が長時間ダウンだと待ちが足りない

### 3. Exponential Backoff（指数バックオフ）

間隔を指数的に伸ばす:

```
1秒 → 2秒 → 4秒 → 8秒 → 16秒 → ...
```

**最も推奨される基本戦略**。
- 早期は早く再試行（一瞬の問題を素早く解消）
- 継続失敗時は長時間待つ（依存先に負荷をかけない）

### 4. Jitter（ジッター / ランダム揺らぎ）

```
[計算された待ち時間] + [ランダム揺らぎ]
```

例: Exponential Backoff に 0〜1秒のランダム追加:

```
1秒+0.3秒 → 2秒+0.7秒 → 4秒+0.1秒 → ...
```

**なぜ必要か**: 全クライアントが**同じ時刻**にリトライすると、サーバー側が一斉に押し寄せられる。**ランダム化で時間分散**。

**実務での推奨**: Exponential Backoff + Jitter が標準。

---

## リトライ対象の見極め

### ◯ リトライすべき（一時的エラー）

| エラー | 原因 |
|--------|------|
| Connection Timeout | ネットワーク瞬断 |
| 503 Service Unavailable | 一時的過負荷 |
| 504 Gateway Timeout | 依存先の一時遅延 |
| 429 Too Many Requests | レートリミット（Retry-After 尊重） |
| DB deadlock | ロック競合 |

### ✕ リトライしてはいけない（永続的エラー）

| エラー | 原因 |
|--------|------|
| 400 Bad Request | リクエストが不正（永遠に失敗） |
| 401 Unauthorized | 認証情報が無効 |
| 403 Forbidden | 権限がない |
| 404 Not Found | リソースが存在しない |
| DB UNIQUE violation | データの論理的矛盾 |

**4xx は基本リトライしない（429/408を除く）、5xxはリトライ候補** が目安。

---

## リトライ回数の上限

永遠にリトライせず、**最大回数を設定**:

| 用途 | 推奨回数 |
|------|---------|
| HTTPクライアント | 3回 |
| キュー Consumer | 3〜5回（超えたら DLQ） |
| 決済処理 | 慎重に（冪等性必須） |
| バッチ再実行 | 5〜10回 |

## 実装例（疑似コード）

### Python（exponential backoff + jitter）

```python
import random
import time

def retry_with_backoff(fn, max_retries=5):
    for attempt in range(max_retries):
        try:
            return fn()
        except TransientError as e:
            if attempt == max_retries - 1:
                raise
            # exponential backoff + jitter
            base = 2 ** attempt  # 1, 2, 4, 8, 16秒
            jitter = random.uniform(0, 1)
            wait = base + jitter
            time.sleep(wait)
        except PermanentError:
            raise  # リトライしない
```

### ライブラリを使う

- **Python**: `tenacity`, `backoff`
- **JavaScript**: `p-retry`, `axios-retry`
- **Go**: `cenkalti/backoff`
- **Java**: `Resilience4j`

車輪の再発明せず、**実績あるライブラリを使う** のが推奨。

## Retry-After ヘッダの尊重

HTTP レスポンスに `Retry-After` がある場合、**その時間を必ず尊重**:

```
HTTP/1.1 429 Too Many Requests
Retry-After: 60
```

→ 60秒待ってからリトライ。勝手に短縮するとレートリミットに引っかかり続ける。

## リトライとタイムアウトの関係

```
Client
  → Server A (タイムアウト 10秒)
      → Server B (タイムアウト 8秒)
          → DB (タイムアウト 5秒)
```

**内側のタイムアウト > 外側のタイムアウト だと悲惨**。
外側が切れてもサーバーが動き続け、**ユーザー側は失敗と思うが実は成功してる** という状況が起きる。

**原則**: 内側のタイムアウト < 外側のタイムアウト（ネストするほど短く）。

---

## リトライの副作用: 冪等性

### リトライ = 同じ処理を複数回

```
1回目: 送信（成功）→ 応答がネットワークで消える
         ↓ タイムアウト判定
2回目: 送信（また成功）→ 2重に処理される
```

→ **処理が冪等でないと、リトライするほど状態が壊れる**。

解決策:
- **Idempotency Key**: `{"key": "abc-123"}` を毎回送り、サーバー側で重複検出
- **UPSERT**: 既存なら上書き、なければ作成
- **状態マシン**: 「次の状態」が同じなら何度でも OK

---

## サーキットブレーカーとの組み合わせ

```
依存先が死んでる
    ↓
何度リトライしても失敗
    ↓
サーキットブレーカーが「一時的に諦める」
    ↓
ヘルスチェックが復活したら再開
```

- リトライ = 短期の失敗に強い
- サーキットブレーカー = 長期の失敗に強い
- **両方を組み合わせる** のが現実解

---

## キュー Consumer のリトライ

### 遅延キューを使ったリトライ

```
[Main Queue] → [Worker] 失敗
                  ↓
              [Delay Queue (30秒)] → 30秒後に [Main Queue] へ再投入
```

キュー製品の機能で実現:
- SQS: Visibility Timeout 延長 or 遅延キュー
- RabbitMQ: DLX + TTL

### 段階的バックオフ

```
1回目失敗 → 1分後再配信
2回目失敗 → 5分後再配信
3回目失敗 → 15分後再配信
4回目失敗 → DLQ へ
```

## よくある落とし穴

### 1. リトライループが無限

- max_retries を設定しないと永遠。必ず上限を。

### 2. 429 を高速リトライ

- レートリミットに引っかかった状態で即リトライしても同じ結果。
- `Retry-After` を尊重する。

### 3. 同期処理の中で何回もリトライ

- 全体のタイムアウトを超えてしまう。
- 同期なら1〜2回、多ければ非同期化。

### 4. Jitter を入れない

- 複数サービスが一斉に同じタイミングでリトライ → 依存先を殺す（Thundering Herd）。

### 5. すべてのエラーをリトライ

- 4xx までリトライすると、永遠に失敗するメッセージが出続ける。

## まとめ

- 一時的エラーはリトライで吸収、永続的エラーはしない
- **Exponential Backoff + Jitter** が標準
- リトライ回数は 3〜5 回が目安
- **冪等性** と組み合わせて初めて安全
- `Retry-After` は必ず尊重
- 内側のタイムアウトを短く（入れ子関係）
- 定番ライブラリを使う（`tenacity` / `p-retry` / etc.）
- キュー Consumer では遅延キューで段階的バックオフ
- サーキットブレーカーと組み合わせるとさらに堅牢
