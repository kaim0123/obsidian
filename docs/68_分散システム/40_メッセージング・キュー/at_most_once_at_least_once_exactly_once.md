# 配信保証 — at-most-once / at-least-once / exactly-once

## はじめに

メッセージキューには **「メッセージが何回届くか」の保証レベル** があります。これを理解せずに使うと:

- メール送信が重複して届く
- 決済が二重に処理される
- ユーザーデータが失われる

といった事故が起きます。**3つの保証レベル** と、その現実を整理します。

---

## 3つの保証レベル

### 1. At-most-once（多くても1回 / アットモストワンス）

> メッセージは **最大1回** 配信される。**ロスはあり得る**、重複はなし。

```
送信 → [Queue] → 受信 → 処理
          ↓失敗
       メッセージ消失（再送しない）
```

**特徴**: 信頼性 < スピード
**使いどころ**: テレメトリ、ログ統計、ロスしても困らないデータ

**例**:
- 計測値（CPU使用率をサンプリング、1つロスしても全体で困らない）
- UDPでのログ送信

---

### 2. At-least-once（少なくとも1回 / アットリーストワンス）

> メッセージは **最低1回は確実に** 配信される。**重複が発生しうる**。

```
送信 → [Queue] → 受信 → 処理 → ACK
                                 ↑失敗すると再送される
                                   → 2回処理されることも
```

**特徴**: 信頼性は高いが **重複の可能性あり**
**使いどころ**: ほぼすべての実用ケース（+ 冪等性で重複を吸収）

**例**:
- ECサイトの注文後処理
- 通知メール送信（ただし冪等性対策必須）
- データのETL

**ほとんどの商用キュー（SQS標準、Kafka、RabbitMQ）はこれ。**

---

### 3. Exactly-once（ちょうど1回 / エグザクトリーワンス）

> メッセージは **確実に1回だけ** 配信・処理される。ロスも重複もなし。

```
送信 → [Queue] → 受信 → 処理 → ACK
   （重複検出・排除機構付き）
```

**特徴**: 理想の世界だが、**実現コストが極めて高い**
**使いどころ**: 金融取引、在庫の厳格管理

**例**:
- 銀行口座の残高更新
- 株取引の約定処理

---

## なぜ exactly-once は難しいのか

分散システムでは、**2つのノードの状態を「完全に一致」させるのは非常に困難** です。

### 問題1: ACK 応答が届かない

```
Consumer → 処理成功 → ACK 送信中にネットワーク切断
   ↓
Queueは「処理されたか」分からない
   ↓
再送 → 2回目の処理（重複）
```

### 問題2: Producer のリトライ

```
Producer → メッセージ送信 → タイムアウト
         → 「届いてないかも」と再送
           → 実は届いていた → 2重に入る
```

### 実際にやること

- **「Queue 内で重複排除」+「Consumer 内で冪等処理」**の組み合わせ
- これを「Effectively-once」や「Exactly-once semantics」と呼ぶ製品も多い

つまり **真の exactly-once は技術的にほぼ不可能**。「実質的に1回」を**アプリ側で作る** のが現実解。

---

## どの保証を選ぶか

| 要件 | 選ぶべきレベル |
|------|--------------|
| ロスしても全体で困らない | at-most-once |
| 失敗は困る、重複は扱える | **at-least-once**（デフォルト選択） |
| 絶対に1回だけ必要（金融等） | exactly-once を目指す設計（実際は at-least-once + 冪等性） |

### 現実的な推奨

> **at-least-once + 冪等性** の組み合わせが、99% のケースで正解

## 冪等性で at-least-once を救う

冪等性（idempotency）とは:

> **同じ操作を何度やっても結果が同じになる性質**

### 冪等な処理の例

```python
# ◯ 冪等
def set_user_email(user_id, email):
    db.update({"user_id": user_id}, {"email": email})
    # 10回実行しても結果は同じ

# ✕ 冪等でない
def increment_counter(user_id):
    db.update({"user_id": user_id}, {"count": count + 1})
    # 10回実行したら +10 される
```

### 冪等化のパターン

1. **UPSERT**（なければ作る、あれば更新）
2. **Idempotency-Key** を使って「このキーは処理済み」を記録
3. **状態チェック**（"processed" 状態ならスキップ）

→ 詳細は `../冪等性/` フォルダ参照。

| 製品 | デフォルトの保証 | 備考 |
|------|-----------------|------|
| **Amazon SQS 標準** | at-least-once | 稀に重複 |
| **Amazon SQS FIFO** | exactly-once 的（重複排除5分窓） | 本当に1回 |
| **Kafka** | at-least-once | 設定で exactly-once 可（追加コスト） |
| **RabbitMQ** | at-least-once（デフォルト） | at-most-once にも設定可 |
| **Redis Streams** | at-least-once | |
| **Google Pub/Sub** | at-least-once | exactly-once サブスク機能あり |

## 設計パターン

### パターン1: 冪等なAPI + at-least-once キュー

```
[Producer] → [At-least-once Queue] → [Consumer]
                                      ↓
                                   冪等な処理（重複OK）
```

最もシンプル。Consumer 側で重複を吸収。

### パターン2: Idempotency Key

```
Producer が UUID を付与:
{"idempotency_key": "abc-123", "amount": 1000, ...}
        ↓
Consumer: DB に「abc-123 は処理済み」を記録
  → 2回目は気付いてスキップ
```

### パターン3: DB のユニーク制約

```sql
CREATE TABLE processed_events (
    event_id UUID PRIMARY KEY  -- UNIQUE制約
);
```

2回目の INSERT は UNIQUE 違反で失敗 → スキップ判定。

### パターン4: 状態マシン

```
注文 = [pending] → [paid] → [shipped] → [delivered]

「shipped → shipped」のメッセージが来たら無視
```

**現在の状態と次の状態を照らして、冪等に処理**。

## 落とし穴

### 1. 「重複しません」という製品ドキュメント文言を過信

厳密には「重複排除機能あり」「重複なしを最善努力」程度。
**必ず冪等性を担保する** のが安全。

### 2. at-most-once の過小評価

「どうせほとんど届くでしょ」と思って使うと、少量でも確実に起きる欠損で事故る。ログなら良いが、ビジネスデータには不向き。

### 3. exactly-once の「魔法」を期待

「Exactly-Once Semantics」対応製品でも、**Consumer 側のコードが冪等でなければ破綻**。「製品任せ」は危険。

### 4. タイムアウトとリトライの設計ミス

- Visibility Timeout（SQSの例）が短すぎると、処理中に再配信される
- Consumer の処理時間 + 余裕 を持たせる

## よくある質問

### Q. 実質的に exactly-once は無理?

A. **分散システムの2ノード間で完全な一致を保証するのは理論的に困難**（FLP不可能性）。
現実には「Queue + Consumer の組み合わせで実質1回」を作る。

### Q. SQS FIFO なら安心?

A. 5分間の **重複排除ウィンドウ** 内なら本当に1回。
ただしウィンドウ外（5分後の再送など）では重複する可能性あり。

### Q. Kafka の exactly-once モードって何?

A. トランザクションAPI + Idempotent Producer で、**Kafka 内部では exactly-once**。
ただし **Consumer の副作用（DB書き込み等）は別問題**。

## まとめ

- **at-most-once**: 最大1回、ロスあり（ログ・計測）
- **at-least-once**: 最低1回、重複あり（**実務のデフォルト**）
- **exactly-once**: 1回だけ、実現困難（金融等）
- **真の exactly-once は分散システムでは理論的に困難**
- 現実的には **at-least-once + 冪等性** が 99% の正解
- 冪等性は **UPSERT / Idempotency-Key / UNIQUE制約 / 状態マシン** で実現
- 「製品の exactly-once 機能」を過信せず、Consumer 側でも冪等化
