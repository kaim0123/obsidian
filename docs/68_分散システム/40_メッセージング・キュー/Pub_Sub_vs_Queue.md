# Pub/Sub vs Queue — 配信モデルの違い

## はじめに

「非同期メッセージング」と呼ばれるものには、**2つの根本的に異なる配信モデル** があります:

- **Queue（キュー）**: 1つのメッセージを **1つの Consumer だけ** が受け取る
- **Pub/Sub（パブリッシュ/サブスクライブ）**: 1つのメッセージを **複数の Subscriber すべて** が受け取る

この違いを理解せずにツールを選ぶと、「メール送信が全員分×サブスクライバー数 飛ぶ」や「どのワーカーも受け取らない」みたいな事故が起きます。

---

## モデルの違い

### Queue（キュー / Point-to-Point）

```
[Producer]
    ↓ メッセージを送る
[Queue]
    ↓
┌──────┬──────┬──────┐
▼      ▼      ▼      ▼
[W1]  [W2]  [W3]  ← 1つのメッセージはどれか1人だけが受け取る
```

- Consumer が何人いても、**1メッセージは1回だけ処理される**
- 負荷分散用途に向く
- 例: 「画像ID 123 のサムネを作る」→ W1 が処理したら、W2/W3 には来ない

### Pub/Sub（パブリッシュ/サブスクライブ）

```
[Publisher]
    ↓ メッセージを送る
[Topic]
    ↓
┌──────┬──────┬──────┐
▼      ▼      ▼      ▼
[S1]  [S2]  [S3]  ← 全員が同じメッセージを受け取る
```

- Subscriber が3人いたら、**同じメッセージを3人全員が受け取る**
- 通知・ブロードキャスト用途に向く
- 例: 「注文が入った」→ 在庫・決済・メール 3サブシステム全員に通知

---

## 具体例で違いを掴む

### シナリオ: サムネイル画像生成

**Queue モデル**:
```
アップロード → [Queue] → ワーカー5台のうち、1台だけが処理
```

ワーカーは5台立ち上げるが、**1つの画像は1回だけ処理される**。負荷分散。

**Pub/Sub モデルだと誤動作**:
```
アップロード → [Topic] → ワーカー5台全員が受信
                         → 同じ画像を5回処理（事故）
```

### シナリオ: 注文イベントの配信

**Queue モデルだと不足**:
```
注文 → [Queue] → 在庫ワーカー
            ↓
        でもメールや分析は？
```

**Pub/Sub モデルが正解**:
```
注文 → [Topic] → [在庫サブシステム]
              → [メールサブシステム]
              → [分析サブシステム]
              → [配送サブシステム]
```

全員が同じイベントを受け取り、それぞれの処理をする。

## キーワード対応表

| モデル | 送信者の呼称 | 受信者の呼称 | 箱の呼称 |
|--------|-------------|-------------|---------|
| Queue | Producer | Consumer | Queue |
| Pub/Sub | Publisher | Subscriber | Topic |

ツールによって呼び方が違うので慣れが必要:

| ツール | Queue的 | Pub/Sub的 |
|--------|--------|-----------|
| Amazon | SQS | SNS |
| RabbitMQ | Queue | Exchange + Queue |
| Kafka | Consumer Group | 複数 Consumer Group |
| Redis | List / Streams | Pub/Sub channel |
| GCP | Pub/Sub（両方） | Pub/Sub |

## Kafka の consumer group という折衷案

Kafka では **Consumer Group** という仕組みで、Queue と Pub/Sub を使い分けます。

```
Topic [order_events]
    ↓
Consumer Group A (メール)
  └─ Worker1 ←─┐
  └─ Worker2 ←─┤ Group A 内では Queue 動作（1メッセージ1人）
  └─ Worker3 ←─┘

Consumer Group B (分析)
  └─ Worker1 ←── Group B も別で同じメッセージ受信（Pub/Sub 動作）
```

- **同じ Group 内**: Queue（並列処理）
- **異なる Group 間**: Pub/Sub（全 Group が受信）

AWS なら「SNS + SQS を組み合わせる」のが同じ効果を生む。

## よくある構成パターン

### SNS + SQS（AWS の定番）

```
[API] → [SNS Topic] ──┬──→ [SQS-メール] → メールワーカー
                      ├──→ [SQS-分析]  → 分析ワーカー
                      └──→ [SQS-検索]  → インデクサ
```

- SNS で **Pub/Sub**（トピックに流す）
- SQS で **Queue**（サブシステム内の並列処理）

→ **Pub/Sub の柔軟性 × Queue の確実性** を両立。

### Kafka + Consumer Group

```
Topic [events]
   ↓
  Group "mailer"   (Queue 動作、並列)
  Group "analytics" (Queue 動作、並列、別ストリーム)
  Group "search"    (Queue 動作、並列、別ストリーム)
```

同じく柔軟。

## 使い分けのガイド

### Queue を選ぶとき

- **タスク処理** の並列化
- 1つのジョブは1回だけ実行したい
- サムネ生成、メール送信、バッチ処理、決済処理
- 成功/失敗を1対1で追跡したい

### Pub/Sub を選ぶとき

- **イベント通知** の配布
- 複数サブシステムが同じイベントに興味あり
- 「注文が入った」「ユーザーが登録した」
- 将来、新しいサブシステムが増える可能性がある

### 両方を組み合わせるとき

- 大きなシステム
- 「通知 × 並列処理」が必要
- SNS + SQS、Kafka Consumer Group で実現

---

## 落とし穴

### 1. Queue で複数サブシステムに配りたくなって「複製して送る」

```
API → [Queue-A (メール)]
API → [Queue-B (分析)]
API → [Queue-C (検索)]
```

これは「**送信側に受信側の知識がある**」= 疎結合の崩壊。
Pub/Sub モデルにすれば API 側は1つのトピックに流すだけで済む。

### 2. Pub/Sub で「1つの Subscriber だけに来てほしい」と思ったら Queue

Pub/Sub で「1人だけに届けたい」は設計ミス。要求が Queue。

### 3. Kafka で Consumer Group を理解せず、1人しか処理されない

Kafka では、**Consumer Group を指定しないと同じグループ扱い**。
複数アプリで同じイベントを受けたいなら、**Group 名を変える**。

### 4. Fan-out しすぎて管理不能

Pub/Sub は便利だが、「何個のサブシステムが受けてるか」を把握しないと、あとで壊したときに影響範囲が読めない。

---

## 他方式との比較

| 方式 | モデル | いつ使うか |
|------|-------|-----------|
| Queue | 1対1 | 並列タスク処理 |
| Pub/Sub | 1対多 | イベント通知 |
| RPC（直接呼び出し） | 同期1対1 | 即レスポンスが必要 |
| Webhook | 1対1（HTTPベース） | 外部への通知 |
| WebSocket | 1対1（双方向） | リアルタイム通信 |

## 選択の意思決定フロー

```
そのメッセージを誰が処理する？
│
├── 1つのワーカーだけ（誰がやるかは問わない）
│       → Queue
│
├── 複数のサブシステム（それぞれ違う目的）
│       → Pub/Sub
│
└── 同じサブシステム内で並列処理したいが、複数サブシステムにも配りたい
        → Pub/Sub + Queue（SNS + SQS / Kafka Consumer Group）
```

## まとめ

- **Queue = 1対1、Pub/Sub = 1対多**
- Queue は **タスク処理** に向く（サムネ生成、メール送信）
- Pub/Sub は **イベント通知** に向く（注文が入った、ユーザー登録）
- AWS なら **SNS + SQS** の組み合わせが定石
- Kafka は **Consumer Group** で両方の動きを使い分ける
- 「複数サブシステムに送るから Queue を複製」は疎結合の崩壊
- 選択の軸は「**1メッセージは1回だけ処理？ それとも全員に届く？**」
