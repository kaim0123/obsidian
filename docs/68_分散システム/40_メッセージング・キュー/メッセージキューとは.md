# メッセージキューとは — 非同期処理の基本形

## はじめに

**メッセージキュー（Message Queue）** とは、

> アプリケーション同士が **直接やり取りせず、「箱」を介して非同期にメッセージを渡す仕組み**

です。「後でやっておくタスク」をキュー（待ち行列）に入れておき、別のプログラムがそれを取り出して処理する、というパターンです。

---

## イメージ

### 直接呼び出し（同期処理）

```
[Web API] ──呼び出し──▶ [メール送信機能]
         ◀───完了───
```

- API はメール送信が終わるまで待つ
- メールサーバが遅いと API も遅くなる
- メールサーバが死んでいると API も失敗する

### メッセージキュー経由（非同期処理）

```
[Web API] ──投入──▶ [キュー] ──取り出し──▶ [メール送信ワーカー]
         ◀即OK───
```

- API は **メッセージをキューに入れるだけ** で終わり
- 別プロセスのワーカーがあとで取り出して実行
- メールサーバが遅くても、API の応答は速い

---

## なぜキューが必要か

### 1. 応答速度の改善

「ユーザー登録 → ウェルカムメール送信 → DB記録 → 分析基盤に通知」
をすべて同期でやると、ユーザーは5秒待たされる。
**重要な処理（DB記録）だけ同期**、他（メール・通知）はキューに流すと、応答は 200ms で返せる。

### 2. 結合度を下げる

- API は「メッセージを投げる」だけ知っていればいい
- どのワーカーが処理するか、何台あるかは意識不要
- **依存方向が減る** = システムが柔軟になる

### 3. 負荷の吸収（バッファ）

- 秒間1万件のリクエストが来ても、DB書き込みは秒間千件しか捌けない
- キューに一旦入れて、**ワーカーが自分のペースで処理**
- ピークを「均す」効果

### 4. 障害の隔離

- メールサーバが落ちても、メッセージはキューに残る
- 復旧したら続きから処理できる
- **データのロス防止**

### 5. スケーラビリティ

- 処理が追いつかなければ **ワーカーを増やす**
- キュー製品自体もクラスタ化でスケールする

## 基本要素

```
  Producer (生産者)              Queue                Consumer (消費者)
┌──────────────┐            ┌──────────┐            ┌──────────────┐
│ Webアプリ    │──Publish──▶│ Msg1 Msg2│──Consume──▶│ ワーカー     │
│ (メッセージ  │            │ Msg3 Msg4│            │ (メッセージを│
│  を入れる側) │            │ ...      │            │  取り出す側) │
└──────────────┘            └──────────┘            └──────────────┘
```

### Producer（プロデューサー / 生産者）

メッセージを **キューに入れる** 側。API サーバー、バッチ処理など。

### Queue（キュー）

メッセージを **一時的に溜めておく箱**。製品として RabbitMQ、SQS、Kafka などがある。

### Consumer（コンシューマー / 消費者）

メッセージを **取り出して処理する** 側。「ワーカー」とも呼ぶ。

### Message（メッセージ）

渡される単位のデータ。典型的には JSON で `{"user_id": 123, "action": "send_welcome_email"}` のような中身。

---

## メッセージの典型的な流れ

```
1. Producer がメッセージを作る
   {"event": "user_signed_up", "user_id": 123}

2. キューに Publish
   API は即座に 200 OK を返す

3. Consumer がキューから取り出す (Receive / Pull)

4. Consumer が処理を実行
   - メール送信
   - 統計DB に書き込み

5. 成功したら ACK（確認応答）をキューに返す
   → キューからメッセージ削除

6. 失敗したら NACK（または無応答）
   → キューに残る / DLQ へ送られる
```

## 具体例

### ケース1: ECサイトの注文処理

```
ユーザー「購入」ボタン
    ↓
[API] → DB に注文保存（同期）
    ↓ 即座に 200 返す
    ↓
[キュー] ← 「注文ID 456 の後処理」メッセージ投入
    ↓
┌─────────────┬─────────────┬─────────────┐
▼             ▼             ▼             ▼
[在庫減算]  [メール送信]  [決済確定]   [配送手配]
```

ユーザーを待たせるのは DB 保存だけ。残りはキュー経由で非同期に。

### ケース2: 画像アップロード

```
[Web] アップロード
    ↓
[API] ファイル保存（同期）
    ↓
[キュー] に「画像ID 789 のサムネ生成」投入
    ↓ 即座にレスポンス
    ↓
[ワーカー] が取り出して ImageMagick で処理
    ↓ 10秒かかってもユーザーは待ってない
```

### ケース3: 監査ログ

```
[API] → 毎リクエストごとに [キュー] に「監査イベント」投入
              ↓ API 応答はブロックしない
              ↓
        [ログ集約ワーカー] → Elasticsearch
```

## キュー vs 「DB + cron」

「DB のテーブルにタスクを書いておいて、cron で処理する」という **自作キュー** もよく使われます。

| 観点 | メッセージキュー | DB + cron |
|------|-----------------|-----------|
| 遅延 | ほぼ即時 | 次の cron 起動まで待つ（数分〜） |
| 並列処理 | 複数 Consumer が自然に動く | 手動で制御必要 |
| 配信保証 | at-least-once 等を選べる | 自作する必要あり |
| 運用 | 専用プロダクトが必要 | DB 一本で済む |
| 向き | リアルタイム系 | バッチ系 |

小規模なら DB + cron で十分。**スケール or 即時性が必要になったらキュー** へ。

## 注意点・落とし穴

### 1. 重複配信が起きうる

後述の `at-most-once_at-least-once_exactly_once.md` の通り、ほとんどのキューは **at-least-once** = 「少なくとも1回届く（= 複数回届く可能性あり）」。
→ **冪等性**（何度処理しても結果が同じ）を Consumer 側で担保する必要がある。

### 2. 順序は保証されないことが多い

複数 Consumer が並列で処理するため、メッセージの到着順 ≠ 処理完了順。
順序が必須なら FIFO キュー / Kafka のパーティションを使う。

### 3. 「とりあえず非同期にしよう」で失敗する

- 本当に非同期にしていいか？（ユーザー待ちの処理を非同期にしても体感は変わらない）
- 失敗したらどう気付くか？（非同期は失敗が見えにくい）
- DLQ（エラー退避）の設計はしてあるか？

### 4. デバッグが難しい

- 処理が複数プロセスに分散する
- ログ追跡に **相関ID** が必須
- トレース基盤（OpenTelemetry 等）との統合が重要

### 5. 順序と冪等性の前提を間違える

「このキューは順序保証ある」「重複は来ない」という思い込みで設計すると、稀に発生する事故で致命的バグになる。

## よく使われるキュー製品

| 製品 | 特徴 | 向き |
|------|------|------|
| **Amazon SQS** | AWSマネージド、非常にシンプル | AWSユーザーの第一選択 |
| **RabbitMQ** | 機能豊富、ルーティング強力 | 複雑な配信ルール |
| **Kafka** | 超高スループット、ストリーム処理 | ログ / 大量イベント |
| **Redis (Streams / List)** | 軽量、既存 Redis を使える | シンプルなタスクキュー |
| **Google Pub/Sub** | GCPマネージド | GCPユーザー |
| **NATS** | 軽量・超低遅延 | IoT / リアルタイム系 |

→ 詳細は `キュー製品の比較.md` 参照。

---

## キューを使うべきか迷ったら

以下のいずれかに当てはまればキュー導入を検討:

- [ ] 応答時間が重要で、バックグラウンド処理を裏で回したい
- [ ] 処理が失敗したとき、自動リトライ・DLQ 退避が欲しい
- [ ] ピークトラフィックを吸収したい
- [ ] 複数サブシステムに同じイベントを配りたい（Pub/Sub）
- [ ] サービス間を疎結合にしたい

逆に以下なら **キューを入れない方が単純**:

- [ ] ユーザーが結果を即座に見たい（同期応答が必要）
- [ ] 1日1回のバッチで十分
- [ ] エラー時は手動介入で構わない

## まとめ

- メッセージキューは **非同期に処理を渡す「箱」**
- Producer がメッセージを入れ、Consumer が取り出す
- **応答速度改善 / 結合度低下 / 負荷吸収 / 障害隔離 / スケール** が主なメリット
- ほぼすべての製品で **重複配信の可能性** があるため、冪等性の設計必須
- 順序保証は基本「ない」前提で設計
- 小規模なら「DB + cron」で代替可。スケール要件が出たらキュー導入
- 製品選びは **AWS なら SQS、大量イベントなら Kafka** が目安
