# イベント駆動アーキテクチャ（EDA）

## はじめに

**イベント駆動アーキテクチャ（Event-Driven Architecture / EDA）** とは、

> システム内の出来事を **「イベント」** として表現し、**発生と反応を疎結合に** 結びつけるアーキテクチャスタイル

のことです。メッセージキュー / Pub/Sub の上に組み上がる、**大規模システムの基本パターン** の一つです。

---

## 従来型（リクエスト駆動）との違い

### リクエスト駆動（Request-Driven）

```
[注文API] → [在庫サービス]
         → [決済サービス]
         → [メール送信]
         → [配送サービス]
         → [ポイント付与]
```

**注文API がすべての下流を知っている**。

**問題**:
- 新しいサブシステムが増えるたびに注文API を改修
- 下流が落ちると注文自体が失敗
- サブシステムの実装詳細に注文API が引きずられる

### イベント駆動（Event-Driven）

```
[注文API] → 「OrderPlaced」イベントを publish
                        ↓
        ┌─────────┬──────────┬────────┬─────────┐
        ▼         ▼          ▼        ▼         ▼
    [在庫]   [決済]    [メール] [配送]  [ポイント]
```

**注文API は「注文された」という事実だけ発信**。誰が反応するかは知らない。

**メリット**:
- 新サービス追加時、注文API は無変更
- 各サービスは独立に稼働・失敗
- 並列・非同期処理で速い

---

## 中心概念

### イベント（Event）

**過去に起きた出来事** を表現するデータ。

```json
{
  "event_type": "OrderPlaced",
  "event_id": "uuid-123",
  "occurred_at": "2026-04-24T12:00:00Z",
  "data": {
    "order_id": 456,
    "user_id": 789,
    "items": [...],
    "total": 5000
  }
}
```

命名は **過去形** が基本: `OrderPlaced`, `PaymentCompleted`, `UserRegistered`。

### Producer / Publisher

イベントを発生させる側。「ドメインの主人」。

### Consumer / Subscriber

イベントに反応する側。複数いてよい。

### イベントバス / ブローカー

イベントを受け渡す基盤。Kafka、SNS、Pub/Sub など。

## イベント駆動のパターン

### 1. イベント通知（Event Notification）

「何かが起きた」だけを伝える。詳細は Consumer が後から取りに行く。

```
[注文API] → 「OrderPlaced: order_id=456」
                ↓
         [メールサービス] ← API に order_id=456 の詳細を聞きに行く
```

**メリット**: イベントサイズが小さい、Producer と Consumer の結合が薄い
**デメリット**: 後から詳細取得するので若干遅い

### 2. イベント駆動状態転送（Event-Carried State Transfer）

イベント自体に **必要な情報を全部含める**。Consumer は API を呼ばなくていい。

```json
{
  "event_type": "OrderPlaced",
  "data": {
    "order_id": 456,
    "user": {"id": 789, "email": "..."},
    "items": [...]
  }
}
```

**メリット**: Consumer が独立稼働、API 依存なし
**デメリット**: イベントが大きくなる、スキーマ変更が影響大

### 3. イベントソーシング（Event Sourcing）

**状態そのものを「イベントの積み重ね」** として保存。

```
ユーザー残高 = 以下のイベントの合計
  + Deposit(1000)
  + Deposit(500)
  - Withdraw(300)
  + Deposit(2000)
  → 現在残高 3200
```

**メリット**: 完全な監査履歴、任意時点の状態復元、時系列分析
**デメリット**: 設計・実装が複雑、クエリがシンプルでない

### 4. CQRS（Command Query Responsibility Segregation）

**コマンド（書き込み）とクエリ（読み取り）を分離**。イベントソーシングと組み合わせることが多い。

```
[Write Side] ← コマンド → イベント → [Event Store]
                                        ↓
[Read Side] ← クエリ ← [読み取り専用DB（イベントから構築）]
```

## イベント設計の原則

### 1. **過去形で名付ける**

◯ `OrderPlaced`（注文された）
✕ `PlaceOrder`（注文する ← これは「コマンド」）

### 2. **イベントは「事実」、不変**

- 「起きたこと」なので、**あとから変更しない**
- 「キャンセルされた」という別イベントで対応

### 3. **ドメインに近い粒度**

- 技術的な変更（「INSERT された」）でなく
- ビジネス的な出来事（「注文が確定した」）で区切る

### 4. **独立性**

イベントだけで意味が成立するように。外部参照が必要なら、値を埋め込む。

### 5. **バージョニング**

スキーマが進化するので、`version` を持たせる or 後方互換性を担保。

```json
{
  "event_type": "OrderPlaced",
  "version": "v2",
  ...
}
```

## 典型的な実装スタック

### AWS

```
[サービスA] → SNS → SQS → [サービスB]
                ↘ SQS → [サービスC]
```

SNS で Pub/Sub、SQS で並列処理。

### Kafka

```
[サービスA] → Topic → Consumer Group 1 (サービスB)
                   → Consumer Group 2 (サービスC)
```

**イベントが永続されるので、過去を再処理可能**。

### GCP

```
[サービスA] → Pub/Sub Topic → Subscription (サービスB)
                           → Subscription (サービスC)
```

## EDA のメリット

### 1. 疎結合

Producer は Consumer を知らない。新しい Consumer を追加しても Producer は無変更。

### 2. スケーラビリティ

各サービスが独立にスケール。Consumer を増やせば処理能力も増える。

### 3. 耐障害性

1つの Consumer が落ちても、他のサービスは動き続ける。
Producer は影響なし。

### 4. 拡張性

「ポイント付与」機能を後から追加 → イベントを subscribe するだけで実装可能。

### 5. 監査・再処理

イベントログが残れば、**過去に遡って解析や再処理** ができる。

---

## EDA のデメリット・難しさ

### 1. デバッグが難しい

同期呼び出しと違い、処理が複数サービスに散らばる。
**相関ID / 分散トレーシング** が必須。

### 2. データ一貫性の課題

「注文した」後に「決済に失敗した」場合のロールバックは?
→ **Saga パターン** や補償トランザクションが必要（`../../Data/整合性/Sagaパターン.md` 参照）。

### 3. 順序保証の難しさ

複数 Consumer が並列処理するため、イベントの順序が前後する。
→ `順序保証の難しさ.md`

### 4. 冪等性の必要性

at-least-once 配信が基本 → 重複を前提に処理を冪等に。

### 5. スキーマ進化の管理

イベント構造を変えると、すべての Subscriber に影響。
→ スキーマレジストリ（Confluent Schema Registry 等）や、後方互換ルール。

### 6. 初期実装コストが高い

同期 API の2〜3倍の実装量になりがち。
**小規模には過剰**。

---

## いつ EDA を使うべきか

### 向いている

- マイクロサービス化した大規模システム
- サブシステムが多く、今後も増える
- 非同期処理が許される（即時性が必須でない）
- 分析・監査が重要

### 向いていない

- 小規模システム
- チームのメッセージング経験が少ない
- 全処理が同期即答を要求される
- モノリスで十分回っている

## アンチパターン

### 1. イベント命名が曖昧

`DataChanged` / `Updated` などは情報量ゼロ。
**具体的な事実で命名**（`EmailChanged`, `OrderCancelled`）。

### 2. Producer と Consumer が強結合

- イベントペイロードに Consumer 専用フィールド
- Consumer の要望で Producer が変更

→ **イベントはドメインの事実** であり、特定 Consumer のためのものではない。

### 3. イベントが巨大

500KB のペイロード → キュー / ブローカーの負荷、ストレージコスト増。
**必要な情報だけを含める**。参照IDだけ入れて、詳細は API で取る手も。

### 4. Saga を使わずに補償処理を個別実装

「決済失敗 → 注文キャンセル」を各サービスが個別に実装 → 散らばって管理不能に。

### 5. 同期 RPC と混在で設計意図が不明

- 一部は REST、一部は Kafka、一部は Queue
- どの通信方式を使うかルールがない

→ **「何を同期 / 何を非同期にするか」のルール** を明文化する。

## まとめ

- EDA は **「事実の発信」で疎結合化** するアーキテクチャ
- イベントは **過去形で名付け、事実、不変、独立** に
- Producer は Consumer を知らない → **新機能追加が容易**
- at-least-once 配信が前提 → **冪等性必須**
- 順序保証・データ整合性は難しく、Saga / 状態マシンで対応
- Kafka / SNS+SQS / GCP Pub/Sub が典型実装
- 大規模・マイクロサービス・非同期許容 の場面で真価
- 小規模には過剰、段階的に取り入れるのが賢い
