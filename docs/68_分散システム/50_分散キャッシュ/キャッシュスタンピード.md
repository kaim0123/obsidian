# キャッシュスタンピード — Thundering Herd

## はじめに

**キャッシュスタンピード（Cache Stampede / Thundering Herd）** とは、

> 人気のキャッシュが期限切れになった瞬間、**大量のリクエストが一斉に DB/API に殺到** して過負荷になる現象

です。

「家畜の群れ（herd）」が一斉に走り出す（thundering = 雷のように）様子から名付けられました。**キャッシュを使うあらゆるシステムで起きうる** 古典的な問題です。

---

## なぜ起きるか

### 通常のキャッシュ動作

```
1. リクエスト → キャッシュヒット（速い）
2. キャッシュ期限切れ
3. 次のリクエスト → ミス → DB → 結果をキャッシュ
4. 以降はまたヒット
```

### スタンピードが起きる条件

```
「人気のキー」があり、期限切れの瞬間に
大量のリクエストが同時に来る
```

### 何が起きるか

```
時刻 T: キャッシュ期限切れ
時刻 T+0.001s: リクエスト1 → ミス → DB クエリ発行
時刻 T+0.002s: リクエスト2 → ミス → DB クエリ発行
時刻 T+0.003s: リクエスト3 → ミス → DB クエリ発行
...
時刻 T+0.1s: リクエスト1000 → ミス → DB クエリ発行

DB に 1000 個の同じクエリが殺到 → 過負荷
```

**全員がキャッシュが復元される前にミス** して、全員が DB を叩く。

---

## 具体例

### シナリオ: トップページの「おすすめ商品」

```
SELECT * FROM recommendations ORDER BY score DESC LIMIT 100;
```

- DB 処理に 500ms かかる高コストクエリ
- TTL 5分でキャッシュ
- トップページは毎秒1000リクエスト

**5分おきに**: 1000 リクエストが同時にミス → 1000 個の重いクエリが DB に殺到 → DB ダウン。

---

## 対策一覧

### 1. TTL にジッター（最基本）

TTL にランダム揺らぎを入れる:

```python
import random
ttl = 300 + random.randint(-30, 30)  # 270〜330秒
r.setex(key, ttl, value)
```

- 5分おきの一斉期限切れを避けられる
- **キーごとに違う時刻に期限切れ**
- 実装コストほぼゼロ

**ただし**: 同じキーに対する殺到は解決しない。下の手段と組み合わせる。

### 2. シングルフライト（Singleflight）

同じキャッシュミスが来たら、**最初の1リクエストだけ DB を叩き、他は結果を待つ**。

```
リクエスト1 → ミス → DB クエリ発行（これが走る）
リクエスト2 → ミス → 「リクエスト1 と同じ」→ 待つ
リクエスト3 → ミス → 「リクエスト1 と同じ」→ 待つ
...
リクエスト1 完了 → 結果をキャッシュ
リクエスト2, 3 ← 同じ結果を返す
```

- **DB への重複クエリを完全防止**
- ライブラリ: Go の `singleflight`、Python の `aiocache_singleflight` 等

### 3. 分散ロック

Redis 等に **「いまこのキーを更新中」** のロックを置き、他リクエストは待つ。

```python
def get_with_lock(key):
    value = r.get(key)
    if value:
        return value

    lock_key = f"lock:{key}"
    if r.set(lock_key, 1, nx=True, ex=10):  # 獲得
        try:
            value = fetch_from_db()
            r.setex(key, 300, value)
            return value
        finally:
            r.delete(lock_key)
    else:
        # 他のリクエストが更新中 → 待つ
        time.sleep(0.1)
        return r.get(key) or fetch_from_db()  # フォールバック
```

### 4. Refresh-ahead

期限切れ **直前に非同期で再取得**:

```
TTL が残り20%になったら、裏でキャッシュ更新開始
→ 期限切れのタイミングでは既に新しい値がある
```

- キャッシュミスが発生しない
- ただし、たまに古い値が返る可能性

### 5. Stale-while-revalidate

期限切れでも **古い値を返しつつ、裏で更新**:

```
1. 期限切れのキャッシュ
2. リクエスト: 古い値を即返す
3. 裏で DB から新しい値取得
4. キャッシュ更新
```

- ユーザーは待たない
- 多少古い値を許容できる場合に最適

HTTP の Cache-Control ディレクティブとしても存在:

```http
Cache-Control: max-age=60, stale-while-revalidate=300
```

### 6. Probabilistic Early Expiration

確率的に期限前に再計算。論文ベースのアルゴリズム（XFetch）:

```python
if random() < probability_of_early_expiration:
    refresh_cache()
```

高度だが、スタンピード問題に対する最適解の1つ。

### 7. 無期限キャッシュ + 明示的無効化

TTL を設定しない代わりに、**データ更新時に明示的に無効化**。

- 期限切れが起きない
- 代わりに、**無効化漏れに注意**

## 実装例: シングルフライト

### Go の例

```go
import "golang.org/x/sync/singleflight"

var g singleflight.Group

func GetUser(userID string) (User, error) {
    v, err, _ := g.Do(userID, func() (interface{}, error) {
        // ここは userID ごとに1回だけ実行される
        return fetchFromDB(userID)
    })
    return v.(User), err
}
```

複数ゴルーチンが同時に `GetUser("123")` を呼んでも、**実際の `fetchFromDB` は1回だけ**。

### Python の例（aiocache）

```python
from aiocache import cached

@cached(ttl=300)
async def get_product(product_id):
    return await fetch_from_db(product_id)
```

多くのキャッシュライブラリは内部でシングルフライト実装している。

---

## 対策の組み合わせ

実務では **複数対策を併用** することが多い:

```
TTL + ジッター    ← 基本
       +
シングルフライト  ← 同一キーへの殺到対策
       +
Stale-while-revalidate ← ユーザー体験最適化
```

特に **ジッター + シングルフライト** は、コストがほぼゼロで効果大。

## 似た問題: Cache Avalanche（キャッシュ雪崩）

### キャッシュスタンピードとの違い

| 現象 | 説明 |
|------|------|
| **スタンピード** | **1つのキー** に大量リクエストが殺到 |
| **雪崩** | **大量のキーが同時期限切れ** |

### 雪崩のシナリオ

```
深夜バッチでキャッシュ大量プリロード
→ TTL 24時間
→ 翌日同時刻に全て期限切れ
→ DB に全キャッシュ分のクエリが殺到
```

### 雪崩の対策

- **TTL ジッター**（±10〜20%）
- 段階的なキャッシュウォームアップ

---

## モニタリング

スタンピード / 雪崩が起きているかを検知:

- **DB クエリ数の急増** を監視
- **キャッシュミス率** の瞬間的上昇
- **同一クエリの同時発行数**
- レイテンシの急上昇

ツール:
- Prometheus + Grafana でダッシュボード
- APM（Datadog, New Relic）でトレース

## よくある失敗

### 1. TTL を全キー同じに

→ 一斉期限切れで雪崩。**必ずジッター**。

### 2. シングルフライトなしで人気キー運用

→ スタンピード発生時、DB が死ぬ。

### 3. キャッシュミス時のエラー処理が雑

→ ミス頻発時に大量のエラーログ、さらに負荷増大。

### 4. 同じデータで多数の異なるキーを作る

例: クエリパラメータの順序違いで別キー扱い
→ 実質的に「毎回ミス」状態になり、スタンピードと同じ結果。

## まとめ

- キャッシュスタンピード = **1つのキー** の期限切れで大量リクエストが DB に殺到
- キャッシュ雪崩 = **複数キー** の同時期限切れ
- 対策の基本:
    - **TTL ジッター**（±10〜20%、実装簡単）
    - **シングルフライト**（同じクエリの重複発行防止）
    - **Refresh-ahead / stale-while-revalidate**（高度、体感ゼロミス）
- 人気の高いキャッシュほど対策必須
- モニタリングでスタンピード発生を検知
- 複数対策の組み合わせが実務の現実解
