# キャッシュ無効化の難しさ — 2つの難問の1つ

## はじめに

コンピュータサイエンスの有名な格言:

> "There are only two hard things in Computer Science: cache invalidation and naming things."
> （コンピュータサイエンスで難しいのは2つだけ: **キャッシュの無効化** と **命名**）
> — Phil Karlton

この記事はその1つ目、**キャッシュ無効化（Cache Invalidation）** の難しさを扱います。なぜ難しいのか、具体的にどんな問題が起きるのか、どう対処するのかを整理します。

---

## キャッシュ無効化とは

> 「キャッシュ内の **古いデータを削除または更新** する行為」

例:
- ユーザーがプロフィールを更新した → キャッシュにある古いプロフィールを削除
- 商品価格が変わった → CDN キャッシュをパージ
- 記事が削除された → 各層のキャッシュを一斉に無効化

---

## なぜ難しいのか

### 1. 真実の所在が分散する

```
[CDN]      ← 5分古い
[Redis]    ← 3分古い
[アプリメモリ]  ← 1分古い
[DB]       ← 今の真実
```

ユーザーがどの層のキャッシュを見るかで、**見える情報が違う**。
全層を一斉更新するのは物理的に不可能。

### 2. 「いつ」更新するかの判断が難しい

- **即座に無効化** → 同期的な削除のコスト、失敗時の取扱い
- **TTL 任せ** → その間は古いデータが見える
- **遅延無効化** → いつなら十分か

### 3. 分散環境で伝播が遅い

```
サーバA で更新 → キャッシュ削除
サーバB で処理中 → まだ古い値を使ってる
```

特に CDN の世界分散キャッシュでは、**全エッジに伝播するのに数分** かかる。

### 4. 「何を消すか」の特定が難しい

- あるユーザーの名前変更 → そのユーザーに関連するキャッシュは?
- `user:123` だけ?
- `orders:user:123` も?
- `recent_comments:post:456` で user:123 が表示されているなら、それも?

→ **影響範囲の追跡が困難**

### 5. 無効化は冪等でない

- 間違って消しすぎる → 無駄に DB を叩く
- 消し漏れ → 古いデータが残る

## 無効化戦略

### 1. TTL ベース（タイムアウト）

```python
r.setex("user:123", 300, data)  # 5分で自動削除
```

**長所**: シンプル、確実に定期更新
**短所**: TTL が切れるまで古いデータが返る

### 2. 明示的な削除（Write-Invalidate）

```python
def update_user(user_id, data):
    db.update(user_id, data)
    r.delete(f"user:{user_id}")   # 即座に削除
```

**長所**: 即座に整合性が取れる
**短所**: 複数キーへの波及が管理困難

### 3. Write-through（キャッシュも更新）

```python
def update_user(user_id, data):
    db.update(user_id, data)
    r.setex(f"user:{user_id}", 300, data)  # キャッシュ自体を更新
```

**長所**: 次回読む時のキャッシュミスがない
**短所**: DB とキャッシュの二重書き、失敗時の不整合

### 4. イベント駆動無効化

```
[DB更新] → イベント publish → [各キャッシュが購読]
                              → 関連キャッシュ削除
```

**長所**: 複数層・複数サービスを協調的に無効化できる
**短所**: イベント基盤が必要、複雑

### 5. バージョニング（Cache Busting）

キーにバージョンを含める:

```
user:123:v1  → 更新で
user:123:v2  ← 古い v1 キーは TTL で消える
```

**長所**: 古いキーはそのまま、自然にフェードアウト
**短所**: 古いキーがメモリを占有する期間

### 6. Tag-based 無効化

キャッシュに **タグ** を付け、タグ単位で削除:

```python
cache.set("user:123", data, tags=["user:123", "all_users"])
cache.set("user:124", data, tags=["user:124", "all_users"])

cache.invalidate_tag("all_users")  # 両方削除
```

**長所**: まとめて無効化が楽
**短所**: すべてのキャッシュがタグ機能を持つとは限らない
**対応製品**: Varnish、一部のライブラリ

## 多層キャッシュの問題

### 典型例

```
ブラウザ → CDN → Redis → アプリメモリ → DB
```

ユーザーのプロフィール更新:

```
1. DB 更新 ← 即座
2. アプリメモリ削除 ← サーバ1台だけ。他は?
3. Redis 削除 ← これは即座に可能
4. CDN パージ ← グローバル伝播に数分
5. ブラウザキャッシュ ← 制御不能（TTL or Cache-Control 任せ）
```

**全部同時に新しくなるのは不可能**。どの層で **どのくらいの古さ** を許すかを設計する。

---

## 不整合の許容設計

### 「Eventual Consistency（結果整合性）」で設計

```
即時整合  ←─────────────→  ゆるい整合
DB       Redis         CDN       ブラウザ
```

- DB は常に真実
- Redis は数秒〜数分遅れ
- CDN は数分遅れ
- ブラウザは TTL 次第

**「何秒遅れまで許容できるか」** を業務要件で決める:
- 価格変更: 1分以内
- プロフィール: 5分以内
- 記事本文: 数時間OK

## CDN 特有の難しさ

CDN パージには以下の選択肢がある:

### 1. URL 指定パージ

```
POST /purge HTTP/1.1
URL: https://example.com/user/123
```

- 特定 URL のキャッシュを消す
- 早い（秒単位）

### 2. タグ / サロゲートキー

```
Surrogate-Key: user-123 orders-user-123
```

- 複数 URL をタグでグループ化して一括パージ
- Fastly, Cloudflare Workers で対応

### 3. 全体パージ

- 全キャッシュを消す
- 緊急時の最終手段（オリジン負荷激増）

### ファイル名ハッシュ方式（パージ不要）

```
/app.a1b2c3.js  ← 旧
/app.d4e5f6.js  ← 新（URLが変わる）
```

**ファイル名自体を変える** ことで無効化不要。
静的アセットはこれが最善。

## 典型的なアンチパターン

### 1. 消し漏れで古いデータが残る

```python
def update_user(user_id, data):
    db.update(user_id, data)
    r.delete(f"user:{user_id}")
    # でも user_list キャッシュも更新が必要…忘れた
```

→ **関連キャッシュの追跡漏れ** が事故の元。

### 2. 消しすぎで DB 殺到

全削除系の無効化で、一斉にキャッシュミス → DB 過負荷。

### 3. DB 更新とキャッシュ削除の順序ミス

```
キャッシュ削除 → DB 更新
    ↓ この間に別リクエストが DB から古い値を読んでキャッシュ
```

正しい順序: **DB 更新 → キャッシュ削除**

### 4. 無限 TTL に頼って消し忘れ

TTL なしで置いたキー → イビクションで不意に消える or 永遠に古いデータ

### 5. 認証付きコンテンツを CDN でキャッシュ

- 他ユーザーに個人情報が漏れる
- 最重大事故

## 実装パターン集

### パターン1: 「先にDB、後でキャッシュ削除」

```python
def update_user(user_id, data):
    db.update(user_id, data)          # 1. DB
    r.delete(f"user:{user_id}")       # 2. Cache
```

最も基本。

### パターン2: Double Delete（DBレプリ遅延対策）

```python
def update_user(user_id, data):
    r.delete(f"user:{user_id}")       # 先に削除
    db.update(user_id, data)          # 2. DB
    time.sleep(0.5)                   # 少し待って
    r.delete(f"user:{user_id}")       # 再度削除
```

### パターン3: Version Key

```python
def get_user(user_id):
    version = r.get(f"user:{user_id}:version") or 1
    key = f"user:{user_id}:v{version}"
    # 以下キャッシュ参照
    ...

def update_user(user_id, data):
    db.update(user_id, data)
    r.incr(f"user:{user_id}:version")  # バージョン上げるだけで旧は無効化
```

古いキーは TTL で自然消滅。

### パターン4: 論理削除フラグ

```python
def update_user(user_id, data):
    db.update(user_id, data)
    r.setex(f"user:{user_id}:dirty", 60, "1")  # 「古い」マーク

def get_user(user_id):
    if r.get(f"user:{user_id}:dirty"):
        r.delete(f"user:{user_id}")
        r.delete(f"user:{user_id}:dirty")
    cached = r.get(f"user:{user_id}")
    ...
```

## よくある質問

### Q. 完璧な無効化は可能?

A. **ほぼ不可能**。多層キャッシュでは必ず「ズレる時間」がある。
「許容できる古さ」を業務要件で決めて、**TTL + 明示的無効化** で埋める。

### Q. CDN パージはどれくらいで伝播?

A. 製品次第:
- Fastly: 150ms（最速）
- Cloudflare: 通常30秒以内
- CloudFront: 数分〜15分
- Akamai: 数分

### Q. 一括パージはあり?

A. 最終手段。**オリジンに負荷が集中**するので、事前準備なしに実行しない。

## まとめ

- キャッシュ無効化は **コンピュータサイエンスの2大難問** の1つ
- **真の無効化は不可能**、「どこまで古くて OK か」を設計
- 戦略: TTL / 明示削除 / Write-through / イベント駆動 / Version Key / Tag
- **「DB 更新 → キャッシュ削除」** の順序が基本
- 多層キャッシュは段階的整合性で許容
- CDN 系は **ファイル名ハッシュ化** で無効化自体を回避が賢い
- ジッターで雪崩を防ぐ
- **関連キーの把握と漏れ防止** が運用の要
