# キャッシュキー設計

## はじめに

キャッシュの世界では、**キー設計の良し悪しがヒット率・保守性・不整合発生率** を大きく左右します。

「適当に `user_123` とか付ければいい」と思っていると、**名前空間の衝突・無効化漏れ・チーム間トラブル** を招きます。本記事では、キャッシュキーを設計する際の実用的ルールを整理します。

---

## キャッシュキーの役割

### 基本

```
キャッシュ = 「キー → 値」の辞書（ハッシュマップ）

r.set("user:123", {"name": "Alice", ...})
r.get("user:123")
```

キーは:
- ユニークに値を特定する
- 人間にも読める
- チーム内で一貫した規則

---

## 良いキーの条件

### 1. 一意性

同じキーで別データが入らないように、**名前空間 + 識別子** で構成。

```
✕ 123
◯ user:123
◯ product:456
```

### 2. 読みやすさ

トラブル時に Redis を直接覗いて理解できる必要。

```
✕ u123p456p7
◯ user:123:product:456:page:7
```

### 3. 予測可能

プログラムから同じ入力で同じキーが生成される必要。

```python
def cache_key(user_id):
    return f"user:{user_id}"
```

### 4. 衝突しない

別の機能・別のチームが同じキーを使わないように。

```
✕ top        ← 何の top?
◯ orders:top:10
```

### 5. 長すぎない

Redis 等のキャッシュでキーが大きすぎるとメモリを食う。
- 100〜200 文字以内が目安
- ハッシュ化する手もある（`sha256(long_key)`）

---

## 一般的な命名規則

### コロン区切り階層

```
[namespace]:[entity]:[id]:[sub-entity]
```

例:
```
user:123
user:123:profile
user:123:orders
orders:2024-04-24:count
product:456:reviews:page:1
```

### メリット

- Redis の `KEYS` パターン指定で検索しやすい
- 階層が視覚的に分かる

---

## アンチパターン

### 1. 意味のない名前

```
✕ data123
✕ temp
✕ cache
```

何のデータか不明。

### 2. 名前空間なし

```
✕ 123          ← 何の ID?
✕ alice        ← 何の alice?
```

他機能と衝突する。

### 3. 情報不足

```
✕ orders  ← 誰の? どの期間の?
◯ orders:user:123:recent
```

### 4. 長すぎる

```
✕ user_profile_information_for_user_with_id_123
◯ user:123:profile
```

### 5. 順序を考えない複合キー

```
✕ user:123:lang:ja       ← と
✕ user:lang:ja:123       ← が別の場所に混在
◯ 常に user:ID:lang:... で統一
```

## クエリパラメータをキーに含める

API 結果をキャッシュするとき、**クエリパラメータもキーの一部**:

```python
# GET /products?category=books&sort=price&page=2
key = "products:category:books:sort:price:page:2"
```

または URL をそのままハッシュ化:

```python
import hashlib
key = "api:" + hashlib.sha256(url.encode()).hexdigest()
```

### 順序の問題

```
?sort=price&category=books
?category=books&sort=price
```

→ クエリ順が違うだけで別キーになる。

**対策**: クエリをソートしてからキー化:

```python
sorted_params = sorted(params.items())
key = "products:" + ":".join(f"{k}:{v}" for k, v in sorted_params)
```

## バージョン情報の埋め込み

### アプリケーションバージョン

デプロイしたらキャッシュを無効化したい場合:

```
user:123:v3
```

デプロイ時に `v3` → `v4` に変えるだけで、旧バージョンのキャッシュは使われなくなる。

### データバージョン

書き込みごとにインクリメント:

```python
r.incr(f"user:{user_id}:version")
version = r.get(f"user:{user_id}:version")
key = f"user:{user_id}:v{version}"
```

## パーソナライズの考慮

### ユーザー固有キャッシュ

```
home_page:user:123      ← A さん用
home_page:user:456      ← B さん用
```

**注意**: 全ユーザー分のキーが生まれて爆発的に増える。メモリ消費に注意。

### 共通キャッシュ + ユーザー情報合成

```
home_page:global  ← 全員共通
    + session に応じてパーソナライズ
```

可能ならこちらがスケール的に有利。

## 多言語 / マルチテナント

### 国際化

```
product:123:lang:ja
product:123:lang:en
```

### マルチテナント SaaS

```
tenant:acme:user:123
tenant:xyz:user:123
```

テナント ID を **先頭** に付けるのが原則。検索・削除が楽。

## 時間軸を含むキー

### 日付範囲

```
daily_stats:2026-04-24
weekly_stats:2026-w17
monthly_stats:2026-04
```

### スライディングウィンドウ

```
rate_limit:user:123:1745509200   ← UNIX時刻（分単位で切り捨て）
```

レートリミット等で、時間単位で独立キーを作る。

## キーの長さと Redis のメモリ

Redis では **キー自体もメモリ消費**:

- `user:123` = 数バイト（OK）
- `user:profile:alice@example.com:preferences:v2` = 大きい（大量なら注意）

### 対策

- **名前空間を短縮**: `usr:123:prf` のように省略
- **ハッシュ化**: 長いキーは SHA-256 等でダイジェストに
- 「1GB に 100万キー」のような規模なら意識

---

## キーのスキャン

Redis の `KEYS` は本番で **使っちゃダメ**:

```
KEYS user:*    ← 全 Redis をブロック（危険）
```

代わりに:

```
SCAN 0 MATCH user:* COUNT 1000
```

- カーソル式で少しずつ読む
- 本番でも安全

キー設計時は **SCAN でパターン検索しやすい命名** を意識する:
```
user:123:profile
user:123:orders
user:123:settings
```
→ `SCAN 0 MATCH user:123:*` で関連キー全部取れる。

---

## キーのドキュメント化

大規模システムでは、**キーの命名規則を文書化** する:

```
キーのプレフィックス一覧:

- user:{id}             ユーザー基本情報
- user:{id}:profile     ユーザープロファイル
- user:{id}:sess        セッション情報
- order:{id}            注文情報
- cache:api:...         API レスポンスキャッシュ
```

→ 新しいメンバーが加わっても、キー命名のブレが減る。

```

```

```

```

```

```


## チーム運用のコツ

### プレフィックス予約

```
team-frontend が使う: fe:*
team-backend が使う: be:*
team-data が使う: data:*
```

→ **名前空間を部門で切る**。チーム間衝突防止。

### ドキュメント化

- 新しいプレフィックスを追加するとき、Wiki / README に記述
- 削除時も書く

### Lint ツール

```python
def validate_key(key):
    if not re.match(r"^[a-z0-9_:-]+$", key):
        raise ValueError(f"Invalid cache key: {key}")
```

キー規則を自動チェック。

## よくある失敗

### 1. コロン以外の区切り文字を使う

```
✕ user.123.profile
✕ user-123-profile
```

Redis の慣習は `:`。他だと混乱する。

### 2. バイナリを直接キーにする

```
r.get(some_binary_data)   ← 意図しない文字混入
```

必ず UTF-8 文字列に変換。

### 3. 大文字小文字の混在

```
user:123
User:123
USER:123
```

大文字小文字で別キー。**小文字に統一**。

### 4. スペース混入

```
"user: 123"  ← スペース
```

→ マッチしない。自動テストで防ぐ。

## まとめ

- キーは **名前空間:エンティティ:ID:サブ** の階層構造
- 区切り文字は `:` に統一（Redis 標準）
- **小文字・ASCII** に統一
- チーム / 部門プレフィックスで衝突防止
- クエリパラメータはソートしてキー化
- 長すぎるキーはハッシュ化
- 本番 `KEYS` は使わず `SCAN`
- キー命名はドキュメント化
- バージョン情報で無効化もしやすくする
