## 要約

本動画（シリーズ第 4 回）は、**Kubernetes などのコンテナ環境** で本番運用に欠かせない **システム監視** の基礎を解説する。**Prometheus**（メトリクス監視）、**EFK スタック**（ログ収集・分析）、**Jaeger**（トレーシング）の 3 ツールを軸に、**オブザーバビリティ（可観測性）の 3 本柱** の考え方、各ツールの構成・使い分け、統合監視の設計、運用のベストプラクティスまでをカバーする。

### テーマ：なぜ監視が必要か

| 理由 | 内容 |
|------|------|
| **障害の早期発見** | サーバーが落ちた「後」ではなく、**壊れる前** に気づく（例：CPU 使用率 90% 超でアラート） |
| **パフォーマンス把握** | どの API が遅いか、ボトルネックはどこかを **勘ではなくデータ** で判断する |
| **キャパシティプランニング** | 利用増加のペースから、将来いつサーバー追加が必要か **予測** する |

### オブザーバビリティの 3 本柱

| 柱 | データの種類 | 本動画で扱うツール |
|----|-------------|-------------------|
| **メトリクス** | CPU 使用率・メモリ・リクエスト数など **数値** | **Prometheus** + **Grafana** |
| **ログ** | エラーログ・アクセスログなど **テキスト** | **EFK スタック**（Elasticsearch / Fluentd / Kibana） |
| **トレース** | 1 リクエストが複数サービスを通る **処理の流れ** | **Jaeger** |

- 3 つは別ツールで担うのが一般的。今回はメトリクスとログを中心に、トレースも概要まで解説する。

### Prometheus：クラウドネイティブ監視のデファクトスタンダード

- **2016 年** に **CNCF**（Cloud Native Computing Foundation）の **2 番目のプロジェクト** として採用（1 番目は Kubernetes）。現在はクラウドネイティブ環境の監視で **事実上の業界標準**。
- 名前はギリシャ神話の **プロメテウス**（火を盗んだ神）に由来。

#### プル型 vs プッシュ型

| 方式 | 動き | 特徴 |
|------|------|------|
| **プッシュ型**（従来型） | 監視対象がデータを **送る** | エージェントを各所に配布・管理しやすいが、一元管理が難しい場合がある |
| **プル型**（Prometheus） | Prometheus が定期的に監視対象へ **取りに行く** | 監視対象を **中央で一元管理** しやすい。デフォルトは **60 秒に 1 回** スクレイプ |

- **短時間で終わるバッチ処理** はプル型だと取りこぼしやすい → **Pushgateway** に結果を送り、Prometheus が後から取得する。

#### 5 つの主要コンポーネント

| コンポーネント | 役割 |
|---------------|------|
| **Prometheus サーバー** | 中核。メトリクスの **収集・保存・クエリ** を担当 |
| **Exporter** | 監視対象からメトリクスを公開するプログラム（例：**Node Exporter**＝サーバー CPU/メモリ、**MySQL Exporter**＝DB）。公式に **数百種類**、自作も可 |
| **Pushgateway** | バッチなど **短命ジョブ** 向けのプッシュ受け口 |
| **Alertmanager** | アラートの **グルーピング・重複除去・通知**（Slack、PagerDuty、メールなど） |
| **Grafana** | Prometheus 本体ではないが **ほぼセット** で使う。メトリクスの **可視化・ダッシュボード** |

#### メトリクスの 4 型

| 型 | 性質 | 例 |
|----|------|-----|
| **Counter** | **単調増加**（リセット以外は減らない） | HTTP リクエスト総数、エラー累計 |
| **Gauge** | **上下する** 数値 | CPU 使用率、メモリ使用量、温度 |
| **Histogram** | **値の分布** をバケットで記録 | レスポンスタイム（0–100ms が何回、100–200ms が何回…）→ **パーセンタイル** 計算に便利 |
| **Summary** | Histogram に似るが **クライアント側で集計** | 最初は Counter と Gauge だけ覚えれば十分、と動画では補足 |

#### PromQL（Prometheus Query Language）

- メトリクスを取得・集計する **クエリ言語**。例：
  - `rate(http_requests_total[5m])` → 過去 5 分のリクエスト **レート**
  - `sum by (job) (up == 0)` → **落ちているサービス数**
- よく使うクエリはネット上に多数公開されており、**コピペから始める** のが現実的。

#### サービスディスカバリとラベル

- **サービスディスカバリ**：監視対象を **自動検出**。Kubernetes なら API から Pod を取得するよう設定するだけで、以降は自動。
- AWS / GCP / Azure など **マルチクラウド** にも対応。
- **ラベル**：全メトリクスに付く **タグ**（`instance`、`pod`、`job` など）。ラベルで絞り込み、サービス別・環境別の分析が可能。
- **カーディナリティに注意**：ユーザー ID など **ユニーク値をラベルにすると時系列が爆発** し、Prometheus が落ちる。
  - 目安：**1 インスタンスで約 100 万時系列** まで。**1000 万超** は危険域。

### EFK スタック：ログの収集・検索・可視化

| 略称 | 正式名 | 役割 |
|------|--------|------|
| **E** | **Elasticsearch** | 分散型 **全文検索エンジン**。JSON をそのまま格納する **NoSQL・スキーマレス** DB。億単位のログからキーワードを高速検索 |
| **F** | **Fluentd**（K8s では **Fluent Bit** も多い） | 各ノードの **ログ収集エージェント**。収集・フィルタ・変換・転送。プラグイン **数百種類** |
| **K** | **Kibana** | Elasticsearch 上のログを **検索・グラフ化**。Grafana がメトリクス、Kibana がログ、という役割分担 |

#### Fluentd の設定構造

- **source**（入力元）→ **filter**（変換）→ **match**（出力先）の 3 ディレクティブで記述。
- 例：Nginx ログを JSON 化、特定キーワードのみ抽出、複数出力先へ同時送信。

#### Kibana の主な機能

- **Discover**：リアルタイムログ検索（例：過去 1 時間のエラーのみ）
- **Dashboard**：エラー率・アクセス数・レスポンスタイム分布などを **1 画面** に配置

#### Prometheus と EFK の使い分け

| ツール | 答える問い | 例 |
|--------|-----------|-----|
| **Prometheus** | **何が** 起きているか（数値） | CPU 80%、エラー率急上昇 |
| **EFK** | **なぜ** 起きたか（ログ） | スタックトレース、エラーメッセージの詳細 |

- **補完関係**：Prometheus でアラート → Kibana で当該時刻のログを調査、という **連携プレイ** が基本。

---

### Jaeger：分散トレーシング

- 名前はドイツ語で **「狩人」**（バグを狩るツール）。
- **マイクロサービス** では 1 リクエストが認証・商品・在庫・決済・配送など **複数サービス** を経由する。
- **Span**：1 処理の開始〜終了（どのサービスで何秒かかったか）
- **Trace**：複数 Span をつないだ **リクエスト全体の流れ**
- UI では **ウォーターフォール** 表示でボトルネックが一目で分かる。

---

### 統合監視システムの設計

#### 障害対応の流れ（3 段階）

1. **Prometheus** でメトリクス監視 → アラート発火
2. **Grafana** でメトリクス推移を確認し、**どのサービスか** 特定
3. **Kibana** で該当時刻のログを検索し、**原因** を調査
4. 必要なら **Jaeger** で遅いトレースを見て **ボトルネック** 特定

#### ダッシュボード・K8s デプロイ

- **Grafana** は Elasticsearch データソースに対応 → **メトリクスとログを 1 ダッシュボード** に集約可能。
- **Prometheus Operator**：Kubernetes 専用。`ServiceMonitor` を書くだけで監視対象を自動追加。
- **Fluentd DaemonSet**：全ノードに 1 Pod ずつ配置し、**自動でログ収集**。

---

### 運用のベストプラクティス（7 項目 + α）

| # | 項目 | 要点 |
|---|------|------|
| 1 | **アラート疲れの防止** | 多すぎるアラートは重要なものを見逃す。**アクショナブル**（対応が必要）なものだけ設定 |
| 2 | **SLO ベースの監視** | **SLO**（Service Level Objective：例・可用性 99%、95% のリクエストが 200ms 以内）を先に決め、**SLO を下回りそうな時** にアラート |
| 3 | **ログレベルの整理** | DEBUG / INFO / WARN / ERROR。本番は **INFO 以上** などに絞り、Elasticsearch の容量を守る |
| 4 | **リテンション（保存期間）** | Prometheus 例：**15 日**、Elasticsearch 例：**30 日**。古いデータは **S3 等にアーカイブ** |
| 5 | **監視システムの監視** | Prometheus 自身が落ちたら意味がない → **別 Prometheus** や UptimeRobot 等で監視（2 段階で十分） |
| 6 | **ランブック（手順書）** | アラートごとの対応手順を文書化。夜中でも寝ぼけず対応できるように |
| 7 | **定期的な見直し** | 不要アラート削除・新メトリクス追加を **月次レビュー**。システムの成長に合わせて更新 |
| α | **ポストモーテム** | 障害後は **事後分析**（何が起きたか・なぜ検知できなかったか・どう改善するか）。責任追及ではなく **システム改善** が目的 |

---

### まとめ・学習の進め方

- **Prometheus**＝メトリクス、**EFK**＝ログ、**Jaeger**＝トレース。3 本柱を **特性に応じて使い分ける** ことが核心。
- 最初は小さく：**Node Exporter + Grafana** から始め、徐々にログ・トレース・統合へ拡張する。
- 監視は **1 日にしてならず、継続的な改善** が大事。
