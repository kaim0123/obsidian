## 要約

本動画（コンテナシリーズ **第 1 回**）は、**コンテナ技術の概念と仕組み** をゼロから解説する。船のコンテナに例えた「**アプリを箱に詰めてどこでも動かす**」という発想から始まり、**仮想マシンとの違い**、**Linux カーネル機能（namespaces / cgroups）**、**イメージのレイヤー構造**、**ネットワーク・ストレージ**、**セキュリティ**、**本番運用（Kubernetes・監視）** までをカバーする。次回は **Docker** の具体的な使い方を扱う。

### テーマ：コンテナとは何か

- **コンテナ**＝アプリケーションと、それを動かすために必要な **OS 設定・ライブラリ・依存関係** をひとまとめにした **実行可能なパッケージ**。
- 船のコンテナと同様、**中身が何であれ同じ形式の箱** に入れることで、**開発者の PC・テスト環境・本番サーバー** など異なる環境でも **同じように動作** させられる。
- 「**私の環境では動くのに**」という問題の原因は、マシンごとに **OS バージョン** や **インストール済みライブラリ** が異なること。コンテナは「このアプリにはこの OS・このライブラリが必要」という情報を **すべて同梱** する。

---

### 仮想マシン（VM）との比較

| 観点 | 仮想マシン（VM） | コンテナ |
|------|------------------|----------|
| **構造** | ホスト上に **ゲスト OS ごと** 複製 | **ホスト OS のカーネルを共有** |
| **起動時間** | 数 **分** | 数 **秒** |
| **メモリ消費** | **GB 単位** | **MB 単位** |
| **比喩** | 重い（F1 カー並みのオーバーヘッド） | 軽い（軽自動車並み） |

- VM は隔離性は高いが **OS 丸ごとの複製** で重い。コンテナは **プロセスレベルの隔離** で、必要な部分だけをパッケージ化するため **圧倒的に軽量・高速**。

---

### 軽量化の核心：namespaces と cgroups

コンテナの「軽さ」と「隔離」は、Linux カーネルの **2 つの機能** によって実現される。

#### namespaces（名前空間）——隔離

- 1 台のマシン上で複数コンテナを動かす際、各コンテナが **「自分だけがこのマシンを使っている」** と錯覚できるようにする **隔離** 技術。
- 例：**プロセス ID（PID）** — コンテナ A 内では PID 1 から、コンテナ B 内でも別の PID 1 から始まり、**お互いのプロセスが見えない**。
- 種類は **8 種類**（PID、ネットワーク、ファイルシステム、ユーザー ID など）。**個室** のようなイメージ。

#### cgroups（Control Groups）——リソース制限

- 各コンテナに **CPU・メモリなどの使用量上限** を設定する技術。
- 例：コンテナ A に **CPU 30%・メモリ 512MB** まで、といった制限。
- 1 つのコンテナが **CPU 100% で暴走** しても、他コンテナの動作を **阻害しない** ようにする——**みんなで仲良く使う** ための仕組み。

> **まとめ**：**namespaces で隔離** + **cgroups で制限** ＝ コンテナの軽量実行の土台。

---

### コンテナイメージ：設計図とレイヤー構造

- **コンテナイメージ**＝コンテナを作るための **設計図・テンプレート**（写真ではない）。
- **レイヤー構造**（ミルフィーユ型）で積み重なる：

| 層（下→上） | 内容 |
|-------------|------|
| 最下層 | ベース OS（例：Ubuntu） |
| その上 | ランタイム環境（例：Python） |
| さらに上 | 必要なライブラリ |
| 最上層 | アプリ本体 |

- **下位レイヤーは読み取り専用** で変更不可。変更が必要な場合は **新しい層を上に追加** する。
- **同じ下位レイヤーは複数イメージ間で再利用** できる——1 回ダウンロードすれば **別コンテナでも使い回し** 可能で効率的。
- **Copy-on-Write（CoW）**：書き込み可能な **最上層** に変更を記録。下位層のファイルを変更する際は **まずコピーしてから変更** し、元ファイルはそのまま残る——**安全** かつ **再現性** が高い。
- イメージがあれば **何度でも同じ状態のコンテナ** を作成でき、**開発環境と本番環境を完全に同一** にできる。

---

### ネットワーク：4 つの主要モード

| モード | 概要 | 用途 |
|--------|------|------|
| **Bridge（ブリッジ）** | 仮想ネットワークを作りコンテナ同士を接続。**デフォルト**。コンテナ専用 Wi-Fi ルーターのイメージ | 一般的な開発・単一ホスト運用 |
| **Host（ホスト）** | ホストマシンのネットワークを **直接共有**（隔離なし、同一 IP） | **パフォーマンス重視** の場面 |
| **Overlay（オーバーレイ）** | **複数ホストマシンにまたがって** コンテナを接続 | **クラウド・複数サーバー** 環境 |
| **None** | **ネットワーク完全遮断** | **セキュリティ重視** で外部通信を禁止したい場合 |

---

### ストレージ：ボリュームによる永続化

- コンテナは **削除すると中身も消える** ため、データを残すには **ボリューム** を使う。
- **2 種類**：

| 種類 | 概要 | 例 |
|------|------|-----|
| **バインドマウント** | ホストの **特定フォルダ** をコンテナ内のパスに **直接マウント** | ホストの `~/data` をコンテナの `/app/data` に接続 |
| **名前付きボリューム** | コンテナランタイムが管理する **専用領域**。保存場所を意識しなくてよい | **データベースのデータ** など。バックアップも容易 |

- **データベースのデータは必ずボリュームに保存** すべき——コンテナ削除で **データが全消失** するのを防ぐ。

---

### セキュリティ：隔離 ≠ 完全安全

- コンテナは **隔離されているが完璧ではない**。
- コンテナは **ホスト OS のカーネルを共有** するため、コンテナ侵害 → **カーネル脆弱性悪用** → **ホスト侵入** の可能性がある。

#### 最低限押さえる 3 つの対策

| 対策 | 内容 |
|------|------|
| **最小権限の原則** | コンテナ内で **root（管理者）権限を使わない**。一般ユーザーで実行するよう設定 |
| **イメージスキャン** | イメージ内の **既知の脆弱性** を検出。**Trivy**・**Clair** などのツールで自動チェック |
| **シークレット管理** | パスワード・API キーなど **機密情報をイメージに直接書かない**（誰でも見られる可能性がある）。専用管理ツールを使用 |

---

### 本番運用：オーケストレーションと監視

| 領域 | ツール・概念 | 役割 |
|------|-------------|------|
| **オーケストレーション** | **Kubernetes（K8s）** | 複数コンテナの **自動管理**。落ちたら再起動、負荷に応じた **台数の自動増減** |
| **モニタリング** | **Prometheus** + **Grafana** | CPU・メモリ使用率などを **リアルタイム監視**。コンテナは起動停止が頻繁なため **ログ収集** も重要 |

---

### 動画のまとめ（要点）

1. コンテナは **アプリを軽量に隔離して実行** する技術。VM より **圧倒的に軽く速い**。
2. **namespaces（隔離）** と **cgroups（制限）** が仕組みの核心。
3. **イメージのレイヤー構造** で効率的に管理・再利用できる。
4. **ネットワーク** は用途に応じて Bridge / Host / Overlay / None を使い分ける。
5. **データはボリューム** で永続化する。
6. **セキュリティ** は最小権限・イメージスキャン・シークレット管理の 3 点を押さえる。
7. **本番運用** では Kubernetes と Prometheus / Grafana などが定番。
