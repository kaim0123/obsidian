## 要約

本動画（コンテナシリーズ **第 3 回**）は、Netflix・Google・Spotify など大規模サービスの基盤となる **Kubernetes（K8s）** を初心者向けに徹底解説する。**誕生の歴史**、**コンテナオーケストレーションの 5 機能**、**宣言的管理とリコンシリエーション**、**コントロールプレイン／ワーカーノードの構造**、**Pod・Service・Deployment などの主要リソース**、**フラットネットワークと Ingress**、**課題とクラウドネイティブエコシステム** までをカバーする。

### テーマ：Kubernetes とは何か

- **Kubernetes**（略称 **K8s**）は、K と s の間の 8 文字を省略した表記。国際化（I18N）と同じ命名規則。
- ギリシャ語で「**舵取り（helmsman）**」を意味する。コンテナという「船」を操るシステムである。
- **Google が 2014 年** にオープンソース公開。社内の **Borg**（2000 年代初頭から運用）で培った大規模コンテナ管理のノウハウが基盤。
- Docker は **1 台のマシン** でのコンテナ運用に最適だが、**複数サーバー・数百コンテナ** の調和動作には **オーケストレーションツール** が必要——それが Kubernetes である。

---

### コンテナオーケストレーションの 5 機能

| # | 機能 | 内容 |
|---|------|------|
| **1** | **スケジューリング** | どのサーバー（ノード）でコンテナを動かすかを **自動決定**。リソースの空き状況を見て最適な配置を行う |
| **2** | **オートヒーリング** | コンテナが落ちたら **自動再起動**。サーバー障害時は別ノードでコンテナを起動する **自己修復** |
| **3** | **オートスケーリング** | 負荷に応じてコンテナ数を **自動増減** |
| **4** | **ロードバランシング** | 複数コンテナへアクセスを **均等分散** |
| **5** | **ローリングアップデート** | コンテナを少しずつ入れ替え、**ダウンタイムゼロ** でアプリを更新 |

---

### 最重要の設計思想：宣言的管理

#### 命令的 vs 宣言的

| 方式 | 考え方 | 問題点 |
|------|--------|--------|
| **命令的**（従来） | 「サーバー 1 でコンテナを起動しろ」など **具体的な手順** を指示 | 途中失敗時の復旧が困難。現在の状態が分かりにくい |
| **宣言的**（K8s） | 「コンテナは常に 3 個あるべき」など **あるべき姿（desired state）** を宣言 | K8s が現在状態を監視し、自動で収束させる |

- この自動収束の仕組みを **リコンシリエーション（調整ループ）** と呼ぶ。例：3 個あるべきなのに 1 個落ちて 2 個になったら、自動で 1 個追加する——これを永続的に繰り返す。
- これが **Infrastructure as Code（IaC）** の本質的な実現方法。YAML ファイルに「あるべき姿」を書けば、インフラ全体を **バージョン管理** できる。
- **kubectl**（kube-control）が CLI ツール。`kubectl apply -f ファイル名` で YAML の内容をクラスタに適用する。

### アーキテクチャ：コントロールプレインとノード

コントロールプレインが **指令塔（脳）**、ノードが **作業員（手足）** という構造。

#### コントロールプレイン（4 コンポーネント）

| コンポーネント | 役割 |
|---------------|------|
| **API Server** | K8s の **心臓部**。ユーザー操作・コンポーネント間通信の **すべて** が API Server を経由する |
| **Scheduler** | 新しい Pod 作成時、**どのノードで動かすか** を決定する |
| **Controller Manager** | 各種 **制御ループ** を管理。リコンシリエーションを実行し、あるべき状態と現在状態の差分を修正する |
| **etcd** | クラスタの **全状態** を保存する分散キーバリュー DB。障害時はクラスタ全体が停止するため、通常は **冗長化** する |

#### ワーカーノード（3 コンポーネント）

| コンポーネント | 役割 |
|---------------|------|
| **kubelet** | ノードの **エージェント**。API Server から指示を受け、コンテナの起動・停止を実行する |
| **kube-proxy** | **ネットワークルーティング** を担当。コンテナへのアクセスを適切に振り分ける |
| **Container Runtime** | コンテナを実際に動かすエンジン。以前は Docker Engine だったが、現在は **containerd** や **CRI-O** が主流 |

- **注意**：ランタイムが変わっても、**Docker で作ったイメージはそのまま K8s で動く**。K8s は特定ランタイムに依存しない柔軟な設計（CRI 規格）になっている。

### 主要リソース

#### Pod（最小単位）

- **1 つ以上のコンテナ** をまとめた最小管理単位。通常は 1 Pod = 1 コンテナ。
- 密接に連携する複数コンテナ（例：Web アプリ + ログ転送の **サイドカー**）を 1 Pod にまとめることもある。
- 同一 Pod 内のコンテナは **ネットワーク名前空間を共有** し、`localhost` で通信できる。
- Pod は **一時的（ephemeral）** に設計される。落ちたら新しい Pod を作り直し、IP も変わる。永続データは **PersistentVolume** に保存する。

#### ラベルとセレクター（接着剤）

- **ラベル**：リソースに付ける **タグ**（例：`app=web`）。名前ではなくラベルで識別する柔軟性が K8s の強み。
- **セレクター**：ラベルでリソースを **選択・紐付け** する。Service がどの Pod に転送するかなど、リソース間の連携はすべてラベル＋セレクターで決まる。

#### Service（アクセス方法）

- Pod は IP が変わるため、**固定の IP や DNS 名** でアクセスする手段が必要——それが Service。
- 複数 Pod をまとめ、**ロードバランシング** も行う。

| 種類 | 用途 |
|------|------|
| **ClusterIP** | クラスタ **内部** のみアクセス可能（デフォルト） |
| **NodePort** | ノードのポートを開放し、**外部からも** アクセス可能 |
| **LoadBalancer** | クラウドプロバイダの **ロードバランサー** と連携 |

#### Deployment（宣言的管理の中核）

- Pod を **宣言的に管理** するリソース。「このアプリを 3 個動かしたい」と宣言すれば、Deployment が実現する。
- Pod が落ちたら **自動再作成**、**ローリングアップデート**（新 Pod を少しずつ増やし、古い Pod を少しずつ減らす）も簡単。
- 裏では **ReplicaSet** が Pod 数を管理しているが、日常の運用では **Deployment だけ意識すれば OK**。

#### その他のリソース

| リソース | 用途 |
|---------|------|
| **ConfigMap** | アプリの **設定値** を管理 |
| **Secret** | パスワード・API キーなど **機密情報** を管理 |
| **PersistentVolume** | データの **永続化** |

### ネットワーク

#### フラットネットワーク設計

- すべての Pod が **同一ネットワーク空間** にあり、IP アドレスで **直接通信** できる（Pod 間通信に NAT は不要）。
- これを実現する **CNI（Container Network Interface）** プラグイン機構がある。

| CNI 実装 | 特徴 |
|---------|------|
| **Flannel** | シンプルで使いやすい |
| **Calico** | **ネットワークポリシー** が強力 |
| **Cilium** | 高性能・高度なセキュリティ機能 |

#### Ingress（外部 HTTP アクセス）

- 外部からの **HTTP/HTTPS アクセス** を制御するリソース。リバースプロキシに相当。
- URL パスで振り分け（例：`example.com/A` → Pod A、`example.com/B` → Pod B）、**SSL 終端** も可能。
- 動作には **Ingress Controller**（NGINX、Traefik、HAProxy など）が必要。K8s は仕組みだけ提供し、実装は選べる。

#### NetworkPolicy（セキュリティ）

- Pod 間の通信を **ルールで制御**（例：「フロントエンドは DB にのみアクセス可能」）。
- マイクロサービスアーキテクチャでは **必須** のセキュリティ機能。

---

### 課題とエコシステム

#### 課題 ①：学習・設定の複雑さ

- 概念が多く、YAML ファイルの記述も大変。**学習コストが高い**。
- 対策：**Helm**（パッケージマネージャー、`helm install wordpress` のように 1 発インストール）、**Kustomize**（YAML 管理の簡素化）などの補助ツールが充実。

#### 課題 ②：クラスタ自体の運用

- バージョンアップ、証明書更新、etcd バックアップなど **運用作業が多い**。
- 対策：**マネージド Kubernetes**——クラウドプロバイダがコントロールプレインを管理する。

| 略称 | 正式名 | 提供元 |
|------|--------|--------|
| **GKE** | Google Kubernetes Engine | Google |
| **EKS** | Amazon Elastic Kubernetes Service | AWS |
| **AKS** | Azure Kubernetes Service | Microsoft |

#### 監視・ログ収集

- Pod が動的に増減するため、従来の監視手法では追いつかない。
- 定番構成：**Prometheus**（監視）+ **Grafana**（可視化）、**EFK スタック**（Elasticsearch + Fluentd + Kibana、ログ収集）。
- K8s は単体ではなく **周辺ツールと組み合わせて使う** のが普通——これを **クラウドネイティブエコシステム** と呼ぶ。
- **CNCF**（Cloud Native Computing Foundation）が関連ツールをまとめて推進している。

#### 今後の進化

- **サービスメッシュ**（Istio など）、**サーバーレス on Kubernetes**（Knative など）など新技術が続々登場。
- K8s はコンテナ管理を超え、**クラウドネイティブアプリの基盤** として確立している。

---

### まとめ：覚えるべきポイント

1. **宣言的管理** が K8s の本質。あるべき姿を YAML で宣言すれば、リコンシリエーションが自動実現する。
2. **Pod**（最小単位）→ **Service**（アクセス方法）→ **Deployment**（宣言的管理）の 3 つが最重要リソース。
3. **ラベル＋セレクター** でリソース同士を柔軟に紐付ける。
4. ネットワークは **フラット設計** + **CNI** + **Ingress** + **NetworkPolicy**。
5. 複雑さは **Helm・マネージド K8s・Prometheus/EFK** などのエコシステムで補える。
6. 手を動かすのが最善——**Minikube** や **Kind** でローカルに無料で K8s 環境を構築できる。
