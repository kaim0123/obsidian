## 要約

本動画（コンテナシリーズ **第 5 回・最終回**）は、コンテナ運用で最も重要な **セキュリティ** を体系的に解説する。コンテナ特有の **5 大リスク** の整理から、**安全なイメージの選び方・管理**、**実行時の防御設定**、**Falco によるランタイム検知**、**インシデント対応**、**シフトレフト・ゼロトラスト** といった今後の方針までをカバーする。タイトルの「3 つの防御テクニック」は、(1) **脆弱性のあるイメージの見分け方**、(2) **コンテナエスケープを防ぐ最小権限の原則**、(3) **Falco を使ったランタイム検知** を指す。

### テーマ：なぜコンテナセキュリティが重要か

- コンテナは便利だが、使い方を誤ると **ホスト全体が侵害** されるリスクがある。
- セキュリティは奥が深いが、**基本を押さえれば十分に対策可能**。
- 本動画で扱う対策は、これまで学んだ監視・開発の知識の上に立つ **最も重要な土台** である。

---

### コンテナの 5 大セキュリティリスク

| # | リスク | 内容 | 具体例 |
|---|--------|------|--------|
| **1** | **イメージの脆弱性** | OS・ライブラリに含まれる既知の脆弱性（CVE）が悪用される | 古い OpenSSL の脆弱性を突かれコンテナ内に侵入される |
| **2** | **設定ミス** | 動いていてもセキュリティホールだらけ、という状態 | root 権限での実行、不要ポートの開放、パスワードのイメージ埋め込み |
| **3** | **コンテナエスケープ** | コンテナから抜け出し **ホスト OS** に侵入する最悪シナリオ | カーネル脆弱性や設定ミスを突かれると、同一ホスト上の全コンテナが危険に |
| **4** | **シークレットの漏洩** | パスワード・API キーなどの機密情報が外部に露出する | `docker history` でイメージ内のシークレットが丸見えになる |
| **5** | **サプライチェーン攻撃** | ソフトウェア供給経路を悪用し、利用者全体を感染させる | 人気 Docker イメージに悪意あるコードを仕込む（**2023 年にも実例あり**） |

- Docker Hub のイメージの **約 50%** に脆弱性がある、という調査結果も紹介される。
- 対策の前提として、**信頼できるソース** からイメージを取得することが重要。

---

### 防御テクニック ①：安全なイメージの選び方と管理

#### イメージの選定

| 方針 | 内容 |
|------|------|
| **公式イメージを使う** | Docker Hub の **Official** バッジ（Docker チーム検証済み）、**Verified Publisher** バッジ（認定企業公開）を確認する |
| **最小限のベースイメージ** | パッケージが少ないほど攻撃面が小さい。**Alpine Linux**（約 5 MB）、**Distroless**（実行に必要な最低限のみ、シェルなし）が推奨される |

#### イメージスキャン（脆弱性チェック）

- イメージ内の全パッケージを調べ、既知の CVE がないか確認する。
- 主なツール：**Trivy**（OSS・無料・人気）、Clair、Snyk、Anchore など。
- Trivy は `trivy image nginx` のように **1 コマンド** でスキャン可能。
- **Critical / High** 以上の脆弱性が見つかったイメージは使用を避ける。

#### CI/CD への組み込み（ベストプラクティス）

- イメージをビルドするたびに **自動スキャン** する。
- 脆弱性があるイメージは **ビルドを失敗** させ、本番デプロイを防ぐ。

#### イメージの署名と検証（上級）

- レジストリ攻撃・中間者攻撃による **改ざん** を防ぐ。
- **Docker Content Trust**、**Sigstore** などで「公式が公開したイメージである」ことを証明する。

---

### 防御テクニック ②：実行時セキュリティ（最小権限の原則）

イメージが安全でも、**実行時の設定ミス** で危険になる。以下を実践する。

#### 基本：root で実行しない

- デフォルトではコンテナは **root 権限** で動作する。乗っ取られると攻撃者も root となり、ホスト攻撃が容易になる。
- **Dockerfile** に `USER` ディレクティブを書き、一般ユーザーで実行する。

#### Linux カーネル機能による制限

| 仕組み | 役割 |
|--------|------|
| **Capabilities（ケーパビリティ）** | root 権限を細分化した権限セット。`--cap-drop` で不要なものを削除し **最小権限** を実現 |
| **Read-only ファイルシステム** | 侵入されてもファイル書き換え・マルウェア設置を防止。ログ・一時ファイル用に **tmpfs** をマウント |
| **seccomp** | 許可しない **システムコール** をブロックし、エクスプロイトを失敗させる |
| **AppArmor / SELinux** | プロセスごとにアクセス可能なファイルを細かく制御する **強制アクセス制御** |

#### ネットワーク分離

- 不要なコンテナ間通信を遮断する。
- Kubernetes では **NetworkPolicy** で設定可能。
- 侵入されても **ラテラルムーブメント**（横方向への拡散）を防ぐ。

---

### 防御テクニック ③：監視・異常検知（ランタイムセキュリティ）

#### パフォーマンス監視との違い

| 種類 | 見るもの |
|------|----------|
| **パフォーマンス監視**（前回） | 遅い・落ちている・リソース逼迫 |
| **セキュリティ監視**（本回） | 普段しないコマンドの実行、未知プロセスの起動など **怪しい動き** |

#### Falco（CNCF プロジェクト）

- **システムコールを監視** し、ルール違反時にアラートを発する **ランタイムセキュリティツール**。
- 検知例：コンテナ内での **シェル起動**、`/etc/passwd` の変更など。
- ルールは **カスタマイズ可能**（例：「このコンテナでは `curl` は使わないはず」）。
- その他の有名ツール：Sysdig、Aqua Security など。

#### ログ収集と監査

- コンテナは頻繁に起動・停止するため、消える前にログを **中央サーバーへ集約** する（Fluentd、Logstash、Loki など）。
- **Kubernetes 監査ログ**：API へのアクセス（誰が・いつ・何をしたか）を記録し、不正調査の証拠とする。

#### インシデント対応の流れ

1. **隔離** — 侵害されたコンテナのネットワークを切断し、影響を封じ込める
2. **フォレンジック** — メモリダンプ・ログ解析で攻撃手口を特定する
3. **再発防止** — 対策を強化し、同じ攻撃を受けないようにする

---

### セキュリティのベストプラクティスと今後の潮流

#### シフトレフト

- 開発の **早い段階**（コーディング・ビルド時）からセキュリティチェックを行う。
- 従来の「開発完了後にチェック」より修正コストが低い。

#### ゼロトラスト

- 「内部ネットワークは安全」という前提を捨て、**すべてを疑う** モデル。
- コンテナ同士の通信でも **毎回認証・認可** を行う。
- **サービスメッシュ**（Istio、Linkerd など）が通信の暗号化・認可を自動化し、ゼロトラストを実装しやすくする。

#### 今後のトレンド

- **AI による脅威検知**、**自動修復機能** など、自動化・インテリジェント化が進む。
- セキュリティは **一度やったら終わりではなく**、継続的な学習と改善が必要。
