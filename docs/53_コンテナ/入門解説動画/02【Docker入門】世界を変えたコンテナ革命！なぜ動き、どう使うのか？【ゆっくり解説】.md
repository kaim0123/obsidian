## 要約

**Docker** は、コンテナ技術の **デファクトスタンダード** として、開発環境を **イメージ** というパッケージにまとめ、「私のマシンでは動いた」という **環境依存の地獄** を終わらせたツールである。本動画（シリーズ第 2 回）は、**2013 年の誕生と普及の背景**、**クライアント・デーモン・レジストリの 3 要素**、**Dockerfile によるイメージ構築**、**ネットワーク・ストレージの仕組み**、**Compose と Kubernetes の使い分け**、**セキュリティ**、**containerd との関係** までを解説する。

### テーマ：Docker が解決した問題

- **環境依存**：開発者の PC では動くのに、本番サーバーでは OS の違いやライブラリの競合で動かない——原因究明に数日かかることもあった。
- **セットアップの負担**：新メンバーの開発環境構築に **丸 1 日** かかり、手順通りでも動かないケースが頻発。
- **Docker の解決策**：アプリと実行環境を **Docker イメージ** にまとめて渡すだけで、誰の PC でも同じように動く。セットアップが **数分〜数秒** で完了する。
- 技術力だけでなく **使いやすさ**（シンプルなコマンド、分かりやすいエラーメッセージ、充実したドキュメント）も普及の要因。

### 誕生と成長の歴史

| 時期 | 出来事 |
|------|--------|
| **2013 年 3 月** | PaaS 企業 **dotCloud** が社内ツールを **オープンソース** として公開——これが Docker の始まり |
| **2013 年 10 月** | 人気の高まりに伴い dotCloud が社名を **Docker Inc.** に変更 |
| **2014 年 6 月** | **Docker 1.0** リリース。企業での本格利用が始まる |

- 公開から間もなく開発者の間で大ブームに。単なる仮想化ツールではなく、**開発ワークフロー全体を変えた** 革命的なツールとして位置づけられる。

### アーキテクチャ：3 つの主要パーツ

| コンポーネント | 役割 |
|---------------|------|
| **Docker クライアント** | ユーザーが直接触る部分。`docker run`・`docker build` などのコマンドを受け付け、デーモンへ命令を伝える **仲介役** |
| **Docker デーモン** | バックグラウンドで常時動作する **実働部隊**。コンテナの起動・停止、イメージ管理、ネットワーク設定などを実行 |
| **Docker レジストリ** | イメージの **保存・配布** 場所。代表例は **Docker Hub**（GitHub の Docker 版） |

- **クライアントとデーモンは別マシンでも可**：**REST API**（HTTP 通信）で連携するため、手元の PC からリモートサーバーの Docker を操作できる。
- **Docker Hub** には世界中の開発者が公開したイメージが集まり、nginx などを **ゼロから作らず** にすぐ利用できる。

### Docker イメージと Dockerfile

- **Dockerfile**＝イメージを作るための **設計図・レシピ**。OS の準備、ライブラリのインストール、コードのコピーといった手順を記述する。
- 各命令（`RUN`・`COPY` など）は **新しいレイヤー** を 1 枚追加する（前回解説のミルフィーユ構造）。

**Dockerfile 作成の 3 つのポイント**：

1. **ベースイメージを使う**——ゼロから作らず、公式イメージ（例：`python:3.9`）を土台にする。Python などが最初から入った状態からスタートできる。
2. **レイヤーの最適化**——変更頻度の低い処理（ライブラリのインストール）を **前** に、高い処理（アプリコードのコピー）を **後** に書く。Docker はレイヤーを **キャッシュ** するため、コード変更時もライブラリ部分を再利用でき、ビルドが高速化する。
3. **マルチステージビルド**（上級）——1 つの Dockerfile 内で **ビルド段階** と **実行段階** を分離。コンパイル用ツールを最終イメージに含めず、実行に必要なファイルだけコピーする → イメージサイズを **数百 MB 単位** で削減できる場合がある。

### ネットワーク

- Docker は **libnetwork** ライブラリでネットワークを管理する（前回のブリッジモード・ホストモードなどを実現）。
- **ブリッジネットワーク**：`docker0` という **仮想ブリッジ**（仮想スイッチングハブ）を作り、コンテナ同士を接続。各コンテナには仮想的な LAN ケーブルが繋がっているイメージ。
- **組み込み DNS**：IP アドレスを覚えなくても、**コンテナ名**（例：`app`）で他のコンテナにアクセスできる。

### ストレージ（ストレージドライバー）

- ファイルシステムの管理方法を担う。**レイヤー構造とコピーオンライト（CoW）** を実現する中核部分。
- **overlay2** が現在の主流：複数のディレクトリを重ねて 1 つに見せる技術。**下層は読み取り専用**、**上層に書き込み**——前回解説の CoW と同じ原理。
- 他に device mapper や Btrfs などもあるが、overlay2 が **パフォーマンス・安定性** で優位。最近の Docker は自動で overlay2 を選択する。

### 実践的な使い方

| 環境 | 推奨ツール | 理由 |
|------|-----------|------|
| **開発** | **Docker Compose** | Web サーバー・DB・キャッシュなど複数コンテナを `docker-compose.yml` に定義し、`docker compose up` **1 コマンド** で一括起動 |
| **本番（大規模）** | **Kubernetes（K8s）** | 数百〜数千コンテナの管理には Compose では力不足。自動スケール・障害復旧など高度なオーケストレーションが必要 |

- 定番の組み合わせ：**開発は Compose、本番は Kubernetes**。

### セキュリティ

- **デーモンの権限**：Docker デーモンは基本的に **root（管理者）権限** で動作する。Docker を操作できる人は、実質的にホストの root 権限を持つのと同等。
- **Rootless モード**：root なしで動かすモードが開発されたが、一部機能に制限があり、完全移行はまだ進行中。
- **イメージの安全性**：Docker Hub には誰でもイメージを公開できるため、悪意あるコードが仕込まれたイメージのリスクがある。
  - **公式イメージ** や **Verified Publisher** マーク付きイメージを使う。
  - **Trivy** などのツールでイメージの **脆弱性スキャン** を行う。

### Docker の今後と containerd

- Docker は今や **開発の標準ツール**。ただし本番のコンテナランタイムとしては **containerd**（Docker から分離した軽量ランタイム）の採用が増えている。
- Kubernetes では Docker ではなく **containerd を直接** 使うケースが増加——本番ではより軽量なランタイムが好まれる。
- **学んだ知識はそのまま活かせる**：イメージ形式（OCI）や基本概念は共通。Docker は引き続き **コンテナ技術の入り口** として重要な役割を果たす。

### まとめ

- Docker は 2013 年 dotCloud による公開から爆発的に普及し、**ソフトウェア開発の標準ツール** となった。
- **クライアント・デーモン・レジストリ** の連携、**Dockerfile とレイヤーキャッシュ**、**libnetwork と overlay2** が、その快適さと効率の土台である。
- 実務では **Compose（開発）＋ Kubernetes（本番）** の使い分けが定番。セキュリティ（Rootless・イメージ検証）にも注意が必要。
- 次回（第 3 回）は **Kubernetes** によるコンテナオーケストレーションを解説予定。
