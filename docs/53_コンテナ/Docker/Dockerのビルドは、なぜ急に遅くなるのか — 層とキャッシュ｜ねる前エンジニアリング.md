## 詳しい要約

**テーマ：Docker イメージの「層」と「ビルドキャッシュ」**

Docker のイメージは Dockerfile の命令 1 つごとにできる層の積み重ねで、どこかの層が変わるとその上の層は命令が同じでも全部作り直しになる。だから変わりにくい依存の取り込みを下（先）に、変わりやすいソースコードを上（後）に置く。また、上の層で消したファイルも下の層には残るので、秘密の鍵は最初から層に入れない。

---

### よくある 4 つの場面

- 画面の文字を 1 文字直しただけでビルドに 2 分かかる
- 昨日まで 10 秒だったビルドが急に遅くなった
- 手元では速いのに CI では毎回最初から作り直しになる
- 消したはずの鍵がイメージの中から見つかった
- これらはすべて **層とキャッシュ** という同じ仕組みから来ている

### 層とキャッシュの基本

- 例の Dockerfile は 5 命令：土台（OS と Node.js 入りのベースイメージ）→ 作業場所の作成 → ファイルを全部コピー → 依存の部品をネットから取り込み → 起動コマンド
- **命令 1 つごとに層が 1 枚**でき、各層は「下の層に比べて何が増えたか（差分）」だけを持つ（ミルフィーユのような重なり）
- 1 回目は依存の取り込みに約 2 分かかる
- Docker は作った層を手元に取っておく（**ビルドキャッシュ**）。何も変えずに 2 回目を実行すると全層が再利用され一瞬で終わる
- 「前と同じか」の判定：命令を実行する層は**命令の文字列**で、ファイルをコピーする層は**コピーするファイルから作った指紋（ハッシュ）**で比べる

### 1 か所変えると上が全部作り直し

- `app.js` を 1 文字直すと「全部コピー」層の指紋が変わり作り直し。ここまでは当然
- 問題はその上の依存取り込み層。命令は同じなのに作り直しになり、また 2 分かかる
- 理由：依存の層は「下のファイルが揃った状態」の上で命令を実行した結果の差分。下が変われば同じ結果になるかは分からず、Docker は命令の中身までは調べないので**安全側に倒して作り直す**（積み木の下段を差し替えたら上段も積み直すのと同じ）
- 原則：**変わりにくいものは下、変わりやすいものは上**

### 順番を入れ替える

- 書き換え後：まず部品の一覧（`package.json` など、`package` で始まり `.json` で終わるファイル）だけをコピー → 依存を取り込む → 残りのファイルを全部コピー
- これで `app.js` を直しても依存の層はキャッシュが効き、2 分 → **2 秒**に
- 命令は 1 つ増えただけ。部品の一覧を変えた日は依存の層から作り直しになるが、それは本当に変わったので正しい

### 関係ないファイルで作り直しになる

- 「全部コピー」には Git の履歴、実行時に出るログファイル、手元で入れた部品フォルダーまで入る
- ログが 1 行増えただけで指紋が変わり作り直しに。コピー量が多いとコピー自体も遅くなる（大量の部品フォルダーを毎回ビルド係に送ることになる）
- 対策：**`.dockerignore`** にコピーしないもの（Git 履歴、ログ、手元の部品フォルダー、機密の鍵ファイル）を書く

### CI では毎回最初から

- CI のビルド機は使い終わったら捨てられる真っさらなマシンなので、前の層の控えを持っていない
- キャッシュは作ったマシンの中にしかなく、別のマシンからは見えない
- 対策：**キャッシュを外の置き場に送り、次のビルドの最初に取ってくる**。設定方法は CI ごとに違うので考え方だけ押さえればよい

### 消したはずの鍵が残る

- 非公開の部品を取り込むために鍵ファイルをコピー → 取り込み → 鍵を削除、という Dockerfile は一見きちんとしている
- しかし削除の層は「ここから上では見えないことにする」差分を足すだけで、**鍵を含む下の層はイメージに残る**。イメージを手に入れた人は層を 1 枚ずつ取り出して読める
- 対策：鍵を層に入れない。**シークレットのマウント**を使えば、命令を実行する間だけ鍵が見え、層には残らない

### AI に Dockerfile を書かせたときのチェックポイント

1. 全部コピーする命令が、重い依存取り込みの命令より上にないか
2. 部品の一覧だけを先にコピーしているか
3. `.dockerignore` があり、履歴やログが書かれているか
4. 鍵や合言葉をファイルでコピーしたり、ビルド引数に書いたりしていないか（引数も記録に残ることがある）
5. CI でキャッシュを外に置く設定があるか

- どれも 1 回ビルドしただけでは分からない。2 回目・3 回目に何がどれだけ作り直されるかを想像するのがレビューの仕事

### ケーススタディ：毎回 3 分のビルド

- Python アプリの Dockerfile が「作業場所 → 全部コピー → 部品一覧を見て取り込み」の順で、テストを 1 文字直すたびに 3 分かかる
- 選択肢：A 毎回キャッシュを全部消す／B 部品の一覧を先にコピーして取り込んでから全部コピー／C 取り込み命令の文字を毎回変える
- 正解は **B**。A は毎回が 1 回目と同じになりかえって遅いまま、C は命令が変わればその層から作り直しになるのでわざと遅くするだけ
- 遅さの原因はキャッシュではなく「キャッシュが使えない順番」になっていたこと

### まとめ

- イメージは命令ごとの層の積み重ねで、変わった層から上は全部作り直しになる
- 依存のような変わりにくいものを下、自分のコードのような変わりやすいものを上に置く
- `.dockerignore` で無関係なファイルを除き、CI ではキャッシュを外に置く
- 上の層で消しても下の層に残るので、秘密は最初から層に入れない（シークレットのマウントを使う）
