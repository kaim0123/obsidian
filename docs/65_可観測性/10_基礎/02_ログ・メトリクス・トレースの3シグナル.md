# ログ・メトリクス・トレースの3シグナル

システムの外に出すデータ（テレメトリ）は、主に **ログ・メトリクス・トレース** の 3 種類に分けられます。OpenTelemetry ではこれらを **シグナル（Signal）** と呼び、最近は 4 つ目として **プロファイル** も加わりました。この章では、それぞれの形・得意なこと・コストを比べ、どう組み合わせるかを整理します。

---

## 1. 3つのシグナルの比較

| シグナル | 形 | 得意なこと | 苦手なこと | コストの特徴 |
|----------|----|------------|------------|--------------|
| **ログ** | 1 件ずつのイベント（時刻 + メッセージ + 属性） | 「その時に何が起きたか」の詳細 | 全体の傾向、サービスをまたぐ流れ | 量に比例して増える（最も高くつきやすい） |
| **メトリクス** | 時系列の数値（名前 + ラベル + 値） | 傾向、閾値アラート、長期保存 | 個々のリクエストの詳細 | 量ではなくラベルの組み合わせ数で決まる |
| **トレース** | リクエスト 1 件の処理の木（スパンの集まり） | サービスをまたぐ流れ、どこで時間がかかったか | 全件保存（サンプリングが必要） | リクエスト数 × スパン数 |

---

## 2. ログ

```json
{"level":"error","time":"2026-09-26T10:15:03.120Z","msg":"payment failed",
 "trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","user_id":"u_123",
 "provider":"stripe","status_code":502,"duration_ms":1830}
```

- **離散的なイベント**の記録です。エラーの詳細、監査記録、業務イベントに向きます。
- **構造化（JSON）** にすれば、あとから属性で検索・集計できます（[[01_構造化ログ]]）。
- 「リクエスト 1 件につき、属性を詰め込んだ 1 行」を出す **Wide Event（広いイベント）** という考え方は、『Observability Engineering』が推奨する形です。

---

## 3. メトリクス

```text
http_requests_total{method="POST",route="/checkout",status="500"} 42
http_request_duration_seconds_bucket{route="/checkout",le="0.5"} 9120
```

- **集計済みの数値**です。1 分間のリクエスト数、p99 レイテンシ、CPU 使用率など。
- データ量がリクエスト数に依存しないので、**安く長く保存**でき、アラートに向きます。
- その代わり、集計した時点で個々のリクエストの情報は失われます。「なぜ」を調べるには他のシグナルが必要です。
- 種類は [[01_メトリクスの種類（カウンタ・ゲージ・ヒストグラム）]] で扱います。

---

## 4. トレース

```text
trace_id=4bf9...  POST /checkout                       ████████████████ 2.1s
  ├─ span  auth.verify                                 █ 20ms
  ├─ span  SELECT orders                               ██ 80ms
  └─ span  HTTP POST api.stripe.com                    ████████████ 1.8s
```

- 1 つのリクエストが、どのサービス・どの処理を通り、**どこで時間を使ったか**を木構造で表します。
- 各処理の単位を **スパン**、全体を束ねる ID を **trace_id** と呼びます（40_分散トレース）。
- 全件保存は高いので、**サンプリング**して一部だけ残すのが普通です。

---

## 5. 4つ目のシグナル：プロファイル

- **継続的プロファイリング**（Continuous Profiling）は、本番で CPU やメモリを「どの関数が使っているか」を常時サンプリングします。
- OpenTelemetry でも Profiles シグナルの仕様化が進んでいます。
- 「CPU が高い」はメトリクスで分かり、「どの関数のせいか」はプロファイルで分かる、という関係です（66_パフォーマンス）。

---

## 6. 組み合わせ方：調査の流れ

| ステップ | 使うシグナル | 問い |
|----------|--------------|------|
| 1. 気づく | メトリクス（アラート） | 何か悪くなっていないか？ |
| 2. 範囲を絞る | メトリクス（ラベルで分解） | どの API・どのリージョンか？ |
| 3. 具体例を見る | トレース | 遅い / 失敗したリクエストはどこで時間を使ったか？ |
| 4. 詳細を読む | ログ | そのとき何が起きていたか（エラーメッセージ、入力）？ |
| 5. コードまで下りる | プロファイル | どの関数が重いか？ |

この流れを滑らかにするには、**シグナル間を ID でつなぐ**ことが欠かせません。ログに `trace_id` を入れる、メトリクスに代表トレースを紐づける（Exemplar）といった工夫です（[[04_ログ・メトリクス・トレースの相関]]）。

---

## 7. どれから始めるか

| 状況 | 最初にやること |
|------|----------------|
| ログが文字列で `console.log` だけ | 構造化ログ + リクエスト ID |
| アラートがない | RED メトリクス（リクエスト数・エラー・レイテンシ） |
| サービスが 3 つ以上に分かれている | 分散トレース |
| CPU・メモリの原因がいつも分からない | 継続的プロファイリング |
