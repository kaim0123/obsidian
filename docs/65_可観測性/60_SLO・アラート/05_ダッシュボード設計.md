# ダッシュボード設計

ダッシュボードは、アラートを受けた人が「**何が、どこで、どのくらい悪いか**」を数十秒でつかむための道具です。パネルを思いつくまま並べると、障害時に目的のグラフが見つかりません。この章では、ダッシュボードの階層の作り方、RED・USE に沿ったレイアウト、Grafana でのダッシュボードのコード管理を説明します（Grafana 公式ドキュメント「Dashboard best practices」が下敷き）。

---

## 1. ダッシュボードの目的を分ける

1 枚のダッシュボードに全部載せず、**見る人と目的ごとに分けます**。

| 種類 | 見る人 | 載せるもの |
|------|--------|------------|
| **SLO ダッシュボード** | プロダクト責任者・チーム全員 | SLI の現在値、残り予算、バーンレート |
| **サービス概要** | オンコール担当 | RED（リクエスト数・エラー・所要時間）、依存先の状態 |
| **リソース詳細** | 調査する人 | USE（CPU・メモリ・ディスク・コネクションプール） |
| **個別コンポーネント** | そのコンポーネントの担当 | DB・キュー・キャッシュ固有の指標 |

---

## 2. 上から下へ掘り下げる階層

障害時の調査は「全体 → サービス → リソース」の順に進みます。ダッシュボードもこの順に**リンクでつなぎます**。

```
[全体：全サービスの SLO 一覧]
      ↓ 赤いサービスをクリック
[サービス概要：RED + 依存先]
      ↓ 遅いエンドポイント・ホストをクリック
[リソース詳細：USE、プロファイル]
      ↓ 時刻範囲を保ったまま
[ログ（Loki）・トレース（Tempo）]
```

- Grafana の**データリンク**と**ダッシュボードリンク**で、時刻範囲と変数（`service`、`instance`）を引き継いで移動できるようにする
- 最後はログとトレースに飛べるようにしておく（[[04_ログ・メトリクス・トレースの相関]]）

---

## 3. RED レイアウト（サービス概要）

リクエストを処理するサービスは、**RED** の 3 行を上から並べます（[[02_REDメソッドとUSEメソッド]]）。

| 行 | パネル | PromQL の例 |
|----|--------|-------------|
| **Rate** | 秒間リクエスト数（エンドポイント別） | `sum by (route) (rate(http_requests_total[5m]))` |
| **Errors** | エラー率（%） | `sum(rate(http_requests_total{code=~"5.."}[5m])) / sum(rate(http_requests_total[5m]))` |
| **Duration** | p50 / p95 / p99 レイテンシ | `histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))` |

- 左に「今の値」の Stat パネル、右に時系列グラフを置くと、現在値と推移が同時に見える
- SLO のしきい値（例：エラー率 0.1%、p99 300ms）を**グラフに線で引いておく**。正常かどうかを考えずに判断できる

---

## 4. USE レイアウト（リソース詳細）

CPU・メモリ・ディスク・ネットワークなどのリソースは **USE** で並べます。

| リソース | Utilization（使用率） | Saturation（飽和） | Errors |
|----------|----------------------|--------------------|--------|
| CPU | CPU 使用率 | ロードアベレージ・スロットリング | — |
| メモリ | 使用量 / 上限 | スワップ・OOM Kill 回数 | — |
| ディスク | 使用率・I/O 使用率 | I/O 待ちキュー長 | I/O エラー |
| DB コネクションプール | 使用中の接続数 / 最大 | 接続待ちの数・時間 | 接続失敗 |

## 5. 見やすくするための約束事

| 約束事 | 理由 |
|--------|------|
| 1 画面に 10〜15 パネルまで | スクロールしないと見えない位置のパネルは見られない |
| 重要なものを左上に | 人の目は左上から見る |
| 単位を必ず設定（ms、%、req/s） | 「0.3」が秒なのか割合なのか迷わない |
| 色は「正常=緑、注意=黄、異常=赤」に統一 | 色の意味をダッシュボードごとに変えない |
| Y 軸を 0 から始める（率・件数） | 小さな変動が大事件に見えるのを防ぐ |
| デプロイを**アノテーション**で表示 | 「デプロイ直後から悪化」が一目でわかる |
| パネルに説明文（Description）を書く | 何を見ればよいかがわからない人のために |

---

## 6. ダッシュボードをコードで管理する

GUI で作ったダッシュボードは、誰かがうっかり変えると元に戻せません。**コードとして Git で管理**します。

| 方法 | 内容 |
|------|------|
| **JSON を Git に保存** | Grafana からエクスポートした JSON をそのまま管理。手軽だが差分が読みにくい |
| **プロビジョニング** | Grafana 起動時にディレクトリの JSON を読み込む設定 |
| **Grafonnet（Jsonnet）** | ライブラリで部品化して生成。RED パネルなどを使い回せる |
| **Terraform の Grafana プロバイダー** | データソースやフォルダ、アラートもまとめて管理 |
| **Grafana Foundation SDK** | TypeScript / Go などでダッシュボードを定義 |

```yaml
# /etc/grafana/provisioning/dashboards/default.yaml
apiVersion: 1
providers:
  - name: default
    folder: Services
    type: file
    options:
      path: /var/lib/grafana/dashboards   # Git から配置した JSON を読む
```

- 変数（`$service`、`$env`）を使い、**サービスごとに同じテンプレート**を使い回す
- 新しいサービスを作ったら、テンプレートから自動で概要ダッシュボードができる状態が理想
