# SLI・SLOの設計

**SLI（Service Level Indicator）**は「サービスがうまく動いているか」を表す測定値、**SLO（Service Level Objective）**はその SLI に対する目標値です。「どのくらい信頼性が必要か」という**方針**は 67 の [[02_リスクの受け入れと信頼性目標]] で扱いました。この章では、それを**実際に計測できる形に落とす方法**、つまり SLI の定義の仕方・測る場所・集計の窓を説明します（Google SRE Workbook 2 章「Implementing SLOs」が下敷き）。

---

## 1. SLI・SLO・SLA の関係

| 用語 | 意味 | 例 |
|------|------|-----|
| **SLI** | 良し悪しを表す測定値（比率で表すのが基本） | 成功したリクエスト ÷ 全リクエスト |
| **SLO** | SLI の社内目標 | 30 日ローリングで 99.9% |
| **SLA** | 顧客との契約。破ると返金などのペナルティ | 月間 99.5% を下回ったら 10% 返金 |

- SLO は **SLA より厳しく**しておく。SLO を割った時点で手を打てば、SLA 違反を防げる
- SLI は「**良いイベント ÷ 有効なイベント**」の比率で書くと、0〜100% にそろって扱いやすい

---

## 2. SLI の仕様と実装を分ける

SRE Workbook では、SLI を 2 段階で書くことを勧めています。

| 段階 | 書くこと | 例 |
|------|----------|-----|
| **SLI の仕様（specification）** | ユーザーにとって何が大事か。計測方法には触れない | 「商品一覧ページが 300ms 以内に表示される割合」 |
| **SLI の実装（implementation）** | 具体的にどこで何を数えるか | 「ロードバランサーのログで `/products` への 2xx 応答のうち、`target_processing_time < 0.3` の割合」 |

仕様を先に決めることで、「測りやすいもの」ではなく「**ユーザーが困ること**」を指標にできます。実装は後から改善できます。

---

## 3. サービスの種類ごとの代表的な SLI

| サービスの種類 | SLI の種類 | 良いイベントの定義例 |
|----------------|------------|----------------------|
| リクエスト/レスポンス（Web API） | **可用性** | 5xx 以外で応答したリクエスト |
| | **レイテンシ** | 300ms 以内に応答したリクエスト |
| | **品質** | 縮退（フォールバック）せずに応答したリクエスト |
| データ処理（バッチ・パイプライン） | **鮮度** | 10 分以内に更新されたデータの割合 |
| | **正しさ** | 検証に通った出力の割合 |
| | **網羅性** | 期限内に処理された入力の割合 |
| ストレージ | **耐久性** | 読み出せたオブジェクトの割合 |

- 最初は **可用性とレイテンシの 2 つ**から始めれば十分
- レイテンシは「平均」ではなく「**しきい値以内の割合**」で書く（例：p99 ではなく「300ms 以内が 99%」）。こうすると可用性と同じ比率の形で扱える

---

## 4. どこで測るか

| 計測点 | 長所 | 短所 |
|--------|------|------|
| **アプリのメトリクス**（Prometheus など） | 細かく分類できる、実装が簡単 | アプリが落ちていると数えられない |
| **ロードバランサー / API ゲートウェイ** | アプリ停止も「失敗」として数えられる | ブラウザ側の問題は見えない |
| **合成監視（外形監視）** | ユーザーと同じ経路で確認できる | リクエスト数が少なく統計的に粗い |
| **クライアント計測（RUM）** | 実際の体験に最も近い | ノイズが多い（端末・回線の問題も混ざる） |

最初は**ロードバランサーのログかアプリのメトリクス**が現実的です。ユーザー体験とのずれが気になったら、合成監視や RUM を足します。

---

## 5. 集計の方式と窓

### リクエストベースとウィンドウベース

| 方式 | 数え方 | 向いているもの |
|------|--------|----------------|
| **リクエストベース** | 成功リクエスト ÷ 全リクエスト | トラフィックの多い Web API |
| **ウィンドウベース** | 「良い 1 分間」の数 ÷ 全体の分数（例：その 1 分の p95 が 300ms 以内なら良い） | トラフィックが少なく、1 件の失敗で比率が大きく揺れるサービス |

リクエストベースのほうが「ユーザーが何件困ったか」に直結するので、基本はこちらを使います。

### 期間

- **ローリング窓（直近 28 日・30 日）**が基本。月初にリセットされるカレンダー窓だと、月末に「まだ余裕がある」という誤った判断を招きやすい
- 28 日にすると、曜日の数がそろう（どの窓にも月曜が 4 回ずつ含まれる）
- 報告用にはカレンダー月の数字も並べておくと、SLA との照合がしやすい

## 6. PromQL で書く例

HTTP サーバーのメトリクス `http_requests_total{code}` と、ヒストグラム `http_request_duration_seconds_bucket` がある前提です。

```promql
# 可用性 SLI（直近 30 日）
sum(rate(http_requests_total{job="api", code!~"5.."}[30d]))
/
sum(rate(http_requests_total{job="api"}[30d]))

# レイテンシ SLI：300ms 以内に返したリクエストの割合（直近 30 日）
sum(rate(http_request_duration_seconds_bucket{job="api", le="0.3"}[30d]))
/
sum(rate(http_request_duration_seconds_count{job="api"}[30d]))
```

- ヒストグラムのバケット境界（`le`）に **SLO のしきい値と同じ値**を用意しておく。境界がないと正確に数えられない（[[04_パーセンタイルとヒストグラムの集計]]）
- 30 日分の `rate` は重いので、実運用では**記録ルール（recording rule）**で短い窓を事前集計してから足し合わせる（[[01_Prometheus]]）

## 7. SLO ドキュメントに書くこと

| 項目 | 例 |
|------|-----|
| サービスと利用者 | 商品検索 API（Web フロントとアプリから呼ばれる） |
| SLI の仕様 | 検索結果が 500ms 以内に正しく返る割合 |
| SLI の実装 | ALB ログ。`/search` の 2xx かつ応答時間 < 0.5s。ヘルスチェックは除外 |
| SLO と窓 | 28 日ローリングで 99.5% |
| 除外するもの | 4xx（利用者側の誤り）、社内の負荷テスト |
| エラーバジェット方針 | [[03_エラーバジェット方針]] へのリンク |
| 見直し時期・責任者 | 四半期ごと・検索チーム |

「**何を失敗と数えるか**」を 1 か所に書いておくことが最重要です。定義があいまいだと、障害のたびに「このエラーは数えない」という議論が始まります。
