# アラート設計の原則

アラートは「**人間が今すぐ何かをしなければならない**」ときにだけ鳴らすものです。鳴りすぎれば無視されるようになり、本当の障害を見逃します。この章では、何をアラートにし、何をしないかの判断基準と、Prometheus Alertmanager での振り分け方を説明します（Google SRE 本 6 章「Monitoring Distributed Systems」、Rob Ewaschuk「My Philosophy on Alerting」が下敷き）。受ける側の運用は 67 の [[03_ページングとアラートの受け方]] で扱います。

---

## 1. アラートにしてよい条件

1 つのアラートを追加するたびに、次の問いに答えます。

| 問い | 「いいえ」なら |
|------|----------------|
| ユーザーに影響が出ている、または近いうちに出るか | ダッシュボードかログで十分 |
| 人が対応しないと解決しないか | 自動復旧に任せる |
| 対応が**今すぐ**必要か | チケットにする（翌営業日に対応） |
| 受けた人が**具体的に何をすればよいか**わかるか | ランブックを先に書く（[[02_ランブックの書き方]]） |
| 同じ問題で他のアラートも鳴っていないか | 重複を消す |

すべて「はい」のものだけを**ページ**（夜中でも起こす）にします。

---

## 2. 症状ベースと原因ベース

| 種類 | 例 | 評価 |
|------|-----|------|
| **症状ベース** | 「エラー率が SLO を割るペース」「決済が 5 分間成功しない」 | ユーザー影響と直結。**ページはこちらを使う** |
| **原因ベース** | 「CPU 90%」「ディスク 80%」「Pod が再起動した」 | 影響がないことも多い。誤報の元 |

- CPU 90% でもレスポンスが速いなら問題ない。逆に CPU 30% でも DB ロックで全リクエストが失敗していることがある
- 原因ベースの指標は、**症状のアラートが鳴った後の調査用**としてダッシュボードに置く
- 例外：**近い将来に確実に影響が出る**もの（ディスクが 4 時間後に満杯になる、証明書が 7 日後に切れる）は原因ベースでもアラートにしてよい

```promql
# ディスクが 4 時間以内に満杯になる予測（predict_linear）
predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 4 * 3600) < 0
```

## 3. 重大度を 2〜3 段階に絞る

| 重大度 | 通知先 | 期待する反応 |
|--------|--------|--------------|
| **page** | PagerDuty / Opsgenie（電話・プッシュ） | 数分以内に対応開始。夜中でも起きる |
| **ticket** | チケット・Slack の専用チャンネル | 営業時間内に対応 |
| （記録のみ） | ダッシュボード・ログ | 通知しない。調査時に見る |

「warning」「info」「notice」など段階を増やしすぎると、誰も見ないチャンネルができるだけです。**「起こすか、起こさないか」の 2 択**に近づけるのがコツです。

---

## 4. アラート疲れを防ぐ

| 症状 | 対策 |
|------|------|
| 同じアラートが何度も鳴る | `for:` で継続時間を条件にする。Alertmanager の `repeat_interval` を長くする |
| 1 つの障害で 50 件鳴る | Alertmanager の**グルーピング**と**抑制（inhibit）** |
| 鳴っても「いつものこと」で無視される | そのアラートを消すか、閾値を見直す。**放置されるアラートは存在しないより悪い** |
| 夜間に対応不要なアラートで起こされる | ticket に下げる |

### 定期的な棚卸し

- 週次または月次で「**鳴ったアラートの一覧**」を振り返る
- 各アラートに「対応した / 誤報 / 対応不要だった」を記録し、誤報率の高いものから直す
- 目安：オンコール 1 シフトあたりのページは **2 件以下**（SRE 本 11 章）

## 5. Alertmanager での振り分け

```yaml
route:
  receiver: slack-default
  group_by: ["alertname", "service"]
  group_wait: 30s        # 最初の通知まで待って、同時に来たアラートをまとめる
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - matchers: ['severity="page"']
      receiver: pagerduty
    - matchers: ['severity="ticket"']
      receiver: slack-tickets

inhibit_rules:
  # サービス全体が落ちているときは、個別エンドポイントのアラートを抑制する
  - source_matchers: ['alertname="ServiceDown"']
    target_matchers: ['severity="ticket"']
    equal: ["service"]

receivers:
  - name: pagerduty
    pagerduty_configs:
      - routing_key: "<secret>"
  - name: slack-tickets
    slack_configs:
      - channel: "#alerts-tickets"
  - name: slack-default
    slack_configs:
      - channel: "#alerts"
```

- **グルーピング**：同じサービスの複数アラートを 1 通にまとめる
- **抑制**：上位の障害が起きているときに、その結果として起きる下位のアラートを黙らせる
- **サイレンス**：メンテナンス中など、一時的に特定のアラートを止める（期限付きで設定する）

## 6. 良いアラートの書き方

| 要素 | 書くこと |
|------|----------|
| 名前 | 何が起きているかがわかる名前（`APIErrorBudgetBurnFast`） |
| summary | 1 行で状況を説明 |
| description | 現在値、影響、どのくらい急ぐか |
| runbook_url | 最初に何をするかの手順書 |
| dashboard_url | 関連するダッシュボードへの直リンク |
| labels | `severity`、`service`、`team`（振り分けに使う） |
