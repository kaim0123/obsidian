# 可観測性ツールの比較と選び方

可観測性のツールは、**OSS を自分で運用する**か、**商用 SaaS に任せる**か、**クラウド事業者の標準機能を使う**かの 3 つに大きく分かれます。どれも「ログ・メトリクス・トレースを集めて見る」という点は同じですが、コストの構造と運用の手間が大きく違います。この章では、代表的なツールの特徴と、選ぶときの判断基準をまとめます。

---

## 1. 3 つの選択肢

| 選択肢 | 代表例 | 長所 | 短所 |
|--------|--------|------|------|
| **OSS を自前運用** | Prometheus + Grafana + Loki + Tempo、Jaeger、OpenSearch | ライセンス費用なし。データを手元に置ける。自由に拡張できる | 運用する人が必要。スケールさせるほど難しくなる |
| **商用 SaaS** | Datadog、New Relic、Honeycomb、Grafana Cloud、Dynatrace | 導入が速い。機能が統合されている。運用不要 | 量に応じて費用が急増しやすい。ベンダーロックイン |
| **クラウド標準** | Amazon CloudWatch・X-Ray、Google Cloud Observability、Azure Monitor | そのクラウドのサービスと自動で連携。すぐ使える | 複数クラウド・オンプレをまたぐと分断される。UI や検索が弱いことも |

---

## 2. 主な商用 SaaS の特徴

| ツール | 特徴 | 課金の主な単位 |
|--------|------|----------------|
| **Datadog** | インフラ・APM・ログ・RUM・セキュリティまで全部入り。統合（インテグレーション）が豊富 | ホスト数、ログの取り込み量・保存量、カスタムメトリクス数 |
| **New Relic** | 全機能を 1 つの料金体系にまとめている。無料枠がある | データの取り込み量（GB）、ユーザー数 |
| **Honeycomb** | **高カーディナリティのイベント**を自由に切り分けて探索するのが得意。「可観測性」の概念を広めた会社（『Observability Engineering』の著者陣） | イベント数 |
| **Grafana Cloud** | LGTM スタックのマネージド版。OSS と同じクエリ言語 | メトリクス系列数、ログ・トレースの GB |
| **Sentry** | エラー追跡に特化。スタックトレース・リリースとの紐付け | エラーイベント数 |

料金体系は頻繁に変わるので、**必ず最新の公式ページで確認**してください。

---

## 3. コストが膨らむ典型パターン

| 原因 | 何が起きるか | 対策 |
|------|--------------|------|
| **カスタムメトリクスのラベル爆発** | ユーザー ID などをタグにして系列数が数百万に | ラベル設計を見直す（[[03_カーディナリティ問題]]） |
| **ログの出しすぎ** | DEBUG ログを本番で全件取り込み | ログレベルとサンプリング、保存期間の階層化（[[02_ログレベルの使い分け]]） |
| **トレースを全件保存** | 取り込み量に比例して課金 | Tail サンプリングで重要なものだけ残す（[[03_サンプリング戦略]]） |
| **ホスト課金 × オートスケール** | ピーク時のホスト数で課金される | 課金方式を確認し、コンテナ単位の課金と比べる |
| **同じデータを複数ツールに送る** | 移行期間に二重課金 | 期限を決めて片方を止める |

- 目安として、可観測性の費用がインフラ費用の **10〜30%** に達することは珍しくありません。**毎月のデータ量をダッシュボードで監視**しておきます

---

## 4. OpenTelemetry を「中立な層」にする

ツール選びで最も大事なのは、**アプリの計装を特定ベンダーに縛らないこと**です。

```
[アプリ（OpenTelemetry SDK）]
          │ OTLP
[OTel Collector]  ← ここで送り先・サンプリング・加工を決める
     ├──→ Prometheus / Tempo / Loki（OSS）
     ├──→ Datadog / New Relic / Honeycomb（SaaS）
     └──→ CloudWatch / X-Ray（クラウド）
```

- 主要な商用 SaaS はすべて **OTLP の受け取り**に対応している
- ベンダー固有のエージェントや SDK で計装すると、乗り換え時にアプリのコードを全部書き換えることになる
- Collector で**同時に 2 か所へ送る**ことができるので、ツールの比較検証や段階的な移行がしやすい（[[03_OTel_Collector]]）

## 5. 選び方の判断基準

| 問い | 答えによる傾向 |
|------|----------------|
| 運用に割ける人がいるか | いない → SaaS かクラウド標準 |
| データ量はどのくらいか | 少ない → SaaS が安くて速い。非常に多い → OSS 自前運用のほうが安くなることが多い |
| マルチクラウド・オンプレがあるか | ある → OSS か、クラウドに依存しない SaaS |
| データを社外に出せない規制があるか | ある → OSS 自前運用 |
| 高カーディナリティで自由に探索したいか | したい → Honeycomb 型のイベント指向ツール |
| 既に AWS に全部載っているか | 載っている → まず CloudWatch・X-Ray（61_AWS/08_管理監視）、足りなくなったら拡張 |

### 規模別の典型的な構成

| 段階 | 構成例 |
|------|--------|
| 個人・小規模 | CloudWatch などクラウド標準 + Sentry。または Grafana Cloud の無料枠 |
| スタートアップ | 商用 SaaS 1 つに統合（計装は OpenTelemetry） |
| 中〜大規模 | OSS（LGTM）を基盤に、エラー追跡や RUM だけ SaaS を併用 |

---

## 6. 評価のしかた

1. 評価の観点を決める（コスト、検索の速さ、相関のしやすさ、アラート、権限管理）
2. OpenTelemetry で計装し、Collector から**候補 2〜3 個に同時送信**する
3. 過去の障害を 1 つ選び、**その障害を各ツールで調査するとどうなるか**を試す
4. 1 か月分のデータ量から費用を見積もる。1 年後にデータが 3 倍になった場合も計算する
