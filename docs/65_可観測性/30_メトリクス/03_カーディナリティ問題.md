# カーディナリティ問題

**カーディナリティ** は、あるデータが取りうる値の種類の数です。メトリクスでは、**ラベルの値の組み合わせの数 = 時系列の数** になるため、ユーザー ID のような値の種類が多いラベルを付けると時系列が爆発し、監視基盤が遅くなったり、請求額が跳ね上がったりします。一方で『Observability Engineering』は、**高カーディナリティのデータこそ調査に役立つ**とも述べています。この章では、この矛盾をどう扱うかを整理します。

---

## 1. 時系列の数はこう決まる

```text
http_requests_total{method, route, status}

method:  5 種類（GET, POST, PUT, DELETE, PATCH）
route:   40 種類
status:  10 種類
→ 最大 5 × 40 × 10 = 2,000 時系列   … 問題なし

ここに user_id（10 万人）を足すと
→ 2,000 × 100,000 = 2 億時系列       … 基盤が落ちる
```

- 時系列の数は **ラベルごとの種類数の掛け算** で増えます。1 つのラベルでも種類が多いと致命的です。
- さらに **Pod 名**（`pod="api-7d9f-x2k"`）のようにデプロイのたびに変わる値は、古い時系列が残り続け、時間とともに増えていきます（チャーン）。

---

## 2. 何が起きるか

| 影響 | 内容 |
|------|------|
| **メモリ不足** | Prometheus は直近の時系列をメモリに持つ。時系列が増えると OOM で落ちる |
| **クエリが遅い** | `sum by (route)` のたびに大量の時系列を読む |
| **コスト** | SaaS（Datadog など）は時系列数（カスタムメトリクス数）で課金されることが多い |
| **監視が止まる** | 監視基盤そのものが障害の原因になる |

---

## 3. 付けてはいけないラベル・付けてよいラベル

| ラベルの候補 | カーディナリティ | メトリクスに付けるか |
|--------------|------------------|----------------------|
| `method`、`status`（クラス：2xx/4xx/5xx） | 低 | 付けてよい |
| `route`（**テンプレート**：`/users/:id`） | 低〜中 | 付けてよい |
| `path`（**実際の URL**：`/users/12345`） | 無限 | **付けない** |
| `user_id`、`email`、`session_id`、`request_id` | 高 | **付けない** |
| `tenant_id` | 中〜高 | テナント数次第。数十なら可、数万なら不可 |
| `error_message`（自由文） | 無限 | **付けない**。`error_type` に分類する |
| `pod`、`instance` | 中（変動する） | 収集側で自動付与される。集約時は `sum without (pod)` |

```ts
// 悪い例：実際のパスをラベルにしている
httpRequests.inc({ path: req.originalUrl });           // /users/12345?ref=abc

// 良い例：ルートのテンプレートを使う
httpRequests.inc({ route: req.route?.path ?? "unknown" }); // /users/:id
```

- Express などでは、**404 のリクエストはルートが決まらない**ので `route="unknown"` などにまとめます。スキャナーの大量アクセスで時系列が増えるのを防ぐためです。

---

## 4. 高カーディナリティの情報はどこに置くか

「ユーザー ID で絞り込みたい」という要求自体は正当です。**置き場所をシグナルで分けます**。

| 情報 | 置き場所 | 理由 |
|------|----------|------|
| 全体の傾向（RPS、エラー率、p99） | **メトリクス**（低カーディナリティ） | 安く長く保存、アラートに使う |
| 個々のリクエストの属性（user_id、tenant、feature flag） | **トレースのスパン属性・構造化ログ** | 1 件ずつの記録なので、属性が多くても時系列は増えない |
| 両者のつながり | **Exemplar**（メトリクスに代表トレース ID を添える） | グラフの点からトレースに飛べる |

『Observability Engineering』が推す **Wide Event**（リクエストごとの属性たっぷりのイベント）は、この「高カーディナリティはイベント側に持つ」考え方を突き詰めたものです（[[01_構造化ログ]]）。列指向のストアや可観測性ツール（Honeycomb など）は、イベントを後から任意の属性で集計できます。

---

## 5. 増えすぎを防ぐ・見つける

### 5.1 防ぐ

- **ラベルの許可リスト**を決める（コードレビューでチェック）
- ラベル値は **有限の分類（enum）** にする：`status_class="5xx"`、`error_type="timeout"`
- OpenTelemetry では **View** で不要な属性を落とせる
- 収集側（Prometheus の `metric_relabel_configs`、OTel Collector）で危険なラベルを削る

### 5.2 見つける

```promql
# 時系列数の多いメトリクス上位 10
topk(10, count by (__name__) ({__name__=~".+"}))

# あるメトリクスのラベルごとの種類数
count(count by (route) (http_requests_total))
```

- Prometheus の Web UI の **TSDB Status** ページで、時系列数の多いメトリクス・ラベルを確認できます。
- SaaS では、カスタムメトリクス数の推移をダッシュボードに出し、急増したらアラートを出します。
