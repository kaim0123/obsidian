# ログ・メトリクス・トレースの相関

3 つのシグナルは、それぞれ単独でも役に立ちますが、本当の力を発揮するのは **行き来できるようにつないだとき** です。「ダッシュボードでエラー率のスパイクを見つける → その時間帯の遅いトレースを開く → そのスパンのログを読む」という流れが数クリックでできれば、調査時間は大きく縮みます。この章では、シグナル同士をつなぐための **共通のキー** と、その入れ方を整理します。

---

## 1. 調査の典型的な流れ

```
メトリクス（何かおかしい）
   │ エグザンプラー / 時間帯と属性で絞り込み
   ▼
トレース（どこで起きているか）
   │ trace_id / span_id
   ▼
ログ（なぜ起きたか：エラーメッセージ・入力値・分岐）
```

| シグナル | 答える問い | 次のシグナルへの橋 |
|----------|------------|--------------------|
| メトリクス | 「いつから・どれくらい悪いか」 | **エグザンプラー**（バケットに添えた trace_id）、共通のラベル（`service.name`、`http.route`） |
| トレース | 「どのサービスのどの区間か」 | **trace_id / span_id** でログを検索 |
| ログ | 「具体的に何が起きたか」 | ログに入った **trace_id** からトレースを開く |

Google SRE 本の「症状から原因へ」という調査の順番（[[03_ゴールデンシグナル]]）を、ツールの上で実現するのが相関です。

---

## 2. つなぐための 3 つのキー

| キー | 役割 | 入れる場所 |
|------|------|------------|
| **trace_id / span_id** | 個々のリクエスト単位でつなぐ | ログのフィールド、エグザンプラー |
| **リソース属性**（`service.name`、`service.version`、`deployment.environment.name`、`k8s.pod.name` など） | 「どのサービスのどのインスタンスか」でつなぐ | 3 シグナルすべてに**同じ値**で付ける |
| **時刻** | 最後の手段。時間帯で突き合わせる | すべて（時計のずれに注意、NTP 必須） |

- **リソース属性の名前と値を 3 シグナルでそろえる**のが最も重要です。メトリクスは `app="api"`、ログは `service: "api-server"`、トレースは `service.name=backend` のようにバラバラだと、ツールが自動でつなげません。
- OpenTelemetry を使うと、1 つの SDK の `Resource` 設定が 3 シグナルすべてに適用されるので、自然にそろいます（[[01_OpenTelemetry入門]]）。

---

## 3. ログに trace_id を入れる

ログの各行に `trace_id` と `span_id` を入れます。OTel の Log Data Model でも、ログレコードの標準フィールドとして `TraceId` / `SpanId` が定義されています。

```json
{
  "timestamp": "2026-09-26T10:15:30.123Z",
  "level": "error",
  "msg": "在庫の取得に失敗しました",
  "service.name": "inventory-service",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "product_id": 42,
  "err": { "type": "TimeoutError", "message": "redis timeout after 500ms" }
}
```

**Node.js（pino）での入れ方**

| 方法 | 内容 |
|------|------|
| 自動計装に任せる | `@opentelemetry/instrumentation-pino` が有効なら、アクティブなスパンの `trace_id` / `span_id` / `trace_flags` がログに自動で追加される（log correlation） |
| 手動で mixin | 下のように、ログを書くたびに現在のスパンから取り出す |

```ts
import pino from 'pino';
import { trace } from '@opentelemetry/api';

export const logger = pino({
  mixin() {
    const span = trace.getActiveSpan();
    if (!span) return {};
    const { traceId, spanId } = span.spanContext();
    return { trace_id: traceId, span_id: spanId };
  },
});
```

- 構造化ログ（JSON）であることが前提です（[[01_構造化ログ]]）。
- さらに、ログ自体を **OTLP でログバックエンドに送る**（Log Bridge）と、バックエンド側でトレースとの紐づけが自動で行われます（[[04_Node.jsアプリの計装例]]）。

## 4. スパンにログ的な情報を入れる

逆方向に、**重要な出来事はスパンのイベントとして記録**しておくと、トレース画面だけで状況が分かります。

```ts
span.addEvent('cache miss', { 'cache.key': `stock:${id}` });
span.recordException(err);                        // exception イベント（型・メッセージ・スタック）
span.setStatus({ code: SpanStatusCode.ERROR, message: err.message });
```

| 情報 | ログに書く | スパンのイベント・属性にする |
|------|------------|-------------------------------|
| リクエスト単位の文脈（ユーザー種別、テナント） | ○ | ○（属性にすると検索・集計できる） |
| 例外 | ○ | ○（`recordException`） |
| 大量の詳細（ループ内の各処理） | △（DEBUG） | ×（スパンが巨大になる） |
| リクエストと無関係な出来事（起動・設定読込・定期ジョブ） | ○ | ×（スパンがない） |

『Observability Engineering』は、「**幅の広い構造化イベント**（wide event）」を 1 リクエストに 1 つ出す方向を勧めています。スパンに属性を豊富に付けるのはその考え方の実践です。

## 5. メトリクスからトレースへ：エグザンプラー

**エグザンプラー（Exemplar）** は、メトリクスのデータ点に「その値の代表例となったトレースの trace_id」を添えたものです（OpenMetrics 仕様、OTel Metrics の Exemplar）。

```
# OpenMetrics 形式の例（ヒストグラムのバケットに trace_id が付く）
http_server_duration_seconds_bucket{le="1.0",route="/checkout"} 1234 # {trace_id="4bf92f35..."} 0.87 1727345730.123
```

- Grafana では、Prometheus のグラフ上にエグザンプラーが**点**として表示され、クリックすると Tempo / Jaeger のトレースが開きます（[[02_Grafana]]）。
- Prometheus 側は `--enable-feature=exemplar-storage` の有効化が必要です（[[01_Prometheus]]）。
- エグザンプラーが指すトレースは、**サンプリングで保存されている必要があります**。テールサンプリングで捨てられていると「リンク先がない」状態になります（[[03_サンプリング戦略]]）。

## 6. 相関がうまくいかないときのチェックリスト

- [ ] 3 シグナルの `service.name` が同じ値か
- [ ] ログに `trace_id` が入っているか（空文字やゼロ埋めになっていないか → スパンの外でログを書いている）
- [ ] ログバックエンドで `trace_id` が**検索可能なフィールド**として取り込まれているか（本文の文字列に埋もれていないか）
- [ ] Grafana の データソース設定で「ログ → トレース」「トレース → ログ」のリンク（derived fields / trace to logs）を設定したか
- [ ] サーバー間の時計が NTP で同期しているか
