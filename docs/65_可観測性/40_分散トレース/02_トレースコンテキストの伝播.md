# トレースコンテキストの伝播

分散トレースがサービスをまたいでつながるのは、呼び出しのたびに **trace_id と親の span_id を相手に渡している**からです。この「渡す」仕組みを **コンテキスト伝播（Context Propagation）** と呼びます。標準形式は W3C の **Trace Context** 仕様で、OpenTelemetry も既定でこれを使います。この章では、ヘッダーの形式、HTTP とキューでの伝え方、トレースが途切れる典型的な原因を整理します。

---

## 1. 伝播の全体像

```
[サービスA]                                   [サービスB]
 現在のスパン (trace_id=T, span_id=A1)
   │  inject: ヘッダーに書き込む
   ├──── HTTP リクエスト ───────────────────▶  extract: ヘッダーから読む
   │   traceparent: 00-T-A1-01                  新しいスパン (trace_id=T, parent=A1, span_id=B1)
```

| 操作 | 意味 | OTel での API |
|------|------|---------------|
| **inject** | 現在のコンテキストを、送信するメッセージ（ヘッダー）に書き込む | `propagation.inject(context.active(), carrier)` |
| **extract** | 受信したメッセージからコンテキストを読み出す | `propagation.extract(context.active(), carrier)` |
| **carrier** | コンテキストを運ぶ入れ物 | HTTP ヘッダー、メッセージの属性、gRPC メタデータ |

HTTP や主要なメッセージングライブラリは**自動計装が inject / extract を代わりにやってくれます**。手で書く必要があるのは、自前のプロトコルや、自動計装が対応していないライブラリのときです。

---

## 2. W3C Trace Context：`traceparent` ヘッダー

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                │
             │  trace-id (32 桁の16進)            parent-id        trace-flags
             version                              (16 桁の16進)     (01 = sampled)
```

| フィールド | 長さ | 意味 |
|------------|------|------|
| version | 2 桁 | 現在は `00` |
| trace-id | 32 桁（16 バイト） | トレース全体の ID。全ゼロは無効 |
| parent-id | 16 桁（8 バイト） | **送信側のスパン ID**（受信側から見た親） |
| trace-flags | 2 桁 | 下位ビットが **sampled** フラグ。`01` なら「記録対象」 |

もう 1 つの **`tracestate`** ヘッダーは、ベンダー固有の情報を `key=value` のカンマ区切りで運ぶためのものです（例：`tracestate: vendorA=abc,vendorB=xyz`）。

> 古いシステムでは Zipkin の **B3 ヘッダー**（`X-B3-TraceId` など）や、AWS X-Ray の `X-Amzn-Trace-Id`、Jaeger の `uber-trace-id` が使われています。OTel では `OTEL_PROPAGATORS=tracecontext,baggage,b3` のように**複数のプロパゲーターを並べて**併用できます。

---

## 3. Baggage：業務情報を下流へ運ぶ

**Baggage** は、トレースとは別に「リクエストに付いて回るキーと値」を運ぶ仕組みです（W3C Baggage 仕様）。

```
baggage: tenant.id=acme,user.tier=premium
```

| 用途 | 例 |
|------|----|
| 下流のサービスでも同じ属性でスパンを絞り込みたい | `tenant.id` を全サービスのスパン属性にコピーする |
| 機能フラグや実験グループを伝える | `experiment=checkout-v2` |

**注意点**

- Baggage は **すべての下流呼び出しに HTTP ヘッダーとして送られます**。外部 API にも送られるので、**個人情報や秘密情報は絶対に入れない**（[[03_ログに書くこと・書かないこと]]）。
- Baggage は自動ではスパン属性になりません。必要なら SpanProcessor でコピーします。
- サイズが大きいとすべてのリクエストが重くなります。数個のキーに抑えます。

---

## 4. 非同期処理での伝播

キューや Pub/Sub では、送信と受信の間に時間差があり、**HTTP ヘッダーがありません**。そこでメッセージの**属性（メタデータ）**にコンテキストを入れます（キューの仕組みは [[メッセージキューとは]]）。

| 仕組み | コンテキストの置き場所 |
|--------|------------------------|
| Kafka | レコードヘッダー |
| RabbitMQ | メッセージの headers プロパティ |
| AWS SQS | MessageAttributes（または X-Ray の AWSTraceHeader システム属性） |
| AWS SNS → SQS | MessageAttributes（Raw Message Delivery の設定に注意） |

```ts
// 送信側：PRODUCER スパンを作ってメッセージ属性に inject
import { context, propagation, trace, SpanKind } from '@opentelemetry/api';

const tracer = trace.getTracer('order-service');

await tracer.startActiveSpan('orders publish', { kind: SpanKind.PRODUCER }, async (span) => {
  const headers: Record<string, string> = {};
  propagation.inject(context.active(), headers);
  await producer.send({ topic: 'orders', messages: [{ value: JSON.stringify(order), headers }] });
  span.end();
});

// 受信側：メッセージ属性から extract して CONSUMER スパンを作る
const parentCtx = propagation.extract(context.active(), message.headers);
await context.with(parentCtx, () =>
  tracer.startActiveSpan('orders process', { kind: SpanKind.CONSUMER }, async (span) => {
    await handle(message);
    span.end();
  }),
);
```

- 受信側のスパンを**送信側の子にするか、リンクでつなぐか**は選択です。1 メッセージ 1 処理なら子、バッチで複数メッセージをまとめて処理するなら **span links** でそれぞれの送信スパンにつなぎます（OTel Messaging のセマンティック規約）。
- キューで何時間も待つ場合、1 本のトレースが極端に長くなります。その場合もリンクのほうが見やすくなります。

## 5. トレースが途切れる典型的な原因

| 症状 | 原因 | 対処 |
|------|------|------|
| サービスごとに別々のトレースになる | 片方のサービスが計装されていない・プロパゲーターの形式が違う（B3 と W3C） | 両方に同じ `OTEL_PROPAGATORS` を設定 |
| ロードバランサー・API ゲートウェイの先で途切れる | プロキシがヘッダーを削除・上書きしている | `traceparent` / `tracestate` / `baggage` を通す設定にする |
| 非同期処理の後で途切れる | `setTimeout`・イベントエミッター・独自のコネクションプールでコンテキストが失われる | Node.js は AsyncLocalStorage ベースのコンテキストマネージャーを使う。`context.bind()` で明示的に束ねる |
| キューの受信側が親なしになる | メッセージ属性に inject していない | 4 章のように手動で inject / extract |
| ブラウザからのトレースがつながらない | CORS で `traceparent` ヘッダーが許可されていない | `Access-Control-Allow-Headers` に追加 |

---

## 6. セキュリティ上の注意

- **外部から来た `traceparent` をそのまま信じるか**は設計判断です。攻撃者が sampled=1 を大量に送ると、トレースの保存量を増やせてしまいます。公開 API の入口では、外部のコンテキストを**リンクとして扱い、新しいトレースを開始する**設定も検討します。
- 外部 API へのリクエストに内部の `baggage` が漏れないよう、送信先ごとにプロパゲーターを制御します。
