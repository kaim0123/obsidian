# 分散トレースとは

**分散トレース（Distributed Tracing）** は、1 つのリクエストが複数のサービス・DB・キューを通り抜けていく道のりを、**時間軸つきの木構造**として記録する仕組みです。Google が 2010 年に発表した **Dapper 論文**（"Dapper, a Large-Scale Distributed Systems Tracing Infrastructure"）が原点で、Zipkin・Jaeger を経て、現在は **OpenTelemetry** が標準の形式になっています。この章では、トレースを構成する要素と、ログやメトリクスでは分からないことが何なのかを整理します。

---

## 1. なぜ分散トレースが必要か

モノリスなら、遅いリクエストは 1 つのプロセスのプロファイラやログで追えます。マイクロサービスや外部 API を使う構成では、1 回の画面表示の裏で 10 個以上の呼び出しが起きることも珍しくありません。

| 知りたいこと | ログだけ | メトリクスだけ | トレース |
|--------------|----------|----------------|----------|
| 「このリクエストはどこで 2 秒かかったか」 | 各サービスのログを時刻で突き合わせる必要がある | サービス単位の平均しか分からない | 1 画面で区間ごとの時間が見える |
| 「どのサービスがどのサービスを呼んでいるか」 | 分からない | 分からない | サービスマップとして自動で描ける |
| 「エラーの発生源はどこか」 | 各所に同じエラーが連鎖して記録され紛らわしい | エラー率が上がったサービスが複数見える | 最初に失敗したスパンが分かる |

『Observability Engineering』では、トレースを「**イベントを因果関係でつないだもの**」と説明しています。ログが「点」、メトリクスが「集計値」だとすると、トレースは「**点と点をつなぐ線**」です（[[02_ログ・メトリクス・トレースの3シグナル]]）。

## 2. トレースとスパン

| 用語 | 意味 | 例 |
|------|------|----|
| **トレース（Trace）** | 1 つのリクエスト全体。**trace_id**（16 バイト）で識別する | 「商品ページを表示する」1 回分 |
| **スパン（Span）** | トレースの中の 1 区間の作業。**span_id**（8 バイト）で識別する | `GET /products/42`、`SELECT products`、`redis GET` |
| **親スパン** | そのスパンを呼び出したスパン。**parent_span_id** で参照する | API ゲートウェイのスパンが、商品サービスのスパンの親 |
| **ルートスパン** | 親を持たない最初のスパン | ブラウザ or ゲートウェイの受信スパン |

スパンを親子関係でつなぐと、次のような**ウォーターフォール図**になります。

```
trace_id = 4bf92f3577b34da6a3ce929d0e0e4736
│
├─ GET /products/42 (api-gateway)                 [0ms ──────────────── 820ms]
│   ├─ GET /products/42 (product-service)          [5ms ─────────── 610ms]
│   │   ├─ SELECT * FROM products (postgres)       [10ms ─ 40ms]
│   │   └─ GET /inventory/42 (inventory-service)   [45ms ─────── 600ms]   ← ここが遅い
│   │       └─ redis GET stock:42                  [50ms ─ 52ms]
│   └─ GET /reviews/42 (review-service)            [615ms ─ 810ms]
```

この図から「inventory-service の中で Redis 以外の何かが 550ms かかっている」「reviews は直列に呼ばれているので並列化できる」といったことがすぐ読み取れます。

## 3. スパンが持つ情報

OpenTelemetry の仕様（Tracing API）では、スパンは次の情報を持ちます。

| 項目 | 内容 | 例 |
|------|------|----|
| **name** | 操作の名前。**低カーディナリティ**にする（ID を入れない） | `GET /products/:id`（`/products/42` ではない） |
| **kind** | スパンの役割 | `SERVER` / `CLIENT` / `PRODUCER` / `CONSUMER` / `INTERNAL` |
| **開始・終了時刻** | ナノ秒精度のタイムスタンプ | |
| **attributes** | キーと値の組。検索・集計に使う | `http.request.method=GET`、`http.response.status_code=200`、`user.tier=premium` |
| **events** | スパンの途中で起きた出来事（時刻つきのログ） | `exception`（スタックトレース）、`cache miss` |
| **status** | 成否 | `UNSET`（既定）/ `OK` / `ERROR` |
| **links** | 親子以外の因果関係 | バッチ処理が複数のメッセージをまとめて処理した場合 |

- 属性名は **セマンティック規約（Semantic Conventions）** に合わせます（`http.route`、`db.system`、`db.query.text` など）。規約に合わせると、どのツールでも同じ名前で検索できます（[[01_OpenTelemetry入門]]）。
- **status は自動では ERROR になりません**。HTTP クライアントの 5xx などは自動計装が設定しますが、業務エラーは自分で `span.setStatus({ code: SpanStatusCode.ERROR })` を呼びます（[[02_自動計装と手動計装]]）。

## 4. span kind と呼び出しの関係

1 回のサービス間呼び出しは、**呼び出し側の CLIENT スパン**と**受け側の SERVER スパン**の 2 つで表します。

| 通信の種類 | 呼び出し側 | 受け側 |
|------------|------------|--------|
| 同期（HTTP・gRPC） | `CLIENT` | `SERVER` |
| 非同期（キュー・Pub/Sub） | `PRODUCER` | `CONSUMER` |
| プロセス内の処理 | `INTERNAL` | — |

CLIENT と SERVER の時間差は、**ネットワーク遅延やキューイング**です。ここが大きいなら、コードではなく通信経路やコネクションプールを疑います。

## 5. 分散トレースで分かること・分からないこと

| 分かること | 分からないこと |
|------------|----------------|
| リクエスト単位の遅延の内訳（クリティカルパス） | 全体のエラー率・スループットの推移（→ メトリクス） |
| サービス間の依存関係（サービスマップ） | サンプリングで捨てたリクエストの詳細（[[03_サンプリング戦略]]） |
| エラーの発生源と伝播経路 | 関数レベルの CPU 消費（→ プロファイラ、66_パフォーマンス） |
| N+1 クエリや直列呼び出しなどの構造的な問題 | 計装していない区間（「空白の時間」として見える） |

- トレースに**空白の区間**があるときは、計装されていない処理（同期 I/O、ロック待ち、GC）が隠れています。手動でスパンを足して埋めていきます。
- トレースは量が多いので、通常は**サンプリング**して一部だけ保存します。エラーや遅いリクエストを確実に残す方法は [[03_サンプリング戦略]]。

## 6. 導入のステップ

1. **入口と出口を計装する**：HTTP サーバー・HTTP クライアント・DB ドライバ。自動計装でほぼ済みます（[[02_自動計装と手動計装]]）。
2. **コンテキストを伝播させる**：サービス間で trace_id を引き継がないと、トレースが途切れます（[[02_トレースコンテキストの伝播]]）。
3. **バックエンドに送る**：OTLP で Collector に送り、Jaeger や Tempo で見る（[[03_OTel_Collector]]、[[03_Jaeger・Tempo]]）。
4. **ログとつなぐ**：ログに trace_id を入れ、ログとトレースを行き来できるようにする（[[04_ログ・メトリクス・トレースの相関]]）。
5. **業務的な属性を足す**：`user.tier`、`tenant.id`、`feature_flag` などを付けると「プレミアム会員だけ遅い」といった問いに答えられるようになります。
