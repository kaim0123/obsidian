# 画像とフォントの最適化

> - 画像フォーマット（AVIF / WebP / JPEG）の選び方とレスポンシブ画像（`srcset` / `sizes`）
> - `width` / `height` 指定で CLS を防ぐ理由、`loading="lazy"` と `fetchpriority="high"` の正しい使い分け
> - `next/image` と画像 CDN でやってくれること
> - Web フォントの最適化（WOFF2、`font-display`、サブセット化、`size-adjust`、`next/font`）

>

## 1. ひとことで言うと

画像は「**引っ越し荷物**」です。4K テレビ用の大きな写真を、スマホの小さな額縁に飾るためにわざわざトラックで運ぶのは無駄です（サイズ過大）。荷物が届く前に家具の配置を決めておかないと、届いた瞬間に全部ずれます（CLS）。そして一番大事な荷物（LCP 画像）を最後に運ぶと、引っ越しはいつまでも終わりません。

- 画像は多くのページで **転送量の最大の割合** を占め、商品詳細ページでは **LCP 要素** になりやすい
- やることは「**小さく（フォーマット・サイズ）・場所を確保して（width/height）・優先順位を正しく（lazy / fetchpriority）**」
- フォントは「**文字が見えない時間**」と「**差し替え時のズレ**」の 2 つが問題になる

## 2. 画像フォーマットとサイズ

### 2-1. フォーマットの選び方

| フォーマット | 特徴 | 対応状況（2026 年時点） |
|---|---|---|
| **AVIF** | 同画質なら一般に最も小さい。エンコードは重い | 2024 年 1 月（Edge 121）で主要ブラウザがそろった。Baseline |
| **WebP** | JPEG より 25〜35% 程度小さいことが多い。透過・アニメ対応 | 全主要ブラウザ対応 |
| **JPEG** | 互換性最強。写真向け | 全ブラウザ |
| **PNG** | 可逆圧縮。ロゴ・スクリーンショット向け。写真には不向き | 全ブラウザ |
| **SVG** | ベクター。アイコン・ロゴに最適 | 全ブラウザ |

削減率は画像の内容と品質設定で大きく変わります。必ず自分の画像で比較してください。

```bash
# sharp-cli で同じ画像を変換して比較（数値は説明用の例）
npx sharp-cli -i hero.jpg -o out/hero.avif -f avif -q 50
npx sharp-cli -i hero.jpg -o out/hero.webp -f webp -q 75
ls -lh hero.jpg out/
# hero.jpg   420K
# hero.webp  260K
# hero.avif  170K
```

古いブラウザに配慮するなら `<picture>` でフォールバックします。

```html
<picture>
  <source type="image/avif" srcset="/img/shoe-800.avif">
  <source type="image/webp" srcset="/img/shoe-800.webp">
  <img src="/img/shoe-800.jpg" alt="ランニングシューズ" width="800" height="800">
</picture>
```

### 2-2. レスポンシブ画像（`srcset` / `sizes`）

幅 390px のスマホに幅 2,000px の画像を送るのは無駄です。`srcset` で候補を並べ、`sizes` で「この画像は画面上で何 px 幅で表示されるか」を伝えると、ブラウザが画面幅と画素密度（DPR）から最適な 1 枚を選びます。

```html
<img
  src="/img/shoe-800.jpg"
  srcset="/img/shoe-400.jpg 400w, /img/shoe-800.jpg 800w, /img/shoe-1200.jpg 1200w, /img/shoe-1600.jpg 1600w"
  sizes="(max-width: 768px) 100vw, 50vw"
  width="800" height="800"
  alt="ランニングシューズ">
<!-- 幅 390px・DPR 3 のスマホ：390 × 3 = 1170px 必要 → 1200w を選ぶ -->
<!-- 幅 1440px・DPR 1 の PC：1440 × 0.5 = 720px 必要 → 800w を選ぶ -->
```

`sizes` を省略すると `100vw` とみなされ、PC で 2 列表示している画像にも全幅用の大きな画像が選ばれてしまいます。

## 3. 画像と Core Web Vitals

### 3-1. `width` / `height` で CLS を防ぐ

サイズ指定のない `<img>` は、画像が届くまで高さ 0 で配置され、届いた瞬間に下の要素を押し下げます。`width` と `height` 属性を書くと、ブラウザはそこから **縦横比** を計算して、届く前から場所を確保します（CSS で `width: 100%; height: auto;` にしても比率は保たれます）。

```css
img { max-width: 100%; height: auto; } /* 属性の比率を使ってレスポンシブに */
.product-thumb { aspect-ratio: 1 / 1; object-fit: cover; } /* CSS で比率を固定する方法も */
```

### 3-2. `loading="lazy"` は LCP 画像に付けない

`loading="lazy"` は画面外の画像の読み込みを、スクロールで近づくまで遅らせる属性です。商品一覧の下の方の画像には効果的ですが、**ファーストビューの LCP 画像に付けると、レイアウトが確定するまで取得が始まらず LCP が悪化** します。

```
  LCP 画像に lazy を付けた場合（時間は説明用の例）
  |―HTML―|―CSS―|レイアウト|―――― 画像ダウンロード ――――|  LCP 3.4s
  付けない＋fetchpriority="high" の場合
  |―HTML―|
         |―――― 画像ダウンロード ――――|  LCP 2.1s（CSS と並行して取得開始）
```

### 3-3. `fetchpriority="high"` で LCP 画像を優先する

ブラウザは画像を最初は低い優先度で取得し、レイアウト後に「ビューポート内だ」と分かってから優先度を上げます。LCP 画像が事前に分かっているなら、`fetchpriority="high"` で最初から高優先度にできます（2026 年時点で主要ブラウザ対応、Baseline）。

```html
<!-- 商品詳細のメイン画像：遅延させず、最優先で -->
<img src="/img/shoe-800.avif" fetchpriority="high" width="800" height="800" alt="…">

<!-- 関連商品のサムネイル：画面外なので遅延 -->
<img src="/img/related-1.avif" loading="lazy" width="200" height="200" alt="…">
```

さらに、LCP 画像が CSS の `background-image` や JS で後から差し込まれる場合は、HTML からは見つけられないので `<link rel="preload" as="image" fetchpriority="high">` で早めに知らせます（[[05_ネットワークと読み込みの最適化]]）。

## 4. `next/image` と画像 CDN

手作業で何種類もの画像を用意するのは大変です。Next.js の `next/image` や画像 CDN はこれを自動化します。

```tsx
// app/products/[id]/ProductHero.tsx
import Image from "next/image";

export function ProductHero({ src, name }: { src: string; name: string }) {
  return (
    <Image
      src={src}                 // 例: https://images.shop.example.com/shoe.jpg
      alt={name}
      width={800}
      height={800}
      sizes="(max-width: 768px) 100vw, 50vw"
      loading="eager"           // LCP 画像：既定の lazy を外す
      fetchPriority="high"      // 最優先で取得
    />
  );
}
```

`next/image` がやってくれること（2026 年時点）：

- `srcset` の自動生成と、リクエスト時のリサイズ・フォーマット変換（`images.formats` で AVIF も有効化可能）
- 既定で `loading="lazy"`。LCP 画像には `loading="eager"` や `fetchPriority="high"` を指定する（以前の `priority` プロパティは Next.js 16 で非推奨になり、`preload` が追加された。公式ドキュメントは多くの場合 `preload` より `loading="eager"` / `fetchPriority="high"` を勧めている）
- `width` / `height` 必須なので CLS を防げる

```ts
// next.config.ts
import type { NextConfig } from "next";
const nextConfig: NextConfig = {
  images: {
    formats: ["image/avif", "image/webp"],
    remotePatterns: [{ protocol: "https", hostname: "images.shop.example.com" }],
  },
};
export default nextConfig;
```

**画像 CDN**（Cloudinary、imgix、Cloudflare Images など）は、URL パラメータ（例：`?w=800&fm=avif`）でリサイズ・変換し、結果をエッジにキャッシュします。自前の Next.js サーバーで変換すると CPU を食うため、画像の多い Shop のようなサイトでは画像 CDN に任せる構成も一般的です。CDN の基本は [[04_CDNによる負荷軽減]] を参照してください。

## 5. Web フォントの最適化

### 5-1. フォントが引き起こす 2 つの問題

```
  FOIT（Flash of Invisible Text）：フォントが届くまで文字が見えない → FCP / LCP が遅れる
  FOUT（Flash of Unstyled Text） ：代替フォントで表示 → 届いたら差し替え → 文字幅が変わり CLS
```

### 5-2. 基本の対策

| 対策 | 内容 |
|---|---|
| **WOFF2** を使う | Brotli ベースの圧縮で、TTF / OTF より大幅に小さい。2026 年時点で全主要ブラウザ対応 |
| **`font-display`** | `swap`：すぐ代替フォントで表示し、届いたら差し替え（FOIT を防ぐ）。`optional`：短時間で届かなければその回は代替フォントのまま（ズレない） |
| **サブセット化** | 使う文字だけに絞る（`unicode-range` で分割配信も可能） |
| **`preload`** | ファーストビューで使うフォントを早めに取得。`crossorigin` 属性が必須 |
| **`size-adjust` などのメトリクス上書き** | 代替フォントの文字幅・高さを Web フォントに合わせ、差し替え時のズレ（CLS）を減らす |
| **自前ホスト** | 外部ドメインのフォントは接続が 1 本余計にかかる |

```css
/* 本命フォント */
@font-face {
  font-family: "ShopSans";
  src: url("/fonts/shop-sans.woff2") format("woff2");
  font-display: swap;
}
/* 代替フォントのサイズを本命に合わせる（値は実測して調整する） */
@font-face {
  font-family: "ShopSans Fallback";
  src: local("Arial");
  size-adjust: 104%;
  ascent-override: 92%;
  descent-override: 24%;
}
body { font-family: "ShopSans", "ShopSans Fallback", sans-serif; }
```

```html
<link rel="preload" href="/fonts/shop-sans.woff2" as="font" type="font/woff2" crossorigin>
```

### 5-3. `next/font`

`next/font` は上記をまとめて自動化します：ビルド時にフォントをダウンロードして **自前ホスト**、**サブセット化**、`size-adjust` 付きの代替フォントを **自動生成** して CLS を抑えます（2026 年時点）。

```tsx
// app/layout.tsx
import { Noto_Sans_JP } from "next/font/google";

const noto = Noto_Sans_JP({
  weight: ["400", "700"],   // 使うウェイトだけに絞る
  display: "swap",
  preload: false,           // 日本語フォントは巨大なので preload しない（下記）
});

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="ja" className={noto.className}>
      <body>{children}</body>
    </html>
  );
}
```

### 5-4. 日本語フォントが重い問題

英字フォントは数百文字で済みますが、日本語フォントはひらがな・カタカナ・漢字を含めて **数千〜2 万字以上** を収録しており、1 ウェイトでも数 MB になります。これをそのまま送ると、モバイル回線では致命的です。

現実的な選択肢：

1. **システムフォントを使う**（最速）。`font-family: system-ui, "Hiragino Sans", "Noto Sans JP", sans-serif;` のように、OS 標準の日本語フォントで十分なことが多い。
2. **Google Fonts / `next/font` の自動分割を使う**。Google Fonts は日本語フォントを `unicode-range` で 100 以上の小さなファイルに分割し、**ページで使われている文字を含むファイルだけ** をブラウザが取得します。
3. **見出しだけ Web フォント**。ロゴや見出しに使う文字だけをサブセット化（`pyftsubset` など）して数十 KB に抑え、本文はシステムフォントにする。
4. ウェイトを増やさない（400 と 700 で 2 倍、全ウェイトで 9 倍）。

```bash
# fonttools で見出し用の文字だけにサブセット化する例
pip install fonttools brotli
pyftsubset NotoSansJP-Bold.otf --text-file=heading-chars.txt \
  --flavor=woff2 --output-file=heading-bold.woff2
```

## 6. どう測るか

- **Lighthouse**：「適切なサイズの画像」「次世代フォーマット」「LCP 画像の遅延読み込み」「LCP リクエストの検出」などの診断（2026 年時点では Insights として表示）で、改善余地のある画像と削減見込みバイト数が出ます。
- **DevTools の Network パネル**：`Img` / `Font` でフィルタし、サイズ・形式・**Priority 列**（右クリックで表示）を確認。LCP 画像が `High` になっているか見ます。
- **Performance パネル**：LCP 要素と、LCP の 4 区間（TTFB / 読み込み遅延 / 読み込み時間 / 描画遅延）が表示されます。
- **RUM**：`web-vitals` の attribution ビルドで、実ユーザーの LCP 要素と区間を集めます（[[06_LighthouseとRUMで計測する]]）。

Shop 商品詳細ページでの改善イメージ（**数値は説明用の例**、モバイル・Slow 4G 相当のラボ計測）：

| 施策 | LCP 画像サイズ | LCP | CLS |
|---|---|---|---|
| Before（2000px JPEG、lazy 付き、サイズ指定なし） | 820KB | 4.1s | 0.21 |
| `srcset` + AVIF | 140KB | 2.9s | 0.21 |
| lazy を外し `fetchpriority="high"` | 140KB | 2.2s | 0.21 |
| `width`/`height` 指定 + `next/font` | 140KB | 2.2s | 0.03 |

## よくある誤解・つまずき

- ❌ 全部の画像に `loading="lazy"` を付ければ速くなる
  ✅ ファーストビューの画像（特に LCP 画像）に付けると逆効果です。画面外の画像だけに付けます。
- ❌ CSS で `width: 100%` にしているから `width`/`height` 属性は不要
  ✅ 属性は表示サイズを固定するためではなく、**縦横比を事前に伝えて場所を確保する** ためのものです。
- ❌ AVIF にすれば常に一番小さい
  ✅ 画像の内容や品質設定次第で、WebP の方が小さいこともあります。エンコード時間も長いので、ビルド時か CDN で変換します。
- ❌ 日本語フォントも `preload` すれば速くなる
  ✅ 数 MB のファイルを最優先で取得させると、LCP 画像や CSS の帯域を奪います。分割配信かシステムフォントを検討します。

## まとめ

- 画像は AVIF / WebP + `srcset` / `sizes` で「必要な大きさだけ」送る
- `width` / `height`（または `aspect-ratio`）で場所を確保して CLS を防ぐ
- LCP 画像は lazy にせず `fetchpriority="high"`。画面外の画像だけ lazy
- `next/image` や画像 CDN でリサイズ・変換・キャッシュを自動化
- フォントは WOFF2・`font-display`・サブセット・`size-adjust`。`next/font` で一括対応
- 日本語フォントは巨大。システムフォント、分割配信、見出しだけサブセットを検討

## 確認クイズ

1. 2 列グリッドで表示される商品画像に `srcset` を付けたのに、PC でも 1600w の画像が選ばれています。何が足りませんか？
> [!tip]- 答え
> `sizes` 属性です。省略すると `100vw`（画面全幅）とみなされ、大きな候補が選ばれます。`sizes="(max-width: 768px) 100vw, 50vw"` のように実際の表示幅を伝えます。

2. Web フォント導入後に CLS が 0.02 から 0.15 に悪化しました。考えられる原因と対策は？
> [!tip]- 答え
> `font-display: swap` で代替フォントから本命フォントに差し替わる際、文字幅・行の高さが変わってテキストブロックの高さが変化したためです。`size-adjust` / `ascent-override` などで代替フォントのメトリクスを合わせる（`next/font` なら自動）、または `font-display: optional` を検討します。

3. 商品詳細ページのメイン画像が CSS の `background-image` で指定されており、LCP が遅いです。なぜ遅く、どう直しますか？
> [!tip]- 答え
> CSS をダウンロード・解析してスタイルを適用するまで、ブラウザは画像の存在を知れないため取得開始が遅れます（読み込み遅延が長い）。`<img>` 要素に変えて `fetchpriority="high"` を付けるか、`<link rel="preload" as="image">` で早期に取得させます。
