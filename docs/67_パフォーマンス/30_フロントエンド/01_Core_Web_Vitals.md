## 1. ひとことで言うと

レストランの「遅い」を思い浮かべてください。「席に着いたのに料理がなかなか出てこない」「店員を呼んでも返事がない」「料理を取ろうとしたら皿を動かされた」。どれも不満ですが、原因も対策もまったく違います。Web ページも同じで、「遅い」には **見えるまで遅い（LCP）／反応が遅い（INP）／ガタつく（CLS）** の 3 種類が混ざっています。Core Web Vitals（コア ウェブ バイタル）は、この 3 つを別々の数字で測るために Google が定めた指標セットです。

- **LCP**：主役のコンテンツが見えるまでの時間
- **INP**：操作してから画面が反応するまでの時間
- **CLS**：レイアウトが予期せずズレた量
- 判定は「平均」ではなく **実ユーザーの 75 パーセンタイル**

> [!info] クリップとの関係
> 3 種類の「遅い」の直感的な説明は [[Webサイトの「遅い」は3種類ある｜Web Vitalsを図で理解する]] が図とアニメーションで分かりやすく解説しています。本稿はその内容を、定義・原因・計測方法まで掘り下げたものです。

## 2. 3 つの指標と閾値

### 2-1. 閾値の一覧（2026 年時点、web.dev で確認）

| 指標 | 測るもの | Good | Needs improvement | Poor |
|---|---|---|---|---|
| **LCP**（Largest Contentful Paint） | 読み込みの速さ | ≤ 2.5 秒 | 2.5〜4.0 秒 | > 4.0 秒 |
| **INP**（Interaction to Next Paint） | 操作への反応の速さ | ≤ 200 ms | 200〜500 ms | > 500 ms |
| **CLS**（Cumulative Layout Shift） | 見た目の安定性 | ≤ 0.1 | 0.1〜0.25 | > 0.25 |

閾値は将来見直される可能性があるため、実務では必ず [web.dev の Web Vitals](https://web.dev/articles/vitals) で最新値を確認してください。

### 2-2. 75 パーセンタイルで判定する

「ページの LCP が Good」とは、**そのページを訪れた実ユーザーの体験を並べて、遅い方から 25% の位置（75 パーセンタイル）が 2.5 秒以下**という意味です。モバイルとデスクトップは別々に集計します。

```
  実ユーザー 100 人分の LCP を速い順に並べたイメージ（数値は説明用の例）

  速い ←――――――――――――――――――――――――――――――→ 遅い
  |■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■|■■■■■■■■■■■|
  1人目                          75人目 = 2.3秒    100人目 = 7秒
                                    ↑
                    ここが 2.5 秒以下なら「Good」
```

平均を使わない理由は [[02_レイテンシとパーセンタイル]] と同じです。平均は一部の極端に遅い体験に引っ張られ、逆に「4 人に 1 人がひどい目にあっている」状況を隠してしまいます。75 パーセンタイルは「大多数のユーザーが良い体験をしている」ことを保証しつつ、外れ値に振り回されにくいバランスの取れた線です。

### 2-3. LCP — 主役が見えるまで

- **定義**：ページの読み込み開始から、**ビューポート（画面に見えている範囲）内で最も大きい画像・動画のポスター・テキストブロック**が描画されるまでの時間。
- ユーザーがクリック・タップ・キー入力をした時点で候補探しは打ち切られます。
- EC サイトの商品詳細ページなら、たいてい **商品のメイン画像** が LCP 要素になります。

web.dev は LCP を 4 つの区間（サブパート）に分けて考えることを勧めています。

```
  ナビゲーション開始                                       LCP
  |―― TTFB ――|― 読み込み遅延 ―|―― 読み込み時間 ――|― 描画遅延 ―|
   HTML の最初     LCP 画像の取得が   LCP 画像の        画像は届いたが
   の 1 バイト     始まるまでの待ち   ダウンロード      描画されるまでの待ち
   目安 ~40%       目安 <10%          目安 ~40%         目安 <10%
```

「LCP が 4 秒」と分かっても、どの区間が長いかで直す場所がまったく変わります。

### 2-4. INP — 操作への反応

- **定義**：ページ滞在中のクリック・タップ・キー入力について、**入力から次のフレームが描画されるまで**の時間を測り、ほぼ最悪の値（操作回数が多いページでは外れ値を少し除いた値）をそのページの INP とします。
- 1 回の操作は **入力遅延**（メインスレッドが空くまでの待ち）＋ **処理時間**（イベントハンドラの実行）＋ **表示遅延**（レイアウト・描画）の合計です。
- スクロールやホバーは対象外です。

**INP が FID を置き換えた経緯**：以前は FID（First Input Delay）が反応性の指標でした。FID は **最初の 1 回の操作の「入力遅延」だけ** を測るため、「2 回目以降の操作が重い」「ハンドラの処理そのものが重い」ページを見逃していました。実際、Chrome のデータでは多くのサイトが FID では Good なのに、ユーザーは反応の悪さを感じていました。そこで **全操作の、入力から描画まで** を測る INP が開発され、**2024 年 3 月 12 日に Core Web Vitals の正式指標として FID を置き換えました**。FID は廃止済みです。

### 2-5. CLS — レイアウトのズレ

- **定義**：ユーザー操作に起因しない予期せぬレイアウトのズレについて、`影響を受けた面積の割合 × 移動距離の割合` を「レイアウトシフトスコア」とし、**最大のセッションウィンドウ**（ズレが 1 秒以内の間隔で続く塊、最長 5 秒）の合計を取ります。
- 単位はなく、「秒」ではありません。
- ユーザーの操作から 500ms 以内に起きたズレ（アコーディオンを開いた等）は数えません。

## 3. 各指標を悪化させる典型的な原因

| 指標 | 典型的な原因 | 詳しくは |
|---|---|---|
| LCP | サーバー応答（TTFB）が遅い | [[05_ネットワークと読み込みの最適化]] |
| LCP | レンダーブロッキングな CSS / JS | [[02_ブラウザのレンダリングと描画]] |
| LCP | LCP 画像が大きい・遅延読み込み（`loading="lazy"`）されている・JS で後から差し込まれる | [[04_画像とフォントの最適化]] |
| LCP | クライアントサイドレンダリング（CSR）で HTML に中身がない | [[05_ネットワークと読み込みの最適化]] |
| INP | メインスレッドを長時間占有する JS（ロングタスク） | [[02_ブラウザのレンダリングと描画]] |
| INP | 巨大な JS バンドル、ハイドレーション、サードパーティスクリプト | [[03_JavaScriptとバンドルの最適化]] |
| INP | 操作のたびに大量の DOM を再描画する | [[02_ブラウザのレンダリングと描画]] |
| CLS | `width` / `height` 指定のない画像・iframe・広告枠 | [[04_画像とフォントの最適化]] |
| CLS | Web フォントの差し替えで文字幅が変わる | [[04_画像とフォントの最適化]] |
| CLS | 後から挿入されるバナー（Cookie 同意、キャンペーン告知） | 本節下 |

**Shop での例**：商品詳細ページで「在庫あり」バッジを API 応答後に価格の上へ差し込むと、価格とカートボタンが下にズレて CLS が悪化します。差し込む場所をあらかじめ `min-height` で確保するか、ズレても他の要素を押し下げない位置（オーバーレイ）に出します。

## 4. 補助指標：TTFB・FCP・TBT

Core Web Vitals の 3 つは「結果」の指標です。原因を切り分けるには補助指標を合わせて見ます。

| 指標 | 意味 | 目安（web.dev, 2026 年時点） | 何の診断に使うか |
|---|---|---|---|
| **TTFB**（Time to First Byte） | リクエストから HTML の最初の 1 バイトが届くまで | ≤ 0.8 秒で Good | サーバー・ネットワーク・リダイレクトの遅さ → LCP の土台 |
| **FCP**（First Contentful Paint） | 何かしらのテキストや画像が最初に描画されるまで | ≤ 1.8 秒で Good | 「真っ白な時間」の長さ |
| **TBT**（Total Blocking Time） | FCP 以降、50ms を超えるタスクの「超過分」の合計（ラボ指標） | Lighthouse では 200ms 以下が目安 | INP のラボ代替。メインスレッドの混雑度 |

```
  TBT の計算例（数値は説明用）
  メインスレッドのタスク: [ 30ms ] [ 120ms ] [ 70ms ] [ 250ms ]
  50ms 超過分:              0        70        20        200
  TBT = 0 + 70 + 20 + 200 = 290ms
```

TBT はラボで測れるため CI に組み込みやすい一方、**実ユーザーの操作は測っていない** ので INP と完全には一致しません。

## 5. どう測るか：フィールドデータとラボデータ

### 5-1. 2 種類のデータ

| | フィールドデータ（Field / RUM） | ラボデータ（Lab / 合成） |
|---|---|---|
| 何か | 実ユーザーのブラウザで計測した値 | 決められた端末・回線で再現した値 |
| 代表例 | **CrUX**（Chrome UX Report）、自前の RUM | Lighthouse、WebPageTest、DevTools |
| 長所 | 本当にユーザーが体験している値。INP が測れる | 再現性がある。原因を深掘りできる。リリース前に測れる |
| 短所 | 集まるまで時間がかかる（CrUX は直近 28 日）。原因が分かりにくい | 実ユーザーの端末・回線・操作とズレる。INP は測れない |
| 判定に使われるのは | **こちら（Core Web Vitals の合否）** | 改善のための診断 |

**CrUX** は、利用統計の送信に同意した Chrome ユーザーの実測値を Google が集計した公開データセットです。直近 28 日のローリング集計で、訪問数が少ないページ・サイトにはデータが出ません。PageSpeed Insights や Search Console の「ウェブに関する主な指標」レポートはこの CrUX を表示しています。

### 5-2. 両方が食い違うのは普通

「Lighthouse では 95 点なのに、Search Console では Poor」はよくあります。

- ラボは **ページ読み込み時だけ** を見ます。読み込み後の操作が重いページは INP（フィールド）だけで悪く出ます。
- 実ユーザーには低スペックの Android や混雑した回線の人がいます。
- 逆に、リピーターが多くキャッシュが効いているサイトでは、フィールドの方が良く出ることもあります。

実務の基本方針は「**フィールドで問題を見つけ、ラボで原因を調べて直し、フィールドで効果を確認する**」です。具体的な手順は [[06_LighthouseとRUMで計測する]] で扱います。

### 5-3. その場でサッと測る

開発中は Chrome DevTools の Performance パネルを開くと、そのページの LCP・CLS・INP がライブで表示されます（2026 年時点）。コードで取るなら `web-vitals` ライブラリが簡単です。

```ts
// web-vitals v4 以降（2026 年時点）。FID 用の onFID は v5 で削除済み
import { onLCP, onINP, onCLS } from "web-vitals";

onLCP((m) => console.log("LCP", Math.round(m.value), "ms", m.rating));
onINP((m) => console.log("INP", Math.round(m.value), "ms", m.rating));
onCLS((m) => console.log("CLS", m.value.toFixed(3), m.rating));
// m.rating は "good" | "needs-improvement" | "poor"
```

## 6. SEO との関係を正しく理解する

よく「Core Web Vitals を改善すると検索順位が上がる」と言われますが、Google の公式説明は次のとおりです（2026 年時点の Google 検索セントラル）。

- **Core Web Vitals はランキングシステムで使われている**。
- しかし Google は **関連性の高いコンテンツを常に優先** する。ページエクスペリエンスが平凡でも、最も関連性の高いページは上位に出る。
- ページエクスペリエンスが効くのは、**関連性が同程度の候補が多いとき** の差になりうる程度。
- Search Console やツールで良い結果が出ても **上位表示は保証されない**。SEO だけのために満点を目指すのは時間の使い方として最善ではない、と明記されている。

つまり Core Web Vitals を改善する一番の理由は **ユーザー体験とビジネス指標（直帰率・コンバージョン率）** であり、SEO は副次的な効果と考えるのが正確です。

## よくある誤解・つまずき

- ❌ Lighthouse のスコアが Core Web Vitals の合否だ
  ✅ 合否は **フィールドデータ（CrUX）の 75 パーセンタイル** で決まります。Lighthouse はラボでの診断ツールで、INP は測れません。
- ❌ LCP は「ページの読み込みが全部終わった時間」
  ✅ **ビューポート内で最大の要素** が描画された時間です。画面外の広告が遅くても LCP には影響しません。
- ❌ INP は最初のクリックの速さ
  ✅ それは廃止された FID です。INP は **滞在中の全操作** を見て、ほぼ最悪のものを取ります。
- ❌ CLS はズレた回数
  ✅ **面積 × 距離** で、最悪のセッションウィンドウの合計です。小さな要素が少し動く程度ならほぼ 0 です。
- ❌ 直したら翌日には Search Console が Good になる
  ✅ CrUX は直近 28 日の集計なので、効果が完全に反映されるまで約 4 週間かかります。

## まとめ

- Core Web Vitals は「見える（LCP ≤ 2.5s）」「反応する（INP ≤ 200ms）」「ズレない（CLS ≤ 0.1）」の 3 指標
- 判定は実ユーザーの **75 パーセンタイル**、モバイル・デスクトップ別
- INP は 2024 年 3 月に FID を置き換えた。全操作の入力〜描画を測る
- TTFB・FCP・TBT は原因を切り分けるための補助指標
- 合否はフィールド（CrUX）、診断はラボ（Lighthouse）。両者のズレは普通
- SEO への効果は「関連性が同程度のときの差」程度。主目的はユーザー体験

## 確認クイズ

1. 実ユーザー 1,000 人の LCP のうち、700 人が 2 秒、300 人が 5 秒でした。このページの LCP は Good でしょうか？
> [!tip]- 答え
> Good ではありません。速い順に並べると 75 パーセンタイル（750 人目）は 5 秒側に入るため **Poor** です。平均（2.9 秒）で見ても分かりませんが、「4 人に 1 人以上がひどい体験」はパーセンタイルなら見逃しません。

2. FID では Good だったのに、INP に切り替わってから Poor になったページがあります。どんな原因が考えられますか？
> [!tip]- 答え
> 例：最初のクリック時はメインスレッドが空いていたが、2 回目以降の操作（フィルタ変更など）で重いハンドラや大量の再描画が走っている。FID は最初の操作の入力遅延しか見ないため、処理時間や描画の遅さ、後半の操作の重さを見逃していました。

3. Lighthouse で LCP 1.8 秒なのに、CrUX では LCP 3.6 秒です。何を疑いますか？
> [!tip]- 答え
> 実ユーザーの端末・回線がラボ条件より遅い、地域による TTFB の差、A/B テストや Cookie バナーなど実環境だけで出る要素、ログイン状態で LCP 要素が変わる、などを疑います。RUM でアトリビューション（どの要素が LCP か、どの区間が長いか）を取って確認します（[[06_LighthouseとRUMで計測する]]）。
