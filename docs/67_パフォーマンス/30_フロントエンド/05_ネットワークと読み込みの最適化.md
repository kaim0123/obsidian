## 1. ひとことで言うと

ネット通販で 10 個の商品を買うとき、「1 個注文して届いたら次を注文」を 10 回繰り返すと、トラックがどれだけ速くても（帯域が太くても）時間がかかります。効くのは「**まとめて注文する**」「**近くの倉庫から送る**」「**次に欲しいものを先に注文しておく**」です。Web の読み込みも同じで、多くの場合、ボトルネックはデータ量よりも **往復（ラウンドトリップ）の回数と 1 往復の時間（RTT）** です。

- 往復を減らす（接続の再利用、HTTP/2・3、リソースヒント）
- 往復を短くする（CDN でユーザーの近くから返す）
- 往復をなくす（キャッシュ、bfcache、事前読み込み）

## 2. なぜ RTT が支配的なのか

**RTT（Round Trip Time）** は、パケットがクライアントとサーバーを往復する時間です。光ファイバーでも東京〜米国西海岸で 100ms 前後、モバイル回線ではさらに数十〜数百 ms が加わります。これは物理的な距離と無線区間の性質で決まるため、帯域を増やしても縮みません。

新しいオリジン（ドメイン）から最初のバイトを受け取るまでの往復：

```
  クライアント                                  サーバー
     |―― DNS 問い合わせ ――――――――→ (DNS)          1 RTT（DNS サーバーまで）
     |←――――――――――――――――――――――|
     |―― TCP SYN ――――――――――――――――――――――――――→|  1 RTT
     |←―――――――――――――――――――――――――― SYN-ACK|
     |―― TLS 1.3 ClientHello ――――――――――――――――→|  1 RTT
     |←―――――――――――――――――――――― ServerHello等|
     |―― HTTP GET /products/42 ―――――――――――――→|  1 RTT + サーバー処理時間
     |←―――――――――――――――――――――――― HTML の先頭|
  
  RTT 150ms（モバイル想定）なら、サーバー処理 0ms でも最初の 1 バイトまで約 600ms
  （数値は説明用の例）
```

さらに TCP は **スロースタート** で、接続直後は少量しか送れず、往復のたびに送信量を増やします。そのため、小さなファイルを何十個も新しい接続で取ると、帯域を使い切る前に往復待ちで時間が過ぎます。

## 3. HTTP/2 と HTTP/3

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 1 接続で並行リクエスト | 不可（ブラウザは 1 オリジン 6 接続程度で並列化） | **多重化**で可能 | 可能 |
| ヘッダー圧縮 | なし | HPACK | QPACK |
| トランスポート | TCP | TCP | **QUIC（UDP 上）** |
| 接続確立 | TCP + TLS で 2 RTT〜 | 同左 | **1 RTT**（再接続は 0-RTT も可） |
| パケットロス時 | — | 1 つのロスで全ストリームが待つ（TCP の Head-of-Line ブロッキング） | 他のストリームは止まらない |
| 回線切り替え（Wi-Fi→4G） | 再接続 | 再接続 | 接続 ID で継続できる |

実務上のポイント：

- HTTP/1.1 時代の「ファイルを 1 つに連結する」「ドメインを分割する（ドメインシャーディング）」は、HTTP/2 以降では **逆効果** になることがあります。接続が分かれると多重化の利点が消え、接続確立の往復も増えます。
- HTTP/3 はパケットロスの多いモバイル回線で効果が出やすいです。多くの CDN ではスイッチ 1 つで有効にできます（2026 年時点）。

```bash
# どのプロトコルで通信しているか確認する
curl -sI --http2 https://shop.example.com/ | head -1          # HTTP/2 200
curl -sI https://shop.example.com/ | grep -i alt-svc          # alt-svc: h3=":443" があれば HTTP/3 対応
# ブラウザでは DevTools Network パネルの Protocol 列（h2 / h3）
```

## 4. リソースヒント

ブラウザは HTML を上から読んで必要なものを見つけますが、CSS の中の画像やフォント、JS が後から読むファイルは発見が遅れます。**リソースヒント** は「これが必要になるよ」と先に教えるための仕組みです。

| ヒント | 何をするか | 使いどころ | 注意 |
|---|---|---|---|
| `dns-prefetch` | DNS 解決だけ先にする | 重要度の低い外部ドメイン | コストはごく小さい |
| `preconnect` | DNS + TCP + TLS まで先にする | **すぐ使う** 外部オリジン（画像 CDN、API） | 使わないと接続が無駄になる。2〜4 個程度まで |
| `preload` | 今のページで使うリソースを高優先度で取得 | 発見が遅い重要リソース（LCP の背景画像、フォント） | 使わないと警告が出て帯域の無駄。乱用すると優先度の意味がなくなる |
| `modulepreload` | ES モジュールを取得し、パース・コンパイルまで先に | 依存が深いモジュール | バンドラーが自動で付けることが多い |
| `prefetch` | **次のページ** で使うリソースを低優先度で取得 | 次に遷移する可能性が高いページ | 今のページの読み込みを邪魔しない |

```html
<head>
  <!-- 画像 CDN へは早めに接続しておく -->
  <link rel="preconnect" href="https://images.shop.example.com">
  <!-- レビューウィジェットはあとで使う。DNS だけ -->
  <link rel="dns-prefetch" href="https://reviews.example.net">
  <!-- CSS の背景で使われる LCP 画像は HTML から発見できないので preload -->
  <link rel="preload" as="image" href="https://images.shop.example.com/hero-800.avif"
        fetchpriority="high">
  <!-- フォントは crossorigin が必須（ないと 2 回ダウンロードされる） -->
  <link rel="preload" as="font" type="font/woff2" href="/fonts/shop-sans.woff2" crossorigin>
</head>
```

さらに一歩進んだ方法として、サーバーが本番の応答を作っている間に **`103 Early Hints`** で preconnect / preload を先に返す方法もあります（CDN が対応していれば TTFB の待ち時間を有効活用できます）。

## 5. TTFB を改善する

TTFB は LCP の土台です。web.dev では 0.8 秒以下が目安とされています（[[01_Core_Web_Vitals]]）。TTFB の中身を分解すると、改善先が見えます。

| 区間 | よくある原因 | 対策 |
|---|---|---|
| リダイレクト | `http→https`、`shop.example.com→www.shop.example.com` の多段リダイレクト | リンクを最終 URL に、HSTS |
| 接続確立 | 遠いサーバー、HTTP/1.1 | CDN（[[04_CDNによる負荷軽減]]）、HTTP/3 |
| サーバー処理 | 遅い API・DB クエリ、毎リクエストのレンダリング | キャッシュ、静的生成、バックエンドの改善（[[01_APIレスポンスタイムの分解]]） |
| 配信 | 圧縮なし、キャッシュ不可の設定 | Brotli、`Cache-Control`（[[06_HTTPキャッシュと圧縮]]） |

```bash
# curl で TTFB の内訳を見る
curl -o /dev/null -s -w \
'DNS: %{time_namelookup}s\nTCP: %{time_connect}s\nTLS: %{time_appconnect}s\nTTFB: %{time_starttransfer}s\nTotal: %{time_total}s\n' \
https://shop.example.com/products/42
# 出力例（数値は説明用）
# DNS: 0.012s  TCP: 0.045s  TLS: 0.090s  TTFB: 1.240s  Total: 1.310s
# → TLS 完了から TTFB まで 1.15s。サーバー処理が支配的
```

ブラウザでは DevTools の Network パネルで HTML のリクエストを選び、**Timing** タブの「Waiting for server response」を確認します。Next.js ならサーバー側で `Server-Timing` ヘッダーを返すと、DB やキャッシュの内訳も Timing タブに表示できます。

## 6. レンダリング戦略の性能比較

ページの HTML を **いつ・どこで** 作るかは、TTFB・LCP・INP に大きく影響します。

| 戦略 | HTML を作るタイミング | TTFB | LCP | JS / INP | 向いているページ |
|---|---|---|---|---|---|
| **CSR**（Client-Side Rendering） | ブラウザで JS 実行後 | 速い（空の HTML） | **遅い**（JS → API → 描画） | 重い | ログイン後の管理画面 |
| **SSR**（Server-Side Rendering） | リクエストごとにサーバーで | サーバー処理分遅い | 良い | ハイドレーション分 | 個人化されたページ、在庫が頻繁に変わるページ |
| **SSG**（Static Site Generation） | ビルド時 | **最速**（CDN から静的配信） | 最良 | ハイドレーション分 | ブログ、ヘルプ |
| **ISR**（Incremental Static Regeneration） | ビルド時＋一定間隔・オンデマンドで再生成 | SSG と同等 | 最良 | 同上 | 商品詳細、商品一覧 |
| **ストリーミング SSR** | サーバーで生成しつつ、できた部分から順に送る | 速い（先頭をすぐ返す） | 良い | 同上 | 遅い部品が混ざるページ |

```
  CSR：|―空HTML―|――JS DL――|―JS実行―|――API――|―描画―|  ← LCP（数値の代わりに区間の長さで比較）
  SSR：|――――― サーバーで API + 描画 ―――――|―HTML―|  ← LCP
  ISR：|―HTML（CDN キャッシュ）―|  ← LCP
  ストリーミング：|―ヘッダー・商品情報―|  ← LCP   |――― レビュー（遅い API）―――| 後から流し込む
```

Shop の商品詳細ページなら、「商品名・画像・価格」は ISR でキャッシュし、「在庫数」「おすすめ」「レビュー」のような遅い・個人化された部分は `<Suspense>` でストリーミングする、という組み合わせが現実的です。

```tsx
// app/products/[id]/page.tsx（Next.js App Router、2026 年時点）
import { Suspense } from "react";
import { getProduct } from "@/lib/api";
import { Reviews } from "./Reviews";

export const revalidate = 300; // 5 分ごとに再生成（ISR）

export default async function Page({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const product = await getProduct(id); // キャッシュされる部分
  return (
    <main>
      <h1>{product.name}</h1>
      {/* LCP 要素は最初のチャンクに含める */}
      <img src={product.imageUrl} width={800} height={800} fetchPriority="high" alt={product.name} />
      <Suspense fallback={<p>レビューを読み込み中…</p>}>
        <Reviews productId={id} /> {/* 遅い API。準備でき次第ストリーミング */}
      </Suspense>
    </main>
  );
}
```

Next.js のキャッシュ設定（`revalidate`、Cache Components / `"use cache"` など）はバージョンによって大きく変わっているため、使っているバージョンの公式ドキュメントを確認してください。

## 7. 「次のページ」を速くする

### 7-1. bfcache（戻る／進むキャッシュ）

**bfcache（back/forward cache）** は、ページから離れるときにページ全体（JS の状態を含む）をメモリに保存し、「戻る」「進む」で **瞬時に復元** するブラウザの機能です。モバイルではナビゲーションのかなりの割合が戻る／進むなので、効果は大きいです。

bfcache が効かなくなる典型例：

- `unload` イベントリスナーを登録している（使わず `pagehide` を使う）
- `Cache-Control: no-store` の HTML（Chrome では条件付きで許容する変更が進んでいるが、2026 年時点でも要確認）
- 開いたままの WebSocket / IndexedDB 接続など

```ts
// bfcache から復元されたことを検知して、古い表示（カートの数など）を更新する
window.addEventListener("pageshow", (e) => {
  if (e.persisted) {
    refreshCartBadge();
  }
});
```

DevTools の **Application → Back/forward cache** で「Test back/forward cache」を実行すると、使えない理由が一覧で表示されます。

### 7-2. Speculation Rules API

**Speculation Rules API** は、次に遷移しそうなページを **事前取得（prefetch）** または **事前レンダリング（prerender）** させる仕組みです。prerender が当たると、クリックした瞬間にページが表示され、LCP がほぼ 0 になります。

```html
<script type="speculationrules">
{
  "prerender": [{
    "where": { "href_matches": "/products/*" },
    "eagerness": "moderate"
  }]
}
</script>
```

- `eagerness`：`immediate`（すぐ）／`eager`／`moderate`（ホバーなど）／`conservative`（押し始め）。積極的なほど当たりやすい反面、外れたときのサーバー負荷とデータ通信が増えます。
- prerender ではページの JS も事前に実行されるため、**表示前に解析イベントが送られる** などの副作用に注意します（主要な解析ツールは対応済みのことが多い）。
- ログアウトやカート追加など **副作用のある URL は対象から外す** 必要があります。
- **対応状況（2026 年時点の調査）**：Chrome / Edge などの Chromium 系は対応。Safari はフラグの後ろで実装中、Firefox は未対応で、Baseline ではありません。非対応ブラウザでは単に無視されるため、段階的強化として導入できます。最新状況は MDN の互換性表で確認してください。

## よくある誤解・つまずき

- ❌ 回線が速ければ読み込みも速い
  ✅ 小さなリソースが多い Web ページでは、帯域より RTT と往復回数が効きます。
- ❌ `preload` をたくさん付ければ速くなる
  ✅ 全部を「最優先」にすると優先度の意味がなくなり、LCP 画像や CSS の帯域を奪います。発見が遅い重要リソースだけに使います。
- ❌ SSR は常に CSR より速い
  ✅ サーバー処理が遅いと TTFB が伸び、全体が遅れます。キャッシュできる部分は SSG / ISR に、遅い部分はストリーミングにします。
- ❌ HTTP/2 でもファイルは 1 つに連結した方がよい
  ✅ 多重化があるので、適度に分割した方がキャッシュ効率も良くなります（極端な細分化は別問題）。
- ❌ Speculation Rules はすべてのリンクに immediate で付ければよい
  ✅ 外れた分だけサーバーとユーザーの通信量を浪費します。遷移確率の高いリンクに、適切な eagerness で使います。

## まとめ

- Web の読み込みは「往復回数 × RTT」が支配的。減らす・短くする・なくすの 3 方向で考える
- HTTP/2 は多重化、HTTP/3 は QUIC で接続確立の短縮とロスに強い通信を実現
- リソースヒントは役割で使い分け。preconnect と preload は少数精鋭で
- TTFB は curl や Timing タブで分解し、リダイレクト・接続・サーバー処理のどこかを特定する
- 静的にできる部分は SSG / ISR、遅い部分はストリーミング。CSR は LCP に不利
- bfcache を壊さない、Speculation Rules で次ページを先回り（Chromium 系のみ）

## 確認クイズ

1. RTT 200ms の回線で、HTTP/1.1 かつ新しいオリジン（TLS 1.3）から HTML を取得します。サーバー処理を 0 とすると、最初のバイトまで何往復かかりますか（DNS 含む）？
> [!tip]- 答え
> DNS 1 + TCP 1 + TLS 1 + HTTP リクエスト 1 = 約 4 往復、およそ 800ms です。HTTP/3 なら TCP と TLS がまとめて 1 往復になり、約 3 往復に減ります。

2. `<link rel="preload" as="font" href="/fonts/a.woff2">` を付けたのに、DevTools でフォントが 2 回ダウンロードされています。なぜですか？
> [!tip]- 答え
> `crossorigin` 属性がないためです。フォントは CORS モードで取得されるので、`crossorigin` なしの preload とは別のリクエストと見なされ、preload した分が使われずに再取得されます。

3. 商品詳細ページを SSR にしたところ LCP が CSR より悪化しました。考えられる原因と対策は？
> [!tip]- 答え
> サーバー側でレビューやおすすめなど遅い API をすべて待ってから HTML を返しているため、TTFB が大きく伸びた可能性があります。商品情報は ISR でキャッシュし、遅い部分は `<Suspense>` でストリーミングして、LCP 要素を含む先頭部分を早く返します。
