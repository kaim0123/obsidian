## 詳しい要約

### 結論：「遅い」は1種類ではない

「サイトが遅い」という不満の裏には、少なくとも次の3つの別体験が混ざっている。

1. **見えるまで遅い** — 開いたのに本文や主役のコンテンツが出ない
2. **反応するまで遅い** — ボタンは見えているのに押しても反応しない
3. **ズレる** — 押そうとした瞬間にレイアウトが動き、意図しない場所を押してしまう

これらは困り方も直し方も違う。ブラウザの「読み込み完了」（`load` イベント）のような**1つの数字では表せない**。だから Core Web Vitals は **LCP・INP・CLS** の3指標で測る。

---

### なぜ「読み込み完了」だけでは足りないか

- ブラウザは遅延読み込みを除き、ページが使うファイルが揃うと「読み込み完了」と言う。
- しかし本文が HTML に最初から無く、JavaScript が後から取得して描くページでは、**ファイル完了と「人が読める」時刻がズレる**（例: 完了1秒／本文4秒）。
- 測っているのは「ファイル」、人が見ているのは「中身」。区切りとしては正しいが、体験の代表値には外れる。
- さらにこの知らせは「押せるか」「ズレないか」を一切見ていない。冒頭の3困りのうち2つは対象外。

---

### LCP（Largest Contentful Paint）：見えるまで

**何を測るか**  
画面内で**面積が一番大きい「中身のある要素」**（画像／動画／テキストの塊）が描かれた時刻。初ピクセルやヘッダーだけだと早すぎ・甘すぎるため、「意味のある表示」を厳密に定義する代わりに、**大抵主役と一致する最大要素を代理**にする。

**ポイント**

- 画面外にはみ出した分は数えない（見えていない遅延で点を落とさない）。
- スクロールで候補は入れ替わるが、**ユーザーがページに触った瞬間で候補探しは打ち切り**、最後に残った時刻が LCP。
- ページ全体の読み込み完了ではない。画面外の広告遅延などは時刻を動かさない。
- LCP までの時間を区間に分けると、同じ合計秒数でも「どこで待ったか」が分かり、改善箇所が変わる（例: ファイルは来ているのに描画待ちなら、描画側を直す）。

**合格ライン（2026年9月時点）**  
Good: **2.5秒以下** ／ Poor: **4.0秒超**（75パーセンタイル）

---

### INP（Interaction to Next Paint）：反応するまで

**何を測るか**  
クリック・タップ・キー入力から、**次に画面が描き変わるまで**の端から端（待ち＋処理＋描画）。API の応答待ちそのものではない。押したことが画面に現れればそこで終わる。

**なぜ遅くなるか**  
画面を作る作業台（メインスレッド）は1本。長い処理が占領すると、ボタン反応も列に並び、押してもすぐ始まらない。通信が遅い問題と、反応が遅い問題は別。ただし返事待ちの間にメインスレッドを塞げば INP は伸びる。

**FID との違い**

- 旧 FID: **最初の操作**がどれだけ待たされたかだけ → 直後は軽く後半が重いページが見えにくい。
- INP: ページを閉じるまで操作を測り、**一番悪かった1回**を取る。長く開くページの「後から出る重さ」も効く。

**数え方の範囲**  
クリック／タップ／キー入力のみ。ホバー・ズーム・スクロールは対象外。

**改善の一例**  
長い処理を細かく切り、間にブラウザの順番（メインスレッドが開く瞬間）を挟む。

**合格ライン**  
Good: **200ms以下** ／ Poor: **500ms超**（75パーセンタイル）

---

### CLS（Cumulative Layout Shift）：ズレない

**何を測るか**  
「何回ズレたか」ではなく、**動いた範囲（画面に占める割合）× 動いた距離**。どちらかが小さければスコアも小さい。狭い範囲の移動は読者の邪魔になりにくい。

**合計の取り方**

- ページを開き続けるほど無限に足し続けない。
- まとまって起きたズレを一塊にし、**一番悪い区間の合計**を取る。
- ユーザー操作直後のごく短い間の変化は「勝手なズレ」とみなさない（自分で開いたものが動くのは当然）。ゆっくりしたアニメは一瞬を過ぎた分が数えられる。

**改善の一例**  
画像に幅・高さを指定し、届く前から場所を確保する。

**合格ライン**  
Good: **0.1以下** ／ Poor: **0.25超**（75パーセンタイル）

---

### 3つで Core Web Vitals

| 困り方 | 指標 | Good の目安 |
|--------|------|-------------|
| 見えるまで | LCP | ≤ 2.5s |
| 反応するまで | INP | ≤ 200ms |
| ズレない | CLS | ≤ 0.1 |

合格ラインは「上限」ではなく目安。体験のすべてがこの3つというわけでもなく、**測ると決めたのがこの3つ**。

---

### ラボ（手元）とフィールド（実ユーザー）は別物

- **手元（Lighthouse 等）**: 決められた1台・条件固定・キャッシュから・押す人がいない。再現しやすく原因の場所が分かる。
- **実ユーザー（CrUX 等）**: 端末・回線・キャッシュがバラバラで、実際に押す。同じページでも人ごとに数字が違う。「本当に起きているか」が分かる。

**「手元100点なのに実ユーザーが悪い」が起きる理由の例**

- Lighthouse のパフォーマンス点数は複数指標の加重和。**INP そのものの配点は0**（点数に直接入らない）。
- 代わりに「メインスレッドが詰まっていた時間」などは手元でも測れるが、**人がいつどこを押したかの実測は手元では取れない**。
- しかも手元の読み込み中の観察だけでは、**読み込み後に重くなるページの操作**は点数に出にくい。

逆に、多くのユーザーがキャッシュを持っていれば、**実ユーザーの方が手元より良く出る**こともある。手元の方がいつも甘い／実ユーザーの方がいつも厳しい、ではない。

**数字のまとめ方**

- 平均ではなく **75パーセンタイル**（4回のうち3回はこれより良かった、という線）。極端値に振り回されにくく、遅い体験を平均に隠さない。
- フィールドはだいたい **直近28日**をまとめる。直しても翌日すぐには反映されず、効果が日を追って少しずつ入る。

**見る場所の目安**

- 手元: DevTools のパフォーマンスパネル（開くと LCP/CLS、操作すると INP も見える）
- 実ユーザー＋ラボ: PageSpeed Insights（1枚に両方）
- サイト全体: Search Console（訪問が少ないとフィールドが出ないことあり）

---

### 検索順位との関係

ランキングシステムは Core Web Vitals を使うが、**一番関連性の高い内容が勝つ**。満点を目的にすることは公式も勧めていない。遅いと感じたとき「3つのどれか」を言えるようになることが本編のゴール。
