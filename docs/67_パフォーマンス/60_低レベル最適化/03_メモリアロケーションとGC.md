## 1. ひとことで言うと

オフィスで書類（オブジェクト）を机に広げて仕事をしていると、いつか机がいっぱいになります。そこで清掃係（GC）が来て「もう誰も使っていない書類」を捨ててくれます。便利ですが、**清掃中は一時的に仕事の手を止める**必要があります。書類を大量に広げる人ほど清掃係が頻繁に来て、そのたびに手が止まります。

- JS・Python・Go・Java ではメモリ解放を GC が自動で行う
- GC は「いらないものを探す」作業なので、**ゴミを大量に出すとその分時間を取られる**
- 平均レイテンシには小さく見えても、**p99 のような遅い側に GC の停止が現れる**

## 2. スタックとヒープ

| | スタック（stack） | ヒープ（heap） |
|---|---|---|
| 置かれるもの | 関数の引数・ローカル変数（の一部）、戻り先 | オブジェクト、配列、クロージャ、文字列など |
| 確保・解放 | 関数呼び出し/終了で自動。ポインタを動かすだけで超高速 | 確保は比較的速いが、解放は GC が行う |
| 寿命 | 関数を抜けたら終わり | 誰かが参照している限り生き続ける |
| サイズ | 小さい（深い再帰で Stack Overflow） | 大きい（Node.js では上限を設定可能） |

JS では「数値はスタック、オブジェクトはヒープ」と単純には言えません（V8 は小さな整数を Smi としてポインタに埋め込み、小数は HeapNumber としてヒープに置くことがあります。逆に、関数の外に漏れないオブジェクトは JIT が**エスケープ解析**で消すこともあります）。開発者が意識すべきは「**`{}`、`[]`、文字列の結合、クロージャはヒープに何かを作る**」という点です。

## 3. GC の基本

### 到達可能性（reachability）

GC は「**ルート（グローバル変数、実行中の関数のローカル変数など）からたどれるオブジェクトは生きている、たどれないものはゴミ**」と判断します。

```
ルート ──→ A ──→ B
              └→ C        D ──→ E    （D, E はどこからも参照されていない）
生存: A, B, C            ゴミ: D, E（お互いに参照し合っていてもゴミ）
```

### マーク&スイープ（mark-and-sweep）

1. **マーク**：ルートからたどって、到達できたオブジェクトに印を付ける
2. **スイープ**：印の無いオブジェクトの領域を空き領域として回収する
3. （**コンパクション**：断片化した空き領域を詰めて、まとまった空きを作る）

### 世代別仮説（generational hypothesis）

「**ほとんどのオブジェクトは若くして死ぬ**」という経験則です。リクエスト処理中に作った一時オブジェクトの大半は、レスポンスを返した時点で不要になります。そこで GC は領域を世代に分け、**若い世代だけを頻繁に・安く掃除**し、生き残ったものだけを古い世代に移します。

## 4. V8 の GC

```
┌─────── Young 世代（小さい：既定で数 MB〜数十 MB）───────┐
│  nursery ──生存──→ intermediate ──さらに生存──→ ─────┼─→ Old 世代へ昇格
│  Scavenge（Minor GC）: 生きているものだけをコピー       │
│  → ゴミが多いほど速い（ゴミには触らない）               │
└─────────────────────────────────────────────────────────┘
┌─────── Old 世代（大きい：上限は --max-old-space-size）───┐
│  Mark-Compact（Major GC）: マーク → スイープ → コンパクション│
│  → ヒープ全体をたどるので重い                            │
└─────────────────────────────────────────────────────────┘
```

| 種類 | 対象 | 方式 | コスト |
|---|---|---|---|
| Scavenge（Minor GC） | Young 世代 | セミスペース方式。生存オブジェクトだけを空き側へコピーして入れ替える | 頻繁だが短い（通常 1ms 前後〜数 ms の桁） |
| Mark-Compact（Major GC） | Old 世代 | マーク・スイープ・コンパクション | 回数は少ないが重い |

### Orinoco：止まる時間を短くする工夫

V8 の GC プロジェクト **Orinoco** は、「JS を止めて全部掃除する（stop-the-world）」時間を減らすため、次の技法を組み合わせています（V8 blog "Trash talk"）。

| 技法 | 意味 |
|---|---|
| 並列（parallel） | JS を止めている間、メインスレッドとヘルパースレッドで手分けして掃除 → 停止時間を短縮 |
| インクリメンタル（incremental） | 掃除を小分けにして JS の実行の合間に挟む → 1 回の停止は短くなる（総量は減らない） |
| 並行（concurrent） | JS を動かしたまま、バックグラウンドスレッドで掃除 → メインスレッドがほぼ止まらない |

現在の V8 では、Scavenge は並列、Old 世代のマーキングとスイープは並行、コンパクションは並列で行われます。それでも**ゼロにはならない**ので、ゴミを大量に生む処理は停止時間を増やします。

### GC 停止が p99 に効く理由

GC はリクエストと無関係なタイミングで起きます。たまたま GC と重なったリクエストだけが遅くなるので、**平均や中央値はほとんど変わらず、p99・p99.9 だけが悪化**します（[[02_レイテンシとパーセンタイル]]）。Node.js はメインスレッドが 1 本なので、GC で止まっている間は**全リクエストの処理が止まります**。

## 5. どう測るか

### GC の頻度と停止時間を見る

```bash
# GC が起きるたびに 1 行出力（2026 年時点の Node.js）
node --trace-gc dist/server.js
# 例: [12345:0x...]  5021 ms: Scavenge 38.2 (52.1) -> 22.4 (52.1) MB, 1.8 / 0.0 ms ...
#     [12345:0x...]  9873 ms: Mark-Compact 180.3 (210.0) -> 95.1 (205.0) MB, 45.2 / 0.0 ms ...
```

本番では、`perf_hooks` の `PerformanceObserver` で GC イベントをメトリクスに送るのが便利です。

```ts
import { PerformanceObserver, constants } from "node:perf_hooks";

const obs = new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    const kind = (e.detail as { kind: number }).kind;
    const name = kind === constants.NODE_PERFORMANCE_GC_MAJOR ? "major"
      : kind === constants.NODE_PERFORMANCE_GC_MINOR ? "minor" : "other";
    // 実務では Prometheus のヒストグラムなどに記録する
    console.log(`gc ${name} ${e.duration.toFixed(1)}ms`);
  }
});
obs.observe({ entryTypes: ["gc"] });
```

`prom-client` の `collectDefaultMetrics()` を使えば `nodejs_gc_duration_seconds` が自動で取れます。**p99 レイテンシのスパイクと Major GC の時刻が一致するか**を見ます（[[MOC_可観測性体系]]）。

### ヒープの使用量を見る

```ts
const m = process.memoryUsage();
console.log({ heapUsedMB: m.heapUsed / 1e6, heapTotalMB: m.heapTotal / 1e6, rssMB: m.rss / 1e6 });
```

`heapUsed` が GC 後も**右肩上がりで戻らない**ならリークを疑います。

```
heapUsed
  │         ／＼  ／＼  ／＼          正常: のこぎり型（GC で下がる）
  │   ／＼／    ＼／    ＼／
  │
  │                    ／＼／        リーク: GC 後の底が上がり続ける
  │            ／＼／＼／
  │    ／＼／＼／
  └──────────────────────────→ 時間
```

## 6. アロケーションを減らすテクニック

GC の仕事量はおおむね「作ったオブジェクトの量」と「生き残っているオブジェクトの量」で決まります。**ホットパスで**作る量を減らします。

### ループ内の一時オブジェクト

```ts
// ❌ 要素ごとに配列とオブジェクトを作る
const total = orders
  .map((o) => ({ ...o, subtotal: o.price * o.qty })) // 100万個の新オブジェクト
  .filter((o) => o.subtotal > 0)                      // さらに新しい配列
  .reduce((s, o) => s + o.subtotal, 0);

// ✅ 1 回のループで集計（中間配列もオブジェクトも作らない）
let total2 = 0;
for (const o of orders) {
  const subtotal = o.price * o.qty;
  if (subtotal > 0) total2 += subtotal;
}
```

数件〜数百件なら前者で問題ありません。差が出るのはデータが大きいバッチやホットパスです。

### 文字列の連結

V8 は `+=` の連結をロープ（rope）という構造で賢く扱うので、少量なら気にしなくて構いません。大量の行を作るなら配列に溜めて `join`、またはストリームで書き出すとメモリのピークを抑えられます。

```ts
// CSV 出力：全行をメモリに溜めず、ストリームに流す
import { createWriteStream } from "node:fs";
const out = createWriteStream("orders.csv");
for (const o of orders) {
  if (!out.write(`${o.id},${o.price},${o.qty}\n`)) {
    await new Promise((r) => out.once("drain", r)); // バックプレッシャーに従う
  }
}
out.end();
```

### オブジェクトプールと Buffer の再利用

生成コストが高いもの・大きいものは使い回します。

```ts
// 固定サイズの Buffer を使い回す（例：バイナリプロトコルのエンコード）
const scratch = Buffer.allocUnsafe(64 * 1024);
function encode(msg: { id: number; price: number }): Buffer {
  let off = 0;
  off = scratch.writeUInt32BE(msg.id, off);
  off = scratch.writeDoubleBE(msg.price, off);
  return scratch.subarray(0, off); // 呼び出し側が次の encode 前に使い終える前提
}
```

> [!warning] プールの注意点
> 使い回しは「前の利用者が触っていない」ことを保証しなければならず、バグの温床になります（上の例も、返り値を保持すると次の呼び出しで上書きされます）。V8 の Young 世代は短命オブジェクトの扱いが非常に得意なので、**小さなオブジェクトのプールはほぼ効果がない**ことが多いです。プールは DB コネクションや大きな Buffer など、生成が本当に高価なものに限りましょう。

## 7. メモリリークの典型と調査

Node.js サーバーは長時間動くので、少しずつのリークが最後には OOM（Out Of Memory）でのクラッシュにつながります。

| パターン | 例 | 対策 |
|---|---|---|
| グローバル変数・モジュールスコープへの蓄積 | `const seen = []` にリクエストごとに push | スコープを狭める、上限を付ける |
| クロージャによる保持 | 大きなデータを参照するコールバックを長寿命オブジェクトに登録 | 必要な値だけを取り出して渡す |
| イベントリスナーの外し忘れ | リクエストごとに `emitter.on(...)` して `off` しない | `once`、`AbortSignal`、`off` を確実に。`MaxListenersExceededWarning` は警告サイン |
| 無制限キャッシュ | `const cache = new Map()` にキーが増え続ける | LRU（`lru-cache` など）で件数・TTL の上限を付ける。弱参照で良いなら `WeakMap` |
| タイマーの止め忘れ | `setInterval` を `clearInterval` しない | ライフサイクルに合わせて解除 |

```ts
// ❌ Shop API でよくある無制限キャッシュ
const productCache = new Map<string, Product>();
app.get("/products/:id", async (req, res) => {
  let p = productCache.get(req.params.id);
  if (!p) { p = await repo.find(req.params.id); productCache.set(req.params.id, p); }
  res.json(p);
}); // 存在しない ID でも何でもキーになり、永遠に増える

// ✅ 上限付き
import { LRUCache } from "lru-cache";
const productCache2 = new LRUCache<string, Product>({ max: 10_000, ttl: 60_000 });
```

### heap snapshot での調査手順

1. **スナップショットを取る**：
   - 開発環境：`node --inspect dist/server.js` → Chrome で `chrome://inspect` → Memory タブ → Heap snapshot
   - 本番に近い環境：`node --heapsnapshot-signal=SIGUSR2 dist/server.js` で起動し `kill -USR2 <pid>`、またはコードから `v8.writeHeapSnapshot()`
2. **負荷をかけて 2〜3 回取る**：起動直後 → 1000 リクエスト後 → さらに 1000 リクエスト後
3. **Comparison ビューで差分を見る**：増え続けているコンストラクタ（`Object`、`Map`、特定のクラス名）を探す
4. **Retainers（保持元）をたどる**：「誰がこのオブジェクトを参照しているか」をルートまでたどると、グローバルのキャッシュやリスナーにたどり着く

> [!note] スナップショットのコスト
> heap snapshot の取得中はプロセスが止まり、ヒープと同程度の追加メモリを使います。本番では負荷分散から外したインスタンスで取りましょう。DevTools の詳しい操作は [[Performance・Memory（遅さとメモリリークの調査）]] を参照してください。

### --max-old-space-size

Old 世代の上限（MiB）を指定します。既定値はシステムメモリなどから決まるため、コンテナでは明示しておくと安全です。

```bash
node --max-old-space-size=1536 dist/server.js   # メモリ 2GB のコンテナで約 75%
```

- 上限を上げるのは**リークの修正にはならない**（OOM までの時間が延びるだけ）
- 上限を大きくすると Major GC 1 回あたりの仕事量が増え、停止が長くなる場合もある
- ヒープ以外（Buffer、ネイティブモジュール）もメモリを使うので、コンテナ上限ぎりぎりには設定しない

## 8. 他の言語の GC（紹介）

| 言語 | 方式 | 主なチューニング |
|---|---|---|
| Python（CPython） | **参照カウント**（参照が 0 になった瞬間に解放）＋循環参照を回収する**世代別 GC** | `gc.freeze()`（fork 前に既存オブジェクトを GC 対象外に）、`gc.set_threshold()`。3.14.0〜3.14.4 はインクリメンタル GC だったが、本番でのメモリ増加報告を受け 3.14.5 で 3.13 の世代別 GC に戻された |
| Go | 並行マーク&スイープ（世代別ではない） | `GOGC`（既定 100：前回 GC 後のヒープの何 % 増えたら GC するか）、`GOMEMLIMIT`（メモリ上限のソフトリミット） |
| Java（JVM） | 世代別。G1 が既定、低停止の ZGC・Shenandoah も選べる | `-Xmx`（最大ヒープ）、`-XX:+UseZGC`、`-XX:MaxGCPauseMillis` |

どの言語でも「**まず GC ログ/メトリクスで停止時間と頻度を測る → アロケーションを減らす → それでも足りなければ GC 設定**」の順番は同じです。

## よくある誤解・つまずき

- ❌「GC がある言語ではメモリリークは起きない」
  ✅ GC は「到達できない」ものしか回収しません。キャッシュやリスナーが参照し続けていれば、使っていなくても回収されません。
- ❌「メモリが足りないなら `--max-old-space-size` を増やせばよい」
  ✅ リークなら時間稼ぎにしかなりません。まずスナップショットの差分で原因を探します。
- ❌「オブジェクトプールを使えば必ず速くなる」
  ✅ 短命な小オブジェクトは V8 の Scavenge が得意です。プールは複雑さとバグを増やすので、大きく高価なものに限ります。
- ❌「平均レイテンシが良ければ GC は問題ない」
  ✅ GC の停止は p99 に出ます。パーセンタイルと GC イベントを並べて見ましょう。

## まとめ

- オブジェクト・配列・クロージャ・文字列はヒープに確保され、GC が回収する
- GC は「ルートから到達できるか」で生死を判定し、世代別仮説に基づいて若い世代を安く掃除する
- V8 は Scavenge（Young）と Mark-Compact（Old）を、Orinoco の並列・インクリメンタル・並行技法で短い停止に抑えている
- GC の停止は p99 に効く。`--trace-gc` や GC メトリクスで測り、ホットパスのアロケーションを減らす
- リークの典型はグローバル・クロージャ・リスナー・無制限キャッシュ。heap snapshot の差分と Retainers で原因をたどる
- `--max-old-space-size` はリーク対策ではない。Python・Go・Java も「測る → 減らす → 設定」の順

## 確認クイズ

1. Shop API の平均レイテンシは 50ms で安定しているのに、p99 だけ時々 300ms に跳ねます。GC を疑う場合、何を確認しますか？
> [!tip]- 答え
> `--trace-gc` や `nodejs_gc_duration_seconds` などで GC の発生時刻と停止時間を記録し、p99 のスパイクの時刻と Major GC（Mark-Compact）が一致するかを確認します。一致するなら、ホットパスのアロケーション削減や Old 世代に残るデータ（大きなキャッシュなど）の見直しを検討します。

2. 世代別 GC が効率的なのはなぜですか？
> [!tip]- 答え
> 「ほとんどのオブジェクトは若くして死ぬ」ため、若い世代だけを頻繁に掃除すれば少ない作業で多くのゴミを回収できます。V8 の Scavenge は生存オブジェクトだけをコピーするので、ゴミが多いほどむしろ速く終わります。

3. heap snapshot を 3 回取って比較したところ、`EventEmitter` のリスナー配列が増え続けていました。考えられる原因と対策は？
> [!tip]- 答え
> リクエストごとに `on` でリスナーを登録し、外していない可能性が高いです。`once` を使う、処理終了時に `off` する、`AbortSignal` で一括解除するなどで対策します。Retainers をたどってどこで登録しているかを特定します。
