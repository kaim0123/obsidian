# レイテンシとパーセンタイル

[[MOC_パフォーマンス体系|📚 目次]] ｜ [[01_パフォーマンスとは何か|← 前へ]] ｜ [[03_性能要件と目標の決め方|次へ →]]

> [!abstract] この記事で分かること
> - 平均応答時間だけを見ると、なぜ問題を見逃すのか
> - p50 / p95 / p99 / p99.9 の意味と、どれをどんなときに見るか
> - ファンアウト（1 リクエストが多数の裏側呼び出しに広がる構成）で「裾（テール）」が効く理由
> - ヒストグラムでの分布の読み方と、「パーセンタイルは平均できない」理由
> - 計測の落とし穴 Coordinated Omission（協調的な欠落）の概要
>
> **前提**：[[01_パフォーマンスとは何か]] を読んでいると理解しやすいです。

## 1. ひとことで言うと

クラス 30 人のテストの平均点が 70 点でも、全員が 70 点前後なのか、半分が 100 点で半分が 40 点なのかでは、先生が打つべき手はまったく違います。レイテンシも同じで、**「平均」は分布の形を消してしまいます**。

そこで「遅い順に並べたとき、上位何％がどれくらい遅いか」を表す **パーセンタイル（percentile）** を使います。特に、ごく一部の非常に遅いリクエスト ＝ **テールレイテンシ（tail latency、分布の裾）** は、大規模なシステムほど多くのユーザーに影響します。

> [!important] 要点
> - レイテンシは平均ではなく **p50・p95・p99** などのパーセンタイルで見る
> - 裾（p99 以上）は「100 人に 1 人の不運」ではなく、ファンアウトやページ内の多数のリクエストで **多くのユーザーが踏む**
> - パーセンタイルは **平均できない**。集計はヒストグラムから計算する
> - 負荷ツールの測り方次第で、裾が実際より小さく見えることがある（Coordinated Omission）

## 2. 平均が嘘をつく理由

### 2.1 例：平均は同じでも中身が違う

次の 2 つの API は、どちらも 10 回の平均が 100ms です（説明用の例）。

```
API-A: 95 98 100 100 101 99 102 100 103 102   → 平均 100ms
API-B: 20 20 20 20 20 20 20 20 20 820         → 平均 100ms
```

API-A は毎回ほぼ 100ms で安定しています。API-B は 9 割のリクエストが 20ms と速いのに、1 割が 820ms もかかります。ユーザーから見れば、API-B は「普段は速いのに、ときどき固まるサイト」です。平均値だけ見ていると、この 2 つの違いは分かりません。

### 2.2 なぜレイテンシの分布はゆがむのか

レイテンシの分布は、テストの点数のような左右対称の山（正規分布）にはなりません。**右に長い裾を引く**のが普通です。理由は、遅くなる原因が「たまに」起きるからです。

- GC（ガベージコレクション）の停止にたまたま当たった
- キャッシュがミスして DB まで取りに行った
- DB のロック待ちに巻き込まれた
- 混雑時にキュー（待ち行列）で待たされた
- TCP の再送が起きた

どれも普段は起きないけれど、起きると数十〜数千倍遅くなります。こういう分布では、平均は「ほとんどのリクエスト」よりも大きく、「遅いリクエスト」よりもずっと小さい、**誰の体験も表していない値**になりがちです。

## 3. パーセンタイルの読み方

### 3.1 定義

**pN（N パーセンタイル）** とは、「全リクエストを速い順に並べたとき、N％の位置にある値」です。言い換えると「N％のリクエストはこの値以下で終わっている」。

| 表記 | 意味 | よく使う場面 |
| --- | --- | --- |
| **p50**（中央値、median） | 半分のリクエストはこれより速い | 「典型的な体験」 |
| **p95** | 20 回に 1 回はこれより遅い | 目標値（SLO）でよく使う |
| **p99** | 100 回に 1 回はこれより遅い | テールの監視。バックエンドの目標 |
| **p99.9** | 1000 回に 1 回はこれより遅い | 大規模サービス、決済などの重要 API |
| max（最大値） | 一番遅い 1 回 | 外れ値の調査用。目標には不向き（1 件で大きく揺れる） |

### 3.2 計算してみる（TypeScript）

パーセンタイルの計算方法にはいくつか流儀（補間するかどうか）がありますが、ここでは一番分かりやすい **nearest-rank 法**（「上から数えて何番目か」をそのまま取る）で書きます。

```ts
// percentile.ts —— npx tsx percentile.ts で実行できます
function percentile(sortedMs: number[], p: number): number {
  if (sortedMs.length === 0) throw new Error("empty");
  // nearest-rank: ceil(p/100 * n) 番目（1 始まり）
  const rank = Math.ceil((p / 100) * sortedMs.length);
  return sortedMs[Math.max(0, rank - 1)];
}

function summarize(samplesMs: number[]) {
  const s = [...samplesMs].sort((a, b) => a - b);
  const avg = s.reduce((a, b) => a + b, 0) / s.length;
  return {
    avg: Math.round(avg),
    p50: percentile(s, 50),
    p95: percentile(s, 95),
    p99: percentile(s, 99),
    max: s[s.length - 1],
  };
}

const apiA = [95, 98, 100, 100, 101, 99, 102, 100, 103, 102];
const apiB = [20, 20, 20, 20, 20, 20, 20, 20, 20, 820];
console.log("A", summarize(apiA)); // A { avg: 100, p50: 100, p95: 103, p99: 103, max: 103 }
console.log("B", summarize(apiB)); // B { avg: 100, p50: 20, p95: 820, p99: 820, max: 820 }
```

平均は同じ 100ms でも、p50 と p95 を並べると違いが一目で分かります。なお、サンプルが 10 件しかないと p95 も p99 も「一番遅い 1 件」になってしまいます。**p99 を語るには最低でも数百〜数千件のサンプルが必要**です。

## 4. 裾（テール）はなぜ効くのか

### 4.1 1 ページ＝ 1 リクエストではない

「p99 なんて 100 回に 1 回でしょ？」と思うかもしれません。ところが現実のユーザー操作は、たくさんのリクエストでできています。

- Shop の商品詳細ページを 1 回表示する間に、ブラウザは HTML・API・画像・JS など数十のリクエストを出す
- 1 人のユーザーは 1 回の訪問で何ページも見る

1 回のリクエストが p99 を踏む確率が 1％でも、20 個のリクエストのどれか 1 つが踏む確率は `1 - 0.99^20 ≒ 18%` です。**「100 人に 1 人の不運」ではなく「5〜6 人に 1 人の日常」になる**わけです。

### 4.2 ファンアウトと The Tail at Scale

サーバー側でも同じことが起きます。1 つのリクエストを処理するために、裏で多数のサーバーに並列に問い合わせ、**全部の返事がそろってから** 応答する構成を **ファンアウト（fan-out）** と呼びます。

```
                ┌─▶ 在庫サービス     12ms
                ├─▶ 価格サービス     9ms
ユーザー ─▶ API ├─▶ レビューサービス 11ms
  （全部待つ）   ├─▶ おすすめサービス 980ms  ← 1 つでも遅いと
                └─▶ 画像メタ情報     8ms
                       ↓
                応答時間 ≒ 一番遅いもの（980ms）
```

Google の Jeffrey Dean と Luiz André Barroso の論文「**The Tail at Scale**」（Communications of the ACM, 2013）は、これを次の例で示しました。

> 通常は 10ms で応答し、p99 が 1 秒のサーバーがあるとする。1 つのリクエストが 100 台のサーバーに問い合わせて全員の応答を待つと、全員が速く返す確率は `0.99^100 ≒ 0.366`。つまり **ユーザーリクエストの約 63％ が 1 秒を超える**。

個々のサーバーにとっては「100 回に 1 回」の遅さでも、ファンアウトすると **全体の典型的な体験** になってしまいます。論文は、こうした裾を減らす工夫（遅い応答を待たずに別のレプリカにも投げる「ヘッジリクエスト」など）も紹介しています。

| ファンアウト数 | 全員が p99 以内に返る確率 | 1 つ以上が p99 を超える確率 |
| --- | --- | --- |
| 1 | 99.0% | 1.0% |
| 5 | 95.1% | 4.9% |
| 20 | 81.8% | 18.2% |
| 100 | 36.6% | 63.4% |

（`0.99^n` から計算した値です。各呼び出しが独立だと仮定しています。）

教訓は「**裏側のサービスほど、高いパーセンタイル（p99・p99.9）で厳しく管理する必要がある**」ということです。

## 5. ヒストグラムで分布を見る

### 5.1 Shop 商品一覧 API の分布（例）

以下は、Shop の `GET /api/products` に 1 万リクエストを流したときの分布の **説明用の例** です（実測値ではありません）。

```
レイテンシ帯      件数   ヒストグラム（1 マス ≒ 100 件）          累積
   0–  50ms     1,800  ██████████████████                       18.0%
  50– 100ms     3,400  ██████████████████████████████████       52.0%  ← p50 はここ
 100– 200ms     2,900  █████████████████████████████            81.0%
 200– 500ms     1,450  ██████████████▌                          95.5%  ← p95 はここ
 500–1000ms       300  ███                                      98.5%
1000–2000ms        60  ▌                                        99.1%  ← p99 はここ
2000–5000ms        90  ▉                                       100.0%  ← p99.9 はここ

平均 ≒ 175ms ／ p50 ≒ 95ms ／ p95 ≒ 490ms ／ p99 ≒ 1.8s ／ p99.9 ≒ 4.7s
（パーセンタイルは区間内を直線補間した概算）
```

この図から読み取れること：

- **平均（175ms）は p50（95ms）の 2 倍近い**。裾の遅いリクエストに平均が引っ張られている
- p99 が約 2 秒 ── この章の題材「商品一覧 API が p99 で 2 秒かかる」の状態
- 2〜5 秒の帯が 1〜2 秒の帯より多い。**山が 2 つある（二峰性、bimodal）** のは、「普段の処理」とは別の原因（例：キャッシュミス時に重い集計クエリが走る、コネクションプール待ちでタイムアウト寸前まで待つ）が混ざっているサインです

最後の点が重要です。**ヒストグラムの形は、原因の手がかりになります**。平均や p99 の 1 つの数字だけでは、「全体がじわっと遅い」のか「一部だけ別の理由で極端に遅い」のか区別できません。

### 5.2 どう測るか

**負荷テストツールで見る**：k6 は実行後のサマリーにレイテンシの統計を出します。2026 年時点の既定は `avg, min, med, max, p(90), p(95)` なので、p99 も見たいときは設定を足します。

```js
// products-test.js —— k6 run products-test.js
import http from "k6/http";

export const options = {
  vus: 20,
  duration: "1m",
  summaryTrendStats: ["avg", "med", "p(95)", "p(99)", "p(99.9)", "max"],
};

export default function () {
  http.get("http://localhost:3000/api/products?page=1");
}
```

負荷テストの設計そのものは [[03_負荷テストの設計と実施]] で扱います。

**本番で見る**：本番では 1 件ずつの値を全部保存するのは重いので、**ヒストグラム（あらかじめ決めた区間ごとの件数）** として記録し、そこからパーセンタイルを計算するのが一般的です（Prometheus の Histogram と `histogram_quantile()`、OpenTelemetry の Histogram など）。区間（バケット）の切り方で精度が決まる点など、集計の詳細は [[04_パーセンタイルとヒストグラムの集計]] を参照してください。

## 6. パーセンタイルは平均できない

ダッシュボードでよくある間違いが「API サーバー 4 台の p99 を平均して全体の p99 とする」ことです。

**例**（説明用）：

- サーバー A：1,000 リクエスト、全部 100ms → p99 = 100ms
- サーバー B：100 リクエスト、50 件が 100ms、50 件が 3,000ms → p99 = 3,000ms

```
p99 の平均        = (100 + 3000) / 2 = 1,550ms   ← 意味のない数字
本当の全体の p99  = 1,100 件を並べた 1,089 番目 = 3,000ms
```

全体では 50/1,100 ≒ 4.5％ のリクエストが 3 秒かかっているので、全体の p99 は 3,000ms です。平均した 1,550ms は、**どのリクエストの体験でもない** 値です。

同じ理由で、「1 分ごとの p99 を 60 個平均して 1 時間の p99 にする」のも間違いです。正しくは、

1. 生データ（全サンプル）から計算する、または
2. **ヒストグラム（区間ごとの件数）を足し合わせてから** パーセンタイルを計算する

のどちらかです。ヒストグラムは件数なので足し算できますが、パーセンタイルは足し算も平均もできません。

## 7. 計測の落とし穴：Coordinated Omission

Azul Systems の Gil Tene は講演「How NOT to Measure Latency」で、多くの負荷テストツールやベンチマークが **裾を実際より小さく見せてしまう** 問題を指摘し、**Coordinated Omission（協調的な欠落）** と名付けました。

### 7.1 何が起きるか

「前のリクエストの応答が返ってから次を送る」タイプの負荷生成（クローズドモデル）を考えます。本来は 10ms ごとに 1 リクエスト送るつもりだとします。

```
本来の予定:  ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲ ...   10ms ごとに送信
             │
サーバーが 1 秒止まった!
             │
ツールの動き: ▲─────────(1秒待つ)─────────▲ ▲ ▲ ...
             記録: 1000ms が 1 件だけ
```

サーバーが 1 秒止まっている間、ツールは応答を待っていて **次のリクエストを送りません**。本物のユーザーなら、その 1 秒間にも約 100 件のリクエストが届いて、それぞれ最大 1 秒近く待たされていたはずです。ところがツールの記録には「1 秒の 1 件」しか残らず、残りの 99 件分の遅さが **計測から消えます**。ツールがサーバーの遅さに「協調して」送信を控えてしまうので、この名前がついています。

結果として、p99 や p99.9 が何桁も楽観的に出ることがあります。

### 7.2 どう避けるか

- **到着率（rps）を固定する負荷生成を使う**（オープンモデル）。k6 なら `constant-arrival-rate` エグゼキューター、wrk2 なら `-R` で目標レートを指定する
- 遅延の起点を「実際に送った時刻」ではなく「**本来送るはずだった時刻**」で測る
- 負荷テストの結果は、本番の RUM（実ユーザー計測）や APM の分布と突き合わせる

詳しくは [[01_計測の基本と落とし穴]] と [[03_負荷テストの設計と実施]] で扱います。

## よくある誤解・つまずき

- ❌「平均応答時間が目標以内だから問題ない」
  ✅ 平均は裾を隠します。p95・p99 を必ず併記しましょう。
- ❌「p99 は 1％ のユーザーにしか影響しない」
  ✅ 1 ページで数十のリクエストが飛び、裏側でファンアウトするので、裾を踏むユーザーはずっと多くなります。
- ❌「各サーバーの p99 を平均すれば全体の p99」
  ✅ パーセンタイルは平均できません。ヒストグラムを合算してから計算します。
- ❌「サンプル 50 件で p99 を出した」
  ✅ 50 件の p99 は実質「最大値」です。高いパーセンタイルほど多くのサンプルが必要です。
- ❌「負荷ツールが出した p99 はそのまま信じてよい」
  ✅ Coordinated Omission で楽観的になっていることがあります。負荷モデル（固定レートかどうか）を確認しましょう。

## まとめ

- レイテンシの分布は右に長い裾を引くので、**平均ではなくパーセンタイル**（p50・p95・p99・p99.9）で見る
- ページ内の多数のリクエストやファンアウトにより、**裾は多くのユーザーの体験になる**（100 台ファンアウトで約 63％ が p99 級の遅さ ── The Tail at Scale）
- ヒストグラムを見ると、二峰性など **原因の手がかり** が分かる
- **パーセンタイルは平均できない**。集計はヒストグラムを足してから計算する
- 負荷テストでは **Coordinated Omission** に注意し、到着率を固定する負荷モデルを使う

## 確認クイズ

1. ある API の 1 分間の値が「平均 120ms、p50 60ms、p99 2.4s」でした。平均だけを報告すると何を見落としますか？
> [!tip]- 答え
> 半数のリクエストは 60ms 以下と速い一方、1％ のリクエストが 2.4 秒以上かかっているという「裾の重さ」を見落とします。平均 120ms は、速い多数派とも遅い少数派とも違う値です。p99 が大きいので、GC・ロック待ち・キャッシュミスなど「たまに起きる原因」を疑って調べます。

2. 商品詳細 API が裏で 5 つのサービスに並列で問い合わせ、全部を待ってから返します。各サービスが独立に 1％ の確率で遅くなるとき、商品詳細 API が遅くなる確率はおよそいくつですか？
> [!tip]- 答え
> `1 - 0.99^5 ≒ 4.9%` です。各サービスにとっては p99 の遅さでも、API 全体では約 20 回に 1 回、つまり p95 付近の遅さになります。だから裏側のサービスは p99 や p99.9 でより厳しく管理する必要があります。

3. 「前の応答が返ってから次のリクエストを送る」負荷ツールで、サーバーが 2 秒止まりました。記録される遅いサンプルは何件程度で、本来は何件あるべきでしょうか？（本来の送信間隔は 20ms）
> [!tip]- 答え
> ツールは応答を待っているので、遅いサンプルは「2 秒の 1 件」だけです。本来は 2 秒間に約 100 件（2000ms ÷ 20ms）が届き、それぞれ最大 2 秒近く待たされていたはずです。これが Coordinated Omission で、裾が大幅に過小評価されます。
