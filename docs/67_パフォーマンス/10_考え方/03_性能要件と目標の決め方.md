# 性能要件と目標の決め方

[[MOC_パフォーマンス体系|📚 目次]] ｜ [[02_レイテンシとパーセンタイル|← 前へ]] ｜ [[04_最適化の進め方とトレードオフ|次へ →]]

> [!abstract] この記事で分かること
> - 性能を「非機能要件」として扱う意味
> - 「p95 < 300ms at 200 rps」のように、**検証できる形** で目標を書く方法
> - 性能目標と SLO（サービスレベル目標）の関係
> - フロントエンドの **パフォーマンスバジェット**（JS サイズ・LCP などの予算）
> - 「Latency Numbers Every Programmer Should Know」で処理時間の桁感を持つ方法と、Shop の性能要件表
>
> **前提**：[[02_レイテンシとパーセンタイル]] を読んでいると理解しやすいです。

## 1. ひとことで言うと

マラソンの練習で「速く走れるようになりたい」とだけ決めても、いつ練習を終えればいいのか分かりません。「フルマラソンを 4 時間以内、気温 15℃ のコースで」と決めれば、今の実力との差が分かり、練習の優先順位も決まります。

性能も同じです。「なるべく速く」は要件ではありません。**何を・どの指標で・どんな条件で・どこまで** を数字で書いて初めて、計測でき、達成したかどうかを判定できます。

> [!important] 要点
> - 性能目標は「指標・パーセンタイル・閾値・負荷条件」をセットで書く（例：`p95 < 300ms at 200 rps`）
> - 本番で守り続ける目標は SLO、リリース前に確かめる目標は負荷テストの合格基準、フロントの資産の上限はパフォーマンスバジェット
> - 処理時間の「桁感」を持っていると、無理な目標や見当違いの改善に早く気づける

## 2. 非機能要件としての性能

### 2.1 機能要件と非機能要件

- **機能要件**：何ができるか（「商品を検索できる」「注文できる」）
- **非機能要件（non-functional requirements）**：どれくらい良くできるか（性能・可用性・セキュリティ・保守性など）

ソフトウェア品質の国際規格 ISO/IEC 25010 では、性能は「**性能効率性（performance efficiency）**」として、次の 3 つの観点に分けられています。

| 観点 | 意味 | Shop での例 |
| --- | --- | --- |
| 時間効率性（time behaviour） | 応答時間・処理時間・スループット | 商品一覧 API の応答時間 |
| 資源効率性（resource utilization） | CPU・メモリ・帯域などの使用量 | API 1 台あたりのメモリ |
| 容量満足性（capacity） | 扱える最大の量 | セール時の同時注文数、商品数の上限 |

[[01_パフォーマンスとは何か]] で見た「3 つの顔」とほぼ対応しています。

### 2.2 性能要件が後回しにされると何が起きるか

機能は動くのに、リリース直前の負荷テストやリリース後のセールで「遅くて使えない」と分かるのが典型的な失敗です。そのときには、データモデル（テーブル設計）や API の粒度（1 画面で何回 API を呼ぶか）がもう固まっていて、直すのが高くつきます。

だから性能要件は **設計の前に、大まかでもいいので決めておく** のが大切です。厳密な数字は後で調整できますが、「桁」を間違えると設計からやり直しになります。

## 3. 目標の書き方

### 3.1 良い性能目標の 5 つの要素

```
  GET /api/products の応答時間が、200 rps の負荷で p95 < 300ms
  └───── 対象 ─────┘ └─ 指標 ─┘   └─ 負荷条件 ─┘ └ 分位 ┘└閾値┘

  ＋ 計測条件：本番相当のデータ量（商品 10 万件）、サーバー側で計測、5 分間
```

| 要素 | 書くこと | ない場合に起きる問題 |
| --- | --- | --- |
| **対象** | どの画面・どの API・どの処理か | 「全部速く」になり優先順位がつかない |
| **指標** | 応答時間、スループット、LCP、CPU 使用率など | 人によって測るものが違う |
| **分位（パーセンタイル）** | p50 / p95 / p99 など | 平均で判定して裾を見逃す |
| **閾値** | 300ms など具体的な数字 | 合否が判定できない |
| **負荷・計測条件** | rps や同時接続数、データ量、どこで測るか、計測期間 | 空の DB・1 リクエストだけで「達成」と誤判定 |

特に見落とされがちなのが **負荷条件** です。1 人で叩けば 50ms の API が、200 rps では 800ms になるのは普通のことです（[[01_スループットと待ち行列理論]]）。「何 rps のときに」を書かない目標は、ほとんど意味がありません。

### 3.2 悪い例 → 良い例

| ❌ 悪い例 | 何が足りない | ✅ 良い例 |
| --- | --- | --- |
| 「API は速くすること」 | 全部 | 「`GET /api/products` は 200 rps で p95 < 300ms、p99 < 800ms」 |
| 「平均 200ms 以内」 | 分位・負荷 | 「p95 < 200ms（ピーク時 150 rps、5 分間）」 |
| 「ページは 3 秒以内に表示」 | 指標の定義・分位・環境 | 「商品詳細ページの LCP が、実ユーザーのモバイルの p75 で 2.5 秒以下」 |
| 「1 万人が同時に使える」 | 「同時に」の意味が曖昧 | 「ピーク 1,500 rps（うち注文 API 100 rps）でエラー率 < 0.1%」 |

### 3.3 どう測るか：目標をそのままテストの合格基準にする

書いた目標は、そのまま負荷テストの **合否判定（threshold）** にできます。k6 なら次のように書けます。

```js
// products-slo-test.js —— k6 run products-slo-test.js
import http from "k6/http";

export const options = {
  scenarios: {
    steady: {
      executor: "constant-arrival-rate", // 到着率を固定（Coordinated Omission 対策）
      rate: 200,            // 200 rps
      timeUnit: "1s",
      duration: "5m",
      preAllocatedVUs: 100,
      maxVUs: 400,
    },
  },
  thresholds: {
    // 目標をそのまま書く。満たさないと k6 は 0 以外の終了コードで終わる
    http_req_duration: ["p(95)<300", "p(99)<800"],
    http_req_failed: ["rate<0.001"],
  },
};

export default function () {
  http.get("http://localhost:3000/api/products?page=1");
}
```

終了コードで合否が分かるので、CI に組み込めば「性能目標を割り込む変更」を自動で検出できます（[[04_最適化の進め方とトレードオフ]] の「リグレッション防止」）。負荷テストの組み立て方は [[03_負荷テストの設計と実施]] で扱います。

## 4. SLO との関係

**SLO（Service Level Objective、サービスレベル目標）** は、本番で継続的に守る品質の目標です（[[01_SLI・SLOの設計]]）。性能目標とは似ていますが、役割が少し違います。

| | 性能目標（負荷テストの合格基準） | レイテンシ SLO |
| --- | --- | --- |
| いつ使う | リリース前・設計時 | 本番運用中ずっと |
| どこで測る | テスト環境（本番相当の負荷を再現） | 本番の実トラフィック |
| 書き方の例 | 200 rps で p95 < 300ms | 28 日間で、リクエストの 99% が 500ms 以内 |
| 守れなかったら | リリースしない／改善する | エラーバジェットを消費 → 機能開発より信頼性改善を優先 |

関係を整理すると：

```
ユーザーの期待・ビジネス要件
        │
        ▼
レイテンシ SLO（本番で守る約束）  例: 28日間で 99% が 500ms 以内
        │  余裕（マージン）を持たせて
        ▼
性能目標（リリース前に確かめる）  例: 想定ピーク 200 rps で p95 < 300ms, p99 < 450ms
        │
        ▼
各コンポーネントの予算             例: DB クエリ p95 < 50ms、外部 API p95 < 100ms
```

SLO の書き方「リクエストの 99% が 500ms 以内」は、「p99 < 500ms」とほぼ同じことを、**良かったリクエストの割合** で表したものです。割合で書くとエラーバジェット（どれだけ失敗してよいか）を計算しやすい、という利点があります。

## 5. パフォーマンスバジェット

### 5.1 考え方

**パフォーマンスバジェット（performance budget）** は、ページの性能に関わる値に「これ以上は使ってはいけない」という **予算（上限）** を決めておくことです。家計簿の予算と同じで、新しい機能（ライブラリ・画像・計測タグ）を足すたびに、予算内に収まるかを確認します。

web.dev は予算を 3 種類に分けています。

| 種類 | 例 | 特徴 |
| --- | --- | --- |
| **量の予算**（quantity-based） | JS の合計サイズ、画像の合計サイズ、Web フォントの数、サードパーティスクリプトの数 | 開発中に確認しやすく、デザイナーにも伝えやすい |
| **マイルストーンの時間**（milestone timings） | LCP、FCP、INP など | ユーザー体験に直結。ただし測定条件で揺れる |
| **ルールベース** | Lighthouse のパフォーマンススコア | 総合的。中身はブラックボックスになりがち |

web.dev の記事では例として「モバイルの商品ページで JavaScript を 170KB 未満」「低速 3G の中位スマホで 5 秒以内に操作可能」などが挙げられています（これらは例であり、普遍的な基準ではありません）。

### 5.2 Shop のバジェット例

| 予算の項目 | 上限（例） | 計測方法 |
| --- | --- | --- |
| 商品詳細ページの JS（圧縮後） | 170KB | ビルド時にバンドルサイズを計測 |
| ファーストビューの画像合計 | 300KB | Lighthouse／WebPageTest |
| LCP（実ユーザー、モバイル p75） | 2.5 秒以下 | RUM（web-vitals ライブラリ） |
| INP（実ユーザー p75） | 200ms 以下 | RUM |
| CLS（実ユーザー p75） | 0.1 以下 | RUM |
| サードパーティスクリプト | 3 個まで | レビュー時にチェック |

（上限値は説明用の例です。自社の現状値と目標から決めます。）

LCP・INP・CLS の閾値は Core Web Vitals の「良い」の基準（75 パーセンタイル）に合わせています（[[01_Core_Web_Vitals]]）。

### 5.3 どう守るか

バジェットは決めるだけでは守られません。**CI で自動チェック** して、超えたらプルリクエストを止めるのが実務の定番です。

- バンドルサイズ：ビルド後のサイズをチェックするツール（size-limit など）を CI で回す
- Lighthouse CI：`assert` で LCP やスコアの下限を設定する（[[06_パフォーマンス（Lighthouse CI）]]）
- 本番：RUM で p75 を監視し、悪化したらアラート（[[06_LighthouseとRUMで計測する]]）

## 6. 桁感を持つ：Latency Numbers Every Programmer Should Know

目標を決めるとき、「その処理はそもそもどれくらいかかるものか」という **桁感** がないと、無理な目標（東京から米国の DB を毎回読むのに 50ms 以内）や、見当違いの最適化（ネットワーク往復を 10 回しているのに、ループの 1ns を削る）に気づけません。

Google の Jeff Dean が広めた（元は Peter Norvig の整理）有名な表があります。以下は 2012 年ごろの値として広く共有されているものです。

| 操作 | 時間 | 人間の感覚に直すと（1ns ＝ 1 秒） |
| --- | --- | --- |
| L1 キャッシュ参照 | 0.5 ns | 0.5 秒 |
| 分岐予測ミス | 5 ns | 5 秒 |
| L2 キャッシュ参照 | 7 ns | 7 秒 |
| mutex のロック／アンロック | 25 ns | 25 秒 |
| メインメモリ参照 | 100 ns | 1 分 40 秒 |
| 1KB を圧縮（Zippy） | 3 µs | 50 分 |
| 1KB を 1Gbps ネットワークで送信 | 10 µs | 2.8 時間 |
| SSD から 4KB ランダム読み込み | 150 µs | 1.7 日 |
| メモリから 1MB 連続読み込み | 250 µs | 2.9 日 |
| 同じデータセンター内の往復 | 500 µs | 5.8 日 |
| SSD から 1MB 連続読み込み | 1 ms | 11.6 日 |
| HDD のシーク | 10 ms | 3.8 か月 |
| HDD から 1MB 連続読み込み | 20 ms | 7.6 か月 |
| カリフォルニア → オランダ → カリフォルニアのパケット往復 | 150 ms | 4.8 年 |

> [!note] 数字そのものより「比」を覚える
> ハードウェアは年々速くなっているので、個々の値は 2026 年時点では古いものもあります（特に SSD やネットワーク）。年ごとの推定値は Colin Scott の対話的な版で確認できます。ただし「メモリはキャッシュの数百倍遅い」「ネットワーク往復はメモリ参照の数千倍以上」「大陸間の往復は光の速さで決まり、ほぼ縮まらない」という **比と桁** は今も通用します。

Shop に当てはめると、こんな見積もりができます。

- API サーバーと PostgreSQL が同じデータセンター内 → 1 往復 0.5ms 前後。**N+1 問題で 1 リクエストに 200 回クエリを投げると、往復だけで 100ms** 前後かかる計算（[[03_N+1問題の発見と解決]]）
- 日本のユーザーが米国のサーバーにアクセス → 往復だけで 100ms 超。TLS 接続確立には複数回の往復が必要なので、**CDN やリージョン選択の方がコードの最適化より効く**（[[04_CDNによる負荷軽減]]）
- Redis の参照（同一 DC）≒ 往復 0.5ms ＋処理 → DB で数十 ms かかる集計をキャッシュすれば大きく効く

## 7. 要件の決め方の手順と Shop の性能要件表

### 7.1 手順

1. **重要なユーザー操作を洗い出す**：売上やユーザー体験に直結する操作から（一覧表示、商品詳細、カート投入、注文確定）
2. **体感の基準を当てる**：0.1 秒／1 秒／10 秒の目安、Core Web Vitals（[[01_パフォーマンスとは何か]]）
3. **負荷を見積もる**：平常時・ピーク時（セール）の rps を、アクセスログや事業計画から出す（[[03_キャパシティプランニング]]）
4. **現状を測る**：ベースライン（今の p50/p95/p99）を取る。目標が現状から遠すぎないか確認
5. **予算を分配する**：画面全体の目標を、フロント・API・DB などの部品ごとの予算に分ける
6. **書いて合意する**：この表をチームと事業側でレビューし、テストと監視に組み込む
7. **見直す**：実ユーザーの計測結果や事業の変化に合わせて定期的に更新する

### 7.2 Shop の性能要件表（例）

| 対象 | 指標 | 目標 | 負荷・計測条件 | 根拠 |
| --- | --- | --- | --- | --- |
| 商品一覧ページ | LCP | p75 ≤ 2.5s | 実ユーザー・モバイル | Core Web Vitals「良い」 |
| 商品詳細ページ | LCP | p75 ≤ 2.5s（現状 4s） | 実ユーザー・モバイル | 同上。現状が最大の課題 |
| 全ページ | INP | p75 ≤ 200ms | 実ユーザー | Core Web Vitals「良い」 |
| `GET /api/products` | 応答時間 | p95 < 300ms、p99 < 800ms（現状 p99 2s） | 平常 200 rps、商品 10 万件 | 1 秒以内に一覧を出すため |
| `GET /api/products/:id` | 応答時間 | p95 < 150ms、p99 < 400ms | 平常 300 rps | LCP の予算から逆算 |
| `POST /api/orders` | 応答時間 | p95 < 500ms、p99 < 1.5s | セール時 100 rps | 決済連携を含むため緩め |
| `POST /api/orders` | エラー率 | < 0.1% | セール時 100 rps | 注文失敗は売上に直結 |
| API サーバー全体 | スループット | 1,500 rps を 4 台で処理 | CPU 使用率 70% 以下 | セールピークの見積もり |
| 商品詳細ページ | JS サイズ | ≤ 170KB（圧縮後） | ビルド時 | パフォーマンスバジェット |

（すべて説明用の例です。「現状」の値も例であり、この章で題材にする典型的な問題を表しています。）

## よくある誤解・つまずき

- ❌「目標は『平均 200ms』で十分」
  ✅ 平均は裾を隠します。p95 や p99 で、負荷条件とセットで書きましょう。
- ❌「目標は高ければ高いほど良い（全部 p99 < 50ms）」
  ✅ 厳しすぎる目標はコストと開発時間を食います。ユーザー体験とビジネス上の必要から逆算し、達成すべきところだけ厳しくします。
- ❌「性能要件はリリース前の負荷テストで決めればいい」
  ✅ その時点では設計が固まっていて直すのが高くつきます。大まかな桁は設計前に決めましょう。
- ❌「Latency Numbers の値を最新の正確な値として使う」
  ✅ 2012 年ごろの目安です。覚えるべきは比と桁で、正確な値は自分の環境で測ります。

## まとめ

- 性能は非機能要件（ISO/IEC 25010 の性能効率性）。**設計前に桁だけでも決める**
- 目標は **対象・指標・分位・閾値・負荷条件** の 5 要素で書く（`p95 < 300ms at 200 rps`）
- 本番で守る約束が **SLO**、リリース前の合格基準が **性能目標**、フロントの資産の上限が **パフォーマンスバジェット**。いずれも CI や監視で自動チェックする
- Latency Numbers で **桁感** を持つと、無理な目標や見当違いの改善に早く気づける
- 要件は「重要な操作 → 体感基準 → 負荷見積もり → 現状計測 → 予算分配 → 合意 → 見直し」の順で決める

## 確認クイズ

1. 「商品検索は 1 秒以内に返すこと」という要件には、何が足りませんか？ 良い形に書き直してください。
> [!tip]- 答え
> 分位（パーセンタイル）・負荷条件・計測条件が足りません。例えば「`GET /api/search` の応答時間が、ピーク 150 rps・商品 10 万件の環境で p95 < 500ms、p99 < 1s（サーバー側で 5 分間計測）」のように書きます。「1 秒以内」がユーザーの体感なら、フロントでの表示まで含めた計測も必要です。

2. 商品詳細 API が裏で DB に 1 件ずつ、合計 150 回クエリを投げています。DB は同じデータセンター内です。往復時間だけでおよそ何 ms かかりますか？ 目標「p95 < 150ms」との関係は？
> [!tip]- 答え
> 同一データセンター内の往復を 0.5ms とすると、150 回 × 0.5ms ≒ 75ms が往復だけで消えます。DB の処理時間を加えると、150ms の予算の大半を使ってしまいます。クエリをまとめる（N+1 の解消）方が、個々のクエリを速くするより効果的だと見当がつきます。

3. レイテンシ SLO「28 日間でリクエストの 99% が 500ms 以内」と、リリース前の性能目標「200 rps で p99 < 450ms」の閾値を変えているのはなぜですか？
> [!tip]- 答え
> 本番は、テスト環境では再現しきれない要因（データの偏り、他の処理との混雑、ネットワークの揺らぎ）があるので、リリース前の目標には余裕（マージン）を持たせます。テストでぎりぎり 500ms だと、本番では SLO を割り込む恐れが高いからです。
