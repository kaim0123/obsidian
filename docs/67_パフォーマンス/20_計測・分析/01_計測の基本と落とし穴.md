# 計測の基本と落とし穴

[[MOC_パフォーマンス体系|📚 目次]] ｜ [[04_最適化の進め方とトレードオフ|← 前へ]] ｜ [[02_ベンチマークの書き方|次へ →]]

> [!abstract] この記事で分かること
> - 性能を測るときに見るべき 4 つの指標（レイテンシ・スループット・エラー率・リソース）
> - ラボ計測と本番計測の違いと、計測環境を本番に近づけるコツ
> - ウォームアップ・ノイズ・観測者効果など、数字を狂わせる落とし穴
> - 正しい時刻の取り方（`performance.now()` / `process.hrtime.bigint()`）と `Date.now()` を避ける理由
> - 計測結果を後から比較できる形で残す記録テンプレート
>
> **前提**：[[02_レイテンシとパーセンタイル]] と [[04_最適化の進め方とトレードオフ]] を読んでいると理解しやすいです。

## 1. ひとことで言うと

体重計に乗るとき、朝起きてすぐ・同じ服・同じ体重計で測らないと「昨日より 1kg 減った！」が本当かどうか分かりません。夕食後に測ったり、体重計を替えたりすれば、ダイエットの効果よりも「測り方の違い」のほうが大きく出てしまいます。

ソフトウェアの性能計測も同じです。**「計測 → 仮説 → 改善 → 再計測」のサイクルは、計測が信頼できて初めて回ります。** 測り方がブレていると、効果のない改善を「効いた」と勘違いしたり、逆に効いた改善を捨てたりします。

要点：
- 何を測るか（指標）を先に決める
- 条件（環境・データ・ウォームアップ）を揃える
- 1 回ではなく複数回測り、ばらつきごと記録する

## 2. 何を測るか：4 つの基本指標

性能の「速い・遅い」は 1 つの数字では表せません。最低限、次の 4 つをセットで見ます。

| 指標 | 英語 | 意味 | Shop での例 |
|---|---|---|---|
| レイテンシ | Latency | 1 リクエストにかかる時間 | 商品一覧 API の p50 / p95 / p99 |
| スループット | Throughput | 単位時間あたりに処理できる量 | 注文 API の requests/sec（RPS） |
| エラー率 | Error rate | 失敗したリクエストの割合 | 5xx・タイムアウトの割合 |
| リソース使用量 | Resource utilization | CPU・メモリ・ディスク・ネットワーク・コネクション | API サーバーの CPU 使用率、DB コネクション数 |

なぜ 4 つセットなのかというと、**どれか 1 つだけを見ると簡単にだまされる**からです。

- レイテンシだけ見る：エラーを即座に返すようになると「速くなった」ように見える（失敗は速い）
- スループットだけ見る：処理量は増えたが p99 が 5 秒になっているかもしれない
- リソースを見ない：CPU 95% で張り付いていて、あと少し負荷が増えると崩壊する状態に気づけない

> [!note] 平均ではなくパーセンタイル
> レイテンシは平均値ではなく p50・p95・p99 などのパーセンタイル（percentile：小さい順に並べて何 % の位置にあるか）で見ます。理由は [[02_レイテンシとパーセンタイル]] で詳しく説明しています。

```
      レイテンシ ──┐
                   │   ┌── 4つを同じ時間軸で並べて見る
    スループット ──┼───┤
                   │   └── どれか1つの改善が他を悪化させていないか確認
       エラー率 ──┤
                   │
     リソース ────┘
```

## 3. ラボ計測と本番計測

計測する「場所」は大きく 2 つに分かれます。

| | ラボ計測（Lab / Synthetic） | 本番計測（Field / Production / RUM） |
|---|---|---|
| どこで | 手元・検証環境・CI | 本番環境の実ユーザー・実トラフィック |
| 強み | 条件を揃えられる・再現できる・改善前後を比較しやすい | 本当のユーザー体験が分かる |
| 弱み | 本番と条件が違う（データ量・ネットワーク・同時実行数） | ばらつきが大きく、原因の切り分けが難しい |
| 代表例 | ベンチマーク、負荷テスト、Lighthouse | APM、メトリクス、RUM（Real User Monitoring） |

**両方が必要です。** 本番計測で「どこが遅いか」を見つけ、ラボ計測で「なぜ遅いか」を再現・検証し、改善したら本番計測で「本当に良くなったか」を確認します。

```mermaid
flowchart LR
  A[本番計測で<br>遅い箇所を発見] --> B[ラボで再現<br>仮説を立てる]
  B --> C[改善して<br>ラボで再計測]
  C --> D[本番にリリース]
  D --> E[本番計測で<br>効果を確認]
  E --> A
```

### 計測環境を本番に近づける

ラボ計測で一番よくある失敗は「手元では速い」です。差が出やすいポイントは次のとおりです。

- **データ量**：products が 100 件の開発 DB と 50 万件の本番 DB では、インデックスが効くかどうかも実行計画も変わります（[[05_実行計画の読み方]]）。本番相当の件数・分布のデータを用意します。個人情報はマスキングするか、生成データで代替します。
- **データの偏り**：「人気商品に注文が集中する」「特定ユーザーだけ注文が 1 万件ある」などの偏りが性能を左右します。均一なダミーデータでは再現しません。
- **ネットワーク**：localhost では往復遅延（RTT）がほぼ 0 です。本番の API ⇔ DB 間が 1ms あれば、1 リクエストで 50 回クエリを投げるコードは 50ms 余計にかかります。Linux なら `tc netem` で遅延を足して再現できます。
- **マシンスペック**：CPU コア数・メモリ・ディスク種別（SSD / ネットワークディスク）を本番と揃えるか、少なくとも記録します。
- **設定**：`NODE_ENV=production`、ログレベル、コネクションプールのサイズ、キャッシュの有無を本番と揃えます。開発モードの Next.js は本番ビルドよりずっと遅いので、計測は必ず本番ビルドで行います。

## 4. 数字を狂わせる落とし穴

### 4-1. ウォームアップ（Warm-up）

プログラムは起動直後が一番遅いのが普通です。

- **JIT コンパイル**：Node.js の V8 は、最初はインタプリタで実行し、何度も呼ばれる関数（ホットな関数）だけを最適化コンパイルします。最初の数百〜数千回の呼び出しは遅いままです（詳しくは [[02_JITとコンパイラ最適化]]）。
- **キャッシュ**：OS のページキャッシュ、DB のバッファキャッシュ（PostgreSQL の shared_buffers）、Redis、アプリ内キャッシュは最初は空（コールド）です。
- **コネクション確立**：DB コネクションプールや HTTP keep-alive の接続は、最初のリクエストで作られます。

対策は「**計測前に捨てる実行を入れる**」ことです。負荷テストなら最初の 1〜2 分を集計から除外し、ベンチマークならウォームアップ回数を設定します。

ただし「コールドスタート時の性能」自体が問題（サーバーレスのコールドスタート、デプロイ直後のスパイク）なら、あえてウォームアップなしで測ります。**何を知りたいかで決める**のがポイントです。

### 4-2. ノイズとばらつき

同じ処理を同じマシンで 10 回測っても、毎回数字は変わります。原因は、他のプロセス・CPU の周波数変動（ターボブースト・サーマルスロットリング）・GC のタイミング・クラウドの「うるさい隣人（noisy neighbor）」などです。

対策：

1. **複数回測る**：最低でも 5〜10 回。負荷テストなら 1 回を十分長く（数分以上）。
2. **中央値を使う**：平均は外れ値 1 個に引っ張られます。中央値（median）は外れ値に強いです。
3. **ばらつきも書く**：最小・最大、標準偏差、または信頼区間（confidence interval：「真の値はこの範囲にありそう」という幅）。
4. **差がばらつきより大きいか確認する**：改善前 100ms±15ms、改善後 95ms±15ms なら「差がない」と見るべきです。

```
改善前  |----[====|====]----|         中央値 100ms
改善後     |----[====|====]----|      中央値  95ms
           ↑ 範囲がほぼ重なっている → 「効果あり」とは言えない

改善前  |----[====|====]----|                  中央値 100ms
改善後                         |--[==|==]--|   中央値  60ms
           ↑ 範囲が離れている → 効果ありと言ってよい
（数値は説明用の例）
```

ベンチマークでの統計的な比較方法は [[02_ベンチマークの書き方]] で扱います。

### 4-3. 観測者効果（Observer effect）

**測ること自体が対象を遅くする**現象です。

- リクエストごとに詳細ログを同期で書き出す → I/O で遅くなる
- 計装（instrumentation：コードに計測処理を埋め込む）型のプロファイラ → 関数呼び出しごとにオーバーヘッドが乗り、小さい関数ほど過大に見える
- `--inspect` でデバッガを接続したまま計測 → 最適化の挙動が変わることがある
- 負荷テストツールを同じマシンで動かす → ツール自体が CPU を奪う

対策は、オーバーヘッドの小さい方法（サンプリング型プロファイラ、集計済みメトリクス）を選ぶこと、負荷生成マシンと被測定マシンを分けることです。詳しくは [[05_プロファイリング]] で扱います。

### 4-4. 間違った場所を測っている

「API のレスポンスタイム」と言っても、どこからどこまでかで値が変わります。

```
ブラウザ ──DNS/TCP/TLS──> LB ──> Nginx ──> Node.js ──> PostgreSQL
   ↑                                         ↑
   ユーザー体感（全部込み）              アプリ内の計測（処理だけ）
```

アプリのログに出る「処理時間 30ms」と、ユーザーが感じる「800ms」は両方正しい値です。どの区間を測ったのかを必ず明記します（区間の分解は [[01_APIレスポンスタイムの分解]]）。

## 5. どう測るか：時刻の正しい取り方

### `Date.now()` を避ける理由

`Date.now()` は「壁時計（wall clock）」の時刻で、OS の時刻合わせ（NTP による補正や手動変更）の影響を受けます。計測中に時刻が補正されると、経過時間がずれたり**マイナスになったり**します。また分解能はミリ秒単位で、1ms 未満の処理は 0 か 1 にしかなりません。

経過時間を測るときは、**単調増加時計（monotonic clock：決して戻らない時計）**を使います。

| 用途 | API | 単位 | 備考 |
|---|---|---|---|
| ブラウザ・Node.js 共通 | `performance.now()` | ミリ秒（小数） | 単調増加。ブラウザではセキュリティのため分解能が粗められている |
| Node.js | `process.hrtime.bigint()` | ナノ秒（BigInt） | 単調増加。高分解能 |
| Python | `time.perf_counter()` / `time.perf_counter_ns()` | 秒 / ナノ秒 | 単調増加 |
| 時刻の記録（いつ起きたか） | `Date.now()` / `new Date()` | ミリ秒 | ログのタイムスタンプ用。経過時間には使わない |

> [!info] ブラウザの分解能（2026 年時点の MDN の記載）
> ブラウザの `performance.now()` はタイミング攻撃対策で精度が粗められており、通常は 100µs、cross-origin isolated なページでは 5µs です。それより短い処理はループで何度も実行して合計時間を測ります。

### Node.js での計測コード例

```ts
// measure.ts — 関数の実行時間を複数回測り、中央値・p95 を出す
import { performance } from "node:perf_hooks";

async function measure(
  label: string,
  fn: () => Promise<unknown> | unknown,
  { warmup = 20, runs = 100 } = {},
) {
  // ウォームアップ：JIT・キャッシュ・コネクションを温める（集計しない）
  for (let i = 0; i < warmup; i++) await fn();

  const samples: number[] = [];
  for (let i = 0; i < runs; i++) {
    const start = process.hrtime.bigint();
    await fn();
    const end = process.hrtime.bigint();
    samples.push(Number(end - start) / 1e6); // ns → ms
  }

  samples.sort((a, b) => a - b);
  const pick = (p: number) =>
    samples[Math.min(samples.length - 1, Math.floor((p / 100) * samples.length))];
  console.log(
    `${label}: median=${pick(50).toFixed(2)}ms p95=${pick(95).toFixed(2)}ms ` +
      `min=${samples[0].toFixed(2)}ms max=${samples.at(-1)!.toFixed(2)}ms (n=${runs})`,
  );
}

// 使用例：JSON シリアライズの時間
const products = Array.from({ length: 1000 }, (_, i) => ({
  id: i,
  name: `product-${i}`,
  price: i * 100,
  tags: ["sale", "new"],
}));

await measure("JSON.stringify 1000 products", () => JSON.stringify(products));

// performance.now() 版（ブラウザでも同じ書き方）
const t0 = performance.now();
JSON.stringify(products);
console.log(`single run: ${(performance.now() - t0).toFixed(3)}ms`);
```

`node --experimental-strip-types measure.ts`（Node.js 22.6 以降）または `npx tsx measure.ts` で実行できます。1 回だけの計測（最後の 3 行）と、ウォームアップ後 100 回の中央値とで値が大きく違うことを確かめてみてください。

### Express のミドルウェアでリクエスト時間を記録する

```ts
import express from "express";

const app = express();

app.use((req, res, next) => {
  const start = process.hrtime.bigint();
  res.on("finish", () => {
    const ms = Number(process.hrtime.bigint() - start) / 1e6;
    // 実務ではログではなくヒストグラムメトリクス（Prometheus 等）に送る
    console.log(`${req.method} ${req.route?.path ?? req.path} ${res.statusCode} ${ms.toFixed(1)}ms`);
  });
  next();
});
```

ラベルに `req.path`（`/products/123` のような生の URL）を使うと種類が爆発するので、メトリクスにする場合はルート定義（`/products/:id`）を使います。集計方法は [[04_パーセンタイルとヒストグラムの集計]] を参照してください。

## 6. 計測結果の記録テンプレート

計測は「後から比較できる」ことに価値があります。数字だけメモすると、半年後に「この 120ms はどの条件だったか」が分からなくなります。次のテンプレートをコピーして使うのがおすすめです。

```markdown
## 計測記録：<何の計測か>（YYYY-MM-DD）

### 目的・仮説
- 例：商品一覧 API の p99 が遅いのは、products の全件ソートが原因ではないか

### 対象
- エンドポイント／関数：GET /products?category=shoes
- コードのバージョン：commit abc1234（ブランチ名）

### 環境
- マシン：c7g.xlarge（4 vCPU / 8GB）×1、DB：db.r7g.large
- ランタイム：Node.js 22.x、PostgreSQL 16
- データ量：products 50 万件、orders 300 万件（本番スナップショットをマスキング）
- 設定：NODE_ENV=production、プール max=20、Redis キャッシュ無効
- ネットワーク：同一 AZ（RTT 約 0.3ms）

### 方法
- ツール：k6 v1.x、constant-arrival-rate 100 RPS × 5 分
- ウォームアップ：最初の 60 秒を除外
- 繰り返し：3 回

### 結果
| 回 | p50 | p95 | p99 | RPS | エラー率 | API CPU |
|---|---|---|---|---|---|---|
| 1 | | | | | | |
| 2 | | | | | | |
| 3 | | | | | | |

### 考察・次のアクション
- 仮説は支持された／されなかった、理由
- 次に試すこと
```

ポイントは「**環境**」と「**方法**」を必ず書くことです。改善前後で 1 つでも条件が違えば、比較は無効になります。

## よくある誤解・つまずき

- ❌ 1 回測って速くなったから改善成功  
  ✅ ばらつきの範囲内かもしれません。複数回測って中央値と幅を比べます。
- ❌ 開発環境で速ければ本番でも速い  
  ✅ データ量・ネットワーク・設定（開発モード）が違えば結果は大きく変わります。本番相当の条件を用意するか、差を記録しておきます。
- ❌ 平均レイテンシが改善したからユーザー体験も改善した  
  ✅ 平均が下がっても p99 が悪化していることがあります。エラー率とリソースも同時に確認します。
- ❌ `Date.now()` の差分で十分  
  ✅ 時刻補正の影響を受け、分解能もミリ秒です。経過時間は `performance.now()` か `process.hrtime.bigint()` を使います。
- ❌ 計測ツールは対象に影響しない  
  ✅ 観測者効果があります。重い計装や同居する負荷ツールは結果を歪めます。

## まとめ

- 性能は「レイテンシ（パーセンタイル）・スループット・エラー率・リソース」の 4 つセットで測る
- ラボ計測で再現・検証し、本番計測で発見と効果確認をする。両方が必要
- データ量・ネットワーク・設定を本番に近づけ、違いは必ず記録する
- ウォームアップを入れ、複数回測って中央値とばらつきで比較する
- 経過時間は単調増加時計（`performance.now()` / `process.hrtime.bigint()`）で測る
- 結果は「目的・環境・方法・結果・考察」のテンプレートで残す

## 確認クイズ

1. 改善前の注文 API が p95 = 210ms（10 回の範囲 190〜240ms）、改善後が p95 = 200ms（範囲 185〜230ms）でした。「改善した」と言えますか？
> [!tip]- 答え
> 言えません。差（10ms）がばらつきの幅（約 50ms）よりずっと小さく、範囲がほぼ重なっています。回数を増やす、ノイズ源を減らす、統計的に比較するなどしてから判断します（数値は例）。

2. 経過時間の計測に `Date.now()` を使うべきでない理由を 2 つ挙げてください。
> [!tip]- 答え
> ① システム時刻の補正（NTP・手動変更）の影響を受け、経過時間がずれたりマイナスになったりする。② 分解能がミリ秒で、短い処理を正確に測れない。単調増加時計の `performance.now()` や `process.hrtime.bigint()` を使います。

3. デプロイ直後だけ商品一覧 API が遅いという報告がありました。ウォームアップを入れて計測すべきでしょうか？
> [!tip]- 答え
> この場合は「コールドな状態の性能」そのものが調査対象なので、ウォームアップなしで測ります。JIT 未最適化・キャッシュが空・コネクション未確立のどれが効いているかを切り分けます。何を知りたいかによってウォームアップの有無を決めます。
