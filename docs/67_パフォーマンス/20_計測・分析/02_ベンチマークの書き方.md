## 1. ひとことで言うと

ベンチマーク（benchmark）は「同じ条件でタイムを測る陸上競技会」です。100m 走のタイムを比べるなら、同じトラック・同じ風速・同じ計時方法でないと意味がありません。しかもプログラムの世界には「ゴールまで走ったふりをしてスタート地点で止まっている選手（＝最適化で消えたコード）」までいます。

要点：
- ベンチマークは「2 つの書き方のどちらが速いか」「変更で遅くならなかったか」を答える道具
- 小さいもの（関数）を測るほど、コンパイラ最適化の罠にはまりやすい
- 結果は 1 つの数字ではなく、ばらつき付きで読む

## 2. マイクロベンチマークとマクロベンチマーク

| | マイクロベンチマーク | マクロベンチマーク |
|---|---|---|
| 対象 | 関数・数行のコード | API 1 本、ユースケース全体、アプリ全体 |
| 例 | `JSON.stringify` vs 自前シリアライザ | 「商品一覧 API を 1 リクエスト処理する時間」 |
| 実行時間 | ナノ秒〜マイクロ秒 | ミリ秒〜秒 |
| 長所 | 速く回せる・差がはっきり出る | 本番に近い結論が出る |
| 短所 | 本番の効果と一致しないことが多い | 遅い・ばらつく・原因が分かりにくい |

**マイクロベンチマークで 10 倍速くなっても、その関数が全体の 1% しか時間を使っていなければ、全体は 1% 弱しか速くなりません**（アムダールの法則。[[04_最適化の進め方とトレードオフ]]）。だから順番は「プロファイリングでホットな箇所を見つける → そこだけマイクロベンチで改善案を比較する → マクロ（負荷テスト）で全体効果を確認する」です。

```
プロファイル                マイクロベンチ               マクロ / 負荷テスト
「serializeが全体の40%」 →  「案Bが案Aの3倍速い」  →   「API p95 が 120→80ms」
（どこを直すか）            （どう直すか）              （本当に効いたか）
                                                         ※数値は説明用の例
```

## 3. Node.js でのベンチマーク

### 3-1. tinybench

tinybench は軽量なベンチマークライブラリで、Vitest の `bench` 機能の内部でも使われています。

```bash
npm i -D tinybench
```

```ts
// bench/serialize.bench.ts
import { Bench } from "tinybench";

type Product = { id: number; name: string; price: number; tags: string[] };
const products: Product[] = Array.from({ length: 500 }, (_, i) => ({
  id: i,
  name: `product-${i}`,
  price: i * 100,
  tags: ["sale", "new"],
}));

// 案A：素直に JSON.stringify
function serializeA(list: Product[]) {
  return JSON.stringify(list);
}

// 案B：必要なフィールドだけに絞ってから stringify
function serializeB(list: Product[]) {
  return JSON.stringify(list.map((p) => ({ id: p.id, name: p.name, price: p.price })));
}

const bench = new Bench({ name: "products serialize", time: 1000 });

let sink = 0; // 結果を「使う」ための変数（デッドコード除去対策）
bench
  .add("A: JSON.stringify all fields", () => {
    sink += serializeA(products).length;
  })
  .add("B: pick fields then stringify", () => {
    sink += serializeB(products).length;
  });

await bench.run(); // 既定でウォームアップ後に計測される
console.table(bench.table());
if (sink === 42) console.log(sink); // sink を最後に参照しておく
```

`bench.table()` には、タスクごとの 1 秒あたり実行回数（throughput）、1 回あたりの時間（latency）、そして誤差の目安（`±x%` で表示される相対誤差 rme）が出ます。**誤差が大きい（例えば ±10% 超）ときは、結果を信用する前にノイズ源を減らします。**

> [!info] 2026 年時点のメモ
> tinybench は v2 → v3 以降で API が変わっています（結果が `task.result.latency` / `task.result.throughput` に整理された等）。古いブログの `task.result.hz` などのコードはそのまま動かないことがあるので、README で確認してください。

### 3-2. mitata

mitata は出力が見やすく、JIT の罠を検出する仕組みを持つベンチマークライブラリです。

```ts
// bench/serialize.mitata.ts
import { bench, run, summary, do_not_optimize } from "mitata";

const products = Array.from({ length: 500 }, (_, i) => ({
  id: i, name: `product-${i}`, price: i * 100, tags: ["sale", "new"],
}));

summary(() => {
  bench("A: all fields", () =>
    do_not_optimize(JSON.stringify(products)));
  bench("B: pick fields", () =>
    do_not_optimize(JSON.stringify(products.map(({ id, name, price }) => ({ id, name, price })))));
});

await run();
```

`do_not_optimize()` は「この値は使われている」と JIT に思わせ、計算そのものが消されるのを防ぎます。`summary()` で囲むと「B は A の何倍速いか」が出ます。mitata は結果が消されていそうなベンチに `!` マークを付けて警告してくれます。

## 4. Python でのベンチマーク

### 4-1. timeit（標準ライブラリ）

```bash
# コマンドラインから：自動で繰り返し回数を決め、複数ラウンドの最良値を出す
python -m timeit -s "import json; d=[{'id':i,'name':f'p{i}'} for i in range(500)]" "json.dumps(d)"
```

```python
import json
import timeit

data = [{"id": i, "name": f"p{i}", "price": i * 100} for i in range(500)]

# repeat=5 ラウンド × number=1000 回。ラウンドごとの合計時間のリストが返る
times = timeit.repeat(lambda: json.dumps(data), repeat=5, number=1000)
per_call_us = [t / 1000 * 1e6 for t in times]
print(f"min={min(per_call_us):.1f}µs  all={[round(x, 1) for x in per_call_us]}")
```

Python の公式ドキュメントは、ばらつきの大部分は他プロセスの干渉によるものなので **`repeat` の最小値**を見るのが妥当だと説明しています（平均や最大は参考程度）。

### 4-2. pytest-benchmark

テストと同じ感覚でベンチマークを書き、保存・比較できるプラグインです。

```python
# test_serialize_bench.py
import json

DATA = [{"id": i, "name": f"p{i}", "price": i * 100} for i in range(500)]

def test_json_dumps(benchmark):
    result = benchmark(json.dumps, DATA)  # 関数と引数を渡すと自動で繰り返し計測
    assert result.startswith("[")         # 結果を検証 → 消されない＆正しさも確認
```

```bash
pytest test_serialize_bench.py --benchmark-autosave        # 結果を .benchmarks/ に保存
pytest test_serialize_bench.py --benchmark-compare         # 前回保存分と比較
pytest test_serialize_bench.py --benchmark-compare-fail=median:10%  # 中央値が10%悪化で失敗
```

## 5. ベンチマークの罠

マイクロベンチマークで「ありえないほど速い」結果が出たら、まず罠を疑います。

### 罠1：デッドコード除去（Dead code elimination）

結果を誰も使わない計算は、JIT コンパイラが「やらなくても同じ」と判断して消すことがあります。

```ts
// ❌ 悪い例：結果を捨てている → 最適化で処理ごと消える可能性
bench.add("sqrt", () => { Math.sqrt(12345); });

// ✅ 良い例：結果を外部に蓄積する / do_not_optimize で包む
let sink = 0;
bench.add("sqrt", () => { sink += Math.sqrt(12345); });
```

### 罠2：定数畳み込み（Constant folding）

入力が毎回同じ定数だと、コンパイル時に結果が計算済みにされることがあります（上の `Math.sqrt(12345)` もその候補です）。入力は外から渡す・配列から順に取るなどして、コンパイラに中身を予測させないようにします。

```ts
const inputs = Array.from({ length: 1024 }, () => Math.random() * 1e6);
let i = 0;
bench.add("sqrt", () => { sink += Math.sqrt(inputs[i++ & 1023]); });
```

### 罠3：入力が現実的でない

- 500 件で速い実装が 5 万件で遅い（計算量の違い）
- 全部同じ形のオブジェクトだと V8 のインラインキャッシュが効いて速いが、本番の不揃いなデータでは遅い（[[02_JITとコンパイラ最適化]]）
- 毎回同じデータを使うので CPU キャッシュに乗りっぱなし

**本番に近いサイズ・形・ばらつきの入力**を用意します。

### 罠4：測っているものが違う

ベンチ関数の中で毎回データを生成すると、「生成 + 処理」を測っていることになります。準備処理はベンチの外（またはセットアップフック）に出します。

### 罠5：GC とメモリ

割り当ての多いコードは、GC がいつ走るかで結果が揺れます。短時間のベンチでは GC が走らず速く見え、本番では GC 停止が効いてくる、ということもあります（[[03_メモリアロケーションとGC]]）。十分長く回し、必要ならメモリ使用量も測ります。

## 6. どう比較するか：公平な比較と結果の読み方

### 公平に比較するためのルール

1. **同じマシン・同じ時間帯で、交互に測る**：A を全部→B を全部ではなく、A→B→A→B と交互に回すと、途中で起きた環境変化（他プロセス・温度）が片方だけに乗るのを防げます。
2. **環境を静かにする**：ブラウザ・IDE・Docker の不要なコンテナを閉じ、ノート PC は電源に接続します。
3. **ランタイムのバージョンを固定・記録する**：Node.js のメジャーバージョンが変わると V8 の最適化が変わり、結果が逆転することもあります。
4. **ばらつきと一緒に比べる**：「B は A より 1.8 倍速い（±3%）」のように誤差込みで報告します。
5. **正しさも確認する**：速い実装が間違った結果を返していないか、出力を比較するテストを必ず書きます。

### 結果の読み方（例）

以下は tinybench の出力イメージです（**数値は説明用の例**）。

```
┌─────────┬──────────────────────────────┬──────────────────┬──────────────────┬─────────┐
│ (index) │ Task name                    │ Latency avg (ns) │ Throughput avg   │ Samples │
├─────────┼──────────────────────────────┼──────────────────┼──────────────────┼─────────┤
│ 0       │ A: JSON.stringify all fields │ 61200 ± 0.85%    │ 16340 ± 0.80%    │ 16340   │
│ 1       │ B: pick fields then stringify│ 48900 ± 1.10%    │ 20450 ± 1.05%    │ 20450   │
└─────────┴──────────────────────────────┴──────────────────┴──────────────────┴─────────┘
```

読み方：
- B のほうが 1 回あたり約 20% 速い。誤差は ±1% 前後なので、差は誤差より十分大きい
- ただし 1 回 61µs → 49µs で、差は 12µs。API のレスポンスが 100ms なら全体への影響は 0.01% 程度 → **この改善に価値があるかは、プロファイルでこの関数がどれだけ時間を占めるか次第**
- B はレスポンスからフィールドを削っているので、仕様変更でもある（クライアントが `tags` を使っていないか確認が必要）

## 7. CI での継続ベンチマーク

一度速くしても、後の変更でこっそり遅くなる（性能リグレッション）ことはよくあります。CI でベンチマークを回し、前回より大きく悪化したら知らせる仕組みを作ります。

### github-action-benchmark

`benchmark-action/github-action-benchmark` は、ベンチマーク結果を gh-pages ブランチに蓄積してグラフ化し、悪化時にコメントや失敗で知らせる GitHub Action です（2026 年時点で `@v1`）。対応ツールは Go・Rust（cargo）・pytest-benchmark・benchmark.js 形式などで、それ以外は `customSmallerIsBetter`（小さいほど良い）/ `customBiggerIsBetter` 形式の JSON を自分で出力して渡せます。

```yaml
# .github/workflows/bench.yml
name: benchmark
on:
  push:
    branches: [main]
permissions:
  contents: write        # gh-pages への push
jobs:
  bench:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22 }
      - run: npm ci
      # ベンチを実行し customSmallerIsBetter 形式で出力する自作スクリプト
      # 出力例: [{"name":"serialize 500 products","unit":"us","value":48.9}]
      - run: node bench/run-and-export.mjs > bench-result.json
      - uses: benchmark-action/github-action-benchmark@v1
        with:
          tool: customSmallerIsBetter
          output-file-path: bench-result.json
          github-token: ${{ secrets.GITHUB_TOKEN }}
          auto-push: true
          alert-threshold: "150%"   # 前回の1.5倍より悪化したら警告（既定は200%）
          comment-on-alert: true
          fail-on-alert: false
```

### CI ベンチの注意点

- **GitHub ホストランナーはうるさい**：共有の仮想マシンなので、同じコードでも 10〜20% 程度揺れることは珍しくありません。閾値は緩め（150〜200%）にし、「大きな悪化を捕まえる」用途と割り切ります。
- 精度が必要なら、専用のセルフホストランナーを使う、または命令数などの「時間以外の指標」で比較するサービス（CodSpeed など。CPU シミュレーションで命令数ベースの計測を行う）を検討します。
- ベンチは重要なホットパスに絞ります。全関数をベンチすると CI が遅くなり、ノイズの警告が増えて誰も見なくなります。
- マクロな性能（API 全体）は、ベンチマークではなく負荷テストや Lighthouse CI（[[06_パフォーマンス（Lighthouse CI）]]）で守ります。

## よくある誤解・つまずき

- ❌ マイクロベンチで 3 倍速くなったからアプリも速くなる  
  ✅ その関数が全体時間に占める割合次第です。プロファイルで割合を確認し、最後はマクロ計測で確かめます。
- ❌ ベンチ結果が 0.1ns だった、すごく速い  
  ✅ デッドコード除去や定数畳み込みで処理が消えている可能性が高いです。結果を使う・入力を変えるなどの対策をします。
- ❌ 1 回の実行結果で A と B の勝敗を決める  
  ✅ 誤差（rme・ばらつき）と比べて差が十分大きいかを見ます。交互に複数回測ります。
- ❌ 自分の PC で速かったから本番でも同じ比率で速い  
  ✅ CPU・ランタイムのバージョン・データの形で結果は変わります。条件を記録し、本番に近い環境で再確認します。
- ❌ CI のベンチで 5% 悪化 → 必ずリグレッション  
  ✅ 共有ランナーのノイズの範囲内であることが多いです。閾値と再実行で判断します。

## まとめ

- マイクロベンチは「どう直すか」、マクロ計測は「本当に効いたか」を答える。順番はプロファイル → マイクロ → マクロ
- Node.js は tinybench / mitata、Python は timeit / pytest-benchmark が手軽
- デッドコード除去・定数畳み込み・非現実的な入力・GC の影響に注意する
- 比較は同じマシンで交互に、誤差と一緒に。速さだけでなく正しさも確認する
- CI では github-action-benchmark などで大きな悪化を検知する。共有ランナーのノイズを前提に閾値を決める

## 確認クイズ

1. 次のベンチマークの問題点は何ですか？ `bench.add("parse", () => { JSON.parse('{"a":1}'); })`
> [!tip]- 答え
> 結果を使っていないのでデッドコード除去の対象になりうること、入力が毎回同じ定数リテラルで現実的でないこと（小さすぎる・キャッシュに乗りっぱなし）です。結果を `sink` に蓄積するか `do_not_optimize` で包み、本番に近いサイズ・多様な入力を用意します。

2. 関数 X をマイクロベンチで 2 倍速くしました。プロファイルでは X は API 処理時間の 10% を占めていました。API 全体は理論上どれくらい速くなりますか？
> [!tip]- 答え
> 10% の部分が半分（5%）になるので、全体は 100 → 95、約 5% の短縮です（アムダールの法則）。全体を大きく速くしたいなら、占める割合の大きい部分を狙います。

3. CI のベンチマークで alert-threshold を 105% にしたところ、ほぼ毎回アラートが出るようになりました。何が起きていて、どうすべきですか？
> [!tip]- 答え
> 共有ランナーのノイズ（数〜十数 % の揺れ）が閾値より大きいため、変更がなくてもアラートが出ています。閾値を 150〜200% 程度に緩める、専用ランナーや命令数ベースの計測を使う、悪化時に再実行して確認するなどの対策をとります。
