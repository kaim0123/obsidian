# フレームグラフの読み方

## 1. ひとことで言うと

フレームグラフ（flame graph）は「会社の部署別の残業時間グラフ」のようなものです。一番下に会社全体、その上に部署、さらに上にチーム、個人……と積み上げ、**横幅をそれぞれが使った時間に比例させる**と、どの部署のどのチームの誰が時間を使っているかが一目で分かります。

プロファイラが集めた何千〜何万個のスタックを、このように積み上げて 1 枚の図にしたのがフレームグラフです。Brendan Gregg が考案しました。

要点：
- **横幅 = その関数がサンプルに現れた割合（≒使った時間の割合）**
- **縦 = 呼び出しの深さ（下が呼び出し元、上が呼び出し先）**
- **x 軸の左右の位置には意味がない（時系列ではない）**

## 2. フレームグラフの構造

```
                    ┌────────┐
                    │ escape │                              ← 一番上：実際に CPU で実行中だった関数
         ┌──────────┴────────┴──┐ ┌──────────┐
         │   JSON.stringify     │ │  sortBy  │
  ┌──────┴──────────────────────┴─┴──────────┴──┐ ┌──────┐
  │            listProductsHandler              │ │ auth │
┌─┴─────────────────────────────────────────────┴─┴──────┴──┐
│                    express router                         │
├───────────────────────────────────────────────────────────┤
│                       (root)                              │  ← 一番下：全サンプル（100%）
└───────────────────────────────────────────────────────────┘
 ←──────────────── 横幅 = サンプル数の割合（時間ではなく「量」）──────────→
（説明用の例）
```

1 つひとつの箱（フレーム）は「スタックフレーム＝ある関数の呼び出し」です。

| 要素 | 意味 |
|---|---|
| 横幅 | その関数（とその上に乗っている子関数）がサンプルに含まれていた割合。広いほど時間を使っている |
| 縦の積み重ね | 呼び出し関係。ある箱の上に乗っている箱は、その関数から呼ばれた関数 |
| 一番上の縁（てっぺん） | サンプル取得の瞬間に実際に CPU で実行していた関数 |
| 左右の並び | **意味なし**。同じスタックをまとめるため、関数名のアルファベット順に並べているだけ |
| 色 | 元祖フレームグラフでは「炎っぽく見せるため」の暖色でランダム。ツールによっては言語・種類（JS / ネイティブ / GC）で色分けする |

### 2 つの「時間」：Self と Total

- **Total（全体）**：その箱の横幅。子関数の時間も含む。「この処理の下で何 % 使っているか」
- **Self（自己）**：その箱のうち、上に何も乗っていない部分の幅。「その関数自身のコードで何 % 使っているか」

```
┌─────────┐┌───┐
│ A (20%) ││B  │          listProducts の Total = 100%（下の箱全体の幅）
├─────────┴┴───┴───────┐   listProducts の Self  = 上に何も乗っていない部分 = 65%
│ listProducts (100%)  │   → listProducts 自身のコード（ループなど）が重い
└──────────────────────┘
```

**「てっぺんが平らで広い箱」が最大の狙い目**です。その関数自身が CPU を使っているので、そこを直せば時間が減ります。

## 3. 仲間の図：アイシクル・フレームチャート・差分・オフ CPU

### アイシクルグラフ（Icicle graph）

フレームグラフを上下逆さにしたもので、root が上、呼び出し先が下に垂れ下がります（つらら＝icicle）。Chrome DevTools や speedscope の一部ビュー、Pyroscope など多くのツールがこちらを採用しています。**読み方はまったく同じ**で、向きが逆なだけです。

### フレームチャート（Flame chart）

**x 軸が時間**のグラフです。Chrome DevTools の Performance パネルや speedscope の「Time Order」ビューがこれです。「最初の 100ms は起動処理、その後 GC が 3 回……」のように時系列のパターンが分かります。見た目はフレームグラフにそっくりなので混同しやすく、ツールによってはフレームチャートを「フレームグラフ」と呼んでいることもあります。

| | フレームグラフ | フレームチャート |
|---|---|---|
| x 軸 | 割合（同じスタックを合算、アルファベット順） | 時間の経過 |
| 分かること | 全体で何に時間を使っているか | いつ何が起きたか、長いタスクの発生タイミング |
| speedscope のビュー | Left Heavy（重い順に左寄せ） | Time Order |

### 差分フレームグラフ（Differential flame graph）

2 つのプロファイル（例：デプロイ前と後）を比べ、**増えた部分を赤、減った部分を青**などで色分けしたものです。「新しいリリースで p95 が悪化した」とき、どの関数の時間が増えたかがすぐ分かります。Brendan Gregg の `difffolded.pl`、Pyroscope の比較ビュー（diff view）などで作れます。

注意点として、2 つのプロファイルの総サンプル数が違うと単純比較できません。正規化（割合で比較）するか、同じ負荷・同じ時間で取ります。

### オフ CPU フレームグラフ（Off-CPU flame graph）

通常のフレームグラフは「CPU 上で実行中」のスタックだけを示します。オフ CPU フレームグラフは、**スレッドがブロックされて待っていたときのスタックと、待っていた時間**を示します。ロック待ち・ディスク I/O・ネットワーク待ちがどこで発生しているかが分かります。

Linux では eBPF ツール（bcc の `offcputime` など）で取得しますが、Node.js のように 1 スレッドが非同期 I/O を待つモデルでは、待ちの多くがイベントループの「何もしていない時間」として現れるため、**アプリの待ち時間の調査には分散トレースのほうが実用的**なことが多いです（[[05_プロファイリング]]）。

## 4. どう測るか：Node.js でフレームグラフを作る

### 方法 A：`--cpu-prof` → speedscope（おすすめ）

```bash
# 1. 本番ビルドでプロファイルを有効にして起動
NODE_ENV=production node --cpu-prof --cpu-prof-dir=./profiles dist/server.js

# 2. 別ターミナルで負荷をかける（30 秒）
npx autocannon -c 50 -d 30 "http://localhost:3000/products?limit=100"

# 3. サーバーを Ctrl+C で止める → profiles/CPU.*.cpuprofile ができる
ls profiles/
```

4. https://www.speedscope.app/ を開き、`.cpuprofile` をドラッグ＆ドロップ（ファイルはブラウザ内で処理され、アップロードされません）。オフラインで使いたい場合は `npx speedscope profiles/CPU.xxx.cpuprofile` でも開けます。
5. 画面上部のビューを切り替えて読みます。
   - **Left Heavy**：同じスタックを合算し重い順に左寄せ。フレームグラフ（アイシクル型）として読む。まずここ
   - **Sandwich**：関数の一覧を Self / Total で並べ替え。関数を選ぶと呼び出し元（上）と呼び出し先（下）が表示される
   - **Time Order**：フレームチャート。時系列で見る

### 方法 B：0x

```bash
npx 0x -P 'autocannon -c 50 -d 20 "localhost:$PORT/products?limit=100"' dist/server.js
# 終了後、生成されたフォルダの flamegraph.html をブラウザで開く
```

0x は古典的な「下から積み上げる」フレームグラフを HTML で出力します。ボタンで Node.js 内部・V8・ネイティブのフレームの表示／非表示を切り替えられます。

### 方法 C：Chrome DevTools

`node --inspect` で起動して `chrome://inspect` から接続し、Performance パネルで記録します。表示はフレームチャート（時系列）が基本で、下部の **Bottom-Up**（Self 時間順）・**Call Tree**（Total 時間順）タブが集計ビューです。

## 5. 例：Shop の商品一覧 API で JSON シリアライズがホット

以下は読み解き方を説明するための**架空の例**です（数値・関数名も説明用）。

**状況**：商品一覧 API（`GET /products?limit=100`）の p99 が 2 秒。トレースを見ると DB スパンは 40ms で、アプリ内の処理が長い。CPU プロファイルを取り、speedscope の Left Heavy で見た。

```
(説明用の例：アイシクル型、上が root)
┌──────────────────────────────────────────────────────────────────────────┐
│ (root) 100%                                                              │
├──────────────────────────────────────────────────────────┬─────┬─────────┤
│ processTicksAndRejections 72%                            │(gc) │(idle)   │
├──────────────────────────────────────────────────────────┤ 14% │ 12%     │
│ listProductsHandler 70%                                  │     │         │
├─────────────────────────────────────────────┬────────────┤     │         │
│ res.json → JSON.stringify 52%               │ toDTO 15%  │     │         │
├────────────────────────┬────────────────────┼────────────┤     │         │
│ Product.toJSON 30%     │ (stringify本体) 22% │ map 15%    │     │         │
├────────────────────────┤                    └────────────┘     │         │
│ Review.toJSON 27%      │                                       │         │
├────────────────────────┤                                       │         │
│ formatDate 18%         │                                       │         │
└────────────────────────┘                                       │         │
```

**読み解きの手順**：

1. **全体を確認**：`(idle)` は 12% で、負荷が十分かかっている。`(gc)` が 14% と多め → 大量のオブジェクトを作っている疑い。
2. **一番広い塔を探す**：`listProductsHandler` が 70%。その中で `JSON.stringify` が 52% と大半。
3. **上に辿る**：`JSON.stringify` の上に `Product.toJSON` → `Review.toJSON` → `formatDate`。つまり、各商品の `toJSON` の中でレビューまでシリアライズし、レビューごとに日付を整形している。
4. **てっぺんの平らな部分（Self）**：`formatDate` が 18% と広い。Sandwich ビューで確認すると、`formatDate` は 1 リクエストで数万回呼ばれていた（100 商品 × 各 200 件のレビュー）。
5. **仮説**：「一覧 API なのに全レビューまでシリアライズしているのが原因。一覧ではレビュー件数と平均評価だけ返せばよい。日付整形も `Intl.DateTimeFormat` を毎回生成しているなら使い回せる。」
6. **改善と再計測**：一覧の DTO からレビュー本体を外し、日付フォーマッタを 1 つだけ生成して使い回す → ベンチマーク（[[02_ベンチマークの書き方]]）で改善案を比較 → 同じ負荷で再プロファイルし、差分を確認。

```ts
// Before（例）：毎回フォーマッタを生成し、一覧でも全レビューを返す
function formatDate(d: Date) {
  return new Intl.DateTimeFormat("ja-JP", { dateStyle: "medium" }).format(d);
}

// After（例）：フォーマッタは 1 回だけ生成。一覧用 DTO はレビューを要約のみ
const dateFmt = new Intl.DateTimeFormat("ja-JP", { dateStyle: "medium" });
const formatDateFast = (d: Date) => dateFmt.format(d);

type ProductListItem = { id: number; name: string; price: number; reviewCount: number; rating: number };
```

改善後のフレームグラフでは `JSON.stringify` の塔が細くなり、`(gc)` の割合も下がるはずです。**「速くなったはず」ではなく、フレームグラフとレイテンシで確認する**のが計測サイクルの最後のステップです。

## 6. よくある読み間違い

```
❌ 左にあるから先に実行された      → x 軸は時系列ではない（並びはアルファベット順や重い順）
❌ 背が高い塔ほど遅い              → 高さは呼び出しの深さ。遅さは「横幅」
❌ 下の広い箱（main, handler）が犯人 → 下の箱は子の時間を含むだけ。Self（てっぺん）を見る
❌ 色が赤いところが危ない          → 元祖フレームグラフの色はランダムな暖色。差分グラフ以外は意味なし
```

- **ライブラリの関数を犯人にしてしまう**：`JSON.stringify` や正規表現エンジンが広くても、「それをそんなに呼んでいる自分のコード」が本当の原因であることが多いです。必ず下（呼び出し元）に辿ります。
- **同じ関数が複数の塔に分かれている**：別々の経路から呼ばれた関数は別の塔になり、1 つひとつは細く見えます。Sandwich ビューや Bottom-Up で関数単位に合算して確認します。
- **匿名関数だらけで読めない**：`(anonymous)` が多い場合は、コールバックに名前を付ける（`function handleList() {}`）と読みやすくなります。ソースマップが効いていないと TypeScript の元の位置が分からないので、ビルド設定も確認します。
- **最適化されたコードとインライン化**：JIT がインライン化した小さな関数は、呼び出し元の箱に吸収されて表示されないことがあります（[[02_JITとコンパイラ最適化]]）。
- **サンプル数が少ない**：数百サンプル程度では細い箱の割合は誤差だらけです。十分な時間・負荷で取ります。

## よくある誤解・つまずき

- ❌ フレームグラフは時間の流れを表している  
  ✅ x 軸は割合で、並びはアルファベット順（または重い順）です。時系列はフレームチャートで見ます。
- ❌ 一番下の広い関数を最適化すればいい  
  ✅ 下の箱は子の時間を含むだけです。てっぺんが平らで広い（Self が大きい）関数が狙い目です。
- ❌ フレームグラフに出てこない処理は速い  
  ✅ CPU フレームグラフには待ち時間が出ません。DB・外部 API の待ちはトレースやオフ CPU 分析で見ます。
- ❌ 差分フレームグラフで赤い箇所が増えた＝その関数が遅くなった  
  ✅ 呼ばれる回数が増えただけかもしれません。負荷やサンプル数が揃っているかも確認します。

## まとめ

- 横幅＝サンプルに現れた割合、縦＝スタックの深さ、左右の位置と（元祖の）色には意味がない
- Total（箱の幅）と Self（てっぺんの平らな部分）を区別し、Self が大きい関数から狙う
- アイシクルは上下逆、フレームチャートは x 軸が時間、差分は前後比較、オフ CPU は待ち時間
- Node.js は `--cpu-prof` → speedscope（Left Heavy / Sandwich / Time Order）が手軽。0x や DevTools も使える
- ライブラリ関数が広くても、それを呼んでいる自分のコードまで下に辿って原因を探す
- 改善後は同じ条件で再プロファイルし、フレームグラフとレイテンシの両方で効果を確認する

## 確認クイズ

1. フレームグラフで、関数 A の箱が左端に、関数 B の箱が右端にありました。「A は B より先に実行された」と言えますか？
> [!tip]- 答え
> 言えません。フレームグラフの x 軸は時系列ではなく、同じスタックをまとめるために関数名順（ツールによっては重い順）に並べているだけです。実行順序を知りたいときはフレームチャート（speedscope の Time Order、DevTools の Performance パネル）を使います。

2. `handleRequest` の箱は幅 80% ですが、その上に `validate`（10%）、`render`（65%）が乗っています。`handleRequest` 自身の Self はおよそ何 % で、どこを優先して調べますか？
> [!tip]- 答え
> Self は 80 − 10 − 65 = 約 5% です。`handleRequest` 自身は重くなく、`render`（65%）の中身を上に辿り、てっぺんが平らで広い関数を探します。

3. デプロイ後に p95 が悪化したので、デプロイ前後のプロファイルから差分フレームグラフを作りたいと思います。正しく比較するために揃えるべき条件は何ですか？
> [!tip]- 答え
> 同じ負荷（RPS・エンドポイント比率）、同じ計測時間・サンプリング間隔、同じ環境（マシン・データ量・ウォームアップ状態）です。総サンプル数が違う場合は割合で正規化して比較します。継続的プロファイリングを使っていれば、同じ時間帯・同じトラフィック量の区間同士を比較できます。
