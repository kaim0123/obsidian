# キャッシュで応答を速くする

[[MOC_パフォーマンス体系|📚 目次]] ｜ [[03_N+1問題の発見と解決|← 前へ]] ｜ [[05_非同期化とキューで待ち時間を隠す|次へ →]]

> [!abstract] この記事で分かること
> - キャッシュを置ける場所（ブラウザ・CDN・Nginx・アプリ内メモリ・Redis・DB）と、それぞれの速さ
> - ヒット率から平均レイテンシを計算し、キャッシュの効果を事前に見積もる方法
> - Redis を使った cache-aside の実装と、TTL・無効化・スタンピード対策
> - キャッシュが効かない／逆効果になるケースと、メモ化
>
> **前提**：[[01_APIレスポンスタイムの分解]] と [[02_DBクエリのチューニング実践]] を読んでいると理解しやすいです。キャッシュ戦略の設計（Write-through など）は [[68_分散システム/50_分散キャッシュ/キャッシュ戦略|キャッシュ戦略]] が本拠地です。

## 1. ひとことで言うと

キャッシュは、**よく使う文房具を引き出しではなく机の上に置いておく**ことです。毎回引き出し（DB）を開けるより、机の上（メモリ）から取る方が速い。ただし机は狭く（容量）、置いたものが古くなる（一貫性）問題があります。

- キャッシュは「**遅い処理の結果を、速い場所に一時的に置いて使い回す**」技術
- 効果は**ヒット率**でほぼ決まる。ヒットしないキャッシュは、むしろ遅くする
- 速さと引き換えに「**古いデータを返すかもしれない**」というトレードオフを受け入れる

> [!warning] キャッシュは最後の手段に近い
> 遅いクエリをインデックスで直せるなら、まずそちらです（[[02_DBクエリのチューニング実践]]）。キャッシュは原因を隠すだけで、無効化という新しい複雑さを持ち込みます。「直しても遅い」「そもそも計算が重い」「同じ結果を何度も返す」ときに使います。

## 2. どこでキャッシュするか

ユーザーに近いほど速く、サーバーの負荷も減りますが、**制御（無効化）しにくく**なります。

```
ユーザーに近い ◀─────────────────────────────────────────▶ データに近い
速い・負荷削減大・無効化しにくい            遅い・負荷削減小・無効化しやすい

ブラウザ    CDN        Nginx        アプリ内メモリ   Redis          DB
(HTTP      (エッジ)    (proxy_     (Map / LRU)     (共有キャッシュ) (バッファ
 キャッシュ)            cache)                                       プール)
 0ms       〜数十ms    〜1ms        〜0.01ms         〜1ms           クエリ次第
```

| 場所 | 向いているもの | 注意点 | 詳しく |
|---|---|---|---|
| ブラウザ | 画像・JS・CSS、変化の少ない API | 一度配ると消せない。`Cache-Control` で制御 | [[06_HTTPキャッシュと圧縮]] |
| CDN | 全ユーザー共通の静的ファイル・公開ページ | ユーザー別データを混ぜない | [[04_CDNによる負荷軽減]] |
| Nginx | 公開 API のレスポンス | 認証付きレスポンスの扱い | [[06_HTTPキャッシュと圧縮]] |
| アプリ内メモリ | 設定・カテゴリ一覧など小さく変化の少ないもの | API 4 台で**中身がバラバラ**になる。プロセス再起動で消える | 本ノート 6 節 |
| Redis | 複数台で共有したい計算結果・セッション | ネットワーク往復（〜1ms）が乗る | 本ノート 4 節 |
| DB | （自動）バッファプール | 意図して制御するものではない | [[05_実行計画の読み方]] |

Shop では、商品画像は CDN、商品一覧の公開ページは CDN / Nginx で短時間、ユーザーごとの「おすすめ」は Redis、カテゴリツリーはアプリ内メモリ、のように**データの性質で置き場所を変えます**。

## 3. 性能から見たキャッシュ：ヒット率と平均レイテンシ

**ヒット率（Hit Ratio）**：キャッシュを見に行ったうち、データがあった割合。

```
平均レイテンシ ＝ ヒット率 × ヒット時の時間 ＋ (1 − ヒット率) × ミス時の時間
ミス時の時間  ＝ キャッシュを見る時間 ＋ 元データを取る時間 ＋ キャッシュに書く時間
```

**計算例**（数値は説明用の例）：Redis の読み書き 1ms、DB の重い集計 80ms。

| ヒット率 | 平均レイテンシ | 計算 |
|---|---|---|
| 0%（キャッシュなし） | 80ms | — |
| 0%（キャッシュあり・全部ミス） | 82ms | 1 + 80 + 1 → **むしろ遅い** |
| 50% | 41.5ms | 0.5 × 1 + 0.5 × 82 |
| 90% | 9.1ms | 0.9 × 1 + 0.1 × 82 |
| 99% | 1.81ms | 0.99 × 1 + 0.01 × 82 |

```
平均レイテンシ（ms）
ヒット率  0% ████████████████████████████████████████ 82
        50% █████████████████████ 41.5
        90% █████ 9.1
        99% █ 1.8
```

ここから分かること：

- **ヒット率 90% と 99% では平均が約 5 倍違う**。ヒット率の数ポイントの改善が大きく効く
- 平均は大きく下がっても、**ミスしたリクエストは 82ms のまま**。p99 はミスの時間で決まることが多い（ヒット率 99% 未満なら p99 はミス側に入る）
- DB の負荷は「ミスの割合」に比例して減る。ヒット率 90% なら DB へのクエリは 1/10

> [!tip] ヒット率は必ずメトリクスにする
> Redis 全体なら `INFO stats` の `keyspace_hits` / `keyspace_misses` で分かりますが、**キーの種類ごと**のヒット率はアプリ側でカウントします（次節のコード）。キャッシュを入れたのに速くならないときは、まずヒット率を見ます。

## 4. cache-aside の実装例（Redis）

**cache-aside（キャッシュアサイド）**：アプリが「まずキャッシュを見て、なければ DB から取ってキャッシュに入れる」パターン。最もよく使われます。他のパターンとの比較は [[68_分散システム/50_分散キャッシュ/キャッシュ戦略|キャッシュ戦略]] を参照してください。

```ts
import { createClient } from "redis"; // node-redis v4 以降（2026 年時点）

const redis = createClient({ url: process.env.REDIS_URL });
await redis.connect();

const hits = new Map<string, { hit: number; miss: number }>();
function count(kind: string, hit: boolean) {
  const c = hits.get(kind) ?? { hit: 0, miss: 0 };
  hit ? c.hit++ : c.miss++;
  hits.set(kind, c); // 実際は Prometheus のカウンタなどに送る
}

async function cached<T>(
  kind: string,
  key: string,
  ttlSec: number,
  load: () => Promise<T>,
): Promise<T> {
  try {
    const raw = await redis.get(key);
    if (raw !== null) {
      count(kind, true);
      return JSON.parse(raw) as T;
    }
  } catch (e) {
    // Redis 障害時は DB にフォールバック（キャッシュは「なくても動く」ように）
    logger.warn({ err: e, key }, "cache get failed");
  }
  count(kind, false);
  const value = await load();
  // TTL にばらつき（ジッター）を加え、一斉に期限切れになるのを防ぐ
  const ttl = Math.round(ttlSec * (0.9 + Math.random() * 0.2));
  redis.set(key, JSON.stringify(value), { EX: ttl }).catch(() => {});
  return value;
}

// 使い方：カテゴリ別の人気商品ランキング（重い集計）を 5 分キャッシュ
app.get("/api/categories/:id/ranking", async (req, res) => {
  const id = Number(req.params.id);
  const ranking = await cached("ranking", `ranking:v1:cat:${id}`, 300, () =>
    db.query(
      `SELECT p.id, p.name, sum(oi.quantity) AS sold
         FROM order_items oi JOIN products p ON p.id = oi.product_id
        WHERE p.category_id = $1 AND oi.created_at > now() - interval '7 days'
        GROUP BY p.id, p.name ORDER BY sold DESC LIMIT 20`,
      [id],
    ).then((r) => r.rows),
  );
  res.json(ranking);
});
```

実装上のポイント：

- **キーにバージョン**（`v1`）を入れる。返す形を変えたら `v2` にすれば古い形式を読まずに済む
- **TTL（Time To Live：有効期限）を必ず付ける**。無効化を漏らしても、最悪 TTL で直る
- **キャッシュ障害で API を落とさない**。Redis のタイムアウトは短く（数十〜100ms 程度）設定する

## 5. 何をキャッシュし、どう無効化するか

### 5.1 キャッシュ向きのデータ

3 つの条件がそろうほど効果が大きくなります。

| 条件 | Shop での例 | 例外 |
|---|---|---|
| **読み多**（同じものが何度も読まれる） | 商品詳細、カテゴリ一覧、ランキング | 検索結果（条件の組み合わせが多くヒットしにくい） |
| **変化少**（多少古くても困らない） | ランキング（5 分古くても OK） | 在庫数・価格（古いと注文トラブル） |
| **計算重**（元データを作るのが遅い） | 集計、外部 API の結果、レコメンド | 主キー検索（DB で 1ms なら Redis と大差ない） |

### 5.2 無効化と一貫性

> "There are only two hard things in Computer Science: cache invalidation and naming things."（Phil Karlton の言葉として知られる）

| 方法 | 内容 | 性能面の特徴 |
|---|---|---|
| TTL のみ | 期限が来たら消える | 最も簡単。TTL の間は古いデータを返す |
| 書き込み時に削除 | 商品更新時に `DEL product:v1:42` | 古さが短い。削除漏れのリスク |
| バージョンキー | `product:v1:42:rev17` のように更新番号を含める | 古いキーは TTL で自然消滅 |

書き込み時は「**DB を更新してからキャッシュを削除**」が基本です。順序の問題や二重削除は [[68_分散システム/50_分散キャッシュ/キャッシュ戦略|キャッシュ戦略]] の「整合性」の節にあります。

### 5.3 スタンピード

人気キーの TTL が切れた瞬間、同時に来た大量のリクエストが**全員ミスして一斉に DB へ**向かう現象です。セール開始時など、まさに負荷が高いときに起きます。

```
TTL 切れ ─┬─ req1 ミス → DB 重い集計 ┐
          ├─ req2 ミス → DB 重い集計 ├ DB が同じ計算を何百回も → 全体が遅延
          └─ req300 ミス → DB ...     ┘
```

主な対策は、①1 つのリクエストだけが再計算し他は待つ／古い値を返す（ロック・single-flight）、②期限前に裏で更新する（refresh-ahead）、③TTL にジッターを入れる、です。詳しくは [[キャッシュスタンピード]] を参照してください。

プロセス内だけでも、**同じキーの読み込み中の Promise を共有する**だけで同時ミスを 1 回にできます。

```ts
const inflight = new Map<string, Promise<unknown>>();

function singleFlight<T>(key: string, load: () => Promise<T>): Promise<T> {
  const existing = inflight.get(key);
  if (existing) return existing as Promise<T>;
  const p = load().finally(() => inflight.delete(key));
  inflight.set(key, p);
  return p;
}
// cached(..., () => singleFlight(key, loadFromDb)) のように組み合わせる
// （API 4 台なら DB への同時再計算は最大 4 回に抑えられる）
```

## 6. メモ化とアプリ内キャッシュ

**メモ化（Memoization）**：関数の引数ごとに結果を覚えておき、同じ引数なら計算を省く手法。プロセス内メモリなので最速（ネットワークなし）ですが、**サイズの上限と期限**が必須です。

```ts
import { LRUCache } from "lru-cache"; // v10 以降（2026 年時点）

const categoryTree = new LRUCache<string, Category[]>({
  max: 100,        // 最大件数（上限なしの Map はメモリリークの原因）
  ttl: 60_000,     // 60 秒
});

async function getCategoryTree(locale: string): Promise<Category[]> {
  const hit = categoryTree.get(locale);
  if (hit) return hit;
  const tree = await loadCategoryTreeFromDb(locale);
  categoryTree.set(locale, tree);
  return tree;
}
```

- **API 4 台で中身がずれる**：台ごとに別々のキャッシュなので、更新後しばらくは台によって古い・新しいが混在する。許容できるデータだけに使う
- **リクエスト単位のメモ化**（[[03_N+1問題の発見と解決|DataLoader]] のキャッシュ）は、1 リクエスト内の重複読み込みを消すのに便利で、古くなる心配もほぼない

## 7. どう測るか：効いているか、逆効果になっていないか

導入前後で次の指標を比べます。

| 指標 | 見る理由 |
|---|---|
| キー種類ごとのヒット率 | 低ければ効果なし。キー設計（ユーザー ID を含めすぎ等）を見直す |
| API の p50 と p99 | p50 だけ改善して p99 が変わらないのはよくある（ミス時が遅いまま） |
| DB の QPS・CPU | ミス率に比例して下がっているか |
| Redis のレイテンシ・メモリ・evicted_keys | 容量不足で追い出されていないか |
| キャッシュ由来の不具合 | 古い価格表示などの問い合わせ |

### キャッシュが効かない・逆効果のケース

- **ヒット率が低い**：キーの種類が多すぎる（検索条件の組み合わせ、ユーザーごと）。全部ミスなら「Redis 往復ぶん遅くなる」だけ
- **元が十分速い**：主キー検索 1ms を Redis 1ms に置き換えても意味がない。複雑さだけ増える
- **値が大きい**：数 MB の JSON を毎回 Redis から取ってパースすると、ネットワークと `JSON.parse` が重い
- **書き込みが多い**：更新のたびに無効化され、ヒットする前に消える
- **個人データの取り違え**：キーにユーザー ID を入れ忘れ、CDN / Nginx で他人のページを返す。性能以前の重大事故

## よくある誤解・つまずき

- ❌ 遅ければまずキャッシュ → ✅ 先に原因（インデックス・N+1）を直します。キャッシュは原因を隠し、無効化の複雑さを持ち込みます。
- ❌ キャッシュを入れれば p99 も下がる → ✅ ミスしたリクエストは元の遅さのままです。p99 を下げるには、ミス時の処理自体を速くするか、ヒット率を非常に高くする必要があります。
- ❌ TTL を長くすればヒット率が上がって得 → ✅ 古いデータを返す時間も伸びます。データごとに「どれだけ古くてよいか」から決めます。
- ❌ アプリ内メモリの Map は手軽で安全 → ✅ 上限がないとメモリリークになり、複数台では中身がずれます。LRU と TTL を使います。
- ❌ Redis が落ちたら API も落ちて当然 → ✅ cache-aside なら DB にフォールバックできます。ただし全リクエストが DB に来るので、DB が耐えられるかは負荷テストで確認しておきます。

## まとめ

- キャッシュはユーザーに近いほど速く負荷も減るが、無効化しにくい。データの性質で置き場所を選ぶ
- 平均レイテンシ ＝ ヒット率 × ヒット時 ＋ ミス率 × ミス時。ヒット率をメトリクスにして効果を測る
- cache-aside はキーにバージョン、必ず TTL、障害時は DB へフォールバック
- 「読み多・変化少・計算重」がキャッシュ向き。在庫や価格など鮮度が重要なものは慎重に
- スタンピードは single-flight・refresh-ahead・TTL ジッターで防ぐ
- ヒット率が低い、元が速い、書き込みが多いときは効かないか逆効果

## 確認クイズ

1. Redis の読み書きが 2ms、DB からの取得が 40ms のとき、ヒット率 80% の平均レイテンシはいくらですか（ミス時は Redis 読み + DB + Redis 書き）。
> [!tip]- 答え
> ミス時は 2 + 40 + 2 = 44ms。平均は 0.8 × 2 + 0.2 × 44 = 1.6 + 8.8 = 10.4ms です。

2. キャッシュを入れて平均レイテンシは大きく下がったのに、p99 がほとんど変わりませんでした。なぜですか。
> [!tip]- 答え
> ヒット率が 99% 未満なら、遅い方から 1% のリクエストはキャッシュミスしたものになり、その時間はキャッシュ前とほぼ同じ（むしろ Redis 往復ぶん少し遅い）だからです。

3. API サーバー 4 台それぞれのメモリにカテゴリ一覧をキャッシュしています。管理画面でカテゴリ名を変更したとき、どんな問題が起きますか。
> [!tip]- 答え
> 更新を受けた台以外は TTL が切れるまで古い名前を返すため、リクエストがどの台に振られるかで表示が変わります。許容できない場合は Redis などの共有キャッシュにするか、更新通知（Pub/Sub）で各台のキャッシュを消します。
