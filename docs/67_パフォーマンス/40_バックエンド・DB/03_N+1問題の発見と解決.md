# N+1問題の発見と解決

> [!abstract] この記事で分かること
> - N+1 問題が ORM（Prisma / TypeORM）のどんな書き方から生まれるか
> - 「往復回数 × レイテンシ」で遅さを見積もる方法
> - 発見の 4 つの手段：クエリログ、リクエストごとのクエリ数カウント、APM、テストでのクエリ数検証

>
> **前提**：概念は [[N+1問題 — ORMの裏で何本SQLが飛んでいるか｜ねる前エンジニアリング]] と [[N+1問題とは？DBアクセスとマイクロサービス設計の本質・対策]] で整理済みです。この回は「Shop API で実際に見つけて直して確かめる」手順に絞ります。

## 1. ひとことで言うと

N+1 問題は、**買い物リストを 1 品ずつ店員に渡して、毎回倉庫まで往復してもらう**ようなものです。1 回の往復は短くても、50 品なら 50 往復。リストをまとめて渡せば 1 往復で済みます。

- 一覧を取る **1 回**のクエリのあと、各行の関連データを取るクエリが **N 回**走る
- 遅さの正体は DB の計算ではなく、**往復回数 × 1 往復のレイテンシ**
- コードの見た目ではなく、**実際に飛んだクエリの本数を測って**判断する

## 2. ORM でどう生まれるか

Shop の商品一覧で「商品名と在庫数とカテゴリ名」を返す API を例にします。

### 2.1 Prisma の例

```ts
// ❌ Before：ループの中で 1 件ずつ取りに行く
const products = await prisma.product.findMany({ take: 50 });          // 1 回
const items = [];
for (const p of products) {
  const stock = await prisma.stock.findUnique({ where: { productId: p.id } });   // N 回
  const category = await prisma.category.findUnique({ where: { id: p.categoryId } }); // N 回
  items.push({ id: p.id, name: p.name, stock: stock?.quantity ?? 0, category: category?.name });
}
// 合計 1 + 50 + 50 = 101 クエリ
```

Prisma は関連を自動で遅延ロードしないので、N+1 は「ループ内の `await prisma.xxx`」として**コードに見える形**で現れます。GraphQL のリゾルバのように、ループが別の関数に隠れていると気づきにくくなります。

### 2.2 TypeORM の例（遅延ロード）

```ts
@Entity()
export class Product {
  @PrimaryGeneratedColumn() id!: number;
  @Column() name!: string;

  // lazy relation：プロパティにアクセスした瞬間に SELECT が走る
  @ManyToOne(() => Category, { lazy: true })
  category!: Promise<Category>;
}

const products = await productRepo.find({ take: 50 }); // 1 回
for (const p of products) {
  const c = await p.category;  // ← 見た目はプロパティ参照だが、ここで毎回 SELECT（N 回）
  console.log(p.name, c.name);
}
```

**遅延ロード（Lazy Loading）**：関連データを「使う瞬間」に取りに行く仕組み。1 件だけ見るなら無駄がない賢いやり方ですが、ループの中では件数分繰り返されます。ORM はループ全体を見てまとめてはくれません（[[17_ORMとは]]）。

## 3. なぜ遅いか：往復回数で見積もる

1 クエリの所要時間は「DB 内の実行時間」＋「ネットワーク往復」＋「ドライバ・ORM の処理」です。N+1 の 1 本 1 本は主キー検索で DB 内は 0.1ms 程度でも、**往復とオーバーヘッドが毎回乗ります**。

```
見積もり式（説明用）：  合計 ≒ (1 + N) × (1 往復の時間)

1 往復 = 1ms（同じデータセンター内の例）     █ = 50ms
  N =   10 →   11ms   ▏
  N =   50 →   51ms   █
  N =  500 →  501ms   ██████████
1 往復 = 5ms（別リージョン・混雑時の例）
  N =   50 →  255ms   █████
  N =  500 → 2505ms   ██████████████████████████████████████████████████
```

> [!note] 数値は説明用の例です
> 1 往復の時間は環境で大きく違います。ポイントは**N に比例して伸びる**ことと、**手元（DB が同じマシン、データ 10 件）では 1 往復がほぼ 0 で N も小さいので気づけない**ことです。

さらに、N+1 は DB の**コネクションを長く握る**ため、同時リクエストが増えると [[02_DBクエリのチューニング実践#5.2 コネクションプール枯渇の症状|プール枯渇]] を引き起こし、無関係な API まで遅くします。

## 4. 発見方法

### 4.1 クエリログを眺める

開発中は ORM のクエリログを常に出しておき、**同じ形で値だけ違う SQL が並んでいないか**を見ます。

```ts
// Prisma：クエリイベントを受け取る（2026 年時点の API。バージョンで設定方法が変わることがあります）
const prisma = new PrismaClient({ log: [{ emit: "event", level: "query" }] });
prisma.$on("query", (e) => console.log(`${e.duration}ms ${e.query}`));
```

```
2ms SELECT ... FROM "Stock" WHERE "productId" = $1 LIMIT $2
1ms SELECT ... FROM "Stock" WHERE "productId" = $1 LIMIT $2
2ms SELECT ... FROM "Stock" WHERE "productId" = $1 LIMIT $2
...（50 行続く）  ← N+1 のサイン
```

### 4.2 リクエストごとにクエリ数を数える

本番でも使えるように、**1 リクエストで何本のクエリを発行したか**をログとメトリクスに出します。Node.js の `AsyncLocalStorage`（非同期処理をまたいでリクエスト単位の値を持ち回る仕組み）を使います。

```ts
import { AsyncLocalStorage } from "node:async_hooks";

type Ctx = { queries: number; dbMs: number };
export const reqCtx = new AsyncLocalStorage<Ctx>();

// Express ミドルウェア：リクエストごとにカウンタを用意し、終了時にログ
app.use((req, res, next) => {
  const ctx: Ctx = { queries: 0, dbMs: 0 };
  res.on("finish", () => {
    logger.info({ route: req.route?.path, queries: ctx.queries, db_ms: ctx.dbMs });
  });
  reqCtx.run(ctx, next);
});

// ORM のクエリイベントでカウント
prisma.$on("query", (e) => {
  const ctx = reqCtx.getStore();
  if (ctx) { ctx.queries++; ctx.dbMs += e.duration; }
});
```

集計基盤で「ルートごとのクエリ数の p99」を見れば、**件数に比例してクエリ数が増えている API** が分かります。前々回の Server-Timing（[[01_APIレスポンスタイムの分解]]）に `db;desc="51 queries"` と出すのも便利です。

### 4.3 APM・分散トレース・pg_stat_statements

- **APM**（Application Performance Monitoring：Datadog、New Relic、Sentry など）や OpenTelemetry のトレースでは、同じ DB スパンが何十本も並ぶ「くし形」のウォーターフォールとして見えます。N+1 を自動検出する機能を持つ製品もあります。
- **pg_stat_statements** の `calls` 順 TOP（[[02_DBクエリのチューニング実践]]）で、API の呼び出し回数の数十倍呼ばれているクエリは N+1 の候補です。

### 4.4 テストでクエリ数を検証する（再発防止）

N+1 は一度直しても、機能追加で簡単に戻ります。**クエリ数の上限をテストで固定**するのが最も確実な再発防止です。

```ts
// vitest の例：データ件数を変えてもクエリ数が一定であることを確かめる
import { describe, it, expect } from "vitest";

async function countQueries(fn: () => Promise<unknown>): Promise<number> {
  const ctx = { queries: 0, dbMs: 0 };
  await reqCtx.run(ctx, fn);
  return ctx.queries;
}

describe("GET /api/products", () => {
  it("商品数に比例してクエリが増えない", async () => {
    await seedProducts(5);
    const q5 = await countQueries(() => listProducts({ limit: 50 }));
    await seedProducts(50);
    const q50 = await countQueries(() => listProducts({ limit: 50 }));

    expect(q50).toBe(q5);          // 件数を増やしても本数は同じ
    expect(q50).toBeLessThanOrEqual(3);
  });
});
```

**件数を 2 通り以上で比べる**のがコツです。テストデータが 3 件だけだと、N+1 でもクエリ数は 4 本で「少ない」ように見えてしまいます。

## 5. 解決方法

### 5.1 JOIN / include（eager loading）

**Eager Loading（先読み）**：最初のクエリの時点で、使うと分かっている関連データも一緒に取る方法です。

```ts
// Prisma：include / select で関連も取る
const products = await prisma.product.findMany({
  take: 50,
  select: {
    id: true,
    name: true,
    stock: { select: { quantity: true } },
    category: { select: { name: true } },
  },
});
// 101 クエリ → 数本（Prisma は既定では関連ごとに IN で別クエリを発行。
// relationLoadStrategy: "join" を指定すると 1 本の JOIN になる。2026 年時点、対応 DB と設定はバージョンを確認）
```

```ts
// TypeORM：relations か QueryBuilder の JOIN
const products = await productRepo.find({
  take: 50,
  relations: { category: true, stock: true },
});

const products2 = await productRepo
  .createQueryBuilder("p")
  .leftJoinAndSelect("p.category", "c")
  .leftJoinAndSelect("p.stock", "s")
  .take(50)
  .getMany();
```

### 5.2 IN / ANY でまとめる（手動バッチ）

ORM の機能が使いにくい場合や、別のデータソースから取る場合は、**ID を集めて 1 回で取り、Map で引き当てる**のが基本形です。

```ts
const products = await prisma.product.findMany({ take: 50 });
const ids = products.map((p) => p.id);

// 1 回でまとめて取得（SQL では WHERE product_id = ANY($1)）
const stocks = await prisma.stock.findMany({ where: { productId: { in: ids } } });
const stockById = new Map(stocks.map((s) => [s.productId, s.quantity]));

const items = products.map((p) => ({
  id: p.id,
  name: p.name,
  stock: stockById.get(p.id) ?? 0,   // 見つからない場合の既定値を忘れない
}));
// 101 クエリ → 2 クエリ（商品数が 500 になっても 2 クエリ）
```

### 5.3 DataLoader（GraphQL のバッチ化）

GraphQL では、`Product.stock` のリゾルバが商品ごとに呼ばれるため、リゾルバの中でそのまま DB を引くと N+1 になります。**DataLoader** は、同じイベントループの周回（tick）内に呼ばれた `load(id)` を集めて、1 回のバッチ関数呼び出しにまとめるライブラリです。

```ts
import DataLoader from "dataloader";

// リクエストごとに作る（作り置きして共有すると、ユーザー間でキャッシュが混ざる）
export function createLoaders() {
  return {
    stockByProductId: new DataLoader<number, number>(async (ids) => {
      const rows = await prisma.stock.findMany({ where: { productId: { in: [...ids] } } });
      const map = new Map(rows.map((r) => [r.productId, r.quantity]));
      // 重要：keys と同じ順序・同じ長さで返す
      return ids.map((id) => map.get(id) ?? 0);
    }),
  };
}

// リゾルバ
const resolvers = {
  Product: {
    stock: (product: { id: number }, _args: unknown, ctx: { loaders: ReturnType<typeof createLoaders> }) =>
      ctx.loaders.stockByProductId.load(product.id),
  },
};
```

```
DataLoader なし                       DataLoader あり
stock(1) → SELECT ... = 1             stock(1) ┐
stock(2) → SELECT ... = 2             stock(2) ├→ 同じ tick で集める → SELECT ... IN (1,2,...,50)
...                                   ...      │
stock(50)→ SELECT ... = 50            stock(50)┘
（50 往復）                            （1 往復）
```

### 5.4 マイクロサービス間の N+1

在庫が別サービス（在庫 API）にある構成では、商品ごとに `GET /stock/{id}` を呼ぶと **HTTP の N+1** になります。HTTP は DB より 1 往復が重い（数 ms〜数十 ms）ので、影響はさらに大きくなります。

- 在庫サービス側に **BatchGet**（`POST /stock:batchGet { ids: [...] }` や `GET /stock?ids=1,2,3`）を用意する。最大件数・順序・一部が見つからない場合の扱いを決めておく
- 複数サービスにまたがる場合は **BFF**（Backend For Frontend：画面ごとの集約 API）でまとめる
- `Promise.all` で並列化するだけでは**待ち時間は縮んでも呼び出し回数は N のまま**で、相手への同時負荷が跳ね上がる

設計面の考え方は [[N+1問題とは？DBアクセスとマイクロサービス設計の本質・対策]] を参照してください。

## 6. 逆に取りすぎる問題と、直した後の確かめ方

N+1 を直そうとして、今度は**取りすぎ**になることがあります。

| 取りすぎの形 | 何が起きるか | 対策 |
|---|---|---|
| 使わない関連まで `include` | 転送量・メモリ・シリアライズが増える | その画面で使う関連と列だけ `select` |
| 1 対多の JOIN で行が膨らむ | 商品 50 件 × レビュー 200 件 = 1 万行が返る | 多側は別クエリの IN にする、件数や集計（COUNT / AVG）だけ取る |
| ページネーションなしで全件 eager loading | 全商品 × 全関連をメモリに載せる | まずページネーションで N 自体を小さくする |
| IN に数万件の ID | 巨大な SQL・計画作成の遅さ | 件数の上限を決め、チャンクに分ける |

**直した後は、必ず Before / After を 3 つの指標で比べます**（数値は説明用の例）。

| 指標 | Before | After（IN でまとめた後） |
|---|---|---|
| 1 リクエストのクエリ数 | 101 | 3 |
| DB 時間（スパン合計） | 600ms | 15ms |
| API の p99 | 2.0s | 0.4s |
| レスポンスサイズ | 40KB | 40KB（変わっていないこと＝取りすぎていないことを確認） |

## よくある誤解・つまずき

- ❌ 1 本 1 本のクエリが速いから問題ない → ✅ N に比例して往復が増え、コネクションも長く握ります。合計時間と本数で判断します。
- ❌ 手元で速いので N+1 はない → ✅ 手元は往復がほぼ 0 でデータも少ないため見えません。クエリ数を数えます。
- ❌ JOIN にすれば常に最速 → ✅ 1 対多の JOIN は行数が掛け算で膨らみます。IN で 2 本に分けた方が速いことも多いです。
- ❌ `Promise.all` で並列にすれば N+1 は解決 → ✅ 待ち時間は縮みますが、DB や下流サービスへの呼び出し回数は N のままです。
- ❌ DataLoader はアプリ全体で 1 つ作ればよい → ✅ リクエストごとに作ります。共有すると古いデータや他ユーザーのデータを返す危険があります。

## まとめ

- N+1 は一覧の 1 回 + 各行ごとの N 回のクエリ。遅さは「往復回数 × レイテンシ」で見積もれる
- 発見はクエリログ・リクエストごとのクエリ数・APM / pg_stat_statements で行い、テストでクエリ数を固定して再発を防ぐ
- 解決は include / JOIN、IN でまとめて Map で引き当てる、GraphQL では DataLoader、サービス間は BatchGet
- 直しすぎ（不要な関連、1 対多 JOIN の膨張、全件取得）に注意する
- 直した後はクエリ数・DB 時間・p99・レスポンスサイズの Before / After を比べる

## 確認クイズ

1. 1 往復 2ms の環境で、商品 200 件の一覧に対して各商品の在庫を 1 件ずつ取ると、DB 往復だけで約何 ms かかりますか。IN でまとめた場合はどうですか。
> [!tip]- 答え
> (1 + 200) × 2ms ≒ 402ms です。IN でまとめれば 2 往復で約 4ms（＋まとめたクエリ自体の実行時間）になります。

2. テストで N+1 の再発を防ぐとき、データ件数を 1 通りではなく 2 通り以上で試す理由は何ですか。
> [!tip]- 答え
> 件数が少ないと N+1 でもクエリ数が少なく見えてしまうためです。件数を変えてもクエリ数が変わらないこと（N に比例しないこと）を確かめるのが本質です。

3. 商品 50 件とそれぞれのレビュー（平均 200 件）を 1 本の JOIN で取ったところ遅くなりました。なぜですか。
> [!tip]- 答え
> 1 対多の JOIN で結果が約 1 万行に膨らみ、商品の列も繰り返し転送されるためです。レビューは別クエリの IN で取る、あるいは件数や平均だけを集計して取る方が適しています。
