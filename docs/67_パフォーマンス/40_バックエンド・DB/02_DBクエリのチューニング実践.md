# DBクエリのチューニング実践

[[MOC_パフォーマンス体系|📚 目次]] ｜ [[01_APIレスポンスタイムの分解|← 前へ]] ｜ [[03_N+1問題の発見と解決|次へ →]]

> [!abstract] この記事で分かること
> - 本番で遅いクエリを見つける 3 つの道具（pg_stat_statements・auto_explain・スロークエリログ）
> - 改善の順番（EXPLAIN ANALYZE → インデックス → 書き換え → 取得量削減 → 非正規化・集計テーブル）
> - よくある改善パターン（SELECT *、OFFSET → キーセット、COUNT(*)、OR / IN、関数インデックス）
> - クエリ自体は速いのに遅い原因：ロック待ち・長いトランザクション・コネクションプール枯渇
> - 改善前後を公平に比べる測り方
>
> **前提**：[[05_実行計画の読み方]] と [[04_インデックスが効かないパターン]] を読んでいると理解しやすいです。この回はそれらの理論を「実務の手順」として使う回です。

## 1. ひとことで言うと

DB チューニングは**病院の診察**に似ています。いきなり手術（スキーマ変更）はしません。まず健康診断（pg_stat_statements）で悪いところの候補を挙げ、精密検査（EXPLAIN ANALYZE）で原因を特定し、軽い治療（インデックス・書き換え）から順に試して、治療後にもう一度検査します。

- **見つける**：「1 回が遅い」より「合計時間が大きい」クエリを優先する
- **直す**：コストの低い手から順に（インデックス → 書き換え → 取得量削減 → 構造変更）
- **確かめる**：同じ条件で Before / After を測る。書き込み性能や他のクエリへの影響も見る

実行計画の読み方そのもの（Seq Scan / Index Scan、見積もりと実測のズレ）は [[05_実行計画の読み方]] に任せ、ここでは手順と典型パターンに絞ります。

## 2. 遅いクエリの見つけ方

### 2.1 pg_stat_statements で TOP-N を出す

**pg_stat_statements**：実行された SQL を「形」ごと（値を `$1` に置き換えて）に集計する PostgreSQL の拡張です。設定方法は [[05_実行計画の読み方]] の 6.2 を参照してください。性能改善では次の 3 つの並べ方を使い分けます。

```sql
-- ① 合計時間 TOP 10：DB 全体の負荷への寄与が大きい順（最優先）
SELECT calls,
       round(total_exec_time::numeric)        AS total_ms,
       round(mean_exec_time::numeric, 2)      AS mean_ms,
       round((100 * total_exec_time / sum(total_exec_time) OVER ())::numeric, 1) AS pct,
       left(query, 80)                        AS query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

-- ② 平均時間 TOP 10：1 回が遅い（ユーザーの p99 を悪くする）
--    ORDER BY mean_exec_time DESC  ※ calls が極端に少ないものは除外して見る

-- ③ 呼び出し回数 TOP 10：N+1 の候補（1 回は速いが回数が異常）
--    ORDER BY calls DESC
```

| 並べ方 | 見つかるもの | 例 |
|---|---|---|
| 合計時間 | DB の CPU・I/O を一番食っているもの | 5ms × 100 万回 = 5000 秒 |
| 平均時間 | 特定の API を遅くしている重いクエリ | 管理画面の集計 3 秒 |
| 呼び出し回数 | [[03_N+1問題の発見と解決|N+1]] | `SELECT ... WHERE product_id = $1` が API 呼び出しの 50 倍 |

> [!tip] 期間を区切って見る
> pg_stat_statements は累積値です。改善の効果を見るときは `SELECT pg_stat_statements_reset();` でリセットしてから一定時間（例：1 時間）ためて比べるか、定期的にスナップショットを取って差分を見ます。

### 2.2 スロークエリログと auto_explain

pg_stat_statements は「形」ごとの集計なので、**どのパラメータで遅かったか**や**そのときの実行計画**は分かりません。それを補うのがログです。

```conf
# postgresql.conf の例
log_min_duration_statement = '500ms'      # 500ms を超えた SQL をログに出す

# auto_explain：遅いクエリの実行計画を自動でログに出す拡張
session_preload_libraries = 'auto_explain'
auto_explain.log_min_duration = '500ms'
auto_explain.log_analyze = on             # 実測値も出す（全クエリの計測コストが増えるので注意）
auto_explain.log_buffers = on
```

> [!warning] log_analyze のオーバーヘッド
> `auto_explain.log_analyze = on` は、閾値を超えたかどうかに関係なく**すべてのクエリで計測を行う**ため、負荷の高い環境では性能に影響します。本番では閾値を高めにする、`auto_explain.sample_rate` でサンプリングする、`log_timing = off` にするなどで調整します。

「本番だけ遅い」クエリは、データ量や値の偏り（特定ユーザーだけ注文が 10 万件など）が原因であることが多く、auto_explain のログに残った計画が最大の手がかりになります。

## 3. 改善の手順

```
① EXPLAIN (ANALYZE, BUFFERS) で現状を測る   ← 本番相当のデータとパラメータで
        ↓
② インデックスで解決できるか                ← 最も安く、効果が大きいことが多い
        ↓ ダメなら
③ クエリを書き換える                         ← 書き方でインデックスが使えないなど
        ↓ ダメなら
④ 取得する量を減らす                         ← 列・行・頻度を減らす。そもそも要るか？
        ↓ ダメなら
⑤ 構造を変える                               ← 非正規化・集計テーブル・マテリアライズドビュー・キャッシュ
```

上ほど影響範囲が小さく、下ほど「データの持ち方」を変えるので、整合性を保つ仕組み（更新時に集計テーブルも直す等）が必要になります。

### 3.1 インデックスを足す前に確認すること

- その列は **WHERE / JOIN / ORDER BY** で使われているか（[[03_インデックスの基本と設計]]）
- 書き方のせいで使われていないだけではないか（[[04_インデックスが効かないパターン]]）
- 本番では `CREATE INDEX CONCURRENTLY` を使う。通常の `CREATE INDEX` はテーブルへの書き込みをブロックします

```sql
-- 本番で書き込みを止めずに作る（トランザクション内では実行できない）
CREATE INDEX CONCURRENTLY idx_orders_user_created
  ON orders (user_id, created_at DESC);
```

インデックスは**書き込みのたびに更新される**ので、増やすほど INSERT / UPDATE が遅くなります。使われていないインデックスは `pg_stat_user_indexes` の `idx_scan = 0` で見つけて整理します。

## 4. よくある改善パターン

### 4.1 SELECT * をやめる

```sql
-- ❌ 一覧に不要な description（長文）や画像メタデータまで読む
SELECT * FROM products WHERE category_id = 3 ORDER BY id LIMIT 20;

-- ✅ 必要な列だけ
SELECT id, name, price, thumbnail_url FROM products WHERE category_id = 3 ORDER BY id LIMIT 20;
```

効果：転送量・アプリのメモリ・シリアライズが減る。さらに必要な列がすべてインデックスに含まれれば **Index Only Scan**（テーブル本体を読まない）が使えます。

### 4.2 OFFSET ページネーション → キーセットページネーション

`OFFSET 10000 LIMIT 20` は、**10,020 行を読んでから 10,000 行を捨てる**処理です。ページが深いほど遅くなります。

```sql
-- ❌ OFFSET：深いページほど遅い
SELECT id, name, price FROM products
ORDER BY created_at DESC, id DESC
OFFSET 10000 LIMIT 20;

-- ✅ キーセット（シーク法）：前ページの最後の値から続きを読む
SELECT id, name, price, created_at FROM products
WHERE (created_at, id) < ($1, $2)          -- 前ページ最後の行の created_at, id
ORDER BY created_at DESC, id DESC
LIMIT 20;
-- インデックス：CREATE INDEX ON products (created_at DESC, id DESC);
```

```
読む行数（説明用のイメージ）
OFFSET   1ページ目 ▏20     100ページ目 ████████████████ 2,000    500ページ目 ████…████ 10,000
キーセット 何ページ目でも ▏20（インデックスで続きの位置に直接飛ぶ）
```

トレードオフ：「37 ページ目に直接飛ぶ」ができない（「次へ」「もっと見る」向き）。API ではカーソル（`?after=<エンコードした created_at,id>`）として返します。

### 4.3 COUNT(*) の重さ

PostgreSQL は MVCC（複数バージョンの行を持つ仕組み）のため、`COUNT(*)` は条件に合う行を**実際に数える**必要があり、大きなテーブルでは遅くなります。

| 方法 | 使いどころ |
|---|---|
| 件数表示をやめる / 「1,000 件以上」と上限付きで数える | 一覧の総件数（ユーザーは正確な数を必要としないことが多い） |
| `LIMIT 21` で取って「次ページがあるか」だけ判定 | 「次へ」ボタンの表示 |
| `pg_class.reltuples` の推定値 | 管理画面の概数 |
| 集計テーブル・カウンタ列 | 正確な件数を頻繁に出す必要がある場合 |

```sql
-- 上限付きカウント：最大 1001 行しか数えない
SELECT count(*) FROM (
  SELECT 1 FROM orders WHERE user_id = $1 LIMIT 1001
) t;
```

### 4.4 OR と IN

PostgreSQL は、OR の両側の列にそれぞれインデックスがあれば **BitmapOr** で組み合わせられます。困るのは、OR の片方が**別テーブル（JOIN 先）の列**だったり、インデックスのない列だったりする場合で、全体が Seq Scan になりがちです。

```sql
-- ❌ 2 つのテーブルにまたがる OR：どちらのインデックスでも絞り込めない
SELECT o.id FROM orders o JOIN users u ON u.id = o.user_id
WHERE o.coupon_code = $1 OR u.email = $2;

-- ✅ UNION で分けて、それぞれインデックスを使わせる（重複が問題なければ UNION ALL）
SELECT o.id FROM orders o WHERE o.coupon_code = $1
UNION
SELECT o.id FROM orders o JOIN users u ON u.id = o.user_id WHERE u.email = $2;
```

同じ列の OR は `IN` / `= ANY($1)` にまとめます。アプリから ID の配列を渡すときは、件数分の `$1, $2, ...` を組み立てるより `= ANY($1::int[])` の方が SQL の形が 1 つに定まり、pg_stat_statements でもまとめて見えます。詳しい理由は [[04_インデックスが効かないパターン]] の 3.2 を参照してください。

### 4.5 関数インデックス（式インデックス）

```sql
-- ❌ 列に関数をかけるとふつうのインデックスは使えない
SELECT id FROM users WHERE lower(email) = lower($1);

-- ✅ 式そのものにインデックスを張る
CREATE INDEX CONCURRENTLY idx_users_lower_email ON users (lower(email));
```

### 4.6 取得量を減らす・構造を変える

- **そもそも毎回要るか**：毎リクエストで同じ「カテゴリ一覧」を引いているなら [[04_キャッシュで応答を速くする|キャッシュ]]へ
- **集計テーブル**：商品ごとのレビュー平均・件数を `product_stats` に持ち、レビュー投稿時に更新する
- **マテリアライズドビュー**：重い集計結果を保存し、`REFRESH MATERIALIZED VIEW CONCURRENTLY` で定期更新（多少古くてよい場合）

これらは「読み込みを速くする代わりに、書き込みと整合性の管理が増える」トレードオフです（[[04_最適化の進め方とトレードオフ]]）。

## 5. クエリは速いのに遅い：ロック待ちとコネクション

EXPLAIN ANALYZE では 5ms なのに、本番では 3 秒かかる。こういうときは**クエリの外で待っている**ことを疑います。

### 5.1 ロック待ちと長いトランザクション

```sql
-- いま待たされているセッションと、待たせている相手
SELECT pid,
       wait_event_type,
       pg_blocking_pids(pid) AS blocked_by,
       now() - xact_start     AS xact_age,
       state,
       left(query, 60)        AS query
FROM pg_stat_activity
WHERE wait_event_type = 'Lock' OR now() - xact_start > interval '1 minute'
ORDER BY xact_start;
```

よくある原因：

- トランザクションの中で**外部 API を呼んでいる**（相手が遅いと行ロックを握ったまま待つ）
- `BEGIN` したまま放置された接続（`state = 'idle in transaction'`）
- 在庫の `UPDATE products SET stock = stock - 1 WHERE id = $1` に人気商品の注文が集中（セール時の注文 API 詰まり）
- 長いトランザクションが VACUUM を妨げ、不要な行が溜まってテーブルが膨らむ

対策：トランザクションは短く（外部 I/O は外へ出す）、`idle_in_transaction_session_timeout` や `statement_timeout`・`lock_timeout` を設定し、ロック待ちは `log_lock_waits = on` でログに残します。トランザクションとロックの理論は [[MOC_データアーキテクチャ体系]] の該当章を参照してください。

### 5.2 コネクションプール枯渇の症状

アプリのコネクションプールが全部使用中だと、クエリは**DB に届く前にアプリ内で順番待ち**します。DB 側の統計には現れないので見落としがちです。

| 症状 | 見え方 |
|---|---|
| アプリで計った DB 時間は長いが、pg_stat_statements の mean は短い | プール待ちが含まれている |
| 負荷が一定を超えると急に全 API が遅くなる | 待ち行列の典型（[[01_スループットと待ち行列理論]]） |
| 「timeout acquiring connection」系のエラー | プールの取得タイムアウト |

プールの仕組みとサイズの決め方は [[01_アプリケーションサーバーとは]] と [[06_データベースサーバーの運用]] にあります。性能の観点で大事なのは、**プール待ち時間を別のメトリクスとして測る**ことと、プールを増やす前に「1 本の接続を長く握っている処理（遅いクエリ・長いトランザクション）」を減らすことです。

## 6. 改善前後の測り方

チューニングの効果は、測り方を間違えると簡単に勘違いします。

1. **データをそろえる**：本番相当の件数と値の偏り。開発 DB の 100 件では Seq Scan でも速い
2. **キャッシュ状態をそろえる**：1 回目（ディスク読み）と 2 回目（バッファヒット）で大きく違う。`BUFFERS` の `read` / `hit` を確認し、複数回実行して中央値を取る
3. **パラメータを複数試す**：件数の多いユーザーと少ないユーザーで計画が変わることがある
4. **単体と全体の両方で見る**：EXPLAIN ANALYZE（単体）に加え、デプロイ後の pg_stat_statements の total / mean と API の p99（全体）
5. **副作用を見る**：インデックス追加後の INSERT 時間、ディスク使用量、他のクエリの計画変化

```bash
# pgbench で特定クエリを同時実行して比較する例（ファイルに SQL を書く）
cat > q.sql <<'EOF'
\set uid random(1, 100000)
SELECT id, total FROM orders WHERE user_id = :uid ORDER BY created_at DESC LIMIT 20;
EOF
pgbench -n -f q.sql -c 16 -T 60 shop   # 16 接続で 60 秒。レイテンシ平均と TPS が出る
```

> [!example] Before / After の書き方（数値は説明用の例）
> | 指標 | Before | After |
> |---|---|---|
> | EXPLAIN ANALYZE（中央値） | 380ms | 4ms |
> | pg_stat_statements mean | 410ms | 5ms |
> | 該当 API の p99 | 2.0s | 0.35s |
> | orders への INSERT p99 | 3ms | 3.2ms（インデックス追加の影響は軽微） |

## よくある誤解・つまずき

- ❌ 遅いクエリ = 1 回の実行時間が長いクエリ → ✅ DB 全体への影響は「合計時間」で見ます。速いクエリの大量実行（N+1）が最大の負荷であることはよくあります。
- ❌ インデックスは多いほど良い → ✅ 書き込みが遅くなり、ディスクとメモリも食います。使われていないものは削除します。
- ❌ 開発環境の EXPLAIN ANALYZE で速ければ本番でも速い → ✅ データ量と分布が違えば計画が変わります。auto_explain で本番の計画を取ります。
- ❌ EXPLAIN ANALYZE が速いなら DB は無関係 → ✅ ロック待ち・プール待ちはクエリの外で起きます。`pg_stat_activity` とプールのメトリクスを見ます。
- ❌ コネクションプールを増やせば解決 → ✅ DB の同時処理能力を超えると全体が遅くなります。まず接続を長く握る原因を減らします。

## まとめ

- 遅いクエリは pg_stat_statements を「合計・平均・回数」の 3 通りで並べて探し、auto_explain / スロークエリログで本番の計画を取る
- 改善はインデックス → 書き換え → 取得量削減 → 構造変更の順に、安い手から
- SELECT * の削減、キーセットページネーション、COUNT(*) の回避、OR の分解、関数インデックスが定番
- クエリ自体が速くても、ロック待ち・長いトランザクション・プール枯渇で遅くなる
- Before / After はデータ・キャッシュ状態・パラメータをそろえて測り、書き込みへの副作用も確認する

## 確認クイズ

1. pg_stat_statements で、平均 2ms・呼び出し 300 万回のクエリと、平均 2 秒・呼び出し 100 回のクエリがあります。DB 負荷の観点ではどちらを先に見るべきですか。
> [!tip]- 答え
> 合計時間は前者が 2ms × 300 万 = 6000 秒、後者が 2 秒 × 100 = 200 秒なので、DB 負荷としては前者が大きいです。前者は N+1 の可能性も疑います。ただし後者が特定 API の p99 を悪化させているなら、ユーザー影響の観点で別途対応します。

2. `OFFSET 50000 LIMIT 20` が遅い理由と、代わりの方法を答えてください。
> [!tip]- 答え
> 50,020 行を順に読んでから 50,000 行を捨てるためです。前ページ最後の行のキー（例：`created_at, id`）を使って `WHERE (created_at, id) < (...)` で続きから読むキーセットページネーションに変えると、どのページでも読む行数がほぼ一定になります。

3. EXPLAIN ANALYZE では 5ms なのに、本番の API では同じクエリに 2 秒かかっています。考えられる原因を 2 つ挙げてください。
> [!tip]- 答え
> 他のトランザクションが行ロックを握っていてロック待ちになっている、またはアプリのコネクションプールが枯渇して DB に届く前に待っている、などです。本番のパラメータで実行計画が違う可能性もあります。
