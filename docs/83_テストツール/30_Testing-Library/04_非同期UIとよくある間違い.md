# 非同期 UI とよくある間違い

データ取得・ローディング表示・アニメーションなど、UI の多くは非同期に変化します。Testing Library には「変化を待つ」ための API がいくつかあり、使い方を間違えると**たまに落ちるテスト**や**何も確かめていないテスト**になります。この章では、待ち方の基本と、Kent C. Dodds の "Common mistakes with React Testing Library" をもとにしたよくある間違いをまとめます。

---

## 1. 待つための API

| API | 何をするか | 使いどころ |
|-----|------------|------------|
| `findBy…` | 要素が現れるまで待つ（`waitFor` + `getBy` の短縮形） | **要素が現れるのを待つ（一番よく使う）** |
| `waitFor(callback)` | コールバックが例外を投げなくなるまで繰り返す | 要素の出現以外の変化を待つ（モックが呼ばれた、属性が変わった） |
| `waitForElementToBeRemoved(el)` | 要素が消えるまで待つ | ローディング表示が消えるのを待つ |

- デフォルトのタイムアウトは 1000ms、確認の間隔は 50ms。`findByText('…', {}, { timeout: 3000 })` のように変えられます。

```ts
render(<UserList />);

// ローディングが消えるのを待つ
await waitForElementToBeRemoved(() => screen.queryByText('読み込み中…'));

// データが表示されるのを待つ
expect(await screen.findByRole('listitem', { name: /山田/ })).toBeInTheDocument();

// モックが呼ばれるのを待つ
await waitFor(() => expect(onSave).toHaveBeenCalledTimes(1));
```

API のモックには MSW を使うと、`fetch` の中身を差し替えずに済みます（[[01_MSWの仕組みとセットアップ]]）。

## 2. act 警告の意味

```
Warning: An update to UserList inside a test was not wrapped in act(...)
```

- **テストが終わった後（または確かめた後）に state が更新された**という意味です。多くの場合、「非同期の処理を待たずにテストを終えている」サインです。
- Testing Library の `render`・`user-event`・`findBy`・`waitFor` は内部で `act` を呼んでいるので、**自分で `act` を書く必要はほぼありません**。
- 警告が出たら、`act` で包んで黙らせるのではなく、**何の更新を待ち忘れているか**を探して `findBy` などで待ちます。

## 3. よくある間違い

### 3.1 await を忘れる

```ts
// ✗ Promise を返すだけで、待っていない
screen.findByText('完了');
user.click(button);

// ○
await screen.findByText('完了');
await user.click(button);
```

ESLint の `eslint-plugin-testing-library` を入れると、この種の間違いを検出できます。

### 3.2 waitFor の中で操作する

```ts
// ✗ waitFor はコールバックを何度も実行するので、クリックが何回も起きる
await waitFor(() => {
  fireEvent.click(button);
  expect(screen.getByText('完了')).toBeInTheDocument();
});

// ○ 操作は外で1回、待つのは確認だけ
await user.click(button);
await waitFor(() => expect(screen.getByText('完了')).toBeInTheDocument());
// さらに短く
expect(await screen.findByText('完了')).toBeInTheDocument();
```

### 3.3 waitFor の中に複数の expect を書く

```ts
// ✗ 1つ目が通るまで2つ目は評価されず、失敗時にどちらが原因か分かりにくい
await waitFor(() => {
  expect(onSave).toHaveBeenCalled();
  expect(screen.getByText('保存しました')).toBeInTheDocument();
});

// ○ 待つのは1つにして、残りは待った後に確かめる
await waitFor(() => expect(onSave).toHaveBeenCalled());
expect(screen.getByText('保存しました')).toBeInTheDocument();
```

### 3.4 空の waitFor

```ts
// ✗ 「何となく少し待つ」は、タイミング次第で落ちる
await waitFor(() => {});
await new Promise((r) => setTimeout(r, 500));

// ○ 何が起きるのを待つのかを書く
await screen.findByRole('alert');
```

### 3.5 否定を getBy で確かめる

```ts
// ✗ 見つからないとエラーになるので、正しく「ない」ことを確かめられない
expect(screen.getByText('エラー')).not.toBeInTheDocument();

// ○
expect(screen.queryByText('エラー')).not.toBeInTheDocument();
```

### 3.6 「消える」ことを findBy で待つ

- `findBy` は「現れる」のを待つもの。**消える**のを待つなら `waitForElementToBeRemoved` を使う。

### 3.7 container や querySelector で探す

```ts
// ✗ 実装（クラス名）に依存する
const { container } = render(<Nav />);
container.querySelector('.nav__item--active');

// ○ ユーザーに見える情報で探す
screen.getByRole('link', { current: 'page' });
```

### 3.8 DOM のプロパティを直接比べる

```ts
// ✗ 失敗時のメッセージが「expected false to be true」だけで、何が違うのか分からない
expect(screen.getByRole('button', { name: '送信' }).disabled).toBe(true);

// ○ jest-dom のマッチャーを使うと、要素の状態を含めたメッセージが出る
expect(screen.getByRole('button', { name: '送信' })).toBeDisabled();
```

- `getBy…` は見つからない時点で失敗するので、`expect(getBy…).toBeInTheDocument()` は厳密には冗長です。それでも「存在を確かめている」ことが読み手に伝わるので、書いておくのが一般的です。

## 4. たまに落ちるテスト（flaky）の原因と対策

| 原因 | 対策 |
|------|------|
| 非同期の変化を待っていない | `findBy` / `waitFor` で待つ |
| 前のテストのモック・タイマー・DOM が残っている | `afterEach` で cleanup・`vi.restoreAllMocks()`・`vi.useRealTimers()` |
| MSW のハンドラの上書きが次のテストに残る | `afterEach(() => server.resetHandlers())`（[[01_MSWの仕組みとセットアップ]]） |
| 現在時刻・乱数に依存する | フェイクタイマー・固定値（[[05_テストデータの用意]]） |
| タイムアウトが短すぎる（CI が遅い） | 原因を探したうえで、必要な箇所だけタイムアウトを延ばす |

調べ方は 84_デバッグ の [[MOC_デバッグ]] にもまとめていきます。
