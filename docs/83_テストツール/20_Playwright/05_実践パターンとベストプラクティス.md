# 05 — 実践パターンとベストプラクティス

テストが増えてくると、「同じページへの遷移や操作」が何度も繰り返され、修正時にあちこちを直す手間が増えます。この章では、**ページオブジェクト**で画面ごとの操作をまとめる方法、**フィクスチャ**でテストの前提条件を共通化する方法、そして**保守しやすく壊れにくいテスト**を書くためのベストプラクティスを解説します。

---

## ページオブジェクトパターンとは

**ページオブジェクト（Page Object）**は、あるページ（または画面の一部）に対する「操作」と「要素の取得」を 1 つのクラスやオブジェクトにまとめる設計パターンです。テストコードでは「どの要素をクリックするか」ではなく「ログインページでログインする」のように、**ユーザーの操作や画面の意味**で書けるようになり、可読性と保守性が上がります。

### メリット

- **変更に強い**：ボタンのセレクターが変わっても、ページオブジェクト内の 1 箇所を直せば、そのページを使うすべてのテストに反映されます。
- **読みやすい**：テストは「ログインする」「商品をカートに追加する」といったフレーズで書け、何をしているかが伝わりやすくなります。
- **再利用できる**：複数のテストで同じログイン処理を使う場合、ページオブジェクトのメソッドを呼ぶだけで済みます。

---

## ページオブジェクトの書き方（クラスベース）

例として「ログインページ」をページオブジェクトにします。

```typescript
// pages/LoginPage.ts
// ログインページに関する操作をこのクラスにまとめる
import { type Page, expect } from '@playwright/test';

export class LoginPage {
  // page（ブラウザのタブ）を受け取って保存しておく
  constructor(private readonly page: Page) {}

  // ログインページに遷移する
  async goto() {
    await this.page.goto('/login');
  }

  // メールアドレスとパスワードを入力してログインボタンを押す
  // → この 3 行を毎回テストに書く代わりに、login() と 1 行で呼べる
  async login(email: string, password: string) {
    await this.page.getByLabel('メールアドレス').fill(email);
    await this.page.getByLabel('パスワード').fill(password);
    await this.page.getByRole('button', { name: 'ログイン' }).click();
  }

  // エラーメッセージが表示されていることを確認する
  async expectError(message: string) {
    await expect(this.page.getByRole('alert')).toHaveText(message);
  }
}
```

テストでは次のように使います。

```typescript
import { test, expect } from '@playwright/test';
import { LoginPage } from '../pages/LoginPage';

test('不正なパスワードでエラーになる', async ({ page }) => {
  // ページオブジェクトを作る（ブラウザのタブを渡す）
  const loginPage = new LoginPage(page);

  // 準備：ログインページを開く
  await loginPage.goto();

  // 操作：間違ったパスワードでログインを試みる
  await loginPage.login('user@example.com', 'wrong');

  // 検証：エラーメッセージが表示されることを確認
  await loginPage.expectError('メールアドレスまたはパスワードが正しくありません');
});
```

> **ページオブジェクトを使う前と後の比較**：
> - **使わない場合**: テストのあちこちに `getByLabel('メールアドレス').fill(...)` のようなコードが散らばる → ラベルが変わったら全テストを修正
> - **使う場合**: `LoginPage.login(...)` の中の 1 箇所だけ修正すれば OK

- **constructor** で `Page` を受け取り、そのページに対する操作をメソッドにまとめています。
- **goto**、**login**、**expectError** のように、「やること」がメソッド名で分かります。
- セレクター（getByLabel、getByRole）はすべて LoginPage の内側にあり、テストは「ログインページでログインして、エラーを検証する」という流れだけを書けばよくなります。

## ページオブジェクトの書き方（関数ベース）

クラスではなく、**関数の集まり**としてページを表現する方法もあります。

```typescript
// pages/login.ts
import { type Page } from '@playwright/test';

export async function gotoLogin(page: Page) {
  await page.goto('/login');
}

export async function login(page: Page, email: string, password: string) {
  await page.getByLabel('メールアドレス').fill(email);
  await page.getByLabel('パスワード').fill(password);
  await page.getByRole('button', { name: 'ログイン' }).click();
}

export function getErrorLocator(page: Page) {
  return page.getByRole('alert');
}
```

テストでは、必要な関数だけ import して使います。

```typescript
import { test, expect } from '@playwright/test';
import { gotoLogin, login, getErrorLocator } from '../pages/login';

test('不正なパスワードでエラーになる', async ({ page }) => {
  await gotoLogin(page);
  await login(page, 'user@example.com', 'wrong');
  await expect(getErrorLocator(page)).toHaveText('メールアドレスまたはパスワードが正しくありません');
});
```

クラスか関数かはチームの好みで選んで構いません。どちらも「ページの操作を 1 か所にまとめる」という目的は同じです。

## フィクスチャで前提条件を共通化する

**フィクスチャ**は、テストの「前提」を用意する仕組みです。例えば「すでにログイン済みの状態でページを開く」「特定のデータが入った DB でテストする」といった設定を、フィクスチャとして定義しておくと、各テストで「ログイン処理」を何度も書かずに済みます。Playwright では **test.extend()** でカスタムフィクスチャを定義できます。

### ログイン済みフィクスチャの例

```typescript
// fixtures/logged-in.ts
// 「ログイン済みの状態」を作るフィクスチャを定義するファイル
import { test as base } from '@playwright/test';
import { LoginPage } from '../pages/LoginPage';

// base.extend で「loggedInPage」という新しいフィクスチャを追加する
export const test = base.extend<{ loggedInPage: void }>({
  loggedInPage: async ({ page }, use) => {
    // ── ここが「準備」部分 ──
    // テストが始まる前にログイン処理を実行する
    const loginPage = new LoginPage(page);
    await loginPage.goto();
    await loginPage.login('test@example.com', 'password123');

    // use() を呼ぶと、ここでテスト本体が実行される
    // つまり「ログイン済みの状態」でテストが始まる
    await use();

    // ── ここに「後片付け」を書ける（今回は不要）──
    // 例: await page.goto('/logout');
  },
});

export { expect } from '@playwright/test';
```

> **フィクスチャが難しいと感じたら**: 最初は `beforeEach` でログイン処理を書く方法（07 章で紹介）でも十分です。テスト数が増えてきて「毎回同じ beforeEach を書くのが面倒」と感じたら、フィクスチャに切り出す、という段階的なアプローチがおすすめです。

使う側のテストでは、**loggedInPage** をフィクスチャとして指定するだけで、そのテストの実行前にログインが行われます。

```typescript
import { test, expect } from '../fixtures/logged-in';

test('ログイン後にダッシュボードが表示される', async ({ page, loggedInPage }) => {
  await expect(page).toHaveURL(/\/dashboard/);
  await expect(page.getByRole('heading', { name: 'ダッシュボード' })).toBeVisible();
});
```

- **extend** で「loggedInPage というフィクスチャ」を追加しています。
- フィクスチャの実装では、ログイン処理を実行したあと **use()** を呼びます。use() の前が「準備」、use() の後は「後片付け」が必要なら書けます。
- テストでは **loggedInPage** を引数に取るだけで、自動的にログインが走ります。テスト本体は「ログイン済みのときの振る舞い」だけに集中できます。

## ベストプラクティス — テストを安定させ、読みやすくする

### 1. セレクターは「ユーザーに近い」ものを優先する

- **getByRole** + **name**、**getByLabel**、**getByText** を優先し、実装詳細（class 名、id）に依存しすぎないようにします。こうすると、デザイン変更で class が変わってもテストが壊れにくくなります。
- どうしても必要なときは **getByTestId** でテスト用 ID を付け、開発と「testid のルール」を決めておくとよいです。

### 2. 固定の sleep は避ける

- **page.waitForTimeout(3000)** のような固定秒待ちは、環境によっては足りなかったり、無駄に長かったりして、フレークの原因になります。
- **expect(...).toBeVisible()** や **waitFor({ state: 'visible' })** で「表示されるまで待つ」ようにし、条件が満たされた時点で先に進むようにします。

### 3. 1 テスト 1 シナリオ

- 1 つのテストでは「1 つのユーザーストーリーや検証ポイント」に絞ると、失敗したときに原因を特定しやすくなります。
- 長いシナリオは「ログイン」「一覧表示」「詳細表示」のように、複数テストに分けても構いません。必要ならフィクスチャで「ログイン済み」などを共通化します。

### 4. テストデータは分離する

- メールアドレスやパスワードなどのテストデータは、定数や設定ファイルにまとめ、テストの先頭で「このユーザーでログインする」のように参照すると、変更が楽になります。
- 他のテストと干渉しないように、可能であれば「テスト用ユーザー」や「テスト用データ」を用意し、並列実行しても衝突しないようにします。

### 5. 失敗時に原因が分かる名前を付ける

- **test('ログインできる', ...)** より **test('有効なメールとパスワードでログインするとダッシュボードに遷移する', ...)** のように、何を検証しているかが分かる名前を付けると、レポートを見たときに理解しやすくなります。
- 長すぎる場合は、**test.describe** でグループ化し、**describe('ログイン', () => { test('有効な認証情報でダッシュボードに遷移する', ...); });** のようにすると整理できます。

### 6. 並列実行を意識する

- Playwright はデフォルトでテストを並列実行します。グローバルな状態（共有 DB の 1 レコードなど）に依存すると、並列で競合することがあります。
- テストごとに独立したデータを使う、または並列度を下げる、必要なら **test.describe.serial** で直列実行にするなど、プロジェクトの性質に合わせて調整します。

## test.describe でテストをグループ化する

関連するテストを **describe** でまとめると、レポートや実行単位の指定がしやすくなります。

```typescript
import { test, expect } from '@playwright/test';
import { LoginPage } from '../pages/LoginPage';

test.describe('ログイン', () => {
  test('有効な認証情報でダッシュボードに遷移する', async ({ page }) => {
    const loginPage = new LoginPage(page);
    await loginPage.goto();
    await loginPage.login('valid@example.com', 'validpass');
    await expect(page).toHaveURL(/\/dashboard/);
  });

  test('無効なパスワードでエラーメッセージが表示される', async ({ page }) => {
    const loginPage = new LoginPage(page);
    await loginPage.goto();
    await loginPage.login('valid@example.com', 'wrong');
    await loginPage.expectError('メールアドレスまたはパスワードが正しくありません');
  });
});
```

- **test.describe.serial** にすると、その describe 内のテストは直列で実行されます。同じユーザーで連続操作する場合などに使います。

---

## この章のまとめ

- **ページオブジェクト**で「ページごとの操作と要素」をまとめると、テストが読みやすくなり、UI 変更時の修正箇所が 1 か所にまとまります。
- **フィクスチャ**で「ログイン済み」などの前提条件を共通化すると、各テストで同じ準備コードを繰り返さずに済みます。
- セレクターは getByRole / getByLabel を優先し、**sleep は避けて**要素の状態や expect の待機に任せると、安定したテストになります。
- **test.describe** でグループ化し、テスト名は「何を検証しているか」が分かるようにすると、保守とデバッグが楽になります。
