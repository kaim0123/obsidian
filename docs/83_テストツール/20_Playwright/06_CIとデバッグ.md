# 06 — CIとデバッグ

テストはローカルで動かすだけでなく、**CI（継続的インテグレーション）** 上でプッシュのたびに自動実行することで、リグレッションを早く検知できます。また、テストが失敗したときに「なぜ失敗したか」を素早く突き止めるため、**レポート**や**トレース**、**デバッグ**の使い方を知っておくと役立ちます。この章では、GitHub Actions での実行例、HTML レポートとトレースの見方、よく使うデバッグのコツを解説します。

---

## CI で Playwright を実行する意味

- **プッシュや PR のたびにテストが走る**ことで、本番に近い環境で「画面が壊れていないか」を自動確認できます。
- **誰がいつ変更しても**同じ手順でテストが実行されるため、属人化を防ぎ、品質の底上げになります。
- 失敗した場合は **レポートやトレース** を確認し、原因を特定してから修正する流れにしやすくなります。

Playwright は **ヘッドレス** で実行できるため、CI のような画面のない環境でもそのまま動かせます。また、**複数ブラウザ**（Chromium / Firefox / WebKit）を並列で回す設定も簡単に書けます。

---

## GitHub Actions で Playwright を実行する

`npm init playwright@latest` のときに「Add a GitHub Actions workflow?」で **Yes** を選んでいれば、すでに `.github/workflows/` にワークフローファイルが作成されています。ここでは、その内容をベースに「何をしているか」を説明します。

### ワークフローファイルの例

```yaml
name: Playwright Tests            # ワークフローの名前（GitHub の Actions タブに表示される）

# いつ実行するか
on:
  push:
    branches: [main, develop]     # main または develop に push されたとき
  pull_request:
    branches: [main, develop]     # main または develop への PR が作られたとき

jobs:
  test:
    timeout-minutes: 60           # ジョブ全体の制限時間（60分）
    runs-on: ubuntu-latest        # Ubuntu の最新版で実行する

    steps:
      # ① リポジトリのコードを取得する
      - uses: actions/checkout@v4

      # ② Node.js をセットアップする
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'            # npm のキャッシュを使って高速化

      # ③ パッケージをインストール（npm ci は再現性が高い）
      - name: Install dependencies
        run: npm ci

      # ④ Playwright 用のブラウザをインストール
      #    --with-deps で Linux に必要なシステムライブラリも一緒に入れる
      - name: Install Playwright Browsers
        run: npx playwright install --with-deps

      # ⑤ テストを実行する
      - name: Run Playwright tests
        run: npm run test

      # ⑥ テスト結果のレポートをアップロードする
      #    if: always() → テストが成功しても失敗してもアップロードする
      #    GitHub の Actions → Summary → Artifacts からダウンロードできる
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 30      # 30日間保存する
```

### 各ステップの意味

| ステップ | 役割 |
|----------|------|
| **checkout** | リポジトリのコードをワークフロー実行環境に取得します。 |
| **setup-node** | Node.js（ここでは 20）をセットし、`npm` のキャッシュを有効にします。 |
| **Install dependencies** | **npm ci** で `package-lock.json` に合わせて依存関係をインストールします。本番に近い再現性のため、`npm install` より **npm ci** が推奨されます。 |
| **Install Playwright Browsers** | **npx playwright install --with-deps** で、Playwright 用のブラウザと、Linux 上で動かすために必要なシステムライブラリをインストールします。 |
| **Run Playwright tests** | **npm run test**（＝ `npx playwright test`）でテストを実行します。 |
| **upload-artifact** | テストの**結果**（成功・失敗に関係なく **if: always()**）として、**playwright-report** フォルダをアーティファクトにアップロードします。GitHub の Actions タブから「Summary → Artifacts」でダウンロードし、ローカルで HTML レポートを開いて失敗内容を確認できます。 |

### レポートを必ず生成するには

デフォルトでは、**失敗時**にのみレポートが生成されることがあります。CI では常にレポートを残したい場合、`playwright.config.ts` で **reporter** を設定し、**outputFolder** を指定します。

```typescript
export default defineConfig({
  reporter: [
    // HTML レポートを生成する（ブラウザで開いて見やすいレポート）
    // open: 'never' → CI ではブラウザを開けないので自動で開かない設定
    ['html', { outputFolder: 'playwright-report', open: 'never' }],
    // ターミナルにテスト結果の一覧を表示する
    ['list'],
  ],
});
```

CI では **open: 'never'** にしておくと、ヘッドレス環境で「ブラウザを開く」ことがないため安全です。**list** はターミナルに結果を出す reporter です。

これで、**npm run test** のたびに **playwright-report** が生成され、先ほどの **upload-artifact** でアップロードされます。

---

## HTML レポートの見方

テスト実行後、**playwright-report** フォルダ内の **index.html** をブラウザで開くと、Playwright の HTML レポートが表示されます。

### 主な画面

- **概要**：全テストの成功・失敗数、実行時間、ブラウザ別の結果などが一覧で見られます。
- **失敗したテスト**：失敗したテストをクリックすると、そのテストの**トレース**や**スクリーンショット**、**エラーメッセージ**を確認できます。
- **トレース**：操作のタイムラインを再生できるため、「どの操作のあとに失敗したか」を追いやすくなります。

CI でアーティファクトとしてアップロードした場合は、GitHub の Actions → 該当ジョブ → Artifacts から **playwright-report** をダウンロードし、解凍して **index.html** を開きます。

---

## トレースで失敗原因を追う

**トレース**は、テスト実行中の操作・スクリーンショット・ネットワーク・コンソールログなどを記録したものです。失敗したテストに対して「その時何が起きていたか」をあとから再生して確認できます。

### トレースを記録する

- **通常実行**では、失敗したテストについてのみトレースが保存されることが多いです（設定により異なります）。
- **常にトレースを取る**場合は、設定で有効にします。

```typescript
// playwright.config.ts
export default defineConfig({
  use: {
    trace: 'on', // または 'retain-on-failure'（失敗時のみ保持）
  },
});
```

- **CLI** からトレース付きで実行する例：

```bash
npx playwright test --trace on
```

### トレースの開き方

- **HTML レポート**から失敗したテストを開くと、トレースのリンクや再生ボタンがあります。
- または、トレースファイル（.zip）が **test-results** などに保存されている場合、次のコマンドでビューアを開けます。

```bash
npx playwright show-trace test-results/.../trace.zip
```

トレースビューアでは、タイムライン上で各操作を選び、その時点のスクリーンショットや DOM、ネットワーク、コンソールを確認できます。「どのクリックのあとで画面が変わっていないか」「どの要素が表示されていなかったか」を特定するのに役立ちます。

## デバッグのコツ

### 1. ヘッド付きで実行して目で確認する

```bash
npx playwright test --headed
```

ブラウザが表示された状態でテストが動くため、「どの画面で止まっているか」「どの要素をクリックしようとしているか」を直感的に確認できます。

### 2. UI モードで 1 本ずつ実行する

```bash
npx playwright test --ui
```

テスト一覧から 1 本だけ選んで実行したり、ブレークポイントを置いたりできます。失敗しやすいテストを繰り返し実行して原因を切り分けるときに便利です。

### 3. デバッグモード（PWDEBUG）で一時停止する

```bash
PWDEBUG=1 npx playwright test
```

（Windows の PowerShell では `$env:PWDEBUG=1; npx playwright test`）

実行すると、Playwright の**デバッグ用の UI** が開き、テストは最初の操作の前で一時停止します。そこから「ステップ実行」や「再実行」で、1 操作ずつ追いかけられます。**pick locator** で要素を指定し直すときにも使えます。

### 4. 失敗時だけスクリーンショットとトレースを残す

設定で、失敗時に自動でスクリーンショットとトレースを保存しておくと、CI やローカルどちらでも原因調査が楽になります。

```typescript
export default defineConfig({
  use: {
    // テストが失敗したときだけスクリーンショットを撮る
    screenshot: 'only-on-failure',
    // テストが失敗したときだけ動画を残す（成功時は削除）
    video: 'retain-on-failure',
    // テストが失敗したときだけトレース（操作の記録）を残す
    trace: 'retain-on-failure',
  },
});
```

> **おすすめ設定**: 上記の 3 つを `'retain-on-failure'` にしておくと、普段は容量を使わず、失敗時にだけ調査に必要な情報が残ります。最初に設定しておくと、あとで「なぜ失敗したか分からない」という状況を防げます。

### 5. コンソールログを確認する

テスト中に **page.on('console', ...)** でコンソール出力を拾ったり、アサーションの前に **console.log** で変数の中身を出したりすると、期待値と実際の値のずれを確認しやすくなります。トレースの「Console」タブでも、その時点までのログを確認できます。

---

## この章のまとめ

- **CI**（ここでは GitHub Actions）で、プッシュや PR のたびに **npm ci** → **playwright install --with-deps** → **npm run test** を実行し、**playwright-report** をアーティファクトでアップロードすると、失敗内容をあとから確認しやすくなります。
- **HTML レポート**で成功・失敗の一覧と、失敗時のトレース・スクリーンショットを確認できます。
- **トレース**を有効にしておくと、失敗したテストについて「どの操作のあとに何が起きていたか」を再生して追えます。
- デバッグでは **--headed** / **--ui** / **PWDEBUG=1** を活用し、**screenshot** / **video** / **trace** を失敗時のみ残す設定にすると、調査が楽になります。
