# 02 — プロジェクト作成と最初のテスト

この章では、Playwright のプロジェクトがどのような構成になっているか、テストはどのように実行するか、そして「最初のテスト」のコードが何をしているかを解説します。実際に手を動かしながら、テストの成功・失敗の意味を理解することが目標です。

---

## プロジェクトのフォルダ構成

`npm init playwright@latest` で作成した場合、おおよそ次のような構成になります。

```
my-playwright-project/
├── node_modules/          # 依存パッケージ（npm が自動作成）
├── e2e/                   # テストファイルを置くフォルダ（名前は質問で変更可）
│   └── example.spec.ts    # サンプルテスト
├── playwright.config.ts   # Playwright の設定ファイル
├── package.json           # プロジェクト情報とスクリプト定義
└── package-lock.json      # 依存関係のロックファイル
```

### 各ファイルの役割

| ファイル・フォルダ | 役割 |
|--------------------|------|
| **playwright.config.ts** | 使用するブラウザ、ベースURL、タイムアウト、リトライ回数、レポート出力先などをまとめて設定します。 |
| **e2e/** | テストコード（`*.spec.ts` や `*.spec.js`）を置く場所です。サブフォルダで機能ごとに分けても構いません。 |
| **package.json** | プロジェクト名や `npm run test` で実行するコマンド、依存パッケージの一覧が書かれています。 |

テストファイルの名前は、慣例として **`〇〇.spec.ts`**（または `.spec.js`）とします。Playwright はデフォルトで `*.spec.ts` / `*.spec.js` などをテストとして認識します。

---

## テストの実行コマンド

プロジェクトのルートフォルダ（`package.json` がある場所）で、次のコマンドを実行します。

### 全テストを実行する

```bash
npx playwright test
```

または、`package.json` に `"test": "playwright test"` が定義されていれば：

```bash
npm run test
```

実行すると、`e2e/` 以下のすべての `*.spec.ts` が実行され、結果がターミナルに表示されます。

### ヘッドレスモードとヘッド付きモード

- **ヘッドレスモード（デフォルト）**：ブラウザのウィンドウを表示せず、バックグラウンドで実行します。CI や大量実行に向いています。
- **ヘッド付き（UI が見える）**：実際にブラウザが起動し、操作の様子を目で確認できます。デバッグや学習時に便利です。

ヘッド付きで実行するには：

```bash
npx playwright test --headed
```

### 特定のブラウザだけ実行する

```bash
npx playwright test --project=chromium
npx playwright test --project=firefox
npx playwright test --project=webkit
```

### 特定のテストファイルだけ実行する

```bash
npx playwright test e2e/example.spec.ts
```

### UI モード（対話的に実行・デバッグ）

```bash
npx playwright test --ui
```

ブラウザが開き、テスト一覧から実行するテストを選んだり、トレースやスクリーンショットを確認したりできます。初心者は「何が起きているか」を理解するのに役立ちます。

## 最初のテストの中身を理解する

サンプルとして、次のようなテストが `e2e/example.spec.ts` に含まれていることがあります（内容はバージョンにより多少異なります）。

```typescript
// ① Playwright のテスト機能を読み込む（テストを書くときは必ずこの 1 行が必要）
import { test, expect } from '@playwright/test';

// ② 1 つ目のテスト：ページのタイトルを確認する
test('has title', async ({ page }) => {
  // ③ 指定した URL を開く（読み込み完了まで自動で待つ）
  await page.goto('https://playwright.dev/');
  // ④ ページの <title> に "Playwright" が含まれることを確認
  await expect(page).toHaveTitle(/Playwright/);
});

// ⑤ 2 つ目のテスト：リンクをクリックして遷移先を確認する
test('get started link', async ({ page }) => {
  await page.goto('https://playwright.dev/');
  // ⑥ 「Get started」というリンクを探してクリック
  await page.getByRole('link', { name: 'Get started' }).click();
  // ⑦ URL に "intro" が含まれることを確認（遷移できたか？）
  await expect(page).toHaveURL(/.*intro/);
});
```

### 1 行ずつの意味

- **`import { test, expect } from '@playwright/test';`**  
  Playwright のテストランナーから `test`（テストケースを定義する関数）と `expect`（期待値の検証）を読み込んでいます。

- **`test('has title', async ({ page }) => { ... });`**  
  - `test`：1 つのテストケースを定義します。  
  - `'has title'`：テストの名前（レポートやログに表示されます）。  
  - `async ({ page }) => { ... }`：非同期のテスト関数です。`page` は「1 枚のブラウザのタブ」を表すオブジェクトで、ここに画面操作やアサーションを書きます。

- **`await page.goto('https://playwright.dev/');`**  
  指定した URL に遷移します。`goto` は「ページの読み込みが完了するまで」自動で待ってくれます。

- **`await expect(page).toHaveTitle(/Playwright/);`**  
  現在のページのタイトル（`<title>` の内容）が、正規表現 `/Playwright/` にマッチすることを検証します。マッチすればテスト成功、マッチしなければ失敗です。

- **`await page.getByRole('link', { name: 'Get started' }).click();`**  
  「Get started」というテキストを持つリンク（`role="link"`）を探してクリックします。  
  **03 章** で、`getByRole` や他のセレクターを詳しく扱います。

- **`await expect(page).toHaveURL(/.*intro/);`**  
  現在の URL に `intro` が含まれることを検証します。Get started をクリックした結果、イントロページに遷移したかを確認しているイメージです。

### テストコードの「型」を覚えよう

Playwright のテストは、基本的に**3 ステップ**で書けます。この「型」を覚えると、どんなテストでも書き始められます。

```typescript
import { test, expect } from '@playwright/test';

test('テストの名前', async ({ page }) => {
  // Step 1: 準備 — テストしたいページを開く
  await page.goto('https://example.com/');

  // Step 2: 操作 — ユーザーの行動を再現する（クリック、入力など）
  await page.getByRole('button', { name: '送信' }).click();

  // Step 3: 検証 — 期待する結果になっているか確認する
  await expect(page.getByText('送信完了')).toBeVisible();
});
```

| ステップ | やること | よく使う API |
|----------|---------|-------------|
| **準備** | ページを開く | `page.goto(url)` |
| **操作** | クリック、入力、選択など | `click()`, `fill()`, `check()` |
| **検証** | 期待する状態を確認 | `expect(...).toBeVisible()`, `toHaveText()` |

### なぜ `async` / `await` を書くのか

テストコードには `async` と `await` がたくさん出てきます。これは「ブラウザの操作には時間がかかるので、終わるまで待ってから次に進む」という意味です。

- `await page.goto(...)` → ページの読み込みが終わるまで待つ
- `await page.getByRole(...).click()` → 要素が見つかってクリックできるまで待つ
- `await expect(...).toBeVisible()` → 要素が画面に表示されるまで待つ

**`await` を付け忘れると、待たずに次の行に進んでしまい、テストが不安定になります。** Playwright の操作には、基本的にすべて `await` を付けると覚えてください。

### テストの「成功」と「失敗」

- **成功**：すべての `expect` が期待どおりで、途中で例外が起きなければ、そのテストは「passed」になります。
- **失敗**：どれか 1 つでも `expect` が満たされない、または `page.goto` や `click` などがタイムアウトやエラーになると、そのテストは「failed」になります。エラーメッセージと、失敗した時点のスクリーンショットやトレースがレポートに含まれます。

## 自分で書く「超シンプルなテスト」

理解を深めるために、次のような最小限のテストを自分で書いて実行してみましょう。

1. `e2e` フォルダに `first.spec.ts` というファイルを作成します。
2. 次の内容を貼り付けます。

```typescript
import { test, expect } from '@playwright/test';

test('Google のタイトルに Google が含まれる', async ({ page }) => {
  // 準備：Google のトップページを開く
  await page.goto('https://www.google.com/');

  // 検証：ページのタイトル（ブラウザのタブに表示される文字）に
  // "Google" が含まれていることを確認する
  // /Google/ は正規表現で「Google という文字を含む」という意味
  await expect(page).toHaveTitle(/Google/);
});
```

3. プロジェクトルートで実行します。

```bash
npx playwright test e2e/first.spec.ts
```

「1 passed」のように表示されれば成功です。タイトルの検証を意図的に変えて（例：`/Yahoo/`）、失敗したときのメッセージも確認してみると、アサーションの動きがよく分かります。

## playwright.config.ts の基本

`playwright.config.ts` は、Playwright のテスト全体に関わる設定をまとめたファイルです。「どのブラウザでテストするか」「どの URL を基準にするか」「タイムアウトは何秒か」といった情報を、テストコードの外で一元管理できます。

### 設定ファイルの全体像（コメント付き）

`npm init playwright@latest` で生成される設定ファイルをベースに、よく使う項目をコメント付きで示します。**最初はすべてを理解する必要はありません**。まずは「こういう項目があるんだ」と眺めて、必要になったら該当箇所を変える、という使い方で大丈夫です。

```typescript
// playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

// defineConfig() で設定を定義します。
// TypeScript の補完が効くので、項目名を途中まで打てば候補が出ます。
export default defineConfig({

  // ── テストファイルの場所 ──────────────────────────
  // どのフォルダにあるテストを実行するか。
  // 'e2e' なら e2e/ フォルダ以下の *.spec.ts が対象です。
  testDir: './e2e',

  // ── テスト全体のタイムアウト ──────────────────────
  // 1 つのテスト（test('...', ...) の 1 本）が
  // 何ミリ秒まで実行できるか。超えると自動で失敗扱いになります。
  // 30_000 は 30,000 ミリ秒 = 30 秒です。
  timeout: 30_000,

  // ── アサーション（expect）のタイムアウト ──────────
  // expect(...).toBeVisible() などが「条件を満たすまで待つ」時間。
  // デフォルトは 5 秒。API が遅い環境では少し伸ばすと安定します。
  expect: {
    timeout: 5_000,
  },

  // ── 並列実行 ─────────────────────────────────────
  // true にすると、テストファイル内のテストも並列で実行します。
  // false（デフォルト）だと、ファイル内は上から順に実行されます。
  // ※ ファイル間の並列実行は workers で制御します。
  fullyParallel: true,

  // ── CI 専用の設定 ─────────────────────────────────
  // test.only() を CI で使うとテストが 1 本しか走らなくなるため、
  // CI 環境では forbidOnly: true にして「only を付けたままプッシュ」を防ぎます。
  forbidOnly: !!process.env.CI,

  // ── リトライ回数 ──────────────────────────────────
  // テストが失敗したとき、自動で何回まで再実行するか。
  // CI では 2 回（一時的な不安定対策）、ローカルでは 0 回が一般的です。
  retries: process.env.CI ? 2 : 0,

  // ── 並列ワーカー数 ────────────────────────────────
  // テストファイルをいくつまで同時に実行するか。
  // undefined（デフォルト）は CPU コア数の半分。
  // CI では 1 に絞ると安定しやすいです。
  workers: process.env.CI ? 1 : undefined,

  // ── レポーター ────────────────────────────────────
  // テスト結果をどの形式で出力するか。
  // 'html' は HTML ファイルを生成し、ブラウザで見やすいレポートになります。
  reporter: 'html',

  // ── use: すべてのテストに共通する設定 ─────────────
  use: {
    // baseURL を設定すると、テスト内で page.goto('/login') のように
    // 相対パスが使えるようになります。
    // 自分のアプリをテストするなら、ここに開発サーバーの URL を入れます。
    baseURL: 'http://localhost:3000',

    // ブラウザのウィンドウサイズ（幅 × 高さ）。
    // モバイル表示を試したいときは { width: 375, height: 812 } など。
    // viewport: { width: 1280, height: 720 },

    // 操作（click, fill など）のタイムアウト。
    // 要素が操作可能になるまで待つ最大時間です。
    // actionTimeout: 15_000,

    // トレース（操作の録画のようなもの）をいつ取るか。
    // 'on-first-retry' なら、リトライ時にだけ記録します。
    // 失敗原因の調査に非常に便利です。
    trace: 'on-first-retry',

    // 失敗時にスクリーンショットを撮る設定。
    // screenshot: 'only-on-failure',
  },

  // ── projects: どのブラウザで実行するか ─────────────
  // 配列で複数ブラウザを指定できます。
  // 学習中は chromium だけ残して他をコメントアウトすると実行が速くなります。
  projects: [
    {
      name: 'chromium',
      use: { ...devices['Desktop Chrome'] },
    },
    // ↓ 不要なときはコメントアウトで OK
    // {
    //   name: 'firefox',
    //   use: { ...devices['Desktop Firefox'] },
    // },
    // {
    //   name: 'webkit',
    //   use: { ...devices['Desktop Safari'] },
    // },

    // ↓ モバイルのテストをしたいときは追加
    // {
    //   name: 'Mobile Chrome',
    //   use: { ...devices['Pixel 5'] },
    // },
  ],

  // ── webServer: テスト前に開発サーバーを自動起動 ────
  // テスト実行時に、指定したコマンドで開発サーバーを起動し、
  // 起動完了（URL にアクセスできる状態）を待ってからテストを始めます。
  // Next.js や Vite などのプロジェクトで便利です。
  // webServer: {
  //   command: 'npm run dev',
  //   url: 'http://localhost:3000',
  //   reuseExistingServer: !process.env.CI,
  // },
});
```

### よく変更する項目ベスト 5

初心者がまず触ることになる項目をまとめます。

| 項目 | 何を変えるか | 例 |
|------|-------------|-----|
| **testDir** | テストファイルのフォルダ名 | `'./tests'` や `'./e2e'` |
| **use.baseURL** | テスト対象アプリの URL | `'http://localhost:3000'` |
| **projects** | テストするブラウザ | chromium だけにする、モバイルを追加する |
| **timeout** | テスト 1 本の制限時間 | 遅い環境なら `60_000`（60 秒）に伸ばす |
| **retries** | 失敗時のリトライ回数 | CI で `2`、ローカルで `0` |

### 設定を変えたらどうなるか — 実験してみよう

設定の効果を実感するために、次のような実験をしてみると理解が深まります。

1. **projects を chromium だけにする** → テスト実行が 3 分の 1 程度の時間で終わる。
2. **timeout を 3_000（3 秒）にする** → 遅いページのテストがタイムアウトで失敗する。
3. **use.baseURL を設定して、テスト内で `page.goto('/')` と書く** → 相対パスで遷移できる。

最初のうちはデフォルトのままで問題ありません。必要に応じて「使うブラウザを chromium だけにする」「baseURL を変える」程度から触っていくとよいです。

---

## この章のまとめ

- プロジェクトは **playwright.config.ts** と **e2e/** 配下の **\*.spec.ts** が中心です。
- テスト実行は **`npx playwright test`**（または **`npm run test`**）で、**`--headed`** でブラウザを表示、**`--ui`** で対話モードになります。
- テストは **`test('名前', async ({ page }) => { ... })`** で 1 本ずつ定義し、**`page.goto`** で遷移、**`expect(page).toHaveTitle(...)`** などで期待値を検証します。
- サンプルを少しずつ書き換えたり、意図的に失敗させたりすることで、「何が成功で何が失敗か」を体感できます。
