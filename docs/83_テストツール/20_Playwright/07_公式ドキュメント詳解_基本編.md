## 2. Intro / Installation — Playwright の前提とインストール

### 2-1. 何ができるツールか（おさらい）

公式 Intro では、Playwright を次のような観点で紹介しています。

- **複数ブラウザを 1 つの API で操作できる**
  - Chromium / Firefox / WebKit（Safari エンジン）をサポート
  - 各ブラウザのヘッドレス・ヘッドフル実行が可能
- **マルチプラットフォーム**
  - Windows / macOS / Linux で同じテストが動く
- **自動待機（auto-waiting）と安定したロケーター**
  - 要素の表示・有効化などを Playwright が自動で待ってくれる
  - `getByRole` など、アクセシビリティ情報を使った安定したロケーターを推奨
- **高速・並列実行**
  - テストをワーカー単位で並列実行
  - ブラウザコンテキストを分けてテスト同士を隔離

01〜02 章で触れた内容を、公式は「売り」の観点で整理していると捉えると読みやすいです。

### 2-2. インストールの基本パターン

公式の推奨パターンは次の 2 つです。

- **1. 既存プロジェクトに追加する**
  - 例: すでに Node.js プロジェクトがある場合
  - `npm install -D @playwright/test`
  - その後、ブラウザバイナリをインストール:  
    `npx playwright install`

- **2. Playwright プロジェクトを新規作成する**
  - 例: E2E 用に専用リポジトリを作る場合
  - `npm init playwright@latest`
  - 対話形式で以下を聞かれる（最新版では質問内容が多少変わる可能性あり）:
    - TypeScript か JavaScript か
    - テスト例を生成するか
    - GitHub Actions 用の CI 設定ファイルを生成するか

どちらの方法でも、最終的には次のような構成になります。

- `playwright.config.ts`（または `.js`）: Playwright Test の設定
- `tests/` ディレクトリ: テストファイル群
- `tests-examples/` など: サンプルテスト（生成を選んだ場合）

## 3. Writing tests — テストファイルの構造と基本パターン

`Writing tests` は、**Playwright Test ランナーでテストを書くときの基本ルール**を説明するページです。ここでは、実務でよく使う部分に絞って整理します。

### 3-1. 最小のテスト例

公式が紹介している最小例は次のような形です。

```ts
import { test, expect } from '@playwright/test';

test('has title', async ({ page }) => {
  await page.goto('https://playwright.dev/');
  await expect(page).toHaveTitle(/Playwright/);
});
```

- `test(...)` が 1 つのテストケース
- `{ page }` は Playwright Test が用意してくれる **フィクスチャ**（テストごとに新しいブラウザインスタンスを用意してくれる仕組み）
- `expect(...)` で結果を検証

### 3-2. `test.describe` でテストをグルーピング

関連するテストは `test.describe` でまとめることが推奨されています。

```ts
import { test, expect } from '@playwright/test';

test.describe('認証フロー', () => {
  test('ログインできること', async ({ page }) => {
    // ...
  });

  test('間違ったパスワードでエラーメッセージが出ること', async ({ page }) => {
    // ...
  });
});
```

- 公式ドキュメントでも、**1 つの機能（例: 認証）を 1 つの `describe` にまとめる**書き方が多用されています。
- `test.describe` レベルで `beforeEach` などを設定すると、同じ前処理を共有できます。

### 3-3. `beforeEach` / `afterEach` で共通処理を整理

`Writing tests` では、重複コードを減らすために **フック関数**を使うことが推奨されています。

```ts
test.describe('ダッシュボード', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('https://example.com/login');
    await page.getByLabel('ユーザー名').fill('user');
    await page.getByLabel('パスワード').fill('password');
    await page.getByRole('button', { name: 'ログイン' }).click();
  });

  test('ウィジェットが表示されている', async ({ page }) => {
    await expect(page.getByRole('heading', { name: 'ダッシュボード' })).toBeVisible();
  });
});
```

- すべてのテストで共通する「ログイン処理」を `beforeEach` にまとめることで、**各テスト本体は「何を確認するか」に集中**できます。
- 公式のサンプルやベストプラクティスでも、**setup（準備）と assertion（検証）をはっきり分ける**書き方が強く推奨されています。

### 3-4. 並列実行とテストの独立性

公式ドキュメントでは、**テストは原則として互いに独立しているべき**と説明されています。

- Playwright Test はデフォルトでテストを並列実行する
- そのため、**テスト間で状態（DB / ファイル / セッションなど）を共有する前提で書かない**
- 必要な状態は、各テストの `beforeEach` やフィクスチャで毎回準備する

これにより、

- 「先に実行されたテストがデータを作ってくれないと落ちる」
- 「テストの実行順を変えたら失敗する」

といった問題を防げます。

## 4. Test assertions — アサーションの考え方と自動待機

`Test assertions` ページは、Playwright 独自の **「自動待機するアサーション」**の仕組みを詳しく説明しています。

### 4-1. 自動待機（auto-waiting）の特徴

Playwright の `expect` は、**条件が満たされるまで一定時間リトライ**してくれます。

```ts
await expect(page.getByRole('alert')).toHaveText('保存しました');
```

この 1 行で、Playwright は次のようなことを内部で行います。

- `getByRole('alert')` で要素を探す
- 要素が見つかるまで一定時間待機
- 見つかったら、そのテキストが `'保存しました'` になるまでリトライ
- 規定のタイムアウト（デフォルト 5 秒）が過ぎたら失敗

**手で `waitForTimeout(1000)` のような固定待機を書く必要は本来ない**、というのが公式の主張です。

### 4-2. ロケーター用と値用の matcher

`expect` は **対象によって使える matcher が少し異なる**点に注意します。

- `expect(page.locator(...))` に対して使う matcher
  - `toBeVisible` / `toHaveText` / `toHaveCount` / `toBeEnabled` など
- `expect(number)` や `expect(string)` など値に対して使う matcher
  - `toBe` / `toEqual` / `toBeGreaterThan` / `toContain` など

公式ドキュメントでは、この 2 つを分けて説明しています。  
例えば「行数が 1 以上であること」を確認したい場合は次のようにします。

```ts
const rows = page.locator('table tbody tr');
const count = await rows.count();        // number 型
expect(count).toBeGreaterThan(0);        // 数値用 matcher
```

### 4-3. ソフトアサーション（soft assertions）

`Test assertions` では、**テストを途中で止めずに複数の失敗をまとめて報告する**「ソフトアサーション」にも触れています。

```ts
test('複数フィールドをまとめて検証', async ({ page }) => {
  await page.goto('https://example.com/profile');

  await expect.soft(page.getByLabel('名前')).toHaveValue('山田 太郎');
  await expect.soft(page.getByLabel('メールアドレス')).toHaveValue('taro@example.com');
});
```

- `expect.soft` を使うと、1 つ目のアサーションが失敗してもテストは続行し、**最後にまとめてレポート**してくれます。
- フォームの初期値チェックなど、「多少ズレていても全部確認したい」ケースに便利です。

### 4-4. `expect.poll` で「ポーリング」する

API のレスポンスや DB の状態など、**ページ外の値を一定間隔で再取得して検証したい**ときには `expect.poll` を使います。

```ts
await expect.poll(async () => {
  const response = await fetch('https://api.example.com/status');
  const json = await response.json();
  return json.state;
}).toBe('ready');
```

- コールバック内の処理を何度も実行し、その戻り値に対して matcher を適用
- タイムアウトまでに `state === 'ready'` になれば成功

## 5. Locators — ロケーターの考え方と公式の推奨

`Locators` ページでは、「**どうやって安定した要素指定を行うか**」が詳しく説明されています。

### 5-1. ロケーターとは何か

Playwright のロケーターは、「**まだ実在しないかもしれない要素への参照**」と考えるとわかりやすいです。

```ts
const saveButton = page.getByRole('button', { name: '保存' });
await saveButton.click();
```

- ここで `saveButton` は「保存ボタンになりそうなもの」を指しているだけで、まだ DOM 上に現れていないかもしれません。
- `click()` するときに、Playwright が要素の出現や有効化を自動で待ちます。

### 5-2. 公式推奨のロケーター優先順位

公式ドキュメントでは、だいたい次の順でロケーターを選ぶことが推奨されています。

1. **`getByRole` / `getByLabel` / `getByPlaceholder` など、アクセシビリティ・意味ベース**
2. **`data-testid` のようなテスト専用属性**
3. CSS セレクター（できるだけ安定している id / class を利用）
4. XPath は最後の手段（なるべく避ける）

例:

```ts
// 最優先: ユーザーに見えるラベルやロールで取る
page.getByRole('button', { name: '保存' });
page.getByLabel('パスワード');

// 次点: テスト専用属性
page.getByTestId('user-row');

// どうしても必要なとき: CSS
page.locator('.user-list .user-row');
```

この方針に従うと、**UI 変更に強く、読みやすいテスト**になりやすいです。

### 5-3. `locator` と `page` API の違い

公式では、`page.click('selector')` ではなく `page.locator('selector').click()` を推奨しています。

- `page.click('button:has-text("保存")')`
  - 古い書き方。1 回限りの操作。
- `page.locator('button:has-text("保存")').click()`
  - ロケーターとして保持でき、再利用・待機の制御などがやりやすい。

03 章でも説明していますが、「**まず locator を作り、その上で操作・アサーションを行う**」のが公式の基本スタイルです。

## 6. Best practices — 公式が勧めるテスト設計の考え方

`Best practices` ページにはさまざまなトピックがありますが、ここでは特に重要なポイントを抜粋します。

### 6-1. ユーザー視点でテストを書く

公式の強いメッセージの 1 つは、

> 実装の詳細ではなく、**ユーザーが見る振る舞い**をテストせよ

という考え方です。

- DOM の構造や内部クラス名ではなく、「ボタンが押せるか」「メッセージが表示されるか」を確認する
- そのために `getByRole` / `getByText` などのロケーターを優先する

これにより、実装のリファクタ（コンポーネント分割・CSS フレームワーク変更など）にテストがひきずられにくくなります。

### 6-2. 1 テスト 1 シナリオ

公式では、1 つのテストに詰め込みすぎず、**「1 テスト = 1 つのユーザーストーリー」**を意識することが推奨されています。

- 悪い例:
  - 「ログインして → 商品を検索して → カートに入れて → 決済して → ログアウトする」を 1 本のテストで実行
- 良い例:
  - 「ログインできること」を 1 本
  - 「商品検索ができること」を 1 本
  - 「カートに追加できること」を 1 本

この方針にすると、

- どの機能が壊れているのかを特定しやすい
- テストが落ちたときの調査範囲が小さくて済む

というメリットがあります。

### 6-3. Page Object Model / Fixtures で再利用性を上げる

大規模化したときに公式が特に推奨するのが **Page Object Model（POM）** と **テストフィクスチャ**です。

- **POM**
  - 画面ごと・コンポーネントごとにクラスや関数を切り出し、
    - `LoginPage.loginAs(user)` のような「意味のある名前のメソッド」にする
  - テストコードからは「何をしたいか」だけが見える
- **Fixtures**
  - `test.extend` で「ログイン済みの page」などをフィクスチャとして提供
  - テスト側は `{ page, loggedInUser }` のように受け取るだけ

05 章で詳しく扱っている内容ですが、「なぜそうするのか？」という背景は `Best practices` にも詳しく書かれています。

## 7. どの公式ページをどう読むとよいか

最後に、「公式ドキュメントをどの順番・観点で読むと理解しやすいか」のガイドを簡単にまとめます。

- **Step 1: `Intro` / `Installation`**
  - すでに環境構築済みであっても、一度目を通して「Playwright が何を大事にしているか」を確認する。
- **Step 2: `Writing tests`**
  - `test.describe` / `beforeEach` / フィクスチャの考え方を公式サンプルで確認。
  - 自分のプロジェクトの書き方と見比べて、ギャップがあれば寄せていく。
- **Step 3: `Test assertions`**
  - どの matcher をどの対象に使うか、`expect.soft` や `expect.poll` など「知らないと損」な機能を把握する。
- **Step 4: `Locators`**
  - 今使っているセレクターが公式の推奨順に沿っているかをチェックし、`getByRole` などに置き換えられないか検討する。
- **Step 5: `Best practices`**
  - 既存テストの設計と照らし合わせ、「将来的に困りそうなパターン」がないかを確認する。
