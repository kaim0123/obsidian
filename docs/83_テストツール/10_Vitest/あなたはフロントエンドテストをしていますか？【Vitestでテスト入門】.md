## 詳しい要約

**テーマ：Vitest + Testing Library + MSW による React フロントエンドテスト入門**

なぜフロントエンドテストが必要か、テストの 4 分類とコストのトレードオフを説明したうえで、ポケモン ID を入力して PokeAPI から取得・表示する「ポケモンファインダー」を題材に、初期レンダリング・API 取得成功・エラー表示の 3 つのテストとカバレッジ計測をハンズオンで実装する。

---

### なぜフロントエンドテストをするのか

- 一言でいえば **プロジェクトの保守性が上がる** から。
- コンポーネントやコード量が増えると、別の箇所の修正で元々動いていた部分が壊れることがある。自動テストがあれば **すぐに検知** できる。
- ログイン・API 呼び出し・決済などを毎回手動でブラウザ確認する手間をコードに任せられる。
- テストを前提にすると **責務の分離** を意識した、きれいなコンポーネント設計につながる。開発者の精神的負担も減る。
- 小さな個人開発なら必須ではない。

### テストの種類（4 分類）

| 種類 | 内容 | 例 |
|---|---|---|
| スタティックテスト | 実行前に検出する静的チェック | ESLint、Prettier、TypeScript の型 |
| ユニットテスト（単体） | 関数・1 コンポーネント単位 | Vitest |
| インテグレーションテスト（結合） | 複数コンポーネントや API との組み合わせ | Vitest + MSW |
| E2E テスト | アプリ全体を通した動作 | Playwright、Cypress |

- 上に行くほど導入コストは高いが、合格したときの **信頼性** も上がる。コストとのトレードオフで、必要な箇所だけ書くバランスが重要。
- 今回は Jest ではなく **Vitest** と Testing Library を使い、単体＋結合テストを扱う。

### セットアップ

1. テンプレートをクローンして `npm i`、`npm run dev`（5173 番）で起動。
2. `npm i -D vitest @testing-library/jest-dom happy-dom @testing-library/react @testing-library/user-event`
3. `vite.config.ts`：先頭に `/// <reference types="vitest" />`、`test: { globals: true, environment: "happy-dom", setupFiles: "./vitest-setup.ts" }`
   - **happy-dom** は以前の jsdom より高速。
4. `package.json` の scripts に `"test": "vitest"`。
5. `vitest-setup.ts` に `import "@testing-library/jest-dom/vitest"`。これで `toBeInTheDocument` などリッチなアサーションが使える。
6. `tsconfig.json` の `types` に `vitest/globals`、`include` に `vitest-setup.ts` を追加しないと型が当たらない。

### テスト 1：初期レンダリング

- `src/tests/PokemonFinder.test.tsx` に `describe` / `test` / `expect` で記述し、`render(<PokemonFinder />)` する。
- `screen.getByText("ポケモンファインダー")`、`getByRole("button")`、`getByPlaceholderText("ポケモンのIDを入力")` を `toBeInTheDocument()` で検証。
- ボタンが複数あると `getByRole` は失敗する → 第 2 引数 `{ name: "ポケモンを見つける" }` で一意に特定。
- **わざと失敗させてテストが正しく機能するか確認する** のも大事。

### テスト 2：API 取得（MSW でモック）

- 外部 API と組み合わせた結合テストには **MSW（Mock Service Worker）** でテスト用 API を用意する。
- `tests/mocks/handlers.ts` に PokeAPI のエンドポイントのハンドラを書き、ID 25（ピカチュウ）の `name` と `sprites.front_default` を返す。存在しなければ 404 `Not Found`。
- `server.ts` で `setupServer(...handlers)` を export。
- `vitest-setup.ts` に `beforeAll(() => server.listen())`、`afterAll(() => server.close())`、`afterEach(() => server.resetHandlers())`。
  - `resetHandlers` は、POST/DELETE などでレスポンスが変わっても各テストを同じ状態で始めるため。
- テスト本体（async）：`userEvent.setup()` → `user.type(input, "25")` → `user.click(button)` → `await screen.findByText("ピカチュウ")`、`getByRole("img")` に `toHaveAttribute("src", ...)` と `toHaveAttribute("alt", "ピカチュウ")`。
- ハマりどころ：返却データにキー（`25`）が残ると `sprites.front_default` が undefined になる → スプレッド構文で展開して返す。

### テスト 3：エラー表示

- ハンドラを `:id` の動的パラメータ対応にし、`params.id` でデータを引いて、あれば 200、なければ 404 を返す。
- 存在しない ID（2000）を入力してクリック →「ポケモンデータが見つかりません」が表示されることを確認。
- テストを起動したまま開発し、常に合格しているかを見ながら進めるとよい。

### カバレッジ

- `npm i -D @vitest/coverage-v8`、scripts に `"coverage": "vitest run --coverage"`。
- ファイルごとのカバー率が表示され、PokemonFinder.tsx は 100%。不要なファイルは設定で除外できる。
- 100% を目指す必要はなく、「60〜70% 以上」のようなチームルールの目安として使う。

### まとめ

- フロントエンドテストの価値は、修正による破壊を即検知できる **保守性** にある。
- テストは静的・単体・結合・E2E の 4 種類で、コストと信頼性のトレードオフを考えて選ぶ。
- Vitest + Testing Library で DOM を検証し、外部 API は MSW でモックして成功・失敗の両ケースを書く。
- カバレッジはテストの充足度の目安で、100% は必須ではない。
