# 06 — カバレッジと UI・ブラウザモード

この章では、テストの網羅率を測定する **カバレッジ**、ブラウザでテスト結果を可視化する **Vitest UI**、そして実ブラウザでテストする **Browser Mode** を解説します。

---

## カバレッジとは

**カバレッジ（Coverage）** は「テストがソースコードのどの部分を実行したか」の割合を示す指標です。一般に次の 4 種類があります。

| 種別 | 意味 |
|------|------|
| **Statements** | 文（statement）のうち実行された割合 |
| **Branches** | `if` / `?:` などの**分岐**のうち、両側通過した割合 |
| **Functions** | 関数のうち呼ばれた割合 |
| **Lines** | 行のうち実行された割合 |

**カバレッジ 100% は「すべての行が動いた」を意味するだけで、「バグがない」ことは保証しません**。あくまで「テストの空白地帯」を見つけるツールとして使います。

---

## カバレッジを取る

### インストール

Vitest 標準のカバレッジは V8 のものを使います。

```bash
npm install -D @vitest/coverage-v8
```

> Istanbul を使いたい場合は `@vitest/coverage-istanbul` を入れて `provider: 'istanbul'` を指定します。`v8` のほうが起動は速いですが、ソースマップ周りで違いが出ることがあります。迷ったら **`v8`** で OK。

### 実行

```bash
npx vitest run --coverage
```

`package.json` のスクリプトにしておくと便利。

```json
{
  "scripts": {
    "coverage": "vitest run --coverage"
  }
}
```

### 出力例

```
 % Coverage report from v8

------------------|---------|----------|---------|---------|---------------------
File              | % Stmts | % Branch | % Funcs | % Lines | Uncovered Line #s
------------------|---------|----------|---------|---------|---------------------
All files         |   85.71 |    66.66 |    75.0 |   85.71 |
 src              |  100.00 |   100.00 |  100.00 |  100.00 |
  math.ts         |  100.00 |   100.00 |  100.00 |  100.00 |
 src/utils        |   71.42 |    50.00 |   50.0 |   71.42 |
  format.ts       |   71.42 |    50.00 |   50.0 |   71.42 | 12-15
------------------|---------|----------|---------|---------|---------------------
```

`Uncovered Line #s` の列に「テストで通っていない行」が表示されます。**この数字をたどって「なぜ通っていないか」を確認する**のが、カバレッジを使う本来の目的です。

### HTML レポート

`coverage/index.html` を開くと、ファイルごとに「実行されなかった行」がハイライト表示されます。CI では `coverage/lcov.info` を成果物として保存し、Codecov などにアップする運用が一般的。

```ts
// vitest.config.ts
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',
      reporter: ['text', 'html', 'lcov'],   // text=コンソール html=ローカル lcov=CI連携
      reportsDirectory: './coverage',
      include: ['src/**/*.{ts,tsx}'],
      exclude: ['src/**/*.test.{ts,tsx}', 'src/**/types.ts', 'src/main.tsx'],
    },
  },
});
```

### しきい値で「下限」を強制する

```ts
coverage: {
  thresholds: {
    statements: 80,
    branches:   75,
    functions:  80,
    lines:      80,
  },
}
```

しきい値を割ると `vitest run --coverage` が**失敗扱い**になります。CI に組み込めば、回帰を機械的に防げます。

> ただし**数値だけ追うと「数字を上げるためだけのテスト」**が増えがちです。「分岐が増えたら必ずテストも増やす」というレビュー文化のほうが本質的に効きます。

---

## カバレッジの落とし穴

### 1. 「100% = 安全」ではない

すべての行を「通過した」だけで、**境界値や仕様の網羅**は別問題です。`if (x > 0)` の `x === 1` も `x === 1_000_000` も同じ 1 行を通れば 100% に見えます。

### 2. 自動生成コードや型定義は除外する

`exclude` にビルド成果物・型定義・エントリポイントなどを入れて、**意味のあるカバレッジ**だけを集計するようにします。

### 3. 「カバレッジを上げるテスト」は本末転倒

`expect` のないテスト、関数を呼ぶだけのテストは数字を上げるが価値はありません。**「壊れたら検知できるか」**を基準に書くこと。

## Vitest UI — ブラウザ上でテスト結果を見る

`@vitest/ui` を使うと、ブラウザでテスト結果を視覚的に確認できます。

### インストールと起動

```bash
npm install -D @vitest/ui
npx vitest --ui
```

ブラウザが開き、左に「テスト一覧（パス・ファイル・ケース）」、右に「コードと結果」が表示されます。

### できること

- ファイル単位 / ケース単位での実行・再実行
- 失敗したテストの**コードのどこで落ちたか**をハイライト表示
- **モジュール依存グラフ**の可視化
- スナップショット差分の表示
- カバレッジレポートの埋め込み表示

ローカル開発で「いまどのテストが落ちてるんだっけ？」を確認したいときに便利です。CI ではなく、開発者個々の作業効率化のためのツールという位置づけです。

## DOM テスト環境 — `jsdom` / `happy-dom`

ブラウザ API（`window`, `document`, `localStorage` など）を使うコードは、`environment` を指定してテストします。

```ts
// vitest.config.ts
export default defineConfig({
  test: {
    environment: 'jsdom',   // または 'happy-dom'
  },
});
```

### `jsdom` vs `happy-dom`

| | jsdom | happy-dom |
|---|---|---|
| 由来 | 老舗。Jest のデフォルト | Vitest 系で人気の新興 |
| 速度 | やや遅め | **より高速** |
| 互換性 | 安定。多くの CSS / DOM API | 最近の API 追従が速い |
| サイズ | 大きめ | 小さい |

**迷ったら `happy-dom`**。問題が起きるライブラリがあれば `jsdom` に切り替えます。インストールも忘れず：

```bash
npm install -D happy-dom
# または
npm install -D jsdom
```

### ファイルごとに環境を切り替える

```ts
// @vitest-environment jsdom
import { ... } from 'vitest';
```

ファイル先頭のコメントで指定すると、そのファイルだけ環境を変えられます。**サーバーサイドのコードは Node 環境、コンポーネントは jsdom**、と使い分けるのに便利。

## Browser Mode — 実ブラウザでテストする

jsdom / happy-dom は便利ですが、**「実際のブラウザの挙動と微妙に違う」**問題が時々起きます。レイアウト計算、Web Animations、クリップボード API、Service Worker など、ブラウザネイティブの機能が必要なときは **Browser Mode** を使います。

### 仕組み

Vitest が **Playwright や WebdriverIO 経由で実ブラウザを起動**し、その中でテストを実行します。E2E ではなく**「コンポーネントテストを本物のブラウザで」**走らせるイメージです。

### セットアップ例（Playwright + Chromium）

```bash
npm install -D @vitest/browser playwright
npx playwright install chromium
```

```ts
// vitest.config.ts
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    browser: {
      enabled: true,
      provider: 'playwright',
      instances: [
        { browser: 'chromium' },
        // { browser: 'firefox' },
        // { browser: 'webkit' },
      ],
    },
  },
});
```

### 実行

```bash
npx vitest --browser
```

ブラウザが立ち上がり、その中でテストが走ります。`page.screenshot()` などの Playwright 系 API も使えます。

### Browser Mode を使う判断基準

| 状況 | 適した方法 |
|------|----------|
| 純粋なロジック | Node 環境 |
| 軽量な DOM 操作 | jsdom / happy-dom |
| **CSS のレイアウトに依存する挙動** | Browser Mode |
| **キーボード/マウスのネイティブな振る舞い**を厳密に | Browser Mode |
| **クロスブラウザ確認**まで含めたい | Browser Mode |
| ページ遷移を含む E2E | **Playwright（独立したテスト）** |

Browser Mode は「**Vitest と同じ書き味で、本物のブラウザで動かしたい**」というニッチを埋める機能です。E2E の代わりではありません。

## 型のテスト — `vitest --typecheck`

TypeScript の **型レベルの挙動** をテストする機能もあります。

```ts
import { expectTypeOf, it } from 'vitest';

it('add は number を返す', () => {
  expectTypeOf(add(1, 2)).toEqualTypeOf<number>();
  expectTypeOf(add).parameter(0).toEqualTypeOf<number>();
});
```

`vitest --typecheck` で実行すると、`tsc` を内部で走らせて型レベルの検証も行います。**ライブラリ作者**や**型ユーティリティの開発者**には特に有用です。

---

## レポーター（出力フォーマット）

Vitest のテスト出力はカスタマイズできます。

```bash
npx vitest run --reporter=verbose --reporter=junit --outputFile=test-results.xml
```

主なレポーター：

| 名前 | 用途 |
|------|------|
| `default` | 通常の見やすい出力 |
| `verbose` | 各ケース 1 行で詳細表示 |
| `dot` | `....F..` のように 1 文字ずつ |
| `junit` | CI 用 XML（GitHub Actions の test summary など） |
| `json` | プログラムから処理しやすい |
| `tap` / `tap-flat` | TAP プロトコル |
| `html` | HTML レポート（`@vitest/ui` が必要） |

複数同時指定もできます。CI では `default` + `junit` の組み合わせがよくあるパターンです。

---

## この章のまとめ

- **カバレッジ**は「テストの空白地帯」を見つける道具。100% を目標化しない。
- 実務では **`@vitest/coverage-v8`** + **しきい値** + **HTML/lcov レポート** が定番。
- ローカルでは **`vitest --ui`** が見やすい。
- DOM テストは **`happy-dom`** がデフォルトとして使いやすい。重い依存があるときだけ jsdom。
- ブラウザ固有の挙動を確認したいときは **Browser Mode**（Playwright 連携）。
- 型まで検証したいなら **`expectTypeOf`** + `--typecheck`。
