# 07 — 実践パターンとベストプラクティス

ここまでで文法面はおおよそ押さえました。この章では「実プロジェクトでどう書くと壊れにくく、読みやすいか」という **設計・運用** の話を扱います。

---

## テストの 3 層構造：AAA パターン

ほとんどのテストは、次の 3 フェーズで書くと読みやすくなります。

```ts
it('割引が適用された合計金額を返す', () => {
  // Arrange — 準備
  const cart = new Cart();
  cart.add({ id: 1, price: 1000 });
  cart.add({ id: 2, price: 2000 });

  // Act — 実行
  const total = cart.totalWithDiscount(0.1);

  // Assert — 検証
  expect(total).toBe(2700);
});
```

- **Arrange（準備）**：入力となるデータや状態を用意する
- **Act（実行）**：テスト対象の**1 つの操作**だけを行う
- **Assert（検証）**：結果を `expect` で確認する

ブランク行で区切るだけでも読みやすくなります。Act が 2 つ以上あると「何のテストか」が曖昧になりがちなので、基本は **Act は 1 つ**に絞ります。

---

## 1 テスト 1 アサート？複数アサート？

昔は「1 テスト 1 アサート」がよく言われましたが、実務では **「1 つの振る舞い」を複数の `expect` で表現**しても問題ありません。

```ts
it('ユーザー登録に成功すると user が作られ、メールが送られる', () => {
  const result = registerUser({ email: 'a@example.com' });

  expect(result.id).toBeDefined();
  expect(result.email).toBe('a@example.com');
  expect(sendMail).toHaveBeenCalledOnce();
});
```

**ガイドライン**：
- 1 つの `it` の中で検証するのは **1 つの「成功条件」**。
- 「違う状況」の検証は**別の `it`** に分ける。例：正常系とエラー系。
- `it` の名前で「何を保証しているか」が読めるなら OK。

## フック (`beforeEach` など) の使いどころ

### 共通セットアップはまとめる

```ts
describe('Cart', () => {
  let cart: Cart;
  let priceList: PriceList;

  beforeEach(() => {
    priceList = new PriceList([{ id: 1, price: 100 }]);
    cart = new Cart(priceList);
  });

  it('空の状態では合計 0', () => {
    expect(cart.total()).toBe(0);
  });

  it('追加すると合計が増える', () => {
    cart.add(1);
    expect(cart.total()).toBe(100);
  });
});
```

**`beforeEach` で毎回新しいインスタンスを作る**ことで、テスト間の独立性が保たれます。

### `beforeAll` は「重い」ときだけ

DB 接続、ブラウザ起動、ファイル読み込みなど、**本当に一度でいい**ものだけに絞ります。状態を共有するほど「前のテストのせいで次が失敗する」バグが混入しやすくなります。

### フックを使いすぎない

`beforeEach` に条件分岐や 10 行以上のセットアップを入れると読みにくくなります。そのときは **ビルダー関数 / ファクトリー** に切り出すほうがよいです。

```ts
// test-helpers/cart.ts
export function makeCart(items: Item[] = []) {
  const cart = new Cart();
  items.forEach(item => cart.add(item));
  return cart;
}

// テスト側
it('割引適用', () => {
  const cart = makeCart([{ id: 1, price: 1000 }, { id: 2, price: 2000 }]);
  expect(cart.totalWithDiscount(0.1)).toBe(2700);
});
```

「このテストが何を入力にしているか」が一目でわかるようになります。

## テストフィクスチャ — `test.extend`

同じセットアップを複数ファイルで共有したいとき、Vitest 固有の強力な仕組みが **`test.extend`** です。

```ts
// test-fixtures.ts
import { test as base } from 'vitest';

type Fixtures = {
  user: User;
  db: Database;
};

export const test = base.extend<Fixtures>({
  db: async ({}, use) => {
    const db = await Database.connect();
    await use(db);              // ← ここでテスト本体が実行される
    await db.disconnect();      // ← 終了後に後片付け
  },
  user: async ({ db }, use) => {
    const user = await db.createUser({ name: 'Alice' });
    await use(user);
    await db.deleteUser(user.id);
  },
});
```

使う側：

```ts
import { expect } from 'vitest';
import { test } from '../test-fixtures';

test('ユーザーが存在する', ({ user }) => {
  expect(user.name).toBe('Alice');
});
```

- **依存関係の順序**（`user` は `db` を必要とする）が自動解決される。
- **使われたテストにだけ**フィクスチャが適用されるので、不要な初期化が走らない。
- Playwright のフィクスチャと思想が同じなので、両方使う人は学習コストが低い。

`beforeEach` + 関数 よりもテスト本体がスッキリします。

## テストの独立性を保つ

テストは**順序に依存せず、個別に実行しても通る**べきです。よくある汚染源：

- **グローバル状態**：シングルトン、モジュールレベルの変数
- **DOM の持ち越し**：Testing Library を使うなら `cleanup()`（`@testing-library/react` は自動）
- **モックの状態**：`vi.clearAllMocks()` / `vi.restoreAllMocks()`
- **タイマー**：`vi.useRealTimers()` を `afterEach` で必ず呼ぶ

`vitest.config.ts` で**まとめてリセット**するのが最も楽です。

```ts
export default defineConfig({
  test: {
    clearMocks: true,       // 履歴をクリア
    restoreMocks: true,     // spyOn を元に戻す
    unstubGlobals: true,    // stubGlobal を元に戻す
    unstubEnvs: true,       // stubEnv を元に戻す
  },
});
```

## 並列実行と隔離

Vitest はデフォルトで**ファイル単位で並列**に実行します。同一ファイル内は順番に走りますが、`concurrent` にすれば `it` も並列化できます。

```ts
describe.concurrent('並列グループ', () => {
  it('A', async () => { /* ... */ });
  it('B', async () => { /* ... */ });
});
```

### 並列化の注意

- **共有リソース**（DB、ファイル、ポート）を使うテストは並列化しない。
- 並列で走らせるなら、各テストが**独自の名前空間**（一時ディレクトリ、ランダムなレコード ID など）を持つように書く。

### プールモード

ワーカーの種類を選べます。

```ts
// vitest.config.ts
export default defineConfig({
  test: {
    pool: 'threads',   // 'threads' | 'forks' | 'vmThreads' | 'vmForks'
    poolOptions: {
      threads: { maxThreads: 4, minThreads: 2 },
    },
  },
});
```

- **`threads`**（既定）：Worker Thread。起動が速い。
- **`forks`**：子プロセス。Node API を分離したいときに。
- **`vmThreads`**：VM コンテキストで実行。モジュールキャッシュの分離が必要なときに。

たいてい既定の `threads` で十分です。**メモリリーク**や**グローバル汚染**が疑わしいときだけ `forks` を検討します。

## セットアップファイル

全テストで共通の前準備（モックの登録、`expect.extend`、カスタムマッチャー、グローバル初期化）は `setupFiles` に書きます。

```ts
// vitest.config.ts
export default defineConfig({
  test: {
    setupFiles: ['./src/test/setup.ts'],
  },
});
```

```ts
// src/test/setup.ts
import '@testing-library/jest-dom/vitest';   // DOM 用マッチャー
import { afterEach } from 'vitest';
import { cleanup } from '@testing-library/react';

afterEach(() => {
  cleanup();
});
```

**各テストファイルに同じ import を書くのはやめ、ここに集約する**のが鉄則。

### `globalSetup` との違い

- **`setupFiles`**：各ワーカーで 1 回ずつ実行。**テストファイルのコンテキストで走る**（`expect` などが使える）。
- **`globalSetup`**：テスト実行全体で 1 回だけ。**テストコンテキストの外**で走る。DB サーバーを立ち上げるなどに使う。

## 変更しやすいテストを書く 7 か条

1. **名前で意図が分かる**：`it('割引 10% 適用で 900 円になる')` のように、入力と期待結果を含める。
2. **Act は 1 つ**：同じテスト内で 2 回操作をしない。
3. **マジックナンバーを避ける**：`expect(total).toBe(900)` より `expect(total).toBe(1000 * 0.9)` のほうが意図が読める場合も。
4. **公開 API をテスト**：`private` メソッドをゴリ押しで叩かない。振る舞い（＝公開 API）を確認する。
5. **DRY より DAMP**：テストは「読みやすさ」優先。**少しの重複 > 無理な抽象化**。
6. **依存の向きを意識**：外部 API や時刻はモックに、自分のコードは実物を通す。
7. **落ちたら情報があるメッセージ**：`expect(...)`  で `toEqual` を使うと差分が出るのに、カスタム assert で boolean を返して「false でした」としかログが出ない書き方は避ける。

## 壊れやすいテスト（Flaky）の兆候と対策

### 兆候

- ローカルは通るが CI では落ちる
- 「再実行したら通る」が口ぐせ
- 実時間を待っている（`setTimeout`、`sleep`）
- ランダムな値や現在時刻に依存
- テストの順序を変えると結果が変わる

### 対策

| 原因 | 対策 |
|------|------|
| 実時間待ち | `vi.useFakeTimers()` で時間を制御 |
| ランダム値 | シード化 or `vi.spyOn(Math, 'random').mockReturnValue(...)` |
| 現在時刻 | `vi.setSystemTime(date)` |
| ネットワーク | モック化 or MSW |
| テスト順序依存 | `beforeEach` で初期化、グローバル状態をなくす |
| 並列競合 | 共有リソース使用テストは `describe.sequential` か別ファイルに |

## テストダブルの語彙整理

混同されがちな用語：

| 用語 | 特徴 |
|------|------|
| **Dummy** | 引数を埋めるだけで使われない |
| **Stub** | 決まった返り値を返す |
| **Spy** | 呼び出しを記録する |
| **Mock** | Spy + 期待する呼び出しの定義 |
| **Fake** | 本物っぽく振る舞う軽量な実装（インメモリ DB など） |

Vitest の `vi.fn()` は上記すべてを柔軟に担えますが、**どの目的で使っているかを意識する**とテストが読みやすくなります。

## Contract Testing と E2E の境界

単体テストでは自分のコードしかカバーできません。外部 API との契約（Contract）や、ページをまたぐユーザーフローは Vitest では扱えません。

- **契約レベル**：Pact / OpenAPI 検証 など
- **E2E**：Playwright → [[00_Playwright_目次]]
- **スモーク**：MSW を使った統合テスト（Vitest でも可能）

テストピラミッド全体の位置づけは [[02_テストの形（ピラミッド・Trophy・Honeycomb）]] を参照。

## この章のまとめ

- テストは **Arrange / Act / Assert** で読みやすく。
- 共通セットアップは `beforeEach` / `setupFiles` / `test.extend` を使い分ける。
- モック・タイマー・グローバルは**毎回リセット**する設定を `vitest.config.ts` に入れておく。
- Flaky の多くは **実時間・乱数・共有状態** に起因する。制御できるものはすべてモック化。
- テストは**読みやすさ優先**。DRY より DAMP。
