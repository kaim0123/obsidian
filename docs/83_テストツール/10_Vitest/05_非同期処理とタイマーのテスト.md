# 05 — 非同期処理とタイマーのテスト

この章では、Promise / async、`setTimeout` / `setInterval`、`Date` など **時間に依存する処理** のテスト方法を解説します。これらは落とし穴が多いトピックですが、パターンを押さえれば安定して書けるようになります。

---

## 非同期テストの基本

### パターン 1：`async` / `await`（推奨）

もっとも読みやすく、ミスも少ない書き方です。

```ts
import { it, expect } from 'vitest';

it('ユーザー情報が取れる', async () => {
  const user = await fetchUser(1);
  expect(user.name).toBe('Alice');
});
```

**テスト関数自体を `async` にして、Promise を `await` する**だけ。Vitest はテスト関数から返された Promise が解決されるまで待ってくれます。

### パターン 2：Promise を `return` する

```ts
it('ユーザー情報が取れる', () => {
  return fetchUser(1).then(user => {
    expect(user.name).toBe('Alice');
  });
});
```

古いコードで見かけますが、今は `async/await` のほうが読みやすいです。

### パターン 3：`resolves` / `rejects`

```ts
it('ユーザー情報が取れる', async () => {
  await expect(fetchUser(1)).resolves.toMatchObject({ name: 'Alice' });
});

it('存在しないユーザーは例外', async () => {
  await expect(fetchUser(999)).rejects.toThrow('not found');
});
```

**`await` を忘れないこと**。忘れると常に成功するテストになって事故の元です。

---

## よくある失敗：`await` 忘れ

```ts
// ❌ Promise を返すが await していない
it('ユーザー情報が取れる', () => {
  fetchUser(1).then(user => {
    expect(user.name).toBe('Bob');   // 失敗するはずなのに、テストは成功扱い
  });
});
```

テスト関数が**同期的に**終了してしまい、中の `expect` が評価される前に Vitest が「OK」と判断してしまいます。対策：

1. **テスト関数を `async` にする**。
2. **内部の Promise は必ず `await` する**（もしくは `return` する）。

ESLint の `@typescript-eslint/no-floating-promises` や `vitest/valid-expect` を入れると、忘れを検出できます。

---

## `expect.assertions` / `expect.hasAssertions` — 保険

非同期テストで「本当に `expect` が呼ばれたか」を保証する仕組みです。

```ts
it('必ず 1 回は assert する', async () => {
  expect.assertions(1);    // このテスト内で expect は 1 回だけ呼ばれるはず
  await expect(fetchUser(1)).resolves.toMatchObject({ name: 'Alice' });
});
```

try/catch を含むテストや、条件分岐で `expect` が走らない経路が生じそうな場合の保険として有効です。

```ts
it('エラー時に catch で検証する', async () => {
  expect.hasAssertions();   // 最低 1 回の expect が必要
  try {
    await fetchUser(999);
  } catch (err) {
    expect((err as Error).message).toBe('not found');
  }
});
```

## タイムアウトの制御

### `it` ごとのタイムアウト

デフォルトでは 1 つのテストが **5 秒** で打ち切られます。長めの処理では第 3 引数で延長できます。

```ts
it('重い処理', async () => {
  await heavyJob();
}, 10_000);  // 10 秒まで待つ
```

### グローバル設定

```ts
// vitest.config.ts
export default defineConfig({
  test: {
    testTimeout: 10_000,     // 個々のテスト
    hookTimeout: 10_000,     // beforeAll などのフック
  },
});
```

タイムアウトを延ばすのは最後の手段です。**まず「なぜ遅いのか」**（外部 API を叩いている、タイマーが本物、など）**を見直す**のが先です。

---

## フェイクタイマー — `vi.useFakeTimers`

`setTimeout` / `setInterval` を使うコードを、**実時間を待たずに** テストする仕組みです。

### 基本形

```ts
import { it, expect, vi } from 'vitest';

it('1 秒後にコールバックが呼ばれる', () => {
  vi.useFakeTimers();            // 以降のタイマーを偽物にする

  const cb = vi.fn();
  setTimeout(cb, 1000);

  expect(cb).not.toHaveBeenCalled();

  vi.advanceTimersByTime(1000);  // 時計を 1000ms 進める

  expect(cb).toHaveBeenCalledTimes(1);

  vi.useRealTimers();            // 後片付け
});
```

**`vi.advanceTimersByTime(ms)`** で時計を進めると、その間に発火すべきタイマーがまとめて実行されます。**実際の 1 秒を待たずに**テストできるのがポイントです。

### 主な操作 API

| API | 動作 |
|-----|------|
| `vi.useFakeTimers()` | タイマーを偽物化 |
| `vi.useRealTimers()` | 本物に戻す |
| `vi.advanceTimersByTime(ms)` | `ms` ミリ秒だけ時計を進める |
| `vi.runAllTimers()` | すべてのタイマーを順に実行（再帰する `setInterval` は注意） |
| `vi.runOnlyPendingTimers()` | いま予約済みのものだけ実行（再帰で追加されたものは次回に持ち越し） |
| `vi.advanceTimersToNextTimer()` | 次のタイマーまで時計を進める |
| `vi.getTimerCount()` | 予約済みタイマーの数 |

### `setInterval` で無限ループに気をつける

```ts
vi.useFakeTimers();
setInterval(() => tick(), 100);
vi.runAllTimers();   // ❌ 無限に実行されて止まらない
```

**`setInterval` を使っているときは `runAllTimers` を呼ばない**こと。代わりに `advanceTimersByTime(300)` のように、進めたい時間を明示します。

### 非同期関数の中でタイマーを使うとき

`setTimeout` の中で await を使っているコードは、`vi.advanceTimersByTimeAsync` を使います。

```ts
it('デバウンスされた API 呼び出し', async () => {
  vi.useFakeTimers();

  const search = debounce(searchApi, 300);
  search('vite');
  search('vitest');

  await vi.advanceTimersByTimeAsync(300);   // ← async 版

  expect(searchApi).toHaveBeenCalledTimes(1);
  expect(searchApi).toHaveBeenCalledWith('vitest');

  vi.useRealTimers();
});
```

**マイクロタスク（`Promise.resolve().then`）も含めて進めたいときは `Async` 付きを使う**のが鉄則です。

## Date のモック

### パターン A：`vi.useFakeTimers` のオプションで固定

```ts
it('現在時刻を固定してテストする', () => {
  vi.useFakeTimers();
  vi.setSystemTime(new Date('2026-04-21T12:00:00Z'));

  expect(new Date().toISOString()).toBe('2026-04-21T12:00:00.000Z');
  expect(Date.now()).toBe(Date.UTC(2026, 3, 21, 12));

  vi.useRealTimers();
});
```

`vi.setSystemTime(date)` で「**いまの時刻**」を固定できます。`Date.now()`、`new Date()`、`performance.now()` などが同じ時刻を返すようになります。

### パターン B：`vi.spyOn` で Date だけ差し替え

```ts
const spy = vi.spyOn(Date, 'now').mockReturnValue(1_700_000_000_000);
```

ピンポイントで差し替えたいときに使えますが、`new Date()` など他の参照先は変わらない点に注意。基本は **パターン A（`setSystemTime`）** が便利です。

---

## 乱数のテスト

`Math.random` を使うロジックは `vi.spyOn` で固定します。

```ts
const spy = vi.spyOn(Math, 'random').mockReturnValue(0.42);
// ... テスト
spy.mockRestore();
```

もしくは、**テスト可能な設計**として乱数をコンストラクタで注入する（依存性注入）パターンに改修するのも手です。

## React / Vue コンポーネントの非同期更新

DOM のテストでは「state を更新したあと、次のレンダリングを待つ」必要があります。これはライブラリ側の API を使います。

### React + Testing Library

```ts
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

it('ボタンを押すとカウントが増える', async () => {
  const user = userEvent.setup();
  render(<Counter />);

  await user.click(screen.getByRole('button', { name: '増やす' }));

  expect(await screen.findByText('count: 1')).toBeInTheDocument();
});
```

- **`userEvent`** の各操作は Promise を返すので `await`。
- **`findByText`** は非同期に要素が現れるのを待つ。`getByText` は同期的なので、即時に見える要素にしか使えない。

### Vue + Test Utils

```ts
import { mount, flushPromises } from '@vue/test-utils';

it('入力と表示', async () => {
  const wrapper = mount(HelloForm);
  await wrapper.find('input').setValue('Alice');
  await wrapper.find('button').trigger('click');
  await flushPromises();
  expect(wrapper.text()).toContain('Hello, Alice');
});
```

- 何か起きるたびに `await` するのが基本。`flushPromises()` で残っているマイクロタスクを一気に捌ける。

## キャッチしきれない Promise — `unhandledRejection`

テスト中に「catch していない rejected Promise」が発生すると、Vitest が警告を出します。

```
 Error: The following error was thrown as an unhandled rejection:
   Error: network down
```

原因の多くは、

- `await` 漏れで Promise が浮いている
- `setInterval` の中で投げた例外
- テスト終了後に遅れて解決・失敗するタイマー

です。`afterEach` で **`vi.clearAllTimers()`** を呼んで後片付けする、すべての非同期処理を `await` で囲むなどの対策が効きます。

## ミニ演習：デバウンス関数をテストする

```ts
// src/debounce.ts
export function debounce<T extends (...args: any[]) => void>(fn: T, ms: number) {
  let timer: ReturnType<typeof setTimeout> | null = null;
  return (...args: Parameters<T>) => {
    if (timer) clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}
```

```ts
// src/debounce.test.ts
import { describe, it, expect, vi, beforeEach, afterEach } from 'vitest';
import { debounce } from './debounce';

describe('debounce', () => {
  beforeEach(() => vi.useFakeTimers());
  afterEach(() => vi.useRealTimers());

  it('待機時間内の連続呼び出しは 1 回にまとまる', () => {
    const fn = vi.fn();
    const debounced = debounce(fn, 300);

    debounced('a');
    debounced('b');
    debounced('c');

    vi.advanceTimersByTime(299);
    expect(fn).not.toHaveBeenCalled();

    vi.advanceTimersByTime(1);
    expect(fn).toHaveBeenCalledTimes(1);
    expect(fn).toHaveBeenCalledWith('c');
  });

  it('待機時間を超えると独立した呼び出しとして扱う', () => {
    const fn = vi.fn();
    const debounced = debounce(fn, 100);

    debounced('first');
    vi.advanceTimersByTime(100);

    debounced('second');
    vi.advanceTimersByTime(100);

    expect(fn).toHaveBeenCalledTimes(2);
  });
});
```

**実時間を待たずに確率的にならないテスト**が書けているのがポイントです。

---

## この章のまとめ

- 非同期テストは **テスト関数を `async` にして `await`** が基本。
- **`resolves` / `rejects`** を使うときは `await` を忘れない。
- 時間に依存するコードは **`vi.useFakeTimers()`** ＋ `vi.advanceTimersByTime(ms)` で制御。
- 現在時刻は **`vi.setSystemTime(date)`** で固定する。
- Promise/async が絡むときは **`advanceTimersByTimeAsync`** を使う。
- `afterEach(() => vi.useRealTimers())` などで必ず後片付けする。
