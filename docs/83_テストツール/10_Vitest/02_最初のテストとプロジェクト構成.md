# 02 — 最初のテストとプロジェクト構成

この章では、Vitest で典型的に使うフォルダ構成、テストファイルの置き場所、そして `describe` / `it` / `expect` の基本の書き方を押さえます。01 章でインストールが終わっている前提です。

---

## 典型的なプロジェクト構成

Vitest で単体テストを書くときの、よくある構成は 2 パターンあります。

### パターン A：**テスト対象のファイルの隣**に置く（推奨）

```
my-app/
├── src/
│   ├── utils/
│   │   ├── format.ts
│   │   └── format.test.ts   ← 隣にテストファイル
│   ├── features/
│   │   ├── cart.ts
│   │   └── cart.test.ts
│   └── main.ts
├── package.json
└── vitest.config.ts
```

- **メリット**：対応するテストが一目で分かる、リファクタ時にファイルを移動しやすい、import のパスが短い。
- **デメリット**：本番ビルドから明示的に除外する設定が必要（`.test.ts` を無視するなど）。

### パターン B：**`tests/` フォルダ**にまとめる

```
my-app/
├── src/
│   ├── utils/format.ts
│   └── features/cart.ts
├── tests/
│   ├── utils/format.test.ts
│   └── features/cart.test.ts
└── vitest.config.ts
```

- **メリット**：テストとソースが物理的に分かれていて整理しやすい。
- **デメリット**：ファイルを探すときに 2 箇所見る必要がある。

どちらでも構いません。**近年は「隣に置く」方式が主流**です。迷ったらパターン A を選びましょう。

---

## テストファイルの命名規則

Vitest はデフォルトで次のパターンを **テストファイル** と認識します。

- `*.test.ts` / `*.test.tsx` / `*.test.js` / `*.test.jsx`
- `*.spec.ts` / `*.spec.tsx` / `*.spec.js` / `*.spec.jsx`

`test` と `spec` はどちらでも良く、チームで統一されていれば OK です。**Jest 由来では `.spec.` がやや多く、Vitest コミュニティでは `.test.` が多い**印象です。

変更したい場合は `vitest.config.ts` の `include` で指定します。

```ts
// vitest.config.ts
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    include: ['src/**/*.{test,spec}.{ts,tsx,js,jsx}'],
    exclude: ['node_modules', 'dist', '.idea', '.git', '.cache'],
  },
});
```

## テストの基本構造

Vitest のテストは **3 層の構造**で書きます。

```ts
import { describe, it, expect } from 'vitest';

describe('テスト対象（グループ）', () => {
  it('何を期待するか（1 つのケース）', () => {
    expect(実行結果).toBe(期待値);
  });
});
```

- **`describe`**：テスト対象の単位でグループ化する（関数名・クラス名・機能名など）。ネスト可能。
- **`it`**（または `test`）：**1 つのテストケース**を書く。`it` と `test` は完全に同じで、好きな方を使える。
- **`expect`**：実際の値と期待値を比較する。これが「アサーション」。

### 最小の例

`src/math.ts`：

```ts
export const add = (a: number, b: number): number => a + b;
export const divide = (a: number, b: number): number => {
  if (b === 0) throw new Error('0 で割ることはできません');
  return a / b;
};
```

`src/math.test.ts`：

```ts
import { describe, it, expect } from 'vitest';
import { add, divide } from './math';

describe('add', () => {
  it('正の数どうしの足し算ができる', () => {
    expect(add(2, 3)).toBe(5);
  });

  it('0 を足しても値は変わらない', () => {
    expect(add(0, 5)).toBe(5);
    expect(add(5, 0)).toBe(5);
  });

  it('負の数も扱える', () => {
    expect(add(-1, -2)).toBe(-3);
  });
});

describe('divide', () => {
  it('正しく割り算できる', () => {
    expect(divide(10, 2)).toBe(5);
  });

  it('0 で割ろうとするとエラーになる', () => {
    expect(() => divide(1, 0)).toThrow('0 で割ることはできません');
  });
});
```

### よい `describe` / `it` の名前付け

- `describe` には「**何の**テストか」を書く（関数名、機能名、コンポーネント名）。
- `it` には「**どうなるはずか**」を書く。主語を省略した日本語なら自然につなげて読める。

```
describe('calculateTax')
    └── it('税率 10% なら 1.1 倍になる') …✓
    └── it('税率が負数ならエラーを投げる') …✓
```

逆に **避けたい** 名前の例：

- `it('test1')`, `it('ちゃんと動く')` → 何を検証したかが追えない
- `it('add が 5 を返すこと')` → 入力が書いていないので、将来仕様が変わったとき読み解けない

## 実行コマンドの使い分け

`package.json` の `scripts` に書いた想定で説明します。

### Watch モード（開発中）

```bash
npm test       # = vitest
```

ファイル変更を検知し、**変わったファイルに関係するテストだけ**を自動で再実行します。起動後は以下のキー操作が可能です。

| キー | 動作 |
|------|------|
| `a` | すべてのテストを再実行 |
| `f` | 失敗したテストだけ再実行 |
| `p` | ファイル名フィルタ（パス指定） |
| `t` | テスト名フィルタ（`it` の名前で絞る） |
| `q` | Watch モードを終了 |
| `Enter` | 変更検知を待たず、いま変更があったテストを実行 |

### 1 回だけ実行（CI / コミット前など）

```bash
npm run test:run    # = vitest run
```

ファイル変更を待たず、1 回だけ実行して終了します。CI や pre-commit フックではこちらを使います。

### ファイル・テスト名で絞り込む

```bash
# ファイル名で絞る
npx vitest math

# テスト名で絞る（-t / --testNamePattern）
npx vitest -t '0 で割る'

# 両方組み合わせ
npx vitest math -t '0 で割る'
```

大きなプロジェクトで「いまは特定のテストだけ直したい」ときに便利です。

### カバレッジ

```bash
npm run coverage   # = vitest run --coverage
```

初回は `@vitest/coverage-v8` のインストールを促されることがあります。詳細は 06 章で扱います。

## `it.only` / `it.skip` / `it.todo`

テストの実行対象を細かくコントロールできます。

```ts
it.only('このテストだけ実行する', () => { /* ... */ });   // 他のテストはスキップ
it.skip('いまは実行しない', () => { /* ... */ });          // 一時的に飛ばす
it.todo('あとで書く');                                     // 空の予約
```

- `only` は**デバッグ時だけ使う**。コミット前に外すことを忘れない。
- `skip` は**理由を書いたコメント**と一緒に付けると良い（Flaky 対策の一時措置など）。
- `todo` は TDD で先にケース名だけ書き出すときに使うと綺麗。

`describe.only` / `describe.skip` も同様に使えます。

## `it.each` — データ駆動テスト

同じロジックを複数パターンで回すときは `it.each` を使います。

```ts
import { describe, it, expect } from 'vitest';
import { add } from './math';

describe('add（パラメタライズ）', () => {
  it.each([
    { a: 1, b: 2, expected: 3 },
    { a: 0, b: 0, expected: 0 },
    { a: -1, b: 1, expected: 0 },
    { a: 100, b: 200, expected: 300 },
  ])('add($a, $b) は $expected になる', ({ a, b, expected }) => {
    expect(add(a, b)).toBe(expected);
  });
});
```

文字列中の `$a` のようなプレースホルダは、オブジェクトのキー名で参照できます。

### 配列スタイル

```ts
it.each([
  [1, 2, 3],
  [0, 0, 0],
  [-1, 1, 0],
])('add(%i, %i) は %i になる', (a, b, expected) => {
  expect(add(a, b)).toBe(expected);
});
```

- `%i` 整数、`%s` 文字列、`%o` オブジェクト…と、`console.log` の書式に近いプレースホルダが使えます。

**テストケースが 3 つ以上に増えたら `it.each` を検討**すると、コードの重複を減らせます。

## フック — `beforeEach` / `afterEach` / `beforeAll` / `afterAll`

セットアップ・後始末のための関数です。

```ts
import { describe, it, beforeEach, afterEach, expect } from 'vitest';

describe('Cart', () => {
  let cart: Cart;

  beforeEach(() => {
    cart = new Cart();          // 各 it の前に毎回新しいインスタンスを作る
  });

  afterEach(() => {
    // 各 it のあとに走る（DB 接続のクローズなど）
  });

  it('初期状態は空', () => {
    expect(cart.items).toHaveLength(0);
  });

  it('追加すると 1 件になる', () => {
    cart.add({ id: 1, name: 'Apple' });
    expect(cart.items).toHaveLength(1);
  });
});
```

- **`beforeEach` / `afterEach`**：各テスト（`it`）の**前後**で毎回走る。**テスト間の独立性**を保つのに使う。
- **`beforeAll` / `afterAll`**：`describe` ブロック全体で**1 回ずつ**走る。DB 接続やサーバー起動など重い処理に使う。

> **原則**：テスト間で状態を共有しない。`beforeEach` で毎回初期化するのが安全です。どうしても重い初期化を共有したいときだけ `beforeAll` にする。

## `expect` の基本だけ押さえる

詳しくは 03 章で扱いますが、頻度が高いものだけ先に紹介します。

```ts
// 厳密な等価
expect(1 + 1).toBe(2);

// オブジェクト / 配列の「中身」が等しい
expect({ a: 1 }).toEqual({ a: 1 });
expect([1, 2]).toEqual([1, 2]);

// 真偽
expect(user.isAdmin).toBe(true);
expect(list).toHaveLength(3);

// 含む
expect('hello world').toContain('world');
expect([1, 2, 3]).toContain(2);

// 例外
expect(() => divide(1, 0)).toThrow('0 で割る');

// not で反転
expect(value).not.toBeNull();
```

### `toBe` と `toEqual` の違い（初学者のつまずきポイント）

- **`toBe`**：**同一性**（`===`）で比較。**プリミティブ**（数値、文字列、真偽値）はこちら。
- **`toEqual`**：**構造的な等価**で比較。**オブジェクトや配列の中身**を比べるときはこちら。

```ts
expect({ a: 1 }).toBe({ a: 1 });      // ❌ 失敗する（別インスタンス）
expect({ a: 1 }).toEqual({ a: 1 });   // ✓ 成功
```

## 失敗時の読み方

わざと失敗させたテストの出力例：

```
 FAIL  src/math.test.ts > add > 正の数どうしの足し算ができる
AssertionError: expected 5 to be 6 // Object.is equality

- Expected
+ Received

- 6
+ 5

 ❯ src/math.test.ts:5:27
      3|
      4|   it('正の数どうしの足し算ができる', () => {
      5|     expect(add(2, 3)).toBe(6);
       |                           ^
```

読み方のコツ：

1. **`FAIL` の行**でテスト名とファイルを特定する。
2. **`Expected` / `Received`** で「期待値」と「実際」を比較する。
3. **行番号 + キャレット（`^`）** で失敗した `expect` を特定する。

---

## この章のまとめ

- テストは **`describe` / `it` / `expect`** の 3 段で書く。
- ファイルは **`*.test.ts`** を使うのが主流。対象ファイルの**隣に置く**構成が見通しが良い。
- 開発中は `vitest`（Watch）、CI は `vitest run` を使い分ける。
- **`beforeEach` でテストごとに初期化**し、テスト間の独立性を保つ。
- 重複したテストは **`it.each`** でまとめる。
- 成功・失敗の出力を読めるようになると、テスト駆動でのリファクタが一気に楽になる。
