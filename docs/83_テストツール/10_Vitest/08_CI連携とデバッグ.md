# 08 — CI 連携とデバッグ

この章では、Vitest を **GitHub Actions で自動実行**する方法と、失敗したテストを**どうやって特定・修正するか**を整理します。

---

## なぜ CI でテストを回すか

- **プッシュや PR のたびに自動で回る**ので、壊れたコードがマージされにくくなる。
- **「ローカルでは通ったのに」問題**を早期に検知できる（Node バージョン、環境差、タイムゾーン）。
- **PR レビュアが「テストが通っているか」を判断材料にできる**。

Vitest は CI で走らせるときは **Watch ではなく `run` モード** を使うのが鉄則です。

```bash
npx vitest run --coverage
```

---

## GitHub Actions の最小構成

`.github/workflows/test.yml`：

```yaml
name: Test

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - run: npm ci
      - run: npm run test:run
```

これだけで PR 時とメインブランチへのプッシュ時にテストが走るようになります。

### ポイント

- **`npm ci`** を使う（`npm install` ではなく）。`package-lock.json` 準拠でクリーンインストールされ、再現性が高い。
- **`cache: npm`** で `~/.npm` がキャッシュされ、2 回目以降が速くなる。
- **Node のバージョン**はプロジェクトで使っている LTS に合わせる（20, 22 など）。

---

## カバレッジをつける

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - run: npm ci
      - run: npm run coverage       # = vitest run --coverage

      - name: Upload coverage to Codecov
        uses: codecov/codecov-action@v4
        with:
          files: ./coverage/lcov.info
          fail_ci_if_error: false
```

Codecov を使わない場合でも、**Artifact として coverage/ を保存**しておくと、あとから HTML レポートが見られます。

```yaml
- uses: actions/upload-artifact@v4
  if: always()
  with:
    name: coverage-report
    path: coverage/
```

`if: always()` をつけると、テストが失敗しても（むしろそのときこそ）成果物が残るので便利です。

---

## マトリクスビルド — 複数 Node / OS で回す

```yaml
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
        node: [20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: ${{ matrix.node }}
          cache: npm
      - run: npm ci
      - run: npm run test:run
```

- **`fail-fast: false`**：1 つが落ちても他を最後まで走らせる（原因特定に役立つ）。
- ライブラリを作っている場合など、**サポート範囲の Node / OS で動くこと**を保証したいときに有効。

## JUnit レポートで GitHub の Test Summary に表示する

```yaml
- run: npx vitest run --reporter=default --reporter=junit --outputFile=test-results.xml

- name: Publish Test Report
  if: always()
  uses: mikepenz/action-junit-report@v4
  with:
    report_paths: 'test-results.xml'
```

PR 画面で「どのテストが落ちたか」が一目でわかるようになります。

## 失敗したテストの絞り込み再実行

CI でよくある流れ：

1. `vitest run` で 100 テスト中 2 つ失敗。
2. ログから失敗したテスト名 / ファイルをコピー。
3. 手元で狭い範囲で再実行する。

```bash
# ファイルで絞る
npx vitest src/features/cart.test.ts

# テスト名で絞る
npx vitest -t '0 で割るとエラー'

# 失敗したものだけ（Watch モード中に f キーと同じ）
npx vitest run --changed
```

`--changed` は Git の差分（HEAD との差）に関連するテストだけを実行します。**PR ブランチで効率的に回したい**ときに便利。

---

## Watch 中のデバッグキー操作

ローカル Watch モード時は、次のキー操作が使えます（01 章で少し触れました）。

| キー | 動作 |
|------|------|
| `h` | ヘルプを表示 |
| `a` | すべて再実行 |
| `f` | 失敗したテストだけ再実行 |
| `p` | ファイル名フィルタ |
| `t` | テスト名フィルタ |
| `u` | スナップショットを更新 |
| `b` | Browser Mode の切替 |
| `q` | 終了 |

**`f` + 失敗テストの修正** を繰り返すのが、もっとも効率的なデバッグループです。

## VS Code から Vitest を動かす

拡張機能 **「Vitest」**（公式）を入れると、次のことができます。

- エディタ左側のテストエクスプローラから個別に実行・再実行
- **コード上のガターにアイコン**が出て、テストの成功／失敗が一目でわかる
- **ブレークポイントを貼ってデバッグ実行**
- 失敗原因の行にインラインでエラー表示

Jest 時代に `Jest Runner` 的な使い方をしていた人は、同じ感覚で使えます。

## Node デバッガで止める

```bash
node --inspect-brk ./node_modules/vitest/vitest.mjs run
```

- `--inspect-brk` で最初の行で一時停止。
- Chrome で `chrome://inspect` を開いて接続。

または、テストコードに `debugger` 文を書いて、Vitest を `--inspect` で起動しても同じことができます。

```ts
it('壊れているケース', () => {
  const x = compute();
  debugger;                // ←ここで止まる
  expect(x).toBe(42);
});
```

## デバッグ時のログ出力

### `console.log` で中を確認する

テスト実行時の `console.log` は **デフォルトでそのまま出力** されます。Jest のように `jest.disableConsoleOutput()` のような設定は不要。

長い配列やオブジェクトは、

```ts
console.dir(obj, { depth: null });
```

のほうが全階層を展開してくれて便利です。

### `onConsoleLog` フックで取捨選択

```ts
// vitest.config.ts
test: {
  onConsoleLog(log, type) {
    if (log.includes('Warning: ReactDOM')) return false; // 出さない
  },
}
```

**テストログがノイズまみれ**になってきたら、こういった方法でフィルタできます。

## 典型的な「ローカルは通るのに CI で落ちる」問題

| 症状 | 原因 |
|------|------|
| 時刻系が合わない | **タイムゾーン**（UTC）。`TZ=Asia/Tokyo` を設定するか、`vi.setSystemTime` で固定 |
| 日本語ソート順が違う | **ロケール**（`en_US.UTF-8`）。`Intl.Collator('ja')` を明示 |
| 改行が CRLF / LF | Git の `core.autocrlf` 設定 or テストが改行に依存している |
| ファイルが見つからない | 大文字小文字の違い（Linux は区別、macOS/Windows はしない） |
| ランダムに失敗 | 並列実行での競合、共有状態、実時間待ち |
| メモリ不足 | ワーカーが多すぎ。`poolOptions.threads.maxThreads` を下げる |

原則：**CI の環境（Linux, UTF-8, UTC）に合わせてローカルも動かす**と再現しやすくなります。Docker でテスト実行する手もあります。

## Pre-commit / Pre-push フック

commit や push の前に **変更に関係するテストだけ** 走らせる運用は、CI の負荷軽減と開発の質向上に有効です。

```bash
npm install -D husky lint-staged
npx husky init
```

`.husky/pre-commit`：

```bash
npx lint-staged
```

`package.json`：

```json
{
  "lint-staged": {
    "*.{ts,tsx}": [
      "eslint --fix",
      "vitest related --run"
    ]
  }
}
```

**`vitest related`** は指定ファイルが関係するテストだけを実行する便利なコマンドです。commit 時にフル実行するよりずっと速いので、体験が良くなります。

> ただし **pre-push では必ず `vitest run` フル実行**が望ましい。commit 時に見つからなかった回帰が混入して、CI で落ちる事故を減らせます。

---

## PR とテストのワークフロー推奨

1. **変更を書く**（TDD なら Red → Green の順で）。
2. **`vitest` で Watch しながら直し続ける**。失敗したテストだけ `f` で絞る。
3. **コミット前に `vitest run` をフル実行**。全部通ることを確認。
4. **PR を出すと CI が自動で回る**。通っているか確認。
5. 落ちたら **PR 画面のサマリ／ログ** で失敗を特定。
6. 原因を修正し、**コミット追加 or amend して再プッシュ**。CI が再実行される。

この 1 ループが短いほど、品質も速度も両立できます。

## この章のまとめ

- CI では `vitest run`（または `run --coverage`）を使う。Watch は NG。
- **GitHub Actions** は最小構成なら `setup-node` → `npm ci` → `npm run test:run` でよい。
- **JUnit レポート**と **Codecov / Artifact** で失敗の可視化・カバレッジ共有。
- 失敗は **`-t` や `--changed`** で狭い範囲に絞って再実行。
- **VS Code 拡張**や **`debugger` + `--inspect`** でデバッグ。
- 「ローカルは通るが CI で落ちる」系は **TZ / ロケール / 並列 / 大文字小文字** を疑う。
- **pre-commit で `vitest related`**、**pre-push で `vitest run`** の二段構えが有効。
