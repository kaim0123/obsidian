## 内容の要約（詳しめ）

本稿は [YouTube 動画](https://www.youtube.com/watch?v=Ca1h3KUfQ5k)（2024年9月公開想定）の内容に基づく整理です。App Router 登場以降、**コンポーネント・データ取得・キャッシュ・レンダリング**が絡み合うため、公式ドキュメントや『[Next.jsの考え方](https://zenn.dev/akfm/books/nextjs-basic-principle)』と併せて俯瞰するのが前提になっています。冒頭ではメタデータ・ミドルウェアも列挙されていますが、本編では主に下記までが中心です。

### コンポーネント設計

- **デフォルトは Server Component**（`"use client"` がない限り）。Next.js はサーバー側レンダリングを推奨している。
- **Client Component は必要最小限**。主な用途は、Hooks（`useState` / `useEffect` 等）、イベントハンドラ（`onClick` など）、ブラウザ API（`localStorage`、`window` など）、入力・検索・タブ切り替えなどインタラクションが主体の UI。**フォーム**は Server Actions と組み合わせれば Server Component のままでも構築できる（用途に応じて選択）。
- **Server Component を優先する理由（動画での整理）**：データ取得がサーバーに近く速い／JS バンドル に載らない／クライアント性能への依存が減る／SEO（完成した HTML とメタ情報）／API キーや DB クエリなどをクライアントに載せにくい。一方、ユーザー操作依存の状態管理はサーバー側では弱く、そこだけクライアントに寄せる。
- **クライアントバウンダリ**：親に `"use client"` を付けると、その**子まで実質クライアント側の境界に巻き込まれる**。意図せず直下全部がクライアント化しないよう、基本的には**ツリーの末端**に `"use client"` を置くのが無難。子をサーバー側のまま保ちたい場合は **Composition パターン**（クライアントが `children` としてサーバー製の子を受け取る）で回避できるが、詳細は書籍など参照。

### データフェッチ

- **`fetch` は Web 標準を Next.js が拡張**。動画収録時点の説明では、**バージョン 15 付近では未指定時 `no-store` 寄り（毎リクエストでソースに触れる SSR 的な挙動）**として理解し、実際のデフォルトは**常に公式の現行ドキュメントで確認する**べきという前提が強い。`cache` / `next: { revalidate }` / `tags` 等で **SSG・ISR・タグ.invalidation** にオプトインするイメージ。
- **ORM（Prisma 等）や独自関数**は、そのままでは `fetch` の Request Memoization の対象外。**重複実行を抑えたい場合は React の `cache()` でラップする**、`fetch` 層へ寄せて同一 URL を保証する、といった話が関連する。
- **Route Handler（`/api`）経由での取得だけが必須ではない**。データ取得のみなら Server Component から DB 直呼びの方が**往復が減る**。公開 API が必要・バックエンド分離などの場合のみ Route を検討。変更系は Server Actions の利用余地が増えている（動画でも言及）。
- **クライアント側の TanStack Query / SWR**：キャッシュやロード・エラー状態の扱いは楽だが、学習コスト・公開ネットワーク・バンドル肥大のトレードオフ。**Next を主役にする場合はサーバー側取得が既定**で、クライアント専用ライブラリは必要なときに。
- **Server Component はリアルタイム性・楽観的 UI・イベント起点のフェッチには弱く**、その場合はクライアントや別フレームワークの検討が話題になる。Server Actions は progressive enhancement に有利だが、**リアルタイム入力バリデーションはクライアント向けフォームライブラリの方が楽**というトレードオフも触れられている。
- **Container / Presentation**：**データ取得（コンテナ）と表示（プレゼンテーション）を分離**する。RTL などでサーバー非同期との切り離しやすさ、Storybook／Composition との相性、RSC Payload の話まで触れる。**小規模では過度な設計になり得る**。
- **並行フェッチ**：依存のない複数取得は **`Promise.all` やコンポーネント分割**で並列化。**過分割は N+1** の温床にもなり得るので、データローダ等は別資料参照。

### キャッシュは 4 層で考える（混同しやすい）

| 名称 | ざっくり |
|------|----------|
| **Request Memoization** | **同一リクエスト中**の同一 `fetch`（URL・オプション一致）の**重複をまとめる**。レスポンス完了とともに捨てられるイメージ。`fetch` 以外は別途 `cache()` 等。サーバーコンポーネント内の **`fetch` に限る**（Route Handler 内の `fetch` では効かない、等の注意あり）。動的メタデータ用の二度 `fetch` もワンセットにできる例として紹介。 |
| **Data Cache** | **`fetch` の結果（JSON）**を**跨リクエスト・跨ユーザーで保持し得る**層。**`force-cache` / `revalidate` / `tags`** や **`no-store`** の振る舞いと直結。**永続〜再検証まで意図をはっきり**させないと、古い表示や個人別データ混入のミスにつながる。 |
| **Full Route Cache** | **ページ全体の静的 HTML / RSC Payload**。**静的レンダリング（ビルド時・ISR 再生成時など）でのみ**。動的 SSR ではフルルートはキャッシュされない。**クッキー・特定の headers 依存などで意図せず動的ルートになる**には注意（App Router は静的レンダリング推奨の流れ）。 |
| **Router Cache** | **クライアントのナビゲーション用**。訪問済みルートをメモリ保持し、戻る／進むや `<Link>` 遷移を速くする。**セッション（タブ）単位**で、閉じると消える。`<Link prefetch>`（静的ページは強め、動的はレイアウトのみ等）、**Stale Times（バージョン 14.1 以降で調整可能）**、`router.refresh()` や関連 API で無効化、など。

**総括**：まずは「べきだったのにキャッシュされていてデータがずれる」「すべきページが静的／動的になっていない」を避ける。余裕があれば、メモ化・データキャッシュ・ルーターキャッシュを計測しながら最適化。挙動はバージョンで変わるため**英語公式を一次情報に**することが勧められている。

### レンダリング

- **静的（SSG / ISR）**：更新の少ないドキュメント・ポリシー、ある程度時間でよいコンテンツ向け。**ISR は `revalidate` の時間運用**。再検証直後は**最初の応答が stale で、裏で更新され次回から新しめ**になり得る、という注意が動画にある。
- **動的（SSR）**：ユーザー別・ヘッダー／Cookie 依存、常に最新が必要な取得は **`fetch` で `no-store` や `dynamic = 'force-dynamic'`** 等でキャッシュしない方向へ。
- **ストリーミング + Suspense / `loading.js`**：遅い部分だけ後から流し込み、`fallback` で待ち時間を明示。**FCP／体感速度**に効く。
- **PPR（Partial Prerendering、実験的）**：**外側は静的プリレンダー、Suspense 内側を動的**にできるモデル。『[SSRとSSGの終焉という新時代の到来](https://zenn.dev/akfm/articles/nextjs-partial-pre-rendering)』等の説明を引用。**`next.config` の実験フラグ**が必要な段階だった。ストリーミング SSR と似た実装でも、**フォールバックまでを静的に寄せられる**という整理。

### 実務上のヒント（動画の締めに近い整理）

レンダリング方針は当面**ルート／ページ単位**で決めつつ、PPR 浸透後は**UI の境界単位**で細かく分ける時代になる可能性。それでも **可能なら静的を土台に、必要なところだけ動的・ストリーミングを足す**のが現実的。キャッシュを覚えるほど Remix など「素の fetch モデル」を選ぶ検討も言及されている。
