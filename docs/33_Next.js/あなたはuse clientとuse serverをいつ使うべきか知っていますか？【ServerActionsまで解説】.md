## 詳しい要約（動画内容）

### この動画で扱うテーマ

Next.js の **React Server Components（RSC）** を前提に、**いつ `"use client"` でクライアントコンポーネントにするか**、**Server Actions（`"use server"`）をどう使うか**、および **Todo リスト** を題材に従来の **Route Handler（`/api/*`）＋fetch** と比較しながら解説している。

---

### 「use client」を付けるタイミング

- **`useState` / `useEffect` など、クライアント専用のフックを使う**場合、そのコンポーネント（またはその祖先）はクライアントコンポーネントである必要がある。サーバーコンポーネントのままだと Next がエラーにする。
- Todo のように **ユーザー入力に応じて画面がすぐ変わる（インタラクティブ）** アプリでは、状態管理や初回フェッチがクライアント側で書きやすく、 **`"use client"` を付けるのが一般的なパターン** として説明されている。
- **SSR で実現する設計なら `"use client"` を外せる**という補足もあり（要件・実装による）。

### サーバーコンポーネント側のイメージ

- **リアルタイム性が低く、コンテンツ中心（ブログ、ある程度静的なサイト、EC の一部など）** では、`"use client"` にせず **サーバーでレンダリング（SSR / SSG のイメージ）** させることを推す流れになる。
- 初回ロードや SEO に有利、というニュアンスでも触れられている。

### 親子の伝播（境界の理解）

- ファイルの先頭などに **`"use client"` を付けた親** の下にある子コンポーネントも、**自動的にクライアントコンポーネントとして扱われる**。子側で別途 `"use client"` を書かなくても、親のフックと同様の世界で動ける、という確認がされている。

---

### Server Actions（`"use server"`）とは何をしているか

- **フォームの `action={...}` に渡す関数**として、サーバー上で実行される処理を直に書ける仕組み。動画では **Prisma で DB に Todo を作成する処理** を、別途 **`fetch('/api/todo')`** を書かずに実装している。
- クライアントでは **`FormData`** を引数として受け取り、**`formData.get('title')`** などで値を読む。**`<input name="title">`** のように **`name` を付ける必要がある** 点が強調されている。

### `"use client"` と `"use server"` を同じファイルに置けない理由と対処

- コンポーネントファイル全体が **`"use client"`** のとき、そのファイルの中に **`"use server"` でマークした Server Action を定義するとエラーになる（クライアント境界の中では Server Action を直接定義できない、という説明）。
- **回避策：** `actions.ts` のような **別ファイルを作り、そのファイル先頭（または関数単位）に `"use server"`** を書き、`addTodo` などを **export してクライアント側からインポート**する。

### 実装ノート（動画内の状態）

- 送信後に入力欄を空にしたい場合は **`useRef` と `form.reset()`** の話が軽く触れられる。
- **`revalidatePath` / `revalidateTag` と `redirect` でキャッシュ更新・遷移**を試みるが、**動画収録時点では期待どおりに動かなかった** と述べ、視聴者にコメントで知見を募る形になっている。**「キャッシュ削除・リダイレクトは本来メリットの一つ」**として言及されているが、デモは未完成の認識でよい。

---

### Server Actions のメリット（講師の整理）

| 観点 | 内容 |
|------|------|
| ボイラープレート | **専用の API Route を増やさず**、サーバー側の処理へ直接繋げる |
| 往復・レンダリング | **fetch の往復や手続きが減る**ため、体感・再レンダリングの余地がやや減る、という説明 |
| DB との距離 | **デプロイ先のサーバーから DB が近い**前提で、ブラウザ→API→DB より直接的な経路になりうる |
| プログレッシブエンハンスメント | **`action` は HTML のフォーム属性としても意味を持ち**、**ハイドレーション完了前（JS がまだ効いていない時間帯）**にもフォーム送信の経路になりうる、という補足的なメリットの話 |

### デメリット・懸念

- **関心の分離の曖昧化**：これまでフロントが fetch、バックが API と役割分担していたものに、フロント近くに **サーバー側の DB 処理**が寄るため、**「誰が API / サーバー責務か」が分かりにくくなる**、という指摘。
- **技術自体のキャッチアップコスト**もデメリットとして触れられる。

---

### 総括としての使い分けイメージ

1. **`"use client"`**：インタラクティブ／クライアントフック必須の UI。
2. **サーバーコンポーネント**：静的寄り・初回や SEO を意識する画面。
3. **Server Actions**：**フォーム中心のミューテーション（Todo 追加、ログイン・新規登録など）**には積極的検討の余地がある一方で、**汎用的なデータ取得や「すべて」を Server Actions に寄せる必要はない**、という講師の個人的見解。**プロジェクトごとにトレードオフで天秤にかける**、と締める。

※動画は **Next.js 13 以降の文脈**で撮影された内容であり、`revalidate` / `redirect` 周りはバージョンやルート構成で挙動が変わり得る点に留意。
