## 動画の要約（詳しめ）

本動画は **Next.js 16** で導入された **`"use cache"` ディレクティブ** と **キャッシュコンポーネント** を軸に、ブログ構成を題材として実装していく入門コンテンツである。狙いは「今までは `fetch` のオプション（`cache` / `revalidate` など）で細かく制御していたキャッシュ」を、コード上の **`"use cache"`** で扱いやすくすることと、それに連動した **PPR（Partial Prerender / パーシャルプリレンダリング）** の考え方を身につけることにある。

### 前提とセットアップ

- **キャッシュコンポーネントの有効化**は、`next.config`（撮影時点では `next.config.ts`）でフラグを `true` にして行う。**オフのままだと v15 寄りの挙動**であり、`"use cache"` を試す際は設定を忘れない。
- `create-next-app` では **撮影時点で v16.0.1**、推奨スタック（TypeScript / Tailwind 等）での作成が説明されている。

### `"use cache"` が担うこと

- 用途は主に **データフェッチ関数** であり、単一関数の先頭に付けるか、ファイル全体に付けて「その単位がキャッシュ対象になる」ようにできる。
- **非同期コンテキスト**では **`async` 関数内**での利用が前提（ビルド時に同期関数ではエラーとなる例がデモされている）。
- ファイル先頭だけに付ける用法はほぼ想定しない、との言及があり、無キャッシュでも静的出力できるページは **従来どおりサーバーコンポーネントとして静的プリレンダ**が一般的、という整理になっている。
- 「キャッシュ」を図書館の例えで説明：**よく参照されるデータを「身近な場所」に置き、取得コストを下げる**イメージ。

### v16 と PPR が厳しくするルール（重要）

キャッシュコンポーネント有効時、**キャッシュされていないデータ取得が Suspense の外で呼ばれる**と **新しいエラー**となる。これは **PPR を前提に組み立てさせるため**であり、対処は次のどちらかである。

1. **フェッチを `"use cache"` でラップしてキャッシュする**（ISR 寄り・ブログ一覧向き、など）。
2. **キャッシュしないなら、その部分を `Suspense` で包む**（SSR / 動的部分として切り分け、`fallback` でスケルトン等を見せて UX を担保）。

ここが **v14/v15 と挙動が変わったポイント**として強調されている。ビルド出力では **`Partial Prerender`** といった表記により、**静的 HTML と動的サーバー（ストリーミング）部分がページ内で分離**できることが確認できる。**従来はページに SSR が混ざるとページ全体が動的側に寄りがちだった**のに対し、**同一レイアウト内で静的／動的を分ける**発想が PPR と説明されている。

### キャッシュ時間の調整：`cacheLife()`

`"use cache"` だけでも **撮影時点の説明ではデフォルトで約15分ごとの再検証**など **ISR に近い特性**があり、TTL や性質の細かな指定は **`cacheLife()`** で行う。また **「完全不变の SSG」の捉え方は変わりつつあり、長期間でも再検証前提のモデルになりうる**という観察と、公式ドキュメント上の **`stale`／`revalidate`／有効期間**などの語の読み替えにも触れている。**常に最新が必要なデータは SSR 側（Suspense で分離した領域）**が適切、という結論にもつなげている。

### タグで無効化・更新：`cacheTag()` と関連 API

ミューテーション後に一覧が更新されないデモでは、ハードリロード（ブラウザのキャッシュバイパス）でようやく反映される状態が示される。運用上の選択肢として次が整理されている。

- **`revalidatePath`**：経路単位での再検証。**タグ必須ではない**場合もある。**投稿直後すぐ一覧を新鮮にしたい**用途で有効な例がある。
- **`cacheTag()`**：キャッシュエントリに **ラベル（付箋）** を付け、一覧・詳細など **複数キャッシュを一括で追跡・更新したいとき**に使う。
- **`updateTag`** と **`revalidateTag`** の差：**後者は ISR 様の「一度古いまま見せ、その裏で再検証」**に寄りうる。**即時反映を優先するなら `updateTag`** を選ぶ場面がある、とのデモがある。
- **`refresh()`（サーバーアクション向けに新しく触れられる）**：動画では **キャッシュされていないデータを最新状態に反映したい／通知や統計など**の文脈で紹介され、**キャッシュ済みコンテンツの即時無効化の代替にはならない**点にも注意がある。

SSR に戻せばミューテーション直後は当然反映されるため、**「キャッシュで速くする」「更新 API で整合を取る」**のトレードオフが明示される。

### 付随トピック

- **`Link`＋ルーターキャッシュ**：本番に近い挙動は `next build` 後 **`npm run start`** で確認する、という開発上のヒントがある。
- **next-devtools-mcp**：開発サーバー連携や **v16 アップグレード補助**、キャッシュセットアップ、ドキュメント検索など **MCP 経由の支援**を紹介。キャッシュヒット率そのものはこの MCP で直接計測できない旨にも触れ、パフォーマンスは **Chrome DevTools 等別手段**とも対比されている。

動画末尾の総括として、**変更の本体は `"use cache"` と PPR のルール／挙動**であり、**RSC・クライアントコンポーネントの基本思想はそのまま活かせる**、個人開発の v16 アップデートも **心理的ハードルは高くない可能性**がある、とのメッセージで締めている。
