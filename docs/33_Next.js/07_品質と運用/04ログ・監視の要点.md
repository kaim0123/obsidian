# ログ・監視の要点

本番運用に入ると、「**何かが起きたとき、その原因を後から追える**」ことが命綱になります。
ログと監視は地味ですが、最初に仕込むと**問題発生時の解決スピードが 10 倍**変わります。

---

## 1. 何を監視するか（3 つのレイヤー）

| レイヤー | 内容 | ツール例 |
|---------|------|----------|
| **エラー** | 例外、500 系、未処理 Promise | Sentry, Bugsnag, Rollbar |
| **パフォーマンス** | LCP、応答時間、エラー率 | Vercel Speed Insights, DataDog |
| **ログ** | 出来事の記録（誰が何をしたか） | Logtail, Axiom, CloudWatch |
| **死活監視** | サイトが生きているか | UptimeRobot, Better Uptime |

最低限のスタートとしては、**エラー監視**と**死活監視**から。

---

## 2. エラー監視：Sentry が定番

### セットアップ

```bash
npx @sentry/wizard@latest -i nextjs
```

これで自動的に必要なファイル・設定が追加されます。

```ts
// sentry.client.config.ts
import * as Sentry from "@sentry/nextjs";

Sentry.init({
  dsn: process.env.NEXT_PUBLIC_SENTRY_DSN,
  tracesSampleRate: 0.1,
  replaysSessionSampleRate: 0.1,
});
```

```ts
// sentry.server.config.ts
import * as Sentry from "@sentry/nextjs";

Sentry.init({
  dsn: process.env.SENTRY_DSN,
  tracesSampleRate: 0.1,
});
```

これで、

- **クライアント側のエラー**が自動的に Sentry に送られる
- **サーバー側のエラー**も同様
- **ソースマップ**もアップロードされて、minify 後のスタックトレースも追える

### 任意のエラーを送る

```ts
import * as Sentry from "@sentry/nextjs";

try {
  await dangerousOperation();
} catch (err) {
  Sentry.captureException(err, { tags: { feature: "checkout" } });
  throw err;
}
```

### ユーザー情報を紐付け

```ts
Sentry.setUser({ id: session.user.id, email: session.user.email });
```

## 3. ログの基本

### 開発時

```ts
console.log("ユーザー作成:", user.id);
console.warn("注意:", message);
console.error("エラー:", error);
```

### 本番時

`console.log` も出力されますが、構造化していないと検索・集計が大変。
本番では **構造化ログ**（JSON 形式）を推奨。

```ts
// lib/logger.ts
type LogLevel = "info" | "warn" | "error";

function log(level: LogLevel, msg: string, meta?: Record<string, any>) {
  const entry = {
    level,
    message: msg,
    timestamp: new Date().toISOString(),
    ...meta,
  };
  console.log(JSON.stringify(entry));
}

export const logger = {
  info: (msg: string, meta?: Record<string, any>) => log("info", msg, meta),
  warn: (msg: string, meta?: Record<string, any>) => log("warn", msg, meta),
  error: (msg: string, meta?: Record<string, any>) => log("error", msg, meta),
};
```

```ts
import { logger } from "@/lib/logger";

logger.info("ユーザー作成", { userId: user.id, plan: "pro" });
logger.error("決済失敗", { orderId, error: err.message });
```

### より本格的に：pino

```bash
npm install pino
```

```ts
import pino from "pino";
export const logger = pino({ level: process.env.LOG_LEVEL ?? "info" });
```

高速で、構造化ログの定番。

## 4. ログ集約

Vercel のログは **2 時間しか保持されない**（Hobby）など制約があるので、外部の集約サービスに送ると安心。

| サービス | 特徴 |
|---------|------|
| [Logtail](https://betterstack.com/logs)（Better Stack） | UI が綺麗、無料枠あり |
| [Axiom](https://axiom.co/) | Vercel 公式統合あり、無料枠手厚い |
| [Datadog Logs](https://www.datadoghq.com/) | エンタープライズ |
| [CloudWatch Logs](https://aws.amazon.com/cloudwatch/) | AWS スタックなら |

### Vercel + Axiom 連携の例

Vercel ダッシュボード → Integrations → Axiom を追加するだけで、すべての関数のログが Axiom に送られる。

## 8. アクセス解析（プロダクト指標）

エラー監視とは別に、「**どのページがよく見られているか**」「**コンバージョン率**」も取りましょう。

| サービス | 特徴 |
|---------|------|
| **Google Analytics 4** | 無料、定番 |
| **Plausible** | プライバシー重視、軽量、有料 |
| **Vercel Analytics** | 数字シンプル、Vercel デプロイ用 |
| **PostHog** | プロダクト分析（イベント、ファネル） |
| **Mixpanel** | 詳細イベント分析 |

### GA4 の最低設定

```tsx
// app/layout.tsx
import Script from "next/script";

<Script
  src={`https://www.googletagmanager.com/gtag/js?id=${process.env.NEXT_PUBLIC_GA_ID}`}
  strategy="afterInteractive"
/>
<Script id="ga" strategy="afterInteractive">
  {`
    window.dataLayer = window.dataLayer || [];
    function gtag(){dataLayer.push(arguments);}
    gtag('js', new Date());
    gtag('config', '${process.env.NEXT_PUBLIC_GA_ID}');
  `}
</Script>
```

## 9. ログの注意点

### A. 機密情報を絶対に出さない

```ts
// ❌ NG
logger.info("ログイン", { password: input.password });
logger.info("API call", { headers: request.headers }); // Authorization が含まれる！

// ✅ OK
logger.info("ログイン", { email: maskEmail(input.email) });
```

### B. 個人情報の扱い

GDPR や個人情報保護法に従って、ユーザー識別子は**ハッシュ化や匿名化**を検討。

### C. ログのレベルを使い分ける

| レベル | 用途 |
|--------|------|
| `debug` | 開発時の詳細 |
| `info` | 通常の出来事（リクエスト処理など） |
| `warn` | 異常ではないが注意（リトライ発生など） |
| `error` | エラー、対処が必要 |

本番は `info` 以上を残す、`debug` は無効化、が一般的。

## 10. 監視の最低構成（個人プロジェクト向け）

| やること | 工数 |
|---------|------|
| Sentry を導入（無料枠 5K event/月） | 30 分 |
| UptimeRobot で死活監視 | 5 分 |

商用プロダクトなら、これに加えて：

- ログ集約（Axiom / Logtail）
- アクセス解析（GA4 / PostHog）
- アラート（Slack 通知）

## 11. つまずきポイント

### Q. Sentry にエラーが届かない

→ DSN が正しいか、ビルド時に環境変数があるか、ネットワークがブロックしていないか。

### Q. Vercel のログが消えてしまう

→ Hobby は 2 時間、Pro は 7 日間。長期保存は外部送信が必要。

### Q. ログが日本語で文字化け

→ 構造化ログ（JSON）にして UTF-8 で出すと安全。

### Q. アラートが多すぎてノイズ

→ サンプリング率を下げる（`tracesSampleRate`）、エラー種別でフィルタ、Slack の通知ルール調整。

### Q. パフォーマンスが悪化したとき、どこを直せばいいか分からない

→ Sentry Performance や DataDog APM の**スパン**を見ると「DB クエリ」「外部 API 呼び出し」など細かい時間が分かる。

---

## まとめ

- 監視は **エラー / パフォーマンス / ログ / 死活** の 4 種類
- 個人〜中規模なら **Sentry + UptimeRobot + Vercel Speed Insights** で十分
- ログは **構造化（JSON）+ 外部集約**（Axiom 等）
- **機密情報は絶対にログに出さない**
- アラート設定がないと「気づけない」ので、最低限 Slack/メール通知を
