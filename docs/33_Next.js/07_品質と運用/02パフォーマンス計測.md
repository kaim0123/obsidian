# パフォーマンス計測

「速い」「遅い」を**感覚ではなく数字で**測ることが、改善の第一歩です。
Next.js には測定の仕組みが多数あり、Google も明確な指標（Core Web Vitals）を定めています。

---

## 1. 計測すべき主要指標：Core Web Vitals

Google が公式に定めた、**ユーザー体験の質**を測る指標です。SEO にも影響します。

| 指標 | 何を測る | Good 基準 |
|------|----------|----------|
| **LCP** (Largest Contentful Paint) | 最大コンテンツの表示時間 | **2.5 秒以下** |
| **INP** (Interaction to Next Paint) | クリック後の応答性 | **200ms 以下** |
| **CLS** (Cumulative Layout Shift) | レイアウトのガタつき | **0.1 以下** |

その他の補助指標：

| 指標 | 何を測る | 目安 |
|------|----------|------|
| **FCP** (First Contentful Paint) | 最初の描画 | 1.8 秒以下 |
| **TTFB** (Time To First Byte) | 最初のバイト到達 | 800ms 以下 |
| **TBT** (Total Blocking Time) | メインスレッドの詰まり | 200ms 以下 |

## 2. 計測ツール

### A. Lighthouse（Chrome DevTools 内蔵）

1. F12 で DevTools を開く
2. 「Lighthouse」タブ
3. 「Analyze page load」

→ パフォーマンス、SEO、アクセシビリティ、ベストプラクティスを点数化。

### B. PageSpeed Insights

<https://pagespeed.web.dev/> に URL を入れる。

- **実ユーザーの計測値**（CrUX）と
- **Lab 環境での測定値**

の両方が見られる。Vercel デプロイ後の確認に最適。

### C. WebPageTest

<https://www.webpagetest.org/>

- 詳細なウォーターフォール表示
- 複数地域から測定可能
- 上級者向け

### D. Vercel Analytics

Vercel にデプロイしているなら、**実ユーザーの実測値**を取得できます。

```bash
npm install @vercel/analytics
```

```tsx
// app/layout.tsx
import { Analytics } from "@vercel/analytics/react";

export default function RootLayout({ children }: any) {
  return (
    <html>
      <body>
        {children}
        <Analytics />
      </body>
    </html>
  );
}
```

### E. Vercel Speed Insights

```bash
npm install @vercel/speed-insights
```

```tsx
import { SpeedInsights } from "@vercel/speed-insights/next";

<SpeedInsights />
```

→ **Core Web Vitals を実ユーザー単位で計測**してくれる。

## 3. Web Vitals を自分で取る

任意の解析サービスに送りたい場合：

```ts
// app/web-vitals.ts
"use client";
import { useReportWebVitals } from "next/web-vitals";

export function WebVitals() {
  useReportWebVitals((metric) => {
    console.log(metric);
    // GA や自前の API に送る
    fetch("/api/vitals", {
      method: "POST",
      body: JSON.stringify(metric),
      keepalive: true,
    });
  });
  return null;
}
```

## 4. 改善の優先順位（まずここを見る）

### 1. LCP（最大コンテンツ表示）

主犯はだいたい：
- **大きな画像**（Hero）
- **遅いサーバーレスポンス**（TTFB）
- **重い JS でレンダリングをブロック**

対策：
- Hero 画像に **`priority`** を付ける
- 画像を **WebP/AVIF** に
- Server Component で取得して**サーバー側で完結**させる
- `next/font` でフォント読み込み待ちを減らす

### 2. CLS（レイアウトシフト）

主犯：
- 画像/動画の **width/height 未指定**
- フォント読み込みでテキストサイズが変わる
- 後から動的に挿入される要素（広告、埋め込み）

対策：
- `<Image>` を使う（自動でサイズ確保）
- `next/font` を使う（CLS 抑制）
- 動的要素にも**プレースホルダ**でサイズ確保

### 3. INP（応答性）

主犯：
- 重いクライアント JS
- 同期的な大きな処理
- ハイドレーション時の負荷

対策：
- Client Component を**葉に近づける**
- `dynamic import` で初期 JS を減らす
- 重い処理を `useTransition` / `useDeferredValue` に逃がす

## 6. ネットワーク観点の改善

### キャッシュ戦略

- 静的アセット（JS/CSS/画像）は **CDN キャッシュ**（Vercel なら自動）
- API レスポンスは **`Cache-Control` ヘッダ** または `next.revalidate`
- 重い計算結果は **`unstable_cache` / `"use cache"`**

### 並列取得

```ts
const [a, b] = await Promise.all([fetch1(), fetch2()]);
```

逐次より並列の方が速い。Layout と Page で同じ `fetch` を呼んでも自動 dedupe。

### Streaming（`<Suspense>`）

「重い部分は後回し、軽い部分は先に表示」を実現。LCP や FCP の改善に有効。

## 7. 画像とフォント

| 項目 | やること |
|------|---------|
| 画像 | `<Image>` 必須、Hero に `priority`、`sizes` 適切に |
| フォント | `next/font` でセルフホスト、`display: swap` |
| サードパーティスクリプト | `next/script` で `strategy="lazyOnload"` |

### `next/script` の strategy

```tsx
import Script from "next/script";

<Script src="https://example.com/analytics.js" strategy="afterInteractive" />
```

| strategy | タイミング |
|---------|-----------|
| `beforeInteractive` | ページ操作可能になる前 |
| `afterInteractive`（デフォルト） | ページ操作可能になった後 |
| `lazyOnload` | アイドル時 |
| `worker` | Web Worker（実験的） |

GA や広告など**遅延 OK のスクリプト**は `lazyOnload`。

## 8. データベース観点

サーバー側が遅いと LCP も TTFB も悪化します。

- **適切なインデックス**を貼る
- **N+1 クエリ**を撲滅（`include`、`Promise.all`）
- **キャッシュ層**を入れる（Redis 等）
- DB をユーザー近くに（複数リージョン）

## 10. つまずきポイント

### Q. ローカルでは速いのに本番が遅い

→ ローカルは CDN キャッシュ無し、本番は CDN ヒットで実は本番の方が速いことも。
→ DB が遠い／コールドスタートが原因のこともある（Vercel ファンクション）。

### Q. Lighthouse スコアが日によって変わる

→ Lab 環境はばらつきがある。**実ユーザーの計測値**（CrUX、Vercel Analytics）も見ましょう。

### Q. CLS がどうしても下がらない

→ DevTools の Performance タブで「**レイアウトシフトの瞬間**」を確認。広告やバナーが原因のことが多い。

### Q. INP が悪い

→ メインスレッドの長時間処理を疑う。`React.lazy`、`dynamic import` で初期 JS を減らす、`useTransition` で重い更新を非ブロッキングに。

### Q. JS バンドルが大きい原因がわからない

→ Bundle Analyzer で可視化。`moment.js`（→ `date-fns`/`dayjs`）、`lodash` の全 import などが典型的犯人。

---

## まとめ

- **Core Web Vitals**：LCP 2.5s、INP 200ms、CLS 0.1 を目標
- **Vercel Speed Insights** が最も簡単に実ユーザー計測を始められる
- 改善優先：**LCP（画像・サーバー速度）→ CLS（サイズ確保）→ INP（JS 削減）**
- **Bundle Analyzer** で重いライブラリを発見
- 本番では**実ユーザー計測**を継続して見ることが大切
