# 2026年の新機能とプライバシー対応

## 🎯 このページのゴール

- 2026年時点のGA4の **新機能と話題のアップデート** を俯瞰する
- Consent Mode v2（同意モード v2）の基礎と、**日本でも意識すべき理由** を理解する
- 「クライアント側だけでは取り逃がす」時代に必要な **サーバーサイドGTM** の考え方を知る

---

## 1. 2026年の新機能ハイライト

### ① Analytics Advisor（AIアシスタント）

2025年12月に一般公開された、GA4画面内の **AIアシスタント**。

- 「先週と比べてCVが減った理由を要約して」と **自然言語で質問** できる
- 過去の問い合わせ文脈を記憶し、**続き物の会話** として使える
- Ads Advisor と連携して「広告予算の最適な配分」も提案
- ホーム画面には **Generated Insights**（前回アクセス以降の主要3変化のサマリー）が常駐

### ② オンボーディングアシスタント

- 新規プロパティ作成時、業種に応じて **推奨設定をAIが自動提案**
- 初心者がハマりがちなタイムゾーン・通貨・拡張計測のON忘れなどを防げる

### ③ cross-channel budgeting（ベータ）

- Google広告・YouTube・その他チャネルの **予算配分最適化提案**
- GA4とGoogle Adsの双方に統合連携が必要

### ④ 改善されたコンバージョン管理（ベータ）

- Google Ads顧客向けに **Web コンバージョンの管理・レポート機能が改善**
- GA4とAds側で **キーイベント状態が双方向に同期** される

### ⑤ Measurement Protocol の強化

- App ストリーム向けに `screen_view` / `ad_impression` が正式対応
- `timestamp_micros` の上書きが可能
- **EU専用エンドポイント** が提供され、地理的なデータ流通の選択肢が広がる

## 2. Consent Mode v2（同意モード v2）

### なぜ必要？

- GDPR・ePrivacy・CCPAなど **プライバシー規制** が強化され、ユーザーの **明示的な同意なし** にCookieや個人データを広告目的に使うと違反になる
- Googleは「同意したユーザーの情報」と「同意しないユーザーの匿名ping」を **分けて受け取る** 仕組みを導入

### v2 で追加された2つの同意パラメータ

| パラメータ | 意味 |
|-----------|------|
| `ad_user_data` | **広告プラットフォームにユーザーデータを送ってよいか** |
| `ad_personalization` | **そのデータをリマーケティングに使ってよいか** |

従来の `ad_storage`（広告Cookie保存）と `analytics_storage`（分析Cookie保存）にこの2つが加わって **合計4種類** になりました。

### 実装パターン

| モード | 同意拒否時の挙動 | 特徴 |
|-------|----------------|------|
| **基本（Basic）** | タグが **読み込まれない** | 実装が簡単。拒否時のデータはゼロ |
| **高度（Advanced）** | タグは読み込まれ、**匿名化されたping** を送る | Googleが統計的モデリングで欠損を補完できる |

### 日本のサイトも対応すべき？

- 日本の個人情報保護法（**2023年改正Cookie規律**）は、**EU並みの明示同意までは義務化されていない** が、**Cookie使用の告知は必須**
- EUユーザーが1人でも訪れる可能性があれば **Consent Mode v2 は実装推奨**
- Google広告のスマート入札機能（オーディエンス拡張など）は **2026年以降 Consent Mode v2 が前提**

### CMP（Consent Management Platform）との連携

- **CookieHub / OneTrust / Cookiebot / Usercentrics** など。**Google認定CMP** を選ぶのが無難
- CMPが出す同意シグナルを、Googleタグ/GTM側が受け取ってタグの挙動を切り替える
- GTM テンプレートギャラリーに **各CMP公式テンプレート** が並んでいる

### 2026年6月15日の重要変更

- この日以降、**Google Analytics データは Google Signals の制御下**
- **Google Ads データは ad_storage の同意のみで制御**
- GAが Ads データの可否をコントロールする構造が無くなる → **Ads連携時は ad_storage 同意が必須**

## 3. クライアント側計測の限界

2026年現在、クライアント側（ブラウザ）だけのGA4実装では **20〜40% のデータを取りこぼす** と報告されています。原因:

- **広告ブロッカー**: uBlock Origin / AdGuard などがGA4/GTMドメインを遮断
- **Safari ITP** (Intelligent Tracking Prevention): サードパーティCookieを7日で削除
- **Firefox / Brave**: 標準でトラッキング防止
- **iOS の プライバシーリレー**
- **社内ネットワークのプロキシ**

### 対策の方向性

| 手法 | 難度 | 効果 |
|------|------|------|
| Consent Mode Advanced | 低 | 同意拒否ユーザーの統計補完 |
| **サーバーサイドGTM** | 中〜高 | 計測リクエストを自社ドメイン経由にし、ブロッカー回避 |
| First-Party Cookie Mode | 中 | CNAME設定で自社ドメインから `_ga` を発行 |

## 4. サーバーサイドGTM（概念だけ）

従来のGTM（Web版）は **ブラウザ上でタグを発火** しますが、サーバーサイドGTMは:

```
[ブラウザ]
  └ First-Party の自社ドメインにイベント送信
       ↓
[サーバーサイドGTM (Cloud Run 等でホスト)]
  └ ここでGA4やGoogle広告にデータを中継
```

### メリット

- **広告ブロッカーの多くを回避**（自社ドメイン経由のため）
- **個人情報の匿名化・サニタイズ** をサーバー側で行える
- **重要なパラメータだけを送る** プライバシー保護が可能
- ページ表示の **パフォーマンス向上**（ブラウザのJS負荷減）

### デメリット

- **インフラコスト**（Google Cloud Run で月数千円〜）
- **実装難度が一段上がる**（Docker・Cloud Run知識）
- デバッグ環境が複雑化

### まず始めるべきか？

- **月間PVが10万未満のLP** → クライアント側 + Consent Mode で十分
- **広告運用でCV最適化している** / **PVが100万超** → 検討推奨

## 5. プライバシー関連の重要な設定

- **管理 → データ設定 → データ収集**
  - Google Signals: 「ユーザー中心のレポート」に関与（広告オーディエンス作成）
  - **2026年6月15日以降** Google Signals が GA のデータを制御するようになる
- **管理 → データ設定 → データ保持**
  - 初期値2か月 → **14か月に延長推奨**
- **管理 → データフィルタ**
  - 社内IPの除外（開発用トラフィックを本番に混ぜない）
- **管理 → データ削除リクエスト**
  - 誤って個人情報を送ってしまった場合の緊急削除
