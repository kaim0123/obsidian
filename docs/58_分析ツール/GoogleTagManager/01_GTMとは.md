# GTMとは

## 🎯 このページのゴール

- GTM（Google Tag Manager）が **解決する課題** を理解する
- GTMの **3つの中核概念（タグ・トリガー・変数）** の関係を掴む
- GA4 だけで計測するのと **GTMを挟む** のとで、何が違うのかを理解する

---

## 1. GTM が解決する課題

### GTMなしの世界

LPにGA4を設置するだけなら、`<head>` にgtag.jsを1回貼れば済みます。
でも「追加でこんな計測をしたい」と言われた瞬間、HTMLの再改修が必要になります:

- 「お問合せボタンのクリック数を測りたい」 → JSを追加
- 「資料DLボタンのクリック数も測りたい」 → JSを追加
- 「ついでに Meta Pixel も入れたい」 → 別のスニペットを追加
- 「LINE Tag も...」 → さらに追加
- 「スクロール率で分岐して...」 → かなり大変

→ **計測タグが増えるほど HTML が肥大化** し、**変更のたびにエンジニア工数** が要る。

### GTMを入れると

```
[HTML] ── GTMのスニペット1つだけ ──
                   ↓
          [GTMコンテナ（クラウド上の管理画面）]
              ├ GA4タグ
              ├ GA4イベントタグ（CTAクリック用）
              ├ Meta Pixel タグ
              ├ LINE Tag
              └ 他の計測/リマーケタグ
```

- **HTMLに触れるのは1回だけ**
- 以降のタグ追加・編集・配信条件変更は **すべて GTM の画面操作で完結**
- **バージョン管理・公開/差し戻し** がGit的に可能

## 2. GTM の3大要素

```
「トリガー」が発火したら「タグ」を動かす。
タグが必要な値は「変数」で取得する。
```

### ① タグ（Tag）

**実際に発火するコード片**。例:

- 「GA4に `form_submit` イベントを送るタグ」
- 「Meta Pixel に PageView を送るタグ」
- 「カスタムHTML（独自JS）を挿入するタグ」

### ② トリガー（Trigger）

**タグを発火させる条件**。例:

- 「ページビューごとに発火」
- 「クラスが `.btn-contact` のボタンがクリックされたとき」
- 「URLが `/thanks` を含むページを表示したとき」
- 「dataLayer に `form_submit_success` がpushされたとき」

### ③ 変数（Variable）

**動的な値を取り出す仕組み**。例:

- `{{Click URL}}`: クリックされたリンクのURL
- `{{Page Path}}`: 現在のURLパス
- `{{Click Classes}}`: クリックされた要素のclass属性
- 自作のデータレイヤー変数（例: `{{DLV - form_id}}`）

## 3. 実例: 「CTAクリックをGA4に送る」を分解する

目的: LPの "お問い合わせはこちら" ボタンが押された回数を数える。

```
[トリガー]
  種類: クリック（一部の要素）
  条件: Click Classes が 'hero-cta-btn' を含む

[タグ]
  種類: GA4 イベント
  イベント名: cta_click
  パラメータ:
    button_name  = {{Click Text}}
    page_path    = {{Page Path}}

[変数]
  {{Click Text}}   ← ボタンに表示されているテキスト
  {{Click Classes}} ← 上記トリガーの判定用
  {{Page Path}}    ← GA4に送るページ識別用
```

これだけで、**HTMLに手を入れずに** LPのCTAクリックをGA4に送れます。

## 4. GTMの世界の構成要素

```
Googleアカウント
  └ GTMアカウント (通常、会社に1つ)
      └ コンテナ (サイト・アプリ単位)
          ├ ワークスペース (作業環境, 複数人対応)
          ├ タグ
          ├ トリガー
          ├ 変数
          ├ テンプレート (再利用可能なタグ/変数の雛形)
          └ バージョン (公開履歴・ロールバック)
```

### コンテナの種類

GTMコンテナはプラットフォーム別に複数種類あります:

| 種類 | 用途 |
|------|------|
| **Web** | 通常のWebサイト（本ノート群の対象） |
| iOS / Android | Firebase SDK 経由でアプリ計測 |
| AMP | AMPページ用 |
| **Server** | サーバーサイドGTM（Cloud Run等でホスト） |

## 5. GTM の画面構成（2026年現在）

左サイドバーは以下の構成:

| メニュー | 役割 |
|---------|------|
| **ワークスペース（概要）** | 直近の変更履歴・未公開の変更数 |
| **タグ** | タグ一覧・作成 |
| **トリガー** | トリガー一覧・作成 |
| **変数** | 変数一覧・作成 |
| **フォルダ** | タグ/トリガー/変数をフォルダ整理 |
| **テンプレート** | 自作/共有テンプレート |

右上:

- **プレビュー**: Tag Assistant を開いてデバッグ
- **公開**: 変更をバージョン付きで本番反映
- **ワークスペース切替**: 複数人の同時作業用

---

## 6. GTM を使うメリット・デメリット

### メリット

- **非エンジニアでも計測改修が可能**
- **1つの管理画面で複数プラットフォーム** のタグを一元管理
- **プレビュー機能** で本番反映前にテスト可能
- **バージョン管理とロールバック**（間違えても前のバージョンに戻せる）
- **公式テンプレート** が豊富（GA4・Meta・LINE・TikTok・Clarity等）
- **無料** で利用可能

### デメリット

- **学習コスト**（本ノート群の分量）
- **タグの発火順序・条件** を誤るとデータが歪む
- **GTM管理画面の権限設計** が甘いと意図しない変更が入る
- **広告ブロッカーでGTM自体が読み込まれない** 可能性（サーバーサイドGTMで解消）

---

## 7. 2026年時点のGTM新機能

- **AIベースの変数提案**: サイトの挙動を学習し、「このパラメータも送ると分析に有用」と自動提案
- **AI駆動のエラー解決**: 壊れたタグをGTMが検知し、修正案を提示
- **リアルタイム イベント ストリーム**: プレビュー画面のデバッグ UI が強化
- **サーバーサイドGTMの普及**: 2026年の実務では「WebとServer両方」の構成が推奨されるケース増加

---

## 8. GTM と GA4 の役割分担（もう一度整理）

| やること | 担当 |
|---------|------|
| 計測用データの送信制御 | **GTM** |
| 「いつ送るか」のルール | **GTM（トリガー）** |
| 「何の値を送るか」 | **GTM（変数）** |
| 送られたデータの受け取り | GA4 |
| データの集計・可視化 | GA4 |
| CV（キーイベント）のマーク | GA4 |
| レポート作成 | GA4 |

→ **GTMは "運ぶ人"、GA4は "集計する人"** と覚えるのが楽。
