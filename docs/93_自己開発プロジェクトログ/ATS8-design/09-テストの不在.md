# 09. テストが存在しない

## design.md の指摘（❌ 未対応）

> **テストが存在しない**
>
> テストファイル・テストスクリプトともに無し。ビジネスロジック（`fixedTaskConfigs`、`build-events-export`、ステージ遷移など）は単体テストの価値が高い。

---

## 基礎知識：テストとは何のためにあるか

**テスト** = コードが期待どおり動くかを **自動で確認するプログラム** です。

```
開発者がコードを変更
    ↓
テストを実行（npm test）
    ↓
全部 ✅ → 安心してデプロイ
1つ ❌ → どこか壊した。修正してからデプロイ
```

### テストの種類（ざっくり）

| 種類 | 対象 | 速度 | 例 |
|------|------|------|-----|
| **単体テスト** | 関数1つ | 速い | マッパ、バリデーション、計算ロジック |
| **結合テスト** | 複数モジュール | 中 | API + DB（モック） |
| **E2E テスト** | ブラウザ操作 | 遅い | ログイン → 応募者登録 |

ATS8 で **まず入れるべきは単体テスト** です。

---

## 何が間違っているか（現状）

### 問題：テストがゼロ

`package.json` を見ると:

```json
"scripts": {
  "dev": "next dev",
  "build": "next build",
  "start": "next start",
  "lint": "eslint"
}
```

**`test` スクリプトがありません。**  
プロジェクト内に `*.test.ts` / `*.spec.ts` も存在しません。

### なぜ危険か

1. **リファクタリングが怖い** — design.md で直したマッパ集約など、動作確認が手作業だけ
2. **退行（regression）** — 以前直したバグがまた出る
3. **仕様がコードにしかない** — 「この関数は DB 空のとき定数を返す」がテストで文書化されていない
4. **CI で品質ゲートがない** — PR マージ前に自動チェックできない

## テストを書く価値が高い箇所（design.md より）

### 1. `fixedTaskConfigs`

選考段階ごとに **固定タスク**（「面接日程調整」など）を定義する設定。

- 入力: 段階 ID
- 出力: タスクのリスト

**純粋関数** に近い → テストしやすい。

### 2. `build-events-export`

イベントデータを Excel エクスポート用に整形するロジック。

- 日付フォーマット
- 列の並び
- 空データの扱い

**バグると現場で Excel が壊れる** → テスト必須級。

### 3. ステージ遷移ロジック

応募者の選考段階を変更するときのルール。

- どの段階からどこへ移れるか
- 履歴が正しく記録されるか

### 4. マッパ関数（[[06-snake_caseとcamelCaseの変換]]）

```typescript
// 例: selectionStageToCamel
expect(selectionStageToCamel({ display_order: 3, ... }))
  .toEqual({ displayOrder: 3, ... })
```

### 5. `resolveEffectiveSources` / `getSourceDisplayName`（[[05-Source型の二重定義]]）

- DB あり → DB を返す
- DB 空 → 定数フォールバック
- 未知 ID → フォールバック or ID 表示

## どう修正すべきか（ステップバイステップ）

### Step 1: テストランナーを入れる

Next.js プロジェクトでは **Vitest** がよく使われます（Jest より軽量・高速）。

```bash
npm install -D vitest @vitejs/plugin-react
```

`package.json` に追加:

```json
"scripts": {
  "test": "vitest",
  "test:run": "vitest run"
}
```

`vitest.config.ts` をプロジェクトルートに作成（`@/` エイリアスを tsconfig と揃える）。

### Step 2: 最初の1本を書く

```typescript
// features/shared/lib/mappers/selection-stage.test.ts
import { describe, it, expect } from 'vitest'
import { selectionStageToCamel } from './selection-stage'

describe('selectionStageToCamel', () => {
  it('snake_case を camelCase に変換する', () => {
    const result = selectionStageToCamel({
      id: '1',
      name: '書類選考',
      display_order: 2,
      created_at: '2025-01-01',
      updated_at: '2025-01-01',
    })
    expect(result.displayOrder).toBe(2)
    expect(result.createdAt).toBe('2025-01-01')
  })
})
```

```bash
npm test
```

### Step 3: 優先度順に増やす

1. マッパ（入力/output が明確）
2. `features/shared/sources.ts`（分岐が多い）
3. `fixedTaskConfigs`
4. `build-events-export`
5. API Route Handler（Supabase をモック）

### Step 4: CI に組み込む（任意）

GitHub Actions で PR 時に `npm test:run` を実行。

## テストを書くときのコツ（初心者向け）

### AAA パターン

```typescript
it('〜のとき〜する', () => {
  // Arrange（準備）— 入力データを用意
  const input = { ... }

  // Act（実行）— テスト対象を呼ぶ
  const result = myFunction(input)

  // Assert（検証）— 期待と比較
  expect(result).toBe(...)
})
```

### 1テスト1断言に近づける

「A も B も C も確認」より、「displayOrder が変換される」に絞ると、失敗時に原因が分かりやすい。

### UI は後回しで OK

React コンポーネントのテストは set up が重い。**ロジック関数から** 始める。

## まとめ

| 現状 | 目標 |
|------|------|
| テスト 0 件 | ビジネスロジックから単体テスト追加 |
| test スクリプトなし | Vitest + `npm test` |
| 手動確認のみ | マッパ・sources・export を自動化 |

**学び**: テストは「余裕があるときのおまけ」ではなく、**リファクタリングと機能追加の安全网** です。ATS8 は design.md で大量の構造改善を済ませているので、今テストを入れるタイミングとして最適です。
