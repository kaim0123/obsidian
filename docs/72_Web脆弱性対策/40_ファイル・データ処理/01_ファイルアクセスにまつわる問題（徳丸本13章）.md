# 安全なWebアプリケーションの作り方（第13章）

Webアプリは、画像・PDF・設定ファイルなど **サーバー上のファイル** を読み書きすることがあります。第13章では、ファイルアクセスまわりで起きやすい脆弱性と対策を解説します。

---

## 📁 ファイルアクセスの問題の概要

ファイルアクセス機能には、主に次の問題があります。

| 問題 | 概要 |
|------|------|
| **ディレクトリ・トラバーサル** | 外部入力でパスを操作され、本来見えないファイルを読まれる・改ざんされる |
| **意図しないファイル公開** | 秘密にすべきファイルが公開ディレクトリに置かれ、URL を知られると誰でも見られる |

### 日常生活での例え

- **正常なファイルアクセス**: 自分のプロフィール画像だけが表示される
- **攻撃された場合**: パスワード一覧や設定ファイルなど、サーバー内の秘密ファイルまで見られてしまう

### なぜ危険か

Webアプリは、サーバー上のファイルを **読み書きする権限** を持っています。その権限が悪用されると、次のような被害が出ます。

```
・設定ファイルやパスワード情報の漏洩
・ソースコードの漏洩
・ログや個人情報ファイルの閲覧
・ファイルの改ざん・削除によるサービス妨害
```

---

## 📂 ディレクトリ・トラバーサル

**ディレクトリ・トラバーサル（Directory Traversal）** とは、外部から渡されたファイル名やパスをそのまま使い、**本来アクセスしてはいけないディレクトリやファイル** にたどり着いてしまう脆弱性です。

「トラバーサル」は「横断する・渡り歩く」という意味です。ディレクトリの境界を越えて、別の場所のファイルへアクセスされるイメージです。

### 日常生活での例え

- **正常**: 「自分の部屋の引き出し」だけ開ける
- **攻撃**: 「../」で廊下に出て、隣の部屋や金庫まで開けてしまう

### 何ができるか（被害）

| 被害 | 説明 |
|------|------|
| **Webサーバー内のファイルの閲覧** | 設定ファイル、パスワード、ソースコード、ログなどを読まれる |
| **Webサーバー内のファイルの改ざん・削除** | 書き込み権限がある場合、内容の書き換えや削除ができる |

閲覧だけでも十分危険です。書き込みまでできると、サイトの改ざんやサービス停止につながります。

### 攻撃のイメージ

たとえば、画像を表示する機能が次のような URL だとします。

```
https://example.com/download.php?file=photo.jpg
```

アプリが `file` パラメータをそのままパスに連結している場合:

```
【正常な入力】
file=photo.jpg
→ /var/www/uploads/photo.jpg を読む（想定どおり）

【攻撃者の入力】
file=../../etc/passwd
→ /var/www/uploads/../../etc/passwd
→ /etc/passwd を読む（想定外のファイル）
```

`../` は「ひとつ上のディレクトリへ移動する」という意味です。これを繰り返すと、公開用フォルダの外へ出ていけます。

```
/var/www/uploads/photo.jpg     ← 本来の場所
/var/www/uploads/../           ← ひとつ上（/var/www/）
/var/www/uploads/../../        ← さらに上（/var/）
/var/www/uploads/../../etc/passwd  ← OS のユーザー一覧など
```

Windows 環境では `..\..\windows\win.ini` のような形でも同様の問題が起きます。絶対パス（`/etc/passwd` や `C:\...`）を直接指定できる場合もあります。

### 攻撃の流れ

```
1. 攻撃者が「ファイル名をパラメータで受け取る」機能を見つける
2. file=../../etc/passwd のようにパスを操作した値を送る
3. アプリが入力値をそのままファイルパスに使う
4. アクセス可否のチェックがないため、秘密ファイルが読まれる
5. 設定情報・パスワード・ソースコードなどが漏洩する
```

### 脆弱性が生まれる原因

次の条件がそろうと、ディレクトリ・トラバーサルが起きやすくなります。

| 原因 | 説明 |
|------|------|
| **ファイル名を外部から指定できる** | URL やフォームのパラメータでファイル名を受け取っている |
| **絶対パスや相対パスで別ディレクトリを指定できる** | `../` や `/etc/passwd` のような入力がそのまま通る |
| **組み立てたファイル名のアクセス可否をチェックしていない** | 「許可されたフォルダ内か」を確認していない |

特に危険なのは、**「ユーザーが指定した名前のファイルを開く」** という仕様そのものです。ダウンロード機能、画像表示、テンプレート読み込みなどでよく見られます。

### 脆弱なコードの例

```php
// ❌ 危険: 外部入力をそのままパスに使っている
$file = $_GET['file'];
$path = '/var/www/uploads/' . $file;
readfile($path);
```

```
リクエスト例:
  /download.php?file=../../config/database.php

結果:
  /var/www/uploads/../../config/database.php
  → /var/www/config/database.php が読まれる
```

## 🛡️ ディレクトリ・トラバーサルの対策

対策の基本は **「外部から自由にパスを指定させない」** ことです。

### 1. 外部からファイル名を指定できる仕様を避ける

最も安全なのは、**ユーザーにファイル名やパスを直接渡させない** ことです。

```
❌ 悪い例
  /download.php?file=report.pdf
  → ファイル名そのものを外部から受け取る

✅ 良い例
  /download.php?id=123
  → ID だけ受け取り、サーバー側で対応するファイルを決める
```

| 方針 | 説明 |
|------|------|
| **ID で管理する** | DB に「ID ↔ 実ファイルパス」を持ち、外部には ID だけ渡す |
| **固定パスを使う** | 読み込むファイルをアプリ側で決め打ちする |
| **選択肢を限定する** | 「avatar」「banner」など許可したキーだけ受け付ける |

```php
// ✅ 良い例: ID からサーバー側でパスを決める
$id = (int)($_GET['id'] ?? 0);

// DB から「このユーザーがアクセスしてよいファイル」を取得
$stmt = $pdo->prepare('SELECT path FROM files WHERE id = ? AND user_id = ?');
$stmt->execute([$id, $currentUserId]);
$row = $stmt->fetch();

if (!$row) {
    exit('ファイルが見つかりません');
}

readfile($row['path']);
```

### 2. ファイル名にディレクトリが含まれないようにする

どうしてもファイル名を受け取る場合は、**ディレクトリ区切り文字を除去・拒否** します。

```php
// ✅ ディレクトリ部分を取り除き、ファイル名だけ残す
$file = $_GET['file'] ?? '';
$basename = basename($file);  // "a/b/c.txt" → "c.txt"

// 許可ディレクトリ配下に限定
$baseDir = '/var/www/uploads/';
$path = $baseDir . $basename;

// 念のため、解決後のパスが許可ディレクトリ内か確認
$realBase = realpath($baseDir);
$realPath = realpath($path);

if ($realPath === false || strpos($realPath, $realBase) !== 0) {
    exit('不正なファイル指定です');
}

readfile($realPath);
```

| チェック | 目的 |
|----------|------|
| **`basename()`** | `../` や `/` を含むパスからファイル名だけ取り出す |
| **`realpath()`** | シンボリックリンクや `../` を解決した実パスを得る |
| **許可ディレクトリ内か確認** | 解決後のパスが想定フォルダの外に出ていないか見る |

`basename()` だけでは不十分な場合もあるため、**最終パスが許可ディレクトリ内か** を必ず確認します。

### 3. ファイル名を英数字に限定する

ファイル名に使える文字を **英数字（と必要なら `_` `.` `-`）だけ** に限定すると、`../` や絶対パスを入れにくくなります。

```php
// ✅ 英数字・アンダースコア・ハイフン・ドットのみ許可
$file = $_GET['file'] ?? '';

if (!preg_match('/\A[a-zA-Z0-9._-]+\z/', $file)) {
    exit('不正なファイル名です');
}

// 先頭のドット（隠しファイル）や ".." も拒否
if ($file === '.' || $file === '..' || str_starts_with($file, '.')) {
    exit('不正なファイル名です');
}

$path = '/var/www/uploads/' . $file;
```

| 方針 | 安全性 | 説明 |
|------|--------|------|
| **外部からファイル名を受け取らない** | 最も安全 | ID 管理など |
| **英数字に限定 + 許可ディレクトリ確認** | 安全 | どうしても名前を受け取る場合 |
| **`basename()` だけ** | 不十分になりやすい | 他のチェックと組み合わせる |

## 🔓 意図しないファイル公開

**意図しないファイル公開** とは、本来インターネットに出してはいけないファイルが、**公開ディレクトリに置かれ、URL を知られれば誰でもアクセスできる** 状態になる問題です。

ディレクトリ・トラバーサルのように「パスを操作して侵入する」のではなく、**最初から公開場所に置いてしまっている** 点が違います。

### 日常生活での例え

- **正常**: 貴重品は鍵付きの金庫（非公開ディレクトリ）に入れる
- **問題**: 貴重品を玄関先（公開ディレクトリ）に置きっぱなしにし、住所（URL）を知った人なら誰でも持っていける

### 脆弱性が生まれる原因

次の3つがそろうと、意図しない公開が起きます。

| 原因 | 説明 |
|------|------|
| **ファイルが公開ディレクトリに置かれている** | Web サーバーが直接配信できる場所にある |
| **ファイルに対する URL を知る手段がある** | 推測・一覧表示・エラー・検索エンジンなど |
| **ファイルに対するアクセス制限が掛かっていない** | ログイン不要で誰でも取得できる |

公開ディレクトリとは、たとえば次のような場所です。

```
/var/www/html/          ← ここ以下は URL で直接アクセスされやすい
/var/www/html/uploads/
/var/www/html/files/

/var/www/data/          ← ドキュメントルートの外（非公開にしやすい）
```

### URL を知られてしまう典型パターン

「URL を知る手段」には、次のようなものがあります。

| パターン | 説明 |
|----------|------|
| **ディレクトリ・リスティングが有効** | フォルダにアクセスするとファイル一覧が表示される |
| **ファイル名が類推可能** | 日付・ユーザー名・連番など、規則から推測できる |
| **エラーメッセージや他の脆弱性** | パス名が画面やログに出てしまう |
| **検索エンジンに登録される** | 外部サイトからリンクされ、Google 等に載る |

#### ディレクトリ・リスティング

Web サーバーの設定で、ディレクトリ一覧表示が有効だと次のように見えます。

```
Index of /backup/

  backup_20260101.sql
  backup_20260201.sql
  users.csv
```

一覧が出るだけで、攻撃者は欲しいファイルの URL をそのまま知ることができます。

#### 類推可能なファイル名

```
❌ 推測されやすい例
  /files/user_1.pdf
  /files/user_2.pdf
  /reports/2026-07-04.xlsx
  /backup/backup.sql

✅ 推測しにくい例（それでも公開ディレクトリに置くのは非推奨）
  /files/a8f3c2e91b0d4f77.pdf
```

連番や日付だと、1件見つかれば前後を総当たりできます。

#### エラーメッセージ・他の脆弱性

```
Warning: fopen(/var/www/html/secret/config.php): failed to open stream
```

このようなメッセージから、秘密ファイルのパスが分かることがあります。ディレクトリ・トラバーサルや XSS など、別の脆弱性と組み合わさるとさらに危険です。

#### 検索エンジンへの登録

一時的に置いたバックアップやテスト用ファイルが、外部からリンクされたりクロールされたりして、検索結果に出ることがあります。

```
site:example.com filetype:sql
site:example.com filetype:env
```

このような検索で、意図せず公開されたファイルが見つかるケースがあります。

### 攻撃の流れ

```
1. バックアップや設定ファイルが公開ディレクトリに置かれている
2. ディレクトリ一覧・推測・エラー・検索エンジンなどで URL が分かる
3. ブラウザやツールでその URL にアクセスする
4. 認証なしでファイルの中身が取得される
5. 個人情報・パスワード・ソースコードなどが漏洩する
```

## 🛡️ 意図しないファイル公開の対策

対策の基本は **「秘密ファイルを公開ディレクトリに置かない」** ことです。

### 1. アプリケーション設計時に、ファイルの安全な格納場所を決める

設計の段階で、「公開してよいもの」と「公開してはいけないもの」を分けます。

```
【公開してよい】
  ・CSS / JavaScript / ロゴ画像など、誰が見てもよい静的ファイル
  ・公開用の商品画像など

【公開してはいけない】
  ・設定ファイル（DB パスワードなど）
  ・アップロードされた個人の書類
  ・バックアップ、ログ、ソースコード
  ・.env、秘密鍵、証明書
```

```
✅ 推奨構成のイメージ

/var/www/
  html/                 ← ドキュメントルート（公開）
    index.php
    assets/css/
    assets/js/
  data/                 ← 非公開（ドキュメントルートの外）
    uploads/
    config/
    logs/
  app/                  ← アプリケーション本体（非公開）
    src/
```

公開が必要なファイルだけを、アプリ経由で配信します。

```php
// ✅ 非公開ディレクトリのファイルを、権限チェック後にだけ返す
session_start();
if (empty($_SESSION['user_id'])) {
    http_response_code(403);
    exit('ログインが必要です');
}

$id = (int)($_GET['id'] ?? 0);
// DB で「このユーザーのファイルか」を確認したうえで配信
// readfile('/var/www/data/uploads/...');
```

| 方針 | 説明 |
|------|------|
| **非公開ディレクトリに置く** | ドキュメントルートの外に保存する |
| **アプリ経由で配信する** | 認証・認可を通したあとだけ中身を返す |
| **直接 URL で取れないようにする** | Web サーバーがファイルを直接配信しない |

### 2. レンタルサーバーでは非公開ディレクトリが使えるか確認する

レンタルサーバーでは、公開ディレクトリしか使えないプランもあります。契約前・利用開始時に次を確認します。

| 確認項目 | 理由 |
|----------|------|
| **非公開ディレクトリがあるか** | 秘密ファイルを置ける場所が必要 |
| **ドキュメントルートを変更できるか** | `public/` だけを公開する構成にできるか |
| **`.htaccess` 等でアクセス拒否できるか** | やむを得ず公開配下に置く場合の防御 |

非公開ディレクトリが使えない場合の応急策:

```apache
# .htaccess の例: secret フォルダへの直接アクセスを拒否
# （可能なら、そもそも公開配下に置かない方がよい）
<IfModule mod_authz_core.c>
    Require all denied
</IfModule>
```

これは **最後の手段** です。設定ミスやサーバー種別の違いで効かないこともあるため、設計としては非公開ディレクトリを使う方が安全です。

### 3. あわせてやっておくとよいこと

| 対策 | 説明 |
|------|------|
| **ディレクトリ・リスティングを無効化** | ファイル一覧が出ないようにする |
| **推測されにくいファイル名** | ただし「名前を隠すだけ」では不十分 |
| **エラーメッセージを詳細に出さない** | 本番ではパス名を画面に出さない |
| **バックアップを公開配下に置かない** | `.sql` `.zip` `.bak` などを特に注意 |
| **検索エンジン対策だけに頼らない** | `robots.txt` は「見ないで」と頼むだけで、取得自体は防げない |

```
❌ よくある失敗
  /var/www/html/backup.sql
  /var/www/html/.env
  /var/www/html/config.php.bak
  /var/www/html/uploads/../../ のような相対配置の誤解

✅ 基本方針
  秘密のものはドキュメントルートの外へ
  必要な人にだけ、アプリが権限チェックして渡す
```

## 📋 まとめ

| 問題 | 本質 | 対策の要点 |
|------|------|------------|
| **ディレクトリ・トラバーサル** | 外部入力でパスを操作される | ファイル名を外部から指定させない。どうしても受け取るなら英数字限定 + 許可ディレクトリ内か確認 |
| **意図しないファイル公開** | 秘密ファイルが公開場所にある | 設計時に格納場所を分ける。非公開ディレクトリを使う。アプリ経由で権限チェックして配信する |

```
ファイルアクセス安全の基本:

1. ユーザーにパスやファイル名を自由に指定させない
2. 秘密ファイルは公開ディレクトリに置かない
3. どうしても渡すときは「誰の・どのファイルか」をサーバー側で決めて検証する
```
