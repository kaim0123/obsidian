# 安全なWebアプリケーションの作り方（第17章）

Webアプリは、設定・API・セッションなど、**決まった形（構造）を持つデータ** を読み込むことがよくあります。第17章では、そのときに起きやすい次の問題を解説します。

| 問題 | 概要 |
|------|------|
| **Evalインジェクション** | 文字列をプログラムとして実行する機能に、外部入力を渡してしまう |
| **安全でないデシリアライゼーション** | オブジェクト復元処理に、改ざんされたデータを渡してしまう |
| **XML外部実体参照（XXE）** | XML の「外部ファイルを読み込む機能」を悪用される |

第14〜16章は「コマンド」「ファイル」「インクルード」など、**実行やファイル操作そのもの** が中心でした。本章は、**データを読み込む処理の中に、意図しない命令やファイルアクセスが紛れ込む** 点がポイントです。

---

## 📎 構造化データの読み込みにまつわる問題の概要

「構造化データ」とは、単なる文章ではなく、**プログラムが解釈できる決まった形式** のデータです。

| 形式の例 | よくある用途 |
|----------|--------------|
| **プログラムの文字列** | 計算式や設定を動的に評価する（`eval` など） |
| **シリアライズ形式** | オブジェクトを保存・復元する（PHP の `serialize` など） |
| **XML / JSON** | API や設定ファイル、外部システムとのデータ交換 |

便利な一方で、読み込み処理が「ただの値」ではなく「命令」や「ファイル参照」まで解釈してしまうと、攻撃につながります。

### 日常生活での例え

- **正常**: 注文票に「商品名・個数」だけが書いてあり、厨房はそのとおり作る
- **攻撃された場合**: 注文票に「商品名」のふりをして「金庫を開けろ」と書かれ、厨房がそれを作業指示として実行してしまう

### なぜ危険か

構造化データの読み込みは、アプリが **「外部から来た文字列を、プログラムの一部として解釈する」** ことがある、ということです。悪用されると、次のような被害が出ます。

```
・設定ファイルやソースコードなどの情報漏洩
・サイトの見た目や内容の改ざん
・不正な機能の実行（管理者権限の操作など）
・他サイトへの攻撃の踏み台にされる
・サーバーの CPU を使った暗号通貨の採掘
```

被害の種類は第14〜16章と似ています。違いは、入り口が「コマンド文字列」や「ファイル名」ではなく、**データの読み込み・復元処理** である点です。

---

## 💥 Evalインジェクションとは

**Evalインジェクション** とは、`eval` のように **文字列をプログラムとして実行する機能** に、外部からの入力を渡してしまい、攻撃者が意図したコードまで動かされてしまう脆弱性です。

PHP の `eval`、JavaScript の `eval`、Python の `eval` / `exec`、一部のテンプレートエンジンや式評価ライブラリなど、「文字列をコードとして動かす」機能が対象になります。

| 項目 | 内容 |
|------|------|
| **分類** | インジェクション系脆弱性 |
| **インターフェース** | 言語の式評価・動的実行機能 |
| **悪用手口** | 計算式や設定のふりをして、任意のコードを実行させる |

### 日常生活での例え

- **正常**: 「1 + 2 を計算して」と頼むと、答えの `3` が返る
- **攻撃**: 「1 + 2。ついでに金庫の鍵も開けて」と書かれ、計算以外の作業まで実行される

### 攻撃のイメージ

たとえば、簡単な計算機機能が次のような URL だとします。

```
https://example.com/calc.php?expr=1+2
```

アプリが `expr` パラメータをそのまま `eval` に渡している場合:

```
【正常な入力】
expr=1+2
→ eval("1+2") を実行（想定どおり、結果は 3）

【攻撃者の入力（イメージ）】
expr=1; system('cat /etc/passwd');
→ 計算のあとに、サーバー上のコマンドまで実行される
```

「計算式を受け取る」つもりが、実際には **プログラム全体を受け取る窓口** になってしまっています。

### 攻撃の流れ

```
1. 攻撃者が「外部入力を eval に渡す」機能を見つける
2. 計算式や設定値のふりをして、任意コードを含む文字列を送る
3. アプリが入力値をそのまま eval に渡す
4. 言語処理系が文字列をプログラムとして実行する
5. 情報漏洩・改ざん・不正操作・他サイト攻撃などが起きる
```

## 🚨 Evalインジェクションで何ができるか（被害）

`eval` で任意コードが動くと、Webアプリが持つ権限の範囲で、ほぼ何でもできます。代表的な影響は次のとおりです。

| 影響 | 説明 |
|------|------|
| **情報漏洩** | 設定ファイル、ソースコード、データベース内容などを読み出される |
| **サイト改ざん** | ページや設定を書き換え、偽情報や不正なリンクを載せる |
| **不正な機能実行** | 管理者だけができる操作を勝手に行う |
| **他サイトへの攻撃** | 自サーバーを踏み台にし、別のサイトへ攻撃する |
| **暗号通貨の採掘** | サーバーの CPU を使い、攻撃者のための採掘プログラムを動かす |

第14章の OSコマンド・インジェクションや、第16章の任意スクリプト実行と同様、**サーバーの乗っ取りに近い状態** になります。

### 1. 情報漏洩

攻撃者がサーバー上でコードを実行できると、アプリから見えるファイルやデータを読み出せます。

```
【起きうること】
・データベースの接続情報（パスワードなど）の取得
・ソースコードや設定ファイルの閲覧
・利用者の個人情報の不正取得
```

### 2. サイト改ざん・不正な機能実行

コード実行ができれば、ファイルの書き換えや、アプリ内部の処理の呼び出しも可能です。

```
【起きうること】
・トップページへの不正な広告・マルウェア配布リンクの埋め込み
・管理者権限でのユーザー操作
・データベースの読み取り・書き換え・削除
```

### 3. 他サイトへの攻撃・暗号通貨の採掘

乗っ取られたサーバーは、攻撃者にとって便利な計算資源・踏み台になります。

```
【起きうること】
・別サイトへの攻撃リクエストの送信
・迷惑メールの送信元になる
・CPU を使い果たす暗号通貨採掘（サーバーが極端に遅くなる）
```

暗号通貨の採掘は、見た目の改ざんほど派手ではありませんが、**電気代・クラウド料金の増大** や **サービス品質の低下** として被害が出ます。

## 🔍 Evalインジェクションが生まれる原因

Evalインジェクションは、次の条件がそろうと起きやすくなります。

| 原因 | 説明 |
|------|------|
| **Evalを用いることがそもそも危険である** | 文字列をコードとして実行する機能自体が、攻撃の入り口になりやすい |
| **Evalに与えるパラメータのチェックがされていない** | 外部入力をそのまま渡し、文字種や内容の制限がない |

特に危険なのは、**「ユーザーが入力した文字列を eval する」** という仕様そのものです。

よくある実装例:

```
・簡易計算機: ?expr=1+2 → eval($expr)
・動的な並び替え: ?sort=price*qty → eval(...)
・設定式の評価: 管理画面で入力した式をそのまま実行
```

便利に見えますが、入力が「数式」ではなく「任意のプログラム」として解釈されると攻撃対象になります。

### 脆弱なコードの例

```php
// ❌ 危険: 外部入力をそのまま eval している
$expr = $_GET['expr'];
$result = eval('return ' . $expr . ';');
echo $result;
```

```
リクエスト例:
  /calc.php?expr=1; system('id'); //

eval に渡されるイメージ:
  return 1; system('id'); //;
→ 計算以外の処理まで実行される
```

## 🛡️ Evalインジェクションの対策

対策の基本は次の3つです。優先順位が高いものから並べています。

| 対策 | 安全性 | 説明 |
|------|--------|------|
| **Evalに相当する機能を使わない** | 最も安全 | そもそも動的実行の入り口を作らない |
| **Evalの引数に外部からのパラメータを含めない** | とても安全 | 使う場合でも、外部入力は渡さない |
| **Evalに与える外部からのパラメータを英数字に限定する** | 安全寄り | やむを得ない場合の最後の手段 |

### 1. Evalを使わない（最優先）

いちばん安全なのは、**`eval` 相当の機能を使わない** ことです。

多くの場合、`eval` がなくても実装できます。

| やりたいこと | eval を使わない方法の例 |
|--------------|-------------------------|
| **四則演算** | 専用の数式パーサ、または許可した演算だけを自分で解釈する |
| **並び替えキーの指定** | `price` / `name` などのキーを受け取り、許可リストで SQL や比較処理を選ぶ |
| **設定の切り替え** | `if` / `switch` / 連想配列で分岐する |

```php
// ✅ 安全: 許可リストで処理を選ぶ（eval 不要）
$ops = [
    'add' => fn($a, $b) => $a + $b,
    'sub' => fn($a, $b) => $a - $b,
];

$op = $_GET['op'] ?? '';
$a = (int)($_GET['a'] ?? 0);
$b = (int)($_GET['b'] ?? 0);

if (!isset($ops[$op])) {
    exit('不正な操作です');
}

echo $ops[$op]($a, $b);
```

### 2. Evalの引数に外部からのパラメータを指定しない

どうしても `eval` が必要な場合でも、**外部入力を引数に混ぜない** ことが重要です。

```php
// ✅ 比較的安全: eval する文字列はアプリ側で固定
// （ただし、eval 自体は避ける方がよい）
$code = 'return 1 + 2;';
$result = eval($code);
```

「固定のコードだけを eval する」ならインジェクションにはなりません。ただし、将来だれかが外部入力を足してしまうリスクがあるため、**そもそも使わない設計** が望ましいです。

### 3. 外部からのパラメータを英数字に制限する

やむを得ず外部入力を使う場合は、**使える文字を英数字だけに限定** します。記号や空白、引用符が入ると、文の区切りや関数呼び出しを作れます。

```php
// ✅ 英数字のみ許可（命令の追加を入れにくくする）
$expr = $_GET['expr'] ?? '';

if (!preg_match('/\A[a-zA-Z0-9]+\z/', $expr)) {
    exit('不正な入力です');
}

// それでも eval は推奨しない。許可リストで値を決める方が安全
```

英数字限定は「記号による命令追加」を防ぎやすくしますが、`eval` を使い続ける限りリスクは残ります。**可能なら eval 自体をやめる** のが本筋です。

### 対策の優先順位

```
1. Eval に相当する機能を使わない
2. 使う場合でも、引数に外部からのパラメータを含めない
3. どうしても外部入力が必要なら、英数字に限定し、許可リストで処理する
```

## 💣 安全でないデシリアライゼーションとは

**安全でないデシリアライゼーション（Insecure Deserialization）** とは、オブジェクトなどを保存した形式（シリアライズ形式）を復元するときに、**攻撃者が改ざんしたデータを渡され、意図しないオブジェクトや処理が動いてしまう** 脆弱性です。

| 用語 | 意味 |
|------|------|
| **シリアライズ** | オブジェクトを、保存や通信できる文字列・バイト列に変換すること |
| **デシリアライズ** | その文字列・バイト列から、オブジェクトを復元すること |

PHP の `unserialize`、Java の `ObjectInputStream`、Python の `pickle`、.NET の BinaryFormatter などが代表例です。これらは「データ」だけでなく、**オブジェクトの種類や、復元時に走る処理** まで表現できることがあります。

### 日常生活での例え

- **正常**: 「預かり証」を見せると、預けた荷物だけが返ってくる
- **攻撃**: 預かり証を偽造し、「荷物」のふりをして「爆弾」や「金庫の鍵」を受け取らせる

JSON が「値のメモ」だとすると、一部のシリアライズ形式は「値」に加えて「どんな種類の物か」「戻したときに何をするか」まで書ける、より強力な預かり証です。

### 攻撃のイメージ

たとえば、ユーザー設定をクッキーにシリアライズして保存しているとします。

```
【正常な利用】
クッキー: シリアライズされた「一般ユーザー設定」
→ unserialize して設定を復元（想定どおり）

【攻撃者の操作】
クッキーを改ざんし、危険なオブジェクトを含むシリアライズ文字列に差し替える
→ unserialize 時に、意図しないクラスのオブジェクトが作られる
→ その過程でファイル削除・コマンド実行などが起きる場合がある
```

ポイントは、**アプリが「自分で保存したデータ」だと思って復元しているのに、実際には利用者が書き換えられる場所（クッキーや Hidden パラメータ）に置いている** ことです。

### 攻撃の流れ

```
1. アプリがシリアライズ形式のデータをクッキーや Hidden などで受け取る
2. 攻撃者がそのデータを改ざんし、悪意あるオブジェクト定義に差し替える
3. アプリが unserialize 等で復元する
4. 復元処理や、その後のオブジェクト利用で意図しない処理が動く
5. 情報漏洩・改ざん・不正操作・他サイト攻撃などが起きる
```

## 🚨 安全でないデシリアライゼーションで何ができるか（被害）

影響は Evalインジェクションとほぼ同種で、条件次第では任意コード実行まで至ります。

| 影響 | 説明 |
|------|------|
| **情報漏洩** | ファイルや内部データの読み出し |
| **サイト改ざん** | ファイルや設定の書き換え |
| **不正な機能実行** | アプリ内部の処理を不正に動かす |
| **他サイトへの攻撃** | 踏み台として悪用される |
| **暗号通貨の採掘** | サーバー資源の不正利用 |

言語やライブラリによって「復元時に自動で危険な処理が走るか」は違いますが、初心者のうちは **「外部から来たシリアライズデータをそのまま復元するのは危険」** と覚えておけば十分です。

### 脆弱なコードの例

```php
// ❌ 危険: 利用者が書き換えられるクッキーをそのまま unserialize
$data = unserialize($_COOKIE['prefs']);
// $data を設定オブジェクトとして利用...
```

クッキーはブラウザ側で自由に書き換えられます。「サーバーが保存したはずのデータ」でも、利用者の手元を経由すると信頼できません。

## 🛡️ 安全でないデシリアライゼーションの対策

対策の基本は次のとおりです。

| 対策 | 安全性 | 説明 |
|------|--------|------|
| **シリアライズ・デシリアライズ機能を使わない** | 最も安全寄り | 特に外部入力に対しては使わない |
| **デシリアライズ処理に外部からのパラメータを含めない** | とても安全 | 復元対象を外部から渡さない |
| **JSON 形式でデータを受け渡す** | 安全寄り | 「値」だけを扱い、オブジェクト復元の罠を避ける |
| **セッション変数など、書き換えできない場所で持つ** | 安全寄り | 利用者の手元を経由させない |
| **HMAC などで改ざん検知する** | 補助的 | どうしてもクライアント側に置く場合の保険 |

### 1. シリアライズ形式ではなく JSON 形式で受け渡す

外部とやり取りするデータは、**オブジェクト復元機能を持たない JSON** を使うのが基本です。

```php
// ✅ 安全寄り: JSON は「値」のやり取り向き
$prefs = json_decode($_COOKIE['prefs'] ?? '{}', true);

// 使う前に型やキーを検証する
$name = $prefs['name'] ?? '';
if (!is_string($name) || !preg_match('/\A[a-zA-Z0-9_]{1,20}\z/', $name)) {
    $name = 'guest';
}
```

| 比較 | シリアライズ形式（例: PHP serialize） | JSON |
|------|----------------------------------------|------|
| **表現するもの** | オブジェクトの種類や状態まで含むことがある | 主に文字列・数値・配列などの値 |
| **復元時のリスク** | 意図しないクラス生成・処理実行がありうる | 値の読み取りが中心（別途検証は必要） |
| **外部入力との相性** | 悪い | 比較的よい |

JSON なら絶対安全、という意味ではありません。中身の検証は必要です。ただし、**「復元しただけで危険なオブジェクトが動く」** タイプの事故は起きにくくなります。

### 2. クッキーや Hidden ではなく、セッション変数で持つ

シリアライズ形式のデータを使う必要がある場合でも、**利用者が書き換えられない場所** に置きます。

```php
// ❌ 危険: 利用者の手元（クッキー）に置く
setcookie('prefs', serialize($prefs));

// ✅ 安全寄り: サーバー側のセッションに置く
session_start();
$_SESSION['prefs'] = $prefs;
```

| 置き場所 | 利用者が書き換えられるか | 評価 |
|----------|--------------------------|------|
| **クッキー** | できる | 危険 |
| **Hidden パラメータ** | できる | 危険 |
| **セッション変数** | 通常はできない | 安全寄り |
| **サーバー側 DB / キャッシュ** | できない | 安全寄り |

「自分で serialize したデータを、あとで unserialize する」場合でも、そのデータを **利用者のブラウザ経由で運ぶ** と改ざんされます。運ぶなら、サーバー側だけに閉じるのが安全です。

### 3. HMAC などで改ざんされていないことを確認する

どうしてもクッキーなどに置く必要がある場合は、**改ざん検知（HMAC など）** を付けます。

```php
// ✅ 改ざん検知付き（概念例）
$payload = json_encode($prefs);
$sig = hash_hmac('sha256', $payload, $serverSecret);
setcookie('prefs', $payload . '.' . $sig);

// 受け取り時
[$payload, $sig] = explode('.', $_COOKIE['prefs'], 2);
$expected = hash_hmac('sha256', $payload, $serverSecret);

if (!hash_equals($expected, $sig)) {
    exit('改ざんの可能性があります');
}

$prefs = json_decode($payload, true);
```

```
【ポイント】
・サーバーだけが知る秘密鍵で署名する
・受け取り時に署名を検証し、一致しなければ拒否する
・署名検証前に unserialize しない（先に改ざんチェック）
```

HMAC は「改ざんされていないこと」を確認できます。ただし、**署名付きでもシリアライズ形式のまま復元するのは避け、JSON にする方がよい** です。署名は保険であり、危険な復元処理そのものをなくす方が本筋です。

### 対策の優先順位

```
1. 外部入力に対してシリアライズ・デシリアライズを使わない
2. データの受け渡しは JSON など、値中心の形式にする
3. 状態はセッションやサーバー側ストレージに置く
4. どうしてもクライアント側に置くなら、HMAC 等で改ざん検知する
5. 署名検証のあとも、値の型・範囲・許可キーを検証する
```

## 📄 XML外部実体参照（XXE）とは

**XXE（XML External Entity）** とは、XML を読み込むときに使える **外部実体参照** という仕組みを悪用し、サーバー内のファイルを読んだり、サーバーから別の URL へアクセスさせたりする攻撃です。

XML には「実体（entity）」という、名前付きの置き換え文字を定義する機能があります。その定義の中で、**外部ファイルや URL** を参照できてしまうパーサ設定だと、攻撃が可能になります。

| 項目 | 内容 |
|------|------|
| **分類** | XML パーサの設定不備を突く攻撃 |
| **悪用される機能** | 外部実体参照（External Entity） |
| **典型的な被害** | サーバー内ファイルの閲覧、内部ネットワークへのアクセス |

### 日常生活での例え

- **正常**: 「注文書（XML）」に商品名が書いてあり、受付はその内容だけを読む
- **攻撃**: 注文書の隅に「倉庫の棚卸し表も添付として読み込め」と書かれ、受付が金庫の中身まで声に出して読んでしまう

### 何ができるか（被害）

| 攻撃の種類 | 説明 |
|------------|------|
| **外部実体参照によるファイルアクセス** | `/etc/passwd` や設定ファイルなど、サーバー内ファイルを読み出させる |
| **URL指定のHTTPアクセスによる攻撃** | サーバーから内部ネットワークや他サイトへ HTTP アクセスさせ、偵察や攻撃の踏み台にする |

```
【ファイルアクセスのイメージ】
攻撃者が送る XML の中に:
  「file:///etc/passwd の内容を、この項目に展開せよ」
と書いておく

アプリが XML をパースすると:
  本来の項目の値として、パスワード関連ファイルの中身が入ってしまう
```

```
【HTTPアクセスのイメージ】
攻撃者が送る XML の中に:
  「http://内部サーバー/管理画面 を読み込め」
と書いておく

アプリが XML をパースすると:
  サーバーが内部ネットワークへアクセスしてしまう
  （ファイアウォールの内側から叩ける）
```

外部から直接は届かない社内システムでも、**XXE で Web サーバーを踏み台にされると届いてしまう** 点が危険です。

### 攻撃の流れ

```
1. アプリが XML を受け取り、外部実体を解決する設定のパーサで読む
2. 攻撃者が、外部ファイルや URL を参照する実体定義を含んだ XML を送る
3. パーサが実体を解決し、ファイル内容や HTTP レスポンスを取り込む
4. その内容がアプリの処理結果やエラーメッセージ経由で攻撃者に見える
5. 情報漏洩や、内部ネットワークへの到達が起きる
```

## 🛡️ XML外部実体参照（XXE）の対策

対策の基本は次のとおりです。

| 対策 | 安全性 | 説明 |
|------|--------|------|
| **XMLの代わりにJSONを用いる** | 最も簡単で安全寄り | 外部実体という仕組み自体を使わない |
| **XMLが必要な場合は外部実体を無効化する** | 必須 | パーサ設定で DTD / 外部実体を拒否する |
| **不要なネットワークアクセスを制限する** | 防御深度 | サーバーからの外向き通信を最小化する |

### 1. XMLの代わりにJSONを用いる（最優先しやすい）

API や設定の受け渡しで XML である必要がなければ、**JSON に置き換える** のが分かりやすい対策です。

```
【なぜ JSON がよいか】
・外部実体参照という仕組みがない
・「ファイルを読め」「URL にアクセスせよ」といった指示を埋め込みにくい
・多くの Web API で標準的に使われている
```

もちろん JSON にも別の問題（巨大なネストによる DoS など）はあり得ますが、XXE 固有の問題は避けられます。

### 2. XML を使い続ける場合は、外部実体を無効化する

既存システムや外部仕様で XML が必須な場合は、**XML パーサの設定で外部実体・DTD を無効化** します。

```
【設定の考え方】
・外部実体参照を解決しない
・外部 DTD を読み込まない
・可能なら DTD 自体を禁止する
```

言語やライブラリごとに設定方法は異なりますが、方針は共通です。「XML を読める」ことと「外部ファイルまで取りに行く」ことは別であり、後者は通常の Web アプリでは不要です。

### 3. 返却内容にも注意する

XXE では、読み取ったファイル内容が **画面や API レスポンスにそのまま出る** と被害が確定します。パーサ設定の修正が本筋ですが、エラーメッセージに内部情報を出しすぎないことも補助になります。

### 対策の優先順位

```
1. 可能なら XML ではなく JSON を使う
2. XML が必要なら、外部実体・DTD を無効化する
3. サーバーからの不要な外向き通信を制限する
4. エラーやレスポンスに内部ファイルの内容を出さない
```

## 📋 まとめ

| 項目 | Evalインジェクション | 安全でないデシリアライゼーション | XXE |
|------|----------------------|----------------------------------|-----|
| **本質** | 文字列をコードとして実行させられる | 改ざんされたオブジェクト定義を復元させられる | XML の外部参照でファイルや URL にアクセスさせられる |
| **主な被害** | 情報漏洩、改ざん、不正実行、他サイト攻撃、採掘 | 同左 | ファイル閲覧、内部ネットへのアクセス |
| **原因** | eval の利用 / 入力チェック不足 | 外部入力の unserialize 等 | 外部実体を解決するパーサ設定 |
| **基本対策** | eval を使わない | JSON 化・セッション保存・改ざん検知 | JSON 化、または外部実体無効化 |

```
構造化データ読み込みの安全の基本:

1. 文字列をプログラムとして実行する機能（eval 等）を使わない
2. 使う場合でも、外部入力を引数に渡さない。渡すなら英数字に限定する
3. 外部から来るデータは、シリアライズ形式ではなく JSON などで受け取る
4. 状態はクッキーや Hidden ではなく、セッションなどサーバー側に置く
5. どうしてもクライアント側に置くなら HMAC 等で改ざんを検知する
6. XML が不要なら JSON にする。XML を使うなら外部実体を無効化する
```

本章に共通する考え方は、**「データを読む」処理が、いつの間にか「命令を実行する」「別のファイルを取りに行く」処理になっていないか** を疑うことです。便利な自動変換・自動実行ほど、外部入力との相性は悪くなります。必要最小限の形式（多くの場合は JSON と明示的な許可リスト）でデータを扱う習慣を付けましょう。
