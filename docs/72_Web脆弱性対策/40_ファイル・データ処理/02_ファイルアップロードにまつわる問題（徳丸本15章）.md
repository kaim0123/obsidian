# 安全なWebアプリケーションの作り方（第15章）

プロフィール画像・添付資料・帳票など、Webアプリは **ファイルのアップロードとダウンロード** をよく使います。第15章では、そのときに起きやすい脆弱性と対策を解説します。

---

## 📤 ファイルアップロードの問題の概要

ファイルアップロード機能には、主に次の問題があります。

| 問題 | 概要 |
|------|------|
| **アップロード機能に対する DoS 攻撃** | 巨大ファイルや大量アップロードでサーバー資源を枯渇させる |
| **アップロードファイルのサーバー側スクリプト実行** | 攻撃用スクリプトをアップロードし、サーバー上で実行させる |
| **仕掛けを含むファイルを利用者にダウンロードさせる攻撃** | 悪意あるファイルを他ユーザーに開かせ、XSS などを起こす |
| **閲覧権限のないファイルのダウンロード** | 他人のファイルや秘密ファイルを不正に取得する |

### 日常生活での例え

- **正常なアップロード**: 自分のプロフィール写真だけが保存され、自分だけが見られる
- **攻撃された場合**: 写真のふりをした「悪いプログラム」がサーバーに置かれ、サーバーごと乗っ取られる。あるいは、他の利用者のブラウザで勝手にスクリプトが動く

### なぜ危険か

アップロード機能は、アプリが **「サーバーにファイルを書き込む権限」** を持っているということです。その権限が悪用されると、次のような被害が出ます。

```
・サーバー上で攻撃用プログラムが動く
・Webサーバー内のファイルの閲覧・改ざん・削除
・他ユーザーへの XSS やマルウェア配布
・他人の非公開ファイルの漏洩
・ディスクや CPU を使い果たす DoS
```

第13章の「ファイルアクセス」は **既存ファイルの読み書き** が中心でした。本章は **外部からファイルを持ち込む** 点がポイントです。持ち込まれたファイルが「ただの画像」ではなく「実行可能なプログラム」や「ブラウザを騙す文書」になると、被害が大きくなります。

---

## 💥 アップロード機能に対する DoS 攻撃

**DoS（Denial of Service）** は、サービス妨害攻撃です。アップロード機能では、次のような方法でサーバーを重くしたり止めたりできます。

| 手口 | 説明 |
|------|------|
| **巨大ファイルのアップロード** | 数 GB のファイルを送り、ディスクやメモリを圧迫する |
| **大量の同時アップロード** | 多くのリクエストで帯域・CPU・接続数を使い果たす |
| **小さなファイルの大量保存** | ディスクの inode（ファイル数の上限）を使い果たす |

### 日常生活での例え

- **正常**: 写真を1枚アップロードする
- **攻撃**: 倉庫いっぱいに巨大な荷物を送りつけ、他の荷物が置けなくなる

### 対策の要点

| 対策 | 説明 |
|------|------|
| **ファイルサイズの上限** | アプリ・Webサーバー・PHP 等の設定で上限を設ける |
| **アップロード回数・頻度の制限** | 同一ユーザー・同一 IP の連続投稿を制限する |
| **保存先ディスクの監視** | 容量逼迫を検知できるようにする |
| **ウイルススキャン等の負荷制御** | 重い処理はキューに回し、Web 応答を止めない |

サイズ制限は「アプリだけ」では不十分なことがあります。Webサーバー（Nginx / Apache）や言語ランタイム側の上限もあわせて設定します。

---

## ☠️ アップロードファイルによるサーバー側スクリプト実行

**アップロードファイルによるサーバー側スクリプト実行** とは、攻撃者が **サーバーで動くプログラム**（PHP・JSP・ASP など）をアップロードし、それを Web 経由で実行させてしまう脆弱性です。

画像や PDF を受け取るつもりが、実際には `shell.php` のような攻撃用スクリプトを置かれてしまうイメージです。

### 日常生活での例え

- **正常**: 受付に「写真」を預ける
- **攻撃**: 「写真」と書いてある封筒の中身が、実は「倉庫の鍵を開ける道具」で、受付が倉庫の中に置いてしまう

### 何ができるか（被害）

スクリプトがサーバー上で動くと、Webアプリが持つ権限の範囲で、ほぼ何でもできます。

| 被害 | 説明 |
|------|------|
| **Webサーバー内のファイルの閲覧・改ざん・削除** | 設定ファイル、ソースコード、データベース接続情報などを読まれる・書き換えられる |
| **外部へのメールの送信** | 迷惑メールやフィッシングメールの踏み台にされる |
| **別のサーバーへの攻撃** | 自サーバーを踏み台に、他サイトへ攻撃する |
| **サーバー上での暗号通貨の採掘** | CPU を勝手に使い、電気代や性能を奪う |

一度スクリプト実行が成功すると、**サーバーの乗っ取り** に近い状態になります。第14章の OSコマンド・インジェクションと同様、影響範囲が非常に広いです。

### 攻撃のイメージ

プロフィール画像のアップロード機能があり、保存先が公開ディレクトリだとします。

```
【正常な利用】
photo.jpg をアップロード
→ https://example.com/uploads/photo.jpg で画像が表示される

【攻撃者の操作】
shell.php をアップロード（中身は攻撃用 PHP）
→ https://example.com/uploads/shell.php にブラウザでアクセス
→ サーバーが PHP として実行してしまう
→ 攻撃者がサーバー上で任意の処理を実行できる
```

攻撃用スクリプトの例（概念）:

```php
<?php
// 攻撃者がアップロードした悪用スクリプトのイメージ
// 実際にはもっと巧妙に隠蔽されることが多い
system($_GET['cmd']);  // URL の cmd パラメータを OS コマンドとして実行
```

攻撃者は次のようにアクセスします。

```
https://example.com/uploads/shell.php?cmd=ls
→ サーバー上で ls が実行され、ファイル一覧が返る
```

### 脆弱性が生まれる原因

この問題が起きる典型的な条件は、次の **2つが同時に成り立つ** ことです。

| 原因 | 説明 |
|------|------|
| **① アップロードしたファイルが公開ディレクトリに保存される** | URL で直接アクセスでき、Webサーバーがそのファイルを処理する |
| **② アップロード後のファイル名として、サーバースクリプトを示す拡張子が指定できる** | `.php` `.jsp` `.aspx` など、実行対象の拡張子で保存できてしまう |

```
【危険な組み合わせ】

公開ディレクトリ（例: /var/www/html/uploads/）
        ＋
実行可能な拡張子（例: .php）
        ↓
URL アクセスだけでスクリプトが動く
```

どちらか一方でも防げれば、この攻撃は成立しにくくなります。

```
✅ 公開ディレクトリに置かない
   → URL で直接アクセスできない

✅ .php などの危険な拡張子を拒否する
   → 置かれてもスクリプトとして実行されない（※サーバー設定にも依存）
```

### 拡張子の偽装にも注意

単純なチェックだけでは、次のような抜け道があります。

| 手口 | 例 |
|------|----|
| **二重拡張子** | `shell.php.jpg`（サーバー設定によっては `.php` として実行される） |
| **大文字小文字** | `shell.PHP` / `shell.pHp` |
| **末尾のドットや空白** | `shell.php.`（環境によって解釈が変わる） |
| **ヌルバイト（古い環境）** | `shell.php%00.jpg`（昔の言語処理で `.php` と解釈された例） |
| **Content-Type だけ信じる** | ブラウザが送る `image/jpeg` は攻撃者が自由に書き換えられる |

「ブラウザが申告した種類」や「ファイル名の見た目」だけを信じないことが重要です。

## 📥 ファイルダウンロードによるクロスサイト・スクリプト（XSS）

アップロードされたファイルを **他の利用者がダウンロード・表示する** 機能でも、XSS が起きることがあります。

攻撃者は、HTML や JavaScript を含むファイルをアップロードし、被害者がそれをブラウザで開くと、**被害者のブラウザ上でスクリプトが実行** されます。

### 日常生活での例え

- **正常**: 共有フォルダから「資料.pdf」を開く
- **攻撃**: 「資料」のふりをしたファイルを開いた瞬間、画面の裏で勝手に操作される（Cookie の盗難、偽画面の表示など）

### なぜ起きるか

ブラウザは、レスポンスの **Content-Type（中身の種類）** を見て、「画像として表示するか」「HTML として実行するか」を決めます。

ここが間違っていると、次のようなことが起きます。

```
【危険な例】
サーバーが text/html で返す
または Content-Type が曖昧で、ブラウザが HTML だと推測する
        ↓
中身に <script> があると、スクリプトとして実行される
```

特に、アップロードファイルを **同一オリジン（同じサイト）上の URL** で配信している場合、実行されたスクリプトはそのサイトの Cookie や DOM にアクセスできます。通常の XSS と同じ被害になります。

### 対策（ダウンロード時）

| 対策 | 説明 |
|------|------|
| **ファイルの Content-Type を正しく設定する** | 画像なら `image/jpeg`、PDF なら `application/pdf` など、中身に合った型を返す |
| **`X-Content-Type-Options: nosniff` を指定する** | ブラウザに「Content-Type を推測せず、宣言どおり扱え」と指示する |
| **ダウンロード想定のファイルには `Content-Disposition: attachment` を指定する** | ブラウザ内で開かず、ダウンロードダイアログを出す（実行・表示を抑える） |

レスポンスヘッダのイメージ:

```
HTTP/1.1 200 OK
Content-Type: image/jpeg
X-Content-Type-Options: nosniff
Content-Disposition: attachment; filename="photo.jpg"
```

| ヘッダ | 役割 |
|--------|------|
| **Content-Type** | 「これは JPEG 画像です」と正しく宣言する |
| **X-Content-Type-Options: nosniff** | 中身を見て HTML だと勝手に判断しない |
| **Content-Disposition: attachment** | 画面に表示せず、ファイルとして保存させる |

※ メモ: ヘッダ名は `Content-Disposition` です（`Cotent-Disposition` は誤記）。

## 📄 PDF ダウンロード機能による XSS

PDF をダウンロード・表示する機能でも、XSS に近い問題が起きます。代表的なのが **PDF に偽装した HTML ファイルによる XSS** です。

### PDF に偽装した HTML ファイルによる XSS

攻撃の流れは次のとおりです。

```
1. 攻撃者が、中身は HTML（+ JavaScript）なのに、
   ファイル名だけ report.pdf にしたファイルをアップロードする

2. 被害者が「PDF を開く」リンクをクリックする

3. サーバーが Content-Type を誤って text/html などで返す
   （またはブラウザが中身を HTML だと推測する）

4. ブラウザが HTML として解釈し、<script> が実行される
```

見た目は「PDF のダウンロード」でも、実際には **HTML ページとして動いてしまう** のがポイントです。

### Content-Type の間違いが根本原因

この攻撃が成立する根本原因は、**サーバーが返す Content-Type が正しくない（または曖昧）** ことです。

| 状況 | 結果 |
|------|------|
| **正しい** `Content-Type: application/pdf` + `nosniff` | ブラウザは PDF として扱う（HTML としては実行しない） |
| **誤り** `Content-Type: text/html` | HTML として実行される |
| **曖昧**（未設定・`application/octet-stream` のみ等） | ブラウザの推測（コンテンツスニッフィング）に依存し、危険 |

ファイル名が `.pdf` でも、**中身の扱いを決めるのは主に Content-Type** です。拡張子だけ見て安心してはいけません。

### Content-Type と IE の挙動の関係

かつての Internet Explorer（IE）は、Content-Type より **中身の先頭バイトを見て種類を推測する**（コンテンツスニッフィング）傾向が強いことで知られていました。

```
【IE で起きやすかったこと】

サーバー: Content-Type: application/pdf と返したつもり
実際の中身: <html><script>...</script></html>
        ↓
IE が「これは HTML だ」と推測して実行してしまう
```

そのため、次の対策が特に重要でした（現代のブラウザでも防御として有効です）。

| 対策 | 効果 |
|------|------|
| **正しい Content-Type** | 種類の宣言を明確にする |
| **`X-Content-Type-Options: nosniff`** | 推測をやめさせ、宣言どおりに扱わせる |
| **`Content-Disposition: attachment`** | ブラウザ内表示を避け、ダウンロードさせる |

現代ブラウザでは挙動が改善されていますが、**古いブラウザや組み込みブラウザ**、設定の違いもあるため、ヘッダ対策は引き続き必須です。

## 🛡️ 対策（アップロードとダウンロード）

対策は **アップロード時** と **ダウンロード時** の両方で行います。どちらか一方だけでは不十分です。

### アップロード時の対策

#### 1. 拡張子が許可されたものかをチェックする

許可リスト（ホワイトリスト）方式で、**必要な拡張子だけ** を通します。拒否リスト（「`.php` 以外は OK」）は抜け道が多く、非推奨です。

```
❌ 悪い例（拒否リスト）
  .php だけ禁止
  → .php5 .phtml .cgi .aspx などで回避されることがある

✅ 良い例（許可リスト）
  画像なら .jpg .jpeg .png .gif .webp のみ許可
  それ以外はすべて拒否
```

実装のポイント:

| ポイント | 説明 |
|----------|------|
| **許可リストを使う** | 業務上必要な拡張子だけ列挙する |
| **大文字小文字を統一して判定** | `.PHP` も `.php` と同じ扱いにする |
| **拡張子はサーバー側で付け直す** | ユーザー指定のファイル名をそのまま使わない |
| **保存名はアプリが決める** | UUID など推測しにくい名前にする |
| **公開ディレクトリに置かない** | ドキュメントルートの外に保存し、アプリ経由で配信する |

```php
// ✅ 許可リストで拡張子をチェックし、保存名はサーバーが決める例（概念）
$allowed = ['jpg', 'jpeg', 'png', 'gif', 'webp'];
$original = $_FILES['photo']['name'];
$ext = strtolower(pathinfo($original, PATHINFO_EXTENSION));

if (!in_array($ext, $allowed, true)) {
    exit('許可されていないファイル形式です');
}

// ユーザーのファイル名は使わず、安全な名前で保存
$newName = bin2hex(random_bytes(16)) . '.' . $ext;
$savePath = '/var/www/data/uploads/' . $newName;  // 非公開ディレクトリ
// move_uploaded_file(..., $savePath);
```

#### 2. あわせてやっておくとよいこと

| 対策 | 説明 |
|------|------|
| **ファイルサイズ上限** | DoS 対策にもなる |
| **画像なら画像として再エンコード** | 余計なデータを取り除き、スクリプト混入を減らす |
| **実行権限を付けない** | 保存先ディレクトリでスクリプト実行を無効化する |
| **ウイルススキャン** | マルウェア配布対策（万能ではないが有効） |

Webサーバー側で、アップロードディレクトリでのスクリプト実行を無効化するのも有効です。

```apache
# アップロードディレクトリで PHP を動かさない例（Apache）
<Directory "/var/www/html/uploads">
    php_admin_flag engine off
</Directory>
```

可能なら、そもそも公開配下に置かない方が安全です。

### ファイルダウンロード時の対策

| 対策 | 説明 |
|------|------|
| **Content-Type を正しく設定する** | 拡張子や用途に応じた正しい MIME タイプを返す |
| **`X-Content-Type-Options: nosniff` を指定する** | コンテンツスニッフィングを防ぐ |
| **必要に応じて `Content-Disposition` を設定する** | 表示が不要なら `attachment` でダウンロード強制 |

```php
// ✅ ダウンロード配信のヘッダ例（概念）
$file = '/var/www/data/uploads/' . $safeName;
$mime = 'image/jpeg';  // 実際はファイル種別に応じて設定

header('Content-Type: ' . $mime);
header('X-Content-Type-Options: nosniff');
header('Content-Disposition: attachment; filename="download.jpg"');
readfile($file);
```

```
【防御の層】

アップロード時: 危険な拡張子を入れない / 非公開に保存する
        ＋
ダウンロード時: 正しい Content-Type / nosniff / attachment
        ↓
スクリプト実行も XSS も起きにくくなる
```

## 📑 PDF の FormCalc によるコンテンツハイジャック

PDF には、フォーム計算などに使う **FormCalc** という仕組みがあります。これを悪用すると、**コンテンツハイジャック**（表示内容の乗っ取り）が起きる場合があります。

### 何が起きるか

悪意のある PDF を、ページ内の `object` や `embed` で埋め込み表示すると、PDF 内のスクリプト的な機能が動き、**親ページの表示や操作に影響する** ことがあります。

```
【攻撃のイメージ】

1. 攻撃者が悪意ある PDF をアップロードする
2. サイトが object / embed でその PDF をページ内表示する
3. PDF 内の FormCalc 等が動き、画面上の情報を書き換えたり奪ったりする
```

通常の XSS とは経路が違いますが、「ユーザーが信頼しているページ上で、意図しない表示・操作が起きる」点では近い被害です。

### 対策

| 対策 | 説明 |
|------|------|
| **PDF はブラウザ内で開かずダウンロードを強制する** | `Content-Disposition: attachment` で保存させる |
| **PDF を `object` / `embed` では開けない仕組みにする** | ページ内埋め込み表示をやめる、または禁止する |

```
❌ 危険な表示方法
  <embed src="/files/report.pdf">
  <object data="/files/report.pdf"></object>
  → ページ内で PDF が動き、FormCalc 等が実行されうる

✅ 安全寄りの方法
  Content-Disposition: attachment でダウンロードさせる
  または、信頼できる専用ビューア経由で、スクリプト無効化して表示する
```

レスポンス例:

```
Content-Type: application/pdf
X-Content-Type-Options: nosniff
Content-Disposition: attachment; filename="report.pdf"
```

「便利だからページ内で PDF を見せたい」という要件があっても、**ユーザーがアップロードした PDF をそのまま埋め込む** のは避けます。どうしても表示が必要なら、サーバー側で無害化・変換する、スクリプトを無効にしたビューアを使う、別オリジンで隔離する、などの追加対策が必要です。

## 📋 まとめ

| 問題 | 本質 | 対策の要点 |
|------|------|------------|
| **アップロードへの DoS** | 資源を使い果たされる | サイズ・回数制限、監視 |
| **サーバー側スクリプト実行** | 実行可能ファイルが公開場所に置かれる | 許可リストで拡張子制限、非公開保存、実行無効化 |
| **ダウンロードによる XSS** | 誤った Content-Type で HTML として実行される | 正しい Content-Type、`nosniff`、`attachment` |
| **PDF 偽装 HTML** | PDF のつもりが HTML として動く | 同上。拡張子だけで判断しない |
| **PDF FormCalc** | 埋め込み PDF がページを乗っ取る | ダウンロード強制、`object`/`embed` で開かない |

```
ファイルアップロード安全の基本:

1. 許可リストで拡張子を厳しく制限し、保存名はサーバーが決める
2. アップロード先は公開ディレクトリにしない（アプリ経由で配信する）
3. ダウンロード時は正しい Content-Type と nosniff を付ける
4. 表示が不要なファイルは Content-Disposition: attachment でダウンロードさせる
5. ユーザー投稿の PDF を object / embed で埋め込まない
```
