# セキュリティヘッダ全般

サーバーがレスポンスに付ける **「ブラウザへの指示書」** です。アプリの脆弱性そのものは直せませんが、XSS・クリックジャッキング・通信の盗聴などが **起きても被害を小さくする** 多層防御の層になります（[[02_深層防御]]）。CSP は大きいので [[09_PKCEとCSPとは]] に分けています。CORS は [[02_CORS（徳丸本3章）]]、Cookie の属性は [[02_クッキー出力にまつわる脆弱性（徳丸本11章）]]。

---

## 🗺 全体像

| ヘッダ | 防ぐもの | 推奨値 |
|------|------|------|
| **Strict-Transport-Security**（HSTS） | HTTP への格下げ・盗聴 | `max-age=63072000; includeSubDomains` |
| **Content-Security-Policy** | XSS・不正なリソース読み込み・フレーム埋め込み | サイトに合わせて作る（[[09_PKCEとCSPとは]]） |
| **X-Frame-Options** | クリックジャッキング | `DENY` または `SAMEORIGIN` |
| **X-Content-Type-Options** | MIME スニッフィングによる XSS | `nosniff` |
| **Referrer-Policy** | URL に含まれる情報の漏えい | `strict-origin-when-cross-origin` |
| **Permissions-Policy** | カメラ・位置情報などの悪用 | `camera=(), microphone=(), geolocation=()` |
| **Cross-Origin-Opener-Policy**（COOP） | 別ウィンドウからの干渉・XS-Leaks | `same-origin` |
| **Cross-Origin-Resource-Policy**（CORP） | 他サイトからのリソース読み込み | `same-origin` / `same-site` |
| **Cache-Control** | 共有キャッシュからの個人情報漏えい | 個人向けページは `no-store` |

**考え方:** どれも「ブラウザに **やってはいけないこと** を教える」ものです。ヘッダが無いと、ブラウザは互換性優先のゆるい動作をします。

---

## 🔒 Strict-Transport-Security（HSTS）

### 何が問題か

利用者が `example.com` と打つと、最初の 1 回は **HTTP** で接続されます。この 1 回を公衆 Wi-Fi などで横取りされると、HTTPS へのリダイレクトを消され、平文のまま通信させられます（SSL ストリップ攻撃）。

### HSTS の働き

```
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
```

| 指定 | 意味 |
|------|------|
| `max-age` | この秒数のあいだ、ブラウザはこのドメインに **HTTPS でしか接続しない**（63072000 秒 = 2 年） |
| `includeSubDomains` | サブドメインにも適用 |
| `preload` | ブラウザに最初から組み込まれた「HTTPS 専用リスト」への登録を希望する |

- 一度受け取ると、利用者が `http://` と打っても **ブラウザ内部で https に書き換える**。証明書エラーも「無視して続行」できなくなります。
- HTTPS のレスポンスで返したときだけ有効です（HTTP で返しても無視される）。

### 注意

- `includeSubDomains` を付ける前に、**HTTP でしか動かないサブドメインがないか** 確認する。あるとアクセスできなくなります。
- `preload` は外すのに数か月かかります。最初は `max-age=300` などの短い値で試し、問題がないことを確かめてから伸ばします。

## 🖼 X-Frame-Options と frame-ancestors（クリックジャッキング対策）

### クリックジャッキングとは

攻撃者のページに、対象サイトを **透明な iframe** で重ねて表示し、利用者に「ゲームのボタン」を押させているつもりで、実は「退会する」「送金する」ボタンを押させる攻撃です。

```
┌──────────────────────────┐
│ 攻撃者のページ            │
│   [ 景品を受け取る ]  ←─ 見えているボタン
│   ┌ 透明な iframe ──────┐ │
│   │  [ 退会する ]  ←─ 実際に押されるボタン
│   └──────────────────────┘ │
└──────────────────────────┘
```

CSRF と違い、**利用者本人が本物の画面で操作する** ので、CSRF トークンでは防げません（[[01_CSRF（徳丸本8章）]]）。

### 対策

```
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none'
```

| 値 | X-Frame-Options | CSP frame-ancestors |
|------|------|------|
| どこにも埋め込ませない | `DENY` | `'none'` |
| 同じオリジンだけ許可 | `SAMEORIGIN` | `'self'` |
| 特定サイトを許可 | （`ALLOW-FROM` は廃止済み） | `https://partner.example` |

- 新しい仕様は **CSP の `frame-ancestors`** です。両方あるとブラウザは `frame-ancestors` を優先します。
- 古いブラウザ向けに **両方付ける** のが一般的です。

## 📄 X-Content-Type-Options

```
X-Content-Type-Options: nosniff
```

ブラウザには、`Content-Type` を信用せず **中身を見て種類を推測する**（MIME スニッフィング）動作があります。これがあると、`text/plain` で返したアップロードファイルの中身に `<script>` があると、HTML として実行されることがあります。

- `nosniff` を付けると、ブラウザは `Content-Type` のとおりに扱います。
- `<script src>` で読む先が JavaScript の MIME タイプでなければ、実行されません。
- アップロードファイルの配信で特に重要です（[[02_ファイルアップロードにまつわる問題（徳丸本15章）]]）。JSON API での効果は [[02_WebAPI実装における脆弱性（徳丸本19章）]]。

**前提:** `Content-Type` を正しく付けること。間違った型を返していると、`nosniff` で逆に動かなくなります。

## 🔗 Referrer-Policy

リンクを踏んだとき、ブラウザは遷移元の URL を `Referer` ヘッダで送ります。URL に **セッション ID・パスワードリセット用トークン・検索語** が入っていると、外部サイトに漏れます。

```
Referrer-Policy: strict-origin-when-cross-origin
```

| 値 | 同じオリジンへ | 別オリジンへ |
|------|------|------|
| `no-referrer` | 送らない | 送らない |
| `same-origin` | フル URL | 送らない |
| `strict-origin-when-cross-origin` | フル URL | オリジンだけ（HTTPS→HTTP では送らない） |
| `unsafe-url` | フル URL | フル URL（使わない） |

- 現在のブラウザの既定値は `strict-origin-when-cross-origin` ですが、明示しておくと古いブラウザでも同じ動作になります。
- 根本対策は **URL に秘密を入れない** ことです。ヘッダは保険です。

## 🎤 Permissions-Policy

カメラ・マイク・位置情報・決済などのブラウザ機能を、**そのページや埋め込んだ iframe が使えるか** を決めます。

```
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()
```

- `()` は「誰にも許可しない」、`(self)` は「自分のオリジンだけ」。
- 広告や外部ウィジェットを埋め込むサイトで、**XSS や外部スクリプトに機能を悪用させない** ために使います。
- 旧名は `Feature-Policy` です。

---

## 🪟 COOP / COEP / CORP（クロスオリジン分離）

Spectre のような CPU の脆弱性や、別ウィンドウからの探り（XS-Leaks）への対策として追加されたヘッダです。

| ヘッダ | 役割 | よく使う値 |
|------|------|------|
| **COOP**（Cross-Origin-Opener-Policy） | `window.open` で開いた別オリジンのウィンドウと、`window.opener` で互いに触れないようにする | `same-origin`（OAuth のポップアップを使うなら `same-origin-allow-popups`） |
| **CORP**（Cross-Origin-Resource-Policy） | 自分のリソース（画像・JS など）を、他サイトが `<img>` や `<script>` で読み込めるか | `same-origin` / `same-site` / `cross-origin` |
| **COEP**（Cross-Origin-Embedder-Policy） | 自分のページが読み込むリソースに、CORP か CORS での許可を必須にする | `require-corp` |

- COOP + COEP がそろうと「クロスオリジン分離」状態になり、`SharedArrayBuffer` などの強力な機能が使えます。
- COEP は外部の画像や広告が読めなくなることがあるので、**必要なサイトだけ** 入れます。COOP と CORP は多くのサイトで入れやすいです。

---

## 🗄 キャッシュ・ログアウト関連

| ヘッダ | 使う場面 |
|------|------|
| `Cache-Control: no-store` | マイページ・個人情報・API の個人向け応答。CDN やプロキシに残さない（[[01_共有資産やキャッシュに関する問題（徳丸本18章）]]） |
| `Clear-Site-Data: "cache", "cookies", "storage"` | ログアウト時に、ブラウザに残ったキャッシュ・Cookie・Web ストレージを消させる |

---

## 🚫 付けない・消すべきヘッダ

| ヘッダ | 理由 |
|------|------|
| `X-XSS-Protection` | 古いブラウザの XSS フィルタ用。フィルタ自体が情報漏えいの原因になったため廃止。付けるなら `0`（無効化）。XSS 対策は CSP で行う |
| `Public-Key-Pins`（HPKP） | 設定ミスでサイトに永久に入れなくなる危険があり廃止 |
| `Expect-CT` | 証明書の透明性が必須になったため不要 |
| `X-Powered-By`・`Server` のバージョン | `Express`・`PHP/8.1.2` などを教えると、攻撃者が既知の脆弱性を探しやすくなる（[[A05_セキュリティの設定ミス]]） |

## 💻 設定例

### Express（helmet）

```javascript
import express from 'express';
import helmet from 'helmet';

const app = express();

// helmet は主要なセキュリティヘッダをまとめて付け、X-Powered-By を消す
app.use(
  helmet({
    contentSecurityPolicy: {
      directives: {
        defaultSrc: ["'self'"],
        frameAncestors: ["'none'"],
      },
    },
    strictTransportSecurity: { maxAge: 63072000, includeSubDomains: true },
    referrerPolicy: { policy: 'strict-origin-when-cross-origin' },
  })
);
```

### Next.js（next.config.js）

```javascript
const securityHeaders = [
  { key: 'Strict-Transport-Security', value: 'max-age=63072000; includeSubDomains' },
  { key: 'X-Frame-Options', value: 'DENY' },
  { key: 'X-Content-Type-Options', value: 'nosniff' },
  { key: 'Referrer-Policy', value: 'strict-origin-when-cross-origin' },
  { key: 'Permissions-Policy', value: 'camera=(), microphone=(), geolocation=()' },
];

module.exports = {
  poweredByHeader: false, // X-Powered-By: Next.js を消す
  async headers() {
    return [{ source: '/(.*)', headers: securityHeaders }];
  },
};
```

### nginx

```nginx
server_tokens off;  # Server ヘッダからバージョンを消す

add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
add_header X-Frame-Options "DENY" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
```

- `always` を付けないと、エラー応答（404・500 など）にヘッダが付きません。
- nginx の `add_header` は、`location` ブロックの中に 1 つでも書くと **外側の設定を引き継がなくなる** ので注意。

## ⚠️ よくある落とし穴

| 落とし穴 | 内容 |
|------|------|
| **一部のページにしか付いていない** | エラーページ・静的ファイル・API にも付ける。リバースプロキシや CDN でまとめて付けると漏れにくい |
| **二重に付いている** | アプリとプロキシの両方で付け、値が食い違う。どちらで付けるか決める |
| **HSTS をいきなり長くする** | HTTP が必要なサブドメインがあると戻せない。短い値から始める |
| **ヘッダで脆弱性が直ったと思う** | ヘッダは被害を減らす保険。XSS ならエスケープ、CSRF ならトークンが本質的対策 |

---

## 🔍 確認方法

- ブラウザの開発者ツール → Network → レスポンスヘッダを見る
- `curl -I https://example.com` でヘッダだけ表示する
- [Mozilla HTTP Observatory](https://developer.mozilla.org/en-US/observatory) や [securityheaders.com](https://securityheaders.com/) で採点する

---

## 📋 対策の優先順位

```
1. HTTPS 化 + HSTS（全サイト必須）
2. X-Content-Type-Options: nosniff と正しい Content-Type（全サイト必須）
3. クリックジャッキング対策（X-Frame-Options + frame-ancestors）
4. CSP（まずは Report-Only で始める）
5. Referrer-Policy・Permissions-Policy・COOP/CORP
6. X-Powered-By などバージョン情報の削除
```
