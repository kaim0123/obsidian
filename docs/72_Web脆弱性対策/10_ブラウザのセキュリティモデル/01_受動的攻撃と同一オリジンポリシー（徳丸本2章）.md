# 安全なWebアプリケーションの作り方（第2章）

第1章では HTTP とセッション管理の基礎を学びました。第2章では、ブラウザが備える **セキュリティの仕組み** と、**同一オリジンポリシー** について解説します。

## ⚔️ 能動的攻撃と受動的攻撃

Webのセキュリティでは、攻撃の種類を **能動的（アクティブ）** と **受動的（パッシブ）** に分けて考えます。

### 能動的攻撃（Active Attack）

攻撃者が **通信やシステムに直接手を加える** 攻撃です。

| 例 | 説明 |
|----|------|
| **SQLインジェクション** | 悪意あるSQLを送り込んでDBを操作 |
| **XSS** | 悪意あるスクリプトをページに埋め込む |
| **CSRF** | ユーザーに意図しないリクエストを送らせる |
| **中間者攻撃（MITM）** | 通信を改ざん・なりすます |

```
ユーザー ──リクエスト──→ 攻撃者（改ざん） ──→ サーバー
         ←──レスポンス── 攻撃者（改ざん） ←──
```

**特徴:** 攻撃者が能動的に介入する。改ざんやなりすましが起きる。

### 受動的攻撃（Passive Attack）

攻撃者が **通信を傍受・監視するだけ** で、内容を改ざんしない攻撃です。

| 例 | 説明 |
|----|------|
| **盗聴（スニッフィング）** | ネットワーク上の通信を盗み見る |
| **トラフィック分析** | 通信の量・パターンから情報を推測 |
| **公開Wi-Fiでの傍受** | 暗号化されていない通信を読む |

```
ユーザー ──リクエスト──→ サーバー
         ↑
      攻撃者（盗み見るだけ、改ざんしない）
```

**特徴:** 攻撃者は「見るだけ」。通信内容が漏洩する。

### 対策の違い

| 攻撃の種類 | 主な対策 |
|-----------|---------|
| **能動的攻撃** | 入力値検証、CSRFトークン、WAF、認可チェック |
| **受動的攻撃** | **HTTPS（TLS暗号化）**、機密情報をURLに載せない |

### 本章との関係

- **同一オリジンポリシー** → 能動的攻撃（他サイトからの不正アクセス）を防ぐ
- **HTTPS** → 受動的攻撃（盗聴）を防ぐ
- **CORS** → 同一オリジンポリシーの制限を、安全な範囲で緩和する（→ [[02_CORS（徳丸本3章）|第3章]]）

## 🏖️ サンドボックス

**サンドボックス（Sandbox）** とは、プログラムを **隔離された安全な環境** で実行する仕組みです。砂場（sandbox）の中で遊ぶと外に影響しないイメージです。

### 日常生活での例え

- **サンドボックス**: 子ども用の砂場（中で遊んでも外の道路には影響しない）
- **ブラウザのサンドボックス**: WebページのJavaScript（中で動いても、PCのファイルには触れない）

### ブラウザのサンドボックスが制限すること

| 制限 | 説明 |
|------|------|
| ローカルファイルへのアクセス | ユーザーのPC上のファイルを読めない |
| 他サイトのデータ | 同一オリジンポリシーにより制限 |
| システムコマンドの実行 | OSの機能を直接操作できない |
| 任意のネットワーク接続 | 一部の通信はブラウザが制御 |

### iframe の sandbox 属性

`<iframe>` に `sandbox` 属性を付けると、埋め込んだページの権限をさらに制限できます。

```html
<!-- スクリプト実行もフォーム送信も禁止 -->
<iframe src="https://untrusted.example.com" sandbox></iframe>

<!-- スクリプトは許可、フォーム送信は禁止 -->
<iframe src="https://example.com/widget" sandbox="allow-scripts"></iframe>
```

| sandbox の値 | 許可する操作 |
|-------------|------------|
| （属性のみ） | ほぼ全て禁止 |
| `allow-scripts` | JavaScriptの実行 |
| `allow-forms` | フォーム送信 |
| `allow-same-origin` | 同一オリジンとして扱う |
| `allow-popups` | ポップアップの表示 |

**注意:** `allow-scripts` と `allow-same-origin` を **同時に付けると** サンドボックスを突破される可能性があるため、信頼できないコンテンツには慎重に使います。

## 🔒 同一オリジンポリシー

**同一オリジンポリシー（Same-Origin Policy, SOP）** は、ブラウザの最も基本的なセキュリティ機能のひとつです。

### オリジンとは

**オリジン** は、Webサイトの「出身地」を表す識別子です。次の3つの組み合わせで決まります。

```
オリジン = プロトコル + ドメイン + ポート番号
```

```
https://example.com:443/page1
  │       │          │
  │       │          └─ ポート（HTTPSは443、省略可）
  │       └─ ドメイン
  └─ プロトコル（スキーム）
```

### 同じオリジン vs 異なるオリジン

| URL A | URL B | 同じ？ | 理由 |
|-------|-------|--------|------|
| `https://example.com/a` | `https://example.com/b` | ✅ 同じ | パスはオリジンに含まれない |
| `https://example.com` | `http://example.com` | ❌ 違う | プロトコルが違う |
| `https://example.com` | `https://api.example.com` | ❌ 違う | ドメインが違う |
| `https://example.com` | `https://example.com:8080` | ❌ 違う | ポートが違う |

### 同一オリジンポリシーのルール

> **あるオリジンのページから、別オリジンのリソースに JavaScript で自由にアクセスすることを禁止する**

```
https://myapp.com のページ
  → https://myapp.com/api/users  ✅ OK（同一オリジン）
  → https://api.example.com/users ❌ NG（異なるオリジン）
```

### なぜ必要か

同一オリジンポリシーがなければ、悪意あるサイトが次のようなことをできます。

```
1. ユーザーが evil.com を開く（銀行サイトにはログイン済み）
2. evil.com の JavaScript が bank.com にリクエストを送る
3. ブラウザが bank.com の Cookie を自動送信
4. 口座情報などが evil.com に漏洩
```

同一オリジンポリシーにより、**evil.com の JavaScript から bank.com のレスポンスを読むこと** がブロックされます。

### 同一オリジンポリシーが守るもの

| 操作 | クロスオリジン |
|------|--------------|
| `<img src="...">` で画像を **表示** | ✅ 可能 |
| `<script src="...">` でJSを **実行** | ✅ 可能（ただし中身は読めない） |
| `<form>` で **送信** | ✅ 可能（ただしレスポンスは読めない） |
| `fetch()` / `XHR` で **レスポンスを読む** | ❌ 原則ブロック |
| 別サイトの DOM に **アクセス** | ❌ 原則ブロック |

「送ること」と「レスポンスを読むこと」は別、という点が重要です。

## 🖼️ iframe

**iframe（Inline Frame）** は、Webページの中に **別のWebページを埋め込む** HTML要素です。

```html
<iframe src="https://maps.example.com/embed" width="600" height="400"></iframe>
```

### 用途

- Google Maps の地図埋め込み
- YouTube 動画の埋め込み
- 決済フォーム（Stripe 等）の埋め込み
- 広告の表示

### 同一オリジンポリシーとの関係

iframe に読み込まれたページは **独立したオリジン** として扱われます。

```
親ページ: https://myapp.com
iframe内: https://widget.example.com

→ 親ページの JavaScript から iframe 内の DOM にはアクセスできない
```

```javascript
// ❌ クロスオリジンの iframe にはアクセス不可
const iframe = document.querySelector('iframe');
iframe.contentDocument; // エラー（SecurityError）
```

### 同一オリジン iframe ならアクセス可能

```javascript
// ✅ 同一オリジンの iframe なら OK
const iframe = document.querySelector('iframe');
iframe.contentDocument.body.innerHTML = '更新';
```

### セキュリティ上の注意

| リスク | 対策 |
|--------|------|
| クリックジャッキング | `X-Frame-Options: DENY` または `Content-Security-Policy: frame-ancestors` |
| 悪意あるコンテンツの埋め込み | `sandbox` 属性で権限を制限 |
| フィッシング | 信頼できるソースのみ iframe で読み込む |

## 🌍 クロスドメインアクセス

**クロスドメインアクセス** とは、**異なるドメイン（オリジン）間** でリソースやデータにアクセスすることです。

### 現代のWebで必要になる理由

フロントエンドとAPIが分離された構成が一般的になりました。

```
フロントエンド: https://myapp.com
バックエンドAPI: https://api.myapp.com   ← ドメインが違う = クロスドメイン
```

```
https://myapp.com の JavaScript
  → fetch('https://api.myapp.com/users')
  → 同一オリジンポリシーにより、レスポンスの読み取りがブロックされる
```

### クロスドメインアクセスの方法

| 方法 | 説明 |
|------|------|
| **CORS** | サーバーが許可を明示（最も一般的） → [[02_CORS（徳丸本3章）\|第3章]] |
| **JSONP** | 旧来の手法（`<script>` タグを利用、非推奨） |
| **プロキシ** | 同一オリジンのサーバー経由で中継 |
| **postMessage** | iframe 間の安全なメッセージング |

## 📝 まとめ

| トピック | 要点 |
|---------|------|
| 能動的攻撃 | 改ざん・なりすまし。入力検証・CSRF対策等 |
| 受動的攻撃 | 盗聴・監視。**HTTPS** が主な対策 |
| サンドボックス | プログラムを隔離実行。iframe の `sandbox` 属性 |
| 同一オリジンポリシー | 異なるオリジン間の JS アクセスを制限するブラウザの基本防御 |
| iframe | ページ埋め込み。クロスオリジンでは DOM アクセス不可 |
| クロスドメインアクセス | 異なるオリジン間の通信。CORS 等で安全に許可 |
