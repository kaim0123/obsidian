## 実装時の判断軸：全アプリ必須 vs 機能実装時

脆弱性対策は「毎回全部やる」のではなく、**どのアプリでも必ず押さえるもの**と、**その機能を入れるときに考えるもの**に分けると漏れにくい。

### A. ほぼすべてのWebアプリで対応が必要

HTMLを返し、状態を持ち、DBやセッションを使う一般的なWebアプリでは、次は前提として対策する。

| 領域 | 対応章 | 要点 |
|------|--------|------|
| 出力のエスケープ（XSS） | 05, 06 | HTML/属性/JS/URLなど文脈ごとのエスケープ |
| SQL呼び出しの安全化 | 07 | プリペアドステートメント、命令とデータの分離 |
| CSRF対策 | 08 | 状態変更リクエストの正当性確認 |
| セッション管理 | 01, 09 | 安全な発行・固定化対策・タイムアウト・無効化 |
| Cookieの扱い | 11 | `HttpOnly` / `Secure` / `SameSite` など |
| HTTPS（通信の保護） | （基礎・インフラ） | 盗聴・改ざん防止。TLSは必須前提 |
| 入力検証の基本 | 04 | 型・長さ・形式の検証（ただしこれだけでは不十分） |
| エラー・情報漏洩の抑制 | 04, 18, 24 | 詳細エラーを外部に出さない、キャッシュ制御 |
| ログ出力 | 24 | 認証失敗・重要操作の記録、秘密情報をログに書かない |

ユーザーアカウントがある場合は、次も **全アプリ必須** に近い。

| 領域 | 対応章 | 要点 |
|------|--------|------|
| 認証 | 21 | パスワード方針、MFA、ブルートフォース対策 |
| 認可 | 23 | サーバー側での権限チェック（UI制御だけでは不可） |
| アカウント管理 | 22 | 登録・変更・リセットの安全なフロー |

### B. 機能を実装するときに考えるセキュリティ

その機能を入れるときだけ、対応する脅威と対策を設計に含める。

| 機能・処理 | 対応章 | 考えること |
|------------|--------|------------|
| 外部URLへのリダイレクト | 10 | オープンリダイレクト、許可リスト |
| メール送信 | 12 | ヘッダインジェクション、送信先の制御 |
| ファイルの読み書き・パス指定 | 13 | パストラバーサル、権限外ファイルへのアクセス |
| OSコマンド・外部プロセス呼び出し | 14 | コマンドインジェクション、呼び出し自体の回避 |
| ファイルアップロード | 15 | 拡張子・内容検査、保存場所、実行権限 |
| 動的インクルード | 16 | 任意ファイル読み込み・実行 |
| XML / YAML / シリアライズ等の読み込み | 17 | XXE、デシリアライズ攻撃 |
| キャッシュ・CDN・共有ストレージ | 18 | キャッシュ汚染、他ユーザーへの情報混入 |
| Web API（JSON等） | 19 | 認証・認可、過剰なデータ公開、レート制限 |
| クライアント側JavaScript | 20 | 秘密情報の埋め込み禁止、DOM XSS、依存ライブラリ |
| CORS設定 | 03 | 許可オリジンの最小化、資格情報付きリクエスト |

### 判断の流れ（実装チェック）

```
機能を追加する
  │
  ├─ 全アプリ必須（A）は満たしているか？
  │     XSS / SQLi / CSRF / セッション / Cookie / HTTPS / ログ …
  │
  └─ この機能固有のリスク（B）は何か？
        メール？ ファイル？ リダイレクト？ API？ コマンド実行？
        → 該当章の対策を設計・実装・テストに含める
```

## 多層防御とOSI参照モデル

アプリ層だけ守っても、下位層や運用が弱いと突破される。**1つの対策が破られても次の層で止める**のが多層防御（Defense in Depth）。

OSI参照モデルに沿って、各層の脅威・対策と、Webサービスでの典型的な配置をまとめる（実務では層がまたがる対策も多い。上からインターネット側）。

| 層 | 名称 | 主な脅威の例 | セキュリティ対策の例 | Webサービスでの配置例 |
|----|------|--------------|----------------------|----------------------|
| **L7** | アプリケーション | SQLi, XSS, CSRF, 認可不備, 不正API利用 | セキュアコーディング、入力検証・出力エスケープ、認証・認可、レート制限、セキュアな設定 | WAF → Webアプリ（認証・認可・入出力対策）→ API認可 |
| **L6** | プレゼンテーション | 平文データの盗聴・改ざん、不正な符号化 | TLSによる暗号化、証明書管理、適切な文字コード・エンコーディング | TLS（HTTPS）の暗号化・証明書 |
| **L5** | セッション | セッションハイジャック、固定化、なりすまし | 安全なセッションID、再発行、タイムアウト、Cookie属性、再認証 | セッション・Cookie管理 |
| **L4** | トランスポート | ポートスキャン、不正なTCP/UDP通信 | 不要ポート閉鎖、ファイアウォール（ポート制御）、TLS終端の適切な配置 | 境界FW（ポート制御）、TLS終端 |
| **L3** | ネットワーク | 不正ルーティング、IPスプーフィング、DDoS | ファイアウォール（IP/ACL）、VPN、IDS/IPS、DDoS対策、セグメンテーション | DDoS対策・境界FW・IDS/IPS |
| **L2** | データリンク | 不正端末の接続、ARPスプーフィング | VLAN分割、ポートセキュリティ、MAC制限（環境による） | VPC/サブネット分割、内部NWの分離 |
| **L1** | 物理 | 機器への不正アクセス、ケーブル盗聴 | 入退室管理、ラック施錠、媒体管理、冗長化・バックアップ拠点 | データセンター／クラウド事業者の物理管理 |
| **（データ）** | L7の先 | 情報漏洩、不正参照・改ざん | DBアクセス制御、保存時暗号化、バックアップ | DB・ストレージの権限と暗号化 |
| **（運用）** | 人・プロセス | 設定ミス、未パッチ、検知遅れ | パッチ適用、監視、インシデント対応 | ログ監視・脆弱性管理・初動手順 |

アプリ開発者が主に担うのは **L5–L7（セッション・アプリ・データ）**。L1–L4 はインフラ・クラウド設定と分担しつつ、前提として把握しておく。

## 補足：ノートに加えて押さえておきたいこと

本書の章立てに直接は無いが、実務ではセットで必要になる領域。

| 領域 | なぜ必要か |
|------|------------|
| **セキュリティバイデザイン** | 後付け対策は漏れやすくコストが高い。要件・設計段階から脅威を洗い出す |
| **依存ライブラリ・サプライチェーン** | 自前コード以外の脆弱性（CVE）が侵入経路になる。更新・SBOM・スキャン |
| **設定・デプロイのセキュリティ** | デバッグモード公開、秘密情報の平文管理、過剰な権限のIAM |
| **秘密情報管理** | APIキー・DBパスワードをコードやリポジトリに置かない（環境変数・シークレット管理） |
| **脆弱性診断・テスト** | 単体・結合に加え、SAST/DAST、ペネトレーションテスト |
| **監視とインシデント対応** | ログ（24章）を活かす検知、初動・隔離・復旧の手順 |
| **プライバシー・法令** | 個人情報の取り扱い、同意、保存期間（アプリ設計に直結） |

## 学習の進め方（推奨）

1. **第I部（01–03）** でHTTP・オリジン・CORSの前提を固める
2. **第II部の必須系（04–09, 11）** で全アプリ共通のバグを押さえる
3. **第III部（21–24）** で認証・認可・アカウント・ログを学ぶ
4. **第II部の機能別（10, 12–20）** を、自分が実装する機能に合わせて読む
5. **多層防御・補足** でインフラ・運用まで視野を広げる
