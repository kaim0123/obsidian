# 安全なWebアプリケーションの作り方（第19章）

スマートフォンアプリやシングルページアプリケーション（SPA）では、画面の裏側で **WebAPI** が JSON などのデータをやり取りします。第19章では、その実装で起きやすい脆弱性と対策を解説します。

| 問題 | 概要 |
|------|------|
| **JSONエスケープの不備** | JSON の作り方・読み方が甘く、スクリプトとして実行されてしまう |
| **JSON直接閲覧によるXSS** | ブラウザが JSON を HTML として解釈し、XSS が起きる |
| **JSONPのコールバック関数名によるXSS** | コールバック名にスクリプトを埋め込まれ、XSS が起きる |
| **WebAPIのCSRF** | 別サイトから、ログイン済み利用者の権限で API を呼ばれる |
| **JSONハイジャック** | 古いブラウザなどで、他サイトから秘密の JSON を盗み取る |
| **JSONPの不適切な利用** | 秘密情報を JSONP で返し、他サイトから読まれてしまう |
| **CORSの検証不備** | 許可オリジンの設定が甘く、意図しないサイトから API を使われる |

第5章の XSS、第8章の CSRF は主に **HTML ページ** が舞台でした。本章は、**API が返す JSON / JSONP** と、**ブラウザのオリジン制限（CORS）** がポイントです。「データだけ返しているから安全」とは限りません。

## 📎 WebAPI実装における脆弱性の概要

WebAPI は、ブラウザやアプリから「データをください」「この操作をしてください」と頼まれる窓口です。応答は多くの場合 **JSON**（または昔ながらの **JSONP**）です。

| 用語 | 意味 |
|------|------|
| **WebAPI** | HTTP でデータをやり取りするプログラムの窓口 |
| **JSON** | データをテキストで表す形式（後述） |
| **JSONP** | `<script>` タグ経由でデータを取る古い手法（後述） |
| **CORS** | 別オリジンからのアクセスを、サーバーが許可する仕組み |

便利な一方で、応答の作り方・読み方・呼び出し方を誤ると、XSS・CSRF・情報漏洩につながります。

### 日常生活での例え

- **正常**: 窓口で「自分の注文内容」を紙で受け取り、自分だけが読む
- **問題が起きた場合**: 紙の書き方が悪く、読んだ人が「命令」として実行してしまう。あるいは、隣の店の人が勝手に窓口へ注文を出す

### なぜ危険か

WebAPI は、ログイン済み利用者の **個人情報や操作権限** に触れることが多いです。実装を誤ると、次のような被害が出ます。

```
・ブラウザ上で悪意あるスクリプトが動く（XSS）
・利用者が意図しない操作が実行される（CSRF）
・メールアドレスやトークンなどの秘密情報が他サイトに漏れる
・攻撃者のサイトから、正規ユーザーの権限で API が呼ばれる
```

「画面がないから XSS は起きない」「JSON だから安全」と思い込むと、対策が抜け落ちます。

## 📘 JSONとは

**JSON（JavaScript Object Notation）** は、データをテキストで表すための形式です。人間にも読みやすく、多くの言語で扱えます。

```
【JSON の例】
{
  "name": "田中",
  "age": 30,
  "admin": false
}
```

| 特徴 | 説明 |
|------|------|
| **テキスト形式** | 文字列として送受信できる |
| **型がある** | 文字列・数値・真偽値・配列・オブジェクトなど |
| **言語非依存** | JavaScript 以外（PHP、Python、Java など）でも使える |

WebAPI では、「サーバーが JSON を返す → クライアントが読み取る」という流れが一般的です。

### JavaScript側のJSONとオブジェクトの相互変換

ブラウザ上の JavaScript では、次の API で **オブジェクト ↔ JSON文字列** を変換します。

| API | 役割 | 例 |
|-----|------|-----|
| **`JSON.stringify`** | オブジェクト → JSON文字列 | `JSON.stringify({a:1})` → `'{"a":1}'` |
| **`JSON.parse`** | JSON文字列 → オブジェクト | `JSON.parse('{"a":1}')` → `{a:1}` |

```
【安全な読み取りのイメージ】
1. サーバーから '{"name":"田中"}' という文字列を受け取る
2. JSON.parse でオブジェクトに変換する
3. data.name のように値だけを使う
```

ここで **やってはいけない** のが、`eval` で JSON を解釈することです。

```
【危険】
eval('(' + jsonText + ')')
→ JSON のつもりが、任意の JavaScript として実行され得る
```

`JSON.parse` は「JSON として正しいデータだけ」をオブジェクトにします。`eval` は「プログラムとして実行」するため、攻撃コードまで動いてしまいます。

### 日常生活での例え

- **`JSON.parse`**: 「注文票」として読み、商品名と個数だけ取り出す
- **`eval`**: 注文票に書かれた文字を「作業指示」としてそのまま実行する

## 📘 JSONPとは

**JSONP（JSON with Padding）** は、CORS が普及する前に使われた、**別オリジンからデータを取る古い手法** です。

通常、ブラウザは `<script src="...">` で **別サイトの JavaScript も読み込めます**。JSONP はこの性質を使い、サーバーに「関数呼び出しの形」でデータを返させます。

```
【呼び出し側（HTML）】
<script src="https://api.example.com/data?callback=showData"></script>

【サーバーの応答（イメージ）】
showData({"name":"田中","age":30});
```

ブラウザはこれを JavaScript として実行し、`showData` 関数にデータが渡ります。

| 項目 | JSON（通常の API） | JSONP |
|------|-------------------|-------|
| **取り方** | `fetch` / `XMLHttpRequest` など | `<script>` タグ |
| **応答の形** | `{"name":"田中"}` | `callback({"name":"田中"})` |
| **オリジン制限** | CORS で制御できる | `<script>` なので別オリジンでも読める |
| **現状** | 推奨 | できるだけ使わない |

JSONP は「別サイトからでも読める」ことが前提の仕組みです。そのため、**秘密情報を返す用途には向きません**。現代では **CORS + JSON** に移行するのが基本です。

## 💥 JSONエスケープの不備

**JSONエスケープの不備** とは、JSON 文字列を作るときに **特殊文字のエスケープが足りない**、あるいは **危険な方法で JSON を解釈する** ことで、意図しないスクリプト実行につながる問題です。

| 項目 | 内容 |
|------|------|
| **分類** | インジェクション / XSS に近い |
| **典型的な原因** | 文字列連結で JSON を手作りする、`eval` や JSONP で評価する |
| **典型的な被害** | ブラウザ上での任意スクリプト実行 |

### 日常生活での例え

- **正常**: 「名前は田中です」とメモに書く。引用符などは正しくエスケープされている
- **攻撃**: 名前欄に `"); 悪い命令(); //` と書き、メモ全体が「命令文」として読まれてしまう

### 原因

主に次の2点です。

```
1. JSON文字列の生成時に、適切なエスケープ処理が行われていない
   （手作業の文字列連結で "{"name":"" + 入力 + ""}" のように作る）

2. JSON の評価に eval などを用いている、または JSONP を用いている
   （データとして読むのではなく、プログラムとして実行している）
```

悪い生成例のイメージです。

```
【悪いイメージ（擬似コード）】
入力 name = '"); alert(1);//'
応答 = '{"name":"' + name + '"}'
→ {"name":""); alert(1);//"}
→ これを eval や script として評価すると、alert が動く
```

信頼できるライブラリの `json_encode`（PHP）や `JSON.stringify`（JavaScript）を使えば、引用符や制御文字は正しくエスケープされます。

### 対策

| 対策 | 説明 |
|------|------|
| **文字列連結で JSON を作らない** | 手作業の `"{" + ... + "}"` はミスしやすい |
| **信頼できるライブラリで生成する** | PHP の `json_encode`、言語標準の JSON API など |
| **`eval` ではなく `JSON.parse` で解釈する** | データとしてだけ読む |

```
【対策の優先順位】
1. JSON は必ずライブラリ / 標準 API で生成する
2. クライアント側は JSON.parse（または同等の安全な API）で読む
3. 新規開発では JSONP を使わない（後述）
```

「エスケープを自分で書く」より、「正しい生成関数に任せる」方が安全です。

## 💥 JSON直接閲覧によるXSS

**JSON直接閲覧によるXSS** とは、API が返した JSON を、利用者がブラウザのアドレスバーなどで **直接開いたとき**、ブラウザがそれを HTML として解釈し、中のスクリプトが動いてしまう問題です。

昔の Internet Explorer（IE）などでは、`Content-Type` が正しくても、中身を見て HTML と判断する **コンテンツスニッフィング** がありました。JSON の中に `<script>` のような文字列があると、HTML として実行される危険がありました。

| 項目 | 内容 |
|------|------|
| **分類** | XSS |
| **典型的な原因** | MIME タイプ不備、`<` `>` の未エスケープ、nosniff 未設定 |
| **典型的な被害** | 直接 URL を開いた利用者のブラウザでスクリプト実行 |

### 日常生活での例え

- **正常**: 「データ一覧」と書かれた紙を、データとしてだけ読む
- **攻撃**: 紙の一部が「命令書」に見え、受け取った人が命令として実行してしまう

### 原因と IE のサポート状況

現代の主要ブラウザでは、この問題は起きにくくなっています。ただし、次の理由で対策は今も有効です。

```
・古いブラウザや特殊な環境が残っている場合がある
・防御の多層化（Defense in Depth）として有効
・MIME タイプや nosniff は、他の攻撃の緩和にも役立つ
```

### JSONでも `<` `>` までエスケープする

JSON の仕様上、`<` や `>` は必ずしもエスケープ必須ではありません。しかし、**HTML として誤解釈されるのを防ぐ** ため、Unicode エスケープすることが推奨されます。

PHP の `json_encode` では、オプションで制御できます。

| オプション | エスケープ対象文字 | エスケープ結果の例 |
|------------|--------------------|--------------------|
| **`JSON_HEX_TAG`** | `<` `>` | `\u003C` `\u003E` |
| **`JSON_HEX_AMP`** | `&` | `\u0026` |
| **`JSON_HEX_APOS`** | `'` | `\u0027` |
| **`JSON_HEX_QUOT`** | `"` | `\u0022` |

```
【例】
入力に <script> が含まれる場合

通常の JSON:
{"msg":"<script>alert(1)</script>"}

JSON_HEX_TAG 適用後:
{"msg":"\u003Cscript\u003Ealert(1)\u003C/script\u003E"}
```

ブラウザが HTML として見ても、`<script>` というタグにはならないため、実行されにくくなります。

### 対策

| 対策 | 説明 |
|------|------|
| **MIMEタイプを正しく設定する** | `Content-Type: application/json` など |
| **`X-Content-Type-Options: nosniff`** | ブラウザに「中身を推測して HTML 扱いしない」と指示する |
| **`<` などを Unicode エスケープする** | `JSON_HEX_TAG` など |
| **XHR / fetch などからのみ呼べるようにする** | 直接閲覧や `<script>` 経由を想定しない設計にする |

```
【レスポンスヘッダの例】
Content-Type: application/json; charset=utf-8
X-Content-Type-Options: nosniff
```

「正しい MIME タイプ」「nosniff」「危険文字のエスケープ」を組み合わせると、直接閲覧による XSS をかなり抑えられます。

## 💥 JSONPのコールバック関数名によるXSS

**JSONPのコールバック関数名によるXSS** とは、利用者が指定した **コールバック関数名** を、サーバーが検証せずそのまま応答に埋め込み、スクリプトとして実行されてしまう問題です。

```
【正常な JSONP】
リクエスト: /api?callback=showData
応答:       showData({"name":"田中"});

【攻撃のイメージ】
リクエスト: /api?callback=alert(1)//
応答:       alert(1)//({"name":"田中"});
→ alert(1) が実行される
```

さらに悪い場合、コールバック名に HTML を混ぜ、`Content-Type` が `text/html` だと、HTML としての XSS にもなります。

| 項目 | 内容 |
|------|------|
| **分類** | XSS |
| **典型的な原因** | コールバック名の未検証、MIME タイプの誤り |
| **典型的な被害** | 任意スクリプトの実行、Cookie 窃取など |

### 日常生活での例え

- **正常**: 「田中さん宛て」と封筒に書き、田中さんだけが開ける
- **攻撃**: 宛名欄に「開けたら爆弾を起動せよ」と書かれ、そのとおり実行される

### 原因

```
1. 外部から指定されたコールバック関数名を、検証せずそのまま表示している
2. MIMEタイプを text/javascript とすべきところを text/html としている
```

コールバック名は「関数名」であるべきなのに、任意の文字列を許すと、そこがスクリプトの入り口になります。

### 対策

| 対策 | 説明 |
|------|------|
| **文字種と文字数を制限する** | 英数字とアンダースコアのみ、長さ上限あり、など |
| **許可リスト方式にする** | あらかじめ決めた関数名だけ許可する |
| **MIMEタイプを正しく設定する** | `application/javascript` や `text/javascript`（HTML にしない） |

```
【コールバック名の検証イメージ】
・許可: showData, callback, cb_1
・拒否: alert(1), <script>, a;evil()

正規表現の例（イメージ）:
/^[A-Za-z_][A-Za-z0-9_]*$/
かつ長さは 1〜32 文字など
```

そもそも JSONP をやめて CORS + JSON にすれば、この問題自体を避けられます。

## 💥 WebAPIのクロスサイト・リクエストフォージェリ

**WebAPI に対する CSRF** は、第8章の CSRF と同じ考え方です。利用者がログインした状態で、**攻撃者のサイトから、その利用者の権限で API を呼び出させる** 攻撃です。

WebAPI でも Cookie でセッションを維持している場合、ブラウザは別サイトからのリクエストに Cookie を付けることがあります。その結果、「本人が操作した」とサーバーが誤認します。

| 項目 | 内容 |
|------|------|
| **分類** | CSRF |
| **典型的な原因** | 状態変更 API に CSRF 対策がない、CORS の設定ミス |
| **典型的な被害** | 不正な投稿・設定変更・送金・退会など |

### 日常生活での例え

- **正常**: 本人が窓口で「住所変更」を申請する
- **攻撃**: 別の店で「ここにサインして」と渡された紙が、実は住所変更届で、本人の印鑑（Cookie）が勝手に押される

### WebAPIに対するCSRF攻撃経路

| 経路 | 説明 |
|------|------|
| **GETリクエストによる攻撃** | `<img src="https://api.example.com/delete?id=1">` のように、画像読み込みで GET を飛ばす |
| **HTMLフォームによる攻撃** | 攻撃ページの `<form>` が、対象 API へ POST する |
| **クロスオリジン対応のXHRによる攻撃** | CORS が緩いと、JavaScript から別オリジンの API を呼べる |

```
【GET による攻撃のイメージ】
攻撃ページ:
<img src="https://bank.example.com/api/transfer?to=attacker&amount=10000">

→ 被害者が攻撃ページを開くだけで、ログイン中なら振込 API が呼ばれる
（※ 本来、状態変更を GET で行うこと自体が問題）
```

```
【フォームによる攻撃のイメージ】
攻撃ページ:
<form action="https://api.example.com/change-email" method="POST">
  <input name="email" value="attacker@evil.example">
</form>
<script>document.forms[0].submit();</script>
```

### 対策

| 対策 | 説明 |
|------|------|
| **CSRFトークン** | 秘密のトークンをフォームやヘッダに付け、サーバーで検証する |
| **二重送信クッキー** | Cookie の値と同じ値を、リクエスト本体やヘッダにも送らせて照合する |
| **カスタムリクエストヘッダ** | `X-Requested-With: XMLHttpRequest` など、単純リクエストでは付けられないヘッダを必須にする |
| **入力データのMIMEタイプを検証する** | `Content-Type: application/json` のみ受け付ける、など |
| **CORSを適切に実装する** | 許可オリジンを必要最小限にし、資格情報付きを安易に許可しない |

```
【カスタムヘッダ対策の考え方】
・ブラウザの「単純リクエスト」では、独自ヘッダを付けられない
・API が「独自ヘッダ必須」なら、HTMLフォームだけでは呼べない
・ただし、CORS が緩いと XHR から独自ヘッダ付きで呼べるので、CORS も正しくする
```

状態を変える操作（登録・変更・削除）は **GET で行わない** ことも重要です。GET は「取得」専用にし、変更は POST / PUT / PATCH / DELETE と CSRF 対策をセットにします。

## 💥 JSONハイジャック

**JSONハイジャック** とは、他サイトのページから、ログイン済み利用者向けの **秘密の JSON** を盗み取る攻撃です。古いブラウザでは、`<script>` で JSON 配列を読み、JavaScript の配列コンストラクタを書き換えて中身を横取りする、といった手法がありました。

現代の主要ブラウザでは、この古典的な手口はほぼ使えません。ただし、**防御の習慣としては今も有効** な対策があります。

| 項目 | 内容 |
|------|------|
| **分類** | 情報漏洩 |
| **典型的な原因** | 秘密 JSON を GET で誰でも取れる、`<script>` でも読める応答 |
| **典型的な被害** | 個人情報・トークンなどの漏洩 |

### 日常生活での例え

- **正常**: 自分宛ての手紙は、自分だけがポストから取り出す
- **攻撃**: 手紙の書き方が「誰でも読める掲示」になっていて、通りがかりが中身を写し取る

### 対策

| 対策 | 説明 |
|------|------|
| **`X-Content-Type-Options: nosniff`** | コンテンツの誤判定を防ぐ |
| **`X-Requested-With: XMLHttpRequest` の確認** | `<script>` や単純な遷移ではなく、XHR / fetch からの呼び出しだけ許可する |
| **認証と認可** | ログイン必須にし、本人のデータだけ返す |
| **秘密情報を JSONP で返さない** | `<script>` 経由で読まれる前提の仕組みを使わない |

```
【X-Requested-With 確認のイメージ】
サーバー側:
if (リクエストヘッダに X-Requested-With: XMLHttpRequest がない) {
  エラーを返す
}
```

自前の JavaScript からはヘッダを付けられますが、他サイトの `<script src="...">` では付けられません。その差を利用して、「正規のクライアントだけ」に絞ります。

## 💥 JSONPの不適切な利用

**JSONPの不適切な利用** とは、JSONP の性質（別オリジンの `<script>` からも読める）を理解せず、**秘密情報を JSONP で返してしまう** ことです。

JSONP は「公開データを、別サイトのページからも使う」ための仕組みです。メールアドレス、セッション情報、個人設定などを JSONP で返すと、攻撃者のサイトからも同じデータを読めます。

| 項目 | 内容 |
|------|------|
| **分類** | 情報漏洩 |
| **典型的な原因** | 秘密 API を JSONP 対応にしてしまう |
| **典型的な被害** | 個人情報・認証情報のクロスオリジン漏洩 |

### JSONPによる秘密情報提供

```
【危険な例】
https://example.com/api/me?callback=cb
応答: cb({"email":"user@example.com","token":"secret"});

攻撃者のページ:
<script src="https://example.com/api/me?callback=steal"></script>
→ 被害者がログイン中なら、攻撃者の steal 関数に秘密情報が渡る
```

Cookie が付く GET リクエストなので、「本人として」秘密 API が呼ばれてしまいます。

### 対策

| 対策 | 説明 |
|------|------|
| **JSONPはできるだけ使わない** | CORS + JSON に移行する |
| **使うなら公開情報のみ** | 誰が呼んでもよいデータだけ |
| **信頼できる提供元のみを使う** | クライアント側も、怪しい JSONP を読み込まない |

```
【方針】
・新規開発: JSONP は使わない
・既存の JSONP: 公開データ以外は廃止し、CORS + JSON へ
・やむを得ず残す場合: 秘密情報を絶対に載せない
```

「昔のライブラリが JSONP 前提」でも、秘密情報の API まで JSONP 対応にする必要はありません。

## 💥 CORSの検証不備

**CORS（Cross-Origin Resource Sharing）** は、ブラウザが「別オリジンのスクリプトから、この API を呼んでよいか」をサーバーに確認する仕組みです。サーバーは応答ヘッダで許可オリジンを伝えます。

**CORSの検証不備** とは、許可するオリジンの判定が甘く、**意図しないサイトから API を読まれたり、資格情報付きで呼ばれたりする** 問題です。

| 項目 | 内容 |
|------|------|
| **分類** | アクセス制御の不備 |
| **典型的な原因** | `*` の安易な使用、Origin チェックの緩和しすぎ |
| **典型的な被害** | 秘密 API の読み取り、CSRF 的な不正操作 |

### 日常生活での例え

- **正常**: 来客リストに載っている人だけ入館できる
- **問題**: 受付が「誰でもどうぞ」と書いてある、または名簿チェックをサボっている

### よくある失敗

| 失敗 | 何が起きるか |
|------|----------------|
| **オリジンとして `*` を指定する** | あらゆるサイトから読み取りが許可される（資格情報付きでは本来 `*` は使えないが、実装ミスで危険な組み合わせになることがある） |
| **Origin のチェックをわざと緩和する** | リクエストの `Origin` をそのまま `Access-Control-Allow-Origin` に返す、部分一致だけで許可する、など |

```
【危険な実装のイメージ】
// リクエストの Origin を無条件で許可してしまう
Access-Control-Allow-Origin: （リクエストの Origin をそのまま）
Access-Control-Allow-Credentials: true

→ 攻撃者のサイト（https://evil.example）からも、
  Cookie 付きで API を呼べてしまう
```

```
【部分一致の罠】
許可したい: https://example.com
誤った判定: Origin に "example.com" が含まれるか？

攻撃者のオリジン例:
https://example.com.evil.example
https://notexample.com
→ 意図せず許可されることがある
```

### 対策

| 対策 | 説明 |
|------|------|
| **許可オリジンは許可リストで厳密に** | 完全一致で比較する |
| **`*` と Credentials を安易に組み合わせない** | 認証付き API では、必要なオリジンだけ明示する |
| **不要なら CORS を有効にしない** | 同一オリジンだけで足りるなら、余計な許可をしない |
| **プリフライトを正しく扱う** | 許可メソッド・ヘッダも最小限にする |

```
【安全な考え方】
1. デフォルトは拒否
2. 必要なオリジンだけを許可リストに載せる
3. 完全一致で判定する（部分一致や末尾一致にしない）
4. 認証が必要な API では、Allow-Credentials と許可オリジンを慎重に組む
```

CORS は「ブラウザの親切な制限」を、サーバーが一部ゆるめる仕組みです。ゆるめすぎると、CSRF や情報漏洩の穴になります。

## 🛡️ セキュリティを強化するレスポンスヘッダ

WebAPI や Web アプリ全体で、次のレスポンスヘッダを付けると、攻撃の影響を小さくできます。

| ヘッダ | 役割 |
|--------|------|
| **`X-Frame-Options`** | ページを iframe に埋め込まれないようにし、クリックジャッキングを防ぐ |
| **`X-Content-Type-Options`** | `nosniff` で、MIME タイプの誤判定を防ぐ |
| **`X-XSS-Protection`** | 古いブラウザの XSS フィルタを制御する（現代では CSP を優先し、`0` で無効化する方針もある） |
| **`Content-Security-Policy`** | 読み込んでよいスクリプトやリソースを制限し、XSS の被害を抑える |
| **`Strict-Transport-Security`** | HTTPS の利用を強制し、平文 HTTP へのダウングレードを防ぐ |

```
【WebAPI で特に重要なもの】
・X-Content-Type-Options: nosniff
  → JSON の誤解釈やハイジャック対策の土台
・Content-Type: application/json
  → 応答が JSON であることを明示する
・（ブラウザ向けページなら）Content-Security-Policy
  → XSS 時の被害範囲を狭める
```

ヘッダだけで全ての脆弱性が消えるわけではありません。**正しい JSON 生成・CSRF 対策・CORS の許可リスト** が本筋で、ヘッダはそれを補強する防御層です。

## 💥 APIからの大量取得（2026年の事例から・追記）

徳丸本の第19章の範囲外ですが、2026年の国内の情報漏洩で問題になった論点です（全体は [[10_2026年_国内情報漏洩の動向と対策]]）。

アフラック生命の事例（約440万人分）では、攻撃は **通常の利用と同じ形式のアクセス** で行われ、**短時間の大量照会を監視・制御する機能が不足** していたとされました。API が 1 件ずつ正しく認可していても、**何件でも取れる** と大量漏洩につながります。OWASP API Security Top 10 の **API4:2023 Unrestricted Resource Consumption**（リソース消費の制限なし）や、**API1:2023 BOLA**（オブジェクト単位の認可の不備）に当たります。

| 対策 | 内容 |
|---|---|
| ページサイズの上限 | `?limit=100000` を受け付けない。サーバー側で最大値を決める |
| レート制限 | ユーザー・トークン・IP ごとに、時間あたりのリクエスト数を制限する |
| 取得件数の上限 | 一定時間に取得できる **レコード数の合計** を制限し、超えたら止めてアラートを出す（[[A09_ログとモニタリングの不備]]） |
| ID を推測させない | 連番 ID だと 1 から順に取得される。UUID などにし、**毎回、所有者かどうかをチェック** する |
| 一括エクスポートは別扱い | CSV 出力などは権限を分け、実行を記録・通知する |

```
❌ GET /api/customers?page=1&limit=100000  → 全件返す
✅ limit は最大 100。1 時間の取得件数が上限を超えたら 429/403 を返し、アラート
```

## 📋 まとめ

| 項目 | 本質 | 基本対策 |
|------|------|----------|
| **JSONエスケープの不備** | 手作り JSON や `eval` でスクリプト実行 | ライブラリで生成、`JSON.parse` で解釈 |
| **JSON直接閲覧によるXSS** | JSON が HTML として誤解釈される | 正しい MIME、`nosniff`、`<` 等の Unicode エスケープ |
| **JSONPコールバック名XSS** | コールバック名にコードを埋め込まれる | 文字種・長さ制限、正しい MIME、JSONP 廃止 |
| **WebAPIのCSRF** | 別サイトから本人権限で API を呼ばれる | CSRF トークン、カスタムヘッダ、CORS の適切な実装 |
| **JSONハイジャック** | 秘密 JSON を他サイトから読む | `nosniff`、XHR ヘッダ確認、JSONP で秘密を返さない |
| **JSONPの不適切な利用** | 秘密情報を `<script>` 経由で渡す | CORS + JSON へ移行、公開情報のみ |
| **CORSの検証不備** | 許可オリジンが広すぎる | 許可リストの完全一致、最小権限 |

```
WebAPI 実装の安全の基本:

1. JSON は標準 API / ライブラリで生成し、eval で読まない
2. Content-Type: application/json と X-Content-Type-Options: nosniff を付ける
3. JSONP は使わず、CORS + JSON にする（使うなら公開情報のみ）
4. 状態変更 API には CSRF 対策を入れる（GET で変更しない）
5. CORS の許可オリジンは、必要最小限を完全一致で許可する
6. セキュリティヘッダで防御を多層化する
```

本章に共通する考え方は、**「API が返すのはデータか、それとも実行可能なプログラムか」「誰のサイトから、誰の権限で呼ばれているか」** を疑うことです。JSON は便利ですが、生成・解釈・呼び出し経路のどこかが甘いと、XSS・CSRF・情報漏洩につながります。現代的な基本形は **CORS + JSON + 正しいヘッダ + CSRF 対策** です。古い JSONP や手作業の文字列連結から離れるほど、事故は起きにくくなります。
