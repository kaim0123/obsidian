## 🔀 オープンリダイレクト

**オープンリダイレクト（Open Redirect）** とは、Webアプリケーションが **任意の外部 URL** へリダイレクトしてしまう脆弱性です。

### 日常生活での例え

- **正常なリダイレクト**: ログイン後、自サイトのマイページへ移動
- **オープンリダイレクト**: 「example.com のリンク」に見せかけて、フィッシングサイトへ飛ばされる

### 脆弱なコード

```php
// ❌ ユーザー指定 URL へそのままリダイレクト
$url = $_GET['url'];
header('Location: ' . $url);
exit;
```

```
https://example.com/redirect?url=https://evil.com/phishing
  ↑ 信頼できるドメイン              ↑ 実際の行き先
```

### 攻撃の流れ

```
1. 攻撃者が悪意ある URL を作成
   https://bank.com/redirect?url=https://evil-bank.com/login

2. 被害者にメール・SNS で送る
   「銀行からのお知らせ」等

3. 被害者が bank.com の URL をクリック（信頼してクリック）

4. bank.com が evil-bank.com へリダイレクト

5. 偽のログインページで ID・パスワードを入力させられる
```

### 被害

| 被害 | 説明 |
|------|------|
| **フィッシング** | 信頼ドメイン経由で偽サイトへ誘導 |
| **OAuth 攻撃** | 認可コード等の窃取（リダイレクト URI 悪用） |
| **マルウェア配布** | 外部サイトへの誘導 |
| **信頼の悪用** | 正規サイトの URL が攻撃に利用される |

### よくある実装箇所

- ログイン後の「元のページへ戻る」
- ログアウト後のリダイレクト
- 言語切替・モバイル版切替
- 広告・提携先リンク
- 「続きはこちら」ボタン

---

## ✅ 差し支えがない場合

外部ドメインへのリダイレクトは **すべて禁止** すべきではありません。用途によっては **問題ない場合** があります。

### 差し支えがない（許容しうる）ケース

| ケース | 説明 |
|--------|------|
| **自サイト内のみ** | 同一ドメイン内のパスへリダイレクト |
| **明示的な外部リンク** | ユーザーが「外部サイトへ移動」と理解できる UI |
| **検証済みの提携先** | ホワイトリストに登録されたパートナー URL |
| **OAuth 等の標準フロー** | 仕様に沿った redirect_uri の検証 |

### 判断のポイント

```
危険:
  → ユーザー入力や URL パラメータを検証なしで Location に設定

許容（対策済み）:
  → 遷移先が固定、またはホワイトリストで検証済み
  → ユーザーに外部遷移が明示されている
```

---

## 🌍 外部のドメインに遷移する仕様

アプリケーションの **仕様として** 外部ドメインへ遷移する機能があります。

### 例

| 機能 | 遷移先 |
|------|--------|
| **SNS 連携** | twitter.com, facebook.com |
| **決済** | 決済代行会社のドメイン |
| **SSO / OAuth** | 認可サーバーのドメイン |
| **提携サービス** | パートナー企業のサイト |
| **アプリストア** | App Store, Google Play |

### 設計上の注意

```
外部遷移が仕様に含まれる場合でも:
  ✅ 遷移先 URL はサーバー側で管理（固定 or ホワイトリスト）
  ✅ ユーザー入力をそのまま Location に使わない
  ❌ ?url= パラメータで任意 URL を受け付けない
```

---

## 👁️ 外部ドメインに遷移することが自明である

外部サイトへ移る場合、**ユーザーがそれと分かる UI** にすることが重要です。

### 自明にする方法

| 方法 | 例 |
|------|-----|
| **確認画面** | 「外部サイト（○○.com）へ移動します。よろしいですか？」 |
| **アイコン表示** | 外部リンクアイコン（↗）を付ける |
| **文言の明示** | 「外部サイトへ移動します」 |
| **中間ページ** | 自サイトの警告ページを挟んでからリダイレクト |

```html
<!-- 中間ページの例 -->
<p>これより外部サイト（partner.example.net）へ移動します。</p>
<p>example.com とは別のサイトです。個人情報の入力にはご注意ください。</p>
<a href="/go/3">partner.example.net へ移動する</a>
<!-- /go/3 はサーバー側で ID→URL に変換 -->
```

### なぜ重要か

```
オープンリダイレクト + 自明でない UI
  → ユーザーは bank.com から来たと思い込む
  → フィッシング成功

対策済み + 自明な UI
  → ユーザーは外部サイトだと認識
  → フィッシングリスク低減
```

**注意:** UI で自明にするだけでは **オープンリダイレクト脆弱性は解消されない**。技術的対策と併用する。

## 🛡️ オープンリダイレクトの対策

オープンリダイレクト対策には、主に3つの方法があります。

---

## 📌 リダイレクト先のURLを固定にする

**最も安全な方法** は、リダイレクト先 URL を **サーバー側で固定** することです。

### 実装例

```php
// ✅ ログイン後は常にダッシュボードへ
header('Location: /dashboard');
exit;

// ✅ ログアウト後は常にトップページへ
header('Location: /');
exit;
```

### 戻り先 URL が必要な場合

```php
// ❌ 任意 URL を受け付ける
$returnUrl = $_GET['return'];
header('Location: ' . $returnUrl);

// ✅ 自サイト内のパスのみ許可
$returnUrl = $_GET['return'] ?? '/';
if (!str_starts_with($returnUrl, '/') || str_starts_with($returnUrl, '//')) {
    $returnUrl = '/';
}
header('Location: ' . $returnUrl);
```

### ポイント

| ポイント | 説明 |
|---------|------|
| **相対 URL の検証** | `/` で始まり、`//` で始まらない |
| **絶対 URL 禁止** | `http://` で始まる外部 URL は拒否 |
| **デフォルト値** | 不正な場合は安全な固定 URL へ |

---

## 🔢 リダイレクト先のURLを直接指定せずに番号指定にする

URL を直接パラメータで渡す代わりに、**番号（ID）** でサーバー側の URL リストから選択します。

### 仕組み

```
サーバー側のマッピング:
  1 → https://partner-a.example.com
  2 → https://partner-b.example.com
  3 → https://help.example.com

リクエスト: /redirect?id=2
  → サーバーが ID=2 の URL へリダイレクト
  → ユーザーは URL を直接指定できない
```

### 実装例

```php
$redirectMap = [
    1 => 'https://partner-a.example.com',
    2 => 'https://partner-b.example.com',
    3 => 'https://help.example.com',
];

$id = (int)($_GET['id'] ?? 0);
if (!isset($redirectMap[$id])) {
    header('Location: /');
    exit;
}
header('Location: ' . $redirectMap[$id]);
exit;
```

### メリット

| メリット | 説明 |
|---------|------|
| **任意 URL 不可** | 攻撃者が evil.com を指定できない |
| **管理が容易** | 提携先変更はサーバー側リストを更新 |
| **監査可能** | 許可 URL がコードまたは DB で明示 |

---

## 🏠 リダイレクト先のドメイン名をチェックする

URL をパラメータで受け取る必要がある場合、**ドメイン名をホワイトリスト** で検証します。[[02_XSS発展編（徳丸本6章）|第6章]] でも触れた手法です。

### ホワイトリスト検証

```php
function isAllowedRedirectUrl(string $url): bool {
    $allowedHosts = ['example.com', 'www.example.com', 'partner.example.net'];

    $parsed = parse_url($url);
    if ($parsed === false || !isset($parsed['host'])) {
        return false;
    }

    // スキーム検証
    if (!in_array($parsed['scheme'] ?? '', ['https', 'http'], true)) {
        return false;
    }

    // ホスト名検証（完全一致）
    return in_array($parsed['host'], $allowedHosts, true);
}

$url = $_GET['url'] ?? '';
if (!isAllowedRedirectUrl($url)) {
    header('Location: /');
    exit;
}
header('Location: ' . $url);
exit;
```

### 注意すべき bypass

| 手法 | 例 | 対策 |
|------|-----|------|
| **サブドメイン偽装** | `example.com.evil.com` | ホスト名の **完全一致** |
| **プロトコル相対** | `//evil.com` | `//` で始まる URL を拒否 |
| **URL エンコード** | `%2f%2fevil.com` | デコード後に再検証 |
| **@ 記号** | `https://example.com@evil.com` | parse_url で host を正しく取得 |
| **javascript:** | `javascript:alert(1)` | スキームを https/http に限定 |

### 相対 URL の扱い

```php
// //evil.com は https://evil.com と同義
if (str_starts_with($url, '//')) {
    return false;  // 拒否
}
```

## 📨 HTTPヘッダ・インジェクション

**HTTPヘッダインジェクション（HTTP Header Injection）** は、ユーザー入力が **HTTP レスポンスヘッダ** に混入し、意図しないヘッダを注入する脆弱性です。

| 項目 | 内容 |
|------|------|
| **分類** | インジェクション系（[[02_Webアプリの機能と脆弱性（徳丸本4章）\|第4章]]） |
| **対象** | Location、Set-Cookie、Content-Type 等のレスポンスヘッダ |

### 日常生活での例え

- **正常**: サーバーが「このページへ移動して」と Location ヘッダを1つ送る
- **インジェクション**: 入力に改行を混ぜ、**追加のヘッダ** や **別のレスポンス** を送らせる

### 脆弱なコード

```php
// ❌ ユーザー入力を Location ヘッダに直接出力
$url = $_GET['url'];
header('Location: ' . $url);
```

### 攻撃入力

```
url=/home%0d%0aSet-Cookie:%20admin=1

%0d%0a = キャリッジリターン + ラインフィード（改行）
```

### 生成されるレスポンス

```
HTTP/1.1 302 Found
Location: /home
Set-Cookie: admin=1

→ 攻撃者が任意の Cookie を注入可能
```

### 他の攻撃例

| 注入先 | 攻撃 |
|--------|------|
| **Location** | リダイレクト + 追加ヘッダ |
| **Set-Cookie** | 任意 Cookie の設定 |
| **本文との混在** | ヘッダ後に HTML を注入（XSS 的効果） |

### 関連：メールヘッダインジェクション

メール送信機能で **To / Subject 等** に改行を混入させ、Bcc 等を追加する攻撃も同系統です（[[02_Webアプリの機能と脆弱性（徳丸本4章）|第4章]]）。

## 🛡️ HTTPヘッダインジェクションの対策

---

## 🚫 外部からのパラメータをHTTPレスポンスヘッダとして出力しない

**根本対策** は、外部入力を **ヘッダ値として使わない** ことです。

```php
// ❌ ユーザー入力をヘッダに
header('Location: ' . $_GET['url']);
header('Set-Cookie: theme=' . $_GET['theme']);

// ✅ 固定値または検証・変換済みの値のみ
header('Location: /dashboard');
header('Set-Cookie: theme=light; HttpOnly; Secure');
```

### 原則

```
HTTP レスポンスヘッダの値 =
  サーバー側で決定した固定値
  または厳密に検証・サニタイズした値

ユーザー入力をそのままヘッダに載せない
```

---

## 🔧 専用APIと改行チェック（両方実施）

ヘッダ生成が必要な場合は、次の **2つを両方** 実施します。

### ① リダイレクトやクッキー生成を専用 API に任せる

**散在させず、専用の関数・クラスに集約** し、検証ロジックを一箇所にまとめます。

```php
// リダイレクト専用関数
function safeRedirect(string $url): void {
    if (!isAllowedRedirectUrl($url)) {
        $url = '/';
    }
    header('Location: ' . $url);
    exit;
}

// Cookie 設定専用関数
function setThemeCookie(string $theme): void {
    $allowed = ['light', 'dark'];
    if (!in_array($theme, $allowed, true)) {
        $theme = 'light';
    }
    setcookie('theme', $theme, [
        'httponly' => true,
        'secure'   => true,
        'samesite' => 'Strict',
    ]);
}
```

### メリット

| メリット | 説明 |
|---------|------|
| **検証の一元化** | 漏れ・バラつきを防ぐ |
| **レビュー容易** | セキュリティコードが一箇所 |
| **テスト可能** | 専用関数の単体テスト |

### ② ヘッダ生成するパラメータの改行文字をチェック

どうしても外部入力を使う場合、**改行文字（CR/LF）を拒否** します。[[02_Webアプリの機能と脆弱性（徳丸本4章）|第4章]] の制御文字チェックと同様です。

```php
function containsHeaderInjectionChars(string $value): bool {
    return preg_match('/[\r\n\x00]/', $value) === 1;
}

function safeRedirect(string $url): void {
    if (containsHeaderInjectionChars($url)) {
        $url = '/';
    }
    if (!isAllowedRedirectUrl($url)) {
        $url = '/';
    }
    header('Location: ' . $url);
    exit;
}
```

### チェック対象の文字

| 文字 | コード | 危険性 |
|------|--------|--------|
| CR | `\r` (0x0D) | 新しいヘッダ行の開始 |
| LF | `\n` (0x0A) | 新しいヘッダ行の開始 |
| NULL | `\0` (0x00) | ヘッダの truncation |

### URL エンコードされた改行も注意

```
入力: %0d%0aSet-Cookie: evil=1
→ urldecode 後に改行チェックが必要
```

```php
$url = urldecode($_GET['url']);
if (containsHeaderInjectionChars($url)) {
    // 拒否
}
```

### フレームワークの利用

| 環境 | 推奨 |
|------|------|
| **PHP** | `header()` 前に検証、または Symfony Response 等 |
| **Express.js** | `res.redirect()` は比較的安全だが URL 検証は必要 |
| **一般** | ヘッダ出力 API をラップして統一 |

## 📝 まとめ

### オープンリダイレクト

| トピック | 要点 |
|---------|------|
| オープンリダイレクト | 任意 URL へ飛ばす脆弱性。フィッシングに悪用 |
| 差し支えない場合 | 検証済み・自サイト内・明示的 UI |
| 外部ドメイン遷移 | 仕様としてあり得るが URL はサーバー管理 |
| URL 固定 | 最も安全 |
| 番号指定 | ID → URL マッピングで任意 URL を防ぐ |
| ドメイン名チェック | ホワイトリスト + bypass 対策 |

### HTTPヘッダインジェクション

| トピック | 要点 |
|---------|------|
| ヘッダインジェクション | 改行で追加ヘッダを注入 |
| 根本対策 | 外部入力をヘッダ値に使わない |
| 専用 API | リダイレクト・Cookie 生成を一元化 |
| 改行チェック | `\r` `\n` `\0` を拒否（両方実施） |

### 対策の優先順位

```
オープンリダイレクト:
  1. リダイレクト先 URL を固定（最優先）
  2. 番号指定でサーバー側マッピング
  3. どうしても URL 指定ならドメインホワイトリスト
  4. 外部遷移は UI で明示

HTTPヘッダインジェクション:
  1. 外部入力をヘッダに載せない
  2. 専用 API に集約 + 改行文字チェック（両方）
  3. 制御文字・URL デコード後の再検証
```
