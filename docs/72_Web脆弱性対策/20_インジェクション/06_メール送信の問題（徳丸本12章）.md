# 安全なWebアプリケーションの作り方（第12章）

お問い合わせフォームや会員登録の確認メールなど、Webアプリは **メール送信** をよく使います。第12章では、メール送信まわりで起きやすい脆弱性と対策を解説します。

---

## 📬 メール送信の問題の概要

メール送信機能には、主に次の問題があります。

| 問題 | 概要 |
|------|------|
| **メールヘッダ・インジェクション** | 外部入力で件名・送信元・宛先などを改変される |
| **Hidden パラメータによる宛先保持** | 画面に隠した宛先を改ざんされ、別の人へ送られる |
| **第三者中継（参考）** | メールサーバーが誰でも中継でき、スパムの踏み台になる |

### 日常生活での例え

- **正常なメール送信**: お問い合わせフォームから、運営宛にだけメールが届く
- **攻撃された場合**: フォームが悪用され、他人へ迷惑メールやウイルス付きメールが送られる

### なぜ危険か

メール送信機能は、アプリが **「メールを送る権限」** を持っています。攻撃者にその権限を乗っ取られると、次のような被害が出ます。

```
・迷惑メール（スパム）の送信に悪用される
・ウイルス付きメールの送信に悪用される
・なりすましメールでフィッシングに使われる
・自社ドメインの信頼が下がる（ブラックリスト入り）
```

---

## 💉 メールヘッダインジェクション

**メールヘッダインジェクション（Email Header Injection）** とは、フォームなどの **外部入力** に改行やヘッダ用の文字列を混ぜ込み、メールのヘッダを勝手に追加・改変する攻撃です。

### メールの構造（ざっくり）

メールは大きく **ヘッダ** と **本文** に分かれます。ヘッダは「誰から・誰へ・件名は何か」を表します。

```
To: support@example.com
From: user@example.com
Subject: お問い合わせ
Bcc: attacker@evil.com          ← 攻撃者が勝手に追加したい行

こんにちは、質問があります。   ← 本文
```

ヘッダの各行は **改行（`\r\n` や `\n`）** で区切られます。そのため、入力値に改行を入れると、**新しいヘッダ行を追加したように見える** ことがあります。

### 攻撃のイメージ

お問い合わせフォームで「メールアドレス」や「件名」をそのままヘッダに埋め込んでいる場合:

```
【正常な入力】
メールアドレス: user@example.com

【攻撃者の入力】
メールアドレス: user@example.com%0ABcc: victim@example.com
                ↑ %0A は改行（URLエンコード）
```

サーバー側でそのままヘッダに連結すると、次のように解釈されます。

```
To: support@example.com
From: user@example.com
Bcc: victim@example.com   ← 攻撃者が追加した宛先
Subject: お問い合わせ
```

### 何を改変されるか

| 改変対象 | 攻撃の例 |
|----------|----------|
| **件名（Subject）** | 迷惑な件名やフィッシング用の件名に差し替え |
| **送信元（From）** | 信頼できる差出人に見せかける |
| **宛先（To / Cc / Bcc）** | 第三者へ勝手にメールを送る |
| **本文** | ヘッダの後に本文を差し込み、ウイルスや詐欺文を送る |

### 悪用の典型例

| 悪用 | 説明 |
|------|------|
| **迷惑メールの送信** | 自社サーバーから大量のスパムを送らせる |
| **ウイルスメールの送信** | マルウェア付きメールの踏み台にする |
| **なりすまし** | 正規サイトからのメールに見せかけて詐欺 |

### 攻撃の流れ

```
1. 攻撃者がお問い合わせフォームを見つける
2. メールアドレス欄などに「改行 + Bcc: 被害者」を入力
3. アプリが入力値をそのままメールヘッダに埋め込む
4. メールサーバーが追加ヘッダを解釈して送信
5. 被害者に迷惑メール・ウイルスメールが届く
6. 送信元は正規サイトのサーバーに見える
```

## 🛡️ メールヘッダインジェクションの対策

対策の基本は **「外部入力をヘッダにそのまま載せない」** と **「改行を許さない」** です。

### 1. 外部からのパラメータをメールヘッダに含ませない

最も安全なのは、**ユーザー入力をヘッダに使わない** ことです。

| ヘッダ項目 | 推奨 |
|------------|------|
| **To（宛先）** | アプリ側で固定（例: `support@example.com`） |
| **From（送信元）** | アプリ側で固定（例: `noreply@example.com`） |
| **Subject（件名）** | 固定文、または許可した文言のみ |
| **本文** | ユーザー入力は本文側にだけ載せ、ヘッダとは分離 |

```
❌ 悪い例
  From: （ユーザーが入力したメールアドレス）
  Subject: （ユーザーが入力した件名）

✅ 良い例
  From: noreply@example.com（固定）
  Subject: 【お問い合わせ】受付完了（固定）
  本文: お名前・内容などユーザー入力を載せる
```

返信先が必要な場合は、`From` ではなく **`Reply-To`** に検証済みのアドレスを入れる、または本文にだけ書く方法が安全です。

### 2. 外部パラメータに改行を含めないようチェックする

ヘッダに載せる値がどうしても必要な場合は、**改行文字を拒否** します。

```php
// ✅ 改行が含まれていたらエラー
function hasNewline(string $value): bool
{
    return preg_match('/[\r\n]/', $value) === 1;
}

$email = $_POST['email'] ?? '';
$subject = $_POST['subject'] ?? '';

if (hasNewline($email) || hasNewline($subject)) {
    // 不正な入力として拒否
    exit('不正な入力です');
}
```

```
チェック対象の文字:
  \r  （キャリッジリターン）
  \n  （ラインフィード）
  \r\n（Windows 系の改行）
```

改行チェックは **最低限の防御** です。可能ならヘッダ自体に外部入力を使わない方が確実です。

### 3. メール送信には専用の API やライブラリを使う

昔の実装では、`mail()` にヘッダ文字列を自分で組み立てて渡すことが多く、インジェクションが起きやすいです。

```php
// ❌ 危険: ヘッダを文字列連結で組み立てている
$to = 'support@example.com';
$subject = $_POST['subject'];
$headers = "From: " . $_POST['email'] . "\r\n";
mail($to, $subject, $_POST['body'], $headers);
```

専用ライブラリや API を使うと、宛先・件名・本文を **別々の引数** で渡し、ライブラリ側がヘッダを安全に組み立てます。

| 手段 | 例 |
|------|-----|
| **言語のメールライブラリ** | PHPMailer、Swift Mailer / Symfony Mailer、Python の email パッケージ |
| **外部メール API** | SendGrid、Amazon SES、Mailgun など |

```php
// ✅ 良い例（イメージ）: 項目ごとにセットする
$mail = new PHPMailer();
$mail->setFrom('noreply@example.com');
$mail->addAddress('support@example.com');
$mail->Subject = '【お問い合わせ】受付完了';
$mail->Body = $safeBody;  // 本文のみユーザー入力を反映
$mail->send();
```

ポイントは、**ヘッダ文字列を自分で連結しない** ことです。

### 4. メールアドレスのチェック

宛先や返信先にメールアドレスを使う場合は、**形式チェック** を行います。

```php
// ✅ 形式チェックの例（PHP）
$email = $_POST['email'] ?? '';

if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
    exit('メールアドレスの形式が正しくありません');
}

// 念のため改行も拒否
if (preg_match('/[\r\n]/', $email)) {
    exit('不正な入力です');
}
```

| チェック内容 | 理由 |
|--------------|------|
| **形式が正しいか** | `user@example.com` のような形か確認 |
| **改行がないか** | ヘッダインジェクション防止 |
| **長さの上限** | 異常に長い入力の拒否 |
| **許可ドメイン（必要なら）** | 社内メールのみ受け付ける等 |

形式チェックだけでは不十分な場合もあるため、**ヘッダに載せない設計** と組み合わせます。

### 5. 件名のチェック

件名にユーザー入力を使う場合も、同様に検証します。

```php
$subject = $_POST['subject'] ?? '';

// 改行禁止
if (preg_match('/[\r\n]/', $subject)) {
    exit('不正な入力です');
}

// 長さ制限（例: 100文字まで）
if (mb_strlen($subject) > 100) {
    exit('件名が長すぎます');
}

// 可能なら固定件名にする方が安全
// $subject = '【お問い合わせ】受付完了';
```

| 方針 | 安全性 | 説明 |
|------|--------|------|
| **件名を固定する** | 最も安全 | ユーザー入力を件名に使わない |
| **許可リスト** | 安全 | 「質問」「要望」など選択肢のみ |
| **改行・長さチェック** | 最低限 | 自由入力を許す場合の防御 |

## 🙈 Hidden パラメータによる宛先保持

お問い合わせフォームなどで、宛先メールアドレスを **`<input type="hidden">`** に入れて送信する実装があります。これは **改ざんしやすい** ため危険です。

### 脆弱な実装

```html
<!-- ❌ 宛先が HTML に埋まっている -->
<form action="/contact" method="POST">
  <input type="hidden" name="to" value="support@example.com">
  <input type="text" name="name">
  <textarea name="body"></textarea>
  <button type="submit">送信</button>
</form>
```

攻撃者はブラウザの開発者ツールで `to` の値を書き換え、**任意の宛先** へメールを送らせられます。

```
1. ページの HTML を開く
2. hidden の value を attacker@evil.com に変更
3. フォームを送信
4. アプリが改ざんされた宛先へメール送信
```

### 対策

| 対策 | 説明 |
|------|------|
| **宛先はサーバー側で固定** | HTML やリクエストに宛先を載せない |
| **どうしても切り替えるならサーバー側の対応表** | `dept=sales` のような ID だけ受け取り、サーバーで `sales@example.com` に変換 |
| **セッションに保持** | 確認画面がある場合、宛先はセッションに置き、hidden に出さない |

```php
// ✅ 良い例: 宛先はサーバー側のみ
$to = 'support@example.com';

// ✅ 部署ごとに送る場合も、許可したキーだけ変換
$deptMap = [
    'sales' => 'sales@example.com',
    'support' => 'support@example.com',
];
$dept = $_POST['dept'] ?? 'support';
$to = $deptMap[$dept] ?? $deptMap['support'];
```

これは [[02_クッキー出力にまつわる脆弱性（徳丸本11章）|第11章]] の「クライアント側に重要な情報を置かない」と同じ考え方です。

## 📮 参考：メールサーバーによる第三者中継

**第三者中継（オープンリレー）** とは、メールサーバーが **認証なしで誰のメールでも中継** してしまう設定です。Webアプリ本体の脆弱性というより、**メールサーバーの設定不備** です。

### 何が起きるか

```
攻撃者 → 自社メールサーバー → 世界中の宛先へスパム送信
         （踏み台にされる）
```

| 影響 | 説明 |
|------|------|
| **スパムの踏み台** | 自社サーバーから大量の迷惑メールが送られる |
| **IP・ドメインの評判低下** | ブラックリストに入り、正規メールも届かなくなる |
| **帯域・リソースの浪費** | サーバー負荷が増える |

### 対策の要点

```
・外部からの無認証リレーを禁止する
・自アプリからの送信は認証付き（SMTP AUTH）や API 経由にする
・送信元 IP・レート制限を設ける
・可能なら SendGrid / SES 等の外部メールサービスを使う
```

Webアプリ側では「ヘッダインジェクション対策」と「宛先のサーバー側固定」を行い、メールサーバー側では「第三者中継を閉じる」ことがセットです。

---

## ✅ 対策まとめ

| 対策 | 内容 |
|------|------|
| **ヘッダに外部入力を載せない** | To / From / Subject は固定またはサーバー側で決定 |
| **改行チェック** | `\r` `\n` を含む入力は拒否 |
| **専用ライブラリ・API を使う** | ヘッダ文字列を自分で連結しない |
| **メールアドレス・件名の検証** | 形式・長さ・改行をチェック |
| **宛先を Hidden に置かない** | クライアント側の値を信じない |
| **第三者中継を禁止** | メールサーバー設定・外部サービス利用 |

### 実装のチェックリスト

```
□ 宛先（To）はサーバー側で固定している
□ From は自社の固定アドレスを使っている
□ 件名は固定、または改行・長さを検証している
□ ユーザー入力は本文にのみ反映している
□ mail() のヘッダ連結ではなく、ライブラリ / API を使っている
□ Hidden パラメータに宛先を入れていない
□ メールサーバーがオープンリレーになっていない
```

この章の要点は、**「メールのヘッダと宛先はアプリが決める。ユーザー入力は本文にだけ使う」** です。
