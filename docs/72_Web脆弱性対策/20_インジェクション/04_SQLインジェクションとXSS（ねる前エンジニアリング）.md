## 詳しい要約

**テーマ：SQLインジェクションとXSSは「データが命令として読まれる」同じ形の穴**

SQLインジェクションとXSS（クロスサイトスクリプティング）は、根っこが同じで、データのつもりで入れた文字が命令として解釈されてしまうことが原因。対策も共通で、データと命令の**境界で分ける**こと。「記号を消す」より「そもそも混ぜない」が基本。

---

### 実務でありそうな場面

- 管理画面の会員検索欄に記号を入れたら、名前と関係なく全員分のデータが出てきた
- 口コミのコメント欄に書かれたコメントを別の人が開いたら、中身がプログラムとして動き出した
- AIに検索処理を書かせたら、入力をそのまま文字列につないで命令を作っていた

### データと命令

- **データ**は読まれるだけのもの（名前やコメント）。中に何が書いてあっても本来は何も起きない
- **命令**は読み手がその通りに動くもの（「この人を探せ」「これを表示しろ」）
- どちらも**同じ文字でできている**ため、境目が曖昧になると取り違えが起きる

### SQLインジェクション

- プログラムは「名前がこれの人を探せ」というひな型の空いた部分に入力をはめ込む。名前は引用符で囲まれ、囲いの中がデータ
- 入力に `' OR 1=1` のような記号を入れると、先頭の引用符で囲いが閉じ、`OR 1=1` が囲いの外に出て**命令として読まれる**
- `1=1` は常に正しいので、全員分のデータが返る。ひな型は何も壊れていないのに、入力が境界を内側から越えてしまう
- 危ない書き方：ひな型の文字列と入力を**足し算でつなぐ**。つないだ瞬間にデータと命令の区別が消え、混ざった1本の文字列がDBに届く
- 安全な書き方：名前の場所に**プレースホルダ**（`?`、値の置き場所の印）を置き、値は命令とは**別の便**で渡す
  - 先に命令だけがDBに渡り、形が確定する。後から届いた値はどんな記号でもただの文字として扱われ、「該当なし」になる
  - 入力は命令の形を変えられない
- 「引用符を消せばよいのでは」→ 昔は危険な記号を無害な形に書き換える対策も使われたが、全部の危ない記号を自分で見つける前提で、1か所忘れたらそこから入られる。記号の書き方には思わぬ抜け道もある
- 命令と値を分ける方法は**仕組みで区別**する。コードを見て「つないでいるか」だけ確かめればよいので見つけやすい

### XSS

- 画面（HTML）も、段落の札などのひな型にコメントをはめ込んで作っている
- コメント欄に `<script>` の札で囲んだプログラムを書き込むと、ブラウザは尖った括弧を札（命令）として読み、中身がプログラムとして動く
- 動く場所は、そのコメントを**開いた別の人のブラウザ**。見た人がログインしていれば、その人の権限で動いてしまうことがある。**書いた人ではなく見た人が被害を受ける**
- 対策：HTMLにはめ込む直前に、入力を文字として表示する形に置き換える（`<` → `&lt;`）。これを**エスケープ**と呼ぶ。スクリプトという文字が画面に見えるだけで動かない
- 自分で探して書き換えるのではなく、Reactのような最近の部品は波括弧で表示すると**自動でエスケープ**してくれる
- 危ないのは自動の仕組みを外す書き方
  - `innerHTML`：中身をHTMLとして入れるので、札があれば命令として読まれる
  - Reactの `dangerouslySetInnerHTML`：名前で「危険」と警告している
- 安全な書き方：`textContent` は文字として入れる。Reactでは波括弧で出せば十分

### 2つを並べると

| | SQLインジェクション | XSS |
|---|---|---|
| 読み手 | データベース | 見た人のブラウザ |
| 化ける記号 | 引用符 | 尖った括弧 |
| 対策 | 値を別の便で渡す | 文字として表示する形に変える |
| 被害 | データを抜かれる・消される | 見た人の画面で勝手にプログラムが動く |

- 読み手が違うだけで、やっていることは同じ。どちらも**データと命令の境界ではっきり分ける**

### AIに書かせたとき見るところ

1. SQLやHTMLを入力とつないで作っていないか。足し算だけでなく、テンプレート文字列（バッククォート）の中に埋め込む書き方も同じ。動くけれど境界が消えていることがあり、動くから気づきにくい
2. `innerHTML` や `dangerously` で始まる書き方を使っていないか。使うなら本当にHTMLとして入れる必要があるのか理由を聞く
3. 「入力をチェックしたから安全」で済ませていないか。チェックは大事だが、それだけに頼ると1か所の漏れで終わり。チェックしたうえで境界でも分ける**二重の守り**が基本（チェックは入口、分けるのは最後の砦）
4. 便利な部品（DBを楽に扱う部品など）の抜け道を使っていないか。生のSQLを書ける機能で値をつないでいたら、部品を使っていても同じ穴が開く

### まとめ

- 原因は、データのつもりの文字が命令として読まれること（入力がデータと命令の境界を越える）
- SQLインジェクションの読み手はDB、XSSの読み手はコメントを見た人のブラウザ
- 対策は境界で分けること。SQLは値を別の便で、HTMLは文字として表示する形に。**消すより混ぜない**
- 攻撃手法のカタログは覚えなくてよい。境界がどこにあるかを見れば新しい手口にも対応できる
