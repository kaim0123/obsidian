# 安全なWebアプリケーションの作り方（第6章）

[[01_XSS基本編（徳丸本5章）|第5章]] では XSS の基礎と HTML 要素内容へのエスケープを学びました。第6章では **出力コンテキストごとの XSS** と、JavaScript へデータを安全に渡す方法、エラー表示の注意点を解説します。

---

## 🛡️ HTMLエスケープの概要

**HTMLエスケープ** は、特殊文字を HTML として解釈されない形式に変換する処理です。第5章でも触れましたが、発展編では **「どこに出力するか（コンテキスト）」** によって必要な対策が変わる点が重要です。

### エスケープ対象の文字（おさらい）

| 文字 | エスケープ後 | 理由 |
|------|------------|------|
| `<` | `&lt;` | タグ開始の防止 |
| `>` | `&gt;` | タグ終了の防止 |
| `"` | `&quot;` | 属性値からの脱出防止 |
| `'` | `&#x27;` | 属性値からの脱出防止 |
| `&` | `&amp;` | 実体参照の防止 |

### コンテキスト別エスケープの原則

```
同じユーザー入力でも、出力場所によって必要なエスケープが異なる

HTML本文     → HTMLエスケープ
HTML属性     → HTML属性エスケープ + 引用符で囲む
URL（href等） → URLエンコード + スキーム検証
JavaScript   → JSエスケープ / JSON による安全な受け渡し
```

**重要:** HTMLエスケープだけでは **href 属性や JavaScript 内** の XSS を防げない場合があります。以降の各節でコンテキストごとの対策を学びます。

## 🔗 href属性やsrc属性のXSS

`<a href="...">` や `<img src="...">` など、**URL を受け取る属性** にユーザー入力を出力すると、HTMLエスケープだけでは不十分なことがあります。

### 典型的な脆弱なコード

```html
<!-- ❌ 脆弱：href にユーザー入力をそのまま出力 -->
<a href="<?= $url ?>">リンク</a>

<!-- 攻撃入力: javascript:alert(document.cookie) -->
<a href="javascript:alert(document.cookie)">リンク</a>
```

```html
<!-- ❌ 脆弱：src にユーザー入力 -->
<img src="<?= $imageUrl ?>">

<!-- 攻撃入力: javascript:alert(1) や onerror イベントを利用したペイロード -->
```

### なぜ HTMLエスケープだけでは足りないか

| 問題 | 説明 |
|------|------|
| **`javascript:` スキーム** | URL として解釈され、クリックでスクリプトが実行される |
| **`data:` スキーム** | Base64 エンコードされた HTML/JS を埋め込める |
| **属性からの脱出** | エスケープ漏れで `"` により属性を閉じ、イベントハンドラを注入 |

### 対策の要点

1. **URL として妥当か検証** する
2. **許可するスキームを限定** する（`http:` / `https:` のみ等）
3. **HTML属性エスケープ** も併用する
4. 可能なら **サーバー側で URL を組み立て**、ユーザー入力はパスやクエリの一部だけに限定

## 🌐 URLを生成する場合の対策

ユーザー入力から URL を動的に生成する場合、次の手順で安全に処理します。

### 安全な URL 生成の手順

```
1. ユーザー入力を URL の「部品」として扱う（URL 全体を信頼しない）
2. スキーム（http/https）をサーバー側で固定
3. パス・クエリ値は URL エンコードする
4. 完成した URL を属性に出力するときは HTML 属性エスケープ
```

### 例：検索結果へのリンク

```php
// ❌ 脆弱：URL 全体をユーザー入力から構成
$url = $_GET['redirect'];
echo '<a href="' . htmlspecialchars($url) . '">移動</a>';
// javascript: スキームを htmlspecialchars しても href として実行される

// ✅ 安全：スキームとホストは固定、パスのみユーザー入力
$path = $_GET['path'];
$safePath = '/' . ltrim(rawurlencode($path), '/');
echo '<a href="https://example.com' . htmlspecialchars($safePath, ENT_QUOTES, 'UTF-8') . '">移動</a>';
```

```javascript
// ✅ JavaScript でクエリパラメータを安全に付加
const keyword = encodeURIComponent(userInput);
const url = `https://example.com/search?q=${keyword}`;
```

### 許可するスキーム

| スキーム | 用途 | ユーザー入力への許可 |
|---------|------|-------------------|
| `https:` | 通常のリンク | ✅（検証後） |
| `http:` | 非暗号化リンク | △（本番では https 推奨） |
| `javascript:` | スクリプト実行 | ❌ **禁止** |
| `data:` | 埋め込みデータ | ❌ **原則禁止** |
| `vbscript:` | 旧IE向け | ❌ **禁止** |

## 🏠 リンク先のドメイン名のチェック

リダイレクト機能や「外部リンク」機能では、**リンク先のドメインを検証** しないとフィッシングや XSS の入口になります。

### 危険なパターン：オープンリダイレクト

```php
// ❌ 脆弱：任意 URL へリダイレクト
header('Location: ' . $_GET['url']);
// 攻撃者が ?url=https://evil.com/phishing 等を仕込める
```

### ドメイン名チェックの方法

**ホワイトリスト方式（推奨）**

```php
$allowedHosts = ['example.com', 'www.example.com', 'api.example.com'];
$url = parse_url($_GET['url']);

if (!in_array($url['host'], $allowedHosts, true)) {
    die('許可されていないリンク先です');
}
header('Location: ' . $url);
```

```javascript
function isAllowedUrl(url) {
  try {
    const parsed = new URL(url);
    const allowed = ['example.com', 'www.example.com'];
    return allowed.includes(parsed.hostname)
      && (parsed.protocol === 'https:' || parsed.protocol === 'http:');
  } catch {
    return false;
  }
}
```

### チェックのポイント

| 項目 | 注意 |
|------|------|
| **ホスト名** | `evil.com` と `example.com.evil.com` を区別 |
| **スキーム** | `javascript:` や `data:` を拒否 |
| **相対 URL** | `//evil.com`（プロトコル相対）も検証対象 |
| **IDN（国際化ドメイン）** | 見た目似たドメイン（同形異義字）への注意 |

### 相対 URL の扱い

```html
<!-- 攻撃入力: //evil.com/phishing -->
<a href="//evil.com/phishing">クリック</a>
<!-- 現在のスキーム（https）が付き、https://evil.com へ誘導 -->
```

**対策:** 外部リンクには **絶対 URL のみ許可** し、ドメインをホワイトリストで検証する。

## ⚡ イベントハンドラのXSS

**イベントハンドラ属性**（`onclick`、`onerror`、`onmouseover` 等）にユーザー入力が入ると、HTMLエスケープをすり抜けて XSS が成立することがあります。

### 典型的な攻撃

```html
<!-- ❌ 脆弱 -->
<img src="invalid" onerror="<?= $userInput ?>">

<!-- 攻撃入力: alert(document.cookie)// -->
<img src="invalid" onerror="alert(document.cookie)//">
```

```html
<!-- ❌ 属性値からの脱出 -->
<div title="<?= $input ?>">テキスト</div>

<!-- 攻撃入力: " onmouseover="alert(1)" x=" -->
<div title="" onmouseover="alert(1)" x="">テキスト</div>
```

### イベントハンドラを使ったペイロード例

| 属性 | 例 |
|------|-----|
| `onerror` | `<img src=x onerror=alert(1)>` |
| `onmouseover` | `" onmouseover="alert(1)` |
| `onclick` | `<a href="#" onclick="alert(1)">` |
| `onload` | `<body onload=alert(1)>` |

### 対策

| 対策 | 説明 |
|------|------|
| **イベントハンドラ属性を使わない** | JavaScript は外部ファイルまたは `<script>` で `addEventListener` を使う |
| **HTML属性エスケープ** | `"` `'` `<` `>` `&` をエスケープ |
| **引用符で属性値を囲む** | 囲まないと脱出しやすい |
| **CSP** | `script-src` でインラインスクリプトを制限 |

```html
<!-- ✅ 安全：イベントハンドラ属性を使わず JS で绑定 -->
<img id="avatar" src="<?= htmlspecialchars($url, ENT_QUOTES, 'UTF-8') ?>">
<script>
  document.getElementById('avatar').addEventListener('error', handleError);
</script>
```

## 📜 Script要素のXSS

`<script>` タグの **中身** や **src 属性** にユーザー入力を含めると、最も危険な XSS になります。

### script 要素内への直接埋め込み

```html
<!-- ❌ 非常に危険 -->
<script>
  var username = '<?= $name ?>';
</script>

<!-- 攻撃入力: '; alert(document.cookie); // -->
<script>
  var username = ''; alert(document.cookie); //';
</script>
```

**HTMLエスケープは `<script>` 内では機能しない** 場合があります（ブラウザは script 内容を HTML としてパースしないため）。

### script の src 属性

```html
<!-- ❌ 脆弱：src にユーザー入力 -->
<script src="<?= $scriptUrl ?>"></script>

<!-- 攻撃者が悪意ある JS ファイルの URL を指定 -->
```

### 対策

| 対策 | 説明 |
|------|------|
| **ユーザー入力を script 内に埋め込まない** | 原則として禁止 |
| **外部 JS ファイルを使う** | ロジックは `.js` ファイルに分離 |
| **src は固定または検証済み URL のみ** | ホワイトリスト |
| **CSP** | 信頼できるソースのみ script 実行を許可 |

## 🔤 JavaScriptの文字列リテラルの動的生成の対策

サーバー側で JavaScript の **文字列リテラルを動的生成** するのは XSS の温床です。どうしてもデータを JS に渡す必要がある場合の安全な方法を学びます。

### 危険なパターン

```javascript
// ❌ サーバーが JS コードを文字列連結で生成
var msg = '<?= $message ?>';
eval('showMessage("' + userInput + '")');
```

```php
// ❌ エスケープ漏れ1文字で突破される
echo "<script>var data = '" . addslashes($input) . "';</script>";
// addslashes だけでは Unicode や改行等で不十分な場合がある
```

### なぜ HTMLエスケープや addslashes だけでは不十分か

| 手法 | 限界 |
|------|------|
| HTMLエスケープ | `<script>` 内では期待通り効かない |
| `addslashes` | JS の文脈を完全にはカバーしない |
| ブラックリスト | 新しい回避手法が次々と登場 |

### 安全な代替手段

1. **Script 要素の外部でパラメータを定義**（次節）
2. **インライン JSON による方法**（その次の節）
3. **API で JSON を取得**（fetch 等）

---

## 📦 Script要素の外部でパラメータを定義してJavaScriptから参照する方法

`<script>` タグの **外** にデータを置き、JavaScript から読み取る方法です。JS 文字列リテラルへの直接埋め込みを避けられます。

### 方法1：data 属性を使う

```html
<!-- ✅ 安全：data 属性に HTML エスケープして出力 -->
<div id="user-data"
     data-username="<?= htmlspecialchars($username, ENT_QUOTES, 'UTF-8') ?>"
     data-email="<?= htmlspecialchars($email, ENT_QUOTES, 'UTF-8') ?>">
</div>

<script>
  const el = document.getElementById('user-data');
  const username = el.dataset.username;  // エスケープ済みの文字列として取得
  const email = el.dataset.email;
</script>
```

### 方法2：hidden の input 要素

```html
<input type="hidden" id="csrf-token"
       value="<?= htmlspecialchars($token, ENT_QUOTES, 'UTF-8') ?>">

<script>
  const token = document.getElementById('csrf-token').value;
</script>
```

### 方法3：meta 要素

```html
<meta name="csrf-token" content="<?= htmlspecialchars($token, ENT_QUOTES, 'UTF-8') ?>">
```

### ポイント

| ポイント | 説明 |
|---------|------|
| **HTML属性エスケープ** | `ENT_QUOTES` で `"` `'` をエスケープ |
| **引用符で囲む** | 属性値は必ず `"` または `'` で囲む |
| **JS 側では DOM API で取得** | 文字列連結で JS コードを生成しない |

## 📋 インラインJSONによる方法

**インライン JSON** とは、`<script type="application/json">` 等を使い、構造化データを **JSON 形式** でページに埋め込む方法です。JavaScript から `JSON.parse` で安全に読み取れます。

※ 原文の「インラインJSONP」は **インライン JSON** の意味で使われることが多いです。JSONP（`<script src="...?callback=...">`）は別の仕組みで、XSS リスクも異なります。

### 基本的な書き方

```html
<!-- ✅ 安全：JSON として埋め込み（実行されない） -->
<script type="application/json" id="app-data">
<?= json_encode($data, JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT) ?>
</script>

<script>
  const jsonText = document.getElementById('app-data').textContent;
  const data = JSON.parse(jsonText);
  console.log(data.username);
</script>
```

```php
// PHP での json_encode 例
$data = ['username' => $username, 'count' => 42];
$json = json_encode($data, JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT);
echo '<script type="application/json" id="app-data">' . $json . '</script>';
```

### JSON_HEX フラグの意味

| フラグ | 効果 |
|--------|------|
| `JSON_HEX_TAG` | `<` `>` を `\u003C` 等に変換（`</script>` 突破防止） |
| `JSON_HEX_AMP` | `&` をエスケープ |
| `JSON_HEX_APOS` | `'` をエスケープ |
| `JSON_HEX_QUOT` | `"` をエスケープ |

### なぜ安全か

```
1. type="application/json" → ブラウザは JavaScript として実行しない
2. json_encode → JS の文法を壊す文字をエスケープ
3. JSON.parse → 文字列として正しく復元
```

### JSONP との違い（注意）

| | インライン JSON | JSONP |
|---|---------------|-------|
| **目的** | 同一ページ内でデータを渡す | クロスオリジンでデータ取得 |
| **形式** | `<script type="application/json">` | `<script src="api?callback=fn">` |
| **XSS リスク** | エンコードすれば低い | callback 名の注入等に注意 |
| **現状** | ✅ 推奨 | △ レガシー（CORS が主流） |

## 🚨 エラーメッセージからの情報漏洩

XSS 対策と並んで、**エラーメッセージの出力** も表示処理の重要な問題です。詳細すぎるエラーは **情報漏洩** につながり、攻撃の手がかりを与えます。

### 漏洩しやすい情報

| 情報 | 攻撃者へのメリット |
|------|------------------|
| **スタックトレース** | ファイルパス、行番号、使用ライブラリが分かる |
| **SQLエラーメッセージ** | テーブル名、カラム名、DB の種類 |
| **OS / ミドルウェアのバージョン** | 既知脆弱性の exploit に利用 |
| **内部 IP アドレス** | ネットワーク構成の推測 |
| **ユーザー入力のそのまま表示** | 反射型 XSS の原因にもなる |

### 危険な例

```php
// ❌ 脆弱：DB エラーをそのまま表示
try {
    $db->query($sql);
} catch (PDOException $e) {
    echo 'エラー: ' . $e->getMessage();
    // → "Table 'users' doesn't exist" 等が漏洩
}
```

```php
// ❌ 脆弱：ユーザー入力をエラーメッセージに含める
echo '「' . $_GET['name'] . '」は見つかりませんでした';
// → 反射型 XSS: name=<script>alert(1)</script>
```

### 安全なエラーハンドリング

```php
// ✅ ユーザーには汎用メッセージのみ
try {
    $db->query($sql);
} catch (PDOException $e) {
    error_log($e->getMessage());  // サーバーログに詳細を記録
    echo '処理中にエラーが発生しました。しばらくしてからお試しください。';
}
```

```php
// ✅ ユーザー入力をエラーに含める場合もエスケープ
$name = htmlspecialchars($_GET['name'], ENT_QUOTES, 'UTF-8');
echo '「' . $name . '」は見つかりませんでした';
```

### ベストプラクティス

| 項目 | 推奨 |
|------|------|
| **本番環境** | 詳細エラーを画面に表示しない |
| **ログ** | 詳細はサーバー側ログに記録 |
| **エラー ID** | ユーザーには「エラーID: ABC123」のみ表示し、サポート時に照合 |
| **デバッグモード** | 開発環境のみ詳細表示を有効化 |
| **カスタムエラーページ** | 500 エラー用の汎用ページを用意 |

### XSS との関連

```
エラーメッセージにユーザー入力をそのまま含める
  → 反射型 XSS の典型パターン

「〇〇が見つかりません」等のメッセージ
  → 必ず HTML エスケープしてから出力
```

## 📝 まとめ

| トピック | 要点 |
|---------|------|
| HTMLエスケープ | コンテキスト（本文・属性・URL・JS）ごとに方法が異なる |
| href / src 属性 | `javascript:` 等の危険スキームを拒否、URL を検証 |
| URL 生成 | スキーム固定 + URLエンコード + 属性エスケープ |
| ドメイン名チェック | ホワイトリストでリンク先を限定 |
| イベントハンドラ | 属性での onclick 等を避け、addEventListener を使う |
| Script 要素 | ユーザー入力を script 内に埋め込まない |
| JS 文字列リテラル | 動的生成を避け、JSON や data 属性で渡す |
| 外部パラメータ定義 | data 属性 / hidden input / meta で安全に渡す |
| インライン JSON | `type="application/json"` + json_encode + JSON.parse |
| エラーメッセージ | 詳細を隠し、ユーザー入力はエスケープ |

### コンテキスト別対策一覧

```
出力コンテキスト          対策
─────────────────────────────────────────
HTML 本文                HTMLエスケープ
HTML 属性値              属性エスケープ + 引用符
href / src（URL）        スキーム検証 + URLエンコード
イベントハンドラ属性      使用を避ける + CSP
<script> 内              埋め込まない → JSON / data 属性
JavaScript 文字列         json_encode / JSON.parse
エラーメッセージ          汎用文言 + エスケープ + ログ記録
```
