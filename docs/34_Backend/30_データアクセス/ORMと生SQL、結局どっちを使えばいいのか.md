## 詳しい要約

**テーマ：ORM と生 SQL は対立ではなく使い分け**

「ORM 派か生 SQL 派か」という論争に対し、結論は「どっちか」ではなく「両方」が正解。基本的な CRUD は ORM、複雑なクエリやパフォーマンスが重要な箇所は生 SQL で書き、ORM を使うにしても SQL は必ず理解しておくべきだと説く。

---

### 第1章 ORM とは何か

- ORM（Object-Relational Mapping）は `User.save` のようなコードから裏で INSERT 文を生成・実行してくれる。
- ORM は **「翻訳機」**。元の言語（SQL）を知らないと **誤訳に気づけない**（Google 翻訳だけで海外旅行するようなもの）。
- 代表例：Ruby の ActiveRecord、Python の SQLAlchemy・Django ORM、JavaScript の Prisma、Java の Hibernate。

### 第2章 ORM の落とし穴

- **N+1 問題**：記事 100 件を取得し、ループで各記事の著者を取得すると合計 101 回のクエリが発行される。JOIN なら 1 回で済む。
- ORM は「優秀な通訳者」ではなく、言われたことをそのまま訳すだけで勝手に最適化はしない。
- **不要なカラムの取得**：ORM はデフォルトで全カラム（`SELECT *`）を取ることが多く、カラムが多いと無駄なデータ転送になる。

### 第3章 生 SQL のメリットとデメリット

| | 内容 |
|---|---|
| メリット | JOIN やインデックスの使い方などパフォーマンスを完全にコントロールできる。サブクエリ・ウィンドウ関数・再帰 CTE など高度な SQL は生で書く方が楽 |
| デメリット | CRUD を全部手書きすると開発速度が落ちる。文字列で書くためタイプミスに実行時まで気づけない |

- モダンな ORM（Prisma など）は存在しないカラムへのアクセスを **コンパイル時にエラー** にでき、DB ごとの構文差（PostgreSQL と MySQL など）も吸収してくれる。

### 第4章 使い分けの実践

- 基本の CRUD（`User.create`、`User.find` など）は ORM で書き、型安全などの恩恵を受ける。
- ダッシュボードの複雑な集計（前年比付きの売上など）や、N+1 を直すための JOIN 手書き・必要カラムだけの取得は生 SQL。
- ほとんどの ORM は生 SQL を実行できる（ActiveRecord の `find_by_sql`、Prisma の `$queryRaw` など）。ORM にも eager load / includes といった N+1 対策はあるが、複雑なケースでは限界がある。

### 第5章 エンジニアとしての心構え

- ORM を使っていても SQL は覚えるべき。パフォーマンス問題や ORM で表現できないクエリが必要な場面で詰む。
- 逆に生 SQL しか書けないと、開発速度で負けたりチームの生産性を下げたりする。
- まずは **ORM が生成する SQL をログに出して眺める** ところから始めると、N+1 にもすぐ気づける。

### まとめ

- ORM も SQL も道具。ノコギリとカンナのように状況で使い分ける。
- CRUD は ORM、複雑なクエリ・性能が重要な箇所は生 SQL。
- ORM を使う人ほど SQL を理解し、生成 SQL を確認する習慣を持つ。
