## 詳しい要約

**テーマ：N+1 問題の本質は「境界を越える I/O が N に比例して増える」こと**

N+1 問題は、最初の 1 回で N 件を取得した後、ループ内で関連情報を 1 件ずつ取りに行き外部 I/O が N 回増える構造である。ORM に限らず GraphQL・HTTP・RPC でも起きる。対策の軸は「境界を越える取得を集合で表現し、所有者の内側でまとめる」ことだ、というのが結論。

---

### なぜ N 回増えるのか

- 問題はループそのものではなく、**N に比例して DB やネットワークの境界を越える取得計画**。
- 直列に呼ぶと往復時間が積み上がる。並列化して待ち時間を縮めても、下流へのコールは N 回のままで、**一斉負荷と失敗点**が残る（例：商品一覧から商品ごとに在庫 API を呼ぶ）。

### DB での対策

- 親一覧と関連データを取る処理では、**ORM の遅延ロード（lazy load）**が親ごとに関連の SELECT を走らせて N+1 を生みやすい。
- 解決策：必要な関連を先に決めて **JOIN** で取る、または親 ID を集めて **SELECT … IN** で一括取得する。
- ただし無条件の JOIN は結果行や SQL を膨らませる。**クエリ本数・結果サイズ・ページネーション**を測って選ぶ。

### マイクロサービスでの対策

- データが複数サービスに分かれ API/RPC で取る構成では、DB 内の工夫だけでは解けない。ID ごとに所有サービスを呼ぶとネットワークコールが N 回になる。
- 他サービスの DB を直接読むと**所有境界**を壊すので NG。
- 同じ所有者なら **BatchGet** を設計する（最大件数・順序・部分失敗の扱いを決める）。
- 複数の所有者にまたがるなら **BFF や集約サービス**で呼び出しをまとめる。

### バッチ・キャッシュ・read model の使い分け

| 手段 | 役割 |
|---|---|
| バッチング | 同時期のキーをまとめる |
| リクエスト単位キャッシュ | 1 リクエスト内の重複を省く |
| 共有キャッシュ | リクエストをまたいで再利用 |
| read model | 読み取り用の形を先に作っておく |

- 共有キャッシュや事前集約はデータが古くなりうるので、**必要な鮮度と整合性**から選ぶ。仕組みを混同しないこと。

### 比例増加を観測する

- テストデータが少ないと、N が小さい間は普通のループに見えて本番規模の比例増加を見落とす。
- **入力件数と I/O 回数を一緒に観測**する：DB なら同じ SQL の呼び出し数・時間・行数、分散系なら同じ下流スパンを見る。データを 1 件・10 件・100 件と増やしてコール数が比例するか確かめる。

### まとめ：4 つの問いで対処を選ぶ

1. 必要なキーを先に集められるか
2. データの所有者へ集合で問えるか
3. 鮮度と整合性はどこまで必要か
4. 失敗時に全体を止めるか、部分結果を返すか

- 答えに応じてバッチ・キャッシュ・read model を選び、入力件数を増やして I/O 回数・時間・データ量が比例していないかを観測する。
