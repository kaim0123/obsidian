## 詳しい要約

**テーマ：N+1 問題 ― 遅さの正体は DB との往復回数**

一覧画面で投稿を 1 本の SQL で取り、ループ内で 1 件ずつ関連データを取りに行くと、件数 N に応じて N 本の SQL が追加で飛ぶ（N+1 問題）。遅さの原因は DB の計算ではなく往復の回数であり、「まとめて取る」ことで件数に関係なく本数を一定にできる。判断はコードの見た目ではなく、実際に飛んだ SQL の本数で行う。

---

### よくある場面

- 手元では一覧画面がさっと出るのに、本番に出すと遅い。
- 最初は速かったのに、データが増えるほどじわじわ遅くなる。
- コードレビューで「ここ N+1 になってない？」と言われる。
- 3 つとも根っこは同じで、**データベースとの往復の回数** が原因。

### 1 本のつもりが 11 本

- ORM は SQL を代わりに書いてくれる「翻訳係」。
- 投稿を 10 件取り（1 本目）、ループで各投稿の書いた人の名前を出すと、名前は別の表にあるため「ユーザーの 1 番をください」「2 番をください」…と 1 件ずつ SQL が飛ぶ。
- 合計 1 + 10 = 11 本。件数を N とすると **N+1 本**。ログには番号だけ違う同じ形の SQL がずらっと並ぶ。
- コード上は 1 行しか書いていないのに、見た目と飛ぶ本数が一致しないのが怖いところ。

### なぜ 1 件ずつ取りに行くのか

- ORM は投稿を取った時点では、後で名前が必要になるかを知らない。いらないかもしれないものを先に取るのは無駄なので、使う瞬間に取りに行く（**遅延読み込み**、lazy loading）。
- 1 件だけなら必要な分しか取らない賢いやり方だが、ループの中では 1 件ずつの判断が件数分繰り返される。
- **ORM はループ全体を見渡してまとめようとはしない。まとめる判断は人の仕事**（今夜一番持ち帰ってほしい点）。

### 遅さの正体は往復の回数

- 仮に 1 往復 2 ミリ秒なら、10 件で 22 ミリ秒（誰も気づかない）、100 件で約 0.2 秒、1000 件で約 2 秒（画面が固まったと感じる）。
- この時間は DB の重い計算ではなく、ほとんどが行って帰ってくる移動の時間。1 回 1 回は軽いのに回数で積もる。
- 例え: スーパーで卵を 1 個ずつレジに通して毎回棚に戻るようなもの。1 パックで買えばよい。
- DB はみんなで使う場所なので、大量の問い合わせは他の人の問い合わせも待たせる。

### 手元では気づけない理由

| | 手元 | 本番 |
|---|---|---|
| データ量 | 試しに入れた 10 件ほど | 数万件もある |
| DB の場所 | 同じパソコンの中 | 別マシン、ネットワーク越し |
| 1 往復の重さ | ほぼ 0 | 往復ごとに待ちが積もる |

- 量と 1 回の重さが掛け算で効く。「手元で速いから大丈夫」とは言えず、本数を数える習慣が大事。

### 直し方：まとめて取る

- 1 本目で投稿 10 件を取り、書いた人の番号を集めて、2 本目で「この 10 人をまとめて」と頼む（**IN** 句に番号の一覧を渡す＝名簿ごと渡す）。合計 2 本で、投稿が 1000 件になっても 2 本のまま。
- もう 1 つの方法は、2 つの表を 1 本の SQL の中で **JOIN**（つなげて取る）すること。これなら 1 本。どちらもよく使われ、ORM が選んでくれることも多い。
- Ruby の Active Record（字幕では「Aはベイズ」と聞こえる）の例: 直した後は 2 行目に **includes** を一言足すだけで、「書いた人も最初にまとめて取っておいて」という指示になる。名前を出す 4 行目はそのままで、手元に取ってあるものを使うだけになり、本数は 11 → 2。
- 他の言語の ORM にも同じ役目の書き方があり、名前が違うだけ。

### もう 1 つの例：いいね数

- 投稿一覧にそれぞれのいいね数を出すと、投稿ごとに「いいねを数えて」が 1 件ずつ飛ぶ。名前か数かの違いだけで同じ N+1。
- 画面の部品や記事を組み立てる部品の中に隠れていることが多く、部品を開かないとループ内で呼ばれていると気づかない。だから **コードを読むより飛んだ本数を見る方が確実**。
- 直し方: 投稿の番号を集め、2 本目で **GROUP BY** を使って投稿ごとにまとめて数えてもらう（合計 2 本）。
- 別の手として、いいね数を投稿の表に持っておき、押されるたびに 1 増やす方法もある（数がずれないよう注意が必要。詳細は別の回）。

### 見つけ方

1. ログで 1 画面を出すのに SQL が何本飛んだかを見る（流れる SQL を眺める癖をつける）。
2. 番号だけ違う同じ形の SQL が並んでいたらまず疑う。
3. テストで SQL の本数に上限をかける（例: この画面は 5 本まで、超えたらテストを落とす）。
4. 検出ツールに知らせてもらう（Rails なら Bullet が知られており、見つけると警告を出す）。

### まとめすぎの落とし穴

- 念のため何でもまとめて取ると、使わないデータまで運ぶ。往復は減っても荷物が重くなるので、その画面で使うものだけまとめる。
- 一覧が 10 万件あれば名簿も 10 万件分になる。そもそも 1 度に出す件数をページに分けて減らすのが先。
- 表を JOIN するとき、1 件の投稿に 100 個の関連があれば結果は 100 行に増える。つなげ方によっては運ぶ量が膨らむ。
- 迷ったら、本数とかかった時間を直す前後で測って比べる。

### AI にコードを書かせたときに見る点

1. ループの中でデータを取りに行っていないか（投稿ごとに書いた人やいいね数を触っていたら疑う）。
2. テストが通っても本数は別に確かめる（テストデータは少数なので N+1 でも速く通る）。
3. 頼むときに「件数が増えても SQL の本数が増えないように」と条件を書いておく。
4. 直させたら、「直しました」という説明ではなく、直す前後のログの本数で確かめる。

### まとめ

- N+1 は一覧を取る 1 本に、1 件ずつの N 本がついてくること。
- 遅さの正体は DB の計算ではなく往復の回数。
- 直し方はまとめて取る（名簿を渡す IN か、表をつなげる JOIN）。件数が増えても本数が増えない形にする。ただし運ぶ量は増やしすぎない。
- コードの見た目ではなく実際に飛んだ本数で判断する。ORM ごとの書き方の違いは覚えなくてよい。
