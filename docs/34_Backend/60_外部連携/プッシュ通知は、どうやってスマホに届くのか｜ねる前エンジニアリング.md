## 詳しい要約

**テーマ：プッシュ通知の通り道 — サーバー → OSの配達所 → スマホ**

プッシュ通知は、アプリのサーバーがスマホへ直接送るのではなく、OS の配達所に「この宛先（トークン）へ」と頼み、配達所が届ける仕組み。配達所の「受け付けました」は「届いた」ではないため届く保証はなく、遅れる・まとめられる・宛先が古いと捨てられる。だから**通知は「何か来たよ」の呼び鈴にとどめ、本当の中身はアプリを開いたときにサーバーから取り直す**、という回。

---

### よくある問い合わせ

- サーバーの記録では送っているのに「通知が来ない」
- 同じ通知が2回鳴った
- アプリを消した人にずっと送り続けていた
- 通知を押して開いたら、もう古い内容だった

### サーバーはスマホに直接話しかけられない

- スマホは回線の奥にいて、外から呼び出せる住所を持たない。アプリは閉じ、画面も消えて眠っている
- アプリが自分で1分ごとに聞きに行くと電池と通信を使い続け、アプリが100個なら100個が聞きに行くことになる
- そこで **OS が窓口を1つにまとめた＝OSの配達所**（iPhone と Android でそれぞれある）。スマホは配達所とだけ細い線を1本つなぎっぱなしにし、どのアプリの通知もこの1本で届くので電池が持つ

### 宛先（トークン）をもらって名簿に書く

- 配達所は「A さん」という名前を知らず、知っているのは**スマホとアプリの組**だけ
- アプリは起動時に OS から、そのスマホのそのアプリ専用の長い文字列＝**トークン**をもらい、自分のサーバーへ送る。サーバーはそれを名簿に書く
- サーバーはスマホの場所を知らなくてよく、宛先さえ持っていればよい
- トークンは**アプリの入れ直しや機種変更で変わることがある**。だからアプリは**起動のたびに宛先を確かめ、変わっていたら送り直す**

### サーバー → 配達所 → スマホ

- サーバーは名簿から宛先を引き、配達所に「この宛先にこの文を届けて」と頼む。配達所はすぐ「受け付けました」と返す
- **「受け付けた」と「届いた」は違う**。宅配の荷物を窓口に出しただけの状態
- 配達所はつなぎっぱなしの線でスマホに流し、**OS が**通知を表示して鳴らす。アプリは起こさなくてよいので閉じていても届く
- サーバーが知っているのは配達所に渡したところまで。「送ったのに来ない」はこの先で起きている

### サーバー側のコードの流れ

1. 誰に何を知らせるかを受け取る
2. その人の宛先を名簿から**全部**取り出す（スマホとタブレットなら2つ）
3. 宛先ごとに配達所へ頼む
4. 成功したら「**受け付けた**」と記録する（「届いた」と書かず、記録の言葉を事実に合わせる）
5. 配達所が「この宛先はもうない」と返したら**名簿から消す**
6. それ以外の失敗は記録に残す

### 圏外のあいだの通知

- 地下鉄で圏外の B さんへの通知は、配達所が預かって圏内に戻ったら届ける
- ただし続けて2通・3通来ると、全部預かるとは限らず、**古いものを捨てて最新の1通にまとめる**ことがある → 3回送ったのに1回しか鳴らない
- 通知は届かないこともある前提で作る。アプリを開いたらサーバーに「新しいものは？」と聞き直す。**本当の中身はサーバーにあり、通知は呼び鈴**

### アプリを消した人の宛先

- アプリを消すと配達所側では宛先がなくなるが、サーバーの名簿には残っている
- 送ると配達所が「この宛先はもうありません」と返すので、そこで**名簿から消す**
- 消さないと、同じ失敗が何万人分も積もり、送る時間が無駄になり、本当の故障が失敗記録に埋もれる。失敗ばかり送り続けると配達所によっては送る側を疑うこともある
- 入れ直した人の新しい宛先は起動時にすぐ書く。**名簿をいつも生きた状態に保つ**のも品質の一部

### 同じ通知が2回鳴る

- 配達所は受け付けて実際に鳴ったが、「受け付けました」の返事が通信の乱れでサーバーに戻らない → サーバーは失敗と見て送り直し → 2回鳴る
- 返事が来ないとき相手が受け取ったかは分からないので、**送り直しは起きるものとして受け取る側で重ねられるように**しておく
- 通知に「注文123の発送」のような**番号**を付けると、同じ番号の通知は OS が前のものと置き換え、画面には1つだけ出る
- サーバー側でも**送ったことを記録してから送る**と、別の仕組みからの二重依頼も防げる

### 通知に載せるもの・載せないもの

| 載せる | 載せない |
|---|---|
| 「何か来た」という呼び鈴 | 本当の中身（開いたときにサーバーから取り直す） |
| 押したときに開く画面の目印 | 届かないと困る処理（お金の処理など） |
| 重ねるための番号 | 住所・残高などの個人情報（ロック画面に出て隣の人に見られうる） |

- 「押したら古い内容が出た」は中身を通知に入れていたのが原因の可能性。作った時点の中身は押したときには古いことがある

### AIに書かせたときのチェックポイント

1. 「宛先はもうない」という返事で名簿から消しているか（AI は成功の道だけ書きがち）
2. アプリ起動のたびに宛先を確かめて送り直しているか（初回だけだと入れ直した人に届かない）
3. 大事な処理を通知が届く前提で作っていないか（通知で受け取った中身をそのまま正しいデータとして保存するのは危険）
4. 通知の文に個人情報を入れていないか（「分かりやすく」と頼むと中身を全部入れがち）

### ケーススタディ：3通送ったのに1通

- 地下鉄を出たら通知が1通だけ鳴った。相手は3通送り、サーバーの記録では3回とも「受け付けた」
- 選択肢：A 届くまで送り直す / B 通知は呼び鈴にし、開いたらサーバーから全件取り直す / C 通知の文に未読を全部入れる
- 正解は **B**。サーバーには3通とも残っているので、開いたときに取り直せば1つも消えない
- A は届いたか分からないまま送り直すので、圏内の人には同じ通知が何回も鳴る。C はその1通もまとめられたり捨てられたりし得るうえ、ロック画面に会話の中身が並ぶ

### まとめ

- 通知はサーバーから OS の配達所を通ってスマホに届く。スマホは配達所とだけ線を1本つないでいる
- トークンはスマホとアプリの組ごとにあり、変わることがある。名簿を生きた状態に保つ
- 「受け付けた」は「届いた」ではない。圏外の間の通知はまとめられたり捨てられたりする
- 通知は呼び鈴、中身は開いたらサーバーから取り直す（配達所との認証鍵の作り方や OS ごとの上限の数字は知らなくてよい）
