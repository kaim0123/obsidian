## 詳しい要約

**テーマ：キャッシュとDBがずれる瞬間と、消す順番・有効期限による対策**

「値段を変えたのに古い値段が出る」「直したのに反映されない」「しばらくすると勝手に直る」の正体はたいていキャッシュのずれ。2人のリクエストが前後しながら進むと古い写しが残る。対策は**書き換えずに捨てる**、**DBを書いてから消す**、そしてそれでもゼロにはできないずれを**有効期限**で最後に直すこと。

---

### キャッシュは速い写し

- DBは値段を記録した正しい**元帳**、キャッシュは元帳の**写し**を置いておく場所。速いが、あくまで写し
- キャッシュに無い（**外れ**）→ 遅いがDBを読みに行き、帰り道にキャッシュへ写しを置く
- キャッシュにある（**当たり**）→ DBまで行かずに済む。DBの負担も減り、利用者が多いほど効き目が大きい

### 書き換える方法と、2人が同時に書くと起きること

- 値段を100円→120円に変えるとき、DBを書き換えてキャッシュも書き換えるのが素直な方法。1人が順に書くなら一瞬ずれるだけで問題ない
- サーバーは多くのリクエストを同時にさばくので、2つの書き込みが前後しながら進むことがある
- 例：Aさんが120円、後からBさんが130円に変更（正解は130円）
  1. AさんがDBを120円に
  2. BさんがDBを130円に
  3. Aさんがもたつく間に、Bさんがキャッシュを130円に
  4. 遅れたAさんがキャッシュを120円に → DBは130円、キャッシュは120円
- **誰も直さない**のが怖い点。次に読む人はキャッシュの当たりで満足し、元帳を確かめに行かない。ずれた写しが当たりとして配られ続ける（再読み込みしても直らない正体）
- 原因は書く順番が2人の間で入れ替わったこと。**押した順と届いた順は同じとは限らない**

### 書き換えずに捨てる

- DBを書き換えたら、キャッシュの写しは**消す**
- 空になったキャッシュに次の人が来ると外れ、DBから新しい値を読んで写しを置く。**写しを作るのはいつも元帳を読んだ人**
- 2人同時でも、消すだけなら空になるだけで安全。書き換えると古い値が残る余地があり、消すとその余地が減る
- 「写しは直さず捨てる」

### 消す順番を間違えると

- 先にキャッシュを消してからDBを書く順だと：
  1. Aさんがキャッシュを消す
  2. AさんがDBを書く前にBさんが読みに来て外れ、DBの古い100円を読む
  3. Bさんがキャッシュに100円を置く
  4. AさんがDBを120円にする → キャッシュは100円のまま、誰も直さない
- 元帳が新しくなる前に隙間ができ、そこに入った人が古い元帳から写しを作ってしまう
- 正しい順は**DBを書いてからキャッシュを消す**。読む人が多いサービスほど、この隙間にほぼ確実に誰かが入る

### 正しい順番でも、まれにずれる

- キャッシュが空、DBは100円の状態から：
  1. Bさんが読みに来て外れる
  2. BさんがDBから100円を読むが、処理がもたつく
  3. その間にAさんがDBを120円にし、キャッシュを消す（もともと空）
  4. Bさんが手に持っていた古い100円を置く
- 条件は「Bさんが読んでから置くまでの間に、Aさんの書き込みと消去が丸ごと終わる」こと。普通は読む方が速いのでめったに起きないが、ゼロではない

### 有効期限は最後の安全網

- 写しに**有効期限**（例：置いてから5分で消える）をつける。牛乳の賞味期限のようなもの
- 期限が切れるまではずれたままだが、切れると自動で消え、次の人がDBから新しい値を持ってきて自然に直る
- ずれる時間の最大が有効期限の長さになる（期限5分なら最悪5分ずれる）
- 期限がないと、直す人が来るまでずっとずれたまま（「ずっと直らない」パターン）。「しばらくすると勝手に直る」は期限が切れた瞬間だった

### 有効期限の長さの決め方

- 短い → ずれてもすぐ直るが、DBに行く回数が増える
- 長い → 速くDBも楽だが、ずれたときに長く残る
- 速さと新しさの綱引きで、いいとこ取りはできない
- 決め手は2つの問い：その値はどれくらいの頻度で変わるか／古い値を見せたら利用者はどれくらい困るか
  - お知らせ一覧は1分古くても困らないが、買ったばかりの注文状況が古いと困る
- 期限は技術だけでなく**仕様の問題**。「何分古くてよいか」を決めるのも作る人の仕事

### コードで見る

- 読む側：まずキャッシュを見て当たりなら返す → 外れならDBから読む → キャッシュに置く（有効期限 300秒＝5分を付ける）。**期限の書き忘れはよくある事故**
- 書く側：先にDBを書く → キャッシュの写しを消す（書き換えではなく消す）
- この2行の順番が逆だと隙間ができる。どちらでも動き、テストも通る。ずれは同時に来たときだけ起きるので1人で試していても見つからない

### 写しで済ませてよいもの、元帳を読むもの

| 写しで十分（少し古くても誰も損しない） | 判断に使う値（元帳を読む） |
|---|---|
| 商品の説明、ランキング、プロフィール | 在庫の数、残高、ポイント、権限 |

- 在庫1個なのに写しの「残り3個」を信じて注文を通すと、無いものを売ってしまう
- 買えるかどうかを決める瞬間は元帳を読む。「残りわずか」と表示するだけなら写しでよい。**見せるのは写し、決めるのは元帳**
- 権限も要注意。権限を外した人が、写しに残った古い権限で見られてしまうとセキュリティ事故になる
- 何を写しで済ませるかの線引きを自分で決めることが、キャッシュに責任を持つということ

### AIに書かせたとき見るところ

1. 値を更新する処理でキャッシュを消しているか（忘れるとずっと古いまま）
2. 順番が「DBを書いてから消す」になっているか（AIは先に消す順で出してくることもある。どちらも動くので気づきにくい）
3. 写しに有効期限が付いているか（期限なしで置くコードはよく出てくる）
4. 在庫や残高など判断に使う値を写しから読んでいないか
5. 一覧の写しの消し漏れ。商品1つを直しても、その商品が載った一覧の写しは別に残っている。どの写しがどの元帳から作られたかまで確かめる

### まとめ

- キャッシュは速い写し、正しい元帳はDB
- 値を変えたら、先にDBを書いて後で写しを捨てる（書き換えずに捨てる、順番は元帳が先）
- それでもずれはゼロにできないので、有効期限が最後の安全網
- 期限の長さは「何分古くてよいか」という仕様で決める
- キャッシュ製品の内部構造は知らなくてよい。「押した順と届いた順は違う」を覚えておく
