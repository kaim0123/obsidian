# キュー製品の比較 — SQS / RabbitMQ / Kafka / Redis Streams

## はじめに

メッセージキュー製品は多数あり、**得意分野と苦手分野がそれぞれ大きく違います**。

この記事では **代表的な6製品** を、用途・特徴・選び方の観点から整理します。「どれを使うべきか」より、「**どれがどの問題に向いているか**」を理解するのが目的です。

---

## 一覧表

| 製品 | 分類 | 特徴 | 向き |
|------|------|------|------|
| **Amazon SQS** | マネージド・クラシック | 極めてシンプル、スケール自動 | AWSで非同期タスク処理 |
| **RabbitMQ** | セルフホスト・クラシック | ルーティング強力、機能豊富 | 複雑な配信ルール |
| **Apache Kafka** | セルフホスト・ストリーム | 超高スループット、永続ログ | 大量イベント、ストリーム処理 |
| **Redis Streams** | セルフホスト・ストリーム | 軽量、既存 Redis で動く | 小〜中規模のストリーム |
| **Google Pub/Sub** | マネージド・Pub/Sub | GCP完全統合、高スループット | GCPで Pub/Sub 型 |
| **NATS / NATS JetStream** | セルフホスト | 超低遅延、軽量 | IoT、マイクロサービス間 |

---

## 1. Amazon SQS

### 概要

AWS のフルマネージドキューサービス。**もっとも使われている** と言ってよい定番。

### 強み

- **運用が楽**: サーバ管理不要、スケール自動、99.9% SLA
- **低コスト**: リクエスト従量課金
- **シンプル**: 概念が少ない（Queue / Message / Visibility Timeout）
- **FIFO キュー** もマネージドで使える

### 弱み

- **スループットは中程度**: 標準でメッセージあたり ~10 ms 遅延
- **機能は基本的なものに絞られている**: ルーティングは SNS と組み合わせる必要
- **AWS 依存**: クラウドロックイン

### 向いている用途

- Web アプリのバックグラウンドジョブ（メール送信、画像処理）
- イベントの非同期処理
- **「とりあえず非同期にしたい」場面の第一選択**

### 向いていない用途

- 秒間10万件超のストリーム
- 順序超厳密（FIFO でもグループ単位の制約あり）
- イベントの過去再処理（メッセージは処理後消える）

---

## 2. RabbitMQ

### 概要

Erlang 製のオープンソース。AMQP プロトコルベース。**機能の多さ** で定評。

### 強み

- **ルーティング機能が強力**: Exchange（fanout / direct / topic / headers）で柔軟に配信先を決められる
- **豊富な機能**: TTL、優先度、遅延キュー、DLX（DLQ）、スキーマ等
- **言語クライアントが豊富**
- **低遅延** ~1 ms

### 弱み

- **セルフホスト運用**: サーバ管理・スケール・耐障害を自分で設計
- **スループット**: 数万 msg/s が現実的な上限（Kafka の 1/100〜1/10）
- **学習コスト**: 概念が多い

### 向いている用途

- マイクロサービス間の複雑な配信（トピック単位、優先度、TTL など）
- オンプレ環境
- 要件が細かく、SQS では収まらないケース

### 向いていない用途

- 秒間数十万超の巨大トラフィック
- イベントソーシング・再処理前提

---

## 3. Apache Kafka

### 概要

分散ストリーミングプラットフォーム。**大量イベント処理のデファクト**。

### 強み

- **超高スループット**: 数十万〜数百万 msg/s
- **永続ログ**: メッセージは消費後も残る（設定期間内）
- **複数 Consumer Group**: 同じイベントを複数アプリが独立に読める
- **パーティション内 FIFO**: 順序保証
- **エコシステム**: Kafka Connect、Kafka Streams、KSQL

### 弱み

- **運用難易度が高い**: Zookeeper / KRaft、パーティション設計、再バランス
- **学習コスト**: トピック / パーティション / オフセット / Consumer Group 等の概念
- **小規模にはオーバースペック**
- **レイテンシは RabbitMQ より高い** ことが多い

### 向いている用途

- イベント駆動アーキテクチャ
- ログ収集・ストリーム処理
- イベントソーシング
- **「過去に戻って再処理」が必要**

### 向いていない用途

- 小規模なタスクキュー（SQS で十分）
- 運用チームが小さい（マネージド版を使うか、他を検討）

**マネージド版**: Confluent Cloud、AWS MSK、Google Managed Kafka

---

## 4. Redis Streams

### 概要

Redis 5.0 から導入された **Kafka 的** なストリーム機能。既存の Redis を使い回せる。

### 強み

- **超軽量**: 既存 Redis サーバで動く、追加インフラ不要
- **低遅延**: Redis なので高速
- **Consumer Group 対応**
- **シンプル**

### 弱み

- **大規模には不向き**: スケールアウトは Redis Cluster の制約
- **永続性**: Redis は基本メモリ、AOF/RDB で補う
- **エコシステムは Kafka に遠く及ばない**

### 向いている用途

- 既に Redis を使っているシステム
- 中規模までのストリーム処理
- リアルタイム通知

### 向いていない用途

- 本当に大規模なイベント処理
- 厳格な永続保証が必要

---

## 5. Google Pub/Sub

### 概要

Google Cloud のフルマネージド Pub/Sub サービス。

### 強み

- **グローバルスケール**: Google の大規模インフラ
- **低遅延**: 10〜100 ms
- **Exactly-once 保証** サブスクリプション対応
- **BigQuery / Dataflow と統合**

### 弱み

- **GCP ロックイン**
- **Pub/Sub モデル前提**: 単純な Queue 用途には過剰

### 向いている用途

- GCP 環境全般
- Pub/Sub 型（ファンアウト）が主用途
- 大規模ストリーミング分析

---

## 6. NATS / NATS JetStream

### 概要

Go 製の軽量メッセージングシステム。**超低遅延** が売り。

### 強み

- **超低遅延**: マイクロ秒オーダー
- **超軽量**: 単一バイナリ、依存なし
- **JetStream**: ストリーム永続化機能

### 弱み

- **エコシステムが小さい**
- **国内事例が少ない**

### 向いている用途

- IoT / エッジコンピューティング
- 低遅延マイクロサービス間通信
- エッジ〜クラウドの軽量メッセージング

## 選び方のガイド

### 「とりあえず非同期処理を入れたい」

→ **SQS**（AWS）、**Cloud Tasks / Pub/Sub**（GCP）、**Redis Streams**

### 「マイクロサービス間で複雑なルーティングが欲しい」

→ **RabbitMQ**

### 「秒間数万〜数十万のイベント」

→ **Kafka**

### 「小規模〜中規模、既に Redis 使ってる」

→ **Redis Streams**

### 「IoT / リアルタイム・低レイテンシ」

→ **NATS**

### 「AWS 中心」

→ **SQS + SNS**（+ Kafka は MSK）

### 「GCP 中心」

→ **Pub/Sub**

---

## 実務での選択フロー

```
トラフィック量?
├── 小〜中（< 秒間1000）
│     ├── クラウド? → マネージド一択（SQS / Pub/Sub）
│     └── オンプレ? → RabbitMQ / Redis Streams
│
├── 大（秒間1〜10万）
│     ├── イベント蓄積・再処理が必要? → Kafka
│     └── タスク処理だけ? → SQS / RabbitMQ
│
└── 超大（秒間10万+）
      → Kafka 一択（マネージドで MSK or Confluent）
```

## 併用パターン

### SQS + SNS（AWS 定番）

- SNS = トピック（Pub/Sub）
- SQS = 各サブシステムの受信箱
- 柔軟な Pub/Sub を構築できる

### Kafka + RabbitMQ

- Kafka: イベント駆動・永続ログ
- RabbitMQ: 特定サービス内の複雑なルーティング
- 用途別に使い分け

### Redis Streams + SQS

- Redis Streams: リアルタイムな低遅延ストリーム
- SQS: 遅延OK の重い処理

---

## よくある失敗

### 1. 「有名だから Kafka」で小規模導入

→ **運用コストに押し潰される**。数万 msg/日 なら SQS で十分。

### 2. 「SQS で十分」と思ったら要件が膨らんだ

→ SQS の制約（ルーティング、順序、保持期間）を超え、全面書き換えに。
**事前に要件を洗い出す**。

### 3. RabbitMQ のオンプレ運用で疲弊

→ クラスタ構成、設定調整、監視 …… 片手間ではできない。
**マネージド版（CloudAMQP等）** の検討を。

### 4. 複数製品の共存で運用複雑化

→ 原則 **1〜2製品** に絞る。理由なく増やさない。

## まとめ

- **SQS**: AWS 定番、シンプル・運用楽（迷ったらこれ）
- **RabbitMQ**: 複雑なルーティング・機能豊富、オンプレ向け
- **Kafka**: 超高スループット、イベントログ、再処理可
- **Redis Streams**: 小中規模、既存 Redis で動く
- **GCP Pub/Sub**: GCP 環境のスケーラブル Pub/Sub
- **NATS**: 超低遅延、IoT・エッジ
- 選択は **トラフィック量 × クラウド × 要件** で決まる
- 「有名だから」で Kafka を入れると運用で苦しむことが多い
