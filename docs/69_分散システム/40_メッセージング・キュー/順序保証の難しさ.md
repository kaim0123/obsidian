# 順序保証の難しさ

## はじめに

「キューに入れた順番通りに処理してほしい」── 一見当たり前の要求に見えますが、**分散システムでこれを満たすのは想像以上に難しい** 問題です。

本記事では、なぜ順序保証が難しいのか、どこまでなら現実的に保証できるのか、設計でどう折り合いをつけるかを整理します。

---

## なぜ順序が崩れるのか

### 1. 複数の Consumer が並列処理

```
[Queue] → Msg1, Msg2, Msg3
              ↓         ↓         ↓
        Worker1    Worker2    Worker3
            ↓         ↓         ↓
         2秒       0.5秒      1秒
            ↓         ↓         ↓
         完了3   完了1    完了2
```

→ **処理順 ≠ 投入順**。各 Worker の処理時間のバラつきで前後する。

### 2. 失敗時の再配信

```
Msg1, Msg2, Msg3 投入
Worker: Msg1 処理中... 失敗
Worker: Msg2 受信 → 成功
Worker: Msg3 受信 → 成功
Worker: Msg1 再配信で受信 → 成功

→ 処理順: Msg2, Msg3, Msg1
```

### 3. 複数 Producer

```
Producer-A: 時刻 T=0.00 に Msg1 投入 → ネットワーク遅延で T=0.05 に Queue 到着
Producer-B: 時刻 T=0.01 に Msg2 投入 → 高速ネットワークで T=0.02 に Queue 到着

→ Queue から見た順序は Msg2 → Msg1
```

Producer 側の時計とネットワーク遅延でも順序がブレる。

### 4. キュー製品自体の仕様

- SQS 標準キュー: **順序保証なし**（最大スループット優先）
- Kafka: パーティション内は順序保証、パーティション間はなし
- Redis Streams: パーティションなしなら順序保証

## 順序保証が必要なシナリオ

### 1. イベントソーシング

```
ユーザーA の更新履歴:
  T1: 名前変更 "Alice" → "Bob"
  T2: 名前変更 "Bob" → "Charlie"

逆順で処理されると最終名が "Bob" になる（誤り）
```

### 2. 在庫管理

```
注文 → 在庫 -1
返品 → 在庫 +1

在庫が1個しかなくて、同時に「売った」「返品された」順が逆になると…
```

### 3. 金融取引

```
送金 → 残高 -10000
引き出し → 残高 -5000

残高が 12000 → 2000 → -3000 か、12000 → 7000 → -3000 か、順で違う
（マイナスの許容が違う）
```

### 4. 状態マシン

```
pending → paid → shipped → delivered

「shipped」メッセージが「paid」より先に処理されると状態が不正
```

## 順序保証の粒度

「全メッセージの順序」は現実的でない。**どの単位で順序が必要か** を設計する。

### 全体順序（Total Ordering）

すべてのメッセージが同じ順序で処理される。
→ **単一 Consumer でシリアル処理** しかない。スループット激減。

### グループ順序（Partial Ordering）

**ある単位の中でだけ順序保証**。ユーザーID、注文ID、セッションID などで区切る。

```
user-1 のメッセージ: A → B → C の順で処理（保証）
user-2 のメッセージ: X → Y → Z の順で処理（保証）
user-1 と user-2 の間の順序は気にしない
```

→ **スループットと順序保証のバランス** を取る現実解。

### 因果順序（Causal Ordering）

「A の結果を見て B を作った」という因果関係だけ守る。
→ Vector Clock や Lamport Clock を使う上級概念。

## 製品ごとの順序保証

### Amazon SQS

| キュー種別 | 順序 |
|-----------|------|
| 標準キュー | **順序保証なし** |
| FIFO キュー | MessageGroupId 内で FIFO |

FIFOキューの例:
```
MessageGroupId = "user-1" → 投入順に処理
MessageGroupId = "user-2" → 投入順に処理（user-1 とは並列可）
```

### Kafka

**パーティション** 内で厳密な FIFO:
```
Topic "orders" with 3 partitions
  Partition 0: msg-A, msg-B, msg-C  ← この順
  Partition 1: msg-X, msg-Y
  Partition 2: msg-P, msg-Q, msg-R  ← この順
```

**パーティション間の順序は保証されない**。
→ Partition Key（ユーザーID等）で「同じキーは同じパーティション」に集める。

### RabbitMQ

- 単一キュー・単一 Consumer なら FIFO
- 複数 Consumer（Competing Consumers）なら **順序崩れる**

### Redis Streams

- パーティションなし: 順序保証
- Consumer Group で複数 Consumer: 崩れうる

---

## 順序保証と並列処理は両立しない（原則）

```
完全な順序保証  ←──→  並列処理（スループット）
```

**トレードオフ**:
- 全体順序を守る = 並列処理できない（Consumer 1台）
- スループットを上げる = 順序保証を捨てる

### 現実的な落とし所

**グループ単位で順序保証、グループ間は並列**

```
Kafka:    ユーザーID で Partition Key
SQS FIFO: ユーザーID を MessageGroupId

→ 同一ユーザー内は FIFO、ユーザー間は並列
→ 1ユーザーが高スループットになることは稀なので、実用十分
```

## アプリ側で順序を補う工夫

### 1. タイムスタンプ / バージョン列

メッセージに時刻やバージョン番号を入れ、**受信側で古いものを無視**。

```python
def handle(msg):
    current = db.get(msg.user_id)
    if msg.version <= current.version:
        return  # 古いメッセージは捨てる
    db.update(msg.user_id, data=msg.data, version=msg.version)
```

→ 順不同で来ても、**最終的な状態は同じ**（冪等 + 冪等性の拡張）。

### 2. 状態マシンによる防御

```python
VALID_TRANSITIONS = {
    "pending": ["paid", "cancelled"],
    "paid": ["shipped", "refunded"],
    "shipped": ["delivered"],
}

def handle(msg):
    current = db.get_state(msg.order_id)
    if msg.new_state not in VALID_TRANSITIONS[current]:
        # 異常な遷移 → 捨てる / DLQ
        return
    db.set_state(msg.order_id, msg.new_state)
```

### 3. 最終一貫性を許容する

「**数秒間だけ順序がズレることがある**」という妥協。
- ECサイトの在庫表示
- いいね数の表示

→ **厳格な順序が本当に必要か？** を問い直す。

## 設計時の問いかけ

1. **本当に全体順序が必要か？** ほとんどの場合は「グループ内順序」で足りる
2. **何を基準にグループ化するか？** ユーザーID / 注文ID / セッションID
3. **順序崩れが起きたらどう気づくか？** ロジカルなチェック（状態マシン、バージョン）
4. **スループットとのトレードオフは許容できるか？**

## 落とし穴

### 1. 「FIFO キュー使ってるから安心」

- FIFO は **MessageGroupId 内** の話
- 全部同じ MessageGroupId にすると並列不可 → スループット崩壊

### 2. Partition Key を適当に設定

- ランダム → 並列度は高いが順序崩れる
- 単一キー → 順序は守れるが並列度ゼロ
- 適切: **ビジネスエンティティ単位**（ユーザーID、注文ID）

### 3. 順序崩れを検知せず事故る

- 静かに順序が崩れて、データが不正な状態に
- **状態マシン / バージョン列** でアプリ側で検知する

### 4. 並列 Producer で順序崩れ

- 複数の Producer が同じ MessageGroupId に投入
- 投入時点の順序が保証されない
- 単一 Producer or シリアライズポイントが必要

### 5. リトライによる順序反転

- 失敗で再配信 → 他のメッセージが先行
- アプリ側のバージョン管理で防御

## よくある質問

### Q. 完全な全体順序を守る方法は?

A. **単一 Queue + 単一 Consumer** しかない。並列処理を諦める。
もしくは Raft/Paxos のような合意アルゴリズムで合意を取るが、実装コストが膨大。

### Q. Kafka で順序を守るには?

A. **Partition Key を「順序保証したい単位」に合わせる**。
たとえば `user_id % N` で 1ユーザーは1パーティションに集約。

### Q. 順序崩れの検知方法は?

A. アプリレベルで**期待する前状態** を確認。
例: 「次は paid のはず」→ current != pending なら異常 → ログ or DLQ。

## まとめ

- 分散キューで **全体順序は実現困難**、基本は **グループ順序** に落とし込む
- 順序崩れの要因は **並列処理 / リトライ / 複数Producer / 製品仕様**
- **順序保証 vs 並列処理（スループット）** はトレードオフ
- SQS は FIFO キュー、Kafka はパーティション、と製品ごとに単位が違う
- MessageGroupId / Partition Key の選定が設計の要
- **アプリ側の防御**（状態マシン / バージョン列）を必ず入れる
- 「本当に順序が必要か？」を問い直すのが最初のステップ
