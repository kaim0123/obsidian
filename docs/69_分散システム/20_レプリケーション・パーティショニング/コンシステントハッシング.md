# コンシステントハッシング — Consistent Hashing

## はじめに

**コンシステントハッシング（Consistent Hashing）** とは、

> **キーをノード（サーバ）に割り振る** アルゴリズムの一種で、ノードの増減時の **再配分コストを最小化** する方法

です。分散キャッシュ（Memcached / Redis Cluster）や分散 DB（DynamoDB / Cassandra）など、**多ノードで同じデータセットを分割管理** する場面で広く使われます。

---

## なぜ必要か

### 素朴なハッシュ分散の問題

「N台のキャッシュサーバに、キーを均等に振り分けたい」。最もシンプルな方法:

```
サーバ番号 = hash(key) mod N
```

例: 4台のサーバ（#0, #1, #2, #3）
```
hash("user:123") = 542 → 542 mod 4 = 2 → サーバ#2
hash("user:456") = 789 → 789 mod 4 = 1 → サーバ#1
```

### 問題: サーバを増減したら…

4台 → 5台にすると、`mod` の結果が変わり、**ほぼすべてのキーが別サーバに移動**:

```
旧: hash("user:123") mod 4 = 2
新: hash("user:123") mod 5 = 4  ← 別サーバ！
```

**ほぼ全キャッシュミス** → DB に殺到（スタンピードの巨大版）。

---

## コンシステントハッシングの考え方

### リングモデル

キーとサーバを **0〜2^32 のハッシュ空間上** に並べ、円環（リング）とみなす:

```
                0
           ┌────┴────┐
      Server A      Server B
      (hash=100)    (hash=2000)
         ↓            ↑
         │            │
         └─── Server C
              (hash=3000)
```

### キーの配置

- キーのハッシュ値を同じ空間にマップ
- キーの次に見つかる **時計回りに最初のサーバ** にそのキーを割り当てる

```
hash("user:123") = 500
→ リング上で 500 の次のサーバ = Server B (2000)
```

### サーバ追加時

新サーバ D (hash=1000) を追加:

```
Server A (100)
Server D (1000) ← 新規
Server B (2000)
Server C (3000)
```

→ **もともと Server B が持っていた「100〜2000」の一部が Server D に移る**。
→ 影響範囲は **一部のキー** だけ。**全体ではない**。

---

## 効果

### 素朴なハッシュ vs コンシステントハッシング

| 項目 | 素朴な mod N | コンシステントハッシング |
|------|-------------|------------------------|
| ノード N台→N+1台 時の再配分 | ほぼ全キー | **1/N 程度** |
| 実装難易度 | 超低 | 中 |
| 負荷分散 | 均等 | 偏りやすい（仮想ノードで対策） |

---

## 仮想ノード（Virtual Nodes / vnode）

### 問題: 素朴なリングだと偏る

各サーバが1点だけリングに置かれる → サーバ間のハッシュ距離が不均等。一部サーバに偏る。

### 解決: 仮想ノードを使う

1つの物理サーバを、**リング上の複数ポイント** に置く。

```
Server A → リング上に A-1, A-2, A-3, ..., A-100 の100ポイント
Server B → リング上に B-1, B-2, ..., B-100
...
```

→ **リング上の分布が均等化**、負荷が揃う。

実装では通常、1サーバあたり **100〜1000 の仮想ノード** を配置。

## 典型的な疑似コード

```python
import hashlib
import bisect

class ConsistentHash:
    def __init__(self, nodes, vnodes=100):
        self.ring = {}          # hash -> node
        self.sorted_hashes = []
        for node in nodes:
            self.add_node(node, vnodes)

    def _hash(self, key):
        return int(hashlib.md5(key.encode()).hexdigest(), 16)

    def add_node(self, node, vnodes):
        for i in range(vnodes):
            vnode_key = f"{node}:{i}"
            h = self._hash(vnode_key)
            self.ring[h] = node
            bisect.insort(self.sorted_hashes, h)

    def remove_node(self, node, vnodes):
        for i in range(vnodes):
            h = self._hash(f"{node}:{i}")
            del self.ring[h]
            self.sorted_hashes.remove(h)

    def get_node(self, key):
        if not self.ring:
            return None
        h = self._hash(key)
        idx = bisect.bisect(self.sorted_hashes, h) % len(self.sorted_hashes)
        return self.ring[self.sorted_hashes[idx]]

# 使用例
ch = ConsistentHash(["node-1", "node-2", "node-3"])
print(ch.get_node("user:123"))  # 'node-2'
print(ch.get_node("user:456"))  # 'node-1'
```

## メリット

1. **ノード追加・削除時の再配分が最小限**（1/N 程度）
2. **キャッシュヒット率が保たれる**
3. **スケールイン・アウトに強い**
4. **障害時の影響範囲が限定的**

---

## デメリット・注意点

### 1. 負荷の偏り（仮想ノードなしの場合）

素朴な実装だと、1台に負荷が集中する可能性。**仮想ノード必須**。

### 2. ホットキー問題

人気の高い単一キーが1台のサーバに集中 → 分散しない。
→ キャッシュ層の前に別の仕組み（local cache など）を挟む。

### 3. 負荷分散は「統計的」

リングで厳密に均等にはならず、ある程度のバラつきはある。

### 4. 実装ミスで再配分が効かない

- 仮想ノード数が少ない
- ハッシュ関数が均等でない
- → 実装のバグで恩恵を得られない

---

## 他の分散方式との比較

### 単純モジュラー（`mod N`）

- 実装最短
- スケール時に全データ再配分
- テスト環境・小規模に限定

### ハッシュスロット（Redis Cluster 方式）

- 16384 個の固定スロット
- スロット単位でノード割り当て
- 再配分時もスロット単位なので **移動が予測しやすい**

### ランデブーハッシング（HRW / Rendezvous Hashing）

- キーごとに「最高スコアのサーバ」を選ぶ
- コンシステントハッシング同等の性質
- 実装がシンプル（リング不要）

### ジャンプハッシング（Google）

- ノード数ベースの数式
- メモリ効率が高い
- ノードIDが連番前提

## 実務での使いどころ

### ◯ 効果的

- 多ノード分散キャッシュ
- 多ノード分散ストレージ
- オートスケール頻発する環境
- ノード数が頻繁に変わる

### ✕ オーバースペック

- サーバ数が固定（2〜3台）で変わらない
- キャッシュサイズが小さく、全データ再配分で問題ない
- コード複雑度を避けたい小規模プロジェクト

## よくある質問

### Q. Redis Cluster はコンシステントハッシング?

A. 厳密には **ハッシュスロット方式** で、コンシステントハッシングとは別。
だが「ノード追加時に一部スロットのみ移動」という性質は同じ。

### Q. 仮想ノードは何個くらい?

A. 100〜1000 が一般的。少なすぎると偏り、多すぎるとメモリ消費増。
100 程度で十分均等化される。

### Q. ホットキー対策は?

A. コンシステントハッシングだけでは解決しない。**ローカルキャッシュ**、**データ分割**、**複製** などの併用。

## まとめ

- コンシステントハッシングは **ノード増減時の再配分を最小化** するアルゴリズム
- キーとノードを **リング（ハッシュ空間）上** に配置、時計回りに最初のノードが担当
- 素朴な `mod N` と違い、**ノード追加は1/N程度のキーだけ動く**
- 偏り対策として **仮想ノード**（物理1台に100〜1000点）
- Memcached / Cassandra / DynamoDB 等で広く採用
- Redis Cluster は似た思想の **ハッシュスロット方式**
- 本当にスケール頻発する環境で効果大、固定構成には過剰
