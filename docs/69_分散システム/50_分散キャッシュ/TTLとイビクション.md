# TTL とイビクション — LRU / LFU / FIFO

## はじめに

キャッシュは **無限に貯められない** ため、「いつデータを捨てるか」の設計が必要です。

この設計には2つの軸があります:

- **TTL（Time To Live）**: 時間による寿命設定
- **イビクション（Eviction / 追い出し）**: メモリ不足時の強制削除戦略

両者を正しく組み合わせないと、**古いデータを使い続ける** / **頻繁に消されて意味がない** という問題が起きます。

---

## TTL（Time To Live）

### 定義

> データがキャッシュに残る **最大時間**

例:
- 「5分後に自動削除」
- 「1時間後に期限切れ」

### Redis の例

```python
r.set("user:123", data, ex=300)  # 300秒 = 5分で消える
r.expire("user:123", 600)        # 既存キーの TTL を変更
r.ttl("user:123")                # 残り秒数を取得
```

### TTL の決め方

| データ性質 | 推奨 TTL |
|-----------|---------|
| マスターデータ（国リスト等） | 1日〜永続 |
| ユーザープロファイル | 5分〜1時間 |
| ニュース一覧 | 1〜5分 |
| 頻繁に更新される在庫 | 数秒〜1分 or キャッシュしない |
| セッション情報 | 30分（不活動で延長） |

### 短すぎる TTL

- キャッシュミスが増える
- DB 負荷が下がらない
- 意味がない

### 長すぎる TTL

- 古いデータが使われる
- 不整合が大きくなる
- メモリを占有

---

## TTL のジッター（ランダム揺らぎ）

```python
import random
ttl = 300 + random.randint(-30, 30)  # 270〜330秒
r.setex(key, ttl, value)
```

なぜ必要か:
- 同じ時刻に書かれたキーが **一斉に期限切れ**
- → DB に一斉にアクセス集中（**Cache Avalanche / キャッシュ雪崩**）
- 少しランダム化することで分散

---

## イビクション（追い出し戦略）

### 定義

> キャッシュが **メモリ上限に達した** とき、どのキーを削除するか

TTL は「時間で消える」、イビクションは「容量超過で消される」。

### 主な戦略

#### 1. LRU (Least Recently Used)

**最後にアクセスされてから時間が経っているもの** を削除。

```
時刻   アクセスしたキー
10:00  A, B, C キャッシュに入る
10:05  A をアクセス → A が新しく扱われる
10:10  容量超過 → B が削除される（一番古いアクセス時刻）
```

- **最も一般的**
- 「最近使ったものは今後も使う」仮説
- Redis の `allkeys-lru` / `volatile-lru`

#### 2. LFU (Least Frequently Used)

**アクセス回数が少ないもの** を削除。

```
キー A: 1000回アクセス
キー B: 5回アクセス
キー C: 100回アクセス

容量超過 → B が削除される
```

- 「よく使うものを残す」
- 短期の一過性アクセスに強い
- Redis 4.0+ の `allkeys-lfu` / `volatile-lfu`

#### 3. FIFO (First In First Out)

**入った順に削除**。アクセス頻度は無視。

- シンプル
- 公平性重視
- 実装が軽い

#### 4. Random

ランダムに削除。

- 最速・最シンプル
- 大規模キャッシュの簡易実装

#### 5. TTL ベース (volatile-*)

TTL が設定されているキーだけ削除対象。

- `volatile-lru`: TTL ありのキーで LRU
- `volatile-lfu`: TTL ありのキーで LFU
- `volatile-ttl`: TTL が近いキーから順

## Redis の eviction policy

Redis の `maxmemory-policy` で設定:

| Policy | 動作 |
|--------|------|
| `noeviction` | 容量オーバー時、書き込みエラー（デフォルト） |
| `allkeys-lru` | 全キーから LRU で削除 |
| `allkeys-lfu` | 全キーから LFU で削除 |
| `allkeys-random` | 全キーからランダム |
| `volatile-lru` | TTL ありのキーで LRU |
| `volatile-lfu` | TTL ありのキーで LFU |
| `volatile-random` | TTL ありのキーでランダム |
| `volatile-ttl` | TTL が近いキーから |

### 推奨

- **典型的なキャッシュ用途**: `allkeys-lru`
- **高頻度アクセスが偏るデータ**: `allkeys-lfu`
- **セッション等、TTL 明示的に管理**: `volatile-lru`

### `noeviction` の罠

- デフォルト設定
- メモリ一杯 → 書き込み失敗 → **アプリエラー**
- 意図的でない限り `noeviction` は避ける

## TTL vs イビクション の使い分け

| 状況 | TTL | イビクション |
|------|-----|------------|
| 時間で古くなる | ◎ | - |
| 「どのくらい残るか」を制御 | ◎ | ✕ |
| メモリ上限 | ✕ | ◎ |
| 高頻度データだけ残したい | - | ◎ (LFU) |

**両方を併用** するのが基本:
- **TTL で時間ベースの整合性** を担保
- **イビクション でメモリ不足時** の保険

## キャッシュヒット率と戦略

### キャッシュヒット率 = 「キャッシュから返せた割合」

```
ヒット率 = ヒット数 / (ヒット数 + ミス数)
```

- 80% 以上: 良好
- 95% 以上: 非常に良好
- 50% 以下: 戦略見直し or キャッシュ不要を検討

### 戦略別のヒット率傾向

| 戦略 | 特徴 | ヒット率傾向 |
|------|------|-------------|
| LRU | 最近使ったもの重視 | 一般には高い |
| LFU | 頻繁アクセス重視 | 偏りがある場合に強い |
| FIFO | 公平 | 低めになりがち |
| Random | 乱択 | 中程度 |

## Cache Stampede / Thundering Herd

### 何が起きるか

```
人気キー "top_products" の TTL が切れる
    ↓
同時に1000リクエストが見に来る
    ↓
全リクエストが「キャッシュなし」と判定
    ↓
全リクエストが DB を叩く
    ↓
DB 過負荷
```

### 対策

1. **TTL ジッター**（±10%など）
2. **シングルフライト**: 最初の1リクエストだけ DB を叩き、他は待つ
3. **Refresh-ahead**: 期限前に再取得
4. **Stale-while-revalidate**: 期限切れでも古い値を返しつつ裏で更新

→ 詳細は `キャッシュスタンピード.md`

## TTL 設計のベストプラクティス

### 1. データ種別ごとに TTL を設計

```python
TTL_CONFIG = {
    "user_profile": 600,      # 10分
    "top_products": 300,      # 5分
    "categories": 86400,      # 1日
    "session": 1800,          # 30分
}
```

### 2. 無限 TTL を避ける

- メモリが溢れる
- 古いデータが取り残される
- **最大でも数日、基本は分〜時間**

### 3. 更新イベントで明示的に無効化

TTL 任せだけでなく:
```python
def update_user(user_id, data):
    db.update(user_id, data)
    r.delete(f"user:{user_id}")  # 即座に無効化
```

### 4. ジッターを入れる

```python
import random
def set_cache(key, value, base_ttl):
    jitter = random.randint(-base_ttl // 10, base_ttl // 10)  # ±10%
    r.setex(key, base_ttl + jitter, value)
```

## モニタリング

定期的に確認すべきメトリクス:

- **ヒット率**（80%以上が健全）
- **ミス数**の推移
- **メモリ使用率**
- **イビクション回数**（頻繁ならメモリ不足）
- **平均 TTL**

ツール:
- Redis: `INFO stats`, `redis-cli --stat`
- Memcached: `stats` コマンド
- Datadog, Prometheus, Grafana で可視化

## 落とし穴

### 1. TTL なしで `SET` するだけ

→ メモリが永遠に増える、イビクションで不本意なキーが消える

### 2. イビクションポリシーが `noeviction` のまま

→ 容量一杯で書き込み失敗、アプリがエラー

### 3. 全キーで同じ TTL

→ 一斉期限切れでキャッシュ雪崩

### 4. 長すぎる TTL

→ 更新後も古いデータが使われ続ける

### 5. TTL と更新イベントの両方を使わない

→ 整合性の穴が残る

## まとめ

- **TTL = 時間による寿命**、**イビクション = 容量による追い出し**
- 両方併用が基本
- LRU が最も一般的、偏りあるなら LFU
- Redis は `allkeys-lru` を設定するのが王道
- **`noeviction` のまま運用しない**（書き込みエラー源）
- **TTL には ±10% のジッター** を入れる（雪崩対策）
- データ種別ごとに TTL を設計
- ヒット率・イビクション数を監視
