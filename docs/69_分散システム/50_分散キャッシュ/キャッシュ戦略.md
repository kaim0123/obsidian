# キャッシュ戦略 — Cache-aside / Read-through / Write-through / Write-behind

## はじめに

**キャッシュ（Cache）** とは、

> 低速なデータソース（DB・API）のデータを、**高速な場所（メモリ等）にコピーしておく** 仕組み

です。

ただ「コピーする」だけでなく、**いつコピーし、いつ同期し、いつ捨てるか** の設計パターンがいくつかあり、これを **キャッシュ戦略** と呼びます。選択を間違えると、**データ不整合や性能劣化** を招きます。

---

## キャッシュを使う理由

```
ユーザー → アプリ → DB（遅い、高コスト）

ユーザー → アプリ → キャッシュ（速い、軽い）
                      ↓ ない時だけ
                    DB
```

- 高速化（ミリ秒→マイクロ秒）
- DB 負荷の削減
- スケーラビリティ向上
- API のレートリミット回避

---

## 主要なキャッシュ戦略

### 1. Cache-aside（キャッシュアサイド / Lazy Loading）

**最もよく使われる戦略**。アプリが自分でキャッシュと DB を制御する。

#### 読み取り

```
1. アプリがキャッシュを見る
2. あればそのまま返す（キャッシュヒット）
3. なければ DB から取得
4. 結果をキャッシュに保存
5. クライアントに返す
```

```python
def get_user(user_id):
    user = cache.get(f"user:{user_id}")
    if user is not None:
        return user  # キャッシュヒット
    user = db.query("SELECT * FROM users WHERE id = ?", user_id)
    cache.set(f"user:{user_id}", user, ttl=300)  # 5分保持
    return user
```

#### 書き込み

```
1. DB を更新
2. キャッシュを削除 (or 更新)
```

```python
def update_user(user_id, data):
    db.update(user_id, data)
    cache.delete(f"user:{user_id}")  # 次回読むときに新データで埋まる
```

#### 長所

- シンプル
- キャッシュが死んでもアプリは動く（DB にフォールバック）
- 必要なものだけキャッシュ

#### 短所

- **初回アクセスが遅い**（キャッシュミス）
- 書き込み時に DB とキャッシュの両方を操作する必要
- 不整合が起きやすい（後述）

---

### 2. Read-through（リードスルー）

読み取りを **キャッシュ層に一任** するパターン。

```
アプリ → キャッシュ → （ない時だけ）→ DB
```

アプリは **キャッシュだけを見る**。キャッシュライブラリ / サービスが DB への取得を代行。

#### 長所

- アプリコードがシンプル
- 責務分離

#### 短所

- 専用のキャッシュライブラリが必要
- 「何をキャッシュするか」の制御が難しい

#### 代表例

- Hibernate 2nd level cache
- 一部の ORM の自動キャッシュ機能

---

### 3. Write-through（ライトスルー）

書き込み時に **キャッシュと DB を同時に更新**。

```
アプリ → キャッシュ層 → DB
          ↓ 両方に書く
```

#### 長所

- キャッシュとDB が常に一致（強整合）
- 読み取り時のミスが少ない

#### 短所

- **書き込みが遅い**（キャッシュ + DB の2回書く時間）
- すべてのデータがキャッシュに乗る（メモリ消費）
- キャッシュ障害時の対応が複雑

#### 使いどころ

- 整合性が最重要（決済、残高等）
- 書き込み < 読み取り の比率

---

### 4. Write-behind（ライトビハインド / Write-back）

書き込みは **キャッシュだけに即座に行い、DB には後で非同期に** 反映。

```
アプリ → キャッシュ （即応答）
             ↓ 非同期
             DB
```

#### 長所

- **書き込みが超高速**
- DB への書き込みをバッチ化できる

#### 短所

- **キャッシュ障害でデータロスト** の可能性
- 整合性が緩い
- 実装が複雑

#### 使いどころ

- 高頻度の書き込み、一部データロストが許される（ログ、統計）
- **データロストが致命的な用途には使わない**

---

### 5. Refresh-ahead（リフレッシュアヘッド）

キャッシュ期限切れ **直前に非同期で再取得** する戦略。

```
TTL が 0 になる前（例: 残り 20%）に、裏で新しい値を取得
→ ユーザーは常に新鮮なキャッシュを得られる
```

#### 長所

- TTL 切れによるキャッシュミスの体感ゼロ
- 常に新しいデータが載っている

#### 短所

- 使わなくてもリフレッシュ → リソース消費
- 実装難度

#### 使いどころ

- 高頻度アクセスの重要データ
- CDN のような大規模キャッシュ

---

## 比較表

| 戦略 | 読み取り | 書き込み | 整合性 | 複雑度 | 使いどころ |
|------|---------|---------|-------|-------|-----------|
| **Cache-aside** | ミス時にDB | アプリが両方 | 弱 | 低 | **迷ったらこれ** |
| Read-through | キャッシュが代行 | - | 弱 | 中 | ORM統合 |
| Write-through | 高速 | 遅い | 強 | 中 | 整合性重視 |
| Write-behind | 高速 | 超高速（非同期） | 弱 | 高 | 書き込み多い |
| Refresh-ahead | 常に速い | - | 中 | 高 | 高頻度アクセス |

---

## 戦略選択のフローチャート

```
書き込みと読み取り、どちらが多い?
├── 読み取り >> 書き込み
│    ├── シンプル重視 → Cache-aside
│    └── 整合性重視 → Read-through + Write-through
│
├── 書き込み多い
│    ├── 整合性重要 → Write-through
│    └── 一部ロスOK → Write-behind
│
└── 超高頻度アクセス
      → Cache-aside + Refresh-ahead
```

## キャッシュ戦略と整合性

### 書き込み時の順序問題

キャッシュと DB の両方を更新するとき、**どちらを先にするか** が重要。

#### パターンA: 先に DB、後でキャッシュ削除（推奨）

```
1. DB に書く
2. キャッシュを削除
```

- 失敗時の被害が小さい（キャッシュがないだけ、次回DB から取る）
- **推奨**

#### パターンB: 先にキャッシュ削除、後で DB

```
1. キャッシュを削除
2. DB に書く
```

- 「キャッシュ削除 → 他リクエストが DB 読んで古い値をキャッシュ → 1のDB書き込み」
- → **古いデータが残る事故が起きやすい**

### Double Delete（二重削除）

```
1. キャッシュを削除
2. DB に書く
3. しばらく待つ（ms）
4. キャッシュを再度削除
```

マスター/スレーブ構成での DB レプリケーション遅延対策。

---

## TTL（Time To Live）の重要性

どの戦略でも **TTL を設定する** のが基本:

- ミスによる不整合を「時間が解決する」
- メモリが溢れない
- 古いデータを強制的に更新

→ 詳細は `TTLとイビクション.md`

---

## 落とし穴

### 1. キャッシュに永遠に残るデータ

TTL を設定せず、`SET` だけで入れる → メモリが一杯になったり、古いデータが使われ続ける。

### 2. キャッシュストーム（Thundering Herd）

同じキャッシュ期限切れのタイミングで大量のリクエストが DB に集中。
→ `キャッシュスタンピード.md` 参照。

### 3. Stale Data（古いデータ）

```
1. User A が DB を更新
2. Cache はまだ古い値
3. User B が古い値を見る（5分）
```

TTL の長さ + Cache-aside パターンでは不可避。**許容できる期間を決める**。

### 4. Write-behind でのデータロスト

キャッシュダウン = 未書き込みデータ消失。**金融・決済には使わない**。

### 5. キャッシュの雪崩（Cache Avalanche）

同じ時刻に大量のキーが一斉期限切れ → DB に殺到。
TTL に **ジッター**（ランダム±10%）を入れて分散。

## 実装パターン

### Cache-aside の最小実装（Python + Redis）

```python
import json
import redis

r = redis.Redis()

def get_user(user_id):
    key = f"user:{user_id}"
    cached = r.get(key)
    if cached:
        return json.loads(cached)

    user = db.query("SELECT * FROM users WHERE id = %s", user_id)
    r.setex(key, 300, json.dumps(user))  # TTL 5min
    return user

def update_user(user_id, data):
    db.update(user_id, data)
    r.delete(f"user:{user_id}")  # 次回読むとき新しい値でキャッシュされる
```

## よくある質問

### Q. Cache-aside と Write-through、どっち?

A. **迷ったら Cache-aside**。シンプルで、キャッシュ障害時もアプリが動く。
Write-through は整合性が極めて重要な場面のみ。

### Q. キャッシュを使う条件は?

A. 以下に当てはまれば効果的:
- 読み取り多い (> 書き込み)
- 同じデータへの繰り返しアクセスが多い
- DB / API が遅い / 高コスト
- 多少の古さは許容できる

### Q. マイクロサービスでキャッシュ共有すべき?

A. **しないのが原則**。共有するとサービス間結合が発生。
各サービスが自分用にキャッシュを持つ。

## まとめ

- **Cache-aside**: アプリが制御、最もよく使われる（**迷ったらこれ**）
- **Read-through**: 読み取りを層に任せる
- **Write-through**: 書き込み時にキャッシュも更新、整合性◎、書き込み遅い
- **Write-behind**: 書き込み超高速、データロストリスク
- **Refresh-ahead**: 期限前に再取得、体感ゼロミス
- 書き込み順序は **「先に DB、後でキャッシュ削除」** が基本
- TTL 必須、ジッターも入れる
- 整合性は常に「緩い」前提で設計
