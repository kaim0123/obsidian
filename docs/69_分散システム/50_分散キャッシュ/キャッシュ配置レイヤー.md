# キャッシュ配置レイヤー — ブラウザ / CDN / アプリ / DB

## はじめに

キャッシュは **「速いところにデータを置く」** という発想ですが、その「速いところ」はシステム内のあらゆる層に存在します。どの層にキャッシュを置くかで、**効果・コスト・運用の複雑さ** が大きく変わります。

本記事では、**リクエストがユーザーからDBに届くまでの経路すべて** で考えられるキャッシュ位置を整理します。

---

## 全体像: リクエストの経路

```
[ユーザーのブラウザ]
        ↓
[ローカル・ブラウザキャッシュ]
        ↓
[CDN / エッジキャッシュ]
        ↓
[ロードバランサ]
        ↓
[アプリケーションキャッシュ]（アプリ内メモリ、Redis等）
        ↓
[DBキャッシュ]（バッファプール等）
        ↓
[ディスク / ストレージ]
```

各層でキャッシュできる。**上流（ユーザー寄り）ほど効果が大きい** が、**下流ほど制御しやすい**。

---

## 1. ブラウザキャッシュ（クライアント側）

### 概要

ブラウザが受信したレスポンスを、**ユーザーのマシンに保存** する。

### 制御方法

HTTP ヘッダで制御:

```http
Cache-Control: max-age=3600
Cache-Control: public, max-age=86400, immutable
Cache-Control: no-cache
Cache-Control: private, no-store
ETag: "abc123"
Last-Modified: Mon, 24 Apr 2026 12:00:00 GMT
```

### 特徴

- **最速**（ネットワーク不要）
- サーバーに負荷ゼロ
- ユーザーごとに保持

### 向き

- 静的アセット（JS/CSS/画像）
- 変更が少ないデータ
- ユーザー固有の情報（`private`）

### 弱点

- **ユーザー側のキャッシュは制御が難しい**（一度キャッシュされたら、期限切れまで更新されない）
- 異なるユーザーで共有されない

### ベストプラクティス

- **ファイル名にハッシュを含める**（`app.a1b2c3.js`）→ 変わったらURLが変わるので、ブラウザは新しいものを取得
- JS/CSS は `immutable` で長期キャッシュ
- HTML は短め（`no-cache` or 数分）

---

## 2. CDN / エッジキャッシュ

### 概要

世界中に分散配置された **CDN 各地点でキャッシュ**。ユーザーから物理的に近い場所で応答。

### 代表製品

- Cloudflare
- AWS CloudFront
- Fastly
- Akamai
- Vercel Edge Network

### 特徴

- **物理距離が短い → レイテンシ削減**
- オリジンサーバーの負荷大幅削減
- DDoS 保護
- グローバルユーザー対応

### 向き

- 静的アセット（画像、JS/CSS、動画）
- 動的でもキャッシュ可能なもの（SSR の結果など）
- 公開ページ（マイページのようなパーソナライズは不向き）

### 弱点

- キャッシュパージ（無効化）の伝播に時間がかかる
- オリジンと CDN の整合性管理
- 複雑な認証コンテンツには向かない

### Cache-Control と CDN

```http
Cache-Control: public, max-age=60, s-maxage=3600
```

- `max-age`: ブラウザのキャッシュ時間（60秒）
- `s-maxage`: CDN のキャッシュ時間（3600秒）
- `public`: CDN でもキャッシュ OK

→ 詳細は `CDNキャッシュ戦略.md`

## 3. リバースプロキシキャッシュ

### 概要

CDN の手前、あるいはオリジンの前段に置かれるキャッシュ。

### 代表例

- Nginx（`proxy_cache`）
- Varnish
- Apache Traffic Server

### 特徴

- **自前で持てる**（オンプレや社内LAN向き）
- 細かい制御が可能
- VCL（Varnish）のような強力な DSL

### 向き

- CDN を使わない構成
- 認証付きだが読み取り多いページ
- オリジンの前段での負荷軽減

---

## 4. アプリケーションインメモリキャッシュ

### 概要

**アプリのプロセス内メモリ** に保存するキャッシュ。

### 例

- Java: Caffeine、Guava Cache
- Node.js: `lru-cache` パッケージ
- Python: `functools.lru_cache`
- .NET: `MemoryCache`

### 特徴

- **最速**（ネットワーク不要、プロセス内アクセス）
- シンプルに組み込める

### 弱点

- **プロセス間で共有されない**（複数サーバだとそれぞれ別キャッシュ）
- プロセス再起動で消える
- メモリサイズに上限

### 向き

- 1リクエスト内での繰り返しアクセス
- 参照多く、変更が少ないマスターデータ（商品カテゴリ等）
- 本当に頻繁にアクセスするもの

---

## 5. 分散キャッシュ（アプリ外の専用キャッシュサーバ）

### 概要

複数のアプリサーバから **共有アクセス** できるキャッシュサーバ。

### 代表例

- **Redis**（最も人気）
- Memcached（シンプル、超高速）
- Hazelcast
- Apache Ignite

### 特徴

- 複数サーバで共有
- 永続化オプション（Redis）
- Pub/Sub、Sorted Set 等の高度なデータ構造（Redis）

### 向き

- マルチサーバ構成
- セッション情報の共有
- DBクエリ結果のキャッシュ
- レートリミット、分散ロック

### 弱点

- ネットワーク越しなので、インメモリキャッシュより若干遅い
- キャッシュサーバー自体の運用が必要

→ 詳細は `Redis設計パターン.md`

---

## 6. DB クエリキャッシュ

### 概要

**DB エンジン自体** が内部で持つキャッシュ。

### 例

- PostgreSQL: shared_buffers（バッファプール）
- MySQL: InnoDB Buffer Pool、Query Cache（8.0 で廃止）
- Oracle: Result Cache

### 特徴

- DB が自動で管理
- アプリは意識しない
- **チューニングで効果大**

### 弱点

- DB 再起動で消える
- クラスタで共有されないこともある

### アプリ側での活用

- DB チューニングで `shared_buffers` を増やす
- ウォームアップでアクセスパターンに載せる

---

## 7. クエリ結果キャッシュ（アプリレベル）

アプリが「このクエリの結果」を外部キャッシュ（Redis等）に置く。

```python
def get_top_products():
    key = "top_products"
    cached = redis.get(key)
    if cached:
        return json.loads(cached)
    result = db.query("SELECT ... ORDER BY sales DESC LIMIT 10")
    redis.setex(key, 300, json.dumps(result))
    return result
```

Cache-aside パターンの典型。

---

## 8. HTTP レスポンスキャッシュ

### 概要

アプリがレスポンス全体をキャッシュ。次回同じリクエストなら、**処理せずに既存レスポンス返却**。

### 例

- Next.js / SSR フレームワークの ISR（Incremental Static Regeneration）
- Django の cache middleware
- Ruby on Rails の page / action caching

### 特徴

- DB/ビジネスロジックを全く動かさない
- **キャッシュヒット時は爆速**

---

## 層の組み合わせ例

### 典型的な Web アプリ

```
ブラウザキャッシュ（画像、JS、CSS）
       ↓
CDN キャッシュ（静的 + 動的 SSR）
       ↓
ロードバランサ
       ↓
アプリのメモリキャッシュ（マスターデータ）
       ↓
Redis（セッション、クエリ結果）
       ↓
DB バッファプール
       ↓
Disk
```

ユーザーリクエストは、**上から順に** キャッシュをチェックし、見つかった時点で応答。

### E コマース商品ページ

| データ | キャッシュ位置 | TTL |
|-------|-------------|-----|
| 画像 | ブラウザ + CDN | 30日 |
| JS/CSS | ブラウザ + CDN | 永続（ハッシュ付ファイル名） |
| HTML | CDN（SSR結果） | 60秒 |
| 商品データ | Redis | 5分 |
| カート情報 | Redis（セッション） | 30分 |
| 在庫 | Redis or DB直 | 短い or リアルタイム |

## どの層に置くべきか

### 優先度（最大効果順）

1. **ブラウザ + CDN**（ユーザーに最も近い、効果最大）
2. **アプリメモリ or Redis**（DB 負荷軽減）
3. **DB バッファプール**（自動、チューニングで）

### 判断基準

- **共有範囲**: 全ユーザーで同じ → 上流（CDN）、特定ユーザー → Redis/ブラウザ
- **変更頻度**: 滅多に変わらない → 長期 CDN、頻繁 → 短TTL or アプリ
- **データサイズ**: 大きい → CDN / Redis、小さく多い → インメモリ
- **パーソナライズ**: あり → Redis 以下、なし → CDN

---

## 落とし穴

### 1. 多層キャッシュで無効化が困難

CDN、Redis、インメモリ、DB に同じデータが存在 → **全部パージしないと一貫しない**。
→ TTL を短めにする、無効化イベントを発行する等で対策。

### 2. 認証付きコンテンツを CDN でキャッシュ

- `Cache-Control: private` or `no-store` を設定しないと、**他ユーザーに漏洩**
- 最重要の事故類型

### 3. 長すぎる CDN TTL

- デプロイしても古いコンテンツが配信され続ける
- ファイル名ハッシュ化 + HTML の短TTL で対応

### 4. アプリインメモリに重要データを置いて、スケール時に不整合

- 複数プロセスで別々のキャッシュ → 同じキーで違う値
- → **Redis 等の共有キャッシュ** に寄せる

### 5. DB キャッシュ任せで満足

- DB 自動キャッシュは強力だが限界あり
- アプリ層でも工夫すべき

## まとめ

- キャッシュは **リクエスト経路の各層** に配置可能
- 上流（ブラウザ・CDN）ほど **効果大、制御難**
- 下流（DB）ほど **効果控えめ、自動**
- 典型的な Web アプリは **ブラウザ → CDN → アプリメモリ → Redis → DB** の多層
- **認証付きコンテンツを CDN でキャッシュしない**（漏洩リスク）
- 変更頻度 × 共有範囲 × サイズ × パーソナライズ で層を選ぶ
- 多層キャッシュは **無効化が難しく** なるので注意
