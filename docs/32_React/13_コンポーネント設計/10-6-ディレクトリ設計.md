# 10-6. ディレクトリ設計（features/components/hooks/lib/utilsの線引き）

## 🎯 この章で学ぶこと

- 何をどこに置くか（features / components / hooks / lib / utils）
- 規模に応じたフォルダ構成
- 「機能でまとめる」考え方

---

## 🧭 前提：フォルダ名より「探しやすさ」と「依存方向」

React 自体は「`src` の下は必ずこうしなさい」を決めていません。迷ったときは次の軸で決めると破綻しにくいです。

1. **3ヶ月後の自分（/他人）が探しやすいか**
2. **依存が正しい方向か**（UI → hooks/services → lib/utils/types/config… のように、上位が下位に依存する）

また、**最初は種類別で開始**し、育ったら **機能別（`features/`）へ寄せる**、が現実的な移行パターンです。

---

## 📖 主な選択肢

### ① 種類別（小規模）

```text
src/
├─ components/
├─ pages/
├─ hooks/
├─ utils/
└─ App.jsx
```

シンプル。アプリ初期はこれで十分。

### ② 機能別（features-based、中〜大規模）

```text
src/
├─ features/
│  ├─ auth/
│  │  ├─ components/
│  │  ├─ hooks/
│  │  ├─ api.ts
│  │  └─ index.ts
│  ├─ products/
│  └─ orders/
├─ components/   # 共通UI
├─ hooks/        # 共通フック
├─ lib/          # 外部ライブラリラッパー
├─ utils/        # 純粋関数
└─ App.jsx
```

機能（feature）ごとに**コンポーネント・フック・APIをまとめる**。

---

## 💡 各フォルダの役割

### features/

「**機能のかたまり**」。1つの feature は完結している（独自のコンポーネント・フック・API）。

例：`features/auth/`
- `LoginForm.jsx`、`SignupForm.jsx`
- `useAuth.ts`、`useCurrentUser.ts`
- `api.ts`（APIクライアント）

別featureから使うなら **`index.ts`** で公開：

```ts
// features/auth/index.ts
export { useAuth } from './hooks/useAuth';
export { LoginForm } from './components/LoginForm';
```

### components/

**アプリ全体で共通の UI**（Button, Modal, Input...）。機能に依存しない。

### hooks/

**アプリ全体で共通のカスタムフック**（useDebounce, useLocalStorage...）。

（カスタムフックの抽出基準・実装パターンは [[10-3-カスタムフック]] を参照。）

### lib/

**外部ライブラリのラッパー**や設定。

例：

- `lib/queryClient.ts`（TanStack Query設定）
- `lib/axios.ts`（axiosインスタンス）
- `lib/dayjs.ts`（dayjs拡張）

### utils/

**副作用なしの純粋関数**。データ変換・バリデーション・フォーマット。

例：

- `formatDate(date)`、`formatCurrency(num)`
- `parseUrl(url)`、`groupBy(arr, key)`

---

## 💡 lib と utils の違い

| | lib | utils |
| --- | --- | --- |
| 内容 | 外部依存あり、設定 | 純粋関数 |
| 例 | axiosインスタンス | formatDate |
| 副作用 | あり得る（接続など） | なし |

迷ったら：**外部ライブラリを使うなら lib、純JSで完結するなら utils**。ただしテンプレートやチームによっては `lib` と `utils` が同義で扱われることも多いです（README があれば最優先）。

### `lib/` に置きがちなもの（例）

- **純粋なヘルパー**（日付・数値・文字列の整形、単位変換、比較関数）
- **軽いデータ変換**（API の生データ → 画面用の形へのマッピング）
- **外部ライブラリの薄いラッパー**（例：クラス名結合 `cn`）

典型例（`cn`）：

```ts
import { clsx, type ClassValue } from "clsx";
import { twMerge } from "tailwind-merge";

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs));
}
```

### `utils/` に置きがちなもの（例）

- **副作用がない／局所的でテスト可能**な関数（できれば純粋関数）
- **何度も出てくる同系統の条件・計算**（ただしドメイン規則として肥大化するなら別モジュールへ）

### `lib` / `utils` に置かない方がよいもの（目安）

| 置きたい内容 | 向く置き場（目安） |
|--------------|--------------------|
| **HTTP（fetch/axios）、API URL** | `services/` / `api/` / `repositories/` など |
| **`useState` / `useEffect` を使う処理** | `hooks/`（カスタムフック） |
| **画面の表示（JSX）** | `components/` |
| **URL・ルーティングに強く結びつく処理** | そのルート専用の近く or `lib/routing` 等“意思を持った名前” |
| **環境変数に依存する値** | `config/` / `env` 用モジュール（例：`src/config/env.ts`） |
| **Zod 等のスキーマ＋型推論** | `schemas/` / `validations/`（機能専用なら feature 内） |

### 例：Vite の `BASE_URL` みたいな「環境値」はどこ？

`import.meta.env` のような **ビルドツール依存**は、`lib/utils.ts` に散らすより `config` 側に閉じると移植性が上がります。

```ts
export const base = import.meta.env.BASE_URL.replace(/\/$/, "");
```

## 💡 components 直下と features/xxx/components の違い

| | 共通 (components/) | 機能内 (features/xxx/components) |
| --- | --- | --- |
| 役割 | 汎用 UI | この機能専用 |
| 例 | Button, Modal, Spinner | LoginForm, ProductCard |
| 移動条件 | 他機能からも使う | 1機能で完結 |

## 🧾 「どのフォルダに、どの処理を書くか」早見表

| 置きたい内容 | 向いている置き場 | 書くものの例 |
|-------------|-----------------|--------------|
| 画面表示・マークアップ | `components/`, `pages/` | JSX を返すコンポーネント |
| 複数箇所で同じ state・副作用 | `hooks/` | `useXxx()`（状態＋操作関数） |
| HTTP・外部API | `services/` / `api/` | `async function`（入出力が明確） |
| 純粋な計算・整形 | `lib/`, `utils/` | `formatDate(d)` など |
| 型 | `types/` 等 | `type` / `interface` |
| ツリー横断の共有値 | `context/`, `providers/` | Provider / `createContext` |
| グローバル状態 | `store/` 等 | store / action / selector |

## 💡 import path の整理

長いパスは alias で短く：

```ts
// vite.config.ts
import path from 'path';
export default {
  resolve: {
    alias: {
      '@': path.resolve(__dirname, 'src'),
    },
  },
};
```

```ts
// before
import { Button } from '../../../components/Button';

// after
import { Button } from '@/components/Button';
```

---

## ❌ よくある間違い

### features 内で別 features を直接 import

```ts
// features/products/ProductList.tsx
import { useAuth } from '../auth/hooks/useAuth'; // ❌
```

→ ✅ 公開窓口経由：`from '@/features/auth'`

→ 機能間の境界が壊れると、循環依存・複雑化の原因に。

### 小規模なのに features を作る

→ ファイルが少ないなら components/ pages/ で十分。

### components/ にロジック付きを置く

→ 共通コンポーネントは propsだけで動くべき。

---

## ✅ ベストプラクティス

1. **小さいうちは種類別**（components/hooks）
2. **大きくなってきたら features 別**
3. **機能間は index.ts で公開**
4. **alias で import path を短く**
5. **「これは機能専用？共通？」**を毎回考える

- 小規模：種類別（components/hooks/utils）
- 中〜大：features別 + 共通フォルダ
- features は index.ts で公開
- lib と utils を分ける
