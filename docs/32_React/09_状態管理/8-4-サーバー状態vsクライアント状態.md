# 8-4. サーバー状態 vs クライアント状態（分ける）

## 🎯 この章で学ぶこと

- 「サーバー状態」と「クライアント状態」の違い
- なぜ分けて考えるとシンプルになるのか
- それぞれに向いた管理方法

---

## 📖 概念の説明

### 状態には2種類ある

| 種類 | 例 | 真実の源 |
| --- | --- | --- |
| **サーバー状態** | ユーザー一覧、商品データ | サーバ |
| **クライアント状態** | モーダル開閉、フォーム入力中 | ブラウザ（React） |

### サーバー状態の特徴

- **真実はサーバ側**にある（DBなど）
- いつ古くなるか分からない（**鮮度**の問題）
- 取得・キャッシュ・再取得が必要
- 失敗・遅延がある

### クライアント状態の特徴

- アプリの中だけで意味がある
- いつ・誰が変えるか自明
- 失敗しない、瞬時

---

## 💡 なぜ分けるか

混ぜて管理すると地獄になる。

### ❌ 全部 useState で混ぜる

```jsx
function App() {
  const [users, setUsers] = useState([]);          // サーバー
  const [loading, setLoading] = useState(false);   // 取得中
  const [error, setError] = useState(null);
  const [modalOpen, setModalOpen] = useState(false); // クライアント
  const [searchText, setSearchText] = useState('');  // クライアント

  useEffect(() => {
    setLoading(true);
    fetch('/api/users')
      .then((r) => r.json()).then(setUsers)
      .catch(setError).finally(() => setLoading(false));
  }, []);
}
```

→ ロジックが複雑、キャッシュなし、再取得は手動、競合状態の対策が必要。

### ✅ 分けて管理

```jsx
function App() {
  // サーバー状態：TanStack Query に任せる
  const { data: users, isLoading, error } = useQuery({
    queryKey: ['users'],
    queryFn: () => fetch('/api/users').then((r) => r.json()),
  });

  // クライアント状態：useState で
  const [modalOpen, setModalOpen] = useState(false);
  const [searchText, setSearchText] = useState('');
}
```

→ サーバ状態の処理はライブラリが担当。クライアント状態だけシンプルに管理。

---

## 💻 サーバー状態の管理ツール

### TanStack Query（旧 React Query）

```jsx
import { useQuery, useMutation } from '@tanstack/react-query';

// 取得
const { data, isLoading, error } = useQuery({
  queryKey: ['user', id],
  queryFn: () => fetch(`/api/users/${id}`).then((r) => r.json()),
});

// 作成・更新
const mutation = useMutation({
  mutationFn: (newUser) => fetch('/api/users', {
    method: 'POST',
    body: JSON.stringify(newUser),
  }),
});

mutation.mutate({ name: '太郎' });
```

→ 自動でキャッシュ、再取得、エラー処理。詳しくは [[7-5-データ取得ライブラリ]]。

### SWR（Vercel製、シンプル）

```jsx
import useSWR from 'swr';

const { data, error, isLoading } = useSWR('/api/user', fetcher);
```

## 💻 クライアント状態の管理ツール

| ツール | 使うとき |
| --- | --- |
| **useState** | コンポーネント内 |
| **useReducer** | 複雑な更新ロジック |
| **Context** | アプリ全体で共有（テーマなど） |
| **Zustand** | 中規模、シンプル |
| **Redux Toolkit** | 大規模、開発者ツール充実 |
| **Jotai / Recoil** | atomベース、細かい制御 |

---

## 💻 区別の例

| データ | 種類 |
| --- | --- |
| 商品リスト（API取得） | サーバー |
| 検索キーワード | クライアント |
| 検索結果 | サーバー |
| モーダル表示中？ | クライアント |
| ログイン中のユーザー | サーバー（取得） + クライアント（保持） |
| ダークモード？ | クライアント（localStorage） |
| カートの中身 | クライアント or サーバー（要件次第） |

---

## ❌ よくある間違い

### サーバ状態を Redux に入れる

→ Reduxにキャッシュロジックを書くと複雑化。**TanStack Queryに任せる**。

### クライアント状態をAPIに毎回投げる

→ モーダル開閉までAPI 1回呼ぶ必要はない。**ローカルで完結**させる。

### 取得した直後に setState で別管理

```jsx
const { data } = useQuery(...);
const [users, setUsers] = useState([]);
useEffect(() => setUsers(data), [data]); // ❌ 二重管理
```

→ ✅ data を直接使う。

---

## ✅ ベストプラクティス

1. **取得・送信は TanStack Query / SWR**
2. クライアント状態は **useState / useReducer**
3. アプリ共有は **Context** か **Zustand**
4. **同じデータを2箇所で持たない**
5. **真実の源はどこか**を毎回意識

---

## 🔬 実践演習

シンプルなブログ画面を考える：

- 記事一覧（サーバー）
- 検索キーワード（クライアント）
- 並び順（クライアント）
- お気に入り（サーバー or クライアント？）

各データを どの管理ツールで持つか分類してみる。

---

## 📝 まとめ

- 状態は「サーバー」と「クライアント」に分ける
- サーバー状態は TanStack Query / SWR
- クライアント状態は useState / Context / Zustand
- 二重管理しない、真実の源を1つに
