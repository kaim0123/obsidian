## 詳しい要約

**テーマ：データ取得は useEffect ではなく useSWR で行う**

useEffect でのデータ取得は記述が複雑でキャッシュも効かないため、キャッシュ・ローディング・エラーハンドリング・再検証をまとめて扱える **useSWR** を使おう、という中級者向け解説。カスタムフック化すれば props のバケツリレーなしに各コンポーネントから同じデータを使える。

---

### useEffect でのデータ取得の問題点

- 典型例：依存配列を空にした useEffect 内で fetch し、`user`・`error`・`loading` の3つの状態変数を useState で管理する。
- 動きはするが、デメリットは2つ。
  - **ロジックが複雑**：状態変数が増え、エラーハンドリングの記述も長くなる。
  - **キャッシュされない**：リロードのたびに毎回 API へ fetch する。キャッシュを自前で実装するとさらに煩雑。

### useSWR の仕組み

- 初回アクセスはサーバーに fetch するが、返したデータをブラウザのメモリに **キャッシュ** する。再アクセス時はキャッシュを返すので速い。
- キャッシュが古くなった場合は再度 fetch して更新する **再検証（revalidate）** がデフォルトで行われる。

### 使い方

- `npm i swr` でインストール。`useSWR(key, fetcher)` で **data / error / isLoading** を1行で受け取れる。
- 第1引数はキャッシュのキー（API URL）、第2引数は Promise を返す **fetcher**（fetch でも axios でもよい）。
- Next.js 13 の App Router ではデフォルトがサーバーコンポーネントなので、`"use client"` の指定が必要。
- JSONPlaceholder のダミー API で、useEffect 版より大幅に短く書き換えられることを実演。

### カスタムフック化で状態管理的に使う

- `useUser(id)` のようなカスタムフックを作り、`{ user, isLoading, isError }` を返す。
- 各コンポーネント（例：ナビバーとアバター）で `useUser` を呼ぶだけでよく、親で取得して props で渡す必要がない。Redux のストアや Context API のように使える。
- 複数のコンポーネントで呼んでも、同じキーなら **重複排除・キャッシュ共有** によりリクエストは1回で済む。

### 再検証のオプション

- フォーカス時・タブ切り替え時・ネットワーク再接続時に自動で再検証する。
- `refreshInterval`（例：1000ms）で定期的な再検証が可能。
- `revalidateOnReconnect: false` などで個別に無効化できる（基本はデフォルトのままでよい）。
- 似た機能を持つライブラリとして **React Query（TanStack Query）** もあり、使いやすい方を選べばよい。

### まとめ

- useEffect でのデータ取得は状態管理が煩雑でキャッシュも効かない。
- useSWR はキャッシュ・ローディング・エラー・再検証を1行で扱え、パフォーマンスも上がる。
- カスタムフック化すると、props を渡さずにどのコンポーネントからも同じデータを共有できる。
