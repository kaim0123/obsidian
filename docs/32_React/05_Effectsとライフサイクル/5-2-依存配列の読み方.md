# 5-2 依存配列の読み方（いつ走るか）

## 🎯 この章で学ぶこと

- `useEffect` の第2引数「依存配列」が何のためにあるかを理解できます
- 依存配列の3つのパターン（省略・空配列・値あり）の挙動の違いを覚えられます
- 何を依存配列に入れて、何を入れなくていいかの判断ができるようになります
- ESLintの `exhaustive-deps` ルールが何を見ているかが分かります
- 「依存が増えすぎる問題」への対処法を知ることができます

## 📖 概念の説明

### 依存配列ってなに？

`useEffect` の第2引数に渡す配列が **依存配列（dependency array）** です。

```jsx
useEffect(() => {
  // 副作用の処理
}, [a, b, c]); // ← これが依存配列
```

これは「**この配列の中身が前回と変わっていたら、もう一度Effectを走らせてね**」という意味です。Reactは前回のレンダリング時の値と今回の値を順番に比較して、1つでも違っていたら副作用を再実行します。

例えるなら、**配達員にチェックリストを渡しておく** ようなものです。「このリストの内容が変わったら、もう一度倉庫まで取りに来てね」と伝えておくイメージです。リストの内容が変わらなければ、配達員はわざわざ動きません。

### 3つのパターン

依存配列の書き方は大きく分けて3パターンあります。

| 書き方 | いつ実行される？ | よく使う場面 |
|---|---|---|
| `useEffect(fn)` 省略 | **毎レンダー** 実行 | ほぼ使わない（バグの元） |
| `useEffect(fn, [])` 空配列 | **マウント時に1回だけ** | 初期化処理 |
| `useEffect(fn, [a, b])` 値あり | **a か b が変わったら** | 値の変化に追従する処理 |

### 「変わった」の判定はどうやってる？

Reactは依存配列の中身を `Object.is` で比較します。これは「**`===` とほぼ同じ**」と覚えておけば大丈夫です。つまり、

- 数値・文字列・真偽値：値が同じなら「変わってない」
- オブジェクト・配列・関数：**参照（メモリ上の場所）が同じなら** 「変わってない」

ここがハマりどころで、毎レンダーで新しいオブジェクトや配列を作っていると、**中身が同じでも「変わった」と判定されて毎回Effectが走ります**。

```jsx
// ❌ 毎レンダーで {} は新しいオブジェクトになる
useEffect(() => {
  console.log('走る');
}, [{ id: 1 }]); // 毎回違う参照 → 毎回実行される
```

### 「何を入れるべきか」のルール

ルールはシンプルです。

> **Effectの内側で使っている、コンポーネントスコープのすべての値（state, props, それらから派生した変数）を依存配列に入れる**

「使っているのに入れない」と、Effectの中で **古い値（stale value）** を見続けるバグになります。これは次の章「よくあるバグ集」で詳しく扱います。

逆に、入れなくていいものもあります。

- `useState` の更新関数（`setCount` など）：Reactが安定参照を保証している
- `useRef` の戻り値（`ref` 自体）：これも安定
- import した関数や定数：コンポーネントスコープではない

## 🔍 深掘り：props→stateに「コピー」したいときの依存配列

`useState(props.x)` のように **propsを初期値としてstateに入れる** とき、よくある落とし穴があります。

### よくある失敗：初回だけコピーされて、その後props更新が反映されない

```jsx
function ReservationList({ reservations }) {
  const [currentReservations, setCurrentReservations] = useState(reservations);
  // これだけだと、reservations が更新されても currentReservations は更新されない
}
```

`useState` の初期値は「初回レンダーで1回だけ」使われるため、親から新しい `reservations` が渡っても子のstateは自動同期されません。

### 対処：propsの変化に追従して同期する

```jsx
import { useEffect, useState } from 'react';

function ReservationList({ reservations }) {
  const [currentReservations, setCurrentReservations] = useState(reservations);

  useEffect(() => {
    setCurrentReservations(reservations);
  }, [reservations]);

  return (
    <ul>
      {currentReservations.map(r => <li key={r.id}>{r.name}</li>)}
    </ul>
  );
}
```

ただし、このパターンは「本当にstateに持つ必要があるか？」をまず疑いましょう。単に表示するだけなら、propsをそのまま使う方がシンプルです（編集・並び替え・フィルタなどで子側の独自状態が必要なときに限定して使うのが安全です）。

## 💻 コード例

### 例1：3パターンの違いを実感する

```jsx
import { useEffect, useState } from 'react';

function DemoEffects() {
  const [count, setCount] = useState(0);
  const [other, setOther] = useState(0);

  // 1. 依存配列なし → 毎レンダー実行
  useEffect(() => {
    console.log('A: 毎レンダー走る');
  });

  // 2. 空配列 → マウント時1回だけ
  useEffect(() => {
    console.log('B: マウント時だけ走る');
  }, []);

  // 3. countに依存 → countが変わったときだけ
  useEffect(() => {
    console.log('C: countが変わったとき走る', count);
  }, [count]);

  return (
    <div>
      <p>count: {count} / other: {other}</p>
      <button onClick={() => setCount(count + 1)}>count++</button>
      <button onClick={() => setOther(other + 1)}>other++</button>
    </div>
  );
}
```

実際に動かしてみてください。「count++」を押すとA, B（初回のみ）, C が動き、「other++」を押すと A だけが走るはずです。

### 例2：propsの変化に追従する

```jsx
import { useEffect, useState } from 'react';

function UserCard({ userId }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    // userIdが変わるたびに、新しいユーザー情報を取得し直す
    console.log(`fetching user: ${userId}`);
    // 実際にはここで fetch を呼ぶ
  }, [userId]); // ← userIdが依存

  return <div>{user?.name}</div>;
}
```

「親から渡されたIDが変わったら取り直す」という、もっとも実用的なパターンです。

### 例3：オブジェクトを依存に入れたいときの落とし穴

```jsx
// ❌ 親から毎回新しいオブジェクトが来ると、毎レンダーEffectが走る
function Bad({ filter }) {
  useEffect(() => {
    console.log('再取得', filter);
  }, [filter]); // filterが毎回新しい参照だと、毎回実行
}

// 親側
<Bad filter={{ status: 'active' }} /> // 毎レンダー新しいオブジェクト

// ✅ プリミティブに分解する
function Good({ status }) {
  useEffect(() => {
    console.log('再取得', status);
  }, [status]); // 文字列なので参照問題が起きない
}

// または useMemo で参照を安定化させる
function Parent() {
  const filter = useMemo(() => ({ status: 'active' }), []); // 安定参照
  return <Good filter={filter} />;
}
```

### 例4：「すべての依存を正しく入れる」例

```jsx
function Search({ query, pageSize }) {
  const [results, setResults] = useState([]);

  useEffect(() => {
    // 内側で query と pageSize を使っている
    fetch(`/api/search?q=${query}&size=${pageSize}`)
      .then(r => r.json())
      .then(setResults);
  }, [query, pageSize]); // ← 使っている2つを両方入れる

  return <ul>{results.map(r => <li key={r.id}>{r.title}</li>)}</ul>;
}
```

`setResults` は `useState` の更新関数なので、依存に入れなくてOKです（Reactが安定を保証）。

### 例5：関数を依存に入れる場合

```jsx
function Parent() {
  // ❌ Parentが再レンダーするたびに新しい関数が作られる
  const onUpdate = () => console.log('updated');
  return <Child onUpdate={onUpdate} />;
}

function Child({ onUpdate }) {
  useEffect(() => {
    onUpdate();
  }, [onUpdate]); // 親が再レンダーするたびに走ってしまう
}

// ✅ useCallback で関数の参照を安定させる
function Parent() {
  const onUpdate = useCallback(() => console.log('updated'), []);
  return <Child onUpdate={onUpdate} />;
}
```

関数を渡すときは `useCallback` で参照を固定するのが定番です。

## ❌ よくある間違い

### 1. 警告を消すために依存を「うそつき」する

```jsx
// ❌ 使ってるのに入れない（嘘の依存配列）
useEffect(() => {
  console.log(count);
}, []); // countは使ってるのに空配列！
```

これをやるとESLintが警告を出します。`// eslint-disable-next-line` で消すのは99%の場合バグの始まりです。

### 2. オブジェクトリテラルを直接依存に入れる

```jsx
useEffect(() => {
  fetch('/api', { headers: { 'X-Token': token } });
}, [{ token }]); // ❌ 毎回新しいオブジェクト
```

依存にはプリミティブ（文字列・数値・真偽値）を入れるのが基本です。

### 3. setStateを依存に入れる

```jsx
useEffect(() => {
  setCount(1);
}, [setCount]); // ❌ 不要、Reactが安定を保証
```

`setCount` は変わらないので、入れる必要はありません。

### 4. 「初回だけ実行したい」ために嘘をつく

```jsx
// ❌ propsを使ってるのに空配列にする
useEffect(() => {
  fetch(`/api/${userId}`);
}, []); // userIdが変わっても再取得されない！
```

「初回だけ」を実現したいなら、**そもそもEffectの設計を見直しましょう**。多くの場合、依存に正しく入れる方が正解です。

## ✅ ベストプラクティス

1. **ESLintの `react-hooks/exhaustive-deps` を必ず有効に**：これが依存配列の警備員です。
2. **使っている値はすべて入れる**：例外を作りたくなったら、設計を疑います。
3. **オブジェクト・配列・関数は参照に注意**：プリミティブに分解するか、`useMemo`/`useCallback` で固定。
4. **依存が多すぎたら関数を切り出す**：Effectが大きくなりすぎたら、カスタムフックに分離するサイン。
5. **「依存を減らすために嘘をつく」のは絶対NG**：それはバグを未来に先送りしているだけです。

## 🔬 実践演習

### お題：依存配列の挙動を観察する

3つの `useEffect`（依存なし、空配列、`[count]`）を持つコンポーネントを作り、ボタンを押すたびにどれが走るかをコンソールで確認してみましょう。

### 発展課題

- 親から渡された `filter`（オブジェクト）を依存に入れて、無限に走ってしまう状況を再現してみましょう
- それを `useMemo` で解決してみましょう

## 📝 まとめ

- 依存配列は「**この値が変わったら再実行**」というルールを書く場所です
- 省略・空配列・値あり、の3パターンで挙動が大きく変わります
- 比較は `Object.is`（≒ `===`）で行われます
- オブジェクト・配列・関数は **参照** で比較されるので注意
- 「使っているものは全部入れる」が鉄則。例外を作るなら設計を見直しましょう
