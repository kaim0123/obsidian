# 17-5 UI事故（ボタンとスクロール等の「なぜ？」）

## 🎯 この章で学ぶこと

- ボタンが反応しない・二重送信される・押せない、といった「ボタン事故」の定番
- スクロールがおかしい（飛ぶ、戻る、効かない）の原因
- z-index / overflow / position の罠
- フォーカスが迷子になるアクセシビリティ事故
- 画面崩壊（CSS）の切り分け方法

## 📖 概念の説明

### UI 事故とは

クラッシュはしないが、ユーザーが「なんで？」と感じる小さな不具合の総称。レビューや QA の段階では見逃されやすく、本番で SNS に晒される類のバグです。

### 「ボタン」に潜む罠

ボタン 1 つでも

- クリックの伝播
- 二重送信
- フォームの type=submit
- disabled の扱い
- スマホでのダブルタップ

など、地味な落とし穴が多数あります。

### スクロールに潜む罠

- ページ遷移後にスクロール位置が引き継がれてしまう
- モーダルを開いたら背面もスクロールする
- iOS の慣性スクロール
- `position: sticky` が効かない

### z-index / overflow

- `overflow: hidden` の中では `position: sticky` が効かない
- `transform` を持つ親は `position: fixed` の基準になる
- `z-index` は同じ stacking context 内でしか比較されない

これらは知らないと一日中ハマるので、症状から即仮説を立てられるようにしておきます。

## 💻 コード例

### 症状: ボタンを連打すると二重投稿される

**原因**: 1 回目のリクエストが終わる前に 2 回目を受け付けている。

```tsx
function PostButton() {
  const [busy, setBusy] = useState(false);
  async function onClick() {
    if (busy) return;
    setBusy(true);
    try {
      await api.post();
    } finally {
      setBusy(false);
    }
  }
  return (
    <button onClick={onClick} disabled={busy}>
      {busy ? "送信中..." : "投稿"}
    </button>
  );
}
```

React Query の `useMutation` を使うなら `mutation.isPending` を `disabled` に渡すだけ。

### 症状: フォーム送信ボタンを押すとページがリロードされる

**原因**: `<button>` の既定の `type` は `submit`。フォーム外なら問題ないが、`<form>` の中だとデフォルトで送信される。

```tsx
// ❌
<form onSubmit={save}>
  <button onClick={cancel}>キャンセル</button>
</form>;

// ✅
<button type="button" onClick={cancel}>キャンセル</button>;
```

`type="button"` を明記する。

### 症状: モーダル内のボタンを押すと背面のリンクも動く

**原因**: イベントの伝播。モーダルの背景のクリックがリンクに到達している。

```tsx
<div className="overlay" onClick={close}>
  <div className="dialog" onClick={(e) => e.stopPropagation()}>
    {children}
  </div>
</div>
```

`stopPropagation` で背景に伝わらないようにする。

### 症状: スマホで disabled なボタンが押せた

iOS Safari では `pointer-events: none` を付けないと、`disabled` だけでは反応してしまうことがあります。

```css
button[disabled] {
  pointer-events: none;
  opacity: 0.5;
}
```

### 症状: ダブルタップで意図せずズームする

```css
button {
  touch-action: manipulation; /* ダブルタップズームを無効化 */
}
```

### 症状: ページ遷移後、前のページのスクロール位置が残る

**原因**: SPA はページがアンマウントされず再描画なので、ブラウザがスクロール位置を「次のページ」に引き継ぐ。

```tsx
// React Router 用
function ScrollToTop() {
  const { pathname } = useLocation();
  useEffect(() => {
    window.scrollTo(0, 0);
  }, [pathname]);
  return null;
}
```

ルートに 1 つ置けば全ページで効く。

### 症状: モーダルを開いたら背面もスクロールできてしまう

```tsx
useEffect(() => {
  const original = document.body.style.overflow;
  document.body.style.overflow = "hidden";
  return () => {
    document.body.style.overflow = original;
  };
}, []);
```

iOS では `position: fixed` で固定するパターンも併用するとさらに堅い。

### 症状: position: sticky が効かない

**原因 1**: 祖先に `overflow: hidden` または `overflow: auto` がある。
**原因 2**: sticky 要素に `top` 値が指定されていない。

```css
header {
  position: sticky;
  top: 0; /* 必須 */
}
.parent {
  /* overflow: hidden を付けない！ */
}
```

### 症状: position: fixed が画面ではなく親基準になる

```css
.parent {
  transform: translateZ(0); /* これがあると fixed の基準が parent になる */
}
.modal {
  position: fixed; /* 画面いっぱいになるはずが…なってない */
}
```

`transform`, `filter`, `perspective`, `will-change` などは新しい stacking context を作ります。

### 症状: z-index が効かない

```css
.a {
  z-index: 99999;
} /* それでも下に行く */
```

**確認ポイント**:

1. 親要素の `position` が `static`（既定）だと z-index は効かない → `position: relative` 等にする
2. 別の stacking context にいる場合、その context 内の最大値しか持たない
3. 兄弟要素の階層を意識する

### 症状: クリックが透明な要素にブロックされる

DevTools で要素を hover して、目的の要素の上に何か重なっていないか確認。`pointer-events: none` で透過させる手も。

### 症状: フォーカスがボタンを押した後に消える

フォームを保存して画面が切り替わると、次の操作対象が分からなくなることがあります。

```tsx
const okButtonRef = useRef<HTMLButtonElement>(null);
useEffect(() => {
  okButtonRef.current?.focus();
}, []);
```

モーダルを開いたら最初のフォームにフォーカス、閉じたら開いたボタンに戻す、が定番。

### 症状: 画面が縦にビヨーンと長い

**よくある原因**: 全体に `100vh` を使うと iOS のアドレスバー込みの高さで計算され、結果として下にスクロールが残る。

```css
.full {
  height: 100vh; /* ❌ */
  height: 100svh; /* ✅ small viewport height */
}
```

`100svh` / `100lvh` / `100dvh` を使い分ける。

### 症状: テーブルのレイアウトが壊れる

```css
table {
  table-layout: fixed; /* 列幅を固定して長文で崩れない */
  width: 100%;
}
td {
  overflow: hidden;
  text-overflow: ellipsis;
  white-space: nowrap;
}
```

### CSS デバッグの神コマンド

```css
* {
  outline: 1px solid red !important;
}
```

すべての要素に枠線を表示する裏技。重なりや謎の余白の正体がすぐ分かる。

## ❌ よくある間違い

### 1. ボタンに `<div onClick>` を使う

キーボードで押せず、スクリーンリーダーでも認識されません。`<button>` を使う。

### 2. `e.stopPropagation()` を多用する

過剰なバブル止めはイベント設計を歪めます。本当に必要なときだけ使う。

### 3. `!important` で z-index 戦争

根本解決になりません。stacking context を見直す。

### 4. モーダル外側の onClick で close するだけ

ESC キーや背景タップだけ対応して、フォーカストラップ（モーダル外にフォーカスが移らないようにする）を実装しないと、アクセシビリティ的に問題があります。`focus-trap-react` 等のライブラリを使うと安全。

### 5. スマホ確認をエミュレータだけで済ます

DevTools のレスポンシブモードでは検出できないバグ（iOS の慣性スクロール、ホームバーの高さなど）があります。実機で 1 度は触る。

## ✅ ベストプラクティス

1. **`<button type="button">` を意識**: フォーム内では特に明示。
2. **二重送信は disabled でブロック**: `useMutation.isPending` を活用。
3. **スクロール制御はカスタムフックに**: `useLockBodyScroll` 等を 1 つ作って使い回す。
4. **デザインの実装前に、`-1px solid red` で枠を全付け**: レイアウト把握が一瞬。
5. **アクセシビリティを後回しにしない**: フォーカス管理・ARIA は最初から組み込む。

## 📝 まとめ

- ボタン事故は「type, disabled, propagation」の 3 点を点検
- スクロール事故は SPA 特有の引き継ぎ問題を疑う
- sticky / fixed / z-index は親要素の overflow / transform を確認
- iOS は `100svh` と `touch-action`, `pointer-events` の追加対策が必要
- フォーカス管理は UX とアクセシビリティの両方に効く
