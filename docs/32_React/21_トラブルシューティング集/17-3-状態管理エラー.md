# 17-3 状態管理エラー（依存配列/スコープ/二重管理）

## 🎯 この章で学ぶこと

- React の依存配列に起因する典型バグの読み方と直し方
- クロージャによる「古い state を参照する」問題の解消法
- サーバ状態とクライアント状態を二重管理した結果起きる事故の例
- `useState` と `useReducer` の使い分け
- React DevTools と React Profiler を活かしたデバッグ

## 📖 概念の説明

### 依存配列とは

`useEffect`, `useMemo`, `useCallback` の第 2 引数。「この値が変わったら再実行する」というルールを書きます。書き忘れたり書き間違えたりすると、

- 古い値を参照し続ける
- 必要なときに再実行されない
- 不要に再実行される

の 3 種類のバグが起きます。

### 古い state（stale closure）問題

JavaScript のクロージャは「定義時点の変数」を覚え込みます。`useEffect` で作った関数の中の `count` は、その関数が定義されたときの `count` を参照し続けます。これが「古い state」と呼ばれる現象です。

### サーバ状態とクライアント状態の二重管理

サーバから取ってきたデータを `useState` に詰めてしまうと、

- サーバ側で他人が更新しても気付けない
- 編集を始めると「サーバ最新値」と「ローカル編集値」のどちらが正か分からない
- キャッシュの整合性を自前で実装する羽目になる

ということが起きます。React Query / SWR のようなライブラリは、これらを引き受けるための道具です。

### `useState` vs `useReducer`

- 単純な値: `useState`
- 複数の値が「ある操作」で同時に変わる: `useReducer`

例: フォーム送信時に「ローディング → 成功 / 失敗」と複数フィールドが連動して変わる場合は、reducer の方が読みやすいです。

## 💻 コード例

### 症状: ボタンを連打すると 1 回しか増えない

```tsx
function Counter() {
  const [count, setCount] = useState(0);
  function add3() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
  }
  return <button onClick={add3}>{count}</button>;
}
```

**原因**: 3 つの `setCount(count + 1)` はすべて同じ `count`（例えば 0）を見ているので、結果は 1 のまま。

**修正**: 関数形式の更新で「直前の値」を引数で受け取る。

```tsx
function add3() {
  setCount((c) => c + 1);
  setCount((c) => c + 1);
  setCount((c) => c + 1);
}
```

### 症状: setInterval が古い state を見ている

```tsx
function Timer() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1); // ❌ count は常に 0
    }, 1000);
    return () => clearInterval(id);
  }, []); // ❌ count が依存に入っていない
}
```

**修正 A**: 関数形式の更新を使う。依存配列を空のままにできる。

```tsx
useEffect(() => {
  const id = setInterval(() => setCount((c) => c + 1), 1000);
  return () => clearInterval(id);
}, []);
```

**修正 B**: ref に最新値を保管する（複雑な計算が必要な場合）。

```tsx
const countRef = useRef(count);
useEffect(() => {
  countRef.current = count;
});
useEffect(() => {
  const id = setInterval(() => {
    setCount(compute(countRef.current));
  }, 1000);
  return () => clearInterval(id);
}, []);
```

### 症状: `useEffect` が無限ループ

```tsx
function Bad() {
  const [list, setList] = useState<number[]>([]);
  useEffect(() => {
    setList([...list, 1]); // 毎回新しい配列 → list が変わる → effect が走る
  }, [list]);
}
```

**修正**: そもそも依存に `list` が入る必要があるか考え直す。

```tsx
useEffect(() => {
  setList((prev) => [...prev, 1]);
}, []); // 初回 1 回だけでよい場合
```

### 症状: 検索条件を変えても結果が更新されない

```tsx
function SearchPage({ keyword }: { keyword: string }) {
  const [results, setResults] = useState<Item[]>([]);
  useEffect(() => {
    fetch(`/api/search?q=${keyword}`)
      .then((r) => r.json())
      .then(setResults);
  }, []); // ❌ keyword が依存にない
}
```

**修正**: ESLint の `react-hooks/exhaustive-deps` ルールを入れていれば警告が出ます。

```tsx
useEffect(() => {
  fetch(`/api/search?q=${keyword}`)
    .then((r) => r.json())
    .then(setResults);
}, [keyword]);
```

### 症状: 2 つの場所で同じ値を持っていてズレる

```tsx
function Page() {
  const { data: user } = useQuery({ queryKey: ["me"], queryFn: fetchMe });
  const [localUser, setLocalUser] = useState(user); // ❌ 二重管理
  useEffect(() => setLocalUser(user), [user]);
  return <Profile user={localUser} />;
}
```

`localUser` は `user` のコピーなので、サーバから来た最新値と表示が乖離することがあります。

**修正**: そもそもコピーしない。編集中の差分だけを別 state で持つ。

```tsx
function Page() {
  const { data: user } = useQuery({ queryKey: ["me"], queryFn: fetchMe });
  const [draft, setDraft] = useState<Partial<User>>({});
  return <Profile user={{ ...user, ...draft }} onChange={setDraft} />;
}
```

### 症状: コンポーネントが大量に再レンダーされる

```tsx
function List() {
  const [filter, setFilter] = useState("");
  const items = data.filter((i) => i.title.includes(filter)); // 毎レンダー再計算

  return items.map((item) => (
    <Row key={item.id} item={item} onClick={() => alert(item.id)} /> // 毎回新しい関数
  ));
}
```

**修正**: 重い計算は `useMemo`、関数は `useCallback`、子は `React.memo`。ただし無闇に使うと逆効果なので、計測してから。

```tsx
const visible = useMemo(
  () => data.filter((i) => i.title.includes(filter)),
  [data, filter]
);
```

### `useReducer` で状態遷移を整理

```ts
type State =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: User }
  | { status: "error"; message: string };

type Action =
  | { type: "FETCH" }
  | { type: "SUCCESS"; data: User }
  | { type: "ERROR"; message: string };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "FETCH":
      return { status: "loading" };
    case "SUCCESS":
      return { status: "success", data: action.data };
    case "ERROR":
      return { status: "error", message: action.message };
  }
}
```

```tsx
const [state, dispatch] = useReducer(reducer, { status: "idle" });
```

`status: "loading"` 時には `data` が型として存在しないので、JSX で誤って参照しようとすると TypeScript が止めてくれます。

### React DevTools の Profiler

「なぜ再レンダーが起きたか」を可視化できる神機能です。

1. ブラウザに React DevTools 拡張を入れる
2. Profiler タブで Record ボタンを押す
3. 操作する
4. Stop して、レンダー回数や原因を確認

「props が変わっただけ」「state が変わっただけ」「親が再レンダーした」のいずれかが見えます。

## ❌ よくある間違い

### 1. ESLint の `exhaustive-deps` を黙らせる

```tsx
useEffect(() => {
  /* */
}, []); // eslint-disable-next-line
```

将来の自分が泣きます。本当に依存が空でよいか、もう一度考える。

### 2. 不変性を守らずに state を更新

```tsx
const [list, setList] = useState([1, 2, 3]);
list.push(4); // ❌ 直接 mutate
setList(list); // 参照が変わらず再レンダーされない
```

```tsx
setList((prev) => [...prev, 4]); // ✅
```

### 3. `useMemo` を「念のため」全部に付ける

メモ化自体にコストがあります。ベンチを取らずに付けると、むしろ遅くなることも。

### 4. Context を「グローバル変数」として乱用

頻繁に変わる値を Context に入れると、配下のすべてのコンポーネントが再レンダーします。状態管理ライブラリ（Zustand 等）の方が適していることも。

### 5. 「フォームの値」をすべて useState に詰める

100 フィールドのフォームを `useState` 100 個で書くと、入力のたびに全部再レンダーします。React Hook Form のような非制御ベースのライブラリで、再レンダーを最小化できます。

## ✅ ベストプラクティス

1. **`exhaustive-deps` を有効に保つ**: 依存配列バグの 9 割を予防。
2. **state 更新は関数形式を第一選択に**: クロージャ問題を回避。
3. **サーバ状態は React Query / SWR に任せる**: 自前で再フェッチ・キャッシュ管理しない。
4. **状態遷移は `useReducer` で表現**: 複数の値が連動するなら reducer。
5. **再レンダーは Profiler で計測してから対処**: 推測でメモ化しない。

## 📝 まとめ

- 依存配列の漏れは React バグ Top 3 の常連。リンタで自動検出
- クロージャによる「古い state」は関数形式の更新で解決
- サーバ状態を `useState` に詰めるのは罠。React Query 等を使う
- `useReducer` は状態遷移を明示化したいときに便利
- パフォーマンス改善は推測でなく計測から

## 📎 事例：`02_TimeSlotSectionの警告と状態更新の注意`（全文）

# TimeSlotSectionの警告と状態更新の注意

## ⚠️ 警告の原因

`TimeSlotSection`コンポーネントの**レンダー中（returnやmapの中）で直接setStateや状態を更新**すると、
Reactは「副作用的な処理がレンダー中に実行された」として警告を出します。

### 例：NGパターン
```jsx
function TimeSlotSection({ slots }) {
  const [editOpen, setEditOpen] = useState(false);

  // ❌ NG: mapの中で直接setState
  return (
    <div>
      {slots.map(slot => {
        if (slot.shouldEdit) {
          setEditOpen(true); // ←ここで警告
        }
        return <SlotItem slot={slot} />;
      })}
    </div>
  );
}
```

---

## 📝 よくある間違い

- `useEffect`の外で状態更新をしている
- `map`や`return`の中で状態更新をしている

---

## ✅ 対応方法

- **mapやreturnの中でsetStateを呼ばない**
- **状態更新は必ずイベントハンドラやuseEffectの中で行う**

### 正しい例
```jsx
function TimeSlotSection({ slots }) {
  const [editOpen, setEditOpen] = useState(false);

  useEffect(() => {
    if (slots.some(slot => slot.shouldEdit)) {
      setEditOpen(true);
    }
  }, [slots]);

  return (
    <div>
      {slots.map(slot => (
        <SlotItem slot={slot} />
      ))}
    </div>
  );
}
```

# 状態管理エラー基礎 - 初心者向け解説

## 状態管理エラーとは？

**状態管理エラー**とは、フロントエンドアプリケーションで、アプリケーションの状態（データ）を管理する際に発生するエラーです。状態が正しく更新されなかったり、複数のコンポーネント間で状態が同期されなかったり、状態の更新タイミングがずれたりする場合に発生します。

### 身近な例で理解する

日常生活で例えると：
- **正しい状態管理**：銀行の預金残高が、ATM、ネットバンキング、スマホアプリで常に同じ金額を表示する
- **状態管理エラー**：ATMでは10万円と表示されるが、スマホアプリでは5万円と表示される（状態が同期されていない）

プログラミングでも同じように、アプリケーションの状態が正しく管理されていないと、UIの表示がおかしくなったり、予期しない動作が発生したりします。

## 状態管理ライブラリの歴史と背景

状態管理の重要性は、フロントエンドアプリケーションの複雑化とともに増してきました。以下に、主要なフレームワークやライブラリの歴史を時系列でまとめます。

### 2006年：jQueryの登場

jQueryが登場し、ブラウザ間の非互換性を吸収し、DOM操作やイベント処理が容易になりました。しかし、この時代はまだ状態管理の概念が明確ではありませんでした。

### 2010年：AngularJSのリリース

Googleが開発したAngularJSがリリースされました。双方向データバインディングや依存性注入などの機能を提供し、SPA（Single Page Application）の開発を容易にしました。これにより、状態管理の重要性が認識され始めました。

### 2013年：Reactの登場

Facebook（現Meta）がReactをオープンソースとして公開しました。Reactはコンポーネントベースのライブラリで、宣言的なUI構築を可能にしました。しかし、React自体には状態管理の仕組みが限定的で、大規模アプリケーションでは外部の状態管理ライブラリが必要とされました。

**背景**：Reactは各コンポーネントが独自の状態（state）を持つことができますが、複数のコンポーネント間で状態を共有する場合、親コンポーネントから子コンポーネントへ「props」として渡す必要がありました。これが「props drilling」と呼ばれる問題を引き起こし、状態管理の複雑さが増しました。

### 2014年：Fluxアーキテクチャの提唱

FacebookがFluxアーキテクチャを提唱しました。これは、データの流れを一方向にすることで、状態管理の複雑さを軽減することを目的としています。

**Fluxの構成要素**：
- **Action**：状態を変更するためのアクション
- **Dispatcher**：アクションをストアに送る
- **Store**：アプリケーションの状態を保持
- **View**：UIを表示

### 2014年：Vue.jsの登場

Evan You氏がVue.jsをリリースしました。Vue.jsは軽量で学習コストが低く、柔軟な構成が可能なフレームワークとして注目を集めました。Vue.jsには双方向データバインディングが組み込まれており、状態管理が比較的容易でした。

### 2015年：Reduxの登場

Dan Abramov氏とAndrew Clark氏がReduxを公開しました。Reduxは、Fluxの概念を拡張し、より扱いやすく設計された状態管理ライブラリです。

**Reduxの3つの原則**：
1. **Single source of truth**：アプリケーション全体の状態を一つのストアで管理
2. **State is read-only**：状態は直接変更せず、アクションを通じてのみ変更
3. **Mutations are written as pure functions**：状態の変更は純粋関数であるリデューサーを通じて行う

**背景**：Reactアプリケーションが大規模化するにつれて、状態管理の複雑さが増し、予測可能な状態管理を実現するためにReduxが開発されました。

### 2016年：Vuexのリリース

Vue.jsの公式状態管理ライブラリであるVuexがリリースされました。Vuexは、Vue.jsアプリケーションの状態を集中管理し、コンポーネント間での状態共有を容易にしました。

**Vuexの構成要素**：
- **State**：アプリケーションの状態
- **Getters**：状態を取得するための計算プロパティ
- **Mutations**：状態を変更するための同期処理
- **Actions**：非同期処理を含む状態変更

### 2019年：React Hooksの導入

React 16.8でHooksが導入されました。これにより、クラスコンポーネントを使用せずに状態やライフサイクルメソッドを関数コンポーネント内で利用できるようになり、状態管理の方法に大きな変化をもたらしました。

**主なHooks**：
- **useState**：コンポーネントの状態を管理
- **useEffect**：副作用（データ取得など）を処理
- **useContext**：コンテキストを使用して状態を共有

### 2019年：Zustandの登場

Zustandがリリースされました。Zustandは、シンプルで軽量な状態管理ライブラリで、ボイラープレートコードを削減し、直感的なAPIを提供することを目的としています。

**背景**：Reduxは強力ですが、設定が複雑でボイラープレートコードが多いという課題がありました。Zustandは、この課題を解決するために開発されました。

### 2020年：Recoilの発表

FacebookがRecoilを発表しました。Recoilは、Reactのための新しい状態管理ライブラリで、コンポーネント間での状態共有を容易にし、パフォーマンスの最適化も考慮されています。

### 2021年：Piniaの登場

Vue.jsの新しい状態管理ライブラリであるPiniaが登場しました。Piniaは、Vuexの後継として開発され、よりシンプルで型安全なAPIを提供します。

**背景**：Vuexは強力でしたが、TypeScriptとの統合が難しく、設定が複雑でした。Piniaは、これらの課題を解決するために開発されました。

## 状態管理エラーの特徴

1. **実行時に発生する**：プログラムを動かしてからエラーが分かる
2. **条件によって発生する**：特定の操作やタイミングでのみ発生する場合がある
3. **発見が難しい**：状態の不整合は、UIの表示がおかしくなるまで気づかない場合がある
4. **デバッグが困難**：状態の更新履歴を追跡するのが難しい場合がある

## よくある状態管理エラーの種類

### 1. 状態の不整合（State Inconsistency）

異なるコンポーネントや場所で状態が同期されていないエラーです。

#### 具体例

```javascript
// Reactの例：エラー例1 - 状態が同期されていない
import React, { useState } from 'react';

function UserProfile() {
  const [user, setUser] = useState({ name: '山田太郎', age: 25 });
  
  const updateName = () => {
    // 間違い: 状態を直接変更している
    user.name = '佐藤花子';  // これは動作しない
    setUser(user);  // Reactは変更を検知できない
  };
  
  return (
    <div>
      <p>名前: {user.name}</p>
      <button onClick={updateName}>名前を変更</button>
    </div>
  );
}

// 正しい例1: 新しいオブジェクトを作成
const updateName = () => {
  setUser({ ...user, name: '佐藤花子' });  // スプレッド演算子を使用
};

// 正しい例2: 関数形式の更新を使用
const updateName = () => {
  setUser(prevUser => ({ ...prevUser, name: '佐藤花子' }));
};
```

```javascript
// Vue.jsの例：エラー例1 - 状態が同期されていない
// エラー例: 直接状態を変更している
export default {
  data() {
    return {
      user: { name: '山田太郎', age: 25 }
    }
  },
  methods: {
    updateName() {
      // 間違い: 直接変更（Vuexを使っている場合は動作しない）
      this.user.name = '佐藤花子';
    }
  }
}

// 正しい例: Vuexを使用する場合
import { mapMutations } from 'vuex';

export default {
  methods: {
    ...mapMutations(['SET_USER_NAME']),
    updateName() {
      this.SET_USER_NAME('佐藤花子');  // Mutationを通じて変更
    }
  }
}
```

#### 解決方法

- **イミュータブル（不変）な更新**：状態を直接変更せず、新しいオブジェクトや配列を作成
- **状態管理ライブラリを使用**：Redux、Vuex、Zustandなどを使用して状態を一元管理
- **状態の正規化**：状態を正規化して、冗長性を排除

---

### 2. 無限ループエラー

状態の更新が無限に繰り返されるエラーです。主に`useEffect`や`useState`の依存配列の設定ミスで発生します。

#### 具体例

```javascript
// Reactの例：エラー例1 - useEffectの無限ループ
import React, { useState, useEffect } from 'react';

function Counter() {
  const [count, setCount] = useState(0);
  
  // 間違い: 依存配列がないため、毎回実行される
  useEffect(() => {
    setCount(count + 1);  // 無限ループが発生
  });  // 依存配列がない
  
  return <div>カウント: {count}</div>;
}

// エラー例2: 依存配列に状態を含めている
useEffect(() => {
  setCount(count + 1);
}, [count]);  // countが変わるたびに実行され、無限ループが発生

// 正しい例1: 依存配列を空にする（マウント時のみ実行）
useEffect(() => {
  // 初期化処理
  console.log('コンポーネントがマウントされました');
}, []);  // 空の依存配列

// 正しい例2: 関数形式の更新を使用
useEffect(() => {
  setCount(prevCount => prevCount + 1);
}, []);  // 依存配列が空でも、関数形式なら安全

// 正しい例3: 条件を追加して無限ループを防ぐ
useEffect(() => {
  if (count < 10) {
    setCount(count + 1);
  }
}, [count]);  // 条件があれば無限ループにならない
```

```javascript
// Reactの例：エラー例2 - useStateの無限ループ
function Component() {
  const [data, setData] = useState([]);
  
  // 間違い: レンダリング中に状態を更新している
  const processedData = data.map(item => {
    setData([...data, item]);  // 無限ループが発生
    return item;
  });
  
  return <div>{processedData}</div>;
}

// 正しい例: useEffect内で処理する
useEffect(() => {
  const processedData = data.map(item => {
    // 処理
    return item;
  });
  setData(processedData);
}, []);  // 適切な依存配列
```

#### 解決方法

- **依存配列を適切に設定**：`useEffect`の依存配列に必要な値のみを含める
- **関数形式の更新を使用**：`setState(prev => ...)`の形式を使用
- **条件を追加**：無限ループを防ぐための条件を追加

### 3. 状態の更新タイミングの問題

非同期処理やイベントの順序により、状態の更新が適切に行われないエラーです。

#### 具体例

```javascript
// Reactの例：エラー例1 - 非同期処理のタイミング問題
import React, { useState } from 'react';

function UserList() {
  const [users, setUsers] = useState([]);
  
  const fetchUsers = async () => {
    // 間違い: 非同期処理の完了を待たずに状態を更新
    fetch('/api/users')
      .then(response => response.json())
      .then(data => {
        setUsers(data);
        console.log(users);  // まだ空の配列（古い状態）
      });
  };
  
  // 正しい例1: async/awaitを使用
  const fetchUsers = async () => {
    try {
      const response = await fetch('/api/users');
      const data = await response.json();
      setUsers(data);
      console.log(data);  // 正しいデータ
    } catch (error) {
      console.error('エラー:', error);
    }
  };
  
  // 正しい例2: useEffect内で処理
  useEffect(() => {
    const fetchUsers = async () => {
      const response = await fetch('/api/users');
      const data = await response.json();
      setUsers(data);
    };
    fetchUsers();
  }, []);
  
  return <div>{/* ユーザーリスト */}</div>;
}
```

```javascript
// Reactの例：エラー例2 - 複数の状態更新の競合
function Component() {
  const [count, setCount] = useState(0);
  
  const increment = () => {
    // 間違い: 複数の状態更新が競合する可能性
    setCount(count + 1);
    setCount(count + 1);  // 期待: count + 2、実際: count + 1
  };
  
  // 正しい例: 関数形式の更新を使用
  const increment = () => {
    setCount(prev => prev + 1);
    setCount(prev => prev + 1);  // 正しく count + 2 になる
  };
  
  return <button onClick={increment}>カウント: {count}</button>;
}
```

```javascript
// Vue.jsの例：エラー例1 - 非同期処理のタイミング問題
export default {
  data() {
    return {
      users: []
    }
  },
  methods: {
    // 間違い: 非同期処理の完了を待たずに状態を更新
    async fetchUsers() {
      const response = await fetch('/api/users');
      const data = await response.json();
      this.users = data;
      console.log(this.users);  // まだ空の配列（Vueのリアクティブシステムの遅延）
    }
  }
}

// 正しい例: nextTickを使用
import { nextTick } from 'vue';

export default {
  methods: {
    async fetchUsers() {
      const response = await fetch('/api/users');
      const data = await response.json();
      this.users = data;
      await nextTick();  // DOMの更新を待つ
      console.log(this.users);  // 正しいデータ
    }
  }
}
```

#### 解決方法

- **async/awaitを使用**：非同期処理を適切に待機
- **関数形式の更新を使用**：`setState(prev => ...)`の形式を使用
- **useEffectを使用**：副作用を適切に処理
- **nextTickを使用**：Vue.jsの場合、DOMの更新を待つ

### 4. 状態管理ライブラリのエラー

Redux、Vuex、Zustandなどのライブラリの使用方法に誤りがあるエラーです。

#### 具体例

```javascript
// Reduxの例：エラー例1 - リデューサーで状態を直接変更
const initialState = { count: 0 };

// 間違い: 状態を直接変更している
function counterReducer(state = initialState, action) {
  if (action.type === 'INCREMENT') {
    state.count++;  // 直接変更（エラー）
    return state;
  }
  return state;
}

// 正しい例: 新しいオブジェクトを返す
function counterReducer(state = initialState, action) {
  if (action.type === 'INCREMENT') {
    return { ...state, count: state.count + 1 };  // 新しいオブジェクト
  }
  return state;
}
```

```javascript
// Reduxの例：エラー例2 - アクションの型が間違っている
// 間違い: アクションの型が定義されていない
dispatch({ type: 'INCREMENT' });  // タイポの可能性

// 正しい例: アクションタイプを定数として定義
const INCREMENT = 'INCREMENT';
const DECREMENT = 'DECREMENT';

dispatch({ type: INCREMENT });
```

```javascript
// Vuexの例：エラー例1 - Mutationで非同期処理を行っている
const store = new Vuex.Store({
  state: {
    users: []
  },
  mutations: {
    // 間違い: Mutationで非同期処理を行っている
    SET_USERS(state, users) {
      fetch('/api/users')  // 非同期処理はMutationでは行わない
        .then(response => response.json())
        .then(data => {
          state.users = data;
        });
    }
  }
});

// 正しい例: Actionで非同期処理を行う
const store = new Vuex.Store({
  state: {
    users: []
  },
  mutations: {
    SET_USERS(state, users) {
      state.users = users;  // 同期的な状態変更のみ
    }
  },
  actions: {
    async fetchUsers({ commit }) {
      const response = await fetch('/api/users');
      const data = await response.json();
      commit('SET_USERS', data);  // Mutationを呼び出す
    }
  }
});
```

```javascript
// Zustandの例：エラー例1 - 状態の更新方法が間違っている
import create from 'zustand';

// 間違い: 状態を直接変更している
const useStore = create((set) => ({
  count: 0,
  increment: () => {
    useStore.getState().count++;  // 直接変更（動作しない）
  }
}));

// 正しい例: set関数を使用
const useStore = create((set) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 }))
}));
```

#### 解決方法

- **ライブラリのドキュメントを読む**：正しい使用方法を確認
- **イミュータブルな更新**：状態を直接変更せず、新しいオブジェクトを返す
- **アクション/ミューテーションの使い分け**：ReduxやVuexでは、同期処理と非同期処理を適切に分ける
- **型定義を使用**：TypeScriptを使用して、型安全性を確保

### 6. 状態の永続化エラー

状態をローカルストレージやデータベースに保存・復元する際のエラーです。

#### 具体例

```javascript
// Reactの例：エラー例1 - ローカルストレージのエラーハンドリングがない
function Component() {
  const [data, setData] = useState(() => {
    // 間違い: エラーハンドリングがない
    return JSON.parse(localStorage.getItem('data'));  // エラーが発生する可能性
  });
  
  // 正しい例: try-catchでエラーハンドリング
  const [data, setData] = useState(() => {
    try {
      const savedData = localStorage.getItem('data');
      return savedData ? JSON.parse(savedData) : [];
    } catch (error) {
      console.error('ローカルストレージの読み込みエラー:', error);
      return [];
    }
  });
  
  // 状態を保存する際もエラーハンドリング
  useEffect(() => {
    try {
      localStorage.setItem('data', JSON.stringify(data));
    } catch (error) {
      console.error('ローカルストレージの保存エラー:', error);
    }
  }, [data]);
  
  return <div>{/* コンテンツ */}</div>;
}
```

```javascript
// Reactの例：エラー例2 - シリアライズできないデータを保存
function Component() {
  const [user, setUser] = useState({ name: '山田太郎' });
  
  // 間違い: 関数を含むオブジェクトを保存
  user.sayHello = () => console.log('Hello');
  localStorage.setItem('user', JSON.stringify(user));  // 関数は失われる
  
  // 正しい例: シリアライズ可能なデータのみ保存
  const saveUser = () => {
    const userData = {
      name: user.name,
      age: user.age
      // 関数は含めない
    };
    localStorage.setItem('user', JSON.stringify(userData));
  };
}
```

```javascript
// Vue.jsの例：エラー例1 - ローカルストレージのエラーハンドリングがない
export default {
  data() {
    return {
      data: []
    }
  },
  mounted() {
    // 間違い: エラーハンドリングがない

  },
  watch: {
    data: {

        localStorage.setItem('data', JSON.stringify(newData));
      },
      deep: true
    }
  }
}

// 正しい例: エラーハンドリングを追加
export default {
  data() {
    return {
      data: []
    }
  },

      const savedData = localStorage.getItem('data');
      this.data = savedData ? JSON.parse(savedData) : [];

```

#### 解決方法

- **エラーハンドリングを追加**：try-catchでエラーを処理
- **シリアライズ可能なデータのみ保存**：関数や循環参照を含むオブジェクトは保存しない
- **ストレージの容量を確認**：ローカルストレージの容量制限（約5MB）を考慮
- **プラグインを使用**：Redux Persistやvuex-persistedstateなどのプラグインを使用

### 7. 非同期状態更新の競合

複数の非同期処理が同時に状態を更新し、競合が発生するエラーです。

#### 具体例

```javascript
// Reactの例：エラー例1 - 複数の非同期処理が競合
function Component() {
  const [count, setCount] = useState(0);
  
  const increment = async () => {
    // 間違い: 複数の非同期処理が同時に実行される可能性
    const response = await fetch('/api/increment');
    const data = await response.json();
    setCount(data.count);  // 古い状態で上書きされる可能性
  };
  
  // ユーザーがボタンを連続クリックすると、競合が発生
  return <button onClick={increment}>カウント: {count}</button>;
}

// 正しい例1: ローディング状態を追加
const [count, setCount] = useState(0);
const [loading, setLoading] = useState(false);

const increment = async () => {
  if (loading) return;  // 既に処理中の場合は何もしない
  setLoading(true);
  try {
    const response = await fetch('/api/increment');
    const data = await response.json();
    setCount(data.count);
  } finally {
    setLoading(false);
  }
};

// 正しい例2: 関数形式の更新を使用
const increment = async () => {
  const response = await fetch('/api/increment');
  const data = await response.json();
  setCount(prev => Math.max(prev, data.count));  // 最新の値を保持
};
```

```javascript
// Reactの例：エラー例2 - コンポーネントのアンマウント後の状態更新
function Component() {
  const [data, setData] = useState([]);
  
  useEffect(() => {
    let cancelled = false;
    
    fetch('/api/data')
      .then(response => response.json())
      .then(data => {
        if (!cancelled) {  // アンマウントされていないか確認
          setData(data);
        }
      });
    
    return () => {
      cancelled = true;  // クリーンアップ
    };
  }, []);
  
  return <div>{/* コンテンツ */}</div>;
}
```

```javascript
// Vue.jsの例：エラー例1 - 複数の非同期処理が競合
```

- **関数形式の更新を使用**：最新の状態を参照
- **クリーンアップを追加**：コンポーネントのアンマウント後に状態を更新しない
- **デバウンス/スロットル**：連続したリクエストを制限

## 状態管理エラーの一般的な解決方法

### 1. 状態管理ライブラリを適切に選択する

アプリケーションの規模や要件に応じて、適切な状態管理ライブラリを選択します。

- **小規模アプリケーション**：React Hooks、Vue.jsのdata/props
- **中規模アプリケーション**：Context API、Zustand、Pinia
- **大規模アプリケーション**：Redux、Vuex、Recoil

### 2. イミュータブルな更新を徹底する

状態を直接変更せず、常に新しいオブジェクトや配列を作成します。

```javascript
// 間違い
state.user.name = '新しい名前';

// 正しい
setState({ ...state, user: { ...state.user, name: '新しい名前' } });
```

### 3. 非同期処理を適切に処理する

async/awaitやPromiseを適切に使用し、エラーハンドリングを追加します。

```javascript
try {
  const data = await fetchData();
  setState(data);
} catch (error) {
  console.error('エラー:', error);
}
```

### 4. デバッグツールを使用する

Redux DevTools、Vue DevToolsなどのデバッグツールを使用して、状態の変更を追跡します。

### 5. テストを書く

状態管理のロジックをテストして、予期しない動作を防ぎます。

## よくある状態管理エラーのチェックリスト

- [ ] 状態を直接変更していないか
- [ ] useEffectの依存配列を適切に設定しているか
- [ ] 非同期処理のエラーハンドリングを追加しているか
- [ ] 状態の初期値を適切に設定しているか
- [ ] 無限ループが発生していないか
- [ ] 状態管理ライブラリの使用方法が正しいか
- [ ] ローカルストレージのエラーハンドリングを追加しているか
- [ ] 非同期処理の競合を防いでいるか

## まとめ

- **状態管理エラー**は、アプリケーションの状態を管理する際に発生するエラー
- **状態の不整合**は、異なる場所で状態が同期されていないエラー
- **無限ループエラー**は、状態の更新が無限に繰り返されるエラー
- **状態の更新タイミングの問題**は、非同期処理により状態の更新が適切に行われないエラー
- **イミュータブルな更新**を徹底して、状態を直接変更しない
- **適切な状態管理ライブラリ**を選択して、アプリケーションの規模に応じた管理を行う
- **デバッグツール**を使用して、状態の変更を追跡する
