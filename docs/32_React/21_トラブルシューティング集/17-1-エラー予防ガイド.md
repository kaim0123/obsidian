# 17-1 エラー予防ガイド（チェックリスト）

## 🎯 この章で学ぶこと

- 「エラーが出てから直す」ではなく「エラーが出にくい構造にする」発想を持つ
- TypeScript / ESLint / Prettier / テスト の 4 段防壁の役割を整理する
- React 特有の落とし穴をチェックリストにまとめる
- コードレビューで活かせる「臭うコード」の見つけ方を覚える
- 自分のプロジェクトに即適用できるエラー予防チェックリストを得る

## 📖 概念の説明

### 「直す」より「出さない」が圧倒的に安い

バグは見つかるタイミングが遅いほど修正コストが上がります。

```
タイピング中に検出 < コミット前 < CI < QA < 本番リリース後
```

つまり、エディタとプリコミットフックでの検出が最強です。本番に出てから直すのは 100 倍以上のコストになると言われます。

### 4 段防壁モデル

1. **TypeScript**: 型で「ありえない値」を防ぐ
2. **ESLint**: 構文・パターンの誤りを警告
3. **テスト**: 振る舞いを保証
4. **コードレビュー**: 設計・命名の妥当性を人がチェック

これらは独立しているようで、抜けたところを補完し合います。

### React 特有の地雷

- 依存配列の漏れ
- key の使い回し
- 二重レンダー（StrictMode）
- 状態の二重管理（サーバ + クライアント両方で持つ）
- 副作用の cleanup 忘れ
- フォーム制御 / 非制御の混在
- props を mutate（`props.list.push(...)`）

これらは型でもリンタでも完全には防げないため、チェックリストとして覚えておきます。

## 💻 コード例

### `tsconfig.json` の strict 設定

```json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "noImplicitOverride": true,
    "exactOptionalPropertyTypes": true,
    "noFallthroughCasesInSwitch": true
  }
}
```

`noUncheckedIndexedAccess` は地味だが効果絶大。`array[0]` が `T | undefined` になるので「空配列チェック忘れ」を発見できます。

### ESLint 推奨設定

```bash
npm i -D eslint @eslint/js typescript-eslint \
  eslint-plugin-react eslint-plugin-react-hooks \
  eslint-plugin-jsx-a11y
```

```js
// eslint.config.js
import js from "@eslint/js";
import tseslint from "typescript-eslint";
import react from "eslint-plugin-react";
import reactHooks from "eslint-plugin-react-hooks";
import a11y from "eslint-plugin-jsx-a11y";

export default [
  js.configs.recommended,
  ...tseslint.configs.recommended,
  react.configs.flat.recommended,
  {
    plugins: { "react-hooks": reactHooks, "jsx-a11y": a11y },
    rules: {
      "react-hooks/rules-of-hooks": "error",
      "react-hooks/exhaustive-deps": "warn",
      "jsx-a11y/alt-text": "warn",
    },
  },
];
```

特に `react-hooks/exhaustive-deps` は依存配列バグを大量に検出してくれる救世主。

### Prettier + lint-staged + husky

```bash
npm i -D prettier husky lint-staged
npx husky init
```

```json
// package.json
{
  "lint-staged": {
    "*.{ts,tsx,js,jsx}": ["eslint --fix", "prettier --write"]
  }
}
```

```bash
# .husky/pre-commit
npx lint-staged
```

これで「コミット時に自動整形 + リント」されます。汚いコードがリポジトリに入りません。

### 危険パターンチェックリスト（DO/DON'T）

```tsx
// ❌ 依存配列の漏れ
useEffect(() => {
  fetch(`/api/users/${userId}`);
}, []); // userId が変わっても再フェッチされない

// ✅ 依存配列を正しく書く
useEffect(() => {
  fetch(`/api/users/${userId}`);
}, [userId]);
```

```tsx
// ❌ index を key に使う（並び替えで破綻）
items.map((item, i) => <Row key={i} item={item} />);

// ✅ 安定した一意 ID を使う
items.map((item) => <Row key={item.id} item={item} />);
```

```tsx
// ❌ props を mutate
function List({ items }: { items: Task[] }) {
  items.sort((a, b) => a.title.localeCompare(b.title));
  return <ul>{items.map(...)}</ul>;
}

// ✅ コピーしてから操作
const sorted = [...items].sort((a, b) => a.title.localeCompare(b.title));
```

```tsx
// ❌ サーバ状態を useState に詰めて二重管理
const [tasks, setTasks] = useState<Task[]>([]);
useEffect(() => {
  fetchTasks().then(setTasks);
}, []);

// ✅ React Query などで一元管理
const { data: tasks } = useQuery({ queryKey: ["tasks"], queryFn: fetchTasks });
```

```tsx
// ❌ 制御 / 非制御の混在
<input value={value} />; // onChange を書いていない → 入力できない

// ✅ value と onChange はセット
<input value={value} onChange={(e) => setValue(e.target.value)} />;
```

```tsx
// ❌ cleanup なしの subscribe
useEffect(() => {
  const id = setInterval(tick, 1000);
}, []);

// ✅ cleanup でメモリリーク防止
useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);
}, []);
```

### エラーバウンダリの設置

```tsx
import { Component, type ReactNode } from "react";

class ErrorBoundary extends Component<
  { children: ReactNode },
  { error: Error | null }
> {
  state = { error: null as Error | null };
  static getDerivedStateFromError(error: Error) {
    return { error };
  }
  componentDidCatch(error: Error, info: React.ErrorInfo) {
    console.error("Caught:", error, info);
    // Sentry などへ送る
  }
  render() {
    if (this.state.error) {
      return (
        <div role="alert">
          予期せぬエラーが発生しました。
          <button onClick={() => location.reload()}>再読み込み</button>
        </div>
      );
    }
    return this.props.children;
  }
}
```

ルートに 1 つ置くだけで、コンポーネント内の例外で画面が真っ白になる事故を防げます。

### CI で型エラー / リントを必須にする

```yaml
# .github/workflows/ci.yml
- run: npm run typecheck   # tsc --noEmit
- run: npm run lint
- run: npm run test
- run: npm run build
```

main へマージするには必ず緑になっている必要がある、という Branch Protection を設定。

## ❌ よくある間違い

### 1. lint の警告を放置

「警告だから後でいいや」が積もると、本当に重要な警告が埋もれます。警告 0 を維持するか、誤検知ならルールを明示的に切る。

### 2. `any` の濫用

```ts
const data: any = await res.json();
```

これは TypeScript を「実質ただの JS」に戻す呪文。`unknown` を使い、`zod` などでバリデーションしてから絞り込む。

### 3. テストを「あとで書く」

書かれません。実装と同時に書くのが定着のコツ。

### 4. `console.log` だけでデバッグ

ブラウザの DevTools には条件付きブレークポイント・ネットワークタブ・React DevTools があります。`console.log` 一本槍だと見えるものが少なすぎる。

### 5. エラー監視を入れない

開発者が踏まないバグは「ない」のではなく「見えていない」だけ。Sentry などの監視ツールで本番のエラーを可視化しましょう。

## ✅ ベストプラクティス

1. **TypeScript は strict、ESLint は recommended から開始**: 緩いところからスタートして、徐々に厳しくしていく。
2. **husky + lint-staged で自動チェック**: 人間の意志に頼らない仕組み化が鉄則。
3. **エラーバウンダリをルートと主要画面に**: 全画面が真っ白事故を未然防止。
4. **CI は通らない PR をマージさせない**: Branch Protection を必ず設定。
5. **Sentry などで本番エラーを観測**: 「ユーザーが踏んだエラー数」が見えるとチームの優先度が変わる。

## 📝 まとめ

- バグは早期発見ほど安い。エディタ + プリコミットが最強の防衛線
- TypeScript / ESLint / テスト / レビュー の 4 段防壁で守る
- React 特有の地雷（依存配列、key、二重管理）はチェックリスト化
- エラーバウンダリと Sentry で本番事故を最小化
- 「警告 0」を維持するルール文化がチームを救う

### 旧版より：ブラウザエラーの予防（抜粋）

## 1. ブラウザエラーの予防

### 1.1 開発前の確認事項

- **ターゲットブラウザを明確にする**
  - プロジェクト開始時にサポートするブラウザを決める
  - `package.json`の`browserslist`で明示的に指定する

```json
{
  "browserslist": [
    ">0.2%",
    "not dead",
    "not op_mini all"
  ]
}
```

### 1.2 コーディング時の予防策

- **Can I Use で事前確認**
  - 新しいAPIや機能を使う前に https://caniuse.com/ で互換性を確認
  - 特にSafariとFirefoxの対応状況に注意

- **Polyfillの活用**
  - `core-js`や`@babel/polyfill`を使用
  - 必要な機能のみを選択的にインポート

```javascript
// 必要な機能のみインポート（推奨）
import 'core-js/features/array/includes';
import 'core-js/features/promise/finally';
```

- **Babelの適切な設定**
  - `@babel/preset-env`でターゲットブラウザに合わせて自動変換

```javascript
// babel.config.js
module.exports = {
  presets: [
    ['@babel/preset-env', {
      useBuiltIns: 'usage',
      corejs: 3
    }]
  ]
};
```

### 1.3 テスト時の予防策

- **複数ブラウザでテストする**
  - Chrome、Firefox、Safari、Edgeの最新版で動作確認
  - BrowserStackやLambdaTestなどのクロスブラウザテストツールを活用


### 旧版より：ルーティングエラーの予防（全文）

## 3. ルーティングエラーの予防

### 3.1 デプロイ環境に応じたRouter選択

- **サーバー設定が可能な場合**: `BrowserRouter`を使用
- **静的ホスティング（GitHub Pages等）**: `HashRouter`を使用
- **Vercel/Netlify**: `BrowserRouter`でOK（自動設定）

```javascript
// 静的ホスティング向け
import { HashRouter } from 'react-router-dom';

function App() {
  return (
    <HashRouter>
      <Routes>
        <Route path="/" element={<Home />} />
      </Routes>
    </HashRouter>
  );
}
```

### 3.2 サーバー設定の確認

- **Nginxの設定例**

```nginx
location / {
  try_files $uri $uri/ /index.html;
}
```

- **Apacheの設定例（.htaccess）**

```apache
<IfModule mod_rewrite.c>
  RewriteEngine On
  RewriteBase /
  RewriteRule ^index\.html$ - [L]
  RewriteCond %{REQUEST_FILENAME} !-f
  RewriteCond %{REQUEST_FILENAME} !-d
  RewriteRule . /index.html [L]
</IfModule>
```

### 3.3 ベースパスの設定

- **サブディレクトリにデプロイする場合**

```javascript
// BrowserRouterの場合
<BrowserRouter basename="/my-app">
  <Routes>...</Routes>
</BrowserRouter>

// Viteの場合（vite.config.js）
export default defineConfig({
  base: '/my-app/'
});
```

### 旧版より：フォーム・ボタン関連エラーの予防（全文）


## 6. フォーム・ボタン関連エラーの予防

### 6.1 ボタンのtype属性を明示する

```javascript
// NG: type省略時は"submit"になる
<button onClick={handleEdit}>編集</button>

// OK: 送信以外のボタンは"button"を明示
<button type="button" onClick={handleEdit}>編集</button>

// OK: 送信ボタンは"submit"を明示
<button type="submit">送信</button>
```

### 6.2 フォーム送信のデフォルト動作を防ぐ

```javascript
const handleSubmit = (e) => {
  e.preventDefault(); // ページリロードを防止
  // フォーム処理
};

<form onSubmit={handleSubmit}>
  <input type="text" value={value} onChange={e => setValue(e.target.value)} />
  <button type="submit">送信</button>
</form>
```

### 6.3 イベントの伝播を制御する

```javascript
// 親要素へのイベント伝播を止める
const handleClick = (e) => {
  e.stopPropagation();
  // 処理
};
```

## 7. 開発時のチェックリスト

### コーディング前

- [ ] ターゲットブラウザを確認したか
- [ ] 使用するAPIの互換性を確認したか
- [ ] 状態設計を検討したか

### コーディング中

- [ ] useStateの更新はコールバック形式を使っているか
- [ ] useEffectの依存配列は正しいか
- [ ] useEffectにクリーンアップ関数があるか
- [ ] ボタンのtype属性を明示しているか
- [ ] フォームでpreventDefaultを呼んでいるか

### コーディング後

- [ ] コンソールに警告やエラーがないか
- [ ] React DevToolsでレンダリング回数を確認したか
- [ ] 複数ブラウザでテストしたか
- [ ] ネットワークエラー時の動作を確認したか
