# 17-4 メモリリーク（購読解除・Abort・ガード）

## 🎯 この章で学ぶこと

- React アプリで起きるメモリリークの主な原因 5 つを整理する
- `useEffect` のクリーンアップで購読解除を行う基本パターン
- `AbortController` を使った fetch のキャンセル
- `isMounted` ガードと、その代替策
- Chrome DevTools の Memory タブでヒープスナップショットを取る方法

## 📖 概念の説明

### メモリリークとは

「使い終わったメモリが解放されないまま溜まり続ける現象」です。短期間ならアプリは動きますが、長く使うと

- ブラウザが重くなる
- スマホのバッテリーが減る
- 「Aw, Snap!」（タブクラッシュ）が出る
- 警告: `Can't perform a React state update on an unmounted component`

といった症状が出ます。

### 主な原因 5 つ

1. **購読解除忘れ**: `addEventListener` / `setInterval` / `subscribe` を解除していない
2. **fetch のキャンセル忘れ**: アンマウント後にレスポンスが来て setState される
3. **WebSocket / EventSource の close 忘れ**
4. **巨大オブジェクトの参照保持**: useRef やクロージャで掴み続ける
5. **DOM 直接操作**: 自分で append したノードを remove していない

### `useEffect` の cleanup

`useEffect` は `return` で関数を返すと、

- 依存が変わったとき
- アンマウントするとき

の前にその関数を呼び出します。これを「cleanup（後片付け）」と呼び、購読解除はここで行うのが鉄則。

### `AbortController`

fetch などをキャンセルする標準 API。`signal` を渡しておけば `controller.abort()` でリクエストを中断できます。

## 💻 コード例

### イベントリスナの解除

```tsx
function ScrollWatcher() {
  useEffect(() => {
    function onScroll() {
      console.log(window.scrollY);
    }
    window.addEventListener("scroll", onScroll);
    return () => window.removeEventListener("scroll", onScroll); // 必須
  }, []);
}
```

`addEventListener` には**同じ関数参照**を `removeEventListener` に渡す必要があります。アロー関数を `addEventListener` の中に直接書くと参照が取れなくなり解除できません。

### setInterval / setTimeout

```tsx
useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);
}, []);
```

これを忘れると、タブを開きっぱなしの間中ずっとタイマーが走り続けます。

### fetch のキャンセル

```tsx
function UserProfile({ id }: { id: string }) {
  const [user, setUser] = useState<User | null>(null);

  useEffect(() => {
    const ctrl = new AbortController();
    fetch(`/api/users/${id}`, { signal: ctrl.signal })
      .then((r) => r.json())
      .then(setUser)
      .catch((err) => {
        if (err.name !== "AbortError") console.error(err);
      });
    return () => ctrl.abort();
  }, [id]);

  return <div>{user?.name}</div>;
}
```

これにより、

- 連続して `id` が変わったとき、古いリクエストはキャンセルされる
- アンマウント時にもキャンセルされる

ことが保証されます。

### isMounted ガード（古典的手法）

```tsx
useEffect(() => {
  let mounted = true;
  fetchData().then((data) => {
    if (mounted) setState(data);
  });
  return () => {
    mounted = false;
  };
}, []);
```

`AbortController` が使えない API のときの代替策。React では「早期 return で setState しない」だけでも警告は消えます。

### WebSocket / EventSource

```tsx
useEffect(() => {
  const ws = new WebSocket("wss://example.com");
  ws.onmessage = handleMessage;
  return () => ws.close();
}, []);
```

```tsx
useEffect(() => {
  const es = new EventSource("/api/stream");
  es.addEventListener("update", onUpdate);
  return () => es.close();
}, []);
```

特に SPA でページ遷移してもタブが閉じない構造では、これらの解除が極めて重要。

### IntersectionObserver / ResizeObserver

```tsx
useEffect(() => {
  const target = ref.current;
  if (!target) return;
  const ob = new IntersectionObserver(callback);
  ob.observe(target);
  return () => ob.disconnect();
}, []);
```

`disconnect` を忘れると、要素が DOM から消えても監視関係が残ります。

### 大きな state の参照を持ち続けるリーク

```tsx
function Modal({ huge }: { huge: BigPayload }) {
  // クローズ後も Modal が再生成されるまで huge を保持し続ける
}
```

巨大なデータを props でずっと持ち回らない。閉じた瞬間に親側で `null` にする等で参照を切る。

### Chrome DevTools の Memory タブ

1. DevTools → Memory タブ
2. 「Heap snapshot」を取る（操作前）
3. 操作（例: モーダルを 100 回開閉）
4. もう一度 snapshot
5. Comparison ビューで Detached DOM nodes や増加しているオブジェクト数を確認

「Detached」が増え続けていたら、DOM 参照が解放されていません。

### Performance Monitor で監視

DevTools → 三点メニュー → More tools → Performance monitor。
「JS heap size」のグラフが時間と共に右肩上がりになっていればリーク疑い。健全なアプリは GC で定期的に下がります。

### よくある React 警告と対処

```
Warning: Can't perform a React state update on an unmounted component.
This is a no-op, but it indicates a memory leak in your application.
```

これは「アンマウント後に setState した」サイン。原因はほぼ間違いなく fetch / setInterval / subscribe の解除漏れ。

```tsx
useEffect(() => {
  const ctrl = new AbortController();
  load(ctrl.signal);
  return () => ctrl.abort();
}, []);
```

で 8 割解決します。

### React Query を使うとどう楽か

```tsx
function User({ id }: { id: string }) {
  const { data } = useQuery({
    queryKey: ["user", id],
    queryFn: ({ signal }) =>
      fetch(`/api/users/${id}`, { signal }).then((r) => r.json()),
  });
}
```

`signal` を `queryFn` の引数で受け取って fetch に渡すだけ。アンマウントや再フェッチ時に自動で abort してくれます。

## ❌ よくある間違い

### 1. cleanup でアロー関数を新しく書く

```tsx
useEffect(() => {
  window.addEventListener("scroll", () => log());
  return () => window.removeEventListener("scroll", () => log()); // ❌ 参照が違う
}, []);
```

同じ関数オブジェクトを使ってください。

### 2. cleanup を `async` 関数にする

```tsx
useEffect(() => {
  return async () => {
    /* ... */
  }; // ❌ React は Promise を待ってくれない
}, []);
```

cleanup は同期関数。async が必要なら内部で `void promise` する。

### 3. `setInterval` を依存配列の中の値で参照

```tsx
useEffect(() => {
  setInterval(() => doSomething(value), 1000); // value が古いまま
}, []);
```

関数形式の更新や ref を使う（[[17-3-状態管理エラー]] 参照）。

### 4. 大量の closure をログに残す

```ts
console.log({ huge });
```

開発者ツールの Console に巨大オブジェクトを送ると、それを保持し続けます。リーク調査中は console を控える。

### 5. 1 度開いたら閉じない構造

モーダルや通知パネルを「閉じても DOM に残す」設計だと、ハンドラ・購読が雪だるま式に増えます。閉じたらアンマウントする。

## ✅ ベストプラクティス

1. **`useEffect` を書いたら必ず cleanup を考える**: 「副作用 ↔ 後片付け」は対の概念。
2. **fetch には `AbortController.signal` を渡す**: コストほぼゼロで安全になる。
3. **長寿命の購読（WS/SSE）は React Query などに集約**: 自前管理を減らす。
4. **DevTools の Memory / Performance Monitor を定期的に見る**: リークは早期発見が肝心。
5. **「閉じた = アンマウント」を徹底**: モーダルや通知のレンダー条件式を素直に書く。

## 📝 まとめ

- メモリリークは「購読解除・キャンセル・ガード」の 3 つで防ぐ
- `useEffect` の cleanup を書く習慣で大半は解決
- `AbortController` で fetch を安全にキャンセル
- 警告 "state update on an unmounted component" はリークのサイン
- DevTools Memory タブで「閉じても増えるオブジェクト」を可視化

# ボタンが反応しない問題とメモリリーク

## 概要

Next.jsアプリケーションで、ボタンが反応しない問題が発生し、ページリロードで解消する場合、フロントエンド側のメモリリークやリソース管理の問題が原因である可能性が高いです。

## 問題の症状

- ボタンをクリックしても反応しない
- ページをリロードすると正常に動作する
- 時間が経つと徐々にパフォーマンスが低下する
- ブラウザのメモリ使用量が増加し続ける

## 主な原因

### 1. メモリリーク（Memory Leak）

メモリリークとは、不要になったメモリが解放されずに残り続ける状態です。これにより、アプリケーションのパフォーマンスが低下し、最終的にUIが反応しなくなることがあります。

### 2. イベントリスナーの重複登録

コンポーネントが再レンダリングされるたびにイベントリスナーが追加され、同じイベントハンドラが複数回登録されることで、予期しない動作やパフォーマンス低下を引き起こします。

### 3. 状態管理の問題

巨大な配列やオブジェクトをstateに保持し続けることで、メモリ使用量が増加し、レンダリングが重くなります。

## フロント側のリークの具体例

### 1. setInterval / setTimeout の解除忘れ

#### 問題のコード例

```typescript
// ❌ 悪い例：クリーンアップしない
useEffect(() => {
  const interval = setInterval(() => {
    console.log('Running...');
  }, 1000);
  // クリーンアップ関数がない
}, []);
```

#### 正しいコード例

```typescript
// ✅ 良い例：クリーンアップ関数で解除
useEffect(() => {
  const interval = setInterval(() => {
    console.log('Running...');
  }, 1000);

  // クリーンアップ関数でタイマーを解除
  return () => {
    clearInterval(interval);
  };
}, []);
```

#### なぜ問題なのか

- コンポーネントがアンマウントされても、タイマーが実行され続ける
- 複数回マウント/アンマウントを繰り返すと、複数のタイマーが同時に動作する
- メモリリークとパフォーマンス低下の原因となる

#### 対処法

- `useEffect`のクリーンアップ関数で必ず`clearInterval`または`clearTimeout`を呼ぶ
- 依存配列を適切に設定し、不要な再実行を防ぐ

### 2. WebSocket / EventSource の close忘れ

#### 問題のコード例

```typescript
// ❌ 悪い例：接続を閉じない
useEffect(() => {
  const ws = new WebSocket('ws://example.com');
  
  ws.onmessage = (event) => {
    setData(JSON.parse(event.data));
  };
  
  // クリーンアップ関数がない
}, []);
```

#### 正しいコード例

```typescript
// ✅ 良い例：クリーンアップ関数で接続を閉じる
useEffect(() => {
  const ws = new WebSocket('ws://example.com');
  
  ws.onmessage = (event) => {
    setData(JSON.parse(event.data));
  };
  
  // クリーンアップ関数で接続を閉じる
  return () => {
    ws.close();
  };
}, []);
```

#### EventSourceの場合

```typescript
// ✅ EventSourceの例
useEffect(() => {
  const eventSource = new EventSource('/api/events');
  
  eventSource.onmessage = (event) => {
    setData(JSON.parse(event.data));
  };
  
  return () => {
    eventSource.close();
  };
}, []);
```

#### なぜ問題なのか

- WebSocketやEventSourceは、ブラウザとサーバー間の接続を維持する
- 接続を閉じないと、不要な接続が残り続ける
- サーバー側のリソースも消費し続ける
- メモリリークとネットワークリソースの無駄遣い

#### 対処法

- コンポーネントのアンマウント時に必ず`close()`を呼ぶ
- エラーハンドリングも実装し、異常終了時にも接続を閉じる

### 3. 巨大な配列を state に溜め続けている

#### 問題のコード例

```typescript
// ❌ 悪い例：配列を無限に追加し続ける
const [messages, setMessages] = useState<string[]>([]);

useEffect(() => {
  const eventSource = new EventSource('/api/messages');
  
  eventSource.onmessage = (event) => {
    const newMessage = JSON.parse(event.data);
    // 配列に追加し続ける（削除しない）
    setMessages(prev => [...prev, newMessage]);
  };
  
  return () => {
    eventSource.close();
  };
}, []);
```

#### 正しいコード例

```typescript
// ✅ 良い例：配列のサイズを制限する
const [messages, setMessages] = useState<string[]>([]);
const MAX_MESSAGES = 100; // 最大件数を設定

useEffect(() => {
  const eventSource = new EventSource('/api/messages');
  
  eventSource.onmessage = (event) => {
    const newMessage = JSON.parse(event.data);
    setMessages(prev => {
      const updated = [...prev, newMessage];
      // 最大件数を超えたら古いものを削除
      return updated.slice(-MAX_MESSAGES);
    });
  };
  
  return () => {
    eventSource.close();
  };
}, []);
```

#### なぜ問題なのか

- 配列が無限に大きくなると、メモリ使用量が増加し続ける
- レンダリング時に大量のデータを処理するため、パフォーマンスが低下
- 仮想DOMの差分計算も重くなる
- 最終的にUIが反応しなくなる

#### 対処法

- 配列の最大サイズを設定し、古いデータを削除する
- 必要に応じて、ページネーションや仮想スクロールを実装
- 不要なデータは定期的にクリーンアップする

## その他の原因

### 4. イベントリスナーの重複登録

#### 問題のコード例

```typescript
// ❌ 悪い例：依存配列がないため、毎回リスナーが追加される
useEffect(() => {
  const handleClick = () => {
    console.log('Clicked');
  };
  
  window.addEventListener('click', handleClick);
  // クリーンアップがない
});
```

#### 正しいコード例

```typescript
// ✅ 良い例：クリーンアップ関数でリスナーを削除
useEffect(() => {
  const handleClick = () => {
    console.log('Clicked');
  };
  
  window.addEventListener('click', handleClick);
  
  return () => {
    window.removeEventListener('click', handleClick);
  };
}, []); // 空の依存配列で一度だけ実行
```

### 5. サブスクリプションの解除忘れ

#### 問題のコード例

```typescript
// ❌ 悪い例：RxJSのサブスクリプションを解除しない
useEffect(() => {
  const subscription = observable.subscribe(data => {
    setData(data);
  });
  // クリーンアップがない
}, []);
```

#### 正しいコード例

```typescript
// ✅ 良い例：サブスクリプションを解除
useEffect(() => {
  const subscription = observable.subscribe(data => {
    setData(data);
  });
  
  return () => {
    subscription.unsubscribe();
  };
}, []);
```

### 6. 大量の再レンダリング

#### 問題のコード例

```typescript
// ❌ 悪い例：毎回新しいオブジェクトを作成
const Component = () => {
  const [count, setCount] = useState(0);
  
  // 毎回新しいオブジェクトが作成される
  const config = {
    option1: true,
    option2: false,
  };
  
  return <ChildComponent config={config} />;
};
```

#### 正しいコード例

```typescript
// ✅ 良い例：useMemoでメモ化
const Component = () => {
  const [count, setCount] = useState(0);
  
  // メモ化して再作成を防ぐ
  const config = useMemo(() => ({
    option1: true,
    option2: false,
  }), []);
  
  return <ChildComponent config={config} />;
};
```

## Next.js特有の問題

### 7. サーバーサイドレンダリング（SSR）での問題

#### 問題のコード例

```typescript
// ❌ 悪い例：SSRでブラウザAPIを使用
const Component = () => {
  const [data, setData] = useState(null);
  
  // SSRではwindowが存在しない
  const ws = new WebSocket(window.location.origin);
  
  return <div>{data}</div>;
};
```

#### 正しいコード例

```typescript
// ✅ 良い例：useEffect内でブラウザAPIを使用
const Component = () => {
  const [data, setData] = useState(null);
  
  useEffect(() => {
    // クライアント側でのみ実行
    const ws = new WebSocket(window.location.origin);
    
    ws.onmessage = (event) => {
      setData(JSON.parse(event.data));
    };
    
    return () => {
      ws.close();
    };
  }, []);
  
  return <div>{data}</div>;
};
```

### 8. ルーティング時のクリーンアップ

Next.jsでは、ページ遷移時にコンポーネントがアンマウントされますが、適切にクリーンアップしないとリソースが残り続ける可能性があります。

```typescript
// ✅ ページ遷移時も確実にクリーンアップ
useEffect(() => {
  const interval = setInterval(() => {
    // 何らかの処理
  }, 1000);
  
  return () => {
    clearInterval(interval);
  };
}, []);
```

## デバッグ方法

### 1. React DevTools Profiler

React DevToolsのProfilerを使用して、再レンダリングの頻度と時間を確認します。

### 2. Chrome DevToolsのメモリプロファイラー

1. Chrome DevToolsを開く
2. Performanceタブを選択
3. Memoryタブでメモリ使用量の推移を確認
4. メモリが増加し続ける場合はリークの可能性

### 3. コンソールログで確認

```typescript
useEffect(() => {
  console.log('Component mounted');
  
  return () => {
    console.log('Component unmounted');
  };
}, []);
```

アンマウント時にログが出力されない場合は、クリーンアップが実行されていない可能性があります。

## ベストプラクティス

### 1. 必ずクリーンアップ関数を実装する

```typescript
useEffect(() => {
  // リソースの作成
  
  return () => {
    // 必ずクリーンアップを実装
  };
}, []);
```

### 2. 依存配列を適切に設定する

```typescript
// 空の配列：マウント時のみ実行
useEffect(() => {
  // ...
}, []);

// 依存配列あり：依存が変更された時のみ実行
useEffect(() => {
  // ...
}, [dependency1, dependency2]);
```

### 3. カスタムフックでリソース管理を抽象化

```typescript
// カスタムフックでリソース管理を統一
function useWebSocket(url: string) {
  const [data, setData] = useState(null);
  
  useEffect(() => {
    const ws = new WebSocket(url);
    
    ws.onmessage = (event) => {
      setData(JSON.parse(event.data));
    };
    
    return () => {
      ws.close();
    };
  }, [url]);
  
  return data;
}
```

### 4. データのサイズを制限する

```typescript
// 配列のサイズを制限
const MAX_ITEMS = 100;
setItems(prev => [...prev, newItem].slice(-MAX_ITEMS));
```

### 5. メモ化を活用する

```typescript
// useMemoで計算結果をメモ化
const expensiveValue = useMemo(() => {
  return expensiveCalculation(data);
}, [data]);

// useCallbackで関数をメモ化
const handleClick = useCallback(() => {
  // 処理
}, [dependency]);
```

## まとめ

ボタンが反応しない問題は、多くの場合メモリリークやリソース管理の問題が原因です。以下の点に注意してください：

1. **必ずクリーンアップ関数を実装する**（setInterval、setTimeout、WebSocket、EventSource等）
2. **配列やオブジェクトのサイズを制限する**
3. **イベントリスナーを適切に削除する**
4. **依存配列を適切に設定する**
5. **メモ化を活用して不要な再レンダリングを防ぐ**

ページリロードで解消するのは、リロード時にすべてのリソースがリセットされるためです。根本的な解決には、適切なリソース管理とクリーンアップの実装が必要です。
