# 7-1 フロントのデータフロー（UI ← 状態 ← API）

## 🎯 この章で学ぶこと

- フロントエンドにおける「データの流れ」を俯瞰できるようになります
- UI、状態、APIの3層が何の役割を持っているかを理解できます
- データが「どこから来て、どこに溜まり、どう表示されるか」を説明できます
- なぜこの分け方が大事なのかが分かります
- 自分のアプリで、各層をどう設計するかの指針を持てるようになります

## 📖 概念の説明

### データはどこから来てどこへ行くのか

Webアプリのデータの流れは、すごく単純化すると次のようになります。

```
[サーバー（DB）] ⇄ [API] ⇄ [フロント状態] ⇄ [UI]
```

- **サーバー（DB）**：本物のデータが置いてある場所（PostgreSQL、Firestore など）
- **API**：そのデータを取り出すためのインターフェース（HTTPエンドポイント、`/api/users` など）
- **フロント状態**：ブラウザ側のメモリに置かれたデータ（`useState`、Zustand、TanStack Query のキャッシュなど）
- **UI**：ユーザーが見る画面（Reactコンポーネント）

このフローを **「UI ← 状態 ← API」** と読むと、上流から下流への流れが見えます。

例えるなら、**スーパーマーケット** をイメージしてください。

- DB = 倉庫
- API = 倉庫からの搬入経路
- フロント状態 = 売場の陳列棚
- UI = お客様の目の前のディスプレイ

倉庫から商品を取り出して、陳列棚に並べて、お客さんに見せる。逆方向（買う、注文する）の流れもありますね。

### 3層を分けて考えるメリット

1. **UI** はデータの取得方法を知らなくていい → 見た目の変更がしやすい
2. **状態** がデータをまとめて持つ → キャッシュや更新がしやすい
3. **API** が通信を一手に引き受ける → エンドポイントの変更が楽

これは「**関心の分離（Separation of Concerns）**」と呼ばれる、ソフトウェア設計の基本原則です。

### データ取得（read）と更新（write）

フロント・サーバー間のやり取りには大きく2方向あります。

- **取得（GET）**：データを読み取って画面に表示する
- **更新（POST/PUT/PATCH/DELETE）**：データを作成・変更・削除する

これに対応してフロント側でも、

- **取得**：`useQuery` 的なパターン（データを引っ張ってきてキャッシュする）
- **更新**：`useMutation` 的なパターン（変更してサーバーに送る）

という2系統の処理が出てきます。

### データの「鮮度」という考え方

サーバーのデータは時々刻々と変わります。フロントが持っているデータは、所詮 **古い可能性がある「コピー」** です。これを意識すると、

- いつ取り直す？（フォーカス時、間隔で、明示的に）
- どれくらい新しければOK？（5秒、5分、永遠？）
- 古さを許容するか、リアルタイムで反映したいか？

といった設計判断ができるようになります。

### 用語の整理

- **API**：プログラム同士がやり取りするための窓口
- **REST**：APIの設計スタイルのひとつ。`GET /users/123` のような形
- **状態管理**：フロントでデータを持って管理すること
- **キャッシュ**：取得したデータを再利用するために保存しておく仕組み
- **fetch**：JavaScriptの組み込みAPI。HTTPリクエストを送る

## 💻 コード例

### 例1：3層を意識したコンポーネント構造

```jsx
// services/userApi.js（API層）
export async function fetchUser(id) {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) throw new Error('取得失敗');
  return res.json();
}

// hooks/useUser.js（状態層）
import { useEffect, useState } from 'react';
import { fetchUser } from '../services/userApi';

export function useUser(id) {
  const [user, setUser] = useState(null);
  const [error, setError] = useState(null);
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    setLoading(true);
    fetchUser(id)
      .then(setUser)
      .catch(setError)
      .finally(() => setLoading(false));
  }, [id]);

  return { user, error, loading };
}

// pages/UserPage.jsx（UI層）
import { useUser } from '../hooks/useUser';

export default function UserPage({ id }) {
  const { user, error, loading } = useUser(id);

  if (loading) return <p>読み込み中...</p>;
  if (error) return <p>エラー: {error.message}</p>;
  if (!user) return null;

  return <h1>{user.name}</h1>;
}
```

3つのファイルにきれいに分かれています。

- **API層** はfetchの詳細を知っている
- **状態層** はそれを使って `loading/error/data` の3点セットを返す
- **UI層** は3点セットを受け取って描画する

このパターンを覚えると、応用が利きます。

### 例2：UIから見たデータフロー

```jsx
function ProductList() {
  // 1. 状態を取得（中で内部的にAPIを呼んでいる）
  const { products, loading, error } = useProducts();

  // 2. 状態に応じて見た目を切り替える
  if (loading) return <Spinner />;
  if (error) return <ErrorBox error={error} />;
  if (products.length === 0) return <EmptyState />;

  // 3. データを描画する
  return (
    <ul>
      {products.map(p => <li key={p.id}>{p.name}</li>)}
    </ul>
  );
}
```

UIコンポーネントは「状態を見て、画面を作る」ことに集中しています。

### 例3：書き込みの流れ（Mutation）

```jsx
// API層
export async function createPost(data) {
  const res = await fetch('/api/posts', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(data),
  });
  if (!res.ok) throw new Error('作成失敗');
  return res.json();
}

// UI層
function NewPostForm() {
  const [title, setTitle] = useState('');
  const [submitting, setSubmitting] = useState(false);

  const handleSubmit = async (e) => {
    e.preventDefault();
    setSubmitting(true);
    try {
      await createPost({ title });
      setTitle(''); // 成功したらフォームをクリア
    } catch (err) {
      alert(err.message);
    } finally {
      setSubmitting(false);
    }
  };

  return (
    <form onSubmit={handleSubmit}>
      <input value={title} onChange={(e) => setTitle(e.target.value)} />
      <button disabled={submitting}>{submitting ? '送信中...' : '投稿'}</button>
    </form>
  );
}
```

**入力 → 状態 → API → サーバー** という方向の流れもあります。

### 例4：状態管理ライブラリを使う場合（概念図）

```jsx
// TanStack Query を使うと、状態層が大幅に簡略化される
import { useQuery } from '@tanstack/react-query';

function UserPage({ id }) {
  const { data, isLoading, error } = useQuery({
    queryKey: ['user', id],
    queryFn: () => fetchUser(id),
  });

  if (isLoading) return <p>...</p>;
  if (error) return <p>エラー</p>;
  return <h1>{data.name}</h1>;
}
```

3層の考え方は変わりません。状態層をライブラリが代行してくれているだけです（[[7-5-データ取得ライブラリ]]）。

### 例5：データフローの全体像（コメント）

```jsx
/*
[ユーザー操作]
   ↓ クリック・入力
[UI（コンポーネント）]
   ↓ ハンドラ呼び出し
[状態管理（カスタムフック）]
   ↓ APIサービス呼び出し
[APIラッパー（services/）]
   ↓ fetch
[サーバー（HTTP）]
   ↓ DBクエリ
[データベース]

逆方向：
[DB] → [サーバー応答] → [API層] → [状態層に格納] → [UI再描画]
*/
```

## ❌ よくある間違い

### 1. UIコンポーネントの中で直接 `fetch` を呼ぶ

```jsx
// ❌ UIにfetchが混在
function UserPage({ id }) {
  const [user, setUser] = useState(null);
  useEffect(() => {
    fetch(`/api/users/${id}`).then(r => r.json()).then(setUser);
  }, [id]);
  return <h1>{user?.name}</h1>;
}
```

短いプロトタイプならOKですが、規模が大きくなったら必ず層を分けましょう。

### 2. APIエンドポイントをUIに直書き

```jsx
// ❌ URLをUIに書くと、変更時にあちこち探すハメに
fetch('/api/v2/users/' + id)
```

API呼び出しは関数（サービス層）にまとめるのが鉄則。

### 3. 状態とサーバーの値の同期を怠る

「ローカルでフォームを編集 → 保存ボタン」のあと、サーバーから最新データを取り直さないと、画面とDBがズレます。「保存後にrefetch」「楽観更新後にinvalidate」など、同期の仕組みを意識しましょう。

### 4. すべてグローバル状態にする

「データはぜんぶ Context や Zustand に入れよう」とすると、規模が大きくなるとパフォーマンスが落ちます。**サーバー由来のデータは TanStack Query** などのデータ取得ライブラリで管理する方が、キャッシュ・再検証の恩恵を受けられます。

## ✅ ベストプラクティス

1. **3層を分ける**：API層、状態層、UI層。フォルダもこの単位で分けるのが一般的。
2. **fetchはサービス層に集約**：UIから直接fetchを呼ばない。
3. **状態は loading / error / data の3点セット**：このパターンを基本に考える。
4. **サーバー由来のデータには専用ライブラリ**：TanStack Query や SWR がおすすめ。
5. **データの鮮度を意識する**：いつ取り直すか、いつまで使い続けるかを設計する。

## 🔬 実践演習

### お題：3層構造でユーザー一覧を作る

- `services/userApi.js`：`fetchUsers()` を export
- `hooks/useUsers.js`：`{ users, loading, error }` を返す
- `pages/UsersPage.jsx`：UIだけを担当

の3ファイルに分けて実装してみましょう。

### 発展課題

- 投稿フォームを追加し、`createPost` を `services/postApi.js` に書く
- 投稿成功後にユーザー一覧を再取得する仕組みを足す（後の章で扱うキャッシュの考えに繋がります）

## 📝 まとめ

- フロントのデータフローは「UI ← 状態 ← API ← サーバー」
- 3層を分けることで関心が整理され、変更に強いコードになります
- 取得（GET）と更新（POST/PUT/DELETE）の2系統がある
- データには「鮮度」という時間軸の概念がある
- サーバー由来のデータは専用ライブラリに任せると幸せ
