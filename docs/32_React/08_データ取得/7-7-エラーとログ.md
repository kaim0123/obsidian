# 7-7 エラーとログ（原因切り分けの型）

## 🎯 この章で学ぶこと

- フロント・サーバー間のエラーを分類できるようになります
- エラーの原因を切り分ける思考の型を身につけられます
- 開発者向けのログとユーザー向けのメッセージを使い分けられます
- エラーバウンダリ・グローバルエラーハンドリングの基本を知ります
- Sentryなどのエラー監視ツールの存在意義を理解できます

## 📖 概念の説明

### エラーは大きく4種類

データ取得周りで起きるエラーは、ざっくり次の4つに分類できます。

1. **ネットワークエラー**：そもそも繋がらない、タイムアウトした
2. **HTTPエラー**：4xx（クライアントが悪い）、5xx（サーバーが悪い）
3. **パースエラー**：返ってきたデータがJSONじゃない、形式が想定外
4. **アプリ内エラー**：取得は成功したが、その後のコードで例外発生

それぞれ **原因と対策が違う** ので、まず分類することが重要です。

例えるなら、医者が「お腹が痛い」患者を診るとき、

- 食中毒（外部要因）
- 内臓疾患（自己要因）
- 心因性（メンタル要因）

を切り分けないと正しい治療ができないのと同じです。

### 切り分けの型

不具合に出会ったとき、次の順で確認します。

1. **ブラウザのDevTools → Network タブ**
   - リクエストは飛んでいる？
   - ステータスコードは？
   - レスポンスの中身は？

2. **Console タブ**
   - エラーメッセージとスタックトレース
   - `console.error` の出力

3. **サーバー側のログ**
   - 同じ時刻のサーバーログを確認

4. **再現条件の特定**
   - 特定のユーザーだけ？特定のデータ？特定のブラウザ？

この順番で見れば、ほぼ原因が絞れます。

### ログの2層構造

**開発者向けログ**：詳細・技術的・原因特定に必要な情報
**ユーザー向けメッセージ**：分かりやすく、次のアクションを示す

両方を分けて設計するのがベストプラクティスです。

```jsx
try {
  await api.save();
} catch (err) {
  console.error('保存失敗:', err); // 開発者向け（詳細）
  alert('保存できませんでした。時間を置いて再度お試しください。'); // ユーザー向け
}
```

### ユーザー向け文言は「アプリ側で決めて」マッピングする

API が返す `data.message`（生の説明文）を、そのままユーザーに表示するのは避けます。

- **言語/口調がバラバラ**になりやすい（英語が混ざる等）
- サービス都合で **文言が突然変わる**ことがある
- 場合によっては **内部情報が混ざる**リスクもある

そのため、ユーザーに見せる文言は **HTTPステータス等からアプリ側でマッピング**します。

```ts
function toUserFacingError(status: number): string {
  if (status === 429)
    return '送信回数の上限に達しました。しばらく時間をおいて再度お試しください。';
  if (status >= 500)
    return 'サーバーで問題が発生しました。しばらく時間をおいて再度お試しください。';
  return '送信に失敗しました。入力内容をご確認のうえ、再度お試しください。';
}
```

### エラー監視ツール

ローカルでは `console.error` で十分ですが、本番環境ではユーザーの環境で起きたエラーを把握できません。**Sentry**、**Datadog**、**Rollbar** などのエラー監視ツールが必要です。

- 本番でユーザーが踏んだエラーを自動で集約
- スタックトレース、再現手順、ユーザー情報がまとめて見られる
- Slack通知や担当者割り当てができる

無料プランでも始められるので、導入を検討する価値があります。

### 用語の整理

- **スタックトレース**：エラー発生時の関数呼び出し履歴
- **エラーバウンダリ**：Reactコンポーネントツリー内のエラーをキャッチする機能
- **エラー監視ツール**：本番環境のエラーを集約するサービス
- **トランザクションID / リクエストID**：1つのリクエストに付ける識別子。ログ追跡に使う

## 💻 コード例

### 例1：エラーを分類する

```js
async function safeFetch(url) {
  try {
    const res = await fetch(url);

    if (!res.ok) {
      // HTTPエラー
      const body = await res.json().catch(() => ({}));
      const error = new Error(body.message || `HTTP ${res.status}`);
      error.kind = 'http';
      error.status = res.status;
      throw error;
    }

    try {
      return await res.json();
    } catch (e) {
      // パースエラー
      const error = new Error('レスポンスの解析に失敗しました');
      error.kind = 'parse';
      throw error;
    }
  } catch (e) {
    if (e.kind) throw e;
    // ネットワークエラー（fetchがrejectされた）
    const error = new Error('ネットワークエラー');
    error.kind = 'network';
    error.cause = e;
    throw error;
  }
}
```

`error.kind` に種別を付けると、呼び出し側で分岐しやすくなります。

### 例2：種別ごとのユーザーメッセージ

```jsx
function getMessage(error) {
  switch (error.kind) {
    case 'network':
      return 'インターネット接続を確認してください';
    case 'http':
      if (error.status === 401) return 'ログインが必要です';
      if (error.status === 403) return '権限がありません';
      if (error.status === 404) return 'データが見つかりません';
      if (error.status >= 500) return 'サーバーで問題が発生しました';
      return 'リクエストに問題があります';
    case 'parse':
      return 'データの解析に失敗しました';
    default:
      return '予期しないエラーが発生しました';
  }
}

function ErrorView({ error }) {
  return (
    <div role="alert">
      <h3>エラーが発生しました</h3>
      <p>{getMessage(error)}</p>
    </div>
  );
}
```

ユーザーには「**何が悪かったか・どうすべきか**」を分かりやすく伝えます。

### catch 側の文言は「通信エラー」寄りにする

`catch` に入るのは、次のような **通信不成立/例外** のケースが多いです。

- ネットワーク断、DNS、タイムアウト
- CORS などで fetch が reject された
- 予期しない例外

一方で「レスポンスは返ってきたが `res.ok === false`」は HTTPエラーです。**原因が違うので文言も分ける**と、ユーザーが次に取るべき行動が明確になります。

```js
try {
  // ...
} catch (err) {
  alert(
    '通信エラーが発生しました。ネットワーク接続をご確認のうえ、再度お試しください。',
  );
  throw err;
}
```

### 例3：開発者向けログを充実させる

```js
function logError(label, error, context = {}) {
  console.group(`❌ ${label}`);
  console.error('error:', error);
  console.log('stack:', error.stack);
  console.log('context:', context);
  console.log('time:', new Date().toISOString());
  console.groupEnd();
}

// 使用例
try {
  await api.saveOrder({ id: 123 });
} catch (err) {
  logError('注文保存失敗', err, { orderId: 123, userId: 'u-456' });
}
```

`console.group` で見やすくまとめます。**何をしようとして失敗したか** をcontextに入れると追跡しやすい。

### 例4：エラーバウンダリ

```jsx
class ErrorBoundary extends React.Component {
  state = { error: null };

  static getDerivedStateFromError(error) {
    return { error };
  }

  componentDidCatch(error, info) {
    // 開発者向けログ
    console.error('レンダリングエラー:', error);
    console.error('component stack:', info.componentStack);
    // 本番なら Sentry.captureException(error) など
  }

  render() {
    if (this.state.error) {
      return (
        <div>
          <h1>申し訳ありません、エラーが発生しました</h1>
          <button onClick={() => this.setState({ error: null })}>再試行</button>
        </div>
      );
    }
    return this.props.children;
  }
}

// 使い方
<ErrorBoundary>
  <App />
</ErrorBoundary>
```

レンダリング中の同期エラーをキャッチします。**非同期エラー（fetch失敗）はキャッチしない** ので注意。

### 例5：グローバルエラーハンドリング

```js
// Promiseのrejectを未処理のまま捨てたとき
window.addEventListener('unhandledrejection', (event) => {
  console.error('未処理のPromise:', event.reason);
  // Sentry.captureException(event.reason);
});

// その他のエラー
window.addEventListener('error', (event) => {
  console.error('グローバルエラー:', event.error);
});
```

どこにも `try/catch` がない非同期エラーをキャッチする最後の砦です。

### 例6：Sentryの基本セットアップ

```js
// main.jsx
import * as Sentry from '@sentry/react';

Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  environment: import.meta.env.MODE, // 'development' or 'production'
  tracesSampleRate: 0.1,
});

// エラー送信
try {
  await api.save();
} catch (err) {
  Sentry.captureException(err);
  throw err;
}
```

これで本番のエラーがダッシュボードで見られるようになります。

### 例7：リクエストIDでトレースする

```js
async function apiCall(path) {
  const requestId = crypto.randomUUID();
  console.log(`[${requestId}] -> ${path}`);

  try {
    const res = await fetch(path, {
      headers: { 'X-Request-Id': requestId },
    });
    if (!res.ok) throw new Error(`HTTP ${res.status}`);
    console.log(`[${requestId}] <- OK`);
    return res.json();
  } catch (err) {
    console.error(`[${requestId}] <- ERROR`, err);
    throw err;
  }
}
```

サーバー側でも同じIDをログに出せば、フロントとサーバーのログが結びつき、原因追跡が劇的に楽になります。

### 例8：ユーザーから報告を受けたときの確認手順

```
1. いつ？
   - エラー発生日時を聞く

2. 何をしていたら？
   - 操作手順を聞く

3. ブラウザのコンソールに何か出ていた？
   - DevTools開いてもらう

4. ネットワーク状況は？
   - 4xx？5xx？タイムアウト？

5. ユーザーIDで本番ログを検索
   - サーバー側のログを確認
```

このフローを社内でテンプレ化しておくと、サポート対応がスムーズになります。

## ❌ よくある間違い

### 1. catch で握りつぶす

```js
try {
  await fetch(...);
} catch {} // ❌ 何も起きないように見えてバグの温床
```

最低でも `console.error`、できればユーザー通知＋エラー監視に送る。

### 2. 全エラーを `Error: Something went wrong` で済ませる

```jsx
return <p>エラーが発生しました</p>; // 不親切
```

種別ごとにメッセージを分けましょう。

### 3. エラー時のスタックトレースを潰す

```js
catch (err) {
  throw new Error('保存失敗'); // ❌ 元のerrの情報が消える
}

// ✅ cause を使う（ES2022〜）
catch (err) {
  throw new Error('保存失敗', { cause: err });
}
```

### 4. エラーバウンダリで非同期エラーを期待

エラーバウンダリは **同期エラー専用**。fetch失敗などは個別に `try/catch` する必要があります。

### 5. console.log だけでエラー監視を済ませる

開発時はそれでよいですが、本番で起きたエラーは見えません。Sentry等を導入しましょう。

## ✅ ベストプラクティス

1. **エラーを分類する**：network/http/parse/app の4分類が基本。
2. **開発者向けとユーザー向けを分ける**：詳細ログと優しいメッセージ。
3. **エラーバウンダリ＋グローバルハンドラを用意**：取りこぼしを減らす。
4. **本番にはエラー監視ツール**：Sentryなどを必ず導入。
5. **リクエストIDでトレース可能に**：フロント・サーバーのログを結びつける。

## 🔬 実践演習

### お題：エラー切り分けの実装

`safeFetch` 関数を作り、ネットワークエラー・HTTPエラー・パースエラーを **`error.kind`** で区別して投げ分けてみましょう。コンポーネントでは `getMessage(error)` を使って種別ごとに違うメッセージを表示します。

### 発展課題

- エラーバウンダリを導入して、レンダリング中のエラーをキャッチしてみましょう
- `unhandledrejection` のグローバルリスナーを設定し、未処理のPromiseを拾ってみましょう
- 開発環境にSentryを導入し、エラーがダッシュボードに届くことを確認しましょう

## 📝 まとめ

- エラーは「ネットワーク・HTTP・パース・アプリ内」の4種類に分類できます
- 開発者向けログ（詳細）とユーザー向けメッセージ（優しい）を分けます
- エラーバウンダリ＋グローバルハンドラ＋エラー監視で多層防御
- リクエストIDでフロント・サーバーのログを連携
- 「catchで握りつぶす」は最大のアンチパターン
