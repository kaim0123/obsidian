# 7-6 キャッシュ・再検証・楽観更新（概要）

## 🎯 この章で学ぶこと

- キャッシュの目的と仕組みを理解できます
- 「再検証（revalidation）」の考え方が分かります
- staleTime と gcTime の違いを覚えます
- 楽観的更新（optimistic update）が何を解決するかを学びます
- これらをTanStack Queryで実践する方法を知ります

## 📖 概念の説明

### キャッシュってなに？

**キャッシュ（cache）** とは、一度取得したデータを保存しておいて、次回以降は再取得せずに使い回す仕組みです。

例えるなら、**冷蔵庫** のようなものです。スーパー（サーバー）まで毎回買いに行かなくても、冷蔵庫（キャッシュ）から取り出して使える。素早いし、ネットワーク負荷も減ります。

ただし、冷蔵庫の中身は時間が経つと **古くなる**。これがキャッシュの本質的な問題です。

### 再検証（revalidation）

「キャッシュにあるデータ、実は古いかもしれない。念のため確認しよう」というのが **再検証** です。冷蔵庫の中身がまだ食べられるか、賞味期限を確認するイメージ。

TanStack Queryでは、次のタイミングで自動的に再検証が走ります。

- **コンポーネントがマウントされたとき**（マウント時）
- **ウィンドウがフォーカスされたとき**（タブ切り替えで戻ってきたとき）
- **ネットワークが復帰したとき**
- **指定間隔ごと**（`refetchInterval`）

これらは全部オプションで切り替えられます。

### staleTime と gcTime

TanStack Queryの2つの重要な時間設定です。

**staleTime（スタイルタイム）**：「**新鮮**」とみなす時間。これが過ぎると `stale`（古い）になり、再検証が走るようになります。デフォルト0msなので、何もしないとマウントごとに毎回再取得します。

**gcTime（旧cacheTime）**：「**メモリに保持**」する時間。コンポーネントがアンマウントされてからこの時間を超えると、ガベージコレクションでキャッシュが消えます。デフォルト5分。

例えるなら、

- staleTime = **賞味期限**（これを過ぎたら念のため確認）
- gcTime = **使用期限**（これを過ぎたら捨てる）

### 楽観的更新（optimistic update）

通常の更新フローは「**送信 → 待つ → 成功したら画面更新**」ですが、これだとユーザーは待たされます。

**楽観的更新** とは、「成功するだろう」と先に画面を書き換えて、サーバーに送る方式です。サーバーから失敗が返ってきたら巻き戻します。

例えるなら、「いいね」ボタンを押した瞬間にハートが赤くなるあの感じ。実際にはまだサーバー処理中ですが、UI上は反応してくれる。**体感が爆速** になります。

「楽観的（optimistic）」という名前は、「成功するという楽観的な前提で先に動く」から来ています。

### 用語の整理

- **キャッシュ**：取得済みデータの保存場所
- **stale（古い）**：再検証が必要な状態
- **fresh（新鮮）**：再検証不要な状態
- **invalidate（無効化）**：手動で「古い」とマークすること
- **再検証（revalidation）**：キャッシュデータが正しいか確認する処理
- **楽観的更新**：サーバー応答を待たずに画面を更新する手法

## 💻 コード例

### 例1：staleTime を使ったキャッシュ調整

```jsx
import { useQuery } from '@tanstack/react-query';

function CountriesList() {
  const { data } = useQuery({
    queryKey: ['countries'],
    queryFn: fetchCountries,
    staleTime: 60 * 60 * 1000, // 1時間は再取得しない
  });

  return <ul>{data?.map(c => <li key={c.code}>{c.name}</li>)}</ul>;
}
```

国名のリストはほぼ変わらないデータなので、長めの `staleTime` を設定。フォーカスのたびに取り直す無駄が省けます。

### 例2：頻繁に更新したいデータ

```jsx
useQuery({
  queryKey: ['notifications'],
  queryFn: fetchNotifications,
  staleTime: 0,                // すぐ古いとみなす
  refetchInterval: 30 * 1000,  // 30秒ごとに自動再取得
});
```

通知データなど、リアルタイム性が必要なものは積極的に再取得します。

### 例3：手動で invalidate する

```jsx
import { useMutation, useQueryClient } from '@tanstack/react-query';

function DeleteButton({ id }) {
  const queryClient = useQueryClient();

  const mutation = useMutation({
    mutationFn: () => fetch(`/api/posts/${id}`, { method: 'DELETE' }),
    onSuccess: () => {
      // 投稿一覧を「古い」とマーク → 自動で再取得が走る
      queryClient.invalidateQueries({ queryKey: ['posts'] });
    },
  });

  return <button onClick={() => mutation.mutate()}>削除</button>;
}
```

### 例4：楽観的更新（いいねボタン）

```jsx
import { useMutation, useQueryClient } from '@tanstack/react-query';

function LikeButton({ postId, liked }) {
  const queryClient = useQueryClient();

  const mutation = useMutation({
    mutationFn: () => fetch(`/api/posts/${postId}/like`, { method: 'POST' }),

    // 1. 送信前にキャッシュを書き換える
    onMutate: async () => {
      // 進行中のクエリをキャンセル
      await queryClient.cancelQueries({ queryKey: ['post', postId] });

      // 現在のキャッシュを保存（巻き戻し用）
      const prev = queryClient.getQueryData(['post', postId]);

      // キャッシュを楽観的に書き換え
      queryClient.setQueryData(['post', postId], (old) => ({
        ...old,
        liked: !old.liked,
        likeCount: old.likeCount + (old.liked ? -1 : 1),
      }));

      return { prev }; // contextとして次のハンドラに渡す
    },

    // 2. エラー時は巻き戻す
    onError: (err, variables, context) => {
      if (context?.prev) {
        queryClient.setQueryData(['post', postId], context.prev);
      }
    },

    // 3. 成功・失敗どちらでも最終的に再検証
    onSettled: () => {
      queryClient.invalidateQueries({ queryKey: ['post', postId] });
    },
  });

  return <button onClick={() => mutation.mutate()}>{liked ? '❤️' : '🤍'}</button>;
}
```

少し長いですが、これがTanStack Queryで楽観的更新する定番パターンです。**ボタンを押した瞬間に色が変わる** UXが得られます。

### 例5：シンプルなトグル系の楽観更新

```jsx
const mutation = useMutation({
  mutationFn: toggleFavorite,
  onMutate: (id) => {
    // 関連キャッシュを楽観的に更新
    queryClient.setQueryData(['favorites'], (old = []) =>
      old.includes(id) ? old.filter(x => x !== id) : [...old, id]
    );
  },
  onError: () => {
    // 失敗したら再取得して同期
    queryClient.invalidateQueries({ queryKey: ['favorites'] });
  },
});
```

### 例6：refetchOnWindowFocus を使い分ける

```jsx
// 重要なデータはフォーカスで再取得
useQuery({
  queryKey: ['stock-prices'],
  queryFn: fetchPrices,
  refetchOnWindowFocus: true, // デフォルト
});

// フォーカスで再取得すると邪魔なデータ
useQuery({
  queryKey: ['user-profile'],
  queryFn: fetchProfile,
  refetchOnWindowFocus: false, // タブ切り替えでもfetchしない
});
```

### 例7：プリフェッチ（先読み）

```jsx
function ProductLink({ id, name }) {
  const queryClient = useQueryClient();

  // ホバー時に先読み
  const prefetch = () => {
    queryClient.prefetchQuery({
      queryKey: ['product', id],
      queryFn: () => fetchProduct(id),
      staleTime: 30 * 1000,
    });
  };

  return (
    <Link to={`/products/${id}`} onMouseEnter={prefetch}>
      {name}
    </Link>
  );
}
```

ユーザーがクリックする前にデータを取りに行っておくと、遷移先が **一瞬で表示される** ようになります。

### 例8：手動でキャッシュを直接読み書き

```jsx
const cached = queryClient.getQueryData(['users']); // 取得
queryClient.setQueryData(['users'], (old) => [...old, newUser]); // 更新
```

楽観更新やソート切り替えなどで、サーバーを叩かずに即座にキャッシュをいじりたいときに使います。

## ❌ よくある間違い

### 1. staleTime を 0 のまま使い続ける

デフォルトの `staleTime: 0` は「マウントごとに再取得」なので、画面遷移のたびに無駄なリクエストが走ります。**動的でないデータは長めに設定** しましょう。

### 2. 楽観更新の巻き戻しを書き忘れる

```jsx
// ❌ 失敗してもUIが書き換わったまま
onMutate: () => {
  queryClient.setQueryData(...);
}
// onErrorで巻き戻す処理がない
```

必ず `onError` で巻き戻し処理を書きましょう。

### 3. invalidate と refetch の使い分けがあいまい

- `invalidateQueries`：「古い」マークを付ける。**マウント中なら自動で再取得が走る**
- `refetchQueries`：今すぐ強制的に再取得

通常は `invalidateQueries` で十分。

### 4. 楽観更新で巻き戻しに対応しない確定的な変更を行う

「いいねカウントを表示順に並べ替える」のような、複雑な副作用を伴う楽観更新は、巻き戻しが難しくなりバグの温床に。**シンプルなトグルや数値増減** に留めるのが安全です。

### 5. 全部のクエリに楽観更新を入れる

実装コストが高いので、**ユーザー体験の効果が高い場所だけ** に絞りましょう。「いいね」「お気に入り」「TODOチェック」など、瞬時に反応してほしい操作に。

## ✅ ベストプラクティス

1. **データの性質に合わせて staleTime を調整**：マスターデータは長く、リアルタイム性が要るものは短く。
2. **mutation 成功時の invalidateQueries を忘れない**：データの一貫性を保つ。
3. **楽観更新は効果の高いトグル系から**：いきなり全部入れない。
4. **巻き戻しは必須**：失敗時に画面が嘘をつかないように。
5. **DevToolsで動きを確認**：キャッシュの遷移が見えると感動します。

## 🔎 深掘り：キャッシュ戦略（React視点での整理）

この章のメインは「TanStack Queryによる *サーバー状態* のキャッシュ」です。一方で、Webのキャッシュにはいくつかレイヤーがあり、混同すると設計判断を誤りやすいです。

### キャッシュのレイヤー（ざっくり）

- **ブラウザ（HTTPキャッシュ）**：`Cache-Control` などで、静的ファイルやGETレスポンスの再利用を制御
- **Service Worker**：オフライン/バックグラウンド更新など、ブラウザ内でより積極的に制御できる
- **CDN**：地理的に近いエッジで配信し、TTFBとオリジン負荷を下げる
- **サーバー/DB（Redisなど）**：アプリケーション内部の読み取り高速化・負荷平準化
- **アプリ内（TanStack Query等）**：UIが必要とする「サーバー状態」を画面単位で賢く再利用

### 代表的なキャッシュ戦略（一般論）

- **Cache-Aside**：アプリが「キャッシュを見る → なければ取得して保存」を主導（最もよく使う）
- **Read-Through**：キャッシュ層が裏側で取得までやってくれる（アプリはキャッシュだけ見ればよい）
- **Write-Through**：書き込みを「DB＋キャッシュ」へ同時反映（整合性は取りやすいが遅くなりがち）
- **Write-Behind**：書き込みをいったんキャッシュに反映し、DBは非同期（速いが障害時の難易度が上がる）

React/TanStack Queryの文脈では「取得系はCache-Aside寄り」「更新系は *楽観更新→失敗時巻き戻し→invalidateで再同期* 」が実務での基本形です。

### キャッシュキー設計（フロントでも重要）

- **一意性**：`['users', userId]` のように *リソースと引数* を含める
- **階層性**：一覧 `['users']` と詳細 `['users', id]` を揃えると invalidate がやりやすい
- **粒度**：大きすぎるキャッシュは局所更新が難しく、小さすぎると管理が複雑になる

## 🔬 深掘り：実装とベストプラクティス（補足）

「再検証」「重複排除」「キャッシュ更新」は、ライブラリが違っても目的は似ています。考え方を揃えておくと、React Query / SWR / 自前実装の比較がしやすくなります。

### SWRでの用語対応（目安）

- **revalidation**：フォーカス復帰などでの再取得（React Queryの `refetchOnWindowFocus` に近い）
- **dedupingInterval**：短時間の重複リクエスト抑制（React Queryの同一 `queryKey` の共有に近い）

### Service Worker / CDN は「別章」で扱う

Service Worker や CDN を含む「配信・エッジ」寄りの話は、Reactコンポーネントのキャッシュとは設計判断が別軸になりやすいので、次章として分離しました。

## 🔬 実践演習

### お題：いいねボタンに楽観更新を導入

- `/api/posts/:id` を `useQuery` で取得
- `/api/posts/:id/like` への POST を `useMutation` で実装
- `onMutate` でキャッシュを書き換え、`onError` で巻き戻し
- ネットワークタブで「Slow 3G」にしても、ボタンが瞬時に反応することを確認

### 発展課題

- ホバーで `prefetchQuery` を実行し、リンク先が即座に開くようにする
- マスターデータ（国一覧など）に長めの `staleTime` を設定して、無駄なfetchが減ることを確認

## 📝 まとめ

- キャッシュは「冷蔵庫」、再検証は「賞味期限の確認」
- staleTime（新鮮期間）と gcTime（保管期間）を区別
- mutation後は invalidateQueries でキャッシュを古くマーク
- 楽観的更新で「ボタンを押した瞬間に反応する」UXを実現
- 失敗時の巻き戻しを忘れずに
