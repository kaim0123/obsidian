# 14-4. 落とし穴と代替パターン（Fragment・key・設計）

## 🎯 この章で学ぶこと

- `React.Children.map` と key の問題（単調な `index` key の弱点）
- フラグメントが「1個の子」のように見えることの影響
- **`cloneElement` 依存から逃げる**代表的な設計

---

## 📖 Fragment と「見えないラッパー」

開発者が `<>{a}{b}</>` と書いた場合、`children` 側には **フラグメントの子として** `a` と `b` がぶら下がっている、といった構造になります。`React.Children.map` で列挙する対象や階層は、見た目の DOM とは一致しません。**「並びをフラットにしたい」**なら `toArray` の挙動や、自前での再帰走査が必要になるケースがあります。ライブラリを書くときほど、このズレが効いてきます。

---

## 📖 index を key にする問題

並び順の入れ替え・途中挿入で **子の状態（入力値、スクロール、内部 state）がズレやすくなる**のは、リストの説明でも出てくれる通り、`React.Children.map` の `map(child, index)` と **インデックス key** は相性が悪い組み合わせになりがちです。

- **並び固定の静的 UI** で、子にも永続状態がほぼない → 許容されることがある
- **動的リスト**や **順序が変わる子** → 子が持つ **安定 ID** で key を付ける、または **データ側で map した結果をリストとして親に渡す** など検討

---

## 📖 cloneElement が増えすぎるとき

`cloneElement` は短い距離の「ラッパーが子にマーカーを足す」用途には向きますが、規模が大きいと：

- どこでどの props が付いたか追いにくい
- リファクタで壊れやすい

次のような **明示的な API** が読みやすいことがあります。

| 狙い | 代替の例 |
| --- | --- |
| 親が「スロット」ごとに違う挿入をしたい | `header` / `footer` のような **名前付き props** で `ReactNode` を渡す |
| タブ・アコーディオンなど親子構造がはっきり | **Compound Components + Context**（`10-5`） |
| 「子リストを親が加工しない」ほうが自然 | **データ配列を props で渡し**、親が `.map` して描画だけ担当する |

---

## 💻 名前付きスロット風の例（コードはシンプルに）

```jsx
function Page({ header, sidebar, children }) {
  return (
    <div className="layout">
      <aside>{sidebar}</aside>
      <header>{header}</header>
      <main>{children}</main>
    </div>
  );
}
```

使う側は「どこに何を入れるか」が宣言的で、`React.Children` を経由しません。

---

## まとめ

- `React.Children` は **「children の形が一定でない」現実**に合わせる道具箱。
- **key / Fragment / 走査の深さ**は思ったよりバグの元。
- アプリの画面レベルでは **Compound・名前付き props・データ駆動の map** の方がメンテしやすいことが多い。

必要になったときに `map` / `only` / `cloneElement` を選べれば十分です。すべてのラッパーで使う必要はありません。
