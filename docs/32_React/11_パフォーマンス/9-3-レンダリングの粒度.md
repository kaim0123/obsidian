# 9-3. レンダリングの粒度（コンポーネント分割）

## 🎯 この章で学ぶこと

- 「コンポーネントを分けると速くなる」仕組み
- どこで分けるかの判断基準
- 状態を「下に降ろす」テクニック

---

## 📖 概念の説明

### Reactの再レンダー範囲

stateが変わると、**そのコンポーネントから下が再レンダー**されます。stateが上にあると、巨大なツリーが毎回再レンダーされる。

```text
App (stateを持つ)        ← ここが変わると…
 ├─ Header              ← これも
 ├─ Sidebar             ← これも
 └─ Main                ← これも
     └─ ItemList        ← これも
         └─ Item × 100  ← 全部再レンダー
```

→ **stateを下に降ろす**だけで、再レンダー範囲が小さくなる。

---

## 💻 例：入力で全画面が遅くなる

### Before：state が App に

```jsx
function App() {
  const [text, setText] = useState('');
  return (
    <div>
      <Header />          {/* 入力のたびに再レンダー */}
      <Sidebar />         {/* 入力のたびに再レンダー */}
      <SearchBox value={text} onChange={setText} />
      <Results query={text} />
    </div>
  );
}
```

入力の度に Header / Sidebar まで再レンダー。

### After：state を下に降ろす

```jsx
function App() {
  return (
    <div>
      <Header />
      <Sidebar />
      <SearchSection /> {/* ここで完結 */}
    </div>
  );
}

function SearchSection() {
  const [text, setText] = useState('');
  return (
    <>
      <SearchBox value={text} onChange={setText} />
      <Results query={text} />
    </>
  );
}
```

state は SearchSection 内で完結。Header / Sidebar は再レンダーされない。

---

## 💡 「state は使う場所の最小範囲に」

```text
state を持つ場所を考える：
  - 上に持ちすぎ → 再レンダー範囲が広い
  - 下すぎ → 共有できない
  
ちょうど「両方が必要とする最も近い親」が最適
```

→ [[8-1-まずはReactだけで]]

---

## 💻 重い子コンポーネントを切り出す

```jsx
function Page() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount((c) => c + 1)}>{count}</button>
      <ExpensiveChart data={largeData} />
    </>
  );
}
```

count が変わるたびに ExpensiveChart も再レンダー。

### 解決1：React.memo

```jsx
const ExpensiveChart = React.memo(({ data }) => {
  // 重い描画
});
```

`data` が変わらなければ再レンダーされない。

### 解決2：children パターン（再レンダーから守る）

```jsx
function Page({ children }) {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount((c) => c + 1)}>{count}</button>
      {children}
    </>
  );
}

function App() {
  return (
    <Page>
      <ExpensiveChart data={largeData} />
    </Page>
  );
}
```

`children` は親の外（App）で作られているので、`Page` の state 変化では再レンダーされない。

---

## 💡 「分けすぎ」の弊害

```jsx
function NameInput({ value, onChange }) { return <input ... /> }
function EmailInput({ value, onChange }) { return <input ... /> }
function PasswordInput({ value, onChange }) { return <input ... /> }
// ... 全部1個1個分割
```

→ ファイル数増、可読性低下。**意味のある単位で分ける**。

---

## 💻 分割の判断基準

| 判断軸 | 説明 |
| --- | --- |
| **再利用** | 別の場所でも使う？ |
| **再レンダー範囲** | stateを下に降ろせる？ |
| **行数** | 大きくなりすぎたら分ける |
| **責務** | 1つのことに集中？ |

「**state を下に降ろしたい**」「**memo で守りたい**」で分けるのが定石。

---

## 💻 例：フォームの最適化

```jsx
function BigForm() {
  const [name, setName] = useState('');
  const [bio, setBio] = useState('');
  const [country, setCountry] = useState('');

  // どれかを入力すると全部再レンダー
}
```

### Better：項目ごとにコンポーネント化 + uncontrolled

```jsx
function BigForm() {
  function handleSubmit(e) {
    e.preventDefault();
    const data = Object.fromEntries(new FormData(e.currentTarget));
  }

  return (
    <form onSubmit={handleSubmit}>
      <input name="name" />
      <textarea name="bio" />
      <select name="country">...</select>
      <button>送信</button>
    </form>
  );
}
```

state を持たないので毎入力で再レンダーしない。

---

## ❌ よくある間違い

### state を最上位で全管理

→ 子で完結できる state は子に。

### 過剰な分割

→ 意味のある単位を超えて分けすぎると逆に読みにくい。

### memo を全コンポーネントに

→ 効果のない場所には不要。

---

## ✅ ベストプラクティス

1. **state は最小範囲に**
2. **重い子は memo + 安定参照**
3. **children パターン**で再レンダーから守る
4. **分割は意味のある単位**で
5. **入力フォームは uncontrolled** も検討

---

## 🔬 実践演習

```jsx
function App() {
  const [search, setSearch] = useState('');
  const [count, setCount] = useState(0);
  return (
    <>
      <input value={search} onChange={(e) => setSearch(e.target.value)} />
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <SuperHeavyList />  {/* これが重い */}
    </>
  );
}
```

入力でも button でも `SuperHeavyList` が再レンダーされない設計に書き換えてください。

---

## 📝 まとめ

- state は最小範囲に降ろす
- 重い子は memo / children パターンで守る
- 分割は意味のある単位で
- 入力は uncontrolled も選択肢
