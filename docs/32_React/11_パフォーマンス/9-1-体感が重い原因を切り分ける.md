# 9-1. 体感が重い原因を切り分ける

## 🎯 この章で学ぶこと

- 「重い」と一口に言っても原因はいろいろあること
- 切り分けの順番（測ってから対策）
- よくある原因のチェックリスト

---

## 🧭 初心者向け：最初に押さえる要点（統合）

Reactで「重い」と感じるときは、まず **不要な再レンダー** を疑います。

- **React.memo**：propsが同じなら子コンポーネントの再レンダーを減らす
- **useMemo**：重い計算や、子に渡すオブジェクト/配列の参照を安定化
- **useCallback**：子に渡す関数参照を安定化（React.memoとセットで効くことが多い）

ただし **「とりあえず全部メモ化」は逆効果**になり得るため、ここから先の「切り分けの順番」に沿って **計測→原因特定→必要箇所だけ**が基本です。

---

## 📖 概念の説明

### 「重い」の種類

| 種類 | 体感 | 原因 |
| --- | --- | --- |
| **初回表示が遅い** | 真っ白いまま | バンドルが大きい、APIが遅い |
| **操作が重い** | クリックして反応しない | 重い計算、再レンダー過剰 |
| **スクロールがガクガク** | カクカク | リスト最適化なし、画像 |
| **入力が遅延する** | 文字入力が追いつかない | 入力ごとに重い処理、再レンダー |

→ 原因を特定してから対策。**「とりあえず memo」は逆効果**もある。

---

## 📌 参考：パフォーマンス指標（Web Vitalsなど）（統合）

- **FCP**：最初のコンテンツが表示されるまで
- **LCP**：主要コンテンツが表示されるまで（体感の核になりやすい）
- **FID**：初回入力への応答（現在はINPが主流だが、概念として把握すると良い）
- **CLS**：レイアウト崩れの大きさ
- **TTI**：操作可能になるまで

「初回表示が遅い」系はLighthouseなどの指標と相性がよい（→ [[9-5-計測]]）。

---

## 🔍 切り分けの順番

```text
1. 計測する（Profiler / Lighthouse）
   ↓
2. ボトルネックを特定
   ↓
3. 種類別の対策
   - 初回表示 → 分割ロード、API改善
   - 操作 → useMemo/useCallback/memo
   - スクロール → 仮想化（react-window）
   - 入力 → デバウンス、controlledを軽く
```

**先に測る**のが鉄則。

---

## 🗂️ 参考：よく使う施策のざっくり比較（統合）

| 施策 | 効きやすい領域 | 実装コスト | 注意点 |
|---|---|---|---|
| **遅延読み込み**（`React.lazy` / 画像lazy） | 初回表示 | 中 | 分割粒度・ローディングUI |
| **画像最適化**（WebP/サイズ調整） | 初回表示/スクロール | 低〜中 | 画質/レイアウトシフト |
| **キャッシュ戦略** | API/再訪 | 中〜高 | 不整合/更新戦略 |
| **CDN** | 配信 | 中 | コスト/キャッシュ無効化 |
| **PWA/Service Worker** | オフライン/再訪 | 高 | キャッシュ破綻に注意 |

この章は「切り分けの導線」なので、各施策の深い実装は必要な章へ（計測→ボトルネック確定後）。

## 💻 計測ツール

### Chrome DevTools の Performance タブ

1. 開発者ツール → Performance
2. 録画ボタン → 操作 → 停止
3. ボトルネックがフレームグラフで見える

### React DevTools Profiler

1. Components タブの隣 Profiler
2. 録画 → 操作 → 停止
3. **どのコンポーネントが何ms使ったか**が分かる

→ [[9-5-計測]]

### Lighthouse（初回表示）

1. DevTools → Lighthouse
2. 「Performance」を選んで実行
3. LCP、CLS、TBT などが点数化

→ [[15-4-パフォーマンス-Lighthouse]]

## 💡 よくある原因チェックリスト

### 初回表示が遅い

- [ ] バンドルサイズが大きい（>500KB）→ 分割ロード（`React.lazy`）
- [ ] 画像が大きい → `<img loading="lazy">`、WebP変換
- [ ] 初回APIが遅い → サーバ側改善、キャッシュ、SSR検討
- [ ] フォントの読み込みでテキストが見えない → font-display: swap

### 操作が重い

- [ ] 親が重く再レンダーしている → React.memo
- [ ] 重い計算を毎レンダー → useMemo
- [ ] 子に渡す関数が毎回新規 → useCallback
- [ ] DOMの数が多すぎる → 仮想化

### 入力が遅い

- [ ] 入力のたびに重い処理 → デバウンス
- [ ] 入力のたびに再フェッチ → デバウンス + AbortController
- [ ] controlled input の親が大きい → 入力部分を切り出す
- [ ] react-hook-form を使う

### スクロールがガクガク

- [ ] リストが大きすぎる（数千件）→ react-window/virtuoso
- [ ] 画像が大量 → lazy loading、small thumbnail
- [ ] スクロールイベントの中で重い処理 → throttle

## 💻 切り分けの例：「ボタンが反応しない」

### Step 1：DevToolsのPerformanceで測る

クリック → 何msで反応した？

- 100ms以下：人間には瞬時
- 200ms：体感あり
- 500ms以上：明確に遅い

### Step 2：原因の絞り込み

```jsx
function handleClick() {
  console.time('click');
  // 重い処理
  console.timeEnd('click');
}
```

### Step 3：再レンダー確認

React DevTools Profiler で「**何個コンポーネントが再レンダーされたか**」を見る。

### Step 4：対策

- 重い処理 → Web Worker か `useDeferredValue`
- 過剰再レンダー → memo / useMemo / useCallback

---

## ❌ よくある間違い

### 計測せずに対策

→ memo を全部に付けたら、メモ化のオーバーヘッドで余計遅いケースも。

### 「重い」と思い込んでいるだけ

→ 体感200ms以下は普通の人には速く感じる。気のせいかも。

### 1か所だけ直して安心

→ ボトルネックは複数あることが多い。Profilerで再計測。

---

## ✅ ベストプラクティス

1. **「重い」と感じたら、まず測る**
2. **DevToolsのProfiler を使う**
3. **原因の種類**で対策を分ける
4. **最適化は最後**（早すぎる最適化は害）
5. **対策後に再計測**

---

## 🔬 実践演習

「クリックすると1秒固まるボタン」を作る：

```jsx
function HeavyButton() {
  function handleClick() {
    const start = Date.now();
    while (Date.now() - start < 1000) {} // 1秒CPU
  }
  return <button onClick={handleClick}>クリック</button>;
}
```

DevToolsのPerformanceで観察 → useDeferredValue や Web Worker で改善。

---

## 📝 まとめ

- 「重い」には種類がある
- 計測 → 原因特定 → 対策
- DevTools Profiler / Lighthouse を活用
- 早すぎる最適化は逆効果
