# 9-6. 「ボタンが反応しない」系の原因（重い処理/イベント/メモリリーク）

## 🎯 この章で学ぶこと

- 「クリックしても反応しない」の典型パターン
- それぞれの原因と切り分け方
- 対策と防止策

---

## 📖 概念の説明

### 「反応しない」の種類

| 症状 | 主な原因 |
| --- | --- |
| クリックしても何も起きない | onClickの渡し方ミス、preventDefault |
| 反応するが遅い（500ms以上） | 重い処理、過剰な再レンダー |
| しばらくすると遅くなっていく | メモリリーク |
| 二重に処理が走る | イベント重複登録、バブリング |
| 連打したら不整合 | 二重送信防止なし |

---

## 💻 ① 関数を渡し忘れ・呼び出してしまっている

```jsx
// ❌ 関数を呼び出している（即実行）
<button onClick={alert('hi')}>クリック</button>

// ❌ 引数を渡そうとして呼び出している
<button onClick={deleteItem(1)}>削除</button>
```

→ ✅ アロー関数で囲む：

```jsx
<button onClick={() => alert('hi')}>クリック</button>
<button onClick={() => deleteItem(1)}>削除</button>
```

---

## 💻 ② preventDefaultで止まっている

```jsx
function handleClick(e) {
  e.preventDefault(); // ← formの中の<button type="submit">のとき影響
  // 処理
}
```

→ ✅ `type="button"` を明示するとデフォルト挙動がない：

```jsx
<button type="button" onClick={handleClick}>送信</button>
```

---

## 💻 ③ 重いonClick処理でメインスレッドが止まる

```jsx
function handleClick() {
  for (let i = 0; i < 1e9; i++) {} // 重いループ
}
```

→ ✅ Web Workerに逃がす、または `useDeferredValue` / `startTransition`：

```jsx
import { useTransition } from 'react';

function App() {
  const [pending, startTransition] = useTransition();

  function handleClick() {
    startTransition(() => {
      // 重いstate更新
      setItems(generateLargeList());
    });
  }
}
```

→ React 18+ で「**緊急じゃない更新**」を後回しにできる。

---

## 💻 ④ 過剰な再レンダーで遅い

ボタンを押すと App 全体が再レンダー → 重い子コンポーネントも再レンダー → 反応が遅い。

→ ✅ memo / 状態を下に降ろす（[[9-3-レンダリングの粒度]])。

---

## 💻 ⑤ メモリリークで時間とともに遅くなる

### 症状

ページを開いて数分後に重くなる。

### 原因例：イベントリスナー解除忘れ

```jsx
useEffect(() => {
  window.addEventListener('scroll', handleScroll);
  // ❌ クリーンアップなし
}, []);
```

→ ✅ クリーンアップ：

```jsx
useEffect(() => {
  window.addEventListener('scroll', handleScroll);
  return () => window.removeEventListener('scroll', handleScroll);
}, []);
```

### 原因例：タイマー解除忘れ

```jsx
useEffect(() => {
  setInterval(...);
  // ❌
}, []);
```

→ ✅ `clearInterval`。

### 原因例：参照を closure で握り続ける

→ メモ化された関数が古いstateを保持し続ける。 [[5-5-よくあるバグ集]]

---

## 💻 ⑥ 二重イベント

```jsx
<div onClick={parentHandler}>
  <button onClick={childHandler}>クリック</button>
</div>
```

→ ボタンクリックで `childHandler` → `parentHandler` の順に走る（バブリング）。

```jsx
function childHandler(e) {
  e.stopPropagation(); // 親に伝播しない
  // 処理
}
```

---

## 💻 ⑦ 連打で多重送信

```jsx
async function handleSubmit() {
  await api.send(...);
}

<button onClick={handleSubmit}>送信</button>
```

連打すると複数回API送信。

→ ✅ disabled + 送信中フラグ：

```jsx
const [submitting, setSubmitting] = useState(false);

async function handleSubmit() {
  if (submitting) return;
  setSubmitting(true);
  try { await api.send(...); } finally { setSubmitting(false); }
}

<button onClick={handleSubmit} disabled={submitting}>
  {submitting ? '送信中...' : '送信'}
</button>
```

→ [[8-8-送信フローの状態管理]]

## 💻 ⑧ z-indexで隠れて押せない

「ボタンが見えてるのに押せない」 → 上に透明な要素が乗っている可能性。

→ DevToolsの **Inspectでホバー** すると、何が乗っているか分かる。

## 💡 切り分けフロー

```text
1. console.log を onClick の頭に → 呼ばれている？
   ├─ 呼ばれていない → 関数の渡し方、z-index、disabled 確認
   └─ 呼ばれている
        ↓
2. 重い処理がある？ → console.time で計測
   ├─ ある → useTransition / Web Worker
   └─ ない
        ↓
3. 連打で問題？ → 二重送信防止
   ├─ 防止なし → フラグ + disabled
   └─ あり
        ↓
4. メモリリーク？ → 時間とともに重くなる？
   └─ クリーンアップ確認
```

# ボタンが反応しない問題とメモリリーク

## 概要

Next.jsアプリケーションで、ボタンが反応しない問題が発生し、ページリロードで解消する場合、フロントエンド側のメモリリークやリソース管理の問題が原因である可能性が高いです。

## 問題の症状

- ボタンをクリックしても反応しない
- ページをリロードすると正常に動作する
- 時間が経つと徐々にパフォーマンスが低下する
- ブラウザのメモリ使用量が増加し続ける

## 主な原因

### 1. メモリリーク（Memory Leak）

メモリリークとは、不要になったメモリが解放されずに残り続ける状態です。これにより、アプリケーションのパフォーマンスが低下し、最終的にUIが反応しなくなることがあります。

### 2. イベントリスナーの重複登録

コンポーネントが再レンダリングされるたびにイベントリスナーが追加され、同じイベントハンドラが複数回登録されることで、予期しない動作やパフォーマンス低下を引き起こします。

### 3. 状態管理の問題

巨大な配列やオブジェクトをstateに保持し続けることで、メモリ使用量が増加し、レンダリングが重くなります。

## フロント側のリークの具体例

### 1. setInterval / setTimeout の解除忘れ

#### 問題のコード例

```typescript
// ❌ 悪い例：クリーンアップしない
useEffect(() => {
  const interval = setInterval(() => {
    console.log('Running...');
  }, 1000);
  // クリーンアップ関数がない
}, []);
```

#### 正しいコード例

```typescript
// ✅ 良い例：クリーンアップ関数で解除
useEffect(() => {
  const interval = setInterval(() => {
    console.log('Running...');
  }, 1000);

  // クリーンアップ関数でタイマーを解除
  return () => {
    clearInterval(interval);
  };
}, []);
```

#### なぜ問題なのか

- コンポーネントがアンマウントされても、タイマーが実行され続ける
- 複数回マウント/アンマウントを繰り返すと、複数のタイマーが同時に動作する
- メモリリークとパフォーマンス低下の原因となる

#### 対処法

- `useEffect`のクリーンアップ関数で必ず`clearInterval`または`clearTimeout`を呼ぶ
- 依存配列を適切に設定し、不要な再実行を防ぐ

### 2. WebSocket / EventSource の close忘れ

#### 問題のコード例

```typescript
// ❌ 悪い例：接続を閉じない
useEffect(() => {
  const ws = new WebSocket('ws://example.com');
  
  ws.onmessage = (event) => {
    setData(JSON.parse(event.data));
  };
  
  // クリーンアップ関数がない
}, []);
```

#### 正しいコード例

```typescript
// ✅ 良い例：クリーンアップ関数で接続を閉じる
useEffect(() => {
  const ws = new WebSocket('ws://example.com');
  
  ws.onmessage = (event) => {
    setData(JSON.parse(event.data));
  };
  
  // クリーンアップ関数で接続を閉じる
  return () => {
    ws.close();
  };
}, []);
```

#### EventSourceの場合

```typescript
// ✅ EventSourceの例
useEffect(() => {
  const eventSource = new EventSource('/api/events');
  
  eventSource.onmessage = (event) => {
    setData(JSON.parse(event.data));
  };
  
  return () => {
    eventSource.close();
  };
}, []);
```

#### なぜ問題なのか

- WebSocketやEventSourceは、ブラウザとサーバー間の接続を維持する
- 接続を閉じないと、不要な接続が残り続ける
- サーバー側のリソースも消費し続ける
- メモリリークとネットワークリソースの無駄遣い

#### 対処法

- コンポーネントのアンマウント時に必ず`close()`を呼ぶ
- エラーハンドリングも実装し、異常終了時にも接続を閉じる

### 3. 巨大な配列を state に溜め続けている

#### 問題のコード例

```typescript
// ❌ 悪い例：配列を無限に追加し続ける
const [messages, setMessages] = useState<string[]>([]);

useEffect(() => {
  const eventSource = new EventSource('/api/messages');
  
  eventSource.onmessage = (event) => {
    const newMessage = JSON.parse(event.data);
    // 配列に追加し続ける（削除しない）
    setMessages(prev => [...prev, newMessage]);
  };
  
  return () => {
    eventSource.close();
  };
}, []);
```

#### 正しいコード例

```typescript
// ✅ 良い例：配列のサイズを制限する
const [messages, setMessages] = useState<string[]>([]);
const MAX_MESSAGES = 100; // 最大件数を設定

useEffect(() => {
  const eventSource = new EventSource('/api/messages');
  
  eventSource.onmessage = (event) => {
    const newMessage = JSON.parse(event.data);
    setMessages(prev => {
      const updated = [...prev, newMessage];
      // 最大件数を超えたら古いものを削除
      return updated.slice(-MAX_MESSAGES);
    });
  };
  
  return () => {
    eventSource.close();
  };
}, []);
```

#### なぜ問題なのか

- 配列が無限に大きくなると、メモリ使用量が増加し続ける
- レンダリング時に大量のデータを処理するため、パフォーマンスが低下
- 仮想DOMの差分計算も重くなる
- 最終的にUIが反応しなくなる

#### 対処法

- 配列の最大サイズを設定し、古いデータを削除する
- 必要に応じて、ページネーションや仮想スクロールを実装
- 不要なデータは定期的にクリーンアップする

## その他の原因

### 4. イベントリスナーの重複登録

#### 問題のコード例

```typescript
// ❌ 悪い例：依存配列がないため、毎回リスナーが追加される
useEffect(() => {
  const handleClick = () => {
    console.log('Clicked');
  };
  
  window.addEventListener('click', handleClick);
  // クリーンアップがない
});
```

#### 正しいコード例

```typescript
// ✅ 良い例：クリーンアップ関数でリスナーを削除
useEffect(() => {
  const handleClick = () => {
    console.log('Clicked');
  };
  
  window.addEventListener('click', handleClick);
  
  return () => {
    window.removeEventListener('click', handleClick);
  };
}, []); // 空の依存配列で一度だけ実行
```

### 5. サブスクリプションの解除忘れ

#### 問題のコード例

```typescript
// ❌ 悪い例：RxJSのサブスクリプションを解除しない
useEffect(() => {
  const subscription = observable.subscribe(data => {
    setData(data);
  });
  // クリーンアップがない
}, []);
```

#### 正しいコード例

```typescript
// ✅ 良い例：サブスクリプションを解除
useEffect(() => {
  const subscription = observable.subscribe(data => {
    setData(data);
  });
  
  return () => {
    subscription.unsubscribe();
  };
}, []);
```

### 6. 大量の再レンダリング

#### 問題のコード例

```typescript
// ❌ 悪い例：毎回新しいオブジェクトを作成
const Component = () => {
  const [count, setCount] = useState(0);
  
  // 毎回新しいオブジェクトが作成される
  const config = {
    option1: true,
    option2: false,
  };
  
  return <ChildComponent config={config} />;
};
```

#### 正しいコード例

```typescript
// ✅ 良い例：useMemoでメモ化
const Component = () => {
  const [count, setCount] = useState(0);
  
  // メモ化して再作成を防ぐ
  const config = useMemo(() => ({
    option1: true,
    option2: false,
  }), []);
  
  return <ChildComponent config={config} />;
};
```

## Next.js特有の問題

### 7. サーバーサイドレンダリング（SSR）での問題

#### 問題のコード例

```typescript
// ❌ 悪い例：SSRでブラウザAPIを使用
const Component = () => {
  const [data, setData] = useState(null);
  
  // SSRではwindowが存在しない
  const ws = new WebSocket(window.location.origin);
  
  return <div>{data}</div>;
};
```

#### 正しいコード例

```typescript
// ✅ 良い例：useEffect内でブラウザAPIを使用
const Component = () => {
  const [data, setData] = useState(null);
  
  useEffect(() => {
    // クライアント側でのみ実行
    const ws = new WebSocket(window.location.origin);
    
    ws.onmessage = (event) => {
      setData(JSON.parse(event.data));
    };
    
    return () => {
      ws.close();
    };
  }, []);
  
  return <div>{data}</div>;
};
```

### 8. ルーティング時のクリーンアップ

Next.jsでは、ページ遷移時にコンポーネントがアンマウントされますが、適切にクリーンアップしないとリソースが残り続ける可能性があります。

```typescript
// ✅ ページ遷移時も確実にクリーンアップ
useEffect(() => {
  const interval = setInterval(() => {
    // 何らかの処理
  }, 1000);
  
  return () => {
    clearInterval(interval);
  };
}, []);
```

## デバッグ方法

### 1. React DevTools Profiler

React DevToolsのProfilerを使用して、再レンダリングの頻度と時間を確認します。

### 2. Chrome DevToolsのメモリプロファイラー

1. Chrome DevToolsを開く
2. Performanceタブを選択
3. Memoryタブでメモリ使用量の推移を確認
4. メモリが増加し続ける場合はリークの可能性

### 3. コンソールログで確認

```typescript
useEffect(() => {
  console.log('Component mounted');
  
  return () => {
    console.log('Component unmounted');
  };
}, []);
```

アンマウント時にログが出力されない場合は、クリーンアップが実行されていない可能性があります。

## ベストプラクティス

### 1. 必ずクリーンアップ関数を実装する

```typescript
useEffect(() => {
  // リソースの作成
  
  return () => {
    // 必ずクリーンアップを実装
  };
}, []);
```

### 2. 依存配列を適切に設定する

```typescript
// 空の配列：マウント時のみ実行
useEffect(() => {
  // ...
}, []);

// 依存配列あり：依存が変更された時のみ実行
useEffect(() => {
  // ...
}, [dependency1, dependency2]);
```

### 3. カスタムフックでリソース管理を抽象化

```typescript
// カスタムフックでリソース管理を統一
function useWebSocket(url: string) {
  const [data, setData] = useState(null);
  
  useEffect(() => {
    const ws = new WebSocket(url);
    
    ws.onmessage = (event) => {
      setData(JSON.parse(event.data));
    };
    
    return () => {
      ws.close();
    };
  }, [url]);
  
  return data;
}
```

### 4. データのサイズを制限する

```typescript
// 配列のサイズを制限
const MAX_ITEMS = 100;
setItems(prev => [...prev, newItem].slice(-MAX_ITEMS));
```

### 5. メモ化を活用する

```typescript
// useMemoで計算結果をメモ化
const expensiveValue = useMemo(() => {
  return expensiveCalculation(data);
}, [data]);

// useCallbackで関数をメモ化
const handleClick = useCallback(() => {
  // 処理
}, [dependency]);
```

## まとめ

ボタンが反応しない問題は、多くの場合メモリリークやリソース管理の問題が原因です。以下の点に注意してください：

1. **必ずクリーンアップ関数を実装する**（setInterval、setTimeout、WebSocket、EventSource等）
2. **配列やオブジェクトのサイズを制限する**
3. **イベントリスナーを適切に削除する**
4. **依存配列を適切に設定する**
5. **メモ化を活用して不要な再レンダリングを防ぐ**

ページリロードで解消するのは、リロード時にすべてのリソースがリセットされるためです。根本的な解決には、適切なリソース管理とクリーンアップの実装が必要です。
