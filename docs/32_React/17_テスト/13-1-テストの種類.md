# 13-1. テストの種類（Unit/Integration/E2E）

## 🎯 この章で学ぶこと

- テストの3種類とそれぞれの目的
- どこで何をテストするかの基準
- React開発で使う主要ツール

---

## 📖 テストの3階層

```text
        E2E  少数 / 遅い / 本物に近い
        ───────
     Integration  中
        ─────────
      Unit  多数 / 速い / 局所的
```

通称「**テストピラミッド**」。下に行くほど**多く・速く**、上に行くほど**少なく・遅い**。

### Unit Test（単体テスト）

- 単一関数・コンポーネントを孤立させて検証
- 数百〜数千個書ける
- 高速、CIで毎回実行

### Integration Test（結合テスト）

- 複数のコンポーネント・モジュールが連携した状態で検証
- API呼び出しはモック
- そこそこ速い

### E2E Test（エンドツーエンドテスト）

- 本物のブラウザで実際の操作を再現
- ログイン → 操作 → 確認 のシナリオ
- 遅い、不安定になりがち
- 重要なフローだけ

---

## 💻 React の主要ツール

| 用途 | ツール |
| --- | --- |
| Test Runner | **Vitest**（おすすめ）/ Jest |
| コンポーネントテスト | **React Testing Library** |
| ユーザー操作 | **@testing-library/user-event** |
| API モック | **MSW (Mock Service Worker)** |
| E2E | **Playwright**（推奨）/ Cypress |

---

## 💻 Vitest セットアップ

Viteベースなら超簡単：

```bash
npm install -D vitest @testing-library/react @testing-library/jest-dom @testing-library/user-event jsdom
```

```js
// vite.config.js
export default {
  test: {
    environment: 'jsdom',
    setupFiles: ['./src/test/setup.ts'],
    globals: true,
  },
};
```

```ts
// src/test/setup.ts
import '@testing-library/jest-dom';
```

## 💻 Unit Test の例（純粋関数）

```ts
// utils/format.ts
export function formatPrice(num: number): string {
  return `¥${num.toLocaleString()}`;
}

// utils/format.test.ts
import { describe, it, expect } from 'vitest';
import { formatPrice } from './format';

describe('formatPrice', () => {
  it('数字を円記号付きで返す', () => {
    expect(formatPrice(1000)).toBe('¥1,000');
  });

  it('0なら ¥0', () => {
    expect(formatPrice(0)).toBe('¥0');
  });
});
```

## 💻 Integration Test の例（コンポーネント）

```tsx
// Counter.tsx
function Counter() {
  const [count, setCount] = useState(0);
  return (
    <>
      <p>カウント: {count}</p>
      <button onClick={() => setCount((c) => c + 1)}>+1</button>
    </>
  );
}

// Counter.test.tsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import Counter from './Counter';

it('ボタンを押すとカウントが増える', async () => {
  const user = userEvent.setup();
  render(<Counter />);

  expect(screen.getByText('カウント: 0')).toBeInTheDocument();
  await user.click(screen.getByRole('button', { name: '+1' }));
  expect(screen.getByText('カウント: 1')).toBeInTheDocument();
});
```

## 💻 E2E Test の例（Playwright）

```ts
// tests/login.spec.ts
import { test, expect } from '@playwright/test';

test('ログインしてダッシュボードへ', async ({ page }) => {
  await page.goto('/login');
  await page.fill('input[name=email]', 'user@example.com');
  await page.fill('input[name=password]', 'password');
  await page.click('button:has-text("ログイン")');

  await expect(page).toHaveURL('/dashboard');
  await expect(page.locator('h1')).toContainText('ダッシュボード');
});
```

→ 本物のブラウザで操作を再現。詳しくは [[13-5-E2E]]。

## 💡 何をどこでテストするか

| 種類 | テスト対象 |
| --- | --- |
| Unit | 純粋関数、ロジック、カスタムフック |
| Integration | UIの操作とstate変化、APIモックでの一連の動き |
| E2E | ログイン、決済などの**ユーザー視点の重要シナリオ** |

### 比率の目安

- Unit：70%
- Integration：20%
- E2E：10%

---

## ❌ よくある間違い

### 全部 E2E にする

→ 遅すぎてCIで実行できない。Unit中心に。

### 内部実装をテスト

```ts
expect(component.state.count).toBe(1); // ❌ 内部状態
```

→ ✅ ユーザーから見える振る舞いをテスト：

```ts
expect(screen.getByText('カウント: 1')).toBeInTheDocument();
```

### モックしすぎ

→ 本当に動くか確認できない。**最小限のモック**。

### テストが落ちにくい

→ どんな変更でもパスするテストは意味がない。

---

## ✅ ベストプラクティス

1. **Unit中心 + Integration補強 + 重要なE2E**
2. **ユーザー視点でテスト**（実装詳細を避ける）
3. **Vitest + RTL**で高速・モダン
4. **MSW でAPI モック**（実装に近い）
5. **CIで毎回実行**

---

## 🔬 実践演習

カウンターコンポーネントを：

- Unit：`add(a, b)` 関数（あれば）
- Integration：ボタンクリックで state 変化
- E2E：ページを開いてボタン押下

---

## 📝 まとめ

- 3階層：Unit / Integration / E2E
- 多い順：Unit > Integration > E2E
- React は Vitest + RTL が定番
- ユーザー視点でテスト
