## 詳細要約（動画のナラティブ）

この動画では、Redux が「状態管理」と呼ばれる理由を具体例から押さえたうえで、**単方向データフロー**（入力 → アクション → ストア更新 → 画面反映）と、Redux Toolkit（RTK）による実装の短縮化をセットで説明している。

### Redux を使うモチベーション

- アプリには「いまユーザーがどの段階にいるか」といった情報（状態）があり、その状態によって次に起こすべき処理や UI が変わることが多い。
- 動画では「レストランの客（太郎くん）の状態」によって、ウェイターが取るべき行動が変わる、というたとえで、**状態を監視し共有することが不可欠だ**ことを説明している。
- 複数コンポーネント／複数箇所で同じ状態を参照・更新するほど、`props` のバケツリレーや場当たり的な状態管理だけでは追いつきにくくなる。そうしたときに Redux のモデルが有効になりやすい、というニュアンスになる。

### 素の Redux が想定する構成（概念図）

動画では図として次の関係が整理される。

| 要素 | 役割（動画での説明） |
|------|----------------------|
| **View（コンポーネント）** | + / − のボタンなどユーザー操作を受ける画面。ストアから画面表示用の状態を読む。 |
| **Action Creator** | 「カウントを増やす」「減らす」など、起こしたい変更の種類を表すオブジェクト（アクション）を作る。 |
| **dispatch** | ストアへ「このアクションが起きました」と通知する。 |
| **Store** | アプリ全体で共有される「状態の保管場」。どのコンポーネントからも参照できる前提で設計する。 |
| **Reducer** | **前の状態 + アクション → 次の状態**という純粋な更新規則。ストアが「どう変えるか」の裏側。 |
| **初期状態（initialState）** | まだイベントが無いときのデフォルト（カウンターなら `0` など）。 |

要点は、アクション経由でのみ状態を書き換え、コンポーネントは **`useSelector` で読む**／**`dispatch` で書く**、という線引きになる。

### Redux Toolkit が簡略化する点（スライス）

従来の Redux では、ストア・リデュサー・アクション・アクションクリエーターを別々に多く書く必要があったが、RTK の **`createSlice`** は次を**1つのスライス**にまとめられると説明される。

- `name` と `initialState`
- **`reducers` オブジェクト**に「イベントごとの更新関数」を書く
- reducer に名前をつけると、その名前に対応した **アクションクリエーターが自動生成**される（手で `type` を文字列連結しない）

結果として、`counterSlice.js` に「状態の形」「更新ロジック」「アクション」を寄せられる。

### デモアプリで実装されるカウンター

最終ゴールは次の機能を持つ React アプリである。

1. **`+`** で `state.value` が `+1`、`−` で `-1`
2. **数字入力フィールドと「追加」**で、入力した数だけ増加（`incrementByAmount` と **payload（ペイロード）**）
3. ストアの値が画面にリアルタイムに反映される

### セットアップの流れ（動画での手順）

- `create-react-app` で雛形を作成し、不要ファイルを削除（デモにより簡略化）。
- `npm install @reduxjs/toolkit` と **`react-redux`** を入れる。
- **`src/store.js`** に `configureStore` でストア作成。開始時は `reducer` プレースホルダーでもよく、後で `counterReducer` を接続。
- **`src/features` または `src/redux/counterSlice.js`**（動画では `redux/counterSlice.js`）で `createSlice`。
  - `increment` / `decrement`：`state.value += 1` のような **Immer 前提の書き方**で簡潔に記述できる（動画では「ミュータブルっぽく書ける」と理解してよいレベルの説明）。
  - **`incrementByAmount`**：`action.payload` で渡された数を加算。入力値は可変なのでペイロードが必要になる、という整理。
- `counterSlice.reducer` を **default export**、アクションは **named export**（`increment` など）でコンポーネント側に渡す。
- **`index.js`** で `react-redux` の **`Provider`** で `<App />` を包み、`store={store}` を渡す。**アプリ直下のすべてのコンポーネント**からストアにアクセス可能になるイメージ（React の Context に近いと説明）。
- **`store.js`** の `configureStore` の **`reducer` フィールドに `counter` キー**で reducer をマウント（例：`counter: counterReducer`）。このキーが **`useSelector` のパスの先頭**になる。

### UI 側のフック（動画で触れる API）

| フック/API | 役割 |
|-----------|------|
| **`useSelector`** | `(state) => state.counter.value` のように、ストア内の値を選択してコンポーネントに購読させる。 |
| **`useDispatch`** | `dispatch(increment())` のように、アクションをストアへ送る。 |
| **`useState`（ローカル）** | 入力欄の数値だけはコンポーネント内の状態で持ち、`dispatch(incrementByAmount(Number(...)))` に渡す。 |

### ハマりどころ（動画で言及）

- **`configureStore`** の reducer に渡す export の括弧／名前の typo でビルド・実行時エラーになる例が示される。
- **入力値を `Number` でキャスト**しないと、文字列結合になってカウントがおかしくなる、という実例がある。
- 「payload の詳細」は Redux / RTK の公式ドキュメントで深掘りするよう促されている。

### 修了時に頭に残しておくとよいこと

- Redux は「**単一の真実のソース（ストア）**」と「**アクションだけが状態変更の入口**」という約束で、複雑化した状態の読み書きを整理しやすくするツールである。
- 日々の React 開発では **`useState` と Context で足りる局面**も多いが、アプリ規模やチーム開発で状態の流れが追いにくくなってきたら Redux / RTK の出番、という位置づけで理解するとよい。
