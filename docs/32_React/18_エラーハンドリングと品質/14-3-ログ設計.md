# 14-3. ログ設計（再現可能なログ）

## 🎯 この章で学ぶこと

- 「再現可能な」ログとは何か
- ログレベル（debug/info/warn/error）の使い分け
- Sentry など外部ツールへの送信

---

## 📖 ログの目的

「**バグが起きたとき、現場を再現できる情報**」を残す。

良いログ：

- いつ
- 誰が（user_id）
- 何をしようとして
- 何が起きたか（エラーの種類、stack trace）
- 環境（ブラウザ、OS）

---

## 💻 ログレベル

| レベル | 用途 | 例 |
| --- | --- | --- |
| `debug` | 開発中だけ | 「fetch 開始: /api/users」 |
| `info` | 普通の動作 | 「ログイン成功: user 123」 |
| `warn` | 警告 | 「APIが200ms超」 |
| `error` | 異常 | 「ユーザー取得失敗」 |
| `fatal` | 復旧不可 | 「DB接続失敗」 |

本番環境では `info` 以上だけ送信、開発では `debug` も。

---

## 💻 シンプルなロガー

```ts
// lib/logger.ts
type LogLevel = 'debug' | 'info' | 'warn' | 'error';

const minLevel: LogLevel = import.meta.env.DEV ? 'debug' : 'info';
const levels = { debug: 0, info: 1, warn: 2, error: 3 };

function log(level: LogLevel, message: string, data?: any) {
  if (levels[level] < levels[minLevel]) return;

  const entry = {
    level,
    message,
    timestamp: new Date().toISOString(),
    data,
    userAgent: navigator.userAgent,
  };

  console[level === 'fatal' ? 'error' : level](entry);

  // 本番ではサーバーに送信
  if (level === 'error' && !import.meta.env.DEV) {
    fetch('/api/logs', { method: 'POST', body: JSON.stringify(entry) });
  }
}

export const logger = {
  debug: (msg: string, data?: any) => log('debug', msg, data),
  info: (msg: string, data?: any) => log('info', msg, data),
  warn: (msg: string, data?: any) => log('warn', msg, data),
  error: (msg: string, data?: any) => log('error', msg, data),
};
```

```ts
import { logger } from './lib/logger';

logger.info('ユーザーログイン', { userId: 123 });
logger.error('API失敗', { url: '/api/users', status: 500 });
```

## 💻 Sentry（本格運用）

エラーログ・監視サービスの定番。

```bash
npm install @sentry/react
```

```ts
// main.tsx
import * as Sentry from '@sentry/react';

Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  environment: import.meta.env.MODE,
  tracesSampleRate: 0.1, // 10%サンプリング
  replaysSessionSampleRate: 0.1,
});
```

```tsx
// 自動でキャッチ（ErrorBoundary連携）
<Sentry.ErrorBoundary fallback={<p>エラー</p>}>
  <App />
</Sentry.ErrorBoundary>
```

```ts
// 手動ログ
Sentry.captureException(new Error('Something broke'));
Sentry.captureMessage('Important event', 'info');

// ユーザー紐付け
Sentry.setUser({ id: '123', email: 'user@example.com' });

// タグ・コンテキスト
Sentry.setTag('feature', 'checkout');
Sentry.setContext('cart', { items: 5 });
```

→ エラーが起きた時の詳細（リプレイ動画含む）が管理画面で見られる。

## 💻 エラーから情報を抽出

```ts
try {
  await api.fetch();
} catch (err) {
  logger.error('API失敗', {
    name: err.name,                    // エラー名
    message: err.message,              // メッセージ
    stack: err.stack,                  // スタックトレース
    url: '/api/users',
    method: 'GET',
    userId: currentUser?.id,
    timestamp: new Date().toISOString(),
  });
}
```

→ **再現するための文脈**が大事。

## 💡 機微情報を漏らさない

```ts
// ❌ パスワードがログに
logger.info('ログイン試行', { email, password });

// ✅
logger.info('ログイン試行', { email });
```

ログにNG：

- パスワード、トークン、APIキー
- クレジットカード番号
- 個人を特定できる情報（要件次第）

→ サーバ送信時に**自動マスキング**するヘルパーを作る。

## 💻 リクエスト ID で追跡

```ts
import { v4 as uuid } from 'uuid';

async function apiCall(url) {
  const requestId = uuid();
  logger.info('API call', { requestId, url });

  const res = await fetch(url, { headers: { 'X-Request-Id': requestId } });

  logger.info('API response', { requestId, status: res.status });
  return res;
}
```

→ クライアント・サーバ両方のログを `requestId` で紐付け。

## ❌ よくある間違い

### console.log を本番に残す

→ 情報漏洩リスク。**ESLint で警告**、ビルド時に削除。

補足：

- PR に `console.log` が残ったままだと、**本番でのノイズ**（調査しづらい）や **機微情報混入**のリスクが上がります
- 開発中だけ必要なら、コミット前に削除するか、チーム方針に沿った **ロガー**（`logger.info/error` など）へ置き換えます

### エラーをcatchして握りつぶす

```ts
try { ... } catch {} // ❌
```

→ ✅ 必ずログかrethrowか、何かする。

### 全部errorレベル

→ 本当のerror が埋もれる。レベルを使い分け。

### 個人情報をログに

→ 要件・法的にもアウト。

---

## ✅ ベストプラクティス

1. **レベルを使い分ける**（debug/info/warn/error）
2. **再現に必要な文脈**を含める
3. **本番は Sentry** 推奨
4. **機微情報を排除**
5. **requestId で前後を追える**ように

---

## 🔬 実践演習

API呼び出しラッパーを作る：

- 各リクエストに requestId を付ける
- 失敗したらlogger.error
- 機微情報（パスワードなど）はマスク
- Sentry に送信

---

## 📝 まとめ

- ログは「再現できる情報」
- レベルを使い分け、Sentryで管理
- 機微情報を漏らさない
- requestId で追跡可能に
