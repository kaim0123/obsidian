# 16-5 デプロイ・振り返り（学びの言語化）

## 🎯 この章で学ぶこと

- Vercel に React アプリをデプロイする最短手順を体験する
- 環境変数（`.env`）の使い方と、フロントに公開してよい / よくない情報の境界を学ぶ
- プレビューデプロイと本番デプロイの違いを理解する
- 振り返り（KPT 法）でプロジェクトを言語化する技術を身につける
- 「公開してから始まる運用」というマインドセットを持つ

## 📖 概念の説明

### デプロイとは

「自分のパソコンの中だけで動くアプリ」を「世界中からアクセスできるアプリ」に変える作業です。React アプリは Vite などでビルドすると `dist/` に静的な HTML/CSS/JS が出来上がります。あとはこれを Web サーバに置けば公開できます。

ただし手作業でアップロードしていては運用が辛いので、現代では Vercel / Netlify / Cloudflare Pages などのサービスに「Git にプッシュしたら自動でデプロイ」してもらうのが普通です。

### Vercel のしくみ

1. GitHub のリポジトリを Vercel に連携する
2. main ブランチへのプッシュ → 本番デプロイ
3. 他ブランチへのプッシュ → プレビューデプロイ（一意な URL が発行される）
4. PR ごとにプレビュー URL がコメントされる

これで「マージ前にレビュアーが実物を触れる」という強力な開発フローが手に入ります。

### 環境変数の扱い

`API_URL` のように環境ごとに変わる値は、コードに直書きせず環境変数として渡します。Vite では `VITE_` で始まる変数だけがフロントにバンドルされます。

重要: フロントのコードは「世界中の誰でも読める」状態になります。**API キー・データベースパスワード・JWT 秘密鍵などは絶対に `VITE_` で公開してはいけません**。これらはサーバ側で持ちます。

### 振り返りの定番: KPT 法

- **Keep**: 続けたいこと
- **Problem**: 困ったこと
- **Try**: 次に試したいこと

15 分でいいのでこれを書くと、経験値が「なんとなくの疲労感」から「次に活きる学び」に変わります。

## 💻 コード例

### `vercel.json`（必要に応じて）

ほとんどの場合 Vercel は自動検出してくれるので不要ですが、SPA で履歴 API を使うときは次のルールが要ります。

```json
{
  "rewrites": [{ "source": "/(.*)", "destination": "/" }]
}
```

これがないと `https://taskmate.example.com/tasks/abc` にダイレクトアクセスしたとき 404 になります。

### 環境変数の使い方

```bash
# .env.local（Git にコミットしない）
VITE_API_BASE_URL=http://localhost:8787
```

```ts
// src/lib/api.ts
const BASE = import.meta.env.VITE_API_BASE_URL;

export async function api<T>(path: string, init?: RequestInit): Promise<T> {
  const res = await fetch(`${BASE}${path}`, init);
  // ...
}
```

Vercel ダッシュボード → Settings → Environment Variables から本番用の値を登録します。Production / Preview / Development の 3 環境で別の値を設定可能です。

### デプロイ手順（Vite + GitHub + Vercel）

```bash
# 1. ビルドが通ることをローカルで確認
npm run build
npm run preview

# 2. GitHub にプッシュ
git push origin main

# 3. Vercel ダッシュボードで「New Project」→ リポジトリ選択
# 4. Framework Preset = Vite を確認
# 5. 環境変数を登録
# 6. Deploy ボタン
```

これだけで `https://taskmate.vercel.app` のような URL が発行されます。

### 本番ビルドで気をつける設定

```ts
// vite.config.ts
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  build: {
    sourcemap: false, // 本番では off にしてコードを読まれにくく
    target: "es2020",
  },
});
```

### CI: PR ごとに lint / test を走らせる

```yaml
# .github/workflows/ci.yml
name: CI
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run test -- --run
      - run: npm run build
```

これがあると、Vercel のプレビューデプロイと合わせて二重に守られます。

### 振り返りの Markdown テンプレート

```markdown
# TaskMate 振り返り（2026-04-27）

## Keep
- React Query 採用で fetch のロジックがほぼ消えた
- MSW で開発と E2E が同じモックを使えて生産性が高い
- 要件定義に半日かけたら手戻りが激減した

## Problem
- JWT を localStorage に入れたまま本番に出してしまった（XSS 対策不足）
- フォームのバリデーションを自作してしまい、メンテが苦しい
- E2E が flaky で CI が時々失敗する

## Try
- 次回は httpOnly Cookie + リフレッシュトークン構成にする
- フォームは React Hook Form + Zod を試す
- E2E は Playwright のリトライ機能と固定時刻を活用する
```

### Lighthouse でパフォーマンスを測る

```bash
npx lighthouse https://taskmate.vercel.app --view
```

「Performance」「Accessibility」「Best Practices」「SEO」のスコアが出ます。70 を切る項目があれば、そこが次の課題です。

## ❌ よくある間違い

### 1. 秘密情報を `VITE_` 環境変数に入れる

これは公開と同義です。BFF（Backend for Frontend）かサーバ側 API ルートで処理してください。

### 2. main に直接プッシュ

プレビュー URL でレビューする習慣をつけましょう。Branch Protection を有効化して、main は PR 経由のみマージ可にすると安心です。

### 3. デプロイしただけで満足する

公開してからが本番です。Sentry などのエラー監視、Vercel Analytics、Lighthouse 定期測定でデータを取り続けます。

### 4. 振り返りを「感想」で終わらせる

「楽しかった」「大変だった」では次に活きません。Try まで書いて、初めて学びになります。

### 5. `.env.local` をコミット

`.gitignore` に必ず入れましょう。事故ったら GitHub のシークレットスキャンで通知が来ますが、漏れた瞬間にキーは無効化が必要です。

## ✅ ベストプラクティス

1. **小さく早くデプロイする**: 「8 割完成してから」ではなく、空のページでよいので最初の週にデプロイしてしまう。
2. **Preview Deploy を活用**: PR レビューが「コードレビュー + 動作確認」の二段構えになる。
3. **環境変数は 3 環境で分ける**: 本番・プレビュー・開発で別の値。Vercel UI で簡単に設定可能。
4. **エラー監視を入れる**: Sentry など、ユーザーが踏んだエラーを見える化する。
5. **振り返りを書面で残す**: KPT を Obsidian / Notion に蓄積していくと、自分の成長グラフが見える。

## 📝 まとめ

- Vercel + GitHub の連携で「プッシュ→自動デプロイ」が簡単に組める
- 環境変数のうち、フロントに出してよいもの / よくないものの境界を意識する
- プレビューデプロイは現代の必須ワークフロー
- KPT 法で振り返りを言語化すると、経験が学びに変わる
- デプロイは「ゴール」ではなく「運用のスタート」
