# 16-4 テスト・リファクタ

## 🎯 この章で学ぶこと

- ユニットテスト・コンポーネントテスト・E2E テストの違いを理解する
- React Testing Library と Vitest を使った基本的なテストの書き方を覚える
- MSW（Mock Service Worker）で API をモックする方法を学ぶ
- リファクタリングを「動作を変えずに構造を変える」作業として定義し、実例を見る
- TaskMate にテストを追加し、コードを段階的に整える

## 📖 概念の説明

### テストの 3 階層（テストピラミッド）

```
        ▲
       ╱E2Eテスト╲       少なめ・遅い・本物に近い
      ╱──────────╲
     ╱統合/コンポ╲     中くらい
    ╱──────────────╲
   ╱  ユニットテスト  ╲   多め・速い・狭い
  ╱──────────────────╲
```

- **ユニットテスト**: 関数 1 つや React コンポーネント 1 つを単独で検証
- **コンポーネントテスト**: ユーザー目線で「クリックしたらどう動くか」を検証（React Testing Library 中心）
- **E2E テスト**: 本物のブラウザで「ログイン→投稿→削除」のような流れを検証（Playwright / Cypress）

ピラミッドの形を意識すると、「速いテスト多め、遅いテスト最小限」のバランスが取れます。

### React Testing Library（RTL）の哲学

「ユーザーが見ている画面に対してテストを書く」がモットーです。`getByRole`, `getByText`, `getByLabelText` など、ユーザー視点のクエリを使うことで、内部実装が変わってもテストが壊れにくくなります。

逆に、`getElementById` や CSS クラス名でセレクトすると、見た目を整えただけでテストが赤くなります。

### MSW（Mock Service Worker）

ネットワーク層でリクエストを横取りして、好きなレスポンスを返すモックライブラリ。テストでも開発サーバでも同じモックが使えるのが強みです。

### リファクタリングとは

「外から見た振る舞いを変えずに、コードの内部構造を整える」作業です。新機能を追加したり、バグを直したりするのとは別物。先にテストを書いておくと「リファクタしても壊れていない」が機械的に確認できます。

### コンポーネントテストの例: タスク一覧

```tsx
// src/features/tasks/TaskListPage.test.tsx
import { render, screen, waitFor } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { TaskListPage } from "./TaskListPage";

function renderWithQuery(ui: React.ReactElement) {
  const qc = new QueryClient({
    defaultOptions: { queries: { retry: false } },
  });
  return render(<QueryClientProvider client={qc}>{ui}</QueryClientProvider>);
}

describe("TaskListPage", () => {
  it("ロード後にタスクが表示される", async () => {
    renderWithQuery(<TaskListPage />);
    expect(screen.getByText(/読み込み/)).toBeInTheDocument();
    await waitFor(() => {
      expect(screen.getByText("牛乳を買う")).toBeInTheDocument();
    });
  });

  it("追加ボタンを押すと新しいタスクが先頭に並ぶ", async () => {
    const user = userEvent.setup();
    renderWithQuery(<TaskListPage />);
    await screen.findByText("牛乳を買う");

    await user.click(screen.getByRole("button", { name: "新規追加" }));
    await user.type(screen.getByLabelText("タイトル"), "卵を買う");
    await user.click(screen.getByRole("button", { name: "保存" }));

    await waitFor(() => {
      const items = screen.getAllByRole("listitem");
      expect(items[0]).toHaveTextContent("卵を買う");
    });
  });
});
```

### ユニットテストの例: 純粋関数

```ts
// src/features/tasks/sort.ts
export function sortByDueDate<T extends { dueDate: string | null }>(
  list: T[]
): T[] {
  return [...list].sort((a, b) => {
    if (a.dueDate === null) return 1;
    if (b.dueDate === null) return -1;
    return a.dueDate.localeCompare(b.dueDate);
  });
}
```

```ts
// src/features/tasks/sort.test.ts
import { sortByDueDate } from "./sort";

describe("sortByDueDate", () => {
  it("期限が近い順にソートされる", () => {
    const input = [
      { dueDate: "2026-05-10" },
      { dueDate: "2026-05-01" },
      { dueDate: null },
    ];
    expect(sortByDueDate(input).map((x) => x.dueDate)).toEqual([
      "2026-05-01",
      "2026-05-10",
      null,
    ]);
  });
});
```

### E2E テストの例（Playwright）

```ts
// e2e/login.spec.ts
import { test, expect } from "@playwright/test";

test("ユーザーはログインしてタスクを追加できる", async ({ page }) => {
  await page.goto("/login");
  await page.getByLabel("メール").fill("test@example.com");
  await page.getByLabel("パスワード").fill("password123");
  await page.getByRole("button", { name: "ログイン" }).click();

  await expect(page).toHaveURL("/");
  await page.getByRole("button", { name: "新規追加" }).click();
  await page.getByLabel("タイトル").fill("E2E テスト用タスク");
  await page.getByRole("button", { name: "保存" }).click();

  await expect(page.getByText("E2E テスト用タスク")).toBeVisible();
});
```

### リファクタの例: コンポーネント分割

**Before（1 ファイルに全部）:**

```tsx
function TaskListPage() {
  const [search, setSearch] = useState("");
  const [page, setPage] = useState(1);
  const { data } = useTasks({ search, page });
  // ...フィルタ UI、リスト、ページャを 200 行ぶん書いている
}
```

**After（責務分割）:**

```tsx
function TaskListPage() {
  const [filters, setFilters] = useState<Filters>({ search: "", page: 1 });
  const { data, isLoading } = useTasks(filters);

  return (
    <>
      <FilterBar value={filters} onChange={setFilters} />
      {isLoading ? <Spinner /> : <TaskTable items={data!.items} />}
      <Pagination
        page={filters.page}
        total={data?.total ?? 0}
        onChange={(p) => setFilters((f) => ({ ...f, page: p }))}
      />
    </>
  );
}
```

各小コンポーネントは独立にテストでき、再利用もできます。

## ❌ よくある間違い

### 1. 実装の詳細をテストする

```tsx
// ❌ state の中身を直接見る
expect(component.state.count).toBe(1);
```

React Testing Library を使うなら「ユーザーが見るもの」だけを検証します。

### 2. テストの中で `setTimeout` で待つ

```tsx
await new Promise((r) => setTimeout(r, 1000)); // ❌ flakeyテストの典型
```

`waitFor` や `findBy*` クエリを使いましょう。

### 3. モックしすぎてテストの意味がなくなる

ぜんぶ `vi.mock` で塗り潰すと、最終的に「モックが正しく呼ばれたか」しか検証していなくなります。MSW などで「本物に近い」レイヤをそのまま使う方が良いです。

### 4. リファクタとフィーチャ追加を同じコミットで行う

差分が読めなくなり、レビューが地獄化します。コミットは「動作を変えないリファクタ」「機能追加」「バグ修正」のいずれかに必ず分けましょう。

### 5. カバレッジ 100% を目標にする

カバレッジは指標であって目的ではありません。「重要な動作が壊れていないか」を測れていれば 70% で十分なケースも多いです。

## ✅ ベストプラクティス

1. **`getByRole` を第一選択にする**: アクセシビリティと可読性が同時に上がる。
2. **テストは「Arrange / Act / Assert」の 3 ブロックで書く**: 準備→実行→検証で揃えると読みやすい。
3. **MSW で API を一元化**: 開発・テスト・Storybook で同じモックが使えて DRY。
4. **リファクタの前に必ずテストを書く**: 「動いていた」を機械的に守る盾になる。
5. **flaky テストを放置しない**: 1 回でも不安定なテストはチームの信頼を蝕みます。原因を即修正。

## 📝 まとめ

- テストは「ユニット / コンポーネント / E2E」のピラミッドで構成
- React Testing Library + Vitest + MSW が現代の定番セット
- ユーザー目線のクエリ（getByRole 等）を使うと壊れにくい
- リファクタは「振る舞いを変えない」作業。テストで安全網を張る
- テストは品質保証であると同時に、設計の良し悪しを映す鏡
