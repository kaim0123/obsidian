# 16-1 要件定義（機能/非機能）

## 🎯 この章で学ぶこと

- 「要件定義」とは何か、なぜ最初に行うのかを理解する
- 機能要件と非機能要件の違いを言葉で説明できるようになる
- TODO アプリを題材に、実際の要件定義書を書いてみる
- ユーザーストーリー形式と受け入れ条件（Acceptance Criteria）の書き方を知る
- 「作る前に決める」ことが、後々の実装をどれだけ楽にするかを体験する

## 📖 概念の説明

### 要件定義とは？

要件定義とは、ひと言でいうと「これから作るものを言語化する作業」です。料理に例えるなら、いきなり鍋に火をかける前に「カレーを作る、4 人分、辛口、ルーは市販品、ジャガイモは入れない」というメニューを決めることに相当します。

プログラマーの世界では、いきなりエディタを開いて `npx create-react-app` から始めたくなるものですが、これは「冷蔵庫を開けて目に入った食材を順番に鍋に放り込む」のと同じです。出来上がりが美味しくなる保証がありません。

要件定義は大きく分けて 2 種類あります。

1. **機能要件（Functional Requirements）**: アプリが「何ができるか」
2. **非機能要件（Non-Functional Requirements）**: アプリが「どのくらいの品質か」

### 機能要件とは

機能要件は、ユーザーが画面上で行える操作を列挙したものです。「タスクを追加できる」「タスクを削除できる」「ログインできる」といった、動詞を含む文章で表現されることが多いです。

ポイントは「曖昧さを残さない」こと。「便利なタスク管理」では何も言っていないのと同じです。「ユーザーはタスクのタイトル（最大 100 文字）と期限日を指定して追加できる」とまで具体化します。

### 非機能要件とは

非機能要件は、機能の「質」を決めるルールです。次のような項目があります。

- **パフォーマンス**: ページ遷移は 1 秒以内、検索結果は 500ms 以内
- **可用性**: 99.5% のアップタイム
- **セキュリティ**: パスワードはハッシュ化保存、HTTPS 必須
- **アクセシビリティ**: キーボードのみで全操作が可能
- **対応ブラウザ**: 最新の Chrome / Edge / Safari / Firefox
- **保守性**: 主要なロジックには単体テストを書く

非機能要件は地味ですが、後から「やっぱりスマホ対応必要でした」と言われるととても困るので、最初に握っておくのが鉄則です。

### ユーザーストーリーで書く

機能要件を書くときに便利なのが「ユーザーストーリー」というフォーマットです。

```
<役割> として、<目的> のために、<機能> を行いたい。
```

例えば、「会社員として、その日のやることを忘れないために、タスクを追加・削除したい」のように書きます。これに「受け入れ条件」を添えれば、開発者にもデザイナーにも認識ズレが起きにくくなります。

### 今回の題材: TODO アプリ「TaskMate」

この章から第 16 章末まで、「TaskMate」という TODO アプリを実際に作っていきます。仕様は次の通りです。

- ユーザー登録 / ログイン（メール + パスワード）
- 自分のタスクの CRUD（作成・取得・更新・削除）
- タスクには期限・優先度・タグを付けられる
- 検索・絞込・ソート・ページネーション
- 一括操作（複数選択して完了にする等）
- CSV インポート / エクスポート

## 💻 コード例

要件定義そのものはコードではありませんが、Markdown で書くと管理しやすいので、テンプレートを示します。

### 要件定義書テンプレート（`docs/requirements.md`）

```markdown
# TaskMate 要件定義書

## 1. 概要
個人向けの TODO 管理 Web アプリ。複数デバイス間で同期する。

## 2. ペルソナ
- 名前: 山田さん（30 歳・会社員）
- 課題: 紙の手帳と Slack DM が混在し、漏れが発生している
- 利用シーン: 朝の通勤電車・昼休み・夜の振り返り

## 3. 機能要件（ユーザーストーリー形式）

### US-01: ユーザー登録
会社員として、自分のデータを安全に保つために、メールとパスワードでアカウントを作りたい。

**受け入れ条件**
- [ ] メールアドレスは形式チェックを行う
- [ ] パスワードは 8 文字以上、英数字混在
- [ ] 同じメールでの重複登録は不可
- [ ] 登録成功後、自動的にログイン状態になる

### US-02: タスク追加
会社員として、思いついたタスクを忘れないために、タイトルと期限を指定して追加したい。

**受け入れ条件**
- [ ] タイトルは必須・1〜100 文字
- [ ] 期限は今日以降の日付を指定可能（任意）
- [ ] 追加後、リストの先頭に表示される
- [ ] 失敗時はトースト通知でエラー表示

### US-03: タスク一覧表示
（以下省略）

## 4. 非機能要件
| 項目 | 要件 |
|------|------|
| パフォーマンス | First Contentful Paint < 1.5s |
| 可用性 | 月間 99.5% 以上 |
| セキュリティ | JWT 認証、HTTPS 必須、CSP ヘッダ設定 |
| 対応ブラウザ | Chrome/Edge/Safari/Firefox 最新 2 バージョン |
| アクセシビリティ | WCAG 2.1 AA 準拠 |

## 5. スコープ外
- スマホネイティブアプリ
- 他ユーザーとのタスク共有（v2 で検討）
```

### 受け入れ条件をテストコードに変換するイメージ

要件定義をきちんと書いておくと、そのままテストの章立てに使えます。

```ts
// __tests__/auth.test.ts （まだ動かなくて OK）
describe("US-01 ユーザー登録", () => {
  it("メール形式が不正なら登録できない", () => {});
  it("パスワードが 7 文字以下なら登録できない", () => {});
  it("登録成功後、自動的にログイン状態になる", () => {});
});
```

このように「要件 → テスト → 実装」の順で進めると、後戻りが激減します。

## ❌ よくある間違い

### 1. 「とりあえず作ってから考える」

最初にやってしまいがちですが、後から「あ、これも必要だった」が雪だるま式に増え、コードが破綻します。せめて 30 分でいいので、紙に書き出すクセをつけましょう。

### 2. 機能要件しか書かない

「速ければ速いほどいい」は要件ではありません。具体的な数値（〇〇 ms 以下）を書いておかないと、性能チューニングの終了条件が決まりません。

### 3. 受け入れ条件があいまい

「使いやすいこと」は受け入れ条件になりません。「タブキーで全フォーム要素を移動できる」のように、検証可能な形に落とし込みましょう。

### 4. スコープを切らない

「ついでにチャット機能も…」「カレンダーも欲しい…」と膨らませると終わりません。まず MVP（Minimum Viable Product）を定義し、それ以外は v2 リストに送りましょう。

## ✅ ベストプラクティス

1. **「やらないこと」を明記する**: スコープ外を書くだけで、議論が短くなります。
2. **数値で書く**: 主観表現（「速い」「軽い」）は禁止。数値で書く。
3. **ペルソナを設定する**: 「ユーザー」と書くと顔が見えませんが、「30 歳営業職の山田さん」と書くと判断軸ができます。
4. **要件と仕様を分ける**: 要件は「何を実現したいか」、仕様は「どう実現するか」。要件定義の段階で `useState` という単語が出てきたら混ざっています。
5. **チームで読み合わせをする**: 1 人で書いた要件は必ず抜けがあります。 30 分でいいので他人の目を入れる。

## 📝 まとめ

- 要件定義は「コードを書き始める前に作るものを言語化する」工程
- 機能要件（何ができる）と非機能要件（どんな品質か）の両方が必要
- ユーザーストーリーと受け入れ条件で曖昧さを排除する
- TaskMate は「個人向け TODO + タグ + 検索 + 一括操作 + インポート/エクスポート」
- 要件定義は後のテスト・実装・議論を 10 倍楽にする「未来への投資」
