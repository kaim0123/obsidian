# メソッド設計を学ぶ理由

## この章の目的

**なぜメソッド設計を学ぶのか**を理解する章です。  
クラス設計・モジュール設計との違い、巨大な `main` から関数へ進む理由、本教材の読み方を押さえます。

---

## 1. クラス設計・モジュール設計との違い

設計には **階層** があります。メソッド設計は、その中で **最も細かい実行単位** を扱います。

| 階層 | 比喩 | 扱うもの |
|------|------|----------|
| モジュール設計 | 部屋の役割分担 | パッケージ・レイヤー |
| クラス設計 | 家具の配置 | 型・オブジェクト・関係 |
| **メソッド設計** | **家具の細部** | **関数・メソッドの中身** |

たとえば注文システムで、

- **モジュール設計**: `order/` と `billing/` を分ける
- **クラス設計**: `Order` クラスと `OrderRepository` を設計する
- **メソッド設計**: `calculateTotal()` が何行で、何を引数に取るかを決める

クラスやモジュールの設計が良くても、**中のメソッドが 500 行** なら読めません。詳細は [[MOC_クラス設計体系|44 クラス設計]]・[[010Programming/43_モジュール設計/00_全体像/目次|43 モジュール設計 目次]] を参照してください。

## 2. 巨大な main から関数へ — なぜ分割するのか

初期のプログラムは `main` にすべてを直書きするスタイルが一般的でした。

```javascript
// 悪い例: すべてが main に入っている
function main() {
  // 入力 50 行
  // 検証 80 行
  // 計算 100 行
  // DB 保存 60 行
  // メール送信 40 行
}
```

**分割する理由** は次のとおりです。

- **読める** — 名前付きの塊で意図が伝わる
- **直せる** — 変更箇所を見積もれる
- **試せる** — 部品単位でテストできる
- **再利用できる** — 同じ処理をコピペしない

関数への分割は、すべてのメソッド設計の **出発点** です（[[02_関数とメソッドの基本]]）。

## 3. メソッド設計が解決する問題

メソッド設計を意識しないと、次の問題が起きやすくなります。

| 問題 | 症状 |
|------|------|
| **読めない** | 100 行関数で何をしているか分からない |
| **テストできない** | DB と UI を両方起動しないと検証できない |
| **変更が怖い** | 1 行直すと想定外の場所が壊れる |

```text
  設計なしのメソッド
      │
      ├─→ 巨大関数（神メソッド）
      ├─→ ネストした if（制御が追えない）
      └─→ 副作用だらけ（テスト困難）
              │
              ▼
        変更恐怖・属人化
```

これらは **構造の問題** です。Extract Method・Guard Clause・CQS などの技法で、かなりの部分は改善できます。

## 4. 本書の読み方と前提知識

### 前提知識

- 変数・関数・条件分岐・ループが書ける
- 小さなプログラム（数十〜数百行）を書いた経験がある

Guard Clause や CQS の **事前知識は不要** です。

### 読み方

1. **第1〜2部** で「なぜ」「何を目指すか」を掴む
2. **第3〜4部** で分割・抽出と制御フローの実践スキル
3. **第5〜6部** で副作用・命名・読みやすさの定着
4. **第7〜8部** でテスト・演習で統合する

> 歴史順で学びたい場合は [[00_メソッド設計の変遷]]（西暦順の整理）を併読してください。

## 5. 最初の一歩 — 今日からできること

メソッド設計は **明日から** 実践できます。

1. 50 行超の関数を 1 つ見つける
2. コメント `// ---` で区切られた塊を数える
3. 塊ごとに「動詞 + 目的語」の名前を考える
4. 次のリファクタリング機会に Extract Method を試す

完璧を目指す必要はありません。**1 関数を 10 行短くする** だけでも、読み手への配慮になります。

---

## まとめ

- メソッド設計は **クラスの中身** — 関数・メソッドの粒度と読みやすさを扱う
- 分割は読める・直せる・試せる・再利用できるコードのための第一歩
- 読めない・テストできない・変更が怖い — これらはメソッド設計で改善できる
- 本教材は技法から学べる構成。プログラミングの基礎があれば読める
