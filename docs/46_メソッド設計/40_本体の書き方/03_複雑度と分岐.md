# 複雑度と分岐

## この章の目的

**循環的複雑度** と分岐の多さを理解し、複雑な関数を分割する技法を学ぶ章です。

---

## 1. 循環的複雑度（McCabe）— 分岐の多さを測る

Thomas McCabe（1976）の **循環的複雑度（Cyclomatic Complexity）** は、プログラムの **分岐の多さ** を数値化します。

**概算**: 1 + 分岐点の数（`if`, `else`, `for`, `while`, `case`, `&&`, `||`, `?` 等）

```javascript
function example(a, b) {
  if (a) {        // +1
    if (b) {      // +1
      return 1;
    }
  }
  return 0;
}
// 複雑度 ≈ 3
```

**目安**: 1 関数あたり **10 以下** が望ましい。15 超は分割を検討。

---

## 2. 複雑度が高い関数の見分け方

| サイン | 説明 |
|--------|------|
| **分岐だらけ** | if / switch が 5 個以上 |
| **テストケース爆発** | 分岐の組み合わせでテストが書けない |
| **「とりあえず else」** | すべての分岐を網羅する else が増える |
| **Lint 警告** | complexity ルールに引っかかる |

```javascript
// 複雑度が高い典型
function getShippingCost(order) {
  if (order.region === 'JP') {
    if (order.weight < 1) { /* ... */ }
    else if (order.weight < 5) { /* ... */ }
    else { /* ... */ }
  } else if (order.region === 'US') {
    // さらに分岐...
  }
}
```

## 3. 分岐の分割 — 小関数・ポリモーフィズム・ルックアップ

複雑度を下げる **3 つの手法** です。

### 小関数への Extract Method

```javascript
function getShippingCost(order) {
  if (order.region === 'JP') return getJpShipping(order);
  if (order.region === 'US') return getUsShipping(order);
  return getDefaultShipping(order);
}
```

### ポリモーフィズム（クラス設計と連携）

地域ごとに `ShippingCalculator` サブクラスを用意（[[MOC_クラス設計体系|44 クラス設計]]）。

### ルックアップテーブル

```javascript
const SHIPPING = {
  JP: getJpShipping,
  US: getUsShipping,
};
function getShippingCost(order) {
  const fn = SHIPPING[order.region] ?? getDefaultShipping;
  return fn(order);
}
```

---

## 4. Lint / CI での閾値設定

チームで **複雑度の上限** を CI に組み込みます。

```json
// ESLint 例
{
  "rules": {
    "complexity": ["warn", 10]
  }
}
```

- **warn** — レビューのきっかけ
- **error** — マージをブロック（段階的導入を推奨）

行数（`max-lines-per-function`）と **併用** すると効果的です。

---

## 5. 行数だけでは測れない複雑さ

| 例 | 行数 | 複雑度 |
|----|------|--------|
| 50 行の直線的処理 | 多い | 低い |
| 20 行の分岐だらけ | 少ない | 高い |

**行数と複雑度は別物** です。20 行でも分岐が多ければ読みにくい。  
Clean Code の「20 行」は目安であり、**複雑度とセット** で判断します（[[01_サイズと抽象度]]）。

## 6. 区分や種別がコードを複雑にする

業務アプリでは「顧客区分」「料金種別」「ステータス」などの **区分・種別** ごとに if / switch が増えます。区分が1つ増えるたびに、同じ分岐がメソッドのあちこちに増殖しやすいです（コードの臭い「重複した switch」→ [[03_コードの臭いとリファクタリング対応表]]）。

整理の段階は次のとおりです。

```text
  1. if 内の式をメソッドに独立（意図に名前を付ける）
  2. else をなくし早期 return（[[02_Guard_Clause]]）
  3. 複文（入れ子の if）を単文の並びに分解
  4. 区分ごとのロジックをクラス／列挙へ（[[07_区分オブジェクトと状態遷移]]）
```

### 6.1 複文は単文に分ける

**複文** は「文の中に文がある」入れ子構造です。ネストした if や、1行に条件と処理を詰め込みすぎた書き方は、意図が追いづらくなります。

```typescript
// 悪い例: 複文（入れ子）
function discount(order: Order): number {
  if (order.isMember()) {
    if (order.total() >= 10000) {
      return order.total() * 0.2;
    } else {
      return order.total() * 0.1;
    }
  }
  return 0;
}

// 良い例: 単文を並べ、早期 return とメソッド名で意図を出す
function discount(order: Order): number {
  if (!order.isMember()) return 0;
  if (order.total() >= 10000) return largeMemberDiscount(order);
  return smallMemberDiscount(order);
}
```

入れ子をほどき、**1段の判断 + 名前付きの処理** にすると、読み手もテストも楽になります。

---

## まとめ

- 循環的複雑度 = 分岐の多さ。10 以下が目安
- 高複雑度は Extract Method・ポリモーフィズム・ルックアップで下げる
- **区分・種別の if** は散らばりやすい。メソッド化 → ガード節 → 区分オブジェクトへ段階的に寄せる
- **複文（入れ子）は単文の並び** に分解する
- Lint / CI で閾値を設定し、可視化する
- 行数だけでなく複雑度も見る
