# リファクタリングの実践

## この章の目的

**メソッド設計のリファクタリング** を実践する章です。  
いつ行うか、主要技法、レガシー関数への段階的適用、技術的負債との向き合い方を学びます。

---

## 1. いつリファクタリングするか

Martin Fowler の **「ルールオブスリー」** 等を参考に、次のタイミングが適切です。

| タイミング | 例 |
|-----------|-----|
| **3 回目の重複** | 同じロジックを 3 回書いた |
| **機能追加の前** | 触る前に読みやすくする |
| **バグ修正の後** | 構造が原因なら直す |
| **レビュー指摘** | 分割・命名の改善 |

**避ける**: リリース直前の大規模リファクタ、テストなしでの一括変更。

## 3. レガシー関数への段階的適用

**200 行の神関数** を一度に直さない — **小さく・安全に** 進めます。

1. **テストを 1 つ** 書く（特性テストでも可）
2. **Guard Clause** で異常系を先に抽出
3. **Extract Method** で 1 ブロックずつ切り出す
4. 各ステップで **テストが通る** ことを確認
5. 切り出した関数に **名前** を付け、責任を明確化

```text
  Week 1: テスト追加 + Guard Clause
  Week 2: 検証部分を extract
  Week 3: 計算部分を extract
  ...
```

---

## 4. 振る舞いを変えずに構造を変える

リファクタリングの **定義**（Fowler）:

> 外部から見た振る舞いを変えずに、内部構造を改善すること

| 許容 | 不可 |
|------|------|
| 関数の分割・統合 | 仕様変更 |
| 名前の変更 | バグ修正（別作業） |
| 引数の整理 | 新機能追加 |

**小さなコミット** + **テスト** で安全網を張ります。

---

## 5. 技術的負債との向き合い方

| 方針 | 説明 |
|------|------|
| **可視化** | 複雑度・行数で負債リストを作る |
| **優先付け** | 変更頻度の高い関数から |
| **Boy Scout Rule** | 触ったファイルは少しきれいに |
| **諦めない** | 全部直す必要はない。重要な所から |

歴史的な整理は [[00_メソッド設計の変遷]] を参照。  
チームでの運用は [[04_チームでメソッド設計を守る]] で扱います。

---

## 6. 安全網 — リファクタ前の最低限

| 手段 | 内容 |
|------|------|
| **特性テスト** | 既存出力を記録し、リファクタ後も一致を確認 |
| **スナップショット** | JSON 出力等を固定 |
| **カバレッジ** | 触る関数の行カバレッジ 80% 以上を目標 |
| **小さな PR** | 1 PR = 1 技法、200 行 diff 以内 |

「テストがないから直せない」→ **まず 1 テスト** から始めます。

**Boy Scout Rule のメソッド版**: 触った関数は、**1 つ Extract Method** するだけでも負債返済になる。

---

## まとめ

- リファクタリング = 振る舞いを変えず構造を改善
- Extract Method / Parameter Object / Replace Conditional が基本
- レガシーは段階的に。テストを先に
- 技術的負債は可視化し、優先付けて改善
