# チームでメソッド設計を守る

## この章の目的

**チーム開発** でメソッド設計の品質を保つ章です。  
スタイルガイド、Lint、CI 閾値、設計負債の可視化、ペアプロを学びます。

---

## 1. 関数スタイルガイドの作り方

**関数スタイルガイド** を文書化し、[[010Programming/59_AI開発ツール・コーディング規約/コーディング規約/目次|コーディング規約]] と連携します。

| 項目 | 例 |
|------|-----|
| 命名 | 動詞 + 目的語、`is`/`has`/`can` |
| サイズ | 目安 20 行、50 行超は要理由 |
| 引数 | 3 個以上は Parameter Object |
| 禁止 | 単独の `process`, `handle`, `data` |
| 必須 | Guard Clause で異常系を先に |

```markdown
## 関数のルール
- 1 関数 1 責任
- getter に副作用を入れない（CQS）
- 計算ロジックは純粋関数に切り出す
```

---

## 2. Lint / Formatter との連携

**自動化できるルール** は Lint に任せます。

```json
// ESLint 例
{
  "rules": {
    "complexity": ["warn", 10],
    "max-lines-per-function": ["warn", { "max": 50 }],
    "max-params": ["warn", 3]
  }
}
```

| ツール | 役割 |
|--------|------|
| **Formatter** | インデント・改行の統一 |
| **Lint** | 複雑度・行数・命名パターン |
| **型チェック** | 引数・戻り値の契約 |

---

## 3. 複雑度・行数の CI 閾値

CI で **閾値超過を警告** し、設計負債を可視化します。

```text
  PR 作成
     │
     ├─→ Lint（complexity, max-lines）
     ├─→ テスト
     └─→ 閾値超過 → 警告コメント（または block）
```

**段階的導入**: まず `warn` → チーム慣れ後に `error`。  
既存コードは **グランドファザー**（既存のみ許容）も検討。

---

## 4. 設計負債の可視化

| 指標 | ツール例 |
|------|----------|
| 循環的複雑度 | ESLint, SonarQube |
| 行数 | cloc, カスタムスクリプト |
| 重複 | jscpd, SonarQube |
| カバレッジ | Jest, pytest-cov |

**負債リスト** — 複雑度 Top 10 の関数を四半期ごとにレビューし、  
リファクタリング PR を計画的に作成します。

---

## 5. ペアプログラミングとメソッド設計

**ペアプロ** でメソッド設計を学ぶ場面:

- 200 行関数の **分割ワークショップ**
- Extract Method の **ライブリファクタ**
- レビュー前の **ペアレビュー**

```text
  Driver: コードを書く
  Navigator: 「ここ extract できない？」「名前は validateOrder？」
```

ナビゲーターが **設計の観点** を口に出す習慣が、チーム全体の底上げになります。

---

## 6. オンボーディング — 新人への伝え方

1. **第1〜3部** の章を 1 週間で読む（[[01_メソッド設計を学ぶ理由]] から）
2. **ペア** で 50 行関数を 1 本 Extract Method
3. **レビュー** でチェックリスト（[[付録B_メソッド設計チェックリスト]]）を一緒に使う
4. **1 ヶ月後** に振り返り — 自分の PR で改善できた点を共有

「ルール暗記」より **分割の感覚** を体で覚えることを優先します。

---

## まとめ

- 関数スタイルガイドを文書化し、コーディング規約と連携
- Lint / CI で複雑度・行数を自動チェック
- 設計負債を可視化し、計画的に返済
- ペアプロで分割・命名を共有
