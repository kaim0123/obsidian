# テストしやすいメソッド設計

## この章の目的

**テスト容易性** をメソッド設計の判断基準にする章です。  
純粋関数のテスト、モックの使い方、モック地獄のサインを学びます。

---

## 1. テスト容易性とは何か

**テスト容易性（Testability）** とは、メソッドが **単体で・高速に・ deterministically** テストできる度合いです。

| テストしやすい | テストしにくい |
|---------------|---------------|
| 入力 → 出力だけ | DB・ネットワーク必須 |
| 副作用なし | グローバル状態に依存 |
| 依存が引数で明示 | 内部で `new` やシングルトン |

テストが書きにくい = **設計改善のサイン** です。

---

## 2. 純粋関数のテスト — 入力と出力だけ

純粋関数は **最もテストしやすい** 形です。

```javascript
function calculateTotal(items) {
  return items.reduce((s, i) => s + i.price * i.qty, 0);
}

// テスト
test('calculateTotal sums items', () => {
  const items = [{ price: 100, qty: 2 }, { price: 50, qty: 1 }];
  expect(calculateTotal(items)).toBe(250);
});
```

モック不要、高速、再現可能 — FCIS の Core をこう設計します（[[03_Functional_Core_Imperative_Shell]]）。

---

## 3. 副作用のモック — どこまで必要か

**Shell** では I/O をモックすることがあります。

```javascript
// 依存を引数で渡す
async function placeOrder(order, repo, notifier) {
  await repo.save(order);
  await notifier.send(order);
}

// テスト
test('placeOrder saves and notifies', async () => {
  const repo = { save: jest.fn() };
  const notifier = { send: jest.fn() };
  await placeOrder(order, repo, notifier);
  expect(repo.save).toHaveBeenCalledWith(order);
});
```

**原則**: モックは **境界（Shell）** だけ。Core はモック不要。

---

## 4. モック地獄 — 設計の問題のサイン

**モック地獄** = 1 テストで 10 個のモックを設定する状態。

| サイン | 原因 |
|--------|------|
| モックが 5 個以上 | 1 関数に関心が多すぎ |
| モックの順序に依存 | 副作用の連鎖 |
| テストが実装の詳細に依存 | 情報隠蔽の失敗 |

**対策**:

1. Extract Method で **純粋部分を切り出す**
2. SoC で **関心を分離** する
3. 依存を **引数で注入** する

---

## 5. テストから見えたメソッド設計の改善

**テスト駆動の設計フィードバック**:

```text
  テストが書きにくい
       │
       ├─→ 副作用を Core から Shell へ
       ├─→ 引数を減らす / Parameter Object
       ├─→ グローバル依存を注入に変更
       └─→ 巨大関数を Extract Method
```

テストを **設計の鏡** として使い、リファクタリングの優先順位を決めます（[[02_リファクタリングの実践]]）。

---

## 6. チェックリスト — テスト容易性

- [ ] 純粋関数として切り出せる計算があるか
- [ ] 時刻・乱数は引数で注入できるか
- [ ] DB / HTTP は Shell だけか
- [ ] 1 テストのモックは 2 個以下か
- [ ] テストが **Given-When-Then** で書けるか

---

## まとめ

- テスト容易性 = 単体・高速・再現可能
- 純粋関数は入力出力だけでテスト
- モックは Shell の境界だけ
- モック地獄 = 設計改善のサイン
