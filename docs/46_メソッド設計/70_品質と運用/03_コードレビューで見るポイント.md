# コードレビューで見るポイント

## この章の目的

**メソッド設計** の観点でコードレビューを進める章です。  
チェックリスト、良い関数・悪い関数の比較、改善提案の書き方を学びます。

---

## 1. メソッド設計レビューの進め方

1. **全体像** — オーケストレーション関数から読む（流れの目次）
2. **粒度** — 1 関数 1 責任か、抽象度は揃っているか
3. **制御** — ネスト・複雑度・Guard Clause
4. **契約** — 副作用・CQS・エラー処理
5. **テスト** — 単体テスト可能か

```text
  レビュー時間の配分（目安）
  ─────────────────────
  40%  構造・分割・責任
  30%  読みやすさ・命名
  20%  エラー・副作用
  10%  スタイル・細部
```

---

## 2. レビュー用チェックリスト

- [ ] 1 メソッド 1 種類の仕事（SoC / SRP）
- [ ] 50 行超・複雑度 10 超の関数がないか
- [ ] ネスト 3 段以上 → Guard Clause を検討
- [ ] `process()` `handleData()` 等の曖昧名がないか
- [ ] getter に副作用がないか（CQS）
- [ ] 引数 3 個以上 → Parameter Object を検討
- [ ] 純粋にできる計算が I/O と混在していないか

## 3. 良い関数・悪い関数の比較

### 悪い例

```javascript
function handle(data, flag) {
  if (data) {
    if (flag) {
      db.save(data);
      return data.total;
    }
  }
}
```

| 問題 | 内容 |
|------|------|
| 名前 | `handle` が曖昧 |
| フラグ引数 | `flag` で複数責任 |
| ネスト | 正常系が深い |
| CQS | 保存と取得が混在 |

### 良い例

```javascript
function persistAndGetTotal(order) {
  if (!order) return null;
  persistOrder(order);
  return order.total;
}
```

さらに `persistOrder` と `getTotal` に分離すると CQS に沿います。

## 4. 改善提案の書き方

**建設的なフィードバック** の型:

1. **観察** — 「この関数は 80 行で、検証と保存が混在しています」
2. **影響** — 「テストで DB モックが必要になります」
3. **提案** — 「`validateOrder` と `saveOrder` に Extract Method しませんか」
4. **参考** — 「[[04_Extract_Method]] の 6.3 節」

```text
  ❌ 「読みにくい」だけ
  ✅ 「検証部分（L12-45）を validateOrder() に切り出すと、
      単体テストしやすくなります」
```

## 5. 新人へのフィードバックの仕方

| 避ける | 推奨 |
|--------|------|
| 人格批判 | コードへの指摘 |
| 一度に 20 指摘 | 優先度付き 3 点 |
| 正解だけ提示 | 理由と参考リンク |

**ペアで読む** — オーケストレーション関数を一緒に上から読み、  
「ここで何をしている？」と問いかけると、新人自身が分割点を見つけやすくなります。

---

## まとめ

- レビューは構造 → 読みやすさ → エラー → スタイルの順
- チェックリストで抜け漏れを防ぐ
- 改善提案は観察・影響・提案・参考
- 新人には理由付きで、優先度を絞る
