# KISS・DRY・YAGNI — メソッドレベルの原則

## この章の目的

メソッド設計で毎日使う **3 つの原則** を学ぶ章です。  
KISS・DRY・YAGNI の意味、衝突時の判断、実践のコツを押さえます。

---

## 1. KISS — 賢さより単純さ

**KISS（Keep It Simple, Stupid）** = **必要以上に賢く書かない**。

```javascript
// 過剰: 1 行の処理を Strategy パターンで 5 ファイルに
// 適切: 素直に書く
function calculateTax(amount, rate) {
  return amount * rate;
}
```

メソッドレベルでは次を意識します。

- 抽象化は **2 回目の重複が見えたとき** に検討
- 「短く」より **意図が一目で分かる**
- 将来の拡張を理由に **使われない引数** を増やさない

---

## 2. DRY — 同じ知識を二重に書かない

**DRY（Don't Repeat Yourself）** = **同じ知識・同じ変更理由** のコードを重複させない。

```javascript
// 悪い例: 同じ税計算が 3 か所
function calcA(x) { return x * 0.1; }
function calcB(y) { return y * 0.1; }

// 良い例: 1 か所に集約
function calculateTax(amount) { return amount * TAX_RATE; }
```

**注意**: 見た目が似ているだけ（偶然の一致）を無理に DRY にしない。  
**知識が同じ** — 税率が変わったら **すべて** 直す必要がある — ときに DRY です。

---

## 3. YAGNI — 使わない引数・汎化を作らない

**YAGNI（You Aren't Gonna Need It）** = **今必要ないものは作らない**。

```javascript
// 悪い例: 使われない options
function sendEmail(to, subject, body, options = {}) {
  const { cc, bcc, template, locale, retryPolicy } = options;
  // cc も bcc も未使用
}

// 良い例: 今必要な引数だけ
function sendEmail(to, subject, body) { /* ... */ }
```

汎用パラメータ・多目的関数・「将来用」のフラグ引数は YAGNI 違反になりやすいです。

---

## 4. 原則同士が衝突するとき（DRY vs SRP vs KISS）

| 状況 | 判断のヒント |
|------|-------------|
| DRY vs SRP | 無理に 1 関数にまとめると責任が混ざる → **SRP を優先** |
| DRY vs KISS | 抽象化でファイルが増えすぎる → **KISS を優先** |
| SRP vs KISS | 1 行関数が 50 個 → **適度に統合** |

```text
  原則は「絶対ルール」ではなく「判断の材料」
  → 変更理由・読み手・テスト容易性で決める
```

---

## 5. 変更理由で判断する実践のコツ

原則が衝突したら **「何が変わったらこのコードを直すか」** で決めます。

1. **変更理由が同じ** → DRY で 1 関数に
2. **変更理由が違う** → SRP で分離
3. **まだ 1 回しか出てこない** → YAGNI で待つ
4. **読み手が迷う** → KISS で単純に

歴史的背景は [[00_メソッド設計の変遷]] の KISS・DRY の節を参照。

---

## 6. 判断ワークショップ — 3 つのシナリオ

| シナリオ | 判断 | 理由 |
|----------|------|------|
| 同じ 3 行の税計算が 2 か所 | DRY | 税率変更が 1 理由 |
| 似たループだが用途が別 | KISS | 変更理由が違う。統合しない |
| `options` に未使用フィールド | YAGNI | 削除する |
| 抽象クラス 1 回しか継承されない | KISS | 2 回目まで待つ |

**覚えておくこと**: 原則は **チェックリスト** ではなく **会話の材料**。  
「DRY にしよう」より「この 2 か所、同じ理由で変わる？」と問う方が実践的です。

---

## まとめ

- KISS = 単純さを優先。過剰な抽象化を避ける
- DRY = 同じ知識の重複を避ける（見た目の一致 ≠ DRY）
- YAGNI = 今使わない汎化・引数を作らない
- 衝突時は変更理由で判断する
