# メソッド設計 — 西暦順でたどる

## このノートの目的

**メソッド設計**（関数設計）とは、クラスやモジュールの **中で最も小さい実行単位** — 関数・メソッド・プロシージャ — を、**読みやすく・テストしやすく・変更しやすい** 形に整えることです。

[[02_設計の階層と全体像]] の比喩で言えば、クラス設計が「家具の配置」なら、メソッド設計は **「家具の細部 — 引き出しの開け方、取っ手の位置、1 動作の粒度」** に相当します。

このノートでは、メソッド設計の考え方を **登場が早い順（おおよその西暦）** に並べ、次の流れで整理します。

1. **その前に、どんな課題があったか**
2. **何を提案したか**
3. **どう解決したか**
4. **向いている場面・限界**

クラス設計との重なりは [[00_クラス設計の変遷]] を参照。ここでは **1 関数・1 メソッド** に焦点を当てます。

---

## 全体の流れ（年表）

| 順番 | 考え方・手法 | 登場時期 | 一言で言うと | 主に解決した課題 |
|------|-------------|----------|-------------|-----------------|
| 0 | **モノリシック main + goto** | 1940〜1950年代 | 上から順に命令を書く | 処理の流れが追えない |
| 1 | **手続き（サブルーチン）・構造化** | 1960〜1970年代 | 名前付きの処理単位に分割 | 巨大 main・goto 地獄 |
| 2 | **KISS** | 1960年頃 | 賢くより単純に | メソッドの過剰な抽象化 |
| 3 | **段階的詳細化（トップダウン）** | 1970年代 | 大きな処理を小さく割る | 関数の粒度の判断がない |
| 4 | **関心の分離（SoC）** | 1974年 | 1 関数 1 種類の仕事 | 1 関数に複数の関心が混在 |
| 5 | **情報隠蔽（関数レベル）** | 1972年 | 詳細は関数の中に閉じる | 呼び出し側が内部を知りすぎ |
| 6 | **循環的複雑度（McCabe）** | 1976年 | 分岐の多さを測る | 複雑な関数の客観評価 |
| 7 | **オブジェクトのメソッド** | 1967年〜 | 状態に対する操作として振る舞いを定義 | データと処理の乖離 |
| 8 | **Design by Contract / Fail Fast** | 1986〜1988年 | 前提を先に検査し、違反は即座に失敗 | 不正な状態の先送り |
| 9 | **CQS（コマンド・クエリ分離）** | 1988年 | 読む操作と書く操作を分ける | 取得メソッドが副作用を持つ |
| 10 | **Guard Clause（早期 return）** | 1990年代〜1999年 | 異常系を先に弾いて本流を浅く | ネストした if の深さ |
| 11 | **Extract Method・リファクタリング** | 1999年 | 長い関数を意味の塊で切り出す | 100 行関数・重複 |
| 12 | **DRY** | 1999年 | 同じ知識を二重に書かない | 関数間のロジック重複 |
| 13 | **SRP（メソッド版）** | 2000年代初頭 | 1 メソッド 1 責任 | 巨大メソッド・変更理由の混線 |
| 14 | **Clean Code の関数ルール** | 2008年 | 小さく・少引数・意図が伝わる命名 | 読めない関数・引数地獄 |
| 15 | **純粋関数・副作用の分離** | 1950年代起源、2000年代再注目 | 同じ入力 → 同じ出力 | テスト困難・状態競合 |
| 16 | **Functional Core, Imperative Shell** | 2010年代 | 計算は純粋、I/O は外縁 | 副作用とロジックの混在 |

> **補足:** 年は「名前が広まった時期」の目安です。  
> **「関数」と「メソッド」:** 手続き指向では **関数（function）**、OOP では **メソッド（method）** と呼びますが、設計上の論点はほぼ同じです。本ノートでは **メソッド** を主語にし、関数型の **純粋関数** も含めて扱います。

## 0. その前：モノリシック main + goto（1940〜1950年代）

高級言語が普及する前、プログラムは **main の中にすべてを直書き** し、`goto` で飛び回るスタイルが一般的でした。

### よく起きていた課題

- **処理の流れが追えない** — ラベルへの `goto` が乱立し、スパゲッティコードになる
- **再利用できない** — 同じ処理をコピペし、修正漏れが発生
- **テストできない** — 全体を実行しないと 1 か所の正しさを確認できない
- **名前で意図を表せない** — 「ここからここまでが入力処理」が **行番号とコメント** 頼み

### 次の時代への問い

> **「処理を、名前付きの小さな単位に分け、流れを読みやすくするには？」**

→ 背景: [[00_ソフトウェア設計の変遷#1. 手続き指向（1950年代〜）]]

---

## 1. 手続き（サブルーチン）・構造化プログラミング（1960〜1970年代）

**背景:** Fortran の SUBROUTINE（1950年代）、ALGOL 60、Dijkstra の構造化プログラミング（1960年代後半〜1970年代）  
**一言:** 処理を **名前付きの手続き（関数・サブルーチン）** に分割し、**順次・分岐・反復** だけで制御する  
**詳細:** [[00_ソフトウェア設計の変遷#1. 手続き指向（1950年代〜）]]

### その前の課題 — 巨大 main と goto 地獄

- 数千行の `main` に入力・検証・計算・出力が **全部入り**
- `goto` で飛ぶため、**どの経路を通ったか** が読み取れない
- 同じ検証ロジックが **3 か所にコピペ** されている
- 1 行直すと **想定外の場所** が壊れる

### 何を提案したか

| 原則 | 内容 |
|------|------|
| **3 つの基本構造** | 順次・分岐・反復だけで組み立てる（`goto` を排除） |
| **手続き（関数）** | 意味のある **名前付き単位** に分割し、呼び出して再利用 |
| **単一入口・単一出口** | 1 関数は 1 か所から入り、出口は整理する（※Guard Clause 登場後は柔軟に解釈） |

```javascript
// 構造化: 意味のある単位に分割
function processOrder(order) {
  validate(order);
  const total = calculateTotal(order);
  save(order, total);
  return total;
}
```

### どう解決したか

- プログラムを **読める塊** に分割し、**トップダウン** で理解できる
- 手続き単位で **デバッグ・再利用** の入口ができる
- `goto` 排除で **制御フローの予測可能性** が上がる

### 向いている場面・限界

- **向く:** すべてのメソッド設計の **出発点**。どんな言語でも関数に分ける
- **限界:** 分けただけでは **関数が巨大・グローバル状態依存** のまま → 段階的詳細化・SoC へ

## 2. KISS — Keep It Simple, Stupid（1960年頃）

**提唱:** Kelly Johnson（Lockheed Skunk Works）  
**一言:** **賢さより単純さ** — メソッドは必要以上に抽象化・汎化しない  
**詳細:** [[00_設計原則の変遷#1. KISS（1960年頃）]]、[[01_DRY_KISS_YAGNI#KISS原則（Keep It Simple, Stupid）]]

### その前の課題 — 過剰な抽象化

- 「将来の拡張」を理由に **3 層のラッパー関数** だけのメソッド
- 1 行で済む処理を **Strategy パターン** で 5 ファイルに分割
- 読む人より **書いた人だけ** が理解できる関数
- **YAGNI 違反** のメソッド引数（使われない `options` オブジェクト）

### 何を提案したか

**最も単純な実装で要件を満たす。** メソッドレベルでは次を意識する。

- 抽象化は **2 回目の重複が見えたとき** に検討（DRY とセット）
- 汎用パラメータより **具体的な名前と引数**
- 「短く書く」より **意図が一目で分かる**

### どう解決したか

- メソッドの **認知負荷** を下げ、レビューと変更が速くなる
- 過剰設計を抑え、**読み手の時間** を節約する

### 向いている場面・限界

- **向く:** 日常の実装判断、リファクタリングで「複雑にしすぎていないか」のチェック
- **限界:** 単純さと **DRY・拡張性** はトレードオフ → 変更理由で判断

---

## 3. 段階的詳細化 — トップダウン設計（1970年代）

**背景:** Niklaus Wirth（*Program Development by Stepwise Refinement*, 1971）  
**一言:** 大きな処理を **一段ずつ小さな関数** に分解していく

### その前の課題 — 関数の粒度の判断がない

- 構造化は分かったが **「どこで切るか」** の基準がない
- 10 行の関数と 500 行の関数が **同じ「関数」** として混在
- 抽象度が **バラバラ** — 高レベルの `process()` の中にビット演算が直書き
- 分解しすぎて **1 行関数が 50 個** 並び、全体像が見えない

### 何を提案したか

**段階的詳細化（Stepwise Refinement）:**

1. まず **問題を 1 つの手続き** として書く（詳細は仮名でよい）
2. 各ステップを **さらに小さな手続き** に置き換える
3. **同じ抽象度のステップ** が並ぶレベルで止める

```text
printChessboard()
  ├─ printRow(row)          ← 行単位
  │    └─ printSquare(row, col)  ← マス単位
  └─ ...
```

### どう解決したか

- **トップダウン** で関数の階層を設計でき、読み手は **必要な深さだけ** 読める
- 後の **Extract Method**（意味の塊で切り出す）の思想的背景になる

### 向いている場面・限界

- **限界:** 粒度の **物差し** だけでは不十分 → SoC・SRP へ

---

## 4. 関心の分離 — SoC（1974年）

**提唱:** Edsger W. Dijkstra（*On the Role of Scientific Thought*, 1974）  
**一言:** 1 つの関数に **1 種類の関心** だけを入れる  
**詳細:** [[01_関心の分離]]

### その前の課題 — 1 関数に複数の関心が混在

- `saveUser()` が **バリデーション・DB 保存・メール送信・ログ出力** まで全部やる
- フォーマット変更のたび **DB ロジック付きの関数** を触る
- テストで **DB とメールサーバを両方モック** する必要がある
- 「この関数、何をする関数？」と **一言で説明できない**

### 何を提案したか

**関心の分離（Separation of Concerns）:** 異なる **変更理由** を持つ処理を、異なる関数（・モジュール）に分ける。

```javascript
// 関心ごとに分離
function validateUser(user) { /* 入力検証だけ */ }
function persistUser(user) { /* 永続化だけ */ }
function notifyUserRegistered(user) { /* 通知だけ */ }

function registerUser(user) {
  validateUser(user);
  persistUser(user);
  notifyUserRegistered(user);
}
```

### どう解決したか

- 変更の **影響を関数単位** に閉じ込める
- テストで **関心ごとにモックを分け** られる
- 後の **SRP（単一責任）** のメソッド版の基盤になる

### 向いている場面・限界

- **向く:** オーケストレーション関数（`registerUser`）と詳細関数の **役割分担**
- **限界:** 分けすぎると **呼び出しチェーン** が長くなる → KISS・適切な粒度で調整

## 5. 情報隠蔽 — 関数レベル（1972年）

**提唱:** David L. Parnas（*On the Criteria To Be Used in Decomposing Systems into Modules*, 1972）  
**一言:** **変更されうる詳細** を関数内部に閉じ、呼び出し側には **契約だけ** 見せる  
**詳細:** [[00_モジュール設計の変遷#2. 情報隠蔽 — Parnas モジュール（1972年）]]

### その前の課題 — 呼び出し側が内部を知りすぎ

- 税計算の内部が「10% 固定」から「地域別税率」に変わるたび、**呼び出し側 20 か所** を修正
- 関数が **内部表現（配列 vs Map）** を返し、利用側が構造に依存
- 「ヘルパー関数」が **モジュール外に漏れ**、直接呼ばれて契約化する
- リファクタリングのたび **利用側の連鎖修正** が起きる

### 何を提案したか

| 観点 | 悪い例 | 良い例 |
|------|--------|--------|
| 公開面 | 内部用 `calculateTaxRate()` も export | **必要な操作だけ** 公開 |
| 戻り値 | 内部データ構造をそのまま返す | **必要な情報だけ** を返す（DTO・値） |
| 引数 | 呼び出し側が内部アルゴリズム用の値を渡す | **意図が分かる引数** だけ |

```javascript
// 内部: 税率テーブル・端数処理は隠す
function calculateTax(amount, region) {
  const rate = lookupRate(region); // 内部詳細
  return roundTax(amount * rate);  // 内部詳細
}
```

### どう解決したか

- 実装変更を **関数の内部** に閉じ込め、呼び出し側の修正を減らす
- クラス設計の **カプセル化** と同じ思想が **関数スコープ** にも適用できる

### 向いている場面・限界

- **向く:** アルゴリズム・フォーマット・外部 API の差し替えが予想される処理
- **限界:** 何を隠すかは **SoC・SRP** とセットで判断

## 6. 循環的複雑度 — McCabe（1976年）

**提唱:** Thomas J. McCabe（*A Complexity Measure*, 1976）  
**一言:** 関数内の **分岐（if / loop / case）の数** で複雑さを測る

### その前の課題 — 複雑な関数の客観評価がない

- 「この関数、複雑すぎでは？」が **感覚論** だけ
- 分岐が 15 個ある関数が **レビューをすり抜ける**
- テストケース数と **分岐数の関係** が設計上意識されない
- リファクタリングの **優先順位** が付けられない

### 何を提案したか

**循環的複雑度（Cyclomatic Complexity）:** おおよそ「独立した実行パスの数」。  
目安として **10 以下** が読みやすく、**15 超** は分割を検討、という運用が広まった。

```javascript
// 複雑度が高い: 分岐が多い
function process(x) {
  if (x > 0) {
    if (x < 10) { /* ... */ }
    else if (x < 100) { /* ... */ }
    else { /* ... */ }
  } else {
    /* ... */
  }
}
// → Guard Clause + 小関数への Extract で分割
```

### どう解決したか

- 関数の **複雑さを数値化** し、Lint や CI で検知できる
- **Guard Clause・Extract Method** で分割する動機付けになる

### 向いている場面・限界

- **向く:** レガシーコードの改修優先度、CI の閾値設定
- **限界:** 行数は短くても **ネストが深い** 問題は別指標 → Guard Clause へ

## 7. オブジェクトのメソッド（1967年〜）

**背景:** Simula（1967）、Smalltalk（1972）、C++（1983）、Java（1995）  
**一言:** **状態（フィールド）に対する操作** としてメソッドを定義する  
**詳細:** [[02_クラスとオブジェクト]]、[[00_クラス設計の変遷#1. オブジェクト・クラス（1967年〜）]]

### その前の課題 — データと処理の乖離（関数版）

- `updateBalance(accountId, amount)` のように **ID とデータが別**
- 同じ口座に触るメソッドが **クラス外に散在**
- 「誰が残高を変更できるか」の **ルール** が呼び出し側に分散
- 手続き名だけでは **どのデータに対する操作か** が不明瞭

### 何を提案したか

**メソッド = オブジェクトに対するメッセージ。** 状態を持つ「もの」に、振る舞いを **メソッドとして結びつける**。

```javascript
class BankAccount {
  #balance = 0;

  withdraw(amount) {
    if (amount > this.#balance) throw new Error('残高不足');
    this.#balance -= amount;
  }
}
```

### どう解決したか

- データと操作が **同じ型の中** にあり、変更の入口が明確
- **Tell, Don't Ask**（後述）の土台 — データを取り出して操作するより、オブジェクトに **お願いする**

### 向いている場面・限界

- **向く:** 状態を持つドメイン概念、不変条件を守りたい操作
- **限界:** ロジックがサービスクラスに逃げる **貧血モデル** → DDD・ドメインメソッドへ

## 8. Design by Contract / Fail Fast（1986〜1988年）

**提唱:** Bertrand Meyer（Eiffel、*Object-Oriented Software Construction*, 1988）  
**一言:** **前提条件をメソッドの先頭で検査** し、違反は **即座に失敗** させる  
**関連:** Fail Fast（Java コミュニティ等で 1990〜2000年代に普及）

### その前の課題 — 不正な状態の先送り

- 引数が `null` なのに **深い処理まで進み**、原因不明の NPE
- エラーを **黙って swallow** し、後段で奇妙な結果だけが出る
- バリデーションが **呼び出し側と関数内に二重** に存在
- 「どこで壊れたか」が **スタックトレースから遠い**

### 何を提案したか

| 概念 | 内容 |
|------|------|
| **前置条件（Precondition）** | 呼び出し側が満たすべき条件 — メソッド先頭で検査 |
| **後置条件（Postcondition）** | メソッドが保証する結果 |
| **Fail Fast** | 異常は **早い段階** で検出し、黙って進まない |

```javascript
function withdraw(account, amount) {
  if (!account) throw new TypeError('account is required');
  if (amount <= 0) throw new RangeError('amount must be positive');
  if (amount > account.balance) throw new Error('残高不足');
  // ここから先は前提が満たされている
  account.balance -= amount;
}
```

### どう解決したか

- バグの **発見地点と原因** が近づく
- メソッドの **契約** がコード上で明示される
- Guard Clause と **相補関係** — 異常系を先に弾く具体技法

### 向いている場面・限界

- **向く:** 公開 API、ドメインルールの境界、ライブラリの入口
- **限界:** すべてを例外にすると **制御フローが読みにくい** 場合も → Result 型等と使い分け

---

## 9. CQS — Command-Query Separation（1988年）

**提唱:** Bertrand Meyer（*Object-Oriented Software Construction*, 1988）  
**一言:** **状態を変える（Command）** と **値を返す（Query）** を **同じメソッドに混ぜない**

### その前の課題 — 取得メソッドが副作用を持つ

- `getUser()` が **DB から読むたびに lastAccessed を更新**
- `findAndMarkAsRead()` のように **名前は get なのに変更** する
- 同じ Query を **2 回呼ぶと結果や状態が変わる**
- テストで「読むだけ」のつもりが **副作用で DB が汚れる**

### 何を提案したか

| 種類 | 役割 | 戻り値 |
|------|------|--------|
| **Command（コマンド）** | 状態を変える | `void`（または成功/失敗のみ） |
| **Query（クエリ）** | 状態を **変えず** 情報を返す | データ（副作用なし） |

```javascript
// Query: 副作用なし
function getBalance(account) {
  return account.balance;
}

// Command: 状態を変える（残高は Query で取得）
function withdraw(account, amount) {
  if (amount > account.balance) throw new Error('残高不足');
  account.balance -= amount;
}
```

**例外:** 同一オブジェクト内の **lazy 初期化** など、副作用が局所で明白な場合は Meyer 自身も pragmatic に許容。

### どう解決したか

- メソッド名と **振る舞いの一致**（`get` / `is` は Query など）
- **参照透過性** に近い Query を保ち、推論・テスト・並行処理が楽になる
- 後の **CQRS**（システム全体の読み書き分離）の **メソッド版** として理解できる

### 向いている場面・限界

- **向く:** ドメインモデル、リポジトリ、boolean を返す `is*` / `has*` / `can*`
- **限界:** 「取得しつつキャッシュ更新」など **現実的な混在** もある → 命名で意図を明示

→ 命名の具体例: [[リーダブルコード]]

## 10. Guard Clause — 早期 return（1990年代〜1999年）

**背景:** 防御的プログラミングの実践、Kent Beck らの Smalltalk / XP 文化  
**書籍:** Martin Fowler *Refactoring*（1999）— **「ネストした条件分岐をガード節に置き換える」**  
**一言:** **異常系・境界条件を先頭で return** し、正常系をフラットに書く

### その前の課題 — ネストした if の深さ

- 正常系が **4 段ネスト** の奥にあり、読むのにスクロールが必要
- `else` 枝が **正常系と異常系** を混在させ、意図が不明
- 新しい条件追加のたび **ネストが深く** なり McCabe 複雑度が上がる
- 「この関数、結局何をしている？」が **最後まで読まないと分からない**

### 何を提案したか

**Guard Clause（ガード節）:** 前提を満たさない場合は **即 return / throw** し、以降は正常系だけ。

```javascript
// Before: ネストが深い
function process(order) {
  if (order) {
    if (order.isValid()) {
      if (order.hasStock()) {
        return execute(order);
      }
    }
  }
  return null;
}

// After: Guard Clause
function process(order) {
  if (!order) return null;
  if (!order.isValid()) return null;
  if (!order.hasStock()) return null;
  return execute(order);
}
```

### どう解決したか

- **正常系が一直線** に読める（Fail Fast・Design by Contract と相性が良い）
- 複雑度と **認知負荷** を下げる
- Extract Method と組み合わせ、ガード後のブロックを **別関数** にできる

### 向いている場面・限界

- **向く:** 前提チェックが多い関数、API の入口、バリデーション
- **限界:** 対称的な分岐（A も B も同等に複雑）では **if-else のまま** の方が読みやすいことも

## 11. Extract Method・リファクタリング（1999年）

**提唱:** Martin Fowler（*Refactoring: Improving the Design of Existing Code*, 1999）  
**一言:** 長い関数から **意味のある塊** を **新しい関数に抽出** する

### その前の課題 — 100 行関数・重複

- コピペで **同じ 10 行** が 3 関数に存在
- 1 関数が **複数の抽象度** を混在（HTTP パースと税計算）
- コメント `// --- ここから検証 ---` が **関数の構造** を代弁している
- テストしたい部分だけ **切り出せない**

### 何を提案したか

**Extract Method（メソッド抽出）:** 選択したコードを、**意図が伝わる名前の関数** にする。

```javascript
// 抽出前
function printOwing(invoice) {
  printBanner();
  let outstanding = 0;
  for (const o of invoice.orders) outstanding += o.amount;
  printDetails(outstanding);
}

// 抽出後
function printOwing(invoice) {
  printBanner();
  const outstanding = calculateOutstanding(invoice);
  printDetails(outstanding);
}
```

関連するリファクタリング: **Replace Temp with Query**、**Introduce Parameter Object**（引数の塊をオブジェクト化）

### どう解決したか

- 関数を **同じ抽象度のステップ** の並びにできる（段階的詳細化の実践）
- 重複除去の **具体手順**（DRY の実装手段）
- テスト対象を **小さく切り出せる**

### 向いている場面・限界

- **向く:** レガシー改修、コードレビュー後の整理
- **限界:** 抽出しすぎると **ジャンプだらけ** → KISS・読み手の視線で調整

→ 詳細: [[04_リファクタリングの考え方]]

## 12. DRY — Don't Repeat Yourself（1999年）

**提唱:** Andy Hunt, Dave Thomas（*The Pragmatic Programmer*, 1999）  
**一言:** **同じ知識** を複数のメソッドに書かない  
**詳細:** [[01_DRY_KISS_YAGNI#DRY原則（Don't Repeat Yourself）]]

### その前の課題 — 関数間のロジック重複

- 税率計算が **5 関数** にコピペされ、税率変更で **5 か所修正**
- 「たまたま同じコード」なのに共通化し、**変更理由の違う** 関数が結合
- ヘルパーを作らず **コピペ** する方が早い短期文化

### 何を提案したか

**DRY:** 重複しているのは **コードの見た目** ではなく **知識（意図・ルール）** かを見る。

- 同じ知識 → **1 つの関数** に集約
- 知識が違う → **分離を維持**（SRP と衝突するときは SRP 優先）

### どう解決したか

- 変更を **1 関数に集約** し、修正漏れを減らす
- Extract Method とセットで **実践的な重複除去**

### 向いている場面・限界

- **向く:** ビジネスルール、フォーマット、定数計算
- **限界:** 偶然の一致を DRY すると **結合が増える** → [[03_DRY・YAGNI原則の落とし穴と実践的判断]]

---

## 13. SRP — メソッド版・単一責任（2000年代初頭）

**提唱:** Robert C. Martin（SOLID、*Agile Software Development*, 2002 前後）  
**一言:** **1 メソッドは 1 つの責任（変更理由）** だけ  
**詳細:** [[01_SRP（単一責任の原則）]]

### その前の課題 — 巨大メソッド・変更理由の混線

- `handleRequest()` が **認証・パース・DB・レスポンス生成** まで 200 行
- ログ形式変更で **DB コードに触る** 必要がある
- メソッド名が `process()` `doIt()` **何をするか不明**
- 単体テストが **シナリオテスト 1 本** しか書けない

### 何を提案したか

**メソッドレベルの SRP:**

- メソッド名で **1 文で説明** できること
- **1 つの抽象度** だけを扱うこと
- 変更理由が複数なら **分割** する

```javascript
// 責任が混在
function handleRequest(req) {
  /* 認証 + バリデーション + 永続化 + ログ + レスポンス */
}

// 責任ごとに分割
function handleRequest(req) {
  const user = authenticate(req);
  const command = parseCommand(req);
  validate(command);
  const result = execute(command, user);
  return formatResponse(result);
}
```

### どう解決したか

- SoC を **メソッド粒度** で具体化
- Clean Code の「**関数は 1 つのことだけ**」につながる

### 向いている場面・限界

- **向く:** サービスクラス、ユースケース関数、HTTP ハンドラ
- **限界:** 分けすぎは **オーケストレーション関数** が増える → 許容範囲内でバランス

---

## 14. Clean Code の関数ルール（2008年）

**提唱:** Robert C. Martin（*Clean Code*, 2008）  
**一言:** **小さく・少引数・意図が伝わる命名・副作用を抑える**

### その前の課題 — 読めない関数・引数地獄

- 関数が **50 行超**、変数宣言だけで画面を占める
- 引数が **7 個** あり、呼び出し時に **順番を間違える**
- `getX()` が **副作用** でログ出力・キャッシュ更新
- 関数名が **`handleData` `processItem`** で検索しても特定できない

### 何を提案したか

| ルール | 目安 |
|--------|------|
| **サイズ** | 短く。20 行以内が目安（長ければ Extract） |
| **抽象度** | 1 関数 = 1 抽象度。`renderPage()` の中に HTML 文字列連結を直書きしない |
| **引数** | **0〜2 が理想**、3 以上は Parameter Object を検討 |
| **命名** | 動詞 + 目的語。boolean は `is` / `has` / `can` |
| **副作用** | Query 風の関数に **隠れ副作用** を入れない（CQS と一致） |
| **エラー** | 例外より **try-catch だらけ** を避け、Guard + Fail Fast |

```javascript
// 引数が多い → Parameter Object
function createUser(name, email, age, role, department, managerId) { /* ... */ }

function createUser(params) {
  validateCreateUserParams(params);
  return buildUser(params);
}
```

### どう解決したか

- メソッド設計の **実践チェックリスト** として広く使われる
- CQS・SRP・Guard Clause・Extract Method を **1 冊に統合**

### 向いている場面・限界

- **向く:** コードレビュー、新規コードのスタイル基準
- **限界:** 行数だけのルールは **文脈を無視** しうる → 意図と抽象度を優先

→ 命名: [[命名規則]]、[[リーダブルコード]]

---

## 15. 純粋関数・副作用の分離（1950年代起源、2000年代再注目）

**背景:** Lisp（1958）、Haskell（1990）、JavaScript / Java への関数型機能取り込み（2000年代〜）  
**一言:** **同じ入力 → 同じ出力**、**外部状態を変えない** 関数を核に  
**詳細:** [[00_ソフトウェア設計の変遷#3. 関数型指向（1950年代に起源、2000年代以降に再注目）]]

### その前の課題 — テスト困難・状態競合

- 同じ引数なのに **呼ぶタイミングで結果が変わる**（グローバル変数・DB 参照）
- ログ・DB・API が **1 関数に混在** し、モック地獄
- 並行実行で **同じ関数が状態を壊し合う**
- 「この関数、何に依存している？」が **読みきれない**

### 何を提案したか

**純粋関数（Pure Function）:**

- 引数以外の **外部状態を読まない**
- **外部状態を書き換えない**（副作用なし）
- 同じ入力に **常に同じ出力**

```javascript
// 非純粋: 外部の taxRate に依存
let taxRate = 0.1;
function calcTax(amount) {
  return amount * taxRate;
}

// 純粋: 依存を引数で明示
function calcTax(amount, rate) {
  return amount * rate;
}
```

**副作用を減らす** 実践:

- 計算・変換・検証は **純粋関数** に
- I/O は **境界** に押し出す（次項 FCIS）

### どう解決したか

- **ユニットテスト** が入力/output だけで完結
- **並行処理** でロックが不要になりうる
- CQS の Query を **より厳密** に実践できる

### 向いている場面・限界

- **向く:** 料金計算、バリデーション、データ変換、ドメインルール
- **限界:** 現実の I/O は副作用 → **どこで許容するか** を設計（FCIS）

## 16. Functional Core, Imperative Shell（2010年代）

**背景:** Gary Bernhardt（*Boundaries*, 2012）、関数型コミュニティの実践知  
**一言:** **中心は純粋関数（Functional Core）**、**外側だけ I/O（Imperative Shell）**

### その前の課題 — 副作用とロジックの混在

- 「少しだけ DB 読む」関数が **ドメイン計算の真ん中** にある
- 純粋にしようとして **モナドだらけ** になり、チームが追いつかない
- テストしたい **計算部分** を切り出す **境界** が設計されていない

### 何を提案したか

```text
┌─────────────────────────────────────┐
│  Imperative Shell（副作用あり）      │
│  HTTP / DB / ログ / 時刻              │
│         ↓ データを渡す               │
│  ┌─────────────────────────────┐    │
│  │ Functional Core（純粋関数）   │    │
│  │ 計算・ルール・変換             │    │
│  └─────────────────────────────┘    │
│         ↑ 結果を受け取る             │
└─────────────────────────────────────┘
```

```javascript
// Shell: I/O
async function createOrderHandler(req) {
  const input = parseRequest(req);
  const order = buildOrder(input);       // Core（純粋）
  await repository.save(order);          // Shell
  return formatResponse(order);
}

// Core: 純粋
function buildOrder(input) {
  validateItems(input.items);
  return { items: input.items, total: calculateTotal(input.items) };
}
```

### どう解決したか

- **純粋関数のメリット** を、現実的な I/O ありシステムで取り込める
- メソッド設計の **最新の落とし所** — OOP のメソッドと FP の関数を **役割で使い分け**

### 向いている場面・限界

- **向く:** ユースケース層、ドメインサービスとリポジトリの境界
- **限界:** 小さな CRUD だけのアプリでは **層が過剰** になりうる → KISS

## 17. まとめ — 歴史は「課題の積み重ね」

```text
モノリシック main + goto
    ↓ 名前付き単位・構造化
  手続き（サブルーチン）（1960s〜）
    ↓ 賢さより単純に
  KISS（1960s）
    ↓ 大きく書いて小さく割る
  段階的詳細化（1970s）
    ↓ 1 関数 1 関心
  関心の分離（SoC, 1974）
    ↓ 詳細を関数内に
  情報隠蔽（Parnas, 1972）
    ↓ 分岐の多さを測る
  循環的複雑度（McCabe, 1976）
    ↓ 状態に対する操作
  オブジェクトのメソッド（1967〜）
    ↓ 前提を先頭で、違反は即失敗
  Design by Contract / Fail Fast（1988）
    ↓ 読むと書くを分ける
  CQS（1988）
    ↓ 異常系を先に return
  Guard Clause（1990s〜1999）
    ↓ 意味の塊で切り出す
  Extract Method / リファクタリング（1999）
    ↓ 同じ知識を二重に書かない
  DRY（1999）
    ↓ 1 メソッド 1 責任
  SRP メソッド版（2000s）
    ↓ 小さく・少引数・命名
  Clean Code 関数ルール（2008）
    ↓ 同じ入力 → 同じ出力
  純粋関数・副作用分離（2000s再注目）
    ↓ 核は純粋、外縁だけ I/O
  Functional Core, Imperative Shell（2010s）
```

### 最初のメモからの対応表

| メモの項目 | 本ノートでの位置づけ |
|-----------|---------------------|
| 単一責任 | §13 SRP（§4 SoC の具体化） |
| 分かりやすい命名 | §14 Clean Code（§9 CQS と命名規則） |
| 引数を減らす | §14 Clean Code、§11 Parameter Object |
| 副作用を減らす | §9 CQS、§15 純粋関数、§16 FCIS |
| Guard Clause | §10 |
| CQS | §9 |
| Fail Fast | §8 Design by Contract |
| 純粋関数 | §15 |
| KISS | §2 |
| DRY | §12 |
| SRP | §13 |

### 初心者が覚えておくとよいこと

1. **分割が最初。** 構造化（§1）と Extract Method（§11）— 長い関数は必ず疑う。
2. **正常系を浅く。** Guard Clause（§10）+ Fail Fast（§8）— 異常系を先に弾く。
3. **読むと書くを分ける。** CQS（§9）— `get` / `is` に副作用を入れない。
4. **計算は純粋に。** 副作用（§15）— テストが一気に楽になる。
5. **物差しは複数。** KISS vs DRY vs SRP は **矛盾することがある** → **変更理由** で判断。

### 学習順 vs 歴史順

| 観点 | おすすめ順 | 理由 |
|------|-----------|------|
| **歴史（本ノート）** | 構造化 → … → FCIS | 課題が **なぜ生まれたか** が分かる |
| **学習** | Extract Method → Guard Clause → CQS → SRP → 純粋関数 | **すぐ書ける技法** から入ると効果が見えやすい |
