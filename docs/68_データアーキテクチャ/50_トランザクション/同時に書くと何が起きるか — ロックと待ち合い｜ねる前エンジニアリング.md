## 詳しい要約

**テーマ：同じ行を同時に書き換えると何が起きるか — 失われた更新とロックの使い分け**

2つの処理がほぼ同時に同じ行を書き換えると、1つずつなら起きない「失われた更新」が起きる。防ぐ道具は「1つの文で引き算」「行ロック（悲観的ロック）で並ばせる」「版の番号（楽観的ロック）で気づく」の3つで、**ぶつかりが多いなら並ばせる、少ないなら見つけてやり直す**、というのが結論。

---

### よくある場面

- セール開始の瞬間に同じ商品へ注文が集中し、後で数えると在庫の数字が実物より多い → ないものを売ってお詫びすることに
- テストでは一度も起きない。**同時に来たときだけ起きる**ので、コードを読んだだけでは気づきにくい

### 更新が消える瞬間（失われた更新）

- 注文処理が「在庫を読む → 手元で1を引く → 書き戻す」の3手順だとする
- 在庫3に A さんと B さんがほぼ同時に注文 → 2人とも3を読み、2人とも2と計算し、2人とも2と書く
- 2つ売れたのに在庫は2のまま。後から書いた人が先の結果を上書きした＝**失われた更新（lost update）**
- 原因は**読んでから書くまでの隙間**に割り込まれること

### 道具1：1つの文で引き算

- 引き算をデータベースの中でやってもらう（`在庫 = 在庫 - 1` を1つの文で頼む）。読む・引く・書くを DB が一度にまとめ、その行に一瞬だけ鍵をかける
- B さんの文は一瞬待って続けて動き、A さんの結果の上に引き算する → 正しく1になる
- さらに「在庫が1以上のときだけ」という条件を同じ文に付ける。在庫0なら何も変わらず、**変わった行の数が0**で返る → アプリは売り切れと表示
- 数の足し引きだけ（在庫やカウンター）ならまずこの形を考える
- コードでは、実行後に**変わった行の数を必ず確かめる**。0行は売り切れでありエラーではない。見落とすと売れていないのに「購入完了」と出る

### 道具2：行ロックで並ばせる（悲観的ロック）

- 在庫・ポイント・クーポンを確かめてから決めるなど、判断が長く1つの文に収まらないときに使う
- `SELECT ... FOR UPDATE`（書き換えるつもりで読む）で、読むときに鍵をかける
- 後から来た B さん・C さんは鍵が外れるまで**1列に並んで待つ（待ち合い）**。A さんが確定（コミット）すると鍵が外れ、次の人は前の結果を見て引き算を重ねるので上書きが起きない
- ぶつかる前提で先に鍵を取るので**悲観的ロック**と呼ぶ

### 鍵を握ったまま待たせない

- 鍵を持ったまま外部の決済サービスを呼び、返事が遅れると、後ろの全員が待ち続ける（決済と在庫は関係ないのに）
- 待つ側は一定時間で諦めて**ロック待ちタイムアウト**のエラーになる。セールの日に注文画面が次々エラーに
- 鍵を持っている間は速く終わることだけをする。**外のサービスを呼ぶのは鍵を取る前か確定した後**
- 遅いと感じたら、誰が鍵を長く持っているかを疑う

### お互いに待つと止まる（デッドロック）

- 剣と盾を交換する処理で、A さんは剣→盾、B さんは盾→剣の順に鍵をかけると、互いに相手の鍵を待ってどちらも進めない＝**デッドロック**
- DB はこの輪に気づくと片方を失敗にして巻き戻す。そのエラーのときは**もう一度やり直す作り**にしておく
- もっと良いのは輪を作らないこと。**鍵を取る順番をみんなで揃える**（例: 番号の小さい行から）。待つことはあっても止まりはしない

### 道具3：版の番号で気づく（楽観的ロック）

- ぶつかることは滅多にないと考える方法。例: 管理画面でお知らせ記事を2人の担当者が編集
- 行に**版（バージョン）の番号**を持たせ、開いたときに読んでメモしておく。編集中は鍵をかけない（何分もかかるので鍵は持たせられない）
- 保存時は「版がまだ5なら書き換えて版を6にする」と頼む。先に保存した A さんは通り、後の B さんは版が6になっているので変わった行が0 → 「他の人が先に直しました」と知らせ、最新版を読み直して直してもらう
- 黙って上書きされるよりずっとよい

### コードで見る2つのロック

- 楽観的ロック：開いたときに版を読み、保存時に版を1増やしつつ「版が読んだときと同じなら」の条件で書き、変わった行数を確かめる。確かめ忘れると何も保存されていないのに「保存しました」と出る
- 行ロック：トランザクション開始後に `FOR UPDATE` で読んだ瞬間に鍵がかかり、コミットで外れる。この間を短く保つ。トランザクションを書き忘れると、設定によっては1文ごとに確定してすぐ鍵が外れ、守っているつもりで守れていない

### ぶつかりが多いと、やり直しが積もる

- 限定アイテムに4人が同時に買いに来ると、楽観的ロックでは最初の1人だけ通り、残りはやり直し、また1人だけ通り…と**やり直しが積もり**、読み直しと書き込みが増えてかえって遅くなる
- 人気の行は1つの文の引き算か行ロックで並ばせる。楽観的ロックが光るのは**ぶつかるのが稀な場所**（管理画面の編集、自分のプロフィール更新など）

### 使い分け

| | 行ロック（悲観的） | 楽観的ロック |
|---|---|---|
| やり方 | 読むときに鍵をかける | 鍵をかけず版の番号を持つ |
| ぶつかったとき | 列で待つ | 0行で気づく |
| 向く場所 | ぶつかりが多い | ぶつかりが少ない |
| 注意 | 鍵の時間を短く、順番を揃える | 0行だったときの処理を必ず書く |

- 選び方：数の足し引きだけ → 1つの文 / 長い判断がいり、ぶつかりが多い → 行ロック / 人が何分も編集する画面 → 楽観的ロック
- ロックの種類は他にもたくさんあるが、全部覚える必要はなく今夜の3つで十分

### AIに書かせたときのチェックポイント

1. 読んで手元で計算して書き戻していないか（AI はとても自然にこう書く。1人で試すと動く）
2. UPDATE の後、変わった行の数を確かめているか
3. 鍵を持ったまま外のサービスを呼んでいないか（トランザクション開始とコミットの間に通信があれば要注意）
4. 複数の行に鍵をかけるとき順番が揃っているか（デッドロック防止）
5. 2人が同時に来るテストがあるか（なければ AI に同時に2つ動かすテストも書かせる。同時実行の問題は普通のテストではまず見つからない）

### まとめ

- 読んで計算して書く、その隙間に割り込まれると更新が消える（失われた更新）
- 数の足し引きだけなら1つの文で DB の中で計算する。長い判断がいるなら行ロックで1列に並ばせ、鍵を持つ時間は短く、取る順は揃える
- 滅多にぶつからないなら楽観的ロックの版の番号で気づいてやり直す
- どの方法でも変わった行の数を確かめる。**ぶつかりが多いなら並ばせる、少ないなら見つけてやり直す**
