# マイグレーションの実践例

[[MOC_データアーキテクチャ体系|📚 目次]] ｜ [[03_マイグレーションの実行とロールバック|← 前へ]] ｜ [[05_マイグレーションのよくある問題と対処法|次へ →]]

> [!abstract] この記事で分かること
> - 実務でよくある 6 つのスキーマ変更を、Shop の例題で手順どおりに進める方法
> - 「1 回のマイグレーションで済む変更」と「複数回のデプロイに分けるべき変更」の見分け方
> - 列名変更・型変更・NOT NULL 追加・テーブル分割・列削除で、データを失わずアプリも止めない順番
> - 機能開発の中でマイグレーションを作り、チームに共有し、本番に届けるまでの流れ
>
> **前提**：[[02_マイグレーションファイルの書き方]] と [[03_マイグレーションの実行とロールバック]] を読んでいると理解しやすいです。

## 1. ひとことで言うと

スキーマ変更は、**営業中のお店の模様替え**に似ています。棚を 1 つ足すだけなら営業中でもすぐできます。しかし「レジの場所を移す」なら、新しいレジを設置する → 両方で会計できるようにする → 店員に新しいレジを使ってもらう → 古いレジを撤去する、と段階を踏むはずです。いきなり古いレジを外すと、その瞬間に会計が止まります。

この記事の例は、すべて次の考え方で組み立てています。

- **足す変更**（テーブル・列・インデックスの追加）は、1 回のマイグレーションで済むことが多い
- **変える・消す変更**（名前変更・型変更・削除・NOT NULL 化）は、**「追加 → 移行 → 切り替え → 削除」**に分けて、複数回のデプロイで進める

```mermaid
flowchart LR
    A["① 追加<br/>新しい列・表を足す"] --> B["② 移行<br/>既存データをコピー・変換"]
    B --> C["③ 切り替え<br/>アプリが新しい方を使う"]
    C --> D["④ 削除<br/>古い列・表を消す"]
```

この流れは**Expand/Contract（拡張と縮小）パターン**と呼ばれます。本番で止めずに行うための細かな注意（ロック、分割実行など）は [[07_ゼロダウンタイムのスキーマ変更]] で詳しく扱います。この記事では、まず**手順の骨格**を身に付けます。

## 2. 例1：新しいテーブルを作る（reviews）

### 要件
商品レビュー機能を追加する。1 人のユーザーは 1 つの商品に 1 件だけレビューできる。評価は 1〜5。

### 手順
これは「足す変更」なので、**1 回のマイグレーション**で済みます。

```bash
# schema.prisma に Review モデルを追加してから
npx prisma migrate dev --create-only --name create_reviews
```

生成された SQL に、Prisma では書けない CHECK 制約を追記します。

```sql
-- prisma/migrations/20260201091500_create_reviews/migration.sql
CREATE TABLE reviews (
  id         BIGSERIAL PRIMARY KEY,
  product_id BIGINT NOT NULL REFERENCES products(id),
  user_id    BIGINT NOT NULL REFERENCES users(id),
  rating     INTEGER NOT NULL,
  body       TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT reviews_product_user_key UNIQUE (product_id, user_id)
);

-- 手で追記
ALTER TABLE reviews ADD CONSTRAINT reviews_rating_check CHECK (rating BETWEEN 1 AND 5);

-- 「ユーザーのレビュー一覧」用。(product_id, user_id) の UNIQUE は product_id 始まりなので、
-- user_id だけの検索には効かない
CREATE INDEX reviews_user_id_idx ON reviews (user_id);
```

### ポイント
- 新しいテーブルはまだ誰も使っていないので、ロックの心配はほぼありません
- 外部キーの列に**インデックスがあるか**を必ず確認します（複合インデックスの先頭列でない列は別途必要。理由は [[03_インデックスの基本と設計]]）

## 3. 例2：列名を変える（users.name → display_name）

### 要件
`users.name` が「本名」と誤解されるので、`display_name` に名前を変えたい。

### やり方 A：メンテナンス時間を取れる場合（1 回で済ませる）

サービスを一時停止してよいなら、`RENAME` 1 文で終わります。

```sql
ALTER TABLE users RENAME COLUMN name TO display_name;
```

アプリを止める → マイグレーション → 新しいアプリを起動、の順で行います。`RENAME` 自体はデータを書き換えないので一瞬で終わります。

### やり方 B：サービスを止めない場合（4 段階）

止められない場合、`RENAME` した瞬間に、まだ動いている古いアプリが `name` 列を探してエラーになります。そこで段階を踏みます。

| 段階 | マイグレーション | アプリの変更 |
|---|---|---|
| ① 追加 | `ALTER TABLE users ADD COLUMN display_name TEXT;` | **両方の列に書き込む**（読むのは `name`） |
| ② 移行 | `UPDATE users SET display_name = name WHERE display_name IS NULL;`（大量なら分割） | — |
| ③ 切り替え | `ALTER TABLE users ALTER COLUMN display_name SET NOT NULL;`（安全な方法は 07 の記事） | **`display_name` から読む**。書き込みは両方を継続 |
| ④ 削除 | `ALTER TABLE users DROP COLUMN name;` | `name` への書き込みをやめる（このデプロイの後で ④ を流す） |

各段階は**別々のデプロイ**です。どの時点でも「動いている全バージョンのアプリ」が正しく動く、というのがポイントです。

### Prisma で書くとき
各段階で `schema.prisma` を次のように変えていきます。

```prisma
// ① 追加の段階
model User {
  id          BigInt  @id @default(autoincrement())
  name        String
  displayName String? @map("display_name")
  // ...
}

// ④ 削除の段階
model User {
  id          BigInt @id @default(autoincrement())
  displayName String @map("display_name")
  // ...
}
```

④で生成される SQL が `DROP COLUMN "name"` だけになっていることを、`--create-only` で確認してから適用します。

## 4. 例3：型を変える（products.price を INTEGER → BIGINT）

### 要件
高額商品を扱うことになり、`INTEGER`（最大約 21 億）では足りなくなる可能性が出てきた。

### 何が問題か
```sql
ALTER TABLE products ALTER COLUMN price TYPE BIGINT;
```

この 1 文は正しく動きますが、`INTEGER` → `BIGINT` は**テーブル全体とインデックスの書き換え**を伴います。その間、テーブルは最も強いロック（`ACCESS EXCLUSIVE`）を取られ、**読み取りも含めて全クエリが止まります**。数千行なら一瞬ですが、数千万行なら数分以上かかることがあります。

> [!note] 書き換えが起きない型変更もある
> `VARCHAR(50)` → `TEXT` のように、データの表現が変わらない（バイナリ互換な）変更は、PostgreSQL ではテーブルの書き換えが不要です。どの変更が書き換えになるかは [[07_ゼロダウンタイムのスキーマ変更]] の表を参照してください。

### 手順（小さいテーブル、または短時間の停止が許される場合）
```sql
SET lock_timeout = '5s';   -- ロックを 5 秒待っても取れなければ諦める（07 の記事参照）
ALTER TABLE products ALTER COLUMN price TYPE BIGINT;
```

### 手順（大きいテーブルで止められない場合）
列名変更と同じく、新しい列を作って移し替えます。

| 段階 | 作業 |
|---|---|
| ① 追加 | `ALTER TABLE products ADD COLUMN price_v2 BIGINT;` アプリは両方に書く |
| ② 移行 | `price_v2` に `price` をコピー（分割して実行） |
| ③ 切り替え | `price_v2` に NOT NULL と CHECK を付け、アプリは `price_v2` を読む |
| ④ 削除 | `price` を削除し、必要なら `price_v2` を `price` に `RENAME`（メンテナンス時間に行うか、`@map` で吸収する） |

### MySQL の場合
MySQL 8.4 では、列のデータ型の変更は `ALGORITHM=COPY`（テーブルのコピー）でしか行えません。大きなテーブルでは gh-ost などのオンラインスキーマ変更ツールを使うのが一般的です（[[07_ゼロダウンタイムのスキーマ変更]]）。

## 5. 例4：NOT NULL を追加する（products.category_id）

### 要件
これまで `products.category_id` は NULL を許していたが、「全商品は必ずカテゴリに属する」ことにしたい。

### 手順

**ステップ 1：違反データを数える**

```sql
SELECT count(*) FROM products WHERE category_id IS NULL;
-- → 1,234 件
```

**ステップ 2：受け皿を作り、アプリが NULL を書かないようにする**

```sql
-- マイグレーション：「未分類」カテゴリを用意（何度流しても1件だけ）
INSERT INTO categories (name) VALUES ('未分類')
ON CONFLICT (name) DO NOTHING;
```

同時に、アプリのコードを「商品作成時にカテゴリ必須」に変更してデプロイします。**これをしないと、ステップ 3 で埋めている間にも新しい NULL が入ってきます。**

**ステップ 3：既存の NULL を埋める**

```sql
UPDATE products
SET category_id = (SELECT id FROM categories WHERE name = '未分類')
WHERE category_id IS NULL;
```

**ステップ 4：NOT NULL 制約を付ける**

```sql
ALTER TABLE products ALTER COLUMN category_id SET NOT NULL;
```

`SET NOT NULL` は、制約を付ける前に**全行を読んで NULL がないか確認**します。その間 `ACCESS EXCLUSIVE` ロックがかかるため、大きいテーブルでは「`CHECK` 制約を `NOT VALID` で付ける → `VALIDATE` する → `SET NOT NULL`」という安全な手順を使います（[[07_ゼロダウンタイムのスキーマ変更]]）。

### ポイント
- 「データを直す」より先に「**新しい違反データが入らないようにする**」
- 埋める値（ここでは「未分類」）は、ビジネス側と相談して決める。適当な値で埋めると、後で本当の値と区別できなくなる

## 6. 例5：テーブルを分割する（users.address → user_addresses）

### 要件
今まで `users` に住所を 1 つだけ持たせていた（`users.address` 列がある前提）。複数の配送先を登録できるようにするため、別テーブルに分けたい。

```
変更前                           変更後
users                            users              user_addresses
├ id                             ├ id          1 ─< ├ id
├ name                           ├ name             ├ user_id  → users.id
├ email                          ├ email            ├ label     ('自宅' など)
└ address                        └ ...              ├ address
                                                    └ is_default
```

### 手順

**① 新しいテーブルを作る**

```sql
CREATE TABLE user_addresses (
  id         BIGSERIAL PRIMARY KEY,
  user_id    BIGINT NOT NULL REFERENCES users(id),
  label      TEXT NOT NULL DEFAULT '自宅',
  address    TEXT NOT NULL,
  is_default BOOLEAN NOT NULL DEFAULT false
);
CREATE INDEX user_addresses_user_id_idx ON user_addresses (user_id);

-- 既定の住所は 1 ユーザー 1 件まで（部分ユニークインデックス）
CREATE UNIQUE INDEX user_addresses_one_default
  ON user_addresses (user_id) WHERE is_default;
```

アプリは「住所を保存するとき、`users.address` と `user_addresses` の**両方に書く**」ように変更します。

**② 既存データをコピーする**

```sql
INSERT INTO user_addresses (user_id, label, address, is_default)
SELECT u.id, '自宅', u.address, true
FROM users u
WHERE u.address IS NOT NULL
  AND NOT EXISTS (                       -- 再実行しても重複しない
    SELECT 1 FROM user_addresses a WHERE a.user_id = u.id
  );
```

**③ 読み取りを切り替える**

アプリが `user_addresses` から住所を読むように変更してデプロイします。しばらく運用して、両者の内容がずれていないか確認します。

```sql
-- ずれの確認：users.address と既定住所が違うユーザー
SELECT u.id
FROM users u
JOIN user_addresses a ON a.user_id = u.id AND a.is_default
WHERE u.address IS DISTINCT FROM a.address;
```

**④ 古い列を削除する**

アプリから `users.address` への読み書きを完全になくしたバージョンをデプロイした**後で**、列を削除します。

```sql
ALTER TABLE users DROP COLUMN address;
```

### ポイント
- コピーは `NOT EXISTS` などで**再実行しても安全**にしておく
- 切り替え後すぐに削除せず、**ずれがないことを確認する期間**を置く
- テーブルの分け方そのもの（正規化）の考え方は [[02_正規化]] を参照

## 7. 例6：列を削除する（products.legacy_code）

### 要件
旧システムから移行したときの `products.legacy_code` が、もう使われていない。

### 手順

| 段階 | 作業 | 理由 |
|---|---|---|
| ① 使っていないことを確かめる | コード全体を `legacy_code` で検索。分析用 SQL、バッチ、外部連携も確認 | アプリ以外（BI ツールなど）が読んでいることがある |
| ② コードから消す | ORM のモデルから列を外してデプロイ | ORM が `SELECT *` 相当で全列を読む場合、列が消えるとエラーになるため、先にモデルから外す |
| ③ 退避する（任意） | `CREATE TABLE _archive_products_legacy_code AS SELECT id, legacy_code FROM products;` | 戻したくなったときの保険 |
| ④ 列を削除する | `ALTER TABLE products DROP COLUMN legacy_code;` | ②のデプロイが全台に行き渡った後で流す |

Prisma の場合、②の段階でモデルからフィールドを消すと、`migrate dev` が**すぐに `DROP COLUMN` を生成してしまいます**。②と④を別のデプロイにするには、②では生成されたマイグレーションを次のリリースまで寝かせるか、`--create-only` で作ったファイルを別のプルリクエストに分けます。

> [!note] PostgreSQL の DROP COLUMN は速い
> PostgreSQL の `DROP COLUMN` は、列を「見えなくする」だけでデータの物理的な削除はその後の更新や `VACUUM FULL` などで行われるため、一瞬で終わります。ただし短時間でも `ACCESS EXCLUSIVE` ロックは必要なので、長いクエリが走っているとそれを待つ間に後続のクエリが詰まることがあります（[[07_ゼロダウンタイムのスキーマ変更]]）。

## 8. 機能開発の中での全体の流れ

最後に、1 つの機能（例：レビュー機能）を作るときの、マイグレーションの流れをまとめます。

```
【開発者A のローカル】
1. ブランチを切る
2. schema.prisma を編集
3. npx prisma migrate dev --create-only --name create_reviews
4. migration.sql を読む・CHECK 制約などを追記
5. npx prisma migrate dev で適用し、アプリを動かして確認
6. コード・schema.prisma・migration.sql を同じコミットに入れて PR を出す

【CI】
7. 空の DB に全マイグレーションを適用 → テスト実行
   （ここで「最初から流すと失敗する」マイグレーションが見つかる）

【レビュー】
8. SQL を含めてレビュー（02 の記事のチェックリスト）→ マージ

【チームメンバー】
9. git pull → npx prisma migrate dev（未適用分だけ流れる）

【ステージング → 本番】
10. パイプラインで npx prisma migrate deploy → アプリをデプロイ
```

## よくある誤解・つまずき

- ❌ 「列名の変更は `RENAME` 1 文で終わる簡単な変更」
  ✅ SQL は 1 文でも、**動いているアプリ**から見ると列が突然消える変更です。止められないサービスでは「追加 → 移行 → 切り替え → 削除」の 4 段階が必要です。

- ❌ 「NOT NULL を付けるには、NULL を埋めてから `SET NOT NULL` するだけ」
  ✅ 埋めている間にもアプリが新しい NULL を書き込むことがあります。先に**アプリが NULL を書かないようにする**のが正しい順番です。

- ❌ 「使っていない列は、モデルから消すのと同時に DB からも消せばいい」
  ✅ デプロイ中は古いアプリがまだ動いています。モデルから消すデプロイが全台に行き渡ってから、別のデプロイで列を消します。

- ❌ 「データのコピーは 1 回流せば終わりなので、再実行のことは考えなくていい」
  ✅ 大量データのコピーは途中で失敗することがあります。`NOT EXISTS` や `WHERE ... IS NULL` を付けて、何度流しても結果が同じになるように書きます。

## まとめ

- **足す変更**は 1 回で、**変える・消す変更**は「追加 → 移行 → 切り替え → 削除」に分ける
- 各段階は別のデプロイにし、**どの時点でも動いているすべてのアプリが正しく動く**ようにする
- NOT NULL 化は「**新しい違反を止める → 既存を直す → 制約を付ける**」の順
- テーブル分割は**両方に書く期間**と**ずれを確認する期間**を置いてから古い列を消す
- 列の削除は**コードから消すデプロイの後で**行う。不安なら退避テーブルを作る
- 大きなテーブルでは型変更や NOT NULL 化が長時間ロックになるので、[[07_ゼロダウンタイムのスキーマ変更]] の手法を使う

## 確認クイズ

1. 止められないサービスで `orders.status` を `orders.state` に名前変更したいとき、`RENAME COLUMN` を 1 回流すだけだと何が起きますか？

> [!tip]- 答え
> マイグレーションが終わった瞬間から、まだ動いている古いバージョンのアプリが `status` 列を参照してエラーになります。新しい列を追加し、両方に書き込み、データを移し、読み取りを切り替え、最後に古い列を消す、という段階を踏みます。

2. `products.category_id` に NOT NULL を付けるため、まず `UPDATE` で NULL を埋めたのに、`SET NOT NULL` が「NULL 値が含まれている」と失敗しました。何が原因と考えられますか？

> [!tip]- 答え
> `UPDATE` の後にも、アプリが `category_id` を指定せずに商品を作成し、新しい NULL が入ったと考えられます。先にアプリ側で NULL を書かないようにしてから、既存データを埋める必要があります。

3. テーブル分割の②（コピー）で `NOT EXISTS` を付けているのはなぜですか？

> [!tip]- 答え
> コピーが途中で失敗したり、両方に書き込む期間中に再実行したりしても、同じユーザーの住所が重複して入らないようにするためです（冪等にするため）。
