## 詳しい要約

**テーマ：マルチテナントの DB 分離 3 方式と使い分け**

Slack のように複数の会社（テナント）が同じサーバー・API を使いながら、データと設定はテナントごとに分かれている状態がマルチテナント。DB の分け方には「共有 DB」「スキーマ分離」「DB 分離」の 3 つがあり、多くの SaaS は共有 DB で十分、規制やカスタマイズが必要ならスキーマ分離、政府・金融のような厳格な分離が必要なら DB 分離を選ぶ。

---

### マルチテナントとシングルテナント

- **テナント**＝サービスを使う各会社。同じエンドポイントを叩いても他社のデータは見えない。
- **シングルテナント**は会社ごとにアプリと DB を別に立てる方式（例: 顧客サーバーに入れる SAP、GitHub Enterprise）。

### ① 共有 DB

- 全テーブルに **テナント ID 列**を持たせ、A 社・B 社のデータが同じテーブルに入る。
- DB が 1 つなのでデプロイ・バックアップは 1 回で済む。
- 弱点: `WHERE` 句を書き忘れると他社の行が見える。バックアップも共有で、DB を失うと全員のデータが失われる。
- 対策として PostgreSQL の **行レベルセキュリティ（Row-Level Security）** で、テナント ID が一致する行だけ許可するポリシーを DB 側に任せられる。
- 大きくなったら**シャーディング**でテナント単位に水平分割（同じテナントの行は必ず同じシャードへ）。
- **ノイジーネイバー問題**: テナント A が CPU を独占すると B・C の応答が遅くなる。対策は ①クエリに 2 秒のタイムアウト ②テナントごとのレート制限 ③無料プランのテナントの処理を後回し ④テナントごとにコネクションプールを制限。

### ② スキーマ分離

- DB は 1 つだが、テナントごとに**スキーマ（名前空間）**を持つ。テーブル構造は同じ。
- テナント単位でバックアップできる。
- ただしマイグレーションを全スキーマに実行する必要があり、スキーマが増えるほど DB が遅くなる。

### ③ DB 分離

- API は共有、DB はテナントごとに別。データが完全に分かれ、ノイジーネイバーもない。
- 大口テナントの DB だけスケールアップできる。
- コストが高く、管理の手間も増える。

### まとめ

- 多くの SaaS は**共有 DB**（＋RLS・ノイジーネイバー対策）で十分。
- 規制・カスタマイズ要件があれば**スキーマ分離**、政府・金融並みの厳格な分離なら**DB 分離**。
