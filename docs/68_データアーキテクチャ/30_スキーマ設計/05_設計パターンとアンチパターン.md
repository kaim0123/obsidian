# 設計パターンとアンチパターン

[[MOC_データアーキテクチャ体系|📚 目次]] ｜ [[04_キーと制約の設計|← 前へ]] ｜ [[06_マルチテナント設計|次へ →]]

> [!abstract] この記事で分かること
> - 論理削除（`deleted_at`）の便利さと落とし穴、そして代替案
> - 履歴テーブル・監査ログで「過去の状態」と「誰が変えたか」を残す方法
> - ステータス管理の 3 つの方法と、状態遷移の履歴の持ち方
> - ツリー構造の 3 パターン（隣接リスト・経路列挙・閉包テーブル）の比較
> - 代表的なアンチパターン（EAV、ポリモーフィック関連、カンマ区切り列、何でも JSON、ID リクワイアドなど）と改善策
>
> **前提**：[[02_正規化]] と [[04_キーと制約の設計]] を読んでいると理解しやすいです。

## 1. ひとことで言うと

料理には「定番のレシピ」と「やりがちな失敗」があります。DB 設計も同じで、多くの現場が同じ問題（削除したデータを戻したい、カテゴリを入れ子にしたい、項目を自由に増やしたい）にぶつかり、うまくいった解き方が**設計パターン**、一見うまくいくのに後で必ず困る解き方が**アンチパターン**として知られています。アンチパターンの多くは、ビル・カーウィンの『SQL アンチパターン』（原題 *SQL Antipatterns*）に名前付きでまとめられています。

> [!info] 要点
> アンチパターンの共通点は「**DB が守ってくれるはずの制約（型・NOT NULL・外部キー・UNIQUE）を手放している**」ことです。その場は柔軟で楽でも、正しさの責任がすべてアプリに移ります。

## 2. 論理削除と、その代替

### 2.1 論理削除とは

**物理削除**は `DELETE` で行を本当に消すこと、**論理削除（Soft Delete）**は削除フラグや削除日時を立てて「消えたことにする」ことです。

```sql
ALTER TABLE products ADD COLUMN deleted_at TIMESTAMPTZ;   -- NULL なら有効

UPDATE products SET deleted_at = now() WHERE id = 3;      -- 「削除」
SELECT * FROM products WHERE deleted_at IS NULL;          -- 有効な商品だけ
```

### 2.2 功：なぜ使われるのか

- 誤操作から**復元**できる
- 過去の注文が参照している商品を消さずに済む（外部キーが壊れない）
- 「いつ消されたか」が残る

### 2.3 罪：何が困るのか

1. **すべてのクエリに `WHERE deleted_at IS NULL` が必要**。1 か所でも忘れると削除済みデータが画面に出ます。JOIN 先にも必要です
2. **UNIQUE 制約が壊れる**：退会した会員と同じメールアドレスで再登録できない。部分 UNIQUE インデックス（`... WHERE deleted_at IS NULL`、[[04_キーと制約の設計]]）で回避が必要
3. **外部キーが意味を失う**：削除済みの親を参照する子が「有効」のまま残る
4. **テーブルが肥大化**し、インデックスにも削除済みの行が残り続ける
5. **個人情報の削除要求**（GDPR・個人情報保護法）に応えられない。「消した」のに残っている

### 2.4 代替案

| 方法 | 内容 | 向いている場面 |
|---|---|---|
| **意味のあるステータス** | `deleted_at` ではなく `status = 'discontinued'`（販売終了）など業務の言葉で表す | 「削除」が実は業務上の状態変化（退会・販売終了・非公開）のとき |
| **アーカイブテーブル** | 削除時に `deleted_products` へ行を移して本体から `DELETE` | 復元はまれで、本体をきれいに保ちたいとき |
| **監査ログ** | 物理削除し、削除前の内容は監査ログ（3 章）に残す | 「誰がいつ消したか」の記録が目的のとき |
| **物理削除** | そのまま消す | 復元不要なデータ（一時トークン、カート） |

実務での指針は「**削除の理由を業務の言葉で説明できるならステータス、記録が目的なら監査ログ、どちらでもないなら物理削除**」です。どうしても `deleted_at` を使うなら、`active_products` のような**ビュー**を作ってアプリからはそちらを参照させると、条件の書き忘れを減らせます。

```sql
CREATE VIEW active_products AS
SELECT * FROM products WHERE deleted_at IS NULL;
```

## 3. 履歴テーブルと監査ログ

### 3.1 履歴テーブル：値の変遷を残す

「商品価格がいつ、いくらだったか」を残したいときは、**有効期間**を持つ履歴テーブルを作ります。

```sql
CREATE TABLE product_prices (
  product_id BIGINT      NOT NULL REFERENCES products(id),
  price      INTEGER     NOT NULL CHECK (price >= 0),
  valid_from TIMESTAMPTZ NOT NULL,
  valid_to   TIMESTAMPTZ,                       -- NULL なら現在も有効
  PRIMARY KEY (product_id, valid_from)
);

-- 2026-10-01 時点の価格
SELECT price FROM product_prices
WHERE product_id = 1
  AND valid_from <= '2026-10-01' AND (valid_to IS NULL OR valid_to > '2026-10-01');
```

期間の重なりを DB で禁止したい場合、PostgreSQL では `btree_gist` 拡張と**排他制約（EXCLUDE 制約）**が使えます。SQL:2011 の**システムバージョン管理テーブル**（SQL Server・MariaDB などが実装）は、この履歴を DB が自動で取ってくれる機能です。PostgreSQL には標準搭載されていません。

### 3.2 監査ログ：誰が何を変えたか

**監査ログ（Audit Log）**は、変更操作そのものを記録するテーブルです。トリガーで汎用的に作れます。

```sql
CREATE TABLE audit_logs (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  table_name TEXT        NOT NULL,
  operation  TEXT        NOT NULL,          -- INSERT / UPDATE / DELETE
  row_id     BIGINT,
  old_data   JSONB,
  new_data   JSONB,
  changed_by TEXT        NOT NULL DEFAULT current_user,
  changed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE FUNCTION write_audit_log() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO audit_logs (table_name, operation, row_id, old_data, new_data)
  VALUES (TG_TABLE_NAME, TG_OP,
          COALESCE(NEW.id, OLD.id),
          CASE WHEN TG_OP <> 'INSERT' THEN to_jsonb(OLD) END,
          CASE WHEN TG_OP <> 'DELETE' THEN to_jsonb(NEW) END);
  RETURN NULL;
END;
$$;

CREATE TRIGGER products_audit
AFTER INSERT OR UPDATE OR DELETE ON products
FOR EACH ROW EXECUTE FUNCTION write_audit_log();
```

監査ログは「調べるときに読む」ものなので、ここで JSONB を使うのは妥当です（スキーマが変わっても記録できる）。Web アプリでは DB ユーザーが全員同じなので、`current_user` ではなく「ログイン中のユーザー ID」を `SET LOCAL app.user_id = '42'` のようにセッション変数で渡し、`current_setting('app.user_id', true)` で記録する方法がよく使われます。

## 4. ステータス管理

注文の `status`（pending → paid → shipped / cancelled）のような**状態**の持ち方は 3 通りあります。

| 方法 | 例 | 長所 | 短所 |
|---|---|---|---|
| TEXT ＋ CHECK | `CHECK (status IN ('pending','paid','shipped','cancelled'))` | シンプル、読みやすい | 値の追加に DDL 変更が必要 |
| ENUM 型 | `CREATE TYPE order_status AS ENUM (...)` | 型として明確、4 バイト | PostgreSQL では値の削除・並べ替えが困難 |
| 参照テーブル | `order_statuses(code PK, label, sort_order)` ＋ 外部キー | 表示名などの属性を持てる、DDL なしで追加 | JOIN が増える |

状態が少なく固定ならテキスト＋CHECK、表示名・並び順・「この状態から遷移できる先」などの属性を持たせたいなら参照テーブルが向いています。

さらに「**いつ、どの状態になったか**」を残したいなら、`orders.status` を上書きするだけでなく、遷移の履歴テーブルを持ちます。

```sql
CREATE TABLE order_status_histories (
  id         BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id   BIGINT      NOT NULL REFERENCES orders(id),
  from_status TEXT,
  to_status  TEXT        NOT NULL,
  changed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

`orders.status` は「今の状態」をすぐ読むためのキャッシュ、履歴テーブルが事実の記録、という関係です（[[03_非正規化と実務での判断]]）。「paid でない注文は shipped にできない」のような遷移ルールは、`UPDATE orders SET status = 'shipped' WHERE id = 1 AND status = 'paid'` のように**前の状態を条件に含めて**更新し、更新件数 0 なら遷移不可とすると、同時実行でも安全です。

## 5. ツリー構造

カテゴリの入れ子（家電 > PC > ノート PC）のような階層を表す方法です。

```
家電(1)
├── PC(2)
│   ├── ノートPC(4)
│   └── デスクトップ(5)
└── カメラ(3)
```

### 5.1 隣接リスト（Adjacency List）

各行が**親の ID だけ**を持つ、最も素直な方法です。

```sql
ALTER TABLE categories ADD COLUMN parent_id BIGINT REFERENCES categories(id);

-- 「家電」配下をすべて取得（再帰 CTE）
WITH RECURSIVE tree AS (
  SELECT id, name, parent_id, 1 AS depth FROM categories WHERE id = 1
  UNION ALL
  SELECT c.id, c.name, c.parent_id, t.depth + 1
  FROM categories c JOIN tree t ON c.parent_id = t.id
)
SELECT * FROM tree;
```

再帰 CTE（`WITH RECURSIVE`）がない時代は「子孫の取得に深さの数だけ JOIN が必要」で、『SQL アンチパターン』では**ナイーブツリー**と呼ばれました。現在は PostgreSQL・MySQL 8.0 以降とも再帰 CTE が使えるので、**まず隣接リストで十分**なことが多いです。

### 5.2 経路列挙（Path Enumeration）

各行が**根からの経路**を文字列で持ちます。

```sql
ALTER TABLE categories ADD COLUMN path TEXT;   -- 例：ノートPC は '/1/2/4/'

SELECT * FROM categories WHERE path LIKE '/1/2/%';   -- PC 配下すべて
```

子孫検索が前方一致 1 回で済み、パンくずリストも経路から作れます。ただし外部キーで経路の正しさを保証できず、ノードを移動すると子孫全員の `path` を書き換える必要があります。PostgreSQL には経路を扱う専用型 **ltree** 拡張があります。

### 5.3 閉包テーブル（Closure Table）

「祖先と子孫のすべての組」を別テーブルに持ちます。

```sql
CREATE TABLE category_paths (
  ancestor_id   BIGINT  NOT NULL REFERENCES categories(id),
  descendant_id BIGINT  NOT NULL REFERENCES categories(id),
  depth         INTEGER NOT NULL,
  PRIMARY KEY (ancestor_id, descendant_id)
);
-- 自分自身との組（depth 0）も入れる。ノートPC(4) なら (4,4,0) (2,4,1) (1,4,2)

-- 子孫すべて：
SELECT c.* FROM categories c
JOIN category_paths p ON p.descendant_id = c.id
WHERE p.ancestor_id = 2;

-- 新しいノード X を親 P の下に追加：
-- INSERT INTO category_paths (ancestor_id, descendant_id, depth)
-- SELECT ancestor_id, X, depth + 1 FROM category_paths WHERE descendant_id = P
-- UNION ALL SELECT X, X, 0;
```

### 5.4 比較

| | 隣接リスト | 経路列挙 | 閉包テーブル |
|---|---|---|---|
| 子の取得 | ◎ | ○ | ◎ |
| 子孫すべて | ○（再帰 CTE） | ◎（前方一致） | ◎（JOIN 1 回） |
| ノードの移動 | ◎（1 行更新） | △（子孫全員更新） | △（組の削除・追加） |
| 参照整合性 | ◎（外部キー） | ✕ | ◎（外部キー） |
| 容量 | 最小 | 小 | 大（深さ×ノード数） |

## 6. アンチパターン集

### 6.1 EAV（Entity-Attribute-Value）

「商品ごとに項目が違うから、項目名と値を縦持ちにしよう」という設計です。

```
product_attributes
product_id | attr_name | attr_value
1          | color     | 赤
1          | weight_g  | 120
2          | color     | 青
2          | wieght_g  | abc        ← 綴り間違い・型違いも入ってしまう
```

**問題**：値がすべて TEXT になり型・CHECK・NOT NULL がかけられない。「重さ 100g 以上の赤い商品」を探すだけで自己 JOIN が属性の数だけ必要。属性名のタイポを防げない。
**改善**：共通の属性は普通の列にする。カテゴリごとに大きく違うなら**サブタイプ別テーブル**（`books`, `clothes` が `products.id` を主キー兼外部キーで参照）にする。本当に自由項目なら JSONB ＋ 必要に応じて CHECK（`attributes ? 'color'` など）にするほうが EAV よりましです。

### 6.2 ポリモーフィック関連（Polymorphic Associations）

コメントを商品にもレビューにも付けたいので、「どのテーブルの、どの ID か」を 2 列で持つ設計です。Rails などの ORM が標準機能として提供しているため広く使われています。

```sql
-- アンチパターン
CREATE TABLE comments (
  id               BIGSERIAL PRIMARY KEY,
  commentable_type TEXT   NOT NULL,   -- 'Product' or 'Review'
  commentable_id   BIGINT NOT NULL,   -- 外部キーを張れない！
  body             TEXT   NOT NULL
);
```

**問題**：`commentable_id` は参照先がテーブルによって変わるので外部キーを張れず、存在しない商品へのコメントや、親を消した後の孤児コメントを DB が防げません。
**改善**：参照先ごとに外部キー列を分け、どれか 1 つだけ埋まるよう CHECK する（**排他アーク**）か、参照先ごとに中間テーブル（`product_comments`, `review_comments`）を作ります。

```sql
CREATE TABLE comments (
  id         BIGSERIAL PRIMARY KEY,
  product_id BIGINT REFERENCES products(id),
  review_id  BIGINT REFERENCES reviews(id),
  body       TEXT NOT NULL,
  CHECK (num_nonnulls(product_id, review_id) = 1)   -- PostgreSQL の関数
);
```

### 6.3 カンマ区切り列（ジェイウォーク）

多対多の中間テーブルを作るのが面倒で、ID をカンマ区切りで 1 列に詰める設計です（**1NF 違反**、[[02_正規化]]）。

```
products.tag_ids = '3,7,12'
```

**問題**：「タグ 7 を持つ商品」の検索が `LIKE '%7%'`（17 や 70 も当たる）になりインデックスも効かない。存在しないタグ ID を防げない。タグの削除時に文字列を書き換える必要がある。
**改善**：中間テーブル `product_tags(product_id, tag_id)` を作る。電話番号を `tel1, tel2, tel3` と列で並べる「**マルチカラムアトリビュート**」も同じ問題の仲間で、別テーブルにします。

### 6.4 何でも JSON

「スキーマ変更が面倒だから、とりあえず `data JSONB` に全部入れる」設計です。

**問題**：型・NOT NULL・外部キー・UNIQUE がかけられず、壊れたデータが入っても気づけない。JSON の構造の知識がアプリのコードに散らばり、古い形式と新しい形式が混在する。統計情報が効きにくく、実行計画も悪くなりがち。
**改善**：**検索・JOIN・制約の対象になる項目は列にする**。JSONB は「まとめて読み書きし、中身で検索しない」データ（外部 API の応答、スナップショット、監査ログ）に限定します（[[03_非正規化と実務での判断]]）。

### 6.5 ID リクワイアド（中間テーブルの UNIQUE 忘れ）

「どのテーブルにも `id` 主キーを付ける」というルールを機械的に当てはめた結果、**本当に一意であるべき列の組に制約がない**状態です。

```sql
-- アンチパターン：id はあるが (product_id, tag_id) の重複を防げない
CREATE TABLE product_tags (
  id         BIGSERIAL PRIMARY KEY,
  product_id BIGINT NOT NULL REFERENCES products(id),
  tag_id     BIGINT NOT NULL REFERENCES tags(id)
);
-- → 同じ商品に同じタグが 2 行入り、集計が倍になる
```

**改善**：中間テーブルは `PRIMARY KEY (product_id, tag_id)` にするか、`id` を残すなら `UNIQUE (product_id, tag_id)` を必ず付けます。`id` は「行を指すための名札」にすぎず、業務上の一意性は守ってくれません（[[04_キーと制約の設計]]）。

### 6.6 その他の代表例

| 名前 | 内容 | 改善 |
|---|---|---|
| キーレスエントリ | 「遅くなる」「面倒」と外部キーを張らない | 外部キーを張る。性能問題はインデックスで解決 |
| ラウンディングエラー | 金額を `FLOAT` / `REAL` で持つ | `INTEGER`（最小単位）か `NUMERIC` を使う |
| サーティワンフレーバー | 頻繁に変わる選択肢を CHECK / ENUM に固定 | 参照テーブルにする |
| メタデータトリブル | `sales_2025`, `sales_2026` と年ごとにテーブルを作る | 1 テーブルにして、必要ならパーティショニング |

## よくある誤解・つまずき

- ❌ とりあえず全テーブルに `deleted_at` を付けておけば安全 → ✅ クエリの条件漏れ・UNIQUE の衝突・個人情報の削除不能という新しい問題を生みます。削除の意味を業務の言葉で考えます。
- ❌ ツリーは隣接リストだと遅いので最初から閉包テーブル → ✅ 再帰 CTE がある今は、隣接リストで足りることがほとんどです。深い階層を頻繁に検索するときに検討します。
- ❌ ORM が用意しているからポリモーフィック関連は問題ない → ✅ 便利さと引き換えに参照整合性を DB で守れなくなっています。
- ❌ JSONB があるから EAV や正規化は不要 → ✅ JSONB は制約・型の恩恵を手放す選択です。中身で検索・集計するなら列にします。
- ❌ `id` 主キーがあれば重複は起きない → ✅ 業務上の一意性（同じ商品に同じタグ）は UNIQUE 制約が必要です。

## まとめ

- 論理削除は**復元のしやすさと引き換えに、クエリ・UNIQUE・外部キー・個人情報削除で困る**。ステータス・アーカイブ・監査ログを先に検討する
- 値の変遷は**有効期間付きの履歴テーブル**、操作の記録は**監査ログ**で残す
- ステータスは CHECK / ENUM / 参照テーブルから選び、遷移の履歴は別テーブル、更新は前の状態を条件にする
- ツリーはまず**隣接リスト＋再帰 CTE**。検索が重ければ経路列挙・閉包テーブル
- アンチパターン（EAV・ポリモーフィック関連・カンマ区切り・何でも JSON・ID リクワイアド）の共通点は、**DB の制約を手放している**こと

## 確認クイズ

1. 論理削除している `users` で、退会した人と同じメールアドレスで新規登録したらエラーになりました。原因と対策は？
> [!tip]- 答え
> `email` の UNIQUE 制約が削除済みの行も対象にしているためです。`CREATE UNIQUE INDEX ... ON users (email) WHERE deleted_at IS NULL` の部分 UNIQUE インデックスに置き換えます。そもそも退会を `status` で表す、退会時に個人情報を消すなどの設計も検討します。

2. `posts.tag_names = 'sql,db,postgres'` という設計で「db タグの記事数」を正しく数えるのが難しいのはなぜですか？
> [!tip]- 答え
> `LIKE '%db%'` では `mydb` のような別タグにも一致し、正確な検索にはカンマ位置を考慮した文字列処理が必要になるからです。インデックスも効きません。`post_tags(post_id, tag_id)` の中間テーブルにすれば `WHERE tag_id = ?` で正確かつ高速に数えられます。

3. ポリモーフィック関連（`commentable_type`, `commentable_id`）で DB が防げない不整合を 1 つ挙げてください。
> [!tip]- 答え
> 存在しない ID（または削除された親）を指すコメントです。外部キーを張れないので、商品を削除してもコメントが孤児として残ります。排他アーク（参照先ごとの外部キー列＋`num_nonnulls` の CHECK）などで解決します。
