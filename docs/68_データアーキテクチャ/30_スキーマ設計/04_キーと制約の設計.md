## 1. ひとことで言うと

**キー**はデータの「住所」、**制約**はデータベースの「入館ゲート」です。住所の付け方（番地か、ランダムな番号か）を間違えると後で引っ越しが大変になり、ゲートを置かずに受付係（アプリ）の目視だけに頼ると、裏口（別のスクリプトや同時アクセス）から変なデータが入り込みます。

> [!info] 要点
> - 主キーは**変わらない・意味を持たない**値にする（代理キー）。業務上の一意性は UNIQUE 制約で守る
> - ID の方式は「インデックスの書き込み効率」と「外から推測されてよいか」で選ぶ
> - 制約は**最後の防衛線**。アプリのバリデーションは使い勝手のため、制約はデータの正しさのため

## 2. 自然キーと代理キー

- **主キー（Primary Key）**：行を一意に特定する列（の組）。NULL 不可・重複不可
- **自然キー（Natural Key）**：業務上の意味を持つ値をそのまま主キーにしたもの。例：メールアドレス、ISBN、社員番号
- **代理キー（Surrogate Key）**：業務と無関係に DB が採番する値。例：`id BIGSERIAL`、UUID

| 観点 | 自然キー | 代理キー |
|---|---|---|
| 値の変更 | 起こりうる（メールアドレス変更、社員番号の体系変更） | 起こらない |
| 変更時の影響 | 参照しているすべての外部キーを更新 | なし |
| 一意性の保証 | 業務ルールが変わると崩れる（ISBN の桁数変更、番号の再利用） | DB が保証 |
| 列の意味 | ある（JOIN 不要で読める） | ない（JOIN が必要） |
| サイズ | 長い文字列になりがち | 8 バイト（BIGINT）/ 16 バイト（UUID） |

実務では**代理キーを主キーにし、自然キーには UNIQUE 制約を付ける**のが定石です。共通スキーマの `users` もそうなっています。

```sql
CREATE TABLE users (
  id    BIGSERIAL PRIMARY KEY,      -- 代理キー：参照に使う
  email TEXT NOT NULL UNIQUE,       -- 自然キー：業務上の一意性
  ...
);
```

ここで大事なのは、**代理キーにしても UNIQUE 制約を忘れないこと**です。`id` だけでは同じメールアドレスの会員が 2 人登録できてしまいます。

一方、国コード（`JP`, `US`）や通貨コード（`JPY`）のように、**国際標準で決まっていてほぼ変わらない**値なら自然キーを主キーにするのも合理的です。

> [!tip] SERIAL より IDENTITY
> `BIGSERIAL` は PostgreSQL 独自の省略記法です。PostgreSQL 10 以降は SQL 標準の `id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` が推奨されています（手動で ID を入れる誤操作を防げる）。MySQL では `BIGINT AUTO_INCREMENT` を使います。

## 3. ID の方式：連番・UUIDv4・UUIDv7・ULID

### 3.1 4 つの方式

- **連番（Sequence / Auto Increment）**：1, 2, 3, … と DB が採番。8 バイト
- **UUIDv4**：128 ビットのうち 122 ビットがランダム。例 `5b30857f-0bfa-48b5-ac0b-5c64e28078d1`
- **UUIDv7**：先頭 48 ビットが**ミリ秒単位の Unix 時刻**、残りがランダム。RFC 9562（2024 年）で標準化。時刻順に並ぶ
- **ULID**：UUIDv7 と同じ発想（先頭 48 ビットが時刻、80 ビットがランダム）で、26 文字の Crockford Base32 文字列で表す（例 `01ARZ3NDEKTSV4RRFFQ69G5FAV`）。UUIDv7 より前から普及していた独自仕様

### 3.2 インデックスの局所性

主キーには B-Tree インデックスが作られます（[[02_B-TreeとLSM-Tree]]）。B-Tree は値の順に並んだ本棚のようなものです。

```
連番 / UUIDv7 / ULID（時刻順）          UUIDv4（ランダム）
[1..100][101..200][201..300][301..▮]   [0a..][3f..▮][7c..▮][b2..▮][e9..▮]
                               ↑ 新しい行は常に右端         ↑ 新しい行があちこちに入る
・書き込み先のページが少数で、メモリに    ・あらゆるページが書き込み対象になり、
  載り続ける                              キャッシュに載りきらない
・ページ分割が右端だけで済む              ・途中のページで分割が多発し、
                                          ページが半分空きのまま増える
```

UUIDv4 を主キーにした大きなテーブルでは、挿入のたびに別々のページを読み書きするため、**キャッシュ効率が落ち、インデックスが肥大化し、WAL（変更ログ、[[05_WALとクラッシュリカバリ]]）も増えます**。UUIDv7 や ULID はこの問題を、時刻を先頭に置くことで解決しています。MySQL（InnoDB）は主キーの順に行そのものを並べる（クラスタ化インデックス）ため、ランダムな主キーの影響が PostgreSQL 以上に大きくなります。

### 3.3 推測可能性

連番は外から推測できます。

- `/orders/1001` が見えれば `/orders/1002` を試される（認可チェックの漏れがあると他人の注文が見える＝IDOR 脆弱性）
- 1 か月後に `/users/52000` なら「この 1 か月で約 2,000 人増えた」と競合に読まれる

ただし**推測できないこと自体はセキュリティ対策ではありません**。認可チェック（その注文の持ち主か）は ID の方式に関係なく必須です。UUIDv7・ULID はランダム部分があるので推測は困難ですが、**作成時刻は ID から読み取れる**点に注意します。

### 3.4 比較表

| 方式 | サイズ | 時刻順 | 推測 | 分散生成（DB を介さず採番） | 備考 |
|---|---|---|---|---|---|
| 連番 | 8 B | ◎ | 容易 | ✕（DB が採番） | 最も小さく速い。件数が漏れる |
| UUIDv4 | 16 B | ✕ | 困難 | ◎ | 挿入が多い大テーブルの主キーには不向き |
| UUIDv7 | 16 B | ◎（ミリ秒） | 困難（時刻は分かる） | ◎ | PostgreSQL 18 で `uuidv7()` が標準搭載 |
| ULID | 16 B（文字列なら 26 文字） | ◎（ミリ秒） | 困難（時刻は分かる） | ◎ | DB の uuid 型に入れるなら変換が必要 |

```sql
-- PostgreSQL 18 以降
CREATE TABLE coupons (
  id   UUID PRIMARY KEY DEFAULT uuidv7(),
  code TEXT NOT NULL UNIQUE
);
-- 17 以前は gen_random_uuid()（v4）しかないので、v7 はアプリ側か拡張で生成する
```

**選び方の目安**：社内システムや単一 DB なら連番で十分です。ID を URL や API で外に出す、複数のサービスやオフラインのクライアントで ID を先に決めたい、将来 DB を分割する可能性がある、といった場合は UUIDv7（または ULID）を選びます。「内部は連番、外部公開用に別の UUID 列（UNIQUE）」という併用もよく使われます。

## 4. 複合キーと外部キー

### 4.1 複合キー

**複合キー（Composite Key）**は複数列の組で一意になる主キーです。`order_items` の `PRIMARY KEY (order_id, product_id)` は「同じ注文に同じ商品は 1 行」という業務ルールそのものを表しています。

- 向いている：中間テーブル（多対多の分解）。親のキーの組が自然に一意になる
- 向いていない：他のテーブルから参照される親テーブル。子が複合外部キーを持つ必要があり、ORM（[[17_ORMとは]]）でも扱いにくい

中間テーブルでも、明細を外部から参照したい（返品テーブルが特定の明細を指すなど）なら、`id` を足して複合キーは `UNIQUE (order_id, product_id)` に降格させます。

### 4.2 外部キーと ON DELETE

**外部キー（Foreign Key）**は「この列の値は、あのテーブルの主キー（または UNIQUE 列）に存在しなければならない」という制約です。これを**参照整合性（Referential Integrity）**と呼びます。親行が削除・更新されたときの動作を指定できます。

| 指定 | 親を削除すると | 使いどころ |
|---|---|---|
| `NO ACTION`（**デフォルト**） | 子が残っていればエラー（文の最後、または遅延時はコミット時に検査） | 迷ったらこれ |
| `RESTRICT` | 子が残っていれば即エラー（遅延不可） | 絶対に消させたくない参照 |
| `CASCADE` | 子も一緒に削除 | 親と運命を共にする子（注文 → 注文明細） |
| `SET NULL` | 子の外部キー列を NULL に | 親がなくなっても子は残す（カテゴリ削除 → 商品はカテゴリなし） |
| `SET DEFAULT` | 子の外部キー列をデフォルト値に | 「未分類」行に寄せたいときなど |

Shop に当てはめると次のようになります。

```sql
CREATE TABLE order_items (
  order_id   BIGINT NOT NULL REFERENCES orders(id)   ON DELETE CASCADE,  -- 注文を消したら明細も
  product_id BIGINT NOT NULL REFERENCES products(id) ON DELETE RESTRICT, -- 注文実績のある商品は消させない
  quantity   INTEGER NOT NULL CHECK (quantity > 0),
  unit_price INTEGER NOT NULL CHECK (unit_price >= 0),
  PRIMARY KEY (order_id, product_id)
);

ALTER TABLE products
  DROP CONSTRAINT products_category_id_fkey,
  ADD  CONSTRAINT products_category_id_fkey
       FOREIGN KEY (category_id) REFERENCES categories(id) ON DELETE SET NULL;

-- PostgreSQL は外部キー列にインデックスを自動作成しない。
-- 親の DELETE 時に子を探すのにも使われるので作っておく
CREATE INDEX order_items_product_id_idx ON order_items (product_id);
```

`CASCADE` は便利ですが、1 行の DELETE が連鎖して大量の行を消すことがあります。`users → orders → order_items` をすべて CASCADE にすると、会員 1 人の削除で売上記録が消えます。**会計・監査に関わるデータは CASCADE にしない**のが安全です（削除の代わりに退会ステータスにする方法は [[05_設計パターンとアンチパターン]]）。

> [!warning] MySQL との違い
> MySQL（InnoDB）では `NO ACTION` は `RESTRICT` と同じ扱いで、制約の遅延検査はできません。また外部キー列のインデックスは自動で作られます。

## 5. UNIQUE・CHECK・NOT NULL・DEFAULT

| 制約 | 意味 | Shop での例 |
|---|---|---|
| `NOT NULL` | 値の省略を許さない | `orders.user_id`（会員のいない注文はない） |
| `UNIQUE` | 重複を許さない | `users.email`、`reviews (user_id, product_id)` |
| `CHECK` | 条件式を満たす値だけ許す | `price >= 0`、`quantity > 0`、`rating BETWEEN 1 AND 5` |
| `DEFAULT` | 省略時に入れる値（制約というより既定値） | `status DEFAULT 'pending'`、`created_at DEFAULT now()` |

```sql
ALTER TABLE orders
  ADD CONSTRAINT orders_status_check
  CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled'));

-- 部分 UNIQUE：退会していない会員の中でだけメールアドレスを一意にする
-- （deleted_at 列を追加した場合の例。05 で詳しく扱う）
CREATE UNIQUE INDEX users_email_active_key ON users (email) WHERE deleted_at IS NULL;
```

細かいが重要な挙動です。

- **NOT NULL は「迷ったら付ける」**。NULL を許すと三値論理（[[05_NULLと三値論理]]）の考慮がすべてのクエリに必要になります。後から付けるのは既存データの修正が必要で大変ですが、外すのは簡単です
- **UNIQUE は NULL 同士を重複とみなさない**（デフォルト）。`NULL` が何行あっても通ります。NULL も 1 つに限りたいなら PostgreSQL 15 以降の `UNIQUE NULLS NOT DISTINCT` を使います
- **CHECK は同じ行の値しか見られない**。「在庫数を超えて注文できない」のような別テーブルを見るルールは CHECK では書けず、トランザクション内のロジックで守ります（[[04_楽観ロック・悲観ロックとデッドロック]]）
- MySQL は **8.0.16 未満では CHECK を構文として受け付けるだけで無視**していました。古い MySQL では効いていないことに注意します

## 6. 制約がアプリのバリデーションとは別に必要な理由

「アプリで入力チェックしているから DB の制約は要らない」は危険な考えです。

### 6.1 同時実行で必ずすり抜ける

```
時刻  リクエストA                          リクエストB
t1    SELECT ... WHERE email='a@ex.com'
      → 0件（重複なし！）
t2                                         SELECT ... WHERE email='a@ex.com'
                                           → 0件（重複なし！）
t3    INSERT ... 'a@ex.com'  成功
t4                                         INSERT ... 'a@ex.com'  成功 ← 重複登録
```

「確認してから書く」は、確認と書き込みの間に他の処理が割り込めます。UNIQUE 制約があれば t4 の INSERT が DB によって**エラーで弾かれる**ので、アプリはそのエラーを捕まえて「既に登録されています」と返せばよいのです。

### 6.2 書き込み経路はアプリだけではない

管理画面、バッチ、データ移行スクリプト、別のマイクロサービス、手作業の SQL、そして将来書き直されるアプリ自身。データは**アプリより長生き**します。DB の制約は、どの経路から来たデータにも同じルールを強制できる唯一の場所です。

### 6.3 役割分担

- **アプリのバリデーション**：使い勝手のため。分かりやすいエラーメッセージ、入力中のチェック、複雑な業務ルール
- **DB の制約**：正しさの最後の砦。シンプルで絶対に破られてはいけないルール（一意性、必須、範囲、参照整合性）

両方に同じルールを書くのは重複ではなく**多層防御**です。

## 7. 命名規則

制約やインデックスに名前を付けておくと、エラーメッセージやマイグレーションで何の制約か一目で分かります。PostgreSQL は名前を省略すると次の形式で自動命名するので、手で付けるときもこれに合わせると一貫します。

| 種類 | 形式 | 例 |
|---|---|---|
| 主キー | `<表>_pkey` | `orders_pkey` |
| 外部キー | `<表>_<列>_fkey` | `orders_user_id_fkey` |
| UNIQUE | `<表>_<列>_key` | `users_email_key` |
| CHECK | `<表>_<列>_check` | `products_price_check` |
| インデックス | `<表>_<列>_idx` | `order_items_product_id_idx` |

テーブル・列名の慣習：

- **snake_case**（小文字＋アンダースコア）。PostgreSQL は引用符なしの識別子を小文字に変換するので、`CamelCase` を使うと毎回 `"UserId"` と引用符が必要になります
- テーブル名は**複数形**（`users`, `orders`）か単数形かを**どちらかに統一**する（Rails などのフレームワークは複数形）
- 外部キー列は `<参照先の単数形>_id`（`user_id`, `product_id`）
- 日時は `_at`（`created_at`, `deleted_at`）、日付は `_on` または `_date`、真偽値は `is_` / `has_`
- `user`, `order`, `group` などの**予約語**はテーブル・列名に避ける（使うと引用符が必要）

## よくある誤解・つまずき

- ❌ 代理キーを主キーにすれば一意性は大丈夫 → ✅ `id` が一意なだけで、業務上の重複（同じメール）は防げません。自然キーに UNIQUE 制約が必要です。
- ❌ UUID なら推測されないので認可チェックは不要 → ✅ ID が漏れる経路（ログ、URL 共有）はいくらでもあります。認可チェックは必須です。
- ❌ 外部キーを張ると自動でインデックスが付く → ✅ PostgreSQL では付きません（MySQL は付く）。親の削除や JOIN が遅くなるので自分で作ります。
- ❌ アプリでチェックしているので制約は不要 → ✅ 同時実行と別経路の書き込みで必ずすり抜けます。
- ❌ UNIQUE 列なら NULL も 1 行まで → ✅ デフォルトでは NULL は何行でも入ります（`NULLS NOT DISTINCT` で変更可）。

## まとめ

- 主キーは**代理キー**、業務上の一意性は**UNIQUE 制約**で守る
- ID は **連番（小さく速い・推測される）/ UUIDv4（ランダムで挿入に弱い）/ UUIDv7・ULID（時刻順でランダム）** から要件で選ぶ
- 外部キーのデフォルトは `NO ACTION`。`CASCADE` は親と運命を共にする子だけに使い、外部キー列にはインデックスを張る
- `NOT NULL` は迷ったら付ける。`CHECK` は同じ行の範囲チェック、`UNIQUE` は NULL の扱いに注意
- 制約は**同時実行と別経路**からデータを守る最後の砦で、アプリのバリデーションとは役割が違う

## 確認クイズ

1. 主キーにメールアドレスを使う設計の問題点を 2 つ挙げてください。
> [!tip]- 答え
> ①メールアドレスは変更されうるため、参照している全テーブルの外部キーを更新する必要がある。②文字列で長く、インデックスや外部キーのサイズが大きくなる。代理キー `id` を主キーにし、email には UNIQUE 制約を付けます。

2. 書き込みが多い 10 億行のログテーブルで、主キーを UUIDv4 から UUIDv7 に変えると何が良くなりますか？
> [!tip]- 答え
> 新しい行の主キーが常に B-Tree の右端に追加されるようになり、書き込み先のページがメモリに載り続け、途中のページ分割やインデックスの肥大化、WAL の増加が抑えられます。

3. `categories` を削除したとき、商品はカテゴリ未設定として残したい。外部キーをどう定義しますか？
> [!tip]- 答え
> `category_id BIGINT REFERENCES categories(id) ON DELETE SET NULL` とします（`category_id` は NULL を許す必要があります）。
