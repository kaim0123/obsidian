## 1. テーブル設計が悪いとプログラムの変更が大変になる

データの整理に失敗している DB は、次のような症状を出しやすいです。

| 症状 | 例 |
|------|-----|
| **用途がわかりにくいカラム** | 省略名、NULL だらけ、マジックナンバー、自由項目／拡張カラム |
| **いろいろな用途に使う巨大なテーブル** | 似たカラムの使い分けが不明、NULL が多い |
| **テーブルの関係がわかりにくい** | 外部キー制約なし、キー列名の一貫性なし |

このような DB は、アプリ側に「この NULL は何を意味するか」「この数字の 2 は何か」という解釈ロジックを押し込み、変更コストを上げます。

---

## 2. データベース設計をすっきりさせる

大切なのは、DB に用意されている **基本的な仕組みを丁寧に使う** ことです（詳細は [[04_キーと制約の設計]]・[[02_正規化]]）。

| 基本 | 内容 |
|------|------|
| 名前を省略しない | テーブル名・カラム名は業務で読める語に |
| 適切なデータ型 | 桁・型を現実に合わせる。何でも TEXT / VARCHAR(2000) にしない |
| 制約を使う | **NOT NULL**・**UNIQUE（一意性）**・**外部キー** |

### 2.1 NOT NULL 制約が導くテーブル設計

事実の記録に NULL（UNKNOWN）は合いません。NOT NULL を徹底しようとすると、**記録タイミングの違う項目を無理に同じ行に詰められなくなり**、テーブル分割＝正規化が進みます。

### 2.2 一意性制約で重複を防ぐ

重複は更新異常の温床です。業務上の一意キーには UNIQUE を付けます（代理キー主キー＋自然キー UNIQUE が定石）。

### 2.3 外部キー制約で関係を明確にする

小さく割ったテーブル同士の関係を、外部キーで明示します。JOIN で正しいデータを再現する土台になります。

## 3. コトに注目するデータベース設計

業務アプリで DB が重要なのは、**コトを正しく記録し参照する**ためです。

- 現実に起きたコトの記録  
- 将来起きるコトの記録（予定）  

ドメイン側のヒト／モノ／コトは [[04_ヒト・モノ・コトと関心事パターン]]。DB ではコトの行に、ヒト・モノへの参照を正確に載せます。

### 3.1 ヒトやモノとの関係を正確に記録する3つの工夫

| 工夫 | 理由 |
|------|------|
| **記録のタイミングが異なるデータはテーブルを分ける** | 同じ行に詰め込むと NULL や「未定」が生まれる |
| **記録の変更を禁止する** | 事実の上書きは履歴を消すことと同じ。取り消し・訂正は別のコトとして INSERT（いわゆる赤黒：元／取消／新） |
| **カラムの追加はテーブルの追加** | 既存テーブルに列を足すと過去行が NULL か偽データになる。新テーブルから既存を外部キーで指す |

---

## 4. 参照をわかりやすくする工夫

### 4.1 コト記録に注力した設計の問題

正規化されたコト中心スキーマは、参照のたびに多数 JOIN や集計が必要になり、ロジックと性能が辛くなりがちです。

### 4.2 状態の参照

コトだけあれば **現在状態は導出可能** です。ただし毎回フル再計算は重いことが多いので、検索インデックスに似た発想で **状態用の二次テーブル**（残高など）を用意します。

- 原本はコトの記録  
- 状態テーブルはコトからいつでも再構築できる **派生データ**  

### 4.3 UPDATE 文は使わない（状態更新の流儀）

状態行の「上書き UPDATE」は、記録の同時性を壊し不整合を混ぜやすい、という立場です。状態の更新は **DELETE + INSERT** の対で置き換える、冪等にもしやすい、という方針が示されます（要件により緩和はありうるが、原則として覚えておく）。

コト自体の訂正も、UPDATE ではなく **取消レコード＋新レコードの INSERT** が基本です。

### 4.4 残高更新は同時でなくてもよい

コトの記録（一次）と残高更新（二次）を、厳密に同一トランザクションで心中させる必要はない、という考え方です。二次が失敗したから一次を取り消すのは本末転倒になりやすい。遅れが許せるなら **非同期メッセージ** で状態更新を切り離せます。

### 4.5 残高更新は1ヵ所でなくてもよい／派生情報の転記

同じコトの発生を、顧客別残高・部門別売上など **目的別の派生ストア** に分配してよい、という発想です（イベント配布／イベントソーシング寄りの読み）。参照はシンプルになり拡張しやすい一方、即時整合や多重派生の整合には仕組みが要ります。

### 4.6 コトの記録から状態を動的に導出する

状態テーブルを持たず、都度導出する方法もあります。テストで過去時点を再現したり、将来のコトを仮置きしてシミュレーションしたりしやすい、という利点があります。性能とトレードオフです（[[03_非正規化と実務での判断]] の集計テーブル・マテビューとも接続）。

## 5. オブジェクト設計との境界

| | オブジェクト | テーブル |
|--|--------------|----------|
| 目的 | データ＋**ロジック**の整理 | **データの**整理・事実の記録 |
| 変更のリズム | 頻繁 | ゆるやか |

似て見えても自動 1:1 マッピングはうまくいきません。役割分担の詳細は [[08_オブジェクトとテーブルの設計]]、リポジトリ経由の分離は [[04_集約とリポジトリ]]・[[07_アプリケーション機能を組み立てる]]。オブジェクト種類の整理は [[06_オブジェクトの種類の整理]]。

## まとめ

- 悪い DB は省略名・巨大テーブル・関係不明でアプリを縛る  
- NOT NULL・UNIQUE・FK を丁寧に使うと設計がすっきりし正規化が進む  
- 業務 DB の中核は **コトの記録**。タイミング分離・変更禁止（赤黒）・列追加＝表追加  
- 状態は派生。UPDATE 乱用を避け、同時性・配置を緩められる  
- オブジェクトはロジック、テーブルは事実。明示マッピングで独立して育てる
