# インデックスが効かないパターン

[[MOC_データアーキテクチャ体系|📚 目次]] ｜ [[03_インデックスの基本と設計|← 前へ]] ｜ [[05_実行計画の読み方|次へ →]]

> [!abstract] この記事で分かること
> - インデックスが効かない原因は「並び順を使えない書き方」と「使わない方が速いという DB の判断」の 2 種類あること
> - 列への関数・演算、暗黙の型変換、中間一致の LIKE、OR、否定条件、複合インデックスの先頭列なし の直し方
> - 選択性が低い・統計情報が古い・テーブルが小さいときに DB がインデックスを使わない理由
> - SARGable（インデックスで探せる形の条件）という考え方
>
> **前提**：[[03_インデックスの基本と設計]] を読んでいると理解しやすいです。

## 1. ひとことで言うと

インデックスは「五十音順の電話帳」です。「中村さん」は引けますが、「名前が『村』で終わる人」や「名前の画数が 10 の人」は、電話帳があっても 1 ページ目から全部見るしかありません。**並び順を使えない問い方**をすると、インデックスは役に立ちません。

もう 1 つは、**DB が自分の判断でインデックスを使わない**ケースです。「日本人の電話番号を全部書き出して」と頼まれたら、索引を 1 件ずつ引くより電話帳を頭から読んだ方が速いですよね。

| 種類 | 原因 | 直し方 |
|---|---|---|
| A. 書き方の問題 | 列を加工している、型が合わない、中間一致、OR、否定、先頭列なし | **クエリを書き換える** / 合うインデックスを作る |
| B. DB の判断 | 選択性が低い、統計が古い、テーブルが小さい | 多くは正しい判断。統計の更新や設計の見直し |

キーワードは **SARGable（Search ARGument ABLE）**：「インデックスで探せる形の検索条件」です。基本は「**列を裸のまま、比較演算子の片側に置く**」こと。

確認はすべて `EXPLAIN` で行います（読み方は [[05_実行計画の読み方]]）。以下、`Seq Scan` はフルスキャン、`Index Scan` などはインデックスが使われたことを表します。

## 2. 書き方の問題（1）：列の加工と型

### 2.1 列に関数・演算をかける

インデックスに並んでいるのは**加工前の値**です。加工後の値の順には並んでいません。

```sql
-- ❌ 悪い例：ordered_at に関数をかけている（idx: orders(ordered_at)）
SELECT * FROM orders
WHERE date_trunc('day', ordered_at) = '2026-10-01';

SELECT * FROM orders
WHERE EXTRACT(YEAR FROM ordered_at) = 2026;

-- ✅ 良い例：列は裸のまま、範囲条件にする
SELECT * FROM orders
WHERE ordered_at >= '2026-10-01' AND ordered_at < '2026-10-02';

SELECT * FROM orders
WHERE ordered_at >= '2026-01-01' AND ordered_at < '2027-01-01';
```

演算も同じです。

```sql
-- ❌ 悪い例：列の側で計算している（idx: products(price)）
SELECT * FROM products WHERE price * 1.1 > 1000;

-- ✅ 良い例：定数の側に計算を移す
SELECT * FROM products WHERE price > 1000 / 1.1;
```

どうしても加工した値で検索したい場合は、**式インデックス**を作ります。

```sql
-- 大文字小文字を区別せずにメールアドレスを検索したい
-- ❌ email のインデックスは使われない
SELECT * FROM users WHERE lower(email) = 'sato@example.com';

-- ✅ 同じ式でインデックスを作る
CREATE INDEX idx_users_lower_email ON users (lower(email));
```

> [!note] `BETWEEN '2026-10-01' AND '2026-10-31'` に注意
> timestamptz 列に日付だけの BETWEEN を使うと、末尾が「10/31 0:00 ちょうど」までになり、31 日の大半が漏れます。`>= 開始 AND < 翌日` の半開区間が安全です。

### 2.2 暗黙の型変換

列と比較する値の型が違うと、DB が型をそろえるために**列の側を変換**することがあり、関数をかけたのと同じことが起きます。

**MySQL の典型例**：文字列型の列を数値と比較する

```sql
-- MySQL：phone が VARCHAR、idx: users(phone) とする
-- ❌ 悪い例：数値と比較 → 全行の phone を数値に変換して比較（インデックスが効かない）
SELECT * FROM users WHERE phone = 0312345678;

-- ✅ 良い例：文字列として比較
SELECT * FROM users WHERE phone = '0312345678';
```

**PostgreSQL の例**：BIGINT の列を NUMERIC（小数）と比較する

```sql
-- ❌ 悪い例：1.0 は numeric 型 → id が numeric に変換され、主キーが使われない
EXPLAIN SELECT * FROM orders WHERE id = 1.0;
--  Seq Scan on orders  Filter: ((id)::numeric = 1.0)

-- ✅ 良い例：型を合わせる
EXPLAIN SELECT * FROM orders WHERE id = 1;
--  Index Scan using orders_pkey on orders
```

PostgreSQL は型に厳しく、`text = integer` のような比較はそもそもエラーになるので、MySQL ほど事故は多くありません。ただし、アプリや ORM がパラメータを想定外の型で送っている場合に起こり得ます。実行計画の `Filter` に `::numeric` や `::text` のような**キャストが列側に付いていたら要注意**です。

> [!warning] MySQL：文字コード・照合順序の不一致
> `utf8mb3` のテーブルと `utf8mb4` のテーブルを文字列列で JOIN すると、片側の変換が必要になり、結合キーのインデックスが使われないことがあります。MySQL 8.0 でデフォルトが utf8mb4 になったため、移行途中のシステムで起きがちです。

## 3. 書き方の問題（2）：LIKE・OR・否定

### 3.1 前方一致以外の LIKE

```sql
-- ✅ 前方一致：先頭が決まっているので、並び順で範囲を絞れる
SELECT * FROM products WHERE name LIKE 'ノート%';

-- ❌ 後方一致・中間一致：先頭が何でもあり得るので、全部見るしかない
SELECT * FROM products WHERE name LIKE '%ノート';
SELECT * FROM products WHERE name LIKE '%ノート%';
```

> [!warning] PostgreSQL の前方一致の落とし穴
> データベースの照合順序（collation）が `C` 以外（例：`ja_JP.UTF-8`、`en_US.UTF-8`）の場合、普通の B-Tree インデックスは `LIKE 'abc%'` に**使われません**。`text_pattern_ops` を指定したインデックスが必要です。
> ```sql
> CREATE INDEX idx_products_name_pattern ON products (name text_pattern_ops);
> ```

中間一致を速くしたいときの選択肢：

```sql
-- ✅ pg_trgm 拡張 + GIN インデックス（3 文字ずつの断片で索引を作る）
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_products_name_trgm ON products USING gin (name gin_trgm_ops);

SELECT * FROM products WHERE name LIKE '%ノート%';  -- インデックスが使われ得る
```

- pg_trgm は 3 文字単位なので、1〜2 文字の検索語には効きにくいです。日本語の短い語では 2 文字単位の `pg_bigm` 拡張や、本格的には全文検索エンジン（Elasticsearch / OpenSearch など）を検討します。
- 後方一致だけなら、`reverse(name)` の式インデックスを作り、`reverse(name) LIKE reverse('ノート') || '%'` と前方一致に変換する手もあります。

### 3.2 OR

```sql
-- idx: orders(user_id) はあるが、status にはインデックスがない
-- ❌ 悪い例：片方の条件にインデックスがない OR → 結局全行を見る
SELECT * FROM orders WHERE user_id = 42 OR status = 'cancelled';
```

OR は「どちらかを満たす行」なので、片方でもインデックスがない条件があると、その条件のために全行を見る必要があります。

```sql
-- ✅ 良い例 1：両方の列にインデックスがあれば、PostgreSQL は
--    BitmapOr で 2 つのインデックスの結果を合体できる
CREATE INDEX idx_orders_status ON orders (status);
--  → Bitmap Heap Scan / BitmapOr / Bitmap Index Scan × 2

-- ✅ 良い例 2：UNION に分けて、それぞれインデックスを使わせる
SELECT * FROM orders WHERE user_id = 42
UNION
SELECT * FROM orders WHERE status = 'cancelled';

-- ✅ 同じ列の OR は IN に（読みやすさ。どちらでもインデックスは使われる）
SELECT * FROM orders WHERE status IN ('pending', 'paid');
```

### 3.3 否定条件（`<>`, `NOT IN`, `NOT LIKE`, `IS NOT NULL`）

否定条件は「それ以外の全部」を意味し、たいてい**テーブルの大部分の行**に当てはまります。並び順で狭い範囲に絞れないため、インデックスはほぼ役に立ちません。

```sql
-- ❌ 悪い例：'delivered' 以外 = 大半の行かもしれないし、範囲を 1 つに絞れない
SELECT * FROM orders WHERE status <> 'delivered';

-- ✅ 良い例 1：取りうる値が決まっているなら、肯定形で列挙する
SELECT * FROM orders WHERE status IN ('pending', 'paid', 'shipped');

-- ✅ 良い例 2：「未完了の注文」を頻繁に探すなら、部分インデックス
CREATE INDEX idx_orders_not_delivered ON orders (ordered_at)
WHERE status <> 'delivered';
-- クエリの WHERE がこの条件を含んでいれば使われる
SELECT * FROM orders WHERE status <> 'delivered' ORDER BY ordered_at LIMIT 50;
```

> [!note] `NOT IN` と NULL
> `NOT IN (サブクエリ)` はサブクエリに NULL が 1 つでもあると結果が 0 行になる落とし穴もあります。`NOT EXISTS` が安全です（[[05_NULLと三値論理]]）。

## 4. 書き方の問題（3）：複合インデックスの先頭列なし

```sql
-- idx: orders(user_id, ordered_at)

-- ❌ 悪い例：先頭列 user_id の条件がない
SELECT * FROM orders WHERE ordered_at >= '2026-10-01';

-- ✅ 良い例 1：先頭列の条件を含める（業務上可能なら）
SELECT * FROM orders WHERE user_id = 42 AND ordered_at >= '2026-10-01';

-- ✅ 良い例 2：その検索が頻繁なら、ordered_at を先頭にしたインデックスを別に作る
CREATE INDEX idx_orders_ordered_at ON orders (ordered_at);
```

姓 → 名の順に並んだ電話帳で、名だけでは探せないのと同じです（左端一致のルール、[[03_インデックスの基本と設計]]）。

> [!info] スキップスキャン（Skip Scan）
> PostgreSQL 18 と MySQL 8.0.13 以降には、先頭列の値ごとに「先頭列 = 値 AND 2 列目の条件」を繰り返し探す**スキップスキャン**があります。ただし有効なのは**先頭列の種類が少ない**場合だけです（例：先頭列が `status` で数種類）。先頭列が `user_id` のように種類が多いと使われません。「先頭列なしでも効くことがある」程度に考え、設計の前提にはしないのが安全です。

## 5. DB の判断（1）：選択性が低い

**選択性（Selectivity）**：条件に当てはまる行の割合。割合が小さいほど「選択性が高い（よく絞れる）」と言います。

```sql
-- orders 1,000 万行。status の内訳：delivered 85%, shipped 10%, paid 4%, pending 1%
CREATE INDEX idx_orders_status ON orders (status);

EXPLAIN SELECT * FROM orders WHERE status = 'delivered';
--  Seq Scan on orders   ← 850 万行を返すならフルスキャンの方が速い（正しい判断）

EXPLAIN SELECT * FROM orders WHERE status = 'pending';
--  Bitmap Heap Scan / Index Scan   ← 10 万行ならインデックスが有利
```

インデックス経由だと、1 行ごとにテーブルのページを**ランダムに**読みに行きます。返す行が多いと、テーブルの全ページを**シーケンシャルに**読むフルスキャンの方が安くなります（[[01_データはディスクにどう保存されるか]]）。分岐点はデータやハードウェアによりますが、**テーブルの数 % 〜 1 割を超える行を返す条件**ではフルスキャンが選ばれやすいと言われます。

**直し方**：これは多くの場合「正しい判断」です。

- 少数派の値だけをよく検索するなら、部分インデックス `WHERE status = 'pending'`
- 他の列と組み合わせて絞り込める複合インデックス（`(user_id, status)` など）
- そもそも大量の行を返すクエリなら、集計テーブルや分析基盤を検討（[[01_OLTPとOLAP]]）

## 6. DB の判断（2）：統計情報が古い・テーブルが小さい

### 6.1 統計情報が古い

オプティマイザは、**統計情報**（テーブルの行数、列の値の分布、よく出る値など）をもとに「この条件で何行返るか」を見積もり、プランを選びます。統計が実態とずれていると、見積もりを誤り、間違ったプランを選びます。

ずれが起きやすい場面：

- 大量の INSERT / DELETE（バッチ取り込み、データ移行）の直後
- 新しく作ったテーブルにデータを入れた直後
- 時間とともに分布が変わる列（「最新の日付」の行は、前回の統計にはまだ存在しない）

```sql
-- ✅ 統計を更新する
ANALYZE orders;

-- 最後に統計が更新された時刻を確認
SELECT relname, last_analyze, last_autoanalyze, n_mod_since_analyze
FROM pg_stat_user_tables
WHERE relname = 'orders';
```

PostgreSQL では autovacuum が自動で ANALYZE も実行しますが、大量投入の直後は追いつかないことがあるため、**バッチ処理の最後に `ANALYZE` を入れる**のが定石です。MySQL では `ANALYZE TABLE orders;` です。

> [!note] 「コードは変えていないのに、ある日突然遅くなった」
> データ量や分布が変わってプランが切り替わるのが典型的な原因です。PostgreSQL のプリペアドステートメントは、同じ形の SQL を 5 回実行した後、条件の値によらない**汎用プラン（generic plan）**に切り替わることがあり、偏った値でだけ遅くなる、という現象も起きます（`plan_cache_mode` で制御可能）。

### 6.2 テーブルが小さい

```sql
-- categories は 20 行（1 ページに収まる）
EXPLAIN SELECT * FROM categories WHERE id = 5;
--  Seq Scan on categories   ← 主キーのインデックスがあっても Seq Scan
```

1 ページしかないテーブルなら、インデックスのページを読んでからテーブルのページを読むより、テーブルの 1 ページを直接読んだ方が速いからです。**問題ではありません**。

> [!warning] 開発環境で EXPLAIN しても本番の答えは出ない
> 開発 DB に 100 行しかなければ、どのクエリも Seq Scan になり、逆にインデックスが不要な問題も見えません。実行計画の確認は、**本番と同程度のデータ量・分布**の環境（ステージングや本番の統計を反映した環境）で行いましょう。

## 7. 見抜くためのチェックリスト

書く前のレビューで拾えるもの（パターン A）：

- [ ] WHERE / JOIN の列に関数・演算・キャストがかかっていないか（列は裸か）
- [ ] 比較する値の型は列の型と一致しているか
- [ ] `LIKE` は前方一致か（PostgreSQL なら `text_pattern_ops` や collation も確認）
- [ ] インデックスのない列を含む `OR` になっていないか
- [ ] 否定条件で大量の行を取っていないか
- [ ] 複合インデックスの先頭列を条件に含めているか

本番で確かめるもの（パターン B）：

- [ ] `EXPLAIN ANALYZE` で見積もり行数と実際の行数が大きくずれていないか（[[05_実行計画の読み方]]）
- [ ] `pg_stat_user_tables` の `last_autoanalyze` が古すぎないか
- [ ] `pg_stat_user_indexes` で `idx_scan = 0` のインデックスがないか
- [ ] スロークエリログ / `pg_stat_statements` に載っていないか

ORM を使っている場合は、**実際に発行された SQL** をログに出してチェックしましょう（[[17_ORMとは]]）。

## よくある誤解・つまずき

- ❌「インデックスを張ったのに Seq Scan になっている。DB がおかしい」
  ✅ 返す行が多い・テーブルが小さいなら、Seq Scan の方が速い正しい判断です。見積もり行数が実態とずれている場合だけが問題です。
- ❌「`LIKE '%keyword%'` も B-Tree インデックスで速くなる」
  ✅ 中間一致・後方一致は B-Tree では探せません。pg_trgm + GIN や全文検索を使います。
- ❌「WHERE 句の条件の書き順を変えればインデックスが効く」
  ✅ `a = 1 AND b = 2` と `b = 2 AND a = 1` は同じです。重要なのはインデックスの列順と、列を加工していないかです。
- ❌「開発環境の EXPLAIN でインデックスが使われていたから本番も大丈夫」
  ✅ データ量と分布が違えばプランも変わります。本番相当のデータで確認します。
- ❌「`EXTRACT(YEAR FROM ordered_at) = 2026` も `ordered_at` のインデックスで探せる」
  ✅ 列に関数をかけると探せません。`ordered_at >= '2026-01-01' AND ordered_at < '2027-01-01'` に書き換えます。

## まとめ

- インデックスが効かない原因は「並び順を使えない書き方」と「DB が使わない方が速いと判断」の 2 種類。
- 書き方の問題は、列を裸のまま比較する（SARGable）、型を合わせる、前方一致にする、OR / 否定を避ける、複合インデックスの先頭列を使う、で直す。
- どうしても加工した値・中間一致で検索するなら、式インデックスや pg_trgm + GIN を使う。
- 選択性が低い・テーブルが小さいときの Seq Scan は正しい判断であることが多い。
- 統計が古いと見積もりを誤る。大量投入後は `ANALYZE`。確認は本番相当のデータで行う。

## 確認クイズ

1. `WHERE date(ordered_at) = '2026-10-01'` を、`ordered_at` のインデックスが使える形に書き換えてください。
> [!tip]- 答え
> `WHERE ordered_at >= '2026-10-01' AND ordered_at < '2026-10-02'` です。列に関数をかけず、範囲条件にします。（なお `date()` は MySQL の関数で、PostgreSQL では `ordered_at::date` や `date_trunc` が相当します。どちらも同じ理由で効きません。）

2. `status` 列にインデックスがあるのに、`WHERE status = 'delivered'` が Seq Scan になりました。考えられる理由と、対処が必要かどうかを答えてください。
> [!tip]- 答え
> `delivered` が全体の大部分を占めるなら、インデックス経由で大量のランダム I/O をするよりフルスキャンの方が速いという、オプティマイザの正しい判断です。対処は不要なことが多いです。ただし `EXPLAIN ANALYZE` で見積もり行数と実際の行数が大きくずれている場合は、統計が古い可能性があるので `ANALYZE` します。

3. 夜間バッチで `orders` に 500 万行を投入した直後から、特定のクエリが遅くなりました。最初に試すべきことは何ですか？
> [!tip]- 答え
> `ANALYZE orders;` で統計情報を更新することです。統計が古いままだと、オプティマイザが行数を誤って見積もり、不適切なプランを選ぶことがあります。バッチ処理の最後に ANALYZE を組み込んでおくと再発を防げます。
