## 詳しい要約

**テーマ：インデックスが効かない原因は「問い方」と「DB の判断」の 2 種類あり、見抜く場所は 3 つ**

インデックスは「貼れば効く」ものではなく、DB には無視する権利がある。原因は「順序で引けない問い方をした」ケースと「使わない方が速いと DB が判断した」ケースの 2 つで、見た目は同じでも原因は正反対。書く前のレビュー・本番の統計・遅いクエリの記録で見抜き、使われないインデックスは書き込みを遅くするので剥がすべき、という話。

### 第1章 B木は1970年ボーイングで生まれた

- 1970 年、ボーイングの研究所で **ルドルフ・バイヤーとエドワード・マクレイト** が B 木を発表。PostgreSQL・MySQL・Oracle のインデックスの初期設定は今も B 木の子孫。
- B が何の頭文字か（Balanced / Boeing / Bayer）は本人たちが明かしていない。
- 1 ノードが数百の枝を持つため、1000 万行でも高さは 3〜4 段。フルスキャンの 1000 万行に対し、数回の読み込みで到達できる。
- ただし B 木は**順序で引く道具**。本の索引と同じで、「あ」で始まる語は引けても「あ」で終わる語は引けない。

### 第2章 効かない5パターン

1. **列に関数・加工をかける**：作成日時から年を取り出して比較すると効かない。直し方は「2026-01-01 以上 2027-01-01 未満」のような**範囲条件**にする。1970 年代 IBM System R で名付けられた **SARGable（Search ARGument ABLE）** という概念。
2. **暗黙の型変換**：文字列型の列を数値と比較すると、MySQL は列側を数値に変換するため 1 と同じことが起きる。
3. **文字コードの不一致**：utf8（utf8mb3）と utf8mb4 のテーブルを文字列列で結合すると、片側の変換が必要になり結合キーのインデックスが使われない。MySQL 8.0 で初期設定が utf8mb4 になってから移行途中のシステムで頻発。
4. **前方一致でない部分一致**：「田中で始まる」は引けるが「田中を含む」は引けない。
5. **複合インデックスの先頭列を飛ばす**：姓・名の順の電話帳で名だけで探すようなもの。

- 大半の原因は**列を「裸のまま」にしていない**こと。DB は列の元の値の順序でしか索引を引けない。

### 第3章 DBが自分の意思で使わない瞬間

- オプティマイザはインデックスと全件読み込みのコストを見積もって選ぶ。性別のように該当行が半分なら全件読みの方が速く、**使わないのは正しい判断**。目安として**テーブルの 1 割を超える行**を返す条件では全件読みが選ばれやすい。
- **開発機（100 行）と本番（1000 万行）で実行計画が変わる**：開発中に実行計画を見ても本番の答えは出ない。
- 逆もあり、データが増えて分布が変わると、コードを変えていないのにある日突然インデックスが効かなくなる（統計情報に基づいて計画するため）。
- PostgreSQL では同じ形の SQL（プリペアドステートメント）を 5 回実行すると 6 回目から **汎用計画（generic plan）** に切り替わり、値によっては全件読みになる。PostgreSQL 12 でこの挙動を固定する設定が追加。SQL Server では **パラメータスニッフィング** として 20 年前から有名。
- 効かない瞬間は突然来るもので、原因はコードではなく**データと統計**にある。

### 第4章 見抜く場所は3つ

1. **書く前**：条件の列が裸かどうかを目視。第 2 章の 5 パターンは実行しなくてもレビューで拾える。
2. **本番の統計**：PostgreSQL はインデックスごとの使用回数を記録しており、0 回のものは一度も効いていない。MySQL は 5.7 から使われていないインデックスを列挙する仕組みが標準搭載。
3. **遅いクエリの記録**：MySQL のスロークエリログには「インデックスを使わなかったクエリだけ記録する」設定がある。PostgreSQL には SQL を形ごとに集計して合計時間と回数を出す拡張（2009 年から標準添付）。
- 道具は 15 年以上前から揃っているが、**見る習慣のあるチームが少ない**。
- 2011 年、マーカス・ウィナンドが「Use The Index, Luke」を公開し、「SQL 性能問題の大半はインデックスの問題で、SQL を書いた開発者の責任」と主張。ORM 利用時こそ実際の SQL を出力して 5 パターンを確認すべき。

### 最終章 貼りすぎの代償とAI

- インデックスは読むときに効かなくても、**書き込み時には必ず更新される**。効かないインデックスが 10 本あれば書き込みは 10 回分余計な仕事をする。
- 2016 年、Uber が PostgreSQL から MySQL へ移行した理由の中心はこの**書き込み増幅**（行更新のたびに全インデックスを書き換える挙動）。
- AI に SQL を見せると高確率で「インデックスを貼りましょう」と返すが、AI は本番の統計を見ていない。**貼る判断はできても剥がす判断はできない**。使われているか本番で確かめて剥がす判断は、統計を読む人間の仕事として残る。

### まとめ

- 効かない原因は「順序で引けない問い方」と「DB が使わない方が速いと判断」の 2 種類。
- 列を裸のまま条件に使う（SARGable）ことが基本。
- 書く前・本番の統計・遅いクエリの記録の 3 か所で見抜く。
- インデックスは「貼るもの」ではなく「観測するもの」。使われていなければ剥がす。
