## 要約

モジュールバンドラーは「WebpackやViteの機能一覧」ではなく、**なぜJavaScriptを途中でまとめてビルドする必要があったのか**を理解するための道具である。結論として、役割は時代とともに変わった——昔は「動かすためにまとめる」、今は「早く・小さく・変換して届けるためにまとめる」。

### scriptタグ時代の3つの問題

バンドラー以前は、使いたいJSを `<script>` で必要な順に並べていた。実行順＝プログラムの前提であり、依存関係はコードの中にしかなく、**読み込み順を守っているのは人**だった。

1. **順番依存** … `app.js` → `user.js` → `utils.js` のように依存があるのに順を間違えると、画面は出てもその部分だけ動かない。ファイルが増えると依存を頭で管理できなくなる。
2. **名前の衝突** … トップレベルの関数・変数がページ全体で共有され、同名は後から読み込んだ方で上書きされる（エラーすら出ない）。長い名前や即時関数で包む工夫は「仕組み不足」の証拠。
3. **通信回数** … ファイルが増えると取りに行く回数も増える。当時のHTTP/1.xでは1ホストあたり同時接続はおよそ6本で、超過分は待ちになる（※今のHTTPは多重化できるが、後述のネストしたimport往復は別問題）。

### 「1ファイルに全部書く」「concat」では足りない

1本にまとめれば順番・衝突は消えるが、探す・同時編集・履歴・再利用が破綻する。開発時は分けて公開前に機械で貼り合わせる方法もあったが、**貼る順番を決めているのはやはり人**（設定ファイルの並び＝scriptタグの並びと同じ）。

要求は2つに分かれる。

- 開発時はファイルを分けたい
- ブラウザには扱いやすい形で渡したい

人手で両立するのは無理がある。

### モジュール・依存グラフ・バンドル

機能ごとに分け、**どのファイルがどれを使うかをコードに書く**単位がモジュール。繋がりが人の頭ではなくコードにあり、機械が読める。

当時ブラウザには標準モジュールがなく、Nodeの **CommonJS**（`require`・同期読み込み）はそのままではブラウザ向きでない。ブラウザ向けの **AMD** は先に依存を宣言してから実行するが書き方が独特で、ライブラリは両対応が必要だった。

そこで人が順番を守るのをやめ、**機械に依存をたどらせる**。

1. **エントリーポイント** を1つ指定する
2. 中の import / require を読む
3. 先のファイルへ進み、さらに依存をたどる
4. 尽きるまで繰り返す → **依存グラフ**（同じファイルは地図上で1つ）

この地図から、配りやすく実行しやすい成果物を作るのが **バンドル**。バンドラーはファイルを順番に貼り合わせているのではなく、モジュール境界を理解し参照を解決し、必要なら名前を付け替えて並べ直す。だから名前がぶつからない。この役割を担うのがモジュールバンドラーで、代表例が **Webpack**（公式：静的モジュールバンドラー。エントリーから依存グラフを作りまとめて出力。ローダー／プラグインでCSSや画像も同じグラフに載せられる）。

### 「まとめること」と「ついでにやること」

よく一緒に語られるが、分けた方が正確。

| まとめること自体 | 同じ道具がついでにやるもの |
| --- | --- |
| 依存解決・バンドル出力 | Tree Shaking（未使用削除） |
|  | Minification（文字数削減） |
|  | Code Splitting（初回／後から分割） |
|  | TypeScript / JSX などの変換 |

右側はバンドルそのものの定義ではないが、ブラウザは今もやってくれないので、ビルド工程として残り続ける。

### ブラウザが import できる今でもビルドする理由

`type="module"` ならブラウザ自身が import をたどれる（文法は2015、主要ブラウザの読み込み対応は2017〜2018頃）。「標準モジュールがないからまとめるしかない」という最大の制約は解消された。

それでもまとめる価値は消えていない。

1. **npm の名前だけの import**（例: React）は、場所がはっきり書かれた import と違い、ブラウザはそのまま解決できない → 解決工程が必要
2. **ネストした import の往復** … ファイルを開くまで次の依存が分からず、深いほど往復が増える。Vite公式も本番でそのまま配るのは非効率と述べる → あらかじめまとめれば往復を減らせる
3. Tree Shaking・minify・TS変換などはブラウザがやらない
4. **開発体験** … 保存で画面の一部だけ差し替える仕組みもビルドツール側

つまりバンドラーが不要になったのではなく、**期待される役割が変わった**。

### 今の道具の位置づけ

- **Webpack** … JS以外も依存グラフに載せる方向へ広がった
- **Rollup** … 小さくまとめる・未使用を静的解析して外す向き
- **esbuild** … とにかく速い。バンドルだけでなく変換にも使われる
- **Vite** … 公式には「ビルドツール」。中身は開発サーバー＋本番ビルド。開発中は自分のコードはまとめず配り、よく使うライブラリは先にまとめる。本番ではやはりまとめる。以前は開発=esbuild／本番=Rollupの2本立てだったが、v8からは **Rolldown**（Rust）に一本化。バンドリングはその中の1工程

道具の名前より「どの工程を担っているか」で見ると混乱しない。モジュールバンドラーが何を解決したかが分かると、WebpackやViteがなぜ存在するのかも見えてくる。
