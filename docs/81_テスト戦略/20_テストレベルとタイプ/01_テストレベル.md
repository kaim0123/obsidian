# テストレベル

**テストレベル**は「どの大きさの単位をテストするか」の区分です。JSTQB では 5 つのレベルを定義していますが、Web 開発の現場では「Unit / Integration / E2E」という開発者寄りの呼び方も使われます。この章では両方を対応づけ、それぞれで**何を確かめ、何を確かめないか**を整理します。

---

## 1. JSTQB のテストレベル

| レベル | 対象 | 主な確認内容 | 主な担当 |
|--------|------|--------------|----------|
| **コンポーネントテスト**（単体テスト） | 関数・クラス・コンポーネント単体 | ロジックが正しいか | 開発者 |
| **コンポーネント統合テスト** | コンポーネント同士のつなぎ目 | 呼び出し方・データの受け渡し | 開発者 |
| **システムテスト** | システム全体 | 機能・非機能の要件を満たすか | QA・テストチーム |
| **システム統合テスト** | 外部システム・サービスとの連携 | 外部 API・他システムとのやり取り | QA・開発者 |
| **受け入れテスト** | システム全体（利用者の視点） | 業務で使えるか、リリースしてよいか | 利用者・PO・顧客 |

受け入れテストはさらに、ユーザー受け入れテスト（UAT）、運用受け入れテスト、契約・規制の受け入れテスト、アルファ・ベータテストに分かれます。

---

## 2. 開発者の呼び方との対応

| 開発者の呼び方 | JSTQB のレベル | 典型的なツール | 実行速度 |
|----------------|----------------|----------------|----------|
| **Unit（単体）** | コンポーネントテスト | Vitest、Jest | ミリ秒 |
| **Integration（結合）** | コンポーネント統合 ／ 一部システム統合 | Vitest + Testing Library、MSW、テスト用 DB | 数十ミリ秒〜秒 |
| **E2E（エンドツーエンド）** | システムテスト ／ システム統合 | Playwright、Cypress | 秒〜分 |
| **手動・UAT** | 受け入れテスト | 人・チェックリスト | 分〜時間 |

> 「Integration」の範囲はチームによって大きく違います。Kent C. Dodds の Testing Trophy では「複数コンポーネントをまとめて、ユーザーに近い操作でテストするもの」を Integration と呼び、ここを一番厚くします（[[02_テストの形（ピラミッド・Trophy・Honeycomb）]]）。**チーム内で言葉の定義をそろえる**のが先です。

---

## 3. 各レベルの考え方

### 3.1 Unit（コンポーネントテスト）

- **確かめること**：分岐・計算・変換などのロジック。境界値や異常系を細かく試すのに向く。
- **確かめないこと**：他の部品とのつながり、画面の見た目、実際のネットワークや DB。
- **依存の扱い**：外部依存はテストダブル（[[04_テストダブルの分類]]）に置き換える。ただし置き換えすぎると「実際にはつながらない」ことを見逃す。

### 3.2 Integration（統合テスト）

- **確かめること**：部品同士のインターフェース。引数の形、データの変換、エラーの伝わり方。
- **統合の進め方**：一度に全部つなぐ（ビッグバン）より、少しずつつなぐ（トップダウン／ボトムアップ）ほうが、どこで壊れたかが分かりやすい。
- **外部の扱い**：DB はテスト用のコンテナ、外部 API は MSW などでモックする、といった線引きをチームで決める。

### 3.3 E2E（システムテスト）

- **確かめること**：ユーザーの主要な流れ（ログイン→購入→完了など）が本番に近い環境で通るか。
- **注意点**：遅い・壊れやすい・原因が分かりにくい。**クリティカルパスに絞る**のが基本（[[03_テスト自動化の考え方]]）。
- 非機能（性能・セキュリティ・アクセシビリティ）もこのレベルで確かめることが多い（[[03_非機能テスト概要]]）。

### 3.4 受け入れテスト

- **確かめること**：業務で使えるか、リリースしてよいか。**妥当性確認**の性格が強い（[[01_テストの目的とテストで行う3つのこと]]）。
- 受け入れ基準は開発の前に決めておくと、実装とテストのずれを防げる（ATDD・BDD）。

---

## 4. レベルを選ぶときの判断

| 確かめたいこと | 一番安く確かめられるレベル |
|----------------|----------------------------|
| 計算・条件分岐が正しいか | Unit |
| フォームの入力→バリデーション→送信の流れ | Integration |
| API のレスポンスを画面が正しく表示するか | Integration（API はモック） |
| 本番構成でログインから購入まで通るか | E2E |
| 実際の業務で使えるか | 受け入れテスト |

- **同じことを複数のレベルで重複して確かめない**。下のレベルで確かめたロジックを、E2E で全パターン試す必要はない。
- 逆に、**下のレベルでは確かめられないこと**（つながり・環境・ユーザー体験）だけを上のレベルに残す。
