# テストの7原則

ISTQB / JSTQB のシラバスには、何十年ものテストの経験から導かれた**7つの原則**があります。試験で必ず問われるだけでなく、「テストをどこまでやればいいのか」を考えるときの前提になるので、実務の言葉に置き換えて整理します。

---

## 1. 一覧

| # | 原則 | 一言でいうと |
|---|------|--------------|
| 1 | テストは欠陥があることは示せるが、欠陥がないことは示せない | 「バグゼロ」は証明できない |
| 2 | 全数テストは不可能 | 全部の組み合わせは試せない |
| 3 | 早期テストで時間とコストを節約 | 早く見つけるほど安く直せる |
| 4 | 欠陥の偏在 | バグは一部の場所に集まる |
| 5 | テストの効果は薄れる（殺虫剤のパラドックス） | 同じテストだけでは新しいバグは見つからない |
| 6 | テストはコンテキスト次第 | 正しいテストのやり方は状況で変わる |
| 7 | 欠陥ゼロの落とし穴 | バグがなくても役に立たなければ失敗 |

---

## 2. 各原則と実務での意味

### 原則1：欠陥がないことは示せない

- テストが全部通っても、「試した範囲では見つからなかった」ということしか言えません。
- **実務では**：リリース判断は「バグゼロ」ではなく「残っているリスクを受け入れられるか」で行う。テスト結果には**何を試したか（範囲）**も一緒に書く。

### 原則2：全数テストは不可能

- 入力が1つの 32bit 整数だけでも約43億通り。画面・状態・タイミングを掛け合わせれば事実上無限です。
- **実務では**：同値分割・境界値分析などの技法（[[06_同値分割法]]、[[07_境界値分析]]）で**代表値に絞る**。リスクで優先順位を付ける（[[04_探索的テストとリスクベーステスト]]）。

### 原則3：早期テスト（シフトレフト）

- 要件の誤りを本番で見つけると、設計・実装・テストをすべてやり直すことになります。
- **実務では**：仕様レビュー、型チェック・静的解析、コードレビュー（[[16_コードレビューの基礎]]）など、**コードを動かす前のテスト**に投資する。テストを先に書く TDD もこの原則の実践です。

### 原則4：欠陥の偏在

- 経験的に、バグの多くは**少数のモジュールに集中**します（パレートの法則に近い）。複雑な処理・変更が多い場所・経験の浅い人が書いた場所などです。
- **実務では**：過去のバグ履歴や変更頻度を見て、テストを厚くする場所を決める。バグが出たモジュールの周辺は追加で探索する。

### 原則5：殺虫剤のパラドックス

- 同じテストを繰り返し流しても、そのテストで見つかるバグはすでに直っているので、新しいバグは見つかりません。
- **実務では**：回帰テストは「壊れていないことの確認」と割り切り、**新しいバグ探しは探索的テストや新しいケースの追加で行う**。テストケースを定期的に見直す。

### 原則6：コンテキスト次第

- 医療機器と社内ツール、決済と個人ブログでは、必要なテストの厚さも種類も違います。
- **実務では**：他社の「ベストプラクティス」をそのまま持ち込まない。自分のプロダクトの**リスクと制約**から戦略を決める（[[01_テスト戦略とは]]）。

### 原則7：欠陥ゼロの落とし穴

- 仕様通りでバグがなくても、ユーザーの役に立たなければ意味がありません。
- **実務では**：検証だけでなく**妥当性確認**を入れる（[[01_テストの目的とテストで行う3つのこと]]）。仕様そのものをレビューする。

---

## 3. 原則同士のつながり

```
原則2（全部は無理）
   └─→ だから絞る：原則4（偏在）で場所を、原則6（コンテキスト）で方法を決める
原則1（ゼロは証明できない）
   └─→ だから「十分か」はリスクで判断する
原則5（効果が薄れる）
   └─→ だからテストを入れ替える・探索する
原則3（早いほど安い）
   └─→ だから動かす前にもテストする
原則7（ゼロでも失敗しうる）
   └─→ だから「正しいものか」も確かめる
```

---

## 4. 試験での覚え方のコツ

- 原則名と「例文」をセットで覚える。例：「同じテストを繰り返しても新しいバグが見つからない」→ 殺虫剤のパラドックス。
- 「全数テストは不可能」と「欠陥がないことは示せない」は取り違えやすい。前者は**量の限界**、後者は**証明の限界**。
