# エラー・欠陥・故障とデバッグ

「バグ」という言葉は、人のミス・コードの誤り・画面に出た異常のどれにも使われます。テストの世界ではこれを**エラー（誤り）・欠陥・故障**の3つに分けて呼びます。区別できると、バグレポートの書き方や「テストとデバッグの役割分担」がはっきりします。

---

## 1. 3つの用語

| 用語 | 英語 | 何か | 例 |
|------|------|------|----|
| **エラー（誤り）** | Error / Mistake | 人が犯す間違い | 「税込みで計算する」を読み落とした |
| **欠陥** | Defect / Bug / Fault | 成果物（コード・仕様書）に入り込んだ誤り | `price * 1.0` と書かれたコード |
| **故障** | Failure | 欠陥が実行されて、期待と違う振る舞いが外に現れたもの | 画面に税抜き価格が表示される |

### 因果関係

```
人のエラー ──→ 欠陥（コードや仕様に残る）──→ 実行されると故障（外から見える）
                    │
                    └─ 実行されなければ故障は起きない（潜在欠陥）
```

- **欠陥があっても故障するとは限らない**：その行が一度も実行されない、特定の条件でしか問題にならない、など。
- **故障は欠陥以外からも起きる**：ハードウェア障害、放射線によるビット反転、設定ミス、外部サービスの停止など。
- **根本原因（Root cause）**：エラーを生んだ理由。「仕様書が曖昧だった」「レビューがなかった」など。再発防止はここに手を打つ。

---

## 2. テストとデバッグの違い

| | テスト | デバッグ |
|---|--------|----------|
| 目的 | **故障を起こして見つける**（または起きないことを確認する） | **故障の原因の欠陥を特定して直す** |
| 誰が | 開発者・QA・ユーザーなど誰でも | 主に開発者 |
| 出力 | 故障の報告、テスト結果 | 修正されたコード |
| 終わった後 | — | 確認テスト（直ったか）＋回帰テスト（他を壊していないか） |

- テストは「どこかがおかしい」を見つけるところまで。**どこを直せばいいか**を突き止めるのはデバッグです。
- 実際の開発では、開発者が単体テストを書きながらデバッグもするので、1人の中で行き来します。役割として区別しておくと、バグレポートに「再現手順（テストの成果）」と「原因の推測（デバッグの入口）」を分けて書けるようになります。

### 修正後の2つのテスト

1. **確認テスト（再テスト）**：報告された故障が再現しなくなったかを確かめる。
2. **回帰テスト**：修正が他の場所を壊していないかを確かめる（[[02_テストの種類（機能・非機能）]]）。

> バグを直すときは、先に「そのバグで落ちるテスト」を書いてから直すと、確認テストと回帰テストを1本で兼ねられます。

---

## 3. 静的テストと動的テスト

欠陥と故障の区別は、テストの2つの大分類にもつながります。

| | 静的テスト | 動的テスト |
|---|------------|------------|
| 動かすか | 動かさない | 動かす |
| 見つけるもの | **欠陥**を直接見つける | **故障**を起こして欠陥を推測する |
| 例 | レビュー、型チェック、Lint、静的解析 | 単体テスト、E2E テスト、手動テスト |
| 強み | 早い段階で安く見つかる。故障にならない欠陥（保守性の問題など）も見つかる | 実際の振る舞いを確かめられる |

静的テストのプロセスは 86_QAプロセス/30_レビュー・静的テスト（[[16_コードレビューの基礎]]）で扱います。

---

## 4. 実務での使い分け

- **バグレポートのタイトル**は「故障」で書く（例：「カート画面で税抜き価格が表示される」）。原因の推測（欠陥）は本文に分けて書く（[[11_欠陥管理とバグレポート]]）。
- **振り返り**では「欠陥」と「根本原因」を分ける。「この1行を直した」で終わらず、「なぜその誤りが入り、なぜテストで見つからなかったか」まで見る。
- デバッグの具体的なやり方は [[MOC_デバッグ]]（84_デバッグ）へ。
