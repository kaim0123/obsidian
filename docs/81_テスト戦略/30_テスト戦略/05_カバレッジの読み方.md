# カバレッジの読み方

**コードカバレッジ**は、テストを実行したときにコードのどれだけが実行されたかを示す割合です。数字で出るので目標にしやすい反面、「数字を上げること」が目的になると、テストの価値を下げてしまうことがあります。この章では、カバレッジの種類と**正しい読み方・使い方**を整理します。

---

## 1. カバレッジの種類

| 種類 | 何を数えるか | 例（`if (a && b) {…}`） |
|------|--------------|------------------------|
| **ステートメント（命令）カバレッジ** | 実行された文の割合 | if の中が1回でも実行されれば 100% |
| **ブランチ（分岐・判定）カバレッジ** | 各分岐の真・偽を両方通った割合 | if が真の場合と偽の場合の両方が必要 |
| **条件カバレッジ** | 各条件（a、b）の真・偽を両方取った割合 | a と b それぞれが真偽両方 |
| **MC/DC** | 各条件が単独で結果を変えることを示せた割合 | 航空・車載などの安全規格で要求 |
| **関数カバレッジ** | 呼ばれた関数の割合 | — |
| **行カバレッジ** | 実行された行の割合 | ステートメントに近い（ツールが出す値） |

- 強さは **ステートメント < ブランチ < 条件の組み合わせ < MC/DC**。ブランチ 100% ならステートメントも 100% になる（逆は成り立たない）。
- JSTQB FL で扱うのはステートメントとブランチの2つ（[[04_テスト分析と設計（テスト技法）]] 4.3）。
- Vitest では `--coverage` で v8 / istanbul のレポートが出ます（[[06_カバレッジとUI・ブラウザモード]]）。

---

## 2. カバレッジが教えてくれること・くれないこと

| 教えてくれること | 教えてくれないこと |
|------------------|--------------------|
| **一度も実行されていないコード**がどこか | 実行されたコードの**結果が正しいか** |
| テストが明らかに足りない場所 | 仕様に書かれていない振る舞いの抜け |
| 分岐の片側しか試していない場所 | 境界値や組み合わせを試したか |
| — | 使いやすさ・性能などの非機能 |

```ts
// カバレッジ 100% だが、何も確かめていないテスト
test('calcTotal', () => {
  calcTotal([{ price: 100, qty: 2 }]); // 実行するだけで expect がない
});
```

- **カバレッジが低い → テストが足りないのはほぼ確実**。
- **カバレッジが高い → テストが十分とは限らない**。
- つまりカバレッジは「足りない場所を探す道具」であって、「十分かを判断する道具」ではありません。

---

## 3. 目標値の決め方

| よくある方針 | 評価 |
|--------------|------|
| 全体で 80% 以上を CI で必須にする | 分かりやすいが、重要でない部分のテストで数字を稼ぐ動機が生まれる |
| 100% を必須にする | コストが急に上がる。意味の薄いテストや、テストのためのコード変更が増える |
| **変更差分のカバレッジを見る** | 新しく書いたコードにテストがあるかを見られる。既存コードの低さに引きずられない |
| **重要なモジュールだけ高い基準にする** | 決済・権限などに絞って 90% 以上、UI の見た目部分は基準なし |
| 基準を設けず、レビューで未実行箇所を確認する | 小さなチーム向け |

- Martin Fowler は「カバレッジは 80〜90% 台に自然になることが多いが、**目標にするものではない**」と述べています。
- 数字を CI の必須条件にするなら、**下がったことに気づく仕組み**（前回より下がったら警告）として使うのが安全です。

---

## 4. 実務での使い方

1. **レポートの赤い部分を見る**：実行されていない分岐を見つけ、「テストすべきか」「消してよいコードか」を判断する。
2. **ブランチカバレッジを見る**：ステートメントだけだと else 側の抜けに気づかない。
3. **テストの質は別の方法で確かめる**：
   - 期待結果のアサーションがあるか（レビュー）
   - 境界値・異常系を試しているか（[[07_境界値分析]]）
   - **ミューテーションテスト**（Stryker など）：コードをわざと壊して、テストが落ちるかを確かめる。落ちなければそのテストは弱い。
4. **除外を明示する**：自動生成コード、設定ファイル、型定義などはカバレッジの対象から外す。
