# 探索的テストとリスクベーステスト

[[01_テストの目的とテストで行う3つのこと]] では、テストの一つに**バグを発見するための探索**があることを述べました。ここでは、その考え方を具体化する**探索的テスト**と、限られた時間で効果を最大化する**リスクベーステスト**の概要をまとめます。

---

## 1. 探索的テスト（Exploratory Testing）

### 1.1 定義と特徴

- **探索的テスト**: あらかじめ詳細なテストケースを書かず、**設計と実行を同時に（あるいは交互に）行い、学習しながらテストする**アプローチ。
- 仕様書に書かれていない経路・組み合わせ・異常操作を試し、**「何かおかしい」**に気づくことを重視する。
- [[../QA・ソフトウェアテスト研修【MIXI 25新卒技術研修】]] でも、「仕様通りのチェックだけでは不十分で、バグを探しに行く活動が必要」と説明されている部分に対応する。

### 1.2 いつ使うか

- 仕様が固まりきっていない、または変更が多いフェーズ。
- 新機能の初期評価や、リリース前の「ざっと全体を触ってみる」確認。
- スクリプト化されたテストでは拾いにくい、UI・UX や想定外の操作で起きる不具合を探すとき。
- 時間が限られていて、重要な部分を**集中して探索**したいとき。

### 1.3 進め方の例

- **時間ボックス**: 例として 90 分など区切りを決め、その中で「何を探索するか」を決めて実行する。
- **チャーター（探索ミッション）**: 「ログイン〜決済まで、エラーを出さないか」「戻るボタンを連打したときの挙動」など、短い目標を書いてから触る。
- **メモ・記録**: 気づいたこと・試したこと・怪しい点をその場でメモし、後でバグチケットやレポートにまとめる。
- **ペアで実施**: 一人が操作し、もう一人が観察・質問・アイデアを出すことで、探索の幅が広がる。

### 1.4 限界と補完

- 探索的テストは**再現性・網羅性を保証するものではない**。経験や知識に依存する部分が大きい。
- したがって、**スクリプト化されたテスト（仕様ベース・技法ベース）と組み合わせる**とよい。重要な経路はテストケースで押さえ、その上で探索で「隙間」を探す。

---

## 2. リスクベーステスト（Risk-Based Testing）

### 2.1 考え方

- **リスク** = 不具合が起きたときの**影響（インパクト）** × **起きやすさ（発生確率・変更の多さなど）** で考えられることが多い。
- **リスクベーステスト**: 限られた時間・リソースのなかで、**リスクが高いところにテストを集中**し、効果を最大化する考え方。
- 「全部を均等にテストする」のではなく、「どこが壊れるとまずいか」「どこが変わりやすいか」を考慮して優先度をつける。

### 2.2 リスクの例

| 観点 | リスクが高くなりやすい例 |
|------|---------------------------|
| **影響が大きい** | 決済、認証、個人情報、医療・安全に関わる処理 |
| **変更が多い** | 今回のスプリントで手を入れたモジュール、リファクタリングした箇所 |
| **複雑・繋がりが多い** | 他システム連携、複数条件が絡むロジック、状態遷移が複雑な部分 |
| **過去に不具合が出た** | 同じ箇所や類似機能でバグが多かった領域 |
| **仕様が曖昧** | 認識齟齬が起きやすい部分 |

### 2.3 テスト計画への反映

- テスト計画やテスト設計の段階で、**リスク一覧**や**リスクマトリクス**を作り、優先度を決める。
- 高リスク領域には、テストケース数を多めにしたり、探索的テストの時間を割り当てたり、自動化の優先度を上げたりする。
- 低リスク領域は、最小限の smoke やサニティで済ませ、リソースを高リスクに回す。

### 2.4 注意点

- リスク評価は**主観や経験に依存**するため、開発・QA・ビジネスで共通認識を持つとよい。
- リスクは**期間ごとに見直す**とよい（新機能追加・障害発生などでリスクが変わる）。

---

## 3. 探索的テストとリスクベーステストの組み合わせ

- **リスクの高い機能や変更箇所**を特定し、その部分に対して**探索的テストの時間を集中して使う**、という形で組み合わせると効果的。
- 例：「決済フローは影響が大きいので、決済周りを 90 分探索する」「今スプリントで変更した API を中心に、異常系を探索する」。
