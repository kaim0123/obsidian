# テスト自動化の考え方

テスト自動化は、**人間の手作業をスクリプトやツールに任せ、繰り返し実行・早期フィードバックを実現する**ための取り組みです。QAエンジニアは「何をいつ自動化するか」「自動化の限界とコスト」を理解し、効果的な自動化戦略を立てる必要があります。

---

## 1. テスト自動化の目的とメリット

### 1.1 主な目的

- **回帰テストの効率化**: 変更のたびに同じテストを手で実行する負荷を減らし、リリース前の安心材料にする。
- **早期フィードバック**: コミットやビルドのたびに自動実行し、壊れた変更を早く検知する（CI との連携）。
- **繰り返しの正確さ**: 手順の取り違えや見落としを減らし、同じ条件で何度でも実行できる。
- **リソースの有効活用**: 単純な反復は自動化に任せ、人は探索的テストや設計・分析に集中する。

### 1.2 デメリット・注意点

- **初期コスト**: スクリプト作成・環境整備に時間がかかる。
- **保守コスト**: 画面や仕様が変わるとテストコードの修正が必要になる。
- **自動化しづらいもの**: UX・見た目・曖昧な仕様・探索的テストは、自動化が難しく、手動が向く。
- **過信のリスク**: 自動テストが通っても「仕様通りのチェック」に偏っていると、本番で想定外の不具合が出る可能性は残る。

---

## 2. テストピラミッド

**テストピラミッド**は、自動化するテストの**量と種類のバランス**を考えるためのモデルです。

```
        /\
       /  \   E2E・UIテスト（少なめ・遅い・壊れやすい）
      /----\
     /      \  API・結合テスト（中程度）
    /--------\
   /          \ 単体テスト（多め・速い・安定）
  /------------\
```

### 2.1 各層の考え方

| 層 | 内容 | 特徴 | 自動化の向き |
|----|------|------|----------------|
| **単体テスト** | 関数・メソッド・クラス単位のテスト | 速い、多い、安定しやすい | 積極的に自動化（CIで毎回実行） |
| **結合・APIテスト** | モジュール間・APIのテスト | 中程度の数・時間、インターフェースの検証 | 重要部分を自動化 |
| **E2E・UIテスト** | ブラウザやアプリ全体を通すテスト | 遅い、環境に依存、変更で壊れやすい | 絞って自動化（クリティカルパスのみ等） |

- **ピラミッドの意図**: 下（単体）を厚くし、上（E2E）は必要最小限にすると、**速さ・安定性・保守コスト**のバランスが取りやすい。
- 「逆ピラミッド」（E2Eばかり）になると、実行時間が長く、画面変更のたびに直すコストが大きくなりがち。

---

## 3. 何を自動化するかの判断

### 3.1 自動化に向いているもの

- 繰り返し何度も実行する回帰テスト。
- 手順が明確で、期待結果が決まっているテスト（同値・境界・デシジョンテーブルで設計したケースなど）。
- 単体・API・DB など、UI に依存しないテスト。
- 毎回のビルド・マージで回したい smoke テスト。

### 3.2 自動化が向いていない・慎重にすべきもの

- 一度きりや、仕様が固まっていない探索的テスト。
- 見た目・使いやすさ・デザインの評価（人間の判断が必要）。
- 環境やデータの準備が毎回複雑で、コストがかかりすぎるテスト。
- すぐに仕様やUIが変わる部分（保守コストが高い）。

### 3.3 判断の目安

- **ROI（投資対効果）**: 同じテストを手動で何回やるか、自動化の作成・保守コストと比べて、回す回数が多いほど自動化のメリットが大きい。
- **安定性**: 環境やデータが安定しているほど、自動化は維持しやすい。
- **クリティカルさ**: 障害時の影響が大きい機能（ログイン、決済など）は、自動化の優先度を高くする。

---

## 4. CI/CD との連携

- **CI（継続的インテグレーション）**: コミットやプルリクエストのたびにビルドし、単体テスト・結合テストを自動実行する。
- **CD（継続的デリバリ）**: ビルド成果物をデプロイ可能な状態にし、ステージングなどに自動デプロイし、E2E や smoke テストを実行する場合もある。
- 自動テストは、このパイプラインに組み込み、**失敗したらビルド・デプロイを止める**（または警告する）ようにすると、効果が大きい。

---

## 5. 保守と設計のポイント

- **ページオブジェクト・コンポーネントの共通化**: UI の変更を一箇所の修正で吸収しやすくする。
- **データ・環境の分離**: テストデータや環境設定をコードから分離し、環境違いで動かしやすくする。
- **安定したセレクター**: ID や data 属性など、変更に強い識別子を使う（本教材の Playwright の章を参照）。
- **フレキシブルな待機**: 固定スリープではなく、要素の出現・非表示を待つようにする。
