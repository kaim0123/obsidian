# テスト戦略とは

テストに使える時間と人は限られています。**テスト戦略**は、その限られた資源を「どのリスクに・どのレベルで・どのやり方で」使うかを決めた方針です。個々のテストケースの話ではなく、**プロジェクト全体でテストをどう組み立てるか**の設計図にあたります。

---

## 1. テスト戦略・テスト計画・テストケースの違い

| | 何を決めるか | 期間 | 例 |
|---|--------------|------|----|
| **テスト戦略** | 方針。何を重視し、どのレベル・タイプ・やり方で、どのくらいテストするか | プロダクト・組織で長く使う | 「ロジックは Unit で厚く、E2E は購入フローだけ」 |
| **テスト計画** | 具体的な段取り。範囲・スケジュール・担当・完了条件 | リリース・スプリント単位 | 「v2.3 では決済の回帰と新機能の探索を 3 日で行う」 |
| **テストケース** | 個々の確認手順と期待結果 | テストごと | 「残高 0 円で購入すると エラー表示」 |

テスト計画の書き方は [[15_テスト計画とドキュメント]] で扱います。この章は一番上の「戦略」の話です。

---

## 2. 戦略で決めること

JSTQB では、テスト戦略を「テストレベル・テストタイプ・テスト技法・テストの実践の選択と組み合わせ」と説明しています。実務では次の問いに答えられれば十分です。

| 問い | 決めることの例 | 参照 |
|------|----------------|------|
| **何を守りたいか** | 失敗したときの影響が大きい機能・品質特性 | リスク分析（[[04_探索的テストとリスクベーステスト]]） |
| **どのレベルで確かめるか** | Unit / Integration / E2E の比重 | [[01_テストレベル]]、[[02_テストの形（ピラミッド・Trophy・Honeycomb）]] |
| **どの種類を入れるか** | 機能に加えて性能・アクセシビリティ・セキュリティをやるか | [[02_テストの種類（機能・非機能）]] |
| **どう作るか** | 仕様からの技法・探索・経験ベースの配分 | [[MOC_テスト設計技法]] |
| **何を自動化するか** | 自動化する範囲・ツール・CI での回し方 | [[03_テスト自動化の考え方]] |
| **いつ十分とするか** | 完了条件・品質ゲート・カバレッジの扱い | [[05_カバレッジの読み方]]、[[00_Webサイト品質ゲート_目次]] |
| **誰がやるか** | 開発者・QA・ユーザーの分担、独立性 | [[05_テストマネジメント]]（JSTQB 第5章） |

## 3. テストアプローチの種類

ISTQB の Advanced Level では、戦略の立て方をいくつかの型に分けています。1つを選ぶのではなく、組み合わせて使います。

| アプローチ | 考え方 | 向いている場面 |
|------------|--------|----------------|
| **分析的**（リスクベースなど） | リスクや要件を分析して、重要なところに集中する | ほとんどのプロダクトの基本 |
| **モデルベース** | 状態遷移図・業務フローなどのモデルからテストを作る | 状態が多いシステム |
| **方法論的** | チェックリストや品質特性の一覧に沿って網羅する | 定型の確認（アクセシビリティ、セキュリティ） |
| **プロセス準拠・標準準拠** | 業界標準・規制に従う | 医療・金融・車載など |
| **指示型（コンサルテーション型）** | 専門家やユーザーの助言に従う | ドメイン知識が必要なとき |
| **回帰回避型** | 既存機能を壊さないことを最優先し、自動回帰を厚くする | 長く運用しているプロダクト |
| **対応型（リアクティブ）** | 実物を触りながら反応的にテストする（探索的テスト） | 仕様が少ない・変化が速い |

---

## 4. 戦略を立てる手順

1. **目的を決める**：このプロダクトで品質とは何か。何が起きたら一番困るか。
2. **リスクを洗い出す**：機能ごとに「起きやすさ × 起きたときの影響」を見積もる。
3. **アプローチを選ぶ**：リスクの高いところは技法で網羅＋探索、低いところはスモーク程度、など。
4. **レベルと自動化の配分を決める**：テストの形（ピラミッド／Trophy）を決め、CI に何を入れるかを決める。
5. **完了条件を決める**：リリースしてよい条件（重大バグ 0、主要フローの E2E が緑、など）。
6. **見直す**：障害や新機能のたびにリスクが変わるので、定期的に更新する。

## 5. Web アプリ開発者向けの戦略例

```
【目的】購入できないこと・誤請求を防ぐ。UI の細かな崩れは許容。

【レベル配分】
  - Unit：価格計算・在庫判定・バリデーションなどのロジック（厚く）
  - Integration：フォーム・一覧・カートなど、画面単位の振る舞い（一番厚く）
  - E2E：ログイン→カート→決済完了 の 1 本と、会員登録 の 1 本だけ
  - 静的：TypeScript strict・Lint を CI で必須

【非機能】
  - アクセシビリティ：axe を Integration に組み込む
  - 性能：Lighthouse CI で予算を超えたら警告

【手動】
  - リリース前に決済周りを 60 分探索（リスクベース）

【完了条件】
  - CI 全緑、E2E の決済フローが緑、重大度 High のバグ 0
```

## 6. よくある失敗

- **戦略がない**：「とりあえずカバレッジ 80%」だけが目標になり、重要でない部分のテストばかり増える。
- **他社のやり方をそのまま使う**：Google のテストサイズ比率を、小さなチームにそのまま当てはめる（原則6「コンテキスト次第」→ [[02_テストの7原則]]）。
- **一度決めて放置**：障害が出てもテストの配分が変わらない。
