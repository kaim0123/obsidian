# テストの形（ピラミッド・Trophy・Honeycomb）

自動テストを**どのレベルにどれだけ書くか**のバランスは、よく図形にたとえて語られます。代表的なのがテストピラミッド、Testing Trophy、Testing Honeycomb です。どれが正しいというより、**何を前提にした形なのか**を知って、自分のプロダクトに合う形を選ぶのが目的です。

---

## 1. テストピラミッド（Mike Cohn, 2009）

```
          /\
         /E2E\        少ない・遅い・壊れやすい
        /------\
       / Service \    中くらい
      /------------\
     /     Unit     \  多い・速い・安定
    /----------------\
```

- 『Succeeding with Agile』で紹介され、Martin Fowler の記事で広まった。
- **前提**：Unit テストは安く速い、UI を通すテストは高く遅い。だから下を厚く、上を薄く。
- **強み**：フィードバックが速く、壊れたときに原因の場所がすぐ分かる。
- **弱み**：Unit をモックだらけで書くと、**部品は全部正しいのにつなぐと動かない**ことを見逃す。

### アンチパターン：アイスクリームコーン

```
    \----------------/
     \  手動テスト   /    ← 一番多い
      \------------/
       \   E2E    /
        \--------/
         \ Unit /         ← ほとんどない
          \----/
```

- テストが遅く、壊れやすく、リリースのたびに手作業が増える。後からテストを足したプロジェクトで起きやすい。

## 2. Testing Trophy（Kent C. Dodds, 2018）

```
        ___
       |E2E|          少し
     ___________
    | Integration |   一番厚い
     ‾‾‾‾‾‾‾‾‾‾‾‾‾
       | Unit |       少なめ
      __________
     |  Static  |     土台（型・Lint）
```

- 「**テストがソフトウェアの使われ方に似ているほど、テストは信頼できる**」という考え方。
- **前提**：フロントエンドでは、個々の関数より「コンポーネントを組み合わせてユーザーが操作したときの振る舞い」にバグが出やすい。Testing Library や MSW で Integration テストが安く書けるようになった。
- **Static（静的解析）を土台に置く**のが特徴。TypeScript と ESLint で、テストを書かずに防げるバグは防ぐ。
- **弱み**：Integration の範囲が広くなりすぎると、失敗したときに原因の場所を探しにくい。

---

## 3. Testing Honeycomb（Spotify, 2018）

```
      ⬡  Integrated（他サービスまで含む）  少し
   ⬡ ⬡ ⬡  Integration（サービス単体を外から） 一番厚い
      ⬡  Implementation Detail（内部の単体） 少し
```

- マイクロサービス向け。1つのサービスは小さいので、**サービスの API を外から叩くテスト**を中心にする。
- 内部実装の Unit テストは、複雑なロジックがあるところだけ。
- 他サービスまで含むテストは壊れやすいので最小限にし、代わりに契約テストを使う。

---

## 4. 比較

| | ピラミッド | Trophy | Honeycomb |
|---|-----------|--------|-----------|
| 一番厚い層 | Unit | Integration | Integration |
| 想定する対象 | バックエンド・ロジック中心 | フロントエンド | マイクロサービス |
| 重視すること | 速さ・原因の特定しやすさ | ユーザーの使い方への近さ | サービス境界の正しさ |
| 静的解析 | 図には含まない | 土台として明示 | 図には含まない |

### Google のテストサイズ

Google はレベルではなく**サイズ**（Small / Medium / Large）で分けます。Small は 1 プロセス・ネットワークなし、Medium は 1 台のマシン内、Large は制限なし。「何をテストするか」ではなく「**何を使ってよいか**」で分けるので、遅さや不安定さの原因が明確になります（目安は Small:Medium:Large = 80:15:5）。

## 5. 自分のプロダクトの形を決める

| プロダクト | 合いやすい形 | 理由 |
|------------|--------------|------|
| 計算・変換が多いライブラリ | ピラミッド | ロジックが本体。Unit で網羅するのが一番安い |
| React / Next.js のフロントエンド | Trophy | バグは部品の組み合わせと操作で出る |
| マイクロサービスのバックエンド | Honeycomb | サービスの API がそのまま契約 |
| モノリスの業務システム | ピラミッド＋厚めの Integration | ドメインロジックと DB 連携の両方が重要 |

判断のための問い：

1. **バグはどこで起きているか？** 過去のバグを見て、ロジック・結合・環境のどれが多いか。
2. **どのレベルのテストが安く書けるか？** ツールとチームの慣れ次第で変わる。
3. **テストが落ちたとき、原因をすぐ見つけられるか？** 上の層ほど難しい。

> 形はあくまで「量のバランス」のたとえです。大事なのは、**同じことを複数の層で重複して確かめず、下の層で確かめられないことだけを上に残す**ことです（[[01_テストレベル]]）。
