# テストデータの用意

テストの Arrange（準備）で一番手間がかかるのが**テストデータ**です。毎回オブジェクトを手書きするとテストが長くなり、共通のデータを使い回すとテスト同士が影響し合います。この章では、フィクスチャ・ファクトリ・ビルダー・シードの使い分けと、データまわりでテストを壊さないための注意点をまとめます。

---

## 1. 用意の仕方

| 方法 | 何か | 向いている場面 |
|------|------|----------------|
| **インライン** | テストの中に直接書く | データが小さく、そのテストでしか使わない |
| **フィクスチャ** | 固定のデータをファイルや定数に置いて共有する | API レスポンスのサンプル、変わらない参照データ |
| **ファクトリ** | デフォルト値つきでオブジェクトを作る関数。必要な項目だけ上書きする | エンティティが多くの項目を持つとき（一番よく使う） |
| **ビルダー** | メソッドチェーンで少しずつ組み立てる | 組み立て方に条件や順序があるとき |
| **シード** | DB に初期データを入れるスクリプト | 統合テスト・E2E テスト |

---

## 2. ファクトリ：テストに関係ある値だけ書く

```ts
// test/factories/user.ts
let seq = 0;
export const buildUser = (overrides: Partial<User> = {}): User => ({
  id: `user-${++seq}`,
  name: 'テスト太郎',
  email: `user${seq}@example.com`,
  isMember: false,
  createdAt: new Date('2026-01-01'),
  ...overrides,
});
```

```ts
test('会員は10%割引される', () => {
  const user = buildUser({ isMember: true }); // このテストで意味があるのは isMember だけ
  expect(calcPrice(1000, user)).toBe(900);
});
```

- テストに**書かれている値＝テストにとって意味のある値**になるので、意図が読み取りやすくなります。
- ID やメールは連番にして、一意制約でぶつからないようにする。
- ライブラリを使う方法もある（`@faker-js/faker` でそれらしい値を作る、`fishery` などのファクトリライブラリ）。ただし**ランダム値は再現性を下げる**ので、シードを固定するか、テストの意図に関わる値は固定にする。

---

## 3. フィクスチャ：共有データの落とし穴

```ts
// ✗ 共有オブジェクトを書き換えると、他のテストに影響する
import { sampleUser } from './fixtures';
test('名前を変更できる', () => {
  sampleUser.name = '変更後'; // 後続のテストでも name が変わったまま
});
```

- 共有データは**読み取り専用**として扱い、書き換えるならコピーするかファクトリを使う。
- フィクスチャが大きくなると、「どのテストがどの項目に依存しているか」が分からなくなる（**謎のゲスト**：テストに見えない場所のデータで結果が決まる状態）。

---

## 4. DB を使うテストのデータ

| 方針 | やり方 | 長所 | 短所 |
|------|--------|------|------|
| **テストごとにトランザクションをロールバック** | 各テストをトランザクションで囲み、最後に戻す | 速い・きれい | テスト対象の中でトランザクションを使うと難しい |
| **テストごとに削除（truncate）** | 各テストの前に全テーブルを空にする | 確実 | 遅くなりやすい |
| **テストごとに別スキーマ・別 DB** | 並列実行のためにワーカーごとに DB を分ける | 並列に強い | 準備が重い |
| **シードを共有して読み取りだけ** | 参照データだけ最初に入れる | 準備が1回で済む | 書き込むテストと混ぜると壊れる |

- 本物の DB を使うなら、Testcontainers などで**テスト専用のコンテナ**を立てると、環境の違いによる不安定さが減ります。
- E2E テストでは、テストの前に API で必要なデータを作ると、UI 操作でデータを作るより速く安定します（[[05_実践パターンとベストプラクティス]]（Playwright））。

---

## 5. 日付・時刻のデータ

- `new Date()` をそのまま使うと、日付が変わるとテストが落ちる（月末・うるう年・タイムゾーン）。
- データには**固定の日時**を入れ、テスト対象の「現在時刻」はフェイクタイマーや引数で固定する（[[05_非同期処理とタイマーのテスト]]）。
- タイムゾーンは CI で `TZ=UTC` などに固定する。

---

## 6. チェックリスト

- [ ] テストの中に書かれている値は、そのテストにとって意味のある値だけか
- [ ] 共有データを書き換えていないか
- [ ] テストの実行順や並列実行でデータがぶつからないか
- [ ] ランダム値や現在時刻で結果が変わらないか
