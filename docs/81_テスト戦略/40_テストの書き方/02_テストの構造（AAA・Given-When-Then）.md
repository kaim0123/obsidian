# テストの構造（AAA・Given-When-Then）

テストコードは本番コード以上に「読まれる」ものです。落ちたときに、何を準備して、何をして、何を期待していたのかがすぐ分かる必要があります。そのための定番の型が **AAA（Arrange-Act-Assert）** と **Given-When-Then** です。

---

## 1. AAA パターン

| 段階 | 意味 | 書くこと |
|------|------|----------|
| **Arrange（準備）** | テストの前提を整える | 入力データ、テスト対象のインスタンス、テストダブル |
| **Act（実行）** | テスト対象を1回動かす | 関数呼び出し、ボタンのクリック |
| **Assert（検証）** | 結果を確かめる | `expect(...)` |

```ts
test('在庫が0の商品はカートに追加できない', () => {
  // Arrange
  const cart = new Cart();
  const item = { id: 'A1', stock: 0 };

  // Act
  const result = cart.add(item);

  // Assert
  expect(result.ok).toBe(false);
  expect(cart.items).toHaveLength(0);
});
```

### 書くときのルール

- **3つの段階を空行で分ける**。コメント `// Arrange` は、慣れたチームなら省いてよい。
- **Act は1行**にする。複数行になるなら、テスト対象の API が使いにくいサイン（または1テストで2つのことを確かめている）。
- **Arrange が長い**ときは、ヘルパー関数やファクトリ（[[05_テストデータの用意]]）に切り出す。
- **Assert の後に Act を続けない**（Act → Assert → Act → Assert）。それは2つのテストに分ける。

---

## 2. Given-When-Then

BDD（振る舞い駆動開発）から来た書き方で、中身は AAA と同じです。**仕様の言葉で書く**点が違います。

| AAA | Given-When-Then | 意味 |
|-----|-----------------|------|
| Arrange | **Given**（前提） | 〜という状況で |
| Act | **When**（操作） | 〜したとき |
| Assert | **Then**（結果） | 〜になる |

```gherkin
Feature: カート
  Scenario: 在庫切れの商品は追加できない
    Given 在庫が 0 の商品「A1」がある
    When  ユーザーが「A1」をカートに追加する
    Then  「在庫切れです」と表示される
    And   カートは空のままである
```

- Cucumber などのツールでは、この文章をそのまま実行できるテストにします。
- ツールを使わなくても、**テスト名や describe の構造に Given-When-Then を反映する**と、仕様書のように読めるテストになります。

```ts
describe('在庫が0の商品があるとき', () => {        // Given
  describe('カートに追加すると', () => {           // When
    test('在庫切れエラーを返す', () => { /* … */ }); // Then
    test('カートは空のままである', () => { /* … */ });
  });
});
```

- 受け入れ基準を Given-When-Then で書いておくと、そのままテストケースになる（87/40_コラボレーションベース）。

## 3. セットアップの共有：beforeEach の使いどころ

```ts
describe('Cart', () => {
  let cart: Cart;
  beforeEach(() => {
    cart = new Cart(); // 毎回新しく作る → テストの独立性を保つ
  });
  // …
});
```

| 共有してよいもの | 共有しないほうがよいもの |
|------------------|--------------------------|
| どのテストでも同じ、意味のない初期化（空のインスタンス作成） | テストごとに意味が違う前提データ |
| DB のリセット、モックの初期化 | 「このテストでは在庫 0」のような条件 |

- **前提がテストの中に書かれていないと、読む人は beforeEach まで遡る必要がある**。テストの意図に関わる準備は、各テストの Arrange に書くほうが読みやすい。

---

## 4. Assert の書き方

- **振る舞いを1つ確かめる**。1つの振る舞いを確かめるために `expect` が複数あるのはよい（例：結果が false で、カートが空）。
- **期待値はリテラルで書く**。本番と同じロジックで期待値を計算すると、ロジックが間違っていてもテストが通る。

```ts
// ✗ 本番のロジックを再実装している
expect(calcTax(1000)).toBe(1000 * TAX_RATE);
// ○ 具体的な値を書く
expect(calcTax(1000)).toBe(100);
```

- 失敗メッセージが分かりやすいマッチャーを選ぶ。`expect(list.length).toBe(0)` より `expect(list).toHaveLength(0)`（失敗時に中身が表示される）。詳しくは [[03_アサーションとexpect完全ガイド]]。
