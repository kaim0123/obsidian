# テストダブルの分類

テスト対象が DB・外部 API・時刻などに依存していると、テストが遅く、不安定になります。そこで本物の代わりに差し込む偽物を**テストダブル**（映画の代役＝スタントダブルから）と呼びます。「モック」と一括りにされがちですが、Gerard Meszaros の『xUnit Test Patterns』では5種類に分けています。区別できると、**何を確かめたいテストなのか**がはっきりします。

---

## 1. 5つの種類

| 種類 | 役割 | 検証するもの | 例 |
|------|------|--------------|----|
| **ダミー（Dummy）** | 引数の穴埋め。使われない | — | 必須引数に渡す空のロガー |
| **スタブ（Stub）** | 決まった値を返して、テスト対象への**入力**を作る | テスト対象の結果 | 「ユーザー取得 API は常に山田さんを返す」 |
| **スパイ（Spy）** | 呼ばれた内容を記録する。本物の処理も通すことがある | 呼び出しの記録（後で確認） | メール送信関数が何回、何の引数で呼ばれたか |
| **モック（Mock）** | 期待する呼び出しを**事前に設定**し、テスト対象からの**出力**を検証する | 呼び出し方そのもの | 「決済 API が金額 900 で1回呼ばれるはず」 |
| **フェイク（Fake）** | 簡易的だが本当に動く実装 | テスト対象の結果 | メモリ上の DB、インメモリのリポジトリ |

### 入力側と出力側で分ける

```
                ┌──────────────┐
  スタブ ──入力→│  テスト対象   │──出力→ モック／スパイ
 （値を返す）   └──────────────┘        （呼ばれ方を確かめる）
```

- **スタブ**は「テスト対象に何かを渡すため」の偽物。スタブが呼ばれたかどうかは確かめない。
- **モック・スパイ**は「テスト対象が外に何かしたか」を確かめるための偽物。

## 2. Vitest での対応

Vitest（Jest も同様）の API は名前が「mock」でも、使い方次第で上のどれにもなります。

```ts
// スタブ：値を返すだけ
const getUser = vi.fn().mockResolvedValue({ id: 1, name: '山田' });

// スパイ：本物を通しつつ呼び出しを記録
const spy = vi.spyOn(logger, 'info');

// モック的な使い方：呼ばれ方を検証
expect(sendMail).toHaveBeenCalledWith('yamada@example.com', expect.any(String));

// フェイク：簡易実装を差し込む
const repo = new InMemoryUserRepository();
```

API の詳細は [[04_モックとスパイ]]（Vitest）、HTTP 通信のモックは MSW（37_HTTPクライアント・ユーティリティ/60_テスト・モック）を参照。

## 3. いつダブルを使うか

### 置き換えるべき依存

| 依存 | 理由 | 使うダブル |
|------|------|------------|
| 外部 API・決済・メール送信 | 遅い、費用がかかる、副作用がある | スタブ（入力）、モック（送信の確認） |
| 現在時刻・乱数 | 結果が毎回変わる | スタブ、フェイクタイマー |
| DB | 遅い・準備が重い | フェイク（インメモリ）、またはテスト用コンテナで本物 |

### 置き換えないほうがよい依存

- **自分たちのコード内の部品同士**。全部モックにすると、部品はそれぞれ正しいのに、つなぐと動かないことを見逃します。
- **値オブジェクト・純粋関数**。本物を使っても速く、決定的です。

### 2つの学派

| | 古典派（デトロイト派） | モック派（ロンドン派） |
|---|------------------------|------------------------|
| 単体の単位 | 1つの**振る舞い**（複数クラスでもよい） | 1つの**クラス** |
| ダブルを使う場所 | 共有される依存・外部依存だけ | 協力するクラスすべて |
| 強み | リファクタリングに強い | 失敗の場所がすぐ分かる、設計を外から考えやすい |
| 弱み | 失敗したとき原因の範囲が広い | 実装に結びつきやすく、リファクタリングで壊れやすい |

- Khorikov は「**アプリケーションの外に見える副作用（メール送信・外部 API 呼び出し）だけをモックする**」ことを勧めています。内部の呼び出しをモックで検証すると、リファクタリングへの耐性が下がる（[[01_良い単体テストの条件]]）。

## 4. よくある失敗

- **モックの設定がテストの大半を占める**：依存が多すぎるサイン。本番コードの設計を見直す（依存を減らす、計算と副作用を分ける）。
- **モックが本物と違う振る舞いをする**：API の仕様が変わってもテストは通り続ける。契約テストや、統合テストで本物との一致を確かめる。
- **モックのリセット忘れ**：前のテストの設定が残り、独立性が壊れる。`afterEach(() => vi.restoreAllMocks())` など。
