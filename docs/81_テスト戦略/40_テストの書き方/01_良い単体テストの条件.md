# 良い単体テストの条件

テストは書けば書くほど良いわけではありません。遅いテスト、たまに落ちるテスト、リファクタリングのたびに壊れるテストは、むしろ開発を遅くします。この章では、**良い単体テストとは何か**を、FIRST 原則と『単体テストの考え方/使い方』（Vladimir Khorikov）の「4本の柱」から整理します。ツールに依存しない話なので、Vitest でも Jest でも pytest でも同じです。

---

## 1. FIRST 原則

『Clean Code』（Robert C. Martin）で紹介された、単体テストが満たすべき5つの性質です。

| 頭文字 | 性質 | 意味 | 破れているサイン |
|--------|------|------|------------------|
| **F** | Fast（速い） | すぐ終わるので気軽に何度も流せる | 全体で数分かかるので、コミット前に流さなくなる |
| **I** | Independent（独立） | 他のテストの結果や実行順に依存しない | 単独で流すと通るが、全体で流すと落ちる |
| **R** | Repeatable（繰り返せる） | どの環境・いつ流しても同じ結果 | 日付・乱数・ネットワークで結果が変わる |
| **S** | Self-validating（自己検証） | 成功か失敗かを自動で判定する | ログを目で見て確認する必要がある |
| **T** | Timely（適時） | 本番コードとほぼ同時に書く | 後回しにした結果、テストしにくい設計が固まる |

### 破れやすいところと対策

- **Independent**：共有の変数・DB・グローバル状態を各テストの前にリセットする。`beforeEach` で毎回作り直す。
- **Repeatable**：現在時刻・乱数・外部 API は引数で渡すか、テストダブルに置き換える（[[04_テストダブルの分類]]）。Vitest なら `vi.useFakeTimers()`（[[05_非同期処理とタイマーのテスト]]）。

## 2. 4本の柱（Khorikov）

Khorikov は、テストの価値を次の4つの掛け算で考えます。どれか1つが 0 なら、そのテストの価値は 0 です。

| 柱 | 意味 |
|----|------|
| **① 退行（リグレッション）に対する保護** | バグが入ったときに、ちゃんと落ちるか |
| **② リファクタリングへの耐性** | 振る舞いを変えずに中身を変えたとき、落ちないか |
| **③ 迅速なフィードバック** | 速く結果が出るか |
| **④ 保守のしやすさ** | 読みやすく、動かすための準備が少ないか |

### ① と ② のトレードオフ

- **偽陰性（バグがあるのに通る）** を減らすのが ①。**偽陽性（バグがないのに落ちる）** を減らすのが ②。
- ②が低いテストの典型は、**内部の実装に結びついたテスト**です。

```ts
// ✗ 実装に結びついている：内部で使う関数の呼ばれ方を確かめている
test('注文を確定すると割引計算関数が1回呼ばれる', () => {
  const spy = vi.spyOn(pricing, 'applyDiscount');
  confirmOrder(order);
  expect(spy).toHaveBeenCalledTimes(1);
});

// ○ 振る舞い（観察できる結果）を確かめている
test('会員は注文確定時に10%割引される', () => {
  const result = confirmOrder({ ...order, isMember: true, subtotal: 1000 });
  expect(result.total).toBe(900);
});
```

- 上のテストは、割引の計算方法を別の関数に移すだけで落ちます。下のテストは、結果が同じなら落ちません。
- **「何をしたか（how）」ではなく「何が起きたか（what）」を確かめる**のが、②を高く保つ基本です。

## 3. テストしやすいコードの形

テストの書きやすさは、本番コードの設計で大きく決まります。

| テストしにくい | テストしやすい |
|----------------|----------------|
| 関数の中で `new Date()`・`fetch` を直接呼ぶ | 時刻や通信を引数や依存として受け取る |
| 計算と保存・送信が1つの関数に混ざっている | 計算（純粋関数）と副作用を分ける |
| グローバルな状態を読み書きする | 状態を引数で受け取り、結果を返す |

- 「計算は純粋関数に、副作用は外側に」（Functional Core, Imperative Shell）にすると、中心のロジックはモックなしで単体テストできます。
- 詳しくは [[01_テストしやすいメソッド設計]]・[[01_テストしやすいクラス設計]]・[[01_テストしやすいコンポーネントと構成]] を参照。

## 4. 何をテストし、何をテストしないか

| テストする | テストしない（しなくてよい） |
|------------|------------------------------|
| ビジネスロジック・計算・条件分岐 | ライブラリやフレームワーク自体の動き |
| 境界値・異常系・エラーの扱い | getter / setter だけの単純なコード |
| バグが出た箇所（再発防止） | private 関数を直接（public 経由で確かめる） |
| 公開された API・コンポーネントの振る舞い | 実装の詳細（呼び出し回数・内部状態） |

## 5. チェックリスト

- [ ] 1テストが数ミリ秒で終わるか
- [ ] 単独でも、どの順番で流しても通るか
- [ ] 時刻・乱数・通信に結果が左右されないか
- [ ] `expect` で結果を自動判定しているか
- [ ] 実装を書き換えても、振る舞いが同じなら通るか
- [ ] テスト名を読めば、何を確かめているか分かるか（[[03_テストの命名と粒度]]）
