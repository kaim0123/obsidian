## 詳しい要約

**テーマ：インデックス（索引）が速い理由は「並び順」**

索引がないと DB は上から全行を見る（フルスキャン）。索引は対象の列を並べ替えた「写し」と元の行の場所を持つもので、並んでいるから半分ずつ捨てて探せる。索引が効くかどうかは「並び順を使える探し方か」で判断でき、後方一致・関数をかけた比較・複合索引の左の列を飛ばす探し方では効かない。

---

### よくある場面

- 手元では一瞬で出る検索が本番だけ遅い（手元の 10 件と本番の 100 万件では違う）。
- 決まった秒数を超えた問い合わせを記録する仕組み（スロークエリの記録）に自分の SQL が載る。
- レビューで「ここインデックス効いてる？」と聞かれる。
- 3 つとも根っこは同じで、**DB が何行を見ているか** が問題。

### 索引がないとき：全部の行を見る

- ユーザー表の行は登録順に並んでおり、名前順ではない。
- 「中村」を探すと、上から 1 行ずつ見るしかない。見つかっても同名の人がいるかもしれないので最後の行まで全部見る。
- 1 万行なら 1 万回、100 万行なら 100 万回の確認。これを **フルスキャン** と呼び、遅い SQL の正体はたいてい行が増えるほど遅くなるこのパターン。

### 索引の正体：並べ替えた写し

- 分厚い技術書で言葉を探すときは巻末の索引を見る。索引は言葉が順に並び、ページ番号が書いてある。
- DB の索引も同じで、名前の列だけを抜き出して五十音順に並べ替えた **写し** に、元の表の何行目にいるかを添えたもの。
- 元の表は登録順のまま動かさず、写しを別に 1 つ持つ（その分の代償は後述）。

### 並んでいると半分ずつ捨てられる（二分探索）

- 真ん中（鈴木）を見て、探す「中村」はそれより後なので前半を丸ごと捨てる。残りの真ん中を見て 2 回で発見し、添えられた行番号（7 行目）へまっすぐ取りに行く。
- この探し方が **二分探索**。1 万行でも 14 回ほど、100 万行でも 20 回ほどで 1 行まで絞れる。行が増えても回数はほとんど増えない。
- 同じ名前は索引の中で隣同士に並ぶので、隣を 1 つ見れば終わる。

### 実際の索引は木の形

- 実際の DB は索引を、根・枝・葉からなる木の形（目次の階層のようなもの）で持つ。根の区切りを見て該当する枝へ、さらに葉へ降りると、名前と行の場所が書いてある。
- 実際の木は 1 つの箱に何百もの区切りが入るので、100 万行でも 1 億行でも 3〜4 段で葉に届く。1 段降りるたびに箱を 1 つ読むだけなので速い。

### コードで見る：作って確かめる

- `SELECT ... WHERE name = '中村'` のような素朴な SQL に対し、**CREATE INDEX** で並べ替える列を指定するだけで写しができる。
- 効いているかは SQL の頭に **EXPLAIN** をつけると、実行前に DB がどう探すつもりかを教えてくれる。
  - MySQL の例: 作る前は type が **ALL**（全行を見る）、key が NULL（使った索引なし）、rows（見込みの行数）が 1 万。
  - 作った後は type が **ref**、key に作った索引の名前、rows が 1。
- 「インデックス効いてる？」と聞かれたら EXPLAIN を見せればよい。

### 範囲で探す・並べ替える

- 「さ行で始まる人全員」のような範囲検索も効く。木をたどってさ行の始まり（佐藤）の葉まで降り、葉同士が横につながっているので隣へ進み、さ行を外れたところで止める。並んでいるからどこで止めるかも分かる。
- 並べ替え（ORDER BY）も、葉を左から横に読むだけで済み、並べ替える手間が丸ごといらない。「新しい順」の画面では日付列の索引が効く。

### 索引が効かない探し方

- **前方一致**（「中」で始まる名前）は効く。索引は頭の文字から並んでいるので半分ずつ捨てられる。
- **後方一致**（「村」で終わる名前）は効かない。頭の文字が何でもありうるので捨てる手がかりがなく、全部見ることになる（電話帳で下の名前だけで探すようなもの）。
- **列に関数をかけてから比べる** 書き方（例: メールアドレスを小文字に直して比較）も効かない。索引に並んでいるのは直す前の値で、直した後の順には並んでいない。

### 2 つの列を組み合わせた索引（複合索引）

- 都道府県 → 年齢の順で作った索引は、まず都道府県順に、同じ都道府県の中で年齢順に並ぶ。
- 「東京で 29 歳」はまず東京の塊に絞り、その中で年齢順に探せるので速い。
- 「都道府県を指定せず 20 代」は、年齢が各都道府県の塊の中でしか並んでいないためバラバラに散っており、結局全部見る（電話帳が苗字順で下の名前だけでは引けないのと同じ）。
- 複合索引は **左の列から順にしか使えない**。どの列を左に置くかは、どんな探し方をするかで決める。

### 索引の代償

- 新しい行を登録すると、表の末尾に足すだけでなく、並び順を保つために写しの正しい位置にも差し込む必要がある。索引が 5 つあれば 5 つの写しを全部直す。
- 写しの分だけディスクの容量を使う。
- 探すのは速くなるが書き込みは少しずつ遅くなる。ログのように書いてばかりでほとんど探さない表に索引を貼りすぎると損の方が大きい。
- 実際によく使う探し方に合わせて、必要な分だけ貼るのが基本。

### AI に SQL を書かせたときに見る点

1. 検索条件に使っている列に索引があるか（AI はどんな索引があるかを知らずに書くことが多く、手元はデータが少ないので遅さにも気づけない）。
2. EXPLAIN で全行を見ていないか確かめる（type が ALL で、見込みの行数が表の行数とほぼ同じなら全部見ている）。
3. 後方一致の検索や、列に関数をかけた比べ方になっていないか。
4. 複合索引なら左の列から使う探し方になっているか。
5. 速くするためにと索引を次々に足していないか（足しすぎると書き込みが遅くなる）。

### まとめ

- 索引がないと DB は全行を見る。行が増えるほど遅くなる。
- 索引は列を並べ替えた写しと元の行の場所。並んでいるから半分ずつ捨てられ、実際は木の形で 3〜4 段たどるだけ。
- 並び順を使えない探し方（後方一致、関数をかけた列、複合索引の左の列を飛ばす）には索引は効かない。木の段数や箱の大きさの計算は知らなくてよい。
- 遅い SQL に出会ったら EXPLAIN を見る。
