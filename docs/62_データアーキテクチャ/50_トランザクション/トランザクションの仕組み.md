## 詳しい要約

**テーマ：トランザクション・ACID・分離レベルの仕組み**

送金を例に、複数の処理をひとまとまりにする**トランザクション**の必要性と、それを支える ACID 特性、分離レベルごとに起きる異常（ダーティリード等）、MySQL と PostgreSQL の並行制御の違いを解説するショート動画。

---

### なぜトランザクションが必要か

- A から B へ 200 ドル送金するには「A から引く」「B に足す」の 2 ステップが必要
- 引いた直後にサーバーが落ちると 200 ドルが消えてしまう
- そこで 2 ステップを 1 単位にまとめる。**BEGIN** で開始し **COMMIT** で確定、途中でエラーに気づけば **ROLLBACK** で全て取り消す

### ACID

- **A（原子性 / Atomicity）**：全部成功か全部失敗か。部分的な成功は許さない
- **C（一貫性 / Consistency）**：ルールを破る変更（残高がマイナスになる更新など）は拒否
- **I（独立性 / Isolation）**：同時実行の処理が干渉しない。未コミットの変更は他から見えない。PostgreSQL は行のバージョンを増やし、MySQL はログから古い値を復元する
- **D（永続性 / Durability）**：コミット後は停電しても残る。**WAL（Write-Ahead Logging）**が支える

### 分離レベルと異常現象

強い順に **Serializable → Repeatable Read → Read Committed → Read Uncommitted**。Serializable は 1 つずつ順に実行したのと同じ結果を保証し、弱い 3 つは許す現象で説明できる。

| 現象 | 内容 |
|---|---|
| **ダーティリード** | A が未コミットで残高を 0 にした値を B が読む。A がロールバックすると存在しなかった値になる |
| **ノンリピータブルリード** | B が同じ行を 2 回読む間に A が更新・コミットし、1 回目 200、2 回目 0 になる |
| **ファントムリード** | B が同じ条件で 2 回検索する間に A が行を挿入・コミットし、2 回目に行が増える |

### MySQL と PostgreSQL の並行制御

- **MySQL**：同じ行に同時アクセスがあると行をロックして順番待ちさせる。待ちが循環すると**デッドロック**となり片方が終了させられる
- **PostgreSQL**：待たせず、何を使ったかを記録しておき、衝突を検知したらその場で片方を止める

### まとめ

- トランザクションは複数処理を「全部か無か」で確定させる仕組み
- ACID と分離レベルで保証の強さを選ぶ。弱いレベルほどダーティ／ノンリピータブル／ファントムリードを許す
- ロックで待たせるか、衝突検知で止めるかは DB によって異なる


**0:00** · How transactions work. Transferring $ 200 from person A to person B. There are two steps: subtract from A and add to B. But if the server crashes right after subtracting, the $ 200 vanishes.

**0:11** · So, we group these two steps into one unit. This is a transaction. Start with BEGIN and finalize with COMMIT. Changes are applied all at once at the moment of commit. If you notice an error halfway, ROLLBACK cancels everything.

**0:24** · This set of guarantees is called ACID.

**0:26** · A is Atomicity: everything succeeds or everything fails. Partial success is not allowed. C is Consistency: changes that break rules are rejected. An update that would make the balance negative is blocked. I is Isolation: concurrent processes don't interfere with each other. Uncommitted changes remain invisible to others. Postgres increases row versions; MySQL restores old values from logs. D is Durability: once committed, data survives power loss. Write-Ahead Logging (WAL) supports this. You choose the strength of isolation via isolation levels.

**0:57** · The four levels from strongest to weakest are Serializable, Repeatable Read, Read Committed, and Read Uncommitted; Serializable guarantees the same result as running one by one. The three weaker levels can be explained by the phenomena they permit. At the loosest level, you can even see pre-commit values. A sets the balance to 0 but hasn't committed yet. B reads that 0.

**1:19** · If A rolls back, that value never existed. This is a dirty read. Next is the case where B reads the same row twice. If A updates and commits in between, the first read is $ 200, the second is $ 0. This is a non-repeatable read. Lastly, the case where B searches twice with the same criteria. If A inserts a row and commits in between, there is an extra row on the second search. This is a phantom read. If multiple users access the same row at once, MySQL locks the row and makes them wait in line. If a wait cycle occurs, a deadlock happens and one side is terminated.

**1:51** · Postgres doesn't make you wait; it keeps a record of what was used. If a conflict is detected, it stops one of the processes on the spot.

**1:57** · This is how transaction mechanisms work .
