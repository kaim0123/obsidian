# 非正規化と実務での判断

[[MOC_データアーキテクチャ体系|📚 目次]] ｜ [[02_正規化|← 前へ]] ｜ [[04_キーと制約の設計|次へ →]]

> [!abstract] この記事で分かること
> - 正規化したテーブルをあえて崩す「非正規化」の動機（JOIN コスト、集計値のキャッシュ）
> - 代表的な手法：冗長列、集計テーブル、マテリアライズドビュー、JSONB
> - 崩したデータの整合性を守る 3 つの方法（トリガー、アプリ、バッチ）と使い分け
> - 「本当に非正規化すべきか」を判断するチェックリスト
> - 注文時価格 `unit_price` のような「履歴として保存すべき値」は非正規化ではないこと
>
> **前提**：[[02_正規化]] を読んでいると理解しやすいです。

## 1. ひとことで言うと

正規化したデータベースは「原本だけが置いてある書庫」です。間違いは起きませんが、毎回あちこちの棚から原本を集めて（JOIN して）コピーを作る手間がかかります。**非正規化（Denormalization）**は、よく使う資料の**コピーを手元に置いておく**ことです。速くなる代わりに、原本が変わったらコピーも直す責任を負います。

> [!info] 要点
> - 非正規化は「整合性を保つ手間」と「読み取りの速さ」の**交換**。タダではない
> - **原本（正規化されたテーブル）は残したまま**、読み取り用のコピーを足すのが基本形
> - 「計測して遅いと分かってから」行う。最初からの非正規化は早すぎる最適化になりやすい

## 2. 非正規化の動機

### 2.1 JOIN のコスト

正規化するとテーブルが増え、1 画面を出すのに JOIN が増えます。JOIN 自体は RDB の得意技で、インデックスが適切なら数テーブルの JOIN はたいてい問題になりません。問題になるのは次のような場合です。

- 一覧画面で**大量の行**それぞれに JOIN が必要（例：商品一覧 1 万件 × カテゴリ名）
- JOIN した結果で**並べ替え・絞り込み**したいが、条件が複数テーブルにまたがってインデックスが効かない（[[04_インデックスが効かないパターン]]）
- アクセス頻度が極端に高く、わずかなコストでも積み重なる

### 2.2 集計値のキャッシュ

もう 1 つの大きな動機は**毎回計算すると重い値**です。

- 注文の合計金額：`SUM(quantity * unit_price)` を注文一覧のたびに計算
- 商品のレビュー件数・平均評価：商品一覧のたびに `COUNT`・`AVG`
- 日別・カテゴリ別の売上：管理画面のダッシュボードが全注文を走査

行数が増えるほど計算は重くなります。結果を保存しておけば読み取りは一瞬ですが、元データが変わったら更新が必要です。

## 3. 非正規化の手法

### 3.1 冗長列（Redundant Column）

別テーブルの値を、JOIN を省くために**コピーして持つ**列です。

```sql
-- 商品一覧で毎回 categories と JOIN しないよう、カテゴリ名を持たせる
ALTER TABLE products ADD COLUMN category_name TEXT;

UPDATE products p
SET    category_name = c.name
FROM   categories c
WHERE  c.id = p.category_id;
```

これで `products` 単独で「カテゴリ名で並べ替え」ができます。代償として、カテゴリ名を変えたら products の該当行もすべて更新しなければなりません（[[02_正規化]] の更新異常そのもの）。

**導出列（計算結果を持つ列）**も冗長列の一種です。

```sql
ALTER TABLE orders ADD COLUMN total_amount INTEGER NOT NULL DEFAULT 0;
```

> [!tip] 生成列（Generated Column）
> 同じ行の列だけから計算できる値なら、PostgreSQL 12 以降の**生成列**を使うと DB が自動で同期します。例：`subtotal INTEGER GENERATED ALWAYS AS (quantity * unit_price) STORED`。別テーブルを参照する値（合計金額など）には使えません。MySQL 5.7 以降にも生成列があります。

### 3.2 集計テーブル（Summary Table）

集計結果を**別のテーブル**として持ちます。元テーブルは一切崩さないのが利点です。

```sql
CREATE TABLE daily_sales (
  sales_date  DATE    NOT NULL,
  category_id BIGINT  NOT NULL,      -- カテゴリ未設定は 0 に寄せる
  amount      BIGINT  NOT NULL,
  order_count INTEGER NOT NULL,
  PRIMARY KEY (sales_date, category_id)
);

-- 夜間バッチで「昨日分」を作り直す（何度実行しても同じ結果になる＝冪等）
INSERT INTO daily_sales (sales_date, category_id, amount, order_count)
SELECT (o.ordered_at AT TIME ZONE 'Asia/Tokyo')::date,
       COALESCE(p.category_id, 0),
       SUM(oi.quantity * oi.unit_price),
       COUNT(DISTINCT o.id)
FROM   orders o
JOIN   order_items oi ON oi.order_id = o.id
JOIN   products p     ON p.id = oi.product_id
WHERE  o.status <> 'cancelled'
  AND  (o.ordered_at AT TIME ZONE 'Asia/Tokyo')::date = CURRENT_DATE - 1
GROUP  BY 1, 2
ON CONFLICT (sales_date, category_id)
DO UPDATE SET amount = EXCLUDED.amount, order_count = EXCLUDED.order_count;
```

`ON CONFLICT ... DO UPDATE`（いわゆる UPSERT）は PostgreSQL の構文です。MySQL では `INSERT ... ON DUPLICATE KEY UPDATE` を使います。

### 3.3 マテリアライズドビュー（Materialized View）

**ビュー（View）**は SELECT 文に名前を付けたもので、参照するたびに中の SELECT が実行されます。**マテリアライズドビュー**は、その結果を**実体として保存**したビューです。集計テーブルを DB に管理させるイメージです。

```sql
CREATE MATERIALIZED VIEW product_review_stats AS
SELECT p.id AS product_id,
       COUNT(r.id)                  AS review_count,
       COALESCE(AVG(r.rating), 0)   AS avg_rating
FROM   products p
LEFT JOIN reviews r ON r.product_id = p.id
GROUP  BY p.id;

-- CONCURRENTLY で更新するには UNIQUE インデックスが必要
CREATE UNIQUE INDEX ON product_review_stats (product_id);

-- 定期的に再計算（CONCURRENTLY なら更新中も SELECT をブロックしない）
REFRESH MATERIALIZED VIEW CONCURRENTLY product_review_stats;
```

- 良い点：定義が SQL 1 本で済み、同期ロジックを自分で書かなくてよい
- 注意点：PostgreSQL のマテリアライズドビューは**自動では更新されません**。`REFRESH` するまで古い値のままで、更新は毎回**全件の再計算**です（差分更新ではない）
- MySQL にはマテリアライズドビューがないため、集計テーブル＋バッチで代用します

### 3.4 JSONB に埋め込む

PostgreSQL の **JSONB**（バイナリ形式の JSON 型）に、関連データをまとめて 1 列に持たせる手法です。ドキュメント DB（[[07_NoSQLのデータモデル]]）の発想を RDB に持ち込むものです。

```sql
-- 注文時点の配送先を、そのままの形で保存する
ALTER TABLE orders ADD COLUMN shipping_address JSONB;

UPDATE orders
SET shipping_address = '{"zip":"100-0001","pref":"東京都","city":"千代田区","line1":"1-1"}'
WHERE id = 1;

SELECT shipping_address->>'pref' FROM orders WHERE id = 1;  -- 東京都
```

- 向いている：まとめて読み書きし、中身で JOIN しないデータ（スナップショット、外部 API の応答、カテゴリごとに項目が違う商品スペック）
- 向いていない：中身の一部を頻繁に更新する、中身で絞り込み・集計・JOIN する、中身に制約（NOT NULL、外部キー）をかけたいデータ

何でも JSON に入れる設計は [[05_設計パターンとアンチパターン]] で扱うアンチパターンです。

## 4. 整合性の守り方

コピーを持つ以上、「誰が、いつ、どうやって同期するか」を必ず決めます。

```
                 即時性   取りこぼし   DB負荷/書き込み遅延   向いているもの
トリガー         ◎即時    ◎なし        △書き込みが重くなる   合計金額などの小さな導出値
アプリで同時更新 ○即時    △経路漏れ    ○                     更新経路が1か所に限られる値
バッチ/REFRESH   △遅れる  ○再計算で回復 ○夜間などに集中      ダッシュボード・ランキング
```

### 4.1 トリガー

**トリガー（Trigger）**は、INSERT/UPDATE/DELETE が起きたときに DB が自動で実行する処理です。どの経路（アプリ、管理画面、手作業の SQL）から変更されても同期されるのが最大の利点です。

```sql
CREATE FUNCTION refresh_order_total() RETURNS trigger
LANGUAGE plpgsql AS $$
DECLARE
  target BIGINT;
BEGIN
  IF TG_OP = 'DELETE' THEN
    target := OLD.order_id;
  ELSE
    target := NEW.order_id;
  END IF;

  -- 差分の足し引きではなく「その注文の明細から計算し直す」と、ずれが残らない
  UPDATE orders
  SET    total_amount = (SELECT COALESCE(SUM(quantity * unit_price), 0)
                         FROM order_items WHERE order_id = target)
  WHERE  id = target;
  RETURN NULL;   -- AFTER トリガーなので戻り値は使われない
END;
$$;

CREATE TRIGGER order_items_total
AFTER INSERT OR UPDATE OR DELETE ON order_items
FOR EACH ROW EXECUTE FUNCTION refresh_order_total();
```

注意点：処理がアプリのコードから見えにくく「なぜか値が変わる」と混乱を招きます。書き込みのたびに処理が走るので、大量更新では遅くなり、同じ親行への同時更新はロック待ちになります（[[03_ロックとMVCC]]）。

### 4.2 アプリケーションで同時に更新する

アプリのコードで、原本の更新とコピーの更新を**同じトランザクション内**で行います。

```sql
BEGIN;
UPDATE categories SET name = '文房具' WHERE id = 1;
UPDATE products   SET category_name = '文房具' WHERE category_id = 1;
COMMIT;
```

処理が見えやすくテストもしやすい一方、**別の更新経路**（管理画面、別サービス、手作業の SQL）が 1 つでもあると漏れます。トランザクションで囲まないと、途中で失敗したときに片方だけ更新された状態が残ります（[[01_トランザクションとACID]]）。

### 4.3 バッチ・定期再計算

一定時間ごとに原本から**全部作り直す**方法です。集計テーブルやマテリアライズドビューの更新はこれに当たります。遅れは許容しなければなりませんが、「作り直せば必ず正しくなる」ので、トリガーやアプリ更新の**保険**として併用されることも多いです（例：普段はトリガー、夜間に全件チェック）。

## 5. 非正規化ではないもの：履歴として保存すべき値

`order_items.unit_price` は `products.price` のコピーに見えますが、**非正規化ではありません**。

- `products.price`：**今の**販売価格。値上げ・セールで変わる
- `order_items.unit_price`：**その注文のときに**お客さんと合意した価格。注文後は変わってはいけない

2 つは**別の事実**で、関数従属で言えば `unit_price` は `(order_id, product_id)` で決まります（[[02_正規化]]）。だからこれを `products.price` と同期させてはいけません。同期させると、値上げした瞬間に過去の請求額が書き換わる**バグ**になります。

同じ性質の値は意外と多くあります。

| 値 | 保存先 | 理由 |
|---|---|---|
| 注文時の単価 | `order_items.unit_price` | 後の値上げで請求額が変わってはいけない |
| 注文時の配送先 | `orders.shipping_address` | 会員が住所を変えても、送った先は変わらない |
| 注文時の商品名 | `order_items.product_name`（必要なら） | 商品名変更・削除後も明細や領収書を再現する |
| 適用した税率 | `orders.tax_rate` | 税率改定後も過去の税額を再計算できる |

見分け方は「**元の値が変わったとき、こちらも変わるべきか？**」です。変わるべきなら冗長コピー（非正規化）で同期が必要、変わってはいけないならスナップショット（履歴）で同期してはいけません。

## 6. 判断チェックリスト

非正規化する前に、次を上から順に確認します。

- [ ] **計測したか**：遅いクエリを `EXPLAIN ANALYZE` で確認したか（[[05_実行計画の読み方]]）。「遅そう」は根拠にならない
- [ ] **インデックスで解決しないか**：JOIN キーや絞り込み列のインデックス不足が原因であることが最も多い
- [ ] **クエリの書き方で解決しないか**：N+1 問題（[[17_ORMとは]]）、不要な列の取得、ページングの方法
- [ ] **キャッシュで解決しないか**：アプリ側のキャッシュ（Redis など）で十分ではないか（[[MOC_パフォーマンス体系]]）
- [ ] **読み取り専用の場所に逃がせないか**：集計テーブル・マテリアライズドビューなら原本を崩さずに済む
- [ ] **鮮度の要件は**：数分〜1 日遅れてよいならバッチ、即時が必要ならトリガーかアプリ更新
- [ ] **同期の責任者は**：トリガー・アプリ・バッチのどれで、全更新経路をカバーできるか
- [ ] **ずれたときの直し方は**：原本から再計算するスクリプトを用意したか
- [ ] **ドキュメントに残したか**：列のコメント（`COMMENT ON COLUMN`）に「何のコピーで、誰が同期するか」を書いたか

分析用途が中心なら、本番 DB で頑張るより分析基盤へ切り出すほうが筋がよいことも多いです（[[01_OLTPとOLAP]]）。

## よくある誤解・つまずき

- ❌ 正規化すると遅い、だから最初から非正規化しておく → ✅ 遅さの原因の多くはインデックス不足やクエリの書き方です。計測してから判断します。
- ❌ 注文時価格を持つのは非正規化だから避けるべき → ✅ 注文時価格は別の事実（スナップショット）で、持たないほうがバグです。
- ❌ マテリアライズドビューは元テーブルが変わると自動で更新される → ✅ PostgreSQL では `REFRESH MATERIALIZED VIEW` を実行するまで古い値のままです。
- ❌ 冗長列はアプリで一緒に更新すれば安全 → ✅ 管理画面・バッチ・手作業 SQL など他の更新経路があると漏れます。全経路を確認するか、トリガー・再計算バッチで保険をかけます。
- ❌ JSONB に入れればスキーマ変更が不要で楽 → ✅ 制約・型・JOIN の恩恵を失い、中身の構造の管理がアプリ任せになります。

## まとめ

- 非正規化の動機は **JOIN コストの削減** と **重い集計値のキャッシュ**
- 手法は **冗長列 / 集計テーブル / マテリアライズドビュー / JSONB**。原本を残してコピーを足す形が安全
- 同期方法は **トリガー（即時・漏れなし）/ アプリ（見やすいが経路漏れ）/ バッチ（遅れるが作り直せる）**
- **注文時価格などのスナップショットは非正規化ではない**。「元が変わったら変わるべきか」で見分ける
- まず計測、次にインデックス・クエリ・キャッシュを検討し、それでも必要なときに非正規化する

## 確認クイズ

1. 商品一覧に「レビュー平均」を表示したい。数分の遅れは許容される。どの手法が向いていますか？
> [!tip]- 答え
> マテリアライズドビュー（または集計テーブル）を定期的に `REFRESH` / 再計算する方法が向いています。原本の reviews を崩さず、鮮度要件（数分遅れ OK）も満たし、ずれても作り直せば回復します。

2. `orders.user_name`（注文者の名前のコピー）と `orders.shipping_address`（注文時の配送先）は、会員情報が変わったときにそれぞれ更新すべきですか？
> [!tip]- 答え
> `user_name` が「今の会員名を表示するためのコピー」なら更新が必要（非正規化）です。`shipping_address` は「実際に送った先」というスナップショットなので更新してはいけません。同じ「ユーザー由来の値」でも意味によって扱いが逆になります。

3. トリガーで合計金額を `total_amount = total_amount + NEW.quantity * NEW.unit_price` のように差分加算せず、毎回明細から再計算しているのはなぜですか？
> [!tip]- 答え
> 差分加算は UPDATE・DELETE の扱いを 1 つ間違えたり、トリガー導入前のデータがあったりすると、ずれが永久に残るからです。再計算方式なら、どの操作の後でも必ず明細と一致します（その分、明細が非常に多い注文では重くなります）。
