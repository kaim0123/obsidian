# レスポンスの型とランタイム検証

> **ひとことで言うと**：`res.json() as User` は「User だと**信じる**」だけで、実際の中身は確かめていない。サーバーから来るデータは外部入力なので、**Zod などのスキーマで実行時に確かめてから**型を付けると、「undefined のプロパティを読んで画面が真っ白」を入口で止められる。

## たとえ話で理解する

宅配便の伝票に「中身：りんご」と書いてあっても、開けたらみかんかもしれない。`as User` は伝票を信じて冷蔵庫に入れること。スキーマ検証は**受け取るときに箱を開けて確かめる**こと。

## 型だけ付ける場合の問題

```ts
const user = (await res.json()) as User; // コンパイルは通る
user.profile.name;                       // サーバーが profile を返さなくなったら実行時エラー
```

- TypeScript の型は**コンパイル時に消える**。実行時には何もチェックしていない
- バックエンドの変更・古いAPIバージョン・プロキシのエラーページなどで簡単に崩れる

## Zod で確かめる

```ts
import { z } from "zod";

export const userSchema = z.object({
  id: z.number(),
  name: z.string(),
  email: z.email(),
  createdAt: z.coerce.date(),   // 文字列 → Date に変換もできる
});
export type User = z.infer<typeof userSchema>; // 型はスキーマから作る（二重管理しない）

const user = userSchema.parse(await res.json()); // 形が違えば ZodError
```

- `parse` は失敗時に例外、`safeParse` は `{ success, data, error }` を返す
- 型を別に書かず `z.infer` で作るので、スキーマと型がずれない

### ky v2 は Standard Schema に対応

Zod・Valibot など Standard Schema 準拠のスキーマを `.json()` に渡すと、検証済みの型付きデータが返る。

## どこまで検証するか

| 方針 | 向いている場面 |
|---|---|
| すべてのレスポンスを検証 | 外部API、バックエンドと別チーム、壊れると困る金額・権限データ |
| 開発時だけ検証（本番は型のみ） | 大量データで検証コストが気になる |
| 型のみ（OpenAPI 生成） | バックエンドと同じリポジトリで型が保証されている |

検証に失敗したら、**エラー監視に送る**と「バックエンドがこっそり形を変えた」ことに早く気づける。
