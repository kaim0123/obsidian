# トークンの付与と自動更新

> **ひとことで言うと**：認証情報は「Cookie で自動的に送られる」方式と「`Authorization: Bearer` ヘッダーに自分で付ける」方式がある。ヘッダー方式では、401 が返ったら**リフレッシュを1回だけ行い、その間に来た他のリクエストは待たせて**、終わったらまとめて再送する。

認証そのものの仕組み（OAuth・JWT・セッション）は 73_認証認可 / 74_セッション管理 が本拠地。ここでは「HTTPクライアントにどう組み込むか」だけを扱う。

## 2つの方式

| 方式 | クライアントの仕事 | 注意点 |
|---|---|---|
| Cookie（セッション・HttpOnly Cookie） | 別オリジンなら `credentials: "include"`（Axios は `withCredentials: true`） | CSRF 対策が必要。サーバー側で CORS の `Access-Control-Allow-Credentials` |
| Bearer トークン | リクエスト前フックで `Authorization` ヘッダーを付ける | トークンの保存場所（localStorage は XSS で盗まれうる）。メモリ保持＋リフレッシュは HttpOnly Cookie が定番 |

## 401 → リフレッシュ → 再送

### 素朴に書くと起きる問題

画面を開いた瞬間に5本のリクエストが同時に401になると、**リフレッシュが5回走る**。リフレッシュトークンが1回使うと無効になる方式（ローテーション）だと、2回目以降が失敗してログアウトされてしまう。

### 解決：リフレッシュを1本にまとめる（single flight）

```ts
let refreshing: Promise<string> | null = null;

function refreshOnce(): Promise<string> {
  // 実行中ならその Promise を共有する
  refreshing ??= fetch("/auth/refresh", { method: "POST", credentials: "include" })
    .then(async (res) => {
      if (!res.ok) throw new Error("refresh failed");
      const { accessToken } = await res.json();
      setAccessToken(accessToken);
      return accessToken;
    })
    .finally(() => { refreshing = null; });
  return refreshing;
}

export async function authFetch(input: string, init: RequestInit = {}, retried = false) {
  const res = await fetch(input, withAuth(init, getAccessToken()));
  if (res.status !== 401 || retried) return res;

  try {
    const token = await refreshOnce();
    return authFetch(input, withAuth(init, token), true); // 1回だけ再送
  } catch {
    emit("auth:expired"); // 画面側でログイン画面へ
    return res;
  }
}
```

ポイント：

- `refreshing` を共有するので、同時に何本401になってもリフレッシュは1回
- `retried` フラグで**無限ループを防ぐ**（リフレッシュ後もまだ401なら諦める）
- リフレッシュ用のリクエスト自体には、このリトライ処理をかけない
- 画面遷移はイベントで知らせ、クライアントは画面を知らないままにする

ky なら `afterResponse` フック、Axios ならレスポンスインターセプターに同じ考え方で書く。

## 先回り更新

JWT の `exp`（有効期限）を見て、切れる少し前にリフレッシュしておくと401自体が減る。ただし端末の時計のずれがあるので、401 時の処理は残しておく。
