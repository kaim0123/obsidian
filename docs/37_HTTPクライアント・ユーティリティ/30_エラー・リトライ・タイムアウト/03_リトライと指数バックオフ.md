# リトライと指数バックオフ

> **ひとことで言うと**：一時的な失敗（回線の瞬断・503）はもう一度送れば成功することが多い。ただし**何度送っても安全なリクエストだけ**を、**だんだん間隔を広げながら（指数バックオフ）、少しずつずらして（ジッター）**、**回数に上限をつけて**送り直す。

## たとえ話で理解する

混んでいる店に電話がつながらないとき：

- 1秒ごとに鬼電する → 店はもっとパンクする（全員がそうすると回線が落ちる）
- 1秒後、2秒後、4秒後、8秒後…と**間隔を倍にしていく** → 指数バックオフ
- みんなが同時にかけ直さないよう**少しずつずらす** → ジッター
- 5回だめなら諦める → 上限回数

## リトライしてよいか：冪等性

**冪等（べきとう）**：同じリクエストを何回送っても結果が1回と同じになること。

| メソッド | 冪等？ | 自動リトライ |
|---|---|---|
| GET / HEAD / OPTIONS | ○ | してよい |
| PUT / DELETE | ○（正しく作られていれば） | してよい |
| POST / PATCH | × | **しない**（注文が2つできる） |

POST をリトライしたいなら、サーバーが **Idempotency-Key**（冪等キー）ヘッダーに対応している必要がある。同じキーの2回目は「もう処理済み」として同じ結果を返してもらう仕組み（決済APIでよく使う）。

## リトライしてよいか：ステータス

| リトライする | リトライしない |
|---|---|
| ネットワークエラー、タイムアウト | 400, 401, 403, 404, 422（何度送っても同じ） |
| 408, 429, 500, 502, 503, 504 | 自分のコードのバグ（TypeError など） |

429 や 503 で `Retry-After` ヘッダーが返ってきたら、その秒数を優先して待つ。

## 待ち時間の計算

```ts
// 指数バックオフ + フルジッター
function backoff(attempt: number, base = 300, max = 10_000) {
  const exp = Math.min(max, base * 2 ** attempt); // 300, 600, 1200, 2400 …
  return Math.random() * exp;                     // 0〜exp の間でばらす
}
```

## ライブラリでの指定

### ky（v2）

既定で GET などの冪等メソッドを、上記のようなステータスのときに最大2回リトライする。v2 からネットワーク起因の失敗だけを自動リトライ対象にし、プログラムのバグではリトライしなくなった。

```ts
const api = ky.create({
  retry: {
    limit: 3,
    methods: ["get", "put", "delete"],
    statusCodes: [408, 429, 500, 502, 503, 504],
    backoffLimit: 10_000,
  },
  totalTimeout: 30_000, // リトライ込みの上限
});
```

### Axios

本体にはリトライ機能が無い。`axios-retry` を足すか、レスポンスインターセプターで自作する。

### TanStack Query との二重リトライに注意

TanStack Query も既定で失敗したクエリを3回リトライする。HTTPクライアントでも2回リトライすると、最悪 3×3＝9回以上送ることになる。**どちらか一方に寄せる**（例：クライアント側は `retry: 0` にして Query に任せる、または Query を `retry: false`）。
