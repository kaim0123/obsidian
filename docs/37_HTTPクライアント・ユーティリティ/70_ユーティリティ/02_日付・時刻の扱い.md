# 日付・時刻の扱い

> **ひとことで言うと**：標準の `Date` は「タイムゾーンが曖昧」「月が0始まり」「書き換え可能」と罠が多い。**通信やDBでは UTC の ISO 8601 文字列でやり取りし、表示するときだけ利用者のタイムゾーンに直す**のが基本。道具は date-fns（今の定番）か、これからの標準 Temporal。

## たとえ話で理解する

海外の友人と「明日の9時に電話」と約束すると、どこの9時かで揉める。**「世界共通の時計（UTC）で何時」と決めておき、それぞれが自分の国の時刻に読み替える**のが安全。

## Date の代表的な罠

| 罠 | 例 |
|---|---|
| 月が0始まり | `new Date(2026, 0, 1)` は1月1日 |
| 文字列の解釈が形式で変わる | `new Date("2026-09-25")` は **UTC** の0時、`new Date("2026-09-25T00:00")` は **ローカル** の0時 |
| 書き換え可能（ミュータブル） | `d.setDate(d.getDate() + 1)` で元の値が変わる。共有していると事故 |
| タイムゾーンを持たない | 中身は「1970年からのミリ秒」だけ。表示時に実行環境のTZが使われる（サーバーとブラウザで結果が変わる） |

## 基本ルール

1. **やり取りは ISO 8601 の UTC**：`"2026-09-25T03:00:00Z"`。API の設計段階で決める（45_API設計）
2. **受け取ったらすぐ変換**：APIレイヤーで文字列 → 日時オブジェクトに（Zod の `z.coerce.date()` など）
3. **計算は日時オブジェクトで**：足し算・比較は文字列でやらない
4. **表示の直前でローカライズ**：`Intl.DateTimeFormat` やライブラリの format
5. **「日付だけ」と「日時」を区別する**：誕生日や締切日は時刻もタイムゾーンも持たない「日付」。UTC に変換すると前日にずれることがある

## 道具の選び方（2026年）

| 道具 | 特徴 | 向いている場面 |
|---|---|---|
| **Intl.DateTimeFormat / Intl.RelativeTimeFormat** | 標準。表示の整形と「3分前」表示 | 表示だけならまずこれ |
| **date-fns** | 関数単位で読み込める。`Date` を変更しない。v4 でタイムゾーン対応（`@date-fns/tz`） | 今の定番。新規でも既存でも |
| Day.js | 2KB。Moment.js と似た書き方 | Moment.js からの移行 |
| **Temporal** | 標準化された新しい日時API。不変・タイムゾーン・暦を正しく扱う。`PlainDate`（日付だけ）などの型が分かれている | これからの本命。未対応環境ではポリフィル |
| Moment.js | メンテナンスモード | 新規では使わない |

### Temporal の雰囲気

```ts
const today = Temporal.Now.plainDateISO();           // 2026-09-25（日付だけ）
const due = today.add({ days: 7 });                   // 元の値は変わらない
const meeting = Temporal.ZonedDateTime.from("2026-09-25T09:00[Asia/Tokyo]");
meeting.withTimeZone("America/New_York").toString(); // 同じ瞬間をNY時刻で
```
