# DBダウン・DB遅延

データベースに接続できない、またはクエリが極端に遅くなる障害です。ほとんどの機能が DB に依存しているため、**影響が全体に広がりやすい** 障害の代表です。このノートは汎用の型なので、自分の構成に合わせて書き換えて使います（[[02_ランブックの書き方]]）。

> 想定スタック：PostgreSQL または MySQL（RDS / Aurora を含む）、Node.js アプリからコネクションプール経由で接続。

---

## 1. 症状とよくある原因

| 症状 | よくある原因 |
|------|--------------|
| `connection refused` / `timeout` | DB インスタンスの停止・フェイルオーバー中、セキュリティグループやネットワークの変更 |
| `too many connections` | アプリのスケールアウトでコネクション数が上限超過、コネクションのリーク |
| 全体的にクエリが遅い | CPU・I/O の飽和、長時間トランザクション、統計情報の古さ、バキューム不足（PostgreSQL） |
| 特定の処理だけ遅い・止まる | ロック待ち、インデックスのないクエリ、バッチ処理との競合 |
| ディスクフル | ログ・一時ファイル・WAL/binlog の増加 |

---

## 2. 影響の確認

- アプリ側：DB 起因のエラー率、コネクションプールの待ち数、API のレイテンシ。
- DB 側：CPU 使用率、接続数、ディスク I/O・空き容量、レプリカ遅延（65_可観測性、RDS なら Performance Insights）。
- **書き込みだけ失敗しているか、読み取りも失敗しているか**。読み取りはレプリカで生かせることがあります。

---

## 3. 初動（止血）

- **重いクエリを止める**：原因のクエリが特定できたら、そのセッションを止める。

```sql
-- PostgreSQL：長く動いているクエリを確認
SELECT pid, now() - query_start AS duration, state, wait_event_type, left(query, 80)
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY duration DESC;

-- 止める（まず cancel、効かなければ terminate）
SELECT pg_cancel_backend(<pid>);
SELECT pg_terminate_backend(<pid>);
```

```sql
-- MySQL
SHOW FULL PROCESSLIST;
KILL <id>;
```

- **負荷の元を絞る**：重いバッチ・管理画面のエクスポート・クローラーを止める。Feature Flag で重い機能を OFF にする。
- **接続の嵐を防ぐ**：アプリがリトライで DB を叩き続けていないか確認する。必要ならアプリ側でレート制限やサーキットブレーカーを効かせる。
- 直前のデプロイで新しいクエリが入っていれば、ロールバックする（[[01_デプロイ直後の異常]]）。

---

## 4. 切り分け

1. **DB は生きているか**：管理コンソールでインスタンスの状態、フェイルオーバーのイベントを確認する。
2. **ロック待ちか**：PostgreSQL なら `pg_locks` と `pg_stat_activity` を突き合わせ、ブロックしている側のセッションを探す。MySQL なら `SHOW ENGINE INNODB STATUS`。
3. **遅いクエリはどれか**：`pg_stat_statements` やスロークエリログで、合計時間の多いクエリを上から見る。`EXPLAIN (ANALYZE)` で実行計画を確認する。
4. **リソースの飽和か**：CPU・メモリ・IOPS・ディスクのどれが上限に張り付いているか（USE メソッド）。
5. **接続数か**：アプリの Pod 数 × プールサイズ が DB の上限を超えていないか計算する。

---

## 5. 復旧

- 停止・フェイルオーバーなら、マネージド DB の自動フェイルオーバー完了を待ち、アプリが再接続できたか確かめる（接続先のエンドポイントを DNS で持っているか）。
- 接続数の問題なら、プールサイズを下げる、RDS Proxy / PgBouncer などのコネクションプーラーを挟む。
- 足りないインデックスは、本番で作るときにロックを避ける（PostgreSQL の `CREATE INDEX CONCURRENTLY`）。
- 一時的に切り抜けるためのスケールアップは有効ですが、戻すかどうかを事後に決めます。
- データの破損が疑われる場合は [[08_データ破損・不整合]] へ。

---

## 6. 事後にやること

- ポストモーテムで「どのクエリ・どの変更が」だけでなく、「**なぜ負荷の増加を事前に検知できなかったか**」を問う。
- 再発防止の候補：
  - スロークエリと接続数のアラートを追加する（[[03_ページングとアラートの受け方]]）
  - ステートメントタイムアウト・ロックタイムアウトを設定する
  - 重いバッチは業務時間外に回す、レプリカで実行する
  - マイグレーションのレビュー観点に「ロックの取り方」を入れる
- DB 設計・インデックス・トランザクションの基礎は 68_データアーキテクチャ。
