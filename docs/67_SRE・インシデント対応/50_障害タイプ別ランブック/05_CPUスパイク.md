# CPUスパイク

CPU 使用率が急に 100% 近くまで上がり、レスポンスが遅くなったりタイムアウトしたりする障害です。Node.js はシングルスレッドなので、**1 つの重い処理がイベントループを塞ぐと、そのプロセスの全リクエストが止まります**。このノートは汎用の型なので、自分の構成に合わせて書き換えて使います（[[02_ランブックの書き方]]）。

---

## 1. 症状とよくある原因

| 症状 | よくある原因 |
|------|--------------|
| 全インスタンスの CPU が一斉に上昇 | トラフィックの急増（キャンペーン・バズ・ボット・DDoS）、キャッシュの一斉失効 |
| 一部のインスタンスだけ高い | 特定のリクエスト（巨大な入力・重いレポート）がそこに当たった、偏った負荷分散 |
| デプロイ後から高い | 非効率なコード（ループ内の重い処理、同期的な暗号化・圧縮・JSON 処理） |
| CPU もメモリも高い | GC の頻発（[[04_メモリリーク・OOM]]） |
| 正規表現を含む処理で固まる | ReDoS（壊滅的なバックトラッキング） |

---

## 2. 影響の確認

- CPU 使用率とレイテンシ・エラー率を並べて見る。CPU が高くても **ユーザー影響がなければ緊急度は下がります**。
- リクエスト数が増えているか（外部要因）、同じ量で CPU だけ増えているか（内部要因）。
- Node.js ならイベントループの遅延（event loop lag）を確認する（65_可観測性）。
- どのエンドポイントが遅いか、APM のトレースで上位を見る。

---

## 3. 初動（止血）

- **トラフィック増なら**：スケールアウトする（オートスケールが追いついていなければ手動で）。

```bash
kubectl scale deployment/api --replicas=20 -n production
```

- **不正なトラフィックなら**：WAF・レート制限で特定の IP・User-Agent・パスを遮断する。
- **特定の重い処理なら**：Feature Flag で OFF にする、そのエンドポイントにレート制限をかける。
- **デプロイ起因なら**：ロールバックする（[[01_デプロイ直後の異常]]）。
- **キャッシュの一斉失効なら**：キャッシュを温め直す、TTL にばらつき（ジッター）を入れる（69_分散システム/50_分散キャッシュ）。

---

## 4. 切り分け

1. **量の問題か、質の問題か**：リクエスト数あたりの CPU 時間が増えていれば質（コード）の問題。
2. **どの処理か**：プロファイルを取って、CPU を食っている関数を特定する。

```bash
# Node.js：CPU プロファイルを取る
node --cpu-prof server.js          # 終了時に .cpuprofile を出力
# 本番で短時間だけ取るなら 0x や clinic flame でフレームグラフを作る
npx 0x server.js
```

3. **フレームグラフを読む**：横幅の広い関数が CPU 時間を多く使っている（66_パフォーマンス/20_計測・分析）。
4. **入力依存か**：遅いリクエストのパラメータ・ペイロードサイズを確認する。巨大な入力・悪意ある正規表現入力を疑う。
5. **同期処理がないか**：`fs.readFileSync`、`crypto.pbkdf2Sync`、巨大な `JSON.parse` などイベントループを塞ぐ処理。

---

## 5. 復旧

- 重い処理を直す：アルゴリズムの改善、キャッシュ、ワーカースレッドやジョブキューへの移動。
- 入力のサイズ上限・タイムアウトを設ける。
- スケールアウトした台数は、落ち着いたら元に戻す（コスト）。オートスケールの設定を見直す。

---

## 6. 事後にやること

- ポストモーテムで「スケールで耐えられたか」「オートスケールは間に合ったか」を確認する。
- 再発防止の候補：
  - CPU ではなく **レイテンシ・イベントループ遅延** をアラートの主軸にする（症状ベースのアラート。[[03_ページングとアラートの受け方]]）
  - 予想されるピーク（キャンペーン）の前に負荷テストとキャパシティ計画をする（66_パフォーマンス/50）
  - ボット対策・レート制限を常設する
  - 正規表現のレビュー・ReDoS 検出ツールを CI に入れる
