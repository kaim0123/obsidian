# メモリリーク・OOM

プロセスのメモリ使用量が増え続け、最後に OOM（Out Of Memory）で強制終了される障害です。**時間をかけてじわじわ悪化し、再起動すると一時的に直る** のが特徴で、根本原因が放置されがちです。このノートは汎用の型なので、自分の構成に合わせて書き換えて使います（[[02_ランブックの書き方]]）。

> 想定スタック：Node.js（V8）のアプリをコンテナ（Kubernetes / ECS）で動かしている。

---

## 1. 症状とよくある原因

| 症状 | よくある原因 |
|------|--------------|
| メモリ使用量がのこぎり型ではなく右肩上がり | リーク（解放されない参照が残り続ける） |
| コンテナが `OOMKilled`（終了コード 137）で再起動 | コンテナのメモリ上限に到達 |
| Node.js が `JavaScript heap out of memory` で落ちる | V8 のヒープ上限（`--max-old-space-size`）に到達 |
| GC が頻発してレイテンシが悪化・CPU も上がる | ヒープが上限近くで GC が回り続けている |
| 特定の操作の後に急増 | 巨大なファイル・レスポンスを丸ごとメモリに載せている |

Node.js でよくあるリークの原因：
- グローバルな配列・Map・キャッシュに入れ続けて消さない（上限のないインメモリキャッシュ）
- イベントリスナーの登録しっぱなし（`MaxListenersExceededWarning` が出る）
- クロージャが大きなオブジェクトを掴み続ける
- タイマー（`setInterval`）の解除漏れ

---

## 2. 影響の確認

- Pod/タスクごとのメモリ使用量の推移（数時間〜数日の範囲で見る）。
- 再起動回数と、その時刻（65_可観測性）。
- 再起動の瞬間にリクエストが失敗しているか（処理中のリクエストが切られる）。
- 全インスタンスで同じ傾向か、一部だけか。

```bash
kubectl get pods -n production          # RESTARTS 列を見る
kubectl describe pod <pod> -n production # Last State: OOMKilled を確認
kubectl top pod -n production
```

---

## 3. 初動（止血）

- **再起動で時間を稼ぐ**：ローリング再起動でメモリを初期化する。根本解決ではないが、ユーザー影響を止められます。

```bash
kubectl rollout restart deployment/api -n production
```

- 直前のデプロイから始まったならロールバックする（[[01_デプロイ直後の異常]]）。
- 一時的にメモリ上限を上げる・インスタンスを増やす。ただしリークなら **倒れるまでの時間が延びるだけ** です。
- 再起動の前に、1 台だけ残して調査用のデータ（ヒープスナップショット）を取れるようにしておくと、原因調査が速くなります。

---

## 4. 切り分け

1. **リークか、単に足りないのか**：負荷が一定でも増え続けるならリーク。負荷に比例して増減するなら上限不足。
2. **ヒープか、ヒープ外か**：`process.memoryUsage()` の `heapUsed` と `rss` を比べる。`rss` だけ増えるなら Buffer・ネイティブモジュールを疑う。
3. **ヒープスナップショットを比べる**：時間をおいて 2〜3 回取り、増えているオブジェクトを比較する。

```bash
# 起動オプションでシグナル受信時にスナップショットを出す
node --heapsnapshot-signal=SIGUSR2 server.js
kill -USR2 <pid>   # .heapsnapshot が出力される → Chrome DevTools の Memory タブで開く
```

4. **いつから**：メモリ推移のグラフの傾きが変わった時点と、デプロイ履歴を突き合わせる。

詳しい調査手順は 84_デバッグ/40_サーバー・Node。

---

## 5. 復旧

- 原因のコードを直してデプロイし、**数時間〜1 日** メモリの推移を見て、横ばいになったことを確かめる。
- インメモリキャッシュには上限（LRU）と TTL を付ける。大きなデータはストリームで処理する。
- コンテナのメモリ上限と V8 のヒープ上限をそろえる（ヒープ上限をコンテナ上限の 7〜8 割程度に）。

---

## 6. 事後にやること

- 「再起動で直ったから終わり」にしない。**根本原因が分かるまでアクションを閉じない**（[[04_再発防止アクションの管理]]）。
- 再発防止の候補：
  - メモリ使用量の **増加率** にアラートを設定する（上限到達より前に気づく）
  - 定期的な再起動に頼っていないか確認する
  - 負荷テストを長時間（ソーク）で回し、メモリの推移を見る
- 同じ症状が繰り返すなら、事例として 91_トラブルシューティング事例集 に残す。
