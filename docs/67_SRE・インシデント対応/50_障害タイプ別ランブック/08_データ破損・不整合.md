# データ破損・不整合

データが消えた、間違った値で上書きされた、テーブル間やシステム間で数字が合わない、といった障害です。サービスが「動いている」ように見えるので気づきにくく、**時間が経つほど被害が広がり、元に戻すのが難しくなります**。他の障害と違い、急いで操作すると取り返しがつかなくなることがあるので、**まず止めて、証拠を残してから直す** のが原則です。このノートは汎用の型なので、自分の構成に合わせて書き換えて使います（[[02_ランブックの書き方]]）。

---

## 1. 症状とよくある原因

| 症状 | よくある原因 |
|------|--------------|
| レコードが消えた | 条件の誤った `DELETE`、カスケード削除、誤ったバッチ・スクリプト |
| 値が間違って上書きされた | `WHERE` なしの `UPDATE`、マイグレーションのバグ、競合する同時更新（lost update） |
| 二重登録・二重請求 | リトライで同じ処理が 2 回走った（冪等性の欠如） |
| システム間で数字が合わない | 分散トランザクションの途中失敗、イベントの取りこぼし・順序違い |
| 文字化け・形式の崩れ | 文字コード・タイムゾーンの扱いの変更 |

---

## 2. 影響の確認

- **いつから**：最初に壊れたデータの作成・更新日時。アプリログ・監査ログ・DB のログ（binlog/WAL）から特定する。
- **どの範囲**：影響を受けたテーブル・レコード数・ユーザー数。お金・個人情報が絡むかどうかで重大度が大きく変わる（[[02_重大度レベル（Severity）]]）。
- **今も壊れ続けているか**：原因の処理がまだ動いているか。
- 法務・カスタマーサポートへの連絡が必要かを判断する（個人情報・決済が絡む場合）。

---

## 3. 初動（止血）

- **壊し続けている処理を止める**：該当のバッチ・コンシューマー・機能を停止する、Feature Flag を OFF にする、書き込みを止める（メンテナンスモード）。
- **証拠を残す**：直す前に、現在の状態をスナップショットで保存する。

```sql
-- 影響範囲のレコードを退避してから作業する
CREATE TABLE orders_backup_20260926 AS
SELECT * FROM orders WHERE updated_at >= '2026-09-26 10:00';
```

- RDS なら手動スナップショットを取る。自動バックアップの保持期間内か確認する（期限切れで復元点を失わないように）。
- **焦って手作業の UPDATE をしない**。本番での修正は、必ず手順を書き、トランザクション内で、別の人がレビューしてから行う。

---

## 4. 切り分け

1. **原因の処理を特定**：壊れたレコードの共通点（作成元・時刻・更新したプロセス）を探す。
2. **正しい値はどこにあるか**：バックアップ、レプリカ、監査ログ、イベントログ、外部システム（決済サービス側の記録）など、真実の元（source of truth）を探す。
3. **復元の方法を選ぶ**：

| 方法 | 向いている場面 | 注意点 |
|------|----------------|--------|
| ポイントインタイムリカバリ（PITR） | 広範囲が壊れた | 別インスタンスに復元して必要な部分だけ戻す。DB 全体を巻き戻すと、その後の正しい更新も消える |
| バックアップから部分復元 | 特定テーブル・レコード | 復元先で抽出 → 本番に差分を適用 |
| ログからの再計算 | イベントソーシング・監査ログがある | 再計算ロジックの正しさを検証する |
| 手作業での修正 | 件数が少ない | 手順書・レビュー・トランザクション必須 |

---

## 5. 復旧

- 修正スクリプトは **まずステージング（本番のコピー）で実行** し、結果を検証してから本番で実行する。
- 本番での実行は、`BEGIN` → 修正 → 件数・内容の確認 → `COMMIT` の順で行い、想定と違えば `ROLLBACK` する。
- 修正後、集計値・システム間の突き合わせ（リコンシリエーション）で整合を確認する。
- 影響を受けたユーザーへの連絡・補償を、サポート・法務と調整する（[[05_インシデント中のコミュニケーションと告知]]）。

---

## 6. 事後にやること

- 再発防止の候補：
  - 本番 DB への手作業の書き込みを制限し、必ずレビューを通す
  - 論理削除・監査ログ・変更履歴テーブルを用意する
  - バックアップからの **復元を定期的に訓練** する（[[04_DR訓練とRTO・RPO]]）
  - 処理を冪等にし、システム間の突き合わせを定期実行する（69_分散システム/60_障害耐性パターン）
  - 破壊的なマイグレーションは expand/contract で段階的に行う（68_データアーキテクチャ）
- データ事故は、ニアミスも含めて記録に残す（[[05_ニアミスとインシデント統計からの学習]]）。
