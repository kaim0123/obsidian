# SREとは

**SRE（Site Reliability Engineering）** は、Google が 2003 年ごろから実践してきた「**運用をソフトウェアエンジニアリングの問題として扱う**」ための考え方と職種です。Google SRE 本（『SRE サイトリライアビリティエンジニアリング』）の冒頭では、SRE を「ソフトウェアエンジニアに運用チームの設計を任せたら生まれるもの」と説明しています。この章では、SRE が何を目指し、従来の運用や DevOps とどう違うのかを整理します。

---

## 1. SRE が解こうとしている問題

従来の組織では、**開発チーム**と**運用チーム**が分かれていました。

| チーム | 評価されること | 変更に対する態度 |
|--------|----------------|------------------|
| 開発 | 新機能を早く出す | 変更したい |
| 運用 | システムを止めない | 変更したくない（障害の多くは変更で起きる） |

目標が正反対なので、リリース前のチェックリストや承認フローが増え、「出したい開発」と「止めたい運用」の綱引きになります。SRE はこの対立を、**数値で合意した信頼性目標（SLO）とエラーバジェット**で解消しようとします（[[03_エラーバジェット方針]]）。

---

## 2. SRE の基本原則（Google SRE 本 Part II より）

| 原則 | 意味 | このフォルダの章 |
|------|------|------------------|
| **リスクを受け入れる** | 100% の信頼性は目指さない。ユーザーが気づかない程度の失敗は許す | [[02_リスクの受け入れと信頼性目標]] |
| **SLO（サービスレベル目標）** | 「どれくらい動いていれば十分か」を数値で決める | [[02_リスクの受け入れと信頼性目標]] |
| **エラーバジェット** | 許容できる失敗の量を「使ってよい予算」として扱う | [[03_エラーバジェット方針]] |
| **トイルの削減** | 手作業の繰り返しを自動化し、エンジニアリングに時間を使う | [[04_トイルの削減と自動化]] |
| **モニタリング** | 症状（ユーザーへの影響）を中心に監視する | 65_可観測性/60_SLO・アラート |
| **自動化** | 人の判断が要らない作業は機械にやらせる | [[04_トイルの削減と自動化]] |
| **リリースエンジニアリング** | 安全で再現可能なリリースの仕組み | 63_リリース・デプロイ |
| **シンプルさ** | 複雑さは信頼性の敵。不要なコードや機能を減らす | 48_原則 |

## 3. SRE と DevOps の関係

「SRE と DevOps は何が違うのか」はよく聞かれる質問です。Google は **「class SRE implements interface DevOps」**（SRE は DevOps という考え方の 1 つの実装）と表現しています。

| 観点 | DevOps | SRE |
|------|--------|-----|
| 性格 | 文化・考え方の運動 | 具体的な職種・プラクティスの集合 |
| 主な関心 | 開発と運用の壁をなくす、デリバリーを速くする | 信頼性を数値で管理しながら変更を続ける |
| 測るもの | DORA メトリクス（デプロイ頻度・変更失敗率など） | SLI / SLO / エラーバジェット |
| 担い手 | チーム全員 | SRE チーム、または SRE の役割を持つ開発者 |

両者は対立するものではなく、**DevOps の「何を目指すか」に対して、SRE は「どう測ってどう回すか」を具体化したもの**と捉えると分かりやすいです。

---

## 4. SRE の仕事の中身

Google SRE 本では、SRE の時間の使い方に上限を設けています。

- **運用作業（トイル・オンコール・チケット対応）は 50% 以下**に抑える
- 残りの 50% 以上は、**運用を減らすためのエンジニアリング**（自動化、信頼性の改善、ツール開発）に使う
- 運用作業が 50% を超えたら、超えた分は開発チームに戻す（開発チーム自身がオンコールに入るなど）

典型的な仕事は次の通りです。

| 分類 | 具体例（Web アプリの場合） |
|------|---------------------------|
| 信頼性目標の設計 | 「API の 99.9% のリクエストが 300ms 以内に成功する」という SLO を決める |
| 監視・アラート | SLO を割りそうなときだけ人を呼ぶアラートを作る |
| オンコール・障害対応 | 夜間のアラートに対応し、ポストモーテムを書く（[[01_オンコール設計]]） |
| キャパシティ計画 | セール前にどれだけサーバーを増やすかを見積もる（66_パフォーマンス） |
| 変更管理 | カナリアリリースや自動ロールバックを整える（63_リリース・デプロイ） |
| トイル削減 | 手動の証明書更新や手動デプロイを自動化する |

---

## 5. 小さなチームでの SRE

SRE チームを持てない小さな組織でも、SRE の考え方は取り入れられます。

1. **重要なユーザー体験を 1〜3 個決め、SLO を置く**（例：ログインできる、決済できる）
2. **アラートを SLO に結びつける**（CPU 使用率ではなく「エラー率が上がった」で呼ぶ）
3. **オンコールを開発者で回す**（You build it, you run it）
4. **障害が起きたら必ずポストモーテムを書く**（[[01_ポストモーテムとは]]）
5. **繰り返している手作業を 1 つずつ自動化する**

大事なのは職種名ではなく、「**信頼性を数値で決め、その範囲で変更を続け、失敗から学ぶ**」というループを回すことです。
