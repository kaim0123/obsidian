# リスクの受け入れと信頼性目標

SRE の出発点は「**100% の信頼性は目標として間違っている**」という考え方です（Google SRE 本 3 章「Embracing Risk」）。この章では、なぜ 100% を目指さないのか、代わりにどうやって「十分な信頼性」を数値で決めるのか（SLI / SLO / SLA）を説明します。

---

## 1. なぜ 100% を目指さないのか

| 理由 | 説明 |
|------|------|
| **ユーザーは違いに気づかない** | ユーザーのスマホ回線や Wi-Fi の信頼性は 99% 程度。サーバーが 99.99% でも 99.999% でも体験はほぼ同じ |
| **コストが指数関数的に増える** | 9 を 1 つ増やすごとに、冗長化・監視・人員のコストが大きく跳ね上がる |
| **変更できなくなる** | 失敗をゼロにする一番の方法は「何も変えないこと」。新機能が出せなくなる |

つまり信頼性は「高ければ高いほど良い」ものではなく、**ユーザーの満足とコスト・開発速度のバランスで決める目標**です。

---

## 2. 9 の数と許容停止時間

| 可用性 | 年間の許容停止 | 30 日あたり | 例 |
|--------|----------------|-------------|----|
| 99% | 約 3.65 日 | 約 7.2 時間 | 社内ツール |
| 99.9% | 約 8.8 時間 | 約 43 分 | 一般的な Web サービス |
| 99.95% | 約 4.4 時間 | 約 22 分 | EC サイトの決済 |
| 99.99% | 約 53 分 | 約 4.3 分 | 決済基盤・認証基盤 |
| 99.999% | 約 5 分 | 約 26 秒 | 通信インフラ |

99.99% を超えると、**人が気づいて対応する時間すらない**ので、自動フェイルオーバーが前提になります。

---

## 3. SLI・SLO・SLA

| 用語 | 意味 | 例 |
|------|------|----|
| **SLI**（Service Level Indicator） | 信頼性を測る指標。「良いイベント ÷ 全イベント」で表すのが基本 | 成功した HTTP リクエストの割合 |
| **SLO**（Service Level Objective） | SLI の目標値と期間 | 30 日間で 99.9% のリクエストが成功 |
| **SLA**（Service Level Agreement） | 顧客との契約。破ると返金などのペナルティ | 月間 99.5% を下回ったら利用料の 10% を返金 |

- **SLA は SLO より緩く**設定します。SLO を割った段階で手を打ち、SLA 違反を防ぐためです。
- SLA がない社内サービスでも、SLO は置けます。

### よく使う SLI

| 種類 | 定義の例 | 向いている対象 |
|------|----------|----------------|
| 可用性 | 5xx 以外のレスポンスの割合 | API、Web ページ |
| レイテンシ | 300ms 以内に返ったリクエストの割合 | API、検索 |
| 品質 | 劣化表示（おすすめ枠が空など）でないレスポンスの割合 | 縮退運転のある画面 |
| 鮮度 | 10 分以内に更新されたデータの割合 | バッチ・集計 |
| 正確性 | 正しい結果を返した割合 | データパイプライン |

SLI は**ユーザーに近い場所**（ロードバランサーのログ、クライアント計測）で測るほど、実際の体験に近づきます。CPU 使用率のような「原因側」の指標は SLI にしません。

---

## 4. SLO の決め方（SRE Workbook 2 章より）

1. **重要なユーザージャーニーを選ぶ**：ログイン、商品検索、カート追加、決済など
2. **ジャーニーごとに SLI を決める**：決済なら「決済 API の成功率」と「3 秒以内の完了率」
3. **過去の実績を見る**：直近 4 週間の実績が 99.95% なら、それより少し緩い 99.9% から始める
4. **関係者と合意する**：プロダクトオーナー・開発・SRE が「これを下回ったら困る」と納得する値にする
5. **定期的に見直す**：四半期ごとに、ユーザーの不満や問い合わせと SLO の乖離を確認する

> 最初から完璧な SLO は作れません。「**測れるものから始めて、実態に合わせて直す**」のが Workbook の推奨です。

### 例：EC サイトの SLO

| ジャーニー | SLI | SLO（30 日） |
|------------|-----|--------------|
| 商品一覧の表示 | 500ms 以内に 200 を返した割合 | 99.5% |
| カート追加 | 成功レスポンスの割合 | 99.9% |
| 決済 | 決済完了までエラーなしで終わった割合 | 99.95% |
| 注文メール送信 | 5 分以内に送信された割合 | 99% |

重要度によって目標を**変える**のがポイントです。全部 99.99% にすると、コストも運用負荷も膨らみます。

---

## 5. 依存先の信頼性を考える

自分のサービスの信頼性は、**依存先の信頼性を超えられません**。

- 直列に 3 つの依存（DB 99.95%、認証 API 99.9%、決済 API 99.9%）があると、全体は約 99.75% まで下がる
- 高い SLO を守るには、依存先の障害時に**縮退運転**（キャッシュを返す、機能を一時的に隠す）できる設計が要る（69_分散システム/60_障害耐性パターン）
