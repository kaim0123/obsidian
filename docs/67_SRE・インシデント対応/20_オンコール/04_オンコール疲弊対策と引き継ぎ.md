# オンコール疲弊対策と引き継ぎ

オンコールは、設計を誤ると**燃え尽き（バーンアウト）**の大きな原因になります。疲れたエンジニアは判断を誤りやすく、障害対応の質も下がります。この章では、オンコールの負荷を測って減らす方法と、当番交代時の**引き継ぎ（ハンドオフ）**のやり方を説明します（Google SRE Workbook 8 章「On-Call」、Atlassian Incident Handbook を参考）。

---

## 1. 疲弊の原因

| 原因 | 典型的な状況 |
|------|--------------|
| ページが多すぎる | 1 シフトで 10 件以上鳴る。ほとんどが対応不要 |
| 夜間の呼び出し | 週に何度も深夜に起こされ、睡眠が細切れになる |
| 1 人に集中 | 詳しい人だけが毎回呼ばれる（ヒーロー依存） |
| 準備不足 | ランブックがなく、毎回ゼロから調べる |
| 心理的な負担 | 「自分のミスで障害が起きた」と責められる文化 |
| 補償がない | 待機も呼び出しも無給、翌日も通常勤務 |

ストレスは、**ページの件数よりも「予測できない」「コントロールできない」**ことから生まれます。ランブックと明確なエスカレーションは、この不安を減らします。

---

## 2. 負荷を測る

感覚ではなく数字で把握します。

| 指標 | 見方 |
|------|------|
| シフトあたりのページ数 | 2 件以下が目安（[[01_オンコール設計]]） |
| 時間外のページ数 | 夜間・休日のページを別に集計 |
| 対応不要ページの割合 | 高いならアラートの問題（[[03_ページングとアラートの受け方]]） |
| 1 人あたりの当番回数 | 特定の人に偏っていないか |
| 対応時間の合計 | 業務時間の 25% を超えていないか |
| 当番後アンケート | 「今週のオンコールはどれくらい大変だったか」を 5 段階で |

これらを**月次でチームに共有**し、悪化していれば改善を優先します。

---

## 3. 負荷を減らす打ち手

### 3.1 アラート側

- 対応不要だったアラートは、**その週のうちに削除・調整**する
- 同じ原因で繰り返すページは、**根本対策をポストモーテムのアクションに入れる**（[[04_再発防止アクションの管理]]）
- 自動で直せるもの（プロセスの再起動、ディスク掃除）は自動化する（[[04_トイルの削減と自動化]]）

### 3.2 体制側

- ローテーションの人数を増やす（隣接チームとの合同、Follow-the-Sun）
- 夜間に呼ばれた翌日は**遅めの出社・午前休**を制度にする
- 当番中は**通常のスプリント作業を減らす**（当番の週は割り込み対応と運用改善に専念）
- 詳しい人への集中を防ぐため、**知識を共有する**（ランブック、ペア対応、Wheel of Misfortune）

### 3.3 文化側

- 障害を個人の責任にしない（[[01_ポストモーテムとは]]）
- 「呼んで何もなかった」を責めない。**早めのエスカレーションを歓迎する**
- 疲れているときは交代を申し出てよい、と明言しておく

---

## 4. 引き継ぎ（ハンドオフ）

当番の交代時に情報が途切れると、同じ調査を繰り返したり、進行中の問題を見落としたりします。

### 4.1 引き継ぎのタイミング

- 週次交代なら、**平日の日中**（例：月曜 11 時）に行う
- 進行中のインシデントがある場合は、**インシデントコマンダーも含めて明示的に交代**する（[[03_インシデントコマンダーと役割分担]]）

### 4.2 引き継ぎメモの雛形

```markdown
## オンコール引き継ぎ 2026-09-21 → 2026-09-28
前任：A さん / 後任：B さん

### 今週のサマリー
- ページ数：5 件（うち夜間 1 件、対応不要 2 件）
- インシデント：SEV3 × 1（決済 API のタイムアウト増加）

### 未解決・継続監視
- [ ] 決済 API のタイムアウト：外部ベンダーの回答待ち。再発したらランブック X
- [ ] DB のディスク使用率 78%：水曜にボリューム拡張予定

### 今週の予定
- 水曜 22:00 DB メンテナンス（担当：DB チーム）
- 金曜 大型セール開始 → 事前スケールアウト済み

### 改善提案
- 「キャッシュヒット率低下」アラートは毎回対応不要 → 削除を提案（チケット #123）
```

### 4.3 引き継ぎで伝えること

| 項目 | 理由 |
|------|------|
| 未解決の問題と次の一手 | 後任がゼロから調べずに済む |
| 予定されている変更・イベント | 障害の原因候補を事前に知っておける |
| 鳴りやすいアラートとその意味 | 誤報への過剰反応を防ぐ |
| 改善の提案 | 疲弊の原因を次の改善につなげる |

---

## 5. 定期的な振り返り

月に 1 回、**オンコールの振り返り会**を開きます。

1. 先月のページ一覧を見る（件数・時間帯・対応内容）
2. 「対応不要だったもの」「自動化できたもの」「ランブックが役に立たなかったもの」を分類
3. 改善アクションを決め、担当と期限を付ける
4. 当番のアンケート結果を共有し、負荷の偏りを確認
