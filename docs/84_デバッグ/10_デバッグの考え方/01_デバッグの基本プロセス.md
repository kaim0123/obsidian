# デバッグの基本プロセス

デバッグは「怪しいところを片っ端から触る」作業ではありません。**観察 → 仮説 → 検証**を繰り返して、原因の範囲を確実に狭めていく作業です。やり方が決まっていれば、知らないコードでも、初めて見るエラーでも、同じ手順で進められます。この章では、どのバグにも使える基本の流れを整理します。

テストとデバッグの役割の違い（テストは故障を見つける、デバッグは原因の欠陥を突き止めて直す）は [[03_エラー・欠陥・故障とデバッグ]] を参照。

---

## 1. 全体の流れ

```
① 再現する ─→ ② 事実を集める ─→ ③ 範囲を狭める ─→ ④ 仮説を立てて確かめる
                                                         │
     ⑦ 再発を防ぐ ←─ ⑥ 直ったことを確かめる ←─ ⑤ 直す ←─┘
```

| 段階 | やること | 終わりの目安 |
|------|----------|--------------|
| ① 再現 | 同じ故障を自分の手元で起こす | 手順を書けば誰でも再現できる |
| ② 事実を集める | エラー・ログ・環境・直前の変更を集める | 「何が・いつ・どこで」を言える |
| ③ 範囲を狭める | 怪しい範囲を半分ずつ減らす | 原因がありそうな場所が数十行以内 |
| ④ 仮説と検証 | 「原因は X だ」と決めて、確かめる実験をする | 仮説どおりに故障を出したり消したりできる |
| ⑤ 直す | 原因に対して修正する | — |
| ⑥ 確認 | 故障が消えたこと、他を壊していないことを確かめる | 再現手順で出ない。テストが通る |
| ⑦ 再発防止 | テストを足す。なぜ入ったかを振り返る | 同じバグが入ればテストで落ちる |

---

## 2. ① 再現する

再現できないバグは、直ったかどうかも確かめられません。最初に一番時間をかける価値がある段階です。

- **手順を書き出す**：どの画面で、何を入力して、何を押したか。
- **環境をそろえる**：ブラウザ・OS・ログイン中のユーザー・データ・環境変数・ブランチ。
- **最小にする**：関係ない手順やデータを1つずつ外し、それでも起きる最小の再現手順を作る。最小の再現を作る過程で原因が分かることも多い。
- **テストにする**：再現手順を自動テストにできれば、⑥の確認と⑦の再発防止を兼ねられる。

### 再現しないとき

| 状況 | 疑うこと |
|------|----------|
| 自分の環境では起きない | ブラウザ・拡張機能・キャッシュ・タイムゾーン・言語設定・権限・データの違い |
| たまにしか起きない | タイミング（非同期の順序）・競合・外部サービスの遅延・乱数・日時（[[02_flakyテストの原因と対策]]） |
| 本番でしか起きない | データ量・設定・ビルドの違い（最適化・環境変数）・複数台構成 |

---

## 3. ② 事実を集める

思い込みで動く前に、**観察できる事実**を集めます。

- **エラーメッセージとスタックトレース**を全部読む（[[03_エラーメッセージとスタックトレースの読み方]]）。
- **ログ**：ブラウザの Console、サーバーのログ、Network パネルのリクエストとレスポンス。
- **いつから起きたか**：直前のデプロイ・依存パッケージの更新・設定変更。「昨日までは動いていた」なら、差分の中に原因がある。
- **どこまで正しいか**：入力は正しいか → API のリクエストは正しいか → レスポンスは正しいか → 画面の state は正しいか、と境界ごとに確かめる。

> 「たぶん〜だろう」と思ったら、それは事実ではなく仮説です。ログやブレークポイントで確かめるまで事実として扱わない。

---

## 4. ③ 範囲を狭める

原因の場所を、確実に半分ずつ減らしていきます。具体的な技法は [[02_原因の切り分け方]] で扱います。

- **レイヤーで分ける**：フロント？ API？ DB？ 外部サービス？ Network パネルで「リクエストは正しく、レスポンスが間違っている」ならサーバー側。
- **時間で分ける**：動いていたコミットと動かないコミットの間を二分探索（`git bisect`）。
- **コードで分ける**：処理の途中にログやブレークポイントを置き、「ここまでは正しい」地点を進めていく。

---

## 5. ④ 仮説を立てて確かめる

- 仮説は**1つずつ**確かめる。同時に3か所を変えると、どれが効いたか分からない。
- **仮説が正しければ起きるはずのこと**を予測し、それを実験で確かめる。例：「キャッシュが原因なら、シークレットウィンドウでは起きないはず」。
- 確かめた結果（当たり・外れ）はメモに残す。同じ仮説を何度も試さないため。
- 1時間以上進まないときは、休憩するか、誰かに説明する（ラバーダック・デバッグ）。説明するために事実を整理すると、見落としに気づくことが多い。

---

## 6. ⑤〜⑦ 直す・確かめる・防ぐ

- **原因を直す**。症状だけを消す修正（`try/catch` で握りつぶす、`?.` を足してエラーを消す）は、別の場所で故障を起こすだけになりがち。
- **確認テスト**（直ったか）と**回帰テスト**（他を壊していないか）を行う（[[02_テストの種類（機能・非機能）]]）。
- **先に落ちるテストを書いてから直す**と、テストが本当にそのバグを捕まえられることも確かめられる。
- 振り返りでは「なぜその誤りが入り、なぜテストやレビューで見つからなかったか」まで見る（根本原因）。事例は 91_トラブルシューティング事例集 に残す。

## 7. デバッグメモのテンプレート

```markdown
## 症状
- 何が起きるか / 期待していたこと

## 再現手順
1.
2.

## 環境
- ブラウザ / OS / ブランチ / データ

## 分かっている事実
- 

## 仮説と検証
| 仮説 | 確かめ方 | 結果 |
|------|----------|------|

## 原因
## 修正
## 再発防止（追加したテスト）
```
