# 原因の切り分け方

デバッグで一番時間がかかるのは「原因がどこにあるか」を見つける段階です。勘で当たりを付けるのではなく、**確実に範囲を半分にする**技法を知っていると、どんなに大きなコードでも数回の試行で原因の近くまで行けます。この章では、よく使う切り分けの技法をまとめます。

---

## 1. 二分探索：半分ずつ減らす

切り分けの基本は二分探索です。1000 行の処理でも、10 回ほどで1行まで絞れます（2¹⁰ = 1024）。

```
処理の流れ： A → B → C → D → E → F → G → H
                        ↑
               真ん中（D の後）で値を確かめる
   正しい → 原因は E〜H     間違っている → 原因は A〜D
```

- 真ん中に `console.log` かブレークポイントを置き、**そこまでの結果が正しいか**を確かめる。
- 「正しいか」を判断するには、**期待する値を先に決めておく**必要があります。値を見てから「たぶん合ってる」と判断しない。

---

## 2. 時間で切り分ける：git bisect

「前は動いていた」なら、動いていたコミットと動かないコミットの間を二分探索します。

```bash
git bisect start
git bisect bad                 # 今のコミットは壊れている
git bisect good v1.4.0         # このタグでは動いていた
# → Git が真ん中のコミットをチェックアウトするので、確かめて good / bad を答える
git bisect good                # または git bisect bad
# … 繰り返すと、壊れた最初のコミットが表示される
git bisect reset               # 元のブランチに戻る
```

### 自動で回す

確かめる手順をスクリプトやテストにできれば、全自動で探せます。

```bash
git bisect start HEAD v1.4.0
git bisect run npx vitest run src/cart.test.ts   # 終了コード 0 なら good、それ以外は bad
```

- 100 コミットあっても 7 回ほどで見つかります。
- 見つかったコミットの差分を読めば、原因はほぼその中にあります。

---

## 3. 差分で切り分ける

「動く環境」と「動かない環境」の**違い**を1つずつ埋めていきます。

| 比べるもの | 例 |
|------------|----|
| 環境 | ローカルでは動くが CI では落ちる → Node のバージョン・タイムゾーン・環境変数 |
| データ | ユーザー A では起きるが B では起きない → 2人のデータの違い |
| ブラウザ | Chrome では動くが Safari では動かない → 対応していない API・CSS |
| 依存 | `npm install` し直したら壊れた → lockfile の差分でどのパッケージが上がったか |
| 設定 | 開発ビルドでは動くが本番ビルドでは動かない → 最適化・環境変数・ソースマップ |

- 違いを**1つずつ**そろえ、どれをそろえたら故障が消えるかを見る。

---

## 4. 最小の再現を作る

関係ない部分を削って、**それでも故障が起きる最小のコード**を作ります。

1. 故障が起きるコピーを作る（ブランチ・StackBlitz・CodeSandbox など）。
2. 関係なさそうな部品・処理・データを1つ削る。
3. まだ故障が起きるなら、そのまま次を削る。起きなくなったら、今削ったものが関係している。
4. これ以上削れなくなるまで繰り返す。

- 最小の再現ができると、原因はたいてい見えています。見えなくても、ライブラリの Issue や同僚に聞くときにそのまま使えます。

---

## 5. レイヤーで切り分ける

Web アプリでは、データがどの境界まで正しいかを順に確かめます。

```
入力 ─→ フロントの処理 ─→ リクエスト ─→ サーバー ─→ DB
画面 ←─ フロントの state ←─ レスポンス ←─┘
```

| 確かめる場所 | 道具 |
|--------------|------|
| リクエスト・レスポンスの中身 | [[Network（通信の監視）]] |
| フロントの state・props | React DevTools（[[2-5-デバッグ]]） |
| フロントの処理の途中の値 | [[Sources（ブレークポイントとステップ実行）]] |
| サーバーの処理 | [[01_Node.jsのデバッガ]]、ログ |
| DB の中身 | SQL クライアントで直接確認 |

- **Network パネルで境界を決めるのが一番速い**。リクエストが間違っていればフロント、レスポンスが間違っていればサーバー、両方正しければ画面の表示処理。

---

## 6. その他の技法

| 技法 | やり方 | 使いどころ |
|------|--------|------------|
| **コメントアウト** | 怪しい処理を一時的に止めて、故障が消えるか見る | 副作用の多い処理の特定 |
| **値の固定** | 入力・API の応答・現在時刻を固定値にする | 外部要因を除く |
| **ラバーダック** | コードを1行ずつ誰か（ぬいぐるみでもよい）に説明する | 思い込みに気づく |
| **ログの差分** | 正常時と異常時のログを並べて比べる | 流れの違いを見つける |
| **最新・最古の依存で試す** | パッケージのバージョンを上げる／下げる | ライブラリのバグかどうか |

---

## 7. 切り分けのアンチパターン

- **同時に複数を変える**：直っても、何が効いたか分からない。
- **仮説を確かめずに修正を始める**：原因でない場所を直して、別のバグを入れる。
- **ログを消し忘れる**：`console.log` を大量に残したままコミットする。デバッグ用のログは作業後に消すか、ログレベルで制御する（[[04_ログを使ったデバッグ]]）。
- **「ありえない」と決めつける**：ありえないはずのことが起きているのがバグ。前提（この値は null にならない、この関数は1回しか呼ばれない）こそ確かめる。
