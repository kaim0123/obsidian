# エラーメッセージとスタックトレースの読み方

エラーが出たとき、真っ赤なメッセージを見て慌てて検索する前に、**全文を上から読む**だけで原因の場所が分かることはよくあります。エラーメッセージには「何が起きたか」、スタックトレースには「どこを通ってそこに来たか」が書かれています。この章では、JavaScript / TypeScript を中心に、その読み方をまとめます。

---

## 1. エラーの構造

```
TypeError: Cannot read properties of undefined (reading 'name')
    at formatUser (src/utils/user.ts:12:23)
    at UserCard (src/components/UserCard.tsx:8:15)
    at renderWithHooks (node_modules/react-dom/...)
    at ...
```

| 部分 | 意味 |
|------|------|
| `TypeError` | エラーの種類 |
| `Cannot read properties of undefined (reading 'name')` | メッセージ：何が起きたか |
| `at formatUser (src/utils/user.ts:12:23)` | 1行目：**エラーが発生した場所**（関数名・ファイル・行・列） |
| 2行目以降 | そこを呼び出した場所を、呼び出し元へさかのぼって並べたもの |

### 読む順番

1. **種類とメッセージ**を読む：何が起きたか。
2. **スタックの中で、自分のコードの一番上の行**を探す：`node_modules` の中ではなく `src/` の行。そこが調べ始める場所。
3. **呼び出し元をたどる**：おかしな値がどこから渡ってきたかを見る。

> ライブラリの中でエラーになっていても、原因はたいてい**ライブラリに渡した自分の値**です。スタックを下にたどって、自分のコードからライブラリを呼んでいる行を探します。

---

## 2. JavaScript のよくあるエラー

| 種類 | 意味 | よくある原因 |
|------|------|--------------|
| **TypeError** | 値の型に対してできない操作をした | `undefined` / `null` のプロパティを読んだ、関数でないものを呼んだ |
| **ReferenceError** | 存在しない変数を参照した | スペルミス、import 忘れ、宣言前の `let` / `const` を使った |
| **SyntaxError** | 文法が間違っている | 括弧の閉じ忘れ、JSON のパース失敗（`Unexpected token < in JSON` は HTML が返ってきている） |
| **RangeError** | 値が許される範囲の外 | 無限再帰（`Maximum call stack size exceeded`）、不正な配列長 |
| **Unhandled Promise Rejection** | reject された Promise を誰も catch していない | `await` の付け忘れ、`.catch` なし |

### メッセージから原因を読む例

| メッセージ | 読み方 |
|------------|--------|
| `Cannot read properties of undefined (reading 'name')` | `x.name` の **x** が undefined。`name` が問題なのではない |
| `x.map is not a function` | x が配列ではない（オブジェクト・undefined・API のエラー応答など） |
| `Unexpected token '<', "<!DOCTYPE "... is not valid JSON` | JSON を期待したのに HTML（404 ページやエラーページ）が返ってきた |
| `Failed to fetch` | ネットワークエラー。CORS・サーバー停止・URL の誤り（Network パネルで確認） |
| `Maximum update depth exceeded`（React） | レンダーのたびに state を更新して無限ループしている |
| `Hydration failed`（React / Next.js） | サーバーとクライアントで描画結果が違う（日時・乱数・`window` の参照） |

## 3. TypeScript のコンパイルエラー

コンパイルエラーは、実行前に教えてくれる分だけ親切です。

```
src/cart.ts:15:7 - error TS2322: Type 'string' is not assignable to type 'number'.
```

- `TS2322` などの番号で検索すると、同じエラーの解説が見つかりやすい。
- 長いエラーは**一番下の行**に核心があることが多い（入れ子の型のどこが合わないかが最後に出る）。
- 型エラーを `as any` や `// @ts-ignore` で消すのは、症状を消しているだけです。まず「型が正しいのか、値が正しいのか」を考える。

## 4. ソースマップ

ビルドされたコードでは、スタックトレースが `main.a1b2c3.js:1:48213` のように読めない場所を指します。**ソースマップ**があると、元の TypeScript のファイルと行に変換されます。

| 環境 | 設定 |
|------|------|
| Vite / Next.js の開発サーバー | 標準で有効 |
| 本番ビルド | `build.sourcemap`（Vite）などで生成。公開したくない場合は `hidden` にして、エラー監視サービス（Sentry など）だけにアップロードする |
| Node.js | `node --enable-source-maps` で TypeScript の行が出る |

## 5. 非同期のスタックトレース

`await` や `setTimeout` をまたぐと、スタックトレースが途中で切れることがあります。

- Chrome DevTools と Node.js は **async スタックトレース**に対応していて、`await` の前の呼び出し元も表示します（`at async fetchUser` のような行）。
- `.then()` のチェーンより `async / await` で書くほうが、スタックが追いやすい。
- エラーを投げ直すときは、元のエラーを `cause` に入れて情報を失わないようにする。

```ts
try {
  await saveOrder(order);
} catch (e) {
  throw new Error('注文の保存に失敗しました', { cause: e });
}
```

## 6. 検索するときのコツ

- **自分のコード固有の部分を消して**検索する（ファイル名・変数名・ID を除き、エラーメッセージの定型部分だけにする）。
- ライブラリ名とバージョンを付ける（`next 15 hydration failed`）。
- GitHub の Issue は、閉じられたものも含めて検索する。
- AI に聞くときは、エラー全文・スタックトレース・関係するコード・試したことをまとめて渡す。
