# ログを使ったデバッグ

ブレークポイントは強力ですが、本番環境・CI・たまにしか起きない問題・複数のサーバーにまたがる問題では使えません。そういう場面で頼りになるのが**ログ**です。この章では、デバッグのための一時的なログと、あとから調査できるようにするための恒久的なログの両方について、書き方と考え方をまとめます。

---

## 1. ログとブレークポイントの使い分け

| | ログ | ブレークポイント |
|---|------|------------------|
| 向いている場面 | 本番・CI・タイミング依存・長い処理の流れ | 手元で再現できる問題、値を詳しく見たいとき |
| 長所 | 止めずに流れ全体を記録できる。後から見返せる | その瞬間の全変数・呼び出し履歴を見られる |
| 短所 | 仕込んだ場所の、仕込んだ値しか分からない | 止めるとタイミングが変わる。本番では使えない |

- 手元で再現できるなら、`console.log` を何度も足して再実行するより、ブレークポイント（[[Sources（ブレークポイントとステップ実行）]]）のほうが速いことが多い。
- ブラウザの**ログポイント**（コードを変えずにログを出す）は、両方の良いところを取った方法です（[[デバッグ実践]]）。

---

## 2. 一時的なデバッグログの書き方

```ts
// ✗ 何の値か分からない
console.log(user);
console.log('ここ');

// ○ ラベルを付け、オブジェクトで出す
console.log('[checkout] before submit', { userId: user.id, total, items: items.length });
```

| テクニック | 書き方 | 効果 |
|------------|--------|------|
| 変数名ごと出す | `console.log({ total, discount })` | 名前と値が並ぶ |
| 表で出す | `console.table(items)` | 配列・オブジェクトの一覧が見やすい |
| 呼び出し元を出す | `console.trace('called')` | そこに来るまでのスタック |
| 回数を数える | `console.count('render')` | 何回呼ばれたか |
| 時間を測る | `console.time('fetch')` … `console.timeEnd('fetch')` | 処理時間 |
| グループ化 | `console.group('order')` … `console.groupEnd()` | 入れ子で読みやすく |

- **オブジェクトは参照で表示される**ことに注意。ブラウザの Console でオブジェクトを後から展開すると、ログを出した時点ではなく**展開した時点の値**が見えます。その時点の値を残したいなら `console.log(JSON.parse(JSON.stringify(obj)))` や `structuredClone(obj)`。
- 作業が終わったら消す。残したくないログを防ぐには ESLint の `no-console` を使う。

## 3. 恒久的なログ（アプリケーションログ）

本番で問題が起きたとき、後から調べられるように**最初から仕込んでおく**ログです。

### ログレベル

| レベル | 用途 | 例 |
|--------|------|----|
| **error** | 処理が失敗し、対応が必要 | 決済 API がエラーを返した |
| **warn** | 失敗ではないが、想定外 | リトライで成功した、非推奨の API が呼ばれた |
| **info** | 重要な出来事の記録 | ユーザーが注文を確定した、サーバーが起動した |
| **debug** | 開発・調査用の詳細 | 関数の入力値、分岐の結果 |

- 本番は `info` 以上、調査するときだけ `debug` を有効にする、のように**環境変数で切り替えられる**ようにする。

### 構造化ログ

```ts
// ✗ 文字列を組み立てる：検索・集計しにくい
logger.info(`User ${userId} ordered ${items.length} items`);

// ○ JSON で出す：userId で絞り込める
logger.info({ event: 'order_created', userId, itemCount: items.length, orderId }, 'order created');
```

- Node.js では pino や winston が定番です（[[02_サーバーのログと本番の調査]]）。
- **リクエスト ID**（トレース ID）をすべてのログに付けると、1つのリクエストに関するログをまとめて追えます。複数のサービスにまたがる場合は分散トレーシング（65_可観測性）へ。

## 4. 何をログに出すか

| 出す | 出さない |
|------|----------|
| 何が起きたか（イベント名） | パスワード・トークン・API キー |
| 誰が・何に対して（ユーザー ID・注文 ID） | クレジットカード番号・個人情報（氏名・住所・メールアドレスは要注意） |
| 結果（成功・失敗・件数・所要時間） | リクエスト・レスポンスの本文をまるごと |
| エラーの種類・メッセージ・スタック | — |
| 外部サービスへの呼び出しと、その応答コード | — |

- 個人情報をログに出すと、ログを見られる人全員に漏れることになります（セキュリティの観点は [[06_ログ出力（徳丸本24章）]]）。

---

## 5. ログを読むときのコツ

- **時刻でそろえる**：複数のサーバー・サービスのログは、同じタイムゾーン（UTC）で並べる。
- **正常時と比べる**：同じ操作の正常時のログと並べ、どこから違うかを見る。
- **最初のエラーを探す**：1つの問題が連鎖して大量のエラーが出ることがある。一番古いエラーが原因に近い。
- **「ない」ログにも注目する**：出るはずのログが出ていない ＝ その処理まで到達していない。
