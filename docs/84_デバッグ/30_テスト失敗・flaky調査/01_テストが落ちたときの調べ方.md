# テストが落ちたときの調べ方

テストが落ちたとき、原因は「本番コードのバグ」だけではありません。テストの書き方の誤り、環境の違い、前のテストの影響など、いくつかの可能性があります。この章では、テストが落ちたときに**どこから見て、どう切り分けるか**を、Vitest と Playwright を例にまとめます。

---

## 1. まず「どれが悪いか」を分ける

テストが落ちたときに疑うべきものは4つです。

| 疑う相手 | サイン | 対応 |
|----------|--------|------|
| **本番コードのバグ** | 最近の変更に関係する場所で、毎回落ちる | 本番コードを直す（テストは正しく仕事をした） |
| **テストの誤り** | 期待値が仕様と違う、テストの準備が足りない | テストを直す |
| **仕様の変更** | 意図して振る舞いを変えた | テストを新しい仕様に合わせる |
| **環境・タイミング** | 手元では通るが CI で落ちる、たまにしか落ちない | [[02_flakyテストの原因と対策]] |

> 落ちたテストを、中身を読まずに期待値だけ書き換えて通すのは一番危険です。「なぜこの値を期待していたのか」を確かめてから直します。

---

## 2. 失敗の出力を読む

```
 FAIL  src/cart.test.ts > Cart > 会員は10%割引される
AssertionError: expected 1000 to be 900

- Expected
+ Received

- 900
+ 1000

 ❯ src/cart.test.ts:24:30
     22|     const cart = new Cart(buildUser({ isMember: true }));
     23|     cart.add({ price: 1000, qty: 1 });
     24|     expect(cart.total).toBe(900);
       |                        ^
```

| 部分 | 読むこと |
|------|----------|
| テスト名 | どの振る舞いが壊れたか（テスト名が仕様の一文になっていると、ここで原因の見当がつく → [[03_テストの命名と粒度]]） |
| Expected / Received | 期待と実際の差。**差の形**がヒントになる（割引がまったく効いていない、符号が逆、1つずれている など） |
| 場所 | 落ちた行。スタックトレースに本番コードの行があれば、そこでエラーになっている |

- 例外で落ちた場合は、[[03_エラーメッセージとスタックトレースの読み方]] と同じ読み方をします。

---

## 3. 範囲を絞って再実行する

```bash
# ファイルを指定
npx vitest run src/cart.test.ts
# テスト名で絞る
npx vitest run -t "会員は10%割引"
# 変更を監視して、保存のたびに再実行
npx vitest src/cart.test.ts
```

- コードで一時的に絞るなら `test.only` / `describe.only`（コミットしないよう注意。CI で `--allowOnly=false` にしておくと安全）。
- **1つだけ流すと通り、全体で流すと落ちる**なら、他のテストの影響です（→ [[02_flakyテストの原因と対策]] の「順序依存」）。

## 4. Vitest のテストをデバッグする

### 値を出して確かめる

- テストの中に `console.log` を書けば、テストの出力に表示されます。
- Testing Library を使っているなら `screen.debug()` で、その時点の DOM が見られます（[[02_クエリの選び方]]）。

### ブレークポイントで止める

**VS Code の JavaScript Debug Terminal**を使うのが一番簡単です。

1. コマンドパレット → 「JavaScript Debug Terminal」を開く。
2. そのターミナルで `npx vitest run src/cart.test.ts` を実行する。
3. エディタで置いたブレークポイントで止まる。

`launch.json` で設定する方法や、Chrome DevTools につなぐ方法（`--inspect-brk`）は [[08_CI連携とデバッグ]]（Vitest）と [[01_Node.jsのデバッガ]] を参照。

### Vitest UI

```bash
npx vitest --ui
```

- ブラウザでテストの一覧・結果・失敗の差分・コンソール出力・モジュールの依存関係を見られます。

## 5. Playwright のテストをデバッグする

| 方法 | コマンド | 用途 |
|------|----------|------|
| **UI モード** | `npx playwright test --ui` | テストを選んで実行し、各ステップの画面を時間をさかのぼって見る |
| **デバッグモード** | `npx playwright test --debug` | ブラウザを表示し、1ステップずつ実行する（Playwright Inspector） |
| **ヘッドありで実行** | `npx playwright test --headed` | ブラウザの動きを目で見る |
| **トレース** | `--trace on`、または設定で `trace: 'on-first-retry'` | 失敗時の DOM・ネットワーク・コンソール・スクリーンショットを記録 |
| **トレースビューア** | `npx playwright show-trace trace.zip` | CI で落ちたテストの記録を手元で開く |
| **一時停止** | テスト内に `await page.pause()` | その時点でブラウザを止めて調べる |

- **CI で落ちた E2E テストは、トレースを見るのが一番速い**。CI の成果物（artifact）としてトレースとレポートを保存しておく（[[06_CIとデバッグ]]）。
- よくあるエラー（要素が見つからない・タイムアウト）の原因は [[01_よくあるE2Eテストエラー集]] にまとめています。

## 6. CI でだけ落ちるとき

| 確認すること | 例 |
|--------------|----|
| Node.js・ブラウザのバージョン | `.nvmrc`・`engines`、Playwright のブラウザのバージョン |
| タイムゾーン・ロケール | CI は UTC、手元は JST。日付の境界で結果が変わる |
| 環境変数 | CI に設定されていない、値が違う |
| 実行速度 | CI のマシンは遅い → タイミングに依存したテストが落ちる |
| 並列実行 | CI は並列数が違う → テスト同士が同じデータを使っている |
| キャッシュ | 古い依存・古いビルド成果物が残っている |

- 手元で CI と同じ条件を作る：`TZ=UTC npx vitest run`、CI と同じ Docker イメージで実行する、など。
