# flaky テストの原因と対策

**flaky テスト**（不安定なテスト）は、コードを何も変えていないのに、通ったり落ちたりするテストです。1本あるだけで「また flaky か」と失敗を無視する習慣がつき、本物のバグが見逃されるようになります。この章では、flaky になる原因の分類と、見つけ方・直し方・運用のしかたをまとめます。

---

## 1. なぜ放置してはいけないか

- **信頼が失われる**：失敗が当たり前になり、本物の失敗も「再実行すれば通る」で片付けられる。
- **時間を奪う**：再実行・調査のたびに CI の時間と人の時間を使う。
- **本物のバグを隠していることがある**：タイミングで落ちるテストは、本番でもタイミングで起きる競合状態を捕まえているかもしれない。

---

## 2. 原因の分類

Google や Microsoft の調査でも、原因の大半は次のどれかです。

| 分類 | 何が起きているか | 典型例 |
|------|------------------|--------|
| **非同期・タイミング** | 処理が終わる前に確かめている | `await` 忘れ、固定時間の `sleep`、アニメーション中にクリック |
| **テストの順序依存** | 前のテストが残した状態に依存している | 共有変数・DB のデータ・モックの設定が次のテストに残る |
| **共有リソース** | 並列実行でテスト同士がぶつかる | 同じユーザー・同じファイル・同じポートを使う |
| **時刻・乱数** | 実行するたびに入力が変わる | `new Date()`、月末・うるう年・タイムゾーン、`Math.random()` |
| **外部依存** | ネットワーク・外部 API の状態で結果が変わる | 本物の API を呼ぶ、DNS・レート制限 |
| **環境・リソース** | マシンの速さ・メモリで結果が変わる | CI が遅くてタイムアウト、並列数が違う |
| **順序が決まっていない処理** | 結果の並び順が毎回違う | `Promise.all` の完了順、DB の `ORDER BY` なしの結果、Set / Map の順 |

---

## 3. 見つけ方

### 何度も流す

```ts
// Vitest：疑わしいテストに repeats を付けて、同じテストを繰り返す
test('カートの合計を計算する', { repeats: 20 }, () => { /* … */ });
```

```bash
# Vitest：順番をシャッフルして、順序依存をあぶり出す
npx vitest run --sequence.shuffle
# Vitest：ファイルごと何度も流す（シェルのループ）
for i in $(seq 20); do npx vitest run src/cart.test.ts || break; done

# Playwright：各テストを 20 回流す
npx playwright test checkout.spec.ts --repeat-each 20
```

- CI の負荷を再現するために、並列数を上げたり、CPU を制限した Docker で流したりするのも有効です。

### 履歴を見る

- CI の結果を記録して、「同じコミットで通ったり落ちたりしたテスト」を一覧にする。多くの CI サービスやテストレポートツールに、flaky の検出機能があります。
- Playwright はリトライで通ったテストを **flaky** としてレポートに表示します。

## 4. 原因別の直し方

### 非同期・タイミング

```ts
// ✗ 固定時間待つ
await new Promise((r) => setTimeout(r, 1000));
expect(screen.getByText('完了')).toBeInTheDocument();

// ○ 条件を待つ
expect(await screen.findByText('完了')).toBeInTheDocument();
```

```ts
// Playwright：✗ waitForTimeout、○ 自動待機するアサーション
await page.waitForTimeout(1000);
await expect(page.getByText('完了')).toBeVisible();
```

- Testing Library の待ち方は [[04_非同期UIとよくある間違い]]、Playwright は [[04_アサーションと待機]] を参照。

### 順序依存・共有状態

- `beforeEach` で毎回作り直す。`afterEach` で片付ける（モック・タイマー・MSW のハンドラ・DB）。
- テストで使うデータは、テストごとにユニークなものを作る（[[05_テストデータの用意]]）。
- グローバルな状態（シングルトン・モジュールのトップレベル変数）は、リセットできる仕組みを用意する。

### 時刻・乱数

```ts
vi.useFakeTimers();
vi.setSystemTime(new Date('2026-03-31T10:00:00+09:00'));
// …
vi.useRealTimers();
```

- CI と手元でタイムゾーンをそろえる（`TZ=UTC`）。Playwright は設定で `timezoneId` と `locale` を固定できます。
- 乱数はシードを固定するか、テストでは固定値を注入する。

### 外部依存

- テストでは本物の外部 API を呼ばない。MSW やスタブで置き換える（[[03_テストでの使い分け（Vitest・Playwright・Storybook）]]）。
- MSW の `onUnhandledRequest: 'error'` で、うっかり本物に通信しているテストを見つける。

### 順序が決まっていない処理

- 結果を並べ替えてから比べる、または順序を問わないマッチャーを使う（`expect(arr).toEqual(expect.arrayContaining([...]))`）。
- 本番コードでも順序が重要なら、それは本物のバグです（`ORDER BY` を付ける）。

---

## 5. 運用のルール

| ルール | 理由 |
|--------|------|
| **リトライは応急処置**と考える | リトライで通すと flaky が見えなくなる。リトライで通ったものは必ず記録して直す |
| **隔離（quarantine）する** | すぐ直せない flaky は、必須のテストから外して別枠で流す。放置しないよう担当と期限を決める |
| **見つけたらすぐ Issue にする** | 「そのうち直す」は直らない |
| **新しいテストは繰り返し流してからマージ** | 追加したテストを `--repeat-each` で数十回流して、最初から flaky でないことを確かめる |
| **削除も選択肢に入れる** | 価値の低いテストが flaky なら、直すより消すほうがよいこともある |
