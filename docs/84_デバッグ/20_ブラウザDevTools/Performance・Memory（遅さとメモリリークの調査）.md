# Performance・Memory（遅さとメモリリークの調査）

「画面が重い」「スクロールがカクつく」「長く開いているとだんだん遅くなる」——こうした問題は、エラーが出ないので Console を見ても分かりません。**Performance パネル**で「何に時間を使っているか」を、**Memory パネル**で「何がメモリを使い続けているか」を調べます。

React 固有の再レンダリングの調査は [[9-1-体感が重い原因を切り分ける]]（32_React）、Web 全体の性能指標は 67_パフォーマンス が本拠地です。

---

## 1. まず測る：遅さの種類を分ける

| 症状 | 原因の候補 | 使うパネル |
|------|------------|------------|
| 最初の表示が遅い | 大きな JS・画像、遅い API、レンダリングをブロックするリソース | Network、Lighthouse、Performance |
| 操作してから反応するまでが遅い | 重い JS の処理（Long Task）、大量の再描画 | Performance |
| スクロール・アニメーションがカクつく | レイアウトの再計算、重い描画 | Performance（Rendering） |
| 使っているうちに遅くなる | メモリリーク | Memory |

- 「遅い」という感覚ではなく、**数値で測ってから直す**。直した後も同じ条件で測り、効果を確かめる。
- 開発ビルドは本番より遅いので、最終的な判断は本番ビルド（`npm run build && npm run preview` など）で行う。

## 2. Performance パネル

### 記録の仕方

1. Performance パネルを開き、**CPU のスロットリング**（4x slowdown など）を設定する。開発者の速いマシンでは問題が見えないため。
2. 記録ボタン（●）を押す → 遅い操作をする → 停止。
3. ページの読み込みを調べるときは、リロードボタン（↻）で「読み込みから記録」する。

- ライブの指標（LCP・INP・CLS）が、記録しなくてもパネルを開いた時点で表示されます。

### 見方

| 領域 | 見るもの |
|------|----------|
| 上部の概要 | CPU の使用率（黄色＝スクリプト、紫＝レイアウト、緑＝描画）、スクリーンショット |
| **Main** | メインスレッドで実行された処理の**フレームチャート**。横が時間、縦が呼び出しの深さ |
| Network | リクエストのタイミング |
| Interactions | クリックなどの操作と、その応答にかかった時間（INP の原因） |
| 下部 Summary / Bottom-Up / Call Tree | 時間を使った関数の集計 |

### 探すもの

- **Long Task（赤い三角が付いた 50ms 以上のタスク）**：この間、ブラウザは操作に反応できない。中を開いて、どの関数が時間を使っているかを見る。
- **Bottom-Up タブ**：自分の時間（Self Time）が長い関数の順に並べると、重い処理がすぐ分かる。
- **紫の Layout が繰り返し出る**：JS でスタイルを書いて、すぐに `offsetHeight` などを読む処理を繰り返している（強制同期レイアウト）。

### よくある原因と対策

| 原因 | 対策 |
|------|------|
| 大きな配列のループ・重い計算を操作のたびに行う | メモ化、計算の回数を減らす、Web Worker に移す |
| 長いリストを全部描画する | 仮想スクロール（TanStack Virtual など） |
| 入力のたびに検索・API 呼び出し | デバウンス |
| 読み込み時の大きな JS | コード分割・動的 import |
| レイアウトの読み書きを交互に行う | 読み取りをまとめてから書き込む |

## 3. Memory パネル：メモリリークを探す

**メモリリーク**は、もう使わないのに参照が残っていて、ガベージコレクションで回収されないメモリです。SPA では画面を行き来するたびに少しずつ増え、最後には重くなったり落ちたりします。

### よくある原因

| 原因 | 例 |
|------|----|
| イベントリスナーの外し忘れ | `window.addEventListener('resize', …)` を画面を離れても外さない |
| タイマーの止め忘れ | `setInterval` を clear しない |
| 購読の解除忘れ | WebSocket・Observable・ストアの subscribe |
| 切り離された DOM への参照 | 削除した要素を変数やクロージャが持ち続ける（Detached DOM） |
| 大きくなり続けるキャッシュ | 上限のない Map・配列 |

React では、`useEffect` のクリーンアップ関数でこれらを解除します（[[17-4-メモリリーク]]）。

### ヒープスナップショットで比べる

1. Memory パネルで **Heap snapshot** を選び、スナップショットを取る（1回目）。
2. 疑わしい操作をする（画面を開いて閉じる、を 5 回くらい繰り返す）。
3. ゴミ箱アイコンで**ガベージコレクションを実行**してから、もう一度スナップショットを取る（2回目）。
4. 2回目を選び、表示を **Comparison** にして1回目と比べる。
5. **# Delta（増えた数）** が操作の回数に比例して増えているオブジェクトが怪しい。
6. オブジェクトを選び、下の **Retainers** で「誰がこれを参照し続けているか」をたどる。

- フィルタに `Detached` と入れると、DOM から外れたのに残っている要素が見つかります。

### その他の方法

| 方法 | 用途 |
|------|------|
| **Allocation instrumentation on timeline** | 時間の経過とともに、どこでメモリが確保されたかを見る（青い棒が残り続けるのがリーク） |
| **Performance Monitor**（`Ctrl + Shift + P` → Show Performance Monitor） | JS ヒープ・DOM ノード数・イベントリスナー数をリアルタイムで見る。操作を繰り返して増え続けるならリーク |
| **Performance パネルで Memory にチェック** | 記録中のヒープの増減をグラフで見る。のこぎり型（増えて GC で戻る）は正常、右肩上がりはリーク |

## 4. Lighthouse との使い分け

| | Lighthouse | Performance パネル |
|---|------------|--------------------|
| 目的 | 問題があるかを**採点**して、改善のヒントを出す | どこに時間を使っているかを**詳しく調べる** |
| 使いどころ | 定期的な確認・CI（[[06_パフォーマンス（Lighthouse CI）]]） | 遅い原因の特定 |
