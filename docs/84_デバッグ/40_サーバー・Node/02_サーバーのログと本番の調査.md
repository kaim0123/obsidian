# サーバーのログと本番の調査

本番環境ではブレークポイントを置けず、再現もしにくく、何台ものサーバーでリクエストが処理されています。そこで頼りになるのが、**あらかじめ仕込んでおいたログとエラー監視**です。この章では、Node.js サーバーでのログの出し方と、本番で問題が起きたときの調べ方をまとめます。ログの一般的な考え方（レベル・構造化・出してはいけないもの）は [[04_ログを使ったデバッグ]] を参照。

---

## 1. 本番調査の流れ

```
① 影響を把握する ─→ ② 時間と範囲を絞る ─→ ③ ログ・エラーで原因を探す ─→ ④ 手元で再現する
   誰が・どれくらい       いつから・どの機能       リクエスト ID でたどる          テストにする
```

- **まず影響を止める**のが先です。原因が分からなくても、直前のデプロイが怪しければロールバックする。調査はその後でもできる。
- 「いつから」は、デプロイ・設定変更・外部サービスの障害・アクセスの急増と照らし合わせる。

---

## 2. 構造化ログ（pino の例）

```ts
import pino from 'pino';

export const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',
  redact: ['req.headers.authorization', 'req.headers.cookie', '*.password'], // 秘密情報を伏せる
});
```

```ts
logger.info({ orderId, userId, amount }, 'order created');
logger.error({ err, orderId }, 'payment failed');   // err は Error オブジェクト（スタックも出る）
```

出力（1行1 JSON）：

```json
{"level":30,"time":1790000000000,"orderId":"o-123","userId":"u-9","amount":1200,"msg":"order created"}
```

- JSON で出しておくと、ログ基盤（CloudWatch Logs、Datadog、Grafana Loki など）で `orderId` や `userId` で絞り込めます。
- 開発中は `pino-pretty` で読みやすく表示する。
- `console.log` は同期的に書き込むので、大量に出すと遅くなることがあります。pino は高速に非同期で書き出すよう設計されています。

## 3. リクエスト ID で1つのリクエストを追う

同時に大量のリクエストが来ると、ログは入り混じります。**リクエストごとに ID を付けて、すべてのログに含める**と、1つのリクエストの流れだけを取り出せます。

```ts
import { randomUUID } from 'node:crypto';
import { AsyncLocalStorage } from 'node:async_hooks';

const als = new AsyncLocalStorage<{ requestId: string }>();

app.use((req, res, next) => {
  const requestId = req.header('x-request-id') ?? randomUUID();
  res.setHeader('x-request-id', requestId);
  als.run({ requestId }, next);
});

export const log = () => logger.child({ requestId: als.getStore()?.requestId });
// どこからでも：log().info({ orderId }, 'order created')
```

- レスポンスヘッダーに ID を返しておくと、ユーザーからの問い合わせやフロントのエラー報告と、サーバーのログを結び付けられます。
- 複数のサービスをまたぐなら、OpenTelemetry などの**分散トレーシング**で、トレース ID を自動で引き継ぎます（65_可観測性）。

## 4. エラー監視サービス

Sentry などのエラー監視サービスは、例外が起きたときに次の情報をまとめて送ってくれます。

| 情報 | 役に立つこと |
|------|--------------|
| スタックトレース（ソースマップで元のコードに変換） | どこで起きたか |
| 発生回数・影響ユーザー数・初回発生日時 | どれくらい深刻か、いつから |
| リクエストの情報（URL・メソッド・ヘッダー） | どんな操作で起きたか |
| パンくず（直前のログ・操作） | そこに至るまでの流れ |
| リリースのバージョン | どのデプロイから起きたか |

- ソースマップは公開せずに、エラー監視サービスにだけアップロードする（[[03_エラーメッセージとスタックトレースの読み方]]）。
- 同じエラーはまとめて1件になるので、「新しく出たエラー」に気づきやすくなります。

## 5. ログから原因を探すコツ

| やること | 理由 |
|----------|------|
| **一番古いエラーを探す** | 1つの原因から大量のエラーが連鎖する。後のエラーは結果にすぎない |
| **正常なリクエストと比べる** | 同じ API の成功したリクエストのログと並べ、どこから違うかを見る |
| **出るはずのログがないことに注目する** | そこまで処理が届いていない（手前で止まった・例外が握りつぶされた） |
| **外部呼び出しの時間を見る** | タイムアウトや遅延は、外部 API・DB の遅さが原因のことが多い |
| **デプロイ時刻と重ねる** | エラーが増え始めた時刻とデプロイの時刻が一致すれば、その差分が原因の候補 |

---

## 6. 本番で再現できないときの手当て

- **ログを足してデプロイする**：原因を絞るためのログを一時的に足す。`debug` レベルを特定のユーザーやリクエストだけ有効にできる仕組みがあると便利。
- **本番のデータで再現する**：個人情報を伏せたデータを手元に持ってくる（扱いのルールに従う）。
- **フィーチャーフラグで切り替える**：新しい処理を一部のユーザーだけに出し、比べる。
- 再現できたら、**その条件を自動テストにする**（[[01_デバッグの基本プロセス]] の⑦再発防止）。
