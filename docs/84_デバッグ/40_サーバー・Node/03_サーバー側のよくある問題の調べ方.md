# サーバー側のよくある問題の調べ方

Node.js のサーバーでよく起きる問題には、決まった症状と決まった調べ方があります。この章では、「プロセスが落ちる」「応答が返らない」「だんだん遅くなる」「メモリが増え続ける」「手元では動くのにデプロイ先で動かない」の5つのパターンについて、原因の候補と調べ方をまとめます。

---

## 1. 症状から引く早見表

| 症状 | 最初に疑うこと | 調べ方 |
|------|----------------|--------|
| プロセスが突然落ちる | 捕まえていない例外・Promise の reject、メモリ不足 | ログの最後、終了コード、`unhandledRejection` |
| 応答が返らない（タイムアウト） | レスポンスの返し忘れ、await されない Promise、外部呼び出しの待ち | リクエストごとのログ、外部呼び出しのタイムアウト設定 |
| 全体が遅い・詰まる | イベントループのブロック、DB の遅いクエリ、接続プールの枯渇 | イベントループの遅延、CPU プロファイル、DB のスロークエリログ |
| 時間とともにメモリが増える | メモリリーク | ヒープスナップショットの比較 |
| デプロイ先でだけ動かない | 環境変数・設定・パス・権限・バージョンの違い | 起動時のログ、環境の差分（[[02_原因の切り分け方]]） |

---

## 2. プロセスが落ちる

### 捕まえていない例外

```ts
process.on('uncaughtException', (err) => {
  logger.fatal({ err }, 'uncaught exception');
  process.exit(1); // 状態が壊れている可能性があるので、記録してから終了する
});

process.on('unhandledRejection', (reason) => {
  logger.fatal({ err: reason }, 'unhandled rejection');
  process.exit(1);
});
```

- 最近の Node.js は、捕まえていない Promise の reject で**プロセスを終了**します。`await` の付け忘れや `.catch` のない Promise が原因です。
- ここでログを出して終了し、プロセスマネージャー（systemd、PM2、コンテナの再起動ポリシー）に再起動させるのが基本です。例外を握りつぶして動かし続けない。

### メモリ不足で落ちる

```
FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
```

- 大きなファイル・大量のレコードを一度にメモリに読み込んでいないか（ストリームやページングで分ける）。
- メモリリーク（→ 5章）。
- `--max-old-space-size` で上限を上げるのは、原因が分かってからの応急処置です。

---

## 3. 応答が返らない

- **レスポンスの返し忘れ**：分岐の一部で `res.send` や `return` を忘れている（Express）。
- **外部呼び出しにタイムアウトがない**：`fetch` は標準ではタイムアウトしない。`AbortSignal.timeout(5000)` を付ける。
- **DB の接続プールが枯渇している**：接続を返し忘れている、同時リクエストに対してプールが小さい。プールの使用状況をログや監視で見る。
- **デッドロック・ロック待ち**：DB のトランザクション同士が待ち合っている。DB 側のロック状況を確認する。

---

## 4. イベントループのブロック

Node.js は1つのスレッドでイベントループを回しているので、**重い同期処理が1つあると、その間すべてのリクエストが止まります**。

### よくある原因

- 大きな JSON の `JSON.parse` / `JSON.stringify`
- 同期版の API（`fs.readFileSync`、`crypto.pbkdf2Sync` など）をリクエストの処理中に使う
- 大きな配列のソート・ループ、複雑な正規表現（ReDoS）

### 調べ方

```ts
import { monitorEventLoopDelay } from 'node:perf_hooks';
const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();
setInterval(() => {
  logger.info({ p99ms: h.percentile(99) / 1e6 }, 'event loop delay');
  h.reset();
}, 10_000);
```

- 遅延が大きくなった時間帯に、何の処理が走っていたかをログで見る。
- **CPU プロファイル**を取る：`node --cpu-prof src/server.js` で実行し、終了時にできる `.cpuprofile` を Chrome DevTools の Performance パネルに読み込む。または [[01_Node.jsのデバッガ]] でつないで、DevTools の Performance / Profiler で記録する。
- 見つけたら、非同期版の API に替える、処理を分割する、Worker Threads に移す。

## 5. メモリリーク

### よくある原因

| 原因 | 例 |
|------|----|
| 上限のないキャッシュ | モジュールのトップレベルの `Map` にリクエストごとのデータを貯め続ける |
| イベントリスナーの外し忘れ | リクエストごとに `emitter.on` して外さない（`MaxListenersExceededWarning` が出る） |
| クロージャが大きなオブジェクトを持ち続ける | タイマーやコールバックが不要になった参照を握っている |
| 終わらないタイマー | `setInterval` をリクエストごとに作って止めない |

### 調べ方

1. 監視で**メモリ使用量（RSS・ヒープ）が右肩上がり**になっていることを確かめる（GC で下がらない）。
2. 手元で負荷をかけながら、[[01_Node.jsのデバッガ]] で Chrome DevTools につなぐ。
3. Memory パネルでヒープスナップショットを取り、負荷をかけて、もう一度取って **Comparison** で比べる（手順はブラウザと同じ → [[Performance・Memory（遅さとメモリリークの調査）]]）。
4. 増え続けているオブジェクトの **Retainers** をたどり、誰が参照しているかを見る。

- 本番のプロセスから取りたい場合は、`node --heapsnapshot-signal=SIGUSR2` で起動しておき、シグナルを送るとスナップショットを書き出せます（書き出し中はプロセスが止まるので注意）。

## 6. デプロイ先でだけ動かない

| 確認すること | 例 |
|--------------|----|
| 環境変数 | 設定されていない・名前が違う → **起動時に必須の環境変数を検証して、なければ落とす**（zod などで） |
| Node.js のバージョン | ローカルと違う → `engines`・`.nvmrc`・Docker イメージのタグをそろえる |
| ファイルのパス・大文字小文字 | macOS は大文字小文字を区別しないが、Linux は区別する（`import './User'` と `user.ts`） |
| 権限・ネットワーク | ファイルの書き込み権限、外部への通信がファイアウォールで止められている |
| ビルドの違い | 開発時は動く `devDependencies` が本番に入っていない |

設定まわりの事例は [[01_設定エラー基礎]]（91_トラブルシューティング事例集）にもまとめています。
