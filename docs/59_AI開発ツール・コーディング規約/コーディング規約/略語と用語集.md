# 略語と用語集 — 統一語彙・禁止略語

## はじめに

プログラミングでは、**同じ概念に違う言葉** を使ってしまうと、すぐに混乱が生まれます。

- `customer` と `user` は同じ？違う？
- `delete` と `remove` はどう違う？
- `cfg` と `config` と `configuration` は同じもの？

チームで **使う言葉を揃えた辞書（用語集）** を持つことが、巨大なコードベースを扱う基本です。

---

## なぜ用語を統一するのか

### 1. 読みやすくなる

同じ概念が統一されていれば、**頭の中で変換する手間がない**。

### 2. 検索しやすくなる

`customer` で検索して、`user` で書かれたコードがヒットしないのは致命的。

### 3. 認識のずれが減る

**言葉が同じ = 意味も同じ** と保証できれば、バグが減る。

### 4. 新メンバーが早く立ち上がる

専門用語の辞書があれば、**そのプロジェクト独自の言い回し** を素早く覚えられる。

---

## 用語集（Glossary）を作る

### 何を載せるか

- **ビジネス上の用語**（顧客、注文、請求、商品、在庫…）
- **略語**（`UI`, `API`, `DB`, `CRUD` など）
- **類似語の使い分け**（`user` vs `customer` vs `member`）
- **プロジェクト固有の造語**

### 例: 用語集のフォーマット

```markdown
## 用語集

### Customer（顧客）
- 定義: 商品を購入した、または購入予定のユーザー
- 同義語として避けるべき: buyer, client, purchaser

### User（ユーザー）
- 定義: システムにログインできる全ての人
- 関連: Customer ⊂ User（顧客はユーザーの部分集合）

### Order（注文）
- 定義: 顧客が商品を購入した記録
- 関連: Cart(買い物かご) → Order(確定後)
```

### 配置場所

- `GLOSSARY.md` をリポジトリのルートに置く
- あるいは Confluence / Notion などのドキュメントツールに
- 常に最新に保つ（古くなると混乱の元）

## よく使われる略語（OK）

### 広く知られた略語は使ってOK

| 略語 | 意味 |
|------|------|
| `id` | identifier（識別子） |
| `URL` | Uniform Resource Locator |
| `API` | Application Programming Interface |
| `DB` | Database |
| `UI` | User Interface |
| `CRUD` | Create/Read/Update/Delete |
| `HTTP` | HyperText Transfer Protocol |
| `JSON` | JavaScript Object Notation |
| `HTML` | HyperText Markup Language |
| `CSS` | Cascading Style Sheets |

---

## 慣習的にOKな短縮

| 短縮 | 元の語 |
|------|--------|
| `i, j, k` | ループカウンタ（短い範囲のみ） |
| `e` | event / error |
| `err` | error |
| `req, res` | request, response |
| `ctx` | context |
| `el` | element（DOM） |

ただし、**2〜3行のスコープを超えるなら略さずフルネームで**。

## 避けるべき略語

### 意味が推測しにくいもの

```javascript
// ❌ 避ける
const usr = ...;      // → user
const acc = ...;      // → account
const prd = ...;      // → product
const qty = ...;      // → quantity（※業界によっては許容）
const addr = ...;     // → address
```

### プロジェクト独自すぎる略語

```javascript
// ❌ 社内用語を略すと新メンバーが分からない
const pprMgr = new PprManager(); // "Paper Manager"?
```

### 紛らわしい類似語

```javascript
// ❌ どれがどれ？
const ord; // order?
const odr; // order?
const ordr; // order?
```

→ **書き方を1つに決める**。

## 統一すべき動詞の対

混在しやすいので、プロジェクトで **どちらを使うか決める**。

| 選択肢 | 使い分けの例 |
|--------|-------------|
| `delete` vs `remove` | 物理削除=delete、関連解除=remove |
| `get` vs `fetch` | get=ローカル、fetch=リモート |
| `create` vs `make` vs `build` | 統一する |
| `find` vs `search` vs `get` | find=1件、search=複数、get=確実に存在 |
| `update` vs `modify` | どちらか片方に統一 |

## 類似した概念の使い分け

### User, Account, Customer, Member

混同しやすい。プロジェクトで役割を明確に。

| 用語 | 例えば |
|------|-------|
| User | ログインできる全員（管理者も） |
| Customer | 商品を買う人（購買者） |
| Member | 特定のグループに所属する人 |
| Account | 資格情報の単位（1ユーザーが複数持つこともある） |

### Amount, Quantity, Count

| 用語 | 意味 |
|------|------|
| Amount | 金額・量（単位つき） |
| Quantity | 数量（個数） |
| Count | 集計・件数 |

```javascript
const totalAmount = 1000; // 円
const itemQuantity = 3;   // 個
const userCount = 150;    // 人数
```

## ドメイン駆動設計のユビキタス言語

DDDには **ユビキタス言語（Ubiquitous Language）** という考え方があります。

> **「開発者も、業務の人も、ドキュメントも、コードも、全員が同じ言葉を使う」**

例えば、業務の人が「商品登録」と呼ぶものをコードで `productInsert` と書いていると、話がかみ合わなくなります。**業務の言葉をそのままコードに** 反映させるのが理想です。

→ 詳しくは [[02_ユビキタス言語]]

## 禁止すべき略語ルール

プロジェクトで以下のような **禁止リスト** を持つと事故が減ります。

```
禁止略語:
- usr, acc, prd, cfg, mgr, ctl
- 理由: 読めない・検索できない

推奨:
- user, account, product, config, manager, controller
```

---

## 用語集の運用

1. **新しい概念が出たら、まず用語集を更新**
2. **PRレビュー時に用語の一貫性を確認**
3. **定期的に用語集を見直す**
4. **非エンジニアも閲覧できる場所に置く**
