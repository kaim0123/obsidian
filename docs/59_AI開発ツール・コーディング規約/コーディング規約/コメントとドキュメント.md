# コメントとドキュメント — 何を書くか / 書かないか

## はじめに

初心者のうちは、「**コメントは多いほど親切**」と考えがちです。しかし、**現場のベテランほどコメントを減らし** ます。

本当に価値のあるコメントと、害になるコメントがあります。この章ではその違いを学びます。

---

## 基本方針: 「コメントが必要 = 名前が悪い」こともある

まず最優先で考えるべきは **「コメントを書かずに済ます方法はないか？」** です。

```javascript
// ❌ コメント必須のコード
let x = 86400; // 1日の秒数

// ✅ コメント不要のコード
const SECONDS_IN_A_DAY = 86400;
```

```javascript
// ❌ コメントで説明
// ユーザーがアクティブかつ管理者かチェック
if (u.s === 1 && u.r === 3) { ... }

// ✅ コードで説明
if (user.isActive() && user.isAdmin()) { ... }
```

**コードだけで意図が伝わるなら、それが最善**。コメントは **コードの補完** であって、**コードの言い訳** ではありません。

---

## 書くべきコメント

### 1. WHY（なぜそうしているか）

コードは **「何をしているか」** を表しますが、**「なぜそうしているか」** は表現しにくい。

```javascript
// ✅ なぜ -1 なのか説明
// 配列の末尾を0-indexedで参照するため -1 する
const last = arr[arr.length - 1];

// ✅ 特殊な制約
// Safari 14以下ではこのAPIが壊れているため代替を使う
const dateFormat = navigator.userAgent.includes('Safari/14') ? fallback : native;
```

### 2. 非自明な前提・制約

```javascript
// ✅ 業務上の制約
// 営業時間は9-18時限定（システム的には24時間受付だが業務ルール上ここで弾く）
if (hour < 9 || hour >= 18) throw new Error('営業時間外');
```

### 3. 複雑なアルゴリズムの意図

```javascript
// ✅ アルゴリズム
// Boyer-Moore 法で部分文字列を検索（通常の indexOf より高速）
function search(text, pattern) { ... }
```

### 4. バグのワークアラウンド

```javascript
// ✅ 既知のバグに対する対応
// 参考: https://github.com/xxx/xxx/issues/123
// iOSでタッチイベントが二重発火するため、300ms以内の重複を無視
```

### 5. TODO / FIXME

```javascript
// TODO: 支払い失敗時のリトライを実装（Issue #42）
// FIXME: 大量データで遅いので最適化が必要
```

## 書かなくていいコメント

### 1. 「何をしているか」の説明

コードを読めば分かることを重ねない。

```javascript
// ❌ コードそのまま
// i を 1 増やす
i++;

// ❌ 名前でわかる
// ユーザーを取得
const user = getUser();
```

### 2. ノイズコメント

```javascript
// ❌ 意味がない
// コンストラクタ
constructor() { ... }

// クラス User を定義
class User { ... }
```

### 3. 古くなった嘘コメント

```javascript
// ❌ 実装と食い違っている
// 結果をミリ秒で返す
function getTime() {
  return Date.now() / 1000; // 秒を返している
}
```

**実装とズレたコメントは、無いよりも害がある**。

### 4. コメントアウトしたコード

```javascript
// ❌ 「念のため」残さない
// const old = calcOldWay();
const result = calcNewWay();
```

Gitが覚えているので **消す**。残すと「これ何？使う？」と毎回迷うノイズになる。

## ドキュメントコメント（APIドキュメント）

関数やクラスの **外部仕様** を書くコメントは別物。JSDoc, TSDoc, JavaDoc, docstring など。

### JSDoc / TSDoc

```typescript
/**
 * 商品の合計金額を計算する
 * @param items 商品リスト
 * @param taxRate 税率（0.1 = 10%）
 * @returns 税込合計金額
 * @throws 空のリストが渡された場合にエラー
 *
 * @example
 * calcTotal([{ price: 100 }], 0.1); // 110
 */
function calcTotal(items: Item[], taxRate: number): number { ... }
```

### Python docstring

```python
def calc_total(items, tax_rate):
    """商品の合計金額を計算する。

    Args:
        items: 商品のリスト
        tax_rate: 税率（0.1 = 10%）

    Returns:
        税込合計金額

    Raises:
        ValueError: 空のリストが渡された場合
    """
```

### 書くべき内容

- 関数の **目的**
- 各引数の **意味・制約**
- 戻り値の **意味**
- **例外** が起こる条件
- **使用例**

### 内部実装は書かない

```typescript
/**
 * ❌ 実装の詳細
 * このメソッドは for ループを使い、内部で result 変数に累積していく
 */
```

**使う人は中身を知らなくてよい**。使い方だけ書く。

## README・設計ドキュメント

### README.md に書くこと

- **何のためのプロジェクトか**
- **セットアップ方法**
- **使い方**
- **開発手順**
- **ディレクトリ構成**

### 設計ドキュメントに書くこと

- **アーキテクチャ概要**
- **主要な判断の理由**（ADR: Architecture Decision Records）
- **ビジネスルール**
- **外部連携の仕様**

### コードではなくドキュメントに書くべきもの

- **機能の全体像**
- **複数ファイルにまたがる説明**
- **図が必要な内容**（UML、シーケンス図）

---

## コメントの鉄則

1. **コードで説明できないか、先に考える**
2. **WHY を書き、WHAT は書かない**
3. **実装ではなく意図を書く**
4. **古くなったら直すか消す**
5. **コメントアウトしたコードは消す**
6. **TODO には Issue 番号を添える**
7. **ドキュメントコメントは外部仕様を書く**

## 良い例 vs 悪い例（ビフォーアフター）

### Before

```javascript
// ユーザーを取得する
function getUser(id) {
  // idが空ならエラー
  if (!id) throw new Error('id required');
  // DBから取得
  const u = db.query('SELECT * FROM users WHERE id = ?', id);
  // 返す
  return u;
}
```

### After

```javascript
function getUser(id: string): User {
  if (!id) throw new Error('id required');
  return db.query('SELECT * FROM users WHERE id = ?', id);
}
```

コメントなしでも十分わかる。**読み手の頭を信頼する**。
