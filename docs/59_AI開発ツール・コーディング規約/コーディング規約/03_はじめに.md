# はじめに — コーディング規約とは何か

## この章のねらい

このフォルダでは「コーディング規約（coding convention）」を、ゼロから学ぶ人向けに順を追って解説していきます。まずはその入り口として、この章で次の2つをつかみましょう。

- **0-1：コーディング規約とは何か** — なぜ命名やスタイルを「揃える」必要があるのか
- **0-2：この教材で扱う範囲** — 何を学び、何は扱わないのか

プログラミングを始めたばかりの人にとっては「動けばいいじゃないか」と感じる話題かもしれません。しかし、コーディング規約は **"将来の自分と他人のために書く"** という、プログラミングの本質に関わる大切なテーマです。

---

## 0-1　コーディング規約とは何か

### ひとことで言うと

**コーディング規約とは、コードの書き方を揃えるための取り決めです。**

「書き方」には、大きく分けて次のようなものが含まれます。

| 分野 | 具体例 |
|------|--------|
| **命名** | 変数・関数・クラスの名前の付け方（`userName` か `user_name` か など） |
| **スタイル（整形）** | インデント（字下げ）の幅、改行の位置、スペースの入れ方 |
| **コメント** | 何に、どのタイミングで、どんな言葉で書くか |
| **ファイル構成** | ファイル名、フォルダ名、1ファイルの分量の目安 |
| **言語ごとの作法** | Pythonなら PEP 8、JavaScriptなら Airbnb など、言語公式・業界標準のルール |

### なぜ必要なのか — 「同じ機能なのに別物に見える」問題

同じ「ユーザー情報を取ってくる」という機能でも、書き方の取り決めがないとこんなに差が出ます。

**Aさんのコード**
```python
def getuserinfo(ID):
    u = db.find(ID)
    return u
```

**Bさんのコード**
```python
def get_user_information(user_id):
    user = db.find(user_id)
    return user
```

**Cさんのコード**
```python
def GetUser(id):
    return db.find(id)
```

3つとも「動く」という意味では同じです。でも、**同じプロジェクトにこの3つが混在する**と、読む人は毎回「これはどういう命名のルールだっけ？」と頭を切り替えることになります。これは、読みやすさ（ひいては保守性）を著しく下げます。

コーディング規約は、この「毎回考え直す」コストをなくすための取り決めです。

### 規約がもたらす3つの効果

1. **読みやすくなる（可読性）**
   書き方が揃うと、コードの意味そのものに集中できます。「どういう書き方だろう」という表面的な引っかかりが消えるからです。

2. **レビューが本質的になる**
   スタイルの指摘（「スペースが1つ多い」「改行が足りない」など）はツールが自動で直してくれます。人間は「このロジックで合っているか」「もっと良い設計はないか」という **本質的な議論** に集中できます。

3. **オンボーディング（新人が加わるとき）の負担が減る**
   規約があれば、新しく参加した人は「この書き方に従えばよい」と明確になります。逆に規約がないと、既存コードから空気を読んで真似するしかなく、混乱と不統一を生みます。

### チーム開発での役割

プログラミングは「書く時間」よりも **「読む時間」の方がずっと長い** と言われます。自分で昨日書いたコードでも、1か月後には他人のコードに見えることさえあります。

- **昨日の自分 ≒ 他人**（記憶は想像以上に早く薄れる）
- **同僚のコード = 他人**（当然、書き方の癖は違う）
- **AIが生成したコード = さらに他人**（生成のたびに揺らぐ）

コーディング規約は、こうした「さまざまな他人」が関わるコードベースで、**共通言語のような役割** を果たします。

> 💡 **補足：AI時代の重要性**
> 近年は ChatGPT や Claude などの生成AIがコードを書く場面が増えています。AIは指示が明確でないと、命名ルールも書き方も揺らぎます。だからこそ、**人間側が規約を持ち、AIの出力を規約に揃える** 作業がより重要になっています。

## 0-2　この教材で扱う範囲

### 扱うこと（このフォルダで学べること）

この `05_コーディング規約` フォルダでは、次の5つを中心に学びます。

| テーマ | 学ぶこと | 参照ノート |
|--------|---------|-----------|
| **可読性** | 読みやすいコードとは何か、どう書けば読みやすくなるか | [[04_コードの読みやすさ]] |
| **命名** | 変数・関数・クラスの名前の付け方、ケース（camelCase など）、略語の扱い | [[命名規則]]、[[05_命名規則とコーディング規約]]、[[07_変数名の略語（e,t,iなど）]] |
| **用語の統一** | プロジェクト内で使う言葉を揃える（用語集・略語辞典の考え方） | [[略語と用語集]] |
| **コメント** | いつ書くか、何を書くか、TODOの付け方、良い例・悪い例 | [[06_コメントの書き方]]、[[コメントとドキュメント]] |
| **自動整形（Lint・フォーマッター）** | 人手で揃えずツールに任せる、設定の共有、CIでの運用 | [[フォーマットとLint]] |

加えて、規約の **「崩れ方」と直し方** も扱います（[[08_命名規則の不統一]]）。現場では、最初にきれいに作っても時間とともに崩れていくものです。そこに対処する目を育てるのが目的です。

### 扱わないこと（この教材のスコープ外）

次のテーマは「参照として名前を出すだけ」または「別フォルダに譲る」方針です。

- **言語ごとの詳細な公式スタイルガイド**
  PEP 8（Python）、Airbnb Style Guide（JavaScript）、Effective Java などは、原典へリンクする形で扱います。深追いは各言語の学習時に。

- **特定フレームワークのファイル配置**
  React のコンポーネント分割や、Next.js のディレクトリ規約などは、フレームワーク固有のノートに譲ります。

- **Git のコミットメッセージ規約・ブランチ命名**
  重要なテーマですが、Git 側のフォルダで扱う内容です。

- **セキュリティ・アクセシビリティの最低限規約**
  より専門の章で扱います（拡張トピック扱い）。

### この教材の「深さ」

想定しているのは、次のレベルの読者です。

- **対象**：プログラミングの基本（変数・関数・条件分岐など）が書ける人
- **前提としないこと**：特定言語の熟練度、大規模開発の経験
- **ゴール**：自分の書くコードを、自然と「読みやすい形」に寄せられるようになること／チームで規約を議論できる足場を作ること

言語は **Python と JavaScript/TypeScript** を中心に例を出します。この2つは仕事・学習の両面で触れる機会が多く、かつ書き方の流儀が適度に違うため、規約の「違いのある世界」を学ぶのに向いています。

## 学習のすすめ方

目次（[[010Programming/02_Foundations/03_設計/階層/05_コーディング規約/目次]]）でも触れていますが、おすすめの順序はこうです。

1. **まず「なぜ」を掴む** — 読みやすさがなぜ大事なのか（Part 1）
2. **次に「命名」** — 実際のコードで一番触る部分（Part 2）
3. **そして「コメント」** — 人間の言葉で補う部分（Part 3）
4. **最後に「ツール」** — 機械に任せる部分（Part 4）

この順序には意味があります。**人間が意識すべきこと → 機械に任せられること** の順で学ぶと、「なぜこのツールが必要なのか」が自然に腑に落ちるからです。

逆にツール（Prettier、ESLint など）から入ると、「言われた通り設定したけど、何を直してくれているのか分からない」という状態になりやすいので注意してください。
