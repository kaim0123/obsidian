# 環境変数と `export`

## この文書のねらい

bash で「設定を変える」ために必ず出てくるのが **環境変数**。
`PATH` を通す、API キーをコマンドに渡す、`LANG` を UTF-8 にする — すべて環境変数の仕事。

ここでは **「シェル変数」と「環境変数」の違い**、`export` が何をしているか、どこに書くのが正解か、をきっちり押さえる。

---

## 1. 変数の種類は 2 つ

### 1-1. シェル変数

```bash
name="Alice"
echo "$name"         # → Alice
```

- 代入した **そのシェルの中だけ** で有効
- 子プロセス（新しく起動するコマンド）には **引き継がれない**

### 1-2. 環境変数

```bash
export NAME="Alice"
echo "$NAME"         # → Alice
```

- **子プロセスにも引き継がれる**
- ほぼすべての言語・ツールが「環境変数」を読む API を持っている
  （Python の `os.environ`、Node の `process.env`、etc）

---

## 2. `export` は何をしているか

> **変数に「外に持ち出してOK」の印をつける。**

```bash
x=1                  # シェル変数（このシェル内でのみ有効）
export x             # 環境変数に「昇格」
export y=2           # 宣言と同時に export
```

### 2-1. 確かめ方

```bash
env                  # 環境変数だけを一覧
set                  # すべての変数（シェル変数含む）
echo $x              # 個別に確認
```

### 2-2. 引き継ぎを体感する

```bash
x=1
bash -c 'echo $x'     # → （空）子プロセスに渡っていない

export x=1
bash -c 'echo $x'     # → 1
```

**これが `export` の意味**。

### 2-3. `unset` で消す

```bash
unset x              # 変数そのものを削除
export -n x          # 「export 属性」だけを外す（シェル変数として残る）
```

---

## 3. 代入時の注意点

### 3-1. `=` の前後に空白を入れない

```bash
x = 1     # ❌ エラー（これはコマンド実行と解釈される）
x=1       # ✅
```

### 3-2. 値に空白を含めるときはクォート

```bash
msg="Hello, world"
path="/home/my dir"
```

### 3-3. 変数参照は `"$var"` を推奨

```bash
rm -rf $dir      # dir="/ tmp" だと危険
rm -rf "$dir"    # 文字列として 1 つ扱い
```

- 空白を含むパス、空文字列で思わぬ挙動を防げる

---

## 4. 一時的に変数を渡す（コマンド前置記法）

```bash
LANG=en_US.UTF-8 man ls
```

- そのコマンド **1 回だけ** 環境変数を上書きできる
- シェル全体には影響しない

よく使う例：

```bash
DEBUG=1 ./script.sh
NODE_ENV=production npm start
http_proxy=http://proxy.example.com curl https://example.com
```

## 5. `PATH` — 最重要の環境変数

> **初めて PATH を触る場合** → 先に `PATHとprofile入門.md`（探し物リスト・`.profile` の関係・「Cursor では動くのに別ターミナルでは動かない」原因）を読むと理解しやすい。

### 5-1. 何をしているか

コマンド名を入力したときに、**どのディレクトリから実行ファイルを探すか** のリスト。

```bash
echo $PATH
# /usr/local/bin:/usr/bin:/bin:/home/alice/.local/bin
```

- `:` で区切られたディレクトリの列
- **左から順に** 検索される（同名コマンドがあれば左優先）

### 5-2. PATH に追加する

```bash
export PATH="$HOME/bin:$PATH"       # 先頭に追加（自作を優先）
export PATH="$PATH:$HOME/bin"       # 末尾に追加（システム優先）
```

**先頭・末尾の使い分け**：
- **先頭**：自作ツール・言語バージョン管理（nvm, pyenv）で、システム既定より優先したい
- **末尾**：システムを尊重し、自作を「後回し」にしたい

### 5-3. よくあるトラブル

```bash
which python         # どのバイナリが呼ばれているか
type -a python       # すべての候補を表示
```

- 複数バージョンが入っていて期待通りに呼ばれない
- `PATH` の順序が原因のことが多い

## 6. よく使う環境変数

| 変数              | 用途                                             |
|-------------------|--------------------------------------------------|
| `HOME`            | ホームディレクトリ                               |
| `USER`            | ユーザー名                                       |
| `SHELL`           | ログインシェルのパス                             |
| `PATH`            | コマンド検索パス                                 |
| `LANG` / `LC_ALL` | ロケール（日本語なら `ja_JP.UTF-8`）             |
| `EDITOR`          | 既定エディタ（`git commit` などで使う）          |
| `PAGER`           | ページャ（`man` などで使う。`less` が一般的）    |
| `TERM`            | 端末の種類（`xterm-256color` など）              |
| `http_proxy` / `https_proxy` | HTTP プロキシ                        |
| `LD_LIBRARY_PATH` | 共有ライブラリの検索パス（Linux）                |
| `TZ`              | タイムゾーン                                     |

## 7. どこに書くのが正解か

**結論：ログインシェルでも読まれる `~/.bash_profile` or `~/.profile` に書くのが基本**。
ただし対話シェル起動のたびに読みたいものは `~/.bashrc` に。

| 置きたいもの                     | 置き場                              |
|----------------------------------|-------------------------------------|
| `PATH` の追加                    | `~/.bash_profile` / `~/.profile`    |
| `EDITOR`, `LANG` などの標準設定  | `~/.bash_profile` / `~/.profile`    |
| エイリアス、シェル関数           | `~/.bashrc`                         |
| プロンプト（`PS1`）              | `~/.bashrc`                         |

詳しくは `bashrcとbash_profile.md`。

### プロジェクトごとに切り替える `.env` と `direnv`

秘密情報（API キーなど）は `~/.bashrc` に書かず、プロジェクト内の `.env` ファイルで管理するのが現代的：

```bash
# .env
DATABASE_URL=postgres://...
OPENAI_API_KEY=sk-xxx
```

`.env` を自動で読み込むツール **`direnv`** を導入すると、ディレクトリに入った瞬間に環境変数がセットされる。秘密情報は **Git に含めない**（`.gitignore` に `.env` を追加）。

## 8. システム全体 vs 個人

| スコープ                 | ファイル例                                      |
|--------------------------|-------------------------------------------------|
| 全ユーザー（システム）   | `/etc/profile`, `/etc/environment`, `/etc/bash.bashrc` |
| 個人                     | `~/.bash_profile`, `~/.bashrc`, `~/.profile`    |
| プロジェクト             | `.env` + direnv / `source` する                 |
| そのコマンドだけ         | `VAR=x command`                                 |

- 個人の好みは **ホーム配下のドットファイル** に
- システム全体をいじる（`/etc/...`）のは慎重に

---

## 9. 設定変更を反映する

`.bashrc` を書き換えただけでは現行シェルに反映されない。次のどれかで反映する：

```bash
source ~/.bashrc       # ドットコマンドでも同じ： . ~/.bashrc
```

または **新しいターミナルを開き直す**。

---

## 10. つまずきやすいポイント

| 症状                                            | 原因・対処                                       |
|-------------------------------------------------|--------------------------------------------------|
| 子スクリプトで変数が空                          | `export` していない                               |
| `.bashrc` に書いたのに SSH ログイン後に効かない | ログインシェルでは読まれない。`.bash_profile` へ |
| `PATH` に追加したのに効かない                   | 区切り文字は `:`（コロン）。`;` や空白はダメ     |
| `PATH` を壊してコマンドが動かなくなった         | `/bin/bash --norc` で最小起動、フルパスで `/bin/vi ~/.bashrc` |
| 日本語が文字化け                                | `LANG=ja_JP.UTF-8` 相当に設定                    |
| `.env` を Git に上げてしまった                  | `.gitignore` 追加、履歴は `git filter-repo` 等で削除 |

---

## 11. まとめ

- **シェル変数 vs 環境変数**、違いは「子プロセスに渡るか」。`export` がその境界
- **`=` の前後に空白を入れない**、**値はダブルクォート**
- **`PATH` は `:` 区切り、左が優先**
- **永続化は `.bash_profile` / `.bashrc`** を使い分け（→ 別ドキュメント）
- **秘密情報は `~/.bashrc` に直書きしない**。`.env` + direnv が現代の作法

「この設定はどのシェルで生きているか」「子プロセスに渡っているか」を常に意識できると、環境トラブルが劇的に減る。
