# ファイル権限 — ACL と chmod の違い

## はじめに

Windows と Linux は **ファイル権限の仕組みが根本的に違います**。

- **Linux**: `chmod 755` のような **シンプルな3ビット制**（所有者・グループ・その他）
- **Windows**: **ACL**（Access Control List）による **柔軟で複雑な権限** 制御

両方を扱う WSL 環境では、この違いを理解しておかないと「chmod が効かない」「権限がおかしい」といった問題に遭遇します。

---

## Linux 流: chmod と 3ビット制

### 基本の仕組み

Linux のファイルには **3つの「誰が」** に対して **3つの権限** が設定されています。

```
      ユーザー  グループ  その他
-rwxr-xr-x
  rwx     r-x      r-x

r = read (4)
w = write (2)
x = execute (1)

rwx = 4+2+1 = 7
rw- = 4+2   = 6
r-x = 4+1   = 5
```

### コマンド例

```bash
ls -l file.txt
# -rw-r--r-- 1 kai kai 1024 Apr 22 12:00 file.txt

chmod 755 script.sh     # rwxr-xr-x（所有者=フル、他=読み実行）
chmod 644 file.txt      # rw-r--r--（所有者=読み書き、他=読み）
chmod +x script.sh      # 実行権限を付加
chown user:group file   # 所有者・グループ変更
```

### シンプルさがメリット

- 8進数3桁で全権限が表現できる
- `ls -l` で一目瞭然
- 歴史が長く、ツールも豊富

### 限界

- 「ユーザーA には読みだけ、ユーザーB には書きまで」のような **個別指定は不可**
- もっと細かい制御には **POSIX ACL**（setfacl / getfacl）という拡張が必要

---

## Windows 流: ACL

### 基本の仕組み

**ACL**（Access Control List）は、ファイル・フォルダごとに **誰に何を許可するか** の **リスト** を持ちます。

```
file.txt の ACL:
  ├── Administrators : フルコントロール
  ├── SYSTEM         : フルコントロール
  ├── kai           : 読み取り・書き込み
  ├── alice         : 読み取り
  └── Everyone       : (明示的拒否)
```

### 権限の種類（NTFS 詳細権限）

- **フルコントロール**
- **変更**
- **読み取りと実行**
- **フォルダーの内容一覧表示**
- **読み取り**
- **書き込み**
- **特殊なアクセス許可**

さらに細分化された14種類の詳細権限もあり。

### 継承

- 親フォルダの ACL が子ファイル・フォルダに継承される
- 継承を切って独立した ACL を持たせることも可能

---

## ACL を見る・設定する

### GUI（エクスプローラー）

1. ファイル/フォルダを右クリック → プロパティ
2. **セキュリティ** タブ
3. ユーザーを選ぶと「許可」「拒否」のチェックボックスが見える
4. 「編集」で変更、「詳細設定」でさらに細かく

### コマンドライン: `icacls`

```cmd
REM 確認
icacls file.txt

REM 出力例:
REM file.txt NT AUTHORITY\SYSTEM:(F)
REM          BUILTIN\Administrators:(F)
REM          kai:(M)

REM 権限追加
icacls file.txt /grant kai:F
REM F=フル、M=変更、RX=読み取り実行、R=読み取り、W=書き込み

REM 権限削除
icacls file.txt /remove kai

REM 継承をリセット
icacls file.txt /inheritance:r /grant:r Administrators:F /grant:r kai:M
```

### PowerShell: `Get-Acl` / `Set-Acl`

```powershell
# 取得
$acl = Get-Acl -Path "C:\data\file.txt"
$acl.Access

# 権限追加
$rule = New-Object System.Security.AccessControl.FileSystemAccessRule(
    "kai",
    "Read",
    "Allow"
)
$acl.AddAccessRule($rule)
Set-Acl -Path "C:\data\file.txt" -AclObject $acl
```

---

## 代表的なユーザー・グループ

| 名前 | 説明 |
|------|------|
| **SYSTEM** | OS 自身のアカウント。高い権限 |
| **Administrators** | 管理者グループ |
| **Users** | 標準ユーザーグループ |
| **Everyone** | すべてのユーザー（匿名含む） |
| **TrustedInstaller** | OS ファイルの所有者（管理者でも変更不可な場合がある） |
| **NETWORK SERVICE / LOCAL SERVICE** | サービス用アカウント |

## WSL での chmod と ACL の接続

### 既定の挙動（`/mnt/c/` 上）

WSL2 から Windows ドライブを見ると、**chmod がほぼ効かない** ことがあります。

```bash
chmod 600 /mnt/c/project/secret.txt
ls -l /mnt/c/project/secret.txt
# -rwxrwxrwx  ← 毎回 777 に見える
```

これは、Windows の NTFS と Linux の chmod の **メタデータが別** だから。

### metadata オプションで解決

`/etc/wsl.conf`:

```ini
[automount]
options = "metadata,umask=22,fmask=11"
```

- `metadata`: Linux の権限情報を Windows の NTFS 拡張属性に保存
- `umask=22`: ディレクトリのマスク（=755）
- `fmask=11`: ファイルのマスク（=644）

再起動:
```powershell
wsl --shutdown
```

これで `chmod` が WSL 側から有効になります。ただし **Windows エクスプローラーから見た ACL とは連動しない** ため、相互編集する場合は注意。

### 純粋な WSL 側（`~/` など）

ext4 上のファイルは Linux 標準の権限管理。`chmod 755` は普通に機能する。

## よくあるシナリオと対処

### 1. 「アクセスが拒否されました」

- まず自分の権限を確認: `icacls file.txt` or プロパティ > セキュリティ
- 管理者としてコマンドを実行してみる（UAC）
- 所有権を取得（次節）

### 2. 所有権を取得したい

```cmd
takeown /F "C:\path\to\file.txt"
takeown /F "C:\path\to\folder" /R /D Y    # フォルダを再帰的に
```

その後で `icacls` で権限付与。

### 3. 「フルコントロール」があるのに書き込めない

- **読み取り専用属性** が付いている可能性:
  ```cmd
  attrib -R file.txt
  ```
- またはファイルがロックされている（他プロセスが開いている）

### 4. OneDrive/Dropbox 同期フォルダで権限問題

- クラウド同期アプリが ACL を変更することがある
- 開発用フォルダは同期フォルダから外すのが無難

### 5. Git が権限を追跡しない

- NTFS では実行ビットが曖昧。Git は **`core.filemode = false`** で対応
- Linux ↔ Windows で共有するリポジトリでは自動設定される

### 6. WSL で chmod 600 にしても「Bad owner or permissions」

例: SSH 秘密鍵を `/mnt/c/` に置いているとき。
→ **WSL 側（`~/.ssh/`）に置くのが正解**。/mnt/c/ 上では権限設定が不安定。

## 実行可能ファイルの扱いの違い

### Linux

- `chmod +x` で実行可能
- ファイル先頭のシバン（`#!/bin/bash`）で解釈プログラムを指定
- 拡張子は不問

### Windows

- **拡張子** で実行可能かを判断（`.exe`, `.bat`, `.ps1` 等）
- `PATHEXT` 環境変数のリストに含まれるもの
- **実行ビットの概念なし**（NTFS には「実行」権限はあるが、拡張子優先）

### WSL では中間

- WSL 内では Linux 流（chmod +x）
- `/mnt/c/` のファイルを実行するとき、Windows バイナリは拡張子で判断

## セキュリティ的な注意

### 1. Everyone にフルコントロールを付けない

開発中に面倒だからと `icacls . /grant Everyone:F /T` してしまうと、誰でも改変可能に。

### 2. 「継承の無効化」は慎重に

親の継承を切ると、親フォルダの権限変更が反映されない。大規模なフォルダ構造で事故の元。

### 3. SYSTEM / Administrators を消さない

これらを消すと自分自身もアクセスできなくなることがある（takeown が必要に）。

### 4. シンボリックリンクの作成権限

Windows では、シンボリックリンクを作るのに **管理者権限** または **開発者モード** が必要。WSL は内部では管理者扱いで作れる。

---

## ACL と POSIX ACL の違い（補足）

Linux にも `setfacl` / `getfacl` を使った **POSIX ACL** があり、Windows の ACL に近い柔軟性を持ちます。しかし:

- 設定が Linux 3ビット制と **二重管理** で混乱しやすい
- 使われる場面が限定的
- 通常の Linux 作業では `chmod + chown` で十分

---

## 実務的な推奨

### 開発環境

- 開発プロジェクトは **自分のユーザー専用フォルダ** に置く（`C:\Users\kai\` または `~/`）
- 権限で困ったら、まず ACL と Linux 権限のどちらの問題かを切り分ける

### 共有サーバー

- 明示的な ACL 設計（各メンバーの役割別に）
- グループを作って、グループに権限付与（個別ユーザー管理は破綻しがち）
- `icacls` の設定はスクリプト化して再現可能に

---

## まとめ

- Linux は **chmod の3ビット制**（シンプル）
- Windows は **ACL**（柔軟で強力、複雑）
- WSL の `/mnt/c/` では **`metadata` オプション** で chmod が効くようになる
- 「アクセス拒否」は **ACL / 読み取り専用属性 / UAC昇格** のどれかを疑う
- 確認は `icacls` や PowerShell の `Get-Acl`、GUI ならプロパティのセキュリティタブ
- 開発の基本: 自分のユーザー所有フォルダで作業、秘密鍵は WSL の `~/.ssh/` に
