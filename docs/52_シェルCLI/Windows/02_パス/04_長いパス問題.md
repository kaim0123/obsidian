# 長いパス問題 — 260文字制限と LongPathsEnabled

## はじめに

Windows には **伝統的に「パスの長さは 260 文字まで」** という制限があります。この制限を「**MAX_PATH 問題**」「長いパス問題」と呼びます。

現代の開発では:

- `node_modules` の深いネスト
- `C:\Users\長い名前\Documents\project-a\subproject-x\src\components\views\...`

などで簡単に超えてしまい、**コピー・削除・Git clone が失敗する** トラブルを引き起こします。

---

## 問題の詳細

### MAX_PATH = 260 の内訳

Windows API の伝統的な定数:

```c
#define MAX_PATH 260
```

内訳:
- ドライブレター `C:\`: 3文字
- パス本体: 256文字
- 終端ヌル文字 `\0`: 1文字
- **合計: 260文字**

### 何が壊れるか

- エクスプローラーでコピー/削除できない
- `cmd` / 古い API で操作できない
- Git clone 失敗（特に Windows 側ファイルで、Linux 由来のリポジトリ）
- インストーラ失敗
- ビルド失敗（Java、Go、.NET 等）
- Electron / Node.js の依存深さで発生

---

## 制限を超えるとどうなる

### よくあるエラー

```
The specified path, file name, or both are too long.
The fully qualified file name must be less than 260 characters.
```

```
ENAMETOOLONG: name too long
```

```
fatal: unable to checkout working tree
warning: Clone succeeded, but checkout failed.
You can inspect what was checked out with 'git status'
```

### 操作不能なファイル

作成できてしまうこともあり（特に WSL や UNC 経由で）、その後 Windows エクスプローラーでは **開けない・消せない・見えない** 状態に。

---

## 解決策1: LongPathsEnabled を有効化（Windows 10 1607+）

Windows 10 以降、**260文字制限を解除** できるようになりました。

### レジストリで有効化

管理者 PowerShell で:

```powershell
New-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem" `
                 -Name "LongPathsEnabled" -Value 1 -PropertyType DWORD -Force
```

### グループポリシーで有効化

1. `gpedit.msc` を起動
2. **コンピューターの構成 → 管理用テンプレート → システム → ファイルシステム**
3. 「**Win32 の長いパスを有効にする**」を **有効** に

### 制限

- **有効化しても、古いアプリは対応していない**
- アプリが以下のいずれかで対応している必要がある:
  - **.exe の manifest** に `<longPathAware>true</longPathAware>`
  - **Unicode API** と `\\?\` プレフィックスを使っている
- エクスプローラー、PowerShell 7、最近のビルドツールは対応
- cmd.exe、古い VB アプリなどは非対応が多い

---

## 解決策2: `\\?\` プレフィックス

Windows API に **`\\?\`** プレフィックスを付けると、長さ制限が緩和されます。

```
\\?\C:\very\long\path\...   最大 32767 文字（UNICODE 版 API）
```

### PowerShell で使う

```powershell
Get-ChildItem "\\?\C:\very\long\path\"
```

### 注意

- **相対パス不可**（絶対パスのみ）
- **スラッシュ `/` は区切り文字として解釈されない**
- 関数によっては対応していない

UNC パス用には `\\?\UNC\server\share\...`。

---

## 解決策3: そもそも短いパスにする

最も確実な対処。

### プロジェクト配置の工夫

```
❌ C:\Users\甲斐PRO\Dropbox\Work\2024\Projects\Frontend\MyAwesomeApp\src\...
   （ユーザー名＋Dropbox＋カテゴリで60文字消費）

✅ C:\dev\myapp\src\...
   （短くシンプル）
```

開発用に `C:\dev\` や `D:\src\` のような短いルートを用意するのがおすすめ。

### ディレクトリのジャンクション

長いパスを短いパスに別名を付ける:

```cmd
mklink /J C:\dev\myapp "C:\Users\長い名前\Documents\Projects\MyApp"
```

`C:\dev\myapp` から実体にアクセス可能に。

### node_modules の平坦化

- npm v3 以降、依存はデフォルトで平坦化
- それでも深くなる場合、`yarn`（Plug'n'Play）や `pnpm` で問題を回避可能
- `pnpm` は symlink 方式で極端に短いパスを維持

---

## 解決策4: WSL に移す

WSL 側（ext4）は、パス長制限が Linux 準拠（ファイル名255文字、パス全長4096文字）。

**Linux 前提のプロジェクト**（Node.js、Python、Go等）は、WSL 内に置けば MAX_PATH 問題から解放される。

```bash
# WSL 内で作業
cd ~/projects/myapp
git clone ...
```

ただし `/mnt/c/` 経由だと Windows 側の制限に戻る。

---

## 解決策5: 古いツールは「短縮名」を使う

Windows には DOS 互換の **8.3 形式短縮名**（`PROGRA~1` = `Program Files`）がある。

```cmd
dir /x    # 短縮名を表示
```

古いツール限定の回避策。現代ではほぼ不要。

## 主な言語・ツールの対応状況

| 対象 | 長いパス対応 |
|------|-------------|
| Windows Explorer | ✅ LongPathsEnabled で対応 |
| PowerShell 7 | ✅ 対応 |
| PowerShell 5.1 | ⚠ 一部対応（cmdlet 次第） |
| cmd.exe | ❌ 非対応 |
| .NET 4.6.2+ | ✅ LongPathsEnabled で対応 |
| Node.js | ⚠ 一部制約あり（`\\?\` 前提の部分も） |
| Git for Windows | ✅ `core.longpaths=true` 設定で |
| VS Code | ✅ 対応 |
| Visual Studio | ✅ 対応 |

### Git の長いパス対応

```bash
git config --global core.longpaths true
```

これで Git が 260 を超えるファイルを扱えるようになる。LongPathsEnabled と併用推奨。

---

## 典型的なトラブルと対処

### 1. `node_modules` でコピー・削除できない

```
D:\project\node_modules\.bin\@babel\...\node_modules\...\...（260超）
```

**対処**:
- `rimraf` を使う（Node.js の `fs.rm` をラップ、長いパス対応）
  ```bash
  npx rimraf node_modules
  ```
- `pnpm` に移行
- プロジェクトを短いパスに移動

### 2. Git clone が失敗

```
warning: Clone succeeded, but checkout failed.
```

**対処**:
```bash
git config --global core.longpaths true
# LongPathsEnabled もレジストリで有効化
```

### 3. ビルドが失敗（Maven / Gradle / dotnet）

パスの深さを浅くする、ジャンクションを使う、LongPathsEnabled を有効化。

### 4. `.git` フォルダ自体が長い

フォルダ名を短くしてクローンし直す:
```bash
git clone https://github.com/xxx/long-repository-name.git lr
```

---

## 設定の優先順位（まとめて有効化）

開発 PC の推奨初期設定:

1. **LongPathsEnabled** をレジストリで `1`
2. **グループポリシー**でも有効化（ある場合）
3. `git config --global core.longpaths true`
4. プロジェクトは **浅いルート**（`C:\dev\`、`D:\src\`）に置く
5. 深くなりがちな依存（npm）は **pnpm** か **WSL** に逃がす

---

## PowerShell で確認スクリプト

```powershell
# 長すぎるパスを探す
Get-ChildItem -Path C:\project -Recurse -Force -ErrorAction SilentlyContinue |
    Where-Object { $_.FullName.Length -gt 240 } |
    Select-Object FullName, @{N='Length';E={$_.FullName.Length}} |
    Sort-Object Length -Descending |
    Select-Object -First 20
```

260近いパスが列挙される。

---

## まとめ

- Windows の **MAX_PATH = 260** は歴史的な制限
- **LongPathsEnabled** をレジストリ/ポリシーで有効化すれば緩和（ただしアプリ側の対応も必要）
- **Git は `core.longpaths=true`** も忘れずに
- 根本対策は **プロジェクトを短いパスに置く** こと
- **WSL 側に逃がす**、**`pnpm` に移行** も有効な選択肢
- `\\?\` プレフィックス、ジャンクションといった小技も覚えておくと救われる
