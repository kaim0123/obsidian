## 1. 見積もりと契約

分析と設計を厳密に分離し、「設計書完成＝見積確定」とする契約は、モデルを育てる開発と相性が悪いことがあります。

| 古典的な前提 | モデル中心の現実 |
|--------------|------------------|
| 要件が先に固まる | 動かしながら理解が深まる |
| 詳細設計書で工数を積む | 関心事の塊・シナリオ単位で見える |
| 変更は別契約 | 変更は本流（スコープの再合意が要る） |

現実的なやり方の例:

- **段階的な合意** — 中核ドメインと最初のシナリオでざっくり、学習後に見直す  
- **成果物を「動くソフト＋テスト＋俯瞰図」** に置く（詳細仕様のページ数ではない）  
- 契約上どうしても固定が要る部分（納期・必須シナリオ・非機能の下限）だけ先に固める  

API など外向け契約の共同作業は [[03_チームでAPI設計を守る]]・[[04_発展性のあるAPI開発]] も参考。

## 2. 進捗の判断

「何％設計書が書いたか」より、次が見えると判断しやすいです。

| 見えやすい進捗 | 見えにくい進捗 |
|----------------|----------------|
| 動くシナリオの数、受け入れ可能な振る舞い | クラス図のページ数だけ |
| テストが通る関心事のかたまり | 「あと少しで設計完了」 |
| モデル用語の安定度（変更頻度の低下） | 未検証の詳細仕様 |

バーンダウンやカンバンは、**ユーザー／業務が理解できる単位**（シナリオ、コト、画面タスク）で切ると、ドメインモデル中心開発と揃います（[[07_アプリケーション機能を組み立てる]]・[[09_画面とドメインオブジェクトの設計]]）。

---

## 3. 品質保証

| 観点 | モデル中心での捉え方 |
|------|----------------------|
| **正しさ** | ドメインの不変条件・自動テスト・例示（具体例） |
| **変更容易性** | レビューで関心事の置き場所を見る（[[04_設計レビューの実践]]） |
| **回帰** | テストが第一級ドキュメント（[[03_テストと設計の関係]]） |
| **非機能** | 目標をテスト／測定可能な形で残す（[[03_非機能テスト概要]]） |

「設計レビュー完了スタンプ」だけに頼らず、**動く仕様（テスト）とコードレビュー**を品質の中心に据えます。QA プロセス全体は [[MOC_QAプロセス]]。

---

## 4. 要員と体制

| 役割のイメージ | 向き合い方 |
|----------------|------------|
| **ドメインに強い人** | モデルとユビキタス言語の世話役（専任の「書き手」だけに閉じない） |
| **実装者** | 分析の傍観者ではなく、モデル対話の当事者 |
| **顧客／業務側** | 例とシナリオでフィードバック（文書レビューだけにしない） |

分析チームと製造チームを壁で分けると、分析＝設計の一体が壊れやすいです。小さくても **同じ言葉でモデルを触る横断**（ペア、合同モデリング、短いレビュー）を残します（[[02_ユビキタス言語]]・[[01_チームで設計を守る]]）。

---

## まとめ

- 見積・契約は「詳細設計完了」前提を緩め、動く単位と段階合意に寄せる  
- 進捗はシナリオ／テスト／モデルの安定で見る  
- 品質はテストと設計レビューを一体に  
- 体制は分析と実装の壁を薄くし、言語を共有する
