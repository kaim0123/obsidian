# オブジェクト指向設計の教え方

## 1. 説明の落とし穴

| やりがち | 起きること |
|----------|------------|
| 「オブジェクトとは〜」から講義 | 意味が不明なまま用語だけ増える |
| メリットを抽象語で並べる | 「なぜよいか」が実感できない |
| 完成したクラス図を見せるだけ | どう辿り着くかが分からない |

学習者と同じく、**臭いのあるコード → 小さな改善 → 差の体感** の順が伝わりやすいです（[[06_オブジェクト指向設計の学び方]]）。

---

## 2. 教え方の型

### 2.1 実際の（または近い）コードで比べる

同じ仕様の「手続き寄り」と「関心事を閉じた」版を並べ、変更タスクを1つ出してどちらが楽かを体験させる。

### 2.2 臭いを手がかりにする

重複・長いメソッド・巨大クラスを指摘し、対応するリファクタ名までつなぐ（[[03_コードの臭いとリファクタリング対応表]]・[[04_Extract_Method]]）。「センス」ではなく **観察可能なサイン** で教える。

### 2.3 少しずつ・テスト付きで直す

一気に理想形へ飛ばさせない。PR やペアでは「このメソッドだけ」「この重複だけ」に範囲を限る（[[04_リファクタリングの考え方]]）。

### 2.4 期間限定の過激な規則

Object Calisthenics を **スパイクや勉強会の期間限定ルール** として課すと、古い癖が自覚しやすい（[[06_Object_CalisthenicsでOOを体得する]]）。本番コードに永久適用する必要はない。

### 2.5 レビューで設計観点を言葉にする

「動くから LGTM」だけでなく、関心事の置き場・名前・テスト容易性を短い質問で返す（[[04_設計レビューの実践]]・[[01_チームで設計を守る]]）。

## 3. 書籍への導き方

| 段階 | 勧めるもの |
|------|------------|
| 手を動かしたあと | Beck『実装パターン』— 小さな書き方の語彙 |
| モジュールの信頼を深めたい | Meyer『オブジェクト指向入門』— 契約・カプセル化 |
| 業務を中心に据えたい | Evans『ドメイン駆動設計』— モデルと実装の一致 |

「先に全部読んでから書け」より、**現場の痛みと本の章を対応づけて紹介する**方が定着します（パターン暗記の失敗と同型 → [[デザインパターンを覚える人が伸びない理由]]）。

## まとめ

- 定義講義より、コード比較と小さな改善で教える  
- 臭い・リファクタ名・レビュー質問を共通言語にする  
- Calisthenics は期間限定の筋トレ、書籍は体得のあとに
