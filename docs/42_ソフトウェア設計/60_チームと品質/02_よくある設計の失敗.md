# よくある設計の失敗

## この章の目的

**アンチパターン** — よくある設計の失敗 — を知り、回避と改善の考え方を学びます。

> 一覧は [[付録E_アンチパターン一覧]] を参照。

---

## 1. 大泥団（Big Ball of Mud）

境界のない単一モデルに全機能が詰め込まれた状態です。

| 症状 | 対策 |
|------|------|
| 用語が文脈なく混在 | 境界づけられたコンテキストで分割 |
| 変更が全体に波及 | モジュール・集約で境界を引く |
| 誰も全体を理解できない | 段階的にコンテキストを分離 |

---

## 2. 神クラス・神サービス

**God Object / God Class** — すべてを担当する巨大なクラス・サービスです。

```text
  ApplicationService
    ・注文処理
    ・在庫更新
    ・メール送信
    ・レポート生成
    ・ユーザー管理  … 全部入り
```

**対策**: 変化の理由で分割。SRP を意識（[[010Programming/44_クラス設計・デザインパターン/00_全体像/目次|クラス設計 目次]]）。

---

## 3. 貧血ドメインモデル

エンティティがデータ入れ物で、ロジックがサービス層に集中した状態です。

```text
  Order { id, status, total }  … getter/setter のみ
  OrderService { validate(), calculate(), save(), notify() }  … 全部ここ
```

**対策**: 振る舞いをエンティティ・値オブジェクトに移す（[[01_戦術的設計]]）。

---

## 4. 過剰な抽象化とパターンの乱用

| 症状 | 例 |
|------|-----|
| インターフェースの乱立 | 実装が 1 つしかないのに Interface |
| パターンのためのパターン | 単純な if で足りるのに Strategy 5 クラス |
| 深い継承階層 | 理解に 30 分かかる |

**対策**: YAGNI。問題が見えてからパターンを適用（[[07_変化に強い設計の考え方]]）。

---

## 5. 失敗から学ぶ改善の進め方

1. **名前を付ける** — 「これは神クラス」「これは大泥団」
2. **影響範囲を限定** — 一度に全部直さない
3. **テストを足す** — リファクタリングの安全網
4. **小さく分割** — Extract Class / Extract Module
5. **振り返る** — なぜそうなったか。ルールで防げるか

```text
  失敗は学習材料。責めずに「次はどうするか」を議論する
```

---

## まとめ

- 大泥団・神クラス・貧血モデル・過剰抽象化は典型の失敗
- 名前を付け、影響を限定し、段階的に改善
- 失敗からルールと学びを得る
