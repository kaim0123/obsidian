# レガシーとの向き合い方

## この章の目的

**レガシーコード** に対して、現実的に設計を改善していく考え方を学びます。

---

## 1. レガシーコードとは何か

**レガシーコード** とは、一般的に **テストがなく・理解が困難・変更が怖い** コードを指します。

- 悪意あるコードとは限らない
- 「当時の制約で作られた、今は負債になったもの」が多い
- 多くの現場では **新規より改修** の方が時間を使う

```text
  レガシー = 設計の練習場でもある
  いきなり全部書き直すのは現実的でないことが多い
```

---

## 2. 理解してから変える

変更の前に **理解** します。

| 手法 | 内容 |
|------|------|
| 読む・動かす | 実際に実行し、挙動を確認 |
| テストを追加 | 変更の安全網（characterization test） |
| 図を描く | 現状の依存関係を可視化 |
| 小さな変更 | 1 箇所だけ直し、影響を観察 |

**「理解なしの大規模リファクタリング」** は新たなバグの温床です。

---

## 3. 絶えず小さく改善する

**ストラングラーパターン** — 少しずつ新しい設計に置き換える — が現実的です。

```text
  巨大な OrderService
       │
       ├── まず calculateTotal() を純粋関数に抽出
       ├── 次に Repository を注入可能に
       └── 最後に Order エンティティに振る舞いを移す
```

一度に全部やらず、**毎スプリント 1 つ** でも改善が積み上がります。

---

## 4. 境界を守りながらの段階的リファクタリング

新機能は **新しい設計** で書き、古い部分との境界を明確にします。

```text
  [レガシー OrderService]  … 触らない。バグ修正のみ
         │
         │  Adapter
         ▼
  [新 Order モジュール]     … 新機能はここに書く
```

**腐敗防止層（ACL）** で古いモデルと新しいモデルを変換します。

---

## 5. 設計を諦めない現実的なライン

すべてを理想設計にする必要はありません。

| 優先する | 後回しでもよい |
|---------|---------------|
| 変更が多い箇所 | ほぼ触らない箇所 |
| バグが多い箇所 | 安定している箇所 |
| 新機能の土台 | 廃止予定の機能 |

```text
  「完璧な設計」より「変更に強い箇所を増やす」
```

---

## まとめ

- レガシーは理解してから、小さく改善する
- ストラングラーと ACL で段階的に置き換え
- 優先度をつけ、全部を一度に直そうとしない
