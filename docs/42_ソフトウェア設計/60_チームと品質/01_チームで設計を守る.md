# チームで設計を守る

## この章の目的

チーム開発で **設計の意図を共有し、守る** ための実践を学びます。

---

## 1. 設計の合意形成

設計は **個人の頭の中だけ** にあると共有されません。

| 手法 | 内容 |
|------|------|
| 設計レビュー | たたき台を出して議論 |
| ペア設計 | 2 人で一緒に構造を決める |
| ADR | 判断の理由を文書化 |
| 用語集 | ユビキタス言語を共有 |

```text
  「なぜこう分けたか」を言語化できると、チームの判断が揃う
```

---

## 2. コードレビューで見るべき設計ポイント

機能の正しさだけでなく、**設計の観点** も見ます。

- [ ] 責務は **1 箇所** に集まっているか
- [ ] 依存の方向は **適切** か
- [ ] 命名は **意図を表している** か
- [ ] 境界（モジュール・レイヤー）を **越えていない** か
- [ ] テストは **適切な単位** で書かれているか

詳細チェックリストは [[010Programming/42_ソフトウェア設計/90_付録/付録B_チェックリスト|付録B_チェックリスト]] を参照。

---

## 3. 設計ルールの文書化

チームで守る **設計ルール** を短く文書化します。

```markdown
## 設計ルール（例）
- ドメイン層はインフラに依存しない
- 1 集約 1 トランザクション
- 新機能は既存モジュールの境界を越えない
- Utils に雑多な処理を追加しない
```

長大な設計書より、**短いルール + 例** の方が守られやすいです。

---

## 4. 設計負債の可視化

**設計負債** を隠さず、共有します。

| 可視化の方法 | 例 |
|-------------|-----|
| 課題チケット | 「Order と Inventory の循環依存を解消」 |
| コード内 TODO | `// DESIGN-DEBT: 本来はイベントで連携` |
| 定期的な振り返り | スプリントごとに負債リストをレビュー |

負債を **悪ではなく、投資の優先順位** として扱います。

---

## 5. 新人への設計の伝え方

- **全体像から** — 設計の階層、モジュール構成の地図
- **具体例で** — 良い例・悪い例のコード比較
- **小さなタスクから** — 1 モジュール内の変更から参画
- **レビューで** — なぜダメかを設計の観点で説明

「ルールを暗記」より **「なぜそうするか」を伝える** ことが定着につながります。

---

## まとめ

- 設計は合意形成と文書化で共有する
- コードレビューに設計観点を含める
- 短い設計ルールと負債の可視化
- 新人には全体像と理由から伝える
