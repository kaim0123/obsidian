# 設計レビューの実践

## この章の目的

設計レビューの **進め方・チェックリスト・改善提案** を学び、次の学習ステップへつなげます。

---

## 1. 設計レビューの進め方

### タイミング

- 新機能の **実装前**（たたき台レビュー）
- 大きなリファクタリングの **前後**
- 定期的な **設計健全性チェック**

### 進行（60 分の例）

1. **目的とスコープ**（5 分）— 何をレビューするか
2. **現状の説明**（15 分）— 図・主要なクラス・依存
3. **質問と議論**（30 分）— チェックリストに沿って
4. **アクション**（10 分）— 改善項目と担当

```text
  批判ではなく「改善のための対話」
  理由を聞き、代替案を一緒に考える
```

## 2. レビュー用チェックリスト

[[010Programming/42_ソフトウェア設計/90_付録/付録B_チェックリスト|付録B_チェックリスト]] の要約です。

### 構造

- [ ] 関心は分離されているか
- [ ] 凝集度は高く、結合度は低いか
- [ ] 依存の方向は適切か（ドメイン → 抽象 → 詳細）

### ドメイン

- [ ] 用語はユビキタス言語と一致しているか
- [ ] 業務ルールはドメイン層にあるか
- [ ] 貧血モデル・神クラスがないか

### 変化

- [ ] 変わりやすい箇所は隔離されているか
- [ ] 過剰な抽象化がないか（YAGNI）

### テスト・運用

- [ ] 単体テスト可能か
- [ ] イベント・非同期の追跡は可能か

## 3. 良い設計・悪い設計の比較

### 注文確定の例

**悪い例**:

```javascript
// Controller に全部
app.post('/orders/:id/confirm', async (req, res) => {
  const order = await db.query('SELECT ...');
  if (order.stock < ...) { ... }
  await db.query('UPDATE stock ...');
  await sendMail(...);
  res.json({ ok: true });
});
```

**良い例**:

```javascript
// 薄い Controller
app.post('/orders/:id/confirm', async (req, res) => {
  await placeOrderUseCase.execute(req.params.id);
  res.json({ ok: true });
});

// ドメインにルール
class Order {
  confirm() { /* ルール + OrderPlaced イベント */ }
}
```

| 観点 | 悪い例 | 良い例 |
|------|--------|--------|
| 関心の分離 | UI・DB・メールが混在 | 層ごとに分離 |
| テスト | DB 必須 | Order 単体でテスト可能 |
| 用語 | SQL と HTTP | confirm(), OrderPlaced |

## 4. 改善提案の書き方

```markdown
## 改善提案: Order への責務移動

**現状**: 確定ロジックが OrderController に 80 行

**問題**: 業務ルールの変更時に Controller を毎回修正。単体テスト困難

**提案**: `Order.confirm()` に移動し、Controller は UseCase 呼び出しのみ

**優先度**: 高（次のスプリントで対応）

**参考**: [[01_戦術的設計]] 貧血モデルの対策
```

**現状・問題・提案・優先度** を書くと actionable になります。

## まとめ

- 設計レビューは対話で改善を見つける場
- チェックリストで観点を漏らさない
- 良い・悪い比較で具体イメージを共有
- 改善提案は現状・問題・提案を明確に。次は下位設計へ
