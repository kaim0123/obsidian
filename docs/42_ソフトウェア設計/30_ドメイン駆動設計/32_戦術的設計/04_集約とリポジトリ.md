# 集約とリポジトリ

## はじめに

ドメインには、**複数のオブジェクトが関連し合って** 意味をなすものがあります。

- 注文（Order）と、注文明細（OrderItem）
- 顧客（Customer）と、配送先（Address）
- ブログ記事（Article）と、タグ（Tag）、コメント（Comment）

これらを **関連する塊として一括で扱う** ための仕組みが **集約（Aggregate）** です。そして、集約を **保存したり取り出したりする窓口** が **リポジトリ（Repository）** です。

---

## 集約（Aggregate）

### 定義

**集約** = **1つの単位として一貫性を保つ、オブジェクトの塊**

- 中心にある代表のエンティティを **集約ルート（Aggregate Root）** と呼ぶ
- 外部から触れるのは集約ルートだけ
- 集約ルートが **中身の一貫性を守る**

### 例: 注文と注文明細

```typescript
// 集約ルート
class Order {
  private items: OrderItem[];

  constructor(
    public readonly id: OrderId,
    items: OrderItem[]
  ) {
    if (items.length === 0) throw new Error('注文には最低1つの商品が必要');
    this.items = items;
  }

  addItem(item: OrderItem) {
    if (this.items.length >= 100) throw new Error('注文数上限');
    this.items.push(item);
  }

  removeItem(itemId: OrderItemId) {
    if (this.items.length === 1) throw new Error('最後の商品は削除できない');
    this.items = this.items.filter(i => !i.id.equals(itemId));
  }

  total(): Money {
    return this.items.reduce(
      (sum, i) => sum.add(i.subtotal()),
      new Money(0, 'JPY')
    );
  }
}

// 集約内のエンティティ
class OrderItem {
  constructor(
    public readonly id: OrderItemId,
    private productId: ProductId,
    private price: Money,
    private quantity: number
  ) {}
  subtotal(): Money {
    return new Money(this.price.amount * this.quantity, this.price.currency);
  }
}
```

### 集約の重要なルール

#### 1. 集約ルート経由でしか触らない

```typescript
// ❌ 集約の中身に外から直接触る
order.items.push(newItem);

// ✅ 集約ルート経由
order.addItem(newItem);
```

### 2. 集約ルートが不変条件を守る

「注文には最低1つの商品」「注文数上限」などの **業務ルール** は、集約ルートの責任。

### 3. 1トランザクションで1集約を保存

1つの操作で **複数の集約** を更新するようなトランザクションは避ける。**集約は整合性の単位**。

---

## 集約の境界の引き方

### 小さく保つ

**集約は小さい方が扱いやすい**。大きい集約は性能も悪く、ロックで詰まる。

### ルールの単位で

「必ず同時に整合していないといけないものは同じ集約」「別々のタイミングで整合してもよいものは別集約」。

### 例: 顧客と注文の関係

```
❌ 顧客集約の中に全注文を持たせる
Customer
├── orders: Order[] ← 注文が大量にあると重い
```

```
✅ 顧客と注文は別集約。参照はIDだけ
Customer (Aggregate)
   id: CustomerId

Order (Aggregate)
   id: OrderId
   customerId: CustomerId  ← 参照はIDのみ
```

集約間の参照は **他集約のオブジェクトではなく、ID** で持つのが原則です。

---

## リポジトリ（Repository）

### 定義

**リポジトリ** = **集約を保存・取得するための抽象的な窓口**

- 集約ルート単位で扱う
- インターフェースは **ドメイン層** に置く
- 実装は **インフラ層** に置く（DBアクセスなど）

### 例

```typescript
// ドメイン層: インターフェース
interface OrderRepository {
  findById(id: OrderId): Promise<Order | null>;
  save(order: Order): Promise<void>;
  delete(id: OrderId): Promise<void>;
}

// インフラ層: 実装
class MySQLOrderRepository implements OrderRepository {
  async findById(id: OrderId): Promise<Order | null> {
    const row = await db.query('SELECT * FROM orders WHERE id = ?', id.value);
    const items = await db.query('SELECT * FROM order_items WHERE order_id = ?', id.value);
    return this.toDomain(row, items); // DB行をドメインオブジェクトに変換
  }

  async save(order: Order): Promise<void> {
    await db.transaction(async t => {
      await t.query('UPSERT INTO orders ...', order);
      await t.query('DELETE FROM order_items WHERE order_id = ?', order.id);
      for (const item of order.items) {
        await t.query('INSERT INTO order_items ...', item);
      }
    });
  }
}
```

---

## リポジトリの3つの責任

### 1. 保存する

集約を丸ごと保存。集約内の子オブジェクトまで一括。

### 2. 取得する

IDで取り出す。**集約全体を復元** する。

### 3. 削除する

集約単位で削除。

### やるべきでないこと

- 業務ルールを書く（→ドメインに書く）
- 集約の中身にアクセスさせるクエリ（→集約ルート経由で）
- 検索・集計のロジック（→読み取り専用のQueryサービスに分ける場合もある）

---

## リポジトリパターンと普通のDAOの違い

| 観点 | DAO | Repository |
|------|-----|-----------|
| 扱う単位 | テーブル1つ | 集約（複数テーブル束ねる） |
| 層 | データアクセス層 | ドメイン層（インターフェース） |
| 思想 | SQLをラップ | ドメインの振る舞い |
| 例 | UserDAO → usersテーブル | OrderRepository → orders + order_items |

DAOは **DB寄り**、Repositoryは **ドメイン寄り**、と捉えると分かりやすいです。

## コードでの使い方

```typescript
// ユースケース層
class CancelOrderUseCase {
  constructor(private orderRepo: OrderRepository) {}

  async execute(orderId: OrderId): Promise<void> {
    const order = await this.orderRepo.findById(orderId);
    if (!order) throw new Error('注文が見つからない');

    order.cancel(); // 業務ルールはOrder（集約ルート）が知っている

    await this.orderRepo.save(order);
  }
}
```

**1. 取り出す → 2. 操作 → 3. 保存する**、という単純な流れ。

---

## CQRS: 読み取り側は別にすることも

複雑な読み取り（検索・集計・ダッシュボード）を **リポジトリにすべて任せると太りすぎる** ため、

- **書き込み**: Repository + 集約
- **読み取り**: Query / DTO直で返す

と分ける **CQRS（Command Query Responsibility Segregation）** という考え方もあります。DDDと組み合わせてよく使われます。

## サービスクラスを DB 詳細から解放する（増田本第5章）

アプリケーション層（サービスクラス）が SQL・カラム・CRUD の言い回しに引っ張られると、業務の関心事が見えなくなります。対策は次のとおりです。

1. **業務の関心事で考える** — 「口座を引き出す」「注文を確定する」。テーブル更新そのものをサービスメソッド名にしない  
2. **リポジトリに収納／取り出しを任せる** — サービスは `find` → ドメインに命じる → `save`  
3. **実装だけが DB を知る** — インターフェースはドメイン側、SQL/ORM はインフラ側  

画面都合でサービスが肥大化する場合や、参照／更新の分割・シナリオクラスは [[07_アプリケーション機能を組み立てる]] を参照してください。

## よくある誤解

### 誤解1: 集約は大きいほうがいい

**逆です**。小さい集約の方が性能も良く扱いやすい。

### 誤解2: Repository はただのDBラッパー

集約単位で扱い、ドメインルールを守る **窓口** です。単なるORMラッパーではありません。

### 誤解3: 集約同士を参照で持つ

**IDで持ち、必要な時にRepositoryで取得** が原則。
