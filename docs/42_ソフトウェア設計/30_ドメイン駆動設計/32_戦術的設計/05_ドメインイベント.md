# ドメインイベント（Domain Events）

## はじめに

業務の世界では、常に「**何かが起きた**」という事実が流れています。

- **注文が確定した**
- **ユーザーが登録された**
- **在庫が切れた**
- **支払いが完了した**

こうした **業務上の出来事** をオブジェクトとして扱うのが **ドメインイベント（Domain Event）** です。

---

## ドメインイベントとは

### 定義

**過去形** で表される、ドメインで起きた **重要な出来事** を表すオブジェクト。

- `OrderPlaced`（注文が確定した）
- `UserRegistered`（ユーザーが登録された）
- `PaymentFailed`（支払いが失敗した）
- `StockDepleted`（在庫が切れた）

### 特徴

- **過去形** で命名する
- **不変（immutable）**：起きた事実は変わらない
- **日時** を持つ（いつ起きたか）
- 関連する **データ** を持つ（誰が、何が）

### 実装例

```typescript
class OrderPlaced {
  constructor(
    public readonly orderId: OrderId,
    public readonly customerId: CustomerId,
    public readonly total: Money,
    public readonly occurredAt: Date = new Date()
  ) {}
}
```

---

## なぜドメインイベントを使うのか

### 1. 副作用を切り離せる

注文確定後に起こすべきこと（メール送信、在庫引当、請求、ポイント付与…）を **注文処理本体から切り離し** できる。

### 2. 業務の因果関係が表現できる

「注文が確定した」→「在庫が引き当てられた」→「配送が指示された」という業務の流れが、コードにも自然に現れる。

### 3. 監査・履歴が残しやすい

すべてのイベントを記録すれば、**いつ何が起きたか** を後から追える。

### 4. システム連携がしやすい

別のコンテキスト（別マイクロサービスなど）とは、イベントを通じて **疎結合** に連携できる。

---

## 使わない場合との対比

### 使わない場合（全部1つの処理に詰め込む）

```typescript
class PlaceOrderUseCase {
  async execute(input) {
    const order = new Order(...);
    await this.orderRepo.save(order);

    // ↓ ここから副作用のてんこ盛り
    await this.stockService.reserve(order);     // 在庫引当
    await this.mailer.sendConfirmation(order);  // メール送信
    await this.pointsService.grant(order);      // ポイント付与
    await this.inventoryService.alertLow();     // 在庫アラート
    await this.analyticsService.track(order);  // 分析記録
    // ...10個くらい続く
  }
}
```

注文処理が **副作用の山** になり、メンテナンスが辛くなる。

### ドメインイベントを使うと

```typescript
class Order {
  confirm() {
    this.status = 'confirmed';
    this.recordEvent(new OrderPlaced(this.id, this.customerId, this.total));
  }
  recordEvent(event) { this._events.push(event); }
  pullEvents() { return this._events.splice(0); }
}

class PlaceOrderUseCase {
  async execute(input) {
    const order = new Order(...);
    order.confirm();
    await this.orderRepo.save(order);

    // イベントを発火するだけ
    const events = order.pullEvents();
    for (const e of events) await this.dispatcher.dispatch(e);
  }
}

// 各ハンドラは別ファイル
class SendConfirmationMail {
  async handle(event: OrderPlaced) { /* メール送信 */ }
}
class ReserveStock {
  async handle(event: OrderPlaced) { /* 在庫引当 */ }
}
```

**注文処理は「注文確定」だけに集中**。副作用は各ハンドラに分散。

---

## イベントの発火と購読

### 1. 発火（Publish）

イベントを発生させる。

```typescript
dispatcher.dispatch(new OrderPlaced(...));
```

### 2. 購読（Subscribe）

イベントに対応するハンドラを登録。

```typescript
dispatcher.on(OrderPlaced, new SendConfirmationMail());
dispatcher.on(OrderPlaced, new ReserveStock());
dispatcher.on(OrderPlaced, new GrantLoyaltyPoints());
```

### 3. 配信（Dispatch）

発火されたイベントを、登録された全ハンドラに配信。

---

## 同期 vs 非同期

### 同期的な配信（インプロセス）

- 同じプロセス内で即時実行
- 成功・失敗をすぐ検知できる
- 失敗時のハンドリングがしやすい

### 非同期的な配信（メッセージキュー）

- Kafka・RabbitMQ・SQSなどに載せる
- **ハンドラの失敗が注文処理に影響しない**
- **別システム** に連携しやすい
- 順序保証・リトライなどは設計が必要

大規模では **非同期** が多く、単体アプリでは **同期的** で十分なこともあります。

## Before / After

### Before: モノリシックな副作用

```typescript
async function placeOrder(cart) {
  const order = new Order(cart);
  await saveOrder(order);
  await sendMail(order);
  await reserveStock(order);
  await notifyWarehouse(order);
  // 20行のてんこ盛り
}
```

### After: イベント駆動

```typescript
// ドメイン層
class Order {
  place(cart) {
    // ビジネスロジックのみ
    this.recordEvent(new OrderPlaced(this.id, ...));
  }
}

// 各ハンドラ
class OrderPlacedHandlers {
  async sendMail(e: OrderPlaced) { /* ... */ }
  async reserveStock(e: OrderPlaced) { /* ... */ }
  async notifyWarehouse(e: OrderPlaced) { /* ... */ }
}
```

責任が分離され、**新しい副作用の追加** が安全にできる。

## マイクロサービス間のイベント

マイクロサービスでは、ドメインイベントを **別サービスに配信** することで疎結合な連携ができます。

```
[注文サービス] → OrderPlaced → [在庫サービス]
                             → [配送サービス]
                             → [メールサービス]
                             → [分析サービス]
```

各サービスは **注文サービスを知らない**、単にイベントを購読するだけ。新しいサービスを追加しても、注文サービスには一切変更が入りません。

---

## イベントソーシングとの関係

**イベントソーシング（Event Sourcing）** は、「**状態の代わりに、起きたイベントを全部保存する**」パターン。

- 通常のDB: 「注文の最新状態」を保存
- イベントソーシング: 「注文にまつわる全イベント」を保存、状態は再生で復元

DDDと相性が良く、**CQRSとセット** で使われることが多いです。

---

## よくある誤解

### 誤解1: 全てのメソッド呼び出しにイベントを発火する

**重要な業務イベント** だけ。何でもイベントにすると、発火でパンクします。

### 誤解2: イベント = ログ

違います。**業務的に意味のある出来事** です。デバッグログではない。

### 誤解3: イベントは上書き・削除できる

できません。**起きた事実は消せない**。

---

## 命名のポイント

- **過去形**: `OrderPlaced`, `PaymentProcessed`
- **業務の言葉**: `PaymentFailed`（UserClickedButtonではない）
- **具体的**: `OrderStatusChanged` より `OrderConfirmed` / `OrderCancelled`
