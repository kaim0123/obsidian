# アプリケーション機能を組み立てる

## この章の目的

増田亨『現場で役立つシステム設計の原則』第5章 — **ドメインオブジェクトを組み合わせて画面・DB から独立した機能を組み立てる** やり方を学びます。

層の基本は [[06_ドメイン層とユースケースとアプリサービス]]、リポジトリは [[04_集約とリポジトリ]]、三層＋ドメインモデルの俯瞰は [[三層アーキテクチャ]]、契約の一般論は [[01_Design_by_Contract]] を参照してください。

---

## 1. アプリケーション層のクラスの役割

三層＋ドメインモデルでは、業務の判断・加工・計算は **ドメインモデル** にあります。アプリケーション層のクラス（**サービスクラス**／アプリケーションサービス／ユースケース）は、次の **進行役・調整役（マネージャー）** です。

| やること | やらないこと |
|----------|--------------|
| プレゼン・ドメイン・データソース間の連絡と指示 | 業務的な判断・加工・計算そのもの |
| ドメインオブジェクトの取り出し・組み合わせ・保存の手順 | SQL や画面項目の都合をそのままロジックに書く |
| トランザクション境界の保持（多くはフレームワークに委譲） | 「マネージャーに雑務をやらせる」状態 |

マネージャーに計算をさせると、第3章の貧血モデル／トランザクションスクリプトに戻ります。

---

## 2. 三層＋ドメインモデルをわかりやすく実装する

| 層 | 役割の例（Spring 等） |
|----|------------------------|
| プレゼンテーション | Controller — 入出力・画面遷移 |
| アプリケーション | Service / Scenario — 手順の制御 |
| ドメイン | Entity / Value Object 等 — 業務ルール |
| データソース | Repository 実装 — 永続化 |

フレームワークの DI（コンストラクタ注入）を使うと、層の依存がコード上でも読みやすくなります。構成の詳細は [[06_ドメイン層とユースケースとアプリサービス]]・[[三層アーキテクチャ]]。

---

## 3. サービスクラスの設計はごちゃごちゃしやすい

複雑になる典型原因は次の3つです。

1. **ドメインオブジェクトが貧弱** — ロジックがサービスに流れ込む  
2. **プレゼンテーションの関心事に振り回される** — 「何でもできる1メソッド」  
3. **データベース入出力の都合に引きずられる** — CRUD がそのまま見える  

対策は本章の残り（ドメインを育てる／小さく分ける／リポジトリで分離）です。

---

## 4. サービスクラスを作りながらドメインモデルを改善する

### 4.1 初期のドメインモデルは力不足

最初のモデルは薄いことが多いです。サービスに業務ロジックを書きたくなるのは自然ですが、そこで妥協すると重複と見通しの悪さが固定します。

### 4.2 ドメインモデルを育てる

サービスにルールを書きそうになったら、次の順でドメイン側へ寄せます（TDD の「仮実装→重複→移動」に近い）。

```text
  1. いったんサービスに書いて動かす（誘惑に気づく）
  2. 重複や「ここは業務ルールだ」と分かる
  3. 適切なドメインオブジェクトへ移す
  4. 置き場所がなければクラスを追加／改名／メソッド追加
```

ぎこちない名前でも、まずドメインに置き、名前は後から業務語に揃えます（[[02_ユビキタス言語]]・[[03_ドメインモデルの作り方]]）。

## 5. 画面の多様な要求を小さく分けて整理する

### 5.1 プレゼンテーション層に影響される複雑さ

検索条件が商品名・金額・特徴など多様だと、「何でも検索する1つのサービスメソッド」に分岐が集まります。編集画面も同様に「何でも編集」になりがちです。

### 5.2 小さく分ける

**参照系と登録（更新）系を分ける** のが基本です。副作用の有無でテスト範囲も切りやすくなります。

```typescript
// 参照系
class BankAccountQueryService {
  canWithdraw(amount: Money): boolean { /* ドメイン＋残高の参照 */ }
  balance(): Money { /* ... */ }
}

// 更新系
class BankAccountUpdateService {
  withdraw(amount: Money): void { /* 引き出しの実行・保存 */ }
}
```

画面ごとの検索も、条件ごとに小さなサービス／クエリに分け、プレゼンは **呼び分けるだけ** にします。

### 5.3 小さく分けたサービスを組み立てる — シナリオクラス

基本サービスを、画面やユースケース単位の **シナリオクラス** が組み立てます。

```typescript
class BankAccountScenario {
  constructor(
    private readonly query: BankAccountQueryService,
    private readonly update: BankAccountUpdateService,
  ) {}

  withdraw(amount: Money): Money {
    if (!this.query.canWithdraw(amount)) {
      throw new Error("残高不足");
    }
    this.update.withdraw(amount);
    return this.query.balance();
  }
}
```

- プレゼン（Controller）はシナリオを呼ぶ  

> [!info] 画面 UI 側の分割・ドメイン連動
> ここまでは **サービス／シナリオ** 側の分割です。画面そのものの関心事分割・タスクベース UI・視覚と論理の揃え方は [[09_画面とドメインオブジェクトの設計]]（増田本第7章）と [[05_画面関心事の分割とドメイン連動]]。
- シナリオは「この業務の流れ」の説明書にもなる  
- **シナリオ単位のテスト** が書きやすい  

（名前はユースケース／アプリケーションサービスと同系統。役割は「小さなサービスを組み合わせる進行役」。）

---

## 6. 利用する側と提供する側の合意を明確にする

プレゼン（使う側）とサービス／シナリオ（提供する側）の **契約** をはっきりさせます（[[01_Design_by_Contract]]）。

| 約束 | 内容 |
|------|------|
| null を渡さない／返さない | 渡された時点で拒否。返す側も null を出さない → 使う側の null チェックが減る |
| 状態依存は使う側が事前確認 | 例: `canWithdraw` してから `withdraw`。提供側は単純実行に寄せる |
| それでも異常なら例外 | 約束を守ったうえでの失敗は例外で通知 |

防御的に何度も同じチェックをサービス内に積み重ねすぎると、またごちゃごちゃします。合意をコードとテストで固定するのが先です。

## 7. データベースの都合から分離する

### 7.1 入出力に引っ張られる問題

業務の関心事が RDB の CRUD に直訳されると、コードから業務の意図が消え、変更時に SQL とサービスを同時に直すことになります。

### 7.2 データベース操作ではなく業務の関心事で考える

ドメインからは **リポジトリ** を「メモリ上のドメインオブジェクトの収納場所」として扱います（`find` / `save`）。インターフェースはドメイン側、実装はデータソース／インフラ側（[[04_集約とリポジトリ]]）。

### 7.3 実際の DB 操作とリポジトリを組み合わせる

実装クラスだけが SQL・ORM・トランザクション詳細を知ります。サービスはリポジトリのメソッド名（業務語）だけを見ます。

```typescript
// サービス（解放された記述）
const account = await this.accountRepo.findById(id);
account.withdraw(amount); // ルールはドメイン
await this.accountRepo.save(account);

// リポジトリ実装の中だけが UPDATE / INSERT を知る
```

### 7.4 サービスクラスを DB 詳細から解放する

サービスに書くのは「取り出す→ドメインに命じる→保存する」の手順まで。テーブル結合やカラム名をサービスに漏らさない。複雑な一覧・集計は参照用クエリに分ける（CQRS 的分離は [[04_集約とリポジトリ]]）。

---

## まとめ

- サービスは進行役。判断・加工・計算はドメインへ  
- ロジックを書きたくなったらドメインを育てる機会  
- 画面の多様さは小さな参照／更新サービス＋**シナリオ**で組み立てる  
- 使う側と提供側の契約（null・事前確認・例外）を明確にする  
- DB はリポジトリの向こう。サービスは業務の関心事の言葉で書く
