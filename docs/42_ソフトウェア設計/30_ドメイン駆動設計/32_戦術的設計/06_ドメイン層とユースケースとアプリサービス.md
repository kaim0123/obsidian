# ドメイン層・ユースケース・アプリケーションサービス

## この教材の目的

[[クリーンアーキテクチャの概要]] では、同心円の中に **Entities** と **Use Cases** がありました。  
DDD では、同じ領域を **ドメイン層**・**アプリケーション層**（ユースケース／アプリケーションサービス）という言葉で語ります。

この教材では、**層（同心円）の中身**を DDD の用語で整理し、**どこに何を書くか**を初心者向けに説明します。

前提: [[02_DDDとは]]、[[クリーンアーキテクチャの概要]]

---

## 1. 全体像 — 3つの役割

```
  外側（UI, DB, API クライアント）
       │
       ▼
┌──────────────────────────────────┐
│  インターフェース層（プレゼン）    │  Controller, GraphQL Resolver など
└──────────────┬───────────────────┘
               ▼
┌──────────────────────────────────┐
│  アプリケーション層               │  ユースケース / アプリケーションサービス
│  「この操作で何をするか」の手順     │  トランザクション境界、権限チェックの入口
└──────────────┬───────────────────┘
               ▼
┌──────────────────────────────────┐
│  ドメイン層                       │  エンティティ、値オブジェクト、集約、
│  「ビジネスのルールそのもの」       │  ドメインサービス、ドメインイベント
└──────────────┬───────────────────┘
               ▼
┌──────────────────────────────────┐
│  インフラ層                       │  DB 実装、外部 API、メール送信
└──────────────────────────────────┘
```

**依存の向き**は変わりません。**内側（ドメイン）が外側を知らない**のが原則です。

---

## 2. ドメイン層 — ビジネスの心臓部

**ドメイン層**には、**その業務領域のルールとモデル**だけを置きます。

### 置くもの

| 種類 | 役割 | 例 |
|------|------|------|
| エンティティ | ID で識別され、状態が変わるもの | `Order`, `Patient` |
| 値オブジェクト | 値そのもので意味が完結 | `Money`, `EmailAddress`, `DateRange` |
| 集約 | 不変条件を守るまとまり（詳細は [[02_集約とエンティティと値オブジェクトとドメインイベント]]） | `Order` + `OrderLine` |
| ドメインサービス | 1つのエンティティに収まらないドメインの処理 | 複雑な料金計算、在庫引当ルール |
| ドメインイベント | ドメイン内で起きた「事実」 | `OrderPlaced`, `PaymentFailed` |
| リポジトリ（インターフェース） | 集約の永続化の**抽象**（実装はインフラ） | `OrderRepository` |

### 置かないもの

- SQL や HTTP の知識
- フレームワーク固有のアノテーション（可能なら）
- 「画面に何を表示するか」の都合

```typescript
// ドメイン層の例 — ルールはここに
class Order {
  private constructor(
    readonly id: OrderId,
    private status: OrderStatus,
    private lines: OrderLine[],
  ) {}

  cancel() {
    if (this.status !== OrderStatus.Pending) {
      throw new Error('確定済みの注文はキャンセルできません');
    }
    this.status = OrderStatus.Cancelled;
  }
}
```

**「この注文はキャンセルできるか」** はドメインの知識です。DB の更新方法は知りません。

## 3. ユースケース — 1つの業務操作

**ユースケース（Use Case）** は、[[クリーンアーキテクチャの概要]] の Use Cases と同じ考え方です。

> **アプリケーションが提供する、1つの具体的な業務操作**  
> 例: 「注文を確定する」「ユーザーを登録する」

### ユースケースの責務

1. **入力を受け取り**、ドメインオブジェクトに変換する
2. **ドメイン層を呼び出し**、ルールを実行する
3. **リポジトリや外部サービス**（インターフェース経由）で永続化・通知する
4. **結果を出力**用の形にまとめる

```typescript
// アプリケーション層（ユースケース）の例
class PlaceOrderUseCase {
  constructor(
    private orderRepo: OrderRepository,
    private paymentGateway: PaymentGateway, // インターフェース
  ) {}

  async execute(input: PlaceOrderInput): Promise<PlaceOrderOutput> {
    const order = Order.create(input.lines);
    await this.paymentGateway.charge(order.total());
    await this.orderRepo.save(order);
    return { orderId: order.id.value };
  }
}
```

ユースケースは **「手順」** を書きますが、**ビジネスルールの詳細**は `Order` などドメイン層に任せます。

## 4. アプリケーションサービス — 名前の違いと実務

DDD の文献やフレームワークによって、**ユースケース**と **アプリケーションサービス（Application Service）** がほぼ同義で使われることが多いです。

| 呼び方 | よく見る文脈 |
|--------|--------------|
| ユースケース | クリーンアーキテクチャ、`Execute` メソッド1つ |
| アプリケーションサービス | DDD 本家、Spring の `@Service` など |

この教材では、**どちらも「アプリケーション層で、1業務操作を orchestrate（指揮）するクラス」** と捉えてよいです。

### アプリケーション層に置いてよいこと

- トランザクションの開始・コミット（フレームワークに委譲することも多い）
- 認可チェック（「このユーザーはこの操作をしてよいか」）
- 複数集約にまたがる**手順**の組み立て
- ドメインイベントの発行指示

### アプリケーション層に置きすぎないこと

- 料金計算の詳細、在庫の引当ルールなど **ドメインの本質的ルール**
- SQL 文、HTTP クライアントの直接呼び出し

**迷ったら「そのルールは、専門家がホワイトボードで説明する内容か？」**  
Yes ならドメイン層、No（手順・連携）ならアプリケーション層、と切るとよいです。

## 5. ドメインサービスとの違い

| | ドメインサービス | アプリケーションサービス／ユースケース |
|--|------------------|----------------------------------------|
| 層 | ドメイン層 | アプリケーション層 |
| 中身 | **純粋なビジネスルール** | **手順・連携・永続化** |
| 状態 | 通常ステートレス | リポジトリなどを注入 |
| 例 | 2つの集約にまたがる引当ルールの計算 | 「注文確定」フロー全体 |

```typescript
// ドメインサービス — ルールそのもの
class ShippingFeeCalculator {
  calculate(order: Order, destination: Address): Money {
    // 距離・重量・会員ランクに基づく料金計算（ビジネスルール）
  }
}

// ユースケース — 手順
class PlaceOrderUseCase {
  async execute(input) {
    const fee = this.feeCalculator.calculate(order, input.address);
    order.applyShippingFee(fee);
    await this.orderRepo.save(order);
  }
}
```

## 6. クリーンアーキテクチャとの対応表

| クリーンアーキテクチャ | DDD での呼び方 | 主な内容 |
|------------------------|----------------|----------|
| Entities | ドメイン層（エンティティ、値オブジェクト、集約） | ビジネスルール |
| Use Cases | アプリケーション層（ユースケース／アプリケーションサービス） | 業務操作の手順 |
| Interface Adapters | プレゼンテーション層、インフラの一部 | HTTP ↔ ユースケースの変換 |
| Frameworks & Drivers | インフラ層 | DB, Web フレームワーク |

**図の名前は違っても、依存の向きと責務の分け方は同じ家族**です。

## 7. フォルダ構成の例

```
src/
├─ domain/                    ← ドメイン層
│   ├─ order/
│   │   ├─ Order.ts           （集約ルート）
│   │   ├─ OrderLine.ts
│   │   ├─ OrderRepository.ts （インターフェース）
│   │   └─ OrderPlaced.ts     （ドメインイベント）
│   └─ shared/
│       └─ Money.ts
├─ application/               ← アプリケーション層
│   └─ order/
│       ├─ PlaceOrderUseCase.ts
│       └─ CancelOrderUseCase.ts
├─ infrastructure/            ← インフラ層
│   └─ persistence/
│       └─ SqlOrderRepository.ts
└─ presentation/              ← プレゼンテーション層
    └─ OrderController.ts
```

## 8. よくある落とし穴

### 貧血ドメインモデル（Anemic Domain Model）

エンティティが **getter/setter だけ** で、ルールが全部サービス層に漏れている状態。

```typescript
// 避けたい例 — Order はただのデータ入れ物
class Order {
  status: string;
}
// ルールは全部 PlaceOrderService の中に…
```

**振る舞い（メソッド）をドメインオブジェクトに持たせる**のが DDD の基本です。

### ユースケースが太りすぎる

if 文が何十行も並ぶユースケースは、ルールがドメイン層に逃げているサインです。  
ドメイン層へ引き戻すか、ドメインサービスに切り出します。
