# 戦術的設計 — コードの書き方

## この章の目的

1 つのコンテキスト **内部** をどうモデル化するか — DDD の **戦術的設計** を学びます。

> 詳細は [[03_エンティティと値オブジェクト]]、[[04_集約とリポジトリ]]、[[06_ドメイン層とユースケースとアプリサービス]] を参照。

---

## 1. エンティティと値オブジェクト

| 種類 | 特徴 | 例 |
|------|------|-----|
| **エンティティ** | 同一性（ID）で識別 | Order, Customer |
| **値オブジェクト** | 値で比較。不変が多い | Money, Address, Email |

```javascript
// 値オブジェクト: 500円 + 300円 = 800円（値で比較）
class Money {
  constructor(amount, currency) {
    this.amount = amount;
    this.currency = currency;
  }
  add(other) {
    return new Money(this.amount + other.amount, this.currency);
  }
}

// エンティティ: ID で識別（同じ金額でも別注文）
class Order {
  constructor(id) { this.id = id; }
}
```

**ルールの置き場所** を型で明確にします。

---

## 2. 集約（Aggregate）— 整合性の単位

**集約** は、**整合性を保つ単位** です。1 つの集約に **集約ルート** があります。

```text
  Order（集約ルート）
    ├── OrderLine（明細）
    └── OrderLine
```

- 外部は **集約ルート経由** でのみ操作
- トランザクション境界は **1 集約** が基本
- 「注文確定」は Order が責任を持つ

詳細 → [[04_集約とリポジトリ]]

---

## 3. リポジトリ — 永続化の抽象化

**リポジトリ** は、集約の **永続化・取得** を抽象化します。

```text
  OrderService ──→ OrderRepository（インターフェース）
                           │
                           └── 実装: DbOrderRepository, InMemory...
```

- ドメイン層は **DB の詳細を知らない**
- テスト時にインメモリ実装に差し替え可能
- 「コレクションのように扱う」イメージ

---

## 4. ドメインサービスとアプリケーションサービス

| 種類 | 役割 | 例 |
|------|------|-----|
| **ドメインサービス** | 特定のエンティティに属さないドメイン処理 | 複雑な価格計算 |
| **アプリケーションサービス** | ユースケースのオーケストレーション | PlaceOrderUseCase |

```text
  アプリケーションサービス（手続き的な流れ）
       │
       ├── ドメインオブジェクトに処理を委譲
       └── リポジトリ・外部サービスを呼ぶ
```

**ロジックはドメインに、流れはアプリケーションに** が基本です。

---

## 5. 貧血ドメインモデルの問題と対策

**貧血ドメインモデル** とは、エンティティが getter/setter だけで、**ロジックがサービス層に集中** した状態です。

```javascript
// 貧血: Order はデータ入れ物
class Order { getTotal() { return this.total; } }
// ロジックは OrderService に全部
class OrderService {
  calculateDiscount(order) { ... }
  validate(order) { ... }
}
```

### 対策

- **振る舞いをエンティティ・値オブジェクトに置く**
- `order.confirm()` のように **業務の言葉でメソッドを命名**
- アプリケーションサービスは **薄く** 保つ

---

## まとめ

- エンティティは ID、値オブジェクトは値で識別
- 集約は整合性の単位。外部はルート経由
- リポジトリで永続化を抽象化
- ロジックはドメインに。貧血モデルを避ける
