## 1. 画面アプリケーションの開発の難しさ

画面には、いろいろな利用者の関心事が一度に詰め込まれます。

| 混ざりやすいもの | 例 |
|------------------|-----|
| 業務の判断・計算 | 割引可否、期限、状態ごとの操作 |
| 操作の流れ | ウィザード、確認ダイアログ、遷移 |
| 見た目・レイアウト | 並び、グループ、強調表示 |
| 入力の便宜 | 初期値、候補、バリデーションメッセージ |

**画面の見た目や項目構成をそのままクラス設計に写す**と、画面が変わるたびにドメインやサービスが巻き込まれます。逆に、画面だけを巨大なまま残すと、関心事が解けないまま肥大化します。

基本は [[04_関心の分離]] と同じです。**関心事を分けて整理し**、画面都合と業務都合を混同しない。

---

## 2. 画面の関心事を小さく分けて独立させる

複雑な1画面は、しばしば **異なる関心事の寄せ集め** です。

- 小さな単位（関心事）に分けて考える  
- 必要なら **画面そのものも分ける**（1画面＝1かたまりの関心事）  
- サービス／シナリオ側の分割は [[07_アプリケーション機能を組み立てる]] §5  
- タスクベース UI・コンポーネント境界は [[05_画面関心事の分割とドメイン連動]]  

「何でもできる一覧＋巨大フォーム」より、**タスク（やりたいこと）単位の画面**の方が、ドメインオブジェクトの境界とも揃えやすい、というのが増田本の立場です。

---

## 3. 画面とドメインオブジェクトを連動させる

### 3.1 どちらも「利用者の関心事のかたまり」

| | 画面 | ドメインオブジェクト |
|--|------|----------------------|
| 役割 | 関心事を **見せ・操作させる** | 関心事を **正しく判断・計算する** |
| よい境界 | 利用者が一度に扱うかたまり | 業務の言葉で閉じたルールのかたまり |

境界が揃っていると、画面変更とルール変更の影響範囲が読みやすくなります。

### 3.2 食い違いは設計改善の手がかり

次のようなずれは、どちらか（または両方）の設計を見直す合図です。

- 画面のグループと、クラス／フィールドのまとまりが一致しない  
- 画面では1操作なのに、コードでは無関係な複数オブジェクトを横断する  
- 画面項目はあるが、対応するドメインの言葉・ルールがない（またはその逆）  

「画面に合わせる」でも「コードに画面を無理に合わせる」でもなく、**利用者の関心事に両方を近づける**ことが目的です（[[03_ドメインモデルの考え方で設計する]]・[[02_ユビキタス言語]]）。

### 3.3 ドメインオブジェクトに書くべきロジック

画面やテンプレートに書きがちで、ドメイン側に寄せた方がよいものの例です。

| 置き場所の候補 | 内容 |
|----------------|------|
| **ドメイン** | 状態・区分に応じた可否判定、表示用ラベル／強調の根拠、金額・期限などの計算 |
| **プレゼン／View** | レイアウト、文言の装飾、ウィジェット固有の操作 |

「この行を赤くするか」の **判断** はドメイン、「赤の CSS を当てる」のは画面、という分担が基本です（[[05_Tell_Dont_Askと貧血モデルの回避]]・[[08_業務ロジックをデータと一体にする]]）。

### 3.4 HTML の class 属性をドメインから出力する

増田本では、状態に応じた見た目の手がかり（例: 期限切れなら警告用の class 名）を、**ドメインオブジェクトが返す**例が示されます。

```typescript
// 判断はドメイン、当て方はテンプレート／コンポーネント
class TemporaryLicense {
  cssClass(): string {
    if (this.isExpired()) return "warning";
    if (this.isExpiringSoon()) return "caution";
    return "normal";
  }
}
```

- class 名そのものをドメインが知ると、CSS 設計と結合するので、実務では **意味のある状態名／表示区分** を返し、画面側で class にマップする形も多い  
- いずれにせよ、「赤くするか」のルールを JSX／テンプレートの if に散らさないことが要点

## 4. 画面（視覚表現）とソフトウェア（論理構造）を関係づける

| 視覚 | 論理（ソフトウェア） |
|------|----------------------|
| 項目の並び順 | フィールド・値オブジェクトの並び／提示順 |
| 画面上のグルーピング | オブジェクトのまとまり・集約・埋め込み値オブジェクト |
| 画面の分割 | 関心事の境界・ユースケース／シナリオの単位 |

デザインと設計を **別々に完成させてから合わせる** より、食い違いを手がかりに両方を少しずつ洗練させる、というのが第7章のメッセージです。

画面以外の利用者向け情報（帳票、メール文面、API の項目名、ヘルプ）も、同じ業務用語・同じグルーピングに揃えると、ドメインモデルの効果が画面の外にも広がります。

---

## まとめ

- 画面は関心事の詰め込み場所。引きずられると変更が辛い → 分けて独立させる  
- 画面もドメインも関心事のかたまり。ずれは改善の合図  
- 判断・計算はドメイン、見た目の当て方は画面。状態に応じた表示の根拠もドメインへ  
- 並び・グループ・画面分割を論理構造と連動させ、画面外の情報とも用語を揃える
