## 1. データ形式とドメインオブジェクトの不一致

| 側 | 関心 |
|----|------|
| **Web API（JSON など）** | 転送・互換・クライアントの使いやすさ |
| **ドメインオブジェクト** | 業務ルール・不変条件・意味のある型 |

機械的な 1:1 写経（テーブル列＝JSON フィールド＝ドメインの public フィールド）は、次の不一致を生みます。

- NULL／欠落フィールドと、ドメインの「必須の値オブジェクト」  
- 文字列コードと、区分オブジェクト／列挙  
- ネストの浅い DTO と、深い集約  
- クライアント向けの別名と、ユビキタス言語  

**明示的な変換（Mapper／Assembler）** を置き、ドメインを API の都合で歪めない、というのが [[08_オブジェクトとテーブルの設計]] と同型の方針です。内部を晒さない話は [[05_APIとドメイン設計]]。

```typescript
// API DTO → ドメイン（イメージ）
function toOrder(dto: OrderRequestDto): Order {
  return Order.place(
    CustomerId.of(dto.customerId),
    Money.of(dto.amount, dto.currency),
  );
}
```

## 2. 導出結果か生データか

レスポンスに何を載せるかの古典的な分岐です。

| 返すもの | 例 | 向き |
|----------|-----|------|
| **導出結果** | 税込価格、表示用ステータス名、可否フラグ | クライアントが同じ計算を重複実装しなくてよい |
| **生データ** | 単価・税率・区分コード | クライアントが別用途に再計算・集計しやすい |

| 判断の目安 | |
|------------|--|
| ルールがドメインの中核で、クライアント実装がバラつくと困る | **導出結果**（または両方） |
| クライアントの用途が多様で、サーバーの解釈を固定したくない | **生データ**＋必要なら導出をオプションで |
| 両方載せる | ペイロード増と契約の複雑さに注意 |

「画面用に全部計算して返す万能レスポンス」は、[[05_API設計の原則]] の「大は小を兼ねる？」と同じ罠になりやすいです。用途が分かれているなら、参照 API を分ける／フィールドを疎にする方がよいことが多いです。

表示判断をドメインに寄せる話（画面）は [[09_画面とドメインオブジェクトの設計]]。API でも「可否・ラベルの根拠」はドメインで出し、JSON には結果だけ載せる形が安全です。

---

## 3. 境界での役割分担

| 置き場所 | 向いていること |
|----------|----------------|
| **ドメイン** | 生成・変更のルール、導出の計算、不変条件 |
| **API 層** | 認証・入出力の検証、DTO 変換、ステータスコード、ページネーション |
| **アプリ／ユースケース** | どのドメインを呼び、何を永続化し、何を返すかの手順 |

サービスを DB／画面から解放する話（[[07_アプリケーション機能を組み立てる]]）の「外向き」版が、この Web API 境界です。

---

## まとめ

- JSON とドメインは別物。明示変換で不一致を吸収する  
- 導出結果と生データは用途で選ぶ。万能レスポンスにしない  
- ルールはドメイン、契約と転送は API 層
