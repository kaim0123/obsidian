# ドメイン駆動設計（DDD）とは — 30_ドメイン駆動設計の入口

## この教材の目的

**ドメイン駆動設計（Domain-Driven Design, DDD）** は、Eric Evans が提唱した、**ビジネスの複雑さをソフトウェアの構造に反映させる**ための設計の考え方です。

この 30_ドメイン駆動設計 では、DDD 全体を深く追うのではなく、**戦略設計と戦術設計の入口**として、次の3つを押さえます。

1. [[03_境界づけられたコンテキストとコンテキストマップ]] … 大きなシステムをどう区切るか
2. [[06_ドメイン層とユースケースとアプリサービス]] … クリーンアーキテクチャの「中身」を DDD の言葉で読む
3. [[02_集約とエンティティと値オブジェクトとドメインイベント]] … ドメイン層の主要な部品

前提として [[クリーンアーキテクチャの概要]] や [[オニオンアーキテクチャとの比較]] を読んでおくと、「ドメインを中心に置く」という共通の土台がつかみやすくなります。

---

## 1. DDD を一言で

> **ソフトウェアの構造と用語を、ビジネス（ドメイン）の現実に合わせて設計する。**

「ドメイン」とは、**そのソフトウェアが扱う事業領域・業務の世界**のことです。  
EC なら「注文・在庫・配送」、病院なら「診療・予約・会計」といった領域がドメインです。

DDD は「DB のテーブル設計から始める」のではなく、

- **現場の人が使う言葉**（ユビキタス言語）
- **業務の区切り**（境界づけられたコンテキスト）
- **ルールを守る単位**（集約）

を先に考え、コードの形に落とし込む、という姿勢を重視します。

---

## 2. 戦略設計と戦術設計

DDD は大きく2つの側面に分かれます。

| 側面 | 主な問い | このフォルダでの扱い |
|------|----------|-------------------|
| **戦略設計** | システム全体をどう区切るか、チーム間をどう連携するか | 境界づけられたコンテキスト、コンテキストマップ |
| **戦術設計** | 1つのコンテキストの中をどうモデル化するか | ドメイン層の部品（集約、エンティティなど） |

**戦略**は「地図を描く」、**戦術**は「1つの街の建物を設計する」イメージです。  
小規模な個人開発では戦術だけ意識することも多いですが、**チームやシステムが大きくなるほど戦略設計の価値が上がります**。

---

## 3. なぜ DDD とアーキテクチャを一緒に学ぶのか

[[クリーンアーキテクチャの概要]] では、すでに **Entities（エンティティ）** や **Use Cases（ユースケース）** という層を見てきました。  
DDD は、それらの**中身をどう設計するか**の指針を与えてくれます。

- クリーンアーキテクチャ … **依存の向き**（内側にドメインを置く）
- DDD … **ドメインの中身の作り方**（集約、値オブジェクト、ドメインイベントなど）

「同心円の図」は**箱の形**、DDD は**箱の中身の詰め方**、と捉えると関係が整理しやすいです。

---

## 4. いつ DDD を意識するとよいか

### 向いている場面

- ビジネスルールが**複雑**で、仕様変更が頻繁
- **複数チーム**が同じシステムの別領域を担当している
- 長期間保守し、**用語のブレ**がバグの温床になっている

### やりすぎになりやすい場面

- 単純な CRUD が中心の小規模アプリ
- ドメインの知識がほとんどなく、**技術的な課題だけ**を解きたいとき

DDD は銀の弾丸ではありません。**「ドメインの複雑さに見合った投資」** として使うのが現実的です。

## 5. このフォルダの読み方

```
  01_DDD（このノート）
       │
       ├─→ 02 境界づけられたコンテキスト … システムの「地図」
       │
       ├─→ 03 ドメイン層・ユースケース・アプリサービス … 層の役割分担
       │
       └─→ 04 集約・エンティティ・値オブジェクト・ドメインイベント … 部品の入門
```
