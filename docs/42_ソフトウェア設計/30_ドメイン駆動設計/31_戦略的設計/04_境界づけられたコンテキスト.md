# 境界づけられたコンテキスト（Bounded Context）

## はじめに

大きな業務システムでは、**1つの言葉が場所によって違う意味を持つ** ことがよくあります。

- 「商品」… 販売時は「値段付きのもの」、倉庫内では「棚にある物体」、配送時は「梱包された荷物」
- 「ユーザー」… 認証では「ログインできる人」、マーケティングでは「広告を見る人」、サポートでは「問い合わせ主」

こうしたとき、**無理に1つの『ユーザー』『商品』クラスでまとめない** のがDDDの考え方です。

**「この範囲ではこの言葉はこの意味」** と範囲を区切るのが **境界づけられたコンテキスト（Bounded Context）** です。

---

## なぜ境界が必要か

### 無理に共通化するとどうなるか

```typescript
// ❌ 全部入りのUserクラス
class User {
  // 認証情報
  email: string;
  password: string;
  // 購入履歴（ECの関心）
  orders: Order[];
  // 配送先（物流の関心）
  shippingAddresses: Address[];
  // マーケ情報（広告の関心）
  adPreferences: AdPref;
  // サポート履歴
  supportTickets: Ticket[];
  // ...全部1つに
}
```

**問題点**:

- クラスが肥大化する
- 変更の影響範囲が広すぎる
- チーム間で衝突する
- テストが重い
- どこで何に使われているか追えない

### 境界を引いて分ける

```
┌────────────────┐  ┌────────────────┐  ┌────────────────┐
│ 認証コンテキスト  │  │ EC コンテキスト  │  │ 配送コンテキスト  │
│ ┌────────────┐ │  │ ┌────────────┐ │  │ ┌────────────┐ │
│ │   User     │ │  │ │  Customer  │ │  │ │ Recipient  │ │
│ │ email      │ │  │ │ orders     │ │  │ │ address    │ │
│ │ password   │ │  │ │ loyalty    │ │  │ │ deliveryId │ │
│ └────────────┘ │  │ └────────────┘ │  │ └────────────┘ │
└────────────────┘  └────────────────┘  └────────────────┘
```

**同じ人物** を、コンテキストごとに違うモデルで表現。必要な情報だけを持つ。

---

## 「コンテキスト」とは

ここでいうコンテキストとは、

- **1つの業務の範囲**
- **用語の意味が一貫している範囲**
- **同じチームが扱う範囲**
- **独立して変更できる範囲**

のこと。抽象的ですが、実務では **「サブシステム」や「マイクロサービス」** に近いものと考えてOKです。

---

## コンテキストを見つける方法

### ヒント1: 言葉の意味がズレる境目

「このチームでは『商品』の意味が違う」と気づいたら、そこが境界。

### ヒント2: チーム・部署の境目

組織構造がコンテキストを反映することが多い（コンウェイの法則）。

### ヒント3: 変更の頻度・理由

同じ理由で変わる部分はまとめ、違う理由で変わる部分は分ける（SRPと同じ発想）。

### ヒント4: ライフサイクル

別々のタイミングでデプロイ・リリースするなら、別のコンテキストかも。

---

## コンテキスト間の関係: コンテキストマップ

複数のコンテキストの **関係を図に表したもの** が **コンテキストマップ** です。

### 主な関係パターン

#### 1. 共有カーネル（Shared Kernel）

2つのコンテキストが **共通のモデル** を共有する。変更には両チームの合意が必要。

#### 2. 顧客/供給者（Customer/Supplier）

片方（上流）が、もう片方（下流）のために情報を提供する。

#### 3. 順応者（Conformist）

下流のチームが、上流のモデルに **合わせるしかない** 関係（相手が強い）。

#### 4. 腐敗防止層（Anti-Corruption Layer, ACL）

**外部システムの都合に自分が汚染されないように、変換層を挟む**。

```typescript
// 外部の古いAPI
interface LegacyUserAPI {
  getUsr(id: string): { uName: string; eAddr: string };
}

// 自社のコンテキストにとって良い形に変換
class LegacyUserAdapter {
  constructor(private legacy: LegacyUserAPI) {}
  findUser(id: string): User {
    const raw = this.legacy.getUsr(id);
    return new User(raw.uName, raw.eAddr); // 自社の言葉に翻訳
  }
}
```

#### 5. 公開ホストサービス（Open Host Service）

外部に **公開APIを提供** するコンテキスト。

#### 6. 別々の道（Separate Ways）

相互作用が少なく、**完全に独立** に進める関係。

## 具体例: ECサイトのコンテキスト分割

```
┌─────────────────┐  ┌─────────────────┐
│  認証コンテキスト │  │ 商品カタログ      │
│  (Auth)          │  │  (Catalog)       │
└─────────────────┘  └─────────────────┘
        │                      │
        └──────────┬───────────┘
                   ↓
        ┌─────────────────┐
        │ 注文コンテキスト  │
        │   (Ordering)     │
        └─────────────────┘
                   │
          ┌────────┴────────┐
          ↓                 ↓
┌─────────────────┐  ┌─────────────────┐
│ 決済コンテキスト  │  │ 配送コンテキスト  │
│  (Payment)       │  │  (Shipping)      │
└─────────────────┘  └─────────────────┘
```

**各コンテキストは独立した言葉を持つ**。注文の「商品」と配送の「商品」は別モデル。

## マイクロサービスとの関係

境界づけられたコンテキストは、**マイクロサービスの分割単位** としてしばしば採用されます。

- 1コンテキスト = 1マイクロサービス
- コンテキスト間の通信 = REST / gRPC / メッセージング

ただし、**コンテキスト ≠ マイクロサービス**。モノリシックな1つのアプリの中でも、**フォルダ単位でコンテキストを区切る** ことは可能です。

---

## 実装のポイント

### 1. コンテキスト間でモデルを共有しない

```typescript
// ❌ 全コンテキストで同じUser
import { User } from '@shared/User';

// ✅ 各コンテキストで独自モデル
import { User } from './auth/User';
import { Customer } from './ordering/Customer';
```

### 2. 通信は小さなDTOで

コンテキストをまたいで渡すデータは、**最小限のDTO** で。モデルをそのまま渡さない。

### 3. 翻訳層を設ける

外部コンテキストからのデータは、**腐敗防止層で自社の言葉に変換**。

### 4. 同じIDでも別モデル

同じ「user_id=123」でも、コンテキストごとに違うクラス（UserのID型 / CustomerのID型）で扱う。

---

## よくある誤解

### 誤解1: 大きなドメインを1つのモデルで表現できる

できません。**分割してこそDDD**。

### 誤解2: コンテキスト = DBテーブル

DBのテーブル境界とは **必ずしも一致しません**。同じテーブルを違うコンテキストから違う意味で読むこともある。

### 誤解3: 境界は永久不変

**時間とともに変わります**。業務が進化すれば、境界も引き直す。
