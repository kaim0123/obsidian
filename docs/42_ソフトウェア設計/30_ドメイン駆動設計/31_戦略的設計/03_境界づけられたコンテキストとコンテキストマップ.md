# 境界づけられたコンテキストとコンテキストマップ

## この教材の目的

大きなシステムでは、**同じ単語が領域によって違う意味**を持つことがよくあります。  
DDD の**戦略設計**では、そうした「意味のまとまり」を **境界づけられたコンテキスト（Bounded Context）** として切り出し、コンテキスト同士の関係を **コンテキストマップ** で可視化します。

この教材では、初心者向けに**ざっくり**その考え方を押さえます。  
詳細なパターンの暗記より、「**なぜ区切るのか**」「**図の読み方**」を重視します。

前提: [[02_DDDとは]]

---

## 1. なぜ区切るのか — 同じ「顧客」でも意味が違う

例えば社内システムで「顧客（Customer）」という言葉を考えます。

| コンテキスト | 「顧客」に含まれる情報・意味 |
|--------------|------------------------------|
| 営業 | 見込み客、商談ステータス、担当者 |
| 会計 | 請求先、与信限度、支払条件 |
| 配送 | 届け先住所、配送希望時間帯 |

**1つの巨大な `Customer` テーブルに全部詰め込む**と、

- フィールドが増え続け、誰も全体像を把握できない
- 営業の変更が会計に副作用を起こす
- チーム間で「顧客とは何か」の議論が終わらない

といった問題が起きやすくなります。

**境界づけられたコンテキスト**は、こうした問題に対して、

> **「この言葉・このモデルは、この境界の中ではこの意味」**  
> と、**意味のまとまりごとに区切る**設計単位です。

---

## 2. 境界づけられたコンテキストとは

**境界づけられたコンテキスト（Bounded Context, BC）** とは、

- **一貫したユビキタス言語**（現場と開発で共有する用語）が使われる
- **その言葉に対応したモデル**（クラス・テーブル・API）が閉じている
- **外のコンテキストとは、はっきり境界がある**

という**独立した意味空間**です。

```
┌─────────────────────┐     ┌─────────────────────┐
│  営業コンテキスト      │     │  会計コンテキスト      │
│                     │     │                     │
│  Prospect（見込み客） │     │  BillTo（請求先）     │
│  Deal（商談）         │     │  Invoice（請求書）    │
│  ...                │     │  ...                │
└─────────────────────┘     └─────────────────────┘
        ↑ 境界                    ↑ 境界
   ここでは「顧客」は          ここでは「顧客」は
   見込み・商談の文脈          請求・与信の文脈
```

1つの BC の中では、**用語とモデルは矛盾なく使える**ようにします。  
BC の外とは、**翻訳（変換）** を挟んで連携するのが基本です。

---

## 3. ユビキタス言語（短く）

BC を語るうえで欠かせないのが **ユビキタス言語（Ubiquitous Language）** です。

> **開発者とビジネス側が、同じ言葉で同じものを指す。**

- コードのクラス名・メソッド名に、現場の用語をそのまま使う
- 「ユーザー」「会員」「顧客」のような曖昧な言い換えを、BC 内では統一する

ユビキタス言語は **BC ごと** に定義されます。  
営業 BC と会計 BC で「顧客」の呼び方や属性が違っても、**それぞれの中で一貫していればよい**のです。

---

## 4. コンテキストマップとは

**コンテキストマップ（Context Map）** は、複数の BC 同士が**どう関係しているか**を図にしたものです。

```
        ┌──────────┐
        │  会計 BC  │
        └────▲─────┘
             │ 顧客ID・請求情報を受け取る
        ┌────┴─────┐
        │  営業 BC  │──────→ 配送 BC
        └──────────┘   受注確定イベントを送る
```

マップを描くと、

- **どこが「上流」で、どこが「下流」か**
- **データを誰が所有しているか**
- **連携は API か、イベントか、バッチか**

が議論しやすくなります。

---

## 5. コンテキスト間の関係 — 代表的なパターン（ざっくり）

全部覚える必要はありません。**よく出るもの**だけ押さえます。

| パターン | イメージ | 例 |
|----------|----------|-----|
| **共有カーネル（Shared Kernel）** | 一部のモデルを2つ以上の BC で共有 | 共通の「金額」「通貨」型 |
| **顧客／供給者（Customer-Supplier）** | 下流が上流の API・モデルに依存 | 会計が営業の顧客 ID を参照 |
| **順応者（Conformist）** | 下流が上流のモデルに合わせきる | 外部 SaaS のデータ形式に完全準拠 |
| **腐敗防止層（Anti-Corruption Layer, ACL）** | 外部のモデルを自 BC の言葉に翻訳 | レガシー API をラップして自社用 DTO に変換 |
| **公開ホストサービス（Open Host Service）** | 標準化した API を広く公開 | 共通の「注文照会 API」 |
| **別々の道（Separate Ways）** | 連携せず、それぞれ独立に実装 | 統合コストが利益を上回るとき |

初心者がまず覚えるとよいのは **ACL（腐敗防止層）** です。  
**外の世界の言葉やモデルが、自コンテキストのきれいなモデルを汚さないように、翻訳の層を挟む** — これはレガシー連携でもマイクロサービス間でも頻出です。

---

## 6. モノリスでも使える

「コンテキスト＝マイクロサービス」とは限りません。

```
src/
├─ sales/          ← 営業 BC（フォルダ・パッケージで境界）
│   ├─ domain/
│   └─ application/
├─ accounting/     ← 会計 BC
│   ├─ domain/
│   └─ application/
└─ shared-kernel/  ← 共有する最小限の型だけ
```

**1つのデプロイ単位（モノリス）の中でも、パッケージやモジュールで BC を分ける**ことはよくあります。  
後からサービス分割する際の**地図**にもなります。

---

## 7. よくある誤解

| 誤解 | 実際 |
|------|------|
| BC は必ずマイクロサービス | モノリス内のモジュール境界でもよい |
| 1 BC に1チーム | 目安にはなるが、小さければ1チームが複数 BC もありうる |
| 最初から完璧なマップを描く | 進化させながら更新するもの。初版は「だいたい」でよい |
| 全部つなぐべき | Separate Ways（連携しない）も正当な選択 |

---

## 8. 小さな練習のしかた

1. 自分のプロジェクトで **3つ以上の「言葉がブレやすい用語」** を書き出す（例: ユーザー、注文、商品）
2. それぞれ **どの業務の文脈か** を分ける
3. 紙に **四角（BC）と矢印（関係）** を描く
4. **誰がデータの正（ソース・オブ・トゥルース）を持つか** を1行ずつメモする

これだけで、コンテキストマップの入門は十分です。
