# ユビキタス言語（Ubiquitous Language）

## はじめに

**ユビキタス言語** は、DDD（ドメイン駆動設計）の中で **最も基本的で、最も重要な概念** です。

「**ユビキタス**」とは「**どこにでも遍在する**」という意味。つまり、

> **「業務の人も、設計者も、実装者も、ドキュメントも、コードも、テストも、全員が同じ言葉を使う」**

という考え方です。

---

## なぜ「同じ言葉」が大事なのか

### 言葉がズレると何が起きるか

業務の人: 「顧客から受注があったら、出荷指示を出してほしい」
開発者: 「じゃあ、`User` が `Order` して、`Delivery` を `create` するんですね」
業務の人: 「『出荷』はやくて、『発送』のはずですけど…」
開発者: 「あ、`Delivery` じゃなくて `Shipment` でした」
業務の人: 「あと『受注』と『注文』は別物です。『受注』は確定前の状態で…」

これが **毎回** 発生します。しかも後日、コードを読んでも、

- `Order` は「受注」? 「注文」?
- `Delivery` と `Shipment` はどう違う?
- `User` は「顧客」なのか「従業員」も含むのか?

と混乱し続けます。

### ユビキタス言語があれば

最初に**用語を揃えて定義しておけば**、こうしたズレが起きません。

```
受注 = Order(status: pending)
注文 = Order(status: confirmed)
発送 = Shipment
顧客 = Customer（Userとは別）
```

全員がこの定義に従って話し・書きます。

---

## どこで「同じ言葉」を使うか

ユビキタスという名のとおり、**あらゆる場所で** 同じ言葉を使います。

### 1. 会議・ディスカッション

「顧客の発送対応で…」と口頭で話すときから揃える。

### 2. 仕様書・ドキュメント

```
【発送処理の仕様】
顧客の注文が確定したら、発送指示書が発行される。
```

### 3. コード

```typescript
class Customer { /* ... */ }
class Order { /* ... */ }
class Shipment { /* ... */ }

class ShipmentService {
  createShipment(order: Order) { /* ... */ }
}
```

**コードのクラス名・メソッド名・変数名** が、業務で使う言葉そのものになっている。

### 4. テスト

```typescript
test('注文が確定したら発送指示書が発行される', () => {
  const order = Order.confirm();
  const shipment = service.createShipment(order);
  expect(shipment).toBeDefined();
});
```

**テストコードの日本語** も同じ言葉で書く。

### 5. Git コミットメッセージ / PRタイトル

```
feat: 発送指示書の発行処理を追加
fix: 顧客IDが空の場合にエラーを返す
```

## ユビキタス言語のつくり方

### ステップ1: 重要な概念を洗い出す

業務の人と一緒に、**登場する物・出来事・ルール** を書き出す。

### ステップ2: 意味を定義する

- 顧客 = 商品を購入する個人または法人
- 注文 = 顧客が商品を指定して購入を申し込む行為

### ステップ3: 用語集（Glossary）を作る

```markdown
## 用語集

### 顧客（Customer）
商品を購入する個人または法人。
ゲスト購入者（アカウントなし）も含む。

### 注文（Order）
顧客が商品を指定して購入を申し込む単位。
状態: pending → confirmed → shipped → delivered

### 発送（Shipment）
注文に対して物理的に商品を送り出す行為。
```

### ステップ4: 英語名も決める

```
顧客 = Customer（buyer, user ではない）
注文 = Order（purchase ではない）
発送 = Shipment（delivery は到着を指すので別）
```

### ステップ5: コードに反映

クラス名・変数名・関数名すべてを統一。

### ステップ6: 育て続ける

業務の新しい言葉が出てきたら即追加。古くなったら更新。

## 実装例

### Before: 言葉がバラバラ

```typescript
class User {
  buy(product) { /* 買う */ }
}

class PurchaseManager {
  processPurchase(user, product) { /* 購入処理 */ }
}

class DeliveryHandler {
  ship(purchase) { /* 発送 */ }
}
```

`User` / `Customer`、`buy` / `Purchase`、`Delivery` / `Ship`、どれもバラバラ。

### After: ユビキタス言語で統一

```typescript
class Customer {
  placeOrder(product: Product): Order { /* 注文する */ }
}

class OrderService {
  confirmOrder(order: Order) { /* 注文確定 */ }
}

class ShipmentService {
  createShipment(order: Order): Shipment { /* 発送指示作成 */ }
}
```

**業務の言葉** がそのままコードになっている。

## ユビキタス言語の敵

### 1. 勝手な意訳

**開発者がカッコいいと思う英語名** を勝手につける。業務の人が読めない。

### 2. 曖昧な同義語

`user` と `customer` と `member` が混在する。

### 3. 略語・暗号

`custMgr`, `purProc`, `dlvSvc` のような **意味不明な略語**。

### 4. 業界用語の無視

業界用語（受注・与信・引当・締日）を勝手な言葉に置き換える。

### 5. 更新されない辞書

用語集が古くなっても放置される。

---

## 境界づけられたコンテキストとの関係

ユビキタス言語は **1つのコンテキスト内** で有効です。

- **受注システム** での「商品」 = まだ買われていない在庫
- **倉庫システム** での「商品」 = 棚にある物理的な物
- **配送システム** での「商品」 = 梱包された荷物

同じ「商品」でも意味が違うなら、**別のコンテキスト** と捉えて、別々のユビキタス言語を持ちます。

→ 詳しくは [[04_境界づけられたコンテキスト]]

---

## 実務での効果

ユビキタス言語を徹底すると、

1. **業務の人とのコミュニケーションがスムーズ**
2. **新メンバーが業務を理解しやすい**
3. **仕様書・ドキュメント・コード・テストが一貫する**
4. **バグの原因になる解釈違いが激減**
5. **業務の変更をコードに素早く反映できる**

「たかが命名」ですが、**最も効果の高い設計活動** と言っても過言ではありません。
