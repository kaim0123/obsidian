# 戦略的設計 — システムの分け方

## この章の目的

DDD の **戦略的設計** — 大きなシステムをどう区切るか — を学びます。

> 詳細は [[03_境界づけられたコンテキストとコンテキストマップ]]、[[04_境界づけられたコンテキスト]] を参照。

---

## 1. 境界づけられたコンテキスト（Bounded Context）

**境界づけられたコンテキスト** とは、**特定のモデルと用語が有効な範囲** です。

同じ「商品」でも、コンテキストによって意味が異なります。

| コンテキスト | 「商品」の意味 |
|-------------|---------------|
| 販売 | 顧客に売るもの（価格・在庫） |
| 物流 | 配送するもの（重量・サイズ） |
| 会計 | 計上するもの（科目・税区分） |

```text
  ┌─────────────┐    ┌─────────────┐
  │ 販売コンテキスト │    │ 物流コンテキスト │
  │ 用語: 注文・商品  │    │ 用語: 出荷・梱包  │
  └─────────────┘    └─────────────┘
```

**1 つの巨大モデルに全部詰め込まない** のが戦略的設計の要点です。

---

## 2. コンテキストマップ — 境界間の関係

**コンテキストマップ** は、コンテキスト同士の **関係** を図示したものです。

| 関係の種類 | 意味 |
|-----------|------|
| **共有カーネル** | モデルの一部を共有 |
| **顧客/供給者** | 下流が上流のモデルに依存 |
| **腐敗防止層（ACL）** | 外部モデルを自コンテキスト用に変換 |
| **別々の道** | 連携しない |

```text
  販売 ──OrderPlaced──→ 物流
    │                      │
    └── イベント or API ────┘
```

境界を越えるときは **変換・契約** を明示します。

---

## 3. 大泥団（Big Ball of Mud）を避ける

**大泥団** とは、境界のない単一モデルに全機能が詰め込まれた状態です。

- 用語が文脈なく混在
- 変更が全体に波及
- チームが同じコードベースで衝突

```text
  大泥団を避ける = コンテキストで「この言葉はここではこの意味」と決める
```

---

## 4. 組織と設計の関係（Conway の法則）

**Conway の法則**: システムの構造は、組織のコミュニケーション構造を反映する。

```text
  3 チームが 1 つの無境界コードベースを触る
       → 設計も組織も混乱しやすい

  コンテキストごとにチームを分ける
       → 設計の境界と組織の境界が整合
```

戦略的設計は **技術だけでなく組織設計** とも関連します。

---

## 5. 戦略的設計の進め方

1. **ドメインを洗い出す** — 業務領域の一覧
2. **用語のブレを探す** — 同じ言葉で違う意味がないか
3. **コンテキスト候補を決める** — モデルと用語が一貫する単位
4. **コンテキストマップを描く** — 連携方法を決める
5. **段階的に分離** — 最初から完璧な分割は不要

小規模なら 1 コンテキストで十分なことも多いです。

---

## まとめ

- 境界づけられたコンテキストはモデルと用語の有効範囲
- コンテキストマップで境界間の関係を明示
- 大泥団を避け、Conway の法則を意識
- 段階的にコンテキストを分けていく
