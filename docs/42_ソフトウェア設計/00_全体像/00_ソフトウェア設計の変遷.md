# ソフトウェア設計 — パラダイムと設計思想の変遷

## このノートの目的

ソフトウェア設計には、**手続き指向 → オブジェクト指向 → 関数型指向 → DDD → イベント駆動** という流れで、課題への応答として新しい考え方が積み重なってきました。

このノートでは、

- **西暦順**に、それぞれが**どんな時代背景・課題**に直面していたか
- **何を解決しようとしたのか**
- **どういう設計の考え方で解決したのか**
- **限界と次の流れ**

を整理します。

> **補足**: これらは「古いものが消えて新しいものに置き換わった」わけではありません。現代のシステムは**複数を組み合わせて**使うのが普通です。

## 1. 手続き指向（1950年代〜）

### 時代背景

コンピュータが商用化され、プログラムの規模が急速に大きくなった時代です。初期は機械語やアセンブリで「命令を上から順に書く」スタイルが中心でした。

### 直面していた課題

- **`goto` 乱用によるスパゲッティコード** — 処理の流れが追えず、バグ修正のたびに別の場所が壊れる
- **グローバル変数の乱立** — どこからでもデータを書き換えられ、原因調査が困難
- **プログラムの肥大化** — 数千行を超えると、全体像を把握できない
- **変更コストの増大** — 1か所直すと、想定外の副作用が連鎖する

### 解決の考え方

**構造化プログラミング**（Edsger Dijkstra ら、1960〜70年代）を中心に、次の原則が確立されました。

| 原則 | 内容 |
|------|------|
| 3つの基本構造 | **順次・分岐・反復**だけで制御フローを組み立てる（`goto` を排除） |
| 手続き（関数・サブルーチン） | 処理を**名前付きの単位**に分割し、再利用する |
| トップダウン設計 | 大きな問題を**小さな手続き**に分解する |
| データと処理の分離（初期形） | データ構造と、それを操作する手続きを**別々に**定義する |

```text
main()
  ├─ input_data()
  ├─ validate()
  ├─ calculate()
  └─ output_result()
```

### 何が改善されたか

- プログラムの**読みやすさ・保守性**が向上
- 手続き単位で**テスト・デバッグ**しやすくなった
- 「処理の流れ」が明確になり、チーム開発が可能になった

### 残った課題（次のパラダイムへの布石）

- データとそれを操作する手続きが**別ファイル・別モジュール**に散らばり、整合性が保てない
- 同じデータ構造に触る手続きが増えると、**変更の影響範囲**が読めなくなる
- 現実世界の「もの」（注文、顧客、口座）を、**手続きの集合**として表現しにくい

## 2. オブジェクト指向（1960年代〜、1990年代に主流化）

### 時代背景

ソフトウェアが業務システムの中核になり、**GUI・アプリケーション・大規模業務システム**の設計が問題になりました。Simula（1960年代）、Smalltalk（1970年代）、C++（1983）、Java（1995）などを経て、1990年代以降は OOP が**事実上の標準**になりました。

### 直面していた課題

- **データと振る舞いの分離** — 手続き指向では「データ構造」と「それを操作する関数」が離れ、変更時に両方を追う必要がある
- **グローバル状態の共有** — 複数の手続きが同じデータを直接書き換え、バグの温床になる
- **コードの再利用の限界** — コピペや巨大な共通関数に頼り、変更が波及する
- **ドメインのモデリングの困難さ** — 現実世界の「もの」と「関係」を、手続きの羅列で表現しにくい

### 解決の考え方

**データ（状態）と振る舞い（メソッド）をひとまとめにした「オブジェクト」** を中心に設計します。

| 概念 | 何を解決するか |
|------|---------------|
| **カプセル化** | 内部状態を隠し、決められた操作だけ公開する → 不正な書き換えを防ぐ |
| **継承** | 共通部分を基底クラスにまとめ、差分だけ派生クラスに書く → 再利用 |
| **多態（ポリモーフィズム）** | 同じインターフェースで異なる実装を差し替える → 拡張に強い |
| **メッセージパッシング** | オブジェクト同士が「命令」ではなく「メッセージ」で協調する → 疎結合 |

```text
[Order オブジェクト] ──place()──→ [Inventory オブジェクト]
       │                                    │
       └── 状態: items, total              └── 状態: stock
           振る舞い: calculate(), submit()       振る舞い: reserve(), release()
```

### 何が改善されたか

- **現実世界の概念**（ユーザー、注文、商品）をコードに直接対応させやすくなった
- 変更の影響を**オブジェクトの境界**で抑えられる
- デザインパターン（GoF, 1994）と組み合わせ、**再利用可能な設計語彙**が生まれた

→ 詳細は [[02_クラスとオブジェクト]]、[[01_SRP（単一責任の原則）]]

### 残った課題（次の流れへの布石）

- **継承の乱用** — クラス階層が複雑化し、かえって理解しにくくなる
- **可変状態（mutable state）** — オブジェクト内部の状態変更が、並行処理・テストで問題になる
- **貧血ドメインモデル** — ロジックがサービスクラスに逃げ、オブジェクトがデータ入れ物になる
- **技術中心の設計** — DB テーブルや画面構造に引っ張られ、**業務の言葉とコードがズレる**

## 3. 関数型指向（1950年代に起源、2000年代以降に再注目）

### 時代背景

関数型の考え方自体は **Lisp（1958）** に遡ります。ただし業務システムの主流になったのは、**マルチコア CPU の普及・並行処理の重要性・テスト文化の成熟** を背景とした 2000年代以降です。Haskell（1990）、Scala（2004）、Clojure（2007）、そして JavaScript / Python / Java への関数型機能の取り込みがこの流れを加速させました。

### 直面していた課題

- **共有 mutable 状態** — OOP でも手続き型でも、複数箇所から同じ状態を書き換えるとバグが追いにくい
- **副作用（side effect）** — ログ出力・DB 更新・外部 API 呼び出しが混ざると、**同じ入力でも結果が変わる**処理になりテストが困難
- **並行処理の複雑さ** — スレッド・ロック・デッドロックの管理が開発者の負担になる
- **「何がいつ変わったか」が読めない** — 状態変更の連鎖がデバッグを困難にする

### 解決の考え方

**関数を第一級オブジェクト**として扱い、**副作用を最小化**する設計を重視します。

| 概念 | 何を解決するか |
|------|---------------|
| **純粋関数** | 同じ入力 → 同じ出力。外部状態を変えない → テスト・推論が容易 |
| **不変データ（immutability）** | データを書き換えず、新しい値を作る → 共有によるバグを防ぐ |
| **高階関数** | 関数を引数・戻り値にする → 処理の合成・抽象化 |
| **参照透過性** | 式の結果が文脈に依存しない → 並列化・最適化しやすい |

```javascript
// 命令型: 状態を直接書き換える
let total = 0;
for (const item of items) {
  total += item.price;  // total が変わる
}

// 関数型: 新しい値を返す（元データは変えない）
const total = items.reduce((sum, item) => sum + item.price, 0);
```

### 何が改善されたか

- **並行・並列処理**で状態競合が起きにくくなった
- ユニットテストが書きやすく、**バグの再現性**が高まった
- データ変換パイプライン（`map` / `filter` / `reduce`）で**意図が読みやすい**コードになった

### 残った課題（次の流れへの布石）

- **現実世界は状態を持つ** — 注文のステータス変更など、immutable だけでは表現が不自然な場面がある
- **I/O との境界** — 結局 DB や HTTP は副作用なので、**どこで現実と接するか**の設計が必要
- **チームの学習コスト** — モナド等の抽象概念が、業務アプリには過剰になりうる
- **ドメインの複雑さ** — 関数型だけでは「業務の言葉と構造のズレ」は解決しない

## 4. DDD — ドメイン駆動設計（2003年〜）

### 時代背景

2000年代初頭、**大規模業務システム**が増え、オブジェクト指向や三層アーキテクチャを使っても、プロジェクトが失敗し続けました。Eric Evans が 2003 年に『Domain-Driven Design』を出版し、**「技術の都合」ではなく「業務（ドメイン）」を設計の中心**に置く方法論が広まりました。

### 直面していた課題

- **ユビキタス言語の欠如** — 開発者と業務担当者が別の言葉を使い、要件のすり合わせが破綻する
- **貧血ドメインモデル** — エンティティは getter/setter だけ、ロジックは巨大なサービスクラスに集中
- **大泥団（Big Ball of Mud）** — 境界のない単一モデルに全機能が詰め込まれ、変更が全体に波及
- **技術主導の設計** — DB スキーマや画面仕様から設計が始まり、**業務ルールがコード中に散在**する
- **組織と設計の不一致** — 1 つの巨大コードベースを多数チームで触り、コンフリクトと認識齟齬が常態化

### 解決の考え方

**業務の構造・言葉・ルールを、ソフトウェアの構造に反映する**。

#### 戦略的設計（システム全体の分け方）

| 概念 | 何を解決するか |
|------|---------------|
| **ユビキタス言語** | チーム全員が同じ用語を使う → 要件とコードのズレを防ぐ |
| **境界づけられたコンテキスト** | 「この範囲ではこの言葉はこの意味」と境界を引く → モデルの混乱を防ぐ |
| **コンテキストマップ** | コンテキスト間の関係（共有・変換・上流/下流）を明示 → 統合の設計 |

#### 戦術的設計（コードの書き方）

| 概念 | 何を解決するか |
|------|---------------|
| **エンティティ / 値オブジェクト** | 業務上の「もの」を型で表現 → ルールの置き場所が明確になる |
| **集約** | 整合性を保つ単位を決める → 不正な状態遷移を防ぐ |
| **リポジトリ** | 永続化の詳細を隠す → ドメインロジックと DB 実装を分離 |
| **ドメインイベント** | 「起きたこと」を明示 → 後続処理との疎結合（イベント駆動への橋渡し） |

```text
  ┌─────────────────────────────────────┐
  │  注文コンテキスト                      │
  │  用語: 注文 / 明細 / 出荷              │
  │  集約: Order（注文確定・キャンセル）    │
  └──────────────┬──────────────────────┘
                 │ OrderPlaced イベント
                 ▼
  ┌─────────────────────────────────────┐
  │  在庫コンテキスト                      │
  │  用語: 引当 / 出庫                     │
  │  集約: StockItem（在庫数の整合性）      │
  └─────────────────────────────────────┘
```

### 何が改善されたか

- **コードと業務の対応**が取りやすくなり、仕様変更の影響範囲を見積もれる
- チームを**コンテキスト単位**で分けられる（Conway の法則との整合）
- 複雑な業務ルールを**ドメイン層に集約**し、フレームワークや DB に引っ張られにくくなった

→ 詳細は [[02_DDDとは]]、[[02_DDDとは]]

### 残った課題（次の流れへの布石）

- **分散システム** — コンテキストを別サービスに分けると、**跨る整合性**や**通信**の設計が別問題になる
- **同期呼び出しの限界** — サービス間を REST で直結すると、**結合と障害伝播**が再発する
- **DDD の形式だけの導入** — 用語集や図だけ作り、ドメインロジックがサービス層に残る「DDD っぽい設計」

## 5. イベント駆動（2000年代〜、2010年代に本格化）

### 時代背景

Web サービス・クラウド・マイクロサービスの普及により、**複数の独立したサービス**が連携する構成が一般化しました。メッセージブローカー（RabbitMQ, Apache Kafka 等）の成熟と、DDD の**ドメインイベント**概念が合流し、**Event-Driven Architecture（EDA）** として整理され始めました。

### 直面していた課題

- **同期 API の結合** — A が B を直接呼ぶと、B が遅い・落ちているとき A も止まる（[[03同期APIとメッセージとイベント駆動の概観]]）
- **時間的結合（temporal coupling）** — 呼び出し側と呼び出し先が**同時に稼働**している必要がある
- **スケールの非対称** — 注文処理は忙しいが、分析処理は閑散とする。同期だとピークが連鎖する
- **ドメイン横断の処理** — 1 つの出来事（注文確定）に、在庫・決済・配送・通知など**複数の関心**が反応したい
- **監査・再現・分析** — 「いつ何が起きたか」の履歴が、サービス間の呼び出しログだけでは追いにくい

### 解決の考え方

**「何かが起きた」という事実（イベント）を publish し、関心のある側が subscribe して反応する**。

| 概念 | 何を解決するか |
|------|---------------|
| **イベント** | 「OrderPlaced」「PaymentCompleted」など、**過去形の事実**を表現 |
| **Publisher / Subscriber** | 送り手は誰が受け取るか知らなくてよい → 疎結合 |
| **メッセージブローカー / イベントストア** | 非同期配送・バッファリング・再試行 → 障害耐性・スケール |
| ** eventual consistency（結果整合性）** | 即時の全体整合ではなく、**時間をかけて収束** → 可用性とスケールのトレードオフを受け入れる |

```text
  注文サービス                    イベントバス / ストリーム
       │                              │
       │  OrderPlaced ───────────────→├──→ 在庫サービス（引当）
       │                              ├──→ 決済サービス（与信）
       │                              ├──→ 通知サービス（メール）
       │                              └──→ 分析サービス（集計）
       │
       └── 注文 API はすぐ 202 Accepted を返せる（非同期）
```

### 何が改善されたか

- サービス間の**結合度を下げ**、独立したデプロイ・スケールが可能になった
- ピーク時に**キューで吸収**でき、システム全体の耐障害性が上がった
- 新機能（例: ポイント付与）を、既存サービスを変更せず**新しい Subscriber として追加**できる
- DDD のドメインイベントと自然に接続し、**業務の出来事**がシステム連携の単位になる

→ 詳細は [[03同期APIとメッセージとイベント駆動の概観]]、[[05_ドメインイベント]]

### 残った課題

- **結果整合性の複雑さ** — 「いつ反映されるか」がユーザーに分かりにくい。UI 設計・冪等性・補償トランザクション（SAGA）が必要
- **デバッグの難しさ** — 処理が非同期・分散するため、**トレーシング**（OpenTelemetry 等）が必須
- **イベントスキーマの進化** — バージョン管理・後方互換を怠ると、Consumer が次々壊れる
- **過剰な非同期化** — 全部イベントにすると、シンプルな CRUD まで複雑になる

## 6. 全体像 — 課題と解決の連鎖

```text
  手続き指向          オブジェクト指向         関数型指向
  ─────────          ──────────────         ──────────
  goto・スパゲッティ  → データと処理の一体化  →  mutable 状態・副作用
  巨大な main         カプセル化・多態         純粋関数・不変性
        │                    │                    │
        └────────────────────┴────────────────────┘
                              │
                              ▼
                    業務の複雑化・組織の拡大
                              │
                              ▼
                           DDD
              業務の言葉と構造を設計の中心に
              境界づけられたコンテキスト・集約
                              │
                              ▼
                    分散・マイクロサービス化
                              │
                              ▼
                        イベント駆動
              疎結合・非同期・結果整合性
              ドメインイベントによる連携
```

| 流れ | 主な課題 | 主な解決策 |
|------|---------|-----------|
| 手続き指向 | 制御フローの混乱、巨大化 | 構造化、手続き分割 |
| オブジェクト指向 | データと処理の分離、再利用 | カプセル化、継承、多態 |
| 関数型指向 | 共有状態、副作用、並行性 | 純粋関数、不変性 |
| DDD | 業務とコードのズレ、複雑なルール | ユビキタス言語、境界、集約 |
| イベント駆動 | 同期結合、スケール、横断関心 | イベント publish/subscribe |

## 7. 現代での使い方（排他ではなく組み合わせ）

これらは**どれか一つを選ぶ**ものではありません。

| レイヤー・場面 | よく使う考え方 |
|---------------|---------------|
| ドメインルールの整理 | **DDD**（ユビキタス言語、集約） |
| ドメインオブジェクトの実装 | **OOP**（エンティティ、値オブジェクト） |
| 副作用の少ない変換・検証 | **関数型**（純粋関数、immutable） |
| ユースケースの手順 | **手続き的**（アプリケーションサービスの流れ） |
| サービス間連携 | **イベント駆動**（ドメインイベント → メッセージ） |

```text
  [イベント駆動]  サービス間は OrderPlaced 等で非同期連携
        │
  [DDD]           各サービス内部は境界づけられたコンテキスト
        │
  [OOP + FP]      集約はオブジェクト、計算部分は純粋関数
        │
  [手続き]        ユースケースのオーケストレーション
```

## 9. まとめ

- ソフトウェア設計の歴史は、**規模と複雑さの増大**に対する応答の積み重ねである。
- **手続き指向**は制御フローと分割、**OOP**はデータと振る舞いの一体化、**関数型**は状態と副作用の管理、**DDD**は業務との整合、**イベント駆動**は分散環境での疎結合、それぞれが**前の時代の限界**を受けて生まれた。
- 現代ではこれらを**状況に応じて組み合わせる**のが実践的な設計である。
