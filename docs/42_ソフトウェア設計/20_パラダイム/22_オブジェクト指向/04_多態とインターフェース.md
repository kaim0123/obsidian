# 多態とインターフェース — 置換可能性

## はじめに

プログラムを書いていると、「同じメソッドなのに、呼んだ相手によって結果が違う」という場面があります。たとえば、

- `dog.speak()` → 「わん！」
- `cat.speak()` → 「にゃー」
- `cow.speak()` → 「もー」

同じ `speak()` なのに、相手が変わると違う結果になります。これが **多態性（Polymorphism）** です。

多態性を支えるのが **インターフェース** という仕組みです。

---

## 多態性（Polymorphism）とは

**多態性** とは、**同じ呼び出しが、受け手の型によって違う振る舞いをする** 性質です。「ポリモーフィズム」とも呼ばれます。

### 身近な例

- **リモコンのボタン** … 同じ「電源ON」ボタンでも、TVなら映像、扇風機なら風、照明なら光がつく
- **プリンタの印刷ボタン** … インクジェットでもレーザーでも「印刷」の呼び出しは同じ

**使う側はやり方を意識せず、結果だけ受け取れる** のが多態性の価値です。

---

## コード例: 多態性なしの場合

```javascript
function makeSound(animal) {
  if (animal.type === 'dog') {
    console.log('わん！');
  } else if (animal.type === 'cat') {
    console.log('にゃー');
  } else if (animal.type === 'cow') {
    console.log('もー');
  }
  // 動物が増えるたびにif追加…
}
```

動物を増やすたびに `makeSound` を修正しないといけません。しかも、動物に関する処理が何か所にも散らばります。

---

## コード例: 多態性あり

```javascript
class Animal {
  speak() { throw new Error('子クラスで実装すべき'); }
}

class Dog extends Animal {
  speak() { console.log('わん！'); }
}

class Cat extends Animal {
  speak() { console.log('にゃー'); }
}

class Cow extends Animal {
  speak() { console.log('もー'); }
}

function makeSound(animal) {
  animal.speak(); // どの動物でも同じ書き方
}

makeSound(new Dog()); // わん！
makeSound(new Cat()); // にゃー
```

新しい動物を追加したいときは **新しいクラスを作るだけ** で、`makeSound` は変更不要です。これが OCP（開放閉鎖の原則）です。

---

## インターフェース（Interface）とは

**インターフェース** は、「このクラスは最低限これができますよ」という **約束の一覧** です。

TypeScript の例：

```typescript
interface Animal {
  speak(): void;
  eat(food: string): void;
}

class Dog implements Animal {
  speak() { console.log('わん！'); }
  eat(food: string) { console.log(`${food}を食べる`); }
}
```

インターフェースを実装する（`implements`）と、**そこに書かれたメソッドを必ず持つ** ことが保証されます。

### なぜインターフェースが必要か

- **使う側が、具体クラスを知らなくてよい**（`Animal` として扱える）
- **差し替え可能**（`Dog` でも `Cat` でも受け取れる）
- **テスト用のモックが作れる**（本物のDBの代わりに偽物を渡す）

---

## リスコフの置換原則（LSP）

多態性が正しく機能するための大前提が **リスコフの置換原則（Liskov Substitution Principle）** です。

> **「親（または実装元のインターフェース）で期待された振る舞いを、子は必ず守る」**

つまり、**子を親のつもりで使っても壊れない** ことが必要です。

### 悪い例

```javascript
class Bird {
  fly() { /* 飛ぶ */ }
}

class Penguin extends Bird {
  fly() { throw new Error('飛べない'); } // LSP違反！
}

function travel(bird) {
  bird.fly(); // Penguinを渡すと壊れる
}
```

ペンギンは鳥だが飛べない。**継承は is-a 関係** だからといって、機械的に extends すると問題が起きる例です。

### 対処法

`Bird` と `FlyableBird` にインターフェースを分けるなど、**「できること」で型を分ける** のが解決策です。

---

## 多態性の3種類

教科書的には、多態性には3つの種類があります。

### 1. 部分型多相（Subtype Polymorphism）

オブジェクト指向のメイン。親子関係・インターフェース実装による多態。

### 2. パラメトリック多相（Parametric Polymorphism）

ジェネリクス・テンプレート。`List<T>` のように、**型をパラメータ化** する。

### 3. アドホック多相（Ad-hoc Polymorphism）

オーバーロード・演算子オーバーロード。**同じ名前で違う引数** を受け取る。

## ダックタイピング

**「アヒルのように歩き、アヒルのように鳴けば、それはアヒルだ」**

PythonやJavaScriptなど動的型付け言語では、**明示的なインターフェース宣言がなくても**、必要なメソッドさえ持っていれば使えます。

```python
class Duck:
    def quack(self): print('ガー')

class FakeDuck:
    def quack(self): print('（録音）ガー')

def perform(duck):
    duck.quack() # 「quackが呼べれば何でもいい」

perform(Duck())
perform(FakeDuck()) # インターフェース宣言なしで動く
```

柔軟ですが、**型で守られていない** ぶんバグを生みやすくもあります。型ヒント（Pythonの `Protocol`、TypeScriptの `interface`）で補うのが実務では一般的です。

## 実務での使いどころ

### 1. 決済方法の切り替え

```typescript
interface PaymentMethod {
  pay(amount: number): void;
}

class CreditCard implements PaymentMethod { /* ... */ }
class PayPal implements PaymentMethod { /* ... */ }
class ApplePay implements PaymentMethod { /* ... */ }

function checkout(method: PaymentMethod, amount: number) {
  method.pay(amount); // どの方法でもOK
}
```

### 2. 通知チャネルの切り替え

```typescript
interface Notifier {
  notify(user: User, message: string): void;
}

class EmailNotifier implements Notifier { /* ... */ }
class SlackNotifier implements Notifier { /* ... */ }
class SMSNotifier implements Notifier { /* ... */ }
```

### 3. テスト時の差し替え

```typescript
interface UserRepository {
  find(id: string): User;
}

class RealDBRepo implements UserRepository { /* ... */ }
class MockRepo implements UserRepository { /* テスト用 */ }
```

---

## まとめ

- **多態性** = 同じ呼び出しで違う振る舞い
- **インターフェース** = 「これができます」という約束
- **使う側が具体クラスを知らなくてよい** → 変更・拡張に強くなる
- LSP（置換原則）を守るのが前提条件
