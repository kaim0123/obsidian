# 継承と合成 — 「is-a」と「has-a」

## はじめに

オブジェクト指向で「既存のクラスを活用して新しいクラスを作る」方法には、2つの代表的なやり方があります。

- **継承（Inheritance）** … 既存のクラスを **拡張** する（「〜の一種である」）
- **合成（Composition）** … 既存のクラスを **部品として持つ**（「〜を持っている」）

初心者のうちは「継承ばかり使う」傾向がありますが、実は **合成のほうが使いやすく、壊れにくい** ことが多いです。この章では、両者の違いと使い分けを学びます。

---

## 継承とは（is-a 関係）

**継承** は、親クラスの性質を子クラスが受け継ぐ仕組みです。「**子クラスは親クラスの一種である（is-a）**」という関係で成り立ちます。

```javascript
class Animal {
  constructor(name) { this.name = name; }
  eat() { console.log(`${this.name}が食べる`); }
}

class Dog extends Animal {
  bark() { console.log(`${this.name}: わん！`); }
}

const pochi = new Dog('ポチ');
pochi.eat();  // 親の機能を使える
pochi.bark(); // 自分の機能
```

`Dog is-a Animal`（犬は動物の一種）という関係です。

### 継承の利点

- コードを **再利用** できる
- **共通の型** として扱える（ポリモーフィズム）

### 継承の欠点

- 親クラスの変更が **全子クラスに影響** する（脆い）
- 親子の関係が **固く結ばれる**（強結合）
- 多重継承すると **依存関係が複雑** になる（ダイヤモンド問題）
- **実装の継承** は「中身の秘密」まで引き継いでしまう

---

## 合成とは（has-a 関係）

**合成** は、クラスが別のクラスのオブジェクトを **部品として持つ** 方法です。「**AはBを持っている（has-a）**」という関係です。

```javascript
class Engine {
  start() { console.log('エンジン始動'); }
}

class Car {
  constructor() {
    this.engine = new Engine(); // Engineを部品として持つ
  }
  start() {
    this.engine.start();
    console.log('車が発進');
  }
}

const car = new Car();
car.start();
```

`Car has-a Engine`（車はエンジンを持っている）。

### 合成の利点

- **部品を差し替えやすい**（ガソリンエンジン→電気モーターなど）
- **関係が弱く**、変更の影響が狭い
- 実行時に **振る舞いを変えられる**
- テスト時に **モックを差し込みやすい**

### 合成の欠点

- コード量が少し増える
- 委譲（delegate）のコードを書く必要がある

---

## 「継承より合成」— なぜ合成が推奨されるか

Gang of Four の『デザインパターン』では、次のように提唱されています。

> **「クラス継承より、オブジェクト合成を使え」（Favor composition over inheritance）**

理由は、継承が **強すぎる関係** を作るからです。

### 継承が招くトラブル例

```javascript
class Stack extends ArrayList {
  // ListのaddAll等も継承してしまう → Stackのルール(LIFO)が崩れる
}
```

Stackは「push/popだけ使える」ことが肝心なのに、ArrayListの機能まで受け継いでしまい、**Stackの意図と矛盾するメソッド** が外から使えてしまいます。

これを合成で書くと：

```javascript
class Stack {
  constructor() {
    this.items = []; // ArrayListを内部に持つだけ
  }
  push(x) { this.items.push(x); }
  pop() { return this.items.pop(); }
  // 必要な機能だけを提供
}
```

Stackは自分の都合に合わせて **必要な操作だけ** 提供できます。

## 使い分けの指針

### 継承を使ってよい場面

- 明確な **「is-a」関係** が成り立つ
- 親クラスが **安定していて変更されない**（標準ライブラリの抽象クラスなど）
- **全ての子クラスで親の振る舞いが適切**（リスコフの置換原則を満たす）

### 合成を選ぶべき場面

- 単に「機能を使いたい」だけ（is-aではなくhas-a）
- 実行時に **振る舞いを切り替えたい**
- 親クラスの実装が変わる可能性がある
- 複数の異なる種類の振る舞いを組み合わせたい

## 合成の活用パターン

### 1. 戦略（Strategy）パターン

振る舞いをオブジェクトとして差し込む。

```javascript
class SortStrategy {
  sort(list) { throw new Error('実装が必要'); }
}
class QuickSort extends SortStrategy { sort(list) { /*...*/ } }
class MergeSort extends SortStrategy { sort(list) { /*...*/ } }

class Sorter {
  constructor(strategy) { this.strategy = strategy; }
  run(list) { return this.strategy.sort(list); }
}

new Sorter(new QuickSort()).run(data);
new Sorter(new MergeSort()).run(data); // 差し替え可能
```

### 2. 委譲（Delegation）

自分の仕事の一部を部品に任せる。

```javascript
class UserService {
  constructor(userRepo, mailer) {
    this.userRepo = userRepo;
    this.mailer = mailer;
  }
  register(user) {
    this.userRepo.save(user);    // 保存は部品に委譲
    this.mailer.send(user.email); // 送信も部品に委譲
  }
}
```

## よくある誤解

### 誤解1: 継承 = コード再利用

継承の本当の目的は **「多態的に扱うため」** であって、単なる再利用ではありません。再利用目的なら合成のほうが適しています。

### 誤解2: 深い継承ツリーが「高度」

継承を3階層以上重ねると、**どこで何が定義されているか分からなくなり** 読解コストが跳ね上がります。多くの場合は2階層以下に留めます。

### 誤解3: 抽象クラスならOK

抽象クラスの継承も、親の変更が全子に伝わるという性質は同じです。**インターフェースの実装（インターフェース継承）** は実装を引き継がないため比較的安全ですが、**実装の継承（extends）** は慎重に。

---

## まとめ

- **継承（is-a）** … 共通の型で扱うのが目的。慎重に使う
- **合成（has-a）** … 部品として使う。デフォルトはこちら
- 迷ったら **合成を選ぶ**
