# オブジェクト指向設計

## この章の目的

**オブジェクト指向（OOP）** の設計的意味を学びます。  
クラス・カプセル化・継承・多態が、なぜ設計に役立つかを押さえます。

> 詳細な解説は [[02_クラスとオブジェクト]]、[[03_継承と合成]]、[[04_多態とインターフェース]] を参照。

---

## 1. オブジェクト指向とは何か

**オブジェクト指向** とは、**データ（状態）と振る舞い（処理）をひとまとめにしたオブジェクト** を中心に設計する考え方です。

手続き指向の課題 — データと処理の分離による変更の困難 — に対する応答として発展しました。

```text
  手続き指向: データ ←→ 処理（別々）
  OOP:        [オブジェクト] = 状態 + 振る舞い（一体）
```

---

## 2. クラスとオブジェクト — 状態と振る舞いの一体化

| 概念 | 役割 |
|------|------|
| **クラス** | オブジェクトの設計図（型） |
| **オブジェクト** | クラスから作った実体（インスタンス） |

```javascript
class Order {
  constructor(items) {
    this.items = items;  // 状態
  }
  total() {              // 振る舞い
    return this.items.reduce((sum, i) => sum + i.price, 0);
  }
}
```

**「注文」という現実の概念** を、コード上の 1 つのまとまりとして表現できます。

---

## 3. カプセル化・継承・多態の設計的意味

| 概念 | 設計的意味 |
|------|-----------|
| **カプセル化** | 内部を隠し、不正な変更を防ぐ。境界を作る |
| **継承** | 共通を基底にまとめ、差分だけ派生に書く（ただし乱用注意） |
| **多態** | 同じインターフェースで実装を差し替える。拡張に強い |

```text
  カプセル化 → 変更の局所化
  継承       → 再利用（is-a が成立するときだけ）
  多態       → OCP の実現（拡張で対応）
```

継承より **合成（Composition）** を選ぶ場面が多いです → [[03_継承と合成]]

## 4. メッセージと協調（オブジェクト同士のやりとり）

OOP では、オブジェクト同士が **メッセージ** で協調します。

```text
[Order] ──place()──→ [Inventory]
              │
              └── reserve(items)
```

- 命令ではなく **「〇〇して」というメッセージ** を送る
- 送り手は相手の内部を知らなくてよい（疎結合）
- オブジェクトの **責務** が協調の単位になる

---

## 5. オブジェクト指向が向く場面と限界

### 向く場面

- 現実世界の **概念をモデル化** したい（注文、顧客、商品）
- **状態とルール** がセットのドメイン
- 振る舞いの **差し替え** が必要（支払い方法、配送方法）
- 多くの言語・フレームワークで標準的

### 限界

- **継承の乱用** で階層が複雑化
- **可変状態** が並行処理・テストで問題に
- **貧血モデル** — ロジックがサービスに逃げ、オブジェクトが空になる
- 単純なデータ変換には **関数型の方が自然** なことも

クラス設計の詳細は [[010Programming/44_クラス設計・デザインパターン/00_全体像/目次|クラス設計 目次]]、SOLID は [[05_SOLIDとの関係]] を参照。

## まとめ

- OOP は状態と振る舞いを一体化したオブジェクトを中心に設計
- カプセル化・継承・多態はそれぞれ設計上の意味がある
- メッセージによる協調で疎結合を実現
- 向く場面と限界を知り、他の考え方と組み合わせる
