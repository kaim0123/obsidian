# クラスとオブジェクト — 状態・振る舞い・カプセル化

## はじめに

オブジェクト指向プログラミング（OOP）の基本の道具が **クラス** と **オブジェクト** です。この2つの関係をたとえで言うと、

- **クラス = 設計図**
- **オブジェクト = その設計図から作った実物**

クッキーの型（クラス）から、同じ形のクッキー（オブジェクト）を何個も作れる、というイメージです。

---

## 基本の概念

### オブジェクトとは

**オブジェクト** は「状態（データ）」と「振る舞い（処理）」をひとまとめにしたものです。

現実世界で考えると分かりやすいです。

- **犬** というオブジェクト
  - 状態: 名前・年齢・色
  - 振る舞い: 吠える・走る・食べる

### クラスとは

**クラス** はオブジェクトの **設計図** です。どんな状態を持つか、どんな振る舞いができるかを定義します。

```javascript
class Dog {
  // 状態（フィールド / プロパティ）
  constructor(name, age) {
    this.name = name;
    this.age = age;
  }

  // 振る舞い（メソッド）
  bark() {
    console.log(`${this.name}: わん！`);
  }

  run() {
    console.log(`${this.name}が走っている`);
  }
}

// クラスからオブジェクトを作る（インスタンス化）
const pochi = new Dog('ポチ', 3);
const hachi = new Dog('ハチ', 5);

pochi.bark(); // ポチ: わん！
hachi.bark(); // ハチ: わん！
```

`pochi` と `hachi` は **別々のオブジェクト** ですが、同じ `Dog` クラスから作られているため **同じ振る舞い** ができます。

## 3つの柱: OOPの基本概念

オブジェクト指向には、一般に「3大要素」と呼ばれるものがあります。

1. **カプセル化**（Encapsulation）
2. **継承**（Inheritance） → [[03_継承と合成]]
3. **多態性**（Polymorphism） → [[04_多態とインターフェース]]

ここでは1つ目の **カプセル化** を中心に解説します。

---

## カプセル化（Encapsulation）

### 意味

**カプセル化** とは、データと、それを扱う処理を **ひとまとめにして、外から勝手にいじらせないようにする** ことです。

薬のカプセルのように、**中身が見えないけれど、必要な機能は使える** ようにするイメージです。

### なぜ必要か

カプセル化がないと、外部から直接データを書き換えられてしまい、不整合が起きます。

### 悪い例（カプセル化なし）

```javascript
class BankAccount {
  constructor() {
    this.balance = 0; // 誰でも自由に変えられてしまう
  }
}

const acc = new BankAccount();
acc.balance = -99999; // 残高がマイナス！ルールを破られた
```

### 良い例（カプセル化あり）

```javascript
class BankAccount {
  #balance = 0; // #は「プライベート」を示す（外から見えない）

  deposit(amount) {
    if (amount <= 0) throw new Error('入金額は正の数');
    this.#balance += amount;
  }

  withdraw(amount) {
    if (amount > this.#balance) throw new Error('残高不足');
    this.#balance -= amount;
  }

  getBalance() {
    return this.#balance;
  }
}

const acc = new BankAccount();
acc.deposit(1000);
// acc.#balance = -99999; // ← エラー。直接触れない
```

ポイントは、

- **データは隠す**（`#balance` は外から見えない）
- **操作はメソッド経由**（`deposit`・`withdraw` にルールを書ける）
- **ルール違反を入り口で止められる**（マイナス入金を拒否）

## 状態と振る舞いを「一緒に」持つ意味

手続き型プログラミングでは、データと処理がバラバラでした。

```javascript
// 手続き型
const balance = 0;
function deposit(balance, amount) { /* ... */ }
function withdraw(balance, amount) { /* ... */ }
```

データと処理が離れているので、**データを変更するたびに関連する処理を探して歩く** 必要があります。

オブジェクト指向では、**データと処理が1つのオブジェクトに結びつく** ため、変更の影響範囲が狭くなります。

---

## クラスの構成要素

| 要素 | 役割 | 例 |
|------|------|-----|
| フィールド（プロパティ） | オブジェクトの状態 | `name`, `age` |
| コンストラクタ | オブジェクト生成時の初期化 | `constructor(name)` |
| メソッド | オブジェクトの振る舞い | `bark()`, `run()` |
| 静的メンバー（static） | クラス全体で共有するもの | `Math.PI` |

### staticの例

```javascript
class MathUtil {
  static PI = 3.14159;
  static add(a, b) { return a + b; }
}

MathUtil.add(1, 2); // オブジェクトを作らずに呼べる
```

---

## クラスはモノとは限らない

初心者向けの説明では「犬」「車」など **実在するモノ** でクラスを例えますが、実際には：

- **UserRepository**（データアクセスの役割）
- **PaymentService**（支払い処理の役割）
- **TaxCalculator**（計算の役割）

のような **「役割」を表すクラス** のほうが実務では多いです。クラスは「モノを作る道具」ではなく、「**責任の単位を表現する道具**」と捉えるほうが本質的です。

---

## よくある誤解

### 誤解1: 何でもクラスにすべき

1つの関数で済むものは、クラスにする必要はありません。状態を持つ／振る舞いをまとめる意味がある場合だけクラスにします。

### 誤解2: Getter/Setter を機械的に作る

```javascript
class User {
  getName() { return this.name; }
  setName(n) { this.name = n; }
  // 全フィールドに対して…
}
```

これは **ただの公開フィールド** と変わらず、カプセル化の意味がありません。**「外に何を見せるか」を設計して絞る** ことが大事です。

### 誤解3: クラス数が多いほど良い

関心を分けるのは大事ですが、過剰にクラスを作ると全体像がつかみにくくなります。**「関係の深いデータと振る舞いは同じクラスに」** が原則です。
