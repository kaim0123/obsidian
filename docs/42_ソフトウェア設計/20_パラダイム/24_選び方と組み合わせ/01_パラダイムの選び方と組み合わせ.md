# パラダイムの選び方と組み合わせ

## この章の目的

手続き・OOP・関数型は **排他的ではありません**。  
状況に応じた選び方と組み合わせ方を学びます。

---

## 1. 排他的な選択ではない

「このプロジェクトは OOP」「あのプロジェクトは関数型」と **1 つだけ選ぶ必要はありません**。

現代のシステムは **複数の考え方を組み合わせて** 使うのが普通です。

```text
  古いものが消えて新しいものに置き換わったわけではない
  課題への応答として、考え方が積み重なってきた
```

→ [[00_ソフトウェア設計の変遷]] の「現代での使い方」も参照。

---

## 2. レイヤー・場面ごとの使い分け

| レイヤー・場面 | よく使う考え方 |
|---------------|---------------|
| ユースケースの流れ | **手続き的**（オーケストレーション） |
| ドメインオブジェクト | **OOP**（エンティティ、値オブジェクト） |
| データ変換・検証 | **関数型**（純粋関数、immutable） |
| サービス間連携 | **イベント駆動**（[[01_イベント駆動を学ぶ理由|40_イベント駆動設計]]） |
| 業務の構造整理 | **DDD**（[[01_DDDを学ぶ理由|30_ドメイン駆動設計]]） |

```text
  [イベント駆動]  サービス間は OrderPlaced 等で非同期連携
        │
  [DDD]           各サービス内部は境界づけられたコンテキスト
        │
  [OOP + FP]      集約はオブジェクト、計算部分は純粋関数
        │
  [手続き]        ユースケースのオーケストレーション
```

---

## 3. マルチパラダイム言語での実践

JavaScript、Python、Java、Kotlin、TypeScript などは **複数のスタイルを混在** できます。

```javascript
// OOP: ドメインオブジェクト
class Order {
  constructor(items) { this.items = items; }
  total() {
    // 関数型: 純粋な集計
    return this.items.reduce((sum, i) => sum + i.price, 0);
  }
}

// 手続き的: ユースケースの流れ
async function placeOrder(order) {
  validate(order);
  await repository.save(order);
  await notify(order);
}
```

**「言語の機能を使い分ける」** のではなく、**「問題に合った考え方を選ぶ」** ことが重要です。

---

## 4. パラダイムの押し付け合いを避ける

| 押し付け | 問題 |
|---------|------|
| すべてをクラスにする | 単純な関数で足りる処理までオブジェクト化 |
| すべてを純粋関数にする | 状態遷移が不自然、I/O 境界が曖昧 |
| 手続きだけで巨大化 | 責務の分散が進まない |

**チームの慣れ・言語・ドメインの性質** を考慮し、柔軟に選びます。  
「正しいパラダイム」は 1 つではなく、**トレードオフの中での選択** です。

---

## 5. 設計レビューでのパラダイムの見方

レビュー時の観点です。

- [ ] この処理は **選んだパラダイムに合っている** か
- [ ] 手続き・OOP・関数型が **一貫して混在** しすぎていないか（意図的なら OK）
- [ ] ドメインの性質（状態重視 vs 変換重視）に **合っている** か
- [ ] チームが **読み・保守できる** スタイルか

比較表は [[付録C_パラダイム比較表]] を参照。

---

## まとめ

- パラダイムは排他的ではなく、組み合わせて使う
- レイヤー・場面ごとに適した考え方がある
- 押し付け合いを避け、問題に合わせて選ぶ
- レビューでは一貫性と適合性を確認
