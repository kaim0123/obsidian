# 不変データと純粋関数 — 関数型の設計原則

## この教材の目的

[[01_関数型指向の考え方]] では、関数型の考え方（第一級関数・純粋関数・副作用・不変性・パイプライン）を概観しました。
この教材では、それを **設計の原則** として一段深く掘り下げます。

- **参照透過性**：なぜ純粋関数は「設計として」嬉しいのか
- **不変データ**：変更しないで、どうやって状態を扱うのか（永続データ構造・構造共有）
- **関数合成**：小さな関数を組み合わせて大きな処理を作る
- **データと振る舞いの分離**：オブジェクト指向との対比
- **副作用を端に寄せる**：設計全体としての置き方

純粋関数と副作用の **メソッド単位の書き方** は 46_メソッド設計 の [[02_純粋関数と副作用]] と [[03_Functional_Core_Imperative_Shell]] が本拠地です。ここでは **設計全体への効き方** を中心に扱います。

---

## 1. 参照透過性 — 「置き換えてよい」ことの価値

### 1.1 定義

> 式を、その **評価結果の値に置き換えても**、プログラムの意味が変わらないとき、その式は **参照透過**（referentially transparent）である。

```typescript
// 参照透過：add(2, 3) をどこで 5 に置き換えても意味は変わらない
const add = (a: number, b: number) => a + b;
const x = add(2, 3) * add(2, 3);   // ≡ 5 * 5

// 参照透過でない：呼ぶたびに結果が変わる・外の世界を変える
let counter = 0;
const next = () => ++counter;
const y = next() * next();          // 1 * 2。next() を値に置き換えられない
```

**純粋関数**（同じ入力に同じ出力を返し、副作用がない関数）の呼び出しは、参照透過です。

### 1.2 設計として何が嬉しいのか

| 効果 | 説明 |
|---|---|
| **局所的に理解できる** | 関数の中だけを読めば、何をするか分かる。外のどこかで変数が書き換えられる心配がない |
| **テストが単純** | 入力を与えて出力を確かめるだけ。モックも、事前準備（DB の初期化など）も不要 |
| **安全にリファクタリングできる** | 式を変数に括り出す・インライン化するなどの変形が、意味を変えずにできる |
| **キャッシュ（メモ化）できる** | 同じ入力なら結果も同じなので、結果を保存して再利用できる |
| **並行処理が安全** | 共有状態を書き換えないので、ロックなしで並列に実行できる |

これは [[06_カプセル化と情報隠蔽]] と同じ方向の効果です。カプセル化が「**状態を隠す**」ことで影響範囲を狭めるのに対し、参照透過性は「**状態を持たない**」ことで影響範囲をゼロにします。

> John Ousterhout の言葉を借りれば、純粋関数は「**知らなければならないことが少ない**（認知負荷が低い）」コードであり、「**知らないことを知らない**（unknown unknowns）」を生みにくいコードです（→ [[00_解説_ソフトウェア設計体系]]）。

## 2. 不変データ — 変えずに新しく作る

### 2.1 不変データとは

**一度作ったら中身を変えないデータ** です。変更が必要なときは、**変更を反映した新しいデータを作ります**。

```typescript
// 可変：元のデータを書き換える
function addItemMutable(cart: Cart, item: Item) {
  cart.items.push(item);           // 呼び出し元の cart も変わる
  cart.total += item.price;
}

// 不変：新しいデータを返す
function addItem(cart: Cart, item: Item): Cart {
  return {
    ...cart,
    items: [...cart.items, item],
    total: cart.total + item.price,
  };
}
```

### 2.2 なぜ不変にするのか

| 可変データで起きる問題 | 不変データでは |
|---|---|
| **どこで変わったか分からない**：同じオブジェクトを複数の場所が参照していると、一か所の変更が予期せぬ場所に波及する（エイリアシング問題） | 誰も変えられないので、渡した先で変わる心配がない |
| **時間による不整合**：処理の途中でデータが変わり、前半と後半で前提が違う | 処理中に前提が変わらない |
| **並行処理の競合**：複数スレッドが同時に書き換えて壊れる | 書き換えがないので競合しない |
| **変更履歴が残らない**：元に戻す・比較するのが難しい | 古い版がそのまま残るので、Undo・差分比較・タイムトラベルデバッグが容易 |

React が状態の更新に **新しいオブジェクトを渡す** ことを求めるのも、「参照が変わったかどうか」だけで変更を検出できるからです（→ 47_フロントエンド設計）。

### 2.3 「毎回コピーしたら遅いのでは？」— 永続データ構造と構造共有

不変データへのよくある懸念は「毎回全体をコピーしたら遅くなる」というものです。これを解決するのが **永続データ構造**（Persistent Data Structure）と **構造共有**（Structural Sharing）です。

```text
元のリスト:      A → B → C
先頭に X を追加: X ↗
                （A → B → C はそのまま共有）
```

- 変更された部分だけを新しく作り、**変わっていない部分は古い版と共有** する
- 木構造なら、根から変更箇所までの経路だけを作り直せばよい
- Clojure・Scala・Haskell などのコレクションや、JavaScript の Immer・Immutable.js がこの仕組みを使っている

> 「永続（persistent）」は DB に保存するという意味ではなく、**古い版が消えずに残り続ける** という意味です。

### 2.4 TypeScript で不変性を表す

```typescript
type Money = Readonly<{ amount: number; currency: "JPY" | "USD" }>;
type Cart = Readonly<{ items: ReadonlyArray<Item>; total: Money }>;

const cart: Cart = { items: [], total: { amount: 0, currency: "JPY" } };
// cart.items.push(item);   ← コンパイルエラー
```

- `readonly`・`Readonly<T>`・`ReadonlyArray<T>`・`as const` でコンパイル時に書き換えを防ぐ
- ただし実行時には防げないので、必要なら `Object.freeze` や Immer を使う

### 2.5 DDD の値オブジェクトとの関係

DDD の **値オブジェクト**（金額・住所・期間など）は、**不変であること** が基本ルールです（→ [[03_エンティティと値オブジェクト]]）。これはオブジェクト指向の中に関数型の考え方を取り入れたもの、と見ることができます。

## 3. 関数合成 — 小さな部品を組み合わせる

### 3.1 合成とは

関数 `f: A → B` と `g: B → C` があれば、それをつないで `A → C` の関数が作れます。これが **関数合成** です。

```typescript
const trim = (s: string) => s.trim();
const toLower = (s: string) => s.toLowerCase();
const removeSpaces = (s: string) => s.replace(/\s+/g, "");

// 合成：小さな関数をつないで新しい関数を作る
const pipe = <T>(...fns: Array<(x: T) => T>) => (x: T) => fns.reduce((v, f) => f(v), x);
const normalizeEmail = pipe(trim, toLower, removeSpaces);

normalizeEmail("  Taro@Example.com ");  // "taro@example.com"
```

### 3.2 設計としての意味

- **部品が小さく、1つのことだけをする**：[[05_凝集度と結合度]] でいう機能的凝集
- **部品同士は「型」でしかつながらない**：`B` を出す関数と `B` を受け取る関数は、互いの中身を知らない（疎結合）
- **ワークフローをパイプラインとして表せる**：「注文を検証する → 価格を計算する → 確認メールを作る」のような業務の流れが、そのままコードの形になる（→ [[03_型でドメインを表す_DomainModelingMadeFunctional]]）

オブジェクト指向が **「オブジェクトの組み合わせ（合成）」** で大きな構造を作るのに対し、関数型は **「関数の合成」** で大きな処理を作ります。どちらも「継承より合成」の考え方です（→ [[03_継承と合成]]）。

## 4. データと振る舞いを分ける

### 4.1 オブジェクト指向との対比

| | オブジェクト指向 | 関数型 |
|---|---|---|
| 基本の単位 | **データと振る舞いを1つのオブジェクトにまとめる** | **データ（型）と振る舞い（関数）を分ける** |
| 状態 | オブジェクトの中に隠して、メソッドで変える | 不変データとして外に出し、関数で新しい版を作る |
| 拡張しやすいもの | **新しい種類（クラス）を足す** のが簡単 | **新しい操作（関数）を足す** のが簡単 |
| 拡張しにくいもの | 全クラスに新しい操作を足す | 全関数に新しい種類を足す |

最後の2行は **Expression Problem**（式の問題）として知られる、パラダイム間の本質的なトレードオフです。

- 図形に「面積計算」という操作を足すのは、関数型なら関数を1つ書くだけ。OOP なら全クラスにメソッドを足す
- 図形に「三角形」という種類を足すのは、OOP ならクラスを1つ書くだけ。関数型なら全関数に分岐を足す

どちらが優れているかではなく、**「種類が増えやすいか、操作が増えやすいか」** で選びます（→ [[01_パラダイムの選び方と組み合わせ]]）。

### 4.2 代数的データ型

関数型では、データを **代数的データ型** で表すことが多いです。

| 種類 | 意味 | 例 |
|---|---|---|
| **直積型**（AND） | 「A **かつ** B **かつ** C」を持つ | 顧客 ＝ 名前 かつ メール かつ 住所（TypeScript のオブジェクト型） |
| **直和型**（OR） | 「A **または** B **または** C」のどれか1つ | 支払い方法 ＝ カード または 銀行振込 または 代引き（TypeScript の判別可能ユニオン） |

```typescript
type PaymentMethod =
  | { kind: "card"; cardNumber: string; expiry: string }
  | { kind: "bankTransfer"; accountId: string }
  | { kind: "cashOnDelivery" };
```

直和型は、「**ありえない組み合わせを表現できないようにする**」設計に直結します。詳しくは [[03_型でドメインを表す_DomainModelingMadeFunctional]] で扱います。

## 5. 副作用を端に寄せる

純粋関数だけではプログラムは何もできません（DB に保存も、画面表示もできない）。関数型の設計は **副作用をなくす** のではなく、**副作用を端に寄せ、中心を純粋に保つ** ことを目指します。

```mermaid
flowchart LR
  IN[入力<br>HTTP・DB読み込み<br>副作用] --> CORE[純粋な中心<br>検証・計算・判断<br>不変データ]
  CORE --> OUT[出力<br>DB書き込み・メール送信<br>副作用]
```

- これは Gary Bernhardt の **Functional Core, Imperative Shell**（[[03_Functional_Core_Imperative_Shell]]）であり、
- アーキテクチャのレベルでは **ヘキサゴナル／クリーンアーキテクチャ** と同じ形です（41_アーキテクチャ の [[依存性のルール]]）

つまり、関数型の設計原則は **関数の書き方** にとどまらず、**システム全体の構造の原則** としても働きます。

---

## 6. 関数型の原則を取り入れる順番（OOP 言語で）

TypeScript・Java・C# などの OOP 言語でも、関数型の原則は段階的に取り入れられます。

| 段階 | やること | 効果 |
|---|---|---|
| 1 | **計算ロジックを純粋関数に切り出す**（価格計算・バリデーション・変換） | テストが一気に書きやすくなる |
| 2 | **値オブジェクト・DTO を不変にする**（`readonly`） | 「どこで変わったか」問題が消える |
| 3 | **ループを map / filter / reduce に置き換える** | 何をしているかが読みやすくなる |
| 4 | **状態の種類を直和型で表す** | ありえない状態を型で防げる |
| 5 | **副作用をユースケースの最初と最後に集める** | 中心のロジックが純粋になり、構造が明確になる |

## 7. ありがちな誤解

### 7.1 「関数型を使うには Haskell などの関数型言語が必要」

**誤りです。** 参照透過性・不変データ・関数合成・副作用の分離は、TypeScript でも十分に実践できます。

### 7.2 「不変データは遅い」

**多くの場合は誤りです。** 構造共有によりコピーのコストは小さく抑えられます。また、変更検出が参照比較だけで済むので、全体としては速くなることもあります。ただし、大量データを頻繁に更新する箇所では計測して判断します。

### 7.3 「関数型とオブジェクト指向は対立する」

**誤りです。** 値オブジェクトの不変性、戦略パターン（関数を渡す）、ヘキサゴナルアーキテクチャ（副作用を外側に）など、両者は多くの場面で混ざり合っています。

---

## 8. まとめ

- **参照透過性**：式を値に置き換えても意味が変わらない。局所的に理解でき、テスト・リファクタリング・並行処理が容易になる
- **不変データ**：変えずに新しく作る。エイリアシング・時間による不整合・競合を防ぐ。**構造共有** で効率も保てる
- **関数合成**：小さな関数を型でつなぐ。機能的凝集と疎結合を自然に実現する
- **データと振る舞いを分ける**：操作の追加に強い（OOP は種類の追加に強い）。**直和型** でありえない状態を防ぐ
- **副作用を端に寄せる**：Functional Core, Imperative Shell。アーキテクチャのレベルではヘキサゴナル／クリーンと同じ形

次は [[03_型でドメインを表す_DomainModelingMadeFunctional]] で、型を使って業務ルールを表現する方法を学びます。
