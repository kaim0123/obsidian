# 手続き指向設計

## この章の目的

ソフトウェア設計の源流である **手続き指向** を理解します。  
構造化プログラミングと手続き分割は、今でもユースケースの流れなどで使われています。

> 歴史的背景は [[00_ソフトウェア設計の変遷]] の「手続き指向」章を参照。

---

## 1. 手続き指向とは何か

**手続き指向** とは、プログラムを **処理の流れ（手続き）** の集合として設計する考え方です。

- データと処理は **別々** に定義されることが多い
- **トップダウン** で大きな処理を小さな手続きに分割する
- `main` やコントローラが全体の流れを制御する

```text
main()
  ├─ input_data()
  ├─ validate()
  ├─ calculate()
  └─ output_result()
```

---

## 2. 構造化プログラミング — 順次・分岐・反復

Edsger Dijkstra らが提唱した **構造化プログラミング** は、制御フローを次の 3 つだけで組み立てます。

| 構造 | 意味 |
|------|------|
| **順次** | 上から順に実行 |
| **分岐** | if / switch で条件により分岐 |
| **反復** | for / while で繰り返し |

`goto` による飛び飛びの制御は避けます。これにより **処理の流れが追いやすく** なりました。

---

## 3. トップダウン設計と手続き分割

**トップダウン設計** は、大きな問題を **段階的に小さな手続きに分解** する手法です。

```text
  「注文を処理する」
       │
       ├─ 入力を検証する
       ├─ 在庫を確認する
       ├─ 金額を計算する
       └─ 結果を保存する
```

分割の基準:

- **1 手続き 1 つの仕事**（関心の分離の萌芽）
- **同じ抽象度** のステップを並べる
- 手続き名が **意図を表す**

メソッド設計の詳細は [[010Programming/46_メソッド設計/00_全体像/目次|メソッド設計 目次]] を参照。

---

## 4. データと処理の分離（初期形）

手続き指向では、**データ構造** と **それを操作する手続き** が分かれます。

```c
// データ
struct Order {
  int id;
  float total;
};

// 処理
void calculate_total(struct Order* order) { ... }
void save_order(struct Order* order) { ... }
```

これは整理しやすい反面、**同じデータに触る手続きが増えると変更の影響範囲が読めなくなる** という課題を残しました。これが OOP への動機のひとつです。

---

## 5. 手続き指向が向く場面と限界

### 向く場面

- **ユースケースのオーケストレーション**（処理の流れの制御）
- 単純なデータ変換パイプライン
- スクリプト・バッチ処理
- 学習初期の小規模プログラム

### 限界

- 同じデータに関する処理が **あちこちに散らばる**
- 現実世界の「もの」を **手続きの集合** として表現しにくい
- 大規模化すると **グローバル状態** の管理が困難

```text
  手続き指向は「消えた」のではなく、
  オーケストレーション層などで今も使われている
```

---

## まとめ

- 手続き指向は処理の流れを中心に設計する
- 構造化プログラミングで制御フローを整理
- トップダウンで手続き分割。データと処理は分離
- 向く場面と限界を知り、他パラダイムと組み合わせる
