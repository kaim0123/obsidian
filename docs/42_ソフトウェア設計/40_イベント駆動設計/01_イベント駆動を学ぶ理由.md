# イベント駆動を学ぶ理由

## この章の目的

**イベント駆動** 設計を学ぶ理由と、基本概念を押さえます。  
同期呼び出しの限界と、イベントによる疎結合のメリットを理解します。

> 歴史的背景は [[00_ソフトウェア設計の変遷]] の「イベント駆動」章を参照。

---

## 1. 同期呼び出しの結合と障害伝播

サービス A がサービス B を **同期的に直接呼ぶ** と:

```text
  A ──HTTP 同期──→ B
       │
       └── B が遅い・落ちている → A も止まる（障害伝播）
```

| 問題 | 説明 |
|------|------|
| **結合** | A は B の存在・API を知る必要がある |
| **時間的結合** | 両方が同時に稼働している必要がある |
| **スケール連鎖** | B の負荷が A に直結 |

---

## 2. イベントとは何か（過去形の事実）

**イベント** は **「何かが起きた」という過去形の事実** です。

- `OrderPlaced`（注文が確定した）
- `PaymentCompleted`（支払いが完了した）
- `StockReserved`（在庫が引当された）

```text
  命令: 「在庫を引当てろ」  … 送り手が受け手を指定
  イベント: 「注文が確定した」 … 事実を publish。誰が反応するかは知らない
```

---

## 3. Publisher / Subscriber の考え方

```text
  注文サービス（Publisher）
       │
       │  OrderPlaced を publish
       ▼
  イベントバス / メッセージブローカー
       │
       ├──→ 在庫サービス（Subscriber）
       ├──→ 決済サービス（Subscriber）
       └──→ 通知サービス（Subscriber）
```

- **Publisher**: イベントを発行する側
- **Subscriber**: イベントを受け取り反応する側
- Publisher は **誰が受け取るか知らなくてよい**（疎結合）

---

## 4. 疎結合と非同期処理のメリット

| メリット | 説明 |
|---------|------|
| 障害の局所化 | 在庫サービスが落ちても注文は受け付け可能（キューに溜める） |
| 独立スケール | 分析処理だけスケールアップ |
| 機能追加 | 新 Subscriber を追加するだけ。Publisher は変更不要 |
| ピーク吸収 | キューでバッファリング |

---

## 5. イベント駆動は万能ではない

| デメリット | 説明 |
|-----------|------|
| 結果整合性 | 即時に全体が整合しない。UI 設計が難しくなる |
| デバッグ | 非同期・分散で追跡が困難。トレーシングが必要 |
| 複雑さ | 単純な CRUD にまでイベントを使うと過剰 |
| スキーマ進化 | イベント形式の変更管理が必要 |

**向いているのは、複数の関心が 1 つの出来事に反応する、分散・非同期が価値ある場面** です。

---

## まとめ

- 同期呼び出しは結合と障害伝播を生む
- イベントは過去形の事実。Publisher/Subscriber で疎結合
- 非同期でスケール・障害耐性・拡張性が向上
- 万能ではない。複雑さとのトレードオフを意識
