# イベント駆動の実践判断

## この章の目的

イベント駆動を **いつ使うか・いつ使わないか** の実践判断を学びます。

---

## 1. いつイベントにするか・いつ同期にするか

| 同期が向く | イベントが向く |
|-----------|---------------|
| 即時の応答が必須（残高確認） | 複数の後続処理がある |
| 強い整合性が必要 | 障害耐性・スケールが重要 |
| 単純な CRUD | コンテキストをまたぐ連携 |
| 小規模・モノリス内 | 独立デプロイのサービス群 |

```text
  判断の問い:
  「呼び出し先が落ちたら、呼び出し元も止まっていいか？」
  「後続処理は即時完了である必要があるか？」
```

---

## 2. 過剰な非同期化を避ける

すべてをイベントにすると、シンプルな処理まで複雑になります。

```text
  過剰な例: ユーザー名変更 → 3 イベント → 3 Subscriber → 結果整合性

  適切な例: ユーザー名変更 → 同期で DB 更新 → 完了
```

**YAGNI** の精神で、必要になるまで同期で十分なことが多いです。

---

## 3. デバッグとトレーシングの必要性

非同期・分散では **処理の追跡** が困難です。

- **相関 ID（Correlation ID）** をイベントに載せる
- **OpenTelemetry** 等でトレーシング
- イベントの **ログ・監査** を設計に含める

```text
  OrderPlaced { orderId, correlationId: "abc-123", ... }
       │
       └── 在庫・決済・通知すべて同じ correlationId で追跡
```

---

## 4. UI とユーザー体験への影響

結果整合性は **ユーザーに「まだ反映されていない」** をどう見せるかが課題です。

| 手法 | 例 |
|------|-----|
| 楽観的 UI | 「処理中です」と表示し、後から更新 |
| ポーリング | 状態を定期的に確認 |
| 通知 | 完了したらメール・プッシュ |

「注文完了」と表示するタイミングを **業務と合意** することが重要です。

---

## 5. 小規模システムでの適用範囲

小規模・モノリスでは:

- **ドメインイベント** は集約内の記録・テストに使う（プロセス内）
- **メッセージブローカー** は不要なことが多い
- コンテキストが 1 つなら **同期呼び出しで十分**

```text
  小規模: ドメインイベントの「考え方」だけ取り入れる
  中〜大規模: メッセージング・結果整合性まで検討
```

段階的に導入するのが現実的です。

---

## まとめ

- 同期とイベントは要件に応じて選択
- 過剰な非同期化を避ける
- トレーシングと UI を設計に含める
- 小規模ではドメインイベントの考え方から始める
