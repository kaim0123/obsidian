# ドメインイベントとシステム連携

## この章の目的

**ドメインイベント** の設計と、DDD・イベント駆動の接続を学びます。

> 詳細は [[05_ドメインイベント]] を参照。

---

## 1. ドメインイベントの設計

**ドメインイベント** は、**ドメイン内で起きた意味のある出来事** です。

```javascript
class OrderPlaced {
  constructor(orderId, occurredAt, items) {
    this.orderId = orderId;
    this.occurredAt = occurredAt;
    this.items = items;
  }
}

class Order {
  confirm() {
    // 業務ルールの実行
    this.status = 'confirmed';
    // ドメインイベントを発行
    this.addDomainEvent(new OrderPlaced(this.id, new Date(), this.items));
  }
}
```

設計のポイント:

- **過去形の名前**（OrderPlaced, not PlaceOrder）
- **発生時刻・識別子** を含める
- **Subscriber が必要な情報** だけを持つ

---

## 2. DDD とイベント駆動の接続

```text
  DDD（コンテキスト内）          イベント駆動（コンテキスト間）
  ─────────────────            ─────────────────────────
  Order.confirm()              OrderPlaced を publish
  ドメインルールを実行    →     在庫・決済・通知が subscribe
```

- **集約内**: ドメインイベントで「起きたこと」を記録
- **コンテキスト間**: イベントをメッセージとして配送
- 業務の **出来事** が連携の単位になる

---

## 3. 結果整合性（Eventual Consistency）の受け入れ

**結果整合性** とは、**即時には整合しないが、時間とともに収束する** 状態です。

```text
  注文確定（即時）
       │
       ├── 在庫引当（数秒後）
       ├── 決済（数秒後）
       └── 通知（数秒後）
```

- **強い整合性**（同期）: 全部完了まで待つ。シンプルだが遅い・脆い
- **結果整合性**（非同期）: すぐ応答、後から収束。速いが UI・設計が複雑

トレードオフを **意図的に選ぶ** ことが重要です。

---

## 4. 冪等性と再試行

イベントは **重複配送・失敗再試行** があり得ます。

**冪等性（Idempotency）**: 同じイベントを複数回処理しても結果が同じ

```text
  StockReserved(orderId=123) を 2 回受信
       │
       └── 2 回目は「既に引当済み」として無視（冪等）
```

- イベント ID やビジネスキーで **重複検知**
- Subscriber は **何度実行しても安全** に設計

---

## 5. イベントスキーマの進化

イベント形式は **バージョン管理** が必要です。

| 方針 | 内容 |
|------|------|
| 後方互換 | 新フィールドは optional。古い Consumer も動く |
| バージョン番号 | `OrderPlacedV2` 等 |
| 変換層 | 古い形式を新形式に変換する Adapter |

破壊的変更は **Consumer が次々壊れる** 原因になります。

---

## まとめ

- ドメインイベントは業務の出来事を表現
- DDD の集約内イベントが、コンテキスト間連携の起点
- 結果整合性はトレードオフとして受け入れる
- 冪等性とスキーマ進化を設計に含める
