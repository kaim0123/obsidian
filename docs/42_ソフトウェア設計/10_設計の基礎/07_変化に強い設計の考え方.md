# 変化に強い設計の考え方

## この章の目的

ソフトウェアは **必ず変わります**。変化を前提にした設計の考え方 — なぜ変更が大変になるか、変化の隔離、OCP、YAGNI — を学びます。

---

## 0. なぜソフトウェアの変更は大変なのか

増田亨『現場で役立つシステム設計の原則』（技術評論社, 2017）第1章は、オブジェクト指向設計の目的を次のように置いています。

> **どこに何が書いてあるのかをわかりやすくし、変更の影響を狭い範囲に閉じ込める。**

副作用や予想外の壊れ方が起きるのは、多くの場合「能力不足」ではなく **設計（ソースの置き方）の問題** です。設計がないときの症状（スパゲッティ・変更恐怖）は [[01_ソフトウェア設計を学ぶ理由]] も参照してください。

### 0.1 変更が大変なプログラムの特徴

次の3つが重なると、影響範囲の特定と理解コストが急に上がります。

| 特徴 | 何が起きるか |
|------|-------------|
| **メソッドが長い** | 手順が追いにくく、「どこを直せばよいか」が見えない |
| **クラスが大きい** | 1クラスに関心事が混在し、変更の波及先が増える |
| **引数が多い** | 渡し方・順序・意味の把握が難しく、取り違えや副作用が増える |

引数の設計は [[010Programming/46_メソッド設計/30_シグネチャ設計/02_引数の設計|02_引数の設計]]、メソッドの分割は [[010Programming/46_メソッド設計/20_責務と分割/01_メソッドの分割|01_メソッドの分割]]、クラスの分割は [[010Programming/44_クラス設計・デザインパターン/20_責務の割り当て/01_クラス分割の基本プロセス|01_クラス分割の基本プロセス]] へ進みます。

### 0.2 変更するたびに変更が大変になる

現場では、1回の修正自体は小さいことが多いです（条件を1つ足す、分岐を1つ増やす、など）。それが **積み重なる** と次が起きます。

```text
  小さな修正
      │
      ▼
  行数・分岐・関心事が増える
      │
      ▼
  構造が入れ子になり、意図が読みにくくなる
      │
      ▼
  次の修正の影響範囲がさらに広がる  ← 悪循環
```

だから「今動けばよい」だけでは足りず、**変更のたびに複雑さが増えない書き方**（小さくまとめる・名前と責務を業務語に揃える）が必要になります。具体的な書き方は 46_メソッド設計・44_クラス設計、値オブジェクトは [[04_値オブジェクトと完全コンストラクタ]] を参照してください。

## 1. 変化の予測と変化の隔離

### 変化の予測

すべての変化を当てることはできません。しかし、**変わりやすい箇所** は経験的に分かります。

- 業務ルール（割引条件、承認フロー）
- UI・画面仕様
- 外部連携（API、DB、メール送信）
- 性能要件

### 変化の隔離

**変わりやすい部分を境界で囲み、変わりにくい部分への波及を防ぐ** ことです。

```text
  変わりやすい          境界           変わりにくい
  ──────────          ────           ──────────
  割引ルール    →    Strategy    →    注文の基本構造
  DB の種類     →    Repository  →    注文の業務ロジック
```

予測ではなく **隔離** を重視するのが現実的です。

## 2. 変化の理由（Reason for Change）

**1 つの部品が、複数の理由で変更される** と設計が脆くなります。  
これは単一責任の原則（SRP）の基礎でもあります。

| 悪い例 | 問題 |
|--------|------|
| `Report` クラスが PDF 出力と Excel 出力の両方を担当 | 出力形式の変更理由が 2 つ |
| `UserService` が認証とプロフィール更新を担当 | セキュリティ変更と UI 変更が混在 |

**「この部品は何のために変更されるか？」** を 1 つに絞る意識が有効です。  
詳細は [[010Programming/44_クラス設計・デザインパターン/00_全体像/目次|クラス設計 目次]] の SRP 章を参照。

## 3. 拡張に開き、変更に閉じる（OCP の入門）

**開放閉鎖の原則（Open-Closed Principle, OCP）** とは、

> 拡張に対しては開いており、変更に対しては閉じているべき

という原則です。

```text
  悪い例: 新しい支払い方法のたびに if 文を追加
  if (type === 'credit') { ... }
  else if (type === 'paypal') { ... }  // 毎回既存コードを変更

  良い例: 新しい支払い方法は新クラスを追加（既存コードは変更しない）
  PaymentMethod インターフェース
    ├── CreditCardPayment
    ├── PayPalPayment
    └── NewPayment  ← 追加するだけ
```

OOP での詳細は [[05_SOLIDとの関係]] を参照。

## 4. YAGNI と過剰設計のバランス

**YAGNI（You Aren't Gonna Need It）** = 「今必要ないものは作らない」

| 過剰設計 | 適切な設計 |
|---------|-----------|
| 将来の 10 機能分の抽象化を先に作る | 今必要な分だけ。拡張点は変化が見えたら追加 |
| 使われないインターフェースが大量 | 実際に差し替える箇所だけ抽象化 |

```text
  過剰設計 ←──────── バランス ────────→ 設計なし
  理解困難・無駄なコード              スパゲッティ・変更恐怖
```

**変化を隔離する意識は持ちつつ、必要になるまで作らない** のが実践的です。

---

## 5. 設計原則の優先順位のつけ方

原則同士が衝突することがあります。初心者向けの優先の目安です。

1. **読める・理解できる** — 過度な抽象化より明確さ
2. **関心の分離・高凝集・低結合** — 基本の物差し
3. **変化の隔離** — 変わりやすい箇所を特定して境界を引く
4. **SOLID 等の原則** — 具体化の指針（詳細は [[010Programming/44_クラス設計・デザインパターン/00_全体像/目次|クラス設計 目次]]）
5. **パターンの適用** — 問題が見えてから

```text
  「原則に従った」が目的ではない
  「変更しやすく、理解しやすい」が目的
```

---

## まとめ

- 変更が大変な典型は **長いメソッド・大きなクラス・多い引数**。小さな修正の積み重ねで悪循環になる
- 設計の第一歩は **どこに何があるかをわかりやすくし、影響を狭く閉じ込める** こと
- 変化は避けられない。予測より **隔離** が現実的
- 変化の理由は 1 つに絞る意識が有効
- OCP は拡張で対応し、既存コードの変更を減らす
- YAGNI で過剰設計を避け、バランスを取る
