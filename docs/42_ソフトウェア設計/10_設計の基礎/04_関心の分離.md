# 関心の分離（Separation of Concerns）

## この章の目的

良い設計の第一歩は **関心の分離** です。異なる目的の処理を混ぜない理由と、実践の仕方を学びます。

---

## 1. 関心の分離とは何か

**関心の分離（Separation of Concerns, SoC）** とは、**目的の異なる処理を別の場所に分ける** 設計原則です。

Edsger Dijkstra が 1974 年に提唱した考え方で、ソフトウェア設計の根幹のひとつです。

```text
  混在（悪い例）              分離（良い例）
  ─────────────              ─────────────
  1 つの関数に                UI 層
  ・画面表示                  業務層
  ・計算                      永続化層
  ・DB 保存
```

「関心」とは **ソフトウェアが扱う関心事** のことです。表示・計算・保存は、それぞれ別の関心です。

---

## 2. 1つの場所に全部書く問題

すべてを 1 か所に書くと、次の問題が起きます。

| 問題 | 具体例 |
|------|--------|
| 読みにくい | 1000 行の関数で何をしているか把握できない |
| 直しにくい | UI を変えると DB 処理まで壊れる |
| 試しにくい | 業務ロジックだけテストできない |
| 再利用できない | 同じ計算を別画面で使えない |

```javascript
// 悪い例: すべてが混在
function handleSubmit() {
  const name = document.getElementById('name').value;  // UI
  if (!name) { alert('名前を入力'); return; }         // 検証
  const tax = calculateTax(name);                     // 業務
  db.save({ name, tax });                             // 永続化
  sendEmail(name);                                    // 通知
}
```

## 3. レイヤー・モジュール・クラスへの分離

関心の分離は、設計の階層ごとに適用できます。

| レベル | 分離の単位 | 例 |
|--------|-----------|-----|
| レイヤー | システムの層 | プレゼンテーション / ドメイン / インフラ |
| モジュール | パッケージ・ディレクトリ | `order/`, `billing/`, `notification/` |
| クラス | 型 | `Order`, `OrderRepository`, `OrderController` |
| 関数 | 処理の塊 | `validate()`, `calculateTotal()`, `save()` |

```text
  Controller（UI の関心）
       │
       ▼
  OrderService（業務の関心）
       │
       ├──→ OrderRepository（永続化の関心）
       └──→ EmailService（通知の関心）
```

詳細なモジュール分割は [[010Programming/43_モジュール設計/00_全体像/目次|モジュール設計 目次]]、クラス分割は [[010Programming/44_クラス設計・デザインパターン/00_全体像/目次|クラス設計 目次]] で扱います。

## 4. 分けすぎ・分け足りないの見分け方

### 分け足りないサイン

- 1 つのファイル・クラスが **複数の理由で変更** される
- 「この処理、どこに書けばいい？」が頻繁に起きる
- テストでモックが大量に必要になる

### 分けすぎのサイン

- たどるファイル数が多すぎて **全体像が掴めない**
- 1 行の変更に **10 ファイル** を触る
- 抽象化のためだけのクラスが増え、意図が読めない

**目安**: 1 つの単位（クラス・モジュール）は **1 つの関心** に集中。ただし、小さすぎる分割は避ける（[[07_変化に強い設計の考え方]] の YAGNI も参照）。

---

## 5. 関心の分離のチェックリスト

設計レビュー時に使えるチェックリストです。

- [ ] この部品は **1 つの関心** に集中しているか
- [ ] UI のコードに **DB や HTTP の詳細** が混ざっていないか
- [ ] 業務ルールが **フレームワークや DB に引っ張られていない** か
- [ ] 横断的関心事（ログ・認証）が **各所にコピペ** されていないか
- [ ] 分離の境界は **チームで説明できる** か

---

## まとめ

- 関心の分離は、目的の異なる処理を別の場所に分ける原則
- 混在は読みにくさ・変更困難・テスト困難を招く
- レイヤー・モジュール・クラス・関数の各レベルで適用できる
- 分けすぎ・分け足りないのバランスが重要
