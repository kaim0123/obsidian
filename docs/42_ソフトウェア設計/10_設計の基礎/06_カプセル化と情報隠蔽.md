# カプセル化と情報隠蔽

## この章の目的

**カプセル化** と **情報隠蔽** は、変更に強い設計の核心です。  
OOP だけでなく、モジュール設計全体に通じる原則として理解します。

---

## 1. カプセル化の目的

**カプセル化（Encapsulation）** とは、データと処理をまとめ、**外から勝手にいじれないようにする** ことです。

目的は次の 3 つです。

1. **不正な操作を防ぐ** — 外部から内部状態を直接壊されない
2. **変更の影響を閉じ込める** — 内部実装を変えても外側に波及しにくい
3. **意図を明確にする** — 公開された操作だけが「できること」

薬のカプセルのように、**中身は見えないが、決められた方法で使える** イメージです。

---

## 2. 公開すべきもの・隠すべきもの

| 公開する | 隠す |
|---------|------|
| 外部が使うべき操作（メソッド） | 内部のデータ構造 |
| 契約としてのインターフェース | 実装の詳細 |
| 不変条件を守るための入口 | 中間計算の過程 |

```javascript
// 良い例: 公開面が明確
class BankAccount {
  #balance = 0;  // 隠す

  deposit(amount) {  // 公開する
    if (amount <= 0) throw new Error('正の金額のみ');
    this.#balance += amount;
  }

  getBalance() { return this.#balance; }
}
```

**すべてを public にする必要はありません。** 本当に外から使うものだけを公開します。

---

## 3. 変更に強くするための隠蔽

内部表現を変えても、公開インターフェースが同じなら **利用者は影響を受けません**。

```text
  変更前: 内部は配列で管理
  変更後: 内部は Map で管理
         ↓
  公開メソッド add() / remove() が同じなら
  呼び出し側は変更不要
```

これが **情報隠蔽（Information Hiding）** の力です。David Parnas が 1972 年に提唱した考え方で、**設計判断ごとに隠す** ことを推奨しました。

---

## 4. 漏れ出す詳細（Leaky Abstraction）の危険性

**漏れ出す抽象化（Leaky Abstraction）** とは、隠すはずの詳細が外に漏れる状態です。

| 漏れの例 | 問題 |
|---------|------|
| DB のテーブル構造が API に露出 | DB 変更で API も変更が必要 |
| 同期/非同期の詳細が呼び出し側に漏れる | 実装変更で全体が壊れる |
| エラーコードが DB 固有 | 別 DB に移行できない |

```text
  良い抽象化: 利用者は「保存できる」だけ知る
  漏れる抽象化: 利用者が SQL やテーブル名を知っている
```

抽象化は **「何を隠すか」** を意識して設計します。

---

## 5. カプセル化は設計全体の原則である

カプセル化は OOP の `private` だけではありません。

| レベル | カプセル化の例 |
|--------|---------------|
| クラス | private フィールド、公開メソッド |
| モジュール | パッケージの公開 API、内部実装の非公開 |
| サービス | 公開 API のみ、内部 DB スキーマは隠す |
| レイヤー | ドメイン層はインフラの詳細を知らない |

```text
  カプセル化 = 「内側」と「外側」の境界を意識する設計の姿勢
```

OOP での詳細は [[02_クラスとオブジェクト]] を参照。

---

## まとめ

- カプセル化は不正操作の防止・変更の局所化・意図の明確化
- 公開すべきものと隠すべきものを意識する
- 情報隠蔽により内部実装の変更が外に波及しにくくなる
- 漏れ出す抽象化に注意。カプセル化は全設計階層に適用できる
