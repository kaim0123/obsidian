# 設計の段階的な深化

## この章の目的

設計は **一度で完成しない** ことを前提に、段階的に深めていく進め方を学びます。

---

## 1. 最初から完璧な設計は不要

- 要件は開発中に変わる
- 理解はコードを書いて初めて深まる
- 過剰な先行設計は **無駄と誤り** になりやすい

```text
  十分に良い設計 → 実装 → 学び → 設計を更新 → 繰り返し
```

**進化する設計** を受け入れることが、長期的な成功につながります。

ドメインモデルも同様で、部分を作りながら全体と往復し、業務を学びながら成長させます（[[03_ドメインモデルの作り方]]・[[02_ユビキタス言語]]）。

---

## 2. 概要設計 → 詳細設計の流れ

| 段階 | 内容 | 粒度 |
|------|------|------|
| **概要設計** | モジュール・主要な境界・パラダイムの選択 | 大まか |
| **詳細設計** | クラス・インターフェース・主要な振る舞い | 具体 |

```text
  概要: 「注文」「在庫」「通知」に分ける
  詳細: Order 集約に confirm() を置く、Repository インターフェースを定義
```

一度に詳細まで行かず、**実装が進むにつれて詳細化** します。

---

## 3. リファクタリングと設計の更新

**リファクタリング** は、振る舞いを変えずに **構造を改善** することです。

| きっかけ | 例 |
|---------|-----|
| 同じ変更で複数箇所を触る | Extract Class で責務を分離 |
| テストが書きにくい | 依存を注入可能にする |
| 名前と実態がズレた | Rename、Move Method |

設計は **リファクタリングの蓄積** で育ちます。詳細は [[010Programming/46_メソッド設計/00_全体像/目次|メソッド設計 目次]] のリファクタリング技法を参照。

---

## 4. 技術的負債との向き合い方

**技術的負債** とは、短期的な妥協が将来のコストになる状態です。

```text
  意図的な負債: 「リリース優先で境界を後回し。3 ヶ月後に分割」
  無意識の負債: 「気づかないうちに神クラス化」
```

- **意図的なら** 期限と理由を記録（ADR）
- **可視化** して優先度をつける
- **絶えず小さく返済** する

---

## 5. 設計判断の記録（ADR 入門）

**ADR（Architecture Decision Record）** は、重要な設計判断を短く記録する形式です。

```markdown
# ADR-001: 注文と在庫を別モジュールに分ける

## 状況
注文確定時に在庫を更新する必要がある

## 決定
Order と Inventory を別モジュールにし、OrderPlaced イベントで連携

## 理由
在庫ロジックの変更が注文に波及しないようにする

## 結果
（後から追記）
```

「なぜそうしたか」が残ると、後任者・未来の自分が助かります。

---

## まとめ

- 完璧な先行設計は不要。進化を前提にする
- 概要 → 詳細の段階的深化
- リファクタリングで設計を更新
- 技術的負債を可視化し、ADR で判断を残す

Web API でも「動かしながら契約を育てる」同じ考え方が使えます（[[04_発展性のあるAPI開発]]・[[03_APIの進化と運用]]）。
