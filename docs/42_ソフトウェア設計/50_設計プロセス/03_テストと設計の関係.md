# テストと設計の関係

## この章の目的

**テストしやすい設計** と、テストから設計を改善する考え方を学びます。

---

## 1. テストしやすい設計とは何か

テストしやすい設計とは、**部品を独立して検証できる** 構造です。

| 性質 | 説明 |
|------|------|
| 依存の注入 | 外部（DB・API）を差し替え可能 |
| 副作用の分離 | 純粋な計算部分を切り出せる |
| 小さな単位 | 1 テストが 1 つの振る舞いを検証 |
| 明確な境界 | 何をモックするかがはっきりしている |

```text
  テストしやすい = 設計が分かれているサイン
  テストしにくい = 設計の問題のサイン
```

---

## 2. 設計がテストを難しくする典型例

| 典型例 | 問題 |
|--------|------|
| 静的メソッドで DB 直叩き | 差し替え不可 |
| 巨大な God クラス | 何をテストしているか不明 |
| コンストラクタで外部接続 | テストのたびに DB が必要 |
| グローバル状態 | テスト順序に依存 |
| ランダム・時刻に依存 | 結果が再現しない |

これらは **設計の改善ポイント** です。

---

## 3. テストから見えた設計の問題

テストを書こうとして **「無理」** と感じたら、設計を見直すチャンスです。

```text
  「OrderService のテストに DB・メール・決済全部必要」
       → 依存が多すぎ。インターフェースで分離を

  「confirm() のテストで 10 個モック」
       → 責務が多すぎ。分割を
```

**テストは設計のフィードバック装置** として使えます。

---

## 4. 副作用の分離とテスト容易性

```javascript
// テストしにくい: 計算と I/O が混在
function processOrder(order) {
  const total = order.items.reduce(...);
  db.save({ ...order, total });
  sendEmail(order.email);
}

// テストしやすい: 計算を純粋関数に
function calculateTotal(items) {
  return items.reduce((sum, i) => sum + i.price, 0);
}
// I/O は別の層。calculateTotal はモック不要でテスト可能
```

関数型の考え方（[[01_関数型指向の考え方]]）がテスト容易性に直結します。

---

## 5. 設計レビューとテスト観点の統合

レビュー時に問いかけること:

- [ ] この部品は **単体テスト可能** か
- [ ] 外部依存は **注入・抽象化** されているか
- [ ] テストで **何を検証しているか** が明確か
- [ ] テストが書きにくい箇所は **設計改善の候補** か

設計レビューとテスト戦略を **別々にしない** と効果的です。

---

## まとめ

- テストしやすさは良い設計の指標
- テスト困難は設計問題のシグナル
- 副作用を分離し、依存を注入可能にする
- レビューにテスト観点を統合する
