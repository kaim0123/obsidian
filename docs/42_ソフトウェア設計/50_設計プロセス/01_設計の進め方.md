# 設計の進め方

## この章の目的

要件から設計案を作る **実践的なプロセス** を学びます。

---

## 1. 要件から設計へ — 何を作るかを整理する

設計の出発点は **「何を作るか」** の理解です。

| 整理するもの | 例 |
|-------------|-----|
| 機能要件 | ユーザーは注文できる、管理者は在庫を更新できる |
| 非機能要件 | 100 同時接続、99.9% 可用性 |
| 制約 | Java で書く、既存 DB を使う、3 ヶ月でリリース |
| 用語 | 注文・明細・出荷の定義 |

```text
  要件が曖昧なまま設計 → 後から大幅な作り直し
  用語を先に揃える   → DDD のユビキタス言語の出発点
```

---

## 2. ユースケースと振る舞いの洗い出し

**ユースケース** は、ユーザー（または外部システム）が **システムに何をさせるか** です。

```text
  注文を確定する
    1. カートの内容を検証する
    2. 在庫を確認する
    3. 金額を計算する
    4. 注文を保存する
    5. 確認メールを送る
```

- **動詞** が振る舞いの候補
- **誰が** 何をするか（アクター）を明確に
- 正常系と異常系の両方を考える

---

## 3. 名詞と動詞から構造を見つける

オブジェクト指向設計の古典的な手法です。

| 抽出 | 設計への対応 |
|------|-------------|
| **名詞** | クラス・エンティティの候補（Order, Item, Customer） |
| **動詞** | メソッド・ユースケースの候補（確定する、計算する） |

```text
  「顧客が注文を確定する」
    名詞: 顧客、注文  → Customer, Order
    動詞: 確定する     → order.confirm()
```

名詞をそのまま全部クラスにする必要はありません。**責務と関心** で取捨選択します（[[010Programming/44_クラス設計・デザインパターン/00_全体像/目次|クラス設計 目次]]）。

---

## 4. スケッチと図の使い方（入門）

完璧な UML より **手書きスケッチ** で十分なことが多いです。

| 図 | 用途 |
|----|------|
| 箱と矢印 | モジュール・サービスの関係 |
| クラス図（簡易） | 主要な型と関係 |
| シーケンス図（簡易） | 処理の流れ |

```text
  [UI] → [OrderService] → [OrderRepository] → [DB]
```

図は **議論の道具**。コードと一緒に更新するか、使い捨てでもよいです。

---

## 5. 最初の設計案を作るワークショップ

60〜90 分でできる演習の流れです。

1. **要件を 3 行で書く**
2. **ユースケースを 1 つ選ぶ**
3. **名詞・動詞を洗い出す**
4. **モジュール候補を 3〜5 個に分ける**
5. **主要なクラスを 5 個以内で決める**
6. **依存の方向を矢印で描く**
7. **「ここが変わりそう」を 1 箇所マークする**

完璧を目指さず、**議論できるたたき台** を作ることが目的です。

---

## まとめ

- 要件・用語を先に整理する
- ユースケースと名詞・動詞から構造の候補を出す
- 簡易な図で関係を可視化
- ワークショップでたたき台を素早く作る
