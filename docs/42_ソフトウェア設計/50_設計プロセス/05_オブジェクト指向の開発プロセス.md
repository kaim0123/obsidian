## 1. 開発の進め方はオブジェクト指向で変わったのか

### 1.1 開発の基本は V 字モデル

古典的な流れは、要件 → 設計 → 実装 → テスト（単体〜結合〜総合）という **V 字**（ウォーターフォール系）です。用語と各工程のテスト位置は [[15_開発のライフサイクル]]。

### 1.2 短期間で開発し、修正と拡張を繰り返すことが重要になった

市場と業務の変化が速くなり、一度きりの大型リリースより、**短いサイクルで出し、直す**ことが価値になります（アジャイル／反復）。段階的深化は [[02_設計の段階的な深化]]。

### 1.3 オブジェクト指向の開発はうまくいっているのか／変更がやっかいなソフト

UML・クラス設計・フレームワークを導入しても、次が起きると「OO なのに変更がつらい」ソフトになります。

| 起きやすいこと | 結果 |
|----------------|------|
| 画面・テーブル起点のクラス分け | 関心事が散らばり、変更が一箇所に収まらない |
| データクラス＋巨大サービス | 貧血モデル（[[05_Tell_Dont_Askと貧血モデルの回避]]） |
| ドキュメントとコードの乖離 | 仕様がどこにあるか分からない |

**ウォーターフォールでも反復でも**、業務ロジックの置き場所が曖昧なら、変更コストは高くなります。パラダイム名より、**何を中心に設計・実装するか**が問題です（[[07_変化に強い設計の考え方]]・[[02_よくある設計の失敗]]）。

## 2. ドメインモデルを中心にしたソフトウェア開発

焦点を **業務ロジック（判断・加工・計算）** に当て、それをドメインオブジェクトとして育てながら機能を組み立てます。

```text
  業務の言葉でモデルを書く
       │
       ├─ 小さく実装し、動かす
       ├─ 食い違いからモデルを直す（分析と設計は一体）
       └─ 画面・DB・API はモデルに合わせて collocate／変換
```

| 中心にする | 引きずられない |
|------------|----------------|
| ユビキタス言語・関心事のかたまり | 画面項目 1:1、テーブル 1:1 |
| ドメインの不変条件と導出 | 手順書だけの巨大サービス |

考え方は [[03_ドメインモデルの考え方で設計する]]、作り方は [[03_ドメインモデルの作り方]]、組み立ては [[07_アプリケーション機能を組み立てる]]。リファクタでモデルを育てるのは [[04_リファクタリングの考え方]]。

## 3. ソースコードを第一級のドキュメントとして活用する

### 3.1 多くのドキュメントは不要になる

コードとテストが最新の仕様を表せているなら、同じ内容の詳細仕様書を二重に維持するコストは下げられます。ただし **「全部捨てる」ではない** です。

### 3.2 重要になる活動

| 活動 | なぜ重要か |
|------|------------|
| **ペア／レビューでの対話** | モデルの意図を共有する |
| **リファクタリング** | コードを読みやすい「文書」に保つ |
| **自動テスト** | 振る舞いの実行可能な仕様 |
| **ユビキタス言語の手入れ** | 名前がドキュメントになる |

### 3.3 更新すべきドキュメント／全体を俯瞰する文書

コードに置きにくいものは残し、更新責任を明確にします。

| 残しやすいもの | 例 |
|----------------|-----|
| **全体俯瞰** | コンテキストマップ、モジュール地図、用語集 |
| **判断の理由** | ADR（[[02_設計の段階的な深化]]） |
| **契約の外向け** | OpenAPI、運用手順、法務・監査向け文書 |
| **長寿命の制約** | 非機能の目標値、セキュリティ方針 |

成果物の役割分担の導入は [[02_設計の階層と全体像]]。

### 3.4 技術方式もソースコードで表現する

ディレクトリ構成、依存の向き、インターフェース、設定の型付けは、アーキテクチャ図の代替／補完になります。「図だけ正しくコードが違う」状態を避ける。

### 3.5 非機能要件はテストコードで表現する

応答時間・可用性・セキュリティなどの目標は、文書の一文だけでなく、**性能テスト・契約テスト・負荷試験・チェックリスト付きの自動検証** として残すと検証可能になります（[[03_テストと設計の関係]]・[[03_非機能テスト概要]]）。

## まとめ

- OO や V 字／反復のラベルだけでは変更容易にならない。業務ロジックの中心が要る  
- ドメインモデルを軸に、分析と設計を一体で反復する  
- コードとテストを第一級にし、俯瞰・理由・外向け契約は intentionally 残す  
- 非機能もテスト可能な形で表現する
