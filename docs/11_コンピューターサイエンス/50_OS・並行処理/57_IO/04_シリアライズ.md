# シリアライズ

## シリアライズとは
メモリ上のオブジェクトを**ファイル保存・通信可能な形式に変換**すること。
逆の操作を**デシリアライズ（復元）**といいます。

```
[メモリ上のオブジェクト]
    ↓ シリアライズ
[バイト列 / 文字列]
    ↓ 保存・送信
[バイト列 / 文字列]
    ↓ デシリアライズ
[メモリ上のオブジェクト]
```

## 用途
- **データ保存**: ファイル、DB
- **通信**: APIリクエスト/レスポンス、メッセージキュー
- **キャッシュ**: Redisに格納
- **プロセス間通信**: 共有メモリ、メッセージ
- **言語をまたいだデータ連携**

## 代表的なフォーマット

### 1. JSON
人が読める・JS互換・最も普及。
```json
{
  "name": "Alice",
  "age": 30,
  "hobbies": ["read", "walk"]
}
```
- 長所: 人間可読、全言語で対応、シンプル
- 短所: バイナリ非対応、冗長、型情報弱い

### 2. XML
タグベース。古くからあり、厳密なスキーマを持てる。
```xml
<user>
  <name>Alice</name>
  <age>30</age>
</user>
```
- 長所: スキーマ（XSD）、属性と要素の区別
- 短所: 冗長、パースが重い

### 3. YAML
インデントベース、設定ファイル向け。
```yaml
name: Alice
age: 30
hobbies:
  - read
  - walk
```
- 長所: 人間可読、簡潔
- 短所: インデント地獄、セキュリティリスク（`!!python/object`等）

### 4. TOML
設定ファイル向け。最近の言語系ツールでよく使われる（Rust Cargo、Pythonのpyproject）。
```toml
[user]
name = "Alice"
age = 30
```

### 5. CSV
表形式。スプレッドシートとの互換性が高い。
```
name,age
Alice,30
Bob,25
```
- 長所: 単純、普及
- 短所: 型なし、ネスト不可、カンマ/改行の扱い

### 6. Protocol Buffers（protobuf）
Googleのバイナリ形式。スキーマ定義あり。
```protobuf
message User {
  string name = 1;
  int32 age = 2;
}
```
- 長所: コンパクト、高速、後方互換
- 短所: 人間可読ではない、スキーマ必要

### 7. MessagePack
JSONと同じデータモデルのバイナリ版。
- 長所: JSONの半分程度のサイズ、速い
- 短所: 人間可読ではない

### 8. Apache Avro / Thrift
protobuf的な分散処理向けフォーマット。Hadoop、Kafkaと相性が良い。

### 9. BSON
MongoDBが内部で使うバイナリJSON。

### 10. 言語固有バイナリ
Pythonの`pickle`、Javaの`Serializable`、Rubyの`Marshal`など。
- 長所: その言語の型を完全再現
- 短所: 他言語と互換性なし、**セキュリティリスク**（任意コード実行）

## 各言語でのJSON処理

### JavaScript
```javascript
const s = JSON.stringify(obj);
const obj = JSON.parse(s);
```

### Python
```python
import json
s = json.dumps(obj)
obj = json.loads(s)
```

### Java
```java
ObjectMapper mapper = new ObjectMapper();
String s = mapper.writeValueAsString(obj);
User u   = mapper.readValue(s, User.class);
```

### Rust (serde)
```rust
let s: String = serde_json::to_string(&obj)?;
let obj: User  = serde_json::from_str(&s)?;
```

## スキーマありフォーマットの利点

### ① 明示的な契約
システム間で型を共有できる。
```protobuf
message Order {
  string id       = 1;
  repeated Item items = 2;
  double total    = 3;
}
```

### ② 後方互換性の管理
フィールド追加・廃止のルールが明確。

### ③ コード生成
スキーマから各言語のクラスを自動生成。
```bash
protoc --java_out=. user.proto
```

### ④ バリデーション
不正なデータを早期検出。

## フォーマット選択の基準

| 用途 | おすすめ |
|---|---|
| Web API (汎用) | JSON |
| 設定ファイル | YAML / TOML |
| マイクロサービス間 | protobuf + gRPC |
| 分析基盤 | Avro / Parquet |
| IoT・低帯域 | MessagePack / protobuf |
| 人間編集 | YAML / TOML |
| 表データ | CSV / Parquet |

## シリアライズのセキュリティ

### 信頼できないデータを直接デシリアライズしない
特に**言語固有のバイナリ形式**は危険。
```python
# ❌ 攻撃者が任意コードを実行できる
obj = pickle.loads(user_input)
```

```java
// ❌ Java Serializableも同様に危険
ObjectInputStream in = new ObjectInputStream(...);
Object o = in.readObject();
```

### 安全な選択肢
- JSON/YAML/TOML/protobuf（データ構造のみ扱う）
- スキーマ検証（JSON Schema、protobuf定義）
- サイズ上限を設ける

## バージョニング戦略

### フィールド追加
- 既存読み取り側が**無視できる**設計に（JSON、protobuf）

### フィールド削除
- いきなり消さず、`deprecated` として残す期間を設ける

### 型変更
- 別名のフィールドを追加して段階的移行

### protobufの例
```protobuf
message User {
  string name = 1;
  int32  age  = 2;
  string email = 3;   // 追加、古い読み手は無視
  // reserved 4;      削除した番号を予約
}
```

## パフォーマンス比較（大雑把な目安）

| 形式 | サイズ | 速度 | 備考 |
|---|---|---|---|
| JSON | 大 | 中 | 標準 |
| XML | 大 | 遅 | 冗長 |
| YAML | 大 | 遅 | パース複雑 |
| MessagePack | 中 | 速 | JSON互換 |
| protobuf | 小 | 速 | スキーマ必須 |
| CSV | 小 | 速 | 表データ限定 |
| Parquet | 小 | 速 | 列指向、分析用 |

## JSONでよくあるハマり

### 1. BigInt / long
64bit整数はJSで精度落ち。文字列で扱うのが安全。
```javascript
JSON.parse('{"id": 9007199254740993}');  // 精度落ちる
```

### 2. 日時の型
JSONに日時型はない。ISO 8601文字列を慣習的に使用。

### 3. 循環参照
```javascript
const a = {};
a.self = a;
JSON.stringify(a);   // エラー
```

### 4. プロトタイプ
JSONはプロパティのみ、メソッドや `__proto__` は保存されない。

### 5. NaN / Infinity
JSONでは `null` にされる / エラーになる。

## バイナリ形式の選び方

### protobuf
- サービス間RPC（gRPC）
- IDLあり、多言語SDK

### Avro
- Hadoop/Kafka生態系
- スキーマをデータと一緒に運べる

### FlatBuffers / Cap'n Proto
- デシリアライズほぼゼロコスト
- ゲーム・リアルタイム処理

## まとめ
- シリアライズは**メモリ上の構造を保存・通信可能な形に変換**する操作
- 汎用API: **JSON**、分散/高性能: **protobuf**、設定: **YAML/TOML**
- 言語固有バイナリは**セキュリティリスク**、信頼できない入力で使わない
- スキーマありフォーマットは**バージョニング・コード生成**で強力
- 用途に応じてフォーマットを選び、**後方互換**を意識して設計する
