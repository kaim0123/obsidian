# ブロッキングとノンブロッキング

## ブロッキングとは
呼び出した処理が**完了するまで呼び出し元が停止（ブロック）**する動作のこと。
```
呼び出し元: read() を呼ぶ
   ↓ データが届くまで待機（進まない）
OSカーネル: データが届く
   ↓
呼び出し元: 結果を受け取り、次へ
```

## ノンブロッキングとは
呼び出した処理が**即座に返る**動作のこと。完了していなければ「まだ」「準備できていない」といった状態を返す。
```
呼び出し元: read() を呼ぶ
   ↓
OSカーネル: 「まだデータなし」を即返す
   ↓
呼び出し元: 別の処理を進め、後でまた試す
```

## 同期/非同期との関係
似た言葉ですが軸が違います。

| 軸 | 意味 |
|---|---|
| 同期 / 非同期 | 呼び出し元が**結果を待つかどうか** |
| ブロッキング / ノンブロッキング | 呼び出しが**即返るかどうか** |

4象限で整理すると:

| | ブロッキング | ノンブロッキング |
|---|---|---|
| 同期 | 一般的な `read()` | ポーリング読み |
| 非同期 | 稀（概念のみ） | コールバック / Promise / AIO |

実用で重要な組み合わせは
- 同期ブロッキング（伝統的）
- 非同期ノンブロッキング（モダンな高並行システム）

## 同期ブロッキング
```python
data = sock.recv(1024)    # データが来るまで止まる
process(data)
```
シンプルだが**1接続=1スレッド**で、多数接続時にスレッドが大量に必要。

## 同期ノンブロッキング（ポーリング）
```c
fcntl(fd, F_SETFL, O_NONBLOCK);
while (1) {
    int n = read(fd, buf, BUF_SIZE);
    if (n >= 0) break;
    if (errno != EAGAIN) handle_error();
    // CPUを無駄に使い続ける
}
```
データが来るまで**ループで聞き続ける**。CPU食い。ほぼ使われない。

## 非同期ノンブロッキング（I/O多重化）
多数のFDをまとめて監視し、準備できたものだけ処理。

### selectとpoll
```c
fd_set readfds;
FD_SET(sock, &readfds);
select(max + 1, &readfds, NULL, NULL, &timeout);
```

### epoll（Linux）
大量FDを効率的に扱える。ポーリングでなくイベント通知型。
```c
int epfd = epoll_create1(0);
epoll_ctl(epfd, EPOLL_CTL_ADD, sock, &ev);
epoll_wait(epfd, events, 10, -1);
```

### kqueue（macOS/BSD）、IOCP（Windows）、io_uring（Linux 5.x〜）
同様のイベント駆動I/Oの仕組み。

## 高水準APIから見ると

### ブロッキング系API
```python
# Python標準（ブロッキング）
data = open("file.txt").read()

# requests（ブロッキング）
response = requests.get(url)
```

### ノンブロッキング系API
```python
# asyncio（非同期ノンブロッキング）
async with aiohttp.ClientSession() as s:
    async with s.get(url) as r:
        data = await r.text()
```

```javascript
// Node.js（非同期ノンブロッキング）
const data = await fs.promises.readFile("file.txt");
```

## Node.jsのモデル
単一スレッドのJSエンジン + 非同期ノンブロッキングI/O。
- JSコードはシングルスレッド
- I/Oはネイティブ層でノンブロッキング実行
- 完了時にコールバック/Promiseが解決

```javascript
console.log("1");
fs.readFile("a.txt", () => console.log("3"));
console.log("2");
// 出力: 1 → 2 → 3
```

## スレッドプールによる「擬似ノンブロッキング」
ブロッキングAPIを別スレッドで実行し、メインスレッドは待たない方式。
```java
// Javaのexecutor
executor.submit(() -> {
    byte[] data = Files.readAllBytes(path);   // ブロッキング、裏で実行
    callback.accept(data);
});
```
Node.jsのファイルI/Oも内部的にはこの仕組み（libuvのスレッドプール）。

## CPU使用のイメージ

### 同期ブロッキング
```
Thread: [───── ブロック ─────][処理][───ブロック───][処理]
           I/O待ち（CPU空き）        I/O待ち
```

### 非同期ノンブロッキング
```
Thread: [処理A][処理B][処理A完了][処理C][処理B完了]...
          ↑ 1スレッドでもフル回転
```

## ユースケース別の選択

### ネットワークサーバー
- 低〜中並行 → ブロッキング + スレッドプール（Java）
- 高並行 → 非同期ノンブロッキング（Node.js, nginx, Go）

### バッチ処理
- 同期ブロッキングで十分

### GUIアプリ
- UIスレッドをブロックしない → 非同期 or 別スレッド

### 組み込み・低レイヤ
- ノンブロッキングI/O + イベントループ（省リソース）

## ブロッキングAPIの罠

### 1つのブロッキング呼び出しで全体停止
Node.jsや非同期Pythonで**同期API**を呼ぶと、イベントループが止まる。
```javascript
// NG: 同期API（イベントループ停止）
const data = fs.readFileSync("big.txt");

// OK: 非同期API
const data = await fs.promises.readFile("big.txt");
```

## C10K問題
「1万接続を1台のサーバーで同時処理する」難題。解法として**非同期ノンブロッキングI/O**が広まった（epoll, kqueue）。現代は C10M（1千万接続）へ向かっている。

## タイムアウトとノンブロッキング
ノンブロッキング = 即座に返る、なのでタイムアウトは別途設定する必要がある。
```javascript
await fetch(url, { signal: AbortSignal.timeout(5000) });
```

## デバッグの着眼点

### 長時間止まる
- どこかで同期ブロッキング呼び出しが混ざっていないか
- DB接続、ファイル読み込みが怪しい

### CPUが張り付く
- ビジーループでポーリングしていないか
- 同期計算が重くないか

### コネクションが滞留
- スレッドプールが枯渇していないか
- バックプレッシャーが機能しているか

## まとめ
- **ブロッキング = 完了まで待つ**、**ノンブロッキング = 即座に返る**
- 同期/非同期と直交する概念
- 高並行システムは**非同期ノンブロッキング（epoll等）**がベース
- Node.js/nginxなどのモデルを支える基本原理
- 同期APIと非同期APIを混ぜないのが鉄則
