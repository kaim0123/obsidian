# ストリーム処理

## ストリームとは
データを**連続した流れ**として扱う抽象化です。全部をメモリに読み込んでから処理するのではなく、**少しずつ流しながら処理**します。

```
[ソース] → [変換1] → [変換2] → [出力]
       チャンク（小さな塊）が順に流れる
```

## なぜストリーム処理か
- **大容量データ**（数GB〜TBのファイル、動画）をメモリに載せずに扱える
- **低レイテンシ**: 最初のバイトから処理開始
- **合成しやすい**: パイプで繋いで処理を組み立てられる
- **効率**: ネットワーク受信と処理を並行できる

## 古典的な例: Unixパイプ
```bash
cat huge.log | grep error | awk '{print $1}' | sort | uniq -c
```
各段がストリームを受け取り、変換して次へ流す。**メモリはほぼ食わない**。

## ストリームの種類

### 読み込みストリーム（Readable）
データを「吐き出す」側。ファイル、ネットワーク、標準入力など。

### 書き込みストリーム（Writable）
データを「受け取る」側。ファイル、ネットワーク、標準出力など。

### 双方向ストリーム（Duplex）
読み書き両方。TCPソケットなど。

### 変換ストリーム（Transform）
読み取ったデータを変換して流す。圧縮、暗号化、エンコード変換など。

## Node.jsの例
```javascript
const fs = require("fs");
const zlib = require("zlib");

fs.createReadStream("big.txt")
  .pipe(zlib.createGzip())
  .pipe(fs.createWriteStream("big.txt.gz"));
```
Readable → Transform → Writable を `pipe` で連結。

## Pythonの例
```python
with open("big.txt") as f:
    for line in f:              # 1行ずつ流れてくる
        if "error" in line:
            print(line)
```
イテレータ自体が軽量なストリーム的性質を持つ。

## Javaの例
```java
try (Stream<String> lines = Files.lines(Path.of("big.txt"))) {
    long errors = lines
        .filter(l -> l.contains("ERROR"))
        .count();
}
```
Stream API は遅延評価で、ストリーム的に処理できる。

## 押し出し vs 引き出し（Push / Pull）

### Pull（消費者駆動）
受け取る側が要求する時だけデータを取りに行く。
- 例: Iterator、ReadableStream（WHATWG）

### Push（生産者駆動）
ソースが自分のペースでデータを送り出す。
- 例: EventEmitter、Observable（RxJS）

モダンAPIは**Pullベース + バックプレッシャー**が主流。

## バックプレッシャー
消費者が追いつかない時に、**生産者のペースを落とす**仕組み。

```
生産者 ──→ [バッファ] ──→ 消費者(遅い)
                ↑
           溜まりすぎたら止める
```

### Node.jsのpipe
```javascript
readable.pipe(writable);   // pipe が自動でバックプレッシャー処理
```

### Rustのtokio
```rust
while let Some(chunk) = stream.next().await {
    sink.send(chunk).await?;    // 消費者の準備待ち
}
```

## リアクティブストリーム
バックプレッシャーを前提にした仕様。Java、.NET、JSで標準化。
- **RxJava / RxJS**（Observable）
- **Project Reactor**（Flux / Mono）
- **Kotlin Flow**

## データ変換の例

### 1. 大きなCSVをフィルタしてDBへ
```javascript
const csv = require("csv-parse");

fs.createReadStream("big.csv")
  .pipe(csv())
  .on("data", row => {
    if (row.active) db.insert(row);
  });
```

### 2. HTTPレスポンスを保存
```javascript
const res = await fetch(url);
await pipeline(res.body, fs.createWriteStream("out.bin"));
```

### 3. ログの集計
```bash
tail -F app.log | grep ERROR | cut -d ':' -f 2 | sort | uniq -c
```
リアルタイムで流しながら処理。

## チャンク単位の考え方
バッファリングの粒度が性能に直結。
- 小さすぎ: システムコール多発
- 大きすぎ: メモリ圧迫、レイテンシ

典型的には数KB〜64KB。多くの実装のデフォルトもこの範囲。

## リアルタイム処理基盤
大規模な分散ストリーム処理で使われる技術:
- **Apache Kafka**: 永続化可能なメッセージストリーム
- **Apache Flink / Spark Streaming**: 分散ストリーム計算
- **Kinesis / Pub/Sub**: マネージドサービス

イベント駆動アーキテクチャ、IoT、監視などで必須。

## ウィンドウ処理
無限ストリームに対して「直近N秒」「直近M件」で区切って集計する手法。
- **タンブリングウィンドウ**: 重ならない固定区間
- **スライディングウィンドウ**: 重なりあり
- **セッションウィンドウ**: 活動の切れ目で区切る

## ストリームのエラーハンドリング
途中の段でエラーが出たら**下流へ伝播**するのが一般的。
```javascript
pipeline(
  fs.createReadStream("a.txt"),
  zlib.createGzip(),
  fs.createWriteStream("a.gz"),
  (err) => { if (err) console.error(err); }
);
```

## デバッグのコツ
- 流れを可視化（各段で件数・バイト数ログ）
- 不具合箇所はチャンク内容を保存
- バッファが溜まりすぎていないか監視
- メモリ使用量グラフを常に確認

## よくあるアンチパターン

### 1. 全部メモリに読み込む
```javascript
const data = fs.readFileSync("10GB.txt");   // NG
```

### 2. バックプレッシャー無視
```javascript
readable.on("data", chunk => writable.write(chunk));  // writeの戻り値を見ない
```
きちんと `pipe` / `pipeline` / async iteration で書く。

### 3. 無限生成
生成速度が消費速度より速いと、バッファが爆発。レートリミットが必要。

## まとめ
- ストリームは**データを少しずつ流しながら処理**する抽象化
- 大容量データ、リアルタイム処理、パイプライン合成に有効
- **バックプレッシャー**で生産者と消費者の速度差を吸収
- Node.js Streams / Java Stream API / RxJS / Kafka など多彩な実装
- 全読みのアンチパターンを避け、`pipe` や async iteration で書く
