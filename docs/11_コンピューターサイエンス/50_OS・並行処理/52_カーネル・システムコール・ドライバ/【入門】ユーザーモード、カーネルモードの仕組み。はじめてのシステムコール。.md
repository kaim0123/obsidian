#オペレーティングシステム #カーネル

## 要約

ログ出力の1行は、ディスプレイに直接は届かない——**CPUのレベルで届かせてもらえない**ようになっている。今回のテーマは **ユーザーモード／カーネルモード** と、外側の世界（ファイル・画面・通信）に触るための唯一の窓口 **システムコール**。境界を一足飛びには越えられず、必ず真ん中を通る。

### 第1章：なぜモードを分けるのか

OSもアプリもどちらもソフトウェアで、同じCPU上で動く。それでもアプリがOSを乗っ取られないのはモードがあるから。

| | ユーザーモード | カーネルモード（特権モード） |
| --- | --- | --- |
| 権限 | メモリ／ハードに直接触れない | すべて直接触れられる |
| クラッシュ | そのアプリだけ終了すればよい | OSが安全を保証できない → 全体停止（BSOD／カーネルパニック） |

モードがなければ、ポインタ1つずれで隣アプリやOSのメモリを壊せ、悪意あるコードはストレージの生データも直接書き換えられる。**ユーザーモード＝安全だが権限なし／カーネルモード＝権限ありだが危険**。だから大半のプログラムはユーザーモードで動き、そのままではファイルも読めず画面にも出せない。

### 第2章：CPUの中のたった1ビット

ソフト同士は対等なので上下関係は作れない → **ハードウェアの助け**が必要。

- **命令セット**のうち、機器と直接やり取りする命令・メモリの見え方を書き換える命令などは **特権命令**
- CPU内の **モードビット**（例: 1＝特権／カーネル、0＝制限／ユーザー）が境界の正体
- 特権命令はモードビットが0だと **トランジスタ配線でゲートが開かず止まる**（ifチェックではない）

誰がビットを1にするか？アプリが自分で1にできたら無意味 → **モードビットを書き換える命令自体が特権命令**。この堂々巡りを断つのは **割り込み**。

割り込みの流れ: (1) 状態保存（レジスタを積む）→ (2) 処理 → (3) 状態復元 → (4) 復帰の特別命令。割り込みが起きると **モードビットが自動で1** になり、飛んだ先（割り込みハンドラー）は特権で動く。だから起動時にOSがその場所を取り鍵をかける。**MMU** なども特権命令でしか触れず、ハンドラーの置き場所を隠せる。

整理: **モードビット・特権命令・割り込み** の3つ。割り込みは「肩を叩いて止める」のではなく、CPUが1命令終えるごとに自分で確認する。境界を超える道は割り込みという細い道1本で、アプリが自分から使うのが **システムコール**。

### 第3章：システムコールが起きる瞬間

地図は5階建て——上2つがユーザー、下2つがカーネル、真ん中がシステムコール。よくある勘違い: `open` などはシステムコールそのものではなく、標準ライブラリの **包み紙**。

包み紙の中身の例（概念）:

1. レジスタに **システムコール番号**（例: read=0, write=1, open=2）
2. 引数をレジスタに並べる（ここまでは普通の代入、特権なし）
3. **`int`（割り込み）** で自分自身にわざと割り込み → 境界越え

起きること: モードビット=1 → **ユーザースタックからカーネルスタックへ切替**（同じプロセスでもスタックは別）→ 状態退避 → カーネル受付が番号を見て処理（特権でディスク操作、ビットは1のまま）→ 専用命令で戻り、ビット=0。

定番化したため CPU に専用命令（syscall / sysret 等）。**呼ぶ方は誰でも使え、戻る方は特権**という非対称が大事。システムコール＝自分の実行を止めてOSに主導権を渡すこと。OSはすぐ返すとは限らず、その隙に別プロセスへ切替えることもある（スケジューラ）。

### 第4章：1行が呼ぶ連鎖

ファイルを読む1行の裏で例: open → fstat（大きさ）→ read → close と **4回の境界往復**。

返る **ファイルディスクリプタ（FD）** はただの整数（自分で開く最初は多くが3。0〜2は標準入出力・エラー）。カーネル側のプロセスごとの表に行が追加され、番号だけ外に出す——**カプセル化**。でたらめな番号なら表になくエラーで済み壊れない。ソケットもパイプも同じ整数で扱える＝「すべてはファイル」の番号による抽象化。

read では **ディスク→カーネル→アプリ** の2段階コピー（境界を守るためカーネルメモリを直接見せない）。ファイルコピー程度でも、プロンプト表示・入力・open・create・read/writeループ・終了表示など、**サイズに応じて何十〜何百回**も往復する。実機では毎秒何千回も境界往復が起きている。

### 第5章：実務につながる3つの視点

**1. ライブラリ関数とシステムコール**  
`man read`（セクション1＝コマンド）と `man 2 read`（セクション2＝システムコール）は別物。3がライブラリ。`printf` はライブラリで、内部で `write` を呼ぶ。ライブラリはバッファして往復を減らし、プラットフォーム差も吸収する。

**2. モードスイッチのコスト**  
- **モードスイッチ** … 同じプロセスのまま権限だけ変わる（システムコールで起きること）  
- **コンテキストスイッチ** … 動くプロセス自体が変わり、アドレス空間も入れ替わる  

モードスイッチはコンテキストスイッチより軽いが、普通の関数呼び出しよりずっと重い（キャッシュも冷え、主導権がすぐ返る保証もない）。実務ではループ内で毎行システムコールするよりまとめて1回——**バッファリング／バルク／非同期**は往復削減の工夫。

逆にシステムコールを一度も呼ばない無限ループだと、協調型OSでは主導権を取り返せない。解決は **タイマー割り込み**（特権でのみ設定）によるプリエンプティブOS。ユーザーモードで特権命令を使うとCPUが割り込みでOSに知らせ、多くはそのプロセスを終了させる。

**3. カーネルモードで動く「他人のコード」**  
カーネルで動くのはOSだけではない。**デバイスドライバ**はハード操作のためカーネルモード。仕切りがないので悪いドライバのバグがOS本体を壊し、ドライバ落ち＝OS落ち（BSODの多くはこれ）。ゲームのアンチチートなどもカーネル権限で入力元を直接調べられるが、他プロセスの中身も見える。CloudStrike 障害のように設定破損でソフトが落ち、カーネルモードゆえOSごと道連れになり世界中の端末が止まった例もある。

マイクロカーネルではドライバをユーザーモードで動かし安全性は上がるが、境界往復は増える——同じトレードオフ。

### まとめ

- 境界の正体は CPU の **モードビット1つ**。1のときだけ特権命令が回路で通る  
- ビットを1にできるのは主に **割り込み**。自分から起こして超えるのが **システムコール**  
- アプリが受け取るのは整数（FD）だけで、実態はカーネルの表に隠されている  
- ログ1行も、ランタイム → ライブラリ → システムコールで境界を超え、ようやく画面に届く
