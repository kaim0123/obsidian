# システムコールとカーネル

プログラムがファイルを読んだり、ネットワーク通信したり、新しいプロセスを作ったりする裏側では、必ず **OS のカーネル** が動いている。
ここでは「カーネルとは何か」「ユーザー空間とカーネル空間の違い」「システムコールの仕組み」を初心者向けに解説する。

---

## 1. カーネルとは

### 一言でいうと
> **OS の核心部分。ハードウェアを直接操作し、プログラムに安全なインターフェースを提供する**

カーネルは OS の一番奥にある中核プログラムで、コンピュータの起動時にメモリに読み込まれ、常に動作し続ける。

### カーネルの主な責務

| 責務 | 内容 |
|---|---|
| **プロセス管理** | プロセスの生成・終了・スケジューリング |
| **メモリ管理** | 仮想メモリ、ページング、メモリの割り当て |
| **ファイルシステム** | ファイルの読み書き、ディレクトリ管理 |
| **デバイス管理** | ドライバを通じたハードウェアの制御 |
| **ネットワーク** | TCP/IP スタック、ソケット通信 |
| **セキュリティ** | アクセス制御、権限管理 |

## 2. ユーザー空間とカーネル空間

### 2 つの世界
CPU は **2 つのモード** を持っている。

```
┌──────────────────────────────────────────┐
│           ユーザー空間（User Space）       │
│                                          │
│  アプリケーション（ブラウザ, エディタ,     │
│  Node.js, Python スクリプト...）          │
│                                          │
│  ※ ハードウェアに直接アクセスできない      │
│  ※ 他のプロセスのメモリに触れない         │
├──────────────────── 境界 ─────────────────┤
│ ↑↓ システムコール（唯一の合法な通過口）  │
├──────────────────────────────────────────┤
│           カーネル空間（Kernel Space）     │
│                                          │
│  カーネル本体                             │
│  デバイスドライバ                         │
│  ファイルシステム                         │
│  ネットワークスタック                      │
│                                          │
│  ※ ハードウェアに直接アクセスできる        │
│  ※ すべてのメモリにアクセスできる          │
└──────────────────────────────────────────┘
```

### なぜ分離するのか
- **安全性**: ユーザープログラムがハードウェアを直接操作すると、他のプログラムやOS自体を壊す可能性がある
- **安定性**: バグのあるアプリがカーネルを巻き込んでクラッシュすることを防ぐ
- **セキュリティ**: 悪意あるプログラムがディスクを直接読み書きしたり、他プロセスのメモリを覗いたりできない

### CPU の特権レベル（Ring）

```
┌───────────────────┐
│   Ring 3          │ ← ユーザーモード（アプリケーション）
│  ┌─────────────┐  │     制限された命令のみ実行可能
│  │  Ring 0     │  │ ← カーネルモード（OS カーネル）
│  │  特権命令OK  │  │     全命令を実行可能
│  └─────────────┘  │
└───────────────────┘
```

- **Ring 0（カーネルモード）**: すべての CPU 命令を実行可能。メモリ全体にアクセス可能
- **Ring 3（ユーザーモード）**: 制限された命令のみ。特権命令を実行するとCPU例外が発生

## 3. システムコールとは

### 一言でいうと
> **ユーザープログラムが OS の機能を使うための「窓口」**

ユーザー空間のプログラムは直接ハードウェアを操作できない。
ファイルを開きたい、ネットワークに接続したい場合は、システムコールを通じてカーネルに依頼する。

### 身近な例

| やりたいこと | システムコール | 言語での表現 |
|---|---|---|
| ファイルを開く | `open()` | Python: `open("file.txt")` |
| ファイルを読む | `read()` | Node.js: `fs.readFile()` |
| ファイルに書く | `write()` | Java: `FileWriter.write()` |
| ファイルを閉じる | `close()` | ほぼすべての言語で対応 |
| プロセスを作る | `fork()` | シェル: コマンド実行 |
| プログラムを実行 | `exec()` | Python: `subprocess.run()` |
| メモリを確保 | `mmap()`, `brk()` | C: `malloc()` の裏側 |
| 時刻を取得 | `gettimeofday()` | JavaScript: `Date.now()` |

### 重要なポイント
普段書くコードで直接システムコールを呼ぶことは少ない。
言語のランタイムや標準ライブラリが**裏側でシステムコールを呼んでいる**。

```
JavaScript: fs.readFileSync("data.txt")
    ↓
Node.js ランタイム（libuv）
    ↓
C ライブラリ（glibc の read()）
    ↓
システムコール: read(fd, buf, size)
    ↓
カーネル → ファイルシステム → ディスクドライバ → ハードウェア
```

## 4. システムコールの仕組み

### 呼び出しの流れ

```
ユーザー空間                      カーネル空間
┌─────────────┐                 ┌──────────────┐
│ 1. 引数を    │                 │              │
│    レジスタに│                 │              │
│    セット   │                 │              │
│             │                 │              │
│ 2. trap命令 │ ──── 切り替え ──→│ 3. システム   │
│   (割り込み) │                 │    コール番号 │
│             │                 │    を見て分岐 │
│             │                 │              │
│             │                 │ 4. 処理を実行 │
│             │                 │              │
│ 6. 結果を   │ ←── 復帰 ──────│ 5. 結果を     │
│    受け取る  │                 │    セット     │
└─────────────┘                 └──────────────┘
```

1. プログラムが引数（ファイル名、バッファのアドレスなど）を CPU レジスタにセット
2. **trap 命令**（ソフトウェア割り込み）を実行 → CPU がカーネルモードに切り替わる
3. カーネルがシステムコール番号を見て、対応する処理を実行
4. 処理結果をレジスタにセット
5. ユーザーモードに戻る
6. プログラムが結果を受け取る

### コスト
- モード切り替え（ユーザー↔カーネル）にはオーバーヘッドがある
- 1 回のシステムコールは数百ナノ秒〜数マイクロ秒
- ファイルの 1 バイトずつ `read()` するのが非効率な理由 → バッファリングで回数を減らす

## 5. 代表的なシステムコールの分類

### プロセス制御
| システムコール | 説明 |
|---|---|
| `fork()` | 現在のプロセスを複製して子プロセスを作る |
| `exec()` | 現在のプロセスを別のプログラムに置き換える |
| `wait()` | 子プロセスの終了を待つ |
| `exit()` | プロセスを終了する |
| `kill()` | シグナルを送る（プロセスの終了要求など） |

### ファイル操作
| システムコール | 説明 |
|---|---|
| `open()` | ファイルを開いて fd を取得 |
| `read()` | fd から読み取り |
| `write()` | fd に書き込み |
| `close()` | fd を閉じる |
| `stat()` | ファイルのメタデータを取得 |
| `lseek()` | 読み書き位置を移動 |

### メモリ管理
| システムコール | 説明 |
|---|---|
| `brk()` / `sbrk()` | ヒープ領域を拡張・縮小 |
| `mmap()` | ファイルやデバイスをメモリにマッピング |
| `munmap()` | マッピングを解除 |

### ネットワーク
| システムコール | 説明 |
|---|---|
| `socket()` | ソケットを作成 |
| `bind()` | ソケットにアドレスを紐付け |
| `listen()` | 接続待ちにする |
| `accept()` | 接続を受け入れる |
| `connect()` | サーバーに接続する |
| `send()` / `recv()` | データの送受信 |

## 6. カーネルの種類

### モノリシックカーネル
> **OS の機能をすべて 1 つの大きなプログラムとして実装**

```
┌──────────────────────────────┐
│         カーネル空間          │
│  プロセス管理                │
│  メモリ管理                  │
│  ファイルシステム             │
│  デバイスドライバ             │
│  ネットワークスタック         │
│  （全部が同じアドレス空間）    │
└──────────────────────────────┘
```

- **メリット**: 高速（関数呼び出しで済む）
- **デメリット**: 1 つのバグがカーネル全体をクラッシュさせうる
- **例**: Linux, FreeBSD

### マイクロカーネル
> **最小限の機能だけカーネルに置き、残りはユーザー空間のサーバーとして実装**

```
ユーザー空間:
┌──────────┐ ┌──────────┐ ┌──────────┐
│ ファイル  │ │ デバイス  │ │ ネット   │
│ サーバー  │ │ ドライバ  │ │ サーバー  │
└────┬─────┘ └────┬─────┘ └────┬─────┘
     │            │            │
     ▼ IPC        ▼ IPC        ▼ IPC
┌──────────────────────────────────┐
│  マイクロカーネル                  │
│  （プロセス管理、メモリ管理、IPC） │
└──────────────────────────────────┘
```

- **メリット**: 安定性が高い（ドライバがクラッシュしてもカーネルは無事）
- **デメリット**: IPC（プロセス間通信）のオーバーヘッドで遅い
- **例**: MINIX, QNX, seL4

### ハイブリッドカーネル
モノリシックとマイクロの中間。基本はモノリシックだが、一部をモジュール化。
- **例**: Windows NT, macOS（XNU）

## 7. Linux でシステムコールを観察する

### strace コマンド
プログラムが発行するシステムコールをリアルタイムで表示するツール。

```bash
# "ls" コマンドが使うシステムコールを表示
strace ls

# 出力例（抜粋）:
# execve("/bin/ls", ["ls"], ...) = 0
# openat(AT_FDCWD, ".", O_RDONLY) = 3
# getdents64(3, ...) = 480
# write(1, "file1.txt\nfile2.txt\n", 20) = 20
# close(3) = 0
# exit_group(0) = ?
```

`ls` のような単純なコマンドでも、裏では数十〜数百のシステムコールが発行されている。

### Windows の場合
Process Monitor（Sysinternals）でシステムコールに相当する API 呼び出しを監視できる。

## 8. 割り込み（Interrupt）

### 一言でいうと
> **CPU に「今の作業を中断して、こちらを処理して」と伝える仕組み**

### 割り込みの種類

| 種類 | 発生源 | 例 |
|---|---|---|
| **ハードウェア割り込み** | デバイス | キー入力、ディスク読み込み完了、ネットワーク受信 |
| **ソフトウェア割り込み** | プログラム | システムコール（trap）、ゼロ除算エラー |
| **タイマー割り込み** | タイマー | プリエンプティブスケジューリングの切り替え |

### 割り込みの流れ
```
1. デバイスが割り込みを発生
2. CPU が現在の作業を中断し、状態を保存
3. 割り込みハンドラ（カーネル内のコード）を実行
4. 処理完了後、中断していた作業を再開
```

---

## 9. 開発者として知っておくべきこと

1. **システムコールの回数を意識する**: ファイル I/O はバッファリングでまとめる。1 バイトずつ `read()` しない
2. **`strace` / `ltrace` はデバッグに強力**: 「ファイルが見つからない」「Permission denied」の原因が一発で分かることがある
3. **カーネルモードのバグは致命的**: デバイスドライバのバグが Blue Screen（Windows）や Kernel Panic（Linux/Mac）を引き起こす
4. **コンテナと名前空間**: Docker などのコンテナは、Linux カーネルの名前空間（namespace）と cgroup というカーネル機能で実現されている。カーネルは共有している
5. **シグナル**: `SIGTERM`（終了要求）、`SIGKILL`（強制終了）、`SIGINT`（Ctrl+C）などはプロセスに送られるカーネルからの通知
