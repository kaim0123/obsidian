## 詳しい要約

**テーマ：CrowdStrike 事件を入り口に、カーネルモードで動く「ドライバ」の仕組み・歴史・安全対策を解説**

2024年7月19日、CrowdStrike のドライバ更新が原因で世界約850万台の Windows が同時にブルースクリーンになった。ドライバは OS とハードウェアの橋渡しをするソフトウェアで、最高権限の Ring 0 で動くため、1つのバグでシステム全体が止まり得る。低レイヤーの仕組み（プロテクションリング、仮想メモリ、DMA/IOMMU）、MS-DOS から WDF までの歴史、署名・PatchGuard・HVCI・Rust といった現代の対策を順に解説する。

---

### ドライバとプロテクションリング

- ドライバは、マウスの「右に3cm動いた」のようなハードウェアの生の信号を OS が理解できる形に翻訳する「通訳」。
- x86 CPU には Ring 0〜3 の権限レベルがあり、実質使われるのは **Ring 0（カーネルモード）** と **Ring 3（ユーザーモード）**。
- Ring 0 では特権命令（割り込みを無効/有効にする CLI/STI など）やメモリ全域・I/O ポートへのアクセスが可能。ユーザーモードで実行すると一般保護例外（GPF）で落ちる。
- カーネルモードドライバは Ring 0 で動くため高性能だが、バグがあるとシステム全体がクラッシュする。

### ブルースクリーンと CrowdStrike 事件の中身

- ブルースクリーンの正式名は**バグチェック**。カーネルが回復不能なエラーを検出すると KeBugCheckEx が呼ばれ、ストップコードが表示される（事件では 0x139 KERNEL_SECURITY_CHECK_FAILURE が多かった）。
- ドライバが設定ファイル（**チャネルファイル291**）を解釈する際、読むべきメモリアドレスの計算を誤り、存在しない場所を参照 → **ページフォルト**。
- 現代の OS は仮想メモリを使い、仮想アドレス → 物理アドレスの変換は **MMU** が担う（x86-64 は4段階のページテーブル、最近は5段階も）。不正なアドレスへのアクセスで例外が起きる。ユーザーモードならプログラムが落ちるだけだが、カーネルモードではダブルフォルト・トリプルフォルトと連鎖し、バグチェックや CPU リセットに至る。

### DMA と IOMMU

- **DMA**（Direct Memory Access）はデバイスが CPU を介さずメモリに直接アクセスする仕組みで高速だが、悪意あるデバイスがカーネルメモリを書き換える **DMA 攻撃**のリスクがある。
- **IOMMU**（Intel VT-d、AMD-Vi）はデバイス用の MMU で、DMA を許可された領域に制限する。ただしドライバ自体のバグには無力。

### ドライバの歴史

| 時代 | 形式 | 特徴 |
|---|---|---|
| MS-DOS | **TSR**（常駐プログラム） | 16ビットのリアルモードでメモリ保護なし。VGA のフレームバッファに直接書き込めた。マウスドライバは割り込み（INT 33h）をフックして動作。複数の TSR が競合しがち |
| Windows 3.x（1990年代前半） | **VxD** | 32ビットのプロテクトモードドライバ。DOS 上のハイブリッドで16/32ビットが混在。V86 モードで DOS アプリを仮想化 |
| Windows 95/98/2000 | PnP、**WDM** | OS をまたいでドライバを共通化。I/O 要求を **IRP**（I/O Request Packet）で表し、**ドライバスタック**（例：USB マウスなら HID クラス → USB → ホストコントローラー → PCI バス）を経由。層が独立しているので下位を替えても上位はそのまま使える。PnP マネージャー・パワーマネージャー（デバイス D0〜D3、システム S0〜S5 の電源状態）を統合 |
| Windows Vista 以降 | **WDF** | WDM の上に構築されたオブジェクト指向 API。IRP の参照カウントやエラー処理をフレームワークが肩代わり。ETW・WPP などのトレース/ログ機能も充実 |

### 現代のセキュリティ対策

- **ドライバ署名**：Vista x64 以降、カーネルモードドライバにデジタル署名が必須（SignTool、PKCS#7、X.509、SHA-256 のハッシュで改ざん検出）。Windows 10 以降は EV 証明書が必要。
  - ただし署名はドライバのバイナリしか検証せず、**読み込むデータファイルの正しさは検証しない**。CrowdStrike ではドライバ本体は正常に署名済みで、チャネルファイル291のパーサーの配列境界チェック不足による**範囲外読み取り（out-of-bounds read）**が原因だった。
- **ガードページ**：バッファの前後にアクセス不可のページを置き、範囲外アクセスを即座に検出。
- **Driver Verifier**：開発・テスト用。スペシャルプールで各割り当ての前後にガードページを置き、メモリ破壊や解放漏れを検出。性能が大きく落ちるので本番では使えない。
- ゼロデイ対応のため設定ファイルを頻繁に配信する必要があり、全パターンのテストが難しかったと推測（セキュリティとのトレードオフ）。
- **PatchGuard（カーネルパッチ保護）**：x64 Windows で常に有効。IDT（割り込みハンドラのテーブル）や SSDT などの改ざんを定期チェックし、検出すると 0x109 CRITICAL_STRUCTURE_CORRUPTION。ルートキット対策だがチェックが定期的なので隙がある。
- **HVCI**（VBS の一部）：Hyper-V のハイパーバイザーでカーネルメモリを保護。コードページは読み取り専用＋実行可、データページは書き込み可＋実行不可（**W^X**）。新しいコードの実行にはハイパーバイザーによる署名検証が必要。自己改変や動的コード生成をするドライバは動かなくなる（互換性とのトレードオフ）。

### Rust への移行

- Linux では Rust for Linux が進み、一部ドライバが Rust で書かれ始めている。
- **所有権システム**でスコープを抜けると自動解放され、メモリリークや**ダングリングポインタ**（解放済みメモリを指すポインタ、C の use-after-free 脆弱性の原因）を防ぐ。**借用チェッカー**が参照の生存期間を解析し、危険なコードをコンパイルエラーにする。
- 危険な操作は `unsafe` ブロックに閉じ込め、レビューで集中的に確認できる。カーネルでは unsafe が避けられないが、最小化して安全なラッパーを作ることでバグを減らせる。
- Microsoft も Azure や Windows 11 カーネルの一部を Rust で書き始めており、動画制作中に「2030年までに C/C++ を撤廃し Rust 化する方針」が発表されたと紹介。

### まとめ

- ドライバは Ring 0 で特権命令や DMA を使ってハードウェアを制御する。IOMMU は DMA 攻撃を防ぐが、ドライバ自身のバグには無力。
- ドライバのアーキテクチャは TSR → VxD → WDM → WDF と進化し、IRP・ドライバスタック・電源管理が整備された。
- 署名・Driver Verifier・PatchGuard・HVCI で多層防御し、さらに Rust のような安全な言語への移行が進んでいる。
