## 詳しい要約

本動画は、前回の **「OS とカーネルの違い」** を前提に、**システムコール（System Call）** がいかにして **アプリケーションとカーネルをつなぐ公式の窓口** として機能するかを初心者向けに解説する。スマホで動画を見る・ゲームでガチャを引く・ブラウザでネットサーフィンする——これら日常の操作はすべて、裏側で **システムコール経由でカーネルに依頼** している。システムコールがなければファイルも開けず、画面にも何も表示できず、ネットにもつながらない。**カーネルがハードウェアの文番** として全アクセスを管理し、アプリは直接ハードウェアに触れない——その制約の中でアプリが機能するための **唯一の正式な手段** がシステムコールである。

### システムコールとは——アプリとカーネルの架け橋

- **OS** はコンピュータ全体を管理する巨大なソフトウェア。**カーネル** はその中核で、CPU・メモリ・ディスクなど **ハードウェアを直接制御する唯一の存在**（OS の「心臓部」）。
- 普通のアプリケーションは **カーネルに直接アクセスできない**。全アプリが勝手にハードウェアを触れば、複数アプリが同時にディスクへ書き込んだ際にデータが壊れるなど **カオス** になる。
- **システムコール** は、アプリがカーネルに「これをやって」と **正式にお願いする窓口**。
- **ホテルの例え**：宿泊客（アプリ）は厨房や倉庫に勝手に入れないが、**ルームサービスやフロントへの依頼**（システムコール）ならスタッフ（カーネル）が対応してくれる。

### ユーザーモードとカーネルモード

CPU には **2 つの実行モード** があり、システムコールの核心はこの **モード切り替え** にある。

| モード | 権限 | 動作する主体 |
|--------|------|-------------|
| **ユーザーモード** | 制限あり。ハードウェア直接操作不可、メモリも自由にアクセス不可 | 一般アプリケーション |
| **カーネルモード** | 特権モード。ハードウェア直接操作・全メモリアクセス可能 | カーネルのみ |

- システムコールが呼ばれると、CPU は **ユーザーモード → カーネルモード** に切り替わり、カーネルが処理を実行した後 **ユーザーモードに戻る**。
- モード切り替えは **ハードウェアレベル** で行われるため安全。カーネルモードのまま常駐させると危険なので、**一時的に入ってすぐ戻る** 設計になっている。
- ホテルの例えで言えば、一般客エリア（ユーザーモード）からスタッフ専用エリア（カーネルモード）への出入りに相当する。

### システムコールの 5 大カテゴリー

Linux だけでも **300 個以上** のシステムコールが存在するが、全部覚える必要はない。大きく **5 つのカテゴリー** に分類できる。

| カテゴリー | 代表的なシステムコール | 役割 |
|-----------|----------------------|------|
| **1. プロセス制御** | `fork`, `exec`, `exit`, `wait` | プログラムの実行・終了・複製を管理 |
| **2. ファイル操作** | `open`, `read`, `write`, `close` | ファイルの開閉・読み書き（ディスクはハードウェアのためカーネル経由が必須） |
| **3. デバイス管理** | `ioctl`, `mmap` | キーボード・マウス・プリンター・NIC などのデバイス制御 |
| **4. 情報管理** | `getpid`, `time`, `sysinfo` | プロセス ID・現在時刻・メモリ使用状況などシステム状態の取得 |
| **5. 通信** | `socket`, `send`, `recv`, `pipe` | プロセス間通信・ネットワーク通信（ブラウザの通信もここ） |

#### プロセス制御の要点

- **`fork`**：親プロセスから子プロセスを複製する（「分身の術」）。カーネルがメモリ内容を丸ごとコピーし、戻り値で親子を区別——親には子の PID、子には `0` が返る。
- **`exec`**：別のプログラムを実行する。
- **`exit`**：プログラムを終了する。
- **`wait`**：子プロセスの終了を待つ。

#### ファイル操作の流れ

1. **`open`** — カーネルにファイルを開いてもらう → 成功すると **ファイルディスクリプタ**（識別用の番号。図書館の受付番号に相当）が返る
2. **`read`** — ファイルディスクリプタを使って内容を読み込む
3. **`close`** — 使い終わったことをカーネルに伝える

アプリは **一度もハードウェアに直接触れず**、すべてカーネルへの依頼で完結する。

### システムコールの内部動作——6 ステップ

システムコールが実行される流れは、大きく **6 つのステップ** に分かれる。

| ステップ | 内容 |
|---------|------|
| **1. ラッパー関数の呼び出し** | アプリが `read()` などの関数を呼ぶ。これは本物のシステムコールではなく、本物を呼び出すための **ラッパー関数**（使いやすく包んだ便利関数） |
| **2. システムコール番号の設定** | ラッパーが番号を設定（Linux 64bit では `read`=0, `write`=1 など）。カーネルは番号で処理を判断 |
| **3. ソフトウェア割り込み** | **syscall 命令**（x86-64）や **int 0x80**（旧 x86）で CPU に「今の処理を中断してカーネルへ」と割り込む |
| **4. モード切り替え** | ユーザーモード → カーネルモード。特権レベルが変わりハードウェア操作権限を得る |
| **5. カーネルによる処理** | **システムコールテーブル**（メニュー表）を参照し、番号に対応する処理を実行 |
| **6. 結果の返却と復帰** | 処理結果を返し、カーネルモード → ユーザーモードに戻る。アプリは何事もなかったかのように続行 |

### オーバーヘッドと効率化

- システムコールには **オーバーヘッド**（余計にかかる時間）がある。モード切り替え・カーネルへのジャンプなどの手間が発生する。
- 頻繁にシステムコールを呼ぶプログラムは **遅くなる** ことがある。
- 対策例：ファイルを **1 バイトずつ読むのではなくまとめて読み込む** など、呼び出し回数を減らす工夫が必要。

### エラーハンドリング

システムコールは失敗することがある。

| 状況 | 例 |
|------|-----|
| ファイル不存在 | `ENOENT`（No such file or directory） |
| 権限不足 | `EACCES`（Permission denied） |
| ディスク満杯 | 書き込み失敗 |

- 失敗時は多くの場合 **−1** が返り、**`errno`** 変数にエラーコードが設定される。カーネルが理由を教えてくれる。

### プロセス間通信——パイプ

- **`pipe`**：カーネルに 2 つのプロセス間でデータをやり取りできる「パイプ」を作ってもらうシステムコール。
- 一方のプロセスが書き込んだデータを、もう一方が読み取れる（`ls | grep text` のようなパイプラインの基盤）。
- データのやり取りもカーネルが仲介するため **安全** に複数プログラムを協調動作させられる。

### よくあるミス

| ミス | 内容 | 対策 |
|------|------|------|
| **ファイルディスクリプタのリーク** | `open` したのに `close` を忘れる → ディスクリプタが枯渇し「これ以上ファイルを開けません」 | 必ず `close` する。借りた本を返さないと新しく借りられない |
| **バッファオーバーフロー** | `read` でバッファサイズを超えて読み込む → メモリ破壊・セキュリティホール | 読み込みサイズを厳密に制限 |
| **競合状態** | 複数プロセスが同じファイルに同時アクセス → データ破壊 | **`fcntl`**, **`flock`** などのロック機構でカーネルに排他制御を依頼 |

### 進化と最新技術

#### システムコールの進化

- 昔は `read` / `write` だけだったが、用途に応じたバリエーションが増えた。
  - **`pread`**：ファイルの特定位置から読み込み
  - **`readv`**：複数バッファに分散して読み込み

#### 非同期 I/O と io_uring

- 通常のシステムコールは **同期**——カーネルの処理が終わるまでアプリは待つ。
- **非同期 I/O** なら「これやっといて」と頼んだらすぐ戻り、完了後に通知を受け取れる。
- Linux の **io_uring** は超高速な非同期 I/O で、従来比 **数倍〜数十倍** 速いことも。ネットワーク処理で特に威力を発揮し、オーバーヘッドを大幅に削減。

#### 仮想化

- 仮想マシン内のシステムコールは **2 段階**：ゲスト OS のカーネル → ホスト OS のカーネル（カーネルがカーネルにお願いする構造）。
- **パラバーチャライゼーション** で 2 段階を効率化。

#### セキュリティ関連

| 技術 | 内容 |
|------|------|
| **eBPF**（Extended Berkeley Packet Filter） | カーネル内で安全にプログラムを実行。システムコールの監視・フィルタリングに利用。セキュリティツール・パフォーマンス監視で実用 |
| **seccomp** | 使えるシステムコールを制限。「このアプリはファイル読み込みしかできません」と **サンドボックス化**（安全な箱の中で遊ばせる） |

#### マイクロカーネルとの関係

- **マイクロカーネル** アーキテクチャではカーネルを極小化し、システムコールの代わりに **メッセージパッシング** でプロセス間協調する設計もある。
- 前回の **モノリシックカーネル vs マイクロカーネル** の違いが、システムコールの設計にも関わる。

### まとめ

| 概念 | 役割 |
|------|------|
| **OS** | コンピュータ全体を管理するシステム |
| **カーネル** | OS の中核。ハードウェアを直接管理する心臓部 |
| **システムコール** | アプリとカーネルをつぐ公式インターフェイス（ホテルのルームサービス） |

- ゲーム・動画視聴・ネットサーフィンなど、日常のあらゆる操作は **システムコールとカーネルのおかげ** で実現している。
- 普段は意識しない **縁の下の力持ち** だが、基本的な考え方——**アプリとカーネルの橋渡し**——は技術が進化しても変わらない。
- 前回の **OS とカーネル** の話と合わせて見ると、コンピュータの仕組みがより立体的に理解できる。
