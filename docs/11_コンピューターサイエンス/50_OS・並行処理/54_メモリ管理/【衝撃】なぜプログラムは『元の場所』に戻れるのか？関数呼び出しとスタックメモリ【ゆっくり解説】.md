## 要約

関数を呼ぶとプログラムは全く別の場所へジャンプするのに、処理が終わると**呼び出し元の次の行**へ戻れる——その「記憶」を支えているのが **スタックメモリ** である。本動画は、メモリ地図・スタックフレーム・呼び出し規約・スタックオーバーフロー・末尾再帰最適化・インライン展開までを一気に解説し、「なぜローカル変数は自動で消えるのか」「なぜ小さな関数は速いのか」「Stack Overflow エラーの正体」を一本の線でつなぐ。

### 問題設定：CPU は一瞬で忘れる

- プログラムは上から順に実行されるだけ、と思いがちだが、**関数呼び出しの瞬間に別アドレスへジャンプ**する。
- それでも終われば呼び出し元の次の命令に戻る。**CPU 自身はその戻り先を覚えていない**——記憶を支えているのがスタック。
- スタックはパンケーキを積み上げるイメージ（**LIFO**：Last In, First Out）。同時に、全プログラマが一度は見る **スタックオーバーフロー** の舞台でもある。

### メモリの4領域

プログラム実行時、メモリは大きく次の4つに分かれる（下から上へ）。

| 領域 | 内容 |
|---|---|
| **コード領域** | 実行するプログラム本体 |
| **データ領域** | グローバル変数・静的変数 |
| **ヒープ領域** | 実行中に動的確保するメモリ（`malloc` / `new` 等） |
| **スタック領域** | 関数呼び出し用の一時メモリ（一番上） |

- **ヒープ**：自由に使える倉庫。好きなタイミングで確保・解放できるが管理が面倒で、**ガベージコレクション**が必要になるのもここ。
- **スタック**：決まった順序で積み上げ、**逆順で取り出す**専用メモリ。関数の入れ子（A→B→C なら戻りは C→B→A）にぴったりはまる。
- スタックの利点：**高速**——確保も解放もポインタを少しずらすだけ（ヒープのように空き領域を探す必要がない）。
- スタックの致命的弱点：**サイズが固定で小さい**（Linux ではだいたい **8 MB** 程度）。大きな配列や、関数を抜けた後も残したいデータはヒープに置くしかない。スタックは**関数内だけで使う、小さくて一時的なデータ専用**。

### スタックフレーム：戻り先を覚える弁当箱

関数が呼ばれるたびに、スタックに **スタックフレーム**（お弁当箱のようなセット）が積まれる。主な中身は次のとおり。

1. **リターンアドレス**  
   処理が終わったらどこに戻るかのアドレス。CPU の **プログラムカウンタ（PC）／インストラクションポインタ（IP）** が「今どの命令を実行しているか」を指しており、関数呼び出し時にその値をスタックへ保存してから新しい場所へジャンプする。終わったらスタックから取り出して戻る。
2. **引数**  
   関数に渡す値。ただしすべてがスタックに載るわけではない（後述の呼び出し規約）。
3. **ローカル変数**  
   その関数内だけで使う変数。関数を抜けるとフレームごと消えるため、**ローカル変数も自動で消える**（わざわざ `free` しなくてよい理由）。
4. **保存されたレジスタ**  
   呼び出し前に使っていたレジスタの値を退避。特に **RBP（ベースポインタ）** や **callee-saved** と呼ばれるレジスタは、関数終了時に復元して呼び出し元の状態に戻す。これがないとレジスタが勝手に書き換わり、呼び出し元でバグになる。

- **x86-64** では **`CALL`** が自動でリターンアドレスをプッシュし、**`RET`** がポップしてジャンプ——この2命令で往復が完結する。CPU 命令レベルでサポートされている。
- スタックは関数の出入りに合わせて**自動管理**されるため、**メモリリークの心配がない**のが最大の利点。

### 呼び出し規約（Calling Convention）とレジスタ渡し

引数の渡し方には **呼び出し規約（ABI）** がある。少ない引数はメモリより速い **レジスタ** 経由で渡すのが最適化の基本。

| | **Linux 等（System V ABI / x86-64）** | **Windows x64** |
|---|---|---|
| 整数引数（先頭） | 最初の **6つ**：RDI, RSI, RDX, RCX, R8, R9 | 最初の **4つ**：RCX, RDX, R8, R9（順番も異なる） |
| それ以降 | スタックに積む | スタックに積む |
| 浮動小数点 | **XMM0〜XMM7**（別レジスタ群） | 同様に XMM 系 |

- 型によって使うレジスタが違うのもポイント。

### 入れ子呼び出しの動き（main → funcA → funcB）

1. 最初は **main** のフレームだけ（main のローカル変数）。
2. **funcA** 呼び出し：スタックポインタ（**RSP**）が上に伸び、新しいフレームが積まれる。main の次命令アドレスがプッシュされ、引数セット・ローカル変数用空間が確保される。RSP は新フレームの先頭を指す。
3. **funcB** 呼び出し：同様に funcA の戻り先がプッシュされ、funcB のフレームが積まれる。スタックはどんどん上へ伸びる。
4. **funcB 終了**：フレームがポップされ、RSP が下がり、保存されていたリターンアドレスを PC に戻して **funcA** へ。
5. **funcA 終了**：同様にポップして **main** へ。スタックは元の高さに戻る。

パンケーキを上から食べていくイメージそのもの。

### スタックオーバーフロー：上限を超えたとき

- スタックには**上限**がある。典型的な落とし穴が **再帰関数**（自分自身を呼び出す関数。階乗・フィボナッチ等）。
- **終了条件を間違える**と永遠に自分を呼び続け、呼び出しのたびにフレームが積まれ、ついにスタック上限を超える。
- スタック領域の外側（別用途のメモリ）に踏み込むと **スタックオーバーフロー**。OS が検知してプログラムを強制終了（**セグメンテーションフォルト**）。有名な Q&A サイト **Stack Overflow** の名前もこのエラーに由来。
- 再帰を使わなくても、A→B→C→D…と**呼び出しが深すぎれば**同様に起きる。スタックサイズは有限。
- 目安：Linux でスタック 8 MB、1フレーム 100 バイトなら約 **8万回**程度呼べる計算（OS・スレッド設定で変わる）。ただしローカルに大きな配列（例：`char buf[1000000]`）を置くと一瞬で埋まる——**大きなデータはヒープへ**（`malloc` / `new`）が鉄則。

### 末尾再帰最適化（Tail Call Optimization）

- **末尾再帰**：関数の最後の処理が自分自身を呼ぶだけのパターン。新しいフレームを積まず**今のフレームを再利用**でき、実質ループに変換される——スタックを消費しない。
- ただし言語・コンパイラ依存：
  - **C / C++**：標準では保証されない。GCC / Clang は最適化レベルを上げれば行うことが多いが絶対ではない。
  - **Scheme / Kotlin** など一部言語は言語仕様で保証。
  - **Java / Rust** は保証しない。
- 再帰を使うときは、その言語とコンパイラの挙動を確認する必要がある。

### 関数呼び出しのオーバーヘッドとインライン展開

関数呼び出し自体にコスト（**オーバーヘッド**）がある。単なるジャンプではない。

1. リターンアドレスをスタックにプッシュ
2. 引数をレジスタ／スタックにセット
3. ベースポインタ（RBP）等を保存し、新しいスタックフレームを作成
4. 終了時は逆手順で巻き戻し・レジスタ復元・リターンアドレスへジャンプ

- 特に `a + b` を返すだけの小さな関数では、**実処理より呼び出し手続きの方が重い**ことがある。
- **インライン展開**：呼び出し元に関数のコードを直接コピーし、呼び出しを消す。例：`result = add(3, 5)` → `result = 3 + 5`。スタック操作もジャンプもなくなる。ループ内で何度も呼ばれる小さな関数では効果が絶大。
- デメリット：
  1. **コードサイズ増大**（10箇所で呼べば10箇所にコピー）
  2. **命令キャッシュ効率の低下**——コードが大きくなるとキャッシュミスが増え、逆に遅くなることがある
- コンパイラは関数サイズ・呼び出し回数・ループ内かどうか等を見て慎重に判断。C++ の `inline` キーワードは「展開してほしい」という**ヒント**であり強制ではない。最近のコンパイラはキーワードなしでも勝手に最適化することが多い。
- 関連する最適化：**レジスタ割り当て**（よく使うローカル変数をレジスタに乗せっぱなし）、**ループアンローリング**（ループを展開してジャンプ回数を減らす）。スタックの仕組みを理解していれば、他の最適化の理屈も追いやすい。

### 結論

- プログラムが「元の場所」に戻れるのは、**スタックフレームにリターンアドレスが保存されているから**。
- スタックは **LIFO** で関数の入れ子に適合し、確保・解放が速く、ローカル変数はフレームごと自動消滅する。
- 一方でサイズは有限——深い呼び出しや大きなローカル配列で **スタックオーバーフロー** が起きる。大きなデータはヒープへ。
- 関数呼び出しにはオーバーヘッドがあり、コンパイラは **インライン展開** 等でそれを削るが、コードサイズとのトレードオフがある。
- 「なぜそのエラーが出るか」「なぜローカル変数は自動で消えるか」「なぜ小さな関数は速いか」は、すべてスタックの仕組みでつながっている。プログラムは CPU とメモリが織りなす密な踊りであり、仕組みを知るほど良いコードが書ける。
