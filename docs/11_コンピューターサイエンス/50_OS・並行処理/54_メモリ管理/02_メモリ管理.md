# メモリ管理

OS はコンピュータの物理メモリ（RAM）という有限な資源を、複数のプロセスで安全かつ効率的に使えるように管理している。
ここでは「仮想メモリ」「ページング」「アドレス空間」を中心に、初心者向けに解説する。

---

## 1. なぜメモリ管理が必要なのか

もし OS がメモリを管理しなかったらどうなるか？

- プログラム A がアドレス `0x1000` に書き込み → プログラム B も同じアドレスに書き込み → **データが壊れる**
- 1 つのプログラムが全メモリを使い切る → 他のプログラムが起動できない
- 悪意あるプログラムが他のプログラムのメモリを盗み読みできてしまう

→ OS がメモリを **隔離・保護・効率的に配分** する仕組みが不可欠。

---

## 2. 物理メモリと仮想メモリ

### 物理メモリ（Physical Memory）
実際に PC に搭載されている RAM のこと。容量に限りがある（例: 16GB）。

### 仮想メモリ（Virtual Memory）
> **各プロセスに「自分専用の広大なメモリ空間があるように見せかける」仕組み**

実際の RAM がいくらであっても、各プロセスは「自分は 0 番地から始まる巨大なメモリを持っている」と思って動作する。

```
プロセスA の視点          プロセスB の視点
┌──────────────┐        ┌──────────────┐
│ 0x0000       │        │ 0x0000       │
│ 0x1000 ← データ│       │ 0x1000 ← データ│
│ 0x2000       │        │ 0x2000       │
│   ...        │        │   ...        │
│ 0xFFFF       │        │ 0xFFFF       │
└──────────────┘        └──────────────┘
    ↓ OS が変換              ↓ OS が変換
    ↓                       ↓
┌─────────────────────────────────┐
│         物理メモリ (RAM)         │
│  0x3000  0x7000  0xA000  ...   │
└─────────────────────────────────┘
```

- プロセス A の `0x1000` と プロセス B の `0x1000` は **別の物理アドレス** に対応する
- これにより、プロセス同士のメモリが自動的に隔離される

## 3. アドレス空間のレイアウト

1 つのプロセスの仮想アドレス空間は、一般的に以下のような構造をしている。

```
高いアドレス
┌─────────────────────┐
│   カーネル空間        │ ← ユーザープログラムはアクセス不可
├─────────────────────┤
│   スタック ↓         │ ← ローカル変数、関数の呼び出し履歴
│   （上から下へ伸びる） │     スレッドごとに 1 つ
│                     │
│   ↑ ↓ 空き領域      │
│                     │
│   ヒープ ↑          │ ← malloc / new で確保する動的メモリ
│   （下から上へ伸びる） │
├─────────────────────┤
│   BSS              │ ← 未初期化のグローバル変数
├─────────────────────┤
│   データ             │ ← 初期化済みグローバル変数
├─────────────────────┤
│   テキスト（コード）   │ ← プログラムの機械語命令（読み取り専用）
├─────────────────────┤
│   （予約領域）        │
低いアドレス
```

### 各領域の役割

| 領域 | 中身 | 例 |
|---|---|---|
| **テキスト** | プログラムの命令コード | `function add(a, b)` のコンパイル結果 |
| **データ** | 初期値ありのグローバル変数 | `int count = 10;` |
| **BSS** | 初期値なしのグローバル変数 | `int buffer[1024];` |
| **ヒープ** | 動的に確保するメモリ | `malloc()`, `new` |
| **スタック** | 関数呼び出し・ローカル変数 | 関数の引数、戻りアドレス |

## 4. ページングの仕組み

### ページとは
仮想メモリと物理メモリを **固定サイズのブロック（ページ）** に分割して管理する方式。

- **ページ**: 仮想アドレス空間側のブロック（一般的に 4KB）
- **フレーム**: 物理メモリ側のブロック（同じサイズ）

### ページテーブル
「仮想ページ番号 → 物理フレーム番号」の対応表。プロセスごとに 1 つ持つ。

```
仮想アドレス空間              ページテーブル         物理メモリ
┌──────┐                  ┌─────────────┐      ┌──────┐
│ page0│──────────────────→│ frame 5     │─────→│      │ frame 5
│ page1│──────────────────→│ frame 2     │─┐   │      │
│ page2│──────────────────→│ (ディスク)   │ │   │      │ frame 2
│ page3│──────────────────→│ frame 8     │ │   │      │
└──────┘                  └─────────────┘ │   │      │
                                          │   │      │ frame 8
                                          └──→│      │
                                              └──────┘
```

### アドレス変換の流れ
1. CPU が仮想アドレスにアクセスしようとする
2. MMU（メモリ管理ユニット）がページテーブルを参照
3. 対応する物理フレームを見つけて、物理アドレスに変換
4. 物理メモリにアクセス

この変換はハードウェア（MMU）が行うので、プログラム側は仮想アドレスだけを意識すればよい。

---

## 5. ページフォールト

ページテーブルを引いた結果、そのページが物理メモリ上にない場合に発生する割り込み。

### 発生する場面
- **初めてアクセスするページ**: まだ物理フレームが割り当てられていない
- **スワップアウトされたページ**: メモリ不足でディスクに退避されている

### 処理の流れ
```
1. CPU が仮想アドレスにアクセス
2. MMU が「物理フレームがない」と判断 → ページフォールト発生
3. OS が割り込みを受け取る
4. OS がディスクからデータを読み込み、空きフレームに配置
5. ページテーブルを更新
6. 中断していた命令を再実行
```

### パフォーマンスへの影響
- ページフォールトはディスクアクセスを伴うため **非常に遅い**（RAM アクセスの数万倍以上）
- メモリ不足でページフォールトが頻発する状態を **スラッシング** と呼ぶ
- スラッシングが起きると、CPU はほぼ仕事をせず I/O 待ちになり、システムが極端に遅くなる

---

## 6. スワップ（Swap）

物理メモリが不足したとき、使用頻度の低いページをディスクに一時退避する仕組み。

```
物理メモリ（RAM）           スワップ領域（ディスク）
┌──────────────────┐      ┌──────────────────┐
│ [使用中] pageA   │      │ [退避] pageX     │
│ [使用中] pageB   │      │ [退避] pageY     │
│ [使用中] pageC   │      │                  │
│ ← 空きなし！     │      │                  │
└──────────────────┘      └──────────────────┘

→ あまり使われていない pageA をディスクに退避（スワップアウト）
→ 新しく必要な pageD を物理メモリに読み込み
```

- Linux では `swap` パーティションまたはスワップファイル
- Windows では「ページファイル」（`pagefile.sys`）
- スワップが多すぎる＝メモリ不足のサイン → RAM の増設を検討

## 7. TLB（Translation Lookaside Buffer）

毎回ページテーブルを引くのは遅いので、**最近変換したアドレスをキャッシュ**する仕組み。

```
CPU → TLB にキャッシュあり？ → あり（TLBヒット）→ すぐに物理アドレス取得
                             → なし（TLBミス）→ ページテーブルを引く → TLB に登録
```

- TLB はハードウェアで実装された高速なキャッシュ
- TLB ヒット率が高いほどメモリアクセスが速い
- コンテキストスイッチ（プロセス切り替え）時に TLB がフラッシュ（クリア）されるのが性能低下の一因

## 8. メモリ保護

仮想メモリの重要な恩恵のひとつが **メモリ保護**。

### 仕組み
ページテーブルの各エントリには、アドレス変換だけでなく **権限情報** が含まれる。

| フラグ | 意味 |
|---|---|
| **Read** | 読み取り可能 |
| **Write** | 書き込み可能 |
| **Execute** | 実行可能 |
| **User/Kernel** | ユーザーモードでアクセス可能か |

### 具体例
- **テキスト領域**: Read + Execute（書き込み不可 → コード改ざん防止）
- **スタック**: Read + Write（実行不可 → バッファオーバーフロー攻撃対策）
- **カーネル空間**: Kernel のみ（ユーザープログラムはアクセス不可）

権限違反が起きると **セグメンテーションフォールト（Segmentation Fault）** が発生してプロセスが強制終了する。

---

## 9. 開発者として知っておくべきこと

1. **メモリリーク**: ヒープに確保したメモリを解放し忘れると、使えるメモリがどんどん減る。GC のある言語（JavaScript, Python, Go）でも参照が残っていればリークする
2. **スタックオーバーフロー**: 再帰が深すぎるとスタック領域を使い切る → `StackOverflowError`
3. **OOM（Out of Memory）**: メモリを使い切ると OS がプロセスを強制終了する（Linux の OOM Killer）
4. **64bit vs 32bit**: 32bit OS は仮想アドレス空間が最大 4GB（2^32）。64bit なら理論上 16EB（2^64）で事実上無制限
