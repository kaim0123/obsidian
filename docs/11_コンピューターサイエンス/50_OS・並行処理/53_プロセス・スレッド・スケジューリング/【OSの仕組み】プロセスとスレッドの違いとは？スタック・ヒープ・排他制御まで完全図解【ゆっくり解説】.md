## 詳しい要約

Chrome が **32 個ものプロセス** を立ち上げるのはバグではなく、**マルチプロセスアーキテクチャ** による意図的な設計である——タブや拡張機能ごとにプロセスを分離することで、**1 つがクラッシュしても他は無事** という **セキュリティと安定性** を確保している。本動画は、この「プロセス分離」の仕組みを起点に、**プロセスの定義・メモリ構造・OS による管理・スケジューリング・プロセス間通信（IPC）・スレッドとの違い** までを、霊夢と魔理沙の対話形式で初心者向けに徹底解説する。

### プロセスとは——プログラムとの違い

- **プログラム** は設計図、**プロセス** はその設計図を使って **実際に動いている状態**。
- 例：Excel のプログラムファイルが 1 つでも、3 つ開けば **3 つのプロセス** が生まれる（同じ設計図から 3 棟建てるイメージ）。
- 各プロセスには **PID（Process ID）** という固有の番号が振られ、OS がプロセスを特定するための「背番号」として使う。
- 各プロセスは **自分専用のメモリ空間** を持つ——他のプロセスとは完全に隔離されている。

### 仮想アドレス空間と MMU

- プロセスが持つ専用メモリ空間を **仮想アドレス空間** と呼ぶ。「仮想」は偽物という意味ではなく、**自分専用に見える** という意味。
- 例え：ホテルの部屋——各部屋は独立しているように見えるが、実際の建物（物理メモリ）は共有している。
- この仕組みを **仮想メモリシステム** と呼ぶ。仮想アドレスから物理アドレスへの変換は **MMU（Memory Management Unit）** が担当する。
- MMU はホテルのフロントのようなもの——「302 号室」を実際の「3 階右端の部屋」に変換する。

### プロセスのメモリ構造——5 つのセグメント

プロセスのメモリ空間は大きく **5 つの部屋** に分かれる。

| セグメント | 内容 | 特徴 |
|-----------|------|------|
| **テキストセグメント** | プログラムの命令（機械語） | **読み取り専用**。実行中に変更されない |
| **データセグメント** | 初期値が決まっている固定データ（グローバル変数など） | プログラムファイルに含まれる |
| **BSS セグメント** | まだ中身が空の変数用領域（Block Started by Symbol） | ファイルに保存不要 → **ファイルサイズを小さく** できる |
| **ヒープ** | 実行中に動的に確保するメモリ（`malloc` / `new` 等） | **下から上** に成長。使い終わったら `free` / `delete` で解放しないと **メモリリーク** |
| **スタック** | 関数呼び出し時の情報（リターンアドレス・ローカル変数など） | **上から下** に成長。**LIFO（後入れ先出し）**。通常 **8 MB 程度** のサイズ制限あり |

- ヒープとスタックは **反対方向に成長** する。衝突したり OS の制限に達すると **スタックオーバーフロー** が発生し、プログラムがクラッシュする原因の 1 つになる。

### PCB（プロセス制御ブロック）——OS の管理台帳

OS がプロセスを管理するための **超詳しい履歴書** が **PCB（Process Control Block）**。Linux では **task_struct** として実装され、100 項目以上の巨大なデータ構造。

| 項目 | 内容 |
|------|------|
| **プロセスの状態** | 実行中・待機中・準備 OK など（人間で言えば働いている・休憩中・待機中） |
| **プログラムカウンター（PC）** | 今どこまで処理が進んでいるか。本のしおりのようなもの——一時停止しても続きから再開できる |
| **CPU レジスタの内容** | プロセス切り替え時に保存・復元する。これをまとめて **コンテキスト** と呼ぶ |
| **スケジューリング情報** | 優先度、**nice 値**（−20〜19。数字が小さいほど「俺が優先」＝親切ではない） |
| **メモリ管理情報** | 5 つのセグメントの位置（地図）。**ページテーブル**（仮想→物理アドレスの変換辞書）も含む |
| **ファイルディスクリプタテーブル** | 開いているファイルの一覧。標準入力=0、標準出力=1、標準エラー=2 |
| **親プロセス ID・子プロセスのリスト** | プロセスの家系図 |

### プロセスのライフサイクル——5 つの状態

プロセスは生まれてから死ぬまで、主に **5 つの状態** を経験する。

1. **新規（New）** — 生まれたばかりの赤ちゃん状態
2. **実行可能（Ready）** — 働く準備はできているが順番待ち（運動会のスタートライン）
3. **実行中（Running）** — 実際に CPU を使って処理中
4. **待機（Waiting/Blocked）** — ファイル読み込み・ネットワークデータ・シグナルなどを待っている
   - **割り込み可能待機**：起こしてもよい（昼寝中）
   - **割り込み不可能待機**：絶対起こすな（手術中）。ディスク書き込みなど重要な作業中
5. **終了（Terminated）** — 仕事を終えてゴール

### プロセスの生成——fork と copy-on-write

- Linux では **fork** システムコールでプロセスを生成する。親プロセスが **自分のコピー（子プロセス）** を作る。
- 完全コピーは無駄が多いため **copy-on-write（COW）** を使う——最初は同じメモリを共有し、**どちらかが書き換えようとした時だけコピー** する（教科書を読むだけなら 1 冊で十分、書き込む人だけコピーを作る）。
- fork 後、子プロセスは **exec** で別のプログラムに「変身」することが多い。
- 例：シェルが `ls` を実行する流れ → **fork** でコピーを作る → コピーが **exec** で `ls` プログラムに変身 → `ls` 終了後、親は **wait** で待機。

### スケジューラ——CPU を誰に使わせるか

**スケジューラ** はどのプロセスに CPU を使わせるかを決める管理者（学校の先生が生徒を指名するイメージ）。

| 方式 | 内容 | 問題点 |
|------|------|--------|
| **先着順（FCFS）** | 早く来た人から順番 | 長いジョブが先だと後ろが **飢餓（starvation）** |
| **最短ジョブ優先（SJF）** | 早く終わる仕事を優先 | 長いジョブが永遠に実行されないことがある |
| **ラウンドロビン（RR）** | 全員に少しずつ時間を割り当て（例：各 10 ms） | 公平。実用的で人気 |
| **優先度ベース** | 重要な仕事を優先（VIP 待遇） | VIP ばかりだと一般が飢餓 → **エージング** で待ち時間が長いプロセスの優先度を上げる |

- 各プロセスに割り当てる時間を **タイムクオンタム（タイムスライス）** と呼ぶ。時間切れで強制的に次のプロセスへ切り替えることを **プリエンプション（先取り）** と呼ぶ。
- Linux の **CFS（Completely Fair Scheduler）** は **仮想実行時間** が最も少ないプロセスを次に実行し、全プロセスの実行時間を均等に保つ。

### コンテキストスイッチ——プロセス切り替えの手順とコスト

プロセスを切り替える作業が **コンテキストスイッチ**（料理の途中で電話に出て、また料理に戻るイメージ）。

1. **現在のプロセスの状態を PCB に保存**（CPU レジスタ・プログラムカウンターなど）
2. **次に実行するプロセスをスケジューラが選択**
3. **次のプロセスの状態を CPU に復元**
4. **メモリマップの切り替え**（ページテーブルの変更。ホテルの部屋を 302 号室から 405 号室へ）

- 所要時間はおおよそ **数 μs〜数十 μs**。短いが CPU から見れば無駄な時間であり、頻繁に切り替えると性能が落ちる（**オーバーヘッド**）。
- プロセスが変わると **TLB（Translation Lookaside Buffer）**——よく使うアドレス変換のキャッシュ——がクリアされ、再構築のコストも大きい。
- それでもこれがないと **マルチタスク**（複数のことを同時にやっているように見える状態）は実現できない。実際は超高速で切り替えているだけ。

### IPC（プロセス間通信）——独立したプロセスの協力

プロセスは独立しているが、協力したい場面もある（動画編集ソフトがプレイヤーにデータを渡すなど）。**IPC（Inter-Process Communication）** には複数の方式がある。

| 方式 | イメージ | 特徴 |
|------|---------|------|
| **パイプ（Pipe）** | 水道管 | 一方通行。`ls \| grep text` のようにコマンド出力を次のコマンドへ渡す |
| **メッセージキュー** | 郵便ポスト | プロセス A がメッセージを投函し、プロセス B が順番に取り出す |
| **共有メモリ** | 共同作業スペース | **最速**。複数プロセスが同じメモリ領域にアクセスできるが、同時書き込みで **競合状態（レースコンディション）** が起きうる |
| **ソケット** | 電話 | ネットワーク通信の基本。同じマシン内でも使える |
| **シグナル** | 合図 | Ctrl+C → **SIGINT**、終了依頼 → **SIGTERM**、強制終了 → **SIGKILL** など |

- 共有メモリでは **ミューテックス（mutex）** や **セマフォ** で交通整理する。**ミューテックス** は「1 人ずつ入ってね」の札（トイレの使用中サイン）。**相互排他（mutual exclusion）** を実現する。

### スレッド——プロセス内の作業員

- **スレッド** はプロセスの中で動く **小さな作業員**（プロセス＝会社、スレッド＝社員）。
- 1 つのプロセスは **複数のスレッド** を持てる（動画編集ソフトが 4 スレッドで 4 作業を同時実行など）。
- 同じプロセス内のスレッドは **メモリを共有** できる（同じオフィス・同じ資料）。**スタックだけは各スレッドが独自に持つ**（個人のメモ帳）。

| | **プロセス** | **スレッド** |
|---|-------------|-------------|
| メモリ空間 | 完全に独立（別会社） | 共有（同じ会社） |
| コンテキストスイッチ | 遅い（メモリマップ切り替えが必要） | **速い**（担当者が変わるだけ） |
| データ共有 | IPC が必要 | グローバル変数に直接アクセス可能 |
| 生成コスト | 高い | **低い** |
| クラッシュの影響 | 1 つが落ちても他は無事 | **1 つが落ちるとプロセス全体が道連れ** になりやすい |
| 競合状態 | 起きにくい（隔離されている） | **起きやすい**（ミューテックスが必要） |

- Chrome が **プロセス分離** を採用するのは、スレッドより **安全性を優先** しているため。

### プロセスの親子関係とゾンビ・孤児

- プロセスは **fork** で他のプロセスを作れる。作った方が **親**、作られた方が **子**。
- fork の戻り値で親子を判別——親には **子の PID**、子には **0** が返る。
- 子は **PPID（親プロセス ID）** を知っている。全プロセスは **init プロセス（PID 1）** から派生する木構造。
- **ゾンビプロセス**：子が終了しても、親が **wait** で終了報告を受け取るまで PCB の一部が残る状態。「成仏していない」プロセス。
- **孤児プロセス**：親が先に死んだ子。init プロセスが養子として引き取る。

### Unix の基本——fork + exec

プログラム実行の基本パターンは **fork と exec の組み合わせ**。

1. シェルが **fork** で子プロセスを作る
2. 子プロセスが **exec** で目的のプログラムに変身する
3. 子が終了したら、親が **wait** で待機・回収する

これが Unix/Linux における **プログラム実行の標準的な流れ** である。

### まとめ

- **プロセス** ＝ 実行中のプログラム ＋ 専用の仮想メモリ空間（ホテルの部屋）
- **メモリ** ＝ テキスト・データ・BSS・ヒープ（下から上）・スタック（上から下）の 5 セグメント
- **PCB** で OS がプロセスを管理。5 つの状態を遷移する
- **スケジューラ** が CPU を割り当て、**コンテキストスイッチ** で切り替え（オーバーヘッドあり）
- **IPC** でプロセス間協力。共有メモリは速いが排他制御が必要
- **スレッド** はプロセス内の軽量な実行単位。速いが安全性はプロセスに劣る
- **Chrome のマルチプロセス** は、このプロセス分離のメリットを最大限活用した設計

`top` コマンドやタスクマネージャーで実際のプロセスを確認すると、OS がどれだけ賢く管理しているかが実感できる。
