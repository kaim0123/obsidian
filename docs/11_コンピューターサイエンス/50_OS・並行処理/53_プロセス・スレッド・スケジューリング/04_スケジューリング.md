# スケジューリング

CPU は 1 つのコアで同時に実行できるプロセス/スレッドは 1 つだけ。
しかし実際には何十ものプロセスが「同時に動いている」ように見える。
これを実現するのが **OS のスケジューラ** による CPU 時間の配分である。

---

## 1. スケジューリングとは

### 一言でいうと
> **「次にどのプロセス（スレッド）に CPU を使わせるか」を決める仕組み**

OS カーネルの中にある **スケジューラ** が、実行可能な（Ready状態の）プロセスの中から次に実行するものを選ぶ。

### なぜ必要か
- CPU の数は限られている（例: 4コア8スレッド）
- 実行したいプロセスは数十〜数百ある
- 公平に CPU を分配しないと、一部のプロセスが永遠に実行されない（飢餓状態）

---

## 2. プリエンプティブ vs 協調的（ノンプリエンプティブ）

スケジューリングには大きく 2 つの方式がある。

### プリエンプティブ（Preemptive）
> **OS がプロセスを強制的に中断し、別のプロセスに CPU を渡す**

- 現代のほぼすべての汎用 OS はこの方式
- タイマー割り込みにより、一定時間（タイムスライス）が経過したら強制的に切り替える
- 1 つのプロセスが CPU を独占できない → 公平

```
時間 →
CPU: [プロセスA][プロセスB][プロセスA][プロセスC][プロセスB]...
      ←10ms→  ←10ms→   ←10ms→   ←10ms→   ←10ms→
      ↑ タイマー割り込みで強制切り替え
```

### 協調的（Cooperative / Non-preemptive）
> **プロセスが自発的に CPU を明け渡すまで、他のプロセスは実行できない**

- 古い OS（Windows 3.1, 初期 Mac OS）で使われていた
- 行儀の悪いプログラムが CPU を手放さないとシステム全体がフリーズする

### 比較

| 観点 | プリエンプティブ | 協調的 |
|---|---|---|
| CPU独占 | できない（OS が強制切り替え） | できてしまう |
| 応答性 | 高い | 低い（行儀の悪いプロセス次第） |
| 実装の複雑さ | 高い | 低い |
| 使用例 | Linux, Windows, macOS | Windows 3.1, 一部の組み込み |

## 3. 代表的なスケジューリングアルゴリズム

### FCFS（First Come, First Served）
**先着順**。キューに並んだ順に実行する。

```
到着順: P1(24ms) → P2(3ms) → P3(3ms)

実行順: [──── P1 (24ms) ────][P2(3ms)][P3(3ms)]

P2, P3 は P1 が終わるまで待たされる（コンボイ効果）
```

- 実装が簡単
- **短いジョブが長いジョブの後ろで待たされる**（コンボイ効果）

### SJF（Shortest Job First）
**実行時間が短いジョブを優先**する。

```
P1(24ms), P2(3ms), P3(3ms)

実行順: [P2(3ms)][P3(3ms)][──── P1 (24ms) ────]

平均待ち時間が最小になる（理論上最適）
```

- 平均待ち時間が最小になることが証明されている
- **問題**: 実行時間を事前に知る必要がある → 実際には予測に頼る
- 長いジョブが永遠に実行されない可能性（飢餓状態）

### ラウンドロビン（Round Robin）
**全員に均等に CPU 時間（タイムスライス/クォンタム）を配る**。

```
タイムスライス = 4ms
P1(24ms), P2(3ms), P3(3ms)

実行順: [P1(4ms)][P2(3ms)][P3(3ms)][P1(4ms)][P1(4ms)]...
```

- 公平でレスポンスが良い
- タイムスライスの設定が重要
  - 短すぎる → コンテキストスイッチのオーバーヘッドが大きい
  - 長すぎる → FCFS と変わらない
- 現代 OS の基本形

### 優先度スケジューリング
**各プロセスに優先度を割り当て、高い優先度のものを先に実行**する。

```
P1(優先度3), P2(優先度1), P3(優先度2)  ※数字が小さい方が高優先度

実行順: [P2(優先度1)][P3(優先度2)][P1(優先度3)]
```

- **問題**: 低優先度のプロセスが永遠に実行されない（飢餓状態）
- **対策**: エイジング — 長く待っているプロセスの優先度を徐々に上げる

### マルチレベルキュー
優先度ごとにキューを分け、キュー間で異なるアルゴリズムを適用する。

```
キュー1（高優先度）: リアルタイムプロセス → FCFS
キュー2（中優先度）: インタラクティブ     → ラウンドロビン（短いスライス）
キュー3（低優先度）: バッチ処理          → ラウンドロビン（長いスライス）

上のキューが空でない限り、下のキューは実行されない
```

### マルチレベルフィードバックキュー
マルチレベルキューの発展形。**プロセスがキュー間を移動**できる。

```
Q1 [タイムスライス 8ms]  → 使い切ったら Q2 に降格
Q2 [タイムスライス 16ms] → 使い切ったら Q3 に降格
Q3 [FCFS]               → 最低優先度

新しいプロセスは Q1 から開始
I/O で自発的に手放したプロセスは昇格（対話型と判断）
```

- CPU をあまり使わないプロセス（I/O バウンド）→ 高優先度に昇格 → 応答が良い
- CPU を長く使うプロセス（CPU バウンド）→ 低優先度に降格 → 他を邪魔しない
- **Linux の CFS（Completely Fair Scheduler）** は、この考え方を赤黒木で効率的に実装したもの

## 4. コンテキストスイッチ

### 一言でいうと
> **CPU の「今の作業状態」を保存し、次のプロセスの状態を復元する操作**

### 保存・復元する情報（コンテキスト）
- プログラムカウンタ（次の命令の位置）
- CPU レジスタの値
- スタックポインタ
- ページテーブルのベースアドレス
- その他のプロセス状態情報

### コスト
- コンテキストスイッチ自体は **数マイクロ秒** で終わる
- しかし**間接的なコスト**が大きい:
  - TLB（アドレス変換キャッシュ）のフラッシュ
  - CPU キャッシュ（L1/L2/L3）のミス率上昇
  - パイプラインのフラッシュ
- プロセス間の切り替えはスレッド間より重い（メモリ空間が異なるため）

## 5. CPU バウンド vs I/O バウンド

スケジューラはプロセスの性質に応じて扱いを変える。

| 種類 | 特徴 | 例 |
|---|---|---|
| **CPU バウンド** | 計算が主。CPU をずっと使い続ける | 動画エンコード、科学計算、暗号処理 |
| **I/O バウンド** | 入出力待ちが主。CPU はあまり使わない | Web サーバー、テキストエディタ、DB クエリ |

スケジューラは一般的に I/O バウンドプロセスを優先する:
- I/O バウンドはすぐに CPU を手放すので、他への影響が小さい
- ユーザーが直接操作するアプリ（エディタ、ブラウザ）は I/O バウンドが多く、応答性が重要

---

## 6. リアルタイムスケジューリング

### 普通の OS との違い
リアルタイムシステムでは「期限（デッドライン）」を守ることが最優先。

| 種類 | 説明 | 例 |
|---|---|---|
| **ハードリアルタイム** | デッドラインを 1 回でも超えると致命的 | エアバッグ制御、ペースメーカー |
| **ソフトリアルタイム** | デッドラインを超えても品質低下で済む | 動画ストリーミング、ゲーム |

Linux にはリアルタイムスケジューリングポリシー（`SCHED_FIFO`, `SCHED_RR`）がある。

---

## 7. 開発者として知っておくべきこと

1. **プロセスの優先度を変える**: Linux の `nice` / `renice` コマンド、Windows のタスクマネージャーで優先度変更
2. **CPU を占有しない**: 無限ループで CPU を回し続けるコードは他のプロセスに影響する。`sleep` や I/O 待ちを適切に入れる
3. **スレッド数 ≠ 速さ**: スレッドを増やしすぎるとコンテキストスイッチのオーバーヘッドで逆に遅くなる
4. **Node.js のイベントループ**: シングルスレッドで I/O バウンドな処理を効率的に捌くのは、スケジューリングのオーバーヘッドを避ける設計
5. **`top` / `htop` コマンド**: CPU 使用率を見て、プロセスが CPU バウンドか I/O バウンドか判断できる
