# 並行性と並列性

## 用語の違い
似た言葉ですが**厳密には別物**です。

- **並行性（Concurrency）**: 複数のタスクを**同時期に扱う**（実際に同時実行とは限らない）
- **並列性（Parallelism）**: 複数のタスクを**物理的に同時実行**する

日常の例:
- 並行性 = 1人のシェフが複数料理を手際よく切り替えて作る
- 並列性 = 複数のシェフがそれぞれ別の料理を同時に作る

## 図でイメージ

### 並行（1コアで時分割）
```
CPU: AAAA  BBBB  AAAA  CCCC  BBBB
時間: →
```

### 並列（複数コアで同時）
```
コア1: AAAAAAAA
コア2: BBBBBBBB
コア3: CCCCCCCC
時間: →
```

## 並行性がなぜ必要か
- **応答性**: UIが固まらない、I/O待ちで止まらない
- **スループット**: I/O待ちの間に別のタスクを進められる
- **構造的な整理**: 独立した作業を独立して書ける

## 並列性がなぜ必要か
- **速度**: CPUコア数に応じて処理時間を短縮
- **スケール**: 大量データを分割処理

## 並行性の実現方法

### ① プロセス
OSレベルで完全に分離。メモリ空間も別。
- 堅牢だが重い
- プロセス間通信（IPC）が必要

### ② スレッド
同じプロセス内でメモリを共有する軽量な実行単位。
- 切替が速い
- 共有メモリ経由で通信
- 排他制御が必要

### ③ 非同期（イベントループ）
単一スレッドで I/O 待ち中に別タスクを処理。
- Node.js, Python asyncio, ブラウザJS
- 軽量・メモリ消費小
- CPUバウンドには不向き

### ④ コルーチン / 軽量スレッド
ユーザーレベルで切替する超軽量スレッド。
- Go の goroutine
- Kotlin コルーチン
- Erlang プロセス

## 並列性の実現方法

### ① マルチコアCPU
物理コアで並列実行。

### ② SIMD（ベクトル化）
1命令で複数データを同時処理（AVX等）。

### ③ GPU
数千コアで大規模並列。機械学習・画像処理に強い。

### ④ 分散システム
複数マシンで分担。Hadoop, Spark, Kubernetes。

## 並行 vs 並列: 具体例

### Webサーバー
- **並行性が中心**: 多数のリクエストを応答良く捌く
- I/O待ちが多いのでスレッド or 非同期で十分

### 画像処理・ML
- **並列性が中心**: 巨大データをマルチコア/GPUで処理

### UI + バックグラウンド作業
- **並行性**: UIを固めずバックグラウンドで実行
- 重い計算は**別スレッドで並列**にすることも

## CPUバウンド vs I/Oバウンド

### CPUバウンド
CPU計算が支配的（動画変換、暗号化、ML）。
- 並列化で速くなる
- マルチスレッド・マルチプロセス・GPU

### I/Oバウンド
I/O待ちが支配的（DB、ネットワーク、ファイル）。
- 非同期で効率化
- スレッドより少ないリソースで大量さばける

## GIL（グローバルインタプリタロック）
PythonやRubyは**1プロセス内で同時にバイトコードを実行するスレッドが1つ**という制約あり。
- I/O待ち中は解放されるので並行I/Oは有効
- CPU並列化にはマルチプロセスが必要

## モデル別まとめ

| モデル | 並行 | 並列 | 代表例 |
|---|---|---|---|
| プロセス | ○ | ○ | OSレベル、Pythonの multiprocessing |
| スレッド | ○ | ○（Python除く） | Java, C#, C++ |
| 非同期/イベントループ | ○ | × | Node.js, asyncio |
| コルーチン | ○ | △（ランタイム次第） | Go, Kotlin, Erlang |
| データ並列 | × | ○ | SIMD, GPU |
| 分散 | ○ | ○ | Hadoop, K8s |

## 実例: 10000件のAPI呼び出し

### シーケンシャル（1件ずつ）
```
合計時間 = 各API時間の合計
```

### 並行（非同期 / async）
```javascript
await Promise.all(ids.map(id => fetch(`/api/${id}`)));
```
I/O待ちがオーバーラップして大幅短縮。

### 並列（マルチスレッド）
CPU処理が重いなら、複数スレッドで分担すると速い。I/Oメインなら並行で十分。

## Amdahlの法則
並列化できない部分がある限り、いくらコアを増やしても速度には限界がある。
```
最大加速 = 1 / (S + P/N)
  S: 並列化できない割合
  P: 並列化できる割合
  N: コア数
```
例: 10%が直列なら、コアを∞にしても最大10倍止まり。

## 設計の指針

### 1. まず「何がボトルネックか」を測る
- I/O待ちが多い → 非同期/スレッド並行
- CPU計算が多い → マルチプロセス/GPU

### 2. 共有状態を減らす
不変データ、メッセージパッシング、純粋関数で並行バグを予防。

### 3. 並列化の粒度に注意
細かすぎると切替コストが上回る。

### 4. 監視・可視化
並行バグは再現困難。ログとメトリクスを仕込んでおく。

## まとめ
- **並行性 = 扱う**、**並列性 = 同時実行**
- 並行性は応答性・構造化、並列性は速度・スループット
- I/Oバウンドは非同期、CPUバウンドは並列化が基本
- Amdahlの法則の通り**直列部分が上限**を決める
- 共有状態を減らす設計が並行バグの最良の予防策
