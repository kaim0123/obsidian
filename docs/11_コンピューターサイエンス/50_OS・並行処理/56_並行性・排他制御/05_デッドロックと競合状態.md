# デッドロックと競合状態

## 並行プログラミングの代表的バグ
並行処理特有の厄介なバグがいくつかあります。
- **競合状態（Race Condition）**: 実行順序でアプリ状態が壊れる
- **デッドロック（Deadlock）**: 互いに待ち合って永久に動かない
- **ライブロック（Livelock）**: 動いているが進まない
- **スタベーション（Starvation）**: 特定のスレッドだけ永久に待たされる

## 競合状態（Race Condition）

### 発生の仕組み
同じデータへのアクセスが**実行タイミングで結果が変わる**状態。

### 例: カウンタ
```java
counter = counter + 1;
```
内部で「読む → 加算 → 書く」の3ステップ。同時に2スレッドで走ると更新が消える。

### ロストアップデート
```
時刻  Thread A     Thread B
 1    読む(0)
 2                読む(0)
 3    +1 → 書く(1)
 4                +1 → 書く(1)   ← 2になるはずが1
```

### チェック後アクション（TOCTOU: Time-Of-Check-Time-Of-Use）
```javascript
if (!exists(file)) create(file);   // 2スレッドが同時に通ると両方createしてしまう
```

### 対策
- ミューテックス、アトミック操作
- CAS（Compare-And-Swap）
- トランザクション
- イミュータブルデータ

## デッドロック（Deadlock）

### 定義
複数のスレッドが**互いに相手のロックを待ち**、全員が動けなくなる状態。

### 典型例
```
Thread A: lock(X) → lock(Y) を待つ
Thread B: lock(Y) → lock(X) を待つ
         └──── 永久に止まる ────┘
```

### コード例
```java
// Thread A
synchronized (lockA) {
    synchronized (lockB) { ... }
}

// Thread B
synchronized (lockB) {
    synchronized (lockA) { ... }
}
```

## デッドロック発生の4条件（Coffman条件）
以下**すべてが同時に成立**するとデッドロックが発生しうる。
1. **相互排除**: リソースを1つずつしか使えない
2. **保持と待機**: リソース保持中に別リソースを要求
3. **非横取り（奪取不可）**: 他者から強制的に取れない
4. **循環待ち**: 待ちが循環している

1つでも崩せば発生しない。

## デッドロックの予防

### ① ロック順序の統一
```java
// 常にIDが小さい順にロック
Account first  = a.id < b.id ? a : b;
Account second = a.id < b.id ? b : a;
synchronized (first) {
    synchronized (second) { ... }
}
```

### ② タイムアウト付きロック
```java
if (lock.tryLock(1, TimeUnit.SECONDS)) {
    try { ... } finally { lock.unlock(); }
} else {
    // 取得失敗、他の処理
}
```

### ③ ロックを持つ時間を短く
重い処理中にロックを握ったまま他のロックを取ろうとしない。

### ④ ロックの階層化
上位→下位の一方向に限定。

### ⑤ メッセージパッシングに切替
共有メモリではなく**チャネル**でやり取り。

## デッドロックの検出と回復

### 検出
- スレッドダンプ（Javaの `jstack`、`kill -3`）
- 待ち合わせグラフを描画
- タイムアウトでハング判定

### 回復
- プロセス再起動
- ロックの強制解放（困難）
- 該当スレッドの停止

## ライブロック（Livelock）
両方が**譲り合って**永久に進まない状態。
```
A: ロック失敗 → 待機 → 再試行
B: ロック失敗 → 待機 → 再試行
（お互い止まってない、でも前進しない）
```

### 対策
- ランダム化した待機時間（例: jitter）
- 優先度設定
- 順序付けされたアクセス

## スタベーション（Starvation）
特定のスレッドだけロックを取れず**永久に待たされる**状態。
- 常に優先度の高いスレッドに取られる
- アンフェアロックで運が悪い

### 対策
- フェアロック（順番保証）
- 公平なスケジューリング

## 競合状態のデバッグは難しい

### 理由
- 再現性が低い
- タイミング依存
- 環境（CPU数・負荷）で変わる

### 有効なツール
- Go: `go run -race`
- Java: ThreadSanitizer、JStack、FindBugs
- Rust: そもそも静的に防ぐ（所有権）
- C/C++: Helgrind、ThreadSanitizer

### ログのタイムスタンプ
ミリ秒・ナノ秒付きログで順序を追う。

## 関連バグ: ABA問題
CAS操作で「値が A → B → A と戻った」ケースを「変わってない」と誤判定する。ロックフリーアルゴリズムで注意。
### 対策
バージョン番号付きの値（AtomicStampedReference）や、ハザードポインタ。

## 予防的な設計指針

### 共有状態を最小化
- スレッドローカル
- イミュータブル
- メッセージパッシング

### 高水準ツールを使う
- 並行データ構造（`ConcurrentHashMap`）
- アクターモデル（Erlang, Akka）
- `async/await` + チャネル（Go, Rust, Kotlin）

### 境界を明確に
共有する部分と共有しない部分をはっきり分ける。

### テストで追い込む
- 負荷テスト
- ファズテスト
- 同時アクセスシミュレーション

## 実例: TOCTOUとその解決

### ❌ 危険
```python
if not os.path.exists(path):
    open(path, "w").write("hello")
# 2プロセスが同時実行すると両方が作る
```

### ✅ アトミックな作成
```python
with open(path, "x") as f:   # 存在すればエラー
    f.write("hello")
```

### データベース例
- **楽観ロック**: バージョン列で更新時にチェック
- **悲観ロック**: `SELECT FOR UPDATE` で行ロック

## 並行性バグのまとめ表

| バグ | 症状 | 主な原因 | 対策 |
|---|---|---|---|
| 競合状態 | 壊れた状態 | 共有データの不同期アクセス | ロック、アトミック、不変 |
| デッドロック | 永久停止 | ロック順序の循環 | 順序統一、タイムアウト |
| ライブロック | 進まない動き | 無限な譲り合い | ランダム化、優先度 |
| スタベーション | 待ち続ける | 不公平なスケジュール | フェアロック |

## まとめ
- **競合状態**はタイミングで壊れるバグ、ロックやアトミック操作で防ぐ
- **デッドロック**は相互待ちで停止、Coffmanの4条件を崩すのが予防
- **ライブロック/スタベーション**も並行特有のハング
- 共有状態を減らし、**メッセージパッシング**や**不変性**を設計で活用
- 並行バグは再現困難、**ツール・負荷テスト・ログ**で追い込む
