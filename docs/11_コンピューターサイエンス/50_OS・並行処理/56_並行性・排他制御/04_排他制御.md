# 排他制御

## 排他制御とは
複数のスレッドが**同じデータに同時アクセス**して壊さないようにする仕組みです。「一度に1人だけ入れる」「書き込み中は読めない」などのルールを設けます。

## なぜ必要か: データ競合の例

### カウンタのインクリメント
```java
counter = counter + 1;   // 一見アトミックに見える
```
実際は内部で
1. counter を読む
2. +1 する
3. 書き戻す
の3ステップ。複数スレッドで実行すると
```
Thread A: 読む(0) → +1 → 書く(1)
Thread B: 読む(0) → +1 → 書く(1)
```
結果が1になる（本来は2）**ロストアップデート**が起きる。

## 排他制御の基本手段

### 1. ミューテックス（Mutex）
**相互排除（Mutual Exclusion）**のためのロック。一度に1スレッドしか保持できない。

```java
Lock lock = new ReentrantLock();
lock.lock();
try {
    counter++;
} finally {
    lock.unlock();
}
```

```python
import threading
mu = threading.Lock()
with mu:
    counter += 1
```

```rust
let m = Mutex::new(0);
{
    let mut num = m.lock().unwrap();
    *num += 1;
}  // スコープを抜けると自動unlock
```

### 2. 同期化メソッド/ブロック（Java）
```java
synchronized (sharedObj) {
    sharedObj.value++;
}

public synchronized void increment() {
    value++;
}
```

### 3. セマフォ（Semaphore）
**N個まで同時に通す**カウンタ付きロック。
```java
Semaphore sem = new Semaphore(3);   // 最大3並行
sem.acquire();
try {
    doWork();
} finally {
    sem.release();
}
```
用途: DBコネクションプール、同時実行数の制限。

### 4. リードライトロック
- 読み取りは複数同時OK
- 書き込みは排他
```java
ReadWriteLock rwLock = new ReentrantReadWriteLock();
rwLock.readLock().lock();    // 読みは並行
rwLock.writeLock().lock();   // 書きは独占
```
読み多書き少のシナリオに有効。

### 5. 条件変数 / モニター
特定の条件を満たすまで待つ。
```java
synchronized (lock) {
    while (!condition) lock.wait();
    // 処理
    lock.notifyAll();
}
```

### 6. スピンロック
ロック取得できるまで**ループで待ち続ける**。切替コストがないので超短時間の排他向き。長時間だとCPUを浪費する。

## アトミック操作
ロックなしでスレッドセーフな操作。CPU命令（CAS: Compare-And-Swap）で実現。
```java
AtomicInteger counter = new AtomicInteger(0);
counter.incrementAndGet();
```

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
let c = AtomicUsize::new(0);
c.fetch_add(1, Ordering::SeqCst);
```

軽量だが、複雑な操作には不向き。

## 並行データ構造
標準ライブラリに**初めからスレッドセーフ**な型がある。

### Java
- `ConcurrentHashMap`
- `CopyOnWriteArrayList`
- `BlockingQueue`

### Go
- `sync.Map`
- チャネル（メッセージパッシング）

### Rust
- `Arc<Mutex<T>>`
- `RwLock<T>`
- `mpsc::channel`

独自ロックより**既存のスレッドセーフな型**を使うのが安全。

## ロックの種類

### 再入可能（Reentrant）
同じスレッドが同じロックを何度もロックできる。
```java
ReentrantLock lock = new ReentrantLock();
lock.lock();
lock.lock();   // 同じスレッドなのでOK、unlock2回必要
```

### フェア / アンフェア
- **フェア**: 待った順にロックを渡す（スタベーションを防ぐが遅い）
- **アンフェア**: 順不同（高速だが長時間待たされるスレッドが出ることも）

## メモリモデルとvolatile
CPUはキャッシュや投機的実行で命令順を入れ替える。
**同期なしに共有変数を読むと古い値が見える**ことがある。

```java
volatile boolean stopFlag;   // 読み書きが他スレッドから見える
```
ロック、アトミック、volatileなどで**可視性**を保証する必要がある。

## 粒度の問題

### 粗すぎるロック
- 同時に何もできず並列性が生かせない
```java
synchronized (this) {  // 何でもかんでもロック
    ...
}
```

### 細かすぎるロック
- デッドロックやバグの温床

**バランス良く**、保護すべき最小範囲にロックを掛ける。

## 共有しない設計（一番安全）
排他制御が最も難しい。**そもそも共有しない**のが最良。
- スレッドローカル変数
- イミュータブルデータ
- メッセージパッシング

```rust
thread_local! {
    static COUNTER: RefCell<u32> = RefCell::new(0);
}
```

## 排他制御のベストプラクティス

### 1. 必要な最小範囲で
ロック保持時間は短く。I/O中はロックしない。

### 2. 順序を決める
複数ロックを取る時は**常に同じ順序**（デッドロック予防）。

### 3. try/finallyで必ず解放
Rustのように自動解放できない言語では特に。

### 4. 既存のスレッドセーフ型を使う
自前のロックより安全。

### 5. 共有を減らす
イミュータブルデータ、メッセージパッシング。

### 6. テストを工夫する
ストレステスト、並行バグ検出ツール（ThreadSanitizer, Go race detector）。

## 実例: 銀行口座

### ❌ 危険
```java
public void transfer(Account to, int amount) {
    this.balance -= amount;
    to.balance += amount;
}
```

### ✅ ロック
```java
public void transfer(Account to, int amount) {
    Account first = this.id < to.id ? this : to;
    Account second = this.id < to.id ? to : this;
    synchronized (first) {
        synchronized (second) {
            this.balance -= amount;
            to.balance += amount;
        }
    }
}
```
常にIDの小さい順にロック取得することでデッドロック回避。

## まとめ
- 排他制御は**共有データを同時アクセスから守る**仕組み
- ミューテックス、セマフォ、R/Wロック、アトミック、並行データ構造などがある
- **短く・順序を決め・共有を減らす**が基本原則
- 言語標準のスレッドセーフ型や**メッセージパッシング**は強力な代替
