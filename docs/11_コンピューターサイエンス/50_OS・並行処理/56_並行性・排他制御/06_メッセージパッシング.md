# メッセージパッシング

## メッセージパッシングとは
並行処理の通信方式の1つで、**共有メモリを使わずメッセージを送受信**してやり取りする方式です。"Don't communicate by sharing memory; share memory by communicating." — Goの格言。

### 共有メモリモデルとの違い
| 観点 | 共有メモリ | メッセージパッシング |
|---|---|---|
| データ共有 | 同じメモリに書き込む | メッセージを送受信 |
| 同期 | ロック・アトミック | キュー・チャネル |
| 競合状態の危険 | 高い | 低い |
| デバッグ | 難しい | 追いやすい |
| 通信コスト | 低い（直接） | 少し高い（コピー等） |

## 代表的な実装: チャネル（Channel）

### Go
```go
ch := make(chan int)
go func() { ch <- 42 }()    // 送信
val := <-ch                  // 受信
```

### Rust（mpsc）
```rust
let (tx, rx) = std::sync::mpsc::channel();
tx.send(42).unwrap();
let val = rx.recv().unwrap();
```

### Kotlin Coroutines
```kotlin
val channel = Channel<Int>()
launch { channel.send(42) }
val value = channel.receive()
```

## チャネルの種類

### 無バッファ（同期）
送信側は受信されるまでブロック。
```go
ch := make(chan int)    // バッファ0
ch <- 1                  // 誰かが受け取るまで止まる
```

### バッファ付き（非同期）
指定個数までは送信しても待たずに進める。
```go
ch := make(chan int, 10)
ch <- 1   // バッファ空きがあれば即返る
```

### 方向性付き
送信専用・受信専用に絞れる。
```go
func produce(out chan<- int) { out <- 1 }
func consume(in  <-chan int) { println(<-in) }
```

## メッセージパッシングの利点

### ① 競合状態が起きにくい
共有データがなければデータ競合は発生しない。

### ② コードが追いやすい
誰が誰にメッセージを送ったかが明示的。

### ③ 分散システムへ拡張しやすい
ローカルとネットワーク越しで同じモデルが使える（Erlang）。

### ④ デッドロックを構造的に減らせる
ロックの順序問題が起きにくい。

## パターン例

### Worker Poolパターン
```go
jobs := make(chan Job, 100)
results := make(chan Result, 100)

// ワーカー起動
for i := 0; i < 10; i++ {
    go worker(jobs, results)
}

// 仕事を投入
for _, j := range jobsToDo {
    jobs <- j
}
close(jobs)

// 結果を集約
for r := range results { handle(r) }
```

### Pipelineパターン
```go
stage1 -> stage2 -> stage3
```
各段がチャネルで連結され、ストリーム処理。

### Fan-out / Fan-in
- **Fan-out**: 1つの入力を複数ワーカーへ分配
- **Fan-in**: 複数ワーカーの結果を1つに集約

## アクターモデル
メッセージパッシングの代表的なパラダイム。各アクターは
- 自分の状態を持ち
- メッセージボックスを持ち
- メッセージを受けて反応し
- 他アクターへメッセージを送る

```
[Actor A] ── message ──→ [Actor B]
                     └→ [Actor C]
```

状態はアクター内部に閉じ込められ、直接アクセスできない（＝共有されない）。

### 代表的な実装
- **Erlang / Elixir**: プロセス単位
- **Akka（Scala/Java）**: JVMでのアクター実装
- **Pony**: 型システムで安全性強化
- **Orleans（.NET）**: 仮想アクター

### 特徴
- **耐障害性**: 片方が落ちても他は動き続ける
- **分散**: ネットワーク越しでも同じAPI
- **位置透過性**: アクターがどこにあるか意識せず通信

## CSPモデル（Communicating Sequential Processes）
Hoareが提案した理論モデル。Goのチャネルはここから来ている。
- 並行プロセスが存在
- チャネル経由で**同期的に通信**
- 共有変数なし

## メッセージパッシングの注意点

### ① バックプレッシャー
受信側が遅いと送信がブロック or メッセージが溜まる。バッファサイズやドロップ戦略が必要。

### ② メッセージの順序
複数チャネルから来るメッセージの順序は保証されないことも。

### ③ クローズ処理
送信側が閉じ、受信側がそれを検知する構造（Goの `close(ch)`）。

### ④ 停止とキャンセル
長時間動くワーカーを止めるには、キャンセルチャネルやコンテキストを使う。
```go
select {
case job := <-jobs: handle(job)
case <-ctx.Done(): return
}
```

### ⑤ デッドロックは完全には防げない
双方が同期的に相手を待つケースは残る。

### ⑥ 性能オーバーヘッド
大量の小さなメッセージは共有メモリより遅い場合がある。

## メッセージパッシング vs 共有メモリ

### 小さな並行処理（単一プロセス内、高頻度）
- 共有メモリ + ロックの方が速いことも
- アトミック変数の方が軽い

### 中〜大規模並行処理
- メッセージパッシングの方が保守しやすい
- 独立性・分散性に優れる

### 分散システム
- 実質メッセージパッシング一択
- gRPC、MQTT、Kafkaなども広義のメッセージパッシング

## 実例: Webサーバー

### Node.js
Worker Threadsやクラスタ間で `postMessage`。
```javascript
worker.postMessage({ task: "resize" });
worker.on("message", result => { ... });
```

### Go
HTTPハンドラが goroutine、DBアクセスは接続プールがチャネルで管理。

### Elixir/Phoenix
リクエストごとに軽量プロセス、アクターが処理。

## メッセージキュー（システム間）
アプリ全体で使う**分散版メッセージパッシング**。
- **RabbitMQ / ActiveMQ**: 汎用キュー
- **Kafka**: 高スループット・永続化ログ
- **AWS SQS / Pub/Sub**: マネージド
- **Redis Pub/Sub / Streams**: 軽量

これらは疎結合・非同期・可用性の高いアーキテクチャの基盤になります。

## Unixのパイプもメッセージパッシング
```bash
cat data.txt | grep error | wc -l
```
プロセス間をパイプ（≒チャネル）で連結する古典的な形。

## まとめ
- メッセージパッシングは**共有メモリを使わない並行通信**
- チャネル（Go/Rust/Kotlin）、アクター（Erlang/Akka）が代表
- 競合状態・デッドロックを**構造的に減らせる**
- バックプレッシャー・キャンセル・閉じ方に注意
- 小規模なら共有メモリも選択肢、**中〜大規模・分散では第一候補**
