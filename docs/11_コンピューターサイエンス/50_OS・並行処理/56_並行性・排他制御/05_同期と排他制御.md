# 同期と排他制御

複数のスレッド（やプロセス）が同じデータに同時にアクセスすると、データが壊れる危険がある。
これを防ぐための仕組みが **同期** と **排他制御** である。

---

## 1. なぜ排他制御が必要なのか

### 競合状態（Race Condition）の例

銀行口座の残高が 1000 円。スレッド A とスレッド B が同時に 500 円を引き出そうとする。

```
期待する動作:
  残高 1000 → A が引き出し → 残高 500 → B が引き出し → 残高 0

実際に起きうること（排他制御なし）:
  スレッドA: 残高を読む → 1000
  スレッドB: 残高を読む → 1000        ← A の書き込み前に読んでしまう
  スレッドA: 1000 - 500 = 500 を書き込む
  スレッドB: 1000 - 500 = 500 を書き込む  ← A の結果を上書き！

結果: 残高 500（本来 0 になるべき）→ 500円が憑りに出現
```

これが **競合状態（Race Condition）**。実行タイミングによって結果が変わるバグ。
再現性が低く、デバッグが非常に困難。

## 2. クリティカルセクション

### 一言でいうと
> **共有データにアクセスするコード領域のこと**

```
read(balance)       ← ┐
new = balance - 500    │ クリティカルセクション
write(new)          ← ┘ （この中に同時に 1 つのスレッドしか入れないようにする）
```

排他制御の目標は **「クリティカルセクションに同時に 1 つのスレッドしか入れない」** ことを保証すること。

### 正しい排他制御の 3 条件
1. **相互排他（Mutual Exclusion）**: 同時に 1 つだけが入れる
2. **進行（Progress）**: 入りたいスレッドがいるのに誰も入れない状態にならない
3. **有限待ち（Bounded Waiting）**: 永遠に待たされるスレッドがいない

---

## 3. ミューテックス（Mutex）

### 一言でいうと
> **「鍵付きの部屋」。鍵を持っている 1 人だけが中に入れる**

```
ミューテックス = 鍵

スレッドA:
  lock(mutex)        ← 鍵を取得（他の人は入れなくなる）
  // クリティカルセクション
  balance -= 500
  unlock(mutex)      ← 鍵を返却（他の人が入れるようになる）

スレッドB:
  lock(mutex)        ← A が鍵を持っている間はここで待つ（ブロック）
  balance -= 500
  unlock(mutex)
```

### 特徴
- **バイナリ（0 か 1）**: ロックされているか、されていないかの 2 状態
- **所有権がある**: ロックしたスレッドだけがアンロックできる
- 最も基本的で広く使われる排他制御

---

## 4. セマフォ（Semaphore）

### 一言でいうと
> **「カウンター付きの入場制限」。N 人まで同時に入れる**

```
セマフォ（初期値 = 3）: 同時に 3 スレッドまでアクセス可能

wait(sem)   ← カウンタを 1 減らす。0 なら待つ
// リソースを使用
signal(sem) ← カウンタを 1 増やす。待っているスレッドを起こす
```

### ミューテックスとの違い

| 観点 | ミューテックス | セマフォ |
|---|---|---|
| 同時アクセス数 | 1 つだけ | N 個（設定可能） |
| 所有権 | あり（ロックした人がアンロック） | なし（誰でも signal 可能） |
| 用途 | 排他制御 | リソースの個数管理、スレッド間の同期 |

### セマフォの使い分け
- **バイナリセマフォ**（初期値 1）: ミューテックスに近い使い方
- **カウンティングセマフォ**（初期値 N）: 例）DB 接続プールの同時接続数制限

## 5. モニタ（Monitor）

### 一言でいうと
> **排他制御の仕組みを言語レベルで組み込んだもの**

ミューテックスの lock/unlock を手動でやるとバグりやすい（unlock 忘れなど）。
モニタは、オブジェクトやクラスに排他制御を組み込んで自動化する。

### Java の synchronized
```java
// この メソッド全体がモニタで保護される
public synchronized void withdraw(int amount) {
    balance -= amount;  // 同時に 1 スレッドだけ実行可能
}
```

### 条件変数（Condition Variable）
モニタと組み合わせて使う「条件を満たすまで待つ」仕組み。

```
例: バッファが空なら消費者は待つ、バッファが満杯なら生産者は待つ

生産者:
  lock(mutex)
  while (buffer.full()):
      wait(not_full, mutex)   ← 「満杯じゃなくなるまで待つ」
  buffer.add(item)
  signal(not_empty)           ← 「空じゃなくなったよ」と通知
  unlock(mutex)

消費者:
  lock(mutex)
  while (buffer.empty()):
      wait(not_empty, mutex)  ← 「空じゃなくなるまで待つ」
  item = buffer.remove()
  signal(not_full)            ← 「満杯じゃなくなったよ」と通知
  unlock(mutex)
```

これは **生産者-消費者問題（Producer-Consumer Problem）** という古典的な同期問題。

## 6. デッドロック

### 一言でいうと
> **2 つ以上のスレッドが互いにロックの解放を待ち合い、永遠に先に進めなくなる状態**

```
スレッドA:                      スレッドB:
  lock(mutex1)  ← 取得成功       lock(mutex2)  ← 取得成功
  lock(mutex2)  ← B が持ってる…   lock(mutex1)  ← A が持ってる…
  // 永遠に待つ                   // 永遠に待つ
```

### デッドロック発生の 4 条件（コフマンの条件）
4 つが**すべて同時に**成立するとデッドロックが起きる。

1. **相互排他**: リソースは一度に 1 スレッドしか使えない
2. **保持と待機**: ロックを持ったまま別のロックを待つ
3. **横取り不可**: 他のスレッドからロックを奪えない
4. **循環待ち**: A→B→C→A のように待ちが環状になっている

### 対策
| 対策 | 方法 |
|---|---|
| **ロック順序の統一** | 全スレッドが mutex1 → mutex2 の順でロックする |
| **タイムアウト** | 一定時間でロック取得を諦めてリトライ |
| **ロック階層** | ロックに番号をつけ、小さい番号からしか取れないルール |
| **ロックの最小化** | クリティカルセクションを短くし、複数ロックを避ける |

## 7. その他の同期手法

### スピンロック
ロックが取れるまで **ループで待ち続ける**（ビジーウェイト）。

```
while (!tryLock(mutex)) {
    // 何もせずループ（CPU を消費し続ける）
}
```

- 待ち時間が非常に短い場合はコンテキストスイッチより高速
- マルチコアのカーネル内部で主に使用
- 待ちが長いとCPU の無駄遣いになるのでユーザーコードでは通常使わない

### リードライトロック（Read-Write Lock）
読み取りは複数同時OK、書き込みは排他的。

```
読み取り: 複数スレッドが同時にロック取得可能
書き込み: 1 つのスレッドだけ（読み取りもブロック）
```

- 「読み取りが多く、書き込みが少ない」場面で高い並行性を維持
- データベースの並行制御でよく使われる考え方

### アトミック操作
ハードウェアレベルで**分割不可能な**操作。ロック不要で高速。

```
// 通常の操作（割り込まれる可能性あり）
count = count + 1    ← read → add → write の 3 ステップ

// アトミック操作（ハードウェアが 1 命令で実行）
atomic_increment(count)  ← 割り込まれない
```

- CAS（Compare-And-Swap）が代表的なアトミック命令
- カウンターやフラグなど単純な操作に有効
- 複雑な処理には向かない

## 8. 優先度逆転

高優先度のスレッドが、低優先度のスレッドが持つロックを待たされる現象。

```
低優先度 L: mutex をロック中
高優先度 H: mutex を取ろうとする → L の完了を待つ
中優先度 M: 割り込んで L より先に CPU を使う

→ H は M が終わるまで間接的に待たされる（優先度が逆転している）
```

### 有名な事例
1997年、火星探査機パスファインダーで優先度逆転によるリセットが繰り返し発生。
対策として **優先度継承（Priority Inheritance）** が適用された（L の優先度を一時的に H と同じに引き上げる）。

## 9. 開発者として知っておくべきこと

1. **できるだけロックを使わない設計を**: イミュータブルなデータ、メッセージパッシング、アクターモデルなどで競合を回避
2. **ロックの粒度は最小限に**: クリティカルセクションは短く。I/O をロック内に入れない
3. **ロック順序を決める**: 複数のロックを使う場合は順序を統一してデッドロックを防ぐ
4. **高レベルの同期プリミティブを使う**: 生のミューテックスより、チャネル（Go）、`asyncio.Queue`（Python）、`ConcurrentHashMap`（Java）などを使う方が安全
5. **テストが難しい**: 競合状態は再現性が低い。ThreadSanitizer（TSan）などのツールを活用
