# 正規化（Unicode Normalization）

## 正規化とは
**見た目が同じなのに内部表現が違う文字列**を、共通の形に揃える処理です。Unicodeでは同じ文字を複数のコードポイント列で表せる場合があり、そのままでは比較・検索・ソートで問題が起きます。

## なぜ同じ文字に複数の表現があるのか

### 例1: 合成文字
「é」は2通りで表現可能。
```
① U+00E9                （単一文字、合成済み）
② U+0065 U+0301         （e + 合成アクセント）
```
どちらも画面上は同じ「é」だが、バイト列が違う。

### 例2: 日本語の濁点
```
① "が" = U+304C（合成済み）
② "か" + "゛" = U+304B U+309B（分解形）
```

### 例3: 全角・半角
```
"Ａ" (U+FF21, 全角)  vs  "A" (U+0041, 半角)
```

### 例4: 互換文字
```
"㈱" (U+3231)  vs  "(株)"
"①" (U+2460)  vs  "1"
```

## 4つの正規化形式（NFC/NFD/NFKC/NFKD）

### NFC（Normalization Form Canonical Composition）
**合成形**。できるだけ単一コードポイントに合成。
```
"é" → U+00E9（1コードポイント）
"が" → U+304C（1コードポイント）
```
**Webや保存時の推奨形式**。

### NFD（Normalization Form Canonical Decomposition）
**分解形**。最大限分解する。
```
"é" → U+0065 U+0301
"が" → U+304B U+309B
```
文字の処理がしやすい（アクセントだけ除去など）。

### NFKC（Normalization Form Compatibility Composition）
**互換合成**。見た目が似ている文字も統一した上で合成。
```
"Ａ" → "A"
"㈱" → "(株)"
"①" → "1"
```
検索などで広く一致させたい時に。

### NFKD（Normalization Form Compatibility Decomposition）
**互換分解**。NFKCの分解版。

## 関係図
```
NFC ←─合成─→ NFD      （可逆、同じ文字を意味）
 │              │
 ↓互換          ↓互換
NFKC ←─合成─→ NFKD    （不可逆、情報が失われる）
```
NFKC/NFKDは「見た目が似ている」文字を同一視するので**情報が失われる**点に注意。

## なぜ正規化が必要か

### ① 文字列比較の失敗
```python
s1 = "café"   # U+00E9
s2 = "café"   # U+0065 + U+0301

s1 == s2              # False（バイト列違い）
nfc(s1) == nfc(s2)    # True
```

### ② 検索漏れ
DBで「café」を検索しても、合成形と分解形が混在すると見つからない。

### ③ ソート順の不安定
同じ文字でも符号列が違うとソート結果が変わる。

### ④ ファイル名の問題
- macOSは内部でNFD
- WindowsはNFC
- 同じ名前に見えて別ファイル扱いになる罠。

### ⑤ パスワード・ユーザー名
入力方法で表現が変わると一致しない。

## 各言語での正規化

### Python
```python
import unicodedata

s1 = "é"              # é
s2 = "é"        # e + ◌́
unicodedata.normalize("NFC", s1) == unicodedata.normalize("NFC", s2)  # True
```

### JavaScript
```javascript
"é".normalize("NFC") === "é".normalize("NFC");   // true
```

### Java
```java
import java.text.Normalizer;
Normalizer.normalize(s, Normalizer.Form.NFC);
```

### Rust（unicode-normalization crate）
```rust
use unicode_normalization::UnicodeNormalization;
let s: String = "café".nfc().collect();
```

## 実例: ユーザー入力の扱い

### ログインID
```python
def canonical(name: str) -> str:
    return unicodedata.normalize("NFKC", name).lower().strip()

canonical("Ｕｓｅｒ　１") == canonical("user 1")   # True
```

### 検索クエリの正規化
全角英数を半角にして比較、濁点の合成形式を揃える、など。

## 正規化形式の選び方

| 用途 | 推奨 |
|---|---|
| 保存・通信（Web全般） | NFC |
| 文字処理（アクセント除去など） | NFD |
| 検索・比較を緩く | NFKC |
| ファイル名（プラットフォーム依存） | 要確認 |

## 互換正規化の副作用

### 失われる情報
```
"Ⅳ" (U+2163, ローマ数字) → "IV"
"㎥" (U+33A5, 立方メートル) → "m3"
"④" → "4"
```
形として重要な意味がある場合、NFKCで潰してしまう。

### 使い分け
- **表示・保存**: NFC（情報保持）
- **検索・比較**: NFKC（一致を広げる）

## 文字列の長さと正規化
「長さ」の定義も正規化形式で変わる。
```javascript
"é".length                         // NFCなら1、NFDなら2
"é".normalize("NFC").length        // 1
"é".normalize("NFD").length        // 2
```

## ファイルシステムの罠

### macOSの不思議
```
echo "が" > a.txt
ls | xxd           # NFDで保存される
```
Linux/Windowsと同期すると、同じ名前が「違うファイル」扱いになる。

### 対策
- Gitの `core.precomposeunicode = true`（macOSでNFCに変換）
- ファイル名は基本ASCIIで保つ

## 絵文字と正規化
基本的に絵文字は正規化しない。
- 家族絵文字 `👨‍👩‍👧` は ZWJ を含む複数コードポイント列
- `"👨‍👩‍👧".length` は8（JS UTF-16単位）
- これは正規化ではなく「絵文字のクラスタ」の話

グラフェム（見かけの1文字）単位で数えたい場合は `Intl.Segmenter` 等を使う。

## 正規化の実務チェックリスト
- [ ] データベース投入前にNFCで統一
- [ ] 検索クエリは入力時にNFKC
- [ ] ファイル名を扱う時は OS の癖を把握
- [ ] ログにバイト列と正規化結果を残せるか
- [ ] 入力フォームで「é」と「e+◌́」を区別しない設計

## 正規化できない違い

### 大文字/小文字
`"A"` と `"a"` は別コードポイント。`toLowerCase()` などで別途処理。

### 書体差・字形差
同じコードポイントでもフォントで違うだけ。比較には影響しない。

### 異体字セレクタ
`"葛"` + `U+E0101` は選択された字形。正規化で変わらない。

## まとめ
- Unicodeでは**同じ文字を複数の符号列で表せる**（合成形・分解形）
- 比較・検索・保存で予期せぬ不一致を起こす
- **NFC / NFD / NFKC / NFKD** の4形式を使い分ける
- 保存はNFC、検索はNFKCが基本的な戦略
- ファイル名はプラットフォームの癖に注意（macOSはNFDの落とし穴）
