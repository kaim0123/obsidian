# エンコーディング問題

## エンコーディング問題とは
文字コードの**不一致・混在・誤解釈**によって起きる一連の問題です。代表的なのが**文字化け**ですが、それ以外にも
- データ破損
- 検索ヒットしない
- ソート順が狂う
- セキュリティ脆弱性

といった影響があります。

## 文字化けの仕組み
「あるエンコーディングで保存されたバイト列」を「別のエンコーディングとして解釈」すると発生します。

```
"あ" → UTF-8 で保存 → E3 81 82（バイト列）
         を Shift_JIS として読む → "縺ゅ"
```

## 有名な文字化けパターン

### 1. UTF-8 を Shift_JIS として読む
```
"こんにちは" → UTF-8: E3 81 93 E3 82 93 ...
           → SJIS解釈: "縺薙ｓ縺ｫ縺｡縺ｯ"
```

### 2. Shift_JIS を UTF-8 として読む
```
"あ" → SJIS: 82 A0
     → UTF-8解釈: 不正バイト列 → "" や "??"
```

### 3. ダブルエンコード
```
"あ" → UTF-8バイト列を さらに UTF-8 として解釈
     → "ã\x81\x82" のような文字列になる
```
これが積み重なると「**三重・四重文字化け**」になる。

### 4. BOMの誤解釈
UTF-8 BOM（`EF BB BF`）が文字として表示されると先頭に謎の3文字が出る。

## 「文字化け」実例 mojibake
有名な化け方の名前:
- **縺（UTF-8→SJIS）**
- **繧（UTF-8→SJIS）**  
- **ã（UTF-8→Latin-1）**
- **æ•（同上）**

これを見たら「UTF-8 を別の系統として読んでいる」とすぐわかる。

## 発生しやすい場面

### ファイル読み込み
```python
open("data.txt")           # デフォルトエンコーディングで読む（環境依存）
open("data.txt", encoding="utf-8")   # 明示的が安全
```

### HTTP/API
- レスポンスヘッダの `Content-Type: charset=...`
- メタタグの `<meta charset="utf-8">`
- 両方が矛盾すると文字化け

### データベース
- 接続文字コード
- 列の文字コード
- サーバーデフォルト
が一致していないと化ける。

### メール
- ヘッダは `=?UTF-8?B?...?=` などMIMEエンコード
- 本文は `Content-Transfer-Encoding`

### URL
ASCII以外はパーセントエンコードが必要。
```
"あ" → %E3%81%82
```

## 対処の手順

### ① 症状の確認
化け方のパターンでどこでズレたか推測。
- "縺"系 → UTF-8をSJISで読んだ
- "ã"系 → UTF-8をLatin-1で読んだ

### ② 実際のバイト列を見る
```bash
# 16進ダンプ
xxd file.txt | head
```

### ③ エンコーディング判定
```bash
# macOS/Linux
file -i data.txt
nkf --guess data.txt       # 日本語定番ツール
chardet data.txt           # Python
```

### ④ 変換
```bash
iconv -f shift_jis -t utf-8 in.txt > out.txt
nkf -w in.txt > out.txt
```
```python
text = open("a.txt", encoding="shift_jis").read()
open("b.txt", "w", encoding="utf-8").write(text)
```

## 代表的な注意点

### Python 2 → Python 3 移行
Python 2は `str` がバイト列、`unicode` が文字列。3で`str`が文字列、`bytes`がバイト列に統一。移行ではエンコーディング明示が必要。

### Windowsの cp932
日本語Windowsのデフォルトは `cp932`（Shift_JISの拡張）。PowerShellやコマンドプロンプトのエンコーディング設定で注意。
```powershell
chcp 65001          # UTF-8に切り替え
$OutputEncoding = [System.Text.Encoding]::UTF8
```

### MySQLの utf8 vs utf8mb4
MySQLの `utf8` は3バイトまでしかサポートせず、4バイト絵文字が入らない。**必ず `utf8mb4` を使う**。
```sql
CREATE TABLE posts (
  content TEXT CHARACTER SET utf8mb4
) DEFAULT CHARSET=utf8mb4;
```

### JSONと非ASCII
JSONは原則UTF-8。`\uXXXX` エスケープで非ASCIIを表現することもある。
```json
{"name": "あ"}  // "あ" と等価
```

### JavaとファイルI/O
```java
// ❌ デフォルトエンコーディング（環境依存）
Files.readAllLines(path);

// ✅ 明示的
Files.readAllLines(path, StandardCharsets.UTF_8);
```

## セキュリティリスク

### UTF-8の不正バイト列
過剰に長いシーケンスでセキュリティフィルタを回避する攻撃。
```
"/" を 3バイトで表現 → 2F を C0 AF として書く
```
モダンなデコーダは拒否するが、古い実装は危険。

### 正規化を悪用した回避
```
"admin" ≠ "ａｄｍｉｎ"（全角）
```
権限チェックを迂回される可能性。入力時にNFKC正規化しておく。

### Homograph攻撃
似た字形のUnicode文字で偽ドメインを作る。
```
"google.com"  （本物）
"gооgle.com"  （キリル文字の о を使用）
```

### Punycode
国際化ドメインはASCII化されて処理される。
```
"日本.jp" → "xn--wgv71a.jp"
```

- [ ] 各種ファイル操作の `encoding` 引数

## 予防策まとめ

### 徹底すべきこと
- すべてを **UTF-8** に統一
- ファイル・通信・DB・ソースコードすべて
- 「デフォルト任せ」を避けて**明示的に指定**

### HTTP
```
Content-Type: application/json; charset=utf-8
```

### HTML
```html
<meta charset="utf-8">
```

### HTTP API設計
- リクエストはUTF-8前提
- レスポンスにcharset明記
- 不正な入力は早期に弾く

### ファイル操作
```python
with open(path, encoding="utf-8") as f: ...
```

### DB
- MySQL: `utf8mb4`
- PostgreSQL: `UTF8`
- 接続時 `SET NAMES utf8mb4`

## まとめ
- エンコーディング問題は**保存側と読込側の不一致**が原因
- 現代は**すべてUTF-8で統一**するのが最善策
- ファイル・通信・DBすべてでエンコーディングを**明示**
- 文字化けは化け方のパターンから原因を推測できる
- セキュリティ上も正規化・入力検証・Punycode対応が重要
