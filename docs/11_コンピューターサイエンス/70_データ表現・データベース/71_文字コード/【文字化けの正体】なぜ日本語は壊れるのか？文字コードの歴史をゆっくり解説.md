## 詳しい要約

本動画は、霊夢が受け取った **文字化けメール** をきっかけに、コンピュータが文字を扱う仕組みと **ASCII から Unicode までの文字コードの歴史** を初心者向けに解説する。結論から言えば、文字化けは **同じバイト列を異なる文字コードで解釈したとき** に起こる。コンピュータは本質的に数字しか扱えないため、文字と数値の対応表（文字コード）がずれると「莉咯轾茤苘趼鋈」のような謎文字が現れる。

### 文字コードの基本——コンピュータは数字しか分からない

**文字コード** は、コンピュータが文字を理解するための **「文字 ↔ 数値」の対応表** である。

| 概念 | 内容 |
|------|------|
| **基本原理** | コンピュータは 0 と 1（数字）しか処理できない。`A` を `65` のように数値に変換して扱う |
| **デコード** | 保存・送信された数値を、指定された文字コード表に従って文字に戻す処理 |
| **文字化けの本質** | 送信側と受信側（または保存側と表示側）で **文字コードの解釈が一致しない** と、別の文字が表示される |

---

### ASCII 時代——英語だけの 128 文字（1960 年代）

1960 年代、アメリカで誕生したコンピュータ向けに **ASCII（American Standard Code for Information Interchange）** が作られた。

| 項目 | 内容 |
|------|------|
| **ビット幅** | **7 ビット**（128 文字） |
| **表現可能な文字** | 英大文字・小文字（26×2）、数字（10）、記号、制御文字 |
| **限界** | 英語圏では十分だが、日本語のひらがなだけでも 50 音あり、漢字は数千文字——**まったく足りない** |

各国が独自の文字コードを開発し始め、**国ごとに異なる「暗号」** を使う状態になった。これが後の国際的混乱の始まりである。

---

### 日本語文字コードの乱立——JIS 規格と 3 つの方式

日本語はひらがな・カタカナ・漢字・英数字が混在し、ASCII の 128 文字では表現不可能だった。

#### JIS X 0208（1978 年）

- 日本の文字コード規格として **JIS X 0208** が策定された。
- **2 バイト（16 ビット）** を使い、約 **6,000 文字** の漢字・ひらがな・カタカナを表現可能に。
- これをベースに、用途の違いから **複数の互換性のない方式** が生まれた。

#### 日本語を扱う 3 つの主要方式

| 方式 | 特徴 | 主な利用環境 |
|------|------|-------------|
| **エスケープ JIS** | 7 ビット世界で `ESC` などの制御文字で「日本語モード」「英語モード」を切り替える | 古い通信・メール |
| **Shift_JIS** | 1 バイト（ASCII 互換）と 2 バイト（日本語）を混在。Microsoft が開発に関与 | **Windows のデフォルト**。日本で最も普及 |
| **EUC-JP** | こちらも 1 バイトと 2 バイトの混在だが、**文字の割り当て方が Shift_JIS と異なる** | **UNIX / Linux 系** で広く使用 |

- **同じ「あ」でも Shift_JIS と EUC-JP では異なる数値** で表現される。
- 文字コードを間違えて開くと、霊夢のメールのように文字化けが発生する。

#### Shift_JIS 特有の罠——円記号とバックスラッシュ

- Shift_JIS では **「¥（円）」とバックスラッシュ `\` が同じコード** を共有する。
- プログラムで `\` をエスケープ文字として使う場面で、日本語の「表」などが **プログラムを壊す** 事例があった。

### 世界規模の文字コード戦争——インターネット時代の混乱

日本だけでなく、世界中で同様の問題が起きていた。

#### ヨーロッパ

| 規格 | 内容 |
|------|------|
| **ISO-8859-1（Latin-1）** | 8 ビット（256 文字）。フランス語のアクセント、ドイツ語のウムラウトなど |
| **Latin-2 / 3 / 4** | 中央欧・南欧・北欧向けに次々と派生。256 文字でも全欧州言語はカバーしきれない |

#### アジア

| 国・地域 | 文字コード |
|---------|-----------|
| **中国** | GB2312 |
| **台湾** | Big5 |
| **韓国** | EUC-KR |

#### 1990 年代——インターネット普及が問題を顕在化

- 世界中の人がメール・Web ページを交換するようになり、**国ごとの文字コードの違い** が致命的になった。
- 中国→日本、フランス→ロシアのメールが文字化け。
- **1 ページに複数言語を混在表示** したい場合、1 つの文字コードでは不可能で、途中切り替えや画像化など **涙ぐましい回避策** が必要だった。
- メール・ファイル名・データベースでも文字化けトラブルが多発。

---

### Unicode——全文字を 1 つのコード空間に（1980 年代後半〜）

**Unicode** は、世界中のあらゆる文字を **1 つの文字コード体系** で表現しようとする壮大なプロジェクトである。

#### 設計の変遷

| 段階 | 内容 |
|------|------|
| **当初の想定** | 16 ビット（65,536 文字）で全世界をカバーできると考えられた |
| **現実** | 中国の漢字だけで数万文字。古代文字・記号・絵文字を含めると **100 万文字以上** が必要に |
| **現在** | **21 ビット相当**（約 200 万コードポイント）まで拡張 |

#### 3 つのエンコーディング方式

Unicode の「文字の番号」（コードポイント）をバイト列に変換する方式が 3 つある。

| 方式 | 特徴 | メリット・デメリット | 主な用途 |
|------|------|---------------------|---------|
| **UTF-32** | 全文字を **4 バイト固定** | 分かりやすいが、英語 1 文字に 4 バイトは **無駄が大きい** | 特殊用途 |
| **UTF-8** | **可変長**（ASCII は 1 バイト、日本語は 3 バイト、特殊文字は 4 バイト） | ASCII 互換・無駄が少ない。**インターネットの標準** | Web、Linux、多くの新規システム |
| **UTF-16** | 多くの文字を **2 バイト** で表現 | CJK 文字の処理が高速 | **Windows 内部**、Java 内部 |

- 例：「Hello、こんにちは」→ `Hello` は 1 バイト×6 + `こんにちは` は 3 バイト×5 = 合計 21 バイト（UTF-8 の場合）。

#### 普及の道のり

| 時期 | 状況 |
|------|------|
| **1990 年代** | Unicode 仕様は策定されたが、日本では Shift_JIS・EUC-JP のレガシーシステムが大量に残り、移行は困難 |
| **2000 年代** | Web の普及とともに **UTF-8 が急速に普及** |
| **2023 年** | Web ページの **98% 以上が UTF-8** を使用。文字コード戦争は事実上終結 |

---

### 新たな課題——絵文字と Unicode の進化

Unicode によって文字化け問題は大きく改善されたが、**絵文字** が新しい課題を生んだ。

#### 絵文字の歴史

| 時期 | 出来事 |
|------|--------|
| **1999 年** | **NTT ドコモ** の栗田穣崇氏が **176 個の絵文字** を開発——**絵文字発祥は日本** |
| **2000 年代** | 各キャリアが独自の絵文字を制作。ドコモの絵文字を au で見ると **別の絵文字に化ける**（再び文字化け問題） |
| **2010 年代〜** | 絵文字が Unicode に統合。現在 **5,000 種類以上** が登録（表情・動物・食べ物・国旗・肌の色のバリエーションなど） |

#### Unicode Consortium による審査

- 新しい絵文字の追加は **Unicode Consortium** が厳格に審査。
- 「本当に必要か」「他の絵文字で代用できないか」「世界中で使われる可能性があるか」などの基準で判断される。

---

### 現代と未来——AI 時代の文字コード

| テーマ | 内容 |
|--------|------|
| **AI・多言語処理** | ChatGPT、Google 翻訳が 100 以上の言語を扱えるのも、Unicode で文字が統一されているから |
| **継続的な拡張** | 古代文字、消滅言語、新たに発見される文字など、Unicode は **今も進化中** |
| **残る課題** | レガシーシステムとの互換問題は未解決のまま残る |
| **現状の標準** | 新規システムでは **UTF-8 がデファクトスタンダード**。文字化けで悩む時代はほぼ終わった |

---

### オチ——霊夢のメールの正体

- 霊夢の文字化けメールは、**Shift_JIS で書かれたメールを UTF-8 として開いた**（またはその逆）ことが原因。
- メールクライアントで **正しい文字コードを指定** すれば正常に読める——実際に「博麗神社の霊夢さんへ いつもお世話になっております。」と表示された。

> 文字コードの歴史は、人類がコンピュータで言語を扱うための **試行錯誤の歴史** でもある。先人の努力のおかげで、今は世界中の人とコミュニケーションできる。文字化けに遭遇したら、まず **文字コードの指定を疑う** ことが第一歩である。
