# UTF-8 / UTF-16 / UTF-32

## UTF（Unicode Transformation Format）
Unicodeのコードポイント（U+0000〜U+10FFFF）を**実際のバイト列に変換する方式**。3つの主要な方式があります。

| 方式 | バイト長 | ASCII互換 | 主な用途 |
|---|---|---|---|
| UTF-8 | 1〜4バイト（可変） | あり | Web、Linux、ファイル保存 |
| UTF-16 | 2または4バイト | なし | Java/JS内部、Windows API |
| UTF-32 | 4バイト固定 | なし | 内部処理、研究 |

## UTF-8

### 特徴
- ASCII互換（0x00〜0x7Fはそのまま1バイト）
- 可変長: 1〜4バイト
- バイトオーダー（エンディアン）に依存しない
- 世界標準、Webで圧倒的多数

### 符号化ルール
| コードポイント | バイト数 | パターン |
|---|---|---|
| U+0000〜007F | 1 | `0xxxxxxx` |
| U+0080〜07FF | 2 | `110xxxxx 10xxxxxx` |
| U+0800〜FFFF | 3 | `1110xxxx 10xxxxxx 10xxxxxx` |
| U+10000〜10FFFF | 4 | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

### 例
```
'A' (U+0041)  → 0x41
'あ' (U+3042) → 0xE3 0x81 0x82
'🍣' (U+1F363) → 0xF0 0x9F 0x8D 0xA3
```

### メリット
- **ASCIIテキストはそのまま**（米国データとの互換性）
- **省サイズ**（英文中心なら1バイト）
- エンディアン問題なし
- 自己同期: 途中から読んでも文字境界が分かる

### デメリット
- 可変長なので「n文字目」アクセスが遅い
- 日本語は3バイトになりがち（UTF-16より大きい）

## UTF-16

### 特徴
- 基本2バイト、補助面は4バイト
- JavaScript、Java、C#、.NET、Windowsの内部表現
- BOMでエンディアン指定（UTF-16LE / UTF-16BE）

### 符号化ルール
| コードポイント | バイト数 | 表現 |
|---|---|---|
| U+0000〜FFFF（BMP） | 2 | コードポイントそのまま |
| U+10000〜10FFFF | 4 | **サロゲートペア** |

### サロゲートペア
U+10000以上を2つの16bit値に分割。
```
'🍣' (U+1F363)
  → 高位: 0xD83C, 低位: 0xDF63
  → バイト列: D8 3C DF 63（BE）/ 3C D8 63 DF（LE）
```

### メリット
- BMPの範囲なら「1文字=2バイト」と計算しやすい
- 日本語（ほとんどBMP）は2バイトで収まる

### デメリット
- サロゲートペアの扱いが複雑
- ASCII非互換（ASCII文字でも2バイト）
- エンディアン問題あり

### JavaScriptでの注意
```javascript
"🍣".length          // 2（サロゲートペアの16bit単位）
"🍣".charCodeAt(0)   // 55356（高位サロゲート）

// 正しくコードポイントを扱う
"🍣".codePointAt(0)  // 127843
[..."🍣"].length     // 1
```

## UTF-32

### 特徴
- 4バイト固定長
- コードポイントがそのまま数値
- 実装が単純

### 例
```
'A' (U+0041)    → 00 00 00 41
'あ' (U+3042)   → 00 00 30 42
'🍣' (U+1F363)  → 00 01 F3 63
```

### メリット
- O(1)でn文字目にアクセス可能
- サロゲートペア不要

### デメリット
- **4倍のサイズ**（大半が0で無駄）
- 通信・保存には非効率
- ほとんどのシステムで採用されない

実用上はメモリ内で Python の一部実装などが使う程度。ストレージ・通信では使われない。

## UTF-8を選ぶべき理由
現代のほとんどのシーンで UTF-8 がベストチョイス。

### ① Webと親和
- HTML5の既定
- JSON、XMLの推奨
- HTTP: `charset=utf-8`

### ② ASCII互換
旧来のASCIIデータがそのまま動く。

### ③ サイズ効率
英文なら1バイト。多国語混在でも平均的に小さい。

### ④ エンディアン無関係
バイトオーダー問題なし。

### ⑤ 自己同期
バイト列の途中から安全に読める。

## BOM（Byte Order Mark）

### 各エンコーディングのBOM
| 形式 | バイト列 |
|---|---|
| UTF-8 | `EF BB BF` |
| UTF-16 BE | `FE FF` |
| UTF-16 LE | `FF FE` |
| UTF-32 BE | `00 00 FE FF` |
| UTF-32 LE | `FF FE 00 00` |

### UTF-8 BOMは必要か?
- 推奨は**付けない**
- ただしWindowsの一部ソフト（古いExcelなど）はBOMを要求
- JSON、シェルスクリプト、ソースコードは付けないのが無難

## 比較表: 日本語文字列

```
"こんにちは" を各形式で保存したときのバイト数
  UTF-8:  15バイト（3バイト × 5文字）
  UTF-16: 10バイト + BOM 2
  UTF-32: 20バイト + BOM 4
```

## 比較表: 英数字文字列

```
"Hello" を各形式で保存したときのバイト数
  UTF-8:  5バイト
  UTF-16: 10バイト + BOM 2
  UTF-32: 20バイト + BOM 4
```
英文では UTF-8 が圧倒的に小さい。

## 言語の内部表現

### UTF-8派
- Rust (`String`, `&str`)
- Go (`string`)
- Python 3 (条件により異なる、文字列はコードポイント列)
- Swift (`String`)

### UTF-16派
- JavaScript (`string`)
- Java (`String`, `char`)
- C# (`string`, `char`)

### 混合
- Python 3: 内部はコードポイントごとに1/2/4バイトで可変（PEP 393）

## 相互変換

### JavaScript（UTF-16 ↔ UTF-8バイト列）
```javascript
// 文字列 → UTF-8バイト列
const bytes = new TextEncoder().encode("こんにちは");

// UTF-8バイト列 → 文字列
const str = new TextDecoder("utf-8").decode(bytes);
```

### Python
```python
# 文字列 → UTF-8バイト列
b = "こんにちは".encode("utf-8")

# UTF-8バイト列 → 文字列
s = b.decode("utf-8")
```

### Rust
```rust
let s = "こんにちは";
let bytes = s.as_bytes();          // &[u8]
let s2 = std::str::from_utf8(bytes).unwrap();
```

## 不正なバイト列の扱い

### 厳密モード
不正なら例外。
```python
b"\xff".decode("utf-8")   # UnicodeDecodeError
```

### 置換モード
不正な箇所を `�`（U+FFFD）に置換。
```python
b"\xff".decode("utf-8", errors="replace")  # "�"
```

### 無視モード
不正な箇所を飛ばす。
```python
b"\xff".decode("utf-8", errors="ignore")   # ""
```

実務では通常「厳密」で失敗を検出するか、「置換」で落ちないようにする。

## パフォーマンスの豆知識
- UTF-8: 可変長なのでインデックスアクセスが遅い
- UTF-16: BMPなら高速だがサロゲートで遅くなる
- UTF-32: インデックスアクセス最速だがメモリ食い

メモリ節約 vs 速度のトレードオフ。ほとんどの用途では **UTF-8** で問題なし。

## 現代のベストプラクティス
- 保存・通信は **UTF-8**（BOMなし）
- DBは **utf8mb4**（MySQL）、**UTF8**（PostgreSQL）
- HTMLは `<meta charset="utf-8">`
- HTTPは `Content-Type: ...; charset=utf-8`
- ソースコードはすべて UTF-8

## まとめ
- UTF-8/16/32は**Unicodeコードポイントをバイト列にする方式**
- **UTF-8**: ASCII互換・可変長・Web標準
- **UTF-16**: Java/JS内部・BMPは2バイト・サロゲートペアに注意
- **UTF-32**: 固定長だがサイズ大、通信・保存向きではない
- 実用では **UTF-8（BOMなし）** を既定にすれば大半の問題を回避できる
