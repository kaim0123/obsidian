# 文字コードの基礎

## 文字コードとは
文字を**数値（符号）に対応付けたルール**のことです。コンピュータは数値しか扱えないので、文字を扱うには必ず文字コードを介します。

```
文字 'A' → 数値 65 → 2進数 01000001 → 保存・通信
```

## なぜ重要か
- 文字化け・データ破損の原因
- Web、DB、メール、ファイル名、すべてで影響
- 多言語対応（国際化・i18n）の前提

## 用語の整理

### 文字集合（Character Set）
扱う文字の**集まり**。「どの文字を使えるか」を定義。
- 例: ASCII, JIS X 0208, Unicode

### コードポイント（Code Point）
集合内の**各文字に割り当てた番号**。
- 'A' = U+0041
- 'あ' = U+3042
- '🍣' = U+1F363

### エンコーディング（Encoding）
コードポイントを**実際のバイト列に変換する規則**。
- UTF-8, UTF-16, Shift_JIS など

同じ文字集合でも、複数のエンコーディングがあり得る。

## 歴史的な文字コード

### ASCII（1963）
英数字・記号・制御文字の**7ビット**128文字。アメリカ用。
```
'A' = 65 = 0x41 = 0b01000001
'a' = 97 = 0x61
'0' = 48 = 0x30
```

### ISO-8859シリーズ
ASCIIを8ビットに拡張して、各地域の文字を追加。
- ISO-8859-1（Latin-1）: 西欧
- ISO-8859-5: キリル文字
- 互いに互換性なし

### 日本語の文字コード

#### JIS X 0208 / JIS X 0213
日本語の文字集合を規定。漢字・かな・記号。

#### Shift_JIS（SJIS）
Windows系で長く使われた日本語エンコーディング。ASCIIと1バイト、日本語は2バイト。

#### EUC-JP
Unix系で使われた日本語エンコーディング。

#### ISO-2022-JP
メールで使われたエスケープシーケンス切替型。

### 問題点
- 言語ごとに別規格 → **混在できない**
- 同じファイルに日本語と中国語、など困難
- 文字化けが頻発

## Unicode（1991〜）
**全世界の文字を1つに統合**しようという試み。現代の標準。

### Unicodeの構造
- コードポイントは **U+0000 〜 U+10FFFF**
- 全体で約111万個の位置
- 17の**面（Plane）**に分かれる
  - BMP（Basic Multilingual Plane, 0面）: よく使う文字
  - SMP, SIP, TIP... : 拡張文字

### 主な収録範囲
- U+0000〜007F: ASCII
- U+3040〜309F: ひらがな
- U+30A0〜30FF: カタカナ
- U+4E00〜9FFF: CJK統合漢字
- U+1F000〜: 絵文字

## Unicodeの表現方法
Unicodeの「番号」を実際のバイト列にする方式（= エンコーディング）:
- **UTF-8**: 1〜4バイトの可変長
- **UTF-16**: 2または4バイト
- **UTF-32**: 4バイト固定

詳細は「UTF-8 / UTF-16 / UTF-32」の章へ。

## バイトと文字の違い
これは文字コード理解の核心。
```
"あ" の UTF-8 表現 = E3 81 82（3バイト）
"あ".length
  JS  → 1（UTF-16コード単位）
  Python3 → 1（コードポイント）
  Rust の bytes() → 3（UTF-8バイト数）
```
**長さ**の意味が言語によって違う。

## サロゲートペア
UTF-16では、BMP外（U+10000以上）を**2つの16bit単位で表す**。
```
'🍣' = U+1F363
UTF-16: 0xD83C 0xDF63（サロゲートペア）
```
JSでは `"🍣".length === 2` となり罠になる。

```javascript
"🍣".length           // 2（サロゲートペアで数えられる）
[..."🍣"].length      // 1（コードポイント数）
```

## BOM（Byte Order Mark）
ファイル先頭に付く、**エンコーディング種別・バイトオーダー**を示す特殊な印。
- UTF-8 BOM: `EF BB BF`
- UTF-16 LE BOM: `FF FE`
- UTF-16 BE BOM: `FE FF`

### 使うべき？
- UTF-8ではBOM不要（推奨は「なし」）
- Windowsの一部ソフト（古いExcel）はBOMがないとSJISとして扱う
- JSONやソースコードはBOMなしが一般的

## バイトオーダー（エンディアン）
多バイト文字を**どちらの順に並べるか**。
- **ビッグエンディアン（BE）**: 上位バイトが先
- **リトルエンディアン（LE）**: 下位バイトが先

UTF-16/32には LE / BE があり、BOMで区別する。UTF-8はバイトオーダー無関係。

## 文字化けの仕組み
エンコーディングが合わないとき、バイト列を誤って解釈して別文字に見える現象。
```
"あ" を UTF-8 で保存 → E3 81 82
     を Shift_JIS として読む → "縺ゅ"（意味不明）
```

## 絵文字と合成文字
```
👨‍👩‍👧 = 男性 + ZWJ + 女性 + ZWJ + 女の子
🇯🇵 = Regional Indicator J + Regional Indicator P
```
1つの「見かけの文字」が複数のコードポイントで構成される（詳しくは「正規化」の章）。

## 言語とデフォルトエンコーディング

| 言語 | デフォルト |
|---|---|
| Python 3 | UTF-8（ソースコード、文字列） |
| JavaScript | UTF-16（内部文字列） |
| Java | UTF-16（charは16bit） |
| Rust | UTF-8（String, str） |
| Go | UTF-8（string） |
| C/C++ | 指定なし（環境依存） |

## ファイル入出力時の注意
明示的にエンコーディングを指定するのが安全。
```python
open("a.txt", encoding="utf-8")
```
```java
Files.readString(path, StandardCharsets.UTF_8);
```

## 現代のベストプラクティス
- **UTF-8 を既定とする**（BOMなし）
- HTTPは `Content-Type: text/html; charset=utf-8`
- HTML: `<meta charset="utf-8">`
- DB: デフォルト文字コードを `utf8mb4`（MySQL）等
- ソースコード: UTF-8

## よくあるハマり
- Excelが Shift_JIS でしか読めない → BOM付きUTF-8で保存
- DBに4バイト絵文字が入らない → `utf8mb4` 使用
- URLに日本語 → **パーセントエンコード**
- メール → `Content-Transfer-Encoding: base64` 等で運ぶ

## まとめ
- 文字コードは**文字 → 数値 → バイト列**の対応ルール
- 歴史的に乱立 → **Unicode** に統合
- 実装形式として **UTF-8 / UTF-16 / UTF-32**
- 現代は **UTF-8（BOMなし）** が既定の選択
- 言語ごとの内部表現とバイト列の違いを意識する
