# 改行コード

## 改行コードとは
テキストファイルで「行の終わり」を表す**特殊な文字**のことです。目に見えないがファイルに存在し、OSやソフトごとに使う文字が異なります。

## 3種類の改行コード

| 略称 | 文字 | 16進 | 主な使用環境 |
|---|---|---|---|
| LF | `\n` | `0x0A` | Unix系、macOS、Linux、現代のWeb |
| CRLF | `\r\n` | `0x0D 0x0A` | Windows、HTTP、メール |
| CR | `\r` | `0x0D` | 旧Mac OS（〜OS 9） |

### 名前の由来（タイプライター時代）
- **CR（Carriage Return）**: キャリッジを行頭に戻す
- **LF（Line Feed）**: 用紙を1行送る

## 各OSのデフォルト

### Unix系（Linux, macOS）
`LF` を使う。1バイトで済む。

### Windows
`CRLF` を使う。2バイト。MS-DOS時代の名残。

### 古いMac（OS 9 以前）
`CR` のみ。現代のmacOSはUnix系なので`LF`。

## プロトコル・フォーマットでの改行

| 対象 | 改行 |
|---|---|
| HTTP | CRLF |
| SMTP/メール | CRLF |
| FTP（ASCIIモード） | CRLF |
| HTML/JSON/XML | 原則LF |
| YAML | LF（CRLFも許容） |
| CSV | 仕様上CRLFだが実運用は様々 |

## なぜ違いが問題になるか

### 1. 混在すると壊れる
```
line1\n
line2\r\n        ← CRLF混ざると表示崩れ
line3\n
```

### 2. Gitの差分がノイズに
改行だけ違うファイルで「全行変更」と表示される。

### 3. シェルスクリプトが動かない
```bash
#!/bin/bash\r\n   ← Windowsで編集したシェルスクリプト
```
`\r\n` が付くと `bad interpreter` エラー。

### 4. 検索・比較の誤動作
`"line\n" === "line\r\n"` は `false`。

### 5. 正規表現
```
/^line$/       # $は \n か \r\n を境界と扱う
/\n/           # \r\n の場合一致しない
```

## 各言語での扱い

### JavaScript
```javascript
"a\nb".split("\n");       // ["a", "b"]
"a\r\nb".split("\n");     // ["a\r", "b"] ← 注意

// 両方対応
"a\r\nb".split(/\r?\n/);
```

### Python
```python
# テキストモードは自動で改行統一
open("a.txt").read()          # \r\n も \n に変換される
open("a.txt", "rb").read()    # バイナリモードは生のバイト
```

### バイナリ vs テキストモード
テキストモードで開くと**OSに応じて自動変換**が入る。バイナリ処理には注意。

### Java
```java
// システムの改行
System.lineSeparator();

// 読み込み時
Files.readAllLines(path);   // 改行を除去して配列に
```

## Gitでの設定

### core.autocrlf
```
true   ← Windows: コミット時LF、チェックアウト時CRLF
input  ← コミット時LF、チェックアウト時そのまま（macOS/Linux推奨）
false  ← 何もしない
```

### .gitattributes
特定ファイルに強制したい場合。
```
*.sh text eol=lf
*.bat text eol=crlf
*.md text auto
```

### エディタ設定
- VS Code: `"files.eol": "\n"` または `"auto"`
- EditorConfigで統一:
```ini
[*]
end_of_line = lf
```

## ファイルの改行確認

### macOS/Linux
```bash
# 表示で ^M が出れば CR
cat -A file.txt

# 16進ダンプ
xxd file.txt | head

# 改行コード判定
file file.txt
```

### 変換コマンド
```bash
# CRLF → LF
dos2unix file.txt
sed -i 's/\r$//' file.txt
tr -d '\r' < in.txt > out.txt

# LF → CRLF
unix2dos file.txt
```

### エディタで変換
- VS Code: 右下の「LF/CRLF」クリックで変更
- Notepad++: 編集 → EOL変換
- sublime text: View → Line Endings

## HTTPでのCRLF

### 仕様
HTTPヘッダ・リクエストラインは**CRLFで終端**が必須。
```
GET / HTTP/1.1\r\n
Host: example.com\r\n
\r\n
```

### CRLFインジェクション
ユーザー入力で `\r\n` を注入するとヘッダ偽装ができる脆弱性。
```
?name=abc\r\nSet-Cookie:%20admin=true
```
入力検証でCR/LFをエスケープ or 拒否する。

## 言語リテラルの改行

### エスケープシーケンス
```
"\n"   → LF
"\r"   → CR
"\r\n" → CRLF
"\t"   → タブ
"\\"   → バックスラッシュ
```

### 生文字列
- Python: `r"..."` ではエスケープが効かない
- JavaScript: `String.raw` / テンプレートリテラル
- Rust: `r"..."`
- C#: `@"..."`

### 複数行リテラル
```python
s = """line1
line2
line3"""
```
ファイルの改行コードがそのまま文字列に入る場合があるので要注意。

## CSV・表計算ソフトの罠

### CSV仕様（RFC 4180）
- 区切り: `,`
- 改行: **CRLF**
- フィールド内改行は `"..."` で囲む

### Excelの扱い
- Windows版Excel: CRLFで保存
- macOS版Excel: CR のことがあった（古いバージョン）
- 保存形式で挙動が違う

## 改行コードを気にする場面

### コードレビュー・PR
混在するとdiffがノイズに。チーム全体で統一。

### 設定ファイル
シェルスクリプト、Dockerfile、CIスクリプトはLFで保存。

### バイナリファイル
画像・ZIP等は `text eol=...` を適用しない。Gitの`.gitattributes`で明示。

### ログ解析
grepが複数行にまたがらないよう、改行を正しく設定。

## まとめ
- 改行コードは **LF（Unix/Mac）**、**CRLF（Windows/プロトコル）**、**CR（旧Mac）**
- OS・ツール間で違いがあり、混在すると各種トラブル
- プロジェクト全体で**LFに統一**するのが現代の標準
- `.gitattributes` / `.editorconfig` / Gitの `autocrlf` で管理
- HTTPやCSVなど**CRLF必須**の規格もあるので仕様に従う
