## 詳しい要約

**テーマ：MongoDBの評判が「楽」から「怖い」へ変わった事件史と、初期設定の教訓**

「とりあえずMongo」と言われるほど愛されたMongoDBは、書き込み確認を省く初期仕様、Jepsenによるデータ消失の指摘、認証なしの初期設定が招いた世界規模の身代金事件によって「怖いDB」と呼ばれるようになった。現在の製品は別物に近いが、「DBは機能ではなく初期設定で評価せよ」「スキーマレスはスキーマがアプリ側に引っ越しただけ」という教訓は今も有効、という話。

---

### 第1章 広告配信の速度競争から生まれたDB

- 2007年、ネット広告企業 DoubleClick 出身の **ドワイト・メリマン** と **エリオット・ホロウィッツ** が 10gen を創業（DoubleClick は同年 Google が買収を発表）
- DoubleClick は毎秒40万件の広告を配信しており、既存のRDBではこの規模・速度に追いつけなかった
- 名前の由来は **humongous（とてつもなく大きい）**。2009年にオープンソース公開
- 刺さった理由：**スキーマ定義不要**、**JSONの形のまま保存**、**JavaScriptとの相性**。Node.js 登場直後で、フロント・サーバー・DBをすべてJSで貫ける世界ができた

### 第2章 MEANスタックと絶頂の裏の時限爆弾

- 2013年頃、**MEANスタック**（MongoDB・Express・Angular・Node.js）がスタートアップの標準装備に。求人・入門書が増え「とりあえずMongo」の空気
- 2017年10月、NASDAQ に上場し、DBベンダーとして異例の成功
- 一方、2010年には「MongoDB is Web Scale」という風刺アニメが拡散し、「速さの理由を誰も説明できない」危うさが早くから指摘されていた
- 裏で進んでいた2つの時限爆弾：**データの安全性** と **セキュリティの初期設定**

### 第3章 データが消える ― Jepsenとの衝突

- 初期のドライバーは、書き込みがサーバーに届いたかを確認せず成功を返すのが標準設定（投げっぱなし）→ ベンチマークが速いのは当然。改められたのは **2012年11月**（公開から約3年間）
- 分散システム検証プロジェクト **Jepsen**（カイル・キングズベリー）が2015・2017・2020年に繰り返し検証
  - 2017年：旧来のレプリケーション方式の設計欠陥で、多数決で確定したはずの書き込みまで失われうることを指摘
  - 2020年：当時の標準設定ではサーバー1台が受け取っただけで成功扱い。その1台が切り替わるとデータが巻き戻って消える。トランザクションでも設定次第で確定済みの書き込みが失われた
- MongoDB が自社サイトで「最強の一貫性と安全性」と宣伝し、Jepsen から「都合のいい部分だけ引用するな」と公開批判され、「怖い」印象を決定づけた
- 2021年のバージョン5.0で標準設定が多数決（majority）に変更され、指摘の多くは修正された
- 速さの一部は安全確認の省略と引き換えで、しかもそれが **標準設定** だった

### 第4章 MongoDBアポカリプス ― 4万件の脅迫文

- 2016年12月末〜2017年、ネットに露出したMongoDBを攻撃者が探し、中身を消して「返してほしければビットコインを払え」という脅迫文だけを残す事件が多発
- 最初の1か月で約4万5000件、同年9月の第2波でさらに2万6000件。医療機関も被害に遭い、米国の Emory Healthcare では20万件以上の患者記録が人質に
- 原因の半分は管理者のミスだが、残り半分は設計：当時は **認証なし・外部からの接続をすべて受け付ける** のが初期設定。攻撃者は検索エンジン Shodan で露出インスタンスを機械的に発見できた（無防備なインスタンスは約9万9000件と報告）
- 2017年11月の **バージョン3.6** でようやく、初期設定がローカルからの接続のみに変更（公開から8年後）

### 第5章 DBは機能ではなく初期設定で評価しろ

- 現在のMongoDBは別物に近い：標準設定は多数決承認、主戦場はクラウドサービス **Atlas** に移って認証も事実上必須、年間売上20億ドル超の企業に成長
- 教訓1：**ユーザーの9割は初期設定のまま使う**。だから初期設定こそがそのDBの本当の思想。「設定すれば安全」と「初期状態で安全」は全く違う
- 教訓2：**スキーマレスの楽さはスキーマの消滅ではなく、スキーマがDBからアプリのコードへ引っ越しただけ**。定義を書くコストは消えず、支払いが運用フェーズに後回しになる
- 新しいDBが「簡単に始められる」と宣伝してきたら、「その楽さは何を省略して手に入れたのか」を問うべき

### まとめ

- MongoDBの「怖さ」は、書き込み確認の省略・レプリケーションの欠陥・認証なしの初期設定という、楽さ優先の設計から生まれた
- 現在の製品では多くが改善済みだが、DBは機能より初期設定で評価すべき
- スキーマレスはコストを後回しにしているだけ、という視点を持つ
