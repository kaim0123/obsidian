「SQLiteなのに、型チェックをしない」——業界のSQL常識から完全に外れた、ある設計選択。  
2026年、世界で稼働しているSQLiteデータベースの数、推定1兆個。  
  
40億のスマートフォン全てに搭載、iPhone、Android、Mac、Windows 10以降、Chrome、Firefox、Safari、Edge、すべての主要OS、すべての主要ブラウザ。Airbus A350、火星探査機まで。「世界で最もデプロイされたソフトウェアモジュール」の候補TOP5。  
  
ところが、SQLiteには、SQL業界の常識から完全に外れた、ある設計選択がある——「型が少ない、そして、型チェックをしない」。  
  
CREATE TABLE users (age INTEGER) でテーブルを作って、INSERT INTO users (age) VALUES ('twenty') を実行する。業界の常識では、エラー。Integerカラムに文字列は入らない。SQLiteでは、エラーにならない。  
文字列'twenty'は、そのまま、ageカラムに保存される。  
技術的には「Manifest Typing」（明示的型付け）——型は、カラムじゃなく、値そのものに付く。5つのstorage classだけ（NULL、INTEGER、REAL、TEXT、BLOB）。Type Affinityは「推奨」であり「強制」じゃない。SQLite公式は宣言する——「Flexible typing is a feature, not a bug」。  
なぜこの「変な」設計が、業界を制覇できたのか——5つの理由。  
  
動的言語との完璧な親和性（PHP、Python、Ruby、Perlの世界と一致）  
任意のtype name acceptance（MySQL、PostgreSQL、Oracleの方言を全て受け入れる）  
スキーマ事前定義なしの高速プロトタイピング  
ドキュメントDBの柔軟性 + SQLの能力  
Postel's Law（寛容に受け入れる）の完璧な体現  
  
そして2021年11月27日、SQLite 3.37.0でSTRICTテーブルが追加された——業界の流行が静的型に戻った時代への妥協。作者本人の極めて率直な発言——「最初からANY型を導入していれば、よかったかもしれない」。それでも、デフォルトは変更できない——「すでに数百万のアプリが柔軟な型に依存している」。  
SQLiteが業界に問いかける、深い真実——「設計選択は、正しい・間違いの軸じゃなく、文脈の軸で評価されるべき」。業界25年の「柔軟性 vs 厳格性」の永遠の議論を、たった1つのDBが、静かに、深く、答え続けています。

## 詳しい要約

**テーマ：SQLiteの柔軟な型システム（Manifest Typing）と、それでも世界で最も普及した理由**

SQLiteはSQL業界の常識に反して「型が少なく、型チェックをしない」設計だが、推定1兆個が稼働する世界で最もデプロイされたDBの一つになった。動的言語との親和性、他DBの方言の受容、プロトタイピング速度、NoSQL的柔軟性、Postelの法則という5つの理由で受け入れられ、2021年にはSTRICTテーブルを追加したがデフォルトは変えられない。設計選択は正誤ではなく文脈で評価すべき、という話。

---

### 第1章 SQLiteとは何か、業界の常識を超えた普及規模

- 2026年時点で稼働するSQLiteデータベースは **推定1兆個**。40億台のスマホすべてに搭載され、iPhone・Android・Mac・Windows 10以降、Chrome・Firefox・Safari・Edge、Airbus A350、火星探査機にも
- **リチャード・ヒップ** が2000年に作った **組み込み型DB**。MySQL・PostgreSQL・Oracleのようなサーバープロセスではなく、アプリの中にライブラリとして組み込まれる
- バイナリは2MB未満、データは1ファイルに保存
- 本体コード1行に対しテストコード約600行という異常な品質基準
- 長年「おもちゃ・プロトタイプ用」という偏見があったが、2025〜2026年に **Turso、Cloudflare D1** などの新プラットフォームが本番運用の主力に押し上げた（**SQLiteルネサンス**）

### 第2章 「型が少ない」の正体

- 通常のSQL DB（PostgreSQL・MySQL・Oracle・SQL Server）は **静的型**：カラムに型を付け、その型のデータしか入らない
- SQLiteは **Manifest Typing（明示的型付け）**：型はカラムではなく **値そのもの** に付く
  - `CREATE TABLE users (age INTEGER)` に `INSERT ... VALUES ('twenty')` をしてもエラーにならず、文字列がそのまま保存される
- **Storage Class は5つだけ**：NULL・INTEGER・REAL・TEXT・BLOB。VARCHAR・BOOLEAN・DATETIME・TIMESTAMP などは内部でこのどれかにマッピング
- **Type Affinity（型親和性）**：INTEGER と宣言しても「INTEGERが推奨」という意味であり「INTEGERしか入らない」ではない
- 型を一切書かずにテーブルを作ることもできる
- 公式の宣言：「**Flexible typing is a feature, not a bug**（柔軟な型はバグではなく機能）」

### 第3章 「型を諦めた」設計が業界制覇した5つの理由

1. **動的言語との完璧な親和性**：ヒップが当初想定したユーザーは Tcl プログラマー（全変数が文字列としても数値としても扱える）。PHP・Python・Ruby・Perl・JavaScript の値を型変換の心配なくそのまま入れられ、認知負荷が極端に低い
2. **任意の型名の受け入れ**：MySQL の TINYINT・MEDIUMTEXT・DOUBLE PRECISION、PostgreSQL の SERIAL・JSON・UUID、Oracle の NUMBER・VARCHAR2・CLOB など、他DBの方言をType Affinityに緩くマッピングして受け入れる → 移植性が極めて高い
3. **スキーマ事前定義なしの高速プロトタイピング**：データ構造を進化させながら開発できる
4. **ドキュメントDBの柔軟性＋SQLの能力**：MongoDB・Cassandra のようなスキーマレスの自由と、JOIN・トランザクション・ACID保証を両立
5. **Postelの法則の体現**：ジョン・ポステルの「送るものには厳格に、受け入れるものには寛容に」。変な型のデータもできる限り受け入れる

### 第4章 2021年STRICTテーブル追加、業界の流行変化への妥協

- 2021年11月27日、**SQLite 3.37.0** で **STRICTテーブル** を追加：INTEGERカラムに文字列を入れるとエラー、型宣言必須、使える型は INT・INTEGER・REAL・TEXT・BLOB・ANY の6つ
- 公式の説明：長らくPostelの法則に従ってきたが、業界は厳格な型チェックへ動いているので、それを期待する開発者のために選択肢を提供
- 背景：TypeScript、Pythonの型ヒント、Rubyの型定義ファイルなど、動的言語の世界が静的型を後付けで取り入れている
- 公式の率直な発言：「最初から **ANY型** を導入していればよかったかもしれない」（明示的に「何でも入る列」と宣言できたため）
- それでも **デフォルトは変えられない**：すでに数百万のアプリが柔軟な型に依存しており、壊さずに変更するのは不可能

### 第5章 柔軟性 vs 厳格性、SQLiteが問いかけるもの

- 業界の好みは振り子のように揺れてきた：
  - 1970〜90年代：静的型（C++・Java・Pascal・SQL）が主流
  - 1990年代後半〜2010年代：動的言語（Python・Ruby・JavaScript・PHP）の時代
  - 2010年代後半〜：TypeScript・型ヒントで再び静的型へ
- SQLiteは2000年に動的側で誕生し、2021年に静的の選択肢を追加、それでもデフォルトは動的 ― 25年の議論を1製品で体現
- 設計選択は **正しい/間違いの軸ではなく、文脈の軸** で評価すべき。1兆個のSQLiteも、PostgreSQLの厳格な型が支える業務システムも、どちらも正しい
- 使い分けの目安：
  - SQLiteの柔軟な型が生産性を最大化：プロトタイプ、組み込み、ローカルファースト、エッジコンピューティング
  - PostgreSQLの厳格な型が安全性を最大化：ミッションクリティカルな業務、大量の同時書き込み、複雑な制約

### まとめ

- SQLiteは値に型が付くManifest Typingと5つのStorage Class、推奨にすぎないType Affinityで「型チェックしない」DBになっている
- その柔軟さが動的言語との親和性や移植性などを生み、世界最大級の普及につながった
- STRICTテーブルで厳格モードも選べるが、互換性のためデフォルトは柔軟なまま
- 型の厳格さに絶対の正解はなく、用途（文脈）でDBを選ぶ
