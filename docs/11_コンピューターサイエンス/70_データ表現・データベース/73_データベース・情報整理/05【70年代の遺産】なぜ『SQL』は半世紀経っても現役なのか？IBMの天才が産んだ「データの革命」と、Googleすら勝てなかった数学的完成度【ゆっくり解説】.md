## 要約

**1970 年の数学的論文** から生まれた SQL（Structured Query Language＝構造化問い合わせ言語）は、大規模化批判や NoSQL ブームを経ても **半世紀以上現役** のまま、銀行・決済・業務システムの基盤を支え続けている。本動画は、IBM のジレンマ、オラクル創業、ACID 特性、NoSQL との攻防、Google Spanner による NewSQL 復活までをたどり、**「何が欲しいか」を宣言する思想** と **数学に根ざした設計** が SQL を生かし続ける理由を解説する。

### テーマ：50 年経っても現役の理由

- IT 業界は進歩が速く、スマホもフレームワークも数年で古くなるのに、**1970 年代生まれの SQL は今も世界中で動いている**（コンビニ決済、口座残高確認、ネットショッピングなど）。
- 一時は **NoSQL に主役を奪われかけた** が、現在は **NewSQL として最強の姿で復活** している。
- 発明者の論文は大企業に **製品化を躊躇** させ、ライバルに **先行者利益** を奪われ、**「死んだ」** と予測された——それでも生き残った **執念の物語**。

### SQL 以前：階層型・ネットワーク型の地獄

- **1960 年代**、企業向けコンピュータの普及とともにデータベースが登場。当時の主流は **階層型**（IBM の **IMS＝Information Management System** が代表）。
- 階層型は **木構造**（会社 → 部署 → 社員）で、目的のデータに辿り着く **ルートをプログラマーがすべてコードに書く** 必要があった。
- データ構造の要件変更（部署別 → プロジェクト別など）が起きると、**物理的な場所に依存したプログラムが全部壊れ、書き直し** になる——「住所を丸暗記していたのに表記法が変わった」状態。
- **ネットワーク型** は柔軟だが **ナビゲーションモデル** で、ポインタ構造をアプリ側が把握する必要があり、**データの物理構造への依存** という根本問題は未解決。
- エンジニアはビジネスロジックより **「データがどこにあるか」の迷宮探索** に時間を取られていた。

### E.F. コッドとリレーショナルモデル（1970 年）

- **E.F. コッド**（1923 年生、イギリス人、IBM 研究所の数学者）が **1970 年** に歴史的論文 **「大規模共有データバンクのためのデータのリレーショナルモデル」** を発表。
- 核心：**データがどこに物理的に保存されているかを人間が気にしなくていい** —— **論理構造と物理構造の完全分離**（プログラム独立性）。
- 比喩：図書館で本の棚番号を知らなくても、司書に「この本ください」と言えばよい。**人間は「何が欲しいか」だけを宣言** すればよい。
- この思想を **宣言型言語**（命令型＝手順を書くのと対比）と呼ぶ。SQL の `SELECT` は **「どう取るか」ではなく「何が欲しいか」** を書くだけ。
- コッドは **集合論** で定義：データを **テーブル（関係＝リレーション）** として扱い、集合演算（積集合など）で操作を記述。**数学に基づくからハードウェアや記憶媒体が変わっても本質は変わらない** —— 50 年生存の根本理由。

### SEQuel → SQL：言語の誕生と IBM のジレンマ

- **SQL 言語そのもの** を設計したのはコッドではなく、論文に触発された IBM の **チェンバリン（Chamberlin）** と **ボイス（Boyce）**。
  - コッド＝**思想の父**、SQL＝**思想を実装する言語**。
- 最初の名称は **SEQuel**（Structured English Query Language）。商標問題で **E を抜いて SQL** になった。
  - ベテランが **「シークェル（Sequel）」** と呼ぶのはこの名残。**SQL 派と SeQuel 派、どちらも間違いではない**。
- IBM 上層部は論文を **喜ばず製品化を躊躇**：
  - 当時 **IMS（階層型）が爆売り** → リレーショナル製品化は **自分の稼ぎ頭を壊す** こと（**イノベーションのジレンマ**）。
  - **System R** は社内研究プロジェクトとして進み、**商品化は後回し**。
- 論文は **Communications of the ACM** で公開され、誰でも読める状態だった。

### ラリー・エリソンとオラクル：先行者の誕生

- 論文を熱心に読んだ **ラリー・エリソン**（後のオラクル創業者）が「これは使える。先に製品化すれば勝てる」と判断。
- 論文は特許ではなく **アイデアに著作権もない**。公開された技術的知見を参考に **0 から独自実装** するのは合法。
- **1977 年** に **Software Development Laboratories（後の Oracle）** を設立。
- **1979 年**、オラクルが **世界初の商用 SQL データベース** をリース。
- IBM の System R は研究段階、IBM 初の商用製品 **SQL/DS** は **1981 年**。**DB2** も後発で、**先行者優位はオラクル** が握った。
- コッド本人は **1981 年にチューリング賞**（コンピュータ科学のノーベル賞）を受賞——製品化は遅れたが **学術的名誉** は得た。

### ACID：SQL が信頼される最大の理由

世界中の銀行が SQL を使い続ける理由は **ACID 特性**（Atomicity, Consistency, Isolation, Durability）。

| 特性 | 日本語 | 要点 |
|------|--------|------|
| **A** Atomicity | 原子性 | 処理は **全部成功するか、全部なかったこと** の 2 択。中途半端な状態は存在しない |
| **C** Consistency | 一貫性 | トランザクション前後で **有効な状態** を保つ（残高マイナス禁止、メール重複禁止など）。DB レベルで制約を守る |
| **I** Isolation | 独立性 | 複数ユーザーが同時操作しても **途中の半端な状態は見えない**（ダーティリード防止）。レベル（Read Uncommitted / Read Committed / Repeatable Read / Serializable）で整合性と性能のトレードオフ |
| **D** Durability | 永続性 | コミットしたデータは **停電・サーバー障害後も消えない**。多くは **WAL（Write-Ahead Logging）** で「先にログ、後で本番書き込み」 |

- 例：ATM で 10 万円振込 → ①自分の口座から引く ②相手に足す。**①だけ成功して停電** すると 10 万円が宙に浮く——これを **トランザクション（コミット / ロールバック）** が防ぐ。
- **「絶対に嘘をつかない」** 信頼感。金融では **99.9% 正確＝0 点、100% でなければならない**。

### 2000 年代：NoSQL ブームと「SQL は死んだ」

- インターネット普及で **データ規模が桁違い** に（Facebook、Google など億単位ユーザー）。
- 批判：**「SQL は古い・遅い・スケールしない」** —— ACID を守りながら複数サーバーに分散すると **整合性確認の通信コスト** が重い。
- **CAP 定理**：ネットワーク分断時、**整合性（Consistency）・可用性（Availability）・分区許容性（Partition tolerance）** を同時に完全には保てない——分散システムでは **必ずトレードオフ** が発生。
- **Google Bigtable**（2006 年論文）：行単位の原子的操作は保証するが **複数テーブルにまたがる分散トランザクションは捨てた** —— スピードとスケール優先。
- **2009 年頃 NoSQL 爆発**：Amazon **DynamoDB**、Facebook **Cassandra** など。スケール重視の主流選択肢に。
- SQL は銀行・基幹系で **細々と生き延び** ていたが、数年後に現実が牙を向く。

### NoSQL の限界と「車輪の再発明（バグ付き）」

- NoSQL 採用企業から **「整合性を自分たちで担保するのが地獄」** という声。
- ACID を捨てた結果、**アプリ側で ACID を手書き** する羽目に——SQL が自動でやっていたことを **自前再発明**（バグ入りやすい）。
- NoSQL の **結果整合性（Eventual Consistency）**：時間が経てばずれるが揃う——
  - SNS のいいね数が一瞬ずれるのは許容。
  - **在庫数・口座残高が「いずれ正しくなる」** では話にならない。

### Google Spanner と NewSQL：SQL の復活

- **2012 年**、Google が **Spanner** 論文を発表——世界中のデータセンターに分散しながら **ACID を完全保証する SQL ベース DB**。
- Google が SQL に「負けた」のではなく、**NoSQL の限界を超える次の段階** として SQL 思想を再採用。
- **NewSQL** ムーブメント：分散・高性能と SQL/ACID を両立——**CockroachDB**、**YugabyteDB**、**TiDB**、**PlanetScale** など。
- コッドの **論理構造と物理構造の分離** は分散時代も正しい——**どのサーバーにデータがあるかをユーザーが意識しない** 理想はそのまま。
- **Amazon** も DynamoDB 推進後、**Aurora**（MySQL / PostgreSQL 互換）で分散 SQL を強化。**みんな最終的に SQL 方向へシフト**。

### 2026 年現在：SQL の使われ方

- **伝統的 RDBMS**：PostgreSQL、MySQL、Microsoft SQL Server、Oracle Database——業務システムで現役。
  - **PostgreSQL** は Stack Overflow 調査で毎年上位。オープンソース、JSON 対応、PostGIS など **時代に合わせて進化**。
- **クラウドマネージド**：Amazon RDS、Google Cloud SQL、Azure Database——サーバー管理不要で SQL を利用。
- **NewSQL クラウド**：Google **Spanner**、**CockroachDB**、Amazon **Aurora** など。
- **AI × SQL（Text-to-SQL）**：LLM が自然言語を SQL に変換して実行——「先月の地域別売上を見せて」と聞くだけ。**UI は自然言語でも、裏側の基盤は SQL**。
- **DB-Engines ランキング** でも Oracle、MySQL、SQL Server、PostgreSQL が常に上位。NoSQL は **適材適所**（ドキュメント・グラフ・速度重視）に落ち着き、**「SQL は死んだ」予測は完全に外れた**。

### なぜ SQL は古びないのか

- 技術には **流行** と **本質的問題を解くもの** がある。SQL は後者。
- **「データを論理的に操作したい」** 欲求は、コンピュータが速くなっても分散されても変わらない。コッドは **数学で解いた** —— **数学は古びない**。
- SQL 自体も **ANSI 標準**（SQL-92、SQL:1999、SQL:2003…）で進化（ウィンドウ関数、JSON 操作など）。**変わらないのは宣言型の根本思想**。
- **SELECT / INSERT / UPDATE / DELETE** は製品間でほぼ共通——**1 つの言語を覚えれば複数 DB で使い回せる**。
- **どんなプログラミング言語（Java、Python など）でも、DB との通信は最終的に SQL** —— **データベースの共通語（lingua franca）**。

### 学習のすすめ

- エンジニアなら **SQL は必須**。AI 時代でも **生成されたクエリの良し悪しを判断** するには基礎が必要。
- 入門は **`SELECT … FROM … WHERE …`** から。ジョイン、サブクエリ、ウィンドウ関数、インデックス設計と **奥は深い** が、**入門は簡単**。
