## 詳しい要約

**テーマ：データベースが 430 種類以上に増え続ける構造的な理由**

DB-Engines に登録された DB は 2026 年時点で 430 以上。リレーショナルモデルで一度は統一された DB の世界は、Web 企業の規模・ハードウェアの変化・資本の論理という 3 つの力で増殖し続けている。DB が増えるのは分野が未成熟だからではなく、データの形とハードウェアが変わり続けるからであり、名前を覚えるより「生まれた理由」を読むべきだ、というのが結論。

---

### 序章 なぜ DB だけが増え続けるのか

- SQL は 1970 年代の発明で理論は枯れ、Oracle も PostgreSQL もある「解決済み」の分野のはずなのに、言語や OS より明らかに速いペースで新作が生まれている。

### 第1章 DB が 1 つに統一されていた時代

- 1970 年、IBM の研究者 **E.F. Codd** がリレーショナルモデルの論文を発表。それ以前は階層型の **IMS** やネットワーク型の **CODASYL** など、データの持ち方が固定された仕組みだった（現在は消滅）。
- Codd の発想は「データを表で持ち、問い合わせは数学で書く」。**アプリの都合とデータの持ち方を切り離した**。
- 1979 年に **Oracle** が商用化し、そこから約 30 年、DB の答えは実質 1 つになった。
- 統一できた理由：
  - 「何が欲しいか」だけ書けば DB が取り方を考える**宣言型の問い合わせ**。
  - **ACID 特性**のトランザクションがお金を扱うシステムの信頼を得た。
- 2000 年代前半までは「DB は選ぶものではなく、どの RDB にするか決めるもの」（MySQL か Oracle か PostgreSQL か）。

### 第2章 統一を壊した Google と Amazon

- 壊したのは **Web のスケール**、具体的には Google と Amazon という当時すでに巨人だった企業。
- 2006 年 Google が **Bigtable**、翌 2007 年 Amazon が **Dynamo** の論文を公開。「RDB では自社の規模をさばけないので別物を作った」という告白だった。
- 理論的裏付けは 2000 年にエリック・ブリュワーが提唱した **CAP 定理**（一貫性・可用性・分断耐性を同時に満たせない）。スケールを取るなら RDB の厳密な一貫性を部分的に諦める必要がある。
- 2009 年、サンフランシスコの勉強会で非リレーショナル DB 群に **NoSQL** という名前がつき、MongoDB・Cassandra・Redis などが続々登場。
- Cassandra（2008 年 Facebook）は Dynamo の分散方式と Bigtable のデータモデルを掛け合わせた設計で、初期 NoSQL はほぼすべて**あの 2 本の論文の子孫**だった。

### 第3章 ハードウェアが変わると DB が生まれる

- DB の内部構造は**その時代のハードウェアの写し鏡**。
- RDB の索引に使う **B ツリー**は、回転する磁気ディスク（HDD）のシーク待ちを減らすため木を浅く保つ設計。
- **SSD** はランダム読み込みが速い一方、書き込みに消去という重い処理が伴う → 書き込みを追記にまとめる **LSM ツリー**が主役に。代表が 2013 年に Facebook が公開した **RocksDB**。
- **RAM** が安くなり、全データをメモリに載せる Redis が成立。
- 分析用途では列ごとに固める**カラムナ型**が伸び、**ClickHouse** や **DuckDB**（2019 年オランダの研究機関 CWI 発、SQLite のように 1 ファイルで動く分析特化 DB）が生まれた。
- ハードウェアの前提が 1 つ変わるたびに最適な設計が変わり、新しい DB が必要になる。

### 第4章 DB は外されない商売である

- 2020 年 9 月、**Snowflake** が NYSE に上場し、初日の時価総額は約 700 億ドル。ソフトウェア企業として史上最大級の IPO。
- DB は**一度採用されたらまず外されない**。アプリのフレームワークは移行できてもデータ移行は桁違いに重く、顧客は 10 年単位で払い続ける。SaaS の理想型。
- **MongoDB** は 2017 年上場で時価総額は一時 400 億ドル超。オープンソースのドキュメント DB が巨大企業になれると証明した。
- VC 資金が DB スタートアップに流入。2023 年にはベクトル DB の **Pinecone** が 1 億ドルを調達。生成 AI で埋め込みベクトル検索という新しいデータの形が出た瞬間、専用 DB が量産された。
- 時系列（InfluxDB、TimescaleDB）、グラフ（Neo4j）なども同様。「**専用 DB は汎用 RDB より速い**」という技術的事実と「**専用 DB は独立した会社として成立する**」という経済的事実がかみ合い、増殖が止まらない。

### 最終章 増えるのに淘汰されない理由

- 退場した DB も多い：2016 年に有望株の **RethinkDB** が会社ごと清算、**FoundationDB** は 2015 年に Apple に買収され公開版が一度引き上げられた。
- 逆流も起きている：**PostgreSQL の拡張機能**がベクトル検索（pgvector）、時系列（TimescaleDB）、地理情報（PostGIS）を取り込み、専用 DB が開拓した市場を後から飲み込む。2026 年上半期の DB-Engines で人気スコアを最も伸ばしたのも PostgreSQL。
- 今の DB 界は「**専用 DB が新しい形を開拓し、成功した形だけを PostgreSQL が標準機能として回収する**」生態系。新 DB は危険を冒す実験部隊の役割。
- 新しい DB を見たときの判断基準：
  1. 新しい**ハードウェアの都合**で生まれたのか
  2. 新しい**データの形**で生まれたのか
  3. **資本の都合**だけで生まれたのか
  - 最初の 2 つなら学ぶ価値がある。最後だけなら 5 年後に存在しない可能性が高い。

### まとめ

- DB は一度リレーショナルに統一されたが、Web の規模（Bigtable・Dynamo・CAP 定理）がそれを壊した。
- 増殖エンジンは「ハードウェアの変化」と「外されにくい商売としての資本」の 2 つ。
- 一方で PostgreSQL が成功した形を拡張で吸収しており、淘汰と回収も同時に進んでいる。
- 名前を追うのではなく、その DB がどの変化から生まれたのかを見抜けば 430 種は少数のパターンに畳める。
