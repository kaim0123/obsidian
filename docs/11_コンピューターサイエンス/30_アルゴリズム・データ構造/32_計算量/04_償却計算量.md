# 償却計算量

## 🎯 このページのゴール

- 「償却計算量（amortized complexity）」という考え方を理解する
- なぜ `list.append()` が「O(1)」と言えるのかを説明できる
- 「最悪ケース」だけ見ると損をするケースを知る

> 前提: [01_計算量の基礎](01_計算量の基礎.md) / [02_時間計算量](02_時間計算量.md) を読んでから読むとスムーズです。

---

## 1. 「最悪ケース」だけ見ると不公平なときがある

普通のBig-Oは **「1回の操作の最悪ケース」** を表します。

でも現実には、**たまにだけ重い処理があって、ほとんどは一瞬で終わる** 処理がたくさんあります。

例えば：

> 「100回の操作のうち、99回は1秒、1回だけ10秒かかる」

これを「最悪ケース = 10秒」だけで評価すると、実際の感覚と合いません。
**1回あたり平均すると (99×1 + 10) / 100 ≒ 1.09秒** ですよね。

こういう **「ならして見たときの1回あたりのコスト」** を表すのが **償却計算量** です。

---

## 2. 一番わかりやすい例：動的配列（Pythonのリスト）

Pythonの `list.append()` や Java の `ArrayList.add()` は
**「O(1) で追加できる」** と説明されます。なぜでしょうか？

### 配列は本当はサイズが固定

配列は内部的には **連続したメモリ領域** で、サイズは作った時点で決まっています。

```
[_, _, _, _]    ← 容量4の配列
```

要素を追加していくと：

```
[A, _, _, _]    # 1個目追加
[A, B, _, _]    # 2個目追加
[A, B, C, _]    # 3個目追加
[A, B, C, D]    # 4個目追加 → 容量いっぱい！
```

ここでもう1個追加しようとすると、**空きがない**。

### どうするか: 倍のサイズの新しい配列を作って全コピー

```
旧:  [A, B, C, D]                      ← 容量4
     ↓ 2倍に拡張してコピー
新:  [A, B, C, D, E, _, _, _]          ← 容量8
```

このコピー作業は **O(n)** かかります。

### 整理すると

- ほとんどの `append`: **O(1)**（空きがあるので末尾に置くだけ）
- たまの `append`: **O(n)**（容量を倍にしてコピー）

これだけ見ると「最悪 O(n) じゃん」となりますが…

---

## 3. ならして計算すると O(1) になる

16個の要素を追加する場合を考えます（容量は1から始まり、足りなくなったら2倍にする）。

| 追加 | 操作 | コスト | 容量 |
|------|------|--------|-----|
| 1 | 置く | 1 | 1 |
| 2 | 拡張(2)→置く | 1+1 | 2 |
| 3 | 拡張(4)→置く | 2+1 | 4 |
| 4 | 置く | 1 | 4 |
| 5 | 拡張(8)→置く | 4+1 | 8 |
| 6 | 置く | 1 | 8 |
| 7 | 置く | 1 | 8 |
| 8 | 置く | 1 | 8 |
| 9 | 拡張(16)→置く | 8+1 | 16 |
| 10〜16 | 置く | 各1 | 16 |

**総コスト** = 1 + 2 + 3 + 1 + 5 + 1 + 1 + 1 + 9 + 7 = **31**

**1回あたりの平均** = 31 / 16 ≒ **1.9回**

→ **n個追加しても、総コストは約 2n** なので、1回あたりは **ならすとO(1)**。

### なぜこう言えるのか（直感的な説明）

拡張は「n個のときに発生」→「次は2n個のとき」→「次は4n個のとき」…と、
**回数が減っていく**ので、重い処理の総コストが支配的にならないのです。

```
拡張コスト:  1 + 2 + 4 + 8 + 16 + ... ≒ 2n （等比数列の和）
軽いappend: n回 × 1 = n

合計 ≒ 3n
1回あたり ≒ 3 → O(1)
```

---

## 4. 用語: 償却O(1) と言うときの意味

| 呼び方 | 意味 |
|-------|------|
| **最悪計算量 O(n)** | 1回の操作で最悪n回かかる可能性がある |
| **償却計算量 O(1)** | 連続して使うと、1回あたり平均して定数時間 |

`list.append` を正確に言うと:
- 最悪: **O(n)**
- 償却: **O(1)**

日常会話では **「appendはO(1)」** と略すことが多いです（= 償却O(1)の意味）。

---

## 5. 平均計算量との違い

似た用語に「**平均計算量（average-case complexity）**」がありますが、意味が違います。

| 用語 | 何を平均する？ | 例 |
|------|--------------|-----|
| **平均計算量** | **ランダムな入力** に対する期待値 | クイックソートは平均 O(n log n)、最悪 O(n²) |
| **償却計算量** | **連続した操作** をならした値 | append の償却 O(1) |

- 平均 = 「**入力の確率**」でならす
- 償却 = 「**操作の回数**」でならす

---

## 6. 他の償却O(1)の例

### Stack / Queue の push / pop
動的配列ベースなら、同じ理屈で償却O(1)。

### ハッシュテーブルの挿入
- 要素が増えるとバケットを拡張（rehash）
- 1回の拡張はO(n) だが、頻度が下がるので償却O(1)

### Union-Find（素集合データ構造）
- 経路圧縮とランクを使うと、1操作あたり **ほぼO(1)**（正確には逆アッカーマン関数）
- これも償却計算量の典型例

---

## 7. 償却が使えない場面に注意

「**1回1回のレイテンシが重要**」な場面では、償却の考え方が通用しません。

### 例: リアルタイムシステム

- ゲームの60FPS処理: 1フレーム16ms以内に終わらないと **カクつく**
- 「平均すると速い」では不十分
- たまのO(n)が **可視化されてしまう**

こういう場面では **最悪ケースのO(1)** を保証するデータ構造が必要（例: リアルタイムデック）。

### 例: サーバーのp99レイテンシ

- 100リクエスト中99回が10msでも、1回が1秒かかると **p99 = 1秒**
- ユーザー体験としては「遅いサービス」

**最悪ケースを見たいか、平均を見たいか** で判断が変わります。

---

## 8. まとめ

- 償却計算量 = **連続した操作をならしたときの1回あたりのコスト**
- 代表例: `list.append` の **償却 O(1)**
- たまの重い処理も、**頻度が十分低ければ** ならすと軽い
- 「平均計算量」とは違う（あちらは入力の確率でならす）
- **リアルタイム性が必要な場面では使えない** ことに注意
