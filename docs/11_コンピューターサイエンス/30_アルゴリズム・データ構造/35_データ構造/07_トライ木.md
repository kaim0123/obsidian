# トライ木（文字列検索用途）

## 概要

**トライ木（Trie / プレフィックス木）** は、**文字列の集合を効率よく格納し、プレフィックス（先頭部分）検索を超高速で行う** ための専用データ構造です。名前は "retrieval"（検索）から来ていますが、読みは「トライ」です。

> **「辞書を木の形で保存する」のがトライ木**

- ハッシュテーブル: キー全体が一致するかしかわからない
- トライ木: **「この文字列から始まる単語はある？」** が自然に扱える

オートコンプリート、スペルチェック、IME、ルーティングテーブルなど、**「先頭が一致するもの」** を求めたい場面で圧倒的に強い構造です。

---

## なぜ重要なのか

検索エンジンやエディタで文字を入力した瞬間に候補がずらりと出るのを見たことがあるはずです。あれを素朴に実装すると、毎回全単語を線形検索することになりますが、トライ木を使えば、

- **検索**: 入力文字列の長さだけの操作で済む — **O(L)**（L は文字列長）
- **プレフィックス列挙**: 該当するサブツリーを辿るだけ
- **複数単語の辞書**: 共通プレフィックスを共有するのでメモリ効率も良い

という驚異的な性能を実現できます。「単なる木の一種」と侮れない重要な武器です。

---

## 基本構造

### イメージ

文字列集合 `{"cat", "car", "card", "dog"}` をトライ木で表すと：

```
              (root)
             /      \
            c        d
           /          \
          a            o
         / \            \
        r   t*           g*
       /|
      d* (end marker)
```

- 各ノードは **1文字** を表す（または辺に文字がある）
- ルートから葉への **パスが1つの文字列**
- `*` 印は「ここで単語が終わる」を示すフラグ

### ポイント

- "car" と "card" は **"car" を共有** している
- "cat" と "car" は **"ca" までを共有** している
- 共通プレフィックスを **1回だけ** 保存するので、多くの単語で重複が減る

## 実装

### ノード構造

```javascript
class TrieNode {
  constructor() {
    this.children = {};   // 文字 → TrieNode の対応
    this.isEnd = false;   // ここで単語が終わるか
  }
}

class Trie {
  constructor() {
    this.root = new TrieNode();
  }

  insert(word) {
    let node = this.root;
    for (const ch of word) {
      if (!node.children[ch]) {
        node.children[ch] = new TrieNode();
      }
      node = node.children[ch];
    }
    node.isEnd = true;
  }

  search(word) {
    let node = this.root;
    for (const ch of word) {
      if (!node.children[ch]) return false;
      node = node.children[ch];
    }
    return node.isEnd;
  }

  startsWith(prefix) {
    let node = this.root;
    for (const ch of prefix) {
      if (!node.children[ch]) return false;
      node = node.children[ch];
    }
    return true;
  }
}

const trie = new Trie();
trie.insert("cat");
trie.insert("car");
trie.insert("card");
trie.insert("dog");

console.log(trie.search("car"));       // true
console.log(trie.search("ca"));        // false (単語終わりではない)
console.log(trie.startsWith("ca"));    // true
console.log(trie.search("carp"));      // false
```

### 単語集(辞書)からプレフィックス候補を列挙

```javascript
function findWithPrefix(trie, prefix) {
  let node = trie.root;
  for (const ch of prefix) {
    if (!node.children[ch]) return [];
    node = node.children[ch];
  }
  const results = [];
  function dfs(n, path) {
    if (n.isEnd) results.push(path);
    for (const [ch, child] of Object.entries(n.children)) {
      dfs(child, path + ch);
    }
  }
  dfs(node, prefix);
  return results;
}

findWithPrefix(trie, "ca"); // ["cat", "car", "card"]
```

## 計算量

L = 単語の長さ、A = アルファベットのサイズ（英字なら26）、N = 単語の数。

| 操作 | 計算量 |
|---|---|
| 挿入 `insert(word)` | O(L) |
| 検索 `search(word)` | O(L) |
| プレフィックス判定 `startsWith(prefix)` | O(L) |
| プレフィックスで始まる単語列挙 | O(L + 結果の文字数合計) |
| メモリ | O(N · L) 最悪（共有で実際は少ない） |

**挿入・検索が単語数 N に依存しない** のが核心。辞書に100万語あっても、1語を引くのは「その語の長さだけ」で済みます。

---

## ハッシュテーブルとの比較

| 特徴 | トライ木 | ハッシュテーブル |
|---|---|---|
| 単一キー検索 | O(L) | O(L)（ハッシュ計算） |
| プレフィックス検索 | **O(L) で自然** | 不可能（全走査必要） |
| キーの列挙順 | **辞書順で出せる** | 順序なし |
| メモリ使用量 | 単語が多く共通プレフィックスがあれば有利 | シンプルで小さい |
| 実装の複雑さ | やや複雑 | 組み込みが多く簡単 |

単なる「この単語があるか？」だけならハッシュテーブルで十分。**「〇〇で始まるものを全部」** という要求があればトライ木の出番です。

## 応用例

### 1. オートコンプリート

```
入力: "pro"
        │
        ▼
  トライ木で "pro" まで辿る
        │
        ▼
  その下のサブツリーをDFSして、全単語を列挙
        │
        ▼
  ["programming", "project", "progress", "process", ...]
```

検索バーに文字を打つたびに O(L) で候補を取り出せます。候補のランキングには別途スコアを持たせるのが普通。

### 2. スペルチェック

辞書に登録された単語の集合をトライで持ち、入力単語をチェック。
さらに、**編集距離1以内の候補** を列挙したい場合はトライを使った枝刈りで高速化できます。

### 3. IME（日本語入力）

「かな → 漢字」の変換候補を高速に出すためにトライが使われます。ローマ字入力なら「か → ka, ki, ke, ko, ku」の分岐をトライで表現。

### 4. ルーティングテーブル（ネットワーク）

IP アドレスの **最長プレフィックス一致** をトライで高速化（**Patricia Trie**、**圧縮トライ**と呼ばれる）。ルーターの経路決定で実用されている。

### 5. DNA 配列の検索

ATCG の4文字アルファベットで短い配列を多数格納するなど、バイオインフォマティクスでも活用。

### 6. T9 ケータイ入力・共通語幹検索

日本語のテキスト入力補助、多言語辞書の高速検索などにも応用される。

## 発展形

### 圧縮トライ（Radix Tree / Patricia Trie）

「1文字ずつ分岐するノード」が連続するとメモリ効率が悪いので、**複数文字をまとめたラベル** を辺に持たせる圧縮版。Linuxのルーティングやetcdのキーストレージで使われます。

```
通常トライ:          圧縮トライ:
    c                    c-a-r-d*  （一本化）
    │
    a
    │
    r
    │
    d*
```

### サフィックストライ / サフィックスツリー

**ある文字列のすべての接尾辞** を格納した木。全文検索、パターンマッチ、バイオインフォマティクスで強力。構築がやや複雑。

### アホ・コラシック法

複数のパターンを同時に検索する古典アルゴリズム。**トライ木 + 失敗リンク** で実装され、ウイルス対策ソフトのパターンマッチに使われる。

### DAWG（有向非循環単語グラフ）

共通サフィックスも共有して、さらにメモリを削る発展形。

## よくある間違い

### 1. 子ノードをオブジェクトで持ちすぎてメモリ浪費

英字26文字しか使わないのに固定長の長さ26の配列を全ノードに持たせると、空き要素が多数生まれメモリを大量消費します。疎な場合は **マップ（オブジェクト）** で持つ方が省メモリ。密な場合は配列で持つ方が速い。

### 2. 単語終わりフラグの付け忘れ

`isEnd` フラグを立て忘れると、`"cat"` は登録されているが `search("cat")` が false を返す、というバグになります。

### 3. Unicode を意識しない

日本語や絵文字を扱う場合、「1文字」の単位が文字（コードポイント）なのかバイト列なのかを意識しないとバグる。JavaScript なら `for (const ch of str)` がコードポイント単位で安全。

### 4. ハッシュテーブルで十分な場面でトライを使う

プレフィックス検索が不要なら、シンプルなハッシュテーブルの方が速く簡単です。**「プレフィックスや辞書順が本当に必要か」** を自問してから選びましょう。

---

## まとめ

### 重要なポイント

1. **トライ木は「文字列の集合」を効率的に扱うための専用構造**
2. **検索・挿入・プレフィックス検索がすべて O(L)**（文字列長のみに依存）
3. **共通プレフィックスを共有するためメモリも意外と効率的**
4. **オートコンプリート、スペルチェック、IME、ルーティングなど応用が豊富**
5. **プレフィックス検索が不要ならハッシュテーブルの方が手軽**
