# 配列とリスト（連続領域 vs 連結リスト）

## 概要

**配列（Array）** と **連結リスト（Linked List）** は、複数の値を並べて保持するための最も基本的なデータ構造です。どちらも「順番に並んだデータの集まり」を表しますが、**メモリ上の配置の仕方**が根本的に異なり、その違いが性能のトレードオフを生みます。

> **配列は「番地が連続している棚」、連結リストは「次の棚の場所を書いたメモ付きの箱」**

この違いを理解すると、「なぜあるケースでは配列が速くて、別のケースでは連結リストが有利なのか」が論理的に説明できるようになります。

---

## なぜ重要なのか

多くのプログラミング言語では `List`、`Array`、`Vector` といった型が用意されており、普段は中身の実装を意識しなくても使えます。しかし、

- 100万件のデータを扱うと急に遅くなる
- メモリ使用量が予想より多い
- 挿入が遅い／検索が遅い

といった問題に直面したとき、**「今使っているのは配列なのか連結リストなのか」** を理解していないと原因が特定できません。データ構造選定のミスは、アルゴリズムを工夫する前の、もっと根本的な性能問題を生みます。

---

## 配列（Array）とは

### イメージ

配列は、**メモリ上の連続した領域** にデータを並べて置いたものです。

```
メモリアドレス:  1000  1004  1008  1012  1016
                 ┌───┬───┬───┬───┬───┐
配列 arr:        │ 3 │ 7 │ 1 │ 9 │ 4 │
                 └───┴───┴───┴───┴───┘
インデックス:     [0]  [1]  [2]  [3]  [4]
```

各要素が 4 バイトの整数なら、「先頭アドレス + インデックス × 4」で任意の要素の位置を **計算だけで** 求められます。つまり、どれだけ大きな配列でも、インデックス指定による読み書きは一定時間で終わります。

### 特徴

- **ランダムアクセスが速い**: `arr[1000000]` も `arr[0]` も同じ速さ（O(1)）
- **メモリ効率が良い**: データ本体以外の追加情報（ポインタなど）が不要
- **キャッシュ効率が良い**: CPUは連続したメモリをまとめて高速メモリ（キャッシュ）に読み込むため、順番に走査する処理が非常に速い
- **サイズが固定（原則）**: あらかじめ確保した領域を超えることはできない

### コード例

```javascript
// JavaScript の配列
const arr = [3, 7, 1, 9, 4];

console.log(arr[2]); // 1 (瞬時)
arr[2] = 100;        // 書き換えも瞬時
console.log(arr.length); // 5
```

```python
# Python の list (実体は動的配列)
arr = [3, 7, 1, 9, 4]
print(arr[2])  # 1
```

## 動的配列（Dynamic Array）

実際の言語で使われる配列の多くは、サイズが自動で増える **動的配列** です（C++ の `vector`、Java の `ArrayList`、Python の `list`、JavaScript の `Array` など）。

### 仕組み

1. 初期容量（たとえば 10 個分）を確保する
2. 要素を末尾に追加していく
3. 容量が満杯になったら、**2倍の大きさ** の新しい領域を確保して全データをコピーする
4. 古い領域を解放する

```
容量4の配列が満杯:
[3][7][1][9]  容量=4

5個目を追加する時:
[3][7][1][9][5][ ][ ][ ]  容量=8 (2倍に拡張, 全データコピー)
```

### なぜ「2倍」にするのか

毎回1つずつ増やすと、N個追加するのに「1回目は1コピー、2回目は2コピー…」と累積で O(N²) の時間がかかります。2倍ずつに増やすと、**N個追加しても総コピー回数は 2N 程度** に収まり、1要素あたり平均 O(1)（償却計算量と呼びます）になります。

### ここがポイント

- **末尾への追加**: 普段は O(1)、拡張時だけ O(N) だが平均すれば O(1)
- **先頭・途中への挿入**: 後ろの要素を全部ずらす必要があり O(N)
- **途中の削除**: 穴埋めのため後ろをずらす必要があり O(N)

## 連結リスト（Linked List）とは

### イメージ

連結リストは、**バラバラの場所に置かれたデータ同士が「次の場所を書いたメモ（ポインタ）」でつながっている** 構造です。

```
HEAD ──┐
       ▼
    ┌─────┬─────┐   ┌─────┬─────┐   ┌─────┬─────┐
    │  3  │  ●──┼──▶│  7  │  ●──┼──▶│  1  │null │
    └─────┴─────┘   └─────┴─────┘   └─────┴─────┘
    node1           node2            node3 (末尾)
```

各ノード（箱）は「値」と「次のノードへの参照」を持ちます。末尾のノードは「次はない（null）」を指します。

### 単方向と双方向

- **単方向連結リスト**: 次だけを指す（上の図）
- **双方向連結リスト**: 前と次の両方を指す。逆方向の走査ができる代わりに、各ノードが1つ分多くメモリを使う

```
双方向リスト:
null ◀──┬─┬────┬────┬─┬──▶ ◀──┬─┬────┬────┬─┬──▶ null
       │●│ 3  │ ●  │●│        │●│ 7  │ ●  │●│
       └─┴────┴────┴─┘        └─┴────┴────┴─┘
```

### 特徴

- **先頭への挿入・削除が速い**: ポインタを1〜2個書き換えるだけ O(1)
- **途中への挿入・削除が速い**（場所が分かっていれば）: O(1)
- **インデックス指定は遅い**: 先頭から順に辿るしかなく O(N)
- **メモリ使用量が多い**: 値そのものに加えて「次を指す情報」を1要素ごとに持つ
- **キャッシュ効率が悪い**: メモリ上で要素がバラバラに散らばっているため、順次走査でも配列より遅くなることが多い

### コード例（自作の単方向連結リスト）

```javascript
class Node {
  constructor(value) {
    this.value = value;
    this.next = null;
  }
}

class LinkedList {
  constructor() {
    this.head = null;
  }

  // 先頭に追加 - O(1)
  prepend(value) {
    const node = new Node(value);
    node.next = this.head;
    this.head = node;
  }

  // 末尾まで走査 - O(N)
  print() {
    let current = this.head;
    while (current !== null) {
      console.log(current.value);
      current = current.next;
    }
  }
}

const list = new LinkedList();
list.prepend(1);
list.prepend(7);
list.prepend(3); // 結果: 3 → 7 → 1
list.print();
```

## トレードオフの比較表

| 操作 | 配列（動的配列） | 連結リスト |
|---|---|---|
| インデックスでアクセス `arr[i]` | **O(1)** | O(N) |
| 末尾に追加 | O(1) 償却 | O(1)（末尾ポインタを持てば） |
| 先頭に追加 | O(N) | **O(1)** |
| 途中に挿入（位置既知） | O(N) | **O(1)** |
| 途中から削除（位置既知） | O(N) | **O(1)** |
| 値の検索（線形探索） | O(N) | O(N) |
| メモリ使用量 | 小さい（値のみ） | 大きい（ポインタ分） |
| キャッシュ効率 | **◎ 非常に良い** | △ 悪い |

太字が「より速い／有利な」側です。

## 実用上の重要な真実：連結リストは意外と遅い

教科書的には「挿入・削除が速いから連結リストが有利」と書かれがちですが、**現代のCPU環境では、連結リストは思っているほど速くありません**。

### なぜか

- CPUはメモリを読むとき、周囲の数百バイトをまとめて **キャッシュ** に読み込む
- 配列は要素が連続しているので、1つ読めば次の要素もキャッシュに乗っている
- 連結リストはノードがバラバラに配置されるので、**毎回メモリを取りに行く「キャッシュミス」が発生**
- 結果として、単純な走査では連結リストは配列より **数倍〜数十倍遅い** ことも珍しくない

### 実践的な指針

- **「挿入・削除が多いから連結リスト」は安易に選ばない**
- 要素数が小さい（数千以下）なら、ほぼ常に配列のほうが速い
- 連結リストが本当に有利なのは、**要素が非常に多く、かつ頻繁に中間挿入・削除が発生する** 場合や、**要素のポインタを他の場所で保持していて直接ノードを操作できる** 場合

多くの場面では「動的配列で十分」というのが、実運用でのリアルな答えになります。

## どちらを選ぶべきか

### 配列が向いている場面

- インデックスで頻繁にアクセスする（例: `arr[i]` で i 番目を取得）
- データを順番に走査する（ループでの集計・変換）
- データサイズが大きく、メモリ効率が重要
- 末尾への追加・削除が中心

**例**: 画像のピクセル配列、CSVのレコード、検索結果のリスト、スコアの集計

### 連結リストが向いている場面

- 先頭への頻繁な追加・削除（キューの実装基盤など）
- すでに手元にノードの参照があり、そこから挿入・削除する
- データ全体のサイズが予測できず、連続領域の確保が困難
- 要素を別のデータ構造（ツリーなど）と共有したい

**例**: LRUキャッシュの実装、一部のスケジューラ、教科書レベルのスタック・キューの説明

## よくある間違い

### 1. 「リスト」という名前に惑わされる

多くの言語では `List` という名前が **動的配列** を指します。

- Java の `ArrayList` → 動的配列
- Python の `list` → 動的配列
- C# の `List<T>` → 動的配列

一方、**連結リスト** は `LinkedList` のように明示された別の型であることが多いです（Java の `LinkedList`、C++ の `std::list`）。名前だけで判断せず、**ドキュメントで中身の実装を確認** しましょう。

### 2. 途中挿入のために連結リストを選んだが、位置を毎回検索している

```javascript
// ❌ 連結リストで i 番目に挿入 - 位置を探すのに O(N)、挿入は O(1) で合計 O(N)
list.insertAt(1000, value); // 結局 O(N)
```

「挿入自体は O(1)」ですが、**挿入位置まで辿るのに O(N)** かかるため、インデックス指定で挿入するなら連結リストのメリットは消えます。

### 3. 動的配列の拡張コストを誤解する

「動的配列は拡張時に全コピーするから遅い」と思われがちですが、拡張は **指数的に稀** になります（2倍ずつ拡張するので、拡張は log N 回しか起きない）。一要素あたりで均せば O(1) です。これを **償却計算量** と呼びます。

## まとめ

### 重要なポイント

1. **配列はメモリ連続、連結リストはポインタでつながる**
2. **配列はインデックスアクセスとキャッシュ効率で圧勝**
3. **連結リストは先頭・途中の挿入削除で有利 - ただし位置が既知の場合のみ**
4. **現代CPUではキャッシュの影響が大きく、連結リストは理論ほど速くない**
5. **迷ったら動的配列を選ぶのが実用上の正解**

### チェックリスト

- [ ] インデックスアクセスが頻繁か？ → 配列
- [ ] 末尾以外への挿入・削除が多いか？ → 連結リスト候補（ただし要素数を考慮）
- [ ] 要素数は数千以下か？ → ほぼ確実に配列で良い
- [ ] 使っている言語の `List` は動的配列か連結リストか確認したか？
