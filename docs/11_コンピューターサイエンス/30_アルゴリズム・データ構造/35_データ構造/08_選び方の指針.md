# 選び方の指針（ユースケース別データ構造選定）

## 概要

データ構造は **「どの操作を高速にしたいか」で選ぶもの** です。魔法のように万能な構造は存在せず、必ず **得意と不得意** があります。このページでは、データ構造の選定を **「使い方のパターン」→「最適な構造」** の視点で整理します。

> **「何を格納するか」より、「どう操作するか」で選ぶ**

---

## なぜ重要なのか

実務でパフォーマンス問題の大半は「**アルゴリズムの問題というより、データ構造の選択ミス**」です。

- 「配列の中から要素を探す処理をループで書いたら、データが増えた瞬間に遅くなった」
- 「メモリがやたら多く使われるが、原因が特定できない」
- 「挿入は速いのに検索が遅い、逆もまた然り」

これらは、**操作のパターンに合わない構造を選んでしまった** のが原因です。使い方から逆算する習慣をつければ、設計の段階でこの種の問題を避けられます。

---

## 選定の3つの軸

### 1. どんな操作が多いのか

- 検索が多い？ 挿入が多い？ 削除が多い？ 順次処理？
- ランダムアクセス？ 順番にたどるだけ？

### 2. 順序は必要か

- 挿入順を保ちたい？ キーの昇順で処理したい？ 順序は不要？

### 3. データサイズは

- 数十？ 数千？ 数百万？
- メモリに収まる？ 収まらない？

これらを組み合わせて、最適な構造を選びます。

---

## ユースケース別の早見表

### ユースケース: 順番にデータを処理したい

**例**: ログ1行ずつ処理、CSVの全行を集計、ピクセル配列を変換

| 条件 | 推奨 |
|---|---|
| 末尾追加 + 順次走査 | **動的配列** |
| 要素数が膨大でメモリ懸念 | ストリーム処理（配列に溜めない） |

👉 迷ったら **配列** で正解です。キャッシュ効率が圧倒的。

---

### ユースケース: インデックスで要素を取り出したい

**例**: 「100番目の要素は？」、行列演算

| 条件 | 推奨 |
|---|---|
| サイズ固定 | **静的配列** |
| サイズ可変 | **動的配列** |

👉 **連結リストは避ける**（インデックスアクセスが O(N)）。

---

### ユースケース: 先頭・末尾の追加・削除が頻繁

**例**: キューの実装、先頭追加の多いアプリ

| 条件 | 推奨 |
|---|---|
| 末尾のみ | **動的配列** |
| 先頭のみ、または両端 | **双方向連結リスト / 両端キュー (Deque)** |

👉 JavaScript の `Array.shift()` は O(N) なので注意。

---

### ユースケース: キーから値を取り出したい

**例**: ユーザーID → ユーザー情報、URL → キャッシュ

| 条件 | 推奨 |
|---|---|
| 順序不要・最速でアクセス | **ハッシュテーブル（Map, Dict）** |
| キー順の列挙が必要 | **自己平衡二分探索木（TreeMap）** |
| 挿入順を保ちたい | **順序付きマップ**（Java: LinkedHashMap, Python: dict 3.7+） |
| プレフィックス検索 | **トライ木** |

👉 デフォルトは **ハッシュテーブル**。範囲検索や順序が必要になったら木に切り替え。

---

### ユースケース: 重複を除きたい、存在判定

**例**: 「このIDは処理済み？」、集合演算

| 条件 | 推奨 |
|---|---|
| 存在判定のみ | **ハッシュセット** |
| 順序付き集合 | **TreeSet / SortedSet** |

👉 `O(N²)` のループは、**ほぼ必ずハッシュセットで O(N)** に改善できます。

---

### ユースケース: 常に最大・最小を取りたい

**例**: ダイクストラ、スケジューラ、Top K、中央値ストリーム

| 条件 | 推奨 |
|---|---|
| 最大または最小のみ | **二分ヒープ（優先度付きキュー）** |
| 両方必要 | **2つのヒープ** または **TreeMap** |
| 動的に値を更新したい | インデックス付きヒープ or 平衡木 |

👉 ソートし直すのは無駄。ヒープで O(log N)。

---

### ユースケース: 範囲検索・順序付き操作

**例**: 「30歳以上40歳以下を列挙」、時刻が指定範囲内のイベント

| 条件 | 推奨 |
|---|---|
| 一般的な範囲検索 | **自己平衡二分探索木（TreeMap, std::map）** |
| 読み出しのみで更新少 | **ソート済み配列 + 二分探索** |
| 区間の集約（合計・最大など） | **セグメント木 / BIT** |

👉 ハッシュは範囲検索できない。順序が絡むなら木系を選ぶ。

---

### ユースケース: 文字列検索

**例**: オートコンプリート、スペルチェック、パターンマッチ

| 条件 | 推奨 |
|---|---|
| プレフィックス検索 | **トライ木** |
| 部分文字列検索 | **サフィックス配列 / サフィックストライ** |
| 複数パターン同時検索 | **アホ・コラシック法（トライ + 失敗リンク）** |
| 単純な完全一致 | **ハッシュセット** |

---

### ユースケース: 関係・ネットワークを表現

**例**: SNS、地図、依存関係、Webリンク

| 条件 | 推奨 |
|---|---|
| ノード数少・辺が密 | **隣接行列** |
| ノード数多・辺が疎 | **隣接リスト** |
| 連結性判定・グループ分け | **Union-Find（素集合データ構造）** |

---

### ユースケース: LIFO / FIFO の順序制御

| 用途 | 推奨 |
|---|---|
| 後入れ先出し（履歴、再帰の手動化） | **スタック** |
| 先入れ先出し（ジョブ処理、BFS） | **キュー** |
| 両端操作 | **Deque（両端キュー）** |
| 優先度順 | **優先度付きキュー（ヒープ）** |

---

## 意思決定フローチャート

```
[格納したいデータは？]
   ├─ キー付きの値のペア
   │    ├─ 順序不要 → ハッシュテーブル
   │    ├─ キー順 → 自己平衡二分探索木 (TreeMap)
   │    ├─ 挿入順 → 順序付きマップ
   │    └─ プレフィックス検索 → トライ木
   │
   ├─ 重複除去・存在判定
   │    └─ ハッシュセット
   │
   ├─ 優先度・最大最小取り出し
   │    └─ ヒープ / 優先度付きキュー
   │
   ├─ 関係性・ネットワーク
   │    └─ グラフ (隣接リスト / 行列)
   │
   └─ 単なる並び
        ├─ インデックスアクセス多 → 動的配列
        ├─ 先頭追加多 → 連結リスト or Deque
        ├─ LIFO → スタック
        └─ FIFO → キュー
```

## 代表的な「この場面ではこれ」集

### 1. 配列から重複を除く

```javascript
const unique = [...new Set(arr)];
```

ハッシュセット で O(N)。

### 2. 2つの配列の共通要素

```javascript
const a = new Set(arrA);
const common = arrB.filter(x => a.has(x));
```

O(N + M)。

### 3. 最も出現回数が多い単語

```javascript
const count = new Map();
for (const w of words) count.set(w, (count.get(w) || 0) + 1);
// 上位 K なら → 最小ヒープで Top K
```

### 4. LRU キャッシュ

- **ハッシュテーブル + 双方向連結リスト**
- ハッシュでキー→ノードを O(1) 参照
- 連結リストで「使った順」を管理、古いものから削除

### 5. オートコンプリート

- **トライ木** にすべての単語を挿入
- プレフィックスまで辿り、サブツリーをDFSして候補列挙

### 6. ダイクストラ

- グラフは **隣接リスト**
- 未訪問の中で最小コストを取り出すのに **二分ヒープ**

### 7. イベントシミュレーション

- 次に起きるイベント（時刻最小）を取るので **優先度付きキュー**

### 8. トポロジカルソート（ビルド順）

- グラフは **隣接リスト + 入次数カウント**
- 入次数0のノードから **キュー** で広げる（Kahn's algorithm）

## 常に意識すべきトレードオフ

### 時間 vs 空間

ハッシュテーブルは高速だが、バケット配列でメモリを余計に使う。動的配列は密だが、拡張時に倍のメモリを一時的に要する。

### 最悪 vs 平均

ハッシュテーブルは平均 O(1) だが、最悪は O(N)。リアルタイム処理で「最悪どうしても O(log N) に抑えたい」なら平衡木を選ぶ。

### 実装の手軽さ vs 性能

自作で平衡木や圧縮トライを書くより、言語標準の `TreeMap` や `Map` を使うほうが速くバグが少ない。**標準ライブラリを最優先** に。

### キャッシュ効率

理論計算量だけで決めると、連結リストやポインタを多用する構造が有利に見える。しかし、現代CPUでは **連続メモリ（配列）を走査する方が数倍〜数十倍速い** ことも多い。迷ったら配列ベースを優先。

## よくある罠

### 1. 「とりあえずリスト」

データ構造の選定を後回しにして、とにかく全部配列（リスト）で書く → 後で O(N²) や O(N³) の処理が爆発。**最初から選ぶ** 習慣が大切。

### 2. 過度な最適化

データが100件しかないのに凝った構造を使うと、実装の複雑さだけが増えて意味がない。**サイズに応じたシンプルさ** を選ぶ。

### 3. 言語仕様を誤解

- Python の `list` = 動的配列（連結リストではない）
- Java の `LinkedList` = 双方向連結リスト（`ArrayList` の方が高速なことが多い）
- JavaScript の `{}` = オブジェクトだがキーは文字列化される、純粋な辞書には `Map` を使う

**ドキュメントで実装を確認** してから選ぶこと。

### 4. 順序を仮定する

ハッシュテーブルは一般に順序を保証しません（Python 3.7+ の `dict` は挿入順保証という例外あり）。**順序が意味を持つなら、保証のある構造を選ぶ**。

### 5. 「これ一つで全部」を期待

どのデータ構造にも弱点があります。1つの問題に対して **複数の構造を組み合わせる**（例: LRUキャッシュ = ハッシュ + 連結リスト）のはよくあるパターン。

---

## まとめ

### 重要なポイント

1. **データ構造は「どの操作を速くしたいか」で選ぶ**
2. **操作パターンと順序要件・データサイズの3軸で考える**
3. **迷ったら動的配列、キー付きならハッシュテーブルから始める**
4. **順序・範囲検索が必要になったら木、プレフィックスならトライ、優先度ならヒープ**
5. **言語標準のライブラリを最大限活用する**
6. **単一構造で解けないなら、複数を組み合わせる**

### 設計時のチェックリスト

- [ ] 最も頻繁に行う操作は何か？
- [ ] その操作の最悪計算量は許容できるか？
- [ ] 順序・一意性・範囲などの要件はあるか？
- [ ] データサイズはどのくらいか？ 成長するか？
- [ ] 使う言語のライブラリに、最適な既製品があるか？
- [ ] 実装の複雑さと性能のバランスは合っているか？
