# チェック例外と非チェック例外

## 2種類の例外
Javaなど一部の言語では例外を**2種類**に分けます。
- **チェック例外（Checked Exception）**: コンパイラが処理を強制
- **非チェック例外（Unchecked Exception）**: 強制されない

## チェック例外

### 特徴
- コンパイル時に**処理（catchまたはthrows宣言）が必須**
- 無視するとコンパイルエラー
- 「予見できる例外的状況」を表す

### 例（Java）
```java
public void readFile(String path) throws IOException {
    BufferedReader br = new BufferedReader(new FileReader(path));
    // ...
}
```
呼び出し側:
```java
try {
    readFile("a.txt");
} catch (IOException e) {
    // 必ず書かないとコンパイルエラー
}
```

### 代表例
- `IOException`
- `SQLException`
- `ClassNotFoundException`
- `InterruptedException`

## 非チェック例外

### 特徴
- 処理しなくてもコンパイルできる
- 主に**プログラミングミス**を表す
- `RuntimeException` とその子孫

### 例（Java）
```java
int[] arr = new int[3];
arr[10] = 1;  // ArrayIndexOutOfBoundsException（非チェック）
```

### 代表例
- `NullPointerException`
- `ArrayIndexOutOfBoundsException`
- `IllegalArgumentException`
- `IllegalStateException`
- `ClassCastException`

## Javaの例外階層
```
Throwable
  ├─ Error            （システム障害、通常捕捉しない）
  │    ├─ OutOfMemoryError
  │    └─ StackOverflowError
  └─ Exception        （アプリ側の例外）
       ├─ チェック例外
       │    ├─ IOException
       │    └─ SQLException ...
       └─ RuntimeException  ← 非チェック
            ├─ NullPointerException
            └─ ...
```

## チェック例外のメリット

### ① 見落としを防ぐ
呼び出し側に対応を強制できる。
```java
// 例外処理を書かないとビルドが通らない
public String readConfig() throws IOException { ... }
```

### ② シグネチャに情報が載る
どんな例外が起きうるかAPIから明示的に分かる。

### ③ 重要な例外を握り潰しにくい
チェック例外は意識せざるを得ないので、無視されにくい。

## チェック例外のデメリット

### ① ボイラープレートが増える
```java
try {
    doSomething();
} catch (IOException e) {
    throw new RuntimeException(e);  // ラップし直すだけ…
}
```

### ② ラムダとの相性が悪い
```java
list.forEach(s -> readFile(s));  // コンパイルエラー（IOException）
```

### ③ 例外の伝搬が面倒
各階層で `throws` を書き続ける必要がある。

### ④ 下層の変更が上層に伝染
例外を投げるメソッドを増やすと、呼び出し側すべてを修正。

## 言語ごとのアプローチ

### Javaのみチェック例外を採用
後発の多くの言語は非チェックに寄せています。

### C# / Kotlin / Scala / JS / Python
**すべて非チェック例外**。開発者の判断で捕捉する。

### Rust / Go
**例外をそもそも使わない**。`Result<T, E>` や戻り値でエラーを表現する。型システムで処理忘れを防ぐ。

```rust
fn read_config() -> Result<String, io::Error> { ... }

match read_config() {
    Ok(s)  => println!("{}", s),
    Err(e) => eprintln!("error: {}", e),
}
```

## チェック例外 vs Result型

| 観点 | チェック例外 | Result型 |
|---|---|---|
| 処理強制 | ○ | ○（型で） |
| シグネチャで明示 | △（1つの例外型に集約されがち） | ○ |
| 構文的負担 | 大 | 小（`?` 演算子等） |
| 表現力 | スタックトレース・継承階層 | 列挙型・パターンマッチ |
| 合成しやすさ | 弱い | 強い（`map`, `and_then` 等） |

Result型の方が**扱いやすく関数合成と相性が良い**と評価されることが多い。

## 実務での使い分け（Java）

### 非チェックにすべき場合
- **プログラミングミス**: 引数不正、状態不正 → `IllegalArgumentException`
- **APIの利用者が復旧不能**なエラー
- **復旧してもしょうがない**システム例外

### チェックにすべき場合（限定的）
- 呼び出し側が**意味のある対処**ができる時
- ライブラリ境界で明示したい時

### 実践的な流儀
- 多くのモダンJavaフレームワーク（Spring など）は**非チェック中心**
- 新規設計では `RuntimeException` 派生に統一する考え方も一般的

## 例外の包み直し
チェック例外を非チェックで包む一般的なテクニック。
```java
public String read(String path) {
    try {
        return Files.readString(Path.of(path));
    } catch (IOException e) {
        throw new UncheckedIOException(e);
    }
}
```

## Kotlinのアプローチ
Javaに互換性を保ちつつ、**すべて非チェック扱い**。
```kotlin
fun readFile(path: String): String {
    return File(path).readText()   // IOException だが catch 強制なし
}
```
必要なら自分で `try/catch` する、という設計。

## チェック例外批判の論点
- **関数型プログラミングとの不一致**（ラムダで扱いにくい）
- **インターフェースの変更が重い**（throws連鎖）
- **握りつぶしを助長**（面倒なので `catch` して何もしない）
- **情報が集約されて失われる**（`Exception` で catch しがち）

## まとめ
- **チェック例外**はコンパイラが処理を強制する例外（Java特有）
- **非チェック例外**は強制されない（プログラミングミスが中心）
- Java以外の多くの現代言語は非チェック、または `Result` 型で代替
- 長所は「見落とし防止」、短所は「ボイラープレート増」「ラムダとの不相性」
- 実務では **非チェック中心 + 必要な所だけ型で表現** が主流
