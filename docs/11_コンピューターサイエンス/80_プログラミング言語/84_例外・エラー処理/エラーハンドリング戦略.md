# エラーハンドリング戦略

## エラーハンドリングとは
エラーや例外に対して**どう対処するかの方針**を設計することです。場当たり的に `try/catch` するのではなく、アプリ全体で一貫した戦略を持つと保守性が大きく変わります。

## エラーの分類

### 1. 想定内エラー（ビジネス上の失敗）
- バリデーションエラー
- 認証失敗
- 在庫不足
- リソース未発見（404）

→ 呼び出し元で**適切に対応できる**。戻り値や専用型で扱う。

### 2. 想定外エラー（バグ・障害）
- NullPointerException
- DB接続断
- メモリ不足

→ 復旧困難。**ログ・アラート・再起動**で対応。

## 主なエラー伝達方法

### ① 例外（throw / raise）
```javascript
throw new Error("予期せぬ状態");
```
- Java, Python, JS の伝統的な方法
- 呼び出し元に暗黙的に伝播

### ② 戻り値（Go式）
```go
user, err := fetchUser(id)
if err != nil { return err }
```
- 明示的、シンプル
- 書き忘れのリスク（静的解析で補う）

### ③ Result / Either型（Rust, Haskell）
```rust
fn fetch_user(id: u32) -> Result<User, FetchError> { ... }

let user = fetch_user(id)?;   // 失敗なら即returnされる
```
- 型で成功/失敗を表現
- `map`, `and_then` などで合成

### ④ Optional / Maybe
```rust
fn find(id: u32) -> Option<User> { ... }
```
- 値が「無いかもしれない」を型で表現
- null の代わり

### ⑤ コールバック / Promise reject（非同期）
```javascript
fetch("/api").then(ok).catch(fail);
```

## 戦略①: フェイルファスト（Fail Fast）
おかしな状態を検知したら、**その場で止める**。
```python
def divide(a, b):
    if b == 0:
        raise ValueError("ゼロ除算")
    return a / b
```
- バグを早期発見できる
- 曖昧な状態を引きずらない

対になる考えは「フェイルセーフ」（なるべく止めず縮退）。

## 戦略②: 境界で集約する（Error Boundary）

### 層ごとに分離
```
[エントリー層]   ← ここで最終的に catch（ユーザー向けエラー表示など）
     ↓
[サービス層]     ← ビジネスエラーは自分で処理、その他は上へ
     ↓
[インフラ層]     ← 低レベルエラーを意味のある型に包んで上へ
```

### 例（Web API）
```typescript
// 最上位ハンドラでまとめて処理
app.use((err, req, res, next) => {
  if (err instanceof ValidationError) return res.status(400).json(...);
  if (err instanceof NotFoundError)   return res.status(404).json(...);
  logger.error(err);
  res.status(500).json({ error: "Internal" });
});
```

## 戦略③: エラーを型で表現する
各失敗モードを型にすると、呼び出し側が漏れなく対応できる。

```typescript
type CreateUserError =
  | { kind: "DuplicateEmail" }
  | { kind: "WeakPassword" }
  | { kind: "DBError"; cause: Error };

function createUser(x: UserInput): Result<User, CreateUserError> { ... }
```

網羅性チェックが働き、新しい失敗モードが増えた時もコンパイラが教えてくれる。

## 戦略④: リトライとバックオフ
ネットワークなど一時的な失敗は**再試行**で解決することがある。

### 指数バックオフ
```javascript
async function retry(fn, max = 5) {
  for (let i = 0; i < max; i++) {
    try { return await fn(); }
    catch (e) {
      if (i === max - 1) throw e;
      await sleep(2 ** i * 1000);  // 1s, 2s, 4s, 8s...
    }
  }
}
```

### リトライしない操作
**冪等でない**操作（課金、メール送信）をそのまま再実行すると二重処理になる。冪等化キーが必要。

## 戦略⑤: サーキットブレーカー
連続失敗が続く相手先への呼び出しを**一時的に遮断**して、自サービスを守る。Netflix Hystrix, resilience4jなどが有名。

```
状態遷移: Closed ─失敗多発→ Open ─一定時間後→ Half-Open ─成功→ Closed
```

## 戦略⑥: タイムアウト
無期限に待たない。すべての外部呼び出しにタイムアウトを設定。
```javascript
await fetch(url, { signal: AbortSignal.timeout(5000) });
```

## 戦略⑦: フォールバック / 縮退運用
エラー時に**代替手段**を返す。全停止よりまし。
```javascript
try {
  return await recommendAPI();
} catch {
  return popularItems();    // キャッシュ済み人気アイテムを返す
}
```

## 戦略⑧: ログ・監視・アラート
エラーは**記録し、観測する**ことが最も重要。
- ログレベル: DEBUG / INFO / WARN / ERROR / FATAL
- 集約: ELK / Datadog / Sentry / CloudWatch
- アラート: しきい値を超えたら通知

### ログに含めるべき情報
- タイムスタンプ
- リクエストID（追跡用）
- ユーザーID
- スタックトレース
- 入力値（機密情報は除く）

## ユーザー向けメッセージ vs 内部メッセージ

### ユーザー向け
- わかりやすく
- セキュリティ情報を漏らさない
- 対処方法を提示

```
「メールアドレスまたはパスワードが正しくありません」
（× 「ユーザーは存在するがパスワードが違う」）
```

### 内部向け（ログ・監視）
- 詳細なスタックトレース
- 原因究明に必要な情報を網羅

## アンチパターン

### ① 握り潰し（空catch）
```java
try { risky(); } catch (Exception e) { }
```
何が起きたかわからなくなる。最低限ログを残す。

### ② 粗すぎる catch
全部 `catch (Exception)` で受けると、想定外まで飲み込む。

### ③ 無意味なラップ
単に再送出するだけの `catch / throw` は害しかない。

### ④ 過剰防御
`null` チェックや `try/catch` を至る所に入れて、本当のエラーが埋もれる。

### ⑤ エラーコードの乱用
`-1`, `0`, `""` など「エラーっぽい値」を返すのは混乱の元。

## チェックリスト
- [ ] 想定内/想定外を区別しているか
- [ ] エラー型が明確か
- [ ] 境界（API入口・DB・外部呼び出し）で処理しているか
- [ ] タイムアウトとリトライが設定されているか
- [ ] ログに十分な情報があるか
- [ ] ユーザー向けメッセージは安全かつ親切か
- [ ] 機密情報（パスワード、トークン）がログに漏れていないか

## まとめ
- エラーは**想定内/想定外**を分けるのが出発点
- 例外 / 戻り値 / Result型 など**伝達方法**を統一
- 境界で集約・型で表現・**ログと監視**を徹底
- 外部呼び出しには**タイムアウト・リトライ・サーキットブレーカー**
- 握りつぶし・粗すぎるcatch・過剰防御は避ける
