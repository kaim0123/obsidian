#オブジェクト指向 #歴史

## 詳しい要約

直也テックによる、**Casey Muratori**（KC村鳥）の講演 *The Big OOPs: Anatomy of a Thirty-five-year Mistake*（BSC 2025）の解説。命題は「オブジェクト指向は失敗だったのか」ではなく、**現実世界の分類をコンパイル時の継承階層として直訳し、そこにカプセル化の境界を引く設計**が、約35年にわたるすれ違いだった、という一点に絞られる。教科書の「乗り物→車」継承を起点に、1998年のゲーム実装から1960年代の源流、Simula→C++→Smalltalkの伝言ゲームまで遡り、明日から使える3原則で締める。

### 第1章 1998年の反逆 — Looking Glass と ECS

入口は1998年のゲーム会社 **Looking Glass**（代表作 *Thief: The Dark Project*）。当時の主流は次の二極だった。

| 設計 | 内容 |
|------|------|
| **ファットストラクト** | 1つの構造体に全データを詰め、タイプフィールドで敵／アイテムを区別。メモリ約2MB時代の現実解 |
| **継承階層の OOP** | Entity を頂点に NPC・アイテムと継承。現実の分類をクラス親子に写す「先進的」流行 |

Looking Glass は第3の道を選ぶ。エンティティを**データなしのただの ID** にし、物理・戦闘などの**システムの側**に配列でデータを置く。ID をキーに各システムへ問い合わせる。商用ゲームとして世界初の **Entity Component System（ECS）**。後の Unity / Unreal でも主流になる形の最初の実例が、1999年頃のこの系譜だった、と直也は位置づける。

動画全体の最重要キーワードは **カプセル化の境界線**。アーキテクチャ設計とは、どこに壁を作りどこを通りやすくするかの問題。

| | OOP（従来） | Looking Glass |
|--|-------------|---------------|
| 境界の引き方 | **オブジェクトの周り**（メックならメックの知っている全てを1カプセル） | **システムの周り**（物理は物理、戦闘は戦闘） |

実装者の一言が本編の出発点になる。「なぜか OOP はドメインモデルと一致するコンパイル階層という発想に囚われてしまった。ドメインモデルはユーザーが体験するものであればいい。**コードはコードにとって都合のいい形で書くべきだ**」。

誤解への釘：OOP の全てが失敗ではない。Muratori が「35年間の間違い」と呼ぶのは、**現実の分類→コンパイル時継承＋そこに境界を引く**という一点だけ。証拠として、C++ 設計者 **Bjarne Stroustrup** 本人の論文が、図形を switch で分岐するのを悪い例、Shape 継承＋仮想関数を正解として売り込んでいることを挙げる。

「世界をそのままモデリングできるから理解しやすい」は嘘か、という疑問への答えは、**人間が理解するためのモデルと、プログラムが効率よく動く構造は一致させなくてよい**、というもの。Looking Glass のエディタでは外側は綺麗な階層に見え、裏側はシステムごとの配列だった。外側は人間向き、内側はコンピュータ向き——切り離してよい。

コメント欄の要点として、ECS を RDB に喩える読み（コンポーネント＝テーブル、エンティティ＝主キー、システム＝問い合わせ）や、ID で表す発想が **E. F. Codd** のリレーショナルモデル（1969年頃）と同型だという指摘も紹介する。

### 第2章 源流への旅 — Ross / Sketchpad / Hoare

行き先は1950年代アメリカ。**Douglas Ross**（ダグラス・ロス）が MIT サーボ機構研究所に着任。人間が言葉で部品を記述し、計算機が工作機械を動かす（CAD / 3Dプリンタの祖先的プロジェクト）。同時代、レコードは磁気テープ上のデータ区切りであり、メモリ上に構造体を作る発想自体がまだ薄い。

| 年頃 | 人物・出来事 | 要点 |
|------|-------------|------|
| 1960 | **John McCarthy** が Lisp 発表 | 全てがポインタ2つの箱（リスト） |
| 1960 | Ross が論文で反論 | 大きなものは大きなまま直接格納せよ。リスト辿りはメモリと時間を食う。**データの持ち方が性能を決める** |
| 同 | Ross の **plex（プレックス）** | データ・他 plex へのポインタ・処理切替フラグが同居。実質的な **struct の起源**。Muratori 曰く「struct は plex と呼ばれるべきだった」 |
| 同 | plex 内の関数ポインタ | 差し替えで動作を変える＝**仮想関数の原型** |
| 1963 | **Ivan Sutherland** の **Sketchpad** | TX-2 上の世界初級の対話型お絵かき。ライトペンで掴んで動かす体験を発明 |
| 1966 | **Tony Hoare**「Record Handling」 | **サブクラス**（継承階層の設計図）と、**判別共用体**（型安全なデータ分岐）を提案 |

Sutherland がデータモデリングで相談した相手が Ross。Sketchpad の線・点は plex 思想で実装された。本当の衝撃は制約ソルバー（垂直・円の中心など宣言すると計算機が解く）。内部はリング構造で、変数・制約・図形が繋がり、**コンパイル時のクラス階層は存在しない**。制約が点や数値に直接触れる「オムニシエント（全知）」——カプセル化の真逆。**データを隠さなかったことが力の源泉**であり、種類ごとにデータを持ち処理側が横断する構造は実質 ECS と同発想、と直也は読む。

1963年の Sketchpad と1998年の *Thief* のあいだ——この**35年**がタイトルの意味だとされる。

現代との接続：当時はメモリが少なかったから並べただけ、という反論には「逆」と答える。今は CPU に対しメモリ遅延がボトルネック（メモリの壁）。オブジェクトを散らばせてポインタ辿りするとキャッシュミスが増え、**60年代の「データを実機に並べる」発想こそ現代ハードを生かす**、という読み。

整理：構造体、関数ポインタ、データ指向の実行時構造、サブクラス、型安全な判別共用体——**1966年までに道具は揃っていた**。

### 第3章 伝言ゲーム — Simula → C++ → Smalltalk

舞台はノルウェー。**Ole-Johan Dahl** と **Kristen Nygaard** の **Simula**（シミュレーション言語）。窓口の客・荷物の流れなどを記述し混雑を統計で見る、今でいう業務シミュレーションに近い。Simula 67 でコード再利用に悩み、「料金所のある橋を車が渡る——トラックかもバスかも」というたとえから **クラス継承** が生まれる。教科書の乗り物クラスは後付け説明ではなく、発明者本人の悩みそのものだった。

ここで目的の違う2つが同じ機能に混ざる。

| 用途 | 例 | 性質 |
|------|-----|------|
| 実装の再利用 | Car が Link を継承（リンクリスト載せ） | コード使い回し |
| ドメイン分類の表現 | Truck / Bus が Car を継承 | 現実の分類の写し |

仮想関数も「クラスごとに処理を差し替えたい」という素朴な動機から。大規模チーム論や設計思想の分析は登場していない。Muratori：「もし当時ジェネリクス（テンプレート）があったら、クラスという概念は生まれてすらなかったかもしれない」。

意外な事実：Simula には **inspect 文**（Hoare 流の型で安全に分岐するスイッチ）があり、仮想関数と型分岐を場面で選べた。

次の受け手は1978年、ケンブリッジの院生 **Bjarne Stroustrup**。専門は分散システム。実験用マシンを多数買えずシミュレータを書くため Simula を使い、直系の弟子筋でもあった。クラスがシミュレート対象にそのまま対応する体験に絶賛。ここが核心だと直也は言う——ドメインが**物理的に隔離されたコンピュータ同士**で、メモリに触れず通信だけ。**モデリング対象が最初からカプセル化されていた特殊ドメイン**だった。

プロジェクト拡大で崩壊：コンパイルが極端に遅い、実行時間の大半（例として約80%）をほぼゴミのない GC が食う。結局型チェックほぼなしの **BCPL** で書き直し。「Simula の思想に恋をして実装に裏切られた」体験が C++ を決める。Bell Labs で **C with Classes**（後の C++）へ——C の速度と Simula の書き心地のいいとこ取り。型チェック導入への貢献は「文句なしに偉大」と評価しつつ、private / const の由来が OS・ハードウェアのメタファー（プロセス保護、ファイル書き込み権限）であること、カプセル化が「大規模チームのため」という証拠は歴史記録上ほぼ見当たらないことにも触れる。

運命の分岐：Simula の2道具のうち、Stroustrup は**判別共用体を意図的に捨てた**。「外部からオブジェクトの型を見分けられるのはモジュール性を壊す悪」という理屈で、仮想関数＋継承階層に一本化。結果、Hoare が完成させ Simula が実装していた安全なデータ分岐は C++ で没収され、Java / C# も知らずに育ち、Rust や TypeScript で再発見されるまで数十年——これが伝言ゲームの代償。

もう一つの継ぎ足しは **Smalltalk**。**Alan Kay** が「オブジェクト指向」という言葉を作った人。分子生物学のバックグラウンドから、細胞のメッセージ協調が理想、という物語は有名だが、一次資料では汎用オブジェクト→Rectangle→Window→Browser の派生図や、図形クラス継承が標準ライブラリに実在する。有名な「本質はメッセージ」発言は2003年のもので、それより10年前には「継承は強力だが誰も使いこなせなかった」とぼやいており、**最初からの信念というより経験を経ての軌道修正**だった可能性が高い、と直也は読む。

家系図のどこを探しても「大規模チームのための設計分析」の根拠は出ず、あったのはコード再利用の悩み・個人研究の体験・それぞれの美学。天才たちが強力なカプセル化を推したのは、分散システムや細胞のように**物理的に隔離されメッセージしかできない世界**では正解だから。マイクロサービスや Web API はその延長。すれ違いの本質は、**同一メモリ空間で密に連携するプログラム内部に、その境界を細かく引きすぎた**こと。

Muratori 自身の告白：1998年頃、18歳でレベルエディタを作り、教科書通り OOP（大量の getter/setter、複数選択用の「影の階層」）で悪夢の二重管理に陥る。後から見ればプロパティをシステム側に置き ID で引く＝ECS そのものだった。「Looking Glass と同じ問題を解いていた。違いは彼らが上手で私が下手だっただけ」。今も検索上位の OOP チュートリアルは、ヒーロー継承・乗り物継承・自転車クラス——**1967年の橋とトラックのたとえが、今も初心者の最初の一歩**として教え続けられている。

### 第4章・3原則 — 明日からどう書くか

| 原則 | 内容 |
|------|------|
| **1. 境界線** | 現実の分類（ユーザー・商品）ではなく、**処理のまとまり**（認証・決済・在庫）に引く。Looking Glass / Sketchpad の教え |
| **2. 継承よりコンポジション** | extends で縦に積む代わりに、機能を持ち物として組み合わせる。「プレミアムユーザーはユーザーである」ではなく「ユーザーが課金情報を持つ」 |
| **3. C++ が捨てた宝を拾う** | 判別共用体／タグ付き union。分岐でコンパイラが型を絞り、書き忘れもエラーに。Hoare 1966 の型安全スイッチを今拾い直せる |

クラスを全部捨ててデータ指向に書き直す必要はない。捨てるべきは**現実の分類をそのまま継承にし、そこに境界を引く習慣**だけ。クラスもインタフェースも適所では強力。Muratori 自身も今も C++ を使い、批判しているのは言語全体ではなくあの設計パターン。**データの形と処理の流れを先に考え、階層は最後の手段**にする順番の入れ替えで見通しが良くなる、と締める。

*System Shock 2* のモッダー証言：一見 OOP っぽいオブジェクト階層はあるが、それはデータの整理方法であってコードのアーキテクチャではない。デザイナーは継承で気持ちよく組み立て、エンジニアはコンポーネント配列を操作する——**人間には階層を、コンピュータには配列を**。

タイトルの35年：1963年 Sketchpad は答えのそばにいたが、世界が戻るのは1998年の *Thief* まで。悪意ではなく、もっともらしいたとえ話が強すぎたことによる壮大なすれ違い。Alan Kay の言葉「最も質の悪いメタファーとは、しばらくうまく機能してしまうメタファーだ。より強力な洞察の誕生を咳止めしてしまうから」。問いへの答えは、失敗だったのはたった一つの使い方。**道具に罪はなく、境界線を引くのはいつだって私たち自身**。
