## 詳しい要約

**つるチャンネル** による、モナド解説（約16分）。定義や「自己関手の圏におけるモノイド対象」から入らず、ユーザー→住所→郵便番号をつなぐときに同じ null チェックを何度も書きたくない、というコード上の問題から **Optional → flatMap → モナド部品 → 他の型 → モナド則** まで組み立てる。Haskell・圏論の前提は不要で、JavaScript / TypeScript が読めれば追える内容。主張の核は、モナドは「箱」ではなく **ある文脈を持った計算を、その文脈を保ったまま次の計算へつなぐ仕組み** だということ。

### 出発点：型が合っているあいだは平和

やりたいことは三つだけ——ID からユーザー、ユーザーから住所、住所から郵便番号を取り出す。前の返り値の型と次の受け取り型がぴったり合っていれば、値をそのまま渡して関数をつなぐだけでよい。

問題は、ユーザー取得がいつもうまくいくとは限らないこと。返り値が「ユーザー」から「ユーザーまたは null」に変わると、次の関数（ユーザーを要求する）に渡せない。だから渡す前に null チェックして打ち切る。住所取得・郵便番号取得も同様に失敗しうるので、同じ確認が3回になる。処理が2〜3個ならまだよいが、増えるたびに確認も増え、本題と確認の主役が入れ替わる。入れ子で書くと、確認のたびに本題が右へ一段ずつ押し出される。

### Optional：値と「ないかもしれない」を一つの型に

手元にあるのはユーザーそのものではなく、「見つかったかもしれない／見つからなかったかもしれない」という状態。値と存在可否がバラバラだと、使う側が毎回確かめることになる。そこで二つを一つの型にまとめる。

| 状態 | 意味 |
|------|------|
| **Some** | 中に値が入っている |
| **None** | 値がない（null の言い換えではない） |

この型を動画では **Optional** と呼ぶ（言語によっては **Maybe**。振る舞い差には踏み込まず自作のみ使用）。大事なのは、持っているのが値そのものではなく **値が今どういう状況にあるか**＝**文脈** だという点。

### Optional だけでは足りない：「箱を開ける」と同じ形

住所取得が欲しいのは `User`。手元は `Optional<User>`。素朴には箱を開けて Some なら中身を渡し、None なら None を返す——動くが、次もその次も同じ。名前が Optional に変わっただけで、null 確認と同じ形で各量は減らない。

面倒なのは箱を開けること自体ではなく、開けたあとに有無を毎回自分で確かめていること。確かめ方は3回とも同じなのでまとめられる。

### 発想の逆転：箱を開けるのをやめ、関数を箱に渡す

次にやりたい関数を箱に預ける。その関数も失敗しうるので返り値は `Optional`。預かった箱が関数を実行するとまた箱が返る → **箱の中に箱**（`Optional<Optional<住所>>`）になる。だから一段にならす。この「ならす」が **flat**。

| 箱の状態 | 振る舞い |
|----------|----------|
| 中身あり | 預かった関数を実行し、帰ってきた箱をそのまま返す |
| 中身なし | 関数を呼ばず **None** を返す |

有無の判断は使う側ではなく箱が持つ。この操作が **flatMap**（言語によっては bind / chain）。中身の差し替えだけなら **map** で足りる。flatMap が要るのは、預ける関数側も文脈つきの値を返すから。

flatMap 本体は数行——あれば関数を呼んで包み直さず返し、なければ None。ここに3回分の確認が一度だけ書かれている。使う側は `flatMap` で住所取得・郵便番号取得を預けていくだけ。失敗時は None が最後まで流れ、以降の関数は実行されない。確認も値の取り出しもない。**文脈を保ったまま処理をつないでいる**。

### モナドの仮定義と部品三つ

ここまでで得た形に名前をつける。

> 値をある文脈に入れ、その文脈を保ったまま次の計算へつなげる仕組み。ただし次の計算も文脈つきの値を返す。これがモナド。

箱・文脈・flatMap はすべて途中に出てきた。呼ぶために必要なのは **部品三つ＋守るべきルール**。

| 部品 | 役割 | 例・別名 |
|------|------|----------|
| **型（外側を M）** | 中身の型を受け取って新しい型を作る | `Optional<User>`、配列の User、Promise の User と同じ形 |
| **値を文脈に入れる** | ただの値 → 文脈つき | of / pure。Haskell では return（関数の return とは別） |
| **flatMap** | 文脈つきの値＋文脈つきを返す関数 → 文脈つきの値 | bind / chain |

どれか一つでも欠ければモナドとは呼ばない。また **flatMap という名前のメソッドがあるだけでは足りない**——満たすべきルール（モナド則）がある。

### 「モナドは箱」の限界

Optional では「箱」のたとえはよく合い、入り口としては分かりやすい。だが定義ではない。中に値が入っていない仲間がある。

**IO** はファイル読みなどの計算を表す型。中身は読んだ結果ではなく **何をするかの手順**。実行するまで何も起きず、箱を開けても値は入っていない。Optional との共通点は「中に何かがある」ではなく、**ある文脈を持った計算同士を、その文脈を壊さずにつなげる**こと。IO なら手順が順に並ぶ。箱は最初の直感には役立つが、そこで止まると値の入っていない仲間を取りこぼす。

### 同じ枠で見る他の型

中身・文脈・つなぐと何が起きか、の三つで見る。

| 型 | 中身 | 文脈 | つなぐと |
|----|------|------|----------|
| **Optional** | 値 | ないかもしれない | なかった時点で残りは実行されない |
| **Result / Either** | 成功時の値 | 失敗理由を持てる | 失敗した時点で理由を持ったまま止まる（なぜ失敗したかが残る） |
| **Array** | 値 | 値が複数 | 各要素に関数を当て、返ってきた配列を一段だけ平らにする。of＋flatMap＋後述の則も満たす → 多くの人はすでにモナドを使っている |
| **Promise** | 値 | 今すぐには手に入らない | then で前の結果のあと次が動く |

Promise は値を返しても Promise を返しても受け取り、map と flatMap を一つで兼ねる形でよく似ている。ただし JS の Promise をそのままモナドと呼ぶには注意が要る。配列は flatMap 時にだけ一段平らにするのに対し、Promise は入れ子を入れた時点で潰し、その状態を作れない。日常の非同期では困りにくいが、代表例として覚えるとつまずく、と話し手は釘を刺す。

共通なのはつなぎ方の形だけ。起きること自体は文脈ごと——なければ止まる、失敗なら止まる、複数なら止まらず枝分かれする。

### モナド則：書き換えても壊れない保証

flatMap は処理をつなぐ仕組みなので、途中の二つをまとめて切り出したり切り出し位置をずらしたりする。組み替えで結果の意味が変わると安心して使えない。だから次の三つを求める（足し算の結合法則・単位元と同じ形）。暗記は不要で、「書き換えても壊れない保証」と分かれば十分。

1. **結合則** … 3行を順につなぐのと、後ろ二つを一まとめにしてからつなぐので、最後の結果が同じ。括る場所を自由に選べる。
2. **左単位** … ただの値を直接関数に渡す道と、いったん箱に入れてから flatMap でつなぐ道が同じ結果。「箱に入れる」が余計なことをしていない。
3. **右単位** … 箱に入った値に「ただ包み直すだけ」の関数をつないでも元のまま。何もしない一行を安心して消せる。

### まとめ（動画内）

最初は確認に本題が埋もれていた。最後は確認を一度も書かない——書けなくなったのではなく、flatMap の中に一度だけ書いたから。

モナドとは、ある文脈を持った計算をその文脈を保ったまま次へつなぐ仕組み（次の計算自体も文脈を持つ）。中身の差し替えだけでなく、次に何が起きるかが前の結果の中身で決まってよい。型で書けば文脈が M。文脈を作る型・値を入れる操作・計算をつぐ操作の三つがモナド則を満たすこと——それがモナド。「自己関手の圏におけるモノイド対象」は、これを数学の言葉で言い切ったもの（モノイド＝まとめる操作・単位・結合を持つ形）。箱の中に箱ができて一段にならす、があれに当たる。難しい概念から入らなくても、「同じ確認を何度も書きたくない」を辿るだけでこの形にたどり着ける。名前と定義は後から合流するだけ。
