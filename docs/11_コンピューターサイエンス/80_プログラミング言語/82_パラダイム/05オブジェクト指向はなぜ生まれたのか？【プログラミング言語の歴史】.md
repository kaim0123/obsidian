## 詳しい要約

プログラミング言語の歴史シリーズ第4回（シリーズ完結）。スマホアプリ・業務システム・Web の多くが共有する **オブジェクト指向（OOP）** の起源は、1960年代ノルウェイの **船のシミュレーション** から。**Simula → Smalltalk → C++ → Java → GoF デザインパターン → SOLID** まで辿り、継承批判・関数型との共存・ケイの「本来の OOP はメッセージパッシング」まで触れる。

### なぜ OOP が生まれたか：ソフトウェア危機

- **1968年 NATO ソフトウェア危機**：大規模化で納期・予算が破綻。IBM **OS/360** は象徴例——フレデリック・ブルックス『人月の神話』。
- **手続き型の限界**：`print` `printLn` `printFinal` 的な **命名地獄**（名前空間なし→グローバル関数）。データを誰でも変更可能→**どこで何が変わったか追えない**。1万行超で保守より作り直し。
- **構造化プログラミング**（ダイクストラ、1968「`goto` は有害」）：制御の流れは整理できたが **データ管理は未解決**。
- OOP の答え：**データと処理を一緒に束ね、外から直接触れない**（銀行口座と残高・入金の例）。構造化と OOP は **同時代の兄弟** の問題意識。
- 「オブジェクト指向プログラミング」という **用語** を広めたのは **アラン・ケイ**（Smalltalk）。Simula 自体はその言葉を使っていなかった——**名前がつくと議論できる**（デザインパターンでも同型）。

### 三本柱

| 柱 | 内容 | 補足 |
|----|------|------|
| **カプセル化** | データと処理をまとめ、外から直接触らせない | `public` / `private` / `protected`。残高を直接 `-100万` できない |
| **継承** | 既存クラスの機能を引き継いで新クラス | 共通部分を1箇所に——のち **誤用・批判** の種にも |
| **ポリモーフィズム** | 同じメッセージで受け手により異なる動作 | `鳴け`→犬はワン、猫はニャー。呼び出し側は動物の種類を気にしない |

- **クラス**＝設計図、**オブジェクト**＝実体。抽象クラス・**インターフェース**（約束だけ、実装は各クラス）。
- 三本柱は相互依存（カプセル化なしに安全なポリモーフィズムは難しい等）。
- **手続き型**＝手順の集まり、**OOP**＝物の集まり——現実世界のモデルをコードへ。
- **継承の誤用**（最多ミス）：再利用のためだけに継承→無関係な親子。**例**：スタックを `ArrayList` 継承——スタックは ArrayList の一種ではない。**is-a** のときだけ継承、それ以外は **コンポジション**（has-a）。
- テストで本物 DB の代わりに偽物を差し替え——後のパターン（DI 等）へ。

### Simula（ノルウェイ、1962〜1967）

- **オーレ＝ヨハン・ダール** & **クリステン・ニーガード**（ノルウェー計算センター）：港の渋滞・船の衝突を **事前シミュレーション**したかった。船・港・クレーンはそれぞれ状態と行動を持つ。
- **Simula I**（1962）→ **Simula 67**（1967）：ALGOL に **クラス** を追加——継承も Simula 由来。
- **コルーチン**：実行を中断・再開——現代の `async/await` の先祖。Kotlin コルーチン等、60年後に再注目。
- **広まらなかった理由**：**10倍以上遅い**（C 比）、大型機・パンチカード時代、利用者が研究機関中心——**概念は先行、実装は後世**（約20年後に C++・Java）。
- ダール：2001年 **チューリング賞**（翌年ダール・ニーガード死去）。C++・Java・Python・Ruby・Kotlin 等は Simula の影響下——**すべての道は Simula に通ず**。

### Smalltalk とアラン・ケイ（ゼロックス PARC、1970年代）

- **ゼロックス PARC**：GUI・Ethernet 等。**スモールトーク**：**すべてがオブジェクト**（数値・文字列・クラス定義そのものもメッセージ）。
- **メッセージパッシング**：「やれ」ではなく「お願いします」——受け手が応答を自律的に決定。ケイは言語より **コンピュータの新しいメディア** と構想（**Dynabook**、1972——子供用携帯 PC のビジョン。東芝 Dynabook とは無関係）。
- ケイの逆説：「私がオブジェクト指向と呼んだものは C++ でも Java でもない」——本来の核心は **メッセージパッシング**。後の言語は **クラス階層・継承** 中心に——**産んだものが想定と別物に**。
- 系譜：Squeak・Pharo、**Ruby** はスモールトーク直系孫とも。ケイは今も「本当の計算機科学はまだ始まっていない」。

### C++（1979〜）と Java（1995）

**C++**（ストローストラップ、ベル研究所）

- ケンブリッジで Simula 使用→**遅すぎる**。**Simula の OOP + C の速度**。
- 1979 **C with Classes** → 1983 **C++** → 1985 公式コンパイラ。クラス・継承・仮想関数（ポリモーフィズム）は Simula、速度は C。

**Java**（ゴスリングら、サン・マイクロシステムズ）

- OOP を **強制**して設計スタイルを統一。**バイトコード + JVM** → **Write Once, Run Anywhere**（1990年代 Web ブームと合致）。C++ は OS ごとに再コンパイル。
- **ガベージコレクション（GC）**：手動 `free` 地獄から解放——代償は **Stop-the-World**（GC 中の一時停止）。ゲーム・低遅延金融では課題。Web・業務では多くの場合許容。
- 1999 **HotSpot JVM** で JIT 強化——初期の「Java は遅い」から改善。**OOP の民主化**と設計の定型化が 1990〜2000年代に並行。

### GoF デザインパターン（1994）

- **Gang of Four**：Gamma・Helm・Johnson・Vlissides。**23パターン**（生成・構造・振る舞い）。
- 革命は **優れた設計に名前をつけた**こと——「ファクトリーで作る」で意図が伝わる。**設計を語る共通言語**。
- 代表例：
  - **Singleton**：インスタンス1つ（設定・ログ）——乱用はテスト困難
  - **Observer**：変化を関係者へ通知——LINE 通知、React の state の思想的先祖
  - **Strategy**：アルゴリズムを差し替え（支払い方法の切替）
  - **Decorator**：継承せず機能を重ねる（コーヒーにミルク）
- 現代：**Spring DI**（Strategy+Factory）、**React**（Observer 的）。**乱用**の罠——パターンのための複雑化。本は「こう使え」ではなく **過去の解決策の知識の集積**。
- **Erich Gamma**：2011年 Microsoft、**VS Code** 開発をリード——設計言語から開発体験まで。

### 批判と進化：継承・SOLID・現代

- **ジョー・アームストロング**（Erlang）：「バナナが欲しいのに、バナナを持つゴリラとジャングル全体をもらう」——継承で不要なものまで付いてくる。
- **リッチ・ヒッキー**（Clojure）：**ミュータブル** 中心の OOP は並行処理時代に不向き——関数型は **不変データ** で並行安全。
- **コンポジション優先**：「車は乗り物」（is-a）より「車はエンジンを持つ」（has-a）。Go の interface+struct、Rust の **trait**、Python の **ダックタイピング**（同じメソッドなら同様に扱う）。
- **SOLID**（ロバート・C・マーティン）：
  - **S** 単一責任、**O** 開放閉鎖、**L** リスコフ置換（子は親と置換可能——Barbara Liskov、チューリング賞）、**I** インターフェース分離、**D** 依存性逆転
- 批判は **否定ではなく精錬**——正しい使い方が明確化。

### まとめ

- OOP は **目の前の船シミュレーション** から始まり、60年後も設計の **共通言語**（オブザーバー・ストラテジー等の会話は今も世界中で）。
- 現代は **マルチパラダイム**（OOP + 関数型 + 適材適所）。概念の寿命は実装より長い——Simula の名前は消えても概念は everywhere。
- シリーズ4回の流れ：**機械語の地獄 → アセンブリ → コンパイラ／高級言語 → インタープリタ／対話 → オブジェクトで現実をモデル化**。
