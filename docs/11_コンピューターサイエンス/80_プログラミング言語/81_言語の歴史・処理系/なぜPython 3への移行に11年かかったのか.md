## 詳しい要約

**テーマ：Python 2→3移行が11年かかった理由と「互換性を壊す」ことの教訓**

Python 3.0（2008年12月3日）から Python 2 のサポート終了（2020年1月1日）まで11年1か月。文字列という根本的欠陥を直すための意図的な非互換だったが、遅い3.0・ライブラリの鶏と卵・快適すぎた2.7のせいで「移行しない方が合理的」な均衡が続き、InstagramやDropboxなど影響力のある組織が先に渡ったことで崩れた。教訓は「壊すな」ではなく「壊すなら、渡った人が最初に得をする橋をかけろ」だ、という話。

---

### 第1章 なぜ作者は互換性を壊したのか

- Python 2 には **バイト列としての文字列とUnicode文字列の2種類** があり、暗黙に混ざる仕様だった → 英語では動くが日本語を入れた瞬間にエンコードエラーで落ちる（2000年代の名物）
- **グイド・ヴァンロッサム** は2000年頃から「Python 3000」の名で抜本改修を構想。過去の設計ミスを一度だけまとめて清算：
  - 文字列はすべて Unicode に統一
  - print を文から関数へ
  - 整数同士の割り算は小数を返す
- 個々の判断は今振り返ってもほぼ正しいが、引き換えに世界中の Python 2 コードがそのままでは動かなくなった
- 当時グイドは Google 在籍で勤務時間の半分をPython開発に充てていた。Python 3 は気まぐれではなく **確信犯的な非互換**

### 第2章 Python 3が無視された10年

- 無視された3つの理由：
  1. **3.0が遅かった**：ベンチマークによっては2.6より1割以上遅く、乗り換える動機がない
  2. **ライブラリの鶏と卵**：アプリはライブラリが対応しないと移行できず、ライブラリは利用者が移行しないと対応する動機がない。NumPy や Django のような土台が渡るまで全員待ち
  3. **快適すぎた2.7**：2010年の2.7は3系の便利機能の一部を取り込んだ最終形で、「困っていないのになぜ移るのか」が業界の本音に
- コミュニティの支援：自動変換ツール **2to3**、2/3両対応ライブラリ **six**。ただしバイト列と文字列の混同は動かして初めてわかるバグで、機械的変換には限界
- 主要ライブラリの対応状況を赤と緑で晒す「Python 3 Wall of Shame」が登場し、移行が進むと「Wall of Superpowers」に改名
- 2011年、**PEP 404** で「Python 2.8 は永遠に出さない」と正式宣言
- それでも進まず、2014年にグイドが折れ、2015年予定のサポート終了を **2020年まで5年延長**
- 停滞の原因は技術ではなく、**移行しない方が合理的という経済**

### 第3章 均衡を崩した大企業たちの移行劇

- **Instagram**：2017年の PyCon 基調講演で全サービスの Python 3 移行完了を発表。開発を止めずに本番コード上で2/3両対応に書き換え続け、新ライブラリは Python 3 対応必須、という体制で約10か月（「飛行中の飛行機のエンジン交換」）
- 動機は **新機能**（型ヒント、非同期処理の構文は Python 3 のみ）。義務としての移行から「報酬を取りに行く移行」へ変わった
- **Dropbox**（グイド本人が在籍）が2018年までに数百万行規模のクライアントを移行
- NumPy・pandas などの開発者が「2020年以降 Python 2 を切る」と共同宣言
- 2020年1月1日に Python 2 公式サポート終了、最終版 2.7.18 が2020年4月に出て幕
- 均衡を崩したのは技術の進歩ではなく、**影響力のある組織が先に渡って見せたこと**

### 第4章 PHP 6とPerl 6、そして学んだ言語たち

- **PHP 6**：内部からのUnicode対応を試みて複雑さに耐えきれずプロジェクトごと消滅。次は7になり、6は永久欠番
- **Perl 6**：2000年構想発表、完成は2015年（15年）。事実上の別言語となり最終的に **Raku** に改名。その間にPerl本体はシェアを失い続けた
- 後発言語は正反対の設計を選んだ：
  - **Go**：2012年の1.0で既存コードを壊さない互換性保証
  - **Rust**：**エディション** の仕組みで新旧コードを同じプログラム内に共存
  - **JavaScript**：「Webを壊さない」を絶対原則に、1995年の奇妙な仕様すら抱え続ける
- Python 3 の11年は業界共通の教材となり、以後の言語設計を「非互換は悪」へ振り切らせた

### 最終章 教訓は「壊すな」でいいのか

- 壊したこと自体は間違いではなかった：文字列を統一した土台の上に **f-string・型ヒント・async** が積み上がり、PythonはAIの共通言語として人気1位に
- 失敗は **壊し方**：移行者への報酬が最初になく、罰（遅さ・動かないコード）が先に来た
- 教訓は「壊すな」ではなく **「壊すなら、渡った人が最初に得をする橋をかけろ」**（罰より先に報酬を）
- 当時の移行作業の大半は大量コードの機械的書き換えだったが、今はAIが変換候補を出しテストで検証できる。移行コストが下がれば「互換性を壊せない」という呪縛も緩み、言語の大改修というタブー自体が過去のものになるかもしれない

### まとめ

- Python 3 は文字列の根本欠陥を直すための意図的な非互換で、判断自体は正しかった
- 移行が11年かかったのは、遅い3.0・ライブラリの鶏と卵・快適な2.7による「移行しない方が得」な経済のため
- 均衡を崩したのは Instagram・Dropbox などの先行移行と新機能という報酬
- 教訓は「壊し方」と順序（報酬を先に）。AIによる移行コスト低下でこの前提も変わりつつある
