## 詳しい要約

プログラミング言語の歴史シリーズ第2回。前回のアセンブリは「救命胴衣を着て嵐の海を泳ぐ」状態にとどまり、**大規模化・機種依存・レジスタ競合** の限界が露呈した。**翻訳を機械に任せ、人間は問題の本質だけ考える**——その発想が **コンパイラと高級言語** を生み、70年超の進化を経て **LLVM・JIT・型推論** まで至った物語。

### 前回の続き：アセンブリでもまだ地獄

- 100行なら余裕でも、1950年代後半には **10万行規模**（軍の弾道計算、航空会社の予約システム）が現実に。
- **1対1対応**：ループ1つでもデクリメント・ジャンプ命令を手で並べる。意図より **命令のやりくり** に時間が吸われる。
- **変数＝メモリアドレス番号**（「4002番地に保存」）。ラベルでも大規模化すると管理不能。「4002って何だっけ？」が日常会話。
- **デバッグ**：レジスタと全メモリを紙に書き出し、命令ごとに **脳内シミュレーション**。
- **レジスタ競合**：複数サブルーチンが同じレジスタを奪い合う——誰がどれを使うか全部人間が管理。
- **機種依存**：IBM 704 向けコードは UNIVAC では動かない。機種アップグレードのたびに **ゼロから書き直し**（コードは使い捨て）。
- そこからの夢：**人間に近い言葉で書き、どの CPU でも動く** → コンパイラの発想へ。

### 誰が最初のコンパイラか（定義で答えが変わる）

| 人物・成果 | 時期 | 位置づけ |
|------------|------|----------|
| **グレース・ホッパー** の **A-0 システム** | 1952年 | サブルーチンライブラリを組み合わせてプログラム生成。翻訳概念の先駆け。現代の「任意ソース→機械語」とは異なり、ローダー／リンカに近い見方も |
| **FORTRAN**（ジョン・バッカス、IBM） | 1957年 | **Formula Translation**。数式を書けば機械語に翻訳。科学技術計算の世界を変え、**普及の影響力** で「最初の高級言語」と言われることが多い |
| **Short Code** / **Autocode** | 1949 / 1952 | FORTRAN より前に存在。ただし業界への影響は FORTRAN が別格 |

- ホッパー：海軍の数学者・プログラマー。バグ伝説・コンパイラ・COBOL 設計と歴史の要所に登場。
- バッカスチーム：約 **3年** 開発。社内は「そんなもの作れるわけない」と懐疑——**動くもので証明**。
- 最大の技術課題：**ループ最適化**（データ依存関係の解析、レジスタ再利用）。**依存解析** は現代スーパーコンピュータにも続く。
- 会議派の批判：「コンパイラは信用できない。機械が作ったコードはアセンブリより遅い」——生成コード品質を上げて黙らせた。
- 信念：**科学者が機械を知らなくてもプログラムできる世界**（何週間→数ヶ月だった作業が数日に）。

### コンパイラの内部：工場の工程

1. **字句解析（レキシング）** —— 文字列をトークンに分解（`x = a + b` → 5トークン）。`++` などは先読みで判定。
2. **構文解析（パーシング）** —— 文法チェックと **AST**（抽象構文木）。`a + b * c` は演算子優先順位が木に反映。
3. **意味解析** —— 型の整合性、未宣言変数、スコープ。文法的に正しくても意味がおかしいものを弾く。
4. **最適化** —— コンパイラの「職人芸」：
   - **定数畳み込み**（`3+5` → コンパイル時に `8`）
   - **デッドコード除去**（到達不能な分岐・未使用関数）
   - **ループ不変式移動**（ループ内で毎回同じ計算を外へ）
   - **共通部分式除去**（同じ式を1回だけ計算）
   - **インライン展開**（小関数を呼び出し元に埋め込み）
   - **末尾呼び出し最適化**（再帰をループ化、スタックオーバーフロー回避）。Scheme（1975）では仕様で義務化
   - 最適化は **連鎖**（インライン → 定数畳み込みの新機会など）、複数パス
5. **コード生成** —— 最適化済み AST／**IR** を CPU の機械語へ。

### IR・フロント／バックエンド・SSA・レジスタ割当

- **IR（中間表現）**：特定 CPU に依存しない形式。AST と機械語の間。
  - **フロントエンド**：ソース → IR。**バックエンド**：IR → 機械語。
  - 新言語はフロントだけ、新 CPU はバックエンドだけ追加——**組み合わせの自由**（現代 Web の FE/BE 分離と同型の発想）。
- **SSA**（Static Single Assignment）：各変数への代入を実質1回に整理。データの流れが追いやすく、最適化が安全に適用しやすい。
- **レジスタ割当**：**干渉グラフ**で同時に生きる変数を分離（グラフ彩色）。理論上 **NP困難** → 実用 **ヒューリスティック** で十分速く解く。

### 抽象化がもたらしたこと

- **何をしたいか**（`A+B` の結果を `X` に）を書けば、ロード・加算・ストアはコンパイラ任せ。
- **プログラミングの民主化**：アセンブリ時代は CPU を深く理解した専門家のみ → FORTRAN 後は物理学者・科学者が自ら実験データを処理。
- **抽象化のレイヤーは言語で異なる**（メモリ管理の例）：
  - **C**：手動 `malloc`/`free`（リークの責任はプログラマ）
  - **Java / Python**：GC（楽だが停止・リアルタイム向きに不向きな場合あり）
  - **Rust**：**所有権**＋コンパイル時検証（GC なしで安全性）。**ゼロコスト抽象化**＝使わない機能の実行時コストは払わない（コンパイル時間は増える）
- **トレードオフ**：抽象化が上がるほど生産性↑、キャッシュ制御・SIMD など **細かい制御** は犠牲。C は高級言語と低レベル操作のバランスで OS・組み込みに残存。
- **移植性**：同一ソースを x86／ARM 向けにコンパイル可能——1950年代には夢。完全な同一挙動は別問題（**移植** という仕事が残る）。
- 現代：レジスタ割当・命令スケジューリング・ベクトル化はコンパイラが自動化。「アセンブリの方が速い」は **ピンポイントチューニング** に限り、大規模全体ではコンパイラが安定・疲れない。

| 1972〜73 | **C**（リッチー、ベル） | UNIX 書き直し用。**ポインタ演算**でアセンブリに近い制御。UNIX は先にアセンブリ＋B で存在 |

- **AOT**（事前コンパイル）：起動速い。組み込み・ゲーム向き。
- **JIT**：実行状況を見て最適化。長時間サーバー向き。**段階的 JIT**（JVM の C1→C2）で起動とピーク性能の両立。
- **セルフホスティング**：C コンパイラが C で書けるようになった瞬間＝言語の自立（前回のブートストラップ問題のゴール）。

### コンパイラの限界とインタープリタへの橋

- **万能ではない**：コンパイラの対になる存在が **インタープリタ**。
  - コンパイラ：**実行前に全部翻訳**（準備型）
  - インタープリタ：**1行ずつ読んで即実行**（ぶっつけ本番型）——プロトタイプ・教育・対話開発に強い
- **CPython**：ソース → バイトコード → VM が解釈（JIT なし→「遅い」イメージの一因）。
- **GIL**（Global Interpreter Lock）：複数スレッドでも Python コード同時実行は1本。参照カウント GC のスレッドセーフ化のトレードオフ。
- **PyPy**：JIT 実装で標準 Python より数倍速い場面も——**同じ言語でも実装で性格が変わる**。
- 現代は **いいとこ取り**（バイトコード＋JIT 等）が主流。

### まとめのメッセージ

- コンパイラは **人間が CPU のことを考えなくていいように** 生まれた。**機械が翻訳する** 発想がソフトウェア産業全体の土台。
- 紙でレジスタ競合を追っていた時代から、**SSA・グラフ彩色・LLVM・JIT** へ——「信用できない」と言われたものが、今は大規模コードで人間より安定して最適化する場面も多い。
- コンパイラ史＝**抽象化とコストのトレードオフをどこで引くか** の繰り返し。翻訳の積み重ねが Web・スマホ・AI を支えている。
