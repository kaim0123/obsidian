## 詳しい要約

**テーマ：V8エンジンとhidden classがJavaScriptを高速化した仕組み**

JavaScriptの言語仕様は動的型付けのまま変わっていないのに、2008年登場のV8エンジンが実行速度を約10倍に引き上げた。その核心は1980年代の研究言語Selfに由来する **hidden class** とインラインキャッシュ、投機的最適化であり、「同じ形のオブジェクトを作る」書き方をすればV8は最大限の速度を出せる、という話。

---

### 第1章 デンマークの農家で生まれた世界最速エンジン

- 2006年、デンマーク・オーフス近郊の、Googleが借りた農家の建物に **ラース・バック** と10人ほどのチームが集められた
- バックは Sun Microsystems で **Java HotSpot VM** の開発を率いた仮想マシンの職人で、その前は研究言語 **Self** の処理系を作っていた
- Googleは「Webアプリの時代が来ればJSの速度がボトルネックになる」と読み、「世界最速のJSエンジン」を注文
- 2008年9月2日、Chrome 公開と同日に V8 をオープンソース化。既存エンジンの **約10倍** の速度を記録

### 第2章 JavaScriptはなぜ遅かったのか

- C や Java は変数の型やプロパティのメモリ位置がコンパイル時に決まり、実行時は決まった「住所」に直行できる
- JS は実行中にプロパティを自由に追加・削除でき型も変わるため、昔のエンジンはオブジェクトを **辞書** として持ち、読むたびに名前で検索していた
- プロパティの読み書きは最も頻繁な操作なので、辞書引きの積み重ねが致命的に遅い。加えてインタープリタ実行が主流だった
- 遅さはエンジニアの書き方ではなく、自由すぎる言語仕様と辞書引きの構造が原因

### 第3章 hidden classという発明

- 原型は1980年代にスタンフォード大学とSunで開発された **Self** の研究。若きバックもその処理系を作っていた
- Selfチームの発見：言語がどれほど自由でも、実際のプログラムは **同じ形のオブジェクトを大量に作る**（例：名前と年齢を持つユーザーオブジェクトを1万個）
- V8はオブジェクト生成時にその形を記録した設計図＝ **hidden class** を裏で自動生成し、同じ形のオブジェクトはそれを共有
- 設計図には「名前は1番目、年齢は2番目」という位置情報があり、辞書引きの代わりに決まった位置へ直行できる → 自由さを残したまま静的言語並みのアクセス
- **インラインキャッシュ**：あるコード箇所にいつも同じ形が来るとわかれば、設計図の確認すら省いて前回の位置情報を再利用

### 第4章 ブラウザを飛び出したV8

- 2009年、ライアン・ダールがV8をサーバーで動かし **Node.js** が誕生。その上に Electron が生まれ、VS Code・Slack・Discord のデスクトップアプリが動いている
- エンジンも進化：2010年に最適化コンパイラ **Crankshaft**、2017年に **Ignition（インタープリタ）＋ TurboFan（最適化コンパイラ）** の新構成へ
- Ignition が軽く実行しながら挙動を観察し、頻繁に呼ばれ同じ形が来る「ホットな」部分だけ TurboFan が機械語まで最適化 → **投機的最適化**
- 予測が外れたら最適化コードを捨てて安全な実行に戻る（**脱最適化 / deoptimization**）

### 最終章 エンジンの気持ちで書くコード

- 形を乱すコードは最適化を壊す：
  - 生成後に条件によってプロパティを足したり足さなかったりする
  - 同じ関数に形の違うオブジェクトを混ぜて渡す
  - → hidden class が分裂しインラインキャッシュが効かなくなる。エラーは出ず、裏で遅くなるだけなので気づきにくい
- 対策：**プロパティは最初に全部そろえて初期化**し、**同じ役割のオブジェクトは同じ形で作る**
- hidden class のアイデアは1980年代に生まれ、2008年のV8で花開くまで20年以上眠っていた。Self自体は消えたが、発明は HotSpot（Java）と V8（JS）で生き残った

### まとめ

- JSの高速化は言語ではなくエンジン（V8）の進化による
- hidden class＋インラインキャッシュで「辞書引き」を「位置への直行」に変え、投機的最適化でホットな部分を機械語化
- 実務では、オブジェクトの形を最初にそろえ、同じ役割のオブジェクトを同じ形に保つ書き方が速度に効く
