## 詳しい要約

**テーマ：Rust は「速さか安全か」の 40 年の二択を終わらせたが、人間側の代償を背負った**

Rust は所有権と借用により C 並みの速さと GC 言語並みのメモリ安全を両立し、Android では書き換えなしで脆弱性を大幅に減らした。一方で学習コスト・コンパイル時間・unsafe という代償、そして Linux カーネルでの C 陣営との衝突という人間側の課題を抱える。AI がコードを書く時代には、厳しいコンパイラが AI 生成コードを受け止める「床」になるが、境界の責任は人間に残る。

---

### オープニング：愛されて、覚えられなくて、心配される言語

- Stack Overflow 調査で 8 年連続「最も愛される言語」なのに、多くの人が所有権・借用チェッカー・ライフタイムで挫折する。
- Rust 公式の 2025 年調査（7,156 人）で最大の心配は「業界で十分に使われていない」（42.1%）。
- それでも 2022 年 12 月の Linux 6.1 で、30 年の歴史で初めて C 以外の言語としてカーネル入りし、Windows にも入った。

### 第1章 21 階の階段から生まれた言語

- 2006 年バンクーバー、Mozilla の 29 歳のプログラマー **Graydon Hoare** が帰宅するとエレベーターの制御ソフトがクラッシュしていた。21 階まで階段を上りながら、この種のクラッシュの多くがメモリの扱いに起因すると考え、小さく速くメモリバグの出ない言語の設計を始めた。
- 名前は「錆」ではなく、生き延びることに過剰設計された **さび菌** から。2006〜2009 年は一人で書き、2009 年に Mozilla が正式支援（Firefox の深刻な脆弱性の大半がメモリ絡みだったため）。ブラウザエンジンを Rust で書き直す **Servo** が走り、2015 年 5 月 15 日に Rust 1.0。
- Hoare は 2013 年に第一線を退いた。Rust は新発明ではなく、1970〜90 年代の言語（CLU、Mesa、Erlang など）の研究の再利用だと本人が語る（「過去の技術が未来を自分自身から救いに来た」）。

### 第2章 40 年続いた二択をどう終わらせたか

| 選択 | 得るもの | 失うもの |
|---|---|---|
| C / C++ | 速さ | use-after-free、二重解放、配列外書き込みを防げない |
| Java / Python など GC 言語 | 安全 | 実行時の停止とランタイムの重さ |

- OS やブラウザは重さを抱えられないので C を選ぶしかなかった。Microsoft の 2019 年の分析では、自社製品の脆弱性の約 70% が 12 年間ずっとメモリ安全性の問題。
- Rust の答えは **所有権と借用**。図書館にたとえると、書き込める状態で借りられるのは常に 1 人、読むだけなら何人でも、ただし誰かが書いている間は誰も読めない。ルール違反は **コンパイル時** に拒否し、実行時には何もしないので速さは C と同等。
- 挫折の正体は、40 年間コンパイラが見逃してきたミスを初日から全部指摘されること。
- Google の 2024 年 9 月の公表：Android の脆弱性のうちメモリ安全性起因は 2019 年の 76% → 2024 年の 24%（業界平均は 70%）。**既存 C++ は書き直さず、新しいコードだけ Rust で書いた**。問題は圧倒的に新しいコードにあり、蛇口を閉めれば古いバグは時間とともに指数関数的に減る。

### 第3章 メモリ安全の代わりに背負った 3 つの代償

1. **学習コスト**：公式調査で「Rust で生産的」と答えたのは 53%。現役ユーザーの半数がまだ勉強中。
2. **コンパイル時間**：2025 年のコンパイラ性能調査（3,700 人）で 55% が小さな変更後の再ビルドに 10 秒以上待つ。Rust をやめた人の 45% が理由にコンパイル時間を挙げた。
3. **安全の範囲**：安全なのは `unsafe` と宣言した区画の外側だけ。OS やドライバには unsafe が必ず要る。安全が消えたのではなく、責任を持つ場所が数行に圧縮され「危険な場所に名札が付いた」。

- 組織の代償：2020 年 8 月に Mozilla が Servo チームを含む 250 人を解雇し、母体が支えられなくなった。2021 年 2 月 8 日に AWS・Google・Huawei・Microsoft・Mozilla が **Rust Foundation** を設立。2025 年調査の心配は「業界で使われていない」42.1%、「言語が複雑になりすぎる」41.6%、「開発者とメンテナーが支えられていない」38.4%。

### 第4章 Linux カーネルで「がん」と呼ばれた日

- 2024 年 8 月、Rust for Linux の中心メンバー（Microsoft の Wedson Almeida Filho）が「非技術的なナンセンス」に疲れてメンテナーを辞任。技術ではなく人で止まった。
- 2025 年 2 月、DMA（デバイスがメモリに直接読み書きする仕組み）の C 側を Rust から呼ぶための接続コードが提案され、担当メンテナー Christoph Hellwig がこれを **「がん」** と呼んだ。主張は「2 言語が混ざったコードベースは保守できない」。
- Linus Torvalds は「メンテナーは自分の担当コードが他でどう使われるかを決められない」と Rust 側についた。Hellwig は Linux 6.14 で DMA メンテナーを降り、同月 Rust 側を擁護して Linus に叱られた Asahi Linux の Hector Martin もカーネルの仕事をやめた。**両側から人が抜けた**。
- C++ 側も動き、Stroustrup が安全性のための「プロファイル」を提案、2024 年には Safe C++ という別提案も出た。Rust が解決した問題は「Rust を使わなくても解決しろ」という圧力になった。
- Rust の次の壁は技術ではなく、30 年 C で書いてきた人たちとの共存。

### 最終章 人間には難しく、AI には向いている言語

- 相性の良さは 2 方向：
  1. AI 時代は新しいコードの量が桁違いに増える。問題は新しいコードにあるので、新しいコードが安全であることの価値が上がる。型と所有権を通ったコードには、人間が読まなくても特定種類のバグがないと保証できる ＝ コンパイラが AI コードを受け止める **床** になり、レビューの一部を任せられる。
  2. Rust 最大の壁だった学習コストを AI が削る。借用チェッカーのエラーは説明されれば理解できる種類のもの。人間に厳しすぎた先生が AI には最高の先生になる。
- ただし第 4 章の問題は残る。AI は Rust を書けても Hellwig を説得はできない。既存 C コードとの境界に置く unsafe を誰が保証するか、その責任は人間の名前でしか置けない。

### まとめ

- Rust が解決したのは「速さか安全か」という 40 年の二択で、書き換えなしで効果が出ることも実証された。
- 代償は学習コスト・コンパイル時間・unsafe の境界、そして運営とコミュニティの人間的問題。
- AI 時代には厳しいコンパイラが価値を増すが、unsafe の境界の責任は人間に残る。
