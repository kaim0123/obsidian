## 要約

HTTPSは、ブラウザとサーバー間の通信を **TLS** で守り、URLの「S」がその印になる仕組みである。ただし暗号化には両側が同じ鍵を持つ必要があり、接続開始時点では両者は鍵を共有していない。動画はこの「どうやって鍵を共有し、相手が本物だと確かめるか」を順にほどく。

### HTTPの問題と「鍵を送れない」壁

HTTPのままでは、ログイン時のメール・パスワードなどが平文で経路上を流れる。公衆Wi-Fiなどでは盗み見だけでなく改ざんも可能で、受け取った側は差し替えに気づけない。そこで中身を共通鍵暗号で暗号化するが、初めて会う相手にあらかじめ同じ鍵は渡っていない。鍵そのものをネットワークで送れば、暗号化前と同じ経路で盗まれて意味がなくなる。

### ECDHEによる鍵共有

答えは「鍵を送らない」こと。ブラウザとサーバーは各自の秘密（A / B）を手元に置き、そこから公開してよい値だけを交換する。公開値から元の秘密を求めるのは現実的な時間では終わらない。ブラウザは「自分の秘密A＋相手の公開値」、サーバーは「自分の秘密B＋相手の公開値」を組み合わせると、材料も順番も違うのに同じ共有秘密が得られる（掛け算の交換法則のイメージ）。第三者は公開値しか持たないので同じ値には到達できない。

これが Diffie–Hellman 鍵共有で、TLSでは楕円曲線版の **ECDHE**（E＝一時的）が一般的。秘密は接続ごとに作り直し破棄するため、後でサーバー秘密が漏れても過去通信を遡って復号できない（前方秘匿性）。共有秘密からまずハンドシェイク保護用の鍵を作り、本文用の鍵は後で別に導出する。

### 中間者攻撃とサーバー証明書

鍵共有だけでは、相手が本当に目的のサーバーかは分からない。攻撃者が双方に成りすまして別々に鍵共有すると、通信は暗号化されていても中身は攻撃者に読まれ・書き換えられる（中間者攻撃）。

そのためサーバーは接続ごとに **サーバー証明書**（ドメイン名・公開鍵・発行者・有効期限・署名など）を提示する。証明書の公開鍵は鍵共有の使い捨て公開値とは別物で、本人確認用として接続間で変わらない。ブラウザはアドレスバーのドメインと証明書のドメインが一致するか確認する。

### 認証局・証明書チェーン・秘密鍵の所持証明

証明書は自作できるので、**認証局（CA）** がそのドメイン管理を確認したうえで署名する。サーバー証明書 ← 中間CA ← ルートCAというチェーンをブラウザがたどり、OS/ブラウザに入っている信頼ルートに到達するかで判断する。信頼はルートから下へ降りる。つながれない証明書は警告になる。

証明書自体はコピー可能だが、対応する **秘密鍵** はついてこない。サーバーはこれまでのやり取りに秘密鍵で署名し（Certificate Verify）、ブラウザは証明書の公開鍵で検証する。検証できれば「証明書の持ち主」だと分かる。コピーだけでは署名を作れない。

### TLS 1.3ハンドシェイクの順番

1. **ClientHello** … ブラウザの公開値と使える暗号スイート  
2. **ServerHello** … サーバーの公開値と選んだ暗号スイート → 共有秘密とハンドシェイク用鍵ができ、以降は暗号化  
3. **Certificate** … 証明書（暗号化後に届くが、この時点ではまだ本人確認は未完了）  
4. チェーン検証  
5. **Certificate Verify** … 秘密鍵の所持証明  
6. **Finished** の交換 → ハンドシェイク完了  

初回接続ではこの順でしか進まない。

### 本文の暗号化とHTTPSが守る／守らないもの

ハンドシェイク後、同じ共有秘密から本文用の鍵を作る。以降は通常のHTTPだが共通鍵暗号でやり取りする。行きと帰りで鍵は別（方向ごとの鍵）。「共通」とは暗号化と復号に同じ鍵を使うという意味。現行TLSでは **AEAD** により暗号化と改ざん検知が一体で行われ、1文字の改ざんでも受信側が気づく。

HTTPSが提供するのは次の3つ。

1. **機密性** … 経路上で中身が読めない  
2. **完全性** … 改ざんに気づける  
3. **認証** … 名乗っている相手だと確かめられる  

守らないもの：サイト自体の信用（詐欺サイトでも自ドメインなら正規証明書を取れる）。HTTPSが守るのは通信路と「つながった相手」まで。秘密を共有していなかった2人が鍵を送らずに同じ秘密を作り、暗号化された通路の中で相手が本物だと確かめてから本文を始める——それがHTTPSである。
