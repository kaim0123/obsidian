## 詳しい要約

**テーマ：シンプルさの象徴だったXMLが「XML地獄」と呼ばれ、解体され、基盤に沈み、AI時代に復権するまでの28年**

XMLは1998年、SGMLを軽量化した「人間にも機械にも読める共通言語」として生まれた。しかしSOAP／WS-*やJavaの設定ファイル文化など、あらゆる問題をXMLで解決しようとする周囲の増築が「地獄」を生み、JSONとHTML5に解体された。それでもOffice文書やSAMLの中で現役であり、LLM時代にはその過剰な明示性が再評価されている。

---

### 第1章 1998年、シンプルさの象徴だったXML

- 1998年2月10日、W3Cが **XML 1.0** を勧告。Sun Microsystemsのジョン・ボサックらの作業部会が設計
- 元は出版業界の巨大なマークアップ言語 **SGML**（HTMLもSGMLの子）。SGMLは複雑すぎて完全な実装がほぼなかった
- 「SGMLの複雑さの2割で用途の8割をカバー」する方針で、仕様本文を約30ページに削り込んだ
- 思想：人間にも機械にも読める、ベンダー非依存、Unicode前提。文書・データ・Webページを同じ文法で書く未来を描いた
- ポイント：XMLは当時むしろシンプルさの象徴だった

### 第2章 SOAPとWS-*が建てた増築の帝国

- 2000年、XMLベースのリモート呼び出しプロトコル **SOAP** が登場（MicrosoftとIBMが推進）
- WSDL（サービス定義）、UDDI（サービス探索）、WS-Security、WS-Addressing、WS-ReliableMessaging、WS-Policyなど **WS-\*** と呼ばれる拡張仕様が数十本積み上がった
- 数値を2つ足すだけの呼び出しでも、本体データはごく一部で残りはエンベロープ・ヘッダー・名前空間宣言
- Javaの世界では EJBのデプロイメント記述子、Strutsの struts-config.xml、Springの applicationContext.xml、Antの build.xml、Mavenの pom.xml など、**振る舞いをコードでなくXMLで書く文化** が支配的に
  - 言い分は「再コンパイルせずに振る舞いを変えられる」だが、現実は1文字のタイプミスで起動せず、コンパイラもIDE補完も助けてくれない
- **XHTML**：2000年頃からW3CはWeb全体のXML化を推進。タグの閉じ忘れ1つでページ全体がエラーになる仕様で、間違いを許してきたWebの文化と合わなかった
- ポイント：XMLの修羅場は言語そのものより、周囲の増築が生んだ

### 第3章 JSONとHTML5による解体

- **JSON**：ダグラス・クロックフォードが2001年頃から広めた記法。仕様が小さく、JavaScriptのオブジェクトそのままで変換不要
- **Ajax**（Asynchronous JavaScript and XML、2005年命名）：名前にXMLを背負いながら、実際に運ばれたデータの主流はJSONだった
- **ブラウザベンダー**：2004年にApple・Mozilla・OperaがW3Cに反発して **WHATWG** を結成しHTML5を開発。2009年にW3CはXHTML 2.0の作業部会を打ち切り、Web全体のXML化計画は終焉
- Java側：Spring 2.5（2007年）でアノテーション導入、Spring Boot（2014年）でXMLをほぼ書かずに動くように。Gradle（2012年に1.0）がビルド記述をスクリプトへ戻した
- セキュリティ問題も噴出：**Billion Laughs攻撃**（数百バイトのXMLで実体参照が雪だるま式に膨らみメモリを食い尽くす）、外部ファイルを読ませる **XXE** は2017年のOWASP Top 10に単独項目で入った
- ポイント：XMLは機能の優劣ではなく、仕様の重さで負けた

### 第4章 ExcelもSVGも、中身は今もXML

- Excelの **XLSX**、PowerPointの **PPTX** の実体はZIP圧縮されたXML群（Office Open XML、2008年にISO標準）
- Web画像の **SVG**、長年のAndroid画面レイアウト（Jetpack Composeの安定版は2021年）もXML
- 企業のシングルサインオンを支える **SAML** もXML署名の上に成り立つ
- Mavenの **pom.xml** も今もJavaのライブラリ配布を支える
- ポイント：主役の座を降りただけで、文書形式と企業基盤では現役の主力

### 第5章 YAMLへの転生とAI時代の復権

- **宿題1：地獄は転生する**。XMLを追い出した後、設定ファイルはYAMLへ移り、Kubernetes担当者は大量のYAMLと格闘している
  - YAMLの **ノルウェー問題**：国コード一覧にノルウェーの「NO」と書くと、処理系によっては偽（false）と解釈される
  - インデント1つのずれで意味が変わり、HelmはYAMLをテキストテンプレートで生成する
  - 沼の正体は記法ではなく、**本来コードで書くべき複雑さをデータへ押し込もうとする欲**。JSONでもYAMLでも同じ景色を再生産する
- **宿題2：XMLの復権**。LLMへのプロンプトでXML風のタグで構造を区切る書き方が定番になり、AnthropicはClaudeの公式ドキュメントでXMLタグの使用を推奨している
  - 理由は過剰なほどの明示性：開始タグと終了タグの両方に名前があり、途中から読んでもどこからどこまでが何のデータか迷わない
  - 人間には過剰だった性質が、確率的に文章を読む機械には最高の道標になった
- 結論：「XML地獄」は機械向けの言語を人間に手書きさせ続けた28年間の壮大な配役ミスだったのかもしれない

### まとめ

- XMLはSGMLの軽量化として生まれ、当初はシンプルさの象徴だった
- 地獄を生んだのはSOAP／WS-\*、Java設定ファイル、XHTMLなど「何でもXMLで」という周囲の増築
- JSON・Ajax・HTML5・アノテーション・Gradleにより表舞台から退いたが、Office文書・SVG・SAML・Mavenで今も現役
- 複雑さをデータに押し込む限り、YAMLでも同じ地獄は繰り返す。一方でLLM時代には明示的なタグ構造が再評価されている
