# 物理層とケーブル・インターフェースの状態

## この章で扱うこと
OSIの一番下、**物理層**の話です。銅線（UTP）と光ファイバ、イーサネット規格、ケーブルの種類を整理したうえで、ネットワーク機器のインターフェースの状態・デュプレックス・エラーカウンタの読み方と、層ごとの切り分けを学びます。

## ケーブルと物理層

### 銅線（UTP）と光ファイバ

| 種類 | 媒体 | 最大長（目安） | 特徴 |
| --- | --- | --- | --- |
| **UTP**（Unshielded Twisted Pair） | 銅線（より対線4対） | **100m** | 安価で扱いやすい。電気的ノイズの影響を受ける。PoE給電が可能 |
| **マルチモード光ファイバ（MMF）** | ガラス（コア径 **50/62.5μm**） | 数百m〜2km程度 | 光が**複数の経路**を通るため信号が広がりやすい。比較的安価。**建物内などの短距離向き** |
| **シングルモード光ファイバ（SMF）** | ガラス（コア径 **約9μm**） | **数km〜数十km以上** | 光が**1つの経路**だけを通るので信号が乱れにくい。レーザー光源で高価。**長距離向き** |
| 同軸（10BASE5 / 10BASE2） | 銅の同軸 | 500m / 185m | 古い規格（太い同軸 / 細い同軸） |

```
マルチモード（コアが太い）                 シングルモード（コアが細い）
 ┌──────────────────────────┐            ┌──────────────────────────┐
 │  ╲    ╱╲    ╱╲    ╱       │ 光が複数   │                           │ 光が1つの
 │ ──╲──╱──╲──╱──╲──╱──→    │ の経路で   │ ─────────────────────→    │ 経路で進む
 │    ╲╱    ╲╱    ╲╱         │ 広がる     │                           │
 └──────────────────────────┘            └──────────────────────────┘
```

光ファイバ共通の利点: **電気的なノイズ（電磁干渉）の影響を受けない**、銅線より長距離・高速。

### 主なイーサネット規格

| 規格 | 速度 | 媒体 | 最大長 |
| --- | --- | --- | --- |
| 10BASE5 | 10Mbps | 太い同軸 | **500m** |
| 10BASE2 | 10Mbps | 細い同軸 | **185m** |
| 10BASE-T | 10Mbps | UTP（Cat3以上） | 100m |
| 100BASE-TX | 100Mbps | UTP（Cat5以上） | 100m |
| 100BASE-FX | 100Mbps | マルチモード光 | **2km** |
| 1000BASE-T | 1Gbps | UTP（Cat5e以上） | 100m |
| 1000BASE-SX | 1Gbps | マルチモード光 | 約550m |
| 1000BASE-LX | 1Gbps | シングルモード光（MMFも可） | 約5km（SMF） |
| 10GBASE-T | 10Gbps | UTP（**Cat6A**） | 100m |
| 10GBASE-SR / LR | 10Gbps | MMF / SMF | 約300m / 10km |

名前の読み方: `1000BASE-T` ＝「1000Mbps」「ベースバンド伝送」「T＝ツイストペア（銅線）」。光の規格では `-SX`/`-SR` が短距離（Short）、`-LX`/`-LR` が長距離（Long）。

**UTPを使うイーサネットの最大長は、10BASE-T から 10GBASE-T（カテゴリ6A）まで共通で100m**です。100mを超えると信号が弱くなったりノイズの影響を受けたりしてエラーが増えます。100mを超える区間には、間にスイッチを置くか、光ファイバを使います。

### ストレート・クロス・ロールオーバー

UTPケーブルのRJ-45コネクタには8本のピンがあり、10BASE-T/100BASE-TXでは 1・2 番と 3・6 番を使います。**機器によって送信に使うピンが異なります**。

| 機器の分類 | 送信ピン | 受信ピン | 例 |
| --- | --- | --- | --- |
| MDI | 1, 2 | 3, 6 | **PC、ルータ**、サーバ、AP |
| MDI-X | 3, 6 | 1, 2 | **スイッチ**、ハブ |

一方の送信ピンが相手の受信ピンにつながる必要があるので、

- **異なる種類**（MDI ⇔ MDI-X）: PCとスイッチ、ルータとスイッチ → ピンをそのままつなぐ **ストレートケーブル**
- **同じ種類**（MDI ⇔ MDI、MDI-X ⇔ MDI-X）: スイッチ同士、PC同士、ルータ同士、PCとルータ → 送信と受信の線を交差させる **クロスケーブル**

```
ストレートケーブル（PC ⇔ スイッチ）     クロスケーブル（スイッチ ⇔ スイッチ）
 PC側(MDI)     SW側(MDI-X)              SW側(MDI-X)     SW側(MDI-X)
 1 送信 ─────── 1 受信                    1 受信 ──╲ ╱── 1 受信
 2 送信 ─────── 2 受信                    2 受信 ───╳─── 2 受信
 3 受信 ─────── 3 送信                    3 送信 ──╱ ╲── 3 送信
 6 受信 ─────── 6 送信                    6 送信 ───╳─── 6 送信
                                         （1⇔3、2⇔6 を交差して、送信→受信につなぐ）
```

| 接続 | 使うケーブル（Auto-MDIXなしの場合） |
| --- | --- |
| PC ⇔ スイッチ | ストレート |
| ルータ ⇔ スイッチ | ストレート |
| スイッチ ⇔ スイッチ | **クロス** |
| PC ⇔ PC | **クロス** |
| ルータ ⇔ ルータ | **クロス** |
| PC ⇔ ルータ（イーサネットポート） | **クロス** |
| PC ⇔ 機器のコンソールポート | **ロールオーバー**（コンソールケーブル） |

**Auto-MDIX** は、ケーブルの種類を自動判別して送受信のピンを内部で切り替える機能です。現在の機器の多くはAuto-MDIXに対応しているので、どちらのケーブルでも通信できます。ただし**Auto-MDIXがない古い機器では、ケーブルの種類を正しく選ぶ必要があります**。なお、1000BASE-T以降は4対すべてで双方向に送受信しますが、ストレート/クロスの考え方は同じです。

```
! Ciscoスイッチの Auto-MDIX（速度・デュプレックスが auto のときに有効）
Switch(config)# interface gigabitethernet1/0/1
Switch(config-if)# speed auto
Switch(config-if)# duplex auto
Switch(config-if)# mdix auto
```

**ロールオーバーケーブル（コンソールケーブル）** は、PCからルータやスイッチの**コンソールポート**に接続して設定するためのケーブルで、通信回線用ではありません（現在はUSBコンソールも多い）。

### ひっかけポイント・よくある誤解

- **「長距離にはマルチモード」は誤り。** マルチモードは光が複数の経路を通って信号が広がるため、建物内など数百m程度の用途向け。数十kmにはシングルモード。
- **コア径の大小の逆転。** シングルモード＝コアが細い（約9μm）、マルチモード＝コアが太い（50/62.5μm）。
- **UTPの最大長を 185m・500m・2km と答える誤り。** 185m＝10BASE2（細い同軸）、500m＝10BASE5（太い同軸）、2km＝100BASE-FX（マルチモード光）。UTPは100m。
- **UTP（カテゴリ6）を長距離用と考える誤り。** 銅線のイーサネットは100mまで。
- **スイッチ同士をストレートでつなぐ、は（Auto-MDIXがなければ）誤り。** 同じ種類の機器同士はクロス。ストレートは異なる種類（PCとスイッチ、ルータとスイッチ）。
- **「どのケーブルでも同じように通信できる」はAuto-MDIXがある場合だけ。**
- **ロールオーバーとクロスの混同。** ロールオーバーはコンソール接続用。コンソールケーブルは通信回線用ではない。

### 押さえておくポイント

- 長距離（数km〜数十km）＝シングルモード光ファイバ（細いコア・レーザー）
- 短距離（建物内・数百m）＝マルチモード光ファイバ（太いコア）
- UTPの最大長＝100m（10BASE-T〜10GBASE-T共通）
- 異なる種類（PC/ルータ ⇔ スイッチ）＝ストレート、同じ種類（スイッチ同士、PC同士、ルータ同士、PC⇔ルータ）＝クロス
- Auto-MDIXがあればどちらのケーブルでもよい
- コンソール接続＝ロールオーバーケーブル

## インターフェースの状態とトラブルシューティング

### show interfaces の読み方

Cisco IOSでインターフェースの状態を詳しく確認するコマンドが `show interfaces` です。

```
Router# show interfaces gigabitethernet0/1
GigabitEthernet0/1 is up, line protocol is up
  Hardware is iGbE, address is 5254.0012.3456 (bia 5254.0012.3456)
  Internet address is 192.168.1.1/24
  MTU 1500 bytes, BW 1000000 Kbit/sec, DLY 10 usec,
     reliability 255/255, txload 1/255, rxload 1/255
  Encapsulation ARPA, loopback not set
  Keepalive set (10 sec)
  Full Duplex, 1Gbps, media type is RJ45
  ...
  5 minute input rate 2000 bits/sec, 3 packets/sec
  5 minute output rate 1000 bits/sec, 2 packets/sec
     12345 packets input, 1234567 bytes, 0 no buffer
     Received 120 broadcasts (0 IP multicasts)
     0 runts, 0 giants, 0 throttles
     0 input errors, 0 CRC, 0 frame, 0 overrun, 0 ignored
     0 watchdog, 0 multicast, 0 pause input
     23456 packets output, 2345678 bytes, 0 underruns
     0 output errors, 0 collisions, 1 interface resets
     0 unknown protocol drops
     0 babbles, 0 late collision, 0 deferred
     0 lost carrier, 0 no carrier, 0 pause output
     0 output buffer failures, 0 output buffers swapped out
```

#### 1行目: 状態

`<インターフェース> is <物理層の状態>, line protocol is <データリンク層の状態>`

- 前半（`is up` / `is down` / `is administratively down`）＝**L1（物理層）**の状態
- 後半（`line protocol is up/down`）＝**L2（データリンク層）**の状態

| 表示（前半 / 後半） | 意味 | 主な原因 | 対処 |
| --- | --- | --- | --- |
| up / up | 正常 | — | — |
| **administratively down / down** | 管理者が無効化している | **`shutdown` コマンドが設定されている** | `no shutdown` |
| down / down | 物理的な問題 | **ケーブル未接続**・断線、相手機器の電源OFFやshutdown | ケーブル・相手側を確認 |
| up / down | L1はOK、L2に問題 | **カプセル化の不一致**（シリアルのHDLC/PPPなど）、キープアライブの問題 | L2の設定を合わせる |
| down / down (err-disabled) | エラーにより自動停止 | ポートセキュリティ違反、BPDUガードなど | 原因を取り除き shutdown → no shutdown |

`administratively` が付くのは**shutdown されているとき**だけです。**Ciscoルータのインターフェースは初期状態で shutdown されている**ことが多いので、IPアドレスを設定しても `no shutdown` を忘れると `administratively down` のままです（Ciscoスイッチのポートは初期状態で有効）。

```
Router(config)# interface gigabitethernet0/1
Router(config-if)# no shutdown
%LINK-3-UPDOWN: Interface GigabitEthernet0/1, changed state to up
%LINEPROTO-5-UPDOWN: Line protocol on Interface GigabitEthernet0/1, changed state to up
```

一覧で確認するなら `show ip interface brief`（Status 列＝L1、Protocol 列＝L2）:

```
Router# show ip interface brief
Interface              IP-Address      OK? Method Status                Protocol
GigabitEthernet0/0     10.1.1.1        YES manual up                    up
GigabitEthernet0/1     192.168.1.1     YES manual administratively down down
GigabitEthernet0/2     unassigned      YES unset  down                  down
Serial0/0/0            172.16.1.1      YES manual up                    down
```

スイッチでは `show interfaces status` も便利です（connected / notconnect / disabled / err-disabled）。

### デュプレックスと速度

| 方式 | 動作 | 衝突 |
| --- | --- | --- |
| **全二重（Full Duplex）** | 送信と受信を**同時**に行う | 起きない（CSMA/CD不要） |
| **半二重（Half Duplex）** | 送信と受信を**交互**に行う | 起きうる（CSMA/CDで検出して再送） |

スイッチ同士、スイッチとPCなどは通常全二重で動作します。ハブは半二重です。

#### オートネゴシエーション

速度とデュプレックスは、両端が `auto` ならオートネゴシエーションで自動的に最適な値にそろいます。片側だけ固定にすると、

- auto 側は**速度**は信号から検出できるが、**デュプレックスは決められない**
- そのとき auto 側は、10/100Mbps なら**半二重**、1Gbps 以上なら全二重を選ぶ

このため、例えば片側を `speed 100` / `duplex full` に固定し、相手を auto にすると、相手は半二重になって**デュプレックスの不一致（duplex mismatch）**が起きます。

#### デュプレックス不一致で起きること

```
 SW1（全二重）                            SW2（半二重）
  「いつでも送ってよい」                    「相手が送っている間は送らない」
   ───── フレーム送信 ──────────────────▶
   ◀──── フレーム送信 ───────────────────   SW2が送信中にSW1からも届く
                                           → SW2は衝突と判断して送信を中断
                                             （送信開始から64バイト以降なら late collision）
   SW1は途中で切れたフレームを受信
   → FCSが合わない → CRCエラー / runts
```

| 側 | 増えるカウンタ |
| --- | --- |
| **半二重側** | **collisions、late collision**（レイトコリジョン） |
| **全二重側** | **CRCエラー（input errors）、runts** など |

症状は「リンクは up/up なのに通信が非常に遅い」。**対策は、両端のデュプレックスと速度の設定を合わせる**（両方を `auto` にするか、両方を同じ値に固定する）ことです。

```
SW2(config)# interface gigabitethernet0/1
SW2(config-if)# speed 1000
SW2(config-if)# duplex full
```

CDPが有効なら、次のようなログで不一致に気付けることもあります。

```
%CDP-4-DUPLEX_MISMATCH: duplex mismatch discovered on GigabitEthernet0/1 (not half duplex), with SW1 GigabitEthernet0/1 (full duplex).
```

### 主なインターフェースのエラーカウンタ

| カウンタ | 意味 | 主な原因 |
| --- | --- | --- |
| **CRC** | FCSの検査に失敗したフレーム数 | **ケーブル不良・ノイズ・規格外の長さ**、デュプレックス不一致 |
| input errors | 受信エラーの合計（CRC、runts、giants などを含む） | 物理層の問題全般 |
| runts | 64バイト未満の短すぎるフレーム | 衝突、デュプレックス不一致 |
| giants | 最大サイズを超えるフレーム | MTU設定の不一致、NICの不良 |
| collisions | 衝突の回数 | 半二重環境（ハブ）、デュプレックス不一致 |
| **late collision** | 送信開始から64バイト以降に検出した衝突 | **デュプレックス不一致**、ケーブルが長すぎる |
| output errors | 送信エラーの合計 | — |
| input/output drops | バッファがあふれて破棄 | 輻輳（帯域不足） |

#### CRCエラーの仕組み

イーサネットフレームの最後には **FCS（Frame Check Sequence）**というエラー検出用の値（CRC-32で計算）が付いています。受信側は受け取ったフレームから同じ計算をし、FCSと一致しなければ**フレームが壊れている**と判断して破棄し、**CRCエラー**として数えます。

```
[宛先MAC][送信元MAC][タイプ][ データ ][FCS]
                                       ↑ 送信側が計算して付加
受信側: 自分で計算した値 ≠ FCS → 破棄して CRC カウンタ +1
```

フレームが壊れる原因は**物理的な問題**（ケーブルの損傷、100mを超える規格外の長さ、電気的なノイズ、コネクタの接触不良）がほとんどで、デュプレックスの不一致も原因になります。したがってCRCエラーが増え続けていたら、**まずケーブルの交換や接続状態を確認**します。

ACLによる拒否、宛先のルートがないことによる破棄、DHCPのアドレス不足などは、より上の層の問題で、インターフェースの受信エラー（CRC）には表れません。

### 層ごとの切り分け

トラブルシューティングでは**下の層から順に**確認するのが基本です。

| 層 | 確認内容 | コマンド例 |
| --- | --- | --- |
| L1 | ケーブル、リンクLED、up/down、CRC・コリジョン | `show interfaces`, `show ip interface brief`, `show interfaces status` |
| L2 | line protocol、デュプレックス、VLAN、MACアドレステーブル | `show interfaces`, `show vlan brief`, `show mac address-table` |
| L3 | IPアドレス・マスク、ルート、到達性 | `show ip route`, `ping`, `traceroute` |
| L4〜L7 | ACL、ポート、名前解決、アプリケーション | `show access-lists`, `nslookup` |

カウンタをリセットして、エラーが**今も増えているか**を確認するのも定番です。

```
Router# clear counters gigabitethernet0/1
Clear "show interface" counters on this interface [confirm]
```

### ひっかけポイント・よくある誤解

- **`administratively down` をケーブル未接続と考える誤り。** ケーブル未接続は `down, line protocol is down`（administratively は付かない）。`administratively down` は shutdown されている状態。
- **`up / down` と `down / down` の混同。** 物理的にはつながっているがL2に問題がある＝`up, line protocol is down`。正常は `up, line protocol is up`。
- **コリジョンの原因を IPアドレス重複・VLAN不一致・OSPFタイマー不一致と考える誤り。** IPアドレス重複はL3の問題、VLAN不一致は通信が届かなくなるだけ、OSPFタイマー不一致はネイバーにならないだけで、どれもインターフェースのコリジョンカウンタには表れない。
- **CRCエラーの原因を ACL・ルートなし・DHCPのアドレス不足と考える誤り。** CRCは受信フレームの破損＝物理層の問題。
- **デュプレックス不一致で両側ともコリジョンが増える、は不正確。** コリジョン（late collision）は半二重側、CRCエラーは全二重側に出る。

### 押さえておくポイント

- `is administratively down, line protocol is down` → shutdown されている → `no shutdown`
- `down / down` → ケーブル・相手側の物理的な問題、`up / down` → L2の問題（カプセル化の不一致など）
- 前半＝L1、後半（line protocol）＝L2
- 片側で late collision が増える → デュプレックス不一致（半二重側でコリジョン、全二重側でCRC）→ 両端の設定を合わせる
- CRCエラーが増加 → まずケーブル不良・ノイズなど物理層を疑う
- Ciscoルータのインターフェースは初期状態で shutdown
