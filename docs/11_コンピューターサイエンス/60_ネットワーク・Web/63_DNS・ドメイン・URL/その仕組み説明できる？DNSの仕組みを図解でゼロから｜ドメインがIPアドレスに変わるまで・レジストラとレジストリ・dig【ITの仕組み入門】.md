## 詳しい要約

**テーマ：ドメインが IP アドレスに変わるまでと、「開かない・反映されない」の正体**

DNS の名前解決を、リゾルバーとネームサーバー（ルート・TLD・権威）のリレー、レコード（NS・A・AAAA・CNAME）、レジストラ・レジストリ・DNS のサービスの役割分担、キャッシュと TTL の順に解説する。後半は Route 53 でのドメイン設定、サブドメインを Google Cloud の Cloud DNS に委任する方法、dig による切り分けまで扱う。「反映されない」のは DNS が遅いのではなく、各地のリゾルバーのメモ（キャッシュ）が TTL まで残っているから、というのが中心の結論。

### 01 大まかな流れ

- ドメインは右から読む木構造：見えない**ルート** → com → example → www。枝ごとに受け持ちの「係」がいる。
- パソコンは自分で探さず「調べ役」に「最後まで調べて答えだけください」と頼む。調べ役は係たちに「知っているところまで教えて」と聞き、答えの代わりに次の相手を教える**紹介**をたどって答えにたどり着く。
- 調べ役は答えと途中の紹介を期限付きの**メモ**に残し、同じ質問にはメモから返す。

### 02 DNS サーバーのリレー（正式な名前）

| 段 | 内容 |
|---|---|
| 1 | パソコン → **リゾルバー**（キャッシュ DNS サーバー）。宛先はあらかじめ設定され、多くは接続事業者が用意 |
| 2 | キャッシュになければ**ルートネームサーバー**へ（IP は最初から書き込み済み）→ com の係を紹介 |
| 3 | **TLD ネームサーバー**（com・jp などルート直下）→ example.com の係を紹介 |
| 4 | **権威ネームサーバー**が答えそのものを返す |
| 5 | リゾルバーはメモしてからパソコンへ返す（パソコンから見れば 1 回頼んだだけ） |

- 聞いて回る側（リゾルバー）と答える側（ネームサーバー）はどちらも **DNS サーバー**だが役割は逆。普段「ネームサーバー」と言えば多くは権威ネームサーバー。
- PC の DNS 設定を 8.8.8.8 にするときの「DNS サーバー」は Google の公開**リゾルバー**であって、ネームサーバーではない。

### 03 リレーで出会うレコード

- レコードの 1 行は「どのドメインか・何秒覚えてよいか（期限）・種類・中身」。
- **NS**：ルートや TLD が返す紹介状。その範囲を受け持つネームサーバーのドメイン名（IP も大抵添付）。故障に備え 2 台以上なので NS は複数並ぶ。紹介の回数は木のどこで受け持ちが分かれるかで変わる。
- 権威ネームサーバーの答えは大きく 3 通り：
  1. **A**（IPv4 アドレス）／**AAAA**（IPv6。A の 4 倍の長さなので A を 4 つ）
  2. **CNAME**：「これは別名で、本当のドメインはあちら」。外部サービス上にサイトを置くときに使う。リゾルバーは本当のドメインでリレーをやり直し、CNAME と A をまとめて返す（例：www.iana.org）
  3. 「ない」：ドメインはあるが種類がない場合はエラーでなく答えが空の形。ドメイン自体がない答えもある

### 04 レコードは誰がいつ作るのか

- ドメインを**買うこと**と**答えを返すこと**は別の仕事で、3 つの役に分かれる。
  - **レジストラ**：ドメインを買う窓口。DNS の問い合わせには答えず、名前解決のリレーにも出てこない
  - **レジストリ**：TLD の台帳の持ち主（com は Verisign）。台帳の NS を元に TLD の中身を作り、TLD ネームサーバーに配る。登録の世界と名前解決の世界にまたがる
  - **DNS のサービス**：権威ネームサーバーを貸し、A・CNAME などを答える（Route 53、Cloud DNS）
- TLD ネームサーバーの中身はキャッシュとは違い期限で消えるものではなく、台帳が変わるとレジストリが配り直す。
- DNS のサービスではドメインごとに**ゾーン**を作ると、受け持つ権威ネームサーバーが自ゾーンの NS として自動で書かれる（名乗り）。親（TLD 台帳）の NS とこの名乗りの NS は**同じ内容にそろえる**決まり。
- 手順は 3 つ：①ドメインを買う ②DNS のサービスでゾーンを作る ③割り当てられたネームサーバーをレジストラ経由で台帳に載せる。同じ会社が両方を提供すると自動化され、レジストラがネームサーバーを用意したように見える（Route 53）。別会社なら、Cloud DNS が示したネームサーバー名を自分でレジストラの管理画面に書く。
- DNS のサービスを用意しなければ、ドメインを持っていても名前解決できない（**持っていることと名前解決できることは別**）。
- サブドメインは買い足さずゾーンに 1 行足すだけで作れる。1 行を作っても世界中に配られるわけではなく、**権威ネームサーバーが答えられるようになるだけ**（Route 53 では通常 60 秒以内に自社の全ネームサーバーへ行き渡る）。

### 05 「反映されない」の正体（キャッシュと TTL）

- リゾルバーは **TTL** 秒の間、聞き直さずメモから返す（dig で 5 秒空けて 2 回聞くと TTL がちょうど 5 秒減っていた）。
- 権威側はほどなく新しい答えを返せるのに、各リゾルバーのメモに古い答えが TTL まで残る。メモした時刻がリゾルバーごとに違うので、人によって開いたり開かなかったりする。
- 「ない」という答えも残る＝**ネガティブキャッシュ**。権威ネームサーバーは SOA（ゾーン管理情報）を添え、その TTL 欄を期限に使う（例では 1800 秒＝30 分）。作る前に api.example.com を試しに開くと、作った後も期限まで「ない」が返る。
- ネームサーバー自体の引っ越しはもっと長い。com の TLD が返す紹介には 2 日の期限があり、自分のゾーンの TTL では短くできない。→ 新しいネームサーバーに同じ内容をそろえてからレジストラで書き換え、古いほうは期限が過ぎるまで同じ答えを返させておく。
- CNAME を置いたドメインには他のレコードを置けない。ゾーン頂点（example.com）には NS と SOA が必ずあるので CNAME は置けない。

### 06 Route 53 でのドメイン設定

- Route 53 で買うと自動でゾーンができ、**4 台の権威ネームサーバー**が割り当てられ、NS・SOA が書かれ、台帳にも届けられる（04 の 3 手順がすべて自動）。あとは A や CNAME を足すだけ。
- ゾーン頂点には CNAME を置けないため、Route 53 独自の**エイリアス**で CloudFront などを指せる。
- 他社で買ったドメインを Route 53 で答えるなら、ゾーン作成後にレジストラでネームサーバーを Route 53 の 4 台に書き換える。忘れると TLD が古いネームサーバーを紹介し続け「開かない」原因になる。

### 07 応用：サブドメインの委任（Route 53 → Cloud DNS）

- API だけ Google Cloud で動かし api.example.com を使う場合：Cloud DNS に api.example.com のゾーンを作り、示された NS を**親の Route 53 のゾーンに NS レコードとして全部**足す。これが**委任**。レジストラでは何も変えない。
- リレーでは Route 53 は api 以下の権威ではなくなり、ルートや TLD と同じく NS で Cloud DNS を紹介する。「受け持っていない範囲を聞かれたら紹介を返す」のはどのネームサーバーも同じなので、紹介の回数は決まっていない。
- api 側の A・CNAME は Cloud DNS のゾーンに足す。なお Route 53 に A レコードを 1 行書くだけでもつながり、そちらがよく使われる。委任は API のレコードを Google Cloud 側で管理したいとき。
- 委任後も www.example.com は Route 53 が答える（任せたのは api 以下の枝だけ）。
- よくあるつまずき：①Cloud DNS のネームサーバー名を全部写していない ②Cloud DNS が自動で作った NS を消す・書き換える（親と食い違う）③作る前に開いて「ない」をメモさせる。

### 08 dig で確かめる

- 形式：`dig @聞く相手 ドメイン 種類`（@ を省くといつものリゾルバー）。Windows では nslookup が似た道具。
- 見るところ 3 つ：
  - **status**：NOERROR（問題なし）／NXDOMAIN（ドメインがない）／SERVFAIL（答えを用意できない）。NOERROR で答えが空なら、NS があれば紹介、SOA があれば種類がない
  - **flags**：QR（応答）、RD（最後まで調べてと頼んだ）、RA（相手が最後まで調べられる）、**AA**（権威ネームサーバーが自分で答えた）。リゾルバーの答えは RD・RA ありで AA なし
  - **セクション**：QUESTION／ANSWER／AUTHORITY（紹介や SOA）／ADDITIONAL（紹介先の IP など）。行は「ドメイン・TTL・IN・種類・中身」
- ルートネームサーバー a.root-servers.net に直接聞くと ANSWER 0 で org の NS が並ぶ紹介、「recursion requested but not available」の警告や RA なしは故障ではない。org の TLD → iana.org の権威とたどると AA 付きで CNAME が返り、TTL 3600 秒（リゾルバー経由で小さかったのはメモの残り時間だったから）。
- `dig +trace` はルートから順にたどってくれるが、CNAME の先は自動でたどらない。
- 切り分け（リゾルバーは家・会社で変わり、ブラウザは **DNS over HTTPS** で別のリゾルバーを使うこともあるので、聞く相手を変えて比べる：いつものリゾルバー／8.8.8.8／権威ネームサーバーに直接）：

| 症状 | 原因の見当 |
|---|---|
| 権威に直接聞いても NXDOMAIN か空で SOA 付き | レコードが本当にない（打ち間違い・作り忘れ） |
| 権威には答えがあるのにいつものリゾルバーだけ古い・ない | キャッシュが残っている |
| 権威には答えがあるのに期限を過ぎてもどこでも見つからない | 親が紹介するネームサーバーと書いた先が違う（レジストラの書き換え忘れなど）→ `+trace` で 1 つ上の NS と管理画面を比較 |
| 正しい IP が返るのに開かない | DNS の先（経路・HTTPS）を疑う。その前にブラウザの DoH のリゾルバーにも確認 |

- 委任も `+trace` で、Route 53 の段で Cloud DNS の NS が紹介され、次の段で Cloud DNS が AA 付きで答えれば成功。

### まとめ

- パソコン → リゾルバー → ルート → TLD → 権威と **NS の紹介**をたどり、CNAME ならやり直して A/AAAA で IP を得る。
- レコードは自分やクラウドが DNS のサービスに書き、そのネームサーバー名は**レジストラが TLD の台帳に NS として届ける**。レジストラ・レジストリ・DNS のサービスは別の役。
- 1 行を書いても配られるのではなく答えられるようになるだけ。答えも「ない」も TTL の間はリゾルバーに残る。これが「反映されない」の正体。
- 開かないときは「レコードがない／メモが古い／紹介先が違う／DNS の先」のどれかを、dig で聞く相手を変えて見分ける。
