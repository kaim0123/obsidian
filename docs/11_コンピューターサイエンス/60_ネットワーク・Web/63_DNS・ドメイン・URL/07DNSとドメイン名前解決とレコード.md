# DNSとドメイン名前解決とレコード

## DNSとは
**Domain Name System**の略で、人間にわかりやすい「ドメイン名」と、コンピュータが使う「IPアドレス」を**変換する仕組み**です。インターネットの「電話帳」に例えられます。

```
google.com  ⇄  142.250.196.142
（ドメイン名）  （IPアドレス）
```

## ドメイン名の構造

```
www.example.co.jp
│    │       │  │
│    │       │  └─ トップレベルドメイン（TLD）
│    │       └──── セカンドレベルドメイン
│    └──────────── サブドメイン
└───────────────── ホスト名
```

### 右から読むのがポイント
階層構造は右側ほど上位です。末尾に省略されたドット（`.`）がルートを表します。

### 代表的なTLD
- **gTLD**: `.com`, `.org`, `.net`, `.dev`
- **ccTLD**: `.jp`, `.us`, `.uk`（国別）

## 名前解決の流れ（再帰問い合わせ）

```
① [ブラウザ] → [フルサービスリゾルバ]「example.comのIPは?」
② リゾルバ → ルートDNS「知らない、.comに聞いて」
③ リゾルバ → .com DNS「example.comの担当サーバを教えて」
④ リゾルバ → example.comの権威DNS「203.0.113.5」
⑤ リゾルバ → ブラウザ「203.0.113.5です」
```

### 登場人物
- **スタブリゾルバ**: OSやブラウザ側のDNSクライアント
- **フルサービスリゾルバ（キャッシュDNS）**: 問い合わせを代行する（ISPやGoogleの `8.8.8.8` など）
- **ルートDNS / TLD DNS / 権威DNS**: 階層的に情報を管理

## キャッシュとTTL
問い合わせ結果は一定時間**キャッシュ**されます。その有効期限が**TTL (Time To Live)**です。
- TTLが短い: 変更がすぐ反映される / 問い合わせが増える
- TTLが長い: 問い合わせが減る / 変更反映に時間がかかる

DNSレコードを切り替える前はTTLを短くしておくのが定番です。

## 主要なDNSレコード

| レコード | 役割 | 例 |
|---|---|---|
| A | ドメイン → IPv4 | example.com → 203.0.113.5 |
| AAAA | ドメイン → IPv6 | example.com → 2001:db8::1 |
| CNAME | 別名（エイリアス） | www.example.com → example.com |
| MX | メールサーバー指定 | example.com → mail.example.com |
| NS | 権威DNSサーバー | example.com → ns1.example.net |
| TXT | 任意の文字列 | SPF, DKIM, 所有権証明 |
| SOA | ゾーンの管理情報 | 管理者、シリアル番号 |
| PTR | IP → ドメイン（逆引き） | 5.113.0.203.in-addr.arpa |
| SRV | サービス指定 | SIP, Microsoft系など |

### TXTレコードの使い道
- **SPF**: メール送信元の認証
- **DKIM**: メールの電子署名
- **DMARC**: SPF/DKIMの運用ポリシー
- ドメイン所有権の証明（Google Search Consoleなど）

## 確認コマンド

### dig / nslookup
```bash
# Aレコードを引く
dig example.com A

# 特定のDNSサーバーに問い合わせる
dig @8.8.8.8 example.com

# すべてのレコードタイプ
dig example.com ANY

# Windowsでは
nslookup example.com
```

## DNSとセキュリティ

### 主な脅威
- **DNSキャッシュポイズニング**: 偽の情報を注入される
- **DNSスプーフィング**: 応答を偽装される
- **DDoS**: DNSサーバー自体への攻撃

### 対策
- **DNSSEC**: 応答に電子署名を付けて改ざんを防ぐ
- **DoH / DoT**: DNS通信自体をHTTPS/TLSで暗号化

## 発展：DNS

名前解決の流れと主なDNSレコードを復習しつつ、ネットワーク機器（Cisco IOS）でのDNSの扱いを見ていきます。

### DNSと名前解決

DNS（Domain Name System）は、`www.example.com` のような **ホスト名に対応するIPアドレスを調べる** 仕組みです。これを **名前解決** と呼びます。人間はIPアドレスより名前のほうが覚えやすく、またサーバのIPアドレスが変わっても名前を変えずに済みます。

- ポート番号は **53**。通常の問い合わせには **UDP** を使います（1往復の小さなやり取りなので軽いUDPが向く）。応答が大きい場合や、DNSサーバ間でゾーン情報をまとめて転送する（ゾーン転送）場合はTCP 53を使います。

**似た仕組みとの区別**

| 仕組み | 何を何に対応づけるか / 役割 |
|---|---|
| DNS | ホスト名 → IPアドレス（名前解決） |
| DHCP | 端末にIPアドレスなどの設定を自動配布 |
| ARP | 同じネットワーク内で、IPアドレス → MACアドレス |
| NAT | プライベートIPアドレス ⇔ グローバルIPアドレスの変換 |

### PCが Webサーバにアクセスするまでの流れ

```
 PC (192.168.1.10, GW 192.168.1.1, DNS 8.8.8.8)

 ① DNS: 「www.example.com のIPアドレスは？」 → 応答「93.184.216.34」
 ② 宛先 93.184.216.34 は自分のネットワーク(192.168.1.0/24)の外
      → デフォルトゲートウェイ 192.168.1.1 へ送る必要がある
 ③ ARP: 「192.168.1.1 のMACアドレスは？」 → 応答「GWのMAC」
 ④ 宛先IP=93.184.216.34 / 宛先MAC=GWのMAC でフレームを送信
```

DNSで「宛先IP」を、ARPで「次に渡す相手（同一ネットワーク内）のMAC」を調べる、という役割分担を押さえてください。（実際には①のDNSサーバへの問い合わせ自体も、DNSサーバが別ネットワークならゲートウェイ経由で送られます。）

### 主なDNSレコード

| レコード | 内容 | 例 |
|---|---|---|
| A | ホスト名 → **IPv4** アドレス | www.example.com → 93.184.216.34 |
| AAAA | ホスト名 → **IPv6** アドレス | www.example.com → 2001:db8::10 |
| CNAME | ホスト名の別名（エイリアス） | web.example.com → www.example.com |
| MX | そのドメイン宛てのメールを受け取るメールサーバ | example.com → mail.example.com |
| PTR | IPアドレス → ホスト名（逆引き） | 34.216.184.93.in-addr.arpa → www.example.com |
| NS | そのドメインを管理するDNSサーバ | example.com → ns1.example.com |

**AAAAの名前の由来**: IPv6アドレスは128ビットで、IPv4（32ビット）の **4倍** の長さ。そこでAレコードの「A」を4つ並べてAAAA（クアッドA）と呼びます。

### Cisco IOSとDNS

ルータ自身が名前解決を行う（例：`ping www.example.com`）には、DNSサーバを指定します。

```
R1(config)# ip domain-lookup            ! 既定で有効
R1(config)# ip name-server 8.8.8.8      ! 問い合わせ先のDNSサーバ
R1(config)# ip domain-name example.com  ! ルータ自身のドメイン名（SSHの鍵作成にも必要）
```

#### 打ち間違いで待たされる問題と no ip domain-lookup

Cisco IOSは、コマンドとして認識できない **1単語** を「Telnetの接続先のホスト名」と解釈し、DNSで名前解決しようとします。DNSサーバを指定していない場合は、**255.255.255.255へブロードキャストで問い合わせ** ます。

```
R1# shwo
Translating "shwo"...domain server (255.255.255.255)
 (しばらく応答待ちで操作できない)
% Bad IP address or host name
% Unknown command or computer name, or unable to find computer address
```

この動作を止めるのが **`no ip domain-lookup`** です。

| コマンド | 効果 |
|---|---|
| `no ip domain-lookup` | DNSによる名前解決そのものを無効化 → 打ち間違いで待たされなくなる |
| `no ip name-server` | DNSサーバの指定を消すだけ。名前解決の試み自体は止まらず、ブロードキャストで問い合わせる |
| `no logging console` | コンソールへのログ表示を止める。名前解決とは無関係 |
| `ip domain-name example.com` | ルータのドメイン名を設定（SSHのRSA鍵作成に必要）。名前解決の動作は止まらない |

検証環境（ラボ）ではDNSサーバがないことが多いので、最初に `no ip domain-lookup` を設定するのが定番です。ただし **ルータで名前解決を使いたい場合は無効にしてはいけません**（ホスト名でpingやNTPサーバを指定できなくなる）。

### ひっかけポイント・よくある誤解

- 名前→IPアドレスはDNS。DHCP（設定の配布）、ARP（IP→MAC）、NAT（アドレス変換）と混同しない。
- **AAAA＝IPv6**、**A＝IPv4**。MXはメールサーバ、CNAMEは別名、PTRは逆引き。
- `no ip name-server` では名前解決は止まらない（ブロードキャストで問い合わせ続ける）。止めるのは `no ip domain-lookup`。
- `ip domain-name` はドメイン名の設定であり、名前解決を止めるものではない。
- DNSは53番。69番（TFTP）と混同しない。

### 押さえておくポイント

- DNS＝名前解決、ポート53、通常はUDP（大きな応答・ゾーン転送はTCP）。
- PCの処理順：DNSで宛先IP → （別ネットワークなら）ARPでGWのMAC → 送信。
- レコード：A（IPv4）、AAAA（IPv6）、CNAME、MX、PTR、NS。
- ルータ：`ip name-server` でDNSサーバ指定、`no ip domain-lookup` で打ち間違い時の名前解決を停止。

## 補足：DNS とドメイン（ドメインの種類・DNS サーバーの種類・運用）

ドメインの種類（gTLD・ccTLD・新 gTLD）、DNS サーバーの種類、ドメインの取得と管理、クラウドでの DNS、トラブルシューティングまでを一覧で整理します。

### 概要

DNS（Domain Name System：ドメインネームシステム）とドメインは、インターネット上でコンピュータを識別するための重要な仕組みです。人間が覚えやすいドメイン名（例：www.example.com）を、コンピュータが理解できるIPアドレス（例：192.168.1.1）に変換する役割を果たしています。

### ドメインとは

#### ドメインの基本概念

- **定義**: インターネット上での識別子
- **役割**: コンピュータやサービスの名前付け
- **形式**: 階層構造を持つ文字列
- **例**: www.example.com、mail.google.com

#### ドメインの構造

```
www.example.com
│   │       │
│   │       └─ トップレベルドメイン（TLD）
│   └───────── セカンドレベルドメイン
└───────────── サブドメイン
```

#### ドメインの階層

- **ルートドメイン**: .（ドット）
- **トップレベルドメイン（TLD）**: .com、.org、.jp
- **セカンドレベルドメイン**: example、google、yahoo
- **サブドメイン**: www、mail、ftp

#### ドメインの種類

##### 汎用トップレベルドメイン（gTLD）

- **.com**: 商用組織
- **.org**: 非営利組織
- **.net**: ネットワーク関連
- **.info**: 情報提供
- **.biz**: ビジネス

##### 国コードトップレベルドメイン（ccTLD）

- **.jp**: 日本
- **.us**: アメリカ
- **.uk**: イギリス
- **.de**: ドイツ
- **.cn**: 中国

##### 新 gTLD

- **.app**: アプリケーション
- **.blog**: ブログ
- **.shop**: ショッピング
- **.tech**: テクノロジー
- **.ai**: 人工知能

### DNS とは

#### DNS の基本概念

- **定義**: ドメイン名と IP アドレスを相互変換するシステム
- **役割**: 名前解決（Name Resolution）
- **分散データベース**: 複数のサーバーで管理
- **階層構造**: ルートサーバーから末端まで

#### DNS の仕組み

1. **クエリ送信**: ユーザーがドメイン名を入力
2. **DNS サーバー問い合わせ**: 最寄りの DNS サーバーに問い合わせ
3. **階層的解決**: ルートサーバーから順次解決
4. **IP アドレス取得**: 最終的に IP アドレスを取得
5. **結果返却**: ユーザーに IP アドレスを返却

#### DNS サーバーの種類

##### ルートサーバー

- **役割**: ドメイン階層の最上位
- **数**: 世界に 13 台（A〜M）
- **機能**: トップレベルドメインの情報提供
- **例**: a.root-servers.net

##### トップレベルドメインサーバー

- **役割**: 各 TLD の情報管理
- **例**: .com、.jp、.org の情報
- **機能**: セカンドレベルドメインの情報提供

##### 権威 DNS サーバー

- **役割**: 特定ドメインの情報管理
- **例**: example.com の情報
- **機能**: そのドメインの詳細情報提供

##### キャッシュ DNS サーバー

- **役割**: 問い合わせ結果の一時保存
- **例**: ISP の DNS サーバー
- **機能**: 高速な名前解決

#### DNS レコードの種類

##### A レコード

- **役割**: ドメイン名と IPv4 アドレスの対応
- **例**: www.example.com → 192.168.1.1
- **用途**: 基本的な名前解決

##### AAAA レコード

- **役割**: ドメイン名と IPv6 アドレスの対応
- **例**: www.example.com → 2001:db8::1
- **用途**: IPv6 対応

##### CNAME レコード

- **役割**: ドメイン名の別名設定
- **例**: www.example.com → example.com
- **用途**: サブドメインの設定

##### MX レコード

- **役割**: メールサーバーの指定
- **例**: example.com → mail.example.com
- **用途**: メール配送

##### NS レコード

- **役割**: 権威 DNS サーバーの指定
- **例**: example.com → ns1.example.com
- **用途**: ドメインの管理

##### TXT レコード

- **役割**: テキスト情報の格納
- **例**: SPF、DKIM、DMARC 設定
- **用途**: メール認証、ドメイン認証

### DNS の動作フロー

#### 名前解決の流れ

1. **ユーザー入力**: ブラウザにドメイン名を入力
2. **ローカルキャッシュ確認**: ブラウザのキャッシュを確認
3. **OS キャッシュ確認**: オペレーティングシステムのキャッシュを確認
4. **DNS サーバー問い合わせ**: 設定された DNS サーバーに問い合わせ
5. **階層的解決**: ルートサーバーから順次解決
6. **結果キャッシュ**: 解決結果をキャッシュに保存
7. **IP アドレス返却**: ユーザーに IP アドレスを返却

#### キャッシュの仕組み

- **TTL（Time To Live）**: キャッシュの有効期限
- **階層的キャッシュ**: 複数レベルでのキャッシュ
- **キャッシュ効率**: 重複問い合わせの削減
- **更新制御**: キャッシュの更新タイミング

### ドメインの取得と管理

#### ドメインの取得

- **レジストラ**: ドメインの販売業者
- **レジストリ**: ドメインの管理機関
- **取得手順**: 検索、選択、登録、支払い
- **更新**: 定期的な更新が必要

#### ドメインの設定

- **ネームサーバー**: DNS サーバーの設定
- **DNS レコード**: 各種レコードの設定
- **サブドメイン**: 追加ドメインの設定
- **リダイレクト**: ドメインの転送設定

#### ドメインの管理

- **Whois 情報**: ドメインの登録情報
- **更新管理**: 有効期限の管理
- **移転**: 他レジストラへの移転
- **削除**: ドメインの削除

### DNS のセキュリティ

#### DNS の脆弱性

- **DNS キャッシュポイズニング**: 偽の情報をキャッシュに注入
- **DNS ハイジャック**: DNS サーバーの乗っ取り
- **DNS スプーフィング**: 偽の DNS 応答
- **DDoS 攻撃**: DNS サーバーへの攻撃

#### セキュリティ対策

- **DNSSEC**: DNS の暗号化と認証
- **DNS over HTTPS**: HTTPS 経由での DNS 通信
- **DNS over TLS**: TLS 経由での DNS 通信
- **フィルタリング**: 悪意あるドメインのブロック

#### プライバシー保護

- **DNS over HTTPS**: 通信の暗号化
- **プライベート DNS**: 個人情報の保護
- **ログ管理**: アクセスログの適切な管理
- **匿名化**: 個人情報の匿名化

### 実用的な DNS 設定

#### 一般的な設定例

- **Web サイト**: A レコードで IP アドレス指定
- **メール**: MX レコードでメールサーバー指定
- **サブドメイン**: CNAME レコードで別名設定
- **CDN**: CNAME レコードで CDN 指定

#### 企業での DNS 管理

- **内部 DNS**: 社内ネットワークの名前解決

### DNS のトラブルシューティング

#### 一般的な問題

- **名前解決失敗**: ドメイン名が解決できない
- **遅い応答**: DNS 解決に時間がかかる
- **間違った結果**: 期待しない IP アドレスが返される
- **キャッシュ問題**: 古い情報がキャッシュされている

#### 診断ツール

- **nslookup**: DNS 情報の確認
- **dig**: 詳細な DNS 情報の取得
- **ping**: 接続性の確認
- **traceroute**: 経路の確認

#### 解決方法

- **DNS サーバー変更**: 別の DNS サーバーを使用
- **キャッシュクリア**: ローカルキャッシュの削除
- **設定確認**: DNS 設定の見直し
- **ネットワーク確認**: ネットワーク接続の確認

### まとめ

DNS とドメインは、インターネットの基盤となる重要な技術です。DNS は、人間が覚えやすいドメイン名を、コンピュータが理解できる IP アドレスに変換する仕組みを提供し、インターネットの利便性を大幅に向上させています。適切な DNS 設定と管理により、安定した Web サービスやメールサービスの提供が可能になります。また、DNS のセキュリティ対策により、安全なインターネット利用を実現することができます。
