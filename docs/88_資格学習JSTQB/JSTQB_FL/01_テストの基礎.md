> [!note] この章ノートの構成（2026-09-25 統合）

## 要点（シラバス v4.0 準拠）

### 1.1 テストとは何か

#### テストの目的
- 要件、ユーザーストーリー、設計、コードなどの作業成果物を**評価**する
- **欠陥（defect）**を発見し、故障（failure）を防ぐ
- 指定された要件が**充足されていること**を確認する
- テスト対象の**品質レベルに対する信頼**を積み上げる
- ステークホルダーが**意思決定**するための情報を提供する

#### テストとデバッグの違い
| テスト | デバッグ |
|--------|---------|
| 故障（failure）を見つける活動 | 故障の原因である欠陥（defect）を見つけて修正する活動 |
| テスト担当者が行う | 開発者が行う |
| 確認テスト（再テスト）で修正を検証 | コードの修正そのもの |

---

### 1.2 テストはなぜ必要か

#### エラー・欠陥・故障の関係
```
人間のエラー（error/mistake）
  → コード・仕様書などに欠陥（defect/bug/fault）が入り込む
    → 実行時に故障（failure）が発生する
```

- エラー: 人間が犯す間違い
- 欠陥: 作業成果物に含まれる不備
- 故障: システムが期待通りに動作しないこと
- **注意**: 欠陥があっても必ず故障するとは限らない（実行されない経路など）
- **根本原因（root cause）**: エラーを引き起こした最も根本的な理由

#### テストの7原則

> **必ず出題される最重要トピック**

| # | 原則 | 説明 |
|---|------|------|
| 1 | テストは欠陥があることは示せるが、欠陥がないことは示せない | テストで欠陥0を証明するのは不可能 |
| 2 | 全数テストは不可能 | すべての入力・条件の組み合わせはテストできない |
| 3 | 早期テストで時間とコストを節約 | 開発の早い段階でテストを開始すべき（シフトレフト） |
| 4 | 欠陥の偏在 | 少数のモジュールに欠陥が集中する（パレートの法則） |
| 5 | 殺虫剤のパラドックス | 同じテストを繰り返すと新たな欠陥を見つけられなくなる |
| 6 | テストはコンテキストに依存する | ドメインやシステムに応じてテストを変える必要がある |
| 7 | 「欠陥ゼロ」の落とし穴 | 欠陥をすべて修正してもユーザーのニーズを満たさなければ意味がない |

---

### 1.3 テストの活動、テストウェア、テストの役割

#### 基本的なテストプロセス
1. **テスト計画**: テストの目的を定義し、アプローチを選択する
2. **テストのモニタリングとコントロール**: 進捗を監視し、計画との乖離に対処する
3. **テスト分析**: 「何をテストするか」を決める（テスト条件の識別）
4. **テスト設計**: 「どのようにテストするか」を決める（テストケース作成）
5. **テスト実装**: テスト実行に必要なものを準備する（テストデータ、環境）
6. **テスト実行**: テストを実行し、結果を記録する
7. **テスト完了**: テストの終了と成果物の整理

#### テストウェア（テスト成果物）
- テスト計画書
- テストケース
- テストデータ
- テストスクリプト
- テストログ
- テスト報告書
- 欠陥レポート

#### テストの役割
| テストマネージャー | テスト担当者 |
|--------------------|-------------|
| テスト計画の作成 | テストの分析・設計・実装・実行 |
| テスト進捗のモニタリング | テスト結果の記録 |
| リソースの調整 | 欠陥レポートの作成 |

---

### 1.4 テストの基本的なスキルとベストプラクティス

#### テスト担当者に必要なスキル
- ソフトウェアテストの知識
- 注意深さ・好奇心・批判的思考
- 効果的なコミュニケーション能力
- ドメイン知識
- 技術的スキル

#### 独立したテスト
- テストの独立性が高いほど、異なる視点からの欠陥発見が期待できる
- 独立性のレベル（低→高）:
  1. 開発者自身によるテスト
  2. 同じチームの別の開発者
  3. 同じ組織の別チーム
  4. 外部組織

### 1.1 テストとは何か

#### ソフトウェアテストの定義

ソフトウェアテストとは、**ソフトウェアの品質を評価し、欠陥を発見するための活動**です。

テストは単に「プログラムを動かして確認する」ことだけではありません。以下のすべてがテストに含まれます：

- テストの**計画**（何をどうテストするか決める）
- テストケースの**設計**（具体的なテスト内容を作る）
- テストの**実行**（実際にテストする）
- 結果の**評価**（期待通りかどうか判断する）
- テストの**報告**（結果をまとめて伝える）

> **ポイント**: テスト＝「動かして確認する」だけではない。計画からレポートまでの一連の活動がテストです。

#### テストの目的

テストにはいくつかの目的があります：

| 目的 | 説明 |
|------|------|
| **欠陥の発見** | バグを見つける（最も一般的な目的） |
| **品質レベルの確認** | 要件を満たしているか確認する |
| **意思決定の情報提供** | リリースしてよいかの判断材料を提供する |
| **欠陥の作りこみ防止** | レビューなどで早期に問題を防ぐ |

#### テストとデバッグの違い

この区別は試験で頻出です。

| | テスト | デバッグ |
|--|--------|----------|
| **目的** | 欠陥（故障）を**発見**する | 欠陥の**原因を特定して修正**する |
| **誰が行うか** | テスト担当者 | 開発者 |
| **作業内容** | テストケースを実行し、期待結果と比較する | コードを解析し、原因を突き止めて直す |

```
テスト → 「ここがおかしい」を見つける
デバッグ → 「なぜおかしいか」を突き止めて直す
```

### 1.2 テストの重要性（なぜテストが必要か）

#### ソフトウェア欠陥がもたらすリスク

ソフトウェアの欠陥は深刻な影響を引き起こす可能性があります：

- **金銭的損失** — 銀行システムの計算ミス、ECサイトの決済エラー
- **時間の浪費** — システム障害による業務停止
- **信頼の喪失** — ユーザー離れ、ブランドイメージの低下
- **人命への影響** — 医療機器や自動車の制御ソフトの不具合

#### テストで品質は向上するか？

テストは品質を**直接的に向上させるわけではありません**。テストは欠陥を**発見**するだけです。品質を向上させるのは、発見した欠陥を**修正**することです。

ただし、テスト活動全体（レビューやテスト設計を含む）を通じて、間接的に品質向上に貢献します。

### 1.3 基本用語：エラー・欠陥・故障

JSTQB FL最重要の用語です。必ず覚えましょう。

#### 3つの用語の関係

```
人間がミスをする → コードにバグが入る → システムが正しく動かない
    エラー              欠陥（defect）          故障（failure）
   （error）           = バグ（bug）
                       = フォールト（fault）
```

| 用語 | 英語 | 意味 | 例 |
|------|------|------|-----|
| **エラー** | error / mistake | 人間の**間違い・思い違い** | 仕様を誤解した、タイプミスした |
| **欠陥** | defect / bug / fault | コードやドキュメントの**誤り** | if文の条件が逆、計算式が間違い |
| **故障** | failure | システムが期待通りに**動作しない**こと | 画面にエラーが表示される、計算結果がおかしい |

#### 覚え方

```
エラー（人がミスする）
  ↓ ミスがコードに入る
欠陥（コードにバグがある）
  ↓ そのコードが実行される
故障（システムが誤動作する）
```

> **注意**: 欠陥があっても、そのコードが実行されなければ故障は起きません。また、故障の原因は欠陥だけではなく、環境要因（メモリ不足など）の場合もあります。

#### 根本原因（root cause）

故障が発生した場合、その**根本的な原因**を追求することが重要です。

```
故障: ログイン画面でエラーが出る
  ↓ なぜ？
欠陥: パスワード照合のコードにバグがある
  ↓ なぜ？
エラー: 開発者が仕様を誤解していた
  ↓ なぜ？（根本原因の追求）
根本原因: 仕様書の記述が曖昧だった
```

### 1.4 テストの7原則

JSTQB FLで最も有名なトピックです。**7つすべて**を覚えましょう。

#### 原則1：テストは欠陥があることは示せるが、欠陥がないことは示せない

```
テストで「バグがある」→ 証明できる ✓
テストで「バグがない」→ 証明できない ✗
```

どれだけテストしても「欠陥がゼロ」とは言えません。テストは欠陥の**存在**を示すことはできますが、**不在**を証明することはできません。

#### 原則2：全数テストは不可能

すべての入力値、すべての条件の組み合わせをテストすることは現実的に**不可能**です。

```
例：数値を2つ入力する画面
  入力A: 0〜999999999（10億通り）
  入力B: 0〜999999999（10億通り）
  組み合わせ: 10億 × 10億 = 100京通り → テスト不可能
```

そのため、**リスクと優先度**に基づいてテストを集中させる必要があります。

#### 原則3：早期テスティング — テストは早期に開始する

欠陥は**早く見つけるほど修正コストが低い**です。

```
要件定義段階で発見 → 修正コスト: 小
設計段階で発見     → 修正コスト: 中
コーディング後に発見 → 修正コスト: 大
リリース後に発見   → 修正コスト: 特大
```

「シフトレフト」とも呼ばれます。テスト活動を開発の早い段階から始めることが重要です。

#### 原則4：欠陥の偏在

欠陥は**均等には分布しません**。特定のモジュールに集中する傾向があります。

```
モジュールA: 欠陥 2個
モジュールB: 欠陥 15個  ← ここに集中！
モジュールC: 欠陥 3個
モジュールD: 欠陥 1個
```

パレートの法則（80:20の法則）に似ています：少数のモジュールに大多数の欠陥が集中します。

#### 原則5：殺虫剤のパラドックス

同じテストを繰り返しても、**新しい欠陥は見つからなくなります**。

```
殺虫剤 → 同じものを使い続けると虫が耐性をもつ
テスト → 同じテストを繰り返すと新しいバグが見つからなくなる
```

対策：テストケースを定期的に**見直し・更新**する必要があります。

#### 原則6：テストは状況次第

テストのやり方は**状況（コンテキスト）によって異なります**。

```
ECサイト     → セキュリティ、決済処理を重点的にテスト
医療システム → 安全性、信頼性を最優先でテスト
ゲームアプリ → ユーザビリティ、パフォーマンスを重視
```

万能のテスト手法は存在しません。対象に応じたテスト戦略が必要です。

#### 原則7：「欠陥ゼロ」の落とし穴

すべての欠陥を修正しても、ユーザーのニーズを満たさなければ意味がありません。

```
欠陥をすべて修正した → でもユーザーが使いにくい → 失敗
```

テストは**ユーザーの要求や期待**も考慮する必要があります。

#### 7原則の覚え方

| # | キーワード | ひとこと |
|---|-----------|---------|
| 1 | 欠陥の存在 | バグゼロは証明できない |
| 2 | 全数テスト不可能 | 全部はテストできない |
| 3 | 早期テスティング | 早く見つけると安い |
| 4 | 欠陥の偏在 | バグは一部に集中する |
| 5 | 殺虫剤のパラドックス | 同じテストでは見つからない |
| 6 | テストは状況次第 | 万能な方法はない |
| 7 | 欠陥ゼロの落とし穴 | バグゼロでも失敗する |

### 1.5 テストプロセス

テストは以下の主要な活動で構成されます。

#### テストプロセスの活動

```
テスト計画 → テストのモニタリングとコントロール → テスト分析
    → テスト設計 → テスト実装 → テスト実行 → テスト完了
```

| 活動 | 内容 | 成果物の例 |
|------|------|-----------|
| **テスト計画** | テストの方針・スケジュール・リソースを決める | テスト計画書 |
| **テストモニタリングとコントロール** | 進捗を監視し、計画との差異を調整する | 進捗レポート |
| **テスト分析** | 「何をテストするか」を決める（テストベースの分析） | テスト条件 |
| **テスト設計** | 「どうテストするか」を決める（テストケース設計） | テストケース |
| **テスト実装** | テスト実行に必要なものを準備する | テスト手順、テストデータ |
| **テスト実行** | テストケースを実行し、結果を記録する | テスト結果、欠陥レポート |
| **テスト完了** | テスト活動をまとめ、教訓を記録する | テスト完了レポート |

#### テスト分析と設計の違い（頻出）

| | テスト分析 | テスト設計 |
|--|-----------|-----------|
| **問い** | **何を**テストするか？ | **どうやって**テストするか？ |
| **作業内容** | テストベースを分析し、テスト条件を識別する | テスト条件をテストケースに具体化する |
| **成果物** | テスト条件 | テストケース |

```
テスト分析: 「ログイン機能をテストすべき」（何を）
テスト設計: 「ID=admin, PW=1234で正常ログインを確認」（どうやって）
```

#### テストベースとテスト対象

| 用語 | 意味 | 例 |
|------|------|-----|
| **テストベース** | テスト設計の**元になる資料** | 要件定義書、設計書、仕様書 |
| **テスト対象** | テストする**対象物** | ソースコード、システム |

### 1.6 テストの心理学

#### 開発者とテスト担当者の違い

| | 開発者 | テスト担当者 |
|--|--------|-------------|
| **目的** | ソフトウェアを**作る** | 欠陥を**見つける** |
| **マインドセット** | 構築的（constructive） | 批判的（critical） |
| **バイアス** | 自分のコードの欠陥を見つけにくい（確認バイアス） | 客観的に欠陥を探せる |

#### 独立したテスト

自分で作ったものを自分でテストすると、無意識に「動くはず」と思い込むため欠陥を見逃しやすくなります。これを**確認バイアス（confirmation bias）**と呼びます。

テストの独立性のレベル：

```
低い ← 独立性 → 高い

開発者自身 → 同じチームの別メンバー → 別チーム → 別組織
```

独立性が高いほど客観的にテストできますが、開発との情報共有が難しくなるトレードオフがあります。
