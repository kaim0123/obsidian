## 要点（シラバス v4.0 準拠）

### 5.1 テスト計画

#### テスト計画書に含まれる内容
- テストの範囲（スコープ）と目的
- テストアプローチ・テスト戦略
- スケジュール・マイルストーン
- リソース（人員・ツール・環境）
- テストの開始基準・終了基準
- リスクと対策
- テスト成果物

#### テストアプローチ
- **分析的アプローチ**: リスクや要件を分析してテストを設計（リスクベーステスト）
- **モデルベースアプローチ**: モデル（状態遷移図など）に基づいてテストを設計
- **体系的アプローチ**: チェックリストや品質特性に基づく体系的なテスト
- **プロセス準拠アプローチ**: 規格やプロセスに準拠したテスト
- **リアクティブアプローチ**: テスト実行中の結果に反応してテストを設計（探索的テスト）

#### 開始基準と終了基準
| 開始基準（Entry Criteria） | 終了基準（Exit Criteria） |
|---------------------------|--------------------------|
| テスト環境が準備できている | 計画したテストケースをすべて実行した |
| テスト対象がデプロイされている | 目標カバレッジを達成した |
| テストデータが準備できている | 未解決の重大欠陥がない |
| テストツールが使用可能 | リスク受容レベルに達した |

---

### 5.2 リスクマネジメント

#### リスクの定義
- **リスク** = 将来、否定的な結果をもたらす事象が発生する可能性
- **リスクレベル** = 発生可能性 × 影響度

#### リスクの種類
| プロダクトリスク | プロジェクトリスク |
|----------------|------------------|
| ソフトウェア品質に関するリスク | プロジェクト遂行に関するリスク |
| 例: 性能が要件を満たさない | 例: スケジュール遅延 |
| 例: セキュリティの脆弱性 | 例: テスト環境が不足 |
| 例: 機能が仕様通りに動かない | 例: テスト担当者のスキル不足 |

#### リスクベーステスト
1. **リスク識別**: プロダクトリスクを洗い出す
2. **リスク評価**: 発生可能性と影響度でリスクレベルを算出
3. **リスク軽減**: リスクレベルの高い順にテストの優先順位を決定
- リスクが高い項目 → テストを厚く、早く実施
- リスクが低い項目 → テストを軽く、後で実施

---

### 5.3 テストのモニタリングとコントロール

#### テスト進捗のモニタリング指標
- テストケースの実行状況（実行済み / 未実行 / 合格 / 不合格）
- 欠陥の検出数と修正状況
- カバレッジの達成率
- テストの残作業量
- テスト環境の可用性

#### テスト報告書
- **テスト進捗報告書**: テスト期間中の定期的な報告
- **テストサマリー報告書**: テスト完了時の最終報告
  - 実施したテストの要約
  - テスト期間中に発生した事象
  - 品質評価
  - 残存リスク
  - 未解決の欠陥一覧

---

### 5.4 構成管理

#### 構成管理の目的
- テストウェア（テストケース・テストデータなど）のバージョン管理
- テスト対象のバージョンとテスト結果の紐づけ
- トレーサビリティの確保

---

### 5.5 欠陥マネジメント

#### 欠陥レポートに含める情報
- 欠陥ID
- タイトル・要約
- 発見日・報告者
- テスト対象の識別情報（バージョンなど）
- 再現手順
- 期待結果と実際の結果
- 重大度（Severity）と優先度（Priority）
- ステータス（新規 → オープン → 修正済み → クローズ）
- スクリーンショット・ログなどの証跡

#### 重大度と優先度の違い
| 重大度（Severity） | 優先度（Priority） |
|-------------------|-------------------|
| 欠陥がシステムに与える技術的影響の大きさ | ビジネス上の修正の緊急度 |
| テスト担当者が判断 | ビジネス側が判断 |
| 例: システムクラッシュ → 高 | 例: デモ前の見た目の問題 → 高 |

### 5.1 テスト組織と独立性

#### テストの独立性レベル

テストの客観性を高めるために、テストの独立性が重要です。

```
低い ← ─── 独立性 ─── → 高い

①開発者自身 → ②同チームの別メンバー → ③別チーム → ④別組織
```

| レベル | 説明 | メリット | デメリット |
|--------|------|---------|-----------|
| ①開発者自身 | 自分で書いたコードを自分でテスト | 迅速、コードの理解が深い | 確認バイアスで見逃しやすい |
| ②同チーム | 同じチームの別メンバーがテスト | バイアスが軽減 | 同じ前提を共有している可能性 |
| ③別チーム | 専門のテストチームがテスト | 客観的、専門スキルがある | 開発とのコミュニケーションコスト |
| ④別組織 | 外部のテスト会社がテスト | 最も客観的 | コスト高、情報伝達が困難 |

#### テストマネージャとテスト担当者の役割

| 役割 | 主な責務 |
|------|----------|
| **テストマネージャ** | テスト計画の作成、リソース管理、進捗管理、テスト戦略の決定 |
| **テスト担当者（テスター）** | テストケースの設計・実行、欠陥の報告、テストデータの準備 |

### 5.2 テスト計画

#### テスト計画書の主な内容

| 項目 | 内容 |
|------|------|
| **テストの範囲** | 何をテストするか・しないか |
| **テストアプローチ** | どのようなテスト技法・ツールを使うか |
| **スケジュール** | いつまでに何を完了するか |
| **リソース** | 人員、環境、ツール |
| **開始基準・終了基準** | テストの開始条件と完了条件 |
| **リスク** | テストに関するリスクと対策 |

#### テストアプローチの種類

| アプローチ | 説明 |
|-----------|------|
| **分析的** | リスク分析に基づいてテストの優先順位を決める（リスクベースドテスト） |
| **モデルベース** | モデル（状態遷移図など）に基づいてテストを設計する |
| **体系的** | チェックリストや品質特性に基づいて体系的にテストする |
| **プロセス準拠** | 標準やプロセスに従ってテストする |
| **コンサルティング型** | 専門家の助言に基づいてテストする |
| **リグレッション回避型** | 回帰テストの自動化を重視する |
| **リアクティブ** | テスト実行時の結果に応じて次のテストを決める（探索的テスト） |

#### 開始基準と終了基準

##### 開始基準（Entry Criteria）

テストを開始してよい条件です。

```
開始基準の例:
  ✓ テスト環境が準備できている
  ✓ テスト対象のビルドが完了している
  ✓ テストケースのレビューが完了している
  ✓ テストデータが準備できている
```

##### 終了基準（Exit Criteria）

テストを完了してよい条件です。

```
終了基準の例:
  ✓ 計画したテストケースを全て実行した
  ✓ ステートメントカバレッジが80%以上
  ✓ 重大な欠陥がすべて修正されている
  ✓ 残存する欠陥が許容範囲内
```

### 5.3 テストの見積もり

テストにかかる工数を見積もる手法です。

| 手法 | 説明 |
|------|------|
| **メトリクスベース** | 過去のプロジェクトのデータ（メトリクス）に基づいて見積もる |
| **エキスパートベース** | 専門家の経験に基づいて見積もる |

```
メトリクスベース:
  「前回のプロジェクトでは1000行あたり5件の欠陥があったので、
   今回の3000行では15件程度の欠陥を想定し、テスト工数を計算する」

エキスパートベース:
  「ベテランのテストマネージャに聞いたところ、
   この規模なら3人で2週間程度かかるとの見積もり」
```

### 5.4 テストのモニタリングとコントロール

#### テストモニタリング

テストの進捗を**監視**する活動です。

##### 主なメトリクス（測定指標）

| メトリクス | 測定内容 |
|-----------|---------|
| **テストケース実行率** | 計画したテストのうち何%を実行したか |
| **合格率** | 実行したテストのうち何%が合格したか |
| **欠陥検出数** | テストで見つかった欠陥の数 |
| **欠陥修正率** | 見つかった欠陥のうち何%が修正されたか |
| **カバレッジ** | コードやテスト条件をどの程度網羅したか |

##### テスト進捗レポート

```
テスト進捗の例:
  計画テストケース数: 200
  実行済み: 150（75%）
  合格: 140
  不合格: 10
  未実行: 50
  検出欠陥数: 15
  修正済み: 10
  未修正: 5（うち重大: 2）
```

#### テストコントロール

モニタリングの結果に基づいて、**計画を修正・調整**する活動です。

```
例:
  モニタリング結果: 重大な欠陥が多く、予定通り進まない
  コントロール: テストの優先順位を見直し、リソースを追加する
```

### 5.5 構成管理（Configuration Management）

テストに関連する成果物を**一元管理**し、変更を追跡可能にすることです。

#### 構成管理の対象

- テスト計画書
- テストケース
- テストスクリプト
- テスト結果
- テスト環境の設定情報
- テスト対象のソフトウェア（バージョン）

```
問題例:
  「テストが失敗した！でも、どのバージョンのソフトをテストしたか分からない...」

構成管理を行えば:
  「バージョン2.1.3でテスト実行。結果はチケット#456に記録済み」
  → 再現・追跡が可能
```

### 5.6 リスクとテスト

#### リスクベースドテスト

リスクの高い部分から優先的にテストするアプローチです。

#### リスクの2つの側面

```
リスクレベル = 発生可能性 × 影響度
```

| 要素 | 説明 |
|------|------|
| **発生可能性** | その問題がどの程度の確率で発生するか |
| **影響度** | 発生した場合、どの程度の影響があるか |

#### リスクの種類

| 種類 | 説明 | 例 |
|------|------|-----|
| **プロダクトリスク** | ソフトウェア製品の**品質に関するリスク** | 機能が動かない、性能が出ない |
| **プロジェクトリスク** | プロジェクトの**管理に関するリスク** | スケジュール遅延、要員不足 |

```
プロダクトリスク:
  「決済処理にバグがあると、金銭的損害が発生する」
  → 発生可能性: 中、影響度: 大 → リスクレベル: 高
  → テストを優先的に実施！

プロジェクトリスク:
  「テスターが病欠で人手が足りない」
  → テスト計画の見直しが必要
```

#### リスクベースドテストの進め方

```
1. リスクを識別する
   「どんな問題が起こりうるか？」

2. リスクを評価する
   「発生可能性 × 影響度 = リスクレベル」

3. テストの優先順位を決める
   リスクが高い → 最優先でテスト
   リスクが低い → 後回し or 省略

4. テストを実行する
   リスクの高いものから順にテスト
```

### 5.7 欠陥マネジメント

#### 欠陥レポート（インシデントレポート）

欠陥を発見した際に記録するレポートです。

##### 欠陥レポートに含める情報

| 項目 | 内容 |
|------|------|
| **識別子** | 一意のID（例: BUG-001） |
| **タイトル** | 欠陥の概要（例: ログインボタンが反応しない） |
| **再現手順** | 欠陥を再現するための手順 |
| **期待結果** | 本来あるべき動作 |
| **実際の結果** | 実際に起きた動作 |
| **重大度** | 欠陥の影響の大きさ |
| **優先度** | 修正の緊急度 |
| **状態** | オープン、修正中、修正済み、クローズなど |
| **環境** | テスト環境の情報（OS、ブラウザなど） |

#### 重大度と優先度の違い（頻出）

| | 重大度（Severity） | 優先度（Priority） |
|--|-------------------|-------------------|
| **定義** | 欠陥がシステムに与える**影響の大きさ** | 欠陥を修正する**緊急度** |
| **誰が決めるか** | 主にテスト担当者 | 主にマネージャ／ビジネス側 |
| **基準** | 技術的な影響度 | ビジネス的な重要度 |

```
重大度: 高 × 優先度: 高
  → 決済処理でデータが消える → すぐ修正！

重大度: 高 × 優先度: 低
  → めったに使わない管理機能の重大バグ → 後で修正

重大度: 低 × 優先度: 高
  → トップ画面のロゴが少しずれている → 見た目の問題だがすぐ修正

重大度: 低 × 優先度: 低
  → ヘルプ画面の誤字 → 余裕があれば修正
```
