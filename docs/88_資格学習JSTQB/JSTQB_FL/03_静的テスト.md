## 要点（シラバス v4.0 準拠）

### 3.1 静的テストの基礎

#### 静的テストとは
- ソフトウェアを**実行せずに**作業成果物を検証する活動
- 対象: 要件仕様書、設計書、コード、テスト計画書、ユーザーマニュアルなど
- **すべての作業成果物**がレビュー対象になりうる

#### 静的テストと動的テストの比較
| 静的テスト | 動的テスト |
|-----------|-----------|
| ソフトウェアを実行しない | ソフトウェアを実行する |
| 欠陥（defect）を直接検出 | 故障（failure）を検出 → 欠陥を特定 |
| 早い段階で実施可能 | 実行可能なコードが必要 |
| レビュー・静的解析 | テスト実行 |

#### 静的テストで検出しやすい欠陥
- 要件の欠陥（矛盾、曖昧さ、欠落）
- 設計の欠陥（非効率な設計、不整合）
- コーディング標準からの逸脱
- セキュリティの脆弱性
- テストベースのカバレッジのギャップ

---

### 3.2 レビュープロセス

#### レビューの種類

| レビュータイプ | 形式度 | 特徴 |
|--------------|--------|------|
| インフォーマルレビュー | 低 | 形式的な手順なし。バディチェックなど |
| ウォークスルー | 低〜中 | 作成者が主導して説明。理解の共有が目的 |
| テクニカルレビュー | 中〜高 | 技術的な観点でのレビュー。技術専門家が参加 |
| インスペクション | 高 | 最も形式的。メトリクス収集、プロセス改善に活用 |

#### レビューの役割
- **作成者（Author）**: レビュー対象の作業成果物を作成した人
- **マネージャー**: レビューの計画を承認、リソースを割り当てる
- **ファシリテーター（モデレーター）**: レビュー会議を効果的に進行する
- **レビューリーダー**: レビュー全体の責任を持つ
- **レビューアー**: 作業成果物の欠陥を見つける
- **記録者（スクライブ）**: 指摘事項を記録する

#### フォーマルレビュープロセス（インスペクション）
1. **計画**: レビュー範囲、目的、参加者を決定
2. **レビュー開始**: 成果物を配布、参加者がレビューの目的を理解
3. **個人レビュー**: 各レビューアーが個別に成果物を確認し、欠陥を記録
4. **課題の共有と分析**: レビュー会議で指摘事項を議論
5. **修正と報告**: 作成者が修正し、レビュー結果を報告

#### レビューの成功要因
- 明確な目的の設定
- 適切なレビューアーの選定
- 十分な準備時間の確保
- マネジメントのサポート
- 建設的なフィードバック文化
- チェックリストの活用

---

### 3.3 静的解析

#### 静的解析ツールが検出できるもの
- コーディング標準違反
- セキュリティの脆弱性
- 到達不能コード
- 未定義変数の使用
- コードの複雑度（循環的複雑度など）
- 制御フローの問題

#### 静的解析 vs レビュー
- **静的解析**: ツールによる自動的な検出（コードに対して実施）
- **レビュー**: 人間による手動の検出（あらゆる作業成果物に対して実施）

### 3.1 静的テストとは

#### 静的テスト vs 動的テスト

| | 静的テスト | 動的テスト |
|--|-----------|-----------|
| **定義** | ソフトウェアを**実行せずに**検証する | ソフトウェアを**実行して**検証する |
| **対象** | コード、仕様書、設計書、テスト計画書など | 実行可能なソフトウェア |
| **方法** | レビュー、静的解析 | テストケースの実行 |
| **発見しやすいもの** | 要件の矛盾、コーディング規約違反、設計の不整合 | 機能の誤動作、性能問題 |

```
静的テスト: コードを「読んで」バグを見つける（実行しない）
動的テスト: コードを「動かして」バグを見つける（実行する）
```

#### 静的テストで発見できる欠陥の例

- 要件定義書の**曖昧さ**や**矛盾**
- 設計書の**不整合**
- コーディング規約への**違反**
- セキュリティの**脆弱性**
- **未使用の変数**、到達不能コード
- **テストケースの不備**

> **ポイント**: 静的テストは**動的テストでは見つけにくい欠陥**を発見できます。両方を組み合わせることが重要です。

### 3.2 レビュープロセス

#### レビューとは

レビューとは、人が成果物（ドキュメント、コードなど）を**調査・検討**して欠陥を見つける活動です。

#### 公式レビューのプロセス

公式なレビューは以下のステップで進みます：

```
計画 → レビューの開始 → 個々のレビュー → 課題の共有と分析 → 修正と報告
```

| ステップ | 内容 |
|----------|------|
| **計画** | レビュー範囲・参加者・スケジュールを決める |
| **レビューの開始** | レビュー対象物を配布し、目的を説明する |
| **個々のレビュー** | 各レビューアが個別にレビュー対象を確認する |
| **課題の共有と分析** | 見つかった課題をレビュー会議で共有・議論する |
| **修正と報告** | 欠陥を修正し、結果を報告する |

#### レビューの役割

| 役割 | 担当内容 |
|------|----------|
| **作成者（Author）** | レビュー対象物を作った人。指摘を受けて修正する |
| **モデレータ（ファシリテータ）** | レビュー会議の**進行役**。最も重要な役割 |
| **レビューア（レビューワー）** | レビュー対象を調査し、欠陥を指摘する人 |
| **レビューリーダー（マネージャ）** | レビューの計画を立て、実施を管理する人 |
| **記録係（スクライブ）** | レビュー会議での指摘事項を記録する人 |

> **試験ポイント**: モデレータ（ファシリテータ）は**最も訓練を必要とする**重要な役割です。

---

### 3.3 レビューの種類

レビューには**形式度（フォーマリティ）**のレベルが異なる種類があります。

#### 4つのレビュータイプ

形式度が低い順に並べます：

```
非公式 ← ─────────────── 形式度 ─────────────── → 公式

非公式レビュー → ウォークスルー → テクニカルレビュー → インスペクション
```

##### 1. 非公式レビュー（インフォーマルレビュー）

| 項目 | 内容 |
|------|------|
| **形式度** | 最も低い |
| **特徴** | 公式な手順・記録なし |
| **例** | 隣の席の同僚にコードを見てもらう（バディチェック） |
| **目的** | 手軽に欠陥を見つける |

```
「ちょっとこのコード見てくれない？」
→ 非公式レビュー
```

##### 2. ウォークスルー

| 項目 | 内容 |
|------|------|
| **形式度** | やや低い |
| **進行者** | **作成者**が主導 |
| **特徴** | 作成者が参加者に内容を説明しながら進める |
| **目的** | 欠陥の発見、学習、共通理解の形成 |

```
作成者: 「この部分はこういう意図で書きました」
参加者: 「この条件分岐はおかしくないですか？」
→ ウォークスルー
```

> **覚え方**: ウォークスルー = 作成者が「ウォーク（歩きながら）」説明する

##### 3. テクニカルレビュー

| 項目 | 内容 |
|------|------|
| **形式度** | やや高い |
| **進行者** | **モデレータ**（訓練された進行役） |
| **参加者** | 技術的な専門家 |
| **特徴** | 技術的な問題を議論、合意形成を行う |
| **目的** | 技術的な欠陥の発見、意思決定 |

##### 4. インスペクション

| 項目 | 内容 |
|------|------|
| **形式度** | **最も高い** |
| **進行者** | 訓練された**モデレータ** |
| **特徴** | 明確なルール・チェックリスト・メトリクスを使用 |
| **目的** | 欠陥の発見（最も効果的） |
| **補足** | 作成者はレビューアになれない |

> **試験ポイント**: インスペクションは最もフォーマルで、最も欠陥発見の効果が高いレビュータイプです。

#### レビュータイプの比較表

| 特徴 | 非公式 | ウォークスルー | テクニカル | インスペクション |
|------|--------|---------------|-----------|----------------|
| 形式度 | 最低 | 低 | 中〜高 | 最高 |
| 主導者 | なし | 作成者 | モデレータ | モデレータ |
| チェックリスト | なし | 任意 | 任意 | **あり** |
| 記録 | なし | 任意 | あり | **必須** |
| メトリクス | なし | なし | 任意 | **あり** |

---

### 3.4 レビューの成功要因

レビューを効果的に行うためのポイント：

- **明確な目的**を定義する
- **適切なレビュータイプ**を選ぶ
- **小さな単位**でレビューする（大きすぎると集中力が続かない）
- **十分な準備時間**を確保する
- **建設的なフィードバック**を心がける（個人攻撃にしない）
- マネジメントがレビューを**支援**する
- **チェックリスト**を活用する

> **重要**: レビューでは「人」ではなく「成果物」を評価します。「あなたのコードはダメだ」ではなく「この部分に問題がある」というスタンスが大切です。

---

### 3.5 静的解析

#### 静的解析とは

静的解析は、**ツールを使って**コードやドキュメントを自動的に分析する手法です。人手のレビューとは異なり、ツールが機械的にチェックします。

#### 静的解析で検出できるもの

| 検出項目 | 例 |
|----------|-----|
| **コーディング規約違反** | 変数名が命名規則に違反している |
| **未使用変数** | 宣言したが使われていない変数 |
| **到達不能コード** | 絶対に実行されないコード |
| **セキュリティ脆弱性** | バッファオーバーフローの可能性 |
| **コードの複雑度** | 複雑すぎてバグが発生しやすい箇所 |

```javascript
// 静的解析で検出できる例

function example() {
    let unusedVar = 10;  // ← 未使用変数

    if (true) {
        return "hello";
    }

    console.log("ここは実行されない");  // ← 到達不能コード
}
```

#### コンパイラとの違い

コンパイラも構文エラーを検出しますが、静的解析ツールはそれに加えて、コーディング規約違反やセキュリティ上の問題など、**より広範な問題**を検出します。
