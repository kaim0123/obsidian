## 要点（シラバス v4.0 準拠）

### 2.1 SDLCにおけるテスト

#### テストと開発モデルの関係
テスト活動はSDLC（ソフトウェア開発ライフサイクル）のモデルに関係なく存在するが、
モデルによってテストのタイミングや進め方が変わる。

#### 良いテストのための一般的な原則
- 開発活動にはそれぞれ対応するテスト活動がある
- テストレベルごとに固有の目的がある
- テスト分析・設計は対応する開発活動と並行して開始する
- 早い段階でのテスト参加（レビューなど）が品質向上に寄与する

#### 主要な開発モデル

##### シーケンシャル開発モデル
- **ウォーターフォールモデル**: 各フェーズが順番に進行。前フェーズの完了後に次へ
- **V字モデル**: 開発の各フェーズに対応するテストレベルが定義される

```
要件定義  ←→  受入テスト
  基本設計  ←→  システムテスト
    詳細設計  ←→  統合テスト
      実装  ←→  コンポーネントテスト
```

##### 反復的・漸進的開発モデル
- **アジャイル（スクラム・XP等）**: 短いイテレーションで開発・テストを繰り返す
- **プロトタイピング**: 試作品を通じてフィードバックを得る
- **スパイラル**: リスク分析を重視した反復モデル

#### シフトレフトアプローチ
- テスト活動をSDLCの**より早い段階**に移動させる考え方
- 例:
  - 開発前にテストケースを作成する
  - 要件段階からレビューに参加する
  - コード記述前にテストを書く（TDD）
  - CI/CDで自動テストを早期に実行する

---

### 2.2 テストレベル

#### テストレベルの一覧

| テストレベル | テスト対象 | 主な目的 | 典型的な実施者 |
|-------------|-----------|---------|--------------|
| コンポーネントテスト（単体テスト） | 個々のモジュール・クラス・関数 | コンポーネント単体の動作確認 | 開発者 |
| コンポーネント統合テスト | コンポーネント間のインターフェース | コンポーネント間の連携確認 | 開発者 |
| システムテスト | システム全体 | 要件に対するシステム全体の動作確認 | 独立テストチーム |
| システム統合テスト | 他システムとのインターフェース | 外部システムとの連携確認 | 独立テストチーム |
| 受入テスト | システム全体 | ビジネス要件の妥当性確認 | ユーザー・顧客 |

#### 受入テストの種類
- **ユーザー受入テスト（UAT）**: ユーザーが実業務の観点で確認
- **運用受入テスト（OAT）**: システム管理者がバックアップ・リカバリ等を確認
- **契約受入テスト**: 契約の受入基準に基づく確認
- **規制受入テスト**: 法規制・標準への準拠を確認
- **アルファテスト**: 開発組織内でユーザーに使ってもらうテスト
- **ベータテスト**: 外部のユーザーに使ってもらうテスト

---

### 2.3 テストタイプ

#### 機能テスト
- システムが**何をするか（what）**をテストする
- 要件・仕様に基づく
- すべてのテストレベルで実施可能

#### 非機能テスト
- システムが**どのように動作するか（how well）**をテストする
- ISO 25010の品質特性に基づく:
  - 性能効率性
  - 互換性
  - 使用性
  - 信頼性
  - セキュリティ
  - 保守性
  - 移植性

#### ブラックボックステスト
- 内部構造を考慮しない
- 仕様・要件からテストケースを導出

#### ホワイトボックステスト
- 内部構造（コード）を考慮する
- コードカバレッジを測定

#### 変更関連テスト
- **確認テスト（再テスト）**: 欠陥修正後に同じテストで修正を確認
- **リグレッションテスト（回帰テスト）**: 変更が他の部分に悪影響を与えていないか確認

---

### 2.4 メンテナンステスト

#### メンテナンステストが必要な場面
- 修正（コレクティブ）: バグ修正
- 適応（アダプティブ）: 環境変更への対応
- 改善（パーフェクティブ）: 機能追加・性能向上
- 予防（プリベンティブ）: 将来の問題を予防

#### 影響度分析
- 変更がシステムの他の部分に与える影響を分析する
- リグレッションテストの範囲を決定するために必要

### 2.1 ソフトウェア開発モデル

#### V字モデル（Vモデル）

JSTQB FLで最も重要な開発モデルです。開発工程とテスト工程が**対応関係**にあります。

```
要件定義 ─────────────────────── 受入テスト
    ↘                           ↗
  基本設計 ──────────────── システムテスト
      ↘                     ↗
    詳細設計 ────────── 結合テスト
        ↘               ↗
      コーディング → 単体テスト
```

**左側**（開発工程）で作成したドキュメントが、**右側**（テスト工程）のテストの基準（テストベース）になります。

| 開発工程 | 対応するテストレベル | テストベース |
|----------|---------------------|-------------|
| 要件定義 | 受入テスト | 要件定義書 |
| 基本設計 | システムテスト | 基本設計書 |
| 詳細設計 | 結合テスト | 詳細設計書 |
| コーディング | 単体テスト | 詳細設計書・コード |

#### その他の開発モデル

| モデル | 特徴 | テストとの関係 |
|--------|------|---------------|
| **ウォーターフォール** | 各工程を順番に進める | テストは後工程で実施 |
| **反復型（イテレーティブ）** | 短いサイクルで繰り返し開発 | 各イテレーションでテストを実施 |
| **インクリメンタル** | 機能を少しずつ追加 | 追加分と既存部分の両方をテスト |
| **アジャイル** | 変化に対応しながら反復開発 | テストが開発に組み込まれる（継続的テスト） |

#### 開発モデルに共通するテストの原則

どの開発モデルでも以下が成り立ちます：

1. **開発活動にはそれぞれ対応するテスト活動がある**
2. **テストレベルにはそれぞれ固有の目的がある**
3. **テスト分析と設計は、対応する開発活動の中で開始すべき**
4. **開発成果物のドラフトが入手可能になり次第、テスト担当者はレビューに参加すべき**

### 2.2 テストレベル

テストレベルとは、テストを**段階的に**組織化したものです。4つのレベルがあります。

#### 4つのテストレベル

```
                    ┌─────────────────┐
                    │   受入テスト     │  ← ユーザー視点
                    └────────┬────────┘
                    ┌────────┴────────┐
                    │ システムテスト   │  ← システム全体
                    └────────┬────────┘
                    ┌────────┴────────┐
                    │   結合テスト     │  ← モジュール間の連携
                    └────────┬────────┘
                    ┌────────┴────────┐
                    │   単体テスト     │  ← 個々のモジュール
                    └─────────────────┘
```

#### 各テストレベルの詳細

##### 1. 単体テスト（コンポーネントテスト / ユニットテスト）

| 項目 | 内容 |
|------|------|
| **テスト対象** | 個々のモジュール、関数、クラス |
| **テストベース** | 詳細設計書、コード |
| **実施者** | 主に**開発者** |
| **目的** | 各部品が単独で正しく動くか確認 |
| **特徴** | スタブやドライバを使うことがある |

```
例：電卓アプリの「足し算関数」だけをテストする
  add(2, 3) → 5 を期待 → 5が返る → OK
  add(-1, 1) → 0 を期待 → 0が返る → OK
```

**スタブとドライバ：**
```
ドライバ: テスト対象を呼び出す仮のプログラム（上位の代わり）
スタブ:   テスト対象が呼び出す仮のプログラム（下位の代わり）

  [ドライバ]    ← 呼び出す側の代役
      ↓
  [テスト対象]
      ↓
  [スタブ]      ← 呼び出される側の代役
```

##### 2. 結合テスト（統合テスト / インテグレーションテスト）

| 項目 | 内容 |
|------|------|
| **テスト対象** | モジュール間のインターフェース、連携 |
| **テストベース** | 設計書、インターフェース仕様 |
| **実施者** | 開発者またはテスト担当者 |
| **目的** | モジュール同士が正しく連携するか確認 |
| **特徴** | 結合する順序（戦略）がある |

```
例：ログイン画面 → 認証モジュール → データベース の連携テスト
  正しいID/PWを入力 → 認証成功 → ホーム画面に遷移するか？
```

**結合テストの戦略：**

| 戦略 | 説明 |
|------|------|
| **トップダウン** | 上位モジュールから下位に向かって結合（スタブを使う） |
| **ボトムアップ** | 下位モジュールから上位に向かって結合（ドライバを使う） |
| **ビッグバン** | すべてを一度に結合してテスト（非推奨、問題箇所の特定が困難） |

##### 3. システムテスト

| 項目 | 内容 |
|------|------|
| **テスト対象** | システム全体 |
| **テストベース** | 要件定義書、基本設計書 |
| **実施者** | **独立したテストチーム** |
| **目的** | システムが要件を満たしているか確認 |
| **特徴** | 本番に近い環境で実施 |

```
例：ECサイト全体を通して
  商品検索 → カートに追加 → 注文 → 決済 → 確認メール送信
  の一連の流れが正しく動くか確認
```

##### 4. 受入テスト（アクセプタンステスト）

| 項目 | 内容 |
|------|------|
| **テスト対象** | システム全体（ユーザー視点） |
| **テストベース** | ユーザー要件、業務プロセス |
| **実施者** | **ユーザー・発注者** |
| **目的** | ユーザーが受け入れ可能か判断 |
| **特徴** | 欠陥発見が主目的ではない |

受入テストの種類：

| 種類 | 目的 |
|------|------|
| **ユーザー受入テスト（UAT）** | ユーザーが業務で使えるか確認 |
| **運用受入テスト** | 運用担当者がバックアップ・復旧などを確認 |
| **契約受入テスト** | 契約上の要件を満たしているか確認 |
| **規制受入テスト** | 法規制・業界標準に準拠しているか確認 |
| **アルファテスト** | 開発元のサイトでユーザーが行うテスト |
| **ベータテスト** | ユーザーのサイトでユーザーが行うテスト |

### 2.3 テストタイプ

テストタイプは「**何を**テストするか」の観点で分類したものです。

#### 4つのテストタイプ

| テストタイプ | 観点 | 例 |
|-------------|------|-----|
| **機能テスト** | システムが**何をするか** | ログイン機能が正しく動くか |
| **非機能テスト** | システムが**どの程度うまく動くか** | レスポンスが3秒以内か |
| **構造テスト** | **内部構造**が正しいか | コードの全分岐を通過したか |
| **変更関連テスト** | 変更後も**正しく動くか** | バグ修正後に他が壊れていないか |

#### 機能テスト

「何をするか」に着目。仕様に書かれた機能が正しく動くかを確認します。

```
仕様: パスワードは8文字以上であること
テスト: 7文字のパスワード → エラーが出るか確認
テスト: 8文字のパスワード → 登録できるか確認
```

#### 非機能テスト

「どの程度うまく動くか」に着目。品質特性を確認します。

| 品質特性 | テスト内容の例 |
|----------|---------------|
| **性能** | 1000人同時接続で応答時間は3秒以内か |
| **ユーザビリティ** | 初めてのユーザーが迷わず操作できるか |
| **信頼性** | 24時間連続稼働してもエラーにならないか |
| **セキュリティ** | SQLインジェクション攻撃を防げるか |
| **互換性** | Chrome、Firefox、Safariで正しく表示されるか |
| **移植性** | Windows、macOS両方で動作するか |

> **非機能テストは全テストレベルで実施可能**です。

#### 構造テスト（ホワイトボックステスト）

コードの内部構造に基づいてテストします。詳しくは第4章で解説します。

```
if (age >= 18) {
    return "成人";
} else {
    return "未成年";
}

→ age=20（trueの分岐）と age=15（falseの分岐）の両方をテスト
```

#### 変更関連テスト

##### 確認テスト（リテスト）

欠陥を修正した後、**その欠陥が本当に直ったか**を確認するテストです。

```
欠陥: ログインボタンが反応しない
修正: ボタンのイベントハンドラを修正
確認テスト: ログインボタンが正しく反応するか確認
```

##### 回帰テスト（リグレッションテスト）

修正や変更によって、**他の部分に悪影響が出ていないか**を確認するテストです。

```
修正: ログイン機能のバグ修正
回帰テスト: ログアウト、パスワード変更、ユーザー登録なども正しく動くか確認
```

> **確認テスト vs 回帰テスト**（超頻出）
> - 確認テスト = 直した箇所が直ったか確認
> - 回帰テスト = 直した影響で他が壊れていないか確認

### 2.4 メンテナンステスト

リリース後のソフトウェアに対する変更に伴うテストです。

#### メンテナンスが発生する理由

| 理由 | 例 |
|------|-----|
| **計画的な改善** | 新機能の追加、UIの改善 |
| **是正的な修正** | 本番で発見されたバグの修正 |
| **環境の変更** | OSのバージョンアップ、データベースの移行 |
| **廃止** | システムの移行やリタイア |

#### 影響度分析

変更がどの範囲に影響するかを分析することです。回帰テストの範囲を決めるのに重要です。

```
「ログイン処理を変更」
  ↓ 影響範囲を分析
  ・認証モジュール → 直接影響あり
  ・ユーザー管理画面 → 間接的に影響あり
  ・商品検索機能 → 影響なし
  → 認証モジュールとユーザー管理画面を回帰テストの対象にする
```
