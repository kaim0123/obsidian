# アプリに組み込むプロンプト設計

[[10_プロンプトエンジニアリングの基本]] は「人が AI ツールに頼むときのプロンプト」の話でした。アプリに組み込むプロンプトは、それと違って **何千人ものユーザーの入力に対して、毎回同じ品質で動く必要があります**。つまり、プロンプトは **コードの一部** として扱います。

---

## 1. プロンプトの部品

| 部品 | 誰が書くか | 例 |
|------|-----------|----|
| **システムプロンプト** | 開発者（固定） | 役割、ルール、口調、出力形式 |
| **参照資料** | アプリが動的に入れる | RAG の検索結果、ユーザーのプロフィール |
| **ユーザー入力** | ユーザー | 質問や依頼の本文 |
| **例（few-shot）** | 開発者 | 入力と理想の出力の組 |

```ts
const system = `あなたは家電メーカーのサポート担当です。

# ルール
- 回答は <documents> の内容だけを根拠にします
- 資料にないことは「分かりかねます」と答え、窓口の電話番号を案内します
- 3 文以内で答えます`;

const userContent = `<documents>
${retrievedDocs}
</documents>

<question>
${userQuestion}
</question>`;
```

- **資料とユーザー入力は XML タグなどで区切ります**。どこまでが指示で、どこからがデータかを LLM に分かるようにするためです。
- 区切っても、データの中に書かれた指示に LLM が従ってしまう可能性は残ります（[[08_プロンプトインジェクション]]）。

---

## 2. 良いシステムプロンプトの書き方

| ポイント | 悪い例 | 良い例 |
|---------|--------|--------|
| **目的と背景を書く** | 「短く答えて」 | 「スマホの通知に出すので 40 字以内で答えて」 |
| **してほしいことを書く** | 「Markdown を使わないで」 | 「普通の文章で、段落に分けて書いて」 |
| **判断に迷う場面の指針を書く** | （書かない） | 「質問があいまいなときは、1 つだけ確認の質問をする」 |
| **例を見せる** | 説明だけ | 理想的な入出力を 2〜3 個 |

- 理由を添えると、LLM は書かれていない場面にもルールの意図を当てはめてくれます。
- 「絶対に」「必ず」を多用すると、最新のモデルではかえって過剰に反応することがあります。普通の言葉で十分です。

---

## 3. プロンプトをコードとして管理する

| やること | 理由 |
|---------|------|
| **Git でバージョン管理** | いつ・誰が・なぜ変えたか追える |
| **変更したら評価を回す** | 1 か所直すと、別のケースが悪くなることがよくある（[[01_LLMアプリの評価（Evals）]]） |
| **ログにプロンプトのバージョンを残す** | 品質が落ちたとき、どの版が原因か分かる（[[01_LLM呼び出しの可観測性]]） |
| **固定部分を先頭に置く** | プロンプトキャッシュが効き、安く速くなる（[[02_LLMのコスト最適化]]） |

- システムプロンプトに **現在時刻やリクエスト ID を入れない** でください。毎回内容が変わり、キャッシュが効かなくなります。必要ならユーザーメッセージ側に入れます。

---

## 4. チェックリスト

- [ ] 指示・資料・ユーザー入力をタグで区切っている
- [ ] ルールには理由や目的を添えている
- [ ] 迷う場面（資料にない、質問があいまい）の振る舞いを決めている
- [ ] プロンプトを Git で管理し、変更時に評価を回している
