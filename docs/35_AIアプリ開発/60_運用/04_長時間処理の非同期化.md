# 長時間処理の非同期化

LLM の処理は数十秒〜数分、エージェントなら数十分かかることもあります。HTTP リクエストの中で終わるのを待つ（同期処理）と、タイムアウト・二重課金・固まった画面の原因になります。

大事なのは「Lambda を使うこと」ではなく、**リクエストの受付と、実際の処理を分ける** ことです。Lambda や Vercel、Trigger.dev などは、その処理を **どこで動かすか** の選択肢にすぎません。

---

## 1. なぜ同期処理だと困るのか

| 問題 | 内容 |
|------|------|
| **ゲートウェイのタイムアウト** | API Gateway（REST）は原則 29 秒、Vercel は既定で 5 分など、HTTP の入口に上限がある |
| **実行時間の上限** | Lambda は最大 15 分。エージェントははみ出すことがある |
| **待ち時間も課金** | 多くのサーバーレスは、LLM の返事を待っているだけの時間も課金される |
| **途中で落ちると最初から** | リトライのたびに LLM を呼び直し、料金も二重にかかる |
| **ユーザーが画面を離れられない** | タブを閉じたら処理が消える |

---

## 2. 基本の形：ジョブ方式

```
① ブラウザ → API ：「この処理をお願い」
② API：ジョブ ID を発行し、DB に status=queued で保存 → キューに入れる → すぐ 202 と ID を返す
③ ワーカー：キューから取り出して LLM を呼ぶ → 結果と status=done を DB に保存
④ ブラウザ：ID の状態を確認（ポーリング / SSE・WebSocket / 完了通知）
```

```ts
// ② 受付 API（どの基盤でも形は同じ）
export async function POST(req: Request) {
  const { input } = await req.json();
  const jobId = crypto.randomUUID();
  await db.jobs.insert({ id: jobId, status: "queued", input, userId });
  await queue.send({ jobId });                       // SQS / Trigger.dev / Inngest など
  return Response.json({ jobId }, { status: 202 });
}

// ③ ワーカー
async function worker({ jobId }: { jobId: string }) {
  const job = await db.jobs.get(jobId);
  if (job.status === "done") return;                 // 二重実行の防止（冪等性）
  await db.jobs.update(jobId, { status: "running" });
  const result = await callLLM(job.input);
  await db.jobs.update(jobId, { status: "done", result });
}
```

### ジョブの状態

| status | 意味 |
|--------|------|
| `queued` | 受け付けた、まだ始まっていない |
| `running` | 処理中（進み具合 `progress` を持たせてもよい） |
| `done` | 完了。`result` を持つ |
| `failed` | 失敗。`error` を持つ |
| `canceled` | ユーザーが中止した |

---

## 3. どの方式でも必要な設計

| 項目 | 内容 |
|------|------|
| **冪等性** | キューは同じメッセージを 2 回届けることがある。ジョブ ID で「もう終わっていたら何もしない」 |
| **リトライの範囲** | 429・5xx・タイムアウトだけ再試行。400 は再試行しない（[[02_LLM APIの基本とストリーミング]]） |
| **失敗の逃がし先** | 何度も失敗するジョブはデッドレターキューへ移し、`failed` にする |
| **途中経過の保存** | 長い処理はステップに分け、終わったステップの結果を保存。落ちても続きから再開できる |
| **結果の受け取り方** | まずはポーリング（数秒ごとに GET）。必要になってから SSE・WebSocket・メール通知 |
| **進み具合とキャンセル** | 「検索中」「3/5 件完了」の表示、中止ボタン（[[03_AI機能のUX設計]]） |
| **権限** | ジョブ ID を知っていれば誰でも結果を見られる、にならないよう userId で確認する |
| **上限** | 1 ユーザーの同時実行数、1 ジョブのトークン上限（[[02_LLMのコスト最適化]]） |

---

## 4. 処理の長さで選ぶ

| 状況 | 方式 |
|------|------|
| チャットで、すぐ表示し始めたい（数分以内） | **ストリーミング**（非同期ではなく「少しずつ返す」） |
| 1 件が十数分以内の単発処理 | **キュー ＋ ワーカー** |
| 複数ステップ、待ち（人の承認など）がある、数十分以上 | **ワークフローエンジン（durable execution）** |
| 1 ステップ自体が非常に長い | **時間制限のないコンテナ / 常駐ワーカー** |
| 急がない大量処理 | LLM の **Batch API**（半額程度になるものが多い） |

**durable execution（耐久実行）** は、ステップごとの結果を基盤が保存してくれる仕組みです。落ちても続きから再開でき、待っている間は課金されないものが多いです。Lambda durable functions、Step Functions、Trigger.dev、Inngest、Vercel Workflow、Cloudflare Workflows などがあります。

---

## 5. AWS で作る場合

| 状況 | AWS の構成 |
|------|-----------|
| ストリーミング | Lambda レスポンスストリーミング（関数 URL / API Gateway）。最大 15 分 |
| キュー ＋ ワーカー | **API Gateway → SQS → Lambda → DynamoDB** |
| 長いワークフロー | **Lambda durable functions**（コードで書く、最長 1 年）または **Step Functions**（状態機械で組む） |
| 1 ステップが長い | ECS / Fargate |
| エージェントの実行を任せる | Bedrock AgentCore Runtime |

細かい設定・制限・注意点は [[20_LLMの長時間処理を非同期で動かす]]（63_AWS/16_サーバーレス開発）にまとめた。

- **向いている人**：すでに AWS を使っている、細かく制御したい、社内の規定で AWS を使う必要がある
- **大変なところ**：IAM・SQS・DynamoDB・Step Functions など **覚えるサービスと設定が多い**。IaC（SAM / CDK）もほぼ必須

---

## 6. AWS より簡単な方法

インフラを組まず、**関数を書いて「これをバックグラウンドで動かして」と呼ぶだけ** で済むサービスが増えています。TypeScript / Next.js のアプリならとくに相性がよいです。

### 6.1 選択肢

| サービス | しくみ | 長さの目安 | 向いている場面 |
|---------|--------|----------|--------------|
| **Trigger.dev** | タスクを Trigger.dev のマシンにデプロイして実行 | 実行時間の上限なし。5 秒以上の待ちは課金されない（クラウド版） | 長いエージェント処理を、ワーカー管理なしで動かしたい。いちばん手軽 |
| **Inngest** | 自分のアプリの API ルートを Inngest が HTTP で呼ぶ。ステップごとに状態を保存 | 1 回の実行は最長 30 日（無料）〜 366 日。各ステップはホスティング先の時間制限に従う | Next.js on Vercel で、ワークフローを普通のルートとして書きたい |
| **Vercel Functions ＋ Vercel Workflow** | 関数の実行時間を延ばす。さらに長いものは Workflow で一時停止・再開 | 関数：既定 5 分、Pro で最大 800 秒（ベータで 30 分）。Workflow は時間制限なし | すでに Vercel にデプロイしている |
| **Upstash Workflow（QStash）** | 自分のアプリのルートを、ステップごとに HTTP で呼んでもらう | 1 ステップは無料で 15 分、固定プランで最大 12 時間 | サーバーレスのまま、ステップ単位の従量課金で使いたい |
| **Cloudflare Workflows** | Workers の上で `step.do` / `step.sleep` で書く | 待ちは最長 365 日。ステップ数は無料 1,024 / 有料 25,000 | すでに Cloudflare Workers を使っている |
| **常駐ワーカー（BullMQ ＋ Redis など）** | Render / Railway / Fly.io などで、普通の Node.js プロセスを動かし続ける | 時間制限なし | サーバーレスの制約が面倒。昔ながらの構成で分かりやすくしたい |
| **LLM ベンダーのエージェント実行基盤** | Claude Managed Agents など。ループと実行環境をベンダーが持つ | 長時間のセッションを想定 | エージェントそのものを任せたい |

> 数字は 2026 年 7〜10 月時点の公式ドキュメント・比較記事によるもの。料金と制限はよく変わるので、使う前に必ず公式で確認する。

### 6.2 イメージ（Trigger.dev の場合）

```ts
// trigger/summarize.ts — バックグラウンドで動くタスク
import { task } from "@trigger.dev/sdk";

export const summarizeTask = task({
  id: "summarize-document",
  run: async ({ jobId }: { jobId: string }) => {
    const job = await db.jobs.get(jobId);
    const result = await callLLM(job.input);       // 何分かかっても OK
    await db.jobs.update(jobId, { status: "done", result });
  },
});

// app/api/jobs/route.ts — 受付 API からは「呼ぶだけ」
await summarizeTask.trigger({ jobId });
```

- SQS・IAM・DynamoDB の設定はいりません。キュー・リトライ・ログ画面がサービス側に最初からあります。
- SDK の書き方はバージョンで変わるので、実装時は公式のクイックスタートに合わせてください。

### 6.3 AWS と簡単な方法の比較

| 観点 | AWS（SQS / Lambda / Step Functions） | Trigger.dev・Inngest など |
|------|-----------------------------------|------------------------|
| 始めるまで | IAM・キュー・テーブル・IaC の準備が必要 | SDK を入れて関数を書くだけ |
| 時間の制限 | Lambda 15 分（durable functions で延長） | 上限なし〜数十日 |
| 画面（ログ・再実行） | CloudWatch などを自分で組み合わせる | ジョブ一覧・再実行の画面が最初からある |
| 料金 | 細かく従量。大規模では安くなりやすい | 無料枠あり。規模が大きくなると割高なことも |
| 依存 | AWS だけで完結 | 外部サービスが 1 つ増える（障害・値上げの影響を受ける） |
| 向いている人 | AWS に慣れている、社内で AWS が決まっている | 個人開発・小さなチーム、まず早く動かしたい |

---

## 7. おすすめの進め方

1. **まず簡単な方法で作る**：Next.js なら Trigger.dev か Inngest、常駐サーバーがあるなら BullMQ。受付 API ＋ ジョブテーブル ＋ ポーリングで始める
2. **処理をステップに分ける**：「検索 → 要約 → 整形」のように分け、ステップごとに結果を保存
3. **必要になったら移す**：AWS に寄せる必要が出てきたら、同じジョブ方式のまま SQS ＋ Lambda や durable functions に置き換える（受付 API とジョブテーブルの形は変わらない）
