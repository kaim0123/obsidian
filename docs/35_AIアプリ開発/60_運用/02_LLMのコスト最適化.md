# LLMのコスト最適化

LLM の料金はトークン単位で、利用が増えるほどそのまま請求が増えます（[[04_モデル選定とトークン課金]]）。**品質を落とさずに減らせるもの → 品質と引き換えのもの** の順に手を付けます。どの施策も、[[01_LLMアプリの評価（Evals）]] で品質が保たれているか確かめてから採用します。

---

## 1. まず測る

- 機能ごと・モデルごとに **入力・出力・キャッシュのトークン数とコスト** を記録します（[[01_LLM呼び出しの可観測性]]）。
- 1 リクエストではなく **1 タスクが完了するまでの合計** で見ます。安い設定でもやり直しが増えれば、結局高くなります。

---

## 2. 品質を落とさずに減らせるもの

| 施策 | 内容 | 効果 |
|------|------|------|
| **プロンプトキャッシュ** | 毎回同じ先頭部分（システムプロンプト・ツール定義・長い資料）をキャッシュする | キャッシュから読んだ部分の入力料金が大幅に安くなり、速くもなる |
| **不要なコンテキストを削る** | 使わない資料、古い履歴、巨大なツール結果を入れない | 入力トークンが減る |
| **出力を短くする** | 「3 文以内」「JSON だけ返す」など、必要な長さを指定する | 単価の高い出力トークンが減る |
| **バッチ API** | 急がない処理（夜間の一括要約など）をまとめて投げる | 通常の半額程度になる API が多い |
| **結果をアプリ側でキャッシュ** | 同じ質問・同じ文書の要約は保存して使い回す | 呼び出し自体がなくなる |

### プロンプトキャッシュの例（Claude API）

```ts
const response = await client.messages.create({
  model: "claude-opus-5-5",
  max_tokens: 16000,
  cache_control: { type: "ephemeral" }, // 最後のキャッシュ可能なブロックまでを自動でキャッシュ
  system: longSystemPromptAndManual,     // 毎回同じ内容を先頭に
  messages,
});

// 2 回目以降、ここが 0 のままならキャッシュが効いていない
console.log(response.usage.cache_read_input_tokens);
```

- キャッシュは **先頭からの完全一致** です。システムプロンプトに日時や ID を入れると毎回変わり、効かなくなります。
- 変わる部分（ユーザーの質問など）は後ろに置きます。

---

## 3. 品質と引き換えのもの

| 施策 | 内容 | 注意 |
|------|------|------|
| **思考の深さ（effort）を下げる** | 簡単な処理では推論の量を減らす | 難しい処理では品質が落ちる |
| **安いモデルに替える** | 分類・抽出など簡単な処理から | 評価セットで必須の例が落ちないか確認 |
| **モデルの振り分け** | 簡単な質問は小さいモデル、難しい質問は大きいモデル | 振り分け自体の精度・管理の手間・キャッシュが分かれる |

- いきなり複数モデルの振り分けを作るより、**同じモデルで思考の深さを下げる** ほうが簡単で、品質も保ちやすいことが多いです。

---

## 4. 悪用と事故を防ぐ

- **ユーザーごとの利用制限**（1 日 N 回、トークン上限）をかけます。
- エージェントには **1 タスクあたりのステップ数・トークン数の上限** を付けます（[[01_エージェントループの設計]]）。
- 1 日のコストにアラートを設定し、予算超過に早く気づけるようにします。
