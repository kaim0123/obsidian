# LLMアプリ開発の全体像

いま「AI をアプリに組み込む」と言うと、ほとんどの場合は **LLM を API で呼び出して、自分のアプリの機能にする** ことを指します。モデルを自分で作る機械学習の知識よりも、**ソフトウェア開発の知識の比重が大きい** のが特徴です。

---

## 1. 必要な知識の地図

| 層 | 内容 | 本ノート群での場所 |
|----|------|------------------|
| **土台の開発スキル** | Python / TypeScript、HTTP・JSON、非同期処理、バックエンドの基本 | 23〜25、31、34 |
| **LLM API を使う** | API 呼び出し、ストリーミング、プロンプト設計、構造化出力、モデル選び | 35/10・35/20 |
| **ツール呼び出し** | LLM にアプリの関数を呼ばせる | [[05_ツール呼び出し（Function Calling）]] |
| **RAG** | 社内文書など、モデルが知らない情報を検索して渡す | 35/30 |
| **エージェント** | 計画 → 実行 → 観察 をくり返す仕組み、MCP | 35/40 |
| **評価（Evals）** | 出力の良し悪しを数字で測る | 35/50 |
| **運用** | 可観測性、コスト、UX、セキュリティ | 35/60・[[08_プロンプトインジェクション]] |

---

## 2. 普通の API 連携と何が違うか

LLM も「外部 API を呼ぶ」という点では普通の外部連携と同じです（34_Backend/60_外部連携）。ただし、次の点が大きく違います。

| 普通の API | LLM API |
|-----------|---------|
| 同じ入力なら同じ出力 | **同じ入力でも出力が毎回変わる** |
| 仕様どおりに動けば正解 | **「だいたい正しい」「たまに間違える」** |
| 応答は数十 ms | 応答に **数秒〜数分** かかることがある |
| 料金はリクエスト数単位が多い | 料金は **トークン（文字量）単位** |
| 入力はただのデータ | 入力の文章が **指示として解釈される**（インジェクションの危険） |

このため、次の 3 つが LLM アプリ特有の仕事になります。

1. **出力の品質を数字で測る**（[[01_LLMアプリの評価（Evals）]]）
2. **遅さとコストを設計で抑える**（ストリーミング、キャッシュ、モデルの使い分け）
3. **間違える前提で UX と安全策を作る**（[[03_AI機能のUX設計]]、[[08_プロンプトインジェクション]]）

---

## 3. 機能の作り方は「簡単なほうから」

| 段階 | 形 | 例 |
|------|----|----|
| **1 回の呼び出し** | 入力 → LLM → 出力 | 要約、分類、抽出、翻訳 |
| **ワークフロー** | コードが手順を決め、途中で LLM を何度か呼ぶ | 「抽出 → 検証 → 整形」のパイプライン |
| **エージェント** | LLM が自分で次の行動（ツール）を選ぶ | 調査、複数ステップの作業代行 |

- **ほとんどの機能は 1 回の呼び出しかワークフローで足ります**。エージェントはコストも遅さも失敗の幅も大きいので、本当に必要なときだけ使います（[[01_エージェントループの設計]]）。

---

## 4. 優先度が低いもの

- **モデルの事前学習**：2026 年の求人では、ほぼ求められていない
- **ファインチューニング**：プロンプト・RAG・評価で足りないときの最後の手段。専門職の扱い
- **機械学習の数学**：あれば理解は深まるが、アプリに組み込むだけなら必須ではない

---

## 5. おすすめの学習順

1. どこかの LLM API で、簡単なチャットを作る（[[02_LLM APIの基本とストリーミング]]）
2. 構造化出力とツール呼び出しを試す（[[03_構造化出力]]、[[05_ツール呼び出し（Function Calling）]]）
3. 自分のメモ（この Obsidian Vault など）を対象に RAG を作る（[[01_RAGの仕組み]]）
4. 評価セットを作って、改善を数字で確かめる（[[01_LLMアプリの評価（Evals）]]）
5. エージェントや MCP に進む（[[01_エージェントループの設計]]、[[02_MCP（Model Context Protocol）]]）
