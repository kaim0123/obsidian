# LLMアプリの評価（Evals）

LLM の出力は毎回変わり、「だいたい正しい」ものです。普通のテストのように `expect(output).toBe(...)` では測れません。そこで **評価セットを用意して、変更のたびに全件流し、点数で比べる** 仕組みを作ります。これが Evals です。2026 年の AI エンジニアの求人では、**いちばん効果の大きいスキル** としてよく挙がります。

考え方の具体例（ネットショップの返信下書き機能で、プロンプトを 1 行変えたら返金の例が壊れた話）は、動画の要約 [[AIの出力を測る — 評価（eval）の考え方｜ねる前エンジニアリング]] が分かりやすいです。このノートは、その要点と実装の型をまとめたものです。

---

## 1. 評価セット（ゴールデンデータセット）

| 種類 | 例 | 意味 |
|------|----|------|
| **普段の例** | 配送の遅れ、サイズ交換 | 毎日来る。崩れると毎日困る |
| **端っこの例** | 怒っている人、英語、関係ない雑談 | めったに来ないが、変な返事をすると目立つ |
| **危ない例** | 返金の約束、他人の個人情報 | 1 回でも起きると被害が出る。**必須** の印を付ける |

- 各例には「一字一句の正解」ではなく **守ってほしいこと** を書きます（「返金を約束しない」「注文番号を聞く」）。
- **本番で見つかった失敗は、直す前に評価セットに足します**。バグを直す前にテストを書くのと同じです。
- 最初は 20〜50 件程度で十分です。実際のログや問い合わせから作ると、現実に近くなります。
- LLM に例を作らせた場合は、期待値が「今の AI の答えの写し」になっていないか確かめます。

---

## 2. 採点の方法

| 方法 | 向いているもの | 特徴 |
|------|-------------|------|
| **ルール（コード）** | 禁止語がないか、JSON の形、必須項目、文字数 | 速い・安い・毎回同じ結果。**まずこれで測れるところを測る** |
| **LLM-as-judge** | 丁寧か、質問に答えているか、資料に忠実か | 中身を見られるが、採点役も間違える |
| **人の評価** | 最終確認、採点役の検証 | 正確だが遅く高い。定期的に少数を見る |

LLM-as-judge の注意点：

- **長くて丁寧な答えを高く採点しがち** です。基準を「謝るだけでなく、届く日か次の手順が書いてあるか」のように具体的にします。
- 「良い答えか」ではなく **「何が書いてあれば合格か」** を基準にします。点数より合格 / 不合格の 2 択のほうが安定します。
- 採点役の判断と人の判断を時々比べ、ずれが大きければ基準を直します。

## 3. 実装の型

```ts
type EvalCase = {
  id: string;
  input: string;
  mustNot?: RegExp[];     // ルールで測る：出てはいけない表現
  criteria: string[];     // 採点役で測る：守ってほしいこと
  required?: boolean;     // 必須の例
};

async function runEval(cases: EvalCase[], generate: (input: string) => Promise<string>) {
  const results = [];
  for (const c of cases) {
    const output = await generate(c.input);
    const rulePass = !(c.mustNot ?? []).some((re) => re.test(output));
    const judgePass = rulePass && (await judge(output, c.criteria)); // ルールで落ちたら採点役は呼ばない
    results.push({ id: c.id, pass: rulePass && judgePass, required: c.required });
  }
  return results;
}
```

- 結果は **例ごと** に保存し、前回の結果と比べます。

---

## 4. 結果の読み方

| 落とし穴 | 対策 |
|---------|------|
| **同じ設定でも点がぶれる** | 何回か流して平均を見る。毎回ぶれる例と、毎回落ちる例を見分ける |
| **合計が同じでも中身が入れ替わる** | 合計だけでなく、例ごとに前回と比べる |
| **必須の例の失敗が合計に埋もれる** | 必須の例は合計とは別に見て、**1 つでも落ちたら止める** |

---

## 5. 変更のたびに自動で回す

| 変更 | 評価を回す |
|------|-----------|
| プロンプトの 1 行 | 回す |
| モデルの変更・バージョンアップ | 回す |
| RAG のチャンクや検索方法 | 回す（検索の指標も見る） |
| ツールの説明文 | 回す |

- CI に組み込み、**① 合格ライン（例：全体の 90% 以上）** と **② 必須の例は全部合格** の 2 段で判定します（62_CI-CD）。
- 評価は API を呼ぶのでお金がかかります。PR ごとには小さなセット、リリース前には全件、のように分けます。

---

## 6. 機能ごとに見る指標

| 機能 | 指標の例 |
|------|---------|
| 分類・抽出 | 正解率、項目ごとの一致率 |
| RAG | 検索：Recall@N・MRR ／ 回答：正答率・資料への忠実さ・出典の正しさ（[[03_ハイブリッド検索とリランキング]]） |
| エージェント | タスクの完了率、ステップ数、1 タスクあたりのコスト、危険な操作の有無 |
| 全体 | 応答時間、1 件あたりの料金 |

- 評価ツールには Braintrust、LangSmith などがありますが、最初は **評価セットのファイルとスクリプトだけの手作り** で十分です。道具より「例の束を先に決めて、前と比べる」考え方のほうが大事です。
- テストの一般的な考え方は 81_テスト戦略 を参照。
