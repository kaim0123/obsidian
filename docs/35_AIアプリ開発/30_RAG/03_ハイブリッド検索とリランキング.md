# ハイブリッド検索とリランキング

チュートリアルの RAG は「ベクトル検索で上位 5 件」で終わりですが、本番ではそれだけでは足りないことが多いです。実務でよく使われるのが **ハイブリッド検索** と **リランキング** です。

---

## 1. ベクトル検索の弱点

| 得意 | 苦手 |
|------|------|
| 言い換え（「ログインできない」↔「パスワードを忘れた」） | **型番・固有名詞・エラーコード**（「E-4012」「RX-500」） |
| あいまいな質問 | 完全一致させたい単語 |

型番を聞かれたのに、似た雰囲気の別の型番のページが出てくる、というのが典型的な失敗です。

---

## 2. ハイブリッド検索

**キーワード検索（スパース検索）** と **ベクトル検索（デンス検索）** を両方行い、結果を混ぜます。

| 検索 | しくみ | 代表 |
|------|--------|------|
| キーワード検索 | 単語の一致と出現頻度で点数を付ける | BM25、全文検索エンジン |
| ベクトル検索 | 意味の近さで点数を付ける | 埋め込み ＋ ベクトル DB |

2 つは点数の尺度が違うので、**順位だけを使って混ぜる RRF（Reciprocal Rank Fusion）** がよく使われます。

```ts
// RRF：各検索での順位 r に対して 1 / (k + r) を足し合わせる（k は 60 程度）
function rrf(results: string[][], k = 60): string[] {
  const score = new Map<string, number>();
  for (const list of results) {
    list.forEach((id, i) => score.set(id, (score.get(id) ?? 0) + 1 / (k + i + 1)));
  }
  return [...score.entries()].sort((a, b) => b[1] - a[1]).map(([id]) => id);
}

const merged = rrf([await keywordSearch(q), await vectorSearch(q)]);
```

## 3. リランキング

検索で **多めに（50 件など）取ってから、精度の高いモデルで並べ直して上位だけ使う** 方法です。

```
質問 → ハイブリッド検索で 50 件 → リランカーで並べ直し → 上位 5 件を LLM へ
```

| 段階 | 速さ | 精度 |
|------|------|------|
| 最初の検索 | 速い（全件から探す） | そこそこ |
| リランキング | 遅い（候補だけ見る） | 高い（質問と文書を一緒に読んで判断する） |

- リランカーには専用モデル（クロスエンコーダー）や、小さな LLM に「関連度を 0〜10 で採点して」と頼む方法があります。
- 遅延とコストが増えるので、**評価で効果を確かめてから** 入れます。

---

## 4. その他の改善手法

| 手法 | 内容 |
|------|------|
| **クエリの書き換え** | 会話の流れを踏まえて質問を独立した文に直す（「それの料金は？」→「RX-500 の料金は？」） |
| **メタデータで絞り込む** | カテゴリ・日付・権限で検索範囲を先に絞る |
| **チャンクに文脈を付ける** | 文書全体の要約や見出しをチャンクの頭に付けてから埋め込む |

---

## 5. 測ってから改善する

| 指標 | 意味 |
|------|------|
| **Recall@N** | 正解のチャンクが上位 N 件に入った割合。まずこれを上げる |
| **MRR** | 正解が何位に出たか（上位ほど高い） |
| **回答の正答率** | 最終的な回答が正しかった割合 |

- 「ハイブリッド検索にしたら Recall@5 が 62% → 81% になった」のように、**数字で説明できる** ことが大事です（[[01_LLMアプリの評価（Evals）]]）。
