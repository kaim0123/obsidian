# 安全なWebアプリケーションの作り方（第11章）

## クッキーに保存すべきでない情報

機密情報や重要な状態は **セッション変数（サーバー側）** に保存し、Cookie には **セッションID など最小限** のみを載せるのが原則です。判断のために、Cookie とセッション変数の違いを比較します。

---

## 🍪 クッキーとセッション変数の比較

| 比較項目 | クッキー（Cookie） | セッション変数（Session） |
|---------|-------------------|-------------------------|
| **使いやすさ** | ブラウザが自動送信するため、クライアント側の実装は簡単。JavaScript からも読み書き可能（HttpOnly 除く） | サーバー側の API だけで完結。クライアントはセッションID のみ保持すればよい |
| **配列やオブジェクトの格納** | 文字列のみ。配列・オブジェクトは JSON 等に **シリアライズ** して保存する必要がある | PHP の `$_SESSION` 等、**ネイティブに配列・オブジェクト** をそのまま格納できる |
| **サイズの制限** | 1 件あたり約 **4KB**、ドメインあたり約 **20 件** 程度（ブラウザ依存） | サーバーのメモリ・DB 次第で **実質制限なし**（ただし過大なデータは非推奨） |
| **利用者による格納情報の直接参照** | **可能**。開発者ツール・`document.cookie`（HttpOnly なし）で内容を確認できる | **不可**。データはサーバー側のみ。利用者が直接中身を見ることはできない |
| **脆弱性などで漏洩した際の情報漏洩のしやすさ** | **高い**。XSS・盗聴・Referer 等で Cookie 全体が漏れると、保存していた **値そのもの** も漏洩 | **低い**（セッションID のみ漏洩した場合）。漏れたのが ID なら、中身はサーバー側に残る（ハイジャックリスクは別問題） |
| **利用者によるデータ改変** | **容易**。ブラウザの開発者ツールや JS で **値を書き換え** 可能（HttpOnly でも改変は可能） | **困難**。利用者はサーバー上のセッションデータに **直接触れない** |
| **第三者によるデータ改変** | **可能**。通信傍受（HTTP）や XSS により、送受信する Cookie 値を改ざんされる恐れ | **困難**。第三者は通常、サーバー上のセッションデータを **直接改変できない**（セッションID 窃取は別） |
| **情報の寿命の制御** | `Expires` / `Max-Age` で **細かく設定可能**。ブラウザを閉じるまで（セッション Cookie）も選択可 | サーバー側で **タイムアウト・ガベージコレクション** を設定。`session.gc_maxlifetime` 等 |
| **異なるサーバーとの情報共有** | 同一 **ドメイン**（および Path 設定）内のサーバー間で **自動的に共有可能** | **サーバーごとに独立**。共有するには DB・Redis 等の **共通セッションストア** が必要 |

### 比較の要点

```
機密性・改ざん耐性が必要  → セッション変数（サーバー側）
クライアントとの利便性     → クッキー（非機密の設定値等）
セッション管理             → クッキーにはセッションID のみ、本体はサーバー側
```

---

## ⚠️ クッキーのセキュア属性不備

**セキュア属性不備** とは、Cookie に **Secure・HttpOnly・SameSite** 等の安全属性が付いていない、または不適切な状態です。セッションID など機密性の高い Cookie では **重大な脆弱性** になります。

### よくある不備

| 不備 | リスク |
|------|--------|
| **Secure なし** | HTTP 通信で Cookie が送信され、**盗聴** される |
| **HttpOnly なし** | XSS で `document.cookie` から **窃取** される |
| **SameSite なし** | クロスサイトリクエストで Cookie が送られ **CSRF** のリスク |
| **Expires が長すぎる** | 盗まれた Cookie が **長期間** 有効 |
| **Domain 過広** | サブドメイン全体に Cookie が **共有** され漏洩しやすい |

### 攻撃イメージ（Secure 属性なし）

```
1. ユーザーが http://example.com（HTTP）にアクセス
2. セッション Cookie が平文で送信される
3. 同一 Wi-Fi 上の攻撃者が通信を傍受
4. セッションID を入手 → なりすまし
```

### 本番環境の最低ライン

```
セッションID 用 Cookie:
  Secure   ✅ 必須（HTTPS のみ送信）
  HttpOnly ✅ 必須（JS から読めない）
  SameSite ✅ Strict または Lax
  適切な有効期限 ✅
```

## 🔒 セッションIDのクッキーに Secure 属性を付ける方法

**Secure 属性** を付けると、Cookie は **HTTPS 接続でのみ** ブラウザから送信されます。

### HTTP レスポンスヘッダ

```
Set-Cookie: sessionId=abc123; Secure; HttpOnly; SameSite=Strict; Path=/
```

### PHP

```php
// session_set_cookie_params（session_start 前に設定）
session_set_cookie_params([
    'lifetime' => 0,
    'path'     => '/',
    'secure'   => true,    // Secure 属性
    'httponly' => true,
    'samesite' => 'Strict',
]);
session_start();

// または setcookie
setcookie('sessionId', $sessionId, [
    'secure'   => true,
    'httponly' => true,
    'samesite' => 'Strict',
    'path'     => '/',
]);
```

### Express.js（Node.js）

```javascript
res.cookie('sessionId', sessionId, {
  secure: true,      // HTTPS のみ（本番では true）
  httpOnly: true,
  sameSite: 'strict',
  maxAge: 3600000,
  path: '/',
});
```

### 注意点

| 注意 | 説明 |
|------|------|
| **HTTPS 必須** | Secure を付けても、サイト全体が HTTPS でないとログインできない場合がある |
| **開発環境** | localhost では `secure: false` にすることがある（本番では必ず true） |
| **HTTP→HTTPS 混在** | HTTP ページでは Secure Cookie が送られない → 後述のトークン対策 |

## 🎫 トークンを用いた対策

**Secure 属性をセッション Cookie に付けられない** 場合（HTTP と HTTPS が混在するレガシー構成等）、**追加のトークン** で安全性を補います。

### なぜ必要か

```
問題:
  サイトの一部が HTTP のまま
  → セッション Cookie に Secure を付けると HTTP ページでセッションが使えない
  → Secure なしだと HTTP で Cookie が盗まれる

対策:
  セッション Cookie（Secure なし）に加え、
  HTTPS 専用の「トークン Cookie」（Secure あり）を別途発行
  → サーバーで両方の一致を検証
```

### 仕組み

```
1. ログイン成功
   サーバー: セッションに auth_token = ランダム値 を保存
   Cookie①: sessionId=abc123（Secure なし・HttpOnly）
   Cookie②: auth_token=xyz789（Secure あり・HttpOnly）← HTTPS のみ

2. HTTP ページへのアクセス
   → sessionId のみ送信（auth_token は Secure のため送られない）
   → サーバー: auth_token が無い → 機密操作は不可

3. HTTPS ページへのアクセス
   → sessionId + auth_token 両方送信
   → サーバー: セッション内の token と Cookie の token が一致 → OK
```

### 実装例（概念）

```php
// ログイン成功時
$token = bin2hex(random_bytes(32));
$_SESSION['auth_token'] = $token;

setcookie('sessionId', session_id(), ['httponly' => true, 'path' => '/']);
setcookie('auth_token', $token, [
    'secure'   => true,
    'httponly' => true,
    'samesite' => 'Strict',
    'path'     => '/',
]);

// 機密操作前の検証
function requireSecureAuth(): void {
    $sessionToken = $_SESSION['auth_token'] ?? '';
    $cookieToken  = $_COOKIE['auth_token'] ?? '';
    if ($sessionToken === '' || !hash_equals($sessionToken, $cookieToken)) {
        die('認証が必要です（HTTPS でアクセスしてください）');
    }
}
```

## ✅ トークンにより安全性が確保できる理由

トークン方式が有効な理由を整理します。

### 攻撃者の視点

| 入手できるもの | 条件 |
|--------------|------|
| **sessionId のみ** | HTTP 通信を傍受 |
| **sessionId + auth_token** | HTTPS 通信を傍受（より困難） |

### 安全性が確保できる理由

```
1. auth_token は Secure 属性付き
   → HTTP 通信には絶対に含まれない
   → HTTP 傍受だけでは token を入手できない

2. auth_token はサーバー側セッションにも保存
   → 一致検証しないと機密操作できない

3. 攻撃者が sessionId だけ盗んでも
   → 機密ページ・操作は auth_token 不一致で拒否される
```

### 限界と注意

| 限界 | 説明 |
|------|------|
| **完全な代替ではない** | サイト全体を HTTPS 化するのが理想 |
| **実装の複雑さ** | トークン発行・検証・更新のロジックが必要 |
| **XSS** | HttpOnly でもセッション固定等の別リスクは残る → XSS 対策も必要 |

**結論:** トークンは **混在環境での第二の防御線**。可能なら **全ページ HTTPS + Secure Cookie** が最善。

## 📋 セキュア属性以外の属性値に関する注意

Secure 以外の属性も、Cookie の **送信範囲・寿命・アクセス制御** に影響します。

---

### Domain 属性

**どのドメイン** に Cookie を送信するかを指定します。

```
Set-Cookie: sessionId=abc123; Domain=example.com
```

| 設定 | 送信先 |
|------|--------|
| `Domain=example.com` | `example.com` と `*.example.com` |
| **省略** | 設定したホストのみ（`www.example.com` だけ等） |

**注意:**

- Domain を **広げすぎない**（サブドメイン間で共有 → 漏洩リスク増）
- 不要なら **Domain 属性は省略**（ホスト限定がより安全）
- `user-content.example.com` に XSS があると、広い Domain 設定で Cookie が危険

---

### Path 属性

**どの URL パス以下** に Cookie を送信するかを指定します。

```
Set-Cookie: sessionId=abc123; Path=/app
```

| 設定 | 送信先 |
|------|--------|
| `Path=/app` | `/app` 以下のみ |
| `Path=/` | サイト全体（最も一般的） |

**注意:**

- Path を狭くすると、意図しないパスで Cookie が送られないようにできる
- セッション Cookie は通常 `Path=/`
- Path の **末尾スラッシュ** に注意（`/app` と `/app/` の挙動）

---

### Expires 属性（および Max-Age）

Cookie の **有効期限** を制御します。

```
Set-Cookie: sessionId=abc123; Expires=Wed, 01 Jan 2025 00:00:00 GMT
Set-Cookie: sessionId=abc123; Max-Age=3600
```

| 設定 | 動作 |
|------|------|
| `Expires` / `Max-Age` あり | 指定時刻・秒数まで有効 |
| **両方省略** | **セッション Cookie**（ブラウザ終了で削除） |

**注意:**

- ログインセッションは **適切な期限** を設ける（長すぎると窃取後の被害拡大）
- 「ログイン状態を保持」は Max-Age を長くするが、**リスクとトレードオフ**
- ログアウト時は **期限切れ Cookie** を明示的に上書き削除

```php
// ログアウト時に Cookie 削除
setcookie('sessionId', '', [
    'expires'  => time() - 3600,
    'path'     => '/',
    'secure'   => true,
    'httponly' => true,
]);
```

---

### HttpOnly 属性

**JavaScript から Cookie にアクセスできない** ようにします。

```
Set-Cookie: sessionId=abc123; HttpOnly
```

| HttpOnly | 効果 |
|----------|------|
| **あり** | `document.cookie` に表示されない → XSS 窃取を防ぐ |
| **なし** | JavaScript から読み書き可能 → **危険** |

**注意:**

- セッションID・auth_token には **必ず HttpOnly**
- HttpOnly でも **ブラウザ開発者ツールでは見える**（利用者自身による改変は可能）
- HttpOnly は **改変防止ではない**（送信値の書き換えは可能）→ 重要データはサーバー側に

```javascript
// HttpOnly なし
document.cookie; // "sessionId=abc123"  ← XSS で送信可能

// HttpOnly あり
document.cookie; // ""  ← sessionId は含まれない
```

---

## 📝 まとめ

| トピック | 要点 |
|---------|------|
| セキュア属性不備 | Secure / HttpOnly / SameSite 欠如は盗聴・XSS・CSRF リスク |
| Secure 属性 | HTTPS のみ Cookie 送信。セッションID には必須 |
| トークン対策 | HTTP/HTTPS 混在時、Secure 付き token Cookie で二重検証 |
| トークンの理由 | HTTP 傍受では token が取れず、機密操作を拒否できる |
| Domain | 広げすぎない。省略でホスト限定が安全 |
| Path | 送信範囲の制限。通常は `/` |
| Expires | 適切な有効期限。ログアウト時は明示削除 |
| HttpOnly | JS からの読取防止。セッションID には必須 |

### セッション Cookie 推奨設定

```
Set-Cookie: sessionId=<値>;
  Secure;
  HttpOnly;
  SameSite=Strict;
  Path=/;
  Max-Age=3600
```
