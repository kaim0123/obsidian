## 🎭 セッションハイジャック

**セッションハイジャック（Session Hijacking）** とは、他人の **セッションIDを入手** し、そのユーザーになりすます攻撃です。

### 日常生活での例え

- **セッションID**: レストランの **整理券**（番号が分かれば同じサービスを受けられる）
- **セッションハイジャック**: 他人の整理券を盗んで、本人になりすまして注文する

### 攻撃の流れ

```
1. 正規ユーザーがログイン（セッションID = abc123）
2. 攻撃者が abc123 を入手
3. 攻撃者が Cookie に sessionId=abc123 を設定
4. サーバーは「正規ユーザー」と判断
5. 攻撃者が本人になりすまして操作
```

### セッションIDが漏れる主な経路

| 経路 | 説明 |
|------|------|
| **推測** | 規則性のある ID を総当たり |
| **盗み出し** | XSS、盗聴、Referer 漏洩等 |
| **強制** | セッション固定化攻撃で被害者に特定 ID を使わせる |

---

## 🔓 セッションIDの推測、盗み出し、強制

セッションハイジャックは、セッションIDを入手する方法によって3つに分けて考えられます。

### 推測

**推測しやすいセッションID** を総当たり（ブルートフォース）で試す方法です。

```
攻撃者: sessionId=100001, 100002, 100003 ... と試行
→ 当たればなりすまし成功
```

### 盗み出し

正当な手段以外で **第三者が ID を取得** する方法です。

| 手法 | 説明 |
|------|------|
| **XSS** | `document.cookie` で Cookie を読み取る |
| **盗聴** | HTTP 通信を傍受（HTTPS 未使用時） |
| **Referer 漏洩** | URL 埋め込みの ID が Referer で外部に送られる |
| **物理アクセス** | 離席中の PC から Cookie をコピー |

### 強制

攻撃者が **被害者に特定のセッションIDを使わせる** 方法です（セッション固定化攻撃）。

```
攻撃者が sessionId=EVIL123 を用意
→ 被害者にその ID でアクセスさせる
→ 被害者がログイン
→ 攻撃者も EVIL123 でアクセス可能
```

## ⚠️ ありがちなセッションID生成方法

安全でないセッションID生成は、**推測攻撃** を可能にします。

### 危険な生成方法

| 方法 | 例 | 問題 |
|------|-----|------|
| **連番** | `100001`, `100002` | 次の ID が容易に推測できる |
| **タイムスタンプ** | `1704067200` | 現在時刻付近を試せば当たる |
| **ユーザー名のハッシュ** | `md5("yamada")` | 入力が限定されれば総当たり可能 |
| **短いランダム** | 6桁の数字 | 試行回数が現実的な範囲 |
| **固定値** | 全ユーザー共通 | 1つ分かれば全員に影響 |

```php
// ❌ 危険な例
$sessionId = md5(time());           // タイムスタンプベース
$sessionId = $_SERVER['REMOTE_ADDR']; // IP アドレス
$sessionId = $userId;               // ユーザーIDそのもの
$sessionId = rand(100000, 999999);  // 範囲が狭い
```

### 安全な生成方法

```php
// ✅ 推奨：暗号学的に安全な乱数
$sessionId = bin2hex(random_bytes(32));  // 256bit

// PHP セッション（php.ini / session_regenerate_id 等と併用）
session_start();
```

### セッションIDの要件

| 要件 | 推奨 |
|------|------|
| **エントロピー** | 128bit 以上（256bit 推奨） |
| **ランダム性** | `random_bytes()` 等の CSPRNG |
| **一意性** | 衝突しないよう DB で確認 |
| **予測不可能** | 時刻・連番・ユーザー情報に依存しない |

## 🎯 推測したセッションIDで成りすましを試行する

**セッションIDの総当たり攻撃** は、推測可能な ID に対して行われます。

### 攻撃の流れ

```
1. 攻撃者がセッションIDの形式を分析
   例: 6桁の数字、タイムスタンプ+連番 等

2. 有効な ID を総当たり
   for id in range(100000, 999999):
       request with Cookie: sessionId=id

3. ログイン済みセッションが見つかればなりすまし
```

### 防御

| 対策 | 効果 |
|------|------|
| **十分なランダム性** | 総当たりを非現実的にする |
| **ログイン試行制限** | ブルートフォースの速度を下げる |
| **セッション有効期限** | 盗んでも使える時間を短くする |
| **異常検知** | IP 変更時に再認証を要求 |

## 🔗 URL埋め込みのセッションID

**URL にセッションIDを含める** 方式（URL リライト、`<a href="?PHPSESSID=abc123">` 等）は **非推奨** です。

### 問題のある URL

```
https://example.com/page?PHPSESSID=abc123def456
https://example.com/page;jsessionid=abc123
```

### なぜ危険か

| 問題 | 説明 |
|------|------|
| **Referer 漏洩** | 外部リンククリック時に Referer で ID が送られる |
| **ブックマーク** | URL が保存され、共有・漏洩のリスク |
| **サーバーログ** | アクセスログにセッションIDが記録される |
| **ブラウザ履歴** | 履歴に ID が残る |
| **共有** | URL をコピーして送ると ID も一緒に渡る |

### 安全な方式

```
✅ Cookie にセッションIDを保存（HttpOnly, Secure）
❌ URL パラメータやパスにセッションIDを含めない
```

```php
// php.ini 設定例
session.use_only_cookies = 1
session.use_trans_sid = 0   // URL への自動付加を無効
```

## 📤 RefererによりセッションIDが漏洩する条件

[[01_HTTPセッション管理（徳丸本1章）|第1章]] で学んだ **Referer** ヘッダにより、セッションIDが外部サイトに漏れる条件があります。

### 漏洩が起きる条件

| 条件 | 説明 |
|------|------|
| **① URL にセッションIDが含まれる** | `?sessionId=abc123` 等 |
| **② ページ内に外部リンクがある** | `<a href="https://evil.com">` 等 |
| **③ ユーザーが外部リンクをクリック** | Referer に元 URL が送られる |
| **④ Referer が送信される** | Referrer-Policy で制限されていない |

### 攻撃の流れ

```
1. ユーザーが https://bank.com/page?sessionId=abc123 を閲覧
2. ページ内の https://evil.com へのリンクをクリック
3. ブラウザが Referer: https://bank.com/page?sessionId=abc123 を送信
4. evil.com がセッションIDを取得
5. 攻撃者が abc123 でなりすまし
```

### 対策

| 対策 | 説明 |
|------|------|
| **Cookie 方式** | URL にセッションIDを載せない（根本対策） |
| **Referrer-Policy** | Referer 送信を制限 |
| **HTTPS 統一** | 混在コンテンツを避ける |

```
Referrer-Policy: strict-origin-when-cross-origin
```

## 📌 セッションIDの固定化

**セッション固定化（Session Fixation）** は、攻撃者が **あらかじめ用意したセッションID** を被害者に使わせ、ログイン後も同じ ID でアクセスする攻撃です。

### 攻撃の流れ

```
1. 攻撃者が example.com にアクセス
   → サーバーが sessionId=EVIL123 を発行

2. 攻撃者が被害者に EVIL123 付き URL を送る
   https://example.com/?PHPSESSID=EVIL123

3. 被害者が URL を開き、ログイン
   → サーバーは EVIL123 にログイン情報を紐付け（ID を変更しない場合）

4. 攻撃者が sessionId=EVIL123 でアクセス
   → 被害者としてログイン状態 ✅
```

### 成立条件

- ログイン **前後でセッションIDが同じ**
- 攻撃者が **ログイン前の ID を知っている**

---

## 🔄 セッションアダプション

**セッションアダプション** とは、ログイン時にサーバーが **新しいセッションIDを発行せず**、ログイン前から存在するセッション（匿名セッション）を **そのまま引き継ぐ** 実装パターンです。

### 脆弱な実装

```php
// ❌ ログイン前から session_start() 済み
session_start();  // 匿名セッション ID = abc123

// ログイン成功後も ID を変更しない
$_SESSION['user_id'] = $userId;
// sessionId は abc123 のまま
```

### セッション固定化との関係

```
セッションアダプション（サーバーの脆弱な実装）
        ↓
ログイン前の ID がログイン後も有効
        ↓
セッション固定化攻撃が成立しやすい
```

| 概念 | 視点 |
|------|------|
| **セッション固定化** | 攻撃者の手法 |
| **セッションアダプション** | サーバー側の脆弱な挙動 |

### 安全な実装

```php
// ✅ ログイン成功時に ID を再生成
session_regenerate_id(true);  // 古い ID は無効化
$_SESSION['user_id'] = $userId;
```

セッション管理の不備に対する対策を、優先度順に整理します。

## 🔑 認証後にセッションIDを変更する

**ログイン成功時にセッションIDを再生成** するのが、セッション固定化対策の **最も重要な手法** です。

### なぜ必要か

```
ログイン前: sessionId = EVIL123（攻撃者も知っている可能性）
ログイン後: sessionId = NEW456（攻撃者は知らない）
→ 固定化攻撃が無効化 ✅
```

### 実装例

**PHP**

```php
session_start();

if (authenticate($username, $password)) {
    session_regenerate_id(true);  // true = 古い ID を削除
    $_SESSION['user_id'] = $userId;
    header('Location: /dashboard');
}
```

**Express.js**

```javascript
req.session.regenerate((err) => {
  if (err) return next(err);
  req.session.userId = user.id;
  res.redirect('/dashboard');
});
```

### 再生成すべきタイミング

| タイミング | 理由 |
|-----------|------|
| **ログイン成功時** | セッション固定化対策（必須） |
| **権限昇格時** | 一般 → 管理者等 |
| **パスワード変更後** | 既存セッションの無効化 |

## 🎫 できない場合はトークンにより対策

レガシーシステム等で **セッションIDを変更できない** 場合、**認証トークン** を別途管理して対策します。

### 仕組み

```
1. ログイン前: セッションID = abc123（変更不可）
2. ログイン成功: サーバーが「認証トークン」をセッションに保存
   $_SESSION['auth_token'] = random_token()
3. 重要操作時: セッションID だけでなく auth_token も検証
4. ログイン前の abc123 には auth_token がない
   → 攻撃者は ID だけでは操作不可
```

### 実装イメージ

```php
// ログイン成功時
$_SESSION['authenticated'] = true;
$_SESSION['auth_token'] = bin2hex(random_bytes(32));
$_SESSION['login_time'] = time();

// 重要ページで検証
function requireAuth() {
    if (empty($_SESSION['authenticated']) || empty($_SESSION['auth_token'])) {
        redirect('/login');
    }
}
```

### 注意点

| 注意 | 説明 |
|------|------|
| **第二の防御線** | セッションID再生成が理想 |
| **トークンも保護** | HttpOnly Cookie、XSS 対策が必要 |
| **複雑性** | 実装・保守コストが増える |

## 🚪 ログイン前のセッションID固定化攻撃の対策

ログイン **前** の段階から、セッション固定化を防ぐ対策です。

### 対策一覧

| 対策 | 説明 |
|------|------|
| **ログイン後に ID 再生成** | 最も重要（前述） |
| **URL にセッションIDを載せない** | 攻撃者が ID を仕込みにくくする |
| **ログイン前セッションの制限** | 匿名セッションでは機密操作不可 |
| **saveUninitialized = false** | 不要な匿名セッションを作らない |

### saveUninitialized（Express.js）

```javascript
app.use(session({
  secret: 'secret-key',
  saveUninitialized: false,  // セッションにデータがなければ Cookie を発行しない
  resave: false,
  cookie: { httpOnly: true, secure: true, sameSite: 'strict' }
}));
```

**効果:** 訪問者ごとに不用意にセッションIDが発行されない。

### ログインフローの安全な設計

```
1. ログインページ表示（匿名。機密操作不可）
2. 認証成功
3. session_regenerate_id() で新 ID 発行  ← 必須
4. ログイン状態を新セッションに保存
5. 以降の操作は新 ID のみ有効
```

### Cookie 属性の設定（再掲）

```
Set-Cookie: sessionId=...; HttpOnly; Secure; SameSite=Strict
```

| 属性 | 効果 |
|------|------|
| **HttpOnly** | XSS による Cookie 窃取を防ぐ |
| **Secure** | HTTPS のみ送信 |
| **SameSite** | CSRF・クロスサイト送信を制限 |

## 📝 まとめ

| トピック | 要点 |
|---------|------|
| セッションハイジャック | セッションIDを奪い、なりすまし |
| 推測・盗み出し・強制 | ID 入手方法の3分類 |
| 危険な ID 生成 | 連番・タイムスタンプ・短い乱数は禁止 |
| URL 埋め込み | Referer・ログ・履歴から漏洩。Cookie 方式を使う |
| Referer 漏洩 | URL に ID がある + 外部リンククリック |
| セッション固定化 | 攻撃者が用意した ID をログイン後も使う |
| セッションアダプション | ログイン時に ID を変更しない脆弱な実装 |
| 認証後の ID 変更 | `session_regenerate_id()` 等（最重要） |
| トークン対策 | ID 変更不可時の第二の防御線 |
| ログイン前対策 | URL 非埋め込み、saveUninitialized 等 |

### セッション管理チェックリスト

```
□ セッションIDは random_bytes 等で128bit以上のランダム生成
□ セッションIDを URL に含めない（Cookie のみ）
□ Cookie に HttpOnly, Secure, SameSite を設定
□ ログイン成功時に session_regenerate_id() で ID 再生成
□ セッションに有効期限を設定
□ ログアウト時にサーバー側セッションを削除
□ HTTPS を必須にする
□ XSS 対策（HttpOnly だけでは不十分な操作がある）
```
