# リフレッシュトークンの設計

アクセストークンは短い期限にしたい、でも利用者に何度もログインさせたくない。その間を埋めるのがリフレッシュトークンです。**長く使える強い鍵** なので、盗まれたときにどうするかまで設計します。基本の説明は [[01_セッション・トークン基礎]] と [[05_アクセストークンとリフレッシュトークンの違い（つるチャンネル）]]。

---

## 🔑 2 つのトークンの役割

| | アクセストークン | リフレッシュトークン |
|------|------|------|
| **使う相手** | API（リソースサーバー） | 認証サーバーだけ |
| **期限** | 短い（5〜15 分程度） | 長い（数日〜数十日） |
| **送る頻度** | API を呼ぶたび | アクセストークンが切れたときだけ |
| **形式** | JWT が多い（[[04_JWTの構造と検証]]） | 中身のないランダムな文字列が多い |
| **盗まれたら** | 期限が切れるまで使われる | **新しいアクセストークンを作り続けられる** |

```
ログイン ──▶ アクセストークン（15分）＋ リフレッシュトークン（30日）

API 呼び出し ── アクセストークン ──▶ API
               （15分後に期限切れ）
更新        ── リフレッシュトークン ──▶ 認証サーバー ──▶ 新しいアクセストークン
```

**ポイント:** アクセストークンは何度もネットワークに出るので、漏れやすい。だから短くする。リフレッシュトークンは認証サーバーにしか送らないので、守りやすい場所に置ける、という分担です。

---

## 🔄 ローテーション（使うたびに作り直す）

OAuth のセキュリティ指針 **RFC 9700**（2025 年 1 月）は、ブラウザやスマホアプリのような **公開クライアント** のリフレッシュトークンに、次のどちらかを **必須** としています。

1. **送信者制約**（そのクライアントしか使えないようにする。DPoP や mTLS）
2. **ローテーション**（更新のたびに新しいリフレッシュトークンを出し、古いものを無効にする）

### ローテーションの仕組み

```
RT1 で更新 ──▶ 新しい AT ＋ RT2（RT1 は無効）
RT2 で更新 ──▶ 新しい AT ＋ RT3（RT2 は無効）
```

### 盗まれたことを見つける（再利用の検知）

攻撃者が RT2 を盗んだとします。本物の利用者と攻撃者のどちらかが先に RT2 を使い、もう一方が **無効になった RT2** を後から使うことになります。

```
利用者:  RT2 で更新 ──▶ RT3 を受け取る
攻撃者:  RT2 で更新 ──▶ ❌ 使用済みの RT2 が来た！
                        → 認証サーバーは、どちらが本物か分からない
                        → RT2 から続く一連のトークン（RT3 も）を全部無効にする
                        → 利用者は再ログイン、攻撃者は締め出される
```

- 同じログインから続くトークンを **1 つの家系（ファミリー）** として記録しておき、使用済みのトークンが来たら家系ごと無効にします。
- 再利用を見つけたら、セキュリティのログに記録し、必要なら利用者に通知します。

### 同時に更新が走る問題

タブを複数開いていると、同じ RT で同時に更新が走り、正規の利用者なのに「再利用」と判定されることがあります。

| 対策 | 内容 |
|------|------|
| **更新を 1 か所にまとめる** | クライアント側で更新処理を 1 つにし、他のリクエストはその結果を待つ |
| **短い猶予期間** | 古い RT を数秒だけ有効にしておく。ただし猶予の間は検知が甘くなる |

---

## ⏳ 期限の決め方

| 期限 | 内容 | 目安 |
|------|------|------|
| **使わないと切れる期限**（アイドル） | 最後に更新してから一定期間使われなければ無効 | 数日〜2 週間 |
| **絶対的な期限** | 最初のログインから一定期間で、必ず再ログイン | 30〜90 日 |
| **アクセストークン** | 短く | 5〜15 分 |

- RFC 9700 も「しばらく使われていないリフレッシュトークンは期限切れにすべき（SHOULD）」としています。
- ローテーションしても **絶対的な期限は延ばさない** こと。延ばすと、一度盗まれたトークンが永遠に使えてしまいます。
- 金融や管理画面など重要なサービスほど短くします。

---

## 🗑 無効にするタイミング

| きっかけ | 処理 |
|------|------|
| **ログアウト** | その端末のリフレッシュトークンを無効にする（認証サーバーの revocation エンドポイント、RFC 7009） |
| **パスワード変更・リセット** | **全端末** のリフレッシュトークンを無効にする |
| **MFA の変更・アカウントの停止** | 全端末を無効にする |
| **再利用の検知** | その家系を無効にする |
| **利用者が「他の端末からログアウト」を押した** | 選んだ端末、または全端末を無効にする |

「ログイン中の端末一覧」を画面に出し、利用者が自分で切れるようにすると、乗っ取りに気づきやすくなります。

## 🗄 サーバー側の保存

```
refresh_tokens
  id            -- 主キー
  token_hash    -- トークンそのものではなく SHA-256 のハッシュを保存
  user_id
  family_id     -- 同じログインから続くトークンの家系
  client_id
  expires_at    -- 絶対的な期限
  last_used_at  -- アイドル期限の判定
  used_at       -- 使用済みなら日時（再利用の検知に使う）
  revoked_at
  device_info   -- 端末一覧の表示用（ブラウザ・OS・おおよその場所）
```

- リフレッシュトークンは **ハッシュで保存** します。DB が漏れても、そのまま使えないようにするためです。ランダムな長い値なので、パスワードのような遅いハッシュは不要で、SHA-256 で十分です。
- 推測されないよう、**暗号学的に安全な乱数で 32 バイト以上** 作ります。

---

## 🔒 送信者制約（盗んでも使えなくする）

ローテーションは「盗まれた後に気づく」仕組みです。もう一歩進めると、**盗んでも使えない** ようにできます。

| 仕組み | 内容 |
|------|------|
| **DPoP**（RFC 9449） | クライアントが鍵ペアを作り、リクエストごとに秘密鍵で署名する。トークンはその鍵と結び付けられるので、トークンだけ盗んでも使えない |
| **mTLS**（RFC 8705） | クライアント証明書と結び付ける。サーバー間の通信向け |
| **DBSC**（Device Bound Session Credentials） | ブラウザが端末の TPM などで鍵を守り、セッションの Cookie をその端末に結び付ける。Chrome 146（2026 年 4 月）から Windows で正式に提供。サイト側の対応が必要 |

ブラウザで DPoP を使う場合、秘密鍵は WebCrypto の **取り出せない鍵**（non-extractable）にして IndexedDB に置きます。XSS で鍵そのものは盗まれませんが、XSS が動いている間はその鍵で署名させられる点は残ります。

---

## 📱 クライアント別の考え方

| クライアント | リフレッシュトークンの置き場所 |
|------|------|
| **サーバー側の Web アプリ・BFF** | サーバー側に保存。ブラウザにはセッション Cookie だけ渡す（最も安全） |
| **SPA（ブラウザだけ）** | できれば BFF にしてブラウザに置かない。置くならメモリか Web Worker の中。localStorage は避ける（[[07_トークンの保存場所（Cookie_vs_localStorage）]]） |
| **スマホアプリ** | iOS のキーチェーン、Android の Keystore で守られた領域 |
| **サーバー間**（M2M） | リフレッシュトークンは使わず、Client Credentials で毎回取り直すのが一般的 |

---

## 📋 チェックリスト

- [ ] アクセストークンの期限は短い（15 分程度まで）
- [ ] 公開クライアントでは、ローテーションか送信者制約を入れている
- [ ] 使用済みの RT が来たら、家系ごと無効にしている
- [ ] アイドル期限と絶対的な期限の両方がある
- [ ] ログアウト・パスワード変更で RT を無効にしている
- [ ] RT はハッシュで保存している
- [ ] ブラウザでは RT を localStorage に置いていない
