JWT を書き換えたのに、なぜサーバーでバレるのか。JWT（JSON Web Token）とは何か、図解で解説します。セッション方式では、ログイン状態をサーバー側のテーブルに保存し、ブラウザには番号（session\_id）だけを渡します。サーバーが複数台になると、このテーブルをどのサーバーからでも参照できる必要が...

## 詳しい要約

**テーマ：JWT はなぜサーバーが状態を持たずにログインを判定できるのか**

JWT（JSON Web Token）はログイン情報そのものをトークンに入れて渡し、サーバーは**署名**を検証するだけでユーザーを確認できる。中身は誰でも読めるが、鍵がないと正しい署名を作れないため、書き換えるとバレる。

---

### 出発点：セッション方式

- ログイン時にサーバー側のテーブルに「`abc123` はユーザー 42、ログイン済み」と書き込み、ブラウザには番号（session_id）だけを渡す
- サーバーが 1 台なら単純だが、3 台に増えるとどのサーバーからも同じテーブルを参照する必要がある → **Redis** などの共有ストアで解決できる
- セッション方式が悪いわけではないが、**状態をサーバー側で管理し続ける**点は変わらない

### JWT の仕組み

- テーブルに書く代わりに、ユーザー ID・ロール・有効期限などをトークンに入れて渡す
- ブラウザは保存して、次回から **Authorization ヘッダー**に付けて送る
- サーバーはテーブルを引かず、トークンを**検証**してユーザー 42 だと確認する

### 書き換えたら管理者になれる？

- JWT は `.` で区切られた 3 部構成：**ヘッダー / ペイロード / 署名**
- ペイロードにはユーザー ID や有効期限などの**クレーム**が入る
- 署名はヘッダーとペイロードから**サーバーだけが知る鍵**で作られるため、1 文字でも変えると署名と合わなくなる
- 書き換え自体はできるが、鍵がないので正しい署名を作れず**拒否**される

### 注意点

- 一般的な JWT は**暗号化されていない**。ペイロードは Base64URL でエンコードされているだけで誰でもデコードして読める
- 署名は「読めなくする」ためではなく「**改ざんを見つける**」ためのもの → パスワードなどの秘密をペイロードに入れてはいけない

### まとめ

- サーバーが覚えていなくても分かるのは署名があるから
- 中身は読めるが、こっそり書き換えることはできない
