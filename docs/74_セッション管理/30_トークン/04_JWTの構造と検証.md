# JWT の構造と検証

JWT（JSON Web Token）は、**中身を誰でも読めるが、改ざんすると分かる** トークンです。安全かどうかは **受け取った側がどう検証するか** で決まります。セッションとトークンの違いは [[02_セッションとトークンとは]]、直感的な説明は [[03_JWTとは_サーバーが覚えていなくても分かる理由（つるチャンネル）]]。

---

## 🧱 構造

```
eyJhbGciOiJSUzI1NiIsInR5cCI6ImF0K2p3dCIsImtpZCI6IjIwMjYtMTAifQ . eyJpc3MiOi... . SflKxwRJSMeKKF2QT4f...
└──────────────── ヘッダ ────────────────┘   └ ペイロード ┘   └── 署名 ──┘
```

3 つの部分を Base64URL で表し、`.` でつないでいます。

| 部分 | 中身 | 例 |
|------|------|------|
| **ヘッダ** | 署名の方式と鍵の情報 | `{"alg":"RS256","typ":"at+jwt","kid":"2026-10"}` |
| **ペイロード** | クレーム（主張）の集まり | `{"iss":"https://auth.example.com","sub":"user_123","aud":"api","exp":1792300000}` |
| **署名** | ヘッダとペイロードに対する署名 | 秘密鍵がないと作れない |

**ポイント:** Base64URL は **暗号化ではありません**。ペイロードは誰でも読めます。パスワード・個人情報・社内の情報を入れてはいけません（中身を隠したいなら JWE を使います）。

### 主なクレーム

| クレーム | 意味 | 検証で確かめること |
|------|------|------|
| `iss`（issuer） | 発行者 | 信頼している発行者か |
| `sub`（subject） | 誰についてのトークンか | 利用者 ID として使う |
| `aud`（audience） | 誰に向けたトークンか | **自分宛てか**。別の API 向けのトークンを受け付けない |
| `exp`（expiration） | 有効期限 | 過ぎていないか |
| `nbf`（not before） | この時刻より前は無効 | まだ早すぎないか |
| `iat`（issued at） | 発行時刻 | 古すぎないか |
| `jti`（JWT ID） | トークンごとの ID | 使い捨てにしたい場合や、失効リストに使う |

---

## ✍️ 署名の方式

| 方式 | 例 | 鍵 | 向いている場面 |
|------|------|------|------|
| **HMAC**（共通鍵） | HS256 | 発行と検証で **同じ秘密** | 発行と検証が同じサーバーのとき |
| **RSA**（公開鍵） | RS256、PS256 | 秘密鍵で署名、公開鍵で検証 | 認証サーバーと API が別のとき |
| **楕円曲線**（公開鍵） | ES256、EdDSA | 同上。鍵と署名が短い | 同上 |

- 認証サーバーと API が分かれているなら **公開鍵方式** にします。HMAC だと、検証するすべてのサーバーが「トークンを作れる秘密」を持つことになります。
- HMAC の秘密は **ランダムな 32 バイト以上**。人が覚えられるパスワードを使うと、手元で総当たりされます。

---

## 🧨 よくある攻撃

JWT の事故のほとんどは、**トークンのヘッダに書かれた内容を信じてしまう** ことが原因です。

| 攻撃 | 手口 | 対策 |
|------|------|------|
| **`alg: none`** | ヘッダを `"alg":"none"` にして署名を消す。署名なしのトークンを受け付けるライブラリがあった | 受け付ける方式を **サーバー側で固定** する。`noNE` のような大文字小文字違いにも注意 |
| **方式の取り違え**（アルゴリズム混同） | RS256 の **公開鍵** を HMAC の秘密として使わせ、`HS256` のトークンを偽造する。公開鍵は誰でも手に入る | 1 つの鍵は 1 つの方式でしか使わない。HMAC と公開鍵方式を同じ検証処理で混ぜない |
| **`kid` の悪用** | 鍵を選ぶ `kid` に `../../dev/null` や SQL を入れ、空の鍵や攻撃者の鍵を選ばせる | `kid` は決まった一覧から選ぶだけにする。ファイルパスや SQL に使わない |
| **`jku`・`x5u` の悪用** | 「この URL の鍵で検証して」と指定し、攻撃者の鍵を読ませる。SSRF にもなる（[[03_SSRF]]） | 鍵の取得先は **サーバーの設定で固定** する。トークンの指定は無視する |
| **トークンの使い回し** | 別のサービス向けのトークンや ID トークンを、API のアクセストークンとして送る | `aud`・`iss`・`typ` を確かめる |
| **弱い HMAC の秘密** | 漏れたトークンから、手元で秘密を総当たりする | 長いランダムな秘密を使い、定期的に入れ替える |

### 実際の脆弱性の例

- **jsonwebtoken**（Node.js）：v8 以前は、検証時に方式を指定しないと `none` などを受け付ける余地があった（CVE-2022-23540 など。v9 で修正）。
- **Java の ECDSA**（CVE-2022-21449、通称 Psychic Signatures）：値が 0 の署名を正しいと判定してしまい、ES256 の JWT を偽造できた。
- **2026 年にも**、JWK に `alg` が書かれていないときに、トークンのヘッダの `alg` を使って検証してしまう脆弱性が報告されています（Hono の CVE-2026-22817、libjwt の CVE-2026-44699 など）。原因はどれも **方式をトークンから決めている** ことです。

## ✅ 検証の手順

```
1. 形式を確かめる（3 つの部分、Base64URL の文字だけ）
2. ヘッダの alg が「サーバーが許可した方式」と一致するか確かめる
3. kid で、サーバーが持っている鍵の一覧から鍵を選ぶ
4. 署名を検証する
5. iss・aud・exp・nbf を確かめる（時計のずれは 1 分程度まで許す）
6. typ を確かめる（アクセストークンなら at+jwt）
7. 必要なら jti で失効済みでないか確かめる
8. ここまで通って初めて、sub や権限のクレームを使う
```

**署名の検証より前にペイロードを使わない** ことが大事です。`jwt.decode()`（検証しない読み取り）の結果で処理を分けると、偽造されたトークンで通ってしまいます。

### 実装例（Node.js・jose）

```javascript
import { jwtVerify, createRemoteJWKSet } from 'jose';

// 鍵の取得先はサーバー側で固定する（トークンの jku は使わない）
const JWKS = createRemoteJWKSet(new URL('https://auth.example.com/.well-known/jwks.json'));

export async function verifyAccessToken(token) {
  const { payload } = await jwtVerify(token, JWKS, {
    algorithms: ['RS256'],              // 許可する方式を固定
    issuer: 'https://auth.example.com', // 発行者
    audience: 'https://api.example.com',// 自分宛てか
    typ: 'at+jwt',                      // アクセストークンか
    clockTolerance: 60,                 // 時計のずれ（秒）
  });
  return payload; // 検証済みのクレームだけを使う
}
```

- `createRemoteJWKSet` は鍵を取ってきて覚えておき、知らない `kid` が来たときだけ取り直します。鍵の入れ替え（ローテーション）に自動で追いつけます。
- 自分で署名の検証を書かないこと。実績のあるライブラリを使い、**最新に保つ** ことも対策の一部です。

## 🔁 鍵の入れ替え

| 手順 | 内容 |
|------|------|
| 1 | 新しい鍵ペアを作り、公開鍵を JWKS（公開鍵の一覧）に **追加** する |
| 2 | 検証側のキャッシュが更新されるのを待つ |
| 3 | 新しい鍵で署名を始める（`kid` で区別される） |
| 4 | 古い鍵で署名したトークンの期限が全部切れたら、古い公開鍵を JWKS から消す |

秘密鍵が漏れたときは、すぐに古い鍵を消し、それで署名したトークンをすべて無効にします。

---

## ⚖️ JWT の弱点：取り消しにくい

JWT は「サーバーが覚えていなくても検証できる」ことが長所ですが、**一度出したトークンを期限前に無効にしにくい** という短所の裏返しでもあります。

| 方法 | 内容 |
|------|------|
| **期限を短くする** | アクセストークンは 5〜15 分程度にし、リフレッシュトークンで更新する（[[06_リフレッシュトークンの設計]]） |
| **失効リスト** | ログアウトや乗っ取りが分かったときの `jti` を、期限まで Redis などに置いて拒否する |
| **トークンの中身を問い合わせる** | API が毎回、認証サーバーに有効か問い合わせる（Token Introspection）。即時に止められるが、JWT の長所は薄れる |

ログイン状態を保つだけなら、**サーバー側のセッション + Cookie のほうが簡単で安全** なことも多いです。JWT は、複数のサービスやサーバー間で認可の情報を渡す場面で特に役立ちます。

---

## 📋 チェックリスト

- [ ] 許可する `alg` をサーバー側で固定している（`none` を受け付けない）
- [ ] HMAC と公開鍵方式を同じ鍵・同じ検証処理で混ぜていない
- [ ] `iss`・`aud`・`exp` を検証している
- [ ] `kid`・`jku`・`x5u` をそのまま使っていない
- [ ] ペイロードに秘密の情報を入れていない
- [ ] アクセストークンの期限が短く、取り消しの手段がある
- [ ] JWT のライブラリを最新に保っている
