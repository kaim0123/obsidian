# ADR — Architecture Decision Record

## この教材の目的

設計会議で「REST にしよう」「DB は PostgreSQL にしよう」と決まっても、**半年後には誰も理由を覚えていない**ことがよくあります。

**ADR（Architecture Decision Record）** は、そうした**アーキテクチャ上の重要な決定**を、短い文書として残すための形式です。

この教材では、

- ADR が何で、何のために書くか
- 典型的なテンプレート（状況・決定・結果）
- いつ書き、どこに置くか
- 初心者向けの記入例

を整理します。

前提: [[01_意思決定と進化]]、[[02_アーキテクチャと設計の違い]]、[[02トレードオフ]]

---

## 1. ADR とは

**ADR** とは、**アーキテクチャに関する1つの決定**について、次を記録した短い文書です。

| 要素 | 英語でよく使う語 | 書く内容 |
|------|------------------|----------|
| **状況** | Context | 何が問題で、どんな制約があるか |
| **決定** | Decision | 何を選んだか（はっきりと） |
| **結果** | Consequences | 得られるメリット・受け入れるデメリット |

```
  状況: チームは3人、リリースは2週間後
     │
     ▼
  検討: モノリス / マイクロサービス / モジュラモノリス
     │
     ▼
  決定: まずモノリス + モジュール境界を明確に
     │
     ▼
  結果: デプロイは単純。将来分離するときの境界は意識済み
```

ADR は**設計書全体**ではありません。  
「**この論点について、こう決めた**」という**1枚（または数段落）**の記録です。

---

## 2. なぜ ADR を書くのか

| メリット | 説明 |
|----------|------|
| **同じ議論の繰り返しを減らす** | 過去の前提が読める |
| **新人・異動者のオンボーディング** | 「なぜこうなっているか」が追える |
| **決定の見直しがしやすい** | 状況が変わったとき、「当時の前提はまだ有効か」と比較できる |
| **トレードオフが可視化される** | 「安易に変えない理由」が残る |

アーキテクチャの仕事は、コードを書くことだけではなく、**チームの記憶を外部化すること**でもあります。  
ADR はそのための**軽量な道具**です。

---

## 3. 典型的なテンプレート

形式はチームごとに多少違いますが、初心者向けには次の構成が扱いやすいです。

```markdown
# ADR-001: 注文と在庫を同一モノリスに置く

## 状況
- 初期メンバー3名、MVP を3ヶ月でリリースしたい
- 注文と在庫は密に連携する（在庫引当は注文確定と同一トランザクション）
- 運用チームはまだ専任なし

## 検討した選択肢
1. モノリス（モジュール分割あり）
2. 注文・在庫を別サービス + 同期 API
3. イベント駆動で非同期連携

## 決定
選択肢1を採用する。パッケージ（またはモジュール）で注文・在庫の境界は分ける。

## 結果
### 良いこと
- ローカル開発・デプロイが単純
- トランザクション境界が明確

### 受け入れること
- 将来サービス分割するとき、データ移行と API 切り出しが必要
- スケールはアプリ全体単位になる

## ステータス
Accepted（2025-06-01）

## 関連
- 見直し条件: DAU 10万超、または在庫チームが独立したとき
```

### 3.1 よく使うステータス

| ステータス | 意味 |
|------------|------|
| **Proposed** | 提案中・議論中 |
| **Accepted** | 採用された |
| **Deprecated** | 原則として使わない（新規は別方針） |
| **Superseded** | 別の ADR に置き換えられた |

決定を変えたときは、古い ADR を消すのではなく、**新しい ADR で Superseded と書き、リンクする**のが一般的です。  
「なぜ変えたか」の歴史が残ります。

---

## 4. 何を ADR にするか

すべての細かい判断を書く必要はありません。目安は次のとおりです。

**ADR に向くこと**

- 変更コストが高い（DB 選定、認証方式、モノリス/分散の方針）
- チーム全体に影響する（API スタイル、エラーハンドリング方針）
- 反対意見や代替案があった（トレードオフがはっきりしている）

**ADR にしなくてよいこと**

- 1ファイル内の実装詳細（通常はコードレビュー・コメントで足りる）
- フレームワークの公式推奨どおりの使い方だけの話
- すぐ戻せる一時的な実験（ただし本番に残るなら ADR または暫定案メモを検討）

迷ったら「**6ヶ月後にこの決定を説明できるか？**」と自問するとよいです。

---

## 5. どこに置くか

| 置き場所 | 向き |
|----------|------|
| リポジトリ内 `docs/adr/` | コードと一緒にバージョン管理できる（よく使われる） |
| Wiki / Notion | 非エンジニアも読みやすい |
| 設計リポジトリ専用 | 複数サービスにまたがる決定を集約 |

ファイル名の例: `0001-use-monolith-for-order-inventory.md`  
番号を振ると時系列が追いやすくなります。

---

## 6. 初心者がつまずきやすい点

### 6.1 長く書きすぎる

ADR は**短く**が原則です。1〜2ページ以内を目安に、**決定とトレードオフ**に集中します。  
詳細設計は別ドキュメントへ。

### 6.2 決定だけ書いて状況がない

「PostgreSQL を使う」だけでは、将来「なぜ MySQL ではなかったのか」が分かりません。  
**当時の制約**（チームのスキル、既存契約、性能要件）を1段落でよいので残します。

### 6.3 書いたあと放置

ADR は**生きた文書**です。前提が変わったら、新しい ADR で更新・置き換えます。  
[[03技術的負債と意図的な暫定案]] と組み合わせ、「暫定で受け入れた決定」の見直し日を ADR に書いておくことも有効です。

---

## 7. まとめ

| 覚えること | 内容 |
|------------|------|
| ADR とは | アーキテクチャの**1つの決定**を、状況・決定・結果で残す短い記録 |
| 目的 | 記憶の共有、議論の短縮、見直しのしやすさ |
| 書き方 | 短く、代替案とトレードオフを含める |
| 更新 | 変えたら新 ADR で Superseded、消さない |
