# レビュー観点 — 図、境界、非機能、運用

## この教材の目的

アーキテクチャのレビューでは、**図がきれいか**だけを見がちです。  
しかし本番で困るのは、境界の曖昧さ、非機能要件の抜け、運用の想定不足であることが多いです。

この教材では、設計レビュー・PR レビュー・振り返りで使える**4つの観点**を、初心者向けのチェックリストとして整理します。

- **図** — 誰に何を伝えるか、レベルは適切か
- **境界** — モジュール・サービス・データのオーナーは明確か
- **非機能** — 品質属性（性能・可用性・セキュリティなど）は触れているか
- **運用** — デプロイ、障害、観測は設計に含まれているか

前提: [[01_意思決定と進化]]、[[01品質属性]]、[[03観測性とログとメトリクスとトレースとアーキテクチャ上の接点]]

---

## 1. レビューとは何をするか

**アーキテクチャレビュー**の目的は、実装の細部を全部見ることではありません。

| 目的 | 説明 |
|------|------|
| **リスクの早期発見** | 後から直すと高い問題を、安い段階で見つける |
| **前提の共有** | チームが同じ地図を見ているか確認する |
| **トレードオフの合意** | 何を優先し、何を犠牲にするかを言語化する |

タイミングの例:

- 新機能の設計提案時
- モノリス分割・大規模リファクタの前
- 本番障害の振り返り後（設計に戻す）
- ADR の Proposed 段階

## 2. 観点1 — 図

### 2.1 図のレベルは読み手に合っているか

図には**抽象度のレベル**があります。C4 モデルはその代表例です（第8部の付録でも触れる予定）。

| レベル | 見せるもの | 読み手の例 |
|--------|------------|------------|
| **コンテキスト** | システムと外部（ユーザー、他システム） | ステークホルダー、新メンバー |
| **コンテナ** | アプリ、DB、キューなどの実行単位 | 開発チーム全体 |
| **コンポーネント** | 1アプリ内の主要モジュール | 実装担当者 |
| **コード** | クラス図など（レビューではあまり使わない） | 詳細設計時 |

```
【コンテキスト図のイメージ】
  ユーザー ──→ [自社ECシステム] ──→ 決済サービス（外部）
                    │
                    └──→ 配送業者API（外部）
```

**よくある問題**: いきなりクラス図だけ出して、**システム全体の位置づけ**が伝わらない。

### 2.2 図のチェックリスト

- [ ] **矢印の意味**が凡例または説明にあるか（同期呼び出し？イベント？）
- [ ] **外部システム**が書かれているか
- [ ] **データの流れ**（誰が書き、誰が読むか）が分かるか
- [ ] **同期・非同期**が区別されているか
- [ ] 図の**版または日付**があるか（古い図は害になる）

## 3. 観点2 — 境界

### 3.1 何の境界を見るか

| 境界の種類 | 問い |
|------------|------|
| **ドメイン境界** | 用語・ルールがコンテキストごとに一貫しているか（[[03_境界づけられたコンテキストとコンテキストマップ]]） |
| **モジュール／サービス境界** | 責務は1つに絞れているか、循環依存はないか |
| **データ境界** | 誰がそのデータの**正**を持つか（[[04データ所有権と分散トランザクションとSAGAと整合性]]） |
| **チーム境界** | オーナーは誰か、横断変更はどう調整するか |

```
  悪い例: 注文サービスが在庫テーブルを直接 UPDATE
  良い例: 在庫サービスの API 経由。在庫が正を持つ
```

### 3.2 境界のチェックリスト

- [ ] **単一責任** — 1つの部品の変更理由は1種類に近いか
- [ ] **依存の方向** — 内側（ドメイン）が外側（UI・DB）に依存していないか（[[01依存性逆転]]）
- [ ] **公開面** — 外部に見せる API と内部実装が分かれているか
- [ ] **横断的関心事** — 認証・ログは各所にコピーされていないか（[[01_横断的関心事]]）
- [ ] **暫定境界** — 「とりあえず同じDB」の場合、見直し条件は書いてあるか（[[03技術的負債と意図的な暫定案]]）

## 4. 観点3 — 非機能（品質属性）

[[01品質属性]] で学んだ**非機能要件**は、図の脚注に消えがちです。  
レビューでは、少なくとも次を**明示的に**聞きます。

### 4.1 よく問う品質属性

| 品質属性 | レビューでの問い | 設計への影響例 |
|----------|------------------|----------------|
| **性能** | 想定 QPS・レイテンシは？ピークは？ | キャッシュ、非同期、読み取りモデル |
| **可用性** | 止まったらどうなる？許容ダウンタイムは？ | 冗長化、フェイルオーバー、デグレード |
| **セキュリティ** | 誰が何にアクセスする？機密データは？ | 認証・認可の置き場所、暗号化 |
| **修正容易性** | どこがよく変わる？ | モジュール分割、インターフェース |
| **スケーラビリティ** | 何を水平スケールする？ | ステートレス化、キュー |

### 4.2 非機能のチェックリスト

- [ ] **数値または目安**があるか（「速く」だけで終わっていないか）
- [ ] **トレードオフ**が言語化されているか（[[02トレードオフ]]）
- [ ] **セキュリティ** — 認証・認可・秘密情報の扱いが図または ADR にあるか
- [ ] **一貫性** — 強い一貫性が必要な箇所と、緩めてよい箇所が分かれているか
- [ ] **テスト可能性** — 重要な振る舞いをどう検証するか

## 5. 観点4 — 運用

**「動けばよい」設計**は、本番で初めて問題になります。

### 5.1 運用で見ること

| 項目 | 問い |
|------|------|
| **デプロイ** | 無停止で出せるか、ロールバックは？ |
| **設定** | 環境ごとの差分はどこで管理するか（[[04設定とシークレットとフィーチャーフラグ]]） |
| **観測性** | 障害時に何をログ・メトリクス・トレースで見るか（[[03観測性とログとメトリクスとトレースとアーキテクチャ上の接点]]） |
| **障害** | 依存先が落ちたときの振る舞いは（[[05BFFとAPIゲートウェイとグレースフルデグレーデーション]]） |
| **データ** | バックアップ、移行、リストアの想定は |

```
  設計図 + 運用の問い
  ┌─────────────────────────────────────┐
  │  API ──→ サービス ──→ DB           │
  │    ↑         ↑          ↑           │
  │  監視      サーキット    バックアップ  │
  │  アラート   ブレーカー   リストア手順  │
  └─────────────────────────────────────┘
```

### 5.2 運用のチェックリスト

- [ ] **障害シナリオ**を1つ以上想定しているか（依存先ダウン、DB遅延など）
- [ ] **ログに載せる情報**（相関 ID、ユーザー ID のマスキング）が決まっているか
- [ ] **アラート**の条件がざっくりでもあるか
- [ ] **手動運用**が必要な作業と、その頻度が分かっているか
- [ ] **オンコール**が必要なら、Runbook またはリンクがあるか

## 6. レビューの進め方（初心者向け）

### 6.1 30分の軽いレビュー例

1. **5分** — コンテキスト図で「何のシステムか」を確認
2. **10分** — 境界（データのオーナー、API の公開面）
3. **10分** — 非機能（性能・可用性・セキュリティのうち1〜2つ）
4. **5分** — 運用（デプロイ、障害時、観測）
5. **メモ** — 決定事項は ADR またはチケットへ（[[02ADRとArchitecture Decision Record]]）

### 6.2 レビュアーでなくても使える

プルリクエストの説明に、次の4行を足すだけでも効果があります。

```markdown
## 境界: 変更は注文モジュール内。在庫APIは呼び出しのみ。
## 非機能: ピーク100req/s、P95 200ms 目標。
## 運用: 既存メトリクス dashboard-X にエラー率追加。
## リスク: 在庫API障害時は注文確定をリトライキューに退避（暫定）。
```

---

## 7. まとめ — 4観点の一覧

| 観点 | 中心の問い | 見落としがちな例 |
|------|------------|------------------|
| **図** | 誰に何を伝えるか | レベルが合わない、矢印の意味が不明 |
| **境界** | 誰が何を持つか | データの二重管理、循環依存 |
| **非機能** | どの品質を優先するか | 「後で考える」性能・セキュリティ |
| **運用** | 本番でどう動かすか | ログなし、ロールバック未考慮 |

アーキテクチャの成熟度は、**きれいな図を描けるか**より、**この4つを習慣的に話せるか**に近いです。
