# 意思決定と進化 — 第7部の入口

## この教材の目的

第0〜6部では、**どんな構造にするか**（層、ドメイン、分散、横断的関心事）を学んできました。

第7部では視点を変え、**その構造をどう決め、どう記録し、どう変えていくか**を扱います。

- ADR（Architecture Decision Record）
- 技術的負債と意図的な暫定案
- 進化型アーキテクチャ、リバースコンウェイの法則（必要なら）
- レビュー観点（図、境界、非機能、運用）

アーキテクチャは「一度描いたら終わり」ではありません。  
チームが変わり、要件が変わり、技術が変わるなかで、**なぜそうしたか**を残し、**いつ直すか**を意識することが長期保守の鍵です。

この第7部は**概要レベル**です。アーキテクト専門職の代わりではなく、「設計会議で何を話し、何を残すか」の地図を押さえることを目的にしています。

前提として [[01_ソフトウェアアーキテクチャとは]]、[[02_アーキテクチャと設計の違い]]、[[01品質属性]]、[[02トレードオフ]] を読んでおくとつながりやすくなります。

---

## 1. 第7部で扱う「意思決定と進化」とは

**意思決定**とは、トレードオフのなかで**選んだ道**のことです。

- モノリスにするか、サービスを分けるか
- 同期 API か、イベント駆動か
- 認証をゲートウェイに集約するか、各サービスで行うか

これらは「正解が1つ」ではなく、**状況・制約・優先順位**によって変わります。  
だからこそ、**なぜその選択をしたか**を残す（ADR）ことが重要です。

**進化**とは、アーキテクチャが**時間とともに変わる**ことです。

```
  初期の設計 ──→ 機能追加 ──→ チーム拡大 ──→ 負債の整理 ──→ 次の形へ
       │              │              │              │
       └──────── ADR・レビュー・意図的な暫定案で「迷子」にならない ─────┘
```

「最初から完璧な設計」は現実にはほとんどありません。  
**測定できる指標とレビューの習慣**を持ち、必要なときに形を変えられるようにするのが進化型アーキテクチャの考え方です。

---

## 2. なぜ第7部を学ぶのか

構造パターンだけ学ぶと、次のような落とし穴に入りやすくなります。

| 問題 | 典型例 |
|------|--------|
| 理由が消える | 「昔そう決めた」が誰も覚えておらず、同じ議論を繰り返す |
| 暫定案が永久化 | 「とりあえず」の実装が、リファクタ予定なしのまま残る |
| 組織と設計のズレ | マイクロサービスを目指したが、チーム構成がモノリス向きのまま |
| レビューが表面的 | 図はきれいだが、障害時の運用や非機能要件が抜けている |

第7部は、**設計の「中身」**だけでなく、**プロセスと記録**を扱います。  
ジュニアでも「この決定、ADR に書きませんか？」「この暫定案、いつ直すか決めましょう」と言えるようになることが目標です。

## 3. この第7部の読み方

```
  01_意思決定と進化（このノート）
       │
       ├─→ 02 ADR … 決定を短く記録する習慣
       │
       ├─→ 03 技術的負債と意図的な暫定案 … 借金と戦略的ショートカット
       │
       ├─→ 04 進化型アーキテクチャ・リバースコンウェイ … 変化と組織
       │
       └─→ 05 レビュー観点 … 図・境界・非機能・運用のチェックリスト
```

**02 → 03 → 05** の順がおすすめです（記録 → 負債の扱い → レビューで実践）。  
チーム編成や組織設計に関心がある場合は、04 を 03 のあとに読むとつながります。

---

## 4. 初心者が覚えておきたい3つのこと

1. **決定には理由を残す** — 結論だけでなく、検討した選択肢とトレードオフを短く書く（[[02ADRとArchitecture Decision Record]]）
2. **暫定案は「暫定」と決める** — 借金をゼロにする必要はないが、**意図・期限・直し方**をセットにする（[[03技術的負債と意図的な暫定案]]）
3. **レビューは4つの観点で** — きれいな図だけでなく、境界・非機能・運用まで見る（[[05レビュー観点と図と境界と非機能と運用]]）
