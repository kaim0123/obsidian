# 依存性逆転（DIP）の実務的イメージ

## この教材の目的

第2部で見たとおり、ソフトウェアの構造化の基本は**層化**でした。
しかし「層を上から下に積む」だけでは、

- ドメイン層（業務ロジック）が**インフラ層（DB・外部API）に依存**してしまう
- DBを変えると**業務ロジックも書き換える**必要がある
- 業務ロジックの**テストにDB起動が必要**になる

という問題が残ります。これを解決するのが**依存性逆転 (Dependency Inversion Principle, DIP)** です。

この教材では、

- DIPとは何か（一言で）
- 「自然な依存」と「逆転した依存」の違い
- なぜ逆転すると嬉しいのか
- **抽象（インターフェース）**を介す具体的な実装イメージ
- クリーン／ヘキサ／オニオンとの関係

を、**初心者でもコードが書けるレベル**まで噛み砕いて解説します。
前提として [[01層化]] と [[03アーキテクチャに効く原則]] を読んでおくと理解が深まります。

---

## 1. 依存性逆転 (DIP) とは

**依存性逆転の原則 (Dependency Inversion Principle, DIP)** とは、SOLID原則の5番目（D）にあたり、一言でいうと、

> **重要な高水準モジュール（業務ロジック）を、低水準モジュール（DBやフレームワーク）に依存させてはいけない。**
> **両方とも「抽象（インターフェース）」に依存させなさい。**

という考え方です。

「依存の向きを**逆転**させる」と言うのは、

- 普通：業務ロジック → DB（業務ロジックがDBに依存）
- 逆転後：業務ロジック → 抽象 ← DB（DBの方が抽象に従う）

のように、**業務ロジックがインフラに依存しない**形に組み替えることを指します。

---

## 2. 「自然な依存」と「逆転した依存」

### 2.1 自然な依存（多くの初学者が書く形）

```
class OrderService {
    submit(order) {
        // MySQL の具体クラスを直接 new する
        const conn = new MySQLConnection("localhost", "root", ...);
        conn.execute("INSERT INTO orders ...");
    }
}
```

このコードでは、`OrderService`（業務ロジック）が `MySQLConnection`（インフラ）を**直接知っている**状態です。

**依存の向き**：

```
[業務ロジック] ───依存───▶ [MySQL（具体）]
```

業務ロジックが、**MySQL という具体的な技術に縛られている**状態です。

### 2.2 逆転した依存

```
// 抽象（インターフェース）を定義する
interface OrderRepository {
    save(order): void;
}

// 業務ロジックは抽象にだけ依存する
class OrderService {
    constructor(repo: OrderRepository) { this.repo = repo; }
    submit(order) { this.repo.save(order); }
}

// MySQL 実装は抽象を「実装する」側
class MySQLOrderRepository implements OrderRepository {
    save(order) { /* MySQL 固有の処理 */ }
}
```

**依存の向き**：

```
[業務ロジック] ──▶ [OrderRepository（抽象）] ◀── [MySQL 実装]
```

業務ロジックも、MySQL 実装も、**両方とも抽象（インターフェース）の方を向いている**状態です。
これが「**依存性が逆転した**」状態です。

---

## 3. なぜ逆転すると嬉しいのか

### 3.1 業務ロジックが技術選択に左右されない

「DBをPostgreSQLに変えよう」「メール送信をSendGridからSESに変えよう」となったとき、

- 自然な依存 → **業務ロジックを書き換える**必要あり
- 逆転した依存 → **新しい実装クラスを足す**だけで済む

### 3.2 テストが書きやすい

テスト時に**偽物（モック）の実装**を渡せます。

```
const fakeRepo = { save: (o) => { /* メモリ内に保存 */ } };
const service = new OrderService(fakeRepo);
service.submit({ id: 1, total: 100 });
// DBを起動せずにテストできる
```

### 3.3 業務ロジックが「読んで分かる」コードになる

業務ロジック側にMySQLのクエリやHTTPクライアントの初期化が出てこなくなり、**「業務として何をやっているか」だけが残る**ため、コードが**読みやすく**なります。

### 3.4 並行開発できる

「**`OrderRepository` というインターフェースだけ先に決める**」という合意があれば、

- Aさん：業務ロジック (`OrderService`) を書く
- Bさん：MySQL実装 (`MySQLOrderRepository`) を書く

を**並行して**進められます。

## 4. 抽象（インターフェース）を介す

DIP の心臓部は「**抽象を間に挟む**」ことです。
抽象とは具体的には、

- **インターフェース**（Java, TypeScript, C# 等）
- **抽象クラス**（多くのOOP言語）
- **プロトコル**（Swift）
- **トレイト**（Rust）
- **型クラス**（Haskell）
- **関数の型シグネチャ**だけを使う（動的言語、関数型）

など、言語によって表現は違いますが、**「実装ではなく契約だけを決める」**点で共通しています。

業務ロジックは、

- 「**保存できる何か**」（インターフェース）にだけ依存する
- どんな技術で保存するかは**知らない**

これにより、技術と業務の**結合度が下がる**（[[03アーキテクチャに効く原則|疎結合]] の話）わけです。

## 5. 実務での実装パターン

### 5.1 DI (Dependency Injection)

業務ロジックに**依存先を外から注入する**手法です。

- **コンストラクタ注入**（最も一般的）
  ```
  new OrderService(new MySQLOrderRepository());
  ```
- **セッター注入**
  ```
  service.setRepository(new MySQLOrderRepository());
  ```
- **メソッド引数による注入**
  ```
  service.submit(order, repo);
  ```

依存先を **`new` するのは、業務ロジックの「外側」（main関数やDIコンテナ）**に寄せるのがコツです。

### 5.2 リポジトリパターンの典型

DDDでも頻出する**リポジトリパターン**は、DIPの代表的な応用例です。

```
[業務ロジック] ──▶ [Repository インターフェース] ◀── [MySQL/Redis/Memory 実装]
```

業務ロジックは「**`UserRepository.findById(id)`**」と書くだけ。
具体的な保存先は、起動時に**外側で組み立てる**（DIコンテナやmainで）。

### 5.3 テスト時の差し替え

```
// 本番
const service = new OrderService(new MySQLOrderRepository());

// テスト
const service = new OrderService(new InMemoryOrderRepository());
```

「**インターフェースさえ満たせば差し替え可能**」がDIPの実用的なご利益です。

詳しくは姉妹フォルダの `03_設計/07_依存関係/01_依存性注入.md` も参照してください。

## 6. 図で理解する（before / after）

### 6.1 自然な依存（DIP 適用前）

```
┌──────────────────┐
│ 業務ロジック      │
│ OrderService    │
└──────┬───────────┘
       │ 依存（具体クラスを new）
       ▼
┌──────────────────┐
│ MySQL の具体     │
│ MySQL接続コード   │
└──────────────────┘
```

**変えにくい・テストしにくい**形。

### 6.2 逆転した依存（DIP 適用後）

```
┌──────────────────┐
│ 業務ロジック      │
│ OrderService    │
└──────┬───────────┘
       │ 依存（抽象だけ）
       ▼
┌──────────────────────┐
│ 抽象                  │
│ OrderRepository      │ ← インターフェース
└──────▲────────────────┘
       │ 実装する
┌──────┴─────────┐  ┌──────────────┐
│ MySQL 実装      │  │ Memory 実装  │
└────────────────┘  └──────────────┘
```

**両方が抽象を向く**＝業務ロジックは具体的な技術に縛られない形になります。

## 7. クリーン／ヘキサ／オニオンとの関係

### 7.1 共通の発想

このあと学ぶ **クリーンアーキテクチャ・ヘキサゴナル・オニオン**は、いずれもDIPを**アーキテクチャ全体に拡大適用**したものです。

- **中心にドメイン**（業務ロジック）を置く
- **周辺にインフラ**（DB、UI、外部API）を置く
- **すべての矢印が中心に向かう**ように、抽象を間に挟む

> 「**ドメインがインフラを知らない**」という鉄則は、結局DIPの言い換えです。

### 7.2 名前は違えど本質は同じ

| アーキテクチャ | 中心 | 周辺 | 介する抽象 |
|---|---|---|---|
| クリーン | エンティティ／ユースケース | フレームワーク／DB／UI | Boundary／Gateway |
| ヘキサゴナル | ドメイン | アダプタ（DB／UI／外部API） | ポート (Port) |
| オニオン | ドメインモデル | インフラ・UI | ドメインサービス／リポジトリの抽象 |

詳細は [[クリーンアーキテクチャの概要]]、[[ヘキサゴナルアーキテクチャ]]、[[オニオンアーキテクチャとの比較]]、[[依存性のルール]] を参照してください。

## 8. ありがちな誤解と落とし穴

### 8.1 「とにかく全部にインターフェースを切れば良い」

**誤りです。**
インターフェースは**増やすほどコードが複雑**になります。
**置き換える可能性がない・テストで偽物が要らない**部品にインターフェースを切るのは過剰設計（YAGNI 違反）です。

> ガイドライン：**外部に依存する境界（DB、外部API、UI、ファイル、時計、乱数など）**にインターフェースを置くのが定石。純粋な計算ロジック同士には不要なことが多いです。

### 8.2 「DIコンテナを使えば自動的にDIP」

**誤りです。**
DIコンテナは**便利な道具**ですが、依存の**向き**を正しく設計するのは**人**の仕事です。
コンテナを使っても、業務ロジックが具体クラスに直接依存していたらDIPは守れていません。

### 8.3 「実装1個のためのインターフェース」

**ありがちなアンチパターンです。**

- 実装クラス `MySQLOrderRepository` のために、**そのコピー**のような `IMySQLOrderRepository` インターフェースを切る
- 結局その実装1つしか存在しない

これは**インターフェースのためのDIP**になっており、本来の目的（**業務ロジック側の都合**で抽象を切る）から逆さです。
**「業務ロジック側にとって必要な操作」**を表すインターフェース名（例：`OrderRepository`）にすべきです。

### 8.4 「インターフェースは多機能なほど良い」

**誤りです。**
インターフェースは「**最低限の契約**」です。
利用者（業務ロジック）が必要としない機能は**書かない**。実装側の都合で機能を増やすと、抽象の意味が薄まります（インターフェース分離の原則 (ISP) と関連）。

---

## 9. まとめ

- **依存性逆転 (DIP)** とは、業務ロジック（高水準）を**抽象（インターフェース）にだけ依存**させ、具体的な技術（低水準）も同じ抽象を**実装する**形に組み替える原則です。
- 自然な依存では「業務ロジック → MySQL」と直接結びつくが、DIP適用後は「業務ロジック → 抽象 ← MySQL」と**両方が抽象を向く**形になります。
- メリットは、**技術選択の独立**・**テストの容易化**・**読みやすさ**・**並行開発**。
- 実装は **DI（コンストラクタ注入が王道）** と **インターフェース／抽象クラス**で行い、`new` するのは業務ロジックの**外側**に寄せます。
- クリーン／ヘキサ／オニオンは、いずれもDIPを**アーキテクチャ全体に適用**したもので、「**ドメインがインフラを知らない**」が共通の鉄則です。
- 「全部にインターフェース」「DIコンテナ＝DIP」「実装1個のためのインターフェース」「実装の都合でインターフェースを増やす」は典型的な誤りです。

次は [[クリーンアーキテクチャの概要]]、[[ヘキサゴナルアーキテクチャ]]、[[オニオンアーキテクチャとの比較]]、[[依存性のルール]] で、DIPを**全体構造**として実装する3つのパターンを見ていきます。
