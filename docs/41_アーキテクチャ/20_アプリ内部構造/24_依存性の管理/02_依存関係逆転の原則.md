# 依存関係逆転の原則（Dependency Inversion Principle, DIP）

## はじめに

SOLID原則の **D** にあたるのが **依存関係逆転の原則（DIP）** です。

直感的に理解しづらい原則ですが、**クリーンアーキテクチャ・ヘキサゴナル・テストしやすいコード** を支える **要** の考え方です。

---

## 原則の本文

Robert C. Martin は次のように述べています。

1. **「上位モジュールは、下位モジュールに依存してはならない。両者は、抽象に依存するべきである。」**
2. **「抽象は、具体的な実装に依存してはならない。具体的な実装が、抽象に依存するべきである。」**

難しく見えますが、一言でいうと、

> **「具体的なものに頼らず、抽象（インターフェース）に頼れ」**

ということです。

---

## 「依存の逆転」とは何か

### 普通の依存の流れ

```
上位（UseCase）  →  下位（MySQL）
    業務ロジック     具体的な技術
```

UseCase が MySQL を直接使うと、**業務ロジックが技術詳細に引きずられる**。

### 逆転した依存の流れ

```
上位（UseCase）  →  抽象（Interface）  ←  下位（MySQL）
```

UseCase は **抽象（Interface）に依存**、MySQL は **その抽象を実装** するだけ。

**下位が上位に『合わせる』形** に変わっています。これが **「逆転」** の意味です。

---

## コードで見る

### ❌ 逆転していない（通常の依存）

```typescript
// 下位（インフラ層）
class MySQLUserRepository {
  async save(user: User) {
    await mysql.query('INSERT INTO users ...');
  }
}

// 上位（業務層）
class RegisterUserUseCase {
  private repo = new MySQLUserRepository(); // 具体クラスに依存

  async execute(input) {
    const user = new User(input);
    await this.repo.save(user);
  }
}
```

**問題点**:
- UseCase が MySQL を知ってしまう
- DB を変えるだけで UseCase も変更が必要
- テスト時にモックできない

### ✅ 逆転している（DIP適用）

```typescript
// 抽象（UseCase側に定義）
interface UserRepository {
  save(user: User): Promise<void>;
}

// 上位（業務層）
class RegisterUserUseCase {
  constructor(private repo: UserRepository) {} // 抽象に依存
  async execute(input) {
    const user = new User(input);
    await this.repo.save(user);
  }
}

// 下位（インフラ層）
class MySQLUserRepository implements UserRepository {
  async save(user: User) {
    await mysql.query('INSERT INTO users ...');
  }
}

// 配線
const useCase = new RegisterUserUseCase(new MySQLUserRepository());
```

**改善点**:
- UseCase は UserRepository（抽象）しか知らない
- DB を PostgreSQL に変えても UseCase は変更不要
- テストではモックを注入できる

---

## なぜ「逆転」と呼ぶのか

### 矢印の向きを比べる

**DIP適用前（普通の依存）**:

```
[UseCase] ──依存──→ [MySQLUserRepository]
  上位                  下位
```

**DIP適用後**:

```
[UseCase] ──依存──→ [UserRepository (interface)]
                            ↑
                          実装
                            │
              [MySQLUserRepository]
                    下位
```

「下位 → 上位」と矢印が逆転したように見えるので **「依存関係逆転」** と呼びます。

## 実装のポイント

### 1. インターフェース（抽象）は上位側に置く

```
src/
├─ usecases/
│   ├─ RegisterUserUseCase.ts
│   └─ UserRepository.ts  ← インターフェース（抽象）
└─ infrastructure/
    └─ MySQLUserRepository.ts  ← 実装
```

**抽象は上位（使う側）の持ち物**。下位（実装者）は上位のインターフェースに合わせに行く。

### 2. 上位が「欲しい」を宣言する

```typescript
// UseCase が自分に必要なものをインターフェースで宣言
interface EmailSender {
  send(to: string, body: string): Promise<void>;
}

// 下位はそれに実装
class SendGridEmailSender implements EmailSender { /* ... */ }
class AWSEmailSender implements EmailSender { /* ... */ }
```

### 3. コンストラクタでDIする

```typescript
class UseCase {
  constructor(private sender: EmailSender) {} // DI
}
```

→ [[01_依存性注入]]

## DIP と DI（依存性注入）の違い

この2つは **似ていて混同しやすい** ですが、別物です。

| | DIP | DI |
|---|-----|-----|
| 何 | 原則・思想 | テクニック |
| 目的 | 抽象に依存させる | 依存を外から渡す |
| ない場合 | 設計の方向性が決まらない | ハードコードされる |

**DIPはゴール、DIはその手段**、と捉えると整理しやすいです。

---

## DIPで何が良くなるか

### 1. 外部依存をテストできる

DB、外部API、メール送信をモックに差し替えて、**純粋なロジックだけテスト** できる。

### 2. 外部システムの変更に強い

MySQLをPostgreSQLに、SendGridをAWS SESに変えても、**業務ロジックは無傷**。

### 3. クリーンアーキテクチャが成立する

内側（ビジネス）を、外側（技術）から守るために不可欠。

### 4. レイヤー間の契約が明確になる

インターフェースが **レイヤー間の約束事** として機能する。

## よくある疑問

### Q1: インターフェースを全クラスに作るべき？

**不要**です。外部依存（DB、API、ファイル、メール）を **跨ぐ境界** だけに作れば十分。中の純粋な計算クラスには不要。

### Q2: 実装が1つしかないのにインターフェースを作る意味は？

**テスト容易性** と **将来の差し替え可能性** のためです。ただし、本当に1つしかないと分かっていて **テストにも困らない** なら、省略してOK。

### Q3: 抽象クラス vs インターフェース

- **抽象クラス**: 実装を共有できるが、1つしか継承できない
- **インターフェース**: 実装は持てないが、複数実装できる
- 迷ったら **インターフェース** を選ぶ

## アンチパターン

### ❌ 上位が下位をnewする

```typescript
class UseCase {
  private db = new MySQLDatabase(); // 具体クラスに直接依存
}
```

### ❌ 下位のインターフェースを下位側に置く

```
infrastructure/
├─ MySQLUserRepository.ts
└─ UserRepository.ts  ← 下位側にインターフェースがある
```

→ これだと、依存は「上位 → 下位」のまま。抽象は **上位側** に置く。

### ❌ インターフェースが実装に引きずられている

```typescript
interface UserRepository {
  executeQuery(sql: string): any; // ← MySQLの都合が漏れている
}
```

→ インターフェースは **ビジネスの言葉** で定義する。

---

## まとめ

- **具体ではなく、抽象に依存せよ**
- **抽象は上位側のもの**、下位が合わせに行く
- **インターフェース + DI** で実現する
- クリーンアーキテクチャ・テスト容易性の **要**
