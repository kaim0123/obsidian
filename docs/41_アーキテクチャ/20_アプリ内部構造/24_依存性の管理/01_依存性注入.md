# 依存性注入（Dependency Injection, DI）

## はじめに

**依存性注入（DI）** は、設計の基本技のひとつです。

> **クラスが必要とする相手（依存先）を、自分で作らず、外から渡してもらう**

たったこれだけの考え方ですが、これを守るだけで **テストが書きやすく、差し替えしやすい** コードになります。

---

## 「依存」とは何か

クラスAが、クラスBのメソッドを呼んでいるとき、**AはBに依存している** といいます。

```typescript
class UserService {
  save(user) {
    const db = new MySQLDatabase(); // ここでBを作っている
    db.insert(user);
  }
}
```

上の例では、`UserService` が `MySQLDatabase` に依存しています。しかも、**自分で作っている**（new している）ので、切り離せません。

---

## DIの3つの形

### 1. コンストラクタ注入（Constructor Injection）← 最も推奨

コンストラクタで依存を受け取る。

```typescript
class UserService {
  constructor(private db: Database) {} // 外から渡してもらう

  save(user) {
    this.db.insert(user);
  }
}

// 使う側
const service = new UserService(new MySQLDatabase());
```

**メリット**: 必須の依存を強制できる。不変に保てる。

### 2. セッター注入（Setter Injection）

setter メソッドで依存を渡す。

```typescript
class UserService {
  private db: Database;
  setDatabase(db: Database) { this.db = db; }
}

const service = new UserService();
service.setDatabase(new MySQLDatabase());
```

**デメリット**: 依存がセットされる前に使われる可能性。

### 3. メソッド注入（Method Injection）

個別のメソッドで依存を渡す。

```typescript
class UserService {
  save(user, db: Database) {
    db.insert(user);
  }
}
```

**用途**: たまにしか使わない依存を、使うときだけ渡す。

---

## DIの効果

### 1. テストが書きやすい

```typescript
class UserService {
  constructor(private db: Database) {}
  save(user) { this.db.insert(user); }
}

// テスト
test('saveはDBのinsertを呼ぶ', () => {
  const mockDb = { insert: jest.fn() };
  const service = new UserService(mockDb);
  service.save({ id: 1 });
  expect(mockDb.insert).toHaveBeenCalled();
});
```

**本物のDBを動かさず** にテストできる。

### 2. 差し替えが簡単

```typescript
// 本番
new UserService(new MySQLDatabase());

// 開発
new UserService(new InMemoryDatabase());

// テスト
new UserService(new MockDatabase());
```

### 3. 依存関係が明示的

「このクラスは何を必要としているか」が **コンストラクタを見れば分かる**。

### 4. SOLIDの原則との相性

- **DIP（依存性逆転）** を実現する手段
- **SRP** により責務の分離ができる
- **OCP** により拡張しやすい

---

## DIとDIコンテナ

### DIコンテナとは

アプリに必要な **全ての依存の組み立て** を自動でやってくれるツール。

### 有名なDIコンテナ

- JavaScript/TS: **InversifyJS**, **tsyringe**, **NestJS** のモジュール
- Java: **Spring**
- C#: **.NET 組み込みDIコンテナ**, **Autofac**
- Python: **dependency-injector**

### 簡単な例: tsyringe

```typescript
import { injectable, inject, container } from 'tsyringe';

@injectable()
class UserService {
  constructor(@inject('Database') private db: Database) {}
}

container.register('Database', { useClass: MySQLDatabase });

const service = container.resolve(UserService); // 自動で組み立て
```

### DIコンテナのメリット

- **配線コードを自動化**
- **ライフサイクル管理**（シングルトン、リクエスト毎、一時など）
- **環境別の差し替え** が楽

### DIコンテナのデメリット

- **学習コスト**
- **デバッグが難しくなる**（マジックが増える）
- **小規模なら手動DIで十分**

## DIを使わない書き方との比較

### ❌ DIなし

```typescript
class OrderService {
  async placeOrder(input) {
    const orderRepo = new MySQLOrderRepository(); // 直接生成
    const payment = new StripePayment();          // 直接生成
    const mailer = new SendGridMailer();          // 直接生成
    const order = new Order(input);
    await payment.charge(order.total);
    await orderRepo.save(order);
    await mailer.send(input.email);
  }
}
```

- **テストできない**（本物のAPIを叩いてしまう）
- **差し替えられない**（Stripeを変えたければ全て書き直し）
- **依存が隠れている**（コードを読まないと何に依存しているか分からない）

### ✅ DIあり

```typescript
class OrderService {
  constructor(
    private orderRepo: OrderRepository,
    private payment: PaymentGateway,
    private mailer: Mailer
  ) {}

  async placeOrder(input) {
    const order = new Order(input);
    await this.payment.charge(order.total);
    await this.orderRepo.save(order);
    await this.mailer.send(input.email);
  }
}
```

- テスト時は全てモックに差し替え可能
- 本番ではStripeや任意の実装を渡せる
- **どれに依存しているかコンストラクタで一目瞭然**

## DIを活かすコツ

### 1. 抽象に依存させる

```typescript
// ❌ 具体クラスに依存（差し替え不可）
constructor(private repo: MySQLUserRepository) {}

// ✅ インターフェースに依存
constructor(private repo: UserRepository) {}
```

→ [[02_依存関係逆転の原則]]

### 2. 依存は少なく保つ

コンストラクタの引数が **5個以上** になったら、**責任が大きすぎるサイン**。SRP違反。

### 3. コンストラクタでは依存を受け取るだけ

重い処理・DB接続・副作用は、コンストラクタで **やらない**。

---

## 手動DI vs DIコンテナ

### 手動DIで十分な場合

- 小〜中規模のアプリ
- Express のルータ単位など、局所的な配線

```typescript
// main.ts
const db = new MySQLDatabase();
const userRepo = new UserRepository(db);
const userService = new UserService(userRepo);
```

### DIコンテナが有効な場合

- 大規模アプリ
- 依存グラフが複雑
- 環境別（本番/テスト/開発）の切り替えが多い

---

## よくある誤解

### 誤解1: DIは難しい高度なテクニック

**「コンストラクタで渡す」** だけのこと。難しくありません。

### 誤解2: DIコンテナを使わないとDIではない

**手動で渡すだけでも立派なDI**。むしろ小規模なら手動の方がシンプル。

### 誤解3: DIは全てのクラスに必要

純粋な計算、値オブジェクトなど、依存がないクラスにはDIは不要。
