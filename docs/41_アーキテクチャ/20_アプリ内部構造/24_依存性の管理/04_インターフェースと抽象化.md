# インターフェースと抽象化

## はじめに

設計について学び始めると、「**抽象**」という言葉に何度も出会います。

- 「具体ではなく抽象に依存せよ」（DIP）
- 「インターフェースに対してプログラミングせよ」（GoF）
- 「詳細を隠せ」（情報隠蔽）

これらすべての核心が **「抽象化（Abstraction）」** と **「インターフェース（Interface）」** です。

---

## 抽象化とは

### 定義

**抽象化** = **本質的な特徴だけを取り出し、余計な詳細を切り捨てる** こと。

### 身近な例

- **車のハンドル** … 内部の油圧やリンク機構を意識せず、「回す」だけで曲がる
- **電源スイッチ** … 中の電気回路を知らなくても、「押す」だけで電気がつく
- **関数 `sort()`** … 中のアルゴリズム（クイックソート？マージソート？）を知らなくても、並び替えられる

使う側が **知るべきことだけを知れば動く** ようにするのが抽象化です。

---

## インターフェースとは

**インターフェース** = **「できることの約束」を定義したもの**

```typescript
interface Mailer {
  send(to: string, body: string): Promise<void>;
}
```

これは「**Mailer と呼ばれるものは、send メソッドを持っていることが約束されている**」という宣言です。

### インターフェースを使う側

```typescript
function notify(mailer: Mailer, user: User) {
  mailer.send(user.email, 'こんにちは');
}
```

使う側は **何の Mailer か** を知らない。**send が呼べればいい**。

### インターフェースを実装する側

```typescript
class SendGridMailer implements Mailer {
  async send(to, body) { /* SendGrid API呼び出し */ }
}

class AWSMailer implements Mailer {
  async send(to, body) { /* AWS SES API呼び出し */ }
}

class MockMailer implements Mailer {
  async send(to, body) { /* テスト用 */ }
}
```

**約束（send）さえ守れば、中身は自由**。

---

## なぜ抽象化が大事か

### 1. 複雑さを閉じ込められる

- インターフェースの **外側** からは、複雑な中身が見えない
- 中身をいじっても、**外に影響しない**

### 2. 差し替え可能になる

- 同じインターフェースなら **どんな実装でも使える**
- 本番はSendGrid、テストはモック、開発はログ出力のみ、と自由

### 3. テストが書ける

- 外部APIに繋がず、**モックでテスト**

### 4. 依存方向を制御できる

- 具体クラスに依存しないので、**依存関係逆転（DIP）** が可能

### 5. 設計の言語が豊かになる

- 「Mailer」「PaymentGateway」「Logger」など、**意図を名前で表現**

## 抽象化の粒度

### 抽象度を上げすぎると

```typescript
interface DoSomething {
  execute(input: any): any; // 何をするかわからない
}
```

何でもできるように見えて、**何もできない** 抽象。意味がない。

### 抽象度を下げすぎると

```typescript
interface SendGridMailer {
  sendViaSendGridApiV3(...): ...; // 特定の実装に引きずられている
}
```

**抽象が具体の都合に汚染** されている。インターフェースとして役立たない。

### 適切な抽象化

```typescript
interface Mailer {
  send(to: string, subject: string, body: string): Promise<void>;
}
```

- **十分に汎用的**（どんなメール配信サービスでも使える）
- **十分に具体的**（使う側は何をすればよいか分かる）

## 抽象化の種類

### 1. 手続きの抽象（関数）

```typescript
// 詳細を隠して、やってくれることだけ見せる
function sendMail(to: string, body: string) { /* ... */ }
```

### 2. データの抽象（クラス・型）

```typescript
class Email {
  // 中身がどう実装されているか気にせず使える
}
```

### 3. 制御の抽象（イテレータ・コールバック）

```typescript
// 内部のループを意識せず処理を渡せる
list.forEach(item => doSomething(item));
```

### 4. ポリモーフィックな抽象（インターフェース）

```typescript
interface Animal {
  speak(): void;
}
// DogもCatも同じ型として扱える
```

## インターフェース設計のコツ

### 1. 小さく保つ（ISP）

多機能インターフェースは使いにくい。**目的別に分ける**。

```typescript
// ❌ 全部入り
interface UserStore {
  save(user); find(id); delete(id);
  sendMail(user); generateReport(); backupAll();
}

// ✅ 分ける
interface UserRepository { save(user); find(id); delete(id); }
interface UserMailer { send(user); }
```

### 2. 利用者目線で定義

**使う側が欲しい形** で定義する。実装の都合に合わせない。

```typescript
// ❌ 実装側目線
interface UserRepository {
  executeQuery(sql: string): any;
}

// ✅ 使う側目線
interface UserRepository {
  findById(id: UserId): Promise<User | null>;
  save(user: User): Promise<void>;
}
```

### 3. ビジネスの言葉で

```typescript
// ❌ 技術の言葉
interface DAO { select(); insert(); update(); delete(); }

// ✅ ビジネスの言葉
interface OrderRepository { findActive(); registerNew(); cancel(); }
```

## 抽象化のやりすぎ注意

### 「すべてに抽象を」はアンチパターン

```typescript
// ❌ クラス数が2倍に増える
interface IUser { ... }
class UserImpl implements IUser { ... }
interface IOrder { ... }
class OrderImpl implements IOrder { ... }
```

**必要がないなら抽象化しない**。YAGNIを守る。

### 抽象化すべきタイミング

- **複数の実装が存在する / する予定**
- **外部システムへの境界**（DB、API、ファイル）
- **テストでモック/スタブを差し込みたい**
- **モジュール境界**（Bounded Context の間）

## 言語別の実装

### TypeScript / Java

```typescript
interface Mailer { send(to, body): Promise<void>; }
class SendGridMailer implements Mailer { /* ... */ }
```

### Python

```python
from abc import ABC, abstractmethod

class Mailer(ABC):
    @abstractmethod
    def send(self, to: str, body: str) -> None: ...

# もしくは Protocol（ダックタイピング）
from typing import Protocol

class Mailer(Protocol):
    def send(self, to: str, body: str) -> None: ...
```

### Go

```go
type Mailer interface {
    Send(to, body string) error
}
```

### JavaScript（interfaceなし）

```javascript
// 型はないが、ダックタイピングで同じことができる
function sendNotification(mailer, user) {
  mailer.send(user.email, 'hello'); // sendがあれば何でもOK
}
```
