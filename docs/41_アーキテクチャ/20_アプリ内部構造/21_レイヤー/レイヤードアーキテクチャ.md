# レイヤードアーキテクチャ

## はじめに

アプリを作っていると、**「どこにどのコードを書けばいいのか」** という問題に必ずぶつかります。これを「**層（レイヤー）**」に分けて整理するのが **レイヤードアーキテクチャ** です。

「上の層は下の層を呼ぶ」というシンプルなルールで、役割の違うコードを別のフォルダ・別のクラスに配置します。

---

## 基本構造: 4つの層

```
┌──────────────────────────┐
│  プレゼンテーション層       │  ← ユーザーが触る部分
│  (Presentation / UI)      │
├──────────────────────────┤
│  アプリケーション層         │  ← ユースケースの流れ
│  (Application)            │
├──────────────────────────┤
│  ドメイン層                │  ← ビジネスルール
│  (Domain / Business)      │
├──────────────────────────┤
│  インフラ層                │  ← DB・外部API
│  (Infrastructure)         │
└──────────────────────────┘
```

**上の層は下の層の機能を使える** が、**下の層は上の層を知らない** のが基本ルールです。

---

## 各層の役割

### 1. プレゼンテーション層

- **役割**: ユーザーとの接点（画面、HTTPエンドポイント、CLI）
- **具体例**:
  - Reactコンポーネント
  - Express のルートハンドラ
  - REST API のコントローラ
- **書くべきこと**: 入力の受付、出力の整形
- **書くべきでないこと**: ビジネスルール、DBアクセス

```javascript
// ✅ 良い例
app.post('/users', async (req, res) => {
  const user = await userService.register(req.body);
  res.json(user);
});
```

### 2. アプリケーション層

- **役割**: 「ユースケース」を1つずつ表現する。流れをまとめる
- **具体例**:
  - `RegisterUserUseCase`
  - `PlaceOrderService`
- **書くべきこと**: 処理の流れ、トランザクション境界
- **書くべきでないこと**: ビジネスルールの中身、UI処理

```javascript
class RegisterUserUseCase {
  async execute(input) {
    const user = User.create(input); // ドメインに依頼
    await this.userRepo.save(user); // インフラに保存を依頼
    await this.mailer.sendWelcome(user.email);
  }
}
```

### 3. ドメイン層

- **役割**: **業務ルール・ビジネスロジック** を持つ中核
- **具体例**:
  - `User`, `Order`, `Product` などのエンティティ
  - `Price`, `Email` などの値オブジェクト
- **書くべきこと**: 業務のルール（「未成年はビール買えない」など）
- **書くべきでないこと**: DBの都合、UIの都合

```javascript
class User {
  constructor(email, age) {
    if (!email.includes('@')) throw new Error('メール不正');
    this.email = email;
    this.age = age;
  }
  canBuyAlcohol() {
    return this.age >= 20;
  }
}
```

### 4. インフラ層

- **役割**: **外の世界** との接続（DB、外部API、ファイル、メール送信）
- **具体例**:
  - `MySQLUserRepository`
  - `SendGridMailer`
- **書くべきこと**: 永続化・外部通信・フレームワーク固有のコード
- **書くべきでないこと**: 業務ルール

---

## 層の間のルール

### 原則: 上から下への依存のみ

```
Presentation → Application → Domain → Infrastructure (古典的な書き方)
```

ただし、**現代的なレイヤードアーキテクチャ** では、インフラ層を **ドメインに逆依存** させる考え方もあります（DIP / クリーンアーキテクチャ）。→ [[依存性のルール]]

### 禁止されていること

- **下位層が上位層を直接呼ぶ**（ドメインがUIを知る）
- **層をスキップする**（UIから直接DBを叩く）
- **業務ルールをUIに書く**
- **DBの都合をドメインに漏らす**

---

## 具体例: ユーザー登録の流れ

```
1. HTTP POST /users           ← プレゼンテーション層
    ↓
2. RegisterUserUseCase.execute ← アプリケーション層
    ↓
3. User.create(input)          ← ドメイン層（ルール検証）
    ↓
4. userRepository.save(user)  ← インフラ層（DB書き込み）
```

---

## メリット

1. **どこに書くべきか迷わない** — フォルダ構成だけで分担がわかる
2. **変更の影響を局所化** — UIを変えてもDBは壊れない
3. **テストしやすい** — ドメインは外部依存なしでテスト可能
4. **チーム分担しやすい** — UIチームとバックエンドチームが並行作業可能

---

## よくある罠

### 1. 「ただのMVC」と混同

MVCは「画面まわりの分担」なので、レイヤードアーキテクチャとは **抽象度が違う** ものです。Controllerは **プレゼンテーション層の中** にあります。

### 2. ドメイン層が空っぽ

初心者がよくやる失敗。**ビジネスロジックを全部サービス層やコントローラに書いてしまい**、ドメイン層がデータ置き場（貧血ドメインモデル）になる。

### 3. 層の横断的な関心

ログ・認証・トランザクションは **全ての層に関係** します。これらは **ミドルウェアや AOP（アスペクト指向）** として別扱いにします。

### 4. 分け過ぎ

必ずしも4層である必要はありません。小さいアプリなら **プレゼンテーション + ドメイン + インフラ** の3層で十分。
