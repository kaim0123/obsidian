# 三層アーキテクチャ

## はじめに

**三層アーキテクチャ（3-Layer Architecture）** は、最もシンプルで広く使われているアーキテクチャの1つです。

アプリを **「表示」「業務」「データ」** の3つの層に分けることで、**誰でも迷わずどこに書くか判断できる** ようにします。

---

## 基本構造

```
┌──────────────────────────┐
│  表示層（プレゼンテーション層） │ ← 画面・UI
├──────────────────────────┤
│  業務層（ビジネスロジック層） │ ← 計算・ルール
├──────────────────────────┤
│  データアクセス層           │ ← DB・ファイル
└──────────────────────────┘
```

- **上の層 → 下の層 を呼び出す**
- **下の層 → 上の層 を知らない**

---

## 各層の役割

### 1. 表示層（Presentation Layer）

- **役割**: ユーザーが見る・触る部分
- **技術例**: HTML, CSS, React, Vue, HTTPエンドポイント
- **やること**:
  - 入力を受け取る
  - 業務層に処理を依頼する
  - 結果を整形して表示する

```javascript
// 例: HTTP コントローラ
app.post('/orders', async (req, res) => {
  const result = await orderService.placeOrder(req.body); // 業務層に依頼
  res.json(result);
});
```

### 2. 業務層（Business Logic Layer, BLL）

- **役割**: アプリケーションの **中核**。業務ルールを扱う
- **技術例**: Service クラス、UseCase クラス
- **やること**:
  - 業務ルールを計算する
  - データアクセス層に読み書きを依頼する
  - 複数の処理をまとめる

```javascript
class OrderService {
  async placeOrder(input) {
    if (input.items.length === 0) throw new Error('商品がない');
    const total = input.items.reduce((sum, i) => sum + i.price, 0);
    const order = { id: uuid(), total, items: input.items };
    await orderRepo.save(order); // データ層に依頼
    return order;
  }
}
```

### 3. データアクセス層（Data Access Layer, DAL）

- **役割**: **DBやファイル** との読み書き
- **技術例**: Repository, DAO, ORM（Prisma, Sequelize, TypeORM）
- **やること**:
  - SQL・クエリを発行する
  - オブジェクトとレコードを変換する

```javascript
class OrderRepository {
  async save(order) {
    await db.query('INSERT INTO orders ...', order);
  }
  async find(id) {
    return db.query('SELECT * FROM orders WHERE id = ?', id);
  }
}
```

## 具体例: 商品検索の流れ

```
ユーザー
  ↓ 「ラーメン」と検索
[表示層] SearchController
  ↓ searchService.search('ラーメン')
[業務層] SearchService（検索ルール適用）
  ↓ productRepo.findByName('ラーメン')
[データ層] ProductRepository
  ↓ SELECT * FROM products WHERE name LIKE '%ラーメン%'
  DB
```

## 日常生活での例え

レストランに例えると次のようになります。

- **表示層（プレゼンテーション）**: ウェイター（お客様との接点）
- **業務層（ビジネスロジック）**: シェフ（料理のルール）
- **データ層**: 冷蔵庫・食材庫（材料の保存）

## メリットの内訳（なぜ分けるのか）

1. **保守性** — UI だけ変えたいときに、業務・データ層を触らなくてよいことが多い  
2. **再利用** — 同じ業務 API を Web・モバイル・管理画面から使える  
3. **テスト** — 業務層を UI 抜きで検証しやすい  
4. **スケール** — 層ごとにサーバや DB を伸ばしやすい  
5. **役割分担** — フロント／バックエンド／データ担当で境界が描きやすい  

## データフローの例: ログイン

```
ユーザー入力（フォーム送信）
  → 表示層: HTTP リクエスト
  → 業務層: 入力検証、認証の流れ
  → データ層: ユーザー検索
  → 業務層: パスワード検証、セッション作成
  → 表示層: レスポンスを画面に反映
```

## 実装でのフォルダ分けの例

```
my-app/
├── frontend/     # 表示層（React など）
├── backend/      # 業務層（ルート・サービス）
└── database/     # スキーマ・マイグレーション（データ層の都合を集約）
```

### Next.js（App Router）での対応（目安）

Next.js は **「どのフォルダが公式に層を決める」わけではない** ので、**ルールはチームで `lib/` などに置く** ことが多いです。三層の考え方で **よく当てはまる配置** は次のとおりです。

| 層 | Next.js 上の置き場所の例 | 役割のイメージ |
|----|-------------------------|----------------|
| **表示層** | `app/**/page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`, `not-found.tsx` などルート配下の UI | 画面の描画・入力の受け取り。業務は **サービスや Server Action へ委譲** |
| **表示層（HTTP 境界）** | `app/api/**/route.ts`（Route Handlers） | REST 的な入出力。中身は薄くし、**業務層の関数を呼ぶだけ** にすると三層に近い |
| **表示層（部品）** | `components/`（クライアント／サーバー問わず、**見た目とイベント** が主なもの） | ボタン・フォーム・レイアウトなど。DB 直叩きや複雑なルールは避ける |
| **業務層** | `lib/services/`, `lib/use-cases/`, `server/actions/` 内の **薄いラッパー以外** の処理 など（命名はプロジェクト次第） | バリデーション（ドメインルール）、計算、複数リポジトリの組み合わせ |
| **データアクセス層** | `lib/repositories/`, `lib/dao/`, Prisma／Drizzle のクエリをまとめたモジュール、`prisma/schema.prisma` | DB・外部ストレージへの読み書き。ORM の利用自体はここに寄せる |

**補足の対応（迷いやすい場所）**

- **`middleware.ts`（ルート直下）** — 認可・リダイレクトなど **横断的な HTTP 前処理** で、厳密には三層のいずれか一つに閉じません。**薄く**保つのが無難です。
- **Server Actions**（`app/.../actions.ts` や `lib/actions/` など）— **HTTP 的な入口** に近いので表示寄りとも言える一方、中に業務や SQL をべた書きすると層が混ざります。**入口は薄く・本体はサービス／リポジトリ** と分けると整理しやすいです。
- **Server Component 内での `fetch` / ORM 直呼び** — ファイルの場所は `app/` でも、**呼んでいる処理の種類**で層が決まります。ページにロジックを詰め込むのではなく、**業務・データは `lib/` 側に出す**と三層の意図に沿います。
- **`public/`** — 静的アセットのみ。ビジネス・データ層ではないです。

Pages Router を使う場合の目安: `pages/**/*` の **ページコンポーネント** は表示層、`pages/api/*` は HTTP 境界、業務・データは App Router と同様に **`lib/` 等へ** という分け方が対応します。

## レイヤードアーキテクチャとの違い

| 項目 | 三層アーキテクチャ | レイヤードアーキテクチャ |
|------|----------|----------|
| 層の数 | 3層 | 4層以上（ドメイン層を分離） |
| ドメイン層 | 業務層に含まれる | 独立した層 |
| 主な使い道 | 小〜中規模のCRUDアプリ | 中〜大規模・複雑な業務 |
| 学習コスト | 低い | やや高い |

簡単に言えば、**三層は「業務層」の中にビジネスルールもユースケースも全部入っている** のに対し、**レイヤードでは「アプリケーション層（ユースケース）」と「ドメイン層（業務ルール）」に分ける** のが違いです。

---

## メリット

- **覚えることが少ない**
- **多くのフレームワークが前提とする構造**（Spring, Rails, Laravel…）
- **小規模チームでも運用できる**
- **教科書どおりで伝わりやすい**

---

## デメリット

- **業務ロジックが肥大化すると業務層が太る**（Fat Service問題）
- **ドメインが育たない**（ビジネスルールが Service 層に散る）
- **データ層の都合がロジックに漏れやすい**（JOIN 前提の設計など）
- **小規模では層分割が過剰**に感じることがある（ファイル数だけ増える）
- **層をまたぐたびにわずかなオーバーヘッド**がある（論理分割・往復のコスト）
- **各層の境界**を誤ると、かえって変更が困難になる

小さいアプリには十分ですが、**複雑な業務** を扱うようになったらレイヤードアーキテクチャやクリーンアーキテクチャへの移行を検討します。

---

## よくある変種

### 三層 + プレゼンターパターン

表示層を Controller / View / Presenter の3つに分ける。MVPパターンと組み合わせる。

### 三層 + リポジトリパターン

データ層を **Repositoryインターフェース + 実装** に分け、業務層はインターフェースだけに依存させる（DIP）。

---

## まとめ

- 最もベーシックな分割
- **表示 → 業務 → データ** の流れ
- 小〜中規模ならこれで十分
- 大きくなったら「業務層」を「アプリケーション層」と「ドメイン層」に分ける
