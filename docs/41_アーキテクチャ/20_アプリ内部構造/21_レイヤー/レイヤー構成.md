# レイヤー構成 — Entities / UseCases / Adapters / Frameworks

## はじめに

クリーンアーキテクチャでは、システムを **4つの層（リング）** に分けます。それぞれに **「何を書くべきか」「何を書くべきでないか」** のルールがあります。

このノートでは、実際のフォルダ構成とコード例を示しながら、各層の具体的な書き方を学びます。

---

## 4層の概要

| 層 | 役割 | 例 |
|---|------|-----|
| **Entities** | 企業全体のビジネスルール | `User`, `Order`, `Money` |
| **UseCases** | アプリ固有の業務フロー | `RegisterUserUseCase` |
| **Interface Adapters** | 外と内の翻訳役 | Controller, Repository実装, Presenter |
| **Frameworks & Drivers** | フレームワーク・DB・UI | Express, React, PostgreSQL |

---

## 1. Entities（エンティティ層）

### 書くべきこと

- **業務上の概念**（User、Order、Product、Email、Price…）
- **業務ルール**（canCancel()、applyDiscount() など）
- **不変条件の保証**（メール形式の検証、金額が負にならないなど）

### 書くべきでないこと

- DBアクセス
- HTTP / REST
- フレームワーク固有のもの
- UI / ビュー

### 例

```typescript
// entities/Order.ts
class Order {
  constructor(
    public readonly id: string,
    public readonly items: OrderItem[],
    private _status: OrderStatus
  ) {
    if (items.length === 0) throw new Error('注文には最低1つの商品が必要');
  }

  canCancel(): boolean {
    return this._status === 'pending';
  }

  cancel(): void {
    if (!this.canCancel()) throw new Error('キャンセル不可');
    this._status = 'cancelled';
  }

  total(): number {
    return this.items.reduce((sum, i) => sum + i.price, 0);
  }
}
```

**外部依存なし、純粋な業務モデル**。どこに持ち出しても動きます。

## 2. UseCases（ユースケース層）

### 書くべきこと

- **アプリ固有の業務の流れ**
- Entity を組み立て、Repository で保存し、外部サービスを呼ぶ、などの **流れ**
- トランザクション境界

### 書くべきでないこと

- HTTP や UI の詳細
- フレームワーク固有の型
- ビジネスルールそのもの（Entity に書くべき）

### 例

```typescript
// usecases/PlaceOrderUseCase.ts
interface OrderRepository {
  save(order: Order): Promise<void>;
}
interface PaymentGateway {
  charge(amount: number): Promise<void>;
}

class PlaceOrderUseCase {
  constructor(
    private orderRepo: OrderRepository,
    private payment: PaymentGateway
  ) {}

  async execute(input: PlaceOrderInput): Promise<Order> {
    const order = new Order(
      generateId(),
      input.items.map(i => new OrderItem(i.id, i.price)),
      'pending'
    );
    await this.payment.charge(order.total());
    await this.orderRepo.save(order);
    return order;
  }
}
```

**インターフェース（OrderRepository、PaymentGateway）は UseCase 層に定義** します。これが依存性逆転のポイント。

## 3. Interface Adapters（アダプタ層）

### 書くべきこと

- **翻訳役**: HTTPリクエスト ↔ UseCase入力、UseCase出力 ↔ レスポンス
- **Controller / Presenter / View Model**
- **Repository の実装**（UseCase のインターフェースを実装し、DBに繋ぐ）

### 例: Controller

```typescript
// adapters/controllers/OrderController.ts
class OrderController {
  constructor(private placeOrder: PlaceOrderUseCase) {}

  async handle(req: Request, res: Response) {
    const input = {
      items: req.body.items.map((i: any) => ({ id: i.id, price: i.price }))
    };
    const order = await this.placeOrder.execute(input);
    res.json({ id: order.id, total: order.total() });
  }
}
```

### 例: Repository実装

```typescript
// adapters/repositories/MySQLOrderRepository.ts
class MySQLOrderRepository implements OrderRepository {
  async save(order: Order): Promise<void> {
    await db.query('INSERT INTO orders (id, status) VALUES (?, ?)', [
      order.id, order._status
    ]);
    // ...
  }
}
```

**UseCase が定義したインターフェース** を、この層で実装します。

## 4. Frameworks & Drivers（フレームワーク層）

### 書くべきこと

- **Express / Fastify** などのWebサーバ起動
- **MySQL / PostgreSQL** などのDB接続
- 外部サービスのクライアント
- main関数・エントリポイント
- **依存関係の組み立て（DIコンテナ）**

### 例

```typescript
// frameworks/main.ts
import express from 'express';
import { MySQLOrderRepository } from '../adapters/repositories/MySQLOrderRepository';
import { StripeGateway } from '../adapters/gateways/StripeGateway';
import { PlaceOrderUseCase } from '../usecases/PlaceOrderUseCase';
import { OrderController } from '../adapters/controllers/OrderController';

const app = express();

// 依存を組み立て
const orderRepo = new MySQLOrderRepository();
const payment = new StripeGateway();
const placeOrder = new PlaceOrderUseCase(orderRepo, payment);
const controller = new OrderController(placeOrder);

app.post('/orders', (req, res) => controller.handle(req, res));
app.listen(3000);
```

**ここが唯一、全ての層を知っている場所**。全部を組み立てる「配線板」です。

## 層ごとの import ルール

| 層 | import してよいもの |
|---|---|
| Entities | 他のEntitiesのみ |
| UseCases | Entities・自分が定義したインターフェース |
| Adapters | UseCases・Entities・フレームワーク |
| Frameworks | 何でも |

**内側ほど、知っているものが少ない** のが正しい姿です。

## テストしやすさ

層に分けた最大の恩恵が **テスト容易性** です。

### Entity のテスト

```typescript
test('canCancelはpendingならtrue', () => {
  const order = new Order('1', [...], 'pending');
  expect(order.canCancel()).toBe(true);
});
```

依存なし、即テスト可能。

### UseCase のテスト（モック注入）

```typescript
test('注文処理の流れ', async () => {
  const mockRepo = { save: jest.fn() };
  const mockPayment = { charge: jest.fn() };
  const useCase = new PlaceOrderUseCase(mockRepo, mockPayment);

  await useCase.execute({ items: [{ id: 'a', price: 100 }] });

  expect(mockPayment.charge).toHaveBeenCalledWith(100);
  expect(mockRepo.save).toHaveBeenCalled();
});
```

**DBもHTTPも使わずにテスト可能**。これがクリーンアーキテクチャの本領。
