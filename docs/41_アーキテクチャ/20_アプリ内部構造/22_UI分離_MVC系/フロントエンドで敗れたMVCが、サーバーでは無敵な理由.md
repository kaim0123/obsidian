## 詳しい要約

**テーマ：MVC が 47 年間生き残った理由**

MVC は 1979 年に Xerox PARC で生まれた設計で、MVP・MVVM・Flux などの挑戦を受けて**フロントエンドでは敗れた**が、Rails・Django・Laravel・Spring などの**サーバーサイドでは今も背骨**であり続けている。その理由は技術的な優秀さよりも、Web の構造・教育・会話という人間側の事情にかみ合い、**「言葉」として生き残った**ことにある、と結論づける。

### 序章：47 年前に生まれた設計

- MVC の誕生は Rails が流行った 2000 年代ではなく **1979 年**。Windows も Mac もない時代
- MVP・MVVM・Flux・クリーンアーキテクチャなど挑戦者は何度も現れ、「MVC は終わった」と何度も言われたが、消えずに使われ続けている

### 第1章：造船業界出身の研究者と Xerox PARC

- 舞台は GUI・イーサネット・パーソナルコンピューターの原型を発明した **Xerox PARC**（Smalltalk もここで誕生）
- 1978 年、ノルウェーから客員研究員の**トリグヴ・リーンスカウグ**（当時 48 歳）が来訪。もとは造船業界で船の設計や生産計画を支えるシステムを作っていた人物
- 関心は理論より「**ユーザーの頭の中のイメージ**」と「**コンピューターの中のデータ**」の溝をどう埋めるか（今でいう UX に近い）
- 1979 年 5 月のメモ「Thing-Model-View-Editor」：現実の物事を Model に写し、View で画面に映し、Editor で操作する。Editor は数か月後の議論で **Controller** に改められた
- Smalltalk チームが実装に落とし込み、**Smalltalk-80** で MVC が初めて動くコードになった（思想が先、実装が後）

### 第2章：名前だけが世界に広がった

- **1988 年**、Krasner と Pope が Smalltalk-80 の MVC を解説した論文を発表し、設計パターンとして広く知られる
- ジョブズの **NeXTSTEP** が MVC を採用し、後に Mac の中核、iPhone アプリの標準設計に受け継がれる
- 決定打は **2004 年の Rails**。DHH が「Web アプリの正しい作り方」として MVC を前面に押し出し、Model＝ActiveRecord、View＝ERB、Controller＝ルーティングと直結。ディレクトリ構成まで決まっていて迷う余地がなかった
- その後 Django・CakePHP（2005）、ASP.NET MVC（2009）、Laravel（2011）が続き業界標準に
- ただし **Web の MVC は元の MVC とは別物**。元は画面部品 1 つ 1 つが M・V・C を持つデスクトップ GUI の設計、Web の MVC は「リクエストを受けて DB を読み HTML を返す」流れの整理術で、Java で **Model 2** と呼ばれていた設計に MVC の名がついたもの

### 第3章：曖昧さが武器になった理由

1. **人間の分業と一致**：デザイナー＝View、DB 担当＝Model、つなぐ人＝Controller。チームの形とコードの形がそろう
2. **Web の仕組みと相性が良い**：HTTP のリクエスト→処理→レスポンスを、入口＝Controller、処理＝Model、出口＝View と一本道で説明できる
3. **教えやすい**：3 つの箱と矢印だけで新人に 5 分で説明できる。学習コストの低さも武器
4. **共通言語になった**（最重要）：「そのロジックを Controller に書くと太りすぎでは」という会話が Rails でも Laravel でも Spring でも通じる

### 第4章：挑戦者たちとの攻防

- **MVP**（1996 年、Taligent）：View と Model を完全に切り離し、Presenter がすべて仲介
- **MVVM**（2005 年、Microsoft のジョン・ゴスマンが WPF 向けに設計）：ViewModel と View をデータバインディングで同期
- 挑戦者の多くは名前が MVC の変形で、MVC という土台の存在感をむしろ強めた
- 最大の強敵は **2014 年の Facebook の Flux**。「双方向のデータの流れが複雑さの元凶」と主張し、React と Redux がフロントエンドを塗り替えた
- ブラウザの中では MVC は敗れたが、サーバー側では何も変わらず、2026 年も Rails 8・Laravel 12・Django は MVC のまま

### 最終章：MVC が本当に残したもの

- サーバーサイドの Web アプリなら、2026 年でも **MVC から始めるのは合理的**。枯れた構造・豊富なドキュメント・誰でも読める配置は新しい設計では得られない
- MVC を窮屈に感じたらアプリが育ったサイン。Controller が肥大化したら**サービス層やドメイン層を足せばよい**。MVC は出発点であって終着点ではない
- MVC が残った本当の理由は、アーキテクチャとしてではなく**言葉として**生き残ったから。厳密な定義は崩れても「どこに何を書くか」を議論する単位として毎日使われている
- リーンスカウグ本人も、MVC の本質は「ユーザーの心の中のモデルとコンピューターの中のデータの橋渡し」であり、実装は時代ごとに変わってよいと振り返っている

### まとめ

- MVC は 1979 年、人間とデータの橋渡しという問題意識から生まれた
- Web の MVC は元の MVC とは別物で、名前として広がった
- フロントエンドでは Flux/React に敗れたが、サーバーサイドでは今も標準
- 長寿の理由は設計の勝利というより「関心を分けて名前をつけ、会話できるようにした」言葉の勝利
