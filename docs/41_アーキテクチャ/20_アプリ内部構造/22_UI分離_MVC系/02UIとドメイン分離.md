# UIとドメインの分離（MVC／MVP／MVVM／フロント状態管理との対応）

## この教材の目的

[[01層化]] で見たとおり、ソフトウェアを層に分けるのは構造化の基本です。
特に**プレゼンテーション層（UI 周辺）**は、

- ユーザー入力の受付
- 画面表示
- 入力バリデーション
- ドメイン（業務ロジック）の呼び出し
- 結果の整形

など**たくさんの関心**が集まりやすい場所で、放っておくと**画面コードが肥大化**します。

これを整理するために生まれたのが、

1. **MVC (Model-View-Controller)**
2. **MVP (Model-View-Presenter)**
3. **MVVM (Model-View-ViewModel)**

の3つの**プレゼンテーションパターン**です。

この教材では、

- なぜUIとドメインを分離するのか
- MVC・MVP・MVVMの**違いと共通点**
- フロントエンドの**状態管理**（Redux など）との対応
- ありがちな誤解と落とし穴

を、初心者でも判断できる形で解説します。

---

## 1. なぜUIとドメインを分離するのか

UIコードとドメインロジックを**同じ場所に書く**と、典型的に次の問題が起きます。

- **ロジックの再利用ができない**：別の画面で同じ計算を再実装する
- **テストが書きにくい**：UIを起動しないとロジックが試せない
- **画面の変更でロジックも壊れる**：軽い見た目変更が業務バグを誘発する
- **読みにくい**：1つのファイルに「描画」と「計算」と「DB呼び出し」が混在

これを防ぐために、**ドメイン（業務ロジック）**を**UI から切り離す**のが大原則です。
MVC 系の読み方の戸口は [[02_MVC_UI分離のまとめ]]。代表的な失敗例は [[01_MVC違反とは]]（モデルに HTML を含めるパターンもここに統合）を参照してください。

## 2. MVC (Model-View-Controller)

### 2.1 構成要素

- **Model（モデル）**：業務ロジックとデータ。**UI に依存しない**
- **View（ビュー）**：画面表示。Model の状態を見て描画する
- **Controller（コントローラ）**：ユーザー入力を受け取り、Model を操作する

### 2.2 動きの典型例

1. ユーザーがボタンを押す
2. **Controller** がイベントを受け取る
3. Controller が **Model** を更新する
4. Model の変化を **View** が描画する

### 2.3 図のイメージ

```
ユーザー入力 → Controller → Model
                              ↓ 通知
                            View ← 画面表示
```

### 2.4 メリットと落とし穴

- ✅ Model が UI から独立して**テストしやすい**
- ✅ Controller・View・Model で**役割が明確**
- ⚠️ View と Controller の境界が曖昧になりやすい
- ⚠️ View が Model を**直接読む**実装と、**Controller経由**で読む実装が混在しがち

詳細は [[02_MVC_UI分離のまとめ]] の読み順に沿って [[33_MVCアーキテクチャとは]]／[[MVCとMVVM]] を参照してください。

## 3. MVP (Model-View-Presenter)

### 3.1 構成要素

- **Model**：MVC と同じく業務ロジック・データ
- **View**：画面表示。**自分で何も決めず**、Presenter の指示通りに動く
- **Presenter（プレゼンター）**：View からのイベントを受け取り、Model を操作し、結果を View に**指示として返す**

### 3.2 MVCとの違い

MVPでは、**View は Model を直接見ない**のが特徴です。
すべての描画指示は **Presenter から View へ**渡ります。

```
ユーザー入力 → View → Presenter → Model
                  ←       ←      (結果)
```

### 3.3 メリットと落とし穴

- ✅ View が**完全に受け身**になり、テスト時に**Presenter だけ単体テスト**できる
- ✅ ロジックが Presenter に集約され、追跡しやすい
- ⚠️ View ⇔ Presenter のインターフェース定義が**手作業で煩雑**になる
- ⚠️ Presenter が肥大化しがち（「神Presenter」問題）

---

## 4. MVVM (Model-View-ViewModel)

### 4.1 構成要素

- **Model**：MVC・MVP と同じ
- **View**：画面表示。**ViewModel を観察**して自動で更新
- **ViewModel（ビューモデル）**：View が表示するためのデータを保持し、ユーザー操作で Model を更新する

### 4.2 MVPとの違い：データバインディング

MVVMの最大の特徴は、**View が ViewModel を「観察」する**ことです。
ViewModel のデータが変われば、View は**自動的に再描画**されます（**データバインディング**）。

```
ユーザー入力 → View ⇔ ViewModel ⇔ Model
                     (双方向バインディング)
```

### 4.3 メリットと落とし穴

- ✅ View に**描画ロジックをほぼ書かない**で済む
- ✅ ViewModel を**画面なしで単体テスト**できる
- ✅ 同じ ViewModel に対して**複数の View**（PC／モバイル）を作りやすい
- ⚠️ データバインディングの仕組みに**フレームワーク依存**する
- ⚠️ 双方向バインディングが**バグの追跡を難しくする**ことがある

---

## 5. 3つのパターンの比較

| 観点 | MVC | MVP | MVVM |
|------|-----|-----|------|
| View が見るのは | ModelとController | Presenterのみ | ViewModel |
| ロジックの主体 | Controller | Presenter | ViewModel |
| View の役割 | 描画＋一部入力処理 | 完全に受け身 | バインディングで自動更新 |
| データ更新方向 | 通知 (push) | Presenter からの指示 | 双方向バインディング |
| 主な舞台 | 古典的Webフレームワーク（Rails等） | デスクトップ・Android | リッチクライアント・モダンフロント |

> どれが「正解」ということはなく、**フレームワークと文化に応じて選ぶ**ものです。
> 共通点は「**View をできるだけ薄くし、ドメイン（業務ロジック）を独立させる**」という方針です。

## 6. フロントエンドの状態管理との対応

モダンなフロントエンド（React, Vue など）では、**状態管理ライブラリ**を使うのが一般的です。
代表例：

- **Redux**, **Zustand**（React 系）
- **Vuex**, **Pinia**（Vue 系）
- **NgRx**（Angular）

これらは、**MVVMの考え方**を**より明示的に**フロントエンドに持ち込んだものと理解できます。

### 6.1 対応関係（おおまかに）

| クラシックMVVM | モダンフロント |
|----------------|---------------|
| Model | API クライアント／ビジネスロジック関数 |
| View | コンポーネント（JSX, テンプレート） |
| ViewModel | ストア (Store) ＋ セレクタ ＋ アクション |
| データバインディング | リアクティブ更新（state → re-render） |

### 6.2 状態管理を使うときの落とし穴

- **ストアにビジネスロジックを書きすぎる**：本来 Model に置くべき計算がストア内に紛れ込む
- **状態を全部グローバルストアに入れる**：本来コンポーネントローカルでよい状態まで肥大化
- **UIの都合の状態と、ドメインの状態を混ぜる**：例：「モーダルが開いている」「フォームの入力値」とドメインデータが同じストアに混在

「**ストアに何を入れて、何を入れないか**」も、結局は**UIとドメインを分離する**設計判断の延長です。

---

## 7. 共通する大原則

3つのパターンと状態管理ライブラリに共通する**大原則**は、

1. **View（描画）をできるだけ薄く**
2. **ドメイン（業務ロジック）は UI から独立**させる
3. View ⇔ ドメインの**橋渡し役**（Controller / Presenter / ViewModel / Store）を**明示的に置く**

の3つです。

つまり「**MVCの C が MVPの P になり MVVMの VM になり、状態管理の Store になった**」と捉えると、

- 名前は変わっても**やっていることの本質は同じ**
- それぞれは**フレームワークや時代の流行に合わせた表現**

だと分かります。

これは第3部で扱う **クリーン／ヘキサ／オニオンの依存ルール**にもつながる発想です。

## 8. ありがちな誤解

### 8.1 「フレームワークが MVC と書いてあるから、これは MVC」

**必ずしも誤りではありませんが、要注意です。**
たとえば Rails の「MVC」は、Modelに**ビジネスロジックとDB操作の両方**が入りがちで、古典的な MVC とは中身が違います。
**名前**より、**実際にどこに何の責任があるか**を見ることが大切です。

### 8.2 「MVVM が一番新しいから一番良い」

**誤りです。**
ベストはコンテキスト次第です。

- サーバーサイドのHTML生成 → MVC が自然
- リアクティブな単一ページアプリ → MVVM／状態管理が自然
- イベント駆動のデスクトップアプリ → MVP が向くことも

### 8.3 「Model と DB テーブルは同じ」

**誤りです。**
Model は**ドメイン（業務ロジック）**を表すもので、DB の構造とは別物です。
DB テーブルそのものを Model にしてしまうと、業務ルールが**SQLの中**や**画面コードの中**に分散してしまいます。

## 9. 画面とドメインの「ずれ」を改善の手がかりにする（増田本）

パターンで View を薄くしたあとも、**画面のグルーピングとドメインオブジェクトの境界が食い違う**ことはよくあります。そのずれは失敗ではなく、利用者の関心事に両方を近づけるための手がかりです。

- 画面とドメインの連動・表示判断の置き場 → [[09_画面とドメインオブジェクトの設計]]
- タスクベースに画面を分ける具体 → [[05_画面関心事の分割とドメイン連動]]

## 10. まとめ

- UI とドメインを分離する目的は、**ロジックの再利用・テスト容易性・変更の局所化**を実現することです。
- 代表的なパターンは **MVC・MVP・MVVM** の3つで、いずれも「**View を薄く、ドメインを独立**させる」が共通の方針。
- **MVC**：View が Model を直接見る／**MVP**：View は Presenter の指示で動く／**MVVM**：View は ViewModel を観察して自動更新。
- モダンフロントエンドの**状態管理ライブラリ**（Redux, Pinia 等）は、**MVVM の発展形**として理解できます。
- 「フレームワークの名前」ではなく「**実際の責任配置**」を見ることが、設計判断の本質です。
- 画面とドメインの境界のずれは、[[09_画面とドメインオブジェクトの設計]] で連動させて洗練させる。

これで第2部「構造パターン（モノリス内）」は完了です。
次は **第3部「依存性の管理（中心と周辺）」** で、クリーン・ヘキサゴナル・オニオンを通して、**依存の向き**という視点を獲得します。
