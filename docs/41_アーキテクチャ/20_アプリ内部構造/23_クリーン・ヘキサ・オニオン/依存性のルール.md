# 依存性のルール — The Dependency Rule

## はじめに

クリーンアーキテクチャの中で **最も大事な1つのルール** が、**The Dependency Rule（依存性のルール）** です。

> **「ソースコードの依存関係は、外側から内側へのみ向かわなければならない」**

これが守られていれば、システムは変更に強くなります。守られていなければ、どんなにきれいな図を描いても意味がありません。

---

## ルールの本質

同心円の図で表すと、

```
外側（詳細、変わりやすい）
  └─ Frameworks/DB/UI
      └─ Interface Adapters
          └─ Use Cases
              └─ Entities（中央、変わりにくい）
```

**矢印（依存）は必ず内側に向く**。逆向きに依存してはいけません。

---

## 何が「依存している」ということか

あるモジュールAが、モジュールBを **import したり、Bのクラス名を書いたりしている** と、**AはBに依存している** といいます。

```typescript
// UserService が UserRepository に依存している
import { UserRepository } from './UserRepository';

class UserService {
  constructor(private repo: UserRepository) {}
}
```

この矢印（依存の方向）を **常に内側に向ける** のがルールです。

---

## OKな例

```typescript
// 内側（Entities）
class User {
  constructor(public email: string) {}
}

// 一つ外側（UseCase）
import { User } from '../entities/User'; // ✅ 内側への依存 OK

class RegisterUserUseCase {
  execute(input) { return new User(input.email); }
}

// さらに外側（Controller）
import { RegisterUserUseCase } from '../usecases/RegisterUserUseCase'; // ✅ 内側への依存 OK

class UserController {
  constructor(private useCase: RegisterUserUseCase) {}
}
```

---

## NGな例

```typescript
// ❌ Entity が外側の「Express」に依存している
import { Request } from 'express';

class User {
  constructor(req: Request) { /* ... */ }
}
```

User（Entity）はドメイン中心の存在。**Express（Framework）を知ってはいけません**。Expressが変わるだけでUserが壊れます。

```typescript
// ❌ UseCase が具体的なDB（MySQL）を知っている
import mysql from 'mysql2';

class PlaceOrderUseCase {
  async execute() {
    const conn = await mysql.createConnection(...);
    await conn.query('INSERT INTO orders ...');
  }
}
```

UseCaseは **どのDBを使うか** まで知るべきではありません。MySQLからPostgreSQLに変わるだけで壊れます。

---

## 依存性逆転（DIP）で解決する

「でも、UseCaseはDBに保存したい。**じゃあどうやって内側から外側を使うの？**」という疑問が出てきます。

ここで登場するのが **依存性逆転の原則（DIP）** です。

### 解決策: インターフェースを内側に置く

```typescript
// 内側: UseCaseがインターフェースを定義
interface OrderRepository {
  save(order: Order): Promise<void>;
}

class PlaceOrderUseCase {
  constructor(private repo: OrderRepository) {} // 抽象に依存
}

// 外側: 具体実装
class MySQLOrderRepository implements OrderRepository {
  async save(order: Order) { /* SQL */ }
}
```

**インターフェース（抽象）は内側にあり、実装（具象）は外側** にある。外側が内側のインターフェースを **実装** するので、依存の方向は **外→内** のまま。

この仕掛けを **依存性逆転（Dependency Inversion）** と呼びます。

→ 詳しくは [[02_依存関係逆転の原則]]

## 依存の流れの見分け方

### 判定チェックリスト

コードを開いて、**import文** を見ます。

- Entity は何を import しているか？ → 何も（または他のEntityのみ）
- UseCase は何を import しているか？ → Entity とインターフェース
- Adapter は何を import しているか？ → UseCase とインターフェース
- Framework層は何を import しているか？ → すべて（Adapter, UseCase, Entity）

**外側の層ほど多くを知り、内側ほど何も知らない** のが理想形です。

---

## データの持ち運びは Cross the Boundary

層をまたぐときは、**単純なデータ（DTO）で持ち運ぶ** のが原則です。

```typescript
// Controller から UseCase へは、専用の入力DTOで
class RegisterUserInput {
  constructor(public email: string, public age: number) {}
}

class RegisterUserUseCase {
  execute(input: RegisterUserInput) { /* ... */ }
}
```

こうすることで、**UseCase は HTTP リクエストの形状を知らずに済みます**。

---

## メリット

### 1. 変更に強い

外側（UI, DB, フレームワーク）が変わっても、中心のロジックは無傷。

### 2. テスト容易

UseCase は **外部依存なしで単体テスト** できる。DBもHTTPも必要ない。

### 3. ドメインが守られる

業務ルールが **フレームワークの都合に振り回されない**。

---

## よくあるNGパターン

### 1. Entity にアノテーションを付ける

```typescript
@Entity() // ← ORMのアノテーション
@Table('users')
class User { /* ... */ }
```

ORMに縛られると、**Entityが外側（ORM）に依存** してしまう。厳格に守るなら、**永続化用のモデルはEntityと別に用意** する。

### 2. UseCase で HTTP 例外を throw する

```typescript
// ❌ UseCase がHTTPを知ってしまう
throw new BadRequestException('invalid');
```

UseCase は **ビジネス例外** を throw し、**HTTP変換は外側の Controller でやる** のが正しい。

### 3. View が Entity を直接使う

Entity の内部構造が変わると View が壊れる。**View には ViewModel / DTO で渡す**。

---

## 完璧主義にならない

依存性のルールを **100%守る** と、小さなアプリでは書く量が爆発します。**重要な部分だけ厳密に守り、周辺は柔軟に** というのが現実解です。

特に：

- **Entities・UseCases はフレームワーク非依存** を死守
- **Controllers・Adapters はフレームワーク依存でもOK**
