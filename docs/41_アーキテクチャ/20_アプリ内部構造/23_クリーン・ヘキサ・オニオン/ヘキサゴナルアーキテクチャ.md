# ヘキサゴナルアーキテクチャ — ポート&アダプタ

## はじめに

**ヘキサゴナル（六角形）アーキテクチャ** は、Alistair Cockburn が2005年に提唱したアーキテクチャスタイルです。別名 **「ポート&アダプタ（Ports and Adapters）」** と呼ばれます。

クリーンアーキテクチャと **ほぼ同じ思想** ですが、図と用語が違います。特に「**ビジネスロジックを中心に置き、外の世界はすべてアダプタで繋ぐ**」という考え方が明快です。

---

## 六角形の図

```
         ┌─────────────────┐
         │  Web UI         │
         └───┬─────────┬───┘
             │ Adapter │
      ┌──────▼─────────▼──────┐
      │                        │
      │   Application Core     │
      │   (ビジネスロジック)     │
      │                        │
      └──────▲─────────▲──────┘
             │ Adapter │
         ┌───┴─────────┴───┐
         │  MySQL DB        │
         └─────────────────┘
```

真ん中に **アプリケーションコア**、周りを **ポート → アダプタ → 外部** の順で囲みます。図を六角形で描くことが多いので「ヘキサゴナル」。

---

## 中心概念

### 1. Application Core（中心）

- 業務ロジックの塊
- **外部のことは何も知らない**
- 例: Entities + UseCases に相当

### 2. Port（ポート）

- **コアが外と会話するための「窓口」**
- 単なるインターフェース
- 2種類ある：
  - **Driving Port（駆動ポート）**: コアが外から呼ばれる側（UseCaseのインターフェース）
  - **Driven Port（被駆動ポート）**: コアが外を呼び出す側（Repositoryのインターフェース）

### 3. Adapter（アダプタ）

- **ポートと外部を繋ぐ具体的な実装**
- 同じポートに対して、複数のアダプタが取り替え可能
- 例: `PostgresUserRepository`, `MongoUserRepository`

---

## 2種類のポート

### Driving Port（左側・入力側）

**外部がコアを呼び出す時に使う窓口**。

```typescript
// Driving Port
interface PlaceOrderPort {
  execute(input: PlaceOrderInput): Promise<Order>;
}

// コア（実装）
class PlaceOrderService implements PlaceOrderPort { /* ... */ }

// Driving Adapter（外から呼ぶ側）
class HTTPOrderController {
  constructor(private port: PlaceOrderPort) {}
  async handle(req) {
    return this.port.execute({ items: req.body.items });
  }
}

// 別のDriving Adapter: CLI
class CLIOrderCommand {
  constructor(private port: PlaceOrderPort) {}
  run(args) { return this.port.execute({ items: args.items }); }
}
```

→ **HTTPから呼んでもCLIから呼んでも、コアは同じ**。

### Driven Port（右側・出力側）

**コアが外を呼び出す時に使う窓口**。

```typescript
// Driven Port
interface OrderRepository {
  save(order: Order): Promise<void>;
}

// コアはこのインターフェースだけを知る
class PlaceOrderService {
  constructor(private repo: OrderRepository) {}
}

// Driven Adapter（外の具体実装）
class MySQLOrderRepository implements OrderRepository { /* ... */ }
class InMemoryOrderRepository implements OrderRepository { /* テスト用 */ }
```

→ **DBをMySQLからインメモリに差し替えても、コアは変更なし**。

---

## メリット

### 1. テストが非常にしやすい

- インメモリのアダプタを差し込めば、DBなしでコアの全てがテストできる
- Driving Adapter はユニットテスト、Driven Adapter は統合テストという分担が自然

### 2. 外部依存の差し替えが簡単

- DB変更、メッセージブローカー変更、UI変更、全てアダプタの差し替えで済む
- レガシーシステムからの移行でも、中核を先に作ってアダプタを後から繋ぎ替えられる

### 3. 新しい入口を増やしやすい

- 既存のHTTP APIに加えて、CLI・Slack Bot・バッチ処理を増やしたい場合、新しい Driving Adapter を書くだけ

## クリーンアーキテクチャとの関係

| 項目 | ヘキサゴナル | クリーン |
|------|-------------|---------|
| 発案者 | Cockburn (2005) | Martin (2012) |
| 図 | 六角形 | 同心円 |
| 用語 | Port, Adapter | Boundary, Interface Adapter |
| 層の数 | コア + アダプタ（2層） | 4層 |
| 本質 | 同じ | 同じ |

両者は **ほとんど同じことを言っています**。クリーンアーキテクチャのほうが **層の内訳が細かく定義** されています。

## フォルダ構成例

```
src/
├─ core/                  ← 中心
│   ├─ domain/            ← Entity
│   │   └─ Order.ts
│   ├─ application/       ← UseCase
│   │   ├─ ports/         ← ポート（インターフェース）
│   │   │   ├─ in/        ← Driving Port
│   │   │   │   └─ PlaceOrderPort.ts
│   │   │   └─ out/       ← Driven Port
│   │   │       └─ OrderRepository.ts
│   │   └─ services/
│   │       └─ PlaceOrderService.ts
├─ adapters/
│   ├─ in/                ← Driving Adapter（入力）
│   │   ├─ web/           ← HTTP Controller
│   │   └─ cli/           ← CLIコマンド
│   └─ out/               ← Driven Adapter（出力）
│       ├─ persistence/   ← MySQL Repository
│       └─ messaging/     ← Kafka Producer
└─ main.ts                ← 配線
```

## 実装のコツ

### 1. Port は必ず core 側に置く

ポートが core の外にあると、core が外部に依存してしまう。**インターフェースは core に、実装は adapters に**。

### 2. Adapter は薄く

アダプタに業務ロジックを書かない。**変換だけ** の薄い層に保つ。

### 3. In と Out を分ける

Driving Port と Driven Port は **フォルダで明確に分ける** と、依存の向きがひと目で分かる。

## テスト例

```typescript
// インメモリのアダプタでテスト
test('注文が保存される', async () => {
  const inMemoryRepo: OrderRepository = {
    orders: [],
    async save(o) { this.orders.push(o); }
  };
  const service = new PlaceOrderService(inMemoryRepo);

  await service.execute({ items: [{ id: 'a', price: 100 }] });

  expect(inMemoryRepo.orders.length).toBe(1);
});
```

**DBを起動せず、モックフレームワークも不要**。これが一番の恩恵。

## よくある誤解

### 誤解1: ポートとアダプタは同じもの

違います。**ポート = インターフェース（設計上の約束）**、**アダプタ = その実装（具体物）** です。

### 誤解2: 六角形は6層を意味する

**六角形の面の数に特別な意味はありません**。Cockburnが「四角形以外にして分かりやすくした」だけ。3面でも8面でも本質は変わりません。

### 誤解3: 全ての機能にポートを作る

過剰設計になります。**外部との境界にだけ** ポートを置けば十分。内部の詳細にまでポートは要りません。
