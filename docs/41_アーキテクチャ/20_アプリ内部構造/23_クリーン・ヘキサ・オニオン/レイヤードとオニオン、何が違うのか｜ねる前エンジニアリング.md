## 詳しい要約

**テーマ：レイヤードとオニオンの違いは「矢印（知っている＝import）の向き」**

どちらも層に分ける点は同じで、違いは依存の矢印の向きだけ。レイヤードは上が下を知るため、一番下のデータベースが変わると業務ルールまで響く。オニオンは業務ルールを中心に置き矢印をすべて内側に向けるので、外側（DB など）を替えても業務ルールは無傷になる。

---

### よくある場面（3 つとも原因は同じ）

- コストの都合などで保存先のデータベースを別製品に変えることになり、AI に直させたら DB と関係ないはずの業務ルールのファイルまで書き変わっていた（差分が大きくレビューがつらい）。
- 業務ルールを試したいだけなのに、テストを動かすと DB が必要になる。

### レイヤードとは

- 上から **画面 → アプリ（手順）→ 業務ルール → データベース** の 4 層に並べる。業務ルールは「在庫が足りなければ注文できない」のような決まり事。
- 決まりは 1 つ: 上の層はすぐ下の層だけを使ってよい。
- 矢印はデータの流れではなく **「知っている」の向き**。コードの中で相手の名前を書いて呼び出す＝ **import している** こと。
- 上は下を知るが、下は上を知らない。だから画面を作り替えても業務ルールは影響を受けない。

### 下の変更が上に響く（レイヤードの弱点）

- 変わるのは一番下の DB。それを知っている上の業務ルールが引きずられる。
- 業務ルールが DB を知っているので、ルールだけ試したくても DB ごと用意することになる。
- **大事なもの（業務ルール）が、変わりやすいもの（DB）に依存している** のが弱点。

### 矢印をひっくり返す（依存性逆転）

- 業務ルールの側に「注文を保存できるもの」という中身のない約束（**インターフェース**）を書く。業務ルールはこの約束だけを知り、DB のことは知らない。
- DB の側がその約束を守るように作られる。すると矢印が DB から業務ルールへ向く。これが **依存の向きの逆転**（シリーズ第 21 回でも扱った話）。

### オニオンの形

- 一番大事な業務ルールを真ん中に置き、その外側にアプリ（手順）、さらに外側に画面・DB・外部サービスを置く（玉ねぎの形）。
- 決まりは 1 つ: **矢印はすべて内側に向ける**。外側は内側を知ってよいが、内側は外側を知らない。
- 外側は細部（よく変わるもの）、内側は方針（めったに変わらないもの）。DB を変えても変わるのは外側の輪だけで、真ん中は無傷。

### 2 つを並べて比べる

| | レイヤード | オニオン |
|---|---|---|
| DB の置き場所 | 一番下 | 一番外 |
| みんなが知っているもの | 下 | 中心 |
| DB 変更の影響 | 上（業務ルール）に響く | 外側の輪だけ |
| 手間 | 少ない | 約束を 1 つ挟む分増える |

- オニオンが常に正解とは限らない。画面から保存まで一直線の小さなアプリならレイヤードで十分。業務ルールが複雑で外のものがよく変わるなら、オニオンの手間が報われる。

### コードで見る

- 中心の業務ルールには「注文の保存先」という約束があり、「保存する」ができるものとだけ書いてある。注文を受ける処理はこの約束を受け取って「保存する」を呼ぶだけで、DB の名前はどこにも出てこない。
- 外側のファイルは一番上で業務ルールの約束を読み込んでおり、**import の向きが外から中へ** になっている。約束を守る形で中身を SQL で書く。
- どの保存先を使うかはアプリの起動時に渡す。これが **依存性の注入（DI）**。

### AI に書かせたときに見る点

1. 業務ルールのファイルの import を見る。DB や外部サービスの名前が出てきたら矢印が外を向いている（ファイルの一番上を見るだけでよい）。
2. 約束（インターフェース）が中心の側に置かれているか。外側に置かれていると、結局中心が外を知ることになる。
3. 変更を頼んだときの差分が外側の輪だけで済んでいるか。中まで変わっていたら、どこかで矢印が逆を向いていると疑う。

### まとめ

- 矢印は「知っている」の向き、コードでは import の向き。
- レイヤードは下を知るので、下の DB が変わると上に響く。オニオンは中心を知るので、外を変えても業務ルールは無傷。
- ただし約束の分だけ手間が増えるので、小さなアプリならレイヤードで十分。
- クリーンアーキテクチャやヘキサゴナルも、矢印を内側に向ける仲間。流派の細かい違いは覚えなくてよい。
