# クリーンアーキテクチャの概要 — 同心円の意味

## はじめに

**クリーンアーキテクチャ（Clean Architecture）** は、Robert C. Martin（Uncle Bob）が提唱した、**長持ちするソフトウェアを作るための設計方針** です。

「クリーン」という言葉のとおり、**フレームワークやDBに依存しない、純粋で変更に強い構造** を目指します。

---

## 象徴的な「同心円」

クリーンアーキテクチャはよく **同心円の図** で表現されます。

```
         外側（詳細・変わりやすい）
    ┌──────────────────────┐
    │  Frameworks & Drivers │   ← DB, Web, UI
    │  ┌──────────────────┐ │
    │  │ Interface Adapters│ │   ← Controller, Presenter
    │  │  ┌──────────────┐ │ │
    │  │  │  Use Cases   │ │ │   ← アプリ固有のルール
    │  │  │  ┌────────┐  │ │ │
    │  │  │  │Entities│  │ │ │   ← 企業全体のルール
    │  │  │  └────────┘  │ │ │
    │  │  └──────────────┘ │ │
    │  └──────────────────┘ │
    └──────────────────────┘
         内側（中核・変わりにくい）
```

---

## 4つの層

### 1. Entities（エンティティ）

- **企業全体のビジネスルール**
- どのアプリでも共通する「物事のあり方」
- 例: `User`, `Order`, `Product`

```javascript
class Order {
  canCancel() {
    return this.status === 'pending';
  }
  applyDiscount(rate) {
    this.total = this.total * (1 - rate);
  }
}
```

### 2. Use Cases（ユースケース）

- **アプリ固有の業務フロー**
- 「ユーザーを登録する」「注文を確定する」など、アプリがやることを1つずつ表現
- Entities を使う

```javascript
class PlaceOrderUseCase {
  constructor(orderRepo, paymentGateway) { /* ... */ }
  async execute(input) {
    const order = Order.create(input);
    await this.paymentGateway.charge(order.total);
    await this.orderRepo.save(order);
  }
}
```

### 3. Interface Adapters（インターフェースアダプタ）

- Use Case と外界の間の **翻訳役**
- Controller / Presenter / Gateway など
- HTTPリクエスト → Use Caseの入力、Use Caseの出力 → HTTPレスポンス、といった変換

### 4. Frameworks & Drivers

- **一番外側**。フレームワーク・DB・UIなど、**差し替え可能な道具**
- Express, React, PostgreSQL, Redis…

---

## 最も大事なルール: 依存は内側へ

```
    ━━━━━━━━━→ 依存の方向
   外 → 中 → 中央
   (Frameworks) → (UseCases) → (Entities)
```

- **外側のものが、内側のものに依存してもよい**
- **内側のものが、外側のものに依存してはいけない**

つまり、**Entities は何も知らない**。**Use Cases はEntitiesだけ知る**。**Adapter や Framework は外側から中を呼ぶだけ**。

→ 詳しくは [[依存性のルール]]

---

## なぜこうするのか

### 1. フレームワークから独立

RailsやNext.jsが廃れても、**ビジネスの中核（Entities, UseCases）は動く**。

### 2. DBから独立

MySQL → MongoDB に変えても、**中心のロジックは変更不要**。

### 3. UIから独立

Web → モバイル → CLI と入れ替えても、**業務ルールは再利用できる**。

### 4. テストが独立して書ける

**外部依存（DB, API, UI）をモック** にして、純粋なUseCase・Entityだけをテストできる。

---

## 依存性逆転で実現する

本来なら「UseCase → DB」の向きに依存しそうですが、クリーンアーキテクチャでは **インターフェースを使って逆転** させます。

```typescript
// UseCase側（内側）が、必要なものをインターフェースで定義
interface OrderRepository {
  save(order: Order): Promise<void>;
}

class PlaceOrderUseCase {
  constructor(private orderRepo: OrderRepository) {} // 抽象に依存
}

// Framework側（外側）が、そのインターフェースを実装
class MySQLOrderRepository implements OrderRepository {
  async save(order: Order) { /* SQL */ }
}
```

こうすると、**UseCase は MySQL も PostgreSQL も知らない** まま動きます。

→ 詳しくは [[02_依存関係逆転の原則]]

## 「ボブおじさんの同心円」をコードに落とす

### フォルダ構成例

```
src/
├─ entities/            ← 中央
│   ├─ User.ts
│   └─ Order.ts
├─ usecases/           ← ユースケース
│   ├─ RegisterUserUseCase.ts
│   └─ PlaceOrderUseCase.ts
├─ adapters/           ← 変換役
│   ├─ controllers/
│   └─ repositories/
└─ frameworks/         ← 外側
    ├─ express/
    ├─ mysql/
    └─ config.ts
```

---

## メリット

1. **変更に強い** — 外側が変わっても内側は無傷
2. **テスト容易** — 中心だけ単体テストできる
3. **ドメインが主役** — 業務ロジックが読み取りやすい
4. **長寿命** — フレームワークが変わっても資産が残る

---

## デメリット

1. **小規模だとオーバースペック** — CRUDが中心ならやりすぎ
2. **書く量が増える** — 変換・インターフェースが多い
3. **学習コスト** — 新メンバーが迷う

「**ビジネスルールが豊か** で、**長く使う予定のシステム**」に向きます。
