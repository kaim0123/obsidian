# オニオンアーキテクチャとの比較

## はじめに

**オニオンアーキテクチャ（Onion Architecture）** は、Jeffrey Palermo が2008年に提唱したアーキテクチャで、**ドメインを中心に据え、外側に層を重ねていく** スタイルです。

名前のとおり **タマネギ** のように層が重なる図で表現されます。クリーンアーキテクチャ・ヘキサゴナルアーキテクチャとよく似ていますが、**微妙な違い** があります。

---

## オニオンの図

```
       ┌─────────────────────────┐
       │   Infrastructure         │ ← 最外層：DB, UI
       │  ┌─────────────────────┐ │
       │  │ Application Service │ │ ← ユースケース
       │  │ ┌─────────────────┐ │ │
       │  │ │ Domain Service  │ │ │ ← ドメインサービス
       │  │ │ ┌─────────────┐ │ │ │
       │  │ │ │ Domain Model│ │ │ │ ← Entity（中心）
       │  │ │ └─────────────┘ │ │ │
       │  │ └─────────────────┘ │ │
       │  └─────────────────────┘ │
       └─────────────────────────┘
```

---

## 各層の役割

### 1. Domain Model（ドメインモデル、最内層）

- Entity、値オブジェクト、集約
- **ビジネスの中核となる概念**
- 外部依存なし

### 2. Domain Service

- 複数のEntityにまたがる業務ロジック
- どこか1つのEntityに閉じない処理（例: 送金 = 2つの口座を操作）

### 3. Application Service

- ユースケースを1つずつ表現
- トランザクション境界
- 外部にインターフェースを提供

### 4. Infrastructure（最外層）

- DB、メール、外部API、UI
- **全ての外部との接続**

---

## クリーン・ヘキサゴナル・オニオン比較

| 項目 | クリーン | ヘキサゴナル | オニオン |
|------|---------|-------------|---------|
| 提唱者 | Robert Martin | Alistair Cockburn | Jeffrey Palermo |
| 発表年 | 2012 | 2005 | 2008 |
| 図 | 同心円 | 六角形 | タマネギ（同心円） |
| 層の数 | 4層（Entities/UseCases/Adapters/Frameworks） | 2層（コア + アダプタ） | 4層（Domain/Domain Service/App Service/Infrastructure） |
| キー用語 | Entities, UseCases, Boundary | Port, Adapter | Domain, Application, Infrastructure |
| ドメイン中心 | ✅ | ✅ | ✅ |
| 依存は内側へ | ✅ | ✅ | ✅ |

### 要点

**3つとも本質的に同じ思想** です。

- **ドメインを中心に置く**
- **依存の向きは外から内へ**
- **外部は差し替え可能**

違うのは：

- **図の描き方**
- **用語**
- **層の切り方の細かさ**

だけです。

---

## 似ている点

### 共通する原則

1. **ドメインが主役**
   - ビジネスルールは中心に
2. **フレームワーク非依存**
   - 外側を差し替えても中心は壊れない
3. **テスト容易**
   - 中心部分は外部依存なしでテスト可能
4. **依存性逆転（DIP）を使う**
   - インターフェースで内側から外側を制御する

---

## 違うところ

### 1. 層の切り方

- **クリーン**: UseCasesを独立した層として明示
- **オニオン**: Domain Service と Application Service を分ける
- **ヘキサゴナル**: そもそも2層（コア + アダプタ）とシンプル

### 2. 言葉の重点

- **クリーン**: 「Boundary（境界）」を強調
- **ヘキサゴナル**: 「Port / Adapter」を強調
- **オニオン**: 「Domain」を強調

### 3. 最外層の扱い

- **クリーン**: Frameworks & Drivers としてまとめる
- **ヘキサゴナル**: Adapter として統一的
- **オニオン**: Infrastructure として明示

---

## オニオン独自のポイント: Domain Service の位置

オニオンでは **Domain Service** が Application Service より内側に置かれます。

- **Domain Service**: ビジネス概念そのもの（送金・認証のような業務ロジック）
- **Application Service**: 「ユースケースを実現する流れ」

この分離は DDD（ドメイン駆動設計）の考え方と親和性が高く、**DDDと一緒に学ぶ** と理解が深まります。

---

## どれを選ぶべきか

### 小〜中規模 or はじめて触る

→ **ヘキサゴナル** がシンプルで覚えやすい

### DDDと組み合わせたい

→ **オニオン** がドメインの切り方と相性が良い

### 層を明確に分けて大規模開発したい

→ **クリーンアーキテクチャ** が最も詳細

### 現場で迷ったとき

→ **どれでも大丈夫**。チームで選んで、**大事な原則（依存の向き）だけ揺らさない** ことが一番大切。

---

## 共通するエッセンス（覚えるべき1行）

> **「ドメインを中心に置き、依存は必ず外から内へ流す」**

この一行さえ覚えておけば、3つのアーキテクチャのうちどれを採用していても、**同じゴール** に向かえます。
