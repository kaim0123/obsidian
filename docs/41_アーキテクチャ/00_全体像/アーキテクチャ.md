# 有名なアーキテクチャ — 西暦順でたどる

## このノートの目的

ソフトウェアのアーキテクチャには、MVC やクリーンアーキテクチャなど、よく名前を聞くスタイルがいくつもあります。  
しかし **「なぜ生まれたのか」「何の問題を解決したのか」** が分からないと、名前だけ覚えても使いどころが分かりません。

このノートでは、代表的なアーキテクチャを **登場が早い順（おおよその西暦）** に並べ、次の流れで初心者向けに解説します。

1. **その前に、どんな課題があったか**
2. **そのアーキテクチャは何を提案したか**
3. **どう解決したか（ざっくりした仕組み）**
4. **向いている場面・限界**

各時代で **コンポーネント（部品）・関係性（依存）・原則・制約** がどう変わったかは、[[01_ソフトウェアアーキテクチャとは]] の 3 要素に沿って **§11** で横断的に整理しています。

詳細は各章のリンク先ノートも参照してください。

---

## 全体の流れ（年表）

| 順番 | アーキテクチャ | 登場時期 | 一言で言うと | 主に解決した課題 |
|------|---------------|----------|-------------|-----------------|
| 1 | **MVC** | 1979 年 | 画面・操作・データを 3 つに分ける | 全部 1 か所に書く乱れ |
| 2 | **3 層アーキテクチャ** | 1990 年代 | 表示・業務・DB を層で分ける | サーバー側の責務の混在 |
| 3 | **MVP** | 1990 年代後半 | 画面制御を Presenter に任せる | MVC の Controller 肥大化 |
| 4 | **ドメイン駆動設計（DDD）** | 2003 年 | ビジネスルールをドメインモデルに集約 | ビジネスロジックの肥大化・用語のズレ |
| 5 | **MVVM** | 2005 年 | View と Model の間に ViewModel を置く | イベントだらけの画面連携 |
| 6 | **ヘキサゴナルアーキテクチャ** | 2005 年 | Port / Adapter で外側を差し替え可能に | 業務ロジックが DB に依存 |
| 7 | **オニオンアーキテクチャ** | 2008 年 | 依存の向きを内側（ドメイン）へ | 依存関係の整理不足 |
| 8 | **クリーンアーキテクチャ** | 2012 年 | これまでの考え方を 1 つに統合 | 層・依存・責務の全体整理 |
| 9 | **イベント駆動アーキテクチャ（EDA）** | 1990 年代〜2010 年代 | 「起きたこと」をイベントで通知し、非同期に反応する | システム間の直接依存・同期連鎖 |
| 10 | **マイクロサービス** | 2014 年頃 | 機能ごとに小さなサービスに分割して独立デプロイ | 巨大モノリスのデプロイ・スケール・チームの瓶頸 |

> **補足:** 年は「名前が広まった時期」の目安です。考え方の源流はもっと前から存在するものもあります。  
> **3 層** は [[レイヤードアーキテクチャ]]（4 層・N 層）の源流で、後者はアプリケーション層・ドメイン層をさらに細分化した発展形です。

## 0. その前：スパゲッティコード

アーキテクチャという言葉が普及する前から、ソフトウェアは作られていました。  
当時（1970年代以前〜）よく起きていたのが、**スパゲッティコード** と呼ばれる状態です。

- 画面の表示、計算、DB アクセスが **1つのファイルに全部書かれている**
- UI を変えると DB 処理まで壊れる
- テストが書けない（全部が密結合）

**「役割ごとに分けて、つなぎ方のルールを決めよう」** という発想が、アーキテクチャの出発点になりました。

---

## 1. MVC（1979 年）

**提唱:** Trygve Reenskaug（Smalltalk 向け）  
**一言:** 画面・操作・データを 3 つに分ける  
**詳細:** [[33_MVCアーキテクチャとは]]、[[02_MVC_UI分離のまとめ]]

### その前の課題 — 全部 1 か所に書く乱れ

- 画面（View）の中に、データ処理や計算まで書いてしまう
- 画面デザインを変えるだけなのに、ロジックまで触る必要がある

### 何を提案したか

| 部品 | 役割 |
|------|------|
| **Model** | データとビジネスルール |
| **View** | ユーザーに見せる部分 |
| **Controller** | 入力を受け取り、Model と View をつなぐ |

```
  ユーザー → View ⇄ Controller ⇄ Model
```

### どう解決したか

- **関心の分離:** 見た目と中身の処理を別の場所に書く
- 画面を差し替えても Model はそのまま使える

### 向いている場面・限界

- **向く:** Web アプリ、デスクトップ GUI など UI があるアプリ全般
- **限界:** Controller や Model が肥大化しやすい → MVP・3 層・DDD へ

---

## 2. 3 層アーキテクチャ（1990 年代）

**背景:** クライアント・サーバー型のエンタープライズシステムの普及  
**一言:** 表示・業務・DB を層で分ける  
**詳細:** [[三層アーキテクチャ]]、[[レイヤードアーキテクチャ]]、[[01層化]]

### その前の課題 — サーバー側の責務の混在

- MVC だけでは Model の中に DB アクセス・ビジネスルール・画面用整形が混ざる
- 大規模システムで「この機能、どのファイルに書く？」がバラバラになる

### 何を提案したか

サーバー側を **3 つの水平な層** に分ける。

```
┌──────────────────────────┐
│  プレゼンテーション層（UI）  │  ← 表示・入力
├──────────────────────────┤
│  ビジネスロジック層         │  ← 業務ルール
├──────────────────────────┤
│  データアクセス層（DB）      │  ← 永続化
└──────────────────────────┘
        上 ──呼ぶ──→ 下
```

### どう解決したか

- **役割の固定:** DB はデータ層、ルールはビジネス層、と決められる
- UI を変えてもビジネス層に手を入れなくて済む（理想形）

### 向いている場面・限界

- **向く:** 中〜大規模の業務システム、モノリスアプリ
- **限界:** ドメイン層が DB や UI に依存してしまうと層の意味が薄れる → ヘキサゴナル・クリーンへ

---

## 3. MVP（1990 年代後半）

**背景:** MVC の Controller 肥大化への対処（Taligent、Windows Forms など）  
**一言:** 画面制御を Presenter に任せる  
**詳細:** [[02UIとドメイン分離]]

### その前の課題 — MVC の Controller 肥大化

- Controller に UI ロジック・バリデーション・Model 操作が全部集まる
- View が Model を直接読む実装と、Controller 経由の実装が混在し、追いにくい
- View の単体テストが難しい

### 何を提案したか

Controller の代わりに **Presenter** を置き、**View は完全に受け身** にする。

```
ユーザー入力 → View → Presenter → Model
                  ←       ←      (結果)
```

| 部品 | MVC との違い |
|------|-------------|
| **View** | Model を直接見ない。Presenter の指示だけ描画 |
| **Presenter** | 画面制御のロジックをすべて担当 |

### どう解決したか

- View が薄くなり、**Presenter だけ単体テスト** しやすい
- 画面とロジックの境界が MVC より明確

### 向いている場面・限界

- **向く:** デスクトップアプリ、Android（初期の UI パターン）など
- **限界:** Presenter 自体が肥大化しやすい（神 Presenter）。双方向の画面更新が多いと MVVM の方が向く

---

## 4. ドメイン駆動設計 — DDD（2003 年）

**提唱:** Eric Evans（*Domain-Driven Design* 出版）  
**一言:** ビジネスルールをドメインモデルに集約  
**詳細:** [[02_DDDとは]]（`02_ソフトウェア設計/04_ドメイン駆動設計`）

### その前の課題 — ビジネスロジックの肥大化・用語のズレ

- ビジネスルールが Service クラスや Controller に散らばる
- 開発者の用語と現場の用語がズレ、要件のすり合わせに時間がかかる
- DB テーブル設計から始めると、業務の本質がコードに反映されない

### 何を提案したか

**ソフトウェアの構造と用語を、ビジネス（ドメイン）の現実に合わせる。**

| 概念 | 意味 |
|------|------|
| **ユビキタス言語** | 開発者と現場が同じ用語を使う |
| **境界づけられたコンテキスト** | 大きなシステムを業務の区切りで分割 |
| **集約・エンティティ・値オブジェクト** | ルールを守る単位としてモデル化 |

```
  現場の言葉 → ドメインモデル → コードの構造
                    ↑
            クリーンアーキテクチャの
            Entities / Use Cases と相性が良い
```

### どう解決したか

- ビジネスルールを **ドメイン層** に集約し、UI や DB から独立させる
- チーム間の境界（戦略設計）と、1 コンテキスト内のモデル（戦術設計）を分けて考える

### 向いている場面・限界

- **向く:** 業務ルールが複雑で、長期保守するシステム
- **限界:** 単純な CRUD では過剰。DDD は **アーキテクチャそのもの** というより **設計の考え方** で、クリーン・オニオンと組み合わせて使う

---

## 5. MVVM（2005 年）

**背景:** Microsoft WPF / Silverlight 向け（John Gossman）  
**一言:** View と Model の間に ViewModel を置く  
**詳細:** [[MVCとMVVM]]、[[02UIとドメイン分離]]

### その前の課題 — イベントだらけの画面連携

- 入力のたびに Controller / Presenter が View を手動更新するコードが増える
- 双方向の画面更新（フォーム ↔ 計算結果）がイベント地獄になる
- 同じデータを PC 版・モバイル版で別々に実装しがち

### 何を提案したか

**ViewModel** が画面用の状態を保持し、**データバインディング** で View と自動同期する。

```
┌─────────┐  データバインディング  ┌────────────┐
│  View   │ ←──────────────→ │ ViewModel  │
└─────────┘                  └──────┬─────┘
                                    ▼
                               Model（ドメイン）
```

### どう解決したか

- View に描画ロジックをほぼ書かず、ViewModel の変更が **自動で画面に反映**
- ViewModel を画面なしでテストできる
- 1 つの ViewModel に複数の View（PC / モバイル）を接続しやすい

### 向いている場面・限界

- **向く:** WPF、Vue、Angular、React + 状態管理など **リッチ UI**
- **限界:** 双方向バインディングのバグは追いにくい。フレームワーク依存が強い

### MVC 系 3 パターンの比較

| 観点 | MVC | MVP | MVVM |
|------|-----|-----|------|
| ロジックの主体 | Controller | Presenter | ViewModel |
| View の役割 | 描画＋一部入力 | 完全に受け身 | バインディングで自動更新 |
| 主な舞台 | Rails 等の Web | デスクトップ・Android | モダンフロント |

---

## 6. ヘキサゴナルアーキテクチャ（2005 年）

**提唱:** Alistair Cockburn（別名 **ポート&アダプタ**）  
**一言:** Port / Adapter で外側を差し替え可能に  
**詳細:** [[ヘキサゴナルアーキテクチャ]]

### その前の課題 — 業務ロジックが DB に依存

- 3 層でも、ドメイン層が MySQL や REST API に **直接依存** してしまう
- DB を変えたいのに SQL がビジネスロジック中に散らばっている
- テストのたびに DB を起動しないといけない

### 何を提案したか

**Application Core（ビジネスロジック）** を中心に置き、外の世界は **Port → Adapter** 経由で接続。

```
  Web UI ──→ [Adapter] ──→ Port
                              │
                     Application Core
                              │
  MySQL  ←── [Adapter] ←── Port
```

### どう解決したか

- 外側（DB・UI）が内側（ルール）に合わせる **依存の向きを逆転**
- DB や UI を差し替えてもコアはほぼ無変更

### 向いている場面・限界

- **向く:** ドメインルールが複雑で、インフラを差し替えたいモノリス
- **限界:** 小さな CRUD では抽象化が過剰

---

## 7. オニオンアーキテクチャ（2008 年）

**提唱:** Jeffrey Palermo  
**一言:** 依存の向きを内側（ドメイン）へ  
**詳細:** [[オニオンアーキテクチャとの比較]]

### その前の課題 — 依存関係の整理不足

- ヘキサゴナルと同様、**フレームワークや DB が主役** になりがち
- 「ドメイン層」「アプリケーションサービス」の **層の役割** がチーム内で曖昧
- 依存逆転（DIP）を **フォルダ構成** として表現したい

### 何を提案したか

**タマネギ状** に層を重ね、**Domain Model が最中心**。

```
       ┌─────────────────────────┐
       │   Infrastructure         │ ← DB, UI
       │  ┌─────────────────────┐ │
       │  │ Application Service │ │ ← ユースケース
       │  │ ┌─────────────────┐ │ │
       │  │ │  Domain Model   │ │ │ ← 中心
       │  │ └─────────────────┘ │ │
       │  └─────────────────────┘ │
       └─────────────────────────┘
              依存はすべて内側へ
```

### どう解決したか

- ドメインモデルを **最も安定した中心** として明示
- ヘキサゴナルと同思想だが、**層の名前と同心円の図** でチーム共有しやすい

### 向いている場面・限界

- **向く:** DDD と組み合わせた長期保守システム
- **限界:** クリーン・ヘキサゴナルと **思想はほぼ同じ** で、用語の違いが主。小規模では過剰

---

## 8. クリーンアーキテクチャ（2012 年）

**提唱:** Robert C. Martin（Uncle Bob）  
**一言:** これまでの考え方を 1 つに統合  
**詳細:** [[クリーンアーキテクチャの概要]]、[[依存性逆転]]

### その前の課題 — 層・依存・責務の全体整理

- ヘキサゴナル・オニオン・DDD がそれぞれ別の言葉で語られ、**初学者が混乱**
- UseCase と Entity の境界、Adapter の置き場所がプロジェクトごとにバラバラ

### 何を提案したか

**同心円の層** と **依存は常に内側へ** というルールを、1 つの図に統合。

```
        ┌─────────────────────────────┐
        │  Frameworks & Drivers（外）   │
        ├─────────────────────────────┤
        │  Interface Adapters          │
        ├─────────────────────────────┤
        │  Use Cases                   │
        ├─────────────────────────────┤
        │  Entities                    │  ← 最も安定
        └─────────────────────────────┘
```

### どう解決したか

- MVC・3 層・ヘキサゴナル・オニオン・DDD の **共通思想を1つに命名**
- エンティティとユースケースを中心に置き、UI・DB の変更影響を最小化

### 向いている場面・限界

- **向く:** 長期保守する業務システム（DDD と相性が良い）
- **限界:** 学習コストとボイラープレート。短命・小規模プロジェクトでは過剰設計

---

## 9. イベント駆動アーキテクチャ — EDA（1990 年代〜2010 年代）

**背景:** メッセージキュー（IBM MQ 等）、*Enterprise Integration Patterns*（2003年）、Kafka（2011年）  
**一言:** 「起きたこと」をイベントで通知し、非同期に反応する  
**詳細:** [[03同期APIとメッセージとイベント駆動の概観]]

### その前の課題 — システム間の直接依存・同期連鎖

- システム A が B を **直接 HTTP で呼ぶ** と、B の障害の影響をそのまま受ける
- 注文・在庫・配送・メールを **1 本の同期フロー** に詰め込むと、1 か所の失敗で全体が止まる

### 何を提案したか

**「何が起きたか（イベント）」** を発行し、必要な側が後から反応する。

```
  注文サービス ──「OrderCreated」──→ [ブローカー]
                                        ├──→ 在庫サービス
                                        ├──→ ポイントサービス
                                        └──→ 通知サービス
```

### どう解決したか

- **疎結合:** 注文サービスは在庫サービスの URL を知らなくてよい
- **非同期:** API はすぐ応答し、重い処理は後回し
- **拡張:** 新しい購読者を既存コードを触らず追加

### 向いている場面・限界

- **向く:** 複数サービス・複数チームの連携、ピーク時の負荷分散
- **限界:** 結果がすぐ揃わない（ eventual consistency）。運用コストが高い

---

## 10. マイクロサービス（2014 年頃）

**背景:** Netflix 等の実践、Martin Fowler / James Lewis による整理  
**一言:** 機能ごとに小さなサービスに分割して独立デプロイ  
**詳細:** [[02モノリスと分散モノリスとマイクロサービスといつ分けるか]]

### その前の課題 — 巨大モノリスのデプロイ・スケール・チームの瓶頸

- 小さな修正でも **全体を再デプロイ** する必要がある
- 100 人規模のチームが 1 つのコードベースでコンフリクト
- 在庫だけスケールしたいのに、全部同じサーバーで動く

### 何を提案したか

システムを **小さな独立サービス** に分割。各サービスは **自分のデータを所有** する。

```
  ┌─────────┐   ┌─────────┐   ┌─────────┐
  │ 注文     │   │ 在庫     │   │ ユーザー  │
  └────┬────┘   └────┬────┘   └────┬────┘
       └─────────────┴─────────────┘
              API / イベント で連携
```

### どう解決したか

- **独立デプロイ・スケール:** 在庫だけ修正・リリース・増強できる
- **チームの自律:** サービス単位でチームを分けやすい
- 内部は **クリーンアーキテクチャ**、連携は **EDA** と組み合わせることが多い

### 向いている場面・限界

- **向く:** 大規模プロダクト、複数チーム、部分ごとにリリース頻度が違う場合
- **限界:** 分散システムの難しさ（[[04データ所有権と分散トランザクションとSAGAと整合性]]）。小さなチームでは **モノリスから始める** 方が合理的なことが多い

## 11. 3 要素の進化 — コンポーネント・関係性・原則

[[01_ソフトウェアアーキテクチャとは]] で述べた **3 つの要素**（コンポーネント・関係性・原則・制約）は、アーキテクチャの「名前」が増えるたびに、**何を部品とみなすか・どうつなぐか・何を守るか** が段階的に洗練されてきました。  
ここでは、上の年表と対応させて、その変化を整理します。

### 11.1 コンポーネント（部品）— 「何を 1 単位とみなすか」

| 段階 | 主なコンポーネント | 変化のポイント |
|------|-------------------|----------------|
| **スパゲッティ** | なし（1 ファイルが全部） | 部品という概念自体がない |
| **MVC** | Model / View / Controller | **UI・操作・データ** を 3 つに分けた最初の型 |
| **3 層** | プレゼンテーション / ビジネス / データ層 | MVC の Model を **サーバー側の水平層** に再分割 |
| **MVP** | View / Presenter / Model | Controller を **Presenter** に特化（画面制御専用部品） |
| **DDD** | エンティティ・値オブジェクト・集約・**境界づけられたコンテキスト** | 技術の層ではなく **ビジネス概念** を部品にする |
| **MVVM** | View / ViewModel / Model | 画面用状態を担う **ViewModel** が新部品として登場 |
| **ヘキサゴナル** | Application Core / Port / Adapter | 中心の **コア** と、外側を差し替える **アダプタ** を明示 |
| **オニオン** | Domain Model / Application Service / Infrastructure | コアを **同心円の層** として名前付け |
| **クリーン** | Entities / Use Cases / Interface Adapters / Frameworks | ヘキサゴナル・オニオン・DDD の部品名を **1 セットに統合** |
| **EDA** | イベント発行者 / ブローカー / 購読者 | 部品の境界が **プロセス・サービスをまたぐ** 単位へ |
| **マイクロサービス** | 注文・在庫・ユーザー…など **独立サービス** | 1 アプリ内のモジュール → **デプロイ単位** が部品になる |

**流れの要約:** 「1 塊のコード」→「UI 用の 3 分割」→「サーバー側の層」→「ビジネス概念（ドメイン）」→「差し替え可能な外側」→「サービス単位の分割」。

### 11.2 関係性（依存・通信・データの流れ）— 「どうつなぐか」

| 段階 | 主な関係性 | 変化のポイント |
|------|-----------|----------------|
| **スパゲッティ** | どこからでもどこへも参照 | 依存の向きが **無秩序** |
| **MVC** | View ⇄ Controller ⇄ Model | **関心ごと** ごとに経路を分ける |
| **3 層** | 上の層 → 下の層（一方向呼び出し） | **層をまたぐ依存** をルール化 |
| **MVP** | View → Presenter → Model（View は受け身） | View と Model の **直接結合を禁止** |
| **DDD** | ドメインモデルが中心、コンテキスト間は明示的な連携 | 部品間の関係を **業務の境界** で定義 |
| **MVVM** | View ⇄ ViewModel（データバインディング）→ Model | **双方向の自動同期** で手動更新を減らす |
| **ヘキサゴナル** | 外側 → Port → Core（**依存の向きを逆転**） | DB・UI がコアに **直接触れない** |
| **オニオン / クリーン** | すべての依存が **内側（ドメイン）へ** | 依存逆転（DIP）を **アーキテクチャの前提** に |
| **EDA** | 発行者 → イベント → 購読者（**非同期・疎結合**） | 呼び出し元は **相手の存在を知らなくてよい** |
| **マイクロサービス** | API（同期）＋ イベント（非同期）でサービス間連携 | 関係性の単位が **プロセス境界** に拡大 |

**流れの要約:** 密結合 → 役割ごとの経路 → 層の一方向 → 内側への依存集中 → イベントによる疎結合 → 分散システム間の連携。

### 11.3 原則・制約（ルール）— 「何を守るか」

| 段階 | 主な原則・制約 | 変化のポイント |
|------|---------------|----------------|
| **スパゲッティ** | （暗黙のルールなし） | 変更の影響範囲が **予測不能** |
| **MVC** | **関心の分離** — 見た目とデータ処理を分ける | アーキテクチャの **最初の明示的ルール** |
| **3 層** | **層の責務固定** — DB はデータ層だけ、など | 「どこに何を書くか」を **チームで共有** |
| **MVP** | View は **描画だけ**、ロジックは Presenter | UI テスト可能にする **役割の縛り** |
| **DDD** | **ユビキタス言語**、境界づけられたコンテキスト | 技術ルールに加え **ビジネス用語の統一** |
| **MVVM** | View にロジックを書かない、**バインディング経由** | フレームワーク前提の **UI 更新ルール** |
| **ヘキサゴナル** | 外側は内側に合わせる、**Port 経由のみ** | インフラ差し替えを **設計段階で保証** |
| **オニオン / クリーン** | **依存は常に内側へ**、フレームワークは詳細 | 変更に強い中心（Entities）を **最優先** |
| **EDA** | **最終的整合性**、イベントは過去形で表現 | 同期処理の **即時一貫性** を手放す代わりに拡張性 |
| **マイクロサービス** | **データ所有権**、独立デプロイ、サービス自律 | チーム・リリース単位の **組織的制約** も含む |

**流れの要約:** ルールなし → 分離・層の責務 → ドメイン中心・依存逆転 → 分散環境での整合性と自律性。

### 11.4 3 要素を横断で見る — 同じ時代、何が変わったか

各アーキテクチャは、3 要素のうち **どこを主に変えたか** が異なります。

| アーキテクチャ | コンポーネント | 関係性 | 原則・制約 | 主な焦点 |
|---------------|--------------|--------|-----------|----------|
| MVC / MVP / MVVM | ◎ | ○ | ○ | **UI まわりの部品分割** |
| 3 層 | ○ | ◎ | ○ | **サーバー側の層と呼び出し方向** |
| DDD | ◎ | ○ | ◎ | **部品の意味をビジネスに合わせる** |
| ヘキサゴナル / オニオン / クリーン | ○ | ◎ | ◎ | **依存の向きと差し替え可能性** |
| EDA | ○ | ◎ | ○ | **システム間のつなぎ方** |
| マイクロサービス | ◎ | ◎ | ◎ | **3 要素すべてをサービス粒度で再定義** |

```
  コンポーネント     関係性           原則・制約
  ─────────────    ─────────────    ──────────────────
  1 塊              絡み合い          なし
    ↓ MVC           ↓ 3 経路         ↓ 関心の分離
  Model/View/…      層の一方向        層の責務
    ↓ DDD           ↓ 内側へ集中     ↓ ユビキタス言語
  ドメイン概念      Port/Adapter     依存逆転
    ↓ MS            ↓ イベント/API   ↓ データ所有権
  サービス単位      疎結合・非同期    独立デプロイ
```

> **覚え方:** 歴史上の「新しいアーキテクチャ」は、毎回 3 要素すべてを発明したわけではありません。  
> 多くは **前の時代の弱点（Controller 肥大、DB 依存、同期連鎖…）を、3 要素のどこか 1〜2 か所で補正** した結果です。  
> だから「最新＝全部が新しい」ではなく、「今の課題が 3 要素のどこにあるか」で選ぶのが実務的です。

## 12. まとめ — 歴史は「課題の積み重ね」

```
スパゲッティ
    ↓ 画面・操作・データを分ける
  MVC → MVP → MVVM        … UI まわりの進化
    ↓ サーバー側を層で整理
  3 層（→ レイヤード / N 層）
    ↓ ビジネスを中心にモデル化
  DDD
    ↓ 依存を内側へ、外側を差し替え可能に
  ヘキサゴナル → オニオン → クリーン   … モノリス内の依存管理
    ↓ システム間を疎結合に
  イベント駆動
    ↓ デプロイ・チーム単位で分割
  マイクロサービス
```

### 2 つの軸で整理すると分かりやすい

| 軸 | 該当するアーキテクチャ | 主な問い |
|----|----------------------|----------|
| **UI の分離** | MVC, MVP, MVVM | 画面とロジックをどう分けるか |
| **モノリス内の構造** | 3 層, DDD, ヘキサゴナル, オニオン, クリーン | ビジネスルールをどこに置き、何に依存させるか |
| **システム間の連携** | EDA, マイクロサービス | サービスをどう分け、どうつなぐか |

上記 3 軸は、§11 の **コンポーネント・関係性・原則** のどこを主に変えたか、という見方とも対応します（UI 分離 → 部品と関係性、モノリス内 → 関係性と原則、システム間 → 関係性と部品の粒度）。

### 初心者が覚えておくとよいこと

1. **新しいほど良いわけではない。** 小さなアプリにマイクロサービスやクリーンは不要なことが多い。
2. **組み合わせて使う。** 例: マイクロサービスの中身はクリーン + DDD、API 層は MVC、サービス間は EDA。
3. **すべてはトレードオフ。** 修正しやすさ、性能、運用コスト、チーム構成で選び方が変わる（[[02トレードオフ]]）。
