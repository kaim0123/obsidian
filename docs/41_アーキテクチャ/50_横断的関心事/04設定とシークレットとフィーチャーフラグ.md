# 設定・シークレット・フィーチャーフラグ — 概要

## この教材の目的

アプリケーションは、**環境（開発・ステージング・本番）** や **運用中の判断（機能の ON/OFF）** によって振る舞いを変える必要があります。  
これらも**どの機能にも関わる横断的関心事**です。

この教材では、

- **設定 (Configuration)** — 接続先 URL、タイムアウト、機能パラメータなど
- **シークレット (Secrets)** — パスワード、API キー、証明書など
- **フィーチャーフラグ (Feature Flags)** — デプロイと機能公開を切り離す仕組み

を、アーキテクチャの観点から**概要レベル**で整理します。

前提: [[01_横断的関心事]]、[[05BFFとAPIゲートウェイとグレースフルデグレーデーション]]、[[クリーンアーキテクチャの概要]]

---

## 1. なぜ横断的関心事か

| 例 | 影響範囲 |
|----|----------|
| DB 接続文字列 | ほぼすべての永続化処理 |
| 外部決済 API の URL | 注文・返金など複数機能 |
| 「新チェックアウト UI を有効化」 | フロント・BFF・複数 API |

設定を**コードに直書き**したり、**リポジトリに秘密情報をコミット**したりすると、環境追加・ローテーション・インシデント対応が一気に難しくなります。

---

## 2. 設定 (Configuration)

**設定**とは、**環境やデプロイごとに変わる値**のことです。ビジネスロジックそのものではなく、「どこに接続するか」「どれくらい待つか」などの**パラメータ**です。

### 2.1 設定の例

| 種類 | 例 |
|------|-----|
| インフラ | DB ホスト、Redis URL、メッセージキュー名 |
| 外部連携 | 決済・メール・地図 API のエンドポイント |
| 動作パラメータ | HTTP タイムアウト、リトライ回数、ページサイズ上限 |
| 環境識別 | `ENV=production`、ログレベル |

### 2.2 設定の置き場所（よくあるパターン）

```
  優先度（一般的なイメージ、下ほど上書きされやすい）

  デフォルト値（コード内）
       ↓
  設定ファイル（config.yaml, appsettings.json）
       ↓
  環境変数
       ↓
  実行時の設定ストア / クラウドパラメータ
```

| 方式 | メリット | 注意 |
|------|----------|------|
| **環境変数** | 12-factor アプリの定番、コンテナと相性がよい | 数が増えると管理が煩雑 |
| **設定ファイル** | 構造化しやすい、ローカル開発向き | 環境ごとにファイルを分ける |
| **専用ストア**（AWS SSM, Vault 等） | 集中管理、監査 | インフラ依存 |

アーキテクチャ上のポイント:

- **ドメイン層**に環境変数を直接読ませない — [[クリーンアーキテクチャの概要]] の「詳細は外側」に合わせ、**インフラ層または composition root** で注入する
- **設定スキーマ**を決める — 起動時に必須項目が欠けていたら**早く失敗**する（fail fast）

### 2.3 環境の分離

| 環境 | 目的 |
|------|------|
| 開発 (dev) | 個人・チームの日常開発 |
| ステージング (staging) | 本番に近い構成で結合テスト |
| 本番 (production) | 実ユーザー向け |

**本番の設定を開発に流用しない**、**本番 DB を開発から触らない** — 境界をアーキテクチャ図に明示すると事故が減ります。

---

## 3. シークレット (Secrets)

**シークレット**は、**漏洩すると被害が大きい設定**です。設定と同じ仕組みで扱うこともありますが、**より厳格な管理**が求められます。

### 3.1 シークレットの例

- DB パスワード
- JWT 署名鍵
- 外部 API のクライアントシークレット
- TLS 証明書の秘密鍵

### 3.2 やってはいけないこと

```
  ❌ ソースコードに API キーを直書き
  ❌ .env を Git にコミット（.gitignore だけに頼りすぎない）
  ❌ ログにシークレットを出力
  ❌ フロントエンド（ブラウザ）に本来サーバーだけが持つ秘密を置く
```

### 3.3 推奨される置き方（概要）

```
  アプリ起動
     │
     ▼
  シークレットストア（Vault, AWS Secrets Manager, K8s Secret …）
     │
     ▼
  環境変数またはファイルとしてマウント → アプリが読み込み
```

| プラクティス | 理由 |
|--------------|------|
| **最小権限** | 必要なサービスだけが読める |
| **ローテーション** | 漏洩時・定期で鍵を差し替え可能に |
| **コードと分離** | デプロイパイプラインまたはランタイムで注入 |

[[02認可と認証の置き方と境界とアイデンティティ]] と合わせて、**JWT の署名鍵**などは特に厳重に扱います。

---

## 4. フィーチャーフラグ (Feature Flags)

**フィーチャーフラグ**（機能フラグ）は、**コードはデプロイ済みだが、機能の ON/OFF を実行時に切り替える**仕組みです。

[[05BFFとAPIゲートウェイとグレースフルデグレーデーション]] でも、障害時に機能をリモート OFF する例が出てきました。

### 4.1 なぜ使うか

| 用途 | 説明 |
|------|------|
| **段階的リリース** | 一部ユーザーだけ新 UI を見せる（カナリア、A/B テスト） |
| **デプロイと公開の分離** | main にマージしても、フラグ OFF ならユーザーに見えない |
| **キルスイッチ** | 本番障害時に問題機能だけ即 OFF |
| **長期ブランチ回避** | 大きな機能を小さくマージし続ける |

### 4.2 ざっくりした仕組み

```
  リクエスト
     │
     ▼
  ┌─────────────────┐
  │ フラグ評価       │  ← フラグサービス / 設定
  │ newCheckout=ON? │
  └────────┬────────┘
           │
     ON ───┴─── OFF
      │          │
      ▼          ▼
  新 UI      旧 UI
```

フラグの状態は、**専用 SaaS**（LaunchDarkly 等）、**自前 DB**、**設定ファイル**などに置きます。

### 4.3 アーキテクチャ上の注意

| 良い習慣 | 悪い習慣 |
|----------|----------|
| フラグは**境界（BFF、ユースケース入口）**で評価 | ドメインの everywhere に `if (flag)` |
| **短命** — 全員 ON になったらフラグを削除 | フラグが永久に残り、分岐が増殖 |
| フラグ OFF 時の**テスト**も書く | ON のパスだけテスト |
| 監視 — フラグ切替をログに残す | 誰がいつ OFF にしたか分からない |

ドメインの**不変条件**（「締め後は変更不可」など）をフラグで無効化するのは危険です。  
フラグは**振る舞いの選択**であり、**ルールの破り方**ではありません。

## 5. 設定・シークレット・フラグの関係

```
  ┌─────────────────────────────────────────────┐
  │  非機密の設定（URL、タイムアウト、フラグ状態）  │
  ├─────────────────────────────────────────────┤
  │  シークレット（パスワード、鍵）— 別管理       │
  ├─────────────────────────────────────────────┤
  │  フィーチャーフラグ — 実行時の振る舞い切替    │
  └─────────────────────────────────────────────┘
           すべて「環境・運用」に近い横断的関心事
```

| 項目 | 変更頻度 | 典型な管理 |
|------|----------|------------|
| 設定 | デプロイ時 | 環境変数、設定ファイル |
| シークレット | ローテーション時 | シークレットマネージャ |
| フィーチャーフラグ | **実行中**も | フラグサービス、管理 UI |

---

## 6. 12-Factor App との対応（入口）

クラウドネイティブな設計では、[12-Factor App](https://12factor.net/ja/) の次の原則がよく参照されます。

- **III. 設定 (Config)** — 設定をコードから分離し、環境変数で注入
- **X. 開発環境と本番環境の等価性** — 環境差を設定で吸収

第6部では詳細まで扱いませんが、「**設定はコードに埋め込まない**」はアーキテクチャの基本です。

---

## 7. よくある誤解

| 誤解 | 実際 |
|------|------|
| .env があれば十分 | 本番では**シークレットストア**と権限管理が必要なことが多い |
| フラグ = 設定ファイル | フラグは**運用中に**切り替える用途が主 |
| フロントにフラグを置けば安全 | **サーバー側**でも検証・制御が必要な機能がある |
| 設定はインフラだけの問題 | **層の境界**（ドメインに漏らさない）も設計課題 |

---

## 8. 小さな練習

1. 自分のプロジェクトで、**環境ごとに変わる値**を3つ書き出す
2. そのうち**シークレット**に該当するものを分離し、今どこに置いているか確認する
3. 新機能を**フラグで段階公開**するなら、**どの層**で ON/OFF を判定するか決める
