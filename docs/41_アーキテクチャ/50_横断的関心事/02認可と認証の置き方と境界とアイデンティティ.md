# 認証・認可の置き方 — 境界とアイデンティティ

## この教材の目的

「ログイン機能を作る」とき、認証・認可は**1つの画面や API** に閉じた話に見えがちです。  
しかしアーキテクチャの観点では、**システム全体のどこで「誰か」を確かめ、どこで「何ができるか」を決めるか**が重要です。

この教材では、

- **認証 (Authentication)** と **認可 (Authorization)** の違い
- **アイデンティティ**（ユーザー・ロール・権限）をどう扱うか
- **境界**（ゲートウェイ、ミドルウェア、ドメイン層）への置き方の選択肢

を、初心者向けに整理します。

前提: [[01_横断的関心事]]、[[05BFFとAPIゲートウェイとグレースフルデグレーデーション]]、[[06_ドメイン層とユースケースとアプリサービス]]

---

## 1. 認証と認可を分ける

| 用語 | 英語 | 問い | 例 |
|------|------|------|-----|
| **認証** | Authentication | **誰**か | パスワード・OAuth で「この人はユーザーA」と確かめる |
| **認可** | Authorization | **何ができる**か | ユーザーAは「自分の注文だけ閲覧可、他人の注文は不可」 |

```
  リクエスト
     │
     ▼
  ┌──────────┐     成功      ┌──────────┐     成功      ┌──────────┐
  │  認証     │ ──────────→ │  認可     │ ──────────→ │  業務処理  │
  │  誰？     │             │  許可？    │             │  注文更新  │
  └──────────┘             └──────────┘             └──────────┘
     │ 失敗 → 401              │ 失敗 → 403
```

- **401 Unauthorized** — 本人確認できていない（未ログイン、トークン無効）
- **403 Forbidden** — 本人は分かったが、**その操作は許可されていない**

初心者が混同しやすいのは「ログインできたのに 403 が出る」ケースです。  
認証は通ったが**認可で弾かれている**、と切り分けます。

---

## 2. アイデンティティとは

**アイデンティティ (Identity)** とは、システムが「**誰（または何）**」としてリクエストを扱うかを表す情報です。

| 概念 | 説明 | 例 |
|------|------|-----|
| **主体 (Subject)** | 操作を行う者 | ユーザー、サービスアカウント、API キー |
| **クレーム (Claim)** | 主体についての属性 | ユーザー ID、メール、所属組織 |
| **ロール (Role)** | まとまった権限のラベル | `admin`、`member`、`guest` |
| **権限 (Permission)** | 具体的な操作の許可 | `order:read`、`order:cancel` |

### 2.1 人間とサービス

分散システムでは、主体は**人間だけ**ではありません。

- **エンドユーザー** — ブラウザやモバイルアプリから操作
- **サービス間** — 注文サービスが在庫サービスを呼ぶ（**サービスアカウント**、mTLS など）

アーキテクチャ図には「**誰が誰を呼んでいるか**」を書く習慣をつけると、認可の置き場所が見えやすくなります。

### 2.2 トークンとセッション（概要）

| 方式 | ざっくりしたイメージ | 向きやすい場面 |
|------|----------------------|----------------|
| **セッション** | サーバー側にログイン状態を保持、クライアントは Cookie で ID を送る | 従来型 Web、サーバー主導 |
| **JWT 等のトークン** | 署名付きの情報をクライアントが持ち、各 API が検証 | SPA、マイクロサービス、モバイル |

どちらも「正解」ではなく、**チームの運用・失効の要否・サービス数**で選びます。  
第6部では詳細プロトコルより、**検証をどこで行うか**に焦点を当てます。

## 3. どこに置くか — 境界の選択肢

認証・認可は横断的関心事なので、**1箇所に集約するか、層ごとに分担するか**を決めます。

### 3.1 入口で一括（ゲートウェイ・リバースプロキシ）

```
  クライアント → API ゲートウェイ（認証・レート制限）→ 各マイクロサービス
```

**メリット**

- 各サービスが認証ロジックを持たなくてよい
- ポリシー変更が一箇所で済む

**デメリット**

- ゲートウェイをすり抜ける経路（内部通信、バッチ）の扱いを別途決める必要がある
- 細かい**業務ルールの認可**（「この注文の所有者か」）はゲートウェイだけでは足りないことが多い

[[05BFFとAPIゲートウェイとグレースフルデグレーデーション]] でも触れた通り、ゲートウェイは**横断的関心事の集約点**としてよく使われます。

### 3.2 各サービス／各 API で検証

```
  クライアント → 注文 API（JWT 検証）→ 注文ドメイン
              → 在庫 API（JWT 検証）→ 在庫ドメイン
```

**メリット**

- ゲートウェイなしの構成でも成立
- サービスごとに独立デプロイしやすい

**デメリット**

- 検証ロジック・鍵の配布が**各所に散らばりやすい**
- 共通ライブラリやポリシーエンジンで**重複を抑える**設計が必要

### 3.3 ミドルウェア（フレームワークの入口）

Web フレームワークでは、**HTTP リクエストの入口**にミドルウェアを置くパターンが一般的です。

- Next.js の `middleware.ts` — [[三層アーキテクチャ]] で触れた**横断的な HTTP 前処理**
- Express / FastAPI の middleware — 認証後に `request.user` をセット

ここで行うのは多くの場合**認証**と**粗い認可**（ログイン済みか、管理者か）です。

### 3.4 ユースケース層・ドメイン層での認可

**「このユーザーはこの注文をキャンセルしてよいか」** のようなルールは、**ビジネスに近い**ため、ドメインまたはユースケース層に置くことが多いです（[[06_ドメイン層とユースケースとアプリサービス]]）。

```
  入口: トークンが有効か（認証）
       ↓
  ユースケース: 操作者は注文の所有者か（認可）
       ↓
  ドメイン: 注文はキャンセル可能な状態か（ビジネスルール）
```

**認可のうち「データと結びつく部分」** は、UI やゲートウェイだけに任せず、**ユースケースまたはドメイン**まで落とすのが安全です。  
「API ではチェックしたが、別経路からは bypass できる」という穴を防ぎやすくなります。

## 4. 置き方のパターン（まとめ表）

| レイヤー | 向いている処理 | 向いていない処理 |
|----------|----------------|------------------|
| API ゲートウェイ | 共通認証、レート制限、TLS 終端 | 注文ごとの所有者チェック |
| ミドルウェア | セッション／JWT 検証、ルート単位のロール | 複雑なドメインルール |
| ユースケース | 「この操作をしてよいか」の orchestration | トークン署名の検証（インフラ寄り） |
| ドメイン | 不変条件と一体の権限（例: 締め後は変更不可） | HTTP ヘッダの解釈 |

## 5. 分散システムでの注意点

### 5.1 信頼境界 (Trust Boundary)

**インターネット向け API** と **内部サービス間通信** では、求める認証の強さが違います。

- 外向き: ユーザー認証必須
- 内部: ネットワーク分離 + サービス認証、またはゼロトラストで再認証

「内部だから認証不要」は、漏洩時に危険です。**境界を図に書く**習慣が重要です。

### 5.2 認可情報の伝搬

BFF や API ゲートウェイを通過したあと、下流サービスに**誰が操作しているか**をどう渡すかを決めます。

- ヘッダ（`X-User-Id` など）— **改ざん防止**（ゲートウェイだけが付与、内部ネットワーク限定）
- トークンそのものを転送
- サービス間は別の**サービス用トークン**

## 6. よくある誤解

| 誤解 | 実際 |
|------|------|
| ログイン画面 = 認証設計の全部 | サービス間・バッチ・管理 API も含めて境界を決める |
| 認可はフロントで非表示にすれば足りる | **サーバー側**で必ず検証する（[[01_MVC違反とは]] の「UI だけの制御」と同根） |
| ゲートウェイですべて解決 | 業務データに依存する認可は下流にも必要 |
| ロールだけで十分 | 細かい操作単位の**権限**が必要になることが多い |

---

## 7. 小さな練習

自分の（または想像の）EC システムについて:

1. **認証**をどこで行うか（ゲートウェイ / 各 API / ミドルウェア）を1つ選ぶ
2. 「他人の注文を見られない」を**どの層**で保証するか書く
3. 注文サービス → 在庫サービスの内部呼び出しは、**誰として**認可するか考える
