# 観測性 — ログ・メトリクス・トレースとアーキテクチャ上の接点

## この教材の目的

システムが本番で動き始めると、「**今何が起きているか**」「**障害の原因はどこか**」を知る必要が必ず出てきます。  
そのための仕組みをまとめて **観測性 (Observability)** と呼びます。

この教材では、

- **ログ (Logs)**、**メトリクス (Metrics)**、**トレース (Traces)** の違い
- なぜアーキテクチャ（境界・層・サービス分割）と**設計段階**で結びつけるか
- 初心者が最初に決めておくとよい**最低限の約束事**

を整理します。

前提: [[01_横断的関心事]]、[[01_分散とスタイル]]、[[01品質属性]]（運用性・可用性）

---

## 1. 観測性とは

**観測性**とは、システムの内部状態を、**外部からの出力（ログ・メトリクス・トレース）** から推測できる度合いのことです。

監視 (Monitoring) が「**決めた指標が閾値を超えたらアラート**」に近いのに対し、観測性は「**想定外の事象**にも、データから原因をたどれる」イメージが強い言葉です。  
実務では両方セットで語られることが多いです。

アーキテクチャとの接点:

- **サービスを分けた** → 1リクエストが複数プロセスをまたぐ → **トレース ID** が必要
- **非同期（メッセージ）** → 処理のつながりが見えにくい → **相関 ID** と構造化ログ
- **レイヤーを分けた** → どの層で失敗したかをログに残す設計

[[03同期APIとメッセージとイベント駆動の概観]] でも、イベント駆動は「デバッグが難しい」と触れています。観測性はその**対症療法ではなく設計の一部**です。

## 2. 三本柱: ログ・メトリクス・トレース

| 種類 | 何を記録するか | 向いている問い | 例 |
|------|----------------|----------------|-----|
| **ログ** | 離散的なイベント・メッセージ | 「この注文 ID で何が起きた？」 | `orderId=123 cancel failed: out of stock` |
| **メトリクス** | 数値の時系列（集計） | 「今エラー率は上がっている？」 | 5xx の割合、P95 レイテンシ |
| **トレース** | 1リクエストの経路と所要時間 | 「どのサービスが遅い？」 | ゲートウェイ → BFF → 注文 → DB |

```
  1つのユーザー操作
       │
       ├─ トレース … 全体の流れと時間（スパン）
       │
       ├─ ログ … 各所での詳細イベント
       │
       └─ メトリクス … 全体の健康状態（集計）
```

### 2.1 ログ (Logs)

**テキストや JSON で「何が起きたか」を残す**ものです。

良いログの目安（初心者向け）:

- **構造化** — JSON など、機械がパースしやすい形式
- **相関 ID** — 同じリクエストを `requestId` / `traceId` でつなぐ
- **コンテキスト** — ユーザー ID、注文 ID など、調査に必要な ID
- **レベル** — DEBUG / INFO / WARN / ERROR を使い分ける

避けたい例:

- パスワード・トークン・個人情報の**平文出力**
- 「エラー occurred」のみで**原因が分からない**メッセージ

### 2.2 メトリクス (Metrics)

**数値を定期的に集計**し、ダッシュボードやアラートに使います。

| 種類 | 例 |
|------|-----|
| **カウンタ** | リクエスト総数、エラー件数 |
| **ゲージ** | 現在の接続数、キュー長 |
| **ヒストグラム** | レイテンシの分布（P50, P95, P99） |

アーキテクチャ上、**各サービスの境界**（HTTP ハンドラ、メッセージ consumer の入口）でメトリクスを取ると、「どの境界がボトルネックか」が分かりやすくなります。

### 2.3 トレース (Traces)

**1つの操作**がシステム内をどう流れたかを、**スパン (Span)** の木構造で記録します。

```
  traceId: abc-123
  ├─ span: API Gateway     12ms
  ├─ span: Order BFF       45ms
  │    ├─ span: Order Svc  30ms
  │    └─ span: Inventory  10ms
  └─ span: total           57ms
```

分散システムでは、**同じ traceId をヘッダで伝搬**するのが定番です。  
モノリスでも、リクエスト開始時に ID を発行し、ログに載せるだけで調査が楽になります。

## 3. アーキテクチャ上の「接点」

観測性は**インフラチームだけの仕事**ではなく、**サービス境界・層・通信方式**を決める段階から関わる横断的関心事です。

### 3.1 境界（Boundary）ごとに計測点を置く

```
  Client
    │  ← ここ: 外部から見たレイテンシ・エラー率
    ▼
  API Gateway
    │  ← ここ: 認証失敗、レート制限
    ▼
  Service A ──→ Service B
    │              ← ここ: サービス間呼び出しの遅延
    ▼
  Database
       ← ここ: クエリ時間、接続プール
```

C4 図やシーケンス図を描くとき、**「ここでログ／メトリクスを取る」** とメモしておくと、実装時の漏れが減ります。

### 3.2 横断的関心事としての実装

[[レイヤードアーキテクチャ]] では、ログ・認証・トランザクションを **ミドルウェアや AOP** で扱う、と説明しています。  
観測性も同様で、**各ハンドラにコピペ** するより、

- HTTP ミドルウェアで requestId 発行
- ORM / DB クライアントのフックでスロークエリログ
- メッセージ consumer の共通ラッパーで処理時間記録

のように **共通基盤** に寄せます。

### 3.3 ドメイン層と観測性の線引き

| 置き場所 | 例 |
|----------|-----|
| インフラ・ミドルウェア | HTTP ステータス、レイテンシ、DB 接続エラー |
| ユースケース | `CancelOrder` 開始・失敗・成功、ビジネス上の拒否理由 |
| ドメイン | 通常は**ログを厚くしない**（ドメインの純度）。重要イベントはドメインイベントとして発行し、別途記録も可 |

**「なぜキャンセルできなかったか」** はビジネス理由なので、ユースケースまたはドメイン近くで**意味のあるログ**を残します。  
**「DB 接続がタイムアウトした」** はインフラ寄りです。

## 4. サービス分割と観測性

### 4.1 モノリス

- **1つの traceId** で十分なことが多い
- ログ集約先（ファイル、stdout → ログ基盤）を**1プロジェクトで統一**

### 4.2 マイクロサービス

- **分散トレーシング**（OpenTelemetry など）の導入を検討
- **ログのフィールド名**（`traceId`, `spanId`, `service.name`）をチームで統一
- ダッシュボードは**サービス横断**で「ユーザー体験」が見えるように設計

### 4.3 非同期（メッセージ・イベント）

```
  API ──publish──→ Queue ──consume──→ Worker
         │                              │
         └─ messageId / correlationId を両方のログに
```

[[03同期APIとメッセージとイベント駆動の概観]] の非同期処理では、**メッセージ ID と元リクエスト ID** を対応づける設計が重要です。

## 5. SLI / SLO の入口（アーキテクチャとの関係）

本番運用では、**何をもって「正常」とするか** を数値で決めることがあります。

| 用語 | 意味 |
|------|------|
| **SLI** (Service Level Indicator) | 測る指標（可用性、レイテンシなど） |
| **SLO** (Service Level Objective) | 目標値（例: 99.9% のリクエストが 500ms 以内） |

[[01品質属性]] で書いた「測れる目標値」が、運用では SLI/SLO になります。  
アーキテクチャ選定（同期 vs 非同期、キャッシュの有無）が、**SLO を達成できるか** に直結します。

---

## 6. よくある誤解

| 誤解 | 実際 |
|------|------|
| ログを大量に出せば観測性が高い | **意味のあるフィールド** と相関 ID がないと探せない |
| メトリクスだけあれば十分 | 個別事象の調査には**ログ・トレース**も必要 |
| 本番リリース後に考えればよい | 形式・ID・計測点は**最初から**決めた方が安い |
| 観測性 = 監視ツールの導入 | ツールは手段。**何を記録するか** が設計 |

---

## 7. 小さな練習

1. 自分のプロジェクトで、**1リクエストを追う ID** はあるか確認する
2. アーキテクチャ図に **3箇所** メトリクス／ログ計測点を書き込む
3. 「注文キャンセル失敗」をログに残すなら、**どの層**で **どんなフィールド** を付けるか決める
