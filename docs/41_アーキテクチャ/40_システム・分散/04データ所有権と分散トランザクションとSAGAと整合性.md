# データ所有権、分散トランザクション、SAGA — 整合性の現実的な扱い

## この教材の目的

サービスを分けると、**データも分かれる**のが原則です。  
そのとき「モノリス時代のように、1つのトランザクションですべて成功させる」ことは**簡単ではありません**。

この教材では、

- **データ所有権**（誰が正を持つか）とは何か
- **分散トランザクション**が難しい理由（概要）
- **SAGA** という現実的な代替のイメージ
- **整合性**を「強い／弱い（最終的）」で考える入門

を、初心者向けに整理します。2PC（二相コミット）の実装詳細は扱いません。

前提: [[01_分散とスタイル]]、[[03同期APIとメッセージとイベント駆動の概観]]

---

## 1. データ所有権（Data Ownership）

### 1.1 とは

**データ所有権**とは、ある種類のデータについて、

> **「このデータの正（ソース・オブ・トゥルース）は、このサービス／コンテキストだけが持つ」**

というルールです。

```
  ┌─────────────┐         ┌─────────────┐
  │  注文サービス  │         │  在庫サービス  │
  │             │         │             │
  │  注文DB ◎   │  ──→   │  在庫DB ◎   │
  │  （注文の正）  │  参照のみ │  （在庫の正）  │
  └─────────────┘         └─────────────┘

  ◎ = そのデータを直接書き換えてよい唯一の場所
```

### 1.2 なぜ重要か

- **変更の責任**がはっきりする
- サービス同士が**同じテーブルを直接更新**しなくてよい
- [[03_境界づけられたコンテキストとコンテキストマップ]] の「誰が正を持つか」と直結する

### 1.3 よくあるアンチパターン

| アンチパターン | 問題 |
|----------------|------|
| 共有 DB | スキーマ変更が全サービスに波及、**分散モノリス**化 |
| 他サービスの DB を直接読む | 内部構造への依存、変更に弱い |
| 同じエンティティを各所にコピーして**双方向更新** | どちらが正かわからなくなる |

### 1.4 他サービスのデータが必要なとき

- **API で問い合わせる**（同期）
- **イベントでコピー（レプリカ）を持つ**（非同期、最終的整合）
- **読み取り専用のビュー**を別途用意する（CQRS の入門イメージ）

「在庫サービスのテーブルに注文サービスが JOIN する」は、所有権の原則に反しやすいです。

## 2. モノリス時代のトランザクション

1つの DB なら、よく知られた **ACID** トランザクションが使えます。

```
  BEGIN;
    INSERT INTO orders ...;
    UPDATE stock SET quantity = quantity - 1 ...;
  COMMIT;   ← 両方成功、または両方取り消し
```

**原子性（Atomicity）**: 全部成功か、全部失敗か。

サービスが分かれると、この「1つの COMMIT」が**そのままは使えなくなります**。

---

## 3. 分散トランザクションが難しい理由（概要）

### 3.1 複数の DB をまたぐ

注文サービス（注文 DB）と在庫サービス（在庫 DB）は**別のデータベース**です。  
1つの SQL トランザクションでは括れません。

### 3.2 2PC（二相コミット）のイメージ

理論上は **2 Phase Commit（2PC）** で「全部コミット」を調整できますが、

- **遅い**（複数ノードの合意が必要）
- **可用性**に弱い（コーディネータが落ちると問題）
- クラウドのマネージド DB 同士では**使えない**ことも多い

そのため、マイクロサービスでは **2PC に頼らない設計**が一般的です。

### 3.3 初心者向けの結論

> **「分散トランザクションで全部を厳密に同時成功」は、最初の選択肢にしない。**

代わりに、**ビジネスプロセスとして段階的に進め、失敗したら戻す**設計（SAGA）や、  
**少しのズレを許す**（最終的整合性）を検討します。

---

## 4. 整合性の2つのレベル

| 種類 | 意味 | 例 |
|------|------|-----|
| **強い整合性（Strong / Immediate）** | 読んだ瞬間、常に最新で矛盾がない | 1 DB 内のトランザクション |
| **最終的整合性（Eventual Consistency）** | 一時的にズレても、**時間が経てば**揃う | イベントで在庫コピーを更新 |

分散システムでは **CAP 定理**（一貫性・可用性・分区間耐性のトレードオフ）の話も出ますが、入門では次で十分です。

- **ユーザーが困るズレ**は減らす（在庫オーバー売れ）
- **許容できるズレ**は設計で明示する（ダッシュボードの数字が数秒遅れる）

[[02トレードオフ]] の「一貫性と遅延」が、ここで具体化します。

## 5. SAGA とは

### 5.1 一言で

**SAGA** は、複数ステップからなるビジネス処理を、

- 各ステップを**独立したローカルトランザクション**で実行し
- 途中で失敗したら、**既に完了したステップを打ち消す（補償）**

ことで、全体として一貫した結果に近づけるパターンです。

### 5.2 例: 注文 → 在庫確保 → 決済

**正常系**

```
  1. 注文作成（注文サービス）     ✓
  2. 在庫確保（在庫サービス）     ✓
  3. 決済（決済サービス）         ✓
  → 完了
```

**3で失敗した場合（補償）**

```
  1. 注文作成                    ✓
  2. 在庫確保                    ✓
  3. 決済                        ✗ 失敗
  ── 補償 ──
  2'. 在庫解放（在庫サービス）
  1'. 注文キャンセル（注文サービス）
```

各ステップは**自分の DB だけ**をトランザクションで更新します。  
全体の「原子性」は、**補償トランザクションのチェーン**で近似的に実現します。

### 5.3 オーケストレーションとコレオグラフィ

| 方式 | 誰が進行を管理するか | イメージ |
|------|----------------------|----------|
| **オーケストレーション** | 専用の**オーケストレータ**が順番に指示 | 指揮者がいるオーケストラ |
| **コレオグラフィ** | 各サービスが**イベント**を見て次を起こす | ダンスで互いに合わせる |

初心者は、最初は**オーケストレーション**の方が流れを追いやすいことが多いです。  
成熟すると、イベント中心の**コレオグラフィ**に寄せることもあります。

### 5.4 SAGA の現実的な注意点

- **補償は必ずしも「元に戻る」わけではない** — 決済済みの返金など、ビジネスルールが必要
- **途中状態が見える** — 「在庫は確保したが決済待ち」など、UI でどう見せるか
- **冪等性** — 同じ補償が2回走っても壊れないようにする
- **監視** — どの SAGA がどの段階で止まっているか追えるようにする

## 6. 在庫オーバー売れを防ぐ例（入門）

最終的整合性だけでは困る典型例です。

**悪い例**: 在庫のコピーを見て注文し、後からイベントで在庫を減らす → 同時注文でオーバー売れ

**現実的な対策の方向性**（概要）:

- 注文確定の**直前**に在庫サービスへ**同期で確保**（`ReserveStock`）
- 在庫サービス側で**楽観ロック／悲観ロック**や在庫引当テーブル
- **1商品の在庫**は在庫サービスだけが更新する（所有権）

「全部非同期」にしない。**お金と在庫に関わるところは強めの整合性**、がよくある落とし所です。

---

## 7. 比較: 何をいつ使うか

| やり方 | 向く場面 | 避けたい場面 |
|--------|----------|--------------|
| 1 DB トランザクション | モノリス、強い整合性が必要 | サービス境界をまたぐとき |
| 2PC 系 | レガシー統合、特定製品内 | 一般のマイクロサービス新規設計 |
| SAGA | 複数サービスにまたがる**長いビジネスフロー** | 補償が定義できない処理 |
| 最終的整合性 | 分析、通知、検索インデックス | 在庫・残高などクリティカルな読み取り |
