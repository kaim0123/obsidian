# 同期 API とメッセージ、イベント駆動の概観

## この教材の目的

サービスやモジュールを分けると、**どうやって連携するか**が設計の中心になります。

この教材では、

- **同期 API**（リクエスト／レスポンス）の特徴
- **メッセージ**（キュー・ブローカー）の特徴
- **イベント駆動**のざっくりしたイメージ
- どれをいつ選ぶかの**初心者向けの目安**

を整理します。実装の詳細（Kafka の設定など）より、**考え方の地図**を重視します。

前提: [[01_分散とスタイル]]、[[02モノリスと分散モノリスとマイクロサービスといつ分けるか]]

---

## 1. なぜ「つなぎ方」が重要か

```
  パターンA: 同期           パターンB: 非同期（メッセージ）
  
  注文 ──呼ぶ──→ 在庫       注文 ──投げる──→ [キュー] ──→ 在庫
       ←──答える──              （すぐ返る）      （後で処理）
```

同じ「在庫を減らす」処理でも、

- **呼び出し側が結果を待つか**
- **後で別のプロセスが処理するか**

で、性能・障害時の振る舞い・データの整合性が大きく変わります。

---

## 2. 同期 API（リクエスト／レスポンス）

### 2.1 どんなものか

クライアントが **HTTP / gRPC などで直接呼び出し**、応答を**待ってから**次に進む方式です。

```
  ブラウザ / 注文サービス
         │
         │  GET /stock/123  （在庫ある？）
         ▼
    ┌─────────┐
    │ 在庫API  │ ──→ 在庫DB
    └─────────┘
         │
         │  200 OK, quantity: 5
         ▼
  呼び出し元はこの結果を使って続行
```

REST API、GraphQL、内部の gRPC 呼び出しは、多くがこの**同期**モデルです。

### 2.2 メリット

- **わかりやすい** — 「呼んだら結果が返る」が直感的
- **すぐ結果が必要**な処理に向く（在庫チェックしてから注文確定、など）
- エラー処理が**その場で**できる（在庫なしなら 409 を返す）

### 2.3 デメリット

- **結合が強くなりやすい** — 在庫 API が遅い・落ちていると、注文も止まる
- **チェーンが長いと遅い** — A→B→C→D と直列に呼ぶと遅延が足される
- 呼び出し先の**負荷がピークと連動**する

### 2.4 向いている例

- ユーザーが**画面で結果を待っている**操作
- **読み取り**が中心で、少しの遅延は許容できる
- サービス数が少なく、**運用を単純に保ちたい**とき

## 3. メッセージ（非同期）

### 3.1 どんなものか

送信側は **メッセージキュー / メッセージブローカー** にメッセージを**投げる**だけで、すぐ戻ります。  
受信側（コンシューマ）が**後から**取り出して処理します。

```
  注文サービス                    在庫サービス
       │                              │
       │  「注文確定」メッセージ          │
       ▼                              │
  ┌─────────┐                         │
  │  キュー   │ ──（非同期）────────────→│ 処理
  │ RabbitMQ │                         │
  │ Kafka 等 │                         ▼
  └─────────┘                      在庫を減らす
```

代表的な製品: RabbitMQ、Amazon SQS、Apache Kafka、Google Pub/Sub など。

### 3.2 メリット

- **時間的な切り離し** — 送信側は相手がオンラインでなくても投げられる（一定期間）
- **負荷の平準化** — ピーク時にキューに溜め、後で処理
- **障害の緩和** — 一時的な障害時にリトライしやすい（設計次第）

### 3.3 デメリット

- **結果がすぐわからない** — 「在庫減ったか」は後で確認が必要
- **運用が増える** — キューの監視、デッドレターキュー、順序・重複の扱い
- **デバッグが難しい** — 処理がいつ・どこで行われたか追いにくい（[[観測性]] は第6部）

### 3.4 向いている例

- **メール送信**、**レポート生成**、**検索インデックス更新**
- ユーザーが**待たなくてよい**後処理
- ピークが激しく、**吸収バッファ**が欲しいとき

## 4. イベント駆動（Event-Driven）

### 4.1 どんなものか

ある処理が起きたとき、**「何が起きたか」という事実（イベント）** を発行し、  
**興味のある複数の購読者**がそれぞれ反応するスタイルです。

```
  注文サービス: 「OrderPlaced（注文された）」イベントを発行
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
   在庫サービス      会計サービス      通知サービス
   在庫を減らす       売上計上          メール送信
```

メッセージキューを使うことも多いですが、**イベント駆動**は特に

- **過去形の事実**を伝える（`OrderPlaced`）
- **発行者は購読者を知らない**（疎結合）
- **購読者が複数**増えやすい

という点を強調します。

### 4.2 コマンドとイベントの違い（入門）

| 種類 | 意味 | 例 |
|------|------|-----|
| **コマンド** | 「〇〇してほしい」という依頼 | `ReserveStock`（在庫を確保して） |
| **イベント** | 「〇〇が起きた」という事実 | `StockReserved`（在庫が確保された） |

コマンドは**1つの宛先**を想定しがち、イベントは**0人以上の購読者**を想定します。  
混同すると設計がぶれやすいので、名前で区別するのがおすすめです。

### 4.3 メリット

- **拡張しやすい** — 新機能は「イベントを購読するサービスを足す」だけでよいことも
- **ドメインの事実**をそのまま伝えられる（[[02_集約とエンティティと値オブジェクトとドメインイベント]] と相性がよい）

### 4.4 デメリット

- **全体の流れが見えにくい** — 誰が何に反応するか、図やドキュメントがないと迷子
- **最終的整合性**になりやすい — すぐには全部揃わない（[[04データ所有権と分散トランザクションとSAGAと整合性]]）
- **順序・重複** — 同じイベントが2回来たらどうするか、を決める必要がある

## 5. 比較表

| 観点 | 同期 API | メッセージ（非同期） | イベント駆動 |
|------|----------|----------------------|--------------|
| 応答 | すぐ返る | 後で処理 | 後で複数が反応 |
| 結合度 | やや強い | 弱め | 弱め |
| ユーザー待ち | 向く | 不向き（本体処理） | 本体は別途 |
| 障害時 | 相手次第で失敗 | キューに残せる | 同上＋購読者増 |
| 運用 | 比較的単純 | キュー監視が必要 | 同上＋可視化が重要 |

## 6. どう選ぶか — 初心者向けの目安

### 同期 API を基本にする

- チーム・サービスがまだ少ない
- ユーザーが**その場で結果**を必要とする
- **強い整合性**が必要（在庫を見てから確定、など）

### メッセージ／イベントを足す

- **後でよい処理**が明確にある
- ピーク吸収や、**呼び出し先のダウン**に耐えたい
- 1つの出来事に**複数の反応**がある（注文→在庫・会計・通知）

### ハイブリッドが現実的

多くのシステムは **同期 API ＋ イベント** の併用です。

```
  ユーザー操作
       │
       ▼
  同期 API で注文確定（すぐ OK/NG を返す）
       │
       └──→ バックグラウンドでイベント発行
                 ├── 在庫更新
                 ├── 分析用ログ
                 └── メール送信
```

「全部イベント」も「全部同期」も極端になりやすいので、**ユーザー体験が必要とする部分**で線を引くとよいです。

---

## 7. よくあるつまずき

| つまずき | 対策のヒント |
|----------|--------------|
| 同期チェーンが長すぎる | 読み取りは集約 API（[[05BFFとAPIゲートウェイとグレースフルデグレーデーション]]）、更新はイベント化を検討 |
| イベントの順序が狂う | 同じ集約 ID でパーティション、またはバージョン番号で順序制御 |
| 同じメッセージが2回来る | **冪等性**（何度処理しても同じ結果）を設計する |
| 失敗したメッセージの行き場 | デッドレターキュー、リトライ上限、アラート |

---

## 8. 小さな練習

EC サイトの「注文確定」について、次を分類してみてください。

1. **同期でやるべきこと**（ユーザーが待つ）
2. **非同期でよいこと**（後でよい）
3. **イベントとして発行するとよさそうな事実**（過去形で名前をつける）

例の答えの一例:

- 同期: 支払い可否、在庫の最終チェック、注文番号の返却
- 非同期: 配送手配、レコメンド更新、社内レポート
- イベント: `OrderPlaced`、`PaymentCaptured`
