# モノリス、分散モノリス、マイクロサービス — いつ分けるか

## この教材の目的

「モノリスは悪」「マイクロサービスが正義」という話をよく聞きますが、実際は**状況に応じた選択**です。

この教材では、

- **モノリス**、**分散モノリス**、**マイクロサービス** がそれぞれ何を指すか
- それぞれの**メリット・デメリット**
- **いつ分けるべきか**、**分けすぎないための目安**

を、初心者向けに整理します。

前提: [[01_分散とスタイル]]、[[03_境界づけられたコンテキストとコンテキストマップ]]

---

## 1. 3つのスタイルを一言で

| スタイル | 一言でのイメージ |
|----------|------------------|
| **モノリス** | 1つのアプリ・1つのデプロイ単位に、ほぼ全部入っている |
| **分散モノリス** | 見た目は複数サービスに分かれているが、**密結合で一緒にデプロイ**される |
| **マイクロサービス** | **独立してデプロイ・運用できる**小さなサービスの集まり |

重要なのは「コードが何ファイルに分かれているか」ではなく、**デプロイ・データ・チームの境界**がどう切れているかです。

---

## 2. モノリス（Monolith）

### 2.1 どんな形か

```
┌──────────────────────────────────────┐
│           1つのモノリスアプリ          │
│  ┌──────┐ ┌──────┐ ┌──────┐        │
│  │ Web  │ │ 注文  │ │ 在庫  │  …     │
│  └──┬───┘ └──┬───┘ └──┬───┘        │
│     └────────┴────────┘              │
│              │                       │
│         ┌────┴────┐                  │
│         │  1つのDB  │                  │
│         └─────────┘                  │
└──────────────────────────────────────┘
         1回のデプロイで全部更新
```

層（プレゼンテーション、ドメイン、インフラ）は分かれていても、**実行時は1プロセス・1リポジトリ・1デプロイ**なら、多くの文脈ではモノリスと呼びます。

### 2.2 メリット

- **開発が単純** — ローカルで全部動かしやすい、デバッグしやすい
- **トランザクションが楽** — 1つの DB なら ACID がそのまま使える
- **性能** — プロセス内の関数呼び出しは、ネットワーク通信より速いことが多い
- **小〜中規模チーム**に向きやすい

### 2.3 デメリット

- コードベースが大きくなると**変更の影響範囲**が読みにくい
- **スケールの単位**がアプリ全体になる（在庫だけ増やしたい、が難しい）
- チームが増えると**同じリポジトリで衝突**しやすい

---

## 3. 分散モノリス（Distributed Monolith）

### 3.1 どんな形か

```
┌─────────┐   HTTP   ┌─────────┐   HTTP   ┌─────────┐
│ 注文API  │────────→│ 在庫API  │────────→│ 会計API  │
└────┬────┘          └────┬────┘          └────┬────┘
     │                    │                    │
     └────────────────────┴────────────────────┘
              密結合・同時リリースが必要
              片方だけ変えると壊れる
```

**見た目はマイクロサービス**（API が分かれ、サーバーも分かれている）なのに、

- サービス同士が**強く依存**している
- **一緒にデプロイ**しないと動かない
- データが**共有 DB** だったり、境界が曖昧

といった状態を **分散モノリス** と呼びます。  
**「分けたつもりのモノリス」** で、ネットワークの複雑さだけ増えた、という皮肉なパターンです。

### 3.2 なぜ起きるか

- 「モダンだから」**早すぎる分割**
- 境界づけられたコンテキストを決めずに**技術単位**（レイヤーだけ）で分割
- 共有 DB を残したまま API だけ分けた

### 3.3 避けるために

- 分割前に **[[03_境界づけられたコンテキストとコンテキストマップ]]** で境界を描く
- **1サービスだけ独立してリリースできるか** を試す
- データの正を**1サービスに閉じる**（[[04データ所有権と分散トランザクションとSAGAと整合性]]）

---

## 4. マイクロサービス（Microservices）

### 4.1 どんな形か

```
┌─────────┐     ┌─────────┐     ┌─────────┐
│ 注文    │     │ 在庫    │     │ 会計    │
│ サービス │     │ サービス │     │ サービス │
└────┬────┘     └────┬────┘     └────┬────┘
     │ DB            │ DB            │ DB
   注文DB          在庫DB          会計DB

  それぞれ別チーム・別デプロイ・別スケールが可能（理想形）
```

**マイクロサービス**には厳密な定義は1つではありませんが、一般に次が重視されます。

- **独立デプロイ** — 1サービスの変更が他に強制リリースを要求しない
- **データ所有権** — 各サービスが自分のデータを所有する
- **組織との対応** — [[リバースコンウェイの法則]]（チーム構造とアーキテクチャが似る）を意識することが多い

### 4.2 メリット

- **チームの自律性** — 領域ごとに開発・リリースのペースを分けられる
- **部分的なスケール** — 負荷の高いサービスだけ増やせる
- **技術の多様性** — サービスごとに言語・DB を選べる（やりすぎ注意）

### 4.3 デメリット

- **運用が重い** — 監視、デプロイ、障害対応が複数に増える
- **分散システムの難しさ** — ネットワーク遅延、部分障害、整合性（[[04データ所有権と分散トランザクションとSAGAと整合性]]）
- **テスト・デバッグ** — エンドツーエンドで再現するのが大変

## 5. 比較表

| 観点 | モノリス | 分散モノリス | マイクロサービス |
|------|----------|--------------|------------------|
| デプロイ単位 | 1つ | 見かけは複数、実質1つ | サービスごと |
| データ | 共有しやすい | 共有しがち（問題） | サービスごとに所有 |
| 開発のしやすさ（初期） | ◎ | △ | △〜× |
| スケールの柔軟性 | △ | △ | ◎ |
| チーム拡大時の分離 | △ | × | ◎（設計が合えば） |
| 運用コスト | 低め | 高め（得しないことも） | 高め |

## 6. いつ分けるか — 実務的な目安

### 6.1 まだモノリスでよいサイン

- チームが**1〜2つ**で、コードベースを把握できている
- ドメイン境界が**まだ固まっていない**（試行錯誤の初期）
- **可用性・スケール**の要求が、1アプリで足りている
- 分割の理由が「流行っているから」だけ

> **Rule of thumb**: 最初は**モジュラーモノリス**（モノリスの中でモジュール境界をはっきり）から始め、痛みが出たら外に出す、という進化がよく使われます。

### 6.2 分けを検討するサイン

- **別チーム**が同じリポジトリで頻繁に衝突する
- **リリース周期**や**可用性要求**が領域ごとに大きく違う
- 特定の部分だけ**スケール**や**技術変更**が必要
- **境界づけられたコンテキスト**がコード上でもはっきりしている
- モノリス内の変更が、**関係ない領域に波及**し続けている

### 6.3 分けるときの進め方（概要）

1. **コンテキストマップ**で境界と関係を描く
2. **最も独立しやすい1つ**から切り出す（依存の少ないところ）
3. **データの正**を決め、共有 DB から徐々に離す
4. 切り出したサービスが**単独デプロイできる**ことを確認する

一気に10サービスにしない。**1つ成功させてから次**が安全です。

## 7. よくある誤解

| 誤解 | 実際 |
|------|------|
| モノリスはレガシー | 多くの成功プロダクトは長くモノリスで運用されている |
| 小さいほどサービス数を増やす | 小さすぎるサービスは運用負荷だけ増える |
| API を分ければマイクロサービス | デプロイとデータの独立性がなければ分散モノリスになりやすい |
| 分ければ必ず速くなる | ネットワーク往復が増え、遅くなることもある |

---

## 8. 小さな練習

1. 自分の（または想像の）システムを **3〜5個の業務領域** に分けて書く
2. 今は **1リポジトリか、複数か** をメモする
3. 各領域について「**単独でリリースできるか**」「**DB を共有しているか**」を Yes/No で答える
4. No が多いのに複数 API があるなら、**分散モノリス**の可能性を疑う
