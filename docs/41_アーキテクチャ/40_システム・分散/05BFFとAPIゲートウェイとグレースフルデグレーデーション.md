# BFF、API ゲートウェイ、グレースフルデグレーデーション

## この教材の目的

サービスが増えると、**クライアント（ブラウザ・アプリ）から見た入口**と、**障害時の振る舞い**が重要になります。

この教材では、

- **BFF（Backend for Frontend）** とは何か
- **API ゲートウェイ** とは何か、BFF との違い
- **グレースフルデグレーデーション** — 一部が壊れても可能な範囲でサービスを続ける

を、初心者向けに整理します。

前提: [[01_分散とスタイル]]、[[03同期APIとメッセージとイベント駆動の概観]]

---

## 1. なぜ「入口」が増えるのか

マイクロサービスをそのままフロントから呼ぶと、次の問題が出ます。

```
  スマホアプリ ──→ 注文API
              ├──→ 在庫API
              ├──→ 会員API
              ├──→ おすすめAPI
              └──→ レビューAPI

  × 呼び先が多すぎる
  × 認証を各所で繰り返す
  × 画面1枚分のデータを集めるのにクライアントが頑張る
```

**入口を1か所（またはクライアント種別ごと）にまとめる**パターンが BFF や API ゲートウェイです。

## 2. API ゲートウェイ

### 2.1 とは

**API ゲートウェイ**は、クライアントとバックエンドの**前に立つ単一の入口**です。

```
                    ┌─────────────────┐
  クライアント ──────→│  API ゲートウェイ  │──────→ 各マイクロサービス
                    └─────────────────┘
                           │
                    ・ルーティング
                    ・認証・レート制限
                    ・SSL 終端
                    ・ログ・メトリクス
```

代表的な製品: Kong、AWS API Gateway、Azure API Management、Envoy など。

### 2.2 主な役割

| 役割 | 説明 |
|------|------|
| **ルーティング** | `/orders` → 注文サービス、`/stock` → 在庫サービス |
| **横断的関心事** | 認証、レート制限、CORS、HTTPS |
| **集約（限定的）** | 複数サービスの結果をまとめて返すこともある |
| **保護** | 内部サービスを直接インターネットに晒さない |

ゲートウェイは**インフラ寄りの横断レイヤ**として使われることが多いです。

### 2.3 注意点

- ゲートウェイに**ビジネスロジックを詰め込みすぎない** — 太るとボトルネック・変更の塊になる
- **単一障害点**になりうる — 冗長化・ヘルスチェックが必要

## 3. BFF（Backend for Frontend）

### 3.1 とは

**BFF** は、**特定のフロントエンド（Web、モバイル、管理画面など）向けに最適化したバックエンド**です。

```
  ┌──────────┐     ┌─────────┐
  │ Web ブラウザ│ ──→ │ Web BFF  │ ──┐
  └──────────┘     └─────────┘   │
                                  ├──→ 注文・在庫・会員 …
  ┌──────────┐     ┌─────────┐   │
  │ モバイルアプリ│ ──→ │ Mobile BFF│ ──┘
  └──────────┘     └─────────┘
```

同じ「商品詳細ページ」でも、

- Web は SEO 用の HTML と多めの情報
- モバイルは軽量 JSON と画像サイズ違い

など、**画面の要望が違う**ときに BFF が効きます。

### 3.2 主な役割

| 役割 | 説明 |
|------|------|
| **API の集約** | 画面に必要なデータを**1リクエスト**で返す |
| **レスポンスの整形** | フロントに不要なフィールドを落とす |
| **フロント特化のロジック** | 表示順、ページネーション、キャッシュ戦略 |
| **バックエンドの変更を隠す** | 内部サービスの分割・統合をフロントから切り離す |

### 3.3 API ゲートウェイとの違い（ざっくり）

| 観点 | API ゲートウェイ | BFF |
|------|------------------|-----|
| 主な目的 | 横断的関心事、ルーティング | **画面・クライアント向け**の API 設計 |
| 誰が書くか | インフラ／プラットフォーム寄り | **フロントチーム**やその近くのチーム |
| ロジック | 薄いのが理想 | 集約・整形のロジックを持つ |
| 個数 | しばしば1つ（環境ごと） | **クライアント種別ごと**に複数ありうる |

実務では **ゲートウェイの内側に BFF がある**構成もよくあります。

```
  クライアント → API ゲートウェイ（認証・レート制限）→ BFF → マイクロサービス
```

## 4. グレースフルデグレーデーション

### 4.1 とは

**グレースフルデグレーデーション（Graceful Degradation）** とは、

> システムの**一部が故障・遅延**していても、**可能な範囲で主要機能を続け**、  
> 壊れた部分だけ機能や品質を**段階的に落とす**設計・運用の考え方です。

「全部動くか、全部落ちるか」の二択を避けます。  
可用性（[[01品質属性]]）に直結するテーマです。

### 4.2 例

| 障害 | デグレードの例 |
|------|----------------|
| おすすめ API が落ちた | 商品一覧は表示するが、**おすすめ欄だけ非表示** |
| レビュー API が遅い | **タイムアウト後はレビューなし**でページ表示 |
| 在庫 API が落ちた | **購入ボタンを無効化**（在庫不明で売らない） |
| 決済が落ちた | 注文は受け付けず、**はっきりエラー**（ここはデグレードしない） |

**何を落としてよいか**はビジネス判断です。  
「おすすめがなくても買える」は OK、「在庫不明のまま売る」は NG、というように**優先度**を決めます。

### 4.3 実装のヒント（概要）

| 手法 | 説明 |
|------|------|
| **タイムアウト** | 遅い依存を待ち続けない |
| **サーキットブレーカー** | 連続失敗したら一時的に呼び出しを止める |
| **フォールバック** | キャッシュ、デフォルト値、簡略版レスポンス |
| **機能フラグ** | 障害時に該当機能をリモートで OFF |
| **Bulkhead（隔壁）** | スレッドプールを分け、1つの遅延が全体を塞がない |

BFF やゲートウェイは、**集約時にタイムアウトとフォールバック**を入れやすい場所です。

### 4.4 ユーザー体験

- **何が使えないか**を可能なら伝える（「おすすめを読み込めませんでした」）
- **サイレントに壊れる**より、制御された劣化の方が信頼されやすい
- クリティカルパス（ログイン、決済、在庫）は**デグレードではなく明確な失敗**も選択肢

## 5. 3つをまとめて見る図

```
                         障害時: おすすめだけ省略
                              ↓
  ┌────────┐    ┌──────────────┐    ┌─────────┐    ┌──────────┐
  │  Web   │───→│ APIゲートウェイ  │───→│ Web BFF │───→│ 注文・在庫 │
  │  画面   │    │ 認証・レート制限  │    │ 画面用集約 │    │ サービス  │
  └────────┘    └──────────────┘    └────┬────┘    └──────────┘
                                         │
                                         └──→ おすすめ（タイムアウト時スキップ）
```

## 6. よくある誤解

| 誤解 | 実際 |
|------|------|
| BFF = ゲートウェイ | 役割が違う。併用は多い |
| ゲートウェイですべて集約 | 集約しすぎると BFF 相当の太さになり、変更が重い |
| デグレード = エラーを隠す | **意図した劣化**であり、監視とログは必要 |
| 全部フォールバック | 在庫・決済などは**失敗を明示**した方が安全なことも |

---

## 7. 小さな練習

自分の（または想像の）EC のトップページについて:

1. **必須のデータ**（なくたらページ自体を出せない）は何か
2. **あればよいデータ**（おすすめ、バナー、レビュー件数など）は何か
3. BFF を置くとしたら、**1 API で何をまとめて返す**か

必須と任意を分けるだけで、グレースフルデグレーデーションの設計がしやすくなります。
