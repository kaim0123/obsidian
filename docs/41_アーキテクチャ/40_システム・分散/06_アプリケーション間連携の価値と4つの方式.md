## 1. ほかのアプリケーションとの連携が価値を高める

業務アプリは単独では完結しにくく、次のような接続で価値が増えます。

| 接続の例 | 得られるもの |
|----------|--------------|
| 会計・在庫・顧客管理をつなぐ | 手入力の二重化を減らし、事実を一箇所から広げる |
| 外部サービス（決済・配送・認証）を使う | 自前実装しない専門機能を取り込める |
| 他チームのサービスを呼ぶ | 組織の境界をまたいで機能を組み立てられる |

連携の設計は「便利な接続」だけでなく、**変更の影響範囲・障害の伝播・データの正しさ** を決める判断でもあります。

---

## 2. アプリケーションを連携する4つのやり方

| 方式 | イメージ | 強み | 弱み・注意 |
|------|----------|------|------------|
| **共有データベース** | 複数アプリが同じ表を読む／書く | 実装が単純に見えやすい | スキーマ共有＝強い結合。独立デプロイが崩れる |
| **ファイル転送** | CSV／バッチファイルの受け渡し | 疎結合・監査しやすい | 遅延が大きい。スキーマ合意と失敗時の再送が要る |
| **リモート呼び出し（Web API など）** | HTTP などで要求し応答を待つ | リアルタイム、契約を明示しやすい | 相手の稼働に依存。タイムアウト・冪等が要る |
| **メッセージング** | キュー／トピックに投げて後で処理 | 時間・障害の切り離し | 結果整合性・順序・重複配信の設計が要る |

```text
  共有DB ── スキーマで強く結ぶ
  ファイル ── 時間をずらして渡す
  Web API ── 今すぐ答えてもらう
  メッセージ ── 出来事を渡して任せる
```

現代のオンライン連携の中心は **Web API** と **メッセージング** です。詳細比較は [[03同期APIとメッセージとイベント駆動の概観]]、HTTP 契約は [[01_HTTPの基本]]、発展の仕方は [[04_発展性のあるAPI開発]]、複雑化への対処は [[07_複雑なアプリケーション間連携]]。

---

## まとめ

- 連携はアプリの価値を広げるが、結合の形を選ぶ設計である  
- 4方式（共有DB／ファイル／リモート呼び出し／メッセージ）のトレードオフを意識する  
- まずは Web API の約束事を押さえ、必要に応じて非同期へ広げる
