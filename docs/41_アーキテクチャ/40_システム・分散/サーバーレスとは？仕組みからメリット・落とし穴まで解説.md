## 詳しい要約

**テーマ：サーバーレスは「サーバー管理をクラウドに任せる」仕組みで、向き不向きを理解して選ぶもの**

サーバーレスはサーバーをなくすのではなく、構築・監視・パッチ適用・スケーリングといった管理をクラウドに任せ、必要なときだけ処理を実行する仕組み。インフラ管理不要・自動スケーリング・従量課金・開発スピードという 4 つのメリットがある一方、コールドスタートや実行時間制限などの落とし穴もあり、小さく段階的に導入するのがよい、という話。

---

### 第1章 サーバーレスとは何か

- 従来はサーバー構築、OS インストール、ミドルウェア設定、デプロイ、監視、セキュリティパッチ、スケーリングなど、アプリと関係ない作業が大量に発生していた。
- サーバーレスはこれらを**クラウドに任せる**仕組み。サーバーは存在するが自分で管理しなくてよい。
- 代表例：**AWS Lambda、Google Cloud Functions、Azure Functions**。

### 第2章 サーバーレスの仕組み

- 従来は注文がなくても 24 時間サーバーを起動しておく必要があった。サーバーレスは**リクエストが来た瞬間だけ起動**し、処理が終わったら消える。
- サーバーレスは処理の実行部分の話で、データは別に保存する。DB もマネージドサービス（DynamoDB、Firestore）を使うことが多い。
- EC サイトの例：注文ボタン → **Lambda** が起動して注文処理 → **DynamoDB** に注文データを保存し在庫を減らす → **S3** に領収書 PDF を保存 → Lambda は消える。処理・データ・ファイルで役割を分けて組み合わせる。

### 第3章 なぜ注目されているのか

- 従来は構築・監視・パッチ適用・障害対応・スケーリングを全部自前でやる必要があり、特に**小さなチームやスタートアップ**には負担が大きい。
- サーバーレスならエンジニアはアプリのコードに集中できる。Netflix、コカ・コーラ、iRobot など大企業でも採用が進んでいる。

### 第4章 4つのメリット

1. **インフラ管理が不要**
2. **自動スケーリング**：アクセスが急増しても自動で対応し、サーバーが落ちる心配がほぼない。
3. **従量課金**：リクエストがなければコストはほぼ 0。平日日中しか使わない社内システムなら夜間・休日のコストが丸ごと節約できる。
4. **開発スピード向上**：インフラ設定に時間を取られず、プロトタイプを素早く作れる。

### 第5章 5つの落とし穴

1. **コールドスタート**：久しぶりのリクエストでは起動に数百ミリ秒〜数秒かかることがあり、リアルタイム性が必要なシステムで問題になる。
2. **実行時間の制限**：AWS Lambda は 1 回最大 **15 分**。動画エンコード、大量データの一括処理、機械学習のトレーニングには不向き。
3. **デバッグの難しさ**：ローカルで完全再現しにくく、ローカルとクラウドで挙動が違うこともある。ログ追跡も手間。
4. **ベンダーロックイン**：Lambda から Cloud Functions への移行は仕様が違い書き直しが必要。
5. **コストの罠**：リクエスト数が膨大だと従来のサーバーより高くつくことがある。

### 第6章 向いている場面・向かない場面

| 向いている | 向かない |
|---|---|
| API のバックエンド | 長時間処理（動画処理・大規模データ変換） |
| イベント駆動処理（画像アップロード時のリサイズ、ファイル保存時のメール通知） | リアルタイム通信（チャット、オンラインゲームなど常時接続） |
| 定期バッチ（15 分以内に終わるレポート生成・集計） | 24 時間常に高負荷のシステム（コスト高） |
| MVP 開発 | |

### 第7章 どう始めるか

- いきなり本番システムをサーバーレスにせず、問い合わせフォーム送信、画像リサイズ、定期データ取得などの**小さな処理**を Lambda で試す。
- 既存システムは全部置き換えず、通知機能だけ切り出すなど**一部から段階的に**導入する。
- 学習は AWS 公式ドキュメントとハンズオン。無料枠で実際に動かし、コールドスタート・ログ・コストを体感する。

### まとめ

- サーバーレスは「サーバー管理をクラウドに任せる」仕組みで、データ保存はマネージド DB・ストレージと組み合わせる。
- メリットだけでなく落とし穴も理解して選ぶ。万能ではない。
- 全部をサーバーレスにせず、合う部分から小さく始める。
