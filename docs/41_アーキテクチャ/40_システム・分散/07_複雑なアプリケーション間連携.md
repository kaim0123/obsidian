# 複雑なアプリケーション間連携

> [!abstract] この記事で分かること
> - 共通部分と個別対応を分けて連携を複雑化させない考え方

>

---

## 1. 共通部分と個別対応部分を明確にする

連携先が増えると、「全部入りアダプタ」や「相手ごとのコピー＆ペースト」に分かれやすいです。

| 置き場所 | 例 |
|----------|-----|
| **共通** | 認証方式、エラー形式、ページネーション、相関 ID、リトライ方針 |
| **個別** | 相手固有のフィールド名、業務ルールの差、特別な補償処理 |

共通をガイドライン／共有ライブラリ／API ゲートウェイに寄せ、個別はアダプタや BFF に閉じます（[[05BFFとAPIゲートウェイとグレースフルデグレーデーション]]・[[03_チームでAPI設計を守る]]）。

コンテキスト間の「翻訳」が必要なときは、共有カーネルを広げすぎず、**腐敗防止層** や明示マッピングで個別を隔離します（[[03_境界づけられたコンテキストとコンテキストマップ]]）。

---

## 2. API を進化させる

複雑な連携ほど、最初の契約を壊さず育てる必要があります。

- 単純な CRUD／参照から始め、利用を見て足す → [[04_発展性のあるAPI開発]]・[[03_APIの進化と運用]]  
- 破壊的変更はバージョンと移行期間で扱う → [[01_バージョニング]]・[[02_後方互換性]]  

「相手が増えたから巨大エンドポイントを1つ足す」より、**中核 API の組み合わせ** や複合サービスの層で伸ばす方が、個別対応の爆発を抑えやすいです。

---

## 3. 小さなアプリケーションに分けて組み合わせる

連携が複雑になったサインとして、次があります。

- 1プロセスに無関係な相手向けロジックが同居する  
- デプロイ単位と変更理由が一致しない  
- 障害時に全体が止まる  

そのときは、境界づけられたコンテキストやサービス分割で **小さく分け、API／メッセージで組み合わせる**（[[02モノリスと分散モノリスとマイクロサービスといつ分けるか]]）。分けすぎると分散のコストが勝つので、連携の痛みが分割の根拠になっているかを見る。

---

## 4. 複雑なデータの交換

| 課題 | 方針の例 |
|------|----------|
| 巨大ペイロード | 参照用 ID＋取得 API、ページネーション、非同期ジョブ |
| 相手ごとに形が違う | アダプタで自ドメインの形に変換（[[10_ドメインオブジェクトとWeb API]]） |
| 途中失敗 | 冪等キー、補償、アウトボックス（[[04データ所有権と分散トランザクションとSAGAと整合性]]） |

ドメインイベントを連携単位にすると、会話が「画面項目」ではなく「起きたこと」に揃いやすいです（[[02_ドメインイベントとシステム連携]]）。

---

## 5. 非同期メッセージングを使った連携

同期 Web API だけでは、次が辛くなります。

- 相手の遅延・停止が自分のレスポンス時間に直結する  
- 一対多への通知・後続処理の扇出  
- ピーク時の負荷平準化  

メッセージング（キュー／トピック）は、**時間と障害を切り離す** 連携です。概観は [[03同期APIとメッセージとイベント駆動の概観]]、実装寄りの入口は [[メッセージキューとは]]・[[MOC_分散システム体系]] のメッセージング節。イベント駆動の判断は [[03_イベント駆動の実践判断]]。

増田本の立場も、複雑になったら同期一辺倒にせず、非同期を選択肢に入れる、という整理です。

---

## まとめ

- 共通と個別を分け、個別をアダプタに閉じる  
- API は進化させ、巨大化より組み合わせで伸ばす  
- 必要なら小さく分けてつなぐ。データ交換は ID・変換・冪等で複雑さを抑える  
- 切り離しが要る箇所はメッセージング
