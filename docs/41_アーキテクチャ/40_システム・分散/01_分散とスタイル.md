# 分散とスタイル — 第5部の入口

## この教材の目的

これまでの第2〜4部では、**1つのアプリケーション（モノリス）の中**で、層の分け方やドメインの置き方を学んできました。

第5部では視点を広げ、**複数の部品・複数のサーバーにまたがるシステム**をどう設計するかを扱います。

- モノリスとマイクロサービス、**いつ分けるか**
- 同期 API とメッセージ、イベント駆動
- データの持ち主、分散トランザクション、SAGA
- BFF、API ゲートウェイ、グレースフルデグレーデーション

この第5部は**概要レベル**です。各トピックを深掘りする前に、「全体の地図」と「初心者がつまずきやすいポイント」を押さえることを目的にしています。

前提として [[03_境界づけられたコンテキストとコンテキストマップ]] や [[01品質属性]] を読んでおくと、「なぜ分けるのか」「何を犠牲にするのか」がつかみやすくなります。

---

## 1. 第5部で扱う「分散」とは

**分散**とは、システムの部品が**複数のプロセス・複数のマシン・複数のチーム**に分かれている状態です。

```
  ユーザー
     │
     ▼
┌─────────┐     ┌─────────┐     ┌─────────┐
│ Web API │────→│ 注文    │────→│ 在庫    │
│         │     │ サービス │     │ サービス │
└─────────┘     └─────────┘     └─────────┘
     │               │               │
     └───────────────┴───────────────┘
              それぞれ別 DB を持つこともある
```

1台のサーバーで全部動く**モノリス**も「分散していない」と言います。  
部品を**別プロセス・別リポジトリ・別デプロイ単位**に分け始めると、設計の論点が一気に増えます。

---

## 2. なぜ第5部を学ぶのか

分散にすると、次のような**新しい課題**が出てきます。

| 課題 | ざっくりした問い |
|------|------------------|
| 通信 | 同期で呼ぶか、メッセージで渡すか |
| データ | 誰が正（ソース・オブ・トゥルース）を持つか |
| 整合性 | 複数サービスをまたぐ処理をどう「まとめて成功」させるか |
| 障害 | 一部が落ちたとき、全体を落とさないか |
| 境界 | フロント向け API をどこに置くか |

「マイクロサービスにすれば楽になる」わけではありません。  
**トレードオフを理解したうえで、意図的に選ぶ**のがアーキテクチャの仕事です（[[02トレードオフ]]）。

## 3. この第5部の読み方

```
  01_分散とスタイル（このノート）
       │
       ├─→ 02 モノリス・分散モノリス・マイクロサービス … スタイルの選び方
       │
       ├─→ 03 同期 API とメッセージ・イベント駆動 … つなぎ方の概観
       │
       ├─→ 04 データ所有権・SAGA・整合性 … データを分けたときの現実
       │
       └─→ 05 BFF・API ゲートウェイ・グレースフルデグレーデーション … 入口と障害時
```

**02 → 03 → 04 → 05** の順がおすすめです。  
すでにマイクロサービスを触っている場合は、04（データと整合性）から入っても構いません。

---

## 4. 初心者が覚えておきたい3つのこと

1. **最初はモノリスでよいことが多い** — 分ける理由がはっきりするまで、無理に分割しない（[[02モノリスと分散モノリスとマイクロサービスといつ分けるか]]）
2. **分散トランザクションは難しい** — 「全部同時に成功」を厳密に保つのはコストが高い。現実的な落とし所を知る（[[04データ所有権と分散トランザクションとSAGAと整合性]]）
3. **障害は前提** — 一部が死んでも、可能な範囲でサービスを続ける設計を考える（[[05BFFとAPIゲートウェイとグレースフルデグレーデーション]]）
