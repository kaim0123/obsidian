# アーキテクチャに効く原則

## この教材の目的

アーキテクチャの判断には、**個別ケースを越えて普遍的に効く原則**があります。
それらの原則は、

- 品質属性が衝突したとき、**どちらを取るかの判断軸**になる
- 新しい状況に出会ったとき、**ゼロから考えるよりも早く正解に近づける**
- チーム内の議論で、**共通言語**として使える

という意味で、アーキテクチャの**地図とコンパス**のような役割を果たします。

この教材では、特にアーキテクチャレベルで効く3つの原則、

1. **関心の分離 (Separation of Concerns)**
2. **凝集度 (Cohesion) と結合度 (Coupling)**
3. **不変条件の境界**

を、初心者でも実装に活かせる形で解説します。
前提として [[01_ソフトウェアアーキテクチャとは]]、[[01品質属性]]、[[02トレードオフ]] を読んでおくと理解が深まります。

---

## 1. なぜ「原則」を持つのか

「原則を覚えても、現場では結局ケースバイケースでは？」と思うかもしれません。
それでも原則を持つ理由は、次の3つです。

1. **判断の速度が上がる**：毎回ゼロから悩まなくて済む
2. **判断の一貫性が保たれる**：人やタイミングで結論がブレにくい
3. **議論の言語が揃う**：レビューで「ここは凝集度が低い」と一言で伝わる

逆に言うと、**原則は教義ではない**ので、

- 状況に応じて**重みを変える**
- 別の原則と**衝突したら優先順位で判断する**

という姿勢が大切です（これも一種の[[02トレードオフ|トレードオフ]]です）。

## 2. 関心の分離 (Separation of Concerns)

### 2.1 一言での意味

**関心の分離**とは、

> **異なる目的・関心を、別々の場所に分けて書く**

という考え方です。「**1つの場所では1つの関心だけを扱う**」と言い換えてもOKです。

### 2.2 具体例

たとえば、Webアプリで商品を表示する処理を考えます。**関心**としては、

- **データを取ってくる関心**（DBアクセス）
- **データを加工する関心**（ビジネスロジック）
- **画面に表示する関心**（HTMLレンダリング）

があります。これらを**1つの巨大な関数**に書くと、

- **読みにくい**（何の処理か追いにくい）
- **テストしにくい**（DBが必要、画面も必要）
- **再利用しにくい**（別の画面でロジックだけ使えない）
- **変更が波及する**（画面の変更でDBクエリのテストまで影響）

逆に、3つの関心を別々の関数／クラス／モジュールに分けると、

- **1ヶ所の変更**が他に波及しない
- **個別にテスト**できる
- **別の場面で再利用**できる

ようになります。

### 2.3 アーキテクチャでの現れ方

関心の分離は、

- **層構造**（プレゼンテーション・業務・データ）
- **モジュール分割**（ユーザー機能・決済機能・通知機能）
- **マイクロサービス**（サービスごとに独立した責任）

など、**アーキテクチャレベルのほぼ全ての分け方**の根底にある原則です。
詳しくは姉妹フォルダ `03_設計/01_原則/02_関心の分離.md` も参照してください。

## 3. 凝集度 (Cohesion)

### 3.1 一言での意味

**凝集度**とは、

> **1つのモジュール（クラス・パッケージ・サービス）の中で、要素同士がどれくらい強く結びついているか**

を表す尺度です。

- **凝集度が高い**：モジュール内の要素が**同じ目的のために**集まっている → 良い
- **凝集度が低い**：モジュール内に**目的の違う要素**が混在している → 悪い

### 3.2 具体例

「凝集度が低いクラス」の例：

```
class Utility {
    formatDate(date) { ... }
    sendEmail(to, body) { ... }
    calculateTax(amount) { ... }
    validatePassword(pw) { ... }
}
```

このクラスは「**何でも屋**」で、それぞれの関数に共通の目的がありません。

「凝集度が高いクラス」の例：

```
class TaxCalculator {
    calculateConsumptionTax(amount) { ... }
    calculateIncomeTax(income, deductions) { ... }
    formatTaxAmount(amount) { ... }
}
```

このクラスは「**税金の計算**」という1つの目的に揃っています。

### 3.3 高凝集が嬉しい理由

- **変更の影響が局所化**する：このモジュール以外を見なくていい
- **意味が分かりやすい**：名前で何の責任か説明できる
- **再利用しやすい**：機能が独立している

## 4. 結合度 (Coupling)

### 4.1 一言での意味

**結合度**とは、

> **モジュール同士がどれくらい強く依存し合っているか**

を表す尺度です。

- **結合度が低い**（疎結合）：互いに**ほぼ独立**している → 良い
- **結合度が高い**（密結合）：互いに**深く依存**している → 悪い

### 4.2 具体例

「密結合」の例：

```
class OrderService {
    submit(order) {
        // MySQL の具体的なクラスに直接依存
        const conn = new MySQLConnection("localhost", "root", ...);
        conn.execute("INSERT INTO orders ...");
        // SendGrid の具体的なクラスに直接依存
        const mailer = new SendGridClient("api-key");
        mailer.send(order.userEmail, "ご注文ありがとうございます");
    }
}
```

このクラスは MySQL と SendGrid の**具体的な実装**にがっつり依存しています。
DB を PostgreSQL にしたい、メール送信を AWS SES にしたい、と思った瞬間に**書き換え範囲が広く**なります。

「疎結合」の例：

```
class OrderService {
    constructor(repo, mailer) {
        this.repo = repo;       // インターフェースとして受け取る
        this.mailer = mailer;   // インターフェースとして受け取る
    }
    submit(order) {
        this.repo.save(order);
        this.mailer.send(order.userEmail, "ご注文ありがとうございます");
    }
}
```

このクラスは「**保存できる何か**」「**メールを送れる何か**」にしか依存していません。
具体的な実装を**差し替え可能**で、テストでは**偽物**を渡すこともできます。

### 4.3 疎結合が嬉しい理由

- **変更が他のモジュールに波及しない**
- **テストしやすい**（依存先を偽物に置き換えられる）
- **再利用しやすい**

---

## 5. 高凝集・疎結合 — 2つの原則はセット

凝集度と結合度は、**良い構造の2軸**として、必ずセットで語られます。

> **高凝集・疎結合 (High Cohesion, Loose Coupling)**

を目指すのが、モジュール分割の鉄則です。

| パターン | 凝集度 | 結合度 | 評価 |
|---|-------|-------|-----|
| ① | 高い | 低い | 良い（理想） |
| ② | 高い | 高い | 部品は良いが、つなぎ方が悪い |
| ③ | 低い | 低い | バラバラに集めただけ |
| ④ | 低い | 高い | 最悪（大泥団子） |

詳しくは `03_設計/07_依存関係/03_疎結合と高凝集.md` も参照してください。

## 6. 不変条件の境界

### 6.1 一言での意味

**不変条件 (Invariant)** とは、

> **常に成り立っていなければならない条件**

のことです。

例：

- 「**注文の合計金額は0以上**」
- 「**ユーザーのメールアドレスは一意**」
- 「**口座残高は引き出し金額以上**でないと出金できない」

これらが**どこかで破られる**と、システムは矛盾した状態になります。

### 6.2 不変条件は「境界」とセット

不変条件を守るためには、**それが必ず守られる場所（境界）**を決める必要があります。

例：「注文の合計金額は0以上」という不変条件を守るには、

- **どこで**この条件をチェックするか？
- **そこを通らない経路**で値が書き込まれないか？

を設計する必要があります。

これを**不変条件の境界**と呼びます。

### 6.3 アーキテクチャでの現れ方

- **集約 (Aggregate)**（DDDの概念）：不変条件を守る単位
- **トランザクション境界**：DBレベルで原子性を担保する範囲
- **モジュール／サービスの境界**：外部から見たときに常に整合が取れている範囲

「**この境界の中では、必ずこの条件が守られている**」と言える設計は、**外側から安心して呼び出せる**部品になります。

逆に、不変条件をチェックする場所が**バラバラに散っている**と、

- どこかで**チェック漏れ**が起きる
- 直しても**他の経路では効いていない**
- バグが**再発し続ける**

ことになります。

## 7. 3つの原則の関係

3つの原則は**独立**ではなく、**お互いに支え合っています**。

- **関心の分離**：何を分けるかの**指針**
- **凝集度・結合度**：分けた結果の**評価尺度**
- **不変条件の境界**：分け方を決めるときの**制約**

具体的には、

> **同じ不変条件を守る要素は、同じモジュールにまとめる（高凝集）。
> 別の関心は、別のモジュールに分ける（関心の分離）。
> 分けたモジュール同士は、最小限のインターフェースだけで繋ぐ（疎結合）。**

これが、ほとんどのアーキテクチャパターンの**根っこ**にある考え方です。

---

## 8. SOLID などとの位置づけ

SOLID 原則（特に SRP — 単一責任の原則）は、**クラスレベル**でこれらの原則を実践するためのガイドラインです。

| レベル | 主な原則 |
|--------|---------|
| アーキテクチャ（広い） | 関心の分離、不変条件の境界 |
| モジュール／パッケージ | 高凝集・疎結合 |
| クラス | SOLID（特にSRP）、デメテルの法則 |
| 関数・メソッド | DRY、KISS、YAGNI |

「**どのレベルの話をしているか**」を意識すると、原則同士が衝突して見える場面でも、**役割分担**として理解できます。
詳しくは `03_設計/01_原則/` の各ノートを参照してください。

## 9. ありがちな誤解

### 9.1 「原則は絶対」

**誤りです。**
原則同士は時に衝突します。**現場ではトレードオフ**になり、状況に応じて重みづけが必要です。

### 9.2 「分ければ分けるほど良い」

**誤りです。**
細かく分けすぎると、

- 変更のたびに**多数のモジュールに手を入れる**必要が出る
- 全体像が**追いにくくなる**

逆効果になります。「**変更が同じ理由で起きる単位**」で分けるのが目安です。

### 9.3 「凝集度・結合度は数値で測れる」

**ある程度測れますが、究極的には設計判断です。**
ツールが出す数値（クラス間の依存数など）は参考になりますが、**意味的な凝集度**は人が判断するものです。

---

## 10. まとめ

- アーキテクチャに効く原則として、**関心の分離・凝集度・結合度・不変条件の境界**の3グループがあります。
- **関心の分離**は、異なる目的を**別の場所**に書く指針。
- **凝集度**はモジュール内のまとまりの強さ、**結合度**はモジュール同士の依存の強さを表し、**高凝集・疎結合**を目指すのが鉄則です。
- **不変条件の境界**は、「**どこで必ず守るか**」を決めることで、外から安心して使える部品を作る考え方です。
- これらの原則は**独立ではなく支え合い**、SOLID 等の細かい原則を**包む大きな枠**として働きます。
- 原則は**教義ではなく道具**。状況に応じてトレードオフし、衝突したときは目的に立ち返って判断します。

これで第1部「品質とトレードオフ」は完了です。
次は **第2部「構造パターン（モノリス内）」** で、レイヤード・三層・MVC など、**実際の分け方の典型**を学びます。
