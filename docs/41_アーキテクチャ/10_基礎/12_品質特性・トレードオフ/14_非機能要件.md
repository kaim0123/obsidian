# 非機能要件

## 📖 非機能要件とは

**非機能要件（Non-Functional Requirements, NFR）**は、システムが**どのように**振る舞うべきかを規定する要件です。「何ができるか」ではなく、「どの程度の品質で」「どのような条件下で」動作するかを定義します。

### 機能要件との違い

| 観点 | 機能要件 | 非機能要件 |
|------|----------|------------|
| **問い** | 何ができるか？ | どのように動くか？ |
| **例** | 「ログインできる」「検索できる」 | 「3秒以内に応答する」「99.9%稼働する」 |
| **検証** | 機能が動くか確認 | 品質・制約を測定 |
| **影響** | 実装すべき機能 | 設計・アーキテクチャ・運用 |

---

## 📊 非機能要件の主なカテゴリ

### 1. 性能（Performance）

システムの反応速度や処理能力に関する要件。

| 観点 | 例 |
|------|-----|
| **応答時間** | 画面表示は2秒以内、APIは500ms以内 |
| **スループット** | 同時1000ユーザーに対応可能 |
| **リソース使用** | メモリ使用量は512MB以下 |

```
例：「商品検索結果は1秒以内に表示されること」
```

---

### 2. 可用性（Availability）

システムがどれだけの時間、正常に稼働するかの要件。

| 観点 | 例 |
|------|-----|
| **稼働率** | 99.9%アップタイム（月間43分以内の停止） |
| **復旧時間** | 障害発生後30分以内に復旧 |
| **計画停止** | メンテナンスは深夜のみ、月1回まで |

```
例：「サービスは年間99.5%以上の稼働率を維持すること」
```

---

### 3. セキュリティ（Security）

機密性・完全性・認証・認可に関する要件。

| 観点 | 例 |
|------|-----|
| **認証** | パスワードは8文字以上、英数字混在 |
| **認可** | 管理者以外は編集不可 |
| **暗号化** | 通信はHTTPS、パスワードはハッシュ化 |
| **監査** | 重要な操作はログに記録 |

```
例：「パスワードはbcryptでハッシュ化して保存すること」
```

---

### 4. ユーザビリティ（Usability）

使いやすさ・学習のしやすさに関する要件。

| 観点 | 例 |
|------|-----|
| **学習曲線** | 初回利用で主要機能に5分以内でアクセス可能 |
| **アクセシビリティ** | WCAG 2.1 レベルAA準拠 |
| **多言語** | 日本語・英語対応 |

```
例：「新規ユーザーが説明なしで3ステップで登録完了できること」
```

---

### 5. 保守性（Maintainability）

変更や修正のしやすさに関する要件。

| 観点 | 例 |
|------|-----|
| **モジュール性** | 機能ごとにモジュール分割 |
| **ドキュメント** | APIはOpenAPI仕様で記載 |
| **ログ** | エラー時にスタックトレースを記録 |

```
例：「新機能追加時の影響範囲が1モジュール以内に収まること」
```

---

### 6. 拡張性（Scalability）

負荷増加に対する対応能力に関する要件。

| 観点 | 例 |
|------|-----|
| **スケールアウト** | 水平スケールで対応可能な設計 |
| **負荷分散** | 複数インスタンスでの負荷分散対応 |

```
例：「ユーザー数が10倍になってもサーバー追加で対応可能なこと」
```

---

### 7. 互換性（Compatibility）

他システムや環境との連携に関する要件。

| 観点 | 例 |
|------|-----|
| **ブラウザ** | Chrome、Safari、Firefox最新2バージョン |
| **OS** | Windows 10以降、macOS 12以降 |
| **API** | REST API、バージョン管理 |

```
例：「主要ブラウザの最新2バージョンで動作すること」
```

---

### 8. 移植性（Portability）

別環境への移行のしやすさに関する要件。

| 観点 | 例 |
|------|-----|
| **インフラ** | Dockerで環境に依存しないデプロイ |
| **クラウド** | AWS/GCP/Azureで稼働可能 |

---

## 🎯 非機能要件の記載方法

### SMARTな要件にする

非機能要件は**測定可能**であることが重要です。

| NG例 | OK例 |
|------|------|
| 速く動くこと | ページ表示は3秒以内であること |
| 安全であること | 通信はTLS 1.2以上を使用すること |
| 使いやすいこと | タスク完了まで3クリック以内であること |

### トレードオフの認識

非機能要件同士は**トレードオフ**の関係になることがあります。

```
例：セキュリティ強化（複雑な認証）⇄ ユーザビリティ（簡単ログイン）
    性能（キャッシュ多用）⇄ 一貫性（常に最新データ）
```

優先順位を決め、バランスを取ることが重要です。

## 🔗 開発フェーズでの位置づけ

```
計画・要件定義 → 非機能要件の洗い出し・優先順位付け
       ↓
設計           → 非機能要件を満たすアーキテクチャ・設計
       ↓
実装           → 非機能要件を考慮したコーディング
       ↓
テスト         → 非機能要件の検証（システムテスト等）
```

- **計画**: ステークホルダーと非機能要件を合意
- **設計**: [[../10_設計の基礎/設計とは何か|設計]]で非機能要件をどう満たすか検討
