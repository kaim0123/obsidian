# なぜ今ここで扱うか — 変更コストとチームと長期保守

## この教材の目的

「アーキテクチャは大事」と頭ではわかっても、**なぜ今、わざわざ立ち止まって扱うのか**は初心者には実感しにくい問いです。
「動くコードを書く方が先では？」と思うのも自然です。

この教材では、

- アーキテクチャを早く意識するほど**得をする**理由
- **変更コスト**・**チーム**・**長期保守**の3つの観点
- 逆に「意識しない」とどんなトラブルが起きるか
- 初心者が**今日から**できる小さな一歩

を、初心者でも納得できる形で解説します。
前提知識として [[01_ソフトウェアアーキテクチャとは]]、[[02_アーキテクチャと設計の違い]] を先に読むと理解が深まります。

---

## 1. 結論：早く意識するほど安く済む

ソフトウェア開発で**最もコストがかかる行為**は、コードを書くことではなく、**書いたコードを書き直すこと**です。
そして書き直しの規模は、

> **アーキテクチャ起因の修正 ＞＞ 詳細設計起因の修正 ＞ コードレベルの修正**

の順に大きくなります（[[02_アーキテクチャと設計の違い]] 参照）。

つまり、**アーキテクチャを早めに少しでも意識するだけで、後の書き直しコストが大きく減る**ということです。

「**早く意識する**」とは、最初から完璧な設計を目指すことではありません。
「**何が部品で、どうつながり、どんなルールにするか**」を、**コードを書きながら少しずつ言語化する**だけでも、効果があります。

---

## 2. 変更コストの観点

### 2.1 変更コストは時間とともに大きく増える

ソフトウェア開発では、**バグや設計の問題は早く見つけるほど安く直る**ことが知られています。

| 修正タイミング | 相対コスト（目安） |
|---------------|------------------|
| 要件定義時に発見 | 1 |
| 設計時に発見 | 5〜10 |
| 実装時に発見 | 10〜50 |
| テスト時に発見 | 50〜200 |
| 本番運用後に発見 | 500〜1,000 |

数字は研究によってばらつきますが、**桁が増えていく**という傾向は共通しています。
「**早く気づくほど安い**」は、ソフトウェア開発における普遍的な経験則です。

### 2.2 アーキテクチャ起因の修正は特に高い

アーキテクチャに起因する問題は、**多くの部品をまたぐ**ため、修正範囲が広くなります。

- 「DB アクセスがあちこちのコードに散らばっている」 → 全モジュールに手を入れる
- 「ビジネスロジックが UI に書かれている」 → 全画面で書き直し
- 「マイクロサービスの分け方が業務単位と合っていない」 → サービスの再分割

これらは**1日で直る**ものではありません。

### 2.3 早めの「骨組み判断」が後の自由度を生む

逆に、最初に**骨組み（部品の分け方・依存の向き・置き場所のルール）を決めておく**だけで、

- 機能追加時に**「どこに書けばいいか」が一意に決まる**
- 仕様変更時に**影響範囲が限定される**
- リファクタリング時に**安全に動かせる範囲がわかる**

という**変更しやすさ**が手に入ります。これは [[01_ソフトウェアアーキテクチャとは]] で挙げた「**保守性・拡張性**」のメリットそのものです。

---

## 3. チームの観点

### 3.1 認識の共有がチーム開発の前提

ひとりで書いていれば、**頭の中の地図**でも何とかなります。
しかし2人以上で開発するとき、

- 「**この機能はどのファイルに書く？**」
- 「**このロジックは UI に書いていい？業務層？**」
- 「**この処理は新しいモジュールにする？既存のどこかに足す？**」

という判断が**毎日のように発生**します。
これが**人によってバラバラ**だと、コードベースは数週間でカオスになります。

アーキテクチャは、**チーム共通のルール**として、こうした判断を**揃える**働きをします。

### 3.2 分業の単位を決めるのもアーキテクチャ

「Aさんはユーザー機能、Bさんは決済機能を担当」のような**分業**は、

- 機能を**サービス・モジュール**にどう分けるか
- それぞれの**境界（インターフェース）**をどう決めるか

というアーキテクチャ判断の上に成立します。
**境界が曖昧**なまま分業すると、

- 同じ処理を**2人が別々に実装**してしまう
- 一方の変更が**他方の動作を壊す**
- レビューで**どこを誰が見ればいいか**が分からない

といった問題が起きます。

### 3.3 オンボーディング（新メンバー）への影響

アーキテクチャが**図やドキュメント**として残っていると、

- 新メンバーは**全体像を素早く把握**できる
- 「この機能はどこを見ればいい？」が**すぐ答えられる**
- レビュー観点が**チームで揃う**

という効果があります。逆に、アーキテクチャが**個々人の暗黙知**にとどまっていると、新メンバーは「**コードを全部読む**」という非現実的な学習を強いられます。

## 4. 長期保守の観点

### 4.1 ソフトウェアは「書いた瞬間から劣化する」

書き上がったコードは、**書いた時点の前提知識**で固定されます。
しかし周囲は刻々と変わっていきます。

- ライブラリ・フレームワークが**バージョンアップ**する
- ビジネス要件が**変化**する
- チームメンバーが**入れ替わる**
- 自分自身が**書いた時の意図を忘れる**（半年後の自分は他人）

このとき、**全体の構造を後から把握する**のは、想像以上に難しい作業です。

### 4.2 アーキテクチャは「読み手のための地図」

アーキテクチャを**意図的に決めて文書化**しておくと、

- **数年後の自分**が「なぜこう作ったか」を思い出せる
- **新しいメンバー**が短時間で全体像を掴める
- **保守担当**が変更の影響範囲を予測できる

つまりアーキテクチャは、**未来の読み手への手紙**でもあります。

### 4.3 「動いているから大丈夫」が崩れる瞬間

コードが**いま動いている**ことと、**今後も変更し続けられる**ことは、別の話です。

- いま動いていても、**1年後に直せない**コードは多い
- 直せないと、機能追加もバグ修正も**できない**
- 結果として、**書き直し（リプレース）**が必要になり、莫大なコストがかかる

アーキテクチャを意識した設計は、**この書き直しを遅らせる、あるいは小さくする**ための投資です。

---

## 5. 「意識しない」と何が起きるか

逆の側からも見てみます。アーキテクチャを意識せずに開発を進めると、典型的に次の症状が現れます。

### 5.1 ビッグボール・オブ・マッド（大泥団子）

- 機能ごとの境界が無く、すべてのコードが**密に絡み合う**
- 1ヶ所を直すと**思わぬ場所が壊れる**
- 新メンバーは「**怖くて触れない**」状態に陥る

### 5.2 散弾銃手術（Shotgun Surgery）

- 1つの機能変更のために、**多数のファイル**を同時に編集する必要がある
- 修正漏れが起きやすく、**バグの温床**になる

### 5.3 神クラス（God Class）

- 何でもやる**巨大なクラス**が出現する
- そのクラスを変えると**システム全体に影響**する
- 単体テストが**事実上書けない**

### 5.4 技術的負債

- 「あとで直す」と先送りされた問題が**積み上がる**
- やがて新機能の追加よりも**負債の利払い（バグ対応・回避策）**に時間を取られる

これらは、**意識的な設計判断の欠落**から生まれるパターンです。

---

## 6. 「動くものを早く作る」との折り合い

ここまで読むと、「**動くコードより設計が大事**」と聞こえるかもしれません。
しかし現代の開発では、**動くものを早く作って学ぶ**ことも同じくらい重要です。

両立のカギは、**全部を最初に決めない**ことです。

### 6.1 「最初に決めるべき」と「あとで決めていい」を分ける

- **最初に決めるべき** — 後戻りコストが大きいもの
  - 大きな部品の分け方（モノリス／マイクロサービス）
  - 依存の向き（UI が業務に依存？業務が DB に依存？）
  - データの所有権（どのサービスが正本データを持つか）
- **あとで決めていい** — 後戻りしやすいもの
  - クラスの細かい分け方
  - メソッドのシグネチャ
  - 命名

「**少し先まで耐える骨組みを最初に**、**詳細は走りながら**」が、現実的なバランスです。

### 6.2 プロトタイプとプロダクションを区別する

- プロトタイプ（試作・学習目的） → アーキテクチャは**最小限**でよい
- プロダクション（本番運用） → **長期保守**を意識した骨組みが必要

「いまどちらを作っているか」を**自分で意識する**だけでも、判断がブレにくくなります。

---

## 7. 初心者が今日からできる3つの一歩

最後に、**今日からできる小さな実践**を3つ紹介します。

### 7.1 ファイル・フォルダの分け方を意識する

- 「**この処理はどこに置くか**」を、置く前に**1秒だけ考える**
- 例：「これは UI 表示の話か、業務ロジックか、DB アクセスか」を分けてフォルダに置く

これだけで、最も基本的なアーキテクチャ感覚が身につきます。

### 7.2 依存の向きを意識する

- 「**このファイルは何をインポートしているか**」を観察する
- 業務ロジックが UI フレームワークをインポートしていたら、**逆向き**かもしれない
- 「**外側の都合（UI、DB）が、中心（業務ロジック）に流れ込まないようにする**」を合言葉に

詳しくは第3部の依存性管理の章（[[クリーンアーキテクチャの概要]] や [[依存性のルール]]）で扱います。

### 7.3 図を1枚描いてみる

- 自分のプロジェクトの**全体構造**を、A4 1枚に手描きで描く
- 「**部品**」「**つながり**」「**データの流れ**」を矢印で表現する
- 描けない・描くと矛盾する部分があれば、それが**設計の弱点**

最初は粗くて構いません。**描くこと自体**が、アーキテクチャを意識する訓練になります。

---

## 8. まとめ

- **アーキテクチャを早く意識するほど、後の書き直しコストが安く済みます**。書き直しコストは時間とともに**指数関数的に増えます**。
- アーキテクチャを意識する価値は、**変更コスト・チーム・長期保守**の3つの観点で説明できます。
  - **変更コスト**：早く骨組みを決めると、後の自由度が増える
  - **チーム**：判断のブレを減らし、分業とオンボーディングを支える
  - **長期保守**：未来の読み手への地図になり、書き直しを遅らせる投資になる
- 意識しないと、**大泥団子・散弾銃手術・神クラス・技術的負債**といった典型症状が現れます。
- ただし「最初に全部決める」必要はなく、**後戻りコストの大きいものだけ先に**、**詳細は走りながら**、が現実的なバランスです。
- 初心者は「**ファイル配置の意識**」「**依存の向きの観察**」「**図を1枚描く**」の3つから始められます。

次は **第1部「品質とトレードオフ」** に入り、「**良いアーキテクチャとは何で、何を犠牲にして何を得ているか**」を、品質属性・トレードオフ・原則の3章で学んでいきます。
