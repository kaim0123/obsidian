ソフトウェアアーキテクチャは４つの側面から成り立っている
１アーキテクチャスタイル
２アーキテクチャ特性
３論理コンポーネント
４アーキテクチャ決定

アーキテクチャ特性は、システムが備える性質と成功基準を定め、システムが何をすべきかを示す

論理コンポーネントは、システムの振る舞いを定義する

アーキテクチャ決定は、システムをどのように構築すべきかのルールを定めるもの

アーキテクチャスタイル

・レイヤードアーキテクチャ
レイヤー分離、レイヤーの追加
リスク；モノリシックなデプロイメントとモジュール性の欠如により耐障害性をサポートしない
　　　　メモリ不足を引き起こすと、アプリケーション全体がクラッシュしてしまう

・モジュラーモノリス
モノリシック構造、モジュラー構造、モジュール間通信

・パイプラインアーキテクチャ
フィルター、パイプ

・マイクロカーネルアーキテクチャ
コアシステム、プラグインコンポーネント、レジストリ、コントラクト

・サービスベースアーキテクチャ
サービスの設計と粒度、ユーザーインターフェースのオプション、APIゲートウェイのオプション

・イベント駆動アーキテクチャ
イベントとメッセージの違い、派生イベント、拡張可能なイベントを送信する、非同期処理機構、ブロードキャスト機構、イベントペイロード、ブヨの群れアンチパターン、データロスの防止、リクエスト・リプライ処理、メディエーター型イベント駆動アーキテクチャ

・スペースベースアーキテクチャ
処理ユニット、仮想化ミドルウェア、メッセージンググリッド、データグリッド、処理グリッド、デプロイメントマネージャー、データポンプ、データライター、データリーダー

・オーケストレーション駆動サービス指向アーキテクチャ
分類、再利用と結合

・マイクロサービスアーキテクチャ
境界づけられたコンテキスト、粒度、データ分離、APIレイヤー、運用面での再利用、フロントエンド、通信、コレオグラフィとオーケスレーション、トランザクション

| 登場時期                         | アーキテクチャ                                            | 解決したかった問題                                                                                                              |
| -------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **1970年代**                     | レイヤードアーキテクチャ                                  | プログラムが一枚岩で、UI・業務処理・DB処理が混在し保守しづらかった。責務を階層ごとに分離したかった。                            |
| **1970年代後半**                 | パイプラインアーキテクチャ                                | データ変換処理を何段階にも分けて再利用・組み合わせしたかった。（コンパイラ、ETLなど）                                           |
| **1980年代**                     | マイクロカーネルアーキテクチャ                            | ソフトウェアの機能追加のたびに本体を変更する必要があり、拡張性が低かった。プラグイン方式にしたかった。                          |
| **1990年代後半**                 | オーケストレーション駆動サービス指向アーキテクチャ（SOA） | 社内システムごとに機能が重複し、再利用できなかった。サービスとして共通化したかった。                                            |
| **2000年代前半**                 | イベント駆動アーキテクチャ                                | システム同士が同期通信で密結合になり、変更や負荷に弱かった。イベントによる疎結合・非同期化を実現したかった。                    |
| **2000年代前半**                 | スペースベースアーキテクチャ                              | アクセス集中でDBがボトルネックになり、スケールできなかった。メモリグリッドを利用して大量アクセスに耐えたかった。                |
| **2000年代後半（2007〜2010頃）** | サービスベースアーキテクチャ                              | SOAはサービス粒度が細かすぎて複雑になった。より粗い粒度でWebアプリ向けにシンプルなサービス分割を行いたかった。                  |
| **2011年頃**                     | マイクロサービスアーキテクチャ                            | モノリシックやSOAでは独立開発・独立デプロイが難しく、チーム開発の速度が上がらなかった。小さなサービス単位で独立運用したかった。 |
| **2018年頃**                     | モジュラーモノリス                                        | マイクロサービスは運用コストが高すぎるケースが多かった。単一アプリのまま内部だけを疎結合にしたかった。                          |

アーキテクチャパターン

アプリケーションアーキテクチャ
| 年代 | 系統 | アーキテクチャ | 解決したかった課題 |
| ------------ | -------------- | --------------------------- | --------------------- |
| **1970年代** | レイヤー系 | レイヤードアーキテクチャ | 責務を分離して保守性を高める |
| **1979** | GUI系 | MVC | 表示と業務ロジックを分離する |
| **1980年代** | GUI系 | PAC | 複雑なGUIを階層的に構築する |
| **1980年代後半** | GUI系 | MVP | GUIをテストしやすくする |
| **1990年代** | GUI系 | Document-View | ドキュメント編集アプリを作りやすくする |
| **1996** | レイヤー系 | Three-Tier Architecture | Webアプリ向けに3層へ明確に分離する |
| **2002** | Web系 | Front Controller | リクエスト処理を一元管理する |
| **2002** | Web系 | Page Controller | ページ単位で処理を管理する |
| **2002** | Web系 | Template View | HTMLとロジックを分離する |
| **2002** | ドメインモデル系 | Domain Model | ビジネスルールをオブジェクトで表現する |
| **2002** | ドメインモデル系 | Transaction Script | 単純な業務処理をシンプルに実装する |
| **2002** | ドメインモデル系 | Table Module | テーブル単位でロジックを管理する |
| **2002** | データアクセス系 | Active Record | DBテーブルとオブジェクトを対応させる |
| **2002** | データアクセス系 | Data Mapper | ドメインをDBから独立させる |
| **2002** | データアクセス系 | Repository | データ取得方法を隠蔽する |
| **2003** | ドメイン中心アーキテクチャ系 | Hexagonal Architecture | 外部技術への依存をなくす |
| **2006** | ドメイン中心アーキテクチャ系 | DCI | オブジェクトの役割を柔軟に表現する |
| **2007** | ドメイン中心アーキテクチャ系 | Onion Architecture | 依存関係を内側へ向ける |
| **2009** | 高度な設計系 | CQRS | 読み取りと書き込みを分離する |
| **2012** | ドメイン中心アーキテクチャ系 | Clean Architecture | ビジネスロジックを技術から完全に独立させる |
| **2014頃** | レイヤー系 | Vertical Slice Architecture | レイヤーより機能単位で管理する |
| **2015頃** | レイヤー系 | Feature Folder Architecture | 機能単位のフォルダ構成にする |
