# ソフトウェアアーキテクチャとは

## この教材の目的

「アーキテクチャ」という言葉は、ソフトウェア開発の現場でよく使われますが、初心者には抽象的でとらえにくい概念です。  
この教材では、**ソフトウェアアーキテクチャが何を指すのか**、**なぜ重要か**、**どのような要素で成り立っているか**を、省略せずに順を追って説明します。  
建築の比喩や具体例を交えながら、初心者でもイメージしやすい形で解説します。

---

## 1. ソフトウェアアーキテクチャの一言での説明

**ソフトウェアアーキテクチャ**とは、

> **ひとつのソフトウェアシステムを、どのような「部品（コンポーネント）」に分け、それらをどのように「つなぎ、役割分担させるか」という、システム全体の骨組み・構造のことを指します。**

つまり、「このシステムは何でできていて、どれとどれがどう連携するか」という**大きな絵**のことです。  
コードの一行一行や、個々の関数・クラスの書き方（いわゆる「設計」や「コーディング」）よりも、**もう一段上の、システム全体の形**を決めるものがアーキテクチャです。

---

## 2. 建築のアーキテクチャとの比喩で理解する

「アーキテクチャ」という言葉は、もともと**建築（建物）**の世界で使われてきました。  
ソフトウェアのアーキテクチャを理解するために、建物の例で考えてみます。

### 2.1 建物における「アーキテクチャ」

一軒の家を建てるとき、建築家は次のようなことを決めます。

- **部屋の割り方**  
  リビング、寝室、キッチン、浴室など、どのような「部屋（＝部品）」に分けるか。
- **部屋同士のつながり**  
  どこに廊下やドアを置き、どの部屋からどの部屋に行けるか。
- **骨組みと強度**  
  土台、柱、梁をどう配置するか。何階建てにするか。
- **設備の配置**  
  水道・電気・ガスをどこで分岐し、どの部屋に引き込むか。

これらは、**内装の色や家具の選び方**（細部のデザイン）よりも前の段階で決まる**「建物の全体の形と構造」**です。  
この**全体の形と構造を決めること**が、建築の世界での「アーキテクチャ」です。

### 2.2 ソフトウェアに置き換えると

ソフトウェアでも同じように考えます。

| 建築での例               | ソフトウェアでの例                           |
|--------------------------|----------------------------------------------|
| 部屋の割り方             | 機能をどの「サービス」や「モジュール」に分けるか |
| 部屋同士のつながり       | コンポーネント同士がどう連携・通信するか     |
| 骨組み・階数             | サーバー構成、何層構造にするか（例：3層構造） |
| 設備の配置               | データベースやキャッシュをどこに置くか       |
| 内装・家具（細部）       | クラス設計、関数の書き方（＝コードレベルの設計） |

つまり、

- **アーキテクチャ** ＝ システム全体の「部品の分け方」と「つなぎ方」の骨組み。
- **設計（詳細設計・コーディング）** ＝ その骨組みの上で、各 part をどう実装するかという細部。

という関係になります。  
「[[設計とは何か]]」で学ぶような、クラスや関数の分け方・依存のさせ方は、この**細部の設計**に当たります。

## 3. もう少し formal な定義（業界でよく使われる説明）

業界では、ソフトウェアアーキテクチャを次のように定義することが多いです。

- **ソフトウェアシステムを構成する主要なコンポーネント（部品）**
- **それらコンポーネントどうしの関係（依存、通信、データの流れ）**
- **それらを支える原則や制約（ルール、技術選定、非機能要件への対応方針）**

を**意図的に決め、文書化・共有したもの**がソフトウェアアーキテクチャです。

つまり、

1. **何を「部品」とするか**（コンポーネント）
2. **部品同士がどう関係するか**（関係性）
3. **どんなルールや制約で縛るか**（原則・制約）

の 3 つが、アーキテクチャの**中身**だと考えればよいです。

---

## 4. アーキテクチャを構成する主な要素（詳説）

ここからは、上で述べた「コンポーネント」「関係性」「原則・制約」を、もう少し具体的に説明します。

### 4.1 コンポーネント（部品・構成要素）

**コンポーネント**とは、システムを構成する**ひとまとまりの機能や役割を持つ単位**です。  
規模や見方によって、次のようなものがあります。

- **モジュール・パッケージ**  
  コードのまとまり（例：ユーザー管理モジュール、注文処理モジュール）。
- **サービス**  
  ネットワーク越しに API で呼び出される独立したアプリケーション（例：認証サービス、決済サービス）。
- **レイヤー（層）**  
  プレゼンテーション層、ビジネスロジック層、データアクセス層のように、役割で分けた「層」。

アーキテクチャを考えるときは、

- システムを**どの粒度で**分けるか（大きな 1 塊にするか、細かくサービスに分けるか）、
- それぞれに**どんな責任（役割）**を持たせるか、

を決めることになります。これが「コンポーネントの設計」です。

### 4.2 関係性（つながり・依存・データの流れ）

コンポーネントが決まっても、**お互いにどう連携するか**が決まっていないと、システムは動きません。  
ここで考えるのが**関係性**です。

- **依存の向き**  
  「A は B を使うが、B は A を知らない」のように、どちらがどちらに依存するかを決めます。依存の向きをそろえることで、変更の影響範囲を限定できます。
- **通信の方法**  
  同じプロセス内の関数呼び出しなのか、HTTP API なのか、メッセージキューなのか、など。
- **データの流れ**  
  どこでデータが作られ、どこに渡され、どこに保存されるか（データフロー）。

「どのコンポーネントがどのコンポーネントと、どのような方法でつながるか」を決めることが、アーキテクチャの**関係性**の部分です。

### 4.3 原則・制約（ルールと技術選定）

アーキテクチャには、**守るべきルールや制約**も含まれます。  
これらは、チーム全員が同じ方針で開発・変更できるようにするために重要です。

- **設計原則**  
  例：「ビジネスロジックは DB や UI に直接依存しない」「新機能は既存コードを壊さずに追加する」など。
- **技術選定**  
  使用する言語、フレームワーク、データベース、インフラ（オンプレ／クラウド）など。
- **非機能要件への対応方針**  
  パフォーマンス、可用性、セキュリティ、スケーラビリティを、アーキテクチャのどの部分でどう実現するか。

「何をしてよいか・してはいけないか」「何を使って実現するか」をアーキテクチャの一部として明文化しておくのが、原則・制約です。

## 5. なぜソフトウェアアーキテクチャが重要か

アーキテクチャをきちんと考えることで、次のようなメリットがあります。

### 5.1 変更しやすさ（保守性・拡張性）

- 役割が分かれていれば、「変更したい部分」だけに手を入れやすくなります。
- 依存の向きが整理されていれば、ある部分の変更が他の部分に及ぼす影響を小さくできます。  
  → **保守性・拡張性**の向上につながります。

### 5.2 複数人での開発（分業と責任の明確化）

- コンポーネントごとに担当を分けやすくなります。
- 「この部分は誰が責任を持つか」が明確になり、重複や手抜きを減らせます。  
  → **チーム開発**がしやすくなります。

### 5.3 品質と信頼性（テスト・障害の局所化）

- 部品ごとにテスト（単体テスト・結合テスト）をしやすくなります。
- 障害が起きたとき、「どのコンポーネントの問題か」を切り分けやすくなります。  
  → **品質と信頼性**の向上に貢献します。

### 5.4 パフォーマンス・スケーラビリティ

- 負荷が高い部分だけをスケールさせたり、キャッシュや DB の配置を決めたりするのは、アーキテクチャの判断です。  
  → **パフォーマンス**や**スケーラビリティ**を計画立てて改善できます。

### 5.5 共通の理解（意思決定の根拠）

- アーキテクチャを図や文書で残しておくことで、「このシステムはこういう形になっている」という**共通の認識**が生まれます。  
  → 新メンバーのオンボーディングや、**技術的な意思決定の根拠**になります。

逆に、アーキテクチャを意識せずに開発を進めると、

- 変更のたびに全体に影響が及ぶ、
- どこに何があるか分からず修正が怖い、
- チームで役割分担がしづらい、

といった状態になりやすく、**技術的負債**がたまりやすくなります。

## 6. 「設計」と「アーキテクチャ」の違い（整理）

よく「設計」と「アーキテクチャ」が混同されます。ここで一度整理します。

| 観点           | アーキテクチャ                         | 設計（詳細設計・コード設計）             |
|----------------|----------------------------------------|------------------------------------------|
| 対象           | システム全体の構造                     | モジュール・クラス・関数などの内部構造   |
| 粒度           | 粗い（サービス・レイヤー・コンポーネント） | 細かい（クラス、メソッド、変数）         |
| 主に決めること | 何を部品にするか、どうつなぐか、ルール | 部品の中身をどう実装するか               |
| 例             | モノリスかマイクロサービスか、3層か    | クラス分割、インターフェース、命名規則   |

- **アーキテクチャ** … 「家の間取りと骨組み」（部屋の分け方、つながり、強度の方針）。
- **設計** … 「各 room の中の家具の配置や仕様」（コードのクラス・関数の分け方、[[Single Responsibility Principle (単一責任の原則)]] など）。

両方とも「構造を決める」ことですが、**スコープと抽象度が違う**と理解するとよいです。

---

## 7. アーキテクチャを決める・描く人（アーキテクト）

アーキテクチャを検討し、方針を決め、図やドキュメントに落とす役割を、**ソフトウェアアーキテクト**（またはアーキテクト役）が担うことが多いです。  
ただし、

- 小さいチームでは、開発者が兼務することも多いです。
- 「アーキテクト」という肩書きがなくても、**「全体の形を決める」「コンポーネントの切り方やつなぎ方を提案する」**という行為そのものが、アーキテクチャを考えることです。

つまり、**誰かが「システムの骨組み」を意識して決め、伝える**ことが重要で、その役割がアーキテクトと呼ばれます。

## 8. 代表的なアーキテクチャの「形」（概要のみ）

「どのような部品に分け、どうつなぐか」には、よく使われる**パターン**があります。  
ここでは名前とイメージだけ挙げます。詳細は別の教材で学ぶとよいです。

- **モノリシックアーキテクチャ**  
  機能を一つの大きなアプリケーションにまとめる形。シンプルだが、規模が大きくなると変更・スケールが難しくなることがある。
- **マイクロサービスアーキテクチャ**  
  機能ごとに小さなサービスに分け、それらが API やメッセージで連携する形。スケールや担当分けに有利だが、運用・連携の複雑さは増す。
- **レイヤードアーキテクチャ（多層アーキテクチャ）**  
  UI 層・ビジネスロジック層・データ層のように「層」で分ける形。多くの Web アプリの基礎になっている。
- **イベント駆動アーキテクチャ**  
  コンポーネント間の連携を「イベントの発生と購読」で行う形。非同期処理や疎結合に向く。

どの形を選ぶかは、**チームの規模、変更の頻度、非機能要件（性能・可用性など）**によって変わります。  
「正解は一つではない」ので、**文脈に合わせて選ぶ**ことがアーキテクチャの考え方です。

## 9. 学習の進め方（次のステップ）

ソフトウェアアーキテクチャを学ぶときの流れの例です。

1. **用語とイメージを固める**  
   本教材で「アーキテクチャ＝システム全体の骨組み（部品の分け方・つなぎ方・ルール）」であることを理解する。
2. **具体例に触れる**  
   [[ソフトウェアアーキテクチャ研修【MIXI 25新卒技術研修】]] などの動画・資料で、モノリス・マイクロサービス・疎結合・DDD などの具体例に触れる。
3. **設計の基礎とつなげる**  
   [[設計とは何か]] や [[Single Responsibility Principle (単一責任の原則)]] など、コードレベルの設計が「アーキテクチャで決めた方針」をどう支えるかを見る。
4. **実務や個人プロジェクトで意識する**  
   小さなシステムでも「コンポーネントの分け方」「依存の向き」「守るルール」を少しずつ意識して設計してみる。

## 10. まとめ

- **ソフトウェアアーキテクチャ**とは、システムを**どのような部品（コンポーネント）に分け、それらをどのようにつなぎ、どのような原則・制約で縛るか**という**システム全体の骨組み・構造**のことです。
- **コンポーネント**（部品）、**関係性**（つながり・依存・データの流れ）、**原則・制約**（ルール・技術選定）の 3 つが、アーキテクチャの主な要素です。
- 建築の「間取りと骨組み」に例えると、アーキテクチャは「間取りと骨組み」、詳細設計・コーディングは「各部屋の内装や家具」に相当します。
- アーキテクチャを意識することで、**変更しやすさ、分業のしやすさ、品質、パフォーマンス**を高めやすくなり、**共通の理解**にもつながります。
- 代表的な「形」には、モノリス、マイクロサービス、レイヤード、イベント駆動などがあり、文脈に応じて選びます。

次の教材では、**モノリシックアーキテクチャ**や**マイクロサービスアーキテクチャ**、**疎結合**や**ドメイン駆動設計（DDD）** など、もう一歩踏み込んだ内容を学んでいきましょう。
