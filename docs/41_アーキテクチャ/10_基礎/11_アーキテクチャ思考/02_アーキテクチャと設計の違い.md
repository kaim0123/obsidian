# アーキテクチャと設計（詳細設計）の違い

## この教材の目的

「アーキテクチャ」と「設計」は、ソフトウェア開発の現場で**しばしば混同**されます。
どちらも「**構造を決める**」行為ですが、扱う**スコープ**と**抽象度**が違います。

この教材では、

- 一言で言うと何が違うのか
- 建築の比喩でイメージをつかむ
- それぞれが**何を決め、何を決めないのか**
- 実務でどう使い分け、どこから手を付けるか

を、初心者でも区別できる形で解説します。
ソフトウェアアーキテクチャの基本は [[01_ソフトウェアアーキテクチャとは]] を先に読むと理解が深まります。

---

## 1. 一言での違い

| 観点 | アーキテクチャ | 設計（詳細設計） |
|------|---------------|------------------|
| 何を決めるか | システム**全体**の骨組み | **個々の部品**の中身 |
| 粒度 | 粗い（サービス、レイヤー、コンポーネント） | 細かい（クラス、メソッド、変数） |
| 抽象度 | 高い | 低い |
| 主な関心 | 部品の分け方、つなぎ方、原則 | アルゴリズム、データ構造、命名 |
| 主な成果物 | アーキテクチャ図、ADR、原則ガイド | クラス図、シーケンス図、コード |

短くまとめると、

- **アーキテクチャ** ＝ 「家の**間取りと骨組み**」を決める
- **設計** ＝ 「**各部屋の家具配置と内装**」を決める

このイメージを最初に固めておくと、以降の議論がぶれません。

---

## 2. 建築の比喩で理解する

### 2.1 建築でのスコープの違い

家を建てるとき、関わる人たちは**それぞれ違う粒度**の決定をします。

- **建築家（アーキテクト）** は、家の**全体構造**を決めます。
  - 何階建てにするか
  - 部屋数と配置（間取り）
  - 玄関・廊下・階段の位置
  - 構造（木造・RC造）と耐震性能
  - 水道・電気の幹線をどう通すか
- **インテリアデザイナー／施主**は、**各部屋の中身**を決めます。
  - リビングのソファをどこに置くか
  - 壁紙・床材の色や素材
  - 照明器具の選定
  - 収納の細かい仕切り

両者とも「家を作る」仕事ですが、**前者は後戻りしにくい大枠**を、**後者は調整しやすい細部**を扱っています。

### 2.2 ソフトウェアに置き換える

| 建築での例 | ソフトウェアでの例 |
|-----------|-----------------|
| 何階建てか・間取り | サーバー構成、層構造（3層など）、サービス分割 |
| 玄関・廊下の位置 | API の境界、認証の置き場所 |
| 構造・耐震性能 | 性能・可用性・スケーラビリティ方針 |
| 水道・電気の幹線 | DB・キャッシュ・メッセージキューの配置 |
| ソファの位置 | クラスやメソッドの分け方 |
| 壁紙の色 | 命名規則、コードの書き方 |
| 収納の仕切り | データクラスの構造、DTO の設計 |

「**ソファをずらすのは簡単だが、間取りを変えるのは大工事**」というのは、ソフトウェアでも同じです。
**アーキテクチャの判断はあとから直しにくい**ため、**先に決めておく価値**があります。

---

## 3. アーキテクチャが決めること

[[01_ソフトウェアアーキテクチャとは]] で見た通り、アーキテクチャは次の3つを扱います。

1. **コンポーネント** — 何を「部品」とするか（モジュール、サービス、レイヤー）
2. **関係性** — 部品同士をどうつなぐか（依存の向き、通信、データフロー）
3. **原則・制約** — どんなルールで縛るか（守るべき方針、技術選定、非機能要件への対応）

具体例で言うと、

- 「**この機能はマイクロサービスに分けるか、モノリスのままか**」
- 「**ビジネスロジックは DB に直接依存しない**というルールを置くか」
- 「**認証は API ゲートウェイで一括するか、各サービスで個別にやるか**」
- 「**性能のために CQRS（読み書き分離）にするか**」

これらは**システム全体の形**に関わる判断で、後から覆すと**多くのコードを書き直す**必要が出てきます。

---

## 4. 設計（詳細設計）が決めること

一方、「設計」（特に**詳細設計**）は、**アーキテクチャで決めた骨組みの中**で、各部品をどう作るかを決めます。

具体例で言うと、

- 「**ユーザー登録のユースケースを、どんなクラスとメソッドに分けるか**」
- 「**`User` クラスにどんなフィールドを持たせるか**」
- 「**メールアドレスのバリデーションをどこで行うか**」
- 「**この処理は `for` ループと `map` のどちらで書くか**」
- 「**この変数の名前は `userList` か `users` か**」

詳細設計では、

- **設計原則**（`SOLID` や DRY、KISS など）
- **オブジェクト指向の概念**（カプセル化、継承、多態）
- **命名規則・コーディング規約**

を駆使して、**アーキテクチャが定めた境界の内側**で部品を磨き上げます。
詳しくは姉妹フォルダ `03_設計/01_原則/` や `03_設計/02_オブジェクト指向/` を参照してください。

## 5. 比較表で整理

両者の違いを、**観点ごと**に並べると次のようになります。

| 観点 | アーキテクチャ | 設計（詳細設計） |
|------|---------------|------------------|
| 対象 | システム全体の構造 | モジュール・クラス・関数 |
| 粒度 | 粗い（サービス・レイヤー） | 細かい（クラス・メソッド） |
| 主な決定 | 部品の分け方、つなぎ方、ルール | 部品の中身、実装方法 |
| 関心 | 非機能要件（性能・可用性・保守性） | 可読性、再利用性、テスト容易性 |
| 例 | モノリス vs マイクロサービス、3層 vs クリーン | クラス分割、インターフェース、命名 |
| 担当者 | アーキテクト／テックリード | 開発者全員 |
| 後戻り | しにくい（大規模改修になりがち） | しやすい（リファクタリングで対応可） |
| ドキュメント | 図、ADR、原則ガイド | コメント、コード自体、クラス図 |
| 検証手段 | プロトタイプ、性能試験、レビュー | 単体テスト、リファクタリング |

「**スコープ（広さ）と抽象度（高さ）**」の2軸で見ると、両者は**地続きのスペクトラム**です。

---

## 6. 境界はグラデーション（実務では曖昧）

注意したいのは、両者の境界は**きっちり線が引けるものではない**という点です。

- 「**ユーザー認証をどこで行うか**」
  - サービス全体の境界の話 → アーキテクチャ
  - その認証ミドルウェアのクラス構成 → 詳細設計
- 「**注文と決済を別サービスにするか**」
  - 分けるかどうか → アーキテクチャ
  - 分けたあとそれぞれ内部をどう作るか → 詳細設計

つまり、**ある決定がアーキテクチャか設計かは、視点の高さで決まる**ということです。
だからこそ、現場では両方を**同時に行ったり来たり**しながら進めるのが普通です。

---

## 7. なぜ区別するのか（区別のメリット）

「グラデーションなら区別する意味は？」と思うかもしれません。
区別することのメリットは次の3つです。

### 7.1 議論の粒度が揃う

「設計レビュー」と言ったとき、**全体の話**をしたいのか、**特定のクラスの話**をしたいのかで、求める意見も判断基準も違います。
区別することで、**いま何の話をしているか**が明確になります。

### 7.2 検証手段が変わる

- アーキテクチャの妥当性は **プロトタイプ・性能試験・経験** で確かめる
- 詳細設計の妥当性は **単体テスト・コードレビュー** で確かめる

両者を混ぜると、「テストでは通るのに本番で性能が出ない」「テストは書きにくいけど実は問題なく動く」のような不一致が起きます。

### 7.3 後戻りコストの見積もりが変わる

「これを直したいです」と言われたとき、

- アーキテクチャ起因 → 大改修（数週間〜数ヶ月）
- 詳細設計起因 → リファクタリング（数時間〜数日）

と、**コスト感**が大きく違います。区別できると見積もりがブレにくくなります。

---

## 8. 実務での扱い方（順序）

実務では、概ね**次の順番**で考えます。

1. **アーキテクチャ** — 何を部品にするか、どうつなぐか、どんなルールにするか
2. **概要設計** — 各部品の責任とインターフェース（クラス／API の境界）
3. **詳細設計** — 各部品の内部構造、データ構造、アルゴリズム
4. **コーディング** — 実装

ただし、これは**完全な滝（ウォーターフォール）**ではありません。
小さく作って試しながら、**1〜4を行き来**するのが現代的な進め方です。

- アーキテクチャの選択が良いかは**動かしてみないと分からない**
- 詳細設計でつまずくと、**アーキテクチャの前提を疑う**こともある

逆に言うと、いきなり 4 から始めて 1 を後回しにすると、**全体の整合性が取れずに技術的負債**が膨らみがちです。
だからこそ、**早い段階でアーキテクチャに目を向ける**価値があります（次のノート [[03_なぜ今ここで扱うか_変更コストとチームと長期保守]] で深掘りします）。

## 9. ありがちな誤解

最後に、初心者がよく引っかかる誤解を整理します。

### 9.1 「アーキテクチャは大規模システムでだけ必要」

**誤りです。**
小さな個人開発でも、

- ファイルをどんなフォルダに分けるか
- ロジックを UI と分けるか混ぜるか
- DB アクセスをどこに置くか

はアーキテクチャ判断です。「意識しないアーキテクチャ」は単に**自然発生したアーキテクチャ**であり、**良い形になっているとは限らない**点に注意してください。

### 9.2 「アーキテクチャは資格者だけが触れる聖域」

**誤りです。**
アーキテクトという肩書きはありますが、**全員が日常的にアーキテクチャ判断をしている**のが実態です。
「`controllers/` と `services/` を分ける」のような小さな判断も、れっきとしたアーキテクチャです。

### 9.3 「アーキテクチャを完璧に決めてからコードを書くべき」

**誤りです。**
完璧を目指すと、**動くコードがないまま机上の空論**で終わりがちです。
**重要な部分だけ先に決めて、細部は走りながら学んで調整する**のが現実的です。

---

## 10. まとめ

- **アーキテクチャ**はシステム**全体の骨組み**を、**設計（詳細設計）**は**個々の部品の中身**を決めます。
- 建築でいうと、アーキテクチャは「**間取りと骨組み**」、詳細設計は「**各部屋の家具配置と内装**」に相当します。
- アーキテクチャは「**コンポーネント・関係性・原則**」を扱い、詳細設計は「**クラス・メソッド・データ構造**」を扱います。
- 両者は**グラデーション**で、現場では**行き来**しながら進めます。それでも区別する意味は、**議論の粒度・検証手段・後戻りコストを正しく見積もる**ためです。
- 「アーキテクチャは大規模だけ」「資格者だけが触れる」「完璧に決めてから書く」はいずれも**誤解**で、**全員が日常的に**アーキテクチャ判断に関わっています。

次は [[03_なぜ今ここで扱うか_変更コストとチームと長期保守]] で、「**なぜアーキテクチャを早い段階で意識する価値があるのか**」を、変更コスト・チーム・長期保守の3つの観点で見ていきます。
