# 疎結合と高凝集 — モジュール品質の2軸

## はじめに

**良い設計** かどうかは、次の2つの軸で判断できます。

- **結合度（Coupling）**: モジュール同士の **つながりの強さ**。**弱い（疎）ほうが良い**。
- **凝集度（Cohesion）**: 1つのモジュール内の **まとまりの強さ**。**強い（高）ほうが良い**。

**疎結合（Loose Coupling）** かつ **高凝集（High Cohesion）** が、良い設計の金科玉条です。

---

## 凝集度（Cohesion）: モジュール内のまとまり

### 高凝集とは

1つのモジュール（クラス・ファイル・パッケージ）の中にあるコードが、**関連性が強く、同じ目的のために動いている** 状態。

### 例: 高凝集なクラス

```typescript
class Order {
  private items: OrderItem[];
  private status: OrderStatus;

  addItem(item) { /* ... */ }
  removeItem(id) { /* ... */ }
  confirm() { /* ... */ }
  cancel() { /* ... */ }
  total() { /* ... */ }
}
```

このクラスは **「注文」に関する操作だけ** を持っている。すべてが同じ目的（注文の管理）に貢献している。

### 例: 低凝集なクラス

```typescript
class Utility {
  sendEmail() { /* ... */ }
  parseJSON() { /* ... */ }
  encryptPassword() { /* ... */ }
  formatDate() { /* ... */ }
  calculateTax() { /* ... */ }
}
```

関連性のない機能が詰め込まれている。これは凝集度が **低い**。

### 凝集度のレベル（参考）

1. **機能的凝集（最高）**: 単一の目的に集中
2. **逐次的凝集**: 出力が次の入力になる手順の連続
3. **通信的凝集**: 同じデータを使う
4. **手順的凝集**: 決まった順序で実行
5. **時間的凝集**: 同じタイミングで実行
6. **論理的凝集**: 似たカテゴリ
7. **偶発的凝集（最低）**: 関係のないものの寄せ集め

上のUtilityクラスは **「偶発的凝集」** に近く、分割するべき。

---

## 結合度（Coupling）: モジュール同士のつながり

### 疎結合とは

モジュール同士が **ゆるやかに** 繋がっていて、一方を変えても他方にあまり影響しない状態。

### 例: 疎結合

```typescript
interface Mailer {
  send(to: string, body: string): Promise<void>;
}

class OrderService {
  constructor(private mailer: Mailer) {} // インターフェースに依存
}
```

OrderService は **Mailer の中身を知らない**。SendGridでもAWSでも差し替え可能。

### 例: 密結合

```typescript
class OrderService {
  async sendMail() {
    const sendgrid = require('@sendgrid/mail');
    sendgrid.setApiKey('xxx');
    await sendgrid.send(...);
  }
}
```

OrderService が **SendGrid の詳細** まで知っている。変更・差し替えが不可能に近い。

### 結合度のレベル（参考）

1. **データ結合（最弱）**: 必要な値だけ渡す
2. **スタンプ結合**: オブジェクト全体を渡す
3. **制御結合**: フラグで振る舞いを制御
4. **外部結合**: 外部システムに直接依存
5. **共通結合**: グローバル変数を共有
6. **内容結合（最強）**: 他のモジュールの内部を直接書き換える

上に行くほど良い（弱い結合）、下に行くほど悪い（強い結合）。

---

## なぜ「疎結合 × 高凝集」が良いのか

### 1. 変更の影響が狭い

- **高凝集**: 変更が1か所に閉じる
- **疎結合**: 他のモジュールに波及しない

### 2. 理解しやすい

- **高凝集**: 「このクラスは何をするもの？」が明確
- **疎結合**: 1つのモジュールを読むのに、他を読まずに済む

### 3. 再利用しやすい

- **高凝集**: 機能の塊として取り出せる
- **疎結合**: 他に引きずられずに使える

### 4. テストしやすい

- **高凝集**: 1つの責任をテストすればよい
- **疎結合**: モックが少なく済む

---

## 「疎結合 × 高凝集」を達成する手段

### 1. 関心の分離

異なる責任は別のモジュールに。→ [[01_関心の分離]]

### 2. SOLID原則

SRP, OCP, LSP, ISP, DIP。すべて結合度・凝集度の改善に寄与。

### 3. 依存性注入・抽象化

具体より抽象に依存。→ [[01_依存性注入]] [[02_依存関係逆転の原則]]

### 4. レイヤー分け

レイヤー間は厳密に、層内は濃く。→ [[レイヤードアーキテクチャ]]

### 5. 凝集の単位 = 変更の単位

**同じ理由で変わるものは一緒に、違う理由で変わるものは別々に**。

## 対となる失敗パターン

### 低凝集 × 密結合 = 最悪

```typescript
class App {
  // 認証も、支払いも、メールも、DB接続も、全部ここに
  login() { /* SendGridに直書き */ }
  payment() { /* Stripeに直書き */ }
  mail() { /* MySQLに直書き */ }
}
```

- 関係のない機能が同じクラスに（低凝集）
- 具体的な実装に直接依存（密結合）

**変更が怖くて、テスト不能** の典型。

### 高凝集だが密結合

```typescript
// 注文に関することだけ扱う（高凝集）
class OrderService {
  // でも StripeとSendGridに直接依存（密結合）
  async place(input) {
    await Stripe.charge(...);
    await SendGrid.send(...);
  }
}
```

凝集は良いが、結合が強いので差し替え・テストが困難。

### 疎結合だが低凝集

```typescript
// インターフェースは使っている（疎結合）
class Utility {
  constructor(
    private mailer: Mailer,
    private db: Database,
    private encryptor: Encryptor,
    // ...10個の依存
  ) {}
  // 何でもやる（低凝集）
}
```

結合は良くても、1クラスに関係ない機能が同居しているので読みにくい。

## 判断の目安

### 凝集度のチェック

- **クラス名を一言で言えるか？**「UserService」「OrderRepository」のような明確な名前で表せる？
- **クラスの全メソッドが同じ目的か？**
- **クラスを見ずにメソッドの内容が想像できるか？**

### 結合度のチェック

- **このクラスを変更したら、どれだけの他クラスが影響を受けるか？**
- **このクラスを単体でテストできるか？**
- **依存先を差し替えられるか？**

## 実例: リファクタリング

### Before: 低凝集 × 密結合

```typescript
class OrderController {
  async handle(req, res) {
    // バリデーション
    if (!req.body.items) return res.status(400).send();
    // 料金計算
    const total = req.body.items.reduce((s, i) => s + i.price, 0);
    // 支払い（Stripeに直接）
    await stripe.charges.create({ amount: total });
    // DBに直接SQL
    await db.query('INSERT INTO orders ...');
    // メール（SendGridに直接）
    await sendgrid.send(req.body.email, '完了');
    res.json({ total });
  }
}
```

### After: 高凝集 × 疎結合

```typescript
// それぞれが1つの責任に集中 = 高凝集
class OrderValidator { validate(input) { /* ... */ } }
class OrderPriceCalculator { calc(items) { /* ... */ } }

interface PaymentGateway { charge(amount): Promise<void>; }
interface OrderRepository { save(order): Promise<void>; }
interface Mailer { send(to, body): Promise<void>; }

// UseCase は抽象に依存 = 疎結合
class PlaceOrderUseCase {
  constructor(
    private validator: OrderValidator,
    private calc: OrderPriceCalculator,
    private payment: PaymentGateway,
    private repo: OrderRepository,
    private mailer: Mailer
  ) {}
  async execute(input) {
    this.validator.validate(input);
    const total = this.calc.calc(input.items);
    await this.payment.charge(total);
    await this.repo.save(input);
    await this.mailer.send(input.email, '完了');
  }
}

class OrderController {
  constructor(private useCase: PlaceOrderUseCase) {}
  async handle(req, res) {
    const result = await this.useCase.execute(req.body);
    res.json(result);
  }
}
```

各クラスは **1つのことに集中** し、**抽象に依存** している。
