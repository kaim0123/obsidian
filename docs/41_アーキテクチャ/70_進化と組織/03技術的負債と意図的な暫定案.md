# 技術的負債と意図的な暫定案

## この教材の目的

「技術的負債」という言葉は、**汚いコードの言い訳**のように聞こえることもあれば、**リファクタの正当化**に使われることもあります。

実際には、負債には**意図的なもの**と**偶然たまったもの**があり、扱い方が違います。

この教材では、

- 技術的負債とは何か（比喩の意味）
- **意図的な暫定案**と**無意識の負債**の違い
- 暫定案を安全に使うためのルール
- チームで負債を扱うときの実務の目安

を、初心者向けに整理します。

前提: [[01_意思決定と進化]]、[[02ADRとArchitecture Decision Record]]、[[03_なぜ今ここで扱うか_変更コストとチームと長期保守]]

---

## 1. 技術的負債とは

**技術的負債 (Technical Debt)** とは、

> **今は楽・早い選択をした結果、将来の変更や保守に余分なコストがかかる状態**

を指す比喩です。金融の「借金」に例えられます。

- **借りたとき** — 早くリリースできた、機能を先に出せた
- **利息** — 同じ変更にかかる時間が増える、バグが出やすい、新人が理解しにくい
- **返済** — リファクタ、設計の見直し、テストの追加

```
  今スピード優先で実装
         │
         ▼
  ┌─────────────────┐
  │  技術的負債      │  ← 将来、変更のたびに「利息」を払う
  └─────────────────┘
         │
         ▼
  ある日「もう触りたくないコード」になる
```

重要なのは、負債は**必ず悪**ではない、という点です。  
ビジネス上、**期限のある市場機会**のために意図的に借りることは、戦略的な判断になり得ます。

## 2. 意図的な暫定案 vs 無意識の負債

| 種類 | 特徴 | 例 |
|------|------|-----|
| **意図的な暫定案** | 「今はこうする。理由と直し方を知っている」 | MVP では手動バッチで在庫同期。3ヶ月後に API 化 |
| **無意識の負債** | 「気づいたらこうなっていた」 | コピペが増え、どこが正か分からない |
| **陳腐化した設計** | 当時は正しかったが、前提が変わった | 10倍のトラフィックで、当時のDB設計が限界 |

アーキテクチャの会話では、**意図的な暫定案を負債として認め、管理する**ことが大切です。  
「暫定」を隠すと、無意識の負債に変わります。

---

## 3. 意図的な暫定案を使うときの4つのセット

暫定案を採用するときは、次の4つを**セット**で決めます。

| # | 項目 | 問い | 例 |
|---|------|------|-----|
| 1 | **意図** | なぜ今は完璧にしないか | デモ期限が2週間後 |
| 2 | **範囲** | どこまでが暫定か | 管理画面のエクスポートのみ CSV 直書き |
| 3 | **期限・条件** | いつ・何が起きたら直すか | 正式リリース前、またはユーザー100人超 |
| 4 | **直し方** | どう直すか（ざっくりでよい） | ジョブキュー + オブジェクトストアに移行 |

これを **ADR** やチケット、README の「Known limitations」に書いておくと、後から「知らなかった」になりにくいです（[[02ADRとArchitecture Decision Record]]）。

### 3.1 コードに残す軽い方法

```python
# TEMP(debt-42): 在庫は夜間バッチで同期。注文API化は Q3 で対応予定。
def sync_inventory():
    ...
```

`debt-42` のように**追跡用 ID** を振ると、一覧化しやすくなります。

## 4. 負債の「利息」が高いサイン

次のような状態は、返済（リファクタ）を検討するタイミングです。

| サイン | 意味 |
|--------|------|
| 小さな変更に何日もかかる | 結合が強く、影響範囲が読めない |
| 同じバグが何度も出る | 根本構造に問題がある |
| 新メンバーが数ヶ月理解できない | 複雑さが知識の属人化を生んでいる |
| テストを書くのが怖い | 設計が変更に耐えていない |
| 「触らないで」が口癖 | 運用リスクが蓄積している |

[[01品質属性]] の **修正容易性 (Modifiability)** が落ちている状態と考えてよいです。

## 5. チームで負債を扱う実務の目安

### 5.1 全部直そうとしない

負債は**ゼロにはなりません**。  
ビジネス価値と「利息」の大きさで**優先順位**をつけます。

```
  影響大 × 利息高  →  早めに返済
  影響小 × 利息低  →  様子見・触るときに直す
  影響大 × 触る機会なし  →  境界だけ整え、大規模変更は計画
```

### 5.2 新機能と返済のバランス

よく使われる考え方:

- **継続的に少しずつ** — 機能開発の20%をリファクタに（チームによる）
- **ボーイスカウトルール** — 触ったファイルは少しきれいにしてから出す
- **ストラングラーフィグ** — 古い部分を少しずつ新実装に置き換える（[[04進化型アーキテクチャとリバースコンウェイの法則]]）

### 5.3 「負債」と言うときの言葉をそろえる

「技術的負債」は感情的になりやすい言葉です。  
会議では次のように言い換えると建設的になりやすいです。

- 「この暫定案の**見直し条件**はまだ有効ですか？」
- 「ここを直すと、**次の3機能がどれだけ楽になる**か」
- 「返済しない場合の**リスク**（障害、セキュリティ、採用）」

## 6. アーキテクチャとの関係

技術的負債は、しばしば**境界の曖昧さ**から生まれます。

| 負債の例 | アーキテクチャ上の原因 |
|----------|------------------------|
| ドメインルールがコントローラに散在 | 層の分離が崩れている |
| サービス間の循環依存 | 境界づけられたコンテキストが不明確 |
| 設定がコードに直書き | 横断的関心事の置き場所が未決定 |

だから、負債の話は「コードが汚い」だけでなく、**設計の見直し**につながります。  
[[05レビュー観点と図と境界と非機能と運用]] の観点で定期的に点検するとよいです。

---

## 7. まとめ

| 覚えること | 内容 |
|------------|------|
| 負債とは | 今の楽さの代わりに、将来の変更コストが増える状態 |
| 意図的な暫定案 | 悪ではない。**意図・範囲・期限・直し方**をセットにする |
| 無意識の負債 | 記録とレビューなしでたまる。避けるべきはこちら |
| 返済 | 全部ではなく、利息が高いところから優先 |
