# 進化型アーキテクチャとリバースコンウェイの法則

## この教材の目的

「アーキテクチャはリリース前に完成させるもの」というイメージは、現実とはずれています。  
システムは**動き続けながら形を変えていく**のが普通です。

この教材では、

- **進化型アーキテクチャ** — 変化を前提に、ガイドしながら形を変える考え方
- **コンウェイの法則** — 組織構造がシステム構造に影響する、という観察
- **リバースコンウェイの法則** — 望むアーキテクチャから組織を設計する、という実践的な応用

を、初心者向けに整理します。

前提: [[01_意思決定と進化]]、[[03_境界づけられたコンテキストとコンテキストマップ]]、[[02モノリスと分散モノリスとマイクロサービスといつ分けるか]]

---

## 1. 進化型アーキテクチャとは

**進化型アーキテクチャ (Evolutionary Architecture)** とは、

> **アーキテクチャを「一度きりの設計」ではなく、継続的に変えていけるようにする**考え方

です。Neal Ford らが提唱した概念として広く知られています。

### 1.1 従来型のイメージ vs 進化型

```
【従来型のイメージ】
  要件定義 → 設計完成 → 実装 → 運用（変更は「改修」）

【進化型のイメージ】
  小さく始める → 測定する → ガイドする → 必要なら形を変える → 繰り返す
```

「最初から完璧なマイクロサービス」より、**今必要な形から始め、データと経験に基づいて分ける**方が現実的、という立場です。

### 1.2 フィットネス関数（概要）

進化型アーキテクチャでは、**フィットネス関数 (Fitness Function)** という言葉がよく出ます。

**「アーキテクチャが満たすべき性質を、自動または半自動でチェックする指標」** のイメージです。

| 例 | 何を守るか |
|----|------------|
| ビルド時に層の依存方向を検査 | ドメイン層が UI に依存しない |
| レスポンスタイムの閾値アラート | 性能要件 |
| 循環依存の検出 | モジュール境界の健全性 |
| セキュリティスキャン | 既知の脆弱性 |

初心者向けの理解: **「設計ルールを、人の記憶だけに頼らない」** 仕組みです。  
CI に組み込むほど強力ですが、まずはレビューチェックリストでも十分に近い考え方です（[[05レビュー観点と図と境界と非機能と運用]]）。

### 1.3 ストラングラーフィグ（絞め殺しのイチジク）

古いシステムを一気に置き換えるのはリスクが高いです。  
**ストラングラーフィグパターン**は、新しい部分を少しずつ増やし、古い部分への依存を減らしていく手法です。

```
  ユーザー
     │
     ▼
  ┌──────────────┐
  │ 新 API（Facade）│──→ 新実装（注文 v2）
  └──────┬───────┘
         │
         └──→ 旧実装（注文 v1）  ← 徐々に呼ばれなくなる
```

[[03技術的負債と意図的な暫定案]] で触れた「計画的な返済」ともつながります。

## 2. コンウェイの法則

**コンウェイの法則 (Conway's Law)** は、1968年に Melvin Conway が述べた観察です。

> **組織のコミュニケーション構造を反映したシステム設計が生まれる**

つまり、

- 1つの大きなチーム → **まとまった1つのモノリス**になりやすい
- 注文チーム・在庫チームが別々 → **注文サービス・在庫サービス**に分かれやすい

```
  組織のつながり方          システムのつながり方
  ┌─────┬─────┐            ┌─────┬─────┐
  │チームA│チームB│    ≈     │モジュールA│モジュールB│
  └──┬──┴──┬──┘            └──┬──┴──┬──┘
     │ 連携多 │                  │ API多 │
```

これは**呪い**ではなく**事実の描述**です。  
「きれいな図を描いたのに、組織が追いつかず分散モノリスになる」——よくあるパターンの背景にコンウェイの法則があります（[[02モノリスと分散モノリスとマイクロサービスといつ分けるか]]）。

## 3. リバースコンウェイの法則

**リバースコンウェイの法則 (Inverse Conway Maneuver)** は、コンウェイの法則を**逆に利用する**考え方です。

> **望むアーキテクチャを得るために、組織構造（チーム境界）を意図的に設計する**

### 3.1 例

| 望むアーキテクチャ | 組織側の工夫（例） |
|--------------------|-------------------|
| 注文と在庫を独立サービスに | 注文チーム・在庫チームを別ユニットに。共通DBチームに閉じ込めない |
| モジュラモノリスを維持 | モジュールごとにオーナーシップを明確に。横断変更はアーキテクトグループで調整 |
| プラットフォームとプロダクト分離 | インフラ・共通APIをプラットフォームチームが担当 |

### 3.2 注意点

- **組織変更はコストが高い** — 絵に描いたマイクロサービスだけでは足りない
- **コミュニケーション経路が設計** — チーム間の API は、コードの API だけでなく**会議・Slack・ドキュメント**も含む
- **無理な分割は逆効果** — 小さすぎるチームの乱立は、運用負荷だけ増やす

初心者向けの実践: 大きな分割をするときは、**「この境界のオーナーは誰か？」** を必ずセットで聞く習慣をつけるとよいです。

## 4. DDD の境界づけられたコンテキストとのつながり

[[03_境界づけられたコンテキストとコンテキストマップ]] で学んだ **境界づけられたコンテキスト (Bounded Context)** は、進化と組織の両方とつながります。

```
  ドメインの境界（コンテキスト）
         ↕  揃えると変更が楽
  チームの境界（オーナーシップ）
         ↕  揃えるとデプロイが楽
  コードの境界（モジュール・サービス）
```

3つが大きくズレていると、**どこを直せばよいか分からない**状態になりやすいです。  
進化型アーキテクチャでは、まず**ドメイン境界を意識し、チームとコードを少しずつ寄せていく**ことが多いです。

## 5. いつこの章を深く読むか

| 状況 | 優先すること |
|------|--------------|
| 個人〜小チーム、モノリス | モジュール境界と ADR で十分なことが多い |
| チームが2〜3に分裂 | コンウェイの法則を意識し、コンテキストマップを更新 |
| マイクロサービス移行を検討 | リバースコンウェイ + データ所有権（[[04データ所有権と分散トランザクションとSAGAと整合性]]） |
| レガシー置き換え | ストラングラーフィグ + フィットネス関数 |

第7部のこのノートは**必要なら**深く読む、で問題ありません。  
組織や分割の話が具体化してきたタイミングで戻ってくると効果的です。

## 6. まとめ

| 覚えること | 内容 |
|------------|------|
| 進化型アーキテクチャ | 変化を前提に、測定とガイドで形を変えていく |
| フィットネス関数 | 「守りたい性質」をチェックする指標・自動化 |
| コンウェイの法則 | 組織のつながり方 ≈ システムのつながり方 |
| リバースコンウェイ | 望む形から逆算してチーム境界を設計する |
