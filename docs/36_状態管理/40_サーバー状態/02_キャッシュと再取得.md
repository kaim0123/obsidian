# キャッシュと再取得

> **ひとことで言うと**：一度取ったデータは「キャッシュ」に取っておいてすぐ見せ、古くなったら裏でこっそり取り直す（再検証する）。これで「速い表示」と「新しいデータ」を両立する。

## たとえ話で理解する

コンビニの店員さんが「今日のおすすめ弁当」を覚えているとします。

- お客さんに聞かれたら、**覚えている答えをすぐ言う**（キャッシュを使う）
- でも朝に聞いた情報なので、**言いながら店長に「まだ合ってます？」と確認する**（再検証）
- 変わっていたら「あ、失礼しました、こちらです」と言い直す（新しいデータで画面を更新）

毎回倉庫まで確認しに行く（毎回通信する）と遅いし、朝の記憶だけで答え続ける（一度も取り直さない）と間違う。その中間が「キャッシュ＋再検証」です。

## なぜ必要？（困りごと）

素の `useEffect` + `fetch` だけで書くと、次の4つの問題が起きがちです。

| 問題 | 何が起きるか |
|---|---|
| 重複リクエスト | ヘッダーとサイドバーが両方「ログインユーザー」を取りに行き、同じ通信が2回飛ぶ |
| 古いデータ | 一覧 → 詳細 → 一覧と戻ると、毎回「読み込み中」が出る／または古いまま |
| 競合（レースコンディション） | 検索で「a」→「ab」と打つと、「a」の結果が後から届いて「ab」の結果を上書きする |
| キャンセル漏れ | 画面を閉じたあとも通信が続き、無駄な処理や警告が出る |

※ **レースコンディション（競合）**：複数の非同期処理の「終わる順番」が保証されないせいで、結果がおかしくなること。

## 基本の仕組み

### キャッシュの3つの状態

```
取得直後 ──(staleTime 経過)──> stale ──(誰も使わなくなって gcTime 経過)──> 削除
 fresh                       古いかも                                  メモリから消える
 そのまま使う                 使いつつ裏で再検証
```

- **キャッシュ**：データを「キー（名札）」付きで保存する箱。例：`["users"]`、`["user", 42]`
- **fresh（新鮮）**：まだ取り直さなくていいとみなす状態
- **stale（古いかも）**：表示には使うが、きっかけがあれば再検証する状態
- **再検証（revalidate / refetch）**：サーバーに取り直して、キャッシュを最新に入れ替えること

### stale-while-revalidate（古いのを見せつつ取り直す）

1. キャッシュがあれば **まずそれを表示**（待ち時間ゼロ）
2. stale なら **裏で再取得**
3. 新しいデータが届いたら **画面を差し替え**

SWR というライブラリ名はこの考え方の頭文字です。

### 再検証のきっかけ（よくあるもの）

- そのデータを使うコンポーネントが新しく表示されたとき
- ブラウザのタブに戻ってきたとき（ウィンドウフォーカス）
- ネットワークが復帰したとき
- 一定間隔（ポーリング）
- データを変更したあと（→ [[04_ミューテーションとキャッシュの無効化]]）

## コード例

### Before：競合とキャンセルを自分で防ぐ

```tsx
function SearchResults({ q }: { q: string }) {
  const [items, setItems] = useState<string[]>([]);

  useEffect(() => {
    const controller = new AbortController();
    fetch(`/api/search?q=${encodeURIComponent(q)}`, { signal: controller.signal })
      .then((r) => r.json())
      .then(setItems)
      .catch((e) => {
        if (e.name !== "AbortError") console.error(e);
      });
    // q が変わったら前のリクエストを中止 → 古い結果で上書きされない
    return () => controller.abort();
  }, [q]);

  return <ul>{items.map((i) => <li key={i}>{i}</li>)}</ul>;
}
```

競合とキャンセルはこれで防げますが、**キャッシュはまだ無い** ので「a」に戻ると再び通信します。重複リクエストをまとめるには、コンポーネントの外に「キー → Promise」の表を自作する必要があり、一気に複雑になります。

### After：ライブラリを使うと

```tsx
import { useQuery } from "@tanstack/react-query";

function SearchResults({ q }: { q: string }) {
  const { data = [] } = useQuery({
    queryKey: ["search", q], // q ごとに別のキャッシュ
    queryFn: ({ signal }) => // signal を渡すと不要になった通信を中止できる
      fetch(`/api/search?q=${encodeURIComponent(q)}`, { signal }).then((r) => r.json()),
    staleTime: 30_000, // 30秒は fresh とみなし、取り直さない
    gcTime: 5 * 60_000, // 使われなくなって5分でキャッシュを捨てる
  });
  return <ul>{data.map((i: string) => <li key={i}>{i}</li>)}</ul>;
}
```

- キーが同じならリクエストは1本にまとめられる（重複排除）
- 表示するのは常に「今の `q`」のキャッシュなので、古い結果に上書きされない
- 「a」に戻ればキャッシュから即表示

SWR なら `` useSWR(`/api/search?q=${q}`, fetcher, { dedupingInterval: 2000 }) `` のように、URL そのものをキーにします。詳細は [[05_TanStack Query]] / [[06_SWR]]。

### staleTime と gcTime の違い（TanStack Query）

| 設定 | 意味 | 既定値 |
|---|---|---|
| `staleTime` | 取得後、何ミリ秒 fresh とみなすか | `0`（すぐ stale） |
| `gcTime` | 使われなくなったキャッシュを何ミリ秒残すか | 5分 |

💡 「どれくらいで古くなるか」と「いつ捨てるか」は別の話。混同しないこと。

## よくある失敗

- ❌ キーに引数を入れ忘れる（`queryKey: ["user"]` で id 違いのデータを取る）→ ⭕ 結果を変える値は全部キーに入れる：`["user", id]`
- ❌ 「毎回取り直すのが遅い」と感じて再検証を全部オフにする → ⭕ 変わりにくいデータだけ `staleTime` を長くする
- ❌ `staleTime` を長くすれば通信が減ると思い、キャッシュが消える `gcTime` の方を短くしてしまう → ⭕ 役割の違いを表で確認する
- ❌ 自作キャッシュをグローバル変数で作り、いつ消すか決めていない → ⭕ 期限と無効化の仕組みまで必要になるので、素直にライブラリを使う
- ❌ `useEffect` で後片付けを書かず、検索結果が入れ替わる → ⭕ `AbortController` で中止するか、ライブラリにキー単位で管理させる

## まとめ

- キャッシュで「すぐ表示」、再検証で「新しさ」を保つ（stale-while-revalidate）
- 素の fetch では重複・古いデータ・競合・キャンセルを全部手で書くことになる
- キーの設計と `staleTime` の決め方が、キャッシュ運用の9割
