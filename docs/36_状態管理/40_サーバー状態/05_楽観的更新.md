# 楽観的更新

> **ひとことで言うと**：「たぶん成功する」と見込んで、サーバーの返事を待たずに先に画面を変えてしまう手法。失敗したら元に戻す（ロールバック）ところまでがセット。

## たとえ話で理解する

友だちに「明日10時に駅でね」とメッセージを送るとき、既読が付く前から手帳に予定を書き込みますよね。ほとんどの場合そのまま決まるからです。
もし「ごめん、明日無理」と返ってきたら、手帳の予定を消します。

- 先に書き込む＝**楽観的更新**
- 断られたら消す＝**ロールバック**

「返事が来るまで手帳に書かない」（＝悲観的な更新）でも間違いではありませんが、待っている間ずっと予定が宙ぶらりんです。

## なぜ必要？（困りごと）

- 「いいね」を押してから 0.5 秒ハートが変わらず、もう一度押してしまう
- チェックボックスを付けてもスピナーが回るだけで、操作が重く感じる
- 通信の遅いスマホ回線で、すべての操作がワンテンポ遅れる

反対に、楽観的更新を雑に作ると別の問題が起きます。

- 失敗したのに画面は「成功した」ように見えたまま（ロールバック忘れ）
- 裏で再取得した **古いデータ** が、先に変えた画面を上書きして一瞬元に戻る（競合）

## 基本の仕組み

### 用語

- **楽観的更新（optimistic update）**：成功を見込んで、先に手元（キャッシュや画面）を変えること
- **ロールバック（rollback）**：失敗したときに、変更前の状態へ巻き戻すこと
- **スナップショット**：巻き戻せるように、変更前のデータを取っておいた写し

### 流れ

```
1. 進行中の再取得をキャンセル   ← 古いデータに上書きされないように
2. 今のデータをスナップショット  ← 巻き戻し用
3. 画面（キャッシュ）を先に更新  ← ユーザーは即座に結果を見る
4. サーバーへ送信
   ├─ 成功 → そのまま
   └─ 失敗 → スナップショットに戻す（ロールバック）＋エラー表示
5. 最後に無効化して再取得        ← サーバーの本当の値に合わせる
```

### 使いどころ

| 向いている | 向いていない |
|---|---|
| いいね、お気に入り、チェック | 決済、送金、在庫の確保 |
| 並び替え、名前の変更 | サーバーで ID や計算結果が決まるもの |
| 失敗がまれで、戻しても困らない操作 | 失敗すると損害が出る操作 |

## コード例

### Before → After（素の React）：ロールバック付き

```tsx
function LikeButton({ postId, initial }: { postId: number; initial: boolean }) {
  const [liked, setLiked] = useState(initial);
  const [error, setError] = useState<string | null>(null);

  const toggle = async () => {
    const previous = liked; // スナップショット
    setLiked(!previous); // 先に画面を変える（楽観的更新）
    setError(null);
    try {
      const res = await fetch(`/api/posts/${postId}/like`, {
        method: previous ? "DELETE" : "POST",
      });
      if (!res.ok) throw new Error();
    } catch {
      setLiked(previous); // 失敗したら戻す（ロールバック）
      setError("いいねできませんでした");
    }
  };

  return (
    <>
      <button onClick={toggle} aria-pressed={liked}>{liked ? "♥" : "♡"}</button>
      {error && <small role="alert">{error}</small>}
    </>
  );
}
```

1つのボタンならこれで十分です。ただし「一覧のキャッシュにも反映」「連打したときの順番」「再取得との競合」まで考えると、手書きではつらくなります。

💡 React 19 には、送信中だけ仮の値を表示する `useOptimistic` フックもあります。

### ライブラリを使うと（TanStack Query）

```tsx
const queryClient = useQueryClient();
const mutation = useMutation({
  mutationFn: (todo: Todo) => updateTodo(todo),
  onMutate: async (newTodo) => {
    await queryClient.cancelQueries({ queryKey: ["todos"] }); // 1. 競合防止
    const previous = queryClient.getQueryData<Todo[]>(["todos"]); // 2. スナップショット
    queryClient.setQueryData<Todo[]>(["todos"], (old = []) =>
      old.map((t) => (t.id === newTodo.id ? newTodo : t)), // 3. 先に更新
    );
    return { previous }; // onError に渡る
  },
  onError: (_err, _newTodo, onMutateResult) => {
    queryClient.setQueryData(["todos"], onMutateResult?.previous); // ロールバック
  },
  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ["todos"] }); // 5. 本当の値に合わせる
  },
});
```

TanStack Query v5 では、キャッシュを触らずに `mutation.variables` と `mutation.isPending` を使って「送信中の項目だけ薄く表示する」簡単な方法もあります。

### SWR を使うと

```tsx
const { data, mutate } = useSWR<Todo[]>("/api/todos", fetcher);

const toggle = (todo: Todo) =>
  mutate(updateTodo(todo), {
    optimisticData: data?.map((t) => (t.id === todo.id ? todo : t)), // 先に表示
    rollbackOnError: true, // 失敗したら自動で戻す
    populateCache: false, // 返り値でキャッシュを上書きしない
    revalidate: true, // 最後に取り直す
  });
```

詳しくは [[05_TanStack Query]] / [[06_SWR]]。

## よくある失敗

- ❌ ロールバックを書かない → ⭕ 変更前のスナップショットを必ず取り、失敗時に戻す
- ❌ 失敗を黙って戻すだけ → ⭕ 「保存できませんでした」と知らせる。黙って戻るとユーザーは混乱する
- ❌ 進行中の再取得をキャンセルせず、古いデータで上書きされる → ⭕ 先に `cancelQueries` する
- ❌ 最後に再取得しない → ⭕ `onSettled` で無効化し、サーバーの本当の値に揃える
- ❌ 決済や在庫など失敗が許されない操作に使う → ⭕ そういう操作は返事を待ってから画面を変える

## まとめ

- 楽観的更新は「先に画面を変え、失敗したら戻す」ことで操作を軽く感じさせる
- 手順は「キャンセル → スナップショット → 先に更新 → 失敗ならロールバック → 最後に再取得」
- 失敗しても困らない操作だけに使う
