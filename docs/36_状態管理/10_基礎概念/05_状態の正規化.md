# 状態の正規化

> **ひとことで言うと**：入れ子（ネスト）になったデータを、「種類ごとの表（ID → データ）」に分けて平らに持つこと。同じデータの重複をなくし、更新を1か所で済ませるための整理術です。

## たとえ話で理解する

学校の名簿を考えます。

- **正規化前**：クラスごとの名簿に、生徒の住所・電話番号まで全部書いてある。ある生徒が部活名簿にも委員会名簿にも載っていたら、引っ越しのたびに **3つの名簿を書き直す** 必要がある
- **正規化後**：「生徒台帳」を1冊だけ作り、各名簿には **出席番号（ID）だけ** 書く。引っ越したら台帳を1か所直すだけ

データベースの「正規化」と同じ考え方を、フロントエンドの状態にも使います。

## なぜ必要？（困りごと）

API から返ってくるデータはよく入れ子になっています。

```ts
// 投稿の中に作者、コメントの中にも作者……
const posts = [
  { id: "p1", author: { id: "u1", name: "たろう" },
    comments: [{ id: "c1", author: { id: "u1", name: "たろう" }, text: "..." }] },
];
```

- 「たろう」が名前を変えたら、**全投稿・全コメントの author を探して直す** 必要がある
- 深いネストの更新はスプレッドが何重にもなり、書き間違えやすい（[[03_イミュータブルな更新]]）
- 1か所だけ直し忘れると、画面によって名前が違う

## 基本の仕組み

### Before / After の形

```
正規化前（ネスト）              正規化後（フラット）
posts: [                        users:    { u1: {id, name} }
  { id: p1,                     posts:    { p1: {id, authorId: u1, commentIds: [c1]} }
    author: {u1, たろう},        comments: { c1: {id, authorId: u1, text} }
    comments: [                 postIds:  [p1]   ← 並び順は別に配列で持つ
      { c1, author: {u1,...} }
    ] }
]
```

### 正規化のルール

| ルール | 説明 |
|---|---|
| 種類ごとに分ける | users / posts / comments を別々の表にする |
| `byId` で持つ | `{ [id]: データ }` のオブジェクト。ID で一発で引ける |
| 関係は ID で表す | `author` オブジェクトではなく `authorId` |
| 順序は配列で | `allIds: ["p1", "p2"]` のように別に持つ |

- **byId**：「ID をキーにした辞書」。配列を `find` で探すより速く、書き方も簡単
- TypeScript では `Record<string, User>`（キーが文字列、値が User の辞書型）で表せます

## コード例

### 正規化した状態の型と更新

```tsx
import { useState } from "react";

type User = { id: string; name: string };
type Post = { id: string; title: string; authorId: string };

type State = {
  users: Record<string, User>;
  posts: Record<string, Post>;
  postIds: string[]; // 表示順
};

export function useBlog(initial: State) {
  const [state, setState] = useState(initial);

  // ユーザー名の変更は users の1か所だけ直せばよい
  const renameUser = (id: string, name: string) =>
    setState((s) => ({
      ...s,
      users: { ...s.users, [id]: { ...s.users[id], name } },
    }));

  return { state, renameUser };
}
```

### 表示時に組み立てる

```tsx
function PostList({ state }: { state: State }) {
  return (
    <ul>
      {state.postIds.map((id) => {
        const post = state.posts[id];
        const author = state.users[post.authorId]; // ID から引く
        return <li key={id}>{post.title} — {author.name}</li>;
      })}
    </ul>
  );
}
```

### API レスポンスを正規化する小さな関数

```ts
function normalizeById<T extends { id: string }>(list: T[]) {
  const byId: Record<string, T> = {};
  for (const item of list) byId[item.id] = item;
  return { byId, allIds: list.map((i) => i.id) };
}
```

### ライブラリを使うと

Redux Toolkit には `createEntityAdapter` という正規化の道具があり、追加・更新・削除の関数を自動で作ってくれます（[[01_Redux]]）。

💡 サーバーから取ったデータを TanStack Query などで扱う場合は、無理に正規化せず「クエリごとにキャッシュ」して、更新後に再取得する方が簡単なことも多いです（[[04_ミューテーションとキャッシュの無効化]]）。

## よくある失敗

- ❌ 小さなデータまで何でも正規化する → ⭕ 重複や深いネストで困ったときに導入する
- ❌ `byId` だけ持って並び順を失う → ⭕ 順序が大事なら `allIds` 配列を別に持つ
- ❌ 関係をオブジェクトのまま残す（`post.author = user`）→ ⭕ `authorId` で参照する
- ❌ 削除時に参照側の ID を消し忘れる → ⭕ `allIds` や `commentIds` からも取り除く
- ❌ サーバーキャッシュと手元の正規化ストアの二重管理 → ⭕ 情報源をどちらかに決める（[[04_派生状態と単一の情報源]]）

## まとめ

- 正規化＝種類ごとの `byId` 表に分け、関係は ID で持つ
- 同じデータが1か所にしかないので、更新が1回で済みズレない
- 必要なときに導入する。サーバー状態はキャッシュ＋再取得で済むことも多い
