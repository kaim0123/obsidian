# Amazon Aurora とは

## 概要

Amazon Aurora は、MySQL および PostgreSQL 互換のリレーショナルデータベースエンジンです。クラウド向けに構築された高機能な仮想データベースサービスで、従来のデータベースの 3 倍のパフォーマンスと、商用データベースの 10 分の 1 のコストを実現します。

## 主な機能

### 1. 高機能な仮想データベースサービス

- MySQL/PostgreSQL 互換
- 高性能なストレージエンジン
- 自動スケーリング
- 高可用性と耐久性

### 2. クラウドネイティブ設計

- 分散ストレージアーキテクチャ
- 自動フェイルオーバー
- ポイントインタイムリカバリ
- 自動バックアップ

### 1. 分散ストレージ

## ネットワーク設計: プライベートサブネット配置と踏み台 EC2（Bastion）

RDS（含む Aurora）は原則としてインターネットに直接晒さないため、**プライベートサブネット**に配置するのがベストプラクティスです。アプリケーションや管理者は、**パブリックサブネット**に配置した踏み台 EC2（Bastion ホスト）や、より安全な Systems Manager Session Manager、VPN/Direct Connect を経由してアクセスします。

### なぜプライベートサブネットか

- **攻撃面の最小化**: パブリック IP/インターネット経路を持たせないことで露出を減らす。
- **セキュリティ境界の明確化**: セキュリティグループと NACL で東西トラフィックのみ許可しやすい。
- **ゼロトラスト/社内網経由と親和**: SSM、VPN、プロキシ、RDS Proxy などと組み合わせた多層防御がしやすい。

### 代表的なアクセスパターン

- アプリ（ECS/EKS/EC2/Lambda）は同一 VPC（推奨は同一 AZ 近接）からセキュリティグループ経由で RDS へ私的通信。
- 管理者の手動接続は、パブリックサブネットの Bastion へ SSH/SSM で入り、そこから RDS へ接続（踏み台）。
- もしくは Session Manager Port Forwarding、Client VPN、Site-to-Site VPN、Direct Connect を利用し、Bastion を省略。

### 最小構成のネットワーク要件

- VPC: 例 10.0.0.0/16
- パブリックサブネット: 例 10.0.1.0/24（Internet Gateway 経路あり、Bastion 配置）
- プライベートサブネット: 例 10.0.2.0/24・10.0.3.0/24（RDS/Aurora 配置、NAT Gateway 経路任意）
- ルートテーブル: パブリックは `0.0.0.0/0 -> IGW`、プライベートは必要に応じて `0.0.0.0/0 -> NATGW`（パッチ/アウトバウンド必要時）
- セキュリティグループ:
  - RDS SG: "DB ポート（例 3306/5432）" を "アプリ SG" と "Bastion SG" からのみ許可
  - Bastion SG: 管理端末の固定グローバル IP からの SSH（22）を最小限許可、RDS へのアウトバウンド許可

### 踏み台 EC2 の運用要点

- キーペア管理、MFA、踏み台へのアクセス元 IP 制限は必須。
- 代替として **AWS Systems Manager Session Manager** の利用を強く推奨（ポート 22 開放やパブリック IP が不要、監査ログも容易）。
- データベース資格情報は **Secrets Manager** で管理し、Bastion に平文で置かない。
- アプリ側は可能なら **RDS Proxy** + IAM DB 認証で接続し、直結・長時間接続を避ける。

### 設計手順（ステップバイステップ）

1. 要件整理
   - **DB エンジン/バージョン**、想定接続元（アプリ/管理）、管理方式（SSM/SSH/VPN）、可用性（Multi-AZ/Aurora レプリカ）を確定。

2. VPC/サブネット設計
   - VPC の CIDR を定義（例 10.0.0.0/16）。
   - 各 AZ にパブリック/プライベートサブネットを 1 つずつ以上作成。
   - パブリックは IGW へ、プライベートは NATGW（必要時）へルート設定。

3. セキュリティ境界設計
   - セキュリティグループを分離（`App SG`、`Bastion SG`、`RDS SG`）。
   - `RDS SG` のインバウンドは `App SG` と `Bastion SG` のみを許可（ポート最小）。
   - NACL は明示的に狭める場合のみ調整（まずはデフォルト許可寄り + SG 厳格が運用しやすい）。

4. 踏み台/運用経路の選定
   - 優先: **SSM Session Manager**（Bastion 不要、監査容易）。
   - 代替: パブリックサブネットに Bastion EC2 を配置し、固定グローバル IP からのみ SSH 許可。
   - 企業接続: Client VPN / Site-to-Site VPN / Direct Connect を評価。

5. 秘密情報・認証
   - DB 資格情報は **Secrets Manager** で集中管理、ローテーション設定。
   - アプリは **IAM DB 認証**（Aurora MySQL/PostgreSQL 対応）を検討。
   - OS レベル鍵や `.env` への秘匿情報直置きを避ける。

6. RDS/Aurora 構築
   - DB サブネットグループにプライベートサブネットのみを指定。
   - Multi-AZ（Aurora は自動でマルチ AZ 相当）/レプリカ数を決定。
   - セキュリティグループを `RDS SG` に設定。
   - 暗号化（KMS）、バックアップ保持、監査ログ/PI を有効化。

7. 接続経路の検証
   - アプリからクラスター/リーダーエンドポイントへ接続検証（セキュリティグループ参照許可のみで到達することを確認）。
   - 管理者は SSM/Bastion から DB クライアントで接続検証。

8. 監査・運用
   - CloudTrail/CloudWatch Logs、RDS イベント、Performance Insights、VPC Flow Logs を有効化。
   - アクセス経路（SSM セッション/SSH）の監査ログ収集を実施。

9. 強化（オプション）
   - RDS Proxy 導入で接続プール/フェイルオーバーを最適化。
   - セルフマネージド Bastion を廃し、**SSM のみ**へ移行。
   - ネットワーク分離を強化（アプリと DB の SG 相互参照、Egress 制限）。

### よくある誤りと対策

- 誤: RDS をパブリックサブネットに配置 → 対策: 必ずプライベートサブネット + 最小権限 SG。
- 誤: `0.0.0.0/0` から DB ポート許可 → 対策: SG 参照で絞り、IP ベースは使わない。
- 誤: Bastion へ広範な SSH 許可/鍵の再利用 → 対策: SSM 優先 + IP 制限 + 鍵ローテーション。
- 誤: 資格情報を EC2 に平文保存 → 対策: Secrets Manager + IAM ロールで取得。

## まとめ

Amazon Aurora は、クラウド向けに最適化された高性能なリレーショナルデータベースサービスです。分散ストレージアーキテクチャと自動スケーリングにより、従来のデータベースを大幅に上回るパフォーマンスと可用性を提供します。適切な設計と設定により、スケーラブルで高可用性なアプリケーションを構築できます。
