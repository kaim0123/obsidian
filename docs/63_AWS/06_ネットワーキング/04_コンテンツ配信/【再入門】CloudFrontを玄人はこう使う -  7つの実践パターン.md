## 詳しい要約

**テーマ：キャッシュだけではない CloudFront の 7 つの実践的な機能**

CloudFront は「S3 の前に置いて静的コンテンツをキャッシュ配信するサービス」とだけ思われがちだが、実際にはアプリケーション層でやりがちな処理を CloudFront 層で解決できる強力な機能が多い。OAC・リバースプロキシ・WAF を組み合わせて通信を CloudFront に集約する考え方が特に重要、という話。

---

### CloudFront は誰もがうっすら苦手なサービス

- キャッシュ・Cookie・エラーページ・CORS などを扱うため責務があいまい。
- フロントエンドが触れるとチームがうまく回るが、AWS コンソールの操作が必要なのでインフラ担当に回りがち。一方インフラ担当はキャッシュや CORS の意図がわからず、「誰も拾いたがらないルーズボール」になりやすい。

### ① OAC（Origin Access Control）

- **CloudFront 経由でしか S3 にアクセスさせない**仕組み（S3 バケット側で設定）。S3 のコンテンツを外部公開するなら必須。
- CloudFront で WAF や署名付き Cookie などの対策をしても、ブラウザから S3 へ直接アクセスするルートが残っていれば意味がない。全通信を CloudFront 経由に強制できる。

### ② リバースプロキシ（今回いちばん伝えたい点）

- CloudFront が代理でリクエストを受け、パスに応じて後段の**オリジン**（S3・Amplify・ALB など）に振り分ける。振り分けルールを**ビヘイビア**と呼ぶ（キャッシュの振る舞いや関数の紐付けもここで設定）。ALB のリスナールールに似た L7 の動き。
- 応用：自社ドメイン（例 `api.example.com`）を CloudFront に割り当て、オリジンに他社 API（Slack、SendGrid など）を設定すると、自社ドメインにアクセスしているように見せて外部 API を呼べる。アクセス先ドメインのホワイトリストが厳しい環境で使う。
- メリット：
  - 外部からのアクセスを **CloudFront に集約**でき、セキュリティ対策を CloudFront 層 1 か所にまとめられる。
  - **ドメインが統一**されるので CORS 設定が不要になり、フロントからは `/api` のようにパスだけで呼べる。

### ③ WAF を適用できる

- DoS、SQL インジェクション、XSS などの攻撃をブロックできる。リバースプロキシで通信を集約した CloudFront に WAF を置けば、後段のオリジン全体を守れる。OAC・WAF・リバースプロキシが組み合わさって効果を発揮する。
- WAF は CloudFront・ALB・API Gateway に付けられる。**CloudFront 用はバージニア北部**で作成し、ALB・API Gateway 用はリージョナル（東京など）で作成する点がはまりどころ。
- 小技：WAF で指定 IP 以外を 503 でブロックし、カスタムレスポンスでメンテナンス用 HTML を返せば**メンテナンス画面**を出せる（Amplify、Nginx、ALB＋Lambda、アプリの環境変数などで出す方法以外の手札）。

### ④⑤ 関数を実行できる（CloudFront Functions / Lambda@Edge）

- アプリを変更せずに全リクエストへ共通処理を適用できる：セキュリティ系レスポンスヘッダーの付与、SPA のパス書き換え（`/users/123` → `index.html`）、旧 URL から新 URL へのリダイレクト、**ステージング環境だけベーシック認証**、エッジでの Cookie 検証による未認証ユーザーのブロックなど。

| 項目 | CloudFront Functions | Lambda@Edge |
|---|---|---|
| 向いている処理 | 軽い処理（パス書き換え・ベーシック認証・リダイレクト） | 重い処理、外部 API 呼び出し |
| 紐付けられるイベント | ビューアーリクエスト／レスポンスのみ | ビューアー・オリジンのリクエスト／レスポンスすべて |
| 制約 | メモリ 2MB・処理 5ms 程度まで | それ以上も可 |

- Lambda@Edge は独立したサービスではなく実体は普通の Lambda。条件（バージニア北部、ランタイムは Node.js か Python、環境変数なし、`$LATEST` ではなく番号付きバージョン、VPC 設定なし）を満たすとビヘイビアに紐付けられる。満たさないと紐付け時にエラーになる。
- 実例：S3 の静的コンテンツを「特定プロジェクトのメンバーだけ」に見せたい場合、署名付き Cookie ではパス単位の単純な制御しかできない。オリジンリクエストで Lambda@Edge が Cookie を自社 API に送って認可し、403 なら拒否、200 なら S3 へ通す。外部 API を呼ぶので Lambda@Edge でないとできない。

### ⑥ 署名付き Cookie

- ブラウザに Cookie をセットし、**指定パス以下の全リソース**へのアクセスを許可する。ログイン API で認証時に発行しておけば、`/private` 以下はログインユーザーだけに配信し、なければ CloudFront 層で 403 にできる。
- **署名付き URL**（S3）との違い：署名付き URL は単一ファイルへの一時的な許可（PDF や CSV を一時的に見せる）、署名付き Cookie はパス単位で複数ファイルをまとめて許可。画像のアクセス制御では署名付き URL・署名付き Cookie・Lambda@Edge がすぐ思い浮かぶとよい。

### ⑦ カスタムエラーレスポンス

- オリジンから 4xx/5xx が返ったときに、S3 に置いたエラーページ HTML を表示できる。
- 複数プロダクトを展開する企業でもエラーページを共通化でき、アプリごとの実装が不要になり、ブランドのトンマナもそろえられる。
- 設定：S3 に 404/500 用 HTML を置き、`/errors` のビヘイビアでその S3 に振り分け、カスタムエラーページ設定で 404 → `/errors/404.html`、5xx → `/errors/500.html` を指定する。

### まとめ

- CloudFront はキャッシュ以外にも、OAC・リバースプロキシ・WAF・関数実行・署名付き Cookie・カスタムエラーレスポンスと実務で使う機能が多い。
- 特に**リバースプロキシで通信を集約**し、WAF と OAC で守る考え方が重要。アプリ層でやっていた処理を CloudFront 層に移せないか、自社の設定を見直すとよい。
