## 詳しい要約

**テーマ：踏み台サーバーがなぜ必要かを AWS ネットワークの基礎から理解する**

踏み台サーバーは当たり前に使われているが、「もしなかったらどうなるか」から考えると、パブリック／プライベートサブネットやルーティングの理解が深まる。踏み台がないと RDS をパブリックサブネットに置くしかなくなり危険なので、DB はプライベートサブネットに置き、同じ VPC 内の踏み台を経由して安全にアクセスする、というのが結論。

---

### 踏み台サーバーとは

- 外部から直接アクセスできないサーバーに接続するための**中継サーバー**（**バスチオンサーバー**とも呼ぶ）。
- AWS ではパブリックサブネット（またはプライベートサブネット）に EC2 を置き、SSH か Session Manager で入って RDS に接続する。
- 用途：デプロイ前に必要なデータを INSERT するなどの**データメンテナンス**、SELECT でデータを確認する**不具合調査**。ローカルの GUI クライアント（TablePlus など）から見られるようにもできる。

### 踏み台がなかったらどうなるか

- 目的は「プライベートサブネットの DB の中身を**安全に**見たい」こと。踏み台がないと、RDS をパブリックサブネットに置いてパブリックアクセスをオンにするしかない。
- **パブリックサブネットとプライベートサブネットの違い**は、サブネットの属性ではなく、紐付けたルートテーブルで **VPC 外向き（0.0.0.0/0）の経路が Internet Gateway を向いているかどうかだけ**。経路がない、または NAT Gateway を向いていればプライベートサブネット。
- **Internet Gateway の役割**：ルートテーブルの宛先になることと、パブリック IP を持つリソースに対する **1 対 1 の NAT**。行きはパブリック IP → プライベート IP に宛先を変換（DNAT）、戻りは送信元をプライベート IP → パブリック IP に変換（SNAT）する。

### RDS をパブリックサブネットに置く危険性

- エンドポイントがインターネットにむき出しになり攻撃対象になる。ホスト・DB 名・ユーザー・パスワードを当てられれば DB の中身が全部見られる。
- セキュリティグループで IP を絞る方法もあり、実際に運用している会社もある。ただリモートワークで開発者ごとに自宅の IP を登録する運用になりがちで、IP はルーター再起動などで変わるので危険かつ運用が大変。結局プライベートサブネットに置くのがベストプラクティス。

### なぜプライベートサブネットの DB には直接アクセスできないか

- パブリックアクセスがオフなら、DNS でプライベート IP（例 `10.0.2.20`）が返る。ローカル PC のルートテーブルにはその経路がないので AWS に向かうことすらできない。
- VPC 内の EC2 なら、ルートテーブルの `10.0.0.0/16 → local` により同じ VPC 内で通信でき、SG で許可すれば RDS に届く。だから踏み台を **VPC 内に置くこと**に意味がある。残る課題はローカル PC → 踏み台の経路。

### 踏み台への接続方法

1. **SSH**：踏み台をパブリックサブネットに置き、IGW 経由で接続。シンプルで多くの会社が採用しているが、インターネットに公開し 22 番ポートを開ける必要があり、攻撃されやすい。
2. **Session Manager（推奨）**：AWS の IAM 権限で接続するので 22 番を開ける必要がなく、踏み台をプライベートサブネットに置ける。退職者が出ても IAM ユーザーや Identity Center のユーザーを削除すればよい（SSH だとキーペアのローテーションが必要）。

### 踏み台のセキュリティ運用

- 通信が踏み台に集約されるので、**ローカル PC → 踏み台の経路だけ**を制御すればよい。
- SSH なら SG で社内 IP だけ許可し VPN 経由に限定。Session Manager なら IAM で誰がどのインスタンスにセッションを開始できるかを細かく制御。
- 最強の方法：踏み台 EC2 を**普段は停止**し、必要なときだけ起動する。

### 実務での運用パターン

| パターン | 方法 | 長所 | 短所 |
|---|---|---|---|
| ① 踏み台から SQL 実行 | 踏み台にログインし psql などでクエリ発行 | 最も堅実で推奨 | CLI 操作で不便 |
| ② ポートフォワーディング | `aws ssm start-session` でローカル 5432 → RDS 5432 をつなぎ、`localhost:5432` に GUI クライアントで接続 | GUI で見られて便利 | 誤更新・誤削除のリスク、本番データをローカルで見るガバナンス上の問題 |

- 検証環境は②、本番は①という併用が多い（本番でも②を許す会社もあり、方針次第）。

### EC2 を使わずに踏み台を実現する方法

- **AWS Client VPN**：PC と VPC の間に仮想的な専用ネットワークを作り、`10.0.0.0/16` 宛てを VPN 経由でクライアント VPN エンドポイント → VPC 内部 → RDS へ届ける。マネージドで EC2 管理が不要だが、月約 1 万 5000 円＋パブリック IP 約 1000 円と高く（低スペック EC2 なら 2〜3 千円）、採用されにくい。
- **ECS Fargate を踏み台にする（おすすめ）**：タスクに SSM エージェントを入れ、Session Manager でポートフォワーディングや ECS Exec でコンテナに入る。タスクを**単発実行**でき、30 秒〜1 分で起動して使い終わったら消せる。初期構築の手間はかかる。

### アプリケーションサーバーを踏み台にしてよいか

- 結論：**おすすめしない**。誤ってアプリのプロセスを kill する、クエリ結果の CSV でディスクを使い切りログが書けなくなる、などで本番障害になりうる。人が運用・メンテする環境とリクエストをさばく環境は分けるべき。
- ECS のアプリ用タスクに入って作業すると、デプロイでタスクが再起動し長い SQL が途中で止まる危険もある。スポットインスタンスも不定期に落ちるので不向き。社内管理画面用サーバーを兼用する会社はある。

### まとめ

- 踏み台がないと DB をパブリックサブネットに置くしかなく危険。DB はプライベートサブネットに置き、同じ VPC 内の踏み台で経路を作る。
- パブリック／プライベートの違いは「VPC 外向きの経路が IGW を向いているか」だけ。
- 接続は Session Manager が推奨。運用は SQL 実行とポートフォワーディングの使い分け、代替手段として Client VPN と ECS Fargate がある。
- 当たり前の構成も「なかったらどうなるか」と立ち止まって考えると、設計の意思決定に腹落ちできる。
