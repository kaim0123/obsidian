# 三層アーキテクチャ

## 概要

三層アーキテクチャ（Three-Tier Architecture）とは、Web アプリケーションを 3 つの論理的な層に分けて構築する設計パターンです。プレゼンテーション層、アプリケーション層、データ層の 3 層で構成され、それぞれが独立した役割を持ち、システムの保守性、拡張性、再利用性を向上させます。

## 三層アーキテクチャの基本構造

### 層の構成

```
┌─────────────────────┐
│  プレゼンテーション層  │ ← ユーザーインターフェース
├─────────────────────┤
│   アプリケーション層   │ ← ビジネスロジック
├─────────────────────┤
│      データ層        │ ← データベース
└─────────────────────┘
```

### 各層の役割

#### 1. プレゼンテーション層（Presentation Layer）

- **役割**: ユーザーとのインターフェース
- **機能**: 画面表示、ユーザー入力の受付
- **技術**: HTML、CSS、JavaScript、フロントエンドフレームワーク
- **例**: Web ブラウザ、モバイルアプリ、デスクトップアプリ

#### 2. アプリケーション層（Application Layer）

- **役割**: ビジネスロジックの実装
- **機能**: データ処理、業務ルールの実装
- **技術**: サーバーサイド言語、フレームワーク
- **例**: Web サーバー、アプリケーションサーバー

#### 3. データ層（Data Layer）

- **役割**: データの保存・管理
- **機能**: データの永続化、検索、更新
- **技術**: データベース、ファイルシステム
- **例**: MySQL、PostgreSQL、MongoDB

## 各層の詳細

### プレゼンテーション層

#### 役割と責任

- **ユーザーインターフェース**: 画面の表示と操作
- **入力検証**: クライアントサイドでの入力チェック
- **表示制御**: データの表示形式の制御
- **ユーザー体験**: 操作性の向上

#### 技術スタック

- **HTML**: ページの構造
- **CSS**: デザインとレイアウト
- **JavaScript**: 動的な動作
- **フレームワーク**: React、Vue.js、Angular
- **UI ライブラリ**: Bootstrap、Material-UI

#### 実装例

```html
<!-- HTML -->
<div id="user-list">
  <h2>ユーザー一覧</h2>
  <ul id="users"></ul>
</div>

<script>
  // JavaScript
  fetch("/api/users")
    .then((response) => response.json())
    .then((users) => {
      const userList = document.getElementById("users");
      users.forEach((user) => {
        const li = document.createElement("li");
        li.textContent = user.name;
        userList.appendChild(li);
      });
    });
</script>
```

### アプリケーション層

#### 役割と責任

- **ビジネスロジック**: 業務ルールの実装
- **データ処理**: データの変換・加工
- **認証・認可**: ユーザーの権限管理
- **API 提供**: プレゼンテーション層へのデータ提供

#### 技術スタック

- **サーバーサイド言語**: Java、Python、PHP、Node.js
- **フレームワーク**: Spring、Django、Laravel、Express
- **Web サーバー**: Apache、Nginx
- **アプリケーションサーバー**: Tomcat、IIS

#### 実装例

```python
# Python (Flask)
from flask import Flask, jsonify, request
from flask_sqlalchemy import SQLAlchemy

app = Flask(__name__)
app.config['SQLALCHEMY_DATABASE_URI'] = 'mysql://user:pass@localhost/db'
db = SQLAlchemy(app)

class User(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    name = db.Column(db.String(80), nullable=False)
    email = db.Column(db.String(120), unique=True, nullable=False)

@app.route('/api/users', methods=['GET'])
def get_users():
    users = User.query.all()
    return jsonify([{'id': u.id, 'name': u.name, 'email': u.email} for u in users])

@app.route('/api/users', methods=['POST'])
def create_user():
    data = request.get_json()
    user = User(name=data['name'], email=data['email'])
    db.session.add(user)
    db.session.commit()
    return jsonify({'id': user.id, 'name': user.name, 'email': user.email})
```

### データ層

#### 役割と責任

- **データ永続化**: データの保存
- **データ整合性**: データの一貫性保証
- **高速検索**: インデックスによる高速化
- **バックアップ**: データの保護

#### 技術スタック

- **リレーショナルデータベース**: MySQL、PostgreSQL、Oracle
- **NoSQL データベース**: MongoDB、Redis、Cassandra
- **ファイルシステム**: ローカルストレージ、クラウドストレージ
- **データベース管理**: 正規化、インデックス設計

#### 実装例

```sql
-- SQL
CREATE TABLE users (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(80) NOT NULL,
    email VARCHAR(120) UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_users_email ON users(email);

INSERT INTO users (name, email) VALUES ('John Doe', 'john@example.com');
SELECT * FROM users WHERE email = 'john@example.com';
```

## 三層アーキテクチャのメリット

### 1. 保守性

- **責任分離**: 各層の役割が明確
- **独立した変更**: 一層の変更が他層に影響しない
- **デバッグ**: 問題の特定が容易
- **テスト**: 各層の独立したテスト

### 2. 拡張性

- **水平スケーリング**: 各層の独立したスケーリング
- **負荷分散**: 層ごとの負荷分散
- **新機能追加**: 既存層への影響を最小化
- **技術選択**: 各層で最適な技術を選択

### 3. 再利用性

- **コンポーネント化**: 各層の独立した再利用
- **API 化**: アプリケーション層の API 化
- **ライブラリ化**: 共通機能のライブラリ化
- **テンプレート化**: 設計パターンの再利用

### 4. セキュリティ

- **層間の分離**: セキュリティ境界の明確化
- **アクセス制御**: 層ごとのアクセス制御
- **データ保護**: データ層の保護
- **監査**: 各層の独立した監査

## 三層アーキテクチャのデメリット

### 1. 複雑性

- **設計の複雑さ**: 層間の依存関係の管理
- **実装の複雑さ**: 各層の実装と連携
- **デバッグの複雑さ**: 層間の問題の特定
- **テストの複雑さ**: 統合テストの必要性

### 2. パフォーマンス

- **層間通信**: ネットワーク通信のオーバーヘッド
- **データ変換**: 層間でのデータ変換コスト
- **レイテンシ**: 複数層を経由する遅延
- **リソース使用**: 各層のリソース使用量

### 3. 運用コスト

- **インフラ**: 各層のインフラ管理
- **監視**: 各層の独立した監視
- **デプロイ**: 各層の独立したデプロイ
- **バックアップ**: 各層の独立したバックアップ

## 実装パターン

### 1. モノリシック

- **特徴**: 全層を一つのアプリケーションで実装
- **メリット**: シンプル、デプロイが簡単
- **デメリット**: スケーリングが困難、技術選択の制限
- **用途**: 小規模アプリケーション

### 2. マイクロサービス

- **特徴**: 各層を独立したサービスで実装
- **メリット**: 高い拡張性、技術選択の自由度
- **デメリット**: 複雑性、運用コスト
- **用途**: 大規模アプリケーション

### 3. ハイブリッド

- **特徴**: モノリシックとマイクロサービスの組み合わせ
- **メリット**: バランスの取れた設計
- **デメリット**: 設計の複雑さ
- **用途**: 中規模アプリケーション

## 設計のベストプラクティス

### 1. 層間の依存関係

- **一方向依存**: 上位層から下位層への依存のみ
- **インターフェース**: 層間の明確なインターフェース
- **依存性注入**: 依存関係の外部化
- **イベント駆動**: 層間の疎結合

### 2. データの流れ

- **データ変換**: 層間での適切なデータ変換
- **バリデーション**: 各層での適切な検証
- **エラーハンドリング**: 層間での適切なエラー処理
- **ログ記録**: 各層での適切なログ記録

### 3. セキュリティ

- **認証**: 適切な認証方式の実装
- **認可**: 層ごとの適切な権限管理
- **暗号化**: 層間通信の暗号化
- **監査**: 各層での適切な監査

## まとめ

三層アーキテクチャは、Web アプリケーションの設計において重要なパターンです。プレゼンテーション層、アプリケーション層、データ層の 3 層に分けることで、システムの保守性、拡張性、再利用性を向上させることができます。適切な設計と実装により、効率的で安全な Web アプリケーションを構築することができます。また、現代の技術発展により、三層アーキテクチャも進化し続けており、クラウドネイティブやマイクロサービスなどの新しいアプローチと組み合わせて活用されています。
