# サーバーレス開発入門

## サーバーレスアーキテクチャとは

### 概要
サーバーレスアーキテクチャは、サーバーの管理や運用を意識せずにアプリケーションを構築・実行できるクラウドコンピューティングの実行モデルです。

**重要な誤解の解消**: 「サーバーレス」という名前ですが、サーバーが存在しないわけではありません。サーバーの管理をクラウドプロバイダー（AWS）が行い、開発者はビジネスロジックに集中できるという意味です。

### 主な特徴

#### 1. サーバー管理不要
```
従来型サーバー:
開発者 → サーバー管理（OS更新、セキュリティパッチ、スケーリング） → アプリケーション開発

サーバーレス:
開発者 → アプリケーション開発（のみ）
AWS → サーバー管理を自動で行う
```

#### 2. 自動スケーリング
- トラフィックに応じて自動的にスケールアップ・ダウン
- 同時実行数の上限設定も可能
- スパイクアクセスにも対応

#### 3. 従量課金
- 実行時間とメモリ使用量に基づく課金
- アイドル時間は課金されない
- 無料枠も充実

#### 4. イベント駆動
- HTTPリクエスト、S3アップロード、DynamoDBの変更などがトリガー
- 非同期処理に最適

## AWSのサーバーレスサービス

### コアサービス

#### 1. AWS Lambda
**役割**: コンピューティング（サーバーの代わり）

```
特徴:
- 関数単位でコードを実行
- 対応言語: Python, Node.js, Java, Go, Ruby, .NET, カスタムランタイム
- 最大実行時間: 15分
- メモリ: 128MB〜10GB
- 一時ストレージ: /tmp（最大10GB）
```

**使用例**:
- API バックエンド
- データ処理
- ファイル変換
- スケジュールタスク

#### 2. Amazon API Gateway
**役割**: APIエンドポイントの管理

```
種類:
1. REST API: フル機能、キャッシング可能
2. HTTP API: 軽量、低コスト
3. WebSocket API: 双方向通信
```

**機能**:
- リクエストルーティング
- 認証・認可
- レート制限
- リクエスト/レスポンス変換
- APIキー管理

#### 3. Amazon Aurora Serverless
**役割**: データベース

```
特徴:
- オンデマンドで自動スケーリング
- データベース容量単位（ACU）で課金
- 使用しない時は自動停止
- PostgreSQLとMySQL互換
```

**Aurora Serverless v2の改善点**:
- より細かいスケーリング（0.5 ACU単位）
- 瞬時のスケーリング（秒単位）
- 常時稼働のワークロードにも対応

### 補完サービス

#### Amazon Cognito
**役割**: ユーザー認証・認可

```
機能:
- ユーザープール: サインアップ/サインイン
- IDプール: 一時的なAWS認証情報の発行
- ソーシャルログイン（Google, Facebook等）
- MFA対応
```

#### Amazon S3
**役割**: オブジェクトストレージ

```
用途:
- 静的ファイルホスティング
- ファイルアップロード先
- データレイク
- Lambdaトリガーソース
```

#### Amazon DynamoDB
**役割**: NoSQLデータベース

```
特徴:
- 完全マネージド型NoSQL
- ミリ秒未満のレスポンス
- 自動スケーリング
- イベントストリーム（DynamoDB Streams）
```

#### AWS Step Functions
**役割**: ワークフロー管理

```
用途:
- 複数のLambda関数のオーケストレーション
- エラーハンドリングとリトライ
- 並列処理と条件分岐
- 長時間実行ワークフロー
```

#### Amazon EventBridge
**役割**: イベントバス

```
機能:
- イベント駆動アーキテクチャの実装
- スケジュール実行
- SaaSアプリケーション連携
- カスタムイベントルーティング
```

## サーバーレスアーキテクチャのメリット

### 1. 開発速度の向上
```
従来型:
サーバー調達 → OS設定 → ミドルウェア設定 → デプロイ設定 → 開発
（数日〜数週間）

サーバーレス:
開発開始
（数分）
```

### 2. 運用負荷の削減
- **OSパッチ適用**: AWS側で自動対応
- **セキュリティ更新**: 自動適用
- **スケーリング**: トラフィックに応じて自動
- **可用性**: 複数AZで自動冗長化

### 3. コスト最適化
```
従来型サーバー:
24時間 × 30日 = 720時間分の課金
（使用率が10%でも100%の料金）

サーバーレス:
実際の使用時間のみ課金
（使用率10% = 10%の料金）
```

**コスト例**（Lambda）:
- 月100万リクエスト: 無料枠内
- 月500万リクエスト: 約$1
- 月1億リクエスト: 約$20

### 4. スケーラビリティ
```
同時実行数の自動調整:
10ユーザー → 10並列実行
1000ユーザー → 1000並列実行（アカウント上限内）
```

## サーバーレスアーキテクチャのデメリットと対策

### 1. コールドスタート
**問題**: 初回実行時に数秒の遅延が発生

```
タイムライン:
初回リクエスト → コンテナ起動（遅い）→ コード実行
2回目以降 → コード実行（速い）
```

**対策**:
- Provisioned Concurrency（事前ウォームアップ）
- 軽量ランタイムの選択（Go, Rust）
- 依存関係の最小化
- Lambda SnapStart（Java専用）

```python
# 初期化をグローバルスコープで実行
import boto3

# グローバルスコープ（再利用される）
s3_client = boto3.client('s3')
db_connection = create_connection()

def lambda_handler(event, context):
    # ハンドラ内（毎回実行される）
    result = s3_client.list_buckets()
    return result
```

### 2. 実行時間制限
**問題**: Lambda最大実行時間は15分

**対策**:
- Step Functionsで分割
- バッチ処理はECS FargateやBatchを検討
- 非同期処理の活用

```
長時間処理の分割例:
Lambda1（5分）→ Step Functions → Lambda2（5分）→ Lambda3（5分）
```

### 3. ローカル開発の難しさ
**問題**: クラウド環境でしか動作確認できない

**対策**:
- AWS SAM CLI（ローカルエミュレーション）
- LocalStack（AWSサービスのモック）
- Cursor + SSH接続でEC2上で開発

### 4. ベンダーロックイン
**問題**: AWS固有の機能に依存

**対策**:
- ビジネスロジックを分離
- インターフェースを定義
- 必要に応じてコンテナ化も検討

```python
# 良い例：ビジネスロジックを分離
class UserService:
    def __init__(self, db_client):
        self.db = db_client  # 抽象化
    
    def create_user(self, user_data):
        # ビジネスロジック（AWS非依存）
        validated = self.validate(user_data)
        return self.db.insert(validated)

# Lambda関数
def lambda_handler(event, context):
    db_client = DynamoDBClient()  # AWS固有
    service = UserService(db_client)
    return service.create_user(event['body'])
```

### 5. デバッグの複雑さ
**問題**: 分散システムのトレーシングが難しい

**対策**:
- AWS X-Ray（分散トレーシング）
- CloudWatch Logs Insights
- 構造化ログの実装

```python
import json
import logging

logger = logging.getLogger()
logger.setLevel(logging.INFO)

def lambda_handler(event, context):
    # 構造化ログ
    logger.info(json.dumps({
        'event': 'user_created',
        'user_id': user_id,
        'request_id': context.request_id,
        'function': context.function_name
    }))
```

## 典型的なサーバーレスアーキテクチャパターン

### パターン1: REST APIバックエンド

```
クライアント
    ↓ HTTPS
API Gateway (REST API)
    ↓ Lambda Proxy統合
Lambda関数（ビジネスロジック）
    ↓
Aurora Serverless（データベース）
```

**用途**:
- Webアプリケーション
- モバイルアプリバックエンド
- SaaSサービス

### パターン2: イベント駆動処理

```
S3バケット
    ↓ イベント通知
Lambda関数（画像リサイズ）
    ↓
S3バケット（変換後）
```

**用途**:
- ファイル処理
- データパイプライン
- ETL処理

### パターン3: マイクロサービス

```
API Gateway
    ├→ Lambda（ユーザーサービス） → DynamoDB
    ├→ Lambda（注文サービス） → DynamoDB
    └→ Lambda（在庫サービス） → DynamoDB
         ↓ EventBridge
    Lambda（通知サービス） → SNS
```

**用途**:
- 大規模アプリケーション
- サービス分離
- チーム間の独立開発

### パターン4: リアルタイム通信

```
クライアント
    ↔ WebSocket（双方向）
API Gateway (WebSocket API)
    ↔
Lambda関数（接続管理）
    ↓
DynamoDB（接続ID管理）
```

**用途**:
- チャットアプリ
- リアルタイムダッシュボード
- ゲーム

### パターン5: 認証付きAPI

```
クライアント
    ↓ 認証トークン
API Gateway
    ↓ トークン検証
Cognito Authorizer
    ↓ 認証成功
Lambda関数（保護されたリソース）
```

## 開発フロー

### 1. 設計フェーズ
```
1. 要件定義
   ↓
2. アーキテクチャ設計
   - どのサービスを使用するか
   - データフロー設計
   - セキュリティ設計
   ↓
3. API設計
   - エンドポイント定義
   - リクエスト/レスポンス形式
```

### 2. 開発フェーズ
```
1. ローカル開発（SAM CLI使用）
   ↓
2. 単体テスト
   ↓
3. 統合テスト（開発環境デプロイ）
   ↓
4. コードレビュー
```

### 3. デプロイフェーズ
```
1. Infrastructure as Code（SAM/CloudFormation）
   ↓
2. CI/CDパイプライン
   ↓
3. ステージング環境デプロイ
   ↓
4. 本番環境デプロイ（Blue/Greenデプロイメント）
```

### 4. 運用フェーズ
```
1. モニタリング（CloudWatch）
   ↓
2. アラート設定
   ↓
3. ログ分析
   ↓
4. パフォーマンスチューニング
```

## まとめ

### サーバーレスが適している場合
✅ トラフィックが変動する
✅ 迅速な開発が必要
✅ 運用リソースが限られている
✅ イベント駆動の処理
✅ マイクロサービスアーキテクチャ

### 従来型サーバーが適している場合
⚠️ 常時高負荷（24時間フル稼働）
⚠️ 15分以上の処理
⚠️ 特殊なOS設定が必要
⚠️ レイテンシに極めて敏感（マイクロ秒単位）
⚠️ 既存システムとの密結合
