## 詳しい要約

**テーマ：AWS セキュリティグループの基礎と実務での設計方法**

セキュリティグループ（SG）はなんとなくの理解で触られがちで、ネットワークエラーの原因の多くを占める。基礎（ホワイトリスト・ステートフル・ENI 単位）を押さえたうえで、ALB → ECS → RDS / ElastiCache という典型構成で SG を設計し、アンチパターンと「SG が不要なケース」まで解説する。

---

### セキュリティグループの 3 つの性質

- SG は EC2 や RDS などにつける **ファイアウォール**で、通信の入口・出口を制御する（例：RDS の 3306 番を EC2 からだけ許可）。
1. **許可ルールのみ（ホワイトリスト方式）**：何もしなければ全てブロック。安全だが、設定し忘れでつながらないという罠にはまりやすい。
2. **ステートフル**：ECS → RDS の 5432 番をインバウンドで許可すれば、戻りの通信は自動で許可される。ECS 側のインバウンドや RDS 側のアウトバウンドで戻りを許可する必要はない。
3. **ENI につける**：SG はインスタンスそのものではなく、VPC 上の仮想 LAN ポートである **ENI（Elastic Network Interface）** に設定する。ENI が複数あれば SG もその数だけ設定できる。

### ネットワーク ACL との違い

| 項目 | セキュリティグループ | ネットワーク ACL |
|---|---|---|
| つける場所 | ENI | サブネット |
| ルール | 許可のみ | 許可と拒否 |
| 状態 | ステートフル | ステートレス（戻りも明示的に許可が必要） |
| 影響範囲 | 個々のリソース | サブネット内の全インスタンス |

- 今はネットワーク ACL はほぼ使わず（デフォルトの全許可のまま）、SG で細かく制御するのが AWS のベストプラクティス。

### ルールの設定方法

- インバウンド／アウトバウンドそれぞれで **タイプ**と**ソース（送信先）** を設定する。タイプを選ぶとプロトコル・ポートは自動入力（PostgreSQL→TCP 5432、HTTPS→443）。カスタム TCP なら任意ポート。
- ソースには CIDR・IP のほか **SG の ID** を指定でき、こちらを使うのがベストプラクティス。

### 典型構成での設計（最も厳しいパターン）

構成：クライアント → ALB → ECS（API）→ RDS（PostgreSQL）/ ElastiCache（Redis）＋外部 API

| SG | インバウンド | アウトバウンド |
|---|---|---|
| SG01（ALB） | HTTPS 443 を 0.0.0.0/0（不特定ユーザーなのでフルオープンしかない） | HTTP 80 → SG02（緩めるなら VPC CIDR や 0.0.0.0/0 の流派もある） |
| SG02（ECS サービス） | HTTP 80 ← SG01 | 5432 → SG03、6379 → SG04、HTTPS 443 → 0.0.0.0/0（外部 API）。楽なのは全許可 |
| SG03（RDS） | 5432 ← SG02 | なし（ステートフルなので戻りは通る） |
| SG04（Redis） | カスタム TCP 6379 ← SG02 | なし |

- ECS の SG は **ECS サービス単位**で設定する（実体はタスクの ENI に付く）。
- 通信が始まる場所から順に考えるとわかりやすい。アウトバウンドをどこまで絞るかは現場のルール次第。

### ベストプラクティス

- **リソースごとに SG を作る**。マイクロサービスで ECS サービスが増えたら SG も分ける。「app」のような抽象的な名前で使い回さない。
- インバウンドのソースには IP ではなく **接続元リソースの SG ID** を入れる。

### アンチパターン

1. **全許可（0.0.0.0/0・全ポート）の SG を「app」などの名前で全リソースに使い回す**：後から絞ろうとすると、同じ SG を使う ALB まで変わってブラウザからのリクエストを受けられなくなる、といった障害が起きる。
2. **IP アドレスベースでルールを書く**：ECS はデプロイでタスクが替わるとプライベート IP が変わり、EC2 も再起動で変わる可能性があるので壊れやすい。SG ID ベースなら Terraform でもリソースの関連付けとして管理しやすい。
- 拡張例（踏み台サーバー追加）：Session Manager を使うなら踏み台 SG（SG05）のインバウンドは不要（SSH ならタイプ SSH が必要）。アウトバウンドは 5432 → SG03。さらに RDS の SG03 のインバウンドに SG05 を追加するのを忘れない。

### セキュリティグループが不要なケース

1. **VPC 外のグローバルなリソース**：CloudFront、API Gateway、S3、Cognito、DynamoDB などは VPC に属さないので SG をつける画面すらない。Lambda はグレーで、**VPC Lambda** にすると SG が必要（実際は AWS 内部の Lambda 用 VPC から自分の VPC に ENI を作って接続する）。
2. **AWS API 経由の接続**：DynamoDB への読み書き（SDK 経由）、Lambda から SDK で RDS を停止する、ローカルから AWS CLI で RDS のメタデータを取得する、などは AWS API を呼んでいるので SG の許可は不要で、**IAM** で制御する。一方、PostgreSQL で RDS にクエリを投げるのは SG の許可が必要。ここが最も間違えやすい。

### まとめ

- SG は「ホワイトリスト・ステートフル・ENI 単位」の 3 性質を押さえる。
- リソースごとに SG を作り、ソースには SG ID を指定する。全許可の使い回しと IP ベースは避ける。
- VPC 外リソースや AWS API 経由の操作は SG ではなく IAM で制御する。
