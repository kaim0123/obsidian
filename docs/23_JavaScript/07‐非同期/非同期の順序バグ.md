# 非同期の順序バグ

## どういう問題か

JavaScript では非同期処理（`fetch`, `setTimeout`, Promise など）を使うと、「書いた順に実行されるとは限らない」ことが起こります。また、並列で走らせた処理の **完了順が入れ替わる** 可能性があります。

これを意識せずに書くと、表示される値が古かったり、後から来た結果に上書きされたりといったバグを生みます。

## 例1：forEach で await しても待たない

```js
async function main() {
  [1, 2, 3].forEach(async (id) => {
    const data = await fetchData(id);
    console.log(id, data);
  });
  console.log("完了");
}
main();
```

このコード、`main` は `console.log("完了")` を **forEach の非同期処理を待たずに** 実行します。

**理由**：`forEach` のコールバックが返す Promise は、`forEach` からは見えません。呼び出し元は Promise を `await` することができない。

### 正しい書き方

```js
// 順番に1つずつ処理する
for (const id of [1, 2, 3]) {
  const data = await fetchData(id);
  console.log(id, data);
}

// 並列に処理し、全部終わるのを待つ
const results = await Promise.all([1, 2, 3].map((id) => fetchData(id)));
```

## 例2：await 忘れ

```js
async function save(data) {
  api.post("/save", data); // await がない！
  console.log("保存完了"); // 実際にはまだ保存されていない
}
```

`await` を忘れると Promise が返るだけで、その場では処理が完了していません。エラーも `unhandledRejection` になりがち。

### 対策

```js
async function save(data) {
  await api.post("/save", data);
  console.log("保存完了");
}
```

ESLint の `@typescript-eslint/no-floating-promises` で検出できます。

## 例3：完了順が違う（レース条件）

ユーザが検索窓に高速で文字を打つとき：

```js
input.addEventListener("input", async (e) => {
  const results = await search(e.target.value);
  renderResults(results);
});
```

「cat」で検索 → 結果が返ってくる前に「cats」で検索 → 「cats」の結果が先に返る → そのあと「cat」の結果が後から返って上書き…

これが **古い結果が新しい結果を上書きする** レース条件です。

### 対策：最後のリクエストだけ有効にする

```js
let seq = 0;
input.addEventListener("input", async (e) => {
  const mySeq = ++seq;
  const results = await search(e.target.value);
  if (mySeq !== seq) return; // 古いリクエストなら捨てる
  renderResults(results);
});
```

もしくは **AbortController** で前のリクエストをキャンセル：

```js
let abortCtrl;
input.addEventListener("input", async (e) => {
  abortCtrl?.abort();
  abortCtrl = new AbortController();
  try {
    const res = await fetch(`/search?q=${e.target.value}`, { signal: abortCtrl.signal });
    const data = await res.json();
    renderResults(data);
  } catch (err) {
    if (err.name === "AbortError") return;
    throw err;
  }
});
```

## 例4：try/catch の外で await

```js
try {
  await fetchSomething();
} catch (err) {
  console.error(err);
}
someOtherFunc().then(() => {
  // ここでエラーが出ても、上の catch では拾えない
});
```

`await` の外の Promise は別世界。それぞれ catch を付ける必要があります。

## 例5：Promise.all で1つ失敗したら他が無駄に

```js
try {
  const [a, b, c] = await Promise.all([fa(), fb(), fc()]);
} catch (err) {
  // どれか1つ失敗したら他の結果も得られない
}
```

全員の結果を確認したいなら `Promise.allSettled` を使う。

```js
const results = await Promise.allSettled([fa(), fb(), fc()]);
for (const r of results) {
  if (r.status === "fulfilled") console.log(r.value);
  else console.error(r.reason);
}
```

## 例6：ループ内で Promise.all を忘れる

```js
// 全部直列で遅い
for (const id of ids) {
  await fetchData(id); // 1つずつ待つ
}

// 並列で速い
await Promise.all(ids.map((id) => fetchData(id)));
```

依存関係がないのに直列にすると、単純に時間が倍々になります。

## 例7：マイクロタスクとマクロタスクの順序

```js
console.log("1");
setTimeout(() => console.log("2"), 0);
Promise.resolve().then(() => console.log("3"));
console.log("4");

// 出力: 1, 4, 3, 2
```

Promise（マイクロタスク）は `setTimeout`（マクロタスク）より先に処理されます。これが発生順序の差を生むことも。

## 例8：async コンストラクタは書けない

```js
class X {
  constructor() {
    await something(); // SyntaxError
  }
}
```

`constructor` は async にできません。代わりに `async create` のような静的メソッドで初期化します。

```js
class X {
  static async create() {
    const x = new X();
    await x.init();
    return x;
  }
}
```

## 例9：await がループのパフォーマンスを壊す

```js
// 1つずつ取得、合計 Nミリ秒
for (const id of ids) {
  results.push(await fetch(`/api/${id}`));
}

// 並列、合計 1リクエスト分の時間
const results = await Promise.all(ids.map((id) => fetch(`/api/${id}`)));
```

## チェックリスト

バグを疑う時のチェックポイント：

- [ ] forEach の中で await を使っていないか
- [ ] await を付け忘れた関数呼び出しはないか
- [ ] 検索 / 非同期の入力 UI でレース条件対策をしているか
- [ ] ループを並列化できるのに直列にしていないか
- [ ] エラーハンドリングが漏れていないか（try/catch or .catch）
- [ ] 完了順に依存した処理がないか

## まとめ

- `forEach` + `async` は待たない → `for...of` か `Promise.all`
- `await` 忘れは重大バグ、Linter で検出可能
- ユーザ入力のような連続呼び出しは **レース条件** に注意。シーケンス番号か AbortController
- `Promise.all` と `Promise.allSettled` の使い分け
- マイクロタスクとマクロタスクの順序にも注意

非同期の順序バグは **「コードを読んだだけでは分からない、実行タイミング依存」** が特徴。テストでも再現しにくいので、書く段階から意識することが大事です。
