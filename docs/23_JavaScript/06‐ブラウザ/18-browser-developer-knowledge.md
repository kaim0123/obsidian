# プログラミングに役立つブラウザの知識（入門）

## 📖 このノートで学ぶこと

- ブラウザに「データを置く」仕組みが**複数ある理由**と、それぞれの違い
- 代表的なストレージ（Web Storage / Cookie / IndexedDB / Cache など）の役割と使いどころ
- ストレージ以外にも、コードを書くうえで押さえておきたい**ブラウザの前提**のイメージ

あわせて読む：[[17-browser-apis|ブラウザAPI入門]]、[[10-dom|第10章：DOM操作]]

---

## 💾 ブラウザのストレージはなぜ種類がある？

Web では **「誰のデータか」「いつまで残すか」「サーバーと共有するか」「どんな形のデータか」** によって、適した置き場所が変わります。そのため **API が分かれている** と理解するとよいです。

ざっくり言うと次のような軸で整理できます。

| 観点 | 意味 |
|------|------|
| **スコープ** | 同一オリジン内の「どの範囲」で共有されるか（タブ単位・オリジン単位など） |
| **寿命** | 閉じるまでか、期限付きか、明示削除まで残るか |
| **サーバー連携** | HTTP リクエストで自動で送られるか（Cookie）、フロントだけか |
| **データの形・量** | 文字列だけか、バイナリや大量データか |

---

## 📚 代表的なストレージの比較（超要点）

| 種類 | 主な API / 仕組み | だいたいの特徴 |
|------|-------------------|----------------|
| **sessionStorage** | `window.sessionStorage` | **タブ（厳密にはトップレベルの閲覧コンテキスト）単位**。閉じたら消えるイメージ。文字列のみ。 |
| **localStorage** | `window.localStorage` | **同一オリジン**で共有。明示削除まで残りやすい。容量に上限あり（ブラウザ依存）。文字列のみ。 |
| **Cookie** | `document.cookie` やサーバー側の `Set-Cookie` | **名前付きの小さなデータ**。`HttpOnly` など属性次第で **JS から読めない** こともある。**リクエストに同梱**されやすい（設計が重要）。 |
| **IndexedDB** | IndexedDB API | **ブラウザ内のデータベース**に近い。オブジェクトやバイナリも扱える。量が多い用途向け。**非同期 API** が基本。 |
| **Cache Storage** | Cache API（多くは **Service Worker** と組み合わせ） | **HTTP レスポンスのキャッシュ**など。PWA・オフライン対応で登場。通常の「設定やユーザー入力の保存」とは用途が違うことが多い。 |

### ストレージの使い分け（目安）

「どれを使うか」は **寿命・スコープ・サーバーに送る必要があるか・データの大きさ** で決めると迷いにくいです。

| やりたいこと | 第一候補 | 注意 |
|--------------|----------|------|
| タブを閉じたら捨ててよい下書き・ウィザードの途中など | `sessionStorage` | 別タブとは共有されない |
| 同じサイトに再訪したときも残したい軽い設定（テーマ、UI の状態など） | `localStorage` | 文字列のみ・同期 API。機密は入れない（XSS リスク） |
| サーバーが毎リクエストで読みたい小さな識別子（セッション ID、同意フラグなど） | **Cookie** | サイズ小さめ。`HttpOnly` / `Secure` / `SameSite` など属性設計が重要 |
| 大量データ・オブジェクト構造・バイナリ・オフライン用のクライアント DB | `IndexedDB` | 非同期。入門後はラッパーライブラリも検討しやすい |
| 取得済み HTML/CSS/JS や API レスポンスの「再配信用」キャッシュ | Cache API（＋ SW） | ユーザー入力の保存とは別物として捉える |

**認証トークンを Cookie にするか、`localStorage` にするか** はプロジェクトの方針・フレームワーク・脅威モデルで議論されやすい領域です。入門では「Cookie なら `HttpOnly` で JS から読めないようにできる」「`localStorage` は XSS で読まれる可能性を常に意識する」程度を押さえ、詳細は MDN や自チームのセキュリティガイドに当たるとよいです。

### Web Storage（localStorage / sessionStorage）の補足

- 値は **文字列** として保存されるため、オブジェクトは `JSON.stringify` / `JSON.parse` で扱うことが多い
- **同期 API**（結果が返るまで次の行に進みにくい）なので、大量書き込みは UI を固めやすい
- **同一オリジン**（プロトコル・ホスト・ポートの組）以外からは読めない

### Cookie について（プログラマ視点）

**Cookie とは** … ブラウザが保持する **`名前=値` の小さなデータ**です。条件を満たす HTTP リクエストに、ブラウザが自動で `Cookie` ヘッダーを付ける（付けない）動きが特徴で、**「フロントだけの保存」ではなく「HTTP とセットで設計する」** もの、と捉えると整理しやすいです。

**誰がどう書くか**

- サーバーはレスポンスヘッダー **`Set-Cookie`** で送る（属性もここで指定することが多い）。
- JavaScript からは **`document.cookie`** で読み書きできるが、**`HttpOnly` など JS から触れない Cookie もある**（セキュリティ上よく使われる）。

**よく出る属性（覚えると実務で効く）**

| 属性 | ざっくりした意味 |
|------|------------------|
| `HttpOnly` | JS から読めない → XSS でトークンが盗まれにくくなる（万能ではない） |
| `Secure` | HTTPS のときだけ送る |
| `SameSite` | クロスサイトからの送信を制限 → **CSRF 対策の一助**（`Strict` / `Lax` / `None` など） |
| `Path` / `Domain` | どの URL に Cookie を送るかの範囲 |
| `Max-Age` / `Expires` | 有効期限。省略するとブラウザを閉じるまで、など**セッション Cookie**として扱われることが多い（細かい挙動は環境依存のため一次資料で確認） |

**サイズと用途**

- **1 個・ドメインあたりとも実質的な上限**があり、大きな JSON やバイナリの置き場には向きません。肥大化させるとヘッダーが太り、毎リクエストのオーバーヘッドにもなります。
- **セッション ID** や **同意（Consent）の記録**、**小さなフラグ**のような「サーバーが知る必要がある短い値」向きです。

**セキュリティはセットで**

- Cookie は **XSS**（悪意あるスクリプトで読まれる／`HttpOnly` で緩和）と **CSRF**（意図しないリクエストに Cookie が乗る／`SameSite` やトークン検証などで緩和）の話題と一緒に学ぶと理解がつながります。
- **サードパーティ Cookie**（別サイトの iframe やリダイレクト経由など）は、プライバシー方針で制限が強まっており、認証・埋め込み連携の設計に影響します（詳細は時期とブラウザで変わるため、必要になったら MDN / ブラウザのドキュメントを確認）。

**まとめ** … 「リクエストに乗せたい小さな状態」なら Cookie、「タブやサイト内だけの比較的大きいデータ」なら Web Storage / IndexedDB、という棲み分けが最初の一歩になりやすいです。

### IndexedDB の補足

- オフラインアプリや、**大量・複雑なクライアント側データ**で選ばれやすい
- ライブラリ（例：Dexie など）を使う選択肢もある（別途調べるとよい）

### Cache API の補足

- 「ユーザー設定を保存する」より **「取得したファイルをキャッシュする」** イメージが強い
- Service Worker なしの入門段階では、名前だけ知っておけば十分なことも多い

## ⚠️ ストレージまわりでよくある注意

1. **機密情報をそのまま入れない** … 平文のパスワードやトークンを `localStorage` に置くのは危険になりやすい（XSS で読まれる可能性）
2. **容量とユーザー操作** … ストレージが満杯・プライベートモード・ユーザー削除で消える前提もある
3. **「消したつもり」にならない** … `sessionStorage` と `localStorage` で寿命が違うので、バグの原因になりやすい
4. **サードパーティ** … Cookie の third-party 制限など、仕様・ブラウザの方針で挙動が変わり続ける領域がある

## 🧭 ストレージ以外：コードを書く人が押さえるブラウザの枠組み

ストレージと並んで、実務で効いてくる「ブラウザの前提」を短くまとめます。

### オリジン（同一オリジンポリシー）

- **プロトコル + ホスト + ポート** の組で「別サイト」かどうかが決まる
- 別オリジンへの `fetch` などは **CORS** のルールのもとで制御される（詳細はネットワークの教材や MDN で）

### レンダリングと JavaScript

- HTML / CSS の結果が画面に描画され、その上で **JavaScript が DOM や API を触る**
- **メインスレッド**で動く処理が重いと、スクロールや入力がもたつく（体感パフォーマンス）

### 開発者ツール（DevTools）

- **Elements**（DOM・CSS）、**Console**（ログ・式の実行）、**Network**（通信）、**Application**（Storage / Cookie など）が、調査の主役になりやすい
- 例：[[DevToolsの開き方と基本|DevToolsの開き方と基本]]、同フォルダの Elements / Console / Network

### 仕様とブラウザの差

- 表示エンジン（Chromium / Firefox / Safari など）で細かい差や対応時期が変わる
- **MDN の互換性情報**や **Can I use** で確認する習慣があると安心

## 🎯 学び方のコツ

### よくある用途のストレージの使い方

実務でよく出るパターンを、**「何を保存したいか」** から逆算すると覚えやすいです（上の比較表とも対応します）。

| 用途の例 | よく選ぶ置き場所 | 補足 |
|----------|------------------|------|
| フォーム下書き、ウィザードの途中状態、一時的な入力バッファ | `sessionStorage` | タブを閉じれば消える想定に合う。**別タブでは共有されない**ので、「同じサイトを複数タブで開いて同期したい」用途には向かない |
| ダークモード、言語、サイドバーの開閉など **軽い UI 設定** | `localStorage` | 再訪問後も同じ表示にしたいとき向き。オブジェクトは `JSON.stringify` で文字列化するのが定番。**機密やトークンは避ける**（XSS で読まれるリスク） |
| 未ログイン時のカートやお気に入りの「とりあえず端末だけ」 | `localStorage` や `IndexedDB` | 件数が少なければ `localStorage`、画像付き・大量なら `IndexedDB`。ログイン後にサーバーへ移す設計も多い |
| **セッション ID**、同意フラグ、サーバーが毎回知りたい小さな識別子 | **Cookie**（多くはサーバーの `Set-Cookie`） | リクエストに自動で乗るのが強み。**`HttpOnly` / `Secure` / `SameSite`** はここで設計する |
| アクセストークンを JS から読める形で持つ（SPA など） | チーム方針次第（`localStorage`・メモリのみ・Cookie など） | 入門では「`localStorage` は XSS で奪われうる」「Cookie なら `HttpOnly` で緩和しうるが CSRF 設計が別途必要」程度を押さえる（詳細はセキュリティガイドへ） |
| オフライン用の大量データ、検索インデックス、バイナリ | `IndexedDB` | Web Storage の容量・文字列前提を超えるとき。**非同期**なので UI を固めない書き方を意識する |
| 取得済みの JS/CSS/画像や API レスポンスの再配信 | Cache API（＋ Service Worker） | **ユーザー設定の保存**とは別物。PWA・オフライン表示の文脈で出てくる |

**一言でまとめると** … 「このタブだけの仮置き」なら `sessionStorage`、「サイトに戻ってきてもよい軽い設定」なら `localStorage`、「HTTP と一緒にサーバーへ渡す小さな状態」なら Cookie、「たくさん・複雑・オフライン」なら IndexedDB、**ファイルのキャッシュ**なら Cache API、と足場を作るとよいです。

1. **用途から選ぶ** … 上表のように **寿命（タブ／ブラウザ／期限）・サーバーに送るか・データ量** で候補を絞る。「ログイン状態」だけを聞かれたときは、**セッション Cookie**・**トークン＋メモリ**・**リフレッシュの置き場** など、プロジェクト全体の設計になるので一次資料とチーム方針を当たる
2. **Application パネルで見る** … DevTools の Storage / Cookies を開き、`localStorage` に書いた値がどう見えるか確認する
3. **セキュリティは後回しにしない** … Cookie・トークン・XSS はセットで一次資料（MDN 等）を当たる
