# オブジェクト参照の罠

## なぜ罠があるのか

JavaScript では値には大きく2種類あります。

- **プリミティブ（数値・文字列・真偽値など）** … 値そのものがコピーされる
- **オブジェクト（配列・オブジェクト・関数など）** … **参照（場所）** がコピーされる

この違いを意識しないと、「変えていないはずのデータが変わっている」という不可解なバグにつながります。

## プリミティブの場合

```js
let a = 10;
let b = a;
b = 99;
console.log(a); // 10（変わらない）
```

プリミティブは **値のコピー**。a と b は独立しています。

## オブジェクトの場合

```js
const a = { x: 1 };
const b = a;
b.x = 99;
console.log(a.x); // 99（連動して変わる！）
```

a と b は **同じオブジェクトを指す** 参照なので、どちらから変更しても両方から見えます。図にすると：

```
a ──┐
     ├──→ { x: 99 }
b ──┘
```

## 典型的な事故パターン

### 1. 関数に渡した引数を変更される

```js
function addTimestamp(obj) {
  obj.updatedAt = Date.now(); // 元のオブジェクトを変更！
}

const user = { name: "太郎" };
addTimestamp(user);
console.log(user); // { name: "太郎", updatedAt: ... }
```

関数の引数として渡しても、参照が渡るので元データに影響します。

### 2. 配列の代入

```js
const a = [1, 2, 3];
const b = a;
b.push(4);
console.log(a); // [1, 2, 3, 4]
```

`=` で代入したから独立、と思うと間違い。

### 3. React の state で意図しない再レンダー

React は state が変わったかを **参照** で判定します。オブジェクトの中身だけ書き換えても、参照は同じなので「変わっていない」と扱われ、再レンダーされません。

```js
// NG：setState しても再レンダーされない
state.user.name = "次郎";
setState(state);

// OK：新しいオブジェクトを作る
setState({ ...state, user: { ...state.user, name: "次郎" } });
```

## 浅いコピーと深いコピー

### 浅いコピー（Shallow Copy）

1階層だけ新しいコピーを作ります。

```js
const a = { x: 1, nested: { y: 2 } };

const b = { ...a };              // スプレッド
const c = Object.assign({}, a);  // assign
const d = Array.isArray(a) ? [...a] : { ...a };
```

ただしネストされたオブジェクトは **共有されます**。

```js
b.x = 99;
console.log(a.x); // 1（大丈夫）

b.nested.y = 99;
console.log(a.nested.y); // 99！（ネストは共有）
```

### 深いコピー（Deep Copy）

全階層を新しく作ります。

#### 1. structuredClone（モダン・推奨）

```js
const deep = structuredClone(a);
```

標準で使える。Date、Map、Set、循環参照にも対応。

#### 2. JSON.parse(JSON.stringify(obj))

```js
const deep = JSON.parse(JSON.stringify(a));
```

手軽だが落とし穴あり：関数、Date（→文字列になる）、undefined、Symbol、循環参照は失われる。

#### 3. ライブラリ

- `lodash.cloneDeep`
- `rfdc`（小さくて速い）

詳しくは [[オブジェクトのディープコピー]]。

## 代入と比較の関係

### 比較も参照

```js
const a = { x: 1 };
const b = { x: 1 };
const c = a;

a === b; // false（別オブジェクト）
a === c; // true（同じ参照）
```

中身が同じでも、別々に作れば `===` は false。

### 配列も同じ

```js
[1] === [1]; // false
```

## 関数は参照型

```js
function fn() {}
const a = fn;
const b = fn;
a === b; // true（同じ関数）
```

「同じロジックの別関数」は別物。

```js
const a = () => 1;
const b = () => 1;
a === b; // false
```

React で `useMemo` / `useCallback` がある理由の1つがここ。

## どう予防するか

### 1. イミュータブルな書き方を意識

元を変えず、新しいオブジェクト/配列を作る癖をつける。

```js
// NG
function addItem(arr, item) {
  arr.push(item);
  return arr;
}

// OK
function addItem(arr, item) {
  return [...arr, item];
}
```

### 2. const を多用する

`const` は変数の再代入を禁じるだけで、オブジェクトの中身の変更は防げませんが、「この変数に入っているオブジェクトは同じもの」という意図を明確にできます。

### 3. Object.freeze

オブジェクト自体を凍結。

```js
const config = Object.freeze({ mode: "prod" });
config.mode = "dev"; // 無視される（strict モードでは TypeError）
```

浅い凍結なので、深くは `deepFreeze` の自作が必要。

### 4. TypeScript の readonly

```ts
type Config = Readonly<{ mode: string }>;
const config: Config = { mode: "prod" };
config.mode = "dev"; // コンパイルエラー
```

### 5. Immer などのライブラリ

「書き換えるように書くと、裏でイミュータブルに変換してくれる」便利なライブラリ。Redux Toolkit に内蔵されています。

## まとめ

- プリミティブは値コピー、オブジェクトは参照コピー
- `=` や関数引数で渡したら **同じ場所を共有**
- 浅いコピーは `{ ...obj }`、深いコピーは `structuredClone`
- 比較は参照比較。中身が同じでも `===` は false
- 元を変えないイミュータブルな書き方を習慣に

「バグの発生源の半分はここ」と言っても過言ではない、JavaScript の中核的な罠です。常に「これは参照を共有していないか？」と一息おける習慣を持てるようにしましょう。
