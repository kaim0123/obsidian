# モノレポとパッケージ分割

## この章の目的

アプリが複数になったり、チームが増えたりしたときに **コードをどのリポジトリ・どのパッケージに分けるか** を判断できるようになる章です。pnpm workspaces・Turborepo・Nx の役割の違いと、`apps/` と `packages/` の切り方を学びます。

---

## 1. モノレポとは — ポリレポとの比較

**モノレポ（monorepo）** は、複数のアプリ・ライブラリを **1 つのリポジトリ** で管理する方式です。対になるのが、1 リポジトリ 1 プロジェクトの **ポリレポ（polyrepo）** です。

| 観点 | モノレポ | ポリレポ |
|------|---------|---------|
| 共有コードの変更 | 1 つの PR で利用側まで直せる | パッケージを公開 → 各リポジトリで更新 |
| バージョン管理 | 内部パッケージは常に最新を参照 | リポジトリごとにバージョンがずれる |
| CI | 影響範囲だけビルドする仕組みが必要 | リポジトリ単位で単純 |
| 権限・独立性 | 全員が全コードを見られる | リポジトリ単位で分けやすい |

| 向く場面 | 向かない場面 |
|---------|-------------|
| 共通 UI・型・設定を複数アプリで使う | アプリ同士がほとんど何も共有しない |
| 同じチーム（または近いチーム）が複数アプリを持つ | 組織・権限を厳密に分ける必要がある |
| フロントとバックエンドで型を共有したい | ビルド時間の最適化に手をかけられない |

---

## 2. ツールの役割分担

モノレポのツールは **レイヤーが違う** ので、組み合わせて使います。

```text
  ┌──────────────────────────────────────┐
  │ タスク実行・キャッシュ  Turborepo / Nx │  ← どの順に、どこまでビルドするか
  ├──────────────────────────────────────┤
  │ 依存のリンク   pnpm / npm / yarn workspaces │  ← パッケージ同士をつなぐ
  └──────────────────────────────────────┘
```

| ツール | 役割 | 特徴 |
|-------|------|------|
| **pnpm workspaces** | パッケージ管理 | `pnpm-workspace.yaml` で対象を列挙。`workspace:*` で内部パッケージを参照 |
| **Turborepo** | タスクランナー | `turbo.json` でタスクの依存関係を定義。変更のないタスクはキャッシュから復元 |
| **Nx** | タスクランナー＋開発基盤 | 依存グラフの可視化、影響範囲（affected）だけの実行、コード生成、モジュール境界の lint ルール |

小〜中規模なら **pnpm workspaces + Turborepo**、パッケージ数が多く境界の強制まで欲しいなら **Nx** がよく選ばれます。

## 3. apps と packages の切り方

典型的な構成は次の通りです。

```text
repo/
├── apps/                 # デプロイする単位（利用する側）
│   ├── web/              # 顧客向け Next.js
│   └── admin/            # 管理画面
└── packages/             # 共有する単位（利用される側）
    ├── ui/               # 共有 UI コンポーネント
    ├── api-client/       # 型付き API クライアント
    ├── config-eslint/    # 共有 ESLint 設定
    └── config-ts/        # 共有 tsconfig
```

判断のルールは 3 つです。

1. **apps は packages に依存してよいが、逆は禁止**（依存は一方向）
2. **apps 同士は依存しない**。共有したくなったら packages に切り出す
3. **2 つ以上のアプリが使うまで packages に切り出さない**（YAGNI）

パッケージを切る粒度は、[[MOC_モジュール設計体系]] の凝集・結合の考え方（一緒に変わるものは一緒に置く）がそのまま使えます。

## 4. 共有 UI パッケージの設計

`packages/ui` は **デザインシステムの実装置き場** になります（[[01_デザインシステムの構成要素]]）。

```tsx
// packages/ui/src/Button.tsx
export type ButtonProps = {
  variant?: "primary" | "secondary";
  children: React.ReactNode;
} & React.ButtonHTMLAttributes<HTMLButtonElement>;

export function Button({ variant = "primary", ...rest }: ButtonProps) {
  return <button data-variant={variant} {...rest} />;
}
```

```json
// packages/ui/package.json（抜粋）
{
  "name": "@acme/ui",
  "exports": { "./button": "./src/Button.tsx" }
}
```

- **業務ロジックを入れない**（`OrderButton` ではなく `Button`）。業務知識はアプリ側の features に置く
- `exports` で **公開する入口を絞る**。内部ファイルへの直接 import を防げる
- 破壊的変更は利用側アプリが全部同じリポジトリにあるので、1 PR で直せる — これがモノレポ最大の利点

---

## 5. よくある失敗

| 失敗 | 症状 | 対策 |
|------|------|------|
| `packages/shared` に何でも入れる | 全アプリが巨大パッケージに依存し、変更の影響が読めない | 目的別に分ける（ui / api-client / utils） |
| 早すぎる切り出し | 使うのは 1 アプリだけのパッケージが増える | 2 つ目の利用者が現れてから |
| キャッシュ設定なし | CI が毎回全ビルドで遅い | Turborepo / Nx のキャッシュ・affected を使う |
| 依存ルールが口約束 | apps 同士の import が紛れ込む | [[04_依存ルールの自動検査]] で機械的に止める |

---

## まとめ

- モノレポは **共有コードを 1 PR で変えられる** のが最大の利点。代わりに CI の最適化が必要
- パッケージ管理（pnpm workspaces）とタスク実行（Turborepo / Nx）は別レイヤー
- `apps/` は使う側、`packages/` は使われる側。依存は apps → packages の一方向
- 共有 UI パッケージには業務ロジックを入れず、`exports` で入口を絞る
