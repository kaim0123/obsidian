# フロントエンドの規約とADR

## この章の目的

チームが大きくなっても設計がぶれないように、**規約を自動化する方法** と、**設計判断を ADR（Architecture Decision Record）として残す方法** を学ぶ章です。

---

## 1. 規約は「書く」より「機械に守らせる」

規約をドキュメントに書くだけでは、レビューで毎回指摘することになります。**機械で検査できるものは機械に任せ、人は判断が必要なことに集中する** のが基本方針です。

| レベル | 手段 | 例 |
|-------|------|-----|
| フォーマット | Prettier / Biome | インデント・引用符・改行 |
| コードの書き方 | ESLint / Biome | `no-unused-vars`、React Hooks のルール |
| 依存の方向 | eslint-plugin-boundaries / dependency-cruiser | `shared` から `features` を import しない |
| 型 | TypeScript（`strict: true`） | `any` の禁止、null チェック |
| アクセシビリティ | eslint-plugin-jsx-a11y / axe | `img` の `alt`、ラベルの欠落 |
| コミット時 | lint-staged + Husky など | 変更ファイルだけ検査 |
| CI | 上記を全部実行 | 違反があればマージ不可 |

依存の方向の検査は [[04_依存ルールの自動検査]] で詳しく扱います。

---

## 2. 人が決める規約

機械で検査できない規約は、**短く・理由付きで** 文書にします。

| 規約 | 例 |
|------|-----|
| 命名 | コンポーネントは名詞（`UserCard`）、フックは `use` + 動詞/名詞 |
| 置き場所 | 1 つの feature でしか使わないものは feature 内に置く |
| 状態 | サーバー由来のデータはサーバー状態ライブラリに置く（[[01_状態の分類と置き場所]]） |
| コンポーネント | Props は 5〜7 個を超えたら分割を検討 |

ポイントは **「なぜ」を必ず書く** ことです。理由のない規約は、例外が必要な場面で判断できません。

---

## 3. ADR とは

**ADR（Architecture Decision Record）** は、アーキテクチャ上の重要な判断を **1 件 1 ファイルの短い文書** で残す手法です。Michael Nygard が 2011 年のブログ記事「Documenting Architecture Decisions」で提案しました。

残す理由は、半年後に「なぜこうなっているのか」を誰も説明できなくなるのを防ぐためです。

```text
docs/adr/
├── 0001-use-feature-sliced-design.md
├── 0002-server-state-with-tanstack-query.md
└── 0003-styling-with-css-modules.md
```

- 連番で管理し、**一度決めた ADR は書き換えない**
- 判断を変えるときは新しい ADR を書き、古いほうを「Superseded by 0007」とする

---

## 4. ADR のテンプレート

Nygard の形式（タイトル / ステータス / コンテキスト / 決定 / 結果）が基本です。

```markdown
# 0002. サーバー状態の管理に TanStack Query を使う

## ステータス
Accepted（2026-09-25）

## コンテキスト
API から取得したデータを Redux に入れており、
ローディング・キャッシュ・再取得のコードが画面ごとに重複している。

## 決定
サーバー由来のデータは TanStack Query で管理する。
Redux（または Zustand）はクライアント固有の UI 状態だけに使う。

## 結果
- 良い: 取得・キャッシュ・再取得のコードが消える
- 悪い: 既存の Redux スライスの移行作業が必要
- 中立: 新メンバーはサーバー状態とクライアント状態の区別を学ぶ必要がある
```

---

## 5. フロントエンドで ADR にすべき判断

| 判断 | 例 |
|------|-----|
| レンダリング方式 | SSR / SSG / CSR をどう使い分けるか |
| ディレクトリ構成 | FSD を採るか、どの layer を使うか |
| 状態管理 | サーバー状態・グローバル状態に何を使うか |
| スタイリング | CSS Modules / Tailwind / CSS-in-JS |
| API との接続 | OpenAPI から型生成するか、tRPC か |
| テスト方針 | どの層をどのテストで守るか |

| ADR にする | ADR にしない |
|-----------|-------------|
| 変えるのが高くつく判断 | ライブラリの小さなバージョン更新 |
| 複数の選択肢を比較した判断 | 規約で決まっていて迷いがない選択 |
| 後から「なぜ？」と聞かれそうな判断 | 1 画面だけに閉じた実装の工夫 |

---

## まとめ

- 規約は **機械で検査できるものから自動化** し、人の規約は理由付きで短く書く
- ADR は重要な判断を 1 件 1 ファイルで残す手法（Nygard, 2011）
- ADR は書き換えず、判断を変えるときは新しい ADR で置き換える
- フロントでは レンダリング・構成・状態・スタイリング・API 接続が ADR の典型
