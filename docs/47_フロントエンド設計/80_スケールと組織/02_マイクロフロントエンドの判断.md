# マイクロフロントエンドの判断

## この章の目的

**マイクロフロントエンド（Micro-Frontends, MFE）** を「採るべきか・やめるべきか」を判断できるようになる章です。統合方式の違いと、MFE を採っても各アプリの内部設計は別に必要なことを学びます。構成そのものの説明は [[00_解説_フロントエンド構成]] を参照してください。

---

## 1. マイクロフロントエンドとは

マイクロサービスの考え方をフロントエンドに持ち込み、**1 つの画面を、独立して開発・デプロイできる複数のアプリで構成する** 方式です。2016 年ごろ ThoughtWorks Technology Radar で取り上げられて広まり、Cam Jackson の記事「Micro Frontends」（martinfowler.com, 2019）で整理されました。

```text
  ┌───────────── シェル（コンテナアプリ） ─────────────┐
  │  ヘッダー                                          │
  │  ┌──────────┐ ┌──────────┐ ┌──────────┐           │
  │  │ 検索 MFE │ │ 商品 MFE │ │ カート MFE│           │
  │  │ チームA  │ │ チームB  │ │ チームC  │           │
  │  └──────────┘ └──────────┘ └──────────┘           │
  └────────────────────────────────────────────────────┘
```

目的は技術ではなく **組織** です。複数チームが互いを待たずにリリースできることが最大の価値です。

---

## 2. 採る・やめるの判断

| 採る価値がある | やめたほうがよい |
|---------------|-----------------|
| 3 チーム以上が 1 つのフロントを触り、リリース待ちが常態化 | 1〜2 チームで開発している |
| 事業領域ごとにチームの責任範囲がはっきりしている | 領域の境界がまだ揺れている |
| レガシー画面を少しずつ新技術に置き換えたい | 性能（バンドルサイズ）が最優先 |
| プラットフォームチームが基盤を保守できる | 共通基盤を持つ人がいない |

判断の順番は次の通りです。

```text
  リリース待ち・衝突が本当に問題か？
        │ いいえ → モノリスのまま（ディレクトリで分ける）
        ▼ はい
  モノレポ + 機能別構成 + 依存ルールで解決できないか？
        │ できる → モノレポ + 機能別構成で十分
        ▼ できない（デプロイまで独立させたい）
  マイクロフロントエンドを検討
```

多くの場合、まず **1 つのアプリの中で機能別に分ける（FSD など）** ほうが安く、効果も大きいです。

## 3. 統合方式の比較

| 方式 | 統合のタイミング | 長所 | 短所 |
|------|----------------|------|------|
| **ビルド時統合**（npm パッケージとして取り込む） | ビルド時 | 単純・型安全 | 1 つ変えるとシェルの再デプロイが必要。独立デプロイにならない |
| **Module Federation**（webpack 5 / Rspack など） | 実行時（JS） | 独立デプロイ・依存の共有（React を 1 つだけ読むなど） | バージョン不一致の事故、設定が複雑 |
| **iframe** | 実行時（ブラウザ） | 最強の分離（CSS・JS が混ざらない） | 画面をまたぐ連携・ルーティング・a11y・レスポンシブが難しい |
| **Web Components**（Custom Elements） | 実行時（DOM） | フレームワーク非依存の境界 | SSR や React との props 受け渡しに工夫が要る |
| **サーバー／エッジでの合成**（SSI・ESI など） | リクエスト時 | 初期表示が速い | インタラクションの連携は別途必要 |

---

## 4. MFE の内部にも設計が要る

MFE が決めるのは **デプロイ単位の分け方** だけです。各 MFE の **内部をどう構成するか** は何も決めません。

```text
  MFE の境界（組織・デプロイ）
     └─ 各 MFE の内部（コード構成） ← FSD / bulletproof-react などが別に必要
```

そのため、各 MFE の中では [[02_Feature-Sliced_Design]] や [[03_bulletproof-reactの構成]] のような構成を採ります。MFE にしたのに中身がスパゲッティなら、小さなスパゲッティが複数できるだけです。

---

## 5. 横断の約束ごと

MFE にするなら、最初に次を決めておきます。

| 約束 | 例 |
|------|-----|
| デザインの一貫性 | 共通のデザインシステム（[[01_デザインシステムの構成要素]]） |
| MFE 間の通信 | URL・Custom Event など疎結合な手段に限る。相手の内部 state を直接読まない |
| 共有依存 | React などのバージョン方針（Module Federation の shared） |
| 認証 | シェルが持ち、MFE はトークンを受け取るだけ |

```tsx
// MFE 間は Custom Event で疎結合に通知する例
window.dispatchEvent(
  new CustomEvent("cart:item-added", { detail: { productId: "p-1" } })
);
```

---

## まとめ

- MFE は **組織の問題（独立リリース）** を解く手段。技術的な流行で採らない
- まずはモノリス内の機能別構成・モノレポで足りないかを確認する
- 統合方式はビルド時 / Module Federation / iframe / Web Components / サーバー合成でトレードオフが違う
- MFE の内部構成は別問題。各 MFE にも FSD などの設計が要る
