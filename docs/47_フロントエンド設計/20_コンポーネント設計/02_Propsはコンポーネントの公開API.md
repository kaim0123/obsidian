# Props はコンポーネントの公開 API

## この章の目的

コンポーネントの **Props を「関数の引数」や「モジュールの公開 API」と同じように設計する** 考え方を学ぶ章です。使う側が迷わず、変更に強い部品のインターフェースを作ることが目標です。

TypeScript での Props の型の書き方は [[10-4-Props設計]]（32_React）が本拠地です。

---

## 1. Props は契約である

コンポーネントを使う側から見えるのは Props だけです。Props は部品と利用者の **契約** です。

```text
  利用者 ──(Props)──▶ [ コンポーネント ] ──(イベント)──▶ 利用者
            公開 API       内部実装は隠す
```

| 良い API の性質 | Props での意味 |
|----------------|---------------|
| 少なく、わかりやすい | 必要な props だけを受け取る |
| 間違った使い方ができない | 矛盾する組み合わせを型で防ぐ |
| 内部を知らなくても使える | 実装の都合を props に出さない |
| 後から拡張しやすい | 既存の呼び出しを壊さずに追加できる |

46_メソッド設計 の「引数の設計」「情報隠蔽」と同じ原則が、そのまま Props に当てはまります。

---

## 2. 名前と形 — 利用者の言葉で

Props の名前は **部品の中身ではなく、利用者から見た意味** で付けます。

| 悪い例 | 良い例 | 理由 |
|--------|--------|------|
| `data` | `user` | 何のデータかわかる |
| `flag` | `isDisabled` | boolean は is / has / can |
| `handleClick` | `onSelect` | イベントは on + 利用者にとっての意味 |
| `bgColor="#f00"` | `variant="danger"` | 見た目の値ではなく意図を渡す |

特に `variant` のように **意図を渡す** 形にすると、デザインが変わっても利用側のコードは変わりません（デザイントークンとの接続は 50 で扱います）。

---

## 3. 矛盾する組み合わせを型で防ぐ

boolean の props が増えると、ありえない組み合わせが生まれます。

```tsx
// 悪い例: isLoading と error が同時に true になりうる
type Props = { isLoading: boolean; error?: string; data?: User[] };

// 良い例: 状態を 1 つの判別可能なユニオンで表す
type Props =
  | { status: 'loading' }
  | { status: 'error'; error: string }
  | { status: 'success'; data: User[] };
```

| パターン | 問題 | 対策 |
|----------|------|------|
| boolean の組み合わせ | `isPrimary && isDanger` が可能 | `variant: 'primary' \| 'danger'` |
| 状態フラグの乱立 | loading と error が同時 | 判別可能なユニオン |
| 片方だけ必要な props | `href` と `onClick` の両方を渡せる | ユニオンで排他にする |

---

## 4. 制御・非制御 — 状態を誰が持つか

入力系の部品では、**値を部品の中で持つか、利用者が持つか** を決める必要があります。

| | 非制御（uncontrolled） | 制御（controlled） |
|--|----------------------|-------------------|
| 値の持ち主 | 部品の内部 | 利用者（親） |
| Props | `defaultValue` | `value` + `onChange` |
| 向く場面 | 値を送信時に読むだけ | 入力に応じて他の UI が変わる |
| 向かない場面 | 入力と連動する表示がある | 単純なフォームで記述が増える |

汎用部品では **両方に対応** し、`value` が渡されたら制御、なければ非制御として振る舞う設計がよく使われます（ネイティブの `<input>` と同じ方式）。

---

## 5. 拡張に強くする — children とスロット

表示内容のバリエーションを props で増やし続けると、部品が肥大化します。

```tsx
// 悪い例: 表示のたびに props が増える
<Card title="..." subtitle="..." icon="..." showFooter footerText="..." />

// 良い例: 中身は children / スロットで利用者が組み立てる
<Card header={<CardTitle icon={<UserIcon />}>ユーザー</CardTitle>}>
  <UserProfile user={user} />
</Card>
```

| 手法 | 向く場面 | 向かない場面 |
|------|---------|-------------|
| 設定 props（`title`, `icon`） | 見た目を厳密に統一したい | バリエーションが多い |
| `children` | 中身を自由に差し込ませたい | 中身の構造を強制したい |
| 名前付きスロット（`header`, `footer`） | 差し込み口が複数ある | 差し込み口が 1 つだけ |

---

## 6. Props の数が多いときの見直し

Props が 7〜10 個を超えたら、部品の責務が大きすぎないかを疑います。

1. 一緒に変わる props をオブジェクトにまとめる（Parameter Object と同じ）
2. 表示の差し込みは children / スロットに逃がす
3. 役割が違うなら部品自体を分ける（[[01_コンポーネントの分割粒度と境界]]）
4. 部品を組み合わせる形（Compound）にする（[[03_コンポーネントパターンの比較]]）

---

## まとめ

- Props は部品の公開 API。少なく、わかりやすく、間違えにくく
- 名前は利用者から見た意味で。見た目の値より意図（variant）を渡す
- 矛盾する組み合わせは判別可能なユニオンで防ぐ
- 入力系は制御・非制御を意識して設計する
- 表示のバリエーションは children / スロットで吸収する
