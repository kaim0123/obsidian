# コンポーネントパターンの比較 — Container-Presentational・Headless・Compound

## この章の目的

コンポーネントの **ロジックと見た目の分け方** についての代表的なパターンを比較し、場面に応じて選べるようにする章です。各パターンの React での実装は 32_React の [[10-2-Container-Presentational]]・[[10-3-カスタムフック]]・[[10-5-Compound-Components-RenderProps]] が本拠地です。

---

## 1. パターンが解こうとしている問題

どのパターンも、根本では同じ問題を解いています。

```text
  1 つの部品に「見た目」と「振る舞い（状態・データ取得・操作）」が混ざる
    → 見た目だけ変えたい / 振る舞いだけ再利用したい ときに困る
```

| パターン | 分けるもの | 登場 |
|----------|-----------|------|
| Container-Presentational | データ取得・状態 と 表示 | 2015 年、Dan Abramov の記事で広まる |
| Render Props / HOC | 振る舞い を部品間で共有 | React コミュニティ（2016〜2017 年頃） |
| カスタムフック | 振る舞い を関数として共有 | React 16.8（2019 年）の Hooks 以降 |
| Compound Components | 1 つの UI を協調する複数部品に分ける | HTML の `<select>`/`<option>` に着想 |
| Headless UI | 振る舞い・a11y だけを提供し、見た目を持たない | Headless UI・Radix・TanStack Table など |

---

## 2. Container-Presentational

```text
  [ UserListContainer ]  データ取得・状態・イベント処理
          │ props
          ▼
  [ UserList ]           props を受け取って描くだけ
```

- **Presentational**: props → 見た目。状態を持たない（持っても UI 状態のみ）
- **Container**: データを用意し、Presentational に渡す

Hooks 登場後、Dan Abramov 自身が「このパターンを機械的に強制する必要はない」と追記しています。現在は **カスタムフックでロジックを切り出し、部品は 1 つのまま** にする書き方が主流です。ただし「表示専用の部品を作る」という考え方自体は、Storybook での確認やテストのしやすさの点で今も有効です。

---

## 3. カスタムフック（振る舞いの関数化）

```tsx
function useUserList() {
  const [keyword, setKeyword] = useState('');
  const { data } = useUsers(keyword);
  return { users: data ?? [], keyword, setKeyword };
}

function UserListPage() {
  const { users, keyword, setKeyword } = useUserList();
  return <UserList users={users} keyword={keyword} onKeywordChange={setKeyword} />;
}
```

Render Props や HOC が担っていた「振る舞いの共有」は、多くの場合カスタムフックで置き換えられます。部品の入れ子が深くならない点が大きな利点です。

---

## 4. Compound Components

1 つの UI を、**暗黙に状態を共有する複数の部品** として公開します。

```tsx
<Tabs defaultValue="profile">
  <Tabs.List>
    <Tabs.Trigger value="profile">プロフィール</Tabs.Trigger>
    <Tabs.Trigger value="settings">設定</Tabs.Trigger>
  </Tabs.List>
  <Tabs.Content value="profile"><Profile /></Tabs.Content>
</Tabs>
```

親（`Tabs`）が状態を持ち、Context で子に共有します。利用者は **並び順や中身を自由に組み立てられる** 一方、props を大量に渡す必要がありません。

---

## 5. Headless UI

**振る舞いとアクセシビリティ（キーボード操作・ARIA 属性）だけ** を提供し、見た目は利用者が付けるパターンです。

| 提供するもの | 提供しないもの |
|-------------|---------------|
| 開閉状態・フォーカス管理 | 色・余白・フォント |
| キーボード操作 | CSS |
| ARIA 属性 | デザイン |

Radix UI、Headless UI、React Aria、TanStack Table などが代表例です。**デザインシステムを自前で持つチーム** にとって、難しい a11y を再実装せずに見た目を完全に制御できる点が利点です。shadcn/ui は Radix の上にスタイルを付けたコードを自分のリポジトリにコピーして使う方式で、同じ考え方の延長にあります。

---

## 6. 比較と選び方

| パターン | 向く場面 | 向かない場面 |
|----------|---------|-------------|
| Container-Presentational | 表示部品を単独で確認・テストしたい | 小さな部品（分けるほうが冗長） |
| カスタムフック | 状態・データ取得のロジックを共有したい | 見た目ごと共有したい |
| Render Props | 描画の一部を利用者に委ねたい（仮想リストの行など） | 単純なロジック共有（フックで足りる） |
| Compound Components | 構造が柔軟な UI（Tabs, Menu, Accordion） | 構造が固定の単純な部品 |
| Headless UI | 独自デザインで a11y を担保したい | 既製デザインで早く作りたい |

```text
  見た目ごと再利用したい？ ── はい ──▶ 普通の部品（＋ variant）
        │いいえ
  構造を利用者に組ませたい？ ── はい ──▶ Compound Components
        │いいえ
  ロジックだけ共有したい？ ── はい ──▶ カスタムフック
        │                         （a11y が難しい UI なら Headless UI を採用）
        └── 表示を単独で確認したい ──▶ 表示専用部品に分ける
```

---

## まとめ

- どのパターンも「見た目」と「振る舞い」を分けるための手段
- Container-Presentational は考え方として有効だが、今はカスタムフックが主流
- Compound Components は構造が柔軟な UI の公開 API に向く
- Headless UI は独自デザイン × アクセシビリティ担保の定番
- パターンは目的で選ぶ。小さな部品に機械的に当てはめない
