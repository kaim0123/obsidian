# コンポーネントの分割粒度と境界

## この章の目的

画面を **どこで部品（コンポーネント）に分けるか** を判断する基準を学ぶ章です。「大きすぎる部品」と「細かすぎる部品」の両方を避けるための物差しを持つことが目標です。

React での具体的な分け方は [[10-1-UIコンポーネントとロジックの分離]]（32_React）が本拠地です。

---

## 1. なぜ分割するのか

コンポーネントを分ける目的は「ファイルを小さくすること」ではありません。

| 目的 | 意味 |
|------|------|
| **理解しやすくする** | 1 つの部品が 1 つの役割を持つ |
| **変更を局所化する** | 仕様変更の影響が 1 部品に収まる |
| **再利用する** | 同じ UI を複数画面で使う |
| **テストしやすくする** | 小さな単位で振る舞いを確かめる |
| **再レンダリングを絞る** | 変化する範囲を小さくする |

再利用は目的の 1 つにすぎません。**1 回しか使わない部品でも、理解と変更のために分ける価値はあります。**

---

## 2. 分割のサイン

次のような兆候があれば、分割を検討します。

| サイン | 例 |
|--------|-----|
| JSX にコメントで見出しを付けている | `{/* ヘッダー部分 */}` |
| 1 つの部品に無関係な状態が並ぶ | 検索キーワードとモーダルの開閉とタブ |
| 条件分岐で見た目が大きく切り替わる | `isEdit ? <巨大な JSX> : <巨大な JSX>` |
| 名前を付けにくい | `MainContent`, `Wrapper2` |
| 一部だけ頻繁に再レンダリングされる | 入力欄のたびに一覧全体が描き直される |

JSX のコメント見出しは、46_メソッド設計 の「コメントが構造を代弁しているサイン」と同じ考え方です。見出しの単位がそのまま部品の候補になります。

---

## 3. 境界の引き方 — 4 つの軸

部品の境界は、次の軸のどれかで引くと安定します。

```text
  ┌─────────────── ページ ───────────────┐
  │ ┌─ 見た目の塊 ─┐  ┌─ 状態の持ち主 ─┐ │
  │ │ Header       │  │ SearchPanel     │ │
  │ └──────────────┘  │  (keyword)      │ │
  │ ┌─ データの単位 ─────────────────┐   │
  │ │ UserCard（User 1 件）          │   │
  │ └────────────────────────────────┘   │
  └──────────────────────────────────────┘
```

| 軸 | 問い | 例 |
|----|------|-----|
| **見た目の塊** | デザイン上ひとまとまりか | Header, Card, Modal |
| **状態の持ち主** | この状態を使うのはどこまでか | 検索条件を持つ SearchPanel |
| **データの単位** | ドメインの 1 件に対応するか | UserCard, OrderRow |
| **変更の理由** | 誰の要望で変わるか | 価格表示（営業）と在庫表示（物流） |

最後の「変更の理由」は単一責任の原則（SRP）の考え方です。一緒に変わるものを同じ部品に、別々に変わるものを別の部品に置きます。

---

## 4. 粒度の目安 — 大きすぎ・細かすぎ

| | 大きすぎ | ちょうどよい | 細かすぎ |
|--|---------|------------|---------|
| 症状 | 読むのに全体を追う必要がある | 名前で中身が想像できる | 追うのにファイルを何枚も開く |
| Props | 使わない props が多い | 役割に必要な分だけ | props を素通しするだけの部品 |
| 変更 | 小さな変更で全体が影響 | 変更が 1〜2 部品に収まる | 1 つの変更で多数の部品を触る |

**細かすぎ** の典型は、props を下へ渡すだけの中間部品が何層も続く状態（props のバケツリレー）です。これは部品を増やしすぎたサインであり、`children` で組み立て直すか、状態の置き場所を見直します。

```tsx
// 中間部品が props を素通しするだけ → children で組み立てる
<Layout sidebar={<UserMenu user={user} />}>
  <Dashboard user={user} />
</Layout>
```

---

## 5. 分ける順番 — 抽出は後からでよい

最初から理想の粒度を狙う必要はありません。

1. ページ単位で素直に書く
2. 見出しコメントが付いた塊を部品に切り出す
3. 状態が一部でしか使われていなければ、その部品に状態を移す
4. 2 回目・3 回目に同じ UI が出たら共通部品にする（早すぎる共通化は避ける）

「3 回目で共通化」は DRY の早すぎる適用を避ける経験則です。似ているだけで変更理由が違う UI を共通化すると、props の分岐が増えて逆に扱いにくくなります。

---

## まとめ

- 分割の目的は理解・変更の局所化・テスト・再利用・再レンダリングの抑制
- JSX の見出しコメントや名前の付けにくさは分割のサイン
- 境界は見た目・状態の持ち主・データの単位・変更の理由で引く
- 細かすぎる分割（props の素通し）も問題。children で組み立て直す
- 共通化は同じ UI が繰り返し出てから
