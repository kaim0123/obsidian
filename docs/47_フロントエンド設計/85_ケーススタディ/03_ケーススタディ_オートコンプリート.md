# ケーススタディ：オートコンプリート

## この章の目的

検索ボックスに入力すると候補が出る **オートコンプリート** を、[[01_RADIOテンプレート]] に沿って設計する章です。小さな部品ですが、デバウンス・リクエストの競合・キャッシュ・アクセシビリティと、設計判断が詰まっています。

---

## 1. R — 要件

| 種類 | 内容 |
|------|------|
| 機能 | 入力に応じて候補を最大 10 件表示 / 矢印キーで選択 / Enter で確定 |
| 非機能 | 入力がもたつかない。サーバーへの無駄なリクエストを減らす |
| a11y | キーボードだけで操作でき、スクリーンリーダーが候補数と選択中の候補を読み上げる |
| 再利用 | 商品検索・ユーザー検索など、複数画面で使う汎用部品にする |

---

## 2. A — 全体構成

```text
  Autocomplete（汎用部品：UI と操作）
   ├─ input（combobox）
   └─ listbox
        └─ option × N
         ▲
         │ fetchSuggestions(query) を Props で受け取る
  ProductSearch（利用側：何を検索するかを知っている）
```

汎用部品は **何を検索するかを知らない** ようにします。取得関数を Props で受け取ることで、商品検索にもユーザー検索にも使えます（[[02_Propsはコンポーネントの公開API]]）。

---

## 3. D — データモデル

| 状態 | 種類 | 置き場所 |
|------|------|---------|
| 入力中の文字列 `query` | UI 状態 | Autocomplete 内の local state |
| 候補一覧 | サーバー状態 | query をキーにキャッシュ |
| 開閉 `isOpen` | UI 状態 | local state |
| 選択中の候補 `activeIndex` | UI 状態 | local state |

`isOpen` は「候補が 1 件以上あり、フォーカスがある」から **派生** できるなら state にしません（[[02_Single_Source_of_Truthと派生状態]]）。

---

## 4. I — インターフェース

### サーバー API

```text
GET /suggestions?q=<query>&limit=10  → { items: { id: string; label: string }[] }
```

### コンポーネントの Props

```tsx
type AutocompleteProps<T> = {
  label: string;
  fetchSuggestions: (query: string, signal: AbortSignal) => Promise<T[]>;
  getOptionLabel: (item: T) => string;
  onSelect: (item: T) => void;
  minChars?: number;   // 既定 2
  debounceMs?: number; // 既定 200
};
```

`signal` を受け取るのは、古いリクエストを取り消せるようにするためです。

---

## 5. O — 最適化と深掘り

### デバウンス

1 文字ごとにリクエストすると無駄が多いので、**入力が止まってから一定時間後** にだけ取得します。

```tsx
function useDebouncedValue<T>(value: T, ms: number) {
  const [v, setV] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setV(value), ms);
    return () => clearTimeout(id);
  }, [value, ms]);
  return v;
}
```

### 競合（レースコンディション）

「ap」の応答が「apple」の応答より **後に** 返ってくると、古い候補が表示されてしまいます。

```text
  入力: a → ap → apple
  応答:           apple の結果 ✓ → ap の結果（遅れて到着）✗ ← これを表示してはいけない
```

対策は 2 つあり、併用できます。

| 対策 | 方法 |
|------|------|
| 取り消す | 新しい入力のたびに `AbortController.abort()` で前のリクエストを止める |
| 無視する | 応答に対応する query が最新の query と一致するときだけ反映する |

サーバー状態ライブラリで query をキーにすれば、キーの切り替えで古い結果が表示されない仕組みを任せられます。

### キャッシュ

同じ query を打ち直したときは、キャッシュから即座に表示します。候補は変化が遅いので、数分のキャッシュで十分なことが多いです。

### アクセシビリティ（combobox パターン）

WAI-ARIA Authoring Practices の **combobox パターン** に従います（[[02_アクセシビリティを部品設計に組み込む]]）。

| 要素 | 属性 |
|------|------|
| input | `role="combobox"`、`aria-expanded`、`aria-controls`（listbox の id）、`aria-activedescendant`（選択中 option の id）、`aria-autocomplete="list"` |
| 候補の箱 | `role="listbox"` |
| 候補 | `role="option"`、`aria-selected` |
| 件数のお知らせ | `aria-live="polite"` の領域に「5 件の候補」 |

フォーカスは **input に置いたまま**、`aria-activedescendant` で選択中の候補を伝えるのがポイントです。

| キー | 動作 |
|------|------|
| ↓ / ↑ | 候補を移動 |
| Enter | 確定 |
| Escape | 閉じる（もう一度で入力を消す） |

### 自作か、ライブラリか

| 自作する | ライブラリ（Headless UI・Downshift など）を使う |
|---------|--------------------------------------------|
| 要件が特殊で既存部品に合わない | a11y を確実に満たしたい |
| 学習目的 | 開発時間を優先したい |

a11y の細部は抜けやすいので、実務では **振る舞いは Headless なライブラリ、見た目は自分たちのデザインシステム** という分担がよく選ばれます（[[03_コンポーネントパターンの比較]]）。

---

## まとめ

- 汎用部品は **何を検索するかを知らない**。取得関数を Props で受け取る
- デバウンスでリクエストを減らし、`AbortController` と「最新の query か」の確認で競合を防ぐ
- 候補は query をキーにしたサーバー状態としてキャッシュする
- a11y は combobox パターン：フォーカスは input、選択は `aria-activedescendant`
