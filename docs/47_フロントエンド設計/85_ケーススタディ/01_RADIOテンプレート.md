# RADIOテンプレート

## この章の目的

「この UI をどう設計するか」を **決まった順番で考えるための型** として、GreatFrontEnd が提唱する **RADIO フレームワーク** を学ぶ章です。85_ケーススタディの各ノートは、このテンプレートに沿って書かれています。

---

## 1. RADIO とは

フロントエンドのシステム設計を 5 段階で進める手順の頭文字です。もとは面接対策として整理されたものですが、実務の設計メモにもそのまま使えます。

```text
  R  Requirements      要件      何を作るか・どこまで作るか
  A  Architecture      全体構成  どんな部品があり、どうつながるか
  D  Data model        データ    どんなデータを、どこに持つか
  I  Interface (API)   境界      部品同士・サーバーとの約束
  O  Optimizations     最適化    性能・a11y・エラー・細部の深掘り
```

順番に意味があります。**要件が決まらないと構成は決まらず、構成が決まらないとデータの置き場所は決まらない** からです。

---

## 2. 各段階で問うこと

### R — Requirements（要件）

| 問い | 例 |
|------|-----|
| 主要なユースケースは？ | 投稿を見る・いいねする・新しい投稿を読む |
| 対象デバイス・環境は？ | モバイル中心、低速回線あり |
| 規模は？ | 1 画面に何件、どれくらいの頻度で更新 |
| 範囲外は？ | 投稿の作成は今回扱わない |

### A — Architecture（全体構成）

- 画面をどんな **コンポーネント** に分けるか（[[01_コンポーネントの分割粒度と境界]]）
- どこが **サーバー状態**、どこが **クライアント状態** か
- レンダリング方式（SSR / CSR）と、API との接続点

### D — Data model（データ）

- 主要なエンティティとフィールド
- それぞれの **置き場所**（[[01_状態の分類と置き場所]]）
- 正規化するか、**真実の源（SSOT）** はどこか（[[02_Single_Source_of_Truthと派生状態]]）

### I — Interface（境界）

- サーバー API：エンドポイント・パラメータ・レスポンス・ページネーション
- コンポーネント API：主要コンポーネントの Props（[[02_Propsはコンポーネントの公開API]]）

### O — Optimizations（最適化・深掘り）

- 性能：初期表示・再レンダリング・大量リスト（[[03_パフォーマンスを設計で作り込む]]）
- アクセシビリティ：キーボード操作・読み上げ（[[02_アクセシビリティを部品設計に組み込む]]）
- エラー・オフライン（[[04_エラー境界とフォールバックUI]]）
- セキュリティ・国際化

---

## 3. 記入テンプレート

新しい設計メモを書くときは、次をコピーして埋めます。

```markdown
# 〇〇の設計

## R. 要件
- 機能要件:
- 非機能要件（性能・対応端末・a11y）:
- 範囲外:

## A. 全体構成
（コンポーネント図を ASCII で）
- サーバー状態:
- クライアント状態:
- レンダリング方式:

## D. データモデル
| エンティティ | 主なフィールド | 置き場所 |
|---|---|---|

## I. インターフェース
- サーバー API:
- 主要コンポーネントの Props:

## O. 最適化・深掘り
- 性能:
- a11y:
- エラー・オフライン:
- トレードオフと選ばなかった案:
```

---

## 4. 使うときのコツ

| コツ | 理由 |
|------|------|
| R に時間を使う | 範囲を決めないと O で話が発散する |
| A は箱と矢印だけで描く | 細部はあとで変わる。まず全体の形を合意する |
| D と I は表にする | 抜け漏れが見える |
| O は「選ばなかった案」も書く | 判断の理由が残る（[[03_フロントエンドの規約とADR]]） |

| 向く場面 | 向かない場面 |
|---------|-------------|
| 新しい画面・機能の設計を始めるとき | 既存画面の小さな修正 |
| 設計レビューの資料 | ライブラリの使い方の調査 |
| フロントエンドのシステム設計面接 | デザインの見た目だけの議論 |

---

## まとめ

- RADIO = 要件 → 全体構成 → データ → 境界 → 最適化 の順に考える型
- 順番に意味がある。前の段階が決まらないと次が決まらない
- 各段階は 47 の各フォルダ（20〜70）の知識を使う総合演習になる
- 記入テンプレートを使い、「選ばなかった案」も残す
