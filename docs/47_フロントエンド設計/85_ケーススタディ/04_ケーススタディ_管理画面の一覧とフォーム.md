# ケーススタディ：管理画面の一覧とフォーム

## この章の目的

業務システムでいちばんよく作る **「一覧（検索・並び替え・ページング）＋ 編集フォーム」** を、[[01_RADIOテンプレート]] に沿って設計する章です。状態の 3 分類（URL 状態・サーバー状態・フォーム状態）の使い分けと、FSD でのディレクトリ配置までを通して扱う、47 の総合演習です。

---

## 1. R — 要件

| 種類 | 内容 |
|------|------|
| 一覧 | 顧客の一覧。キーワード・ステータスで絞り込み、列で並び替え、ページング |
| 編集 | 行をクリックすると編集画面。保存するとサーバーに反映され、一覧に戻る |
| 共有 | 絞り込んだ状態の URL を同僚に送ると同じ一覧が見える |
| 非機能 | 入力ミスは送信前に分かる。保存中の二重送信を防ぐ |

「URL で共有できる」という要件が、状態の置き場所を決める鍵になります。

---

## 2. A — 全体構成

```text
  /customers?q=山田&status=active&sort=-createdAt&page=2
   └─ CustomerListPage
        ├─ CustomerFilter      ← URL 状態を読み書き
        ├─ CustomerTable       ← サーバー状態を表示
        └─ Pagination          ← URL 状態を読み書き

  /customers/:id/edit
   └─ CustomerEditPage
        └─ CustomerForm        ← フォーム状態 → 送信でサーバー状態を更新
```

---

## 3. D — データモデルと状態の置き場所

| 状態 | 種類 | 置き場所 | 理由 |
|------|------|---------|------|
| q / status / sort / page | URL 状態 | クエリパラメータ | 共有・ブラウザバック・再読み込みで保たれる |
| 顧客一覧・総件数 | サーバー状態 | サーバー状態ライブラリ（URL 状態をキーに） | 真実の源はサーバー |
| 編集中の入力値・エラー | フォーム状態 | フォームライブラリ | 送信までは下書き |
| 行の選択・モーダル開閉 | UI 状態 | local state | その画面だけの一時的な状態 |

ポイントは **絞り込み条件を useState に持たない** ことです。useState に持つと URL と二重管理になり、共有もブラウザバックも壊れます（[[01_状態の分類と置き場所]]、[[02_Single_Source_of_Truthと派生状態]]）。

```tsx
// URL を真実の源にし、サーバー状態のキーに使う
function useCustomerListParams() {
  const [sp, setSp] = useSearchParams();
  const params = {
    q: sp.get("q") ?? "",
    status: sp.get("status") ?? "all",
    sort: sp.get("sort") ?? "-createdAt",
    page: Number(sp.get("page") ?? "1"),
  };
  const update = (patch: Partial<typeof params>) =>
    setSp({ ...Object.fromEntries(sp), ...patch, page: String(patch.page ?? 1) });
  return [params, update] as const;
}

const { data } = useQuery({
  queryKey: ["customers", params],
  queryFn: () => customerApi.list(params),
});
```

絞り込みを変えたら `page` を 1 に戻すのも、ここで一か所にまとめます。

## 4. I — インターフェース

### サーバー API

```text
GET   /customers?q=&status=&sort=-createdAt&page=2&perPage=20
      → { items: Customer[], total: number }
GET   /customers/:id
PATCH /customers/:id   → 400 のときは { errors: { field: message } }
```

一覧は総件数が必要で任意ページに飛ぶので、フィードと違い **オフセット（ページ番号）方式** が向きます（[[02_ケーススタディ_ニュースフィード]] と比較）。

### 型とバリデーション

入力の検証ルールは **スキーマ 1 つ** に集め、フォームの検証と型の両方に使います（[[02_APIレイヤと型の共有]]）。

```ts
export const customerSchema = z.object({
  name: z.string().min(1, "名前は必須です"),
  email: z.string().email("メールアドレスの形式が正しくありません"),
  status: z.enum(["active", "inactive"]),
});
export type CustomerInput = z.infer<typeof customerSchema>;
```

クライアントの検証は **使いやすさのため**、サーバーの検証は **正しさのため** です。サーバーから返った 400 のエラーもフォームの各項目に表示します（[[01_フロントとサーバーの責務分担]]）。

## 5. O — 最適化と深掘り

### 保存の流れ

```text
  送信 → ボタンを無効化（二重送信防止）→ PATCH
    成功: 一覧のキャッシュを無効化 → 一覧へ戻る（URL 状態はそのまま）
    400 : 項目ごとのエラーをフォームに表示
    その他: 画面上部にエラー + 入力内容は保持
```

一覧に戻ったとき、絞り込み条件が URL に残っているので、**編集前と同じ一覧** に戻れます。

### 一覧の体験

| 工夫 | 方法 |
|------|------|
| キーワード入力でちらつかない | デバウンスしてから URL を更新（[[03_ケーススタディ_オートコンプリート]]） |
| ページ切り替えで表が消えない | 前のデータを表示したまま次を取得（TanStack Query の `placeholderData`） |
| 空の結果 | 「条件に一致する顧客はいません」と条件のクリアボタン |

### アクセシビリティ

- 表は `<table>` と `<th scope="col">` を使い、並び替え中の列に `aria-sort` を付ける
- フォームの各項目に `<label>`、エラーは `aria-describedby` で項目に結び付け、`aria-invalid` を付ける（[[02_アクセシビリティを部品設計に組み込む]]）

## 6. ディレクトリ配置（FSD）

[[02_Feature-Sliced_Design]] の layer に当てはめると次のようになります。

```text
src/
├── pages/
│   ├── customer-list/        # 画面の組み立てだけ
│   └── customer-edit/
├── widgets/
│   └── customer-table/       # 表 + ページング（複数ページで再利用するなら）
├── features/
│   ├── customer-filter/      # 絞り込み操作（URL 状態の読み書き）
│   └── customer-edit-form/   # 編集フォーム・送信
├── entities/
│   └── customer/             # model（型・スキーマ）・api・表示用の小部品
└── shared/
    ├── ui/                   # Button・Table・TextField
    └── api/                  # HTTP クライアント
```

| 置き場所の判断 | 理由 |
|---------------|------|
| スキーマ・型は `entities/customer` | 一覧・編集フォームの両方が使う業務の概念 |
| 絞り込みは `features` | ユーザーの操作（振る舞い）の単位 |
| 汎用の Table は `shared/ui` | 業務を知らない部品 |

依存は `pages → widgets → features → entities → shared` の一方向で、[[04_依存ルールの自動検査]] で守ります。

---

## まとめ

- 状態は 3 つに分ける：**絞り込みは URL 状態、一覧はサーバー状態、編集中はフォーム状態**
- 絞り込み条件を useState に持たない。URL を真実の源にし、サーバー状態のキーに使う
- 検証ルールはスキーマ 1 つにまとめ、型にも使う。サーバーのエラーもフォームに返す
- 保存後はキャッシュを無効化して一覧へ。URL 状態のおかげで元の一覧に戻れる
- FSD では型・スキーマは entities、操作は features、画面の組み立ては pages
