# エラー境界とフォールバックUI

## この章の目的

エラーが起きたときに **画面のどこまでを壊し、何を代わりに見せ、どう回復させるか** を設計できるようになる章です。Error Boundary と Suspense による境界の置き方、エラーの分類、リトライ UI を扱います。

React での実装詳細は 32_React/18_エラーハンドリングと品質、HTTP エラーの扱いは 37（[[MOC_HTTPクライアント体系]]）が本拠地です。

---

## 1. 何もしないと何が起きるか

React では、描画中に例外が発生して誰も捕まえないと、**アプリ全体がアンマウントされ真っ白な画面** になります。

```text
  App
   ├ Header
   ├ Sidebar
   └ Main
      ├ OrderList
      └ RecommendWidget  ← ここで例外
                ↓
  境界がない → App 全体が消える（真っ白）
  境界がある → RecommendWidget だけ「表示できませんでした」
```

設計のゴールは、**壊れる範囲を小さくし、ユーザーが次の行動をとれる状態を保つ** ことです。

---

## 2. エラーの分類 — 誰が・どう対処できるか

すべてのエラーを同じ画面で扱うと、ユーザーは何をすればよいか分かりません。まず分類します。

| 分類 | 例 | ユーザーができること | 表示場所 |
|---|---|---|---|
| 入力エラー | 必須項目が空・形式が違う | 直して再送信 | フォームの項目のそば |
| 業務エラー | 在庫切れ・権限なし | 別の操作を選ぶ | 画面内のメッセージ |
| 一時的な障害 | ネットワーク切断・タイムアウト・503 | **再試行** | その部品の位置 + リトライボタン |
| 認証切れ | 401 | 再ログイン | ログイン画面へ誘導 |
| 存在しない | 404 | 別のページへ | Not Found 画面 |
| バグ | 描画中の例外・想定外の値 | できない（報告） | Error Boundary のフォールバック |

**上の 4 つは予期できるエラー** なので、Error Boundary に投げずに **状態として扱い** ます。Error Boundary は主に **予期しないエラー（バグ）の最後の砦** です。

---

## 3. Error Boundary — 壊れる範囲を区切る

Error Boundary は、子孫の **描画中・ライフサイクル中** の例外を捕まえて、代わりの UI を表示します。イベントハンドラ内や非同期処理（`setTimeout`、Promise）の例外は捕まえない点に注意が必要です。

```tsx
import { ErrorBoundary } from "react-error-boundary";

<ErrorBoundary
  FallbackComponent={({ resetErrorBoundary }) => (
    <div role="alert">
      <p>おすすめを表示できませんでした。</p>
      <button onClick={resetErrorBoundary}>再読み込み</button>
    </div>
  )}
  onError={(error) => reportError(error)} // 監視サービスへ送る
>
  <RecommendWidget />
</ErrorBoundary>
```

**どこに置くか** は、3 段階で考えるのが定番です。

| 粒度 | 置き場所 | フォールバック |
|---|---|---|
| アプリ全体 | ルート | 「問題が発生しました」+ トップへ戻る |
| ページ / ルート | 各画面 | ナビゲーションを残したまま本文だけ差し替え |
| 部品（ウィジェット） | 独立した領域（おすすめ・グラフなど） | その領域だけ差し替え |

判断の基準は「**この部分が壊れても、残りの画面は使えるか**」です。使えるなら境界を置きます。

---

## 4. Suspense と組み合わせる — 読み込み中・失敗・成功

データ取得を伴う部品は、**読み込み中・失敗・成功** の 3 状態を持ちます。Suspense（読み込み中）と Error Boundary（失敗）を **同じ単位で並べる** と、状態ごとの表示を宣言的に書けます。

```tsx
<ErrorBoundary FallbackComponent={OrderListError}>
  <Suspense fallback={<OrderListSkeleton />}>
    <OrderList />  {/* データ取得中は suspend、失敗は throw */}
  </Suspense>
</ErrorBoundary>
```

| 状態 | 表示 | 設計のポイント |
|---|---|---|
| 読み込み中 | スケルトン | 最終形と同じ大きさ（CLS 対策、[[03_パフォーマンスを設計で作り込む]]） |
| 失敗 | エラー表示 + リトライ | 何が起きたか・何ができるかを書く |
| 成功（0 件） | 空状態 | 「まだ注文はありません」+ 次の行動 |

**空状態を失敗と混同しない** ことも重要です。0 件はエラーではありません。

Next.js App Router の `error.tsx` / `loading.tsx` は、ルート単位でこの組み合わせを自動で作る仕組みです。

## 5. リトライ UI — 回復の手段を用意する

一時的な障害は、**再試行すれば直る** ことが多いエラーです。

| 手段 | 内容 | 注意点 |
|---|---|---|
| 自動リトライ | 数回まで間隔をあけて再試行（指数バックオフ） | 4xx（入力エラー・権限）はリトライしない |
| 手動リトライ | 「再試行」ボタン | 押したら境界をリセットし、データを取り直す |
| 楽観的更新の巻き戻し | 送信失敗時に画面を元に戻す | 何が戻ったかを通知する |

```tsx
// TanStack Query と組み合わせる例 — 境界のリセット時にクエリも再実行
const { reset } = useQueryErrorResetBoundary();
<ErrorBoundary onReset={reset} FallbackComponent={OrderListError}>…</ErrorBoundary>
```

自動リトライの設定は 37 のリトライ・タイムアウト設計が本拠地です。

---

## 6. 監視 — 捕まえたエラーを知る

フォールバックを表示しただけでは、開発者はエラーに気づけません。

- `onError` で監視サービス（Sentry など）へ送る
- ユーザー ID・画面・直前の操作を添える（個人情報は送らない）
- 「同じエラーが何人に起きたか」で優先度を付ける

---

## まとめ

- 予期できるエラー（入力・業務・一時障害・認証・404）は **状態として扱う**。Error Boundary はバグの最後の砦
- 境界は「アプリ / ページ / 部品」の 3 段階で、「壊れても残りが使えるか」で置き場所を決める
- Suspense と Error Boundary を同じ単位で並べ、読み込み中・失敗・空・成功を区別する
- 一時障害にはリトライ手段を用意し、捕まえたエラーは監視に送る
