# パフォーマンスを設計で作り込む

## この章の目的

パフォーマンスを「遅くなってから直すもの」ではなく、**設計段階の判断で大部分が決まるもの** として扱えるようになる章です。Core Web Vitals（LCP / INP / CLS）を物差しに、バンドル分割・レンダリング境界・画像の扱いを整理します。

計測と個別の最適化は 66_パフォーマンス（[[01_パフォーマンスとは何か|パフォーマンスとは何か]]）と 32_React/11_パフォーマンス（[[Part 13 初期ロード最適化：Code SplittingとLazy Loading設計]] など）が本拠地です。

---

## 1. 物差し — Core Web Vitals

Google が定める **Core Web Vitals** は、ユーザー体験を 3 つの指標で測ります。2024 年 3 月に、応答性の指標は FID から **INP** に置き換わりました。

| 指標 | 測るもの | 「良好」の目安 | 主に効く設計判断 |
|---|---|---|---|
| **LCP**（Largest Contentful Paint） | 主要コンテンツが表示されるまで | 2.5 秒以下 | レンダリング方式・画像・初期 JS 量 |
| **INP**（Interaction to Next Paint） | 操作してから画面が反応するまで | 200 ミリ秒以下 | メインスレッドの負荷・再レンダリング範囲 |
| **CLS**（Cumulative Layout Shift） | レイアウトのずれ | 0.1 以下 | 画像・広告・遅延要素の領域確保 |

目安は、実ユーザーの **75 パーセンタイル** で判定します。

---

## 2. 設計で決まる部分と、後で直せる部分

```text
  設計段階で決まる（後から変えるのが高い）       後から直せる
  ─────────────────────────────              ─────────────
  レンダリング方式（CSR / SSR / SSG / RSC）       個別の memo 化
  状態の置き場所（再レンダリング範囲）             画像フォーマット変換
  依存ライブラリの選定（バンドルサイズ）           遅延読み込みの追加
  データ取得の設計（ウォーターフォール）           キャッシュ設定の調整
```

左側を間違えると、右側をいくら頑張っても限界があります。

---

## 3. 初期表示（LCP）— 送る JS を減らす

| 設計判断 | 内容 |
|---|---|
| レンダリング方式 | 表示内容が決まっているページは SSG / SSR で HTML を先に返す（[[00_解説_フロントエンド構成]]） |
| ルート単位の分割 | 画面ごとに JS を分け、最初の画面に不要なコードを送らない |
| 重い部品の遅延 | エディタ・グラフ・地図などは `lazy` で必要になってから読み込む |
| ライブラリ選定 | 導入前にサイズを確認（bundlephobia など）。日付・ユーティリティは軽量な代替を検討 |
| RSC | サーバーだけで使う処理のコードはクライアントに送られない |

```tsx
// 重い部品は必要なときだけ読み込む
const Chart = lazy(() => import("./Chart"));
<Suspense fallback={<ChartSkeleton />}><Chart data={data} /></Suspense>
```

**データ取得のウォーターフォール** にも注意します。親が取得 → 描画 → 子が取得、という直列の連鎖は、ルートやサーバー側でまとめて並列に取得する設計で避けます。

---

## 4. 応答性（INP）— レンダリングの境界を設計する

INP を悪化させる主な原因は、**操作のたびに広い範囲が再レンダリングされる** ことと、**メインスレッドを長く占有する処理** です。

| 原因 | 設計での対処 |
|---|---|
| 状態を上に置きすぎる | 状態は使う部品の近くに置く（[[01_状態の分類と置き場所]]） |
| 巨大な Context の値が頻繁に変わる | Context を分割する / 状態管理ライブラリのセレクタを使う |
| 長いリストを全部描画 | 仮想化（表示範囲だけ描画） |
| 重い計算を入力のたびに実行 | `useDeferredValue` / `useTransition` で優先度を下げる、Web Worker に逃がす |

```text
  状態を上に置いた場合                 状態を近くに置いた場合
  App（検索文字列）                    App
   ├ Header       ← 再描画             ├ Header
   ├ SearchBox    ← 再描画             ├ SearchArea（検索文字列）
   └ ResultList   ← 再描画             │  ├ SearchBox  ← 再描画
                                       │  └ ResultList ← 再描画
                                       └ Footer
```

---

## 5. 安定性（CLS）— 領域を先に確保する

| 原因 | 対処 |
|---|---|
| 画像のサイズ未指定 | `width` / `height` か `aspect-ratio` を必ず指定 |
| 後から出るバナー・広告 | 表示領域を先に確保する |
| Web フォントの切り替え | `font-display` の指定、フォールバックフォントのサイズ調整 |
| ローディング表示 | 最終形と同じ大きさのスケルトンを使う |

---

## 6. 画像 — 最も効果が大きい資源

LCP の対象要素は画像であることが多いため、画像の扱いは設計ルールとして決めておきます。

- 最初に見える画像（LCP 候補）は **遅延読み込みしない**、`fetchpriority="high"` を検討
- それ以外は `loading="lazy"`
- `srcset` / `sizes` で画面幅に合ったサイズを配信、AVIF / WebP を使う
- フレームワークの画像コンポーネント（Next.js の `Image` など）があれば標準にする

---

## 7. 予算で守る

**パフォーマンス予算** を決めて CI で監視すると、設計判断の劣化を早く検出できます。

| 予算の例 | 監視方法 |
|---|---|
| 初期 JS 200KB（圧縮後）以下 | バンドルサイズの CI チェック |
| LCP 2.5 秒以下 | Lighthouse CI / 実ユーザー計測（RUM） |

---

## まとめ

- 物差しは Core Web Vitals（LCP / INP / CLS）、実ユーザーの 75 パーセンタイルで見る
- レンダリング方式・状態の置き場所・ライブラリ選定は後から変えにくい。設計段階で決める
- LCP は送る JS を減らす、INP は再レンダリング範囲を絞る、CLS は領域を先に確保する
- 予算を決めて CI で監視し、劣化を早く見つける
