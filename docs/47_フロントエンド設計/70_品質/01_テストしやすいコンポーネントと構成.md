# テストしやすいコンポーネントと構成

## この章の目的

**テストが書きやすいかどうかは設計で決まる** ことを理解し、どの層を・どの種類のテストで守るかを判断できるようになる章です。Testing Trophy、ロジックの分離、MSW によるネットワークのモックを扱います。

テストの種類と Testing Library の使い方は 32_React（[[13-1-テストの種類]]、[[13-2-Testing-Libraryの基本]]）、テスト戦略全体は 81_テスト戦略 が本拠地です。

---

## 1. Testing Trophy — フロントエンドのテスト配分

Kent C. Dodds が提唱した **Testing Trophy** は、フロントエンドでは **統合テストを厚くする** 配分を勧めます。

```text
          ╭───╮       E2E（少数・重要な導線だけ）
        ╭─┴───┴─╮
        │ 統合   │    ← 最も厚く：画面単位で振る舞いを確認
        │ テスト │
        ╰─┬───┬─╯
          │単体│      純粋なロジック（計算・変換）
        ══╧═══╧══
          静的解析     TypeScript・ESLint
```

| 層 | 対象 | 道具の例 |
|---|---|---|
| 静的解析 | 型の誤り・危険な書き方 | TypeScript, ESLint |
| 単体 | 純粋関数・カスタムフックのロジック | Vitest, Jest |
| 統合 | コンポーネント + 状態 + API のモック | Testing Library + MSW |
| E2E | ログイン → 購入など主要導線 | Playwright, Cypress |

理由は、**ユーザーが触るのは部品の組み合わせ** だからです。細かい部品を個別にテストしても、組み合わせたときの不具合は見つかりません。

## 2. テストしにくいコンポーネントの特徴

```tsx
// テストしにくい例
function OrderPage() {
  const [orders, setOrders] = useState<Order[]>([]);
  useEffect(() => {
    fetch("/api/orders").then(r => r.json()).then(setOrders); // 通信が直書き
  }, []);
  const total = orders.reduce((s, o) => s + o.price * 1.1, 0); // 計算が埋め込み
  return <div>{new Date().toLocaleDateString()} 合計: {total}</div>; // 現在時刻に依存
}
```

| 特徴 | 何が困るか | 設計での対処 |
|---|---|---|
| 通信が直書き | テストで本物の API を叩く | API レイヤに分離し、MSW でモック |
| 計算が JSX に埋め込み | 計算だけを検証できない | 純粋関数に切り出す |
| 現在時刻・乱数に依存 | 結果が毎回変わる | 引数や props で注入する |
| グローバル状態に直接依存 | テストごとに状態が漏れる | Provider で包んで初期値を渡す |

## 3. ロジックの分離 — テストの層を分ける設計

ロジックを **純粋関数 → カスタムフック → 表示コンポーネント** に分けると、それぞれに合ったテストを書けます（[[10-1-UIコンポーネントとロジックの分離]]、[[10-3-カスタムフック]]）。

```ts
// 1. 純粋関数 — 単体テストが最も簡単
export const calcTotal = (orders: Order[], taxRate: number) =>
  orders.reduce((s, o) => s + o.price, 0) * (1 + taxRate);
```

```tsx
// 2. 表示 — props だけで描画が決まる
export function OrderSummary({ total }: { total: number }) {
  return <p>合計: {total.toLocaleString()}円</p>;
}
```

| 層 | テスト方法 | 速さ |
|---|---|---|
| 純粋関数 | 入力 → 出力を assert | 非常に速い |
| カスタムフック | `renderHook` または画面の統合テストで | 速い |
| 表示コンポーネント | props を渡して描画を確認 / Storybook | 速い |
| 画面（組み合わせ） | 統合テスト + MSW | 中 |

## 4. MSW — ネットワーク層でモックする

**MSW（Mock Service Worker）** は、fetch や axios を差し替えるのではなく、**リクエストをネットワークの層で横取り** して偽のレスポンスを返します。

```ts
// mocks/handlers.ts
import { http, HttpResponse } from "msw";
export const handlers = [
  http.get("/api/orders", () => HttpResponse.json([{ id: "o_1", price: 1000 }])),
];
```

| 利点 | 説明 |
|---|---|
| 実装の詳細に依存しない | fetch から axios に変えてもテストはそのまま |
| 開発でも使える | バックエンド未完成でも画面を作れる |
| Storybook と共有できる | 同じハンドラを部品カタログでも使う |

エラー系（500・タイムアウト）もハンドラで再現できるため、[[04_エラー境界とフォールバックUI]] の確認にも使えます。

## 5. 構成の判断 — どこまでテストするか

| 判断 | 目安 |
|---|---|
| 単体テストを書く対象 | 分岐の多い計算・変換・バリデーション |
| 統合テストの単位 | 1 画面 or 1 機能（Feature）単位 |
| E2E の対象 | 止まると売上や業務に直結する導線だけ |
| 見た目の確認 | Storybook + ビジュアルリグレッション |

テストは **実装ではなく振る舞い** を検証します。「state が変わったか」ではなく「画面に何が表示されたか」を確認すると、リファクタリングで壊れにくくなります。

---

## まとめ

- Testing Trophy では **統合テストを最も厚く**、E2E は主要導線だけに絞る
- テストしにくさの原因（通信直書き・計算埋め込み・時刻依存）は設計で取り除く
- 純粋関数・フック・表示に分けると、層ごとに最適なテストが書ける
- MSW でネットワーク層をモックすれば、実装を変えてもテストが壊れない
