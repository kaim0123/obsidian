# アクセシビリティを部品設計に組み込む

## この章の目的

アクセシビリティ（a11y）を「最後にチェックするもの」ではなく、**共通部品の設計に最初から組み込むもの** として扱えるようになる章です。セマンティクス、WAI-ARIA Authoring Practices Guide（APG）、フォーカス管理、Headless UI の活用を扱います。

HTML の基礎としての a11y は 21_HTML（[[12-アクセシビリティ]]）、自動チェックの運用は 86_QAプロセス（[[04_アクセシビリティ（axe-core）]]）が本拠地です。

---

## 1. なぜ「部品の設計」で扱うのか

a11y の問題の多くは、**共通部品 1 つの作りの悪さが全画面に広がる** ことで起きます。

```text
  Dialog 部品にフォーカス管理がない
        │
        ├─▶ 注文確認ダイアログ   ─ キーボードで閉じられない
        ├─▶ 削除確認ダイアログ   ─ スクリーンリーダーが背景を読む
        └─▶ 設定ダイアログ       ─ 閉じた後フォーカスが迷子
```

逆に言えば、**共通部品を正しく作れば、全画面がまとめて改善** します。a11y はデザインシステム（[[01_デザインシステムの構成要素]]）の品質基準に含めるべきものです。

基準としては **WCAG 2.2**（W3C の勧告）が使われ、多くの組織は **適合レベル AA** を目標にします。

---

## 2. 原則1 — まずネイティブ要素を使う

WAI-ARIA の第一原則は「**ネイティブの HTML 要素で済むなら ARIA を使わない**」です。

```tsx
// 悪い例 — div をボタンにすると、キーボード操作・役割・フォーカスを自前で作る必要がある
<div className="btn" onClick={save}>保存</div>

// 良い例 — button は Enter/Space・フォーカス・役割がすべて標準で付く
<button type="button" onClick={save}>保存</button>
```

| やりたいこと | 使う要素 |
|---|---|
| 操作する | `button` |
| 移動する | `a href` |
| 入力に名前を付ける | `label` + `input`（`htmlFor` / `id`） |
| 見出し構造 | `h1`〜`h6` を順番通りに |
| 領域 | `header` `nav` `main` `footer` |

「ボタンかリンクか」は **押すと何が起きるか** で決めます。画面遷移ならリンク、処理の実行ならボタンです。

---

## 3. 原則2 — 複雑な部品は APG のパターンに従う

タブ・コンボボックス・メニュー・ダイアログなど、ネイティブ要素がない部品は **WAI-ARIA Authoring Practices Guide（APG）** のパターンに従います。APG は、部品ごとに **必要な role・aria 属性・キーボード操作** を定めています。

| 部品 | 主な role | 期待されるキーボード操作（抜粋） |
|---|---|---|
| Tabs | `tablist` / `tab` / `tabpanel` | ←→ でタブ移動 |
| Dialog（モーダル） | `dialog` + `aria-modal="true"` | Esc で閉じる、Tab がダイアログ内で循環 |
| Combobox | `combobox` / `listbox` / `option` | ↑↓ で候補移動、Enter で確定 |
| Menu | `menu` / `menuitem` | ↑↓ で移動、Esc で閉じる |

自作する場合は、この表を **部品の仕様書** として扱い、テストで確認します。

---

## 4. 原則3 — フォーカスを設計する

キーボード利用者とスクリーンリーダー利用者にとって、**フォーカスの位置 = 今いる場所** です。

| 場面 | フォーカスの正しい動き |
|---|---|
| モーダルを開く | ダイアログ内の最初の要素（または見出し）へ移す |
| モーダルを閉じる | **開いたボタンに戻す** |
| SPA で画面遷移 | 新しい画面の見出しへ移す、またはページタイトルを通知 |
| 要素を削除 | 次の要素か親へ移す（消えた要素に残さない） |
| エラー表示 | エラー要約か最初のエラー項目へ移す |

```tsx
// フォーカスの見た目は消さない（:focus-visible で必要なときだけ表示）
button:focus-visible { outline: 2px solid var(--color-focus); }
```

---

## 5. Headless UI を使うという判断

APG に沿った部品を自作するのは大変です。そこで **振る舞い（a11y・キーボード操作）だけを提供し、見た目は自由** な Headless ライブラリが選択肢になります。

| 方式 | 例 | 向く場面 | 向かない場面 |
|---|---|---|---|
| Headless ライブラリ | Radix UI, React Aria, Headless UI | 独自デザイン + 高い a11y 品質 | ライブラリの制約が合わない特殊な部品 |
| 既製の UI ライブラリ | MUI など | 見た目もまとめて任せたい | ブランドに合わせて大きく変えたい |
| 完全自作 | — | 既存にない部品 | APG を読み込む時間がない |

```tsx
// Radix UI の Dialog — フォーカス管理・Esc・aria 属性は自動で付く
<Dialog.Root>
  <Dialog.Trigger asChild><button>設定</button></Dialog.Trigger>
  <Dialog.Content>
    <Dialog.Title>設定</Dialog.Title>
    …
  </Dialog.Content>
</Dialog.Root>
```

Headless の考え方自体は [[03_コンポーネントパターンの比較]] を参照してください。

## 6. 仕組みで守る

| 手段 | 見つけられるもの | 限界 |
|---|---|---|
| eslint-plugin-jsx-a11y | alt 抜け・不正な role | 実行時の振る舞いは分からない |
| axe-core（テスト・CI） | コントラスト・ラベル抜けなど | 自動で分かるのは一部だけ |
| Testing Library の `getByRole` | 役割と名前で要素を取れるか | — |
| 手動（キーボードのみ・スクリーンリーダー） | 操作の流れ・読み上げ順 | 時間がかかる |

`getByRole("button", { name: "保存" })` でテストを書くと、**テストを書くこと自体が a11y の確認** になります（[[01_テストしやすいコンポーネントと構成]]）。

---

## まとめ

- a11y は共通部品で作り込むと、全画面にまとめて効く
- まずネイティブ要素、ない部品は APG のパターンに従う
- フォーカスの移動（開く・閉じる・遷移・削除）を設計に含める
- 独自デザインと a11y の両立には Headless ライブラリが有効。自動チェックと手動確認を組み合わせる
