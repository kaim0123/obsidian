# 付録A　フロントエンド設計用語集

## 使い方

47_フロントエンド設計 の本文に出てくる用語を、五十音順・英字順に並べた早見表です。各語の末尾のリンク先で詳しく扱っています。

---

## あ行

- **アイランドアーキテクチャ（Islands Architecture）** — 静的 HTML の中で、対話が必要な部分（島）だけを JavaScript で動かす構成。→ [[00_解説_フロントエンド構成]]
- **アクセシビリティ（a11y）** — 障害の有無や利用環境に関係なく、誰もが UI を操作・理解できること。→ [[02_アクセシビリティを部品設計に組み込む]]
- **依存ルール** — 「どの層・どのフォルダがどこを import してよいか」の決まり。Lint で自動検査する。→ [[04_依存ルールの自動検査]]
- **イミュータブル（不変）** — 状態を直接書き換えず、新しい値を作って置き換えること。変更検知と予測可能性の土台。→ [[02_UIは状態の関数と単方向データフロー]]
- **エラー境界（Error Boundary）** — 子コンポーネントの描画エラーを捕まえ、代わりのフォールバック UI を表示する仕組み。→ [[04_エラー境界とフォールバックUI]]

## か行

- **型共有** — OpenAPI・tRPC・Zod などで、サーバーとフロントが同じ型定義を使うこと。→ [[02_APIレイヤと型の共有]]
- **楽観的更新（Optimistic Update）** — サーバーの応答を待たずに UI を先に更新し、失敗したら戻す手法。→ [[01_フロントとサーバーの責務分担]]
- **Container-Presentational** — データ取得・状態を持つ部品と、見た目だけの部品に分けるパターン。→ [[03_コンポーネントパターンの比較]]
- **Compound Components** — `<Tabs>` と `<Tabs.Tab>` のように、複数の部品が暗黙の状態を共有して 1 つの UI を作るパターン。→ [[03_コンポーネントパターンの比較]]
- **コロケーション（Colocation）** — 一緒に変更されるコード（部品・スタイル・テスト・型）を近くに置く原則。→ [[01_ディレクトリ構成の方式比較]]
- **コンポーネント** — UI を構成する再利用可能な部品。入力（Props）から出力（UI）を返す。→ [[01_コンポーネントの分割粒度と境界]]

## さ行

- **サーバー状態** — サーバーが真の持ち主で、フロントはキャッシュを持っているだけの状態。TanStack Query などで扱う。→ [[01_状態の分類と置き場所]] / [[MOC_状態管理体系]]
- **スライス（slice）** — FSD で、層の中をビジネス領域ごとに分けた単位（例: `features/auth`）。→ [[02_Feature-Sliced_Design]]
- **セグメント（segment）** — FSD で、スライスの中を技術的な役割で分けた単位（`ui` / `model` / `api` / `lib` / `config`）。→ [[02_Feature-Sliced_Design]]
- **Single Source of Truth（SSOT）** — 同じデータの「正」を 1 か所だけに置く原則。→ [[02_Single_Source_of_Truthと派生状態]]

## た行

- **単方向データフロー（Unidirectional Data Flow）** — データは親から子へ、変更要求はイベントとして子から親へ、の一方向に流す設計。→ [[02_UIは状態の関数と単方向データフロー]]
- **デザイントークン** — 色・余白・フォントなどの設計上の決定を名前付きの値にしたもの。→ [[01_デザインシステムの構成要素]]
- **デザインシステム** — トークン・コンポーネント・ガイドライン・ドキュメントをまとめた、UI の一貫性の仕組み。→ [[01_デザインシステムの構成要素]]

## な行

- **ナビゲーション状態 / URL 状態** — 検索条件・ページ番号・選択タブなど、URL に持たせるべき状態。→ [[01_状態の分類と置き場所]]

## は行

- **バレルファイル（barrel file）** — `index.ts` で公開するものだけを re-export し、フォルダの公開 API を定める手法。→ [[03_bulletproof-reactの構成]]
- **派生状態（Derived State）** — 他の状態から計算できる値。state として持たず、描画時に計算する。→ [[02_Single_Source_of_Truthと派生状態]]
- **ハイドレーション（Hydration）** — サーバーで生成した HTML に、クライアント側でイベント処理と状態をつなぐ処理。→ [[00_解説_フロントエンド構成]]
- **Headless コンポーネント** — 見た目を持たず、振る舞い・状態・アクセシビリティだけを提供する部品（Radix UI・React Aria など）。→ [[03_コンポーネントパターンの比較]]
- **Props** — 親から子へ渡す入力。コンポーネントの公開 API にあたる。→ [[02_Propsはコンポーネントの公開API]]
- **フォールバック UI** — 読み込み中・エラー時に代わりに表示する UI。→ [[04_エラー境界とフォールバックUI]]
- **BFF（Backend for Frontend）** — 特定のフロントエンド専用に、API を束ね・整形するサーバー層。→ [[01_フロントとサーバーの責務分担]] / [[00_解説_フロントエンド構成]]

## ま行

- **マイクロフロントエンド（Micro-Frontends）** — フロントエンドを、独立してデプロイできる小さなアプリの集まりとして作る構成。→ [[02_マイクロフロントエンドの判断]]
- **モノレポ（Monorepo）** — 複数のアプリ・パッケージを 1 つのリポジトリで管理する方式。→ [[01_モノレポとパッケージ分割]]

## ら行

- **レイヤー型（技術別）構成** — `components/` `hooks/` `api/` のように技術的な種類でフォルダを分ける方式。→ [[01_ディレクトリ構成の方式比較]]
- **ローカル状態（UI 状態）** — 開閉・入力中の値など、1 つの部品の中だけで使う状態。→ [[01_状態の分類と置き場所]]
- **RADIO** — 要件（Requirements）→ 全体構成（Architecture）→ データモデル（Data model）→ インターフェース（Interface）→ 最適化（Optimizations）の順で UI を設計する枠組み（GreatFrontEnd）。→ [[01_RADIOテンプレート]]

## 英字

- **ADR（Architecture Decision Record）** — 設計判断とその理由・却下した案を短く記録する文書。→ [[03_フロントエンドの規約とADR]]
- **Atomic Design** — UI を Atoms → Molecules → Organisms → Templates → Pages の 5 段階で組み立てる方法論（Brad Frost）。→ [[04_Atomic_Design]]
- **bulletproof-react** — 機能別フォルダ（`features/`）と一方向の依存ルールを示す React の構成例。→ [[03_bulletproof-reactの構成]]
- **Code Splitting** — バンドルを分割し、必要になったときに読み込む手法。→ [[03_パフォーマンスを設計で作り込む]]
- **Core Web Vitals** — LCP（読み込み）・INP（応答性）・CLS（視覚的安定性）の 3 指標。→ [[03_パフォーマンスを設計で作り込む]]
- **CSR / SSR / SSG / ISR** — レンダリング方式（クライアント／サーバー／ビルド時／増分再生成）。→ [[00_解説_フロントエンド構成]]
- **CSS Modules / CSS-in-JS / Utility-first** — スタイリング方式の代表 3 系統。→ [[02_スタイリング方式の比較]]
- **dependency-cruiser / eslint-plugin-boundaries** — import の依存ルールを検査するツール。→ [[04_依存ルールの自動検査]]
- **FSD（Feature-Sliced Design）** — `app / pages / widgets / features / entities / shared` の層で依存方向を固定するフロントエンド構成の方法論。→ [[02_Feature-Sliced_Design]]
- **OpenAPI** — HTTP API の仕様を機械可読に書く形式。型やクライアントの自動生成に使う。→ [[02_APIレイヤと型の共有]] / [[MOC_API設計体系]]
- **RSC（React Server Components）** — サーバーだけで実行され、クライアントに JS を送らないコンポーネント。→ [[00_解説_フロントエンド構成]]
- **Storybook** — コンポーネントを単体で表示・カタログ化するツール。デザインシステムのドキュメントとしても使う。→ [[01_デザインシステムの構成要素]]
- **Testing Library** — 利用者の操作に近い形（ロール・ラベル）で UI をテストするライブラリ群。→ [[01_テストしやすいコンポーネントと構成]]
- **tRPC** — TypeScript の型をサーバーからクライアントへそのまま共有する RPC ライブラリ。→ [[02_APIレイヤと型の共有]]
- **UI = f(state)** — UI は状態を入力とする関数、という宣言的 UI の基本の考え方。→ [[02_UIは状態の関数と単方向データフロー]]
- **WAI-ARIA** — 支援技術に役割・状態を伝える属性の仕様。→ [[02_アクセシビリティを部品設計に組み込む]]
- **Zod** — 実行時にデータを検証し、同時に TypeScript の型も得られるスキーマライブラリ。→ [[02_APIレイヤと型の共有]]
