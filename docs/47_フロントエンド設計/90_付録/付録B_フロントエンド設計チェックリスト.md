# 付録B　フロントエンド設計チェックリスト（総合版）

## 使い方

- **新しい画面・機能を作る前**、**設計レビュー**、**リファクタリングの着手前** に上から確認します
- すべてを満たす必要はありません。チェックが付かない項目は「なぜ満たさないのか」を説明できれば十分です
- 判断に迷った項目は、各章のリンク先で理由と例を確認してください

---

## 1. 基礎 — 何を設計するのか

→ [[01_フロントエンド設計とは]] / [[02_UIは状態の関数と単方向データフロー]]

- [ ] この画面・機能の **状態** と **表示** の関係を説明できる（UI = f(state)）
- [ ] データは親 → 子、変更要求はイベントで子 → 親、の **一方向** に流れている
- [ ] DOM を直接書き換えて状態を表していない
- [ ] 設計判断（何を選び、なぜか）と、フレームワーク固有の実装を分けて考えている

## 2. コンポーネント設計

→ [[01_コンポーネントの分割粒度と境界]] / [[02_Propsはコンポーネントの公開API]] / [[03_コンポーネントパターンの比較]] / [[04_Atomic_Design]]

- [ ] 各コンポーネントの責務を 1 文で説明できる
- [ ] 分割の理由が「再利用」「変更理由の分離」「読みやすさ」のどれかで説明できる（行数だけで分けていない）
- [ ] Props の数が多すぎない（目安 5〜7 個。超えるなら分割か `children` を検討）
- [ ] boolean の Props を組み合わせて見た目を切り替えていない（`variant` などの列挙に寄せる）
- [ ] 見た目の部品がデータ取得・グローバル状態に直接依存していない
- [ ] 同じ状態を共有する部品群は Compound や Headless を検討した
- [ ] Atomic Design の階層分けに迷って時間を使っていない（迷うなら機能別の配置を優先）

## 3. 状態とデータフロー

→ [[01_状態の分類と置き場所]] / [[02_Single_Source_of_Truthと派生状態]] / [[MOC_状態管理体系]]

- [ ] 各状態を **ローカル / 共有 / サーバー / URL / フォーム** のどれかに分類した
- [ ] 状態は、それを使う部品の **最も近い共通の親** に置いている（必要以上にグローバルにしていない）
- [ ] サーバーのデータをグローバルストアにコピーしていない（サーバー状態のキャッシュとして扱う）
- [ ] 他の状態から計算できる値を state として持っていない（派生状態は描画時に計算）
- [ ] 検索条件・ページ番号・タブなど、共有・再読み込みで残すべき状態は URL にある
- [ ] 同じデータの「正」が 1 か所だけ（SSOT）

## 4. ディレクトリ・モジュール構成

→ [[01_ディレクトリ構成の方式比較]] / [[02_Feature-Sliced_Design]] / [[03_bulletproof-reactの構成]] / [[04_依存ルールの自動検査]] / [[10-6-ディレクトリ設計]]

- [ ] 採用した構成方式（レイヤー型 / 機能別 / FSD）と、その理由がチームで共有されている
- [ ] 1 つの機能を消すとき、ほぼ 1 フォルダを消せば済む
- [ ] 機能どうしが互いを直接 import していない（共通化するなら下の層へ移す）
- [ ] 各フォルダの公開 API（`index.ts` など）が決まっていて、内部ファイルを直接 import していない
- [ ] 依存ルールが Lint / CI で自動検査されている
- [ ] `utils/` `common/` が何でも入る場所になっていない

## 5. デザインシステム・スタイリング

→ [[01_デザインシステムの構成要素]] / [[02_スタイリング方式の比較]] / [[CSS設計（BEM-OOCSS）]]

- [ ] 色・余白・フォントサイズを直接値で書かず、デザイントークンを使っている
- [ ] スタイリング方式が 1 つに決まっている（混在しているなら移行方針がある）
- [ ] 共通部品はカタログ（Storybook など）で一覧・確認できる
- [ ] 部品の使い方・使ってはいけない場面がドキュメントにある
- [ ] デザイナーと同じ名前で部品・トークンを呼んでいる

## 6. サーバーとの境界

→ [[01_フロントとサーバーの責務分担]] / [[02_APIレイヤと型の共有]] / [[MOC_HTTPクライアント体系]] / [[MOC_API設計体系]]

- [ ] API 呼び出しがコンポーネントに直書きされず、API レイヤにまとまっている
- [ ] レスポンスの型がサーバーと共有・生成されている（OpenAPI・tRPC・Zod など）
- [ ] 外部から来たデータを境界で検証している
- [ ] ビジネスルールの最終判断がサーバー側にある（フロントの検証は UX のため）
- [ ] 読み込み中・空・エラーの 3 状態を画面ごとに設計している
- [ ] レンダリング方式（CSR / SSR / SSG / RSC）を画面の性質で選んでいる → [[00_解説_フロントエンド構成]]

## 7. 品質

→ [[01_テストしやすいコンポーネントと構成]] / [[02_アクセシビリティを部品設計に組み込む]] / [[03_パフォーマンスを設計で作り込む]] / [[04_エラー境界とフォールバックUI]]

- [ ] ロジックが純粋関数・カスタムフックに切り出され、UI なしでテストできる
- [ ] テストは実装の詳細ではなく、ロール・ラベルなど利用者に見えるものを使っている
- [ ] ボタン・リンク・フォーム要素に正しい HTML 要素を使っている（`div` + `onClick` にしていない）
- [ ] キーボードだけで操作でき、フォーカスの移動が自然
- [ ] 画像・アイコンボタンに代替テキスト・ラベルがある
- [ ] 重い画面・ライブラリを Code Splitting で遅延読み込みしている
- [ ] Core Web Vitals（LCP・INP・CLS）の目標値と計測方法がある → [[01_Core_Web_Vitals]]
- [ ] 画面の一部が壊れても全体が真っ白にならない（エラー境界がある）
- [ ] エラーが監視ツールに送られている

## 8. スケールと組織

→ [[01_モノレポとパッケージ分割]] / [[02_マイクロフロントエンドの判断]] / [[03_フロントエンドの規約とADR]]

- [ ] 複数アプリで共有するコードは、パッケージとして境界と所有者が決まっている
- [ ] マイクロフロントエンドは「チームの独立デプロイが本当に必要か」を確認してから採用した
- [ ] 命名・フォルダ・状態の置き場所などの規約が文書化されている
- [ ] 重要な設計判断が ADR に残っている（採用しなかった案と理由も）
- [ ] 規約の多くが Lint・フォーマッタ・テンプレートで自動化されている
