# bulletproof-react の構成

## この章の目的

GitHub で公開されている React アプリの設計ガイド **bulletproof-react**（alan2207/bulletproof-react）のプロジェクト構成を読み、**Feature型の構成を実務でどう運用するか** を学ぶ章です。

React 固有の書き方は 32_React が本拠地です。ここでは **構成の考え方** を取り出します。

---

## 1. bulletproof-react とは

bulletproof-react は、中〜大規模の React アプリを **崩れにくく作るための構成・規約のサンプル** です。コードだけでなく、`docs/` 以下にプロジェクト構成・状態管理・API 層・テスト・エラー処理などの方針が文章で書かれています。

特定のライブラリを強制するものではなく、「**こういう判断をした**」という参考例として読むのが適切です。

---

## 2. トップレベルの構成

```text
src/
├── app/          # アプリ層: ルート（routes/）、プロバイダ、ルーター
├── assets/       # 静的ファイル
├── components/   # アプリ全体で共有するコンポーネント
├── config/       # グローバル設定・環境変数
├── features/     # 機能ごとのモジュール ← 中心
├── hooks/        # 共有フック
├── lib/          # ライブラリを設定済みで再公開したもの
├── stores/       # グローバルな状態ストア
├── testing/      # テスト用ユーティリティ・モック
├── types/        # 共有の型
└── utils/        # 共有ユーティリティ
```

**機能に属さないもの** だけがトップレベルに残り、機能固有のコードは `features/` に入ります。

---

## 3. feature フォルダの中身

```text
src/features/discussions/
├── api/          # API リクエストの宣言と、それを使うフック
├── assets/
├── components/   # この機能専用のコンポーネント
├── hooks/
├── stores/
├── types/
└── utils/
```

- 必要なフォルダだけを作る（全部そろえる必要はない）
- **API 呼び出しを機能ごとに置く** のが特徴。「どの機能がどのエンドポイントを使うか」がフォルダで分かる

API 層の考え方は [[03_APIレイヤーのフォルダ構成]]（37）と対応しています。

---

## 4. 依存の向きのルール

bulletproof-react の中心となるルールは 2 つです。

**(1) 機能どうしを import しない**

```ts
// NG: features/comments から features/discussions を import
import { DiscussionView } from '@/features/discussions/components/discussion-view';
```

機能を組み合わせたいときは、**上位のアプリ層（app/routes）で組み立て** ます。

**(2) 共有 → 機能 → アプリ の一方向**

```text
  shared（components, hooks, lib, types, utils）
        ↓ 使われる
  features
        ↓ 使われる
  app
```

共有コードは機能を知らず、機能はアプリ層を知りません。このルールは ESLint の `import/no-restricted-paths` で検査する方法が紹介されています（[[04_依存ルールの自動検査]]）。

---

## 5. barrel ファイルの扱い

以前のバージョンでは各 feature に `index.ts` を置き、そこから export する（barrel ファイル）方針でした。現在のドキュメントでは、**Vite 環境で tree shaking やパフォーマンスに悪影響が出ることがある** ため、**ファイルを直接 import する** 方針に変わっています。

| 方針 | 利点 | 欠点 |
|---|---|---|
| barrel ファイルあり | 公開 API が明確（FSD はこちら） | ビルド・開発サーバーが重くなることがある、循環参照の温床 |
| 直接 import | ツールに優しい | 内部ファイルへの依存が生まれやすい（ルールで補う） |

どちらを選ぶ場合も、**「外から使ってよいのはどれか」を決めて守る** という目的は同じです。

---

## 6. FSD との比較

| 観点 | bulletproof-react | FSD |
|---|---|---|
| 分け方 | 共有 / features / app の 3 段 | 6 層 × スライス × セグメント |
| 機能の粒度 | 業務機能（discussions, users） | entity（もの）と feature（操作）を区別 |
| ルールの数 | 少ない | 多い（その分明確） |
| 学習コスト | 低い | 高い |
| 向く場面 | 中規模、React 中心のチーム | 大規模、長期運用、構成の標準化を重視 |

bulletproof-react は **Feature型に最小限のルールを足したもの**、FSD は **それをさらに層で細かく規格化したもの** と捉えると整理しやすいです。

---

## 7. 取り入れるときの判断

- **そのまま真似る必要はない**。features と「機能どうし import しない」ルールだけでも効果が大きい
- `lib/`（設定済みライブラリの再公開）は、ライブラリ差し替え時の影響を 1 か所に閉じる良い習慣
- `testing/` を最初から置くと、モック・テストデータの置き場所で迷わない

---

## まとめ

- bulletproof-react は **Feature型構成の実践例**。ドキュメントで方針まで読める
- 機能固有のコードは `features/<機能>/` に、API もその中に置く
- **機能どうしは import しない**、依存は **共有 → 機能 → アプリ** の一方向
- barrel ファイルは現在は非推奨寄り（ツールの都合）。目的は公開範囲を守ること
- FSD より軽量で、中規模の React アプリに取り入れやすい
