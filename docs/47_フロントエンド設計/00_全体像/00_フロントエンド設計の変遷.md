# フロントエンド設計 — 西暦順でたどる

## このノートの目的

**フロントエンド設計** とは、ブラウザ上の UI を **再利用可能な部品** に分け、**状態と表示の関係**・**データの流れ**・**フォルダ構成** を決め、長期間メンテナンスできる形に整えることです。

[[010Programming/42_ソフトウェア設計/10_設計の基礎/02_設計の階層と全体像|設計]] の比喩で言えば、API 設計が「窓口の決め方」なら、フロントエンド設計は **「画面の部屋割りと、情報の配管」** に相当します。

このノートでは、フロントエンドでよく語られる **7つの設計思想** を **登場が早い順（おおよその西暦）** に並べ、次の流れで整理します。

1. **その前に、どんな課題があったか**
2. **何を提案したか**
3. **どう解決したか**
4. **向いている場面・限界**

前提として [[010Programming/42_ソフトウェア設計/10_設計の基礎/02_設計の階層と全体像|設計]] の「ソフトウェア設計」層に位置づけられます。サーバーとの境界は [[MOC_API設計体系|API設計]] も参照してください。

---

## 全体の流れ（年表）

| 順番 | 考え方 | 登場時期 | 一言で言うと | 主に解決した課題 |
|------|--------|----------|-------------|-----------------|
| 1 | **コンポーネント指向** | 1990年代〜（Web 本格化: 2010年代） | UI を独立した部品に分ける | HTML/JS のコピペ地獄 |
| 2 | **State Driven UI** | 2013年〜 | 状態が変われば UI が変わる | 命令型 DOM 操作の複雑化 |
| 3 | **Atomic Design** | 2013年〜 | デザインを原子→分子→生物と階層化 | UI のバラつき・デザインシステム不在 |
| 4 | **Unidirectional Data Flow** | 2014年〜 | データは一方向にだけ流す | 双方向バインディングの予測不能さ |
| 5 | **Single Source of Truth** | 2014〜2015年〜 | 真実のデータは1か所だけ | 同じデータの多重コピーと不整合 |
| 6 | **Feature First / FSD** | 2018〜2020年〜 | 機能（ドメイン）単位でフォルダを切る | 技術レイヤー分割のスケール限界 |
| 7 | **Server State 管理** | 2019年〜 | サーバー由来の状態を専用に扱う | Redux に API データを詰め込む過剰設計 |

> **補足:** 年は「Web フロントエンドで名前が広まった時期」の目安です。  
> コンポーネント指向はデスクトップ UI（Visual Basic、Swing など）から以前に存在します。ここでは **ブラウザアプリ** を主な文脈とします。

## 0. その前：サーバー生成 HTML + jQuery 時代（〜2010年代初頭）

React や Vue が主流になる前、多くの Web アプリは **サーバーが HTML を生成** し、ブラウザ側は **jQuery で DOM を直接触る** 構成が一般的でした。

### よく起きていた課題

- 同じヘッダー・フォーム・モーダルを **ページごとにコピペ** し、修正漏れが頻発
- `$('#submit').click(...)` のような **命令型 DOM 操作** がファイル全体に散らばる
- 「今このボタンが有効か？」の判断が **DOM の属性** と **JS の変数** に二重に存在し、ズレる
- 画面が複雑になるほど **どこを触ると何が変わるか** が追えない（スパゲッティ化）
- デザインの **統一ルール** がなく、開発者ごとに見た目がバラバラ

### 次の時代への問い

> **「UI を部品として再利用し、状態と表示の関係を整理するには？」**

---

## 1. コンポーネント指向（1990年代〜 / Web: 2010年代〜）

**背景:** デスクトップ UI フレームワーク（Swing、Qt など）→ Web Components 構想（2011）→ React（2013）、Vue（2014）  
**一言:** 画面を **独立した UI 部品（コンポーネント）** の組み合わせとして設計する

### その前の課題 — モノリシック HTML とコピペ

- ナビゲーション、カード、フォームが **各ページの HTML に直書き** され、1 箇所の変更が全ページに波及
- 「ボタンコンポーネント」を作りたくても、**HTML 断片 + CSS + JS** がバラバラに存在
- グローバルな CSS セレクタ（`.btn`）が **意図せず他の画面に効く**
- テストしにくい — DOM 全体を読み込まないと部品単体を検証できない

### 何を提案したか

UI を **カプセル化された部品** に分割する。各部品は **自分の見た目・振る舞い・（場合により）状態** を持ち、親から **props（入力）** を受け取って描画する。

```jsx
// ボタンを部品として切り出す
function PrimaryButton({ label, onClick, disabled }) {
  return (
    <button className="btn-primary" onClick={onClick} disabled={disabled}>
      {label}
    </button>
  );
}
```

| 概念 | 役割 |
|------|------|
| **コンポーネント** | 再利用可能な UI の最小単位（またはその組み合わせ単位） |
| **props** | 親から子へ渡す設定・データ |
| **カプセル化** | 内部実装を隠し、外部にはインタフェースだけ公開 |

### どう解決したか

- **再利用:** 同じ `<UserCard />` を一覧・詳細・ダッシュボードで使い回せる
- **変更の局所化:** カードのデザイン変更は **1 コンポーネント** だけ直せばよい
- **分割統治:** 大きな画面を **小さな部品のツリー** に分解し、チームで分担しやすくなる
- **テスト:** 部品単位で「この props ならこの HTML になる」を検証できる

### 向いている場面・限界

| 向く | 向かない |
|------|----------|
| 同じ UI が複数画面に現れる | 1 回きりの静的ランディングページ |
| 中〜大規模 SPA | 部品分割しすぎて props が深く渡り続ける（prop drilling） |

**限界:** コンポーネント分割だけでは **状態の置き場所** や **データの流れ** は決まらない → 次の思想へ。

## 2. State Driven UI（2013年〜）

**背景:** React（2013）、Elm（2012）など関数型 UI の潮流  
**一言:** **UI = f(state)** — 状態が決まれば表示が決まる。DOM を直接いじらない

### その前の課題 — DOM が「真実」になっていた

- 「チェック済みか？」を `input.checked` で見る一方、JS 側にも `isChecked` 変数があり **二重管理**
- データ更新のたびに `document.getElementById(...).innerHTML = ...` を **手動で書く**
- 更新漏れ・順序バグ（A を更新したが B を忘れた）が起きやすい
- 「今の画面の状態」を **DOM ツリーを辿って** 復元する必要がある

### 何を提案したか

**状態（state）を唯一の入力** とし、UI はその **純粋な関数（または宣言）** として記述する。フレームワークが **差分検知**（Virtual DOM など）で DOM 更新を代行する。

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  // UI は state から決まる — DOM を直接触らない
  return (
    <div>
      <p>カウント: {count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </div>
  );
}
```

### どう解決したか

- **宣言的:** 「こう見せたい」を書けば、**どう DOM を更新するか** はフレームワーク任せ
- **再現性:** 同じ state なら **必ず同じ UI** — デバッグで state を見ればよい
- **更新漏れの削減:** state を更新すれば、関連 UI が **一括で** 再描画される
- **テスト:** DOM 操作ではなく **state → 出力** を検証できる

### 向いている場面・限界

| 向く | 向かない |
|------|----------|
| 動的に変化する SPA | 完全に静的な HTML ページ |
| フォーム・一覧・ダッシュボード | アニメーション DOM を細かく直接制御したい場面（例外はある） |

**限界:** state が **コンポーネントごとにバラバラ** だと、兄弟・親子間の共有が複雑になる → データフローの整理へ。

## 3. Atomic Design（2013年〜）

**背景:** Brad Frost による方法論（2013 年記事、2016 年書籍）  
**一言:** UI を **原子 → 分子 → 生物 → テンプレート → ページ** の階層で設計する

### その前の課題 — デザインと実装の断絶

- 「ボタン」「入力欄」が **開発者ごとに微妙に違う** 色・余白・フォント
- デザイナーの Figma と実装の React コンポーネントの **対応関係が曖昧**
- `components/` フォルダに **粒度のバラバラな部品** が混在（アイコンとページ全体が同列）
- デザイン変更時に **どこまで直せばよいか** の範囲が読めない

### 何を提案したか

UI を **5 段階の階層** で整理する。

| 階層 | 例 | 役割 |
|------|-----|------|
| **Atoms（原子）** | ボタン、ラベル、入力欄 | これ以上分割しない最小 UI |
| **Molecules（分子）** | ラベル + 入力 + エラー文 | 原子の組み合わせ |
| **Organisms（生物）** | ヘッダー、商品カード | 独立した UI ブロック |
| **Templates（テンプレート）** | 一覧ページの骨組み | レイアウト・配置 |
| **Pages（ページ）** | 実データを当てはめた完成形 | 最終的な画面 |

### どう解決したか

- **共通言語:** デザイナーとエンジニアが **同じ粒度** で会話できる
- **デザインシステムの土台:** Atoms / Molecules が **Storybook** などのカタログ化と相性がよい
- **変更の波及範囲:** ボタン色の変更は **Atom 1 つ** で全アプリに効かせられる
- **一貫性:** 「この画面だけ特別なボタン」を **意図的に作らない限り** 防げる

### 向いている場面・限界

| 向く | 向かない |
|------|----------|
| デザインシステム・複数画面で UI を統一 | プロトタイプ段階で細部まで階層化する必要がない |
| 中〜大規模プロダクト | 階層の厳密な分類に **時間を取りすぎる** |

**限界:** Atomic Design は **見た目・部品の粒度** の話であり、**アプリの状態管理やフォルダ構成** は別問題 → データフロー・機能分割へ。

## 4. Unidirectional Data Flow（2014年〜）

**背景:** Facebook Flux（2014）、Redux（2015）、Vue の一方向フロー  
**一言:** データは **Action → State → View** の一方向にだけ流し、逆流させない

### その前の課題 — 双方向バインディングのスケール限界

- AngularJS（1.x）の **two-way binding** は小規模では便利だが、大規模になると **誰が誰を更新したか** が追えない
- 子コンポーネントが **親の state を直接書き換える** と、変更経路が増えてデバッグ困難
- 「この値が変わったのは、入力？ API？ 親？」が **調査に時間がかかる**
- イベントと state 更新が **循環** し、無限ループや予期しない再描画が起きる

### 何を提案したか

データの流れを **一方向** に固定する。

```text
User Action
    ↓
  Action（「何が起きたか」の記述）
    ↓
  State 更新（ reducer / store ）
    ↓
  View 再描画（ state から UI を計算）
    ↓
  （View から State へ直接書き込まない）
```

```javascript
// Redux 風のイメージ
dispatch({ type: 'TODO_ADD', payload: { text: '買い物' } });
// → reducer が state を更新 → コンポーネントが再描画
```

### どう解決したか

- **変更経路の単純化:** state が変わる入口は **Action だけ** — ログを見れば原因が分かる
- **予測可能性:** 同じ Action 列なら **同じ state** になる（再現しやすい）
- **デバッグ:** Redux DevTools のように **Action 履歴を巻き戻し** できる
- **大規模チーム:** 「state を触っていい場所」が **ルールとして明確**

### 向いている場面・限界

| 向く | 向かない |
|------|----------|
| 複数画面で共有するクライアント state | 単純なフォーム 1 画面だけの小アプリ |
| 変更履歴・Undo が欲しい UI | ボイラープレートを嫌う小規模プロジェクト |

**限界:** 一方向にすると **記述量が増える** ことがある。あわせて「state の置き場所」を決める SSOT とセットで語られる。

## 5. Single Source of Truth（2014〜2015年〜）

**背景:** Flux / Redux の中核原則。React 公式ドキュメントでも「Single Source of Truth」として説明  
**一言:** 同じデータについて **正本は1か所だけ**。他はすべてそこから **導出（derive）** する

### その前の課題 — 同じデータの多重コピー

- ユーザー名が **Profile コンポーネント**・**Header**・**Redux store**・**localStorage** にそれぞれ存在
- API 取得後に **3 箇所を手動で同期** し、1 箇所だけ古い値が残る
- 「一覧の件数」と「詳細の件数」が **別 state** で管理され、不整合
- キャッシュと表示用データが **別々に更新** され、UI がちらつく

### 何を提案したか

アプリケーション state を **1 つのツリー（store）** に集約し、各画面は **必要な部分を select（購読）** する。派生値（フィルタ済み一覧、合計金額）は **毎回計算** するか **メモ化** するが、**別の正本にはしない。

```javascript
// 正本は store.user.name だけ
const state = {
  user: { id: '1', name: '田中' },
  todos: [/* ... */],
};

// Header も Profile も同じ store を参照 — コピーを持たない
const name = state.user.name;
```

| 原則 | 意味 |
|------|------|
| **1 データ 1 正本** | 同じ意味の値を複数 state に持たない |
| **派生は計算** | `filteredTodos = todos.filter(...)` は正本ではなく導出 |
| **同期ではなく参照** | 更新は正本だけ。他は再描画で追従 |

### どう解決したか

- **不整合の削減:** 更新箇所が **1 か所** なので「古い値が残る」バグが減る
- **デバッグ:** アプリ全体の state を **1 スナップショット** で見られる
- **テスト:** 初期 state + Action → 期待 state を **純粋関数** で検証できる
- **Time-travel:** 正本が 1 つなら履歴管理がしやすい

### 向いている場面・限界

| 向く | 向かない |
|------|----------|
| 複数画面で同じデータを参照 | すべてを global store に入れ **過剰に中央集権化** |
| 複雑なクライアント state（ウィザード、エディタ） | サーバー由来データまで全部 Redux に入れる（→ Server State 管理へ） |

**限界:** 「正本を1つ」は **クライアント側 UI state** には有効だが、**API から取ってくるデータ** は性質が異なる — キャッシュ・再取得・鮮度の問題。

## 6. Feature First / FSD（2018〜2020年〜）

**背景:** Feature-Sliced Design（FSD、Roman Remont ら、2018 年頃〜2020 年に方法論として整理）  
**一言:** フォルダを **技術（components / hooks / utils）** ではなく **機能（feature）** 単位で切る

### その前の課題 — 技術レイヤー型フォルダの限界

```text
src/
  components/   ← 全機能の UI が混在
  hooks/
  utils/
  services/
```

- 「注文キャンセル」機能を直すのに **5 フォルダ** を横断する
- 使われなくなったコードの **削除範囲** が分からない（どこからどこまでが1機能？）
- 共通 `components/` が **巨大なゴミ箱** になる
- 新メンバーが **画面とファイルの対応** を把握しにくい
- **モジュール間の依存** がルールなく増え、循環 import が発生

### 何を提案したか

**機能（スライス）** を主軸に、各機能の中に UI・ロジック・API をまとめる。FSD では **レイヤー × スライス** のルールで依存方向を制限する。

```text
src/
  app/           # ルーティング・プロバイダ
  pages/         # ルート単位の画面
  widgets/       # 独立した UI ブロック
  features/      # ユーザー操作・ビジネス機能（例: add-to-cart）
  entities/      # ドメインの核（例: user, product）
  shared/        # 汎用 UI・lib
```

| 考え方 | 意味 |
|--------|------|
| **Feature First** | 「この機能に必要なもの」を **1 か所に集約** |
| **FSD のスライス** | `features/cart/add-item/` のように **垂直分割** |
| **依存ルール** | 下位レイヤー（shared）に上位（features）が依存しない |

### どう解決したか

- **変更の局所化:** 機能追加・削除が **フォルダ単位** で完結しやすい
- **オンボーディング:** 「注文機能 = このディレクトリ」と **地図が作れる**
- **スケール:** チームを **機能ごとに分担** しやすい
- **デッドコード削減:** 機能フォルダごと削除できる

### 向いている場面・限界

| 向く | 向かない |
|------|----------|
| 中〜大規模 SPA・複数機能 | 画面 1〜2 枚の小アプリ |
| 長期メンテ・複数人開発 | ルール学習コストを払えない短期プロジェクト |

**限界:** フォルダ構成は **コードの置き場** の話。API データの **キャッシュ・再取得** は Server State 管理の領域。

## 7. Server State 管理（2019年〜）

**背景:** TanStack Query（React Query, 2019）、SWR（2019）、Apollo Client（GraphQL, 2015〜）など  
**一言:** **サーバーが正本のデータ** は、クライアント global state とは **別枠** で取得・キャッシュ・同期する

### その前の課題 — Redux に全部入れる時代

- 一覧 API の結果を **Redux に `FETCH_SUCCESS` で保存** — loading / error / cache の定番コードが毎回必要
- 画面を離れて戻ったとき **再取得するか**、**キャッシュを使うか** がプロジェクトごとにバラバラ
- **同じ API を複数コンポーネント** が呼び、重複リクエスト
- **楽観的更新** や **バックグラウンド再検証** を自前実装し、バグが出やすい
- 「UI state（モーダル開閉）」と「サーバー data（ユーザー一覧）」が **同じ store** に混在し、責務が曖昧

### 何を提案したか

**Client State**（UI の一時的な状態）と **Server State**（API が正本のリモートデータ）を **分離** する。Server State は専用ライブラリが **キャッシュ・再取得・無効化** を担当する。

```javascript
// TanStack Query のイメージ
function UserList() {
  const { data, isLoading, error } = useQuery({
    queryKey: ['users'],
    queryFn: fetchUsers,
    staleTime: 60_000, // 1分は fresh とみなす
  });

  if (isLoading) return <Spinner />;
  if (error) return <Error message={error.message} />;
  return data.map(user => <UserRow key={user.id} user={user} />);
}
```

| 概念 | 役割 |
|------|------|
| **queryKey** | キャッシュの識別子（同じ key は同じデータを共有） |
| **stale / fresh** | データの「古さ」と再取得タイミング |
| **invalidation** |  mutation 後に関連 query を再取得 |
| **Client State** | モーダル、タブ、フォーム入力中 — useState / Zustand など |

### どう解決したか

- **ボイラープレート削減:** loading / error / retry / dedupe を **ライブラリが標準提供**
- **キャッシュ共有:** 同じ `queryKey` なら **1 回の取得で複数コンポーネント** が使える
- **鮮度管理:** `staleTime`・ウィンドウフォーカス時の再取得など **ポリシーを宣言的** に
- **責務分離:** Redux は **UI state だけ**、API データは Query — **SSOT の正本はサーバー** と割り切れる

### 向いている場面・限界

| 向く | 向かない |
|------|----------|
| REST / GraphQL でデータ取得が中心の SPA | オフライン専用・サーバー通信ほぼなし |
| 一覧・詳細・ダッシュボードで同じ API を共有 | 極端にシンプルな CRUD 1 画面 |

**限界:** オフライン優先・複雑なローカル DB 同期には **別のアプローチ**（IndexedDB、CRDT など）が必要な場合がある。

---

## 7つの思想の関係（まとめ）

```text
[ コンポーネント指向 ]     UI を部品化
        ↓
[ State Driven UI ]       表示 = f(state)
        ↓
[ Atomic Design ]         部品の見た目・粒度を体系化（並行して適用も可）
        ↓
[ Unidirectional Flow ]   変更の向きを一方向に
        ↓
[ Single Source of Truth ] クライアント正本を1つに
        ↓
[ Feature First / FSD ]   コードの置き場を機能単位に
        ↓
[ Server State 管理 ]     サーバー正本を専用レイヤーで
```

| 思想 | 主に解決するレイヤー |
|------|---------------------|
| コンポーネント指向 | UI の **構造・再利用** |
| State Driven UI | **表示と状態** の関係 |
| Atomic Design | **デザイン一貫性** |
| Unidirectional Data Flow | **変更の追跡可能性** |
| Single Source of Truth | **クライアント data の不整合** |
| Feature First / FSD | **コードベースのスケール** |
| Server State 管理 | **API データのキャッシュ・同期** |

---

## 学習・適用の順番（参考）

歴史順と **学びやすい順** は一致しません。実務では次の順が理解しやすいことが多いです。

1. **コンポーネント指向** + **State Driven UI**（React / Vue の基本）
2. **Server State 管理**（小〜中規模アプリで早めに導入してもよい）
3. **Unidirectional Flow** + **SSOT**（共有 state が複雑になってから）
4. **Atomic Design**（デザインシステムを作る段階）
5. **Feature First / FSD**（フォルダが散らかってきたタイミング）
