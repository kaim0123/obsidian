# 状態の分類と置き場所

## この章の目的

フロントエンドの状態（state）を **種類ごとに分類** し、それぞれを **どこに置くべきか** を判断できるようになる章です。

「とりあえずグローバルストアに入れる」をやめ、状態の性質から置き場所を決めます。ライブラリの使い方や実装は [[MOC_状態管理体系]]（36_状態管理）が本拠地で、47 では **判断の基準** だけを扱います。

---

## 1. なぜ分類が必要か

状態管理が破綻する典型は、**性質の違う状態を 1 か所に混ぜる** ことです。

| 混ぜたときの症状 | 原因 |
|---|---|
| API のデータが古いまま表示される | サーバーのデータを「自分の状態」としてコピーした |
| リロードすると絞り込み条件が消える | URL に置くべき状態をメモリに置いた |
| 入力 1 文字ごとに画面全体が再描画される | フォームの状態をグローバルに置いた |
| 合計金額と明細がずれる | 計算で出せる値を別の状態として保存した |

置き場所を間違えると、**同期のためのコード** が増え続けます。分類はそれを防ぐための道具です。

---

## 2. 6 種類の状態

| 種類 | 例 | 真の持ち主 | 寿命 |
|---|---|---|---|
| **ローカル（UI）状態** | モーダルの開閉、タブの選択、ホバー | そのコンポーネント | 画面にある間 |
| **共有（クライアント）状態** | ログイン中のユーザー表示設定、テーマ、カート（未送信） | アプリ全体・複数画面 | セッション中 |
| **派生状態** | 合計金額、絞り込み後の一覧、入力が有効か | 他の状態（計算で出る） | 元の状態と同じ |
| **サーバー状態** | 商品一覧、注文履歴、プロフィール | **サーバー**（フロントはキャッシュ） | サーバー側で変わりうる |
| **URL 状態** | 検索語、ページ番号、並び順、選択中の ID | URL（共有・ブックマーク可能） | URL が残る限り |
| **フォーム状態** | 入力中の値、エラー、送信中フラグ | そのフォーム | 送信・破棄まで |

ポイントは **「真の持ち主は誰か」** です。サーバー状態の持ち主はサーバーであり、フロントが持っているのは **コピー（キャッシュ）** にすぎません。この区別は [[8-4-サーバー状態vsクライアント状態]] でも扱っています。

---

## 3. 置き場所の判断フロー

```text
その値は…
 ├─ 他の状態から計算で出せる？ ─────────── Yes → 状態にしない（派生：描画時に計算）
 ├─ サーバーが持ち主？ ─────────────────── Yes → サーバー状態ライブラリのキャッシュ
 ├─ リロード・共有・戻るボタンで残したい？ ─ Yes → URL（検索パラメータ・パス）
 ├─ 入力中のフォームの値？ ─────────────── Yes → フォームの状態（フォームライブラリ or ローカル）
 ├─ 1 つのコンポーネントだけが使う？ ────── Yes → ローカル状態
 ├─ 近い親子だけが使う？ ─────────────────── Yes → 共通の親に持ち上げる（lifting state up）
 └─ 離れた多数の画面が使う？ ─────────────── Yes → 共有状態（Context / ストア）
```

上から順に判定するのがコツです。**グローバルストアは最後の選択肢** で、多くの値はそこまで到達しません。

---

## 4. 「近くに置く」原則（colocation）

状態は **使う場所のできるだけ近く** に置きます。

```tsx
// 悪い例: モーダルの開閉をグローバルストアに置く
const isOpen = useAppStore((s) => s.isEditModalOpen);

// 良い例: 使うコンポーネントの中に置く
function EditButton() {
  const [isOpen, setIsOpen] = useState(false);
  return (
    <>
      <button onClick={() => setIsOpen(true)}>編集</button>
      {isOpen && <EditModal onClose={() => setIsOpen(false)} />}
    </>
  );
}
```

近くに置くと、

- 影響範囲が狭く、**どこで変わるか** がすぐ分かる
- コンポーネントを消すと状態も一緒に消える（削除しやすい）
- 再描画の範囲が小さくなる

という利点があります。必要になってから **上に持ち上げる** のが順序です（逆に、最初から上に置いたものを下げるのは難しい）。

---

## 5. 種類ごとの置き場所と向き不向き

| 種類 | 向く置き場所 | 向かない置き場所 | 実装の本拠地 |
|---|---|---|---|
| ローカル | コンポーネント内の state | グローバルストア | 36 の 20_ローカル・UI状態 |
| 共有 | Context / 軽量ストア | props のバケツリレー（深い場合） | 36 の 30_グローバル状態 |
| 派生 | 描画時の計算・メモ化 | 別の state として保存 | [[02_Single_Source_of_Truthと派生状態]] |
| サーバー | サーバー状態ライブラリ（キャッシュ） | 自前のグローバルストアにコピー | 36 の 40_サーバー状態 |
| URL | 検索パラメータ・ルートパラメータ | メモリ上の state | 36 の 50_URL状態 |
| フォーム | フォームライブラリ・フォーム内の state | グローバルストア | 36 の 60_フォーム状態 |

---

## 6. よくある判断ミス

- **API レスポンスをストアにコピーする** — 再取得・無効化・ローディング管理を自前で書くことになる。サーバー状態として扱う
- **絞り込み条件をメモリに置く** — 共有 URL で同じ画面を再現できない。URL に置く
- **「あとで使うかも」でグローバルに置く** — YAGNI。使う場所に置き、必要になったら持ち上げる
- **フォームの途中入力をストアに流す** — 入力のたびに広範囲が再描画される

---

## まとめ

- 状態は **ローカル / 共有 / 派生 / サーバー / URL / フォーム** の 6 種類に分けて考える
- 判断の軸は **「真の持ち主は誰か」** と **「どこまでの範囲が使うか」**
- 計算で出せる値は状態にしない。サーバーのデータはキャッシュとして扱う
- 状態は使う場所の近くに置き、必要になってから持ち上げる
- 実装（ライブラリの使い方）は 36_状態管理 で扱う
