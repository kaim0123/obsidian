# デザインシステムの構成要素

## この章の目的

**デザインシステム** を「UI 部品集」ではなく、**トークン・コンポーネント・ドキュメント・運用ルール** からなる仕組みとして捉え、どこまで作るかを判断できるようになる章です。

CSS の書き方そのものは 22_CSS（[[CSS設計（BEM-OOCSS）]]）、React でのコンポーネント実装は 32_React（[[10-4-Props設計]]）が本拠地です。ここでは **何を共通化し、誰がどう守るか** を扱います。

---

## 1. デザインシステムとは何か

デザインシステムは、**見た目と振る舞いの一貫性を、個人の注意力ではなく仕組みで保つ** ためのものです。

```text
  ┌──────────────────────────────────────────┐
  │ 4. ガバナンス（誰が変更し、どう広めるか）   │
  ├──────────────────────────────────────────┤
  │ 3. ドキュメント（使い方・原則・Do/Don't）   │
  ├──────────────────────────────────────────┤
  │ 2. コンポーネント（Button, Dialog, Table…） │
  ├──────────────────────────────────────────┤
  │ 1. デザイントークン（色・余白・文字・影…）   │
  └──────────────────────────────────────────┘
        下の層ほど変更の影響範囲が大きい
```

| よくある誤解 | 実際 |
|---|---|
| UI キット（Figma ファイル）を作れば完成 | 実装・ドキュメント・運用が揃って初めて機能する |
| コンポーネントライブラリ = デザインシステム | ライブラリは 4 層のうち 1 層にすぎない |
| 一度作れば終わり | プロダクトと一緒に **進化し続ける製品** |

---

## 2. デザイントークン — 値に名前を付ける

**デザイントークン** は、色や余白などの **デザイン上の決定を名前付きの値** にしたものです。W3C の Design Tokens Community Group が共通フォーマット（JSON）の仕様化を進めています。

トークンは 2〜3 階層に分けるのが定番です。

| 階層 | 例 | 役割 |
|---|---|---|
| プリミティブ（基本値） | `blue-600: #2563eb` | 使える値のパレット |
| セマンティック（意味） | `color-action-primary: {blue-600}` | **用途** に名前を付ける |
| コンポーネント | `button-primary-bg: {color-action-primary}` | 部品単位の上書き点（必要な場合のみ） |

```css
/* セマンティックトークンを CSS 変数として公開する */
:root {
  --color-action-primary: #2563eb;
  --color-text-default: #111827;
  --space-2: 8px;
}
[data-theme="dark"] {
  --color-action-primary: #60a5fa;
  --color-text-default: #f9fafb;
}
```

**判断のポイント**: コンポーネントは **セマンティックトークンだけ** を参照させます。プリミティブを直接使うと、ダークモードやブランド変更のときに全箇所を書き換えることになります。

---

## 3. コンポーネントライブラリ — 何を共通部品にするか

すべてを共通化すると、使われない汎用部品が増えます。**3 回使われたら共通化** くらいの感覚で、次の順に揃えるのが現実的です。

| 優先度 | 対象 | 理由 |
|---|---|---|
| 高 | Button, Input, Select, Checkbox, Dialog | 使用頻度が高く、a11y の作り込みが難しい |
| 中 | Table, Tabs, Toast, Tooltip | 振る舞いの一貫性が UX に効く |
| 低 | 画面固有のカード・レイアウト | 変更理由がプロダクト側にある |

実装の選択肢は大きく 3 つです。

| 方式 | 例 | 向く場面 | 向かない場面 |
|---|---|---|---|
| 既製ライブラリをそのまま使う | MUI, Chakra UI | 早く作りたい・独自ブランド性が低い | 見た目を大きく変えたい |
| Headless + 自前スタイル | Radix UI, React Aria | 独自デザイン + a11y を確保したい | スタイリングの工数を割けない |
| コードを取り込んで所有 | shadcn/ui | 部品を自分たちで改変し続けたい | 更新の追従を自動化したい |

振る舞い（キーボード操作・フォーカス管理）は Headless に任せ、見た目はトークンで統一する構成が、独自デザインと a11y を両立しやすい組み合わせです（[[02_アクセシビリティを部品設計に組み込む]]）。

## 4. ドキュメント — Storybook と使い分けの指針

部品があっても **いつ使うか** が伝わらなければ、似た部品が再発明されます。

- **Storybook**: 部品ごとの状態（通常・hover・disabled・エラー）をカタログ化。ビジュアルリグレッションや a11y チェックのアドオンとも連携できる
- **使い分けの指針**: 「Dialog と Drawer のどちらを使うか」「Primary ボタンは 1 画面 1 つ」など **判断ルール** を書く
- **Do / Don't**: 良い例と悪い例を並べる

```tsx
// Button.stories.tsx — 状態ごとに 1 ストーリー
export const Primary = { args: { variant: "primary", children: "保存" } };
export const Disabled = { args: { variant: "primary", disabled: true, children: "保存" } };
```

## 5. ガバナンス — 誰が変更し、どう広めるか

| モデル | 内容 | 向く規模 |
|---|---|---|
| 中央集権型 | 専任チームが全部品を管理 | 大規模・複数プロダクト |
| 連邦型 | 各チームの代表が共同で管理 | 中規模・複数チーム |
| 兼任型 | プロダクトチームが片手間で管理 | 小規模・1 プロダクト |

最低限決めておくことは次の 3 つです。

1. **バージョニング**: 共通パッケージなら SemVer と変更履歴（[[01_モノレポとパッケージ分割]]）
2. **追加の基準**: 新しい部品をライブラリに入れる条件
3. **逸脱の扱い**: 画面側で上書きしてよい範囲（例: 余白は可、色は不可）

---

## まとめ

- デザインシステムは **トークン・コンポーネント・ドキュメント・ガバナンス** の 4 層
- トークンは **プリミティブ → セマンティック** の階層にし、部品はセマンティックだけ参照する
- 共通部品は使用頻度と a11y の難しさで優先度を決め、画面固有の部品は無理に共通化しない
- 「いつ使うか」のドキュメントと、変更のルールがないと形骸化する
