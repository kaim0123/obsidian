# フロントとサーバーの責務分担

## この章の目的

バリデーション・権限・データ整形などを **フロントとサーバーのどちらに置くか** を判断できるようになる章です。BFF や React Server Components（RSC）・Server Actions の登場で **境界の位置そのものが動く** ことも扱います。

HTTP クライアントの実装は 37（[[MOC_HTTPクライアント体系]]）、レンダリング方式と BFF の構成は 41（[[00_解説_フロントエンド構成]]）、API の設計は 45（[[MOC_API設計体系]]）が本拠地です。

---

## 1. 大原則 — クライアントは信用しない

ブラウザで動くコードは **ユーザーが自由に書き換えられます**。そのため、次の原則が出発点になります。

| 種類 | どこで保証するか | フロントの役割 |
|---|---|---|
| セキュリティ（認証・認可） | **サーバーのみ** | 見せ方の調整（ボタンを隠すなど） |
| データの整合性（業務ルール） | **サーバーのみ** | 早めのフィードバック |
| ユーザー体験（即時の反応） | フロント | 主担当 |

```text
  ブラウザ                              サーバー
  ┌─────────────────┐                ┌─────────────────┐
  │ 入力チェック      │ ── request ──▶ │ 入力チェック（本番）│
  │ （UX のため）     │                │ 認可・業務ルール    │
  │ ボタンの出し分け   │ ◀── response ─ │ エラーを構造化して返す│
  └─────────────────┘                └─────────────────┘
```

---

## 2. バリデーションの二重化

入力チェックは **両方に置く** のが基本です。役割が違うからです。

| | フロント | サーバー |
|---|---|---|
| 目的 | すぐに気づかせる（UX） | 不正なデータを入れない（正しさ） |
| 省略したら | 使いにくいだけ | **データが壊れる** |
| 例 | 必須・形式・文字数 | 上記 + 重複チェック・在庫・権限 |

二重化の手間は、**スキーマを共有** して減らします（[[02_APIレイヤと型の共有]]）。

```ts
// shared/schema/user.ts — フロントとサーバーで同じ定義を使う
import { z } from "zod";
export const UserInput = z.object({
  name: z.string().min(1).max(50),
  email: z.string().email(),
});
```

ただし **サーバーでしか判定できないルール**（メールアドレスの重複など）は共有できません。サーバーからのエラーをフォームに表示する経路を必ず用意します。

---

## 3. 権限 — 隠すのはフロント、守るのはサーバー

```tsx
// フロント: 権限がなければボタンを出さない（UX）
{can(user, "order:delete") && <DeleteButton />}
```

- ボタンを隠しても、API を直接呼べば実行できてしまう
- **サーバー側の認可チェックが本体**、フロントの出し分けは補助
- 権限の判定ロジックを両方で持つなら、権限一覧（ロール → 操作）をサーバーから受け取り、フロントは表示に使うだけにする

---

## 4. データ整形はどこでやるか

「API のレスポンスを画面の形に変える処理」をどこに置くかは、選択肢が複数あります。

| 置き場所 | 向く場面 | 向かない場面 |
|---|---|---|
| フロント（API レイヤで変換） | API が 1 つ・画面も少ない | 複数 API を画面ごとに組み合わせる |
| **BFF**（画面専用のサーバー層） | 複数のバックエンドを束ねる / Web とモバイルで必要な形が違う | 小規模で BFF の運用コストが見合わない |
| バックエンド API を画面に合わせる | 1 つのフロント専用の API | 複数のクライアントが同じ API を使う |

BFF は「**フロントエンドチームが持つサーバー**」です。フロントの都合（集約・整形・キャッシュ）をバックエンドに押し付けずに済みます。

---

## 5. RSC / Server Actions で境界が動く

React Server Components と Server Actions（Next.js App Router など）では、**同じコンポーネントツリーの中にサーバー側のコードが入ります**。

```tsx
// Server Component — サーバーで実行され、DB に直接アクセスできる
export default async function OrdersPage() {
  const orders = await db.order.findMany(); // API を経由しない
  return <OrderList orders={orders} />;
}

// Server Action — フォームから直接サーバー関数を呼ぶ
async function cancelOrder(formData: FormData) {
  "use server";
  const id = String(formData.get("id"));
  await assertCanCancel(id); // ← 認可はここで必ず行う
  await db.order.update({ where: { id }, data: { status: "canceled" } });
}
```

| 変わること | 注意点 |
|---|---|
| フロントのコードが DB に触れる | **Server Action は公開エンドポイントと同じ**。認可・入力検証を省略しない |
| API レイヤが不要になる場面がある | 他のクライアント（モバイル等）が同じ処理を使うなら API は別途必要 |
| データ取得がコンポーネントに近づく | サーバー専用コードがクライアントに混ざらないよう `server-only` などで境界を明示する |

**判断の軸は変わりません**: 境界の位置が動いても、「信用できない入力は、信用できる場所で検証する」が原則です。

---

## まとめ

- 認証・認可・業務ルールの **保証はサーバー**、フロントは UX のための補助
- バリデーションは二重化し、スキーマ共有で手間を減らす。サーバー専用ルールのエラー経路も用意する
- 画面向けの整形は、規模と API の利用者の数で「フロント / BFF / API 側」を選ぶ
- RSC・Server Actions では境界がコンポーネント内に入るが、Server Action は公開エンドポイントとして扱う
