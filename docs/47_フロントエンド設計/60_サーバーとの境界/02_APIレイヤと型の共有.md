# APIレイヤと型の共有

## この章の目的

フロントとサーバーの間で **型やスキーマをどう共有するか** — OpenAPI からのコード生成、tRPC、Zod スキーマの共有、GraphQL Code Generator — を比べ、構成に合った方式を選べるようになる章です。

API レイヤのフォルダ構成とクライアント実装は 37（[[03_APIレイヤーのフォルダ構成]]、[[MOC_HTTPクライアント体系]]）が本拠地です。

---

## 1. なぜ型の共有が必要か

フロントが API の形を **手で書き写す** と、次のことが起きます。

```ts
// 手書きの型 — サーバーが total を totalPrice に変えても気づけない
type Order = { id: string; total: number };
```

| 問題 | 結果 |
|---|---|
| 型のずれ | 実行時に `undefined` が出るまで気づかない |
| 二重管理 | 同じ定義をサーバーとフロントで保守する |
| 型を信じすぎる | 型があっても実行時のデータは保証されない |

解決策は **「唯一の定義（契約）」を決めて、そこから両側を導く** ことです。どこを唯一の定義にするかで方式が分かれます。

```text
  契約の置き場所          方式
  ─────────────          ──────────────────────
  API 仕様書（YAML）   →  OpenAPI + コード生成
  サーバーの TS コード  →  tRPC
  共有スキーマ         →  Zod などのスキーマ共有
  GraphQL スキーマ     →  GraphQL Code Generator
```

---

## 2. 各方式

### OpenAPI + コード生成（スキーマファースト）

OpenAPI の仕様書から、型や API クライアントを **生成** します（openapi-typescript、Orval など）。

```ts
import type { paths } from "./generated/schema";
type Order = paths["/orders/{id}"]["get"]["responses"]["200"]["content"]["application/json"];
```

- サーバーの言語を問わない。仕様書がそのままドキュメントになる
- 仕様書と実装がずれないよう、**サーバー側からの生成** または **契約テスト** が必要

### tRPC（TypeScript のエンドツーエンド型）

サーバーの関数定義の型を、**コード生成なしで** フロントが直接参照します。

```ts
// server
export const appRouter = router({
  orderById: publicProcedure.input(z.string()).query(({ input }) => getOrder(input)),
});
// client — 引数も戻り値も型推論される
const order = trpc.orderById.useQuery("o_1");
```

- 開発体験が非常に良い。変更すると即座に型エラーになる
- **サーバーもクライアントも TypeScript で、同じリポジトリ（モノレポ）** にあることが前提。公開 API には向かない

### Zod などのスキーマ共有

スキーマを共有パッケージに置き、**型の生成と実行時検証を同じ定義から** 行います。

```ts
export const Order = z.object({ id: z.string(), total: z.number() });
export type Order = z.infer<typeof Order>;

// フロントの API レイヤで、受け取ったデータを検証する
const order = Order.parse(await res.json());
```

- **実行時の検証** ができるのが最大の利点（型だけでは外部データを保証できない）
- 既存の REST API に後付けしやすい

### GraphQL Code Generator

GraphQL スキーマとクエリから型を生成します。

- 画面が **必要なフィールドだけ** を取得でき、その型が得られる
- GraphQL サーバーの導入・運用が前提

---

## 3. 比較 — 向く場面 / 向かない場面

| 方式 | 向く場面 | 向かない場面 |
|---|---|---|
| OpenAPI + 生成 | サーバーが別言語 / 公開 API / 複数クライアント | 仕様書を保守する体制がない |
| tRPC | フルスタック TS・モノレポ・社内向け | 外部公開 API / サーバーが別言語 |
| Zod スキーマ共有 | 既存 REST に型と検証を足したい / フォームと共有したい | スキーマが巨大で手書きがつらい |
| GraphQL Codegen | 画面ごとに取得項目が大きく違う | 単純な CRUD / GraphQL 未導入 |

組み合わせも一般的です。例: **OpenAPI から Zod スキーマを生成** し、型と実行時検証を両方得る。

---

## 4. API レイヤの責務 — 型の境界をどこに置くか

どの方式でも、**API のデータ形式を画面に直接流さない** 層を 1 つ挟むと変更に強くなります。

```text
  サーバーの形（DTO）  ──▶  API レイヤ  ──▶  画面の形（ドメイン型）
  { total_price: 1200 }     検証 + 変換      { total: 1200 }
```

| API レイヤでやること | やらないこと |
|---|---|
| 実行時検証（parse） | 画面の状態管理 |
| DTO → 画面用の型への変換 | 画面固有の表示整形（通貨記号など） |
| エラーの型付け（業務エラー / 通信エラー） | UI の表示 |

変換層を省略してもよいのは、**サーバーとフロントを同じチームが持ち、API がそのフロント専用** の場合です（tRPC 構成など）。

---

## まとめ

- 型の共有は「唯一の契約をどこに置くか」で方式が決まる
- 公開・多言語なら OpenAPI、フルスタック TS なら tRPC、既存 REST の後付けなら Zod
- 型は実行時のデータを保証しない。外部から来るデータは検証する
- API レイヤで検証と変換を行い、サーバーの形を画面に直接流さない
