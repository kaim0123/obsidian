# フロントエンド設計とは — 責務と、何を決めるのか

## この章の目的

**フロントエンド設計** が何を扱い、何を決める仕事なのかを整理する章です。React や Vue の書き方ではなく、**どのフレームワークでも必要になる設計判断** の全体像をつかみます。

フレームワーク固有の実装は [[10-1-UIコンポーネントとロジックの分離]] など 32_React が本拠地です。47 では「どれを選ぶか・なぜか」を扱います。

---

## 1. フロントエンドの責務

フロントエンドは「画面を描く」だけの層ではありません。ブラウザ上で動くアプリとして、次の責務を持ちます。

| 責務 | 内容 | 例 |
|------|------|-----|
| **表示** | 状態を画面に描く | 一覧・詳細・フォーム |
| **入力の受け付け** | ユーザー操作をイベントとして扱う | クリック・入力・ドラッグ |
| **状態の保持** | 画面に必要なデータを持つ | 選択中のタブ、入力途中の値 |
| **サーバーとの通信** | データを取得・送信する | API 呼び出し、キャッシュ |
| **画面遷移** | URL と画面を対応させる | ルーティング |
| **品質** | 誰でも速く・壊れず使える | a11y、パフォーマンス、エラー表示 |

サーバーサイドと比べて特徴的なのは、**状態が長時間ブラウザに残り、ユーザー操作で絶えず変わる** ことです。フロントエンド設計の難しさの多くはここから来ます。

---

## 2. フロントエンド設計で決めること

2025 年前後のフロントエンド設計の議論は、おおむね次の 4 本柱に集約されます。

```text
            ┌───────────────────────────┐
            │     フロントエンド設計       │
            └───────────────────────────┘
   ┌──────────┬──────────┬──────────┬──────────┐
   │コンポーネント│  状態と    │ディレクトリ│デザイン    │
   │  の境界    │データフロー│・モジュール│システム    │
   │ (20)      │ (30)      │ (40)      │ (50)      │
   └──────────┴──────────┴──────────┴──────────┘
        ＋ サーバーとの境界(60) ＋ 品質(70) ＋ スケール(80)
```

| 問い | 決めること | フォルダ |
|------|-----------|---------|
| 画面をどう部品に分けるか | 粒度・境界・Props | 20_コンポーネント設計 |
| 状態をどこに持つか | 状態の種類と置き場所 | 30_状態とデータフロー |
| コードをどこに置くか | フォルダ構成・依存ルール | 40_ディレクトリ・モジュール構成 |
| 見た目をどう揃えるか | トークン・CSS 方式 | 50_デザインシステム・スタイリング |
| サーバーとどうつなぐか | API レイヤ・型共有 | 60_サーバーとの境界 |

---

## 3. 「設計」と「実装」の線引き

同じテーマでも、設計判断と実装は分けて考えると整理しやすくなります。

| テーマ | 設計判断（47） | 実装（本拠地） |
|--------|---------------|---------------|
| 状態管理 | どの状態をグローバルにするか | Zustand / TanStack Query の書き方（36） |
| コンポーネント | どこで部品を切るか | Hooks・Props の型（32_React） |
| レンダリング | 構成への影響 | CSR/SSR の仕組み（[[00_解説_フロントエンド構成]]） |
| API 通信 | フロントとサーバーの責務分担 | fetch/axios ラッパー（[[MOC_HTTPクライアント体系]]） |

設計判断は **フレームワークが変わっても残る知識** です。React から別のライブラリへ移っても、「状態の置き場所を決める」問いそのものは変わりません。

---

## 4. なぜ設計が必要になるのか

小さな画面なら設計なしでも動きます。問題は **規模と時間** が増えたときです。

```text
  小規模                           中〜大規模
  ──────                           ──────────
  1 画面・1 人                      数十画面・複数チーム
  状態は useState だけで足りる       同じデータが複数画面に登場
  フォルダ構成は気にならない          「どこに書くか」で毎回迷う
  見た目は手作業で揃う               ボタンが 5 種類に増殖
```

よくある症状と、効く設計テーマの対応です。

| 症状 | 効くテーマ |
|------|-----------|
| 1 ファイル 1000 行のページコンポーネント | コンポーネントの分割（20） |
| 同じデータがずれて表示される | Single Source of Truth（30） |
| 機能を消すとあちこち壊れる | Feature 単位の構成・依存ルール（40） |
| 画面ごとに色や余白が違う | デザインシステム（50） |

---

## 5. 設計の進め方 — 小さく始めて育てる

フロントエンド設計は **最初から完成形を目指さない** のが基本です。

1. まずは素直に書く（ページ単位・useState 中心）
2. 痛みが出た箇所だけ構造を入れる（部品の切り出し、状態の持ち上げ）
3. チームや画面が増えたらルールにする（ディレクトリ規約、デザイントークン）
4. さらに大きくなったら組織構造に合わせる（モノレポ、マイクロフロントエンド）

歴史的にも、各設計思想は「前の時代の痛み」から生まれています（[[00_フロントエンド設計の変遷]]）。

---

## まとめ

- フロントエンドは表示・入力・状態・通信・遷移・品質を担う
- 設計の中心はコンポーネントの境界 / 状態の置き場所 / コードの置き場所 / 見た目の一貫性
- 47 は「判断」、フレームワーク固有の書き方は 32_React・36・37 が本拠地
- 規模と時間が増えたときの痛みに合わせて、段階的に構造を入れる
