# UI = f(state) と単方向データフロー

## この章の目的

現代のフロントエンド設計の土台になっている 2 つの考え方 — **UI は状態の関数（UI = f(state)）** と **単方向データフロー** — を理解する章です。コンポーネント設計（20）も状態設計（30）も、この 2 つを前提に組み立てられています。

---

## 1. 命令的 UI と宣言的 UI

jQuery 時代の UI は、**「何が起きたら DOM をどう書き換えるか」** を命令的に書いていました。

```javascript
// 命令的: 変化のたびに DOM を直接操作
$('#add').on('click', () => {
  count++;
  $('#count').text(count);
  if (count > 10) $('#warning').show();
});
```

状態が増えると「どの操作がどの DOM を変えたか」を追えなくなり、**DOM そのものが真実** になってしまいます。

宣言的 UI では、**「この状態ならこう見える」** だけを書きます。

```tsx
// 宣言的: 状態から見た目を決める
function Counter({ count }: { count: number }) {
  return (
    <>
      <p>{count}</p>
      {count > 10 && <p role="alert">多すぎます</p>}
    </>
  );
}
```

---

## 2. UI = f(state)

宣言的 UI を一言で表すと **UI = f(state)** です。

```text
   state ──▶ [ f = コンポーネント ] ──▶ UI
```

| 性質 | 意味 | 設計上のうれしさ |
|------|------|-----------------|
| **同じ状態なら同じ見た目** | f は純粋関数に近い | 再現・テストがしやすい |
| **状態だけを変える** | DOM は触らない | 変更箇所が 1 か所に集まる |
| **見た目は結果** | 表示は状態から導かれる | 表示のズレが起きにくい |

設計の問いは「DOM をどう変えるか」から **「どんな状態を持つか」** に移ります。状態の設計が良ければ UI は自然に正しくなり、状態の設計が悪ければどれだけ UI を工夫してもバグが残ります。

---

## 3. 単方向データフロー

UI = f(state) を複数のコンポーネントに広げたときのルールが **単方向データフロー** です。2014 年に Facebook が Flux アーキテクチャとして発表し、Redux などに受け継がれました。

```text
        ┌─────────── state ───────────┐
        │                             ▲
        ▼ (props で下へ)               │ (イベントで上へ)
   ┌─────────┐                   ┌─────────┐
   │   View  │ ── ユーザー操作 ──▶ │  Action │
   └─────────┘                   └─────────┘
```

- **データは親から子へ props で流れる**
- **変更は子から親へイベント（コールバック）で伝える**
- 状態を書き換えるのは、その状態の **持ち主だけ**

```tsx
function Parent() {
  const [name, setName] = useState('');
  // 状態の持ち主は Parent。子は表示と「変えたい」の通知だけ
  return <NameInput value={name} onChange={setName} />;
}
```

## 4. 双方向バインディングとの比較

AngularJS（1.x）などの双方向バインディングは、View とモデルが互いに更新し合います。

| 観点 | 双方向バインディング | 単方向データフロー |
|------|---------------------|-------------------|
| 記述量 | 少ない（フォームが楽） | やや多い（onChange を書く） |
| 変更の追跡 | どこから変わったか追いにくい | 持ち主とイベントを見ればわかる |
| 規模が大きいとき | 連鎖更新でデバッグが難しい | 流れが一方向なので予測しやすい |
| 向く場面 | 小さなフォーム中心の画面 | 画面間でデータを共有するアプリ |

Vue の `v-model` のように、**書き方は双方向でも中身は単方向**（props + イベントの糖衣構文）という設計も一般的です。

## 5. 設計判断への効き方

この 2 つの考え方から、後の章で使う判断基準が導かれます。

| 原則 | 導かれる判断 | 詳しく |
|------|-------------|--------|
| UI は状態の結果 | 状態は最小限に、派生値は計算で出す | [[02_Single_Source_of_Truthと派生状態]] |
| 状態には持ち主がいる | 状態は使う部品の最も近い共通の親に置く | [[01_状態の分類と置き場所]] |
| データは上から下へ | 部品は props を受け取り、イベントを返す | [[02_Propsはコンポーネントの公開API]] |
| 表示と状態を分ける | 表示専用部品とロジックを分ける | [[03_コンポーネントパターンの比較]] |

---

## まとめ

- 命令的に DOM を操作する代わりに、状態から見た目を宣言する（UI = f(state)）
- 設計の中心は「どんな状態を持つか」に移る
- 単方向データフロー: データは props で下へ、変更はイベントで上へ
- 双方向バインディングは記述が楽だが、規模が大きいと変更の追跡が難しい
