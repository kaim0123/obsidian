# バレル（`index.ts`）と循環参照

> **バレル**（barrel）は「ディレクトリの公開APIを `index.ts` でまとめる」パターン。短い import が書け、内部実装を隠せる ── が、**循環参照とビルド速度低下**の温床にもなります。便利と危険のバランスを理解して、適切に使うのがプロのスタイルです。

## 1. バレル（barrel）とは

ディレクトリの**公開APIを `index.ts` で集約**するパターン。

### バレルなし

```
src/components/
  Button.tsx
  Card.tsx
  Modal.tsx
```

```typescript
import { Button } from "@/components/Button";
import { Card } from "@/components/Card";
import { Modal } from "@/components/Modal";
```

### バレルあり

```
src/components/
  Button.tsx
  Card.tsx
  Modal.tsx
  index.ts   ← バレル
```

```typescript
// components/index.ts
export { Button } from "./Button";
export { Card } from "./Card";
export { Modal } from "./Modal";
```

```typescript
import { Button, Card, Modal } from "@/components";
```

→ **1行に集約**できる。

---

## 2. バレルのメリット

### (1) import 文が短い

```typescript
// before
import { Button } from "@/components/Button";
import { Card } from "@/components/Card";

// after
import { Button, Card } from "@/components";
```

### (2) 内部構造を隠せる

```typescript
// 利用側は内部のファイル構造を知らなくてよい
import { Button } from "@/components";
```

→ あとで `Button.tsx` を `Button/index.tsx` にリファクタしても利用側に影響なし。

### (3) 公開APIを絞れる

```typescript
// components/index.ts
export { Button } from "./Button";
// Card は意図的に export しない → 内部利用のみ
```

→ 「**公開していい/しないを `index.ts` で制御**」できる。

### (4) ライブラリの「メインエントリ」表現

npm パッケージは慣例的に `index.ts` がエントリ。

---

## 3. バレルのデメリット

### (1) **循環参照の温床**

最大の問題。詳しくは後述。

### (2) **ビルド・型チェック速度の低下**

`import { x } from "@/components"` は、内部で**`components/index.ts` を全部読み込む**。

→ 1個しか使わなくても**全モジュールの型解析**が走る。大規模プロジェクトでは無視できない遅さ。

### (3) **Tree shaking が効きにくい**

未使用 export が**バンドルに残る**ことがある（バンドラ次第）。

```typescript
// components/index.ts
export { Button } from "./Button";
export { HugeUnusedComponent } from "./HugeUnusedComponent";
```

→ Vite/Webpack は基本対応するが、CJS 経由だと残ることも。

### (4) IDE のジャンプ（Go to Definition）が1段増える

```typescript
import { Button } from "@/components";
// Button の定義に飛ぶと、まず index.ts に行き、そこから Button.tsx へ
```

→ 慣れないと「??」となる。

---

## 4. 循環参照（circular dependency）

### 問題のあるパターン

```typescript
// a.ts
import { b } from "./b";
export const a = "A";
console.log("a uses", b);

// b.ts
import { a } from "./a";
export const b = "B";
console.log("b uses", a);
```

→ どちらが先に実行されるか不明。`undefined` が混入することがある。

### バレルで起きやすい

```typescript
// components/index.ts
export { Button } from "./Button";
export { Card } from "./Card";

// Button.tsx
import { Card } from "./"; // index.ts 経由
// → Card は同じバレル内にある → 循環！
```

直接 `import { Card } from "./Card"` なら問題ないが、バレル経由で**意図せず循環**することがある。

---

## 5. 循環参照の症状

### (1) 実行時の `undefined`

```typescript
// a.ts
import { b } from "./b";
export const a = `using ${b}`; // b が undefined のことがある
```

### (2) `Cannot access 'X' before initialization`

ESM のホイスティング絡みで起きる、TDZ (Temporal Dead Zone) エラー。

### (3) 「動くけど挙動が不安定」

最も厄介。**テストで偶然通って本番で死ぬ**こともある。

### (4) ビルドツールの警告

```
Warning: Circular dependency detected:
src/a.ts -> src/b.ts -> src/a.ts
```

→ 警告が出ても**動いてしまうので無視しがち** ── これが最悪のパターン。

---

## 6. 循環参照を防ぐ設計

### (1) **依存方向を一方向に**

```
common  ← features  ← pages
        ← lib
```

「下位（common）は上位（features）を知らない」。一方向の依存に。

### (2) **バレルを介さない直接 import**

同じディレクトリ内では**直接 import**:

```typescript
// components/Card.tsx
import { Button } from "./Button"; // ✅ 直接
// import { Button } from "./";    // ❌ バレル経由（循環の元）
```

### (3) **共通の型を別ファイルに切り出す**

`a.ts` と `b.ts` が互いの型を必要とするなら、型を `types.ts` に逃がす:

```typescript
// types.ts
export type Common = { ... };

// a.ts
import { Common } from "./types";

// b.ts
import { Common } from "./types";
```

### (4) **依存性逆転（DI）**

「片方が片方を直接 import」をやめ、**インターフェース**を介する:

```typescript
// service.ts
export interface Logger { log(s: string): void }
class Service {
  constructor(private logger: Logger) {}
}
```

### (5) ESLint の `import/no-cycle` ルール

```json
{
  "rules": {
    "import/no-cycle": "error"
  }
}
```

→ 循環参照を**コンパイル時に検出**できる。

## 7. バレルの使い分けガイド

### バレルを使うべき場所

#### (1) **公開APIの境界**

```
src/
  components/
    index.ts    // ✅ コンポーネント群の公開API
  features/
    user/
      index.ts  // ✅ ユーザー機能の公開API
```

→ 外から使うときの「玄関」。

#### (2) **ライブラリのエントリポイント**

```typescript
// my-lib/index.ts
export * from "./api";
export * from "./types";
```

#### (3) **小規模・関連性の強いユーティリティ**

```typescript
// utils/string/index.ts
export { capitalize } from "./capitalize";
export { camelize } from "./camelize";
```

### バレルを使わない方がよい場所

#### (1) **内部実装の集合**

```
features/user/
  internal/      // ❌ ここに index.ts は不要、外から使わない
```

#### (2) **大量のモジュール**

```typescript
// components/index.ts
export * from "./A"; // 100個以上...
export * from "./Z";
```

→ 全部読み込まれてビルドが遅い。**個別 import** か**サブディレクトリで分割**。

#### (3) **頻繁に変わる場所**

`index.ts` の更新コストが高い。

---

## 8. 「バレル使わない」最近の流派

### Next.js / Vite の最近の動向

「バレルは害」と判断するチームも増えている:

- ビルド遅い
- 循環参照リスク
- Tree shaking が完全でない場合がある

→ **直接 import を強制**するスタイル:

```typescript
// ✅
import { Button } from "@/components/Button";
import { Card } from "@/components/Card";
```

ESLint で `no-restricted-imports` で `@/components` を禁止することも。

### React コンポーネントの場合

「**1コンポーネント = 1ディレクトリ**」のとき、その中の `index.tsx` は許容:

```
components/
  Button/
    index.tsx     // バレルというより「メインファイル」
    Button.styles.ts
    Button.test.tsx
```

→ これは**バレルではなくエントリ**。問題なし。

## 9. バレルの書き方パターン

### (1) Re-export（最も一般的）

```typescript
// index.ts
export { Button } from "./Button";
export { Card } from "./Card";
```

### (2) Wildcard re-export

```typescript
export * from "./Button";
export * from "./Card";
```

→ **何が公開されているか分からなくなる**ため、`export {}` で個別指定が推奨。

### (3) Default の re-export

```typescript
export { default as Button } from "./Button";
```

### (4) 型のみ re-export

```typescript
export type { ButtonProps } from "./Button";
```

→ `isolatedModules: true` 環境では**必須**。

### (5) namespace としてまとめる

```typescript
import * as Buttons from "./buttons";

Buttons.Primary;
Buttons.Secondary;
```

## 10. 循環参照のデバッグ

### (1) ESLint で検出

`import/no-cycle` ルール有効化。

### (2) ツールで可視化

```bash
npx madge --circular --extensions ts,tsx src/
```

→ 循環を一覧。

### (3) ビルドツールの警告を見る

Vite/Webpack の build ログに `Circular dependency` 警告が出ることがある。

### (4) 段階的に解消

1. 循環の中の最も小さなノードを特定
2. 共通部分を別ファイルに切り出す
3. 依存方向を整理

## 11. 実例: バレル + 循環参照のバグ

### 悪い構造

```typescript
// utils/index.ts
export { foo } from "./foo";
export { bar } from "./bar";

// foo.ts
import { bar } from "./"; // ← 循環

// bar.ts
import { foo } from "./"; // ← 循環
```

### 修正

```typescript
// foo.ts
import { bar } from "./bar"; // ✅ 直接

// bar.ts
import { foo } from "./foo"; // ✅ 直接
```

または、共通ロジックを切り出す:

```typescript
// utils/core.ts
export function commonHelper() { ... }

// foo.ts
import { commonHelper } from "./core";

// bar.ts
import { commonHelper } from "./core";
```

## 12. ベストプラクティス

### (1) **バレルは「公開API境界」だけに置く**

機能・モジュールの**入口**だけ。内部の集約には作らない。

### (2) **同じディレクトリ内は直接 import**

```typescript
// 同じディレクトリから
import { helper } from "./helper"; // ✅ 直接

// バレル経由はしない
import { helper } from "./"; // ❌
```

### (3) **`export *` より `export { }`**

公開する内容を**明示**する。

### (4) **ESLint で循環参照を防ぐ**

`import/no-cycle` を `error` に。

### (5) **バレル経由の import は外部からだけ**

```typescript
// ✅ 外部から
import { Button } from "@/components";

// ❌ 内部から
// components/Card.tsx
import { Button } from "./"; 
```

### (6) **大規模なら個別 import を推奨**

ビルド速度を優先するなら、バレルを薄く保つ。

---

## 13. まとめ

- **バレル** = `index.ts` でディレクトリの公開APIを集約
- **メリット**: 短い import / 内部隠蔽 / 公開API制御
- **デメリット**: **循環参照** / ビルド遅い / Tree shaking 不完全
- 使うべき場所: **公開API境界、ライブラリエントリ、小規模ユーティリティ**
- 使わない場所: **内部実装集合、大量モジュール、頻繁に変わる場所**
- **同じディレクトリ内は直接 import**
- ESLint の **`import/no-cycle`** で循環参照を防ぐ
- 最近は「**バレル使わない**」流派も増加（ビルド速度優先）

> バレルは「**便利な道具だが、循環参照の罠を抱えている**」。公開境界だけ薄く使い、内部では直接 import ── このルールで、ビルド速度と保守性のバランスが取れます。
