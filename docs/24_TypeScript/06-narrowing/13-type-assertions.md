# 型アサーション（Type Assertion）

> **このノートについて**  
> TypeScript で「`as` を付けたら通った」経験がある方向けのメモです。**方針としては `as` による型アサーションを推奨せず、型定義や型の絞り込みで表現する**ことを前提に書いています。Zenn のスクラップに転載する場合は、末尾の Obsidian 用リンク（`[[...]]`）だけ削除または URL に差し替えてください。

## 1. ひとことで言うと

**型アサーション**（`value as SomeType` など）は、TypeScript に対して

> 「この値は、**こういう型として扱ってください**」

と**言い切る**書き方です。

ここで大事なのは次の2点です。

1. **JavaScript が実行されるときには何も変わらない**（値はそのまま）  
2. **本当にその型のデータかどうかは、チェックしてくれない**（コンパイラを黙らせるだけ）

なので、**間違った言い切りは実行時バグ**につながります。TypeScript を使う本来の目的は「型で意図を表し、矛盾をコンパイルで拾う」ことなので、**日常のコードでは `as` に頼らず、ちゃんとした型とコード（絞り込み・定義）で表現する**のが望ましいです。

---

## 2. たとえ話：名札を自分で付けるだけ

学校の入り口で、本来は教師が「あなたは一年生ですね」と確認してくれるとします。それが**型チェック（コンパイラ）**です。

型アサーションは、**自分で胸に「二年生です」と名札を付ける**ようなものです。  
名札を付ければ門番は通しますが、**本当に二年生かどうかは見ていません**。

だから学習・実装のスタンスとしては、

- **第一選択**：`interface` / `type` で形を定義し、**`if` や型ガードでコンパイラに理由を示す**  
- **`as` で型を言い換える**：型システムの外に出るので、**原則使わない・チームで禁止に近い扱い**にする  

という整理がおすすめです。例外はごく限られ、**書くなら理由とレビュー合意**があるべき、というニュアンスです。

---

## 3. `as` の構文（知識として。日常では使わない前提）

仕様上は次のように書けますが、**「こう書くのが正解」ではなく「他人のコードや古い記事で見かけるので意味だけ知っておく」**程度で十分です。

```typescript
// 型アサーションの例（※このノートでは推奨しない書き方）
const el = document.getElementById("root") as HTMLDivElement;
```

角括弧の書き方（`<Type>value`）も同じく**型の言い換え**であり、`.tsx` では JSX と衝突するのであまり使いません。**どちらも「ちゃんとした型表現」の代替にはなりません。**

### 代わりにどう書くか（例）

**null やタグの違いを型に反映したい**ときは、実行時に確認してから絞り込みます。

```typescript
const el = document.getElementById("root");
if (el === null) {
  throw new Error("#root が見つかりません");
}
if (!(el instanceof HTMLDivElement)) {
  throw new Error("#root は div である必要があります");
}
// ここでは el は HTMLDivElement として扱われる（as なし）
```

ポイントは、**コンパイラに「なぜその型か」をコードで見せる**ことです。

## 4. なぜ `as` より「ちゃんとした型」なのか

初心者で多いのが、**エラーを消すためにとりあえず `as` を付ける**ことです。一時的には楽ですが、型安全のメリットを自分で捨てています。

| やり方 | イメージ |
|--------|----------|
| **型を定義し、`if` や型ガードで絞る** | コンパイラが矛盾を検出できる＝**ちゃんとした型の使い方** |
| **`as` で型を言い換える** | 検証なしに通す。**おかしいのにコンパイルが通る**ことがある |

> **`as` は型を変換する魔法ではない。  
> チェッカーへの言い切りであり、実行時の安全は増えない。**

だから **可能な限り `as` は使わず、型定義と絞り込みで意図を表す**のがよい、という立場です。

---

## 5. `as` の代わりにやること（初心者向け）

名前は難しくても、やることはシンプルです。

1. **`if` で中身を調べる**（`typeof` / `in` / `instanceof`）  
   → ブロック内で型が狭まり、**`as` なしで**目的の型として扱えることが多いです。  
2. **オブジェクトの形は `interface` や `type` で名前を付ける**  
   → API のレスポンスや state の形を**型として残す**。  
3. **関数は引数・戻り値に型を書く**  
   → 呼び出しと実装のズレをコンパイルで拾う。  

慣れてきたら、**ユーザー定義型ガード**（`function isUser(x): x is User`）や **Zod** などで「実行時検証の結果」を型に載せます。いずれも **`as` でごまかすより、型として筋が通る**やり方です。

---

## 6. `as const` だけは別物

`as const` は**別の機能**です。リテラル型として推論してほしいときの指定であり、**任意の型への言い換え**ではありません。

```typescript
const modes = ["read", "write"] as const;
// 'read' | 'write' の readonly タプルとして推論される
```

**「型アサーションの `as` を減らす」話とは切り離して考えてよい**です。

---

## 7. `as unknown as なんとか` について

二重アサーションは型チェックをほぼ無視できます。**このノートの方針（ちゃんとした型で表現する）からは外れる**ので、**推奨しません**。やむを得ない外部ライブラリの不整合など、例外で使うなら**理由をコメントとレビューに残す**のが最低限です。

---

## 8. 「型があいまいなコード」を見つけるには？

「どこが緩いか」を機械的に洗い出すには、次のような方法があります。

### ステップ1：`tsconfig.json`

- **`"strict": true`** でチェックを厳しくする。  
- **`noImplicitAny`**（`strict` に含まれる）で、暗黙の `any` を減らす。  

いきなり全部オンでエラーだらけになることもあるので、**少しずつ直しながら厳しくする**のが現実的です。

### ステップ2：ESLint（入っているプロジェクトなら）

- **`no-explicit-any`** … `any` の使用を抑える  
- **`no-unsafe-*`** … `any` 経由の危険な代入などを拾う  

`as` 専用の標準ルールは限定的ですが、**`as any` や無理な言い換え**は上記とあわせて減らしやすくなります。

### ステップ3：エディタとコマンド

- **問題（Problems）パネル**で警告・エラーを一覧する  
- **`npx tsc --noEmit`** で型チェックだけ実行する  

### ステップ4：検索で「逃げ」を探す

次は **`as` やチェック無効化で型を回避している**サインです。リファクタ候補のリストにするとよいです。

- `as any` / `as unknown as`（典型的な「型を逃がす」パターン）  
- 単体の `as` を全文検索すると **`as const` も大量にヒット**するので、必要なら **`as const` を除く**など工夫する  
- `@ts-ignore` / `@ts-expect-error`  

---

## 9. まとめ（スクラップ用・短く）

- **型アサーション（`as`）は推奨しない前提**。実行時は安全にならず、チェックをすり抜けさせるだけ。  
- **`interface` / `type` と絞り込み（`if`・型ガード・検証ライブラリ）で表現する**のが「ちゃんとした型」の使い方。  
- **`as const`** は別物（推論の指定）。  
- 緩い・逃げのコードは **`strict`・ESLint・`tsc --noEmit`・検索** で洗い出す。
