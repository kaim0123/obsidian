# 判別可能ユニオン（Discriminated Unions）

> 判別可能ユニオンは TypeScript で**最も強力な設計パターン**の1つ。「**共通のリテラル型フィールド**」で複数の状態をユニオン化することで、各状態に固有のフィールドが型安全に扱えるようになります。Reduxのアクション、API応答、ロード状態 ── あらゆる「複数の状態」がこのパターンで表現できます。

## 1. 判別可能ユニオンとは

ユニオン型のメンバーすべてが、**共通のリテラル型フィールド**（判別子, discriminant）を持つもの。

```typescript
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; side: number }
  | { kind: "rectangle"; width: number; height: number };
```

`kind` が判別子。すべてのメンバーが `kind` を持ち、その値が**それぞれ違うリテラル**になっている。

---

## 2. 何が嬉しいのか

判別子で `if` / `switch` すると、**残りのフィールドが型安全に絞り込まれる**。

```typescript
function area(s: Shape): number {
  switch (s.kind) {
    case "circle":
      return Math.PI * s.radius ** 2;        // s: { kind: "circle"; radius: number }
    case "square":
      return s.side ** 2;                     // s: { kind: "square"; side: number }
    case "rectangle":
      return s.width * s.height;              // s: { kind: "rectangle"; width: number; height: number }
  }
}
```

→ **`s.radius`** や **`s.side`** など、各ケース固有のフィールドが型エラーなく使える。`as` も型ガードも要らない。

---

## 3. 判別子の選び方

### (1) 名前

定番:

- `kind`
- `type`
- `tag`
- `_tag`（fp-tsなど関数型ライブラリで多用）

**チームで統一**するのが大事。

### (2) 値

**リテラル型**にする（`string` / `number` / `boolean`）。

```typescript
// ✅
type T = { kind: "a" } | { kind: "b" };

// ❌ 値の型が広いと判別不可
type T = { kind: string } | { kind: string };
```

### (3) すべてのメンバーで**同じ判別子名**を使う

```typescript
// ❌ 判別子が違うと絞り込めない
type T =
  | { kind: "a" }
  | { type: "b" }; // 判別子の名前がバラバラ

// ✅
type T =
  | { kind: "a" }
  | { kind: "b" };
```

## 4. 典型的な使用例

### (1) Reduxのアクション

```typescript
type Action =
  | { type: "INCREMENT" }
  | { type: "DECREMENT" }
  | { type: "SET"; payload: number }
  | { type: "RESET" };

function reducer(state: { count: number }, action: Action) {
  switch (action.type) {
    case "INCREMENT": return { count: state.count + 1 };
    case "DECREMENT": return { count: state.count - 1 };
    case "SET":       return { count: action.payload };  // ✅ payload にアクセス可
    case "RESET":     return { count: 0 };
  }
}
```

### (2) ロード状態

```typescript
type LoadState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: string };

function render(state: LoadState<User>) {
  switch (state.status) {
    case "idle":    return "Click to load";
    case "loading": return "Loading...";
    case "success": return `Hello, ${state.data.name}`;  // ✅ data
    case "error":   return `Error: ${state.error}`;       // ✅ error
  }
}
```

「**ロード中なのにdataにアクセス**」のようなバグが**コンパイル時に防げる**。

### (3) Result型（成功 or 失敗）

```typescript
type Result<T, E = Error> =
  | { ok: true; value: T }
  | { ok: false; error: E };

function divide(a: number, b: number): Result<number> {
  if (b === 0) return { ok: false, error: new Error("zero division") };
  return { ok: true, value: a / b };
}

const r = divide(10, 2);
if (r.ok) {
  console.log(r.value);   // ✅ number
} else {
  console.log(r.error);   // ✅ Error
}
```

例外の代わりに「失敗もデータ」として扱える。詳しくは「7章 代表的なデータ構造の型設計」で。

### (4) APIレスポンス

```typescript
type ApiResponse<T> =
  | { status: 200; data: T }
  | { status: 404; error: "not_found" }
  | { status: 500; error: "internal_error" };

function handle(res: ApiResponse<User>) {
  if (res.status === 200) {
    res.data;      // ✅ User
  } else {
    res.error;     // ✅ "not_found" | "internal_error"
  }
}
```

ステータスコードで分岐するパターン。

### (5) HTMLイベント

```typescript
type FormEvent =
  | { type: "input"; field: "name" | "email"; value: string }
  | { type: "submit" }
  | { type: "reset" };

function handle(e: FormEvent) {
  if (e.type === "input") {
    e.field;  // ✅ "name" | "email"
    e.value;  // ✅ string
  }
}
```

## 5. 網羅性チェック（Exhaustiveness Check）── これが最大のメリット

`switch` 文で全パターンを書いたかを **コンパイル時に保証** できる。

```typescript
function area(s: Shape): number {
  switch (s.kind) {
    case "circle":    return Math.PI * s.radius ** 2;
    case "square":    return s.side ** 2;
    case "rectangle": return s.width * s.height;
    default:
      const _exhaustive: never = s; // 全部処理済みなら s は never
      return _exhaustive;
  }
}
```

新しい `Shape` メンバー（`triangle`）を追加した瞬間、**`default` 節がコンパイルエラー** になります。

```typescript
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "square"; side: number }
  | { kind: "rectangle"; width: number; height: number }
  | { kind: "triangle"; base: number; height: number }; // 追加

// area() の default 節:
// const _exhaustive: never = s;
// ❌ Type '{ kind: "triangle"; base: number; height: number }' is not assignable to type 'never'.
```

**漏れを型システムが教えてくれる**。これは TypeScript で最も価値あるパターンの一つ。

### `assertNever` ヘルパーで使い回す

```typescript
function assertNever(x: never): never {
  throw new Error(`unhandled: ${JSON.stringify(x)}`);
}

function area(s: Shape): number {
  switch (s.kind) {
    case "circle":    return Math.PI * s.radius ** 2;
    case "square":    return s.side ** 2;
    case "rectangle": return s.width * s.height;
    default:          return assertNever(s);
  }
}
```

## 6. 判別可能ユニオンの設計指針

### (1) 「あり得る状態」を**全部列挙**する

「`loading` 中なのに `data` を持っているかもしれない」というオブジェクトは設計が悪い。状態ごとに**フィールドを明確に分ける**。

```typescript
// ❌ 悪い例: 全部のフィールドが optional
type State = {
  status: string;
  data?: User;
  error?: string;
};

// ✅ 良い例: 判別可能ユニオン
type State =
  | { status: "loading" }
  | { status: "success"; data: User }
  | { status: "error"; error: string };
```

良い例では、`status: "success"` のときに `data` が**必ず存在する**ことが型で保証される。

### (2) 判別子を**最初のフィールド**に

慣例として、判別子を**プロパティの先頭**に置くと読みやすい。

```typescript
type T = { kind: "a"; x: number; y: string };
//        ↑ ここに置く
```

### (3) 数値リテラルや boolean も判別子に使える

```typescript
type Result =
  | { ok: true; value: number }
  | { ok: false; error: Error };
```

`true` / `false` を判別子にする型は「**Result型**」「**成功/失敗**」でよく使う。

```typescript
type Status =
  | { code: 200; data: User }
  | { code: 404; reason: "not_found" }
  | { code: 500; reason: "internal_error" };
```

数値リテラルも有効。

## 7. 判別子なしのユニオン型は使いづらい

### 判別子がない例

```typescript
type T = { name: string } | { age: number };

function f(v: T) {
  if ("name" in v) {
    v.name; // ✅
  } else {
    v.age;  // ✅
  }
}
```

`in` で絞り込めるが、**判別子付きの方が圧倒的に読みやすく安全**。設計時に判別子を入れる。

```typescript
// ✅ 判別子を入れる
type T =
  | { kind: "named"; name: string }
  | { kind: "aged"; age: number };
```

## 8. ネストした判別ユニオン

判別ユニオンは**ネストできる**。

```typescript
type Event =
  | { kind: "click"; target: { type: "button"; id: string } | { type: "link"; href: string } }
  | { kind: "scroll"; offset: number };

function handle(e: Event) {
  if (e.kind === "click") {
    if (e.target.type === "button") {
      e.target.id;   // ✅
    } else {
      e.target.href; // ✅
    }
  }
}
```

ただしネストが深くなりすぎたら、**型を切り出す**べきサイン。

```typescript
type ClickTarget = { type: "button"; id: string } | { type: "link"; href: string };
type Event =
  | { kind: "click"; target: ClickTarget }
  | { kind: "scroll"; offset: number };
```

## 9. ジェネリクスとの組み合わせ

```typescript
type Result<T, E = Error> =
  | { ok: true; value: T }
  | { ok: false; error: E };

function ok<T>(value: T): Result<T> {
  return { ok: true, value };
}

function err<E>(error: E): Result<never, E> {
  return { ok: false, error };
}

const r = divide(10, 2);
if (r.ok) {
  r.value; // ✅
}
```

ジェネリクスと組み合わせると、**型安全な汎用パターン**が書ける。

## 10. 判別ユニオンの落とし穴

### (1) 判別子を**広い型**にしてしまう

```typescript
type T =
  | { kind: string; x: number }   // ❌ kind が string（リテラルでない）
  | { kind: string; y: string };

function f(v: T) {
  if (v.kind === "a") {
    v; // ❌ 絞り込めない（kind が string なので）
  }
}
```

→ `kind: "a"` のように**リテラル型**にする。

### (2) 判別子の値が**重複**している

```typescript
type T =
  | { kind: "x"; a: number }
  | { kind: "x"; b: string }; // ❌ 重複した kind

function f(v: T) {
  if (v.kind === "x") {
    v; // ❌ 絞り込めない
  }
}
```

→ それぞれ別の値にする。

### (3) `as const` を忘れて型が広がる

```typescript
const action = { type: "ADD", payload: 1 };
// 型: { type: string; payload: number }
//          ↑ 広がっている

function dispatch(a: Action) { ... }
dispatch(action); // ❌ Actionに合わない
```

→ `as const` でリテラル型を保つ。

```typescript
const action = { type: "ADD", payload: 1 } as const;
// 型: { readonly type: "ADD"; readonly payload: 1 }
```

### (4) `default` ケースを書き忘れる

```typescript
function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return ...;
    case "square": return ...;
    // rectangle を忘れた
  }
  // 戻り値型が number と合わない（undefined を返すパスがある）
}
```

→ `default` で `assertNever` を呼ぶ習慣を。

### (5) 判別子が**深い場所**にある

```typescript
type T =
  | { meta: { kind: "a" }; x: number }
  | { meta: { kind: "b" }; y: string };

function f(v: T) {
  if (v.meta.kind === "a") {
    v.x; // ✅ TS 4.4以降ならネストした判別子も追えるが、浅い方が安全
  }
}
```

TS 4.4以降は深い判別子も追えるが、**判別子は最上位**に置く方が確実。

## 11. 判別可能ユニオン vs クラス階層

OOPの「クラスと継承」も「複数の形」を表現する手段ですが、判別可能ユニオンの方が:

- データと振る舞いが分離できる（純粋関数で扱える）
- パターンマッチで網羅性が保証される
- JSON化しやすい
- 拡張時に変更箇所が明確

→ TypeScriptでは **クラス階層より判別可能ユニオン**が好まれる傾向。

---

## 12. まとめ

- 判別可能ユニオン = **共通のリテラル型フィールド**を持つユニオン型
- `if` / `switch` で**自動絞り込み**、各ケース固有のフィールドが安全に使える
- **網羅性チェック**（`assertNever`）で漏れをコンパイル時に検出
- 用途: アクション、状態、結果、APIレスポンス、イベント
- 設計: 判別子は**リテラル型**で、**最上位**に、**`kind` か `type`** で統一
- `as const` でリテラル型を保つ

> 判別可能ユニオン + 網羅性チェックは、**TypeScriptの最も価値ある武器**。状態を「ありうる形」で列挙し、対応漏れをコンパイラが教えてくれる ── この体験を一度味わうと、もう昔のJSには戻れません。
