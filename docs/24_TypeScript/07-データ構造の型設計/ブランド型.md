# ブランド型（Branded Types）

## 動機：意味の違う「同じ型」を区別したい

TypeScript は **構造的部分型** なので、構造さえ同じなら互換性ありとみなされます。

```typescript
type UserId = number;
type ProductId = number;

function getUser(id: UserId) {}

const pid: ProductId = 42;
getUser(pid); // 通ってしまう（どちらも number）
```

「`UserId` と `ProductId` は意味が違うのに、どちらも `number`」だと取り違えバグが起きます。
これを **コンパイル時に防ぐ** のがブランド型のテクニックです。

## ブランド型の基本パターン

「**実体は同じだが、型システム上だけ別物**」にします。

```typescript
type UserId    = number & { readonly __brand: "UserId" };
type ProductId = number & { readonly __brand: "ProductId" };
```

`& { readonly __brand: "..." }` の部分は **存在しないプロパティ**ですが、型システムには「タグ」として認識されます。
これにより、`UserId` と `ProductId` は **代入互換ではなくなります**。

```typescript
function getUser(id: UserId) {}

const pid = 42 as ProductId;
getUser(pid); // ❌ エラー
```

## 値を「ブランド付き」に変える

`as` でキャストして作るのがシンプルです。

```typescript
function asUserId(n: number): UserId {
  return n as UserId;
}

const id = asUserId(123);
getUser(id); // OK
```

「**生成関数を 1 か所**」にまとめれば、どこで作られているかが追えます。

## さらに安全に：バリデーション付き生成関数

```typescript
function toUserId(n: number): UserId | null {
  if (!Number.isInteger(n) || n <= 0) return null;
  return n as UserId;
}
```

「**正の整数だけが UserId**」というドメインルールを、生成のときに守れます。

## どんな型にも使える

`number` だけでなく、`string` や object にも使えます。

```typescript
type Email = string & { readonly __brand: "Email" };

function toEmail(s: string): Email | null {
  return /^.+@.+\..+$/.test(s) ? (s as Email) : null;
}
```

「**バリデーションを通した値**」だけを `Email` 型として扱えるので、後続の関数で再検証する必要がなくなります。

## ヘルパー型でテンプレ化

毎回 `& { __brand: "..." }` を書くのは面倒なので、ヘルパーを作ると楽です。

```typescript
type Brand<T, B extends string> = T & { readonly __brand: B };

type UserId = Brand<number, "UserId">;
type Email  = Brand<string, "Email">;
```

## opaque（不透明）型として強化

ブランドプロパティを **`unique symbol`** にすると、外から型を作りにくくなり、より厳格になります。

```typescript
declare const userIdBrand: unique symbol;
type UserId = number & { readonly [userIdBrand]: true };
```

`as UserId` するには `userIdBrand` にアクセスできる必要があり、**専用ファクトリ経由を強制** できます。

## 注意点

- ブランドプロパティは **実体には存在しない**：JSON 化しても消えるが、型は揺らがない
- **演算結果はブランドが落ちる**ことがある：`(a + b)` の結果は `number` に戻る
  - その場合は **再度ファクトリを通す**設計に
- 過剰に使うと **コードが冗長** になる：本当に取り違えが怖い ID や値だけに

## まとめ

- 構造的部分型のせいで「同じ形だが意味が違う型」が混同されやすい
- **ブランド型**は **実体は同じ・型システムだけ別物** にするテクニック
- 専用の生成関数を 1 か所にまとめると、ドメインルールも守れる
- `Brand<T, B>` のヘルパーを作ると簡潔
- 「ID」「Email」「JWT」「正規化済み文字列」などに有効
