# 不変（immutable）を前提にした型

> 「**オブジェクトを書き換える**」ことが、ソフトウェアの複雑さの大部分を生んでいます。TypeScriptには `readonly` / `Readonly<T>` / `as const` などの不変化の道具が揃っており、**「書き換えられないことを型で保証する」**設計に切り替えると、バグ・並行処理・状態管理がぐっとシンプルになります。

## 1. なぜ不変なのか

### 可変オブジェクトの問題

```typescript
function process(arr: number[]) {
  arr.sort();  // 呼び出し側の配列を破壊！
  return arr[0];
}

const data = [3, 1, 2];
const min = process(data);
console.log(data); // [1, 2, 3]（元の順序が消えた）
```

→ **関数が引数を書き換える**ことを呼び出し側は予測できない。コードを読まないと挙動が分からない。

### 不変なら起きない

```typescript
function process(arr: readonly number[]) {
  return [...arr].sort()[0]; // コピーを作って操作
}

const data = [3, 1, 2];
const min = process(data);
console.log(data); // [3, 1, 2] （変更されない）
```

→ **呼び出し側が安心して渡せる**。リファクタしても周りに影響しない。

---

## 2. 不変化の3つの道具

TypeScript で不変を表現する手段:

| 手段 | 効果 | 例 |
|---|---|---|
| **`readonly` 修飾子** | プロパティ/配列を書き換え不可に | `readonly x: number` |
| **`Readonly<T>`** | 全プロパティを `readonly` に | `Readonly<User>` |
| **`as const`** | 値を完全に固定（深い readonly + リテラル化） | `[1, 2] as const` |

---

## 3. `readonly` プロパティ

```typescript
type Point = {
  readonly x: number;
  readonly y: number;
};

const p: Point = { x: 10, y: 20 };
p.x = 100; // ❌ Cannot assign to 'x' because it is a read-only property.
```

### クラスでも使える

```typescript
class Point {
  readonly x: number;
  readonly y: number;

  constructor(x: number, y: number) {
    this.x = x;
    this.y = y;
  }
}
```

クラスフィールドの省略形:

```typescript
class Point {
  constructor(
    readonly x: number,
    readonly y: number
  ) {}
}
```

## 4. `Readonly<T>` ユーティリティ型

`type` の全プロパティを一括で `readonly` にする。

```typescript
type User = { name: string; age: number };
type FrozenUser = Readonly<User>;
// { readonly name: string; readonly age: number }
```

### 関数引数で使う

```typescript
function update(u: Readonly<User>) {
  u.name = "..."; // ❌
}
```

「**この関数は引数を書き換えない**」が型で表現される。

### ただしシャロー

```typescript
type Group = {
  members: User[];
};

const frozen: Readonly<Group> = { members: [] };
frozen.members = [];        // ❌
frozen.members.push(...);   // ✅ 中身は書き換えられる！
```

→ 完全な不変が必要なら自前で深く `readonly` を書く（後述）。

---

## 5. `readonly` 配列

```typescript
const arr: readonly number[] = [1, 2, 3];

arr.push(4);    // ❌
arr[0] = 100;   // ❌
arr.sort();     // ❌

arr.map(n => n * 2);    // ✅ 非破壊メソッドはOK
[...arr, 4];             // ✅ コピーして新しい配列
```

詳しくは [[02-配列とタプルとreadonly配列]]。

### 関数引数のデフォルトは `readonly T[]`

```typescript
function sum(arr: readonly number[]): number { ... }
function find<T>(arr: readonly T[], pred: (x: T) => boolean): T | undefined { ... }
```

「書き換えない契約」を型で示すのが基本。

## 6. `as const` で完全な不変

```typescript
const config = {
  api: { url: "https://...", timeout: 5000 },
  features: ["dark", "i18n"],
} as const;

// 型:
// {
//   readonly api: { readonly url: "https://..."; readonly timeout: 5000 };
//   readonly features: readonly ["dark", "i18n"];
// }

config.api.url = "...";    // ❌ 全部 readonly
config.features.push(...);  // ❌ readonly tuple
```

`as const` は**ネスト全体に readonly + リテラル型**を適用。**真の定数**。

詳しくは [[05-リテラル型とas-const]]。

## 7. 深い不変（DeepReadonly）の自作

`Readonly<T>` はシャロー。深い `readonly` が欲しいときは自作:

```typescript
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object
    ? DeepReadonly<T[K]>
    : T[K];
};

type FullyFrozen = DeepReadonly<{
  a: { b: { c: number } };
  arr: number[];
}>;
// { readonly a: { readonly b: { readonly c: number } }; readonly arr: readonly number[] }
```

`as const` でも同じ効果が得られるが、**型レベルの操作で深く readonly化**したいときは `DeepReadonly`。

## 8. 不変な「更新」のパターン

不変な型は「変えられない」のではなく、「**変えるときは新しい値を作る**」のがルール。

### オブジェクトの一部を更新

```typescript
const u1: User = { id: "1", name: "Alice", age: 30 };
const u2 = { ...u1, age: 31 }; // 新しい User
```

### ネストしたフィールドの更新

```typescript
const state = { user: { name: "Alice", age: 30 } };
const newState = {
  ...state,
  user: { ...state.user, age: 31 },
};
```

ネストが深くなるとつらい。**Immer** などのライブラリで救う:

```typescript
import { produce } from "immer";

const newState = produce(state, draft => {
  draft.user.age = 31; // 中で書き換えても、結果は不変なオブジェクト
});
```

### 配列の更新

```typescript
const arr = [1, 2, 3];

// 追加
const added = [...arr, 4];

// 削除
const removed = arr.filter((_, i) => i !== 1);

// 1要素変更
const updated = arr.map((v, i) => (i === 1 ? 99 : v));

// ソート（コピーしてから）
const sorted = [...arr].sort();
```

## 9. 不変な型と React / Redux

### React の Props

```typescript
type Props = {
  readonly user: Readonly<User>;
  readonly onChange: (u: User) => void;
};

function UserCard(props: Props) { ... }
```

→ **コンポーネント内部で props を書き換えない**ことが型で保証される。React の本質的な思想と一致。

### Redux の State

```typescript
type State = Readonly<{
  user: ReadonlyArray<User>;
  filter: string;
}>;
```

Reducerで「**state を直接書き換えない、新しい state を返す**」原則を型で守る。Immer を使えば書き味は可変っぽくできる。

## 10. 不変なクラス（値オブジェクト）

```typescript
class Money {
  constructor(
    readonly amount: number,
    readonly currency: string
  ) {}

  add(other: Money): Money {
    if (this.currency !== other.currency) throw new Error();
    return new Money(this.amount + other.amount, this.currency); // 新しいインスタンス
  }
}
```

クラスフィールドが `readonly`、メソッドは**自身を変えず新しいインスタンスを返す**。これが不変な値オブジェクトの基本形。

## 11. `Object.freeze` との違い

JavaScriptの `Object.freeze` も不変化の手段ですが、TypeScript の `readonly` とは**性質が違う**:

| 観点 | `readonly` | `Object.freeze` |
|---|---|---|
| いつ効く | コンパイル時 | 実行時 |
| 違反時 | コンパイルエラー | サイレント無視 / `strict mode` でエラー |
| パフォーマンス | 影響なし（消える） | わずかにコスト |
| 深く効くか | シャロー | シャロー（自前で再帰） |
| 型情報 | 反映される | 反映されない |

→ **TS的には `readonly` が中心**。実行時にも防ぎたいなら `Object.freeze` を併用。

```typescript
const config = Object.freeze({ ... }) as Readonly<Config>;
```

## 12. 不変設計のメリット

### (1) **時間の経過で値が変わらない**

```typescript
const u: Readonly<User> = loadUser();
doStuff(u);
// この時点で u は最初と同じ ── 確信できる
```

→ 状態管理が単純に。

### (2) **コピーが安全**

```typescript
const u2 = u; // 参照コピーで OK（元が書き換わらないので）
```

### (3) **並行処理に強い**

不変ならスレッド/非同期で同時アクセスしても安全。

### (4) **テストが簡単**

「この入力でこの出力」が決まる。副作用のない関数（純粋関数）と相性が良い。

### (5) **デバッグしやすい**

「いつ書き換わったか」を追わなくていい。

---

## 13. 不変設計のコスト

- **コピーのコスト**: 大きなオブジェクトを毎回コピーすると遅い（→ Immer / Immutable.js で解決）
- **学習コスト**: 「変えるときは新しいものを作る」発想に慣れる必要
- **メモリ**: 元のオブジェクトと新しいオブジェクトが両方残る場面も
- **ボイラープレート**: ネストの更新が冗長になりがち

→ **アプリ全体を不変にする必要はない**。状態・引数・公開APIの境界で不変を意識し、内部の小さなロジックは可変でOK。

---

## 14. 実務での「不変」適用ガイド

| 場所 | 不変化 |
|---|---|
| 関数の引数（基本） | ✅ `readonly` / `Readonly<T>` |
| 関数の戻り値 | △ 場合による（呼び出し側に自由を渡すなら可変） |
| 設定オブジェクト | ✅ `as const` |
| Reactのprops | ✅ `Readonly<Props>` |
| Reduxのstate | ✅ `Readonly<State>` |
| ドメインモデル | ✅ `readonly` フィールド |
| ローカル変数 | △ `const` で十分なことが多い |
| 一時的な計算 | × 過剰 |

## 15. アンチパターン

### (1) `readonly` を関数の引数に使わない

```typescript
function sum(arr: number[]): number { // ❌ 書き換える可能性が型に出ている
  return arr.reduce(...);
}

function sum(arr: readonly number[]): number { // ✅
  return arr.reduce(...);
}
```

### (2) ネストを忘れる（シャロー readonly）

```typescript
type T = Readonly<{ items: number[] }>; // items は書き換え可能！
```

→ `DeepReadonly` か `as const`。

### (3) 不変な型を `as` で「外す」

```typescript
function f(arr: readonly number[]) {
  (arr as number[]).push(1); // ❌ 嘘の書き換え
}
```

→ 不変の意味がなくなる。設計を見直す。

### (4) 全部不変にして書き味が悪くなる

```typescript
let i = 0;
i = i + 1; // 普通の処理は可変でOK
```

→ 「**境界で不変、内部は適度に**」。

---

## 16. まとめ

- 不変 = 「**書き換えられない**」を型で保証
- 道具: **`readonly`** / **`Readonly<T>`** / **`as const`** / **`DeepReadonly`**
- 関数引数のデフォルトは **`readonly T[]`** / **`Readonly<T>`**
- 値オブジェクト・state・props は不変設計が定石
- `Object.freeze` は実行時、`readonly` はコンパイル時（用途で使い分け）
- ネストは**シャロー** ── 完全な不変は `as const` か `DeepReadonly`
- 過剰な不変化は逆効果。**境界 = 不変、内部 = 必要に応じて**

> 「**変えない**」と決めることは、「**今のコードが何をしうるか**」という理解可能性を取り戻す行為です。`readonly` を書く分だけ、3か月後の自分とチームが救われます。
