# ドメインモデルの表現（ID・値オブジェクト・列挙）

> 「**`string` でも動くから `string` でいい**」 ── このまま書き続けると、`UserId` と `OrderId` を取り違えても気付かないコードになります。**ドメインの概念を型で表現する**ことは、TypeScriptの最も価値ある投資の1つ。「IDをID型に」「値を値オブジェクトに」「選択肢を列挙に」── この3つを身につけると、ロジックがバグに強くなります。

## 1. なぜドメインを型にするのか

### `string` のままだと何が起きるか

```typescript
function transfer(fromUserId: string, toUserId: string, amount: string) { ... }

// 引数の順序を間違えても気付かない
transfer(toId, fromId, "100");

// 別のIDを渡しても通る
transfer(orderId, userId, "100"); // ❌ orderId は本来User用ではない
```

→ **型システムは「全部 string」だと判断**するので、間違いを検出できない。

### ドメインの型を作ると

```typescript
type UserId = string & { __brand: "UserId" };
type OrderId = string & { __brand: "OrderId" };
type Amount = number & { __brand: "Amount" };

function transfer(fromUserId: UserId, toUserId: UserId, amount: Amount) { ... }

const u1: UserId = ...;
const o1: OrderId = ...;

transfer(u1, o1, ...); // ❌ OrderId は UserId に代入できない
```

**取り違えがコンパイル時にバレる**。

## 2. Branded Types（ブランド型）── ID型の作り方

### 基本パターン

`string` や `number` に「**フェイクのプロパティ**」を交差させて、型を区別する。

```typescript
type UserId = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };
```

`__brand` は実体には存在しない**型レベルだけのマーカー**。`string` としては使えるが、`UserId` と `OrderId` は別の型として扱われる。

### 値の作成

普通の文字列を直接代入はできない:

```typescript
const id: UserId = "u123"; // ❌ "u123" には __brand プロパティがない
```

→ **コンストラクタ関数**を作る。

```typescript
function userId(s: string): UserId {
  return s as UserId; // 内部で1回だけ as
}

const u: UserId = userId("u123"); // ✅
```

### バリデーション付きコンストラクタ

```typescript
function userId(s: string): UserId {
  if (!/^u\d+$/.test(s)) {
    throw new Error(`Invalid UserId: ${s}`);
  }
  return s as UserId;
}
```

→ **「ID型を作れる = ID として正当**」という保証が型に込められる。

### Result型版（throwしない）

```typescript
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

function userId(s: string): Result<UserId, "invalid"> {
  if (!/^u\d+$/.test(s)) return { ok: false, error: "invalid" };
  return { ok: true, value: s as UserId };
}
```

詳しくは [[02-結果型Result_Either]]。

## 3. Branded Types のバリエーション

### `__brand` の名前は何でもよい

```typescript
type UserId = string & { _tag: "UserId" };
type UserId = string & { __type: "UserId" };
type UserId = string & { readonly brand: unique symbol };
```

慣例として `__brand` か `_tag` を使うことが多い。**チームで統一**するのが大事。

### `unique symbol` 版（より厳密）

```typescript
declare const UserIdBrand: unique symbol;
type UserId = string & { [UserIdBrand]: true };
```

**他のコードからアクセスできないsymbol**を使う。最も厳密だが、書き味が複雑になる。

### ヘルパー型化

```typescript
type Brand<T, B> = T & { readonly __brand: B };

type UserId = Brand<string, "UserId">;
type OrderId = Brand<string, "OrderId">;
type Email = Brand<string, "Email">;
type ProductId = Brand<number, "ProductId">;
```

`Brand<T, B>` を1個用意しておくと、増やすときが楽。

### Zod での導出

```typescript
import { z } from "zod";

const UserIdSchema = z.string().regex(/^u\d+$/).brand("UserId");
type UserId = z.infer<typeof UserIdSchema>;

const u = UserIdSchema.parse("u123"); // UserId
```

Zodの `.brand()` でスキーマと型を一元管理できる。**実務ではこれが一番楽**。

## 4. Branded Types の効果

### (1) 引数の取り違えを防ぐ

```typescript
function getOrder(orderId: OrderId): Order { ... }

const u = userId("u1");
getOrder(u); // ❌ UserIdはOrderIdとして使えない
```

### (2) コードを読むだけで意図が分かる

```typescript
function send(to: Email, subject: Subject): Promise<void> { ... }
```

`string` `string` より、**何を渡すべきか一目瞭然**。

### (3) 文字列操作で「型が剥がれる」ことに気付ける

```typescript
const u: UserId = userId("u1");
const upper = u.toUpperCase(); // 型: string（UserId ではなくなる）
```

→ ID型を**変換せずに保つ**設計になる。

## 5. 値オブジェクト（Value Object）

「**値そのものに意味を持たせる**」ためのオブジェクト。プリミティブのラッパーだが、不変・等価性・操作を型に込める。

### 例: Money

```typescript
type Currency = "JPY" | "USD" | "EUR";

class Money {
  constructor(
    readonly amount: number,
    readonly currency: Currency
  ) {
    if (amount < 0) throw new Error("amount must be non-negative");
  }

  add(other: Money): Money {
    if (this.currency !== other.currency) {
      throw new Error("currency mismatch");
    }
    return new Money(this.amount + other.amount, this.currency);
  }

  equals(other: Money): boolean {
    return this.amount === other.amount && this.currency === other.currency;
  }
}
```

→ **通貨が違うMoneyを足せない**こと、**負の金額を持てない**ことが型・ロジックで保証される。

### 値オブジェクトの特徴

1. **不変**（`readonly`）
2. **等価性は値で判定**（参照ではない）
3. **不正な値を持てない**（コンストラクタでチェック）
4. **操作は新しい値を返す**（自身を変更しない）

### 値オブジェクトを `type` だけで作る（軽量版）

```typescript
type Money = {
  readonly amount: number;
  readonly currency: Currency;
};

function money(amount: number, currency: Currency): Money {
  if (amount < 0) throw new Error();
  return { amount, currency };
}

function addMoney(a: Money, b: Money): Money {
  if (a.currency !== b.currency) throw new Error();
  return { amount: a.amount + b.amount, currency: a.currency };
}
```

クラス vs 関数+型は好み。**シンプルなら関数で十分**、メソッドが多いならクラス。

## 6. 列挙の表現方法

「選択肢が決まっているもの」を型で表現する方法は3つ。

### (1) リテラルユニオン型（推奨）

```typescript
type Role = "admin" | "user" | "guest";
type Status = "loading" | "success" | "error";
```

メリット:

- **シンプル**
- **タイポがコンパイル時に検出**される
- ツリーシェイキングで余分なコードが残らない

### (2) `as const` オブジェクト

```typescript
const Role = {
  Admin: "admin",
  User: "user",
  Guest: "guest",
} as const;

type Role = typeof Role[keyof typeof Role];
// "admin" | "user" | "guest"
```

メリット:

- **値（定数）も型も両方使える**
- import して `Role.Admin` のように使える

### (3) `enum`（**非推奨**になりつつある）

```typescript
enum Role {
  Admin = "admin",
  User = "user",
  Guest = "guest",
}
```

問題点:

- TypeScript固有（純粋なJSではない）
- ツリーシェイキングが効きにくい
- `const enum` は `isolatedModules` で使えない
- `enum` の値が `Role` 型に絞り込めず、`string` を渡せてしまう（数値enumの場合）
- 型と値の両方を生成し、複雑さが増す

→ **新規コードでは `enum` を避け、`as const` オブジェクトかリテラルユニオンを使う**のが現代の主流。

詳しくは [[enum_vs_const_assertions]]。

## 7. ドメイン型の典型例

### Email

```typescript
type Email = string & { readonly __brand: "Email" };

function email(s: string): Email {
  if (!/^[^@]+@[^@]+\.[^@]+$/.test(s)) throw new Error("invalid");
  return s as Email;
}
```

### URL

```typescript
type URLString = string & { readonly __brand: "URL" };

function url(s: string): URLString {
  try {
    new URL(s);
    return s as URLString;
  } catch {
    throw new Error("invalid url");
  }
}
```

### 日付（ISO文字列）

```typescript
type ISODate = string & { readonly __brand: "ISODate" };

function isoDate(s: string): ISODate {
  if (isNaN(Date.parse(s))) throw new Error("invalid date");
  return s as ISODate;
}
```

### 正の整数

```typescript
type PositiveInt = number & { readonly __brand: "PositiveInt" };

function positiveInt(n: number): PositiveInt {
  if (!Number.isInteger(n) || n <= 0) throw new Error();
  return n as PositiveInt;
}

function repeat(s: string, count: PositiveInt): string {
  return s.repeat(count);
}
```

→ **「正の整数しか受け入れない」ことが型で保証**される。

## 8. ドメインモデルの組み合わせ

```typescript
type UserId = Brand<string, "UserId">;
type Email = Brand<string, "Email">;
type Age = Brand<number, "Age">;

type User = {
  readonly id: UserId;
  readonly email: Email;
  readonly age: Age;
  readonly name: string;
};

function createUser(input: {
  email: string;
  age: number;
  name: string;
}): User {
  return {
    id: userId(generateId()),
    email: email(input.email),
    age: age(input.age),
    name: input.name,
  };
}
```

各フィールドが**意味のある型**になり、誤代入が防がれる。

## 9. ドメイン型と外部世界の境界

### 入力境界（外部 → ドメイン）

```typescript
async function loadUser(id: string): Promise<User> {
  const data: unknown = await fetch(`/api/users/${id}`).then(r => r.json());
  return UserSchema.parse(data); // Zodで検証 → User型へ
}
```

### 出力境界（ドメイン → 外部）

```typescript
function userToJSON(u: User): { id: string; email: string; age: number; name: string } {
  return {
    id: u.id,         // Branded → string に自動で広がる
    email: u.email,
    age: u.age,
    name: u.name,
  };
}
```

ドメイン型は**内部だけで使う**。外部とのやりとりでは普通の型に戻すか、Zodで検証する。

## 10. アンチパターン

### (1) 全部 `string`

```typescript
function transfer(from: string, to: string, amount: string) { ... }
```

→ Branded Typesで意味を持たせる。

### (2) 同じドメインで重複した型

```typescript
type UserId1 = string;
type UserId2 = Brand<string, "UserId">;
// プロジェクトに混在
```

→ 1つの型に統一。

### (3) Branded Type を `as` で乱用

```typescript
const id: UserId = anyString as UserId; // ❌ 検証なし
```

→ **コンストラクタ関数を経由**する（バリデーションを内包）。

### (4) `enum` を新規コードで使う

→ `as const` オブジェクトかリテラルユニオン。

### (5) 値オブジェクトを `let` で書き換える

```typescript
const m = new Money(100, "JPY");
m.amount = 200; // readonly でないとできてしまう
```

→ **`readonly` 必須**。

## 11. ドメイン型のコスト

ドメイン型化には**コスト**もある:

- ボイラープレートが増える
- バリデーションロジックを書く必要
- 入出力で変換が必要
- チームメンバーの理解が必要

### コスト vs 利益の判断

- **小さなスクリプト** → やらなくてOK
- **業務アプリ** → IDと値オブジェクトはやる価値あり
- **金融・医療など、間違いが致命的** → 全力でやる

---

## 12. まとめ

- **Branded Types**: `string & { __brand: "X" }` で型を区別
- **値オブジェクト**: 不変・等価・自己バリデーション・新しい値を返す
- **列挙**: リテラルユニオン or `as const` オブジェクトを推奨（`enum` は非推奨）
- **コンストラクタ関数**でバリデーションを内包
- **Zod の `.brand()`** で楽に作れる
- **入出力境界**で変換、ドメイン型は内部に閉じる

> 「**型でドメインを表現する**」とは、コードを書くより**設計を書く**こと。最初は手間に感じますが、3か月後の自分が「IDを取り違えるバグ」で時間を溶かさないための投資です。
