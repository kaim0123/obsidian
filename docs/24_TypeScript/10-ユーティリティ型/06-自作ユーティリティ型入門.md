# 自作ユーティリティ型入門（作りすぎない基準）

> マップ型と条件型を覚えると「**自分で何でもユーティリティ型を作れる**」気分になります。が、**作りすぎは保守の敵**。本ファイルでは「**いつ自作するか**」「**いつ標準で済ますか**」「**よくある自作型のパターン**」を整理します。

## 1. 自作する前に確認: 標準で済まないか？

**まず標準ユーティリティ型を思い出す**:

| やりたいこと | 標準型 |
|---|---|
| 全 optional | `Partial<T>` |
| 全必須 | `Required<T>` |
| 全 readonly | `Readonly<T>` |
| 一部キーだけ | `Pick<T, K>` |
| 一部キー除外 | `Omit<T, K>` |
| ユニオンから除外 | `Exclude<T, U>` |
| ユニオンから抽出 | `Extract<T, U>` |
| null/undefined 除外 | `NonNullable<T>` |
| 関数戻り値 | `ReturnType<T>` |
| 関数引数 | `Parameters<T>` |
| Promise 中身 | `Awaited<T>` |
| 任意キー → V | `Record<K, V>` |

これらの**組み合わせ**で大半は解決する。

```typescript
// 例: id を除いて全 optional に
type UpdateInput = Partial<Omit<User, "id">>;

// 例: 公開用に password を抜いて readonly に
type PublicUser = Readonly<Omit<User, "password">>;
```

→ **組み合わせで書ける**ならそれが正解。自作は最後の手段。

## 2. 「自作すべき」シグナル

以下のいずれかに当てはまるなら、自作する価値あり:

### (1) 同じパターンが**3箇所以上**で出てくる

```typescript
// プロジェクト内で頻出
type T1 = Partial<Omit<User, "id" | "createdAt">>;
type T2 = Partial<Omit<Post, "id" | "createdAt">>;
type T3 = Partial<Omit<Comment, "id" | "createdAt">>;

// → ヘルパ型化
type UpdateInput<T> = Partial<Omit<T, "id" | "createdAt">>;
```

### (2) 標準型では**深さ**や**条件**が足りない

```typescript
// Partial はシャロー → DeepPartial を自作
type DeepPartial<T> = {
  [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K];
};
```

### (3) **ドメイン特有の表現**

```typescript
// Result 型
type Result<T, E = Error> =
  | { ok: true; value: T }
  | { ok: false; error: E };

// Branded Type
type Brand<T, B> = T & { readonly __brand: B };
```

### (4) **チームの規約**として標準化したい

```typescript
type ApiResponse<T> = {
  data: T;
  meta: { timestamp: string; requestId: string };
};
```

## 3. 「自作しない方がよい」シグナル

### (1) 1か所限り

```typescript
// 1か所しか使わないなら…
type T = Partial<Omit<User, "id">>;
// インラインで書けば十分
```

### (2) 名前が思いつかない

「**良い名前を付けられない型**」は、たいてい**設計が悪い**。先に設計を整える。

### (3) 既存の型と1文字違いの「微妙に違う」型を量産

```typescript
type UserCreate = ...;
type UserCreate2 = ...;  // 1か所違うだけ
type UserCreate3 = ...;
```

→ ジェネリクスでまとめる、もしくは設計の見直し。

### (4) 高度すぎてチームメンバーが読めない

```typescript
type Wat<T> = { [K in keyof T as `__${K & string}__`]?: T[K] extends infer U ? Partial<U> : never };
```

→ 自分しか読めない型は資産にならない。

## 4. 定番の自作ユーティリティ型

実プロジェクトでよく自作されるもの。

### `DeepPartial<T>`

```typescript
type DeepPartial<T> = {
  [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K];
};
```

### `DeepReadonly<T>`

```typescript
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};
```

### `DeepRequired<T>`

```typescript
type DeepRequired<T> = {
  [K in keyof T]-?: T[K] extends object ? DeepRequired<T[K]> : T[K];
};
```

### `Override<T, R>`（プロパティ上書き）

```typescript
type Override<T, R> = Omit<T, keyof R> & R;

type T = Override<User, { age: string }>;
// User の age を string に置き換え
```

### `StrictOmit<T, K>`（タイポを検出する Omit）

```typescript
type StrictOmit<T, K extends keyof T> = Omit<T, K>;

type T = StrictOmit<User, "wrong"); // ❌ エラー
```

→ 標準 `Omit` の制約は緩いので、厳密版を作る価値あり。

### `Brand<T, B>`（Branded Types）

```typescript
type Brand<T, B> = T & { readonly __brand: B };

type UserId = Brand<string, "UserId">;
type Email = Brand<string, "Email">;
```

### `Result<T, E>` / `Option<T>` / `Either<L, R>`

```typescript
type Result<T, E = Error> =
  | { ok: true; value: T }
  | { ok: false; error: E };

type Option<T> = T | null;

type Either<L, R> =
  | { left: L }
  | { right: R };
```

### `Nullable<T>` / `Undefinable<T>`

```typescript
type Nullable<T> = T | null;
type Undefinable<T> = T | undefined;
type Maybe<T> = T | null | undefined;
```

### `KeysOfType<T, V>`（特定型のキーだけ抽出）

```typescript
type KeysOfType<T, V> = {
  [K in keyof T]: T[K] extends V ? K : never;
}[keyof T];

type T = KeysOfType<User, string>;
// User の string 型のキーのみ
```

### `PickByType<T, V>`（特定型のフィールドだけ）

```typescript
type PickByType<T, V> = {
  [K in keyof T as T[K] extends V ? K : never]: T[K];
};

type T = PickByType<User, string>;
// { name: string; email: string } など
```

### `Awaitable<T>` / `MaybePromise<T>`

```typescript
type MaybePromise<T> = T | Promise<T>;

function process<T>(value: MaybePromise<T>): Promise<T> {
  return Promise.resolve(value);
}
```

### `Prettify<T>`（型表示を見やすく）

```typescript
type Prettify<T> = {
  [K in keyof T]: T[K];
} & {};
```

VSCode のホバーで **`{ a: ...; b: ...; }` のように展開**してくれる。複雑な型を読むときの神テクニック。

## 5. 「タイプチャレンジ」級の高度な型

ライブラリ作者向け。アプリでは滅多に書かない。

### `Get<T, P>`（深いプロパティアクセス）

```typescript
type Get<T, P extends string> =
  P extends `${infer K}.${infer Rest}`
    ? K extends keyof T
      ? Get<T[K], Rest>
      : never
    : P extends keyof T
    ? T[P]
    : never;

type T = Get<{ a: { b: { c: number } } }, "a.b.c">; // number
```

### `CamelCase<T>`（テンプレートリテラル型）

```typescript
type CamelCase<S extends string> =
  S extends `${infer First}_${infer Rest}`
    ? `${First}${Capitalize<CamelCase<Rest>>}`
    : S;

type T = CamelCase<"hello_world_foo">; // "helloWorldFoo"
```

これらは「**書けると気持ちいい**」が、**実務コードに持ち込まない**のがプロのマナー。読み手に負担をかけるだけ。

→ どうしても必要なら **`type-fest`** などのライブラリから持ってくる。

## 6. ライブラリで提供されているユーティリティ型

`type-fest` は「自作したくなる型」のほぼ全部を提供:

```typescript
import {

  ReadonlyDeep,
  RequiredDeep,
  CamelCase,
  KebabCase,
  SnakeCase,
  Promisable,

  // ... 他数百

```

→ **自作する前に `type-fest` を見る**。再発明を避ける。

## 7. 自作型の置き場所

### (1) プロジェクト全体で共通

```
src/
  types/
    common.ts       // Brand, Result, DeepPartial など
    api.ts          // ApiResponse, ApiError
    domain.ts       // ドメイン特有の型
```

### (2) モジュールごとに固有

```

  features/
    user/
      types.ts       // User, UserId, UserUpdateInput
```

## 8. 自作ユーティリティ型のベストプラクティス

### (1) **JSDoc コメントを書く**

```typescript
/**
 * オブジェクトのプロパティを再帰的に optional にする。
 * @example
 * type T = DeepPartial<{ a: { b: number } }>;
 * //   ^ { a?: { b?: number } }
 */
type DeepPartial<T> = {
  [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K];
};
```

→ 読み手が**意図と挙動**をすぐ理解できる。

### (2) **テストする**

複雑な型は**実際のオブジェクトに適用**して結果を確認:

```typescript
type Test = DeepPartial<{ a: { b: number; c: string }; d: boolean[] }>;

const x: Test = { a: { b: 1 } }; // ✅ コンパイルが通るかで動作確認
```

または `tsd` のような型テストライブラリで:

```typescript
import { expectType } from "tsd";

expectType<{ a?: number }>(({} as DeepPartial<{ a: number }>));
```

### (3) **シンプルに保つ**

```typescript
// ❌ 1行で全部書こうとする
type X<T> = { [K in keyof T as T[K] extends Function ? never : K]: T[K] extends object ? X<T[K]> : T[K] | null };

// ✅ 段階的に組み立てる
type ExcludeFunctions<T> = {
  [K in keyof T as T[K] extends Function ? never : K]: T[K];
};
type Nullable<T> = T | null;
type X<T> = {
  [K in keyof ExcludeFunctions<T>]: T[K] extends object ? X<T[K]> : Nullable<T[K]>;
};
```

→ 読みやすく、デバッグしやすい。

### (4) **`Prettify` で型展開を確認**

```typescript
type T = Override<User, { age: string }>;
type T2 = Prettify<T>;
// VSCodeでホバー: 全プロパティが展開されて見える
```

## 9. アンチパターン

### (1) **自作型の名前が標準型と被る**

```typescript
type Pick<T, K> = ...; // ❌ 標準と衝突
```

### (2) **ジェネリクスの名前が分かりにくい**

```typescript
type X<A, B, C, D> = ...; // ❌ A, B, C, D の意味が不明

type X<TInput, TOutput, TError> = ...; // ✅ 意味が分かる
```

### (3) **過剰な再帰**

```typescript
type Recursive<T> = { x: Recursive<T> }; // 無限再帰でコンパイラが死ぬ
```

→ 終了条件を**必ず明示**。

### (4) **「動くからOK」で複雑な型を放置**

```typescript
type Wat<T> = T extends infer U ? U extends ... : ...;
```

→ 半年後に自分も読めない。**シンプルに書き直す**。

### (5) **「全部自作してアイデンティティ」**

```typescript
type MyPartial = ...;  // 標準 Partial で済むのに自作
type MyOmit = ...;
```

→ 標準で済むなら標準。

## 10. 自作する前のチェックリスト

- [ ] 標準ユーティリティ型の組み合わせで書けない？
- [ ] `type-fest` などのライブラリにない？
- [ ] 同じパターンが**3箇所以上**で出る？
- [ ] **良い名前**が付けられる？
- [ ] **JSDoc** で意図を書ける？
- [ ] **テスト**で動作確認できる？
- [ ] チームメンバーが**読める**複雑度？

## 12. まとめ

- **まず標準ユーティリティ型と組み合わせ**で済むか確認
- 自作するシグナル: **3箇所以上 / 標準では深さ不足 / ドメイン特有 / チーム規約化**
- 定番の自作型: **`DeepPartial`, `Override`, `StrictOmit`, `Brand`, `Result`**
- 高度な型は**`type-fest`** から持ってくる
- ベストプラクティス: **JSDoc / テスト / シンプル / 段階的に組み立て**
- アンチパターン: 標準と名前衝突 / ジェネリクス名が不明 / 過剰再帰 / 全部自作

> 「**ユーティリティ型は書けるほど偉い**」ではなく、「**チームが読める範囲で必要なものだけ**」が成熟したスタイル。標準型を組み合わせて80点、自作で残り15点、ライブラリで5点 ── このバランスが理想です。
