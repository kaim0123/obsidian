# 自作ユーティリティ型

標準のユーティリティ型では足りないとき、自分で作ることができます。
ただし「**作りすぎない**」のが鉄則。**標準にあるものを優先**し、本当に必要なものだけを定義しましょう。

## DeepPartial：深く入れ子に省略可

`Partial` は 1 階層しか効きません。ネストの中までオプショナルにしたいときは、再帰型で書きます。

```typescript
type DeepPartial<T> = {
  [P in keyof T]?: T[P] extends object
    ? DeepPartial<T[P]>
    : T[P];
};

type Config = {
  server: { host: string; port: number };
  log: { level: "info" | "debug" };
};

type PartialConfig = DeepPartial<Config>;
// {
//   server?: { host?: string; port?: number };
//   log?: { level?: "info" | "debug" };
// }
```

`object` 判定は配列や関数も含むので、厳密には用途に応じて条件を増やします。

## DeepReadonly：深く不変にする

```typescript
type DeepReadonly<T> = {
  readonly [P in keyof T]: T[P] extends object
    ? DeepReadonly<T[P]>
    : T[P];
};
```

「設定オブジェクト全体を絶対に書き換えない」ことを保証したいときに有用です。

## NonEmptyArray：空配列を許さない

```typescript
type NonEmptyArray<T> = [T, ...T[]];

const ok: NonEmptyArray<number> = [1, 2, 3];
// const ng: NonEmptyArray<number> = []; // エラー
```

「**最低 1 件は必ずある**」という業務ルールを型で表現できます。

## ValueOf：オブジェクトの値型を取り出す

```typescript
type ValueOf<T> = T[keyof T];

const status = {
  PENDING: "pending",
  APPROVED: "approved",
} as const;

type Status = ValueOf<typeof status>;
// "pending" | "approved"
```

`as const` と組み合わせると、enum なしで「定数の集合」を型に変換できます。

## RequireAtLeastOne：少なくとも 1 つ必須

「**`a` か `b` か `c` のどれか 1 つは必ず指定**」のような型を作れます。

```typescript
type RequireAtLeastOne<T, K extends keyof T = keyof T> = {
  [P in K]-?: Required<Pick<T, P>> & Partial<Pick<T, Exclude<K, P>>>;
}[K];

type Contact = {
  email?: string;
  phone?: string;
  postal?: string;
};

type AnyContact = RequireAtLeastOne<Contact>;
// 少なくとも email/phone/postal のどれか 1 つは必須
```

少し複雑ですが、フォームバリデーションで重宝します。

## Result 型：成功か失敗か

例外より戻り値で扱いたいときの型（→ `05-レシピ/Result型の自作.md`）。

```typescript
type Ok<T>  = { ok: true;  value: T };
type Err<E> = { ok: false; error: E };
type Result<T, E = Error> = Ok<T> | Err<E>;
```

判別可能ユニオンとして扱えるので、型ガードと相性ばつぐんです。

## 自作するときのチェックリスト

1. **標準にないか確認した？**（`Partial` / `Pick` / `Omit` / `Exclude` などで足りることが多い）
2. **2 か所以上で使う？** 1 か所だけなら、その場で書く方が読みやすい
3. **名前は意図を表している？** `MyType` ではなく `DeepPartial` のように動作が伝わる名前
4. **再帰や条件が複雑になっていないか？** 読み手の負荷が高い型は **コメントを付ける**
5. **型のテストはある？** `expectType` などで挙動を担保しておくと将来の自分が助かる

## まとめ

- 標準ユーティリティ型で足りないときだけ、自分で定義する
- `DeepPartial` / `DeepReadonly` / `NonEmptyArray` / `ValueOf` あたりは定番
- 複雑になりすぎたら、それは「設計の見直しサイン」かもしれない
- 自作型はライブラリのように **再利用される責任** を持つので、慎重に育てる
