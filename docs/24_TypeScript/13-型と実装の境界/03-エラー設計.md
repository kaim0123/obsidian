# エラー設計（例外・戻り値・エラーオブジェクト）

> エラーハンドリングは「**どこで発生したかを伝え、適切な階層で対処する**」設計の問題です。例外（throw）・戻り値（Result型）・カスタムエラーオブジェクト ── どれをどこで使うか、TypeScript ならではの**型を活かしたエラー設計**を整理します。

## 1. エラーは「**どこで対処するか**」の問題

エラーには2種類:

### (1) 回復可能なエラー

ユーザ入力エラー、ネットワーク失敗、権限不足など。**呼び出し側で適切に対処**したい。

→ **戻り値（Result型）** で表現。

### (2) 回復不可能なエラー

プログラマのバグ、不変条件違反、メモリ不足など。**処理を中断して上位に通知**するしかない。

→ **例外（throw）** で表現。

---

## 2. 例外（throw）と戻り値（Result）の使い分け

### 例外を使うべき場面

```typescript
// プログラマのバグ
function divide(a: number, b: number): number {
  if (b === 0) throw new Error("zero division (programmer bug)");
  return a / b;
}

// 起動時の致命的エラー
const env = EnvSchema.parse(process.env); // 失敗で throw → fail fast

// アサーション
function assert(cond: boolean): asserts cond {
  if (!cond) throw new Error("invariant violated");
}
```

### Result を使うべき場面

```typescript
// ユーザ入力検証
function parseUser(s: string): Result<User, "invalid_format" | "missing_field"> { ... }

// ネットワーク
async function fetchUser(id: string): Promise<Result<User, "not_found" | "network">> { ... }

// 権限チェック
function canEdit(user: User, post: Post): Result<true, "not_owner" | "locked"> { ... }
```

→ **「対処したい」失敗 = Result**、**「ありえない」失敗 = throw**。

詳しくは [[02-結果型Result_Either]]。

## 3. `Error` クラスの基本

```typescript
const e = new Error("oops");
e.message;  // "oops"
e.stack;    // スタックトレース
e.name;     // "Error"
```

### 標準のサブクラス

| クラス | 用途 |
|---|---|
| `Error` | 一般的なエラー |
| `TypeError` | 型の誤り |
| `RangeError` | 範囲外 |
| `SyntaxError` | 構文エラー |
| `ReferenceError` | 未定義変数 |
| `URIError` | URI 関数の失敗 |

→ 普段は `Error` で十分。**JavaScriptランタイムが投げる**特殊系として知っておく。

## 4. カスタムエラークラス

エラーの**種類を区別**したいなら、`Error` を継承:

```typescript
class NotFoundError extends Error {
  constructor(message: string) {
    super(message);
    this.name = "NotFoundError";
  }
}

class UnauthorizedError extends Error {
  constructor(message: string) {
    super(message);
    this.name = "UnauthorizedError";
  }
}

try {
  // ...
} catch (e) {
  if (e instanceof NotFoundError) {
    // 404 表示
  } else if (e instanceof UnauthorizedError) {
    // ログイン画面へ
  } else {
    // 予期しないエラー
  }
}
```

### コンテキストデータを持たせる

```typescript
class ValidationError extends Error {
  constructor(
    message: string,
    readonly fields: Record<string, string[]>
  ) {
    super(message);
    this.name = "ValidationError";
  }
}

throw new ValidationError("invalid form", {
  email: ["不正なメールアドレス"],
});
```

→ `instanceof` で絞り込んで`fields` が安全に使える。

### 注意: `extends Error` の TypeScript 罠

古い TypeScript では `target: ES5` で `Error` を継承すると `instanceof` が効かないことがある:

```typescript
class MyError extends Error {}
const e = new MyError();
e instanceof MyError; // false （ES5 ターゲットで起きうる）
```

→ 対策:

```typescript
class MyError extends Error {
  constructor(message: string) {
    super(message);
    Object.setPrototypeOf(this, MyError.prototype);
  }
}
```

または `target: ES2015+` にする。**モダン環境では問題ない**。

## 5. `catch (err)` の `err` は `unknown`

`useUnknownInCatchVariables: true`（`strict: true` の一部）で `err` の型は `unknown`:

```typescript
try {
  // ...
} catch (err) {
  err.message; // ❌ unknown
  if (err instanceof Error) {
    err.message; // ✅
  }
}
```

→ **`Error` インスタンスとは限らない**前提の安全設計。

### ヘルパで読みやすく

```typescript
function getErrorMessage(err: unknown): string {
  if (err instanceof Error) return err.message;
  if (typeof err === "string") return err;
  return JSON.stringify(err);
}

try { ... } catch (err) {
  console.error(getErrorMessage(err));
}
```

## 6. エラー階層の設計

### ドメイン別階層

```typescript
abstract class AppError extends Error {
  abstract readonly code: string;
}

class NotFoundError extends AppError {
  code = "NOT_FOUND";
}

class ValidationError extends AppError {
  code = "VALIDATION";
  constructor(message: string, readonly fields: Record<string, string[]>) {
    super(message);
  }
}

class NetworkError extends AppError {
  code = "NETWORK";
}
```

→ **全アプリエラーが `AppError` 経由**になる。`code` で区別可能。

### 利用側

```typescript
try {
  await doStuff();
} catch (err) {
  if (err instanceof AppError) {
    return handleAppError(err);
  }
  throw err; // 未知のエラーは再スロー
}
```

## 7. 例外と Result のハイブリッド

「**回復可能 = Result、不可能 = throw**」を使い分ける:

```typescript
// ドメインロジック
async function loadUser(id: string): Promise<Result<User, "not_found">> {
  try {
    const data = await db.users.findById(id);
    if (!data) return err("not_found");
    return ok(UserSchema.parse(data));
  } catch (e) {
    // DB接続エラーなどはバグ扱いで throw
    throw new InternalError("DB error", { cause: e });
  }
}

// 利用側
const r = await loadUser(id);
if (!r.ok) {
  return showNotFound();
}
processUser(r.value);
```

→ ユーザ向けの「想定された失敗」は Result、システム的な「想定外の失敗」は throw。

---

## 8. `cause` プロパティ（ES2022）

エラーの**原因チェーン**を作れる:

```typescript
try {
  await doSomething();
} catch (e) {
  throw new Error("higher level error", { cause: e });
}

try {
  // ...
} catch (e) {
  console.error(e);            // higher level error
  console.error(e.cause);      // 元の error
}
```

→ エラーラッピング時に**根本原因を失わない**。

## 9. グローバルエラーハンドリング

### Node.js

```typescript
process.on("uncaughtException", err => {
  console.error("uncaught", err);
  process.exit(1);
});

process.on("unhandledRejection", reason => {
  console.error("unhandled rejection", reason);
});
```

→ どこでも catch されないエラーを最終的に拾う。

### ブラウザ

```typescript
window.addEventListener("error", e => { ... });
window.addEventListener("unhandledrejection", e => { ... });
```

### React

```typescript
class ErrorBoundary extends React.Component {
  componentDidCatch(error, info) { ... }
  render() { ... }
}
```

→ コンポーネントツリー内のエラーをキャッチ。

## 10. ログとエラー報告

エラーが起きたら:

1. **ログに記録**（コンテキスト含めて）
2. **監視ツールに送信**（Sentry, DataDog など）
3. **ユーザに適切なメッセージ**

```typescript
import * as Sentry from "@sentry/node";

try {
  await doStuff();
} catch (e) {
  Sentry.captureException(e, {
    extra: { userId, action: "doStuff" },
  });
  throw new UserVisibleError("予期しないエラーが発生しました");
}
```

→ 「**機械向けの詳細**」と「**人間向けのメッセージ**」を区別。

## 11. エラー設計のチェックリスト

新しいエラーケースを書くとき:

- [ ] **回復可能か不可能か** を判断（Result or throw）
- [ ] **エラーの種類**を型で表現（リテラルユニオン or カスタムクラス）
- [ ] **対処方法**が利用側で分かるように
- [ ] **コンテキストデータ**を含める（どのフィールドが失敗したか等）
- [ ] **ユーザ向けメッセージ**と**ログ用メッセージ**を区別
- [ ] **再試行可能か**をエラーに含める

## 12. ベストプラクティス

### (1) **エラーは具体的な情報を持たせる**

```typescript
// ❌ 抽象的
throw new Error("error");

// ✅ 具体的
throw new ValidationError("invalid email format", {
  email: ["不正な形式"],
});
```

### (2) **`Error` を必ずスローする**

```typescript
// ❌
throw "something wrong";

// ✅
throw new Error("something wrong");
```

文字列を throw すると `catch` で `instanceof Error` が効かない。

### (3) **`cause` で原因チェーンを残す**

```typescript
catch (e) {
  throw new BusinessError("高レベルの失敗", { cause: e });
}
```

### (4) **境界（API入口・出口）でエラーをマップ**

```typescript
async function apiHandler(req, res) {
  try {
    const result = await businessLogic();
    res.json(result);
  } catch (e) {
    if (e instanceof ValidationError) return res.status(400).json({ ... });
    if (e instanceof NotFoundError) return res.status(404).json({ ... });
    res.status(500).json({ error: "internal" });
  }
}
```

### (5) **「絶対起きない」も書いておく**

```typescript
function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return ...;
    case "square": return ...;
    default: return assertNever(s); // 「ここに来たらバグ」
  }
}
```

[[02-判別可能ユニオン]] の網羅性チェック。

### (6) **エラーメッセージは英語で書く（チーム規約次第）**

ログを国際チームで読むなら英語、日本語チームなら日本語でも。**統一**が大事。

## 13. アンチパターン

### (1) **`catch` で握りつぶす**

```typescript
try { ... } catch {} // ❌ エラーが消える
```

### (2) **すべてを `try/catch` で囲む**

```typescript
try {
  ... // 100行
} catch (e) { ... }
```

→ 細かく分割。

### (3) **エラーの型を `any` で受ける**

```typescript
catch (e: any) { e.message } // ❌
```

→ `unknown` で受けて型ガード。

### (4) **`Error` を `string` で投げる**

```typescript
throw "fail"; // ❌
```

### (5) **バリデーション結果と例外を混ぜる**

```typescript
function validate(data: unknown): User {
  if (!isUser(data)) throw new ValidationError(...);
  return data;
}
```

→ 用途次第。バリデーションは Result の方が呼び出し側に優しいことが多い。

### (6) **`Error` を継承せず `Error` ライクなオブジェクトを使う**

```typescript
throw { code: 404, message: "not found" }; // ❌
```

→ `instanceof Error` が効かず、stack trace もない。

---

## 14. まとめ

- **回復可能 = Result**、**不可能 = throw** で使い分け
- **カスタムエラークラス**で種類を区別（`instanceof` で絞り込み）
- `catch (err)` の `err` は **`unknown`**（`useUnknownInCatchVariables`）
- ES2022 の **`cause`** で原因チェーンを保持
- **境界でエラーをマップ**（API ハンドラなど）
- **網羅性チェック**で「絶対起きない」をコンパイラに任せる
- ログ・監視・ユーザメッセージを**分離**

> エラー設計は「**どこで対処するかを型で示す**」こと。Result型と例外を使い分け、カスタムエラーで種類を区別する ── このシンプルなルールで、エラーハンドリングは劇的に整います。
