# バリデーション（Zod 等）と型の同期

> 「**型と実行時バリデーションを別々に書く**」と必ず食い違いが生まれます。スキーマから型を導出する設計（**`z.infer`** / **`Type.Static`** など）にすると、**スキーマ1つ書けば型もバリデータも揃う**。これが現代TSの実務パターンです。

## 1. 型と検証の二重管理問題

### 別々に書くと…

```typescript
// 型定義
type User = {
  id: string;
  email: string;
  age: number;
};

// バリデータ（手書き）
function isUser(v: unknown): v is User {
  if (typeof v !== "object" || v === null) return false;
  const o = v as any;
  return (
    typeof o.id === "string" &&
    typeof o.email === "string" &&
    typeof o.age === "number"
  );
}
```

→ `User` にフィールドを追加したら、**`isUser` も更新**しないとズレる。**人間が忘れる**。

### スキーマから型を導出すれば

```typescript
import { z } from "zod";

const UserSchema = z.object({
  id: z.string(),
  email: z.string().email(),
  age: z.number().int().nonnegative(),
});

type User = z.infer<typeof UserSchema>;
// { id: string; email: string; age: number }
```

→ **スキーマ1か所**に書けば、型もバリデータも揃う。**ずれない**。

## 2. Zod の基本

### インストール

```bash
npm install zod
```

### スキーマの定義

```typescript
import { z } from "zod";

const StringSchema = z.string();
const NumberSchema = z.number();
const BoolSchema = z.boolean();
const DateSchema = z.date();
const NullSchema = z.null();
const UndefinedSchema = z.undefined();
```

### オブジェクト

```typescript
const UserSchema = z.object({
  id: z.string(),
  name: z.string(),
});
```

### 配列・タプル

```typescript
const StringsSchema = z.array(z.string());      // string[]
const TupleSchema = z.tuple([z.string(), z.number()]); // [string, number]
```

### ユニオン・判別ユニオン

```typescript
const Status = z.union([z.literal("ok"), z.literal("ng")]);
// z.enum(["ok", "ng"]) でも書ける

const Action = z.discriminatedUnion("type", [
  z.object({ type: z.literal("ADD"), value: z.number() }),
  z.object({ type: z.literal("REMOVE"), id: z.string() }),
]);
```

### Optional / Nullable

```typescript
const Schema = z.object({
  email: z.string().email().optional(),    // string | undefined
  middleName: z.string().nullable(),         // string | null
  bio: z.string().nullish(),                 // string | null | undefined
});
```

### Default

```typescript
const Schema = z.object({
  retries: z.number().default(3),
});
// 入力に retries がなくても 3 が入る
```

### 制約

```typescript
z.string().min(1).max(100);
z.string().email();
z.string().url();
z.string().regex(/^[a-z]+$/);
z.string().uuid();
z.number().positive();
z.number().int();
z.number().min(0).max(100);
```

## 3. 型の導出: `z.infer`

スキーマから型を取り出す:

```typescript
const UserSchema = z.object({ id: z.string(), name: z.string() });
type User = z.infer<typeof UserSchema>;
// { id: string; name: string }
```

→ **スキーマと型が一致する保証**。

---

## 4. パースとセーフパース

### `parse` ── 失敗時に throw

```typescript
const user = UserSchema.parse(data);
// 成功: User
// 失敗: ZodError を throw
```

### `safeParse` ── Result 型を返す

```typescript
const result = UserSchema.safeParse(data);
if (result.success) {
  result.data; // User
} else {
  result.error; // ZodError
}
```

→ **エラーハンドリングを強制**したいなら `safeParse`。

### `parseAsync` ── 非同期検証

```typescript
const user = await UserSchema.parseAsync(data);
```

非同期な `refine` を使う場合に必要。

---

## 5. 変換 (`transform`)

検証 + 変換を1つのスキーマで:

```typescript
const Schema = z.object({
  date: z.string().transform(s => new Date(s)),
  age: z.string().transform(s => parseInt(s, 10)),
});

type T = z.infer<typeof Schema>;
// { date: Date; age: number }
```

→ **入力は string、出力は Date** のような変換をスキーマレベルで定義。

### 入力型と出力型を区別: `z.input` / `z.output`

```typescript
const Schema = z.string().transform(s => parseInt(s));

type Input = z.input<typeof Schema>;   // string
type Output = z.output<typeof Schema>;  // number
type Inferred = z.infer<typeof Schema>; // number （出力と同じ）
```

→ API入力（string）と内部処理（number）の境界を明確にできる。

---

## 6. カスタム検証 (`refine`)

ビルトインで足りないルールを追加:

```typescript
const PasswordSchema = z.string().min(8).refine(
  s => /\d/.test(s),
  { message: "must contain a digit" }
);
```

### `superRefine` ── 複数エラーを生成

```typescript
const FormSchema = z.object({
  password: z.string(),
  confirmPassword: z.string(),
}).superRefine((data, ctx) => {
  if (data.password !== data.confirmPassword) {
    ctx.addIssue({
      code: "custom",
      message: "passwords don't match",
      path: ["confirmPassword"],
    });
  }
});
```

## 7. 構造の組み合わせ

### 拡張・部分適用

```typescript
const BaseUser = z.object({ id: z.string(), name: z.string() });

const FullUser = BaseUser.extend({ email: z.string() });
const PartialUser = BaseUser.partial();   // すべて optional
const NameOnly = BaseUser.pick({ name: true });
const WithoutId = BaseUser.omit({ id: true });
const StrictUser = BaseUser.strict();      // 余分なキーを禁止
```

→ `Pick` / `Omit` / `Partial` 相当の操作をスキーマレベルでも。

### マージ

```typescript
const A = z.object({ a: z.number() });
const B = z.object({ b: z.string() });
const Merged = A.merge(B); // { a: number; b: string }
```

## 8. エラー処理

### `ZodError` の構造

```typescript
const result = Schema.safeParse(data);
if (!result.success) {
  result.error.issues; // { path, message, code }[]
  result.error.format(); // ネストしたオブジェクト形式
  result.error.flatten(); // フィールド別エラー
}
```

### フォームでの使い方

```typescript
const result = LoginSchema.safeParse(formData);
if (!result.success) {
  const errors = result.error.flatten().fieldErrors;
  // { email?: string[]; password?: string[] }
  setFormErrors(errors);
}
```

## 9. APIクライアントでの典型パターン

```typescript
import { z } from "zod";

const UserSchema = z.object({
  id: z.string(),
  name: z.string(),
});

type User = z.infer<typeof UserSchema>;

async function fetchUser(id: string): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) throw new Error(`fetch failed: ${res.status}`);
  const data: unknown = await res.json();
  return UserSchema.parse(data); // 検証
}
```

→ `fetch().json()` の `any` を `unknown` 経由で受け、検証して `User` に。

### 一覧の検証

```typescript
const UsersSchema = z.array(UserSchema);

async function fetchUsers(): Promise<User[]> {
  const data: unknown = await (await fetch("/api/users")).json();
  return UsersSchema.parse(data);
}
```

## 10. 環境変数の検証

```typescript
import { z } from "zod";

const EnvSchema = z.object({
  PORT: z.coerce.number().int().positive().default(3000),
  DATABASE_URL: z.string().url(),
  API_KEY: z.string().min(20),
  LOG_LEVEL: z.enum(["debug", "info", "warn", "error"]).default("info"),
});

export const env = EnvSchema.parse(process.env);
// 型: { PORT: number; DATABASE_URL: string; API_KEY: string; LOG_LEVEL: ... }
```

→ **起動時に1回検証**。失敗したら起動を中断（fail fast）。

## 11. フォームバリデーション（React Hook Form など）

```typescript
import { z } from "zod";
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";

const Schema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
});

type FormData = z.infer<typeof Schema>;

function LoginForm() {
  const { register, handleSubmit, formState: { errors } } = useForm<FormData>({
    resolver: zodResolver(Schema),
  });

  return (
    <form onSubmit={handleSubmit(data => { ... })}>
      <input {...register("email")} />
      {errors.email && <span>{errors.email.message}</span>}
      ...
    </form>
  );
}
```

→ **スキーマ1つでフォームの型・検証が揃う**。

## 12. Zod 以外の選択肢

### Yup

`Zod` 以前の定番。React等のフォームでよく使われた。型推論は Zod ほど洗練されていない。

```typescript
import * as yup from "yup";
const schema = yup.object({ name: yup.string().required() });
```

### Valibot

軽量・高速な代替。Tree shakingしやすい。

```typescript
import * as v from "valibot";
const Schema = v.object({ name: v.string() });
```

→ **バンドルサイズ重視**ならValibot。

### TypeBox

JSON Schemaを直接生成。バックエンド（Fastify等）で使うならこちら。

```typescript
import { Type, Static } from "@sinclair/typebox";
const User = Type.Object({ name: Type.String() });
type User = Static<typeof User>;
```

### ArkType

新しめ、TypeScript 構文に近い記述。

```typescript
import { type } from "arktype";
const User = type({ name: "string" });
```

### io-ts

関数型寄り、fp-ts と組み合わせる派向け。

→ **新規プロジェクトはZodがデフォルト**。特殊要件があれば他を検討。

## 13. 「型 → スキーマ」 vs 「スキーマ → 型」

### スキーマ → 型（推奨）

```typescript
const Schema = z.object({ ... });
type T = z.infer<typeof Schema>;
```

→ **スキーマが正準**。型は導出。実行時保証あり。

### 型 → スキーマ（古い設計）

```typescript
type T = { ... };
const Schema = ... ; // 型に合わせて手書き
```

→ **二重管理**になる。古いプロジェクトで見るパターンだが、現代では非推奨。

---

## 14. パフォーマンスの注意

Zod は実行時に検証するため、**ホットパス（毎回呼ばれる場所）では注意**:

- 大きなオブジェクトを毎リクエスト検証 → やや遅い
- ネストが深いと比例して遅くなる

→ **境界で1回検証、内部では型のみ**を信頼する設計が大事。

### 並列処理

`Promise.all` で並列に検証することは可能（CPU負荷次第）。

## 15. ベストプラクティス

### (1) **スキーマと型は同居**

```typescript
// types/user.ts
export const UserSchema = z.object({ ... });
export type User = z.infer<typeof UserSchema>;
```

スキーマと型を**同じファイル**に置くと迷わない。

### (2) **境界で検証、内部では信頼**

```
外部 → [Schema.parse] → 内部型 → ロジック
```

検証は**1度だけ**。内部のループで毎回検証しない。

### (3) **`safeParse` をデフォルト**

`parse` は throw するので、エラーハンドリングが分散する。`safeParse` で結果をハンドリング。

### (4) **エラーメッセージはユーザに優しく**

```typescript
z.string().min(8, "パスワードは8文字以上必要です")
```

→ デフォルトの英語メッセージそのままだとUX悪い。

### (5) **大きなスキーマは分割**

```typescript
const AddressSchema = z.object({ ... });
const UserSchema = z.object({ ..., address: AddressSchema });
```

→ ネストしたスキーマは別途定義して合成。

### (6) **DTOとドメインモデルを分ける**

API境界の型（DTO）と内部のドメイン型を分け、変換層を持つ:

```typescript
// 受信スキーマ
const UserDTOSchema = z.object({ ... });
type UserDTO = z.infer<typeof UserDTOSchema>;

// 内部ドメイン
class User { ... }

// 変換
function toUser(dto: UserDTO): User { ... }
```

## 16. アンチパターン

### (1) 型と手書きバリデータが別々

```typescript
type User = { ... };
function isUser(v: unknown): v is User { ... }
```

→ Zodで一元化。

### (2) `parse` と `try/catch` で分散

```typescript
try {
  const user = Schema.parse(data);
  // ...
} catch { ... }
// 同じパターンが各所に
```

→ 共通の境界関数を作る。

### (3) スキーマを動的に組み立てすぎ

```typescript
let s = z.object({});
for (const f of fields) s = s.extend({ [f]: z.string() });
```

→ デバッグしにくく、型推論が効かないことも。可能なら静的に。

### (4) Zod を内部ロジックでも使う

```typescript
function process(user: User) {
  UserSchema.parse(user); // 内部でも検証
  // ...
}
```

→ 境界以外では不要。**型を信用する**。

### (5) `as` でZodを回避

```typescript
const user = data as User;
```

→ Zodの意味がない。

---

## 17. まとめ

- **スキーマと型の二重管理**が問題 → **`z.infer` で導出**
- **Zod** が現代TSのデフォルト（軽量なら Valibot、JSON Schema なら TypeBox）
- `parse` (throw) / `safeParse` (Result) を使い分け
- `transform` で**入力と出力の型を区別**
- 環境変数・設定・APIレスポンスを**起動時/境界で1回検証**
- **境界で検証、内部では型のみ信頼**

> 「**スキーマ = 型 + バリデータ**」 ── これが現代TSの実務原則。Zodで境界をしっかり守るだけで、外部データ起因のバグはほぼ消えます。
