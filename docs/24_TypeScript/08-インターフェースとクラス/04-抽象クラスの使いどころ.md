# 抽象クラス（使いどころ）

> 抽象クラス（`abstract class`）は「**共通の実装は持つが、一部のメソッドはサブクラスに任せる**」ためのテンプレート機能。便利ですが、**実務での出番は限定的**で、多くの場合は `interface` + 関数 + 合成（composition）で代替できます。本ファイルでは「**何ができるか**」と「**いつ使うべきか**」を整理します。

## 1. 抽象クラスとは

`abstract` キーワードを付けたクラス。**直接インスタンス化できない**。

```typescript
abstract class Shape {
  abstract area(): number; // 実装なし、サブクラスで実装必須

  describe(): string {
    return `This shape has area ${this.area()}`; // 実装あり
  }
}

new Shape(); // ❌ Cannot create an instance of an abstract class.

class Circle extends Shape {
  constructor(readonly radius: number) { super(); }
  area(): number {
    return Math.PI * this.radius ** 2;
  }
}

const c = new Circle(5);
console.log(c.describe()); // ✅
```

### 構文の特徴

- `abstract class Foo {}` → クラス自体が抽象
- `abstract method(): T;` → 実装なし。**サブクラスで必ず実装**
- `abstract` メソッドは **`abstract class` の中だけ**で使える

---

## 2. `interface` との違い

| | `interface` | `abstract class` |
|---|---|---|
| 実装を持てる | ❌（メソッドの宣言のみ） | ✅（一部実装、一部抽象） |
| インスタンス化 | できない | できない |
| 継承の数 | 複数 implements 可 | 単一 extends のみ |
| プロパティ初期化 | できない | できる |
| アクセス修飾子 | なし | `private` `protected` `public` |
| ランタイム実体 | なし（消える） | あり（クラス） |

### 単純な比較

```typescript
// interface: 形だけ
interface IShape {
  area(): number;
}

// abstract class: 形 + 共通実装
abstract class AbstractShape {
  abstract area(): number;
  describe(): string { return `area: ${this.area()}`; }
}
```

→ **共有したい実装がある**なら `abstract class`、**形だけ揃えたい**なら `interface`。

## 3. 抽象クラスの使い所

### (1) Template Method パターン

「**全体の流れは同じ、一部だけ差し替えたい**」場合の典型。

```typescript
abstract class Pipeline {
  run(input: string): string {
    const cleaned = this.clean(input);
    const processed = this.process(cleaned);
    return this.format(processed);
  }

  protected clean(s: string): string {
    return s.trim();
  }

  protected abstract process(s: string): string; // サブクラスで実装

  protected format(s: string): string {
    return `[result] ${s}`;
  }
}

class Uppercase extends Pipeline {
  protected process(s: string): string {
    return s.toUpperCase();
  }
}

new Uppercase().run("  hello  "); // "[result] HELLO"
```

→ `run` の流れは固定、`process` だけサブクラスで自由に。

### (2) 部分実装の共通化

「全部のサブクラスで同じコードを書きたくない」場合。

```typescript
abstract class Animal {
  constructor(public name: string) {}

  greet(): string {
    return `Hi, I'm ${this.name}.`;
  }

  abstract speak(): string;
}

class Dog extends Animal {
  speak() { return "Woof!"; }
}

class Cat extends Animal {
  speak() { return "Meow!"; }
}
```

→ `greet` は共通、`speak` だけ実装。

### (3) フレームワークの拡張ポイント

「**ライブラリが提供するベースクラスを継承して使う**」場合。

```typescript
// Angular のコンポーネント基底クラス（例）
abstract class BaseComponent {
  abstract render(): string;
  destroy() { /* デフォルト実装 */ }
}

class MyComponent extends BaseComponent {
  render() { return "<div>...</div>"; }
}
```

ただし、**現代のフレームワークは関数型寄り**（React Hooksなど）になっており、抽象クラスを使う場面は減少傾向。

## 4. 抽象クラスを使わない代替

### (1) 関数 + 高階関数

```typescript
function pipeline(input: string, process: (s: string) => string): string {
  return `[result] ${process(input.trim())}`;
}

pipeline("  hello  ", s => s.toUpperCase());
```

→ **継承不要**。シンプル。

### (2) `interface` + composition

```typescript
interface Processor {
  process(s: string): string;
}

class Pipeline {
  constructor(private readonly processor: Processor) {}
  run(input: string): string {
    return `[result] ${this.processor.process(input.trim())}`;
  }
}

class UppercaseProcessor implements Processor {
  process(s: string): string { return s.toUpperCase(); }
}

new Pipeline(new UppercaseProcessor()).run("  hello  ");
```

→ **継承より合成**（composition over inheritance）。差し替え・テストしやすい。

### (3) ストラテジーパターン

```typescript
type Strategy = (s: string) => string;

const upperStrategy: Strategy = s => s.toUpperCase();
const lowerStrategy: Strategy = s => s.toLowerCase();

function pipeline(input: string, strategy: Strategy): string {
  return `[result] ${strategy(input.trim())}`;
}
```

→ 関数型で同じことが軽量に書ける。

## 5. 「継承より合成」── なぜ抽象クラスは出番が減ったか

### 継承の問題

- **強い結合**: 親クラスを変えると子全部に影響
- **多重継承不可**: 1つしか継承できない
- **テストしにくい**: モック化が複雑
- **柔軟性が低い**: 後から差し替えにくい

### 合成の利点

- **疎結合**: 部品を組み合わせる
- **複数の機能を組み合わせ可能**
- **モック化が簡単**: インターフェース型でDI
- **拡張に強い**: 部品を差し替え

→ 現代のTSコードでは**抽象クラスより合成**が好まれる。

---

## 6. それでも抽象クラスを使うべき場面

### (1) サブクラスが**3つ以上**あって**実装の80%が共通**

→ 共通実装を1か所に置くメリットが大きい。

### (2) **既存のフレームワーク**が抽象クラスを要求する

→ 従う。

### (3) **状態を持つ部品**で、複数バリエーションが**同じインターフェース + 同じ初期化**

→ コンストラクタや初期化ロジックを共有できる。

### (4) **チームがOOP前提のコードベース**

→ 一貫性のため。

### (5) Template Method がきれいにハマる場面

→ 流れを固定して一部だけ変える、というパターンが本当にあるとき。

## 7. 抽象クラスの構文の詳細

### 抽象プロパティ

```typescript
abstract class Animal {
  abstract name: string; // フィールドも抽象に
}

class Dog extends Animal {
  name = "Pochi";
}
```

### 抽象 getter / setter

```typescript
abstract class Shape {
  abstract get area(): number;
}

class Circle extends Shape {
  constructor(readonly radius: number) { super(); }
  get area(): number { return Math.PI * this.radius ** 2; }
}
```

### 抽象クラスにコンストラクタ

```typescript
abstract class Animal {
  constructor(public readonly name: string) {}
  abstract speak(): string;
}

class Dog extends Animal {
  constructor(name: string, public breed: string) {
    super(name); // 親のconstructorを呼ぶ
  }
  speak() { return "Woof"; }
}
```

子クラスは `super()` を呼ぶ必要がある（フィールド初期化のため）。

## 8. 抽象クラスの落とし穴

### (1) 継承階層が深くなると地獄

```typescript
abstract class A { ... }
abstract class B extends A { ... }
abstract class C extends B { ... }
class D extends C { ... } // どこに何があるか分からない
```

→ **3階層以上の継承は避ける**。合成への転換を検討。

### (2) `super` の呼び忘れ

```typescript
class Dog extends Animal {
  constructor(name: string) {
    // super(name) を忘れると…
    this.name = name; // ❌
  }
}
```

`super()` を呼ばないとフィールド初期化前に `this` を使えない。

### (3) 抽象メソッドのシグネチャ違反

```typescript
abstract class Foo {
  abstract method(x: number): string;
}

class Bar extends Foo {
  method(x: string): string { return x; } // ❌ 引数型が違う
}
```

→ シグネチャは厳密に揃える。

### (4) 「`abstract` だから安全」と思い込む

```typescript
abstract class Shape {
  abstract area(): number;
  perimeter(): number {
    return this.area() * 4; // ❌ 円や三角では成り立たない
  }
}
```

→ 共通実装が**全サブクラスで意味を持つか**を慎重に。

### (5) 抽象クラスを `interface` のように使う

```typescript
abstract class IFoo {
  abstract a(): void;
  abstract b(): void;
} // 全部 abstract → interface で十分
```

→ 全メソッドが abstract なら **`interface`** にする。

## 9. クラスを使う／使わない判断

抽象クラスに限らず、TSでクラスを使うべきかの判断軸:

| 状況 | 推奨 |
|---|---|
| 状態 + 振る舞いが密結合 | クラス |
| 不変な値オブジェクト | クラス（`readonly`）or `type` |
| 関数 + 型で表現できる | 関数 |
| 多態が必要（同じ形・違う実装） | クラス + interface |
| Reactコンポーネント | 関数（フック化） |
| ドメインサービス | クラス（DI先） |
| ユーティリティ関数群 | モジュール（`export function`） |

## 10. 実例: いつ抽象クラスを選ぶか

### 例1: 通知サービス（合成が向いている）

```typescript
// ❌ 抽象クラス（過剰）
abstract class Notifier {
  abstract send(msg: string): Promise<void>;
}
class EmailNotifier extends Notifier { ... }
class SmsNotifier extends Notifier { ... }

// ✅ interface + 合成
interface Notifier {
  send(msg: string): Promise<void>;
}
class EmailNotifier implements Notifier { ... }
class SmsNotifier implements Notifier { ... }

class NotificationService {
  constructor(private notifier: Notifier) {}
}
```

→ 共通実装がない。`interface` で十分。

### 例2: HTTPクライアント（abstract が活きる）

```typescript
abstract class HttpClient {
  protected abstract send(req: Request): Promise<Response>;

  async get<T>(url: string): Promise<T> {
    const res = await this.send({ method: "GET", url });
    return res.json();
  }

  async post<T>(url: string, body: unknown): Promise<T> {
    const res = await this.send({ method: "POST", url, body });
    return res.json();
  }
}

class FetchClient extends HttpClient {
  protected async send(req: Request) { return fetch(req.url, { ... }); }
}
class MockClient extends HttpClient {
  protected async send(req: Request) { return new Response("..."); }
}
```

→ `get` / `post` の共通実装を抽象クラスに集約、`send` だけサブクラスで実装。**Template Method がハマる**例。

## 11. まとめ

- **`abstract class`**: 一部実装 + 一部抽象、**インスタンス化不可**
- **使い所**: Template Method、共通実装の集約、フレームワーク拡張
- **使わない場面**: シンプルな多態（`interface` で十分）/ 全部抽象（`interface` で十分）/ 関数で書ける場合
- **継承より合成**（composition over inheritance）が現代の主流
- 注意: 継承階層を深くしない / `super()` を忘れない / 全部 abstract なら `interface` に

> 抽象クラスは「**Template Method を表現する道具**」。「共通の流れがあって、一部だけ差し替える」場面以外では、**`interface` + composition + 関数**の方がシンプルで強力です。クラスを書く前に、本当に必要か一度立ち止まる癖を。
