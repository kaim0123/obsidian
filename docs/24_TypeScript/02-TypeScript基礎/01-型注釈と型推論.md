# 型注釈と型推論

> TypeScriptで最初に身につけるべきは「型を**書く**こと」ではなく「型を**任せる**こと」。型推論を信頼し、必要なところだけ型注釈を書く ── これが読みやすいTypeScriptの第一歩です。

## 1. 型注釈（Type Annotation）とは

**型注釈**とは、変数・引数・戻り値などに「この値はこの型である」と明示的に書くことです。

```typescript
let age: number = 30;
let name: string = "Alice";
let isAdmin: boolean = false;

function greet(user: string): string {
  return `Hello, ${user}`;
}
```

`変数名: 型` の形式で書きます。これは**コンパイラへの宣言**であり、実行時のJavaScriptには残りません（コンパイル時に消えます）。

### 関数の型注釈

引数と戻り値の両方に書けます。

```typescript
function add(a: number, b: number): number {
  return a + b;
}
```

引数の型は基本的に**書く**、戻り値の型は**ケースバイケース**（後述）。

---

## 2. 型推論（Type Inference）とは

TypeScriptは**書かれた値から型を自動で推測**します。これが**型推論**です。

```typescript
let age = 30;          // ageは number と推論される
let name = "Alice";    // nameは string と推論される
const PI = 3.14;       // PIは 3.14（リテラル型）と推論される
```

`age` に文字列を入れようとするとエラーになります。

```typescript
age = "thirty"; // エラー: Type 'string' is not assignable to type 'number'.
```

### 関数の戻り値も推論される

```typescript
function double(x: number) {
  return x * 2; // 戻り値は number と推論
}

const result = double(5); // result も number
```

戻り値の型注釈を書かなくても、`return` 文から自動で決まります。

---

## 3. `let` と `const` で推論結果が変わる

これは初心者が最初に驚くところです。

```typescript
let s = "hello";     // 型: string（広い型 = 再代入されうるから）
const c = "hello";   // 型: "hello"（リテラル型 = 変わらないから）
```

- `let` は再代入される可能性があるので、TypeScriptは**広い型**（`string`）に推論
- `const` は再代入できないので、**そのリテラル値そのもの**を型に推論

この挙動を **widening（広げ）** と呼びます。詳しくは [[05-リテラル型とas-const]] で扱います。

## 4. 型注釈を「書くべき場面」と「書かないべき場面」

### 書くべき場面

#### (1) 関数の引数

引数は呼び出し側が何を渡すか分からないため、**必ず書く**。

```typescript
// ❌ 引数の型がany（暗黙のany）になりエラー
function greet(user) {
  return `Hello, ${user}`;
}

// ✅
function greet(user: string) {
  return `Hello, ${user}`;
}
```

`tsconfig.json` で `"noImplicitAny": true`（または `"strict": true`）にしておけば、引数の型注釈漏れは自動で警告されます。

#### (2) 公開API（exportされる関数）の戻り値

ライブラリのように外部から使われる関数は、戻り値を**明示**しておくと、

- 内部実装を変えても戻り値型が意図せず変わらない（インターフェースが安定）
- 型エラーがその関数の中で止まる（呼び出し側まで波及しない）

```typescript
// ✅ 戻り値を明示
export function fetchUser(id: string): Promise<User> {
  return fetch(`/api/users/${id}`).then(r => r.json());
}
```

#### (3) 値が後から代入される変数

宣言時に値がない場合、推論ができないので注釈が必要です。

```typescript
let user: User;
if (loggedIn) {
  user = getCurrentUser();
} else {
  user = guestUser();
}
```

#### (4) 推論結果が広すぎる場合

```typescript
const status = "loading"; // 推論: "loading"（リテラル型）
let nextStatus = status;  // 推論: string（広がる）

// "loading" | "success" | "error" に絞りたい場合
let nextStatus: "loading" | "success" | "error" = status;
```

---

### 書かない方がよい場面

#### (1) 初期値から自明な変数

```typescript
// ❌ 冗長
const age: number = 30;
const items: string[] = ["a", "b"];

// ✅ 推論で十分
const age = 30;
const items = ["a", "b"];
```

書くと**ノイズになり、変更時の修正箇所が増える**だけです。

#### (2) 推論可能な戻り値（小さなprivate関数）

```typescript
// ❌ 冗長
function double(x: number): number {
  return x * 2;
}

// ✅ 推論に任せる
function double(x: number) {
  return x * 2;
}
```

ただし「公開API」「実装が長く戻り値が読みにくい関数」は書く方がよい（前述）。

#### (3) ジェネリクスの型引数

呼び出し側で型推論されるなら、明示しなくてOK。

```typescript
const arr = [1, 2, 3];
arr.map<string>(n => n.toString()); // ❌ 不要
arr.map(n => n.toString());          // ✅ 推論される
```

## 5. 型推論が効かないケース

### (1) 引数

前述の通り、引数は推論できません。必ず注釈を。

### (2) 空配列の初期化

```typescript
const items = []; // 型: any[]（広すぎ・危険）

// ✅ 注釈で補う
const items: string[] = [];
```

`noImplicitAny` を有効にしていても、空配列の `any[]` は警告対象外なので注意。

### (3) コールバックの引数（場合による）

```typescript
const arr: number[] = [1, 2, 3];
arr.forEach(n => console.log(n.toFixed())); // n は number と推論される

// 型情報のない外部APIだと推論が効かないことも
someLib.on("data", (data) => { /* dataの型はany */ });
```

## 6. 「契約 vs ヒント」の考え方

型注釈と型推論を**役割で使い分ける**と判断が楽になります。

| 観点 | 型注釈（書く） | 型推論（任せる） |
|---|---|---|
| 役割 | **契約**（Contract） | **ヒント**（Inference） |
| 場所 | 関数引数・戻り値・公開API | ローカル変数・短い関数 |
| 目的 | 外部とのインターフェースを固定 | 書く量を減らし可読性を上げる |
| 変更時 | 注釈と実装の両方を意識 | 実装変更で型も自動追従 |

> **覚え方**: 「**境界には書く、内側は任せる**」

境界 = 関数の入口・出口、モジュールのexport、API応答  
内側 = 関数内のローカル変数、小さなコールバック

## 7. よくある間違い

### (1) 推論されているのに毎回書いてしまう

```typescript
// ❌ 全部冗長
const message: string = "hello";
const count: number = 0;
const isReady: boolean = true;

// ✅ 推論に任せる
const message = "hello";
const count = 0;
const isReady = true;
```

### (2) 型注釈と実際の値が食い違っているのに気づかない

```typescript
// 型は number[] と書いたが…
const ids: number[] = [1, 2, "3"]; // エラー: '"3"' is not assignable to type 'number'.
```

エディタが赤線で教えてくれるので、**保存時に必ず確認**する習慣を。

### (3) 戻り値の推論を信じすぎる

```typescript
// 一見良さそうだが、実装ミスで戻り値が undefined になっても気付けない
function findUser(id: string) {
  if (id === "admin") return { id, role: "admin" };
  // 他のidは undefined を返す（戻り値型: { id: string; role: string } | undefined）
}
```

公開関数では戻り値を明示しておけば、**意図しない `| undefined`** がついた瞬間に気付けます。

```typescript
function findUser(id: string): { id: string; role: string } {
  if (id === "admin") return { id, role: "admin" };
  // エラー: undefinedを返すパスがある
}
```

---

## 8. まとめ

- **書く**: 関数の引数 / 公開APIの戻り値 / 後から代入する変数 / 推論が広すぎる場合
- **書かない**: 初期値から自明な変数 / 短い関数の戻り値 / ジェネリクスで推論可能な箇所
- **判断軸**: 「境界には書く、内側は任せる」
- **`strict: true`**（特に `noImplicitAny`）を有効にすれば、書き忘れは自動で教えてくれる

型注釈は「書けば書くほど安全」ではありません。**必要な場所に必要な分だけ**書くのが、TypeScript上達の最初のコツです。
