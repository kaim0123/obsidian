# TypeScript の型

このジャンルでは、**`fetch` のレスポンスを `response.json()` で受け取るとき**に、**型を付けて安全に扱う**ことが中心です。

---

## 指摘: `response.json()` の戻り値に型がない

### 原文（レビュー・再構成）

> **`response.json()` の戻り値に型がない**  
> デフォルトでは `Promise<any>` に近く、`data.success` や `data.message` が**型安全ではない**。  
> Web3Forms の応答に合わせた**判別可能なユニオン**型を定義してほしい。

### 言葉の意味

| 用語 | 意味 |
|------|------|
| **`any`** | TypeScript で「型チェックをほぼ諦める」扱い。プロパティの打ち間違いに**コンパイル時に気づきにくい**。 |
| **型安全** | 「このオブジェクトにはこのプロパティがある」と**エディタとコンパイラが保証**してくれる状態。 |
| **判別可能なユニオン（discriminated union）** | `success: true` と `success: false` のように、**共通のキー（タグ）で形が切り替わる**型。`if (data.success)` のあとで**利用できるプロパティが絞り込まれる**。 |

### ユニオン型（`|`）とは何か

**ユニオン型**は、`A | B` と書いて「**この値は型 A であるか、型 B であるかのどちらか**」と宣言する仕組みです。`ContactForm` の `Web3FormsResponse` は、

- `{ success: true }`（成功時の形）**または**
- `{ success: false; message?: string }`（失敗時の形）

の**どちらか一方**を表すユニオンです。

コンパイル時点では「まだどちらのオブジェクトか分からない」ため、**両方に共通して存在するプロパティ**（ここでは `success`）だけを無条件に触るのが安全です。存在しないかもしれない `message` に、絞り込みなしでアクセスすると型エラーになることがあります。これは **`any` のように何にでもアクセスできる**のとは対照的で、**打ち間違いや取り違えをコンパイルで止めやすい**という利点があります。

**判別可能なユニオン**は、そのユニオンの各メンバーが**同じ名前のタグ**（例: `success`）を持ち、値が `true` / `false` のように**リテラル型で食い違う**書き方です。`if (data.success)` のような分岐のあと、TypeScript が「今は成功側（または失敗側）のメンバーだ」と**型を自動で絞り込む（narrowing）**ので、分岐の中ではその側にだけあるプロパティを安心して扱えます。

### なぜそうするか

- 外部 API の返却は **仕様として型に書いておく**と、**仕様のメモ**にもなり、リファクタ時も壊れにくい。
- `success` が `false` のときだけ `message` がある、など **分岐ごとの形**を表現できる。

### 実際どう直すか

**1. コンポーネントの外などに型を定義**

```typescript
type Web3FormsResponse =
  | { success: true }
  | { success: false; message?: string };
```

**2. `json()` の結果に型を付ける**

```typescript
const data: Web3FormsResponse = await response.json();
```

**3. 分岐で型が効く例**

```typescript
if (data.success) {
  // ここでは data は { success: true } として扱われる
} else {
  // ここでは message にアクセスしうる、など
}
```

**補足:** 画面に出す**ユーザー向けの日本語**は、別途 [[01Programming/修正内容/レビュー解説/05-エラーとログ]] のように **HTTP ステータスから組み立てる**方針と組み合わせることが多いです（API の `message` をそのまま表示しない、という指摘とセット）。
