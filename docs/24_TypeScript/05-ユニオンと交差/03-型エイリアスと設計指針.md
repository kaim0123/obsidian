# 型エイリアスと設計指針（いつ `type` を切るか）

> 「型を**いつ切り出すか**」「**どう名付けるか**」 ── これは TypeScript 設計の中心的な判断です。インラインで書き続けると読みにくくなり、何でも切り出すと逆にコードを追いにくくなる。実務で迷わないための判断軸を整理します。

## 1. 型エイリアスとは

`type` キーワードで「型に名前を付ける」もの。

```typescript
type UserId = string;
type User = { id: UserId; name: string };
type Status = "loading" | "success" | "error";
```

`interface` と並んで型に名前を付ける2大手段。詳しい比較は [[interface vs type]]。

---

## 2. 型エイリアスを「**切り出すべき**」場面

### (1) 同じ型を**複数箇所で使う**とき

```typescript
// ❌ 重複してメンテが破綻する
function createUser(u: { id: string; name: string }) { ... }
function updateUser(u: { id: string; name: string }) { ... }
function deleteUser(u: { id: string; name: string }) { ... }

// ✅ 切り出す
type User = { id: string; name: string };
function createUser(u: User) { ... }
function updateUser(u: User) { ... }
function deleteUser(u: User) { ... }
```

「**3箇所以上で出てくる型は切り出す**」が一つの目安。

### (2) 名前があった方が**意図が伝わる**とき

```typescript
// ❌ 何の string か分からない
function send(to: string, subject: string, body: string) { ... }

// ✅ 名前で意図を伝える
type EmailAddress = string;
type Subject = string;
type Body = string;

function send(to: EmailAddress, subject: Subject, body: Body) { ... }
```

ただし、`string` のラッパーだけだと**型としては区別されない**（後述のbranded typesで対処可）。

### (3) **複雑な構造**を1か所にまとめたいとき

```typescript
// ❌ インラインで書くと読みにくい
function process(
  data: { items: { id: string; tags: { key: string; value: string }[] }[] }
) { ... }

// ✅ 段階的に切り出す
type Tag = { key: string; value: string };
type Item = { id: string; tags: Tag[] };
type Data = { items: Item[] };

function process(data: Data) { ... }
```

ネストが深いほど切り出すメリットが大きい。

### (4) **判別可能ユニオン**

```typescript
type Action =
  | { type: "ADD"; payload: number }
  | { type: "REMOVE"; id: string }
  | { type: "RESET" };
```

ユニオン型に名前を付けないとどこからも参照できない。**必ず切り出す**。

### (5) **公開API**で型を露出するとき

```typescript
// ライブラリ・モジュールのexport
export type CreateUserInput = { name: string; email: string };
export type CreateUserResult = { id: string; createdAt: Date };

export function createUser(input: CreateUserInput): Promise<CreateUserResult> { ... }
```

利用者が `import` して使えるようにする。

## 3. 型エイリアスを「**切り出さない方がよい**」場面

### (1) **1か所でしか使わない**簡単な型

```typescript
// ❌ 過剰
type Greeting = string;
function greet(): Greeting { return "hello"; }

// ✅ そのまま
function greet(): string { return "hello"; }
```

### (2) 関数の戻り値が**1回しか参照されない**

```typescript
// ❌
type FormData = { name: string; email: string };
function getForm(): FormData { ... }

// ✅ 1回しか使わないならインラインでもOK
function getForm(): { name: string; email: string } { ... }
```

ただし「**今後使い回しそう**」なら切り出してもOK。判断は文脈次第。

### (3) 推論で十分なローカル変数

```typescript
// ❌
type Item = { name: string; count: number };
const item: Item = { name: "apple", count: 3 };

// ✅
const item = { name: "apple", count: 3 };
```

ローカル変数は型推論に任せる。

### (4) **1か所限り**の `Pick` / `Omit`

```typescript
// ❌ あえて切り出さなくても
type Without = Omit<User, "password">;
function publish(user: Without) { ... }

// ✅ インラインでもOK
function publish(user: Omit<User, "password">) { ... }
```

## 4. 名付けの原則

### (1) **「何か」を表す名詞**

```typescript
type User = ...;
type Order = ...;
type ApiResponse<T> = ...;
```

`Userable`, `OrderInfo` のような曖昧な名前は避ける。

### (2) **役割を含めた名詞**

```typescript
type CreateUserInput = ...;       // 入力
type CreateUserResult = ...;       // 結果
type UserListItem = ...;           // 一覧表示用
type UserDetailDTO = ...;          // 詳細表示用
```

「**用途・場面**」を名前に入れると検索もしやすい。

### (3) ジェネリクスの型変数

```typescript
type Wrapper<T> = { value: T };           // 一般用途は T
type Map<K, V> = ...;                       // キー、値は K, V
type Result<TData, TError> = ...;          // 複数あるなら T プレフィックス
```

慣例に従う。`A`, `B` のような無意味な名前は最後の手段。

### (4) **接尾辞**の使い方（チームで統一）

| 接尾辞 | 意味 |
|---|---|
| `Input` | 関数の入力 |
| `Output` / `Result` | 関数の出力 |
| `Props` | コンポーネントのprops |
| `State` | 状態 |
| `Config` | 設定 |
| `Options` | 引数のオプション |
| `DTO` | データ転送オブジェクト（API境界） |
| `Schema` | バリデーションスキーマ |

### (5) 避けるべき名前

- `Type`, `Interface`, `Object` などの汎用語
- `IUser` の `I` プレフィックス（C#由来、TSでは推奨されない）
- 略語（`Usr`, `Mgr`）── 検索しにくい

## 5. `type` を切り出す前に考えること

### Q1: その型は本当に**新しい意味**を持つか？

```typescript
// ❌ stringを意味なくラップ
type Name = string;

// ✅ branded type で意味を持たせる
type UserId = string & { __brand: "UserId" };
```

単純な `type X = string` は、**実装上は string と区別されない**。本当に意味のある型にしたいなら branded types のテクニックを使う。

### Q2: その名前は**他のメンバーから検索可能**か？

```typescript
type T = { x: number }; // 検索しても何も見つからない
type Point = { x: number; y: number }; // 検索でヒット
```

### Q3: **インライン**でも読めるか？

```typescript
function f(callback: (item: string) => void) { ... } // インラインでも読める
function f(callback: Callback) { ... }                // 名前から実体が見えない
```

短くて読めるならインラインの方が**追いやすい**こともある。

## 6. `type` のベストプラクティス

### (1) ファイル内で**使う前に定義**する

```typescript
// ファイルの上の方
type User = { ... };
type Order = { ... };

// 関数定義
function processOrder(o: Order) { ... }
```

`type` を**ファイルの先頭**にまとめると、構造がぱっと見でわかる。

### (2) 公開する型は **`export type`** で明示

```typescript
export type User = { ... };  // ✅ 明示的にexport

type InternalConfig = { ... };  // 公開しない（exportしない）
```

`isolatedModules: true` を有効にすると、`export type` を強制される。これは推奨設定。

### (3) **ドメインモデルは1ファイル1型**

複雑なドメインの場合、`User`, `Order`, `Product` などを別ファイルに分離。

```
src/types/
  User.ts
  Order.ts
  Product.ts
```

### (4) **小さな型は1ファイルにまとめてOK**

```typescript
// types/api.ts
export type ApiSuccess<T> = { status: "success"; data: T };
export type ApiError = { status: "error"; message: string };
export type ApiResponse<T> = ApiSuccess<T> | ApiError;
```

関連する型は1ファイルにまとめると追いやすい。

## 7. `type` と `interface` の使い分け（簡略版）

| 観点 | `type` | `interface` |
|---|---|---|
| 表現力 | ◎（ユニオン、条件型、Mapped、すべて可） | △（オブジェクト型限定） |
| 拡張 | `&` で交差 | `extends` |
| 同名宣言で**マージ** | できない（重複定義はエラー） | できる（declaration merging） |
| エラーメッセージ | やや読みにくい | 読みやすい |
| 推奨 | **デフォルトで `type`** | クラスのcontract時のみ |

詳細は [[interface vs type]] へ。

**シンプルなルール**: 迷ったら `type`。クラスの `implements` 用なら `interface`。

## 8. 複雑な型の整理術

### (1) **段階的に切り出す**

```typescript
// 一度に書くと地獄
type X = { a: { b: { c: { d: number } } } };

// 段階的に
type D = { d: number };
type C = { c: D };
type B = { b: C };
type A = { a: B };
```

ネストの各層に意味があるなら名前を付ける。

### (2) **関連する型は近くに置く**

```typescript
// ✅ 関連型は近くに
type CreateUserInput = { name: string };
type CreateUserResult = { id: string };
function createUser(i: CreateUserInput): CreateUserResult { ... }

type DeleteUserInput = { id: string };
function deleteUser(i: DeleteUserInput): void { ... }
```

### (3) **ユーティリティ型で導出する**

```typescript
type User = { id: string; name: string; password: string };

type PublicUser = Omit<User, "password">;
type UpdateUserInput = Partial<Omit<User, "id">>;
```

元の型から派生させると、**メンテナンスが1か所**で済む。

## 9. アンチパターン

### (1) 何でも `type` にする

```typescript
type StringPair = [string, string];
type NumberPair = [number, number];
type BooleanPair = [boolean, boolean];
// ... など、ジェネリクスで済むものを個別に定義
```

→ ジェネリクス `Pair<T> = [T, T]` で十分。

### (2) `type` の名前が抽象的すぎる

```typescript
type Data = ...; // 何のデータ？
type Info = ...; // 何の情報？
```

具体的に。

### (3) 型エイリアスを循環参照させる

```typescript
type A = { b: B };
type B = { a: A };
```

定義は可能だが、複雑な再帰型はパフォーマンス問題やエラーメッセージの悪化の原因に。**`interface` で書く**と循環参照に強い。

### (4) `type` で `enum` のような書き方をする（誤用ではないが冗長）

```typescript
// ❌ 冗長
type Color = "red" | "green" | "blue";
const RED: Color = "red";
const GREEN: Color = "green";

// ✅ as const オブジェクトの方が値も型もまとめられる
const Color = {
  Red: "red",
  Green: "green",
  Blue: "blue",
} as const;
type Color = typeof Color[keyof typeof Color];
```

## 10. 設計判断チェックリスト

新しい型を書くとき、以下を自問:

- [ ] 同じ構造を**3箇所以上**で使う？ → 切り出す
- [ ] 名前を付けると**意図がより明確**になる？ → 切り出す
- [ ] **公開API**として外部から使われる？ → 切り出して `export`
- [ ] **判別可能ユニオン**？ → 必ず切り出す
- [ ] **1か所限り**でシンプル？ → インラインでOK
- [ ] **ユーティリティ型で導出**できる？ → `Pick` / `Omit` / `Partial` など

---

## 11. まとめ

- **切り出すべき**: 複数箇所で使う / 意図が伝わる / 構造が複雑 / 判別ユニオン / 公開API
- **切り出さない**: 1回限り / 推論で十分 / ローカルでシンプル
- 名前は**役割と用途**を含める（`CreateUserInput` など）
- ファイル先頭・近くにまとめる・`export type` を明示
- 迷ったら **`type`** を使う（`interface` は限定用途）
- ジェネリクスとユーティリティ型で**派生**させると保守性UP

> 型エイリアスは「**コードの語彙を増やす**」行為。良い名前と適切な切り出しは、3か月後の自分やチームメンバーへのプレゼントになります。**過剰でも過少でもない**バランスを意識しましょう。
