# 再帰型（必要最低限）

> 型レベルでの再帰は**強力だが諸刃の剣**。`DeepReadonly` のような実用的な型から、フィボナッチ数を型レベルで計算するような遊び型まで作れます。本ファイルでは「**実務で必要な再帰型**」と「**避けるべき再帰型**」の境界を整理します。

## 1. 再帰型とは

「**型の中で自分自身を参照する**」型。

```typescript
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object
    ? DeepReadonly<T[K]>  // 自分自身を再帰呼び出し
    : T[K];
};
```

→ オブジェクトの**ネストした全フィールド**に readonly を適用。

---

## 2. 値レベルの再帰関数と同じ発想

```typescript
// 値レベル（JSの再帰関数）
function deepFreeze(o: any): any {
  if (typeof o !== "object" || o === null) return o;
  for (const k of Object.keys(o)) deepFreeze(o[k]);
  return Object.freeze(o);
}

// 型レベル（同じ発想）
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};
```

「**自分自身を呼び出す**」「**終了条件**を持つ」 ── ふつうの再帰と同じ構造。

---

## 3. 終了条件が必須

再帰関数と同じく、**終了条件**を書かないと無限ループに:

```typescript
// ❌ 終了条件なし（コンパイラがエラーで止める）
type Bad<T> = { x: Bad<T> };

// ✅ 終了条件あり
type Good<T> = T extends object ? { [K in keyof T]: Good<T[K]> } : T;
```

「**`extends` で条件分岐し、再帰しないパスを必ず作る**」のが原則。

---

## 4. 実用的な再帰型

### `DeepReadonly<T>`

```typescript
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object
    ? T[K] extends Function
      ? T[K]                          // 関数はそのまま
      : DeepReadonly<T[K]>            // ネストしたオブジェクトは再帰
    : T[K];
};
```

→ 全プロパティを readonly に（ネスト含む）。

### `DeepPartial<T>`

```typescript
type DeepPartial<T> = {
  [K in keyof T]?: T[K] extends object ? DeepPartial<T[K]> : T[K];
};
```

→ 全プロパティを optional に。

### `DeepRequired<T>`

```typescript
type DeepRequired<T> = {
  [K in keyof T]-?: T[K] extends object ? DeepRequired<T[K]> : T[K];
};
```

### `DeepNonNullable<T>`

```typescript
type DeepNonNullable<T> = {
  [K in keyof T]: T[K] extends object
    ? DeepNonNullable<T[K]>
    : NonNullable<T[K]>;
};
```

→ 全レベルから `null` / `undefined` を除外。

## 5. 文字列・タプルの再帰

### 文字列を分割

```typescript
type Split<S extends string, D extends string> =
  S extends `${infer Head}${D}${infer Tail}`
    ? [Head, ...Split<Tail, D>]
    : [S];

type R = Split<"a,b,c", ",">;  // ["a", "b", "c"]
```

→ テンプレートリテラル型 + 再帰。詳しくは [[03-テンプレートリテラル型]]。

### タプルを反転

```typescript
type Reverse<T extends any[]> =
  T extends [infer First, ...infer Rest] ? [...Reverse<Rest>, First] : [];

type R = Reverse<[1, 2, 3]>;  // [3, 2, 1]
```

### タプルの長さ

```typescript
type Length<T extends readonly any[]> = T["length"];

type R = Length<[1, 2, 3]>; // 3
```

→ こちらは再帰不要。`["length"]` で取れる。

### Promise を再帰的に剥がす

```typescript
type Unwrap<T> = T extends Promise<infer U> ? Unwrap<U> : T;

type R = Unwrap<Promise<Promise<string>>>; // string
```

## 6. オブジェクトのキーを文字列パスに変換

```typescript
type Paths<T, Prev extends string = ""> = {
  [K in keyof T & string]:
    T[K] extends object
      ? Paths<T[K], `${Prev}${K}.`> | `${Prev}${K}`
      : `${Prev}${K}`;
}[keyof T & string];

type T = { a: { b: { c: number } }; d: string };
type R = Paths<T>;
// "a" | "a.b" | "a.b.c" | "d"
```

→ Lodashの `_.get(obj, "a.b.c")` のような型安全なパス。

---

## 7. 値の取得（`Get<T, P>`）

```typescript
type Get<T, P extends string> =
  P extends `${infer K}.${infer Rest}`
    ? K extends keyof T
      ? Get<T[K], Rest>
      : never
    : P extends keyof T
    ? T[P]
    : never;

type T = { a: { b: { c: number } } };
type R = Get<T, "a.b.c">; // number
```

→ ドット区切りパスから値の型を取り出す。

---

## 8. 再帰の深さ制限

TypeScript には**型計算の深さ制限**がある:

```typescript
type DeepRecursion<T extends number, Acc extends any[] = []> =
  Acc["length"] extends T ? Acc : DeepRecursion<T, [...Acc, any]>;

type R = DeepRecursion<50>; // OK
type R2 = DeepRecursion<1000>; // ❌ Type instantiation is excessively deep
```

→ おおむね **45〜50 階層**が限度（バージョンによる）。

### 緩和テクニック

```typescript
type Tail<T extends any[]> = T extends [any, ...infer R] ? R : [];
```

末尾呼び出し最適化されるパターンで書くと、深い再帰も通ることがある。詳しくはタイプチャレンジ等を参照。

---

## 9. 再帰型を使うべき場面

### 使うべき

- **DeepXxx 系**（DeepReadonly / DeepPartial）── 標準にないが実用的
- **オブジェクト構造の変換**（プロパティ全部に処理）
- **タプル・文字列の分解**
- **ライブラリ作成**（型安全な `Get`, `Paths` など）

### 使わない方がよい

- **業務ロジック**（実行時で書ける処理を型でやらない）
- **「動くからOK」程度の用途**（テストなしの再帰型は危険）
- **チームメンバーが読めない複雑度**

---

## 10. 落とし穴

### (1) 終了条件を書き忘れる

```typescript
type Bad<T> = { x: Bad<T> }; // 無限再帰
```

→ TS が止めるが、エラーが分かりにくい。

### (2) 深すぎてコンパイル不能

```typescript
type T = SomeRecursive<...>;
// Type instantiation is excessively deep and possibly infinite.
```

→ 入力サイズを制限するか、別アプローチを。

### (3) パフォーマンス低下

巨大な型の再帰計算は **VSCode の補完が遅く**なることも。

### (4) `object` の判定が緩い

```typescript
type T = string extends object ? true : false; // false
type T2 = number[] extends object ? true : false; // true
type T3 = (() => void) extends object ? true : false; // true
```

→ `object` は配列や関数も含む。意図しない再帰になることも:

```typescript
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};
// 配列・関数もネストしたオブジェクトとして再帰される
```

### (5) `infer` の同名衝突

```typescript
type Bad<T> = T extends [infer A, ...infer A] ? A : never;
// A が ユニオン化される
```

→ 別名にする。

## 11. デバッグのコツ

### 中間型を作る

```typescript
type Step1 = MyRecursive<...>;
type Step2 = AnotherStep<Step1>;
```

VSCode で各段階の型をホバーで確認。

### `Prettify` で展開

```typescript
type Prettify<T> = { [K in keyof T]: T[K] } & {};

type R = Prettify<DeepReadonly<...>>;
```

### 小さい入力でテスト

```typescript
type _Test1 = DeepReadonly<{ a: number }>;
type _Test2 = DeepReadonly<{ a: { b: string } }>;
```

予想と合っているか確認。

## 12. ベストプラクティス

### (1) **標準やライブラリを優先**

`type-fest` の `PartialDeep`, `ReadonlyDeep` などを利用。

### (2) **JSDoc + 例を必須に**

```typescript
/**
 * オブジェクトを再帰的に readonly にする。
 * @example
 * type T = DeepReadonly<{ a: { b: number } }>;
 * //   ^ { readonly a: { readonly b: number } }
 */
type DeepReadonly<T> = ...;
```

### (3) **シンプルに保つ**

3階層以上ネストする条件型は読めない。**中間型に分解**を。

### (4) **テスト型を書く**

```typescript
type _Assert1 = Expect<Equal<DeepReadonly<{ a: 1 }>, { readonly a: 1 }>>;
```

`type-fest` や自作の `Equal<A, B>` で検証。

### (5) **本当に必要か再確認**

「型でやる」より「**ランタイムでやる**」方が読みやすいことも:

```typescript
// ❌ 型レベルで全部やる
type ParseConfig<S extends string> = ...;

// ✅ ランタイム + Zod
const config = ConfigSchema.parse(JSON.parse(s));
```

---

## 13. アンチパターン

### (1) **業務コードに深い再帰型**

```typescript
// アプリ内で
type DeepUserPath = ...;
```

→ ライブラリ作者の領域。アプリでは標準型 + 実装で。

### (2) **「動くからOK」で放置**

```typescript
type X<T> = ... // 半年後に自分も読めない
```

→ コメント・テスト・分解を。

### (3) **再帰の意図が不明**

```typescript
type Y<T> = T extends infer X ? Y<X> : never;
```

→ 何をしたいか不明。設計を見直す。

### (4) **過度な型計算でビルドが遅い**

→ ベンチマークし、遅ければ妥協する。

---

## 14. 「型計算」の哲学

TypeScript の型システムは**チューリング完全**（型レベルで何でも計算できる）。

### しかし

「**できる**」と「**やるべき**」は違う。型レベルプログラミングは:

- **強力**だが **読みにくい**
- **ライブラリ**では価値があるが **アプリ**では負担
- **TypeScript の進化に追従**する必要

→ 「**最小限で最大の効果**」を目指す。

---

## 15. 実例: 「実用」と「遊び」の境界

### 実用: `DeepReadonly`

```typescript
type DeepReadonly<T> = {
  readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K];
};
```

→ 設計に明確な意味、業務でも使える。

### 遊び: フィボナッチ数

```typescript
type Fib<N extends number, ...> = ...;
```

→ TypeScript チャレンジの世界。**業務では絶対に書かない**。

---

## 16. まとめ

- **再帰型** = 型の中で自分自身を参照
- 必須: **終了条件**（`extends` で再帰しないパスを作る）
- 実用: **`DeepReadonly` / `DeepPartial`**, タプル・文字列分解
- 限界: **深さ制限（〜45階層）**、計算速度低下
- 落とし穴: 終了条件忘れ / 深すぎ / パフォーマンス
- 「**できる**」と「**やるべき**」は別 ── アプリでは標準型 + ライブラリ

> 再帰型は「**型の世界の最終兵器**」。`DeepXxx` のような実用型は便利だが、業務コードでは「**そもそも書かない**」が正解なことが多い。**「型でやるか、ランタイムでやるか」**を毎回問うのがプロのスタンスです。
