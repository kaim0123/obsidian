# 「読める型」のための命名・分割

> 高度な型は「**書ける**」ことより「**読める**」ことの方が遥かに難しい。条件型・`infer`・再帰を駆使した型を、半年後の自分やチームメイトが理解できる形に保つには、**命名と分割の規律**が必要です。本ファイルは型レベルプログラミングの**最後の関門**です。

## 1. 「読めない型」が生む問題

```typescript
type X<T> = T extends infer U ? U extends (...args: infer A) => infer R
  ? R extends Promise<infer P> ? P extends Array<infer E> ? E : P : R : T : never;
```

→ 何をしているか**1秒で分からない**。

### 実害

- **デバッグ困難**: エラーメッセージから原因特定不能
- **変更時の事故**: 1か所変えると別の場所が壊れる
- **チームの足を引っ張る**: 他人が触れない
- **TypeScriptバージョン更新で動かなくなる**: 複雑型ほど挙動変化に弱い

→ **「動く」だけでは資産にならない**。読める型こそ価値。

---

## 2. 命名の原則

### (1) 意図を表す名前

```typescript
// ❌ 何の型か分からない
type X<T> = ...;
type Y<T, U> = ...;

// ✅ 意図が分かる
type DeepReadonly<T> = ...;
type Override<T, R> = ...;
```

### (2) 動詞 vs 名詞

| パターン | 例 | 用途 |
|---|---|---|
| **動詞** | `Pick`, `Omit`, `Extract` | 操作（〜する） |
| **名詞** | `Partial`, `Readonly`, `Promise` | 結果の状態 |
| **形容詞 + 名詞** | `DeepReadonly`, `RequiredKeys` | 修飾された結果 |

→ 標準ライブラリの命名にならう。

### (3) ジェネリクス引数の名前

| 慣例 | 用途 |
|---|---|
| `T` | 一般型（最頻出） |
| `K` | キー（`keyof`） |
| `V` | 値 |
| `R` | 戻り値（return） |
| `E` | 要素・エラー |
| `P` | プロパティ・パラメータ |
| `U`, `W` | 2つ目以降の一般型 |

```typescript
type Get<T, K extends keyof T> = T[K];
type Map<T, U> = ...;
type Result<T, E> = ...;
```

→ **慣例から外れる名前は、意味を持たせる**:

```typescript
type Validators<TInput, TOutput> = ...;
```

`A`, `B`, `C` のような無意味な名前は最後の手段。

### (4) 「動詞 + 名詞」の組み合わせ

```typescript
type ExtractParams<S> = ...;
type RemoveProperty<T, K> = ...;
type FilterByType<T, V> = ...;
```

→ 「**何を**」「**どうする**」が読み取れる。

---

## 3. 分割の原則

### (1) 1つの型 = 1つの責任

```typescript
// ❌ 1つの型が複数のことをしている
type Complex<T> = ...; // (フィルタ + 変換 + ネスト)

// ✅ 役割ごとに分割
type FilterByType<T, V> = ...;
type Transform<T, F> = ...;
type Nest<T> = ...;

type Complex<T> = Nest<Transform<FilterByType<T, string>, ToUppercase>>;
```

### (2) 中間型に名前を付ける

```typescript
// ❌ ネストが深い
type X<T> = T extends infer U
  ? U extends Array<infer E>
    ? E extends string ? Capitalize<E> : E
    : U
  : T;

// ✅ 段階的に
type ElementOf<T> = T extends Array<infer E> ? E : T;
type CapitalizeIfString<T> = T extends string ? Capitalize<T> : T;

type X<T> = CapitalizeIfString<ElementOf<T>>;
```

→ **読めば動きが分かる**型に。

### (3) 終了条件を最初に書く

```typescript
// ✅ 「終わる条件」が先頭
type DeepReadonly<T> =
  T extends Function ? T :                  // 関数はそのまま
  T extends object ? { readonly [K in keyof T]: DeepReadonly<T[K]> } :
  T;                                         // プリミティブはそのまま
```

`if-else if-else` の発想で、**例外ケース → 通常ケース** の順で書くと読みやすい。

## 4. JSDoc の活用

### (1) 何をする型か

```typescript
/**
 * オブジェクトのすべてのプロパティを再帰的に readonly にする。
 */
type DeepReadonly<T> = ...;
```

### (2) 例を入れる

```typescript
/**
 * @example
 * type T = DeepReadonly<{ a: { b: number } }>;
 * //   ^ { readonly a: { readonly b: number } }
 */
```

### (3) 制約を説明

```typescript
/**
 * @typeParam T - 変換対象。プリミティブは変換されずそのまま返る。
 * @typeParam K - 除外するキー。`keyof T` のサブセット。
 */
type Without<T, K extends keyof T> = Omit<T, K>;
```

### (4) 失敗ケース

```typescript
/**
 * 配列でない型を渡すと never。
 */
type ElementOf<T> = T extends (infer E)[] ? E : never;
```

→ **意図 + 例 + 制約 + エッジケース**の4点セット。

## 5. 型のテスト

複雑な型は**テスト型**で動作確認:

### 自作 Equal ヘルパ

```typescript
type Equal<X, Y> =
  (<T>() => T extends X ? 1 : 2) extends
  (<T>() => T extends Y ? 1 : 2) ? true : false;

type Expect<T extends true> = T;

// テスト
type _T1 = Expect<Equal<DeepReadonly<{ a: 1 }>, { readonly a: 1 }>>;
type _T2 = Expect<Equal<ElementOf<number[]>, number>>;
```

→ 期待する型と一致しないとコンパイルエラーになる。

### `tsd` ライブラリ

```typescript
import { expectType, expectError } from "tsd";

expectType<DeepReadonly<{ a: 1 }>>({} as { readonly a: 1 });
```

→ より公式なテストライブラリ。

## 6. ファイル構成

### 1ファイル1型〜数個

```
src/types/
  deep-readonly.ts
  override.ts
  utility.ts        // 小さい型をまとめて
```

→ 大きな型は**ファイル分離**、小さい型は**まとめる**。

### 関連型をグルーピング

```typescript
// types/string-paths.ts
type Paths<T> = ...;
type PathValue<T, P> = ...;
type Get<T, P> = ...;
type Set<T, P, V> = ...;
```

→ 用途が近い型は1ファイルに。

## 8. リファクタの実例

### Before: 読めない型

```typescript
type X<T> = T extends Promise<infer U>
  ? U extends Array<infer E>
    ? E extends { name: infer N }
      ? N extends string
        ? Capitalize<N>
        : never
      : never
    : never
  : never;
```

### After: 段階的に分解

```typescript
/** Promise の中身を取り出す */
type Unwrap<T> = T extends Promise<infer U> ? U : T;

/** 配列の要素型を取り出す（配列でなければ never） */
type ElementOf<T> = T extends Array<infer E> ? E : never;

/** name プロパティの値型を取り出す */
type NameOf<T> = T extends { name: infer N } ? N : never;

/** 文字列なら Capitalize、それ以外は never */
type CapitalizeStr<T> = T extends string ? Capitalize<T> : never;

/**
 * Promise<{ name: string }[]> から最初の name の Capitalize を取得。
 */
type X<T> = CapitalizeStr<NameOf<ElementOf<Unwrap<T>>>>;
```

→ **5つの小さな型**に分けたら、各段階の意味が明確に。

## 9. ライブラリ作者が気をつけていること

`type-fest`, `Zod`, `tRPC` などの作者は:

### (1) **エラーメッセージの読みやすさ**

```typescript
// ❌ 失敗時に never だけ
type X<T> = T extends ... ? ... : never;

// ✅ 失敗時に意味あるメッセージ
type X<T> = T extends ... ? ... : { error: "T must be ..." };
```

→ ユーザに「なぜダメか」を伝える設計。

### (2) **ジェネリクスの制約で早期エラー**

```typescript
// ❌
type Pick<T, K> = ...;

// ✅
type Pick<T, K extends keyof T> = ...;
```

→ 制約で**呼び出し時にエラー**を出す。

### (3) **「サイレントフェイル」を避ける**

```typescript
// 失敗時に never を返すと、利用側で「使えない型」が静かに通ってしまう
```

→ 失敗時に**目立つ型**（明示的なエラー型など）を返す設計も。

---

## 10. アプリ開発者の戦略

### (1) **ライブラリ任せ**

`Zod`, `type-fest`, `tRPC` などに任せ、**自分では書かない**。

### (2) **必要最小限で**

業務コードに高度な型を持ち込まない。**標準ユーティリティの組み合わせ**で。

### (3) **読めない型はリファクタ**

PR レビューで「読めない型」が来たら**書き直す勇気**を。

### (4) **「型でやる」より「ランタイムでやる」**

型レベルでパースより、Zodで検証の方が読みやすい。

## 11. アンチパターン

### (1) **暗号のような型名**

```typescript
type T1<X> = ...;
type T2<X, Y> = ...;
```

→ 命名は型のドキュメント。

### (2) **インラインで書きまくる**

```typescript
function f<T extends ...と..., K extends keyof T extends..., ...>() { ... }
```

→ 型を切り出す。

### (3) **「動くからOK」で放置**

```typescript
type X = ... // 半年後の自分も読めない
```

### (4) **コメントなしの再帰型**

```typescript
type DeepXxx<T> = ...;
// 何が起きてるか不明
```

### (5) **TypeScript チャレンジ風の型を業務で使う**

```typescript
type Fib<N> = ...; // 業務に不要
```

## 12. ベストプラクティス

### (1) **「型を書く時間 < 型を読む時間」を意識**

書くのは1回、読むのは何度も。**読みやすさ優先**。

### (2) **3階層ネストを超えたら分解**

機械的なルール。

### (3) **JSDoc + 例を必須化**

ESLintで強制可能（`jsdoc/require-jsdoc` など）。

### (4) **テスト型を書く**

```typescript
type _Test = Expect<Equal<X<...>, ...>>;
```

ファイルの末尾にまとめて。

### (5) **チームで型レビュー基準を持つ**

「**1分で読めない型はNG**」のような規律。

---

## 13. まとめ

- **書ける型 ≠ 読める型**。読めない型は**負債**
- **命名**: 動詞/名詞、ジェネリクスは慣例 (`T`, `K`, `V`, `R`)
- **分割**: 1つの責任、中間型に名前、終了条件を最初に
- **JSDoc**: 意図 + 例 + 制約 + エッジケース
- **テスト型**: `Equal<A, B>` で動作保証
- **「型でやる」より「ランタイムでやる」**を毎回問う
- 業務コードでは**標準型 + ライブラリ**が基本、自作は最小限

> 高度な型を書ける力より、「**他人が読める型を書く**」「**書かないで済ます**」判断力の方が、TypeScriptプログラマとしての成熟度を表します。「**できる**」と「**するべき**」は別 ── これが14章の最終結論です。
