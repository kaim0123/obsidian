# 監視と可観測性の違い

**監視（Monitoring）** と **可観測性（Observability）** はよく混同されますが、指している範囲が違います。『Observability Engineering』（Charity Majors ほか）では、可観測性を「**システムの内部状態を、新しいコードを出荷せずに、外に出ているデータだけで理解できる度合い**」と定義しています。この章では、両者の違いと、なぜ今「可観測性」が重視されるのかを整理します。

---

## 1. 言葉の定義

| 用語 | 問い | 性格 |
|------|------|------|
| **監視** | 「あらかじめ決めた異常が起きていないか？」 | 既知の問題を見張る。ダッシュボードとアラートが中心 |
| **可観測性** | 「今、何が起きていて、なぜそうなったのか？」 | 未知の問題を調べられる性質。システムの**特性**を指す |

- 「可観測性」はもともと制御工学の用語で、**出力から内部状態を推定できるか**という性質のことです。
- 監視は「行為」、可観測性は「システムの性質」です。監視は可観測性の上に成り立つ活動の 1 つ、と考えると整理しやすくなります。

---

## 2. 既知の未知と未知の未知

| 分類 | 例 | 向いている手段 |
|------|----|----------------|
| **既知の既知**（分かっていて、見張れる） | CPU 使用率が 90% を超える | 監視・アラート |
| **既知の未知**（起きうると分かっている） | DB のコネクションが枯渇するかもしれない | 監視・ダッシュボード |
| **未知の未知**（想定していなかった） | 特定の国の、特定のアプリ版の、特定の決済手段だけ遅い | 可観測性（高カーディナリティのデータを自由に絞り込む） |

モノリスの時代は、壊れ方がある程度決まっていたので「既知」を見張る監視で足りました。マイクロサービス・クラウド・頻繁なデプロイの時代には、**壊れ方の組み合わせが爆発**し、事前にダッシュボードを用意できない問題が増えています。

---

## 3. 何が違うのか：具体例

「チェックアウト API が一部のユーザーだけ遅い」という問い合わせが来たとします。

**監視だけの場合**

1. ダッシュボードを見る → 全体の平均レイテンシは正常
2. CPU・メモリも正常
3. 「再現しない」で調査が止まる

**可観測性がある場合**

1. 遅いリクエストのトレースを検索する（`duration > 2s AND route = /checkout`）
2. 属性で絞り込む → `payment.provider = "X"` かつ `app.version = "3.2.0"` に集中していると分かる
3. そのトレースのスパンを見る → 外部決済 API の呼び出しで 1.8 秒待っている
4. 同じ `trace_id` のログを見る → リトライが 3 回発生している

違いは、**事前に想定していない切り口で、あとから自由に絞り込めるか**です。そのためには、リクエスト単位で豊富な属性（ユーザー ID、バージョン、テナントなど）を持ったデータが必要になります（[[03_カーディナリティ問題]]）。

---

## 4. 可観測性を支えるもの

| 要素 | 内容 | このフォルダの章 |
|------|------|------------------|
| **テレメトリ** | ログ・メトリクス・トレースなどの外に出すデータ | [[02_ログ・メトリクス・トレースの3シグナル]] |
| **計装** | コードやライブラリからテレメトリを出す仕組み | 50_計装・OpenTelemetry |
| **相関** | 別々のデータを同じリクエストとして結びつける | 40_分散トレース |
| **問い方** | 何を見れば健全か分かるか | [[03_ゴールデンシグナル]]、60_SLO・アラート |

- 可観測性はツールを買えば手に入るものではありません。**アプリ自身が、調べるのに必要な情報を出しているか**が本質です。
- 「ログ・メトリクス・トレースの 3 本柱があれば可観測性がある」とは限りません。『Observability Engineering』は、柱の数より **任意の属性で切って比べられるか** を重視しています。

---

## 5. 監視は不要になるのか

不要にはなりません。役割が変わります。

| 活動 | 目的 | 使うもの |
|------|------|----------|
| **アラート** | ユーザーに影響が出たら人を呼ぶ | SLO に基づく症状ベースのアラート（60_SLO・アラート） |
| **ダッシュボード** | 全体の健康状態をひと目で把握する | ゴールデンシグナル |
| **調査（デバッグ）** | なぜ起きたかを突き止める | トレース・構造化ログ・高カーディナリティの絞り込み |

Google SRE 本 6 章では、監視の目的を「**何が壊れているか（症状）** と **なぜ壊れているか（原因）**」に分けています。アラートは症状で出し、原因の調査に可観測性を使う、という分担が現在の標準的な考え方です。

---

## 6. 小さく始めるなら

1. ログを **構造化（JSON）** にする（[[01_構造化ログ]]）
2. すべてのログに **リクエスト ID / trace_id** を付ける
3. 主要 API の **リクエスト数・エラー数・レイテンシ** をメトリクスにする（[[02_REDメソッドとUSEメソッド]]）
4. OpenTelemetry の自動計装で **トレース** を取り始める（50_計装・OpenTelemetry）
5. ユーザー目線の **SLO** を 1 つ決めて、それだけでアラートする（60_SLO・アラート）
