# ログレベルの使い分け

**ログレベル** は、ログの重要度を表すラベルです。レベルを正しく付けておくと、本番では重要なものだけを出し、調査のときだけ詳しく出す、といった切り替えができます。逆にレベルがいい加減だと、「ERROR が多すぎて誰も見ない」「本当の異常が INFO に埋もれる」状態になります。この章では、各レベルの意味と判断基準を整理します。

---

## 1. 代表的なレベル

pino・winston・Log4j・Python logging などで名前は多少違いますが、考え方はほぼ共通です。OpenTelemetry のログ仕様では SeverityNumber（1〜24）に対応づけられています。

| レベル | 意味 | 本番で出すか | 例 |
|--------|------|--------------|----|
| **FATAL** | プロセスが続行できない | 出す | 起動時に必須の設定がない |
| **ERROR** | 処理が失敗し、誰かが対応すべき | 出す | 決済 API が 500 を返し、注文が確定できなかった |
| **WARN** | 想定外だが処理は続けられた | 出す | リトライで成功した、非推奨 API が呼ばれた |
| **INFO** | 正常な重要イベント | 出す | サーバー起動、注文確定、ジョブ完了 |
| **DEBUG** | 開発・調査用の詳細 | 通常は出さない | 関数の入力値、分岐の結果 |
| **TRACE** | さらに細かい追跡 | 出さない | ループの各回、SQL の全パラメータ |

## 2. 判断の基準

迷ったら、**「このログを見た人は何をすべきか」** で決めます。

```text
このログが出たとき…
├─ 人がすぐ対応すべき？ ── はい → ERROR（件数が増えたらアラート）
├─ 放置すると問題になりうる？ ── はい → WARN
├─ 業務・運用上、記録として残したい？ ── はい → INFO
└─ 開発・調査のときだけ欲しい？ ── はい → DEBUG
```

### ERROR と WARN の境目

| 状況 | レベル | 理由 |
|------|--------|------|
| 外部 API が失敗し、リトライで成功した | WARN | ユーザーへの影響はない |
| 外部 API がリトライ上限まで失敗し、ユーザーにエラーを返した | ERROR | ユーザーに影響した |
| ユーザーがパスワードを間違えた | INFO（または出さない） | 正常な業務の一部 |
| バリデーションエラー（400） | INFO / DEBUG | クライアント側の問題 |
| 同じ IP から短時間に大量のログイン失敗 | WARN | 攻撃の兆候（セキュリティログとしても残す） |

- **クライアントの誤り（4xx）を ERROR にしない**のが大原則です。ERROR はサーバー側で対処が必要なものに限ります。
- 「ERROR が 1 日 1 万件出ていて誰も見ていない」は、ERROR の意味が失われているサインです。

## 3. 本番でのレベル設定

```ts
const logger = pino({ level: process.env.LOG_LEVEL ?? "info" });
```

- 本番は **INFO 以上**が一般的です。DEBUG を常に出すとコストが跳ね上がります。
- 調査のときだけ詳しくしたい場合の方法：

| 方法 | 内容 |
|------|------|
| 環境変数を変えて再起動 | 簡単だが、再起動で状況が変わることがある |
| 実行時にレベルを変える API | `logger.level = "debug"` を管理用エンドポイントから切り替える |
| 特定リクエストだけ DEBUG | ヘッダー（例：`x-debug: true`）や Feature Flag で子ロガーのレベルを上げる |
| サンプリング | DEBUG を 1% だけ出す |

## 4. レベルとアラートの関係

- **ログ 1 件ごとにアラートを出さない**のが基本です。ERROR ログの**件数や割合**をメトリクスにして、閾値でアラートします。
- さらに良いのは、ログではなく **SLO（エラー率・レイテンシ）でアラートする**ことです。ERROR ログは原因調査の材料として使います（60_SLO・アラート）。

```promql
# ログ基盤からメトリクス化した ERROR 件数（例：Loki）
sum(rate({service="checkout-api"} | json | level="error" [5m]))
```

## 5. よくある失敗

| 失敗 | 何が困るか | 対策 |
|------|------------|------|
| 例外を catch するたびに ERROR を出し、さらに上に投げる | 同じエラーが何重にも出る | **ログを出す場所を 1 か所に決める**（最上位のエラーハンドラーなど） |
| すべて INFO | 重要度で絞り込めない | 判断基準をチームで決める |
| 正常系の詳細を INFO で大量に出す | コスト増、重要ログが埋もれる | DEBUG に下げる、Wide Event にまとめる |
| WARN を誰も見ない | 障害の予兆を逃す | WARN の件数推移をダッシュボードに出す |
