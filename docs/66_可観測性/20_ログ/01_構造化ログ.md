# 構造化ログ

**構造化ログ（Structured Logging）** は、ログを人が読む文章ではなく、**キーと値の組（多くは JSON）** として出力するやり方です。ログを「読むもの」から「検索・集計するデータ」に変えるための、可観測性の最初の一歩です。この章では、構造化ログの形、Node.js（pino）での書き方、よくある失敗を整理します。

---

## 1. 非構造化ログと構造化ログ

**非構造化（文字列）**

```text
2026-09-26 10:15:03 ERROR Payment failed for user u_123 with stripe (502) after 1830ms
```

**構造化（JSON）**

```json
{"level":"error","time":"2026-09-26T10:15:03.120Z","msg":"payment failed",
 "user_id":"u_123","provider":"stripe","status_code":502,"duration_ms":1830,
 "trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","service":"checkout-api"}
```

| 観点 | 文字列ログ | 構造化ログ |
|------|------------|------------|
| 人が読む | 読みやすい | そのままでは読みにくい（整形ツールで解決） |
| 検索 | 正規表現頼み。書式が変わると壊れる | `provider = "stripe" AND status_code >= 500` |
| 集計 | 困難 | 「プロバイダ別の失敗件数」が簡単 |
| 型 | すべて文字列 | 数値・真偽値として扱える |

## 2. Node.js での書き方（pino）

```ts
import pino from "pino";

export const logger = pino({
  level: process.env.LOG_LEVEL ?? "info",
  base: { service: "checkout-api", env: process.env.NODE_ENV },
  timestamp: pino.stdTimeFunctions.isoTime,
  redact: ["req.headers.authorization", "*.password", "*.cardNumber"],
});

// メッセージは固定文、変わる値はフィールドに
logger.error(
  { userId: "u_123", provider: "stripe", statusCode: 502, durationMs: 1830 },
  "payment failed",
);
```

- **メッセージは固定の文**にして、変わる値はフィールドに入れます。`"payment failed for u_123"` のように値を埋め込むと、同じ種類のログを集計できなくなります。
- 開発中は `pino-pretty` で読みやすく表示し、本番は JSON のまま出します。
- `redact` で機密情報を自動で伏せます（[[03_ログに書くこと・書かないこと]]）。

## 3. リクエスト単位のコンテキスト

同じリクエストのログを後から束ねられるように、**すべてのログに共通の ID** を付けます。

```ts
import pinoHttp from "pino-http";
import { randomUUID } from "node:crypto";

app.use(pinoHttp({
  logger,
  genReqId: (req) => req.headers["x-request-id"] ?? randomUUID(),
}));

app.post("/checkout", async (req, res) => {
  req.log.info({ cartId: req.body.cartId }, "checkout started"); // reqId が自動で付く
});
```

- OpenTelemetry を入れている場合は、`trace_id` / `span_id` をログに自動で入れられます（[[04_ログ・メトリクス・トレースの相関]]）。
- 子ロガー（`logger.child({ tenantId })`）で、テナントやジョブ ID などを一度に付けられます。

## 4. 標準的なフィールド

チーム内で**フィールド名をそろえる**ことが、検索のしやすさを左右します。OpenTelemetry のセマンティック規約や Elastic Common Schema（ECS）を参考にすると迷いません。

| フィールド | 例 | 説明 |
|------------|----|------|
| `time` | ISO 8601（UTC） | タイムゾーンを明記する |
| `level` | `info` / `error` | [[02_ログレベルの使い分け]] |
| `msg` | `"payment failed"` | 固定文 |
| `service` / `env` / `version` | `checkout-api` / `prod` / `3.2.0` | どこから出たか |
| `trace_id` / `span_id` / `request_id` | | 相関用 |
| `http.method` / `http.route` / `http.status_code` | | HTTP の情報 |
| `duration_ms` | `1830` | 単位をフィールド名に入れる |
| `error.type` / `error.message` / `error.stack` | | エラー情報はまとめて |

- `userId` と `user_id` が混在すると検索で漏れます。**命名規則（snake_case か camelCase か）を 1 つに決める**のが大事です。

## 5. Wide Event（広いイベント）

『Observability Engineering』では、処理の途中で何行もログを出すより、**リクエストの終わりに属性を詰め込んだ 1 行を出す**ことを勧めています。

```json
{"msg":"request completed","http.route":"/checkout","http.status_code":200,
 "duration_ms":412,"user_id":"u_123","tenant":"acme","cart.items":3,
 "payment.provider":"stripe","payment.retries":1,"db.queries":7,
 "cache.hit":false,"feature_flag.new_checkout":true,"app.version":"3.2.0"}
```

- 1 行に情報が集まっているので、「`feature_flag.new_checkout = true` のときだけ遅いか？」のような**未知の問い**に答えられます。
- 分散トレースのスパンに属性を付けるのも同じ発想です。

## 6. よくある失敗

| 失敗 | 問題 | 対策 |
|------|------|------|
| メッセージに値を埋め込む | 集計できない | 値はフィールドへ |
| `console.log(obj)` をそのまま使う | 形式がばらばら、レベルがない | ロガーライブラリを使う |
| 例外を文字列化して捨てる | スタックトレースが失われる | `logger.error({ err }, "...")` |
| ログを同期でファイルに書く | イベントループを止める | 標準出力に出し、収集は基盤に任せる（12-Factor App） |
| 1 リクエストで何百行も出す | コストと検索性の悪化 | Wide Event にまとめる、デバッグログは本番で無効化 |
