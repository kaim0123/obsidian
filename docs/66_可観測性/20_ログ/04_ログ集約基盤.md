# ログ集約基盤

サーバーが 1 台なら `tail -f` で足りますが、コンテナが数十個に増え、しかも数分で入れ替わる環境では、**ログを 1 か所に集めて検索できる仕組み** が必要です。これをログ集約基盤（ログ管理基盤）と呼びます。この章では、ログが集まるまでの流れ、代表的な構成、コストの抑え方を整理します。

---

## 1. なぜ集約するのか

| 問題 | 集約しないと |
|------|--------------|
| コンテナは使い捨て | Pod が消えるとログも消える |
| リクエストが複数サービスをまたぐ | サーバーを 1 台ずつ見て回ることになる |
| 障害時は時間が勝負 | `ssh` して `grep` している余裕がない |
| アクセス権 | 本番サーバーへのログインを許可したくない |

---

## 2. ログが集まるまでの流れ

```text
[アプリ] → stdout → [収集エージェント] → [バッファ/加工] → [保存・索引] → [検索・可視化]
            │           Fluent Bit          OTel Collector     Elasticsearch   Kibana
            │           Vector              Kafka              Loki            Grafana
            └ ファイル   Promtail/Alloy                          CloudWatch Logs
```

| 段階 | 役割 | 代表例 |
|------|------|--------|
| **出力** | アプリは標準出力に JSON で出すだけ | pino、winston |
| **収集** | ノード上でログを拾い、メタデータ（Pod 名、ラベル）を付ける | Fluent Bit、Vector、Grafana Alloy |
| **加工・バッファ** | パース、機密情報の除去、サンプリング、送り先の振り分け | OpenTelemetry Collector、Kafka |
| **保存・索引** | 検索できる形で保存 | Elasticsearch / OpenSearch、Loki、ClickHouse |
| **検索・可視化** | クエリ、ダッシュボード、アラート | Kibana、Grafana |

- **アプリはログの送り先を知らない**のが理想です（12-Factor App の「ログをイベントストリームとして扱う」）。送り先の変更は基盤側で吸収します。

---

## 3. 代表的な構成

| 構成 | 特徴 | 向いている場面 |
|------|------|----------------|
| **EFK / ELK**（Elasticsearch + Fluentd/Logstash + Kibana） | 全文検索が強い。インデックス作成が重く、運用コストも高い | 自由な全文検索が必要 |
| **Grafana Loki** | ラベルだけ索引し、本文は圧縮保存。安い | Prometheus / Grafana を既に使っている |
| **クラウドのマネージド** | CloudWatch Logs、Cloud Logging。導入が楽 | 小〜中規模、クラウド 1 社で完結 |
| **SaaS** | Datadog、New Relic、Splunk など。高機能だが従量課金 | 運用を任せたい、トレースと一体で使いたい |
| **列指向 DB** | ClickHouse などに Wide Event を保存 | 高カーディナリティの分析をしたい |

製品の比較は 90_ツール別リファレンス / [[04_可観測性ツールの比較と選び方]] で扱います。

---

## 4. 検索の例

**Loki（LogQL）**

```text
{service="checkout-api", env="prod"} | json | level="error" | provider="stripe"
```

**CloudWatch Logs Insights**

```text
fields @timestamp, msg, provider, status_code
| filter level = "error" and provider = "stripe"
| stats count() by bin(5m)
```

- 構造化ログ（[[01_構造化ログ]]）でなければ、こうした絞り込みや集計はほぼできません。

---

## 5. コストを抑える

ログは 3 シグナルの中で最も**量に比例して**費用が増えます。

| 手段 | 内容 |
|------|------|
| **出さない** | DEBUG を本番で無効に、ヘルスチェックのアクセスログを除外 |
| **まとめる** | 1 リクエスト 1 行の Wide Event にする |
| **サンプリング** | 正常なリクエストのログは 10% だけ、エラーは全件 |
| **階層保存** | 直近 7 日は高速ストレージ、それ以降は S3 などの安いストレージへ |
| **保存期間** | 用途別に決める（調査用 14〜30 日、監査用は別基盤で長期） |
| **メトリクス化** | 「件数」だけ欲しいならログではなくメトリクスで出す |

---

## 6. 運用上の注意

- **ログ基盤が落ちてもアプリを止めない**。送信は非同期、バッファが溢れたら捨てる設計にします。
- **ログの欠落を検知する**。サービスごとのログ流量がゼロになったらアラートを出します。
- **時刻をそろえる**。サーバーの時計がずれていると、サービスをまたぐ時系列が狂います（NTP）。
- **アクセス制御と保存期間**を決める（[[03_ログに書くこと・書かないこと]]）。
- 大規模障害時は**ログ量も急増**します。基盤が一番必要なときに詰まらないよう、余裕を見積もっておきます。
