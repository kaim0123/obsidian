# ログに書くこと・書かないこと

ログは調査の命綱ですが、書きすぎると **個人情報や秘密情報の漏えい源** になり、書かなさすぎると障害時に何も分かりません。OWASP Logging Cheat Sheet は、「何を記録すべきか」と「何を記録してはいけないか」の両方をまとめています。この章では、その内容を Web アプリの実務に落として整理します。

---

## 1. 書くべきこと

### 1.1 イベントの種類（OWASP Logging Cheat Sheet より）

| 分類 | 例 |
|------|----|
| **入力検証の失敗** | 不正なパラメータ、プロトコル違反 |
| **認証の成功・失敗** | ログイン、ログアウト、MFA の失敗 |
| **認可の失敗** | 権限のないリソースへのアクセス |
| **セッション管理の失敗** | 改ざんされた Cookie、無効なトークン |
| **アプリのエラー・システムイベント** | 例外、起動・停止、設定変更、外部サービスの接続失敗 |
| **重要な業務操作** | 注文確定、送金、権限の変更、データのエクスポート |
| **高リスクな操作** | ユーザー削除、管理者権限の付与、一括更新 |

### 1.2 1 件のログに含める情報（いつ・どこ・誰・何）

| 要素 | フィールド例 |
|------|--------------|
| **いつ** | `time`（UTC、ミリ秒まで） |
| **どこで** | `service`、`version`、`host`、`http.route` |
| **誰が** | `user_id`（ID のみ）、`tenant_id`、送信元 IP（扱いは後述） |
| **何を** | `msg`、`event.action`、`http.method` |
| **結果** | `http.status_code`、`outcome: success/failure`、`duration_ms` |
| **つなぐ** | `trace_id`、`request_id` |

## 2. 書いてはいけないこと

| 分類 | 例 | 理由 |
|------|----|------|
| **認証情報** | パスワード、セッション ID、アクセストークン、API キー、`Authorization` ヘッダー | 漏れた時点で乗っ取られる |
| **暗号の鍵・シークレット** | DB パスワード、秘密鍵、接続文字列 | 同上 |
| **決済情報** | クレジットカード番号、CVV | PCI DSS 違反 |
| **機微な個人情報** | マイナンバー、健康情報、パスワードリセット用の回答 | 法令（個人情報保護法、GDPR）の対象 |
| **個人を特定できる情報（必要最小限に）** | 氏名、メールアドレス、電話番号、住所 | 保存期間・アクセス権の管理が必要になる |
| **大きなペイロードそのもの** | リクエスト / レスポンスの全文、アップロードファイル | 上記が紛れ込む、コスト増 |

- **「念のためリクエストボディを全部出す」は最も危険**なパターンです。ログイン API のボディにはパスワードが入っています。
- ログ基盤は、アプリ本体の DB より**アクセスできる人が多く、保存期間も長い**ことがよくあります。そこに秘密を書くのは、鍵を掲示板に貼るのと同じです。

## 3. 伏せ方（マスキング・墨消し）

### 3.1 ロガーで自動的に伏せる

```ts
const logger = pino({
  redact: {
    paths: [
      "req.headers.authorization",
      "req.headers.cookie",
      "*.password",
      "*.token",
      "*.cardNumber",
    ],
    censor: "[REDACTED]",
  },
});
```

### 3.2 方針

| 方法 | 使いどころ |
|------|------------|
| **出さない（許可リスト方式）** | 最も安全。ログに出すフィールドを明示的に選ぶ |
| **伏せる（redact）** | ヘッダーやオブジェクトを丸ごと出すとき |
| **部分表示** | カード番号の下 4 桁、メールの `t***@example.com` |
| **ハッシュ化** | 同一人物かどうかだけ分かればよいとき（ソルト付き） |
| **ID で参照** | メールアドレスではなく `user_id` を出し、必要なら DB で引く |

- **拒否リスト（伏せる項目を列挙）より、許可リスト（出す項目を列挙）** のほうが漏れにくいです。新しいフィールドが追加されても勝手に出ません。
- IP アドレスは、GDPR では個人データとして扱われます。保存期間を短くする、下位ビットを落とすといった配慮を検討します。

## 4. ログ自体を守る

| 対策 | 内容 |
|------|------|
| **ログインジェクション対策** | ユーザー入力の改行や制御文字をエスケープする。構造化ログ（JSON）ならライブラリが処理してくれる |
| **アクセス制御** | ログ基盤の閲覧権限を絞る。本番ログを誰でも見られる状態にしない |
| **改ざん防止** | 監査ログは追記専用のストレージに送る |
| **保存期間** | 用途ごとに決める（調査用 30 日、監査用 1 年など）。長く持つほどリスクとコストが増える |
| **ログが出ないことの検知** | ログ送信が止まったらアラートする（攻撃者はまずログを止める） |

---

## 5. 監査ログとアプリログを分ける

| 種類 | 目的 | 特徴 |
|------|------|------|
| **アプリログ** | 障害調査・デバッグ | 量が多い、保存期間は短め、サンプリングしてよい |
| **監査ログ** | 誰がいつ何をしたかの証跡 | 欠けてはいけない、改ざん防止、長期保存 |
| **セキュリティログ** | 攻撃の検知 | SIEM に送って相関分析する（71_セキュリティ基礎/50） |

同じロガーから出しても、**フィールド（`log.type: audit`）や送り先を分けて**扱いを変えます。

---

## 6. チェックリスト

- [ ] ログイン・決済などの API で、ボディをそのまま出していない
- [ ] `Authorization` / `Cookie` ヘッダーが伏せられている
- [ ] 例外メッセージに接続文字列やトークンが含まれていないか確認した
- [ ] ユーザーは ID で記録し、メールアドレスや氏名は出していない
- [ ] ログ基盤の閲覧権限と保存期間が決まっている
- [ ] 認証・認可の失敗が記録されている
