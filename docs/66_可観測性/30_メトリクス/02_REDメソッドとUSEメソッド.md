# REDメソッドとUSEメソッド

「どのメトリクスを取ればいいか」に答える代表的な型が、**RED メソッド**（Tom Wilkie）と **USE メソッド**（Brendan Gregg）です。RED は**サービス（リクエストを処理するもの）**、USE は**リソース（CPU・メモリ・ディスクなど）** を見るための型で、両方を組み合わせるとシステム全体を漏れなく見られます。この章では、それぞれの中身と Web アプリへの当てはめ方を整理します。

---

## 1. 2つの型の比較

| | **RED** | **USE** |
|---|---------|---------|
| 提唱者 | Tom Wilkie（Weaveworks → Grafana Labs） | Brendan Gregg（『Systems Performance』） |
| 対象 | サービス、エンドポイント、マイクロサービス | ハードウェア・OS のリソース、プール、キュー |
| 視点 | **ユーザーから見た体験** | **システムの内側の余裕** |
| 指標 | Rate / Errors / Duration | Utilization / Saturation / Errors |
| 答える問い | ユーザーは困っているか？ | どのリソースがボトルネックか？ |

Google SRE 本のゴールデンシグナル（[[03_ゴールデンシグナル]]）は、RED にサチュレーションを足したもの、と捉えられます。

---

## 2. RED メソッド

| 指標 | 意味 | PromQL の例 |
|------|------|-------------|
| **Rate** | 1 秒あたりのリクエスト数 | `sum by (route) (rate(http_requests_total[5m]))` |
| **Errors** | 失敗したリクエスト数（または割合） | `sum by (route) (rate(http_requests_total{status=~"5.."}[5m]))` |
| **Duration** | 処理時間の分布 | `histogram_quantile(0.99, sum by (le, route) (rate(http_request_duration_seconds_bucket[5m])))` |

- **すべてのサービスで同じ 3 つを、同じ名前で**出すのが RED の強みです。ダッシュボードをテンプレート化でき、知らないサービスでも見方が分かります。
- 1 つのヒストグラム `http_request_duration_seconds`（ラベル `route`、`status`）があれば、R・E・D の 3 つがすべて計算できます（[[01_メトリクスの種類（カウンタ・ゲージ・ヒストグラム）]]）。
- HTTP だけでなく、**外部 API 呼び出し、DB クエリ、キューのコンシューマー**にも同じ型を当てはめられます。

```ts
// 外部 API 呼び出しにも RED を
const outbound = new client.Histogram({
  name: "http_client_request_duration_seconds",
  labelNames: ["peer", "status"],   // peer = "stripe" など
  buckets: [0.1, 0.25, 0.5, 1, 2.5, 5],
});
```

## 3. USE メソッド

Brendan Gregg は「**すべてのリソースについて、使用率・飽和度・エラーを確認せよ**」と述べています。

| 指標 | 意味 | CPU の例 | DB コネクションプールの例 |
|------|------|----------|---------------------------|
| **Utilization** | リソースが忙しかった時間の割合 / 使用中の割合 | CPU 使用率 | 使用中 / 最大 |
| **Saturation** | 処理しきれず待たされている量 | ランキューの長さ、ロードアベレージ | コネクション待ちのリクエスト数 |
| **Errors** | エラーの件数 | （ハードウェアエラー） | 取得タイムアウトの件数 |

### Web アプリで USE を当てはめるリソース

| リソース | Utilization | Saturation | Errors |
|----------|-------------|------------|--------|
| CPU | 使用率 | ロードアベレージ、スロットリング（コンテナ） | — |
| メモリ | 使用量 / 上限 | スワップ、GC 時間、OOM Kill | OOM の回数 |
| ディスク | I/O 使用率 | I/O 待ち行列 | I/O エラー |
| ネットワーク | 帯域使用率 | 再送、ドロップ | インターフェースのエラー |
| Node.js イベントループ | イベントループ使用率（ELU） | イベントループ遅延 | — |
| DB コネクションプール | 使用中の割合 | 待ち行列の長さ | 取得タイムアウト |
| スレッドプール / ワーカー | 稼働中の割合 | 待ちタスク数 | 拒否されたタスク |

- **Saturation が一番見落とされやすく、一番役に立つ**指標です。Utilization が 60% でも、瞬間的に詰まって待ちが発生していることがあります。
- 性能問題の調査手順としての USE の使い方は 67_パフォーマンス で扱います。

## 4. 組み合わせ方

```text
ユーザーが困っている？ ── RED を見る（サービス単位）
      │ はい
      ▼
どのサービス・どのエンドポイント？ ── RED をラベルで分解
      │
      ▼
なぜ遅い / 失敗する？ ── そのサービスが使うリソースの USE を見る
      │                  （CPU 飽和？ コネクションプール枯渇？）
      ▼
さらに詳細 ── トレース・ログ・プロファイル
```

| 用途 | 使う型 |
|------|--------|
| アラート（ページング） | RED（症状）→ SLO 化する |
| 容量計画・予兆検知 | USE（Saturation の傾向） |
| 原因調査 | RED で場所を特定 → USE で原因リソースを特定 |

---

## 5. ダッシュボードへの落とし込み

- **サービスごとの RED ダッシュボード**：上段に Rate / Errors / Duration の 3 グラフ、下段にエンドポイント別の内訳。
- **インフラの USE ダッシュボード**：ノード・コンテナ・DB ごとに U / S / E を並べる。
- 両方を同じ時間軸で見比べられるようにしておくと、「レイテンシが上がった時刻にコネクション待ちが増えた」のような相関がすぐ分かります（60_SLO・アラート / 05_ダッシュボード設計）。
