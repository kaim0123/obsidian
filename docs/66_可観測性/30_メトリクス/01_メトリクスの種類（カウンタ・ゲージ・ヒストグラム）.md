# メトリクスの種類（カウンタ・ゲージ・ヒストグラム）

**メトリクス** は、ある時点の数値を時系列で記録したものです。Prometheus や OpenTelemetry では、数値の性質に応じて **カウンタ・ゲージ・ヒストグラム**（Prometheus ではさらに **サマリー**）という型を使い分けます。型を間違えると、正しいグラフもアラートも作れません。この章では、それぞれの型の意味と、Node.js（prom-client）での書き方を整理します。

---

## 1. メトリクスの構造

```text
http_requests_total{method="POST", route="/checkout", status="200"}  15234  @1727345703
└─ 名前 ──────────┘ └─ ラベル（次元）─────────────────────────────┘  └ 値 ┘  └ 時刻 ┘
```

- **名前 + ラベルの組み合わせ** 1 つが、1 本の時系列になります。
- ラベルの組み合わせが増えるほど時系列が増え、コストが増えます（[[03_カーディナリティ問題]]）。

---

## 2. 4つの型

| 型 | 値の動き | 例 | よく使う関数（PromQL） |
|----|----------|----|------------------------|
| **カウンタ（Counter）** | 増えるだけ（再起動で 0 に戻る） | リクエスト数、エラー数、送信バイト数 | `rate()`、`increase()` |
| **ゲージ（Gauge）** | 上下する | 使用中のコネクション数、メモリ使用量、キューの長さ | そのまま、`avg_over_time()` |
| **ヒストグラム（Histogram）** | 値をバケット（区間）ごとに数える | レイテンシ、レスポンスサイズ | `histogram_quantile()` |
| **サマリー（Summary）** | クライアント側でパーセンタイルを計算 | レイテンシ（古い方式） | そのまま |

---

## 3. カウンタ

```ts
import client from "prom-client";

const httpRequests = new client.Counter({
  name: "http_requests_total",
  help: "HTTP リクエスト数",
  labelNames: ["method", "route", "status"],
});

httpRequests.inc({ method: "POST", route: "/checkout", status: "200" });
```

- **生の値そのものには意味がない**ことに注意します。「起動してから 15234 回」は、いつ再起動したかで変わります。
- 必ず `rate()`（1 秒あたりの増加率）や `increase()`（期間中の増加量）で使います。これらはカウンタのリセットを自動で補正してくれます。

```promql
sum by (route) (rate(http_requests_total[5m]))        # ルートごとの RPS
```

- 命名規則：カウンタは `_total` で終わらせます（Prometheus の慣習）。

---

## 4. ゲージ

```ts
const dbPoolInUse = new client.Gauge({
  name: "db_pool_connections_in_use",
  help: "使用中の DB コネクション数",
});

dbPoolInUse.set(pool.totalCount - pool.idleCount);
```

- 「今いくつか」を表します。**値そのものに意味がある**のがカウンタとの違いです。
- `rate()` をゲージに使うのは誤りです（増減の向きが意味を持たないため）。変化を見たいなら `deriv()` や `delta()` を使います。
- 「一瞬だけ跳ねた値」はスクレイプ間隔の間に見逃すことがあります。見逃したくない量はカウンタで数えるほうが確実です。

---

## 5. ヒストグラム

```ts
const httpDuration = new client.Histogram({
  name: "http_request_duration_seconds",
  help: "HTTP リクエストの処理時間",
  labelNames: ["method", "route", "status"],
  buckets: [0.05, 0.1, 0.25, 0.5, 1, 2.5, 5],
});

const end = httpDuration.startTimer({ method: "POST", route: "/checkout" });
// ... 処理 ...
end({ status: "200" });
```

内部では次のような時系列ができます。

```text
http_request_duration_seconds_bucket{le="0.1"}   8120   ← 0.1 秒以下の件数（累積）
http_request_duration_seconds_bucket{le="0.5"}   9870
http_request_duration_seconds_bucket{le="+Inf"} 10000
http_request_duration_seconds_sum               812.4   ← 合計時間
http_request_duration_seconds_count             10000   ← 件数
```

- `_count` はカウンタとしても使えるので、**1 つのヒストグラムでリクエスト数と平均とパーセンタイルが全部取れます**。
- **バケットの境界の選び方**が精度を決めます。SLO の閾値（例：300ms）をバケットの境界に含めておくと、「300ms 以内の割合」が正確に計算できます（[[04_パーセンタイルとヒストグラムの集計]]）。
- 単位は**秒**で統一するのが Prometheus の慣習です（`_seconds`）。

---

## 6. ヒストグラムとサマリーの違い

Prometheus のドキュメント「Histograms and summaries」の要点です。

| 観点 | ヒストグラム | サマリー |
|------|--------------|----------|
| パーセンタイルの計算場所 | サーバー側（クエリ時） | クライアント側（アプリ内） |
| **複数インスタンスの集約** | **できる** | **できない**（p99 の平均は p99 ではない） |
| 精度 | バケット境界に依存 | 設定した誤差の範囲で正確 |
| 後から分位点を変える | できる | できない |

- 複数の Pod で動かすのが普通の今、**基本はヒストグラム**を選びます。
- 最近は、バケットを自動で細かく持つ **ネイティブヒストグラム**（Prometheus）や **指数ヒストグラム**（OpenTelemetry）も使えるようになり、境界を悩む必要が減っています。

---

## 7. OpenTelemetry の計器との対応

| OpenTelemetry | Prometheus での対応 |
|---------------|---------------------|
| Counter | Counter |
| UpDownCounter | Gauge（増減する累計） |
| Gauge / ObservableGauge | Gauge |
| Histogram | Histogram |

OpenTelemetry で計装し、Prometheus 形式で出力することもできます（50_計装・OpenTelemetry）。
