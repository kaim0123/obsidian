# パーセンタイルとヒストグラムの集計

レイテンシを **平均** で見ると、ユーザー体験を見誤ります。可観測性では **パーセンタイル（p50 / p95 / p99）** で見るのが基本ですが、パーセンタイルは足し算や平均ができないという落とし穴があり、集計のしかたを間違えると「それらしいけれど間違った数字」が出てきます。この章では、パーセンタイルの読み方と、ヒストグラムから正しく計算する方法を整理します。

---

## 1. なぜ平均ではだめか

100 件のリクエストのうち、99 件が 100ms、1 件が 10 秒だったとします。

| 指標 | 値 | 読み取れること |
|------|----|----------------|
| 平均 | 約 199ms | 「まあ速い」ように見える |
| p50（中央値） | 100ms | 典型的なユーザーの体験 |
| p99 | 10 秒 | **100 人に 1 人はひどく待たされている** |

- レイテンシの分布は**右に長い裾**を持つのが普通で、平均は少数の外れ値に引っ張られつつ、その外れ値の存在は隠してしまいます。
- ユーザーは 1 ページで何十回も API を呼びます。**1 回の p99 は、ページ単位では頻繁に当たる**ため、裾（テールレイテンシ）が体験を左右します（Jeff Dean「The Tail at Scale」）。

---

## 2. パーセンタイルの読み方

| 表記 | 意味 | 使いどころ |
|------|------|------------|
| **p50** | 半分のリクエストがこれ以下 | 典型的な体験 |
| **p90 / p95** | 90% / 95% がこれ以下 | 多くのユーザーの上限 |
| **p99** | 99% がこれ以下 | 裾の体験、SLO によく使う |
| **p99.9** | 1000 件に 1 件の遅さ | 大規模サービス、重要 API |
| **max** | 最悪の 1 件 | 外れ値の確認（ノイズが多い） |

- **件数が少ないと高いパーセンタイルは信用できません**。1 分に 50 件しかない API の p99 は、実質「最大値」です。
- Web Vitals（LCP など）は **p75** を評価基準にしています（67_パフォーマンス）。

---

## 3. パーセンタイルは平均できない

**よくある間違い**

```promql
# ✗ Pod ごとの p99 を平均している（サマリーを使った場合など）
avg(http_request_duration_seconds{quantile="0.99"})
```

Pod A の p99 が 100ms、Pod B の p99 が 2 秒でも、平均の 1.05 秒は**全体の p99 ではありません**。全体の p99 を出すには、**元の分布（件数）を合算してから**パーセンタイルを計算する必要があります。これがヒストグラムを使う理由です（[[01_メトリクスの種類（カウンタ・ゲージ・ヒストグラム）]]）。

**正しい集計**

```promql
# ✓ 全 Pod のバケットを合算してから p99 を計算
histogram_quantile(0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

# ✓ ルートごとの p99（le は必ず残す）
histogram_quantile(0.99,
  sum by (le, route) (rate(http_request_duration_seconds_bucket[5m])))
```

- `sum by (...)` に **`le` を必ず含める**のがポイントです。落とすとバケットが潰れて計算できません。
- 同じ理由で、「1 分ごとの p99 を 1 時間分平均する」のも誤りです。長い期間の p99 が欲しいなら、`rate(...[1h])` のように**期間を広げて計算し直します**。

---

## 4. ヒストグラムの精度

`histogram_quantile` は、バケットの中では値が均等に分布していると仮定して**線形補間**します。

```text
バケット: le=0.25 → 9500件, le=0.5 → 9900件, le=1 → 10000件
p99 = 9900件目 → ちょうど 0.5 秒の境界
p99.5 = 9950件目 → 0.5〜1 秒のバケットの中間あたり → 約 0.75 秒と推定
```

- **バケットの幅が広いと誤差が大きく**なります。上の例で本当の p99.5 が 0.52 秒でも 0.75 秒と出るかもしれません。
- 対策：
  - **よく見る範囲（SLO の閾値付近）を細かく**区切る
  - SLO の閾値そのもの（例：0.3 秒）を境界に入れる
  - ネイティブヒストグラム（Prometheus）・指数ヒストグラム（OpenTelemetry）を使い、バケットを自動で細かくする

---

## 5. パーセンタイルより「閾値以内の割合」

SLO では、パーセンタイルより **「300ms 以内に返ったリクエストの割合」** のほうが扱いやすいことが多いです。

```promql
# 300ms 以内の割合（le="0.3" のバケットが必要）
sum(rate(http_request_duration_seconds_bucket{le="0.3"}[5m]))
  / sum(rate(http_request_duration_seconds_count[5m]))
```

| 観点 | p99 | 閾値以内の割合 |
|------|-----|----------------|
| 精度 | バケットで補間（誤差あり） | 境界が合っていれば**正確** |
| 期間・インスタンスの合算 | 分布の合算が必要 | 件数の割り算なので**簡単** |
| エラーバジェットとの相性 | 変換が必要 | そのまま「良いイベントの割合」になる |

この考え方は 60_SLO・アラート で SLI の設計に使います（[[01_SLI・SLOの設計]]）。

---

## 6. グラフで気をつけること

- **平均と p99 を同じグラフに並べる**と、裾の広がりがひと目で分かります。
- **ヒートマップ**でバケットごとの件数を色で表すと、「二山の分布」（キャッシュヒットとミスなど）が見えます。平均やパーセンタイルでは見えない形です。
- 成功と失敗のレイテンシは**分けて**表示します（[[03_ゴールデンシグナル]]）。
