# サンプリング戦略

トレースは 1 リクエストあたり数十個のスパンを生むため、すべて保存すると**ストレージ費用とネットワーク負荷**が急増します。そこで一部のトレースだけを残す **サンプリング** を行います。難しいのは「**ほとんどのリクエストは捨ててよいが、エラーと遅いリクエストだけは確実に残したい**」という要求です。この章では、ヘッドサンプリングとテールサンプリングの違いと、実務での組み合わせ方を整理します。

---

## 1. なぜサンプリングが必要か

| 規模 | 例 | 全件保存すると |
|------|----|----------------|
| 1,000 req/s、1 リクエスト 20 スパン | 20,000 スパン/秒 | 1 日で約 17 億スパン。SaaS なら月に数百万円規模になることもある |

- 正常で速いリクエストのトレースは、**ほとんど同じ形**をしています。1% 残せば傾向は十分に分かります。
- 一方、**エラーや p99 の遅いリクエストは数が少なく、調査で一番見たいもの**です。単純な確率サンプリングでは、これらも 99% 捨ててしまいます。
- 集計値（エラー率・レイテンシの分布）はトレースからではなく**メトリクスから**取るのが原則です。サンプリングされたトレースから率を計算すると、サンプリング率の分だけ補正が必要になります（[[01_メトリクスの種類（カウンタ・ゲージ・ヒストグラム）]]）。

---

## 2. ヘッドサンプリング

**リクエストの最初（ルートスパンを作る時点）で残すかどうかを決める**方式です。決定は `traceparent` の sampled フラグで下流に伝わり、下流も同じ判断に従います（[[02_トレースコンテキストの伝播]]）。

| サンプラー（OTel SDK） | 動き |
|------------------------|------|
| `AlwaysOn` | すべて残す（開発環境向け） |
| `AlwaysOff` | すべて捨てる |
| `TraceIdRatioBased(0.1)` | trace_id のハッシュで 10% を残す。同じ trace_id なら必ず同じ判定になる |
| `ParentBased(root=…)` | **親があれば親の判断に従う**。親がないとき（ルート）だけ root サンプラーで決める |

```bash
# 環境変数で設定（OpenTelemetry SDK 共通）
OTEL_TRACES_SAMPLER=parentbased_traceidratio
OTEL_TRACES_SAMPLER_ARG=0.1
```

- **`ParentBased` を必ず使う**のが基本です。サービスごとにバラバラに判定すると、トレースの途中のスパンだけが欠ける「虫食いトレース」になります。
- **長所**：軽い。捨てるスパンはそもそも作らない（記録しない）ので、アプリの負荷も下がる。
- **短所**：開始時点では**結果（エラーか、遅いか）が分からない**。珍しいエラーを取りこぼす。

---

## 3. テールサンプリング

**トレースが終わってから、全体を見て残すかどうかを決める**方式です。アプリ側では全スパンを送り、**OTel Collector**（またはベンダーのバックエンド）が一定時間スパンを溜めてから判断します（[[03_OTel_Collector]]）。

```yaml
# OTel Collector の tail_sampling プロセッサ（contrib ディストリビューション）
processors:
  tail_sampling:
    decision_wait: 10s          # トレースの全スパンが揃うのを待つ時間
    num_traces: 100000          # メモリに保持するトレース数
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: slow
        type: latency
        latency: { threshold_ms: 1000 }
      - name: premium-users
        type: string_attribute
        string_attribute: { key: user.tier, values: [premium] }
      - name: baseline
        type: probabilistic
        probabilistic: { sampling_percentage: 5 }
```

ポリシーは **OR 条件**で評価され、どれか 1 つに当たれば残ります。この例では「エラー全件 + 1 秒以上全件 + プレミアム会員全件 + それ以外の 5%」を残します。

| 長所 | 短所 |
|------|------|
| エラー・遅延を**確実に**残せる | アプリは全スパンを送るので、ネットワークと Collector の負荷が高い |
| 業務属性で柔軟に決められる | 同じトレースのスパンを**同じ Collector インスタンスに集める**必要がある（`loadbalancing` exporter で trace_id ごとに振り分ける 2 段構成） |
| | `decision_wait` を過ぎて届いたスパンは判定に間に合わない |

## 4. 方式の比較と選び方

| 観点 | ヘッド | テール |
|------|--------|--------|
| 判断のタイミング | 開始時 | 終了後 |
| エラー・遅延の取りこぼし | あり | なし（ポリシー次第） |
| アプリの負荷 | 小 | 中（全スパンを送る） |
| インフラの複雑さ | 低 | 高（Collector のスケーリング・振り分けが必要） |
| 向いている規模 | 小〜中規模、まず始めるとき | 中〜大規模、トレースで障害調査をする文化があるとき |

**実務でよくある組み合わせ**

1. **最初は ParentBased + TraceIdRatio（10〜100%）** で始める。トラフィックが少ないうちは 100% でもよい。
2. 費用が問題になったら、**ヘッドで 20〜50% に落としつつ、テールでエラーと遅延を全件残し、正常系はさらに間引く**。
3. サービスごとに重要度が違うなら、決済などの重要サービスだけ率を上げる（ルートでの判断なので、入口のサービスで経路ごとに率を変える）。

## 5. サンプリングとメトリクスの関係

- トレースからメトリクス（RED）を作る **spanmetrics コネクタ**（Collector）や、バックエンドの「トレースから生成したメトリクス」は、**サンプリングの前**で計算しないと値が過小になります。
- **エグザンプラー（Exemplar）** を使うと、メトリクスのヒストグラムのバケットに「代表的な trace_id」を添えられます。グラフのスパイクから、実際に残っているトレースへ直接飛べます（[[04_ログ・メトリクス・トレースの相関]]）。
- ログはサンプリングしないことが多いので、「ログにはあるがトレースは捨てられた」ことが起きます。ログの trace_id で検索して見つからなければ、サンプリングで落ちた可能性を疑います。
