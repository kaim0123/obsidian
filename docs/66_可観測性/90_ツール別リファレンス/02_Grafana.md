# Grafana

**Grafana** は、さまざまなデータソースのメトリクス・ログ・トレースを 1 つの画面で可視化するオープンソースのツールです。自分ではデータを持たず、Prometheus や Loki、CloudWatch などに問い合わせて表示します。Grafana Labs はログの **Loki**、トレースの **Tempo**、メトリクスの **Mimir** も開発しており、これらを合わせて **LGTM スタック**と呼びます。この章では、Grafana の主な機能と LGTM スタックの構成をまとめます（Grafana 公式ドキュメントが下敷き）。

---

## 1. Grafana の位置づけ

```
            ┌──────────── Grafana（可視化・アラート・探索）────────────┐
            │                    │                    │                  │
       [Prometheus/Mimir]   [Loki]             [Tempo]          [CloudWatch / PostgreSQL / ...]
        メトリクス           ログ               トレース          その他のデータソース
```

| 特徴 | 意味 |
|------|------|
| **データソース非依存** | 100 以上のデータソースに対応。複数のソースを 1 枚のダッシュボードに並べられる |
| **データを持たない** | 保存は各バックエンドの仕事。Grafana 自体は設定とダッシュボードだけを持つ |
| **OSS とクラウド** | 自前で動かすか、Grafana Cloud（マネージド）を使うか選べる |

---

## 2. 主な機能

| 機能 | 用途 |
|------|------|
| **ダッシュボード** | パネル（時系列・Stat・表・ヒートマップなど）を並べた画面。変数でサービスや環境を切り替え |
| **Explore** | ダッシュボードを作らずにクエリを試す画面。障害調査でよく使う |
| **Grafana Alerting** | Prometheus 以外のデータソースも対象にしたアラート。通知先の管理（Contact points） |
| **アノテーション** | デプロイや障害の時刻をグラフに縦線で表示 |
| **データリンク** | パネルの点をクリックして別ダッシュボード・ログ・トレースへ移動 |
| **プロビジョニング** | データソースやダッシュボードをファイルから自動設定（[[05_ダッシュボード設計]]） |

---

## 3. LGTM スタック

| 文字 | ツール | 扱うデータ | 特徴 |
|------|--------|------------|------|
| **L** | **Loki** | ログ | 本文にインデックスを張らず、**ラベルだけ**にインデックス。安く大量に保存できる |
| **G** | **Grafana** | 可視化 | すべての入口 |
| **T** | **Tempo** | トレース | トレース ID での検索に特化。オブジェクトストレージに保存して安い（[[03_Jaeger・Tempo]]） |
| **M** | **Mimir** | メトリクス | Prometheus 互換の水平スケール型ストレージ（[[01_Prometheus]]） |

加えて、プロファイル（CPU・メモリの使い方）を扱う **Pyroscope**、収集エージェントの **Grafana Alloy**（OTel Collector 互換）があります。

### Loki のクエリ（LogQL）

```logql
# api サービスの error ログ
{service="api", env="prod"} |= "error"

# JSON ログを解析して、status が 500 のものだけ
{service="api"} | json | status = 500

# 1 分あたりのエラーログ件数（ログからメトリクスを作る）
sum(count_over_time({service="api"} | json | level="error" [1m]))
```

- Loki は**ラベルで絞ってから本文を検索する**設計。ラベルを増やしすぎると Prometheus と同じくカーディナリティ問題が起きる（[[03_カーディナリティ問題]]）
- ログの設計は [[01_構造化ログ]]・[[04_ログ集約基盤]] を参照

## 4. シグナル間の移動（相関）

Grafana の強みは、メトリクス → トレース → ログを**クリックで行き来できる**ことです。

| 移動 | 仕組み |
|------|--------|
| メトリクス → トレース | **Exemplar**：ヒストグラムの点にトレース ID を付けておき、遅いリクエストのトレースに飛ぶ |
| トレース → ログ | Tempo の設定で、スパンの `trace_id` を使って Loki を検索 |
| ログ → トレース | Loki の **Derived fields**：ログ中の `trace_id` をリンクにする |
| トレース → メトリクス | スパンから RED メトリクスを生成（Tempo の metrics-generator） |

```yaml
# データソースのプロビジョニング例（Loki のログから Tempo へリンク）
apiVersion: 1
datasources:
  - name: Loki
    type: loki
    url: http://loki:3100
    jsonData:
      derivedFields:
        - name: TraceID
          matcherRegex: '"trace_id":"(\w+)"'
          url: "$${__value.raw}"
          datasourceUid: tempo
```

詳しくは [[04_ログ・メトリクス・トレースの相関]] を参照してください。

## 5. 導入の進め方

1. Prometheus をデータソースに追加し、公式やコミュニティのダッシュボード（Node Exporter Full など）を読み込んで動作確認
2. 自分のサービスの RED ダッシュボードを作る（[[05_ダッシュボード設計]]）
3. Loki を足してログを同じ画面で見られるようにする
4. OpenTelemetry でトレースを Tempo に送り、相関リンクを設定する
5. ダッシュボードとデータソースをコード化して Git 管理に移す
