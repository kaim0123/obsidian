# セキュアバイデザイン（Secure by Design）

## はじめに

**セキュアバイデザイン**（Secure by Design）とは、

> **「設計段階からセキュリティを組み込む」**

という開発哲学です。**後からセキュリティを追加するのではなく**、最初から安全な設計を前提にします。

似た概念に **セキュア・バイ・デフォルト**（Secure by Default: 初期設定が安全）があり、両者は合わせて使われます。

### 一言でいうと

> 「**セキュリティは"後付け"ではなく"仕様"**」

---

## なぜ「設計段階で」必要なのか

### 1. 後から直すのは高コスト

ソフトウェア開発では、**バグは発見が遅れるほど修正コストが指数関数的に増える**（IBM System Science Institute のデータ）:

| 発見タイミング | 修正コスト（相対値） |
|--------------|---------------------|
| 設計段階 | 1 |
| コーディング段階 | 5〜6倍 |
| テスト段階 | 10倍 |
| 本番リリース後 | 30〜100倍 |

セキュリティ欠陥も同じ。設計の欠陥は、コードで後付けしてもほぼ直らず、**作り直し** になります。

### 2. コードのバグではなく「設計の穴」は実装では防げない

OWASP A04（安全でない設計）で強調されたように、**設計そのものに穴があると、コードをいくら綺麗に書いても防げません**。

例:
- パスワードリセットの本人確認が弱い → コードは完璧でも本質的に脆弱
- 業務ロジックで二重使用ができる → コードのバグではなく仕様の問題

### 3. セキュリティを「機能」として最初から定義する

「ログイン機能を作る」ではなく、「**ログイン + MFA + レート制限 + 監査ログ** を作る」と最初から定義する。これで後付けの漏れがなくなる。

## セキュアバイデザイン の原則（NIST, CISA 提唱）

米国 CISA（Cybersecurity and Infrastructure Security Agency）が2023年に公表したガイダンスから、主要原則を紹介します。

### 1. 製造者（開発者）が責任を負う

「ユーザーが設定を頑張って安全にする」ではなく、**開発者側が安全な状態で提供する**。

### 2. 透明性を保つ

脆弱性情報、パッチ提供状況、サポート終了などを **積極的に公開**。

### 3. Secure by Default を徹底

- 初期状態でセキュリティ機能が **ON**
- 危険な機能は **OFF**（必要な人が明示的に有効化）
- デフォルトパスワード廃止、強いパスワード要求

## 代表的な設計原則（古典）

Saltzer と Schroeder が1975年に提唱した設計原則は、現代でも有効です。

### 1. Economy of Mechanism（機構の経済性）

設計はシンプルに。複雑なセキュリティ機構はバグを生む。

### 2. Fail-safe Defaults（フェイルセーフなデフォルト）

デフォルトは **拒否**。許可は明示的に。

```python
# ❌ 悪い: デフォルトで許可
if is_blocked(user): return deny()
return allow()  # 例外的なcaseを見落とすと悪用される

# ✅ 良い: デフォルトで拒否
if is_allowed(user): return allow()
return deny()  # 知らない状態は安全側
```

### 3. Complete Mediation（完全な媒介）

**すべての** アクセスを毎回チェック。キャッシュしない（またはキャッシュ失効を慎重に管理）。

### 4. Open Design（オープンデザイン）

**仕組みを公開しても安全** であるべき。「隠蔽による安全」（security through obscurity）は脆い。

### 5. Separation of Privilege（特権の分離）

重要操作に **複数の条件** を要求する。MFA、承認フロー、分割鍵など。

### 6. Least Privilege（最小権限）

`最小権限の原則.md` 参照。

### 7. Least Common Mechanism（共通機構の最小化）

ユーザー間で共有するリソースを最小化。共有は攻撃経路になる。

### 8. Psychological Acceptability（心理的受容性）

ユーザーが使いやすくないと、回避されて無意味。**使いやすい安全** を目指す。

### 9. Work Factor（作業係数）

攻撃のコストを、それによって守る資産の価値より大きくする。

### 10. Compromise Recording（侵害の記録）

侵害時に **ログで追跡可能** にする（予防が無理でも、検知はできる）。

## セキュア・バイ・デフォルト の例

### ❌ よくある悪い例

- データベース: 初期パスワード `admin / admin`
- ルーター: `admin / 1234` のまま出荷
- 新規作成したバケット: パブリックアクセス可能
- メッセージングアプリ: 通信暗号化は設定画面で有効化が必要

### ✅ 良い例

- **bitwarden** などのパスワードマネージャ: 強いマスターパスワード必須
- **Signal**: すべてのメッセージが最初からE2E暗号化
- **AWS S3**（現代）: アカウントレベルで Block Public Access が推奨ON
- **iOS**: 最初からフルディスク暗号化、サンドボックス化

## 開発プロセスへの組み込み

### Shift Left（シフトレフト）

開発のライフサイクル（左から右：計画→設計→実装→テスト→運用）で、**セキュリティを早い段階に移動**。

```
計画 → 設計 → 実装 → テスト → 運用
  ↑     ↑
  ここに移動（従来はテスト以降で対応）
```

### セキュアSDLC の活動

| フェーズ | 活動 |
|---------|------|
| **要件定義** | 悪用ケース、セキュリティ要件定義 |
| **設計** | 脅威モデリング、アーキテクチャレビュー |
| **実装** | セキュアコーディング、コードレビュー |
| **ビルド** | SAST、SCA、シークレットスキャン |
| **テスト** | DAST、ペネトレーションテスト |
| **デプロイ** | IaC スキャン、コンテナスキャン |
| **運用** | WAF、監視、インシデント対応 |
| **改善** | ポストモーテム、教訓の反映 |

### DevSecOps

CI/CDパイプラインに **自動セキュリティチェック** を組み込む。

```yaml
# 例: GitHub Actions
- name: SAST
  uses: github/codeql-action/analyze@v3

- name: Dependency scan
  run: npm audit --audit-level=high

- name: Secret scan
  uses: trufflesecurity/trufflehog@main

- name: Container scan
  run: trivy image myapp:latest
```

## 設計時に自問すべきこと

新機能を設計するとき、以下を必ず考えます。

### 入力について

- どこから入力が来るか？
- 信頼できるか？ できないならどう検証？
- サイズ、型、形式の制限は？
- ホワイトリスト型の検証か？

### 認証・認可について

- 誰がアクセスできる機能か？
- 所有権チェックは？
- 特権操作には追加の認証を要求するか？
- セッションタイムアウトは？

### データについて

- どんな機密性のデータを扱うか？
- 暗号化は？（転送中・保存中）
- ログに機密情報が出ないか？
- 保管期間と削除ポリシーは？

### エラーと例外

- エラー時、どこに何を出すか？
- 内部情報が漏れていないか？
- 攻撃の痕跡がログに残るか？

### 悪用シナリオ

- どんな悪用があり得るか？
- 並列・二重実行に耐えるか？
- レート制限は必要か？

### 依存関係

- 外部ライブラリは安全か？ 更新は？
- 外部APIを信頼しすぎていないか？
- サプライチェーンリスクは？

## OWASP との関係

OWASP Top 10 2021 版で **A04 安全でない設計** が新設されたのは、この考え方の重要性を示しています。

セキュアバイデザインは、OWASP 全項目の **予防策** として機能します。

- A01〜A10 のどれも、設計時に考慮していれば防げたケースが多数

## まとめ

- セキュアバイデザインは **「設計段階から安全を組み込む」** 哲学
- **後付けは高コスト**。設計での欠陥はコードで防げない
- **Secure by Default**（安全が初期設定）も合わせて徹底
- Saltzer/Schroeder の古典原則は現代でも有効
- **シフトレフト** と **DevSecOps** で開発プロセスに組み込む
- 脅威モデリング・最小権限・深層防御・ゼロトラストと連携して実現
