# 深層防御（Defense in Depth）

## はじめに

**深層防御**（Defense in Depth）とは、

> **「1つの防御が破られても、次の防御層で止める」**

ために、**複数のセキュリティ対策を多層的に重ねる** 考え方です。もともとは軍事用語で、城の **外堀 → 城壁 → 内堀 → 天守閣** のような多層防御をイメージすると分かりやすいです。

### 一言でいうと

> 「**卵は一つのカゴに盛るな**」

単一の防御策に依存せず、複数の層で守ります。

---

## なぜ必要なのか

### 1. 完璧な防御は存在しない

どんな強固な対策も、いつか破られる可能性があります。

- 新たな脆弱性（ゼロデイ）が発見される
- 設定ミスで無効化されている
- 人的ミスで認証情報が漏れる
- 予期しない攻撃手法が登場する

### 2. 攻撃者を遅らせ、コストを上げる

**破るのに何層も突破が必要** なら、攻撃者は:
- 時間がかかる → 検知される可能性が上がる
- コストが嵩む → 他の標的に移る
- ミスをする → 防御側が気付ける

### 3. 検知と対応の時間を稼ぐ

突破される間に **異常を検知** し、**対応できる時間** を確保できます。

---

## 「多層」の例: Webアプリ

1つの目標「DBの顧客情報を盗む」に対して、複数の防御層を重ねます。

```
【7】監査ログと異常検知
  ↑ 侵入されても検知してアラート

【6】DB自体の暗号化（At Rest）
  ↑ ファイルごと盗まれても読めない

【5】DBユーザーの最小権限
  ↑ 侵入されても DROP/管理権限なし

【4】ネットワーク隔離（VPC、プライベートサブネット）
  ↑ DBにインターネットから直接アクセス不可

【3】アプリの入力検証・パラメタ化クエリ
  ↑ SQL インジェクションを防ぐ

【2】認証・認可・セッション管理
  ↑ 他人のふりをさせない、権限外を触らせない

【1】WAF / CDN / DDoS対策
  ↑ 明らかに悪意ある通信を入口で遮断

🌐 インターネット（攻撃者）
```

どれか1層だけでは不十分。**すべての層を積んで** 初めて実用的な防御になります。

## 具体的な層の例

### 物理層

- データセンターの入退室管理、監視カメラ
- サーバー機器の施錠
- 廃棄時のディスク破壊

### ネットワーク層

- **ファイアウォール**（入口の交通整理）
- **IDS/IPS**（侵入検知・防止）
- **VPC・セグメンテーション**（内部ネットワーク分割）
- **VPN / ゼロトラストネットワーク**

### ホスト層

- OS パッチの自動適用
- アンチウイルス / EDR
- ホストファイアウォール
- ディスク暗号化

### アプリケーション層

- 入力検証 / 出力エスケープ
- 認証・認可
- セッション管理
- CSRF対策、CSP、セキュリティヘッダー

### データ層

- 転送中の暗号化（TLS）
- 保存中の暗号化
- 機密フィールドの追加暗号化
- アクセスログ

### 運用・人間層

- セキュリティ教育
- フィッシング訓練
- 最小権限運用
- インシデント対応計画

## 例: ログイン機能の多層防御

1つの機能でも、複数の対策を積みます。

1. **HTTPS** で通信経路を保護（盗聴防止）
2. **CSP** で XSS の影響を制限
3. **強いパスワードポリシー**（漏洩PW禁止、12文字以上）
4. **bcrypt / Argon2** でパスワードハッシュ
5. **レート制限**（IP・アカウント・デバイス）
6. **MFA** で認証情報漏洩に備える
7. **セッションCookie の属性**（HttpOnly, Secure, SameSite）
8. **異常検知**（地理的異常、普段と違うデバイス）
9. **不正ログインアラート** をユーザーに通知
10. **監査ログ** で追跡可能に

1〜3 が甘くても 4〜6 で守れる。4〜6 が破られても 8〜10 で検知できる。これが深層防御。

## アプリ層の多層防御パターン

### 入力 → 処理 → 出力 の各段階で守る

#### 入力時

- 型チェック・範囲チェック
- ホワイトリスト検証
- サイズ制限

#### 処理時

- パラメータ化クエリ
- 認可チェック（所有権含む）
- トランザクション

#### 出力時

- エスケープ（HTML/JS/URL）
- 機密情報のフィルタリング
- ヘッダー設定（X-Content-Type-Options等）

## 深層防御と最小権限の関係

両者は **補完的** に機能します。

- **最小権限**: 侵入された場合の「1層あたりの被害」を小さくする
- **深層防御**: そもそも何層も突破させない

両方合わせて、**侵入確率 × 侵入後の被害** の積を小さくします。

---

## アンチパターン

### 1. 「WAFを入れれば安全」

WAF（Web Application Firewall）は1つの層にすぎません。アプリ内部の対策を怠る言い訳にはならない。

### 2. 「社内ネットだから信頼」

「外からの攻撃にしか備えない」は古い。内部からの攻撃・侵害されたマシンからの横移動にも備える。**ゼロトラスト** 参照。

### 3. 多層ではなく多重

同じ層の対策を3つ重ねても、1つが破られる攻撃には弱いまま。**違う層・違う性質** の対策を組み合わせるのが「深層」防御。

### 4. 層を増やしすぎて運用不能

層が増えすぎて、**誰も全体を把握できない** 状態も問題。管理性とのバランスが必要。

### 5. 最後の砦「人間」を忘れる

どんなに技術対策を積んでも、**フィッシングメール1通で社員が認証情報を渡す** と台無し。教育と訓練も層の1つ。

---

## 層の優先順位（投資の考え方）

すべてを一度に実装するのは無理。優先順位の目安:

1. **コストが低く効果が高い**: HTTPS、セキュリティヘッダー、依存関係更新
2. **設計変更しないと入らない**: 認証・認可・ログ
3. **運用で継続が必要**: パッチ適用、権限棚卸し、監視
4. **高コストだが重要**: WAF、SIEM、セキュリティ運用センター（SOC）

**最も攻撃される層**（通常はアプリ層）から優先的に固める。

---

## 現代の潮流

### ゼロトラスト

「境界防御」だけでは不十分、という考え方。**すべてのアクセスを認証・認可・暗号化** する。深層防御の延長線上にある概念。

### セキュアバイデザイン

設計段階からセキュリティを織り込む。後付けではなく前提。深層防御を **設計の一部** として組み込む。

### プラットフォームセキュリティ

各層を個別に作るのではなく、**プラットフォーム**（クラウド・コンテナ基盤）が複数層をまとめて提供する。例: AWS の VPC + Security Group + WAF + Shield + GuardDuty。

## 2026年の事例から：被害半径（ブラスト・ラジアス）で考える（追記 2026-10-17）

2026年の国内の漏洩事例を分析した記事では、**被害の大きさは「入られたこと」より、侵入後の動きが続いた時間と、届いたデータの量に比例していた** と指摘されています（全体は [[10_2026年_国内情報漏洩の動向と対策]]）。

| 事例 | 侵入〜発覚 |
|---|---|
| アフラック生命 | 15日（CPU 高負荷で発覚） |
| ショップサーブ | 約72日 |
| 両毛システムズ（委託元への通知） | 43日 |
| 米国防総省 DMDC（海外） | 約9か月 |

入口の防御だけでは足りず、**入られたあとの層** が被害を決めます。

| 層 | 役割 | 2026年に足りなかった例 |
|---|---|---|
| 入口 | 脆弱性を塞ぐ | VPN の脆弱性・ゼロデイ（[[07_脆弱性管理（境界機器・パッチ運用）]]） |
| 権限 | 1 つの ID で届く範囲を絞る | 保守アカウントで大量アクセス（[[01_最小権限の原則]]） |
| ネットワーク | 横に広がらないよう分ける | フラットな構成で DB まで到達 |
| データ | 持たない・分ける・暗号化する | 退会者データ・免許証画像の保持（[[05_データ最小化]]） |
| 検知 | 異常な大量取得に気づいて止める | 大量照会の監視不足（[[A09_ログとモニタリングの不備]]） |
| 復旧 | バックアップから戻す | ランサムウェアで長期停止（[[08_ランサムウェア対策]]） |

## まとめ

- 深層防御は **「多層的に、性質の違う防御を重ねる」** 考え方
- **単一対策に依存しない**（WAFさえあれば、HTTPSさえあれば…は誤り）
- **違う層** で **違う性質** の対策を組み合わせる
- 最小権限・ゼロトラストと合わせて、被害を二重三重に限定
- 人間（教育・訓練）も防御層の1つ
- 優先順位は「低コスト・高効果」「設計段階で必要」から
