# ゼロトラスト（Zero Trust）

## はじめに

**ゼロトラスト**（Zero Trust）とは、

> **「何も信頼しない。すべてのアクセスを都度検証する」**

というセキュリティモデルです。2010年に Forrester のアナリスト John Kindervag が提唱し、2020年代に入って急速に主流化しました。

スローガンは:

> **"Never trust, always verify"**（決して信頼せず、常に検証する）

---

## 従来の「境界防御モデル」の限界

### 境界防御 = 城壁モデル

```
┌──────────────────────────┐
│                          │
│   [社内]（信頼）          │
│   ←→ すべて自由           │
│                          │
├──────────────────────────┤
│ [ファイアウォール]        │  ← ここが唯一の検問
├──────────────────────────┤
│                          │
│  [外部]（非信頼）          │
│                          │
└──────────────────────────┘
```

- **入口（境界）で厳しくチェック**
- **一度入れば、社内は自由に動ける**

長い間、これが標準でした。しかし現代では破綻しています。

### なぜ破綻したか

1. **リモートワーク**: 社員は自宅・カフェ・海外から接続。「社内」の境界が消失
2. **クラウド利用**: データはSaaS・クラウドに分散。自社DCに境界を引けない
3. **モバイル端末**: スマホ・私物PCが業務に使われる
4. **サプライチェーン攻撃**: 正規の経路（アップデート等）で侵入される
5. **内部犯・内部侵害**: 一度侵入した攻撃者は「社内=信頼」を悪用して横展開

**「境界の内側だから安全」は、もはや幻想** になりました。

---

## ゼロトラストの考え方

### 核となる原則

1. **すべての通信を認証・認可する**（社内・社外問わず）
2. **最小権限**（必要最小限のアクセスのみ許可）
3. **マイクロセグメンテーション**（内部でも細かく区切る）
4. **常時検証**（一度認証したら終わりではなく、継続的に）
5. **暗号化**（すべての通信を暗号化）
6. **可視化とログ**（全アクティビティを監視・記録）

### アクセスは「動的に判定」

1回のログインだけで判定せず、**アクセスごとに** 以下を総合評価:

- ユーザーは誰か、MFAを通過したか
- 端末は管理されているか、OSは最新か、マルウェア感染していないか
- 場所はどこか（普段と違うか、危険地域か）
- 時間帯は通常業務時間か
- 行動は普段通りか、異常ではないか
- 対象データの機密度はどれくらいか

---

## 従来モデル vs ゼロトラスト

| | 従来（境界防御） | ゼロトラスト |
|---|----------------|-------------|
| 信頼モデル | 内側を信頼 | 誰も信頼しない |
| 認証 | 入口で1回 | アクセスごとに都度 |
| ネットワーク | 内外で分ける | セグメント化 |
| アクセス | 権限を与えたら固定 | 動的・コンテキスト次第 |
| 対象 | 主にユーザー | ユーザー＋デバイス＋ワークロード |
| VPN | 社外からの入口 | 必ずしも必要ない |

## ゼロトラストの代表的な実装要素

### 1. IDaaS（Identity as a Service）

組織のID基盤を統合。認証の中心。

- **Okta、Azure AD（Entra ID）、Google Workspace、Auth0**
- SSO、MFA、条件付きアクセスを提供

### 2. ZTNA（Zero Trust Network Access）

従来のVPNの代替。**アプリケーション単位** でアクセスを制御。

- **Cloudflare Access、Zscaler Private Access、Tailscale、Twingate**
- 「社内ネットワークに入れる」ではなく「このアプリだけ使える」

### 3. デバイス管理（MDM / EDR）

- **Jamf、Intune、Kandji**（MDM）
- **CrowdStrike、SentinelOne**（EDR）
- 端末の健全性を継続的に評価

### 4. マイクロセグメンテーション

ネットワークを **細かく区切る**。侵害されても横展開を防ぐ。

- サービス間通信は mTLS で相互認証
- Kubernetes の NetworkPolicy
- Service Mesh（Istio、Linkerd）

### 5. Policy Decision Point（PDP）

アクセスを判定するポリシーエンジン。

- **Open Policy Agent (OPA)**
- クラウド IAM の条件付きポリシー
- 条件: ユーザー属性 + 端末状態 + リクエスト内容

### 6. 継続的な可視化

- SIEM / UEBA（User and Entity Behavior Analytics）
- 異常行動の検知
- 監査ログの集約

## 実装のステップ（NIST SP 800-207 参照）

### Phase 1: 準備

- 守るべき資産の洗い出し
- データフロー・アクセス経路の把握
- 既存アイデンティティ基盤の評価

### Phase 2: 最小構成のゼロトラスト

- すべてのユーザーに MFA を強制
- SSO 統合
- デバイス管理の導入
- 重要アプリから ZTNA に移行

### Phase 3: 拡張

- マイクロセグメンテーション
- アプリ間通信に mTLS
- ポリシーエンジン導入
- 継続的な行動分析

### Phase 4: 最適化

- 自動化（ポリシーのコード化）
- AIによる異常検知
- 定期的なアクセスレビュー

## 例: 開発者が本番サーバーにアクセスする流れ

### 従来のやり方

1. VPN に接続（社内ネットになる）
2. SSH で本番サーバーに接続
3. `sudo` で root に昇格
4. 作業

**問題**: VPN越えたら全社内が見える、1つのSSH鍵が漏れたら全サーバーに被害、権限は固定。

### ゼロトラスト版

1. IDaaS で **SSO + MFA** 認証
2. **デバイス健全性チェック**（OS最新、EDR動作中）
3. **JIT 権限昇格**：承認者の許可を取得
4. **ZTNA トンネル** を対象サーバーへだけ張る
5. **Session Recording**：すべての操作を録画
6. 時間が経つと **自動で権限失効**

攻撃者が認証情報を1つ奪っても、端末や場所や時間で弾かれる。

## ゼロトラストの誤解

### 1. 「製品を買えば実現できる」

**ゼロトラストはアーキテクチャ思想** であって、単一製品ではない。複数ツールの組み合わせと運用で実現する。

### 2. 「VPN 廃止がゴール」

VPNはしばしば代替されるが、**ゴールではない**。認証・認可のあり方全体が変わる。

### 3. 「完全な実装は難しいから意味がない」

**段階導入** が前提。MFAを全社展開するだけでも大きな効果がある。

### 4. 「内部を信頼しないのは性悪説」

悪意の有無でなく、**マルウェア感染や乗っ取り** に備える。善良な社員の端末が侵害される前提。

### 5. 「ユーザー体験が悪くなる」

うまく実装すれば、SSO + 条件付きアクセスで **むしろシームレス** に。ポリシーが合えばパスワード入力不要。

## ゼロトラストと他の原則との関係

- **最小権限**: ゼロトラストの基礎。「与える権限が最小」だからこそ、常時検証が意味を持つ。
- **深層防御**: ゼロトラストは深層防御の進化形。境界頼みをやめ、すべての層で防御。
- **セキュアバイデザイン**: ゼロトラストは **設計原則として** 初期から組み込む。

## 業界の動き

- **2020年** NIST が SP 800-207「Zero Trust Architecture」を公表
- **2021年** 米国大統領令で連邦政府機関にゼロトラスト採用を義務化
- **2022年** 日本のNISCもゼロトラスト指針を公表
- 主要クラウド（AWS、Azure、GCP）がゼロトラスト関連サービスを拡充

## 2026年の事例から：VPN が最大の入口に（追記 2026-10-17）

境界防御モデルの限界は、2026年の国内の統計にもはっきり表れています（全体は [[10_2026年_国内情報漏洩の動向と対策]]）。

- 警察庁によると、2026年上半期のランサムウェア被害で経路が分かった 36件のうち、**VPN 機器が 18件、リモートデスクトップが 9件**
- 攻撃の中心は **未修正の脆弱性と漏えいした認証情報**。「社内ネットワークに入れれば信頼される」構造が悪用された
- VPN 装置そのものがインターネットに公開された攻撃対象になっている（デジタル庁 GSS、両毛システムズなど）

### 認証のあとも検証が必要

海外では、攻撃者が **電話で従業員を誘導して SSO と MFA を奪い、自分の MFA デバイスを登録させる** 手口（ShinyHunters 系）が報告されています。ログインの瞬間だけ確かめても防げません。

- MFA デバイスの登録・パスワードリセット直後の高リスク操作は追加で確認する（[[04_二要素認証（2FA）機能]]）
- ログイン後の挙動（大量のデータエクスポートなど）を継続して監視する（[[A09_ログとモニタリングの不備]]）

### 実務での優先順位

1. VPN をすぐやめられないなら、**MFA 必須・パッチ SLA・使っていないアカウントの削除**（[[07_脆弱性管理（境界機器・パッチ運用）]]）
2. RDP をインターネットに公開しない
3. 段階的に **ZTNA** へ移し、VPN 装置をインターネットから見えなくする

## まとめ

- ゼロトラストは **「決して信頼せず、常に検証する」** モデル
- 境界防御モデルは、リモートワーク・クラウド時代に限界
- **ID、デバイス、コンテキスト** を毎回検証
- **最小権限 + 継続検証 + 可視化** が柱
- 製品1つで実現するものではなく、**段階的な旅**
- MFA 全社展開 → SSO → ZTNA → マイクロセグメンテーション の順が一般的
