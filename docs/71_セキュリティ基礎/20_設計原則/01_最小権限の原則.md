# 最小権限の原則（Principle of Least Privilege）

## はじめに

**最小権限の原則**（PoLP: Principle of Least Privilege）とは、

> **「人・プログラム・プロセスは、必要最小限の権限だけを持つべき」**

というセキュリティの基本原則です。1970年代に Saltzer と Schroeder が提唱した、情報セキュリティの古典的原則の1つで、現代でもほぼすべてのセキュリティ設計の土台になっています。

### 一言でいうと

> 「**使わない権限は持たせない**」

---

## なぜ重要なのか

### 1. 侵害時の被害を最小化する

完璧なセキュリティは存在しません。**いつか破られる** 前提で設計するなら、**破られたときの影響範囲を小さく** することが重要。

最小権限なら:
- アカウント1つが乗っ取られても、そのアカウントでできる範囲しか被害が及ばない
- サーバー1台が侵害されても、そのサーバーからアクセスできる範囲しか広がらない

### 2. 誤操作・人的ミスの被害も減らす

セキュリティだけでなく、**誤操作** の被害も減らせます。

- 開発者が本番DBを直接操作して全レコード削除、という事故を防げる
- 読み取り権限しかなければ、誤UPDATE/DELETEは不可能

### 3. コンプライアンス要件

多くの規制（GDPR、PCI-DSS、SOX等）が最小権限を明示的に要求しています。

---

## 最小権限の3つの次元

### 1. 権限の **種類**

何ができるか（CRUD: Create / Read / Update / Delete）を必要なものに絞る。

例: レポート閲覧ユーザーなら Read だけ、Write は不要。

### 2. 権限の **範囲**

どこに対してか、をできるだけ狭く。

例: 「全テーブル」ではなく「売上テーブルだけ」。

### 3. 権限の **期間**

いつまで有効か、必要な時だけ。

例: メンテ作業時の一時的な権限昇格（ジャストインタイム、JIT）。

## 具体例

### 例1: ユーザーアカウント

#### ❌ 悪い例

「管理者に1人1アカウントを作って、全員フル権限」。

- 誰か1人が侵害されれば全権限が奪われる
- 退職者のアカウントが残りがち
- 監査で誰が何をしたか追跡しづらい

#### ✅ 良い例

- **役割ベース**（RBAC）で権限を分離
- 一般ユーザー: 閲覧のみ
- 編集者: 自分の担当範囲のみ書き込み
- 管理者: 必要な業務に応じて最小限の管理権限
- 監査ログ用ユーザー: 読み取り + 書き込み不可（改ざん防止）

### 例2: データベースアカウント

#### ❌ 悪い例

```
アプリ用DBユーザー = root (全権限)
```

SQLインジェクションで侵入されると、テーブルDROP・OS侵入まで可能。

#### ✅ 良い例

```
- アプリ用ユーザー: SELECT, INSERT, UPDATE, DELETE のみ（DDL不可）
- 読み取り専用ユーザー: SELECT のみ（分析用）
- マイグレーション用ユーザー: DDL含むフル権限（デプロイ時のみ一時使用）
```

### 例3: クラウドIAM（AWS等）

#### ❌ 悪い例

```json
{
  "Effect": "Allow",
  "Action": "*",
  "Resource": "*"
}
```

フル権限付きのアクセスキー。漏れたら終了。

#### ✅ 良い例

```json
{
  "Effect": "Allow",
  "Action": ["s3:GetObject", "s3:PutObject"],
  "Resource": "arn:aws:s3:::my-app-uploads/*"
}
```

- **必要なアクションのみ**
- **特定のバケット・プレフィックスのみ**
- 条件（IP制限、時間帯、MFA必須）も付加可能

### 例4: コンテナ・プロセス

- **root で動かさない**（非root ユーザーでコンテナ起動）
- 不要な Linux capability を落とす
- **read-only ファイルシステム** でコンテナ起動
- `seccomp` / `AppArmor` / `SELinux` で syscall を制限

```dockerfile
# 非rootユーザーで実行
RUN useradd -r -u 1001 appuser
USER appuser
```

### 例5: CI/CD トークン

#### ❌ 悪い例

GitHub Actions のジョブトークンが **リポジトリのフルアクセス**。

#### ✅ 良い例

```yaml
permissions:
  contents: read      # コード読み取り
  issues: write       # Issue への書き込み（必要な場合のみ）
  # その他はデフォルトで拒否
```

## 実装パターン

### 1. RBAC（Role-Based Access Control）

**役割（Role）** に権限を紐付け、ユーザーを役割に割り当てる。

```
Role: editor
  - permissions: ["article.read", "article.write"]

Role: admin
  - permissions: ["article.*", "user.*"]

User "alice" → Role "editor"
User "bob"   → Role "admin"
```

中小規模なら RBAC で十分。

### 2. ABAC（Attribute-Based Access Control）

**属性**（ユーザー所属部署、時間帯、場所等）で動的に判定。

```
Allow if user.department == resource.owner_department
       && time.now() in business_hours
       && user.mfa_verified == true
```

複雑な条件が必要な場合に採用。

### 3. PBAC / Policy-as-Code

**Open Policy Agent (OPA)** 等のエンジンで、ポリシーをコードとして管理。Kubernetes、マイクロサービス、API Gatewayで広く採用。

### 4. Just-in-Time アクセス（JIT）

平常時は権限ゼロ、必要時だけ一時的に権限を付与。

- AWS IAM Identity Center の **Permission Set**
- PAM（Privileged Access Management）ソリューション
- 「作業を始める」ボタンで承認フロー → 30分だけ sudo 可能

### 5. 権限の棚卸し（Access Review）

定期的に「このユーザーに本当にこの権限が必要か？」を見直す。

- 四半期に1回、各マネージャが部下の権限をレビュー
- 退職者・異動者の権限を即座に削除
- 使われていない権限を自動検出（CloudTrail ログ分析等）

## アンチパターン

### 1. 「とりあえず admin」

開発中に面倒だからとフル権限で始め、そのまま本番に持ち込む。

### 2. 共有アカウント

複数人が1つのアカウントを使い回す。誰が何をしたか追跡できない + 退職時に無効化しにくい。

### 3. 権限の足し算しかない

追加は気軽にやるが、削除はしない。権限が **単調増加** していき、気がつけば全員がフル権限。

### 4. 一時権限が恒久化

「一時的に admin にするね」→ 半年後もそのまま。

### 5. サービスアカウントに人の権限を与える

バッチ処理が「念のため」管理者権限を持っている。実際は読み書き少しずつで十分なのに。

## 最小権限を実現する手順

### Step 1: 現状把握

- 誰がどの権限を持っているか可視化
- どの権限が実際に使われているか監査ログで確認

### Step 2: ベースラインを決める

- 役割ごとの **最低限の権限セット** を定義
- それ以上は例外として管理

### Step 3: 権限を縮小

- 使われていない権限を削除
- 「要件として明確でない権限」は削除（デフォルト拒否）

### Step 4: 仕組みで維持

- IaC（Terraform）でポリシーをコード化
- 新規ユーザー作成時のデフォルトを最小に
- 自動スキャン（AWS Access Analyzer、IAM Policy Simulator）

### Step 5: 定期レビュー

- 四半期に1回の棚卸し
- 退職・異動時の即時無効化
- インシデント時の権限の振り返り

## 関連する原則

### Need-to-Know 原則

「知る必要のある情報だけ知らせる」。機密情報の閲覧権限に特化した考え方。

### Separation of Duties（職務分掌）

重要操作を **1人では完結できない** ようにする。開発者が本番にデプロイできない、承認と実行が別人、等。

### Defense in Depth（深層防御）

1層目の権限制御が破られても、2層目で止める。`深層防御.md` 参照。

### Zero Trust

「社内だから信頼する」を廃し、**すべてのアクセスを検証** する。`ゼロトラスト.md` 参照。最小権限はゼロトラストの基礎。

## 2026年の事例から（追記 2026-10-17）

2026年の国内の情報漏洩では、**侵入されたあとに持っていた権限の広さ** が被害の大きさを決めた例が多く報告されました（全体は [[10_2026年_国内情報漏洩の動向と対策]]）。

| 事例 | 権限の問題 |
|---|---|
| デジタル庁 GSS | VPN の脆弱性から侵入され、**保守担当者のアカウント** で大量のファイルにアクセスされた |
| 両毛システムズ | **VPN アカウント** が悪用され、ランサムウェア被害が委託元の自治体などに波及 |
| 会員システム各種 | Web サーバーや業務 ID を 1 つ奪われると DB の奥まで届く「フラットな構成」が指摘された |
| AIエージェント（研究者の検証） | AWS AgentCore の検証で、既定で有効なシェルツールから **実行ロールのトークン** が盗まれ、別の MCP サーバーで使い回せた |

### 教訓

- **保守・委託先アカウントは常時有効にしない**。作業のときだけ有効にする JIT アクセスにし、届く範囲も作業対象に限る
- アプリ用 DB アカウントが **全件を SELECT できる** と、1 回の侵入で全会員分が持ち出される。ビューや行レベルセキュリティで絞り、1 回の取得件数の上限と組み合わせる（[[A09_ログとモニタリングの不備]]）
- AIエージェントに渡すツールと実行ロールにも最小権限を適用する（[[08_プロンプトインジェクション]]）

## まとめ

- 最小権限の原則は **「使わない権限は持たせない」**
- **種類 / 範囲 / 期間** の3次元で最小化する
- RBAC → ABAC → JIT の順に、組織の成熟度に合わせて導入
- **侵害時の被害最小化** が最大の目的
- 権限の **棚卸し** と **コード化** で、維持可能にする
