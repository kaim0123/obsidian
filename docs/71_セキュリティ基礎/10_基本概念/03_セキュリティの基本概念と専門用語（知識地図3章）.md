# 第3章：セキュリティの基本概念と専門用語

第1章で脅威の全体像、第2章で監視・分析の技術を学んだ。本章では、セキュリティの議論で **必ず登場する専門用語** を、初心者向けに丁寧に解説する。

「用語を覚える」ことが目的ではなく、**ニュースや脆弱性情報を読んだときに意味がわかる状態** を目指す。

---

## 1. 情報セキュリティの7要素

情報を守るとき、何を「守る」のかを言葉で表したもの。もっとも有名な **CIA トライアド**（機密性・完全性・可用性）に、4つが加わった形が「7要素」。

### 1.1 CIA トライアド（基本の3つ）

| 要素 | 英語 | 意味 | 守れていないときの例 |
|------|------|------|----------------------|
| **機密性** | Confidentiality | 許可された者だけが情報にアクセスできる | 個人情報の漏洩、パスワードの流出 |
| **完全性** | Integrity | 情報が改ざん・破壊されていない | データベースの不正書き換え、ファイルの改ざん |
| **可用性** | Availability | 必要なときに情報・サービスが使える | サーバー停止、DDoSによるアクセス不能 |

> 3つはトレードオフの関係にあることも多い。例：厳しい認証（機密性↑）は手間が増え、使いにくくなる（可用性↓）ことがある。

---

### 1.2 追加の4要素

| 要素 | 英語 | 意味 | 具体例 |
|------|------|------|--------|
| **真正性** | Authenticity | 送信者・情報源が本物であること | なりすましメールの検知、デジタル署名による確認 |
| **信頼性** | Reliability | システムが期待どおり正確に動作すること | 決済システムの計算ミス、誤ったログ記録 |
| **責任追跡性** | Accountability | 誰が何をしたか追跡できること | 監査ログ、操作履歴の記録 |
| **否認防止** | Non-repudiation | 行ったことを後から「やっていない」と否定できないこと | 電子署名付き契約、改ざん困難なログ |

### 1.3 7要素の関係（イメージ）

```
【情報の保護】
  機密性 … 見られないようにする
  完全性 … 変えられないようにする
  可用性 … 使えなくされないようにする

【情報の信頼】
  真正性 … 送り主が本物か確認する
  信頼性 … システムが正しく動くか確認する

【事後の証明】
  責任追跡性 … 誰がやったか残す
  否認防止 … やったことを否定させない
```

### 1.4 対策技術との対応（ざっくり）

| 要素 | 主な対策技術 |
|------|--------------|
| 機密性 | 暗号化、アクセス制御、認証 |
| 完全性 | ハッシュ値、デジタル署名、バージョン管理 |
| 可用性 | 冗長化、バックアップ、DDoS対策 |
| 真正性 | MFA、デジタル証明書、SPF/DKIM |
| 信頼性 | テスト、監視、エラーハンドリング |
| 責任追跡性 | 監査ログ、SIEM |
| 否認防止 | 電子署名、タイムスタンプ、改ざん検知ログ |

## 2. 攻撃に関する専門用語

第1章でも触れた用語を、定義を明確にして整理する。

### 2.1 サービス妨害系

| 用語 | 正式名称 | 説明 |
|------|----------|------|
| **DoS攻撃** | Denial of Service | **1か所から** 大量リクエストを送り、サービスを使えなくする攻撃 |
| **DDoS攻撃** | Distributed Denial of Service | **多数の端末（ボットネット等）から同時に** 攻撃する DoS。規模が大きく防御が難しい |

**狙う要素：** 可用性（Availability）

**例：** ECサイトへのアクセス集中、DNSサーバーの過負荷

---

### 2.2 脆弱性悪用系

| 用語 | 説明 | 例え |
|------|------|------|
| **脆弱性（Vulnerability）** | ソフトウェアや設定の弱点 | 家の鍵のかかっていない窓 |
| **エクスプロイト（Exploit）** | 脆弱性を**実際に悪用する**コードや手法 | その窓から入る道具・手口 |
| **ペイロード（Payload）** | 攻撃が成功したあとに実行される**本体の処理**（マルウェア本体、データ窃取など） | 侵入後に運び込む「荷物」 |
| **ゼロデイ攻撃** | 修正パッチがまだない脆弱性（ゼロデイ）を悪用した攻撃 | 鍵屋が来る前に窓から入る |
| **PoC** | Proof of Concept（概念実証） | 脆弱性が本当に悪用可能か示す**実証コード**。悪用と同等の危険性がある場合も |

**関係の整理：**

```
脆弱性（弱点がある）
    ↓ 悪用する
エクスプロイト（侵入の手段）
    ↓ 成功後に動く
ペイロード（マルウェア、情報窃取など）
```

---

### 2.3 マルウェア・標的型攻撃

| 用語 | 説明 |
|------|------|
| **マルウェア（Malware）** | 悪意のあるソフトウェアの総称（ウイルス、ランサムウェア、トロイの木馬など） |
| **標的型攻撃（Targeted Attack）** | 特定の組織・個人を狙って綿密に計画された攻撃。APT（持続的標的型攻撃）と呼ばれる高度なものも含む |

**標的型攻撃の特徴：**
- スピアフィッシングで入口を作る
- 長期間潜伏して情報を収集する
- 一般のマルウェアより検知が難しい

---

### 2.4 認証・人を狙う攻撃

| 用語 | 説明 |
|------|------|
| **ブルートフォース攻撃** | パスワードを総当たりで試す攻撃 |
| **フィッシング（Phishing）** | 正規の連絡を装い、パスワードや個人情報を騙し取る |

**関連用語（覚えておくと便利）：**

| 用語 | 説明 |
|------|------|
| **辞書攻撃** | よく使われるパスワードのリストで試す |
| **パスワードスプレー** | 少数のよくあるパスワードを多数アカウントに試す |
| **クレデンシャルスタッフィング** | 他サイトで漏洩したID/パスワードの使い回しを試す |

## 3. 脆弱性の指標・識別子

脆弱性情報は世界中で毎日公開される。**同じ弱点に同じ名前を付け、深刻度を数値化する** 仕組みが整備されている。

### 3.1 全体の関係

```
【何が弱いか】        CWE（弱点の種類）
【どの製品のどの穴か】 CVE + CPE（製品とバージョン）
【どれくらい危険か】  CVSS / SSVC / EPSS（深刻度・優先度）
【今すぐ直すべきか】  KEVカタログ（実際に悪用されているか）
```

---

### 3.2 CVE（Common Vulnerabilities and Exposures）

**公開された脆弱性に付けられる一意のID。**

| 項目 | 内容 |
|------|------|
| **形式** | `CVE-年-連番`（例：`CVE-2024-12345`） |
| **管理** | MITRE 社が管理、NVD（米国国立脆弱性データベース）などで詳細公開 |
| **役割** | 「この製品のこのバグ」を世界中で同じ名前で呼ぶ |

**例：** `CVE-2021-44228`（Log4Shell）— Java のログライブラリ Log4j の重大な脆弱性

**初心者のポイント：** セキュリティニュースで `CVE-XXXX-XXXXX` と出てきたら、「公式に登録された脆弱性の名前」と思えばよい。

---

### 3.3 CWE（Common Weakness Enumeration）

**脆弱性の「原因・パターン」の分類。CVE より抽象的。**

| 項目 | 内容 |
|------|------|
| **形式** | `CWE-番号`（例：`CWE-79`） |
| **役割** | 「どんな種類のコーディングミスか」を分類 |

**CVE と CWE の違い：**

| | CVE | CWE |
|---|-----|-----|
| **粒度** | 特定製品の特定のバグ | 弱点のパターン・種類 |
| **例** | CVE-2021-44228（Log4jの具体的な穴） | CWE-917（Expression Language Injection） |

**よく見る CWE の例：**

| CWE | 名称 | 説明 |
|-----|------|------|
| CWE-79 | クロスサイトスクリプティング（XSS） | Webページに悪意のあるスクリプトを埋め込む |
| CWE-89 | SQLインジェクション | SQL文に悪意のある入力を混ぜる |
| CWE-787 | バッファオーバーフロー | 想定外の大量データでメモリを破壊 |
| CWE-798 | ハードコードされた認証情報 | ソースコードにパスワードを直書き |

---

### 3.4 CVSS（Common Vulnerability Scoring System）

**脆弱性の深刻度を 0.0〜10.0 の数値で表すスコア。**

| スコア帯 | 深刻度 | 目安 |
|----------|--------|------|
| 0.0 | None | 影響なし |
| 0.1〜3.9 | Low | 低 |
| 4.0〜6.9 | Medium | 中 |
| 7.0〜8.9 | High | 高 |
| 9.0〜10.0 | Critical | 最重要 |

**評価の観点（CVSS v3.1 の例）：**

| 観点 | 内容 |
|------|------|
| **攻撃ベクトル** | ネットワーク経由か、物理接触が必要か |
| **攻撃の複雑さ** | 悪用の難易度 |
| **必要な権限** | 攻撃に必要な権限レベル |
| **ユーザー操作** | 被害者の操作が必要か |
| **影響** | 機密性・完全性・可用性への影響 |

**注意：** CVSS は「技術的な深刻度」であり、**自社環境での実際のリスク** とは異なる場合がある。スコアが高くても自社で使っていなければ影響はない、ということも多い。

---

### 3.5 CPE（Common Platform Enumeration）

**影響を受ける製品・バージョンを機械可読な形式で表す識別子。**

| 項目 | 内容 |
|------|------|
| **形式** | `cpe:2.3:a:ベンダー:製品:バージョン:...` |
| **役割** | 脆弱性スキャナーが「自社のどのソフトに当てはまるか」を自動判定 |

**例：**
```
cpe:2.3:a:apache:log4j:2.14.1:*:*:*:*:*:*:*
```
→ Apache Log4j バージョン 2.14.1

**初心者のポイント：** CPE は日常会話ではあまり出てこないが、パッチ管理ツールや脆弱性スキャナの裏側で使われている。

---

### 3.6 SSVC（Stakeholder-Specific Vulnerability Categorization）

**組織ごとの状況に合わせて、パッチ適用の優先度を判断するフレームワーク。**

CVSS は「脆弱性そのものの深刻度」だが、SSVC は **「自社にとってどれくらい急ぎか」** を考える。

| 判断軸 | 質問の例 |
|--------|----------|
| **悪用の可能性** | 攻撃コードは既に公開されているか |
| **影響の規模** | 自社でそのソフトを使っているか、重要システムか |
| **環境の安全性** | インターネットに公開されているか、内部のみか |

**出力例：** Track（監視）/ Track*（優先監視）/ Attend（対応）/ Act（即時対応）

**初心者のポイント：** CVSS 9.8 でも自社未使用なら優先度は低い、CVSS 7.0 でもインターネット公開サーバーなら最優先、という判断に使う。

---

### 3.7 EPSS（Exploit Prediction Scoring System）

**今後52日以内にその脆弱性が悪用される確率を 0〜1（0〜100%）で予測するスコア。**

| 項目 | 内容 |
|------|------|
| **提供** | FIRST（フォーラム・オブ・インシデント対応セキュリティチーム） |
| **役割** | CVSS だけでは見えない「実際に攻撃に使われそうか」を補完 |
| **更新** | 日次で更新される |

**使い方の例：**
- CVSS が中程度でも EPSS が高い → 早めにパッチ
- CVSS が高くても EPSS が低い → 他の対応を優先してもよい場合がある

---

### 3.8 KEVカタログ（Known Exploited Vulnerabilities Catalog）

**米国 CISA（サイバーセキュリティ・インフラストラクチャセキュリティ庁）が管理する、「実際に悪用が確認された脆弱性」のリスト。**

| 項目 | 内容 |
|------|------|
| **正式名称** | CISA KEV Catalog |
| **掲載条件** | 実際の攻撃で悪用が確認された CVE |
| **意味** | リストに載っている = **今すぐ対応すべき** の強いシグナル |

**実務での使い方：**
1. 自社資産のスキャン結果と KEV リストを照合
2. 一致した CVE は最優先でパッチまたは緩和策を適用
3. 政府機関・大企業の調達要件で KEV 対応が求められることも

---

### 3.9 脆弱性指標の使い分け（まとめ）

| 指標 | 何を教えてくれるか | いつ使うか |
|------|-------------------|------------|
| **CVE** | 脆弱性の名前 | 情報検索、パッチ照合 |
| **CWE** | 弱点の種類 | 開発時の防止、コードレビュー |
| **CVSS** | 技術的深刻度 | 初期の優先度付け |
| **CPE** | 影響製品の特定 | スキャナーによる自動マッチング |
| **SSVC** | 組織にとっての優先度 | パッチ運用の判断 |
| **EPSS** | 悪用される確率 | CVSS を補完した優先度付け |
| **KEV** | 実際に悪用済みか | 最優先対応の判断 |

## 4. 暗号技術

第2章でも触れたが、本章では **用語の定義と仕組み** を中心に整理する。暗号は機密性・完全性・真正性・否認防止の基盤技術。

### 4.1 暗号の2大分類

```
暗号技術
  ├─ 共通鍵暗号（対称鍵）… 同じ鍵で暗号化と復号
  └─ 公開鍵暗号（非対称鍵）… 公開鍵と秘密鍵のペア
```

---

### 4.2 共通鍵暗号（対称鍵暗号）

**暗号化と復号に同じ鍵を使う** 方式。高速で大量データの暗号化に向く。

| 項目 | 内容 |
|------|------|
| **仕組み** | 送信者と受信者が事前に同じ鍵を共有 |
| **長所** | 処理が速い |
| **短所** | 鍵を安全に渡す問題（鍵配送問題）がある |

**代表アルゴリズム：**

| アルゴリズム | 状態 | 用途 |
|--------------|------|------|
| **AES** | 現行標準 | ファイル暗号化、VPN、TLS の中身など |
| **3DES** | 非推奨（レガシー） | 古いシステム |
| **ChaCha20** | 現行 | TLS、モバイル向け（AES より高速な環境も） |

#### AES（Advanced Encryption Standard）とは

- 2001年に米国政府が標準として採用
- 鍵長：128 / 192 / 256 ビット
- 「軍事級暗号」と表現されることが多いが、**正しく実装・運用されていることが前提**
- Wi-Fi（WPA2/WPA3）、ディスク暗号化（BitLocker 等）、HTTPS の中で広く使われる

---

### 4.3 公開鍵暗号（非対称鍵暗号）

**公開鍵と秘密鍵のペア** を使う方式。鍵配送問題を解決できる。

| 鍵 | 誰が持つか | 用途 |
|----|------------|------|
| **公開鍵** | 誰でも入手可能 | 暗号化、署名の検証 |
| **秘密鍵** | 本人だけが保持 | 復号、署名の作成 |

**代表アルゴリズム：**

| アルゴリズム | 用途 |
|--------------|------|
| **RSA** | 電子署名、鍵交換（レガシーだが広く残存） |
| **ECDSA / ECDH** | 現代のTLS、Bitcoin など（楕円曲線、鍵が短く効率的） |

**仕組みの例（暗号化）：**
```
Alice が Bob に秘密のメッセージを送る
  1. Bob の公開鍵で暗号化
  2. Bob だけが自分の秘密鍵で復号できる
```

---

### 4.4 ハッシュ関数

**任意長のデータから固定長の「指紋」を作る** 一方向関数。復号はできない。

| 項目 | 内容 |
|------|------|
| **性質** | 同じ入力 → 常に同じ出力、少しでも入力が変わると出力が大きく変わる |
| **用途** | パスワード保存、ファイルの改ざん検知、デジタル署名の一部 |
| **注意** | 暗号化ではない（元に戻せないが、総当たりで推測される場合がある） |

**代表アルゴリズム：**

| アルゴリズム | 状態 |
|--------------|------|
| **SHA-256** | 現行標準 |
| **SHA-3** | 現行標準 |
| **MD5 / SHA-1** | 非推奨（衝突攻撃が現実的） |

**パスワード保存の正しい方法：**
```
❌ パスワードをそのまま保存
❌ 単純なハッシュだけ（レインボーテーブルに弱い）
✅ bcrypt / scrypt / Argon2 など「遅い」ハッシュ + ソルト
```

---

### 4.5 電子署名

**送信者の身元確認と改ざん検知** を同時に実現する技術。

```
【署名の作成】
  1. メッセージのハッシュ値を計算
  2. 送信者の秘密鍵でハッシュを暗号化 → これが「署名」

【署名の検証】
  1. 受信者が送信者の公開鍵で署名を復号 → ハッシュA
  2. 受信メッセージのハッシュを計算 → ハッシュB
  3. ハッシュA と ハッシュB が一致 → 改ざんなし＆送信者確認
```

**守れる要素：** 真正性、完全性、否認防止

---

### 4.6 PKI（公開鍵基盤）

**公開鍵とデジタル証明書を信頼できる形で配布・管理する仕組み** の総称。

| 構成要素 | 役割 |
|----------|------|
| **CA（認証局）** | デジタル証明書を発行する信頼の起点 |
| **デジタル証明書** | 「この公開鍵はこの組織のものである」と CA が保証する電子文書 |
| **CRL / OCSP** | 失効した証明書のリスト・確認サービス |

**身近な例：**
- ブラウザのアドレスバーの鍵マーク（HTTPS）
- 社内 VPN のクライアント証明書
- コード署名（ソフトウェアの改ざん防止）

**信頼の連鎖：**
```
ルートCA（ブラウザに最初から入っている）
    ↓ 署名
中間CA
    ↓ 署名
サーバー証明書（example.com）
```

---

### 4.7 TLS（Transport Layer Security）

**インターネット上の通信を暗号化するプロトコル。** 旧称 SSL。HTTPS の「S」の正体。

| 項目 | 内容 |
|------|------|
| **守れること** | 通信内容の機密性、改ざん検知 |
| **仕組み** | 公開鍵暗号で鍵を交換 → 以降は共通鍵（AES等）で高速暗号化 |
| **確認方法** | ブラウザのアドレスバーで `https://` と鍵アイコンを確認 |

**TLS ハンドシェイク（簡略）：**
```
1. クライアント「接続したい」
2. サーバー「これが私の証明書です」（公開鍵入り）
3. クライアントが証明書を検証（CA の署名を確認）
4. 双方で共通のセッション鍵を安全に決定
5. 以降の通信はセッション鍵（AES等）で暗号化
```

**注意点：**
- HTTPS は「通信経路の暗号化」であり、**サイト自体が安全とは限らない**（フィッシングサイトも HTTPS にできる）
- 古い TLS 1.0 / 1.1 は非推奨。TLS 1.2 / 1.3 を使う

---

### 4.8 暗号技術の関係マップ

```
【データの保護】
  共通鍵暗号（AES）──── 大量データの暗号化
  公開鍵暗号（RSA/EC）── 鍵交換、署名

【データの検証】
  ハッシュ関数（SHA-256）─ 改ざん検知、パスワード保存
  電子署名 ────────────── 送信者確認 + 改ざん検知

【信頼の仕組み】
  PKI（CA + 証明書）──── 公開鍵の信頼性を保証

【通信の保護】
  TLS ───────────────── HTTPS、メール、API通信
        （公開鍵で鍵交換 + AESで暗号化 + 証明書で身元確認）
```

## 5. 用語の相互関係（総合マップ）

```
【守りたいもの】 7要素（CIA + 真正性・信頼性・責任追跡性・否認防止）
        ↑ 脅かす
【攻撃】 DoS/DDoS、エクスプロイト、マルウェア、フィッシング…
        ↑ 突く
【弱点】 CVE で名前が付く脆弱性（原因パターンは CWE）
        ↑ 評価
【指標】 CVSS（深刻度）、EPSS（悪用確率）、KEV（悪用済み）、SSVC（自社優先度）
        ↑ 守る
【技術】 暗号（AES、TLS、PKI）、アクセス制御、監視（第2章）
```

## 6. この章のまとめ

| カテゴリ | 覚えておくこと |
|----------|----------------|
| **7要素** | CIA が基本。真正性・否認防止は「誰が・本当に」を守る |
| **攻撃用語** | 脆弱性 → エクスプロイト → ペイロード の順で理解 |
| **CVE/CWE** | CVE は「具体的な穴」、CWE は「穴の種類」 |
| **CVSS/EPSS/KEV** | 深刻度・悪用確率・悪用済みか、を組み合わせて優先度を決める |
| **暗号** | 共通鍵は速い、公開鍵は鍵交換・署名、TLS は両方を組み合わせた通信保護 |

これらの用語は、脆弱性情報の読み方（次章以降のパッチ管理）や、セキュリティ設計の議論の土台になる。ニュースで CVE や CVSS が出てきたら、本章に戻って確認する習慣をつけると理解が定着する。
