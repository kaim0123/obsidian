# A04: 安全でない設計（Insecure Design）

## はじめに

**安全でない設計** は、2021年版で新設されたカテゴリです。これまでの Top 10 は「コードのバグ」が中心でしたが、A04 は **「設計段階での欠陥」** に焦点を当てています。

### 具体例でイメージする

- パスワード再設定の本人確認が、生年月日だけ
- 登録フォームに CAPTCHA がなく、botで大量登録が可能
- ECサイトで、在庫数以上の注文を受け付けてしまう
- 1人が同じ質問に何度も挑戦できるクイズシステム

**どれだけコードを完璧に書いても、設計が甘いと安全ではない** というのが A04 の教えです。

---

## 「実装の欠陥」と「設計の欠陥」の違い

| | 実装の欠陥（Bug） | 設計の欠陥（Flaw） |
|---|---|---|
| **例** | SQLインジェクション、バッファオーバーフロー | CAPTCHA未実装、本人確認の甘さ |
| **見つけ方** | コードレビュー、SAST | 脅威モデリング、設計レビュー |
| **修正** | コードを直す | 仕様・フローから見直し |
| **コスト** | 比較的低い | 高い（作り直しに近い） |

**設計の欠陥は、コードをいくら直しても消えません。** 仕様レベルで直す必要があります。

---

## よくある「安全でない設計」の例

### 1. 認証・本人確認が弱い

- パスワードリセットの質問が「母親の旧姓」だけ（SNSで調べられる）
- 多要素認証がない
- ログイン試行回数制限がない → 総当たり攻撃し放題

### 2. 業務ロジックの悪用（Business Logic Flaw）

**コード上はバグではないが、仕様の穴を突く** 攻撃です。

- クーポンを複数回適用できる
- 注文確定後に価格を書き換えて送信できる
- ポイント付与の条件を何度も満たせる

### 3. レート制限の欠如

- 1秒間に1万回 SMS認証コードを送れる → キャリア料金爆発、サービス停止
- 1つの IP から無制限にアカウント作成できる

### 4. セキュアなデフォルト設定の欠如

- 新規登録時、デフォルトで「公開プロフィール」
- 権限設定の初期値が「全員書き込み可」

### 5. 脅威モデリングの欠如

そもそも「どんな攻撃があり得るか」を考えていないと、対策のしようがありません。

## 悪い例: パスワードリセットフロー

```
1. ユーザーがメールアドレスを入力
2. 生年月日を聞く
3. 正解ならパスワードを変更できる
```

**問題点**:
- 生年月日は SNS で調べられる
- 試行回数に制限がない
- 他人のメールアドレスを入れれば、そのアカウントを乗っ取れる

## 良い例: 安全なパスワードリセットフロー

```
1. ユーザーがメールアドレスを入力
2. 「もしそのアドレスが登録されていれば、メールを送信しました」と常に同じ応答（列挙攻撃防止）
3. メールに、15分で失効する使い切りのトークン付きURLを送信
4. URLをクリックしたら新パスワードを設定
5. トークンは1回使ったら失効、同時に全セッションを無効化
6. 変更完了を本人のメールに通知
```

**設計の改善ポイント**:
- メールアドレスの存在をレスポンスから読み取れない
- トークンの有効期限・使い切り化
- セッション無効化で、乗っ取られていても排除
- 変更通知で、本人が気づける

## 設計段階で考えるべきこと

### 1. 脅威モデリング

実装前に「誰が」「どうやって」「何を狙うか」を洗い出します。

代表的な手法:
- **STRIDE**（脅威を6カテゴリに分類）
- **アタックツリー**（攻撃経路を木構造で可視化）
- **データフロー図 + 信頼境界**

詳しくは `02_Foundations/セキュリティ基礎/脅威モデリング/` を参照。

### 2. セキュアバイデザイン / セキュア・バイ・デフォルト

- 最初から安全な状態で動く
- 危険な機能はデフォルトOFF
- 権限は必要最小限で付与

### 3. 多層防御（Defense in Depth）

1つの防御が破られても、次の層で止まる設計にします。

例: ログイン画面
- レート制限（1層目）
- CAPTCHA（2層目）
- 多要素認証（3層目）
- 異常検知アラート（4層目）

### 4. 悪用ケース（Misuse Case）の検討

ユースケース（正常系）だけでなく、「**悪用者がどう悪用するか**」のシナリオを書き出します。

ユースケース: 「ユーザーはポイントで買い物ができる」
悪用ケース: 「攻撃者はAPIを並列で叩き、ポイントを二重使用する」

## 業務ロジックの穴を防ぐ

### 1. トランザクションと排他制御

```javascript
// ❌ 危険: ポイント使用処理にレース条件
async function usePoints(userId, amount) {
  const user = await db.getUser(userId);
  if (user.points >= amount) {
    await db.updatePoints(userId, user.points - amount);
  }
}
// 並列で叩かれると、両方とも if を通過してマイナス残高に！

// ✅ 良い: アトミックに更新
async function usePoints(userId, amount) {
  const result = await db.query(
    'UPDATE users SET points = points - ? WHERE id = ? AND points >= ?',
    [amount, userId, amount]
  );
  if (result.affectedRows === 0) throw new Error('Insufficient points');
}
```

### 2. サーバーサイドで必ず再検証

フロントで「このクーポンは1回のみ」と制御していても、攻撃者はAPIを直接叩きます。**価格計算・在庫チェック・権限チェックは、必ずサーバーで最終確認**。

### 3. レート制限

```javascript
// 例: express-rate-limit
import rateLimit from 'express-rate-limit';
app.post('/api/login', rateLimit({ windowMs: 60_000, max: 5 }), loginHandler);
```

- [ ] セキュリティを破った場合に、検知・対応できる仕組みはあるか？

---

## まとめ

- A04 は **「コードではなく設計の欠陥」** に焦点を当てた新カテゴリ
- **コードを直しても、設計が悪いと安全にならない**
- **脅威モデリング** と **セキュアバイデザイン** が予防の鍵
- **悪用ケース** を洗い出し、**多層防御** を設計に組み込む
- 業務ロジックは並列・順序改ざん・二重実行に耐える必要がある
