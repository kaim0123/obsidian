# A10:2025 例外的状況の不適切な処理（Mishandling of Exceptional Conditions）

## はじめに

OWASP Top 10:2025 で **新設** されたカテゴリです（2021年版との対応は [[01_OWASP_Top10_2025の変更点]]）。

**例外的状況** とは、「想定どおりに進まない状況」すべてのことです。

- 入力が欠けている・多すぎる・形式が違う
- DB や外部 API がタイムアウトする、エラーを返す
- メモリ・ディスク・接続数が足りない
- 権限が足りない、トークンが期限切れ
- 処理の途中でネットワークが切れる

OWASP は、ソフトウェアがこうした状況を

1. **防げない**（そもそも起こさない工夫がない）
2. **検知できない**（起きていることに気づかない）
3. **適切に対応できない**（起きた後の振る舞いがまずい）

のいずれかに当てはまるとき、「例外的状況を不適切に処理している」と定義しています。

> **アプリケーションが「次に何をすべきか分からない」状態になったら、それは例外的状況の処理に失敗している**（OWASP）

### 具体例でイメージする

```
決済処理:  ① 残高を減らす → ② 相手の残高を増やす → ③ 取引ログを書く

②でネットワークエラー → ①だけ確定したまま
  → お金が消える／あるいはリトライで②が2回走って二重送金
```

```
認可チェック:  外部の権限サービスに問い合わせ
  → タイムアウト → catch して何もせず処理を続行
  → 誰でも管理機能が使えてしまう（フェイルオープン）
```

## なぜ起きるのか

### 1. 正常系しか考えていない

開発やテストは「うまくいく場合」を中心に進みがちです。異常系は「とりあえず catch しておく」で済まされ、**catch した後に何をするか** が設計されていません。

### 2. エラー処理が遠くで、まとめて行われる

エラーが起きた場所ではなく、ずっと上の層で「何かエラーが起きた」としか分からない形で処理されると、適切な回復ができません。

### 3. 例外処理のやり方がバラバラ

あるモジュールは例外を投げ、あるモジュールは `null` を返し、あるモジュールはエラーコードを返す。呼び出し側が戻り値のチェックを忘れる余地が生まれます。

### 4. 環境の異常を想定していない

メモリ不足、ディスクフル、権限不足、DNS 障害、時刻のずれ。これらは本番環境で初めて起こることが多いです。

### 5. 攻撃者は異常系を「わざと」突く

攻撃者は正常な使い方をしません。パラメータを抜く・増やす・巨大にする・同時に大量に送る。**エラーを起こさせること自体が攻撃の手段** です。

| 被害 | 例 | CIA |
|---|---|---|
| 情報漏洩 | スタックトレースや SQL エラーが画面に出て、DB 構造やライブラリのバージョンが分かる | 機密性 |
| 認証・認可の迂回 | 権限チェック中の例外を握りつぶし、処理を続行（フェイルオープン） | 機密性・完全性 |

| クラッシュ | NULL 参照、ゼロ除算、未捕捉例外でプロセスが落ちる | 可用性 |

## 攻撃シナリオ（OWASP の例）

### シナリオ1: リソース枯渇による DoS

ファイルアップロード中の例外は catch しているが、**リソースを解放していない**。攻撃者が失敗するアップロードを繰り返すと、ファイルハンドルや一時領域がロックされたまま溜まり、やがてサービス全体が使えなくなる。

### シナリオ2: エラーメッセージからの情報収集

DB エラーがそのまま利用者に表示される。攻撃者はわざとエラーを起こし、テーブル名・カラム名・DBMS の種類を集め、より精度の高い SQL インジェクション（[[A03_インジェクション]]）を組み立てる。

### シナリオ3: 金融取引の状態破壊

「引き落とし → 入金 → ログ記録」という複数ステップの送金を、攻撃者が通信妨害で途中で止める。システムが取引全体をロールバックしないと、口座から資金が抜かれたり、レースコンディションを突いて **同じ送金が複数回実行** されたりする。

## 悪い例と対策

### ❌ 悪い例1: 認可チェックのフェイルオープン

```typescript
async function canAccessAdmin(userId: string): Promise<boolean> {
  try {
    const res = await authzService.check(userId, "admin");
    return res.allowed;
  } catch (e) {
    // 権限サービスが落ちていても業務を止めたくない…
    return true; // ← 障害時に誰でも管理者になれる
  }
}
```

### ✅ 良い例1: フェイルクローズ（安全側に倒す）

```typescript
async function canAccessAdmin(userId: string): Promise<boolean> {
  try {
    const res = await authzService.check(userId, "admin");
    return res.allowed === true; // 想定外の値（undefined など）も拒否
  } catch (e) {
    logger.error({ event: "authz_check_failed", userId, err: String(e) });
    return false; // 判断できないときは拒否する
  }
}
```

> 「可用性を優先して通す」判断が必要な機能もあるが、それは **リスク評価のうえで明示的に決める** こと（[[04_リスク管理とリスクアセスメント]]）。認証・認可・決済は原則フェイルクローズ。

### ❌ 悪い例2: 詳細なエラーをそのまま返す

```typescript
app.get("/orders/:id", async (req, res) => {
  try {
    res.json(await db.query(`SELECT * FROM orders WHERE id = $1`, [req.params.id]));
  } catch (e: any) {
    res.status(500).json({ error: e.message, stack: e.stack }); // ← 内部情報が漏れる
  }
});
```

### ✅ 良い例2: 利用者には一般的なメッセージ、詳細はログへ

```typescript
app.get("/orders/:id", async (req, res, next) => {
  try {
    const order = await orderRepo.findById(req.params.id);
    if (!order) return res.status(404).json({ error: "not_found" });
    res.json(order);
  } catch (e) {
    next(e); // 処理はグローバルハンドラに集約
  }
});

// グローバル例外ハンドラ（最後の安全網）
app.use((err: unknown, req: Request, res: Response, _next: NextFunction) => {
  const errorId = crypto.randomUUID();
  logger.error({ errorId, path: req.path, err }); // 詳細はサーバー側だけに残す
  res.status(500).json({ error: "internal_error", errorId }); // 問い合わせ用のIDだけ返す
});
```

### ❌ 悪い例3: 途中で失敗すると中途半端な状態が残る

```typescript
await db.query("UPDATE accounts SET balance = balance - $1 WHERE id = $2", [amount, from]);
await db.query("UPDATE accounts SET balance = balance + $1 WHERE id = $2", [amount, to]); // ← ここで失敗したら？
await db.query("INSERT INTO transfers ...");
```

### ✅ 良い例3: トランザクションで全体を戻す ＋ 冪等性キー

```typescript
async function transfer(idempotencyKey: string, from: string, to: string, amount: number) {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    // 同じキーの送金が既にあれば何もしない（リトライによる二重実行を防ぐ）
    const dup = await client.query("SELECT 1 FROM transfers WHERE idempotency_key = $1", [idempotencyKey]);
    if (dup.rowCount) { await client.query("ROLLBACK"); return; }

    const r = await client.query(
      "UPDATE accounts SET balance = balance - $1 WHERE id = $2 AND balance >= $1",
      [amount, from],
    );
    if (r.rowCount !== 1) throw new Error("insufficient_funds"); // 戻り値を必ず確認
    await client.query("UPDATE accounts SET balance = balance + $1 WHERE id = $2", [amount, to]);
    await client.query("INSERT INTO transfers (idempotency_key, from_id, to_id, amount) VALUES ($1,$2,$3,$4)",
      [idempotencyKey, from, to, amount]);
    await client.query("COMMIT");
  } catch (e) {
    await client.query("ROLLBACK"); // 部分的な成功を残さない
    throw e;
  } finally {
    client.release(); // 成功しても失敗しても必ず解放
  }
}
```

### ❌ 悪い例4: 握りつぶし

```python
try:
    verify_signature(payload, sig)
except Exception:
    pass  # ← 検証に失敗しても先に進む（CWE-390, CWE-396）
process(payload)
```

### ✅ 良い例4: 想定する例外だけを捕まえ、それ以外は上に投げる

```python
try:
    verify_signature(payload, sig)
except InvalidSignature:
    log.warning("invalid_signature", extra={"source": src})
    raise HTTPException(status_code=400)
# 想定外の例外は catch しない → グローバルハンドラで 500 + ログ
process(payload)
```

## 防御のアプローチ（OWASP の推奨を整理）

### 1. 失敗を前提に設計する

- 設計段階で「この処理が失敗したらどうなるか」を書き出す（[[04_セキュアバイデザイン]]）
- 脅威モデリングで異常系も扱う。STRIDE の「サービス拒否」「改ざん」は異常系から生まれることが多い（[[02_STRIDE]]）

### 2. エラーは起きた場所で処理する

- 発生箇所で捕まえ、**意味のある回復**（リトライ、代替処理、ロールバック、拒否）を行う
- 回復できないなら、文脈を付けて上に投げる

### 3. グローバル例外ハンドラを最後の安全網に

- 取りこぼした例外を必ず捕まえ、プロセスを未知の状態で走らせ続けない
- 利用者には一般的なメッセージとエラーID、詳細はログへ

### 4. フェイルクローズ（安全に失敗する）

- 判断できないときは **拒否** する
- 複数ステップの処理は **全体をロールバック** して最初からやり直す。部分的な状態から回復しようとしない

### 5. リソースに上限を設ける

- レート制限、クォータ、スロットリング、タイムアウト、サイズ上限
- 例外的状況そのものを起こしにくくし、DoS や総当たり攻撃も抑える
- `finally` や `using` / `with` / `defer` で、成功・失敗にかかわらずリソースを解放する

### 6. 入力を厳密に検証する

- 欠けたパラメータ・余分なパラメータ・型違い・範囲外を入口で弾く（スキーマバリデーション）
- 受け入れる必要がある危険な文字は、適切にエスケープ・無害化する

### 7. エラー処理・ログ・監視・アラートを一元化する

- 1つのやり方に統一し、ハンドラを乱立させない
- **同じエラーが急増** したら攻撃の兆候。監視で検知し、自動でブロックや通知を行う
- 同じエラーが大量に出る場合は、件数と期間を集計して記録し、ログが溢れて監視が機能しなくなるのを防ぐ（[[A09_ログとモニタリングの不備]]）

### 8. 組織として標準化し、検証する

- エラー処理の方針を組織で統一すると、レビューや監査がしやすい
- コードレビュー・静的解析（握りつぶし、戻り値の未チェック、汎用例外の catch を検出）
- 負荷テスト・カオスエンジニアリング・ペネトレーションテストで異常系を実際に起こしてみる

## 言語・フレームワークごとの注意

| 環境 | 注意点 |
|---|---|
| JavaScript / Node.js | `await` 忘れや `.catch` なしの Promise で未処理の reject。`unhandledRejection` を監視し、Express では非同期エラーを `next(err)` に渡す |
| Go | `err` の無視（`_ =`）。`errcheck` などのリンターで検出 |
| Java / C# | `catch (Exception e) {}` の握りつぶし。try-with-resources / `using` でリソースを解放 |
| Python | 素の `except:` は `KeyboardInterrupt` まで捕まえる。具体的な例外クラスを指定 |
| C / C++ | NULL 参照、戻り値の未チェック、メモリ解放漏れ。メモリ安全な言語の採用も検討 |
| Web フレームワーク | 本番でデバッグモード・詳細エラーページを無効化（[[A05_セキュリティの設定ミス]]） |

## まとめ

- A10:2025 は **異常系（エラー・例外・想定外の状態）の扱い** に関する新カテゴリ。24 の CWE をまとめたもの
- 失敗は **防ぐ・検知する・適切に対応する** の3段階で考える
- 最重要は **フェイルクローズ**：判断できないときは拒否、途中で失敗したら全体を戻す
- 詳細なエラーは **ログに、利用者には一般的なメッセージとエラーID** だけ
- エラー処理・ログ・監視は **一元化して標準化** し、エラーの急増を攻撃の兆候として監視する
