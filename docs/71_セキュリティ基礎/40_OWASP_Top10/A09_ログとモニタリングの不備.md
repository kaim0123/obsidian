# A09: ログとモニタリングの不備（Security Logging and Monitoring Failures）

## はじめに

いくら堅牢に作っても、**攻撃を完全に防ぐことは不可能** です。だからこそ「攻撃されたときに気づけるか」「後から何が起きたか追跡できるか」が重要になります。

A09 は、**セキュリティ事象のログ取得・監視・対応が不十分** なことで、攻撃の検知・初動対応・原因究明ができない問題です。

### 具体例でイメージする

- 不正ログイン試行が1時間に1万回あったのに、誰も気づかなかった
- 情報漏洩が起きてから半年後に、外部から指摘されて初めて発覚
- 「何が起きたか」のログがなく、被害範囲も原因も特定できない
- ログはあるが、攻撃時には保存期間を過ぎて消えていた

業界調査では、**侵害を検知するまでの平均日数は200日を超える** とされます。

---

## なぜ重要なのか

### 1. 攻撃を早期発見するため

攻撃は一瞬で完了しません。**偵察 → 侵入試行 → 権限昇格 → データ持ち出し** の流れを踏みます。途中で気づければ被害を最小化できます。

### 2. 原因と被害範囲を特定するため

インシデント発生時、「何が・いつ・どこまで起きたか」を特定するには **ログが命** です。ログがなければ、何を修復すべきかすら分かりません。

### 3. 法的・コンプライアンス要件

- GDPR: 侵害発覚後 **72時間以内** に当局へ報告義務
- 個人情報保護法（日本）: 漏洩時の報告義務
- PCI-DSS: 監査ログの保持・レビュー要求

---

## 記録すべきセキュリティイベント

| カテゴリ | 例 |
|---------|---|
| **認証** | ログイン成功/失敗、ログアウト、パスワード変更、MFA設定変更 |
| **認可** | 権限昇格、管理機能アクセス、拒否されたアクセス |
| **入力検証失敗** | 不正な入力の検出、SQL/XSSの試行と思われるパターン |
| **重要データ** | 個人情報・金融情報の参照/変更/削除 |
| **設定変更** | セキュリティ関連設定の変更、ユーザー追加/削除 |
| **異常** | 大量リクエスト、異常なエラー率、未定義APIへのアクセス |

---

## ログに含めるべき情報

### ✅ 含めるべき

- **タイムスタンプ**（タイムゾーン含む、できればUTC+ISO 8601）
- **イベントの種類**（ログイン、権限変更等）
- **関与したユーザー**（ユーザーID、セッションID）
- **発信元IPアドレス / User-Agent**
- **対象リソース**（どのデータ、どのエンドポイント）
- **結果**（成功/失敗）
- **失敗時は理由**（パスワード不一致、MFA失敗 等）

### ❌ 含めてはいけない

- **パスワード・トークン・APIキー** そのもの
- **クレジットカード番号** のフル桁
- **個人情報** を必要以上に（マスキングする）
- **セッションID** 全体（末尾数文字だけにする等）

機密情報をログに含めると、**ログ自体が情報漏洩の対象** になります。

## 悪い例と対策

### ❌ 悪い例1: ログが足りない

```javascript
app.post('/login', async (req, res) => {
  const user = await authenticate(req.body);
  if (!user) return res.status(401).send('NG');
  // 成功も失敗もログに残らない
  res.json({ token: generateToken(user) });
});
```

### ✅ 良い例1: 構造化ログを残す

```javascript
app.post('/login', async (req, res) => {
  const user = await authenticate(req.body);
  if (!user) {
    logger.warn({
      event: 'login.failure',
      email: req.body.email,
      ip: req.ip,
      userAgent: req.headers['user-agent'],
      reason: 'invalid_credentials',
    });
    return res.status(401).send('NG');
  }
  logger.info({
    event: 'login.success',
    userId: user.id,
    ip: req.ip,
  });
  res.json({ token: generateToken(user) });
});
```

**JSON形式の構造化ログ** にすると、後で検索・集計が容易です。

### ❌ 悪い例2: パスワードをログに出す

```javascript
logger.info(`Login attempt: ${JSON.stringify(req.body)}`);
// req.body.password もログに残ってしまう！
```

### ✅ 良い例2: 機密フィールドを除外

```javascript
const { password, ...safeBody } = req.body;
logger.info({ event: 'login.attempt', ...safeBody });
```

多くのログライブラリには「機密フィールド自動マスキング」機能があります（pino の `redact`、Winston のフィルタなど）。

## ログ基盤の考え方

### 1. 集約（Aggregation）

各サーバー・コンテナのログを **1箇所に集める**。

- **ELK スタック**: Elasticsearch + Logstash + Kibana
- **Loki + Grafana**
- **Datadog、Splunk、New Relic、Sumo Logic**（商用）
- **CloudWatch Logs、Cloud Logging**（クラウドネイティブ）

### 2. 改ざん耐性

攻撃者は侵入後、**ログを消したり書き換えたり** します。これを防ぐには:

- ログを別サーバー・別アカウントに転送（攻撃者の権限でアクセスできないところへ）
- WORM ストレージ（Write Once Read Many）に保存
- ハッシュチェーン / タイムスタンプサービスで改ざん検知

### 3. 保持期間

- セキュリティログは **最低6ヶ月〜1年**、業種によっては **7年** 保持
- インシデント調査時に古いログが必要になることが多い
- アーカイブと費用のバランスを考える

### 4. 時刻同期

複数サーバーのログを突き合わせるには、時刻が揃っていることが必須。**NTPで時刻同期** し、UTCで記録するのが基本。

## モニタリングとアラート

ログを取るだけでは意味がありません。**異常を検知してアラート** を出す仕組みが必要です。

### アラート例

- 1分間に同一IPからログイン失敗 20回以上 → 総当たり疑い
- 通常は存在しないURLへの大量アクセス → スキャン行為
- 管理者権限操作が営業時間外に発生
- 短時間で大量データがエクスポートされた

### SIEM（Security Information and Event Management）

ログを集約・相関分析して **セキュリティ事象を検知** する専用システム。

- **Splunk Enterprise Security**
- **Microsoft Sentinel**
- **Elastic Security**
- **Chronicle**（Google）

### インシデント対応プロセス

検知しても対応できなければ意味がありません。以下のフローを事前に整備:

1. **検知**（Detection）
2. **トリアージ**（真の攻撃か、誤検知か判断）
3. **封じ込め**（Containment: 被害拡大を止める）
4. **根絶**（Eradication: 攻撃者を排除）
5. **復旧**（Recovery: 正常化）
6. **事後分析**（Post-mortem: 次回改善）

## 防御的プログラミングとの関係

アプリが **自発的にセキュリティイベントを記録する** 姿勢が重要です。

```javascript
// 認可チェック失敗 → ログを残す
if (!isAuthorized(user, resource)) {
  logger.warn({ event: 'access.denied', userId: user.id, resource });
  return res.status(403).send();
}

// 異常なパラメータ → ログを残す
if (input.length > MAX_LENGTH) {
  logger.warn({ event: 'validation.failed', field: 'input', length: input.length });
  return res.status(400).send();
}
```

## チェックリスト

- [ ] ログイン成功/失敗、管理操作、権限変更をログに記録しているか？
- [ ] ログに機密情報（パスワード、カード番号）が含まれていないか？
- [ ] ログはタイムスタンプ、ユーザーID、IP等の基本情報を含むか？
- [ ] ログは集約され、1か所で検索できるか？
- [ ] ログの保持期間は十分か？（最低6ヶ月〜1年）
- [ ] ログの改ざん・削除を防ぐ仕組みはあるか？
- [ ] 異常検知のアラートを設定しているか？
- [ ] アラートが誰にどう届くか決まっているか？
- [ ] インシデント対応の手順書があるか？
- [ ] 時刻同期（NTP）が設定されているか？

## 2026年の事例から：「正規の操作」に見える大量取得（追記 2026-10-17）

全体は [[10_2026年_国内情報漏洩の動向と対策]]。

### アフラック生命の事例

- 約440万人分（うち口座情報 約22万人）が漏えい。侵入は 6/10、発覚は 6/25（**15日後**）
- 発覚のきっかけは **CPU の高負荷**。セキュリティの仕組みではなく、性能の異常で気づいた
- 調査結果では、攻撃は **通常の利用と同じ形式のアクセス** で、**短時間の大量照会を監視・制御する機能が不足** していたとされた

WAF や IDS は「怪しいリクエスト」を探しますが、正規の ID と正規の API で 1 件ずつ取得されると見分けられません。**業務的にありえない量** を見る必要があります。

### 見るべき指標

| 指標 | 例 |
|---|---|
| 1 ユーザー・1 セッションあたりの取得レコード数 | 普段は 1 日 50 件なのに 1 時間で 1 万件 |
| データのエクスポート量 | CSV 出力・一括ダウンロードの回数とサイズ |
| 認証まわりの連続した操作 | **パスワードリセット直後の MFA デバイス登録**、普段と違う接続元からの管理操作 |
| サーバーからの外向き通信 | 見たことのない宛先への送信、DNS を使った持ち出し。ショップサーブでは外部送信が約72日続いた |

### 実装例：取得件数の上限と自動遮断

```ts
// 1 ユーザーあたり、直近 1 時間に取得したレコード数を数えて、上限を超えたら止める
// （例のため Map を使う。本番では Redis などの共有ストアを使う）
const WINDOW_MS = 60 * 60 * 1000;
const MAX_RECORDS_PER_WINDOW = 1000;
const usage = new Map<string, { start: number; count: number }>();

export function recordAccess(userId: string, recordCount: number): void {
  const now = Date.now();
  const u = usage.get(userId);
  const current = !u || now - u.start > WINDOW_MS ? { start: now, count: 0 } : u;
  current.count += recordCount;
  usage.set(userId, current);

  if (current.count > MAX_RECORDS_PER_WINDOW) {
    securityLog.warn({ event: "bulk_access_blocked", userId, count: current.count });
    throw new TooManyRecordsError(); // 403 を返し、セキュリティ担当にアラート
  }
}
```

- 閾値は普段の利用の分布（p99 など）から決め、業務で一括処理が必要なアカウントは別に管理する
- 止めるだけでなく、**アラートを出してアカウントを一時停止** できるようにしておく

### 運用の KPI

- **MTTD（検知までの時間）** を測る。2026年の事例では、発覚まで 15日〜約9か月かかっていた
- 「性能の異常」も重要なセキュリティシグナルとして、セキュリティ担当に共有する

---

## まとめ

- **完璧な防御は存在しない**。検知・対応できる仕組みが必要
- ログは **構造化・集約・保持・改ざん耐性** が鍵
- 機密情報は絶対にログに出さない（ログ自体が漏洩対象に）
- **取るだけでなく監視** して、異常を検知 → アラート → 対応
- インシデント対応プロセスを事前に整備しておく
