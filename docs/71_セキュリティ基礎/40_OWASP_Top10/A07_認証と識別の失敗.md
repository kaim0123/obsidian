# A07: 認証と識別の失敗（Identification and Authentication Failures）

## はじめに

**認証**（Authentication）とは、「あなたは本当にあなたですか？」を確認する仕組みです。ログイン処理の正体がこれです。

認証が破られると、他人になりすまして何でもできるようになります。銀行残高を引き出されたり、メールを勝手に送られたり、個人情報を盗まれたり…。認証は **アプリのセキュリティの土台** です。

### 具体例でイメージする

- パスワードリスト攻撃（他サービスから漏れた ID+PW で一斉ログイン試行）
- 総当たり攻撃（ブルートフォース）で弱いパスワードを突破
- セッションIDを盗んで、ログインせずに他人になりすます
- 「秘密の質問」を SNS 情報で突破してパスワードリセット

---

## 認証と認可の違い（再確認）

- **認証（Authentication / AuthN）**: あなたは誰？ → ログイン
- **認可（Authorization / AuthZ）**: それをやっていい？ → 権限チェック（A01参照）

A07 は **認証** の失敗、A01 は **認可** の失敗です。

---

## 認証の「3要素」

| 要素 | 意味 | 具体例 |
|------|------|--------|
| **知識要素**（What you know） | 本人だけが知っている | パスワード、PIN、秘密の質問 |
| **所持要素**（What you have） | 本人だけが持っている | スマホ、ハードウェアトークン、ICカード |
| **生体要素**（What you are） | 本人そのもの | 指紋、顔、虹彩、声 |

**多要素認証（MFA: Multi-Factor Authentication）** とは、これらのうち **異なる種類を2つ以上** 組み合わせること。「パスワード + もう1つパスワード」はMFAになりません（どちらも知識要素）。

---

## よくある攻撃パターン

### 1. パスワードリスト攻撃（Credential Stuffing）

他のサービスから漏れたID/PW のリストを使って、別のサービスにログイン試行。**パスワード使い回し** が前提で、多くの人が引っかかります。

### 2. 総当たり攻撃（Brute Force）

ありうる組み合わせを全部試す。弱いパスワードほど早く突破されます。

### 3. 辞書攻撃

よく使われるパスワード（`password123`、`qwerty`、`admin`）や、単語リストから試す。

### 4. セッションハイジャック

セッションID（Cookie等）を盗んで、そのままなりすます。

- 通信盗聴（HTTPじゃない場合）
- XSSで `document.cookie` を盗む
- PC共有時のログアウト忘れ

### 5. セッション固定化（Session Fixation）

攻撃者が事前に作ったセッションIDを被害者に使わせ、そのIDで後から乗り込む。

### 6. パスワードリセットの悪用

- 秘密の質問が弱い（母親の旧姓など）
- リセットトークンが推測可能
- リセットURLの有効期限が長すぎる

### 7. アカウント列挙

ログイン失敗時のメッセージで「そのアドレスは登録されていません」と返すと、**どのメアドが登録済みか** が攻撃者に分かります。

## パスワードの保存（A02 暗号化とも関連）

### ❌ 最悪: 平文

```javascript
db.users.insert({ email, password }); // そのまま保存
```

### ❌ 悪い: MD5 / SHA-1

```javascript
const hash = crypto.createHash('md5').update(password).digest('hex');
```

GPUで1秒に数十億回計算できるので、総当たりで突破されます。

### ✅ 良い: bcrypt / scrypt / Argon2

```javascript
import bcrypt from 'bcrypt';

// 登録時
const hash = await bcrypt.hash(password, 12);

// 検証時
const ok = await bcrypt.compare(password, hash);
```

- **わざと遅い**（パスワード用途では「遅さ」が武器）
- **ソルト自動付加**（同じPWでも違うハッシュになり、レインボーテーブル無効化）
- **コストパラメータ**で将来の計算速度向上にも対応できる

現代の推奨は **Argon2id**、次点で **bcrypt / scrypt**。

## パスワードポリシー（最新推奨）

古い推奨（複雑性・定期変更）は **NIST SP 800-63B** により改訂されました。

### ✅ 現代の推奨

- **最低8文字、できれば12文字以上**（長さを重視）
- **既知の漏洩パスワード禁止**（`password`、`123456` 等）
- **定期変更は強制しない**（パターン化して逆に弱くなるため）
- **複雑性要件（大文字小文字記号混在）は必須にしない**

### 推奨しない

- 「90日ごとに変更」
- 「大文字・小文字・記号・数字を混ぜろ」
- 「秘密の質問」による本人確認

## セッション管理

### セッションIDの要件

- 十分に長くランダム（128ビット以上）
- 予測不可能（暗号論的乱数で生成）
- 推測可能な情報（ユーザー名、時刻）から生成しない

### Cookie の属性

```
Set-Cookie: sessionId=abc123;
  HttpOnly;         ← JSからアクセス不可（XSS対策）
  Secure;           ← HTTPS のみ送信
  SameSite=Lax;     ← CSRF対策
  Path=/;
  Max-Age=3600
```

### ログアウト・タイムアウト

- ログアウトで **サーバー側でも無効化**（Cookie削除だけでは不十分）
- 一定時間操作がなければ自動ログアウト
- パスワード変更時は全セッション無効化

## 多要素認証（MFA）

### MFA の方式

| 方式 | 仕組み | セキュリティ |
|------|--------|-------------|
| **SMSコード** | 電話番号に番号送信 | 低（SIM スワップ攻撃リスク） |
| **メールコード** | メールに番号送信 | 中 |
| **TOTP**（Google Authenticator 等） | 30秒で変わる6桁コード | 高 |
| **プッシュ通知** | スマホアプリで承認 | 高 |
| **FIDO2 / パスキー** | 端末の秘密鍵で認証 | 最高（フィッシング耐性） |

MFAを導入するだけで、認証情報漏洩による不正ログインを **99%以上防げる** と言われます。

### パスワードレス認証（パスキー）

FIDO2 / WebAuthn をベースにした、**パスワードそのものをなくす** 認証方式。大手（Apple / Google / Microsoft）が推進中。フィッシング耐性が極めて高い。

## 悪い例と対策

### ❌ 悪い例: 試行回数無制限

```javascript
app.post('/login', async (req, res) => {
  const user = await db.getUser(req.body.email);
  if (user && user.password === hashedPassword) { ... }
});
```

### ✅ 良い例: レート制限 + アカウントロック

```javascript
import rateLimit from 'express-rate-limit';

const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15分
  max: 5, // 5回失敗でブロック
});

app.post('/login', loginLimiter, async (req, res) => { ... });
```

- IP単位 + アカウント単位の両方でレート制限
- N回連続失敗でアカウントを一時ロック
- 失敗時のメッセージは「メールまたはパスワードが違います」で統一（アカウント列挙防止）

### ❌ 悪い例: セッションIDをURLに含める

```
https://example.com/page?sid=abc123
```

URLはReferer、ブックマーク、ログで漏れます。

## 認証を「自前実装」しない

モダンな開発では、**認証ライブラリ／サービス** を使うのが定石。

- **Auth0 / Okta / Firebase Auth / Clerk / Supabase Auth**（IDaaS）
- **Passport.js / NextAuth.js**（ライブラリ）
- **Keycloak**（OSS）

自作すると、OAuth2 / OIDC / パスワードハッシュ / MFA / セッション管理などを自力で正しく作る必要があり、リスクが大きいです。

- [ ] パスワード変更で全セッションを無効化しているか？

## まとめ

- 認証は **アプリのセキュリティの土台**
- **bcrypt / Argon2** でハッシュ、**MFA** 導入、**レート制限** の3点が基本
- **パスワードレス（パスキー）** が今後の主流
- **自前実装を避け**、信頼できる認証サービスを使うのが現代的な選択
- セッション管理の基本（Cookie属性、ログアウト、タイムアウト）も忘れず
