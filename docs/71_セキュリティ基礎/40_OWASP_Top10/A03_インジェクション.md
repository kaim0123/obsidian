# A03: インジェクション（Injection）

## はじめに

**インジェクション**（injection: 注入）とは、**ユーザーの入力がコードの一部として解釈されてしまう** 攻撃の総称です。

入力欄からコードを「注入」して、本来意図しない動作をさせる。これがすべてのインジェクション攻撃の本質です。

2021年版で **XSS（クロスサイトスクリプティング）** もこのカテゴリに統合されました。

### 具体例でイメージする

- 検索フォームに `' OR '1'='1` と入力したらログイン画面を素通りできた
- 名前欄に `<script>alert(1)</script>` と入力したら全ユーザーのブラウザでJSが動いた
- ファイル名に `; rm -rf /` と入れたらサーバーが壊れた

これらはすべてインジェクションの例です。

---

## 根本原因: 「データ」と「コード」の混在

インジェクション攻撃が成立するのは、**ユーザー入力（データ）が、コマンド文字列（コード）に直接結合される** からです。

```
"SELECT * FROM users WHERE name = '" + userInput + "'"
              ↑ コード部分                 ↑ データ部分

userInput に 「' OR '1'='1」 が入ると:

"SELECT * FROM users WHERE name = '' OR '1'='1'"
                                     ↑ 全件マッチする条件になってしまった！
```

「データをコードとして実行させない」ことが、防御の基本原則です。

---

## 主なインジェクションの種類

### 1. SQLインジェクション（SQLi）

DBへのクエリに悪意ある文字列を注入。

```javascript
// ❌ 危険
const sql = `SELECT * FROM users WHERE email = '${email}'`;
```

`email` に `' OR '1'='1' --` を入れられると、全ユーザー情報が返ります。

### 2. コマンドインジェクション（OS Command Injection）

シェルコマンドに注入。

```javascript
// ❌ 危険
exec(`convert ${filename} output.png`);
```

`filename` に `image.jpg; rm -rf /` を入れられると、サーバーのファイルが消えます。

### 3. XSS（クロスサイトスクリプティング）

HTMLページに悪意あるJSを注入。

```javascript
// ❌ 危険
document.getElementById('name').innerHTML = userInput;
```

`userInput` に `<script>fetch('/api/cookie?c='+document.cookie)</script>` を入れられると、他ユーザーのクッキーが盗まれます。

### 4. LDAPインジェクション

LDAPクエリに注入。認証バイパスなどに悪用。

### 5. NoSQLインジェクション

MongoDB等のNoSQLにも、似た攻撃があります。

```javascript
// ❌ 危険
db.users.find({ username: req.body.username, password: req.body.password });
// req.body に { username: {$ne: null}, password: {$ne: null} } を送ると
// 「usernameがnullでない AND passwordがnullでない」= 全件マッチしてログイン可能
```

### 6. テンプレートインジェクション（SSTI）

サーバーサイドのテンプレートエンジンに注入。`{{7*7}}` が `49` になるなどで検知される。

### 7. XMLインジェクション / XXE

XMLに外部エンティティを注入して、サーバー内のファイルを読む等。

## SQLインジェクションの詳細例

### ❌ 悪い例: 文字列結合

```javascript
const email = req.body.email; // ユーザー入力
const sql = `SELECT * FROM users WHERE email = '${email}'`;
const result = await db.query(sql);
```

攻撃: `email = "' OR '1'='1' --"` を送る → 全ユーザーが返る。

### ✅ 良い例1: プリペアドステートメント（パラメータ化クエリ）

```javascript
// データとコードを分離
const sql = 'SELECT * FROM users WHERE email = ?';
const result = await db.query(sql, [email]); // emailはデータとして扱われる
```

`?` にバインドされる値は **データとしてしか** 扱われないので、そこに `' OR '1'='1'` が来てもコード解釈されません。

### ✅ 良い例2: ORMを使う

```javascript
// Prisma
const user = await prisma.user.findUnique({ where: { email } });

// Sequelize
const user = await User.findOne({ where: { email } });
```

多くのORMはプリペアドステートメントを内部で使うため、デフォルトで安全です。

## XSS の詳細例

### XSSの3分類

| 種類 | 説明 |
|------|------|
| **反射型** | 攻撃用URLを踏ませて、その場で実行 |
| **蓄積型（格納型）** | DBなどに保存され、他ユーザーが閲覧時に実行 |
| **DOMベース** | サーバーを経由せず、JSがDOMを操作する過程で発生 |

### ❌ 悪い例: innerHTML への直接代入

```javascript
document.getElementById('profile').innerHTML = `こんにちは ${userName}さん`;
```

`userName` に `<img src=x onerror="fetch('/api/steal?c='+document.cookie)">` を入れられると発火。

### ✅ 良い例1: textContent を使う

```javascript
document.getElementById('profile').textContent = `こんにちは ${userName}さん`;
```

`textContent` はHTMLとして解釈されないので安全。

### ✅ 良い例2: フレームワークを信じる

React、Vue、Angular などは **デフォルトでエスケープ** します。

```jsx
// React: 自動的にエスケープされる
<div>{userName}</div>

// ❌ 危険: dangerouslySetInnerHTML は名前のとおり危険
<div dangerouslySetInnerHTML={{ __html: userInput }} />
```

### ✅ 良い例3: CSP（Content Security Policy）で多重防御

```
Content-Security-Policy: default-src 'self'; script-src 'self'
```

万一XSSが混入しても、外部スクリプトの実行や `eval` を禁止できます。

## コマンドインジェクションの例

### ❌ 悪い例

```javascript
import { exec } from 'child_process';
exec(`ping ${host}`, callback); // host に ";rm -rf /" が入るとアウト
```

### ✅ 良い例: 引数配列を使う

```javascript
import { execFile } from 'child_process';
execFile('ping', [host], callback); // hostは引数として扱われ、シェル解釈されない
```

**原則**: シェルを経由しない、引数を配列で渡す、コマンド自体をホワイトリスト化。

---

## 防御の原則

### 1. パラメータ化（分離）

データとコードを必ず分離。プリペアドステートメント、パラメータ化クエリ、引数配列を使う。

### 2. エスケープ（出力時の無害化）

HTML / JS / URL / SQL それぞれの文脈に応じた **エスケープ** を行う。

```javascript
// HTMLエスケープの基本
function escapeHtml(str) {
  return str
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#39;');
}
```

ただし、自前エスケープは漏れが出やすいので、**ライブラリ任せが基本**。

### 3. 入力検証（ホワイトリスト方式）

「許可するものを列挙する」発想で検証。ブラックリスト（禁止するものを列挙）は抜けやすい。

```javascript
// ✅ 許可: 英数字とハイフンのみ
if (!/^[a-zA-Z0-9-]+$/.test(input)) throw new Error('Invalid input');
```

### 4. 最小権限

DBユーザーは必要最小限の権限に。アプリ用ユーザーに `DROP TABLE` 権限を与えない。

### 5. WAF・CSP・SRI による多重防御

- **WAF**（Web Application Firewall）で怪しいリクエストをブロック
- **CSP** でXSSの影響を制限
- **SRI**（Subresource Integrity）で外部スクリプトの改ざんを検知

---

## まとめ

- インジェクションの本質は **データとコードの混在**
- 対策の王道は **「分離」**（プリペアドステートメント、引数配列）
- 出力時は **「エスケープ」**（フレームワーク任せが基本）
- 入力時は **ホワイトリスト検証**
- CSP・WAF・最小権限で多重防御
