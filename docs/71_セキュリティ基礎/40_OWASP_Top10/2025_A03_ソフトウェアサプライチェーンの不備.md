# A03:2025 ソフトウェアサプライチェーンの不備（Software Supply Chain Failures）

## はじめに

OWASP Top 10:2025 で **新設** されたカテゴリです（2021年版との対応は [[01_OWASP_Top10_2025の変更点]]）。

2021年版の [[A06_脆弱で古いコンポーネント]] は「**既知の脆弱性を持つライブラリを使っている**」問題でした。2025年版の A03 はそこから範囲を広げ、

> **ソフトウェアが「作られ・配布され・更新される」仕組みのどこかが壊れている、または乗っ取られている**

ことすべてを扱います。対象は依存ライブラリだけでなく、**CI/CD・ビルドサーバー・開発者の端末・IDE 拡張・パッケージレジストリ・コンテナレジストリ・SaaS 連携** まで含みます。

CVE が少ないのは、サプライチェーン攻撃の多くが「ソフトウェアの欠陥」ではなく「**仕組みの悪用**」（アカウント乗っ取り、悪意あるパッケージの公開）であり、CVE 番号が付きにくいためです。データだけでなくコミュニティ調査でも選ばれた理由はここにあります。

## A06（2021）・A08 との違い

| 観点 | A06:2021 脆弱で古いコンポーネント | A03:2025 サプライチェーンの不備 | A08 整合性の不備 |
|---|---|---|---|
| 主な問題 | 既知の脆弱性を持つ部品を使っている | 部品の調達・ビルド・配布の仕組みが弱い／侵害されている | 改ざんされたコード・データを検証せずに信用する |
| 攻撃者の動き | 公開された脆弱性を突く | 上流（ベンダー・メンテナー・CI）を乗っ取り、正規の経路で悪意あるコードを届ける | 署名なしの更新や、信頼できない入力のデシリアライズを悪用 |
| 代表例 | Log4Shell、Struts 2 | SolarWinds、Shai-Hulud、Bybit | 署名なしの自動更新、CI での未検証プラグイン |
| 主な対策 | SCA、パッチ適用 | SBOM、変更管理、CI/CD と開発端末の強化、段階的展開 | 署名、来歴（provenance）の検証 |

A03 は A06 を包含し、A08 とは「署名・来歴の検証」で重なります。組織・委託先の観点（ソフトウェア以外のサプライチェーン）は [[09_サプライチェーン攻撃と委託先管理]] にまとめています。

## 攻撃シナリオ（OWASP の例）

### シナリオ1: 信頼しているベンダーが侵害される（SolarWinds, 2019〜2020）

攻撃者が SolarWinds のビルド環境に侵入し、監視製品 Orion の正規アップデートにバックドアを混入。**約18,000の組織** が、署名された正規の更新としてマルウェアを取り込みました。

### シナリオ2: 特定の条件でだけ動く悪意あるコード（Bybit, 2025）

暗号資産取引所 Bybit から **約15億ドル** が盗まれた事件。ウォレットソフトウェアのサプライチェーンが侵害され、**標的のウォレットを使うときだけ** 悪意ある動作をするよう仕込まれていました。条件付きで動くため、テストや監視で見つけにくいのが特徴です。

### シナリオ3: 自己増殖する npm ワーム（Shai-Hulud, 2025）

初めて成功した **自己増殖型の npm ワーム** とされます。

1. 人気パッケージの悪意あるバージョンが公開される
2. インストール時の `postinstall` スクリプトが、開発者の端末や CI から認証情報（トークン・クラウドの鍵）を盗み、公開 GitHub リポジトリに書き出す
3. 盗んだ **npm トークン** を使い、被害者がメンテナンスしている別のパッケージにも悪意あるバージョンを公開
4. 2 に戻って連鎖

npm が止めるまでに **500以上のパッケージバージョン** が影響を受けました。**開発者の端末そのものがサプライチェーン攻撃の主要な標的になった** ことを示した事件です。

### シナリオ4: 権限を持つ部品の欠陥

コンポーネントは通常アプリと同じ権限で動くため、どれか1つの欠陥がアプリ全体の侵害になります。

- CVE-2017-5638（Apache Struts 2 の RCE）: 大規模な情報漏洩につながった
- CVE-2021-44228（Log4Shell）: ランサムウェア・暗号資産採掘などに悪用された（[[A06_脆弱で古いコンポーネント]] の「Log4Shell から学ぶ教訓」）

## 脆弱な状態のチェック（OWASP の挙げる条件）

次に当てはまるなら、A03 のリスクがあります。

- 推移的な依存（依存の依存）を含め、**クライアント側・サーバー側すべての部品のバージョンを把握していない**
- OS・Web サーバー・DBMS・API・ランタイム・ライブラリに、脆弱・サポート切れ・古いものがある
- 定期的な脆弱性スキャンや、セキュリティ情報の購読をしていない
- サプライチェーン全体（IDE・拡張機能・リポジトリ・サンドボックス・成果物の保管場所）の **変更管理・変更履歴** がない
- サプライチェーンの各要素（特にアクセス制御）を強化していない
- **職務分離がない**: 1人がコードを書いて、誰のチェックも受けずに本番へ出せる
- 信頼できない提供元の部品が本番に影響しうる
- パッチを月次・四半期ごとにしか当てず、数日〜数か月の無防備期間がある
- 更新したライブラリの互換性をテストしていない
- **CI/CD パイプラインのセキュリティが、それがビルド・デプロイするシステムより弱い**

## 防御のアプローチ

### 1. 部品とパッチの管理

- **SBOM**（ソフトウェア部品表）を、組織のソフトウェア全体について一元的に生成・管理する（形式は CycloneDX、SPDX）
- 直接依存だけでなく **推移的な依存** も追跡する
- 使っていない依存・機能・ファイルを削除し、攻撃対象を減らす
- OWASP Dependency-Track / Dependency-Check、Retire.js などで継続的に棚卸し
- CVE・NVD・**OSV** を監視し、SCA ツールで自動化、アラートを購読
- 信頼できる提供元から、安全な経路で取得。**署名付きパッケージ** を優先（[[A08_ソフトウェアとデータの整合性の不備]]）
- 依存のバージョンは意図して選び、必要なときに上げる（無条件の最新追従はしない）
- メンテナンスされていない部品に注意。パッチが出ないなら代替へ移行、移行もできないなら **仮想パッチ**（WAF などで検知・遮断）
- CI/CD・IDE・開発ツール自体も定期的に更新
- **一斉に更新しない**。段階的ロールアウトやカナリアで、ベンダーが侵害された場合の影響を限定する

### 2. 変更管理（変更を追跡する対象）

- CI/CD の設定、ビルドツール、パイプライン
- コードリポジトリ、サンドボックス
- 開発者の IDE と拡張機能
- SBOM ツールと生成物
- ログ基盤とログ
- SaaS を含む外部連携
- 成果物リポジトリ、コンテナレジストリ

### 3. 強化（ハードニング）

すべてで **MFA を有効にし、IAM を最小権限に**（[[01_最小権限の原則]]）。

| 対象 | 対策 |
|---|---|
| コードリポジトリ | 秘密情報をコミットしない、保護ブランチ、バックアップ |
| 開発者の端末 | 定期的なパッチ、MFA、監視（EDR） |
| ビルドサーバー・CI/CD | 職務分離、アクセス制御、**署名付きビルド**、環境ごとにスコープを絞った秘密情報、改ざん検知可能なログ |
| 成果物 | 来歴（provenance）・署名・タイムスタンプで整合性を確認。**環境ごとに再ビルドせず、同じ成果物を昇格させる**。ビルドは不変（immutable）に |
| IaC | 他のコードと同じく、プルリクエストとバージョン管理で扱う |

### 4. 開発者の端末と npm 系エコシステムの実践

Shai-Hulud 型の攻撃を踏まえた、すぐできる対策です。

```bash
# インストールスクリプトを既定で実行しない（必要なパッケージだけ許可）
npm config set ignore-scripts true

# ロックファイルどおりに入れる（CI では npm install ではなく npm ci）
npm ci

# 公開から一定期間たっていない新しいバージョンを避ける（pnpm の例）
# pnpm-workspace.yaml
# minimumReleaseAge: 1440   # 分。公開から24時間未満のバージョンは入れない
```

- npm への公開は **Trusted Publishing（OIDC）** を使い、長期間有効な公開トークンを持たない
- パッケージの公開アカウントには **フィッシング耐性のある MFA**（パスキー・セキュリティキー）
- CI の秘密情報は、必要なジョブ・環境だけに渡す。PR からのワークフローに秘密情報を渡さない
- GitHub Actions は **コミット SHA で固定** する（タグは書き換えられる）

```yaml
# ❌ タグ参照: 乗っ取られると中身が差し替わる
- uses: some-org/some-action@v3
# ✅ コミット SHA で固定（Dependabot / Renovate で更新）
- uses: some-org/some-action@3f1c2b7e9a0d4c5b6e7f8a9b0c1d2e3f4a5b6c7d # v3.2.1
```

### 5. フレームワーク

- **SLSA**（Supply-chain Levels for Software Artifacts）: ビルドの来歴と改ざん耐性のレベル
- **Sigstore / cosign**: 成果物・コンテナイメージへの署名と検証
- **OpenSSF Scorecard**: OSS プロジェクトのセキュリティ慣行の自動評価
- **NIST SSDF（SP 800-218）**: セキュアなソフトウェア開発の枠組み

## チェックリスト

- [ ] 全サービスの SBOM を生成し、一元管理しているか？
- [ ] 推移的依存の脆弱性まで自動で検知・通知されるか？
- [ ] 使っていない依存を定期的に削除しているか？
- [ ] 本番へのデプロイに、作成者以外のレビュー・承認が必須か（職務分離）？
- [ ] CI/CD・リポジトリ・レジストリ・パッケージ公開アカウントに MFA と最小権限を適用しているか？
- [ ] CI の秘密情報は環境ごとにスコープが絞られ、長期トークンを使っていないか？
- [ ] 外部の GitHub Actions を SHA で固定しているか？
- [ ] 開発者端末でインストールスクリプトの実行を制限しているか？
- [ ] 成果物に署名し、デプロイ時に検証しているか？ 環境ごとに再ビルドしていないか？
- [ ] 更新を段階的に展開しているか？
- [ ] メンテナンスが止まった部品の移行計画があるか？

## まとめ

- A03:2025 は、A06:2021 を **「部品の脆弱性」から「作る・配る・更新する仕組み全体」へ** 拡張したカテゴリ
- 発生率は全カテゴリで最も高く、コミュニティ調査でも半数が1位に選んだ
- 攻撃者は **上流（ベンダー・メンテナー・CI・開発者端末）を乗っ取り、正規の経路で届ける**
- 対策の柱は **SBOM と棚卸し・変更管理・CI/CD と開発端末の強化・署名と来歴・段階的展開**
- **CI/CD は、それがデプロイするシステムと同じかそれ以上に守る**
