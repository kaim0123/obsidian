# A05: セキュリティの設定ミス（Security Misconfiguration）

## はじめに

**セキュリティの設定ミス** は、ソフトウェアやクラウド、サーバーの **設定が不適切なまま** 運用されている問題です。コードは完璧でも、設定1つで全てが台無しになります。

### 具体例でイメージする

- S3バケットが「全公開」に設定されていて、顧客情報が漏洩
- 管理画面のパスワードがデフォルトの `admin/admin` のまま
- エラー画面にスタックトレースと DB 接続情報が表示される
- 開発用のデバッグエンドポイントが本番に残っている
- サンプルデータ（テスト用ユーザー）が本番DBに残っている

これらはすべて「設定ミス」で、**コードではなく運用の問題** です。

---

## よくある設定ミスのパターン

### 1. デフォルト認証情報の放置

ルーター、DB、管理ツールなどが **初期パスワードのまま** 運用されている。

- DB: `root / (空パスワード)` や `admin / admin`
- 管理画面: `admin / password`
- IoT機器: `admin / 1234`

botが世界中をスキャンしてデフォルト認証情報で侵入しています。

### 2. 過剰な情報を含むエラー画面

```
[ERROR] 500 Internal Server Error
  at users.controller.js:42
  DB connection failed: postgres://admin:mySecretPass@10.0.0.5:5432/prod
  Stack trace: ...
```

開発中は便利ですが、**本番では禁止**。DBサーバーのIPやパスワードが丸見えになります。

### 3. 不要な機能・ポート・アカウントの有効化

- サンプルアプリケーションがそのまま配置されている
- 使っていないポート（21番/FTP、23番/Telnet）が開いている
- 退職者のアカウントが残っている

### 4. セキュリティヘッダーの欠如

Webアプリで以下のヘッダーが未設定:
- `Content-Security-Policy`
- `Strict-Transport-Security`
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options` / `frame-ancestors`
- `Referrer-Policy`

### 5. クラウドリソースの公開設定ミス

- **S3バケット**が全世界に公開
- **GCS / Azure Blob** が認証不要で読める
- データベースがインターネットに直接公開されている（`0.0.0.0/0` 許可）
- Elasticsearch / MongoDB が認証なしで公開

### 6. CORS の設定ミス

```javascript
// ❌ 危険: すべてのオリジンを許可
app.use(cors({ origin: '*', credentials: true }));
```

`credentials: true` で `origin: '*'` は最悪の組み合わせ。

### 7. 古いサンプル設定・チュートリアル設定の残存

- Jenkinsのセットアップウィザードをスキップしたまま公開
- Kubernetesダッシュボードが認証なしで公開

## 悪い例と対策

### ❌ 悪い例1: 本番でデバッグモード有効

```python
# Django settings.py
DEBUG = True  # ← 本番ではTrueにしない！
ALLOWED_HOSTS = ['*']
```

`DEBUG=True` だと、エラー時にソースコード・設定・環境変数がブラウザに表示されます。

### ✅ 良い例1: 環境変数で制御

```python
import os
DEBUG = os.environ.get('DEBUG', 'False') == 'True'
ALLOWED_HOSTS = ['example.com', 'www.example.com']
```

### ❌ 悪い例2: S3が全公開

```json
{
  "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-bucket/*"
}
```

### ✅ 良い例2: 認証必須にする

- バケットポリシーで特定のIAMロール・オリジンのみ許可
- **Block Public Access** をアカウントレベルで有効化
- CloudFront + OAI（Origin Access Identity）経由で配信

### ❌ 悪い例3: 生のエラーをクライアントに返す

```javascript
app.use((err, req, res, next) => {
  res.status(500).json({ error: err.stack }); // スタックトレース丸見え
});
```

### ✅ 良い例3: 汎用メッセージ + ログ

```javascript
app.use((err, req, res, next) => {
  logger.error(err); // サーバーログにだけ詳細
  res.status(500).json({ error: 'Internal Server Error' }); // クライアントには汎用
});
```

### ❌ 悪い例4: 必須ヘッダー欠如

デフォルト設定のまま → XSS・クリックジャッキング等に弱い。

### ✅ 良い例4: セキュリティヘッダーを設定

```javascript
// Express + helmet
import helmet from 'helmet';
app.use(helmet()); // 基本的なセキュリティヘッダーを自動設定
```

## 最低限設定すべきセキュリティヘッダー

| ヘッダー | 役割 | 推奨値例 |
|---------|------|---------|
| `Strict-Transport-Security` | HTTPS強制 | `max-age=31536000; includeSubDomains` |
| `Content-Security-Policy` | XSS影響の制限 | `default-src 'self'` |
| `X-Content-Type-Options` | MIME sniffing 防止 | `nosniff` |
| `X-Frame-Options` | クリックジャッキング防止 | `DENY` |
| `Referrer-Policy` | Referer 制限 | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | ブラウザ機能の制限 | 用途に応じて設定 |

## 防御の原則

### 1. セキュアなベースラインの確立

- **ハードニング（強化）** された構成テンプレートを用意
- Infrastructure as Code（Terraform、CloudFormation）で構成を一貫させる
- 新環境を作るたびに、同じベースラインから始める

### 2. 本番と開発の分離

- 開発環境の設定（デバッグON、認証簡略化）を本番に持ち込まない
- `.env.production` / `.env.development` を分離
- 本番に開発用エンドポイントを含めない

### 3. 不要なものを削除（Minimize Attack Surface）

- 使わない機能は無効化または削除
- 使わないポートは閉じる
- 退職者・不要アカウントは速やかに削除
- サンプルコード・テストデータを本番に残さない

### 4. 自動スキャン

- **構成スキャナ**: CIS Benchmark、AWS Security Hub、GCP Security Command Center
- **クラウド公開チェック**: AWS Config、Prowler、Scout Suite
- **ヘッダーチェック**: securityheaders.com

### 5. 定期的な見直し

設定は一度決めて終わりではなく、**定期的にレビュー** します。退職者、使われなくなった機能、新たに発見された脆弱性への対応が必要です。

## チェックリスト

### アプリケーション
- [ ] `DEBUG` / verbose モードが本番で無効化されているか？
- [ ] エラー画面から内部情報が漏れていないか？
- [ ] セキュリティヘッダー（helmet相当）を設定しているか？
- [ ] デフォルト認証情報を変更したか？
- [ ] 不要な管理エンドポイントを削除したか？

### インフラ・クラウド
- [ ] S3/GCS/Azureの公開設定を確認したか？
- [ ] DBがインターネットに直接公開されていないか？
- [ ] 不要なポートが開いていないか？
- [ ] 退職者・テストアカウントを削除したか？
- [ ] CORS 設定は適切か？（`origin: '*'` + `credentials: true` は NG）

### プロセス
- [ ] 構成はコード化（IaC）されているか？
- [ ] 本番デプロイ前にセキュリティスキャンを実施しているか？
- [ ] セキュリティベースラインは文書化されているか？

---

## まとめ

- 設定ミスは **コードではなく運用の問題**。頻度が非常に高い
- **デフォルト設定を信じない** のが基本姿勢
- 本番と開発は設定を分離する
- 攻撃面（Attack Surface）を最小化する
- Infrastructure as Code と自動スキャンで、人為ミスを減らす
