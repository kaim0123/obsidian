# A06: 脆弱で古いコンポーネント（Vulnerable and Outdated Components）

## はじめに

現代のアプリケーションは、**自分で書いたコードよりも、外部ライブラリ（依存関係）の方が圧倒的に多い** のが普通です。npm、pip、Maven などで取り込むオープンソースコンポーネントが、アプリの大部分を占めます。

それらに **既知の脆弱性** があって放置されていると、攻撃者はそれを狙ってきます。これが A06 の問題です。

### 具体例でイメージする

- **Apache Struts** の脆弱性で Equifax から1.4億人の個人情報流出（2017年）
- **Log4Shell**（Log4j の脆弱性、2021年）で世界中のJavaアプリが攻撃対象に
- **Heartbleed**（OpenSSL、2014年）でSSL通信の内容を盗まれる
- npmのライブラリが攻撃者に乗っ取られ、悪意あるコードが配布（サプライチェーン攻撃）

これらは「自分のコードは無傷」でも、使っていただけで被害に遭います。

---

## なぜ起きるのか

### 1. 依存関係が多層で、全体を把握しきれない

```
my-app
 ├── express (直接依存)
 │    ├── body-parser
 │    │    └── qs (間接依存)
 │    │         └── ...
 │    └── ...
 └── react
      └── ...
```

Node.jsの平均的なプロジェクトで、依存関係ツリーは数百〜数千パッケージになります。その中のどこか1つに脆弱性があると影響を受けます。

### 2. アップデートが怖い

「動いているものに触りたくない」「破壊的変更が怖い」という心理で、古いバージョンのまま使われ続けます。

### 3. 公開された脆弱性情報は攻撃者にも見える

**CVE**（Common Vulnerabilities and Exposures）として公開された脆弱性は、世界中の攻撃者も知ります。公開後、数日でPoC（攻撃コード例）が出ることも多いです。

---

## 重要な用語

### CVE（Common Vulnerabilities and Exposures）

個別の脆弱性に付けられる **一意のID**。例: `CVE-2021-44228`（Log4Shell）。

### CVSS（Common Vulnerability Scoring System）

脆弱性の **深刻度スコア**（0.0〜10.0）。

| スコア | 深刻度 |
|--------|--------|
| 0.0 | なし |
| 0.1〜3.9 | 低（Low） |
| 4.0〜6.9 | 中（Medium） |
| 7.0〜8.9 | 高（High） |
| 9.0〜10.0 | 緊急（Critical） |

### SBOM（Software Bill of Materials）

アプリに含まれる **全コンポーネントの一覧**。「材料表」のようなもの。米国大統領令で政府調達に必須化され、現在は業界標準になりつつあります。

### SCA（Software Composition Analysis）

依存関係をスキャンして脆弱性を見つけるツールのカテゴリ。

### サプライチェーン攻撃

攻撃者がライブラリや配布パイプラインを汚染し、**正規の配布経路を通じて** マルウェアを広める攻撃。

---

## よくあるリスクパターン

### 1. 古いメジャーバージョンを使い続けている

- Node.js 10 / Python 2 / PHP 5 など、**既にサポートが終了** したランタイム
- セキュリティパッチが提供されないので、新しい脆弱性が出ても修正されない

### 2. 直接依存は更新しても、間接依存が古い

`package.json` に書いていないパッケージでも、依存の依存でインストールされています。そこに脆弱性があると影響を受けます。

### 3. フォーク版や無保守のパッケージを使っている

- メンテナが消えたパッケージ
- スターが付いていない小規模パッケージ
- 最終更新が何年も前のパッケージ

### 4. 使っていないのに入れっぱなし

「ちょっと試したが使わなかった」パッケージが `package.json` に残っている。攻撃面が無駄に広がります。

## 悪い例と対策

### ❌ 悪い例: 依存を放置

```json
{
  "dependencies": {
    "express": "^4.16.0",
    "lodash": "^4.17.10"  // ← Prototype Pollution 脆弱性(古いバージョン)
  }
}
```

### ✅ 良い例1: 定期的な監査

```bash
# npm
npm audit
npm audit fix

# yarn
yarn audit

# pip
pip-audit

# Go
govulncheck ./...
```

### ✅ 良い例2: Dependabot / Renovate で自動化

GitHubの **Dependabot**、あるいは **Renovate** を使うと、新しいバージョンが出るたびに自動でPRを作ってくれます。

```yaml
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
```

### ✅ 良い例3: SBOM の生成

```bash
# Syft でSBOMを生成
syft packages dir:. -o spdx-json > sbom.json

# Grype で脆弱性スキャン
grype sbom:sbom.json
```

## 具体的な防御アプローチ

### 1. インベントリ（在庫表）を作る

まず「何を使っているか」を把握します。

- 直接依存 + 間接依存をすべてリスト化
- バージョン、ライセンス、出所（npm? forked?）を記録
- SBOMツールで自動化

### 2. 脆弱性監視を自動化

- **GitHub Dependabot**（無料、GitHub連携）
- **Snyk**、**Mend**、**Black Duck**（商用）
- **OWASP Dependency-Check**、**Trivy**（OSS）

CI/CDに組み込み、脆弱性のあるPRはマージ不可にする運用が理想。

### 3. 使わないものは削除する

```bash
# npm で使われていないパッケージを検出
npx depcheck

# 不要な依存を削除
npm uninstall <package>
```

### 4. 信頼できるソースからのみ取得

- 公式レジストリ（npm、PyPI、Maven Central）を使う
- 内部プロキシ（Nexus、Artifactory）を経由させ、監査を一元化
- `npm install --ignore-scripts` でインストール時スクリプトを無効化（サプライチェーン攻撃対策）

### 5. バージョン固定とロックファイル

- **ロックファイル**（`package-lock.json`、`Pipfile.lock`、`go.sum`）をコミットする
- 本番ビルドは `npm ci`（lockfile厳密）を使う
- 意図しないバージョンアップを防ぐ

### 6. ランタイムも更新

OS、ランタイム（Node、Python）、コンテナイメージのベースイメージも定期更新。

```dockerfile
# ❌ 具体的でないタグ、古くなりがち
FROM node:latest

# ✅ 明示的なバージョン、かつ定期的に更新
FROM node:20.11-alpine3.19
```

## Log4Shell から学ぶ教訓

2021年12月、**Log4j**（Javaの超有名ログライブラリ）に致命的な脆弱性（CVE-2021-44228）が発見されました。

- CVSS **10.0**（最高）
- 認証不要で **リモートコード実行**
- Java 製のほぼすべてのエンタープライズアプリが影響
- 間接依存のさらに奥に潜んでいるケースが多数

**教訓**:
- SBOMがないと、自分が影響を受けているかすら分からない
- 影響把握と緊急パッチ適用体制を日頃から準備しておく必要がある
- 「有名で枯れている」≠「安全」

## 2026年の事例から（追記 2026-10-17）

2026年は **脆弱性の悪用が漏洩の最大の入口** になりました。Verizon DBIR 2026 では、入口の 31% が脆弱性の悪用で、盗まれた認証情報を初めて上回っています（全体は [[10_2026年_国内情報漏洩の動向と対策]]）。

| 事例 | コンポーネントの問題 |
|---|---|
| KDDI ISP向けメール基盤 | システムの一部に組み込んだ **第三者製ソフトのゼロデイ脆弱性**。5/16 から被害、6/17 に把握。メールアドレス 1,223万件・パスワード 762万件が漏えい |
| タイムズカー | サポートが終わった Java フレームワーク **Seasar2** を使っていたという指摘がある（因果関係は未確認） |
| VPN・ファイル転送製品 | 国内ランサムウェアの入口の約5割が VPN 機器（警察庁、2026年上半期） |

### 教訓

- **ライブラリだけでなく、組み込んだ製品・ミドルウェア・境界機器も** インベントリの対象にする
- **EOL（サポート終了）の技術を洗い出す**。Seasar2 のように国内で広く使われ、今はメンテされていないものは要注意
- 優先度は CVSS だけでなく **CISA KEV（悪用実績）** を重視する
- ゼロデイはパッチでは防げないので、検知と被害限定（[[A09_ログとモニタリングの不備]] / [[05_データ最小化]]）も組み合わせる
- 境界機器の運用は [[07_脆弱性管理（境界機器・パッチ運用）]] にまとめた

---

## まとめ

- 現代のアプリは **大部分が外部コンポーネント**。脆弱性は自分のコード外からやってくる
- **インベントリ化 → 監視 → 自動更新** のサイクルを回す
- Dependabot/Renovate、`npm audit`、SBOMツール等を組み合わせる
- Log4Shell のような事件は再発する前提で、**迅速に対応できる体制** を用意しておく
- 「使わないものは削除」で攻撃面を減らす
