# A02: 暗号化の不備（Cryptographic Failures）

## はじめに

**暗号化の不備** とは、パスワードやクレジットカード番号などの「大切なデータ」を守るべき場面で、暗号化していなかったり、弱い暗号を使っていたり、鍵管理を間違えていたりする問題です。

旧名は **「機密データの露出」**（Sensitive Data Exposure）でした。2021年版で原因にフォーカスした名前に変わっています。

### 具体例でイメージする

- パスワードが平文でDBに保存されている
- クレジットカード番号が http（暗号化なし）で送信される
- 古い暗号方式（MD5、SHA-1、DES）でハッシュ化されている
- 暗号鍵がソースコードに直書きされ、GitHubに公開されてしまった

これらはすべて暗号化の不備です。

---

## 守るべき「機密データ」とは

以下はすべて「暗号化して守るべきデータ」です。

| 分類 | 具体例 |
|------|--------|
| **認証情報** | パスワード、APIキー、秘密鍵、セッショントークン |
| **個人情報（PII）** | 氏名・住所・電話番号・マイナンバー・生年月日 |
| **金融情報** | クレジットカード番号、銀行口座 |
| **医療情報** | 病歴、処方箋 |
| **業務データ** | 顧客リスト、契約情報、社内文書 |

法規制（GDPR、個人情報保護法、PCI-DSS、HIPAA など）で **暗号化が必須** とされているデータもあります。

---

## データの「3つの状態」と暗号化

データには3つの状態があり、それぞれで守り方が違います。

### 1. 転送中（In Transit）

ネットワークを流れているデータ。**TLS（HTTPS）** で守ります。

- http:// ではなく **https://** を使う
- TLS 1.2 以上（理想は1.3）
- 自己署名ではなく、正規の証明書（Let's Encrypt等で無料取得可能）

### 2. 保存中（At Rest）

DBやディスク上のデータ。**暗号化ストレージ** やアプリ層の暗号化で守ります。

- DBの透過的暗号化（TDE）
- ディスク全体の暗号化（BitLocker、FileVault、LUKS）
- クラウドの暗号化（AWS KMS、GCP KMS など）

### 3. 使用中（In Use）

メモリ上のデータ。通常は守りにくいですが、機密性が極めて高い用途では **TEE**（Trusted Execution Environment）や **Confidential Computing** を使います。

## よくある悪い例と対策

### ❌ 悪い例1: パスワードを平文で保存

```javascript
// 絶対にやってはいけない
db.users.insert({ email, password: 'mypassword123' });
```

DBが漏れたら即終了です。

### ✅ 良い例1: 強いハッシュで保存

```javascript
import bcrypt from 'bcrypt';

const hashed = await bcrypt.hash(password, 12); // コスト12
db.users.insert({ email, password: hashed });
```

**パスワードには** `bcrypt`, `scrypt`, `Argon2` を使います。MD5、SHA-1、SHA-256 単体は **パスワード用途では不適切** です（高速すぎて総当たりされる）。

### ❌ 悪い例2: 弱い暗号

```python
# DES、3DES、RC4、MD5、SHA-1 は非推奨
cipher = DES.new(key, DES.MODE_ECB)
```

### ✅ 良い例2: 強い暗号を選ぶ

```python
# 対称暗号: AES-256-GCM
# ハッシュ: SHA-256, SHA-3
# 鍵交換・署名: RSA-2048以上, ECDSA P-256以上
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
aesgcm = AESGCM(key)  # keyは256ビット
ciphertext = aesgcm.encrypt(nonce, plaintext, associated_data)
```

### ❌ 悪い例3: 暗号鍵をソースコードに直書き

```javascript
const SECRET_KEY = 'my-super-secret-key-12345'; // GitHubに公開されたら終了
```

### ✅ 良い例3: 秘密情報管理サービスを使う

- 環境変数
- AWS Secrets Manager / HashiCorp Vault / GCP Secret Manager
- `.env` ファイル（ただし `.gitignore` 必須）

### ❌ 悪い例4: 独自の暗号アルゴリズムを作る

「自分で考えた最強の暗号」は、ほぼ確実に破られます。

### ✅ 良い例4: 標準ライブラリ・標準アルゴリズムを使う

自作せず、**広くレビューされ枯れているライブラリ** を使いましょう。

## 現在推奨される暗号方式（2024時点）

| 用途 | 推奨 | 非推奨 |
|------|------|--------|
| パスワード保存 | Argon2id、bcrypt、scrypt | MD5、SHA-1、SHA-256単体 |
| 対称暗号 | AES-256-GCM、ChaCha20-Poly1305 | DES、3DES、RC4、AES-ECB |
| ハッシュ | SHA-256、SHA-3、BLAKE2 | MD5、SHA-1 |
| 公開鍵署名 | Ed25519、ECDSA P-256、RSA-2048以上 | RSA-1024以下、DSA |
| TLS | TLS 1.3、TLS 1.2 | SSL 3.0以前、TLS 1.0/1.1 |
| 乱数 | `crypto.randomBytes`、`secrets` | `Math.random()`、`rand()` |

## 防御の原則

### 1. 不要なデータは持たない

「そもそも保存しない」が最強の対策です。例えばクレジットカード番号は、自社で保存せず **決済代行サービス（Stripe等）** に任せるのが安全。

### 2. 必要なデータは必ず暗号化

保存時・転送時の両方で暗号化します。

### 3. 暗号鍵の管理を徹底

- 鍵をコードに埋め込まない
- 鍵は定期的にローテーション（交換）する
- 鍵の保存先と暗号対象のデータは別の場所に

### 4. 安全な乱数を使う

セキュリティ用途では、**暗号論的乱数生成器**（CSPRNG）を使います。

```javascript
// ❌ Math.random() は予測可能
// ✅ crypto.randomBytes() を使う
import crypto from 'crypto';
const token = crypto.randomBytes(32).toString('hex');
```

### 5. 通信は常にHTTPS

HSTS（`Strict-Transport-Security`）ヘッダーで、ブラウザに「絶対HTTPSを使え」と指示します。

```
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

## 2026年の事例から（追記 2026-10-17）

全体は [[10_2026年_国内情報漏洩の動向と対策]]。

| 事例 | 暗号化・保存の観点 |
|---|---|
| タイムズカー（約660万アカウント） | パスワードは **復元できない形式** で保存されていた（良い点）。一方で **運転免許証などの画像** 約160万件も対象に含まれた |
| KDDI メール基盤 | 約762万人分の **パスワード** が漏えい |
| 米国防総省 DMDC（海外） | **暗号化していない** 個人情報をファイル共有システムに置いていた |

### 教訓

- **ディスク暗号化（保存時の暗号化）だけでは足りない**。アプリや正規アカウント経由で読まれると、復号されたデータがそのまま出ていく。本人確認書類や口座番号は **アプリ層で項目ごとに暗号化** し、鍵は KMS で管理して、復号できるサービスを限る（エンベロープ暗号化）
- パスワードは bcrypt / Argon2 で保存していれば、漏れても元のパスワードを割り出されにくい
- **変更できない情報**（免許証画像・生年月日）は、暗号化より先に「持たない」ことを考える（[[05_データ最小化]]）

---

## まとめ

- データは **転送中・保存中・使用中** の3状態で守る
- パスワードは **bcrypt / Argon2**、それ以外の暗号は **AES-256-GCM** など標準的なものを
- **自作しない、古いものを使わない、鍵を漏らさない** が三原則
- 「そもそも保存しない」選択が最もリスクを減らす
