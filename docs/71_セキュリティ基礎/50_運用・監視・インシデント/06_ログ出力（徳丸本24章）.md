# 安全なWebアプリケーションの作り方（第24章）

認証・認可・アカウント管理を固めても、**何が起きたかを後から追えない** と、攻撃や事故に気づけず、調査もできません。そのための記録が **ログ出力** です。本章では、ログの目的と種類、記録すべきイベントと項目、保護・保管・時刻合わせ、実装時のログレベルまでを解説します。

| テーマ | 概要 |
|--------|------|
| **ログの目的** | 予兆検知、事後調査、運用監査 |
| **ログの種類** | 層別（Web／アプリ／DB）と用途別（エラー／アクセス／デバッグ） |
| **記録すべきイベントと項目** | 誰が・いつ・何を・どうしたか・結果はどうだったか |
| **保護・出力先・保管期間** | 改ざん防止、置き場所、どれだけ残すか |
| **時刻合わせと実装** | サーバー時刻の同期と、ログレベルの使い分け |

## 📎 ログ出力とは何か

**ログ** とは、アプリケーションやサーバーが「いつ・誰が・何をしたか」「どんなエラーが起きたか」を、時系列で残した記録です。画面には出さず、運用者やセキュリティ担当が後から読むためのメモ、というイメージです。

| 用語 | 意味 |
|------|------|
| **ログ出力** | 処理の途中や結果を、ファイルやログ基盤に書き出すこと |
| **アクセスログ** | リクエストや操作の履歴 |
| **エラーログ** | 失敗や例外の記録 |
| **監査ログ** | セキュリティや運用監査に使う、重要な操作の記録 |

### 日常生活での例え

- **ログ**: マンションのオートロックが「何時に誰のカードで開いたか」を残す入退室記録
- **予兆検知**: 深夜に何度も失敗している記録を見て、不正侵入の疑いを早めに察知する
- **事後調査**: 荷物が消えたあと、誰がいつその部屋に入ったかを記録からたどる
- **運用監査**: 「ルールどおり運用しているか」を、記録を見て第三者に説明できる

### なぜ重要か

ログが無い、または足りないと、次のような困りごとが起きます。

```
・攻撃されているのに気づけない
・被害が出ても、「誰が・いつ・何をしたか」が分からない
・パスワード変更や権限変更の履歴がなく、不正操作を証明できない
・障害の原因調査に時間がかかる
・監査やインシデント報告で説明できない
```

「ログイン画面を固めた」「認可を入れた」だけでは、**起きた事実を残す** ことにはなりません。ログは、防御の最後の砦というより、**防御と運用を支える証拠とセンサー** です。

## 🎯 ログ出力の目的

ログを取る理由は、大きく次の3つです。

| 目的 | 何のためか | 例 |
|------|------------|-----|
| **予兆の把握と早期対策** | 攻撃や事故の前兆をログから見つけ、被害が大きくなる前に止める | 短時間に大量のログイン失敗、異常な権限エラーの増加 |
| **事後調査** | 事故や攻撃のあと、「何が起きたか」を時系列で再現する | いつ・どのIP・どのユーザーが・どのデータを触ったか |
| **運用監査** | ルールどおり運用されているかを確認し、説明責任を果たす | 管理者による重要データの参照・変更履歴 |

### 攻撃や事故の予兆を把握し、早期に対策するため

攻撃は、いきなり成功するとは限りません。パスワードの総当たり、権限のないURLへの連続アクセス、異常なAPI呼び出しなどは、**失敗や拒否のログとして先に現れます**。

```
【予兆のイメージ】
・同じIPから、1分に100回ログイン失敗
・存在しないユーザーIDへのログイン試行が急増
・一般利用者なのに /admin 配下へのアクセスが続く
・深夜帯だけ、特定アカウントへのパスワード変更が繰り返される
```

こうしたパターンを監視（アラート）しておけば、アカウントロックやIP制限、担当者への通知など、**被害が広がる前の対策** が取れます。ログは「あとから読むもの」だけでなく、「今起きている異常を知らせるもの」でもあります。

### 攻撃や事故の事後調査のため

被害が分かったあと、次の問いに答える必要があります。

```
・いつ始まったか
・誰（どのアカウント・どのIP）が関与したか
・どのデータ・機能が触られたか
・成功した操作と失敗した操作は何か
・まだ影響が残っていないか
```

ログが無いと、推測しかできません。ログがあれば、**時系列で事実を組み立て**、影響範囲の特定や再発防止に使えます。

### アプリケーションの運用監査のため

社内規定や法令、取引先との契約で、「重要な操作は記録し、一定期間保管する」ことが求められる場合があります。管理者による個人情報の参照、権限変更、データ削除などは、**正当な業務でも記録が必要** です。

```
監査で見られることの例:
・誰がいつ、顧客情報を参照・出力したか
・権限の付与・剥奪は誰が行ったか
・システム設定の変更履歴はあるか
```

「やっていない」ではなく、「やっていないことがログから分かる／やったことがログに残っている」状態が、運用監査の土台です。

## 📚 ログの種類

ログは、**どこが出すか（層）** と **何のために使うか（用途）** の両方で整理すると分かりやすいです。

### 層による分類（Webサーバー・アプリケーション・データベース）

| 種類 | 誰が出すか | 主な内容 | 向いている調査 |
|------|------------|----------|----------------|
| **Webサーバーのログ** | nginx、Apache など | リクエストのURL、ステータスコード、IP、応答時間 | アクセス全体の把握、404/500の傾向、攻撃の入口 |
| **アプリケーションのログ** | 自作のWebアプリ | ログイン成否、業務操作、例外、認可拒否 | 「誰が何をしたか」の業務・セキュリティ調査 |
| **データベースのログ** | MySQL、PostgreSQL など | 接続、遅いクエリ、エラー、監査設定次第ではSQL | DB障害、不正な大量取得の手がかり |

```
【層のイメージ】
ブラウザ
  → Webサーバー（アクセスログ）
    → アプリケーション（業務・セキュリティログ）
      → データベース（DBログ）
```

セキュリティ調査では、**アプリケーションログが中心** になることが多いです。Webサーバーログだけでは「どのユーザーがパスワードを変えたか」までは分からないことが多く、DBログだけでは「画面上のどの操作か」が分かりにくいためです。三者を組み合わせると、より正確に再現できます。

### 用途による分類（エラー・アクセス・デバッグ）

| 種類 | 何を残すか | 本番での扱い |
|------|------------|--------------|
| **エラーログ** | 例外、失敗、想定外の状態 | 必ず残し、監視する |
| **アクセスログ** | リクエストや重要操作の履歴 | セキュリティ・監査用に残す |
| **デバッグログ** | 開発時の詳細な内部状態 | 本番では原則オフ、または最小限 |

デバッグログは原因調査に便利ですが、**個人情報やパスワード、トークンが混ざりやすい** です。本番で出しっぱなしにすると、ログ自体が情報漏洩の原因になります。

## 📝 ログに記録すべきイベント

すべてを記録すると量が増えすぎ、重要な出来事が埋もれます。セキュリティと監査の観点では、少なくとも次のイベントは残します。

| イベント | なぜ記録するか |
|----------|----------------|
| **ログイン・ログアウト** | なりすましや不正利用の入口・出口を追うため |
| **アカウントロック** | 総当たり攻撃や、ロック解除の不正を検知するため |
| **ユーザー登録・削除** | 不正なアカウント作成や、痕跡消しを防ぐため |
| **パスワード変更** | 乗っ取り後の定着や、本人以外の変更を追うため |
| **重要情報の参照** | 個人情報などの覗き見・持ち出しを監査するため |
| **重要な操作** | 権限変更、設定変更、削除、送金など、影響の大きい処理のため |

### ログイン・ログアウト

成功だけでなく、**失敗も記録** します。失敗だけが急増していると、パスワード試行の予兆になります。

```
記録したい例:
・ログイン成功（ユーザーID、IP、時刻）
・ログイン失敗（入力されたID、IP、時刻、失敗理由の概要）
・ログアウト（ユーザーID、IP、時刻）
```

失敗理由は、「パスワード不一致」「アカウント停止中」など、運用に必要な粒度に留めます。パスワードそのものは絶対に書きません。

### アカウントロック

ロック発生と、ロック解除（自動解除・管理者解除）を残します。「誰がロックを外したか」が無いと、攻撃者がロックを解除した痕跡を追えません。

### ユーザー登録・削除

新規登録の成功、削除（退会）の実行者、対象アカウントを残します。攻撃者が自分用の裏口アカウントを作ったり、調査前にアカウントを消したりする動きを追うためです。

### パスワード変更

本人による変更、管理者によるリセット、パスワード忘れによる再設定は、いずれも **アカウント乗っ取りの定着手段** になり得ます。成功・失敗の両方を残します。

### 重要情報の参照

「変更」だけでなく、「見るだけ」も被害になります。顧客の個人情報、クレジットカード情報、社外秘の帳票など、**参照そのものが監査対象** になるデータを決め、閲覧ログを残します。

### 重要な操作

サービスごとに「重要」の定義は違いますが、次のような操作は候補です。

```
・権限・ロールの変更
・管理者機能の利用
・データの一括エクスポート
・設定変更（セキュリティ設定、通知先など）
・金銭やポイントの移動
・データの削除・論理削除の解除
```

「失敗した操作」も残します。認可で拒否された操作の連続は、権限昇格や他人データへの攻撃の予兆です。

## 📋 ログの出力項目

イベントを記録するとき、最低限そろえたい項目は次のとおりです。**誰が・いつ・どこから・何に対して・何をして・どうなったか** が後から分かる形にします。

| 項目 | 内容 | 例 |
|------|------|-----|
| **アクセス日時** | いつ起きたか（タイムゾーン付きが望ましい） | 2026-07-04T15:30:00+09:00 |
| **リモートIPアドレス** | どこから来たか | 203.0.113.10 |
| **ユーザーID** | 誰が行ったか（未ログインならその旨） | user_12345 / anonymous |
| **アクセス対象** | どの機能・画面・APIか | /orders/42、script_id=checkout |
| **操作内容** | 何をしたか | 閲覧、変更、削除、ログイン |
| **操作対象** | どのリソースか | order_id=42、user_id=99 |
| **操作結果** | 成功か失敗か、件数など | success / failure、件数=1 |

```
【良いログのイメージ（1行）】
2026-07-04T15:30:00+09:00 ip=203.0.113.10 user=user_12345
action=UPDATE target=order_id=42 result=success

【悪いログのイメージ】
エラーが起きました
→ いつ・誰が・何をしたか分からない
```

### 各項目のポイント

| 項目 | 初心者がつまずきやすい点 |
|------|--------------------------|
| **日時** | サーバーごとに時刻がずれていると、複数ログを突き合わせられない（後述の時刻合わせ） |
| **IPアドレス** | プロキシやロードバランサ経由では、転送ヘッダの扱いに注意。なりすまし可能なヘッダを盲信しない |
| **ユーザーID** | セッション上のIDを使う。リクエストパラメータの「自称ユーザーID」は信用しない |
| **アクセス対象** | URLだけでなく、画面IDやAPI名があると業務調査がしやすい |
| **操作内容・対象** | 「更新しました」だけでは不十分。何のIDをどうしたかを残す |
| **操作結果** | 成功だけ残すと、攻撃の失敗パターンが見えない |

### 書いてはいけないもの

ログは運用者が読む前提でも、**秘密情報そのものを書いてはいけません**。

```
ログに書いてはいけない例:
・パスワード（平文・ハッシュ問わず、入力値は残さない）
・クレジットカード番号、セキュリティコード
・セッションIDやAPIトークン（漏洩するとなりすましに使える）
・個人情報の本文を必要以上に長く残すこと
```

「調査に必要だから全部残す」ではなく、**調査に必要な識別子（ID）は残し、秘密の中身は残さない** のが基本です。

## 🔒 ログの保護

ログには、ユーザーID、IP、操作内容など、攻撃者にとって有用な情報が含まれます。ログが読めたり書き換えられたりすると、次の被害が起きます。

| リスク | 何が起きるか |
|--------|--------------|
| **漏洩** | ログから個人情報やシステムの内部構造が漏れる |
| **改ざん・削除** | 攻撃者が自分の痕跡を消す、または他人に罪をなすりつける |
| **不正な追加** | 偽のログを混ぜて調査を混乱させる |

### 保護の基本

```
1. ログファイルの閲覧・変更権限を、必要最小限の担当者・プロセスに限定する
2. アプリケーションの実行ユーザーが、過去ログを自由に削除・改ざんできないようにする
3. 可能なら、アプリサーバーとは別の場所（専用ログサーバー、クラウドのログサービス）へ転送する
4. 転送後のログは追記のみ（改ざんしにくい）にする
5. バックアップとアクセス監査を行い、ログ自体の操作も追跡できるようにする
```

攻撃者は、侵入後に **自分の足跡を消す** ことが多いです。アプリと同じディスク上のログだけに頼ると、侵入と同時に消される可能性があります。**書き出したあと、すぐ別の場所へ送る** 設計が有効です。

## 📤 ログの出力先

ログの置き場所は、用途と保護のしやすさで選びます。

| 出力先 | 特徴 | 向いている用途 |
|--------|------|----------------|
| **ローカルファイル** | 実装が簡単。サーバー障害時も残ることがある | 小規模、まずは確実に残す |
| **標準出力／コンテナログ** | コンテナ環境で収集しやすい | クラウド・オーケストレーション |
| **専用ログサーバー・SIEM** | 集約・検索・アラートがしやすい | 本格的な監視とインシデント対応 |
| **クラウドのログサービス** | 保管・権限管理・保持期間の設定がしやすい | マネージド運用 |

```
【推奨イメージ】
アプリ →（即時または短時間で）→ 集約先（改ざんしにくい保管庫）
                ↘ ローカルにも短期間残す（転送失敗時の保険）
```

開発環境と本番環境で出力先を分け、**本番のログにデバッグ用の詳細が流れない** ようにします。また、ログの出力先自体がインターネットに公開されていないかも確認します。

## 🗓️ ログの保管期間

ログは永遠に残す必要はありませんが、短すぎると調査や監査に使えません。

| 観点 | 考え方 |
|------|--------|
| **インシデント調査** | 発覚が遅れることもあるため、数週間〜数か月分はすぐ検索できると安心 |
| **法令・契約・社内規定** | 業種によっては保持期間が決まっている |
| **容量とコスト** | 古いログは圧縮・アーカイブし、ホット（すぐ見る）とコールド（安く長く置く）を分ける |

```
運用の例:
・直近90日: 検索しやすい場所に置く（調査用）
・それ以降: アーカイブして長期保管（監査・重大インシデント用）
・保持期間を過ぎたら、手順に従って削除する
```

保管期間は「なんとなく1週間」ではなく、**調査に必要な長さ** と **規定上の長さ** の両方を満たすように決めます。削除するときも、誤って必要な期間より早く消さないよう、自動化の設定を確認します。

## ⏰ サーバーの時刻合わせ

ログ調査では、Webサーバー・アプリ・DB・認証基盤など、**複数のログを時刻で突き合わせます**。サーバーごとに時計がずれていると、同じ事件なのに順序が入れ替わって見えます。

```
【時刻ずれの問題】
サーバーAのログ: 15:00:10 ログイン成功
サーバーBのログ: 15:00:05 権限変更（実際はログイン後なのに、時刻だけ見ると前）
→ 調査で因果関係を誤る
```

### 対策

| 対策 | 説明 |
|------|------|
| **NTPなどで時刻同期する** | すべてのサーバーの時計を信頼できる時刻源に合わせる |
| **タイムゾーンを統一して記録する** | UTCで統一するか、オフセット付き（+09:00）で残す |
| **同期状態を監視する** | 時刻同期が止まったら気づけるようにする |

「ログに日時を出す」だけでなく、**その日時が信頼できること** が調査の前提です。

## 🛠️ ログ出力の実装

実装では、フレームワークや言語のロギングライブラリを使い、**ログレベル** で出し分けます。重要度の高いものから順に示すと、次のとおりです。

| レベル | 意味 | 使う場面の例 | 本番での扱い |
|--------|------|--------------|--------------|
| **fatal** | 致命的。サービス継続が難しい | 起動不能、必須設定の欠落 | 必ず出す。即対応 |
| **error** | エラー。処理は失敗したが、プロセスは生きている | 例外、外部API失敗、DBエラー | 必ず出す。監視する |
| **warn** | 警告。すぐ落ちないが、放置すると問題になり得る | リトライ発生、設定の非推奨、認可拒否の連続 | 出す。閾値でアラートも検討 |
| **info** | 通常運用の重要な出来事 | ログイン成功、設定変更、バッチ開始・終了 | 監査・運用に必要な範囲で出す |
| **debug** | 開発・調査用の詳細 | 変数の値、分岐の途中経過 | 本番では原則オフ |
| **trace** | debugよりさらに細かい追跡 | ループ内の逐次出力など | 本番では原則オフ |

```
重要度（高い → 低い）:
fatal > error > warn > info > debug > trace
```

### レベルの使い分けの考え方

```
・セキュリティ上重要なイベント（ログイン、権限変更、重要情報参照）
  → info 以上で、必ず残る設定にする
・想定外の失敗
  → error（または状況により fatal）
・攻撃の予兆になり得る拒否や異常
  → warn または info（監視しやすいレベルで統一する）
・変数ダンプや詳細トレース
  → debug / trace（開発時のみ）
```

本番のログレベルを `debug` のままにすると、量が増えてディスクを圧迫し、秘密情報が混入しやすくなります。**本番は info 以上を基本** とし、障害調査のときだけ一時的に詳細化する運用が安全です。

### 実装時の注意点

| 注意点 | 説明 |
|--------|------|
| **例外を握りつぶさない** | エラーを無視すると、errorログも残らず調査不能になる |
| **ログ出力自体の失敗を想定する** | ディスク満杯などで書けなくても、本処理の扱いを決めておく |
| **フォーマットを揃える** | 日時・レベル・メッセージの形式を統一すると検索しやすい |
| **リクエストIDを付ける** | 1回の操作にIDを振り、複数行のログを追えるようにする |
| **ユーザー入力をそのまま長く書かない** | ログインジェクションや、想定外の巨大ログを防ぐ |

```
【リクエストIDのイメージ】
request_id=abc-123 user=user_1 action=login result=failure
request_id=abc-123 reason=bad_password
→ 同じ操作のログを request_id でまとめられる
```

## 📋 まとめ

| テーマ | 本質 | 対策の要点 |
|--------|------|------------|
| **目的** | 予兆・調査・監査の材料を残す | 失敗も含めて重要な出来事を記録する |
| **種類** | 層と用途で役割が違う | アプリログを中心に、必要に応じて組み合わせる |
| **イベント** | 認証・アカウント・重要操作が中心 | 成功だけでなく失敗も残す |
| **項目** | 誰が・いつ・何を・どうしたか | 秘密情報は書かず、識別子と結果を残す |
| **保護** | ログも攻撃対象 | 権限制限と、別場所への転送 |
| **出力先・保管** | 残す場所と期間を決める | 集約・保持期間・削除手順を明確にする |
| **時刻** | 複数ログの突き合わせの前提 | NTPなどで全サーバーを同期する |
| **実装** | レベルで出し分ける | 本番は info 以上を基本、debug は出さない |

```
ログ出力の基本:

1. 予兆検知・事後調査・運用監査の3目的を意識して設計する
2. ログイン、アカウント変更、重要情報の参照・操作を必ず残す
3. 日時・IP・ユーザー・対象・操作・結果をそろえる
4. パスワードやトークンなど秘密情報はログに書かない
5. ログの改ざん・削除・漏洩を防ぐ（権限と転送先）
6. 保管期間を決め、規定と調査に耐える長さを残す
7. サーバー時刻を合わせ、タイムゾーンを明確にする
8. ログレベルを使い分け、本番では debug/trace を出さない
```
