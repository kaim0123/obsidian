# 第4章：ネットワーク・アプリケーション・エンドポイントのセキュリティ

第1〜3章で脅威、分析技術、基本概念を学んだ。本章では **実際のシステムを守るための技術と仕組み** を、ネットワークからアプリケーション、端末、そして最新のセキュリティモデルまで順に整理する。

---

## 1. ネットワークの基礎

セキュリティを理解するには、まず **データがどうやって届くか** を知る必要がある。

### 1.1 TCP/IP

**インターネットの事実上の標準プロトコル群。** 現在のネットワーク通信のほとんどは TCP/IP 上で動いている。

| プロトコル | 層 | 役割 | 例 |
|------------|-----|------|-----|
| **IP** | ネットワーク層 | パケットに宛先アドレス（IPアドレス）を付けて届ける | `192.168.1.1` |
| **TCP** | トランスポート層 | 信頼性のある通信（届いたか確認、順序保証） | Web（HTTPS）、メール |
| **UDP** | トランスポート層 | 高速だが確認なし（ストリーミング、DNS） | 動画配信、DNS |
| **ICMP** | ネットワーク層 | エラー通知、疎通確認（ping） | ping コマンド |

**セキュリティの観点：**
- ファイアウォールは主に **IPアドレス・ポート番号** で通信を制御する
- 攻撃者は **ポートスキャン** で開いているサービスを探す
- よく使うポート：80（HTTP）、443（HTTPS）、22（SSH）、3389（RDP）

---

### 1.2 OSI参照モデル

ネットワーク通信を **7つの層** に分けて理解するための枠組み。TCP/IP との対応も覚えておくと、どこでセキュリティ対策が効くかがわかりやすい。

| 層 | OSI | 主な機能 | TCP/IP 対応 | セキュリティの例 |
|----|-----|----------|-------------|------------------|
| 7 | アプリケーション | Web、メールなど | HTTP, SMTP | WAF、入力検証 |
| 6 | プレゼンテーション | データ形式の変換 | TLS（ここに位置づけることも） | 暗号化 |
| 5 | セッション | 通信の確立・維持 | — | セッション管理 |
| 4 | トランスポート | 端到端の通信 | TCP, UDP | ポート制御 |
| 3 | ネットワーク | ルーティング | IP | ファイアウォール、VPN |
| 2 | データリンク | 同一ネットワーク内の通信 | Ethernet | MAC フィルタ |
| 1 | 物理 | ケーブル、電波 | — | 物理的アクセス制御 |

> 日常のセキュリティ議論では **L3（ネットワーク）〜 L7（アプリケーション）** という言い方がよく使われる。

---

## 2. ファイアウォールと周辺技術

**ネットワークの境界で、許可された通信だけを通す** 装置・ソフトウェア。

### 2.1 ファイアウォールの3つのタイプ

| タイプ | 見る層 | 仕組み | 長所 | 短所 |
|--------|--------|--------|------|------|
| **パケットフィルタリング型** | L3/L4 | IP・ポート・プロトコルごとに許可/拒否 | 高速・シンプル | 内容は見ない |
| **ステートフルインスペクション型** | L3/L4 | 通信の「状態」（接続中か）も追跡 | 不正なパケットを弾きやすい | アプリ内容は見ない |
| **アプリケーション型（プロキシ型）** | L7 | アプリケーションプロトコル（HTTP等）の中身まで検査 | 詳細な制御が可能 | 処理が重い |

**例：**
```
パケットフィルタ：「443番ポートへの通信は許可」
ステートフル：「外向きに開始したHTTPS接続の返答だけ許可」
アプリケーション型：「HTTP通信の中身にウイルスがないか検査」
```

---

### 2.2 IDS・IPS・CDN

| 技術 | 正式名称 | 役割 |
|------|----------|------|
| **IDS** | Intrusion Detection System | 侵入を**検知してアラート**（第2章参照） |
| **IPS** | Intrusion Prevention System | 侵入を**検知してブロック** |
| **CDN** | Content Delivery Network | コンテンツを世界各地のサーバーに分散配置し、高速配信。**DDoS緩和**やWAF機能も提供 |

**CDN のセキュリティ的メリット：**
- 攻撃トラフィックをエッジ（末端）で吸収
- オリジンサーバー（本番サーバー）への直接攻撃を減らす
- Cloudflare、Akamai、AWS CloudFront など

## 3. 暗号化通信

ネットワーク上の通信を盗み見・改ざんから守る技術（第3章の TLS を実務視点で整理）。

### 3.1 VPN（Virtual Private Network）

**インターネット上に「仮想の専用線」を作り、通信を暗号化する** 技術。

| 用途 | 説明 |
|------|------|
| **リモートアクセス VPN** | 在宅・外出先から社内ネットワークに安全に接続 |
| **サイト間 VPN** | 拠点同士をインターネット経由で接続 |

**仕組み：** 端末 → 暗号化トンネル → VPNサーバー → 社内ネットワーク

**代表プロトコル：** IPsec、OpenVPN、WireGuard

---

### 3.2 HTTPS と TLS ハンドシェイク

**Web通信を暗号化する仕組み。** ブラウザとサーバー間で TLS（旧SSL）を使う。

#### HTTPS 確立の4ステップ

```
① TLSハンドシェイク（接続の開始・能力の交渉）
      ↓
② デジタル証明書の送付（サーバーが身元を提示）
      ↓
③ 暗号化キーの交換（セッション鍵を安全に決定）
      ↓
④ 通信の暗号化（以降、AES等でデータを暗号化してやり取り）
```

| ステップ | 何が起きるか |
|----------|--------------|
| **① ハンドシェイク** | クライアント「接続したい」→ サーバー「対応する暗号方式はこれ」 |
| **② 証明書** | サーバーが CA 発行の証明書を送る。ブラウザが CA の署名を検証 |
| **③ 鍵交換** | 公開鍵暗号でセッション鍵（共通鍵）を安全に共有 |
| **④ 暗号化通信** | セッション鍵で HTTP データを暗号化して送受信 |

**初心者の確認方法：** アドレスバーが `https://` で、鍵マークが表示されているか

**注意：** HTTPS は通信経路の保護であり、**サイト自体が安全とは限らない**（フィッシングサイトも HTTPS 化できる）

---

### 3.3 Wi-Fi セキュリティ

無線LANの暗号化方式。古い方式ほど危険。

| 方式 | 状態 | 説明 |
|------|------|------|
| **WEP** | **非推奨（危険）** | 最初期の方式。数分で解読可能 |
| **WPA** | 非推奨 | WEP の改良版だが、現在は不十分 |
| **WPA2** | 現行（一般的） | AES 暗号。2018年の KRACK 攻撃以降、パッチ必須 |
| **WPA3** | **推奨（最新）** | より強固な暗号、オフライン辞書攻撃への耐性向上 |
| **オープンネットワーク** | 暗号化なし | カフェ等の公共Wi-Fi。**VPNなしでの機密通信は危険** |

**公共Wi-Fi 利用時の基本：**
- 機密情報（銀行、社内システム）は避ける、または VPN を使う
- 「自動接続」をオフにする
- 自宅・オフィスの Wi-Fi は WPA2 以上（可能なら WPA3）を使う

## 4. メールのセキュリティ

メールは **送信者のなりすまし** が容易。SPF・DKIM・DMARC で送信元の真正性を検証する。

### 4.1 3つの仕組み

| 仕組み | 正式名称 | 何を検証するか | 仕組み |
|--------|----------|----------------|--------|
| **SPF** | Sender Policy Framework | 送信元IPが正規か | DNS に「このドメインのメールはこのIPから送る」と登録 |
| **DKIM** | DomainKeys Identified Mail | メールが改ざんされていないか | 送信者がメールにデジタル署名を付け、受信側が検証 |
| **DMARC** | Domain-based Message Authentication | SPF/DKIM の結果をどう扱うか指示 | 「失敗したメールは拒否/隔離/報告」と DNS で宣言 |

### 4.2 動作の流れ

```
送信者が example.com からメール送信
    ↓
受信側が SPF を確認：「このIPは example.com の正規サーバーか？」
    ↓
受信側が DKIM を確認：「署名は正しいか？改ざんされていないか？」
    ↓
DMARC ポリシーに従い：拒否 / 隔離（スパムフォルダ）/ 受信
```

**組織としての対策：** 自社ドメインに SPF・DKIM・DMARC を設定し、なりすましメールを防ぐ

## 5. アプリケーションセキュリティ

Webアプリケーションは **インターネットに直接公開される** ことが多く、攻撃の主要な標的になる。

### 5.1 Web の基本構成

| 要素 | 役割 | セキュリティの観点 |
|------|------|-------------------|
| **Webブラウザ** | ユーザー側の表示・操作 | XSS 被害を受ける側 |
| **HTTP通信** | クライアントとサーバーのやり取り | HTTPS 化、ヘッダー設定 |
| **JavaScript** | ブラウザ上で動くプログラム | 悪意のあるスクリプト実行（XSS） |
| **データベース** | データの保存・検索 | SQLインジェクション |
| **セッション管理** | ログイン状態の維持 | セッションID の保護 |

---

### 5.2 代表的な脆弱性

| 脆弱性 | 概要 | 被害の例 |
|--------|------|----------|
| **SQLインジェクション** | SQL文に悪意のある入力を混ぜる | DB全体の漏洩・改ざん |
| **クロスサイトスクリプティング（XSS）** | 他ユーザーのブラウザで悪意のスクリプトを実行 | セッション窃取、偽ページ表示 |

**SQLインジェクションの例：**
```
入力欄に ' OR '1'='1 を入力
→ SQL が「全ユーザーを返せ」と解釈されてしまう
```

**XSS の例：**
```
掲示板に <script>悪意のあるコード</script> を投稿
→ 他ユーザーがそのページを開くとスクリプトが実行される
```

---

### 5.3 セッション管理と Cookie の属性

ログイン後、サーバーは **セッションID** を Cookie でブラウザに渡す。この Cookie の設定が重要。

| 属性 | 効果 |
|------|------|
| **HttpOnly** | JavaScript から Cookie にアクセスできなくする → XSS によるセッション窃取を防ぐ |
| **Secure** | HTTPS 通信でのみ Cookie を送る → 平文通信での Cookie 漏洩を防ぐ |
| **SameSite** | 他サイトからのリクエストで Cookie を送らない → CSRF を軽減 |

**設定例：**
```
Set-Cookie: sessionid=abc123; HttpOnly; Secure; SameSite=Strict
```

---

### 5.4 セキュア設計（ビジネスロジック）

技術的な脆弱性以外に、**アプリケーションの設計・仕様そのもの** に穴がある場合がある。

| 問題 | 例 |
|------|-----|
| **権限チェックの欠如** | URL を直接入力すると他人のデータが見える |
| **レート制限なし** | クーポンを無限に使える、パスワード試行が止まらない |
| **ワークフローの欠陥** | 決済前に商品を先に発送してしまう |

**対策：** 脅威モデリング、コードレビュー、ペネトレーションテスト

## 6. ソフトウェアセキュリティ

アプリケーションの **開発プロセス全体** でセキュリティを組み込む。

### 6.1 代表的な脆弱性（実装レベル）

| 脆弱性 | 説明 | 結果 |
|--------|------|------|
| **バッファオーバーフロー** | 想定より多くのデータを書き込み、メモリを破壊 | 任意コード実行 |
| **リモートコード実行（RCE）** | ネットワーク経由で攻撃者のコードを実行させる | サーバー完全乗っ取り |

> 現代の言語（Java、Python、C# 等）はメモリ保護機能があるが、C/C++ や unsafe な処理では依然として重要。

---

### 6.2 開発プロセスのセキュリティ

| 概念 | 説明 |
|------|------|
| **セキュアコーディング** | 最初から安全なコードを書く規約・ガイドライン（入力検証、エスケープ、最小権限） |
| **依存・パッチ管理** | 使っているライブラリの脆弱性を把握し、更新する（第3章の CVE 参照） |
| **CI/CD** | Continuous Integration / Delivery。コード変更を自動ビルド・テスト・デプロイ |
| **DevSecOps** | 開発（Dev）+ セキュリティ（Sec）+ 運用（Ops）を統合。セキュリティを開発パイプラインに組み込む |
| **シフトレフト** | セキュリティ対策を **開発の早い段階（左側）** に移す。本番後ではなく設計・コーディング段階で対策 |

**DevSecOps パイプラインの例：**
```
コード作成 → 静的解析（SAST）→ 依存関係スキャン（SCA）→ テスト → デプロイ → 動的解析（DAST）
     ↑ ここ（左）でセキュリティ問題を見つける = シフトレフト
```

---

## 7. エンドポイントのセキュリティ

PC、サーバー、スマートフォンなど **個々の端末** を守る。

### 7.1 防御技術

| 技術 | 説明 |
|------|------|
| **アンチウイルスソフト** | 既知マルウェアのシグネチャを検知・駆除 |
| **EDR** | Endpoint Detection and Response。端末の行動を監視し、未知の脅威も検知・調査 |
| **ディスク暗号化** | 端末紛失時にデータを読まれないようにする（BitLocker、FileVault 等） |
| **改ざん検知** | ファイルや設定の不正変更を検知（FIM: File Integrity Monitoring） |

**アンチウイルス vs EDR：**

| | アンチウイルス | EDR |
|---|--------------|-----|
| 検知方式 | 既知パターン（シグネチャ） | 行動分析＋シグネチャ |
| 未知の脅威 | 弱い | 強い |
| 調査機能 | 限定的 | 詳細なタイムライン・原因分析 |

---

### 7.2 運用・管理

| 項目 | 説明 |
|------|------|
| **パッチ管理** | OS・アプリの脆弱性修正を定期的に適用 |
| **バックアップとリカバリ** | ランサムウェア等からの復旧手段。3-2-1 ルール（3コピー、2種類の媒体、1つはオフサイト） |
| **ログ管理** | 端末の操作履歴を記録し、インシデント調査に使う |
| **SBOM** | Software Bill of Materials。ソフトウェアに含まれる部品（ライブラリ）の一覧。サプライチェーン攻撃対策 |

---

### 7.3 インシデント対応体制

| 組織 | 正式名称 | 役割 |
|------|----------|------|
| **CSIRT** | Computer Security Incident Response Team | 組織全体のセキュリティインシデント対応チーム |
| **PSIRT** | Product Security Incident Response Team | 特定製品の脆弱性対応チーム（ベンダー企業向け） |

**インシデントレスポンスの流れ（復習）：**
```
準備 → 検知・分析 → 封じ込め → 根絶 → 復旧 → 事後対応（教訓）
```

## 8. セキュリティモデルと最新技術

組織全体のセキュリティ **考え方（モデル）** と、それを支える **統合プラットフォーム**。

### 8.1 境界防御モデル vs ゼロトラスト

| モデル | 考え方 | 弱点 |
|--------|--------|------|
| **境界防御（パリメータモデル）** | 社内ネットワークは「安全な城」、外部は「敵地」。ファイアウォールで守る | 内部からの脅威、クラウド時代の境界の曖昧さ |
| **ゼロトラスト** | 「内外問わず、一切信頼しない」。常に認証・認可・検証 | 導入・運用が複雑 |

**ゼロトラストの原則：**
- ネットワークの位置（社内/社外）で信頼度を決めない
- 最小権限の原則を常に適用
- すべてのアクセスを継続的に検証

---

### 8.2 多層防御（Defense in Depth）

**1つの対策に頼らず、複数の層で防御する** 考え方。

```
【多層防御の例】
  物理セキュリティ（入退室管理）
      ↓
  ネットワーク（ファイアウォール、セグメンテーション）
      ↓
  エンドポイント（EDR、アンチウイルス）
      ↓
  アプリケーション（WAF、入力検証）
      ↓
  データ（暗号化、アクセス制御）
      ↓
  人（教育、ポリシー）
```

1層が破られても、次の層で被害を食い止める。

---

### 8.3 統合セキュリティプラットフォーム

| 技術 | 正式名称 | 役割 |
|------|----------|------|
| **SIEM** | Security Information and Event Management | ログ集約・相関分析・アラート（第2章参照） |
| **XDR** | Extended Detection and Response | エンドポイント・ネットワーク・クラウド等を横断的に検知・対応 |
| **UEBA** | User and Entity Behavior Analytics | ユーザー・端末の行動異常を機械学習で検知 |
| **SOAR** | Security Orchestration, Automation and Response | インシデント対応の自動化・ワークフロー化 |
| **CASB** | Cloud Access Security Broker | クラウドサービス（SaaS）へのアクセスを監視・制御 |
| **SWG** | Secure Web Gateway | Web トラフィックをフィルタリング（マルウェア、不正サイト） |
| **SASE** | Secure Access Service Edge | ネットワークとセキュリティをクラウドで統合（VPN + SWG + CASB + FWaaS） |

**関係のイメージ：**
```
【従来】 拠点ごとに FW + VPN + プロキシ … バラバラ
【SASE】  クラウド上でネットワーク＋セキュリティを統合提供
              ├─ SWG（Web保護）
              ├─ CASB（クラウド保護）
              ├─ FWaaS（ファイアウォール）
              └─ ZTNA（ゼロトラストアクセス）
```

---

### 8.4 動的アクセス制御（Conditional Access）

**ユーザーの属性・端末状態・リスクスコアに応じて、アクセスを動的に許可/拒否する** 仕組み。ゼロトラストの実装要素。

| 判断要素 | 例 |
|----------|-----|
| ユーザー | 管理者か、一般ユーザーか |
| 端末 | 社給PCか、個人端末か、パッチは最新か |
| 場所 | 社内か、海外か |
| リスク | ログイン失敗の回数、通常と異なる時間帯 |

**例：** 「海外からの管理者ログイン → MFA を追加要求」「パッチ未適用端末 → 社内リソースへのアクセス拒否」

---

## 9. 技術の全体マップ

```
【ネットワーク層】
  TCP/IP / OSI → ファイアウォール → IDS/IPS → CDN
  暗号化通信 → VPN、HTTPS（TLS）、Wi-Fi（WPA3）
  メール → SPF / DKIM / DMARC

【アプリケーション層】
  HTTP / セッション / Cookie（HttpOnly, Secure）
  脆弱性 → SQLi、XSS、ビジネスロジックの欠陥
  開発 → セキュアコーディング、DevSecOps、シフトレフト

【エンドポイント層】
  アンチウイルス / EDR / ディスク暗号化 / パッチ管理
  SBOM / バックアップ / CSIRT・PSIRT

【組織・モデル層】
  境界防御 → 多層防御 → ゼロトラスト
  SIEM / XDR / UEBA / SOAR
  CASB / SWG / SASE
```

## 10. この章のまとめ

| レイヤ | 覚えておくこと |
|--------|----------------|
| **ネットワーク** | ファイアウォールは境界の基本。HTTPS と VPN で通信を守る |
| **メール** | SPF + DKIM + DMARC でなりすましを防ぐ |
| **アプリ** | SQLi・XSS は開発段階で防ぐ。Cookie は HttpOnly + Secure |
| **開発** | シフトレフト：早い段階でセキュリティを組み込む |
| **端末** | EDR + パッチ + バックアップの3点セット |
| **モデル** | 境界防御からゼロトラストへ。多層防御は今も有効 |

第1〜3章の「脅威・分析・用語」と合わせ、本章で **どこに何の対策を置くか** の地図が揃った。次はこれらを **組織のポリシー・法規制・リスク管理** に結びつけると、知識が実務に変わる。
