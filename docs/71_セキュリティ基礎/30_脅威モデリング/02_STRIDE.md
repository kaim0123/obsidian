# STRIDE — 6カテゴリの脅威分類

## はじめに

**STRIDE**（ストライド）は、Microsoft が提唱した **脅威を6つのカテゴリに分類する手法** です。脅威モデリングで最も広く使われているフレームワークです。

各カテゴリは、守るべき「セキュリティ性質」と対になっています。「**何を守れていないと、何が起きるか**」がきれいに対応しているのが特徴。

---

## STRIDE の全体像

| 頭文字 | 脅威 | 守るべき性質 | 一言で |
|--------|------|-------------|-------|
| **S** | **S**poofing | Authenticity（真正性） | 他人のふりをする |
| **T** | **T**ampering | Integrity（完全性） | データを書き換える |
| **R** | **R**epudiation | Non-repudiation（否認防止） | 「やってない」と言い逃れる |
| **I** | **I**nformation Disclosure | Confidentiality（機密性） | 見られたくない情報を見る |
| **D** | **D**enial of Service | Availability（可用性） | サービスを止める |
| **E** | **E**levation of Privilege | Authorization（認可） | 権限を奪う／昇格する |

---

## S — Spoofing（なりすまし）

### どんな脅威？

攻撃者が **他者のふりをする** 攻撃。認証を突破するタイプ。

### 具体例

- パスワードを盗んで他ユーザーとしてログイン
- セッションIDを盗んでなりすまし
- 偽の証明書でサーバーを偽装
- フィッシングで認証情報を盗む
- IP / メール送信元の偽装

### 緩和策

- 強い認証（bcrypt/Argon2）
- **多要素認証（MFA）**
- セッションIDの保護（HttpOnly, Secure, SameSite）
- 証明書の正当性検証（TLS）
- SPF / DKIM / DMARC（メール送信元認証）
- 署名付きトークン（JWT、署名付きCookie）

関連: OWASP A07（認証と識別の失敗）

---

## T — Tampering（改ざん）

### どんな脅威？

データを **書き換える** 攻撃。完全性を破壊。

### 具体例

- 通信中のデータをパケット改ざん（MITM 攻撃）
- DBに直接アクセスしてレコードを書き換える
- フロントから送る価格パラメータを書き換える（商品価格を0円に）
- アプリバイナリの改ざん（モバイルアプリの解析・改造）
- ログの改ざん（攻撃の痕跡を消す）
- JWTのpayload改ざん

### 緩和策

- **HTTPS / TLS** による通信暗号化・完全性保護
- デジタル署名、HMAC（メッセージ認証コード）
- DBへの直接アクセス制限
- **サーバー側で最終検証**（価格や数量はフロント値を信じない）
- ファイル・ログの改ざん検知（ハッシュチェーン、WORM ストレージ）
- コード署名

関連: OWASP A03（インジェクション）、A08（整合性不備）

---

## R — Repudiation（否認）

### どんな脅威？

ユーザーが **「そんな操作していない」と言い逃れ** できてしまう状況。操作の証拠が残らないのが問題。

### 具体例

- ログを残さず、誰が何をしたか分からない
- ログを消せる権限を使って証拠隠滅
- 電子契約で「自分が署名した証拠」がない
- 共有アカウントで、個人を特定できない

### 緩和策

- **監査ログ**（タイムスタンプ、ユーザーID、操作内容）
- ログの改ざん防止（署名、外部転送、WORM）
- **デジタル署名**（本人以外には作れないもの）
- 共有アカウントの禁止、個人アカウントの徹底
- タイムスタンプサービス（法的に有効な日時証明）

関連: OWASP A09（ログとモニタリングの不備）

---

## I — Information Disclosure（情報漏洩）

### どんな脅威？

**見られてはいけない情報が見られる** 状態。機密性の侵害。

### 具体例

- 平文で保存されたパスワードが流出
- エラー画面にスタックトレース・DB接続情報が表示される
- HTTPSなしの通信でカード番号が漏れる
- S3バケットが全公開で個人情報ダウンロードし放題
- SSRFで内部ネットワーク情報が漏れる
- レスポンスヘッダーから内部IP・サーバーバージョンが漏れる
- アクセス制御不備で他人の請求書が見える

### 緩和策

- データの **暗号化**（転送中: TLS / 保存中: AES-256）
- 適切な **アクセス制御**
- エラーメッセージの汎用化（詳細はサーバーログのみ）
- **最小権限の原則**
- クラウドリソースの公開設定見直し
- 機密情報のマスキング / 最小化（保存しないのが最強）

関連: OWASP A01（アクセス制御）、A02（暗号化）、A05（設定ミス）

---

## D — Denial of Service（サービス妨害）

### どんな脅威？

サービスを **使えなくする** 攻撃。可用性の侵害。

### 具体例

- DDoS 攻撃で大量リクエストを浴びせてサーバーダウン
- アプリの特定処理でCPU/メモリを使い切らせる（ReDoS、Zip爆弾）
- DBのコネクションを使い切らせる
- 大きすぎるファイルをアップロードさせて容量枯渇
- ログイン試行を無制限に打てる → アカウントロックで合法ユーザーを締め出す

### 緩和策

- **レート制限**（IPごと、ユーザーごと、エンドポイントごと）
- タイムアウト・入力サイズ上限
- リソース使用量の上限（スレッド、コネクション、ファイルサイズ）
- CDN / WAF / DDoS対策サービス（AWS Shield, Cloudflare 等）
- オートスケーリング
- 危険な正規表現（ReDoS）の回避
- 非同期処理・キュー・バックプレッシャー

---

## E — Elevation of Privilege（権限昇格）

### どんな脅威？

本来持っていない **高い権限** を不正に獲得する攻撃。

### 具体例

- 一般ユーザーが管理者機能にアクセスできる
- バッファオーバーフロー等のメモリ破壊から任意コード実行
- sudo / setuid プログラムの脆弱性でroot権限奪取
- SQLインジェクション → DB管理者権限奪取 → OS侵入
- JWTの権限フィールド改ざん
- コンテナエスケープ（コンテナ→ホストへ抜ける）

### 緩和策

- **最小権限の原則**（Principle of Least Privilege）
- サーバーサイドでの認可チェック（所有権チェック含む）
- **入力検証とサンドボックス化**
- メモリ安全な言語の使用（Rust、Go 等）
- コンテナランタイム強化（seccomp、AppArmor、gVisor）
- JWT の署名検証を厳密に（`alg=none` 禁止）
- 特権プロセスを減らす、分離する

関連: OWASP A01（アクセス制御）

## STRIDE の使い方（ミニマム実践）

### Step 1: データフロー図を描く

コンポーネントとフローを図にする（詳細は `データフロー図.md`）。

### Step 2: 各要素に STRIDE を当てる

データフロー図の **各要素** に対して、6カテゴリをチェックリスト的に適用します。

| 要素 | S | T | R | I | D | E |
|------|---|---|---|---|---|---|
| プロセス | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| データフロー | ✓ | ✓ | | ✓ | ✓ | |
| データストア | | ✓ | ✓ | ✓ | ✓ | |
| 外部エンティティ | ✓ | | ✓ | | | |

**プロセスには6つ全部** 当てはまるので、重点チェック対象です。

### Step 3: 「ありうるか？」を議論する

カテゴリごとに「このシステムで、この脅威は現実的に起き得るか？」「起きたらどう影響するか？」を議論。

### Step 4: 対策を決める

各脅威に対して、緩和 / 移転 / 受容 / 回避 を選択。

---

## 実例: ログインAPI

**対象**: `POST /api/login`（ユーザー → サーバー → DB）

| STRIDE | 脅威例 | 緩和策 |
|--------|--------|--------|
| **S** | パスワードリスト攻撃、セッション固定 | MFA、レート制限、セッションID再発行 |
| **T** | リクエストボディ改ざん | HTTPS、サーバーでのPW検証 |
| **R** | 「ログインしてない」と主張される | ログイン成功/失敗ログ記録 |
| **I** | エラーメッセージでアカウント存在が漏れる | メッセージ統一（「メールまたはPWが違います」） |
| **D** | 大量ログイン試行で DB 枯渇 | レート制限、接続プール上限 |
| **E** | 権限フィールド改ざんで admin に | サーバーで権限を検証、署名付きトークン |

このように STRIDE を当てていくと、**漏れなく脅威を洗い出せる** のがメリットです。

---

## STRIDE の限界

- **網羅性はあるが、優先順位はつけられない** → DREAD や CVSS と組み合わせる
- **業務ロジックの脆弱性**（Business Logic Flaw）はやや見つけにくい → 悪用ケース分析も併用
- 慣れないうちは **冗長に見える** → 最初はフロー数を絞って練習

---

## まとめ

- STRIDE は **脅威を6カテゴリに漏れなく分類** するフレームワーク
- 各カテゴリは **守るべきセキュリティ性質** と対応
- データフロー図の **各要素に当てはめて** 使う
- チェックリストとして使うと、抜け漏れを減らせる
- 優先度付けは DREAD など別手法と組み合わせる
