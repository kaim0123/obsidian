# データフロー図 — 信頼境界の特定

## はじめに

**データフロー図**（DFD: Data Flow Diagram）とは、システム内で **データがどう流れるか** を視覚化する図法です。脅威モデリングでは、**信頼境界**（Trust Boundary）を特定するための主要な道具として使われます。

### なぜ脅威モデリングで使うのか

- どのコンポーネントが **信用できない入力** を受け取るかが分かる
- どこで **認証・認可が必要か** が明らかになる
- **STRIDE** を各要素に当てはめるベースになる

「どこで攻撃者と接触するか」を物理的に見える化することが、脅威分析の出発点です。

---

## 4つの基本要素

DFDは、たった4種類の記号で描けます。

### 1. プロセス（Process）

データを **処理するもの**。アプリケーション、サービス、関数、マイクロサービス等。

記号: **円** または **角丸長方形**

例: ログインAPI、決済サービス、画像変換関数

### 2. データストア（Data Store）

データが **保存されるもの**。

記号: **2本の水平線に挟まれた長方形**、または **円筒**

例: データベース、ファイル、キャッシュ、オブジェクトストレージ

### 3. 外部エンティティ（External Entity）

システムの **外側にいる** もの。人間、他システム、外部API等。

記号: **長方形**

例: ユーザー、外部の決済サービス、他社API

### 4. データフロー（Data Flow）

データの流れ。矢印で表現。

記号: **矢印**（何のデータが流れるかラベル付き）

例: 「ログインリクエスト」「クエリ結果」「JWT」

---

## 信頼境界（Trust Boundary）

**もっとも重要な概念**。異なる信頼レベルの間に引く線のこと。

### どこに引くか

信頼レベルが変わる場所 = 信頼境界。典型的には:

- **インターネット ↔ 自社ネットワーク**（最大の境界）
- **フロントエンド ↔ バックエンド**
- **バックエンド ↔ データベース**
- **一般ユーザー領域 ↔ 管理者領域**
- **社内ネット ↔ クラウドサービス**
- **アプリ ↔ OSカーネル**
- **コンテナ ↔ ホスト**

### 記号

**点線の四角形** で囲む、または **点線の線** を境界として引きます。

### なぜ重要か

**境界を越えるデータは、常に信用できない** と扱う必要があります。

- 境界を越えたらまず **検証・認証・エスケープ**
- 境界がどこにあるか分からないと、どこで検証すべきか分からない
- 境界の見落としが **設計の脆弱性** を生む

---

## 図の記号まとめ

```
[外部エンティティ]         長方形
    │
    │ データフロー        矢印
    ▼
  (プロセス)              円 / 角丸長方形
    │
    │ データフロー
    ▼
 ==========             2本線
  データストア
 ==========

┌─────────────┐
│ 信頼境界      │         点線
└─────────────┘
```

## 具体例: ログイン機能の DFD

### シンプルなログインAPIを DFD で描く

```
┌─────────────────── インターネット境界 ──────────────────┐
│                                                        │
│   [ユーザー]                                           │
│       │                                                │
│       │ ①ログインリクエスト (email+password)           │
│       │    via HTTPS                                   │
└───────┼────────────────────────────────────────────────┘
        │
        ▼
    (ログインAPI)
        │
        │ ②ユーザー検索クエリ
        ▼
    ═══════════
    ユーザーDB
    ═══════════
        │
        │ ③クエリ結果（ハッシュ化PW等）
        ▼
    (ログインAPI)
        │
        │ ④JWT トークン
        ▼
    [ユーザー]
```

### この図から読み取れること（STRIDEを当てる）

1. **①の境界**: ユーザー → API
   - **S**poofing: 他人になりすまし → 認証を堅牢に、MFA
   - **T**ampering: リクエスト改ざん → HTTPS 必須
   - **D**oS: 大量リクエスト → レート制限
2. **②③の境界**: API → DB
   - **T**ampering: クエリ改ざん → プリペアドステートメント
   - **I**nformation Disclosure: 平文DB接続 → TLS、VPC内限定
3. **④**: JWT
   - **T**ampering: JWT改ざん → 署名検証
   - **I**nformation Disclosure: ペイロードの平文 → 機密情報を入れない

## もう1つの例: 画像アップロード + 外部CDN

```
[ユーザー]
    │ ① POST /upload (画像ファイル)
    ▼
(アップロードAPI)
    │ ② 保存
    ▼
═══════════
 S3 バケット
═══════════
    │ ③ CloudFront 経由で配信
    ▼
[他のユーザー] (ブラウザ)

※ 信頼境界:
  - ユーザー ↔ API
  - API ↔ S3
  - CloudFront ↔ ブラウザ（公開CDN）
```

**議論すべき点**:
- アップロード時のファイル種別検証（悪意あるファイル対策）
- ファイル名のサニタイズ（パストラバーサル）
- S3 バケットの公開設定（A05 設定ミス）
- 配信URLの推測可能性（IDOR）
- ウイルススキャン

## DFD の階層化

### Level 0: Context Diagram（コンテキスト図）

システム全体を **1つのプロセス** として、外部とのやりとりだけ描く。俯瞰用。

### Level 1: 主要コンポーネントへ分解

メインのプロセスを、フロントエンド・バックエンド・DB など **主要要素** に分解。

### Level 2+: さらに詳細化

必要に応じて、特定のコンポーネントを内部構造まで掘り下げる。

**コツ**: 最初から Level 2 を描かない。**Level 1 で信頼境界を正しく引く** ことに集中。

---

## 描くときのコツ

### 1. 完璧でなくていい

ホワイトボードや紙に手描きで十分。**議論のための図** であって、芸術作品ではない。

### 2. 外部エンティティをすべて洗い出す

- 利用者（一般ユーザー、管理者、ゲスト）
- 外部API（決済、認証、メール配信）
- 依存するクラウドサービス
- 内部の他サービス（マイクロサービス）

見落としは即ち **認証・認可の抜け** につながる。

### 3. すべての入力ポイントを把握

- Webフォーム、API エンドポイント
- アップロード
- Webhook
- メッセージキュー
- 設定ファイル、環境変数
- 他サービスからの呼び出し

「ここから悪意ある入力が来たらどうなる？」を各ポイントで問う。

### 4. データの機密性をラベル化

各データフローに **機密度**（公開 / 内部 / 機密 / 極秘）を付けると、優先度が見える。

### 5. 認証状態を明示

「認証済みユーザーからのフロー」「匿名ユーザーからのフロー」は別に描く。認証境界が見えやすくなる。

## ツール

- **Microsoft Threat Modeling Tool**（無料、自動STRIDE適用）
- **OWASP Threat Dragon**（OSS、GitHubと連携可能）
- **draw.io / diagrams.net**（無料、汎用図）
- **Miro / FigJam**（コラボ型）
- **PlantUML**（コード管理しやすい）

---

## DFD と UML の違い

| | DFD | UML |
|---|-----|-----|
| 主眼 | **データの流れ** | クラス関係、振る舞い、構造 |
| 使いどき | 脅威モデリング、業務分析 | 設計、コード構造の文書化 |
| 対象 | システム全体 | オブジェクト・コンポーネント |

脅威モデリングでは **DFD** が第一選択です。UMLの「配置図」「シーケンス図」も補助的に使えます。

## よくある失敗

### 1. 信頼境界を引き忘れる

**DFDの存在意義が失われます**。必ず境界を意識して描く。

### 2. 網羅しようとして破綻

システム全体を1枚に描こうとすると、複雑すぎて使えない。**階層化** で整理。

### 3. 実装と乖離している

一度描いて放置すると、実装と違うDFDを眺めることに。**実装変更時に更新** するか、コード化可能なツール（PlantUML、Threat Dragon）を使う。

### 4. データストアしか意識しない

プロセス間・外部サービス間の通信も要チェック。

---

## まとめ

- DFDは **プロセス / データストア / 外部エンティティ / データフロー** の4要素で描く
- **信頼境界** の特定が最重要 — 境界を越える所で認証・検証・暗号化を検討
- シンプルに、**Level 1（主要コンポーネント）** から始める
- STRIDE と組み合わせて、各要素・フローに脅威を当てていく
- 実装と乖離させないため、更新しやすい形で管理する
