# IssueとProjectの違い

## 概要

GitHubでプロジェクト管理を行う際、**Issue**と**Project**は異なる役割を持つ重要な機能です。この章では、両者の違いと使い分けを詳しく説明します。

## Issueとは

### 基本的な概念

**Issue（イシュー）**は、個別のタスクや課題を管理するための**チケットシステム**です。1つのIssueが1つのタスクやバグを表します。

### Issueの特徴

- **個別管理**: 1つのタスクを1つのIssueとして管理
- **詳細情報**: タイトル、説明、ラベル、マイルストーン、担当者などの情報を保持
- **議論の場**: コメント機能で議論や進捗を記録
- **連携機能**: プルリクエストと連携して自動的に閉じることも可能

### Issueの例

```
Issue #123: ユーザー認証機能を追加する
├─ タイトル: [FEATURE] ユーザー認証機能の実装
├─ 説明: ユーザーがログイン・ログアウトできる機能を実装する
├─ ラベル: feature, priority: medium
├─ マイルストーン: v1.0.0 Release
├─ 担当者: @username
└─ コメント: 進捗や議論の記録
```

## Projectとは

### 基本的な概念

**Project（プロジェクト）**は、複数のIssueやプルリクエストを**視覚的に管理するボード**です。カンバンボード形式で全体の進捗を把握できます。

### Projectの特徴

- **集合管理**: 複数のIssueやプルリクエストを一つのボードで管理
- **視覚的表示**: カンバンボード形式で進捗を可視化
- **状態管理**: カラム（To do、In progress、Doneなど）で状態を管理
- **ドラッグ＆ドロップ**: カードをドラッグして状態を変更

### Projectの例

```
Project: v1.0.0 Release
├─ To do
│   ├─ Issue #123: ユーザー認証機能
│   └─ Issue #124: ダッシュボード実装
├─ In progress
│   └─ Issue #125: API統合
└─ Done
    └─ Issue #100: ログイン機能
```

## 主な違い

### 比較表

| 項目 | Issue | Project |
|------|-------|---------|
| **単位** | 1つのタスク | 複数のタスクの集合 |
| **形式** | チケット形式 | カンバンボード形式 |
| **用途** | 個別タスクの詳細管理 | 全体の進捗可視化 |
| **情報** | 詳細な説明、コメント | カラムでの状態管理 |
| **操作** | コメント、ラベル付け | ドラッグ＆ドロップ |
| **連携** | プルリクエストと直接連携 | IssueやPRをカードとして表示 |

### 視覚的な違い

#### Issue（チケット形式）
```
┌─────────────────────────────────┐
│ Issue #123                      │
│ [FEATURE] ユーザー認証機能      │
│                                 │
│ 説明: ユーザーがログイン...     │
│ ラベル: feature, priority: high │
│ 担当者: @username               │
│ コメント: 5件                   │
└─────────────────────────────────┘
```

#### Project（カンバンボード形式）
```
┌──────────┬──────────────┬──────┐
│ To do    │ In progress  │ Done │
├──────────┼──────────────┼──────┤
│ Issue #123│ Issue #125   │ #100 │
│ Issue #124│              │      │
└──────────┴──────────────┴──────┘
```

## 関係性

### 包含関係

```
Project（プロジェクトボード）
  ├─ Issue #123: ユーザー認証機能
  ├─ Issue #124: ダッシュボード実装
  ├─ Issue #125: API統合
  └─ Pull Request #50: バグ修正
```

**Projectは複数のIssueを管理する容器**のような役割です。

### 連携の流れ

1. **Issueを作成**: 個別のタスクをIssueとして作成
2. **Projectに追加**: 作成したIssueをProjectのボードに追加
3. **状態管理**: ProjectのカラムでIssueの状態を管理
4. **自動更新**: Issueの状態変更がProjectに自動反映

## 使い分けのガイドライン

### Issueを使う場面

✅ **個別のタスクやバグを記録する**
- 「ユーザー認証機能を追加する」
- 「ログインボタンがクリックできない」

✅ **詳細な要件や議論を記録する**
- 要件の詳細な説明
- 技術的な議論
- 進捗の記録

✅ **プルリクエストと連携する**
- プルリクエストでIssueを参照
- マージ時に自動的にIssueを閉じる

### Projectを使う場面

✅ **複数のIssueの進捗を一覧で確認する**
- スプリント全体の進捗
- リリース全体の進捗

✅ **チーム全体の作業状況を可視化する**
- 誰が何をしているか
- どのタスクがブロックされているか

✅ **スプリントやリリースを管理する**
- スプリント計画
- リリース計画

✅ **優先順位や担当者ごとに整理する**
- 優先度の高いタスクを確認
- 担当者ごとの作業量を確認

## 実践例

### 例1: 機能開発の流れ

```bash
# 1. Issueを作成（個別タスク）
# GitHub上で「ユーザー認証機能を追加する」→ Issue #123

# 2. Projectに追加（全体管理）
# 「v1.0.0 Release」プロジェクトの「To do」カラムに追加

# 3. 作業開始
# Issueにラベル`status: in-progress`を追加
# → Projectの「In progress」カラムに自動移動

# 4. ブランチ作成と開発
git checkout -b feature/123-user-authentication
# ... 開発 ...

# 5. プルリクエスト作成
git push origin feature/123-user-authentication
# → Projectの「Review」カラムに自動追加

# 6. マージと完了
# プルリクエストをマージ
# → Issue #123が自動的に閉じられる
# → Projectの「Done」カラムに自動移動
```

### 例2: スプリント管理

**Project**: 「Sprint 1 - Q1 2024」

**含まれるIssue**:
- Issue #100: ログイン機能（To do）
- Issue #101: パスワードリセット（In progress）
- Issue #102: セッション管理（Done）

**使い方**:
- Projectで全体の進捗を確認（「50%完了」など）
- 各Issueで詳細な要件や議論を管理
- カラムを移動して進捗を更新

### 例3: バグ修正の緊急対応

```bash
# 1. 緊急バグのIssueを作成
# Issue #456: ログインボタンがクリックできない
# ラベル: bug, priority: critical

# 2. 緊急対応プロジェクトに追加
# 「Hotfix」プロジェクトの「Critical」カラムに追加

# 3. 即座に対応
git checkout -b hotfix/456-fix-login-button
# ... 修正 ...
git commit -m "Fix login button - fixes #456"

# 4. 緊急マージ
# → Issue #456が自動的に閉じられる
# → Projectの「Resolved」カラムに移動
```

## ベストプラクティス

### Issueの管理

1. **明確なタイトル**: Issueの内容が一目で分かるタイトル
2. **詳細な説明**: 要件や背景を詳しく記述
3. **適切なラベル**: カテゴリや優先度を明確に
4. **定期的な更新**: 進捗をコメントで更新

### Projectの管理

1. **明確なカラム構成**: チームのワークフローに合わせた構成
2. **自動化の活用**: ラベル変更で自動的にカラムを移動
3. **定期的な確認**: プロジェクトボードを定期的に確認
4. **カードの整理**: 完了したタスクは定期的にアーカイブ

### 両者の連携

1. **一貫性**: IssueとProjectで一貫したラベルやステータスを使用
2. **自動化**: GitHub Actionsで自動的に連携
3. **可視化**: Projectで全体像を、Issueで詳細を管理

## まとめ

- **Issue = 個別のタスクを管理するチケット**
- **Project = 複数のタスクを視覚的に管理するボード**

両方を組み合わせることで：
- **Issue**: 個別タスクの詳細管理
- **Project**: 全体の進捗可視化

この2つを効果的に使い分けることで、効率的なプロジェクト管理が可能になります。
