## 詳しい要約

**テーマ：Git の仕組みを 4 つの勘違いから理解する**

Git をコマンドのコピペで使っていると、ある日データを消すなどのトラブルを招く。「Git と GitHub は別物」「コミットはスナップショット」「ブランチはポインタ」「マージとリベースは履歴が違う」の 4 点を押さえれば、Git の仕組みが見えて怖くなくなる、という内容。

---

### 1. Git と GitHub は別物

- 関係は「**動画と YouTube**」に近い。Git はバージョン管理ツールそのもの、GitHub は Git で管理したものを置いておくサービス
- Git は 2005 年に **Linus Torvalds** が Linux 開発の管理のために作成。GitHub は 2008 年登場で、Git のほうが 3 年先輩
- GitHub のほかに GitLab、Bitbucket などもあり、どれも「置き場所」
- Git は**ローカルで完結する分散バージョン管理システム**。ネットがなくてもコミットもブランチ作成もできる

### 2. コミットは差分ではなくスナップショット

- コミットは「前回からの変更点」ではなく、その瞬間のプロジェクト全体の**スナップショット（写真）**
- 変更のないファイルは前のコミットへの**参照**だけを持つので、データが重複して膨らむことはない（概念は全体保存、実装は効率的）
- 差分方式だと 1 万コミット前に戻るには差分を 1 万回適用する必要があるが、スナップショットなら**直接アクセス**できる → `git checkout` が一瞬で終わる

### 3. ブランチはコピーではなくポインタ

- ブランチを作ってもファイルは 1 バイトもコピーされず、**ポインタ（本のしおり）**が 1 つ増えるだけ
- 1GB のプロジェクトでもブランチ作成は一瞬。かつての **SVN** は実際にファイルをコピーしていたため何分もかかった
- コストがほぼゼロなので気軽にブランチを切ってよい
- **HEAD** は「今自分がいる場所」を指す特別なポインタ。ブランチ切り替えは HEAD が移動するだけ（作業ディレクトリはそのコミットの状態に更新される）

### 4. マージとリベースは履歴が違う

| | マージ | リベース |
|---|---|---|
| たとえ | 川の**合流** | 川の**源流の付け替え** |
| 履歴 | 合流した事実がそのまま残る（正直） | 一直線になり読みやすい（綺麗） |
| 注意点 | — | 歴史を書き換え、コミットのハッシュが変わる |

- **プッシュ後のリベースは危険**：他の人が見ている古い歴史と食い違い、混乱を招く
- よくあるルールは「**ローカル作業中はリベース、共有したらマージ**」（自分だけの歴史は書き換えてよいが、みんなの歴史は書き換えない）

### Git を理解すると何が変わるか

- トラブル時に何が起きているか分かり、「このコマンドは履歴を書き換える」「ポインタを動かすだけ」と判断できるようになる
- `reset` と `revert`、`fetch` と `pull` の違いも仕組みから見えてくる
- 例：`git reset` はしおりを動かすコマンド。`--soft` はしおりだけ動かし、`--hard` は作業中のファイルも巻き戻す

### まとめ

- Git と GitHub は別物で、Git はローカルで完結する
- コミットはスナップショット、ブランチはポインタなので高速・軽量
- マージは履歴を残し、リベースは履歴を書き換える。共有後のリベースは避ける
- 「このコマンドは何をしているか」を意識して使うと理解が深まる
