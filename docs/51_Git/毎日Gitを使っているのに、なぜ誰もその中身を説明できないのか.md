## 詳しい要約

**テーマ：Git の中身は「中身から名前を決めたスナップショットの鎖」**

多くの人は Git が差分（変更点）を保存していると思っているが、実際は各時点のプロジェクト全体の「写真（スナップショット）」を保存している。中身から名前を決める仕組みが重複排除と改ざん検知を同時に実現し、コミットが 1 つ前を指す鎖になることで改ざん耐性と分散（サーバー不要）まで生まれた。add・commit・push はすべてこの 1 つの思想の上の操作にすぎない。

---

### 第1章 差分ではなく「全体の写真」を保存

- Git は毎回、変わった部分だけでなく **プロジェクト丸ごとのその瞬間の姿** を保存する
- それでも容量が膨らまないのは、**変わっていない中身は取り直さず、前の写真の中身を指し示して使い回す** から。新しく保存するのは本当に変わった分だけ
- 変更点を見たいときは、2 枚の写真をその場で見比べて計算する。**差分は保存物ではなく、その場で作る結果**
- 昔ながらの仕組みは「元ファイルへの変更履歴」を積み重ねるが、Git はそれを捨て、各時点の完全な姿を持つ

### 第2章 中身が名前を決める：重複排除と改ざん検知

- 普通は「名前が先、中身が後」だが、Git は逆に **中身を計算して、中身そのものから名前を決める**
- 同じ中身なら必ず同じ名前 → 名前を見るだけで重複を一瞬で見抜ける（使い回しの正体）
- 中身が少しでも変われば名前は丸ごと別物 → こっそりいじるとすぐバレる
- 名前は入れ子で積み上がる：ファイルの名前 → それを束ねるフォルダの名前 → 上のフォルダの名前。奥の小さな変化がてっぺんの名前まで伝わる

### 第3章 コミットは鎖、ブランチと HEAD は「付箋」

- 各コミットは **1 つ前のコミットの名前を抱えて** おり、写真が鎖状につながる
- 鎖は枝分かれ（**ブランチ**）も合流（**マージ**）もし、全体として向きの決まった網になる
- **ブランチ** は網のどこかを指すただの名札、**HEAD** は今自分がいる位置を指す特別な札。実体は付箋にすぎない
- だからブランチ切り替えは付箋を貼り替えるだけで、重いコピーは起きない

### 第4章 なぜ改ざんできず、サーバーなしで動けるのか

- 「名前は中身から決まる」＋「各コミットは前の名前を持つ」の 2 つが鎖を固く縛る
- 過去の写真を 1 か所書き換えると名前が変わり、次の写真が持つ「前の名前」と合わなくなって、その先の鎖全体がドミノのように崩れる → **痕跡なく過去を直すことはできない**
- 先端の写真の名前 1 つがその時点のプロジェクト全体を言い当てるので、名前 1 つが **無事の証明書** になる
- 過去を直すコマンドも実は直しておらず、古い写真はそのまま **新しい写真を別に作って並べ替えている** だけ
- 各自が歴史丸ごとの完全な複製を持ち、名前を比べるだけで足りない写真が分かる → 中央サーバーに聞きに行かなくてよい **分散** が成立した

### 第5章 「スナップショットの鎖」という思想

- 私たちは Git を使っているというより、「中身で名前を決めた写真を鎖でつなぐ」という **1 つの思想の上で動かされている**
- add・commit・push は、中身から名前をつけて 1 つ前につなぐという同じ動きの言い換えにすぎない

### まとめ

- Git は差分ではなくスナップショットを保存し、変わらない中身は使い回す
- 中身から名前を決める仕組みが、重複排除・改ざん検知・改ざん耐性・分散をまとめて生んだ
- ブランチと HEAD は鎖の位置を指す付箋にすぎないので、切り替えは軽い
