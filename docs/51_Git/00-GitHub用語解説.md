# GitHub 用語解説

GitHubでよく使われる専門用語を、カテゴリ別に解説します。Gitの基本用語と、GitHub固有の用語の両方を含みます。

---

## リポジトリ関連

### リポジトリ（Repository / Repo）
**プロジェクトの変更履歴一式が格納されている場所。** コード、コミット履歴、ブランチ、設定などがまとまって保存されています。GitHub上では「リポ」と略されることが多いです。

- **ローカルリポジトリ**: 自分のPC内にあるリポジトリ
- **リモートリポジトリ**: GitHubなどのサーバ上にあるリポジトリ

### フォーク（Fork）
**他者のリポジトリを自分のGitHubアカウントにコピーすること。** 元のリポジトリとは独立したコピーができ、自分で変更を加えたり、元のリポジトリへPull Requestを送ったりするときに使います。オープンソースへの参加でよく使われます。

### クローン（Clone）
**リモートリポジトリをローカル（自分のPC）に丸ごとコピーすること。** `git clone <URL>` で実行します。フォークは「GitHub上でのコピー」、クローンは「PC上へのコピー」という違いがあります。

### テンプレートリポジトリ（Template Repository）
**他のリポジトリの「ひな形」として使えるようにしたリポジトリ。** フォークと違い、履歴を引き継がずに新規リポジトリとして作成できます。プロジェクトの初期構成を共有するときに便利です。

## ブランチ・変更の同期

### ブランチ（Branch）
**履歴を分岐させて、本流（main/master）に影響を与えずに作業するための枝。** 機能追加やバグ修正ごとにブランチを作り、作業後に本流へマージする運用が一般的です。

### メインブランチ（main / master）
**リポジトリの「本流」となるブランチ。** 現在は `main` がデフォルト名として推奨されています。`master` は以前のデフォルト名です。

### プッシュ（Push）
**ローカルのコミットをリモートリポジトリに送ること。** `git push` で実行します。

### プル（Pull）
**リモートリポジトリの最新の変更をローカルに取り込むこと。** `git fetch` + `git merge` をまとめて行うコマンドが `git pull` です。

### フェッチ（Fetch）
**リモートの最新情報を取得するが、ローカルの作業ブランチにはまだ反映しないこと。** 内容を確認してからマージするときに使います。

## コミット・履歴

### コミット（Commit）
**ある時点の変更を「確定した記録」としてリポジトリに保存すること。** メッセージと一緒に履歴として残り、後から参照・取り消しができます。

### コミットメッセージ（Commit Message）
**そのコミットで「何を・なぜ変更したか」を説明する短文。** 良いメッセージは、後で履歴をたどるときの手がかりになります。

### ステージング（Staging）
**次のコミットに含める変更を「選んで用意する」こと。** `git add` でステージングエリア（インデックス）に追加し、`git commit` でコミットします。

### ヘッド（HEAD）
**現在チェックアウトしているコミット（またはブランチ）を指すポインタ。** 「今どこで作業しているか」を表します。

---

## マージ・プルリクエスト

### マージ（Merge）
**あるブランチの変更を別のブランチに取り込むこと。** 例：feature ブランチを main にマージして、機能を本流に反映します。

### プルリクエスト（Pull Request / PR）
**「このブランチの変更を、指定したブランチ（多くは main）に取り込んでほしい」という依頼。** コードの差分表示・レビュー・議論・マージをGitHub上で一括して行います。略して「PR」と呼ばれることが多いです。

### マージリクエスト（Merge Request / MR）
**GitLabなどで使われる用語。** 意味はプルリクエストとほぼ同じで、「このブランチをマージしてほしい」という依頼です。

### レビュー（Review）
**PRのコード変更内容を確認し、コメントや承認・却下を行うこと。** チーム開発では必須の作業です。

### コンフリクト（Conflict）
**複数のブランチで同じ箇所を別々に変更したため、自動でマージできなくなった状態。** 手動でどちらの変更を採用するか決めて解消する必要があります。

### スカッシュ（Squash）
**複数のコミットを1つにまとめてからマージすること。** PRをマージする際に「Squash and merge」を選ぶと、PR内のコミットが1つにまとまって main に入ります。

### リベース（Rebase）
**ブランチの基点となるコミットを、別のコミットの直後に付け替えること。** 履歴を一直線に整理したいときに使います。`git rebase` で実行します。

## Issue・プロジェクト管理

### イシュー（Issue）
**バグ報告・機能要望・タスク・質問などを管理する「チケット」。** 番号（例：#42）で参照でき、PRと紐づけて「このPRは #42 を閉じる」のように書けます。

### クローズ（Close）
**IssueやPRを「完了した」状態にすること。** PRをマージすると、紐づけたIssueを自動でクローズする設定もできます。

### マイルストーン（Milestone）
**複数のIssueやPRを「バージョン1.0」「〇月リリース」のようにグループ化する機能。** 進捗の可視化に使います。

### ラベル（Label）
**IssueやPRに付けるタグ。** 「bug」「enhancement」「priority: high」などで分類・フィルタしやすくします。

### プロジェクト（Project）
**IssueやPRをカンバン形式（To Do / In Progress / Done）などで管理するボード。** GitHub Projects で、スプリントやリリース単位の管理ができます。

### アサイン（Assign）
**IssueやPRの担当者を特定のメンバーに割り当てること。** 「Assignees」で指定します。

## その他のGitHub機能

### スター（Star）
**リポジトリをお気に入り登録すること。** 人気の指標にもなります。自分用のブックマークとしても使えます。

### ウォッチ（Watch）
**リポジトリのIssue・PR・リリースなどの更新通知を受け取る設定。** 「Watch」→「All Activity」や「Custom」で通知範囲を選べます。

### リリース（Release）
**特定のタグ（例：v1.0.0）に紐づけた配布用のスナップショット。** ソースコードのZIPやビルド成果物を添付し、変更履歴（Release notes）を書けます。

### タグ（Tag）
**特定のコミットに名前（多くはバージョン番号）を付けたもの。** 例：`v1.0.0`。リリースの基点として使われます。

### GitHub Actions
**リポジトリ内でCI/CD（テスト・ビルド・デプロイ）などを自動実行する機能。** ワークフローをYAMLで定義し、pushやPRなどをトリガーに実行します。

### Gist
**小さなコードスニペットやメモを公開・共有するためのサービス。** 1ファイル単位で簡単に共有でき、リポジトリほど大げさにしたくないときに使います。

### Wiki
**リポジトリに紐づいたドキュメント用のWiki。** マークダウンで書け、仕様書や運用メモを置くのに使います。

### Organization（組織）
**複数人で使うチーム用アカウント。** リポジトリやメンバーをまとめて管理し、権限を細かく設定できます。

### コラボレーター（Collaborator）
**そのリポジトリに直接アクセス権（読み書き）を与えられたユーザー。** 個人リポジトリで「Settings」→「Collaborators」から追加します。

### フォロワー / フォロー（Follower / Follow）
**他のユーザーをフォローすると、その人の公開活動がタイムラインに表示されます。** ソーシャル的な機能です。

## 権限・セキュリティ

### 公開 / 非公開（Public / Private）
**リポジトリの「誰がコードを読めるか」を決める設定。** Public はインターネット上の誰でも clone・閲覧でき、Private は権限を与えた人だけが読めます。

重要なのは、**公開＝誰でも main に書き込める・マージできる、ではない**ことです。見える範囲（Visibility）と、変更できる権限（Write / Maintain / Admin など）は別です。

### 公開リポジトリで、最初から守られていること
権限のない第三者（Collaborator でも Organization メンバーでもない人）に対しては、だいたい次のとおりです。

| 操作 | 権限のない第三者 |
|------|------------------|
| コードを読む・clone する | できる |
| `main` などに直接 push する | **できない**（Write 以上が必要） |
| PR をマージする（Merge ボタン） | **できない**（Write 以上が必要） |
| Issue を作る・コメントする | **できる**（既定。オフにもできる） |
| PR を作る | **できる**（多くは fork 経由） |
| PR にコメントする | **できる**（既定） |

つまり Issue や PR は誰でも作れますが、**マージしなければ本流のコードは変わりません。** マージできるのはリポジトリの書き込み権限を持つ人（個人リポなら通常は所有者と Collaborator）だけです。

一方で、ブランチ保護ルールが無いと次のリスクが残ります。

- 所有者自身の誤った直接 push / force push
- トークンや SSH 鍵が漏れたときの直接 push
- 後から Collaborator を追加したときの事故

### ブランチ保護ルール（Branch Protection Rules）
**指定したブランチ（多くは main）への直接 push や force push を制限する設定。** PRとレビューを必須にし、誤って本流を壊すのを防ぎます。設定場所は「Settings」→「Branches」→「Add branch protection rule」です。

一人開発でも、まず次を付けると効果が大きいです。

- **Require a pull request before merging** … main への直 push をやめ、PR 経由にする
- **Require approvals** … レビュー承認を必須にする（一人開発では承認者が自分だけになりがちなので、まずは「PR 必須」だけでも可）
- **Do not allow bypassing the above settings** … 管理者でもルールをすり抜けにくくする（使える場合）
- **Restrict who can push to matching branches** … push できる人を限定する
- （任意）**Require status checks to pass** … CI が通らないとマージできないようにする
- （任意）**Require conversation resolution** … レビューコメントの解消を必須にする

### Issue・PR のノイズ対策
公開リポジトリでは、スパム Issue や無関係な PR が来ることがあります。コード自体はマージしなければ変わりませんが、運用の負担になります。

- Issues が不要なら「Settings」→「General」→ Features で **Issues をオフ**
- **Interaction limits** で、新規アカウントなどからの操作を一時制限する
- Issue / PR テンプレートで報告の質を上げる
- 迷惑なものは Close・Lock、悪質なら Block user

fork 経由の PR は「提案」にすぎません。中身を確認し、取り込まない判断をすれば main は安全です。

### その他の防衛
- **2FA（二要素認証）** を GitHub アカウントで有効にする
- Collaborator は必要最小限の権限にする（作業内容によっては Write ではなく Triage）
- API キーや `.env` など秘密情報をリポジトリに置かない（Secret scanning / push protection の利用も有効）
- 依存パッケージの脆弱性通知のために Dependabot を有効にする

### メイン（main）
**現在のデフォルトのメインブランチ名。** 以前は `master` が一般的でした。保護ルールを付ける対象として最もよく選ばれます。

### フォースプッシュ（Force Push）
**リモートの履歴を、ローカルの履歴で上書きする push。** `git push --force`。共有ブランチでは原則禁止とされることが多いです。ブランチ保護で禁止できます。

### トークン（Token）
**APIや `git push` などで、パスワードの代わりに使う認証用の文字列。** Personal Access Token（PAT）や、GitHub Actions 用のトークンなどがあります。漏れると権限の範囲で push や設定変更ができるため、有効期限・最小権限・定期ローテーションが重要です。

### SSH キー
**パスワードなしでGitHubと通信するための認証鍵。** 公開鍵をGitHubに登録し、秘密鍵を自分のPCに置いて使います。

## まとめ

| 用語 | 一言で言うと |
|------|----------------|
| リポジトリ | プロジェクトの履歴一式が入った「入れ物」 |
| 公開（Public） | 誰でも読める。ただしマージや直 push は権限者だけ |
| フォーク | 他人のリポジトリを自分のアカウントにコピーする |
| クローン | リモートを自分のPCにコピーする |
| ブランチ | 本流を分岐させた「作業用の枝」 |
| コミット | 変更を確定して履歴に残す |
| プッシュ | ローカルの変更をリモートに送る |
| プル | リモートの変更をローカルに取り込む |
| プルリクエスト（PR） | 「このブランチをマージしてほしい」という依頼 |
| マージ | ブランチの変更を別ブランチに取り込む |
| Issue | バグ・要望・タスクを管理するチケット |
| ブランチ保護 | main などへの直 push / 無審査マージを制限する設定 |
| リリース | タグに紐づけた配布用スナップショット |
| GitHub Actions | テスト・ビルドなどを自動実行する機能 |
