## 要約

**Git** は、プロジェクト全体の変更履歴を記録し、過去の任意の時点へ戻したり、多数の開発者が同時に作業した変更を安全に統合したりする **バージョン管理システム（VCS）** である。本動画は **2005 年の BitKeeper 事件** からリーナス・トーバルズによる **約 10 日での初期実装**、**集中管理型（SVN/CVS）との設計対比**、**スナップショット・DAG・ハッシュ** といった技術的本質、**GitHub との違い** と現代の開発文化への影響までを、ゆっくり解説形式でたどる。

### テーマ：Git とは何か

- **バージョン管理**＝コードの「タイムマシン」。誰が・いつ・何を変えたかを記録し、昨日や数週間前の状態へ **プロジェクト全体** を一発で巻き戻せる。
- **Ctrl+Z との違い**：エディタの取り消しは **開いているファイル・現在のセッション** に限られる。Git は **閉じた後も数年分の履歴** を保持し、**100 人規模の同時編集** も追跡・統合できる。
- 現代の Google・メルカリ・スマホアプリなど、大規模ソフトウェア開発の **事実上の標準インフラ** になっている。

### 2005 年：BitKeeper 事件と「1 週間休んで自分で作る」

| 時期・人物 | 内容 |
|-----------|------|
| **当時の状況** | Linux カーネル開発（年間 **1,500〜2,000 人** 規模）が **BitKeeper** という VCS を使用。カーネル開発者向けには無料提供されていたが、一般企業利用は有料 |
| **トリッジェル（Andrew Tridgell）** | Samba 作者。BitKeeper の **公開コマンドを叩いて通信プロトコルを調査** し、相互運用ツール構築のための調査を開始 |
| **論点** | BitKeeper ソフト自体は使っていないため **明確なライセンス違反とは断定されなかった** が、BitMover CEO **ラリー・マクボイ** は「ライセンスの精神に反する」と判断 |
| **結果** | Linux チームへの **無料提供打ち切し**——白黒がつかないまま、世界規模プロジェクトの基盤ツールが突然使えなくなる事態に |
| **リーナスの反応** | 謝罪ではなく **「1 週間休む。その間に自分でツールを作る」** と宣言——実際には **約 10 日** で実用レベルの初期版が完成 |

- 怒りだけでなく、**「こうあるべき」という明確な設計ビジョン** が既存ツールへの批判として蓄積されていたことが、短期間での実装を可能にした。

### 集中管理型（SVN/CVS）の限界

**SVN（Subversion）**——集中管理型の代表：

- **中央サーバー 1 台** に全員がアクセスし、コードを取得・返送する（全員が同じ「銀行口座」を使うイメージ）。
- サーバー障害 → **全員の作業がストップ**。最悪、サーバー破損で **プロジェクト履歴ごと消失** のリスク。
- **ブランチ（開発の枝）** は作りやすいが、**マージ（本流への合流）** が大規模プロジェクトでは重く、衝突解決も手作業が多い → **ブランチを気軽に使う文化が育ちにくかった**。

**CVS**（SVN より古い）——リーナスの辛辣な評価の背景：

- ファイルの **リネームを正しく追跡できない** など設計が古い。
- **アトミックコミットがない**——複数ファイルの変更を **1 つのまとまり** として記録できず、ファイル単位で個別記録。コミット途中でサーバーが落ちると **中途半端な状態が残る** 危険がある。
- リーナス：「CVS を使うくらいなら **パッチをメールで送る方がまだマシ**」——ブランチ・マージの実用性への不満の表れ。

**リーナスが Git で目指した 3 点**：

1. **サーバーがなくても動く**
2. **ブランチとマージが高速**
3. **データの整合性が信頼できる**

### 分散管理型：設計思想の核心

| 方式 | イメージ | 特徴 |
|------|---------|------|
| **集中管理（SVN）** | 中央の金庫に通帳だけ | サーバー依存。サーバー停止＝全滅リスク |
| **分散管理（Git）** | 全員が金庫の **完全コピー** を携帯 | オフラインでも履歴参照・コミット可能。誰か 1 人の PC が残れば **全履歴が復旧可能** |

- 実務では **参照用の中央リポジトリ** を 1 台置くことは多いが、**「そのサーバーが唯一の正」という強制がなくなった** ことが革命的。
- ブロックチェーンと **本質的に似た思想**（Git の方が **10 年以上前** に実装）——ただし目的・仕組みは別物。

### 技術的本質：差分ではなくスナップショット

**古い VCS（CVS/SVN）**：

- **差分（デルタ）** を積み重ねる方式。「ファイル A の 3 行目がこう変わった」という **変化のリスト**。
- 変更が **1 万個** 積もると、特定時点の再現に **最初から全部たどり直す** 必要があり、遅くなる。

**Git**：

- **スナップショット**——その瞬間のプロジェクト全体の状態を記録（厳密にはファイル単位の **ツリー構造** として保存）。
- **コンテンツアドレス**：ファイル中身を **ハッシュ値（指紋）** で管理。中身が同じなら **重複保存せず参照のみ**。内部的に差分圧縮も併用 → 容量は思ったより抑えられる（アニメの **同じ背景の使い回し** に近い）。

### 有向非巡回グラフ（DAG）とマージ

- 各 **コミット（セーブポイント）** が **親コミットへの矢印** を 1 本以上持つ、**ループのない有向グラフ**。
- **マージコミット** は親が **2 つ**（合流した瞬間に「お父さん A・お母さん B」）——枝が **別れた瞬間** ではなく **くっついた瞬間** に二親が生まれる。
- この構造により **共通の祖先コミット** を高速に特定でき、**3-way マージ** と組み合わさって **マージが速く正確** になる。

### 整合性：SHA-1 ハッシュ

- コミット・ファイル・ディレクトリ構造など **すべてのオブジェクト** に **40 桁の 16 進数（SHA-1）** の指紋を付与。
- **同じデータ → 同じハッシュ**、**1 ビットでも変更 → 全く別の値**。
- 過去のコミットを改ざんするとそのハッシュが変わり、**子コミットのハッシュも連鎖的に変わる** → 即座に検出可能。
- リーナス本人の説明では、主目的は **悪意ある改ざん防止** ではなく **ネットワーク転送・ディスク障害による偶発的なデータ破損の検出**。悪意への完全防御は **署名** など別の仕組みが担う——**設計目的と結果的な効果を分けて理解する** ことが正確。

### 開発タイムライン（2005 年）

| 日付 | 出来事 |
|------|--------|
| **4 月 3 日** | 開発スタート |
| **開発開始から数日** | **セルフホスト**——作りかけの Git を Git 自身で管理し始める（ツールが最低限使える証拠） |
| **4 月 18 日**（開始から **15 日**） | 複数ブランチの同時マージが初めて成功 |
| **6 月 16 日**（約 2 ヶ月後） | Linux カーネル **2.6.12** のリリース管理が Git に移行（**本格採用**、完全一括ではなく段階的移行） |

- 企業では要件定義だけで数ヶ月かかる規模の仕事を、リーナスは **約 10 日で実用レベル** まで到達。
- 品質が保たれた理由：**(1)** 設計段階からデータ構造の核心を徹底検討 **(2)** 最初のユーザーが **Linux カーネル開発チーム** という世界最高クラスのベータテスター集団だったこと。

### 名前の由来とメンテナンス体制

- **「Git」**＝イギリス英語のスラングで「嫌なやつ・愚か者」。リーナス：「俺は自己中心的な野郎だから、プロジェクトには **自分にちんした名前** をつける」——**リナックス（Linus）→ Git（自分が git なやつ）** というジョークの一つ（複数のジョークを語っており、唯一の由来とは言い切れない）。
- README に由来説明が残る **歴史的ユーモア**。
- 開発が落ち着くとリーナスは **Linux カーネルに集中** するためメンテナを譲渡。**浜野順（Junio Hamano）** が **2005 年から** メンテナを担当——リーナスが生み、浜野さんが育てた、という分担。

### Git と GitHub の違い

| | **Git** | **GitHub** |
|---|---------|------------|
| **正体** | **コマンドラインツール**（ターミナルで使うソフトウェア） | Git を土台にした **Web 上の開発コラボレーションプラットフォーム** |
| **管理** | 商標は **FSF（ソフトウェア自由のための財団）** | Microsoft が **2018 年に約 75 億ドル（当時で約 8,000 億円規模）** で買収 |
| **機能** | 履歴管理・ブランチ・マージなど **VCS 本体** | コードホスティング、Issue、レビュー、**プルリクエスト** など開発ワークフロー全体 |
| **開始** | **2005 年** | 開発 **2007 年**、正式サービス **2008 年 4 月** |

- **プルリクエスト（PR）**：「こう変更したので本流に取り込んでください」という **お願い＋レビュー** の仕組み。勝手に書き換えるのではなく、透明なプロセスで品質を保つ——**ソーシャルコーディング** の象徴。
- それ以前のオープンソースは **メーリングリスト＋パッチファイル** が主流。GitHub が **誰でも読め・報告でき・変更を提案できる場** にし、PR を使いやすく広めた。
- **2023 年時点**：GitHub 上に **1 億人以上のアカウント**、**3 億以上のリポジトリ**（公式発表）。企業内では **GitHub Enterprise・GitLab・Gerrit** なども併用されるが、開発文化の中心的存在は間違いない。

### 世界への影響

- Git/GitHub がなければ、**現規模のオープンソース共同開発文化** は成立しなかった、という見方は技術者の間で多い（CVS/SVN 時代にも OSS はあったが、**今のような規模・速度** は困難だった）。
- **Linux カーネル・Python・Android** など、主要プロジェクトはすべて Git で管理されている。

### 教訓：怒りだけでは革命は起きない

- リーナスの本当の強みは **起きたことへの反応** より、**正しい設計を事前に知っていたこと**。
  - 分散にする、スナップショットにする、全オブジェクトをハッシュで管理する——これらは **コンピュータサイエンスの深い理解** がないと出てこない設計判断。
- **「何が悪いかを正確に言語化できる人間だけが、それを正確に解決できる」**——ソフトウェアに限らない教訓。

### 現在の進化と実務のヒント

- **SHA-1 の衝突攻撃** への対応として、より安全な **SHA-256** への段階的移行が進行中（完全移行は未了、**後方互換を保ちながら** 長期計画）。
- 約 **20 年前** に作られたものが現役で進化し続けるのは、**データの保存形式と処理手順（ネットの部分）** を正しく設計した証拠。
- **コミットメッセージ**：「fix」だけでなく **何を・なぜ直したか** を書く（例：「ログイン時にパスワードが空でも通過できるバグを修正」）。後から自分や仲間が履歴を追うときに決定的。リーナス自身も **雑なコミットメッセージに容赦なく怒る** ことで有名——Git を使う上でもその精神が生きている。
