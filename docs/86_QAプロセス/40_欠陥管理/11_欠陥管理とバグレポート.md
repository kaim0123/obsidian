# 欠陥管理とバグレポート

テストで見つけた不具合を**欠陥（デフェクト）・バグ**として記録し、修正〜完了まで追うプロセスを**欠陥管理**といいます。QAエンジニアは、**再現可能で修正しやすいバグレポート**を書くことが重要です。

---

## 1. 欠陥（デフェクト）とは

- **欠陥（Defect / Bug）**: ソフトウェアが仕様・要件・期待される振る舞いと異なる状態、あるいはユーザーに悪影響を与える問題。
- テストで「期待結果と実際の結果が一致しない」「仕様にない不具合」を発見した場合、それを欠陥として登録し、開発側と共有する。

---

## 2. 欠陥のライフサイクル（状態遷移）

欠陥は、発見からクローズまで**状態**で管理することが多いです。プロジェクトやツールによって名前は異なりますが、典型的な流れは以下のとおりです。

| 状態（例） | 説明 |
|------------|------|
| **新規（New）** | テスト担当者が不具合を登録した直後 |
| **割り当て済み（Assigned）** | 修正担当者（開発者）が決まった |
| **対応中（In Progress）** | 修正作業中 |
| **修正済み（Fixed）** | 修正が完了し、再テスト待ち |
| **再現しない（Cannot Reproduce）** | 再現手順では再現せず、要確認・情報追加 |
| **保留（Deferred / Postponed）** | 今回リリースでは対応しない（優先度・リソースの都合） |
| **クローズ（Closed）** | 修正確認済みで完了、または「対応しない」と判断して完了 |
| **再オープン（Reopened）** | 再テストでまだ不具合が残っていた場合、再度オープン |

- **ワークフロー**: 新規 → 割り当て → 対応中 → 修正済み → （再テスト）→ クローズ or 再オープン。
- 「修正済み」のあと、QAが再テストして問題なければ「クローズ」、問題があれば「再オープン」とする運用が一般的。

---

## 3. 深刻度（Severity）と優先度（Priority）

### 3.1 深刻度（Severity）

**欠陥がシステム・ユーザーに与える影響の重さ**を表します。開発・QAが「技術的にどの程度ひどいか」を評価する際に使います。

| レベル（例） | 説明 | 例 |
|--------------|------|-----|
| **Critical（致命的）** | システム停止、データ損失、重大なセキュリティ問題 | ログイン不可、決済が通らない、クラッシュ |
| **Major（重大）** | 主要機能が使えない、代替手段がない | 検索が常にエラー、保存ができない |
| **Minor（軽微）** | 機能は動くが誤表示・軽い誤動作 | 文言ミス、一部レイアウト崩れ |
| **Trivial（ trivial ）** | 影響がごく小さい | コメントの誤字、未使用コード |

### 3.2 優先度（Priority）

**いつまでに直すか（対応の優先順位）**を表します。ビジネス・リリース計画を考慮して、プロジェクト・プロダクトオーナーなどが決めることが多いです。

| レベル（例） | 説明 |
|--------------|------|
| **High** | すぐに対応する（リリースブロッカーになりうる） |
| **Medium** | 計画されたスプリント・リリース内で対応 |
| **Low** | 余裕があれば対応、バックログに積む |

- **重要**: 深刻度が高くても、優先度を「Low」にする場合がある（例：影響範囲が限定的で回避策がある）。逆に、深刻度は中でもビジネス影響が大きければ優先度を高くする、という判断が行われる。

---

## 4. 良いバグレポートの書き方

再現できず「再現しない」でクローズされる原因の多くは、**レポートの情報不足**です。以下の要素をそろえると、開発者が再現・修正しやすくなります。

### 4.1 必須といえる項目

| 項目 | 内容 |
|------|------|
| **タイトル（件名）** | 何がおかしいかを一文で要約（例：「ログイン画面でメール形式でない入力でも送信できてエラーになる」） |
| **再現手順（Steps to Reproduce）** | 操作を**番号付きで具体的に**書く。「〜を開いて」ではなく「URL ○○ を開き、ログインIDに `test@example.com` と入力し…」のように、第三者が同じ操作を再現できるレベルで書く |
| **期待結果** | 仕様・要件から期待される正しい振る舞い |
| **実際の結果** | 実際に起きたこと（エラーメッセージ、画面の状態、ログの抜粋など） |
| **環境** | OS、ブラウザ（バージョン）、アプリのバージョン、端末（モバイルの場合）など |

### 4.2 あると有用な項目

- **発生条件**: いつでも起きるのか、特定のデータ・時間・順序のときだけか。
- **発生頻度**: 毎回／ときどき／1回だけ。
- **スクリーンショット・動画**: エラー画面、コンソール、ネットワークタブなど。
- **ログ・スタックトレース**: アプリログやブラウザコンソールのエラーを貼る。
- **関連するテストケース・要件**: どの仕様・テストケースに紐づくか。

### 4.3 書くときのポイント

- **事実と解釈を分ける**: 「バグだ」ではなく「○をしたら△と表示された。仕様では□とある」と書く。
- **1件1バグ**: 複数の不具合を1本のチケットに書まず、1件ずつ分ける。
- **再現手順を自分でやり直す**: 手順だけ読んで第三者が再現できるか確認する。

---

## 5. 欠陥管理の実務

- **ツール**: Jira、Redmine、Backlog、GitHub Issues、Azure DevOps などで欠陥をチケット管理するのが一般的。
- **運用**: 起票者・担当者・状態・深刻度・優先度・修正バージョン・再テスト結果などを揃え、定期的にバグ会議や triage で優先度・スコープを調整する。
- **メトリクス**: オープン数、修正済み数、再オープン率、平均解決時間などを見て、品質トレンドやリリース可否の判断材料にする（[[16_テストメトリクスと品質指標]] 参照）。
