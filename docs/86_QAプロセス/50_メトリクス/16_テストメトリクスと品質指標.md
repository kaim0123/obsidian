# テストメトリクスと品質指標

テストの進捗・効果・品質の状態を客観的に把握するために、**メトリクス（指標）**を使います。QAエンジニアは、何を測り、どう解釈するかを理解し、リリース判断や改善活動に役立てます。

---

## 1. テスト進捗に関するメトリクス

### 1.1 実施進捗

| 指標 | 説明 | 活用例 |
|------|------|--------|
| **計画テスト数** | 計画したテストケースの総数 | スコープの把握 |
| **実施済み数** | 実行したテストケースの数 | 進捗率の算出 |
| **合格数 / 不合格数** | Pass / Fail の内訳 | 残作業の把握 |
| **進捗率** | 実施済み / 計画数 × 100（%） | スケジュールとの照合 |

- 進捗率だけでは「品質」は分からない。合格率や欠陥の傾向と合わせて見る。

### 1.2 カバレッジ（網羅率）

| 種類 | 説明 | 注意点 |
|------|------|--------|
| **要件カバレッジ** | 要件のうち、テストでカバーした割合 | 要件の粒度に依存 |
| **コードカバレッジ** | コードの行・分岐のうち、テストで実行された割合 | 高ければよいというわけではない（ dead code や無意味なテストの可能性） |
| **テストケースカバレッジ** | テスト観点・条件のうち、テストケースでカバーした割合 | 設計の網羅性の目安 |

- カバレッジは**何を基準にしているか**を明確にし、**未カバー部分のリスク**を意識して解釈する。

## 2. 欠陥に関するメトリクス

### 2.1 欠陥の数・傾向

| 指標 | 説明 | 活用例 |
|------|------|--------|
| **発見欠陥数** | テストで見つかった欠陥の数 | 品質トレンド、モジュール別の傾向 |
| **オープン欠陥数** | 未クローズの欠陥数 | リリースブロッカーの把握 |
| **深刻度別の内訳** | Critical / Major / Minor などの数 | リリース可否の判断 |
| **修正済み・未修正** | 修正済みの数、再オープン数 | 開発対応状況の把握 |

### 2.2 欠陥密度・傾向

| 指標 | 説明 |
|------|------|
| **欠陥密度** | 欠陥数 / 規模（KLOC、機能点、ストーリーポイントなど） |
| **再オープン率** | 再オープンした欠陥 / 修正済みとした欠陥数 |
| **モジュール・機能別の欠陥分布** | どこに欠陥が集中しているか（リスクの高い領域の特定） |

- 欠陥が「増えている」ことが必ずしも悪いわけではない。テストを進めた結果、発見が増えている可能性もある。**クローズ率や深刻度の推移**と合わせて見る。

---

## 3. リリース判断に使う指標（例）

- **クリティカル・ブロッカー**: 0 件であること（または合意した基準を満たすこと）。
- **テスト完了率**: 計画したテストのうち、実施・合格した割合が基準以上（例：100% 実施、合格率 95% 以上）。
- **オープン欠陥**: 残り欠陥の深刻度・優先度が許容範囲内（例：Major 以上は 0、Minor は N 件まで許容）。
- **自動テスト**: 主要な回帰テストがパスしていること（CI がグリーンなど）。

これらは**出口基準（Exit Criteria）**としてテスト計画に書いておき、達成したかどうかでリリース可否を議論する。

---

## 4. テスト効率・効果の指標（例）

| 指標 | 説明 |
|------|------|
| **欠陥検出率** | 発見した欠陥数 / 実施したテスト数（または時間） |
| ** escaped defects ** | 本番で発覚した欠陥数（テストで拾えなかったもの）。少ないほどテストの効果が高い |
| **自動化率** | 自動テスト数 / 全回帰テスト数（目安。自動化の進捗） |
| **テスト実行時間** | 回帰テスト一式の実行時間（短いほどフィードバックが早い） |

---

## 5. 解釈の注意点

- メトリクスは**文脈なしに単体で解釈しない**。プロジェクトのフェーズ、スコープの変更、リソースの増減を考慮する。
- **数値目標の悪用**（欠陥数を減らすために報告を控える、など）を防ぐため、目的を「品質の可視化と改善」に置く。
- メトリクスは**改善のための材料**。トレンドを見て、テスト設計の見直し、リスクの再評価、自動化の優先度の調整に活かす。
