# ビジュアル回帰（Playwrightスナップショット）

## そもそも「ビジュアル回帰テスト」とは？

ビジュアル回帰テストとは、**Webページのスクリーンショットを撮影して保存しておき、コード変更後のスクリーンショットと自動比較することで、見た目の変化を検出する**テスト手法のこと。

たとえるなら、リフォーム前の部屋の写真を撮っておいて、リフォーム後に同じアングルで写真を撮り、「意図しない変化がないか」を比べるようなもの。壁紙を変えたのは意図通りだが、天井にヒビが入っていたら問題──それを自動で検出する仕組み。

CSSの変更やコンポーネントの更新は、意図した画面以外にも影響を及ぼすことがある。コードレビューでは「CSSのプロパティが変わった」ことはわかっても、「実際の見た目がどう変わったか」は確認しづらい。ビジュアル回帰テストは、この「見た目の差分」を画像として明確にする。

## 目的

- CSS 変更やコンポーネント更新による **見た目の崩れ**（レイアウト、余白、フォント、色の意図しない変化）を自動検知する
- コードレビューでは見落としやすい「UIの微妙な差分」を、画像の差分として明確にする

## 何をチェックするか（代表例）

### 1. 主要ページの全体スクリーンショット

ページ全体を撮影して、レイアウトの崩れや予期しない変化を検出する。

- トップページ
- 検索結果ページ
- 詳細ページ
- フォームページ

### 2. 重要コンポーネント単位

ページ全体ではなく、特定のコンポーネント（UIパーツ）だけを切り出して撮影する。ページ全体よりも差分が検出しやすく、安定しやすい。

- カード（商品カード、記事カードなど）
- ナビゲーションバー
- モーダル（ポップアップダイアログ）
- フォーム部品（入力欄、ボタン、セレクトボックスなど）

### 3. 状態の差分

同じコンポーネントでも、状態によって見た目が変わるものは、各状態をそれぞれ撮影する。

- **エラー表示**: バリデーションエラーが表示された状態
- **空状態**: データがないときの「データがありません」表示
- **ローディング**: データ読み込み中のスピナーやスケルトン表示
- **ダークモード**: ライトモードとダークモードの両方

### 4. レスポンシブ

画面サイズによってレイアウトが変わる場合、主要なブレークポイントごとに撮影する。

- **デスクトップ**: 1280px 幅
- **タブレット**: 768px 幅
- **モバイル**: 375px 幅

```typescript
// Playwright でビューポートサイズを指定してスクリーンショットを撮る例
await page.setViewportSize({ width: 375, height: 812 });
await expect(page).toHaveScreenshot("top-mobile.png");
```

## 失敗しがちなポイント（フレーク要因）

ビジュアル回帰テストは「画像の比較」であるため、わずかな差でも「差分あり」と判定されてしまう。以下は「本当は問題ないのにテストが落ちる」よくある原因。

### 時刻 / 乱数 / 広告枠などの可変要素

画面に現在時刻、ランダムなおすすめコンテンツ、広告バナーなどが表示されていると、撮影するたびに画像が変わる。

### フォント差（OS / CI 環境）

開発者のMac（ヒラギノフォント）とCI環境のLinux（Notoフォント）ではフォントのレンダリングが微妙に異なる。文字の太さや間隔がピクセル単位で違うだけでテストが失敗する。

### アニメーション / 遷移の途中を撮影

要素がフェードインしている途中や、スライドアニメーションの途中でスクリーンショットを撮ると、毎回異なる画像になる。

### データ差

テスト実行のたびにAPIから取得するデータが異なると、表示内容が変わり差分が出る。

## 安定化のコツ

### 固定データを使う

テスト専用の固定データ、またはモック（偽のAPIレスポンス）を用意して、表示内容が毎回同じになるようにする。

```typescript
// Playwright でAPIレスポンスをモックする例
await page.route("**/api/products", (route) => {
  route.fulfill({
    body: JSON.stringify([
      { id: 1, name: "テスト商品A", price: 1000 },
      { id: 2, name: "テスト商品B", price: 2000 },
    ]),
  });
});
```

### マスク / 除外

動的に変化する領域をマスク（黒塗りなどで覆い隠す）して、比較対象から除外する。

```typescript
// 特定の要素をマスクして比較する
await expect(page).toHaveScreenshot("top.png", {
  mask: [
    page.locator('[data-testid="current-time"]'),
    page.locator('[data-testid="ad-banner"]'),
  ],
});
```

### 待機の徹底

フォントの読み込み、画像の読み込み、アニメーションの完了を確実に待ってから撮影する。

```typescript
// ❌ 悪い例: 固定秒数の待機
await page.waitForTimeout(3000);

// ✅ 良い例: 条件を満たすまで待機
await page.waitForLoadState("networkidle"); // ネットワーク通信が落ち着くまで待つ
// アニメーションを無効化する方法もある
await page.emulateMedia({ reducedMotion: "reduce" });
```

### 環境統一

CI環境のフォント、解像度、レンダリング条件を固定する。Docker コンテナを使って、毎回同じ環境でテストを実行するのが最も確実。

> **しきい値（threshold）の設定**: Playwright の `toHaveScreenshot` には、どの程度の差分を許容するかを設定できる `maxDiffPixelRatio` オプションがある。ピクセル単位の微差を無視するために、小さなしきい値（例: 0.01 = 1%）を設定することもある。ただし、しきい値を大きくしすぎると本物のバグを見逃すリスクがある。

## 運用の考え方

### 「更新の手間」もコスト

ビジュアル回帰テストは、意図的なデザイン変更をしたときにもスクリーンショットの更新が必要になる。画面数が多いほどこの更新作業が膨大になるため、**本当に重要な画面に絞る**ことが大切。

### 差分レビューを儀式化する

スクリーンショットに差分が出たとき、以下の判断をする。

1. **意図した変更か？** → スクリーンショットを更新する（`npx playwright test --update-snapshots`）
2. **意図しない変更か？** → 原因を調査して修正する

この判断をPRレビューの中で必ず行うフローにしておく（「画像差分が出ていますが、意図通りですか？」と確認する）。

### PR 必須テストは最小限にする

```
PR:
  → 主要フロー（トップ、ログイン、検索結果）のスクリーンショットのみ必須

nightly:
  → 全ページ・全状態・全ブレークポイントの網羅的な比較
```

PR で全画面を比較すると、デザイン変更のたびに大量のスクリーンショット更新が発生し、開発速度が落ちる。
