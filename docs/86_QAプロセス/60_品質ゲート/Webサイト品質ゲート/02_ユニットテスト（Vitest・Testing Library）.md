# ユニットテスト（Vitest・Testing Library）

## そもそも「ユニットテスト」とは？

ユニットテストとは、プログラムの **最小単位（関数やコンポーネント）** を個別に取り出して、正しく動作するかを検証するテストのこと。

たとえば料理で言えば、「完成した料理を味見する」のではなく、「塩を量る計量スプーンが正確か」「包丁がちゃんと切れるか」を個別にチェックするようなもの。部品レベルで品質を担保しておけば、組み合わせたときに壊れる可能性が大幅に減る。

## 目的

- 小さな単位（関数・コンポーネント・モジュール）の仕様を固定し、**ロジックの回帰バグ**（以前は正しく動いていたものが壊れること）を早期に検知する。
- E2E テスト（ブラウザを使った結合テスト）で見つけると時間もコストもかかる不具合を、**安価に・高速に** 検出する。

> **Vitest とは？**
> JavaScript / TypeScript 向けの高速なテストフレームワーク。Vite（ビルドツール）と親和性が高く、設定が少なくてすぐに使い始められる。Jest の代替として急速に普及している。

> **Testing Library とは？**
> UI コンポーネントのテストを「ユーザーの視点」で書くためのライブラリ。「ボタンをクリックしたら何が表示されるか」をテストする。内部実装の詳細には踏み込まず、ユーザーが実際に操作するのと同じ観点でテストを書くことを推奨している。

## 何をテストするか（優先度の目安）

すべての関数にテストを書く必要はない。効果が高いところから順に書いていく。

### 1. ドメイン / ビジネスロジック（最優先）

アプリケーションの核心となる計算・判定ロジック。ここが壊れるとユーザーに直接的な被害が出る。

- **金額計算**: 税込み計算、割引適用、合計算出（1円のずれでも問題になる）
- **バリデーション**: メールアドレスの形式チェック、パスワード強度の判定、入力値の範囲チェック
- **状態遷移**: 注文ステータスの変更（「未発送 → 発送済み → 配達完了」の遷移ルール）

### 2. 境界条件

プログラムが「普通じゃない入力」を受け取ったときの挙動。バグはこの境界で発生しやすい。

- **null / undefined**: 値が存在しない場合に正しく処理されるか
- **空配列 / 空文字列**: 要素が0個のときにエラーにならないか
- **桁あふれ**: 数値が非常に大きい・小さいときにどうなるか
- **タイムゾーン**: 日付処理が UTC と JST で結果が変わらないか

### 3. 分岐・例外

エラーが起きたときに、適切なメッセージを返すか、正しいリカバリーをするか。

- **エラー時のメッセージ**: 「不正な入力です」のような適切なエラーメッセージが返されるか
- **例外処理**: API が失敗したときにクラッシュせず、適切にエラーハンドリングされるか
- **リトライ条件**: 「3回失敗したら諦める」のようなロジックが正しく動くか

### 4. UI（Testing Library）

コンポーネントが正しく表示・動作するかを、ユーザーの視点で確認する。

- 「ボタンをクリックしたらモーダルが開く」
- 「フォームに入力してSubmitしたら、成功メッセージが表示される」
- 「エラーが起きたら、エラーメッセージが画面に表示される」

## アンチパターン（やってしまいがちな失敗）

### 実装詳細テスト

```
❌ 悪い例: 「内部の関数Aが3回呼ばれたことを確認する」
✅ 良い例: 「入力に対して期待する出力が返ることを確認する」
```

内部の実装方法（どの関数を何回呼ぶか、内部の変数がどういう値になるか）をテストで固定してしまうと、コードをリファクタリング（動作を変えずに実装を整理すること）したときにテストが大量に壊れる。テストが壊れるのが怖くてリファクタリングできなくなるという本末転倒な状況に陥る。

> **原則**: テストは「何を入れたら何が出るか（入力と出力）」を検証すべきであり、「どうやって処理しているか（内部実装）」を検証すべきではない。

### スナップショット乱用

スナップショットテストとは、コンポーネントの出力（HTML構造）を丸ごと保存し、次回実行時に差分がないか比較する手法。便利に見えるが、安易に多用すると問題が起きる。

- ちょっとした CSS クラス名の変更でもテストが壊れる
- 差分が出たとき、「何が重要な変更で、何が無視していい変更か」が判断できない
- 結果として「とりあえずスナップショットを更新する」が習慣化し、テストの意味がなくなる

> **代わりにどうするか**: 「この要素が表示されているか」「このテキストが含まれているか」など、**重要なポイントだけを明示的にアサーション（検証）** する。

### 外部 I/O に依存する

テストがネットワーク通信、現在時刻、乱数などの外部要因に依存すると、同じテストなのに実行するたびに結果が変わる「不安定なテスト」になる。

- **ネットワーク**: 実際の API サーバーに通信するテストは、サーバーの状態によって成功したり失敗したりする
- **時刻**: `new Date()` に依存するテストは、実行する時間帯によって結果が変わる
- **乱数**: `Math.random()` に依存するテストは、毎回結果が変わる

> **対策**: モック（偽物の代替品）を使う。API通信には `msw`（Mock Service Worker）、時刻には `vi.useFakeTimers()`、乱数にはシード値の固定など。

## テスト設計のコツ

### AAA パターン（Arrange-Act-Assert）

テストを3つのブロックに分けて書く。読みやすく、何をテストしているか一目でわかる。

```typescript
test("税込み価格が正しく計算される", () => {
  // Arrange（準備）: テストに必要なデータや状態を用意する
  const price = 1000;
  const taxRate = 0.1;

  // Act（実行）: テスト対象の関数を呼び出す
  const result = calculateTaxIncluded(price, taxRate);

  // Assert（検証）: 結果が期待通りか確認する
  expect(result).toBe(1100);
});
```

### テスト名を具体的にする

テスト名は「どういう条件で、何が起きるか」を明示する。日本語で書いても問題ない。

```typescript
// ❌ 悪い例: 何をテストしているかわからない
test("calculate", () => { ... });

// ✅ 良い例: 条件と期待結果が明確
test("税率10%のとき、1000円の商品は税込み1100円になる", () => { ... });
test("価格が0円のとき、税込み価格も0円になる", () => { ... });
test("価格が負の値のとき、エラーがスローされる", () => { ... });
```

### 境界値を意識する

**同値分割**（入力を「同じ結果になるグループ」に分ける）と **境界値分析**（グループの境目の値をテストする）を組み合わせると、少ないテストケースで効率よくバグを見つけられる。

```
例: 「18歳以上なら成人」という判定ロジック
- 17歳（境界の直前）→ 未成年
- 18歳（境界値）→ 成人
- 19歳（境界の直後）→ 成人
```

## 実行戦略（CI）

- PR ではユニットテストを **必須化** する（ユニットテストが通らない PR はマージできない）
- E2E テストは別ジョブにする（ユニットテストは数秒〜数十秒で終わるが、E2E テストは数分かかることが多い。まずユニットテストで素早くフィードバックを得る）
- 失敗時に原因がわかるよう、**アサーションメッセージを丁寧に書く**

```typescript
// ❌ アサーションメッセージがない → 失敗時に何が問題か分からない
expect(result).toBe(1100);

// ✅ メッセージがある → 失敗時にすぐ原因が分かる
expect(result).toBe(1100);
// Vitest ではテスト名が十分に具体的であれば、追加メッセージは不要な場合も多い
// テスト名で「何が起きるべきか」を明確にすることが最も重要
```
