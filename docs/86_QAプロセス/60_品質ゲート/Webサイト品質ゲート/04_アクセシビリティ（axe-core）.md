# アクセシビリティ（axe-core）

## そもそも「アクセシビリティ（a11y）」とは？

アクセシビリティとは、**障害の有無や利用環境に関係なく、誰もがWebサイトやアプリを利用できるようにすること**。

たとえば以下のような人々がWebを利用している。

- **視覚障害**: スクリーンリーダー（画面読み上げソフト）を使ってWebページの内容を音声で聞いている
- **色覚特性**: 赤と緑の区別がつきにくく、色だけで情報を伝えるUIでは内容がわからない
- **運動障害**: マウスが使えず、キーボードだけで操作している
- **一時的な制約**: 片手にケガをしている、明るい屋外でスマホを見ている、騒がしい環境にいる

アクセシビリティが不十分なサイトは、こうした人々が「操作できない」「読めない」「理解できない」状態になる。これは単に「配慮が足りない」という問題ではなく、ユーザーを排除してしまっている状態。

> **「a11y」とは？**
> "accessibility" の略記。a と y の間に11文字あるため "a11y"（a-eleven-y）と表記される。"i18n"（internationalization）と同じ略記法。

## 目的

- 障害の有無や利用環境に関わらず、誰もが機能を利用できる状態を担保する
- 重大なアクセシビリティ欠陥（操作不能、読み上げ不能）を早期に検知し、手戻りを減らす
- 結果的に **SEO**（検索エンジンもHTMLの意味構造を読むため）、**CVR**（より多くのユーザーが使えれば転換率も上がる）、**法令/社内基準への適合**にも寄与する

> **axe-core とは？**
> Deque Systems が開発したアクセシビリティ検査エンジン。HTMLをスキャンして、WCAG（Web Content Accessibility Guidelines）に基づくルール違反を自動検出する。Playwright や他のテストフレームワークに組み込んで使える。

## 何をチェックするか（代表例）

### 1. 名前 / ラベル

フォームの入力欄に「何を入力すべきか」がプログラム的に伝わるかどうか。

```html
<!-- ❌ 悪い例: スクリーンリーダーが「テキスト入力欄」としか読めない -->
<input type="text" placeholder="メールアドレス" />

<!-- ✅ 良い例: スクリーンリーダーが「メールアドレス」と読み上げる -->
<label for="email">メールアドレス</label>
<input type="text" id="email" />

<!-- ✅ または aria-label で明示する -->
<input type="text" aria-label="メールアドレス" />
```

> **なぜ placeholder ではダメなのか？**
> `placeholder` は入力を開始すると消えてしまう。スクリーンリーダーによっては読み上げない実装もある。`label` 要素や `aria-label` を使うことで、常にアクセス可能な名前が提供される。

### 2. 見出し構造

`h1`〜`h6` の見出しタグが、ページの論理的な構造を正しく反映しているか。

```html
<!-- ❌ 悪い例: h2 が飛んでいる（h1 → h3） -->
<h1>サイトタイトル</h1>
<h3>セクション名</h3>

<!-- ✅ 良い例: 階層が連続している -->
<h1>サイトタイトル</h1>
<h2>セクション名</h2>
<h3>サブセクション名</h3>
```

> スクリーンリーダーのユーザーは、見出しの一覧を使ってページ内をジャンプ移動する。見出しの階層が壊れていると、ページ構造を理解できない。

### 3. コントラスト

文字色と背景色のコントラスト比が十分かどうか。コントラストが低いと、視力が弱い人や明るい環境で見ている人には文字が読めない。

- **通常テキスト**: コントラスト比 4.5:1 以上（WCAG AA基準）
- **大きいテキスト（18pt以上、または14pt太字以上）**: コントラスト比 3:1 以上

> たとえば白い背景に薄いグレーの文字（`#999`）はコントラスト比が約 2.85:1 で、基準を下回る。

### 4. キーボード操作

マウスを使わなくても、キーボードだけですべての操作ができるか。

- **Tab キーでのフォーカス移動**: すべてのインタラクティブ要素（リンク、ボタン、入力欄）に Tab キーで到達できるか
- **フォーカスの視認性**: 今どの要素にフォーカスがあるか、視覚的にわかるか（フォーカスリングが表示されるか）
- **操作不能な要素がないか**: `div` に `onClick` を付けただけの「ボタンのようなもの」は、キーボードで操作できない

```html
<!-- ❌ 悪い例: divはキーボードで操作できない -->
<div onclick="handleClick()">クリック</div>

<!-- ✅ 良い例: button要素はキーボードで自然に操作できる -->
<button onclick="handleClick()">クリック</button>
```

### 5. ARIA の誤用

ARIA（Accessible Rich Internet Applications）属性は、HTMLの意味を補足するためのもの。正しく使えばアクセシビリティを向上させるが、誤用すると逆にスクリーンリーダーを混乱させる。

- **不正な role**: `<div role="button">` と書いたのに、キーボード操作やフォーカスを実装していない
- **属性の矛盾**: `aria-hidden="true"` を付けた要素の中にフォーカス可能な要素がある
- **参照先の不整合**: `aria-labelledby="foo"` と書いたが、`id="foo"` の要素が存在しない

> **ARIA の第一ルール**: 「ネイティブ HTML 要素で表現できるなら、ARIA を使わない」。`<button>` を使えばいいところを `<div role="button">` にする必要はない。

## 自動テストでできること・できないこと

### 得意なこと（axe-core が検出できる）

- ラベルの欠落
- ARIA 属性の不整合
- コントラスト不足
- 見出し構造の破綻
- 画像の代替テキスト（alt属性）の欠落
- フォーカス管理の基本的な問題

### 苦手なこと（人間の判断が必要）

- **代替テキストの妥当性**: `alt="画像"` と書いてあれば機械的にはOKだが、それが画像の内容を適切に伝えているかは判断できない
- **文言のわかりやすさ**: 「ここをクリック」というリンクテキストより「利用規約を見る」のほうがわかりやすい、という判断は機械には難しい
- **操作フローの理解しやすさ**: フォームの入力手順が直感的かどうか
- **動的コンテンツの操作性**: モーダルが開いたときにフォーカスが適切に移動するか（一部は検出可能だが、完全ではない）

> **結論**: 自動テストは「最低限の安全柵」。アクセシビリティを本気で担保するなら、実際のスクリーンリーダーを使った手動テストや、障害を持つユーザーによるユーザーテストも組み合わせる。

## 運用のポイント

### まずは致命傷を潰す

axe-core の検出結果には severity（深刻度）がある。

- **critical**: 操作不能、コンテンツにアクセスできないなど致命的な問題
- **serious**: 大きな支障はあるが、代替手段で回避可能な場合もある問題
- **moderate**: 一部のユーザーに影響がある問題
- **minor**: 小さな改善点

最初は `critical` と `serious` をブロック対象（これが検出されたらマージ不可）にし、改善が進んだら段階的に対象を広げる。

### E2E テストに統合する

Playwright のテスト実行後に `@axe-core/playwright` でページをスキャンするのが効率的。既存のE2Eテストに数行追加するだけで、アクセシビリティチェックも同時に実行できる。

```typescript
import AxeBuilder from "@axe-core/playwright";

test("トップページのアクセシビリティ", async ({ page }) => {
  await page.goto("/");
  const results = await new AxeBuilder({ page })
    .withTags(["wcag2a", "wcag2aa"]) // WCAG 2.x の A/AA 基準でチェック
    .analyze();
  expect(results.violations).toEqual([]);
});
```

### 対象画面を絞る

全ページを毎PRでチェックするのは現実的でない場合が多い。まずは以下のような「影響が大きい画面」を優先する。

- トップページ
- 検索結果ページ
- フォーム（問い合わせ、会員登録、購入など）
- ログインページ

### 例外を増やしすぎない

axe-core のルールを `disable`（無効化）する例外が増えるほど、検出力が落ちる。例外を設定する場合は、必ず **理由**（なぜ今は対応できないのか）と **期限**（いつまでに対応するか）をセットにする。

```
  → 全ページを対象にした包括的な a11y スキャン
```
