# バンドルサイズ予算（size-limit）

## そもそも「バンドルサイズ」とは？

Webアプリケーションを公開するとき、開発中に書いた複数のJavaScriptファイルやCSSファイルは、ビルドツール（Vite、webpack など）によって1つまたは少数のファイルにまとめられる。このまとめられたファイルを「バンドル」と呼び、そのファイルサイズが「バンドルサイズ」。

ユーザーがWebサイトにアクセスすると、このバンドルをダウンロードして実行する。バンドルサイズが大きいほど、ダウンロードに時間がかかり、ブラウザでの実行にも時間がかかり、結果として **ページの表示が遅く、操作の反応が鈍くなる**。

たとえるなら、レストランのメニュー表が分厚い百科事典のようになっていたら、読み込む（読む）のに時間がかかるのと同じ。必要な情報だけが載った簡潔なメニューのほうが、すぐに注文できる。

## 目的

- JS / CSS の肥大化を継続的に抑え、読み込み遅延・操作遅延の回帰を防ぐ
- 「便利だから追加したライブラリ」が積み重なって起きるパフォーマンス劣化を、PR（プルリクエスト）の時点で検知する

> **size-limit とは？**
> JavaScript のバンドルサイズをチェックするツール。設定した上限（バジェット）を超えるとエラーを出す。gzip / brotli 後のサイズで計測できるため、実際の配信サイズに近い指標が得られる。PR のコメントにサイズの増減を表示する機能もある。

## 何をチェックするか（代表例）

### 1. エントリポイント別サイズ

Webアプリケーションには通常、複数の「入口」（エントリポイント）がある。それぞれのサイズを個別に監視する。

- **`main`**: メインのアプリケーションバンドル
- **`admin`**: 管理画面用のバンドル
- **`landing`**: ランディングページ用のバンドル

> エントリポイントごとに監視することで、「管理画面にだけ巨大なライブラリが追加された」のように、問題の発生箇所を特定しやすくなる。

### 2. gzip / brotli 後のサイズ

JavaScriptファイルはサーバーからブラウザに送信される際、通常は圧縮される。圧縮前のサイズ（例: 500KB）と圧縮後のサイズ（例: 150KB）は大きく異なるため、**圧縮後のサイズで計測する**のが実態に近い。

- **gzip**: 最も広くサポートされている圧縮方式
- **brotli**: gzip より圧縮率が高い。モダンブラウザはほぼ対応済み

### 3. 増分（diff）

PR で「何KB増えたか」「何KB減ったか」を表示する。これにより、レビューアーが「このPRでバンドルサイズが急増していないか」を一目で判断できる。

### 4. チャンク分割の健全性

コード分割（Code Splitting）を使っていても、1つのチャンク（分割されたファイル）が巨大化していないかを監視する。

> **チャンクとは？**
> バンドルをさらに小さなファイルに分割したもの。たとえば「トップページに必要なコード」「管理画面に必要なコード」を分けることで、ユーザーが必要としないコードのダウンロードを避けられる。

## 予算（budget）の決め方

「バンドルサイズをいくつ以下に保つか」という数値目標が「予算（バジェット）」。

### ステップ 1: 現状を計測する

まず今のバンドルサイズを正確に把握する。

```bash
# size-limit で現状を計測
npx size-limit
```

### ステップ 2: 「大きな悪化だけ止める」ラインを設定する

現状のサイズに対して、ある程度の余裕を持たせた閾値を最初に設定する。

```json
// package.json の設定例
{
  "size-limit": [
    {
      "path": "dist/main.js",
      "limit": "150 kB",
      "gzip": true
    },
    {
      "path": "dist/admin.js",
      "limit": "200 kB",
      "gzip": true
    }
  ]
}
```

> 例えば現状が 120KB なら、まずは 150KB（+30KB）を閾値にする。「+20KB 以上増えたら何かおかしい」という感覚。

### ステップ 3: 改善が進んだら閾値を下げる

不要な依存の削除、コード分割の改善、Tree Shaking（未使用コードの除去）などで実際のサイズが改善されたら、閾値も合わせて引き下げ、**段階的に厳しく**する。

### 重要ページから優先する

すべてのエントリポイントに一律の予算を設けるより、ユーザーが最初にアクセスするページ（トップページ、ランディングページ）から優先して予算を設ける。初回表示が遅いと離脱率が上がるため、ここが最も重要。

## 失敗しがちなポイント

### 閾値が厳しすぎて常に赤になる

閾値を現実よりも厳しく設定すると、ほとんどのPRでサイズチェックが失敗する状態になる。すると開発者は「このチェックはいつも失敗するから無視しよう」という態度になり、チェックが形骸化する。

> **対策**: 最初は「明らかにおかしい増加だけ止める」ゆるい閾値から始める。全員が「このチェックが通れば大丈夫」と信頼できる状態を維持することが重要。

### 測定対象が不適切

以下のようなミスで、計測値が実態と合わなくなる。

- **dev ビルドで計測**: 開発用ビルドには、デバッグ情報やソースマップが含まれるため、本番ビルドより大幅に大きい
- **sourcemap を含めて計測**: ソースマップ（`.map` ファイル）はデバッグ用で、ユーザーにはダウンロードされない
- **計測条件が毎回違う**: ある時は gzip あり、ある時は gzip なしで計測すると、比較にならない

> **対策**: 本番ビルド（`pnpm build`）の出力に対して、常に同じ条件（gzip あり / brotli あり）で計測する。

### 原因が追えない

「バンドルサイズが 50KB 増えた」とわかっても、どのパッケージ / どのコードが原因かわからないと対処できない。

**対策**: バンドル分析ツールを使って、何がサイズを占めているか可視化する。

```bash
# Vite の場合、rollup-plugin-visualizer などで可視化
# webpack の場合、webpack-bundle-analyzer
```

> バンドルの中身を可視化すると「このライブラリが全体の 30% を占めている」「使っていないモジュールが含まれている」といった発見ができる。

## 運用のコツ（回帰を減らす）

### 理由の明文化

予算を超えるPRが出た場合、PRテンプレートで以下を問う。

- **なぜこの増加が必要か？**: 新機能に不可欠なライブラリなのか
- **代替案はないか？**: より軽量な代替ライブラリはないか、自前で実装したほうが小さくならないか

### 大きい依存の監視

以下のカテゴリのライブラリは特にサイズが大きくなりやすいため、追加時には特に注意する。

| カテゴリ | 例 | サイズの目安 |
|---|---|---|
| 日付ライブラリ | moment.js, date-fns | 20KB〜70KB（gzip） |
| チャート | chart.js, recharts, D3 | 40KB〜200KB（gzip） |
| リッチエディタ | TipTap, ProseMirror, Quill | 50KB〜150KB（gzip） |
| Markdownパーサー | marked, remark | 10KB〜30KB（gzip） |
| UIフレームワーク | MUI, Ant Design | 50KB〜300KB（gzip） |

> **1つのライブラリ追加でバンドルが倍増することもある**。追加前に「このライブラリのサイズはどのくらいか」を [bundlephobia.com](https://bundlephobia.com) などで確認する習慣をつける。

### コード分割（遅延ロード）

重要でない画面や機能は、ユーザーが実際にアクセスしたときに初めてコードを読み込む「遅延ロード」に寄せる。

```typescript
// ❌ すべてのページのコードが初回に読み込まれる
import AdminPage from "./pages/Admin";

// ✅ 管理画面は、アクセスしたときに初めて読み込まれる
const AdminPage = lazy(() => import("./pages/Admin"));
```

> これにより、トップページを表示するために必要なコードだけが初回にダウンロードされ、管理画面のコードは管理者がアクセスするまでダウンロードされない。

## CI での位置づけ（例）

```
PR:
  → pnpm build → size-limit で各エントリポイントのサイズを計測
  → 予算を超えたら失敗（ブロック）
  → PRコメントにサイズの増減を表示

定期（weekly）:
  → バンドルサイズの推移グラフを更新
  → 急増しているエントリポイントがあればアラート
```
