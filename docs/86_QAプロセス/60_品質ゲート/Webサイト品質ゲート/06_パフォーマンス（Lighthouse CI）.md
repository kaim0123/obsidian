# パフォーマンス（Lighthouse CI）

## そもそも「パフォーマンス品質ゲート」とは？

Webサイトの表示速度や操作の快適さを数値で計測し、一定の基準を下回ったら自動的にアラートを出す仕組みのこと。

ユーザーは「表示が遅い」と感じると離脱する。Googleの調査では、ページの読み込み時間が1秒から3秒に増えると直帰率が32%増加するとされている。パフォーマンスはユーザー体験に直結するため、「知らないうちに遅くなっていた」を防ぐことが重要。

## 目的

- 体感速度・操作性・安定性に直結する指標（Core Web Vitals 等）を継続的に監視し、**パフォーマンスが悪化する回帰を防ぐ**
- 「ちょっとした機能追加」「ライブラリの追加」が積み重なって、気づいたときにはサイト全体が重くなっている──という事態を、PR（プルリクエスト）やCIの段階で早期に検出する

> **Lighthouse とは？**
> Google が開発した Web ページの品質監査ツール。パフォーマンス、アクセシビリティ、ベストプラクティス、SEO を自動的にスコアリングする。Chrome DevTools に内蔵されているほか、コマンドラインからも実行できる。

> **Lighthouse CI（LHCI）とは？**
> Lighthouse の計測をCIパイプラインに組み込むためのツール。計測結果を保存・比較し、スコアが閾値（しきい値）を下回ったらCIを失敗させることができる。「PR単位でどれだけ悪化/改善したか」を追跡できる。

## 何をチェックするか（代表例）

### Core Web Vitals（コアウェブバイタル）

Google が「ユーザー体験の核」として定義した3つの指標。検索順位にも影響する。

#### LCP（Largest Contentful Paint）

ページの中で **最も大きなコンテンツ（メイン画像、見出しテキストなど）が表示されるまでの時間**。ユーザーが「ページが表示された」と感じるタイミングに相当する。

- **良好**: 2.5秒以内
- **改善が必要**: 2.5〜4.0秒
- **不良**: 4.0秒超

> 原因の例: 巨大な画像、遅いサーバー応答、レンダリングをブロックするCSS/JS

#### INP（Interaction to Next Paint）

ユーザーがクリックやタップなどの操作をしてから、**画面が反応するまでの遅延時間**。「ボタンを押したのに何も起きない」と感じさせないための指標。

- **良好**: 200ミリ秒以内
- **改善が必要**: 200〜500ミリ秒
- **不良**: 500ミリ秒超

> 原因の例: 重い JavaScript の実行がメインスレッドをブロックしている

#### CLS（Cumulative Layout Shift）

ページの読み込み中に **要素が予期せずズレる量** の累計値。「読もうとしていたテキストが突然下にずれて、間違ったリンクを押してしまった」という体験を測定する指標。

- **良好**: 0.1 以下
- **改善が必要**: 0.1〜0.25
- **不良**: 0.25 超

> 原因の例: サイズ未指定の画像、遅延読み込みされる広告、動的に挿入されるバナー

### 補助指標

Core Web Vitals だけでなく、以下の指標も有用。

- **TTFB（Time to First Byte）**: サーバーが最初の応答を返すまでの時間。サーバー側の性能指標
- **Total Blocking Time（TBT）**: メインスレッドが50ミリ秒以上ブロックされた時間の合計。INP と相関が高い
- **画像最適化**: 画像が適切なフォーマット（WebP/AVIF）・サイズで配信されているか
- **未使用 JS**: 読み込んだが使われていない JavaScript の量
- **キャッシュ設定**: 静的ファイルに適切なキャッシュヘッダーが設定されているか

### ベストプラクティス

- **圧縮**: テキストリソース（HTML/CSS/JS）がgzip/brotliで圧縮されているか
- **HTTP/2**: 高速な通信プロトコルが使われているか
- **リソースヒント**: `preload` / `prefetch` / `preconnect` が適切に使われているか

## 運用のポイント（現実的な設計）

### 計測環境を固定する

パフォーマンス計測は環境によって値がブレる。ローカルの高性能マシンとCIの共有ランナーでは、同じページでもスコアが大きく異なる。

- 可能なら **同一のCIランナー/同一の条件** で毎回計測する
- または、パフォーマンス計測専用の環境（専用サーバー、専用コンテナ）で実行する
- 「絶対値」よりも「前回からの差分」に注目するほうがブレに強い

### 対象ページを絞る

すべてのページを毎回計測するのは現実的でない。事業影響が大きいページから優先する。

- トップページ（最もアクセスが多い）
- 検索結果ページ（ユーザーの目的達成に直結）
- 商品詳細 / 記事詳細（コンテンツの消費ページ）
- 購入 / 申込みフォーム（コンバージョンに直結）

### 閾値は段階的に導入する

1. まずは「大きな悪化だけ止める」ゆるい閾値を設定する（例: LCP が 5 秒を超えたら失敗）
2. 現状のスコアを把握し、改善に取り組む
3. 改善が進んだら閾値を下げ、徐々に厳格にする

> いきなり厳しい閾値を設定すると、既存ページが軒並み失敗して形骸化する。

### 差分を見る

合否だけでなく、「PRでどの指標がどれだけ変化したか」を追えるようにする。

- 「JS が 50KB 増えた → LCP が 0.3 秒悪化」のように因果を追える
- LHCI の `upload` 機能で計測結果をサーバーに保存し、ダッシュボードで推移を確認できる

## 失敗しがちなポイント

### 計測がブレる

同じページを同じ条件で計測しても、ネットワーク遅延やCPU負荷、バックエンドの応答時間によって値が揺れる。

**対策**:
- **複数回計測して中央値を採用する**（LHCI は `--numberOfRuns` で回数を指定できる）
- 対象ページを絞り込み、計測ノイズを減らす
- バックエンドが安定している環境（ステージング環境やモック）で計測する

### ログイン後のページが計測できない

ログインが必要なページは、Lighthouse を単純に実行しても到達できない。

**対策**:
- 事前にログイン処理を行い、Cookie を注入してから Lighthouse を実行する
- LHCI の `puppeteerScript` を使って、ログインフローをスクリプト化する

## CI での位置づけ（例）

```
PR:
  → 主要ページ（3〜5ページ）を対象に Lighthouse CI を実行
  → 閾値を下回ったら警告 or 失敗

nightly / weekly:
  → 全対象ページを計測し、スコアの推移をダッシュボードで確認
  → 悪化傾向があれば改善タスクを起票
```
