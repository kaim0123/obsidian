# E2Eテスト（Playwright）

## そもそも「E2Eテスト」とは？

E2E（End-to-End）テストとは、**実際のユーザーと同じようにブラウザを操作して**、アプリケーション全体が正しく動くかを検証するテストのこと。

ユニットテストが「部品の検査」だとすれば、E2Eテストは「完成品を実際に使ってみる検査」。ログイン画面にIDとパスワードを入力し、ログインボタンを押し、ダッシュボードが表示されるか──という一連の流れを、本物のブラウザ上で自動的に再現して確認する。

## 目的

- 実際のユーザーの操作動線（画面遷移・入力・送信・表示）を **すべてのシステムが連携した状態で** 検証し、致命的な回帰バグを防ぐ。
- 「個々のコンポーネントは正常なのに、組み合わせると壊れる」という種類の不具合を拾う。
  - 例: 認証トークンの受け渡し、APIのレスポンス形式の変更、ルーティング設定の不整合、Cookie / LocalStorage の挙動、権限による画面出し分け

> **Playwright とは？**
> Microsoft が開発したE2Eテストフレームワーク。Chromium（Chrome）、Firefox、WebKit（Safari）の3つのブラウザエンジンを1つのツールで自動操作できる。テスト実行の安定性が高く、トレース（実行記録）やスクリーンショットの保存も簡単にできる。

## 何をテストするか（最小セットの考え方）

E2Eテストは実行に時間がかかるため、すべての機能をテストするのではなく、**「壊れたら一番困る機能」** から優先的にテストを書く。

### 1. クリティカルパス（最優先）

事業に直接影響する最重要の操作フロー。これが壊れると売上や信頼に直結する。

- **ログイン / ログアウト**: 認証が壊れるとすべての機能が使えなくなる
- **購入 / 申込み**: ECサイトの購入フロー、サービスの申込みフローなど
- **投稿 / 保存**: コンテンツ投稿、データ保存が正しく完了するか
- **検索**: 検索結果が正しく表示されるか（検索が壊れるとユーザーが目的のページにたどり着けない）

### 2. 主要ブラウザ / デバイス

ユーザーが実際に使う環境でテストする。

- **Chromium**（Chrome / Edge）: 最もシェアが大きい
- **WebKit**（Safari）: iOS / macOS ユーザー向け。レンダリングの違いでレイアウトが崩れることがある
- **モバイル相当**: Playwright ではビューポートサイズやユーザーエージェントを指定して、モバイル環境をシミュレートできる

> すべてのブラウザ・デバイスの組み合わせをテストする必要はない。アクセス解析を見て、ユーザーが実際に使っている環境に絞る。

### 3. 権限・ロール

ユーザーの権限によって見える画面や操作できる機能が異なる場合、それぞれの権限で正しく動くかを確認する。

- **管理者**: すべての機能にアクセスできる
- **一般ユーザー**: 管理画面にアクセスできない、他人のデータを編集できない
- **未ログインユーザー**: 公開ページのみ閲覧可能、ログイン必須ページにアクセスするとリダイレクトされる

### 4. 失敗系

正常系だけでなく、エラーや異常が起きたときの挙動もテストする。

- **バリデーションエラー**: 必須項目を空にして送信したら、エラーメッセージが表示されるか
- **APIエラー**: サーバーが500エラーを返したときに、適切なエラー画面が表示されるか
- **タイムアウト**: 通信が遅延したときにユーザーが困らない表示になっているか
- **空結果**: 検索結果が0件のときに「結果がありません」と表示されるか

## 安定運用のためのポイント

### テストID（data-testid）を使う

E2Eテストでは、画面上の要素（ボタン、入力欄など）を「どうやって見つけるか」が重要。CSSクラス名やHTML構造に依存すると、デザイン変更のたびにテストが壊れる。

```html
<!-- テスト用のIDを付与する -->
<button data-testid="submit-button">送信</button>
```

```typescript
// テストコードではこのIDで要素を特定する
await page.getByTestId("submit-button").click();
```

> **なぜ data-testid？**
> CSSクラス（`.btn-primary`）はデザイン変更で変わりやすい。テキスト（`"送信"`）は多言語対応で変わりうる。`data-testid` はテスト専用の属性なので、デザインやテキストの変更に影響されない。

### 待機の設計

E2Eテストで最も不安定さを生む原因が「タイミング」の問題。画面の描画やAPIの応答を待たずに次の操作をすると、テストが失敗する。

```typescript
// ❌ 悪い例: 決まった秒数だけ待つ（遅いと足りず、速いと無駄）
await page.waitForTimeout(3000);

// ✅ 良い例: 特定の条件が満たされるまで待つ
await page.waitForSelector('[data-testid="result-list"]');
await page.waitForURL('/dashboard');
await page.waitForResponse(resp => resp.url().includes('/api/data'));
```

### 状態の初期化

テストが毎回同じ結果になるためには、テスト開始時のアプリケーション状態が毎回同じである必要がある。

- **テストデータの準備**: テスト専用のデータベースやシードデータを用意する
- **ログイン状態の再利用**: `storageState` を使って、ログイン済みの Cookie / セッションを保存し、テストごとに再利用する（毎回ログイン操作をする必要がなくなり、テストが速くなる）

```typescript
// ログイン状態を保存
await page.context().storageState({ path: "auth.json" });

// 別のテストでログイン状態を復元
const context = await browser.newContext({ storageState: "auth.json" });
```

### 並列実行

テストを並列で実行すると速度は上がるが、テスト同士がデータを共有していると競合が起きる。

- **悪い例**: テストAとテストBが同じユーザーアカウントを使って同時にログインし、片方のセッションが上書きされる
- **対策**: テストごとに独立したテストデータ（別のユーザーアカウント、別のレコード）を使う

## 失敗しがちなポイント

### フレーク（Flaky Test：たまに落ちるテスト）

実行するたびに成功したり失敗したりする不安定なテスト。E2Eテスト最大の敵。

- **ネットワーク遅延**: API の応答が普段より遅いと、タイムアウトで失敗する
- **アニメーション**: 要素がアニメーション中でクリックできない
- **テストデータの競合**: 並列テストが同じデータを操作して衝突する
- **環境の違い**: ローカルでは通るがCIでは遅いマシンで実行されて失敗する

> **フレークが危険な理由**: テストが「たまに落ちる」ことが当たり前になると、本当のバグで落ちたときにも「またフレークだろう」と無視されるようになる。フレークは発見したらすぐに修正するか、一時的に無効化して原因調査する。

### テスト範囲を増やしすぎる

E2Eテストは1件あたりの実行時間が長い（数秒〜数十秒）ため、数を増やすとCIの実行時間が急激に伸びる。

> **原則**: まずは **少数の高価値テストを堅牢に** 作る。安定して動作することを確認してから、価値の高い順にテストを追加していく。100個の不安定なテストより、10個の安定したテストのほうが価値がある。

## CI での位置づけ（例）

```
PR（プルリクエスト時）:
  → 短時間のスモークテスト（最重要フローだけ、5〜10件程度）

nightly（毎晩の定期実行）:
  → 広範囲の回帰テスト（全フロー、全ブラウザ、全デバイス）
```

- PR では開発者が素早くフィードバックを得られるように、最小限のテストだけ実行する
- 包括的なテストは夜間に実行し、翌朝結果を確認する
- 失敗時に原因を追えるよう、**スクリーンショット・動画・トレース**（操作の記録）を保存する

> **トレースとは？**
> Playwright のトレースビューアーは、テストの実行をステップごとに再現できるツール。どの時点でどの要素をクリックし、そのときの画面がどう表示されていたかを、動画のように確認できる。デバッグに非常に有用。
