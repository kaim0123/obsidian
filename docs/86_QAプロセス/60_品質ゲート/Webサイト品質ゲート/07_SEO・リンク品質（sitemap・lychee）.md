# SEO・リンク品質（sitemap・lychee）

## そもそもなぜ「SEO・リンク品質」を品質ゲートにするのか？

Webサイトの価値は「作ること」だけでなく、「ユーザーに見つけてもらえること」にもある。検索エンジン（Google など）は、サイトの構造やリンクの健全性を読み取って検索順位を決めている。

リニューアルやURLの変更で「昨日まで検索1位だったページが404になっていた」「重要なページが検索結果から消えていた」という事故は、売上や集客に直結する大きな損失になる。こうした事故を自動的に検知するのが、このゲートの役割。

## 目的

- 検索流入を維持するために、**クロール可能性**（検索エンジンがサイトを正しく巡回できるか）と **リンク健全性**（リンク切れがないか）を継続的に担保する
- リニューアルやルーティング変更で起きがちな「404（ページが見つからない）」「リンク切れ」「意図しない noindex（検索エンジンに"このページを索引しないで"と伝えてしまう）」などを早期に検知する

## 何をチェックするか（代表例）

### 1. sitemap（サイトマップ）

サイトマップとは、Webサイトに含まれるページのURLを一覧にしたXMLファイル（`sitemap.xml`）のこと。検索エンジンはこのファイルを読み取って「このサイトにはどんなページがあるか」を把握する。

チェック項目:

- **生成されているか**: ビルド後に `sitemap.xml` が存在するか確認する（ビルド設定のミスで生成されないことがある）
- **URLが妥当か**:
  - 本番ドメイン（`https://example.com/...`）になっているか（ステージング用のURLが混入していないか）
  - インデックスすべきでないURL（管理画面、テストページなど）が含まれていないか
  - 同じページが重複して掲載されていないか
- **`lastmod`（最終更新日）が正しいか**: 検索エンジンは `lastmod` を参考にクロール頻度を調整するため、実態と合っていないと非効率なクロールになる

### 2. リンク切れ（lychee 等でチェック）

リンク切れとは、クリックしたリンク先のページが存在しない（404）、またはサーバーエラー（500）になっている状態のこと。ユーザー体験を損なうだけでなく、SEO評価にもマイナスの影響がある。

> **lychee とは？**
> Rust で書かれた高速なリンクチェッカー。Webサイトやドキュメント内のリンクを巡回し、404やタイムアウトなどの問題を検出する。HTMLファイルだけでなく、Markdown や README のリンクもチェックできる。

チェック項目:

- **内部リンクの 404 / 500**: サイト内のリンクが壊れていないか（最優先。自分たちで修正できる）
- **外部リンクの死活**: 外部サイトへのリンクが生きているか（外部サイトの都合で壊れることがある）
- **README / ドキュメントの参照切れ**: ソースコード内のドキュメントに書かれたURLが有効か

### 3. メタ / robots（追加の観点）

検索エンジンへの指示が正しいかどうか。

- **`robots.txt`**: サイトのルートに配置するファイルで、検索エンジンに「クロールしてよいページ」「クロールしないでほしいページ」を指示する。このファイルが正しく設定されているか
- **`canonical`（正規URL）**: 同じ内容のページが複数のURLで存在する場合、「このURLが本物です」と検索エンジンに伝えるための指定。正しく設定されていないと、検索エンジンがどのURLをインデックスすべきか混乱する
- **`noindex` の付け忘れ / 付けすぎ**:
  - **付け忘れ**: ステージング環境や管理画面が検索結果に表示されてしまう（セキュリティリスク）
  - **付けすぎ**: 本番の重要なページが検索結果から消えてしまう（集客ダメージ）

```html
<!-- このページを検索結果に表示しないでほしい場合 -->
<meta name="robots" content="noindex, nofollow" />

<!-- 正規URLを指定する場合 -->
<link rel="canonical" href="https://example.com/products/123" />
```

## 運用のポイント

### 外部リンクは不安定

外部サイトへのリンクは、相手サイトのダウンタイムやURL変更によって、自分たちのコード変更と無関係に壊れることがある。PR の必須チェックに含めると、外部サイトの一時障害で自分たちのマージがブロックされるノイズが発生する。

**対策**:
- **PRでは内部リンクのみチェック**（自分たちのコード変更で壊れたリンクを検出する）
- **外部リンクは nightly（定期実行）でチェック**（壊れていたら翌朝修正する）
- 特定のURLを除外するための `allowlist`（許可リスト）/ `denylist`（拒否リスト）を用意する

### sitemap の対象ルールを決める

「どのページをインデックス対象にするか / しないか」をチームで合意し、サイトマップの生成ロジックに反映する。

- **インデックスすべきページ**: 商品詳細、ブログ記事、ランディングページなど
- **インデックスすべきでないページ**: 管理画面、テストページ、検索結果ページ（パラメータ付き）、ステージング環境

### リダイレクトも品質

ページが移動した場合、旧URLが404を返すのではなく、新URLへのリダイレクト（301 / 308）を設定する。

- **301 リダイレクト**: 「このページは恒久的に移動しました」（検索エンジンの評価が新URLに引き継がれる）
- **308 リダイレクト**: 301 と同様だが、HTTPメソッドを変更しない（POSTリクエストのリダイレクトなどで使う）

> リダイレクト先のURLが正しいかどうかもチェック対象にする。リダイレクトしたけど、その先がまた404──というケースもある（リダイレクトチェーンの破綻）。

## 失敗しがちなポイント

### 環境差

ステージング環境用のドメイン（`staging.example.com`）がサイトマップに混入する。ビルド時の環境変数（`SITE_URL` など）の設定ミスが原因。

> **対策**: CIのビルド設定で本番ドメインが正しく設定されているか確認するテストを入れる。

### 動的ページの取りこぼし

SSG（静的サイト生成）やSSR（サーバーサイドレンダリング）で動的に生成されるページが、サイトマップの生成ロジックから漏れることがある。逆に、下書きや非公開ページがサイトマップに含まれてしまうケースも。

> **対策**: サイトマップに含まれるURL数を監視し、大きく増減したらアラートを出す。定期的にサイトマップの内容をレビューする。

### 認証が必要なページ

ログインが必要なページは、リンクチェッカーやクローラーがアクセスできずに403/401エラーとして誤検知される。

> **対策**: 認証が必要なURLは除外リストに入れるか、認証済みの状態でチェッカーを実行する。

## CI での位置づけ（例）

```
ビルド後:
  → sitemap.xml が存在するか確認
  → sitemap.xml 内のURLが本番ドメインであるか確認

PR:
  → 内部リンクのリンク切れチェック（lychee --exclude-external）

nightly:
  → 内部 + 外部リンクの包括チェック
  → sitemap のURL数の増減監視
```
