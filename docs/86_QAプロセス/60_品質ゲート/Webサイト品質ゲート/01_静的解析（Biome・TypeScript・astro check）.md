# 静的解析（Biome・TypeScript・astro check）

## そもそも「静的解析」とは？

静的解析とは、**コードを実行せずに**ソースコードを読み取って問題を見つける手法のこと。
人間がコードを目視でレビューする前に、機械（ツール）が自動的に「このコードおかしくない？」と指摘してくれる仕組みである。

たとえば日本語の文章で言えば、文法チェッカーが「てにをは」の誤りや誤字脱字を指摘してくれるようなもの。
文章の内容（ロジック）が正しいかどうかは判断できないが、少なくとも「文法的に壊れた文章」は事前に防げる。

## 目的

- 型の不整合、構文ミス、コーディングスタイルの逸脱などを **コードを実行する前に検知** し、手戻りと回帰バグを減らす。
- コードレビューで「インデントがずれている」「変数名の命名規則が違う」といった機械的な論点を排除し、レビューを **仕様・設計・リスク** といった本質的な議論に集中させる。

> **「回帰バグ」とは？**
> 以前は正しく動いていた機能が、別の変更をきっかけに壊れてしまうこと。静的解析は、こうした意図しない破壊を早い段階で食い止める役割がある。

## 何をチェックするか（代表例）

### 1. フォーマット / リンティング（Biome など）

**フォーマット**はコードの見た目の統一（インデント、改行、セミコロンの有無など）を自動的に整えること。**リンティング**はコードの中にある潜在的な問題（未使用の変数、危険な記法、非推奨APIの使用など）を検出すること。

- **未使用変数の検出**: 宣言したのに一度も使っていない変数は、消し忘れかバグの兆候であることが多い
- **危険な記法の警告**: たとえば `==`（型を無視した比較）ではなく `===`（厳密比較）を使うべき、など
- **コードスタイルの統一**: チーム全員が同じ書き方をすることで、誰が書いたコードでも読みやすくなる

> **Biome とは？**
> JavaScript / TypeScript のフォーマットとリンティングを一つのツールで高速に行えるツール。以前は ESLint + Prettier という2つのツールを組み合わせるのが主流だったが、Biome はそれを1つにまとめ、設定の煩雑さと実行速度の問題を解消している。

### 2. 型検査（TypeScript `tsc`）

TypeScript は JavaScript に「型」という安全装置を追加した言語。型検査は「この変数には数値が入るはずなのに、文字列を渡している」といった矛盾を、コードを実行する前に見つけてくれる。

- **破壊的変更の検出**: 関数の引数や戻り値の型が変わったとき、呼び出し側が追従できていなければエラーになる
- **null / undefined の安全性**: 「この変数は null かもしれないのに、null チェックなしでプロパティにアクセスしている」を検出する

> **なぜ型検査が重要なのか？**
> JavaScript だけでは、変数に何が入っているかは実行してみないとわからない。TypeScript の型検査を通すことで、「実行時にクラッシュする可能性がある箇所」を事前に洗い出せる。

### 3. フレームワーク固有チェック（Astro `astro check`）

Astro のようなフレームワークには、そのフレームワーク特有のルールや構文がある。`astro check` は、Astro コンポーネント内の型チェックやコンテンツコレクションの整合性など、TypeScript 単体ではカバーしきれないフレームワーク固有の問題を検出する。

- **ルーティングの整合性**: ファイルベースルーティングで、ページが正しく認識されるか
- **コンテンツの型チェック**: Markdown/MDX のフロントマターが定義したスキーマと一致しているか

## 失敗しがちなポイント

### ローカルでは通るのに CI で落ちる

開発者のPCでは問題なく通るのに、CI（自動ビルド・テスト環境）では失敗するケース。よくある原因は以下。

- **Node.js / pnpm のバージョン差**: ローカルが Node 20 で CI が Node 18 だと、使える構文や動作が異なる
- **設定ファイルの差分**: `.biomerc` や `tsconfig.json` がローカルだけ変更されている
- **キャッシュの違い**: ローカルでは古いキャッシュが残っていて通ってしまうが、CI はクリーンな状態で実行される

> **対策**: CI と同じ Node バージョンをローカルでも使う（`.node-version` や `.nvmrc` で固定する）。コミット前に `pnpm lint && pnpm typecheck` を手元で実行する習慣をつける。

### ルールが厳しすぎて形骸化する

最初からすべてのルールを有効にすると、大量のエラーが出て「どうせ全部直せないから無視しよう」という空気になりがち。

> **対策**: 初期は「放置すると本当に危険なルール」（未使用変数、型エラー、セキュリティ上の問題など）だけを必須にし、慣れてきたら段階的にルールを追加する。

### 型エラーを「警告」にしてしまう

型エラーを「エラー（ブロック）」ではなく「警告（通過可能）」にすると、チーム全体が警告を無視する習慣がつく。気づいたときには修正すべき型エラーが数百件に膨れ上がり、修正コストが跳ね上がる。

> **対策**: 型エラーは最初から「CI をブロックする」設定にする。既存コードに大量の型エラーがある場合は、`// @ts-expect-error` で一時的に抑制しつつ、計画的に解消する。

## 導入の考え方（運用設計）

### 必須ゲート（PRで必ず通す）

以下は PR（プルリクエスト：コードの変更を本番に取り込む前のレビュー段階）で必ず通過させるべき項目。

- **format**: コードの見た目が統一されているか
- **lint**: 危険な記法や非推奨パターンがないか
- **typecheck**: 型の整合性が保たれているか

これらが通らない PR はマージ（取り込み）できないように設定する。

### 段階的導入

既存のコードが大量にある場合、いきなり全体にルールを適用すると修正量が膨大になる。

1. まずは **差分だけ厳格にする**（`lint-staged` 等を使い、変更したファイルだけチェックする）
2. 新規コードは最初から厳格なルールに従う
3. 既存コードは計画を立てて徐々にルール適合させる
4. 最終的に全体に厳格なルールを適用する

### 品質の定義を合意する

「どのルール違反がマージをブロックするか」をチームで事前に合意しておく。
これがないと、「このルールは無視していいの？」という判断が個人に委ねられ、基準がブレる。

## CI での位置づけ（例）

```
依存インストール → lint → typecheck → check → ユニットテスト → E2Eテスト
               ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
               静的解析はテストより先に実行する
```

- `lint` / `typecheck` / `check` をそれぞれ **別のジョブ** にする（失敗したとき、どこで落ちたかすぐわかる）
- 依存パッケージのインストール後、テストよりも **先に** 走らせる（静的解析は実行が速いので、問題があれば数秒で落ちる。テストを待つ前に気づける）

> **考え方**: 「早く落ちるほど安い」。静的解析で10秒で気づけるミスを、E2Eテストで5分かけて見つけるのは非効率。
