# 依存関係セキュリティ（Dependabot・pnpm audit）

## そもそも「依存関係のセキュリティ」とは？

現代のWebアプリケーションは、多数の外部パッケージ（ライブラリ）に依存している。たとえばReactアプリの `node_modules` フォルダには数百〜数千のパッケージが入っている。これらのパッケージに **セキュリティ上の脆弱性（攻撃に悪用できる弱点）** が発見されることがある。

たとえるなら、自分の家（アプリ）に使っている建材（パッケージ）にリコール（脆弱性の報告）が出たようなもの。自分のコードには問題がなくても、使っているパッケージに穴があれば、アプリ全体のセキュリティが脅かされる。

この品質ゲートは、「使っているパッケージに既知の脆弱性がないか」を自動的にチェックし、問題があれば早期に対処するための仕組み。

## 目的

- 依存パッケージに含まれる **既知の脆弱性** を早期に検知し、影響が小さいうちに修正する
- 「気づいたら深刻な脆弱性を何ヶ月も抱えていた」という事態を防ぎ、対応を計画的にする

## 何をチェックするか

### 1. 脆弱性スキャン（pnpm audit）

`pnpm audit` は、プロジェクトが依存しているすべてのパッケージを、既知の脆弱性データベースと照合して、問題があるパッケージを報告するコマンド。

```bash
# 実行すると脆弱性の一覧が表示される
pnpm audit

# JSON形式で出力（CIでの自動判定に便利）
pnpm audit --json
```

報告される情報:
- **パッケージ名**: どのパッケージに問題があるか
- **脆弱性の内容**: どんな攻撃に利用される可能性があるか（XSS、RCE、プロトタイプ汚染など）
- **深刻度（severity）**: critical / high / moderate / low の4段階
- **修正バージョン**: 脆弱性が修正されたバージョン（存在する場合）
- **依存経路**: 直接依存か、間接依存（依存の依存）か

> **直接依存と間接依存**
> `package.json` に直接書いているパッケージが「直接依存」。そのパッケージがさらに使っているパッケージが「間接依存」。脆弱性は間接依存で見つかることが多く、自分では直接制御しにくいため対応が複雑になることがある。

### 2. 更新提案（Dependabot / Renovate）

パッケージの更新を自動的にPR（プルリクエスト）として提案してくれるツール。

> **Dependabot とは？**
> GitHub が提供する依存パッケージの自動更新ツール。セキュリティアップデート（脆弱性の修正版への更新）と定期アップデート（最新版への定期的な更新）の2種類のPRを自動作成する。

> **Renovate とは？**
> Dependabot の代替ツール。より細かい更新戦略の設定が可能。グループ化（複数のパッケージ更新を1つのPRにまとめる）やスケジュール設定など、柔軟な運用ができる。

### 3. ポリシー（判断基準）の設定

チームで以下を合意しておく。

- **どの深刻度以上をブロックするか**: 例えば「high / critical はマージ不可」「moderate 以下は定期レポートで追う」
- **対象範囲**: 本番で使う依存（`dependencies`）だけ止めるか、開発時のみ使う依存（`devDependencies`）も止めるか

> **devDependencies の脆弱性は無視していいのか？**
> 一般的に、本番環境に含まれない `devDependencies` のリスクは低い。ただし、ビルド時に悪意のあるコードが注入されるケース（サプライチェーン攻撃）もあるため、完全に無視するのではなく、深刻度の高いものは確認する。

## 運用のポイント

### 自動PRを「流さない」

Dependabot や Renovate が自動で作るPRを、内容を確認せずにマージするのは危険。パッケージの更新には破壊的変更が含まれる可能性がある。

**安全な取り込みフロー**:
1. 自動PRが作成される
2. CI（ユニットテスト / E2Eテスト）が通るか確認する
3. `CHANGELOG` や更新内容を確認する
4. 問題なければマージする

### 更新の粒度は小さく頻繁に

パッケージの更新を溜めると、以下の問題が起きる。

- 一度に多くのパッケージが更新され、何かが壊れたときに原因の特定が困難になる
- バージョン差が大きくなり、移行手順が複雑になる
- 「差分が大きすぎて怖くてマージできない」状態に陥る

> **原則**: 小さな更新を頻繁に取り込む。1回の更新で壊れたら、その1パッケージが原因だとすぐわかる。

### 破壊的変更（メジャーアップデート）の扱い

パッケージのバージョンが `1.x → 2.x`（メジャーバージョンアップ）になる場合、API の変更や非互換が含まれることが多い。

- 別の作業ブランチで計画的に対応する
- 移行手順を整理し、影響範囲を洗い出す
- 可能であれば、パッケージの公式マイグレーションガイドに従う

### 例外管理（すぐに更新できない場合）

脆弱性が見つかっても、すぐに更新できない場合がある（互換性の問題、大規模な修正が必要など）。その場合は以下を記録する。

- **理由**: なぜ今は更新できないのか
- **期限**: いつまでに対応するか
- **影響範囲**: この脆弱性が実際に悪用される条件は何か
- **代替策**: WAF（Webアプリケーションファイアウォール）でのブロック、該当機能の一時停止など

## 失敗しがちなポイント

### 自動PRの放置

Dependabot / Renovate のPRを放置し続けると、以下の悪循環に陥る。

1. PRが溜まる
2. 古いPRが最新のコードとコンフリクト（衝突）する
3. コンフリクト解消が面倒で、さらに放置する
4. パッケージのバージョン差が大きくなり、更新が怖くなる
5. ますます放置する

> **対策**: 週に1回、依存更新PRを処理する時間をチームで確保する。または、Renovate の自動マージ機能を使って、テストが通るマイナーアップデートは自動で取り込む。

### ノイズが多すぎる

`devDependencies` の影響度が低い脆弱性まで毎回報告されると、チームが「またか」とアラートを無視するようになる（オオカミ少年問題）。

**対策**:
- PRでブロックするのは「high / critical のみ」に絞る
- moderate 以下は定期レポート（週次/月次）で確認する
- 影響度が低い `devDependencies` の脆弱性は、nightly チェックに寄せる

## CI での位置づけ（例）

```
PR:
  → pnpm audit で high / critical があれば失敗（ブロック）
  → moderate 以下は警告のみ（ブロックしない）

定期（weekly / nightly）:
  → 全依存の監査レポートを生成
  → Dependabot / Renovate のPR棚卸し
```
