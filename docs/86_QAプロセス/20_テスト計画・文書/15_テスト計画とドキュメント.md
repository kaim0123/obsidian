# テスト計画とドキュメント

テストを**計画的に・抜け漏れなく・再現可能に**行うために、テスト計画やテスト設計の成果物を文書化します。QAエンジニアは、プロジェクトの規模やフェーズに応じて、必要なドキュメントを用意し、関係者と認識を揃えることが重要です。

---

## 1. テスト戦略（Test Strategy）とテスト計画（Test Plan）

### 1.1 テスト戦略

- **テスト戦略**: プロジェクトや製品全体で「どのような方針でテストするか」を定めたもの。対象範囲・テストレベル・種類・自動化の方針・品質基準・リスクへの対応方針などを含む。
- 組織やプロダクトで共通のテスト方針をまとめ、個別プロジェクトではそれをベースにカスタマイズすることが多い。

### 1.2 テスト計画（Test Plan）

- **テスト計画**: 特定のリリース・スプリント・プロジェクト向けに、「何を・いつ・誰が・どのように・どの基準で」テストするかを記述した文書。
- テスト戦略を具体化し、スケジュール・リソース・環境・成果物・完了基準を明示する。

### 1.3 テスト計画に含めるとよい項目（例）

| 項目 | 内容 |
|------|------|
| **目的・スコープ** | このテストで何を検証するか、対象機能・対象外 |
| **テストレベル** | 単体・結合・システム・受入のどれをどの程度行うか |
| **テストの種類** | 機能・性能・セキュリティ・ユーザビリティ・アクセシビリティ等、どの種類を実施するか |
| **リスクと対策** | リスクベースで優先度をつけたテストの考え方（[[04_探索的テストとリスクベーステスト]]） |
| **スケジュール** | テスト開始・終了、マイルストーン、他工程との関係 |
| **リソース・役割** | 担当者、役割分担 |
| **テスト環境・データ** | 使用する環境、データの準備方針 |
| **成果物** | テストケース一覧、バグレポート、テスト結果レポートなど |
| **完了基準（出口基準）** | いつテストを終了とするか（例：クリティカル・ブロッカー 0 件、〇〇% カバーなど） |

## 2. テスト設計とテストケース

### 2.1 テスト設計

- **テスト設計**: 仕様・要件・リスクを元に、「どの観点で・どの条件で」テストするかを決める作業。
- 同値分割・境界値・デシジョンテーブル・ペアワイズ・状態遷移（[[06_同値分割法]]〜[[10_状態推移テスト]]）などの技法を使って、テスト観点やテストケースを導出する。
- テスト設計の結果は、**テスト設計書**や**テスト観点一覧**として残すと、レビューや回帰テストで再利用しやすい。

### 2.2 テストケース

- **テストケース**: 1 件 1 件のテストの「手順・データ・期待結果」を記述したもの。
- 項目の例：テストケース ID、対象機能・要件、前提条件、手順、テストデータ、期待結果、優先度、実施結果。
- テストケースは、Excel・スプレッドシート・テスト管理ツール（TestRail、Zephyr、Jira のテスト機能など）で管理することが多い。

### 2.3 テスト設計とテストケースの関係

- テスト設計で「観点・条件の組み合わせ」を決め、そこから具体的なテストケース（手順・データ・期待結果）を展開する。
- 設計書に「境界値 0, 1, 9, 10 を確認する」と書いておき、テストケースでは「入力 0 のときエラーメッセージ ○○ が表示される」のように具体化する。

---

## 3. テスト結果の記録とレポート

### 3.1 実施結果の記録

- 各テストケースについて、**実施日・実施者・結果（Pass / Fail / Blocked / Skip）**を記録する。
- 失敗した場合は、[[11_欠陥管理とバグレポート]] に従って欠陥を起票し、テストケースと紐づける。

### 3.2 テストレポート

- **テストレポート**: テスト実施後、**何を・どれだけ・どの結果で**行ったかをまとめた報告書。
- 含めるとよい内容：実施期間、テスト対象、実施したテストケース数、成功・失敗・保留の内訳、発見した欠陥の概要・深刻度、リスクや残課題、リリース可否の判断材料。
- ステークホルダーが「今の品質がどの程度か」を理解できるように書く。

---

## 4. アジャイル・反復開発での扱い

- アジャイルでは、**大きなテスト計画書を一度に作る**のではなく、**スプリントごと・リリースごとに「今スプリントで何をテストするか」を計画**することが多い。
- テスト戦略は軽量に保ち、テストケースやバグはバックログ・ボードで可視化し、デイリーミーティングや振り返りで調整する。
- 自動テストと手動テストの役割を明確にし、リグレッションは自動化、新機能・探索は手動で補う形がよくある。
