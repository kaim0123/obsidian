## 詳しい要約

**テーマ：リクエストが ELB → EC2 → DB・S3 と渡る道筋と、各サービスの担当**

設定画面や料金ではなく、1 つのリクエストがどの箱をどの順に通るかに絞って、ELB・EC2・S3（とデータベース）の担当を整理する回。ELB は「入口と振り分け」、EC2 は「考える係（使い捨てで何も抱えない）」、S3 は「しまう係（名札で丸ごと出し入れし、台とは別に残る）」、DB は「表の係（名札を記録する）」。「画像が時々表示されない」「入れ替えたら消えた」「台を増やしたらログインが切れる」はどれも、EC2 に状態を抱えさせたことによる同じ形の事故である。

---

### よくある 4 つの場面

1. ユーザーがアップした画像が **時々** 表示されない。
2. サーバーを入れ替えたらファイルが消えた。
3. 台数を増やしたらログインが切れるようになった。
4. AI が書いた保存処理をレビューすることになった。

- 1〜3 はどれも **箱ごとの担当を取り違える** と起きる事故。

### リクエストの道筋をひと回り

- ブラウザがマイページを開く → まず **ELB**（入口）に届く。ELB は渡す先を選ぶだけで中身は作らない。
- **EC2** の 1 台目に届き、アプリが **データベース** に名前や画像の **名札（キー）** を問い合わせる。画像そのものは DB に入れない。
- その名札で **S3** から画像の中身をもらい、画面と画像が揃ってブラウザに戻る。
- 流れは「入口 → 考える → 表 → 置き場 → 戻る」。

### ELB：入口と振り分け

- **負荷を振り分ける** 係。入口の住所は 1 つだけで、後ろに何台あっても利用者はその住所だけ知っていればよい（配り方の種類は知らなくてよい）。
- もう 1 つの仕事が **ヘルスチェック**。一定間隔で後ろの各台に「元気か」を聞き、返事がない失敗が続く（例：3 回）と、その台を配る先から外す。利用者は止まったことに気づかない。
- **やること**：入口の住所を 1 つにする／後ろの台に配る／様子を見て壊れた台を外す／**暗号化通信（TLS）を入口で解いて** 後ろへ渡す（後ろの台は暗号の手間を気にしなくてよい）。
- **やらないこと**：画面の中身は作らない／データも覚えない。あくまで「受付で配る人」。

### EC2：借りたコンピュータ

- OS があり、アプリが動き、手元のディスクもある。普通のサーバーと同じように使えるからこそ落とし穴がある。
- 場面 1 の正体：写真のアップロードが 1 台目に配られて **1 台目の手元のディスク** に保存される。次の表示リクエストが 2 台目に配られると「画像が見つかりません」。もう一度頼んで 1 台目に配られると表示される。**当たるかどうかは配られ方次第**。
- 場面 2 の正体：EC2 は壊れたら捨てて作り直すことが多く、**手元のディスクはその台と一緒に消える**。

### S3：みんなの置き場

- 解決策は **置き場を台の外に出す** こと。それが S3 の担当。
- アップロードを受けた EC2 は手元にしまわず、名札（キー）をつけて S3 に置く。表示時はどの台に配られても S3 から名札で取ってくるので必ず表示される。台を作り直しても写真は失われない。
- **EC2 は考える係、S3 はしまう係** と分ける。

### S3 はディスクではない

| | EC2 の手元のディスク | S3 |
|---|---|---|
| 見える範囲 | その台からだけ | どの台からも届く |
| 書き換え | ファイルの途中だけ書き換えられる | **丸ごと置く・丸ごと取る**（途中だけ直すことはできず置き直す） |
| 寿命 | 台と一緒に消える | 台とは別の場所に残り続ける |
| 容量 | 先に決めて借りる | 置いた分だけ増える |

- 名札で出し入れする置き場なので **データベースの代わりにはならない**。細かく書き換える表は DB、画像・動画・書き出したファイルのようなまとまったものは S3。
- 現在の S3 は、置いた直後に読めば置いたものがちゃんと返ってくる作りになっている。

### 大きなファイルは直接運ぶ（署名付き URL）

- 2GB の動画を EC2 で全部受け取ると、受け取りっぱなしで他の依頼が待たされ、考える係が荷物運びで手一杯になる。
- そこで、ブラウザは「アップしたい」とだけ伝え、EC2 は中身を受け取らずに **期限付き（例：15 分）で置く場所も決まった許可の札** を作って渡す。ブラウザは動画と札を持って **S3 に直接運ぶ**。EC2 は名札だけを DB に記録する。
- 期限が切れた札は S3 が断る（ずっと使える札は危ない）。考える係は札を出すだけ、重い荷物は置き場へ直接。

### コードで見る

- **危ない書き方**：受け取った画像を **その台のフォルダに保存** し、その台の中の場所を DB に記録する。台が 2 台になった瞬間に「時々見えない」が起き、別の台から見ると意味のない場所になる。
- **外に出す書き方**：ぶつからないよう **新しい番号から名札を作り**（ユーザーがつけたファイル名をそのまま使わない）、S3 に名札をつけて丸ごと置き、DB には名札だけを記録する。表示時は DB の名札で S3 から取ってくるので、どの台で動いても同じ答えになる。

### 台を増やしても壊れない

- 場面 3 の正体：1 台のときは A さんのログイン状態を 1 台目が覚えていて問題が出ない。2 台目を足すと、A さんの依頼が 2 台目に配られたときに「知らない人」になりログインが切れる。画像のときとまったく同じ形の事故。
- 直し方も同じで、**覚えておくことは台の外の置き場に出す**。すると台を増やしても減らしても入れ替えても大丈夫になる。ELB が自由に配れるのは、台が何も抱えていないから。

### 4 つの箱の担当

| 箱 | 担当 |
|---|---|
| ELB | 入口と配る係。住所は 1 つ、壊れた台を外す |
| EC2 | 考える係。アプリが動く。**何も抱えない（使い捨て）** |
| S3 | しまう係。名札で丸ごと出し入れし、台とは別に残る。画像や動画など大きなまとまり |
| データベース | 表の係。細かく書き換え、名札を記録する |

### AI に保存・配置のコードを書かせたときに見るところ

1. 画像を **その台のフォルダに保存** していないか（手元で試すと動くので AI もよく書く。1 台では気づけない）。
2. ログインなどの記憶を **その台のメモリ** に置いていないか（台を増やした日に初めて壊れる）。
3. 置き場を **誰でも読める設定** にしていないか。見せたいものだけ期限付きの札で見せるのが基本。
4. 鍵や合言葉を **コードに直接** 書いていないか。コードは共有されるので、鍵は別の仕組みから渡す。
5. ELB のヘルスチェックに **「元気」と答える道** を用意しているか。ないと ELB は壊れた台を外せない。

### まとめ

- リクエストは「入口（ELB）→ 考える（EC2）→ 表（DB）→ 置き場（S3）」の順に渡る。
- **台は使い捨て、覚えておくことは台の外へ**。EC2 に状態を抱えさせると「時々見えない」「入れ替えで消える」「ログインが切れる」が起きる。
- 表には名札、中身は置き場。大きなファイルは期限付きの札で S3 に直接運ばせる。
- 料金体系や設定画面は、必要になったときに調べれば十分。
