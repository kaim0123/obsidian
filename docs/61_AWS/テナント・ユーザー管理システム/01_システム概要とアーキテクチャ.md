# システム概要とアーキテクチャ

## システム概要

### 何を作るのか
マルチテナント対応のユーザー管理システムを構築します。複数の組織（テナント）が同じシステムを共有しながら、データは完全に分離されます。

### ユースケース
```
例：SaaS型プロジェクト管理ツール
- 企業A（テナントA）
  - 管理者ユーザー
  - 一般ユーザー
  - プロジェクトデータ

- 企業B（テナントB）
  - 管理者ユーザー
  - 一般ユーザー
  - プロジェクトデータ

→ 企業Aと企業Bのデータは完全に分離
```

## マルチテナントアーキテクチャとは

### マルチテナントの種類

#### 1. サイロモデル（Silo Model）
```
各テナントごとに完全に独立したインフラ

テナントA → 専用DB + 専用Lambda
テナントB → 専用DB + 専用Lambda

メリット:
✅ 完全なデータ分離
✅ テナント単位のカスタマイズが容易
✅ パフォーマンス分離

デメリット:
❌ コストが高い
❌ 運用管理が複雑
❌ スケールしにくい
```

#### 2. プールモデル（Pool Model）
```
すべてのテナントが同じインフラを共有

全テナント → 共有DB + 共有Lambda
（データはテナントIDで分離）

メリット:
✅ コスト効率が高い
✅ 運用管理が簡単
✅ スケールしやすい

デメリット:
❌ データ分離を慎重に設計する必要
❌ ノイジーネイバー問題（他テナントの影響を受ける）
```

#### 3. ハイブリッドモデル
```
基本は共有、一部のテナントは専用

通常テナント → 共有インフラ
大企業テナント → 専用インフラ
```

### 本システムの選択：プールモデル
このシステムでは、コスト効率とスケーラビリティを重視して**プールモデル**を採用します。

### 使用するAWSサービス

#### 1. Amazon Cognito
**役割**: ユーザー認証と認可

```
機能:
- ユーザープール（サインアップ/サインイン）
- JWT トークン発行
- カスタム属性（tenantId）
- ユーザーグループ（admin, user）
- MFA（多要素認証）対応
```

#### 2. Amazon API Gateway
**役割**: APIエンドポイントの管理

```
機能:
- REST API エンドポイント
- Cognito Authorizer（認証検証）
- リクエスト検証
- レート制限
- CORS設定
```

#### 3. AWS Lambda
**役割**: ビジネスロジックの実行

```
Lambda関数一覧:
1. テナント作成
2. テナント取得
3. テナント更新
4. テナント削除
5. ユーザー作成
6. ユーザー取得
7. ユーザー一覧
8. ユーザー更新
9. ユーザー削除
10. ユーザー招待
11. ロール管理
```

#### 4. データベース

**オプションA: Amazon Aurora PostgreSQL Serverless v2（推奨）**
```
特徴:
- リレーショナルデータベース
- 正規化されたスキーマ
- 複雑なJOINクエリが容易
- 外部キー制約でデータ整合性保証
- トランザクション対応
- 自動スケーリング（0.5〜128 ACU）
- PostgreSQL完全互換

推奨理由:
✅ 権限管理の複雑なクエリが1回で完結
✅ データ整合性が重要
✅ レポート・分析機能が必要
```

**オプションB: Amazon DynamoDB（参考）**
```
特徴:
- NoSQLデータベース
- シングルテーブルデザイン
- グローバルセカンダリインデックス（GSI）
- 超高速レスポンス（1ms未満）
- 無制限のスケーラビリティ

適している場合:
- シンプルなデータモデル
- 超高速アクセスが最優先
- 極めて大規模なユーザー数
```

#### 5. Amazon SNS
**役割**: 通知サービス

```
用途:
- ユーザー招待メール
- パスワードリセット通知
- 管理者アラート
```

#### 6. Amazon CloudWatch
**役割**: 監視とログ

```
機能:
- Lambda関数ログ
- APIアクセスログ
- メトリクス監視
- アラート設定
```

## データ分離戦略

### 1. テナントIDによる分離
```python
# すべてのクエリにテナントIDを含める
def get_users(tenant_id: str):
    response = table.query(
        KeyConditionExpression='PK = :pk AND begins_with(SK, :sk)',
        ExpressionAttributeValues={
            ':pk': f'TENANT#{tenant_id}',
            ':sk': 'USER#'
        }
    )
    return response['Items']
```

### 2. JWT トークンからテナントID取得
```python
def get_tenant_id_from_token(event):
    """認証トークンからテナントIDを取得"""
    claims = event['requestContext']['authorizer']['jwt']['claims']
    tenant_id = claims.get('custom:tenantId')
    return tenant_id
```

### 3. IAMポリシーでの制御
```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "dynamodb:Query",
      "dynamodb:GetItem"
    ],
    "Resource": "arn:aws:dynamodb:*:*:table/TenantUserManagement",
    "Condition": {
      "ForAllValues:StringEquals": {
        "dynamodb:LeadingKeys": ["TENANT#${custom:tenantId}"]
      }
    }
  }]
}
```

## セキュリティ設計

### 1. 認証フロー
```
1. ユーザーがログイン
   ↓
2. Cognitoがトークン発行（IDトークン、アクセストークン）
   ↓
3. クライアントがAPIリクエスト時にトークンを送信
   ↓
4. API GatewayのCognito Authorizerが検証
   ↓
5. 検証成功 → Lambda実行
```

### 2. データアクセス制御
```python
# すべてのAPI呼び出しでテナントIDをチェック
def verify_tenant_access(event, target_tenant_id):
    user_tenant_id = get_tenant_id_from_token(event)
    if user_tenant_id != target_tenant_id:
        raise PermissionError('Access denied')
```

### 3. ロール検証
```python
def require_admin(event):
    """管理者権限が必要な操作"""
    claims = event['requestContext']['authorizer']['jwt']['claims']
    groups = claims.get('cognito:groups', [])
    
    if 'admin' not in groups:
        raise PermissionError('Admin access required')
```
