# ボーイスカウトの規則（The Boy Scout Rule）

## はじめに

コードは、何もしなくても少しずつ汚れていきます。急ぎの修正、とりあえずのコピペ、意味の変わった変数名……。これが積み重なると、やがて誰も触りたくないコードになります。

かといって「全部きれいに書き直す時間」はなかなか取れません。そこで役に立つのが **ボーイスカウトの規則** です。

---

## 一言でいうと

**「来たときよりも美しく」**

コードに触ったら、**触る前より少しだけきれいにしてから離れる**、という習慣です。

---

## 定義・背景

- ボーイスカウトには「キャンプ場は来たときよりもきれいにして帰ろう」という教えがあります
- Robert C. Martin（Uncle Bob）が、これをプログラミングに当てはめて紹介しました。『Clean Code』（2008 年）の冒頭でも取り上げられています
- 大きなリファクタリングの計画を立てるのではなく、**日々の小さな改善を積み重ねて、コードの劣化を止める** という考え方です

「1 回の改善は小さくていい。ただし毎回やる」のがポイントです。

---

## 悪い例: 触ったところだけ直して去る

送料の計算にバグがあり、修正を頼まれたとします。

```javascript
// 修正前
function calc(o) {
  let t = 0;
  for (let i = 0; i < o.items.length; i++) {
    t = t + o.items[i].p * o.items[i].q;
  }
  if (t > 5000) {
    return t;
  } else {
    return t + 500; // ← 本当は「5000 以上」で送料無料にしたい
  }
}
```

```javascript
// 悪い直し方: バグだけ直して、読みにくさはそのまま
function calc(o) {
  let t = 0;
  for (let i = 0; i < o.items.length; i++) {
    t = t + o.items[i].p * o.items[i].q;
  }
  if (t >= 5000) {
    return t;
  } else {
    return t + 500;
  }
}
```

次にこのコードを読む人も、`calc`・`o`・`t`・`p`・`q` の意味を一から読み解くことになります。

## 良い例: ついでに少しだけ整える

```javascript
const FREE_SHIPPING_THRESHOLD = 5000;
const SHIPPING_FEE = 500;

function calcTotalWithShipping(order) {
  const subtotal = order.items.reduce(
    (sum, item) => sum + item.price * item.quantity,
    0
  );
  if (subtotal >= FREE_SHIPPING_THRESHOLD) return subtotal;
  return subtotal + SHIPPING_FEE;
}
```

やったことは、

- 関数名・変数名を **意味の分かる名前** にした
- マジックナンバーを **定数** にした

だけです。設計を大きく変えたわけではありませんが、次に読む人の負担はぐっと減ります。

> ※ プロパティ名 `p` / `q` の変更は呼び出し元にも影響するので、範囲が広がるなら別の作業に分けます（下の「やりすぎ」を参照）。

---

## どのくらい「きれいに」すればいいか

| ちょうどよい例 | やりすぎの例 |
|---|---|
| 分かりにくい変数名を 1〜2 個直す | ファイル全体の命名規則を書き換える |
| 長い関数から 1 か所だけ関数を切り出す | クラス構成を作り直す |
| 不要になったコメント・未使用コードを消す | 使っていないかもしれない機能を推測で消す |
| マジックナンバーを定数にする | 設定ファイルの仕組みを新しく作る |

目安は **「本来の修正のレビューを邪魔しない程度」** です。

---

## よくある誤解・やりすぎ

### 誤解1: 触ったファイルは全部きれいにすべき

改善の範囲が広がると、**本来の修正とリファクタリングが混ざり、レビューもしにくく、バグの原因も追いにくく** なります。大きな改善は別のコミット・別の PR に分けましょう。

### 誤解2: テストがなくてもとりあえず直す

テストがない場所での「ついでの改善」は、新しいバグを生むことがあります。**安全に直せる範囲（名前の変更・定数化など）にとどめる** か、先にテストを書きます。

### 誤解3: 他人のコードは触らない方が礼儀

チームのコードは **チーム全員のもの** です。ただし、方針が分かれそうな変更（書き方の好みなど）はチームで合意してから行います。

---

## まとめ

- **触ったコードは、来たときより少しだけきれいにして去る**
- 1 回の改善は **小さくていい**。ただし **毎回やる**
- 本来の修正を邪魔しない範囲にとどめ、大きな改善は **分けて行う**
- テストがない場所では **安全な改善だけ** にする
