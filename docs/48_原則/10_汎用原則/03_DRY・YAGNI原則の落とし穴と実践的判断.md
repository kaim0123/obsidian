# DRY・YAGNI原則の落とし穴と実践的判断

> 基本的な定義は [[02_DRY原則・KISS原則]] を参照

設計原則は「知っている」だけでは不十分で、**いつ適用し、いつ適用しないか**の判断が本質である。この文書では DRY・YAGNI・SRP が衝突する場面での考え方を整理する。

---

## 1. DRY原則の致命的な誤解

### 原著者による訂正

『The Pragmatic Programmer』20周年記念版で、著者の Dave Thomas と Andy Hunt は DRY の誤解を明確に訂正した。

> 「DRYとは『知識』や『意図』の重複に関するものです」

**本来の定義:**

> すべての知識はシステム内で単一で、あいまいでなく、権威ある表現を持たなければならない

つまり **避けるべきは「コードの外観の重複」ではなく「ビジネス上の知識や意図の重複」** である。

### 偶然の重複 vs 本質的な重複

コードが同じでも、表している**知識**が異なれば、それは「偶然の一致」であり DRY 違反ではない。

```typescript
// 年齢の検証
function validateAge(value: number) {
  validateType(value, 'integer');
  validateMinInteger(value, 0);
}

// 数量の検証
function validateQuantity(value: number) {
  validateType(value, 'integer');
  validateMinInteger(value, 0);
}
```

一見同じコードだが、**年齢と数量は異なる知識**を表している:
- 年齢 → 将来「20歳以上」という制約が追加される可能性
- 数量 → 将来「在庫数以下」という制約が追加される可能性

これらを無理に共通化すると、**変更理由が異なるものが結合**してしまい、一方の変更がもう一方に波及する。

### 判断のチェックリスト

共通化すべきか迷ったら、以下を確認する:

| 質問 | Yes → 共通化 | No → 分けておく |
|------|-------------|----------------|
| 同じビジネスルールを表しているか？ | ○ | × |
| 一方が変わったら必ず他方も変わるか？ | ○ | × |
| 変更理由（＝責務）は同一か？ | ○ | × |

## 2. DRY vs SRP（単一責務原則）の衝突

### なぜ衝突するのか

- **DRY** は「共通知識の重複」を警告する
- **SRP** は「変更理由の混線」を警告する

この2つは、同じコードに対して**正反対の指示**を出すことがある。

### 具体例: 部門ごとの税計算

```javascript
// 営業部の売上税計算
function calcSalesTax(amount) {
  return amount * 0.1;
}

// 経理部の仕入税計算
function calcPurchaseTax(amount) {
  return amount * 0.1;
}
```

DRY の観点: 「同じ `amount * 0.1` が重複している → 共通化すべき」
SRP の観点: 「営業部と経理部は異なる変更理由を持つ → 分離すべき」

**正解は SRP を優先する場合が多い。** なぜなら:
- 税率改正で売上税と仕入税が異なる率になる可能性がある
- 共通化していると、片方だけ変更したいときに条件分岐が増殖する

### 壊れ方のトレードオフで考える

良い設計とは「正解を選ぶ」ことではなく、**壊れ方の比較**である。

| 選択 | 壊れ方 |
|------|--------|
| DRY を優先して共通化 | 変更理由が分岐したとき、条件分岐が増殖してスパゲティ化 |
| SRP を優先して分離 | 共通のビジネスルールが変わったとき、複数箇所の修正が必要 |

**どちらの壊れ方がより危険か**を判断する。将来の変更が予測しにくい場合は、分離しておく方が安全である。

## 3. 「間違った抽象化」より「重複」の方が安い

Sandi Metz の名言:

> "Duplication is far cheaper than the wrong abstraction"
> （重複は、間違った抽象化よりはるかに安上がりである）

不適切な共通化がもたらすスパゲティコードの修正コストは、2箇所に同じコードがある状態の修正コストより**はるかに高い**。

### Rule of Three（3回の法則）と AHA

**AHA（Avoid Hasty Abstractions）**: 性急な抽象化を避ける

1. **1回目**: 普通にコードを書く
2. **2回目**: 同じ処理でもコピペして重複させる（まだ共通化しない）
3. **3回目**: 3回目で初めて共通化を検討する

2つのサンプルだけでは、共通化のパターンが本当に正しいか判断できない。3回目に初めて「これは本質的に同じ知識だ」と確信を持てる。

## 4. YAGNI原則が初心者に遵守できない理由

### 「何が不要か」を見抜く難しさ

YAGNI の文言「まだ必要ないものは作らない」は一見簡単に見える。しかし実際には **「何が不要か」を正しく判断する能力**が前提となる。

初心者が識別できる「不要な機能」:
- 明らかに使わない画面やボタン
- 誰も要求していない機能

ベテランが識別できる「不要なもの」:
- 過剰な抽象化レイヤー
- 先回りしたデザインパターンの適用
- 将来の拡張を見越した不要なインターフェース
- 必要以上の設定可能性（configurability）

**初心者は「不要なもの」の認識範囲が狭い**ため、YAGNI を知っていても実践できない。

### YAGNI が成立する前提条件

YAGNI が機能するには、以下が**必須**:

1. **テスト環境が整っていること** — 後から安全に変更できる保証
2. **リファクタリング能力があること** — 「後で追加する」が実行できる技術力
3. **CI/CD が整備されていること** — 変更を素早くデプロイできる体制

これらがなければ「今は作らない → 必要になったら追加する」の後半が成立せず、YAGNI は**ただの手抜きの言い訳**になる。

### 教育上の課題

標語の暗記では YAGNI は身につかない。身につけるには:
- 具体的なコードレビューを通じて「これは不要」「これは必要」の境界線を体験する
- ベテランの判断過程を言語化してもらう
- 自分で「作りすぎた」「作らなさすぎた」の両方を経験する

---

## 5. ベテランの「勘」の正体

ベテランの設計判断が素早く見えるのは、才能やセンスではなく**危険察知のパターンマッチング**である。

過去に「共通化して壊れた」「分離しておいて助かった」という経験の蓄積が、コードを見た瞬間に「これは危ない」というシグナルを発する。

初心者との違いは:
- 初心者: 原則を「ルール」として機械的に適用する
- ベテラン: 原則を「ヒューリスティクス（経験則）」として、状況に応じて使い分ける

## 6. 実践的な判断フローチャート

```
コードの重複を発見
  │
  ├─ 同じビジネスルール/知識を表しているか？
  │    │
  │    ├─ Yes → 一方が変わったら他方も必ず変わるか？
  │    │         │
  │    │         ├─ Yes → 共通化する（DRY適用）
  │    │         └─ No  → 分離しておく（SRP優先）
  │    │
  │    └─ No → 偶然の一致。共通化しない
  │
  └─ 3回以上出現したか？（Rule of Three）
       │
       ├─ Yes → 共通化を検討する
       └─ No  → まだ様子を見る
```

---

## 7. まとめ

| 原則 | よくある誤解 | 正しい理解 |
|------|------------|-----------|
| DRY | 同じコードは共通化すべき | 同じ**知識**の重複を避ける。コードの見た目が同じでも知識が違えば共通化しない |
| YAGNI | 簡単に実践できる | 「何が不要か」の判断にはテスト・リファクタリング能力が前提 |
| SRP | DRYと矛盾しない | DRYと衝突する場面がある。変更理由が異なるなら分離を優先 |

**設計判断の本質は「正解を選ぶ」ことではなく「どちらの壊れ方がマシか」を比較すること。**
