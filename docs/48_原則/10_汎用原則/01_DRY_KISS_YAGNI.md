# DRY・KISS・YAGNI — 基本的な開発原則

## はじめに

プログラムを書くとき、「どう書けばよいコードになるのか」と迷うことがあります。そんなときに道しるべになってくれるのが、先人たちが残した **開発原則** です。

ここでは、特に有名な3つの原則を学びます。

- **DRY**（ドライ）… 同じことを繰り返し書かない
- **KISS**（キス）… シンプルに保つ
- **YAGNI**（ヤグニ）… 今いらない機能は作らない

この3つは、それぞれ頭文字を取った略語です。どれも「読みやすく、壊れにくいコードを書くため」のものです。

---

## DRY原則（Don't Repeat Yourself）

**「同じことを繰り返し書かない」** という原則です。Andy Hunt と Dave Thomas が『達人プログラマー』で提唱しました。

### なぜ必要なのか

同じ処理をあちこちにコピーして書いてしまうと、次のような問題が起きます。

- **修正漏れが発生する** … 仕様変更のとき、1つだけ直し忘れてバグになる
- **読むのに時間がかかる** … 同じようなコードが散らばっていると、どれが本物か分からなくなる
- **テストが難しい** … 同じロジックを何度もテストしなくてはならない

### 悪い例

```javascript
function calcTaxForFood(price) {
  return price + price * 0.08; // 軽減税率8%
}

function calcTaxForBook(price) {
  return price + price * 0.08; // 同じ計算！
}

function calcTaxForToy(price) {
  return price + price * 0.10; // 標準税率10%
}
```

軽減税率が将来8%から9%に変わったら、2か所を直さなくてはなりません。直し忘れると、食べ物と本で税額がズレてバグになります。

### 良い例

```javascript
const TAX_REDUCED = 0.08;
const TAX_STANDARD = 0.10;

function calcTax(price, rate) {
  return price + price * rate;
}

calcTax(1000, TAX_REDUCED); // 食べ物
calcTax(1500, TAX_REDUCED); // 本
calcTax(3000, TAX_STANDARD); // おもちゃ
```

税率の変更は定数1か所の修正で済みます。

### DRYで気をつけること

**「見た目が同じ」なだけで無理にまとめない** ことです。たまたま同じコードになっているだけなら、別物として置いておくほうが安全な場合もあります。DRYは「**同じ知識**を二重に書かない」ことが本質です。

## KISS原則（Keep It Simple, Stupid）

**「シンプルに保て」** という原則です。「難しいことをしようとせず、単純に作れ」という意味です。

### なぜ必要なのか

複雑なコードは、書いた本人でさえ1週間後には読めなくなります。**コードは書く時間より読む時間のほうが圧倒的に長い** ため、シンプルさは大きな武器です。

### 悪い例（複雑すぎる）

```javascript
// 偶数か判定する関数
function isEven(n) {
  return ((n & 1) === 0) ? true : (((n % 2) === 0) ? true : false);
}
```

ビット演算や三項演算子を使って格好良く見えますが、読みにくくバグの温床になります。

### 良い例（シンプル）

```javascript
function isEven(n) {
  return n % 2 === 0;
}
```

### KISSで気をつけること

- **賢いコードより、わかりやすいコードを書く**
- **早すぎる最適化は避ける**（パフォーマンスより読みやすさ優先）
- **1つの関数は1つのことだけを行う**

## YAGNI原則（You Aren't Gonna Need It）

**「たぶん必要にならない」** という原則です。エクストリーム・プログラミング（XP）で提唱されました。

**「将来役に立ちそうだから」という理由で、今不要な機能を先回りして作ってはいけない** という意味です。

### なぜ必要なのか

「将来のために」と思って作った機能は、**80%以上は使われない** と言われています。にもかかわらず、

- コードが肥大化して読みにくくなる
- テストしなければならないコードが増える
- 仕様変更のとき、使わないコードも直さなくてはならない
- 本当に使うときには要件が変わっていて、作り直しになる

### 悪い例

```javascript
// ユーザー登録機能だけ作ればいい場面で…
class UserManager {
  register(user) { /* ... */ }
  
  // 「将来使うかも」でつくった
  exportToPDF() { /* 未使用 */ }
  exportToCSV() { /* 未使用 */ }
  exportToXML() { /* 未使用 */ }
  sendSMS() { /* 未使用 */ }
  integrateWithSlack() { /* 未使用 */ }
}
```

### 良い例

```javascript
class UserManager {
  register(user) { /* 今必要な機能だけ */ }
}
// エクスポート機能は、本当に必要になってから実装する
```

### YAGNIで気をつけること

「いつか必要になる」の **「いつか」は来ない** と思っておくくらいでちょうど良いです。本当に必要になったときに追加すれば、その時点の要件に合った形で作れます。

---

## 3つの原則の関係

3つはそれぞれ独立した原則ですが、互いに補い合います。

| 原則 | 意味 | 一言で |
|------|------|--------|
| DRY | 重複を避ける | 書くのは1回だけ |
| KISS | シンプルを保つ | 賢さより分かりやすさ |
| YAGNI | 先回りしない | 今いらないものは作らない |

### まとめた例

```javascript
// 悪い例: DRY違反・KISS違反・YAGNI違反すべて
function processUser(user, type, format, notify, future1, future2) {
  if (type === 'admin') { /* 独自処理A */ }
  if (type === 'user') { /* 独自処理A（コピペ）*/ }
  if (format === 'json') { /* 変換 */ }
  if (format === 'xml') { /* 未使用 */ }
  if (notify) { /* まだ使わない通知 */ }
  // ...
}

// 良い例: 3つの原則すべてを満たす
function processUser(user) {
  validate(user);
  save(user);
}
```

## よくある誤解

### 誤解1: DRYだからといって何でもまとめる

たまたま見た目が似ているだけの2つの関数を無理にまとめると、逆にコードが複雑になります。**同じ「意味」「目的」「責任」を持つコードだけをまとめる** のが正しいDRYです。

### 誤解2: KISSだから機能を削ってもよい

KISSは「**実装**をシンプルに」という原則で、「**要件**を削る」ことではありません。必要な機能は必要な分だけ作ります。

### 誤解3: YAGNIだから拡張性を考えなくてよい

後から変更しやすい **構造** を作ることと、今いらない **機能** を先回りで作ることは別物です。構造の柔軟性は大切ですが、未使用の機能は作らない。これがYAGNIです。
