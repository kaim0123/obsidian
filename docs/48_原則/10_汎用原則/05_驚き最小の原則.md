# 驚き最小の原則（Principle of Least Astonishment）

## はじめに

`getUser()` という名前の関数を呼んだら、ユーザーを取ってくるだけでなく **こっそりデータベースを更新していた**。こんな体験をすると、そのコードは二度と安心して呼べなくなります。

こうした「えっ、そんなことするの？」を減らすための考え方が **驚き最小の原則（Principle of Least Astonishment, POLA）** です。**驚き最小の法則**、**Principle of Least Surprise** とも呼ばれます。

---

## 一言でいうと

**「使う人が予想したとおりに動くように作る」**

名前・見た目・使い方から **普通の人が期待する動き** と、**実際の動き** を一致させよう、という原則です。

---

## 定義・背景

- もともとは **ユーザーインターフェース設計** の分野で言われていた考え方で、1970〜80 年代のプログラミング言語・UI の議論の中で広まりました（特定の 1 人の提唱者がいる原則ではありません）
- 「ユーザー」は画面を触るエンドユーザーだけではありません。**関数・クラス・API を呼ぶプログラマも「ユーザー」** です
- Ruby の作者まつもとゆきひろ氏が Ruby の設計方針として「驚き最小（ただし **自分にとっての**）」を挙げたことでもよく知られています

ポイントは、**「驚き」は使う人の予想とのズレ** だということです。だから「誰が使うのか」「その人たちは何を当たり前と思っているか」で答えが変わります。

---

## 悪い例: 名前と動きがずれている

```javascript
class UserService {
  // 「取得する」名前なのに、ログイン日時を書き換えている
  getUser(id) {
    const user = this.repository.find(id);
    user.lastLoginAt = new Date();
    this.repository.save(user);
    return user;
  }

  // 「チェックする」名前なのに、不正なら勝手に値を直している
  isValidEmail(user) {
    if (!user.email.includes('@')) {
      user.email = user.email + '@example.com';
    }
    return true;
  }
}

// 引数の配列を破壊的に並べ替えてしまう
function topScores(scores) {
  return scores.sort((a, b) => b - a).slice(0, 3);
}
```

### 何が問題か

- `getUser()` を **画面表示のためだけに呼んだ** のに、ログイン日時が更新されてしまう
- `isValidEmail()` が **常に true を返し、しかもデータを書き換える**。検証のつもりで呼んだ人は気づけない
- `topScores(scores)` を呼んだあと、**元の `scores` の並び順が変わっている**

どれも「名前から想像できない副作用」がバグの原因になっています。

---

## 良い例: 名前どおりに動かす

```javascript
class UserService {
  // 取得は取得だけ
  getUser(id) {
    return this.repository.find(id);
  }

  // 更新したいなら、それと分かる名前の別メソッドにする
  recordLogin(id) {
    const user = this.repository.find(id);
    user.lastLoginAt = new Date();
    this.repository.save(user);
  }

  // is〜 は真偽を返すだけ。データには触らない
  isValidEmail(user) {
    return user.email.includes('@');
  }
}

// 元の配列はコピーしてから並べ替える
function topScores(scores) {
  return [...scores].sort((a, b) => b - a).slice(0, 3);
}
```

「取得」「判定」「更新」が **名前を見ただけで区別できる** ようになり、呼ぶ側は安心して使えます。

---

## 驚きを減らすためのチェックポイント

| 観点 | 驚きを生む例 | 驚きを減らす方向 |
|---|---|---|
| 名前 | `getXxx()` が書き込みもする | 名前どおりの 1 つの仕事だけをする |
| 副作用 | 引数のオブジェクト・配列を書き換える | コピーして返す／書き換えるなら名前で示す |
| 戻り値 | 見つからないときだけ例外、ときどき `null`、ときどき `-1` | 失敗時の返し方をそろえる |
| 慣習 | `size()` と `length` と `count()` が混在 | 言語・フレームワーク・チームの慣習に合わせる |
| 引数の順序 | 似た関数なのに引数の順番がバラバラ | 似たものは同じ形にそろえる |

## よくある誤解・やりすぎ

### 誤解1: 「驚き」は誰にとっても同じ

同じコードでも、**Java に慣れた人と Python に慣れた人では驚く点が違います**。「自分は驚かない」ではなく、**そのコードを使う人たち（チーム・言語のコミュニティ）の常識** を基準にします。

### 誤解2: 新しいことを一切してはいけない

驚き最小の原則は「新しい仕組みを入れるな」という意味ではありません。**新しいことをするなら、名前やドキュメントで予告して驚きを小さくする** という意味です。

### 誤解3: 慣習に合わせれば何でも OK

悪い慣習に合わせ続けると、全体がわかりにくくなることもあります。慣習を変えるときは **チームで合意し、まとめて変える** のが驚きを最小にするやり方です。

## 他の原則との関係

- **KISS** — シンプルなものほど予想しやすく、驚きが少ない（[[01_DRY_KISS_YAGNI]]）
- **コマンド・クエリ分離（CQS）** — 「値を返すメソッドは状態を変えない」と決めておくと、`getUser()` のような驚きが起きない（[[05_コマンド・クエリ分離（CQS）]]）
- **リスコフの置換原則（LSP）** — サブクラスが親クラスと違う動きをすると、呼ぶ側が驚く（[[03_LSP (リスコフの置換原則)]]）

---

## まとめ

- **使う人が予想したとおりに動かす**
- 名前・副作用・戻り値・慣習の **ズレ** が驚きを生む
- 「驚き」の基準は **使う人たちの常識**
- 新しいことをするなら **名前やドキュメントで予告** する
