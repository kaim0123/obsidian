# 関心の分離（Separation of Concerns）

## はじめに

プログラムを読み書きしていると、「いろんなことが1つの場所にまとまっていて、何が本題か分からない…」と感じることがあります。これを解決するのが **関心の分離（Separation of Concerns, SoC）** という考え方です。

一言でいうと **「違うことは違う場所に書く」** という原則です。

---

## 「関心」とは何か

ここでいう **「関心（Concern）」** とは、ソフトウェアが担っている **1つの役割・目的・責任** のことです。

たとえば、ユーザー登録の画面を作るとき、内部で行っていることは次のように複数あります。

- 画面の見た目を描画する（**表示の関心**）
- ユーザーが入力した値をチェックする（**検証の関心**）
- データベースに保存する（**永続化の関心**）
- 確認メールを送る（**通知の関心**）

これらは「ユーザー登録」という1つの流れの中にありますが、それぞれ **目的がまったく違います**。こうした異なる目的を混ぜずに分けて書く、というのが「関心の分離」です。

---

## なぜ分けるのか

### 悪い例: 何もかも詰め込んだ関数

```javascript
function registerUser(name, email, password) {
  // HTMLを生成（表示の関心）
  const html = `<div>登録中: ${name}</div>`;
  document.body.innerHTML = html;

  // 入力チェック（検証の関心）
  if (!email.includes('@')) {
    alert('メール形式が不正');
    return;
  }

  // パスワード暗号化（セキュリティの関心）
  const hashed = btoa(password);

  // DBに保存（永続化の関心）
  const db = new Database();
  db.query(`INSERT INTO users VALUES ('${name}', '${email}', '${hashed}')`);

  // メール送信（通知の関心）
  sendMail(email, '登録完了しました');

  // アクセスログ記録（監査の関心）
  console.log(`${new Date()} ${name} 登録`);
}
```

1つの関数に6つの関心が詰まっています。問題は、

- **メール送信だけ直したい** のに、関数全体を読む必要がある
- **DBを別の種類に変更したい** のに、画面コードまで影響してしまう
- **テストが書きにくい**（DBもメールも同時に動かす必要がある）
- **誰かが似た処理を別のところでコピペして** コード重複が生まれる

### 良い例: 分けて書く

```javascript
// 検証の関心
function validate(email) {
  if (!email.includes('@')) throw new Error('メール形式が不正');
}

// セキュリティの関心
function hashPassword(password) {
  return bcrypt.hash(password);
}

// 永続化の関心
function saveUser(user) {
  return db.users.insert(user);
}

// 通知の関心
function sendWelcomeMail(email) {
  return mailer.send(email, '登録完了しました');
}

// これらを組み合わせる「流れ」の関心
async function registerUser({ name, email, password }) {
  validate(email);
  const hashed = await hashPassword(password);
  await saveUser({ name, email, password: hashed });
  await sendWelcomeMail(email);
}
```

それぞれの関数は **1つのことだけ** をするので、理解しやすく、差し替えやテストもしやすくなります。

## 関心を分ける主な軸

### 1. レイヤー（階層）で分ける

よく使われる分け方です。

- **プレゼンテーション層** … 画面・UIの関心
- **アプリケーション層** … 業務の流れ（ユースケース）
- **ドメイン層** … ビジネスルール
- **インフラ層** … DB・外部APIなどの関心

→ 詳しくは [[レイヤードアーキテクチャ]]

### 2. 機能（モジュール）で分ける

「ユーザー機能」「注文機能」「商品機能」のように、業務の単位で分けます。

### 3. 横断的関心事（Cross-Cutting Concern）で分ける

ログ出力・例外処理・トランザクション・認証などは、**どの機能でも必要** なので、専用の仕組み（ミドルウェア、アスペクト指向など）にまとめます。

---

## SOLIDとの関係

関心の分離は、SOLID原則の **SRP（単一責任の原則）** と深く関係しています。

- **関心の分離** … 全体を設計する際の大方針
- **SRP** … 個々のクラスに対する具体的なガイドライン

どちらも根は同じで、「1つのものに複数の役割を持たせない」という思想です。

---

## 分けすぎにも注意

関心の分離は大切ですが、**何でも細かく分ければよい、というわけではありません**。

- 関数が1行だけのファイルが100個ある
- 読むために10個のファイルを行き来しないといけない

これは **過剰分離** で、かえって読みにくくなります。目安は、**「別々の理由で変更される部分は分ける」「同じ理由で変更される部分はまとめる」** です。

---

## 実例: Webアプリでの関心の分離

| 関心 | 置き場所（例） |
|------|---------------|
| 画面の見た目 | HTML/CSS, Reactコンポーネント |
| 画面の操作 | JavaScript, イベントハンドラ |
| 業務ルール | Service / UseCase / ドメイン層 |
| データ保存 | Repository / DAO / Model |
| 外部API連携 | Adapter / Gateway |
| 認証・認可 | ミドルウェア |
| ログ | ロガー / AOP |

この表のように **「どこに何を書くか」が揃っている** だけで、チーム全体のコードが劇的に読みやすくなります。
