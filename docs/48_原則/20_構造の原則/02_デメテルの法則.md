# デメテルの法則（Law of Demeter）

## はじめに

プログラムを書いていると、`user.company.address.city.name` のように **オブジェクトをたどってたどってたどって** 値を取り出すコードを見ることがあります。一見自然に見えますが、実は **後々バグや変更コストを生む原因** になります。

これを防ぐのが **デメテルの法則（Law of Demeter, LoD）** です。

別名 **「最小知識の原則（Principle of Least Knowledge）」** とも呼ばれます。

---

## 一言でいうと

**「知り合いの知り合いと話してはいけない」**

あるオブジェクトは、自分がすぐ知っている相手（直接のフィールドや引数）だけと話すべきで、**その相手の内部構造までたどって触ってはいけない** という原則です。

---

## 正式なルール

あるメソッドの中から呼んでよいのは、次のものだけです。

1. **自分自身** のメソッド
2. **引数として渡された** オブジェクトのメソッド
3. **自分のフィールド（プロパティ）** のメソッド
4. **自分の中で作った** オブジェクトのメソッド

これ以外、つまり **「呼び出した結果、返ってきたオブジェクト」のメソッドをさらに呼ぶのはNG** というルールです。

---

## 悪い例: メソッドチェーンでたどる

```javascript
class Wallet {
  constructor(money) { this.money = money; }
  getMoney() { return this.money; }
  setMoney(m) { this.money = m; }
}

class Customer {
  constructor(name, wallet) {
    this.name = name;
    this.wallet = wallet;
  }
  getWallet() { return this.wallet; }
}

class PaperBoy {
  // 新聞配達員が、お客さんの財布に直接手を突っ込んでお金を取る
  charge(customer, price) {
    const wallet = customer.getWallet();
    const money = wallet.getMoney();
    if (money >= price) {
      wallet.setMoney(money - price);
    }
  }
}
```

`customer.getWallet().setMoney(...)` のように、**Customer の内部にある Wallet の内部構造** まで PaperBoy が知ってしまっています。

### 何が問題か

- **Customer の中身が変わると PaperBoy まで壊れる**（例: Wallet を廃止してクレカに変更）
- **カプセル化が崩れる**（Wallet を外から自由にいじれてしまう）
- **現実世界でも変**（配達員が勝手に財布から金を抜いてよいわけがない）

---

## 良い例: 「頼む」形に変える

```javascript
class Customer {
  constructor(name, wallet) {
    this.name = name;
    this.wallet = wallet;
  }
  // 支払いは Customer に「頼む」
  pay(price) {
    return this.wallet.withdraw(price);
  }
}

class Wallet {
  constructor(money) { this.money = money; }
  withdraw(amount) {
    if (this.money < amount) throw new Error('残高不足');
    this.money -= amount;
    return amount;
  }
}

class PaperBoy {
  charge(customer, price) {
    customer.pay(price); // Customer に支払いを頼むだけ
  }
}
```

PaperBoy は **Customer に「支払って」と頼む** だけ。Wallet の存在も構造も知りません。Customer がクレカに変わっても PaperBoy は影響を受けません。

---

## 見分け方: 「ドットの数」ルール

### よく言われる目安

> **「メソッド呼び出しのドット（`.`）は1つまで」**

```javascript
a.b()       // OK
a.b().c()   // 怪しい（デメテル違反の可能性）
a.b().c().d() // ほぼアウト
```

ただし、**厳密に1つまで守れ** という意味ではありません。以下は違反ではない例です。

```javascript
// メソッドチェーンでも、同じオブジェクトを返し続けているだけならOK
builder.setName('a').setAge(20).setEmail('x@x').build();

// 自分自身のメソッドや、引数のメソッドを呼ぶのもOK
this.repository.save(user);
```

**「他人のオブジェクトの内部をたどっているか」** が判断の基準です。

---

## なぜ守るのか

### 1. 変更に強くなる

`user.company.address.city.name` のようなチェーンは、途中のどこが変わっても壊れます。法則を守っておけば、内部構造の変更が外に漏れません。

### 2. カプセル化が守られる

「持っているデータ」ではなく「してほしいこと」を頼む設計になるので、オブジェクト指向本来の強さが出ます。

### 3. テストが書きやすくなる

モックするオブジェクトが減ります。`user.company.address.city.name` をテストするには `company`, `address`, `city` すべてを用意する必要がありますが、`user.getCityName()` なら `user` 1つで済みます。

---

## 実務でよくある違反パターン

### パターン1: Getterの連鎖

```javascript
order.getCustomer().getAddress().getZipCode()
```

→ **`order.getShippingZipCode()`** のように、Orderに代わりに聞く。

### パターン2: DTO（データ転送オブジェクト）へのアクセス

```javascript
config.database.connection.pool.max
```

→ 深いアクセスは **設定オブジェクトに getMaxPoolSize() のような薄いメソッドを持たせる** か、ここは DTO なので例外扱いとして許容する、など判断が必要。

### パターン3: フレームワーク/ライブラリ

```javascript
$('.btn').on('click', fn) // jQuery
```

これは **Fluent API** と呼ばれる意図的な設計で、同じオブジェクトを返し続けているだけなので違反ではありません。

---

## 例外: いつ守らなくてよいか

- **DTOや設定オブジェクト** など、単なる「データの入れ物」へのアクセス
- **ビルダーパターン** のような、自身を返すメソッドチェーン
- **標準ライブラリ**（`list.stream().filter(...).map(...).collect(...)`）

デメテルの法則は **「振る舞いを持つオブジェクトの内部をたどってはいけない」** という趣旨なので、振る舞いを持たないデータだけの構造には厳しく適用しなくてOKです。

---

## まとめ

- **知り合いの知り合いとは話さない**
- 自分が **直接触れる相手** にだけ話しかける
- 深いメソッドチェーンは **「頼む」形** に書き直す
- データの入れ物（DTO）や Fluent API では例外的に許容される
