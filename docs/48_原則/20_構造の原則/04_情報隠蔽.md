# 情報隠蔽（Information Hiding）

## はじめに

プログラムを部品（モジュール）に分けるとき、**どこで分けるか** によって、その後の変更のしやすさは大きく変わります。

「処理の順番で分ける」のはとても自然ですが、実はそれだと変更に弱くなることがあります。これを 1972 年に指摘し、別の分け方を提案したのが **情報隠蔽（Information Hiding）** です。

---

## 一言でいうと

**「変わりそうな決定は、1 つのモジュールの中に隠す」**

外からは **何ができるか（インターフェース）** だけが見え、**どうやっているか（実装の詳細）** は見えないようにする原則です。

---

## 定義・背景

- **David L. Parnas** が **1972 年** の論文「On the Criteria To Be Used in Decomposing Systems into Modules」（モジュール分割の基準について）で提唱しました
- 論文では同じシステムを 2 通りに分割して比べています
  - **処理の流れ（フローチャート）の段階ごと** に分ける方法
  - **変わりそうな設計上の決定ごと** に分け、その決定を各モジュールの中に隠す方法
- 後者のほうが、データの持ち方などを変えたときに **影響が 1 つのモジュールで済む** ことを示しました

Parnas のいう「隠す」は、**秘密にする** ことではなく、**変更の影響を閉じ込める** ことです。

---

## 情報隠蔽とカプセル化の違い

よく混同されますが、焦点が違います。

| | 情報隠蔽 | カプセル化 |
|---|---|---|
| 何か | **設計の原則**（何を隠すべきか） | **言語の仕組み・技法**（データと処理をまとめ、アクセスを制限する） |
| 問い | どの決定が変わりそうか？ それをどこに閉じ込めるか？ | `private` にするか？ getter を作るか？ |
| 関係 | 目的 | 手段の 1 つ |

`private` を付けても、**変わりそうな決定がメソッド名や戻り値の形で外に漏れていれば**、情報隠蔽はできていません。

---

## 悪い例: 内部の持ち方が外に漏れている

```javascript
class ShoppingCart {
  constructor() {
    // 商品を「[商品ID, 数量] の配列」で持つ、という決定
    this.items = [];
  }
  getItems() {
    return this.items; // 内部の配列をそのまま返す
  }
}

// 使う側があちこちで内部の形を前提にしている
const cart = new ShoppingCart();
cart.getItems().push(['A001', 2]);
const count = cart.getItems().reduce((sum, [, qty]) => sum + qty, 0);
const hasA = cart.getItems().some(([id]) => id === 'A001');
```

### 何が問題か

- 「`[ID, 数量]` の配列で持つ」という **内部の決定** を、使う側全員が知っている
- これを `Map` に変えたくなったら、**呼び出し元すべて** を直す必要がある
- 外から `push` できてしまうので、**不正な状態**（数量がマイナスなど）も作れる

---

## 良い例: 決定を中に閉じ込める

```javascript
class ShoppingCart {
  #quantities = new Map(); // 持ち方は外から見えない

  add(productId, quantity) {
    if (quantity <= 0) throw new Error('数量は 1 以上');
    const current = this.#quantities.get(productId) ?? 0;
    this.#quantities.set(productId, current + quantity);
  }
  totalQuantity() {
    let sum = 0;
    for (const qty of this.#quantities.values()) sum += qty;
    return sum;
  }
  contains(productId) {
    return this.#quantities.has(productId);
  }
}

const cart = new ShoppingCart();
cart.add('A001', 2);
cart.totalQuantity();
cart.contains('A001');
```

使う側は **「追加できる」「合計数が分かる」「含まれているか分かる」** ことだけを知っています。中身を配列から `Map` に変えても、データベースに変えても、呼び出し元は変わりません。

---

## 何を隠すべきか

Parnas の考え方では、隠す対象は **「変わりそうな設計上の決定」** です。たとえば、

- **データの持ち方**（配列か Map か、どんな形式で保存するか）
- **アルゴリズム**（どの順で検索・計算するか）
- **外部とのやりとり**（どの API・どの DB を使うか）
- **ハードウェアや OS の違い**
- **業務ルールの細かい部分**（税率、割引の条件など）

逆に、**変わりにくく、使う側が本当に必要なもの** はインターフェースとして公開します。

---

## よくある誤解・やりすぎ

### 誤解1: private にすれば情報隠蔽

すべてのフィールドに getter / setter を付けて公開すると、`private` でも **中身の構造はそのまま外に漏れています**。大事なのは「何を公開するか」です。

### 誤解2: 全部隠せば隠すほどよい

使う側が必要な情報まで隠すと、**同じ情報を得るために回りくどい手順** が必要になります。DTO や設定値のような **ただのデータの入れ物** は、隠さないほうが素直なこともあります。

### 誤解3: 情報隠蔽はオブジェクト指向の話

Parnas の論文はオブジェクト指向が広まる前のものです。**関数・モジュール・パッケージ・サービス・API** など、どの単位にも当てはまります。

---

## まとめ

- **変わりそうな決定を、1 つのモジュールの中に隠す**
- Parnas が **1972 年** に、「処理の流れ」ではなく「変わりそうな決定」で分けるべきだと示した
- カプセル化は **手段**、情報隠蔽は **目的**
- getter / setter で中身をそのまま見せると、隠したことにならない
