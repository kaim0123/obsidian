# 機構と方針の分離（Separation of Mechanism and Policy）

## はじめに

「リトライ処理を書いたら、3 回・1 秒間隔で固定になっていた。別の場所では 5 回・指数的に待ちたいのに、ほぼ同じコードをもう 1 つ書く羽目になった」。

こうなる原因は、**「どうやるか」と「どうするか」が 1 つのコードに混ざっている** ことです。この 2 つを分けよう、というのが **機構と方針の分離** です。

---

## 一言でいうと

**「仕組み（どうやるか）と、決まりごと（何をどうするか）を分ける」**

- **機構（Mechanism）** … **できること** を提供する部品。例: 「繰り返し実行できる」「アクセスを許可・拒否できる」
- **方針（Policy）** … その部品を **どう使うかの判断**。例: 「3 回まで」「管理者だけ許可」

---

## 定義・背景

- **OS の設計** から生まれた考え方です。1975 年ごろ、Hydra というオペレーティングシステムの論文（Wulf らによる）で、OS のカーネルは **仕組み（機構）だけを提供し、使い方の判断（方針）はその上に任せる** という設計方針として示されました
- その後、**マイクロカーネル** の設計や、**UNIX 哲学** の文脈でも繰り返し語られています
  - 例: X Window System は「ウィンドウを描く仕組み」は提供するが、「どんな見た目・操作にするか」はウィンドウマネージャやアプリに任せる
- 現在では OS に限らず、**ライブラリ・フレームワーク・アプリケーションの設計全般** で使われる考え方です

方針は **変わりやすく**、機構は **変わりにくい**。だから分けておくと、方針だけを差し替えられます。

---

## 悪い例: 機構と方針が混ざっている

```javascript
async function fetchUserWithRetry(id) {
  // 「繰り返す仕組み」と「3 回・1 秒・ネットワークエラーのみ」という決まりが混ざっている
  for (let i = 0; i < 3; i++) {
    try {
      return await api.getUser(id);
    } catch (e) {
      if (e.name !== 'NetworkError') throw e;
      await new Promise((r) => setTimeout(r, 1000));
    }
  }
  throw new Error('リトライ上限');
}
```

### 何が問題か

- **別の API** にもリトライを付けたいと、同じ構造をコピーすることになる
- 「5 回・指数的に待つ」ような **別の決まり** にしたいとき、関数ごと書き直しになる
- 「リトライの仕組みのバグ」と「決まりの設定ミス」が **同じ場所** にあり、テストも分けにくい

---

## 良い例: 機構と方針を分ける

```javascript
// 機構: 「方針に従って繰り返す」ことだけを知っている
async function retry(task, policy) {
  for (let attempt = 1; ; attempt++) {
    try {
      return await task();
    } catch (e) {
      if (!policy.shouldRetry(e, attempt)) throw e;
      await new Promise((r) => setTimeout(r, policy.delay(attempt)));
    }
  }
}

// 方針: 回数・待ち時間・対象のエラーを決める
const networkPolicy = {
  shouldRetry: (e, attempt) => e.name === 'NetworkError' && attempt < 3,
  delay: () => 1000,
};

const backoffPolicy = {
  shouldRetry: (e, attempt) => attempt < 5,
  delay: (attempt) => 100 * 2 ** attempt, // 指数的に待つ
};

await retry(() => api.getUser(id), networkPolicy);
await retry(() => api.getOrders(id), backoffPolicy);
```

- `retry` は **何回・何秒待つかを知らない**。どの API にも使える
- 決まりごとを変えたいときは **方針のオブジェクトだけ** を差し替えればよい
- 機構と方針を **別々にテスト** できる

## 身近な例

| 例 | 機構 | 方針 |
|---|---|---|
| 並べ替え | `Array.prototype.sort` | 比較関数（何の順で並べるか） |
| 権限チェック | 「許可・拒否を判定する」仕組み | ロールごとの許可ルール |
| ログ出力 | ログを書き出す仕組み | どのレベルを・どこへ出すかの設定 |
| ファイアウォール | パケットを通す・落とす仕組み | ルール表 |
| ストラテジーパターン | 処理の枠組み（Context） | 差し替えられるアルゴリズム（Strategy） |

## よくある誤解・やりすぎ

### 誤解1: 方針は必ず設定ファイルに出すべき

方針を分けるとは、**コード上で別の場所に置く** ことです。すべてを設定ファイルや DB に出すと、かえって **何がどう動くか追いにくく** なります。変わる見込みが低いなら、コード内の定数で十分です。

### 誤解2: どんなコードも汎用の機構にすべき

1 か所でしか使わない処理まで「機構と方針」に分けると、**使われない柔軟性** が増えるだけです（YAGNI）。**方針が 2 通り以上必要になったとき** が分けどきです。

### 誤解3: 機構は方針をまったく持たない

完全に方針ゼロの機構は使いにくくなります。**よく使う方針をデフォルトとして用意しつつ、差し替えられるようにする** のが実用的です。

## まとめ

- **機構 = どうやるか（できること）**、**方針 = どうするか（決まりごと）**
- OS 設計（Hydra、マイクロカーネル）から生まれ、今は設計全般で使われる
- 方針は変わりやすいので、**機構から切り離して差し替えられる** ようにする
- 方針が 1 通りのうちは分けすぎない
