# ハリウッド原則・制御の反転（IoC）

## はじめに

自分で書くプログラムは、ふつう **自分が主役** です。必要なライブラリを自分で呼び出し、処理の順番も自分で決めます。

ところがフレームワークを使い始めると、事情が変わります。`onClick` に関数を登録しておくと、**クリックされたときにフレームワークのほうから** 呼んでくれます。自分は「呼ばれる側」になるのです。

この「呼ぶ・呼ばれる」の主導権がひっくり返る考え方を **制御の反転（Inversion of Control, IoC）**、それを標語にしたものを **ハリウッド原則** と呼びます。

---

## 一言でいうと

**「こちらから電話するな。用があればこちらから電話する（Don't call us, we'll call you.）」**

オーディションを受けた俳優に、ハリウッドの事務所が言う決まり文句が由来です。部品は自分から全体を呼びに行かず、**全体（フレームワーク）が適切なタイミングで部品を呼ぶ** ように作ります。

---

## 定義・背景

| 用語 | 意味 |
|---|---|
| 制御の反転（IoC） | 処理の流れの主導権を、自分のコードではなくフレームワーク側に持たせること |
| ハリウッド原則 | IoC を一言で言い表した標語。GoF 本（1994）の Template Method パターンの説明でも紹介されている |
| 依存性注入（DI） | IoC の一種。「使う部品を自分で `new` せず、外から渡してもらう」こと |

- 「制御の反転」という言葉は、Ralph Johnson と Brian Foote の論文「Designing Reusable Classes」（1988）でフレームワークの特徴として使われたのが早い例
- 2004 年、Martin Fowler が「IoC という言葉は広すぎる」として、部品の受け渡しに絞った呼び名 **Dependency Injection** を提案した

### ライブラリとフレームワークの違い

IoC は **ライブラリとフレームワークを分ける目印** としてよく使われます。

| | 誰が誰を呼ぶか |
|---|---|
| ライブラリ | **自分のコードが** ライブラリを呼ぶ（例: `_.sortBy(list)`） |
| フレームワーク | **フレームワークが** 自分のコードを呼ぶ（例: React がコンポーネント関数を呼ぶ） |

---

## 悪い例: 部品が全体の流れを握っている

```javascript
class ReportJob {
  run() {
    // 自分で部品を作り、自分で順番を管理している
    const db = new MySqlDatabase('prod-host');
    const rows = db.query('SELECT * FROM sales');
    const csv = rows.map(r => `${r.date},${r.amount}`).join('\n');
    const mailer = new SmtpMailer('smtp.example.com');
    mailer.send('boss@example.com', csv);
  }
}
```

- 使う DB やメール送信の手段が **クラスの中に埋め込まれていて** 差し替えられない
- テストのたびに本物の DB とメールサーバーが必要になる

---

## 良い例1: 流れは枠組みが持ち、部品は呼ばれるだけ（Template Method）

```javascript
// 流れ（取得 → 整形 → 送信）は親が握る
class Job {
  run() {
    const data = this.fetch();     // 子を「呼ぶ」のは親のほう
    const text = this.format(data);
    this.deliver(text);
  }
}

class SalesReportJob extends Job {
  fetch()        { return [{ date: '10/1', amount: 100 }]; }
  format(rows)   { return rows.map(r => `${r.date},${r.amount}`).join('\n'); }
  deliver(text)  { console.log(text); }
}

new SalesReportJob().run();
```

`SalesReportJob` は「いつ呼ばれるか」を気にせず、**呼ばれたときにやること** だけを書いています。

## 良い例2: 部品を外から渡してもらう（DI）

```javascript
class ReportJob {
  constructor(db, mailer) { // 自分で new せず、受け取る
    this.db = db;
    this.mailer = mailer;
  }
  run() {
    const rows = this.db.query('SELECT * FROM sales');
    this.mailer.send('boss@example.com', rows.map(r => `${r.date},${r.amount}`).join('\n'));
  }
}

// 組み立てはアプリの入口（Composition Root）でまとめて行う
const job = new ReportJob(new MySqlDatabase('prod-host'), new SmtpMailer('smtp.example.com'));

// テストでは偽物を渡せる
const testJob = new ReportJob({ query: () => [] }, { send: () => {} });
```

## よくある誤解

### 誤解1: 「IoC = DI」

DI は IoC の **一つの形** にすぎません。イベントハンドラー、コールバック、Template Method、プラグイン機構なども IoC です。

### 誤解2: 「IoC = DI コンテナを使うこと」

DI コンテナは組み立てを自動化する道具です。上の例のように **コンストラクタで渡すだけ（手動 DI）** でも DI は成り立ちます。小さなアプリなら手動で十分です。

### 誤解3: 「IoC = 依存性逆転の原則（DIP）」

似た名前ですが別物です。

| | 反転するもの |
|---|---|
| IoC | **処理の流れ（誰が呼ぶか）** |
| DIP | **依存の向き（どちらが抽象を持つか）** |

DI は DIP を実現する手段としてよく一緒に使われるため、混同されやすいです。

### 誤解4: 「反転させるほど良い設計」

制御を外に出しすぎると、**コードを読んでも処理の順番が見えなくなる** という副作用があります。「どこから呼ばれているのか分からない」状態は、デバッグを難しくします。

---

## まとめ

- **「呼ぶな、呼んでやる」**: 部品は呼ばれる側に徹し、流れは枠組みが持つ
- IoC はフレームワークとライブラリを分ける目印
- DI は IoC の一種で、「部品を外から渡してもらう」こと（Fowler 2004 の命名）
- IoC（流れの反転）と DIP（依存の向きの反転）は別の概念
