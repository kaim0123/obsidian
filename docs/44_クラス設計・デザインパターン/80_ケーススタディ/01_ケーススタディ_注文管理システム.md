# ケーススタディ：注文管理システム

## この章の目的

**注文管理** を題材に、要件整理からクラス設計・実装・振り返りまで一通り体験します。  
GRASP・関係・インターフェースの実践を統合します。

---

## 1. 要件の整理

### ユースケース（抜粋）

1. 顧客が商品をカートに入れる
2. カートから注文を確定する（在庫確認あり）
3. 注文をキャンセルする（確定前のみ）
4. 注文一覧を参照する

### 業務ルール

- 明細が空の注文は確定できない
- 在庫不足の場合は確定できない
- 確定後のキャンセルは別フロー（本演習では対象外）

---

## 2. クラス候補の洗い出し

| 名詞 | クラス候補 | 種類 |
|------|-----------|------|
| 顧客 | `Customer` | エンティティ |
| 商品 | `Product` | エンティティ |
| カート | `ShoppingCart` | 集約候補 |
| 注文 | `Order` | 集約ルート |
| 明細 | `OrderLine` | エンティティ/値 |
| 在庫 | `Inventory` | ドメインサービス候補 |

動詞配置: `addItem` → Cart、`confirm` → Order、`canFulfill` → Inventory。

---

## 3. GRASP で責務を分配する

| GRASP | 適用 |
|-------|------|
| Information Expert | `OrderLine.subtotal()` |
| Creator | `Order` が `OrderLine` を生成 |
| Controller | `PlaceOrderController` がユースケース窓口 |
| Low Coupling | `OrderRepository` インターフェース |
| Protected Variations | 在庫確認を `Inventory` に隔離 |

```javascript
class Order {
  confirm(inventory) {
    if (this.lines.length === 0) throw new Error('明細なし');
    if (!inventory.canFulfill(this)) throw new Error('在庫不足');
    this.status = OrderStatus.CONFIRMED;
  }
}
```

---

## 4. 関係とインターフェースの設計

```text
Customer 1 ──< * Order
Order 1 ◆─── * OrderLine
Order ..> Inventory : canFulfill
PlaceOrderController ..> OrderRepository
```

```typescript
interface OrderRepository {
  save(order: Order): void;
  findByCustomer(customerId: string): Order[];
}
```

永続化は Repository に閉じ、ドメインは DB を知りません（DIP）。

---

## 5. 実装と振り返り

### 実装の順序

1. `OrderLine`, `Money`（値オブジェクト）
2. `Order` + 単体テスト
3. `Inventory`（スタブでテスト）
4. `OrderRepository` インターフェース + メモリ実装
5. `PlaceOrderController`

### 振り返りチェック

- [ ] 貧血モデルになっていないか
- [ ] 神クラスができていないか
- [ ] テストは DB なしでドメインを検証できているか

改善案: 配送先 `Address` を値オブジェクト化、確定時に `OrderConfirmed` イベント発行。
