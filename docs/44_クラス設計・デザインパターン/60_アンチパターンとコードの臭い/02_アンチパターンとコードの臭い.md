# アンチパターンとコードの臭い

## はじめに

**デザインパターン** が「繰り返し現れる設計問題の、良い解き方」なのに対し、**アンチパターン（Anti-Pattern）** は **「一見よさそうだが、実は悪い結果を生む解き方」** です。

良いパターンもアンチパターンも、**見た目はよく似ていることがあります**。大事なのは、**コードの形ではなく、意図と結果** を見極めることです。

---

## なぜアンチパターンを学ぶのか

1. **やらかしを避けるため**
2. **「これパターンっぽいな」と思っても、実はアンチパターンだった** ということを防ぐため
3. **他人のコードレビューで根拠を持って指摘** できるようになるため

---

## 代表的なアンチパターン

### 1. God Object（神オブジェクト）

**1つのクラスが全てを知っている** 状態。`UserManager` や `AppController` のような巨大クラス。

```javascript
// ❌ 神オブジェクト
class AppController {
  login() {}
  logout() {}
  register() {}
  sendEmail() {}
  processPayment() {}
  generateReport() {}
  backupDatabase() {}
  // ...さらに50メソッド
}
```

**SRP違反**。責任を分割するのが正解。

### 2. Spaghetti Code（スパゲッティコード）

**制御の流れが入り組んで** 追えないコード。`goto`・深いネスト・多数のグローバル変数などが原因。

### 3. Magic Number / Magic String

意味不明な数値・文字列が直書き。

```javascript
if (user.role === 3) { /* 3って何？ */ }
if (status === 'AA23X') { /* 何これ？ */ }
```

→ 定数化・enum化する。

### 4. Copy & Paste Programming

同じようなコードをコピペで増やす。DRY違反。

### 5. Premature Optimization（早すぎる最適化）

**計測せずに「速そうだから」という理由で難しいコードを書く**。たいていは読みにくくなるだけで、本当のボトルネックは別の場所にある。

> 「早すぎる最適化は諸悪の根源である」 — ドナルド・クヌース

### 6. Over Engineering（過剰設計）

**将来のための拡張性** や **万能な抽象化** を求めすぎて、今必要なものまで見えなくなる。YAGNI違反。

```javascript
// ❌ Hello World にファクトリーと戦略を盛り込む
class GreetingStrategyFactory { /* ... */ }
class JapaneseGreetingStrategy { /* ... */ }
// 本来は console.log('こんにちは') で済む
```

### 7. Anemic Domain Model（貧血ドメインモデル）

**ドメインオブジェクトが単なるデータの入れ物になっていて、振る舞いが外のサービスクラスに全て書かれている** 状態。

```javascript
// ❌ データだけのUser
class User {
  constructor(email, password) { this.email = email; this.password = password; }
}

// 処理は全部ここ
class UserService {
  validateEmail(user) { /* ... */ }
  hashPassword(user) { /* ... */ }
  canLogin(user) { /* ... */ }
}
```

カプセル化の意義が失われる。

### 8. Singleton の誤用

**グローバル変数の置き換え** としてSingletonを乱用すると、テストが難しくなり、依存関係が見えなくなる。

### 9. Yo-Yo Problem

継承階層が深すぎて、**1つのメソッドの挙動を理解するのに何階層も上下に行き来** する必要がある状態。

### 10. Dead Code（デッドコード）

使われていないコード。「念のため残しておく」が溜まると、読むコストばかり増える。Gitに残して削除するのが正解。

## 良いパターンとアンチパターンの見分け方

### Singleton vs グローバル変数置き場

- 良い使い方: 本当に1つしかあってはいけないもの（ハードウェア制御など）
- アンチパターン: 単にどこからでもアクセスしたいから使う

### Strategy vs 過剰抽象化

- 良い使い方: 本当にアルゴリズムを差し替える必要がある
- アンチパターン: 1種類しか実装がないのに抽象化している

### Factory vs 新規関数の濫用

- 良い使い方: 作るクラスを条件で切り替える必要がある
- アンチパターン: `new Foo()` で済むものに Factory を噛ませる

### Observer vs カプセル化破り

- 良い使い方: 疎結合に通知する
- アンチパターン: 大量のリスナーが相互に依存し、結局追跡不能になる

## 判断基準

1. **今、本当にそれが必要か？**（YAGNI）
2. **パターンなしで書いたコードより、読みやすくなっているか？**
3. **テストしやすくなっているか？**
4. **将来の仕様変更に対して、変更範囲が狭くなるか？**

これらに **自信を持ってYes** と言えないなら、パターンを外すほうが良いことが多いです。

---

## コードの「匂い」（Code Smell）

アンチパターンに陥る一歩手前のサインを **コードの匂い（Code Smell）** と呼びます。Martin Fowler 『リファクタリング』に多数紹介されています。

| 匂い | 説明 |
|------|------|
| Long Method | 関数が長すぎる |
| Large Class | クラスが大きすぎる |
| Long Parameter List | 引数が多すぎる |
| Duplicate Code | 重複 |
| Feature Envy | 他のクラスのデータばかり触る |
| Data Clump | 同じ引数群が何度も登場 |
| Shotgun Surgery | 1つの変更が多くの場所に影響 |
| Divergent Change | 1つのクラスが複数の理由で変わる |

匂いを見つけたら、**リファクタリングで適切なパターンに置き換える** のが定石です。

---

## パターンを使わない勇気

- **問題がないのに使わない**（YAGNI）
- **1つしか実装がないのに抽象化しない**
- **読みにくくなるならパターンを外す**

「パターンを使った」こと自体は価値ではありません。**問題を解いているかどうか** がすべてです。
