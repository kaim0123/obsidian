# クラス設計 — 西暦順でたどる

## このノートの目的

**クラス設計** とは、モジュールの **中身** を **クラス（型・オブジェクト）** 単位に分け、**責任の置き場所**・**状態の隠蔽**・**変更に強い関係** を整えることです。

[[MOC_ソフトウェア設計体系|設計]] の比喩で言えば、モジュール設計が「部屋の役割分担」なら、クラス設計は **「家具の配置と、家具同士のつなぎ方」** に相当します。

このノートでは、クラス設計の考え方を **登場が早い順（おおよその西暦）** に並べ、次の流れで整理します。

1. **その前に、どんな課題があったか**
2. **何を提案したか**
3. **どう解決したか**
4. **向いている場面・限界**

モジュール設計（パッケージ・レイヤー）との重なりは [[00_モジュール設計の変遷]] を参照。ここでは **1 クラス〜少数クラスの組** に焦点を当てます。

---

## 全体の流れ（年表）

| 順番 | 考え方・手法 | 登場時期 | 一言で言うと | 主に解決した課題 |
|------|-------------|----------|-------------|-----------------|
| 0 | **手続き + 分離されたデータ** | 1950〜1960年代 | データと処理を別に書く | 巨大 `main`・goto 地獄 |
| 1 | **オブジェクト・クラス** | 1967年〜 | 状態と振る舞いを一体化 | データと手続きの乖離 |
| 2 | **カプセル化・抽象データ型** | 1960年代後半〜1970年代 | 内部を隠し操作だけ公開 | 生データへの直接アクセス |
| 3 | **情報隠蔽（Parnas）** | 1972年 | 設計判断ごとに隠す | 実装変更の波及 |
| 4 | **高凝集・低結合** | 1968〜1974年 | まとまりよく、ゆるくつなぐ | クラス分割の物差しがない |
| 5 | **継承と多態** | 1970〜1980年代 | is-a で共通部分を再利用 | コード重複・型の差し替え |
| 6 | **リスコフ置換（LSP）** | 1987年 | 子は親の代わりになれる | 継承の誤用・振る舞いの破綻 |
| 7 | **開放閉鎖（OCP）** | 1988年 | 拡張に開き、変更に閉じる | 条件分岐の肥大化 |
| 8 | **デメテルの法則** | 1988年 | 知り合いの知り合いと話さない | オブジェクトチェーンの結合 |
| 9 | **デザインパターン（GoF）** | 1994年 | 定番問題の定番の解 | 同じ設計問題の再発明 |
| 10 | **GRASP** | 1997年 | 責任をどのクラスに置くか | 「この処理、どこに書く？」 |
| 11 | **SOLID** | 1990年代〜2000年代初頭 | 変更に強いクラスの 5 原則 | 肥大化・結合・拡張困難 |

## 0. その前：手続き + 分離されたデータ（1950〜1960年代）

クラスという概念が確立する前、プログラムは **手続き（関数）** と **データ構造（レコード・配列）** を **別々に** 定義していました。

### よく起きていた課題

- **データと処理が別モジュール** に散らばり、変更時に両方を追う必要がある
- **グローバル変数** がどこからでも書き換えられ、整合性が保てない
- 同じデータ構造に触る手続きが増えると、**変更の影響範囲** が読めなくなる
- 現実世界の「もの」（注文、顧客、口座）を **手続きの集合** として表現しにくい

### 次の時代への問い

> **「データと、それを扱う処理を、どうひとまとめにして設計するか？」**

この問いが、クラス設計の出発点になりました。

→ 背景: [[00_ソフトウェア設計の変遷#1. 手続き指向（1950年代〜）]]

---

## 1. オブジェクト・クラス（1967年〜）

**背景:** Simula（1967）、Smalltalk（1972）、C++（1983）、Java（1995）  
**一言:** **状態（データ）と振る舞い（メソッド）** をひとまとめにした **オブジェクト** を設計の中心に  
**詳細:** [[02_クラスとオブジェクト]]

### その前の課題 — データと手続きの乖離

- `struct Customer` と `updateCustomer()`、`validateCustomer()` が **別ファイル・別名前空間** に存在
- 「顧客の残高を更新する」処理が **10 か所** に散らばり、ルール変更のたびに漏れが出る
- 同じ形のデータを **コピペ** し、修正漏れが発生
- ドメインの概念を **型として表現** できず、コメントと命名だけに頼る

### 何を提案したか

**クラス = 設計図**、**オブジェクト = 実物** というモデルで、関連する状態と振る舞いを **1 つの単位** にまとめる。

```javascript
class Customer {
  constructor(name, balance) {
    this.name = name;
    this.balance = balance;
  }

  withdraw(amount) {
    if (amount > this.balance) throw new Error('残高不足');
    this.balance -= amount;
  }
}
```

| 概念 | 役割 |
|------|------|
| **クラス** | オブジェクトの設計図（型） |
| **オブジェクト** | クラスから作られた実体（インスタンス） |
| **メッセージ** | オブジェクト同士が命令ではなく「お願い」で協調する |

### どう解決したか

- データとそれを操作する処理が **同じクラス内** に収まり、変更の入口が明確になる
- 現実世界の「もの」を **型として直接モデル** できる
- オブジェクトの **境界** で副作用を局所化できる

### 向いている場面・限界

- **向く:** 状態を持つドメイン概念、GUI 部品、リソース管理
- **限界:** 内部状態を **直接公開** すると再びグローバル変数と同じ問題 → カプセル化へ

## 2. カプセル化・抽象データ型（1960年代後半〜1970年代）

**背景:** Hoare、Liskov らの抽象データ型（ADT）研究、Smalltalk のメッセージング  
**一言:** 内部状態を **隠し**、決められた **操作だけ** 外部に公開する  
**詳細:** [[02_クラスとオブジェクト#カプセル化（Encapsulation）]]

### その前の課題 — 生データへの直接アクセス

- `customer.balance = -100` のように **外部から内部状態を直接書き換え** られる
- バリデーションや不変条件（残高 ≥ 0 など）を **呼び出し側すべて** に書く必要がある
- 内部表現（配列 vs 連結リスト）を変えると、**データに触るすべてのコード** を修正する
- 「何が公開 API か」がコード上で **区別できない**

### 何を提案したか

**カプセル化（Encapsulation）:** データと処理をまとめるだけでなく、**外部から見えない部分（private）** と **公開する部分（public）** を分ける。

```javascript
class BankAccount {
  #balance = 0; // 外部から直接触れない

  deposit(amount) {
    if (amount <= 0) throw new Error('正の金額のみ');
    this.#balance += amount;
  }

  getBalance() {
    return this.#balance; // 読み取りだけ許可
  }
}
```

**抽象データ型（ADT）:** 「スタック」「キュー」のように、**内部表現は隠し、push/pop などの操作だけ** を契約として公開する。

### どう解決したか

- **不変条件** をクラス内部に閉じ込め、呼び出し側の責任を減らす
- 内部表現を変えても **公開 API が同じ** なら外部コードは変更不要
- 後の **情報隠蔽・DIP・リポジトリ** の実装基盤になる

### 向いている場面・限界

- **向く:** すべてのクラス設計の **基本**。ドメインルールを 1 か所に集約したいとき
- **限界:** getter/setter だけの「カプセル化」は **貧血モデル** になりうる → DDD へ

## 3. 情報隠蔽 — Parnas（1972年）

**提唱:** David L. Parnas（*On the Criteria To Be Used in Decomposing Systems into Modules*）  
**一言:** **設計判断（design decision）** ごとに隠す  
**詳細:** [[00_モジュール設計の変遷#2. 情報隠蔽 — Parnas モジュール（1972年）]]、[[04_インターフェースと抽象化]]

### その前の課題 — 実装変更の波及

- クラス内部の表現（`price` を整数セントで持つ vs 小数で持つ）を変えると、**そのフィールドに触るすべてのクラス** が壊れる
- 「処理の流れ順」でクラスを分けると、**1 つの設計判断が複数クラスに散らばる**
- 内部の詳細が public になると、**変更できない契約** として固定される

### 何を提案したか

| 分割の軸 | 従来（悪い例） | Parnas の提案 |
|---------|--------------|--------------|
| 基準 | 処理の流れ順 | **設計判断・変更理由** |
| クラスの中身 | 処理ステップの塊 | **1 つの秘密（secret）** を持つ塊 |
| 外部との接触 | 内部データを直接触る | **インターフェース（契約）** だけ公開 |

```
  クラス A                         クラス B
  ┌─────────────┐                 ┌─────────────┐
  │  秘密（内部）  │                 │  秘密（内部）  │
  │  ─────────  │  公開メソッドのみ  │  ─────────  │
  │  実装の詳細   │ ←────────────→ │  実装の詳細   │
  └─────────────┘                 └─────────────┘
```

### どう解決したか

- **情報隠蔽（Information Hiding）:** 変更されうる詳細をクラス内部に閉じ込める
- 外部は **「何ができるか」** だけ知ればよい
- カプセル化を **「なぜ隠すか」** まで含めた設計原則に昇格させた

### 向いている場面・限界

- **向く:** クラス設計の **思想的根底**。永続化方式・アルゴリズム・外部 API の差し替え
- **限界:** 何を「秘密」にするかの判断は別問題 → 高凝集・低結合・GRASP が必要

## 4. 高凝集・低結合（1968〜1974年）

**提唱:** Larry L. Constantine, Wayne Stevens, Glenford Myers（*Structured Design*, 1974年）  
**一言:** クラス内は **まとまりよく**、クラス間は **ゆるやかに**  
**詳細:** [[03_疎結合と高凝集]]、[[00_設計原則の変遷#2. 高凝集・低結合]]

### その前の課題 — クラス分割の物差しがない

- クラスは作れるようになったが、**「この分け方、良いの？」** を客観的に語れない
- 関係のない責任が 1 クラスに混在（**低凝集**）— `User` が DB 保存・メール送信・HTML 生成まで担当
- クラス同士が **内部を直接触り合う**（**高結合**）— 1 か所の変更が連鎖する
- 「とりあえず 1 ファイル 1 クラス」だけでは **設計の質** が上がらない

### 何を提案したか

| 指標 | 意味 | クラス設計での目標 |
|------|------|------------------|
| **高凝集** | クラス内の要素が **同じ理由で変わる** | 1 つの概念・責任に集中 |
| **低結合** | クラス間の依存が **少なく、ゆるい** | インターフェース経由、必要最小限の知識 |

```text
  低凝集（悪い）              高凝集（良い）
  ┌──────────────┐          ┌─────┐ ┌─────┐ ┌─────┐
  │ User         │          │User │ │Repo │ │Mail │
  │ save()       │          └─────┘ └─────┘ └─────┘
  │ sendEmail()  │
  │ render()     │
  └──────────────┘
```

### どう解決したか

- クラス分割の **良し悪しを測る物差し** を提供
- 後の **SRP（単一責任）** の思想的背景
- モジュール設計と **同じ指標** がクラスレベルにも適用できることを示した

### 向いている場面・限界

- **向く:** リファクタリングの判断、コードレビューの共通言語
- **限界:** 物差しはあるが **具体的な分け方の手順** は別 → GRASP、SOLID へ

## 5. 継承と多態（1970〜1980年代）

**背景:** Smalltalk、C++（1983）、Eiffel  
**一言:** **is-a** で共通部分を再利用し、**同じ型として差し替え** 可能に  
**詳細:** [[03_継承と合成]]、[[04_多態とインターフェース]]

### その前の課題 — コード重複と型の差し替え

- `Dog.eat()` と `Cat.eat()` が **ほぼ同じ実装** を重複する
- 種類ごとに `if (type === 'dog')` … と **条件分岐** が増殖する
- 共通の **振る舞いの集合** を型として扱えず、配列に別型を混在させにくい
- 新しい種類を追加するたび **既存コードを修正** する必要がある

### 何を提案したか

| 概念 | 関係 | 役割 |
|------|------|------|
| **継承（Inheritance）** | is-a（〜の一種） | 親クラスの性質を子が受け継ぐ |
| **多態（Polymorphism）** | 同じインターフェース | 呼び出し側は具体型を知らずに使える |

```javascript
class Animal {
  eat() { console.log('食べる'); }
}

class Dog extends Animal {
  bark() { console.log('わん'); }
}

function feed(animal) {
  animal.eat(); // Dog でも Cat でも同じ呼び方
}
```

### どう解決したか

- 共通コードを **基底クラス** に集約し、重複を削減
- **多態** により、呼び出し側を具体実装から切り離せる
- 後の **OCP・LSP・Strategy パターン** の基盤になる

### 向いている場面・限界

- **向く:** 明確な is-a 関係、フレームワークの拡張ポイント（テンプレートメソッド）
- **限界:** 継承の乱用で **クラス階層が複雑化**、親の変更が子全体に波及 → LSP、合成（委譲）へ

## 6. リスコフ置換原則 — LSP（1987年）

**提唱:** Barbara Liskov（*Data Abstraction and Hierarchy*, 1987年）  
**一言:** **子クラスは親クラスの代わりに使っても** プログラムが壊れない  
**詳細:** [[03_LSP (リスコフの置換原則)]]

### その前の課題 — 継承の誤用・振る舞いの破綻

- 「正方形は長方形の一種」なので `Square extends Rectangle` としたが、**幅と高さを独立に設定** できなくなり、呼び出し側が壊れる
- 子クラスが親のメソッドを **空実装や例外** で上書きし、多態が機能しない
- 見かけ上 is-a でも **振る舞いの契約** が親と異なる
- 継承階層が **「型チェックは通るが実行時に破綻」** する温床になる

### 何を提案したか

**リスコフ置換原則（LSP）:** 親型 `S` のオブジェクトを、子型 `T` のオブジェクトに置き換えても、**プログラムの正当性** が保たれること。

```javascript
// LSP 違反の典型: 正方形は長方形のサブタイプになれない
class Rectangle {
  setWidth(w) { this.w = w; }
  setHeight(h) { this.h = h; }
}

class Square extends Rectangle {
  setWidth(w) { this.w = this.h = w; } // 親の契約を破る
}
```

### どう解決したか

- 継承を **「名前の一致」ではなく「振る舞いの契約」** で判断する基準を与えた
- 多態が **安全に機能するための前提条件** を明示
- SOLID の **L** として、OCP とセットで継承設計を評価できるようになった

### 向いている場面・限界

- **向く:** 継承階層のレビュー、抽象クラス・インターフェース設計
- **限界:** is-a が成り立たない場合は **合成（has-a）** を選ぶ → GoF「継承より合成」へ

## 7. 開放閉鎖の原則 — OCP（1988年）

**提唱:** Bertrand Meyer（*Object-Oriented Software Construction*, 1988年）  
**一言:** **拡張には開き**、**変更には閉じる**  
**詳細:** [[02_OCP (開放閉鎖の原則)]]

### その前の課題 — 条件分岐の肥大化

- 商品種別が増えるたび `calcPrice()` の **if-else を修正** する
- 割引ルール・税率・通貨が増えると **1 つの関数が巨大化** する
- 新機能追加のたび **既存の動作しているコード** に手を入れ、リグレッションが起きる
- 多態は使えるが、**設計の意図として拡張点が明示** されていない

### 何を提案したか

**開放閉鎖の原則（OCP）:** ソフトウェアの実体（クラス・モジュール）は、**拡張に対しては開いて** いるべきだが、**修正に対しては閉じて** いるべきである。

```javascript
// 拡張: 新クラスを追加するだけ
class Book {
  calcPrice() { return this.price * 0.9; }
}
class Food {
  calcPrice() { return this.price * 0.95; }
}
// calcPrice() の呼び出し側は変更不要
```

### どう解決したか

- **抽象（インターフェース・抽象クラス）** を拡張点として設計する指針
- 多態の **設計上の目的** を「変更コストの削減」と結びつけた
- Strategy、Template Method など **デザインパターン** の理論的背景

### 向いている場面・限界

- **向く:** ルール・算法・出力形式が **将来増える** と分かっている箇所
- **限界:** すべてを抽象化すると **過剰設計** → YAGNI とバランス

---

## 8. デメテルの法則（1988年）

**提唱:** Ian Holland, Karl Lieberman ら（*Object-Oriented Programming: An Objective Sense of Style*, 1988年）  
**一言:** **知り合いの知り合いと話さない**（最小知識の原則）  
**詳細:** [[02_デメテルの法則]]

### その前の課題 — オブジェクトチェーンの結合

- `order.getCustomer().getAddress().getCity().getName()` のように **内部構造をたどる** コードが増える
- 住所の内部表現（`City` オブジェクト vs 文字列）を変えると、**たどる側すべて** が壊れる
- 1 クラスが **多数のクラスの内部** を知り、変更に弱い **高結合** になる
- 「Tell, Don't Ask（頼め、聞くな）」の反面教師となるコード

### 何を提案したか

**デメテルの法則（Law of Demeter）:** メソッド内から呼んでよいのは、**自分・引数・自分のフィールド・自分が作ったオブジェクト** のメソッドだけ。

```javascript
// 悪い: 内部構造をたどる
const city = order.getCustomer().getAddress().getCity();

// 良い: 相手に頼む（Tell, Don't Ask）
const city = order.getShippingCity();
```

### どう解決したか

- クラス間の **知識の量を最小化** し、結合度を下げる
- **ラッパーメソッド** や **委譲** で、内部構造の変更を局所化
- 高凝集・低結合を **クラス間の呼び出し** レベルで具体化

### 向いている場面・限界

- **向く:** ドメインモデルの連鎖呼び出し、DTO 以外の深い getter チェーン
- **限界:** 単純なデータ取得（Fluent API）では **過剰** になりうる。意図的なビルダーは例外

---

## 9. デザインパターン — GoF（1994年）

**提唱:** Gamma, Helm, Johnson, Vlissides（*Design Patterns*, 1994年）  
**一言:** **繰り返し現れる設計問題** の **定番の解** を名前付きで体系化  
**詳細:** [[02_デザインパターンの概要]]

### その前の課題 — 同じ設計問題の再発明

- 「算法を差し替えたい」「生成処理を隠したい」など **同じ問題** を毎回ゼロから設計する
- 継承ばかり使い **クラス階層が爆発** する（継承の乱用）
- 良い設計と悪い設計の **共通語彙** がなく、チーム内で議論しにくい
- OCP を **どう具体化するか** の実例が不足

### 何を提案したか

23 の **デザインパターン** を生成・構造・振る舞いに分類。クラス設計で特に重要なメッセージ:

| メッセージ | 内容 |
|-----------|------|
| **継承より合成（委譲）を favor** | has-a で機能を組み合わせ、is-a 階層を浅く保つ |
| **Strategy** | 算法をクラスとして差し替え（OCP の定番形） |
| **Factory** | 生成の詳細を隠す（情報隠蔽の定番形） |
| **Observer** | 変更通知を疎結合に |

```javascript
// 継承より合成: Strategy
class Order {
  constructor(pricingStrategy) {
    this.pricingStrategy = pricingStrategy;
  }
  total() {
    return this.pricingStrategy.calc(this.items);
  }
}
```

### どう解決したか

- クラス設計の **再利用可能な語彙** を提供
- 「継承より委譲」が **ベストプラクティス** として広まった
- SOLID・GRASP と **相互に参照** できる設計カタログになった

### 向いている場面・限界

- **向く:** 拡張点が明確な問題、チーム内の設計議論
- **限界:** 問題がないのにパターンを **当てはめると過剰設計** → [[02_アンチパターンとコードの臭い]]

---

## 10. GRASP（1997年）

**提唱:** Craig Larman（*Applying UML and Patterns*, 1997年）  
**一言:** **責任をどのクラスに割り当てるか** の 9 原則  
**詳細:** （本リポジトリ内に専章なし — 以下に要点）

### その前の課題 — 「この処理、どこに書く？」

- 高凝集・低結合は **物差し** だが、**具体的な割り当て手順** がない
- 「コントローラに全部書く」「サービスクラスに逃がす」など **場当たり的** な配置
- 初学者は **データクラス + 巨大サービス** に陥りやすい
- UML で図は書けるが、**クラス責任の根拠** を説明できない

### 何を提案したか

**GRASP（General Responsibility Assignment Software Patterns）** — 9 つの責任割り当てパターン:

| 原則 | 一言 | 典型例 |
|------|------|--------|
| **Information Expert** | 情報を持つクラスが処理する | 注文合計は `Order` が計算 |
| **Creator** | 作成責任を適切なクラスに | `Order` が `OrderLine` を作る |
| **Controller** | システムイベントの最初の受け手 | `PlaceOrderController` |
| **Low Coupling** | 依存を少なく | インターフェース経由 |
| **High Cohesion** | 関連する責任だけ | 1 概念 1 クラス |
| **Polymorphism** | 型で振る舞いを分岐 | Strategy 的な多態 |
| **Pure Fabrication** | ドメインにないが必要なクラス | `OrderRepository` |
| **Indirection** | 中間者で結合を下げる | Facade、Mediator |
| **Protected Variations** | 変わりやすい点を保護 | OCP・抽象化 |

### どう解決したか

- 「**誰がこの責任を持つべきか**」を **チェックリスト** で判断できる
- Information Expert → **SRP**、Protected Variations → **OCP/DIP** へ自然に接続
- SOLID の **前段階** として、初学者向けの **実践的な割り当て指針** になった

### 向いている場面・限界

- **向く:** ユースケース実装時のクラス分担、設計レビュー
- **限界:** 大規模ドメインでは **集約・BC** など DDD の概念と組み合わせが必要

## 11. SOLID（1990年代〜2000年代初頭）

**提唱:** Robert C. Martin ら（各原則は 1987〜1990年代、**SOLID** という名称は 2000年代初頭に普及）  
**一言:** 変更に強いクラス設計の **5 原則**  
**詳細:** [[05_SOLIDとの関係]]、[[01_SRP（単一責任の原則）]]

### その前の課題 — 肥大化・結合・拡張困難

- 1 クラスに **複数の変更理由** が混在（SRP 違反）
- 新機能のたび **既存クラスを直接修正**（OCP 違反）
- 継承階層が **振る舞いの契約を破る**（LSP 違反）
- **巨大インターフェース** により未使用メソッドの実装を強いる（ISP 違反）
- 上位クラスが **具体クラス（MySQL、SendGrid）** に直接依存（DIP 違反）

### 何を提案したか

| 記号 | 名称 | 主に解決する課題 |
|------|------|-----------------|
| **S** | Single Responsibility | 1 クラス 1 責任 |
| **O** | Open-Closed | 拡張で増やし、修正を避ける |
| **L** | Liskov Substitution | 継承の正当性 |
| **I** | Interface Segregation | 小さなインターフェース |
| **D** | Dependency Inversion | 抽象に依存する |

```typescript
// DIP: 具体ではなく抽象に依存
interface OrderRepository {
  save(order: Order): void;
}

class PlaceOrderService {
  constructor(private repo: OrderRepository) {}
}
```

### どう解決したか

- 1960〜1990年代に **個別に提唱** された原則を **1 つの語彙（SOLID）** にまとめた
- OOP の 3 要素（カプセル化・継承・多態）と **設計判断** を結びつける **物差し** になった
- テスト容易性・DI（依存性注入）文化の **共通言語** になった

### 向いている場面・限界

- **向く:** 中長期保守するクラス、フレームワークに依存しないドメイン層
- **限界:** 原則の **形式だけ守る** とインターフェース爆発・過剰抽象化 → 実際の変更理由で判断

## 12. DDD — Entity / Value Object（2003年）

**提唱:** Eric Evans（*Domain-Driven Design*, 2003年）  
**一言:** 業務上の **「もの」** を **エンティティ** と **値オブジェクト** に分けてモデル化  
**詳細:** [[03_エンティティと値オブジェクト]]、[[02_集約とエンティティと値オブジェクトとドメインイベント]]

### その前の課題 — 貧血モデル・ルールの散在

- クラスはあるが **getter/setter だけ** で、ロジックは `OrderService` に集中（**貧血ドメインモデル**）
- 「同じ値なら同じもの」か「ID で区別するもの」かが **型で表現されない**
- 金額・住所・期間など **値のルール**（負の金額禁止など）が **あちこちに散在**
- DB テーブル構造に引っ張られ、**業務の言葉とクラス名がズレる**

### 何を提案したか

| 種類 | 識別 | 典型例 | クラス設計での役割 |
|------|------|--------|------------------|
| **Entity（エンティティ）** | **ID** で同一性 | `Order`, `Customer` | ライフサイクル・状態遷移 |
| **Value Object（値オブジェクト）** | **値** で同一性 | `Money`, `Address` | 不変・ルールの封入 |

```typescript
class Money {
  constructor(
    public readonly amount: number,
    public readonly currency: string
  ) {
    if (amount < 0) throw new Error('金額は負にできない');
  }

  add(other: Money): Money {
    return new Money(this.amount + other.amount, this.currency);
  }
}
```

### どう解決したか

- **ルールの置き場所** を型で明示（Information Expert のドメイン版）
- 値オブジェクトの **不変性** で、関数型の考え方と **組み合わせ可能**
- 集約（Aggregate）と合わせ、**整合性の境界** をクラス設計に組み込める

### 向いている場面・限界

- **向く:** 業務ルールが複雑、ドメインエキスパートと協調するプロジェクト
- **限界:** 単純 CRUD には **過剰**。境界づけられたコンテキスト（モジュール設計）と **セット** で効く

## 13. まとめ — 歴史は「課題の積み重ね」

```text
手続き + 分離データ（データと処理が別）
    ↓ 状態と振る舞いを一体化
  オブジェクト・クラス（Simula 1967〜）
    ↓ 内部を隠し操作だけ公開
  カプセル化・抽象データ型
    ↓ 設計判断ごとに隠す
  情報隠蔽（Parnas, 1972）
    ↓ 良し悪しを測る物差し
  高凝集・低結合（1974）
    ↓ is-a・同じ型として差し替え
  継承と多態（1970s〜）
    ↓ 継承の契約を守る
  リスコフ置換（LSP, 1987）
    ↓ 拡張で増やし修正を避ける
  開放閉鎖（OCP, 1988）
    ↓ 知識を最小限に
  デメテルの法則（1988）
    ↓ 定番問題の定番の解
  デザインパターン（GoF, 1994）— 継承より合成
    ↓ 責任の割り当て手順
  GRASP（1997）
    ↓ 5 原則に体系化
  SOLID（1990s〜2000s）
    ↓ 業務の「もの」を型で表現
  Entity / Value Object（DDD, 2003）
```

### 初心者が覚えておくとよいこと

1. **カプセル化と情報隠蔽が根っこ。** 内部を隠し、契約だけ公開する — 1970年代から変わっていない。
2. **継承は万能ではない。** GoF（1994）以降、**合成（委譲）** が第一選択肢になりやすい。
3. **物差しは複数ある。** 高凝集・低結合 → GRASP → SOLID は **補完関係**。矛盾するときは **変更理由** で判断。
4. **モジュール設計とセット。** クラスがきれいでも BC を越えると破綻する → [[00_モジュール設計の変遷]] と [[02_DDDとは]] を併読。

### 学習順 vs 歴史順

| 観点 | おすすめ順 | 理由 |
|------|-----------|------|
| **歴史（本ノート）** | OOP → カプセル化 → … → DDD | 課題が **なぜ生まれたか** が分かる |
| **学習** | OOP → GRASP → SOLID → パターン → DDD | **手順と物差し** を先に持ったほうが書きやすい |
