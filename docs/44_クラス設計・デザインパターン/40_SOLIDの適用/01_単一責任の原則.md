# 単一責任の原則（SRP）

> この章は「クラス設計でどう使うか」を扱います。原則そのものの説明は 48 の [[01_SRP（単一責任の原則）]] を参照してください。

## この章の目的

SOLID の第一原則 **単一責任の原則（SRP）** をクラス設計の観点で学びます。  
責務の見つけ方、神クラスの問題、分割手順と限界まで押さえます。

---

## 1. 「1クラス1責務」とは何か

SRP は「クラスは **変化の理由が1つ** であるべき」という原則です。  
初心者向けには **「1クラス1責務」** と説明することも多いですが、正確には **「変化の軸が1つ」** です。

| 誤解 | 正しい理解 |
|------|-----------|
| メソッドは1つだけ | 関連する複数メソッドは1責務になりうる |
| クラスは小さければよい | 責務のまとまりが大事 |
| ファイルは1つ | 責務の単位とファイルは別問題 |

```text
  Order クラスの責務（例）
  ─────────────────────
  ・注文の状態管理
  ・明細の追加・削除
  ・合計金額の計算
  → いずれも「注文」という変化の理由
```

---

## 2. 責務の見つけ方（変化の理由で分ける）

責務は **「なぜこのクラスを変更するか」** から見つけます。

1. クラス名を書く（例: `UserService`）
2. 「変更理由」を列挙する
   - 認証方式の変更
   - メールテンプレートの変更
   - レポート形式の変更
3. 理由が複数なら **分割候補**

| クラス | 変化の理由 | 分割案 |
|--------|-----------|--------|
| `UserService` | 認証・プロフィール・通知 | `Authenticator`, `Profile`, `Notifier` |

[[05_SOLIDとの関係]] も参照。

---

## 3. 神クラス（God Class）の問題

**神クラス** は、システムのあらゆる処理を抱えた巨大クラスです。

```javascript
class Application {
  login() { }
  createOrder() { }
  sendEmail() { }
  exportCsv() { }
  calculateTax() { }
  // … 数千行
}
```

| 問題 | 影響 |
|------|------|
| 変更の連鎖 | どこを直しても壊れる |
| テスト困難 | モックだらけ・実行が重い |
| チーム衝突 | 同じファイルを全員が触る |

神クラスは [[01_アンチパターンとの見分け]] でも扱います。

---

## 4. 責務を分割する実践手順

1. **変更理由をリストアップ** する
2. **グループ化** — 関連する理由をまとめる
3. **新クラスを命名** — 責務が名前に表れるように
4. **Extract Class** — フィールドとメソッドを移動
5. **呼び出し側を更新** — 新クラスへ委譲
6. **テストで確認**

```text
  UserService
      │
      ├─ Extract → Authenticator（認証）
      ├─ Extract → ProfileService（プロフィール）
      └─ Extract → Notifier（通知）
```

リファクタリングの詳細は [[02_変更に強いクラス設計の実践]] を参照。

---

## 5. SRP の限界と判断のコツ

| 状況 | 判断 |
|------|------|
| 小さなスクリプト | 過剰分割は避ける（YAGNI） |
| 密接に関連する処理 | 無理に分けない |
| 変化の頻度が違う | 積極的に分ける |

**「変化の理由が複数あるか」** を問い、Yes なら分割を検討します。  
完璧な1責務より、**変更の影響が読める** ことが目的です。

---

## まとめ

- SRP = 変化の理由を1つに（1クラス1責務の実体）
- 変更理由の列挙が責務発見の手がかり
- 神クラスは保守・テスト・チームの障害
- Extract Class で段階的に分割
- 小さすぎる分割も避け、変化の軸で判断
