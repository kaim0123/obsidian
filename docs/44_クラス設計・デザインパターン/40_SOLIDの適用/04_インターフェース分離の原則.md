# インターフェース分離の原則（ISP）

> この章は「クラス設計でどう使うか」を扱います。原則そのものの説明は 48 の [[04_ISP (インターフェース分離の原則)]] を参照してください。

## この章の目的

**インターフェース分離の原則（ISP）** を学び、クライアントに不要な依存を課さない設計を身につけます。  
役割インターフェースと YAGNI のバランスも押さえます。

---

## 1. クライアントが使わないメソッドに依存させない

ISP: クライアントは、自分が使わないインターフェースに **依存すべきではない**。

```javascript
// 肥大インターフェース
interface Worker {
  work();
  eat();
  sleep();
}
class Robot implements Worker {
  work() { /* OK */ }
  eat() { throw new Error('ロボットは食べない'); }  // 無理
  sleep() { throw new Error('ロボットは寝ない'); }
}
```

ロボットは `work` だけ必要なのに、`eat` / `sleep` に縛られています。

---

## 2. 肥大化したインターフェースの分割

大きなインターフェースを **クライアントごとの小さな契約** に分けます。

```javascript
interface Workable { work(); }
interface Eatable { eat(); }
interface Sleepable { sleep(); }

class Human implements Workable, Eatable, Sleepable { /* */ }
class Robot implements Workable { /* */ }
```

```text
  Worker（巨大）
      ↓ 分割
  Workable / Eatable / Sleepable
```

---

## 3. 役割インターフェース（Role Interface）

**役割インターフェース** は、クラス名ではなく **役割・能力** で名前をつけます。

| 名前の付け方 | 例 |
|-------------|-----|
| クラスベース | `Printer` インターフェース |
| 役割ベース | `Printable`, `Scannable` |

```javascript
interface Notifier { notify(message): void; }
interface Persistable { save(): void; }
```

クライアントは必要な **役割だけ** を依存します。

---

## 4. ISP と YAGNI のバランス

| 極端 | 問題 |
|------|------|
| ISP 無視 | 無用なメソッド実装・空 throw |
| ISP 過剰 | インターフェースが細切れで複雑 |

**「今のクライアントが本当に使うか」** で分割を判断します。  
将来の拡張だけを理由に10個のインターフェースを作るのは YAGNI 違反です。

---

## 5. ISP の実践例

レポート出力:

```javascript
// 悪い — PDF だけ欲しいクライアントも Excel メソッドを実装させる
interface ReportExporter {
  exportPdf();
  exportExcel();
  exportCsv();
}

// 良い — 形式ごとに分離
interface PdfExporter { exportPdf(); }
interface ExcelExporter { exportExcel(); }
```

または **1メソッドの関数型**（`export(format)`）で十分な小規模では分割しすぎない。

---

## まとめ

- ISP = 使わないメソッドへの依存を避ける
- 肥大インターフェースは役割ごとに分割
- 役割インターフェースで意図を明確に
- YAGNI と両立。今のクライアント基準で判断
