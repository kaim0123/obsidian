# SOLID の統合と判断

## この章の目的

SOLID 5原則の **関係性・衝突時の優先順位・適用しすぎの回避** を学びます。  
レビュー観点とよくある違反の修正まで押さえます。

---

## 1. 5原則の関係性

| 原則 | 略称 | クラス設計での役割 |
|------|------|-------------------|
| 単一責任 | SRP | 責務の分割 |
| 開放閉鎖 | OCP | 拡張点の設計 |
| リスコフ置換 | LSP | 継承の契約 |
| インターフェース分離 | ISP | 小さな契約 |
| 依存性逆転 | DIP | 抽象への依存 |

```text
  SRP（何を分けるか）
      ↓
  OCP + LSP（どう拡張するか）
      ↓
  ISP + DIP（どうつなぐか）
```

[[05_SOLIDとの関係]] も参照。早見表は [[付録D_SOLID早見表]]。

---

## 2. 原則同士が衝突するときの優先順位

| 衝突 | 判断のヒント |
|------|-------------|
| SRP vs クラス数爆増 | 変化の理由が同じならまとめる |
| OCP vs YAGNI | 実際に来そうな変化だけ拡張点に |
| ISP vs 単純さ | クライアントが2つ以上なら分割検討 |
| DIP vs 直書き | テスト・差し替えが必要なら抽象化 |

**完璧な SOLID より、変更の影響が読めること** を優先します。

---

## 3. SOLID を適用しすぎない

| 過剰適用の兆候 | 対策 |
|---------------|------|
| 1メソッド1クラス | 凝集度を見直す |
| インターフェースだらけ | 実際のクライアント数を確認 |
| パターンの乱用 | 問題が起きてから導入 |

小規模スクリプトやプロトタイプでは、**動くものを作ってから** 原則を当てはめます。

---

## 4. レビューで見るべき SOLID のポイント

- [ ] クラスに **複数の変更理由** がないか（SRP）
- [ ] 新機能で **既存クラスを何度も直している** か（OCP）
- [ ] 継承先で **親の使い方が壊れない** か（LSP）
- [ ] 実装クラスが **空メソッド・未サポート** を返していないか（ISP）
- [ ] ドメインが **DB・フレームワークの型** を知っていないか（DIP）

---

## 5. よくある SOLID 違反と修正

| 違反 | 修正 |
|------|------|
| 5000行の `UserService` | SRP で Extract Class |
| 支払いの巨大 switch | OCP + Strategy |
| `Square extends Rectangle` | インターフェース + 別実装 |
| `implements` で10個の未使用メソッド | ISP で分割 |
| `new MySqlClient()` が散在 | DIP + コンストラクタ注入 |

---

## まとめ

- SOLID は分割・拡張・契約・接続のセット
- 原則は衝突する。変化の軸とチーム規模で判断
- 適用しすぎは複雑化。YAGNI と両立
- レビューと早見表で定着させる
