# クラス設計を学ぶ理由

## この章の目的

**なぜクラス設計を学ぶのか**を理解する章です。  
モジュール設計との違い、手続き指向からオブジェクト指向への視点の転換、クラス設計が解決する問題を押さえます。

---

## 1. モジュール設計との違い（部屋と家具の比喩）

[[MOC_モジュール設計体系]] では、パッケージやレイヤーといった **大きな区切り** を扱いました。  
クラス設計は、その区切りの **中身** を型とオブジェクトの単位で組み立てる作業です。

| 比喩 | 設計の層 | 問い |
|------|---------|------|
| 建物の間取り | モジュール設計 | どの部屋に何を置くか |
| 家具の配置 | クラス設計 | どの家具をどうつなぐか |
| 家具の細部 | メソッド設計 | 引き出しの仕組みはどうか |

```text
  order パッケージ（モジュール）
      │
      ├─ Order クラス      … 注文の状態と振る舞い
      ├─ OrderLine クラス  … 明細
      └─ OrderRepository   … 永続化の窓口
```

モジュールが「境界」を決め、クラスが **境界の中の責務分担** を決めます。

---

## 2. 手続き指向からオブジェクト指向へ

手続き指向では、データと処理が分離しがちです。

```javascript
// 手続き指向 — データと処理がバラバラ
let balance = 0;
function deposit(amount) { balance += amount; }
function withdraw(amount) { balance -= amount; }
```

オブジェクト指向では、**関連するデータと処理を1つのクラスにまとめ**ます。詳細は [[02_クラスとオブジェクト]] を参照。

```javascript
class BankAccount {
  #balance = 0;
  deposit(amount) { /* ルールをここに */ }
  withdraw(amount) { /* ルールをここに */ }
}
```

設計の問いが「どの関数に書くか」から「**どのクラスが責任を持つか**」へ移ります。

---

## 3. クラス設計が解決する問題

クラス設計を意識しないと、次の問題が起きやすくなります。

| 問題 | 症状 | クラス設計での対策 |
|------|------|-------------------|
| 神クラス | 1 クラスに全部入り | 単一責任・分割 |
| 貧血モデル | データだけのクラス | 振る舞いをクラスに置く |
| 密結合 | 変更が連鎖する | カプセル化・抽象化 |
| 継承の乱用 | 階層が深く壊れやすい | 合成・インターフェース |

```text
  クラス設計なし
      │
      ├─→ どこに何があるか分からない
      ├─→ 1 行直すと全体が壊れる
      └─→ テストが書けない
              │
              ▼
        変更コストの増大
```

## 4. 本書の読み方と前提知識

### 前提知識

- どれか 1 言語でクラス・メソッド・フィールドが書ける
- [[MOC_ソフトウェア設計体系]] の「凝集度・結合度・カプセル化」の概要を知っているとよい
- GRASP や SOLID の **事前知識は不要**

### 読み方

1. **第1〜2部** で「なぜ」「何を目指すか」を掴む
2. **第3〜4部** で分割と関係の実践スキルを学ぶ
3. **第5〜6部** で SOLID・パターンを定着させる
4. **第7〜8部** で品質・チーム・演習で統合する

> オブジェクト指向の基礎を復習したい場合は [[01_オブジェクト指向設計|42 / 22_オブジェクト指向]] を併読してください。

## まとめ

- クラス設計は **モジュールの中身** を型単位で組み立てる層
- 手続き指向の「関数に書く」から「**クラスが責任を持つ**」へ視点を移す
- 神クラス・貧血モデル・密結合などを予防できる
- 段階的に学べる構成。[[MOC_クラス設計体系]] の学習順に読むのがおすすめ
