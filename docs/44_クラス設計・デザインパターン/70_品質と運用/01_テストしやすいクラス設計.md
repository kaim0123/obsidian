# テストしやすいクラス設計

## この章の目的

**テスト容易性** をクラス設計の要件として扱い、副作用の局所化・DI・モック地獄の回避を学びます。

---

## 1. テスト容易性とは何か

**テスト容易性** は、クラスを **単体で・速く・安定して** 検証できる度合いです。

| 高い | 低い |
|------|------|
| 依存を差し替え可能 | DB・ネット必須 |
| 純粋なドメインロジック | 静的グローバルに依存 |
| 小さな単位 | 神クラス1本で全部 |

設計はテストの **前提** です。42 の [[03_テストと設計の関係]] とも接続します。

---

## 2. 副作用の局所化

**副作用**（DB・ファイル・時刻・乱数・外部 API）をクラスの **端** に寄せます。

```javascript
// テストしやすい — 計算は純粋
class Pricing {
  total(lines, taxRate) {
    const sub = lines.reduce((s, l) => s + l.subtotal(), 0);
    return sub * (1 + taxRate);
  }
}

// 副作用は別クラス
class OrderRepository { save(order) { /* DB */ } }
```

ドメインクラスから I/O を追い出すと、テストが **計算だけ** に集中できます。

---

## 3. 依存の注入（DI）とクラス設計

**依存性注入** は、依存を外部から渡し、`new` をクラス内に書かないことです。

```javascript
class PlaceOrderUseCase {
  constructor(orderRepo, inventory, clock) {
    this.orderRepo = orderRepo;
    this.inventory = inventory;
    this.clock = clock;  // 時刻も注入
  }
}
```

| 注入方法 | 用途 |
|---------|------|
| コンストラクタ | 必須依存 |
| メソッド引数 | 呼び出しごとに変わる依存 |
| セッター | 任意（テストではコンストラクタ推奨） |

[[03_インターフェースと抽象化]] の DIP と一体です。

---

## 4. モックが必要になる設計の問題

モックだらけは **設計の匂い** です。

| 症状 | 設計上の問題 |
|------|-------------|
| 1テストで10個モック | 責務過多・神クラス |
| すべてのメソッドをスタブ | インターフェース肥大（ISP） |
| プライベートをモック | テストが実装に依存 |

**モックを減らす** 方向に設計を直す（責務分割・純粋関数の抽出）。

---

## 5. テストから見えたクラス設計の改善

テストを書きながら設計を直す流れ:

1. テストが書きにくいクラスを特定
2. **何に依存しているか** を列挙
3. 副作用を境界へ Extract Class
4. インターフェースを切って注入
5. テストが短くなったか確認

```text
  テスト困難 → 依存の可視化 → 分割・注入 → 再テスト
```

メソッドレベルの改善は [[010Programming/46_メソッド設計/00_全体像/目次|46_メソッド設計/目次]] へ。

---

## まとめ

- テスト容易性は設計の品質指標
- 副作用は境界クラスに集約
- DI で具象から解放
- モック過多は設計改善のシグナル
