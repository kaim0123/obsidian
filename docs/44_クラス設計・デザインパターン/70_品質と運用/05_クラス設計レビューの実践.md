# クラス設計レビューの実践

## この章の目的

**クラス設計レビュー** の進め方・チェックリスト・良悪比較・改善提案の書き方を学びます。  
本教材の統合と、次の学習ステップへつなぎます。

---

## 1. クラス設計レビューの進め方

| 段階 | 内容 | 時間目安 |
|------|------|---------|
| 1. 文脈 | 要件・変更の背景 | 5分 |
| 2. 全体 | クラス図・パッケージ | 10分 |
| 3. 詳細 | 争点のあるクラス | 15分 |
| 4. まとめ | 指摘・合意・フォロー | 5分 |

```text
  事前: クラス図 or 主要クラス名リストを共有
  当日: 「なぜこの分割か」を説明させる
  事後: 改善チケットを1〜3件に絞る
```

コードレビューと併用し、**大きな構造変更** は設計レビューで先に合意します。

---

## 2. レビュー用チェックリスト

[[付録B_クラス設計チェックリスト]] をベースに、レビュー時は次を重点確認します。

- [ ] **SRP**: 変更理由は1つか
- [ ] **凝集・結合**: God Class / 循環依存はないか
- [ ] **カプセル化**: 不変条件はクラス内か
- [ ] **継承**: is-a が成立しているか。深すぎないか
- [ ] **DIP**: ドメインが DB・フレームワークを知っていないか
- [ ] **テスト**: ドメインを単体テストできるか
- [ ] **命名**: ユビキタス言語と一致しているか

## 3. 良い設計・悪い設計の比較

### 注文確定の例

**悪い設計**

```javascript
class OrderService {
  confirm(orderId) {
    const order = db.query('SELECT ...');
    if (order.lines.length === 0) return;
    stripe.charge(order.total);
    db.query('UPDATE ...');
    sendMail(order.email);
  }
}
```

| 問題 | 責務混在・DB/Stripe/メール直結・テスト困難 |

**良い設計**

```javascript
class Order {
  confirm(inventory) { /* ルール */ }
}
class PlaceOrderUseCase {
  execute(orderId) {
    const order = this.repo.findById(orderId);
    order.confirm(this.inventory);
    this.repo.save(order);
    this.notifier.notify(order);
  }
}
```

| 改善 | ドメイン分離・依存注入・テスト可能 |

## 4. 改善提案の書き方

レビューコメントは **現象 → 影響 → 提案** の順が伝わりやすいです。

```markdown
## 指摘: OrderService が永続化と決済を直接実行している

**影響**: 単体テストに DB と Stripe が必要。変更が連鎖する。

**提案**:
1. `Order.confirm(inventory)` にルールを移動（貧血モデル解消）
2. `OrderRepository`, `PaymentGateway` インターフェースを注入
3. まず `Order` のテストを1本追加してから Extract

**優先度**: 高（次の支払い方法追加前）
```

批判ではなく **次の一歩** を示します。

---

## まとめ

- 設計レビューは文脈→全体→詳細→合意の流れ
- チェックリストで見落としを防ぐ
- 良悪比較で「なぜ」を共有
- 改善提案は影響と具体手順を書く
