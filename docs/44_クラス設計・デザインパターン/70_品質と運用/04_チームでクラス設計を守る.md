# チームでクラス設計を守る

## この章の目的

チーム開発で **クラス設計の合意を維持** する方法を学びます。  
レビュー・文書化・負債の可視化・新人への伝え方を押さえます。

---

## 1. 設計の合意形成

クラス設計は個人の好みではなく、**チームの合意** が必要です。

| 場面 | 手法 |
|------|------|
| 新機能 | 短い設計スケッチ + クラス名リスト |
| 争点 | ADR（設計判断の記録） |
| 定期 | アーキテクチャ・設計の勉強会 |

```text
  提案 → レビュー → 合意 → コード → 振り返り
```

[[01_チームで設計を守る]] と同じ考え方をクラス単位に適用します。

---

## 2. コードレビューで見るべきポイント

| 観点 | 質問 |
|------|------|
| SRP | このクラスの変更理由は1つか |
| 凝集・結合 | 無関係な処理・過剰な依存はないか |
| カプセル化 | 不変条件は守られているか |
| 命名 | クラス名で責務が伝わるか |
| テスト | 単体テストしやすい構造か |

**スタイル（インデント等）** より **構造** を優先します。

---

## 3. クラス設計ルールの文書化

1ページでよいので、チームの **クラス設計ルール** を残します。

```markdown
## 例: クラス設計ルール
1. ドメインルールはエンティティに置く（貧血モデル禁止）
2. new は Composition Root / Factory に集約
3. 継承は2階層まで。それ以上は合成
4. Repository はインターフェース + infrastructure 実装
5. 500行超えたら Extract Class を検討
```

[[付録B_クラス設計チェックリスト]] をベースにカスタマイズします。

---

## 4. 設計負債の可視化

| 手法 | 内容 |
|------|------|
| ラベル | `tech-debt`, `refactor` チケット |
| メトリクス | クラス行数、循環依存 |
| ボーンマルク | 理想のパッケージ図と現状の差分 |

```text
  負債リスト → 優先度（影響×頻度）→ スプリントに1〜2件
```

隠すと **変更恐怖** が増えます。可視化して計画的に返済します。

---

## 5. 新人への説明の仕方

1. **比喩から** — 部屋と家具（[[01_クラス設計を学ぶ理由]]）
2. **悪い例1つ** — 神クラスを見せて問題を体感
3. **直し方1つ** — Extract Class をペアで
4. **チェックリスト** — [[付録B_クラス設計チェックリスト]]
5. **既存コードの良い例** — チームのお手本クラスを指す

理論の前に **「なぜ痛いか」** を体験させると定着します。

---

## まとめ

- 設計は合意形成が前提。スケッチと ADR を活用
- レビューは構造・責務・テスト容易性を見る
- ルールとチェックリストを短く文書化
- 負債は可視化して計画返済。新人には悪い例から
