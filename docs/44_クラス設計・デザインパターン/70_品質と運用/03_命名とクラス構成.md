# 命名とクラス構成

## この章の目的

**クラス名・メソッド名・ファイル配置** が設計を表すように整える方法を学びます。  
チームでの命名統一も押さえます。

---

## 1. クラス名が設計を表す

良いクラス名は **責務が一目で分かる** 名前です。

| 良い例 | 悪い例 |
|--------|--------|
| `Order`, `OrderLine` | `Data`, `Info` |
| `TaxCalculator` | `Helper`, `Util` |
| `StripePaymentGateway` | `Manager`（何を管理？） |

```text
  名前を説明できない → 責務が曖昧 → 分割を検討
```

**ユビキタス言語**（[[02_ユビキタス言語]]）と揃えると、業務とコードのギャップが減ります。

---

## 2. メソッド名と責務の一致

メソッド名は **動詞 + 目的語** で、副作用を正直に表します。

| 種類 | 命名 | 例 |
|------|------|-----|
| 問い合わせ | `get` / `find` / `is` | `findById`, `isEmpty` |
| 変更 | `add` / `remove` / `confirm` | `addLine`, `confirm` |
| 副作用あり | 正直に | `sendEmail`, `saveToDb` |

```javascript
// 曖昧
process()  // 何をする？

// 明確
confirmOrder()
calculateShippingFee()
```

`get` で副作用があるのは誤解を招きます（`fetch` / `load` を検討）。

---

## 3. 1ファイル1クラスの原則と例外

多くの言語・チームでは **1ファイル1公開クラス** が標準です。

| メリット | 検索・レビュー・衝突回避 |
|---------|------------------------|
| 例外 | 小さな private 補助クラス、Record 型、密接な Value Object |

```text
  order/
    Order.ts
    OrderLine.ts
    OrderStatus.ts
```

巨大ファイルは **Extract Class** でファイルも分割します。

---

## 4. パッケージ内でのクラス配置

[[MOC_モジュール設計体系]] のモジュール境界の **内側** でクラスを整理します。

```text
  com.example.order
    domain/       … Order, OrderLine（ドメイン）
    application/  … PlaceOrderUseCase
    infrastructure/ … SqlOrderRepository
```

| 原則 | ドメインを中心に、技術詳細は外側 |
|------|-------------------------------|
| 依存の向き | 内側は外側を知らない |

---

## 5. 命名規則とチームでの統一

チームで **短いガイド** を決めます。

| 項目 | 例（Java/C# 風） |
|------|-----------------|
| クラス | `PascalCase` |
| メソッド | `camelCase` |
| 定数 | `UPPER_SNAKE` |
| インターフェース | `IOrderRepository` または `OrderRepository` |

```markdown
## クラス命名ルール（例）
- エンティティ: 名詞（Order）
- サービス: 動詞+Service は避け、UseCase / Handler
- Repository: {集約}Repository
- 禁止: Utils に業務ロジックを書かない
```

[[04_チームでクラス設計を守る]] で文書化します。

---

## まとめ

- クラス名 = 責務の説明。Helper/Util の安易な使用を避ける
- メソッド名は動詞で副作用を明示
- 1ファイル1クラスを基本に配置を整理
- パッケージはドメイン中心。チームで規約を共有
