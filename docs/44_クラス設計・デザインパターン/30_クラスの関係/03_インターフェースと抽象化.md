# インターフェースと抽象化

> この章は「クラス設計でどう使うか」を扱います。DIP（依存性逆転の原則）そのものの説明は 48 の [[05_DIP (依存性逆転の原則)]] を参照してください。

## この章の目的

**インターフェース** と **抽象化** を通じて、具象に依存しないクラス設計を学びます。  
DIP・テスト容易性との関係も押さえます。

---

## 1. インターフェースの役割

**インターフェース** は「**何ができるか**」の契約を定義します。実装の詳細は隠します。

```typescript
interface OrderRepository {
  save(order: Order): void;
  findById(id: string): Order | null;
}
```

| 役割 | 効果 |
|------|------|
| 契約の明示 | 呼び出し側が知るべき操作がはっきり |
| 実装の差し替え | DB・メモリ・モックを入れ替え可能 |
| 結合度の低減 | 具象クラスに依存しない |

[[04_多態とインターフェース]] を参照。

---

## 2. 抽象クラスとインターフェースの使い分け

| 観点 | 抽象クラス | インターフェース |
|------|-----------|-----------------|
| 状態の共有 | 共通フィールドを持てる | 通常は持たない |
| 多重継承 | 1つのみ（言語による） | 複数実装可能 |
| 向く場面 | 共通実装 + 一部抽象 | 能力の契約だけ |

```text
  共通の骨格がある → 抽象クラス（Template Method）
  能力の差し替えだけ → インターフェース
```

---

## 3. 依存性逆転の原則（DIP）

**DIP**: 上位の方針は下位の詳細に依存すべきでない。両方とも **抽象** に依存する。

```text
  悪い:  OrderService → MySqlOrderRepository（具象）
  良い:  OrderService → OrderRepository（抽象）← MySqlOrderRepository
```

```javascript
class OrderService {
  constructor(repository) {  // 抽象（インターフェース）に依存
    this.repository = repository;
  }
}
```

[[05_SOLIDの統合と判断]] で SOLID 全体とつなげます。

---

## 4. 具象に依存しないクラス設計

具象依存を避けるチェックポイント:

- [ ] `new` をビジネスクラスの中で直接書いていないか
- [ ] 外部 API・DB の型がドメインに漏れていないか
- [ ] 設定・環境で変わるものは抽象の裏に隠しているか

```javascript
// 悪い — ドメインが MySQL を知る
class Order {
  save() { new MySqlClient().insert(this); }
}

// 良い — 永続化は Repository に委譲
class OrderService {
  save(order) { this.repository.save(order); }
}
```

---

## 5. テスト容易性との関係

抽象化は **テストダブル** を差し込む前提です。

```javascript
class InMemoryOrderRepository {
  save(order) { this.store.set(order.id, order); }
}

// テスト
const repo = new InMemoryOrderRepository();
const service = new OrderService(repo);
```

| 具象依存 | 抽象依存 |
|---------|---------|
| DB がないとテスト不可 | メモリ実装で単体テスト |
| 外部 API を叩く | スタブで応答を固定 |

詳細は [[01_テストしやすいクラス設計]] を参照。

---

## まとめ

- インターフェースは契約。実装を隠して差し替え可能に
- 抽象クラスは共通骨格、インターフェースは能力の契約
- DIP で依存の向きを抽象へ
- テスト容易性は抽象化の副産物
