#継承 #コンポジション

## 詳しい要約

**テーマ：「継承よりコンポジション」を画像ライブラリの例で具体的に理解する**

継承とコンポジションはどちらも「書いたコードを再利用する」ための道具。継承は親クラスに強く縛られるため変更に弱く、コンポジション＋インターフェース（＋依存性注入）のほうが変更に強い。変更に強い設計にしたいならコンポジションから始め、継承は必要なときだけ慎重に使う、というのが結論。

---

### 継承の落とし穴

- `Image` クラスに `Resize`・`FlipHorizontal`・`FlipVertical` を持たせ、抽象メソッド `Save` / `Load` を追加。`JPEGImage`・`PNGImage`・`BMPImage` がそれぞれ `Save` / `Load` だけを実装すれば、他の処理はタダで再利用できる
- ここに「ファイル由来でない、ユーザーが描けるDrawableImage」という要望が来ると破綻する。親の構造がそのまま押し付けられ、意味のない `Save` / `Load` を実装して例外を投げるしかない
- 回避するには親を組み替え（`Image` から `Save` / `Load` を外し、間に `FileImage` を挟む）る必要があり、`Image` が保存できる前提のコードがすべて壊れる
- 継承は **共通点を親に集める** ので、例外が1つ見つかるだけで大規模な再設計になる。「変更が必要になった瞬間に継承は破綻し、変更されないコードは存在しない」。正規化しすぎたDBスキーマがデータ増加でつまずくのに似ている（NoSQLが重複を許す方向に寄った理由と同じ、と話者は考えている）

### コンポジション

- 「機能を共有したいなら、その機能を **使えばいい**」。継承を使わない再利用で、実は普段からやっていること
- `Image` はメモリ上の画像を表すだけの単純なクラスにし、JPEG / PNG / BMP クラスは `Image` を継承しない。`this` で親をたどる代わりに、対象の画像を **引数で受け取る**
- 描画の要望には、画像を受け取る `ImageDraw` クラスを追加するだけ。他のクラスに一切触れずに済む
- 使い方も「目的に合う1クラスを選ぶ」から「**複数のクラスを組み合わせる**」に変わる（JPEGを読み→描画→保存、BMPを読み→反転→リサイズして書き出し など）

### 継承による抽象化とインターフェース・DI

- 継承は「コードの再利用」と「**抽象化**」の2つの能力を1つにまとめている。抽象化とは、相手が具体的に何かを知らずに使える状態で、双方が守る取り決めを **契約（contract）** と呼ぶ
- 継承版では、アプリは親クラスの参照で画像を持ち、ファイル形式を気にせず `save` を呼べた（親のメソッドが契約になっていた）
- コンポジション版で同じことをするには **インターフェース** を使う。変数もメソッド本体も持たず、契約だけを定義する。例：`save` / `load` を持つ `ImageFile` インターフェースを各形式が実装
- 親クラスはすべてを共有するので変えにくいが、インターフェースは必要な契約だけなので、既存クラスにも後から付けやすい
- どの `ImageFile` を生成するかの判断をアプリの外に出し、使う側から渡してもらう → これが **依存性注入（Dependency Injection）**。「大げさな名前だが、やっていることはそれだけ」
- 話者は「継承が悪いとまでは言わないが、ほぼ使わなくなった」

### 継承を使うとき

- コンポジションも完璧ではない：内部部品を初期化する **ボイラープレート** が増え、中身を呼ぶだけのラッパーメソッドが量産されがち。それでもオブジェクト同士の **接触面** が小さくなり、変更時の痛みが減る
- 継承が有効なのは、重複だらけの巨大レガシーで1箇所だけ直したいとき（例：インターフェースに従う100クラスの半分が同じロジックを繰り返している。作り直しにはチームで数か月かかる）
- 継承を使うなら **継承されることを前提に設計** する：フィールドを `protected` にしない（`public` にしないのと同じ理由）、オーバーライド用には明示的な `protected` APIだけを用意し、それ以外は `private` / `final` / `sealed` にする。これで親を変えたときのバグを防げる

### まとめ

- 継承とコンポジションは同じ問題（コード再利用）のための道具
- 継承は親に強く結合し、例外が出ると大規模な再設計が必要になる
- 抽象化はインターフェースで、生成の判断は外から注入（DI）すれば、継承なしで同じことができる
- 変更に強い設計はコンポジションから始め、継承は「継承される前提の設計」で必要なときだけ使う
