## 詳しい要約

**テーマ：デザインパターンは「覚える」のではなく、問題を経験した後に「出会う」もの**

GoF の 23 パターンを暗記しても実務で使えない人が多いのは、パターンが「問題に対する解決策」なのに問題を経験していないから。覚えた人ほど「パターンを使いたい病」にかかり過剰設計になりやすい。伸びる人はまず問題にぶつかって苦労し、その後でパターンを知って理解する。パターンは道具箱として存在を知っておけばよく、使わない判断こそが大事、という話。

---

### 第1章 デザインパターンを覚えても使えない人

- 23 パターンを全部暗記し本を何冊も読んだのに、実務で全く使えない人が多い。
- シングルトンやファクトリーを説明できても、**目の前のコードにどう適用するか**が分からない。知識と実践が結びついていない。
- 試験勉強のように覚えて「自分は知っている」と**自己満足**しているが、使えなければ意味がない。

### 第2章 パターンは解決策であって問題ではない

- 多くの人は問題を知らないまま解決策を覚えようとする。例：オブザーバーパターンの定義（状態変化を依存オブジェクトに通知）は覚えられても、なぜ必要かを体験していないとピンとこない。
- **薬の名前を覚えても医者にはなれない**：どの症状にどの薬かは患者を診ないと分からない。同様に、コードが何に苦しんでいるかを診断するにはコードと格闘する経験が必要。
- if-else が 20 個並んだコードを保守した経験があれば、ストラテジーパターンを見て「これだ」となる。

### 第3章 パターンを使いたい病

- 「このパターンを使いたい」から設計が始まる＝**手段の目的化**。
- 新プロジェクトで問題を分析する前に「今回はファクトリーを使おう」と決める。必要ないのにストラテジーやデコレーターを導入し、**過剰設計**に。
- 本人は良い設計をしていると思っているが、後から入った人は「なぜこんなに複雑なのか」と困惑する。知っているからこそ陥る罠で、**知識が足かせ**になることもある。

### 第4章 伸びる人の学び方

- パターンを覚える前に、まず実際のコードで**問題にぶつかる**。
- 例：if-else を条件が増えるたびに追加し 20 個、30 個と増えて保守が大変になりバグが増える → 問題に気づく → どうすればいいか分からない → そのタイミングでストラテジーを知り「まさにこれが欲しかった」と感動する。
- 苦労した分だけ価値が分かり、次に同じ問題に出会ったとき**すぐ適用できる**。順序は「問題の経験 → パターン」。

### 第5章 デザインパターンとの正しい付き合い方

- **覚えるな**（暗記しようとするな）。実際の問題の中で出会うのがベスト。
- 「こういうパターンがあるらしい」というレベルで**道具箱**として存在を知っておき、詳細は必要になったときに調べればよい。
- パターンは問題を解決するためにあり、パターンを使うために問題を作るのではない。
- **使わなくて済むなら使わない**。知っていてあえて使わない判断ができるのが上級者。

### まとめ

- パターンは問題への解決策。問題を経験していないと本当には理解できない。
- 「パターンを使いたい病」は過剰設計を生む。
- 覚えるな、出会え。苦労してから学ぶ。使わない判断こそ大事。
