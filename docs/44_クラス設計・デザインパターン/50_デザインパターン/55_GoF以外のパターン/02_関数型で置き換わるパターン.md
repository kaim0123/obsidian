# 関数型で置き換わるパターン

## この章の目的

GoF のデザインパターン（1994年）は、主に **C++ と Smalltalk** を前提に書かれました。
その後、多くの言語が **第一級関数**（関数を値として渡せる）・**クロージャ**・**ジェネレータ**・**モジュール** などの機能を持つようになり、**いくつかのパターンは、言語機能でずっと簡単に書けるようになりました**。

この章では、

- Peter Norvig の「**23パターン中16がシンプルになる**」という指摘
- **関数で置き換えられるパターン**（Strategy・Command・Template Method・Observer など）
- **言語機能で置き換えられるパターン**（Iterator・Singleton・Factory など）
- それでも **パターンの考え方が役立つ理由**
- TypeScript での判断基準

を、Before / After のコードで解説します。

---

## 1. Peter Norvig の指摘（1996年）

Google の研究責任者として知られる Peter Norvig は、1996 年の講演「Design Patterns in Dynamic Programming」で次のように述べました。

> **GoF の23パターンのうち16は、Lisp や Dylan のような動的言語では、少なくとも一部の使い方において、C++ より質的に簡単に実装できる（あるいは見えなくなる）。**

その理由として、Norvig は **第一級関数（高階関数）・動的な型・マクロ** などの言語機能を挙げています。

> パターンが **消えたのではなく、言語に吸収された** のです。

ここから「デザインパターンは、**言語の機能不足を補うための回避策** でもある」という見方が生まれました。現代の TypeScript・Python・Kotlin・Swift などは、これらの機能の多くを持っています。

## 2. 関数で置き換えられるパターン

### 2.1 Strategy → 関数を渡す

**Strategy**：アルゴリズムを差し替え可能にする（→ [[01_振る舞いに関するパターン]]）

```typescript
// Before：クラスで Strategy
interface SortStrategy { compare(a: Product, b: Product): number; }
class ByPrice implements SortStrategy { compare(a: Product, b: Product) { return a.price - b.price; } }
class ByName implements SortStrategy { compare(a: Product, b: Product) { return a.name.localeCompare(b.name); } }

class ProductList {
  constructor(private strategy: SortStrategy) {}
  sort(items: Product[]) { return [...items].sort((a, b) => this.strategy.compare(a, b)); }
}

// After：関数を渡す
type Compare = (a: Product, b: Product) => number;
const byPrice: Compare = (a, b) => a.price - b.price;
const byName: Compare = (a, b) => a.name.localeCompare(b.name);

const sorted = [...items].sort(byPrice);
```

- `Array.prototype.sort` 自体が、**比較関数という Strategy を受け取る** 設計になっている
- メソッドが1つだけの Strategy は、**ほぼ常に関数で置き換えられる**

### 2.2 Command → クロージャ

**Command**：操作をオブジェクトにして、後で実行・取り消し・キューイングできるようにする

```typescript
// Before：クラスで Command
interface Command { execute(): void; }
class AddItemCommand implements Command {
  constructor(private cart: Cart, private item: Item) {}
  execute() { this.cart.add(this.item); }
}
queue.push(new AddItemCommand(cart, item));

// After：クロージャ（引数を閉じ込めた関数）
type Command = () => void;
queue.push(() => cart.add(item));
```

- クロージャは、**実行に必要な値を閉じ込めた関数** なので、Command オブジェクトそのもの
- ただし **取り消し（Undo）** が必要なら、`{ execute, undo }` のペアを持つオブジェクトにする方が分かりやすい

### 2.3 Template Method → 関数を引数で渡す

**Template Method**：処理の骨組みを親クラスで決め、一部を子クラスで埋める

```typescript
// Before：継承で Template Method
abstract class ReportGenerator {
  generate(data: Row[]) {
    const header = this.header();
    const body = data.map((r) => this.formatRow(r)).join("\n");
    return `${header}\n${body}`;
  }
  protected abstract header(): string;
  protected abstract formatRow(row: Row): string;
}
class CsvReport extends ReportGenerator { ... }

// After：差し替える部分を関数で受け取る
function generateReport(data: Row[], opts: { header: string; formatRow: (r: Row) => string }) {
  return `${opts.header}\n${data.map(opts.formatRow).join("\n")}`;
}
generateReport(rows, { header: "id,name", formatRow: (r) => `${r.id},${r.name}` });
```

- 継承を使わないので、[[04_継承より合成]] で見た脆い基底クラス問題も避けられる

### 2.4 Observer → コールバック・イベント・リアクティブ

**Observer**：状態の変化を、登録された複数のオブジェクトに通知する

```typescript
// Before：Observer インターフェースを実装するクラス
interface Observer { update(price: number): void; }
class PriceDisplay implements Observer { update(p: number) { /* 表示更新 */ } }

// After：関数を登録する
type Listener = (price: number) => void;
class PriceFeed {
  private listeners = new Set<Listener>();
  subscribe(fn: Listener) { this.listeners.add(fn); return () => this.listeners.delete(fn); }
  publish(price: number) { this.listeners.forEach((fn) => fn(price)); }
}

const unsubscribe = feed.subscribe((p) => console.log("価格:", p));
```

- ブラウザの `addEventListener`、Node.js の `EventEmitter`、RxJS の Observable、React の状態管理ライブラリの購読 API は、どれも **関数を登録する Observer**
- 購読解除の関数を返すのが、現代的な書き方

### 2.5 Decorator → 高階関数

**Decorator**：オブジェクトを包んで機能を追加する

```typescript
// After：関数を受け取って、機能を足した関数を返す（高階関数）
const withLogging = <A extends unknown[], R>(fn: (...args: A) => R) =>
  (...args: A): R => {
    console.log("呼び出し:", args);
    return fn(...args);
  };

const withRetry = <A extends unknown[], R>(fn: (...args: A) => Promise<R>, times = 3) =>
  async (...args: A): Promise<R> => {
    for (let i = 0; ; i++) {
      try { return await fn(...args); } catch (e) { if (i >= times - 1) throw e; }
    }
  };

const fetchUser = withLogging(withRetry(rawFetchUser));
```

- Express のミドルウェア、React の高階コンポーネント（HOC）も同じ発想
- ただし、**複数のメソッドを持つオブジェクト** を包むなら、クラスの Decorator の方が自然（→ [[04_継承より合成]]）

### 2.6 Chain of Responsibility → 関数の配列・パイプライン

```typescript
type Handler = (req: Request) => Response | null;   // 処理できなければ null

const handle = (handlers: Handler[]) => (req: Request) => {
  for (const h of handlers) {
    const res = h(req);
    if (res) return res;
  }
  return notFound();
};
```

- Express・Hono・Koa のミドルウェアチェーンが代表例

## 3. 言語機能で置き換えられるパターン

### 3.1 Iterator → 言語の反復プロトコル・ジェネレータ

```typescript
// Before：Iterator クラス（hasNext / next）
class TreeIterator { hasNext() { ... } next() { ... } }

// After：ジェネレータ
function* walk(node: TreeNode): Generator<TreeNode> {
  yield node;
  for (const child of node.children) yield* walk(child);
}
for (const n of walk(root)) console.log(n.name);
```

- JavaScript の `for...of`・`Symbol.iterator`・ジェネレータが、Iterator パターンを **言語に組み込んでいる**

### 3.2 Singleton → モジュール

```typescript
// Before：Singleton クラス
class Config {
  private static instance: Config;
  private constructor() {}
  static getInstance() { return (this.instance ??= new Config()); }
}

// After：ES モジュールは一度だけ評価される
// config.ts
export const config = loadConfig();
```

- ES モジュールは **最初の import のときに一度だけ評価** され、以後は同じ値が共有される
- ただし、Singleton もモジュールのグローバルな値も、**テストで差し替えにくい** という問題は同じ。依存性注入（DI）で渡す方が望ましいことが多い（→ 41 の [[03_制御の反転とComposition Root]]、[[02_アンチパターンとコードの臭い]] の「Singleton の誤用」）

### 3.3 Factory Method / Abstract Factory → 関数・オブジェクトリテラル

```typescript
// After：生成関数を渡す
type CreateNotifier = (config: Config) => Notifier;
const createNotifier: Record<Channel, CreateNotifier> = {
  email: (c) => new EmailNotifier(c.smtp),
  slack: (c) => new SlackNotifier(c.webhookUrl),
};
const notifier = createNotifier[channel](config);
```

### 3.4 Visitor → パターンマッチ（判別可能ユニオン）

**Visitor**：データ構造の種類ごとに異なる処理を、データ構造を変えずに追加する

```typescript
// After：判別可能ユニオン＋switch（網羅性チェック付き）
type Shape =
  | { kind: "circle"; r: number }
  | { kind: "rect"; w: number; h: number };

function area(s: Shape): number {
  switch (s.kind) {
    case "circle": return Math.PI * s.r ** 2;
    case "rect": return s.w * s.h;
  }
}
// 新しい操作（perimeter など）は関数を1つ追加するだけ
```

- Visitor は「**操作を追加しやすくする**」ためのパターン。関数型の **直和型＋パターンマッチ** は、まさにその性質を持っている（42 の [[02_不変データと純粋関数_関数型の設計原則]] の Expression Problem）

### 3.5 Prototype → スプレッド構文・`structuredClone`

```typescript
const copy = { ...original, name: "コピー" };
const deep = structuredClone(original);
```

## 4. まとめ表

| GoF パターン | 置き換え | 置き換えやすさ |
|---|---|---|
| **Strategy** | 関数を渡す | ◎ メソッド1つなら、ほぼ常に関数でよい |
| **Command** | クロージャ | ◎（Undo が必要ならオブジェクト） |
| **Template Method** | 関数を引数で渡す | ◎ |
| **Observer** | コールバック・イベント・Observable | ◎ |
| **Iterator** | `for...of`・ジェネレータ | ◎ 言語に組み込み |
| **Chain of Responsibility** | 関数の配列・ミドルウェア | ◯ |
| **Decorator** | 高階関数 | ◯（複数メソッドならクラス） |
| **Factory Method / Abstract Factory** | 生成関数・オブジェクトリテラル | ◯ |
| **Visitor** | 判別可能ユニオン＋パターンマッチ | ◯ |
| **Singleton** | モジュール | △ テスト容易性の問題は残る。DI を検討 |
| **Prototype** | スプレッド構文・`structuredClone` | ◯ |
| **Adapter・Facade・Proxy・Composite・State** など | — | 構造を表すパターンは、関数型でも考え方として残る |

## 5. それでもパターンを学ぶ価値

関数で置き換えられるからといって、パターンを学ぶ意味がなくなるわけではありません。

| 価値 | 説明 |
|---|---|
| **共通の語彙** | 「ここは Strategy にしよう」と言えば、関数で書くかクラスで書くかに関係なく、**意図が伝わる** |
| **問題の型を見抜く力** | 「アルゴリズムを差し替えたい」「変化を通知したい」という **問題の形** に気づけることが本質。書き方は二の次 |
| **ライブラリ・フレームワークの理解** | React・Express・RxJS などは、パターンの考え方の上に作られている |
| **オブジェクトの方が適している場面** | 状態を持つ・複数のメソッドを持つ・Undo が必要などの場合は、クラス版のパターンの方が分かりやすい |

> Norvig も、パターンを否定したのではなく、**「パターンは言語によって形が変わる」** ことを示したのです。

## 6. TypeScript での判断基準

| 状況 | おすすめ |
|---|---|
| 差し替える部分が **メソッド1つ・状態なし** | **関数** |
| 差し替える部分が **複数のメソッド** を持つ | **インターフェース＋クラス**（またはメソッドを持つオブジェクトリテラル） |
| 差し替える部分が **状態** を持つ（キャッシュ・接続など） | **クラス** |
| **DI コンテナ** やフレームワークがクラスを前提にしている | クラス |
| チームが **どちらに慣れているか** | 一貫性を優先する |

## 7. ありがちな誤解

### 7.1 「関数型言語ではデザインパターンは不要」

**誤りです。** GoF の一部のパターンが簡単になるだけで、関数型にも独自のパターン（モナド・パイプライン・Reader など）があります。「問題の型」と「解き方の定石」という考え方自体は普遍的です。

### 7.2 「関数で書けるなら常に関数で書くべき」

**場合によります。** 状態や複数のメソッドを持つなら、クラスの方が分かりやすいこともあります。

### 7.3 「パターン名を知らなくても関数で書けば同じ」

**コードは同じでも、伝わり方が違います。** パターン名は、**設計の意図を短く伝える語彙** として価値があります。

---

## まとめ

- Peter Norvig（1996）：**GoF の23パターン中16は、動的言語では簡単になるか見えなくなる**。パターンは言語に吸収された
- **Strategy・Command・Template Method・Observer** は、**関数・クロージャ** でシンプルに書ける
- **Iterator** はジェネレータ、**Singleton** はモジュール、**Visitor** は判別可能ユニオン＋パターンマッチで置き換えられる
- Singleton をモジュールにしても、**テストしにくさの問題は残る**
- パターンの価値は **問題の型を見抜く力と共通の語彙** にあり、書き方は言語に合わせて選ぶ
- **メソッド1つ・状態なしなら関数、複数メソッドや状態があるならクラス**
