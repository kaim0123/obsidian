# ドメインを表すクラス

## この章の目的

業務をコードに写す **ドメインモデル** の基本要素を学びます。  
エンティティ・値オブジェクト・集約・ドメインルールの置き場所を押さえます。

---

## 1. エンティティ（Entity）— 同一性を持つもの

**エンティティ** は **ID で区別される** オブジェクトです。  
属性が変わっても「同じもの」として追跡します。

```javascript
class Order {
  constructor(id) {
    this.id = id;  // 同一性の鍵
    this.status = 'DRAFT';
  }
  confirm() {
    if (this.status !== 'DRAFT') throw new Error('確定済み');
    this.status = 'CONFIRMED';
  }
}
```

| 特徴 | 例 |
|------|-----|
| 同一性（ID） | 注文番号、ユーザーID |
| ライフサイクル | 作成→確定→配送→完了 |
| ミュータブル | 状態が変わる |

---

## 2. 値オブジェクト（Value Object）— 値で比較するもの

**値オブジェクト** は **属性の値で等価性** を判断します。ID は持ちません。

```javascript
class Money {
  constructor(amount, currency) {
    if (amount < 0) throw new Error('負の金額');
    this.amount = amount;
    this.currency = currency;
  }
  add(other) {
    if (this.currency !== other.currency) throw new Error('通貨不一致');
    return new Money(this.amount + other.amount, this.currency);
  }
}
```

| 特徴 | 例 |
|------|-----|
| 不変（immutable） | 変更時は新インスタンス |
| 値で比較 | 1000円と1000円は同じ |
| ルールを内包 | 通貨・丸め・範囲 |

詳細は [[03_エンティティと値オブジェクト]] を参照。

---

## 3. エンティティと値オブジェクトの使い分け

| 問い | エンティティ | 値オブジェクト |
|------|-------------|---------------|
| 同じものの追跡が必要？ | Yes | No |
| 属性が変わっても同一？ | ID で Yes | 値が変われば別物 |
| 例 | `Customer`, `Order` | `Money`, `Address`, `DateRange` |

住所は「同じ建物でも表記が変われば別値」として値オブジェクトにすることが多いです。

---

## 4. 集約（Aggregate）とクラス境界

**集約** は、整合性を保つ **クラスのまとまり** です。  
**集約ルート** だけが外部から触られ、内部はルート経由で操作します。

```text
  Order（ルート）
    ├── OrderLine
    └── ShippingAddress（値オブジェクト）
  
  外部は Order 経由のみ。Line を直接追加させない。
```

```javascript
class Order {
  addLine(product, qty) {
    this._lines.push(new OrderLine(product, qty));
    this._validate();  // 集約全体の不変条件
  }
}
```

[[04_集約とリポジトリ]] も参照。

## 5. ドメインルールをクラスに置く

業務ルールは **ドメインクラスの中** に置きます。

| ルール | 置き場所 |
|--------|---------|
| 注文は空で確定できない | `Order.confirm()` |
| 割引は0〜100% | `Discount` 値オブジェクト |
| 在庫不足で注文不可 | `Order` または `Inventory` |

```javascript
class Order {
  confirm(inventory) {
    if (this.lines.length === 0) throw new Error('明細なし');
    if (!inventory.canFulfill(this)) throw new Error('在庫不足');
    this.status = 'CONFIRMED';
  }
}
```

サービス層にロジックを逃がすと **貧血モデル** になります（[[01_クラス分割の基本プロセス]]）。

## 6. 狭い関心事に特化したクラス（ドメインオブジェクト）

関連する業務データと業務ロジックを、**1つの関心事だけ** に絞ったクラスにまとめたものを、増田亨『現場で役立つシステム設計の原則』では **ドメインオブジェクト** と呼びます（業務の用語とクラス名を一致させる）。

例: 送料に関する値と計算だけを持つ `ShippingCost`。送料と無関係な処理は入れない。

```typescript
class ShippingCost {
  private constructor(readonly amount: number) {}

  static forBasePrice(basePrice: number): ShippingCost {
    return new ShippingCost(basePrice < 3000 ? 500 : 0);
  }
}
```

| やること | 効果 |
|----------|------|
| 関心事ごとに小さなクラスを切る | 変更箇所がクラス名から辿れる |
| クラス名を業務用語にする | 「送料のルールを変えたい」→ `ShippingCost` を開く |
| 関係ないロジックを入れない | クラスが大きくなりにくい |

値そのものを専用クラスにする話は [[04_値オブジェクトと完全コンストラクタ]]、一覧のルールを閉じ込める話は [[06_オブジェクトの種類の整理]] のコレクションオブジェクトを参照してください。

---

## まとめ

- エンティティ = ID で同一性、値オブジェクト = 値で等価・不変
- 集約ルートが整合性の窓口
- ドメインルールはクラス内に。サービスはオーケストレーション
- **狭い関心事に特化した小さなクラス**（ドメインオブジェクト）にすると、変更の影響を閉じ込めやすい
