# クラス分割の基本プロセス

## この章の目的

要件から **クラス候補を見つけ、振る舞いを配置し、最初の設計案を作る** 手順を学びます。  
データクラス・貧血モデル、分割の過不足の見分け方も押さえます。

---

## 1. 要件から名詞（クラス候補）を抽出する

ユースケースや要件文から **名詞** を拾い、クラス候補にします。

> 顧客が **商品** を **カート** に入れ、**注文** を確定する。  
> **在庫** を確認し、**配送先** に届ける。

| 名詞 | クラス候補 | 備考 |
|------|-----------|------|
| 顧客 | `Customer` | エンティティ |
| 商品 | `Product` | エンティティ |
| カート | `ShoppingCart` | 集約の候補 |
| 注文 | `Order` | 集約の候補 |
| 配送先 | `Address` | 値オブジェクト候補 |

すべての名詞がクラスになるわけではありません。**振る舞いと状態を持つもの** を優先します。

---

## 2. 動詞（振る舞い）をどのクラスに置くか

**動詞** はメソッド候補です。**情報を持つクラス** に置くのが基本（後述の GRASP Information Expert）。

| 動詞 | 置き場所 | 理由 |
|------|---------|------|
| カートに入れる | `ShoppingCart` | カートが明細を持つ |
| 合計を計算する | `Order` | 注文が明細を持つ |
| 在庫を引く | `Inventory` または `Product` | 在庫データの所在 |

```javascript
class ShoppingCart {
  add(product, quantity) { /* カートが自分の明細を更新 */ }
}
```

「サービスに全部書く」のではなく、**データと振る舞いの一体化** を意識します。

---

## 3. データクラスと貧血モデルの問題

**データクラス** はフィールドと getter/setter だけのクラスです。  
**貧血モデル** はドメインロジックがサービス層に偏り、エンティティがデータ入れ物になる状態です。

```javascript
// 貧血モデル — Order はデータだけ
class Order {
  get lines() { return this._lines; }
}
class OrderService {
  calculateTotal(order) { /* ロジックはここ */ }
}
```

| 問題 | 対策 |
|------|------|
| ロジックが散在 | ドメインルールをエンティティへ |
| 重複 | 振る舞いを1か所に |
| テストがサービス依存 | 小さな単位でテスト可能に |

[[03_エンティティと値オブジェクト]] も参照。

---

## 4. 分割しすぎ・分割不足の見分け方

| 症状 | 診断 | 対策 |
|------|------|------|
| 1 変更で10ファイル | 分割しすぎ | 関連クラスをまとめる |
| 1 クラスが数千行 | 分割不足 | SRP で分割 |
| 名前が `Helper` だらけ | 責務不明 | ドメイン語で命名 |
| 常に3クラスセットで動く | 過剰分割 | 集約・1クラスに統合検討 |

**変化の理由** と **凝集度** を物差しにします。

---

## 5. 最初のクラス設計案を作るワークショップ

1. **要件を3行で要約** する
2. **名詞リスト** を作り、候補を10個以内に絞る
3. **主要ユースケース1つ** を選び、動詞を配置する
4. **クラス図をスケッチ**（完璧不要）
5. **「ここが変わりそう」** をマークし、境界を確認
6. **ペアで説明** — 説明できなければ責務が曖昧

```text
  15分: 名詞抽出
  15分: 動詞配置
  15分: 図スケッチ
  15分: レビュー
```

詳細な GRASP 判断は [[02_GRASP]] へ。

---

## まとめ

- 名詞からクラス候補、動詞から振る舞いの配置
- データと振る舞いは同じクラスに（貧血モデルを避ける）
- 分割は変化の理由と凝集度で判断
- 短いワークショップで最初の設計案を作れる
