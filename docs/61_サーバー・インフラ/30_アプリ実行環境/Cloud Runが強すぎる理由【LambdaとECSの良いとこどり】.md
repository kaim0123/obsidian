## 詳しい要約

**テーマ：Lambda と ECS のトレードオフを解消する Google Cloud の Cloud Run**

AWS で安く API を動かそうとすると、実質 Lambda（安いが制限が多い）か ECS（安定しているが高い）の二択になり、そのトレードオフに悩み続けることになる。Google Cloud の Cloud Run は「ゼロスケールできるのに ECS 並みのパワーがある」ため、その両方の良いところを取れる。新規サービスを立ち上げるなら真っ先に検討したいほどおすすめ、という話。

---

### Lambda の強み

- **ゼロスケール**：イベント（リクエスト）があったときだけ起動し、終われば停止する。**イベント駆動アーキテクチャ**を実現でき、ワークロードの少ないサービスなら非常に安く運用できる。
  - 事例：Lambda ＋ API Gateway ＋ EFS（EFS 上で SQLite を動かして DB 代わりにする）で、月額約 200 円の社内システムを作った。RDS だと月 5〜6 千円かかる。
- **スケーラビリティが優秀**：リージョンあたりアカウント全体で同時実行数 1000（申請で引き上げ可）。処理 200ms なら秒間約 5000 リクエスト、100ms なら約 1 万リクエストをさばける。
- スケールアウトも速く、10 秒ごとに最大 1000 個の実行環境を追加する。テレビ局の数万同時接続規模の配信システムにも使われている。

### Lambda の弱み

- **ハードクォータ**（緩和できない上限）が多い：
  - タイムアウト 15 分（前段に API Gateway を置くと実質 **約 29〜30 秒**）
  - リクエスト／レスポンスボディ **6MB**（特にきつい。CSV アップロードが大きくなり ECS へ移行した実体験あり）
  - ファイルディスクリプタ 1024 個、解凍後のデプロイパッケージ 250MB
- Durable Functions で「最大 1 年実行」と発表されたが、マルチステップで合計 1 年という意味で、1 回の実行のタイムアウト 15 分は変わらない。
- **コールドスタート**：久しぶりのリクエストでコンテナ初期化から始まり 3〜5 秒の遅延。SSR を Lambda で行うと最初のユーザーが体感 10 秒待たされることもあった。
- Provisioned Concurrency で温めておけるが、常時課金になりゼロスケールのメリットが消える（それなら ECS でよい）。社内システムなど多少の待ちを許容できるなら Lambda で問題ない。

### ECS の強みと弱み

- Lambda の逆：**パワーがあり安定**しているが、ゼロスケールできず常時起動なのでコストは高め（最小スペックでも月 5000〜7000 円程度）。
- タイムアウト・ファイル数・コールドスタートなどの制約がなく、迷ったら多少コストを払っても ECS にしておけ、と言えるほど安定。
- 他の選択肢：App Runner はゼロスケールできず新規受付も停止、EKS はさらに高い。結局「Lambda か ECS か」のトレードオフを考え続けるのが今の AWS の実態。

### Cloud Run が強すぎる理由

| 項目 | Lambda | Cloud Run |
|---|---|---|
| ゼロスケール | 可 | 可（最小インスタンス数 0） |
| パワー | 弱め | 最大 8 vCPU / 32GB メモリ |
| リクエスト／レスポンス上限 | 6MB | 32MB（ストリーミングならそれ以上） |
| タイムアウト | 15 分（API Gateway 経由で約 30 秒） | 最大 60 分 |

- 例えるなら「**Fargate のコンテナを Lambda っぽく使える**」のが Cloud Run。

### 実務で Cloud Run に救われた事例

- 要件：リモートデスクトップを立て、Playwright でスクレイピング的な操作をし、**WebSocket** でユーザー画面からインタラクティブに操作。認証情報を一時保存する機能。
- Lambda が厳しかった理由：15 分タイムアウト、リクエスト後に停止する性質で常駐 WebSocket サーバーと相性が悪い（API Gateway の WebSocket はあるが常駐接続の維持には不向き）。
- ECS が厳しかった理由：たまにしか使わない機能のためにタスクを常駐させるとコストが高い。単発でタスクを起動すると約 1 分かかりユーザー体験が許容できない。
- Cloud Run なら使うときだけ起動して安く、起動は 10〜20 秒程度。**起動時の CPU ブースト**でコールドスタートをさらに改善でき、タイムアウト 60 分、WebSocket も使えたため要件を満たせた。

### まとめ

- サービスの得意・不得意をざっくり頭に入れておくと、技術選定ですぐ判断できる。
- Lambda＝安くてスケールに強いがハードクォータとコールドスタートがある、ECS＝安定・高パワーだが常時コストがかかる。
- Cloud Run はゼロスケールとパワーを両立し、社内ツールやワークロードの少ないサービス、初期フェーズの選択肢として非常に有力。
