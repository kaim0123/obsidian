## 詳しい要約

**テーマ：オートスケールはなぜ急な山に間に合わないのか、どう備えるか**

オートスケールは「混んだと気づく → 決める → 起動する → 温まる」の4つの時間を**山が来た後に**払うため、ゆっくり増える山には間に合っても急な山には数分間間に合わない。設定が正しくても仕組みとして遅れるので、**余裕を残す・前もって増やす・増やす合図と起動を見直す**で備え、減らすときはゆっくり、という回。

---

### よくある場面

- 夜8時に全員へお知らせを送った直後から数分間アプリがつながらない
- 翌朝グラフを見るとサーバーはちゃんと増えていたが、増え切ったのは送信から8分後。設定は間違っていない

### ふつうの動き（ゆっくり増える山）

- 1台で毎秒100件さばけるとして4台で毎秒400件。「さばける量の7割を超えたら1台足す」という決まり
- 合図を超えてから実際に台が加わるまで**いつも5分くらい遅れる**が、ゆっくり増える山なら残りの3割の余裕でその5分を持ちこたえられ、一度も溢れずに朝の山を乗り切る

### 急な山が来たとき

- 4台・毎秒400件の能力に毎秒250件が来ている状態で、お知らせ送信により一気に**毎秒900件近く**へ跳ね上がる。能力を超えた分は長く待たされるか断られ、利用者には「つながらない」に見える
- 監視は CPU 使用率の**直近5分平均が70%を超えたら増やす**。サーバーはもう手一杯なのに、山の前の暇な時間の数字が混ざるので平均は56%とゆっくりしか上がらない
- 8時8分にやっと70%超え → たまたまで増やさないよう1分後にもう一度確かめ、8時9分に6台足すと決める → 起動に約3分 → 起動直後はキャッシュもDB接続も空で遅い（温め中）
- 8時13分半に10台・毎秒1000件になって溢れが止まる。**8分以上、およそ25万件が溢れた**。オートスケールは動いたが間に合わなかった

### 増えるまでの4つの時間

| 時間 | 理由 |
|---|---|
| 1. **気づく** | 数字を何分かならして見るので立ち上がりに遅れる（一瞬の数字は跳ねて落ち着かないのでならす） |
| 2. **決める** | たまたまの揺れで増やさないよう何回か続けて確かめる |
| 3. **起動する** | 機械を用意し OS とアプリが立ち上がるまで。アプリが大きく準備が多いほど長い |
| 4. **温まる** | 起動直後はキャッシュも DB とのつなぎも空っぽで一人前に働けない |

- どれもなくせない理由がある。大事なのは**この時間を山が来た後に払っている**こと。この順番を覚えておくとどこを縮めればよいかが見える

### 溢れている間に起きること

- 振り分け役（ロードバランサー）は**ヘルスチェック**で各サーバーの様子を見ている
- 忙しすぎて返事が間に合わなかったサーバーが「壊れた」と判断されて切り離され、その依頼が残りに回り、残りもさらに苦しくなって次々切り離される
- 1台倒れると隣も倒れやすくなる**ドミノ**。溢れは待っていても自然に収まらず、むしろ広がる。増えた頃には今いる台が減っていることもある

### 温まる前に流すと

- 起動したばかりの台にも振り分け役は他と同じだけ依頼を渡すが、キャッシュが空なので毎回 DB へ取りに行き1件ずつが遅い。その台に当たった人だけ待たされる
- 新しい台が一斉に DB へ行くので DB も混み、増やした直後にかえって遅くなることがある
- 手当て：加わったばかりの台には**少しずつ流す**。**本当に温まってから「準備できた」と返す**（起動しただけですぐ返さない）

### 備え1：余裕を残しておく

- 4台で足りるところを8台で動かしておくと、同じ山でも溢れは約4万件（25万件よりずっと少ない）
- 普段の費用は高くなる。余裕は保険のようなもので、**増えるまでの時間にどれくらいの山が来るか**で量を決める

### 備え2：前もって増やす

- お知らせを送るのは自分たちなので、山の時刻は分かっていた → 7時50分から予定で台を足し始め、7時58分半に10台が揃い、8時5分の山でも溢れは出ない
- 4つの時間は縮んでいない。**払う時刻を山の前にずらしただけ**
- セール開始、ゲームのイベント、テレビで紹介される時刻など、分かっている山は意外と多い。過ぎたら予定通り減らせば費用もその時間分で済む

### 備え3：合図と起動を見直す

- **CPU 平均**はならすので上がるのが遅れる。さらに手一杯になると100%で止まり、2倍足りないのか10倍足りないのか分からない
- **来ている依頼の数**なら来た瞬間に増え、サーバーの状態に関係なく数えられる。900件来て1台100件なら9台必要と一度に分かる（1台あたりの量で割ると台数の計算がまっすぐになる）
- 起動そのものを短くする工夫：起動済みで温めた予備の台を止めて待たせておけば、起動の3分を飛ばせる
- 合図を早くして（前の2つの時間）、起動を短くする（後ろの2つの時間）

### 減らすときの落とし穴

- 少し空いたらすぐ2台減らす → また少し増えて溢れ、慌てて足すが起動に時間がかかる → 増やす・減らすを繰り返し、そのたびに細い溢れが出る
- 減らすときに処理中の依頼を持ったまま止めるとその依頼が消える。**手元の依頼を終わらせてから止める**
- 手当て：空いた状態がしばらく続いてから減らす。**増やすのは早く、減らすのはゆっくり**。この非対称が落ち着いた動きを作る

### AIに書かせた設定のチェックポイント

- 最小台数が1台 → 1台倒れると0台。余裕もなく少しの山ですぐ溢れる
- 増やす合図が CPU 平均90%を10分ならす → 使い切ってからさらに遅れて気づく
- 減らすまでの待ち時間が0秒 → 増減の繰り返しになる
- 準備確認が起動したらすぐOK → 温まる前に他と同じだけ依頼が流れる
- 起動のたびに真っさらな機械から作る → 起動時間が最長になる
- 最大台数（例: 50台）は問題ではない。上限を上げても増えるのが遅ければ間に合わない
- 見るのは「**4つの時間のどれかを長くしていないか**」と「**余裕があるか**」

### ケーススタディ：イベント開始の8分間

- 毎週土曜夜8時のゲームイベント開始から約8分つながらない。自動で増えてはいるが増え切るのは8時9分頃。上限20台にはまだ届いていない
- 選択肢：A 増やす合図を CPU 90%から60%に下げる / B 毎週7時45分に前もって台数を増やす / C 上限を20台から50台に上げる
- 正解は **B**。山の時刻が分かっているので、起動と温めを山の前に払える
- A は気づく時間が少し縮むだけで、起動と温めの数分は残り、山の後に払う形も変わらない。C は上限に届いておらず、「さばききれない」のではなく「増えるのが遅い」だけ

### まとめ

- オートスケールで台が増えるまでには、気づく・決める・起動する・温まるの4つの時間がかかる
- ゆっくりの山には間に合うが、急な山には間に合わず、その間溢れが続いてドミノのように倒れる台も出る
- 備えは、余裕を残す・分かっている山の前に増やす・合図を依頼の数のように早いものにする（起動も短く）
- 減らすのはゆっくり。温まる前に全部の依頼を流さない（クラウドごとの設定画面や項目名は覚えなくてよい）
