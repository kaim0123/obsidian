## 詳しい要約

**テーマ：MySQL が「セキュリティが弱い」と言われる理由と本当の問題**

「MySQL はセキュリティが弱い」という評判は誤解で、弱いのは MySQL ではなく**設定と運用**である。デフォルト設定のまま使う、権限を緩くする、サポート切れのバージョンを使い続けることが事故の原因であり、PostgreSQL に乗り換えても使い方が同じなら同じ事故が起きる、というのが結論。

---

### 第1章 弱いと言われる理由

- 情報漏洩事故で「MySQL を使っていた」と報道されるが、直接の原因は**設定ミスやアプリケーションの脆弱性**であることが多い。
- MySQL は世界で最も使われる DB の 1 つなので、**利用者が多いぶん事故が目立つ**。PostgreSQL や Oracle でも事故は起きているが話題になりにくい。
- 事故が起きるとツールのせいにしたくなる（責任転嫁しやすい）。

### 第2章 弱いのは設定と運用

- MySQL のデフォルト設定には、セキュリティより利便性を優先している部分がある。
  - 古いバージョンでは **root パスワードなし**でインストールでき、直後はパスワードなしで root ログインできた（最近のバージョンでは改善）。
  - **bind-address** の設定ミスで外部接続を許可してしまう（本来は localhost に限定すべき）。
  - クラウドで**セキュリティグループ**を誤り、MySQL のポートがインターネットに公開される。
- **権限設定**が最も致命的：「面倒だから」「動けばいいから」と全ユーザーに全権限を与えるとセキュリティホールになる。

### 第3章 MySQL 5.7 を使い続ける危険性

- MySQL 5.7 は **2023 年 10 月にサポート終了**。以後はセキュリティパッチが出ず、新しい脆弱性が修正されない。
- それでも本番で 5.7 を動かしている現場は多い。理由は **5.7 と 8.0 の互換性**の問題（一部挙動が変わりアプリが動かなくなる可能性）と、大規模テスト・本番停止のリスク → 「動いているから触らない」。
- サポート切れソフトを使い続けるのは**時限爆弾を抱えている状態**。これも MySQL ではなく運用の問題。

### 第4章 安全に使うための対策

| 対策 | 内容 |
|---|---|
| 初期設定 | インストール直後に **mysql_secure_installation** を実行（root パスワード設定、不要ユーザー・匿名ユーザーの削除など） |
| 最小権限の原則 | アプリには SELECT・INSERT・UPDATE・DELETE など必要な権限だけ。DROP は与えない → SQL インジェクションが起きても被害を最小化 |
| 暗号化 | 通信は SSL/TLS、データは透過的データ暗号化（TDE）。個人情報を扱うなら必須 |
| 監査 | 誰がいつ何をしたかを記録し、問題発生時に追跡できるようにする |
| バージョンアップ | 最も大事。最新のセキュリティパッチを適用し、サポート切れは使わない。これができないと他の設定は意味がない |

### 第5章 PostgreSQL なら安全なのか

- 答えは No。デフォルト設定の甘さ、権限の設定ミス、古いバージョンの放置は PostgreSQL でも起きる。
- 「エンタープライズ向けだから」「設計思想が堅牢だから」という主張は根拠が曖昧なことが多い。
- Oracle・SQL Server・PostgreSQL・MySQL のどれでも、設定を間違えれば危険、正しく設定すれば安全。脆弱性の発見頻度や対応速度に差はあるが、**設定と運用の影響の方が大きい**。

### まとめ

- MySQL が弱いと言われるのは、利用者が多く事故が目立つから。
- 事故の多くは設定・権限・古いバージョン放置という運用ミスが原因。
- 対策は初期設定、最小権限、暗号化、監査、そして何よりバージョンアップ。
- DB を乗り換える前に、自分の設定と運用を見直すべき。
