## 第1章 セキュリティの基本概念とセキュリティプログラム

### 1.1 セキュリティの4つの基本用語

セキュリティの議論は、次の4つの用語を正しく使い分けるところから始まります。CCNAでは「この説明はどの用語に当たるか」という形で問われます。

| 用語 | 英語 | 意味 | 例 |
|---|---|---|---|
| 脆弱性 | vulnerability | システムが持っている**弱点そのもの**。攻撃に悪用される可能性がある | パッチ未適用のOSのバグ、初期パスワードのまま、Telnetが有効 |
| 脅威 | threat | 脆弱性を悪用して**被害を与える可能性のあるもの** | 攻撃者、マルウェア、内部不正、災害 |
| エクスプロイト | exploit | 脆弱性を**実際に悪用するための手段** | 攻撃コード、攻撃ツール |
| 緩和策 | mitigation | 脆弱性や脅威による**リスクを減らす対策** | パッチ適用、ACL、MFA、教育 |

4つの関係は一文で覚えると混乱しません。

```
  脅威（攻撃者）が  ──>  エクスプロイト（攻撃手段）を使って  ──>  脆弱性（弱点）を突く
                                                                      ↑
                                              緩和策（パッチ・ACLなど）で防ぐ
```

- 「パッチが適用されていないOSのバグ」は、それ自体が攻撃者でも攻撃コードでもなく、**システム側にある弱点**なので「脆弱性」です（sf-004）。
- 「攻撃者」「マルウェア」は脅威、「攻撃コード」はエクスプロイト、「パッチ適用」は緩和策です。

> 補足: これらの組み合わせで「リスク」（被害が起こる可能性 × 影響の大きさ）を考えます。脆弱性があっても、それを突く脅威やエクスプロイトがなければリスクは小さく、逆に脅威が大きくても脆弱性を塞げばリスクは下がります。

### 1.2 セキュリティプログラム（人・物理面の対策）

ACLやファイアウォールなどの**技術的な対策だけではセキュリティは守れません**。フィッシングやテールゲーティングのように「人」を狙う攻撃には、人への働きかけや物理的な制限が必要です。Ciscoは「セキュリティプログラム」の要素として次の3つを挙げています。

| 要素 | 内容 | 具体例 |
|---|---|---|
| ①ユーザーの意識向上（user awareness） | **全員**が日頃から脅威に気を付けるようにする | 不審なメールの見分け方の周知、**模擬フィッシングメール**の定期送信、ポスター、注意喚起メール |
| ②ユーザートレーニング（user training） | **特定の役割の人**に正式な研修を行う | 新任のネットワーク管理者向けのセキュリティ研修、開発者向けのセキュアコーディング講座 |
| ③物理的なアクセス制御（physical access control） | 重要な場所・機器に物理的に近づけないようにする | サーバ室のカードキー、生体認証、監視カメラ、共連れ防止ゲート、入退室記録 |

「意識向上」と「トレーニング」の違いは対象と形式です。

```
ユーザーの意識向上  … 対象：全社員     形式：日常的な周知・模擬訓練（非公式でもよい）
ユーザートレーニング … 対象：特定の役割  形式：正式な研修・講座
```

sf-007 の「全社員に不審なメールの見分け方を伝え、定期的に模擬フィッシングメールを送って確認する」は、対象が**全社員**で日常的な取り組みなので「ユーザーの意識向上」です。

一方、選択肢に出てくる **ACL** と **AAA** は「技術的な対策」です。

- ACL: ルータなどで通信を許可・拒否する（第6章）
- AAA: 認証・認可・アカウンティングで、機器やネットワークへのアクセスを管理する（第5章）

### ひっかけポイント・よくある誤解

- **脆弱性と脅威の混同**: 「脅威」は攻撃者やマルウェアなど“害を与える側”。「脆弱性」は“守る側の弱点”。バグや設定ミスは脆弱性。
- **エクスプロイトと脅威の混同**: エクスプロイトは「手段（攻撃コードやツール）」。攻撃者本人は脅威。
- **緩和策**は「リスクを減らす対策」で、脆弱性そのものではない。パッチ適用やACLは緩和策。
- 模擬フィッシングメールは「ACL」でも「AAA」でもなく人への対策。**技術的対策（ACL・AAA）と人の対策を区別**する。
- 「物理的なアクセス制御」はサーバ室への入室制限など。メールの見分け方の周知は物理対策ではない。

### 試験のポイント

- 脅威がエクスプロイトで脆弱性を突き、緩和策で防ぐ、という関係で4用語を整理する。
- セキュリティプログラムの3要素：**ユーザーの意識向上、ユーザートレーニング、物理的なアクセス制御**。
- 全員向け＝意識向上、特定の役割向けの正式な研修＝トレーニング。
- 技術的な対策だけでなく、人と物理面の対策を組み合わせる。

## 第2章 攻撃手法とマルウェア

CCNAでは、代表的な攻撃の名前と内容を対応させる問題が多く出ます。「何を狙うか（人・サービス・情報・L2の仕組み）」で分類すると覚えやすくなります。L2（スイッチ）を狙う攻撃（MACフラッディング、DHCPスタベーション、VLANホッピング、ARPスプーフィングなど）は、対策とセットで第7章で扱います。

### 2.1 攻撃の分類マップ

```
攻撃
├─ 人をだます（ソーシャルエンジニアリング）
│    ├─ フィッシング（メール＋偽サイト）
│    │    └─ スピアフィッシング（特定の人物を狙う）
│    ├─ ビッシング（電話・音声）
│    ├─ スミッシング（SMS）
│    └─ テールゲーティング／共連れ（物理的なすり抜け）
├─ サービスを止める
│    ├─ DoS（1台から）
│    └─ DDoS（ボットネットなど多数の端末から）
├─ 情報を集める
│    └─ 偵察攻撃（DNS問い合わせ、pingスイープ、ポートスキャン）
├─ 通信に割り込む／なりすます
│    ├─ 中間者攻撃（man-in-the-middle）
│    └─ スプーフィング（送信元IP/MACの偽装）
├─ パスワードを破る
│    ├─ ブルートフォース（総当たり）
│    ├─ 辞書攻撃
│    └─ パスワードクラッキング（盗んだハッシュから割り出す）
└─ マルウェア
     ├─ ウイルス／ワーム／トロイの木馬
     └─ ランサムウェア
```

### 2.2 ソーシャルエンジニアリング

**ソーシャルエンジニアリング**は、技術的な弱点ではなく「人の心理的な隙」を突いて情報を盗む手法の総称です。機器の設定だけでは防ぎきれないため、第1章の「ユーザーの意識向上」が主な対策になります。

| 手法 | 手段 | 説明 |
|---|---|---|
| フィッシング | メール＋偽Webサイト | 銀行などの正規の組織を装ったメールで偽サイトへ誘導し、ID・パスワードを入力させる |
| スピアフィッシング | メール | 特定の人物・組織を狙い撃ちにしたフィッシング |
| ビッシング（vishing） | 電話（音声） | 電話で人をだまして情報を聞き出す |
| スミッシング（smishing） | SMS | ショートメッセージを使ったフィッシング |
| テールゲーティング（共連れ） | 物理 | 入館カードを持つ社員の後ろについて、カードを使わずに入り込む |

- sf-005: 「正規の組織を装ったメール → 偽のWebサイト → ID/パスワード入力」は**フィッシング**。
- sf-036: 「社員の後ろについてサーバ室へ入り込む」は**テールゲーティング（共連れ）**。物理的なアクセス制御をすり抜けるソーシャルエンジニアリングの一種です。

**なぜ物理セキュリティが重要か**: ネットワーク機器に物理的に触れられると、コンソールポートからパスワードの回復操作（ROMMONでコンフィグレジスタを変更して起動するなど）を行い、設定を書き換えられてしまう恐れがあります。どれほど強いパスワードを設定しても、物理的に触られれば突破され得るのです。共連れの対策は、一人ずつしか通れないゲート（セキュリティゲート）、監視カメラ、入退室の記録、社員への教育などです。

### 2.3 DoS / DDoS

| 攻撃 | 送信元 | 特徴 |
|---|---|---|
| DoS（Denial of Service） | 1台 | 大量の通信などでサーバやネットワークを過負荷にし、サービスを止める |
| DDoS（Distributed DoS） | 多数（ボットネット） | マルウェアに感染させた多数の端末から一斉に攻撃。送信元が多数あるため、送信元を1つずつ遮断する対策が効きにくい |

```
         [攻撃者] ── 指令（C&C） ──┐
                                    v
   ボット  ボット  ボット  ボット  ボット   ← マルウェアに感染して乗っ取られた端末群（ボットネット）
     \      \      |      /      /
      \______\_____|_____/______/
                   v
             [標的のサーバ]   ← 処理しきれずサービス停止
```

sf-006 の「マルウェアに感染させた多数の端末から一斉に大量の通信」は**DDoS攻撃**です。

選択肢に出る他の用語も確認しておきます。

- **スプーフィング**: 送信元のIPアドレスやMACアドレスを偽装する手法（なりすまし）。DoSの送信元隠しやARPスプーフィングなどに使われる。
- **パスワードクラッキング**: 盗んだパスワードのハッシュ値などから、元のパスワードを割り出す攻撃。
- **ブルートフォース攻撃**: 考えられるパスワードを片っ端から試して突破する総当たり攻撃。対策は長いパスワード、ログイン試行の制限（`login block-for`、第4章）、MFA。
- **中間者攻撃（man-in-the-middle）**: 通信する2者の間に入り込み、通信を盗聴・改ざんする攻撃。ARPスプーフィングや偽DHCPサーバ（第7章）はこの攻撃の入口になる。

### 2.4 偵察攻撃（reconnaissance）

本格的な攻撃の前に、標的のネットワークの情報を集める段階です。

| 手法 | 分かること |
|---|---|
| DNSの問い合わせ（whois、nslookupなど） | 組織が使うドメイン・IPアドレス範囲、公開サーバ |
| pingスイープ | どのアドレスでホストが**動いているか** |
| ポートスキャン | ホストで**どのサービス（ポート）が開いているか** |

```
① DNS/whois で対象のアドレス範囲を調べる
      ↓
② pingスイープ   203.0.113.1 〜 .254 に ping → 応答したホストを特定
      ↓
③ ポートスキャン  応答したホストの TCP 22/23/80/443 ... を調べる → 動いているサービスを特定
      ↓
④ 見つけたサービスの脆弱性を突く本格的な攻撃へ
```

sf-034 の「pingスイープで動いているホストを探し、ポートスキャンで開いているサービスを調べる」は**偵察攻撃**です。

対策は「集められる情報を減らす」こと：不要なサービスを止める、ACLで不要な通信（外部からのICMPなど）を遮断する、IPSで不審なスキャンを検知する。

### 2.5 マルウェア

マルウェア（悪意のあるソフトウェア）の違いは「**どうやって広がるか**」で整理します。

| 種類 | 広がり方 | 自己複製 | 利用者の操作 |
|---|---|---|---|
| ウイルス | 他のプログラムやファイルに**寄生**し、それが実行されたときに広がる | する | 必要（ファイルを開く・実行する） |
| ワーム | **ネットワークを通じて自動で**自分自身を複製して広がる（OSなどの脆弱性を突く） | する | **不要** |
| トロイの木馬 | 便利なソフトに**見せかけて**インストールさせ、裏で不正な動作をする | しない | 必要（インストール） |
| ランサムウェア | データを**暗号化**して使えなくし、元に戻すための**身代金**を要求する | （種類による） | （種類による） |

sf-035 の「利用者がファイルを開くなどの操作をしなくても、ネットワークを通じて自分自身を複製して広がる」は**ワーム**です。ワームは短時間で大量の端末に広がるため、**OSのパッチ適用**（脆弱性を塞ぐ）と**不要なポートの遮断**（ACL・ファイアウォール）が重要な対策です。

> ランサムウェアは「何をするか（暗号化して身代金）」で定義される名前で、広がり方の分類とは軸が違います。ワーム型のランサムウェアも存在します。sf-034 ではランサムウェアは「偵察（情報収集）」ではない、という意味の誤答として出てきます。

### ひっかけポイント・よくある誤解

- フィッシングは技術的な攻撃ではなく**人をだます**攻撃。DoS（過負荷でサービス停止）、中間者攻撃（間に入って盗聴・改ざん）、ブルートフォース（総当たり）とは別物。
- **DoSとDDoSの違いは送信元の数**。「多数の端末から一斉に」ならDDoS。
- スプーフィングは「偽装」、ソーシャルエンジニアリングは「人の心理の隙」、パスワードクラッキングは「ハッシュから元のパスワードを割り出す」。どれも「多数の端末からの大量通信」ではない。
- 偵察攻撃の目的は**情報収集**。DoS（停止させる）、ブルートフォース（パスワード突破）、ランサムウェア（身代金）と目的が違う。
- ウイルスは**ファイルに寄生して実行されて広がる**。「操作不要で自動で広がる」ならワーム。トロイの木馬は**自己複製しない**。
- テールゲーティング（物理的な共連れ）と、ビッシング（電話）、スミッシング（SMS）、フィッシング（メール＋偽サイト）を手段で区別する。

### 試験のポイント

- フィッシング＝偽メール＋偽サイト。特定人物狙いはスピアフィッシング。対策の中心は**ユーザーの意識向上（教育）**。
- DDoS＝ボットネットなど多数の端末からのDoS。
- 偵察攻撃＝DNS問い合わせ・pingスイープ・ポートスキャンで情報収集。
- ワーム＝ネットワーク経由で自動拡散。ウイルス＝寄生して実行で拡散。トロイの木馬＝正規ソフトを装う。
- テールゲーティング＝共連れ。物理的に機器へ触れられるとパスワード回復で乗っ取られる恐れ。

## 第3章 認証の基礎（パスワードポリシーと多要素認証）

### 3.1 認証の3要素

**認証**とは「あなたは本当にその人か」を確認することです。確認に使う情報は3種類に分けられます。

| 要素 | 英語のイメージ | 例 |
|---|---|---|
| 知識 | Something you **know**（知っているもの） | パスワード、PIN、秘密の質問の答え |
| 所持 | Something you **have**（持っているもの） | スマートフォン（ワンタイムコードのアプリ）、ICカード、ハードウェアのセキュリティキー、証明書の入った端末 |
| 生体 | Something you **are**（本人の身体的な特徴） | 指紋、顔、静脈、虹彩 |

sf-043: ICカード、スマートフォン、ハードウェアのセキュリティキーは**所持**の要素です。

### 3.2 多要素認証（MFA）

**多要素認証（MFA: Multi-Factor Authentication）**は、**異なる種類**の要素を2つ以上組み合わせる認証です。

```
パスワード（知識） ＋ スマホのワンタイムコード（所持）   → 多要素（MFA）◯
パスワード（知識） ＋ 指紋（生体）                       → 多要素（MFA）◯
パスワード（知識） ＋ 秘密の質問（知識）                 → 同じ種類が2つ ＝ 多要素ではない ✕
```

sf-011: 「パスワードを入力した後に、スマートフォンのアプリに表示されるワンタイムコードの入力も求める」は、知識＋所持の組み合わせなので**多要素認証（MFA）**です。パスワードが漏れても、攻撃者がスマートフォンを持っていなければログインできません。

混同しやすい用語:

| 用語 | 意味 | MFAとの違い |
|---|---|---|
| シングルサインオン（SSO） | **一度の認証**で複数のシステムを利用できるようにする仕組み | 「認証の回数を減らす」仕組みで、要素の数とは関係ない |
| パスワードの複雑化 | パスワードを長く、推測しにくくするルール | パスワードという**1つの要素**だけの対策 |
| ACLによるアクセス制御 | IPアドレスなどの条件で通信を許可・拒否 | **ユーザーの認証方式ではない** |

パスワードの**代わり**になる認証方式としては、**証明書**（デジタル証明書による認証）や**生体認証**があります。

### 3.3 パスワードの管理方針（パスワードポリシー）

sf-037 の正解は「十分な長さの推測されにくいパスワードにし、他のシステムと使い回さない」です。理由を一つずつ理解しておきましょう。

| 方針 | 正しいか | 理由 |
|---|---|---|
| 十分な長さ・推測されにくい・使い回さない | ◯ | **長さは強度に大きく影響**する（総当たりの組み合わせ数が指数的に増える）。使い回すと、1か所で漏れたときに他も突破される |
| 覚えやすい短い単語や誕生日 | ✕ | **辞書攻撃**や推測で簡単に突破される |
| すべての機器で同じパスワード | ✕ | 1台のパスワードが漏れると、**すべての機器に侵入**されてしまう |
| 紙に書いて機器に貼る | ✕ | 機器に近づいた人に知られてしまう（物理セキュリティの問題） |

長さが効く理由の目安（使える文字が英大小文字＋数字の62種類の場合）:

```
 8文字: 62^8  ≒ 2.2 × 10^14 通り
12文字: 62^12 ≒ 3.2 × 10^21 通り   ← 4文字増えるだけで約1,400万倍
```

パスワードだけに頼らない工夫:

- **MFA、証明書、生体認証**を組み合わせる。
- 多数の機器のアカウントは**AAAサーバで一元管理**する（第5章）。退職者のアカウントの無効化なども1か所で確実に行える。
- 機器側では最小文字数の強制（`security passwords min-length`）、ログイン試行の制限（`login block-for`）も使える（第4章）。

### ひっかけポイント・よくある誤解

- **SSOはMFAではない**。SSOは一度の認証で複数システムを使えるようにする仕組み。
- **パスワードの複雑化は1要素だけの対策**であり、MFAではない。
- **パスワード＋秘密の質問はMFAではない**（どちらも知識）。
- ICカードやスマートフォンは「所持」。「どの要素にも当てはまらない」は誤り。
- ACLはユーザーの認証方式ではない。
- 「覚えやすさ」「管理の簡単さ」を理由にした短いパスワード・共通パスワード・貼り紙はすべて誤り。

### 試験のポイント

- 認証の3要素：**知識・所持・生体**。MFAは**異なる種類**を2つ以上。
- ワンタイムコードのアプリ（スマホ）＝所持。
- パスワードは長く、推測されにくく、使い回さない。
- パスワードの代替・追加：MFA、証明書、生体認証。多数の機器はAAAで一元管理。

### 関連問題

sf-011, sf-037, sf-043

## 第4章 機器へのアクセス保護（パスワード・ライン・SSH・特権レベル）

ルータやスイッチ自体が乗っ取られると、ACLもVPNもすべて書き換えられてしまいます。この章では「機器にログインする入口」をどう守るかを、IOSの設定コマンドとともに学びます。

### 4.1 IOSのモードとログインの入口

```
                     コンソールケーブル（物理）        ネットワーク経由（Telnet/SSH）
                            │                                 │
                       line con 0                      line vty 0 4（0〜15）
                            │  ← password + login / login local で認証
                            v                                 v
                  ┌──────────────────────────────────────────────┐
                  │ ユーザーEXECモード   Router>     （特権レベル1）  │
                  └──────────────────────────────────────────────┘
                            │ enable  ← enable secret（または enable password）で認証
                            v
                  ┌──────────────────────────────────────────────┐
                  │ 特権EXECモード      Router#     （特権レベル15） │
                  └──────────────────────────────────────────────┘
                            │ configure terminal
                            v
                  グローバル設定モード  Router(config)#
```

守るべき入口は次の3つです。

| 入口 | 設定場所 | 用途 |
|---|---|---|
| コンソール | `line con 0` | ケーブルで機器に直接接続する（IPアドレス不要） |
| vty（仮想端末） | `line vty 0 4`（機種により `0 15`） | Telnet/SSHでネットワーク経由で接続する |
| 特権EXECモード | `enable secret` | `enable` で設定変更ができるモードに入る |

### 4.2 ラインのパスワード：password と login

ラインにパスワードを設定するには、`password` と `login` の**両方**が必要です。`password` だけでは「パスワードを持っている」だけで、確認は行われません。`login` を設定して初めてパスワードが要求されます。

```
Router(config)# line con 0
Router(config-line)# password cisco123
Router(config-line)# login
Router(config-line)# exit
```

コンソール接続時の動作:

```
User Access Verification

Password:          ← 入力した文字は表示されない
Router>
```

sf-010 の正解は `line con 0 → password cisco123 → login` です。

- `line vty 0 4 → password ... → login` は**リモート接続用**のラインで、コンソールには影響しない。
- `enable secret` は**特権EXECモード**に入るときのパスワードで、コンソールに接続した時点では要求されない。
- `username admin secret ...` はローカルユーザーを作るだけで、ラインに `login local` を設定しないと使われない。

#### ユーザー名とパスワードで認証する（login local）

```
Router(config)# username admin secret Cisco!2026
Router(config)# line con 0
Router(config-line)# login local          ← ローカルユーザーのデータベースで認証
Router(config-line)# line vty 0 4
Router(config-line)# login local
```

```
User Access Verification

Username: admin
Password:
Router>
```

| ラインの設定 | 認証の方法 |
|---|---|
| `login` | そのラインの `password` で認証（ユーザー名なし） |
| `login local` | `username` で作成したローカルユーザーで認証 |
| （AAA使用時）`login authentication ...` / default | AAAの方法リストで認証（第5章） |

### 4.3 password と secret（平文・タイプ7・ハッシュ）

IOSのパスワード保存方式は「**password＝平文（またはタイプ7）、secret＝ハッシュ**」と覚えます。

| コマンド | 保存形式 | 安全性 |
|---|---|---|
| `enable password XXX` | 平文（タイプ0） | 低い。`show running-config` でそのまま見える |
| `enable secret XXX` | ハッシュ（タイプ5＝MD5、8＝PBKDF2-SHA256、9＝scrypt） | 高い。復元が困難 |
| `username U password XXX` | 平文（タイプ0） | 低い |
| `username U secret XXX` | ハッシュ（タイプ5/8/9） | 高い |
| `line ... password XXX` | 平文（タイプ0） | 低い |
| 上記の平文 ＋ `service password-encryption` | タイプ7 | 低い（簡単に復号できる） |

#### enable password と enable secret の両方を設定した場合

```
Router(config)# enable password cisco
Router(config)# enable secret Str0ng!Pass
```

このとき `enable` で使えるのは **enable secret の方だけ**です（sf-008）。enable secret が存在すると enable password は無視されます。両方を順番に入力する仕組みも、どちらでも入れる仕組みもありません。実務では enable secret だけを使います。

```
Router# show running-config | include enable
enable secret 9 $9$8hG7bW2yQ0n7yE$Zk0p...（ハッシュ値）
enable password cisco          ← 平文で見えてしまう（しかも使われない）
```

#### service password-encryption

```
Router(config)# service password-encryption
```

設定ファイル内の**平文のパスワード**（line の password、enable password、username ... password）を、**弱い方式（タイプ7）**で暗号化して表示するコマンドです（sf-009）。

```
! 実行前
line vty 0 4
 password cisco123
! 実行後
line vty 0 4
 password 7 0822455D0A16544541
```

- 目的は「**肩越しにのぞかれても読めない**」程度。タイプ7は解読ツールで簡単に元に戻せる。
- **通信は暗号化しない**（通信の暗号化はSSHやVPN）。
- ログインの動作は変わらない。
- 強い保護が必要なら `enable secret` や `username ... secret` を使う。

sf-041: ローカルユーザーのパスワードをハッシュで保存するのは `username admin secret Cisco!2026`。`username admin password ...` は平文で保存され、service password-encryption を使っても弱いタイプ7になるだけです。

```
Router# show running-config | include username
username admin secret 9 $9$nhEmQVczB7dqsO$X.HsgL6x1il0RxkOSSvyQYwucySCt7qFm4v7pqCxkKM
```

### 4.4 パスワードの最小文字数：security passwords min-length

```
Router(config)# security passwords min-length 10
Router(config)# enable secret short
% Password too short - must be at least 10 characters. Password configuration failed
```

- グローバル設定のコマンド（sf-038）。
- **これ以降に設定する**パスワード（enable secret、username、line の password など）に適用される。
- すでに設定されている短いパスワードは**自動では変わらない**ので、設定し直す必要がある。

誤答の確認:

- `service password-encryption` … 表示を隠すだけで長さは制限しない。
- `enable secret 10` … 特権EXECモードのパスワードを「10」にしてしまう。
- `exec-timeout 10 0` … 10分無操作で切断する line の設定。

### 4.5 ブルートフォース対策：login block-for

```
Router(config)# login block-for 120 attempts 3 within 60
```

読み方:

```
login block-for 120   attempts 3   within 60
                 │            │           │
                 │            │           └─ 失敗を数える期間（秒）：60秒以内に
                 │            └──────────── 失敗回数：3回失敗したら
                 └───────────────────────── 禁止する時間（秒）：120秒間ログインを受け付けない
```

sf-039 の「60秒以内に3回失敗したら、その後120秒間ログインを受け付けない」は `login block-for 120 attempts 3 within 60` です。数字の位置を逆にした `login block-for 60 attempts 3 within 120` は誤り。

- グローバル設定のコマンド。総当たり攻撃（ブルートフォース）の速度を大きく落とせる。
- ブロック中（quiet mode）は**管理者もログインできなくなる**。そこで、管理用PCのアドレスだけはブロックの対象外にする `login quiet-mode access-class` を組み合わせることがある。

```
Router(config)# access-list 5 permit 192.168.100.0 0.0.0.255
Router(config)# login quiet-mode access-class 5
Router# show login
     A login delay of 1 seconds is applied.
     Quiet-Mode access list 5 is applied.
     Router enabled to watch for login Attacks.
     If more than 3 login failures occur in 60 seconds or less,
     logins will be disabled for 120 seconds.
```

### 4.6 無操作セッションの自動切断：exec-timeout

```
Router(config)# line con 0
Router(config-line)# exec-timeout 5 0      ← 5分0秒
Router(config)# line vty 0 4
Router(config-line)# exec-timeout 5 0
```

| 設定 | 意味 |
|---|---|
| `exec-timeout 5 0` | 5分（「**分 秒**」の順） |
| `exec-timeout 0 5` | 5**秒**（順番を間違えた例） |
| `exec-timeout 0 0` | タイムアウト無効（切断しない）。本番では非推奨 |
| （未設定） | デフォルトは**10分** |

- line（`line con 0`、`line vty 0 4`）の中で設定する（sf-040）。
- ログインしたまま放置された画面を他人に操作される危険を防ぐ。
- 検証環境では `0 0` にすることもあるが、本番環境では避ける。
- `login block-for` はログイン**失敗**による制限で、無操作セッションの切断とは別物。

### 4.7 SSHの設定（Telnetを使わない理由）

**TelnetではなくSSHを使う主な理由は、通信内容が暗号化されるため**です（sf-001）。Telnetはパスワードを含むすべての通信を**平文**で送るので、盗聴されるとユーザー名やパスワードがそのまま読まれてしまいます。

```
Telnet（TCP 23）:  PC ── "admin" "cisco123" "show run" ──> ルータ   ← 盗聴すれば丸見え
SSH   （TCP 22）:  PC ── "x9#Fq0...暗号文..." ────────────> ルータ   ← 読めない
```

| 誤った理由 | 正しくは |
|---|---|
| 通信速度が速い | 速度は理由ではない。暗号化処理の分むしろわずかに負荷が増える |
| 設定が不要 | 逆。ホスト名・ドメイン名・RSA鍵などの設定が必要 |
| IPアドレスがなくても接続できる | SSHもTelnetもIPで通信する。IPなしで接続するならコンソールケーブル |

#### SSHの設定手順

```
Router(config)# hostname R1                          ! ① ホスト名（デフォルトの Router では鍵を作れない）
R1(config)# ip domain-name example.com               ! ② ドメイン名（①②から鍵の名前が決まる）
R1(config)# crypto key generate rsa modulus 2048     ! ③ RSA鍵の生成（SSHv2には768ビット以上）
R1(config)# ip ssh version 2                         ! ④ SSHv2を使う（推奨）
R1(config)# username admin secret Cisco!2026         ! ⑤ ローカルユーザーの作成
R1(config)# line vty 0 4
R1(config-line)# login local                         ! ⑥ ローカルユーザーで認証
R1(config-line)# transport input ssh                 ! ⑦ vtyへの接続をSSHだけに（Telnetを禁止）
R1(config-line)# exec-timeout 5 0
```

確認:

```
R1# show ip ssh
SSH Enabled - version 2.0
Authentication methods:publickey,keyboard-interactive,password
Authentication timeout: 120 secs; Authentication retries: 3
...
R1# show ssh
Connection Version Mode Encryption  Hmac         State           Username
0          2.0     IN   aes256-ctr  hmac-sha2-256 Session started admin
```

さらに、vtyへの接続元を管理用ネットワークに限定するには `access-class` を使います（第6章 6.9、sf-030）。

### 4.8 特権レベル（0〜15）

| レベル | 内容 |
|---|---|
| 0 | `logout`、`enable`、`disable`、`exit`、`help` など、ごく一部のコマンドのみ |
| 1 | **ユーザーEXECモード**（`Router>`）。確認用の一部のコマンドだけ使える |
| 2〜14 | **カスタマイズ用**。管理者が使えるコマンドを割り当てて使う |
| 15 | **特権EXECモード**（`Router#`）。すべてのコマンドを実行できる。`enable` で入るレベル |

sf-042 の正解は **15** です。

```
Router(config)# username operator privilege 5 secret Op3rator!Pass
Router(config)# privilege exec level 5 show running-config
Router# show privilege
Current privilege level is 15
```

ユーザーごとに特権レベルを割り当てると、「オペレーターには確認用のコマンドだけを許可する」といった制御ができます。これは**認可（何をしてよいか）**の一種です。より細かく、多数の機器で一元的に制御したい場合は、**AAAの認可（TACACS+など）**を使います（第5章）。

### 4.9 機器のアクセス保護 チェックリスト

```
hostname R1
security passwords min-length 10                 ! 最小文字数
enable secret <強いパスワード>                     ! secret を使う（password は使わない）
service password-encryption                      ! 平文で残るものをタイプ7で隠す（補助）
username admin privilege 15 secret <強いパスワード>
login block-for 120 attempts 3 within 60         ! 総当たり対策
ip domain-name example.com
crypto key generate rsa modulus 2048
ip ssh version 2
access-list 10 permit 192.168.100.0 0.0.0.255    ! 管理用ネットワーク
!
line con 0
 login local
 exec-timeout 5 0
line vty 0 4
 access-class 10 in                              ! 接続元の制限
 login local
 transport input ssh                             ! SSHのみ
 exec-timeout 5 0
```

### ひっかけポイント・よくある誤解

- **SSHを使う理由は速度でも設定の簡単さでもなく「暗号化」**。SSHはむしろ設定が必要（hostname、ip domain-name、RSA鍵、ユーザー、transport input ssh）。
- **enable password と enable secret の両方がある場合、使えるのは secret だけ**。「どちらでも」「両方を順番に」は誤り。
- **service password-encryption は通信を暗号化しない**し、**強力でもない**（タイプ7は簡単に復号可能）。
- **`password` だけでは認証されない**。`login` が必要。`username` を作っても `login local` がないと使われない。
- vty の設定はコンソールに影響しない。enable secret はコンソール接続時点では要求されない。
- `username ... password` は平文。ハッシュにしたいなら `username ... secret`。
- `security passwords min-length` は**既存の**パスワードを変えない。
- `login block-for X attempts Y within Z`：X＝禁止時間、Z＝失敗を数える期間。**数字の位置**に注意。
- `exec-timeout` は「**分 秒**」の順。`0 5` は5秒、`0 0` は無効。デフォルトは10分。
- 特権EXECは15。1はユーザーEXEC、0はごく一部のみ、2〜14はカスタマイズ用。

### 試験のポイント

- password＝平文/タイプ7、secret＝ハッシュ（5/8/9）。enable も username も secret を使う。
- ラインは `password` ＋ `login`、またはローカルユーザー ＋ `login local`。
- SSHの必須設定：hostname、ip domain-name、crypto key generate rsa、ローカルユーザー、`transport input ssh`。
- `security passwords min-length`、`login block-for`、`exec-timeout` の書式と意味。
- 特権レベル15＝特権EXEC、1＝ユーザーEXEC。

### 関連問題

sf-001, sf-008, sf-009, sf-010, sf-038, sf-039, sf-040, sf-041, sf-042

## 第5章 AAA（TACACS+ / RADIUS / 802.1X）

### 5.1 AAAの3つの機能

**AAA**は、アクセスを管理する3つの機能の頭文字です。

| 機能 | 問い | 例 |
|---|---|---|
| 認証（Authentication） | **あなたは誰か** | ユーザー名とパスワードで本人確認 |
| 認可（Authorization） | **何をしてよいか** | このユーザーは `show` だけ、あのユーザーは `configure` も可 |
| アカウンティング（Accounting） | **何をしたか** | 誰が、いつログインし、どのコマンドを実行したかを記録 |

```
 ユーザー ──①ログイン──> [ルータ] ──②「この人は本物？」──────> [AAAサーバ]
                                 <──③認証OK───────────────────
          ──④コマンド──> [ルータ] ──⑤「このコマンドを許可する？」─> （認可）
                                 <──⑥許可/拒否─────────────────
                         [ルータ] ──⑦「誰が何をしたか」の記録──> （アカウンティング）
```

sf-024: 「ログインしたユーザーが、どのコマンドを実行できるかを制御する」は**認可（Authorization）**です。暗号化はAAAの要素ではありません。

**なぜAAAサーバを使うのか**: 機器が100台あると、ローカルユーザーを100台それぞれで作成・変更・削除しなければなりません。AAAサーバ（例：**Cisco ISE**）を使えば、ユーザーを一元管理でき、退職者のアカウントの無効化も1か所で確実に行えます。

### 5.2 TACACS+ と RADIUS

機器（ルータ、スイッチ、WLCなど）とAAAサーバの間の通信には、TACACS+ か RADIUS を使います。

| 項目 | TACACS+ | RADIUS |
|---|---|---|
| 開発・標準 | **Cisco**が開発 | **IETF**の標準（オープン） |
| トランスポート | **TCP 49** | **UDP 1812（認証/認可）、1813（アカウンティング）**（古い実装では1645/1646） |
| 暗号化の範囲 | パケットの**本文全体**を暗号化 | **パスワードだけ**を暗号化 |
| AAAの扱い | 認証・認可・アカウンティングを**個別**に扱える | 認証と認可を**まとめて**扱う |
| コマンドごとの認可 | できる | 基本的にできない |
| 主な用途 | **ネットワーク機器にログインする管理者**の認証とコマンド制御 | **ネットワークを利用するユーザー**の認証（無線LANの802.1X、有線802.1X、VPN接続） |

覚え方:

```
TACACS+ … TCP / 全体暗号化 / Cisco / 機器の管理者（デバイス管理）
RADIUS  … UDP / パスワードだけ / IETF標準 / ネットワーク利用者（ネットワークアクセス）
```

sf-025 の正解は「TCP（49番）を使い、パケットの本文全体を暗号化する」です。「UDPでパスワードだけ暗号化」はRADIUSの特徴、「IEEEが定めたオープンな標準」は誤り（TACACS+はCisco開発、RADIUSはIETF標準）、「無線LANの暗号化方式」はWPA2/WPA3のことです。

### 5.3 IOSでのAAA設定と方法リスト

```
R1(config)# username admin secret Local!Backup1          ! サーバ障害時の予備のローカルユーザー
R1(config)# aaa new-model                                 ! ① AAAを有効化（すべての始まり）
R1(config)# tacacs server TAC1                            ! ② TACACS+サーバの定義
R1(config-server-tacacs)# address ipv4 192.168.100.10
R1(config-server-tacacs)# key T@cacsKey
R1(config-server-tacacs)# exit
R1(config)# aaa authentication login default group tacacs+ local    ! ③ 認証の方法リスト
R1(config)# aaa authorization exec default group tacacs+ local      ! （認可）
R1(config)# aaa accounting commands 15 default start-stop group tacacs+   ! （アカウンティング）
```

#### 方法リストの評価（sf-054）

`aaa authentication login default group tacacs+ local` は、認証方法を**左から順に**試します。ただし「次へ進む」のは**前の方法が使えない（エラー・無応答）ときだけ**です。

```
ログイン要求
   │
   v
[TACACS+サーバに問い合わせ]
   │
   ├─ 応答あり：認証成功 ──────> ログイン許可
   ├─ 応答あり：認証失敗（PASS/FAIL の FAIL）──> ログイン拒否（ここで終了。local は試さない）
   └─ 応答なし（サーバ停止・到達不能＝ERROR）
          │
          v
     [ローカルユーザー（local）で認証]
          ├─ 成功 ─> ログイン許可
          └─ 失敗 ─> ログイン拒否
```

| 解釈 | 正誤 |
|---|---|
| TACACS+サーバに**到達できない場合に**ローカルユーザーで認証する | ◯ |
| TACACS+とローカルの**両方**で成功する必要がある | ✕（予備であって二重認証ではない） |
| TACACS+で**パスワードが間違っていた**場合にローカルで再認証 | ✕（サーバが「失敗」を返したらそこで終了） |
| ローカルを優先し、ないユーザーだけTACACS+ | ✕（書いた順＝TACACS+が優先） |

AAAサーバが故障したり、ネットワークが切れたりしたときに誰もログインできなくなるのを防ぐため、**最後に local を入れる**のが一般的で、そのためにローカルユーザーを作っておきます。

### 5.4 802.1X（ポートベースの認証）

**802.1X**は、LANのポート（有線ならスイッチのポート、無線ならAPとの接続）を、認証に成功した端末にだけ開放する仕組みです。3つの役割があります。

| 役割 | 担当する機器 | 内容 |
|---|---|---|
| サプリカント（要求者） | PCなどの端末（802.1Xクライアントソフト） | 認証を**受ける側** |
| オーセンティケータ（認証者） | **スイッチ**、無線AP/WLC | 端末とRADIUSサーバの間で認証のやり取りを**中継**し、結果に応じて**ポートを開く** |
| 認証サーバ | RADIUSサーバ（例：Cisco ISE） | ユーザー情報を持ち、実際に認証を**判断**する |

```
 [PC]                        [スイッチ]                       [RADIUSサーバ / ISE]
 サプリカント               オーセンティケータ                  認証サーバ
    │  ── EAPoL（EAP over LAN）──>  │  ── RADIUS（EAPを中継）──>  │
    │  <────────────────────────── │  <──────────────────────── │
    │                               │      Access-Accept / Reject │
    │                     認証成功ならポートを開放
    │                     （成功するまでは EAPoL 以外は通さない）
```

sf-055: 有線LANの802.1Xで、PCを接続された**スイッチ**の役割は**オーセンティケータ**です。DHCPサーバは802.1Xの3つの役割に含まれません。

認証に成功するまで、スイッチのポートは認証用の通信（EAPoL）以外を通さないので、**許可されていない端末をLANにつないでも通信できません**。無線LANのエンタープライズモード（第9章）も同じ仕組みで、オーセンティケータが無線AP/WLCになります。

```
SW(config)# aaa new-model
SW(config)# radius server ISE
SW(config-radius-server)# address ipv4 192.168.100.20 auth-port 1812 acct-port 1813
SW(config-radius-server)# key R@diusKey
SW(config)# aaa authentication dot1x default group radius
SW(config)# dot1x system-auth-control
SW(config)# interface g0/1
SW(config-if)# switchport mode access
SW(config-if)# authentication port-control auto
SW(config-if)# dot1x pae authenticator
```

### ひっかけポイント・よくある誤解

- 「どのコマンドを実行できるか」は**認可**。認証（本人確認）、アカウンティング（記録）と区別する。**暗号化はAAAの要素ではない**。
- **TACACS+＝TCP 49・全体暗号化・Cisco**、**RADIUS＝UDP 1812/1813・パスワードのみ暗号化・IETF標準**。逆にしたひっかけが多い。「IEEE標準」も誤り。
- TACACS+やRADIUSは無線LANの**暗号化方式ではない**（それはWPA2/WPA3）。
- 方法リストの local は「**サーバに到達できないときの予備**」。サーバが「認証失敗」と答えたら local は試さない。両方での認証でも、ローカル優先でもない。
- 802.1Xでスイッチは**オーセンティケータ**。サプリカントは端末、認証サーバはRADIUS。DHCPサーバは無関係。

### 試験のポイント

- AAA＝認証（誰か）→認可（何をしてよいか）→アカウンティング（何をしたか）。AAAサーバ例：Cisco ISE。
- TACACS+は機器管理者のコマンド制御向け、RADIUSはネットワーク利用者（802.1X、VPN）の認証向け。
- `aaa new-model` で開始。方法リストは左から順、次へ進むのはエラー（無応答）時のみ。最後に `local`。
- 802.1Xの3役割：サプリカント・オーセンティケータ・認証サーバ。認証前はEAPoLのみ通過。

## 第6章 ACL（アクセスコントロールリスト）

ACL（Access Control List）は、ルータを通過するパケットを条件に応じて**許可（permit）**または**拒否（deny）**するための、上から順に並んだルールのリストです。ACLの1行1行を **ACE（Access Control Entry）** と呼びます。CCNAのセキュリティ分野で最も出題数が多いテーマなので、仕組み・書式・計算・適用・確認まで一通り身につけましょう。

### 6.1 ACLの種類

| 種類 | 番号 | 条件にできるもの | 推奨される適用場所 |
|---|---|---|---|
| 標準ACL | **1〜99**、1300〜1999 | **送信元IPアドレスだけ** | **宛先**に近い場所 |
| 拡張ACL | **100〜199**、2000〜2699 | プロトコル、送信元IP、宛先IP、送信元/宛先ポート番号など | **送信元**に近い場所 |
| 名前付きACL | 番号の代わりに名前 | 標準（standard）または拡張（extended）を指定 | 標準/拡張それぞれの推奨に従う |

sf-002: 標準ACL（1〜99）で条件にできるのは**送信元IPアドレスだけ**です。宛先IPアドレス、宛先ポート番号、プロトコル（TCP/UDP）を条件にするには拡張ACLを使います。

```
標準ACL:  access-list 10  permit 192.168.1.0 0.0.0.255
                          │      └──── 送信元（＋ワイルドカード）だけ
拡張ACL:  access-list 100 permit tcp 192.168.1.0 0.0.0.255 host 10.1.1.10 eq 80
                          │      │   └──── 送信元 ────┘  └── 宛先 ──┘  └ 宛先ポート
                          │      └ プロトコル
                          └ 動作
```

### 6.2 ACLの評価順序（上から順・最初に一致・暗黙のdeny）

ACLの動作は、次の3つのルールですべて説明できます。

1. **上の行から順に**確認する。
2. **最初に一致した行**の動作（permit/deny）だけを適用し、そこで確認を**終了**する（下の行は見ない）。
3. どの行にも一致しなければ、最後にある**暗黙の deny any**（設定にも表示されない）で**破棄**する。

```
パケット到着
   │
   v
[1行目に一致？] ──Yes──> 1行目の動作（permit/deny）を実行して終了
   │No
   v
[2行目に一致？] ──Yes──> 2行目の動作を実行して終了
   │No
   v
  ...
   │No
   v
[暗黙の deny any] ─────> 破棄
```

sf-015 の正解は「上の行から順に確認し、最初に一致した行の動作だけを適用する」です。

- 「すべての行を確認し、**最後に**一致した行」→ 誤り。最初に一致した行。
- 「**deny を先に**確認し、そのあと permit」→ 誤り。種類に関係なく**書かれた順**。
- 「条件が**最も具体的な行**を優先」→ 誤り。ルーティングの**ロンゲストマッチと混同**している。ACLは書いた順番がすべて。

このため、ACLは**具体的な条件の行を上に、広い条件の行を下に**書くのが基本です。

```
! 悪い例：permit any が先頭にあるので、2行目の deny は一度も使われない
access-list 10 permit any
access-list 10 deny   host 192.168.1.5

! 良い例：具体的な deny を先に、広い permit を後に
access-list 10 deny   host 192.168.1.5
access-list 10 permit any
```

#### 暗黙の deny any（sf-014、sf-050）

ACLの最後には、設定に表示されない「**すべての通信を拒否する（deny any）**」が必ずあります。「permit any」ではありません。「直前のルールを繰り返す」ような動作も、「暗黙のルールは存在しない」ということもありません。

```
access-list 10 deny host 192.168.1.5
(access-list 10 deny any)       ← 表示されないが必ず存在する
```

**代表問題 sf-050 の解き方（ステップごと）**

問題: 192.168.1.5 のPCだけを止めるつもりで `access-list 10 deny host 192.168.1.5` だけを作り、インターフェースに適用した。結果は？

```
ステップ1: 実際に評価される行を書き出す（暗黙の行も含める）
    1行目  deny host 192.168.1.5
    暗黙   deny any

ステップ2: 送信元 192.168.1.5 のパケットを当てはめる
    1行目に一致 → deny（破棄）

ステップ3: 送信元 192.168.1.20 のパケットを当てはめる
    1行目に不一致 → 暗黙の deny any に一致 → 破棄

ステップ4: 結論
    permit の行が1つもないので、すべての送信元からの通信が拒否される
```

- 「192.168.1.5 だけ拒否され、他は許可される」→ 誤り。permit の行がない。
- 「192.168.1.5 だけが許可される」→ 誤り。deny を指定している。
- 「permit がないのでACLは無視される」→ 誤り。permit がなくてもACLは有効で、すべてを拒否する。

意図どおりにするには2行目を追加します。

```
R1(config)# access-list 10 permit any
```

> **実務の注意**: 「denyだけのACLはすべてを止める」は実務でもよくある事故です。リモート（SSH）からACLを変更・適用すると、**自分の管理用の接続まで切ってしまう**ことがあります。

### 6.3 ワイルドカードマスク

ACLでアドレスの範囲を指定するには、サブネットマスクではなく**ワイルドカードマスク**を使います。

| ビット | 意味 |
|---|---|
| **0** | そのビットは**一致が必要**（チェックする） |
| **1** | そのビットは**どの値でもよい**（無視する） |

サブネットマスクとは0と1の意味が**逆**です。

| 指定 | 意味 | キーワードでの書き方 |
|---|---|---|
| `192.168.1.5 0.0.0.0` | 全ビット一致が必要 → **1台だけ** | `host 192.168.1.5` |
| `0.0.0.0 255.255.255.255` | 全ビットどの値でもよい → **すべてのアドレス** | `any` |
| `192.168.1.0 0.0.0.255` | 先頭3オクテットが一致すればよい → 192.168.1.0/24 | — |

#### 計算方法: 255.255.255.255 からサブネットマスクを引く

```
  255.255.255.255
− 255.255.255.0     （/24 のサブネットマスク）
─────────────────
    0.  0.  0.255   ← ワイルドカードマスク
```

**代表問題 sf-016 の解き方**

問題: 標準ACLで 192.168.1.0/24 全体を許可。`access-list 10 permit 192.168.1.0` の後に指定するワイルドカードマスクは？

```
ステップ1: /24 のサブネットマスクは 255.255.255.0
ステップ2: 255.255.255.255 − 255.255.255.0 = 0.0.0.255
ステップ3: 意味の確認
           0.0.0.255 → 前の3オクテット（192.168.1）は一致が必要、最後のオクテットはどの値でもよい
           → 192.168.1.0 〜 192.168.1.255
答え: access-list 10 permit 192.168.1.0 0.0.0.255
```

誤答の確認:

| 選択肢 | 意味 |
|---|---|
| 255.255.255.0 | サブネットマスクそのもの。ワイルドカードでは意味が逆になる |
| 0.0.0.0 | 192.168.1.0 の1つのアドレスだけ（host と同じ） |
| 255.255.255.255 | すべてのアドレス（any と同じ） |

#### 速算法: 最後のオクテット＝ブロックサイズ − 1

| プレフィックス | サブネットマスク（第4オクテット） | ブロックサイズ | ワイルドカード（第4オクテット） |
|---|---|---|---|
| /24 | 0 | 256 | 255 |
| /25 | 128 | 128 | 127 |
| /26 | 192 | 64 | **63** |
| /27 | 224 | 32 | 31 |
| /28 | 240 | 16 | 15 |
| /29 | 248 | 8 | 7 |
| /30 | 252 | 4 | 3 |
| /32 | 255 | 1 | 0（host） |

**代表問題 sf-017 の解き方**

問題: 192.168.1.64/26（192.168.1.64〜192.168.1.127）を指定するワイルドカードマスクは？

```
ステップ1: /26 のサブネットマスク → 255.255.255.192
ステップ2: 反転する → 255 − 192 = 63 → 0.0.0.63
          （速算：/26 のブロックサイズは 256 − 192 = 64 → 64 − 1 = 63）
ステップ3: 範囲の検算
          192.168.1.64  = ...0100 0000
          ワイルドカード63 = ...0011 1111   ← 下位6ビットはどの値でもよい
          → 192.168.1.64（01 000000）〜 192.168.1.127（01 111111）  ✔
答え: access-list 10 permit 192.168.1.64 0.0.0.63
```

誤答の確認:

| 選択肢 | なぜ誤りか |
|---|---|
| 0.0.0.64 | ブロックサイズ64をそのまま書いている。ワイルドカードは**ブロックサイズ − 1** |
| 255.255.255.192 | /26 のサブネットマスク。ワイルドカードではない |
| 0.0.0.127 | /25 のワイルドカード。192.168.1.0〜127 になり**広すぎる** |

> 補足: ACLでは、指定したアドレスとワイルドカードマスクの組み合わせで「0のビットだけを比較」します。アドレス部分はネットワークアドレス（ブロックの先頭）で書くのが原則です。

### 6.4 拡張ACLの書式

```
access-list 番号 {permit|deny} プロトコル 送信元 ワイルドカード [ポート条件] 宛先 ワイルドカード [ポート条件]
```

- 番号: 100〜199（および2000〜2699）
- プロトコル: `ip`（すべてのIP）、`tcp`、`udp`、`icmp` など
- アドレス: `any`、`host X.X.X.X`、`X.X.X.X ワイルドカード`
- ポート条件: `eq 80`（等しい）、`neq`、`lt`、`gt`、`range 20 21` など。**送信元の後に書けば送信元ポート、宛先の後に書けば宛先ポート**

よく使うポート番号:

| サービス | プロトコル/ポート |
|---|---|
| FTP | TCP 20/21 |
| SSH | **TCP 22** |
| Telnet | **TCP 23** |
| SMTP | TCP 25 |
| DNS | UDP 53（TCP 53も） |
| DHCP | UDP 67/68 |
| TFTP | UDP 69 |
| HTTP | **TCP 80** |
| HTTPS | **TCP 443** |
| SNMP | UDP 161/162 |
| TACACS+ | TCP 49 |
| RADIUS | UDP 1812/1813 |

**代表問題 sf-018 の解き方**

問題: 192.168.1.0/24 のPCから、Webサーバ 10.1.1.10 への**HTTP通信だけ**を許可する拡張ACLの行は？

```
ステップ1: 必要な要素を書き出す
          プロトコル … HTTP は TCP
          送信元     … 192.168.1.0/24 → 192.168.1.0 0.0.0.255
          宛先       … 10.1.1.10 の1台 → host 10.1.1.10（= 10.1.1.10 0.0.0.0）
          宛先ポート … HTTP = 80 → eq 80
          番号       … 拡張なので 100〜199
ステップ2: 「プロトコル 送信元 宛先 eq ポート」の順に並べる
答え: access-list 100 permit tcp 192.168.1.0 0.0.0.255 host 10.1.1.10 eq 80
```

誤答の確認:

| 選択肢 | なぜ誤りか |
|---|---|
| `... permit udp ... eq 80` | HTTPはTCP。UDPを指定するとHTTP通信に一致しない |
| `... permit tcp host 10.1.1.10 192.168.1.0 0.0.0.255 eq 80` | **送信元と宛先が逆**。拡張ACLでは送信元を先に書く |
| `access-list 10 permit tcp ...` | 番号10は**標準ACL**（1〜99）なので、宛先やポートを指定できない |

**代表問題 sf-049 の読み取り方**

```
access-list 101 deny tcp any host 10.1.1.1 eq 23
access-list 101 permit ip any any
```

```
ステップ1: 1行目を「プロトコル 送信元 宛先 ポート」に分解
          deny | tcp | any（送信元：すべて）| host 10.1.1.1（宛先：1台）| eq 23（宛先ポート：Telnet）
          → 「どこからでも、10.1.1.1 宛ての Telnet を拒否」
ステップ2: 2行目
          permit | ip（すべてのIP通信）| any | any → 「残りはすべて許可」
ステップ3: 暗黙の deny any は、2行目ですべて一致するため実質的に使われない
結論: 10.1.1.1 へのTelnetだけを拒否し、それ以外の通信はすべて許可する
```

誤答の確認:

- 「10.1.1.1 **からの**すべての通信を拒否」→ 10.1.1.1 は**宛先**で、拒否しているのはTelnetだけ。
- 「すべての通信を拒否」→ 2行目の `permit ip any any` でTelnet以外は許可される。
- 「10.1.1.1 へのSSHを拒否」→ SSHは**TCP 22**。拒否しているのは23番（Telnet）。

最後の `permit ip any any` がないと、暗黙の deny any によってすべての通信が止まってしまう点も合わせて押さえましょう。

### 6.5 ACLの適用場所（標準は宛先の近く、拡張は送信元の近く）

```
  [PC-A 192.168.1.10]──[R1]──────[R2]──────[R3]──[Server-X 10.3.3.3]
                         │                    │
                     送信元側                 └──[Server-Y 10.3.3.4]
                                             宛先側
```

**目的: PC-A から Server-X への通信だけを止め、PC-A から Server-Y への通信は通したい**

- **標準ACL**は送信元しか見ないので、`deny host 192.168.1.10` を送信元に近いR1に置くと、PC-A から**Server-Yへの必要な通信まで**止めてしまう。→ **宛先に近い**R3（Server-X側のインターフェース）に置くのが基本。
- **拡張ACL**は宛先・ポートまで指定できるので、`deny ip host 192.168.1.10 host 10.3.3.3` を**送信元に近い**R1に置けば、Server-Y への通信は通しつつ、不要な通信を**早い段階で**止められる。宛先の近くに置くと、最終的に破棄される通信がネットワーク内（R1→R2→R3）を長く流れて**帯域を無駄**にする。

sf-048 の正解は「止めたい通信の**送信元にできるだけ近い場所**」です。

| 選択肢 | 判定 |
|---|---|
| 送信元にできるだけ近い場所 | ◯（拡張ACLの推奨） |
| 宛先にできるだけ近い場所 | ✕（これは**標準ACL**の推奨） |
| どこに置いても効果は同じ | ✕（止められる範囲や無駄に流れる通信量が変わる） |
| 必ずコア層のスイッチ | ✕（コア層は高速転送に専念させ、細かいフィルタは置かないことが多い） |

覚え方：「**拡張は送信元の近く、標準は宛先の近く**」。

### 6.6 インターフェースへの適用：ip access-group

ACLは**作成しただけでは効果がありません**。インターフェースに**方向を指定して**適用する必要があります。

```
R1(config)# access-list 100 permit tcp 192.168.1.0 0.0.0.255 host 10.1.1.10 eq 80
R1(config)# interface g0/0
R1(config-if)# ip access-group 100 in       ← 受信方向（インターフェースに入ってくるパケット）
```

方向の考え方は「**ルータから見て**」です。

```
             in（ルータに入る）           out（ルータから出る）
  LAN ─────────────────> [g0/0  R1  g0/1] ─────────────────> WAN
```

sf-019 の正解は `ip access-group 100 in`（インターフェース設定モード）。

| 選択肢 | 実際の意味 |
|---|---|
| `ip access-group 100 in` | ◯ インターフェースに受信方向で適用 |
| `access-class 100 in` | **vty**（Telnet/SSHのライン）にACLを適用して、機器へのリモートログインを制限するコマンド |
| `ip access-list 100 in` | **存在しない**コマンド。`ip access-list` は名前付きACLを**作成**するとき（例：`ip access-list extended WEB`） |
| `service-policy input 100` | **QoS**のポリシーをインターフェースに適用するコマンド |

ルール: 1つのインターフェースに適用できるACLは、**1方向・1プロトコル（IPv4/IPv6）ごとに1つまで**です（例：g0/0 に IPv4 の in 1つ、IPv4 の out 1つ、IPv6 の in 1つ…）。

適用状況は `show ip interface` で確認します。

```
R1# show ip interface g0/0
GigabitEthernet0/0 is up, line protocol is up
  Internet address is 192.168.1.1/24
  ...
  Outgoing access list is not set
  Inbound  access list is 100
  ...
```

### 6.7 名前付きACLとシーケンス番号

名前付きACLは、用途がわかる名前を付けられ、**シーケンス番号**で行単位の編集ができます。

```
R1(config)# ip access-list extended WEB
R1(config-ext-nacl)# 10 permit tcp any host 10.1.1.10 eq 80
R1(config-ext-nacl)# 20 deny   ip any host 10.1.1.10
R1(config-ext-nacl)# permit ip any any            ← 番号なし → 最後に追加（30）
R1(config-ext-nacl)# exit
R1(config)# interface g0/0
R1(config-if)# ip access-group WEB in
```

**代表問題 sf-047: 10と20の間に行を追加する**

```
R1(config)# ip access-list extended WEB
R1(config-ext-nacl)# 15 permit tcp any host 10.1.1.10 eq 443
```

```
R1# show access-lists WEB
Extended IP access list WEB
    10 permit tcp any host 10.1.1.10 eq www
    15 permit tcp any host 10.1.1.10 eq 443      ← 番号で指定した位置に挿入された
    20 deny ip any host 10.1.1.10
    30 permit ip any any
```

- 各行にはデフォルトで **10、20、30…** と10ずつ間隔を空けたシーケンス番号が付く。
- 間に行を**挿入**できる（例：15）。
- `no 20` のように番号を指定して**1行だけ削除**できる。
- **番号を付けずに入力した行はACLの最後**に追加される（自動で10と20の間には入らない）。
- 「作り直すしかない」は、番号付きACLを昔の方法（グローバル設定の `access-list` コマンド）で編集する場合の話。
- 「順番は関係ない」は誤り。ACLは上から順に確認されるので**順番はとても重要**。

```
R1(config)# ip access-list extended WEB
R1(config-ext-nacl)# no 20                        ← 20番の行だけ削除
R1(config-ext-nacl)# exit
R1(config)# ip access-list resequence WEB 10 10    ← 番号を10から10刻みに振り直す
```

名前付きの標準ACLは `ip access-list standard 名前` で作ります。

### 6.8 確認とトラブルシューティング：show access-lists と show ip interface

```
R1# show access-lists
Standard IP access list 10
    10 deny   192.168.1.5 (3 matches)
    20 permit any (152 matches)
Extended IP access list 101
    10 deny tcp any host 10.1.1.1 eq telnet (15 matches)
    20 permit ip any any (2048 matches)
```

sf-051: 各行（ACE）に何個のパケットが一致したかは **`show access-lists`** で確認します（各行末の `(15 matches)`）。

| コマンド | わかること |
|---|---|
| `show access-lists`（`show ip access-lists`） | ACLの内容と、**各行の一致数** |
| `show ip interface` | どのインターフェースに、どのACLが、**どの方向**で適用されているか（一致数は出ない） |
| `show running-config` | 設定全体（適用コマンドも含む） |
| `show ip route` | ルーティングテーブル（ACLとは無関係） |
| `show ip nat translations` | NATの変換テーブル（ACLとは無関係） |

トラブルシューティングの手順:

```
① show ip interface   → 「どこに・どの向きで」適用されているか
② show access-lists   → 「どの行に一致しているか」（カウンタ）
③ 期待した行のカウンタが増えていない場合:
     ・上の行に先に一致している（順番の問題）
     ・適用したインターフェースや方向（in/out）が間違っている
     ・暗黙の deny any で落ちている（どの行のカウンタも増えない）
④ clear access-list counters でカウンタをリセットして再テストすると分かりやすい
```

### 6.9 vtyへのACL適用：access-class

機器へのSSH/Telnetの接続元を制限するには、ACLを**vtyライン**に `access-class` で適用します。

```
R1(config)# access-list 10 permit 192.168.100.0 0.0.0.255    ! 管理用PCのネットワーク
R1(config)# line vty 0 4
R1(config-line)# access-class 10 in
R1(config-line)# transport input ssh
R1(config-line)# login local
```

```
                     ┌──────────── R1 ────────────┐
管理用PC 192.168.100.5 ─SSH─> │ vty: access-class 10 in → 許可 → ログイン画面 │
一般PC   192.168.1.20  ─SSH─> │ vty: access-class 10 in → 拒否（接続拒否）     │
                     └─────────────────────────────┘
       ※ R1を「通過」するパケットには影響しない（それは ip access-group の役目）
```

sf-030 の正解は `access-class 10 in`（line vty 0 4 の設定モード）。

| コマンド | 適用先・役割 |
|---|---|
| `access-class 10 in` | **vty**への接続を、ACLで許可した送信元だけに制限 |
| `ip access-group 10 in` | **インターフェース**を通過するパケットを制御。line vty モードでは使えない |
| `transport input ssh` | vtyで使える接続方式をSSHだけにする（Telnet禁止）。接続元の制限はしない |
| `login local` | ローカルユーザーで認証する。接続元の制限はしない |

覚え方：「**インターフェースには ip access-group、vty には access-class**」。3つ（access-class・transport input ssh・login local）を組み合わせると、機器への管理アクセスを安全に制限できます。

### ひっかけポイント・よくある誤解

- 標準ACLは**送信元だけ**。宛先・ポート・プロトコルは拡張ACL。
- ACLの最後は**暗黙の deny any**（permit any ではない）。deny だけのACLは**すべてを止める**。permit がなくてもACLは無視されない。
- ACLは**最初に一致した行**で終了。最後の一致でも、deny優先でも、最長一致（ロンゲストマッチ）でもない。
- ワイルドカードはサブネットマスクと0/1が逆。**ブロックサイズ − 1**（64ではなく63）。0.0.0.0＝host、255.255.255.255＝any。/25の0.0.0.127は/26には広すぎる。
- 拡張ACLは**送信元→宛先**の順。HTTPは**TCP**。番号10は標準ACLなのでポート指定不可。
- 「host 10.1.1.1」が宛先位置にあれば「10.1.1.1 **への**」通信。23はTelnet、22はSSH。
- 拡張は**送信元の近く**、標準は**宛先の近く**。コア層に必ず置くわけではない。
- インターフェースは `ip access-group`、vty は `access-class`。`ip access-list 100 in` は存在しない。`service-policy` はQoS。
- 1インターフェースに、1方向・1プロトコルごとに1つのACL。
- 名前付きACLで番号なしの行は**末尾**に追加。順番は重要。
- 一致数は `show access-lists`、適用場所と方向は `show ip interface`。

### 試験のポイント

- 標準（1〜99）＝送信元のみ・宛先の近く／拡張（100〜199）＝詳細条件・送信元の近く。
- 評価順序：上から順・最初の一致で終了・最後は暗黙の deny any。具体的な行を上に。
- ワイルドカード＝255.255.255.255 − サブネットマスク（最後のオクテットはブロックサイズ − 1）。
- 拡張ACL書式：`access-list 番号 動作 プロトコル 送信元 WC 宛先 WC eq ポート`。
- 適用：`ip access-group 番号 in|out`（インターフェース）、`access-class 番号 in`（vty）。
- 名前付きACLはシーケンス番号で挿入（`15 ...`）・削除（`no 20`）が可能。
- 確認：`show access-lists`（matches）と `show ip interface`（適用状況）。

## 第7章 L2セキュリティ（ポートセキュリティ・DHCPスヌーピング・DAI・L2攻撃）

スイッチ（レイヤー2）は、社内の端末が直接つながる場所です。社内に入り込んだ攻撃者や不正な機器は、まずL2の仕組みを悪用します。この章では「攻撃」と「対策機能」を対応させて学びます。

### 7.1 L2攻撃と対策の対応表

| 攻撃 | 手口 | 被害 | 主な対策 |
|---|---|---|---|
| MACフラッディング | 送信元MACを次々に変えた大量のフレームでMACアドレステーブルをあふれさせる | スイッチがハブのようにフラッディング → 盗聴 | **ポートセキュリティ**（学習できるMAC数の制限） |
| DHCPスタベーション | 偽のMACで大量の DHCPDISCOVER → アドレスを使い切らせる | 正規の端末がIPをもらえない（DoS） | **DHCPスヌーピング**（レート制限）、ポートセキュリティ |
| DHCPスプーフィング | 偽のDHCPサーバとして応答し、偽のゲートウェイ/DNSを配る | 通信を攻撃者経由にされる（中間者攻撃） | **DHCPスヌーピング**（untrustedポートのサーバ応答を破棄） |
| ARPスプーフィング | 「ゲートウェイのIPは自分のMACだ」という偽ARPを送る | 通信を攻撃者に引き寄せる（中間者攻撃） | **DAI**（ダイナミックARPインスペクション） |
| VLANホッピング（スイッチスプーフィング） | DTPで交渉してトランクを作る | 全VLANにアクセス | アクセスポートに固定・**DTP無効**（`switchport nonegotiate`） |
| VLANホッピング（ダブルタギング） | 外側にネイティブVLAN、内側に標的VLANのタグを付ける | 別のVLANへフレームを送り込む | **ネイティブVLANを未使用VLANに変更** |
| 不正なスイッチの接続（STP操作） | PortFastのポートでBPDUを送る | ルートブリッジの乗っ取りなど | **BPDUガード** |

### 7.2 MACフラッディングとポートセキュリティ

#### MACフラッディング（sf-031）

スイッチはMACアドレステーブルを使って、宛先MACのあるポートだけにフレームを転送します。テーブルの容量には上限があります。

```
攻撃者がランダムな送信元MACのフレームを大量に送る
  aa:01 → ... aa:02 → ... aa:03 → ... （数万個）
           │
           v
  MACアドレステーブルが満杯 → 新しい宛先を学習できない
           │
           v
  宛先不明のフレーム（ユニキャストフラッディング）を全ポートへ送る ＝ ハブ状態
           │
           v
  攻撃者のポートにも他人の通信が届く → 盗聴できる
```

sf-031 の「送信元MACアドレスを次々に変えた大量のフレームで、MACアドレステーブルをあふれさせる」は**MACフラッディング**です。対策は**ポートセキュリティ**で、1つのポートで学習できるMACアドレスの数を制限します。

#### ポートセキュリティの基本（sf-003）

**ポートセキュリティ**は、スイッチのポートに接続できる端末を**MACアドレスで制限**する機能です。許可するMACアドレスや、その数を制限します。許可していないMACアドレスの端末がつながると**違反**として扱います。

```
SW(config)# interface g0/1
SW(config-if)# switchport mode access                          ! ① アクセスポートにする（必須）
SW(config-if)# switchport port-security                        ! ② 機能を有効化（必須）
SW(config-if)# switchport port-security maximum 2              ! 許可するMACの数（デフォルト1）
SW(config-if)# switchport port-security mac-address sticky     ! 学習したMACを設定に自動追加
SW(config-if)# switchport port-security violation restrict     ! 違反時の動作（デフォルト shutdown）
```

- ポートセキュリティを使うには、ポートを**アクセスポート**（`switchport mode access`）にして、`switchport port-security` で**機能を有効**にする必要がある（DTPのdynamicモードのままではコマンドが拒否される）。
- 許可する数は `switchport port-security maximum` で指定。**デフォルトは1**。
- 静的に登録するなら `switchport port-security mac-address 0011.2233.4455`。

#### sticky（sf-023）

`switchport port-security mac-address sticky` は、ポートで**学習したMACアドレスを、許可するアドレスとして running-config に自動で追加**します。1台ずつ手動で登録する手間が省けます。

```
SW# show running-config interface g0/1
interface GigabitEthernet0/1
 switchport mode access
 switchport port-security
 switchport port-security mac-address sticky
 switchport port-security mac-address sticky 0011.2233.4455    ← 自動で追加された
```

- running-config に書き込まれるので、`copy running-config startup-config` で保存すれば**再起動後も維持**される（保存しなければ再起動で消える）。
- 許可する**数**とは無関係（数は `maximum`）。
- err-disabled からの**自動復旧**とは無関係（それは `errdisable recovery`）。
- MACアドレステーブルの**エージング（保持時間）**とは無関係。

#### 違反時の動作（violation モード）（sf-022）

| モード | ポート | フレーム | ログ（syslog/SNMP） | 違反カウンタ |
|---|---|---|---|---|
| **shutdown**（デフォルト） | **停止（err-disabled）** | 破棄 | 出す | 増える |
| restrict | 止めない | 破棄 | 出す | 増える |
| protect | 止めない | 破棄 | **出さない** | 増えない |

覚え方：「ポートを止めるか」「ログを出すか」の2軸。

```
            ポートを止める   ログを出す
shutdown         ◯              ◯
restrict         ✕              ◯
protect          ✕              ✕
```

`sticky` は違反時の動作ではなく、学習したMACを設定に保存する機能です（sf-022 のひっかけ）。

#### 状態の確認

```
SW# show port-security interface g0/1
Port Security              : Enabled
Port Status                : Secure-shutdown
Violation Mode             : Shutdown
Aging Time                 : 0 mins
Aging Type                 : Absolute
SecureStatic Address Aging : Disabled
Maximum MAC Addresses      : 1
Total MAC Addresses        : 1
Configured MAC Addresses   : 0
Sticky MAC Addresses       : 1
Last Source Address:Vlan   : 00aa.bbcc.ddee:10
Security Violation Count   : 1

SW# show interfaces status
Port      Name   Status       Vlan  Duplex  Speed Type
Gi0/1            err-disabled 10    auto    auto  10/100/1000BaseTX
```

#### err-disabled からの復旧（sf-053）

shutdown モードで違反すると、ポートは **err-disabled** 状態になります。

```
%PM-4-ERR_DISABLE: psecure-violation error detected on Gi0/1, putting Gi0/1 in err-disable state
%PORT_SECURITY-2-PSECURE_VIOLATION: Security violation occurred, caused by MAC address 00aa.bbcc.ddee on port GigabitEthernet0/1.
```

手動での復旧手順:

```
① 原因を取り除く（許可していない端末を外す、または許可設定を見直す）
② SW(config)# interface g0/1
   SW(config-if)# shutdown          ← いったん管理的に無効にする
   SW(config-if)# no shutdown       ← 有効にすると err-disabled が解除される
```

- **no shutdown だけでは復旧しない**。先に shutdown が必要。
- `clear mac address-table` は MACアドレステーブルを消すだけで、err-disabled は解除されない。
- 自動復旧（`errdisable recovery`）を設定していなければ、**自動では復旧しない**。
- **原因を取り除かずに復旧させると、すぐにまた違反**になる。

自動復旧の設定:

```
SW(config)# errdisable recovery cause psecure-violation
SW(config)# errdisable recovery interval 300         ! 300秒後に自動復旧（デフォルトも300秒）
```

### 7.3 DHCPスタベーションとDHCPスプーフィング（sf-032）

```
【ステップ1：DHCPスタベーション（枯渇攻撃）】
 攻撃者 ── DHCPDISCOVER（偽MAC #1）──> 正規DHCPサーバ  → 10.0.0.10 を貸し出す
        ── DHCPDISCOVER（偽MAC #2）──>                → 10.0.0.11 を貸し出す
        ── ...（数百〜数千回）       ──>                → アドレスプールが空に
 → 正規の端末がアドレスをもらえない（DoS）

【ステップ2：DHCPスプーフィング（偽DHCPサーバ）】
 新しいPC ── DHCPDISCOVER ──> （正規サーバは枯渇して応答できない）
 攻撃者   ── DHCPOFFER：IP=10.0.0.50, GW=攻撃者のIP, DNS=攻撃者のIP ──> 新しいPC
 → PCの通信はすべて攻撃者を経由する（中間者攻撃）
```

sf-032 の「偽のMACアドレスで大量の DHCPDISCOVER を送り、アドレスを使い切らせる」は**DHCPスタベーション**。偽のDHCPサーバとして応答するのは**DHCPスプーフィング**で、スタベーションはその準備にもなります。

対策: **DHCPスヌーピング**（偽サーバの遮断、DHCPメッセージのレート制限）と**ポートセキュリティ**（1ポートの偽MACの数を制限）。

### 7.4 DHCPスヌーピング

#### 仕組み（sf-020）

DHCPスヌーピングは、スイッチのポートを **trusted（信頼）** と **untrusted（非信頼）** に分け、**untrusted ポートから届いたDHCPサーバの応答（OFFER/ACK など）を破棄**します。

```
                    ┌──────────── スイッチ（DHCPスヌーピング有効） ────────────┐
正規DHCPサーバ ── Gi0/24 [trusted]   ← OFFER/ACK を受け付ける                     │
                    │                                                          │
PC-A ──────────── Gi0/1  [untrusted] ← DISCOVER/REQUEST は通す                 │
攻撃者（偽サーバ）── Gi0/2  [untrusted] ← OFFER/ACK が来たら破棄 ✕               │
                    └──────────────────────────────────────────────────────────┘
```

| ポート | 設定 | 理由 |
|---|---|---|
| 正規のDHCPサーバにつながるポート（アップリンクなど） | **trusted** | サーバの応答を受け付けるため |
| 一般ユーザーのPCがつながるポート | untrusted（デフォルトのまま） | 不正なDHCPサーバがつながっても、その応答を破棄できる |

- **すべて trusted** にすると、不正なDHCPサーバを防げない。
- DHCPスヌーピングを有効にすると、デフォルトで**すべて untrusted** になる。どのポートも trusted にしないと、**正規のサーバの応答も届かなくなる**。

さらに、DHCPスヌーピングは「どのポートの、どのMACアドレスに、どのIPアドレスが割り当てられたか」を記録した**バインディングテーブル**を作ります。これがDAIなどで使われます。

```
SW# show ip dhcp snooping binding
MacAddress          IpAddress        Lease(sec)  Type           VLAN  Interface
------------------  ---------------  ----------  -------------  ----  --------------------
00:11:22:33:44:55   10.0.10.21       86250       dhcp-snooping   10    GigabitEthernet0/1
00:11:22:33:44:66   10.0.10.22       86100       dhcp-snooping   10    GigabitEthernet0/3
Total number of bindings: 2
```

#### 設定（sf-052）

```
SW(config)# ip dhcp snooping                         ! ① 機能の有効化（グローバル）
SW(config)# ip dhcp snooping vlan 10                 ! ② 対象のVLANを指定（これがないとどのVLANでも動かない）
SW(config)# interface g0/24
SW(config-if)# ip dhcp snooping trust                ! ③ 正規のDHCPサーバの方向のポートだけ trusted
SW(config)# interface range g0/1 - 23
SW(config-if-range)# ip dhcp snooping limit rate 10  ! （任意）untrustedポートのDHCPメッセージを毎秒10個に制限＝スタベーション対策
```

```
SW# show ip dhcp snooping
Switch DHCP snooping is enabled
DHCP snooping is configured on following VLANs:
10
...
Interface                  Trusted    Allow option    Rate limit (pps)
-----------------------    -------    ------------    ----------------
GigabitEthernet0/24        yes        yes             unlimited
GigabitEthernet0/1         no         no              10
```

sf-052 の正解は「`ip dhcp snooping vlan 10` のように対象のVLANを指定する」。

| 誤答 | 理由 |
|---|---|
| すべてのポートで `ip dhcp snooping trust` | 不正なDHCPサーバを防げない。trust は正規サーバ側のポートだけ |
| `ip arp inspection vlan 10` | DAIの設定。DHCPスヌーピングを働かせるものではない |
| `switchport port-security` | ポートセキュリティの設定。別の機能 |

> 補足: レート制限を超えたポートは err-disabled になります（`errdisable recovery cause dhcp-rate-limit` で自動復旧可能）。

### 7.5 ダイナミックARPインスペクション（DAI）（sf-021）

#### ARPスプーフィング（ARPポイズニング）

```
正常:   PC-A の ARPキャッシュ   10.0.10.1（GW） → GWのMAC（00:aa:...:01）

攻撃:   攻撃者 ── 偽のARP応答「10.0.10.1 は 00:bb:...:99（攻撃者のMAC）です」──> PC-A
        PC-A の ARPキャッシュ   10.0.10.1（GW） → 攻撃者のMAC   ← 書き換えられた
        → PC-A がゲートウェイに送るつもりのフレームは攻撃者に届く（中間者攻撃）
```

#### DAIの仕組み

DAIは、untrusted ポートで受信したARPに書かれた「**IPアドレスとMACアドレスの組み合わせ**」を、**DHCPスヌーピングのバインディングテーブル**と照合し、一致しなければ破棄します。

```
受信したARP： 送信元IP 10.0.10.1 / 送信元MAC 00:bb:...:99（Gi0/2）
バインディングテーブル： 10.0.10.1 と 00:bb:...:99 の組み合わせは存在しない
→ 破棄＋ログ
```

| 選択肢 | なぜ参照先にならないか |
|---|---|
| **DHCPスヌーピングのバインディングテーブル** | ◯ IPとMACの対応が記録されている |
| MACアドレステーブル | スイッチの転送用の表。MACとポートの対応で、**IPアドレスとの対応は記録されていない** |
| ルーティングテーブル | ルータが宛先ネットワークへの経路を決める表 |
| NATテーブル | アドレス変換の対応表 |

そのため、**DAIを使うには先にDHCPスヌーピングを有効にしておく必要**があります（静的IPの機器はARP ACLで許可する）。

```
SW(config)# ip dhcp snooping
SW(config)# ip dhcp snooping vlan 10
SW(config)# ip arp inspection vlan 10                ! DAIを有効化
SW(config)# interface g0/24
SW(config-if)# ip dhcp snooping trust
SW(config-if)# ip arp inspection trust               ! アップリンクは DAI でも trusted
```

```
SW# show ip arp inspection vlan 10
 Vlan     Configuration    Operation   ACL Match          Static ACL
 ----     -------------    ---------   ---------          ----------
   10     Enabled          Active
```

### 7.6 VLANホッピングとその対策（sf-033）

VLANホッピングは、本来アクセスできない別のVLANの通信に入り込む攻撃で、2つの手口があります。

#### ①スイッチスプーフィング

```
攻撃者PC ── DTP「トランクにしよう」──> スイッチのポート（dynamic auto/desirable のまま）
         <── トランク成立 ──
→ 攻撃者PCがすべてのVLANのフレームを送受信できる
```

対策: 端末用のポートを**アクセスポートに固定**し、**DTPを無効**にする。

```
SW(config)# interface range g0/1 - 23
SW(config-if-range)# switchport mode access
SW(config-if-range)# switchport nonegotiate     ! DTPフレームを送らない
```

#### ②ダブルタギング（二重タグ）

```
攻撃者（VLAN 1 = ネイティブVLANのアクセスポート）
  送信フレーム: [外側タグ VLAN1][内側タグ VLAN20][データ]
      │
  SW1: 外側タグ＝ネイティブVLAN(1) → トランクではネイティブVLANはタグなしで送るので「外側タグを外す」
      │  トランク上: [内側タグ VLAN20][データ]
      v
  SW2: VLAN20 のタグ付きフレームとして受信 → VLAN20 の被害者へ転送
  ※ 一方向の攻撃（応答は返ってこない）
```

対策: トランクの**ネイティブVLANを、どの端末も使っていない未使用のVLANに変更**する。

```
SW(config)# vlan 999
SW(config-vlan)# name UNUSED_NATIVE
SW(config)# interface g0/24
SW(config-if)# switchport mode trunk
SW(config-if)# switchport trunk native vlan 999
SW(config-if)# switchport nonegotiate
```

| 選択肢 | 判定 |
|---|---|
| 端末用ポートをアクセスに固定しDTPを無効 | ◯ |
| ネイティブVLANを未使用のVLANに変更 | ◯ |
| ネイティブVLANをデフォルトのVLAN 1のまま | ✕ VLAN 1は初期状態で全ポートが所属しており、攻撃に利用されやすい |
| すべてのポートをトランクにする | ✕ 端末が複数VLANの通信にアクセスできてしまう |

その他のベストプラクティス：未使用のポートは shutdown して未使用VLANに割り当てる、VLAN 1を業務に使わない。

### 7.7 BPDUガード（参考：sf-003 の誤答）

**BPDUガード**は、PortFastを設定したポート（端末用）でBPDU（STPの制御フレーム）を受信したら、ポートを err-disabled にして停止する機能です。不正なスイッチの接続やSTPの乗っ取りを防ぎます。

```
SW(config-if)# spanning-tree portfast
SW(config-if)# spanning-tree bpduguard enable
```

### 7.8 機能の比較まとめ（sf-003 の選択肢）

| 機能 | 何を防ぐか | 見るもの |
|---|---|---|
| **ポートセキュリティ** | 許可されていない端末の接続、MACフラッディング | 送信元MACアドレス・MACの数 |
| DHCPスヌーピング | 不正なDHCPサーバ、DHCPスタベーション | DHCPメッセージの種類と受信ポート（trusted/untrusted） |
| BPDUガード | PortFastポートへのスイッチ接続 | BPDUの受信 |
| ダイナミックARPインスペクション | ARPのなりすまし | ARPのIP/MACの組とバインディングテーブル |

### ひっかけポイント・よくある誤解

- MACで端末を制限するのは**ポートセキュリティ**。DHCPスヌーピング・BPDUガード・DAIと機能を混同しない。
- 違反時のデフォルトは **shutdown**（err-disabled）。restrict＝止めない・ログあり、protect＝止めない・ログなし。**sticky は違反モードではない**。
- sticky は「学習したMACを running-config に追加」。数の制限（maximum、デフォルト1）、自動復旧（errdisable recovery）、エージングとは無関係。保存しないと再起動で消える。
- err-disabled は **shutdown → no shutdown**。no shutdown だけ、clear mac address-table では戻らない。自動復旧は設定しない限り行われない。
- DHCPスヌーピングの trusted は**正規のDHCPサーバ側だけ**。全部 trusted は無意味、どこも trusted にしないと正規の応答も届かない。
- DHCPスヌーピングは `ip dhcp snooping` だけでは動かない。**`ip dhcp snooping vlan`** が必要。`ip arp inspection vlan` はDAI。
- DAIの参照先は**DHCPスヌーピングのバインディングテーブル**（MACアドレステーブルにはIPの情報がない）。
- MACフラッディング（テーブルをあふれさせる）、ARPスプーフィング（IPのなりすまし）、DHCPスタベーション（アドレス枯渇）、DHCPスプーフィング（偽サーバ）、VLANホッピング（別VLANへの侵入）を区別する。
- VLANホッピング対策は「アクセス固定＋DTP無効」「ネイティブVLANを未使用VLANに」。VLAN 1のまま・全ポートトランクは逆効果。

### 試験のポイント

- ポートセキュリティ：`switchport mode access` → `switchport port-security` → `maximum`（既定1）／`mac-address sticky`／`violation {shutdown|restrict|protect}`（既定shutdown）。
- err-disabled の復旧：原因除去 → `shutdown` → `no shutdown`。自動は `errdisable recovery cause psecure-violation`。確認は `show port-security interface`、`show interfaces status`。
- DHCPスヌーピング：`ip dhcp snooping` → `ip dhcp snooping vlan X` → 正規サーバ側に `ip dhcp snooping trust`。`limit rate` でスタベーション対策。バインディングテーブルを作る。
- DAIはバインディングテーブルを参照 → DHCPスヌーピングが前提。
- VLANホッピング：スイッチスプーフィング（DTP）とダブルタギング（ネイティブVLAN）。

## 第8章 VPN（サイト間VPN・リモートアクセスVPN・IPsec・GRE）

**VPN（Virtual Private Network）**は、インターネットのような信頼できない回線の上に、暗号化された仮想的な専用線（トンネル）を作る技術です。

### 8.1 サイト間VPNとリモートアクセスVPN

| 項目 | サイト間VPN（site-to-site VPN） | リモートアクセスVPN |
|---|---|---|
| つなぐもの | **拠点と拠点**（本社⇔支社） | **個々の端末**（在宅勤務のPCなど）⇔社内 |
| トンネルを張る機器 | 拠点の**ルータやファイアウォール同士** | 端末の**VPNクライアントソフト**⇔VPN装置（ASA/FTDなど） |
| 接続のタイミング | **常時**（常設） | 必要なときに接続 |
| 端末の特別なソフト | **不要**（端末は普段どおり通信するだけ） | 必要（Cisco Secure Client〔旧AnyConnect〕など）または**Webブラウザ** |
| 主なプロトコル | **IPsec** | **TLS**（IPsec/IKEv2を使うこともある） |

```
【サイト間VPN】
 本社LAN ── [R-本社] ══════ IPsecトンネル（インターネット経由・常時）══════ [R-支社] ── 支社LAN
             203.0.113.1                                              198.51.100.1
  PCは普段どおり通信するだけ。暗号化はルータが行う。

【リモートアクセスVPN】
 在宅PC（Cisco Secure Client）══ TLS（TCP 443）トンネル ══> [VPN装置(ASA/FTD)] ── 社内LAN
 出張先PC（Webブラウザ）      ══ TLS ═══════════════════> ┘
```

sf-012: 本社と支社の**ルータ同士**で、インターネット越しに**常時**トンネルを張って拠点間のLANをつなぐのは**サイト間VPN**。

- VLAN：スイッチ内でネットワークを論理的に分ける技術。暗号化やインターネット越しの接続とは無関係。
- NAT：プライベートIPとグローバルIPを変換する技術。暗号化はしない。

sf-045: 在宅勤務の社員が Cisco Secure Client や Web ブラウザで接続するリモートアクセスVPNで主に使われるのは **TLS**（HTTPSでも使われる暗号化の仕組み）。TLSはWebブラウザでも使われているため、**ファイアウォールを通りやすい（TCP 443）**という利点があります。

| 誤答 | 理由 |
|---|---|
| GRE | カプセル化するトンネルのプロトコルで、**暗号化の機能がない** |
| Telnet | 機器へのリモートログイン。通信は暗号化されない |
| SNMPv2c | 機器の監視。コミュニティ名も平文 |

### 8.2 IPsecが提供するセキュリティ機能（sf-013）

| 機能 | 内容 | 使う技術の例 |
|---|---|---|
| **機密性**（暗号化） | 盗聴されても内容を読めない | AES など |
| **完全性**（改ざん検知） | 途中でデータが書き換えられていないか確認する | ハッシュ（HMAC-SHA など） |
| **認証** | 通信相手が本物かを確認する | 事前共有キー、デジタル証明書 |
| **リプレイ攻撃の防止** | 盗聴したパケットを再送する攻撃を防ぐ | シーケンス番号 |

覚え方：「機密性・完全性・認証・リプレイ防止」。

- IPアドレスの自動割り当て → **DHCP**の役割。
- 通信帯域の保証 → **QoS**の役割。

> 補足: IPsecは、鍵交換に IKE（Internet Key Exchange、UDP 500/4500）を使い、データの保護には ESP（暗号化＋完全性。IPプロトコル番号50）または AH（完全性・認証のみで暗号化なし。番号51）を使います。VPNで暗号化を行うのは ESP です。

### 8.3 IPsecのモード：トンネルモードとトランスポートモード（sf-044）

```
元のパケット:                  [元IPヘッダ][TCP/UDP][データ]

トンネルモード:   [新IPヘッダ][ESPヘッダ][元IPヘッダ][TCP/UDP][データ][ESPトレーラ/認証]
                   ↑ルータ同士の          └──────── 暗号化される範囲 ────────┘
                    グローバルアドレス       （元の送信元・宛先も隠れる）

トランスポートモード:         [元IPヘッダ][ESPヘッダ][TCP/UDP][データ][ESPトレーラ/認証]
                              ↑そのまま              └── 暗号化される範囲 ──┘
```

| モード | 暗号化の範囲 | 新しいIPヘッダ | 主な用途 |
|---|---|---|---|
| **トンネルモード** | **元のIPパケット全体**（元のIPヘッダを含む） | **付ける** | **サイト間VPN**（ゲートウェイ間） |
| トランスポートモード | データ部分だけ（元のIPヘッダはそのまま） | 付けない | 端末同士の通信（ホスト間）、GRE over IPsec |

サイト間VPNでは、拠点のルータが社内のパケットを**まるごと暗号化**し、ルータ同士のグローバルアドレスを付けた**新しいヘッダ**でインターネットへ送ります。受け取った相手のルータが外側のヘッダを外して復号し、元のパケットを社内へ転送します。社内のアドレスなど、元の送信元・宛先も隠せます。

- パッシブモード：**FTP**のデータ転送の方式。
- モニターモード：**無線AP**のモードの一つ。

### 8.4 GREとGRE over IPsec（sf-046）

**GRE（Generic Routing Encapsulation）**は、パケットをカプセル化して拠点間を**仮想的につなぐ**トンネルのプロトコルです。

| 項目 | GRE | 従来のIPsec（クリプトマップ方式） |
|---|---|---|
| 暗号化 | **できない** | できる |
| マルチキャスト（OSPFなどのルーティングプロトコル） | **運べる** | 運べない（ユニキャストのみ） |

互いの弱点を補うため、**GREでカプセル化したうえでIPsecで暗号化する（GRE over IPsec）**構成が使われます。

```
[元のOSPFパケット（マルチキャスト 224.0.0.5）]
      ↓ GREでカプセル化（ユニキャストのトンネルパケットになる）
[GREの外側IPヘッダ][GREヘッダ][元のパケット]
      ↓ IPsecで暗号化
[IPヘッダ][ESP][暗号化された GRE パケット][ESP認証]
```

GREトンネルの設定例（暗号化なし）:

```
R1(config)# interface tunnel 0
R1(config-if)# ip address 172.16.0.1 255.255.255.252
R1(config-if)# tunnel source g0/1                    ! 自分のグローバル側
R1(config-if)# tunnel destination 198.51.100.1       ! 相手のグローバルアドレス
R1(config-if)# exit
R1(config)# router ospf 1
R1(config-router)# network 172.16.0.0 0.0.0.3 area 0  ! トンネル越しにOSPFが動く
```

```
R1# show interfaces tunnel 0
Tunnel0 is up, line protocol is up
  Hardware is Tunnel
  Internet address is 172.16.0.1/30
  Tunnel source 203.0.113.1 (GigabitEthernet0/1), destination 198.51.100.1
  Tunnel protocol/transport GRE/IP
```

| 誤答 | 理由 |
|---|---|
| AESで通信を暗号化する | GREは暗号化しない。AESで暗号化するのはIPsecなど |
| 無線LANの認証方式 | 無線LANとは無関係 |
| ユニキャストしか運べない | GREは**マルチキャストも運べる**ため、トンネル越しにOSPFなどを動かせる |

> 補足: 現在はVTI（仮想トンネルインターフェース）方式のIPsecやDMVPNなど、IPsecでもルーティングプロトコルを扱える方式もありますが、CCNAでは「GRE＝マルチキャスト可・暗号化なし、従来のIPsec＝暗号化あり・マルチキャスト不可、組み合わせて GRE over IPsec」の理解が問われます。

### ひっかけポイント・よくある誤解

- 拠点間・常時・ルータ同士＝**サイト間VPN**。個人の端末・必要なとき・クライアントソフト＝**リモートアクセスVPN**。VLANやNATはVPNではない。
- IPsecの機能は機密性・完全性・認証・リプレイ防止。**IPアドレス割り当て（DHCP）や帯域保証（QoS）はしない**。
- 元のIPヘッダごと暗号化して新ヘッダを付けるのは**トンネルモード**。トランスポートモードはデータ部分だけ。パッシブモード（FTP）、モニターモード（無線AP）は無関係。
- リモートアクセスVPNの主なプロトコルは**TLS**（TCP 443で通りやすい）。サイト間VPNは主にIPsec。
- **GREは暗号化しない**。GREはマルチキャストを運べる（ユニキャストだけではない）。

### 試験のポイント

- サイト間VPN＝拠点ルータ同士・常時・主にIPsec。リモートアクセスVPN＝端末から必要時・Cisco Secure Client/ブラウザ・TLS（またはIPsec/IKEv2）。
- IPsec＝機密性（AES）・完全性（ハッシュ）・認証・リプレイ防止。
- サイト間VPNはトンネルモード（元のパケット全体を暗号化＋新IPヘッダ）。
- GRE＝カプセル化のみ・暗号化なし・マルチキャスト可 → GRE over IPsec で補完。

### 関連問題

sf-012, sf-013, sf-044, sf-045, sf-046

## 第9章 無線LANセキュリティ（WEP〜WPA3・PSK/802.1X・WLC・PMF）

無線LANは電波が壁の外まで届くため、有線以上に「認証」と「暗号化」が重要です。

### 9.1 無線LANセキュリティ方式の変遷

| 方式 | 暗号 | 状況 |
|---|---|---|
| WEP | **RC4** | 最初の方式。短時間で解読できるため**使ってはいけない** |
| WPA | **TKIP**（RC4ベース） | WEPの弱点を補う**暫定的**な方式。現在は使うべきではない |
| WPA2 | **AES（CCMP）** | 現在も広く使われている標準的な方式 |
| WPA3 | **AES（CCMP、上位のモードではGCMP）** | **最も新しく安全**。パーソナルでは**SAE**、**PMF必須** |

```
古い（危険）                                         新しい（安全）
  WEP(RC4) ──> WPA(TKIP) ──> WPA2(AES-CCMP) ──> WPA3(SAE + PMF必須, AES-CCMP/GCMP)
```

sf-026: 最も新しく安全性が高いのは **WPA3**。
sf-027: WPA2で使われる暗号化は **AES（CCMP）**。

- TKIPはWPAで使われた方式で、WEPと同じRC4をもとにしており、現在は非推奨。
- RC4はWEPで使われた方式で、簡単に解読される。
- **MD5は暗号化方式ではなくハッシュ関数**（データの要約値を作る仕組み）。
- WPA2の設定で暗号方式を選ぶ画面があれば、**TKIPではなくAES**を選ぶ。

#### WPA3のSAE

WPA2パーソナル（PSK）では、攻撃者が接続時のやり取り（4ウェイハンドシェイク）を盗聴しておけば、あとから**オフラインで**パスフレーズを総当たり（辞書攻撃）できてしまいました。WPA3パーソナルは **SAE（Simultaneous Authentication of Equals）** で認証するため、盗聴したデータからパスワードを推測する**オフライン辞書攻撃が難しく**なりました。

### 9.2 パーソナルモード（PSK）とエンタープライズモード（802.1X）（sf-028）

WPA2/WPA3 にはそれぞれ2つのモードがあります。

| 項目 | パーソナル（PSK） | エンタープライズ（802.1X） |
|---|---|---|
| 認証の単位 | 全員が**同じ事前共有キー**（パスフレーズ） | **ユーザーごと**（ユーザー名とパスワード、または証明書） |
| 認証サーバ | 不要 | **RADIUSサーバ**（例：Cisco ISE） |
| 向いている環境 | 家庭、小規模オフィス | 企業 |
| 退職者が出たとき | **全員のキーを変更**しなければならない | **その人のアカウントだけ無効**にすればよい |
| WPA3での認証 | SAE | 802.1X/EAP（EAP-TLSなど） |

```
【エンタープライズ（802.1X）】
 [端末]                [AP / WLC]                [RADIUSサーバ（ISE）]
 サプリカント  ─EAP─>  オーセンティケータ  ─RADIUS─>  認証サーバ
                       ←───── 成功なら接続を許可（暗号鍵も配布）
```

sf-028 の正解は**エンタープライズモード（802.1X）**。

- オープン認証：認証なしで誰でも接続できる方式。
- MACアドレスフィルタリングのみ：MACアドレスは簡単に偽装できるため、単独では安全な認証にならない。

### 9.3 WLCのGUIでWPA2-PSKのWLANを作成する（sf-029）

```
WLC GUI の流れ（AireOS系の例）
 ① WLANs タブ → Create New → Go
      Type: WLAN / Profile Name: CORP-PSK / SSID: CORP-PSK     ← SSID を決める
 ② General タブ → Status: Enabled にチェック                     ← 有効化しないと端末から見えない
 ③ Security タブ → Layer 2 タブ
      Layer 2 Security : WPA+WPA2
      WPA2 Policy      : ☑         WPA2 Encryption : ☑ AES（TKIPは選ばない）
      Authentication Key Management（認証キー管理）:
           802.1X ☐   PSK ☑
           PSK Format: ASCII   [ パスフレーズを入力 ]           ← 事前共有キー
 ④ Apply
```

sf-029 で必要なものは **SSID** と **事前共有キー（パスフレーズ）** の2つ。

| 誤答 | 理由 |
|---|---|
| RADIUSサーバのアドレス | **エンタープライズモード（802.1X）**で必要。PSKでは不要 |
| ユーザーごとのクライアント証明書 | 証明書で認証する方式（**EAP-TLS**）は802.1Xで使う。PSKでは不要 |

> エンタープライズにする場合は、認証キー管理で 802.1X を選び、Security → AAA Servers タブで RADIUS サーバ（事前に Security → RADIUS → Authentication で登録）を指定します。

### 9.4 PMF（Protected Management Frames）（sf-056）

無線LANの**管理フレーム**（ビーコン、認証解除〔deauthentication〕、関連付け解除〔disassociation〕など）は、従来は暗号化も認証もされていませんでした。そのため攻撃者が**偽の切断要求**を送り、端末を無理やり切断させることができました（**認証解除攻撃**）。

```
攻撃者 ── 偽の Deauthentication（送信元をAPに偽装）──> 端末
従来:   端末は本物か確認できず切断される
PMF:    管理フレームに保護（暗号化・完全性チェック）があるため、偽物を破棄できる
```

- **PMF**は **IEEE 802.11w** で定義された機能。
- **WPA2では任意**だったが、**WPA3では必須**。
- WPA3では、SAEによる認証に加え、PMFが必須になって認証解除攻撃を防いでいる。

| 誤答 | 理由 |
|---|---|
| SSIDのステルス（非表示） | 端末の一覧に表示しないだけ。管理フレームは保護されず、効果は小さい（SSIDは他の管理フレームから分かる） |
| MACアドレスフィルタリング | 許可したMACの端末だけ接続。MACは偽装できるので効果は限られる |
| TKIP | WPAの古い暗号化方式。非推奨 |

### ひっかけポイント・よくある誤解

- 新しい順は **WPA3 > WPA2 > WPA > WEP**。WPAはTKIP、WEPはRC4。
- WPA2の暗号は**AES（CCMP）**。TKIPはWPA、RC4はWEP、**MD5はハッシュ関数**で暗号化方式ではない。
- 企業でユーザーごとに認証＝**エンタープライズ（802.1X）＋RADIUS**。PSKは全員で1つのキー。オープン認証は認証なし。MACフィルタは偽装可能で単独では不十分。
- WPA2-PSKのWLAN作成に必要なのは**SSIDとパスフレーズ**。RADIUSや証明書（EAP-TLS）は802.1X用。
- 管理フレームを守るのは**PMF（802.11w）**。SSIDステルスやMACフィルタは管理フレームを保護しない。PMFはWPA3で必須（WPA2では任意）。

### 試験のポイント

- WEP＝RC4、WPA＝TKIP、WPA2＝AES（CCMP）、WPA3＝AES（CCMP/GCMP）＋SAE＋PMF必須。
- パーソナル＝PSK（共有キー）、エンタープライズ＝802.1X＋RADIUS（ユーザーごと）。
- WLCでのWPA2-PSK：SSID → WPA2＋AES → 認証キー管理でPSK＋パスフレーズ → Enabled。
- WPA3のSAEはオフライン辞書攻撃に強い。PMFは認証解除攻撃を防ぐ。
