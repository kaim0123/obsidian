## 1. ネットワーク自動化の意義と従来型ネットワーク

### 1.1 従来型（コントローラを使わない）ネットワークの姿

ネットワークの自動化を理解する出発点は、「自動化しないとどうなっているか」を知ることです。

従来型のネットワークでは、ルータやスイッチの **1台1台が独立した“頭脳”** を持っています。

```
          従来型（分散型）ネットワーク

   管理者 ──SSH──> R1   管理者 ──SSH──> R2   管理者 ──SSH──> SW1
                   │                    │                    │
              [頭脳+転送]  <--OSPF-->  [頭脳+転送]  <--STP-->  [頭脳+転送]

   ・設定は 1 台ずつ CLI（SSH/コンソール）で投入
   ・経路の判断（コントロールプレーン）は各機器が隣接機器と情報交換して個別に実施
```

- **経路などの判断（コントロールプレーン）が各機器に分散**している。各ルータは OSPF などで隣接ルータと情報を交換し、自分でルーティングテーブルを作ります。
- **設定も機器ごとに分散**している。管理者は SSH やコンソールで 1 台ずつログインし、CLI でコマンドを入力します。
- もちろん、パケットを実際に転送する **データプレーンはどの機器にもあります**（これはコントローラ型でも同じ）。
- 従来型の機器の設定手段は主に **CLI（SSH/コンソール）** であり、「REST API しか使えない」ということはありません。

### 1.2 手作業による管理の問題点

台数が少ないうちは CLI での手作業でも困りません。しかし数十〜数千台になると次の問題が顕在化します。

| 問題 | 内容 |
| --- | --- |
| 時間がかかる | 台数に比例して作業時間が増える。メンテナンス時間内に終わらない |
| 入力ミス | タイプミス、コピー&ペーストの貼り間違い、対象機器の取り違え |
| 不統一 | 同じ役割の機器でも担当者ごとに書き方がばらばら（→ 構成ドリフト。12章） |
| 確認が大変 | 設定が標準どおりかを 1 台ずつ `show running-config` で目視確認 |
| 履歴が残らない | 誰がいつ何を変えたのかが追えない |

### 1.3 自動化のメリット

自動化（スクリプト、構成管理ツール、コントローラなど）を導入すると、

- **手作業による設定ミスが減る**
- **多数の機器に同じ設定を一貫して適用できる**
- 作業時間が短縮される
- 設定が標準どおりかを **機械的に確認** できる
- 変更履歴を管理しやすくなる（Git などと組み合わせる。12章）

という効果があります。

一方で、次のような「自動化で起きないこと」もはっきり区別しておきましょう。

| 誤った期待 | 実際 |
| --- | --- |
| ルータやスイッチが不要になる | 自動化は機器の設定・管理を効率化するもの。**機器そのものは必要** |
| セキュリティ対策が不要になる | 不要にはならない。むしろ **自動化の仕組み自体（認証情報、APIトークン、管理サーバ）を守る必要** が生じる |
| 回線の帯域幅が増える | 帯域幅は回線契約や物理的な性能で決まる。自動化とは無関係 |

### 1.4 コントローラ型との比較（予告）

| 観点 | 従来型 | コントローラ型（SDN） |
| --- | --- | --- |
| コントロールプレーン | 各機器に分散 | コントローラに集中 |
| 設定方法 | 1台ずつ CLI | コントローラの GUI / API でまとめて |
| 全体の把握 | 機器ごとにログインして確認 | コントローラで一覧表示 |
| データプレーン | 各機器 | 各機器（変わらない） |

コントローラ型の詳細は 3章・4章で扱います。

### ひっかけポイント・よくある誤解

- 「自動化すれば機器が要らなくなる」「セキュリティ対策が不要になる」「帯域が増える」はすべて誤り（au-004）。
- 「コントローラがすべての機器の転送ルールを一元的に決める」は **コントローラ型（SDN）** の特徴であって、従来型ではない（au-005）。
- 「従来型の機器は REST API でしか設定できない」は誤り。従来型は **CLI（SSH/コンソール）** が中心（au-005）。
- 「従来型はデータプレーンを持たない」は誤り。**データプレーンはどの方式でも各機器にある**（au-005）。

### 試験のポイント

- 自動化の主なメリット ＝ **ミスの削減と設定の一貫性**、時間短縮、確認の機械化、履歴管理。
- 従来型 ＝ **分散型コントロールプレーン ＋ 機器ごとの CLI 設定**。
- 自動化しても機器・セキュリティ対策は必要。自動化基盤そのものの保護も課題になる。

### 関連問題

## 2. ネットワーク機器の3つのプレーン

### 2.1 プレーンとは

ネットワーク機器の中で行われる処理は、役割ごとに **3つのプレーン（層）** に分けて考えます。SDN を理解するための必須の概念です。

```
 ┌──────────────────────────────────────────────┐
 │ 管理プレーン (Management Plane)               │  機器を「管理」する
 │   SSH/Telnet ログイン, SNMP, Syslog, NTP,    │
 │   API(NETCONF/RESTCONF)による設定            │
 ├──────────────────────────────────────────────┤
 │ コントロールプレーン (Control Plane)          │  転送の「ルール」を決める
 │   OSPF/EIGRP/BGP, STP(BPDU), ARP             │
 │   → ルーティングテーブル / MACテーブル等を作る │
 ├──────────────────────────────────────────────┤
 │ データプレーン (Data Plane / Forwarding)      │  ルールに従って「転送」する
 │   パケット転送, フレームのスイッチング,        │
 │   ACL による破棄, NAT の変換, カプセル化       │
 └──────────────────────────────────────────────┘
```

| プレーン | 一言でいうと | 主な例 |
| --- | --- | --- |
| **コントロールプレーン** | 「どう転送するか」を決める | OSPF などのルーティングプロトコル（ネイバーとのルート情報・LSA 交換）、STP の BPDU 送受信とブロックポートの決定、ARP による MAC アドレスの学習 |
| **データプレーン**（フォワーディングプレーン） | 決まったルールに従って実際に転送する | ルーティングテーブルに基づくパケット転送、MAC アドレステーブルに基づくフレーム転送、ACL の deny に一致したパケットの破棄、NAT のアドレス変換 |
| **管理プレーン** | 機器そのものを管理・監視する | SSH/Telnet でのログイン、SNMP による監視、Syslog の送信、NTP、API による設定 |

### 2.2 判断のコツ

迷ったら次の質問で判定します。

1. **ユーザーのパケット／フレーム 1 つ 1 つに対する処理か？** → データプレーン
   - 「転送する」だけでなく「**破棄する**」（ACL の deny）もパケットごとの判断なのでデータプレーン。
2. **転送ルール（テーブル）を作るための、機器同士の情報交換か？** → コントロールプレーン
   - OSPF の LSA 交換、STP の BPDU、ARP。
3. **人や管理システムが機器を操作・監視するための通信か？** → 管理プレーン
   - SSH ログイン、SNMP で CPU 使用率を送る、Syslog、NTP。

```
例：ルータ R1 がパケットを受信した時の流れ

  [コントロールプレーン] OSPF でルートを学習 ──> ルーティングテーブル作成
                                                     │（ルールを渡す）
                                                     ▼
  受信パケット ──> [データプレーン] テーブルを引いて出力IFへ転送 ──> 送信
                                    （ACL deny ならここで破棄）

  管理者 ──SSH──> [管理プレーン] show コマンドで状態を確認
```

> 補足：ARP は「IP と MAC の対応表（ARP テーブル）を作る」処理なので、CCNA の教材ではコントロールプレーンに分類されます。テーブル作成＝コントロール、テーブル参照による転送＝データ、と覚えるとぶれません。

### 2.3 SDN との関係

SDN（3章）では、このうち **コントロールプレーンの処理をコントローラに集約** します。データプレーンは引き続き各機器が担います。「アプリケーションプレーン」という言葉は SDN アーキテクチャの層（アプリケーション層）を指して使われることはありますが、**一般的なネットワーク機器の3つのプレーンには含まれません**。

### ひっかけポイント・よくある誤解

- 「ACL の deny で破棄する」は **データプレーン**。「セキュリティのルールだからコントロール」と考えるのは誤り（au-007）。
- 「スイッチが MAC アドレステーブルに従ってフレームを転送する」は **データプレーン**（au-007）。MAC アドレスを「学習してテーブルを作る」ことと「テーブルを引いて転送する」ことを混同しない。
- 「SSH でログイン」は **管理プレーン**（au-007）。
- 「STP の BPDU を送受信してブロックするポートを決める」は、どのポートを使うかというルールを決めるので **コントロールプレーン**（au-027）。
- 「SNMP で CPU 使用率を監視マネージャへ送る」は **管理プレーン**（au-027）。
- 「アプリケーションプレーン」は機器の3プレーンには含まれない（au-006）。
- データプレーンは「フォワーディングプレーン」とも呼ぶ（au-006）。

### 試験のポイント

- **コントロール＝決める、データ＝転送する（破棄も含む）、管理＝管理する**。
- OSPF / STP / ARP → コントロール。転送 / ACL 破棄 / NAT → データ。SSH / SNMP / Syslog / NTP / API → 管理。
- SDN はコントロールプレーンを集約する技術。

### 関連問題

au-006, au-007, au-027

## 3. SDNのアーキテクチャとノースバウンド／サウスバウンドAPI

### 3.1 SDN とは

**SDN（Software-Defined Networking）** は、ネットワークの制御をソフトウェア（**コントローラ**）に集約し、ネットワーク全体をプログラムから制御できるようにする考え方です。

- 従来：各機器がコントロールプレーンを持ち、個別に判断（分散型）
- SDN：**コントローラがネットワーク全体を把握し、コントロールプレーンを集中して担う**。各機器はコントローラの指示に従ってデータを転送する（データプレーン）

Cisco の SDN コントローラの代表例が **Catalyst Center（旧DNA Center）** です（4章）。

コントローラは、アクセススイッチ、ファイアウォール、無線アクセスポイントとは役割が異なります。

| 機器 | 役割 |
| --- | --- |
| **コントローラ** | ネットワーク全体を把握し、各機器に指示を出す（制御の集中） |
| アクセススイッチ | 端末をつなぐ層のスイッチ。SDN では主に **データプレーン（転送）** を担う |
| ファイアウォール | 通信を許可・拒否してネットワークを守る |
| 無線アクセスポイント（AP） | 無線端末をネットワークにつなぐ。多数の AP を集中管理するのは **WLC（無線LANコントローラ）** |

### 3.2 SDN の3層構造と API の向き

SDN の構成図は、上にアプリケーション、真ん中にコントローラ、下にネットワーク機器を描きます。地図と同じく **上が北（North）、下が南（South）** です。

```
 ┌───────────────────────────────────────────────┐
 │ アプリケーション層                               │
 │  管理ツール / Python スクリプト / 監視・チケット │
 └───────────────────────────────────────────────┘
                  ▲  ノースバウンドAPI（NBI）
                  │  例：REST API（HTTPS + JSON）
                  ▼
 ┌───────────────────────────────────────────────┐
 │ コントロール層：SDNコントローラ                   │
 │  （Catalyst Center など）ネットワーク全体を把握    │
 └───────────────────────────────────────────────┘
                  ▲  サウスバウンドAPI（SBI）
                  │  例：NETCONF, RESTCONF, OpenFlow,
                  │      CLI(SSH), SNMP
                  ▼
 ┌───────────────────────────────────────────────┐
 │ インフラストラクチャ層：ルータ / スイッチ / AP      │
 │  （データプレーン＝実際の転送）                    │
 └───────────────────────────────────────────────┘
```

| API | どこの間か | 代表的な技術 |
| --- | --- | --- |
| **ノースバウンドAPI** | **コントローラ ⇔ その上で動くアプリケーション**（管理ツール、スクリプトなど） | **REST API**（HTTPS + JSON） |
| **サウスバウンドAPI** | **コントローラ ⇔ ネットワーク機器** | **NETCONF、RESTCONF、OpenFlow**、CLI（SSH）、SNMP |

- ノースバウンドAPI を使うと、アプリケーションがコントローラに指示を出したり、情報（機器一覧、障害情報など）を取得したりできます。
- **機器同士**（ルータとルータ）の通信は OSPF などのプロトコルで行われ、ノースバウンド／サウスバウンドという API の区分には入りません。
- ユーザーの PC とインターネットの間の通信も SDN の API とは無関係です。

### 3.3 サウスバウンドのプロトコル

#### OpenFlow

- **ONF（Open Networking Foundation）** が標準化した、初期の SDN を代表するサウスバウンドプロトコル。
- コントローラがスイッチの **フローテーブル**（どのパケットをどう転送するかのルール）を **直接書き換える**。
- コントロールプレーンを **完全にコントローラへ移し**、スイッチは受け取ったルールに従って転送するだけになる。

```
 コントローラ ──OpenFlow──> スイッチのフローテーブル
                           ┌─────────────────────────────┐
                           │ 一致条件            │ 動作    │
                           │ 宛先IP 10.1.1.0/24  │ port 2  │
                           │ TCP 宛先ポート 23   │ drop    │
                           └─────────────────────────────┘
```

#### NETCONF / RESTCONF

- 機器の **設定や状態を取得・変更** するためのプロトコル（詳細は 10章）。
- **NETCONF**：SSH（TCP 830）＋ XML。
- **RESTCONF**：HTTPS ＋ JSON/XML。
- どちらも **YANG** というデータモデルで設定項目の構造が定義されている。

#### CLI（SSH）・SNMP

- 従来の機器を扱うために、コントローラが SSH で CLI コマンドを投入したり、SNMP で情報を収集したりすることもある。

### 3.4 サウスバウンドと間違えやすいプロトコル

| プロトコル | 実際の役割 | SDN のサウスバウンド？ |
| --- | --- | --- |
| HSRP | デフォルトゲートウェイを冗長化する FHRP の一つ | いいえ |
| DHCP | 端末に IP アドレスを自動割り当て | いいえ |
| ARP | IP アドレスから MAC アドレスを調べる | いいえ |
| OSPF | ルータ同士がルート情報を交換するルーティングプロトコル | いいえ（コントローラが使うものではない） |
| LLDP | 隣接機器の情報を取得する | いいえ |
| NETCONF / RESTCONF / OpenFlow | 機器の設定・転送ルールを制御 | **はい** |

### ひっかけポイント・よくある誤解

- 「コントローラとネットワーク機器の間」はノースバウンドではなく **サウスバウンド**（au-008）。
- 「ネットワーク機器同士の間」は API 区分ではない（au-008）。
- 「アクセススイッチが制御を担う」は誤り。SDN ではアクセススイッチは主に **データプレーン**（au-001）。
- 多数の AP を集中管理する機器は **WLC**。AP 自体がコントローラではない（au-001）。
- HSRP / DHCP / ARP / OSPF / LLDP をサウスバウンドプロトコルと取り違えない（au-009, au-040）。
- OpenFlow は「フローテーブルを直接書き換える」。NETCONF は「設定を取得・変更する」。役割の言い回しで区別する（au-040, au-038）。

### 試験のポイント

- SDN ＝ **コントロールプレーンをコントローラに集約**、機器はデータプレーンを担う。
- **ノースバウンド＝コントローラとアプリ間（REST API）**、**サウスバウンド＝コントローラと機器間（NETCONF / RESTCONF / OpenFlow / CLI / SNMP）**。
- OpenFlow ＝ ONF 標準、フローテーブルを直接制御。
- Cisco のコントローラ例 ＝ Catalyst Center（旧DNA Center）。

### 関連問題

au-001, au-008, au-009, au-040

## 4. Catalyst Center・インテントベースネットワーキング・SD-Access

### 4.1 Catalyst Center（旧DNA Center）

**Catalyst Center** は Cisco のキャンパス（企業LAN）ネットワーク向けコントローラです。以前は **DNA Center** と呼ばれていました。

主な機能：

- 多数の機器を **1か所から管理** し、ポリシーや設定を **まとめて適用**
- 機器の状態の監視（アシュアランス）、障害の分析
- ソフトウェア（OS イメージ）の一括更新
- GUI に加え、**REST API（ノースバウンドAPI）** を公開。スクリプトや他システムからも操作できる
- SD-Access ファブリックの管理

従来型との対比：

| 観点 | 従来型の管理 | コントローラ（Catalyst Center）による管理 |
| --- | --- | --- |
| 設定の確認 | **機器ごとにログイン** して確認 | コントローラで **一覧** 確認 |
| 設定の適用 | 1台ずつ CLI | ポリシーとしてまとめて適用 |
| 一貫性 | 担当者次第でばらつく | テンプレート・ポリシーで統一 |
| 障害対応 | ログを機器ごとに収集 | 集中監視で原因を素早く特定 |

注意点：

- コントローラで管理していても、**必要に応じて SSH/CLI でのログインは可能**。CLI が使えなくなるわけではありません。
- コントローラは機器と **IP で通信する** ため、機器には **管理用の IP アドレスが必要** です。

### 4.2 インテントベースネットワーキング（IBN）

**インテント（Intent）＝意図、「何を実現したいか」** のことです。

```
 従来：管理者が「どう設定するか(How)」を考え、機器ごとにコマンドを入力
   管理者 → R1 : access-list 101 deny ip 10.50.0.0 0.0.255.255 10.10.0.0 0.0.255.255 ...
          → SW1: ...
          → SW2: ...

 IBN：管理者は「何をしたいか(What)」= ポリシーを定義するだけ
   管理者 →「来客用の端末は社内サーバにアクセスさせない」
             │
             ▼
        コントローラ（Catalyst Center）
             │ ① 意図を各機器の具体的な設定に変換（翻訳）
             │ ② 各機器へ自動適用
             │ ③ 意図どおりに動いているかを継続的に確認（アシュアランス）
             ▼
        R1 / SW1 / SW2 / WLC ...
```

- IBN の代表的な製品が **Catalyst Center（旧DNA Center）**。
- 「ポリシーを定義 → コントローラが変換・適用 → 継続的に確認」の流れが IBN の特徴です。

### 4.3 Cisco SD-Access

**SD-Access** は Catalyst Center が管理する、キャンパス向けの SDN ソリューションです。
**物理ネットワーク（アンダーレイ）の上に、仮想ネットワーク（オーバーレイ）を作る** のが基本構造です。

```
   ┌───────────── オーバーレイ（仮想ネットワーク）──────────────┐
   │  VN: 社員     VN: 来客     VN: IoT       ← 利用者/端末を   │
   │                                           グループ分け    │
   │      ═══════ VXLAN トンネル ═══════                      │
   └──────────────────────────────────────────────────────────┘
   ┌───────────── アンダーレイ（物理ネットワーク）──────────────┐
   │  物理スイッチ・ルータを IP ルーティング（例：IS-IS）で接続   │
   │   [Edge]──[Border]──[Edge]──[Control Plane Node]         │
   └──────────────────────────────────────────────────────────┘
          アンダーレイ ＋ オーバーレイ ＝ ファブリック
                    管理：Catalyst Center
```

| 用語 | 意味 |
| --- | --- |
| **アンダーレイ** | 物理的なスイッチ・ルータと、それらを **IP ルーティングでつないだ** 土台のネットワーク |
| **オーバーレイ** | アンダーレイの上に、**トンネル（VXLAN）** を使って作る仮想的なネットワーク |
| **ファブリック** | アンダーレイとオーバーレイを合わせた **ネットワーク全体** |

利用者や端末はオーバーレイでグループ分けされるため、**物理的な接続場所に関係なく同じポリシーを適用** できます（例：社員はどのフロアのどのポートにつないでも「社員」のポリシー）。

#### SD-Access の3つの要素

| 要素 | 技術 | 役割 |
| --- | --- | --- |
| **データプレーン** | **VXLAN** | 元のフレームを **UDP パケットで包んで（カプセル化）**、アンダーレイ越しに運ぶ |
| **コントロールプレーン** | **LISP** | 端末が **どこ（どのエッジ）にいるか** を管理する。データのカプセル化はしない |
| **ポリシー** | **Cisco TrustSec（SGT）** | セキュリティグループタグでグループ単位のアクセス制御 |

VXLAN のカプセル化のイメージ：

```
 ┌──────────┬────────┬────────┬─────────────────────────────────┐
 │ 外側 IP   │ 外側UDP │ VXLAN  │ 元のEthernetフレーム（内側）       │
 │(エッジ間) │ (4789) │ ヘッダ  │ 宛先MAC/送信元MAC/IP/データ ...    │
 └──────────┴────────┴────────┴─────────────────────────────────┘
   ↑ アンダーレイはこの外側IPだけを見てルーティングする
```

VXLAN でカプセル化することで、**物理ネットワーク（アンダーレイ）の構成に関係なく** 仮想ネットワークを自由に作れます。

#### 間違えやすい技術

| 技術 | 実際の役割 | SD-Access のオーバーレイのカプセル化？ |
| --- | --- | --- |
| VXLAN | L2 フレームを UDP でカプセル化 | **はい（データプレーン）** |
| LISP | 端末の位置情報の管理 | いいえ（コントロールプレーン） |
| 802.1Q | トランクで VLAN タグを付ける | いいえ |
| NAT | IP アドレス変換 | いいえ（カプセル化しない） |

### ひっかけポイント・よくある誤解

- 「コントローラを使うと SSH/CLI でログインできなくなる」は誤り（au-012）。
- 「機器ごとにログインして設定を確認する必要がある」は従来型の特徴（au-012）。
- 「機器に IP アドレスが不要になる」は誤り。管理用 IP は必要（au-012）。
- 物理的なネットワーク＝**アンダーレイ**。オーバーレイ（仮想）やファブリック（全体）と取り違えない。「ノースバウンド」は API の用語（au-010）。
- LISP は SD-Access で使われるが **コントロールプレーン**。カプセル化は VXLAN（au-011）。
- 「ポリシーを定義するとコントローラが設定に変換」＝ **IBN**。構成ドリフト（設定のずれ）やロンゲストマッチ（ルート選択規則）とは無関係（au-041）。

### 試験のポイント

- Catalyst Center（旧DNA Center）＝ Cisco のキャンパス向けコントローラ。**GUI ＋ REST API（ノースバウンド）**。
- IBN ＝「何をしたいか」を定義 → コントローラが変換・適用・継続確認。
- SD-Access：**アンダーレイ（物理）＋オーバーレイ（仮想）＝ファブリック**。
- SD-Access の要素：**データ＝VXLAN、コントロール＝LISP、ポリシー＝TrustSec（SGT）**。

### 関連問題

au-010, au-011, au-012, au-041

## 5. REST APIの基礎：特徴・URI・HTTPメソッドとCRUD

### 5.1 API と REST

**API（Application Programming Interface）** は、プログラム同士がやり取りするための窓口です。人が GUI や CLI を操作する代わりに、プログラムが API を呼び出して情報取得や設定変更を行います。

**REST（REpresentational State Transfer）** は、**HTTP を使った API の設計方式** です。REST の考え方に沿った API を REST API（RESTful API）と呼びます。Catalyst Center のノースバウンドAPI や RESTCONF などで使われます。

REST では、リクエストを次の2つで表します。

- **どのリソースに** → **URI**（例：`/api/v1/network-device`）
- **何をするか** → **HTTP メソッド**（例：`GET`）

### 5.2 REST の主な特徴

| 特徴 | 説明 |
| --- | --- |
| **ステートレス** | サーバは **前のリクエストの状態を保持しない**。1つ1つのリクエストに、処理に必要な情報（**認証情報** など）をすべて含める |
| クライアント／サーバ | クライアント（スクリプト等）がリクエストし、サーバ（コントローラ等）が応答する |
| 統一インターフェース | リソースを URI で識別し、HTTP メソッドで操作する |
| キャッシュ可能 | 応答がキャッシュ可能かどうかを示せる |
| 階層化システム | 間にプロキシやロードバランサがあってもよい |

**なぜステートレスが嬉しいのか**：サーバがクライアントごとのセッション状態を覚えていなくてよいので、どのサーバがリクエストを受けても処理できます。結果として **負荷分散がしやすく、構成をシンプルにできます**。代わりに、毎回のリクエストにトークンなどの認証情報を付ける必要があります。

その他の重要事項：

- REST API は **HTTP/HTTPS を使うので、TCP 上で動作**します（HTTPS は通常 TCP 443）。「必ず UDP を使う」は誤り。
- データ形式は **JSON がよく使われる** が、**XML など他の形式も使える**。「XML しか使えない」は誤り。

### 5.3 URI の構造

```
 GET https://controller.example.com/api/v1/network-device?family=Switches
     └─┬─┘   └────────┬──────────┘ └────────┬─────────┘ └──────┬───────┘
     スキーム        ホスト                 パス           クエリパラメータ
   （プロトコル）  （サーバ）    （操作の対象となるリソース） （絞り込み条件）
```

| 部分 | 例 | 意味 |
| --- | --- | --- |
| スキーム | `https` | 通信方式 |
| ホスト | `controller.example.com` | API サーバ（コントローラ） |
| パス | `/api/v1/network-device` | **操作の対象となるリソース**（ここではネットワーク機器の一覧） |
| クエリパラメータ | `?family=Switches` | 条件による絞り込み（`?キー=値`、複数は `&` で連結） |

- パスに `v1` のような **バージョン** を入れておくと、API の仕様が変わっても古いバージョンを使い続けられます。
- **操作の種類は URI ではなく HTTP メソッド** で表します。
- **認証情報は URI に含めず、HTTP ヘッダ**（`Authorization` など）で送るのが通常です。
- **希望する応答のデータ形式は `Accept` ヘッダ** などで指定します。

### 5.4 HTTP メソッドと CRUD

データに対する基本操作 **Create（作成）・Read（取得）・Update（更新）・Delete（削除）** をまとめて **CRUD** と呼びます。REST では CRUD を HTTP メソッドに対応させます。

| CRUD | HTTP メソッド | 動作 | データを変更するか |
| --- | --- | --- | --- |
| **C**reate | **POST** | 新しいリソースを作成 | する |
| **R**ead | **GET** | リソースを取得 | **しない** |
| **U**pdate | **PUT** | 既存リソースを **全体置き換え** | する |
| **U**pdate | **PATCH** | 既存リソースの **一部の項目だけ** 更新 | する |
| **D**elete | **DELETE** | リソースを削除 | する |

#### PUT と PATCH の違い

元のリソース：

```json
{"vlan": 10, "name": "Sales", "description": "3F"}
```

**PATCH** で `name` だけを送る → 送った項目だけ変わる：

```http
PATCH /api/v1/vlans/10
Content-Type: application/json

{"name": "Sales-JP"}
```

結果：`{"vlan": 10, "name": "Sales-JP", "description": "3F"}`

**PUT** で同じように一部だけ送る → リソース全体が送った内容で置き換わる：

```http
PUT /api/v1/vlans/10
Content-Type: application/json

{"vlan": 10, "name": "Sales-JP"}
```

結果：`{"vlan": 10, "name": "Sales-JP"}` ← **送らなかった description は消えたり初期値に戻ったりする**

つまり PUT と PATCH の違いは **更新の範囲が全体か一部か** です。

### 5.5 リクエストと応答の例

機器一覧を取得する（Read）：

```http
GET /api/v1/network-device HTTP/1.1
Host: controller.example.com
Accept: application/json
X-Auth-Token: eyJ0eXAiOiJKV1Qi...
```

応答：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "response": [
    {"hostname": "SW1", "managementIpAddress": "10.1.1.11", "family": "Switches and Hubs"},
    {"hostname": "R1",  "managementIpAddress": "10.1.1.1",  "family": "Routers"}
  ]
}
```

Python（requests ライブラリ）で書くと次のようになります。

```python
import requests

url = "https://controller.example.com/api/v1/network-device"
headers = {"Accept": "application/json", "X-Auth-Token": token}
r = requests.get(url, headers=headers)
if r.status_code == 200:          # ステータスコードで成功を判定（6章）
    for dev in r.json()["response"]:
        print(dev["hostname"])
```

### ひっかけポイント・よくある誤解

- 取得は **GET**。POST（作成）、PUT（更新・置き換え）、DELETE（削除）と混同しない（au-003）。
- 一部だけ更新は **PATCH**。PUT は全体置き換えで、送らなかった項目は消えたり初期値に戻ったりする（au-015）。
- GET は **データを変更しない**（au-015）。
- 「サーバがセッション状態を保持し続ける」はステートフルの説明。REST は **ステートレス**（au-013）。
- 「REST は必ず UDP」は誤り。**HTTP/HTTPS ＝ TCP**（au-013）。
- 「XML しか使えない」は誤り。**JSON が主流**、XML も可（au-013）。
- URI のパスは **リソース**。操作の種類（メソッド）、認証情報（ヘッダ）、応答形式（Accept ヘッダ）ではない（au-028）。

### 試験のポイント

- REST ＝ HTTP ベース、**ステートレス**、URI でリソース、メソッドで操作。
- CRUD：**Create=POST / Read=GET / Update=PUT(全体)・PATCH(一部) / Delete=DELETE**。
- URI：スキーム・ホスト・パス・クエリ。パスにバージョン（v1）を含めることが多い。

### 関連問題

au-003, au-013, au-015, au-028

## 6. HTTPステータスコードとHTTPヘッダ

### 6.1 HTTP リクエスト／レスポンスの構成

HTTP のリクエストは **メソッドと URI、ヘッダ、本文（ボディ）** で構成されます。

```
 ── リクエスト ─────────────────────────────
 POST /api/v1/vlans HTTP/1.1          ← メソッド + URI（リクエスト行）
 Host: controller.example.com          ┐
 Content-Type: application/json        │ ヘッダ
 Accept: application/json              │
 Authorization: Bearer eyJhbGci...     ┘
                                       ← 空行
 {"vlan": 20, "name": "Eng"}           ← 本文（ボディ）

 ── レスポンス ─────────────────────────────
 HTTP/1.1 201 Created                  ← ステータスコード
 Content-Type: application/json        ← ヘッダ

 {"vlan": 20, "name": "Eng"}           ← 本文
```

### 6.2 ステータスコード

ステータスコードは **先頭の数字** で大きく分類されます。スクリプトではこのコードを確認して処理が成功したかどうかを判断します。

| 分類 | 意味 | 主なコード |
| --- | --- | --- |
| 1xx | 情報 | 100 Continue |
| **2xx** | **成功** | **200 OK**、**201 Created**、**204 No Content** |
| 3xx | リダイレクト | 301 Moved Permanently |
| **4xx** | **クライアント側の問題** | **400 Bad Request**、**401 Unauthorized**、**403 Forbidden**、**404 Not Found** |
| **5xx** | **サーバ側の問題** | **500 Internal Server Error** |

各コードの詳細：

| コード | 意味 | 典型的な場面 |
| --- | --- | --- |
| **200 OK** | リクエスト成功（一般的な成功） | GET の成功など |
| **201 Created** | 新しいリソースが作成された | **POST での作成に成功** |
| **204 No Content** | 成功したが返す本文はない | DELETE の成功など |
| **400 Bad Request** | リクエストの書式・内容に誤り | **JSON の文法エラー**（カンマ抜け等）を送った |
| **401 Unauthorized** | **認証の失敗**：認証情報がない／誤っている（「あなたは誰？」） | トークンなし、パスワード誤り |
| **403 Forbidden** | **認可の失敗**：誰かはわかったが権限がない（「あなたにはその権限がない」） | 読み取り専用ユーザーが変更しようとした |
| **404 Not Found** | 指定したリソース（URI）が見つからない | URI のタイプミス、存在しない機器 ID |
| **500 Internal Server Error** | サーバ側でエラー | サーバの不具合・障害 |

#### 401 と 403 の違い ＝ AAA の「認証」と「認可」

```
 リクエスト ─> [認証 Authentication] 誰？ ──失敗──> 401 Unauthorized
                     │成功
                     ▼
              [認可 Authorization] その操作をしてよい？ ──失敗──> 403 Forbidden
                     │成功
                     ▼
              処理実行 ──> 200 / 201 / 204
```

名前は "Unauthorized（認可されていない）" なのに実際は **認証** の失敗を表す点がややこしいので注意しましょう。

### 6.3 よく使う HTTP ヘッダ

| ヘッダ | 方向 | 意味 | 例 |
| --- | --- | --- | --- |
| **Content-Type** | 送る側 | **送る本文の形式** | `Content-Type: application/json`（XML なら `application/xml`） |
| **Accept** | リクエスト | **受け取りたい応答の形式** | `Accept: application/json` |
| **Authorization** | リクエスト | 認証情報 | `Authorization: Basic YWRtaW46Q2lzY28xMjM=` / `Authorization: Bearer <トークン>` |
| User-Agent | リクエスト | リクエストを送ったソフトウェアの種類 | `User-Agent: python-requests/2.31` |
| X-Auth-Token | リクエスト | Catalyst Center などで使うトークン用ヘッダ | `X-Auth-Token: eyJ...` |

**Content-Type（送る形式）と Accept（受け取りたい形式）** は混同しやすいポイントです。「POST の本文が JSON であることを伝える」のは **Content-Type** です。

### ひっかけポイント・よくある誤解

- 認証情報がない／誤り → **401**。200（成功）、404（リソースなし）、500（サーバエラー）ではない（au-014）。
- 認証成功だが権限なし → **403**。401 と取り違えない（au-030）。
- POST で作成成功 → **201 Created** が多い。200 は一般的な成功（GET など）、400 は書式誤り、500 はサーバエラー（au-029）。
- 本文の形式は **Content-Type**。Accept は受け取りたい形式、Authorization は認証、User-Agent はソフトウェアの種類（au-031）。

### 試験のポイント

- **2xx 成功 / 4xx クライアント側 / 5xx サーバ側**。
- **200 OK、201 Created、204 No Content、400 Bad Request、401 Unauthorized（認証）、403 Forbidden（認可）、404 Not Found、500 Internal Server Error**。
- Content-Type ＝ 送る形式、Accept ＝ 受け取りたい形式。

### 関連問題

au-014, au-029, au-030, au-031

## 7. REST APIの認証と認可（Basic認証・トークン・APIキー・OAuth）

REST はステートレスなので、**リクエストのたびに「誰が送ったか」を証明する情報** を付けます。主な方式は次のとおりです。

| 方式 | 仕組み | 注意点 |
| --- | --- | --- |
| **Basic認証** | `ユーザー名:パスワード` を **Base64 でエンコード** し、`Authorization: Basic ...` ヘッダに入れて送る | Base64 は **暗号化ではなく誰でも元に戻せる**。必ず **HTTPS** と組み合わせる。パスワードを毎回送る |
| **トークン認証**（Bearer トークンなど） | 最初の認証で発行された **一時的な文字列（トークン）** を、以降のリクエストに付けて送る | トークンには有効期限がある |
| **APIキー** | 事前に発行された **固定のキー文字列** をリクエストに付けて送る | 漏れると悪用されるので管理が重要 |
| **OAuth** | 利用者のパスワードを他のアプリに渡さずに、**必要な範囲だけのアクセス権を委任** する。アプリは **アクセストークン** を受け取って API にアクセス | トークンには **有効期限とスコープ（使える範囲）** があり、不要になれば **取り消せる** |

### 7.1 Basic 認証の中身

```
 ユーザー名: admin   パスワード: Cisco123
        ↓ "admin:Cisco123" を Base64 エンコード
 Authorization: Basic YWRtaW46Q2lzY28xMjM=
        ↓ 誰でもデコードできる
 "admin:Cisco123"   ← だから HTTPS(TLS) で通信路を暗号化する必要がある
```

### 7.2 トークン認証の流れ（Catalyst Center の例）

Catalyst Center の API では、**まず Basic 認証でトークンを取得し、以降のリクエストではそのトークンを使います**。

```http
POST /dna/system/api/v1/auth/token HTTP/1.1
Host: catalyst-center.example.com
Authorization: Basic YWRtaW46Q2lzY28xMjM=
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"Token": "eyJ0eXAiOiJKV1QiLCJhbGciOiJSUzI1NiJ9..."}
```

```http
GET /dna/intent/api/v1/network-device HTTP/1.1
Host: catalyst-center.example.com
X-Auth-Token: eyJ0eXAiOiJKV1QiLCJhbGciOiJSUzI1NiJ9...
Accept: application/json
```

パスワードを送るのは最初の1回だけで済み、以降は期限付きのトークンを使うのが利点です。

### 7.3 OAuth（認可の委任）

「Google アカウントでログイン」のように、**外部のサービスに自分のパスワードを教えずに連携できる** のは OAuth の仕組みによります。

```
 利用者 ──(1) アプリAに「私のデータを使っていいよ」と許可──> 認可サーバ
                                                      │
 アプリA <──(2) アクセストークン（期限・スコープ付き）─────┘
   │
   └──(3) Authorization: Bearer <アクセストークン> ──> API サーバ
        ※ アプリAは利用者のパスワードを一度も知らない
```

- **認可（何をしてよいか）の委任** の仕組みとして広く使われます。
- Basic 認証との対比：Basic 認証では **パスワードそのものをアプリに渡す** ことになる。

### 7.4 間違えやすい用語

| 用語 | 正体 |
| --- | --- |
| AAA | 認証（Authentication）・認可（Authorization）・アカウンティング（Accounting）の **枠組み**。HTTP ヘッダ形式の名前ではない |
| SNMPv2c | 機器監視のプロトコル。**コミュニティ名を平文で送る** |
| WPA2-PSK | 無線 LAN で事前共有キーを使って認証する方式 |

### ひっかけポイント・よくある誤解

- 「Base64 でエンコードして Authorization ヘッダ」＝ **Basic認証**。トークン認証（一時的な文字列）、APIキー（固定キー）、AAA（枠組み）ではない（au-016）。
- **Base64 は暗号化ではない**（au-016）。
- 「パスワードを渡さずに、必要な範囲だけのアクセス権を委任」＝ **OAuth**。Basic認証は逆にパスワードを渡す方式（au-049）。
- SNMPv2c や WPA2-PSK は REST API の認可方式ではない（au-049）。

### 試験のポイント

- Basic（Base64、HTTPS 必須）／トークン（Bearer、一時的）／APIキー（固定）／OAuth（委任、スコープ・期限・取り消し）。
- Catalyst Center：Basic 認証でトークン取得 → 以降はトークン。

### 関連問題

au-016, au-049

## 8. データ形式の比較：JSON・XML・YAML

### 8.1 データ形式（エンコード方式）とは

API やツールでデータをやり取りするには、「データをどういう文字の並びで表すか」を決める必要があります。これを **データ形式（データのエンコード方式）** といいます。主なものは **JSON・XML・YAML** です。

**同じデータでも JSON・XML・YAML のどれでも表せます。** 形式が違っても、表している中身（どの項目にどの値が入るか）は同じです。

#### 同じインターフェース情報を3形式で表す

**JSON**（`{ }` と `[ ]` で階層を表す。REST API で主流）

```json
{
  "interface": {
    "name": "GigabitEthernet0/1",
    "enabled": true,
    "vlans": [10, 20]
  }
}
```

**XML**（開始タグと終了タグでデータを囲む。NETCONF で使用）

```xml
<interface>
  <name>GigabitEthernet0/1</name>
  <enabled>true</enabled>
  <vlans>10</vlans>
  <vlans>20</vlans>
</interface>
```

**YAML**（インデントで階層を表す。Ansible のプレイブックで使用）

```yaml
interface:
  name: GigabitEthernet0/1
  enabled: true
  vlans:
    - 10
    - 20
```

### 8.2 比較表

| 項目 | JSON | XML | YAML |
| --- | --- | --- | --- |
| 階層の表し方 | `{ }`（オブジェクト）と `[ ]`（配列） | `<タグ>...</タグ>` の入れ子 | **インデント（字下げ）の深さ** |
| インデントの意味 | 見やすさのためだけ。**文法上の意味はない** | 見やすさのためだけ | **文法上の意味がある**（ずれると意味が変わる／エラー） |
| 主な用途 | **REST API**（最も一般的）、RESTCONF | **NETCONF**、RESTCONF | **Ansible** のプレイブック、設定ファイル |
| 特徴 | 人にも読みやすく、プログラムでも扱いやすい | 冗長だが厳密 | 括弧・クォートが少なく人が読み書きしやすい |
| HTTP の Content-Type | `application/json` | `application/xml` | （API ではあまり使わない） |

### 8.3 YAML の基本

```yaml
---                      # 文書の開始（省略可）
- name: VLANを作成        # 「- 」はリスト（配列）の要素
  hosts: switches        # 「キー: 値」で辞書（マッピング）
  gather_facts: false
  tasks:
    - name: VLAN 10
      cisco.ios.ios_vlans:
        config:
          - vlan_id: 10
            name: Sales
```

- **インデントの深さで階層が決まる**（タブではなく **スペース** を使う）。スペースの数がずれると意味が変わったりエラーになったりします。
- `-` はリストの要素、`キー: 値` は辞書。
- `#` 以降はコメント（JSON にはコメントがない）。

### 8.4 XML の基本

```xml
<?xml version="1.0" encoding="UTF-8"?>
<interface>                          <!-- 開始タグ -->
  <name>GigabitEthernet0/1</name>    <!-- 要素：<タグ>値</タグ> -->
  <enabled>true</enabled>
</interface>                         <!-- 終了タグ（/ が付く） -->
```

- 開始タグ `<name>` と終了タグ `</name>` で値を囲む。
- 入れ子で階層を表す。

### 8.5 データ形式と間違えやすいもの

| 用語 | 正体 |
| --- | --- |
| **MIB** | SNMP で管理する情報の定義（データベース）。REST API のデータ形式ではない |
| **Syslog** | ログメッセージを送るためのプロトコル。データ形式ではない |
| **CSV** | 値をカンマで区切って並べる表形式。**階層構造は表せない** |
| **HCL** | Terraform で使われる設定言語（11章） |
| **YANG** | データの「構造を定義する」言語（データモデル）。データ形式そのものではない（10章） |

### ひっかけポイント・よくある誤解

- REST API でよく使うデータ形式は **JSON と XML**。MIB（SNMP の定義）や Syslog（ログのプロトコル）は違う（au-017）。
- 「インデントで階層を表す・Ansible」＝ **YAML**。JSON のインデントには文法上の意味はない（au-035）。
- 「開始タグと終了タグで囲む」＝ **XML**。CSV は階層を表せない（au-036）。
- HCL は Terraform の言語（au-035）。

### 試験のポイント

- **JSON：`{}` `[]`、REST API の主流** ／ **XML：タグ、NETCONF** ／ **YAML：インデント、Ansible**。
- 同じデータはどの形式でも表現可能。中身は同じ。

### 関連問題

au-017, au-035, au-036

## 9. JSONの文法とデータ型を読み解く

CCNA では「JSON を読んで値やデータ型を答える」「正しい JSON を選ぶ」問題がよく出ます。ここでは JSON を確実に読めるようにします。

### 9.1 JSON の基本ルール

**JSON（JavaScript Object Notation）** の文法は次のルールだけで成り立っています。

| ルール | 内容 |
| --- | --- |
| オブジェクト | `{ }` で囲み、中身は **「キー: 値」の組** |
| 配列 | `[ ]` で囲み、中身は **値の並び**（順番に意味がある） |
| キーと値の区切り | **`:`（コロン）**。`=` ではない |
| 要素どうしの区切り | **`,`（カンマ）** |
| キー | **必ずダブルクォート `"` で囲む** |
| 文字列の値 | **必ずダブルクォート `"` で囲む**。**シングルクォート `'` は使えない** |
| 数値・true/false・null | **クォートで囲まない** |
| 最上位 | オブジェクトでも配列でもよい（例：`[10, 20, 30]` も正しい JSON） |
| 空 | 空のオブジェクト `{}`、空の配列 `[]` も正しい |

### 9.2 JSON の6つのデータ型

| データ型 | 例 | 見分け方 |
| --- | --- | --- |
| **文字列**（string） | `"Sales"`、`"10.1.1.1"`、`"true"` | **ダブルクォートで囲まれている** |
| **数値**（number） | `10`、`3.14`、`-1` | クォートなしの数字 |
| **ブール値（真偽値）**（boolean） | `true`、`false` | クォートなし・**小文字** |
| **null** | `null` | クォートなし・小文字。「値が存在しない（空である）」 |
| **オブジェクト**（object） | `{"hostname": "R1"}` | `{ }` |
| **配列**（array） | `["Gi0/1", "Gi0/2"]` | `[ ]` |

**クォートの有無で、文字列かそれ以外かが決まる** のが最重要ポイントです。

```json
{
  "vlan": 10,            ← 数値
  "vlan_str": "10",      ← 文字列（クォートあり）
  "name": "Sales",       ← 文字列
  "enabled": true,       ← ブール値
  "enabled_str": "true", ← 文字列（クォートあり）
  "ip": "10.1.1.1",      ← 文字列（IPアドレスは数値ではない）
  "description": null,   ← null（値なし）
  "comment": "",         ← 空文字列（「空の文字列という値」がある）
  "count": 0,            ← 数値のゼロ（「0という値」がある）
  "ports": [],           ← 空の配列
  "device": {}           ← 空のオブジェクト
}
```

> 注意：上の `←` の注釈は説明用で、JSON にはコメントを書けません。

#### null・""・0・None の違い

| 書き方 | 意味 |
| --- | --- |
| `null` | **値が存在しない**。JSON の正しい書き方 |
| `""` | 長さ0の文字列。「値がない」のではなく「空の文字列という値がある」 |
| `0` | 数値のゼロという値がある |
| `None` | **Python** のキーワード。JSON では使えない（JSON では `null`） |

#### JSON と Python の対応

Python で JSON を読み込む（`json.loads()` や `requests` の `r.json()`）と次のように変換されます。

| JSON | Python |
| --- | --- |
| オブジェクト `{}` | 辞書 `dict` |
| 配列 `[]` | リスト `list` |
| 文字列 `"..."` | `str` |
| 数値 | `int` / `float` |
| `true` / `false` | `True` / `False` |
| `null` | `None` |

Python ではシングルクォートで文字列を書けますが、**JSON ではダブルクォートのみ** です。`{'hostname': 'R1'}` は Python の辞書としては正しくても JSON としては誤りです。

### 9.3 正しい JSON・誤った JSON

| 例 | 判定 | 理由 |
| --- | --- | --- |
| `{"hostname": "R1", "vlan": 10}` | 正しい | キーと文字列はダブルクォート、数値はクォートなし |
| `{hostname: R1, vlan: 10}` | 誤り | キーも文字列の値もクォートで囲まれていない |
| `{'hostname': 'R1', 'vlan': 10}` | 誤り | **シングルクォートは使えない**（Python や JavaScript では使える） |
| `["hostname" = "R1", "vlan" = 10]` | 誤り | 区切りは `=` ではなく `:`。キーと値の組は `[ ]` ではなく `{ }` |
| `{"vlan": 10 "name": "Sales"}` | 誤り | **要素の間の `,` が抜けている** |
| `{"vlan": 10, "name": "Sales",}` | 誤り | **最後の要素の後ろに余分な `,`**（末尾カンマ） |
| `{"vlan": 10, "name": "Sales"}` | 正しい | `,` で区切られている |
| `{"ports": []}` | 正しい | 値が空の配列 |
| `[10, 20, 30]` | 正しい | 最上位が配列でもよい |

**JSON でよくある誤り**：
1. 要素の間の `,` の抜け
2. 最後の要素の後ろの余分な `,`
3. シングルクォートの使用
4. キーをクォートで囲み忘れる

文法誤りのある JSON を API に送ると **400 Bad Request** が返されます（6章）。

### 9.4 入れ子（ネスト）構造の読み方

JSON は **`{ }` と `[ ]` の対応を見て階層を読みます**。インデントして書き直すと読みやすくなります。

#### 例1：配列

```json
{"hostname": "SW1", "interfaces": ["Gi0/1", "Gi0/2", "Gi0/3"]}
```

- `interfaces` の値は `[ ]` で囲まれているので **配列**。
- 配列の各要素（`"Gi0/1"` など）は文字列だが、**`interfaces` の値全体は配列**。
- 配列は同じ種類のデータを複数並べるときに使い、要素は `,` で区切り、**順番に意味がある**。

#### 例2：オブジェクトの中のオブジェクト

```json
{"device": {"hostname": "R1", "ip": "10.1.1.1"}, "site": "Tokyo"}
```

整形すると：

```json
{
  "device": {                 ← device の値はオブジェクト
    "hostname": "R1",         ← device の内側のキー
    "ip": "10.1.1.1"          ← クォートあり → 文字列
  },
  "site": "Tokyo"
}
```

```
 最上位オブジェクト
 ├── device : オブジェクト
 │     ├── hostname : "R1"
 │     └── ip       : "10.1.1.1"（文字列）
 └── site   : "Tokyo"
```

- **最上位のキーは `device` と `site` の2つ**。`hostname` は `device` の内側のキー。
- プログラムでは `data["device"]["hostname"]` のようにたどって `"R1"` を取り出します。

#### 例3：配列の中のオブジェクト（API 応答で頻出）

```json
{"devices": [{"name": "R1"}, {"name": "R2"}, {"name": "SW1"}]}
```

```
 data
 └── "devices" : 配列
        [0] → {"name": "R1"}
        [1] → {"name": "R2"}
        [2] → {"name": "SW1"}
```

- `data["devices"]` → 配列
- `data["devices"][2]` → 配列の **2番目（0から数えるので3つ目）** の要素 `{"name": "SW1"}`
- `data["devices"][2]["name"]` → **`"SW1"`**

**配列の番号（インデックス）は 0 から数えます。** 1 から数えると `"R2"` と誤答します。要素は3つ（0〜2番目）あるので `[2]` は存在し、エラーにはなりません（`[3]` ならエラー）。

Python での例：

```python
data = {"devices": [{"name": "R1"}, {"name": "R2"}, {"name": "SW1"}]}
print(data["devices"][2]["name"])   # SW1
print(len(data["devices"]))         # 3
for d in data["devices"]:
    print(d["name"])                # R1, R2, SW1
```

### ひっかけポイント・よくある誤解

- シングルクォート、クォートなしのキー、`=` 区切り、`[ ]` でキーと値の組 → いずれも誤り（au-002）。
- `true`（クォートなし）は **ブール値**。`"true"` なら文字列（au-018）。`10` が数値（au-018）。
- `["Gi0/1", ...]` の値全体は **配列**。要素が文字列だからといって「文字列」と答えない（au-019）。
- `{ }` はオブジェクト、`[ ]` は配列（au-019, au-020）。
- 入れ子の内側のキー（hostname）を最上位と誤認しない（au-020）。
- `"10.1.1.1"` はクォートがあるので **文字列**。IP アドレスだから数値、ではない（au-020）。
- 配列は **0 から数える**。`[2]` は3つ目（au-032）。
- 値がないのは `null`。`""` は空文字列、`0` は数値、`None` は Python（au-033）。
- カンマ抜けは文法エラー。空配列や最上位の配列は正しい（au-034）。

### 試験のポイント

- JSON の6つの型：**文字列・数値・ブール値・null・オブジェクト・配列**。
- **キーと文字列はダブルクォート**、数値・true/false・null はクォートなし。
- `:` で区切り、`,` で並べる。末尾カンマ不可。
- 入れ子は `data["a"]["b"]`、配列は `[0]` から。

### 関連問題

au-002, au-018, au-019, au-020, au-032, au-033, au-034

## 10. モデル駆動のプログラマビリティ：YANG・NETCONF・RESTCONF

### 10.1 なぜ「モデル駆動」が必要か

従来、プログラムで機器の情報を取るには `show` コマンドの出力（人間向けのテキスト）を解析（スクレイピング）していました。

```
R1# show ip interface brief
Interface              IP-Address      OK? Method Status                Protocol
GigabitEthernet0/0     10.1.1.1        YES manual up                    up
```

- 出力形式が **機種・OS バージョンごとにばらばら**
- バージョンアップで列がずれるとスクリプトが壊れる

そこで、**「どんなデータがあり、どんな型か」をあらかじめ定義（モデル化）し、その構造どおりにデータをやり取りする** 方式が生まれました。これを **モデル駆動のプログラマビリティ** と呼びます。

```
 ┌────────────────────────────────────────────┐
 │ YANG（データモデル＝設計図）                   │  どんな項目・型があるか
 └────────────────────────────────────────────┘
          │ この構造に従ったデータを
          ▼
 ┌──────────────────────┐  ┌──────────────────────┐
 │ エンコード：XML         │  │ エンコード：JSON / XML  │  実際の書き方
 └──────────────────────┘  └──────────────────────┘
          │                          │
 ┌──────────────────────┐  ┌──────────────────────┐
 │ プロトコル：NETCONF     │  │ プロトコル：RESTCONF    │  やり取りの方法
 │ トランスポート：SSH 830 │  │ トランスポート：HTTPS   │
 └──────────────────────┘  └──────────────────────┘
```

### 10.2 YANG（データモデリング言語）

- **YANG（Yet Another Next Generation）** は **データの構造を定義する言語（データモデリング言語）** です。
- インターフェースや VLAN などの設定項目に「どんな項目があり、それぞれどの型の値を取るか」を定義します。
- YANG は「どんなデータがあるか」という **設計図**。それを実際にやり取りするときの **書き方が XML や JSON** です。

YANG の例（簡略化）：

```yang
container interfaces {
  list interface {
    key "name";
    leaf name    { type string; }
    leaf enabled { type boolean; default true; }
    leaf mtu     { type uint16; }
  }
}
```

この構造に従ったデータを JSON で表すと（RESTCONF の場合）：

```json
{
  "ietf-interfaces:interfaces": {
    "interface": [
      {"name": "GigabitEthernet1", "enabled": true}
    ]
  }
}
```

比較：SNMP では **MIB** で管理項目を定義しました。YANG は NETCONF / RESTCONF における「MIB に相当するもの」とイメージすると理解しやすいです。

| 役割 | SNMP の世界 | モデル駆動の世界 |
| --- | --- | --- |
| データ構造の定義 | MIB | **YANG** |
| プロトコル | SNMP（Get/Set） | **NETCONF / RESTCONF** |

### 10.3 NETCONF

| 項目 | 内容 |
| --- | --- |
| トランスポート | **SSH（TCP 830）** |
| データ形式 | **XML** |
| 扱うデータ | YANG で定義されたデータ |
| 操作 | **RPC（リモートプロシージャコール）** の形で要求：`get-config`（設定取得）、`edit-config`（設定変更）、`get`（状態取得）など |
| Cisco IOS XE での有効化 | `netconf-yang` コマンド |
| SDN での位置 | **サウスバウンド**（コントローラ → 機器） |

```
R1(config)# netconf-yang
```

NETCONF の RPC の例（設定取得）：

```xml
<rpc message-id="101" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get-config>
    <source><running/></source>
  </get-config>
</rpc>
```

NETCONF は **SSH で暗号化された接続の上** で XML のメッセージをやり取りします。HTTPS（TCP 443）、SNMP（UDP 161）、Telnet（TCP 23）は NETCONF のトランスポートではありません。

### 10.4 RESTCONF

| 項目 | 内容 |
| --- | --- |
| トランスポート | **HTTPS**（TCP 443） |
| データ形式 | **JSON または XML** |
| 扱うデータ | YANG で定義されたデータ |
| 操作 | **REST API と同じ HTTP メソッド**（GET、POST、PUT、PATCH、DELETE） |
| 利点 | Web API の知識で扱えるので、スクリプトから使いやすい |

RESTCONF のリクエスト例：

```http
GET https://r1.example.com/restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet1
Accept: application/yang-data+json
Authorization: Basic YWRtaW46Q2lzY28xMjM=
```

Cisco IOS XE では `restconf` コマンド（と HTTPS サーバ `ip http secure-server`）で有効にします。

### 10.5 NETCONF・RESTCONF・SNMP・OpenFlow の比較

| プロトコル | トランスポート / ポート | データ形式 | データ定義 | 主な用途 |
| --- | --- | --- | --- | --- |
| **NETCONF** | **SSH / TCP 830** | **XML** | YANG | 設定の取得・変更（RPC） |
| **RESTCONF** | **HTTPS / TCP 443** | **JSON / XML** | YANG | 設定の取得・変更（HTTP メソッド） |
| SNMP | UDP 161（トラップは 162） | BER | **MIB** | 監視（Get/Set） |
| OpenFlow | TCP（6653） | バイナリ | ― | フローテーブルの直接制御 |

### ひっかけポイント・よくある誤解

- データの構造を定義するのは **YANG**。JSON はエンコード方式であって構造の定義そのものではない。Python はプログラミング言語、SNMP は監視プロトコル（定義は MIB）（au-037）。
- 「HTTPS で、GET/PUT などで YANG データを操作」＝ **RESTCONF**。NETCONF は SSH + XML、SNMP は MIB を Get/Set、OpenFlow はフローテーブル制御（au-038）。
- NETCONF ＝ **SSH（TCP 830）**。HTTPS 443 は RESTCONF、UDP 161 は SNMP、Telnet 23 は使わない（au-039）。
- NETCONF はサウスバウンド。データは XML、SSH で通信（au-009）。

### 試験のポイント

- **YANG ＝ データモデル（設計図）**、XML/JSON ＝ 書き方、NETCONF/RESTCONF ＝ 運び方。
- **NETCONF：SSH・TCP 830・XML・RPC（get-config / edit-config）・`netconf-yang`**。
- **RESTCONF：HTTPS・JSON/XML・HTTP メソッド**。

au-009, au-037, au-038, au-039

## 11. 構成管理ツール：Ansible・Terraform・Puppet・Chef

### 11.1 構成管理ツールとは

**構成管理ツール** は、機器やサーバの「あるべき設定」をコード（ファイル）として記述し、そのとおりに自動で設定・維持するツールです。CCNA で問われる代表は **Ansible・Terraform**、比較対象として **Puppet・Chef** です。

### 11.2 プッシュ型とプル型

```
 プッシュ型（Ansible）                     プル型（Puppet / Chef）
                                         
  管理サーバ ──SSHで接続して設定を送る──>   管理サーバ <──定期的に設定を取りに行く── エージェント
       │                    機器             (Puppet Master /          (各機器に
       ├──────────────────> 機器              Chef Server)              インストール)
       └──────────────────> 機器
  ・管理サーバが主体                        ・機器側のエージェントが主体
  ・エージェント不要                        ・エージェントが必要
```

| 方式 | 動作 | 代表例 |
| --- | --- | --- |
| **プッシュ型** | **管理サーバが主体** となって機器に接続し、設定を送り込む | **Ansible** |
| **プル型** | 機器に入れた **エージェント** が、定期的に管理サーバへ設定を **取りに行く** | **Puppet、Chef** |

ネットワーク機器には追加のソフト（エージェント）を入れられないことが多いため、**エージェント不要のプッシュ型（Ansible）はネットワークの自動化と相性がよい** のです。
（「ブロードキャスト型」「ピアツーピア型」は構成管理ツールの方式を表す用語ではありません。）

### 11.3 ツール比較

| 項目 | **Ansible** | **Terraform** | Puppet | Chef |
| --- | --- | --- | --- | --- |
| 方式 | **プッシュ型** | プッシュ型（API 経由） | プル型 | プル型 |
| エージェント | **不要**（SSH / API で接続） | 不要（プロバイダが API を呼ぶ） | 必要 | 必要 |
| 記述言語 | **YAML**（プレイブック） | **HCL** | Puppet 独自 DSL（マニフェスト） | **Ruby**（レシピ／クックブック） |
| 記述スタイル | 主に **手順的**（タスクを順に実行） | **宣言的**（あるべき状態を書く） | 宣言的 | 手順的 |
| 状態の記録 | なし | **ステートファイル** | ― | ― |
| よく使う用途 | **機器の設定変更** | **リソースの構築**（クラウド、ネットワーク） | サーバ構成管理 | サーバ構成管理 |

> 補足：Ansible のモジュール自体は冪等に作られており「あるべき状態」を書く側面もありますが、プレイブックはタスクを上から順に実行する手順的な記述です。試験では「Ansible＝YAML のプレイブックで処理の手順を記述」「Terraform＝HCL で宣言的」と区別します。

### 11.4 Ansible の構成要素

| 要素 | 内容 |
| --- | --- |
| **インベントリ** | 管理対象の機器の **ホスト名・IPアドレス・グループ**（routers、switches 等）を書く一覧。「**どの機器に**」 |
| **プレイブック** | 実行する処理の内容と手順を **YAML** で書くファイル。「**何をするか**」 |
| モジュール | 個々の処理の部品（例：`cisco.ios.ios_vlans`、`ios_config`） |
| 変数・テンプレート | 機器ごとに違う値（ホスト名、IP など）の扱い。テンプレートは Jinja2 |

インベントリの例（INI 形式）：

```ini
[routers]
R1 ansible_host=10.1.1.1
R2 ansible_host=10.1.1.2

[switches]
SW1 ansible_host=10.1.1.11
SW2 ansible_host=10.1.1.12

[all:vars]
ansible_network_os=cisco.ios.ios
ansible_connection=ansible.netcommon.network_cli
```

プレイブックの例（YAML）：

```yaml
---
- name: VLANを作成
  hosts: switches            # インベントリのグループ名 → SW1, SW2 の全台に実行
  gather_facts: false
  tasks:
    - name: VLAN 10 Sales を作る
      cisco.ios.ios_vlans:
        config:
          - vlan_id: 10
            name: Sales
        state: merged
```

実行：

```
$ ansible-playbook -i inventory.ini vlan.yml
```

プレイブックで **グループ名を指定すると、そのグループのすべての機器に同じ処理を実行** できます。

Ansible の特徴まとめ：
- **エージェント不要**、**SSH** で接続（API 接続も可）
- **YAML** のプレイブック
- **プッシュ型**
- 監視ツールではなく、主に **設定の自動化** ツール（SNMP 監視専用ツールではない）

### 11.5 Terraform

- インフラの「**あるべき状態**」を **HCL（HashiCorp Configuration Language）** で **宣言的** に記述し、その状態になるようにリソースを作成・変更する。
- **宣言的** ＝「どういう手順で作るか」ではなく「**最終的にどうなっていてほしいか**」を書く。
- 現在の状態を **ステートファイル**（terraform.tfstate）に記録し、書かれた状態との **差分だけを適用** する。
- クラウドやネットワークのリソースをコードで構築・管理する **IaC（Infrastructure as Code）** の代表的ツール。

HCL の例：

```hcl
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "web" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
}
```

#### Terraform の基本ワークフロー

```
 terraform init  ──>  terraform plan  ──>  terraform apply   (… terraform destroy)
   準備                変更内容の確認          適用                 全削除
 (プロバイダ取得)     (差分の一覧を表示)
```

| コマンド | 役割 |
| --- | --- |
| `terraform init` | 作業ディレクトリを初期化し、必要な **プロバイダ（プラグイン）** を準備 |
| **`terraform plan`** | 現在の状態と設定ファイルの差分から、**何が作成・変更・削除されるかを表示**（実際には変更しない） |
| `terraform apply` | 変更を **実際に適用** |
| `terraform destroy` | 管理しているリソースを **すべて削除** |

`plan` で **意図しない削除などがないかを確認してから `apply`** することで、作業ミスによる事故を防げます。

```
$ terraform plan
  + resource "aws_subnet" "web" { cidr_block = "10.0.1.0/24" ... }
  - resource "aws_subnet" "old" { ... }      ← 意図しない削除がないか確認！
Plan: 1 to add, 0 to change, 1 to destroy.
```

### 11.6 Ansible と Terraform の使い分け

| | Ansible | Terraform |
| --- | --- | --- |
| 得意 | 既存機器の **設定変更** | リソース（VM、VPC、ネットワーク）の **構築** |
| ファイル | インベントリ ＋ プレイブック（YAML） | 設定ファイル（HCL）＋ ステートファイル |
| スタイル | 手順を記述 | あるべき状態を宣言 |

### ひっかけポイント・よくある誤解

- 「機器ごとにエージェントが必要」は **Puppet / Chef** の特徴。Ansible は **エージェント不要**（au-021）。
- 「Ruby で記述」は **Chef**。Ansible は YAML（au-021）。
- Ansible は監視ツールではない（au-021）。
- 「HCL で宣言的」＝ **Terraform**。Ansible は YAML のプレイブックで手順を記述。Syslog / NTP はプロトコル（au-022）。
- Ansible ＝ **プッシュ型**。プル型は Puppet / Chef。ブロードキャスト型・ピアツーピア型という方式名はない（au-042）。
- 機器の一覧＝**インベントリ**、処理内容＝**プレイブック**、Terraform の状態記録＝**ステートファイル**、running-config は Cisco 機器の動作中の設定（au-043）。
- 変更前の確認＝ **`terraform plan`**。apply は適用、init は準備、destroy は全削除（au-044）。

### 試験のポイント

- **Ansible：エージェントレス・SSH・YAML プレイブック・プッシュ型・インベントリ**。
- **Puppet / Chef：エージェント型・プル型。Chef は Ruby**。
- **Terraform：HCL・宣言的・ステートファイル・init → plan → apply**。

### 関連問題

au-021, au-022, au-042, au-043, au-044

## 12. 構成管理の考え方：構成ドリフト・冪等性・IaCとバージョン管理

### 12.1 構成ドリフト

**構成ドリフト（configuration drift）** とは、**手作業の変更が積み重なり、機器の設定が標準の設定から少しずつずれていく問題** です。

```
 標準設定（ゴールデンコンフィグ）
   SW1: ntp server 10.0.0.1 / logging 10.0.0.5 / snmp ... 
   SW2: 同上
   SW3: 同上
        │ 障害対応で SW2 に一時的な設定を追加 → 戻し忘れ
        │ SW3 は担当者が独自に ACL を修正
        ▼
   SW1: 標準どおり
   SW2: 標準 + debug設定 + 一時ACL        ← ドリフト
   SW3: 標準 - logging + 独自ACL          ← ドリフト
   → 同じ役割の機器なのに設定がばらばら → トラブルの原因
```

**対策**：構成管理ツールで「あるべき設定」をコードとして定義しておけば、
- 変更履歴が残る
- 標準とのずれを **機械的に検出** できる
- ツールを再実行して **元に戻せる**

構成ドリフトは「**設定内容のずれ**」のことであり、次とは無関係です。

| 似て非なるもの | 実際の話題 |
| --- | --- |
| STP の再計算でルートブリッジが移る | STP の動作 |
| NTP の同期が外れて時刻がずれる | 時刻のずれ（NTP で防ぐ） |
| 無線端末が AP 間を移動する | 無線 LAN のローミング |

### 12.2 冪等性（べきとうせい）

**冪等性（idempotency）** とは、**同じ処理を何度実行しても、結果が同じ状態になる性質** です。

```
 処理：「VLAN 10 (Sales) が存在する状態にする」

 1回目: VLAN 10 なし → 作成する        → 結果：VLAN 10 あり   (changed)
 2回目: VLAN 10 あり → 何もしない      → 結果：VLAN 10 あり   (ok)
 3回目: VLAN 10 あり → 何もしない      → 結果：VLAN 10 あり   (ok)
         ↑ 何度実行しても同じ状態 ＝ 冪等
```

冪等でない例：実行するたびに設定が1行ずつ追加されていく（実行のたびに結果が変わる）。

**なぜ重要か**：
- すでに望ましい状態なら何も変更しないので、**安心して繰り返し実行できる**。
- 一部の機器で処理が失敗しても、**同じ処理をもう一度すべての機器に実行するだけで**、全体を望ましい状態にそろえられる。
- 構成ドリフトの修正にも使える（定期的に再実行すれば標準に戻る）。

冪等性は「処理時間（1秒以内に終わる）」や「並列実行（全機器に同時に実行）」とは関係ありません。

### 12.3 IaC（Infrastructure as Code）とバージョン管理

**IaC（Infrastructure as Code）** は、**インフラの設定をコードとして管理する考え方** です。ネットワークの設定やプレイブックを **Git などのバージョン管理システム** で管理すると、ソフトウェア開発と同じ方法でネットワークの変更を管理できます。

```
 担当者A: vlan.yml を編集 ─> git commit ─> プルリクエスト
                                              │ レビュー（担当者Bが差分を確認）
                                              ▼
                                         テスト環境で事前確認
                                              │
                                              ▼
                                       main にマージ → Ansible で本番適用
                                              │ 問題発生！
                                              ▼
                                       git revert で以前の版に戻して再適用
```

Git で管理する利点：

| 利点 | 内容 |
| --- | --- |
| 変更履歴 | **誰がいつ何を変更したか** が残る |
| 差分確認 | 変更前後の差分を確認できる |
| レビュー | 複数人で変更内容をレビューできる |
| テスト | テスト環境で事前に確認できる |
| 切り戻し | 問題が起きたとき **以前の状態（バージョン）へ戻しやすい** |

注意点：
- 機器の **転送性能は変わらない**（管理方法の話）。
- **セキュリティ対策は不要にならない**。むしろ **コードの中にパスワードなどを書かない** よう注意が必要（Ansible Vault や環境変数などで秘密情報を分離）。
- 設定ミスは減らせるが **絶対に起きなくなるわけではない**。レビューやテストと組み合わせる。

### ひっかけポイント・よくある誤解

- 構成ドリフト＝ **設定内容のずれ**。STP のルートブリッジ移動、NTP の時刻ずれ、無線ローミングではない（au-023）。
- 冪等性＝ **何度実行しても同じ結果**。1行ずつ追加される（冪等でない）、1秒以内、同時実行とは無関係（au-045）。
- Git で管理しても性能向上・セキュリティ不要・ミスゼロにはならない（au-046）。

### 試験のポイント

- 構成ドリフト ＝ 手作業変更の蓄積による標準からのずれ。構成管理ツールで検出・修正。
- 冪等性 ＝ 何度実行しても同じ状態。望ましい状態なら何もしない。
- IaC ＋ Git ＝ 履歴・レビュー・テスト・切り戻し。秘密情報をコードに書かない。

### 関連問題

au-023, au-045, au-046

## 13. AIと機械学習（予測AI・生成AI）

CCNA 200-301 v1.1 では、ネットワーク運用における **AI（生成AI・予測AI）と機械学習** の役割が出題範囲に加わりました。

### 13.1 ルールベースと機械学習

| 方式 | 判断の仕方 | 例 |
| --- | --- | --- |
| **ルールベース** | 人が書いた **if 文などのルール** だけに従う。データから学習しない | 「CPU 使用率が 90% を超えたら通知」（しきい値監視） |
| **機械学習（ML）** | ルールを一つ一つプログラムするのではなく、**データからパターンを学習** して判断や予測を行う | 普段の通信パターンを学習し、いつもと違う通信を検知 |

機械学習は、大量のデータから **人が書ききれない規則性** を見つけ出せるのが強みです。

機械学習ではないもの：
- 設定ファイルを自動でバックアップする仕組み → 構成管理ツールやスクリプトでできること
- ルーティングプロトコルが最短経路を計算する仕組み → OSPF（SPF/ダイクストラ）などは **決められたアルゴリズム** で計算しており、学習はしない
- ロンゲストマッチ → ルータがルートを選ぶときの規則

### 13.2 教師あり学習と教師なし学習

| 方式 | 学習データ | できること | ネットワークでの例 |
| --- | --- | --- | --- |
| **教師あり学習** | **正解（ラベル）付き** のデータ（例：「この通信は攻撃」「これは正常」） | 新しいデータの **分類・予測** | 正解付きデータが十分ある場合に、通信の種類（アプリ）を分類 |
| **教師なし学習** | **正解なし** のデータ | データの特徴から **グループ（クラスタ）や外れ値** を見つける | 普段の通信を学習し、そこから外れた **異常な通信を検知** |

```
 教師なし学習による異常検知のイメージ

   通信量
    ▲            ×  ← 外れ値（異常の可能性）
    │   ●●●●
    │  ●●●●●●       ← 普段のパターン（クラスタ）
    │   ●●●●
    └──────────────▶ 時間帯
```

ネットワークでは **「異常な通信」の正解データを十分に集めるのが難しい** ため、**教師なし学習** で普段との違いを見つける用途がよく使われます。

### 13.3 予測AI と 生成AI

ネットワーク運用での AI の主な使い方は2種類で、どちらも **機械学習（ML）が土台** です。

| 種類 | 何をするか | ネットワーク運用での例 |
| --- | --- | --- |
| **予測AI（predictive AI）** | 過去のデータのパターンから **将来起きそうなことを予測**、異常を検知 | 過去の通信量やログを学習し、**リンクの輻輳や機器の故障が起きる前に兆候を通知**、キャパシティ計画 |
| **生成AI（generative AI）** | 文章や設定ファイルなど **新しいコンテンツを作り出す** | 自然な文章での質問への回答、**設定やスクリプトの案の作成**、トラブルシューティングのヒント、ログの要約 |

予測AI と混同しやすいもの：
- **ルールベースのしきい値監視** → 人が決めたルールで判定。学習しない。
- **Syslog によるログ送信** → ログを集める仕組みで、予測は行わない。ただし **予測AI の学習データの元** にはなる。

### 13.4 生成AI を使うときの注意点

```
 生成AI ──「R1 に OSPF を設定するコンフィグを作って」──> 出力（案）
                                                        │
               ┌────────────────────────────────────────┘
               ▼
   ① 人が内容を確認（公式ドキュメントと照合）
   ② 検証環境（ラボ）でテスト
   ③ 変更内容をレビュー
   ④ 本番に適用
```

| 注意点 | 理由 |
| --- | --- |
| **出力を人が確認・検証してから適用する** | 生成AI は学習データから「それらしい」文章を作る仕組みで、**内容が事実として正しいとは限らない**。1つの誤ったコマンドが大きな障害につながる |
| **ハルシネーション** に注意 | 存在しないコマンドや誤った仕様を、**もっともらしく自信のある文章で出力** してしまう現象（「幻覚」の意味） |
| **機密情報を入力しない** | パスワードや社内の IP アドレス設計などを入力すると、**外部に保存・学習される場合がある**。組織のルールに従う |
| **ネットワークの知識は引き続き必要** | 出力が正しいか判断するためにも知識が要る |

AI の出力は **「案」として扱い、検証してから使う** のが原則です。

ハルシネーションと紛らわしい用語：

| 用語 | 意味 |
| --- | --- |
| 構成ドリフト | 機器の設定が標準から少しずつずれていく問題 |
| ブロードキャストストーム | L2 のループなどで、ブロードキャストが増え続ける現象 |
| フラッディング | スイッチが宛先不明のフレームを全ポートへ送る動作 |

### ひっかけポイント・よくある誤解

- 故障や輻輳の **予兆を知らせる** ＝ **予測AI**。生成AI はコンテンツ生成、しきい値監視は学習しない、Syslog は収集のみ（au-024）。
- 「AI が作った設定は正確なのでそのまま本番に適用」「機密情報を自由に入力」「ネットワーク知識が不要になる」はすべて誤り（au-025）。
- 「if 文などのルールだけに従う」は **ルールベース**。設定バックアップや最短経路計算は ML ではない（au-026）。
- 正解なしで異常やまとまりを見つける ＝ **教師なし学習**。正解付きで分類 ＝ 教師あり学習（au-047）。
- 存在しないコマンドをもっともらしく出力 ＝ **ハルシネーション**（au-048）。

### 試験のポイント

- ML ＝ データからパターンを学習。**教師あり（正解付き・分類）／教師なし（正解なし・異常検知・グループ化）**。
- **予測AI ＝ 予測・異常検知**、**生成AI ＝ 文章・設定案の生成**。
- 生成AI：**ハルシネーション** に注意、人が検証、機密情報を入力しない。
