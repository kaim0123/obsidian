## 詳しい要約

**テーマ：バックエンドエンジニアがインフラ力を身につけるべき理由・難しさ・学び方・5 段階ロードマップ**

7 年のエンジニア経験を持つ SRE の投稿者が、インフラ（ここでは AWS・Google Cloud などクラウド上の、アプリを安定稼働させる土台）の重要性、バックエンドとインフラを掛け合わせる価値、インフラの実務経験が積みにくい構造的な理由、学習の 5 つのポイント、そして EC2 → ECS → Lambda → Google Cloud → EKS（Kubernetes）の習得ロードマップをまとめて語る。結論は、インフラは「運ガチャ」に頼らず正しいやり方で再現性高く伸ばせる、ということ。

---

### なぜ今インフラが重要か

- 生成 AI でアプリの母数が膨大になった。ローカルで動くものは誰でも作れるが、デプロイして公開する部分は難しく、インフラの知識が要る
- リリース後もセキュリティ、クラウドコスト管理、リクエスト増に応じた増強、障害時の復旧など、やることは膨大に増える
- AI でバックエンド処理がリッチになり、**非機能要件**の水準も上がっている。それを AI だけで丸ごと解決する未来は、SRE として働く投稿者にはまだ見えない

### バックエンドエンジニアこそインフラをやるべき理由

- テックリードや CTO はほぼ例外なくバックエンドもインフラも強い。テックリードまで上がるにはインフラを避けて通れない
- 「技術の難易度（横軸）× 領域（縦軸：インフラ／バックエンド／フロント）」の図で、メンバークラスとテックリードの差分は **非機能要件への設計力** と **インシデント対応力**。どちらもバックエンドとインフラにまたがらないと発揮できない

**掛け算①：非機能要件への設計力**

- 例：レスポンス 50ms 以下（99%）の API、エンタープライズ向けの論理ネットワーク分離、100 万件のメールを 1 時間以内に一斉配信、1 万人同時接続のストリーミング、10GB の 3D データを 30 分以内に低コストで変換、など
- API 性能改善の手札：バックエンド側（クエリチューニング、N+1 の解消、Redis などのアプリケーションキャッシュ）＋インフラ側（DB のリードレプリカ、Web サーバーのオートスケール）
- 設計ドキュメントも両方の観点が必要：API 仕様書・DB スキーマ・シーケンス図・負荷試験＋インフラ構成図・監視（例：SQS のメッセージ数やデッドレターキューを監視して Slack 通知）。非同期処理（SQS・Kafka・Pub/Sub）や RDBMS 以外の DB の選定力も要る
- 生成 AI 時代に加速：LLM のストリーミングには長時間接続を維持する設計、ベクトル検索の本番運用には大規模データの低レイテンシ検索基盤、AI エージェントの並列実行には非同期処理とキューイング基盤が必要
- 非機能要件は大口顧客の導入可否を左右し、満たせるかは **0 か 100** の世界。高い水準で満たせるエンジニアは市場価値が高く、AI に置き換えられにくい

**掛け算②：インシデント対応**

- 500 エラー調査：バックエンド側（アプリケーションログ→ソースコード、DB コネクション数、スロークエリ）＋インフラ側（ネットワークの異常、CPU・メモリ・ディスク）
- 両方分かれば多角的に仮説を立てられ、「そこはインフラ側なので分かりません」といった押し付け合いにならない

### インフラができるメリット 4 つ

1. **技術のポータビリティが高い**：A 社で苦労して EC2 → ECS 移行をした経験で、B 社の ECS 新規構築は一瞬で終わった。インフラはドメイン知識から遠く、OSI 参照モデルの L1〜L6 など標準化された技術を扱う割合が高い（バックエンドは主に L7 で、ドメイン知識と密結合）。業界が変わっても構成は EC2・ECS・Kubernetes・Cloud Run など似たり寄ったり
2. **技術が陳腐化しにくい**：根底にあるのはネットワーク・DB・SQL・Linux・CS など息の長い技術。フロントエンド（Next.js・React）や生成 AI のように半年で常識が変わる領域と違い、後から来た人に逆転されにくい
3. **実績を語りやすい**：「AWS コストを月 25 万円削減」「デプロイを 25 分 → 5 分」「API を 2 秒 → 20ms」のように数字で語れ、他社の人にも大変さがすぐ伝わる。バックエンドの実績は社外秘も多く「〇〇 API を開発」と抽象化するしかない
4. **単価が高い**：ミスの影響範囲が大きく誰もやりたがらない、学習コストが高く参入障壁が高い、ためできる人が少ない。ハードスキル次第で月単価 100 万円超（高い人で 165 万円）も

### なぜインフラの経験は積みにくいのか（4 つの理由）

1. **プロダクトの心臓だから**：DB や DNS の対応を間違えると大障害。1 分の障害で数十万〜数百万円が飛ぶこともある。フロントの文言修正のような「肩慣らしタスク」がなく、最初の打席に立ちにくい
2. **レバレッジが効くから**：Terraform などの IaC や CI/CD を作れば半永久的に効き、お手本の構成は若手に真似されて広がる。逆に未熟な人が作った初期構成は負債が雪だるま式に増える（本番では「動いているものが正義」なので、緩い設定もそのままコピーされる）。だから経験者に任せたい力学が働く
3. **不可逆だから**：例として、DB をパブリックサブネットに作ると後からプライベートに移すには作り直しが必要。リソース名も ID として使われるため変更には作り直しが要る。アプリ層のように git revert で戻せない
4. **タスクが少ないから**：フロント：バックエンド：インフラのタスク量は体感 5：4：1。詳しい人が 1 人いれば回ってしまい、できる人がタスクを独占する（本人は任せたいが、納期や顧客影響を考えてつい自分でやってしまう）

### インフラ力が上がらないジレンマ

- **経験豊富な人がいる会社**：収益が安定しておりサービスを落とせないので、SRE チームやプラットフォームチームによる分業体制。実績がないと任せてもらえず、打席が回ってこない
- **未経験でも触り放題の会社**（小規模スタートアップ）：お手本もフィードバックもなく我流になり、頭打ち。変な癖がついてむしろ悪化することも
- 我流構成のあるある：1 つの AWS アカウントにステージと本番が混在（S3 バケット内をパスで dev/stg/prod に分けるケースも）、DB や ECS がパブリックサブネットにむき出し、命名規則（prd・prod・production、接頭辞・接尾辞）が揺れまくり、全員に AdministratorAccess、セキュリティグループを使い回して 0.0.0.0/0 でフルオープン、毎月の AWS コストを誰も知らない、インシデントにユーザーの問い合わせで初めて気づく

### インフラ学習で押さえるべき 5 つのポイント

1. **クラウド代をケチらない**：ALB で月 2,000 円、NAT Gateway で 7,000 円といった請求が怖くて手を動かせないことが最大の心理的な壁。ただし闇雲に作ると高額請求も起こるので、詳しい人に頼るのが確実（学習時間外の自動停止や、NAT Gateway の代わりに NAT インスタンスを使って月数百円に抑える工夫など）
2. **ベストプラクティスに沿った綺麗な構成を真似する**：これが最も大事。投稿者はスタートアップで EC2・ECS・API Gateway・Lambda・Step Functions・CloudFront などを触り倒しても一定以上伸びなかったが、メガベンチャーで高レベルな構成を見て霧が晴れた。特に、既存の dev・stg・prod に加えて sandbox 環境を Terraform（Google Cloud）と Kubernetes マニフェストで複製したタスクで力が大きく伸びた。眺めるだけでなく、複製するために既存設定を理解するインプットとアウトプットの往復が効く
3. **最初はコンソールから手動で構築する**：いきなり Terraform・CloudFormation・CDK から入ると GUI でしか得られない手触り感を捨てることになる。おすすめは「コンソールで構築 → `terraform import` でコード化 → 別環境を apply で複製」。例：CloudFront のオリジン設定画面では、重要な項目が上にあり追加設定はトグルで隠れている、関数（CloudFront Functions）はディストリビューションと同階層なので独立して作って紐付ける、オリジンやビヘイビアはディストリビューション内で 1 対 N で作る、といった重要度やリソース同士の関係が直感的に分かる。この感覚で初見の Cloudflare もすぐ使えた
4. **点ではなく線（ストーリー）で構築する**：ハンズオンの「いきなり NAT Gateway を作りましょう」は点の学習。線の例：API を動かす → 外部パッケージや外部 API に通信できない → ECS をパブリックサブネットに置いてグローバル IP を持たせる → 外からアクセスできてしまうのは危険 → NAT Gateway が必要 → 学習用には月 7,000 円は高い → EC2 で iptables を設定して NAT の代わりにする → 停止忘れを防ぐため EventBridge Scheduler で自動停止。小さな理由付けと意思決定の積み重ねが設計力になり、実務と同じ筋肉を使う（資格教材は点になりがち）
5. **アプリケーションコードにこだわる**：チュートリアルが「Welcome to nginx」で完結するから実務に効かない。実務では DB マイグレーション、バッチ・非同期処理、外部 API や AWS サービス連携、認証情報、環境変数の管理、デプロイパイプラインなどが必要。教材が nginx だらけなのは、教える側がインフラエンジニアでアプリ側は専門外かつ工数を割きたくないからでは、という仮説。理想は実務で本格的な構成を丸ごと作ること。次点はバックエンドエンジニアと組んだ個人開発

### インフラスキル習得ロードマップ（5 段階）

- 多くの会社のインフラ構成はおおむね次の 5 パターンに集約され、「うちは ECS」「うちは Kubernetes」と聞くだけで技術力・プロダクト特性・組織文化がある程度透けて見える。下に行くほど学習コストが上がる（業界のレベルマップのようなもの）

| STEP | サービス | 抽象化した概念 |
|---|---|---|
| 1 | EC2 | 仮想マシン |
| 2 | ECS | コンテナ |
| 3 | Lambda | イベント駆動 |
| 4 | Google Cloud | マルチクラウド |
| 5 | EKS | Kubernetes |

### STEP1：EC2（仮想マシン）

- 選ぶ動機：①自由度が圧倒的に高い（責任共有モデルで OS から上が利用者の管理）②既存資産との互換性（オンプレの API をそのまま移す。後に Kubernetes へ移る流れも多い）③特殊要件（GPU インスタンス、大容量メモリの X 系インスタンスなど）
- 採用企業は「AWS に詳しい人がいない」か「非常に詳しい人がいる（金融・製造・公共・医療・物流などの基幹システム、大手日系企業）」の両極端
- キャリア上の利点：**インフラの手触り感**。SSH で入ってプロセスを起動・停止、`wget` でインストール、`nslookup`・`dig` で疎通確認など。コンテナ時代でもビルド時に Linux コマンドで中身を構築するので、全ての原点になる
- つらい点
  - サーバー管理の負担：OS のセキュリティパッチ、Apache・nginx などのミドルウェアのバージョン管理、カーネル更新、脆弱性対応を全台分。台数が増えると指数関数的に大変になり、メンテナンスのたびにダウンタイムの調整も要る
  - リソース割り当てが柔軟でない：同居するプロセス A（ピーク時に 3GB へスパイク）・B・C のために、平常時も 3GB のインスタンスを払い続ける。プロセスごとに分けるとコストと運用工数が増える
  - 属人性が高くなる：EC2 再起動後にアプリが起動しないインシデントの原因は、最近別の人が入れた Datadog エージェントと、サーバー内で動かしていた別のプロセスが悪さをしていたことだった。中で何でもできるので、誰が何をしたか把握できなくなる（Ansible・Chef で多少改善するが、緊急時の手作業は残る）

### STEP2：ECS（コンテナ）

- 選ぶ動機：EC2 のつらさを解決
  - **Fargate** なら、ホスト OS のハードニング（不要ポートの閉鎖、SSH・SELinux 設定）、OS の監視、パッチ適用を AWS が管理する
  - **属人性を構造的に排除**：インフラは JSON の**タスク定義**（イメージ、CPU・メモリ、環境変数、ログ出力先、ヘルスチェック）と **Dockerfile** の 2 つで静的に管理。タスクはデプロイのたびに使い捨てなので手作業の変更が残らない（ECS Exec でログインはできるが例外的な使い方）
  - リソース割り当てが柔軟：タスク・コンテナ単位で CPU・メモリを割り当てられる
- 多くの Web 系企業でメジャー。キャリア上の利点は**コンテナ時代のお作法**（プロセスをコンテナで包む、Dockerfile の書き方、SSH せず構成を静的に定義する、サーバーを使い捨てる）が身につくこと。Kubernetes や Azure Container Apps などにも横展開でき、Lambda もコンテナで動かせる
- 弱点：常駐課金でコストが高くつきやすい（社内ツールや初期プロダクトには割高）、オートスケールは自動だが即時ではない（タスク起動・安定まで 30〜60 秒で急なスパイクに間に合わないことも）、CPU・メモリ・ネットワークセキュリティ・スケーリングなどの管理負担は残る

### STEP3：Lambda（イベント駆動）

- イベントが起きたときに一時的に起動し、処理が終わると停止する
- 選ぶ動機：①従量課金で圧倒的に安い ②スケーラビリティ（設定不要で 1,000 並列まで自動スケール、数十ミリ秒単位で立ち上がる）③デプロイが速い（ECS は 5〜20 分かかることもあるが、Lambda はものの 5 分ほど）
- デメリット：コールドスタートで数秒かかる、リクエスト・レスポンスサイズ上限 6MB、タイムアウト 15 分などの制約。ECS の完全な上位互換ではない
- キャリア上の利点：**イベント駆動アーキテクチャ**という設計の手札。例：DynamoDB へのレコード put を検知して別の場所へ同期、S3 へのアップロードを検知して圧縮や動画変換。EC2・ECS は AWS のイベントから直接起動できず EventBridge・SQS・Lambda を挟む必要があるので、Lambda はイベント駆動の入口として活躍する。あわせて EventBridge、Step Functions、SQS、SNS、Kinesis Data Streams、Firehose にも詳しくなると世界が広がる
- EC2・ECS・Lambda の 3 つで、1 つのクラウドにおける仮想マシン・コンテナ・イベント駆動を一通りカバーできる

### STEP4：Google Cloud（マルチクラウド）

- 前提：AWS の次は自分の業界でシェアが高いクラウドを選ぶ（Web 系やスタートアップなら Google Cloud、大手 SIer や金融系の顧客なら Azure）
- 理由①**AWS の理解が深まる**（海外に行くと日本が分かるのと同じ）：Cloud Run を触って、ECS は VPC・サブネット・セキュリティグループ・タスク定義・タスク実行ロール／タスクロールなど設定項目が多いと気づいた。裏返せば細かいセキュリティ要件に柔軟に対応できる良さでもある。Cloud Run はゼロスケールできるが ECS はできない、似たことは Lambda でできるがサイズやタイムアウトの制約がある、など俯瞰して見えるようになる
- 理由②**いいとこ取りの設計**：API はゼロスケールできる Cloud Run、データ基盤は BigQuery、メール配信は Amazon SES、ビデオ通話は Amazon Chime、他社とのファイル連携は権限設計が柔軟な S3、フロントのホスティングは Amplify、Kubernetes のマイクロサービス基盤は GKE、など
- 生成 AI で SaaS のソフト自体より保有データに価値があるという風潮が強まり、データ基盤を整える流れから「データ基盤は BigQuery、API は AWS の ECS」というマルチクラウド構成の会社が増えている
- 2 倍の労力にはならない：仮想マシン・コンテナ・イベント駆動の概念があればすぐキャッチアップでき、サービスはほぼ 1 対 1 で対応する（EC2 ↔ GCE、ECS ↔ Cloud Run、S3 ↔ GCS、RDS ↔ Cloud SQL、Lambda ↔ Cloud Functions）。考え方が大きく違う IAM・ネットワーク・Cloud Load Balancing を重点的に押さえればよい

### STEP5：EKS / Kubernetes

- Kubernetes は Google が社内で培ったコンテナ運用ノウハウを OSS 化したコンテナオーケストレーションツール
- 導入の動機：ECS でマイクロサービスが増えると、機能ごとに AWS サービスを継ぎはぎする意思決定・キャッチアップのコストが積み上がる（サービス間通信は Cloud Map・Service Connect、デプロイは CodePipeline・CodeBuild・CodeDeploy、監視は CloudWatch、オートスケールは ECS Service Auto Scaling、バッチは EventBridge Scheduler・AWS Batch など）。Kubernetes ならマニフェスト（YAML）で統一的に表現でき（Service・Istio、Argo CD、Prometheus・Grafana、HPA、CronJob・Argo Workflows、マイグレーションは Job）、規模が大きいほど差が効く
- キャリア上の利点①**技術力がブーストする**：Kubernetes が必要なプロダクトは限られ、ほとんどは ECS で十分。それでも習得するとコンテナ・ネットワーク・クラウドの理解が大きく上がる。投稿者は EC2 → ECS で挫折 → Cloud Run → GKE → ECS と経験し、GKE の後は ECS が非常に簡単に感じ、コンテナ本を 1 冊読むだけでベストプラクティスに沿った設計・構築ができた
- キャリア上の利点②**Kubernetes を扱う会社は技術レベルが高い**：金銭・学習・運用コストが高いので、売上があり組織に投資できる会社でないと導入しない。採用力が強く、勉強熱心なエンジニアが集まる。投稿者も GKE の案件で優秀なメンバーから刺激を受けて技術力が爆発的に伸びた

### ロードマップのまとめ

- 5 段階を一通り経験すれば、Web 系の会社のどれかの技術でキャッチアップに困らない
- 「EC2 なら ECS に変えたら？」「ECS なら Lambda や Kubernetes を入れたら？」「AWS なら Google Cloud を取り入れたら？」と多角的に考えられ、奥深い設計力がつく
- インフラは広く深く、一朝一夕では身につかないが、だからこそ逆転されにくい。最初から全部やろうと気負わず、実務をこなしながら少しずつ守備範囲を広げればよい

### まとめ

- バックエンド × インフラの掛け算が、テックリード級の非機能要件の設計とインシデント対応を可能にし、市場価値を高める
- インフラは「心臓・レバレッジ・不可逆・タスクが少ない」ために経験を積みにくく、強い人がいる会社でも我流の会社でも伸び悩むジレンマがある
- 学び方の鍵は、クラウド代をケチらない、綺麗な構成を真似して複製する、まずコンソールで手動構築、ストーリーで線として学ぶ、本格的なアプリコードで構築する、の 5 点
- 習得順は EC2（仮想マシン）→ ECS（コンテナ）→ Lambda（イベント駆動）→ Google Cloud（マルチクラウド）→ EKS（Kubernetes）
