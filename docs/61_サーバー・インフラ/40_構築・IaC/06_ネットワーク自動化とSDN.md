## 1. ネットワーク自動化の意義と従来型ネットワーク

### 1.1 従来型（コントローラを使わない）ネットワークの姿

ネットワークの自動化を理解する出発点は、「自動化しないとどうなっているか」を知ることです。

従来型のネットワークでは、ルータやスイッチの **1台1台が独立した“頭脳”** を持っています。

```
          従来型（分散型）ネットワーク

   管理者 ──SSH──> R1   管理者 ──SSH──> R2   管理者 ──SSH──> SW1
                   │                    │                    │
              [頭脳+転送]  <--OSPF-->  [頭脳+転送]  <--STP-->  [頭脳+転送]

   ・設定は 1 台ずつ CLI（SSH/コンソール）で投入
   ・経路の判断（コントロールプレーン）は各機器が隣接機器と情報交換して個別に実施
```

- **経路などの判断（コントロールプレーン）が各機器に分散**している。各ルータは OSPF などで隣接ルータと情報を交換し、自分でルーティングテーブルを作ります。
- **設定も機器ごとに分散**している。管理者は SSH やコンソールで 1 台ずつログインし、CLI でコマンドを入力します。
- もちろん、パケットを実際に転送する **データプレーンはどの機器にもあります**（これはコントローラ型でも同じ）。
- 従来型の機器の設定手段は主に **CLI（SSH/コンソール）** であり、「REST API しか使えない」ということはありません。

### 1.2 手作業による管理の問題点

台数が少ないうちは CLI での手作業でも困りません。しかし数十〜数千台になると次の問題が顕在化します。

| 問題 | 内容 |
| --- | --- |
| 時間がかかる | 台数に比例して作業時間が増える。メンテナンス時間内に終わらない |
| 入力ミス | タイプミス、コピー&ペーストの貼り間違い、対象機器の取り違え |
| 不統一 | 同じ役割の機器でも担当者ごとに書き方がばらばら（→ 構成ドリフト。[[02_IaCとは]] の「発展」節） |
| 確認が大変 | 設定が標準どおりかを 1 台ずつ `show running-config` で目視確認 |
| 履歴が残らない | 誰がいつ何を変えたのかが追えない |

### 1.3 自動化のメリット

自動化（スクリプト、構成管理ツール、コントローラなど）を導入すると、

- **手作業による設定ミスが減る**
- **多数の機器に同じ設定を一貫して適用できる**
- 作業時間が短縮される
- 設定が標準どおりかを **機械的に確認** できる
- 変更履歴を管理しやすくなる（Git などと組み合わせる。[[02_IaCとは]]）

という効果があります。

一方で、次のような「自動化で起きないこと」もはっきり区別しておきましょう。

| 誤った期待 | 実際 |
| --- | --- |
| ルータやスイッチが不要になる | 自動化は機器の設定・管理を効率化するもの。**機器そのものは必要** |
| セキュリティ対策が不要になる | 不要にはならない。むしろ **自動化の仕組み自体（認証情報、APIトークン、管理サーバ）を守る必要** が生じる |
| 回線の帯域幅が増える | 帯域幅は回線契約や物理的な性能で決まる。自動化とは無関係 |

### 1.4 コントローラ型との比較（予告）

| 観点 | 従来型 | コントローラ型（SDN） |
| --- | --- | --- |
| コントロールプレーン | 各機器に分散 | コントローラに集中 |
| 設定方法 | 1台ずつ CLI | コントローラの GUI / API でまとめて |
| 全体の把握 | 機器ごとにログインして確認 | コントローラで一覧表示 |
| データプレーン | 各機器 | 各機器（変わらない） |

コントローラ型の詳細は 3章・4章で扱います。

### ひっかけポイント・よくある誤解

- 「自動化すれば機器が要らなくなる」「セキュリティ対策が不要になる」「帯域が増える」はすべて誤り。
- 「コントローラがすべての機器の転送ルールを一元的に決める」は **コントローラ型（SDN）** の特徴であって、従来型ではない。
- 「従来型の機器は REST API でしか設定できない」は誤り。従来型は **CLI（SSH/コンソール）** が中心。
- 「従来型はデータプレーンを持たない」は誤り。**データプレーンはどの方式でも各機器にある**。

### 押さえておくポイント

- 自動化の主なメリット ＝ **ミスの削減と設定の一貫性**、時間短縮、確認の機械化、履歴管理。
- 従来型 ＝ **分散型コントロールプレーン ＋ 機器ごとの CLI 設定**。
- 自動化しても機器・セキュリティ対策は必要。自動化基盤そのものの保護も課題になる。

## 2. ネットワーク機器の3つのプレーン

### 2.1 プレーンとは

ネットワーク機器の中で行われる処理は、役割ごとに **3つのプレーン（層）** に分けて考えます。SDN を理解するための必須の概念です。

```
 ┌──────────────────────────────────────────────┐
 │ 管理プレーン (Management Plane)               │  機器を「管理」する
 │   SSH/Telnet ログイン, SNMP, Syslog, NTP,    │
 │   API(NETCONF/RESTCONF)による設定            │
 ├──────────────────────────────────────────────┤
 │ コントロールプレーン (Control Plane)          │  転送の「ルール」を決める
 │   OSPF/EIGRP/BGP, STP(BPDU), ARP             │
 │   → ルーティングテーブル / MACテーブル等を作る │
 ├──────────────────────────────────────────────┤
 │ データプレーン (Data Plane / Forwarding)      │  ルールに従って「転送」する
 │   パケット転送, フレームのスイッチング,        │
 │   ACL による破棄, NAT の変換, カプセル化       │
 └──────────────────────────────────────────────┘
```

| プレーン | 一言でいうと | 主な例 |
| --- | --- | --- |
| **コントロールプレーン** | 「どう転送するか」を決める | OSPF などのルーティングプロトコル（ネイバーとのルート情報・LSA 交換）、STP の BPDU 送受信とブロックポートの決定、ARP による MAC アドレスの学習 |
| **データプレーン**（フォワーディングプレーン） | 決まったルールに従って実際に転送する | ルーティングテーブルに基づくパケット転送、MAC アドレステーブルに基づくフレーム転送、ACL の deny に一致したパケットの破棄、NAT のアドレス変換 |
| **管理プレーン** | 機器そのものを管理・監視する | SSH/Telnet でのログイン、SNMP による監視、Syslog の送信、NTP、API による設定 |

### 2.2 判断のコツ

迷ったら次の質問で判定します。

1. **ユーザーのパケット／フレーム 1 つ 1 つに対する処理か？** → データプレーン
   - 「転送する」だけでなく「**破棄する**」（ACL の deny）もパケットごとの判断なのでデータプレーン。
2. **転送ルール（テーブル）を作るための、機器同士の情報交換か？** → コントロールプレーン
   - OSPF の LSA 交換、STP の BPDU、ARP。
3. **人や管理システムが機器を操作・監視するための通信か？** → 管理プレーン
   - SSH ログイン、SNMP で CPU 使用率を送る、Syslog、NTP。

```
例：ルータ R1 がパケットを受信した時の流れ

  [コントロールプレーン] OSPF でルートを学習 ──> ルーティングテーブル作成
                                                     │（ルールを渡す）
                                                     ▼
  受信パケット ──> [データプレーン] テーブルを引いて出力IFへ転送 ──> 送信
                                    （ACL deny ならここで破棄）

  管理者 ──SSH──> [管理プレーン] show コマンドで状態を確認
```

> 補足：ARP は「IP と MAC の対応表（ARP テーブル）を作る」処理なので、ネットワークの教材ではコントロールプレーンに分類されます。テーブル作成＝コントロール、テーブル参照による転送＝データ、と覚えるとぶれません。

### 2.3 SDN との関係

SDN（3章）では、このうち **コントロールプレーンの処理をコントローラに集約** します。データプレーンは引き続き各機器が担います。「アプリケーションプレーン」という言葉は SDN アーキテクチャの層（アプリケーション層）を指して使われることはありますが、**一般的なネットワーク機器の3つのプレーンには含まれません**。

### ひっかけポイント・よくある誤解

- 「ACL の deny で破棄する」は **データプレーン**。「セキュリティのルールだからコントロール」と考えるのは誤り。
- 「スイッチが MAC アドレステーブルに従ってフレームを転送する」は **データプレーン**。MAC アドレスを「学習してテーブルを作る」ことと「テーブルを引いて転送する」ことを混同しない。
- 「SSH でログイン」は **管理プレーン**。
- 「STP の BPDU を送受信してブロックするポートを決める」は、どのポートを使うかというルールを決めるので **コントロールプレーン**。
- 「SNMP で CPU 使用率を監視マネージャへ送る」は **管理プレーン**。
- 「アプリケーションプレーン」は機器の3プレーンには含まれない。
- データプレーンは「フォワーディングプレーン」とも呼ぶ。

### 押さえておくポイント

- **コントロール＝決める、データ＝転送する（破棄も含む）、管理＝管理する**。
- OSPF / STP / ARP → コントロール。転送 / ACL 破棄 / NAT → データ。SSH / SNMP / Syslog / NTP / API → 管理。
- SDN はコントロールプレーンを集約する技術。

## 3. SDNのアーキテクチャとノースバウンド／サウスバウンドAPI

### 3.1 SDN とは

**SDN（Software-Defined Networking）** は、ネットワークの制御をソフトウェア（**コントローラ**）に集約し、ネットワーク全体をプログラムから制御できるようにする考え方です。

- 従来：各機器がコントロールプレーンを持ち、個別に判断（分散型）
- SDN：**コントローラがネットワーク全体を把握し、コントロールプレーンを集中して担う**。各機器はコントローラの指示に従ってデータを転送する（データプレーン）

Cisco の SDN コントローラの代表例が **Catalyst Center（旧DNA Center）** です（4章）。

コントローラは、アクセススイッチ、ファイアウォール、無線アクセスポイントとは役割が異なります。

| 機器 | 役割 |
| --- | --- |
| **コントローラ** | ネットワーク全体を把握し、各機器に指示を出す（制御の集中） |
| アクセススイッチ | 端末をつなぐ層のスイッチ。SDN では主に **データプレーン（転送）** を担う |
| ファイアウォール | 通信を許可・拒否してネットワークを守る |
| 無線アクセスポイント（AP） | 無線端末をネットワークにつなぐ。多数の AP を集中管理するのは **WLC（無線LANコントローラ）** |

### 3.2 SDN の3層構造と API の向き

SDN の構成図は、上にアプリケーション、真ん中にコントローラ、下にネットワーク機器を描きます。地図と同じく **上が北（North）、下が南（South）** です。

```
 ┌───────────────────────────────────────────────┐
 │ アプリケーション層                               │
 │  管理ツール / Python スクリプト / 監視・チケット │
 └───────────────────────────────────────────────┘
                  ▲  ノースバウンドAPI（NBI）
                  │  例：REST API（HTTPS + JSON）
                  ▼
 ┌───────────────────────────────────────────────┐
 │ コントロール層：SDNコントローラ                   │
 │  （Catalyst Center など）ネットワーク全体を把握    │
 └───────────────────────────────────────────────┘
                  ▲  サウスバウンドAPI（SBI）
                  │  例：NETCONF, RESTCONF, OpenFlow,
                  │      CLI(SSH), SNMP
                  ▼
 ┌───────────────────────────────────────────────┐
 │ インフラストラクチャ層：ルータ / スイッチ / AP      │
 │  （データプレーン＝実際の転送）                    │
 └───────────────────────────────────────────────┘
```

| API | どこの間か | 代表的な技術 |
| --- | --- | --- |
| **ノースバウンドAPI** | **コントローラ ⇔ その上で動くアプリケーション**（管理ツール、スクリプトなど） | **REST API**（HTTPS + JSON） |
| **サウスバウンドAPI** | **コントローラ ⇔ ネットワーク機器** | **NETCONF、RESTCONF、OpenFlow**、CLI（SSH）、SNMP |

- ノースバウンドAPI を使うと、アプリケーションがコントローラに指示を出したり、情報（機器一覧、障害情報など）を取得したりできます。
- **機器同士**（ルータとルータ）の通信は OSPF などのプロトコルで行われ、ノースバウンド／サウスバウンドという API の区分には入りません。
- ユーザーの PC とインターネットの間の通信も SDN の API とは無関係です。

### 3.3 サウスバウンドのプロトコル

#### OpenFlow

- **ONF（Open Networking Foundation）** が標準化した、初期の SDN を代表するサウスバウンドプロトコル。
- コントローラがスイッチの **フローテーブル**（どのパケットをどう転送するかのルール）を **直接書き換える**。
- コントロールプレーンを **完全にコントローラへ移し**、スイッチは受け取ったルールに従って転送するだけになる。

```
 コントローラ ──OpenFlow──> スイッチのフローテーブル
                           ┌─────────────────────────────┐
                           │ 一致条件            │ 動作    │
                           │ 宛先IP 10.1.1.0/24  │ port 2  │
                           │ TCP 宛先ポート 23   │ drop    │
                           └─────────────────────────────┘
```

#### NETCONF / RESTCONF

- 機器の **設定や状態を取得・変更** するためのプロトコル（詳細は 5章）。
- **NETCONF**：SSH（TCP 830）＋ XML。
- **RESTCONF**：HTTPS ＋ JSON/XML。
- どちらも **YANG** というデータモデルで設定項目の構造が定義されている。

#### CLI（SSH）・SNMP

- 従来の機器を扱うために、コントローラが SSH で CLI コマンドを投入したり、SNMP で情報を収集したりすることもある。

### 3.4 サウスバウンドと間違えやすいプロトコル

| プロトコル | 実際の役割 | SDN のサウスバウンド？ |
| --- | --- | --- |
| HSRP | デフォルトゲートウェイを冗長化する FHRP の一つ | いいえ |
| DHCP | 端末に IP アドレスを自動割り当て | いいえ |
| ARP | IP アドレスから MAC アドレスを調べる | いいえ |
| OSPF | ルータ同士がルート情報を交換するルーティングプロトコル | いいえ（コントローラが使うものではない） |
| LLDP | 隣接機器の情報を取得する | いいえ |
| NETCONF / RESTCONF / OpenFlow | 機器の設定・転送ルールを制御 | **はい** |

### ひっかけポイント・よくある誤解

- 「コントローラとネットワーク機器の間」はノースバウンドではなく **サウスバウンド**。
- 「ネットワーク機器同士の間」は API 区分ではない。
- 「アクセススイッチが制御を担う」は誤り。SDN ではアクセススイッチは主に **データプレーン**。
- 多数の AP を集中管理する機器は **WLC**。AP 自体がコントローラではない。
- HSRP / DHCP / ARP / OSPF / LLDP をサウスバウンドプロトコルと取り違えない。
- OpenFlow は「フローテーブルを直接書き換える」。NETCONF は「設定を取得・変更する」。役割の言い回しで区別する。

### 押さえておくポイント

- SDN ＝ **コントロールプレーンをコントローラに集約**、機器はデータプレーンを担う。
- **ノースバウンド＝コントローラとアプリ間（REST API）**、**サウスバウンド＝コントローラと機器間（NETCONF / RESTCONF / OpenFlow / CLI / SNMP）**。
- OpenFlow ＝ ONF 標準、フローテーブルを直接制御。
- Cisco のコントローラ例 ＝ Catalyst Center（旧DNA Center）。

## 4. Catalyst Center・インテントベースネットワーキング・SD-Access

### 4.1 Catalyst Center（旧DNA Center）

**Catalyst Center** は Cisco のキャンパス（企業LAN）ネットワーク向けコントローラです。以前は **DNA Center** と呼ばれていました。

主な機能：

- 多数の機器を **1か所から管理** し、ポリシーや設定を **まとめて適用**
- 機器の状態の監視（アシュアランス）、障害の分析
- ソフトウェア（OS イメージ）の一括更新
- GUI に加え、**REST API（ノースバウンドAPI）** を公開。スクリプトや他システムからも操作できる
- SD-Access ファブリックの管理

従来型との対比：

| 観点 | 従来型の管理 | コントローラ（Catalyst Center）による管理 |
| --- | --- | --- |
| 設定の確認 | **機器ごとにログイン** して確認 | コントローラで **一覧** 確認 |
| 設定の適用 | 1台ずつ CLI | ポリシーとしてまとめて適用 |
| 一貫性 | 担当者次第でばらつく | テンプレート・ポリシーで統一 |
| 障害対応 | ログを機器ごとに収集 | 集中監視で原因を素早く特定 |

注意点：

- コントローラで管理していても、**必要に応じて SSH/CLI でのログインは可能**。CLI が使えなくなるわけではありません。
- コントローラは機器と **IP で通信する** ため、機器には **管理用の IP アドレスが必要** です。

### 4.2 インテントベースネットワーキング（IBN）

**インテント（Intent）＝意図、「何を実現したいか」** のことです。

```
 従来：管理者が「どう設定するか(How)」を考え、機器ごとにコマンドを入力
   管理者 → R1 : access-list 101 deny ip 10.50.0.0 0.0.255.255 10.10.0.0 0.0.255.255 ...
          → SW1: ...
          → SW2: ...

 IBN：管理者は「何をしたいか(What)」= ポリシーを定義するだけ
   管理者 →「来客用の端末は社内サーバにアクセスさせない」
             │
             ▼
        コントローラ（Catalyst Center）
             │ ① 意図を各機器の具体的な設定に変換（翻訳）
             │ ② 各機器へ自動適用
             │ ③ 意図どおりに動いているかを継続的に確認（アシュアランス）
             ▼
        R1 / SW1 / SW2 / WLC ...
```

- IBN の代表的な製品が **Catalyst Center（旧DNA Center）**。
- 「ポリシーを定義 → コントローラが変換・適用 → 継続的に確認」の流れが IBN の特徴です。

### 4.3 Cisco SD-Access

**SD-Access** は Catalyst Center が管理する、キャンパス向けの SDN ソリューションです。
**物理ネットワーク（アンダーレイ）の上に、仮想ネットワーク（オーバーレイ）を作る** のが基本構造です。

```
   ┌───────────── オーバーレイ（仮想ネットワーク）──────────────┐
   │  VN: 社員     VN: 来客     VN: IoT       ← 利用者/端末を   │
   │                                           グループ分け    │
   │      ═══════ VXLAN トンネル ═══════                      │
   └──────────────────────────────────────────────────────────┘
   ┌───────────── アンダーレイ（物理ネットワーク）──────────────┐
   │  物理スイッチ・ルータを IP ルーティング（例：IS-IS）で接続   │
   │   [Edge]──[Border]──[Edge]──[Control Plane Node]         │
   └──────────────────────────────────────────────────────────┘
          アンダーレイ ＋ オーバーレイ ＝ ファブリック
                    管理：Catalyst Center
```

| 用語 | 意味 |
| --- | --- |
| **アンダーレイ** | 物理的なスイッチ・ルータと、それらを **IP ルーティングでつないだ** 土台のネットワーク |
| **オーバーレイ** | アンダーレイの上に、**トンネル（VXLAN）** を使って作る仮想的なネットワーク |
| **ファブリック** | アンダーレイとオーバーレイを合わせた **ネットワーク全体** |

利用者や端末はオーバーレイでグループ分けされるため、**物理的な接続場所に関係なく同じポリシーを適用** できます（例：社員はどのフロアのどのポートにつないでも「社員」のポリシー）。

#### SD-Access の3つの要素

| 要素 | 技術 | 役割 |
| --- | --- | --- |
| **データプレーン** | **VXLAN** | 元のフレームを **UDP パケットで包んで（カプセル化）**、アンダーレイ越しに運ぶ |
| **コントロールプレーン** | **LISP** | 端末が **どこ（どのエッジ）にいるか** を管理する。データのカプセル化はしない |
| **ポリシー** | **Cisco TrustSec（SGT）** | セキュリティグループタグでグループ単位のアクセス制御 |

VXLAN のカプセル化のイメージ：

```
 ┌──────────┬────────┬────────┬─────────────────────────────────┐
 │ 外側 IP   │ 外側UDP │ VXLAN  │ 元のEthernetフレーム（内側）       │
 │(エッジ間) │ (4789) │ ヘッダ  │ 宛先MAC/送信元MAC/IP/データ ...    │
 └──────────┴────────┴────────┴─────────────────────────────────┘
   ↑ アンダーレイはこの外側IPだけを見てルーティングする
```

VXLAN でカプセル化することで、**物理ネットワーク（アンダーレイ）の構成に関係なく** 仮想ネットワークを自由に作れます。

#### 間違えやすい技術

| 技術 | 実際の役割 | SD-Access のオーバーレイのカプセル化？ |
| --- | --- | --- |
| VXLAN | L2 フレームを UDP でカプセル化 | **はい（データプレーン）** |
| LISP | 端末の位置情報の管理 | いいえ（コントロールプレーン） |
| 802.1Q | トランクで VLAN タグを付ける | いいえ |
| NAT | IP アドレス変換 | いいえ（カプセル化しない） |

### ひっかけポイント・よくある誤解

- 「コントローラを使うと SSH/CLI でログインできなくなる」は誤り。
- 「機器ごとにログインして設定を確認する必要がある」は従来型の特徴。
- 「機器に IP アドレスが不要になる」は誤り。管理用 IP は必要。
- 物理的なネットワーク＝**アンダーレイ**。オーバーレイ（仮想）やファブリック（全体）と取り違えない。「ノースバウンド」は API の用語。
- LISP は SD-Access で使われるが **コントロールプレーン**。カプセル化は VXLAN。
- 「ポリシーを定義するとコントローラが設定に変換」＝ **IBN**。構成ドリフト（設定のずれ）やロンゲストマッチ（ルート選択規則）とは無関係。

### 押さえておくポイント

- Catalyst Center（旧DNA Center）＝ Cisco のキャンパス向けコントローラ。**GUI ＋ REST API（ノースバウンド）**。
- IBN ＝「何をしたいか」を定義 → コントローラが変換・適用・継続確認。
- SD-Access：**アンダーレイ（物理）＋オーバーレイ（仮想）＝ファブリック**。
- SD-Access の要素：**データ＝VXLAN、コントロール＝LISP、ポリシー＝TrustSec（SGT）**。

## 5. モデル駆動のプログラマビリティ：YANG・NETCONF・RESTCONF

### 5.1 なぜ「モデル駆動」が必要か

従来、プログラムで機器の情報を取るには `show` コマンドの出力（人間向けのテキスト）を解析（スクレイピング）していました。

```
R1# show ip interface brief
Interface              IP-Address      OK? Method Status                Protocol
GigabitEthernet0/0     10.1.1.1        YES manual up                    up
```

- 出力形式が **機種・OS バージョンごとにばらばら**
- バージョンアップで列がずれるとスクリプトが壊れる

そこで、**「どんなデータがあり、どんな型か」をあらかじめ定義（モデル化）し、その構造どおりにデータをやり取りする** 方式が生まれました。これを **モデル駆動のプログラマビリティ** と呼びます。

```
 ┌────────────────────────────────────────────┐
 │ YANG（データモデル＝設計図）                   │  どんな項目・型があるか
 └────────────────────────────────────────────┘
          │ この構造に従ったデータを
          ▼
 ┌──────────────────────┐  ┌──────────────────────┐
 │ エンコード：XML         │  │ エンコード：JSON / XML  │  実際の書き方
 └──────────────────────┘  └──────────────────────┘
          │                          │
 ┌──────────────────────┐  ┌──────────────────────┐
 │ プロトコル：NETCONF     │  │ プロトコル：RESTCONF    │  やり取りの方法
 │ トランスポート：SSH 830 │  │ トランスポート：HTTPS   │
 └──────────────────────┘  └──────────────────────┘
```

### 5.2 YANG（データモデリング言語）

- **YANG（Yet Another Next Generation）** は **データの構造を定義する言語（データモデリング言語）** です。
- インターフェースや VLAN などの設定項目に「どんな項目があり、それぞれどの型の値を取るか」を定義します。
- YANG は「どんなデータがあるか」という **設計図**。それを実際にやり取りするときの **書き方が XML や JSON** です。

YANG の例（簡略化）：

```yang
container interfaces {
  list interface {
    key "name";
    leaf name    { type string; }
    leaf enabled { type boolean; default true; }
    leaf mtu     { type uint16; }
  }
}
```

この構造に従ったデータを JSON で表すと（RESTCONF の場合）：

```json
{
  "ietf-interfaces:interfaces": {
    "interface": [
      {"name": "GigabitEthernet1", "enabled": true}
    ]
  }
}
```

比較：SNMP では **MIB** で管理項目を定義しました。YANG は NETCONF / RESTCONF における「MIB に相当するもの」とイメージすると理解しやすいです。

| 役割 | SNMP の世界 | モデル駆動の世界 |
| --- | --- | --- |
| データ構造の定義 | MIB | **YANG** |
| プロトコル | SNMP（Get/Set） | **NETCONF / RESTCONF** |

### 5.3 NETCONF

| 項目 | 内容 |
| --- | --- |
| トランスポート | **SSH（TCP 830）** |
| データ形式 | **XML** |
| 扱うデータ | YANG で定義されたデータ |
| 操作 | **RPC（リモートプロシージャコール）** の形で要求：`get-config`（設定取得）、`edit-config`（設定変更）、`get`（状態取得）など |
| Cisco IOS XE での有効化 | `netconf-yang` コマンド |
| SDN での位置 | **サウスバウンド**（コントローラ → 機器） |

```
R1(config)# netconf-yang
```

NETCONF の RPC の例（設定取得）：

```xml
<rpc message-id="101" xmlns="urn:ietf:params:xml:ns:netconf:base:1.0">
  <get-config>
    <source><running/></source>
  </get-config>
</rpc>
```

NETCONF は **SSH で暗号化された接続の上** で XML のメッセージをやり取りします。HTTPS（TCP 443）、SNMP（UDP 161）、Telnet（TCP 23）は NETCONF のトランスポートではありません。

### 5.4 RESTCONF

| 項目 | 内容 |
| --- | --- |
| トランスポート | **HTTPS**（TCP 443） |
| データ形式 | **JSON または XML** |
| 扱うデータ | YANG で定義されたデータ |
| 操作 | **REST API と同じ HTTP メソッド**（GET、POST、PUT、PATCH、DELETE） |
| 利点 | Web API の知識で扱えるので、スクリプトから使いやすい |

RESTCONF のリクエスト例：

```http
GET https://r1.example.com/restconf/data/ietf-interfaces:interfaces/interface=GigabitEthernet1
Accept: application/yang-data+json
Authorization: Basic YWRtaW46Q2lzY28xMjM=
```

Cisco IOS XE では `restconf` コマンド（と HTTPS サーバ `ip http secure-server`）で有効にします。

### 5.5 NETCONF・RESTCONF・SNMP・OpenFlow の比較

| プロトコル | トランスポート / ポート | データ形式 | データ定義 | 主な用途 |
| --- | --- | --- | --- | --- |
| **NETCONF** | **SSH / TCP 830** | **XML** | YANG | 設定の取得・変更（RPC） |
| **RESTCONF** | **HTTPS / TCP 443** | **JSON / XML** | YANG | 設定の取得・変更（HTTP メソッド） |
| SNMP | UDP 161（トラップは 162） | BER | **MIB** | 監視（Get/Set） |
| OpenFlow | TCP（6653） | バイナリ | ― | フローテーブルの直接制御 |

### ひっかけポイント・よくある誤解

- データの構造を定義するのは **YANG**。JSON はエンコード方式であって構造の定義そのものではない。Python はプログラミング言語、SNMP は監視プロトコル（定義は MIB）。
- 「HTTPS で、GET/PUT などで YANG データを操作」＝ **RESTCONF**。NETCONF は SSH + XML、SNMP は MIB を Get/Set、OpenFlow はフローテーブル制御。
- NETCONF ＝ **SSH（TCP 830）**。HTTPS 443 は RESTCONF、UDP 161 は SNMP、Telnet 23 は使わない。
- NETCONF はサウスバウンド。データは XML、SSH で通信。

### 押さえておくポイント

- **YANG ＝ データモデル（設計図）**、XML/JSON ＝ 書き方、NETCONF/RESTCONF ＝ 運び方。
- **NETCONF：SSH・TCP 830・XML・RPC（get-config / edit-config）・`netconf-yang`**。
- **RESTCONF：HTTPS・JSON/XML・HTTP メソッド**。
