## 詳しい要約

**テーマ：ステートファイルの理解と terraform import の反復で Terraform 恐怖症を克服する**

本番で Terraform を触るのが怖い根本原因は、コマンド実行後に「世界」（ソースコード・AWS リソースの実体・ステートファイル）がどう変わるかをイメージできていないこと。特に影の薄い**ステートファイル**を理解することが克服のセンターピンで、そのための最も効果的な練習が **terraform import をやりまくる**こと、という話。

---

### なぜ Terraform が怖いのか

- 実務では `plan` と `apply` 以外のコマンド（`state rm`、`state mv`、`import` など）はチームのステートを書き換え、他の人が実行したときに大量の destroy & create 差分を生むため、基本的に禁止されている。
- そのため plan と apply だけを繰り返すことになり、ステートファイルを理解する機会がなく、恐怖心が消えない。既存コードのコピーや新規作成はできても、本番で意図しない差分が出ると手も足も出なくなる。

### ステートファイルとは・理解すべき理由

- Terraform が管理するリソースの状態を記録するファイル（実務では S3 や Terraform Cloud に置く）。中身を見たことがある人は少ない。
- 理由①：**plan の差分の元になる**。差分は「ソースコード・実体・ステートファイル」の 3 つの関係で決まる。
- 理由②：**予期せぬ差分に落ち着いて対応できる**。大量の destroy & create や replace が出たとき、apply してよいかの判断と回避方法がわかる。

### 実体験：深夜の本番リリース

- AWS WAF を適用する深夜リリースで、plan に予期しない大量の destroy & create が出た。朝 6 時までに終える必要があり、依存関係が複雑で中止もできず、Terraform に詳しいのは実質本人だけ。
- `state rm`・`import`・`state mv` でステートと実体のつじつまを合わせ、どうしても消えない差分は `lifecycle` の `ignore_changes` で一時的に無視し、最後に必要な create だけを残して安全に apply できた。
- 本質的な Terraform 力とは「どんな予期しない差分が出ても、手触り感をもって元の状態に戻せる力」（時限爆弾の切ってはいけない線を見極めるイメージ）。

### plan と apply の内部の仕組み

| 要素 | 実体 | 呼び方 |
|---|---|---|
| ステートファイル（`.tfstate`） | S3 など | Current（現在の状態） |
| ソースコード（`.tf`） | 手元 | Desire（こうしたいという意思） |
| AWS リソース | AWS | Real（実体） |

- **plan**：S3 からステートをダウンロードしてメモリに保持 → ステート内の ID をもとに AWS API で実体を参照し、メモリ上のステートを最新にリフレッシュ → `.tf` と比較して差分を出力。
  - ステートを鵜呑みにせず実体を見に行く点、**ステートにないリソースは API で問い合わせすらされず存在しないものとして扱われる**点が重要。
- **apply**：plan 結果を反映（例：ECR を作成）し、最新の状態をメモリ上のステートに展開して S3 にアップロード。Current・Real・Desire の 3 つがそろうので、再度 plan すると No changes になる。

### 実演：ECR リポジトリで変化を追う

| 操作 | 予想と結果 |
|---|---|
| 初回 plan → apply | create 差分 → ECR とステート（JSON）ができる |
| コンソールで実体を削除して plan | 実体を見に行くので create 差分が出る |
| コンソールで MUTABLE → IMMUTABLE に変更して plan | IMMUTABLE → MUTABLE に戻す差分が出る |
| 実体を削除し、コードもコメントアウトして plan | どちらもないので No changes |
| ステートファイルだけ削除して plan | ステートにないので実体を認知できず create 差分 → apply すると **AlreadyExists エラー** |
| `terraform import` | 既存の実体をステートに取り込み、Terraform で管理できるようになる（plan の出力からリソースアドレスをコピーすると楽） |
| `terraform state rm` | ステートからは消えるが実体は残る。例：Route 53 のレコードが事故で消えたので Terraform 管理外にしたいとき。`terraform state list` で管理対象を確認できる |

- 仮説を立てて plan の結果が当たるようになると、Terraform の解像度が上がる。

### 実力がつかないアンチパターン

- 入門書によくある「コードをコピー → plan → apply で新規リソースを作成」をひたすら繰り返すこと。楽しいがステートファイルを意識しないので、本番への恐怖心は一生消えない。
- 実務ではゼロから作ることはほぼなく、既存の大量のコードとリソースに変更をかけたときに出る予期せぬ差分を地道に解きほぐす力が求められる。

### 正しい学習法：terraform import をやりまくる

- import は既存の AWS リソースを Terraform の管理下に置くコマンド。新規導入する会社だけでなく実務でもよく使う：初めての構成はまずコンソールで手動構築して動作確認し、構成が固まってから import でコード化する流れが多い。
- 本人の経験：5 年ほど前、既存環境の Terraform 化プロジェクトで先輩 SRE のコードを見て学んでいたが、差分が出ると周りに泣きつく状態だった。副業で Google Cloud 環境を一人で Terraform 化したとき、import ではきれいな差分が出ず、あらゆるケースを踏み抜いた。その中で「モジュールに切り出したら `state mv`」「相性の悪いリソースは `state rm` で外す」「ひどい差分は一度 `state rm` して import し直す」といった判断ができるようになった。同じ年に別案件で 2 つ、既存リソースの全面 Terraform 化を担当し、力が大きく伸びた。

### Terraform はインフラ版の Git

- Git に慣れた人は、`reset`・`rebase`・`cherry-pick`・`revert` などでどの状態からどの状態になるかを体でわかっている（ぐちゃぐちゃな履歴を CTO があらゆるコマンドで戻した例）。
- Terraform も同じで、`state mv`・`state rm`・`import`・`refresh` を駆使して、本番を絶対に壊さないという確信をもって操作できる状態が「自由自在に扱える」状態。

### まとめ

- 恐怖心の原因は、ステートファイルを含む 3 者の関係をイメージできていないこと。
- plan は「ステートを読み込み → 実体でリフレッシュ → コードと比較」、apply は「反映してステートを更新」。ステートにないものは認知されない。
- 新規作成の繰り返しではなく、**terraform import で既存リソースを取り込む練習**を重ねるのが克服の近道。
