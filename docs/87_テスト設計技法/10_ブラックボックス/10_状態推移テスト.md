# 状態推移テスト（State Transition Testing）

**状態推移テスト**は、システムが持つ**状態**と、**イベント**による**遷移**をモデル化し、状態遷移を網羅的にテストする技法です。状態を持つシステム（ログイン、カート、ワークフローなど）に適しています。

## 📖 状態推移テストとは

多くのシステムは「状態」を持ち、ユーザー操作やイベントによって状態が変わります。状態遷移図や状態遷移表でこの振る舞いを表現し、全ての遷移や状態の組み合わせをテスト対象にします。

## 🎯 目的

- **状態の網羅**: すべての状態と遷移をテスト
- **遷移漏れの防止**: 想定外の遷移や未定義の遷移を発見
- **仕様の可視化**: 状態と遷移を図で整理し、曖昧さを減らす

## 📊 状態遷移図の要素

| 要素 | 記号/説明 |
|------|-----------|
| **状態** | 丸または四角で表す |
| **遷移** | 矢印（イベント/条件 → アクション） |
| **初期状態** | 黒丸から出る矢印で表す |
| **終了状態** | 二重丸で表す（ある場合） |

## 💡 例1: ログイン機能

### 状態

- **未ログイン**: 初期状態
- **ログイン中**: 認証済み
- **ロック中**: 連続失敗でロック
- **エラー表示**: 認証失敗メッセージ表示中

### イベントと遷移

| 現在の状態 | イベント | 次の状態 | アクション |
|------------|----------|----------|------------|
| 未ログイン | 正しいID/PWでログイン | ログイン中 | ダッシュボード表示 |
| 未ログイン | 誤ったID/PWでログイン | エラー表示 | エラーメッセージ表示 |
| 未ログイン | 3回連続失敗 | ロック中 | ロックメッセージ表示 |
| エラー表示 | 再入力 | 未ログイン | フォームクリア |
| ログイン中 | ログアウト | 未ログイン | セッション破棄 |
| ロック中 | 10分経過 | 未ログイン | ロック解除 |
| ロック中 | 管理者解除 | 未ログイン | ロック解除 |

### 状態遷移図（簡略）

```
[未ログイン] --正しい認証--> [ログイン中]
     |                            |
     | 誤認証(1-2回)              | ログアウト
     v                            v
[エラー表示] <---------------- [未ログイン]
     |
     | 誤認証(3回目)
     v
[ロック中] --10分経過/管理者解除--> [未ログイン]
```

### テストケース例

| No | テスト内容 | 期待結果 |
|----|------------|----------|
| 1 | 未ログイン → 正しくログイン | ログイン中へ遷移 |
| 2 | 未ログイン → 誤認証1回 | エラー表示へ遷移 |
| 3 | エラー表示 → 再入力 | 未ログインへ遷移 |
| 4 | 未ログイン → 3回連続誤認証 | ロック中へ遷移 |
| 5 | ログイン中 → ログアウト | 未ログインへ遷移 |
| 6 | ロック中 → 10分待機 | 未ログインへ遷移 |
| 7 | ロック中からログイン試行 | 拒否、ロック継続 |

## 📐 Nスイッチカバレッジ（詳細）

Nスイッチカバレッジは、状態遷移テストの**網羅レベル**を表す指標です。「N+1個の状態を結ぶN本の遷移」で構成される**遷移の連続シーケンス**を、どれだけテストするかを定義します。

---

### 🌱 初心者向け：Nスイッチを「駅と電車」でイメージする

**「スイッチ」＝「区間（1本の線路）」** だと思ってください。状態は「駅」、遷移は「A駅からB駅へ向かう1区間」です。

| 言い換え | 意味 |
|----------|------|
| **0-スイッチ** | 「各線路を1回ずつ乗る」＝駅と駅の**1区間だけ**をテスト |
| **1-スイッチ** | 「**2区間つながった乗り継ぎ**」をテスト（例：東京→新宿→渋谷） |
| **2-スイッチ** | 「**3区間つながった乗り継ぎ**」をテスト（例：東京→新宿→渋谷→品川） |
| **N-スイッチ** | 「**N+1区間つながった乗り継ぎ**」をテスト |

**なぜ「つながり」をテストするのか？**  
1区間ずつは問題なくても、「A→B→C」と続けたときにだけ起きる不具合（例：Bの状態が正しく引き継がれていない）があるためです。Nを大きくすると、より長い操作の流れをまとめて検証できます。

**覚え方のコツ**

- **「N-スイッチ」＝「N本の矢印（遷移）が連続したパス」** をカバーする
- 0-スイッチ＝1本の矢印、1-スイッチ＝2本連続、2-スイッチ＝3本連続……

まずは **0-スイッチ（全遷移）** を押さえ、余力があれば **1-スイッチ（遷移のつながり）** を追加する、と考えると取り組みやすいです。

---

### 定義

| 用語 | 説明 |
|------|------|
| **スイッチ** | 状態間の1本の遷移（エッジ） |
| **N-スイッチ** | N本の遷移が連続したパス（＝N+1個の状態を通過） |
| **N-スイッチカバレッジ** | すべての「N本連続の遷移パス」を少なくとも1回テストすること |

### レベル別の詳細

#### 0-スイッチカバレッジ（遷移カバレッジ）

**内容**: すべての**単一遷移**を1回以上テストする。

- **カバー対象**: 各エッジ（A→B の遷移）を1回ずつ
- **テストケース数**: 遷移の総数と同程度
- **強度**: 最低限。単体の遷移の正しさは確認できるが、遷移の「つながり」は検証しない

**ログイン例での0-スイッチ**:
```
遷移1: 未ログイン → ログイン中
遷移2: 未ログイン → エラー表示
遷移3: 未ログイン → ロック中
遷移4: エラー表示 → 未ログイン
遷移5: ログイン中 → 未ログイン
遷移6: ロック中 → 未ログイン
... 各1ケースずつ
```

---

#### 1-スイッチカバレッジ（遷移ペアカバレッジ）

**内容**: すべての**2連続遷移**（状態A→B→C）を1回以上テストする。

- **カバー対象**: 2本連続の遷移パス（A→B→C）
- **強度**: 中程度。前の遷移の結果が次の遷移に正しく影響するかを検証
- **バグ検出**: 遷移の「つながり」の不具合（例: ログイン後の状態が不正）を発見しやすい

**ログイン例での1-スイッチ（例）**:
```
パス1: 未ログイン → ログイン中 → 未ログイン（ログアウト）
パス2: 未ログイン → エラー表示 → 未ログイン（再入力）
パス3: 未ログイン → エラー表示 → 未ログイン → ロック中（3回失敗）
パス4: 未ログイン → ロック中 → 未ログイン（10分経過）
... すべての「2連続遷移」をカバー
```

---

#### 2-スイッチカバレッジ

**内容**: すべての**3連続遷移**（状態A→B→C→D）を1回以上テストする。

- **カバー対象**: 3本連続の遷移パス
- **強度**: 高。より長い操作シーケンスでの不具合を検出
- **テストケース数**: 1-スイッチより増加

---

#### N-スイッチカバレッジ（一般）

**内容**: すべての**N+1連続遷移**（N+2個の状態を通過するパス）を1回以上テストする。

| N | カバーするパス | 例 |
|---|----------------|-----|
| 0 | 1本の遷移 | A→B |
| 1 | 2本連続 | A→B→C |
| 2 | 3本連続 | A→B→C→D |
| k | k+1本連続 | 長さk+1のパス |

### 具体例: ショッピングカートでの比較

```
状態: 空(S0) → 商品あり(S1) → チェックアウト中(S2) → 注文完了(S3)
      S0 ←── S1 ←── S2（キャンセルで戻る）
```

| カバレッジ | テストするパスの例 | ケース数イメージ |
|------------|-------------------|------------------|
| 0-スイッチ | S0→S1, S1→S2, S2→S3, S2→S1... | 遷移数分 |
| 1-スイッチ | S0→S1→S2, S0→S1→S0, S1→S2→S3, S1→S2→S1... | 遷移ペア数分 |
| 2-スイッチ | S0→S1→S2→S3, S0→S1→S2→S1... | さらに増加 |

### テストケース数の傾向

遷移が複雑になるほど、Nが大きいほどテストケース数は急増します。

| 状態数 | 遷移数 | 0-スイッチ | 1-スイッチ | 2-スイッチ |
|--------|--------|------------|------------|------------|
| 少ない | 少ない | 少ない | 中程度 | 多め |
| 多い | 多い | 多め | 多い | 非常に多い |

### 選定の目安

| 状況 | 推奨レベル |
|------|------------|
| リソースが限られる、基本確認 | 0-スイッチ |
| 一般的な業務システム | 0-スイッチ + 重要経路は1-スイッチ |
| 決済・認証などクリティカルな処理 | 1-スイッチ以上 |
| 医療・金融など高信頼性が求められる | 2-スイッチを検討 |
| 全パスを検証したい | 可能なら全経路（現実的でない場合も多い） |

### 1-スイッチのテストケース作成手順

```
1. 状態遷移図から、すべての「2連続遷移」を列挙
   例: (A→B) と (B→C) が連続 → パス A→B→C

2. 各パスについて、初期状態に至る手順を考える
   例: A→B→C をテストするには、まずAに到達する操作が必要

3. テストケースを設計
   前提条件 + 操作1（A→B） + 操作2（B→C） + 期待結果

4. 複数パスを1つのテストケースにまとめられる場合は統合
   例: A→B→C→D は、A→B→C と B→C→D の両方をカバー
```

### まとめ

| レベル | カバー対象 | 強度 | コスト |
|--------|------------|------|--------|
| 0-スイッチ | 全遷移 | 低 | 低 |
| 1-スイッチ | 全遷移ペア | 中 | 中 |
| 2-スイッチ | 3連続遷移 | 高 | 高 |
| N-スイッチ | N+1連続遷移 | より高 | より高 |

実務では**0-スイッチを必須**とし、重要経路（ログイン→操作→ログアウト、購入フロー全体など）に**1-スイッチ**を追加するのが現実的なバランスです。

## 📋 作成手順

```
1. 仕様から状態を洗い出す
2. 各状態間の遷移条件（イベント）を特定
3. 状態遷移図または状態遷移表を作成
4. 全遷移をリストアップ
5. 各遷移に対応するテストケースを作成
6. 異常系（想定外イベント）も検討
```

## ⚠️ 注意点

1. **並行状態**: 複数の状態が同時に成り立つ場合は、状態の分解やサブ状態の検討が必要。
2. **初期状態・終了状態**: 明確に定義する。
3. **異常系**: 不正なイベント、タイムアウトなどもテスト対象にする。

## 🔗 関連技法

- **デシジョンテーブル**: 状態とイベントの組み合わせを表で整理する場合に併用
- **ペアワイズ法**: 状態・イベント・前提条件の組み合わせを削減する場合に検討
