# 安全なWebアプリケーションの作り方（第23章）

ログインできたあとでも、「その人が、その操作やそのデータに触れてよいか」を毎回確かめないと、他人の情報が見えたり、管理者だけが使える機能を一般利用者に使われたりします。その仕組みが **認可（Authorization）** です。本章では、認可不備の典型例と、認可制御を要件としてどう定義するかを解説します。

| テーマ | 概要 |
|--------|------|
| **認可不備の典型例** | URL直打ち、ID改ざん、画面だけの制御、クライアント側の権限情報 |
| **認可制御の要件定義** | 誰が・何に・何をしてよいかを、サーバー側で必ず判定する設計 |

[[01_認証（徳丸本21章）|第21章]] は「誰か」を確かめる認証、[[07_アカウント管理（徳丸本22章）|第22章]] はアカウントのライフサイクルが中心でした。本章は、**認証後に「何をしてよいか」を決める認可** がポイントです。

---

## 📎 認可とは何か

**認可** とは、「今アクセスしている人が、その操作やそのデータに対して権限を持っているか」を判定し、許可または拒否する処理です。

| 用語 | 意味 | 例 |
|------|------|-----|
| **認証（Authentication）** | 「誰か」を確かめること | ログインして本人だと確認する |
| **認可（Authorization）** | 「何をしてよいか」を決めること | 自分の注文だけ見られる／管理者だけ削除できる |

認証と認可はセットで語られますが、別物です。

```
認証に成功した ＝ 「ログインできた」
認可に成功した ＝ 「その操作・そのデータに触れてよい」
```

ログインできても、**他人の注文履歴を見たり、管理者メニューを使ったりしてよいとは限りません**。認可は、その境界線を守る仕組みです。

### 日常生活での例え

- **認証**: 会社の入口で社員証を見せ、「社員本人です」と確認してもらう
- **認可**: 自分のデスクと自分のキャビネットだけ開ける（他の人の引き出しは開けられない）
- **認可不備**: 社員証さえあれば、誰のキャビネットでも番号を知っていれば開けられる状態

### なぜ危険か

認可が甘いと、次のような被害が出ます。

```
・他人の個人情報・注文・メッセージが見られる
・他人のデータを書き換え・削除される
・一般利用者なのに管理者機能を使える
・ログインしていないのに、URLを知っているだけで秘密情報が見られる
```

「ログイン画面を固めた」「メニューを隠した」だけでは足りません。**サーバーが、リクエストごとに権限を判定する** ことが本質です。

## 💥 認可不備の典型例

認可の不備は、画面上は正しく見えても、**URLやパラメータを少し変えるだけで突破できる** ことが多いです。代表的なパターンを整理します。

| 典型例 | 何が起きるか |
|--------|--------------|
| **URLを知っていると認証なしで閲覧できる** | ログイン不要の直リンクで秘密情報が見える |
| **IDを変更すると権限外の情報が参照できる** | 自分以外のデータのIDに書き換えて読める（IDOR） |
| **メニューの表示・非表示のみで制御している** | 画面は隠しているが、URL直打ちで機能が使える |
| **Hiddenやクッキーに権限情報を保持している** | クライアント側の値を改ざんして権限を上げられる |

---

### 情報リソースのURLを知っていると認証なしで情報が閲覧できる

「このURLを知っている人だけが見られる」という設計は、認可ではありません。URLは推測されたり、共有されたり、履歴やログに残ったりします。

```
【危険なイメージ】
https://example.com/reports/secret-2026.pdf

・ログイン不要
・URLを知っていれば誰でもダウンロードできる
・メール転送、ブラウザ履歴、Referer、ログからURLが漏れる
```

| なぜ起きるか | 説明 |
|--------------|------|
| **認証チェックがない** | 「ログインしているか」すら見ていない |
| **推測可能なURL** | 連番や日付など、当てやすいパスになっている |
| **秘密の共有にURLだけを使う** | 「URLが秘密」という前提が崩れやすい |

#### 対策の考え方

| 対策 | 説明 |
|------|------|
| **認証を必須にする** | ログインしていない利用者には見せない |
| **認可も必須にする** | ログイン済みでも、その人に閲覧権限があるか確認する |
| **推測困難なトークンだけでは足りない場合がある** | トークン付きURLは一時共有には使えるが、権限管理の代わりにはならない |

```
【安全なイメージ】
1. 利用者がログインしているか確認する
2. その利用者が、そのレポートを見てよいか確認する
3. 許可された場合だけファイルを返す
```

「URLが長いから大丈夫」は、認可の代わりになりません。**誰がアクセスしているかをサーバーが判定する** 必要があります。

---

### 情報リソースのIDを変更すると権限外の情報が参照できる

自分のデータの詳細画面で、URLやパラメータのIDを書き換えると、他人のデータが見えてしまう問題です。**IDOR（Insecure Direct Object Reference）** と呼ばれる典型的な認可不備です。

```
【危険なイメージ】
自分の注文: https://example.com/orders?id=1001
他人の注文: https://example.com/orders?id=1002  ← IDだけ変える

サーバーの処理:
SELECT * FROM orders WHERE id = 1002
→ 「今ログインしている人が、この注文の持ち主か」を見ていない
```

| なぜ起きるか | 説明 |
|--------------|------|
| **IDの存在確認だけしている** | 「そのIDのレコードがあるか」だけ見て、所有者を見ていない |
| **クライアントから渡されたIDを信じている** | URL・フォーム・JSONのIDをそのまま使う |
| **一覧は自分だけ、詳細は誰でも** | 一覧画面だけ絞り込み、詳細APIで認可を忘れている |

注文だけでなく、次のようなリソースでも同じです。

```
・ユーザープロフィール（/users/123）
・メッセージ（/messages/456）
・請求書・領収書（/invoices/789）
・アップロードしたファイル（/files/abc）
・APIのオブジェクト（GET /api/orders/1002）
```

#### 対策の考え方

| 対策 | 説明 |
|------|------|
| **所有者または権限を毎回確認する** | 「この注文は、今の利用者のものか」「閲覧権限があるか」 |
| **対象はセッションから決める** | 自分専用の一覧なら、ログイン中のユーザーIDで絞り込む |
| **クライアントのIDを信じない** | 渡されたIDは「候補」であり、権限チェック後にだけ使う |

```
【安全なイメージ】
1. セッションから「今ログインしている利用者」を特定する
2. リクエストの order_id を受け取る
3. その注文が、その利用者のものか（または閲覧権限があるか）をDB等で確認する
4. 権限がなければ 403 Forbidden（または存在を隠すなら 404）を返す
5. 権限がある場合だけデータを返す
```

[[07_アカウント管理（徳丸本22章）|第22章]] の「別ユーザーのパスワード変更」と同じ考え方です。**操作対象は、クライアントが指定したIDではなく、サーバーが権限付きで決める** のが基本です。

### メニューの表示・非表示のみで制御している

管理者メニューを一般利用者の画面に出さない、という実装だけでは不十分です。**画面を隠すこと** と **機能を使えないようにすること** は別問題です。

```
【危険なイメージ】
・一般利用者の画面には「ユーザー削除」ボタンを出さない
・しかし URL https://example.com/admin/users/delete?id=10 は生きている
・一般利用者がURLを直打ちすると、削除できてしまう
```

| なぜ起きるか | 説明 |
|--------------|------|
| **UIだけを制御している** | HTMLやJavaScriptでボタンを消しただけ |
| **サーバー側に認可がない** | リクエストが来たら、誰からのものでも処理してしまう |
| **「見えない＝使えない」と思い込む** | 攻撃者は画面を見なくてもURLやAPIを試す |

フロントエンド（ブラウザ側）の制御は、**使いやすさのためのもの** です。セキュリティの境界ではありません。

#### 対策の考え方

| 対策 | 説明 |
|------|------|
| **サーバー側で必ず認可する** | 管理機能のエンドポイントすべてで、管理者かどうかを確認する |
| **UI制御は補助** | メニュー非表示は誤操作防止やUXのため。権限の代わりにしない |
| **APIも同じルール** | 画面用URLだけでなく、裏側のAPIにも同じ認可を入れる |

```
【安全なイメージ】
1. /admin/... へのリクエストを受け取る
2. セッションから利用者を特定する
3. その利用者が管理者ロールを持つか確認する
4. 持っていなければ拒否する
5. 持っている場合だけ処理する
```

「ボタンを消したから安全」ではなく、**ボタンがなくてもリクエストが来たら拒否できるか** が認可の本質です。

---

### Hiddenパラメータやクッキーに権限情報を保持している

権限やロールを、HTMLの hidden フィールドやクッキーに入れて、サーバーがそれを信じると危険です。クライアント側の値は、利用者（攻撃者）が自由に書き換えられます。

```
【危険なイメージ】
<form action="/update" method="post">
  <input type="hidden" name="role" value="user">
  ...
</form>

攻撃者が role=admin に書き換えて送信
→ サーバーが「adminとして処理してよい」と判断してしまう
```

クッキーでも同様です。

```
【危険なイメージ】
Cookie: role=user

攻撃者が Cookie を role=admin に変更
→ 管理者機能が使える
```

| なぜ起きるか | 説明 |
|--------------|------|
| **クライアントを信頼している** | ブラウザから来た値を、権限の根拠にしている |
| **改ざん検知がない** | 署名やサーバー側照合がなく、値をそのまま信じている |
| **見た目の隠し方とセキュリティを混同している** | hidden は画面に見えないだけで、改ざんは簡単 |

#### 対策の考え方

| 対策 | 説明 |
|------|------|
| **権限はサーバー側で持つ** | DBやセッションに、利用者のロール・権限を保存する |
| **リクエストごとにサーバーで判定する** | クライアントから送られた role は使わない（無視する） |
| **どうしてもクライアントに載せるなら改ざん防止が必要** | 署名付きトークン等でも、最終判定はサーバー側の権限情報で行う |

```
【安全なイメージ】
1. ログイン時に、サーバー側セッションへ user_id と role を保存する
2. 以降のリクエストでは、セッションの user_id から権限を引く
3. フォームやクッキーの role は見ない（あっても無視する）
4. 操作ごとに、その権限で許可されるか判定する
```

「画面に出していないから安全」「クッキーに入れておけば便利」は、認可の根拠になりません。**権限の正は、サーバーが管理する情報** です。

## 📝 認可制御の要件定義

認可不備を防ぐには、実装の前に **「誰が・何に対して・何をしてよいか」** を要件として明確にします。ここが曖昧だと、画面ごとにチェックが抜けたり、APIだけ甘くなったりします。

### 要件定義で決めること

| 決める項目 | 内容 | 例 |
|------------|------|-----|
| **主体（誰が）** | 利用者の種類・ロール | 未ログイン、一般利用者、管理者 |
| **対象（何に）** | 守るリソース | 注文、プロフィール、管理画面、ファイル |
| **操作（何を）** | 許可する行為 | 閲覧、作成、更新、削除 |
| **判定の場所** | どこでチェックするか | **必ずサーバー側**（画面・API・バッチも含む） |
| **拒否時の振る舞い** | 権限がないときの応答 | ログイン画面へ誘導、403、404 など |

### 権限マトリクスの例

要件を表にすると、抜け漏れに気づきやすくなります。

| 操作＼主体 | 未ログイン | 一般利用者 | 管理者 |
|------------|------------|------------|--------|
| 商品一覧の閲覧 | ○ | ○ | ○ |
| 自分の注文の閲覧 | × | ○（自分のみ） | ○ |
| 他人の注文の閲覧 | × | × | ○ |
| 注文のキャンセル | × | ○（自分のみ） | ○ |
| ユーザー削除 | × | × | ○ |

「自分のみ」と書いた行は、**ログインしているだけでは不十分** で、対象リソースの所有者チェックが必要、という意味です。

### 要件として書いておくべき原則

```
認可制御の基本原則:

1. 認証と認可は別物として設計する
   （ログイン済みでも、権限がなければ拒否する）

2. 認可はサーバー側で、リクエストごとに行う
   （画面の表示制御だけでは不十分）

3. クライアントから送られた権限情報を信じない
   （role、isAdmin、user_id などをそのまま使わない）

4. すべての入口で同じルールを適用する
   （Web画面、API、管理ツール、バッチ処理）

5. デフォルトは拒否し、許可条件を明示する
   （書いていない操作はできない、が安全側）
```

### 実装に落とすときのチェックリスト

| チェック項目 | 確認すること |
|--------------|--------------|
| **認証が必要か** | 未ログインで触れてはいけない機能に、ログイン必須があるか |
| **ロールチェックがあるか** | 管理者専用機能で、管理者かどうかを見ているか |
| **所有者チェックがあるか** | 自分のデータだけ触る機能で、ID改ざんに耐えるか |
| **UI以外でも守れるか** | URL直打ち・API直接呼び出しでも拒否されるか |
| **拒否が統一されているか** | 権限なしのときに、意図したステータスと画面になるか |

### 要件定義の書き方の例

要件は、次のように具体的に書くと実装とテストに使えます。

```
【要件例】
・注文詳細の閲覧は、ログイン済みかつ、その注文の購入者本人、
  または管理者のみ可能とする
・一般利用者が他人の注文IDを指定した場合は、データを返さず拒否する
・管理者メニューおよび /admin 配下の全機能は、管理者ロールを持つ
  利用者のみ実行可能とする
・権限情報はサーバー側セッションまたはDBで管理し、
  リクエストパラメータやクッキーの値は権限判定に用いない
```

「管理者だけが使える」「自分のデータだけ」といった言葉は、**どのURL・どのAPI・どの操作か** まで落として初めて要件になります。

## 📋 まとめ

| テーマ | 本質 | 対策の要点 |
|--------|------|------------|
| **URL直打ちで閲覧できる** | URLを知っている＝権限、ではない | 認証＋認可をサーバーで行う |
| **ID改ざん（IDOR）** | リソースIDを信じすぎている | 所有者・権限を毎回確認する |
| **メニュー非表示のみ** | UI制御と認可を混同している | 全エンドポイントでサーバー側認可 |
| **Hidden・クッキーの権限** | クライアントの値を信じている | 権限の正はサーバー側で持つ |
| **要件定義** | 誰が・何に・何をしてよいかの曖昧さ | 権限マトリクスと原則を明文化する |

```
認可安全の基本:

1. 認証（誰か）と認可（何をしてよいか）を分けて設計する
2. 認可はサーバー側で、リクエストごとに必ず判定する
3. URLを知っていることや、画面にボタンが無いことを権限の根拠にしない
4. リソースIDは改ざんされる前提で、所有者・権限を確認する
5. Hiddenパラメータやクッキーの権限情報を信じない
6. 「誰が・何に・何をしてよいか」を要件として書き、全入口に同じルールを適用する
7. デフォルトは拒否し、許可条件だけを明示する
```

[[01_認証（徳丸本21章）|第21章]] とあわせて読むと、「ログインできた人」に対して「どこまで許すか」を、認証と認可の両面から整理できます。
