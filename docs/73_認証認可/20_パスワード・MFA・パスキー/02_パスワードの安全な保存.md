# パスワードの安全な保存（ハッシュ・ソルト・ストレッチング）

「なぜ暗号化ではなくハッシュか」「ソルトとストレッチングの考え方」は [[01_認証（徳丸本21章）]] にまとめました。ここでは **実際に何を選び、どう設定し、古い方式からどう移るか** を整理します。

---

## 🎯 結論：何を使うか

| 優先 | アルゴリズム | 推奨設定（OWASP の目安） | 使う場面 |
|------|------|------|------|
| 1 | **Argon2id** | メモリ 19 MiB・反復 2・並列 1 | 新しく作るなら第一候補 |
| 2 | **scrypt** | N=2^17・r=8・p=1 | Argon2 が使えない環境 |
| 3 | **bcrypt** | コスト 10 以上 | 古くからある実績重視の環境。**72 バイトまでしか使われない** 点に注意 |
| 4 | **PBKDF2**（HMAC-SHA-256） | 反復 600,000 回 | FIPS 準拠が必要なとき |

| 使ってはいけない | 理由 |
|------|------|
| 平文・可逆な暗号化 | DB と鍵が漏れれば全員分が分かる |
| MD5・SHA-1・SHA-256 を 1 回 | 速すぎる。GPU なら 1 秒に数十億回試せる |
| 自作の「SHA-256 を 1000 回」 | 回数が足りず、実装ミスも起きやすい。専用のアルゴリズムを使う |

**ポイント:** パスワード用ハッシュは **わざと遅く、メモリを多く使う** ように作られています。正規の利用者は 1 回計算するだけですが、攻撃者は何十億回も計算する必要があるので、その差で守ります。

---

## 🧂 ソルト・ペッパー・ストレッチングの役割

| 要素 | 中身 | どこに置くか | 防ぐもの |
|------|------|------|------|
| **ソルト** | 利用者ごとのランダム値（16 バイト以上） | ハッシュと一緒に DB に置く（秘密ではない） | レインボーテーブル、同じパスワードの利用者が一目で分かること |
| **ストレッチング** | 計算を重くする設定（コスト・反復・メモリ） | ハッシュ文字列の中に記録される | オフラインでの総当たり |
| **ペッパー**（任意） | 全員共通の秘密の値 | DB とは **別の場所**（環境変数・KMS・HSM） | DB だけが漏れた場合の解析 |

- Argon2・bcrypt・scrypt のライブラリは **ソルトを自動で作り、結果の文字列に含めます**。自分で管理する必要はありません。
- ペッパーは、HMAC で混ぜるか、ハッシュ結果を鍵で暗号化します。鍵を入れ替える手順も決めておく必要があるので、**ここまでは任意** です。

### 保存される文字列の例

```
$argon2id$v=19$m=19456,t=2,p=1$c29tZXNhbHQ$RdescudvJCsgt3ub+b+dWRWJTmaaJObG
 └ 方式 ─┘ └版┘ └─ コスト設定 ──┘ └ ソルト ┘ └──── ハッシュ値 ────┘
```

方式・設定・ソルトが文字列に含まれるので、**照合に必要な情報は 1 つの列にまとまります**。後で設定を強くしても、古い行は古い設定のまま照合できます。

---

## 💻 実装例（Node.js）

```javascript
import argon2 from 'argon2';

const OPTIONS = {
  type: argon2.argon2id,
  memoryCost: 19456, // KiB（= 19 MiB）
  timeCost: 2,
  parallelism: 1,
};

// 登録・パスワード変更時
export async function hashPassword(password) {
  return argon2.hash(password, OPTIONS);
}

// ログイン時
export async function verifyPassword(user, password) {
  const ok = await argon2.verify(user.passwordHash, password);
  if (!ok) return false;

  // 設定を強くした後なら、ログイン成功のタイミングで新しい設定に作り直す
  if (argon2.needsRehash(user.passwordHash, OPTIONS)) {
    user.passwordHash = await hashPassword(password);
    await user.save();
  }
  return true;
}
```

- 比較は必ずライブラリの `verify` を使います。`===` で文字列比較すると、処理時間の差から情報が漏れる（タイミング攻撃）ことがあります。
- 存在しないユーザーでもダミーのハッシュで `verify` を実行し、**応答時間でアカウントの有無が分からない** ようにします。

### コストの決め方

- 本番と同じ性能のサーバーで測り、**1 回の計算がおよそ 0.1〜0.5 秒** になる設定にします。
- 重くしすぎると、ログイン画面への大量アクセスでサーバーが止まります（DoS）。レート制限と一緒に考えます。

## 🔄 古い方式からの移行

MD5 や SHA-1 で保存してしまっている場合、元のパスワードが分からないので、すぐには作り直せません。2 つの方法を組み合わせます。

| 方法 | 内容 | 長所・短所 |
|------|------|------|
| **ログイン時に作り直す** | ログイン成功時に、入力された平文で Argon2id のハッシュを作り直す | 簡単。ただし、ログインしない利用者は古いまま残る |
| **包んで作り直す** | 今ある MD5 の値を入力にして `Argon2id(MD5(password))` を全件すぐに作る。照合時も同じ順で計算する | 全件をすぐ強くできる。どの方式で包んだかの印を持たせる |

```
1. 全件を Argon2id(旧ハッシュ) に置き換え、方式の列に "wrapped" と記録
2. ログイン成功時に Argon2id(平文) へ作り直し、"argon2id" に更新
3. 一定期間ログインのない利用者は、パスワードを無効にしてリセットしてもらう
```

## 📏 パスワードの受け付け方（NIST SP 800-63B）

保存方法とあわせて、**どんなパスワードを受け付けるか** も決めます。NIST の最新の指針（SP 800-63B Rev.4）の要点です。

| 項目 | 指針 |
|------|------|
| **最小の長さ** | パスワードだけで認証するなら 15 文字以上、MFA と組み合わせるなら 8 文字以上 |
| **最大の長さ** | 64 文字以上は受け付ける。空白・絵文字などすべての文字を許す |
| **文字種の組み合わせルール** | 「大文字・数字・記号を必ず入れる」のような強制はしない |
| **定期的な変更** | 強制しない。漏えいが分かったときだけ変更させる |
| **ブロックリスト** | よく使われるパスワード・漏えい済みのパスワード・サービス名を含むものを拒否する |
| **貼り付け** | パスワードマネージャーのために、貼り付けを許可する |

- 漏えい済みかどうかは、Have I Been Pwned の Pwned Passwords API で確かめられます。ハッシュの先頭 5 文字だけを送る方式なので、パスワードそのものは外に出ません。
- bcrypt を使う場合、72 バイトを超えた部分は無視されます。最大の長さを決めるか、Argon2id を選びます。

## ⚠️ よくある落とし穴

| 落とし穴 | 内容 |
|------|------|
| **ログに平文が残る** | リクエストボディをそのままログに出し、パスワードが残る。マスクする項目を決める（[[06_ログ出力（徳丸本24章）]]） |
| **パスワードをメールで送る** | 登録完了やリセットのメールに平文を書く。リセットは 1 回だけ使えるリンクで行う（[[03_パスワードリセット機能]]） |
| **「パスワードを表示」機能のためにとっておく** | 復号できる形で保存する理由にならない。利用者にはリセットしてもらう |
| **ハッシュ化をクライアント側だけで行う** | 送られてきたハッシュがそのままパスワードの代わりになる。サーバー側で必ずハッシュ化する |

---

## 📋 対策の優先順位

```
1. 平文・可逆暗号・高速ハッシュをやめ、Argon2id（または scrypt / bcrypt）で保存する
2. コストを本番環境で測って決め、needsRehash で順次強くする
3. 古いハッシュは「包んで作り直す」で全件すぐ強くする
4. 漏えい済みパスワードのブロックリスト・長さの指針を入れる
5. ペッパー（DB と別の場所に置く秘密）は余裕があれば追加
```

パスワードは「保存を正しくしても、使い回しやフィッシングには勝てない」仕組みです。根本的な対策は [[03_MFAの方式比較]] と [[04_パスキーとWebAuthn]] に続きます。
