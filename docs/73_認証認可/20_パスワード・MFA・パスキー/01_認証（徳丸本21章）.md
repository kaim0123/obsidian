# 安全なWebアプリケーションの作り方（第21章）

Webアプリの多くは、「この人は誰か」を確かめてから機能を使わせます。その仕組みが **認証（Authentication）** です。本章では、最も一般的な **パスワード認証** を中心に、ログイン機能への攻撃と対策、パスワードの保存方法、自動ログイン、ログインフォーム・エラーメッセージ・ログアウトの設計を解説します。

| テーマ | 概要 |
|--------|------|
| **ログイン機能への攻撃** | SQLインジェクション、パスワード試行、ソーシャルエンジニアリング、フィッシング |
| **パスワード認証の対策** | 予測困難なパスワード、アカウントロック、二段階認証など |
| **パスワードの保存方法** | 平文保存の危険、暗号化の課題、ハッシュ＋ソルト＋ストレッチング |
| **自動ログイン** | セッション延長・トークン・チケットの安全な実装 |
| **フォーム・エラー・ログアウト** | マスク表示、HTTPS、曖昧なエラー、POSTでのログアウト |

[[01_HTTPセッション管理（徳丸本1章）|第1章]] や [[01_セッション管理の不備（徳丸本9章）|第9章]] は「ログイン後の状態をどう保つか」が中心でした。本章は、**本人確認そのもの** と、**パスワードという秘密情報の扱い** がポイントです。

## 📎 認証とログイン機能の概要

**認証** とは、「今アクセスしている人が、主張どおりの本人である」ことを確かめる処理です。Webアプリでは、多くの場合 **ユーザーID（またはメールアドレス）とパスワード** の組み合わせで行います。

| 用語 | 意味 |
|------|------|
| **認証（Authentication）** | 「誰か」を確かめること（本人確認） |
| **認可（Authorization）** | 「何をしてよいか」を決めること（権限） |
| **ログイン** | 認証に成功し、以降のリクエストで本人として扱われる状態になること |
| **ログアウト** | ログイン状態を終わらせること |

認証と認可はセットで語られますが、別物です。「ログインできた」＝認証成功、「管理者メニューを開ける」＝認可の結果、というイメージです。

### 日常生活での例え

- **認証**: ホテルのフロントで身分証を見せ、「予約した本人です」と確認してもらう
- **認可**: 確認後、自分の部屋の鍵だけをもらう（他の部屋には入れない）
- **ログイン状態**: リストバンドを付けている間は、館内サービスを本人として使える
- **ログアウト**: リストバンドを返却し、本人扱いをやめる

### 本章で扱う主な機能

```
・ログイン機能（IDとパスワードの確認）
・パスワードの安全な保存
・自動ログイン（「ログイン状態を保持する」）
・ログインフォームとエラーメッセージ
・ログアウト機能
```

これらは一見当たり前の機能ですが、実装を誤ると **なりすまし** や **パスワード漏洩** につながります。

## 💥 ログイン機能に対する攻撃

ログイン画面は、攻撃者にとって「他人になりすます入口」です。代表的な攻撃を整理します。

| 攻撃 | 概要 |
|------|------|
| **SQLインジェクションによるバイパス** | ログイン判定のSQLを改ざんし、パスワードなしで通る |
| **SQLインジェクションによるパスワード入手** | DBからパスワード（やハッシュ）を抜き出す |
| **ログイン画面でのパスワード試行** | 何度もログインを試し、パスワードを当てる |
| **ソーシャルエンジニアリング** | 人をだましてパスワードを聞き出す |
| **フィッシング** | 偽サイトに誘導し、本物だと思わせて入力させる |

### SQLインジェクション攻撃によるログイン機能のバイパス

ログイン処理が、入力をそのままSQLに埋め込んでいると、**パスワードを知らなくてもログインできてしまう** ことがあります。

```
【危険なイメージ】
入力: ID = admin' --
SQL: SELECT * FROM users WHERE id='admin' --' AND password='...'
→ パスワード条件がコメントアウトされ、admin で通る
```

「パスワードが正しいか」を見る前に、SQLの意味が壊れてしまいます。詳細は [[03_SQL呼び出しに伴う脆弱性（徳丸本7章）|第7章]] を参照してください。

### SQLインジェクション攻撃によるパスワードの入手

バイパスだけでなく、SQLインジェクションで **ユーザーテーブル全体を読み出す** 攻撃もあります。平文や弱いハッシュで保存されていると、そのまま悪用されます。

### ログイン画面に対するパスワード試行

攻撃者が、ログイン画面から何度もパスワードを試す方法です。よくあるパスワード（`password`、`123456` など）や、辞書に載っている単語を順に試します。後述の辞書攻撃・パスワードスプレーなどがここに含まれます。

### ソーシャルエンジニアリングによるパスワード入手

技術的な脆弱性ではなく、**人をだます** 手法です。「サポートです。パスワードを教えてください」といった電話やメールで、本人から聞き出すイメージです。

### フィッシングによるパスワード入手

本物そっくりの偽ログイン画面を用意し、メールやSNSのリンクから誘導します。利用者が本物だと思って入力すると、攻撃者にパスワードが渡ります。

```
1. 攻撃者が偽のログインページを用意する
2. 「アカウント確認が必要です」などのメールでリンクを送る
3. 利用者が偽サイトでID・パスワードを入力する
4. 攻撃者がその情報で本物のサイトにログインする
```

### なぜ危険か

ログインを突破されると、攻撃者は **その利用者本人として** 操作できます。

```
・個人情報の閲覧・変更
・金銭やポイントの不正利用
・投稿・削除などの操作
・管理者アカウントなら、サービス全体の乗っ取り
```

## 🛡️ ログイン機能の基本対策

攻撃の入口は多様ですが、アプリ側でまず押さえるべき対策は次のとおりです。

### SQLインジェクションなどセキュリティバグをなくす

ログイン処理そのものに脆弱性があると、パスワードの強さとは無関係に突破されます。特に次は、ログイン周辺でよく問題になります。

| 脆弱性 | ログインとの関係 |
|--------|------------------|
| **SQLインジェクション** | 認証バイパスやパスワード漏洩 |
| **セッションIDの固定化** | ログイン後に攻撃者の用意したセッションを使わされる |
| **クッキーのSecure属性不備** | HTTPSでない通信でセッションIDが盗まれる |
| **オープンリダイレクト** | ログイン後の遷移先を偽サイトにし、フィッシングに悪用 |
| **HTTPヘッダ・インジェクション** | 応答ヘッダの改ざん、意図しないCookie設定など |

「パスワードを強くする」以前に、**認証まわりの実装バグをなくす** ことが前提です。セッション固定化は [[01_セッション管理の不備（徳丸本9章）|第9章]]、オープンリダイレクトは [[02_リダイレクト処理にまつわる脆弱性（徳丸本10章）|第10章]]、Cookieは [[02_クッキー出力にまつわる脆弱性（徳丸本11章）|第11章]] も参照してください。

### パスワードを予測困難なものにする

パスワード試行や漏洩後の悪用を難しくするため、**推測されにくいパスワード** を使わせます。

#### パスワードの文字種と桁数の要件

| 要件の例 | 意図 |
|----------|------|
| **十分な桁数**（例: 8文字以上、できればそれ以上） | 総当たりの組み合わせ数を増やす |
| **文字種の混在**（英大文字・小文字・数字・記号など） | 単純な単語だけのパスワードを減らす |

ただし、「記号を必ず1つ」などのルールだけでは、`Password1!` のような **パターン化された弱いパスワード** は防げません。桁数を長くする方が、効果が高いことが多いです。

#### 積極的なパスワードポリシーのチェック

登録・変更時に、次のようなチェックを行う考え方です。

```
・短すぎるパスワードを拒否する
・よくあるパスワード（password、123456 など）を拒否する
・漏洩パスワードリストに載っているものを拒否する
・ユーザーIDと同じ・似すぎるものを拒否する
```

「最低8文字で英数字混在」だけだと不十分なことがあるため、**既知の弱いパスワードを弾く** 積極的なチェックが有効です。

## 🔐 パスワード認証を狙った攻撃への対策

パスワードが正しくても、**何度も試せる** と突破される可能性があります。試行を制限する仕組みが必要です。

### 基本的なアカウントロック

同じアカウントに対して、短時間にログイン失敗が続いたら、一時的にログインを拒否する方式です。

```
【イメージ】
1. ユーザーAのパスワードを連続で間違える
2. 失敗が N 回に達する
3. 一定時間、ユーザーAへのログインをロックする
4. 時間経過後、または管理者が解除して再開
```

| メリット | 注意点 |
|----------|--------|
| 特定アカウントへの総当たりを止めやすい | 攻撃者がわざと失敗させ、正規ユーザーをロックアウトできる（DoS） |
| 実装が比較的わかりやすい | ロック条件・解除方法の設計が必要 |

### パスワード認証に対する攻撃のバリエーション

アカウントロックだけでは防ぎきれない攻撃パターンがあります。

| 攻撃名 | 内容 |
|--------|------|
| **辞書攻撃** | よく使われるパスワードのリストを順に試す |
| **ジョーアカウント探索** | `admin` / `admin` のように、IDとパスワードが同じ・単純なアカウントを探す |
| **リバースブルートフォース攻撃** | 1つのパスワードを、多数のIDに対して試す |
| **パスワードスプレー攻撃** | よくある少数のパスワードを、多数のアカウントに少しずつ試す（ロックを避ける） |
| **パスワードリスト攻撃** | 別サイトから漏洩した「IDとパスワードの組」を、そのまま試す（credential stuffing） |

#### 辞書攻撃

`password`、`qwerty`、`iloveyou` など、人間が選びがちなパスワードをまとめた辞書を使い、総当たりより効率よく当てます。

#### ジョーアカウント探索

IDとパスワードが同じ、または `test` / `test` のような雑なアカウントを探す攻撃です。開発用・検証用アカウントが本番に残っていると狙われます。

#### リバースブルートフォース攻撃

通常のブルートフォースは「1アカウントに対して多数のパスワード」です。リバースは逆で、**1つのパスワードを多数のアカウントに試す** 方式です。アカウントロックが「アカウント単位」だと、ロックされにくいことがあります。

#### パスワードスプレー攻撃

`Welcome1` や `Password1` など、よくあるパスワードを少数用意し、多くのアカウントに **ゆっくり** 試します。失敗回数が分散するため、単純なアカウントロックをすり抜けやすいです。

#### パスワードリスト攻撃

別サービスから漏洩した「メールアドレスとパスワード」のリストを使い、同じ組み合わせでログインを試みます。利用者が **パスワードを使い回している** と成功します。近年特に多い攻撃です。

### パスワードを狙った攻撃への対策

| 対策 | 効果 |
|------|------|
| **二段階認証（多要素認証）** | パスワードが漏れても、もう一つの要素がないとログインできない |
| **積極的なパスワードチェック** | 弱い・漏洩済みパスワードの登録を防ぐ |
| **ログイン失敗率の監視** | スプレー攻撃やリスト攻撃の兆候を検知し、追加対策やアラートにつなげる |
| **アカウントロック（適切に設計）** | 単一アカウントへの高速総当たりを抑止 |
| **パスワードの使い回し防止の啓発** | リスト攻撃の成功率を下げる |

```
【対策の重ね方のイメージ】
1. 実装バグ（SQLiなど）をなくす
2. 強いパスワードを促し、弱いものを拒否する
3. 試行を制限・監視する
4. 二段階認証で「パスワードだけ」に依存しない
```

二段階認証は、パスワードに加えて **スマホアプリのワンタイムコード** や **SMS**、**ハードウェアトークン** などを求める方式です。「知っているもの（パスワード）」に「持っているもの」を足すイメージです。

## 💾 パスワードの保存方法

サーバーは、ログイン時にパスワードを照合するため、何らかの形でパスワード情報を保持します。**平文のまま保存してはいけません。**

### パスワード保護の必要性

データベースが漏洩した場合でも、攻撃者がそのままログインできないようにするためです。保護が不十分だと、次のような悪用が起きます。

| 悪用 | 説明 |
|------|------|
| **パスワードリスト攻撃への悪用** | 漏洩したID・パスワードを、他サービスでも試される |
| **該当利用者の権限で使える機能の悪用** | なりすまして、その人だけができる操作を実行される |
| **データの投稿・更新・削除** | 本人の権限で、内容を書き換え・消される |

### 日常生活での例え

- **平文保存**: 金庫の暗証番号を、メモにそのまま書いて机に置く
- **適切な保護**: メモには「本人だけが再現できる形」だけを残し、元の番号は書かない

## 🔑 暗号化によるパスワード保護と課題

パスワードを暗号アルゴリズムで暗号化して保存する考え方です。一見よさそうですが、**パスワード保存には向かない** ことが多いです。

| 論点 | 内容 |
|------|------|
| **安全な暗号アルゴリズムの選定** | 古い・弱いアルゴリズムは使えない |
| **暗号化・復号処理の安全な実装** | 実装ミスで平文が漏れたり、改ざんされたりする |
| **鍵の生成** | 推測しやすい鍵では意味がない |
| **鍵の保管** | 鍵がDBと同じ場所にあると、DB漏洩時にまとめて復号される |

最大の課題は **復号できる** ことです。サーバーが復号できるなら、鍵を手に入れた攻撃者も復号できます。パスワード照合に必要なのは「入力が同じかどうか」であり、元のパスワードを取り出せる必要はありません。

```
【暗号化のイメージ】
保存: パスワード →（鍵で暗号化）→ 暗号文をDBへ
照合: 入力 →（同じ鍵で暗号化）→ DBの暗号文と比較
     または、暗号文を復号して入力と比較

→ どちらも「鍵」が弱点になる
```

そのため、パスワード保存の定石は暗号化ではなく、次に説明する **メッセージダイジェスト（ハッシュ）** です。

## #️⃣ メッセージダイジェストによるパスワード保護

### メッセージダイジェストとは

**メッセージダイジェスト（ハッシュ値）** とは、入力データから計算した、固定長の要約値です。代表的な性質は次のとおりです。

| 性質 | 意味 |
|------|------|
| **一方向性** | ハッシュから元のパスワードを簡単には戻せない |
| **決定性** | 同じ入力なら、いつも同じハッシュになる |
| **入力が少し違うと大きく変わる** | 1文字違うだけで、見た目が全く違う値になる |

パスワード保存では、MD5やSHA-1のような高速な汎用ハッシュをそのまま使うのは推奨されません。パスワード向けには **bcrypt**、**scrypt**、**Argon2** などの専用アルゴリズムが使われます。

### メッセージダイジェストを用いてパスワードを保護する

```
【登録時】
1. 利用者がパスワードを入力
2. サーバーがハッシュを計算
3. ハッシュだけをDBに保存（元パスワードは捨てる）

【ログイン時】
1. 利用者がパスワードを入力
2. 同じ方法でハッシュを計算
3. DB上のハッシュと比較し、一致すれば認証成功
```

元パスワードがDBに無いので、DBが漏れても **すぐにはパスワードが分からない** のが利点です。ただし、ハッシュだけでは不十分な攻撃もあります。

### ハッシュに対する攻撃

| 攻撃 | 内容 |
|------|------|
| **オンラインブルートフォース攻撃** | ログイン画面経由で、実際にログインを試し続ける |
| **レインボーテーブル** | よくあるパスワードのハッシュを事前計算した巨大な表で、ハッシュからパスワードを逆引きする |
| **ユーザーDB内にパスワード辞書を作られる** | 漏洩したハッシュを、攻撃者の手元で辞書や総当たりで解析する（オフライン攻撃） |

オンライン攻撃はアカウントロックや監視で抑えられます。一方、DBが漏洩したあとの **オフライン攻撃** は、攻撃者の計算機リソース次第で高速に試行できるため、ハッシュの作り方が重要です。

### ハッシュ解読対策の考え方：ソルトとストレッチング

| 対策 | 内容 | 効果 |
|------|------|------|
| **ソルト（salt）** | ユーザーごとに異なるランダム値をパスワードに足してからハッシュする | 同じパスワードでもハッシュが異なり、レインボーテーブルが使いにくい |
| **ストレッチング** | ハッシュ計算を何千・何万回と繰り返す（または意図的に遅いアルゴリズムを使う） | オフライン総当たりの速度を落とす |

```
【ソルト付きハッシュのイメージ】
保存するもの:
  ・ソルト（平文でよい。秘密ではない）
  ・ハッシュ(ソルト + パスワード)

照合:
  入力パスワードと、保存してあるソルトで同じ計算をし、ハッシュを比較
```

```
【ストレッチングのイメージ】
hash = H(password)
hash = H(hash)
hash = H(hash)
... を多数回繰り返す

→ 1回の照合が重くなるので、攻撃者の試行回数も減る
```

現代的なパスワードハッシュ（bcrypt、Argon2など）は、ソルトとコスト（遅さ）の考え方を組み込んでいます。自前でSHA-256を何度も回すより、**実績のあるパスワード用ライブラリを使う** 方が安全です。

## 🔄 自動ログイン

「ログイン状態を保持する」にチェックを入れると、ブラウザを閉じてもログインしたままになる機能です。便利な一方、**端末を他人に使われたときのリスク** や、**トークン漏洩時のなりすまし** に注意が必要です。

### 自動ログインの安全な実装方法

代表的な方式は次の3つです。

| 方式 | 概要 |
|------|------|
| **セッションの寿命を伸ばす** | 通常より長いセッションタイムアウトにする |
| **トークンを使う** | ログイン状態を示すトークンをCookieなどに持ち、サーバー側で検証する |
| **チケットを使う** | 認証チケットを発行し、それで自動ログインする |

### セッションの寿命を伸ばす方式

通常のセッションはブラウザ終了や短時間で切れますが、自動ログインでは寿命を延ばします。PHPの例では、`session_set_cookie_params` でセッションIDクッキーの **Expires** を設定します。

```
【実装のポイント（イメージ）】
・セッションタイムアウトを1週間などに伸ばす
・セッションIDクッキーのExpires属性を1週間後に設定する
・タイムアウト時間はセッション変数 Timeout に保持する
・タイムアウト時刻はセッション変数 Expires に保持する
```

| 項目 | 役割 |
|------|------|
| **Timeout** | 「何秒（何日）で切るか」という長さ |
| **Expires** | 「いつ切れるか」という時刻 |

単純でわかりやすい一方、**セッションIDが長い間有効** になるため、盗まれたときの被害期間が長くなります。また、サーバー側のセッション保存が増えることもあります。

### トークンによる自動ログイン

セッションとは別に、**自動ログイン用トークン** を発行する方式です。

```
【ログイン時】
1. 通常どおり認証する
2. 十分な長さのランダムなトークンを生成する
3. トークン（のハッシュ）をサーバー側DBに保存する
4. トークンをCookieなどにセットする（Secure、HttpOnly など適切な属性）

【次回アクセス時】
1. セッションが切れていても、トークンCookieがあれば読む
2. DB上のトークンと照合する
3. 正しければ、その利用者としてセッションを開始する（自動ログイン）

【ログアウト時】
1. 通常のセッションを破棄する
2. 自動ログイン用トークンもDBから削除（または無効化）する
3. クライアント側のトークンCookieも削除する
```

トークンは **推測困難なランダム値** にし、可能ならDBにはハッシュだけを保存します。漏洩時に備え、トークンの定期的な再発行や、端末ごとの管理も有効です。

### 認証チケットによる自動ログイン

認証チケットは、トークンと同様に「この人は以前ログイン済み」と示す証明書のようなデータです。署名付きのデータをクライアントに持たせる方式など、実装には幅があります。本書の文脈では、**サーバー側で検証可能なチケット／トークンを用いる自動ログイン** として理解するとよいです。

クライアントだけで完結する「改ざん可能な覚え書き」だけに頼ると危険です。**サーバー側で正当性を検証できる** ことが重要です。

### トークン方式のメリット

| メリット | 説明 |
|----------|------|
| **自動ログインを選ばない利用者に影響しない** | 通常セッションの寿命を全体で延ばさなくてよい |
| **複数端末から一斉ログアウトできる** | サーバー側のトークンをまとめて無効化すればよい |
| **管理者が特定利用者のログインをキャンセルできる** | DB上のトークンを消す・無効にする |
| **クライアント側に秘密情報が渡らない設計にできる** | パスワード自体は送らず、トークンだけを持つ。解析されてもパスワードは出ない |

セッション寿命を全体で延ばす方式より、**制御しやすく、影響範囲を限定しやすい** のがトークン方式の利点です。

## 📝 ログインフォーム

ログイン画面の作り方にも、基本的な注意点があります。

| 要件 | 理由 |
|------|------|
| **パスワード入力欄はマスク表示** | 肩越しに読まれる（ショルダーハッキング）を防ぐ。HTMLでは `type="password"` |
| **HTTPSを利用** | 通信経路での盗聴・改ざんを防ぐ。パスワードやセッションIDの平文送信を避ける |

```
【良い例のイメージ】
<form method="post" action="/login">
  <input type="text" name="id">
  <input type="password" name="password">
  <button type="submit">ログイン</button>
</form>
→ ページ全体をHTTPSで提供する
```

マスク表示は「画面上で見えない」だけなので、端末にキーロガーがある場合などは防げません。あくまで基本的な保護です。HTTPSは、ログインページだけでなく、**ログイン後の全ページ** でも使うのが安全です（セッションIDの保護）。

## ⚠️ エラーメッセージの要件

ログイン失敗時のメッセージは、**攻撃者にヒントを与えすぎない** ことが重要です。

### IDとパスワードのどちらが間違いか分かるとまずい理由

```
【悪い例】
・「ユーザーIDが存在しません」
・「パスワードが違います」

【良い例】
・「ユーザーIDまたはパスワードが正しくありません」
```

悪い例だと、攻撃者は次のように情報を得られます。

| 分かること | 悪用 |
|------------|------|
| **IDが存在するかどうか** | 登録済みメールアドレスの洗い出し、ジョーアカウント探索の効率化 |
| **パスワードだけが違うこと** | そのIDに対するパスワード試行に集中できる |

エラーメッセージは、正規利用者には少し不便でも、**IDとパスワードのどちらが原因か分からない** 表現に統一します。パスワード再設定の有無などでIDの存在が分かる場合もあるため、そちらの設計もあわせて検討します。

## 🚪 ログアウト機能

ログアウトは、「もう本人として扱わない」ための処理です。実装が中途半端だと、**なりすましが続く** ことがあります。

| 要件 | 理由 |
|------|------|
| **POSTメソッドでリクエストする** | ログアウトはサーバー状態を変える副作用のある操作だから。`<a href="/logout">` のようなGETは、画像埋め込みやprefetchで意図せず実行されうる |
| **セッションを破棄する** | サーバー側のログイン状態を消す。Cookieを消すだけでは不十分な場合がある |
| **必要な場合はCSRF対策の対象とする** | 罠ページからログアウトさせ、利用者を妨害する（または再ログインを誘う）攻撃を防ぐ |

```
【ログアウト処理のイメージ】
1. POSTでログアウトを受け付ける（CSRFトークンを検証）
2. サーバー側セッションを破棄する
3. 自動ログイン用トークンがあれば無効化する
4. クライアント側のセッションCookie・トークンCookieを削除する
5. ログイン画面などへ誘導する
```

「画面上はログイン前に戻ったように見えるが、セッションIDはまだ有効」という状態は危険です。**サーバー側でセッションを確実に破棄する** ことが本質です。CSRFの詳細は [[01_CSRF（徳丸本8章）|第8章]] を参照してください。

## 📋 まとめ

| テーマ | 本質 | 対策の要点 |
|--------|------|------------|
| **ログインへの攻撃** | なりすましの入口になる | SQLi等のバグ除去、試行制限、二段階認証 |
| **パスワードポリシー** | 弱いパスワードは当てられる | 十分な長さ、弱い・漏洩済みパスワードの拒否 |
| **パスワード保存** | DB漏洩時に悪用される | パスワード用ハッシュ＋ソルト＋ストレッチング（暗号化は非推奨） |
| **自動ログイン** | 長期のなりすましリスク | トークン方式が制御しやすい。ログアウトで無効化 |
| **フォーム・エラー** | 漏洩と情報収集を助ける | マスク、HTTPS、曖昧なエラーメッセージ |
| **ログアウト** | ログイン状態の終了 | POST、セッション破棄、必要ならCSRF対策 |

```
認証安全の基本:

1. ログイン処理の脆弱性（SQLi、セッション固定化など）をなくす
2. 予測困難なパスワードを促し、弱いものを拒否する
3. 試行の制限・監視と、可能なら二段階認証を入れる
4. パスワードは専用ハッシュ（ソルト＋コスト）で保存し、平文や単純な暗号化は使わない
5. 自動ログインはトークン等で制御し、ログアウトで確実に無効化する
6. フォームはHTTPSとマスク表示、エラーはID/パスワードを区別しない
7. ログアウトはPOSTで行い、サーバー側セッションを破棄する
```
