# MFA の方式比較

MFA（多要素認証）は、パスワードが漏れてもログインされないための仕組みです。ただし **方式によって防げる攻撃が大きく違います**。ここでは方式ごとの強さと選び方を整理します。TOTP・SMS の実装コードは [[04_二要素認証（2FA）機能]] にあります。

---

## 🧩 認証の 3 要素

| 要素 | 例 | 弱点 |
|------|------|------|
| **知識**（知っているもの） | パスワード、PIN、秘密の質問 | 漏えい・推測・使い回し |
| **所持**（持っているもの） | スマホ、セキュリティキー、IC カード | 紛失・盗難・SIM の乗っ取り |
| **生体**（本人そのもの） | 指紋、顔 | 変更できない。端末の中で使うのが基本 |

- **多要素** は「別の種類の要素」を組み合わせることです。パスワード + 秘密の質問は、どちらも知識要素なので多要素ではありません。
- パスキーの指紋・顔認証は、生体情報をサーバーに送りません。**端末（所持）のロックを外すためだけ** に使います。

---

## 📊 方式の比較

| 方式 | フィッシングへの耐性 | 主な攻撃 | 利用者の手間 | 導入コスト |
|------|:------:|------|------|------|
| **SMS のワンタイムコード** | ✕ | SIM スワップ、偽サイトでのコードの横取り、SMS の盗み見 | 少ない | 送信料がかかる |
| **メールのワンタイムコード** | ✕ | メールアカウントの乗っ取り、横取り | 少ない | 安い |
| **TOTP**（認証アプリ） | ✕ | 偽サイトで入力させて横取り | 普通 | 安い |
| **プッシュ通知で承認** | △ | 通知を大量に送り、うっかり承認させる（MFA 疲れ） | 少ない | 製品が必要 |
| **プッシュ + 番号の照合** | △ | 偽サイトで表示された番号をそのまま入れさせる | 普通 | 製品が必要 |
| **セキュリティキー**（FIDO2） | ◎ | 物理的な盗難 | 普通（キーを持ち歩く） | キーの配布 |
| **パスキー**（FIDO2） | ◎ | 端末やクラウドのアカウントの乗っ取り | 少ない | 安い |

**ポイント:** ワンタイムコードは「人が画面に打ち込む」ので、**偽サイトに打ち込んでも気づけません**。FIDO2（セキュリティキー・パスキー）だけは、ブラウザが **接続先のドメイン** を確かめてから署名するので、偽サイトでは使えません。

---

## 🎣 MFA を突破する攻撃

| 攻撃 | 手口 | 効く方式 | 対策 |
|------|------|------|------|
| **中間者フィッシング**（AiTM） | 偽サイトが本物のサイトへの中継役になり、パスワードとコードを入力させ、**ログイン後のセッション Cookie を盗む** | SMS・メール・TOTP・プッシュ | FIDO2 にする |
| **MFA 疲れ** | パスワードを入手した攻撃者が承認通知を大量に送り、うっかり「承認」させる | プッシュ | 番号の照合、通知回数の制限、身に覚えのない通知を報告させる |
| **SIM スワップ** | 携帯会社をだまして電話番号を自分の SIM に移す | SMS | SMS を MFA に使わない |
| **ヘルプデスクへのなりすまし** | 「スマホをなくした」とサポートに連絡し、MFA を外してもらう | すべて | 回復の手続きを厳しくする（下の表） |
| **セッションの乗っ取り** | MFA の後に発行された Cookie やトークンを盗む | すべて（FIDO2 でも） | セッションの寿命・端末との結び付け・異常検知（[[MOC_セッション管理]]） |

2026 年の具体的な事例は [[04_二要素認証（2FA）機能]] の追記にまとめています。

## 🧭 選び方

| 対象 | 推奨 |
|------|------|
| **管理者・開発者・経理など、権限の強い人** | セキュリティキーかパスキーを **必須** にする |
| **社員全体** | パスキー（または FIDO2 対応の認証製品）。移行するまでは番号の照合つきのプッシュ |
| **一般の利用者（BtoC）** | パスキーを勧め、TOTP も選べるようにする。SMS は最後の手段 |
| **規制がある業種** | 金融庁や業界の指針で、フィッシングに強い方式が求められているか確認する |

NIST の指針（SP 800-63B）でも、SMS の利用は **制限付き** の扱いで、より強い方式への移行が勧められています。

---

## 🔁 回復手段の設計（いちばん弱いところ）

MFA の強さは、**MFA を外す手続きの強さ** で決まります。強い方式を入れても、回復がメール 1 通で済むなら、攻撃者はそちらを狙います。

| 手段 | 注意点 |
|------|------|
| **バックアップコード** | 1 回ずつしか使えない。ハッシュで保存する。使ったら通知する |
| **2 つ目のセキュリティキー・パスキー** | 登録時に 2 つ以上の登録を勧める |
| **サポートによる本人確認** | 社員なら上長の承認やビデオ通話での確認。電話だけで外さない |
| **待ち時間を置く** | MFA の解除やメールアドレスの変更は、すぐ反映せず、元の連絡先に通知して数日待つ（[[07_アカウント管理（徳丸本22章）]]） |

---

## ⬆️ 追加の確認（ステップアップ認証）

ログイン時だけでなく、**危険な操作の直前** にもう一度確認する設計です。

- 対象：送金、パスワード・メールアドレスの変更、MFA の解除、管理画面の操作
- 普段と違う国・端末・時間帯からのアクセスでだけ MFA を求める **リスクベース認証** と組み合わせると、手間を減らせます。

---

## 📋 対策の優先順位

```
1. 権限の強いアカウントから、FIDO2（セキュリティキー・パスキー）を必須にする
2. プッシュ方式なら番号の照合と回数制限を入れる。SMS はやめていく
3. 回復手段（バックアップコード・サポートの手続き）を MFA と同じ強さにする
4. 危険な操作の前にステップアップ認証をする
5. MFA の後のセッションも守る（寿命・異常検知）
```

## 発展：認証の3要素とパスワードポリシー（ネットワーク機器の管理も含めて）

認証の3要素と MFA の定義、混同しやすい用語（SSO など）、パスワードの管理方針を基礎から整理します。

### 認証の3要素

**認証**とは「あなたは本当にその人か」を確認することです。確認に使う情報は3種類に分けられます。

| 要素 | 英語のイメージ | 例 |
|---|---|---|
| 知識 | Something you **know**（知っているもの） | パスワード、PIN、秘密の質問の答え |
| 所持 | Something you **have**（持っているもの） | スマートフォン（ワンタイムコードのアプリ）、ICカード、ハードウェアのセキュリティキー、証明書の入った端末 |
| 生体 | Something you **are**（本人の身体的な特徴） | 指紋、顔、静脈、虹彩 |

ICカード、スマートフォン、ハードウェアのセキュリティキーは**所持**の要素です。

### 多要素認証（MFA）

**多要素認証（MFA: Multi-Factor Authentication）**は、**異なる種類**の要素を2つ以上組み合わせる認証です。

```
パスワード（知識） ＋ スマホのワンタイムコード（所持）   → 多要素（MFA）◯
パスワード（知識） ＋ 指紋（生体）                       → 多要素（MFA）◯
パスワード（知識） ＋ 秘密の質問（知識）                 → 同じ種類が2つ ＝ 多要素ではない ✕
```

「パスワードを入力した後に、スマートフォンのアプリに表示されるワンタイムコードの入力も求める」方式は、知識＋所持の組み合わせなので**多要素認証（MFA）**です。パスワードが漏れても、攻撃者がスマートフォンを持っていなければログインできません。

混同しやすい用語:

| 用語 | 意味 | MFAとの違い |
|---|---|---|
| シングルサインオン（SSO） | **一度の認証**で複数のシステムを利用できるようにする仕組み | 「認証の回数を減らす」仕組みで、要素の数とは関係ない |
| パスワードの複雑化 | パスワードを長く、推測しにくくするルール | パスワードという**1つの要素**だけの対策 |
| ACLによるアクセス制御 | IPアドレスなどの条件で通信を許可・拒否 | **ユーザーの認証方式ではない** |

パスワードの**代わり**になる認証方式としては、**証明書**（デジタル証明書による認証）や**生体認証**があります。

### パスワードの管理方針（パスワードポリシー）

パスワードの管理方針として正しいのは「十分な長さの推測されにくいパスワードにし、他のシステムと使い回さない」です。理由を一つずつ理解しておきましょう。

| 方針 | 正しいか | 理由 |
|---|---|---|
| 十分な長さ・推測されにくい・使い回さない | ◯ | **長さは強度に大きく影響**する（総当たりの組み合わせ数が指数的に増える）。使い回すと、1か所で漏れたときに他も突破される |
| 覚えやすい短い単語や誕生日 | ✕ | **辞書攻撃**や推測で簡単に突破される |
| すべての機器で同じパスワード | ✕ | 1台のパスワードが漏れると、**すべての機器に侵入**されてしまう |
| 紙に書いて機器に貼る | ✕ | 機器に近づいた人に知られてしまう（物理セキュリティの問題） |

長さが効く理由の目安（使える文字が英大小文字＋数字の62種類の場合）:

```
 8文字: 62^8  ≒ 2.2 × 10^14 通り
12文字: 62^12 ≒ 3.2 × 10^21 通り   ← 4文字増えるだけで約1,400万倍
```

パスワードだけに頼らない工夫:

- **MFA、証明書、生体認証**を組み合わせる。
- 多数の機器のアカウントは**AAAサーバで一元管理**する（[[07_AAA（RADIUS・TACACS+・802.1X）]]）。退職者のアカウントの無効化なども1か所で確実に行える。
- 機器側では最小文字数の強制（`security passwords min-length`）、ログイン試行の制限（`login block-for`）も使える（[[06_ネットワーク機器への管理アクセス（パスワード・SSH・ファイル転送）]]）。

### ひっかけポイント・よくある誤解

- **SSOはMFAではない**。SSOは一度の認証で複数システムを使えるようにする仕組み。
- **パスワードの複雑化は1要素だけの対策**であり、MFAではない。
- **パスワード＋秘密の質問はMFAではない**（どちらも知識）。
- ICカードやスマートフォンは「所持」。「どの要素にも当てはまらない」は誤り。
- ACLはユーザーの認証方式ではない。
- 「覚えやすさ」「管理の簡単さ」を理由にした短いパスワード・共通パスワード・貼り紙はすべて誤り。

### 押さえておくポイント

- 認証の3要素：**知識・所持・生体**。MFAは**異なる種類**を2つ以上。
- ワンタイムコードのアプリ（スマホ）＝所持。
- パスワードは長く、推測されにくく、使い回さない。
- パスワードの代替・追加：MFA、証明書、生体認証。多数の機器はAAAで一元管理。
