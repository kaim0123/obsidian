# 安全なWebアプリケーションの作り方（第22章）

ログインできたあとでも、**アカウントそのものをどう作る・変える・止める・消すか** を誤ると、なりすましや乗っ取りにつながります。本章では、ユーザー登録からパスワード変更・メールアドレス変更・パスワードリセット、アカウントの停止・削除まで、アカウント管理機能の設計と、そこに生じやすい脆弱性を解説します。

| テーマ | 概要 |
|--------|------|
| **ユーザー登録** | メール受信確認、ID重複防止、自動登録対策、パスワードの注意 |
| **パスワードの変更** | 現在パスワードの確認、メール通知、CSRF・権限まわりの脆弱性 |
| **メールアドレスの変更** | 乗っ取り経路になりやすい変更処理と、受信確認・再認証・通知 |
| **パスワードリセット** | 本人確認と、新しいパスワードの安全な届け方 |
| **アカウントの停止・削除** | 不正利用への対応と、退会時のデータの扱い |

[[01_認証（徳丸本21章）|第21章]] は「ログイン時の本人確認」が中心でした。本章は、**アカウントのライフサイクル全体**（作る・直す・止める・消す）がポイントです。

## 📎 アカウント管理の概要

**アカウント管理** とは、利用者がサービスを使い続けるための「身分」を、安全に作成・変更・無効化・削除する一連の機能です。

| 機能 | 何をするか |
|------|------------|
| **ユーザー登録** | 新しいアカウントを作る |
| **パスワード変更** | ログイン済み利用者が自分のパスワードを変える |
| **メールアドレス変更** | 連絡先・ログインIDとして使うメールを変える |
| **パスワードリセット** | パスワードを忘れたときに、本人確認のうえで再設定する |
| **アカウント停止** | 不正利用などで、一時的または恒久的に使えなくする |
| **アカウント削除** | 退会などにより、アカウントを消す（または使えなくする） |

### 日常生活での例え

- **登録**: 会員証を新規発行する（本人の連絡先を確認してから）
- **パスワード変更**: 自分でロッカーの暗証番号を変える（今の番号を知っている人だけが変えられる）
- **メール変更**: 会員証の連絡先を書き換える（新しい住所が本当に届くか確認する）
- **リセット**: 暗証番号を忘れたとき、身分証を見せて再設定する
- **停止・削除**: 不正利用で会員証を一時停止する／退会して破棄する

### なぜ危険か

アカウント管理の機能は、どれも **「誰のアカウントを、どう変えるか」** に関わります。実装を誤ると、次のような被害が出ます。

```
・他人のアカウントを勝手に作る・乗っ取る
・パスワードやメールアドレスを勝手に変更される
・パスワードを忘れたふりをして、他人のアカウントを奪う
・退会したつもりでもデータや権限が残る
```

「ログイン画面だけ固めれば十分」ではなく、**登録・変更・リセット・停止・削除** も同じくらい重要です。

## 📝 ユーザー登録

ユーザー登録は、サービスに新しいアカウントを作る入口です。ここでは特に、**メールアドレスの受信確認**、**IDの重複防止**、**自動登録への対処**、**パスワードの扱い**、そして登録処理に起きやすい脆弱性を整理します。

### メールアドレスの受信確認

登録時に入力されたメールアドレスが、**本当にその人のものか** を確かめる処理です。確認しないと、他人のメールアドレスで勝手に登録されたり、連絡が届かないアカウントが増えたりします。

代表的な方法は次の2つです。

| 方式 | 流れ |
|------|------|
| **方式A（URL方式）** | メールに **トークン付きURL** を送り、利用者がそのURLを開くと登録（または有効化）が続く |
| **方式B（トークン入力方式）** | メールアドレス入力後、トークン入力画面へ進む。トークンは指定メールに送られ、画面に入力して確認する |

```
【方式Aのイメージ】
1. 利用者がメールアドレスなどを入力して登録申請
2. サーバーが推測困難なトークンを発行し、メールにURLを載せて送る
   例: https://example.com/verify?token=a8f3...（長いランダム値）
3. 利用者がメール内のURLをクリック
4. サーバーがトークンを検証し、メールアドレスを確認済みにする

【方式Bのイメージ】
1. 利用者がメールアドレスなどを入力
2. トークン入力画面を表示し、同時にメールでトークン（例: 6桁のコード）を送る
3. 利用者がメールを見て、画面にトークンを入力
4. サーバーが一致を確認し、メールアドレスを確認済みにする
```

トークンは **推測困難なランダム値** にし、有効期限を付け、一度使ったら無効化するのが基本です。

### メールの受信確認方法A・Bのメリット・デメリット

| 観点 | 方式A（URL） | 方式B（トークン入力） |
|------|--------------|------------------------|
| **操作の簡単さ** | リンクを押すだけで済むことが多い | メールを見て手入力が必要 |
| **メールクライアントの影響** | プレビューや自動リンクチェックで、意図せずURLが開かれることがある | URLを踏まないので、その種の誤作動は起きにくい |
| **フィッシングとの見分け** | 偽サイトへの誘導リンクと紛らわしい場合がある | 「コードを入力する」形なので、URL誘導型と少し性質が違う |
| **実装のイメージ** | トークンをURLパラメータやパスに載せる | セッション等と紐づけた入力画面が必要 |
| **モバイルでの使いやすさ** | メールアプリからそのまま開ける | メールとブラウザを行き来して入力する手間がある |

どちらが絶対に正しい、というわけではありません。**誤クリックで確認が完了してしまうリスク** を抑えたい場合は方式Bが有利なことがあります。一方、**利用者の手間を減らしたい** 場合は方式Aが選ばれやすいです。いずれにしても、トークンの推測困難さ・有効期限・使い捨てが重要です。

### ユーザーIDの重複防止

同じユーザーID（またはログイン用メールアドレス）が二重に登録されると、後から登録した人が先のアカウントを上書きしたり、ログインできなくなったりする事故につながります。

| 対策 | 説明 |
|------|------|
| **DBの一意制約** | ユーザーID列に UNIQUE 制約を付け、DBレベルで二重登録を防ぐ |
| **登録前の存在チェック** | アプリ側でも「既に使われているか」を確認する（ただしチェックとINSERTの間に競合がありうる） |
| **一意制約を最終防衛線にする** | アプリのチェックだけでは不十分なため、**DBの制約が本命** |

```
【危険なイメージ】
同時に2人が同じIDで登録ボタンを押す
→ どちらも「未使用」と判定
→ 両方INSERTされ、データが壊れる／後勝ちで上書きされる

【安全なイメージ】
UNIQUE制約があるため、後から来たINSERTは失敗する
→ アプリはエラーを返し、重複登録を防ぐ
```

「画面でチェックしたから大丈夫」ではなく、**データベース側で一意であることを保証する** のが基本です。

### ユーザーの自動登録への対処

攻撃者やボットが、スクリプトで大量にアカウントを作る行為です。迷惑メールの踏み台、不正投稿、在庫の買い占め、リソースの浪費などに使われます。

| 対策 | 説明 |
|------|------|
| **CAPTCHA等のボット対策** | 人間かどうかを確認する（完全ではないが抑止になる） |
| **メール受信確認の必須化** | 実在するメールを持たないと有効なアカウントにならない |
| **登録レート制限** | 同一IP・同一時間あたりの登録回数を制限する |
| **監視と停止** | 不審な登録パターンを検知し、アカウント停止につなげる |

メール確認だけでは、捨てアド（使い捨てメール）で大量登録されることもあります。重要サービスでは、レート制限や追加の本人確認も検討します。

### パスワードに関する注意

登録時に決めるパスワードは、[[01_認証（徳丸本21章）|第21章]] と同じ考え方がそのまま当てはまります。

| 注意点 | 理由 |
|--------|------|
| **十分な長さ・複雑さ（または長さ重視のポリシー）** | 総当たりや辞書攻撃に耐えるため |
| **弱い・漏洩済みパスワードの拒否** | よく使われるパスワードは最初から狙われる |
| **平文で保存しない** | DB漏洩時にそのまま悪用される |
| **パスワード用ハッシュ＋ソルト＋ストレッチング** | 専用のパスワードハッシュで保存する |

登録フォームでも、パスワード入力欄はマスク表示し、通信はHTTPSで行います。

### ユーザー登録に生じやすい脆弱性

#### SQLインジェクション脆弱性

登録処理で、入力値をそのままSQLに埋め込んでいると、DBの改ざんや情報漏洩が起きます。

```
【危険なイメージ】
入力されたユーザー名やメールを文字列連結でINSERT
→ 攻撃者がSQLを注入し、別テーブルを読む・管理者権限を付ける、など
```

対策は [[03_SQL呼び出しに伴う脆弱性（徳丸本7章）|第7章]] と同様で、**プレースホルダ（バインド）を使う** ことです。

#### メールヘッダ・インジェクション脆弱性

登録完了メールなどを送るとき、宛先や件名に利用者の入力をそのままヘッダへ埋め込んでいると、**追加のヘッダや本文を注入** されることがあります。

```
【危険なイメージ】
宛先や件名に改行（\r\n）を含められる
→ Bcc: attacker@example.com のようなヘッダが追加される
→ 迷惑メールの踏み台にされる／想定外の宛先にメールが送られる
```

| 対策 | 説明 |
|------|------|
| **改行を拒否する** | メールアドレスや件名に `\r` / `\n` を含めない |
| **メール送信用ライブラリを正しく使う** | ヘッダを自分で文字列連結しない |
| **宛先はサーバー側で確定する** | 利用者入力を「To:」にそのまま載せない設計にする |

メールを送る機能がある登録処理では、SQLインジェクションだけでなく、**メールヘッダ・インジェクション** も必ず意識します。詳細はメール送信まわりの章（メールヘッダ・インジェクション）も参照してください。

## 🔑 パスワードの変更

ログイン済みの利用者が、自分のパスワードを新しいものに変える機能です。「ログインできている＝本人」と思い込みがちですが、**セッションが盗まれている場合** や **CSRF** では、本人以外が変更できてしまいます。

### 現在のパスワードを確認すること

パスワード変更の前に、**今のパスワードをもう一度入力させる** のが基本です。

| 理由 | 説明 |
|------|------|
| **なりすましの抑止** | セッションを盗まれていても、現在のパスワードが分からなければ変更しにくい |
| **共有端末での誤操作・悪戯の抑止** | 席を離れたすきにパスワードを変えられるリスクを下げる |
| **重要な操作としての再認証** | パスワード変更はアカウントの鍵を変える操作なので、追加確認が妥当 |

```
【良い流れ】
1. ログイン済みである
2. 現在のパスワードを入力
3. 新しいパスワード（と確認入力）を入力
4. 現在のパスワードが正しければ更新
5. 可能ならメールで「パスワードが変更されました」と通知
```

現在パスワードの確認は、**再認証** の一種です。セッションがあるだけでは不十分、という考え方がポイントです。

### パスワード変更時のメール通知

パスワードが変わったことを、登録メールアドレスへ通知します。

| 目的 | 説明 |
|------|------|
| **本人への早期検知** | 身に覚えのない変更に気づける |
| **被害の拡大防止** | 気づいた利用者がサポートへ連絡したり、再リセットしたりできる |

通知メール自体に **新しいパスワードを書かない** ことが重要です。メールは途中経路や端末で読まれる可能性があるため、「変更があった事実」だけを伝え、必要なら公式のリセット手順へ誘導します。

### パスワード変更機能に生じやすい脆弱性

| 脆弱性 | 何が起きるか |
|--------|----------------|
| **SQLインジェクション** | 変更用SQLを改ざんされ、意図しない更新や情報漏洩が起きる |
| **CSRF脆弱性** | 罠サイト経由で、ログイン済み利用者のパスワードが勝手に変わる |
| **再認証の回避** | 現在パスワードなしで変更でき、セッション奪取だけで乗っ取り完了する |
| **別ユーザーのパスワード変更** | ユーザーIDを改ざんし、他人のパスワードを変えられる（権限・認可の不備） |
| **全ユーザーのパスワードを一斉に変更** | 更新条件の不備で、WHERE句が効かず全員分が書き換わる |

#### SQLインジェクション

パスワード更新のSQLに入力を連結していると、条件や更新内容を改ざんされます。プレースホルダで防ぎます。

#### CSRF脆弱性

利用者がログインしたまま罠ページを開くと、知らないうちにパスワード変更リクエストが送られることがあります。

```
【CSRFのイメージ】
1. 利用者が正規サイトにログイン中
2. 攻撃者のページを開く
3. 隠しフォーム等が /change-password にPOSTする
4. ブラウザが正規サイトへCookie付きでリクエストを送る
5. 現在パスワード確認やCSRFトークンが無いと、パスワードが変わる
```

対策は [[01_CSRF（徳丸本8章）|第8章]] のとおり、**CSRFトークン** の検証などです。パスワード変更は特に影響が大きいため、必ず対策対象にします。

#### 再認証を回避してパスワード変更

「ログインしていれば現在パスワードは不要」という実装は危険です。セッションハイジャックだけで、攻撃者が好きなパスワードに変え、正規利用者を締め出せます。**現在のパスワード確認（再認証）** を省略しないことが対策です。

#### 別ユーザーのパスワード変更

リクエストに含まれるユーザーIDを信じすぎると、他人のIDに書き換えてパスワードを変更できます。

```
【危険なイメージ】
POST /change-password
user_id=被害者のID
new_password=attacker-pass

→ サーバーが「今ログインしている人」ではなく、指定されたuser_idを更新してしまう
```

| 対策 | 説明 |
|------|------|
| **対象ユーザーはセッションから決める** | 「今ログインしている利用者自身」だけを更新する |
| **クライアントから渡すIDを信じない** | 隠れたフィールドの user_id は改ざんされる前提で扱う |

これはパスワード変更に限らず、**認可（この操作をしてよいか）** の基本です。

#### 全ユーザーのパスワードを一斉に変更

更新SQLのWHERE句が欠落していたり、条件が常に真になっていたりすると、**全ユーザーのパスワードが同じ値に更新される** 事故が起き得ます。

```
【危険なイメージ】
UPDATE users SET password = ?
（WHERE user_id = ? が無い）

→ 全行が同じパスワードハッシュになる
```

更新対象は **必ず当該ユーザー1件に限定** し、更新件数の確認（1件だけ更新されたか）も有効です。

## 📧 メールアドレスの変更

メールアドレスは、パスワードリセットや重要通知の届け先です。ここを乗っ取られると、**パスワードをリセットしてアカウント全体を奪う** ことができます。パスワード変更以上に慎重に扱うべき機能です。

### メールアドレス変更に対する攻撃

| 攻撃 | 概要 |
|------|------|
| **セッションハイジャック** | 盗んだセッションでメールアドレスを変更し、以降のリセット通知を攻撃者へ向ける |
| **CSRF攻撃** | 罠ページから、ログイン済み利用者のメールアドレスを勝手に変更する |
| **SQLインジェクション攻撃** | 変更処理のSQLを改ざんし、任意のユーザーのメールを書き換えるなど |

```
【乗っ取りの典型的な流れ】
1. セッションを盗む、またはCSRFでメール変更を実行させる
2. 被害者のメールアドレスを攻撃者のものに変える
3. 「パスワードを忘れた」でリセットメールを攻撃者が受け取る
4. パスワードを再設定し、アカウントを完全に掌握する
```

メールアドレスは「ただの連絡先」ではなく、**アカウント回復の鍵** です。

### メールアドレス変更に必要な機能的対策

| 対策 | 内容 |
|------|------|
| **新規メールアドレスに対する受信確認** | 新しいアドレスが本当に使える（その人のものである）ことを確認してから反映する |
| **再認証** | 現在のパスワード入力など、重要な操作としての追加確認 |
| **メール通知** | 変更があったことを、**変更前のメールアドレス** にも通知する |

#### 新規メールアドレスに対する受信確認

新しいアドレスへトークン付きURLや確認コードを送り、確認が取れるまでログイン用メールとしては有効化しない、という流れが安全です。確認前に切り替えてしまうと、打ち間違いや他人のアドレスへの変更がそのまま通ってしまいます。

#### 再認証

セッションがあるだけでは不十分です。パスワード変更と同様、**現在のパスワード確認** などを求め、セッション奪取だけではメールを変えられないようにします。

#### メール通知

変更後だけでなく、**変更前のアドレス** にも「メールアドレス変更の手続きがありました」と知らせます。身に覚えがなければ、利用者が異常に気づけます。通知に新しいパスワードやトークンを載せない点も、パスワード変更時と同じです。

```
【安全な変更のイメージ】
1. ログイン済み＋現在のパスワードで再認証
2. 新しいメールアドレスを入力
3. 新アドレスへ確認メール（トークン）を送る
4. 確認が取れたらメールアドレスを更新
5. 旧アドレス（と必要なら新アドレス）へ変更通知を送る
6. CSRFトークンも検証する
```

## 🔄 パスワードリセット

パスワードを忘れた利用者が、ログインできない状態からパスワードを再設定するための機能です。**本人確認が弱いと、他人がリセットしてアカウントを奪えます。**

### 利用者向けパスワードリセット機能

一般的な流れは次のとおりです。

```
1. 「パスワードを忘れた」画面で、登録メールアドレス（またはID）を入力
2. サーバーが本人確認用のトークンを発行し、登録メールへ送る
3. 利用者がメール内のURLを開く、またはコードを入力する
4. 本人確認できた場合のみ、新しいパスワードを設定できる
5. 設定後はトークンを無効化し、必要ならメールで完了通知する
```

「パスワードを忘れた」画面で、**そのメールアドレスが登録されているかどうか** をはっきり返すと、攻撃者のID洗い出しに使われます。可能なら、「入力された場合はメールを送りました（登録の有無は伝えません）」のように、応答を揃えます。

### 本人確認の方法

| 方法 | 説明 | 注意点 |
|------|------|--------|
| **登録メールへのトークン送付** | 最も一般的。メールを読める人＝アカウント所有者とみなす | メールアカウント自体の乗っ取りには弱い |
| **事前に設定した秘密の質問** | 質問と答えで本人確認する | 答えが推測・調査されやすく、現在は非推奨になりがち |
| **SMSや別チャネル** | 電話番号など別経路でコードを送る | コストやSIMスワップ等の別リスクがある |
| **サポートによる手動確認** | 身分確認書類などで対応** | 運用負荷となりすまし対応の手順が必要 |

Webアプリでは、**推測困難なトークンをメールで送り、有効期限内の一度きりで使う** 方式が基本です。トークンをURLに載せる場合は、HTTPS必須で、ログやReferer経由の漏洩にも注意します。

### パスワードの通知方法

リセット後に「新しいパスワードをどう伝えるか」も重要です。

| 方法 | 評価 | 説明 |
|------|------|------|
| **利用者が自分で新パスワードを設定する** | 推奨 | トークン確認後の画面で、新しいパスワードを入力させる |
| **仮パスワードをメールで送る** | 非推奨になりやすい | メール経路でパスワードが残る。使うなら初回ログインで強制変更 |
| **現在のパスワードをメールで教える** | 論外 | サーバーが平文パスワードを持っている前提になり、設計として誤り |

```
【推奨】
トークンで本人確認 → その場で新しいパスワードを設定
→ パスワードはメール本文に書かない

【避ける】
「あなたのパスワードは ○○○ です」とメールで送る
（保存方法が平文であることの証拠にもなる）
```

仮パスワードを使う場合でも、**十分に長いランダム値** にし、メール受信後すぐに変更させ、再利用できないようにします。可能なら最初から「自分で設定する方式」にします。

## 🛑 アカウントの停止

不正利用、利用規約違反、漏洩の疑いなどがあるとき、アカウントを **一時的または恒久的に使えなくする** 機能です。管理者向けの運用機能であることが多いですが、設計を誤ると正規利用者への妨害や、停止の回避につながります。

| 観点 | 内容 |
|------|------|
| **停止の効果** | ログイン不可、API利用不可、自動ログイン用トークンの無効化など、入口をすべて塞ぐ |
| **停止理由と記録** | いつ・誰が・なぜ停止したかを残し、誤停止に対応できるようにする |
| **解除手順** | 一時停止なら、本人確認のうえで解除する流れを決めておく |
| **通知** | 可能なら登録メールへ停止を通知し、身に覚えのない場合の問い合わせ先を示す |

```
【停止時にやるべきことのイメージ】
1. アカウントを「停止中」状態にする
2. 既存セッションを破棄する（ログイン中でも即座に無効）
3. 自動ログイン用トークンを無効化する
4. パスワードリセット等の回復手段を、方針に応じて制限または監視する
```

「画面上は止めているが、古いセッションではまだ操作できる」状態は不十分です。**認証・セッション・トークンをまとめて無効化** します。

パスワード試行の多発や、漏洩パスワードの利用検知などと組み合わせると、[[01_認証（徳丸本21章）|第21章]] のアカウントロックとも連携できます。ロック（一時的な試行制限）と、運用上のアカウント停止は目的が少し異なりますが、「使えなくする」点では近い考え方です。

## 🗑️ アカウントの削除

退会や、利用者本人・管理者による削除です。「消したつもり」でもデータや権限が残ると、プライバシーや不正利用の問題になります。

| 観点 | 内容 |
|------|------|
| **本人確認** | 退会は取り返しがつきにくい操作なので、再認証（パスワード確認など）を求める |
| **CSRF対策** | 罠ページから勝手に退会させられないようにする |
| **削除の意味の定義** | 物理削除か、論理削除（退会済みフラグ）か、関連データをどう扱うかを決める |
| **残すデータと消すデータ** | 法令・契約上残す必要があるログと、個人情報として消すべきものを分ける |
| **外部連携** | 外部サービスに渡したデータの削除・連携解除も必要なら行う |

```
【削除時のイメージ】
1. ログイン済み＋パスワード等で再認証
2. CSRFトークンを検証
3. アカウントを削除（または退会済みに更新）
4. セッション・自動ログイントークンをすべて無効化
5. 必要に応じて関連個人情報を削除または匿名化
6. 確認メールを送る（送れる場合）
```

「退会ボタンを押したら画面から消えただけ」では不十分です。**ログインできないこと**、**トークンが使えないこと**、**方針どおりデータが残らないこと** をセットで設計します。

論理削除（フラグで退会扱い）にする場合は、同じメールアドレスでの再登録ルール（すぐ再利用できるか、一定期間ダメか）も決めておくと、運用とセキュリティの両方で迷いにくくなります。

## 📋 まとめ

| テーマ | 本質 | 対策の要点 |
|--------|------|------------|
| **ユーザー登録** | 偽アカウント・自動登録・注入攻撃の入口 | メール確認、IDの一意制約、ボット対策、SQLi・メールヘッダインジェクション対策 |
| **パスワード変更** | 鍵の付け替え。セッション盗用やCSRFで奪われる | 現在パスワード確認、CSRF対策、自分のアカウントだけ更新、メール通知 |
| **メールアドレス変更** | 回復手段の乗っ取りにつながる | 新アドレスの受信確認、再認証、旧アドレスへの通知、CSRF・SQLi対策 |
| **パスワードリセット** | ログインできない人の本人確認 | 推測困難なトークン、有効期限と使い捨て、パスワードはメールで送らない |
| **アカウント停止** | 不正利用への緊急対応 | セッション・トークンまで無効化、記録と解除手順 |
| **アカウント削除** | 退会とデータの後始末 | 再認証、CSRF対策、削除範囲の明確化 |

```
アカウント管理安全の基本:

1. 登録時はメール受信確認とIDの一意性（DB制約）を確保する
2. 自動登録には確認メール・レート制限・ボット対策などで備える
3. パスワード変更は「現在のパスワード確認」＋CSRF対策＋自分自身のみ更新
4. メールアドレス変更は、新アドレス確認・再認証・旧アドレス通知をセットにする
5. パスワードリセットはトークンで本人確認し、新パスワードは自分で設定させる
6. 停止・削除ではセッションとトークンを確実に無効化する
7. 登録・変更系の処理ではSQLインジェクションとメールヘッダ・インジェクションを防ぐ
```

[[01_認証（徳丸本21章）|第21章]] とあわせて読むと、「ログインする」「アカウントを維持・回復する」両面から、なりすまし対策を整理できます。
