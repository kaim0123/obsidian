# モジュールと名前空間

## モジュールとは
関連するコード（関数・クラス・定数など）を**1つのまとまりにしたもの**。ファイル単位、パッケージ単位でまとめるのが一般的です。

### 目的
- **整理**: 機能ごとに分ける
- **再利用**: 他の場所でも読み込んで使える
- **隠蔽**: 内部実装を外から守る
- **名前衝突を防ぐ**: 同じ名前を別モジュールで使える

## 名前空間とは
名前（識別子）が**有効となる領域**のこと。モジュールはそれぞれ独自の名前空間を持ちます。
```
moduleA.foo()  // A の foo
moduleB.foo()  // B の foo（別物）
```

## 各言語のモジュール構文

### JavaScript (ESM)
```javascript
// math.js
export function add(a, b) { return a + b; }
export const PI = 3.14;
export default function multiply(a, b) { return a * b; }

// main.js
import multiply, { add, PI } from "./math.js";
```

### Python
```python
# math_utils.py
PI = 3.14
def add(a, b): return a + b

# main.py
import math_utils
from math_utils import add, PI as pi
```

### Java
```java
package com.example.utils;

public class MathUtils {
    public static int add(int a, int b) { return a + b; }
}

// 使う側
import com.example.utils.MathUtils;
```

### Rust
```rust
// lib.rs
pub mod math;

// math.rs
pub fn add(a: i32, b: i32) -> i32 { a + b }

// 使う側
use crate::math::add;
```

### Go
```go
package math_utils

func Add(a, b int) int { return a + b }

// 使う側
import "myapp/math_utils"
math_utils.Add(1, 2)
```

## importの形式

### 名前付きインポート
必要なものだけ取り出す。
```javascript
import { add, sub } from "./math.js";
```

### デフォルトインポート
モジュールが1つだけ「主役」をエクスポートしている時。
```javascript
import React from "react";
```

### ワイルドカードインポート
モジュール全体をオブジェクトとして取り込む。
```javascript
import * as math from "./math.js";
math.add(1, 2);
```

```python
from math import *   # 全公開シンボルを取り込む（非推奨）
```

### エイリアス
名前の衝突回避や簡略化。
```python
import numpy as np
```

## 公開と非公開

### 明示的に公開する（JS, Rust, Go）
- JS: `export` を付けたものだけ外へ
- Rust: `pub` を付けたものだけ
- Go: 大文字で始まる名前が公開

### すべて公開される（Python）
- Python: 慣習的にアンダースコア始まり（`_private`）は「内部用」とみなす

### Javaのアクセス修飾子
- `public` / `protected` / パッケージ（省略）/ `private`

## 名前空間の階層

### パッケージ / ディレクトリ構造
```
myapp/
  users/
    model.py
    service.py
  orders/
    model.py
    service.py
```
`users.model` と `orders.model` は同名でも区別される。

### 深いネストの注意
- 名前空間が深すぎると `import` が冗長
- エイリアスやバレルファイル（まとめエクスポート）で緩和
```javascript
// index.js（バレル）
export * from "./a.js";
export * from "./b.js";
```

## モジュール解決（Resolution）

### 相対パス
```
./utils/math.js
../shared/config.js
```

### 絶対パス / パッケージ名
- Node.js: `require("react")` → `node_modules` 内を探索
- Python: `sys.path` を順に探す
- Java: クラスパスで探す

### エイリアス設定（バンドラ）
```json
// tsconfig.json
{ "compilerOptions": {
    "paths": { "@/*": ["src/*"] }
}}
```

## 名前衝突の回避

### エイリアスで解決
```python
from foo import sort as foo_sort
from bar import sort as bar_sort
```

### 修飾アクセス
```javascript
import * as a from "./a.js";
import * as b from "./b.js";
a.process();  b.process();
```

## 循環参照
モジュールAがBを、BがAを呼ぶ状態。部分的に初期化されて不具合の原因に。

### 対策
- 共通部分を第3のモジュールに抽出
- インターフェース（抽象）を介する
- 動的 `require` / 遅延読み込み

## パッケージマネージャとの関係
モジュール単位で配布する時は、npm / pip / cargo / maven などのパッケージマネージャを通す。
- npm: `package.json` + `node_modules`
- pip: `pyproject.toml` / `requirements.txt`
- cargo: `Cargo.toml`
- maven: `pom.xml`

## 設計のコツ

### 高凝集・低結合
- モジュール内部: 密接に関係した機能だけ
- モジュール間: 依存は最小限に

### APIを最小に
外に公開するのは必要最小限。実装を隠蔽しておくと変更しやすい。

### ディレクトリ構造で意図を伝える
```
src/
  features/      # 機能単位
  shared/        # 共通ユーティリティ
  domain/        # ビジネスルール
```

## まとめ
- モジュールは**関連コードをまとめた単位**、名前空間は**名前が属する領域**
- 各言語ごとに `export` / `import` / `pub` / `package` などの構文が異なる
- **公開/非公開**を意識して外部APIを最小化
- **循環参照**や**深すぎるネスト**はリファクタリング対象
- パッケージマネージャを使えばチーム・外部と共有しやすい
