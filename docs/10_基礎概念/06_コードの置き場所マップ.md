# コードの置き場所マップ

## このノートの目的

教材のコードを実際に書くときに **「このコードはどのフォルダの、どのファイルに書くのか」** を1か所で引けるようにするためのノートです。

- 基準は **Next.js（App Router）＋ `src/` ＋ features 構成**（[[03-featuresフォルダ構成の一貫性|ATS8]] と同じ形）
- Vite + React（SPA）と Express（バックエンド）の違いは後半にまとめています
- 構成の「考え方」や方式の比較は [[01_ディレクトリ構成の方式比較]]、[[03_bulletproof-reactの構成]] を参照

> [!tip] 使い方
> 教材を読んでいて「これどこに書くの？」と思ったら、まず **§4 教材トピック別の置き場所** を見る。載っていなければ **§3 迷ったときの判断フロー** で決める。

## 1. 基準のディレクトリ構成（Next.js App Router）

```text
my-app/
├── public/                  # 画像・favicon など、そのまま配信する静的ファイル
├── src/
│   ├── app/                 # ルーティング（URL と 1:1）。ページの「入口」だけを書く
│   │   ├── layout.tsx       # 全ページ共通のレイアウト・Provider の設置
│   │   ├── page.tsx         # "/" のページ
│   │   ├── globals.css      # 全体 CSS（Tailwind の読み込み）
│   │   ├── candidates/
│   │   │   ├── page.tsx     # "/candidates"
│   │   │   ├── loading.tsx  # 読み込み中 UI
│   │   │   ├── error.tsx    # エラー UI
│   │   │   └── [id]/page.tsx  # "/candidates/123"
│   │   └── api/
│   │       └── candidates/route.ts   # Route Handler（API エンドポイント）
│   │
│   ├── features/            # 機能（ドメイン）ごとのまとまり ← コードの大半はここ
│   │   ├── candidates/
│   │   │   ├── components/  # この機能専用の UI
│   │   │   ├── hooks/       # この機能専用のカスタムフック
│   │   │   ├── api/         # この機能のデータ取得（fetch 関数・クエリ）
│   │   │   ├── actions.ts   # Server Actions（"use server"）
│   │   │   ├── schemas.ts   # Zod スキーマ（フォーム・API 入力の検証）
│   │   │   ├── store.ts     # この機能だけで使う状態ストア
│   │   │   ├── types.ts     # この機能専用の型
│   │   │   └── lib/         # この機能固有の計算・変換ロジック
│   │   └── shared/          # 複数 feature で使う型など
│   │
│   ├── components/          # 機能に依存しない共有 UI
│   │   ├── ui/              # Button, Input, Modal などの部品
│   │   └── layouts/         # Header, Sidebar など
│   ├── hooks/               # 機能に依存しない共有フック（useDebounce など）
│   ├── lib/                 # 外部ライブラリを「設定して」使える状態にしたもの
│   ├── stores/              # アプリ全体のグローバル状態
│   ├── utils/               # 純粋な小さい関数（日付整形・文字列変換など）
│   ├── types/               # 共有の型・*.d.ts
│   ├── config/              # 環境変数の読み込み・定数
│   ├── testing/             # テスト用のモック・ヘルパー（MSW のハンドラなど）
│   ├── middleware.ts        # 認証ガードなど（Next.js 16 以降は proxy.ts）
│   └── instrumentation.ts   # 計測・監視の初期化（OpenTelemetry など）
│
├── e2e/                     # Playwright の E2E テスト
├── .env.local               # 秘密情報（Git に入れない）
├── next.config.ts
├── tsconfig.json
├── vitest.config.ts
├── playwright.config.ts
├── eslint.config.mjs
└── package.json
```

> [!note] `src/` は任意
> `src/` を作らず `app/` をルートに置く構成もある。どちらでも中身の考え方は同じ。

## 2. フォルダの役割一覧

### よく混同する3つ：`lib/` ・ `utils/` ・ `hooks/`

| フォルダ | 何を置くか | 例 | 見分け方 |
|---|---|---|---|
| `lib/` | **外部ライブラリの初期化・設定済みインスタンス** | `lib/supabase/server.ts`、`lib/api-client.ts`（axios/ky の設定）、`lib/query-client.ts`、`lib/auth.ts`、`lib/prisma.ts` | 中で `import ... from "外部パッケージ"` して **設定してから export** している |
| `utils/` | **ライブラリに依存しない純粋な関数** | `utils/format-date.ts`、`utils/to-camel-case.ts` | 引数 → 戻り値だけ。どのプロジェクトにコピーしても動く |
| `hooks/` | **`use` で始まる React フック** | `hooks/use-debounce.ts`、`hooks/use-media-query.ts` | 中で `useState` / `useEffect` などを使っている |

> [!tip] ひとことで
> - **lib** ＝「道具を組み立てて置いておく場所」
> - **utils** ＝「小さな計算メモ」
> - **hooks** ＝「React の状態や副作用を使う関数」

### 共有か、機能専用か

| 置き場所 | 条件 |
|---|---|
| `features/〇〇/components/` | その機能の画面でしか使わない |
| `components/ui/` | どの機能でも使う、業務の言葉が出てこない部品 |
| `features/〇〇/types.ts` | その機能だけで使う型 |
| `features/shared/types.ts` または `types/` | 2つ以上の機能で使う型 |

**最初は機能の中に置き、2か所目で必要になったら共有フォルダへ移す**、が基本ルール。

### `app/` に書くもの・書かないもの

| 書く | 書かない |
|---|---|
| `page.tsx` / `layout.tsx` / `loading.tsx` / `error.tsx` / `route.ts` | 大きなコンポーネント本体、ビジネスロジック |
| features から import して並べるだけの薄いコード | 何度も使う関数 |

```tsx
// src/app/candidates/page.tsx — 入口は薄く
import { CandidateList } from "@/features/candidates/components/candidate-list";

export default function Page() {
  return <CandidateList />;
}
```

## 3. 迷ったときの判断フロー

```text
書こうとしているコードは…

① URL に対応するページ / API の入口？
   └ Yes → src/app/ 以下（page.tsx / route.ts）

② 外部ライブラリを初期化・設定するコード？（createClient, axios.create, new QueryClient …）
   └ Yes → src/lib/

③ 特定の機能（応募者・イベント…）に関係する？
   └ Yes → src/features/〇〇/ の中
          ├ UI → components/
          ├ use〇〇 → hooks/
          ├ fetch / クエリ → api/
          ├ "use server" → actions.ts
          ├ Zod → schemas.ts
          └ 型 → types.ts

④ どの機能にも属さない？
   ├ 見た目の部品 → src/components/ui/
   ├ use〇〇 → src/hooks/
   ├ 純粋な関数 → src/utils/
   ├ アプリ全体の状態 → src/stores/
   └ 型 → src/types/

⑤ ツールの設定ファイル？（〇〇.config.ts）
   └ Yes → プロジェクトのルート（package.json と同じ階層）
```

## 4. 教材トピック別の置き場所

教材フォルダごとに「そこで学ぶコードを実プロジェクトで書くならどこか」をまとめた表。

### 32_React

| 学ぶこと | 置き場所の例 |
|---|---|
| コンポーネント（JSX） | 機能専用 → `features/〇〇/components/candidate-card.tsx`<br>共有部品 → `components/ui/button.tsx` |
| カスタムフック | 機能専用 → `features/〇〇/hooks/use-candidates.ts`<br>汎用 → `hooks/use-debounce.ts` |
| useContext（Context と Provider） | 機能専用 → `features/〇〇/context.tsx`<br>アプリ全体（テーマ等）→ `components/providers/theme-provider.tsx`、設置は `app/layout.tsx` |
| ルーティング | Next.js → `app/` のフォルダ構造そのもの<br>Vite + React Router → `src/app/router.tsx`（§5） |
| エラーバウンダリ | Next.js → `app/〇〇/error.tsx`<br>汎用コンポーネント → `components/error-boundary.tsx` |
| フォーム実例 | `features/〇〇/components/〇〇-form.tsx` ＋ `features/〇〇/schemas.ts` |
| TypeScript の props 型 | 同じコンポーネントファイルの中に書く（外に出すのは複数ファイルで使うときだけ） |

### 36_状態管理

| ライブラリ / 種類 | 置き場所の例 |
|---|---|
| Zustand / Jotai（グローバル状態） | アプリ全体 → `stores/use-ui-store.ts`、`stores/atoms.ts`<br>機能専用 → `features/〇〇/store.ts` |
| Redux Toolkit | `stores/index.ts`（configureStore）＋ `features/〇〇/〇〇-slice.ts`、Provider は `app/providers.tsx` |
| TanStack Query / SWR（サーバー状態） | QueryClient の設定 → `lib/query-client.ts`<br>Provider → `app/providers.tsx`<br>各クエリ → `features/〇〇/api/get-candidates.ts`（`useCandidates` フックもここ） |
| React Hook Form（フォーム状態） | `features/〇〇/components/〇〇-form.tsx`、スキーマは `features/〇〇/schemas.ts` |
| URL 状態（searchParams） | 読む側のコンポーネント内。共通化するなら `features/〇〇/hooks/use-filter-params.ts` |
| XState（状態機械） | `features/〇〇/machines/〇〇-machine.ts` |
| ローカル状態（useState） | そのコンポーネントの中（外に出さない） |

### 37_HTTPクライアント・ユーティリティ

| 学ぶこと | 置き場所の例 |
|---|---|
| axios / ky / fetch ラッパーの共通設定（baseURL・ヘッダー・リトライ・タイムアウト） | `lib/api-client.ts` |
| 認証トークンの付与（インターセプター） | `lib/api-client.ts` の中 |
| エンドポイントごとの関数 | `features/〇〇/api/get-candidate.ts` |
| OpenAPI などから生成した型・クライアント | `types/api.generated.ts` または `lib/api/generated/`（自動生成なので手で編集しない） |
| date-fns / Lodash / es-toolkit を使った小関数 | `utils/format-date.ts` など |

### 33_Next.js

| 学ぶこと | 置き場所の例 |
|---|---|
| ページ・レイアウト | `app/〇〇/page.tsx`、`app/〇〇/layout.tsx` |
| Route Handler | `app/api/〇〇/route.ts` |
| Server Actions | `features/〇〇/actions.ts`（ページ専用なら `app/〇〇/actions.ts` も可） |
| Server / Client Component の境界 | `"use client"` のファイルは `features/〇〇/components/` に置き、`page.tsx` は Server Component のままにする |
| データ取得（サーバー側） | `features/〇〇/api/` に関数を置き、`page.tsx` から呼ぶ |
| middleware / proxy | `src/middleware.ts`（Next.js 16 以降は `src/proxy.ts`）。`app/` の中ではないので注意 |
| Supabase クライアント | `lib/supabase/server.ts`、`lib/supabase/client.ts`（→ [[07-Supabaseクライアントの重複]]） |

### 38_その他フレームワーク（Tailwind）

| 学ぶこと | 置き場所の例 |
|---|---|
| Tailwind の読み込み・テーマ変数 | `app/globals.css`（v4 は `@import "tailwindcss";` と `@theme` をここに書く） |
| 設定ファイル（v3 系） | ルートの `tailwind.config.ts` |
| クラス結合ヘルパー `cn()` | `lib/utils.ts`（shadcn/ui の慣習。`utils/cn.ts` でも可） |

### 73_認証認可 / 74_セッション管理

| 学ぶこと | 置き場所の例 |
|---|---|

| 未ログインのリダイレクト（認証ガード） | `src/middleware.ts`（→ [[01-認証ガードとmiddleware]]） |
| ログイン画面・フォーム | `app/login/page.tsx` ＋ `features/auth/components/login-form.tsx` |
| ログイン中ユーザーの取得 | `features/auth/api/get-current-user.ts` または `lib/auth.ts` |

| Route Handler 共通の認証チェック | `lib/api/with-auth.ts` のようなラッパー（→ [[08-RouteHandlerの認証チェック重複]]） |

| 種類 | 置き場所の例 |
|---|---|
| ユニット・コンポーネントテスト（Vitest + Testing Library） | **テスト対象の隣**：`candidate-card.tsx` → `candidate-card.test.tsx`<br>（まとめたい派は `__tests__/` フォルダ） |

| テスト用データ（ファクトリ） | `testing/factories/candidate.ts` |

### 24_TypeScript / 23_JavaScript

| 学ぶこと | 置き場所の例 |
|---|---|
| 共有の型 | `types/〇〇.ts`（機能専用なら `features/〇〇/types.ts`） |
| 宣言ファイル（`*.d.ts`）・型の拡張 | `types/global.d.ts`、`types/env.d.ts` |

| 学ぶこと | 置き場所の例 |
|---|---|

| Dockerfile | ルートの `Dockerfile`、`compose.yaml` |

## 5. Vite + React（SPA）の場合の違い

Next.js との違いは **「ルーティングを `app/` のフォルダで表さない」** ことだけ。`features/`、`components/`、`lib/` などの考え方は同じ。

```text
my-spa/
├── index.html               # エントリーの HTML（Vite はルートに置く）
├── src/
│   ├── main.tsx             # React を DOM にマウントする起点
│   ├── app/
│   │   ├── app.tsx          # ルートコンポーネント
│   │   ├── provider.tsx     # QueryClientProvider などをまとめる
│   │   ├── router.tsx       # React Router のルート定義
│   │   └── routes/          # 各ページ（Next.js の page.tsx に相当）
│   │       └── candidates.tsx
│   ├── features/  components/  hooks/  lib/  stores/  utils/  types/  testing/
│   └── index.css            # Tailwind の読み込み
├── vite.config.ts
└── .env                     # クライアントに出す値は VITE_ で始める
```

| Next.js | Vite + React |
|---|---|
| `app/candidates/page.tsx` | `src/app/routes/candidates.tsx` ＋ `router.tsx` に登録 |
| `app/layout.tsx` | `src/app/app.tsx`（レイアウト用ルートコンポーネント） |
| `app/api/〇〇/route.ts` | **なし**（API は別のバックエンドで作る → §6） |
| Server Actions / middleware | **なし** |
| `NEXT_PUBLIC_〇〇` | `VITE_〇〇` |

## 6. バックエンド（Express + Prisma）の場合

34_Backend の教材のコードはこの形を想定。**リクエストが入ってから DB に届くまでの順番** でフォルダが並ぶ。

```text
my-api/
├── prisma/
│   ├── schema.prisma        # DB のテーブル定義
│   ├── migrations/          # マイグレーション（自動生成）
│   └── seed.ts              # 初期データ（→ [[05_シード（乱数シードとDBシード）]]）
├── src/
│   ├── server.ts            # app.listen() する起点
│   ├── app.ts               # express() の生成・ミドルウェアの登録
│   ├── routes/              # URL とコントローラの対応
│   │   └── candidates.routes.ts
│   ├── controllers/         # req を受けて res を返す（薄く）
│   │   └── candidates.controller.ts
│   ├── services/            # ビジネスロジック本体
│   │   └── candidates.service.ts
│   ├── repositories/        # DB アクセス（Prisma の呼び出し）
│   │   └── candidates.repository.ts
│   ├── middlewares/         # 認証・ログ・エラーハンドラ
│   │   ├── auth.ts
│   │   └── error-handler.ts
│   ├── schemas/             # Zod によるリクエスト検証
│   ├── lib/                 # prisma.ts（PrismaClient）・logger.ts・redis.ts
│   ├── config/              # 環境変数の読み込み
│   └── types/               # Express の型拡張（express.d.ts）
├── tests/
└── .env
```

| 学ぶこと（34_Backend） | 置き場所 |
|---|---|
| ルーティング | `routes/` |
| ミドルウェア（認証・CORS・ログ） | `middlewares/`、登録は `app.ts` |
| バリデーション | `schemas/` ＋ `middlewares/validate.ts` |
| ビジネスロジック | `services/` |
| DB アクセス・ORM | `repositories/`、クライアントは `lib/prisma.ts` |
| エラー処理・ロギング | `middlewares/error-handler.ts`、`lib/logger.ts` |
| キャッシュ（Redis） | `lib/redis.ts`、使うのは `services/` |
| 外部 API 連携 | `lib/〇〇-client.ts`（Stripe など） |
| キュー・ジョブ | `jobs/` または `workers/` |

> [!note] 機能ごとに分ける書き方もある
> 規模が大きくなると `src/modules/candidates/{routes,controller,service,repository}.ts` のように **フロントエンドの features と同じ発想** で機能ごとにまとめることも多い。考え方は [[02_レイヤードアーキテクチャのモジュール構成]] を参照。

## 7. 命名のルール（迷ったらこれ）

| 対象 | ルール | 例 |
|---|---|---|
| ファイル名 | ケバブケース | `candidate-card.tsx`、`use-candidates.ts` |
| コンポーネント名（中身） | パスカルケース | `export function CandidateCard()` |
| フック | `use` で始める | `useCandidates` |
| テスト | 対象名 ＋ `.test` / `.spec` | `candidate-card.test.tsx` |
| Next.js の特殊ファイル | 決まった名前のみ | `page.tsx`、`layout.tsx`、`route.ts` |

> ファイル名をパスカルケース（`CandidateCard.tsx`）にするプロジェクトも多い。**どちらかに統一されていること** の方が大事。
