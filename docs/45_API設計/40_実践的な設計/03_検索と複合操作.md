# 検索と複合操作

## この章の目的

検索・一括操作・非同期ジョブなど、**CRUD だけでは表現しにくい操作** の設計を学ぶ章です。

---

## 1. 検索 API の設計（`?q=` と専用エンドポイント）

検索は REST の **クエリパラメータ** または **専用エンドポイント** で表現します。

| 方式 | 例 | 向いている場面 |
|------|-----|---------------|
| クエリ | `GET /products?q=python&category=book` | シンプルなキーワード検索 |
| コレクション + フィルタ | `GET /users?email=taro@example.com` | フィールド完全一致 |
| RPC 風 | `POST /products/search` + 複雑な JSON 条件 | 多条件・全文検索 |

```text
  シンプル  →  GET /products?q=keyword
  複雑      →  POST /search/products  { "filters": [...], "sort": ... }
```

**チームで方針を決め**、単純なものは GET、複雑なものだけ RPC 風にするなど線引きします。

---

## 2. バルク操作（一括作成・一括削除）

複数リソースをまとめて操作する **バルク API** です。

```http
POST /v1/users/bulk
Content-Type: application/json

{
  "items": [
    { "name": "田中", "email": "taro@example.com" },
    { "name": "佐藤", "email": "sato@example.com" }
  ]
}
```

| 設計のポイント | 内容 |
|---------------|------|
| 部分成功 | 一部失敗時は `207 Multi-Status` や結果配列で成功/失敗を返す |
| 上限 | 1 リクエストあたりの件数上限（例：100 件） |
| 冪等性 | 一括削除は DELETE + ボディ、または POST `/bulk-delete` |

REST だけでは表現しにくいが、**実務ではよく必要** になる操作です。

---

## 3. 非同期処理とジョブ API（202 Accepted）

時間のかかる処理（レポート生成、一括インポートなど）は **非同期** にします。

```text
  1. POST /jobs  →  202 Accepted  { "job_id": "job_abc" }
  2. GET  /jobs/job_abc  →  { "status": "running" | "completed" | "failed" }
  3. 完了時  →  結果 URL やダウンロードリンクを返す
```

| ステータス | 意味 |
|-----------|------|
| **202 Accepted** | リクエストは受理、処理は非同期で継続 |
| **200** | ジョブ状態の照会成功 |

```json
{
  "data": {
    "id": "job_abc",
    "status": "completed",
    "result_url": "/v1/exports/exp_123/download"
  }
}
```

## 4. ファイルアップロードの基本

JSON 以外の **ファイル** は `multipart/form-data` など別形式を使います。

```http
POST /v1/users/usr_123/avatar
Content-Type: multipart/form-data

（ファイルバイナリ + メタデータ）
```

| 方式 | 用途 |
|------|------|
| `multipart/form-data` | フォームからのファイルアップロード |
| 署名付き URL | クライアントが直接ストレージ（S3 等）へアップロード |
| Base64 in JSON | 小さいファイルのみ（大きいと非効率） |

大きなファイルは **専用のアップロードフロー** を設計し、API 本体とは分けることが多いです。

---

## 5. 「REST らしくないが必要な」操作の扱い方

承認・キャンセル・送信など、**動詞的な操作** は REST だけでは不自然になりがちです。

| パターン | 例 | コメント |
|----------|-----|----------|
| POST + サブリソース | `POST /orders/{id}/cancel` | **よく使われる実務的妥協** |
| PATCH で状態変更 | `PATCH /orders/{id}` `{ "status": "cancelled" }` | REST らしい |
| RPC 風 | `POST /orders/{id}/actions/cancel` | 操作が増えると整理しやすい |

```text
  原則: URL は名詞、操作はメソッド
  例外: 状態遷移・ワークフローは POST + サブリソース を許容
       │
       ▼
  ガイドラインに「例外的な操作の書き方」を明記する
```

**一貫した例外ルール** があれば、REST から多少外れても混乱は抑えられます。
