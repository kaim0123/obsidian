---

## 1. エンドポイント・リソース設計
- リソース指向（/users, /posts, /orders など）
- 名詞ベースのエンドポイント設計（動詞は使わない）
- 階層構造でリレーションを表現（/users/1/posts など）
- 一貫した命名規則（小文字・複数形推奨）

---

## 2. バージョニング
- APIの仕様変更時はバージョンを明示（/v1/users, /api/v2/… など）
- URLパス・ヘッダー・クエリパラメータでのバージョン管理
- 旧バージョンの互換性維持と段階的な廃止

---

## 3. エラー設計
- 一貫したエラーレスポンス形式（例：{ "error": { "code": 400, "message": "Bad Request" } }）
- 適切なHTTPステータスコードの選択
- バリデーションエラーや認証エラーの詳細なメッセージ
- エラーIDやトレースIDで障害調査を容易に

---

## 4. 認証・認可
- APIキー、OAuth2、JWTなどの認証方式
- 権限ごとのアクセス制御（RBAC, ABAC）
- HTTPS必須、CORS設定

---

## 5. ドキュメント化
- OpenAPI（Swagger）やAPI Blueprintで仕様を明文化
- サンプルリクエスト/レスポンス、エラー例も記載
- 自動生成ツールの活用（Swagger UI, Redoc など）

---

## 6. パフォーマンス・スケーラビリティ
- ページネーション、フィルタリング、ソートの設計
- レートリミット、キャッシュ制御（ETag, Cache-Control）
- 非同期処理やバルクAPIの検討

---

## 7. セキュリティ
- 入力値バリデーション、SQLインジェクション・XSS対策
- レートリミット、IP制限、監査ログ
- セキュリティヘッダー（CSP, HSTS, X-Frame-Options など）

---

## 8. アンチパターン
- 動詞ベースのエンドポイント（/getUser, /createOrder など）
- 一貫性のないレスポンス形式
- 過度なネストや巨大なレスポンス
- バージョン管理の欠如

---

API設計は「一貫性・拡張性・保守性・セキュリティ」を意識して行いましょう。
