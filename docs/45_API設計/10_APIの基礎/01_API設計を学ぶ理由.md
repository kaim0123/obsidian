# API設計を学ぶ理由

## この章の目的

API がプログラム同士の「窓口」として何を担うか、設計がないと何が起きるかを理解する章です。

---

## 1. プログラム同士の「窓口」としての API

**API（Application Programming Interface）** は、あるプログラムが別のプログラムの機能を使うための **約束された入口** です。

レストランに例えると、厨房（サーバー）の中身は見えませんが、**メニュー（API）** を通じて注文できます。

| 種類 | 誰が使うか | 例 |
|------|-----------|-----|
| ライブラリ API | 同じプログラム内 | `list.sort()` |
| OS API | アプリケーション | ファイルの読み書き |
| Web API | 別マシン上のプログラム | `GET /users` |

本教材では **Web API**（HTTP でデータをやり取りする API）を中心に扱います。

---

## 2. 「動く API」と「使われ続ける API」の違い

動く API は「リクエストを送れば何か返る」状態です。  
使われ続ける API は、**クライアント開発者が迷わず・壊さず・長く使える** 状態です。

| 観点 | 動く API | 使われ続ける API |
|------|---------|-----------------|
| 命名 | `/getUser` と `/users/list` が混在 | 全体で同じルール |
| エラー | 500 だけ返す | ステータス + 機械可読な code |
| 変更 | フィールド名を突然変更 | バージョンと後方互換を意識 |
| 権限 | 401 と 403 が曖昧 | 認証・認可が明確 |

```text
  動く API  →  自分だけ使うなら一時的に足りる
  使われ続ける API  →  チーム・外部・将来の自分のために設計が必要
```

---

## 3. 設計がないと起きること

設計なしで API を増やすと、次の問題が積み上がります。

- **命名のバラバラ** — エンドポイントごとにルールが違う
- **破壊的変更** — フィールド削除でクライアントが一斉に壊れる
- **クライアントの混乱** — ドキュメントを読んでも「この API だけ違う」がある

```text
  設計なしで API 追加
       │
       ├─→ クライアント側の共通処理が書けない
       ├─→ レビュー基準がない
       └─→ レガシー API が増える
               │
               ▼
         開発速度の低下
```

## 4. 本書の読み方と前提知識

### 前提知識

- クライアント・サーバーの基本
- JSON の読み書き
- 1 つの言語で Web アプリやスクリプトを書いた経験

### 読み方

1. **10〜20** — なぜ・原則・HTTP の基礎
2. **30** — REST とリソース設計（設計の中心）
3. **40〜60** — エラー・互換性・セキュリティ
4. **70〜80** — ドキュメント・運用・他のAPIスタイル
5. **85** — ケーススタディで統合
