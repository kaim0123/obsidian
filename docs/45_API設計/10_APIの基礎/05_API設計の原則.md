# API設計の原則

## この章の目的

一貫性を支える **設計の考え方** — 予測可能性、契約、クライアント体験 — を学ぶ章です。

---

## 1. 予測可能性 — ドキュメントなしでも「だいたい当たりがつく」

**予測可能性（Predictability）** とは、1 つの API を理解すれば、他も **同じパターン** で推測できる状態です。

| 予測可能 | 予測不可能 |
|----------|-----------|
| `GET /users`, `GET /orders` で同じレスポンス構造 | エンドポイントごとに JSON の形が違う |
| エラーは常に `{ "error": { "code": ... } }` | ある API は文字列、ある API は配列 |
| 作成は常に `POST` + `201` | ある API は `POST /createUser` |

```text
  予測可能な API  →  学習コスト低・SDK 化しやすい
  予測不可能な API  →  毎回ドキュメント必読・バグの温床
```

---

## 2. 最小の驚き（Principle of Least Astonishment）

**最小の驚きの原則** — 利用者が **直感的（intuitive）** に期待する動きに合わせる、という考え方です。

| 驚きが少ない | 驚きが大きい |
|-------------|-------------|
| `DELETE /users/123` で削除 | `GET /users/123/delete` で削除 |
| 404 = 存在しない | 404 = 権限不足（403 の方が自然） |
| `created_at` は作成日時 | `created_at` が文字列 `"不明"` を返す |

```text
  「一般的な Web API の常識」から大きく外れる設計
       │
       ▼
  クライアント開発者の混乱・バグ・問い合わせ増
```

REST や HTTP の慣習から **意図的に外れる** ときは、理由をドキュメントに明記します。

---

## 3. 契約（Contract）としての API

API は **契約（Contract）** です。サーバーとクライアントの間で「こう送れば、こう返す」と約束します。

| 契約の要素 | 内容 |
|-----------|------|
| URL・メソッド | どこに、何をするか |
| リクエスト形式 | 必須フィールド、型 |
| レスポンス形式 | 成功・失敗時の JSON 構造 |
| ステータスコード | 結果の種類 |
| 後方互換性 | 変更してよい範囲（[[02_後方互換性]]） |

```text
  サーバー ──契約（API）── クライアント
              │
              破るとクライアントが壊れる
```

OpenAPI などで契約を **機械可読** にすると、テスト・レビューに活かせます（[[01_OpenAPIとドキュメント]]）。

---

## 4. クライアント開発者の体験を想像する

API 設計は **サーバー側の都合だけ** で決めると使いにくくなります。

### 想像すべきクライアント

| クライアント | 設計で気をつけること |
|-------------|---------------------|
| ブラウザ（SPA） | CORS、トークン管理 |
| モバイルアプリ | 古いバージョンが長期間残る、オフライン |
| 他サーバー | 安定性、レート制限、冪等性 |
| 管理画面 | 一覧・フィルタ・ページネーション |

```text
  「自分がこの API を使う側だったら？」
       │
       ▼
  命名・エラー・ページネーションの判断が変わる
```

[[01_API設計を学ぶ理由]]でも触れたように、API 設計は **橋渡し** の仕事です。

---

## 5. 設計判断の優先順位のつけ方

すべてを一度に完璧にしようとせず、**優先順位** をつけます。

| 優先度 | 項目 | 理由 |
|--------|------|------|
| 高 | 一貫性・REST 基本・エラー形式 | 後から直すと全体に波及 |
| 高 | 認証・HTTPS | セキュリティは最初から |
| 中 | ページネーション・バージョニング | データが増えてから必要 |
| 中 | OpenAPI ドキュメント | チームが増えたら必須 |
| 低（最初は） | HATEOAS など発展的 REST | 基本が固まってから |

```text
  小さく公開 → 利用フィードバック → ガイドライン更新
```

[[03_APIの進化と運用]]「API の進化と運用」でも、**最初から完璧は不要** という視点を扱います。
