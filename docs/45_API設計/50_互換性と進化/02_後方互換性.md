# 後方互換性

## この章の目的

変更しても古いクライアントが壊れない「安全な変更」と、バージョンアップが必要な「破壊的変更」を見分ける章です。

---

## 1. 後方互換性とは何か

**後方互換性（Backward Compatibility）** とは、**サーバー側を更新しても、古いクライアントがそのまま動く** 状態のことです。

```text
  サーバー v1.1 に更新
       │
       ├─→ 古いクライアント（v1 契約）  →  動く ✅
       └─→ 新しいクライアント（v1 契約）  →  動く ✅
```

API の契約は **暗黙の約束** です。「この JSON に `name` がある」とクライアントは信頼しています。

---

## 2. 安全な変更（フィールド追加・新エンドポイント）

一般に **安全** とされる変更です。

| 変更 | なぜ安全か | 例 |
|------|-----------|-----|
| 任意フィールドの追加 | 古いクライアントは無視できる | `"avatar_url"` を追加 |
| 新エンドポイント追加 | 既存 URL に影響なし | `POST /v1/users/{id}/avatar` |
| 新クエリパラメータ | 指定しなければ従来どおり | `?sort=created_at` |
| レスポンスに null 許容フィールド | パースは成功する | `"bio": null` |

```json
// v1.0 のレスポンス
{"id": 1, "name": "太郎"}

// v1.1 — フィールド追加（後方互換）
{"id": 1, "name": "太郎", "avatar_url": "https://..."}
```

---

## 3. 破壊的変更（削除・リネーム・型変更・必須化）

次は **破壊的変更** です。古いクライアントが壊れる可能性が高いです。

| 変更 | 問題 | 例 |
|------|------|-----|
| フィールド削除 | 参照で undefined / 例外 | `name` を削除 |
| リネーム | 古い名前で読めない | `user_id` → `id` |
| 型変更 | パース失敗 | `"price": "1000"` → `1000` |
| 任意→必須 | 送信しないクライアントが 422 | 更新時に `email` 必須化 |
| ステータスコード変更 | 分岐ロジックが狂う | 404 → 403 |

```json
// 破壊的 — フィールド名変更
// 旧: {"user_id": 1}
// 新: {"id": 1}   ← 古いクライアントは user_id が取れない
```

---

## 4. 破壊的変更とバージョンアップの判断

```text
  変更を検討
       │
       ├─ 後方互換？ ──Yes──→ 同じ v1 でリリース + CHANGELOG
       │
       └─ No（破壊的）
              │
              ├─ 内部 API・同時更新可 → 破壊的変更も可（要告知）
              └─ 外部 API → v2 を新設、v1 は Sunset まで維持
```

| 判断材料 | 質問 |
|---------|------|
| 利用者 | 外部開発者がいるか |
| 更新速度 | クライアントを強制更新できるか |
| 影響範囲 | 何件のフィールド・エンドポイントが変わるか |
| 代替手段 | v1 並行期間中に v2 へ誘導できるか |

---

## 5. 内部 API と外部 API での方針の違い

| 種類 | 後方互換の厳しさ | 典型方針 |
|------|----------------|---------|
| 内部 API | 中（同時デプロイなら緩め） | 破壊的変更 OK、Slack で告知 |
| パートナー API | 高 | Deprecation 期間必須 |
| 公開 API | 最高 | v2 新設 + 長期サポート |

内部 API でも **モバイルアプリ** が古いバージョンを長期保持する場合は、外部 API と同様の慎重さが必要です。

> **覚え方**: 外部ほど「古い約束を守る期間」が長くなります。
