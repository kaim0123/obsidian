# バージョニング

## この章の目的

API を長く使い続けるために、変更の世代をどう分けるかを学ぶ章です。

---

## 1. なぜバージョニングが必要か

API を公開すると、クライアントは **特定の形** に依存し始めます。  
フィールド名や URL を突然変えると、更新していないアプリが一斉に壊れます。

| 状況 | バージョンなし | バージョンあり |
|------|--------------|--------------|
| フィールド追加 | 古いクライアントは無視できる | v1 はそのまま、v2 で新形式 |
| URL 変更 | 全クライアントが 404 | v1 は旧 URL、v2 は新 URL |
| 破壊的変更 | 緊急対応・問い合わせ増 | 移行期間を設けられる |

```text
  v1 クライアント ──→ /v1/users  （当面サポート）
  v2 クライアント ──→ /v2/users  （新しい契約）
```

バージョニングは **「古い約束を守りながら、新しい約束を始める」** ための仕組みです。

---

## 2. URL パス方式（`/v1/`）・ヘッダ方式・クエリ方式

バージョンを伝える代表的な 3 方式です。

| 方式 | 例 | メリット | デメリット |
|------|-----|---------|-----------|
| URL パス | `GET /v1/users` | 一目で分かる、キャッシュしやすい | URL が長くなる |
| ヘッダ | `Accept: application/vnd.myapi.v1+json` | URL を汚さない | 試しに叩きにくい |
| クエリ | `GET /users?version=1` | 実装が簡単 | キャッシュ・ログが乱れやすい |

**初心者・小規模チーム** では **URL パス方式** が最も分かりやすく、curl やブラウザでも試せます。

```http
GET /v1/users/42 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbG...
```

## 3. 初心者・チーム向けの選び方

| 条件 | おすすめ |
|------|---------|
| 外部公開 API | URL パス `/v1/` + 明確な CHANGELOG |
| 内部 API のみ | 同時デプロイならバージョン省略も可 |
| モバイルアプリが多い | 古い v1 を長期サポートする前提で設計 |

**ルール例（チーム合意用）**

1. 公開 API は必ず `/v1/` から始める
2. 破壊的変更は **新メジャーバージョン**（v2）で行う
3. v1 の廃止日は **最低 6 ヶ月前** に告知

> 内部 API だけなら「全クライアントを同時に更新できる」ため厳密なバージョンは不要なこともあります。ただし **将来外部公開する可能性** があるなら、最初から `/v1/` を付けておくと楽です。

---

## 4. 非推奨（Deprecation）と廃止（Sunset）の告知

いきなり API を消すのではなく、**段階的に移行** させます。

| 段階 | 意味 | クライアントへの伝え方 |
|------|------|---------------------|
| Deprecation | 非推奨（使わないでほしい） | レスポンスヘッダ `Deprecation: true` |
| Sunset | 廃止予定日 | ヘッダ `Sunset: Sat, 01 Jan 2027 00:00:00 GMT` |

```http
HTTP/1.1 200 OK
Deprecation: true
Sunset: Sat, 01 Jan 2027 00:00:00 GMT
Link: </v2/users>; rel="successor-version"
Content-Type: application/json

{"data": {"id": 42, "name": "太郎"}}
```

ドキュメント・メール・ダッシュボードなど **複数チャネル** で告知すると、移行漏れが減ります。

---

## 5. CHANGELOG の書き方

CHANGELOG は **API の変更履歴** です。クライアント開発者が最初に読む資料になります。

```markdown
## v1.3.0 (2026-06-01)
### Added（後方互換）
- `GET /v1/users` に `?role=` フィルタを追加
- レスポンスに `created_at` フィールドを追加（任意）

### Deprecated
- `GET /v1/users/list` → `GET /v1/users` へ移行してください

## v2.0.0 (2026-12-01) ※破壊的変更
### Changed
- 日時形式を ISO 8601 UTC に統一
- `user_id` を `id` にリネーム
```

| ラベル | 後方互換 | 例 |
|--------|---------|-----|
| Added | ○ | 新フィールド、新エンドポイント |
| Deprecated | △ | 旧エンドポイントの非推奨化 |
| Removed / Changed | × | フィールド削除、型変更 |

---

## 6. 増田本での位置づけ

バージョンは破壊的変更の受け皿であり、雑な破壊の免罪符ではありません。まず後方互換で伸ばし、どうしてもなら世代を分ける、という進め方は [[04_発展性のあるAPI開発]]・[[02_後方互換性]]。
