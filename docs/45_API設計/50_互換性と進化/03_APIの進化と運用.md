# APIの進化と運用

## この章の目的

API をリリース後も改善し続ける運用の考え方を学ぶ章です。

---

## 1. 最初から完璧な API は不要

**動く契約** を早く出し、利用フィードバックで改善する方が現実的です。

```text
  v1.0 最小 CRUD
       │
       ├─ 利用データ・問い合わせを収集
       ├─ フィールド追加（後方互換）
       └─ 必要なら v2 で整理
```

| 完璧主義 | 進化型 |
|---------|--------|
| 6 ヶ月設計のみ | 2 週間で β 公開 |
| 使われないフィールド多数 | 必要なものから追加 |

ただし **命名・エラー形式・認証** だけは最初に固めると、後の変更コストが下がります。

---

## 2. 利用状況を見ながら改善する

| 指標 | 分かること |
|------|-----------|
| エンドポイント別 RPS | ホットスポット |
| 4xx/5xx 率 | 設計・バリデーションの問題 |
| レイテンシ p99 | 一覧 API のページネーション不足 |
| 非推奨 API の利用数 | Sunset のタイミング |

```text
  ダッシュボード
       │
       └─ `/v1/users/list` がまだ 30% → 移行促進キャンペーン
```

---

## 3. モニタリングと `request_id` による調査

[[01_エラー設計]] の `request_id` をログと APM で追跡します。

```json
{
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "しばらくしてから再試行してください",
    "request_id": "req_abc123"
  }
}
```

| 調査フロー | 操作 |
|-----------|------|
| ユーザー報告 | `request_id` を聞く |
| ログ検索 | `request_id` でトレース |
| 原因特定 | 認可バグ / DB タイムアウト等 |

**request_id はレスポンスとサーバーログの橋** です。

---

## 4. レガシー API への段階的改善

```text
  レガシー API
       │
       ├─ 1. 新 API を並行提供（/v2/）
       ├─ 2. 旧 API に Deprecation ヘッダ
       ├─ 3. 利用数ゼロ近傍まで待つ
       └─ 4. Sunset → 503 または 410 Gone
```

| フェーズ | 旧 API | 新 API |
|---------|--------|--------|
| 並行期 | 維持 | 推奨 |
| 移行期 | Deprecation | ドキュメントで誘導 |
| 廃止 | 停止 | 唯一の正 |

---

## 5. API の廃止と移行支援

API 廃止は **技術** だけでなく **コミュニケーション** です。

| 支援 | 内容 |
|------|------|
| 移行ガイド | 旧 → 新の対応表 |
| SDK 更新 | クライアントライブラリの v2 対応 |
| 猶予期間 | Sunset ヘッダ + メール |
| 410 Gone | 廃止後も「なぜ使えないか」を JSON で返す |

```http
HTTP/1.1 410 Gone
Content-Type: application/json

{
  "error": {
    "code": "API_SUNSET",
    "message": "v1 は 2026-12-01 に廃止されました。/v2/users をご利用ください"
  }
}
```

---

## まとめ

- 最初から完璧な API は不要
- 利用状況を見ながら改善する
- モニタリングと `request_id` による調査
- レガシー API への段階的改善
- API の廃止と移行支援
