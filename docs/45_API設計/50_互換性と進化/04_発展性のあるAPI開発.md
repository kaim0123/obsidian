# 発展性のあるAPI開発

[[MOC_API設計体系|📚 目次]] ｜ [[03_APIの進化と運用|← 前へ]]

> [!abstract] この記事で分かること
> - 単純なことをかんたんにできる API から始める理由
> - 動かしながら育てる・利用側と提供側の共同・中核 API セット
> - バージョン管理と複合サービスの位置づけ（増田本）
>
> **前提**：進化の運用は [[03_APIの進化と運用]]、バージョンは [[01_バージョニング]]。連携全体は [[06_アプリケーション間連携の価値と4つの方式]]。

増田亨『現場で役立つシステム設計の原則』第8章「発展性に富んだ API 開発」の要点です。既存の互換性ノートと重複しないよう、**進め方と組み立て** に絞ります。

---

## 1. 単純なことをかんたんにできる API から始める

「将来全部入り」の巨大エンドポイントより、**よく使う小さな操作が迷わず呼べる** 状態が先です。

| 始め方 | 避けたい始め方 |
|--------|----------------|
| 中核リソースの CRUD／参照が予測可能 | 全業務を1レスポンスに詰めた万能 API |
| エラー形式・命名が最初から一貫 | 例外だらけの特別エンドポイントから設計 |

「大は小を兼ねる」万能 API は、かえって使いにくいことが多いです（[[05_API設計の原則]]）。部品として呼べる粒度は [[03_検索と複合操作]] も参照。

---

## 2. 動かしながら設計を発展させる

```text
  最小の契約を公開
       │
       ├─ 実際の呼び出し・問い合わせを見る
       ├─ フィールド追加は後方互換で
       └─ 形が歪んだらバージョンで整理
```

最初から完璧は不要（[[03_APIの進化と運用]]）。一方で **エラー形式・認証・リソース命名** だけは早めに固めると、後の変更が楽です。設計プロセス一般は [[02_設計の段階的な深化]]。

---

## 3. 利用側と提供側の共同作業の環境を整える

API は契約なので、提供側だけで閉じて設計すると現場とずれます。

| 仕組み | 目的 |
|--------|------|
| OpenAPI 草案の共有 | 実装前に形を合わせる |
| フィードバック窓口 | 「使いにくい」を早期に拾う |
| CHANGELOG / Deprecation | 変更の見通しを共有する |

詳細は [[03_チームでAPI設計を守る]]・[[01_OpenAPIとドキュメント]]。

---

## 4. 中核となる API のセットを設計する

発展の軸は「エンドポイントの数」ではなく、**繰り返し組み合わせる中核操作** です。

```text
  中核: 顧客・注文・在庫の参照／基本更新
    │
    ├─ 画面や他サービスは中核を組み合わせる
    └─ 例外的な業務だけ専用 API または複合サービス
```

中核が安定していると、個別要望のたびに契約全体を壊しにくくなります。ドメイン側の境界は [[05_APIとドメイン設計]]・[[10_ドメインオブジェクトとWeb API]]。

---

## 5. Web API のバージョン管理

破壊的変更は避けきれないので、世代を分ける約束が必要です。方式と Sunset は [[01_バージョニング]]、互換のルールは [[02_後方互換性]]。

増田本の趣旨は、バージョンを盾に雑な破壊を正当化するのではなく、**まず互換で伸ばし、どうしてもなら世代を分ける** ことです。

---

## 6. API を複合したサービスの提供

クライアントに多数の中核 API を直叩きさせず、次の層でまとめることがあります。

| 層 | 役割 |
|----|------|
| 中核 API | ドメインの基本操作 |
| 複合サービス／BFF | 画面・チャネル向けに組み立て |

ゲートウェイ／BFF の位置づけは [[05BFFとAPIゲートウェイとグレースフルデグレーデーション]]。複合しすぎて「また万能 API」に戻らないよう、チャネル固有の組み立てに限定します。

---

## まとめ

- かんたんに使える小さな API から始め、動かしながら育てる  
- 利用側と提供側の共同と、中核セットの安定が発展の土台  
- バージョンと複合サービスで、破壊と個別要望を吸収する
