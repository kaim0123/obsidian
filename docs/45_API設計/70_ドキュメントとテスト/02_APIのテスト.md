# APIのテスト

## この章の目的

契約テストの考え方と、API 設計の品質をテストで守る方法を学ぶ章です。

---

## 1. 契約テスト（Contract Test）の考え方

**契約テスト** は、API が **約束した形** で応答するかを検証します。

```text
  OpenAPI（契約）
       │
       ├─→ サーバー側テスト: レスポンスがスキーマに合うか
       └─→ クライアント側テスト: モックが契約に合うか
```

ユニットテストが「内部ロジック」、契約テストが **「窓口の形」** を守ります。

---

## 2. 正常系・異常系・境界値のテスト観点

| 観点 | 例 |
|------|-----|
| 正常系 | `GET /v1/todos/1` → 200 + 期待 JSON |
| 異常系 | 無効トークン → 401、他人の todo → 403 |
| 境界値 | `limit=0`, `limit=最大値+1`, 空文字タイトル → 422 |
| 冪等性 | 同じ Idempotency-Key で 2 回 POST → 1 件だけ作成 |

```text
  テストピラミッド（API）
       │
       ├─ 契約テスト（エンドポイント単位）
       ├─ 統合テスト（DB 含む）
       └─ E2E（少数）
```

---

## 3. モックサーバーと開発フロー

クライアントチームが **サーバー完成前** に開発できるよう、モックを用意します。

| ツール例 | 用途 |
|---------|------|
| Prism | OpenAPI からモックサーバー |
| WireMock | 固定レスポンス・遅延のシミュレート |

```text
  フロントエンド開発
       │
       └─→ モック API（OpenAPI 準拠）
              │
              後から本番 API に差し替え
```

OpenAPI が **唯一の真実** になると、モックと本番のズレが減ります。

---

## 4. 回帰テストと破壊的変更の検知

既存クライアント向けに **レスポンス形状が変わっていないか** を CI で確認します。

| 検知したい変更 | 手段 |
|--------------|------|
| フィールド削除 | スキーマ diff / 契約テスト |
| 型変更 | JSON Schema バリデーション |
| ステータス変更 | 固定シナリオのスナップショット |

```text
  v1.2 リリース PR
       │
       └─ v1.1 時点の契約テストが全部 Green → 後方互換 OK の目安
```

破壊的変更は **意図的に v2** として分岐させ、v1 の契約テストは v1 ブランチで維持します。

---

## 5. テストから見えた設計の問題

テストを書きにくい API は、設計に問題があるサインです。

| テストで苦労する点 | 設計上の問題 |
|------------------|-------------|
| 同じ操作に URL が 3 通り | 一貫性不足 |
| エラー形式がエンドポイントごとに違う | エラー設計未統一 |
| 状態が分からず 404/403 がランダム | 認可ルールが不明確 |
| POST の結果が毎回別 ID | 冪等性未設計 |

> **テストは設計の鏡** — 書きやすい API を目指すと、クライアントにとっても使いやすくなります。
