# チームでAPI設計を守る

## この章の目的

チームで API 設計の品質を維持するためのガイドラインとレビュー文化を学ぶ章です。

---

## 1. API 設計ガイドラインの策定

**1 枚のガイドライン** に、チームの「当たり前」を書きます。

| 項目 | 例ルール |
|------|---------|
| URL | 複数形・小文字・`/v1/` 必須 |
| JSON | `snake_case` 統一 |
| 日時 | ISO 8601 UTC |
| エラー | `{ "error": { "code", "message" } }` |
| 認証 | Bearer Token、401/403 の使い分け |

[[04_一貫性]] のチェックリストをベースに、**自チーム版** を作ります。

---

## 2. 設計レビューとコードレビューの違い

| 種類 | タイミング | 見るもの |
|------|-----------|---------|
| 設計レビュー | **実装前** | URL・契約・後方互換・セキュリティ |
| コードレビュー | 実装後 | ロジック・テスト・パフォーマンス |

```text
  新 API 提案
       │
       ├─ 設計レビュー（OpenAPI 草案）→ 合意
       ├─ 実装
       └─ コードレビュー → マージ
```

設計を後から直すコストは **実装後の 10 倍** とも言われます。

---

## 3. API レビューで見るべきポイント

| # | 質問 | NG 例 |
|---|------|-------|
| 1 | URL は名詞か | `POST /createUser` |
| 2 | メソッドは適切か | `GET /deleteUser` |
| 3 | エラー形式は統一か | HTML エラーページ |
| 4 | 破壊的変更か | 既存フィールド削除 |
| 5 | 認可は明確か | 他人のデータが見える |
| 6 | ページネーションは必要か | 無制限一覧 |

レビューは **批評** ではなく、クライアント体験を想像する **対話** にします。

---

## 4. 設計ルールの文書化と自動チェック

| 自動化 | ツール例 |
|--------|---------|
| Lint | Spectral（OpenAPI ルール） |
| Breaking change 検知 | openapi-diff |
| CI | PR 時にスキーマ検証 |

```yaml
# Spectral ルール例（概念）
paths:
  must-use-plural-nouns: error
  must-have-version-prefix: warn
```

人が見るガイドライン + 機械チェックの **二段構え** が効果的です。

---

## 5. クライアントチームとの合意形成

```text
  サーバーチーム          クライアントチーム
       │                        │
       └──── OpenAPI 草案 ──────→ フィードバック
       ←─── 「この形なら実装可能」──┘
       │
       └── 合意版を CHANGELOG とともに固定
```

| 合意事項 | 文書化 |
|---------|--------|
| リリース日 | CHANGELOG |
| 非推奨 API | Deprecation 告知 |
| サポート窓口 | README / Slack チャンネル |

**早期にクライアント代表を巻き込む** と、リリース後の「使いにくい」が減ります。

増田本第8章も、発展性のある API は **提供側と利用側の共同作業の環境** が前提だと述べます。中核セットの設計や複合サービスとの関係は [[04_発展性のあるAPI開発]]。
