# API設計レビューの実践

## この章の目的

実際の API 案をレビューする手順と、学習の次のステップを示す章です。

---

## 1. 設計レビューの進め方

```text
  1. 事前: OpenAPI 草案 + 背景（なぜこの API が必要か）
  2. 独読: レビュアーが 15 分で読む
  3. 同期 30 分: URL・エラー・認可・互換性を議論
  4. 記録: 決定事項を ADR または CHANGELOG に残す
  5. フォロー: 実装 PR で OpenAPI diff を確認
```

| 役割 | 担当 |
|------|------|
| 提案者 | 草案作成・ユースケース提示 |
| レビュアー | サーバー + クライアント代表 |
| オブザーバー | 将来の利用者（任意） |

---

## 2. レビュー用チェックリスト

[[010Programming/45_API設計/90_付録/付録B_チェックリスト]] をベースに、レビュー時に使う短縮版です。

| カテゴリ | 確認項目 |
|---------|---------|
| URL | 複数形・名詞・浅いネスト・`/v1/` |
| メソッド | GET は安全・副作用なし |
| レスポンス | 成功形・エラー形が統一 |
| 認証認可 | 401/403 の使い分け・所有者チェック |
| 寿命 | 破壊的変更か・Deprecation 計画 |
| ドキュメント | OpenAPI・サンプル・CHANGELOG |
| 信頼性 | レート制限・Idempotency-Key（必要時） |

印刷して **☐ チェック** しながらレビューすると漏れが減ります。

## 3. 良い API・悪い API の比較

**ユーザー検索 API の比較**

| 観点 | 悪い例 | 良い例 |
|------|--------|--------|
| URL | `GET /getUserByEmail?email=` | `GET /v1/users?email=` |
| エラー | 500 のみ | 422 + `VALIDATION_ERROR` |
| 一覧 | 全件返却 | `page` / `limit` + `meta` |
| 認証 | クエリに API Key | `Authorization` ヘッダ |

```http
# 悪い例
GET /api/getUserByEmail?email=taro@example.com&api_key=SECRET

# 良い例
GET /v1/users?email=taro@example.com
Authorization: Bearer <token>
```

**違いの本質**: 良い例は **他エンドポイントと同じルール** で予測できます。

## 4. 改善提案の書き方

レビューコメントは **問題 + 理由 + 具体案** の 3 点セットにします。

```markdown
## 指摘: 注文キャンセル API

**現状案**: POST /v1/cancelOrder

**問題**: 動詞 URL で他 API（/v1/orders）と一貫性がない

**提案**: POST /v1/orders/{id}/cancel
         または PATCH /v1/orders/{id} body: {"status": "cancelled"}

**参考**: [[02_URLとリソースの設計]] — リソースは名詞
```

| NG コメント | OK コメント |
|------------|------------|
| 「ダメです」 | 「`/v1/orders/{id}` に統一すると一覧と同じ規則になります」 |
| 「セキュリティが心配」 | 「owner チェックが無いので 403 を返す処理を追加してください」 |

## 5. 次の学習ステップ

本教材で **API 設計の全体像** を押さえました。次のステップ例です。

| 方向 | おすすめ |
|------|---------|
| 実装 | 好きな言語で TODO API を実装 + 契約テスト |
| 設計の深化 | [[MOC_モジュール設計体系]]、[[02_DDDとは]] |
| セキュリティ | OAuth 2.0 公式仕様、OWASP API Security |
| 運用 | オブザーバビリティ（ログ・メトリクス・トレース） |
| 付録 | [[010Programming/45_API設計/90_付録/付録A_用語集]]、[[010Programming/45_API設計/90_付録/付録D_アンチパターン一覧]] |

```text
  本教材（API 設計）
       │
       ├─→ 実装経験で体感
       ├─→ モジュール・DDD で境界を深める
       └─→ チームガイドラインを作って運用
```

お疲れさまでした。**あなたの API を、誰が使っても迷わない窓口に** していきましょう。
