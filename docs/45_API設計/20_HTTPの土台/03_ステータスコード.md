# ステータスコード

## この章の目的

HTTP **ステータスコード** の意味と、API 設計でどう選ぶかを学ぶ章です。

---

## 1. 2xx・4xx・5xx の大分類

ステータスコードは **3 桁の数字** で、結果の種類を表します。

| クラス | 範囲 | 意味 | 誰の問題？ |
|--------|------|------|-----------|
| **2xx** | 200〜299 | 成功 | — |
| **3xx** | 300〜399 | リダイレクト等 | — |
| **4xx** | 400〜499 | クライアントエラー | リクエスト側 |
| **5xx** | 500〜599 | サーバーエラー | サーバー側 |

```text
  2xx  →  意図どおり処理できた
  4xx  →  リクエストの内容・権限に問題（再送しても同じ失敗になりやすい）
  5xx  →  サーバー側の障害（一時的なら再試行の余地あり）
```

API 設計では **2xx / 4xx / 5xx を正しく使い分ける** ことが、クライアントのエラー処理を楽にします。

---

## 2. よく使うコード一覧（200、201、204、400、401、403、404、409、422、429、500）

| コード | 名称 | 典型的な用途 |
|--------|------|-------------|
| **200** | OK | GET 成功、PATCH/PUT 成功（ボディあり） |
| **201** | Created | POST でリソース作成成功 |
| **204** | No Content | DELETE 成功、更新成功（ボディなし） |
| **400** | Bad Request | 形式不正、必須項目不足 |
| **401** | Unauthorized | 未認証（ログイン・トークンが必要） |
| **403** | Forbidden | 認証済みだが権限不足 |
| **404** | Not Found | リソースが存在しない |
| **409** | Conflict | 重複、楽観ロック競合 |
| **422** | Unprocessable Entity | 形式は正しいが業務ルール違反 |
| **429** | Too Many Requests | レート制限超過 |
| **500** | Internal Server Error | サーバー内部エラー |

詳細は [[010Programming/45_API設計/90_付録/付録C_HTTPステータスコード早見表]] も参照してください。

## 3. ステータスコードの選び方

同じ「失敗」でも、**原因の種類** に応じてコードを分けます。

| 状況 | 選ぶコード | 理由 |
|------|-----------|------|
| メール形式が不正 | `400` | リクエストの形式・入力の問題 |
| 在庫不足で注文不可 | `422` | JSON は正しいが業務ルール違反 |
| 他人の注文を参照 | `403` | 存在はするが権限がない |
| 存在しない注文 ID | `404` | リソースそのものがない |
| 同じメールで二重登録 | `409` | 競合・重複 |

```text
  ❌  すべて 400 や 500 で返す  →  クライアントが原因別に対処できない
  ✅  401 / 403 / 404 / 422 を使い分ける  →  UI・再試行・ログが設計しやすい
```

## 4. ステータスとエラーボディの役割分担

ステータスコードとボディは **役割が分担** されています。

| 担当 | 内容 | 例 |
|------|------|-----|
| **ステータスコード** | 大分類（成功 / クライアントエラー / サーバーエラー） | `422` |
| **エラーボディ** | 詳細（機械可読 code、人間向け message、フィールドエラー） | [[01_エラー設計]] |

```json
HTTP/1.1 422 Unprocessable Entity

{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "在庫が不足しています"
  }
}
```

ステータスだけでは足りない情報をボディで補います。**ステータスだけ返してボディが空** も、設計としては避けた方がよいことが多いです。

---

## 5. ステータスコードのチェックリスト

新しいエンドポイントを設計するときの確認項目です。

- [ ] 成功時に **200 / 201 / 204** を適切に使い分けているか
- [ ] 認証・認可で **401 と 403** を混同していないか
- [ ] 存在しないリソースは **404** か（権限不足は 403）
- [ ] バリデーションと業務ルール違反で **400 と 422** を分けているか
- [ ] サーバー障害は **500**、一時的な過負荷は **503** を検討したか
- [ ] エラー時も **一貫した JSON 形式** のボディがあるか（[[01_エラー設計]]）
