# HTTPの基本

## この章の目的

Web API の土台となる **HTTP** の仕組みを、リクエスト・レスポンスの流れから理解する章です。

---

## 1. HTTP とは何か

**HTTP（HyperText Transfer Protocol）** は、Web 上でデータをやり取りするための **通信ルール（プロトコル）** です。

ブラウザがページを表示するときも、スマホアプリが API を呼ぶときも、多くの場合 HTTP が使われています。

| 用語 | 意味 |
|------|------|
| プロトコル | 通信の約束事・手順 |
| クライアント | リクエストを送る側（ブラウザ、アプリ、他サーバー） |
| サーバー | リクエストを受け取り、レスポンスを返す側 |

```text
  クライアント  ──HTTP リクエスト──→  サーバー
  クライアント  ←─HTTP レスポンス──  サーバー
```

API 設計では「HTTP のルールの上に、どんな URL・形式・エラーを使うか」を決めます。

---

## 2. リクエストとレスポンスの流れ

HTTP 通信は **1 回のリクエストに対して 1 回のレスポンス** が返る、シンプルな往復です。

```text
  1. クライアントがリクエストを組み立てる
           │
           ▼
  2. ネットワーク経由でサーバーへ送る
           │
           ▼
  3. サーバーが処理し、レスポンスを返す
           │
           ▼
  4. クライアントがステータス・ボディを解釈する
```

| 段階 | クライアント側の例 |
|------|-------------------|
| 送信 | `fetch('https://api.example.com/users')` |
| 受信 | ステータス 200、JSON のユーザー一覧 |

[[02_リクエストとレスポンスの構造]]で、リクエスト・レスポンスの **中身（ヘッダ・ボディ）** を詳しく見ます。

---

## 3. URL・パス・クエリパラメータの読み方

API の「どこにアクセスするか」は **URL** で表します。

```text
https://api.example.com/v1/users?page=2&limit=20
└─────┬─────────────┘ └┬┘ └──────┬──────┘ └───────┬────────┘
   スキーム・ホスト    バージョン  パス（リソース）   クエリパラメータ
```

| 部分 | 役割 | 例 |
|------|------|-----|
| スキーム | 通信方式 | `https://` |
| ホスト | サーバーの場所 | `api.example.com` |
| パス | リソースの位置 | `/v1/users` |
| クエリ | フィルタ・ページなど | `?page=2&limit=20` |

- **パス** — 「何のリソースか」を表す（[[02_URLとリソースの設計]]で設計方法を学ぶ）
- **クエリ** — 一覧の絞り込み・並び替え・ページ送りなど（[[02_ページネーション・フィルタ・ソート]]）

## 4. ステートレスという性質

HTTP は **ステートレス（状態を持たない）** プロトコルです。  
サーバーは、前のリクエストの内容を **自動では覚えません**。

```text
  リクエスト1: GET /users/1   → 200 OK
  リクエスト2: GET /users/1   → サーバーは「さっきも同じ人？」とは知らない
```

| ステートレスの意味 | 設計への影響 |
|-------------------|-------------|
| 各リクエストは独立 | 認証情報は毎回ヘッダなどで送る |
| サーバーがセッションを持たない | JWT など自己完結型トークンが使われやすい |
| スケールしやすい | どのサーバー instance でも同じリクエストを処理できる |

「ログイン状態」などは、Cookie・トークン・セッション ID など **別の仕組み** で表現します（[[01_認証]]）。

---

## 5. HTTPS が必須である理由

本番の API では **HTTPS（HTTP + TLS 暗号化）** が必須です。

| 方式 | 内容 | API 設計での位置づけ |
|------|------|---------------------|
| HTTP | 平文通信 | 開発環境のみ（本番では不可） |
| HTTPS | 暗号化通信 | トークン・個人情報を送る本番 API |

```text
  HTTP   …  途中で内容が読み取られる可能性（パスワード・トークンが漏洩）
  HTTPS  …  暗号化され、改ざん検知も可能
```

- 認証トークン・API キーを **平文 HTTP で送らない**
- 本番 URL は `https://` で始める
- 60_セキュリティと信頼性で認証・認可と合わせて詳しく扱います
