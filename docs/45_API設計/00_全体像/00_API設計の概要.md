# API設計 — 初心者向けガイド

## このノートの目的

**API（Application Programming Interface）** は、プログラム同士がデータをやり取りするための「窓口」です。  
Web API では、クライアント（ブラウザ、スマホアプリ、他のサーバー）が **HTTP** を使ってサーバーにリクエストを送り、JSON などの形式でレスポンスを受け取ります。

このノートでは、API を設計するときに押さえる **8つの基本テーマ** を、初心者向けに整理します。

1. 一貫性
2. RESTリソース設計
3. HTTPメソッド
4. エラー設計
5. バージョニング
6. 後方互換性
7. Pagination
8. 認証認可

前提として [[MOC_ソフトウェア設計体系|設計]] の「ソフトウェア設計」層に位置づけられます。ドメインの考え方は [[02_DDDとは]] も参考になります。

---

## API設計を一言で

> **「誰が使っても迷わない窓口」を、長く使える形で決めること。**

良い API は、**名前・形式・エラー・権限** が揃っていて、クライアント開発者がドキュメントを読まなくても「だいたい当たりがつく」状態を目指します。

## 1. 一貫性

### 何か

**同じ種類の操作は、同じルールで表現する**こと。  
一貫性がない API は、エンドポイントごとに「命名が違う」「日付の形式が違う」「成功時の形が違う」などの混乱を生みます。

### なぜ重要か

- クライアント側の共通処理（エラーハンドリング、ログ、SDK）が書きやすい
- 新しいエンドポイントを追加するときの判断基準になる
- チーム開発で「各自バラバラに作る」を防げる

### 揃えるべき項目（例）

| 項目 | 良い例（統一） | 悪い例（バラバラ） |
|------|----------------|-------------------|
| 命名 | `snake_case` または `camelCase` を全体で固定 | `/getUser` と `/orders/list` が混在 |
| 日時 | 常に ISO 8601（`2026-06-19T10:00:00Z`） | `2026/06/19` と Unix 秒が混在 |
| ID | 常に文字列 UUID | 数値 ID と UUID が混在 |
| レスポンス | 常に `{ "data": ... }` でラップ | 配列を直返しする API とオブジェクト返しが混在 |
| 真偽値 | `true` / `false` | `1` / `0` や `"yes"` / `"no"` |

### 実践のコツ

1. **API 設計ガイドラインを1枚にまとめる**（命名、日時、エラー形式など）
2. **OpenAPI（Swagger）** などでスキーマを定義し、レビュー時の基準にする
3. 既存 API があるなら、**新規だけ直すのではなく**、段階的に揃える計画を立てる

```json
// 一貫した成功レスポンスの例
{
  "data": {
    "id": "usr_01HXYZ",
    "name": "田中太郎",
    "created_at": "2026-06-19T10:00:00Z"
  }
}
```

## 2. RESTリソース設計

### 何か

**REST（Representational State Transfer）** は、Web API でよく使われる設計スタイルです。  
中心となる考え方は **「URL は名詞（リソース）、操作は HTTP メソッドで表現する」** ことです。

### リソースとは

**操作の対象**のこと。例えば「ユーザー」「注文」「商品」など、ビジネス上の「もの」を URL で表します。

```text
/users          … ユーザー一覧（コレクション）
/users/{id}     … 特定のユーザー（単一リソース）
/orders/{id}/items  … 注文に紐づく明細（ネストしたリソース）
```

### 良い URL 設計

| 原則 | 良い例 | 悪い例 |
|------|--------|--------|
| 名詞を使う | `GET /users` | `GET /getUsers` |
| 複数形でコレクション | `/orders` | `/order` |
| 階層は浅く | `/users/{id}/orders` | `/api/v1/company/department/team/user/order` |
| 動詞は URL に入れない | `DELETE /users/{id}` | `POST /deleteUser` |
| 小文字・ハイフン | `/order-items` | `/OrderItems` |

### リソース設計の手順（初心者向け）

1. **ドメインの名詞を洗い出す**（ユーザー、商品、カート、注文…）
2. **URL パスに落とす**（`/products`, `/carts`, `/orders`）
3. **関連はネストで表現**（`/orders/{order_id}/items`）
4. **検索・フィルタはクエリパラメータ**（`GET /products?category=book&sort=price`）

### REST 以外も知っておく

- **RPC 風**（`/users/search` など）は便利な場面もあるが、乱用すると一貫性が崩れやすい
- **GraphQL** は「1つのエンドポイントで必要なデータだけ取得」向き
- 小規模プロジェクトでも **REST の基本（名詞 + HTTP メソッド）** は最初の土台として有効

## 3. HTTPメソッド

### 何か

HTTP メソッドは **「リソースに対して何をしたいか」** を表す動詞です。  
REST では、URL（名詞）とメソッド（動詞）の組み合わせで操作を表現します。

### 主要メソッド一覧

| メソッド | 意味 | 典型用途 | 冪等性※ | 安全※ |
|----------|------|----------|---------|-------|
| **GET** | 取得 | 一覧・詳細の参照 | ○ | ○ |
| **POST** | 作成 | 新規リソース作成、非冪等な処理 | × | × |
| **PUT** | 置換 | リソース全体の更新（存在しなければ作成も可） | ○ | × |
| **PATCH** | 部分更新 | 一部フィールドだけ変更 | △ | × |
| **DELETE** | 削除 | リソース削除 | ○ | × |

※ **冪等性**：同じリクエストを何度送っても結果が同じになること（POST は通常 ×）  
※ **安全**：サーバー側の状態を変えないこと（GET は ○）

### ステータスコードとの組み合わせ

| 操作 | 成功時 | 失敗例 |
|------|--------|--------|
| GET 一覧 | `200 OK` | `404`（存在しないコレクション） |
| GET 詳細 | `200 OK` | `404 Not Found` |
| POST 作成 | `201 Created` + `Location` ヘッダ | `400 Bad Request`, `409 Conflict` |
| PUT / PATCH 更新 | `200 OK` または `204 No Content` | `404`, `409` |
| DELETE 削除 | `204 No Content` | `404` |

### よくある間違い

```text
❌ GET /users/123/delete     … 削除を GET で行う（副作用あり・危険）
❌ POST /users/123/update    … 更新を POST + 動詞 URL で行う
✅ DELETE /users/123         … メソッドで意図を表現
✅ PATCH /users/123          … 部分更新
```

**GET は副作用を持たせない**（キャッシュや prefetch で意図せず実行されるため）。  
削除・更新・作成は必ず POST / PUT / PATCH / DELETE を使います。

## 4. エラー設計

### 何か

API は **成功だけでなく失敗も、予測可能な形で返す**必要があります。  
クライアントはエラー内容を見て、再試行・ユーザーへの表示・ログ送信を判断します。

### 基本方針

1. **HTTP ステータスコード**で大分類（4xx = クライアントの問題、5xx = サーバーの問題）
2. **レスポンスボディ**で詳細（機械可読なコード + 人間向けメッセージ）
3. **一貫した JSON 形式**で返す

### よく使うステータスコード

| コード | 意味 | 使う場面 |
|--------|------|----------|
| 400 | Bad Request | バリデーションエラー、形式不正 |
| 401 | Unauthorized | 認証されていない（ログインが必要） |
| 403 | Forbidden | 認証済みだが権限がない |
| 404 | Not Found | リソースが存在しない |
| 409 | Conflict | 重複、楽観ロック競合 |
| 422 | Unprocessable Entity | 形式は正しいが業務ルール違反 |
| 429 | Too Many Requests | レート制限超過 |
| 500 | Internal Server Error | サーバー内部エラー |
| 503 | Service Unavailable | メンテナンス、過負荷 |

### エラーレスポンスの例

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "入力内容に誤りがあります",
    "details": [
      {
        "field": "email",
        "code": "INVALID_FORMAT",
        "message": "メールアドレスの形式が正しくありません"
      }
    ],
    "request_id": "req_abc123"
  }
}
```

### 設計のポイント

- **`code` は固定文字列**（`VALIDATION_ERROR` など）。クライアントが分岐しやすい
- **`message` は人間向け**。多言語化するなら `message_key` + クライアント側翻訳も可
- **`request_id`** を付けると、サポート・ログ調査が楽になる
- **5xx の詳細（スタックトレース）は本番レスポンスに含めない**
- バリデーションエラーは **フィールド単位** で返すとフォーム UI と相性が良い

## 5. バージョニング

### 何か

API は公開すると **クライアントが依存し始める**ため、破壊的変更をいきなり入れられません。  
**バージョニング**は、古いクライアントを動かし続けながら、新しい仕様を提供する仕組みです。

### なぜ必要か

- モバイルアプリはユーザーが古いバージョンを長期間使う
- 外部連携先はすぐに改修できない
- 「フィールド名を変えただけ」がクライアント側の大量修正につながる

### 主な方式

| 方式 | 例 | メリット | デメリット |
|------|-----|----------|------------|
| URL パス | `/v1/users`, `/v2/users` | 分かりやすい、キャッシュしやすい | URL が長くなる |
| ヘッダ | `Accept: application/vnd.myapi.v2+json` | URL を汚さない | 初心者にはやや難 |
| クエリ | `/users?version=2` | 実装が簡単 | あまり推奨されない |

**初心者・チーム開発では URL パス方式（`/v1/`）が最も理解しやすい**ことが多いです。

```text
https://api.example.com/v1/users
https://api.example.com/v2/users
```

### 運用のコツ

- **v1 をいつまで維持するか**（非推奨 → 廃止日）をドキュメントで明示
- 変更は **CHANGELOG** に記録
- 内部 API（自社フロント専用）ならバージョンなし + 同時デプロイも選択肢

## 6. 後方互換性

### 何か

**既存のクライアントが、変更後も壊れずに動き続けること**です。  
バージョニングとセットで考えるのが基本です。

### 安全な変更（後方互換を保てる）

| 変更 | 例 |
|------|-----|
| 新フィールドの追加 | レスポンスに `nickname` を追加（クライアントは無視できる） |
| 新エンドポイント追加 | `GET /users/{id}/preferences` を新設 |
| オプショナルなクエリ追加 | `?include=orders` を追加 |
| 新しいエラーコード追加 | 既存コードはそのまま |

### 破壊的変更（後方互換が崩れる）

| 変更 | 例 |
|------|-----|
| フィールド削除・リネーム | `user_name` → `name` |
| 型の変更 | `price: "1000"` → `price: 1000` |
| 必須化 | 任意だった `email` を必須に |
| ステータスコード変更 | 404 → 403 |
| URL 変更 | `/users` → `/members` |

**破壊的変更は新バージョン（v2）で行い、v1 は一定期間維持**するのが定石です。

### 実務での判断

```text
小さな追加 → 同じ v1 で OK
形を変える変更 → v2 を切る + v1 に非推奨マーク
```

レスポンスに **`deprecated` フィールド** や **`Sunset` HTTP ヘッダ** で「いつ消えるか」を伝えると、クライアント側の移行がスムーズです。

## 7. Pagination

### 何か

一覧 API（`GET /users`, `GET /orders` など）は、データが増えると **一度に全部返すと遅く・重く**なります。  
**Pagination（ページネーション）** は、結果を **分割して返す**仕組みです。

### なぜ必要か

- レスポンスサイズと DB 負荷を抑える
- モバイル回線でも扱いやすい
- タイムアウトを防ぐ

### 主な方式

#### オフセット方式（page / limit）

```text
GET /users?page=2&limit=20
```

| 項目 | 内容 |
|------|------|
| リクエスト | `page`（何ページ目）, `limit`（1ページ件数） |
| レスポンス例 | `{ "data": [...], "meta": { "page": 2, "limit": 20, "total": 150 } }` |
| メリット | 実装・理解が簡単、「N ページ目へジャンプ」しやすい |
| デメリット | データ追加・削除で **重複や取りこぼし** が起きやすい |

#### カーソル方式（cursor）

```text
GET /users?limit=20&cursor=eyJpZCI6MTIzfQ
```

| 項目 | 内容 |
|------|------|
| リクエスト | `limit`, `cursor`（前回レスポンスの続き位置） |
| レスポンス例 | `{ "data": [...], "meta": { "next_cursor": "...", "has_more": true } }` |
| メリット | リアルタイム更新に強い、大量データ向き |
| デメリット | 任意ページへのジャンプが難しい |

### 選び方（目安）

| 用途 | おすすめ |
|------|----------|
| 管理画面の表、件数が少〜中 | オフセット |
| SNS タイムライン、ログ、無限スクロール | カーソル |

### 共通のベストプラクティス

- **`limit` に上限**を設ける（例：最大 100）
- **`total`（総件数）** は DB コストが高い場合、省略または概算を検討
- ソート順を固定する（例：`created_at desc, id desc`）
- レスポンスに **`has_more` や `next_cursor`** を含め、クライアントの実装を単純にする

## 8. 認証認可

### 用語の整理

| 用語 | 意味 | 例 |
|------|------|-----|
| **認証（Authentication）** | 「あなたは誰か」を確認 | ログイン、API キー、JWT |
| **認可（Authorization）** | 「何ができるか」を確認 | 管理者のみ削除可、自分の注文のみ閲覧可 |

**認証 → 認可** の順。ログインしていない（401）と、ログイン済みだが権限不足（403）を混同しない。

### 主な認証方式

| 方式 | 概要 | 向いている場面 |
|------|------|----------------|
| **API Key** | 固定文字列をヘッダに付与 | サーバー間連携、シンプルな内部 API |
| **Bearer Token（JWT 等）** | `Authorization: Bearer <token>` | モバイル・SPA、ステートレス |
| **OAuth 2.0 / OpenID Connect** | 第三者 IdP 経由の委任 | Google ログイン、SaaS 連携 |
| **Session Cookie** | サーバー側セッション + Cookie | 伝統的な Web アプリ |

### リクエスト例

```http
GET /v1/users/me HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

### 認可の設計

1. **リソース所有者チェック** — `GET /orders/{id}` で、注文の `user_id` が本人か
2. **ロールベース（RBAC）** — `admin`, `editor`, `viewer` など
3. **スコープ** — OAuth の `read:orders`, `write:products` など

```text
認証 OK + 注文の所有者 → 200
認証 OK + 他人の注文   → 403 Forbidden
認証 NG                → 401 Unauthorized
```

### セキュリティの基本

- **HTTPS 必須**（平文 HTTP でトークンを送らない）
- トークン・API キーを **URL クエリに載せない**（ログに残りやすい）
- **レート制限**（429）で brute force を抑える
- 本番と開発で **キーを分ける**
- 最小権限の原則 — 必要なスコープだけ付与

## 8つのテーマの関係（まとめ）

```text
一貫性 ─────────────┐
RESTリソース設計 ───┤
HTTPメソッド ───────┼→ 「使いやすい窓口」の形
エラー設計 ─────────┤
Pagination ─────────┘

バージョニング ─────┐
後方互換性 ─────────┼→ 「長く使える窓口」の寿命

認証認可 ───────────→ 「安全な窓口」
```

| # | テーマ | 初心者が最初に決めること |
|---|--------|--------------------------|
| 1 | 一貫性 | 命名・日時・レスポンス形式のルールを1枚に |
| 2 | RESTリソース | URL は名詞、複数形、浅い階層 |
| 3 | HTTPメソッド | GET=取得、POST=作成、PATCH=更新、DELETE=削除 |
| 4 | エラー設計 | ステータス + 固定 `code` + `request_id` |
| 5 | バージョニング | `/v1/` から始める |
| 6 | 後方互換性 | 追加 OK、削除・改名は v2 |
| 7 | Pagination | 一覧は必ず分割、`limit` 上限 |
| 8 | 認証認可 | 401 と 403 を分ける、HTTPS |

---

## 次に学ぶとよいこと

- **OpenAPI（Swagger）** … スキーマ定義とドキュメント自動生成
- **HATEOAS** … レスポンスにリンクを含め、クライアントの探索を助ける REST の発展形
- **Idempotency-Key** … POST の二重送信防止（決済 API など）
- **レート制限設計** … `X-RateLimit-*` ヘッダの返し方

API 設計は一度決めて終わりではなく、**利用者のフィードバックと利用状況を見ながら少しずつ改善**していくものです。まずは上記 8 項目をガイドラインにし、小さな API から試してみるのがおすすめです。
