## 詳しい要約

**テーマ：二重処理の入り口と、冪等性（idempotency）で防ぐ3つの道具**

二重課金・ポイントの二重付与・同じメールの二重送信は、コードの書き間違いではなく、1つずつ見れば正しい処理の組み合わせで起きる。**冪等**とは「何回やっても1回やったのと同じ結果になる」性質で、「2回届いても事故にならないか」を問うことが大切。防ぐ道具は**依頼番号・先に席を取る・結果で書く**の3つ。

---

### 冪等とは

- 「電気をつける」は何回やってもついたまま（冪等）。「スイッチで切り替える」は2回押すと消える（冪等でない）
- 「残高を1000円にする」は冪等、「残高に200円足す」は2回動くと増えてしまう
- 「注文を支払い済みにする」は冪等、「注文を新しく作る」は2回で注文が2つになる
- 数学的な厳密な定義は知らなくてよい

### 二重の入り口は3つ

1. 人がボタンを2回押す（反応が遅いと押してしまう。ボタンを押せなくする工夫だけでは防げない）
2. 返事が分からないのでプログラムが**送り直す**（以前のモバイル通信の回はスマホ側、今回はサーバー同士）
3. 仕組みそのものが**「少なくとも1回」届ける**作り（ちょうど1回を約束するのはとても難しいため、多くの仕組みは「たまに2回届くかも」としている）

### 送り直しで二重課金 → 道具1：依頼番号

- ショップが決済サービスに1000円の請求を送り、決済サービスは引き落として返事を返すが、返事が途中で消える（ネットワークの詰まりやタイムアウト）
- ショップからは成功か失敗か分からないので自動でもう一度送り、決済サービスは新しい依頼だと思ってまた引く → 2000円引かれる
- 対策：請求を送る前に注文用の**依頼番号**を1つ作り、送り直すときも**同じ番号**を使う（送り直すたびに作り直してはダメ。最初に1回だけ作る）
- 決済サービスは番号を処理済みとして記録し、同じ番号が来たらお金を引かずに**前の結果をそのまま返す**
- 多くの決済サービスはこの依頼番号を受け取る仕組みを用意している。送る側は番号を同じにし、受ける側は番号で見分ける

### 「少なくとも1回」届く知らせ（Webhook）と受け取る側の守り方

- 支払いが済むと決済サービスからショップへ知らせが届く（**Webhook**：向こうから教えてくれる仕組み）
- ショップが支払い済みにしてポイントを100付け、返事をするが返事が消える → 同じ知らせが再送され、何も考えずに処理するとポイントが200に
- こうした仕組みは「届かない」より「2回届く」を選んでいる
- 守り方は依頼番号と同じ考え方。知らせには番号が付いているので、処理済みかを記録で確かめ、処理するときに「処理済み」の記録も一緒に書く
- 2回目は何もせず「受け取りました」とだけ返す。**エラーを返すと届いていないと思われてまた送られる**ので、済んでいるなら成功として返す
- 仕事を順番に並べて処理する**キュー**も、多くは少なくとも1回取り出せる作りなので同じ

### 同時に2つ届くと → 道具2：先に席を取る

- 同じ番号の依頼がほぼ同時に2つ届くと（2度押しや早すぎる送り直し）、両方が「済んでいるか」を記録に聞き、どちらも「まだ」と答えられて両方が決済に進む
- 「確かめてから書く」の間に隙間がある。1人ずつなら正しい手順が、同時だと壊れる。依頼番号を使っていても防げない
- 対策：確かめる前に、いきなり「処理中」の行を書き込む（**席を取る**）
- DBに「同じ依頼番号の行は1つしか入れられない」という約束（**一意制約**）をさせておく。映画館の座席のように同じ席は1人しか取れない
- 席を取れた1回目だけが決済に進み、終わったら「済み」に書き換えて**結果も保存**する（後で同じ番号が来たときに返すため）
- 断られた2回目は「処理中です」と返して終わる

### コードで見るポイント

- 受け取る側：依頼番号を取り出す → まず「処理中」の行を書き込む → 書き込めなければ同じ番号が既にあるので前の記録を見る → 席を取れたときだけ決済 → 済みに書き換えて結果を保存
- 2回目以降：済んでいれば前の結果を返す、処理中なら「処理中です」と返す
- DB側に `UNIQUE` の制約を付ける。**コードの順番よりDBの約束が要**。アプリ内で確かめるだけでは隙間が残り、本番でサーバーが何台も動くならなおさら
- 途中で落ちて「処理中」のまま止まった行は、時間が経ったらやり直せるようにしておくのが普通

### 道具3：結果で書く

- 「電気をつける」側に寄せる。「ポイントを100足す」ではなく「注文123のポイントを100にする」と、注文番号と結びつけて結果を書けば何回でも同じ
- 在庫も「1減らす」ではなく「注文123の分を確保済みにする」
- メールのように外に出たら取り消せないものは、送信済みの記録を見てから送る
- 全部をきれいに冪等にはできなくても、寄せることはできる

### AIに書かせたとき見るところ

AIは1回きりで正しく動くコードは上手に書くが、「2回届いたら」はこちらが言わないと抜けがち。

1. 送り直す処理の中で依頼番号を作り直していないか（繰り返しの中で作ると毎回違う番号になる）
2. 「済んでいるか確かめてから書く」順番になっていないか
3. DBに「同じ番号は1つだけ」という約束があるか
4. 2回目の依頼にエラーを返していないか（済んでいるなら前の結果を返す）
5. 足し算の処理が2回動いたらどうなるか。AIに「この処理は2回届いたらどうなる？」と聞いてみる

### まとめ

- 冪等とは、何回やっても1回やったのと同じ結果になること
- 二重の入り口は、2度押し・送り直し・少なくとも1回届ける仕組みの3つ
- 送り直すときは同じ依頼番号で、受け取る側は番号で見分ける
- 確かめてから書くのではなく先に席を取り、DBの一意制約で同時に来た2つを1つにする（席を取れた人だけが進む）
