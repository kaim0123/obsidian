# 認証

> この章は「API でどう認証を扱うか」を扱います。認証方式そのもの（OAuth 2.0・OIDC・SAML など）は 73 の [[03_ログインの種類と認証方式]]・[[01_OAuth2.0とは]]、Cookie・セッションは 74 を参照してください。

## この章の目的

「あなたは誰か」を確認する認証の基本と、API でよく使う方式を学ぶ章です。

---

## 1. 認証（Authentication）とは何か

**認証** は **本人確認** です。「このリクエストは誰から来たか」をサーバーが判断します。

| 概念 | 英語 | 問い |
|------|------|------|
| 認証 | Authentication | あなたは誰？ |
| 認可 | Authorization | 何ができる？ |

```text
  クライアント ──(認証情報)──→ サーバー
                                    │
                                    ├─ 認証 OK → ユーザー ID を特定
                                    └─ 認証 NG → 401 Unauthorized
```

認証が通っても、**操作の許可**（認可）は別途チェックします（[[02_認可]]）。

---

## 2. API Key・Bearer Token（JWT）・Session Cookie

| 方式 | 渡し方 | 向いている用途 |
|------|--------|--------------|
| API Key | ヘッダ `X-API-Key: ...` | サーバー間連携、管理が簡単 |
| Bearer Token | ヘッダ `Authorization: Bearer <token>` | SPA・モバイル（JWT など） |
| Session Cookie | Cookie 自動送信 | 同一ドメインの Web アプリ |

**JWT（JSON Web Token）** は、トークン自体にユーザー ID や有効期限が入った文字列です。

```http
GET /v1/me HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

| 方式 | 注意点 |
|------|--------|
| API Key | 漏洩するとなりすまし可能 → ローテーション・権限最小化 |
| JWT | 有効期限・署名検証必須、ログアウトはブラックリスト等が必要 |
| Cookie | CSRF 対策（SameSite 等）が必要 |

---

## 3. OAuth 2.0 / OpenID Connect の概要

**OAuth 2.0** は、ユーザーが **パスワードをアプリに渡さず** に、限定的なアクセス権を付与する仕組みです。

```text
  ユーザー ──→ 認可サーバーでログイン
                    │
                    └──→ アクセストークン ──→ API サーバー
```

| 用語 | 意味 |
|------|------|
| アクセストークン | API を呼ぶための鍵 |
| リフレッシュトークン | アクセストークンを更新する鍵 |
| OpenID Connect | OAuth + 「ユーザー情報（ID）」の標準 |

初心者は **Bearer Token をヘッダで渡す** 流れを押さえ、OAuth の詳細は必要になったときに深掘りすれば十分です。

---

## 4. 認証情報の渡し方（ヘッダに載せる・URL に載せない）

**認証情報を URL に載せない** 理由:

- ブラウザ履歴に残る
- サーバーアクセスログに残る
- Referer ヘッダで漏洩する

```text
  ❌ GET /v1/users?api_key=SECRET123
  ✅ GET /v1/users
     Authorization: Bearer SECRET123
```

| 情報 | 載せてよい場所 |
|------|--------------|
| API Key / Token | `Authorization` ヘッダ |
| セッション ID | `HttpOnly` Cookie（Web のみ） |
| 公開パラメータ | クエリ（`page`, `limit` など） |

---

## 5. 401 Unauthorized の返し方

認証に失敗したときは **401** を返します（403 ではない）。

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api"
Content-Type: application/json

{
  "error": {
    "code": "UNAUTHORIZED",
    "message": "認証トークンが無効または期限切れです"
  }
}
```

| 状況 | ステータス |
|------|-----------|
| トークンなし・無効・期限切れ | 401 |
| 認証済みだが権限不足 | 403（[[02_認可]]） |

クライアントは 401 を受け取ったら **再ログイン** や **トークン更新** のフローに入ります。

## 発展：REST API の認証方式の比較（Basic・トークン・APIキー・OAuth）

ネットワーク機器・コントローラの REST API を例に、主な認証方式の仕組みと注意点を比較します。

### REST APIの認証と認可（Basic認証・トークン・APIキー・OAuth）

REST はステートレスなので、**リクエストのたびに「誰が送ったか」を証明する情報** を付けます。主な方式は次のとおりです。

| 方式 | 仕組み | 注意点 |
| --- | --- | --- |
| **Basic認証** | `ユーザー名:パスワード` を **Base64 でエンコード** し、`Authorization: Basic ...` ヘッダに入れて送る | Base64 は **暗号化ではなく誰でも元に戻せる**。必ず **HTTPS** と組み合わせる。パスワードを毎回送る |
| **トークン認証**（Bearer トークンなど） | 最初の認証で発行された **一時的な文字列（トークン）** を、以降のリクエストに付けて送る | トークンには有効期限がある |
| **APIキー** | 事前に発行された **固定のキー文字列** をリクエストに付けて送る | 漏れると悪用されるので管理が重要 |
| **OAuth** | 利用者のパスワードを他のアプリに渡さずに、**必要な範囲だけのアクセス権を委任** する。アプリは **アクセストークン** を受け取って API にアクセス | トークンには **有効期限とスコープ（使える範囲）** があり、不要になれば **取り消せる** |

#### Basic 認証の中身

```
 ユーザー名: admin   パスワード: Cisco123
        ↓ "admin:Cisco123" を Base64 エンコード
 Authorization: Basic YWRtaW46Q2lzY28xMjM=
        ↓ 誰でもデコードできる
 "admin:Cisco123"   ← だから HTTPS(TLS) で通信路を暗号化する必要がある
```

#### トークン認証の流れ（Catalyst Center の例）

Catalyst Center の API では、**まず Basic 認証でトークンを取得し、以降のリクエストではそのトークンを使います**。

```http
POST /dna/system/api/v1/auth/token HTTP/1.1
Host: catalyst-center.example.com
Authorization: Basic YWRtaW46Q2lzY28xMjM=
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"Token": "eyJ0eXAiOiJKV1QiLCJhbGciOiJSUzI1NiJ9..."}
```

```http
GET /dna/intent/api/v1/network-device HTTP/1.1
Host: catalyst-center.example.com
X-Auth-Token: eyJ0eXAiOiJKV1QiLCJhbGciOiJSUzI1NiJ9...
Accept: application/json
```

パスワードを送るのは最初の1回だけで済み、以降は期限付きのトークンを使うのが利点です。

#### OAuth（認可の委任）

「Google アカウントでログイン」のように、**外部のサービスに自分のパスワードを教えずに連携できる** のは OAuth の仕組みによります。

```
 利用者 ──(1) アプリAに「私のデータを使っていいよ」と許可──> 認可サーバ
                                                      │
 アプリA <──(2) アクセストークン（期限・スコープ付き）─────┘
   │
   └──(3) Authorization: Bearer <アクセストークン> ──> API サーバ
        ※ アプリAは利用者のパスワードを一度も知らない
```

- **認可（何をしてよいか）の委任** の仕組みとして広く使われます。
- Basic 認証との対比：Basic 認証では **パスワードそのものをアプリに渡す** ことになる。

#### 間違えやすい用語

| 用語 | 正体 |
| --- | --- |
| AAA | 認証（Authentication）・認可（Authorization）・アカウンティング（Accounting）の **枠組み**。HTTP ヘッダ形式の名前ではない |
| SNMPv2c | 機器監視のプロトコル。**コミュニティ名を平文で送る** |
| WPA2-PSK | 無線 LAN で事前共有キーを使って認証する方式 |

#### ひっかけポイント・よくある誤解

- 「Base64 でエンコードして Authorization ヘッダ」＝ **Basic認証**。トークン認証（一時的な文字列）、APIキー（固定キー）、AAA（枠組み）ではない。
- **Base64 は暗号化ではない**。
- 「パスワードを渡さずに、必要な範囲だけのアクセス権を委任」＝ **OAuth**。Basic認証は逆にパスワードを渡す方式。
- SNMPv2c や WPA2-PSK は REST API の認可方式ではない。

#### 押さえておくポイント

- Basic（Base64、HTTPS 必須）／トークン（Bearer、一時的）／APIキー（固定）／OAuth（委任、スコープ・期限・取り消し）。
- Catalyst Center：Basic 認証でトークン取得 → 以降はトークン。
