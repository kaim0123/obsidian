# 認可

> 権限モデル（RBAC・ABAC など）の詳細は 73 の [[01_認証と認可とは]]・[[02_RBAC・ABAC・ACLの使い分け（Hayk Simonyan）]] を参照してください。

## この章の目的

認証のあとに「この操作をしてよいか」を判断する認可の考え方を学ぶ章です。

---

## 1. 認可（Authorization）とは何か

**認可** は **権限チェック** です。認証で「誰か」が分かったあと、「何ができるか」を決めます。

```text
  リクエスト DELETE /v1/todos/99
       │
       ├─ 認証: ユーザー A としてログイン済み
       └─ 認可: todo 99 の所有者は A か？
              ├─ Yes → 204 No Content
              └─ No  → 403 Forbidden
```

---

## 2. 認証と認可の違い（401 と 403）

| ステータス | 意味 | クライアントの対応 |
|-----------|------|------------------|
| 401 Unauthorized | 認証されていない / 無効 | ログイン・トークン更新 |
| 403 Forbidden | 認証済みだが許可なし | 操作を諦める・管理者に連絡 |

```text
  401 = 「身分証を見せてください」
  403 = 「身分は分かったが、この部屋には入れません」
```

混同すると、クライアントが **無限リトライ** したり、**誤った UI** を表示します。

---

## 3. リソース所有者チェック

多くの API では **「自分のリソースだけ操作できる」** ルールがあります。

```text
  GET /v1/todos/42
       │
       └─ todo.user_id == ログインユーザー.id ?
              ├─ Yes → 200 + todo 本体
              └─ No  → 403（または 404 で存在を隠す）
```

| 方針 | 403 | 404 |
|------|-----|-----|
| メリット | 権限不足が明確 | 存在自体を隠せる（セキュリティ） |
| 向く場面 | 内部 API | 公開 API（ID 推測対策） |

チームで **403 と 404 のどちらを使うか** を統一してください。

---

## 4. ロールベース（RBAC）とスコープ

| 方式 | 考え方 | 例 |
|------|--------|-----|
| RBAC | ロールに権限を付与 | `admin` は全ユーザー削除可 |
| スコープ | トークンに許可操作を列挙 | `read:orders`, `write:orders` |

```json
// JWT ペイロード例（概念）
{
  "sub": "user-123",
  "roles": ["member"],
  "scope": "read:todos write:todos"
}
```

管理画面 API では RBAC、外部連携では **細かいスコープ** がよく使われます。

---

## 5. 最小権限の原則

**最小権限（Least Privilege）** — 必要な権限だけを付与する。

| 悪い例 | 良い例 |
|--------|--------|
| 読み取り専用アプリに `admin` ロール | `read:products` スコープのみ |
| 全 API Key が DELETE 可能 | 用途別 Key（在庫連携用・分析用） |

```text
  権限設計
       │
       ├─ この操作に本当に必要か？
       ├─ 漏洩したときの被害は？
       └─ ロール / スコープを分離できるか？
```

認可は **設計段階** でエンドポイントごとに「誰が呼べるか」を表にしておくと、実装漏れが減ります。
