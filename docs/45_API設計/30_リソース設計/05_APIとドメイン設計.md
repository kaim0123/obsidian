# APIとドメイン設計

## この章の目的

ドメインモデルと API のリソース設計をどう結びつけるかを学ぶ章です。

---

## 1. ドメインの名詞がリソースになる

ビジネスで使う **名詞** が、そのまま API のリソース候補になります。

| ドメイン（EC） | リソース候補 |
|--------------|-------------|
| 商品 | `/products` |
| カート | `/carts` |
| 注文 | `/orders` |
| 在庫 | 内部のみ（公開しないことも） |

```text
  ドメインエキスパートの会話
  「注文に商品を追加する」
       │
       ▼
  POST /v1/orders/{id}/items
```

---

## 2. ユビキタス言語とエンドポイント名

**ユビキタス言語** — チーム全体で同じ用語を使う（[[02_DDDとは]]）。

| ドメイン用語 | API で避けたい命名 |
|------------|------------------|
| 注文 (Order) | `/purchases`, `/buy_requests` が混在 |
| 会員 (Member) | `/users` と `/members` の二重表現 |

```text
  用語集（1 枚）
       │
       ├─ 日本語: 注文
       ├─ 英語 URL: orders
       └─ ID 形式: ord_{uuid}
```

エンドポイント名は **コード・UI・ドキュメント** で同じ単語を使います。

---

## 3. 集約と API 境界の関係

**集約（Aggregate）** は、一緒に整合性を保つオブジェクトのまとまりです。

```text
  Order 集約
  ├── Order（ルート）
  └── OrderItem × n
```

| 設計 | 例 |
|------|-----|
| 集約ルート経由 | `POST /orders/{id}/items`（Order 経由で Item 追加） |
| Item 単独公開 | `PATCH /order-items/{id}` → 整合性が崩れやすい |

**原則**: 集約外から子エンティティを直接 PATCH しない。

---

## 4. 内部モデルをそのまま晒さない

DB テーブルや ORM エンティティを **そのまま JSON 化** しない。

| 内部モデル | API レスポンス |
|-----------|--------------|
| `password_hash` | **含めない** |
| 内部ステータス `status=7` | `"status": "shipped"` など意味のある文字列 |
| 3 テーブル JOIN 結果 | クライアントに必要な形に整形 |

```json
// ❌ 内部丸出し
{"id": 1, "password_hash": "...", "internal_flag": true}

// ✅ API 用 DTO
{"id": 1, "email": "taro@example.com", "display_name": "太郎"}
```

**DTO（Data Transfer Object）** 層を挟むと、内部変更と API 契約を分離できます。

---

## 5. [[02_DDDとは]] との接続

| DDD の概念 | API 設計での対応 |
|------------|----------------|
| エンティティ | リソース（`/orders/{id}`） |
| 値オブジェクト | JSON のネストフィールド |
| リポジトリ | 一覧・検索 API |
| ドメインサービス | RPC 風エンドポイント or サブリソース |

```text
  モジュール設計（境界）
       ↓
  API 設計（公開するリソース）
       ↓
  クラス設計（DTO・ハンドラ）
```

[[MOC_モジュール設計体系]] で決めた境界のうち、**外部に見せる部分** が本章の対象です。
