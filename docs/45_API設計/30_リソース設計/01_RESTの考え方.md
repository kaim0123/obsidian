# RESTの考え方

## この章の目的

**REST** — URL は名詞、操作は HTTP メソッド — という Web API の基本スタイルを学ぶ章です。

---

## 1. REST（Representational State Transfer）とは何か

**REST（Representational State Transfer）** は、Roy Fielding が提唱した **Web API の設計スタイル** です。  
厳密な規格というより、**よく使われる設計の考え方** として理解するとよいです。

| REST の中心思想 | 意味 |
|----------------|------|
| リソース | URL で表す「もの」（ユーザー、注文など） |
| 表現（Representation） | JSON など、リソースの送受信形式 |
| ステートレス | 各リクエストは独立（[[01_HTTPの基本]]） |
| 統一インターフェース | HTTP メソッドで操作を統一 |

本教材では **REST ベースの Web API** を中心に扱います。

---

## 2. リソースと表現（Representation）

**リソース** は操作の **対象** です。**表現** は、そのリソースを JSON などで **どう表すか** です。

```text
  リソース（概念）     表現（JSON）
  ───────────────     ─────────────
  ユーザー usr_123  →  { "id": "usr_123", "name": "田中" }
  注文 ord_456      →  { "id": "ord_456", "total": 3000 }
```

同じリソースでも、XML や JSON など **複数の表現** があり得ますが、現代の Web API では **JSON が主流** です。

---

## 3. URL は名詞、操作は HTTP メソッド

REST の基本ルールです。

| 要素 | 役割 | 例 |
|------|------|-----|
| URL（パス） | **名詞** — 何に対する操作か | `/users`, `/orders/{id}` |
| HTTP メソッド | **動詞** — 何をするか | GET, POST, PATCH, DELETE |

```text
  ❌  POST /deleteUser        … URL に動詞
  ❌  GET  /users/123/update  … 更新を GET で
  ✅  DELETE /users/123       … メソッドで操作を表現
  ✅  PATCH  /users/123       … 部分更新
```

[[02_URLとリソースの設計]]で URL の設計、[[03_HTTPメソッドと操作の表現]]でメソッドの使い分けを詳しく学びます。

---

## 4. REST の利点と限界

| 利点 | 説明 |
|------|------|
| 学習しやすい | HTTP の標準機能をそのまま使う |
| キャッシュ | GET は CDN・ブラウザキャッシュと相性が良い |
| ツールが豊富 | curl、Postman、OpenAPI エコシステム |
| 一貫性 | 名詞 + メソッドで CRUD を統一 |

| 限界 | 説明 |
|------|------|
| 複雑な検索 | 1 リクエストで多条件・多リソース取得が冗長になりやすい |
| 非 CRUD 操作 | 「送信」「承認」などを無理やり CRUD に当てはめると不自然 |
| N+1 問題 | 関連データ取得でリクエストが増える |

限界を知ったうえで、**基本は REST、必要なら例外**（[[03_検索と複合操作]]）という姿勢が現実的です。

---

## 5. REST 以外のスタイル（RPC 風・GraphQL）との関係

| スタイル | 特徴 | 向いている場面 |
|----------|------|---------------|
| **REST** | リソース + HTTP メソッド | 一般的な CRUD API |
| **RPC 風** | `/users/search` など操作指向 URL | 検索・集計・複雑な処理 |
| **GraphQL** | 1 エンドポイント、クライアントが欲しいフィールドを指定 | 多様なクライアント、柔軟な取得 |

```text
  まず REST の基本（名詞 + メソッド）を固める
           │
           ▼
  必要に応じて RPC 風・GraphQL を検討（[[01_REST以外のAPIスタイル]]）
```

スタイルを **混在させすぎる** と一貫性が崩れやすいので、チームで方針を決めます。
