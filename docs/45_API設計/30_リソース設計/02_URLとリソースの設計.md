# URLとリソースの設計

## この章の目的

ドメインの **名詞** からリソースを洗い出し、**読みやすい URL** を設計する章です。

---

## 1. リソースの洗い出し（ドメインの名詞から）

URL 設計の第一歩は、**ビジネス上の「もの」** を名詞として洗い出すことです。

### 例：EC サイト

| 名詞（リソース） | URL の候補 |
|-----------------|-----------|
| ユーザー | `/users` |
| 商品 | `/products` |
| カート | `/carts` |
| 注文 | `/orders` |
| 注文明細 | `/orders/{id}/items` |

```text
  ドメインの名詞を書き出す
       │
       ▼
  コレクション / 単一 / ネスト に分類
       │
       ▼
  URL パスに落とす
```

[[02_DDDとは]] のユビキタス言語と揃えると、チーム内の会話と API が一致しやすくなります（[[05_APIとドメイン設計]]）。

---

## 2. コレクションと単一リソース（`/users` と `/users/{id}`）

| 種類 | URL 例 | 典型メソッド |
|------|--------|-------------|
| **コレクション** | `GET /users` | GET（一覧）, POST（作成） |
| **単一リソース** | `GET /users/{id}` | GET（詳細）, PATCH, DELETE |

```text
  /users           … ユーザー全体（コレクション）
  /users/usr_123   … ID が usr_123 の 1 人（単一）
```

- コレクションは **複数形**（`/users` 而非 `/user`）
- `{id}` は UUID やプレフィックス付き ID（`usr_01HXYZ`）

---

## 3. ネストしたリソース（`/orders/{id}/items`）

**親子関係** があるリソースは、パスでネストして表現します。

```text
  /orders/{order_id}/items           … 注文に属する明細一覧
  /orders/{order_id}/items/{item_id} … 特定の明細
  /users/{user_id}/orders            … ユーザーの注文一覧
```

| ネストの目安 | 例 |
|-------------|-----|
| 強い所属関係 | 注文 → 明細 |
| スコープが明確 | ユーザー → その人の注文 |
| 浅く保つ | 3 階層以上は避ける傾向 |

```text
  ❌  /api/v1/company/dept/team/user/order/item  … 深すぎ
  ✅  /orders/{id}/items                         … 2 階層で十分なことが多い
```

---

## 4. 命名規則（複数形・小文字・ハイフン・浅い階層）

| 原則 | 良い例 | 悪い例 |
|------|--------|--------|
| 名詞を使う | `/products` | `/getProducts` |
| 複数形でコレクション | `/orders` | `/order` |
| 小文字 | `/order-items` | `/OrderItems` |
| ハイフンで単語区切り | `/order-items` | `/order_items`（URL ではどちらも可、**統一** が重要） |
| 階層は浅く | `/users/{id}/orders` | 5 階層以上の深いネスト |
| 動詞は URL に入れない | `DELETE /users/{id}` | `POST /deleteUser` |

バージョンは先頭に `/v1/` を付けることが多いです（[[01_バージョニング]]）。

---

## 5. よくある URL 設計の間違い

| 間違い | 問題 | 改善 |
|--------|------|------|
| `GET /getUser?id=1` | 動詞 URL、ID がクエリ | `GET /users/1` |
| `POST /users/create` | 作成が冗長 | `POST /users` |
| `/user`（単数）と `/orders`（複数）混在 | 一貫性なし | すべて複数形 |
| すべてを 1 URL に | REST 的でない | リソースごとに分ける |
| 内部 DB テーブル名をそのまま露出 | ドメインとずれる | ドメインの言葉を使う |

詳細なアンチパターンは [[010Programming/45_API設計/90_付録/付録D_アンチパターン一覧]] も参照してください。
