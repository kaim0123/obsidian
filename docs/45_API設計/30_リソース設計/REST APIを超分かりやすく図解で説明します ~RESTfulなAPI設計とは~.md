## 詳しい要約

**テーマ：REST の 4 大設計原則を身近なたとえで理解する**

REST は Web サービスの **設計思想の一つ** であり、その設計ルール（アドレス可能性・統一インターフェース・ステートレス性・接続性）を満たした API を **RESTful な API** と呼ぶ、という入門解説。家の建築設計、レストラン、ウォーターサーバー、美容室、ブログのリンクといった例えで各原則を説明し、最後に「REST（Representational State Transfer）」という名前の意味を振り返る。

---

### REST とは

- 一言でいうと **Web サービス設計思想の一つ**。家を木造にするか鉄筋にするかを目的で選ぶように、「大量アクセスのある SNS を作る」といった目的に合わせて採用する設計方針
- 他に SOAP という設計方式もあったが、現在は REST が主流
- 名前の直訳は Re（Representational＝代表的な）・S（State＝状態）・T（Transfer＝転送する）
- 設計ルールは 6 つほどあるが、大きな 4 つを押さえればよい

### 1. アドレス可能性（Addressability）

- URL を送ると、その URL に対応するデータ（例: Twitter API で最新ツイート）が **一意に** 返ってくる性質
- **レストランの例**: お客様＝クライアント、ウェイター＝**API**、厨房＝サーバー。メニューから「ハンバーガーください」と頼む＝URL を指定する
- API（Application Programming Interface）の「インターフェース」は何かと何かをつなぐもの（マウスやキーボードのように）。API はクライアントとサーバーを中継ぎする

### 2. 統一インターフェース（Uniform Interface）

- **GET（取得）・POST（投稿）・PUT（更新）・DELETE（削除）** の HTTP メソッドを統一して使うルール
- サーバーが返すデータ形式も統一する。昔は XML、今は **JSON** が一般的
- **ウォーターサーバーの例**: 蛇口をひねって水を汲む＝GET、水をセットする＝POST、減った水を足す＝PUT、水を取り外す＝DELETE。どの業者と契約しても操作方法は同じ＝統一されている

### 3. ステートレス性（Stateless）

- 「状態（情報）を持たない」＝ **サーバーがクライアントの情報（キャッシュやセッション）を保持しない** 設計
- **美容室の例**: 行きつけの店が「田中さんはいつもショートカット」と覚えているのが **ステートフル**。毎回「ショートカットで」と伝えなければならないのが **ステートレス**
- 過去の情報を保持すると管理コストが高くなるため、ステートレスにして **シンプルな設計** にし、運用コストを下げ **スケーラビリティ（拡張性）** を高める
- 過去の情報を覚えておけばすぐログインできるなどの利点もあるが、REST の基本はステートレス

### 4. 接続性（Connectability）

- ブログや技術記事の末尾に複数のリンクが貼られているように、一つの点から複数の方向へ **リンクでつながっている** 状態
- Web（＝クモの巣）が広まった理由そのものの考え方

### まとめ

- REST の名前は「URL を **代表（Representation）** として、リソースの **状態（情報）** を **転送** する」という意味だと考えられる（諸説あり）
- REST API とは **REST のルールに従った API**（ウェイターが REST のルールで動いている状態）
- Twitter や Facebook のような、アクセスが集中する大規模 SNS などで適用される設計
