# テストしやすいモジュール設計

## この章の目的

**テスト容易性** を意識したモジュール設計を学びます。  
テストが書きにくい構造は、設計に問題がある **シグナル** です。

---

## 1. テスト容易性とは何か

**テスト容易性** とは、モジュールを **少ないセットアップ** で、**速く**、**安定して** テストできる性質です。

| テストしやすい | テストしにくい |
|--------------|--------------|
| 依存を差し替え可能 | DB・ネットワーク必須 |
| 副作用が局所化 | グローバル状態に依存 |
| 入力出力が明確 | 巨大なコンテキストが必要 |

[[03_テストと設計の関係]] のモジュール版です。

---

## 2. モック・スタブが必要になる理由

**モック / スタブ** = 本物の代わりに使う偽の実装。

```text
  UseCase テスト
  PlaceOrderUseCase
    ├── OrderRepository → InMemory（スタブ）
    └── PaymentGateway  → Fake（モック）
```

| 必要になる理由 | 対策 |
|--------------|------|
| 外部 I/O がある | ポート + インターフェース（[[03_ヘキサゴナルアーキテクチャのモジュール構成]]） |
| 時間・乱数に依存 | Clock / IdGenerator を注入 |
| 他モジュールに依存 | 境界で Fake を差し替え |

**モックだらけ** = 結合度が高いサイン。設計の見直しを検討します。

---

## 3. 副作用の局所化

**副作用**（DB 書き込み、HTTP、ファイル I/O）を **インフラ層・アダプタ** に閉じ込めます。

```text
  domain/        ← 副作用なし（純粋なルール）
  application/   ← orchestration（ポート経由のみ）
  infra/         ← 副作用はここだけ
```

| 層 | テスト |
|----|--------|
| domain | 単体、瞬時 |
| application | ポート Fake |
| infra | 統合テスト |

---

## 4. 単体テスト・結合テストの境界

| 種類 | 範囲 | モジュール設計との関係 |
|------|------|----------------------|
| **単体** | 1 クラス / 関数 | domain はここ |
| **モジュール** | 1 モジュール + Fake 依存 | application + Fake ports |
| **結合** | 複数モジュール / 実 DB | 重要パスのみ |

```text
  テストピラミッド（モジュール視点）
        ▲
       /結合\        少数・遅い
      /──────\
     / モジュール \   中程度
    /────────────\
   /  domain 単体 \  多数・速い
  ────────────────
```

---

## 5. テストから見えた設計の問題

テストを書こうとして **詰まったら**、設計を疑います。

| テストの症状 | 設計の問題 |
|-------------|-----------|
| 20 個モックが必要 | 結合度が高い |
| 1 テストに 10 秒 | 副作用が domain に漏れている |
| どこを assert すればよいか不明 | 責務が曖昧 |
| テストのセットアップが 100 行 | ファクトリ・ビルダー不足 or 設計複雑 |

**テストは設計のフィードバックループ** として使います。

---

## まとめ

- **テスト容易性** = 速く・安定して・少ないセットアップで試せる
- **ポート + 注入** でモック・スタブを可能に
- **副作用は infra に局所化**、domain は純粋に
- テストが書きにくい = **設計改善のシグナル**
