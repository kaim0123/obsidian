# モジュール設計の進化

## この章の目的

設計は **最初から完璧でなくてよい** — 段階的にモジュール境界を改善する進め方を学びます。

---

## 1. 最初から完璧な設計は不要

| 現実 | 対応 |
|------|------|
| 要件は変わる | 境界も見直す |
| 学習しながら進む | 小さく試して修正 |
| 時間は有限 | 重要な境界から |

```text
  設計の進化
  動くモノリス → モジュール仮説 → 実装で検証 → 境界調整 → 定着
```

[[02_設計の段階的な深化]] と同じ精神です。

---

## 2. 小さく始めて段階的に分割する

### 段階的アプローチ

1. **第 1 段階**: レイヤーだけ分ける（web / app / domain / infra）
2. **第 2 段階**: ドメインモジュールを 2〜3 個に分割
3. **第 3 段階**: 依存ルールと CI を導入
4. **第 4 段階**: 細分化・イベント連携

```text
  Week 1:  order と catalog を分離
  Week 4:  payment を切り出し
  Month 3: 依存チェックを CI に
```

**Big Bang リライト** は避け、**Strangler Fig**（絞め殺しのイチジク）パターンで置き換えます。

---

## 3. リファクタリングのタイミング

| タイミング | 例 |
|-----------|-----|
| 機能追加前 | 触るモジュールの整理 |
| バグ修正後 | 根本原因が境界なら分割 |
| テスト追加時 | 依存を注入可能に |
| 定期 | 四半期の依存グラフレビュー |

**ルール**: リファクタ専用 PR と機能 PR を **分ける** とレビューしやすい。

---

## 4. 機能追加時の境界の見直し

新機能が **既存モジュールの責務外** なら、境界を見直します。

| 質問 | アクション |
|------|-----------|
| どのモジュールの「変化の理由」に合うか | そこに置く |
| どのモジュールにも合わない | **新モジュール** を検討 |
| 2 モジュールにまたがる | どちらが主担当か、イベント連携か |

```text
  新機能「クーポン」
  order に置く？ promotion 新設？
  → 変化の理由が「販促ルール」なら promotion モジュール
```

---

## 5. レガシーコードへの適用

[[03_レガシーとの向き合い方]] のモジュール版です。

| 原則 | 説明 |
|------|------|
| 理解してから | 依存グラフ・ホットスポットを把握 |
| 新コードは良い境界 | 旧コードを触らなくてよい形で拡張 |
| 絶えず小さく | 触ったファイルの周辺だけ整理 |
| 諦めないライン | 100% きれいは不要。改善トレンドが重要 |

```text
  レガシー
  ┌─────────────────────┐
  │ 旧コード（触らない）  │
  │  ┌───────────────┐  │
  │  │ 新 order 模块 │  │ ← アンチコラプション層で接続
  │  └───────────────┘  │
  └─────────────────────┘
```

---

## まとめ

- **完璧な初期設計は不要** — 仮説と検証を繰り返す
- **段階的分割** でリスクを抑える
- 機能追加・バグ修正を **境界見直しの機会** に
- レガシーは **新コードから良い境界** を広げる
