# 変更に強いモジュール設計

## この章の目的

**仕様変更・技術変更** に耐えるモジュール設計 — OCP、拡張点、後方互換 — を学びます。

---

## 1. 開放閉鎖の原則（OCP）

**OCP（Open-Closed Principle）** = **拡張に対して開き、変更に対して閉じる**。

| 閉じる（変更不要） | 開く（拡張可能） |
|------------------|----------------|
| 既存モジュールのコアロジック | 新しい支払い方法の追加 |
| 安定した公開 API | 新しいアダプタの追加 |

```text
  悪い例: payment モジュールに if (stripe) ... else if (paypal) ...
  良い例: PaymentGateway IF + StripeAdapter, PayPalAdapter
```

[[05_SOLIDとの関係]] をモジュール単位に適用します。

---

## 2. 拡張点の設計

**拡張点** = 新機能を **既存コードを書き換えず** 足せる場所。

| 拡張点 | 例 |
|--------|-----|
| インターフェース | `NotificationSender` |
| プラグイン / レジストリ | 税率計算の Strategy |
| イベント購読 | 新リスナーを追加 |
| 設定 | 機能フラグ |

```typescript
interface TaxCalculator {
  calculate(amount: Money, region: Region): Money;
}
// 新地域 = 新クラスを追加するだけ
```

**拡張点を増やしすぎ** も YAGNI 違反。変化が **実際に起きた** 軸に置きます。

---

## 3. 後方互換性の考え方

公開 API を変えるとき、**既存の呼び出し元を壊さない** 配慮が必要です。

| 手法 | 説明 |
|------|------|
| 追加のみ | 新関数・新フィールド（オプション） |
| 非推奨期間 | `@deprecated` → 次メジャーで削除 |
| バージョン分離 | `/api/v1`, `/api/v2` |
| アダプタ | 旧 API を新実装でラップ |

[[01_モジュール間インターフェースの設計]] の 9.5 と連動します。

---

## 4. リファクタリングしやすい構造

| 条件 | 理由 |
|------|------|
| 高凝集・低結合 | 変更が局所化 |
| テストがある | 安全网 |
| 依存が一方向 | 切り離しやすい |
| 小さなコミット単位 | モジュールごとに漸進改善 |

```text
  リファクタリングの順序
  1. テストを足す（または characterization test）
  2. 内部を整理（外部 API は維持）
  3. 必要なら API を段階的に変更
```

---

## 5. 技術的負債との向き合い方

**技術的負債** = 設計を妥協した結果の将来コスト。

| 戦略 | 説明 |
|------|------|
| 可視化 | 負債リスト、依存グラフ |
| 優先付け | 変更頻度 × 痛み |
| 絶えず小さく | Boy Scout Rule — 触ったモジュールを少し良く |
| 境界を守る | 新コードは良い設計、旧コードは段階的に |

完璧を待たず、**新規・変更箇所から** 適用します（[[04_モジュール設計の進化]]）。

---

## まとめ

- **OCP** — 拡張で足し、既存を書き換えない
- **拡張点** は変化の実績がある軸に置く
- **後方互換** で公開 API 変更の影響を抑える
- **テスト + 高凝集低結合** がリファクタリングの前提
