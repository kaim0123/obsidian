# モジュール設計レビューの実践

## この章の目的

モジュール設計の **レビュー手順** と **改善提案の書き方** を学び、本教材を総仕上げします。

---

## 1. 設計レビューの進め方

| フェーズ | 時間 | 内容 |
|---------|------|------|
| 事前 | — | モジュール図・依存図・README を共有 |
| イントロ | 5 分 | 目的・スコープ |
|  walkthrough | 20 分 | モジュール一覧と主要フロー |
| 深掘り | 20 分 | 境界・依存・リスク |
| まとめ | 10 分 | アクションアイテム |

```text
  参加者
  ・設計者（説明）
  ・実装者
  ・将来メンテする人（必須）
  ・業務担当（ドメイン分割時）
```

コードレビューより **早い段階**（PR 前・スプリント計画時）に行うと効果が大きいです。

---

## 2. レビュー用チェックリスト

[[010Programming/43_モジュール設計/90_付録/付録B_チェックリスト]] の抜粋:

- [ ] 各モジュールを **1 文** で説明できる
- [ ] **凝集度** — 無関係な処理が混在していない
- [ ] **結合度** — 循環依存・共有 DB 直アクセスがない
- [ ] **依存の向き** — domain → infra の逆がない
- [ ] **公開面** — 最小限の export
- [ ] **命名** — ユビキタス言語と一致
- [ ] **テスト** — domain / usecase が単体テスト可能
- [ ] **変更シナリオ** — 「決済 API 変更」で触るモジュールは妥当か

---

## 3. 良い設計・悪い設計の比較

### 例: 注文キャンセル

| 悪い設計 | 良い設計 |
|---------|---------|
| web コントローラが SQL で在庫戻し | order が CancelOrderUseCase、inventory に `release()` |
| payment の内部クラスを import | PaymentPort.refund(orderId) |
| 1 関数 500 行 | order/application + domain に分割 |

```text
  悪い: web → SQL, payment/internal
  良い: web → CancelUseCase → Order domain + InventoryPort
```

---

## 4. 改善提案の書き方

| 要素 | 例 |
|------|-----|
| 観察 | 「comment が article の Entity を import している」 |
| 影響 | 「article の DB 変更が comment に波及する」 |
| 提案 | 「ArticleSummaryDto または articleId のみ渡す」 |
| 優先度 | High / Medium / Low |

```markdown
### 提案 #1: comment → article の依存を緩める
- **現状**: CommentService が OrderEntity を直接参照
- **問題**: 結合度が高い（内容結合）
- **提案**: ArticleId + getSummary(id) API に変更
- **優先度**: High
```

**批判ではなく改善** — 代替案を 1 つ以上示します。

---

## まとめ

- 設計レビューは **図と README** を共有し、早い段階で実施
- **チェックリスト** で凝集度・結合度・依存・公開面を確認
- 良い/悪いを **具体例** で比較
- 改善提案は **観察・影響・提案・優先度** で書く
