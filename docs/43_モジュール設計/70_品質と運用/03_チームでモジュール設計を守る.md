# チームでモジュール設計を守る

## この章の目的

複数人で開発するとき、**モジュール境界を維持** するための合意・レビュー・ルールを学びます。

---

## 1. 設計の合意形成

モジュール設計は **チームの合意** がなければ守られません。

| ステップ | 内容 |
|---------|------|
| 1. 草案 | モジュール一覧 + 依存図（1 ページ） |
| 2. レビュー | 全員が「なぜこの境界か」を議論 |
| 3. 記録 | ADR または README に残す |
| 4. 更新 | 大きな機能追加時に見直し |

```text
  合意の対象
  ・モジュール名と 1 文説明
  ・依存の向き（禁止ルール含む）
  ・公開 API の方針
```

[[01_チームで設計を守る]] と同様のプロセスをモジュール単位で行います。

---

## 2. コードレビューで見るべきポイント

| 観点 | 質問 |
|------|------|
| 境界 | 正しいモジュールに置かれているか |
| 依存 | 禁止方向の import がないか |
| 公開面 | 不要な export を増やしていないか |
| 命名 | ユビキタス言語と一致するか |
| テスト | モジュール単位で意味あるテストがあるか |

```text
  PR レビュー
  ✓ order モジュールへの変更
  ? payment/infra を import → 境界違反！
```

---

## 3. 設計ルールの文書化

**短い 1 ページ** で十分です。

```markdown
## モジュール設計ルール（例）
1. トップレベルはドメイン名（order, payment）
2. domain は infra を import 禁止
3. モジュール間は index.ts 経由のみ
4. common は新規追加禁止（既存は段階的縮小）
```

- リポジトリの `docs/architecture.md` または Wiki
- **具体例**（良い import / 悪い import）を 1 つずつ

---

## 4. 境界を壊す変更の防止

| 手段 | 説明 |
|------|------|
| 静的解析 | dependency-cruiser, ArchUnit |
| CI チェック | ルール違反でビルド失敗 |
| CODEOWNERS | モジュールごとにレビュアー |
| ペア / 設計レビュー | 大きな境界変更の前 |

```text
  CI
  npm run lint:deps  →  cycle detected: order ↔ payment  → FAIL
```

---

## 5. 設計負債の可視化

| 方法 | 内容 |
|------|------|
| 依存グラフ | 定期的に生成・共有 |
| Tech Debt ラベル | Issue でモジュール名を付ける |
| 健全性スコア | 循環数、common サイズ、テストカバレッジ |
| リファクタ枠 | スプリントの 10% など |

**責めない** — 可視化して **優先順位** をつけて改善します。

---

## まとめ

- **合意** → 記録 → レビューで設計を維持
- コードレビューは **境界・依存・公開面** を見る
- **短いルール文書** + CI で自動チェック
- 設計負債は **可視化** して計画的に返済
