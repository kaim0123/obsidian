# パッケージ設計の原則 — REP/CCP/CRP・SDP/SAP

## はじめに

クラスの設計に **SOLID原則** があるように、**パッケージ（モジュール・コンポーネント）** の設計にも原則があります。

Robert C. Martin が提唱した、**6つのパッケージ設計原則** です。

- **REP / CCP / CRP** — パッケージの **凝集（中身のまとまり）** に関する3原則
- **ADP / SDP / SAP** — パッケージ間の **結合（つながり）** に関する3原則

クラスレベルでは見えない、**大きな粒度での設計指針** として役立ちます。

---

## 凝集の3原則（中身のまとまり）

### 1. REP（Reuse-Release Equivalence Principle）— 再利用・リリース等価の原則

> **「再利用の単位は、リリースの単位に等しい」**

パッケージとして **再利用してもらう** なら、**リリース（バージョン管理された配布物）** の単位で提供すべき。

具体的には：

- バージョン番号がついている
- 変更履歴がある
- 壊す変更は新バージョンで示す

npm, PyPI, Cargo などのパッケージは、REPに従ってバージョン管理されています。

### 2. CCP（Common Closure Principle）— 共通閉鎖の原則

> **「同じ理由で変更されるクラスは、同じパッケージにまとめよ」**

**SRPのパッケージ版**。仕様変更時に、**1つのパッケージだけ変更すれば済む** ように。

例: 「税率が変わる」という変更なら、税計算に関わるクラスは **同じパッケージ** に集めておく。

### 3. CRP（Common Reuse Principle）— 共通再利用の原則

> **「一緒に使われるものは、同じパッケージに。使われないものは、別パッケージに」**

使う側は **不要なものを含んだパッケージ** を引き込みたくない。使うクラスだけを含む **小さなパッケージ** が望ましい。

**ISPのパッケージ版** とも言える。

---

## 凝集3原則のトレードオフ

この3つは **同時に完全に満たすのは不可能** な関係です。

```
     REP (リリース単位)
        /            \
    CCP                CRP
  (まとめよ)          (分けよ)
```

- REP と CRP を取ると、パッケージが **小さくなりすぎ**、リリースが煩雑に
- REP と CCP を取ると、パッケージが **大きくなり**、不要なものも含まれる
- CCP と CRP を取ると、**再利用しにくい**

**プロジェクトの段階** によって、どの原則を重視するかが変わります。

- 開発初期: CCP（共通閉鎖）を重視
- 成熟期: CRP（共通再利用）を重視

---

## 結合の3原則（つながり）

### 4. ADP（Acyclic Dependencies Principle）— 非循環依存の原則

> **「パッケージの依存関係に循環があってはならない」**

パッケージ A → B → C → A のような **依存の輪** を作らない。

#### 循環依存の何が悪いか

- ビルド順序が決まらない
- 1つ変更すると全体を再テスト
- モジュールが事実上1つの大きな塊になってしまう

#### 対策

1. **依存方向を統一**（上から下へ）
2. **共通部分を別パッケージに抽出**
3. **依存性逆転でインターフェースを挟む**

### 5. SDP（Stable Dependencies Principle）— 安定依存の原則

> **「安定しているパッケージに依存せよ」**

変更されやすいパッケージを、変更されにくいパッケージが依存すると、**常に巻き込まれる**。

- **安定している** = 他から多く依存される、自分からは少ししか依存しない
- **不安定** = 他への依存が多く、自分は他から少ししか依存されない

依存は常に **不安定 → 安定** の向きで。

### 6. SAP（Stable Abstractions Principle）— 安定抽象の原則

> **「安定なパッケージは抽象的であれ」**

安定なパッケージ（他から多く依存される）は、**具体ではなく抽象であるべき**。

- 具体的だと、変更があったときに **多くの依存元が壊れる**
- 抽象なら、具体実装を差し替えても影響が最小化

→ **DIP（依存性逆転）** のパッケージ版。

---

## SDPとSAPの関係: 安定性と抽象度は相関する

```
       抽象的
          ↑
          │    理想（安定＋抽象）
          │         ●
          │
          │
          │   ●
          │  危険（安定＋具体）
          └───────────→ 安定
                 苦痛ゾーン
```

- **安定かつ抽象** = 良い（インターフェースが定まっている基盤）
- **不安定かつ具体** = 良い（詳細は自由に変更できる）
- **安定かつ具体** = 苦痛（変更しにくいのに、変更の要求が多い）
- **不安定かつ抽象** = 無益（抽象なのに、誰も使っていない）

## 実務での活かし方

### 1. 共通ユーティリティ置き場を小さく保つ

`shared/` や `utils/` が巨大化しやすい。**本当に共通なものだけ** を置く。

### 2. ライブラリは抽象的に

自分で作る共有ライブラリは、**具体的な業務ロジックを持たない** ようにする（安定＋抽象）。

### 3. 依存の向きを可視化する

パッケージ間の依存関係図を描き、循環がないか確認する。

### 4. 内部ルールを強制する

ESLintのimportルール、モノレポのパッケージ境界、Nxのboundariesなど、**ツールで依存方向を強制** する。

## 初心者向けの実践ガイド

### 小規模プロジェクト

- **CCP**（同じ理由で変わるものはまとめる）を意識
- **ADP**（循環依存を避ける）を守る

この2つだけで十分です。

### 中〜大規模プロジェクト

- **CRP**（使われないものは別パッケージに）
- **SDP**（安定したものに依存）
- **REP**（バージョン管理する）

ライブラリ化・モノレポ化するときに意識。

## npmパッケージでの例

### REP を満たす

```json
{
  "name": "@company/user-lib",
  "version": "1.2.3",   // バージョン管理あり
  "main": "dist/index.js",
  "files": ["dist"]
}
```

### CRP を満たす

```typescript
// user-lib（ユーザー機能だけを含む）
export { User, UserRepository };

// order-lib（注文機能だけを含む）
export { Order, OrderRepository };
```

**ユーザー機能だけ使いたい人が、order-libを引き込まずに済む**。

## まとめ

| 原則 | 意味 | 一言で |
|------|------|--------|
| REP | 再利用単位=リリース単位 | バージョン管理を |
| CCP | 同じ理由で変わるものは一緒に | 変更の単位でまとめる |
| CRP | 一緒に使われるものは一緒に | 使われないものは除外 |
| ADP | 循環依存するな | 矢印は一方向に |
| SDP | 安定なものに依存 | 不安定→安定 |
| SAP | 安定なら抽象 | DIPの拡大版 |
