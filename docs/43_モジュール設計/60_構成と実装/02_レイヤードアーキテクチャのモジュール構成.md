# レイヤードアーキテクチャのモジュール構成

> この章は「レイヤードをモジュール・ディレクトリにどう落とし込むか」を扱います。スタイル自体の説明は 41 の [[レイヤードアーキテクチャ]] を参照してください。

## この章の目的

**レイヤー（層）** でモジュールを組織化する、最も広く使われる構造を学びます。  
[[03_技術的関心事による分割]] で触れた 3 層を、実践レベルで理解します。

---

## 1. レイヤー構造の基本

**レイヤードアーキテクチャ** とは、関心ごとに **水平な層** に分け、**上から下へ** 依存させる構造です。

```text
  ┌─────────────────────────────┐
  │   Presentation Layer        │  HTTP, UI
  ├─────────────────────────────┤
  │   Application Layer         │  ユースケース
  ├─────────────────────────────┤
  │   Domain Layer              │  業務ルール
  ├─────────────────────────────┤
  │   Infrastructure Layer      │  DB, 外部 API
  └─────────────────────────────┘
         依存の向き: 上 → 下（Domain は下に依存しない）
```

---

## 2. 各レイヤーの責務

| レイヤー | 責務 | 含むもの例 |
|---------|------|-----------|
| **Presentation** | 入出力、HTTP ステータス | Controller, View, DTO 変換 |
| **Application** | ユースケースの orchestration | ApplicationService, CommandHandler |
| **Domain** | 業務ルール・不変条件 | Entity, ValueObject, DomainService |
| **Infrastructure** | 技術詳細 | Repository 実装, ORM, HTTP Client |

```typescript
// Application 層の例
class PlaceOrderUseCase {
  constructor(
    private orderRepo: OrderRepository,  // interface（Domain）
    private payment: PaymentPort
  ) {}

  async execute(cmd: PlaceOrderCommand): Promise<OrderId> {
    const order = Order.create(cmd.items);  // Domain
    await this.payment.charge(order.total);
    await this.orderRepo.save(order);       // Infra 実装が注入
    return order.id;
  }
}
```

---

## 3. レイヤー違反の典型例

**レイヤー違反** = 依存の向きを破ること。

| 違反 | 例 |
|------|-----|
| Presentation → Infrastructure 直行 | Controller が SQL を直接実行 |
| Domain → Infrastructure | Entity が ORM アノテーションだらけ |
| Infrastructure → Presentation | Repository が HTTP レスポンスを返す |

```text
  違反
  Controller ──→ SQL（Infra をスキップ）

  正しい
  Controller → UseCase → Repository(IF) ← RepositoryImpl
```

---

## 4. レイヤード構造のメリット・デメリット

| メリット | デメリット |
|---------|-----------|
| 関心が分かれて理解しやすい | 1 機能が複数層に散らばる |
| インフラの差し替えがしやすい | 小規模では過剰に感じる |
| チームで層分担しやすい | 「どの層？」の議論が増える |

**向く場面**: 中規模以上の Web/API アプリ、CRUD + 業務ルールがあるシステム。

**注意**: レイヤーを **ドメインモジュールごと** に繰り返すと、機能単位の見通しが良くなります（[[03_技術的関心事による分割]]）。

---

## まとめ

- **レイヤード** = 水平分割 + 上から下への依存
- Presentation / Application / Domain / Infrastructure の **4 層** が一般的
- **レイヤー違反**（直行・逆依存）を避ける
- 規模に応じて簡略化し、ドメインごとに層を繰り返す
