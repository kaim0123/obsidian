# 命名・ディレクトリ・パッケージ構成

## この章の目的

**名前とフォルダ構造** が設計意図を伝える方法を学びます。  
コードを開く前に、**ディレクトリ一覧だけで地図** になる状態を目指します。

---

## 1. 名前が設計を表す

良い名前は **責務と境界** を説明します。

| 良い名前 | 悪い名前 |
|---------|---------|
| `order`, `payment` | `core`, `base` |
| `PlaceOrderUseCase` | `OrderManager` |
| `OrderRepository` | `OrderDAO`（層が混在） |

```text
  名前のチェック
  「このモジュールは何をする？」→ 名前だけで答えられるか
```

[[02_ドメインに基づくモジュール設計]] のユビキタス言語と一致させます。

---

## 2. ディレクトリ構造とモジュール境界

**1 ディレクトリ = 1 モジュール（または明確なサブモジュール）** が基本です。

```text
src/
  order/
    domain/
    application/
    infra/
    index.ts          ← 公開 API
  payment/
    domain/
    application/
    infra/
  shared-kernel/      ← 最小限の共有（注意して使う）
```

| 原則 | 説明 |
|------|------|
| 深すぎない | 3〜4 階層が目安 |
| 技術名だけのトップ | `controllers/` 単体は避け、ドメイン配下に |
| 対称性 | 各ドメインモジュールが同じ構造 |

---

## 3. パッケージの公開範囲

言語・ツールで **export 可能な範囲** を制限します。

| 手段 | 例 |
|------|-----|
| barrel file | `order/index.ts` だけ export |
| package.json exports | `"exports": { ".": "./dist/index.js" }` |
| Java module system | `module-info.java` |
| アーキテクチャテスト | domain が infra を import 禁止 |

```typescript
// order/index.ts — 公開面
export { PlaceOrderUseCase } from './application/place-order';
export type { OrderId } from './domain/order-id';
// domain/infra の内部は export しない
```

---

## 4. 命名規則とチームでの統一

| 対象 | 例（TypeScript） |
|------|-------------------|
| モジュール / ディレクトリ | kebab-case: `order-management` |
| クラス / インターフェース | PascalCase: `OrderRepository` |
| 関数 / メソッド | camelCase: `placeOrder` |
| 定数 | UPPER_SNAKE または camelCase（チームで統一） |

- **README または ADR** に規約を 1 ページで文書化
- レビューで **命名と配置** も見る（[[03_チームでモジュール設計を守る]]）

---

## 5. 構成が伝える設計意図

新メンバーが **5 分で構造を把握** できるか、を基準にします。

```text
  構成が伝えること
  order/domain/order.ts     → 注文の核はここ
  order/infra/postgres-*    → DB はインフラ
  order/application/*       → ユースケースの入口
```

| 良いサイン | 悪いサイン |
|-----------|-----------|
| ドメイン名で並ぶ | `util`, `helper`, `misc` が巨大 |
| 各モジュールが対称 | 1 フォルダだけ構造が違う（理由なし） |
| import パスが読める | `../../../` の連続 |

---

## まとめ

- **名前** は責務の説明。ユビキタス言語に合わせる
- **ディレクトリ** = モジュール境界の物理表現
- **公開範囲** を barrel / ツールで制限
- **命名規約** をチームで統一し、構成自体が地図になる
