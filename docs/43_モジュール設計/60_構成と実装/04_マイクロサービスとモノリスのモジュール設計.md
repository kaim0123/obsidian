# マイクロサービスとモノリスのモジュール設計

> この章はモノリス内のモジュール境界とサービス境界の関係を扱います。分散システムとしての判断は 41 の [[02モノリスと分散モノリスとマイクロサービスといつ分けるか]] を参照してください。

## この章の目的

**モノリス内のモジュール** と **マイクロサービス** の関係を理解し、**いつサービスに分けるか** の判断基準を学びます。

---

## 1. モノリス内モジュールとサービス境界の共通点

どちらも **責務・境界・インターフェース** で区切る点は同じです。

| 観点 | モノリス内モジュール | マイクロサービス |
|------|---------------------|-----------------|
| 境界 | パッケージ / ディレクトリ | 独立デプロイ単位 |
| 通信 | 関数呼び出し | HTTP / メッセージ |
| データ | 同一 DB（分離推奨） | サービスごと DB |

```text
  モノリス                    マイクロサービス
  ┌─────────────┐            ┌──────┐  ┌──────┐
  │ order│payment│            │order │  │payment│
  │ module│module │     →      │ svc  │  │ svc  │
  └─────────────┘            └──────┘  └──────┘
  プロセス内                    プロセス間
```

**良いモノリス内モジュール** は、将来サービス分割するときの **候補境界** になります。

---

## 2. いつモジュールをサービスに分けるか

| 分ける理由が強い | 分けない方がよい |
|---------------|-----------------|
| 独立したデプロイ・スケールが必要 | 小チーム・小規模 |
| チームが完全に独立 | 頻繁な横断変更 |
| 技術スタックを分けたい | トランザクション整合性が厳しい |
| 障害の分離が重要 | ネットワーク遅延が許容できない |

```text
  判断フロー（簡易）
  独立デプロイが必要？ ─No→ モジュール分割で十分
         │
        Yes
         ▼
  モジュール境界は明確？ ─No→ 先にモノリス内で整理
         │
        Yes
         ▼
  サービス分割を検討
```

---

## 3. モジュール設計がマイクロサービス分割の土台になる理由

サービス分割前に **モノリス内でモジュール境界を確立** しておくと:

- 依存関係が **すでに一方向**
- 公開 API が **すでに定義** されている
- 分割時は **通信方式を HTTP/イベントに置き換える** 程度

| 段階 | 状態 |
|------|------|
| 1 | スパゲッティモノリス |
| 2 | **モジュール化されたモノリス** ← ここを目指す |
| 3 | サービス分割（必要なら） |

**Distributed Monolith**（分散しただけで密結合）を避けるには、段階 2 が不可欠です。

---

## 4. 過剰分割のリスク

| リスク | 説明 |
|--------|------|
| 運用コスト | デプロイ・監視・ログが N 倍 |
| 分散トランザクション | 整合性が複雑 |
| レイテンシ | ネットワーク往復 |
| デバッグ困難 | リクエストが複数サービスを横断 |

```text
  過剰分割
  UserService → ProfileService → AvatarService → ImageService
       （1 画面表示に 4 回 HTTP）
```

**YAGNI**: 必要になるまでサービス分割しない。まず **モジュール** で境界を学ぶ。

---

## まとめ

- モノリス内モジュールとサービスは **境界設計の考え方が共通**
- サービス分割は **独立デプロイ・チーム・障害分離** が理由のとき
- **モジュール化されたモノリス** が分割の土台
- **過剰分割** は運用・整合性・性能のコストを増やす
