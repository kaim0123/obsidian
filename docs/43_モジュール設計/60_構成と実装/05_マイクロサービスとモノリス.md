# マイクロサービスとモノリス — 分割粒度のトレードオフ

## はじめに

システムの **アプリケーション全体をどう分けるか** という、最も大きな粒度での分割の話。

- **モノリス（Monolith）** … **1つの大きなアプリ** として作る
- **マイクロサービス（Microservices）** … **複数の小さなサービス** に分けて作る

どちらが優れているというものではなく、**それぞれにトレードオフ** があります。

---

## モノリスとは

### 構造

```
┌────────────────────────────────────┐
│         1つのアプリケーション        │
│  ┌──────┐ ┌──────┐ ┌──────┐       │
│  │ユーザー│ │ 注文  │ │在庫   │       │
│  └──────┘ └──────┘ └──────┘       │
│         ↓         ↓         ↓         │
│         ┌───────────────┐             │
│         │    1つのDB     │             │
│         └───────────────┘             │
└────────────────────────────────────┘
1プロセス、1デプロイ、1データベース
```

全機能が **1つのコードベース・1つのプロセス** で動く。

### メリット

- **開発が簡単**
- **デバッグしやすい**
- **トランザクションが扱いやすい**（同じDB内で整合を取れる）
- **デプロイが単純**（1つのサービスを動かすだけ）
- **パフォーマンスが良い**（ネットワーク越しの通信がない）

### デメリット

- **コードが巨大化**
- **チーム同士の衝突**（同じコードを触る）
- **一部の変更で全体を再デプロイ**
- **技術スタックを統一しないといけない**
- **スケールが難しい**（一部だけ増やせない）

---

## マイクロサービスとは

### 構造

```
┌─────────┐  ┌─────────┐  ┌─────────┐
│ユーザー  │  │ 注文    │  │ 在庫    │
│サービス  │  │サービス  │  │サービス  │
└────┬────┘  └────┬────┘  └────┬────┘
     ↓            ↓            ↓
 ┌──────┐   ┌──────┐   ┌──────┐
 │ DB-A │   │ DB-B │   │ DB-C │
 └──────┘   └──────┘   └──────┘
```

機能ごとに **独立したサービス** を動かし、HTTP/gRPC/メッセージングで連携する。

### メリット

- **独立したデプロイ**（影響範囲が狭い）
- **チーム独立**（他チームに邪魔されない）
- **技術選択の自由度**（Node.js + Go + Python など）
- **障害の隔離**（1サービス落ちても他は動く）
- **個別にスケール可能**
- **境界づけられたコンテキスト** に合わせて切りやすい

### デメリット

- **複雑さが爆増**（デプロイ・監視・ログ・トレース）
- **分散トランザクションが難しい**
- **ネットワーク起因の問題**（遅延・失敗・タイムアウト）
- **開発環境の構築が大変**
- **チームに経験が必要**（初心者には厳しい）
- **初期コストが高い**

---

## 比較表

| 観点 | モノリス | マイクロサービス |
|------|---------|----------------|
| 開発のしやすさ | 簡単 | 難しい |
| デプロイ | 1つ | サービスごと |
| 一貫性 | 強い（ACID） | 弱い（結果整合性） |
| チーム数 | 1〜少数 | 多数 |
| スケール | 難しい | 個別に可 |
| 技術スタック | 統一 | 自由 |
| 障害の局所化 | 低い | 高い |
| ネットワーク遅延 | なし | あり |
| 運用コスト | 低い | 高い |
| 初期開発コスト | 低い | 高い |

---

## 「モノリスが悪」ではない

一時期「マイクロサービスが正義」という風潮がありましたが、**モノリスは現在も現役** です。

### モノリスが向く場面

- **小〜中規模** のプロジェクト
- **スタートアップ初期**（仕様が不確定）
- **チームが小さい**（10人以下）
- **運用体制が整っていない**
- **業務ロジックがそれほど複雑でない**

### マイクロサービスが向く場面

- **大規模** な組織・システム
- **チームが多数**（コンウェイの法則）
- **異なる技術が必要**
- **個別のスケールが必要**
- **障害の隔離が重要**
- **既に運用体制が整っている**

---

## マジョニスとモジュラーモノリス

最近注目されているのが、**モジュラーモノリス（Modular Monolith）** です。

- **1つのアプリ**として動かす（デプロイ単位はモノリス）
- **内部では明確にモジュールで分ける**（境界づけられたコンテキストを意識）
- **将来必要になったら** マイクロサービスに切り出せる

```
┌──────────────────────────────────────┐
│  モジュラーモノリス（1アプリ）          │
│  ┌─────────┐ ┌─────────┐ ┌────────┐ │
│  │ user    │ │ order   │ │ stock  │ │
│  │ module  │ │ module  │ │ module │ │
│  └─────────┘ └─────────┘ └────────┘ │
│      ↕（内部API）    ↕          ↕     │
└──────────────────────────────────────┘
```

**マイクロサービスの設計思想** と、**モノリスのシンプルさ** のハイブリッド。多くのプロジェクトでは、これが現実的な選択肢。

---

## 「マイクロ」の粒度

「マイクロ」と名がついていても、**コードが少ない必要はありません**。

- **1サービス = 1業務境界**
- **独立してデプロイ・運用できる**
- **内部は1つのアプリとして十分な機能を持つ**

粒度が細かすぎる（例: 1 関数 = 1 サービス）のは **ナノサービス** と揶揄されることも。逆効果です。

---

## マイクロサービスの代表的な課題

### 1. 分散トランザクション

複数サービスをまたいだデータ整合性をどう取るか。

- **Saga パターン**: 各サービスが自分の処理 + 補償トランザクションを持つ
- **結果整合性**: 一時的なズレを許容

### 2. サービス間通信

- 同期通信（HTTP/gRPC）: シンプルだが依存が強くなる
- 非同期通信（メッセージキュー）: 疎結合だが複雑

### 3. 観測性（Observability）

- **分散トレーシング**（OpenTelemetry, Jaeger）
- **集約ログ**（ELK, Loki）
- **メトリクス**（Prometheus）

何か問題が起きたとき、**どのサービスの、どの処理で失敗したか** を追える仕組みが必須。

### 4. サービスディスカバリ

どのサービスがどこにあるかを動的に解決する（Kubernetes, Consul）。

---

## どう始めるか

### 基本方針: 「モノリスファースト」

1. まず **モノリス** で作る
2. 業務を理解し、**境界づけられたコンテキスト** を見つける
3. 成長とともに、**モジュラーモノリス** に整理
4. どうしても必要なら、**一部をマイクロサービスに切り出す**

**最初からマイクロサービス** は危険。業務を理解する前に分けると、間違った境界で分けてしまい、**やり直しが巨大コスト** になります。

---

## よくある失敗

### 1. 早すぎるマイクロサービス化

業務理解が浅いまま分けて、後で **境界の引き直し** に大きな手戻り。

### 2. サービス間の強結合

「マイクロサービス」と言いつつ、サービス間の呼び出しが多すぎて、**実質モノリス + ネットワーク遅延** 状態。

### 3. 運用コストを過小評価

マイクロサービスは、**インフラ・監視・CI/CDの整備コスト** が大きい。これを甘く見積もると破綻する。

### 4. データ共有

複数サービスが同じDBテーブルを触る → 密結合。**DBも分ける**。
