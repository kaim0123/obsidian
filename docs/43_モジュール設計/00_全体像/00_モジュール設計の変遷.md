# モジュール設計 — 西暦順でたどる

## このノートの目的

**モジュール設計** とは、コードを **「まとまりのある単位（モジュール・パッケージ・コンポーネント）」** に分け、**中身のまとまり（凝集）** と **つながり方（結合）** を整えることです。

アーキテクチャが「家全体の間取り」なら、モジュール設計は **「部屋の役割分担と、部屋同士のドアの付け方」** に相当します（[[MOC_ソフトウェア設計体系|設計]]）。

このノートでは、モジュール設計の考え方を **登場が早い順（おおよその西暦）** に並べ、次の流れで整理します。

1. **その前に、どんな課題があったか**
2. **何を提案したか**
3. **どう解決したか**
4. **向いている場面・限界**

詳細は各章のリンク先ノートも参照してください。

---

| 3 | **高凝集・低結合** | 1968〜1974年 | まとまりよく、ゆるくつなぐ | 良い分割の物差しがない |

| 8 | **コンポーネント再利用（OSGi 等）** | 1990年代〜2000年代 | バイナリ単位で差し替え | ソースレベル再利用の限界 |

| 11 | **機能分割（Feature First / Vertical Slice）** | 2010年代〜 | 業務機能ごとに縦に切る | レイヤー横断の変更コスト |
| 12 | **マイクロサービス** | 2014年頃 | デプロイ単位でサービス分割 | 巨大モノリスのリリース瓶頸 |

## 0. その前：モノリシック（分割なし）

モジュールという概念が確立する前、プログラムは **1 つの大きな塊** として書かれていました。

### よく起きていた課題

- **グローバル変数** がどこからでも書き換えられ、原因調査が困難
- **`goto` 乱用** により、処理の流れが追えない（スパゲッティコード）
- 数千行を超えると **全体像を把握できない**
- 1 か所を直すと **想定外の副作用** が連鎖する

### 次の時代への問い

> **「大きなプログラムを、どう小さな単位に分け、つなぎ方のルールを決めるか？」**

この問いが、モジュール設計の出発点になりました。

## 1. 手続き・サブルーチン分割（1960年代）

**背景:** 構造化プログラミング（Dijkstra ら）、Fortran / ALGOL / COBOL の普及  
**一言:** 処理を **名前付きの手続き（関数・サブルーチン）** に分ける  
**詳細:** [[00_ソフトウェア設計の変遷#1. 手続き指向（1950年代〜）]]

### その前の課題 — 巨大プログラムの把握不能

- すべての処理が `main` から直線的に続き、**再利用** できない
- 同じ処理をコピペし、修正漏れが発生
- 「この処理、どこにある？」が分からない

### 何を提案したか

**トップダウン設計** で大きな問題を **小さな手続き** に分解する。

```text
main()
  ├─ input_data()
  ├─ validate()
  ├─ calculate()
  └─ output_result()
```

### どう解決したか

- 処理を **名前付き単位** に分割し、読みやすさ・テスト容易性を向上
- **3 つの基本構造**（順次・分岐・反復）だけで制御フローを組み立て、`goto` を排除

### 向いている場面・限界

- **向く:** 小規模プログラム、手続き的な処理の整理
- **限界:** データと手続きが **別モジュールに散らばり** 整合性が保てない → 情報隠蔽・OOP へ

---

## 2. 情報隠蔽 — Parnas モジュール（1972年）

**提唱:** David L. Parnas（*On the Criteria To Be Used in Decomposing Systems into Modules*）  
**一言:** **設計判断（design decision）** ごとに隠す  
**詳細:** [[04_インターフェースと抽象化]]

### その前の課題 — フローチャート順の分割

- モジュール分割を **処理の流れ（フローチャート）** に沿って行うと、**1 つの設計判断が複数モジュールに散らばる**
- 例: データ形式を変えると、流れ上「後ろ」のモジュールばかりでなく **全体** に手を入れる必要がある
- **内部実装の詳細** が外に漏れ、変更の影響が広がる

### 何を提案したか

| 分割の軸 | 従来（悪い例） | Parnas の提案 |
|---------|--------------|--------------|
| 基準 | 処理の流れ順 | **設計判断・変更理由** |
| モジュールの中身 | 処理ステップの塊 | **1 つの秘密（secret）** を持つ塊 |
| 外部との接触 | 内部データを直接触る | **インターフェース（契約）** だけ公開 |

```
  モジュール A                    モジュール B
  ┌─────────────┐               ┌─────────────┐
  │  秘密（内部）  │               │  秘密（内部）  │
  │  ─────────  │  インターフェース │  ─────────  │
  │  実装の詳細   │ ←──────────→ │  実装の詳細   │
  └─────────────┘               └─────────────┘
```

### どう解決したか

- **情報隠蔽（Information Hiding）:** 変更されうる詳細をモジュール内部に閉じ込める
- 外部は **「何ができるか（インターフェース）」** だけ知ればよい
- 後の **カプセル化・抽象データ型・DIP** の思想的源流

### 向いている場面・限界

- **向く:** すべてのモジュール設計の **根底にある考え方**
- **限界:** インターフェース設計そのものの良し悪しは別問題 → 高凝集・低結合の物差しが必要

## 3. 高凝集・低結合（1968〜1974年）

**提唱:** Larry L. Constantine, Wayne Stevens, Glenford Myers（*Structured Design*, 1974年）  
**一言:** モジュール内は **まとまりよく**、モジュール間は **ゆるやかに**  
**詳細:** [[03_疎結合と高凝集]]、[[00_設計原則の変遷#2. 高凝集・低結合]]

### その前の課題 — 良い分割の物差しがない

- モジュール分割は行われ始めたが、**「この分け方、良いの？」** を客観的に語れない
- 関係のない処理が 1 モジュールに混在（**低凝集**）
- モジュール同士が内部まで知り合い（**密結合**）

### 何を提案したか

| 尺度 | 悪い状態 | 良い状態 |
|------|---------|---------|
| **凝集度** | 目的の違う処理が混在 | 同じ目的の処理だけが集まる |
| **結合度** | 内部まで相互に依存 | 最小限のインターフェースだけで接続 |

### どう解決したか

- **高凝集:** 変更の理由が同じものは 1 モジュールにまとめ、影響を局所化
- **低結合:** モジュール間は抽象越しに接続し、差し替え・テストを容易に
- Parnas の情報隠蔽を **評価・改善するための物差し** として機能

### 向いている場面・限界

- **向く:** あらゆる粒度（関数・クラス・パッケージ・サービス）の **品質評価**
- **限界:** 物差しはあるが **具体的な切り方の指針** は別途必要 → SoC、レイヤー分割、機能分割へ

## 4. 関心の分離 — SoC（1974年）

**提唱:** Edsger W. Dijkstra  
**一言:** **目的の違う処理** は別のモジュールに分ける  
**詳細:** [[01_関心の分離]]、[[00_設計原則の変遷#3. 関心の分離 SoC]]

### その前の課題 — 1 モジュールに複数の関心

- 1 つの関数・モジュールに **表示・検証・永続化・通知** が混在
- 正しさ・効率・見た目など **評価軸の異なる性質** を同時に扱うと思考が混乱
- 1 か所の変更が **無関係な関心** に波及

### 何を提案したか

**異なる関心（concern）** — 目的・責任・評価軸 — を **別の場所** に分離する。

```
  ❌ 1 モジュールに全部
  registerUser() { 表示 + 検証 + DB保存 + メール送信 }

  ✅ 関心ごとに分離
  UserController  → 表示・入力
  UserValidator   → 検証
  UserRepository  → 永続化
  MailService     → 通知
```

### どう解決したか

- 1 つの関心に集中して **設計・実装・テスト** できる
- 高凝集・低結合と組み合わさり、**MVC・レイヤードアーキテクチャ** の根底にある

### 向いている場面・限界

- **向く:** すべてのモジュール分割の **基本原則**
- **限界:** 「何が 1 つの関心か」の判断が難しい → レイヤー分割 vs 機能分割の議論へ

## 5. 言語モジュール・パッケージ（1970〜1990年代）

**背景:** Modula-2（1978）、Ada packages（1980）、C の translation unit、Java packages（1995）  
**一言:** **コンパイル単位** と **名前空間** を言語・ビルドシステムで支える

### その前の課題 — 独立ビルドと名前衝突

- ソースレベルで分けても、**全部再コンパイル** しないとビルドできない
- 大規模プロジェクトで **関数名・変数名の衝突** が頻発
- **アクセス制御**（public / private）が言語レベルでない

### 何を提案したか

| 仕組み | 役割 |
|--------|------|
| **コンパイル単位**（C の .c + .h） | 変更された部分だけ再コンパイル |
| **モジュールシステム**（Modula-2, Ada） | `import` / `export` で公開 API を明示 |
| **パッケージ**（Java） | 名前空間 + アクセス修飾子（public, protected, package-private） |
| **名前空間**（C++） | シンボルの衝突を防ぐ |

### どう解決したか

- Parnas の **インターフェース vs 実装** を、**言語とビルドツール** で強制
- モジュール境界が **物理的なファイル・ディレクトリ** として表現される

### 向いている場面・限界

- **向く:** 中〜大規模プロジェクトの **ビルド効率と名前管理**
- **限界:** 言語のパッケージは **技術的な整理** であり、**業務の切り方** とは一致しない → DDD へ

---

## 6. レイヤー分割 — 水平分割（1990年代）

**背景:** 3 層アーキテクチャ、クライアント・サーバー型業務システムの普及  
**一言:** **役割（技術的関心）** ごとに層で分ける  
**詳細:** [[04_モジュール分割の考え方#レイヤー別（水平分割）]]、[[アーキテクチャ#2. 3 層アーキテクチャ]]

### その前の課題 — 技術的責務の混在

- MVC だけでは Model の中に DB アクセス・ビジネスルール・画面用整形が混ざる
- フォルダ構成が **技術名**（controller, service, model）で、**業務が見えない**
- 1 機能追加で **複数の層フォルダ** をまたぐ必要がある

### 何を提案したか

**技術的な役割** で水平に分割する。

```
src/
├─ controllers/     ← プレゼンテーション
├─ services/        ← ビジネスロジック
├─ repositories/    ← データアクセス
└─ models/          ← データ構造
```

### どう解決したか

- **「この処理、どこに書く？」** が層のルールで決まる
- 同じ役割のコードが **1 か所に集まる**（初心者に理解しやすい）
- 小〜中規模では **十分に整理された** 構成

### 向いている場面・限界

- **向く:** 小〜中規模、チームが小さい、CRUD 中心のアプリ
- **限界:** 大規模になると **同じ層のフォルダが肥大化**、機能の境界が見えない → 機能分割・DDD へ

---

## 7. パッケージ設計原則（1990年代〜2002年）

**提唱:** Robert C. Martin（*Agile Software Development*, 2002）  
**一言:** パッケージ（モジュール）にも **SOLID 的な 6 原則** を適用  
**詳細:** [[01_パッケージ設計の原則]]

### その前の課題 — 大規模パッケージの腐敗

- クラス設計は SOLID で語れるが、**パッケージレベル** の指針が不足
- パッケージ間に **循環依存** が発生し、ビルド順序が決まらない
- `utils/` や `common/` が **巨大化** し、変更の影響が全体に波及
- 安定したパッケージが **具体実装** を持ち、変更しにくい

### 何を提案したか

**凝集の 3 原則** と **結合の 3 原則**。

| 原則 | 意味 | 一言 |
|------|------|------|
| **REP** | 再利用単位 = リリース単位 | バージョン管理を |
| **CCP** | 同じ理由で変わるものは一緒に | SRP のパッケージ版 |
| **CRP** | 一緒に使われるものは一緒に | ISP のパッケージ版 |
| **ADP** | 循環依存するな | 矢印は一方向に |
| **SDP** | 安定なものに依存 | 不安定 → 安定 |
| **SAP** | 安定なら抽象 | DIP のパッケージ版 |

### どう解決したか

- 高凝集・低結合を **パッケージ粒度** で具体化
- **CCP + ADP** だけで小規模プロジェクトは十分
- モノレポ・npm パッケージ化のときに **REP / CRP / SDP** が効く

### 向いている場面・限界

- **向く:** 中〜大規模、ライブラリ化、モノレポ
- **限界:** REP / CCP / CRP は **同時に完全には満たせない** トレードオフ → 段階に応じて重視する原則を選ぶ

## 8. コンポーネント再利用 — OSGi 等（1990年代〜2000年代）

**背景:** COM / DCOM（Microsoft）、CORBA、OSGi（1999）、EJB  
**一言:** **バイナリ単位** でモジュールを差し替え・再利用する

### その前の課題 — ソースレベル再利用の限界

- ソースコードをコピーすると **バージョン管理が不能**
- 1 つの変更が **全利用者に波及**
- 実行時に **プラグインの追加・削除** ができない

### 何を提案したか

| 仕組み | 特徴 |
|--------|------|
| **DLL / 共有ライブラリ** | バイナリをリンクして再利用 |
| **COM / CORBA** | インターフェース契約によるコンポーネント連携 |
| **OSGi** | JVM 上で **動的に** バンドル（モジュール）をロード・アンロード |
| **EJB** | サーバー側コンポーネントの標準化（当時のエンタープライズ Java） |

### どう解決したか

- Parnas の情報隠蔽を **デプロイ・実行時** まで拡張
- **REP（再利用 = リリース単位）** の実践形

### 向いている場面・限界

- **向く:** プラグインアーキテクチャ、製品のカスタマイズ、大規模エンタープライズ
- **限界:** 設定・バージョン管理が複雑。現代では **npm / Cargo / Maven** などパッケージマネージャ + モノレポが主流

---

## 9. DDD — 境界づけられたコンテキスト（2003年）

**提唱:** Eric Evans（*Domain-Driven Design*）  
**一言:** **業務の区切り** でモジュール境界を決める  
**詳細:** [[02_DDDとは]]、[[03_境界づけられたコンテキストとコンテキストマップ]]、[[04_境界づけられたコンテキスト]]

### その前の課題 — 技術軸分割と用語のズレ

- `controllers/` `services/` の **技術名フォルダ** では、**業務の境界** が見えない
- 開発者と現場の **用語がズレ**、同じ「顧客」が文脈によって意味が違う
- 1 つの巨大モデルに全部詰め込み、**矛盾したルール** が共存

### 何を提案したか

**境界づけられたコンテキスト（Bounded Context, BC）** — ユビキタス言語が **一貫して通用する** 境界。

```
  営業コンテキスト          請求コンテキスト
  ┌──────────────┐       ┌──────────────┐
  │ Customer      │       │ Customer      │
  │ （見込み客）    │  ≠   │ （請求先）      │
  │ Order（見積）   │       │ Invoice       │
  └──────────────┘       └──────────────┘
       ↑ 別モジュールとして独立
```

### どう解決したか

- モジュール分割の軸を **技術** から **ビジネス** に移す
- BC 間は **コンテキストマップ** で明示的に連携（Shared Kernel, Anti-Corruption Layer 等）
- **1 デプロイ（モノリス）の中でも** パッケージ・モジュール境界として BC を切れる

### 向いている場面・限界

- **向く:** 業務ルールが複雑、複数チーム、長期保守
- **限界:** 単純 CRUD では過剰。BC ≠ 必ずマイクロサービス（モノリス内モジュールでもよい）

## 10. ヘキサゴナル / オニオン / クリーン — 依存の向きで層を分ける（2005〜2012年）

**提唱:** Alistair Cockburn（2005）、Jeffrey Palermo（2008）、Robert C. Martin（2012）  
**一言:** **依存は常に内側（ドメイン）へ**、外側は差し替え可能に  
**詳細:** [[アーキテクチャ#6〜8]]、[[ヘキサゴナルアーキテクチャ]]、[[クリーンアーキテクチャの概要]]

### その前の課題 — ドメインが DB・UI に依存

- レイヤー分割しても、ビジネスロジックが **MySQL や REST API に直接依存**
- フォルダは分かれているが、**import の向き** が乱れ、テストのたびに DB が必要
- 「ドメイン層」「アプリケーション層」の **物理的な置き場所** がプロジェクトごとにバラバラ

### 何を提案したか

**同心円状のモジュール構造** — 内側ほど安定、外側ほど詳細（フレームワーク・DB）。

```
       ┌─────────────────────────┐
       │  Infrastructure（外）   │  ← DB, UI, Framework
       │  ┌─────────────────────┐ │
       │  │ Use Cases / App     │ │  ← アプリケーションサービス
       │  │ ┌─────────────────┐ │ │
       │  │ │  Domain / Core  │ │ │  ← エンティティ・ドメインルール
       │  │ └─────────────────┘ │ │
       │  └─────────────────────┘ │
       └─────────────────────────┘
              依存はすべて内側へ
```

### どう解決したか

- **Port / Adapter** または **Interface Adapters** で、外側と内側の接続点を明示
- **DIP** を **フォルダ構成・import ルール** として表現
- モジュール内の **依存方向** を統一し、変更の影響を内側に閉じ込める

### 向いている場面・限界

- **向く:** 1 サービス（モノリス）内の **モジュール構造**、DDD と組み合わせ
- **限界:** 小規模 CRUD では抽象化が過剰。3 つのアーキテクチャは **思想がほぼ同じ** で用語の違いが主

---

## 11. 機能分割 — Feature First / Vertical Slice（2010年代〜）

**背景:** Screaming Architecture（Robert C. Martin）、Vertical Slice Architecture（Jimmy Bogard）、Feature Folders  
**一言:** **業務機能ごと** に縦に切る  
**詳細:** [[04_モジュール分割の考え方#機能別（垂直分割）]]

### その前の課題 — レイヤー横断の変更コスト

- 注文機能を 1 つ追加するのに `controllers/` `services/` `repositories/` `models/` **全部** を触る
- フォルダを開くと **「MVC だ」と叫んでいる** が、**「注文システムだ」とは叫んでいない**
- チーム分担が **技術スキル**（フロント担当、DB 担当）基準になり、**機能のオーナーシップ** が不明確

### 何を提案したか

**機能（Feature）** 単位で **縦に** すべての層を含めて分割する。

```
src/
├─ features/
│   ├─ order/              ← 注文機能（全部ここ）
│   │   ├─ OrderController.ts
│   │   ├─ OrderService.ts
│   │   ├─ OrderRepository.ts
│   │   └─ Order.ts
│   ├─ user/
│   └─ product/
└─ shared/                 ← 本当に共通なものだけ
```

### どう解決したか

- **1 機能 = 1 フォルダ** で凝集度が最大化（CCP の実践）
- 機能単位で **開発・削除・チーム分担** できる
- DDD の BC と組み合わせると、**業務が見えるフォルダ構成**（Screaming Architecture）になる

### 向いている場面・限界

- **向く:** 中〜大規模、機能ごとにチーム分担、モジュラーモノリス
- **限界:** `shared/` の肥大化、`common/` 地獄。小規模では **レイヤー別の方がシンプル**

---

## 12. マイクロサービス（2014年頃）

**背景:** Netflix 等の実践、Martin Fowler / James Lewis による整理  
**一言:** **デプロイ単位** でサービスに分割  
**詳細:** [[05_マイクロサービスとモノリス]]、[[アーキテクチャ#10. マイクロサービス]]

### その前の課題 — 巨大モノリスのリリース瓶頸

- 小さな修正でも **全体を再デプロイ**
- 100 人規模のチームが 1 コードベースで **コンフリクト**
- 在庫だけスケールしたいのに **全部同じサーバー**
- モジュール境界が **コード上はあっても、デプロイ・データ所有権が共有**

### 何を提案したか

**独立したサービス** として分割。各サービスは **自分のデータを所有** する。

```
  ┌─────────┐   ┌─────────┐   ┌─────────┐
  │ 注文     │   │ 在庫     │   │ ユーザー  │
  │ サービス  │   │ サービス  │   │ サービス  │
  └────┬────┘   └────┬────┘   └────┬────┘
       └─────────────┴─────────────┘
              API / イベント で連携
```

### どう解決したか

- モジュール分割の粒度が **プロセス・デプロイ単位** まで拡大
- **独立デプロイ・スケール・チーム自律** を実現
- 内部構造は **クリーン + DDD**、連携は **EDA** と組み合わせることが多い

### 向いている場面・限界

- **向く:** 大規模、複数チーム、部分ごとにリリース頻度が違う
- **限界:** 分散システムの複雑さ。小さなチームでは **モノリスファースト** が合理的

---

## 13. モジュラーモノリス — Modulith（2010年代〜2020年代）

**背景:** Simon Brown、Robert C. Martin の Modular Monolith 提唱、Spring Modulith（2023）  
**一言:** **1 アプリ** の中で **モジュール境界を厳格に守る**  
**詳細:** [[05_マイクロサービスとモノリス#マジョニスとモジュラーモノリス]]

### その前の課題 — 2 つの極端

| 極端 | 問題 |
|------|------|
| **境界なきモノリス** | モジュール分割のルールが守られず、再びスパゲッティ化 |
| **早すぎるマイクロサービス** | 業務理解前に分割し、**境界の引き直し** に巨大コスト |

### 何を提案したか

```
┌──────────────────────────────────────┐
│  モジュラーモノリス（1 アプリ・1 デプロイ） │
│  ┌─────────┐ ┌─────────┐ ┌────────┐ │
│  │ user    │ │ order   │ │ stock  │ │
│  │ module  │ │ module  │ │ module │ │
│  └─────────┘ └─────────┘ └────────┘ │
│      ↕ 内部 API のみ     ↕          ↕ │
└──────────────────────────────────────┘
```

- **デプロイは 1 つ**（モノリスのシンプルさ）
- **内部は BC 単位** で明確に分離（マイクロサービスの設計思想）
- **必要になったら** モジュールをサービスとして切り出せる

### どう解決したか

- **Feature First + DDD + パッケージ原則（ADP/CCP）** を 1 アプリ内で実践
- ESLint import ルール、Nx boundaries、Spring Modulith など **ツールで境界を強制**
- 「モノリスファースト → 痛みが出たら外に出す」という **進化の中間点**

### 向いている場面・限界

- **向く:** 多くの中〜大規模プロジェクトの **現実的な第一選択**
- **限界:** 境界の設計・維持に **規律とツール** が必要。形だけ作っても意味がない

## 14. 分割軸の進化 — 何を基準に切るか

モジュール設計の歴史は、**「何を基準に切るか」** の変遷でもあります。

| 段階 | 分割の基準 | フォルダの例 | 主な焦点 |
|------|-----------|-------------|---------|
| 手続き分割 | **処理の流れ** | `main`, `validate()`, `calculate()` | 読みやすさ |
| 情報隠蔽 | **設計判断・秘密** | インターフェース / 実装 | 変更の局所化 |
| レイヤー分割 | **技術的役割** | `controllers/`, `services/` | 責務の固定 |
| 機能分割 | **業務機能** | `order/`, `user/` | 凝集・チーム分担 |
| DDD | **業務の言語・文脈** | `sales/`, `billing/`（BC） | 用語の一貫性 |
| クリーン等 | **安定性・依存の向き** | `domain/`, `infrastructure/` | 変更に強い中心 |
| マイクロサービス | **デプロイ・データ所有権** | 独立リポジトリ・DB | 組織・リリース自律 |

```
  処理の流れ → 設計判断 → 技術的役割 → 業務機能 → デプロイ単位
  （1960s）    （1972）    （1990s）     （2000s〜）  （2014〜）
```

---

## 15. 2 つの分割軸 — 水平 vs 垂直

現代のモジュール設計で最も実務的な問いは、**水平（レイヤー）と垂直（機能）のどちらを主軸にするか** です。

| 軸 | 切り方 | 向く規模 | 関連 |
|----|--------|---------|------|
| **水平（レイヤー別）** | controller / service / model | 小〜中規模 | §6 レイヤー分割 |
| **垂直（機能別）** | order / user / product | 中〜大規模 | §11 機能分割 |
| **ハイブリッド** | 機能フォルダ + 内部でレイヤー | 中規模 | [[04_モジュール分割の考え方#規模による使い分け]] |

```
  水平分割                    垂直分割
  controllers/               order/
  services/        vs          ├─ controller
  repositories/               ├─ service
  models/                     └─ repository
                              user/
                              └─ ...
```

**最初から最終形を目指さない。** 規模に応じて段階的に進化させる（[[04_モジュール分割の考え方#ディレクトリ構成の進化パターン]]）。

## 16. まとめ — 歴史は「課題の積み重ね」

```text
モノリシック（グローバル・goto）
    ↓ 処理を名前付き単位に
  手続き・サブルーチン分割
    ↓ 設計判断ごとに隠す
  情報隠蔽（Parnas, 1972）
    ↓ 良し悪しを測る物差し
  高凝集・低結合 + 関心の分離
    ↓ 言語・ビルドで物理化
  言語モジュール・パッケージ
    ↓ 技術的役割で水平分割
  レイヤー分割（1990s）
    ↓ パッケージにも SOLID 的ルール
  パッケージ設計原則（REP/CCP/CRP/ADP/SDP/SAP）
    ↓ 業務の区切りで分ける
  DDD・境界づけられたコンテキスト（2003）
    ↓ 依存の向きで層を整理
  ヘキサゴナル → オニオン → クリーン（2005〜2012）
    ↓ 業務機能ごとに縦分割
  機能分割 / Feature First（2010s〜）
    ↓ デプロイ単位まで拡大
  マイクロサービス（2014〜）
    ↓ 1 アプリ内で境界を厳格に
  モジュラーモノリス / Modulith（2010s〜2020s）
```

### 初心者が覚えておくとよいこと

1. **情報隠蔽がすべての根っこ。** 内部を隠し、インターフェースだけ公開する — Parnas（1972）から変わっていない。
2. **新しいほど良いわけではない。** 小規模ならレイヤー分割、中規模ならハイブリッド、大規模なら機能分割 + モジュラーモノリス。
3. **水平と垂直は排他ではない。** 機能フォルダの中に controller / service を置く **ハイブリッド** が現実的。
4. **アーキテクチャと組み合わせる。** 例: モジュラーモノリス + DDD の BC + クリーンの依存方向 + 必要なら一部マイクロサービス化。
