# ケーススタディ：業務システム

## この章の目的

**受注・在庫・請求** を含む業務システムを題材に、複雑なルール・チーム分担・外部連携のモジュール設計を学びます。

---

## 1. 複雑な業務ルールの分割

| ドメイン | 主なルール |
|---------|-----------|
| 受注 | 注文確定、キャンセル、ステータス遷移 |
| 在庫 | 引当、解放、在庫不足 |
| 請求 | 請求書発行、税計算、入金消込 |

```text
  業務ルールは「そのドメインのモジュール内」に
  order/domain/   … キャンセル条件
  inventory/domain/ … 引当ルール
  billing/domain/   … 税・請求タイミング
```

**共通の計算**（税）が必要なら `shared-kernel` または `billing` が提供する **値オブジェクト** を検討 — 巨大 common は避けます。

---

## 2. 複数チームでのモジュール分担

| チーム | 担当モジュール |
|--------|---------------|
| 受注チーム | order, catalog |
| 物流チーム | inventory, shipping |
| 経理チーム | billing, payment |

```text
  Conway の法則
  組織の構造 ≒ システムのモジュール構造
```

| 運用 | 内容 |
|------|------|
| CODEOWNERS | モジュールごと |
| 公開 API レビュー | 他チーム影響のある変更 |
| コンテキストマップ | チーム間の統合方式を文書化 |

[[01_戦略的設計]] のコンテキスト境界と対応させます。

---

## 3. 外部システム連携の境界

| 外部 | モジュール側 |
|------|-------------|
| 決済 GW | payment/infra/StripeAdapter |
| 倉庫 WMS | shipping/infra/WmsClient |
| 会計 ERP | billing/infra/ErpExporter |

```text
  order (domain)
       │
       ▼ PaymentPort (interface)
  payment/infra/StripeAdapter → 外部 API
```

- **アンチコラプション層（ACL）** で外部のモデルを内部モデルに変換
- 外部 DTO を domain に持ち込まない

---

## 4. よくある設計ミスと修正

| ミス | 修正 |
|------|------|
| 全モジュールが `orders` テーブルに直接 SQL | OrderRepository のみ書き込み、他は Query API |
| 在庫引当を Order 内で直接 SQL | inventory モジュールの `reserve()` を呼ぶ |
| 請求ロジックが order に散在 | billing に集約、OrderPlaced イベントで連携 |
| `integration` 巨大モジュール | 外部ごとに該当ドメインの infra へ |

```text
  Before: order が在庫 SQL を直接実行
  After:  inventory.reserve(orderId, lines) を API 経由
```

---

## まとめ

- 複雑な業務ルールは **ドメインモジュールごと** に domain 層へ
- **チーム境界 ≒ モジュール境界** で並行開発
- 外部連携は **ポート/アダプタ + ACL**
- 共有 DB・巨大 integration は [[010Programming/43_モジュール設計/90_付録/付録C_アンチパターン一覧]] の典型
