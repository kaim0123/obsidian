# モジュール分割の考え方 — 機能別 vs レイヤー別

## はじめに

プロジェクトが大きくなると、**「フォルダをどう切るか」「ファイルをどう分けるか」** という問題に必ずぶつかります。

これを **モジュール分割（module decomposition）** と呼び、大きく2つの軸で考えます。

- **機能別（垂直分割）**: 「ユーザー機能」「注文機能」のように、**業務ごと** に分ける
- **レイヤー別（水平分割）**: 「controller」「service」「model」のように、**役割ごと** に分ける

どちらが正解というわけではなく、**規模と目的に応じて使い分け** ます。

---

## レイヤー別（水平分割）

### 例: 典型的なMVCフォルダ

```
src/
├─ controllers/
│   ├─ UserController.ts
│   ├─ OrderController.ts
│   └─ ProductController.ts
├─ services/
│   ├─ UserService.ts
│   ├─ OrderService.ts
│   └─ ProductService.ts
├─ repositories/
│   ├─ UserRepository.ts
│   ├─ OrderRepository.ts
│   └─ ProductRepository.ts
└─ models/
    ├─ User.ts
    ├─ Order.ts
    └─ Product.ts
```

### メリット

- **役割が揃っている**（「controllerを探す」で全て見つかる）
- **初心者に理解しやすい**
- **小規模なら十分に整理されている**

### デメリット

- **1つの機能追加でフォルダをまたぐ**（user機能を足すのに、controllers/services/repositories/modelsすべてを触る）
- **大規模になると同じ層のフォルダが肥大化**
- **機能の境界が見えなくなる**

---

## 機能別（垂直分割）

### 例: 機能ごとのフォルダ

```
src/
├─ features/
│   ├─ user/
│   │   ├─ UserController.ts
│   │   ├─ UserService.ts
│   │   ├─ UserRepository.ts
│   │   └─ User.ts
│   ├─ order/
│   │   ├─ OrderController.ts
│   │   ├─ OrderService.ts
│   │   ├─ OrderRepository.ts
│   │   └─ Order.ts
│   └─ product/
│       └─ ...
└─ shared/
    └─ ...
```

### メリット

- **1つの機能が1つのフォルダに集まる**（凝集度が高い）
- **機能単位で開発・削除できる**
- **チーム分担しやすい**
- **機能が増えても他のフォルダに影響しない**

### デメリット

- **共通部分（shared）の扱いに悩む**
- **小規模すぎると冗長**
- **機能間の共通化が難しくなる**

---

## 規模による使い分け

### 小規模（〜数十ファイル）

**レイヤー別** で十分。全体を把握しやすい。

### 中規模（数十〜数百ファイル）

**機能別 + レイヤー別のハイブリッド** が有効。

```
src/
├─ user/
│   ├─ controller/
│   ├─ service/
│   └─ model/
├─ order/
│   ├─ controller/
│   ├─ service/
│   └─ model/
└─ shared/
```

### 大規模（数百〜数千ファイル）

**機能別（= 境界づけられたコンテキスト）** が主。モノレポ、マイクロサービスへ発展する。

---

## モジュール分割の原則

### 1. 同じ理由で変わるものは一緒に

SRPをモジュール単位に拡張した原則。機能追加・仕様変更のとき、**1つのフォルダだけ触れば済む** のが理想。

### 2. 依存方向を明確に

- 機能 A → 機能 B への依存はあるか
- 共通部分は両方から依存されていいか
- **循環依存を作らない**

### 3. 公開APIを絞る

各モジュールに **外から使ってよい入口（公開API）** を1つ決め、内部実装は隠す。

```typescript
// user/index.ts — 公開する
export { UserController } from './UserController';
export { User } from './User';

// user/UserRepository.ts — 非公開
```

### 4. 共通部分は慎重に

`shared/`, `common/`, `utils/` は、**全機能から依存される** ため、**変更しにくくなる** リスクあり。必要なものだけ置く。

## 機能の境界をどう見つけるか

### ヒント1: 業務の言葉で分かれる単位

「ユーザー管理」「注文」「請求」「配送」など、業務の人が **別々の話題** として扱う単位。

### ヒント2: 変更理由が違う単位

「セール機能を変えたい」のときに、ユーザー管理まで触る必要がある → 境界が正しくない。

### ヒント3: ライフサイクル・チーム

**別々のタイミングでリリース** する、**別々のチームが担当** するなら、別のモジュールに。

### ヒント4: データの所有権

あるデータを **誰が書き込めるか** で分ける。User機能だけがUser を書き込める、など。

---

## 循環依存の回避

```
A → B
B → A
```

これは **循環依存**。以下の問題を引き起こします。

- ビルド順序が決まらない
- 変更の影響が連鎖する
- テストが書けない
- 理解できない構造になる

### 対策

1. **共通部分を抽出**（A・Bから依存されるC を作る）
2. **依存方向を統一**（どちらかを上位、どちらかを下位に）
3. **イベント駆動にする**（A→B から、A→Event→B へ）

## モジュールの公開APIを考える

### 悪い例: 全部export

```typescript
// user/index.ts
export * from './UserController';
export * from './UserService';
export * from './UserRepository';
export * from './UserValidator';
export * from './UserMailer';
// 内部実装まで全部漏れている
```

### 良い例: 必要なものだけ

```typescript
// user/index.ts
export { UserController } from './UserController';
export type { User } from './User';
// UserService、UserRepository は内部用
```

**「外から触ってよいもの」と「内部用」を分ける** ことで、モジュールを変更しても外への影響を抑えられます。

## Screaming Architecture

Robert C. Martin の言葉：

> **「コードを開いたとき、それが『注文システム』だと叫んでいるべき」**

つまり、

```
❌ src/
    controllers/
    services/
    models/  ← これは「MVC」だと叫んでいる

✅ src/
    order/
    shipping/
    customer/  ← これは「注文管理システム」だと叫んでいる
```

技術ではなく、**業務が見えるフォルダ構成** が理想とされます。

---

## ディレクトリ構成の進化パターン

1. **スタート**: 単一ファイルやフラット構成
2. **レイヤー別**: controller/service/modelに分ける
3. **ハイブリッド**: 機能フォルダ + 内部でレイヤー
4. **機能別**: 完全に業務単位のモジュール
5. **モノレポ / マイクロサービス**: 独立したパッケージ・サービスへ

**最初から最終形を目指さない**。規模に応じて段階的に進化させる。
