# モジュール分割の基本プロセス

## この章の目的

要件から **最初のモジュール分割案** を作る手順を学びます。  
凝集度・結合度の基準を、実際の分割作業に当てはめます。

---

## 1. 要件から責務を抽出する

分割の第一歩は、要件を **「誰が何を担当するか」** に言い換えることです。

### 手順

1. 要件一覧・ユーザーストーリーを読む
2. 各要件について「**主語（担当）**」を考える
3. 似た主語・似た関心をグループ化する

| 要件 | 責務の候補 |
|------|-----------|
| ユーザーがログインする | 認証 |
| 商品をカートに入れる | カート |
| 注文を確定する | 注文 |
| 決済する | 決済 |

```text
  要件リスト
      │
      ▼  責務に変換
  [Auth] [Cart] [Order] [Payment]
```

---

## 2. 名詞と動詞から境界を見つける

[[01_設計の進め方]] と同様の技法を、モジュール単位に使います。

- **名詞** → モジュール候補（Order, User, Product）
- **動詞** → ユースケース・公開 API（placeOrder, cancelOrder）

```text
  「ユーザーが注文をキャンセルする」
     名詞: ユーザー, 注文  → User, Order モジュール
     動詞: キャンセル      → Order.cancel()
```

**注意**: 名詞 1 つ = モジュール 1 つ、とは限りません。関連する名詞は 1 モジュールにまとめることもあります。

---

## 3. 変化の理由（Reason for Change）で分ける

**SRP（単一責任の原則）** のモジュール版: **変化の理由が異なるものは別モジュール** に分けます。

| 変化の理由 | モジュール |
|-----------|-----------|
| 注文ルールの変更 | order |
| 決済 API の変更 | payment |
| UI デザインの変更 | web（プレゼン層） |

```text
  同じタイミングで変わる？ → 同じモジュール
  別の理由で変わる？       → 別モジュール
```

---

## 4. 分割しすぎ・分割不足の見分け方

| 症状 | おそらく |
|------|---------|
| 1 変更で 5 モジュール以上触る | **分割しすぎ** or 依存設計の問題 |
| 1 モジュールが 50 ファイル以上 | **分割不足** |
| モジュール名が説明できない | **分割不足**（責務が混在） |
| モジュール間の呼び出しが多すぎる | **分割しすぎ** |

**目安**: 1 モジュールを **1 文で説明** でき、チームの **1〜3 人が担当** できる粒度。

---

## 5. 最初の分割案を作るワークショップ

### 60 分ワークショップ（例）

| 時間 | 内容 |
|------|------|
| 10 分 | 要件を 3〜5 行に要約 |
| 15 分 | 名詞リスト → モジュール候補 |
| 15 分 | 変化の理由で統合・分割 |
| 10 分 | 依存の矢印を矢印で描く |
| 10 分 | チェックリストでレビュー |

### 成果物

- モジュール一覧（名前 + 1 文説明）
- 依存関係の簡易図
- 公開 API のたたき台

完璧を目指さず、**動く仮説** として始め、実装・テストで修正します（[[04_モジュール設計の進化]]）。

---

## まとめ

- 要件 → **責務** → モジュール候補、の順で考える
- **名詞・動詞** と **変化の理由** が分割の手がかり
- 分割しすぎ・不足は「変更時の触る数」「1 文説明」で判断
- ワークショップで仮説を作り、実装で検証する
