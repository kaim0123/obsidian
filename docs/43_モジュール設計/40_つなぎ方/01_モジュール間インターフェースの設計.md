# モジュール間インターフェースの設計

## この章の目的

モジュール同士が **どうやって通信するか** — 公開 API・契約・命名 — を設計する章です。  
[[03_モジュールのカプセル化と情報隠蔽]] で隠した内部と、外に見せる **境界** を具体化します。

---

## 1. インターフェースの役割

モジュール間の **インターフェース** は、次の役割を持ちます。

| 役割 | 説明 |
|------|------|
| **契約** | 何を渡し、何が返るかを約束する |
| **境界** | 内部実装と外部利用者を分離する |
| **安定点** | 変更しにくい「接合面」になる |

```text
  Module A          Interface          Module B
  ────────          ─────────          ────────
  内部実装    ──→   placeOrder()   ←──  呼び出し
                    cancelOrder()
```

---

## 2. 入力・出力・契約（Contract）

良いインターフェースは **入出力が明確** です。

```typescript
// 契約の例
interface PlaceOrderCommand {
  customerId: string;
  items: { productId: string; quantity: number }[];
}

interface PlaceOrderResult {
  orderId: string;
  totalAmount: number;
}

function placeOrder(cmd: PlaceOrderCommand): Promise<PlaceOrderResult>;
```

| 要素 | 設計ポイント |
|------|-------------|
| 入力 | 必要最小限。バリデーション責務をどちらが持つか決める |
| 出力 | 成功・失敗の型を明示（例外 or Result 型） |
| 副作用 | DB 更新・メール送信など、何が起きるか文書化 |

---

## 3. 最小限の公開面（Surface Area）

**公開面** = 外に export する API の総量。**小さいほどよい** です。

| 原則 | 理由 |
|------|------|
| 必要な関数・型だけ export | 変更の影響範囲を限定 |
| 内部型は export しない | Leaky Abstraction を防ぐ |
| Facade で入口を 1 つに | `index.ts` からだけ公開 |

```text
  公開面が大きい              公開面が小さい
  ─────────────              ─────────────
  export 50 クラス           export 3 関数
  変更が広く波及              内部自由にリファクタ可能
```

---

## 4. 命名と可読性

インターフェースの **名前** は、利用者の **意図** が読めるようにします。

| 良い例 | 悪い例 |
|--------|--------|
| `OrderService.placeOrder` | `OrderService.doProcess` |
| `OrderRepository.findById` | `OrderRepo.get` |
| `OrderCancelledEvent` | `EventType3` |

- **ユビキタス言語** に合わせる（[[02_ドメインに基づくモジュール設計]]）
- モジュール名をプレフィックスに含めると衝突を防げる

---

## 5. インターフェース変更の影響範囲

公開 API を変えると、**依存するすべてのモジュール** に影響します。

| 変更の種類 | 影響 |
|-----------|------|
| 新関数の追加 | 通常は安全（後方互換） |
| 引数の追加 | デフォルト値やオーバーロードで互換維持 |
| 引数・戻り値の変更 | **破壊的変更** — 全呼び出し元を更新 |
| 関数の削除 | 破壊的 — 非推奨期間を設ける |

```text
  変更前: placeOrder(userId, items)
  変更後: placeOrder(userId, items, couponCode?)
              ↑
  オプション引数で後方互換を保つ
```

**バージョニング**（API v1 / v2）や **非推奨（deprecated）** マーキングも検討します。

---

## 6. 「インターフェース」の2つの意味

設計の文脈では「インターフェース」が2つの意味で使われます。混ざりやすいので区別しておきます。

| 意味 | 何を指すか | 例 | 目的 |
|---|---|---|---|
| **① 公開 API** | モジュールが外に見せる入口の総体 | `index.ts` から export される関数・型 | 内部を隠し、変更の影響を限定する |
| **② 抽象型（ポート）** | 実装を差し替えるための型 | `interface OrderRepository` | 実装を隠し、差し替え・テストを可能にする |

```text
  ① 公開 API                         ② 抽象型（ポート）
  ─────────                          ─────────────────
  [order モジュール]                  [order]  ──→ «OrderRepository»
   ├─ index.ts  ← ここだけ見せる                         ▲
   ├─ domain/   （隠す）                                 │ implements
   └─ infra/    （隠す）                     [PostgresOrderRepository]
```

①は **モジュールの外側** をどう見せるか、②は **モジュールが外部に何を求めるか** の話です。  
1〜5節は主に①を、以下の7〜8節は主に②を扱います。

---

## 7. インターフェースは誰が持つか（所有権）

②の抽象型は、**どちらのモジュールに置くか** で依存の向きが変わります。

### 提供側が所有する（Provided Interface）

```text
  payment/
    PaymentGateway.ts      ← interface をここに置く
    StripeGateway.ts
  order/
    OrderService.ts        ← payment を import する

  依存: order ──→ payment
```

- 汎用ライブラリや、多数の利用者がいる共通基盤に向く
- 契約の形は **提供側の都合** で決まる

### 利用側が所有する（Required Interface / ポート）

```text
  order/
    domain/PaymentPort.ts  ← order が必要とする形で定義
    OrderService.ts
  payment/
    StripePaymentAdapter.ts ← order の PaymentPort を実装する

  依存: order ←── payment
```

- 業務ロジック（上位）と技術的詳細（下位）の境界に向く
- 契約の形は **業務の都合** で決まる。これが **依存性逆転の原則（DIP）** です

| 判断基準 | 提供側に置く | 利用側に置く |
|---|---|---|
| 守りたいのはどちらか | 提供側（共通基盤） | 利用側（業務ロジック） |
| 利用者の数 | 多い | 少ない（主に1つ） |
| 変わりやすいのは | 利用側 | 提供側（DB・外部サービス） |
| 代表例 | ロガー、HTTP クライアントのラッパ | リポジトリ、決済・通知のポート |

依存の向きの詳細は [[02_依存関係の管理]]、ディレクトリでの表現は [[03_ヘキサゴナルアーキテクチャのモジュール構成]] を参照。

## 8. ポートは小さく、利用者の言葉で

利用側が所有するインターフェースは、**利用者が本当に使う操作だけ** に絞ります（[[04_ISP (インターフェース分離の原則)]]）。

```typescript
// 悪い例：実装（S3）の機能をそのまま写した大きなインターフェース
interface StorageService {
  putObject(bucket: string, key: string, body: Buffer, acl: string): Promise<void>;
  getObject(bucket: string, key: string): Promise<Buffer>;
  listObjects(bucket: string, prefix: string): Promise<string[]>;
  setLifecycle(bucket: string, rule: LifecycleRule): Promise<void>;
  // ...
}

// 良い例：使う側がやりたいことだけ。技術用語（bucket, acl）が漏れていない
interface AttachmentStore {
  save(attachment: Attachment): Promise<AttachmentId>;
  load(id: AttachmentId): Promise<Attachment>;
}
```

| 観点 | 悪い例 | 良い例 |
|---|---|---|
| 名前 | 技術の名前（Storage, S3） | 業務の名前（AttachmentStore） |
| 引数 | 技術の概念（bucket, acl） | 業務の概念（Attachment） |
| 操作数 | 実装ができること全部 | 利用者が必要なものだけ |
| 差し替え | S3 以外に替えにくい | SFTP・メモリ実装に替えやすい |

**技術の都合がインターフェースに漏れると、抽象化しても結合は弱まりません**（[[04_深いモジュールと浅いモジュール_情報漏洩]]）。

## 9. TypeScript での実現のコツ

| テクニック | 効果 |
|---|---|
| `import type { X }` を使う | 型だけの依存であることを明示し、実行時の依存を生まない |
| 構造的型付けを活かす | `implements` を書かなくても、形が合えば渡せる（アダプタを薄くできる） |
| 公開面は `index.ts` / `package.json` の `exports` で制御 | ①の公開 API を物理的に制限できる（[[06_言語のモジュール機構_ESM・TypeScript・barrel]]） |
| インターフェースの隣に偽物実装を置く | `InMemoryOrderRepository` をテストで使い回せる |

```typescript
// order/domain/Clock.ts
export interface Clock { now(): Date; }

// テストでは implements なしでも渡せる（構造的型付け）
const fixedClock = { now: () => new Date('2026-01-01T00:00:00Z') };
const service = new OrderService(repo, fixedClock);
```

疎結合・インターフェース・DIP・DI の関係は [[04_疎結合・インターフェース・DIP・DIの整理]] にまとめています。

---

## まとめ

- インターフェース = **契約・境界・安定点**
- 入出力・副作用を明確にし、**最小限の公開面** にする
- **命名** はユビキタス言語と利用者の意図を反映
- 公開 API の変更は **影響範囲が広い** — 後方互換を意識する
- 「インターフェース」には **①公開 API** と **②抽象型（ポート）** の2つの意味がある
- ポートを **利用側が所有** すると依存の向きが逆転する（DIP）
- ポートは小さく、**業務の言葉** で。技術の都合を漏らさない
