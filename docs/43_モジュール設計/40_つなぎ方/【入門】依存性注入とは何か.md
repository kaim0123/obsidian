#依存性注入 #エンジニア

## 要約

依存性注入（Dependency Injection）は名前ほど難しくない。**あるコードが別のコードを使いたいとき、内部で直接作らず外から渡してもらう**——渡すことを「注入」と呼ぶ。仕組みはこれだけ。形としては古くからある **Strategy パターン** とほぼ同じで、「プログラミングの大半は Builder と Strategy」と言うシニアもいるほど身近な考え方。

動画はビジネスチャットの **添付ファイルサービス** を題材に、if 分岐地獄から DI で組み直す流れで解説する。

### 題材：保存先が顧客ごとに違う

メッセージ本文はリアルタイムのチャットサービスへ。添付は専用アタッチメントサービスへ上がり、一時保存→処理→最終保存先へ。デフォルトは **S3** だが、一部企業は永続保存を嫌い保存先を切替える必要がある（多くは **SFTP**、1社だけ **WebDAV**）。

### if 文で拡張すると何が壊れるか

保存先指定と接続情報を引数で渡す／保存先ごとにユニオン型で項目を縛る、といった手もあるが、分岐を足していくと次の問題が出る。

1. **責任が肥大** … AWS・SFTP・WebDAV が1箇所に絡み、流れが追いにくい  
2. **呼び出し側が不親切** … 保存先ごとに必要な情報が違い、任意引数だらけ・どれを埋めるかはコメント頼み・ミスは実行時  
3. **設定のバケツリレー** … 会社を一番よく知るのはリクエスト入口なのに、ゴールまで接続情報を引き回す  

### DI の導入

1. ストレージを表す **インターフェース**（upload / download だけ＝呼ぶ側がやりたいこと）  
2. 差し込み口に合う実装を3つ（各接続設定はコンストラクタで受け取る → 任意引数だらけが消え、足りなければその場でエラー）  
3. 認証後に会社が分かった瞬間に使うストレージを作り、**完成したストレージだけ**をリクエスト処理へ渡す＝注入  

リクエスト処理は行き先を知らず、「upload を呼べば保存される」だけ知っている。組み立てはファクトリーに切り出せる（入力＝会社設定、出力＝ストレージ）。

### パイプライン：最終保存は最後の1歩

実際のアップロードは次の4工程を経てから保存される。

1. **ウイルススキャン**（本番: ThreatProtect／開発のみ契約の Synergy → 共通 IF、起動時にどちらを注入）  
2. **画像縮小**（Sharp → ImageScaler IF。対応可否を返すメソッドも）  
3. **プレビュー**（文書・動画・画像の3実装。画像用は ImageScaler を再利用して再注入。どれを使うかは MIME 次第 → 選ぶ責任ごとファクトリーに注入）  
4. **暗号化**（AES 1実装。鍵はユーザーごとに KeyService から → KeyService を暗号化へ注入 → 暗号化入りストレージを StorageFactory が組み立て）  

リクエスト処理は相変わらず upload を呼ぶだけ。構成のすべてが **1箇所で決まる** ので、契約変更は数行、新プレビューは実装を1つ足す、ローカルにキーサーバがなければ固定キーを差し込む、など変更が局所化される。

注入タイミングは2種類（原理は同じ）。

- 多くは **起動時** に決まる  
- 一部は **リクエスト到来時** に選ばれる  

コードは必要な依存を宣言し、外側が満たす。

### 実装が1つでもインターフェースを使う理由：テスト

部品同士が IF 越しなら、接続点はすべて差し替え可能。偽物／スタブを注入すれば一部だけ隔離テストできる。例：偽 S3 で upload 検証 → 暗号化のせいで中身検証できないなら「何もしない暗号化」を注入して upload だけ隔離。

批判（本物の通信も暗号化も走らない＝テストか？）への反論の一例：「テスト対象は自分のコード。S3が動くかは Amazon の仕事」。良いモックの目安として「本番でも使えそうな偽物なら価値がある（例: Postgres → SQLite）。本番でありえないなら捨ててよい」という見方もある。モックの強みは **わざと失敗させる**（切断・停止を好きなタイミングで再現）。どこで切るか（キーストアだけ偽／暗号＋AWSは統合で本物など）を自由に選べる。プライベートメソッドのテストに悩み始めたら、その部分を分離して注入すべきシグナル、という話もある。

### 現場の声と使いどころ（万能ではない）

やりすぎると：

- 引数6〜7個の関数だらけで手に負えない  
- 定義へジャンプが IF に止まり実装探しがつらい  
- 初めて入った人が「少し処理して依存に投げる」の連鎖で、**読んでも分からず動かさないと分からない**コードになる  

対策の例：インターフェース・実装・どれを選ぶかのルールをなるべく同じ場所にまとめ、遠くから魔法のように引かない。デバッグでは「注入される側のバグ」ではなく「注入するものを間違えた」ケースが厄介（気づくまで時間がかかり、ファクトリーの奥にまた注入…）。

よく聞く批判：**早すぎる抽象化は早すぎる最適化よりたちが悪い**。変わるかも、だけで作った差し込み口は使われず複雑さだけ残る。間違った抽象より重複の方がましで、3回目に気づいてからまとめてよい、という意見もある。

差し込み口を作る目安（3シグナル）：

1. 分岐が **3つ以上** に増えてきた  
2. テストのためにその依存を用意するのが明らかに面倒  
3. たまにしか使わないのに起動を重くしている部品がある  

どれにも当てはまらなければまだ作らなくてよい。**最初の1行から完璧に注入しない**——まずは素直に書き、辛くなってから必要な場所だけ引き出す。今日の題材も複雑になりすぎたコードを後から直す作業。

### まとめ

DI は万能薬ではなく、**変わりうる境界にだけ差し込み口を作る道具**。どこに作りどこは作らないかを見極めるのが設計力。

- 依存は中で作らず外から渡す  
- 繋がりはインターフェースに任せる  

それだけで変更もテストもパズルのように自由になる——それが依存性注入。
