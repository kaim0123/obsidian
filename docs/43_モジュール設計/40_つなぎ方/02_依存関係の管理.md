# 依存関係の管理

## この章の目的

モジュール間の **依存の向き** を決め、**循環依存** を避け、**依存逆転** を実践する章です。  
[[02_結合度]] の具体的な運用方法です。

---

## 1. 依存とは何か

**依存** とは、モジュール A がモジュール B の **型・関数・データ** を使うことです。

```text
  order  ──depends on──→  payment
    │
    import { charge } from '../payment'
```

| 依存の形 | 例 |
|---------|-----|
| import / require | コード上の参照 |
| 実行時注入 | DI コンテナ経由 |
| 設定・環境 | 同じ DB への接続 |

**依存がある** = **変更が伝播する可能性がある**、と考えます。

---

## 2. 依存の方向を決める

依存は **一方向** に流れるように設計します。

### 一般的なルール

```text
  Presentation  →  Application  →  Domain
                        ↓
                   Infrastructure
                        ↑
              （Domain は Infra に依存しない）
```

| ルール | 意図 |
|--------|------|
| 内側（ドメイン）ほど安定 | 変更の少ない核 |
| 外側ほど詳細（DB, UI） | 差し替えやすい |
| **依存は内側に向かう** | ドメインがフレームワークに依存しない |

---

## 3. 循環依存の問題と解消法

**循環依存** = A → B → A のように、依存が輪になる状態。

```text
  order ──→ payment
    ↑          │
    └──────────┘   ← 循環！
```

| 問題 | 説明 |
|------|------|
| 変更が相互に波及 | どちらを先に直すか決められない |
| テスト・ビルド困難 | 単体で切り離せない |
| 理解困難 | 責務の境界が曖昧 |

### 解消法

1. **共通部分を第 3 モジュールに抽出**
2. **インターフェースを Domain に置き、依存逆転**（次節）
3. **イベント** で非同期・一方向に（[[03_データの受け渡しと共有]]）

---

## 4. 依存逆転の原則（DIP）

**依存逆転の原則（DIP）** = 詳細（実装）が抽象（インターフェース）に依存する。

```text
  Before（ドメインが DB に依存）
  order/domain ──→ postgres/driver

  After（DIP）
  order/domain ──→ OrderRepository (interface)
                        ↑
              postgres/OrderRepositoryImpl
```

| 要素 | 役割 |
|------|------|
| 抽象（ポート） | ドメイン側が定義 |
| 実装（アダプタ） | インフラ側が実装 |
| 注入 | アプリケーション層で組み立て |

[[05_SOLIDとの関係]] も参照。

---

## 5. 依存グラフの読み方と改善

### 読み方

- **矢印の多いモジュール** = 変更のハブ（注意）
- **双方向の矢印** = 循環の候補
- **ドメインから外への矢印** = DIP 違反の候補

```text
        web
         │
         ▼
    application ──→ domain
         │              ↑
         ▼              │
       infra ────────────┘  （infra が domain の IF を implement）
```

### 改善

- ツール: `dependency-cruiser`, `madge`, IDE の依存図
- **ルールを CI でチェック**（例: domain は infra を import 禁止）
- 改善は **循環と DIP 違反** から優先

ルールの書き方と導入手順は [[06_依存ルールの自動検査]] を参照。

---

## 6. DIP をもう一段深く

### 6.1 何が「逆転」するのか

「逆転」とは、**処理の流れ** と **ソースコードの依存** の向きが逆になることです。

```text
  処理の流れ（実行時に誰が誰を呼ぶか）
    order/application ───呼ぶ───▶ postgres/OrderRepositoryImpl

  ソースコードの依存（誰が誰を import するか）
    order/application ──▶ order/domain/OrderRepository ◀── postgres/OrderRepositoryImpl
```

- 業務ロジックが DB を呼ぶ、という **処理の流れは変わらない**
- しかし **import の矢印は DB 側から業務側へ** 向く

依存の矢印は「**矢印の先が変わると、矢印の元が壊れる**」と読みます。DIP 後は DB を替えても業務ロジックは壊れません。

### 6.2 DIP の核心は「インターフェースの所有者」

インターフェースを作っただけでは DIP になりません。**どのモジュールに置くか** がすべてです。

| インターフェースの置き場所 | import の向き | DIP か |
|---|---|---|
| `infra/OrderRepository.ts` | `order → infra` | ✕（矢印はそのまま） |
| `order/domain/OrderRepository.ts` | `infra → order` | ◯ |
| `shared/interfaces/OrderRepository.ts` | `order → shared ← infra` | △（共通置き場が肥大しやすい） |

インターフェースの形は「DB が提供できるもの」ではなく、「**業務ロジックが必要とするもの**」で決めます（[[01_モジュール間インターフェースの設計]] の7〜8節）。

### 6.3 よくある失敗

| 失敗 | 何が問題か | 直し方 |
|---|---|---|
| インターフェースを infra 側に置く | 矢印が逆転しない | 使う側（domain）に移す |
| 実装の機能をそのまま写したインターフェース | 技術の都合が業務に漏れる | 業務の言葉で、必要な操作だけにする |
| インターフェースを作ったのに中で `new` | 結局、具体クラスに依存したまま | DI で外から渡す（7節） |
| 全クラスに `IXxx` / `XxxImpl` | 抽象が多すぎて追えない | 境界だけに絞る（8節） |
| domain が ORM のエンティティ型を使う | 型経由で infra に依存している | domain 独自の型を定義し、アダプタで変換する |

## 7. DI と Composition Root：誰が組み立てるか

DIP で依存の向きを整えても、どこかで `new PostgresOrderRepository()` は必要です。  
それを **使う側の外** で行い、完成品を渡す技法が **依存性注入（DI）** です。

### 7.1 コンストラクタ注入

```typescript
// order/application/PlaceOrderUseCase.ts
import type { OrderRepository } from '../domain/OrderRepository';
import type { PaymentPort } from '../domain/PaymentPort';

export class PlaceOrderUseCase {
  constructor(
    private readonly orders: OrderRepository,
    private readonly payment: PaymentPort,
  ) {}
}
```

| 注入の方法 | 内容 | 評価 |
|---|---|---|
| コンストラクタ注入 | 生成時に渡す | ◎ 必須の依存が明確、不変にできる |
| メソッド注入 | 呼び出しごとに引数で渡す | ○ 呼び出しごとに変わるもの向け |
| セッター注入 | 後から set で渡す | △ 未設定のまま使われるリスク |

### 7.2 Composition Root はどこに置くか

**Composition Root** = 依存を組み立てる **唯一の場所**。アプリの入口（`main.ts` など）の近くに置きます。

```text
src/
  order/          ← new しない。受け取るだけ
  payment/        ← new しない。受け取るだけ
  infra/          ← new しない。受け取るだけ
  main.ts         ← ここだけが全モジュールを知り、組み立てる
```

```typescript
// main.ts（Composition Root）
const pool = new Pool(config.db);
const orders = new PostgresOrderRepository(pool);
const payment = new StripePaymentAdapter(config.stripeKey);
const placeOrder = new PlaceOrderUseCase(orders, payment);

startServer({ placeOrder });
```

`main.ts` だけは **全モジュールに依存してよい** 特別な場所です。逆に、他のモジュールが `main.ts` を import してはいけません。

### 7.3 モジュールごとに組み立て関数を公開する

モジュールが増えると `main.ts` が肥大します。各モジュールが **組み立て関数** を公開し、`main.ts` はそれをつなぐだけにすると見通しがよくなります。

```typescript
// order/index.ts（order モジュールの公開面）
export type { OrderRepository } from './domain/OrderRepository';
export type { PaymentPort } from './domain/PaymentPort';

export function createOrderModule(deps: {
  orders: OrderRepository;
  payment: PaymentPort;
}) {
  return {
    placeOrder: new PlaceOrderUseCase(deps.orders, deps.payment),
    cancelOrder: new CancelOrderUseCase(deps.orders, deps.payment),
  };
}
```

```typescript
// main.ts
const order = createOrderModule({
  orders: new PostgresOrderRepository(pool),
  payment: new StripePaymentAdapter(config.stripeKey),
});
```

- モジュールが外に求めるもの（`deps` の型）が **関数の引数として明示** される
- モジュール内部の配線（どのユースケースに何を渡すか）は内部に隠れる

### 7.4 DI コンテナとサービスロケーター

| 方式 | 内容 | 評価 |
|---|---|---|
| 手動 DI | 上のように自分で `new` して渡す | 小〜中規模ならこれで十分 |
| DI コンテナ | 型やトークンから自動で組み立てる（NestJS, InversifyJS など） | 大規模・ライフタイム管理が必要なとき |
| サービスロケーター | 使う側が `container.get(X)` で取りに行く | ✕ 依存が隠れる。アンチパターン |

DI コンテナも **Composition Root の外で `get` するとサービスロケーターになります**。詳しくは [[03_制御の反転とComposition Root]] を参照。

## 8. どこに DIP・DI を適用するか

| 適用する | 適用しなくてよい |
|---|---|
| DB・外部 API・メール・ファイルなど I/O | 純粋な計算、値オブジェクト |
| 時刻・乱数など、テストで固定したいもの | 同じモジュール内の密接なクラス同士 |
| 別チームのモジュールとの境界 | 実装が1つで、替わる見込みもテストの不便もないもの |
| 循環依存を断ち切りたい箇所 | 標準ライブラリ・安定した言語機能 |

最初から全部に差し込み口を作る必要はありません。**素直に書いて、辛くなった境界から引き出す** のが現実的です（[[【入門】依存性注入とは何か]]）。

疎結合・インターフェース・DIP・DI の関係は [[04_疎結合・インターフェース・DIP・DIの整理]] にまとめています。

---

## まとめ

- **依存** = 変更が伝播するつながり
- 依存は **内側（ドメイン）に向かう一方向** が基本
- **循環依存** は抽出・DIP・イベントで解消
- **依存グラフ** を可視化し、CI でルールを守る
- DIP は **処理の流れはそのまま、import の向きだけを逆にする**。鍵は **インターフェースを使う側が所有** すること
- DI は **生成を外に出す** 技法。`new` は **Composition Root** に集める
- 各モジュールは **組み立て関数** で必要な依存を明示すると見通しがよい
- DIP・DI は **I/O や境界** に絞って適用する
