# 結合度（Coupling）

## この章の目的

モジュール同士の **依存の強さ** — **結合度** — を学びます。  
高凝集と **低結合** の組み合わせが、変更に強いモジュール構造の基本です。

---

## 1. 結合度とは何か

**結合度（Coupling）** とは、モジュール同士が **どれだけ強く依存し合っているか** を表す指標です。

| 結合度 | 状態 | 例 |
|--------|------|-----|
| **低い（疎結合）** | 最小限の契約だけ共有 | インターフェース経由の呼び出し |
| **高い（密結合）** | 内部の詳細まで知っている | 相手モジュールの内部クラスを直接 import |

```text
  低結合                         高結合
  ──────                         ──────
  Order ──→ [IOrderRepo] ←── DB   Order ──→ DB の SQL 文を直接実行
              ↑
         契約だけ知る
```

**結合度は低いほどよい** とされます。

---

## 2. 結合度が高いときに起きる問題

| 問題 | 説明 |
|------|------|
| 変更の連鎖 | A を直すと B・C も直す必要が出る |
| テスト困難 | 1 モジュールのテストに全体が必要 |
| 差し替え不可 | DB や外部 API の実装を変えにくい |
| 並行開発の衝突 | 同じモジュールに多数が依存し、変更がぶつかる |

```text
  密結合
    A ←→ B ←→ C
         │
    1 箇所変更 → 全体に波及
```

---

## 3. 結合の種類

モジュール間の結合には、強さの異なる種類があります（弱い順のイメージ）。

| 種類 | 説明 | モジュール例 |
|------|------|-------------|
| **データ結合** | 必要なデータだけ渡す | DTO で注文 ID を渡す |
| **スタンプ結合** | 構造体の一部だけ使うが全体を渡す | 巨大な `User` オブジェクトを丸ごと |
| **制御結合** | 相手の処理フローを制御する | フラグで相手の分岐を指定 |
| **外部結合** | 外部で決められた形式・規約を共有する | 2つのモジュールが同じ CSV 形式・通信プロトコルに依存 |
| **共通結合** | グローバルな共有状態 | 全モジュールが同じ DB テーブルを直接更新 |
| **内容結合** | 内部実装に直接依存 | 相手の private 関数を呼ぶ |

**目標**: データ結合に近づける。共通結合・内容結合は避ける。

---

## 3.1 6種類の結合を詳しく見る

この分類は、Stevens・Myers・Constantine の論文「Structured Design」（1974）で示され、Yourdon & Constantine の同名書籍（1979）や Myers『高信頼性ソフトウェア』で広まったものです。応用情報技術者試験などでもよく出ます。**強い（悪い）順** に並べると次のとおりです。

```text
 強い（避ける）                                              弱い（目指す）
 内容結合 → 共通結合 → 外部結合 → 制御結合 → スタンプ結合 → データ結合
 └─ 内部を直接触る ─┘└─ 共有データ ─┘└─ 処理を操る ─┘└─ 引数で渡す ─┘
```

> 見分け方のコツ：**「相手と何を共有しているか」** を見ます。内部実装 → グローバルデータ → 外部の形式 → 制御情報 → データ構造 → 必要なデータだけ、の順に共有するものが小さくなり、結合が弱くなります。

### (1) 内容結合（Content Coupling）— 最も強い

**相手モジュールの内部（private なデータ・関数・コード）を直接参照・変更する** 結合です。

```typescript
// payment モジュールの内部状態を、order モジュールが直接書き換える
import { _internalCache } from '../payment/internal/cache';
_internalCache.balance = 0;
```

- 相手は「使われている」ことを知らないので、相手の **リファクタリングだけで壊れる**
- 情報隠蔽（カプセル化）を完全に破っている
- 昔のアセンブラでの「他モジュールのコード途中へのジャンプ」もこれにあたる

### (2) 共通結合（Common Coupling）

**複数のモジュールが、同じグローバルなデータ（共通領域）を読み書きする** 結合です。

```typescript
// global-state.ts
export const appState = { currentUser: null as User | null, taxRate: 0.1 };

// order と invoice の両方が appState を直接読み書きする
appState.taxRate = 0.08;   // ← どこで変わったか追えない
```

- 誰がいつ値を変えたか **追跡できない**。1か所の誤りが予期しない場所に波及する
- グローバル変数、書き換え可能なシングルトン、複数モジュールが直接更新する共有 DB テーブルが典型

### (3) 外部結合（External Coupling）

**外部で決められたデータ形式・通信プロトコル・デバイスのインターフェースなどを、複数のモジュールが共有する** 結合です。共通結合と似ていますが、共有しているのが **データそのものではなく「外から押しつけられた形式・規約」** である点が違います。

```typescript
// import モジュールと export モジュールが、取引先指定の固定長フォーマットを
// それぞれ独自に解釈している
const amount = Number(line.slice(20, 32));   // 20〜31桁目が金額、という外部仕様
```

- 外部の仕様が変わると、それに依存する **すべてのモジュールを同時に直す** 必要がある
- 対策は、外部形式を解釈する場所を **1か所（アダプタ・腐敗防止層）に閉じ込め**、他のモジュールには内部の型で渡すこと

### (4) 制御結合（Control Coupling）

**フラグなどの「何をすべきか」という制御情報を渡して、相手の処理の流れを操る** 結合です。

```typescript
function printReport(data: Report, mode: 'summary' | 'detail' | 'csv') { /* mode で分岐 */ }
printReport(report, 'csv');   // 呼び出し側が相手の内部の分岐を知っている
```

- 呼び出し側が **相手の内部ロジック（どんな分岐があるか）を知っている**
- 相手に分岐が増えると、呼び出し側も影響を受ける
- 弱め方は 8節（インターフェース＋多態）を参照

### (5) スタンプ結合（Stamp Coupling）

**構造体・オブジェクトを丸ごと渡すが、受け取る側はその一部しか使わない** 結合です。

```typescript
// メール送信に必要なのはアドレスと名前だけなのに、User 全体を受け取る
function sendWelcome(user: User) {
  mail.send(user.email, `${user.name}さん、ようこそ`);
}
```

- 使っていない項目（`User` の住所・権限など）の **変更でも影響を受ける可能性がある**
- テストのたびに巨大な `User` を組み立てる必要がある
- 「データ構造という型（スタンプ）を共有している」ことが名前の由来

### (6) データ結合（Data Coupling）— 最も弱い

**必要なデータだけを、引数として渡す** 結合です。

```typescript
function sendWelcome(email: string, name: string) {
  mail.send(email, `${name}さん、ようこそ`);
}
```

- やりとりが引数と戻り値だけで完結し、**相手の内部も、余計なデータも知らない**
- 理想の状態。ただし引数が増えすぎる場合は、**必要な項目だけの小さな型** を作って渡すのが現実的（それは「スタンプ結合」ではなく、目的に合わせて設計されたデータ結合と考えてよい）

### 6種類の比較

| 結合 | 共有しているもの | 問題になる場面 | 対策 |
|---|---|---|---|
| 内容結合 | 相手の内部実装 | 相手のリファクタリング | 公開 API だけを使う |
| 共通結合 | グローバルデータ | どこで変わったか分からない | データの所有者を1つに決める |
| 外部結合 | 外部の形式・規約 | 外部仕様の変更 | アダプタに閉じ込める |
| 制御結合 | 制御フラグ | 相手の分岐の追加・変更 | 多態で振る舞いを分ける |
| スタンプ結合 | データ構造全体 | 使わない項目の変更 | 必要な項目だけの型にする |
| データ結合 | 必要なデータのみ | ほぼなし | — |

### 補足：紛らわしいポイント

- **共通結合と外部結合の違い**：共通結合は「同じ **データ** を共有」、外部結合は「同じ **形式・規約**（外部から決められたもの）を共有」。資料によって境界の書き方に揺れがあります。
- **スタンプ結合は必ずしも悪ではない**：オブジェクト全体を渡す方が自然な場面（エンティティをそのまま保存する等）もあります。問題なのは「使わない項目まで知ってしまう」ことです。
- **現代的な見方**：この分類は手続き型プログラミング時代のものです。現代のモジュール・サービス単位では、[[04_統合強度_侵入・機能・モデル・契約|統合強度]]（侵入的・機能的・モデル・契約）や、[[04_コナーセンス]] で捉え直されています。おおまかには、内容結合 ≒ 侵入的結合、データ結合 ≒ 契約結合に近い位置づけです。

## 4. 疎結合を保つための原則

1. **インターフェース経由** でだけ通信する
2. **必要最小限のデータ** だけ渡す（巨大 DTO を避ける）
3. **グローバル状態・共有 DB テーブル** に頼らない
4. **依存の方向** を決める（[[02_依存関係の管理]]）
5. **イベント** で非同期・疎結合にする（必要な場合）

```typescript
// 密結合（悪い例）
import { postgresPool } from '../infra/db';  // 他モジュールの内部

// 疎結合（良い例）
import { OrderRepository } from './order-repository.interface';
```

## 5. 結合度のチェックリスト

- [ ] モジュールは **公開 API 以外** に依存していないか
- [ ] **循環依存**（A→B→A）がないか
- [ ] 共有の **グローバル変数・シングルトン** に頼っていないか
- [ ] 変更時に触るモジュール数は **妥当** か
- [ ] テストで **本物の DB や外部 API** が必須になっていないか

依存グラフの読み方は [[010Programming/43_モジュール設計/90_付録/付録D_参考図解]] を参照。

## 6. 「疎結合」とは何を知らないことか

疎結合は「依存がない」ことではありません。**依存はあるが、相手の事情を最小限しか知らない** 状態です。  
モジュール A が B について知りうることを並べると、知っている範囲が狭いほど結合は弱くなります。

| A が B について知っていること | 結合 | B のどんな変更で A が壊れるか |
|---|---|---|
| B の内部クラス名・private な関数 | 非常に強い | B のリファクタリングすべて |
| B が使っている技術（Postgres、S3 など） | 強い | 技術の差し替え |
| B の具体クラス名（`new` するため） | 中 | クラス名・コンストラクタ引数の変更 |
| B の公開 API（関数シグネチャ） | 弱い | 公開 API の破壊的変更だけ |
| **自分が定義した** インターフェースだけ | 最も弱い | 自分が契約を変えたときだけ |

最後の行が **依存性逆転の原則（DIP）** を適用した状態です。A は B を知らず、自分で決めた契約だけを知っています（[[02_依存関係の管理]]）。

## 7. 見落としやすい結合：生成による結合

import している型だけでなく、**`new` していること** 自体も結合です。

```typescript
// 型はインターフェースでも、生成で具体クラスに縛られている
class OrderService {
  private repo: OrderRepository = new PostgresOrderRepository(pool);
}
```

| `new` で生まれる結合 | 問題 |
|---|---|
| 具体クラス名を知る | 実装の差し替えにコード修正が必要 |
| コンストラクタ引数を知る | 相手の依存（`pool` など）まで知ってしまう |
| 生成タイミングを決める | テストで偽物に差し替えられない |

これを断つ技法が **依存性注入（DI）** です。生成は外側（Composition Root）に任せ、自分は受け取るだけにします。

```typescript
class OrderService {
  constructor(private readonly repo: OrderRepository) {}
}
```

詳しくは [[01_依存性注入]]、[[03_制御の反転とComposition Root]] を参照。

## 8. 結合の種類ごとの弱め方

3節の結合の種類それぞれに、典型的な弱め方があります。

| 結合の種類 | 弱め方 | 使う道具 |
|---|---|---|
| **内容結合** | 公開 API だけを使い、内部は export しない | `index.ts` による公開面の制限（[[01_モジュール間インターフェースの設計]]） |
| **共通結合** | 共有データの所有者を1モジュールに決め、他は API 経由で使う | データの所有権（[[03_データの受け渡しと共有]]） |
| **外部結合** | 外部形式の解釈を1か所に閉じ込め、内部の型に変換して渡す | アダプタ・腐敗防止層 |
| **制御結合** | フラグで分岐させず、振る舞いごとに実装を分けて渡す | インターフェース + 多態（[[04_多態とインターフェース]]） |
| **スタンプ結合** | 必要な項目だけの型を定義して渡す | 専用 DTO、小さなインターフェース（ISP） |
| **具体クラスへの依存** | 使う側が定義した抽象に依存させる | DIP + DI |

制御結合をインターフェースで解消する例です。

```typescript
// 制御結合：呼び出し側がフラグで相手の分岐を指定
function notify(user: User, channel: 'email' | 'slack' | 'sms') {
  if (channel === 'email') { /* ... */ }
  else if (channel === 'slack') { /* ... */ }
  else { /* ... */ }
}

// 疎結合：振る舞いを実装ごとに分け、使う側はインターフェースだけ知る
interface Notifier { send(user: User, message: string): Promise<void>; }

class SignupService {
  constructor(private readonly notifier: Notifier) {}
  async signup(user: User) {
    // ...
    await this.notifier.send(user, 'ようこそ');
  }
}
```

## 9. 疎結合にしすぎるコスト

結合度は低いほどよい、と言っても **ゼロにはできず、ゼロを目指すべきでもありません**。

| やりすぎ | 起きること |
|---|---|
| すべてのクラスにインターフェース | 「定義へジャンプ」がインターフェースで止まり、読むのがつらくなる |
| モジュール内部まで DI | 引数が6〜7個のコンストラクタだらけになる |
| 何でもイベントで通知 | 処理の流れが追えず、動かさないと分からないコードになる |

判断の目安は次のとおりです。

- **モジュールの内部** は密でよい（高凝集。[[01_凝集度]]）
- **モジュールの境界**、特に変わりやすい外部（DB・外部 API）との境界を疎にする
- どこを疎にするかは、強度・距離・変動性で判断する（[[03_バランス結合_強度・距離・変動性]]）

疎結合・インターフェース・DIP・DI の関係は [[04_疎結合・インターフェース・DIP・DIの整理]] にまとめています。

## まとめ

- **結合度** = モジュール間の依存の強さ（低いほどよい）
- 密結合は変更連鎖・テスト困難・差し替え困難を招く
- データ結合に近づけ、共通結合・内容結合を避ける
- 結合は強い順に **内容 → 共通 → 外部 → 制御 → スタンプ → データ**。見分けるには「相手と何を共有しているか」を見る
- インターフェース・最小データ・依存方向で疎結合を保つ
- 疎結合とは **相手の事情を最小限しか知らない** こと。最も弱いのは「自分が定義した契約だけを知る」状態（DIP）
- `new` も結合。生成は DI で外に出す
- 結合はゼロにしない。**境界だけを疎に**、内部は高凝集に
