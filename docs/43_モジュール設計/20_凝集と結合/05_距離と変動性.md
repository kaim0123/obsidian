# 距離と変動性

> **バランス結合ノート群**（Khononov『ソフトウェア設計の結合バランス』）
> [[03_バランス結合_強度・距離・変動性|概要とバランスの式]] ／ [[04_統合強度_侵入・機能・モデル・契約|統合強度]] ／ [[05_距離と変動性|距離と変動性]] ／ [[06_結合と複雑性_クネビンと相互作用|結合と複雑性]] ／ [[07_結合の再均衡化・フラクタル・実践|再均衡化・フラクタル・実践]]

## この章の目的

結合の3つの次元のうち、[[04_統合強度_侵入・機能・モデル・契約|統合強度]] 以外の2つを扱います（原著 第8章・第9章）。

- **距離**：結合している部品同士を一緒に変えるのに、どれだけ手間がかかるか
- **変動性**：その部品がどれくらい頻繁に変わるか

## 1. 距離（Distance）— 変更を伝えるのにどれだけ手間がかかるか

結合している部品同士が **どれだけ離れているか** です。距離が遠いほど、**一緒に変更するコスト** が大きくなります。

| 距離 | 例 | 一緒に変えるコスト |
|---|---|---|
| 近い | 同じ関数・同じクラスの中 | 1つのファイルを直すだけ |
| ↓ | 同じモジュール・同じパッケージ | 数ファイル。同じ人が直せる |
| ↓ | 別のモジュール（同じリポジトリ） | 別チームとの調整が必要になることも |
| ↓ | 別のサービス（別リポジトリ・別デプロイ） | 複数チームの調整、デプロイ順序の管理、互換性の維持 |
| 遠い | 別の組織・外部システム | 交渉が必要。こちらからは変えられないことも |

距離は **コードの物理的な位置** だけでなく、**組織的な距離**（同じチームか、別チームか、別の会社か）も含みます（→ 41 の コンウェイの法則）。

### 1.1 距離に影響する追加要因（第8章）

| 要因 | 距離への影響 | 例 |
|---|---|---|
| **カプセル化の境界** | 越える境界（メソッド → クラス → モジュール → サービス → システム）が多いほど遠い | 基本の物差し |
| **社会技術的な要因（所有者の距離）** | 別チーム・別組織が持っていると、コードが近くても遠くなる | 同じリポジトリでも、別チームのモジュールを直すには調整が要る |
| **ランタイムの結合** | 同期呼び出しで相手が落ちると自分も落ちる。非同期にすると実行時の結びつきは弱まるが、**共有知識（統合強度）は減らない** | 第7章「統合強度と非同期実行」 |

> 第7章の注意点：**非同期にしても統合強度は下がりません。** メッセージキューを挟んでも、相手のドメインモデルをそのままイベントに載せていればモデル結合のまま、業務ルールを共有していれば機能結合のままです。

### 1.2 距離と近接 — 距離にもコストがある（第8章「距離と近接」）

「強度が低いなら離せばよい」と言われると、何でも遠ざけたくなります。しかし **近くにあること（近接）** には別の結合が伴います。

- **遠い** ほど：一緒に変更するコスト（調整・デプロイ順序・互換性維持）が増える
- **近い** ほど：**ライフサイクル結合**（一緒にビルド・テスト・デプロイされる）が強まる。関係ないものまで一緒にリリースを待つことになる

つまり距離は「遠いほど悪い／近いほど悪い」ではなく、**統合強度との組み合わせで適切な値を選ぶもの** です（→ [[03_バランス結合_強度・距離・変動性]] のバランスの式）。

## 2. 変動性（Volatility）— どれくらい頻繁に変わるか

結合している部品が **どれくらい頻繁に変更されるか** です。

- **変わらないもの同士なら、強く結びついていても問題は起きない**
- 変動性を予測する手がかりとして、Khononov は DDD の **サブドメインの分類** を使います（→ 42 の [[05_コアドメインとサブドメイン]]）

| サブドメイン | 変動性 |
|---|---|
| コア（競争優位を生む） | **高い**（改善し続ける） |
| 支援（自社特有だが単純） | 低い |
| 汎用（どこも同じ） | 低い（外部サービスに任せることが多い） |

> 例：標準ライブラリの `Date` や `Math` に、アプリ中のあらゆるコードが強く結合しています。それでも問題にならないのは、**ほとんど変わらない**（変動性が低い）からです。

### 2.1 本質的な変動性と偶発的な変動性（第9章「ソフトウェアが変わる理由」）

| 種類 | 意味 | 例 |
|---|---|---|
| **本質的な変動性** | 業務そのものが変わるから変わる | コアサブドメインの料金ルールを、競争のために頻繁に改善する |
| **偶発的な変動性** | 設計がまずいせいで変わる | 別の機能を直すたびに、強く結合しているこのモジュールも直す羽目になる |
| **偶発的な「変わらなさ」** | 業務は変えたいのに、怖くて誰も触れない | 巨大で危険なレガシーコード。変化率が低く見えても、本当は変動性が高い |

> 変更履歴（git log）の頻度だけで変動性を測ると、最後の「怖くて触れない」ケースを見落とします。**業務戦略上どれだけ変わるべきか** を併せて見ます。

### 2.2 推測される変動性（Inferred Volatility）

変動性は、そのモジュール単体だけでは決まりません。**変動性の高いモジュールと強く結合しているモジュールは、自分も一緒に変わらざるを得ない** ため、その変動性を「受け継ぎ」ます。

- 例：支援サブドメインの請求モジュールでも、コアサブドメインの料金モデルを直接使っていれば、料金モデルが変わるたびに変わる → 実質的には変動性が高い
- だから変動性を見積もるときは、**サブドメインの分類 ＋ 何と結合しているか** の両方を見ます

※ 2.1・2.2 は原著第9章の節（Why Software Changes／Inferred Volatility）と、著者のポッドキャストでの説明をもとにした整理です。

### 2.3 戦略が変わると変動性も変わる

支援サブドメインが新しい事業の柱になってコアに格上げされる、といったことは普通に起きます。**変動性は固定の属性ではない** ので、定期的に見直します（→ [[07_結合の再均衡化・フラクタル・実践]] の再均衡化）。

## まとめ

- **距離**：一緒に変更するコスト。コードの位置（カプセル化の境界）＋ 組織の距離 ＋ ランタイムの結合
- 近すぎると **ライフサイクル結合** が強まる。距離は統合強度との組み合わせで選ぶ
- **変動性**：変更の頻度。コアサブドメインほど高い。本質的／偶発的を区別し、「怖くて触れない」所に注意
- 変動性の高いものと強く結合すると、その変動性を **受け継ぐ**（推測される変動性）
- 変動性は戦略の変化で変わるので、定期的に見直す
