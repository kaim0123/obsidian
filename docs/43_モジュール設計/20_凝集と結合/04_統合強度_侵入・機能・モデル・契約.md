# 統合強度 — 侵入・機能・モデル・契約

> **バランス結合ノート群**（Khononov『ソフトウェア設計の結合バランス』）
> [[03_バランス結合_強度・距離・変動性|概要とバランスの式]] ／ [[04_統合強度_侵入・機能・モデル・契約|統合強度]] ／ [[05_距離と変動性|距離と変動性]] ／ [[06_結合と複雑性_クネビンと相互作用|結合と複雑性]] ／ [[07_結合の再均衡化・フラクタル・実践|再均衡化・フラクタル・実践]]

## この章の目的

[[03_バランス結合_強度・距離・変動性]] で紹介した結合の3つの次元のうち、1つ目の **統合強度（Integration Strength）** ＝ **部品の境界を越えてどれだけの知識を共有しているか** を詳しく見ます（原著 第7章）。

## 1. 統合強度の4段階

部品の境界を越えて **共有される知識の量と種類** です。強い順に4段階あります。

| 強度 | 名前 | 共有している知識 | 例 |
|---|---|---|---|
| 最強 | **侵入的結合**（Intrusive） | 相手の **非公開の実装の詳細** | 他モジュールの DB テーブルを直接読む、内部クラスを import する、ログの文字列を解析する |
| 強 | **機能的結合**（Functional） | **業務の要件・ルール** そのもの | 同じ割引ルールを2つのモジュールが別々に実装している。業務が変わると両方を直す |
| 中 | **モデル結合**（Model） | **業務のモデル**（データ構造・概念） | 注文モジュールのドメインモデル `Order` を、配送モジュールがそのまま使う |
| 弱 | **契約結合**（Contract） | **統合のために設計された最小限の契約** | 公開 API・DTO・イベントのスキーマだけを共有する |

### 1.1 各段階の補足

- **侵入的結合**：相手が「公開したつもりのないもの」に依存している。相手は自分が依存されていることを知らないので、**予告なしに壊れる**。
- **機能的結合**：コードを共有していなくても起きる点に注意します。同じ業務ルールを2か所に書いていれば、それは機能的結合です（→ 42 の DRY、41 の [[04_コナーセンス]] の「アルゴリズムのコナーセンス」）。
- **モデル結合**：相手の内部モデルを使うと、相手のモデル変更（フィールドの追加・名前の変更）がこちらに波及します。
- **契約結合**：相手の内部が変わっても、契約（公開インターフェース）を守る限り影響を受けない。DDD の **公開ホストサービス**・**公表された言語** や **腐敗防止層** は、モデル結合を契約結合に下げる手法です（→ 42 の [[03_境界づけられたコンテキストとコンテキストマップ]]）。

> 統合強度は、41_アーキテクチャ の [[04_コナーセンス]]（結合の種類と強さ）を、**モジュール・サービスのレベル** で整理したものと考えると理解しやすいです。

## 2. 統合強度をさらに詳しく

> **呼び方の注意**：資料によって訳語が揺れます。**侵入的結合 ＝ 侵入結合**、**機能的結合 ＝ 機能結合**、**契約結合 ＝ コントラクト結合**（Contract Coupling）は同じものです。

### 統合強度とは「境界を越えて共有される知識」の量

[[02_モジュールの基本概念]] で見たように、モジュールには **機能（公開）・ロジック（隠す）・コンテキスト（前提）** があります。統合強度は、2つのモジュールが連携するときに **相手のどの知識まで知ってしまっているか** を表します。

```text
 共有する知識        多い・暗黙的                                少ない・明示的
 ─────────────────────────────────────────────────────────────────────────
 侵入結合      →    機能結合      →    モデル結合     →    コントラクト結合
 相手の実装          相手の業務要件        相手の業務モデル        統合専用の契約だけ
（ロジック）        （何を実現するか）    （何で表すか）         （公開された約束）
```

- 上に行くほど（侵入結合に近いほど）、**共有している知識が多く、しかも暗黙的**。相手が変わったときに壊れやすい
- 下に行くほど（コントラクト結合に近いほど）、**共有知識が少なく、明示的**。変更の影響が予測しやすい

### (1) 侵入結合（Intrusive Coupling）

**公開インターフェースを通さず、相手の非公開の実装の詳細に依存する** 結合です。

- 例：他サービスの内部 DB を直接読む、private なフィールドにリフレクションでアクセスする、画面の HTML をスクレイピングする、ログ文字列を解析する
- 実装の詳細が漏れているので、**相手の実装知識をすべて共有している** ものとみなす必要がある
- 最大の危険は、**相手の作者が「依存されていること」を知らない** こと。相手は善意のリファクタリングで、知らないうちにこちらを壊す

```typescript
// ✕ 侵入結合：配送サービスが注文サービスの内部テーブルを直接読む
const rows = await orderDb.query('SELECT status, shipped_flag FROM t_order_internal WHERE id = $1', [id]);

// ○ コントラクト結合：注文サービスが公開した API を使う
const order = await orderApi.getOrderSummary(id);   // 返り値は統合用の DTO
```

### (2) 機能結合（Functional Coupling）

**相手が「何を実現しているか」（業務の機能要件）を共有している** 結合です。コードを共有していなくても、**業務要件が変わると一緒に変えなければならない** なら機能結合です。

機能結合には、弱い順に次の **3つの度合い** があります（※ 二次資料による整理。度合いの名前・順番は原著で確認推奨）。

| 度合い | 何が起きているか | 例 |
|---|---|---|
| **順序結合**（Sequential / Temporal） | 処理を **決まった順番** で実行する必要がある | 「在庫を引き当ててから決済する」という順番を、2つのモジュールが前提にしている |
| **トランザクション結合**（Transactional） | 複数の操作を **1つの作業単位として** まとめて成功・失敗させる必要がある | 注文の確定と在庫の減算は、両方成功するか両方失敗するかのどちらか |
| **対称結合**（Symmetric） | **同じ機能を、複数の場所が別々に実装している** | 送料の計算ルールを、フロントエンドとバックエンドがそれぞれ実装している |

- **対称結合が最も強い** のは、**重複していることがコードからは見えない** ためです。ルールが変わったとき、片方だけ直して不整合が起きます（→ 42 の DRY 原則）
- 順序結合・トランザクション結合は、[[04_コナーセンス]] の **動的コナーセンス**（実行順序・値）と対応させて比べられます

```typescript
// ✕ 対称結合：同じ業務ルール「5000円以上で送料無料」が2か所にある
// frontend/cart.ts
const shippingFee = subtotal >= 5000 ? 0 : 500;
// backend/order-service.ts
const shippingFee = subtotal >= 5000 ? 0 : 500;

// ○ ルールを1か所に置き、もう一方はその結果を受け取る
// frontend は backend の見積もり API の結果を表示するだけにする
const { shippingFee } = await orderApi.quote(cart);
```

### (3) モデル結合（Model Coupling）

**業務を表すモデル（データ構造・概念）を共有している** 結合です。

- 例：注文サービスのドメインモデル `Order`（内部で使うフィールドも含めて）を、配送サービスがそのまま使う。共通ライブラリに全社共通の `Customer` クラスを置き、全サービスが使う
- モデルが変わる（フィールドの追加・名前変更・意味の変更）と、**結合しているすべてのモジュールが変更に巻き込まれる**
- モデル結合同士の強さは、**静的コナーセンス**（名前・型・意味・位置…）で比べられます。共有するモデルが大きく、意味の約束事が多いほど強い
- DDD が **1つの巨大なモデルより、境界づけられたコンテキストごとの専用モデル** を好むのは、モデル結合で広がる知識を小さくするためです（→ 42 の [[03_境界づけられたコンテキストとコンテキストマップ]]）

### (4) コントラクト結合（Contract Coupling）

**統合のためだけに設計された契約（コントラクト）を通して連携する** 結合です。最も弱く、最も明示的です。

- 契約の目的は、**実装の詳細だけでなく、内部の業務モデルや機能要件の知識までも包み隠す** こと
- 内部モデルが変わっても、契約を守れば相手には影響しない

| 契約結合を作るパターン | 内容 |
|---|---|
| **ファサード**（Facade） | 複雑な内部を、単純な入口の背後に隠す |
| **公開ホストサービス／公表された言語**（OHS / PL） | 提供側が、外部向けの安定した API とデータ形式を公開する |
| **腐敗防止層**（ACL） | 利用側が、相手のモデルを自分のモデルに翻訳する層を置く |
| **DTO**（Data Transfer Object） | 内部モデルとは別に、受け渡し専用の型を定義する |

```typescript
// 内部モデル（自由に変えてよい）
class Order { id; customer; items; internalRiskScore; status; /* ... */ }

// 契約（統合専用。変更は慎重に、バージョン管理する）
type OrderSummaryV1 = { orderId: string; status: 'PLACED' | 'SHIPPED'; totalYen: number };
```

> コントラクト結合でも結合はゼロではありません。契約のフィールド名・型（名前・型のコナーセンス）は共有しています。それでも **共有しているのは「共有するために設計した最小限の知識」だけ** なので、最も弱いとされます。

### 古典的な分類との対応（目安）

| 統合強度 | 構造化設計の結合度（[[02_結合度]]） | コナーセンス（[[04_コナーセンス]]） |
|---|---|---|
| 侵入結合 | 内容結合・共通結合に近い | （実装の詳細すべて） |
| 機能結合 | 制御結合などに近い。対称結合は「同じロジックの重複」 | 動的コナーセンス（実行順序・値）、アルゴリズム |
| モデル結合 | スタンプ結合・外部結合に近い | 静的コナーセンス（名前・型・意味・位置） |
| コントラクト結合 | データ結合に近い | 名前・型（最も弱い部類） |

※ この対応表は、各分類の定義を並べて比べた **目安** です。Khononov の本でも、統合強度は構造化設計の結合度とコナーセンスを土台に作られていますが、1対1で対応するものではありません。

### 判定のための問い

1. 相手の **非公開の部分**（内部 DB・private・ログ）に触れているか？ → Yes なら **侵入結合**
2. 相手と **同じ業務ルール・処理の順番・トランザクション** を共有しているか？ → Yes なら **機能結合**
3. 相手の **内部の業務モデル** をそのまま使っているか？ → Yes なら **モデル結合**
4. **統合のために設計された契約** だけを使っているか？ → Yes なら **コントラクト結合**

上から順に問い、最初に Yes になったものが、その連携の統合強度です。

---

## まとめ

- 統合強度は、境界を越えて共有される知識の量。強い順に **侵入 → 機能 → モデル → 契約**
- 機能結合の度合いは弱い順に **順序 → トランザクション → 対称**。対称結合（同じルールの重複）が最も見えにくく強い
- 契約結合は、ファサード・OHS/PL・ACL・DTO で作る
- 非同期にしても統合強度は下がらない（→ [[05_距離と変動性]]）
