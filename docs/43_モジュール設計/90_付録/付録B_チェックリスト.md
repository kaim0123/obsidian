# 付録B　モジュール設計チェックリスト（総合版）

設計レビュー・リファクタ前に使えるチェックリストです。

---

## 1. モジュール分割

- [ ] 各モジュールを **1 文** で説明できる
- [ ] モジュール名が **ユビキタス言語** と一致している
- [ ] `util` / `common` / `misc` に無関係な処理が溜まっていない
- [ ] 分割しすぎ（1 変更で 5 モジュール以上）でない
- [ ] 分割不足（1 モジュール 50 ファイル超）でない

---

## 2. 凝集度・結合度

- [ ] モジュール内のファイルは **同じ変化の理由** を持つ
- [ ] モジュール間は **インターフェース** 経由で通信
- [ ] **循環依存** がない
- [ ] **共有 DB テーブル** への直接アクセスがない
- [ ] 巨大 DTO の受け渡しを避け、必要最小限のデータ

---

## 3. 境界・カプセル化

- [ ] 公開 API は **最小限**（barrel / exports で制限）
- [ ] 内部型・ORM Entity を export していない
- [ ] domain が infra / フレームワークに依存していない
- [ ] Leaky Abstraction（内部詳細の漏れ）がない

---

## 4. 依存関係

- [ ] 依存の向きが **一方向**（内側に向かう）
- [ ] **DIP** — ドメインがポートを定義、infra が実装
- [ ] 依存グラフを **定期的に確認** している
- [ ] CI で依存ルールを **自動チェック** している（可能なら）

---

## 5. インターフェース

- [ ] 入出力・エラー・副作用が **明確**
- [ ] 公開 API 変更時に **後方互換** を考慮
- [ ] 命名が **意図を伝える**

---

## 6. テスト・品質

- [ ] domain が **DB なし** で単体テスト可能
- [ ] application が **Fake ポート** でテスト可能
- [ ] 副作用が **infra に局所化** されている
- [ ] テストが書きにくい箇所に **設計問題** がないか確認

---

## 7. チーム・運用

- [ ] モジュール設計ルールが **文書化** されている
- [ ] コードレビューで **境界・依存** を見ている
- [ ] 設計負債が **可視化** されている
- [ ] 大きな境界変更前に **設計レビュー** がある

---

## 8. 変更シナリオ（What-If）

| シナリオ | 触るモジュールは妥当か |
|---------|----------------------|
| 決済 API の差し替え | payment のみ（+ 設定） |
| 注文キャンセルルール変更 | order のみ |
| UI を REST から gRPC に | web/adapter のみ |
| 新ドメイン「クーポン」追加 | 新モジュール or 既存のどちらか明確 |
