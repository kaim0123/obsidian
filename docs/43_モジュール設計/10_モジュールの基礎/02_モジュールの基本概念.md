# モジュールの基本概念

## この章の目的

**モジュール** とは何か、関数・クラス・パッケージとの関係、**境界・責務・インターフェース** の基本を押さえる章です。  
以降の章で繰り返し使う言葉の定義をここで固めます。

---

## 1. モジュールとは何か

**モジュール** とは、ソフトウェアを **ひとまとまりの部品** として扱う単位です。  
言語やプロジェクトによって、次のような形で現れます。

| 形 | 例 |
|----|-----|
| パッケージ | Java の `com.example.order` |
| ディレクトリ | `src/order/` |
| 名前空間 | C# の `namespace Order` |
| サービス（論理） | 「注文サービス」モジュール |

```text
  アプリケーション
  ┌─────────────────────────────┐
  │  [Order]  [User]  [Payment] │  ← モジュール
  │     │        │         │    │
  │  クラス群  クラス群   クラス群 │
  └─────────────────────────────┘
```

モジュールは **「外から見える単位」** です。中身の詳細は隠し、決めた入口だけを公開します。

---

## 2. 関数・クラス・パッケージ・サービスとの関係

| 単位 | 粒度 | モジュールとの関係 |
|------|------|-------------------|
| 関数 | 最小 | モジュール **内部** の処理 |
| クラス | 小 | モジュールを構成する部品 |
| パッケージ / ディレクトリ | 中 | モジュールの **物理的な表現** が多い |
| サービス（マイクロサービス） | 大 | 独立デプロイされる **モジュールの極端な形** |

```text
  モジュール Order
  ├── OrderService.java      （クラス）
  ├── OrderRepository.java   （クラス）
  └── calculateTotal()       （関数・メソッド）
```

**1 モジュール = 関連するクラス・関数の集まり + 公開インターフェース** と考えるとよいです。

---

## 3. 責務（Responsibility）という考え方

**責務** とは、そのモジュールが **担当すべき仕事** です。

- 良い例: `Payment` モジュール → 「支払い処理と決済連携」
- 悪い例: `Common` モジュール → 「なんでも」

| 問い | 意図 |
|------|------|
| このモジュールは **何のため** に存在するか | 1 文で説明できるか |
| 変化の理由は **1 つ** にまとまるか | 分割・統合の判断材料 |

責務が曖昧なモジュールは、時間とともに **ゴミ箱** になりやすいです。

---

## 4. 境界（Boundary）と内部・外部

**境界** は、モジュールの **内側と外側** を分ける線です。

```text
        外部（他モジュール）
              │
    ──────────┼──────────  ← 境界（公開 API）
              │
        内部（実装の詳細）
        ・private クラス
        ・DB アクセスの具体
        ・内部ヘルパー
```

- **内部**: 自由に変更してよい（外に影響しない限り）
- **外部**: 公開インターフェース。**変更は慎重に**

境界がないと、他モジュールが内部実装に直接依存し、**結合度** が上がります。

---

## 5. インターフェースと実装の分離

モジュールは **インターフェース（契約）** と **実装（中身）** を分けて設計します。

```typescript
// インターフェース（境界の外側に見える契約）
interface OrderRepository {
  findById(id: string): Promise<Order | null>;
  save(order: Order): Promise<void>;
}

// 実装（境界の内側・差し替え可能）
class PostgresOrderRepository implements OrderRepository {
  // ...
}
```

| 分離する理由 | 効果 |
|-------------|------|
| 実装を隠す | 内部変更が他モジュールに波及しにくい |
| 契約を固定する | 呼び出し側のコードが安定する |
| 差し替え | テスト用の偽実装（モック）を入れやすい |

詳細は [[01_モジュール間インターフェースの設計]] で深掘りします。

## 6. モジュールが持つ3つの基本的な性質：機能・ロジック・コンテキスト

Vlad Khononov『ソフトウェア設計の結合バランス』（原著 *Balancing Coupling in Software Design*、2024）の第4章「結合とモジュール性」では、モジュールを **機能（Function）・ロジック（Logic）・コンテキスト（Context）** の3つの性質で捉えます。

> **モジュールとは、明確に定義された機能を囲む境界であり、その機能をシステムの他の部分に公開するもの** である。

| 性質 | 何か | 外から見えるか | ひとことで |
|---|---|---|---|
| **機能（Function）** | モジュールの目的。提供する機能 | **公開**（公開インターフェースで表現） | **何をするか** |
| **ロジック（Logic）** | 機能を実現するための実装と設計判断のすべて | **隠す**（境界で守る） | **どうやってするか** |
| **コンテキスト（Context）** | モジュールが使われる環境についての、明示的な要件と暗黙の前提 | 公開だが、**インターフェースには現れにくい** | **どんな状況で使う前提か** |

### 6.1 身近な例で理解する

本で使われている例です。

| | レゴブロック | 交換レンズ（カメラ） |
|---|---|---|
| **機能** | 他のブロックとつながる（上のポッチと下の穴＝接続インターフェース） | 特定の焦点距離・絞りで画像をとらえる |
| **ロジック** | 丈夫な構造を支え、確実にくっつくプラスチック素材 | カメラとつながり、光学効果を生む内部の機構 |
| **コンテキスト** | 子ども向けの安全なおもちゃ。**本物の家を建てるためのものではない** | 対応するカメラの機種。オートフォーカスが使えるかどうかは機種による |

ソフトウェアで言うと、たとえば次のようになります。

```typescript
// 機能：公開メソッドが「何ができるか」を表す
interface CustomerRepository {
  load(id: string): Promise<Customer>;
  save(customer: Customer): Promise<void>;
  findByName(name: string): Promise<Customer[]>;
  findByPhone(phone: string): Promise<Customer[]>;
}
// ロジック：RDB でも、ドキュメント DB でも、複数の DB の組み合わせでもよい。利用者は知らなくてよい
// コンテキスト：例えば「呼び出しは認証済みである前提」「同時アクセスは少ない前提」など。シグネチャには書かれない
```

### 6.2 3つの性質と結合の関係

- **機能だけを知って使える** なら、結合は弱い（契約結合・データ結合）
- **ロジックを知らないと使えない**（DB を直接読む、内部クラスを使う）なら、結合は強い（侵入的結合・内容結合）
- **コンテキストは見落とされやすい**。インターフェースに現れないため、「いつの間にか前提が崩れて壊れる」原因になる

### 6.3 設計・レビューでの問い

- そのモジュールの **機能（目的）を、ロジック（実装の詳細）に触れずに説明できる** か？
- そのモジュールの **使われ方の前提（コンテキスト）は明示されている** か？ それとも、いずれ忘れられる暗黙の前提になっていないか？

> 4節の「境界の外 ＝ インターフェース、内 ＝ 実装」は、**機能（外）とロジック（内）** の区別にあたります。コンテキストは、そのどちらにも書かれにくい **第3の要素** として意識しておくと、設計の抜け漏れに気づきやすくなります。

## 7. モジュール化は多層的に行われる：サービス・パッケージ・サブパッケージ・オブジェクト

2節では「関数・クラスはモジュールの **内部**」と整理しました。これは「業務単位のモジュール」を中心に見た場合の言い方です。Khononov はもっと広く、

> **独立した単位として切り出せる可能性があるなら、それはモジュールである。**

と考えます。つまり、**サービスもパッケージもクラスもメソッドも、それぞれがモジュール** です。そして、モジュールは平らに並ぶのではなく、**入れ子（階層）** になっています。

```text
 システム
 └─ サービス（注文サービス）              ← モジュール
     └─ パッケージ（order）               ← モジュール
         └─ サブパッケージ（order/billing）← モジュール
             └─ オブジェクト（Invoice）   ← モジュール
                 └─ メソッド（total()）   ← モジュール
```

### 7.1 どの層にも「機能・ロジック・コンテキスト」がある

| 層 | 機能（公開するもの） | ロジック（隠すもの） | コンテキスト（前提）の例 |
|---|---|---|---|
| **サービス** | REST API・メッセージなどの公開契約 | ソースコード、内部の DB・メッセージバス | 実行環境、計算資源、ネットワーク帯域、「呼び出しは認証済み」 |
| **パッケージ** | 公開されたクラス・関数（`index.ts` で export するもの） | 非公開のクラスと、その協調の仕方 | パッケージ全体が前提とする設定・ランタイム |
| **サブパッケージ** | 親パッケージ内の他の部分に見せるもの | サブパッケージ内部の実装 | 親パッケージの中だけで使われる前提 |
| **オブジェクト（クラス）** | public なメソッド・プロパティ | private なフィールド・メソッド、データの保存方法 | 呼び出し順序、スレッド安全性の前提など |
| **メソッド（関数）** | 名前とシグネチャ | メソッドの本体、private なヘルパー | 引数の前提（null でない等）、必要な状態 |

※ サービスとオブジェクトの機能・ロジックの例は本の記述に基づきます。コンテキスト列の多くと、パッケージ・サブパッケージの行は、同じ考え方を当てはめた補足です。

### 7.2 フラクタル（自己相似）な構造

どの層も「境界・公開インターフェース・隠された実装」という **同じ形** をしています。拡大しても縮小しても同じ模様が現れる図形（フラクタル）に似ているので、Khononov はこれを **ソフトウェア設計のフラクタル的な性質** と呼びます（本の第III部にも「ソフトウェア設計のフラクタル幾何学的性質」という章があります）。

ここから分かる大事なことは2つです。

1. **同じ原則がどの層にも使える**
   情報隠蔽・高凝集・疎結合・バランス結合は、メソッドの設計にもサービスの設計にも使えます。「設計」と「アーキテクチャ」に本質的な境目はなく、**見ている縮尺が違うだけ** です。
2. **ある層の「外の複雑さ」は、1つ上の層では「中の複雑さ」になる**
   クラス同士のつながり（クラスの外の複雑さ）は、パッケージから見れば内部の問題です。だから、**モジュールを分けるだけでは複雑さは消えず**、上の層に押し上げられるだけのこともあります（→ [[03_バランス結合_強度・距離・変動性]] の「分散した複雑さ」）。

### 7.3 実務でのヒント

- 「モジュール」という言葉を見たら、**いまどの層の話をしているか** を確認する
- 各層で「機能を、ロジックに触れずに説明できるか」を確かめる。メソッド名で中身が説明できない、パッケージの公開 API が内部クラスだらけ、などは境界がうまく引けていないサイン
- 下の層ほど変更コストが小さい（同じファイル内）。上の層ほど大きい（別チーム・別デプロイ）。**強く結びつくものほど、下の層（近い場所）にまとめる**

---

## まとめ

- **モジュール** = 責務を持つ、境界で囲まれた部品の塊
- 関数・クラスはモジュール **内部**、パッケージ・ディレクトリはモジュールの **表現**
- **責務** が明確だと分割・命名・レビューがしやすい
- **境界** の外はインターフェース、内は実装 — この分離がモジュール設計の基本
- モジュールの3つの性質：**機能**（何をするか・公開）、**ロジック**（どうやるか・隠す）、**コンテキスト**（どんな前提で使うか・暗黙になりがち）
- モジュール化は **サービス → パッケージ → サブパッケージ → オブジェクト → メソッド** と多層的（フラクタル）に行われ、どの層にも同じ原則が使える
